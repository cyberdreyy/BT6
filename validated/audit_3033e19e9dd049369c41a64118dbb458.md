### Title
Builder withdrawal amount is minted uncapped by the EL while the CL only debits `min(amount, balance)`, allowing supply inflation - (File: `specs/gloas/beacon-chain.md`)

### Summary
This is the consensus-specs analog of the C4 finding "use `safeTransfer`/`safeTransferFrom` consistently" (unchecked return value → silent transfer failure → broken accounting). In `LaunchEvent.sol`, a token `transfer`/`transferFrom` call could silently fail while the contract's bookkeeping still assumed the transfer succeeded, breaking the equality between "tokens moved" and "tokens accounted for." In Gloas (`specs/gloas/beacon-chain.md`), the equivalent equality — "amount debited from a builder's CL balance" == "amount the execution layer is committed to mint/pay to the fee_recipient" — is broken the same way: the withdrawal amount queued for the execution layer is never capped to the builder's actual balance, while the CL-side deduction silently saturates.

### Finding Description
`get_builder_withdrawals` copies the *requested* amount straight from `state.builder_pending_withdrawals` into the `Withdrawal` object that becomes part of `state.payload_expected_withdrawals` (and ultimately the execution payload's withdrawals list, which the EL is required to honor by minting/paying `withdrawal.amount` to `withdrawal.address`): [1](#0-0) 

No `min(..., builder.balance)` cap is applied here — unlike the analogous validator-sweep code, which caps partial-withdrawal amounts to available balance before constructing the `Withdrawal`.

`apply_withdrawals` then performs the actual CL-side deduction, and *there* it silently caps the debit: [2](#0-1) 

```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
```

This is exactly the "silent failure instead of `require`/`safeTransfer`" pattern from the report: instead of asserting that `withdrawal.amount <= builder.balance` (the "require" analog) or capping the *committed* amount to what can actually be paid from the builder's balance (the "safeTransfer" analog), the spec lets the committed `Withdrawal.amount` stay at the full, possibly-unbacked value while the balance-side bookkeeping just saturates at zero.

The repository's own test suite documents this exact scenario as expected behavior rather than treating it as an invariant violation: [3](#0-2) 

```
Input State Configured:
    - state.builders[0]: Builder exists with only 1 ETH balance
    - builder_pending_withdrawals: Contains 1 entry requesting 5 ETH
    - builders[0].balance: 1 ETH (insufficient for requested 5 ETH)

Output State Verified:
    - payload_expected_withdrawals: Contains 1 withdrawal
    - withdrawal.amount: 5 ETH (requested amount)      <-- full 5 ETH is what EL must pay
    - builders[0].balance: 0 (deduction capped to available balance)  <-- only 1 ETH is debited
```

So `state.payload_expected_withdrawals` commits the block (and hence the execution layer, which is contractually required to honor these withdrawals) to paying out 5 ETH to `fee_recipient`, while the consensus layer only ever removed 1 ETH from the builder's stake. The other 4 ETH is paid to a non-owner (the fee_recipient) without being backed by any decrease anywhere in `state.builders[*].balance` or `state.balances[*]` — new Gwei effectively enters circulation on the EL side with no corresponding CL-side debit, breaking the invariant that the sum of committed withdrawal amounts must equal the sum of balance decreases.

The pathway for a builder's balance to fall below a previously-committed pending-withdrawal amount is architecturally supported: a bid is only checked for sufficient balance at bid-acceptance time via `can_builder_cover_bid`/`process_execution_payload_bid`, but the resulting `BuilderPendingWithdrawal` may sit in `state.builder_pending_payments`/`state.builder_pending_withdrawals` for a variable number of slots/epochs before `settle_builder_payment` or the sweep in `process_withdrawals` finally consumes it: [4](#0-3) 

During that window multiple additional bids/withdrawal requests against the same builder can be accepted and queued (each individually checked against the balance *at accept time*, not against the cumulative total that will eventually be owed), so by the time all queued withdrawals are drained via `apply_withdrawals`, the aggregate committed amount can exceed the builder's real balance.

### Impact Explanation
This falls under "a payload or payment applied that the block did not commit to" / "Gwei created ... paid to a non-owner" (Critical) per the scan's impact taxonomy: the execution layer mints/pays the fee_recipient the full requested withdrawal amount that the consensus layer, by its own accounting, never actually backed with a real balance decrease past the point of saturation. This is a genuine equality break between the CL's committed withdrawal list and the CL's own balance ledger, not merely a documentation quirk — the spec even documents (in the surrounding `process_withdrawals` note) that such saturation "creates a net supply inflation," but that note is scoped to validator/consolidation interactions, not to this builder-specific uncapped-amount pattern, which has no analogous mitigating note and no assertion preventing it.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires no external validator/attacker collusion — a single builder that accepts/queues withdrawal commitments (via bid settlement, and via `BuilderExitRequest`/sweep interactions) faster than its balance can support, or whose balance is reduced by concurrent processing (e.g. multiple pending payments settling in the same epoch window) before the withdrawal is applied, triggers this on its own. No malicious peer, coalition, or client bug is needed — it is entirely reachable purely from valid, spec-following state transitions given adversarial-but-permitted ordering of a single builder's bids/exits.

### Recommendation
Cap the `amount` field written into the `Withdrawal` object in `get_builder_withdrawals` to `min(withdrawal.amount, builder.balance)` at construction time (mirroring how validator partial withdrawals are capped before being queued), so the amount committed to the execution layer can never exceed what `apply_withdrawals` is actually able to debit. Alternatively, assert `withdrawal.amount <= builder.balance` when appending to `builder_pending_withdrawals`/`builder_pending_payments`, and re-validate/cap cumulative committed pending amounts against current caller balance before each withdrawal is added to the queue.

### Proof of Concept
1. Builder `B` deposits/holds balance `X`.
2. `B` submits (and has accepted) bid 1 with value `v1`; `can_builder_cover_bid` passes since balance at that time `>= v1 + existing pending`. Payment settles into `builder_pending_withdrawals` with `amount = v1`.
3. Before that withdrawal is swept by `process_withdrawals`, `B` submits and gets accepted bid 2 with value `v2`, again individually validated against balance at acceptance time (which may not yet reflect `v1`'s future debit) — `v1 + v2 > X` in aggregate.
4. Multiple `BuilderPendingWithdrawal` entries queue up whose *sum* exceeds `X`.
5. When `process_withdrawals` -> `get_builder_withdrawals` runs, each `Withdrawal.amount` is copied verbatim (uncapped) into `payload_expected_withdrawals`, e.g. total requested `= v1 + v2 > X`.
6. `apply_withdrawals` debits `min(amount, current_balance)` per entry — the balance saturates to 0 partway through, but the full uncapped `v1 + v2` remains in `state.payload_expected_withdrawals`, which the execution layer is required to pay out to the respective `fee_recipient`s (as demonstrated directly by the existing test `test_builder_withdrawal_insufficient_balance`, which asserts `withdrawal.amount == 5 ETH` while `builders[0].balance` only ever held and lost 1 ETH).
7. Net result: `4 ETH` (in that concrete example) is paid out on the execution layer that was never backed by any consensus-layer balance decrease — an unbacked payment / effective Gwei creation.
