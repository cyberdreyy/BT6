### Title
LDAP Bind DN injection via unescaped comma in Email field allows authentication against an unintended directory entry - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.CreateSession` builds the LDAP Bind DN by string-concatenating the user-supplied `Email` field after only applying `ldap.EscapeFilter`, which escapes LDAP *search-filter* metacharacters, not LDAP *DN* metacharacters (comma, `+`, `"`, `\`, `<`, `>`, `;`). An attacker who controls the `Email` field of a `POST /sessions` request can inject extra RDN components into the Bind DN, causing the Bind (and the subsequently cached identity) to resolve to a directory entry other than the one implied by the submitted email.

### Finding Description
The HTTP handler `SessionsController.Create` (`core/web/sessions_controller.go:29-68`) unmarshals the request body directly into `sessions.SessionRequest{Email, Password, ...}` [1](#0-0)  with no email-format validation, then forwards it unchanged to `AuthenticationProvider().CreateSession(ctx, sr)` [2](#0-1) . The `SessionRequest.Email` field itself has no validation constraints [3](#0-2) .

In `ldapAuthenticator.CreateSession` the Bind DN is constructed as:
```go
escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
if err = conn.Bind(searchBaseDN, sr.Password); err != nil { ... }
``` [4](#0-3) 

`ldap.EscapeFilter` only escapes RFC 4515 filter metacharacters (`*`, `(`, `)`, `\`, NUL) — it does not escape DN separator/metacharacters such as `,`. Because the escaped email is spliced directly into a DN string via `fmt.Sprintf`, a value like `victim,ou=admins,dc=example,dc=com` (or any comma-containing local part) inserts additional RDN components, changing which entry the constructed DN resolves to relative to what the caller intended. The resulting `searchBaseDN` is passed straight into `conn.Bind`, so the LDAP server's Bind call is performed against an attacker-influenced DN rather than the DN literally corresponding to `BaseUserAttr=<email>,<UsersDN>,<BaseDN>`.

Subsequently, `l.FindUser(ctx, escapedEmail)` is used to resolve role/session identity from the *unmodified, comma-containing* `escapedEmail` string via a filter search (not the Bind DN) [5](#0-4) . This creates a split: the entry actually authenticated against by `conn.Bind` can differ from the entry whose attributes/roles are looked up and cached into `ldap_sessions`, i.e., request binding of "one authenticated identity to one session" is violated — the session's cached email/role can diverge from the directory entry that was actually Bound.

No layer between the HTTP request and `conn.Bind` sanitizes or rejects DN metacharacters in `Email`.

### Impact Explanation
This falls under authentication/request-impersonation impact: the LDAP Bind can be redirected to resolve against a directory entry other than the one implied by the supplied email, and the cached session identity (email/role written to `ldap_sessions`) is derived from a string that does not correspond 1:1 to the DN actually authenticated. In environments with nested/multiple OUs under the configured `UsersDN`/`BaseDN`, this enables authentication-target confusion and违反 identity binding of the request, potentially resulting in a session created with a role/identity different than the credentials used.

### Likelihood Explanation
The attacker needs only unauthenticated network access to `POST /sessions` and does not need any prior privilege on the node — they need a valid LDAP-bindable credential pair (any account whose password they know) where the local part (or attacker-controlled `Email` field) can contain a comma reaching an alternate, structurally valid DN under the same base tree. This is fully attacker-controlled at the HTTP layer (no client-side validation of `Email` format) and is reproducible deterministically via a mocked `LDAPConn.Bind`.

### Recommendation
Do not build the Bind DN via raw string concatenation of user input. Either:
- Validate `sr.Email` against a strict email-format regex and reject any value containing DN metacharacters (`,`, `+`, `"`, `\`, `<`, `>`, `;`, leading/trailing spaces, `#`) before use, or
- Use a proper LDAP DN-escaping function (escape DN attribute values per RFC 4514, not `EscapeFilter`, which is for filters only) when constructing `searchBaseDN`, or
- Resolve the user's DN via an authenticated Search (using `EscapeFilter` correctly in a filter, e.g. `(&(objectClass=...)(<BaseUserAttr>=<escapedEmail>))`) scoped under `UsersDN`/`BaseDN`, and Bind using the DN literally returned by the LDAP server rather than one assembled from user input.

### Proof of Concept
Go unit test plan (extends `core/sessions/ldapauth/ldap_test.go` style with the existing `LDAPConn` mock):
1. Configure `config.LDAP` mock with `BaseUserAttr()="uid"`, `UsersDN()="ou=users"`, `BaseDN()="dc=example,dc=com"`.
2. Build `sr := sessions.SessionRequest{Email: "victim,ou=admins,dc=example,dc=com", Password: "attackerpw"}`.
3. Mock `LDAPConn.Bind` to capture the `username` (DN) argument passed in.
4. Call `ldapAuthenticator.CreateSession(ctx, sr)`.
5. Assert that the captured Bind DN string is `uid=victim,ou=admins,dc=example,dc=com,ou=users,dc=example,dc=com` (or similar) — i.e., contains extra unescaped RDN components derived from the comma in `Email`, rather than a single-valued `uid=<escaped-email>,ou=users,dc=example,dc=com`.
6. Assert this proves the effective Bind target diverges from `BaseUserAttr=<full email>,UsersDN,BaseDN`, demonstrating DN injection due to `ldap.EscapeFilter` not escaping DN metacharacters at `core/sessions/ldapauth/ldap.go:406-408`.
