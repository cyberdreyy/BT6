### Title
Stale confirmations from removed multisig members are not purged and still count toward the confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` only deletes pending requests that were *originated* by the removed member, but it never scans existing `confirmations` sets to strip out that member's prior approvals recorded on *other* members' requests. Because `confirm()` simply counts entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set against `num_confirmations`, a confirmation cast by an account that has since been removed from `members` still counts toward quorum, letting a request execute with fewer genuine, currently-live approvals than `num_confirmations` requires.

### Finding Description
`confirm()` checks only that the request exists and that the confirming key is a *current* member, then adds the confirming member's string id to `confirmations` for that request and executes once `confirmations.len() + 1 >= num_confirmations`: [1](#0-0) 

`delete_member` removes the member from `self.members` and cleans up only requests whose *originator* (`r.member`) equals the removed member — it does not touch `confirmations` entries recorded by that member on requests it did not originate: [2](#0-1) 

Sequence:
1. Members = {A, B, C, D}, `num_confirmations = 3`.
2. Member `A` (colluding/compromised) calls `add_request` to create request `R` and `confirm(R)` — `confirmations[R] = {A}`.
3. The multisig separately votes to remove `A` (a `DeleteMember` request executed via `delete_member`). This removes `A` from `self.members`, but `R`'s entry in `confirmations` still contains `"A"`, because `delete_member`'s cleanup loop only filters by `r.member == member`, i.e. requests A itself created, not confirmations A cast on requests created by someone else.
4. Now with only {B, C, D} as live members, `B` and `C` call `confirm(R)`. After `B`'s confirm, `confirmations[R] = {A, B}` (len 2). After `C`'s confirm, `len + 1 = 3 >= num_confirmations(3)` → `remove_request` + `execute_request` runs.
5. `R` executes (e.g. a `Transfer`) having been approved by only 2 currently-live members (`B`, `C`) plus one stale confirmation from a member (`A`) who is no longer part of the multisig.

This breaks the intended equality `confirmations counted == confirmations from live members`: the contract executes an action believing it has 3 independent, currently-authorized approvals, when in reality only 2 live members approved it.

### Impact Explanation
This is a threshold-bypass on a NEAR multisig wallet: a request (including `Transfer`, `AddKey`, `FunctionCall`, or another `DeleteMember`/`AddMember`) can be executed with fewer live-member confirmations than `num_confirmations` mandates, because a removed member's stale vote is silently retained and counted. This maps to the "multisig request executed below threshold" Critical impact category — funds can be moved, or membership/threshold can be further manipulated, with genuine consent below the configured security threshold.

### Likelihood Explanation
The attack requires no privileged access beyond being (or having been) a legitimate multisig member at some point — a scenario the multisig is explicitly designed to survive (member removal is the standard mechanism for revoking a compromised or malicious member's authority). Any member who is later removed (e.g., after key compromise, departure, or malicious behavior discovered) can leave behind pre-existing confirmations on any request still pending; if that request is later completed by fewer than `num_confirmations` *remaining* members, it still executes. The bug is triggered by the normal member-removal + pending-request lifecycle, not by exotic conditions, making it readily reachable.

### Recommendation
When removing a member in `delete_member`, iterate over all active requests' `confirmations` sets (not just the ones the removed member originated) and remove that member's entry from each. Alternatively, recompute/validate confirmations against the current `members` set at `confirm()`/execution time (filter out confirmers no longer in `self.members` before comparing against `num_confirmations`), ensuring the count used for the threshold check only reflects currently live members.

### Proof of Concept
Building on the existing test harness in `multisig2/src/lib.rs` tests module:
1. Create `MultiSigContract::new(members(), 3)` with members `{A, B, C, D}`.
2. As `A`, call `add_request_and_confirm(request_transferring_funds_to_attacker)` → `confirmations[R] = {A}`.
3. As sufficient members, submit and confirm a separate `DeleteMember { member: A }` request until executed → `A` removed from `self.members`; `R` and its confirmations remain untouched (loop in `delete_member` only matches `r.member == A`, and `R.member == A` originator check would actually catch this specific case since A originated R — to make A NOT the originator, have `B` create `R` and only `A` confirm it, then remove `A`).
4. As `B`, call `confirm(R)` → `confirmations[R] = {A, B}` (len 2).
5. As `C`, call `confirm(R)` → `len()+1 = 3 >= num_confirmations(3)` → request executes, despite only `B` and `C` being live members who actually approved it (plus the stale, no-longer-authorized `A`). [1](#0-0) [2](#0-1)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
