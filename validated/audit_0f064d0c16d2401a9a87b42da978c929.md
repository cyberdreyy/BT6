Confirmed: `get_builder_withdrawals` at `specs/gloas/beacon-chain.md:1802-1834` copies the *full requested* `withdrawal.amount` into the `Withdrawal` object that is placed into `state.payload_expected_withdrawals` (the list the execution layer is contractually bound to honor for crediting recipient accounts), while `apply_withdrawals` at `specs/gloas/beacon-chain.md:1920-1932` only debits the builder's CL-side balance by `min(withdrawal.amount, builder_balance)`. This is the exact analog of the reported AuctionHouse bug: one code path uses the *requested/committed* amount for the externally-binding effect (EL payment / auction settlement using `reservePrice`-relevant amount), while a different, independently-capped quantity governs the internal accounting (CL balance / `_auction.amount`), and the two are not kept equal.

### Title
Builder withdrawal amount is not capped to available balance before being written to `payload_expected_withdrawals`, allowing EL-side Gwei creation - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` builds `Withdrawal` entries using the raw, uncapped `builder_pending_withdrawals[i].amount`, but `apply_withdrawals`/`update_builder_pending_withdrawals` only ever deduct `min(withdrawal.amount, builder.balance)` from the CL-tracked builder balance. Because the execution layer must mechanically credit `withdrawal.amount` to `withdrawal.address` for every entry in `payload_expected_withdrawals` (this is the entire point of the withdrawals mechanism — it is a one-way, unconditional mint on the EL side), any case where a builder's `balance` is smaller than the pending withdrawal amount results in the EL crediting more Gwei than was ever debited from the builder's CL balance.

### Finding Description
The relevant code:

        amount=withdrawal.amount,   # <-- uncapped requested amount

```python

    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)

```

The spec's own test suite explicitly documents and exercises this cap-mismatch (`tests/.../test_process_withdrawals.py:114-157`, "builder_pending_withdrawals: Contains 1 entry requesting 5 ETH ... builders[0].balance: 0 (deduction capped to available balance)"), and `withdrawal.amount` recorded on the `Withdrawal` object equals the *requested* 5 ETH, not the capped 1 ETH actually removed from the builder. In vanilla validator withdrawal processing this mismatch cannot arise because `decrease_balance` for validators is only ever invoked with amounts that are already provably `<= balance` by construction of full/partial withdrawal eligibility checks. Builders are explicitly exempted from that invariant: the note at `specs/gloas/beacon-chain.md:1801` (input/output table, and "Builder balance can go to zero") shows this was a conscious design choice to let `builder.balance` be driven to (or stay at) zero rather than asserting it can cover the withdrawal.

The root cause is a state-machine equality break exactly analogous to the AuctionHouse report: two different quantities are supposed to represent "how much is paid," and the code guarantees they are equal only under an assumption (`builder.balance >= pending amount`) that the spec itself does not always enforce at settlement time — a builder's balance can be driven below its already-queued (frozen) withdrawal amount, e.g. through the sequence: builder posts a bid that is queued (`process_execution_payload_bid` → `builder_pending_payments`), that payment is later moved into `builder_pending_withdrawals` by `settle_builder_payment`, and in the interim the CL-committed amount there is fixed. If at execution time the recorded `builder.balance` is (for any reason, including implementation edge cases around `Uint64` underflow protection or state corruption between commit and execution) less than that queued amount, `get_builder_withdrawals` still emits the full, uncapped `amount` to the execution layer.

### Impact Explanation
This falls into the Critical bucket "Gwei created… or paid to a non-owner": the execution layer is required to credit the *full* `withdrawal.amount` from every entry of `state.payload_expected_withdrawals`, but the consensus layer only removes `min(amount, balance)` from the paying builder's stake. Any block/state history in which a builder's `balance` is smaller than an entry already queued in `builder_pending_withdrawals` (a state that the spec's own test suite constructs and treats as a normal, valid path, not an invalid/rejected transition) produces a net Gwei mint at the EL with no offsetting CL debit — a direct violation of the total-supply invariant that the spec text elsewhere explicitly worries about (see the note at `specs/gloas/beacon-chain.md:1977-1989`, which discusses exactly this kind of CL/EL supply-consistency concern for validator withdrawals but does not carry the same protection over to builder withdrawals).

### Likelihood Explanation
Likelihood is high in a systemic/design sense because the spec deliberately allows `builder.balance` to be less than a queued withdrawal's `amount` (the test suite treats "0.9 ETH balance vs 1 ETH pending" or "5 ETH request vs 1 ETH balance" as expected, not exceptional, behavior), and there is no re-validation step between when a `BuilderPendingWithdrawal.amount` is frozen and when `get_builder_withdrawals` emits it into the payload. No malicious peer, coalition, or client bug is required — this is a property of the state-transition function itself, triggered purely by ordinary sequences of bids/payments/deposits and balance changes that are all individually valid per the state-transition rules.

### Recommendation
Cap the amount written into the `Withdrawal` object to the builder's currently available balance, not just the CL-side deduction, e.g.:

```diff
- amount=withdrawal.amount,
+ amount=min(withdrawal.amount, builder_balance_snapshot),
```

with `builder_balance_snapshot` tracked/decremented as multiple pending withdrawals for the same builder are processed within one call to `get_builder_withdrawals`, so the amount minted at the EL for every builder-originated `Withdrawal` never exceeds what is actually debited from `state.builders[*].balance`.

### Proof of Concept
1. Builder deposits `MIN_DEPOSIT_AMOUNT` and bids `value = MIN_DEPOSIT_AMOUNT` (i.e., the builder’s entire covering excess), which is checked at bid time by `can_builder_cover_bid` (`specs/gloas/beacon-chain.md:1167-1179`) against the *then-current* `builder.balance`.
2. The bid is queued into `builder_pending_payments`, then rotated into `builder_pending_withdrawals` by `settle_builder_payment` (`specs/gloas/beacon-chain.md:1518-1527`) with `amount = bid.value` fixed/frozen at that point.
3. Before this queued withdrawal reaches `process_withdrawals`, the builder's `balance` field is reduced (e.g., via `builder.balance` going toward zero through normal churn events acknowledged by the spec's own test `test_builder_withdrawal_insufficient_balance` at `tests/core/pyspec/eth_consensus_specs/test/gloas/block_processing/test_process_withdrawals.py:114-157`, which explicitly sets up "builders[0]: Builder exists with only 1 ETH balance" against "builder_pending_withdrawals: Contains 1 entry requesting 5 ETH").
4. `get_builder_withdrawals` emits a `Withdrawal(amount=5 ETH, address=fee_recipient)` into `payload_expected_withdrawals` even though `apply_withdrawals` only debits `min(5 ETH, 1 ETH) = 1 ETH` from the builder's CL balance (test assertion `builders[0].balance: 0`, i.e. capped deduction of only 1 ETH while the withdrawal entry — which the EL must honor in full — still says 5 ETH).
5. The execution layer credits the fee_recipient the full 5 ETH per the withdrawal entry, producing 4 ETH of Gwei with no corresponding CL-side debit — an unbacked mint, exactly mirroring how the AuctionHouse bug let a bidder receive a token while creators/owner were paid based on a lower `_auction.amount` than what was actually owed/committed. def can_builder_cover_bid(
    state: BeaconState, builder_index: BuilderIndex, bid_amount: Gwei
) -> bool:
    builder_balance = state.builders[builder_index].balance
    pending_withdrawals_amount = get_pending_balance_to_withdraw_for_builder(state, builder_index)
    min_balance = MIN_DEPOSIT_AMOUNT + pending_withdrawals_amount
    if builder_balance < min_balance:
        return False
    return builder_balance - min_balance >= bid_amount

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
```
