### Title
Unprivileged pubsub subscription can starve the shared `RecentItems` buffer and force-disconnect other subscribers - (File: `rpc/src/rpc_subscriptions.rs`)

### Summary
The `RpcSubscriptions` notifier keeps notification payloads alive for delivery to slow websocket clients in a single, globally-shared `RecentItems` ring buffer bounded by item count and byte size (`queue_capacity_items`/`queue_capacity_bytes`, shared across *all* pubsub connections). Any one unprivileged client's subscription (e.g., a `programSubscribe`/`blockSubscribe` on a busy account/program) can generate enough notification volume/size to evict entries that other, unrelated clients' slower websocket connections have not yet consumed. When that happens the other clients' `Weak<String>` references fail to upgrade and their connections are forcibly closed by the server. This mirrors the Vault bug class: one user's heavy, otherwise-legitimate usage of a shared bounded resource blocks/harms other users relying on the same resource.

### Finding Description
`RpcSubscriptions::new_with_config` creates a single `broadcast::channel` and a single `RecentItems` buffer shared by every websocket connection on the pubsub server: [1](#0-0) 

`RecentItems::push` evicts from the front of a shared `VecDeque` whenever the combined size of *all* subscribers' notifications (across the whole node) exceeds `max_len` or `max_total_bytes`: [2](#0-1) 

The actual JSON payload sent over `broadcast::Sender` is only referenced weakly (`json: Weak<String>`); the only strong reference keeping it alive long enough for a slow reader to consume it is the one held inside `RecentItems`: [3](#0-2) 

On the connection-handling side, if a subscriber's websocket task is scheduled slightly behind and its corresponding entry has already been evicted from `RecentItems` by other traffic, `Weak::upgrade()` fails and the handler returns `Error::NotificationIsGone`, which is propagated with `?` and terminates that client's connection: [4](#0-3) [5](#0-4) 

Because `queue_capacity_items`/`queue_capacity_bytes` are global caps shared by every connection/subscription type on the validator (not per-connection or per-client quotas), a single unprivileged client subscribing to a high-churn or large-payload feed (`programSubscribe` on a busy program, `blockSubscribe`, `logsSubscribe` with a lot of activity) can rapidly cycle through this shared buffer, evicting the still-unconsumed notifications belonging to other clients before their websocket task gets scheduled to read them.

### Impact Explanation
Any legitimate pubsub subscriber can be involuntarily disconnected as a side effect of another, unrelated client's normal (not malicious, not rate-limit-violating) subscription activity. This is analogous to the reported Vault issue: a shared, bounded resource (`RecentItems`/broadcast delivery window) that is consumed on a first-come basis lets one user's ordinary usage (a busy programSubscribe/blockSubscribe) degrade or disrupt the service other users rely on, forcing them to reconnect and resynchronize their subscription state, with no documentation of this corner case in the config/help text for `--rpc-pubsub-queue-capacity-items` / `--rpc-pubsub-queue-capacity-bytes`.

### Likelihood Explanation
This requires only normal API usage — a single `programSubscribe`/`blockSubscribe`/`logsSubscribe` call by any RPC client against a high-activity account/program, no privileged access, no more than one subscription-establishing call, and no interpreter/loader/metrics dependency. The default configuration (`DEFAULT_QUEUE_CAPACITY_ITEMS = 10_000_000`, `DEFAULT_QUEUE_CAPACITY_BYTES = 256MB`) is large but is still a shared, finite resource across every connection on a node; smaller/testnet configurations (`DEFAULT_TEST_QUEUE_CAPACITY_ITEMS = 1000`, `DEFAULT_TEST_QUEUE_CAPACITY_BYTES = 16MB`) make this far easier to trigger: [6](#0-5) 

### Recommendation
- Short term: document this corner case for operators/users of `--rpc-pubsub-queue-capacity-items`/`--rpc-pubsub-queue-capacity-bytes`, explaining that these are shared, global buffers and that heavy subscriptions from one client can cause other clients to be disconnected with "client has lagged behind."
- Long term: consider per-connection (or per-subscription-type) budgets/backpressure instead of (or in addition to) a single global `RecentItems` buffer, so that one subscriber's notification volume cannot starve the delivery window of unrelated subscribers.

### Proof of Concept
1. Start a validator/test-validator with the default (or smaller, e.g. test) pubsub queue capacity.
2. Client A opens a websocket, calls `slotsUpdatesSubscribe` (or any low-churn subscription) and pauses briefly before reading (simulating a slow/busy client, e.g. behind a slow network or a busy consumer loop).
3. Client B opens `programSubscribe` on a program/account receiving rapid, high-volume writes (or `blockSubscribe`), driving notification volume through `RpcSubscriptions::notify_watchers`/`RpcNotifier::notify` (`rpc/src/rpc_subscriptions.rs:290-322`) fast enough to push more than `queue_capacity_items`/`queue_capacity_bytes` worth of new notifications into the shared `RecentItems` (`rpc/src/rpc_subscriptions.rs:233-246`) before Client A's connection task gets scheduled to drain its `broadcast_receiver`.
4. Client A's next `broadcast_receiver.recv()` in `handle_connection` upgrades a `Weak<String>` that has already been evicted, returns `Error::NotificationIsGone`, and the server closes Client A's websocket connection (`rpc/src/rpc_pubsub_service.rs:394-405`), even though Client A did nothing wrong and made no more than its single subscription call.

                .expect("serialization never fails");

        });
