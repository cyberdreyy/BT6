### Title
Blacklisted redeem receiver permanently DoSes async-redeem solves (`solveRequestsVault`) for that request and any other requests batched with it, freezing funds until deadline - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.requestRedeem` lets an ordinary user pick an arbitrary `receiver` for their redeem request [1](#0-0) . When a solver later calls `solveRequestsVault`, the active-path (non-expired) branches of `_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice` transfer the redeemed token directly to `request.receiver` with a bare `token.safeTransfer`, with no try/catch or fallback [2](#0-1) [3](#0-2) . If that token is a blacklist-enforcing stablecoin (e.g. USDC) and `receiver` is blacklisted, this transfer reverts. This matches the reported root cause exactly — the "claim"-equivalent function has no defense against a blacklisted recipient, unlike the expired/refund path, which explicitly guards against exactly this failure mode via `_transferWithFallback` [4](#0-3) .

### Finding Description
`requestRedeem(token, unitsIn, minTokensOut, solverTip, deadline, maxPriceAge, isFixedPrice, receiver)` lets msg.sender set any `receiver` address (no approval or self-check enforced beyond non-zero) [5](#0-4) . When a keeper/solver batches this request in `solveRequestsVault` → `_solveRequestsVault`, it iterates all requests in the batch and dispatches to `_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice` [6](#0-5) .

Inside those functions, on the "not yet expired" branch the vault is exited and the token is sent straight to `request.receiver` via `token.safeTransfer(...)`, with zero fallback handling: [7](#0-6) [8](#0-7) 

If the underlying `token` is a blacklist-enforcing token (USDC) and `receiver` is on the blacklist, `safeTransfer` reverts. Because `_solveRequestsVault` has no try/catch around this call inside its loop, the revert propagates and aborts the **entire batch transaction**, not just the one problematic request [9](#0-8) . This means any other, entirely unrelated user requests bundled in the same `solveRequestsVault` call are also blocked from being solved.

By contrast, once `request.deadline` passes, the same functions fall into the refund branch which correctly uses `_transferWithFallback`, which retries with a `trySafeTransfer` and falls back to `request.user` on failure [10](#0-9) [11](#0-10) . The active-solve branch lacks this same protection — an inconsistency that is the exact root cause pattern from the report (blacklisted recipient blocks the claim/settle call, no fallback).

`solveRequestsDirect`'s `_solveRequestDirect` active-path redeem also does an unguarded `token.safeTransferFrom(msg.sender, request.receiver, request.tokens)` [12](#0-11) , same issue, though this only affects that one request per call (no batching there).

### Impact Explanation
While the request's deadline has not elapsed, redeem requests targeting a blacklisted `receiver` cannot be solved via `solveRequestsVault`, and — because of the unguarded revert inside the shared batch loop — this also blocks the solving of any other unrelated users' requests bundled in the same call, since solvers naturally batch multiple requests together for gas efficiency. Funds (already escrowed vault units) remain locked in the provisioner until the request's deadline passes, at which point the refund path (which does have fallback protection) allows recovery. This is a temporary freeze of user funds/yield-bearing positions, consistent with Immunefi Medium severity for temporary freezing of funds.

### Likelihood Explanation
The precondition — a token with issuer-enforced blacklisting (USDC/USDT-style) configured as an async-redeem token in `tokensDetails`, and a `receiver` address becoming blacklisted before the request's deadline — is realistic for any production deployment using USDC as the redeem asset. Any ordinary user can trigger the specific request path themselves via `requestRedeem`, and a solver's normal, expected operational behavior (batching requests) is what causes the wider blast radius.

### Recommendation
Use the same `_transferWithFallback` mechanism (or a `trySafeTransfer`-based pattern with a well-defined fallback recipient, e.g. `request.user`) in the active-solve branches of `_solveRedeemVaultAutoPrice`, `_solveRedeemVaultFixedPrice`, and `_solveRequestDirect`, exactly as already implemented in their refund branches, so a single blacklisted receiver cannot revert an entire solve batch or permanently prevent settlement.

### Proof of Concept
1. Fork mainnet (or deploy a mock USDC with a `blacklist` mapping enforced in `transfer`) and deploy `ProvisionerV2`/`MultiDepositorVault` with USDC configured with `asyncRedeemEnabled = true`.
2. User A deposits and obtains vault units, then calls `requestRedeem(USDC, unitsIn, minTokensOut, tip, deadline, maxPriceAge, isFixedPrice=true, receiverA)`.
3. Have Circle (or the mock) blacklist `receiverA`.
4. User B (unrelated) also calls `requestRedeem(USDC, ..., receiverB)` with a non-blacklisted `receiverB`.
5. A solver calls `solveRequestsVault(USDC, [requestA, requestB], "", "")` before either deadline.
6. Assert: the call reverts (bubbling from `token.safeTransfer(receiverA, ...)` inside `_solveRedeemVaultFixedPrice`), and `RedeemSolved` is emitted for neither A nor B — i.e., B's legitimate, unrelated redeem is also blocked purely because A's receiver is blacklisted.
7. Contrast: wait until `requestA.deadline` passes and call again; A's units are refunded via `_transferWithFallback` (falls back to `request.user`), confirming the refund path is protected while the active-solve path is not.

            token, msg.sender, receiver, requestType, minTokensOut, unitsIn, solverTip, deadline, maxPriceAge
        );

    /// @notice Transfers amount to receiver and falls back to requester if receiver transfer fails
    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
