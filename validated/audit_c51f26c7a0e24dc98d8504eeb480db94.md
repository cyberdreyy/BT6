### Title
Unprivileged attacker can set vault APR terms before the CDO is wired — `setApr`/`setAprs` skip authorization when `idleCDO == address(0)` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Ghost's GHSA-9gh8-wp53-ccc6 was a gap in API validation that let unprivileged members modify newsletter settings belonging to privileged roles. The direct analog in this codebase is the APR configuration surface of `IdleCreditVault`: `setApr`, `setAprs`, and `setAprsWithBuffer` are externally callable and the only authorization check — `msg.sender != idleCDO && msg.sender != manager → revert` — is entirely skipped while `idleCDO` is unset, which is explicitly acknowledged in the comment "this can happen only during the setup." Any EOA can therefore permanently fix the vault's scaled and unscaled APR before the owner calls `setWhitelistedCDO`.

### Finding Description
`setApr(uint256 _apr)` is `public` and guards callers only inside `if (_cdo != address(0))`:

- `contracts/strategies/idle/IdleCreditVault.sol:225-235` — `setApr` skips the `NotAllowed` check when `idleCDO == address(0)` and only enforces `maxApr` on the scaled value.
- `contracts/strategies/idle/IdleCreditVault.sol:206-220` — `setAprs`/`setAprsWithBuffer` write `unscaledApr` unconditionally; `unscaledApr` has **no cap at all** (the `maxApr` bound applies only to `_apr` inside `setApr`).
- `contracts/strategies/idle/IdleCreditVault.sol:954-957` — `setWhitelistedCDO` is `onlyOwner` and cannot set `idleCDO` back to `address(0)`, so the attacker-set values persist into every epoch once the CDO is wired.

So in the window between `initialize` and `setWhitelistedCDO` (a real deployment path — e.g., a vault initialized directly rather than wired atomically by a factory), an unprivileged attacker executes `setAprs(type(uint256).max, 20e18)` and locks in `unscaledApr = type(uint256).max`, `lastApr = maxApr = 20e18` (2000%/yr).

Downstream, `lastApr` feeds `expectedEpochInterest`/interest accounting on the honest CDO, and `unscaledApr` selects the APR0 accounting path in `requestWithdraw` (`IdleCreditVault.sol:285-286`) and gates `prepareStopEpochWithApr0` (`IdleCreditVault.sol:506-508`). With `unscaledApr = 0` + `lastApr = 20e18`, APR0-mode requests compute a pro-rata share of a massively inflated interest base, inflating `pendingWithdraws` (`IdleCreditVault.sol:535`) far beyond real yield — the honest borrower cannot fund `collectWithdrawFunds`, so `stopEpoch` cannot complete.

### Impact Explanation
Two concrete modes, both reproducible by an unprivileged EOA:

1. **Insolvency-grade interest inflation** (`unscaledApr` arbitrary, `lastApr = 20e18`): for a 1,000,000 USDC vault and a 7-day epoch, expected interest ≈ `1e6 * 20 * 7/365 ≈ 383,561 USDC` — ~38% of TVL of phantom yield the borrower never agreed to. Either the honest borrower is forced to overpay (theft-by-config), or `stopEpoch` funding fails and lender funds are frozen until governance intervention.
2. **Trapped funds via APR0 misconfiguration** (`unscaledApr = 0`, `lastApr = 20e18`): requests route into the `apr0Users` bucket while `apr0RateByEpoch` is computed on the inflated base, inflating `pendingWithdraws` and the receipt basis at `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`), again blocking epoch closure — temporary-to-permanent freezing of all pending withdrawals proportional to TVL.

The broken invariant is privileged-settings integrity: vault economic parameters (which determine the interest the borrower owes and the withdraw basis lenders claim against) are writable by unauthorized callers.

### Likelihood Explanation
- **Preconditions**: the vault proxy must be initialized with `idleCDO` unset (true after `initialize`, which never sets it) and the attacker must front-run or sandwich `setWhitelistedCDO`. Factory-driven deployments that wire the CDO atomically eliminate the window; manual/proxy deployments or a delayed `setWhitelistedCDO` do not.
- **Attacker cost**: one call, no capital, no KYC — the check is skipped entirely (`IdleCreditVault.sol:229-231`).
- **Mitigations present**: `maxApr` caps the scaled APR at `DEFAULT_MAX_APR = 20e18` (`IdleCreditVault.sol:89-91, 232-233`), but does not prevent the attack and leaves `unscaledApr` completely unbounded. `setWhitelistedCDO` is `onlyOwner` but cannot undo already-written APR state.

Likelihood is therefore deployment-dependent: high where the CDO is not wired atomically in the initialization transaction.

### Recommendation
- Apply the same authorization guard regardless of `idleCDO` being set: revert unless `msg.sender == owner() || msg.sender == manager || msg.sender == idleCDO` in `setApr` (and transitively `setAprs`/`setAprsWithBuffer`), or gate the setup window with a `onlyOwner`/`initializer`-style flag that is cleared once `setWhitelistedCDO` runs.
- Bound `unscaledApr` with the same `maxApr` sanity check as the scaled APR.
- Prefer wiring `idleCDO` inside `initialize` (as the factory flow effectively does) so the unauthenticated window cannot exist.

### Proof of Concept
Foundry fork/unit test against `contracts/strategies/idle/IdleCreditVault.sol`:

```solidity
// test setup: deploy ERC1967Proxy over IdleCreditVault impl, then:
vault.initialize(USDC, owner, manager, borrower, "Borrower", 5e17); // idleCDO still 0

address attacker = makeAddr("attacker");
vm.prank(attacker);
vault.setAprs(0, 20e18); // succeeds: _cdo == address(0) skips auth; unscaledApr = 0 (APR0 mode), lastApr = 2000%

vm.prank(owner);
vault.setWhitelistedCDO(address(idleCDOEpoch)); // attacker values persist

// Epoch flow: lenders deposit via CDO, borrower takes funds.
// A lender requests a withdraw -> requestWithdraw routes to _requestWithdrawApr0
// because unscaledApr == 0 (IdleCreditVault.sol:285).
// At stopEpoch, prepareStopEpochWithApr0 computes APR0 interest on the inflated
// expectedEpochInterest (lastApr = 20e18), inflating pendingWithdraws
// (IdleCreditVault.sol:513-537).
// borrower.approve + stopEpoch -> collectWithdrawFunds pulls far more than real
// yield; if borrower cannot fund, stopEpoch reverts and all pending lender
// withdrawals are frozen (fund-impact DoS).
assertEq(vault.unscaledApr(), 0);
assertEq(vault.lastApr(), 20e18);
// expectedEpochInterest for 1M USDC, 7d epoch ~= 383_561e6 vs ~= 959e6 at the
// intended 5% APR -> pendingWithdraws basis inflated ~400x.
```

Assertion highlights: the `vm.prank(attacker)` call must succeed (demonstrating the missing check), `unscaledApr`/`lastApr` retain attacker values after `setWhitelistedCDO`, and the stopEpoch funding requirement computed from `expectedEpochInterest`/`pendingWithdraws` is orders of magnitude above the intended APR, blocking `collectWithdrawFunds` for the honest borrower.

Note on certainty: I verified the guard gap, the lack of a cap on `unscaledApr`, and the downstream APR0/`pendingWithdraws` plumbing in `IdleCreditVault.sol`. I did not fully verify whether `IdleCreditVaultFactory` wires `setWhitelistedCDO` atomically within `initialize`'s transaction; if it does for all production deployments, the realistic likelihood drops (deployment-misconfiguration dependent) but the missing access control itself remains a defect standing on the code's own logic.
