### Title
Permissionless `create` allows lockup account squatting with attacker-chosen whitelist - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the lockup account id deterministically as `sha256(owner_account_id)[..20].<factory>` and performs `create_account()` for it, but places no restriction on who may call `create` or that the caller must be, or be authorized by, `owner_account_id`. Any unprivileged account can call `create("victim.near", ..., whitelist_account_id=Some("evil-whitelist.near"))` before the legitimate grantor does, permanently claiming the deterministic lockup address for `victim.near` with attacker-chosen staking-pool whitelist and lockup parameters.

### Finding Description
The broken binding is:
`LockupArgs@sha256("victim.near")[..20].<factory> == args the real creator intended for victim.near`

Tracing the code: `create` computes `lockup_account_id` purely from `owner_account_id` [1](#0-0) , with no check that `env::predecessor_account_id()` is `owner_account_id`, the foundation, or any other privileged party — the only guard is the deposit-size assertion [2](#0-1) . The `staking_pool_whitelist_account_id` defaults to the factory-wide whitelist only if the caller omits it; otherwise the caller's own `whitelist_account_id` argument is used verbatim [3](#0-2) . The function then does `Promise::new(lockup_account_id).create_account().deploy_contract(CODE)...function_call(b"new", LockupArgs{...})` [4](#0-3) , permanently binding that deterministic account name to the attacker's chosen `LockupArgs`, including the malicious whitelist and `lockup_duration=0`/no vesting schedule (since `vesting_schedule` is optional and only the foundation is inserted when a vesting schedule is provided) [5](#0-4) .

Because NEAR account creation is a one-time claim, once the attacker's `create_account()` for that derived id succeeds, the real grantor's later `create("victim.near", ...)` call will derive the identical `lockup_account_id` and its `create_account()` will fail (account already exists). The `on_lockup_create` callback only checks `is_promise_success()`; on failure it logs and refunds the deposit to the *predecessor* of that failed call (the legitimate grantor), returning `false` — it does not revert or reclaim the attacker's already-deployed contract [6](#0-5) . No `assert_owner`, `assert_called_by_foundation`, or any predecessor/owner equality check exists anywhere in this file or in `lockup-factory/src/utils.rs` to prevent this.

### Impact Explanation
The attacker permanently squats the deterministic lockup address that would have been used for `victim.near`, with a `staking_pool_whitelist_account_id` pointing to a pool the attacker controls (`evil-whitelist.near`). This matches the Critical category "a lockup deployed with parameters its rightful creator never chose": once the real owner is later given/transfers funds into that same account name expectation (or if the ecosystem/UI resolves the lockup address for `victim.near` to this squatted account), any staking approved through the attacker's whitelist can later be directed to an attacker-controlled draining pool. It also blocks the legitimate grantor from ever deploying the intended lockup for `victim.near` at all, since the account name is already taken — freezing/redirecting the deposit process for that beneficiary. The attack is repeatable against any target account name the attacker anticipates, at the cost of one `MIN_ATTACHED_BALANCE` (3.5 NEAR) deposit per squat.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to know or guess the intended beneficiary's `AccountId` (e.g., a known employee/investor about to receive a lockup) and attach `MIN_ATTACHED_BALANCE`. `create` is `#[payable]` and fully public with no allow-list of callers, so any NEAR account can invoke it. The only real barrier is guessing the correct grant name/timing before the legitimate grantor acts, which is plausible for publicly known team/investor account names.

### Recommendation
Restrict `create` so that only the account matching `owner_account_id`, or a designated privileged grantor (e.g., `foundation_account_id` / an authorized allow-list), may create a lockup for that `owner_account_id`; alternatively require `assert_eq!(env::predecessor_account_id(), owner_account_id.as_ref())` unless the caller is the foundation account, and disallow attacker-supplied `whitelist_account_id` overrides for non-privileged callers.

### Proof of Concept
```rust
// In lockup-factory/src/lib.rs tests module (or a new test file)
#[test]
fn test_squat_lockup_before_real_owner() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 0;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker (not account_tokens_owner) squats the lockup for the victim first.
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // "victim" owner_account_id
        lockup_duration,
        None,
        None,
        None,
        Some(custom_whitelist_account_id()), // attacker-controlled "evil-whitelist"
    );

    // Simulate the attacker's create_account succeeding for the derived id.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    assert_eq!(
        contract.on_lockup_create(lockup_account(), ntoy(35).into(), String::from("attacker.near")),
        true // squatted account now exists with attacker's whitelist
    );

    // Legitimate grantor now tries to create the real lockup for the same owner.
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // The derived account already exists -> create_account fails downstream.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner()),
    );
    // Real grantor's creation fails/refunds — proving identity/binding was broken by the squatter.
    assert_eq!(res, false);
}
```
This demonstrates that `lockup_account_id` derived from `owner_account_id` is claimed by an unprivileged attacker with attacker-chosen `LockupArgs` (custom whitelist) before the legitimate creator can ever deploy the intended lockup for that owner, and the legitimate `create` call subsequently fails against the already-existing squatted account.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
