### Title
Stale operator identity in `distribution_pool` after `switch_operator` bypasses the departing operator's configured beneficiary — ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`switch_operator()` re-keys a `StakingContract` from `old_operator` to `new_operator` inside the staker's `Store`, but any commission share that was queued (via `request_commission_internal`) for `old_operator` immediately before the switch keeps `old_operator`'s raw address as its `distribution_pool` shareholder key. Later payouts compare that stale key against the *current* operator parameter (`new_operator`), so the beneficiary-redirect check never fires for it, and the funds are paid to `old_operator`'s own address instead of the beneficiary `old_operator` had configured via `set_beneficiary_for_operator`.

### Finding Description
`switch_operator` at [1](#0-0)  removes the `StakingContract` under `old_operator`, forces a `distribute_internal` (which correctly flushes already-inactive funds to `old_operator`'s beneficiary, since `operator == old_operator` at that point), then calls `request_commission_internal(old_operator, &mut staking_contract)`. That call unlocks the *newly* accrued commission and records it with `add_distribution(old_operator, staking_contract, old_operator, commission_amount)` [2](#0-1) , adding a `distribution_pool` shareholder keyed literally by the address `old_operator`. This new commission is not yet withdrawable (still `pending_inactive`), so it cannot be flushed before the struct is re-inserted into the store under `new_operator`.

When this pending amount is eventually paid out (via `distribute`, `unlock_stake`, or `request_commission`, all callable by anyone once `staking_contract_exists(staker, new_operator)`), `distribute_internal` is invoked with `operator = new_operator` [3](#0-2) . The payout loop's beneficiary redirect is:
```
if (recipient == operator) { recipient = beneficiary_for_operator(operator); };
```
Here `recipient` is the literal `old_operator` address left over from the switch, and `operator` is now `new_operator`. Since they never match, `beneficiary_for_operator(old_operator)` is never consulted, and `aptos_account::deposit_coins(recipient, ...)` pays `old_operator`'s raw address directly. This directly contradicts the module's own documented invariant in `pending_attribution_snapshot`, which states "Operator commission ... may ultimately be paid to a separate beneficiary address during distribution. Call `beneficiary_for_operator(operator)` to determine the final recipient" [4](#0-3)  — the implementation only performs that redirect when the *current* store operator equals the shareholder key, which becomes false the moment `switch_operator` runs.

Additionally, `update_distribution_pool` (invoked from every subsequent `add_distribution`/`distribute_internal` call) periodically skims ongoing "commission growth" from every outstanding shareholder — including the stale `old_operator` entry — and transfers those shares to whatever `operator` parameter is passed in, i.e. `new_operator` [5](#0-4) . This means value that continues to accrue on `old_operator`'s already-finalized, unpaid commission balance is siphoned to `new_operator` rather than staying with `old_operator`.

### Impact Explanation
This falls under "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account." An operator who has delegated payout control to a custody/beneficiary address via `set_beneficiary_for_operator` [6](#0-5)  loses that guarantee for any commission requested in the same transaction/epoch window as a `switch_operator` call: the funds are diverted to the operator's own raw address (bypassing the intended beneficiary), and part of the ongoing accrual on that unpaid balance is additionally re-routed to the new operator instead of the original one. Because `staking_proxy::set_operator` (a convenience wrapper reachable by any staker/vesting admin) also calls `staking_contract::switch_operator` under the hood [7](#0-6) , this is trivially reachable via a normal operator-rotation flow, not an edge case requiring privileged access.

### Likelihood Explanation
Medium. It requires only an ordinary operator switch (by the staker or a vesting-contract admin, both unprivileged with respect to the operator's own beneficiary configuration) to occur while the outgoing operator has an unlocked-but-not-yet-inactive commission request in flight — a routine and easily triggered sequencing rather than a rare race condition, matching the "Medium/Medium" severity profile of the seed report.

### Recommendation
When switching operators, either (a) fully distribute and flush the outgoing operator's pending distribution-pool balance using `beneficiary_for_operator(old_operator)` *before* re-keying the `StakingContract`, or (b) make the beneficiary redirect check in `distribute_internal` compare against the actual shareholder address's own beneficiary record (`beneficiary_for_operator(recipient)`) rather than against the currently active `operator` parameter, so that stale shareholder entries created for a previous operator continue to resolve correctly regardless of subsequent operator changes.

### Proof of Concept
1. Staker creates a staking contract with `operator_1` and validator joins; rewards accrue.
2. `operator_1` calls `set_beneficiary_for_operator(operator_1, beneficiary)`.
3. Staker calls `switch_operator(staker, operator_1, operator_2, new_commission_pct)`. Inside, `request_commission_internal` unlocks new commission and records it under shareholder key `operator_1` in the (still pending_inactive) `distribution_pool`, then the whole `StakingContract` is moved to be keyed by `operator_2`.
4. After the lockup period elapses, anyone calls `distribute(staker, operator_2)` (or `unlock_stake`/`request_commission` with `operator_2`).
5. `distribute_internal` runs with `operator = operator_2`; the shareholder `operator_1` fails the `recipient == operator` check, so `beneficiary_for_operator(operator_1)` is never consulted — the coins are deposited straight to `operator_1`'s address instead of `beneficiary`, and any commission growth on that balance since the switch is transferred to `operator_2` via `update_distribution_pool`.

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }

    fun distribute_internal(
        staker: address,
        operator: address,
        staking_contract: &mut StakingContract,
    ) acquires BeneficiaryForOperator {
        let pool_address = staking_contract.pool_address;
        // Create the Staker resource if it doesn't exist to backfill the Staker resource for each pool.
        if (!exists<Staker>(pool_address)) {
            let pool_signer =
                &account::create_signer_with_capability(&staking_contract.signer_cap);
            move_to(pool_signer, Staker { staker });
        };
        let (_, inactive, _, pending_inactive) = stake::get_stake(pool_address);
        let total_potential_withdrawable = inactive + pending_inactive;
        let coins =
            stake::withdraw_with_cap(
                &staking_contract.owner_cap, total_potential_withdrawable
            );
        let distribution_amount = coin::value(&coins);
        if (distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        let distribution_pool = &mut staking_contract.distribution_pool;
        update_distribution_pool(
            distribution_pool,
            distribution_amount,
            operator,
            staking_contract.commission_percentage
        );

        // Buy all recipients out of the distribution pool.
        while (distribution_pool.shareholders_count() > 0) {
            let recipients = distribution_pool.shareholders();
            let recipient = recipients[0];
            let current_shares = distribution_pool.shares(recipient);
            let amount_to_distribute =
                distribution_pool.redeem_shares(recipient, current_shares);
            // If the recipient is the operator, send the commission to the beneficiary instead.
            if (recipient == operator) {
                recipient = beneficiary_for_operator(operator);
            };
