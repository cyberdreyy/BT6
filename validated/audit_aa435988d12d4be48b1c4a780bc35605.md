### Title
Unprivileged ERC4626 vault user can drain vault liquidity to brick `onStopEpoch`, temporarily freezing epoch settlement and all pending withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
`ProgrammableBorrower.onStopEpoch` unconditionally calls `vault.withdraw(shortfall, ...)` on the externally configured ERC4626 vault whenever IdleCDO requests more than the on-hand balance, and reverts with `StopEpochVaultLiquidityUnavailable` on any withdrawal failure. Because `_currentVaultAssets()` is a share-valuation view (`convertToAssets`) rather than a liquidity check, an unprivileged user of that ERC4626 vault can borrow or withdraw its available liquidity right before `stopEpoch`, making the vault withdrawal revert even though the borrower's shares nominally cover the shortfall. The revert propagates through `IdleCDOEpochVariant.stopEpoch`, so the epoch cannot be stopped and all `requestWithdraw` payouts are frozen until vault liquidity returns.

### Finding Description
The Anchore bug class — attacker-supplied external input breaking a privileged processing step — maps here to externally controlled ERC4626 vault state breaking the privileged epoch-settlement path. In `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:231-268):

```solidity
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

- The guard `shortfall > _currentVaultAssets()` only checks that vault *shares* economically cover the shortfall; it does not check that the vault currently holds enough liquid underlying to service the withdrawal.
- ERC4626 lending-style vaults (the documented use case for `ProgrammableBorrower`) can be liquidity-constrained: any third-party depositor/borrower of that vault can withdraw or borrow the idle liquidity.
- When `vault.withdraw` reverts, `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, aborting `stopEpoch` in `IdleCDOEpochVariant`. The code comment ("an otherwise-covered ERC4626 withdrawal failure should make stopEpoch retryable") confirms the revert is intended to propagate, i.e. there is no fallback path — settlement simply cannot proceed while the vault is illiquid.

During the blocked window, tranche holders' `requestWithdraw` claims cannot be honored because the epoch never stops, so `epochEndDate` accounting and claim processing stay frozen. The attacker — any EOA with no protocol role, only an ordinary user/borrower of the external ERC4626 vault — bears only gas plus the cost of holding a borrow/withdraw position.

### Impact Explanation
Temporary freezing of all user funds in the credit vault: queued withdraw requests and tranche redemptions depending on `stopEpoch` cannot complete while the external vault is drained. The freeze persists as long as the attacker keeps vault liquidity unavailable (e.g. an open borrow), and in lending vaults where borrowed liquidity can be extended or re-drained after repayments, the attacker can repeatedly re-trigger the condition each time liquidity returns. All pooled lender capital in the facility is affected, not just the attacker's position.

### Likelihood Explanation
Requires only that the configured ERC4626 vault exposes liquidity to third parties (standard for lending/yield vaults) and that the shortfall exceeds the borrower's on-hand balance — the normal case, since idle funds are parked in the vault. No privileged role, no KYC, no capital lockup beyond the borrow itself. Monitor-based mitigations (Hypernative pauser) do not cover this path because `stopEpoch` itself is what reverts. Residual uncertainty: whether `IdleCDOEpochVariant.stopEpoch` wraps the hook call in its own try/catch was not fully verified in this pass; the in-code comment strongly indicates the revert is designed to propagate, but a wrapping catch would downgrade impact to a narrower freeze.

### Recommendation
Do not let an external vault's transient illiquidity hard-block epoch settlement. Options:

1. Replace the hard revert with graceful degradation: attempt `vault.withdraw`, and on failure proceed with the on-hand amount (return `false`/partial or record a `pendingShortfall`), letting IdleCDO's existing default/shortfall path handle the gap instead of reverting.
2. Use `vault.maxWithdraw(address(this))` (the ERC4626 liquidity-aware view) rather than `convertToAssets(balanceOf)` to size the withdrawal, and withdraw `min(shortfall, maxWithdraw)`.
3. Add a catch-all fallback in `IdleCDOEpochVariant.stopEpoch` so a reverting borrower hook enters a retryable-but-not-blocking state for withdraw request servicing.
