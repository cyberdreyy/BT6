### Title
Post-default instant withdraw receipts drain `defaultRecoveryReserve` earmarked for defaulted-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestWithdraw` explicitly branches when `defaultRecoveryFinalized` is true and routes new requests into `postDefaultRequests`, but `requestInstantWithdraw` performs no such check. A post-default instant request is recorded under `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, where `epochNumber` still equals `defaultRecoveryEpoch`, so `claimInstantWithdrawRequest` pays it out of `defaultRecoveryReserve` at the old `defaultRecoveryPrice` — reserve that was sized only for pre-default claimants.

### Finding Description
`finalizeDefaultRecovery` snapshots `defaultRecoveryEpoch = epochNumber` and fixes `defaultRecoveryReserve`/`defaultRecoveryPrice` to exactly cover the claim basis that existed at finalization (`defaultPendingClaimBasis()` = `pendingWithdraws` plus current-epoch instant claims). After finalization:

1. `requestInstantWithdraw` (lines 356–375) never checks `defaultRecoveryFinalized`. It burns the CDO's strategy tokens, mints a receipt to the user, and writes `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount`. Since `epochNumber` is unchanged since default, the receipt lands in `defaultRecoveryEpoch`.
2. `claimInstantWithdrawRequest` (lines 380–393) sees `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` and calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, finds the attacker's freshly minted post-default receipt, and calls `_transferDefaultRecovery(_user, claimBasis * defaultRecoveryPrice / RECOVERY_FULL)` (line 855).
3. `_transferDefaultRecovery` decrements `defaultRecoveryReserve` (line 915), which was reserved exclusively for pre-default claimants. `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` (line 853) can even underflow if the post-default receipt exceeds the recorded epoch basis, reverting — but the normal path pays the attacker.

Contrast with `requestWithdraw` (lines 247–257), which detects `defaultRecoveryFinalized` and isolates new requests in `postDefaultRequests` so they cannot touch the reserve.

### Impact Explanation
Any tranche holder can, after default finalization, mint an instant-withdraw receipt that is indistinguishable from a defaulted-epoch receipt and withdraw `amount * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve`. Every unit withdrawn is a unit no longer available to legitimate pre-default claimants (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`, `_claimPostDefaultWithdrawRequest` all draw on the same reserve). When reserve is exhausted, honest claimants' `_transferDefaultRecovery` underflows and their claims revert — permanent freezing/theft of their recovery. Loss is bounded by `defaultRecoveryReserve` minus the attacker's own haircut contribution, i.e., up to the full recovery reserve across a vault's defaulted claimants.

### Likelihood Explanation
Requires only an unprivileged tranche-token holder calling `requestInstantWithdraw` then `claimInstantWithdrawRequest` through the CDO after `finalizeDefaultRecovery`. No privileged action needed; the only precondition is that the CDO still routes instant-withdraw requests while defaulted (no `defaulted()` gate exists inside the strategy function itself — `requestInstantWithdraw` only checks `_onlyIdleCDO` and `_ensureDefaultRecoveryInitialized`, both of which pass post-default). Caveat: I was unable to fully verify the CDO-side entry point (`IdleCDOEpochVariant`) does not independently block instant-withdraw requests once `defaulted()` is true; if it does, the exploit path closes.

### Recommendation
Mirror the `requestWithdraw` post-default branch in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, revert (or route the receipt into a separately funded bucket such as `postDefaultRequests`). At minimum, write post-default instant receipts under a fresh epoch key rather than `defaultRecoveryEpoch`, e.g. revert `NotAllowed()` while `defaultRecoveryFinalized` since no honest user benefits from an instant request in a defaulted pool.

### Proof of Concept
```solidity
// Foundry fork test sketch
// Setup: vault has defaulted, manager/owner called the CDO default flow,
// finalizeDefaultRecovery ran with recoveryPrice = e.g. 0.6e18,
// defaultRecoveryReserve = R covering pre-default claims.

function testPostDefaultInstantDrainsReserve() public {
    // attacker holds BB tranche tokens worth X underlying
    vm.startPrank(attacker);
    // 1) post-default instant request via the CDO
    cdo.requestInstantWithdraw(X); // -> strategy.requestInstantWithdraw(X, attacker)
    // instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch] = X
    // 2) claim immediately
    cdo.claimInstantWithdrawRequest(); // -> strategy.claimInstantWithdrawRequest(attacker)
    vm.stopPrank();

    // attacker received X * defaultRecoveryPrice / 1e18 from defaultRecoveryReserve
    assertEq(underlying.balanceOf(attacker), X * strategy.defaultRecoveryPrice() / 1e18);
    // reserve reduced by funds owed to pre-default claimants
    assertLt(strategy.defaultRecoveryReserve(), R_before);
    // a legitimate defaulted claimant now reverts/underpays
    vm.expectRevert();
    vm.prank(innocentClaimant);
    cdo.claimWithdrawRequest();
}
```
