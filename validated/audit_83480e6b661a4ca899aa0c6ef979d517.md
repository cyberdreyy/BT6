### Title
Loss-adjusted withdraw receipts bypass their haircut and are paid at par because `lossRecoveryPriceByEpoch` is indexed by the post-stop epoch while `lastWithdrawRequest` stores the pre-stop epoch - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.requestWithdraw` records the user's request under the *current* `epochNumber` (`lastWithdrawRequest[_user] = currentEpoch`, `withdrawsRequestsByEpoch[_user][currentEpoch]`). During `stopEpoch`/`stopEpochWithDuration`, `IdleCDOEpochVariant` calls `strategy.deposit(...)`, which increments `epochNumber` while the epoch is still running (`epochNumber += 1` at `IdleCreditVault.sol:610`), and only afterwards calls `collectWithdrawFunds(_amount)`, which stores the realized haircut under the *new*, already-incremented epoch: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (`IdleCreditVault.sol:421`).

The claim path `_claimLossAdjustedWithdrawRequest` looks the price up under `lastWithdrawRequest[_user]` — the pre-increment epoch — reads `0`, and silently skips the loss-adjusted claim. The receipt then falls through to `_claimFundedWithdrawRequest`, which pays the full `withdrawsRequests[_user]` at par.

This is the direct analog of CVE-2024-34161 (worker reads stale/freed memory): a receipt created under epoch `N` is later resolved against state written under epoch `N+1`, so the stale lookup misses the haircut that was actually recorded.

### Finding Description
Flow in a loss-adjusted stop (`stopEpochWithDuration(_lossAmount > 0)`):

1. Buffer phase, epoch `N`: user calls `IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw` sets `lastWithdrawRequest[_user] = N`, `withdrawsRequestsByEpoch[_user][N] = _amount`, `withdrawsRequests[_user] += _amount`, `pendingWithdraws += _amount` (`IdleCreditVault.sol:259-294`).
2. `stopEpochWithDuration` executes: internal `deposit`/`mintStrategyTokens` calls bump `epochNumber` to `N+1` while `isEpochRunning()` is still true (`IdleCreditVault.sol:607-610`).
3. `collectWithdrawFunds(pendingToFund)` runs with `epochNumber == N+1`. Because `_amount < pendingWithdraws`, it stores `lossRecoveryPriceByEpoch[N+1] = _amount * 1e18 / pendingBasis` and sets `pendingWithdraws = 0` (`IdleCreditVault.sol:411-421`). Note `lossRecoveryPriceByEpoch[N]` is never written.
4. User calls `claimWithdrawRequest` (`IdleCreditVault.sol:301-313`):
   - `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0 → returns 0 (`IdleCreditVault.sol:789-801`).
   - `_claimFundedWithdrawRequest` passes its gate because `epochNumber (N+1) > lastWithdrawRequest (N)` (`IdleCreditVault.sol:326-328`), computes `amount = withdrawsRequests[_user]` (the **full, un-haircut** receipt), burns the receipt tokens, clears the counters, and calls `_transferFundedClaim` for the whole amount (`IdleCreditVault.sol:338-349`).

Only `pendingToFund` (the haircut amount) was transferred into the strategy in step 3, but the user receives the full receipt. The difference `pendingBasis - pendingToFund` is paid out of strategy underlyings that belong to other claimants / the recovery reserve path, breaking the loss-waterfall invariant that pending receipts absorb their pro-rata share of `activeLoss`/`pendingLoss` computed by `previewLossAdjustedWithdrawFunds`.

The existing guard in `requestWithdraw` (`IdleCreditVault.sol:263-271`) does not help: it only prevents opening a *new* request while a loss-adjusted receipt is pending, and since the lookup epoch is wrong, the receipt is never even treated as loss-adjusted. `_transferFundedClaim`'s reserve guard (`IdleCreditVault.sol:897-907`) only protects `defaultRecoveryReserve`, not ordinary funded-claim solvency.

### Impact Explanation
Direct theft / insolvency: every pending withdraw receipt whose epoch ends with `stopEpochWithDuration(_lossAmount > 0)` is paid at 100% instead of `lossRecoveryPrice`, with the shortfall drawn from underlying held by `IdleCreditVault` that is owed to other users (other funded receipts, post-default reserve accounting via the shared balance check, or later claimants who then revert on insufficient balance). Loss magnitude equals `pendingLoss = _lossAmount * pendingBasis / totalBasis` per affected epoch; if the strategy balance is insufficient the claims of other users permanently revert (freezing of unclaimed funds).

### Likelihood Explanation
Requires only an unprivileged tranche holder calling `requestWithdraw` before an epoch that is later stopped with a partial loss via `stopEpochWithDuration` — a normal, expected protocol path (manager is honest; borrower shortfall is a routine scenario the loss machinery exists for). No privileged malicious action, no oracle dependence, no donation needed. The flaw is purely an off-by-one epoch index between the write (`collectWithdrawFunds`) and read (`_claimLossAdjustedWithdrawRequest`) sites.

### Recommendation
Index `lossRecoveryPriceByEpoch` by the epoch in which the receipts were *created*, not the post-increment `epochNumber`. Concretely, in `collectWithdrawFunds` store under `epochNumber - 1` (or pass the request epoch explicitly from `IdleCDOEpochVariant.stopEpochWithDuration`), or conversely record `lastWithdrawRequest`/`withdrawsRequestsByEpoch` under the epoch that `collectWithdrawFunds` will observe (i.e., account for the `epochNumber += 1` bump inside `deposit` during `stopEpoch`). Add a regression test asserting that a receipt haircut by `stopEpochWithDuration` pays exactly `claimBasis * lossRecoveryPrice / 1e18` and that `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` after the stop.

### Proof of Concept
Foundry fork test (place in `test/foundry/`, reuse helpers from `IdleCreditVault.t.sol`):

```solidity
function testLossAdjustedReceiptPaysAtPar() external {
    address user = makeAddr('loss-epoch-user');
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(user, amount, true);
    idleCDO.depositAA(amount); // ensure active basis exists for the loss split

    // Buffer phase of epoch N: user opens a normal withdraw request
    uint256 requestEpoch = strategy.epochNumber();
    vm.prank(user);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(strategy.lastWithdrawRequest(user), requestEpoch);

    _startEpochAndCheckPrices(0);

    // Honest borrower repays only part: realize a loss so collectWithdrawFunds is partial
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 lossAmount = (activeBasis + pendingBasis) / 2;
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, borrower, repay);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), repay);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), lossAmount);

    // Haircut was stored under the POST-stop epoch, not the request epoch
    assertEq(strategy.lossRecoveryPriceByEpoch(requestEpoch), 0, 'request epoch has no haircut');
    uint256 storedPrice = strategy.lossRecoveryPriceByEpoch(strategy.epochNumber());
    assertGt(storedPrice, 0);
    assertLt(storedPrice, 1e18);

    // BUG: user claims the FULL receipt at par even though only pendingToFund was collected
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = IERC20Detailed(defaultUnderlying).balanceOf(user) - balPre;

    uint256 expected = pendingBasis * storedPrice / 1e18;
    assertGt(paid, expected, 'receipt paid above its loss-adjusted price');
    assertEq(paid, pendingBasis, 'receipt paid at par');
}
```

Uncertainty note: I could not dump the exact `stopEpochWithDuration` body in this session to confirm the `epochNumber += 1` (inside `deposit`/`mintStrategyTokens`, `IdleCreditVault.sol:607-610`) strictly precedes the `collectWithdrawFunds` call. The finding stands if both run in the same stop transaction with the deposit first — which the code comments (`IdleCreditVault.sol:608-610`, "deposit done on stopEpoch … so we reset the counter") and the funded-claim gate relying on `epochNumber > lastWithdrawRequest` after `stopEpoch` strongly indicate. If `collectWithdrawFunds` is ever invoked before the bump, the index would instead be `N` and the bug would not trigger; the PoC assertions make this trivially verifiable.
