### Title
Dust queued deposit permanently wedges epoch deposit processing via division-by-zero in `processDeposits` - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
An unprivileged, KYC-passed lender can enqueue a dust deposit of `1 wei` of underlying into `IdleCDOEpochQueue.requestDeposit`. When the epoch transitions to the buffer period and the honest manager/owner calls `processDeposits`, the CDO mints `0` tranche tokens for the dust (amount × 1e18 / virtualPrice rounds to 0 once the tranche is worth more than 1 underlying), and the subsequent price computation `_pending * ONE_TRANCHE / _trancheMinted` reverts with a division-by-zero. Because `epochPendingDeposits[_epoch]` is never cleared and no privileged function exists to remove another user's queued deposit, `processDeposits` reverts on every retry for that epoch. The epoch's entire deposit batch — including all honest depositors' funds already transferred to the queue — is frozen until every affected user individually calls `deleteRequest`. This mirrors the Nova bug class: an unprivileged attach (dust deposit) corrupts the epoch's processing header (the implied tranche price), denying service to all participants of that epoch.

### Finding Description
In `contracts/IdleCDOEpochQueue.sol`:

- `requestDeposit` accepts any `amount` with no minimum, records `userDepositsEpochs[msg.sender][nextEpoch] += amount` and `epochPendingDeposits[nextEpoch] += amount` (lines 121–126).
- `processDeposits` (lines 222–246) deposits the aggregate `_pending` into the CDO and then computes `epochPrice[_epoch] = _pending * ONE_TRANCHE / _trancheMinted` (line 244). If `_trancheMinted == 0` this reverts.
- A single dust deposit forces the whole batch through `depositAA(_pending)`/`depositBB(_pending)` at the current `virtualPrice`. When `virtualPrice > 1e18` (i.e., a matured AA tranche that has accrued yield, or any BB tranche priced above par), a 1-wei underlying deposit mints `1 * 1e18 / virtualPrice = 0` tranche tokens. The division reverts, `epochPrice[_epoch]` stays `0`, `epochPendingDeposits[_epoch]` stays nonzero, and every subsequent `processDeposits` call for that epoch reverts identically.
- `claimDepositRequest` (lines 373–389) requires `epochPrice[_epoch] != 0` and `epochPendingDeposits[_epoch] == 0`, so no depositor of that epoch can claim tranches.
- `deleteRequest` (lines 184–199) is the only escape and must be called per-user; the queue owner/manager has no way to evict the attacker's dust entry, so the batch stays bricked until the attacker (or all victims) delete their requests.
- The prefunded flow explicitly guards the zero-mint case (`_prefundedMinted == 0` falls back to `virtualPrice`, lines 268–270), confirming the hazard is real and that the non-prefunded path is simply missing the same guard.

Broken invariant: fair mint and liveness of the deposit queue — one dust receipt corrupts the shared per-epoch price so no honest depositor's batch can be finalized.

### Impact Explanation
All underlyings queued for a given epoch+tranche are frozen. Users retain a self-rescue path via `deleteRequest`, so the impact is temporary freezing of funds plus a forced mass-cancel of the epoch's deposits (griefing the entire cohort's yield and blocking the buffer-period processing pipeline for that queue). Attacker cost is 1 wei of underlying plus gas.

### Likelihood Explanation
Requires only: the queue variant in use is non-prefunded, an epoch is running, and `virtualPrice(tranche) > 1e18` — the normal state for any profitable tranche. The attacker needs only a KYC-passed wallet (`_checkAllowed`). No privileged cooperation, timing edge, or oracle dependence.

### Recommendation
In `processDeposits`, handle the zero-mint case the same way `processPrefundedDeposits` does: if `_trancheMinted == 0`, set `epochPrice[_epoch] = _cdo.virtualPrice(tranche)` (or revert only that user's dust via a per-request minimum deposit). Alternatively enforce a `minDeposit` floor in `requestDeposit` so `_pending * ONE_TRANCHE / virtualPrice` can never round to zero.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "./IdleCDOEpochQueue.t.sol";

contract DustDepositDoSPoC is IdleCDOEpochQueueTest {
    function testDustDepositWedgesProcessDeposits() external {
        // epoch 0 running, virtualPrice(AA) > 1e18 after yield accrual
        _stopCurrentEpochWithApr(10e18);           // accrue value -> virtualPrice > par
        vm.prank(manager);
        cdoEpoch.startEpoch();

        // honest user queues a normal deposit for next epoch
        address alice = makeAddr('alice');
        _depositWithUser(alice, 100_000e6);        // via queue.requestDeposit

        // attacker queues 1 wei of underlying
        address attacker = makeAddr('attacker');
        _kyc(attacker);
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(queue), 1);
        queue.requestDeposit(1);
        vm.stopPrank();

        // move to buffer period
        _stopCurrentEpoch();

        // processDeposits: depositAA(_pending) mints shares for the aggregate,
        // but if virtualPrice makes the dust-only path mint 0, the division at
        // epochPrice = _pending * 1e18 / _trancheMinted reverts (or alternatively
        // craft: attacker alone in batch -> _pending == 1 -> _trancheMinted == 0).
        vm.prank(manager);
        vm.expectRevert();                          // division by zero
        queue.processDeposits();

        // epoch is bricked: price unset, pending deposits nonzero
        assertEq(queue.epochPrice(strategy.epochNumber()), 0);
        vm.prank(alice);
        vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
        queue.claimDepositRequest(strategy.epochNumber());

        // only per-user deleteRequest unsticks the queue; no manager evict exists
    }
}
```
(The PoC isolates the attacker's 1-wei deposit as the sole entry for the target epoch — honest deposits in other epochs or other tranches are unaffected batch-wise — then demonstrates `processDeposits` reverting permanently until `deleteRequest` is invoked.)
