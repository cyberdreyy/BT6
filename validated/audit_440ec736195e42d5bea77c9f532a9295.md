### Title
Cross-user callback hijack via `savedCallbacks` MessageId collision - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores the caller-supplied callback in `h.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageId`, with no binding to the sender/signer. Any signed message (from any address) whose payload's `Timestamp` passes the freshness check can reuse a MessageId that is already pending in the map, silently overwriting the original entry and diverting the eventual node response to the attacker's callback.

### Finding Description
`HandleLegacyUserMessage` decodes and validates only the payload timestamp and method, then unconditionally overwrites the map entry: [1](#0-0) 
There is no check for an existing entry, and the key (`msg.Body.MessageId`) is not tied to the signer/sender at all — it is an arbitrary, attacker-chosen string that is part of the signed payload the attacker signs with their own key.

The MessageId originates directly from the client-supplied JSON-RPC request `ID` field, set in `ValidatedMessageFromReq`: [2](#0-1) 
and it is dispatched to the handler from `gateway.ProcessRequest` with only signature/length validation, no per-ID authorization or existing-callback check: [3](#0-2) 

The comment directly above the map write acknowledges the missing protection: [4](#0-3) 

Because `Message.Validate()`/`Sign()` only verify that the signature matches *some* signer over the message body (including the MessageId) — they do not verify MessageId uniqueness or bind it to a specific caller — a second, unrelated signer can submit a request with the identical `MessageId` as a currently in-flight legitimate request. As long as its own `Timestamp` is within `MaxAllowedMessageAgeSec`, the check at line 372 passes independently for each message: [5](#0-4) 
and the attacker's callback silently replaces the victim's callback in `h.savedCallbacks[msgId]`. When the DON node's response for that MessageId arrives at `handleWebAPITriggerMessage`, it is delivered only to whichever callback currently occupies the map slot: [6](#0-5) 
so the victim's HTTP request (blocked on `callback.Wait(ctx)` in `gateway.ProcessRequest`) times out, while the attacker receives the victim's response payload.

### Impact Explanation
This is a cross-user response confusion / unauthorized disclosure of another user's request result: an unprivileged party who can submit a signed gateway user message (any address is permitted; no allowlist is implemented here per the `TODO` comment) can hijack delivery of another in-flight webAPI-trigger response by colliding on `MessageId`. Depending on payload content, the diverted response could contain data intended only for the victim.

### Likelihood Explanation
Exploitability requires only that the attacker know or predict a MessageId currently in flight for another user (client-chosen IDs are frequently non-secret, e.g., sequential/predictable, or observable through logs, timing, or side channels) and be able to sign their own valid gateway message with a fresh timestamp — no special privilege, no DON/operator compromise, and no allowlist bypass is needed since none exists at this layer. The race window equals the round-trip time between forwarding the request to DON nodes and the DON responding, which is on the order of the configured HTTP/callback timeout, making repeated attempts feasible.

### Recommendation
Bind `savedCallbacks` entries to the message sender (e.g., composite key of `Sender+MessageId`, or store/verify the original sender's address in `savedCallback` and reject writes/reads from mismatched senders), and reject `HandleLegacyUserMessage` calls whose `MessageId` already has a non-expired entry from a different sender instead of silently overwriting.

### Proof of Concept
Handler-level Go test in `core/services/gateway/handlers/capabilities/handler_test.go`, using existing helpers (`setupHandler`, `triggerRequest`, `hc.NewCallback`):
1. Generate two node keys/signers `victimKey` and `attackerKey`.
2. Build `msgVictim := triggerRequest(t, victimKey, ..., "", "")` and `msgAttacker` with the same forced `MessageId` (e.g. patch `triggerRequest` or construct manually) but signed by `attackerKey`, both with fresh `Timestamp`.
3. Call `handler.HandleLegacyUserMessage(ctx, msgVictim, victimCb)`, then `handler.HandleLegacyUserMessage(ctx, msgAttacker, attackerCb)`.
4. Inspect `handler.savedCallbacks[msgVictim.Body.MessageId]` (via exported test accessor or reflection) and assert it now references `attackerCb`, not `victimCb`.
5. Simulate the DON node response via `handler.HandleNodeMessage(...)` for that MessageId; assert `attackerCb.Wait(ctx)` returns the response while `victimCb.Wait(ctx)` times out/never resolves — demonstrating the cross-user hijack.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

	}
	return nil
