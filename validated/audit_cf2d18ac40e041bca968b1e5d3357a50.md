### Title
Unbounded operator-fee scalar/constant lets an L1 SystemConfig update force EIP-8130 payers to pay arbitrarily large fees beyond what they signed for - (File: `crates/common/genesis/src/updates/operator_fee.rs`)

### Summary
`SystemConfig.operator_fee_scalar`/`operator_fee_constant` are decoded from an L1 `ConfigUpdate(OperatorFee)` log with no upper bound and applied verbatim [1](#0-0) . They flow, unclamped, into `L1FeeParams::operator_fee_charge_inner`, which computes `gas * scalar [* 100 for Jovian] / decimal + constant` using only `saturating_*` arithmetic [2](#0-1) . This operator fee is charged on top of the EIP-8130 payer's pre-charge in `prepay`, in addition to the gas cost and L1 data fee [3](#0-2) .

### Finding Description
`FeeCheck::validate_balance`/`max_fee_charge`, which is what a sponsor's `payer_auth` signature implicitly relies on to bound its exposure, only covers `(gas_limit + payer_auth_cost) · max_fee_per_gas` [4](#0-3) . The payer's EIP-8130 signature (`payer_signature_hash`) commits only to the transaction body fields (sender, gas_limit, max_fee_per_gas, calls, etc.) — it never commits to, or caps, the L1 data fee or the operator fee, both of which are computed independently at execution time from the *current* `L1BlockInfo`/`SystemConfig` values [5](#0-4) . `prepay` then debits `gas_charge + l1_cost + operator_cost` from the payer's balance without any independent ceiling on `operator_cost` or `l1_cost` [3](#0-2) .

Because `operator_fee_scalar` (`u32`) and `operator_fee_constant` (`u64`) are taken directly off an L1 log with no sanity/ceiling check anywhere in the decode or apply path (`OperatorFeeUpdateError` only validates structural ABI encoding, never value magnitude) [6](#0-5) [1](#0-0) , once this config change is included in a derived L1 info deposit transaction it is applied chain-wide to every subsequent L2 transaction's operator-fee charge, with the resulting cost bounded only by `U256` saturation, not by any per-tx or protocol-level fee cap.

This mirrors the reported Harpie `Transfer.sol` class of bug: a component upstream of the actual payer sets an unbounded fee parameter, and downstream code has no independent ceiling to protect the party who must pay it — the accounting layer that computes "how much must I be able to afford" (`FeeCheck`) is decoupled from the accounting layer that actually charges the fee (`prepay`/`settle_fees`), and the gap (`operator_cost`, `l1_cost`) is unbounded.

### Impact Explanation
An operator-fee update with a maximal or near-maximal `operator_fee_scalar`/`operator_fee_constant` causes every EIP-8130 sponsored transaction's `operator_cost` to balloon far beyond anything the sponsor (payer) explicitly authorized or budgeted for via `max_fee_per_gas`. Because `prepay`/`settle_fees` saturating-add this uncapped cost on top of the gas charge and debit it directly from the payer's account, a sponsor can be drained of funds it never agreed to spend for a given transaction, or (more broadly) legitimate transactions across the chain become unaffordable / fail admission once payer balances can no longer cover `gas_charge + l1_cost + operator_cost`, effectively halting EIP-8130 transaction processing chain-wide. This is a fund-loss/chain-halt condition, matching Medium/High severity.

### Likelihood Explanation
Setting `operator_fee_scalar`/`operator_fee_constant` requires an L1 `ConfigUpdate` event from the `SystemConfig` contract — a privileged, but not directly-EOA-triggerable, action. However, since the derivation and fee-accounting code paths themselves apply the value with **no bound whatsoever** (unlike other OP-stack chain parameters, which are typically range-checked), any misconfiguration, compromise, or unreviewed governance action instantly and chain-wide affects every EIP-8130 payer without a bounded blast radius, exactly the scenario the original Harpie fix (adding a ceiling/timelock) was designed to prevent.

### Recommendation
Enforce a protocol-level maximum on `operator_fee_scalar`/`operator_fee_constant` (and, more generally, bound `l1_cost`/`operator_cost` independently of `max_fee_per_gas` in `FeeCheck::validate_balance`/`max_fee_charge`, or fold them into the payer's committed fee cap) so that no single `SystemConfig` update can force EIP-8130 payers or ordinary senders to pay fees they never explicitly bounded. Consider validating the decoded scalar/constant against a sane ceiling in `OperatorFeeUpdate::try_from`/`apply`, and adding a `FeeError` variant so `FeeCheck` fails closed when a payer's authorized `max_fee_per_gas` cannot possibly cover the full `l1_cost + operator_cost` component, rather than silently debiting whatever the current chain-level scalars produce.

### Proof of Concept
1. A `SystemConfig` owner emits a `ConfigUpdate(OperatorFee)` log with `operator_fee_scalar = u32::MAX`, `operator_fee_constant = u64::MAX` [7](#0-6) .
2. Once the corresponding L1 block is included in the rollup's derivation, `SystemConfig::update_with_receipts` applies the update unconditionally [8](#0-7) , and it propagates into every subsequent L2 block's L1 info deposit transaction (`operator_fee_encoded_in_l1_info_from_isthmus_onward` test demonstrates this propagation mechanism) [9](#0-8) .
3. Any EIP-8130 sponsored transaction submitted after this point has its `operator_cost` computed from the new scalar/constant in `prepay`, saturating-added to the gas charge and debited directly from the payer's balance — a sum the payer never signed for or bounded via `max_fee_per_gas` [3](#0-2) .

    /// Signing-hash preimage for the payer, per [EIP-8130].
    ///
    /// `keccak256(EIP8130_PAYER_TYPE || rlp([all body fields through `payer`]))`
    /// with the `sender` slot replaced by the recovered sender address. The
    /// payer commits to the full transaction body — including the `payer` slot
    /// itself — and only the `sender_auth` / `payer_auth` slots (which live in
    /// the signed wrapper) are excluded.
    ///
    /// [EIP-8130]: https://eips.ethereum.org/EIPS/eip-8130
    pub fn payer_signature_hash(&self, resolved_sender: Address) -> B256 {
        let sender = Some(resolved_sender);
        let payload_length = self.rlp_encoded_fields_length_with_sender(&sender);
        let mut buf = Vec::with_capacity(1 + length_of_length(payload_length) + payload_length);
        buf.put_u8(Eip8130Constants::EIP8130_PAYER_TYPE);
        Header { list: true, payload_length }.encode(&mut buf);
        self.rlp_encode_fields_with_sender(&sender, &mut buf);
        keccak256(&buf)
    }
