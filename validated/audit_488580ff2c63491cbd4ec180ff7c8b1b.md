This confirms the vulnerability. Unlike its sibling factories, `MultisigFactory::create` has no `.then()` callback, no `is_promise_success()` check, and no `is_valid_account_id` validation on the constructed `account_id`, contrasting sharply with `lockup-factory/src/lib.rs`'s `create`/`on_lockup_create` pair and `staking-pool-factory/src/lib.rs`'s `create_staking_pool`/`on_staking_pool_create` pair, both of which explicitly refund `predecessor_account_id` on failure.

### Title
No refund on failed multisig deployment (unvalidated/oversized account id, no callback) - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` builds `account_id` via `format!("{}.{}", name, env::current_account_id())` with no length/validity check, and schedules `create_account().deploy_contract().transfer(deposit).function_call(...)` as a single un-chained `Promise` with no `.then()` callback. [1](#0-0)  If `name` is long enough that the resulting id exceeds the 64-character NEAR account-id limit, the receipt fails on-chain, and because there is no callback checking `is_promise_success()`, the attacher's deposit is never returned to them.

### Finding Description
The broken binding: `attacker_balance_after_failed_create == attacker_balance_before_create - gas_burnt` (i.e., a failed deployment must refund the deposit) is violated; instead `attacker_balance_after_failed_create == attacker_balance_before_create - deposit - gas_burnt`.

`create` computes `account_id = format!("{}.{}", name, env::current_account_id())` without calling `env::is_valid_account_id` on the result, unlike `staking-pool-factory/src/lib.rs`'s `create_staking_pool`, which explicitly asserts `env::is_valid_account_id(staking_pool_account_id.as_bytes())` before proceeding. [2](#0-1)  With `multisig-factory`'s own account id long enough (or `name` chosen at/near the 64-char limit), `account_id` exceeds the protocol's account-id length limit. The `Promise::new(account_id).create_account().deploy_contract(...).transfer(deposit).function_call(...)` call is a single batched receipt with no `.then()` follow-up. [3](#0-2)  When nearcore processes that receipt, `CreateAccount` fails because the target account id is invalid, causing the whole receipt (including the `Transfer` action carrying the attacker's deposit) to fail. Because the receipt's predecessor is the factory contract itself (not the original attacker), any refund from that failed receipt returns to the factory's own account balance, not to the attacker who called `create` and attached the deposit.

Compare this to the two sibling factories in the same repo, both of which route the deposit refund back to `env::predecessor_account_id()` in a callback:
- `lockup-factory/src/lib.rs`'s `create`/`on_lockup_create`, which calls `.then(ext_self::on_lockup_create(...))` and on failure does `Promise::new(predecessor_account_id).transfer(attached_deposit.0)`. [4](#0-3) 
- `staking-pool-factory/src/lib.rs`'s `create_staking_pool`/`on_staking_pool_create`, same pattern. [5](#0-4) 

`MultisigFactory::create` has neither the `is_valid_account_id` guard nor the callback/refund pattern, so the invariant "a failed deployment refunds the payer" does not hold for this contract. [6](#0-5) 

### Impact Explanation
The attacker's attached NEAR deposit is consumed with nothing returned: it is not credited to any account the attacker controls, and the multisig they intended to create never comes into existence. The funds end up refunded (by nearcore's own failed-receipt refund mechanics) to the factory contract's balance rather than to the attacker, so `multisig-factory`'s actual NEAR balance silently grows beyond what its (empty) contract state accounts for — an accounting divergence that "another party settles on" only if/when that balance is later moved (e.g., factory redeploy, account deletion, or any future logic that assumes the factory holds zero discretionary balance). This is repeatable by any account, for any deposit amount, once per attempt, matching the High severity category ("an accounting value diverging from reality where another party settles on it").

### Likelihood Explanation
No privileged role is required — any account can call `create` with an attached deposit and a `name` long enough (or crafted) so that `name.multisig-factory-account-id` exceeds NEAR's 64-character account-id limit. The attacker's only cost is the wasted deposit and gas per attempt (which is the loss itself, not a barrier), and the exploit is trivially repeatable across accounts and calls since `create` performs no state checks or dedup and takes no `#[init]`-gated permissions.

### Recommendation
Add a `.then()` callback (mirroring `lockup-factory`'s `on_lockup_create` and `staking-pool-factory`'s `on_staking_pool_create`) that calls `assert_self()`, checks `is_promise_success()`, and on failure issues `Promise::new(env::predecessor_account_id()).transfer(attached_deposit)`. Additionally, validate `account_id` with `env::is_valid_account_id(account_id.as_bytes())` before scheduling any promise, so an obviously invalid id is rejected synchronously (and its deposit refunded automatically by the runtime) rather than failing mid-receipt.

### Proof of Concept
Using `near-sdk-sim`/`near-workspaces` against `multisig-factory`:
1. Deploy `multisig-factory` under an account id whose length, combined with a `name` chosen at/near the 64-character account-id limit (e.g., `name` of length such that `format!("{}.{}", name, factory_account_id)` > 64 chars), guarantees the child account id is invalid.
2. Record attacker balance before calling `create(name, members, num_confirmations)` with a non-trivial attached deposit (e.g., 5 NEAR).
3. Call `create`, and `process_all()`/await the resulting receipt; assert the receipt for the batched `CreateAccount`/`Transfer`/`FunctionCall` actions failed (`ExecutionStatus::Failure`).
4. Assert `attacker_balance_after ≈ attacker_balance_before - deposit - gas_burnt` (deposit NOT refunded), proving `attacker_balance_after_failed_create != attacker_balance_before_create - gas_burnt`, in contrast to the equivalent test against `staking-pool-factory`'s `create_staking_pool`, where `on_staking_pool_create`'s failure branch returns the deposit and the equality holds.
