### Title
Stale scaled APR after `bufferPeriod` change overpays withdrawal receipts - ([contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`setEpochParams` allows the owner or manager to change `epochDuration` and `bufferPeriod`, but does not rescale the strategy APR. `lastApr` remains scaled using the previous duration and buffer. Subsequent withdrawal requests unscale that stale APR using the new parameters, producing an incorrect fixed receipt. If the buffer is reduced, requesters receive interest for buffer time that is no longer part of the epoch schedule.

### Finding Description
At epoch configuration, the strategy APR is scaled as:

```solidity
apr_scaled = apr_unscaled * (epochDuration + bufferPeriod) / epochDuration
```

through `_setScaledApr` and `IdleCreditVault.setAprsWithBuffer` (`contracts/IdleCDOEpochVariant.sol:544-546`, `contracts/strategies/idle/IdleCreditVault.sol:217-220`).

Withdrawal receipts remove the buffer component using the currently stored parameters:

```solidity
interest = amount * apr_scaled * epochDuration
         * epochDuration / (epochDuration + bufferPeriod)
```

in `_calcInterestWithdrawRequest` (`contracts/IdleCDOEpochVariant.sol:856-877`).

`setEpochParams` changes the denominator inputs without updating `lastApr` (`contracts/IdleCDOEpochVariant.sol:117-125`). For example, changing a `30 day + 5 day` configuration to `30 day + 0 day` leaves a previously configured 10% APR stored as 11.666…%. A withdrawal request then applies the full 11.666…% scaled APR for 30 days instead of the intended 10%.

The code explicitly warns that `bufferPeriod` must not be changed because interest calculations become wrong, but the setter still permits it.

### Impact Explanation
A KYC-passed tranche holder can request a withdrawal immediately after an honest manager changes the epoch parameters. The excessive receipt is recorded in `pendingWithdraws` and is funded by the borrower at the next `stopEpoch`.

With principal `P`, unscaled APR `r`, prior duration `D`, and prior buffer `B`, reducing the buffer to zero overpays the requester by:

```text
excess = P * r * B / 365 days
```

For a 10% APR and a 5-day prior buffer, this is approximately `0.13699%` of the requested principal. This is a direct transfer of excess borrower-funded assets to the attacker and reduces funds available to other lenders.

### Likelihood Explanation
The exploit requires an honest owner or manager to call `setEpochParams` with a different buffer or duration while withdrawal requests are enabled. This is an externally available configuration path, despite the inline warning. Once called, any eligible tranche holder can execute `requestWithdraw` and lock in the incorrectly scaled receipt before the next epoch.

### Recommendation
Do not allow `bufferPeriod` to change after initialization, matching the documented invariant. Alternatively, make parameter updates atomic with APR rescaling:

1. Accrue and settle pending accounting.
2. Compute the new scaled APR from `unscaledApr`, the new `epochDuration`, and new `bufferPeriod`.
3. Update `lastApr` in the same transaction.
4. Prevent parameter changes while stale withdrawal receipts or running-epoch accounting can still be valued under the old parameters.

### Proof of Concept
Insert this into the existing `test/foundry/IdleCreditVault.t.sol` fixture and run it against the suite’s deployed credit vault:

```solidity
function testStaleScaledAprAfterBufferChangeOverpaysWithdraw() external {
    uint256 amount = 1_000_000 * ONE_SCALE;

    // Remove fee effects so the assertion isolates the stale APR scaling.
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);
    _setManagementFee(0);

    uint256 trancheAmount = idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    uint256 principal =
        trancheAmount * cdoEpoch.tranchePrice(address(AAtranche)) /
        ONE_TRANCHE_TOKEN;

    // Initial fixture: epochDuration = 30 days, bufferPeriod = 5 days.
    // lastApr is therefore unscaledApr * 35 / 30.
    uint256 unscaledApr = creditVault.unscaledApr();

    // Honest manager reduces only the buffer. The scaled APR is not recalculated.
    vm.prank(manager);
    cdoEpoch.setEpochParams(30 days, 0);

    uint256 requested = cdoEpoch.requestWithdraw(
        trancheAmount,
        address(AAtranche)
    );

    uint256 intendedReceipt = principal +
        principal * (unscaledApr / 100) * 30 days /
        (365 days * ONE_TRANCHE_TOKEN);

    uint256 staleScaledReceipt = principal +
        principal * ((unscaledApr * 35 / 30) / 100) * 30 days /
        (365 days * ONE_TRANCHE_TOKEN);

    assertEq(requested, staleScaledReceipt);
    assertGt(requested, intendedReceipt);

    uint256 excess = requested - intendedReceipt;
    assertApproxEqAbs(
        excess,
        principal * unscaledApr * 5 days /
            (365 days * 100 * ONE_TRANCHE_TOKEN),
        2
    );
}
```

The receipt can subsequently be funded through the normal `startEpoch`/`stopEpoch` flow and claimed with `claimWithdrawRequest`, making the excess transferable rather than only an accounting discrepancy.
