### Title
Stale instant-withdraw per-epoch basis inflates default recovery reserve and permanently freezes claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out a funded instant receipt but never clears the per-epoch accounting entries `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. The already-paid amount survives as a stale ("default-initialized") value that is later re-read as a live claim if a default is finalized for that same epoch, corrupting `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and the per-user defaulted claim.

### Finding Description
The instant-withdraw request path records receipt basis in three places [1](#0-0) :

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

When the CDO funds the request, `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` [2](#0-1) , and when the user claims, `claimInstantWithdrawRequest` only zeroes `instantWithdrawsRequests[_user]` and transfers at par [3](#0-2) . Neither path touches `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` — the paid receipt leaves phantom basis behind, analogous to reading an uninitialized/stale buffer as valid data.

If the borrower then defaults in that same epoch, `finalizeDefaultRecovery` treats the phantom basis as real:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [4](#0-3) .
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` and counts the phantom `A1` as underlying already held by the strategy — but those tokens were already transferred to the user [5](#0-4) .
- `finalizeDefaultRecovery` bakes the phantom amount into both `defaultRecoveryReserve` and `defaultRecoveryPrice` without pulling any tokens for it [6](#0-5) .

On the claim side, `_claimDefaultedInstantWithdrawRequest` executes `instantWithdrawsRequests[_user] -= claimBasis` where `claimBasis` includes the already-paid first receipt, so it underflows for the double-requesting user and reverts forever [7](#0-6) .

### Impact Explanation
Concrete sequence in a running epoch (any mode; only requires instant withdraws enabled):

1. KYC'd lender requests instant withdraw `A1` in epoch N via `IdleCDOEpochVariant.requestInstantWithdraw`.
2. Manager/borrower funds it; CDO calls `collectInstantWithdrawFunds(A1)`; user calls `claimInstantWithdrawRequest` and is paid `A1` at par. `instantWithdrawsRequestsByEpoch[user][N]` and `instantWithdrawClaimsByEpoch[N]` still hold `A1`.
3. Same user requests instant withdraw `A2` in epoch N (e.g., the funded amount only covered part of the queue, or new liquidity arrived).
4. Epoch N stops with the borrower under-repaying → `defaulted()`. Manager calls `finalizeDefault(recovered, source)`.
5. `defaultPendingClaimBasis` = `pendingWithdraws + (A1 + A2)` though only `A2` is a real unfunded instant claim; `prefundedReserve` = `A1` of tokens the strategy no longer holds.

Two accepted-impact outcomes:

- **Recovery insolvency / permanent freezing**: `defaultRecoveryReserve` and `defaultRecoveryPrice` are computed with phantom `A1` in the numerator and denominator. Total claims against the reserve exceed the actual token balance by `A1`, so the last defaulted claimants' `underlyingToken.safeTransfer` in `_transferDefaultRecovery` reverts — their recovery payout is permanently frozen (loss ≈ `A1` distributed across claimants).
- **Direct permanent freeze for the requester**: `instantWithdrawsRequests[user] (A2) -= claimBasis (A1 + A2)` underflows on every `claimInstantWithdrawRequest` call once `defaultInstantWithdrawsFinalized` is true, permanently blocking that user's `A2` claim.

No existing guard prevents it: `_onlyIdleCDO` is satisfied via the normal CDO entry points, `_transferFundedClaim`'s reserve check runs after the corrupted price was stored, and the `defaultInstantWithdrawsFinalized` gate is precisely what routes execution into the buggy path [8](#0-7) .

### Likelihood Explanation
Requires only ordinary unprivileged actions: an instant withdraw request that gets funded and claimed, a second instant request in the same request epoch, then a borrower default with `pendingInstantWithdraws != 0` at finalization. The partially-funded-instant-then-default scenario is explicitly anticipated by the code comments (partial funding of the instant queue is a documented case in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`), so this is a reachable, realistic sequence rather than a corner case. The attacker needs no privileged role — the borrower default is an external market event, not attacker-controlled privileged behavior.

### Recommendation
In `claimInstantWithdrawRequest` (and equivalently wherever a funded instant receipt is consumed), clear the per-epoch records for the epoch(s) the receipt was created in: subtract the claimed amount from `instantWithdrawClaimsByEpoch[reqEpoch]` and zero `instantWithdrawsRequestsByEpoch[_user][reqEpoch]`. This likely requires storing the request epoch per user (e.g., a `lastInstantWithdrawRequest` marker, mirroring `lastWithdrawRequest`) so the funded-claim path knows which epoch bucket to decrement. Alternatively, derive claimable instant amounts solely from `instantWithdrawsRequestsByEpoch` and always delete the entry on payout, so defaulted-epoch basis can never include already-paid receipts.

### Proof of Concept
Foundry fork PoC sketch (pattern follows `test/foundry/IdleCreditVault.t.sol` default-recovery tests, e.g. `testFinalizeDefaultHaircutsApr0PendingRedeemsWithAdjustedInterestBasis`):

```solidity
function testStaleInstantBasisCorruptsDefaultRecovery() external {
    address user = makeAddr('instant-user');
    uint256 A1 = 5_000 * ONE_SCALE;
    uint256 A2 = 3_000 * ONE_SCALE;

    // deposit + epoch machinery so pool is in buffer phase of epoch N
    _depositWithUser(user, 20_000 * ONE_SCALE, true);
    idleCDO.depositAA(20_000 * ONE_SCALE);

    // epoch N: request instant withdraw A1
    vm.prank(user);
    cdoEpoch.requestInstantWithdraw(A1, address(AAtranche));

    // manager/borrower funds A1; CDO calls strategy.collectInstantWithdrawFunds(A1)
    _fundInstantWithdraw(A1);              // pulls underlyings into strategy

    // user claims at par — instantWithdrawsRequests[user] = 0,
    // but instantWithdrawsRequestsByEpoch[user][N] and instantWithdrawClaimsByEpoch[N] still = A1
    vm.prank(user);
    cdoEpoch.claimInstantWithdrawRequest();

    // same epoch N: second instant request A2 (left unfunded)
    vm.prank(user);
    cdoEpoch.requestInstantWithdraw(A2, address(AAtranche));

    // borrower under-repays -> default, then finalize with partial recovery
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, _expectedRepayShortfall());
    _checkDefault();

    uint256 recovered = _partialRecoveryAmount();
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    IdleCreditVault cv = IdleCreditVault(address(strategy));
    // phantom A1 counted as held reserve that was already paid out
    assertEq(cv.defaultInstantWithdrawsFinalized(), true);

    // user's own claim permanently reverts: A2 - (A1 + A2) underflows
    vm.prank(user);
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Caveat: the exact epoch alignment (the second request must land in the same `epochNumber` that becomes `defaultRecoveryEpoch`) follows the same request-then-default ordering used by the existing `instantUser` default tests in `IdleCreditVault.t.sol` around line 4531; the arithmetic corruption (`A1` phantom basis in `instantWithdrawClaimsByEpoch`, the underflow at `instantWithdrawsRequests[_user] -= claimBasis`) is directly readable from `IdleCreditVault.sol` lines 371-392, 644-649, 685-696, and 842-856.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
