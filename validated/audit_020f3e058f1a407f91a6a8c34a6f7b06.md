### Title
Stale `instantWithdrawClaimsByEpoch` basis from already-claimed instant withdrawals leaks into default recovery accounting and inflates `defaultRecoveryPrice` — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` pays a funded instant-withdraw receipt but only clears the aggregate `instantWithdrawsRequests[_user]` counter. The per-epoch receipt bookkeeping — `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` — is never decremented on a successful funded claim. If the borrower defaults in the same epoch while some other instant request is still unfunded (`pendingInstantWithdraws != 0`), `finalizeDefaultRecovery` reads that stale epoch data: `defaultPendingClaimBasis` adds the already-paid amount into the claim basis, and `_defaultPrefundedInstantReserve` counts the same already-paid amount as underlying still held by the strategy. The recovery price is therefore computed on phantom funds, overpaying early recovery claimants and leaving the `defaultRecoveryReserve` insolvent for the remaining ones — the same bug class as the Quarkus/Vert.x leak, where stale "parent" state silently contaminates a new transaction's accounting.

### Finding Description
On a funded instant-withdraw claim, only the aggregate is cleared:

- `claimInstantWithdrawRequest` reads `instantWithdrawsRequests[_user]`, burns it, and zeroes it, but never touches `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. [1](#0-0) 
- The only place those per-epoch mappings are decremented is the defaulted-epoch path `_claimDefaultedInstantWithdrawRequest`. [2](#0-1) 
- `collectInstantWithdrawFunds` only reduces `pendingInstantWithdraws`, not the per-epoch basis. [3](#0-2) 

At default finalization this stale epoch data is consumed as if it were live:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` (which still includes the already-paid receipt) whenever `pendingInstantWithdraws != 0`. [4](#0-3) 
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant`; the already-paid amount is therefore counted as underlying "already held" by the strategy even though it was transferred out to the claimant. [5](#0-4) 
- `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` where both terms contain the phantom amount. [6](#0-5) 

Let `A` be an instant receipt that was funded and fully paid out earlier in epoch `N`, and `B` an unfunded instant receipt (`pendingInstantWithdraws = B`) in the same epoch when `finalizeDefaultRecovery` runs. Then `instantBasis = A + B`, so `totalBasis` is overstated by `A` and `prefundedReserve` is overstated by `A` (phantom — the real strategy balance is lower by `A` since it was paid out). Post-finalization:

- `defaultRecoveryPrice = (realReserve + A) / (realBasis + A)` — every defaulted claim receives a haircut computed as if `A` underlying were still sitting in the vault.
- Claimants are paid `(claimBasis * recoveryPrice) / RECOVERY_FULL` via `_transferDefaultRecovery`, which draws down the finite `defaultRecoveryReserve`. The aggregate payout entitlement exceeds the real reserve by the phantom `A`, so the last claimants' transfers either underflow the reserve or the strategy is drained, leaving their claims unpaid (insolvency) or reverting (permanent freezing of unclaimed recovery).

The guard in `requestWithdraw` that forces claiming of old receipts does not apply to the instant path, and `defaultInstantWithdrawsFinalized` is set precisely when `pendingInstantWithdraws != 0` — the exact precondition that makes the stale basis get consumed. [7](#0-6) 

### Impact Explanation
Direct loss of funds for defaulted-epoch claimants. If an attacker can be both the early instant claimant (`A`) and a holder of defaulted receipts (`B`, plus normal withdraw receipts), they receive part of their own payout twice in effect: once at par pre-default and once embedded in the inflated `defaultRecoveryPrice` numerator that boosts every basis unit's payout while the reserve stays fixed. Any claimant acting first — including the attacker — extracts more than their fair share; whoever claims last receives less than `claimBasis * fairPrice` or cannot claim at all because the reserve is exhausted. The loss equals the overstated `prefundedReserve` amount `A`, i.e., the full size of any instant withdrawal funded and claimed earlier in the defaulted epoch.

### Likelihood Explanation
Requires: (1) an epoch in which at least one instant withdrawal is fully funded and claimed (routine — `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` exist for exactly this), (2) a second unfunded instant request outstanding when the borrower defaults in that same epoch, and (3) default finalization. All steps are achievable by unprivileged actors sequencing around honest manager/borrower calls; the attacker only needs to be a KYC'd lender making instant withdraw requests and defaulted receipts. The per-epoch basis is never cleared anywhere else, so the stale-data precondition is guaranteed whenever it is set up.

### Recommendation
Keep per-epoch instant bookkeeping consistent with the aggregate: in `claimInstantWithdrawRequest`, delete `instantWithdrawsRequestsByEpoch[_user][epoch]` entries and decrement `instantWithdrawClaimsByEpoch[epoch]` for the epochs being paid (or track the user's request epoch analogously to `lastWithdrawRequest`). Alternatively, decrement `instantWithdrawClaimsByEpoch[epochNumber]` in `collectInstantWithdrawFunds`/`_transferFundedClaim` so the per-epoch basis always reflects only unpaid receipts.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testStaleInstantBasisInflatesDefaultRecovery() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    address alice = makeAddr('alice');   // early instant claimer
    address bob   = makeAddr('bob');     // unfunded instant requester

    // 1) deposits, start epoch N
    _depositWithUser(alice, 100_000 * ONE_SCALE, true);
    _depositWithUser(bob,   100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    uint256 epoch = vault.epochNumber();

    // 2) alice requests instant withdraw; CDO funds it via collectInstantWithdrawFunds
    vm.prank(alice);
    cdoEpoch.requestInstantWithdraw(50_000 * ONE_SCALE); // CDO-side entry point
    // manager/CDO moves available liquidity to strategy
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds(50_000 * ONE_SCALE);
    vm.prank(alice);
    cdoEpoch.claimInstantWithdrawRequest();              // paid at par
    // stale basis remains:
    assertEq(vault.instantWithdrawClaimsByEpoch(epoch), 50_000 * ONE_SCALE);

    // 3) bob requests instant withdraw, left unfunded
    vm.prank(bob);
    cdoEpoch.requestInstantWithdraw(10_000 * ONE_SCALE);
    assertEq(vault.pendingInstantWithdraws(), 10_000 * ONE_SCALE);

    // 4) borrower defaults in same epoch; finalize with real recovered funds R
    _triggerBorrowerDefault();                           // helper: stopEpoch with default
    uint256 realReserve = /* actual recovered + held underlying */;
    vm.prank(manager);
    cdoEpoch.finalizeDefault(realReserve);

    // 5) recovery price is computed on instantBasis = 60k but real prefunded is 0
    //    defaultRecoveryPrice > realReserve / realBasis  -> phantom 50k counted
    uint256 price = vault.defaultRecoveryPrice();
    uint256 basis = vault.defaultPendingClaimBasis();    // includes alice's stale 50k
    // total entitled payout (price * basis) exceeds realReserve by ~50k worth:
    // last claimant's _transferDefaultRecovery drains reserve -> insolvency/revert
    // bob claims first and is overpaid relative to fair share; a later defaulted
    // withdraw claimant reverts or receives truncated payout.
}
```

    uint256 pendingInstant = pendingInstantWithdraws;

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
