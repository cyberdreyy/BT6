### Title
Owner-check runs after replay-guard recording, letting attackers pre-poison a victim's request digest and cause denial-of-service - (`core/capabilities/vault/authorizer.go`)

### Summary
`authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord` before `validateSecretOwnersMatchAuthorized`, so a request that is ultimately rejected for owner mismatch still permanently (until expiry) consumes the replay-guard slot for its digest. An attacker who can predict or reconstruct a victim's forthcoming request digest can pre-register that digest via an owner-mismatched request, causing the victim's later legitimate identical-digest request to be rejected with `ErrRequestAlreadySeen`.

### Finding Description
In `AuthorizeRequest`, the order is: authorize via allowlist/JWT → `replayGuard.CheckAndRecord(digest, expiresAt)` → `validateSecretOwnersMatchAuthorized(req, owner)`. [1](#0-0) 

`CheckAndRecord` unconditionally inserts the digest into the `seen` map with the caller-supplied `expiresAt` the first time it's observed, and only afterward is ownership validated: [2](#0-1) 

The digest itself is derived purely from request content (`req.Digest()` over Method+Params+ID), independent of the authorized owner, and is compared against `allowedRequests` fetched from the on-chain workflow registry allowlist purely by digest value, regardless of which owner registered it: [3](#0-2) [4](#0-3) 

Exploit flow:
1. Attacker (a legitimate but distinct workflow owner who can register allowlist entries under their own address on the workflow registry) predicts the exact `Method+Params+ID` bytes of a victim's forthcoming `SecretsCreate`/`Update`/`Delete` request (preconditions given).
2. Attacker allowlists that exact digest under their own owner address with a long expiry.
3. Attacker submits a request with that same digest but whose `Params` embed the victim's owner (`Id.Owner = victim`), so `allowListBasedAuth.AuthorizeRequest` succeeds (digest matches, workflowOwner=attacker) and returns an `AuthResult`.
4. `CheckAndRecord` records the digest as seen with attacker's chosen `expiresAt` and returns nil (first time seen).
5. `validateSecretOwnersMatchAuthorized` then correctly rejects the request because `Id.Owner` (victim) ≠ `AuthorizedOwner()` (attacker), so `AuthorizeRequest` returns an ownerErr — but the replay-guard damage is already done. [5](#0-4) 
6. When the victim later submits their own byte-identical legitimate request (which would independently pass allowlist/JWT authorization and owner validation), `CheckAndRecord` finds the digest already in `seen` and returns `ErrRequestAlreadySeen` before the owner check is even reached, blocking the legitimate request until the attacker-chosen expiry passes.

The root cause is that state mutation (`CheckAndRecord`) happens before the request has been fully validated end-to-end (owner binding check), violating the stated invariant that authorization/replay-guard state must not be poisoned by requests that ultimately fail authorization.

### Impact Explanation
This is a targeted, repeatable denial-of-service against a specific victim's legitimate Vault secret operation (create/update/delete/list), which can block secret management for a workflow owner for up to the attacker-chosen expiry window (bounded by the registry's max allowlist duration). This matches Chainlink's bounty "Denial of Service" impact class for a scoped, addressable victim rather than node-wide.

### Likelihood Explanation
Exploitability strictly requires the attacker to predict/reconstruct the exact digest (Method+Params+ID) of a not-yet-sent victim request — this is the given precondition. Given that, the attack needs only unprivileged capability to register an allowlist entry for themselves (or, in the JWT path, obtain a valid JWT for their own tenant/org whose `request_digest` claim matches the crafted content) and to submit one JSON-RPC/gateway request — no elevated privileges. It is fully repeatable each time a new victim digest can be predicted.

### Recommendation
Move `validateSecretOwnersMatchAuthorized` (and any other content-integrity validation) before `replayGuard.CheckAndRecord`, so that the replay-guard state is only mutated for requests that pass full authorization (auth mechanism success AND owner binding). Alternatively, make `CheckAndRecord` a two-phase operation (reserve-then-commit) where the digest is only durably recorded after all checks succeed, with the reservation rolled back on any subsequent failure.

### Proof of Concept
Go unit test in `core/capabilities/vault/authorizer_test.go` style:
1. Construct `req` with `Method: MethodSecretsCreate`, `Params` containing `EncryptedSecret.Id.Owner = "0xattacker"` is swapped for `Owner = "0xvictim"` while `AuthorizeRequest` returns `AuthResult{workflowOwner: "0xattacker", digest: D, expiresAt: future}` (mock `allowListBasedAuth`/`jwtBasedAuth` to simulate this).
2. Call `a.AuthorizeRequest(ctx, req)` — assert it returns a non-nil owner-mismatch error (current behavior).
3. Build a second request `req2` with identical `Method`/`Params` (with `Owner="0xvictim"`)/`ID` as `req` (so `req2.Digest() == D`), and mock the auth mechanism to return `AuthResult{workflowOwner: "0xvictim", digest: D, expiresAt: future}`.
4. Call `a.AuthorizeRequest(ctx, req2)` — assert current (buggy) behavior returns `vault.ErrRequestAlreadySeen` even though `req2`'s owner matches its authorized owner, proving the legitimate request is blocked.
5. After applying the fix (owner check before replay-guard record), re-run the same sequence and assert step 2 still fails with owner mismatch AND step 4 now succeeds with `authResult.AuthorizedOwner() == "0xvictim"`.

func validateSecretOwnersMatchAuthorized(req jsonrpc.Request[json.RawMessage], workflowOwner string) error {
	switch req.Method {
	case vaulttypes.MethodPublicKeyGet:
		return nil
	case vaulttypes.MethodSecretsCreate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var createReq vaultcommon.CreateSecretsRequest
		if err := json.Unmarshal(*req.Params, &createReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(createReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsUpdate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var updateReq vaultcommon.UpdateSecretsRequest
		if err := json.Unmarshal(*req.Params, &updateReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(updateReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsDelete:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var deleteReq vaultcommon.DeleteSecretsRequest
		if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
			return err
		}
		return validateSecretIdentifierOwnerMismatch(deleteReq.Ids, workflowOwner)
	case vaulttypes.MethodSecretsList:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var listReq vaultcommon.ListSecretIdentifiersRequest
		if err := json.Unmarshal(*req.Params, &listReq); err != nil {
			return err
		}
		if vaultutils.NormalizeOwner(listReq.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("list secrets owner %q does not match authorized workflow owner %q", listReq.Owner, workflowOwner)
		}
		return nil
	default:
		return fmt.Errorf("owner validation not implemented for method %q", req.Method)
	}
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
