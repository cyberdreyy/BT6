### No Vulnerability found for this question.

**Analysis basis:**

`SignableMessage<T>` serializes as `discriminant: MessageDiscriminant` (a fixed `u32`, little-endian, 4 bytes) followed by `msg: &T` [1](#0-0) . The discriminant is derived from `SignableMessageType` via `MessageDiscriminant::new_on_chain(nep)`, computed as `MIN_ON_CHAIN_DISCRIMINANT + nep` for fixed constants `NEP_366_META_TRANSACTIONS = 366` and `NEP_611_GAS_KEYS = 611` [2](#0-1) .

`DelegateAction::get_nep461_hash` always tags with `SignableMessageType::DelegateAction` (discriminant = `MIN_ON_CHAIN_DISCRIMINANT + 366`), and `VersionedDelegateActionPayload::get_nep461_hash` always tags with `SignableMessageType::DelegateActionV2` (discriminant = `MIN_ON_CHAIN_DISCRIMINANT + 611`) [3](#0-2) [4](#0-3) . These discriminant values are hardcoded by the verifying code itself — never attacker-supplied — so the first 4 bytes of the borsh-serialized `SignableMessage` (and therefore the hash preimage) are unconditionally different between the two message types, independent of anything an attacker controls inside `actions`, `method_names`, or `args`. No amount of "byte-alignment" padding in nested `NonDelegateAction` fields can make these leading 4 bytes coincide, because they are fixed constants baked into the code, not part of the serialized payload the attacker constructs.

Consequently `SignedDelegateAction::verify()` always recomputes the hash tagged with `DelegateAction` (366) and `VersionedSignedDelegateAction::verify()` always recomputes it tagged with `DelegateActionV2` (611) [5](#0-4) [6](#0-5) . A signature produced under one discriminant cannot verify under the other regardless of any attacker-chosen padding, since the preimages diverge at the very first bytes. This is exactly what the repo's own regression test asserts: signing a `VersionedDelegateActionPayload::V2` under the V1 (`DelegateAction`) discriminant and confirming `verify()` returns `false` [7](#0-6) .

The premise that a "structural" collision (matching suffix bytes after a leading discriminant byte) could produce a cross-version replay is incorrect: the domain-separation discriminant is a full 4-byte constant prepended by trusted code, not something whose value or position an attacker can manipulate via padding. Defeating this would require an actual cryptographic hash collision (SHA-256, per `near_primitives_core::hash::hash`), which is outside the scope of a structural/byte-alignment attack and not a demonstrated, reachable vulnerability.

impl From<SignableMessageType> for MessageDiscriminant {

        // unwrapping here is ok, we know the constant NEP numbers used are in range
        match ty {
            SignableMessageType::DelegateAction => {
                MessageDiscriminant::new_on_chain(NEP_366_META_TRANSACTIONS).unwrap()
            }
            SignableMessageType::DelegateActionV2 => {
