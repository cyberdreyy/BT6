### Title
Replay guard digest is recorded before owner validation, allowing attacker-submitted colliding-digest requests to pre-empt a victim's genuine request as a false "replay" - ([File: core/capabilities/vault/authorizer.go], function `authorizer.AuthorizeRequest`)

### Finding Description
`authorizer.AuthorizeRequest` runs three sequential checks: (1) resolve `AuthResult` via `authorizeRequest` (allowlist or JWT path), (2) `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())`, and only then (3) `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())`. [1](#0-0) 

`RequestReplayGuard.CheckAndRecord` keys purely on the `digest` string parameter, with no owner/identity component folded into the map key itself. [2](#0-1) 

Because the digest is recorded in step (2) *before* the owner-binding check in step (3), any request whose auth mechanism yields the same `Digest()` value consumes the replay-guard slot regardless of whether it subsequently fails owner validation. If an attacker can construct or predict a request that hashes to the same digest as a victim's genuine, not-yet-submitted request (e.g., identical `Method`+`Params` with default/empty `RequestId` and generic secret parameters), submitting it first causes `CheckAndRecord` to succeed and store that digest, and the attacker's own request is then rejected downstream by `validateSecretOwnersMatchAuthorized` for owner mismatch — but the victim's subsequent, legitimate, byte-identical request will hit `ErrRequestAlreadySeen` in the replay guard and be rejected as a duplicate, even though it was never actually processed.

I was unable to directly inspect the exact digest-derivation formula in `allow_list_based_auth.go` / `jwt_based_auth.go` within the available tool budget, so I cannot conclusively confirm whether the digest already incorporates a signature or JWT-bound owner claim that would prevent two different owners from producing a colliding digest for structurally similar params. This is a material gap: if the digest is derived from the JWT/signature bytes (which are owner-specific), the described collision would not be achievable by an unprivileged third party. Given the uncertainty, this should be treated as a partially-verified finding rather than a fully proven one.

### Impact Explanation
If the digest can collide across owners, the effect is a DoS against a specific victim's legitimate vault request (secret creation/update/deletion/list), which would be silently rejected as `ErrRequestAlreadySeen`. This does not by itself grant the attacker access to the victim's secrets, because the attacker's own request would still fail the subsequent owner-binding check (`validateSecretOwnersMatchAuthorized`) — so cross-owner state confusion where the attacker's data is stored is not demonstrated by the current control flow. The confirmed issue is check-ordering (digest recorded prior to owner validation) rather than confirmed absence of owner binding in the digest itself.

### Likelihood Explanation
Exploitability strictly depends on facts I could not verify: (1) whether the digest formula binds to owner/signature material, and (2) whether default/common request params (e.g. empty `RequestId`) are common enough in practice for two independent callers to produce colliding params. Without confirming the digest source, likelihood cannot be firmly established.

### Recommendation
Regardless of the digest formula, move the owner-binding validation (`validateSecretOwnersMatchAuthorized`) before the replay-guard `CheckAndRecord` call in `authorizer.AuthorizeRequest`, so that a request which fails owner validation never consumes a digest slot. Additionally, confirm that `Digest()` implementations in `allow_list_based_auth.go` and `jwt_based_auth.go` incorporate the authenticated owner/signature (not just raw `Method`+`Params` bytes) so that two different authorized owners cannot produce the same digest.

### Proof of Concept

Construct two `jsonrpc.Request[json.RawMessage]` with identical `Method` (`MethodSecretsCreate`) and identical `Params` bytes (e.g., same generic secret ID and empty `RequestId`), but arrange for the underlying auth mechanism (mock allowlist/JWT) to report two different `AuthorizedOwner()` values for each (owner A vs owner B) while `Digest()` returns the same value for both (mock `AuthResult` accordingly to isolate the digest-collision scenario, since actual digest derivation could not be verified here).
2. Call `authorizer.AuthorizeRequest` with owner-A request first; assert it fails with an owner-mismatch error from `validateSecretOwnersMatchAuthorized` (since payload owner won't match, per test setup) but the replay guard already recorded the digest.
3. Call `authorizer.AuthorizeRequest` with owner-B's genuine, matching request (same digest); assert it incorrectly returns `ErrRequestAlreadySeen` instead of succeeding, proving the digest-then-owner check order allows a rejected/attacker request to consume a legitimate victim's replay-guard slot.
4. As a follow-up, add a test directly against `allow_list_based_auth.go`/`jwt_based_auth.go` digest computation to confirm whether owner/signature material is included, to fully resolve whether cross-owner digest collisions are practically achievable.

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
