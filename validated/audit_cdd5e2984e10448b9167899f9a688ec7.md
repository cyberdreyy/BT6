### Title
Unauthenticated `InitializeBuffer` allows front-running/hijacking of BPF Upgradeable Loader buffer accounts - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `UpgradeableLoaderInstruction::InitializeBuffer` handler in the BPF Upgradeable Loader sets the `authority_address` of a loader-owned buffer account purely from an unauthenticated account key, with no signature check on either the buffer account or the proposed authority. Any transaction sender who can name a loader-owned, `Uninitialized` buffer account can claim ownership of it, exactly mirroring the reported `GenericOracle.initialize()` pattern where the first caller "wins" an unauthenticated initializer.

### Finding Description
`process_loader_upgradeable_instruction` handles `InitializeBuffer` as follows: [1](#0-0) 

The only precondition checked is that the target account's state is `UpgradeableLoaderState::Uninitialized`. There is:
- No signer check on the buffer account (`instruction_context.try_borrow_instruction_account(0)`).
- No signer check on the proposed `authority_key`, which is read directly from `get_key_of_instruction_account(1)` and stored as the new authority — the "authority" does not even need to consent to being named.
- No check that the transaction sender/payer has any relationship to the account being initialized.

Because a writable account's data can only be mutated by its owning program (the loader), the only real precondition is that the buffer account already has `owner == bpf_loader_upgradeable::id()` and `state == Uninitialized`. Once an account reaches that state — for example immediately after a `CreateAccount` assigning ownership to the upgradeable loader, but before the legitimate deployer's own `InitializeBuffer` instruction lands — *any* other transaction naming that same buffer pubkey can call `InitializeBuffer` first and set an attacker-controlled `authority_address`. This is structurally identical to the reported bug class: an initializer that anyone can call to set a value that should only ever be set by the rightful owner, enabling a front-run.

Compare this with `programs/system/src/system_instruction.rs::initialize_nonce_account`, which similarly transitions `Uninitialized -> Initialized`, but at least the durable-nonce initializer is normally invoked atomically with account creation and its authority is meaningful only once initialized; the loader's `InitializeBuffer` has the same "first initializer wins, no signature required" weakness but is compounded by the fact that the "authority" field is fully attacker-chosen and unauthenticated.

### Impact Explanation
If a legitimate deployer's `CreateAccount` (assigning ownership to `bpf_loader_upgradeable`) is observed in the mempool/gossip before its paired `InitializeBuffer` instruction is committed — or if tooling ever splits buffer creation from buffer initialization across separate transactions (common when large program uploads are chunked to respect transaction size limits) — an attacker can race an `InitializeBuffer` instruction referencing the same buffer pubkey and set themselves (or an arbitrary key) as `authority_address`. This:
- Denies service to the legitimate deployer, whose subsequent `Write`/`DeployWithMaxDataLen`/`Upgrade` instructions will fail with `IncorrectAuthority`, since those all gate on `authority_address` matching a signer, per [2](#0-1) .
- Gives the attacker exclusive write control over the buffer's contents (via `Write`, which they can now sign for), letting them stage arbitrary bytecode in an account that a victim (or automation) might later reference for deployment, a precursor to malicious code substitution.

This does not by itself move funds or directly corrupt consensus, but it is an unauthenticated state-mutating instruction that can hijack control of a security-critical account (a to-be-deployed program's buffer), satisfying the "no signer/owner check on a privileged initializer" bug class called out in the report.

### Likelihood Explanation
Exploitation requires either (a) observing an in-flight `CreateAccount` (owner=`bpf_loader_upgradeable`) transaction before its accompanying `InitializeBuffer` commits, or (b) any workflow where buffer-account creation and initialization are not strictly atomic in the same transaction. Standard `create_buffer` builders package both instructions atomically, which limits the practical race window; however, nothing in `process_loader_upgradeable_instruction` itself enforces atomicity or authentication — the vulnerability is a missing access-control check in the instruction handler itself, not merely a client-side convention. Any future or third-party tooling, program, or CPI path that creates a loader-owned, uninitialized buffer account and defers `InitializeBuffer` to a later instruction/transaction is immediately exploitable with no additional preconditions.

### Recommendation
Require a signer for the `InitializeBuffer` instruction: at minimum, require the account being named as `authority_address` (account index 1) to be a signer of the transaction, so an authority cannot be assigned without its own consent. Additionally, consider requiring the buffer account itself (or its creator, tracked via metadata) to sign, closing the atomicity gap. This mirrors adding an `onlyOwner`-style guard as recommended in the original report, translated to Solana's model as a required-signer check.

### Proof of Concept
1. Victim submits `CreateAccount(buffer_pubkey, owner = bpf_loader_upgradeable::id())` in transaction T1 (or T1 includes both `CreateAccount` and `InitializeBuffer`, but attacker observes T1 in the mempool before it lands).
2. Attacker crafts transaction T2 containing only:
   ```
   UpgradeableLoaderInstruction::InitializeBuffer
   accounts: [buffer_pubkey (writable, not signer), attacker_pubkey (authority, not signer)]
   ```
   and submits it to land immediately after T1's `CreateAccount` executes but before the victim's own `InitializeBuffer` (if in a separate transaction) commits.
3. `process_loader_upgradeable_instruction` sees `buffer.get_state()? == Uninitialized`, and unconditionally sets `authority_address = Some(attacker_pubkey)` — see [3](#0-2) . No signature from `attacker_pubkey` or from the buffer account is required.
4. Victim's later `Write`/`DeployWithMaxDataLen` calls against `buffer_pubkey` now fail `IncorrectAuthority`, while the attacker can freely `Write` malicious ELF bytes into the hijacked buffer.
