## Title
Stale confirmations from deleted multisig keys still count toward the confirmation threshold, allowing request execution below the intended live-member quorum — (`multisig/src/lib.rs`)

### Summary
The `RubiconMarket` bug pattern — a disable/validity check that is misplaced so a value that should invalidate an action no longer does — has a direct analog in `MultiSigContract`. When a key is deleted via `DeleteKey`, the contract only purges *requests the deleted key originated*, but never scrubs that key's *confirmations* recorded on other still-pending requests. Those stale confirmations remain counted when tallying `num_confirmations`, letting a request execute using approvals from keys that are no longer valid signers on the account.

### Finding Description
`confirm()` tallies approvals purely by set size, without re-validating that every public key in the `confirmations` set is still an active key on the contract account: [1](#0-0) 

`DeleteKey` execution only cleans up requests *created* by the deleted key (`r.signer_pk == pk`); it never iterates other requests' `confirmations` sets to remove the deleted key's prior votes: [2](#0-1) 

Sequence that breaks the binding `confirmations counted == approvals from currently authorized keys`:
1. `num_confirmations = 3`. Members A, B, C, D each hold a key.
2. A calls `add_request` for request `R1` (e.g. a `Transfer`). B and D call `confirm(R1)`. `confirmations[R1] = {B, D}` (len 2, below threshold).
3. Separately, the group revokes D via a `DeleteKey{public_key: D}` multisig request (confirmed by A, B, C). Execution runs the `DeleteKey` branch: it removes `D`'s own outstanding requests and `num_requests_pk[D]`, then calls `promise.delete_key(D)`. It does **not** touch `confirmations[R1]`, so `{B, D}` is untouched even though `D` is now an invalid key on the account.
4. C later calls `confirm(R1)`. `confirmations.len() + 1 == 3 >= num_confirmations`, so `execute_request` fires the `Transfer`.
5. The transfer executed with only two currently-valid keys (B and C) actually approving it "live"; D's approval is a residue from a key that no longer exists on the account.

### Impact Explanation
This is a Critical-class issue per the custody rules: **a multisig request executed below threshold**. The `num_confirmations` (K-of-N) guarantee is the sole authorization control gating `Transfer`, `FunctionCall`, `AddKey`, `DeleteKey`, etc. If stale confirmations from removed keys count toward the quorum, an attacker only needs to get `num_confirmations - 1` *live* confirmations plus one confirmation that was cast before its key was revoked, effectively lowering the real quorum by one (or more, if several keys were revoked while their confirmations lingered on unexecuted requests). Given enough churn in key membership (a normal, expected operational event — not requiring any bad-faith owner action), arbitrary funds held by the multisig account can be moved with fewer genuinely live approvals than the operator configured, breaking the equality between "confirmations recorded" and "confirmations from members currently entitled to grant them."

### Likelihood Explanation
Likelihood is moderate: it requires (a) a pending, unconfirmed request with at least one confirmation from a key, (b) that key subsequently being deleted (a routine, expected multisig operation — key rotation, offboarding, compromise response), and (c) the pending request later being confirmed to threshold. No privileged/owner-only step beyond normal `confirm`/`DeleteKey` usage is needed, and the flaw is silent — nothing in `confirm()` or `DeleteKey` execution signals that stale approvals exist, so operators have no visibility that a request's true "live" support is below what `get_num_confirmations` implies.

### Recommendation
When executing `DeleteKey` (and the analogous `DeleteMember` in `multisig2/src/lib.rs`), iterate over **all** outstanding requests' `confirmations` sets (not just requests originated by that key) and remove the deleted key/member from each. Alternatively, validate at `confirm`-time (or at execution time, right before `execute_request`) that every public key/member in a request's `confirmations` set is still present among the account's currently valid keys/members, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
```rust
// num_confirmations = 3; keys A, B, C, D on the multisig account
// A: add_request(R1: Transfer{...})           -> confirmations[R1] = {}
// B: confirm(R1)                              -> confirmations[R1] = {B}
// D: confirm(R1)                              -> confirmations[R1] = {B, D}   (2/3, pending)

// A,B,C: add_request_and_confirm / confirm(R_delete: DeleteKey{public_key: D})
//   -> execute_request runs DeleteKey branch:
//        removes requests where signer_pk == D (none, since D didn't create R1)
//        removes num_requests_pk[D]
//        promise.delete_key(D)                -> D's key removed from the account
//        confirmations[R1] is untouched, still {B, D}

// C: confirm(R1)
//   -> confirmations.len() (2) + 1 == 3 >= num_confirmations
//   -> execute_request(R1) fires the Transfer
//   -> Only B and C are still-valid keys; D's stale vote let the quorum be met
```
`multisig/src/lib.rs` lines 198–216 (`DeleteKey` cleanup) and 246–266 (`confirm` tally) show the missing cross-request scrub that makes this possible; the same pattern exists in `delete_member` in `multisig2/src/lib.rs` (lines 355–379). [3](#0-2)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
