### Title
Stale runner-token map key orphans the Kubernetes autoscaler's pause-pod manager on token rotation - (File: executors/kubernetes/autoscaler/provider.go)

### Summary
GitLab Runner has already fixed exactly this bug class once, in the fleeting/taskscaler autoscaler provider: `runnerScalerKey` was changed to key by `URL+ID` (with a documented rationale) specifically because "the runner ID survives token rotation, so keying by URL+ID keeps a rotated token pointing at the existing scaler instead of spinning up a second one that prunes the still-running instances" [1](#0-0) , with a regression test explicitly modeling issue #39380 [2](#0-1) . The Kubernetes autoscaler's `Provider` (a separate, parallel implementation for pause-pod management) still has the unfixed version of this pattern: its `managers` map is keyed by `config.GetToken()` [3](#0-2) .

### Finding Description
`Provider.ensureManager` looks up an existing `autoscalingManager` using the runner's current token as the map key, and `GetManager` does the same: [4](#0-3) [5](#0-4) 

GitLab Runner performs in-place runner authentication token rotation via `resetOneRunnerToken`, which mutates `runnerCfg.Token` through `common.ResetToken` and saves the config, without a full config reload cycle (it does not go through `reloadConfig()`/bump `ConfigLoadedAt` for other runners) [6](#0-5) . This is the exact scenario the fleeting-provider fix and its tests describe: "Rotate the authentication token in place, exactly as resetOneRunnerToken does" [7](#0-6) .

When this happens for a runner using the Kubernetes executor with an autoscaler policy configured:
1. `ensureManager` computes `token := config.GetToken()` with the *new* token and finds no entry in `p.managers` (the existing manager is stored under the *old* token key) [8](#0-7) .
2. Since `exists` is false, the old manager is never stopped/cancelled — the code only calls `rm.manager.Stop()` / `rm.cancel()` in the `if exists` branch [9](#0-8) .
3. A brand-new `PausePodManager` and background goroutine (`go manager.Start(ctx)`) are created and stored under the new token key [10](#0-9) [11](#0-10) .
4. The old manager and its goroutine are leaked (orphaned) — never stopped, holding a stale entry in `p.managers` under the old token forever, since nothing ever deletes it.

This mirrors the NativeVault report's root cause precisely: an unsynchronized state key (slashing handler / token) diverges from a map keyed on that same value, and old entries become orphaned/unreachable rather than being migrated or cleaned up.

### Impact Explanation
Each `PausePodManager` independently manages a pool of "pause pods" in the same Kubernetes namespace, bounded by `MaxPausePods`, and runs its own reconciliation loop against the cluster. With the old manager orphaned and a new one created after every token rotation:
- Two (or more, after repeated rotations) independent pause-pod managers continuously fight over/duplicate pause pod provisioning and cleanup for the same runner/namespace, since neither knows about the other's pods.
- The orphaned manager's goroutine (`manager.Start(ctx)`) keeps running indefinitely, consuming resources and issuing Kubernetes API calls, since its `cancel()` is never invoked.
- `GetManager(config)` (used by `Acquire`/`Release` to increment/decrement active-job counts) now resolves to the *new* manager only, so job-count bookkeeping on the abandoned manager is permanently frozen, while pods it created/tracks are never released, potentially exhausting `MaxPausePods` capacity and preventing new pause pods from being scheduled — a persistent availability degradation for Kubernetes autoscaling with pause pods, without requiring a privileged or trusted-role action beyond the ordinary, expected runner token rotation.

### Likelihood Explanation
Token rotation is a normal, non-privileged, automatic and expected operational event: `resetOneRunnerToken`/`resetRunnerTokens` run periodically in every `gitlab-runner run` process for any runner with `TokenExpiresAt` set (the default for GitLab-managed runner authentication tokens since runner registration tokens were deprecated), and it is on by default unless the `DisableAutomaticTokenRotation` feature flag is enabled [12](#0-11) . Any GitLab Runner instance running the Kubernetes executor with autoscaler pause-pod policies configured (`config.Kubernetes.Autoscaler.Policy`) will hit this path on essentially every automatic token rotation. No attacker action or misconfiguration is required — this is a functional/DoS bug reachable purely through normal runner lifecycle behavior.

### Recommendation
Apply the same fix already used for the fleeting-based autoscaler provider: key `Provider.managers` by a value stable across token rotation (e.g., `URL+RunnerID`, falling back to token only when ID is unset, as done in `runnerScalerKey`) instead of `config.GetToken()`. Alternatively, detect token changes for an already-tracked runner (e.g., by comparing `RunnerID`/`SystemID`) and migrate/replace the map entry while explicitly stopping the previous manager, rather than allowing a stale entry to remain under the old key.

### Proof of Concept
1. Configure a runner using the Kubernetes executor with `config.Kubernetes.Autoscaler.Policy` set (pause-pod autoscaling enabled) and a token that has `TokenExpiresAt` set (automatic rotation enabled).
2. Let the runner run; `Provider.ensureManager` creates `autoscalingManager` keyed by the initial token, starting a `PausePodManager` goroutine [10](#0-9) .
3. Wait for (or trigger) automatic token rotation via `resetOneRunnerToken`, which updates `runnerCfg.Token` in place [6](#0-5) .
4. On the next job `Acquire` call, `ensureManager` computes the new token, finds no matching key in `p.managers`, and creates a second `PausePodManager`/goroutine while leaving the first manager (under the old token key) running and never stopped [13](#0-12) .
5. Observe: `len(p.managers) == 2` for a single runner, two independent reconciliation loops against the same Kubernetes namespace, and `GetManager` job-count tracking split between the two managers — reproducing the same "duplicate manager" / "orphaned state" pattern that the fleeting-provider regression test (`TestInitReusesScalerOnTokenRotation`, `TestProviderTokenRotationDoesNotPruneInstance`) was written to prevent for the other autoscaler implementation.

Note: I was unable to directly execute this PoC in the environment (no runtime/tooling access here); the analysis is based on static code review of the cited files. A live reproduction against a Kubernetes autoscaler-enabled runner should be run to confirm the exact operational blast radius (e.g., whether `MaxPausePods` is enforced per-manager instance, amplifying pod-count drift).

func runnerScalerKey(config *common.RunnerConfig) string {
	if config.ID == 0 {
		// Legacy/pre-v15.3.0 configs have no ID; URL+0 would collide distinct
		// runners onto one scaler, so fallback to the token.
		return config.GetToken()
	}

	return fmt.Sprintf("%s|%d", config.URL, config.ID)
}

func (p *Provider) ensureManager(config *common.RunnerConfig) error {
	if config.Kubernetes == nil || config.Kubernetes.Autoscaler == nil {
		return nil
	}

	if len(config.Kubernetes.Autoscaler.Policy) == 0 {
		return nil
	}

	p.mu.Lock()
	defer p.mu.Unlock()

	token := config.GetToken()
	rm, exists := p.managers[token]

	// Check if config changed
	configKey := configLoadedKey(config)
	if exists && rm.configLoadedAt == configKey {
		return nil
	}

	// Stop existing manager if config changed
	if exists {
		rm.manager.Stop(context.Background())
		rm.cancel()
		delete(p.managers, token)
	}

	// Create new manager
	manager, cancel, err := p.createManager(config)
	if err != nil {
		return err
	}

	p.managers[token] = &autoscalingManager{
		manager:        manager,
		cancel:         cancel,
		configLoadedAt: configKey,
	}

	return nil
}

// GetManager returns the pause pod manager for a runner, if one exists.
// This is used by the executor to update active job counts.
func (p *Provider) GetManager(config *common.RunnerConfig) *PausePodManager {
	p.mu.Lock()
	defer p.mu.Unlock()

	rm, exists := p.managers[config.GetToken()]
	if !exists {
		return nil
	}
	return rm.manager
}

func (mr *RunCommand) resetOneRunnerToken() bool {
	var task runAtTask
	runnerResetCh := make(chan *common.RunnerConfig)

	config := mr.configfile.Config()
	runnerToReset, runnerResetTime := nextRunnerToReset(config)
	if runnerToReset != nil {
		task = mr.runAt(runnerResetTime, func() {
			runnerResetCh <- runnerToReset
		})
	}

	select {
	case runner := <-runnerResetCh:
		// When the FF is enabled, the token is not reset, however, a message is logged to warn the user
		// that his token is about to expire
		if runner.IsFeatureFlagOn(featureflags.DisableAutomaticTokenRotation) {
			mr.log().Warningln(fmt.Printf(
				"Automatic token rotation is disabled for runner: %s-%s. Your token is about to expire",
				runner.ShortDescription(),
				runner.GetSystemID(),
			))
			return false
		}
