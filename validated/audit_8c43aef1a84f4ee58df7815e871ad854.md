### Title
External Initiator credentials can trigger arbitrary non-webhook job runs via `POST /v2/jobs/:ID/runs` due to broken `isUser` check - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` intends to restrict integer job-ID runs to real users only ("EIs not allowed" per the inline comment), but it implements this by calling `auth.GetAuthenticatedUser(c)` and checking only the boolean `ok` return value. Since `AuthenticateExternalInitiator` also populates `SessionUserKey` with a synthetic `User{Role: UserRoleRun}`, an EI-authenticated request satisfies `isUser` and reaches `prc.App.RunJobV2` for any integer job ID, with no check that the EI is associated with that job.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered at [1](#0-0)  with `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` followed by `auth.RequiresRunRole(prc.Create)`. `AuthenticateExternalInitiator` validates only the EI access key/secret headers (`X-External-Initiator-Key`/`Secret`) and, on success, sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` at [2](#0-1) , independent of any real user or of which job the EI is bound to.

In `Create`, the code does:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
```
at [3](#0-2) . `GetAuthenticatedUser` simply reads `SessionUserKey` from context at [4](#0-3) , and since EI auth also populates this key, `isUser` is `true` for both real users and EIs. The comment's intended distinction ("EIs not allowed") is never actually enforced — the correct check would need to verify the absence of `auth.GetAuthenticatedExternalInitiator(c)`, but that function is never called in `Create`. `RequiresRunRole` only checks `user.Role != UserRoleView`, which the synthetic EI user also passes at [5](#0-4) .

As a result, any holder of a valid EI access key/secret (obtained e.g. via `POST /v2/external_initiators`, which requires only `RequiresEditRole`) can send `POST /v2/jobs/<int_job_id>/runs` with EI headers and trigger `RunJobV2` on any job by numeric ID — including OCR, cron, keeper, direct-request, or any other non-webhook job type — regardless of whether that EI was ever linked to the job via `job.WebhookSpec.ExternalInitiatorWebhookSpecs`/`bridges.ExternalInitiator`. Only UUID-based webhook job execution is blocked (that code path is fully removed per [6](#0-5) ), so this specifically enables cross-job/cross-tenant execution of any job addressable by integer ID.

### Impact Explanation
This is an authorization-bypass allowing an EI-credentialed low-privilege caller to invoke `RunJobV2` on arbitrary jobs unrelated to their initiator registration — job runs may consume node resources, incur gas costs on downstream on-chain writes (e.g., triggering transmissions/keeper actions), interfere with production jobs, or leak execution outputs/errors of jobs the caller has no legitimate access to. This matches "unauthorized job run" / role-authorization bypass impact classes.

### Likelihood Explanation
Preconditions are minimal: possession of any valid EI access key and secret is sufficient (no association to any specific job or bridge is checked). EI credentials are created via the standard `/v2/external_initiators` endpoint by an edit-role user, and any process/service that legitimately holds one EI's credentials for its own webhook could reuse them against any other job's integer ID. The attack is trivially repeatable (single HTTP POST, no timing or race dependency).

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests where `auth.GetAuthenticatedExternalInitiator(c)` returns `ok == true` before allowing the integer-ID `RunJobV2` path, rather than relying on the ambiguous `isUser` boolean that both auth methods satisfy. Alternatively, split routing so EI-authenticated runs use a separate handler that verifies job-to-EI association via `bridges.ExternalInitiator` webhook spec binding.

### Proof of Concept
1. Create an application (`cltest.NewApplicationWithConfig`) and register an EI via `cltest.CreateExternalInitiatorViaWeb` (unrelated to any job), yielding `eip.AccessKey`/`eip.Secret`.
2. Create/insert an unrelated non-webhook job (e.g., OCR job as in `setupPipelineRunsControllerTests`), obtaining `jb.ID` (int32).
3. Send `POST /v2/jobs/<jb.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` (per `static.ExternalInitiatorAccessKeyHeader/SecretHeader`) set to the EI credentials, and no session/API-token headers.
4. Assert response is `200 OK` with a `pipelineRun` resource returned, and assert a new row exists in `pipeline_runs` for `jb.ID` — proving the EI executed a job it was never bound to, contradicting the code's own "EIs not allowed" comment.
