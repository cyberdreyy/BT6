### Title
Stale confirmations from deleted multisig members allow a request to execute below the true live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges requests that were *originated* by the removed member, but never scans and purges that member's *confirmations* recorded on other members' pending requests. Because `confirm` counts raw confirmation-set size against `num_confirmations` without re-validating that every recorded confirmer is still a current member, a request can later be executed with fewer genuinely live, authorized confirmations than the configured threshold.

### Finding Description
The custody binding that must hold is: **confirmations counted == confirmations from currently live members**. `confirm` enforces the threshold purely by set cardinality: [1](#0-0) 

```rust

    let mut confirmations = self.confirmations.get(&request_id).unwrap();

        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(member.to_string());
```

`delete_member` removes membership and any request *originated* by that member, but does not touch `self.confirmations` entries the member may have already cast on requests originated by other members: [2](#0-1) 

```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    assert(
        self.members.len() - 1 >= self.num_confirmations as u64,
        "Removing given member will make total number of members below number of confirmations",
    );
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
```

The filter is `r.member == member` — i.e. only requests whose *submitter* equals the removed member. A request submitted by member A but already confirmed by member C is untouched when C is later deleted: the string `C.to_string()` remains in that request's `confirmations` set in `self.confirmations`. When `assert_valid_request` and `confirm` are later invoked, nothing re-checks that every account/key present in the confirmation set for a request is still contained in `self.members`: [3](#0-2) 

So the stale confirmation from a now-removed member still counts toward the `num_confirmations` threshold, breaking the equality "confirmations counted == confirmations from live members."

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." A transaction (e.g. `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`) that was intended to require `k` genuinely live signers can execute with only `k-1` (or fewer) live confirmations plus one stale confirmation belonging to a member who has since been removed (e.g., because they were compromised, offboarded, or otherwise no longer trusted). This undermines the entire security assumption of the multisig — that any consented action must be co-signed by at least `k` currently trusted parties — and can lead to unauthorized transfers of NEAR or unauthorized privileged actions (adding/removing keys, deploying new code) on the multisig account.

### Likelihood Explanation
No external/unprivileged attacker is required beyond ordinary contract usage: any pending request that has accumulated partial confirmations, followed by a legitimate `DeleteMember` action (itself a normal multisig-governed operation, e.g., offboarding a departing team member), leaves an exploitable stale confirmation. Any remaining member simply continuing to confirm the still-pending, older request will trigger execution below the intended live threshold, without needing to bypass any additional check — `assert_valid_request` and `confirm` never re-validate confirmer membership.

### Recommendation
When deleting a member, also purge that member's identifier from every `confirmations` set of every still-pending request (not only requests they authored), or alternatively, have `confirm` re-validate at execution time that every principal recorded in `confirmations` is still present in `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new` with members `[A, B, C, D, E]` and `num_confirmations = 3`.
2. `A` calls `add_request` to submit a `Transfer` request, `request_id = 0` (no auto-confirm).
3. `B` calls `confirm(0)` → confirmations = `{B}` (1 < 3, pending).
4. `C` calls `confirm(0)` → confirmations = `{B, C}` (2 < 3, pending).
5. Via a separate, fully-confirmed multisig self-request, the group executes `DeleteMember { member: C }`. `delete_member` only inspects `self.requests` for entries with `r.member == C`; request `0` was submitted by `A`, so it is untouched — `self.confirmations.get(&0)` still returns `{B, C}` even though `C` is no longer in `self.members`.
6. `D` calls `confirm(0)` → `confirmations.len() + 1 == 3 >= num_confirmations (3)` → the `Transfer` request executes.
7. Result: the transfer was authorized by confirmations from `{B, C, D}`, but `C` was removed from the multisig before execution — only two currently-live members (`B`, `D`) plus `A`'s original submission genuinely support this action, one confirmation short of the configured 3-of-n threshold.
