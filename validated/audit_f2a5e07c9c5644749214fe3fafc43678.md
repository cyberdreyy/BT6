### Title
Instant withdrawals bypass upfront management and performance fees, letting users pocket the protocol's fee share on every APR-decrease exit - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The bug class from the external report is "on a position decrease, fees owed to the protocol are instead paid out to the exiting user." In `IdleCDOEpochVariant.requestWithdraw`, the normal exit path computes projected interest, deducts `_totalWithdrawFees` (upfront management fee + net performance fee), books them in `pendingWithdrawFees`, and only queues `principal + interest - totalFees` for the user. The instant-withdraw branch, taken whenever the strategy APR dropped by more than `instantWithdrawAprDelta`, skips that entire fee block: it queues the full tranche-price value `_underlyings` (principal plus all accrued interest embedded in the price) for immediate claim and reduces NAV by the full amount. The fee share that should accrue to `feeReceiver`/owner is paid to the withdrawer instead, funded out of the vault's instant liquidity / borrower-funded pool.

### Finding Description
In `requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:739-790`):

```solidity
if (_isInstantWithdrawEnabled()) {
  uint256 currentApr = creditVault.unscaledApr();
  if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
    // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
    creditVault.requestInstantWithdraw(_underlyings, msg.sender);
    // burn tranche tokens and decrease NAV
    _withdrawOps(_amount, _underlyings, _tranche);
    return _underlyings;
  }
}
```

Contrast the normal path on the same function (`contracts/IdleCDOEpochVariant.sol:772-790`):

```solidity
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
interestForOverUnderPerformance += diff;
creditVault.requestWithdraw(_underlyings, msg.sender, principal);
_withdrawOps(_amount, principal, _tranche);
```

The instant branch differs in three fee-relevant ways:

1. `_totalWithdrawFees` is never applied. `_underlyings` is the full `_trancheToUnderlyings` value, which already contains accrued interest via the tranche price, so the performance fee on that interest (`fee` share in `_netGainAfterFees`) and the upfront management fee (`_calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration())`, covering remaining buffer + one full epoch) are never charged.
2. `pendingWithdrawFees` is not incremented, so at the next `stopEpoch` nothing is split out to fee receivers for this exit — the fee is neither collected from the user nor requested from the borrower; the amount simply leaks into the user's payout.
3. `_withdrawOps` burns NAV by the full `_underlyings` instead of `principal`, and `interestForOverUnderPerformance` is not updated, so the remaining tranche holders' `expectedEpochInterest` accounting is not adjusted for the over/under-performance the withdrawal realizes — the AA/BB interest split tracked in `expectedEpochInterest` stays as if the exiting position still accrues.

`IdleCreditVault.requestInstantWithdraw` then mints the user a 1:1 receipt (`contracts/strategies/idle/IdleCreditVault.sol:356-375`) which `claimInstantWithdrawRequest` pays out in full (`IdleCreditVault.sol:380-393`) from funded liquidity, with no second chance to deduct fees.

Broken invariant: fair burn / fee integrity — a withdrawal realizing accrued interest must route the configured `fee` + `managementFee` share to fee receivers; here the exiting user receives the gross amount and the pool NAV loses it.

### Impact Explanation
Every eligible instant withdrawal transfers the protocol's fee share to the withdrawer. The magnitude per exit is `managementFee * principal * (remainingBuffer + epochDuration) / year + fee * accruedInterest`, which is identical to the `totalFees` the normal path would deduct. Because the excess is paid out of vault liquidity that belongs to remaining LPs/fee accounting, the pool is drained by exactly the skipped fees each time — the same "slow drain of the diamond" mechanics as the reference bug, where the protocol distributes fees it never collected. In minted-interest mode the leakage is compounded because `pendingWithdrawFees`/`unclaimedFees` bookkeeping (`IdleCDOEpochVariant.sol:418-432`) never sees these fees at all.

### Likelihood Explanation
The trigger is fully permissionless for any KYC-passed tranche holder: it requires only `lastEpochApr > currentApr + instantWithdrawAprDelta`, i.e., the manager lowering the pool APR — a routine configuration change, not an attacker-dependent event. Any holder observing the APR drop can call `requestWithdraw` in the same state and exit fee-free instantly rather than waiting an epoch and paying fees. Repeated APR cycles let the same holder compound the dodge. No privileged role misbehavior is needed; `allowAAWithdrawRequest`/`allowBBWithdrawRequest` just need to be open (buffer/stopped phase). One caveat: instant withdrawals require vault instant liquidity and are disabled for programmable-borrower deployments, so impact is bounded by available liquidity per event.

### Recommendation
Apply the same fee haircut in the instant branch: compute `(interest, diff) = _calcInterestWithdrawRequest(_underlyings, _tranche)` (or charge at minimum the upfront management fee plus performance fee on interest embedded in the tranche price), call `creditVault.requestInstantWithdraw(_underlyings - totalFees, msg.sender)`, increment `pendingWithdrawFees` and `interestForOverUnderPerformance` as in the normal path, and reduce NAV by `principal` only. If instant exits are intended to carry no epoch interest, strip the interest component entirely rather than paying it gross of fees.

### Proof of Concept
Foundry fork sketch (following the harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testInstantWithdrawSkipsFees() external {
    uint256 amount = 10_000 * ONE_SCALE;
    _setFeeParams(TL_MULTISIG, 10_000, FULL_ALLOC, cdoEpoch.managementFee()); // 10% perf fee
    _setManagementFee(1_000); // 1% mgmt fee

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);          // epoch running, interest accrues into AA price

    // manager lowers APR so lastEpochApr > currentApr + instantWithdrawAprDelta
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(lowerApr, 0);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, interest);       // lastEpochApr now > currentApr + delta

    uint256 feesBefore = cdoEpoch.pendingWithdrawFees();
    uint256 navBefore  = cdoEpoch.getContractValue();

    uint256 requested = cdoEpoch.requestWithdraw(trancheAmt, address(AAtranche));

    // BUG: no fee was booked and user receipt equals full tranche value
    assertEq(cdoEpoch.pendingWithdrawFees(), feesBefore);          // fees skipped
    assertEq(requested, trancheAmt * cdoEpoch.tranchePrice(AA) / ONE_TRANCHE_TOKEN); // gross, not net
    // remaining LPs bear the leak: NAV dropped by gross amount incl. uncollected fee share
    assertEq(navBefore - cdoEpoch.getContractValue(), requested);

    cdoEpoch.claimInstantWithdrawRequest(); // pays full gross amount from vault liquidity
    // feeReceiver receives 0 for this exit vs totalFees it would have earned on normal path
}
```

Uncertainty noted: the exact gating in `_isInstantWithdrawEnabled()` and the liquidity source check in `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` were not fully traced in this pass, but the fee-bypass in `requestWithdraw` itself is unconditional once the APR-delta branch is entered.
