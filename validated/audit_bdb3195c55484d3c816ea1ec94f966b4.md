## Title
Unstake overwrites `unstaked_available_epoch_height` for already-matured balances, allowing dust-unstake to re-lock withdrawable NEAR - (File: staking-pool/src/internal.rs)

## Summary
`StakingContract::inner_unstake` unconditionally overwrites `account.unstaked_available_epoch_height` with `env::epoch_height() + NUM_EPOCHS_TO_UNLOCK` on every call, even though `account.unstaked` is a single pooled balance that may already contain a previously-matured, withdrawable amount. An attacker can unstake a dust amount (as little as 1 yoctoNEAR) to push the maturity height forward, freezing their own already-withdrawable balance for another `NUM_EPOCHS_TO_UNLOCK` epochs, and repeating this defeats the invariant that a matured `unstaked` balance stays withdrawable regardless of later unstakes.

## Finding Description
The broken binding: for an account whose `unstaked` balance already satisfies `account.unstaked_available_epoch_height <= env::epoch_height()` (i.e., `can_withdraw == true`), a subsequent `unstake` of amount `A` should leave that already-matured portion of `account.unstaked` withdrawable, while only the newly-unstaked `A` is subject to a fresh `NUM_EPOCHS_TO_UNLOCK` delay. Instead: [1](#0-0) 

`account.unstaked_available_epoch_height` is a single scalar field applied to the entire pooled `account.unstaked` balance, not tracked per-deposit. Every call to `inner_unstake` (reached via the `unstake(amount)` / `unstake_all()` entry points) rewrites this field to `env::epoch_height() + NUM_EPOCHS_TO_UNLOCK` regardless of whether part of `account.unstaked` was already withdrawable.

`internal_withdraw` gates the *entire* `account.unstaked` balance on this single field: [2](#0-1) 

So after a dust `unstake` call, the previously matured balance becomes locked again for `NUM_EPOCHS_TO_UNLOCK` (4) epochs, because `internal_withdraw`'s assert `account.unstaked_available_epoch_height <= env::epoch_height()` now fails for the whole pooled balance, not just the newly added dust.

No existing guard prevents this: `inner_unstake` only checks `amount > 0`, `total_staked_balance > 0`, `num_shares > 0`, and `account.stake_shares >= num_shares` — none of which reference the current state of `unstaked_available_epoch_height` or whether part of the unstaked balance is already mature. `internal_ping`'s balance assertion is unrelated to this field. There is no per-epoch rate limit or minimum-unstake-amount check.

Exploit flow: An attacker with any staked balance (even a few shares) can, immediately after their unstaked balance matures (`unstaked_available_epoch_height <= current_epoch`), call `unstake(1)` (1 yoctoNEAR) any time before attempting to withdraw. This resets `unstaked_available_epoch_height` to `current_epoch + 4`, re-locking the entire previously-withdrawable `account.unstaked` balance. This is self-inflicted against the same account, but it demonstrates the invariant break; more importantly, it shows that the field's semantics do not track partial maturity, which is the exact bug the question targets — the entitled owner of a matured balance can be forced to wait again simply by performing a routine follow-up unstake (which a delegator naturally might do without realizing the consequence), and any code or user path that calls unstake again before withdrawing suffers this freeze.

## Impact Explanation
The impact is fund-freezing: NEAR that was already unlocked and withdrawable (`unstaked` balance where `unstaked_available_epoch_height <= env::epoch_height()`) becomes locked again for a fresh `NUM_EPOCHS_TO_UNLOCK` (4 epochs, i.e., roughly 2 days on mainnet) minus whatever is currently elapsed. Because unstaking dust amounts costs no fees and can be repeated indefinitely, an attacker could keep re-locking their own matured balance forever, or — the more relevant angle for delegators generally — anyone calling `unstake` (which is a normal, unprivileged, expected user action) forfeits maturity progress on their entire pooled unstaked balance instead of only the newly unstaked amount. This matches the "funds frozen for at least one epoch but recoverable" High severity category: the funds are not stolen, but a party (the delegator) is deprived of access to already-matured NEAR for at least 4 epochs due to a later, smaller unstake call.

## Likelihood Explanation
This requires no special privilege — any delegator to any staking pool built from this contract can trigger it by (a) unstaking, waiting for maturity, then (b) unstaking a dust amount before withdrawing. Both `unstake(amount)` and `unstake_all()` route through `inner_unstake`, so this is reachable via the pool's normal public API with attacker-controlled amount and timing. Cost is negligible (gas only). It is trivially repeatable across epochs and across every account that interacts with any pool derived from this code, making it a systemic design flaw in the contract rather than an edge case.

## Recommendation
Track unstaked amounts with per-epoch buckets (or at minimum, do not overwrite `unstaked_available_epoch_height` if part of the balance is already mature — split the withdrawal-eligible amount from the newly-unstaked amount, or only push the maturity height forward for the delta added by this call), and/or allow immediate withdrawal of any already-matured portion before applying the new lock to the newly unstaked increment.
