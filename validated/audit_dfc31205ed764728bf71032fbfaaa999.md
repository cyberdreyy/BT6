### Title
Post-default instant withdraw requests drain the default recovery reserve at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` lacks the `defaultRecoveryFinalized` guard that `requestWithdraw` has, and `claimInstantWithdrawRequest` pays the full `instantWithdrawsRequests[_user]` balance through `_transferFundedClaim` — the strategy's own underlying balance, which post-default is the `defaultRecoveryReserve`. An unprivileged tranche holder can mint fresh instant-withdraw receipts after default finalization and redeem them 1:1, stealing recovery funds that belong to defaulted-epoch claimants who are only entitled to `defaultRecoveryPrice`.

### Finding Description
The CVE is a use-after-free: a stale pointer to released memory is dereferenced. The analog is stale epoch bookkeeping being reused after its bucket was "freed" (finalized). After `finalizeDefaultRecovery`, all defaulted receipts are meant to be paid exclusively through `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` at `defaultRecoveryPrice` from `defaultRecoveryReserve` (`IdleCreditVault.sol:772-856`).

The normal-withdraw path correctly distinguishes pre- and post-default state: `requestWithdraw` reverts if the user has unfinalized claims and routes new requests into `postDefaultRequests`, paid 1:1 only because the CDO already applied the haircut via `virtualPrice` (lines 247-257). The instant-withdraw path has no equivalent guard:

- `requestInstantWithdraw` (lines 356-375) burns CDO strategy tokens, mints receipts to the user, and increments `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws` — with no `defaultRecoveryFinalized` check.
- `claimInstantWithdrawRequest` (lines 380-393) clears the defaulted-epoch receipt only when `defaultInstantWithdrawsFinalized` is set, then burns the entire remaining `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim`, paying at par from strategy-held underlying.

Post-finalization, the strategy's underlying balance is the recovery reserve. A new instant request creates a receipt that was never haircut (no `virtualPrice` reduction applies to the instant path, and `pendingInstantWithdraws` is never decremented on claim — only via `collectInstantWithdrawFunds`, which the honest CDO never calls post-default). The attacker claims the full amount at par, depleting the reserve before honest defaulted claimants (paid only `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` at lines 782-783, 855) can claim.

Attack sequence (defaulted/finalized epoch phase, fixed-APR or APR0 mode):
1. Borrower defaults; `finalizeDefaultRecovery` sets `defaultRecoveryPrice < RECOVERY_FULL` and holds the reserve in the strategy.
2. Attacker calls `requestInstantWithdraw` via the CDO with tranche tokens (or a post-default deposit), minting a fresh receipt.
3. Attacker calls `claimInstantWithdrawRequest`; `_claimDefaultedInstantWithdrawRequest` returns 0 for the new epoch, then the full `instantWithdrawsRequests` balance is paid at par via `_transferFundedClaim`.
4. Reserve shrinks below what honest defaulted claimants are owed — direct theft.

### Impact Explanation
Direct theft of the default recovery reserve. New post-default instant receipts are paid 100 cents on the dollar while defaulted claimants are haircut to `defaultRecoveryPrice`. Each attacked unit withdrawn at par removes reserve backing multiple defaulted claims, causing permanent under-collateralization of `DefaultDistributor`/recovery claims. Loss is quantified by `amount * (1 - defaultRecoveryPrice/RECOVERY_FULL)` per request, up to the entire reserve.

### Likelihood Explanation
Requires a borrower default followed by finalized recovery — a real but infrequent state. Once in that state, any unprivileged tranche-token holder (or post-default depositor) can execute it with two transactions and no privileged cooperation. The asymmetry with `requestWithdraw`'s explicit post-default guard strongly suggests the instant path was simply missed.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert or route the request into a haircut-aware path. Additionally, `claimInstantWithdrawRequest` should pay post-default receipts through `_transferDefaultRecovery` at `defaultRecoveryPrice` (or a dedicated post-default-par bucket only if the CDO applies the haircut upstream), and should decrement `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` consistently so the reserve accounting cannot be double-counted.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// 1. Run a normal epoch, deposit as honest LP and attacker, let borrower repay.
// 2. Trigger borrower default; call IdleCDOEpochVariant finalizeDefaultRecovery
//    with partial recovery so defaultRecoveryPrice < RECOVERY_FULL.
// 3. Honest user holds a defaulted-epoch withdraw receipt (unclaimed).
// 4. Attacker (holds tranche tokens or deposits post-default):
//    - cdoEpoch.requestInstantWithdraw(amount)  // no revert: missing guard
//    - cdoEpoch.claimInstantWithdrawRequest()
// 5. Assert attacker received `amount` at par (no haircut) while
//    strategy.underlying balance == defaultRecoveryReserve decreased by `amount`.
// 6. Honest user's defaulted claim now underfunded: expected payout
//    claimBasis * defaultRecoveryPrice / RECOVERY_FULL cannot be fully paid.
```

Uncertainty: I could not fully verify that the CDO still forwards `requestInstantWithdraw`/`claimInstantWithdrawRequest` calls after `defaulted()` is set (that gating lives in `IdleCDOEpochVariant`, not shown here). If the CDO blocks instant-withdraw entrypoints post-default, the attack surface narrows to instant receipts created before finalization but claimed after — which is partially covered by `_claimDefaultedInstantWithdrawRequest`, though only for `defaultRecoveryEpoch`'s per-epoch bucket; receipts recorded under a different `instantWithdrawsRequestsByEpoch` key would still pay at par. A fork PoC should confirm CDO-level reachability first.
