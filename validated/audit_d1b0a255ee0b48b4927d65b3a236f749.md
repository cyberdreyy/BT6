### Title
Attacker-controlled ERC4626 vault illiquidity permanently reverts `stopEpoch`, freezing all pending withdraw claims - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The external report's bug class — a malicious/untrusted external party's responses causing denial of service — maps directly onto `ProgrammableBorrower.onStopEpoch`. When `stopEpoch` needs to recall cash for pending withdraw requests (or epoch interest in non-minted mode), the hook calls `vault.withdraw(shortfall, ...)` on the configured ERC4626 vault and reverts with `StopEpochVaultLiquidityUnavailable` if that call fails. Any unprivileged user of that external vault (e.g., a MetaMorpho/Blue borrower draining idle liquidity) can force the revert on every `stopEpoch` attempt, indefinitely freezing the epoch and all pending withdraw receipts.

### Finding Description
`IdleCDOEpochVariant.stopEpoch` calls `IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)` when `isProgrammableBorrower` is set, and hook reverts intentionally bubble so "transient ERC4626 liquidity failures can be retried" [1](#0-0) . Inside `onStopEpoch`, if the required amount exceeds on-hand cash, the code only checks `shortfall > _currentVaultAssets()` (a `convertToAssets` valuation) before attempting `vault.withdraw` [2](#0-1) .

The gap: `convertToAssets` prices shares against the vault's **total** assets (including lent-out liquidity in Morpho-style vaults), while `withdraw` reverts on **idle** liquidity (`maxWithdraw`/`maxRedeem`). An attacker who is a borrower/depositor of the underlying ERC4626 vault can borrow out its idle liquidity such that `convertToAssets` still reports the sleeve as covering the shortfall, but `withdraw` reverts. The revert propagates through `onStopEpoch` → `stopEpoch`, leaving `isEpochRunning == true`, `epochAccountingActive == true`, and `pendingWithdraws` unfunded — confirmed by the code's own test expectation [3](#0-2) .

### Impact Explanation
- **Temporary/indefinite freezing of funds.** Every holder of a pending withdraw receipt (`withdrawsRequestsByEpoch`, APR0 `apr0Users` buckets) cannot be funded or claimed while the epoch is stuck running, because `claimWithdrawRequest` requires `epochNumber > lastWithdrawRequest[_user]` and epoch rollover only happens at a successful `stopEpoch` [4](#0-3) .
- **No default escape.** Because shares nominally cover the shortfall, the `shortfall > _currentVaultAssets()` branch never returns the default path, so the loss-socialization/recovery machinery cannot kick in either — funds are neither withdrawable nor defaulted.
- **Repeatable at will.** The attacker re-drains vault liquidity every epoch (or simply maintains a Morpho borrow), so each retry by the honest manager reverts again. This is not a one-off transient failure as the code comment assumes.
- **Quantified loss.** All assets parked in the vault sleeve plus all `pendingWithdraws` become unclaimable for the duration of the attack; the attacker's cost is borrow interest on the drained vault liquidity, which can be far below the frozen LP principal.

### Likelihood Explanation
The attacker needs only to be a user of the configured ERC4626 vault — explicitly an unprivileged role per scope. Draining Morpho-vault idle liquidity is a normal market operation (borrowing), fully permissionless. The only mitigations are managerial (keeper retries, `emergencyExitVault` by owner/manager, `setVault` migration), all of which require privileged intervention and can be front-run or made moot if the vault's other markets are also utilized. The revert path is not speculative — it is exercised in `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable`.

### Recommendation
In `onStopEpoch`, check withdrawable liquidity rather than accounting coverage, e.g. compare `shortfall` against `vault.maxWithdraw(address(this))` (or `maxRedeem`), and when idle liquidity is insufficient return `true` so the CDO's `transferFrom` fails and flows into `_handleBorrowerDefault` — converting the freeze into the designed default/loss-waterfall path. Alternatively, attempt `withdraw` against `min(shortfall, maxWithdraw)` and let any residual shortfall trigger default, so a liquidated-liquidity scenario settles receipts pro-rata instead of reverting forever.

### Proof of Concept
Fork-based Foundry test against a real MetaMorpho vault (as in `ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testAttackerFreezesStopEpochViaVaultLiquidity() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
    _startEpochAndCheckPrices(0);

    uint256 pendingWithdraws = strategy.pendingWithdraws();
    assertGt(pendingWithdraws, 0);

    // Attacker: permissionless Morpho borrower drains the underlying market's
    // idle liquidity so maxWithdraw(programmableBorrower) < pendingWithdraws
    // while convertToAssets(shares) still covers it on paper.
    _attackerBorrowsAllIdleLiquidityFromMorphoMarket();

    assertGe(morphoVault.convertToAssets(morphoVault.balanceOf(address(programmableBorrower))), pendingWithdraws);
    assertLt(morphoVault.maxWithdraw(address(programmableBorrower)), pendingWithdraws);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Retry still reverts; epoch cannot stop, receipts cannot be claimed,
    // and the pool cannot enter the default path.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}
```

Uncertain: exact mainnet liquidity conditions of the production-configured vault determine how cheap the drain is; the finding holds wherever `convertToAssets` coverage exceeds `maxWithdraw` coverage, which is inherent to lending-vault designs, not to a specific market state.
