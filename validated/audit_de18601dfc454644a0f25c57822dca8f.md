### Title
Borrow rate-limiter outflow tracking uses a zero price on oracle failure, silently bypassing the group outflow cap - (File: `programs/marginfi/src/instructions/marginfi_account/borrow.rs`)

### Summary
`lending_account_borrow` fetches the oracle price used to value the borrow for the group rate limiter, but swallows any oracle error and substitutes `I80F48::ZERO` instead of failing the transaction. That zero price is then fed into `record_withdrawal_outflow`, which converts the borrowed amount to a USD value for the group's outflow cap. If the oracle call fails (stale price, wrong account, confidence too high, etc.), the recorded outflow value becomes $0 regardless of the actual amount borrowed, silently bypassing the rate limiter's protection.

``` [2](#0-1) 

The `.ok()` discards any `MarginfiResult` error from the oracle fetch (e.g. `PythPushStalePrice`, `SwitchboardStalePrice`, `WrongOracleAccountKeys`, `OracleMaxConfidenceExceeded`), and `unwrap_or(I80F48::ZERO)` substitutes a price of zero rather than reverting the transaction. This directly parallels the reported bug class: an oracle failure produces a `0` value instead of erroring, and that `0` is then used in a downstream value-based safety check.

This is the exact same failure pattern the codebase explicitly guards against elsewhere. In `withdraw.rs`, `kamino/withdraw.rs`, and `drift/withdraw.rs`, the equivalent oracle-fetch-for-rate-limiting code explicitly checks `check!(price > I80F48::ZERO, MarginfiError::ZeroAssetPrice)` whenever the price will actually be used for a financial decision (receivership/deleverage): [3](#0-2) 

But the borrow path has no equivalent zero-price guard before it is fed to `record_withdrawal_outflow`, which uses the price to compute the USD value counted against the group's rate-limiter outflow cap (via `calc_value`, imported in `general.rs`): [4](#0-3) 

### Impact Explanation
The group rate limiter is meant to bound the USD-denominated outflow (borrows + withdrawals) per time window as a circuit breaker against oracle manipulation, bank-run scenarios, or rapid drains. If the oracle for the borrowed bank fails for any reason during a `lending_account_borrow` call, the borrowed amount is valued at $0 for rate-limiting purposes, meaning the borrow does not count against the cap at all. A user (or colluding set of users) could repeatedly borrow while the oracle for that bank is stale/misconfigured/highly volatile (confidence exceeded), draining liquidity far beyond the intended cap, defeating the very protection the rate limiter is designed to provide. This is a durable, exploitable bypass of a financial safety control, not merely informational — it has a real value/liquidity impact on the protocol during oracle-degraded conditions.

### Likelihood Explanation
This requires the oracle for the specific bank being borrowed to be in a failing state (stale, wrong verification level, confidence exceeded) at the time of the borrow. This is not attacker-controlled in the general case, but oracle staleness/failures are a realistic, periodically-occurring condition (crank delays, RPC issues, extreme volatility triggering confidence rejection), and an attacker monitoring oracle health could specifically time borrows during such windows to bypass the rate limiter. Given that other identical patterns in the codebase (withdraw paths) were hardened with an explicit `ZeroAssetPrice` check, the omission here appears to be an oversight rather than intended design, increasing confidence that it's a genuine gap rather than accepted risk.

### Recommendation
Apply the same guard used in `withdraw.rs`, `kamino/withdraw.rs`, and `drift/withdraw.rs`: when `group_rate_limit_enabled` is true, do not silently swallow the oracle error with `.ok()`/`unwrap_or(I80F48::ZERO)`. Instead, propagate the oracle error (fail the borrow) or explicitly `check!(rate_limit_price > I80F48::ZERO, MarginfiError::ZeroAssetPrice)` before calling `record_withdrawal_outflow`, ensuring a failed oracle cannot be used to record a $0 outflow value while still permitting the underlying token transfer.

### Proof of Concept
1. Configure or wait for a bank's oracle to enter a failing state recognized by `fetch_unbiased_price_for_bank_with_cache` (e.g., stale Pyth push price beyond `oracle_max_age`, or confidence interval exceeding `oracle_max_confidence`) — while the account's own health check still uses a separate remaining-accounts oracle set that may tolerate/skip stale collateral oracles for `RequirementType::Initial` (per `calc_weighted_asset_value_standalone`'s "skip stale oracles for Initial requirement" logic), allowing `check_account_init_health` to still pass.
2. Call `lending_account_borrow` for a large amount from that bank while `group.rate_limiter.is_enabled()` is true.
3. Observe that `fetch_unbiased_price_for_bank_with_cache(...).ok()` returns `None`, so `rate_limit_price` becomes `I80F48::ZERO`.
4. `record_withdrawal_outflow` computes the USD-denominated outflow using this zero price, recording $0 against the group cap and letting the borrow proceed unrestricted, regardless of the true dollar value borrowed.
5. Repeat borrows during the oracle-failure window to drain far more than the configured group rate-limit cap would normally allow.
