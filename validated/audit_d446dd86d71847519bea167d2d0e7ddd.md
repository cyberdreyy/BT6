### Title
Stale confirmations from a deleted multisig key remain counted toward the confirmation threshold, allowing request execution with fewer than `num_confirmations` live keys - ([File: multisig/src/lib.rs])

### Summary
`MultiSigContract::execute_request`'s `DeleteKey` handler only purges *requests originally created* by the deleted public key, and clears `num_requests_pk` for that key. It never scans the `confirmations` map for entries where that key appears as a *confirmer* on requests created by someone else. Because `confirm()` later counts `confirmations.len()` against `num_confirmations` without re-validating that every recorded public key is still a live access key on the account, a confirmation cast by a key that has since been removed still counts toward the threshold, letting a request execute with fewer currently-authorized signers than the configured `K`.

### Finding Description
The confirmation/threshold binding the contract is supposed to enforce is:
`confirmations.get(request_id).len() >= num_confirmations` ⇒ `len()` distinct **currently valid** signer keys.

`confirm()` only checks the size of the stored `HashSet<PublicKey>` against `num_confirmations`: [1](#0-0) 

The `DeleteKey` action, executed as part of `execute_request`, removes only the requests where the deleted key was the *original request signer* (`r.signer_pk == pk`), and clears that key's `num_requests_pk` entry: [2](#0-1) 

It does **not** iterate `self.confirmations` to strip the deleted key from confirmation sets on requests it merely *confirmed* (but did not create). Those `HashSet<PublicKey>` entries are left untouched, so a pending request's confirmation count still includes a key that no longer has any access to the account.

Concretely: with members A, B, C, D and `num_confirmations = 3`:
1. A creates request X (`add_request`); A and B confirm X → `confirmations[X] = {A, B}` (2/3).
2. A separate request to `DeleteKey { public_key: B }` is confirmed by 3 valid keys and executes, removing B's access key from the account. Because request X was created by A (not B), it is untouched by the `DeleteKey` cleanup, so `confirmations[X]` still contains B.
3. C confirms X. `confirmations[X].len()` becomes 3, which is `>= num_confirmations`, so `execute_request(X)` runs — even though B's key no longer exists and only A and C are actually authorized signers at execution time.

This breaks the "confirmations counted versus live members" equality the K-of-N scheme is supposed to guarantee: the number of confirmations accepted for execution is not equal to the number of currently valid distinct signers.

### Impact Explanation
This is a Critical-impact analog: "a multisig request executed below threshold." Any request type can be affected, including `Transfer` (moving NEAR/funds out of the multisig account) and `AddKey`/`DeployContract` (which could be used to escalate to full account takeover), all executed with one fewer live signature than the operator configured. This directly undermines the custody guarantee the multisig is meant to provide.

### Likelihood Explanation
The scenario requires no external attacker privilege beyond being one of the multisig's own signers — a normal, expected participant in the K-of-N scheme. Key rotation (removing a compromised/departing member's key while pending requests exist) is a realistic and even recommended operational practice, and it is exactly the workflow that triggers the stale-confirmation state. No malicious admin/foundation role, no victim key theft, and no reentrancy trick are needed — only ordinary, sequential use of `add_request`, `confirm`, and `DeleteKey` that the contract's own documented API exposes.

### Recommendation
When executing a `DeleteKey` action (and analogously for member deletion in `multisig2`), iterate all entries in `self.confirmations` and remove the deleted public key from every confirmation set, not just from requests it originally created. Alternatively, re-validate at `confirm()`/`execute_request()` time that every public key recorded in a request's confirmation set is still a currently valid access key on the account (or member of the multisig) before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with access keys for members A, B, C, D.
2. As A: `add_request_and_confirm(Transfer { amount, receiver_id })` → request X created, `confirmations[X] = {A}`.
3. As B: `confirm(X)` → `confirmations[X] = {A, B}` (2/3, not yet executed).
4. Separately, get 3 valid confirmations to add and execute a request `DeleteKey { public_key: B }` (not authored by B), removing B's access key from the account. Verify via `execute_request`'s handling shown at [2](#0-1)  that request X and `confirmations[X]` are unaffected because B did not author X.
5. As C: `confirm(X)`. In `confirm()` [1](#0-0) , `confirmations[X].len() + 1 == 3 >= num_confirmations`, so `execute_request(X)` runs the `Transfer`, even though B's key was deleted in step 4 and only A and C are currently valid signers — one short of the configured 3-of-N threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
