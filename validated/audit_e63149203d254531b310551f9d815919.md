### Title
Invalid low-`chain_length` block proposals unconditionally reset the tenure activity timer when `signed_group` is `None` - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
In `SortitionData::check_latest_block_in_tenure`, the early-rejection branch for a proposal that does not exceed the tenure's known chain length calls `signer_db.update_last_activity_time` whenever `info.signed_group` is `None`, with no time bound on that condition. Because `Option::is_none_or` returns `true` unconditionally on `None`, an already-invalid or stuck miner's tenure can have its activity clock reset forever by any low-`chain_length` proposal, as long as the tenure's last accepted block never reaches `signed_group` (global acceptance).

### Finding Description
The claimed equality is: the per-tenure activity timer (read by `SortitionState::is_timed_out` to decide tenure-timeout fallback) should track genuine miner liveness, not repeated invalid proposal submissions.

The code path: [1](#0-0) 

When a proposal's `chain_length` is `<=` the known tenure chain length, the function rejects it (`Ok(false)`) but first checks:
```rust
if info.signed_group.is_none_or(|signed_time| {
    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
}) {
    signer_db.update_last_activity_time(...);
}
```
`Option::is_none_or` returns `true` immediately when the option is `None`, without evaluating any time bound — the `reorg_attempts_activity_timeout` bound is only applied in the `Some` branch (i.e., once the last known block has become globally accepted). So when the tenure's last known block is only locally accepted (`signed_group == None`, e.g. because the miner produced one block, this signer accepted it, but the miner then stalled before enough signers converged for global acceptance), *every* subsequent low-`chain_length` proposal — valid or fabricated — refreshes `last_activity_time` with no expiration. This function performs no signature or authenticity check on the proposal beyond comparing `chain_length`; the tenure-identity binding is via `tenure_id`/`block.header.consensus_hash`, not via verifying the block was actually produced by the tenure's legitimate miner.

`SortitionState::is_timed_out` (via `SortitionStateV1`/`SortitionStateV2::is_timed_out`) reads this same activity timestamp against `proposal_config.block_proposal_timeout` to decide tenure timeout / fallback eligibility, so an unbounded reset here defeats the timeout gate.

### Impact Explanation
This is a liveness issue: it can wedge a signer such that `is_timed_out` never returns `true` for a stuck tenure, preventing the signer from falling back to sign the next honest miner's blocks — matching the "High" category ("a signer wedged into never signing valid blocks (liveness)"). It does not break chain safety (no invalid block is signed), only the timeout fallback mechanism.

### Likelihood Explanation
The precondition is narrow and not fully attacker-controlled: it requires the victim tenure to be stuck in a state where its last known block is locally accepted by this signer but never reaches `signed_group` (global acceptance) — a transient state during normal operation that closes automatically once enough honest signers converge and acceptance becomes global, at which point the `reorg_attempts_activity_timeout` bound applies and the free reset window ends. The attack is only durable if the tenure is genuinely stalled (the scenario the timeout fallback exists to handle) for a prolonged period, which is somewhat self-defeating to describe as attacker-caused since it depends on the miner/network state, not solely on attacker action. Additionally, I could not verify from the available code (tool budget exhausted before locating `v0/signer.rs`'s proposal-ingestion/authentication logic) whether a `BlockProposal` for a tenure the attacker does not control can reach `check_latest_block_in_tenure` without first being filtered by a miner-signature/tenure-ownership check earlier in the pipeline. This is a material open question for exploitability: if such a gate exists upstream, an attacker outside the victim tenure cannot inject qualifying proposals at all.

### Recommendation
Apply the same `reorg_attempts_activity_timeout` bound (measured from `approved_time` or another anchor) in the `None` branch instead of unconditionally treating `signed_group.is_none()` as fresh activity, so that a locally-accepted-but-never-globally-accepted block also has a bounded activity-refresh window rather than an indefinite one.

### Proof of Concept
Given the unresolved authentication-gate question above, a full PoC would need to first confirm in `stacks-signer/src/v0/signer.rs` whether `confirms_latest_block_in_same_tenure`/`check_tenure_change_confirms_parent` can be reached by a proposal for a tenure the caller does not own. Assuming it can (or in a unit test calling `check_latest_block_in_tenure` directly, bypassing that question):
1. Seed `signer_db` with a tenure's last accepted block in `LocallyAccepted` state (`signed_group = None`).
2. Loop calling `SortitionData::check_latest_block_in_tenure` with a crafted `NakamotoBlock` whose `chain_length` is below the known chain length, spaced apart by more than `block_proposal_timeout`.
3. Assert `signer_db.get_last_activity_time` keeps advancing on each call, and that `SortitionState::is_timed_out` never returns `true` despite elapsed wall-clock time exceeding `block_proposal_timeout`, contrasted with a control test where `signed_group` is set (globally accepted) and the timeout does eventually fire once `reorg_attempts_activity_timeout` elapses.
