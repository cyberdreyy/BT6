### Title
Unrestricted, unrate-limited JWT authorization probing enables workflow-signer allowlist enumeration - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` only calls `h.jwtCache.recordUsage(claims.ID)` after the signer-authorization check succeeds, so a JWT signed by an unauthorized key that fails the `authorizedKeys[workflowID]` lookup leaves no side effect and can be resubmitted indefinitely against other `workflowID`s. Because `httpTriggerHandler.HandleUserTriggerRequest` only invokes the per-workflow rate limiter (`checkRateLimit`) *after* `authorizeRequest` succeeds, failed authorization attempts are never throttled at all, enabling unbounded probing.

### Finding Description
In `Authorize`, the JWT is first cryptographically verified against the request digest (`utils.VerifyRequestJWT`), then checked for replay via `jti` (`h.jwtCache.isReplay`), then checked against `h.authorizedKeys[workflowID]`. `recordUsage(claims.ID)` is the last statement, executed only on the success path: [1](#0-0) 

Because `utils.VerifyRequestJWT` binds the JWT digest to the JSON-RPC request contents (`method`, `id`, `params`) but not to a specific `workflowID`, the same signed token and same `req` object can be replayed by an attacker across many different `workflowID` values (`resolveWorkflowID` only requires the ID to exist in `workflowIDToRef`, no ownership check) without ever tripping the replay cache, since `recordUsage` is skipped whenever the "signer not authorized for workflow" branch is hit: [2](#0-1) 

Additionally, in `HandleUserTriggerRequest`, `authorizeRequest` runs before `checkRateLimit`: [3](#0-2) 

`checkRateLimit` applies the per-workflow-owner `userRateLimiter` only for the resolved `workflowID`, and only reached after a *successful* authorization: [4](#0-3) 

The gateway's top-level entry point for these requests, `HandleJSONRPCUserMessage`, forwards directly to `triggerHandler.HandleUserTriggerRequest` with no separate global or per-caller rate limiter applied before authorization: [5](#0-4) 

The `globalNodeRateLimiter` / `perNodeRateLimiters` fields on `gatewayHandler` are used for node-originated outbound HTTP action traffic, not for inbound user trigger requests, so they do not mitigate this path.

Consequently, an attacker holding a validly-signed JWT (signed with their own key, unauthorized for every real workflow) can iterate over many `workflowID`s using the same request/token pair. Each failed attempt costs nothing (no `jti` burn, no rate-limit consumption, no callback registration since `setupCallback` is only reached after `checkRateLimit`), letting the attacker efficiently discover which workflow(s), if any, list their signer address as an authorized key.

### Impact Explanation
This falls under allowlist/quota bypass and authorization-boundary weakening: an attacker can brute-force/enumerate the workflow authorization allowlist for a given signer key with no throttling, cost, or detection barrier from the framework itself. While this does not by itself grant the attacker execution rights on a workflow they aren't already authorized for, it does allow silent, unlimited reconnaissance to find any (possibly misconfigured or leaked-key) workflow that would accept the signer, which can precede a request-impersonation or unauthorized job-run attempt on that discovered workflow.

### Likelihood Explanation
Preconditions are minimal: attacker only needs any ECDSA keypair and the ability to send gateway JSON-RPC `workflowExecute` requests (unauthenticated network-reachable clients of the gateway, per the threat model). No privileged role or credentials are required. The check-ordering bug (`checkRateLimit` after `authorizeRequest`) is deterministic and always reproducible; every failed-authorization test case in `TestWorkflowMetadataHandler_Authorize` ("unauthorized signer" subtest) demonstrates `recordUsage` is skipped.

### Recommendation
- Apply a rate limiter (keyed by signer address or by source, before or independent of `authorizeRequest`) to bound the number of authorization attempts per unit time, regardless of outcome.
- Consider recording/burning the JWT `jti` as soon as it passes signature verification (not only on successful workflow-key match), or otherwise binding the JWT to a specific workflow ID inside the signed digest so a single token cannot be replayed against arbitrary `workflowID`s.
- Move `checkRateLimit` (or an equivalent generic per-caller limiter) ahead of `authorizeRequest` in `HandleUserTriggerRequest`.

### Proof of Concept
Go unit test extending `TestWorkflowMetadataHandler_Authorize`:
1. Register `authorizedKeys[workflowID1] = {addrA}` only (attacker key `addrX` not authorized anywhere).
2. Create one JWT signed by `addrX` bound to a fixed `req` (fixed `req.ID`, `params`).
3. Loop calling `handler.Authorize(workflowIDi, tokenString, req)` for `workflowID1..workflowIDN` (all distinct, none containing `addrX`).
4. Assert every call returns the "not authorized for workflow" error, and that `handler.jwtCache.isReplay(claims.ID)` remains `false` after all N attempts (i.e., `recordUsage` was never invoked).
5. Then add `addrX` to `authorizedKeys[workflowIDN+1]` and call `Authorize` again with the same token/req — assert it succeeds, proving the token was still valid/unused despite N prior failed probes.
6. At the `httpTriggerHandler.HandleUserTriggerRequest` level, add a handler-integration test asserting that `userRateLimiter.AllowErr` (or an equivalent counter) is never invoked/decremented for the failed-authorization iterations, confirming no rate limiting mitigates the probing.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	// TODO orgID https://smartcontract-it.atlassian.net/browse/CRE-1707
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}

func (h *gatewayHandler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback handlers.Callback) error {
	h.metrics.IncrementTriggerRequestCount(ctx, h.lggr)
	err := h.triggerHandler.HandleUserTriggerRequest(ctx, &req, callback, time.Now())
	if err != nil {
		h.lggr.Errorw("failed to handle user trigger request", "requestID",
			req.ID, "err", err)
		// error response is sent to the response channel by the trigger handler
		// so return nil after logging
	}
	return nil
}
