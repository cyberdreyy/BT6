### Title
Open APR0 withdraw bucket permanently reverts `stopEpoch` if `unscaledApr` is changed before settlement — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` contains a reachable assertion: if `apr0TotalPrincipal != 0` and `unscaledApr != 0`, it reverts with `NotAllowed`. The APR0 bucket can only be closed inside that same function (or via the closed-pool lazy-init path), so once `unscaledApr` is set non-zero while a bucket is open, every `stopEpoch`/`stopEpochWithDuration` call reverts until the manager manually restores `unscaledApr = 0`. An unprivileged KYC'd lender arms this state by making an ordinary `requestWithdraw` during a zero-APR period; a subsequent routine APR change (e.g. `setAprs`/`setAprsWithBuffer` by the manager between epochs or mid-epoch) then bricks the epoch state machine. This mirrors CVE-2020-13595's bug class: a crafted packet/transaction sequence drives the system into a reachable assertion that disables the whole stack.

### Finding Description
`requestWithdraw` in `IdleCreditVault` routes requests into the APR0 bucket whenever `unscaledApr == 0`: [1](#0-0) 

The bucket is only ever cleared in two places: `prepareStopEpochWithApr0` (the normal path) and `_ensureDefaultRecoveryInitialized` (only on a closed, non-defaulted pool). `prepareStopEpochWithApr0` reverts before clearing when the APR no longer matches the request lifecycle: [2](#0-1) [3](#0-2) 

`setAprs`/`setAprsWithBuffer` let the CDO or manager change `unscaledApr` at any time with no check on `apr0TotalPrincipal`: [4](#0-3) 

Every `stopEpoch` must pass through `prepareStopEpochWithApr0` before the new APR is applied via `_setScaledApr`, so the mismatch cannot self-heal: [5](#0-4) [6](#0-5) 

Attack sequence (buffer phase, fixed-APR mode):
1. Manager configures a zero-APR epoch (`setAprs(0, 0)` — a supported configuration; tests exercise it via `setAprs(0, 0)`).
2. Attacker (any KYC-passing lender) calls `IdleCDOEpochVariant.requestWithdraw`, which calls `IdleCreditVault.requestWithdraw` → `_requestWithdrawApr0`, setting `apr0Users[attacker].principal` and `apr0TotalPrincipal > 0`.
3. Manager later calls `setAprs`/`setAprsWithBuffer` with a non-zero APR (e.g. repricing the next epoch early, a routine operation since `requestWithdraw` timestamps show APR is intended to float between epochs). Now `unscaledApr != 0` while `apr0TotalPrincipal != 0`.
4. The epoch runs; at `epochEndDate`, `stopEpoch` reverts at the `unscaledApr != 0` check — every time, for any `_newApr`/`_interest` parameters, including the `_interest == 1` close-pool path (that path also calls `prepareStopEpochWithApr0` first).

Because `epochNumber`/`isEpochRunning` never advance, all pending withdraw requests cannot be funded or claimed (the `epochNumber <= lastWithdrawRequest` gate in `_claimFundedWithdrawRequest` stays closed), deposits remain paused, and the entire TVL sits with the borrower with no recall path through the normal flow.

### Impact Explanation
Temporary freezing of all vault funds: while the assertion is live, `stopEpoch`/`stopEpochWithDuration`/`claimWithdrawRequest` are unusable and the contract cannot recall principal from the borrower. Loss magnitude is the full pool NAV plus pending receipts for the duration of the freeze. Recovery requires the manager to notice and restore `unscaledApr = 0` via `setAprs(0, x)` before calling `stopEpoch`; if the APR change is effected through a flow that cannot be trivially reverted (e.g. an operator script that only pushes the new epoch parameters into `stopEpochWithDuration`, or multisig latency), the freeze persists and forces the following epoch to settle under the wrong (zero) unscaled APR basis that the APR0 requests were priced on, silently mis-accruing `apr0RateByEpoch` interest against active LPs.

### Likelihood Explanation
Medium-low. Arming the trap is permissionless and cheap — a single `requestWithdraw` during any zero-APR epoch window creates the bucket (the attacker need only be a KYC-passing lender). The trigger is not attacker-controlled: it needs a manager APR change while the bucket is open. However, the assertion gives no warning at the time `setAprs` is called, the revert surfaces only at the epoch-stop transaction after funds are already committed to the borrower for a full epoch duration, and no guard couples `setAprs` to `apr0TotalPrincipal`. The inconsistency is structural: `unscaledApr` is global mutable state while APR0 requests are epoch-scoped, so any out-of-band repricing creates an inconsistent state that the settlement function treats as fatal.

### Recommendation
- In `setAprs`/`setAprsWithBuffer`, revert (or force-settle the open bucket) when `apr0TotalPrincipal != 0` and the new `unscaledApr != 0`, so the invalid state is unreachable.
- Alternatively, remove the `unscaledApr != 0` revert in `prepareStopEpochWithApr0` and settle the open APR0 bucket at the stored rate (or zero rate) for its recorded `principalEpoch`, since `apr0RateByEpoch` is already keyed per-epoch and does not depend on the current APR.
- Emit an event and document that APR must remain 0 across the full request lifecycle (request epoch through the following `stopEpoch`).

### Proof of Concept
Foundry fork test (place in `test/foundry/IdleCreditVault.t.sol`, reusing the file's helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `AAtranche`, `initialProvidedApr`, `manager`, `borrower`):

```solidity
function testApr0BucketBricksStopEpoch() external {
  IdleCreditVault creditVault = IdleCreditVault(address(strategy));

  // Configure a zero-APR epoch
  vm.prank(manager);
  creditVault.setAprs(0, 0);

  // Attacker: KYC'd lender deposits and requests a withdraw while APR == 0
  address attacker = makeAddr('apr0-attacker');
  _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
  idleCDO.depositAA(10_000 * ONE_SCALE); // keep pool solvent
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(0, address(AAtranche));

  assertGt(creditVault.apr0TotalPrincipal(), 0, 'APR0 bucket not armed');

  // Epoch runs with the bucket open
  _startEpochAndCheckPrices(0);

  // Manager reprices APR mid-epoch (allowed by setAprs auth: cdo or manager)
  vm.prank(manager);
  creditVault.setAprs(initialProvidedApr, initialProvidedApr);

  // Borrower repays fully; epoch end passes
  deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
  vm.warp(cdoEpoch.epochEndDate() + 1);

  // Reachable assertion: every stopEpoch path reverts while bucket is open
  vm.prank(manager);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.stopEpoch(0, 0);

  vm.prank(manager);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.stopEpoch(0, 1); // even the recall-everything close path is blocked

  // Funds stay frozen: epoch still running, claims still gated
  assertTrue(cdoEpoch.isEpochRunning(), 'epoch should be stuck');
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  vm.prank(attacker);
  cdoEpoch.claimWithdrawRequest();

  // Only remediation is manager restoring unscaledApr = 0, after which the
  // APR0 bucket settles at the wrong-APR epoch's realized rate.
  vm.prank(manager);
  creditVault.setAprs(0, 0);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);
}
```

The assertion at `IdleCreditVault.sol:506` is reachable purely from the attacker's `requestWithdraw` plus a permitted APR update, and blocks every stop path including the `_interest == 1` emergency recall, freezing the full pool NAV until manual remediation.

  /// @param _unscaledApr unscaled APR
  /// @param _duration epoch duration
  /// @param _buffer buffer duration
  function setAprsWithBuffer(uint256 _unscaledApr, uint256 _duration, uint256 _buffer) external {
    unscaledApr = _unscaledApr;
    setApr(_duration == 0 ? _unscaledApr : _unscaledApr * (_duration + _buffer) / _duration);
  }
