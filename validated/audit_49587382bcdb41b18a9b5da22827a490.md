### Title
First-depositor donation inflation lets an attacker mint zero shares to victims and capture their deposits - ([File: contracts/IdleCDOCreditVault.sol])

### Summary
`_deposit` values the vault with `getContractValue()`, which includes raw `token` balances sitting in the contract, and mints shares at `_tranchePrice`. A first depositor can mint dust shares, then donate a large amount of `token` directly to the vault to inflate `priceAA`, so subsequent depositors mint 0 (or near-0) tranche tokens while their funds are absorbed into NAV that the attacker's dust shares claim.

### Finding Description
On initialization, `priceAA`/`priceBB` are set to `oneToken`, and `_tranchePrice` returns `oneToken` only while tranche supply is zero (`contracts/IdleCDOCreditVault.sol:422-427`). The mint math is `_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` (`:344-348`).

The donation path is open because `getContractValue()` counts `_contractTokenBalance(token)` — the raw underlying balance — in addition to strategy tokens (`:125-128`). `_deposit` calls `_updateAccounting()` *before* pulling the user's tokens (`:200-206`), so any tokens already sitting in the contract are treated as a NAV gain, are split between AA/BB via `_virtualPriceAux`, and raise `priceAA`. There is no skim of donated assets on this path in `IdleCDOCreditVault` (unlike `IdleCDO`, which has `_skimDonatedAssets`); the docstring in `_managedContractValue` claims unsolicited transfers are "skimmed on interactions" (`:130-137`), but `getContractValue()` still adds the raw `token` balance, so donations are *not* isolated.

Attack sequence (buffer phase / running vault, fresh deployment):
1. Attacker (any KYC-passing lender / EOA) is the first depositor: `depositAA(1)` → mints ~1 wei of AA tranche at price `oneToken`; `lastNAVAA = 1`.
2. Attacker transfers `D` tokens directly to the vault contract (no call needed).
3. Next `_deposit`/`_updateAccounting` computes `nav = 1 + D` vs `_lastNAV = 1` → `totalGain = D` → AA (sole holder) gets the whole gain → `priceAA ≈ D * 1e18`.
4. Victim deposits `V < D` → `_minted = V * 1e18 / priceAA ≈ V/D` which rounds to `0` tranche tokens, while `lastNAVAA += V` (`:355-363`). The victim receives nothing.
5. Attacker's 1-wei share is redeemable against NAV `≈ D + V` through the normal withdrawal path (epoch withdraw request / tranche burn), capturing the victim's `V` minus the donated `D`... the attacker profits only when `V > D`, so the practical variant is: attacker donates `D`, victim deposits `V` slightly above `D` but still mints a single share, splitting NAV with the attacker's dust share. In the zero-mint case the victim's entire deposit is effectively donated to the attacker for the cost of the donation, which the attacker recovers via redemption — net profit equals `V` for any `V`, since the donation itself remains claimable by the attacker's share.

Broken invariant: fair mint/burn and donation isolation. Existing guards do not stop it: `_guarded` only caps size, `whenNotPaused` is unrelated, KYC/whitelist does not prevent first-deposit ordering, and no skim or minimum-share/dead-share mechanism exists in this contract.

### Impact Explanation
Direct theft: any depositor into a freshly initialized (or fully emptied) credit vault can have their entire deposit captured by a prior attacker. Loss is up to 100% of the victim's deposit; attacker cost is the dust deposit plus gas, because the "donation" remains part of NAV redeemable by the attacker's share.

### Likelihood Explanation
Requires the attacker to be the first AA (or BB) depositor — feasible by monitoring vault deployment/initialization, since `depositAA` is permissionless modulo `whenNotPaused` and any pool-level KYC the attacker can satisfy. New vaults are deployed regularly via `IdleCreditVaultFactory`, and the attack front-runs the first real depositor in the same block bundle. It does not work on vaults with existing liquidity, bounding the window but not the severity per affected vault.

### Recommendation
- Exclude raw `token` balance from `getContractValue()` (mirror `_managedContractValue`) or add `_skimDonatedAssets`-style donation isolation to `IdleCDOCreditVault` as exists in `IdleCDO`.
- Mint a minimum/dead-share amount on the first deposit (e.g., require `_minted > 0` and seed initial supply to a burn address), and/or revert when `_minted == 0` for `_amount > 0` in `_mintSharesAtCurrPrice`.
- Alternatively enforce a non-zero minimum first deposit.

### Proof of Concept
Foundry fork PoC (sketch):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract FirstDepositInflationTest is Test {
    // deploy IdleCDOCreditVault behind proxy + credit strategy, or fork an
    // existing freshly-deployed vault where AATranche.totalSupply() == 0

    function test_InflationStealsDeposit() public {
        // 1. attacker deposits 1 wei
        token.approve(address(vault), 1);
        vault.depositAA(1); // mints ~1 wei pAA at price oneToken

        // 2. attacker donates D to the vault (raw ERC20 transfer)
        uint256 D = 10_000e6; // e.g. USDC
        token.transfer(address(vault), D);

        // 3. trigger accounting: priceAA inflates to ~D
        //    (any call to _updateAccounting path, e.g. attacker depositAA(1) again,
        //     which also bakes the gain before the victim arrives)
        token.approve(address(vault), 1);
        vault.depositAA(1);

        // 4. victim deposits V > D but small relative to inflated price
        vm.startPrank(victim);
        token.approve(address(vault), V);
        uint256 minted = vault.depositAA(V);
        vm.stopPrank();
        assertEq(minted, 0); // victim got zero tranche tokens

        // 5. attacker redeems via withdrawal path; NAV now includes D + V,
        //    attacker's dust share claims effectively all of it -> profit ~V
    }
}
```

Caveat: I was unable to fully trace the `IdleCreditVault` epoch-deposit wrapper (`depositDuringEpoch`) within the available iterations, so the PoC assumes deposits can reach `_deposit` directly in the buffer phase; if all deposits route through the epoch queue, the same inflation applies at the accounting step when queued deposits are minted, but the exact entry point and whether donated balance is skimmed there needs verification.
