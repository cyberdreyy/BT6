### Title
Forced deleverage reverts on banks in `Paused` operational state, blocking the emergency risk-unwind mechanism - (File: `programs/marginfi/src/instructions/marginfi_account/withdraw.rs`, `programs/marginfi/src/instructions/marginfi_account/repay.rs`)

### Summary
`start_deleverage` / `ACCOUNT_IN_DELEVERAGE` is marginfi's analog of the HMX/GMX-style forced-deleverage safety mechanism: the risk admin snapshots an unhealthy or risky account and then issues `lending_account_withdraw` / `lending_account_repay` instructions to forcibly unwind it, bypassing the normal signer and (protocol-wide) pause checks so the incident can be resolved end-to-end. However, each of these instructions still unconditionally calls `validate_bank_state(&bank, InstructionKind::FailsInPausedState)` against the *per-bank* `operational_state`, which is never bypassed for `ACCOUNT_IN_DELEVERAGE`. If the specific bank involved in the deleverage (collateral or liability side) has been individually set to `Paused` — analogous to a "closed market" — the withdraw/repay leg of the deleverage reverts with `BankPaused`, exactly mirroring the reported HMX bug where deleveraging reverted for positions in markets that were in closed trading hours.

### Finding Description
`start_deleverage` sets `ACCOUNT_IN_RECEIVERSHIP`/marks the account for a forced unwind, and the accompanying documentation states the pause bypass exists specifically "so a deleverage can be completed end-to-end": [1](#0-0) 

The `group`-level constraint in both `LendingAccountWithdraw` and `LendingAccountRepay` does bypass the protocol-wide pause (`is_protocol_paused()`) when `ACCOUNT_IN_DELEVERAGE` is set: [2](#0-1) [3](#0-2) 

But the *bank-level* operational-state check inside the instruction body is unconditional and has no `ACCOUNT_IN_DELEVERAGE` carve-out: [4](#0-3) [5](#0-4) 

`validate_bank_state` throws `MarginfiError::BankPaused` for any instruction of `InstructionKind::FailsInPausedState` when `bank.config.operational_state == BankOperationalState::Paused`, with no exception for deleverage/receivership flags: [6](#0-5) 

The bank-state documentation confirms `Paused` blocks Withdraw, Repay, and Liquidate unconditionally, and that `Paused` is also the mandatory default state for every newly created bank and a common emergency response state: [7](#0-6) 

This means: if the risk admin pauses a specific bank in response to an incident (e.g., depegged collateral, broken oracle, exploited integration) — the textbook scenario in which a forced deleverage would be needed to unwind exposure to that asset — the withdraw/repay legs of `start_deleverage`/`end_deleverage` on that bank will revert with `BankPaused`, exactly like the HMX `TradeService.sol` bug where the deleveraging safety mechanism reverted for positions in "closed" markets.

### Impact Explanation
This breaks a documented emergency risk-management guarantee: the `PERMISSIONS_AND_ROLES.md` guide explicitly states forced deleverage is meant to "run... end-to-end" while other operations are blocked, including implying it works around exactly the kind of incident (a bank being frozen) that triggers deleverage need. If a bank is Paused due to an incident and the risk admin cannot withdraw collateral or repay debt for accounts holding positions in that bank via the deleverage flow, bad debt cannot be resolved through the intended safety mechanism, prolonging insolvency exposure and potentially forcing riskier workarounds (e.g., temporarily un-pausing a compromised bank, which reintroduces the very risk the pause was meant to contain). This is a durable freeze of the deleverage functionality with financial effect (undischarged bad debt / delayed loss socialization), not merely cosmetic.

### Likelihood Explanation
Likelihood is credible but conditional: it requires the specific scenario where an admin has set a bank's `operational_state` to `Paused` (a standard, documented emergency action) while accounts with exposure to that bank simultaneously need forced deleverage. Since `Paused` is both the default state for new banks and the recommended action "to halt all activity on a bank while investigating an issue," and deleverage is precisely the mechanism intended for use during such issues, the overlap of these two conditions is a realistic operational scenario rather than a purely theoretical one.

### Recommendation
Extend the bank-level `validate_bank_state` bypass logic (or add a new `InstructionKind`/parameter) so that when the calling account carries `ACCOUNT_IN_DELEVERAGE` (and analogously `ACCOUNT_IN_RECEIVERSHIP`, if intended for liquidation of paused-bank positions too), the `Paused` bank-state check in `lending_account_withdraw` and `lending_account_repay` is skipped, consistent with the documented intent that forced deleverage can "complete end-to-end." `KilledByBankruptcy` should remain a hard block in all cases since that state is irrecoverable by design.

### Proof of Concept
1. Group admin sets `sol_bank` (or any bank holding a distressed borrower's collateral) to `BankOperationalState::Paused` via `configure_bank`, per the state-transition rules in `configure()`: [8](#0-7) 
2. Risk admin calls `start_deleverage` on the borrower's unhealthy `MarginfiAccount`, which succeeds and sets receivership/deleverage flags per `start_receivership`: [9](#0-8) 
3. Within the same transaction, risk admin issues `lending_account_withdraw` for the paused `sol_bank` to withdraw collateral (or `lending_account_repay` for a paused liability bank). The protocol-level pause bypass constraint passes (protocol may not even be paused), but the instruction body's `validate_bank_state(&bank, InstructionKind::FailsInPausedState)` call executes because the bank itself is `Paused`, returning `MarginfiError::BankPaused` and reverting the entire deleverage transaction. [4](#0-3)

```rust
#[derive(Debug, Clone, Copy)]
pub enum InstructionKind {
    /// Only fails if the bank is in `BankKilledByBankruptcy`, technically doesn't exist (yet)
    Unrestricted,
    /// E.g. withdraw, repay
    FailsInReduceState,
    /// E.g. liquidation
    FailsInPausedState,
    /// E.g. borrow, deposit
    FailsIfPausedOrReduceState,
}

// TODO remove redundant checks for these elsewhere in the program (they are nested many laters deep
// in various value delta functions)
/// Validate the bank's state does not forbid the execution of an instruction
pub fn validate_bank_state(bank: &Bank, kind: InstructionKind) -> MarginfiResult {
    if bank.config.operational_state == BankOperationalState::KilledByBankruptcy {
        return err!(MarginfiError::BankKilledByBankruptcy);
    }
    // Bank exists but has not completed one-time setup (e.g. JupLend seed deposit). Block every
    // operation until init runs.
    if bank.config.operational_state == BankOperationalState::Uninitialized {
        return err!(MarginfiError::BankUninitialized);
    }

    match kind {
        InstructionKind::FailsInReduceState if bank.config.operational_state.is_reduce_only() => {
            return err!(MarginfiError::BankReduceOnly);
        }

        InstructionKind::FailsInPausedState
            if bank.config.operational_state == BankOperationalState::Paused =>
        {
            return err!(MarginfiError::BankPaused);
        }

        InstructionKind::FailsIfPausedOrReduceState
            if matches!(
                bank.config.operational_state,
                BankOperationalState::Paused
                    | BankOperationalState::ReduceOnly
                    | BankOperationalState::ReduceOnlyWithBorrowingPower
            ) =>
        {
            return match bank.config.operational_state {
                BankOperationalState::Paused => {
                    err!(MarginfiError::BankPaused)
                }
                state if state.is_reduce_only() => {
                    err!(MarginfiError::BankReduceOnly)
                }
                _ => unreachable!(),
            };
        }
        _ => {}
    }

    Ok(())
}
```

**File:** guides/ADMIN/BANK_STATE.md (L18-58)
```markdown
### Paused

All operations are halted. Users cannot deposit, borrow, withdraw, repay, or be liquidated. This is
the default state for newly created banks.

Use cases:
- Initial setup: configure the bank before allowing users to interact with it.
- Emergency: halt all activity on a bank while investigating an issue.

### Operational

Normal operations. All user actions are allowed: deposit, borrow, withdraw, repay, and liquidation.

### ReduceOnly

Only withdrawals and repayments are allowed. New deposits and borrows are blocked. This state is
intended for winding down a bank.

Important nuances for health calculations in ReduceOnly:
- **Initial margin**: assets in a ReduceOnly bank are valued at **$0**. This means users cannot
  open new borrows using ReduceOnly collateral.
- **Maintenance margin**: assets in a ReduceOnly bank retain their **full value**. This means
  existing positions are not immediately liquidatable just because a bank entered ReduceOnly.

This asymmetry is by design: the system prevents new risk from being taken on ReduceOnly assets,
while not force-liquidating users who already hold them.

### KilledByBankruptcy

The bank was killed by a bankruptcy event and is irrecoverable. All operations are blocked. This
state can only be set programmatically by the `handle_bankruptcy` instruction when a bankruptcy
event wipes out all remaining assets in the bank. It **cannot** be set manually by an admin.

## Summary Table

| State | Deposit | Borrow | Withdraw | Repay | Liquidate | Initial Margin | Maintenance Margin |
|-------|---------|--------|----------|-------|-----------|----------------|--------------------|
| **Paused** | No | No | No | No | No | N/A | N/A |
| **Operational** | Yes | Yes | Yes | Yes | Yes | Full value | Full value |
| **ReduceOnly** | No | No | Yes | Yes | Yes | $0 | Full value |
| **KilledByBankruptcy** | No | No | No | No | No | N/A | N/A |
```

```rust
pub fn start_deleverage<'info>(ctx: Context<'info, StartDeleverage<'info>>) -> MarginfiResult {
    let mut marginfi_account = ctx.accounts.marginfi_account.load_mut()?;
    let mut liq_record = ctx.accounts.liquidation_record.load_mut()?;
    liq_record.liquidation_receiver = ctx.accounts.risk_admin.key();
    marginfi_account.set_flag(ACCOUNT_IN_DELEVERAGE, false);
    marginfi_account.indexer_flags.has_ever_been_deleveraged = 1;
    start_receivership(
        &mut marginfi_account,
        &mut liq_record,
        ctx.remaining_accounts,
        true,
    )?;

    let sysvar = &ctx.accounts.instruction_sysvar;
    validate_instructions(
        sysvar,
        ctx.program_id,
        &ix_discriminators::START_DELEVERAGE,
        &ix_discriminators::END_DELEVERAGE,
    )
}
```
