### Title
Manipulable ERC4626 share price inflates `totalInterestDueNow`, minting unbacked strategy tokens at `stopEpoch` - (contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In programmable-borrower mode, `stopEpoch` prices epoch interest from `IProgrammableBorrower.totalInterestDueNow()`, which derives vault interest from `vault.convertToAssets(shares)` — a spot ERC4626 valuation that an unprivileged vault user can transiently inflate (direct donation to the vault, or manipulation of the vault's own underlying reserves). Because interest is handled in minted mode (`isInterestMinted`), the inflated value is crystallized by `mintStrategyTokens(_grossInterest)` and baked into `lastNAVAA`/`lastNAVBB` via `_updateAccounting`, letting the attacker redeem tranche tokens against phantom yield before the share price reverts and the loss is socialized onto remaining holders.

### Finding Description
`ProgrammableBorrower._currentVaultAssets()` values the position as `vault.convertToAssets(vault.balanceOf(address(this)))` (ProgrammableBorrower.sol:546-549). `_vaultNetInterest()` then reports `bufferedVaultDelta + earnedAssets - principalAssets` as vault interest (lines 337-347), and `totalInterestDueNow()` exposes it as the pool-facing epoch gain (lines 330-334).

`IdleCDOEpochVariant._stopEpoch` resolves `_interest` through `_resolveStopEpochInterest` (line 357), which in programmable mode reads `totalInterestDueNow()` (programmable callers may only pass `0` or `1`, per line 320). The `maxApr` sanity cap at line 379 only runs when `_interest > 1`, so it never bounds the resolved value. With `isInterestMinted` (required for programmable borrowers — `setIsInterestMinted` reverts otherwise, IdleCDOEpochVariant.sol:166-169) and `_interest != 1`, `_amountToPullFromBorrower` is `0` and the full `_grossInterest` is created out of thin air via `_strategy.mintStrategyTokens(_grossInterest)` (line 430). `getContractValue` counts strategy-token balance 1:1 (IdleCDOCreditVault.sol:125-128), so `_updateAccounting` splits the phantom gain across tranche NAVs and raises `priceAA`/`priceBB`.

`_skimDonatedAssets` only sweeps raw `token` held by the CDO itself; it cannot observe or filter inflation inside the external vault's `convertToAssets`.

### Impact Explanation
1. During a running epoch, attacker (a user of the borrower's ERC4626 vault — explicitly an allowed unprivileged actor) transiently pumps the vault's share price (donation to the vault or manipulation of its reserve source).
2. Honest manager calls `stopEpoch(0, newApr)`; `totalInterestDueNow()` returns inflated `vaultInterest`; `_grossInterest` phantom strategy tokens are minted; tranche prices rise.
3. Attacker `requestWithdraw`/`claimWithdrawRequest` (or sells tranche tokens) at the inflated price, extracting real underlying held for pending claims.
4. Vault price normalizes; the minted strategy tokens remain in NAV until a subsequent accounting realizes the loss BB-first. If the attacker exits first, remaining LPs absorb the inflated mint.

Quantified loss: up to the delta the attacker can inject into `convertToAssets` × PB's share balance, converted directly into over-minted tranche redemption value — direct theft of pool assets, not just a DoS.

### Likelihood Explanation
Requires a programmable-borrower vault whose `convertToAssets` is manipulable by unprivileged users (donation-inflatable or reserve-derived) — the same class the external report describes (`additionalOwnedAssets` manipulation). The protocol's mitigation "enforce monotonic share price off-chain" is a governance guarantee, not a code guard; nothing in `_stopEpoch` caps resolved interest in the `_interest == 0` path. Likelihood is medium: it needs a manipulable integrated vault and timing around `stopEpoch`, but requires no privileged compromise.

### Recommendation
- Enforce the `maxApr` bound on the resolved interest for all stop paths, not only `_interest > 1`.
- Track vault position via cost-basis accounting (assets deposited minus withdrawn, as already done via `epochDepositedToVault`/`epochWithdrawnFromVault`) and only count *realized* PnL from actual `withdraw`/`redeem` proceeds rather than spot `convertToAssets`.
- Alternatively cap `vaultInterest` per epoch by a configured bound or TWAP of the vault share price.

### Proof of Concept
Foundry fork sketch (against `test/foundry/ProgrammableBorrowerCreditVault.t.sol` harness):

```solidity
// epoch running, isInterestMinted = true, PB holds shares of external ERC4626 `vault`
uint256 sharesPB = vault.balanceOf(address(pb));
uint256 pricePre = vault.convertToAssets(1e18);

// 1. Attacker inflates vault share price (donation or reserve manipulation)
uint256 spike = 500_000e6;
deal(asset, attacker, spike);
vm.prank(attacker);
IERC20(asset).transfer(address(vault), spike); // or swap that skews vault reserves

uint256 inflatedInterest = pb.totalInterestDueNow();
assertGt(inflatedInterest, expectedLegitInterest);

// 2. Honest manager stops epoch -> mints phantom strategy tokens
vm.warp(cdo.epochEndDate() + 1);
vm.prank(manager);
cdo.stopEpoch(newApr, 0);

uint256 priceAA = cdo.virtualPrice(address(AAtranche)); // inflated

// 3. Attacker exits tranche at inflated NAV
vm.prank(attacker);
cdo.requestWithdraw(0, address(AAtranche));
vm.prank(attacker);
cdo.claimWithdrawRequest();

// 4. Vault price reverts; minted interest was unbacked -> residual holders take the loss
```

Uncertainty I could not fully resolve within the search budget: the exact body of `_resolveStopEpochInterest` (the snippet shows it is called at line 357 but its implementation confirming the `totalInterestDueNow` read was not opened) — however the natspec at lines 325-334 of `ProgrammableBorrower.sol` states it is "the single value read by IdleCDO to price the epoch," which supports the trace.
