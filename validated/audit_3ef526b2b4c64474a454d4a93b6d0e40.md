### Title
DKG result export endpoint permits low-privilege Edit-role callers to exfiltrate the full raw DKG secret package for any instance, with no ownership check or field redaction - ([File: core/web/vault_controller.go], [File: core/web/presenters/vault.go])

### Summary
`VaultController.ExportDKGResult` is registered behind `auth.RequiresEditRole` rather than `auth.RequiresAdminRole`, unlike every other secret/key export endpoint in the router. `presenters.NewExportDKGResultResource` unconditionally serializes the full `HexDKGResultPackage` with no per-instance ownership check or redaction, so any Edit-role token/session can fetch the raw encrypted DKG result package for an arbitrary `instanceId` it never participated in.

### Finding Description
The route is registered as: [1](#0-0) 

Contrast this with every other secret-bearing export route in the same file (ETH, OCR, OCR2, VRF, CSA, and generic chain keys), which are all gated by `auth.RequiresAdminRole`: [2](#0-1) [3](#0-2) 

`ExportDKGResult` takes an attacker-supplied `instanceId`, looks it up directly via the ORM with no check that the caller (or the credential's role/token) is associated with or authorized for that specific DKG instance, and returns the full raw package: [4](#0-3) 

The presenter then unconditionally marshals the raw hex-encoded result package into the JSON response, with no field-level redaction based on caller role or DKG-instance ownership: [5](#0-4) 

Because `RequiresEditRole` is a strictly lower privilege bar than `RequiresAdminRole` (used everywhere else for key/secret export in this router), and because there is no instance-level authorization check tying the requester to the specific DKG round, any credential holding only Edit role (which may be issued for mundane purposes like managing bridges or jobs) can pull the complete raw DKG result package for any instance ID stored on the node — including rounds it had no part in.

### Impact Explanation
This maps to the Chainlink bounty "key or secret disclosure" / "role or authorization bypass" impact class. Successful exploitation discloses the raw hex-encoded DKG result package (the multi-party encrypted secret share material for a DON's vault DKG round) to a caller whose privilege level was never intended to authorize secret export, since the analogous operations (VRF/OCR/ETH/CSA key export) all require Admin role. This is a privilege-boundary violation: sensitive DKG oracle secret material is reachable one authorization tier below every comparable export endpoint, and with no per-instance ownership check.

### Likelihood Explanation
Exploitation requires only an Edit-role API token or session — a much lower bar than Admin, and Edit-role tokens are commonly issued to less-trusted integrations (e.g., CI systems managing job/bridge configuration) that have no business accessing DKG secrets. The `instanceId` is caller-supplied and requires no proof of participation, so the attack is trivially repeatable against any known/guessable instance ID once Edit-level access is obtained.

### Recommendation
- Change the route registration to `auth.RequiresAdminRole(vault.ExportDKGResult)` (and consider the same for `VerifyDKGResult` if it also exposes sensitive material), consistent with all other key/secret export endpoints.
- Add an explicit instance-ownership/authorization check in `ExportDKGResult` before returning the package, rather than relying solely on route-level role gating.

### Proof of Concept
1. Handler-level integration test: create an Edit-role (non-Admin) authenticated API token; seed the vault ORM with a `ReportWithResultPackage` for `instanceId = "X"`; issue `POST /v2/vault/dkg_results/export` with `{"instanceId":"X"}` using the Edit-role token; assert HTTP 200 and that `hexDKGResultPackage` field is present in the response — demonstrating that a role below the Admin bar used for all sibling export endpoints can retrieve raw secret material.
2. Table-based router test verifying that `/vault/dkg_results/export` currently resolves via `auth.RequiresEditRole` while `/keys/*/export/*` resolve via `auth.RequiresAdminRole`, to lock in the intended fix (route uses `RequiresAdminRole`) and prevent regression.
3. Unit test on `presenters.NewExportDKGResultResource` confirming no redaction/ownership context is threaded through, i.e., any (hexResult, sha) pair is serialized verbatim — supporting the finding that redaction must be enforced at the authorization layer, not the presenter.

```go
func (vc *VaultController) ExportDKGResult(c *gin.Context) {
	var req ExportDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	hexPackage := hex.EncodeToString(v.ReportWithResultPackage)
	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewExportDKGResultResource(hexPackage, shaStr), "exportDKGResult")
```

```go
type ExportDKGResultResource struct {
	JAID
	HexDKGResultPackage string `json:"hexDKGResultPackage"`
	SHA                 string `json:"sha"`
}

// GetName implements the api2go EntityNamer interface
func (ExportDKGResultResource) GetName() string {
	return "exportDKGResult"
}

func NewExportDKGResultResource(hexResult, sha string) ExportDKGResultResource {
	return ExportDKGResultResource{
		JAID:                NewJAID(sha),
		HexDKGResultPackage: hexResult,
		SHA:                 sha,
	}
}
```
