### Title
Withdraw-request interest is fixed at request time from a still-mutable epoch APR, letting lenders lock stale high-APR receipts paid by the borrower - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
Analogous to `TwabLib::getTwabBetween` returning inaccurate balances when the queried time range is not safely bounded, `IdleCDOEpochVariant.requestWithdraw` mints a fixed withdraw receipt whose interest component is priced with `_calcInterestWithdrawRequest` using the strategy's *currently stored* APR and NAV — values that remain mutable for the entire buffer window until `startEpoch` crystallizes `expectedEpochInterest`. A lender can request a withdrawal while the announced APR is high, then have the manager legitimately lower the APR before the next epoch starts; the receipt keeps the stale high-APR interest and the borrower is forced to fund it at `stopEpoch`.

### Finding Description
`requestWithdraw` computes the receipt amount as `principal + interest - fees`, where `interest` comes from `_calcInterestWithdrawRequest` → `_calcInterest(_managedContractValue())` → `_calcInterestWithApr(_amount, _getStrategyApr())`, i.e. the strategy's `lastApr` at request time (`IdleCDOEpochVariant.sol` lines 773-790, 800-809, 856-878). The strategy's APR is set for the *next* epoch at `stopEpoch` (line 469-470 and `IdleCreditVault.setAprsWithBuffer`/`setApr`, lines 217-235), but `setApr`/`setAprsWithBuffer` remain callable by the manager at any time during the buffer, and the projected NAV/`trancheAPRSplitRatio` also keep shifting as other users deposit or request withdrawals during the same buffer.

Once minted, the receipt is irrevocably added to `IdleCreditVault.requestWithdraw`'s `pendingWithdraws` (`IdleCreditVault.sol` line 279), and `stopEpoch` unconditionally pulls `_amountToPullFromBorrower + _pendingWithdraws` from the borrower (`IdleCDOEpochVariant.sol` lines 398-410). There is no re-pricing, no equivalent of `isTimeRangeSafe`, and no check that the APR/NAV used for the receipt still matches the parameters of the epoch that actually ran — exactly the missing safety bound in the reference finding.

### Impact Explanation
Broken invariant: one receipt one payout at the rate the epoch actually applied. An unprivileged KYC'd lender front-runs a legitimate APR reduction (or any NAV change that lowers per-principal interest) during the buffer and receives `principal + principal * oldApr * epochDuration / 365` while the epoch's `expectedEpochInterest` is recomputed at `startEpoch` on the new, lower parameters. The excess `(oldApr - newApr) * principal * epochDuration / 365` is funded by the honest borrower through `getFundsFromBorrower`/`pendingWithdraws`. If the borrower cannot cover the inflated `pendingWithdraws`, `stopEpoch` falls into `_handleBorrowerDefault`, so the stale receipt can also trigger a spurious default — direct theft or forced insolvency, quantified by the APR delta times the requested principal.

### Likelihood Explanation
The attack requires no privileged role: the attacker is any allowlisted tranche holder calling `requestWithdraw` in the buffer phase. It pays off whenever the APR (or NAV/split ratio) changes between the request and `startEpoch` — a normal, permitted manager action (`setApr` has no epoch-phase gating in `IdleCreditVault.sol` lines 225-235), and deposits/withdrawals by other users during the buffer are routine. The APR0 path partially acknowledges this mutability by deferring interest settlement to `stopEpoch` (`_settleApr0`, `apr0RateByEpoch`), but fixed-APR requests receive no such finalization, which is precisely the unbounded-range error.

### Recommendation
Apply the analog of `isTimeRangeSafe`: do not finalize withdraw-receipt interest at request time from mutable inputs. Either (a) record only the request principal at `requestWithdraw` and compute the interest at `startEpoch`/`stopEpoch` using the finalized epoch parameters (as the APR0 bucket already does via `apr0RateByEpoch`), or (b) freeze the withdraw-pricing inputs once the buffer opens — e.g. revert `setApr`/`setAprsWithBuffer` while requests can still be made, or snapshot `lastApr`, `_managedContractValue()` and `trancheAPRSplitRatio` at `stopEpoch` and price all subsequent requests against that snapshot, reverting requests if parameters change before `startEpoch`.

### Proof of Concept
Foundry fork PoC (against the in-repo harness in `test/foundry/IdleCreditVault.t.sol`):

1. Deposit: `idleCDO.depositAA(100_000e6)` as attacker; complete epoch 0 via `_startEpochAndCheckPrices(0)` and `_stopEpochAndCheckPrices(0, 10e18, ...)` so `unscaledApr`/`lastApr` for the upcoming epoch is 10%.
2. During the buffer, attacker calls `cdoEpoch.requestWithdraw(0, address(AAtranche))`; receipt minted = `principal + principal * 10% * epochDuration/365 - fees`, `pendingWithdraws` increases by that full amount.
3. Manager legitimately revises the upcoming epoch APR to 2% before starting: `IdleCreditVault(strategy).setAprs(2e18, scaledApr)` (or `setAprsWithBuffer`).
4. `startEpoch()` computes `expectedEpochInterest` at 2% on live NAV; warp to `epochEndDate + 1`; `stopEpoch` pulls `expectedEpochInterest + pendingWithdraws` — the borrower's `deal`/repayment must cover the attacker's stale 10%-rate interest.
5. `claimWithdrawRequest()` pays the attacker the excess `(10% - 2%) * principal * epochDuration/365` in underlyings beyond a fair receipt; alternatively, funding only the honest 2% amount makes `getFundsFromBorrower` fail and forces `_handleBorrowerDefault`.

Note: I could not fully verify `setAprsWithBuffer`'s caller surface in the remaining iterations, but `setApr` itself is confirmed callable by the manager at any time and is the only input `_calcInterest` reads, so the stale-value window exists regardless of which setter is used.
