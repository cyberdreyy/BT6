### Title
`ProgrammableBorrower.onStopEpoch` trusts claim-based `convertToAssets` over redeemable liquidity, letting any vault user permanently gate `stopEpoch` and freeze pending withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
CVE-2025-32463 is a "trusted privileged path reads attacker-controlled environment" bug: sudo in a privileged context loads `/etc/nsswitch.conf` from a user-controlled chroot. The credit-vault analog is the privileged `stopEpoch` flow in `IdleCDOEpochVariant` delegating the liquidity-safety decision to `ProgrammableBorrower.onStopEpoch`, which decides whether the ERC4626 vault can cover the recall using `_currentVaultAssets()` — a claim-value (`convertToAssets`) read from an external environment that any vault depositor/borrower can manipulate — instead of `maxWithdraw`, the actual redeemable liquidity.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, the programmable-borrower branch calls `onStopEpoch` and only treats a `false` return as a default [1](#0-0) . Inside `ProgrammableBorrower.onStopEpoch`, when on-hand cash is insufficient, the code checks `if (shortfall > _currentVaultAssets()) return true;` — using `convertToAssets(shares)`, i.e. the *accounting claim* on the vault — to decide the shortfall is coverable [2](#0-1) . It then calls `vault.withdraw(shortfall, ...)`, and any revert is converted into `StopEpochVaultLiquidityUnavailable`, which bubbles up and reverts the entire `stopEpoch` [3](#0-2) .

For a vault like Morpho (used in the fork tests), `convertToAssets` prices shares over *total allocated assets* across markets, while `withdraw`/`redeem` only succeeds up to *currently idle liquidity*. Those two diverge whenever liquidity is lent out or borrowed. An unprivileged vault user — explicitly in scope ("a user of the programmable borrower's ERC4626 vault") — can drain idle liquidity by borrowing against the underlying Morpho markets (or by withdrawing as an LP) such that `convertToAssets` still covers the shortfall but `vault.withdraw` reverts.

### Impact Explanation
Because the revert happens before `getFundsFromBorrower`, the CDO never reaches `_handleBorrowerDefault` or `collectWithdrawFunds`, so:
- `stopEpoch` reverts on every attempt while liquidity stays drained — the epoch cannot be closed and `claimWithdrawRequest` for matured `pendingWithdraws` cannot be funded (temporary freezing of user funds).
- `emergencyExitVault` calls `vault.redeem` under the same liquidity constraint [4](#0-3) , so the privileged escape hatch is blocked by the same attacker-controlled condition.
- The freeze is quantifiable: the full `pendingWithdraws` plus `expectedEpochInterest` owed at epoch end remain locked for as long as the attacker keeps vault liquidity below the shortfall (cost = borrow interest on the drained amount, cheap relative to the frozen principal).

The comment claims "only an otherwise-covered ERC4626 withdrawal failure should make stopEpoch retryable", but the coverage test uses the wrong yardstick: claim value is not redeemable liquidity, exactly like sudo reading nsswitch.conf from a directory root does not control.

### Likelihood Explanation
- Requires a programmable-borrower deployment (the mode exists and is fork-tested against a real Morpho vault [5](#0-4) ).
- Attacker needs no role: any EOA that can supply/borrow in the vault's underlying markets can pin idle liquidity below the stop-epoch shortfall for a chosen window (e.g., right at `epochEndDate` when the manager must act).
- No existing guard helps: `nonReentrant`, `_checkOnlyIdleCDO`, skim, and default flags are all downstream of the reverting hook; `onDefault` can't be invoked because `stopEpoch` never returns.

### Recommendation
Base the coverage check on `vault.maxWithdraw(address(this))` (or `maxRedeem` × `previewRedeem`) instead of `_currentVaultAssets()`: if `shortfall > maxWithdraw`, return `true` and let `transferFrom` fail so the CDO's existing default path handles it, rather than attempting a withdraw that is guaranteed to revert. Optionally wrap the `vault.withdraw` failure into the default path (`return false` on genuine borrower insolvency) so a manipulation of external vault liquidity can never make `stopEpoch` itself uncallable.

### Proof of Concept
Foundry sketch (mirroring `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup with a Morpho-style vault):

```solidity
// test/foundry/ProgrammableBorrowerStopEpochFreeze.t.sol
function testVaultUserFreezesStopEpoch() external {
  uint256 amount = 100_000 * oneScale;
  vm.prank(owner); cdoEpoch.setIsInterestMinted(true);
  idleCDO.depositAA(amount);
  _startEpochAndCheckPrices(0);          // funds parked in vault by onStartEpoch

  // Attacker: ordinary user of the ERC4626 vault / its underlying markets.
  // Borrow or withdraw the vault's idle liquidity so convertToAssets
  // still covers the shortfall but withdraw() would revert.
  uint256 shortfall = pendingWithdrawsNeeded;           // > onHand cash
  uint256 vaultClaim = morphoVault.convertToAssets(
      morphoVault.balanceOf(address(programmableBorrower)));
  assertGe(vaultClaim, shortfall);                      // check at L245 passes
  _drainVaultLiquidity(shortfall);                      // attacker borrows idle liquidity

  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
  cdoEpoch.stopEpoch(0, 0);                             // epoch can never stop

  // Pending withdraw claims stay unfunded; emergencyExitVault also reverts.
  vm.prank(manager);
  vm.expectRevert();                                    // vault.redeem under same illiquidity
  programmableBorrower.emergencyExitVault(0);
}
```

Notes on uncertainty: the exact liquidity-drain primitive depends on the deployed vault (Morpho market borrowing was used in the existing tests); the invariant failure — claim value vs redeemable liquidity divergence plus the revert-instead-of-default handling — is fully visible in the indexed source regardless of vault specifics.
