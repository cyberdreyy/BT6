`accountSubscribe` silently ignores the client's `minContextSlot` guarantee, letting callers receive stale account data without any error - (File: rpc/src/rpc_pubsub.rs)

### Summary
`RpcAccountInfoConfig::min_context_slot` is the JSON-RPC layer's analog to a "minimum acceptable result" guard, comparable to a slippage-protection parameter: a caller sets it to require that returned data reflect at least a given slot, and if the bank hasn't reached that slot the request is supposed to fail with `MinContextSlotNotReached` rather than silently returning older/weaker data. This guarantee is honored everywhere else in the JSON-RPC surface (`get_account_info`, `get_multiple_accounts`, `get_blocks`, `get_signatures_for_address`, etc. all call `get_bank_with_config`, which explicitly checks `min_context_slot`), but `account_subscribe` in the pubsub handler explicitly discards the field.

### Finding Description
In `RpcSolPubSubImpl::account_subscribe`, the config is destructured and `min_context_slot` is bound to `_` with an inline `// ignored` comment, while every other field of the identical `RpcAccountInfoConfig` struct (`encoding`, `data_slice`, `commitment`) is applied to build the subscription params: [1](#0-0) 

Contrast this with the plain `getAccountInfo`/`getMultipleAccounts` JSON-RPC handlers in `rpc/src/rpc.rs`, which route every request through `get_bank_with_config`, and which explicitly return `RpcCustomError::MinContextSlotNotReached` when the bank slot is behind the requested `min_context_slot`: [2](#0-1) [3](#0-2) 

This is the direct analog of the reported bug class: the caller supplies a parameter meant to bound the acceptable staleness/weakness of the result (`min_context_slot`, the RPC equivalent of a "minimum acceptable amount" guard), the API silently accepts the parameter as valid input, but the actual enforcement is dropped, so the caller receives a result that can be worse than what they explicitly required — with no error, exactly like the liquidator in the original report receiving less collateral than expected with no revert path.

### Impact Explanation
A subscriber who sets `minContextSlot` on `accountSubscribe` intends to ensure notifications only reflect state at or after a specific slot (e.g., after their own transaction landed, to avoid acting on stale pre-transaction account state). Because the check is silently dropped, subscribers can receive account-state notifications computed against banks/slots earlier than the slot they explicitly required, without any indication of the discrepancy. Downstream consumers (wallets, bots, indexers) that rely on this parameter as a correctness guarantee can act on stale/wrong data believing it satisfies their staleness bound. This matches the "wrong-slot/fork/account data returned" acceptance criterion for a valid analog — data is returned that violates an explicit caller-specified guarantee, with no error surfaced.

### Likelihood Explanation
This is trivially triggerable by any unprivileged client: simply call `accountSubscribe` with a `minContextSlot` set ahead of the current bank slot. There's no operator/validator privilege required and no race window needed — the field is unconditionally discarded on every call, so the behavior is 100% reproducible.

### Recommendation
Do not discard `min_context_slot` in `account_subscribe` (and check `program_subscribe`, which similarly does not read `min_context_slot` from `RpcProgramAccountsConfig`'s `account_config`). Either enforce it at subscription time against the current bank slot (returning `MinContextSlotNotReached` similar to `get_bank_with_config`), or gate initial/ongoing notifications so that only slots at or after `min_context_slot` are delivered, and document/reject the parameter if truly unsupported for streaming subscriptions instead of silently accepting and ignoring it.

### Proof of Concept
1. Start a validator, note current bank slot `S`.
2. Call `accountSubscribe(pubkey, { "minContextSlot": S + 1000 })` — the parameter is accepted without error (per the destructuring in `rpc/src/rpc_pubsub.rs:424-443`, it is bound to `_`).
3. Immediately receive/observe account notifications for slots `< S + 1000`, i.e., before the required minimum context slot has ever been reached, despite the caller's explicit request to bound results to that slot or later. Compare to `getAccountInfo` with the same `minContextSlot`, which correctly errors with `MinContextSlotNotReached` until slot `S + 1000` is reached (`rpc/src/rpc.rs:273-289`, `534-560`).

impl JsonRpcRequestProcessor {
    fn get_bank_with_config(&self, config: RpcContextConfig) -> Result<Arc<Bank>> {
        let RpcContextConfig {
            commitment,
            min_context_slot,
        } = config;
        let bank = self.bank(commitment);
        if let Some(min_context_slot) = min_context_slot
            && bank.slot() < min_context_slot
        {
            return Err(RpcCustomError::MinContextSlotNotReached {
                context_slot: bank.slot(),
            }
            .into());
        }
        Ok(bank)
    }
