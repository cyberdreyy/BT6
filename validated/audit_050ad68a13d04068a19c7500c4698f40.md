### Title
No refund on failed multisig deployment - missing callback in `create` - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` batches `create_account`, `deploy_contract`, `transfer(attached_deposit)`, and `function_call("new", ...)` into a single promise targeted at the new sub-account, but never attaches a `.then(...)` callback to check the outcome and refund the depositor on failure. If any action in that batch fails (e.g., the target account already exists because the same `name` was used twice, or `new` panics due to invalid `members`/`num_confirmations`), the whole batched receipt fails and the attached NEAR is not returned to the original caller, unlike the sibling `staking-pool-factory` which explicitly implements this refund pattern.

### Finding Description
The broken binding: `deposit_paid_by_caller == deposit_returned_to_caller_on_failure` should hold when deployment fails, but here it does not — there is no code path that returns the deposit to `env::predecessor_account_id()`.

Code path: `create(name, members, num_confirmations)` computes `account_id = format!("{}.{}", name, env::current_account_id())` and issues a single batched `Promise` with `create_account().deploy_contract(CODE.to_vec()).transfer(env::attached_deposit()).function_call(b"new", ...)` [3](#0-2) . There is no `#[ext_contract(ext_self)]` trait, no `on_create` callback, and no `.then(ext_self::on_create(...))` anywhere in the file — the function simply returns the promise chain. Compare this to `staking-pool-factory::create_staking_pool`, which chains `.then(ext_self::on_staking_pool_create(...))` and implements `on_staking_pool_create` to call `is_promise_success()` and, on failure, execute `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` [4](#0-3) .

Root cause: any failure in the batched actions on the `account_id` receipt (most simply, calling `create` twice with the same `name` in the same block, so `create_account` fails because the account already exists) causes the entire receipt including the `transfer` action to fail. Per NEAR's action-batch semantics, the deposit that was already deducted from the factory contract's balance and attached to that failed receipt is refunded to the receipt's *predecessor* — the factory contract itself, not the original transaction signer. Since the factory never forwards that refund back to `env::predecessor_account_id()` of the original `create` call, the attacker's NEAR is stuck in the factory contract, appearing as extra balance the factory never intended to hold, and the caller who paid receives nothing back. No existing guard (`assert_self()`, `is_promise_success()`, etc.) exists in this file to catch and remedy this because there is no callback at all.

### Impact Explanation
Repeating an identical `create(name, members, num_confirmations)` call within the same block guarantees the second attempt's `create_account` fails deterministically (the account was just created by the first call). The attached deposit from the failed second call is absorbed into the `multisig-factory` contract balance rather than refunded to the caller, causing the factory's held balance to diverge from any deposit accounting a caller or off-chain system expects, matching the "accounting value diverges from reality" High-severity category. This is trivially repeatable by any unprivileged account against itself or by griefing others' identical-parameter calls, and the blast radius is the deposit amount per failed attempt, permanently stuck (recoverable only by the factory's own privileged action, which does not exist in this contract).

### Likelihood Explanation
No special privileges, balances, or setup are needed beyond having NEAR to attach as a deposit — any account can call `create` twice with the same arguments in the same block to force a deterministic failure. This is a pure self-serve or low-cost griefing setup and is repeatable indefinitely against any `name` value.

### Recommendation
Add an `ext_self` callback trait and a `.then(ext_self::on_create(env::predecessor_account_id(), env::attached_deposit().into(), &env::current_account_id(), NO_DEPOSIT, CALLBACK_GAS))` after the deployment promise, mirroring `staking-pool-factory::on_staking_pool_create`: check `is_promise_success()` and, on failure, `Promise::new(predecessor_account_id).transfer(attached_deposit)`.

### Proof of Concept
Using `near-sdk-sim` / unit test pattern analogous to `staking-pool-factory`'s `test_create_staking_pool_rollback`:
1. Set `testing_env!` with `predecessor_account_id = attacker`, `attached_deposit = X`.
2. Call `MultisigFactory::create(name, members, num_confirmations)` — assert it returns a `Promise` with no `.then` callback (inspect via `test_utils::get_created_receipts` if available, or via `near-workspaces` sandbox test executing two `create` calls with identical arguments in the same block).
3. In a sandbox integration test, submit the same `create` transaction twice in the same block; assert the second one's receipt fails (`ExecutionStatus::Failure`).
4. Assert `attacker`'s account balance after both calls is less than `initial_balance - 2X` plus gas costs is not restored — i.e., `attacker_balance_after != attacker_balance_before - X - gas_used` for the successful call (only the first deposit should be spent), proving the second deposit was not refunded.
5. Contrast with `staking-pool-factory/src/lib.rs::test_create_staking_pool_rollback`, which asserts (`ntoy(31)` refunded via `context.account_balance += ntoy(31)` and successful callback execution) — no equivalent test or code path exists for `multisig-factory`.
