## Finding

### Title
Response cache key omits `WorkflowID`, causing cross-workflow response cache confusion - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The HTTP Handlers V2 gateway caches outbound HTTP responses using a cache key computed by `gateway_common.OutboundHTTPRequest.Hash()`. The handler's own documentation states responses are workflow-scoped ("Cache Key: Generated from workflow ID and request hash", "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage") [1](#0-0) , but the actual implementation's hash intentionally ignores `WorkflowID` while including `WorkflowOwner`, method, URL, headers, and body [2](#0-1) . This mirrors the reported bug class: a value meant to be scoped to a specific, narrow context (per-workflow cache entry / per-user redemption share) is instead computed and shared across a broader grouping (per-owner across all their workflows / per-market redemption pool), producing incorrect cross-context results.

### Finding Description
`responseCache` is described as caching HTTP responses "keyed by a hash of the request (method, URL, headers, body, workflowOwner)" [3](#0-2) . The test suite explicitly documents and asserts this behavior:

- Different `WorkflowID` values on otherwise identical requests produce the **same** hash: "having different workflowID results in same Hash" [4](#0-3) .
- Different `WorkflowOwner` values produce different hashes, but that is the only cross-owner isolation dimension [5](#0-4) .

`Fetch` and `Set` both use `req.Hash()` as the sole cache key without any additional workflow-scoping [6](#0-5) . In `makeOutgoingRequest`, the gateway calls `h.responseCache.Fetch` / `.Set` directly with the parsed `OutboundHTTPRequest` from the workflow node, with no separate workflow-ID-based cache namespace applied at the call site [7](#0-6) .

Consequently, if two different workflows belonging to the same owner (a common pattern — one owner running many concurrent CRE workflows) issue outbound HTTP action requests with the same method, URL, headers, and body (e.g., calling the same third-party API endpoint with the same static parameters), they will read and write the exact same cache entry, even though the README explicitly promises per-workflow isolation. This is a direct contradiction between the documented security property ("Workflow Isolation... to prevent cross-workflow data leakage") and the actual code.

### Impact Explanation
A workflow whose HTTP action is configured with `CacheSettings.Store = true` can have its response served to a *different* workflow belonging to the same owner (or vice versa) as long as the request signature matches. This breaks the workflow isolation guarantee documented for the gateway and can lead to one workflow's execution consuming stale or unintended data cached by another workflow, silently corrupting that workflow's results — analogous to how the `Holdings` bug let one user's redemption depend on unrelated market state rather than their own entitlement.

### Likelihood Explanation
This requires no privileged access: any workflow owner running multiple workflows that happen to issue identical outbound HTTP requests (a realistic and even common scenario for shared external API integrations) will trigger the shared cache path automatically, without any adversarial input needed. This is a straightforward correctness/isolation bug reachable through normal CRE workflow HTTP action requests.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the cache key computed by `Hash()`, or otherwise namespace the `responseCache` map by workflow ID in addition to the request hash, so that cache entries cannot be shared across distinct workflows as the README already claims.

### Proof of Concept
1. Workflow A (owner `0xabc`, workflow ID `wf-1`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings: {Store: true}}`.
2. The gateway calls `responseCache.Set` and stores the response keyed by `req.Hash()`, which does not include `WorkflowID` [8](#0-7) .
3. Workflow B (same owner `0xabc`, but workflow ID `wf-2`) issues an identical `OutboundHTTPRequest` with `CacheSettings.MaxAgeMs > 0`.
4. `responseCache.Fetch` computes the same `req.Hash()` (since `WorkflowID` is excluded, per the test at `response_cache_test.go:139-149`) and returns Workflow A's cached response to Workflow B without making a new HTTP call, violating the documented per-workflow cache isolation.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
