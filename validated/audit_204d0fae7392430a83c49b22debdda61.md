### Title
Same-tenure reorg permit blanket-excludes ALL conflicts in a superseded tenure, letting a signer double-sign a tenure-start block race - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`mark_tenure_superseded`/`reorg_permit_stands` operate at the granularity of a whole tenure (`consensus_hash`), not a specific conflicting block. Once a tenure is marked superseded because a *different*, later tenure legitimately reorged it under the `first_proposal_burn_block_timing` rule, the own-tenure conflict guard in `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1432-1457`) treats *any* same-tenure conflict as excluded, even a genuine sibling tenure-start block race that has nothing to do with the permitted reorg. This lets the signer sign two conflicting blocks in the same tenure at the same height.

### Finding Description
The equality being broken is UNIQUENESS: a signer must never sign two distinct `signer_signature_hash` values for the same tenure/height once one of them is globally accepted.

The exploit path:
1. Attacker (single miner slot) wins sortition for tenure X and broadcasts two racing tenure-start proposals A and B for tenure X, timed so that different signers see them in different orders (the same class of race already acknowledged by `run_sibling_scenario`/`reproposal_cannot_bypass_fresh_conflict` tests in `stacks-signer/src/v0/tests.rs:711-857`). At proposal time, `validate_tenure_change_payload`'s `DuplicateBlockFound` check (`stacks-signer/src/chainstate/v1.rs:505-518`) only fires if the signer already recorded a signed block for X at the moment B is validated — it does not run again later (documented at `docs/signer-flows.md:425-437`).
2. Block A eventually reaches global acceptance (one globally-accepted block in tenure X).
3. Before B's delayed pre-commit reaches the 70%/threshold re-evaluation, the attacker uses a second mining slot to win tenure Y, building off X's *parent* instead of X. Because X produced only one globally-accepted block and its first proposal was judged "too close to the next sortition" (`checked_proposal_timing` in `check_parent_tenure_choice`, `stacks-signer/src/chainstate/mod.rs:210-274`), the reorg is permitted, and `record_superseded_tenure` → `SignerDb::mark_tenure_superseded` (`stacks-signer/src/signerdb.rs:1642-1660`) records tenure X as superseded by Y, keyed only by `consensus_hash = X`.
4. B's pre-commit now finally crosses threshold. `check_block_against_signer_db_state` (`stacks-signer/src/v0/signer.rs:1803-1880`) re-checks only the *parent* tenure for a tenure-change block, so it does not see A. `get_signed_conflicts` (`stacks-signer/src/signerdb.rs:1606-1625`) returns A annotated with `superseded_by = Y` because the LEFT JOIN keys only on `consensus_hash`, not on the specific conflicting block. The first, cross-tenure conflict filter (`signer.rs:1403-1411`) already excludes A since `reorg_permit_stands` returns true. The dedicated own-tenure guard (`signer.rs:1432-1435`) is defeated the same way: because the only same-tenure conflict (A) carries a standing permit, `.any()` is false, so the node's tenure-tip authority check (`signer.rs:1436-1456`) is skipped entirely, and the code falls through to sign B (`signer.rs:1458-1467`).

The root cause is that the superseded-tenure record is a blanket exclusion for the whole tenure `X`, but the own-tenure guard it disables was purpose-built (per the code comments at `signer.rs:1423-1431` and `docs/signer-flows.md:274-286`) to catch exactly the case this attack produces: a second tenure-start block for the *same* tenure reaching pre-commit late. The permit was intended only to let tenure Y's block replace X's tip; it inadvertently also authorizes the signer to sign a second, unrelated sibling (B) still native to X itself.

### Impact Explanation
This breaks UNIQUENESS for the superseded tenure: the signer places its signature on two conflicting blocks (A, globally accepted, and B) at the same height in the same tenure, without ever consulting the node's canonical tip for that tenure. If B's signature set also reaches the network threshold, it produces a second aggregate signature bundle for tenure X's tip height, i.e., a signed equivocation — Critical per the "signer signing … conflicting block (chain safety)/UNIQUENESS" category. The exploit is repeatable for any tenure that can be made to qualify for `first_proposal_burn_block_timing` and that had a genuine sibling proposal race at its start.

### Likelihood Explanation
Preconditions: attacker needs to win two mining slots close together (X, then Y skipping X), control the timing of A's broadcast so it is judged "too close to the next sortition," and win a genuine sibling proposal race for tenure X (B pre-commit lands late, after Y's reorg is processed). This uses only the attacker's own mining resource and message gossip — no signer majority, no auth token, no local access — matching the allowed threat model, though it requires favorable timing across two consecutive tenures and a network race for the sibling block, making it opportunistic rather than trivially on-demand.

### Recommendation
Scope the reorg-permit exclusion to the specific conflicting block/height it actually authorizes, not the whole tenure: either (a) record and check `superseded_tenures` per `(consensus_hash, stacks_height)`/`first_block_mined` instead of per `consensus_hash`, or (b) in the own-tenure guard (`signer.rs:1432-1457`), never skip the node tenure-tip check purely because a *same-tenure* conflict is "superseded" — a superseded-tenure permit should only ever excuse conflicts whose `consensus_hash` differs from the currently-evaluated block's own tenure, mirroring the intended cross-tenure-only semantics documented for `reorg_permit_stands`.
