### Title
Signer restart drops the capitulation-derived `InvalidatedBeforeFirstBlock` guard on `SortitionsView.cur_sortition` because it is only set as an in-memory side effect of `LocalStateMachine::capitulate_viewpoint`, never persisted or re-derived by `SortitionsView::fetch_view`/`check_proposal` - (File: `stacks-signer/src/v0/signer_state.rs`, `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionMinerStatus::InvalidatedBeforeFirstBlock` set because the local signer's state machine capitulated to a different miner than the current sortition's winner (`LocalStateMachine::capitulate_viewpoint`, lines 964-976 of `signer_state.rs`) lives only inside the in-memory `SortitionsView`, and is applied only when a `SortitionsView` object already exists. On process restart, `sortition_state` starts as `None`, so the very next `capitulate_viewpoint` call cannot write the invalidation anywhere; the subsequent proposal handling instead calls `SortitionsView::fetch_view`, which unconditionally constructs a fresh `SortitionState` with `miner_status: SortitionMinerStatus::Valid` [1](#0-0)  and `check_proposal` never re-derives the capitulation-based mismatch on its own.

### Finding Description
`SortitionsView::check_proposal` re-derives two of the three ways `cur_sortition.miner_status` can become `InvalidatedBeforeFirstBlock` purely from persisted/re-fetchable facts, so those are restart-safe:
- Timeout invalidation is recomputed from `SortitionState::is_timed_out`, which reads persisted timestamps from `SignerDb` (`get_burn_block_receive_time_ch`, `get_last_activity_time`) [2](#0-1) .
- Parent-tenure-mismatch invalidation is recomputed via `check_parent_tenure_choice`, which reads chain data from the node and persisted `SignerDb` tenure records [3](#0-2) .

The third path is different: `LocalStateMachine::capitulate_viewpoint` marks `cur_sortition.miner_status = InvalidatedBeforeFirstBlock` purely as a side effect on an *already-existing* `SortitionsView`, when the local state machine capitulates to a different miner than the current sortition's own winner: [4](#0-3) 

That write happens only inside `if let Some(sortition_state) = sortition_state`. On a fresh process (restart), `sortition_state: &mut Option<SortitionsView>` is `None` at the moment `capitulate_viewpoint` first runs in `process_event` (it runs before any block proposal is evaluated) [5](#0-4) . When the first `BlockProposal` for the reward cycle is then handled, `check_block_against_local_state` sees `sortition_state.is_none()` and calls `SortitionsView::fetch_view`, which builds `cur_sortition` fresh with `miner_status: Valid` and has no knowledge of the local state machine's already-updated `current_miner` viewpoint [6](#0-5) [7](#0-6) . `check_proposal` itself never cross-checks `proposed_by.state().data.miner_pkh` against `self.local_state_machine.current_miner`; the only channel that communicates that disagreement into the sortition view is the side effect above, which requires a pre-existing `SortitionsView` object to mutate. As a result, a proposal from the same sortition winner that the majority state machine had already deemed invalid (a mismatch neither caught by timeout nor by parent-tenure checks) can pass `check_proposal`'s `ProposedBy::CurrentSortition` status check (`sortition.miner_status != Valid`) [8](#0-7)  after the process restarts.

This gap is specific to the v1 / pre-global-signer-state-activation path (`check_block_against_local_state`, used when the fleet's negotiated protocol version has not reached `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`) [9](#0-8) . The v2 `GlobalStateView` path re-derives `current_miner` from `SignerStateMachine.current_miner` on every call rather than caching a separate invalidation flag, so it is not affected by this gap.

### Impact Explanation
This breaks the "fail-closed" equivocation guard for the restarting signer only: it can lose its previously-established local view that a particular sortition's miner is invalid and re-accept/pre-commit/sign a proposal from that miner. Since the attacker controls at most one signer's own weight and cannot force other signers to restart or race their own `capitulate_viewpoint`/`fetch_view` timing, this affects a single honest signer's vote at a time, not the aggregate 70% threshold. That matches the "High" category in the rubric ("a signer... losing the equivocation guard on restart") rather than "Critical," since a single signer's mis-vote does not by itself finalize an invalid block; it would need to coincide with enough other signers independently reaching (or having reached) the same restart-timing race to cross the acceptance threshold.

### Likelihood Explanation
Preconditions are narrow: (1) the fleet must be on the v1/local-state path (protocol version below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`), (2) the specific signer's `cur_sortition.miner_status` invalidation must have originated purely from the capitulation-mismatch path (not timeout or parent-tenure mismatch, both of which are safely re-derived), and (3) the signer process must restart/crash/upgrade exactly in the window between the state-machine's capitulation decision and a fresh `SortitionsView` being built for the next proposal from the same still-invalid miner. This is not attacker-triggerable directly (the attacker cannot force a signer's process restart), so exploitation is opportunistic and depends on operational timing outside attacker control, making it low-likelihood but real. The attacker's contribution is limited to crafting/broadcasting the block proposal that arrives during the restart window — cheap and repeatable, but the vulnerable window itself is not attacker-controlled.

### Recommendation
Persist the capitulation-derived invalidation (or its underlying cause — the disagreement between the local state machine's `current_miner_pkh` and `cur_sortition.data.miner_pkh`) in `SignerDb`, and have `SortitionsView::fetch_view`/`check_proposal` re-derive it from that persisted record and/or from the current `LocalStateMachine.current_miner` on every call, the same way timeout and parent-tenure invalidations are re-derived from persisted facts rather than cached only in the in-memory `SortitionState`.

    /// Fetch a new view of the recent sortitions
    pub fn fetch_view(
        config: ProposalEvalConfig,
        client: &StacksClient,
    ) -> Result<Self, ClientError> {
        let CurrentAndLastSortition {
            current_sortition,
            last_sortition,
        } = client.get_current_and_last_sortition()?;

        let cur_sortition = SortitionState::try_from(current_sortition)?;
        let last_sortition = last_sortition
            .map(SortitionState::try_from)
            .transpose()
            .ok()
            .flatten();

        Ok(Self {
            cur_sortition,
            last_sortition,
            config,
        })
    }
