## Answer

The exact bug described in the question — that a payout would be redirected to `beneficiary_for_operator(new_operator)` — does **not** occur. But the code has a related, verifiable flaw: after `switch_operator`, a pending commission distribution originally owed to the old operator bypasses the beneficiary lookup entirely and pays the *raw* old-operator address, rather than `beneficiary_for_operator(old_operator)`.

### How `distribute_internal` decides where to send funds

`distribute_internal` is invoked with the *current* operator key of the staking contract (i.e., whatever operator is currently registered), and it only redirects a payout to the beneficiary when the recipient recorded in the distribution pool equals that current operator parameter: [1](#0-0) 

```
895: // If the recipient is the operator, send the commission to the beneficiary instead.
896: if (recipient == operator) {
897:     recipient = beneficiary_for_operator(operator);
898: };
```

### What happens on `switch_operator`

`switch_operator` first force-distributes any already-inactive stake, then calls `request_commission_internal(old_operator, &mut staking_contract)`, which records a *pending distribution* keyed to `old_operator` inside `staking_contract.distribution_pool` via `add_distribution(operator, staking_contract, operator, commission_amount)` — using the **old** operator address as both the caller and the shareholder key: [2](#0-1) 

After that, the operator on the stake pool and in the `StakingContract`'s map key is switched to `new_operator`.

When `distribute` (an unprivileged, `public entry` function — anyone can call it) or `request_commission` is later called against the staking contract, it looks it up by the *current* key (`new_operator`) and calls `distribute_internal(staker, new_operator, staking_contract)`: [3](#0-2) 

Inside `distribute_internal`'s payout loop, the pending share recorded for `old_operator` is redeemed with `recipient == old_operator`, but it is compared against `operator == new_operator`. Since they don't match, the `if (recipient == operator)` branch is **skipped**, so `beneficiary_for_operator` is never consulted for that payout — the funds go straight to the raw `old_operator` address instead of `beneficiary_for_operator(old_operator)`.

This is directly confirmed by the existing framework test `test_staker_can_switch_operator`, where after `switch_operator`, the old operator's commission is paid straight to `operator_1_address` (not through any beneficiary lookup): [4](#0-3) 

```
1613: request_commission(operator_2, staker_address, operator_2_address);
...
1620: let operator_1_balance = coin::balance<AptosCoin>(operator_1_address);
1621: assert!(
1622:     operator_1_balance == INITIAL_BALANCE + commission_for_operator_1,
1623:     operator_1_balance
1624: );
```

Note that new commission accrued *after* the switch, under `new_operator`, is correctly redirected via `beneficiary_for_operator(new_operator)` because in that case `recipient == operator` (both equal `new_operator`).

### Why the specific claim in the question is not confirmed

The question's proof idea asserts the payout would go to `beneficiary_for_operator(new_operator)` instead of `beneficiary_for_operator(old_operator)`. Based on the code and the existing test, that specific redirection does not happen — the old-operator's pending commission is paid to the literal old-operator address, completely bypassing any beneficiary indirection (old or new). I was not able to find a test in the codebase that exercises `switch_operator` *after* a beneficiary has been set for the old operator (the `test_set_beneficiary_for_operator` test's tail past line ~1800 could not be fully retrieved from the index — some lines returned empty, likely due to indexing truncation), so I cannot conclusively state the exact balance outcome for that combined scenario from the index alone. However, the mechanics of `distribute_internal`'s `recipient == operator` check make it clear that whichever beneficiary is set for `old_operator` will **not** receive the payout once the operator key has changed — the raw `old_operator` address does, which is itself value-misdirection away from the intended beneficiary, distinct from the "wrong beneficiary" claim in the question.

### Assessment against review standard

This is an unprivileged-triggerable path (`distribute` and `request_commission` are `public entry`, callable by anyone) that produces a divergence between the intended beneficiary and the actual recipient of accrued commission for an operator that has been switched out. This is a real, root-caused deviation from the intended semantics of `beneficiary_for_operator`, but it is **not** the specific vulnerability alleged (i.e., it does not pay to `beneficiary_for_operator(new_operator)`) — it instead **fails to apply any beneficiary indirection** for the old operator's pending payout, sending funds to the bare address.

### Title
Old-operator commission distribution after `switch_operator` bypasses beneficiary indirection - (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` re-keys a `StakingContract` under the new operator while leaving a pending distribution entry keyed to the old operator's raw address in `distribution_pool`. Later, unprivileged calls to `distribute`/`request_commission` pass the *current* (new) operator into `distribute_internal`, so the `recipient == operator` beneficiary-redirection check fails for the old operator's entry, and the payout goes to the bare old-operator address instead of `beneficiary_for_operator(old_operator)`.

### Finding Description [5](#0-4)  only redirects to a beneficiary when the pool's shareholder key matches the operator parameter passed into `distribute_internal`, which is always the operator currently registered in the `Store`'s map key/`stake::get_operator`, not the operator who actually earned the commission being redeemed in that iteration.

### Impact Explanation
If an operator with a set beneficiary is switched out via `switch_operator`/`staking_proxy::set_staking_contract_operator`/`vesting::update_operator`, and there is unredeemed commission recorded for that operator at switch time, the eventual payout (triggered by anyone, including the unrelated caller of `distribute`) is sent to the raw old-operator address rather than its configured beneficiary, misrouting commission value away from the intended payee.

### Likelihood Explanation
Requires an operator switch with pending commission and a beneficiary set for the departing operator; both are supported, ordinary flows (used in vesting-backed staking contracts as well), and the triggering `distribute` call itself is unprivileged/permissionless.

### Recommendation
In `distribute_internal`, compare each shareholder against the actual commission-owner recorded per distribution entry (e.g., store/verify the operator address associated with each pending distribution) rather than against the staking contract's current operator, so beneficiary resolution always uses the operator who earned that specific commission.

### Proof of Concept
The existing unit test `test_staker_can_switch_operator` in `staking_contract.move` already demonstrates the mechanism: [4](#0-3)  shows `operator_1`'s post-switch commission paid to `operator_1_address` directly via a `request_commission` call scoped to `operator_2_address`, confirming the beneficiary-redirection check is evaluated against the wrong (new) operator address for stale distribution entries.
