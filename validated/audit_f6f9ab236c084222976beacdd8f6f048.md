### Title
Rebasing underlying breaks fixed-amount withdrawal receipts — recorded claims exceed actual vault balance after a negative rebase, and positive rebases are swept to feeReceiver - (File: contracts/IdleCDOEpochVariant.sol, contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The credit vault denominates every obligation (deposit minting, withdrawal receipts, expected epoch interest, borrower repayment) as a fixed amount of `token` recorded at the time of the transaction, but pays claims later out of the actual `token` balance held by `IdleCreditVault`. There is no shares/wrapper abstraction over the underlying. If `token` is a rebasing (elastic-supply) ERC20, the balance backing already-recorded claims changes without any transfer, so the accounting can no longer be honored.

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw` the user burns tranche tokens and a fixed `_underlyings` amount is registered with the vault via `creditVault.requestWithdraw(_underlyings, msg.sender, principal)`, which stores the claim in `withdrawsRequestsByEpoch` / per-user receipt state [1](#0-0) . The funds to honor those receipts are pulled from the borrower at `stopEpoch` (`collectWithdrawFunds`) and sit as raw `token` balance in `IdleCreditVault` until `claimWithdrawRequest` transfers the recorded amount.

Two failure modes mirror the OpenQ report exactly:

1. **Negative rebase (balance shrinks).** After the borrower repays and claims are funded, a downward rebase reduces `IERC20Detailed(token).balanceOf(vault)` below the sum of recorded receipts. Every claim still tries to `safeTransfer` its full recorded `_underlyings`; early claimers are paid in full and late claimers' transfers revert — identical to "the amount recorded when a deposit was made might not all be there when a refund is called." The invariant "one receipt, one payout" is broken with no trigger by any privileged actor.

2. **Positive rebase (balance grows) at the CDO layer.** Any raw `token` balance held by `IdleCDOEpochVariant` is treated as a donation: `_skimDonatedAssets` sweeps `balanceOf(this)` entirely to `feeReceiver`, and it is invoked on every entry point (`_deposit`, `depositDuringEpoch`, `requestWithdraw`, `startEpoch`, `finalizeDefault`, `updateAccounting`) [2](#0-1) . A positive rebase accruing to underlying temporarily held by the CDO is therefore redirected to `feeReceiver` instead of backing depositors — the vault deliberately cannot attribute rebase mints.

NAV itself is also balance-driven (`lastNAVAA/BB` are set from `_contractTokenBalance(strategyToken)`), but strategy tokens are minted/burned 1:1 against recorded underlying amounts, so they inherit the same mismatch.

### Impact Explanation
Insolvency / direct loss of user funds: with a rebasing underlying, recorded withdrawal receipts are no longer fully backed after a negative rebase between funding and claim (last claimers lose the rebase delta, potentially their full claim), and positive rebases on CDO-held underlying are confiscated to `feeReceiver`. No privileged misbehavior is required — the token contract itself performs the mint/burn. The loss equals the rebase delta applied to the funded-but-unclaimed balance, which can be arbitrarily close to 100% of pending claims for a token like AMPL during a contractionary epoch.

### Likelihood Explanation
`initialize` accepts any `_guardedToken` ERC20 with no rebasing check, and the protocol places no restriction on the underlying. Deployment intent is stablecoins (USDC), which lowers the practical likelihood, but nothing in code prevents a rebasing token from being configured, and fee-on-transfer/rebasing accounting was never designed in — claims are strictly `amount`-denominated while payouts are `balanceOf`-limited. Existing guards do not help: `_skimDonatedAssets` actively worsens the positive-rebase case, and the `Default` check in `stopEpoch` only compares expected vs actual repayment at one instant, not subsequent rebases of already-funded claims.

### Recommendation
Reject rebasing/elastic-supply tokens at initialization (e.g., verify `totalSupply`/`balanceOf` stability or maintain an allowlist), or wrap the underlying in a shares-denominated vault (like wstETH for stETH) so that all accounting is in non-rebasing units. If rebasing tokens must be supported, receipts should record a share of the funded pool rather than a fixed token amount, and `_skimDonatedAssets` must not sweep balances that back pending claims.

### Proof of Concept
Reproducible Foundry fork PoC (outline; exact claim mechanics in `IdleCreditVault` were partially verified — `requestWithdraw`/`collectWithdrawFunds`/`claimWithdrawRequest` entry points confirmed at `contracts/strategies/idle/IdleCreditVault.sol`):

```solidity
// Deploy IdleCDOEpochVariant with a rebasing mock ERC20 as `token`
// (MockRebasingToken: balanceOf can be scaled by setRebaseFactor).

function testRebaseInsolvency() public {
    // 1. Buffer phase: alice deposits 10_000e18 into AA.
    idleCDO.depositAA(10_000e18);

    // 2. Alice requests withdraw of full position; receipt records fixed
    //    _underlyings = 10_000e18 in IdleCreditVault.withdrawsRequestsByEpoch.
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 3. Manager starts epoch, runs it, borrower repays principal + interest;
    //    collectWithdrawFunds pulls 10_000e18 (+interest) of `token` into the vault.
    _startEpochAndCheckPrices(0);
    deal(address(token), borrower, owed);
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr, duration);

    // 4. ATTACK/TOKEN EVENT: negative rebase — vault balance shrinks 10%.
    token.rebase(address(strategy), 0.9e18); // balance now 9_000e18

    // 5. Alice (first claimer) still pulls her full recorded 10_000e18 claim,
    //    leaving the vault unable to pay bob's identical funded receipt.
    cdoEpoch.claimWithdrawRequest(); // alice succeeds
    vm.expectRevert();               // bob's claim: insufficient balance
    bobClaim();
}
```

The identical structure applies to `_skimDonatedAssets` sweeping a positive rebase: mint a positive rebase to `cdoEpoch` while it holds underlying between `requestWithdraw` funding and `claimWithdrawRequest`, then observe `feeReceiver` absorb it on the next user call [2](#0-1) .

Note: I was unable to fully read `IdleCreditVault`'s claim/collect function bodies in the available iterations; the PoC assumes claims transfer the full recorded receipt amount from the vault's token balance (consistent with `requestWithdraw(_underlyings, msg.sender, principal)` and the `collectWithdrawFunds` funding flow). If claims are instead pro-rata over the current balance, the negative-rebase branch weakens, but the `_skimDonatedAssets` positive-rebase confiscation stands independently.
