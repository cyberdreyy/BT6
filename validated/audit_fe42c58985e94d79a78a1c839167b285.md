### Title
Denial of Service via Front-Running Account Migration (PDA squatting) - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The `marginfi_account_transfer_to_new_account_pda` instruction derives the destination account address as a PDA seeded by a caller-supplied, unchecked `new_authority` pubkey plus a caller-chosen `account_index`/`third_party_id`. Because `new_authority` never has to sign and the resulting PDA is fully predictable from public transaction data, any unprivileged attacker can observe a pending migration transaction and front-run it with their own (cheap, attacker-controlled) "old account", claiming the exact same PDA address before the legitimate transaction lands. This causes the victim's `init` constraint to fail, denying the migration — the same bug class as the report's `loanId` front-running DoS in Folks Finance's `LoanManager`.

### Finding Description
`TransferToNewAccountPda` derives the new account address deterministically: [1](#0-0) 

The seeds are `[MARGINFI_ACCOUNT_SEED, group, new_authority, account_index, third_party_id]`, and `new_authority` is explicitly documented as unchecked: "WARN: New authority is completely unchecked" [2](#0-1) . Only the *old* account's `authority` must sign — `new_authority` is never required to sign or otherwise prove ownership of that key [3](#0-2) .

This differs from the plain `MarginfiAccountInitializePda` path, where the PDA seed's `authority` *must* sign the transaction [4](#0-3) , making front-running impossible there (an attacker cannot forge another user's signature). The migration path removes that protection: since `new_authority`, `account_index`, and `third_party_id` are all attacker-observable (they appear in the pending transaction) and none require a signature tying them to the real intended recipient, an attacker can submit a competing `TransferToNewAccountPda` instruction using their own throwaway `old_marginfi_account` (any account they control) but copying the victim's `new_authority`, `account_index`, and `third_party_id` values. If the attacker's transaction lands first, the PDA is created and the victim's `init` constraint on `new_marginfi_account` fails at account-validation time, before any of the check!/fee logic in `transfer_to_new_account_pda` executes [5](#0-4) .

This is the same root-cause pattern as the reported bug: a deterministic, permissionless, publicly-derivable identifier (there `loanId`, here the PDA seed tuple) that is claimed on a first-come basis without binding the claim to the actual intended owner's signature, letting anyone squat the identifier ahead of the legitimate user.

### Impact Explanation
The impact is griefing/DoS rather than fund theft: the victim's migration transaction reverts, so they do not lose the `ACCOUNT_TRANSFER_FEE` (charged after the account-validation phase, so `init` failing means the fee transfer instruction inside the handler is never reached), but they do lose the transaction fee and must retry with a different `account_index`/parameters. An attacker with no profit motive can repeatedly grief any specific victim's migration attempts by monitoring the mempool and resubmitting with higher priority, matching the "Griefing" impact category explicitly named in the reference report. It does not compromise funds or authorization directly, so it is a lower-severity denial-of-service issue rather than a fund-loss issue.

### Likelihood Explanation
Exploitation only requires: (1) an attacker-controlled cheap `old_marginfi_account` (trivial to create via `marginfi_account_initialize`), (2) visibility into the victim's pending `TransferToNewAccountPda` transaction (standard mempool monitoring), and (3) submitting a competing transaction with higher priority fee. No privileged role, no oracle manipulation, and no special timing beyond standard front-running is needed, so likelihood is moderate — bounded mainly by whether users' migration transactions are actually visible pre-confirmation and whether an attacker has reason to target a specific victim.

### Recommendation
Require `new_authority` to co-sign `TransferToNewAccountPda` (and non-PDA `TransferToNewAccount`), or otherwise cryptographically bind the claim to the intended recipient (e.g., a signed message/nonce from `new_authority`) before allowing `init` of the destination account. Alternatively, allow the old account authority to reserve/pre-register the destination PDA in the same transaction that also verifies `new_authority`'s consent, closing the front-runnable window entirely.

### Proof of Concept
1. Alice calls `marginfi_account_transfer_to_new_account_pda` with `old_marginfi_account = AliceOld`, `new_authority = NA` (a fresh pubkey she controls), `account_index = 0`, `third_party_id = None`. This is broadcast and visible in the mempool/leader schedule before confirmation.
2. Bob (attacker), who has a cheap throwaway account `BobOld` (created via `marginfi_account_initialize`), observes Alice's pending transaction and extracts `group`, `new_authority = NA`, `account_index = 0`, `third_party_id = None`.
3. Bob immediately submits his own `marginfi_account_transfer_to_new_account_pda` with `old_marginfi_account = BobOld`, `authority = Bob` (self-signed, valid), `new_authority = NA` (copied, no signature required), `account_index = 0`, `third_party_id = None`, with a higher priority fee.
4. Bob's transaction lands first, creating the PDA at `derive_pda(group, NA, 0, None)`.
5. Alice's transaction now fails the `init` constraint on `new_marginfi_account` because the account already exists, per the `#[account(init, ...)]` constraint [6](#0-5) , denying her intended migration.
