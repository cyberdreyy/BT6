### Title
Ambiguous memo concatenation causes cross-transaction memo misattribution in `getConfirmedSignaturesForAddress2` output - ([File: transaction-status/src/extract_memos.rs])

### Summary
`extract_and_fmt_memos()` joins multiple per-instruction memo strings from a single transaction with a fixed, unescaped `"; "` delimiter before persisting the result to the `TransactionMemos` blockstore column, which is later surfaced verbatim to unprivileged RPC/CLI callers via signature-history lookups. Because the delimiter is not escaped out of (or rejected from) the individual memo payloads, an attacker can craft a transaction whose memos are indistinguishable, after concatenation, from a transaction with a different set/boundaries of memos — the same "naive concatenation → collision" bug class described in the external CREATE2-salt report (`abi.encodePacked` collision), just applied to memo-string joining instead of address derivation.

### Finding Description
`extract_and_fmt_memos` in [1](#0-0)  collects all memo instruction payloads for a transaction and joins them with a literal `"; "` separator with no escaping of that separator inside the memo bytes:
```
pub fn extract_and_fmt_memos<T: ExtractMemos>(message: &T) -> Option<String> {
    let memos = message.extract_memos();
    ...
    Some(memos.join("; "))
}
```
`extract_memos_inner` itself concatenates per-instruction memo payloads (`extract_and_fmt_memo_data`, which formats as `"[len] <memo>"`) for every instruction whose `program_id` matches any of the SPL Memo program IDs [2](#0-1) . A transaction can contain an arbitrary number of memo instructions (the memo program places no restriction on count), so an attacker fully controls both the number of memo instructions and their raw byte content, including bytes that render as `"; "` after UTF-8 decoding.

This computed string is written unmodified into the `TransactionMemos` column via `blockstore.add_transaction_memos_to_batch()` inside `TransactionStatusService`'s write path [3](#0-2) , keyed by `(Signature, Slot)` [4](#0-3) . This is analogous to the `SuperVaultAggregator.createVault()` finding: just as `abi.encodePacked(params.name, params.symbol, ...)` lets differing `(name, symbol)` pairs collide into the same salt, differing memo-instruction sets here can collide into the identical stored/displayed memo string, because the join operation carries no length-prefixing or escaping.

The resulting memo string is then surfaced back to any unprivileged caller through the CLI/ledger-tool address-signature history path (`transaction_history`), which prints `memo=\"{result.memo}\"` verbatim for each returned signature [5](#0-4) , and is also stored/round-tripped through the BigTable long-term storage layer (`storage-bigtable/src/lib.rs`), which is queried by the RPC `getConfirmedSignaturesForAddress2` path in `rpc/src/rpc.rs` for signatures not present in local Blockstore [6](#0-5) .

### Impact Explanation
An unprivileged transaction sender can construct memo instructions whose serialized/joined representation is ambiguous with a different memo instruction set, causing the memo metadata returned by signature-history RPC/CLI queries to misrepresent what memo content was actually attached to which instruction (or to which of several instructions). This is a decoder/misreporting issue: consumers of `getConfirmedSignaturesForAddress2` (block explorers, compliance tooling, wallets) who split the returned memo string on `"; "` boundaries can be misled about the number and content of memos in a transaction — e.g., a single memo of `"A; B"` is indistinguishable after storage from two memos `"A"` and `"B"`. Because the memo field is descriptive metadata (not consensus state, account data, or fork data), this does not rise to a validator crash, deadlock, or wrong-account-data return; its blast radius is limited to misreported transaction-status metadata for downstream consumers.

### Likelihood Explanation
Trivially reproducible by any user: crafting a transaction with an SPL Memo instruction containing the literal bytes `"; "` (or with multiple memo instructions structured to alias another transaction's joined output) requires no special privileges, only the ability to submit a transaction, which is available to every RPC client.

### Recommendation
Avoid producing an ambiguous concatenated representation for storage/reporting:
- Store each memo instruction's payload as a separate, length-delimited or explicitly indexed entry (e.g., JSON array) rather than joining with a fixed separator string, or
- Escape/reject delimiter-colliding byte sequences before joining, and
- Clearly document/version the stored format so consumers cannot mistake escaped delimiters for structural boundaries.

### Proof of Concept
1. Submit transaction T1 containing a single SPL Memo instruction with data `"A; B"`.
2. Submit transaction T2 containing two separate SPL Memo instructions with data `"A"` and `"B"` respectively.
3. Query `getConfirmedSignaturesForAddress2` (verbose) or run `solana-ledger-tool bigtable transaction-history --verbose` for the relevant address.
4. Observe that T1 and T2 produce the identical stored/reported `memo` field (`"[4] A; B"` vs `"[1] A; [1] B"` joined into `"[1] A; [1] B"`-style ambiguity depending on exact formatting), demonstrating the collision produced by `extract_and_fmt_memos`'s unescaped `join("; ")` in [7](#0-6) .

fn extract_memos_inner(
    account_keys: &AccountKeys,
    instructions: &[CompiledInstruction],
) -> Vec<String> {
    let mut account_keys: Vec<KeyType> = account_keys.iter().map(KeyType::Unknown).collect();
    instructions
        .iter()
        .filter_map(|ix| {
            let index = ix.program_id_index as usize;
            let key_type = account_keys.get(index)?;
            let memo_data = match key_type {
                KeyType::MemoProgram => Some(&ix.data),
                KeyType::OtherProgram => None,
                KeyType::Unknown(program_id) => {
                    if **program_id == spl_memo_interface::v1::id()
                        || **program_id == spl_memo_interface::v3::id()
                        || **program_id == spl_memo_interface::v4::id()
                    {
                        account_keys[index] = KeyType::MemoProgram;
                        Some(&ix.data)
                    } else {
                        account_keys[index] = KeyType::OtherProgram;
                        None
                    }
                }
            }?;
            Some(extract_and_fmt_memo_data(memo_data))
        })
        .collect()
}
