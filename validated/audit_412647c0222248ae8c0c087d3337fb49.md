### Title
`claimInstantWithdrawRequest` never clears the per-epoch receipt markers, corrupting defaulted-epoch claims and freezing later payouts - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.requestInstantWithdraw` records each instant-withdraw receipt under three bookkeeping entries: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. The funded claim path `claimInstantWithdrawRequest` zeroes only the aggregate (`instantWithdrawsRequests[_user] = 0`) and never clears the per-epoch entries. This is the direct analog of the CSXTrade bug class: a trade/claim-terminating function forgets to remove an identifier marker, so a later cleanup pass (`_claimDefaultedInstantWithdrawRequest`) treats the already-settled receipt as still pending.

### Finding Description
- `requestInstantWithdraw` writes `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` at `IdleCreditVault.sol:371-372`.
- `claimInstantWithdrawRequest` at `IdleCreditVault.sol:380-393` burns the receipt and clears `instantWithdrawsRequests[_user]`, but leaves `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` permanently set.
- If the borrower then defaults on that same epoch, `defaultRecoveryEpoch` equals the stale epoch. After `finalizeDefaultRecovery`, `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`) reads the stale `claimBasis`, executes `instantWithdrawsRequests[_user] -= claimBasis` (underflow on the zeroed aggregate → revert), decrements `instantWithdrawClaimsByEpoch[defaultEpoch]` and `pendingInstantWithdraws` for an already-paid claim, then attempts `_burn(_user, claimBasis)` on receipt tokens that were already burned.
- The whole `claimInstantWithdrawRequest` therefore reverts for any user holding other legitimate receipts (older funded instant receipts are claimed in the same call after `_claimDefaultedInstantWithdrawRequest`), and the recovery-accounting aggregates are inflated by the stale basis.

### Impact Explanation
Two direct consequences, both with fund impact:
1. **Permanent freezing of unclaimed yield**: a user who claimed an instant withdrawal during epoch N and holds any other pending/funded receipt can never call `claimInstantWithdrawRequest` again once epoch N is finalized as defaulted — `_claimDefaultedInstantWithdrawRequest` always reverts on `instantWithdrawsRequests[_user] -= claimBasis` (0 − stale > 0). Same pattern applies to `_claimDefaultedWithdrawRequest` if the corresponding stale normal-path entries are hit (`withdrawsRequests[_user] -= normalAmount` underflow in `_clearWithdrawClaimForEpoch`, `IdleCreditVault.sol:819`), since `_claimFundedWithdrawRequest` also clears only the aggregate (`withdrawsRequests[_user] = 0`, line 344) and never `withdrawsRequestsByEpoch`.
2. **Recovery mispricing / insolvency**: `instantWithdrawClaimsByEpoch[defaultEpoch]` remains inflated by already-paid claims, so the default-finalization reserve accounting double-counts settled receipts — the isolated `defaultRecoveryReserve` is mis-sized, stealing from or short-changing real default claimants.

### Likelihood Explanation
Requires a borrower default in the same epoch in which a user both requested and successfully claimed a funded instant withdrawal. That is a normal, unprivileged sequence: request during the running epoch, claim after `instantWithdrawDelay` inside the same epoch, borrower defaults at `stopEpoch`. The attacker/victim needs only KYC'd-lender-level access; no privileged role misbehaves. Existing guards (`_onlyIdleCDO`, default gating, epoch checks) do not prevent it — the bug is exactly a missing cleanup step, not a missing guard.

### Recommendation
In `claimInstantWithdrawRequest`, before zeroing the aggregate, iterate/clear the user's per-epoch entries (`instantWithdrawsRequestsByEpoch[_user][*]`) and decrement `instantWithdrawClaimsByEpoch[epoch]` for each cleared epoch — i.e. add a `_clearInstantReceiptMarkers(_user)` helper, exactly mirroring the CSX `_rmvAId()` fix. Apply the same fix in `_claimFundedWithdrawRequest` for `withdrawsRequestsByEpoch` (and verify `postDefaultRequests`/APR0 paths clear their per-epoch markers too).

### Proof of Concept
Foundry fork PoC sketch (mode: instant-withdraw enabled, then borrower default):

```solidity
function testStaleInstantReceiptBlocksPostDefaultClaim() external {
    _setFeeParams(feeReceiver, 0, FULL_ALLOC, 0);
    uint256 mintedAA = idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);            // epoch N running

    // enable instant withdrawals with a short delay
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    uint256 requested = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
    skip(101);
    cdoEpoch.claimInstantWithdrawRequest();  // funded claim: aggregate cleared, per-epoch entry stays
    assertEq(strategy.instantWithdrawsRequests(address(this)), 0);
    // stale marker remains:
    assertGt(strategy.instantWithdrawsRequestsByEpoch(address(this), strategy.epochNumber()), 0);

    // make another (normal) withdraw request that must be claimable later
    uint256 requested2 = cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));

    // borrower defaults at end of epoch N
    _warpToEpochEnd();
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, /* loss triggers default */ type(uint256).max);
    strategy.finalizeDefaultRecovery();      // or equivalent finalization path

    // user can never claim anything again: defaulted-path underflows on stale basis
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();
    // legitimate funded receipt `requested2` value is frozen
}
```

Uncertainty: the exact revert point depends on whether `instantWithdrawsRequests[_user] -= claimBasis` or the earlier `_burn` fires first; both revert. A variant PoC where the user still holds receipt balance demonstrates the recovery-reserve double-count instead of the DoS.
