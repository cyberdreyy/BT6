## Analysis: Unsigned fields in `BlockRejection` — analog to "Enum not present in EIP-712"

The Hats/Palmera finding is about an `Enum.Operation` field being included in a message that gets signed, but not actually being part of the type that is hashed for the EIP-712 signature — so the signature silently fails to commit to that field, breaking the intended data-integrity guarantee of "what is signed is what is validated."

The direct analog in this codebase is in the structured-data signature scheme used by `BlockRejection`.

### Root cause

`BlockRejection::hash()` computes the signed digest as: [1](#0-0) 

This only feeds `self.signer_signature_hash` (as a raw buffer) and a domain tuple (`name`, `version`, `chain_id`) into `structured_data_message_hash`. However, the full `BlockRejection` struct that is serialized, gossiped, and consumed by other signers/the node contains several additional semantically important fields that are **not** part of this hash: [2](#0-1) 

Specifically `reason` (free-form string), `reason_code` (the `RejectCode` enum, itself wrapping `ValidateRejectCode`), and the entire `response_data: BlockResponseData` (which carries `reject_reason: RejectReason`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`, etc.) are excluded from `hash()`.

`verify()` / `recover_public_key()` both simply recompute this same incomplete `hash()`: [3](#0-2) 

Compare this to `BlockAccepted`, where the signed payload is `signer_signature_hash().bits()` directly over the block itself — narrower in scope, but at least it's exactly what's being attested to. For `BlockRejection`, the struct implies (via its serialized shape, and via test helpers keying off `reject_reason` alongside `signature`, e.g. `wait_for_block_global_rejection_with_reject_reason`) that the rejection's reason and metadata are meant to be an authenticated part of a signer's on-the-wire statement, but the cryptographic commitment doesn't cover them.

### Reachability / impact

Both `BlockResponse::Accepted` and `BlockResponse::Rejected` variants share `get_tenure_extend_timestamp()`: [4](#0-3) 

meaning `response_data.tenure_extend_timestamp` from a *rejection* message is consumed the same way as from an acceptance — feeding into node/miner tenure-idle-extension logic (as seen for the `Accepted` case being consumed in `stackerdb_listener.rs`): [5](#0-4) 

Because `response_data` (and `reason_code`/`reason`) are not covered by the signature, any single relaying party — a miner, a gossiping node, or a compromised StackerDB replica, no majority or private key needed — can take a legitimately signed `BlockRejection` and rewrite its `reason_code`, `reason`, `reject_reason`, or `tenure_extend_timestamp`/`tenure_extend_read_count_timestamp` fields while leaving `signature` and `signer_signature_hash` untouched. `verify()` will still return `true` for the tampered message, since it only re-derives the hash from the still-unmodified `signer_signature_hash`.

This lets an attacker forge the *reason* a signer supposedly gave for rejecting a block, and/or forge the tenure-idle-extension timestamp attributed to that signer — both of which downstream consumers (signers tallying rejection reasons, and the miner's tenure-extend timing logic) may treat as an authenticated statement from that signer. This is a liveness-relevant tampering primitive: forged `tenure_extend_timestamp`/`tenure_extend_read_count_timestamp` values could distort the miner's idle-tenure-extension decisions built from (falsely) signer-attributed data, and forged `reject_reason`/`reason_code` values could mislead any logic keyed on why a block was rejected.

### What I could not fully verify

I was not able to complete tracing every downstream consumer of `BlockRejection.response_data`/`reason_code` on both the node side (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`, rejected-branch handling was cut off in my view) and inside `stacks-signer/src/v0/signer.rs`'s ~60 references to `reject_reason`/`reason_code` before running out of tool budget, so I cannot give an exhaustive list of every place a forged, unauthenticated `reject_reason`/`tenure_extend_timestamp` could produce a concrete state-machine wedge — only that the field is used symmetrically with the (verified) acceptance path via `get_tenure_extend_timestamp()`, and that `reject_reason` is treated by tests/helpers as meaningful signer-attributed data. A full assessment of exact severity (e.g., whether it can force a specific liveness wedge, as opposed to just misleading logging/heuristics) would require a deeper read of those call sites, ideally in a full Devin session with complete file access.

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
