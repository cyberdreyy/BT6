### Title
Panic on Deposit-Transaction Fee-Accounting Overflow Halts the Chain - (File: `crates/common/evm/src/handler.rs`)

### Summary
`BaseHandler::validate_against_state_and_deduct_caller` in `crates/common/evm/src/handler.rs` calls `.expect("Deposit transaction effective balance spending overflow")` on the result of `tx.effective_balance_spending(basefee, blob_price)` when processing an L2 deposit transaction. `.expect()` on `None` panics the process, and this code runs during ordinary block execution/derivation — the same "any panic in per-block accounting halts the chain" bug class described in the Babylon advisory (an unchecked overflow inside a mandatory per-block calculation causes `EndBlocker`/block-processing panic). [1](#0-0) 

### Finding Description
When a transaction is a deposit (`tx.tx_type() == DEPOSIT_TRANSACTION_TYPE`), the handler computes the effective balance spending and immediately unwraps it with `.expect(...)` instead of propagating an error: [2](#0-1) 

This mirrors exactly the bug class in the reported advisory: a per-block/per-transaction arithmetic computation that is expected to "never overflow" is unwound with an unwrap/expect rather than checked arithmetic, so that if the precondition is ever violated, the node process panics rather than rejecting the single transaction. In Babylon's case this was reachable by minting large token amounts via IBC and depositing them into the validator rewards pool, corrupting a `cumulative_reward_ratio` calculation inside `EndBlocker`. In Base, the analogous mandatory per-block hook is transaction execution itself (every deposit runs through this exact code path in the block-building/derivation pipeline), and the value/mint fields feeding this arithmetic originate from L1 `TransactionDeposited` events, which are attacker-observable/attacker-influenced inputs decoded and consumed via `Deposits::decode`/`unmarshal_v0` and fed into `TxDeposit` (`mint: u128`, `value: U256`). [3](#0-2) 

Elsewhere in the same handler and in the newer `evm2` deposit path, the same class of computation is deliberately implemented with `saturating_add`/`saturating_sub` or `checked_*` + typed errors (e.g. `new_balance` a few lines below the panic site, and the EIP-8130 fee-settlement code in `crates/common/evm/src/eip8130.rs`, which uses `checked_mul`/`checked_add` and returns a `BaseTransactionError` rather than panicking): [4](#0-3) 

The `.expect()` call at line 121 is the outlier: rather than returning a `Result`/typed error like every neighboring arithmetic path, it converts an overflow condition into a hard panic.

### Impact Explanation
If `effective_balance_spending` can return `None` for any reachable combination of `basefee`, `blob_price`, and deposit `gas_limit`/`gas_price` fields (all of which are ultimately derived from L1-observed data decoded from the `TransactionDeposited` log and are not re-validated for "cannot overflow" invariants at this call site), then a single crafted L1 deposit would cause every L2 node executing that block (sequencer, verifier, replica) to panic during block execution — a full network Denial-of-Service / chain halt, identical in class and severity to the Babylon `EndBlocker` panic (CWE-190/CWE-770, "Node halt" impact in the validation criteria). Because it's `checked_sub`/`checked_add`-free, and immediately followed by `- tx.value()` without any accompanying check that `effective_balance_spending() >= tx.value()`, this line also risks a second (subtraction) panic/underflow in debug builds independent of the `.expect()`.

### Likelihood Explanation
Deposit transactions are constructed by the derivation pipeline directly from L1 log data (`Deposits::decode`) with attacker-controlled `mint`, `value`, and `gas_limit` fields (bounded only by the opaque-data decode logic, not by "no overflow" arithmetic invariants). Whether the specific `effective_balance_spending` computation is practically reachable at `U256`/`u128` boundary conditions could not be fully confirmed from the indexed code (the `effective_balance_spending` trait method itself is defined in the external `revm` crate and was not present in the indexed sources), so the exact overflow trigger conditions are unverified. However, the pattern — panicking (`.expect`) on a value derived from externally-supplied deposit fields inside the block-execution path — is the same reachable bug class as the reported advisory and is the only such panic-on-overflow call site found in this handler.

### Recommendation
Replace the `.expect("Deposit transaction effective balance spending overflow")` with a checked path that returns a transaction-level error (consistent with every other arithmetic operation in this function and with the `eip8130.rs` pattern), and, if overflow at the individual deposit level is not something L2 consensus can reject (deposits "can't fail" per the OP-Stack spec), route it through the same failed-deposit fallback used by `handle_deposit`/`catch_error` in `crates/common/evm2/src/registry.rs` rather than panicking the process. Additionally verify (upstream in `revm`) exactly which field combinations can produce `None` from `effective_balance_spending` for a `DEPOSIT_TRANSACTION_TYPE` transaction, and add a `checked_sub` guard before `- tx.value()`.

### Proof of Concept
Concrete reproduction was not verified against actual `revm` `effective_balance_spending` semantics because that trait method's implementation is in the external `revm` dependency, not in this repository's indexed sources — this could not be confirmed with certainty. Conceptually: an attacker deposits via `OptimismPortal`/`TransactionDeposited` on L1 with `mint`/`value`/`gas_limit` fields chosen so that `effective_balance_spending(basefee, blob_price)` internally overflows (e.g. extreme `gas_limit`/`gas_price` combined with maximal `blob_price`), producing `None`; when the L2 derivation pipeline decodes and executes this deposit via `handle_deposit` → `validate_against_state_and_deduct_caller`, the `.expect(...)` fires and panics every node executing the block.
