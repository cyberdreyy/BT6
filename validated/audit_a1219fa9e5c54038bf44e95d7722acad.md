### Title
Rejected-signer weight is never retracted, letting a later legitimate `Accepted` response desynchronize `total_weight_rejected`/`total_weight_approved` and trigger a false `SignersRejected` outcome - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` tallies signer weight for a proposed block by watching `BlockResponse::Accepted`/`BlockResponse::Rejected` messages coming from StackerDB. The "already counted" guard used for the `Accepted` branch is keyed on `gathered_signatures` (a per-signer signature map), while the guard for the `Rejected` branch is keyed on the disjoint set `responded_signers`. Because a single signer's rejection weight is *never removed* once counted, and the acceptance branch does not check whether that same signer already contributed weight to the rejected tally, a signer that first sends `Rejected` and later legitimately sends `Accepted` for the exact same `signer_signature_hash` ends up double-counted: its weight remains permanently baked into `total_weight_rejected` **and** is separately added to `total_weight_approved`.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- On `Accepted`, weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`: [1](#0-0) 
- On `Rejected`, weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` (i.e., first time seen at all): [2](#0-1) 

There is no code path that removes a signer's weight from `total_weight_rejected` if that signer subsequently sends an `Accepted` response for the same block, nor any check in the `Accepted` branch that inspects whether the sender already contributed to `total_weight_rejected`. The `Accepted` branch's own dedup key (`gathered_signatures`) is independent from the `Rejected` branch's key (`responded_signers`), so the same signer's weight can legitimately land in both totals simultaneously.

This is not a theoretical case: the documented signer decision flow explicitly allows a signer to change its answer for a re-evaluated/re-proposed block once the reason for rejection "has since gone away": [3](#0-2) 

The coordinator (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) checks the (now-desynchronized) `total_weight_rejected` **before** checking `total_weight_approved`: [4](#0-3) 

Because the rejected tally can be inflated by weight from a signer who has since switched to `Accepted`, `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can become true (crossing the >30% blocking-minority line) purely due to stale/duplicated weight, even though the *distinct* signer weight currently rejecting the block never actually reached that level. This breaks the intended equality that "aggregated rejected weight" reflects the current, verified, non-overlapping set of rejecting signers.

### Impact Explanation
This is a liveness wedge/miscount on the miner-coordination path: the block can be forced into the `SignersRejected` branch (miner discards proposal, excludes txids, re-proposes) even though a sufficient/valid weight of signers has actually accepted or would accept the block, because one or more signers' stale rejection weight is never retracted after they change their vote to accept. This does not require a majority of malicious signers — a single signer legitimately reconsidering its vote (a documented, intended behavior) is enough to permanently pollute the rejected tally for that block hash. The result matches the "aggregated-weight vs verified-accepts" equality-break category and a state-machine liveness wedge (miner repeatedly treats a signable block as globally rejected, forcing unnecessary re-proposals / possible txid exclusion side effects).

### Likelihood Explanation
Reachable by a single ordinary signer's normal vote-revision behavior (reject → later accept for the same block, as explicitly anticipated by the documented signer decision flow) combined with gossip of both messages over StackerDB — no majority collusion, no other signer's key, and no consensus-acceptance change is required. The desync is purely an accounting bug in the node's tally bookkeeping.

### Recommendation
Make the two weight tallies mutually aware of each other:
- Track, per signer, a single canonical "last decision" (accept/reject) with its weight, and recompute `total_weight_approved`/`total_weight_rejected` from that canonical map rather than from two independently-guarded structures (`gathered_signatures` vs `responded_signers`).
- When a signer transitions from `Rejected` to `Accepted` (or vice versa) for the same `signer_signature_hash`, subtract the previously counted weight from the old bucket before adding it to the new one, ensuring `total_weight_approved + total_weight_rejected` for any given block never exceeds the sum of weights of signers who have actually voted (each signer contributing weight to exactly one bucket at a time).

### Proof of Concept
1. Signer A (weight `w`) initially sends `BlockResponse::Rejected` for block hash `H` (e.g., due to a transient chainstate mismatch). `stackerdb_listener.rs` records `responded_signers.insert(slot_A)` and adds `w` to `total_weight_rejected`. [2](#0-1) 
2. The reason for A's rejection resolves (per the documented signer behavior of re-evaluating a re-proposed block), and A subsequently sends `BlockResponse::Accepted` for the same `H`. Since `gathered_signatures` does not yet contain `slot_A`, its weight `w` is *also* added to `total_weight_approved`. [1](#0-0) 
3. `total_weight_rejected` still includes A's `w` (never retracted). If other signers' rejections push `total_weight_rejected + weight_threshold > total_weight`, the coordinator triggers `NakamotoNodeError::SignersRejected` even though A (and possibly enough other signers) has actually accepted the block. [5](#0-4)
