### Title
Tranche APR split ratio / performance fee applied retroactively to uncrystallized interest - ([File: contracts/IdleCDO.sol])

### Summary
`IdleCDO` splits all interest accrued since the last accounting update using the *current* `trancheAPRSplitRatio` and `fee`, but the owner setters `setTrancheAPRSplitRatio` and `setFee`/`setFeeParams` change those parameters without first crystallizing the pending gain via `_updateAccounting()`. As a result, yield that accrued under the old ratio/fee is distributed under the new one, misallocating funds between AA and BB tranche holders (or between LPs and the fee recipient). This is the exact analog of the ZeroLend M-9 bug: a globally changeable parameter is applied inconsistently — interest accrual is implicitly bound to the value at the last update, while distribution uses the freshly set value.

### Finding Description
In `IdleCDO._updateAccounting` (and the credit-vault variant `IdleCDOCreditVault._updateAccounting`), the NAV gain since the last deposit/withdraw/harvest is split between tranches at the *currently stored* `trancheAPRSplitRatio`, and the performance fee is charged at the *currently stored* `fee`:

- `unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;` (`IdleCDO.sol:281`, `IdleCDOCreditVault.sol:231`)
- `_virtualPriceAux(...)` splits `totalGain` with `_trancheAPRSplitRatio` (`IdleCDOCreditVault.sol:326`, `IdleCDOLeveregedEulerVariant.sol:163`)

The relevant setters do not checkpoint pending yield:

- `setTrancheAPRSplitRatio` in `IdleCDO.sol:900-903` writes the new ratio directly with no `_updateAccounting()` call — unlike `setFeeParams` in `IdleCDOCreditVault.sol:461-470`, which correctly calls `_accrueManagementFee()` before mutating `managementFee`, showing the checkpointing pattern exists but is not applied to `fee` or `trancheAPRSplitRatio`.

Concretely: interest accrues between accounting updates at rate determined by the market. When the owner later calls `setTrancheAPRSplitRatio`, the entire accrued-but-unsplit gain is re-split at the *new* ratio the next time `_updateAccounting()` runs. If the ratio for AA is raised, AA tranche holders capture yield that economically accrued under a lower ratio — a direct transfer from BB holders (and vice versa). Likewise, raising `fee` via `setFee`/`setFeeParams` without a prior accounting update retroactively charges the new performance fee on gains that accrued under the old fee, transferring LP yield to `feeReceiver`.

The ZeroLend report maps cleanly: `reserveFactor` ≡ `trancheAPRSplitRatio`/`fee`; `_updateIndexes` using the stale rate ≡ interest accruing under the pre-change economics; `_accrueToTreasury` using the new value ≡ the next `_updateAccounting()`/`_virtualPriceAux` splitting the stale gain at the new parameter. Their recommended fix (store `lastReserveFactor`, or force `syncIndexesState` before the change — the Aave v3.1 fix cited in the report) is exactly "checkpoint accounting before mutating the parameter."

### Impact Explanation
Tranche holders (unprivileged lenders) suffer a direct redistribution of yield. In an epoch-based credit vault with large NAV and infrequent accounting (accounting only runs on deposit/withdraw/stopEpoch), a large amount of interest can be pending; changing the split ratio or fee mid-accrual shifts that entire pending gain, not just future yield. Example: AA NAV 900k, BB NAV 100k, pending gain 10k accrued at `trancheAPRSplitRatio = 50%`; owner raises ratio to 90%. Next `_updateAccounting` credits AA `10k * 90% = 9k` instead of the `5k` earned under the old ratio — a ~4k transfer from BB to AA, i.e., ~4% of BB NAV lost on a single honest admin call. With `fee`, the same retroactive skim transfers LP yield to `feeReceiver`/`owner`. Losses are quantifiable and not bounded by rounding.

### Likelihood Explanation
`trancheAPRSplitRatio`, `fee`, and `feeSplit` are intended to be tunable over a vault's lifetime, and `_updateAccounting` only runs on user interactions, so pending-gain windows of hours–days are normal in the epoch-based vault. Every honest change of these parameters with pending yield misallocates funds deterministically — no admin mistake beyond calling the function is required (the function itself is incomplete, matching the ZeroLend judge's reasoning that this is broken functionality, not admin error). Severity is bounded by the size of pending gain times the parameter delta, which is typically moderate rather than vault-draining, consistent with the source finding's Medium rating.

### Recommendation
Checkpoint accrued yield before changing either parameter, mirroring the existing `_accrueManagementFee()` pattern in `setFeeParams`:

```diff
// IdleCDO.sol
function setTrancheAPRSplitRatio(uint256 _trancheAPRSplitRatio) external virtual {
  _checkOnlyOwner();
+ _updateAccounting();
  _checkAmountTooHigh((trancheAPRSplitRatio = _trancheAPRSplitRatio) > FULL_ALLOC);
}
```

Similarly, ensure `setFee`/`setFeeParams` runs `_updateAccounting()` (or at least accrues `unclaimedFees` on the pending gain at the *old* `fee`) before overwriting `fee`, so performance fees are only charged on yield accruing after the change. Note `_updateAccounting` can revert `Default()` on deep losses; if that blocking behavior is undesirable for parameter updates, use the `_forceUpdateAccounting()` path instead.

### Proof of Concept
Foundry-style PoC against `IdleCDO`/`IdleCDOCreditVault` (adapt fixture from `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testRetroactiveSplitRatio() public {
    // Setup: AA = 900k, BB = 100k, trancheAPRSplitRatio = 50%
    idleCDO.depositAA(900_000 * ONE_SCALE);
    idleCDO.depositBB(100_000 * ONE_SCALE);

    // Accrue 10k of strategy yield (mock strategy price up / warp + interest)
    _accrueYield(10_000 * ONE_SCALE);

    // Honest owner raises AA split to 90% WITHOUT any user interaction first
    vm.prank(owner);
    idleCDO.setTrancheAPRSplitRatio(0.9e5); // 90% of FULL_ALLOC

    // Next accounting crystallizes the whole pending 10k at the NEW ratio
    vm.prank(owner);
    idleCDO.updateAccounting();

    // AA got 9k instead of the 5k earned under the 50% ratio in force during accrual
    assertApproxEqAbs(idleCDO.lastNAVAA(), 909_000 * ONE_SCALE, 1e18);
    // BB is short ~4k: lastNAVBB == 101k, should have been 105k
    assertApproxEqAbs(idleCDO.lastNAVBB(), 101_000 * ONE_SCALE, 1e18);
}
```

The same pattern with `setFee`/`setFeeParams` raising `fee` shows `unclaimedFees` inflated by `(newFee - oldFee) * pendingGain`, directly reducing `lastNAVAA + lastNAVBB` available to tranche holders. I was unable to fully verify whether `IdleCDOCreditVault` inherits `setTrancheAPRSplitRatio` or defines its own setter (grep indicated `trancheAPRSplitRatio` usage in that file but I could not read the setter before the iteration limit); the bug is confirmed in `IdleCDO.sol:900-903` and in the shared `_updateAccounting`/`_virtualPriceAux` logic the credit vault reimplements at `IdleCDOCreditVault.sol:222-249`.
