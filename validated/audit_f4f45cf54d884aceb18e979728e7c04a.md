### Title
A single dust APR=0 withdrawal request permanently bricks `stopEpoch` once APR is raised — `prepareStopEpochWithApr0` reverts on `unscaledApr != 0` while `apr0TotalPrincipal > 0` - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
Analogous to the Carousel rollover bug — where a user enlists under one `relayerFee` and the mint reverts after the fee is raised — in `IdleCreditVault` a user opens an APR0 withdrawal bucket while `unscaledApr == 0`, and `prepareStopEpochWithApr0` unconditionally reverts if the APR for the next epoch is any non-zero value while that bucket is open. An unprivileged lender can therefore force the vault to run only zero-APR epochs (or never settle), denying all depositors their yield.

### Finding Description
`IdleCDOEpochVariant.requestWithdraw` forwards to `IdleCreditVault.requestWithdraw`, which routes to the APR0 bucket when `unscaledApr == 0` (`IdleCreditVault.sol:285-286`, `_requestWithdrawApr0` at `:567-577`). Any tranche holder can create this state during a buffer period with a dust withdrawal: `_underlyings` just needs to be > 0 to pass the early return at `:246`.

At epoch end, `IdleCDOEpochVariant._stopEpoch` calls `_strategy.prepareStopEpochWithApr0(_interest)` (`IdleCDOEpochVariant.sol:362`), which does:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) return ...;
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```
(`IdleCreditVault.sol:499-508`)

There is no catch around this call in `_stopEpoch` — the revert propagates and `stopEpoch`/`stopEpochWithDuration` can never succeed while a non-zero APR is configured and an APR0 bucket is open. The bucket is only cleared inside `prepareStopEpochWithApr0` itself (`apr0TotalPrincipal = 0`, `:540`), which is unreachable when APR is non-zero. The only escape is the honest manager stopping the epoch with `newApr = 0` — at which point the attacker simply opens another dust APR0 request during the next buffer (withdraw requests are re-enabled after `stopEpoch`, `IdleCDOEpochVariant.sol:481-482`), re-arming the revert indefinitely.

### Impact Explanation
- **Permanent denial of yield**: the vault can never return to a non-zero APR while the attacker keeps a dust APR0 request open each cycle. All lenders' interest for every subsequent epoch is permanently lost.
- **Operational deadlock**: `stopEpoch`/`stopEpochWithDuration` revert with no error-handling path, so a manager attempting a normal APR raise repeatedly hits `NotAllowed`.
- The attacker's cost is one minimal deposit + one `requestWithdraw` per epoch — negligible gas, and the principal is fully recoverable via `claimWithdrawRequest` after the zero-APR epoch settles.

### Likelihood Explanation
Requires only a KYC-passing lender (explicitly an allowed attacker) with enough tranche tokens to produce `_underlyings > 0`. It triggers whenever the protocol wants to raise APR from 0 — a routine manager action — making the grief reliably exploitable in APR0 deployments. No privileged misbehavior needed; the manager is an honest actor whose legitimate `setAprs`/`stopEpoch(newApr, ...)` sequencing is what arms the revert.

### Recommendation
Re-validate or degrade gracefully at settlement time instead of reverting (mirroring the fix direction of the external report):
- If `unscaledApr != 0`, treat the pending APR0 principal as a normal withdraw receipt: move `apr0TotalPrincipal` into `withdrawsRequests`-equivalent accounting (or pay it at 0 rate) and clear the bucket, rather than reverting.
- Alternatively, block new APR0 requests once the manager signals a non-zero next-epoch APR (e.g., gate `_requestWithdrawApr0` on a `nextApr == 0` marker set at `stopEpoch`).

### Proof of Concept
Foundry fork test (based on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testApr0DustRequestBlocksAprRaise() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // APR0 vault
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // attacker deposits and requests a dust withdrawal while APR == 0
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);           // epoch settles at APR 0
    _forceLastEpochAprToZero();

    // attacker keeps APR0 bucket open with minimal request
    uint256 trancheReq = 1e12;          // dust but _underlyings > 0
    cdoEpoch.requestWithdraw(trancheReq, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // manager starts next epoch and (honestly) raises APR
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, 1e24);

    // any stopEpoch with non-zero APR reverts inside prepareStopEpochWithApr0
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(5e18, 5e18);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(manager);
    cdoEpoch.stopEpoch(5e18, 0);

    // only escape: stop with newApr = 0 -> attacker repeats request in next buffer,
    // permanently pinning the vault to APR 0 and denying all lender yield.
}
```

Key code paths: `IdleCreditVault.sol:285-286` (APR0 routing), `:567-577` (`_requestWithdrawApr0`), `:499-508` (unconditional revert), `IdleCDOEpochVariant.sol:362` (uncaught call site), `:481-482` (requests re-enabled each buffer for re-arming).
