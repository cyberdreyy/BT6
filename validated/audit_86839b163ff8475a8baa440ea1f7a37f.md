### Title
`get_transaction` with `commitment=confirmed` can return transaction data from a forked-out, non-rooted slot because the finalized-path check compares slot numbers instead of ancestor relationship - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_transaction` retrieves a transaction by signature from the blockstore and then decides whether to serve it based on either (a) the confirmed bank's `status_cache_ancestors()` containing the transaction's slot, or (b) the transaction's slot being numerically `<= highest_super_majority_root`. The second check is a bare numeric comparison and does not verify that the transaction's slot is actually an ancestor of the rooted chain, so a transaction whose slot forked out before finalization can still be returned as if it were on the canonical, finalized chain.

### Finding Description
In `get_transaction` [1](#0-0) , once `blockstore.get_complete_transaction(signature, highest_confirmed_slot)` returns a `ConfirmedTransactionWithStatusMeta` for slot `S` (populated for any processed slot up to `highest_confirmed_slot`, regardless of whether that slot ultimately becomes part of the canonical fork), the code performs two checks:

1. `commitment.is_confirmed() && confirmed_bank.status_cache_ancestors().contains(&confirmed_transaction.slot)` — this is ancestor-relation-aware since `status_cache_ancestors()` is derived from the confirmed bank's actual ancestor chain plus status-cache roots [2](#0-1) . If `S` has forked out, `S` is correctly excluded here.
2. `confirmed_transaction.slot <= highest_super_majority_root` [3](#0-2)  — this is a pure numeric comparison against the current root slot number, with no verification that `S` is an ancestor of the block at `highest_super_majority_root`. Since `highest_super_majority_root` only guarantees that the *chain leading up to that root* is finalized, a forked-out slot `S` with a numerically lower or equal slot number is not necessarily part of that chain, yet this check will still succeed and the code returns the transaction as if finalized.

By contrast, the analogous code path for `get_block` explicitly calls `self.check_blockstore_root(&result, slot)` [4](#0-3)  and relies on `blockstore.get_rooted_block`, which reads from blockstore's root-marked data structures rather than a raw slot-number comparison. `get_transaction`'s numeric fallback branch has no equivalent ancestry validation.

### Impact Explanation
This allows `getTransaction` with `commitment=confirmed` (or the default, since `confirmed` is the minimum for this RPC) to return transaction status/metadata for a transaction that landed in a slot that was later forked out and never became part of the canonical/rooted chain, as long as the numeric slot value happens to be `<= highest_super_majority_root`. This is a wrong-slot/fork data return: the client can be told a transaction succeeded (or observe its statusMeta) referencing an unrooted, non-canonical block, violating the invariant that finalized-looking answers must only be derived from rooted/ancestor slots. This matches the "wrong-slot/fork data returned" category in the bounty scope.

### Likelihood Explanation
Preconditions require a fork to occur naturally: a transaction lands in slot `S` (via a validator's normal block production), that slot is later abandoned in favor of a competing fork whose root slot number surpasses `S`, and the blockstore still retains blockstore-status data for the abandoned slot (which is retained until pruned/purged, and dead/forked slots are not always purged synchronously). The attacker only needs to submit a normal transaction and then issue a single `getTransaction` call after the fork resolves — no elevated privileges are required, satisfying the "one client, single call" constraint. Fork occurrences of this kind (competing blocks at overlapping slot ranges) are a normal, expected part of cluster operation, so the precondition is realistic, though the exact timing window (query must happen after `S` is superseded but blockstore retains the stale status entry) narrows practical exploitability somewhat.

### Recommendation
Replace the numeric comparison `confirmed_transaction.slot <= highest_super_majority_root` with an ancestor-relationship check equivalent to what `get_block` uses (e.g., verify via `blockstore.get_rooted_transaction`/root markers, or check that the transaction's slot is actually rooted in blockstore, not merely numerically less than or equal to the current root). Concretely, for the "finalized" fallback branch, only serve the transaction if `blockstore` confirms the slot is marked as a root (i.e., re-fetch via `get_rooted_transaction` or check `blockstore.is_root(slot)`) rather than trusting the pre-fetched `get_complete_transaction` result combined with a bare slot-number bound.

### Proof of Concept
Integration test plan (Rust, in `rpc/src/rpc.rs` test module or a ledger/runtime integration test):
1. Set up a `BankForks` + `Blockstore` test harness with two competing forks branching from a common parent bank at slot `N`.
2. Submit a transaction `tx` that is processed and recorded (via blockstore transaction-status writer) in slot `S` on fork A.
3. Advance and root fork B instead, such that `highest_super_majority_root` becomes some slot `R >= S` while `S` (fork A) is never an ancestor of the rooted chain (fork A is dropped/pruned from `BankForks` but blockstore retains its transaction-status entry).
4. Call `JsonRpcRequestProcessor::get_transaction(tx.signature, Some(RpcTransactionConfig { commitment: Some(CommitmentConfig::confirmed()), .. }))`.
5. Assert the result is `None` (transaction should not be reported as available/finalized since it is not on the canonical chain), or alternatively assert that if a non-`None` result is returned, `confirmed_transaction.slot` must be verified as an ancestor of `highest_super_majority_root`'s bank rather than merely `<= highest_super_majority_root`.
6. As currently implemented, the test would show `get_transaction` incorrectly returning `Some(...)` for the forked-out slot `S`, demonstrating the bug.

    pub fn status_cache_ancestors(&self) -> Vec<u64> {
        let (min, mut ancestors) = {
            let status_cache = self.status_cache.read().unwrap();
            let roots = status_cache.roots();
            let mut ancestors = Vec::with_capacity(roots.len() + self.ancestors.len());
            let mut min = Slot::MAX;
            for root in roots {
                ancestors.push(*root);
                min = min.min(*root);
            }
            (if roots.is_empty() { 0 } else { min }, ancestors)
        };

        ancestors.extend(self.ancestors.iter().filter(|ancestor| *ancestor >= min));
        ancestors.sort_unstable();
        ancestors.dedup();
        ancestors
    }
