### Title
External-initiator credentials satisfy `GetAuthenticatedUser` and bypass the "EIs not allowed" restriction on integer-ID job runs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` stores a synthesized `*clsessions.User{Role: UserRoleRun}` under the same `SessionUserKey` used for real session/token users, so `auth.GetAuthenticatedUser` cannot distinguish an EI-authenticated request from a genuine User. `PipelineRunsController.Create` relies on this exact check (`_, isUser := auth.GetAuthenticatedUser(c)`) to gate the integer-job-ID run path, which its own comment says is "EIs not allowed" — but the check silently passes for EI holders, defeating the intended restriction.

### Finding Description
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` authenticates a request purely from EI AccessKey/Secret headers and then does: [1](#0-0) 
This puts a fabricated `*clsessions.User` (Role `UserRoleRun`) into the same context key (`SessionUserKey`) that `AuthenticateBySession`/`AuthenticateByToken` use for real, DB-backed users: [2](#0-1) [3](#0-2) 

`PipelineRunsController.Create` (reached via `POST /v2/jobs/:ID/runs`) explicitly tries to restrict integer-ID job runs to genuine Users, with a comment stating EIs are not allowed to use this path: [4](#0-3) 

Because `AuthenticateExternalInitiator` populates `SessionUserKey` with a `*clsessions.User`, `auth.GetAuthenticatedUser(c)` returns `ok=true` for an EI-authenticated request exactly as it would for a real user — there is no way at the handler level to tell the two apart. The only field that differentiates them is `SessionExternalInitiatorKey`, which `Create` never checks. As a result, an attacker holding only EI AccessKey+Secret (no session, no API token, no `clsessions.User` record at all) can call `POST /v2/jobs/<int-ID>/runs` and successfully trigger `prc.App.RunJobV2`, contradicting the code's own stated intent ("only users are allowed to run jobs using int IDs - EIs not allowed").

### Impact Explanation
This is an identity-confusion/authorization-bypass bug: possession of EI credentials — meant only to trigger webhook-type job runs — is sufficient to invoke the general integer-ID job-run endpoint that the code intends to reserve for authenticated Users. This corresponds to Chainlink's "unauthorized job run" bounty impact class: EI credentials are used to reach run-role functionality (`prc.Create` → `RunJobV2`) that the code explicitly tries to exclude them from.

### Likelihood Explanation
Preconditions are minimal: only a valid EI AccessKey/Secret pair (an unprivileged, non-admin, non-session credential) is required. The exploit is a single unauthenticated-from-User-perspective HTTP request (`POST /v2/jobs/<numeric-ID>/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) and is fully repeatable against any job whose numeric ID the attacker knows or can enumerate.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests authenticated as an external initiator instead of relying on `auth.GetAuthenticatedUser`'s boolean result. Use `auth.GetAuthenticatedExternalInitiator(c)` to detect EI-based auth and return an error/forbidden response before allowing the integer-ID run path, e.g.:
```go
if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI {
    jsonAPIError(c, http.StatusUnauthorized, errors.New("external initiators cannot run jobs by ID"))
    return
}
```
More broadly, avoid overloading `SessionUserKey` with a synthetic `User` for EI principals; instead expose a distinct, explicit "principal type" so all downstream handlers can unambiguously distinguish EI vs. real User without needing extra guards.

### Proof of Concept
1. Handler-level Go test using `gin.CreateTestContext`:
   - Call `auth.AuthenticateExternalInitiator(c, mockStore)` with a valid EI token/secret and a mocked `FindExternalInitiator` that succeeds.
   - Assert `auth.GetAuthenticatedUser(c)` returns `(&clsessions.User{Role: UserRoleRun}, true)`.
2. Integration test against `PipelineRunsController.Create`:
   - Register the route with `auth.Authenticate(store, auth.AuthenticateExternalInitiator)` (mirroring router.go's EI-auth setup for this route).
   - Send `POST /v2/jobs/<int-ID>/runs` with valid EI headers only (no session cookie, no API token).
   - Expected (buggy) behavior today: request proceeds past `isUser` check, `prc.App.RunJobV2` is invoked, and a `201`/pipeline-run resource is returned.
   - Expected (fixed) behavior: handler detects EI principal via `GetAuthenticatedExternalInitiator` and returns `422`/`401` with "bad job ID"/"unauthorized" rather than executing the run.
