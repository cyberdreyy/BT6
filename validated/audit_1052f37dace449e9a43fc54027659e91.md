### Title
APR0 withdraw receipt permanently bricks `stopEpoch` once APR is non-zero — unvalidated mixed-mode state freezes all vault funds - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault` runs two parallel withdrawal accounting modes: "normal" receipts (`withdrawsRequests`/`withdrawsRequestsByEpoch`) and APR0 receipts (`apr0Users`/`apr0TotalPrincipal`). A receipt created while `unscaledApr == 0` lives exclusively in the APR0 bucket. `prepareStopEpochWithApr0` — invoked by the CDO on every `stopEpoch` — reverts whenever `apr0TotalPrincipal != 0 && unscaledApr != 0` (lines 505-508), and the revert happens *before* `apr0TotalPrincipal` is cleared (line 540). The APR0 receipt itself cannot be claimed or settled until a `stopEpoch` succeeds, because `_settleApr0` requires `reqEpoch < epochNumber` (line 553) and `_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest` (line 326). This is a circular dependency with no exit: `stopEpoch` reverts forever and the entire vault TVL is frozen.

### Finding Description
The net-snmp bug is improper input validation where the same SET is processed simultaneously through two agent paths with inconsistent validation. The analog here is improper validation when two accounting "agents" (normal and APR0 receipt paths) coexist across an APR transition:

1. During an epoch where `unscaledApr == 0`, an unprivileged KYC'd lender calls `requestWithdraw` on the CDO. `IdleCreditVault.requestWithdraw` routes to `_requestWithdrawApr0`, setting `apr0Users[user].principal`/`principalEpoch` and incrementing `apr0TotalPrincipal` (lines 285-286, 567-577). The user receives a strategy-token receipt and `pendingWithdraws` is increased.
2. The borrower/manager — honestly, per protocol design — starts the next epoch with a non-zero APR, so `unscaledApr != 0` while the APR0 bucket is still open.
3. At the next `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which hits `if (unscaledApr != 0) revert NotAllowed()` (lines 506-508). The bucket is only closed at line 540, which is unreachable. Every subsequent `stopEpoch` reverts identically.
4. Escape hatches are all blocked: the user cannot claim (epoch gate), cannot settle (`_settleApr0` needs a bumped `epochNumber`), and `apr0TotalPrincipal` can only be decremented via `_clearWithdrawClaimForEpoch` on the default-claim path — which requires `defaulted()`/`defaultRecoveryFinalized`, i.e., it cannot self-heal. There is no cancel-request function.

### Impact Explanation
Permanent freezing of all vault funds. `stopEpoch` is the only path that returns borrower funds, accrues interest, and matures withdraw receipts; with it permanently reverting, no lender can ever withdraw and no epoch can close. Loss equals the entire vault NAV plus all pending receipts — far exceeding the attacker's deposit, which is a single minimal `requestWithdraw` (even 1 wei of APR0 principal keeps `apr0TotalPrincipal != 0`).

### Likelihood Explanation
The attacker only needs to be a KYC-passing lender submitting `requestWithdraw` during an APR0 epoch — a legitimate, unprivileged action (they can even self-front-run an announced APR change). Triggering the freeze additionally requires the honest manager/borrower to raise APR while an APR0 receipt is pending, which is a routine operational transition the code permits and never warns about. The window is open for the whole duration the APR0 request is pending (a full epoch), so the attacker's cost is negligible and can be planted speculatively.

### Recommendation
In `prepareStopEpochWithApr0`, close the APR0 bucket unconditionally (move `apr0TotalPrincipal = 0` and per-user settlement before the `unscaledApr` check), or revert earlier at `startEpoch`/APR-set time so the invalid mixed state is never entered. Alternatively, force-settle outstanding APR0 principal at zero interest when APR transitions to non-zero.

### Proof of Concept
```solidity
// Foundry fork PoC against the IdleCreditVault test harness (test/foundry/IdleCreditVault.t.sol)
function testApr0ReceiptBricksStopEpoch() external {
    // epoch 0: deposit and run with APR = 0
    _depositWithUser(user1, 10_000 * ONE_SCALE, false);
    _startEpochAndCheckPrices(0);          // unscaledApr == 0 for this epoch
    // attacker plants an APR0 withdraw receipt (legitimate user action)
    vm.prank(user1);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // manager honestly raises APR for the next epoch; epoch 0 is stopped
    // borrower repays; stopEpoch(0, interest) internally calls prepareStopEpochWithApr0
    // -> reverts NotAllowed() because apr0TotalPrincipal != 0 && unscaledApr != 0
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, nonzeroInterest);

    // every retry reverts; user cannot claim (epoch gate), cannot settle
    vm.prank(user1);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
    // vault is permanently frozen
}
```

Caveats: I could not fully verify within the iteration budget exactly where `unscaledApr` transitions (presumably via `startEpoch` APR parameters controlled by the honest manager/borrower) and whether a higher-level guard blocks APR changes while `apr0TotalPrincipal != 0`. If such a guard exists, this finding collapses to a revert-by-design DoS-without-impact and should be rejected; the circular revert/claim dependency in `prepareStopEpochWithApr0`/`_settleApr0` itself is confirmed by the cited code.
