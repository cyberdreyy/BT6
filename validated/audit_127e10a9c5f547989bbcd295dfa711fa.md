### Title
Signer v1 chainstate accepts a duplicate/conflicting tenure-change block because `validate_tenure_change_payload` checks only `get_last_globally_accepted_block` instead of `get_last_signed_block` - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
The v1 `SortitionsView::validate_tenure_change_payload` duplicate-tenure-start guard queries `signer_db.get_last_globally_accepted_block(...)` [1](#0-0)  to decide whether the signer has "already signed a block in this tenure." This check only sees blocks that have crossed the *global* (network-wide) signature threshold. A block that this very signer has already locally accepted/signed (`LocallyAccepted`) or pre-committed to (`PreCommitted`) — but which has not yet reached the 70% global threshold — is invisible to this check, so a second, different (conflicting) tenure-start block for the same tenure passes the proposal-time duplicate check and can proceed toward being signed.

The equivalent v2 code path, `SortitionData::validate_tenure_change_payload` in `chainstate/v2.rs`, was already fixed to use `get_last_signed_block` (locally-or-globally accepted) [2](#0-1) , and a regression test explicitly documents this as a fix for exactly this bug class [3](#0-2) . The v1 path was left with the pre-fix, narrower check.

### Finding Description
This is the same bug class as the SVGO `removeScripts` advisory: a security-relevant matching/equality check was updated in one code path (the "default namespace" case — here, v2/`GlobalStateView`) but the equivalent, still-reachable code path (the "prefixed" case — here, v1/`SortitionsView`) was left with the old, incomplete matcher. In both cases the fix narrows correctly-handled inputs in one branch while an alternate branch that should enforce the same invariant still uses the old, over-permissive comparison.

Concretely:
- `BlockInfo::mark_locally_accepted` / `mark_pre_committed` transition a block into `LocallyAccepted` or `PreCommitted` state without needing 70% signature weight [4](#0-3) .
- `get_last_globally_accepted_block` (used by v1) only returns blocks in `BlockState::GloballyAccepted`, whereas `get_last_signed_block` (used by v2, per the fix) also returns `LocallyAccepted`/`PreCommitted` blocks, as demonstrated by the test at `get_accepted_blocks` [5](#0-4) .
- `validate_tenure_change_payload` in v1 is the only place that guards against a duplicate/conflicting tenure-start block for the *same tenure* at proposal time [6](#0-5) . Because it uses the narrower query, a signer that has already locally accepted block A (tenure-start block for tenure T) will still pass a second, conflicting tenure-start proposal B for the same tenure T through this check if A has not yet reached global 70% signature weight — e.g., because other signers are slow, network partitioned, or the attacker deliberately delays gossip of A's acceptances to the rest of the set while re-proposing B to signers who haven't seen A yet.
- Per the project's own documentation, this proposal-time check is **not** re-run at validate-ok or at signing time; the only backstop is the pre-commit-threshold conflict guard (`get_signed_conflicts` / freshness / own-tenure checks) in section 5 of the state machine [7](#0-6) . That guard is time-bounded (`reorg_attempts_activity_timeout`) and, once a same-tenure conflict goes stale, falls back to asking whether the node has confirmed anything in that tenure — if it hasn't (plausible if network delivery to the node is also delayed or the tenure is still forming), the signer proceeds to `SIGN` anyway [8](#0-7) . This means the v1-only gap is not reliably compensated by the later stage.

### Impact Explanation
This breaks the "one canonical tenure-start block per tenure" equality the signer set is supposed to enforce (`DuplicateBlockFound`) for signers still running the v1 chainstate path. A single miner (one slot, as required by scope) can craft two conflicting tenure-change blocks for the same tenure and get a v1 signer to sign both, once the first has only local (not yet global) acceptance — a signer signing a conflicting/non-canonical block, satisfying the Critical impact bar ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
Exploitability requires only ordinary gossip timing skew (the first block's acceptances not yet reaching 70% network-wide) and does not require compromising a majority of signers, another signer's key, or any node-level access — matching the "one-slot miner plus gossip" threat model in scope. The bug is deterministic in the code (`get_last_globally_accepted_block` vs `get_last_signed_block`) and is already proven as a real, previously-fixed defect class by the existing v2 regression test, confirming it is a genuine, non-theoretical gap that was simply not backported to v1.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` to call `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the v2 fix, so that locally-accepted and pre-committed blocks in the same tenure are also treated as a duplicate/conflict at proposal time.

### Proof of Concept
1. Signer set is on the v1 (`SortitionsView`) chainstate path.
2. Miner proposes tenure-start block A for tenure T. Signer S locally accepts/signs A (`mark_locally_accepted`), but network-wide signature weight for A stays below 70% (e.g., other signers are slow or the miner suppresses rebroadcast of A's acceptance votes to part of the set).
3. Miner proposes a second, conflicting tenure-start block B for the same tenure T (different transactions/coinbase) to signer S.
4. In `check_proposal` → `validate_tenure_change_payload`, `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` returns `None` because A is only `LocallyAccepted`, so the `DuplicateBlockFound` rejection is not triggered [6](#0-5) .
5. B proceeds to validation/pre-commit/signing; whether S ultimately signs B depends on the section-5 conflict-freshness/own-tenure-confirmation logic, which is time-bounded and can also permit signing once A's conflict is deemed stale and the node has not yet confirmed the tenure [9](#0-8) , resulting in S having signed two conflicting tenure-start blocks for tenure T.
