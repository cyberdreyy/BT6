### Title
Mature-Message Rate-Limiter Bypass via Delayed Submission of Off-Chain-Signed Bridge Messages — (`bridge/evm/contracts/SuiBridgeV2.sol`, `bridge/evm/contracts/utils/BridgeUtilsV2.sol`)

---

### Summary

`SuiBridgeV2.transferBridgedTokensWithSignaturesV2` passes the **payload-embedded timestamp** (signed off-chain by the bridge committee) to `BridgeUtilsV2.isMatureMessage`. If that timestamp is more than 48 hours older than `block.timestamp`, the entire rate-limiter check — both `willAmountExceedLimit` and `recordBridgeTransfers` — is skipped. Because the signed message can be submitted by **anyone** at any time after the committee signs it, an ordinary bridge user can hold a valid signed message for 48+ hours and then submit it, bypassing the rate limiter entirely and withdrawing an unlimited amount from the EVM vault in a single transaction.

---

### Finding Description

**Root cause — off-chain signed timestamp controls an on-chain security gate:**

`BridgeUtilsV2.isMatureMessage` compares the timestamp baked into the signed payload against `block.timestamp`: [1](#0-0) 

```solidity
function isMatureMessage(uint256 messageTimestamp, uint256 currentTimestamp)
    internal pure returns (bool)
{
    return currentTimestamp > messageTimestamp + 48 * 3600;
}
```

`SuiBridgeV2._transferTokensFromVault` is decorated with `limitNotExceededV2`, which calls `isMatureMessage` and, when it returns `true`, skips both the limit check and the limiter recording: [2](#0-1) 

```solidity
modifier limitNotExceededV2(...) {
    if (!BridgeUtilsV2.isMatureMessage(timestampSeconds, block.timestamp)) {
        require(!limiter.willAmountExceedLimit(chainID, tokenID, amount), ...);
        limiter.recordBridgeTransfers(chainID, tokenID, amount);
    }
    _;
}
```

The timestamp is decoded from the signed payload: [3](#0-2) 

```solidity
tokenTransferPayload.timestampMs / 1000   // passed as timestampSeconds
```

`transferBridgedTokensWithSignaturesV2` is `external` with no caller restriction — any address may submit a valid signed message: [4](#0-3) 

The timestamp embedded in the payload originates from the Sui-side deposit event (`TokenDepositedEventV2.timestamp_ms`), which is set at deposit time on Sui: [5](#0-4) 

The bridge committee signs the message (including the timestamp) off-chain. Once signed, the message is a static blob that anyone can hold and submit at any future time.

---

### Impact Explanation

The rate limiter (`BridgeLimiter`) is the primary on-chain backstop against large-scale vault drainage. Its 24-hour rolling window is designed to cap the damage from any exploit or compromise. The mature-message path completely removes this backstop for any transfer whose signed message is submitted more than 48 hours after the Sui deposit timestamp. A single transaction can drain the entire EVM vault (e.g., all WETH, USDC, USDT) with no limit check and no limiter update, leaving the window state unchanged for subsequent transfers.

This matches the "harmful smart-contract behavior" impact class.

---

### Likelihood Explanation

The attack requires only:
1. A legitimate deposit on Sui (ordinary user action).
2. Obtaining the committee-signed V2 message (the bridge node publishes this; it is also observable on-chain once submitted).
3. Waiting 48 hours and 1 second.
4. Calling `transferBridgedTokensWithSignaturesV2` with the held message.

No special privilege, no committee compromise, no validator access is needed. The committee acts honestly throughout — they sign a legitimate transfer. The bypass is purely a consequence of delayed submission. Any bridge user can execute this.

---

### Recommendation

1. **Remove the mature-message limiter bypass entirely.** The rate limiter should apply to all transfers regardless of message age. If large or delayed transfers need special handling, require an explicit governance action rather than a timing side-channel.

2. **If the bypass must be retained for operational reasons**, add an upper-bound check: reject messages whose embedded timestamp is older than a configurable maximum age (e.g., 72 hours), so the window cannot be gamed indefinitely.

3. **Add a freshness check on submission**: verify that `block.timestamp` is within an acceptable window of `messageTimestamp` (e.g., ± N hours), analogous to the recommendation in the external report to make off-chain signatures expire quickly.

---

### Proof of Concept

```solidity
// 1. User deposits a large amount on Sui at time T.
//    Bridge committee signs a V2 message with timestampMs = T * 1000.
//    The signed message is available to the user.

// 2. User waits until block.timestamp > T + 48*3600 + 1.

// 3. User calls (no special role required):
bridgeV2.transferBridgedTokensWithSignaturesV2(committeeSignatures, message);
// Inside limitNotExceededV2:
//   isMatureMessage(T, block.timestamp) == true  →  limiter skipped entirely
// Full amount (e.g. $10M USDC) is transferred from vault to recipient.
// limiter.recordBridgeTransfers is never called.
// The 24-hour window is unaffected; subsequent transfers also face no accumulated limit.
```

This is confirmed by the repository's own test suite: [6](#0-5) [7](#0-6) 

Both `testMatureUSDCTransferBypassesLimit` and `testMatureMessageDoesNotUpdateLimiter` explicitly demonstrate that a message with a 49-hour-old timestamp bypasses the $1M/24h limit and leaves the limiter window state unchanged — confirming the bypass is reachable and complete.

            nonce: 1,

    function testMatureMessageDoesNotUpdateLimiter() public {
        // Fill vault with WETH
        changePrank(deployer);
        vm.deal(deployer, 200 ether);

        IERC20(wETH).transfer(address(vault), 100 ether);

        // Record limiter window amount before (chainID = 0 for source chain)
        uint256 windowAmountBefore = limiter.calculateWindowAmount(0);

        // Create mature message (49h old) - should NOT update limiter

        uint256 matureTimestamp = block.timestamp - (49 * 3600);
        bytes memory payload =
            _createV2TransferPayload(bridgerA, BridgeUtils.ETH, amount, matureTimestamp);

        BridgeUtils.Message memory message = BridgeUtils.Message({
            messageType: BridgeUtils.TOKEN_TRANSFER,
            version: 2,
            nonce: 1,
            chainID: 0,
            payload: payload
        });

        bytes memory encodedMessage = BridgeUtils.encodeMessage(message);
        bytes32 messageHash = keccak256(encodedMessage);

        signatures[0] = getSignature(messageHash, committeeMemberPkA);
