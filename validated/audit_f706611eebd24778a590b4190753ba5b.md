### Title
Stale confirmations from a removed multisig member allow request execution below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` in `multisig2/src/lib.rs` removes a member and their *own* originated requests, but leaves that member's confirmations intact on requests originated by other, still-active members. `confirm()` counts confirmations purely by `HashSet` length, so a stale confirmation from a deleted member still counts toward `num_confirmations`. This lets a request execute with fewer live-member approvals than the configured threshold.

### Finding Description
The multisig invariant is that `execute_request` should only run once `num_confirmations` *live* members have approved a request — i.e. `confirmations_from_live_members == num_confirmations`. The implementation instead enforces `confirmations.len() >= num_confirmations` [3](#0-2) , where `confirmations` is a raw set of member-identity strings recorded at confirmation time, never revalidated against current membership.

`delete_member` is the only code path that mutates `confirmations` in response to membership changes, and it only targets requests that the *removed* member created (`filter_map(|(k, r)| if r.member == member ...)`) [4](#0-3) . It never iterates `self.confirmations` to strip the removed member's entries from requests created by *other* members. Once that member is deleted (via a separate, correctly-executed `DeleteMember` multisig action), their earlier confirmation stored on someone else's pending request remains counted.

Same pattern exists in the older `multisig/src/lib.rs` contract, whose `DeleteKey` action removes only requests keyed by that `signer_pk` [5](#0-4) , and does not scrub that key's confirmations from other requests either.

### Impact Explanation
This is a Critical finding under the stated impact criteria: "a multisig request executed below threshold." Concretely, with members `{A, B, C}` and `num_confirmations = 2`:
1. `A` calls `add_request` (not `add_request_and_confirm`) for a sensitive action (e.g. `Transfer`, `FunctionCall`, `AddKey`) — 0 confirmations recorded.
2. `C` calls `confirm(request_id)` — 1 confirmation recorded (from `C`).
3. Members separately execute a legitimate 2-of-3 `DeleteMember{C}` request, removing `C` from `self.members` and its access key. Because that removal request was created by `A` or `B` (not `C`), and the pending request from step 1 is not owned by `C`, `delete_member`'s cleanup loop does not touch it — `C`'s stale confirmation survives.
4. `A` now calls `confirm(request_id)` on the original request. `confirmations.len() (1) + 1 >= num_confirmations (2)` is true, so `execute_request` runs — even though only one *live* member (`A`) ever approved it.

The request executes (transfer, key/permission grant, function call, etc.) with only a single genuine remaining approver, defeating the k-of-n authorization guarantee the contract is meant to enforce.

### Likelihood Explanation
The attacking party needs no special privilege beyond being a multisig member who later gets removed (or colludes with a member about to be removed), and the sequence (create request → confirm → unrelated member removal → final confirm) is straightforward multisig usage with no need for races, gas griefing, or external actors. Any deployment that legitimately rotates/removes members while requests are outstanding is exposed.

### Recommendation
When a member is deleted, iterate all pending requests' `confirmations` sets (not just those the member originated) and remove the deleted member's entry from each; alternatively, validate at confirmation-counting time that every recorded confirmer is still present in `self.members`, discarding stale entries before comparing against `num_confirmations`. Apply the equivalent fix to `multisig/src/lib.rs`'s `DeleteKey` handling.

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C], 2)`.
2. As `A`, call `add_request(request_R)` for some `Transfer`/`FunctionCall` action — confirmations for `R` = `{}`.
3. As `C`, call `confirm(R)` — confirmations for `R` = `{C}` (1 < 2, not executed).
4. Execute a legitimate `DeleteMember{C}` request via 2 confirmations from `A` and `B` — `self.members = {A, B}`, but `self.confirmations[R]` still equals `{C}` because `delete_member` only filters `self.requests`/`self.confirmations` for requests where `r.member == C` (`R` was created by `A`, so it's skipped) [4](#0-3) .
5. As `A`, call `confirm(R)`. `confirmations.len() == 1`, `1 + 1 >= 2` → `execute_request(R)` runs [3](#0-2) , even though only `A` among the current members ever approved it.

        self.assert_valid_request(request_id);

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
