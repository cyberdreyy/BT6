## Title
Builder sweep withdrawal double-counts already-queued `builder_pending_withdrawals`, minting excess Gwei - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas fork, `get_expected_withdrawals` assembles the payload's withdrawal list from four sources in sequence: builder pending withdrawals, pending partial withdrawals, builder sweep withdrawals, and validator sweep withdrawals. For validators, every later-stage function (`get_pending_partial_withdrawals`, `get_validators_sweep_withdrawals`) recomputes the validator's balance via `get_balance_after_withdrawals`, which subtracts any withdrawal amounts already placed earlier in the *same* batch. The builder-equivalent sweep function, `get_builders_sweep_withdrawals`, has no such adjustment: it reads `state.builders[builder_index].balance` directly from state, ignoring any amount already committed for that builder by `get_builder_withdrawals` earlier in the same call. This lets a single builder be committed twice for overlapping amounts in the same execution payload, causing the execution layer to mint more Gwei than the builder ever actually held.

### Finding Description
`get_builder_withdrawals` [1](#0-0)  iterates `state.builder_pending_withdrawals` and emits `Withdrawal(amount=withdrawal.amount)` verbatim for each queued builder payment, without ever checking it against the builder's current balance or against other withdrawals already added to the batch.

Later in the same function, `get_builders_sweep_withdrawals` [2](#0-1)  checks `builder.withdrawable_epoch <= epoch and builder.balance > 0` and emits a full-balance withdrawal `amount=builder.balance` — reading the balance straight from `state.builders[builder_index].balance`, with no subtraction of any withdrawal amount already added for that same builder by `get_builder_withdrawals` in the same `all_withdrawals` list.

Contrast this with the validator-side sweep logic, `get_validators_sweep_withdrawals` [3](#0-2) , which explicitly computes `balance = get_balance_after_withdrawals(state, validator_index, all_withdrawals)` before deciding the sweep amount — correctly netting out any partial withdrawal already queued in the same batch for that validator. Builders have no equivalent `get_balance_after_withdrawals`-style helper applied in their sweep path.

Because `get_expected_withdrawals` [4](#0-3)  runs `get_builder_withdrawals` first and `get_builders_sweep_withdrawals` third, a builder that (a) has a matured entry in `builder_pending_withdrawals` (from a previously accepted/quorum-approved bid, via `settle_builder_payment` / `process_builder_pending_payments` [5](#0-4) ) and (b) is simultaneously sweep-eligible (`builder.withdrawable_epoch <= epoch`, reachable by the builder exiting via `initiate_builder_exit` [6](#0-5) ) will have **both** its pending amount and its full current balance committed as separate `Withdrawal` entries in the same `payload_expected_withdrawals` list.

When `apply_withdrawals` actually deducts balances [7](#0-6) , it processes withdrawals sequentially and caps each deduction at the (already-shrinking) live `builder.balance`, so the on-chain CL total deduction can never exceed the builder's real balance — it saturates. But the committed `Withdrawal.amount` values in the payload are the un-capped, double-counted figures. Per the spec's own note on `process_withdrawals` [8](#0-7) , "the execution layer mints the full committed amount regardless, [so] any CL-side saturation creates a net supply inflation." That note was written for the validator/`decrease_balance` saturation case, but the same mechanism applies identically to the builder sweep path, since `apply_withdrawals` performs an analogous `min(withdrawal.amount, builder_balance)` saturation for builders.

### Impact Explanation
This breaks the "Gwei created" invariant: the execution layer mints Gwei to fee recipients that was never backed by real consensus-layer stake, because the committed withdrawal amount for the builder-sweep entry is not reduced by the pending amount already committed earlier in the same batch. This is a Critical-severity class finding (Gwei created and paid to a non-owner / minted from nothing) reachable by a single unprivileged builder acting alone, with no coalition or foreign key required — only self-timed exit relative to its own already-approved bid payment.

### Likelihood Explanation
The builder itself fully controls the timing: it submits a bid that eventually gets quorum-approved into `builder_pending_withdrawals`, and separately triggers its own exit (`builder_exit_request` → `initiate_builder_exit`) so that `builder.withdrawable_epoch <= epoch` becomes true in the same slot the pending withdrawal is swept. Both are legitimate protocol actions available to any registered builder; no cooperation from other parties beyond ordinary proposer/committee participation in approving the original bid is required.

### Recommendation
Introduce a builder-equivalent of `get_balance_after_withdrawals` and apply it in `get_builders_sweep_withdrawals` (and ideally in `get_builder_withdrawals` too), netting out any amount already present in `all_withdrawals` for the same `builder_index` before computing the sweep's `amount=builder.balance`, mirroring how `get_validators_sweep_withdrawals` nets out prior withdrawals for validators.

### Proof of Concept
1. Builder `B` submits a valid, quorum-winning bid of value `V`; after 1–2 epochs `process_builder_pending_payments`/`settle_builder_payment` appends `BuilderPendingWithdrawal(builder_index=B, amount=V)` to `state.builder_pending_withdrawals`.
2. Before this entry is swept, `B` submits a `BuilderExitRequest`, causing `initiate_builder_exit` to set `builder.withdrawable_epoch = current_epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY`; wait until that epoch is reached.
3. In the block where both conditions hold simultaneously, `get_expected_withdrawals` calls:
   - `get_builder_withdrawals` → emits `Withdrawal(builder_index=B, amount=V)`.
   - `get_builders_sweep_withdrawals` → since `builder.balance` (say `S`, with `S >= V`) is still read unadjusted, emits `Withdrawal(builder_index=B, amount=S)`.
4. The payload commits to total `V + S` for builder `B`, but `apply_withdrawals` only ever deducts up to `S` from `state.builders[B].balance` (saturating on the second entry). The execution layer nonetheless mints `V + S` to the specified fee recipients/execution address — `V` Gwei created with no corresponding consensus-layer stake reduction.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

##### New `get_builders_sweep_withdrawals`

```python
def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
