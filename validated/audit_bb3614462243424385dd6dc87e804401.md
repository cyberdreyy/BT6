### Title
`delete_member` clears only requests it authored, leaving its stale confirmations on other members' requests, allowing execution below live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` filters `self.requests` by `r.member == member` and removes confirmations only for requests **created by** the removed member. It never scrubs the removed member's own confirmation entries from `self.confirmations` sets attached to requests **created by other members**. A stale confirmation string from a now-deleted member therefore keeps counting toward `num_confirmations`, letting a request execute with one fewer live-member confirmation than the threshold requires.

### Finding Description
The binding that should hold is: after `delete_member(member)` returns, for every remaining request `r`, `confirmations[r.id]` contains no entry equal to `member.to_string()`. Instead the code only enforces this for requests where `r.member == member` (i.e., requests the removed member *authored*): [1](#0-0) 

Requests authored by *other* members that the soon-to-be-removed member had merely *confirmed* via `confirm()` are left untouched — their `confirmations` `HashSet<String>` still contains the removed member's `to_string()` key: [2](#0-1) 

Exploit flow (concrete counter-example):
1. Members = {A, B, C, D}, `num_confirmations = 3`.
2. A calls `add_request(R)` targeting some receiver/action (request authored by A, zero confirmations).
3. B calls `confirm(R)` → confirmations = {B}.
4. C calls `confirm(R)` → confirmations = {B, C} (2 of 3, one short of threshold).
5. Separately, a `DeleteMember{ member: C }` request is created and confirmed by 3 members and executed. `delete_member` checks `members.len() - 1 >= num_confirmations` (4-1=3≥3, passes) and only removes requests where `r.member == C` — since R was authored by A, it is untouched. `confirmations[R]` still equals `{B, C}` even though C is no longer a member.
6. Live members are now {A, B, D}. D calls `confirm(R)`. Confirmation count becomes 3 (`{B, C, D}`), meeting `num_confirmations`, and `execute_request` runs.
7. The executed request only had *two* live-member confirmations (B and D); C's confirmation was a ghost from a removed member. This violates the invariant that a request needs `num_confirmations` live-member approvals.

`assert_valid_request` and `current_member` only check that the *caller* confirming/creating is a current member — they never re-validate that *previously recorded* confirmations still belong to current members, so this stale-entry path is not caught anywhere else in the contract.

### Impact Explanation
This allows a multisig request (e.g., a `Transfer`, `AddKey`, `FunctionCall`, or another `DeleteMember`/`AddMember`) to execute with fewer live-member approvals than `num_confirmations` mandates — funds can leave the multisig account, or membership/key changes can be pushed through, using a confirmation "vote" from someone who is no longer a member. This maps to the Critical impact category explicitly listed in scope: "a multisig request executed below `num_confirmations` live members." It is repeatable any time a member is removed while they hold outstanding confirmations on requests they did not author.

### Likelihood Explanation
No special privilege is required beyond being a legitimate multisig member at the time of confirming (which any of the members named in scope already are) — the flaw is purely in the accounting done by `delete_member`, triggered by the normal member-removal workflow that every multisig using this contract eventually performs. It requires only ordinary usage: a pending request with fewer than `num_confirmations` confirmations, one of the confirmers subsequently being removed, and a new member later pushing the confirmation count to threshold. No attacker-controlled deposits, races, or unusual gas conditions are needed, making this straightforward and reliably reproducible.

### Recommendation
In `delete_member`, iterate over **all** `self.requests` (or the underlying `self.confirmations` map) and remove `member.to_string()` from every request's confirmation set, not just the set of requests the member itself authored. Additionally, re-check after removal whether any request's confirmation count now falls below `num_confirmations` given the reduced live member set (defense in depth), or recompute confirmations counts based only on `self.members.contains(...)` at execution time in `confirm`.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
