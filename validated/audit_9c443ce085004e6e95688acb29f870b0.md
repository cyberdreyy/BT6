### Title
Miner-invalidation status is not re-checked before signing, letting a signer sign a block for a miner it has already marked invalid - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`SortitionsView::check_proposal` (`stacks-signer/src/chainstate/v1.rs`) is the only place that checks a miner's `SortitionMinerStatus` (`Valid` / `InvalidatedBeforeFirstBlock` / `InvalidatedAfterFirstBlock`) and rejects a proposal with `RejectReason::InvalidMiner`/`NotLatestSortitionWinner` when the miner has been deemed invalid. [1](#0-0)  That check runs exactly once, at proposal arrival, via `check_block_against_state` → `check_block_against_local_state` → `SortitionsView::check_proposal`. [2](#0-1)  The two later re-checks that gate the state transitions which actually produce a signature - `handle_block_validate_ok` (pre-commit) and `handle_block_pre_commit` (the point the signature is placed) - call only `check_block_against_signer_db_state`, which re-verifies tenure-confirmation/height rules but never re-examines `SortitionMinerStatus`. [3](#0-2) [4](#0-3)  This is the same bug class as the report: a status ("liquidated"/"invalidated") that should permanently gate an actor's ability to act is checked once on entry but never re-verified at the point where the state-changing action (utilize funds / place a signature) is finally taken.

### Finding Description
`cur_sortition.miner_status` starts `Valid` and can be flipped to `InvalidatedBeforeFirstBlock` by this signer itself in two ways while a proposal for that same miner is already sitting in the signer's pending/pre-committed pipeline:

1. Timeout-based invalidation inside `check_proposal`, evaluated freshly on every new incoming proposal: `if self.cur_sortition.miner_status == Valid && is_timed_out(...) { self.cur_sortition.miner_status = InvalidatedBeforeFirstBlock }`. [5](#0-4) 
2. Reorg-rejection-based invalidation inside `store_and_process_block_rejection`, triggered once 30% weighted rejections with `ReorgNotAllowed` accumulate for a *different* block from the same tenure: `sortition_state.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock`. [6](#0-5) 

Both of these can occur strictly *after* the signer has already validated (`Ok` from the node) and pre-committed to a proposal from the same miner, and *before* that proposal crosses the pre-commit weight threshold that triggers `handle_block_pre_commit`'s final signing decision. The pre-commit path re-runs only `check_block_against_signer_db_state`, whose body is limited to `check_tenure_change_confirms_parent` / `check_latest_block_in_tenure` - it never reads `miner_status` at all. [7](#0-6)  The `handle_block_validate_ok` path is identical in this regard, marking the block `PreCommitted` and broadcasting a pre-commit based on the same limited re-check. [8](#0-7)  The docstring on `check_block_against_signer_db_state` itself flags this as deliberately narrow ("WARNING: This is an incomplete check. Do NOT call this function PRIOR to check_proposal") but that guarantee is only about ordering at first call, not about staleness of `miner_status` by the time the *pre-commit threshold* is crossed, which can be an arbitrary amount of time later (bounded by `tenure_last_block_proposal_timeout`/network propagation). [9](#0-8) 

The result: this signer can place its own signature (`mark_locally_accepted`, `handle_block_signature`, broadcast acceptance) over a block from a miner that this same signer's local state machine has already flagged `InvalidatedBeforeFirstBlock` - i.e., the "current miner" equality the state machine is supposed to enforce (`current_miner`/`miner_status` in `SortitionsView`) is violated at the moment the signature is actually produced, because the enforcement point (`check_proposal`) and the action point (sign-at-threshold) are decoupled and only the weaker check runs at the action point.

### Impact Explanation
This falls under the Critical bucket: a signer signing for a miner it has itself already determined to be invalid breaks the "approved-parent vs canonical"/"current miner" equality that the whole `SortitionsView` state machine exists to enforce. It is not merely a stale-view issue (which the docs already treat as an accepted edge case in section 5) - it is a specific field, `miner_status`, that is deliberately checked once at intake and then dropped from every subsequent re-validation path that gates the signature.

### Likelihood Explanation
This affects the v1 (local, non-global) chainstate signer protocol path, which is exercised whenever the active signer protocol version does not use global state (`state_version.uses_global_state()` false, see `check_block_against_state`). [10](#0-9)  It requires only: (a) the signer's own node returning `Ok` for a proposal (normal validation flow) so it pre-commits, and (b) a subsequent event - either the tenure's inactivity timeout elapsing, or ≥30% weighted `ReorgNotAllowed` rejections accumulating on a competing block in the same tenure - occurring before the pending pre-commit crosses the 70% threshold. Both triggering conditions are ordinary, gossip-driven signer-set behavior and do not require compromising a majority of signers or another signer's key; they only require timing between two events that are already part of normal operation.

### Recommendation
Re-run (or otherwise re-derive) the `SortitionMinerStatus` check for the block's sortition inside `check_block_against_signer_db_state`, or explicitly re-invoke the miner-validity portion of `SortitionsView::check_proposal` before `mark_pre_committed` and before the final signing decision in `handle_block_pre_commit`, so that a miner invalidated after initial proposal intake can no longer receive a signature from this signer for that tenure.

### Proof of Concept
1. Miner M proposes block B1 (tenure T). This signer's node validates B1 `Ok`; `handle_block_validate_ok` runs `check_block_against_signer_db_state` (passes, no miner_status check) and calls `mark_pre_committed`, broadcasting a pre-commit for B1. [8](#0-7) 
2. Before B1 reaches the 70% pre-commit threshold, either (a) `tenure_last_block_proposal_timeout` elapses with no signed block in T, so the next incoming proposal's `check_proposal` call flips `cur_sortition.miner_status` to `InvalidatedBeforeFirstBlock`, [5](#0-4)  or (b) a competing block B2 in tenure T accumulates ≥30% weighted `ReorgNotAllowed` rejections, causing `store_and_process_block_rejection` to set the same flag. [6](#0-5) 
3. Pre-commits for B1 from peers continue to arrive and cross the 70% threshold. `handle_block_pre_commit` re-checks only `check_block_against_signer_db_state` (tenure/height rules), which still passes for B1, and proceeds to `mark_locally_accepted`/`handle_block_signature`, producing this signer's signature over B1 even though `cur_sortition.miner_status` is now `InvalidatedBeforeFirstBlock`. [4](#0-3) 

This is a code-path/logic finding based on static analysis of the interaction between `check_proposal`, `check_block_against_signer_db_state`, `handle_block_validate_ok`, and `handle_block_pre_commit`; I did not run the signer against a live testnet to trigger the exact timing window, so the precise reachability window (whether other guards elsewhere in the codebase incidentally close this gap in practice) could not be fully confirmed from static reading alone.

    /// Re-verify a block's chain length against the last signed block within signerdb.
    /// This is required in case a block has been approved since the initial checks of the block validation endpoint.
    fn check_block_against_signer_db_state(
        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,
                self.proposal_config.tenure_last_block_proposal_timeout,
                self.proposal_config.reorg_attempts_activity_timeout,
            ) {
                Ok(true) => return None,
                Ok(false) => {
                    return Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))

                Err(e) => {
                    warn!("{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %proposed_block.block_id()
                    );
                    return Some(self.create_block_rejection(
                        RejectReason::ConnectivityIssues(
                            "error checking block proposal".to_string(),
                        ),
                        proposed_block,
                    ));
                }
            }
        }
