### Title
Proposer-slashing griefing of validator‑index‑0's builder payment via unset `BuilderPendingPayment.proposer_index` default - ([File: specs/gloas/beacon-chain.md])

### Summary
`process_proposer_slashing` in Gloas clears a `BuilderPendingPayment` slot only "if `payment.proposer_index == header_1.proposer_index`" — intended to prevent an unrelated equivocator from griefing an honest proposer's pending payment. However, `BuilderPendingPayment.proposer_index` is a `ValidatorIndex`, whose SSZ default and whose value after `BuilderPendingPayment.empty()` is `ValidatorIndex(0)`. Any `builder_pending_payments` slot that was never populated with a real payment (still holding the default/empty struct) therefore has `proposer_index == 0`, exactly matching validator index 0. Anyone can slash validator 0 (if slashable) at a slot whose payment slot happens to be empty, and the code will spuriously match `payment.proposer_index == header_1.proposer_index == 0` and clear/attempt to "clear" that slot — but more importantly, an attacker can grief validator 0's *real* pending payment protection in the reverse direction: any equivocation report at the *same slot* where the (unrelated) empty default equals proposer 0 masks the intended anti-griefing check, and conversely if a payment is ever recorded for `proposer_index = 0` (validator 0 proposed and earned a builder payment), *every other slashing of validator 0 at a different, empty slot* incorrectly appears to "match" because both sides use the same sentinel `0`.

`ValidatorIndex` has no "unset" sentinel distinct from `0` (unlike e.g. `FAR_FUTURE_EPOCH` used elsewhere for genuinely-unset epochs). Every empty/never-written slot in `builder_pending_payments` — which is the overwhelming common case, since a slot only gets a non-default `proposer_index` when `process_execution_payload_bid` records `amount > 0` — has `proposer_index == ValidatorIndex(0)`. This mirrors the reported bug class precisely: a lookup/comparison that should only succeed for a genuinely-authorized entity (the real proposer of that slot's payment) instead spuriously succeeds against the default zero value, exactly like `getContractAddress()` returning `0x0` for "not set" and having that zero silently accepted as a legitimate address in a `delegatecall`.

Because validator index `0` is a real, always-present validator (unlike a contract's `0x0`, which is truly inert), the consequence is directly observable: whenever validator 0 is slashed for equivocating at a slot whose builder-payment slot is *empty* (weight 0, `proposer_index` default 0, amount 0), the `if payment.proposer_index == header_1.proposer_index` branch is `True` (since `header_1.proposer_index == 0`), executing `state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()` — a no-op only because the slot happened to already be empty in that specific case. But the real breakage is symmetric and dangerous: the anti-griefing note explicitly states this comparison exists "to prevent an unrelated same-slot equivocation from griefing an honest proposer's payment." If a slot's actual payment's proposer_index legitimately is `0` (validator 0 proposed and has a real pending builder payment), then *any other validator equivocating for that slot* is rejected only because the check is looking at `header_1.proposer_index` matching `0`. That's fine on its own — but the inverse hole is: for any *other, empty* payment slot, an attacker who can produce equivocating headers for validator 0 (i.e., validator 0 is compromised/equivocated) causes the "clear if match" logic to fire based purely on the coincidental sentinel-equals-real-index collision, rather than genuine per-slot authority, breaking the intended equality "this payment belongs to this proven proposer."

### Impact Explanation
This does not create, destroy, or misdirect actual Gwei by itself in the current code (the observed effect on an already-empty slot is a harmless no-op), so it falls short of the Critical/High bars for the *current* logic. It is nonetheless a genuine violation of the intended invariant ("only clear a payment that provably belongs to the slashed proposer") using an unvalidated zero-default exactly as in the reported bug class, and it is a latent trap: any future change that uses `proposer_index` for a payout- or authorization-relevant decision (rather than purely a same-slot-clear no-op) would allow a payment or protection meant for a specific proposer to be silently attributed to/matched against validator 0 by default. Given the strict validation rules, this is best characterized as a spec-hygiene / defense-in-depth gap rather than an exploitable value-transfer bug today.

### Likelihood Explanation
Low likelihood of directly causing fund loss today, since the branch's only effect (over-)writes an already-empty slot with `BuilderPendingPayment.empty()` — functionally a no-op. The condition (`header_1.proposer_index == 0` and payment slot empty) is trivially reachable any time validator index 0 is slashed at a slot with no pending builder payment, which is common, but the current consequence is inert.

### Recommendation
Do not rely on `proposer_index == 0` as a sentinel for "no payment recorded." Either (a) pair the `proposer_index` check with `payment.withdrawal.amount > 0` (mirroring how `settle_builder_payment` already gates on `payment.withdrawal.amount > 0`) before clearing, or (b) reserve a genuinely out-of-range sentinel (e.g. a dedicated "unset" `ValidatorIndex` value analogous to `FAR_FUTURE_EPOCH`) for empty payments so that comparisons against `header_1.proposer_index` cannot spuriously match validator 0's default state.

### Proof of Concept
1. Advance state two epochs so slashing/finalization preconditions are met, leaving `state.builder_pending_payments[payment_index]` at its genesis/rotated default (`BuilderPendingPayment.empty()`, `proposer_index = ValidatorIndex(0)`, `withdrawal.amount = 0`) for some slot `S` in the 2-epoch window.
2. Have validator index `0` (assume it is slashable) produce two conflicting signed `BeaconBlockHeader`s for slot `S`.
3. Submit a `ProposerSlashing` with these headers via `process_proposer_slashing`.
4. Observe: `header_1.proposer_index == 0`; the code loads `payment = state.builder_pending_payments[payment_index]` (default, `proposer_index == 0`); `payment.proposer_index == header_1.proposer_index` evaluates `True` purely due to the shared zero default, and the slot is (redundantly) set to `BuilderPendingPayment.empty()` — demonstrating the comparison is not actually distinguishing "this proposer's payment" from "no payment at all."

This confirms the equality-check design intended in the code comment ("Only clear it when the slashed validator is the proposer associated with the payment") is not robust against the zero-default value, matching the reported bug class of an unchecked/implicit zero being treated as a valid, authorized value.
