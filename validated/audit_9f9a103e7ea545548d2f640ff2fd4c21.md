### Title
Group-level USD rate limiter can be trivially bypassed by structuring many small withdraw/borrow instructions within the admin settlement lag window - ([File: programs/marginfi/src/utils/general.rs])

### Summary
The group-level rate limiter (`configure_group_rate_limits`) is designed to cap total USD outflow across an entire marginfi group over hourly/daily windows. Unlike the bank-level rate limiter, which is updated inline on every withdraw/borrow because the bank account is writable, the group-level counter is deliberately left read-only during user transactions and is only mutated later by a privileged off-chain aggregator calling `update_group_rate_limiter`, with an allowed staleness of up to 1,500 slots (~10 minutes). This mirrors the GMX virtual-impact bug class: a global protective threshold is checked per-instruction against a delta, but the actual global state isn't updated in real time, so many small operations that individually pass the check can cumulatively blow far past the intended cap before the lagging aggregate state catches up.

### Finding Description
`record_withdrawal_outflow` in [1](#0-0)  is called on every withdraw/borrow. It updates the bank-level limiter inline, but for the group-level limiter it only performs a **read-only** check:
```
if group.rate_limiter.hourly.is_enabled() {
    let remaining = group.rate_limiter.hourly.effective_remaining_capacity(clock.unix_timestamp);
    if value.to_num::<i64>() > remaining { return Err(...); }
}
```
It never mutates `group.rate_limiter` — it only `emit!`s a `RateLimitFlowEvent` for later off-chain aggregation. The actual mutation of `group.rate_limiter.cur_window_outflow` only happens when the `delegate_flow_admin` calls `update_group_rate_limiter`, documented in [2](#0-1)  to tolerate up to `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS = 1_500` (~10 minutes) of staleness, and the guide states the admin batches "every ~10 minutes" in production (see [3](#0-2) ).

This is functionally identical to the GMX bug: a single instruction's outflow is checked against a threshold (`effective_remaining_capacity`) instead of against the true, continuously updated aggregate outflow. Because the on-chain group counter is not advanced by user transactions, every withdraw/borrow made before the next admin update reads the *same* stale `remaining` value. Multiple accounts (or repeated instructions from the same account) can each individually stay under the group cap check, yet their cumulative outflow within the lag window (a single block, or up to ~10 minutes / 1500 slots) can vastly exceed the configured `groupHourly`/`groupDaily` USD cap — precisely the "structuring" bypass the external report describes: chopping one large withdrawal into many smaller ones that each individually clear the threshold check.

The test suite explicitly documents and relies on this read-only, delayed-settlement behavior — see [4](#0-3)  ("group rate limiter is read-only during user instructions") and the batched-aggregation test at [5](#0-4) , confirming that many separate borrows succeed unconstrained by each other until the admin later aggregates and applies them in one lump sum.

### Impact Explanation
An attacker (or coordinated set of accounts) can withdraw/borrow far more USD value from the group than the configured `groupHourly`/`groupDaily` cap permits, simply by issuing many withdraw/borrow instructions (across different banks/accounts, or even the same account) before the delegate flow admin's next settlement — a window that can legitimately be as long as ~1500 slots (~10 minutes) per `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS`. Since the group rate limiter is the *only* USD-denominated, cross-bank defense-in-depth mechanism against rapid mass-drain of the protocol (e.g. during a compromised oracle, market dislocation, or bank misconfiguration event), this bypass defeats its entire purpose: cumulative outflow well in excess of the intended safety cap can occur before any protective response, directly undermining the risk-mitigation guarantee the feature exists to provide.

### Likelihood Explanation
Any unprivileged user can trigger this by simply performing several normal withdraw/borrow calls in quick succession (same block or within the admin lag window) — no special permissions, oracle manipulation, or privileged access is required. The bug is inherent to the documented architecture (asynchronous, event-driven settlement to avoid making the group account writable on every transaction), so it is reachable deterministically, not merely theoretical, whenever `configure_group_rate_limits` is enabled.

### Recommendation
Either (a) make the group-level counter authoritative in real time by requiring the group account to be writable and updated inline on every withdraw/borrow (accepting the serialization cost), or (b) bound the exploitable window tightly and add a per-instruction/per-account sub-limit so no single settlement gap can be drained beyond an acceptable fraction of the group cap, and shrink `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` substantially, or (c) require the off-chain worker's settlement cadence to be enforced on-chain (e.g. reject any outflow-consuming instruction once too much time has elapsed since `rate_limiter_last_admin_update_slot`) so the checked capacity can never diverge from ground truth by more than a small, safe amount.

### Proof of Concept
1. Admin configures `configure_group_rate_limits(hourly_max_outflow_usd = X)`.
2. Attacker (or several colluding/independent users) issues N withdraw/borrow instructions, each with value `< X` (so each individually passes the `effective_remaining_capacity` check in `record_withdrawal_outflow`), within the same block or within the `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` (~1500 slot) window before the delegate flow admin calls `update_group_rate_limiter`.
3. Because `group.rate_limiter` is never mutated by these user transactions (confirmed by the test at [4](#0-3) ), every one of the N instructions reads the same unadvanced `remaining` capacity and succeeds.
4. Total realized outflow = N × (per-tx amount), which can be made arbitrarily larger than `X` by increasing N, completely defeating the configured group-wide cap before the aggregator's next settlement lands.

/// Records withdrawal outflow on bank-level rate limiter and validates against
/// group-level rate limits (read-only). Emits a `RateLimitFlowEvent` for the
/// delegate flow admin to aggregate off-chain and update the group
/// rate limiter via
/// `update_group_rate_limiter`.
pub fn record_withdrawal_outflow(
    group_rate_limit_enabled: bool,
    native_amount: u64,
    balance_amount: u64,
    price: I80F48,
    bank: &mut Bank,
    group: &MarginfiGroup,
    group_key: Pubkey,
    bank_key: Pubkey,
    marginfi_account: &MarginfiAccount,
    clock: &Clock,
) -> MarginfiResult<()> {
    // Rate limiting tracks net outflow; skip for flashloan/liquidation/deleverage flows.
    if !should_skip_rate_limit(marginfi_account.account_flags) {
        if bank.rate_limiter.is_enabled() {
            bank.rate_limiter
                .try_record_outflow(native_amount, clock.unix_timestamp)?;
        }

        // Group-level rate limiting: read-only validation + event emission.
        // The admin aggregates events off-chain and calls update_group_rate_limiter.
        if group_rate_limit_enabled {
            check!(price > I80F48::ZERO, MarginfiError::InvalidRateLimitPrice);

            let value = calc_value(
                I80F48::from_num(balance_amount),
                price,
                bank.get_balance_decimals(),
                None,
            )?;
            if group.rate_limiter.hourly.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .hourly
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupHourlyRateLimitExceeded.into());
                }
            }
            if group.rate_limiter.daily.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .daily
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupDailyRateLimitExceeded.into());
                }
            }

            emit!(RateLimitFlowEvent {
                group: group_key,
                bank: bank_key,
                mint: bank.mint,
                flow_direction: 0, // outflow
                native_amount,
                mint_decimals: bank.mint_decimals,
                current_timestamp: clock.unix_timestamp,
            });
        }
    }
    Ok(())
}
