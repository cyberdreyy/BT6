### Title
QUIC pre-handshake connection-attempt flood bypasses both the global and per-IP rate limiters, exhausting `ClientConnectionTracker` slots and starving legitimate TPU connections - (File: streamer/src/nonblocking/quic.rs)

### Summary
The global (`overall_connection_rate_limiter`) and per-IP (`rate_limiter`) QUIC connection rate limiters are only *decremented* after a handshake successfully completes (`register_connection` / `consume_tokens` in the `Ok(new_connection)` branch of `setup_connection`), while the pre-accept gate only *peeks* at their current token counts (`current_tokens() == 0` and `is_allowed`). An attacker who never completes the TLS handshake (stalling until `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`) never triggers the decrement, so both rate limiters stay effectively full forever regardless of how many connection attempts are sent — including from a single, unspoofed IP. This lets the attacker flood `Incoming` connections fast enough to keep all `ClientConnectionTracker` slots (bounded by `qos.max_concurrent_connections()`) occupied, starving legitimate clients.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:331-379`), for every `Incoming` connection the server:
1. Peeks the global bucket: `if overall_connection_rate_limiter.current_tokens() == 0 { ... incoming.ignore(); continue; }` [1](#0-0) 
2. Peeks the per-IP bucket: `if !rate_limiter.is_allowed(&incoming.remote_address().ip()) { ... incoming.ignore(); continue; }` [2](#0-1) 
3. Only then creates a `ClientConnectionTracker` via `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())`, which is the actual capacity gate (`open_connections >= max_concurrent_connections` → `Err`). [3](#0-2) 

Both `TokenBucket::current_tokens()` and `ConnectionRateLimiter::is_allowed()` are read-only "peek" operations that do not consume any tokens: [4](#0-3) [5](#0-4) 

Tokens are only actually consumed later, inside `setup_connection`, and only in the branch where the handshake *succeeds*:
```
if !rate_limiter.register_connection(&from.ip()) { ... }
if overall_connection_rate_limiter.consume_tokens(1).is_err() { ... }
``` [6](#0-5) 

If the handshake never completes (attacker deliberately stalls it), execution instead falls into the `timeout(...)` branch, which only increments `connection_setup_timeout` — no token bucket is ever touched: [7](#0-6) [8](#0-7) 

Consequently, an attacker who never lets any handshake finish can send an unbounded number of `Incoming` connection attempts — even from one source IP — without ever depleting either rate limiter, because the limiters' state is only mutated by successful completions the attacker deliberately avoids. The only real cap on outstanding attempts is `ClientConnectionTracker::new`'s check against `qos.max_concurrent_connections()`, and each attempt can occupy a slot for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2 seconds) before being freed via `stats.outstanding_incoming_connection_attempts.fetch_sub` / `Drop for ClientConnectionTracker`. [9](#0-8) [10](#0-9) 

By sending stalled-handshake connections at a rate exceeding `qos.max_concurrent_connections() / QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, the attacker keeps `stats.open_connections` pinned at `max_concurrent_connections`, causing `ClientConnectionTracker::new` to return `Err` for legitimate incoming connections, which are then refused with `stats.refused_connections_too_many_open_connections` incremented and `incoming.refuse()` called. [11](#0-10) [3](#0-2) 

This defeats the design intent stated in the code's own comment (limit duration of in-flight attempts with a timeout, protect against bursts with a global rate limiter, rate-limit abusive peers by IP, cap total connections per peer/IP) [12](#0-11)  because two of those four listed mitigations (the global and per-IP rate limiters) never actually activate against an attacker who intentionally never completes the handshake.

### Impact Explanation
This is a remote, non-RPC ingest-starvation / resource-exhaustion vulnerability on the TPU QUIC ingest path: legitimate stakers/unstaked clients are refused connections (`refused_connections_too_many_open_connections` rises) while the validator's transaction ingest slot for new connections stays saturated with never-completing handshakes from a hostile client, degrading leader connectivity and transaction submission for honest participants. This matches Solana's bounty category for validator DoS / remote resource exhaustion on the network ingest path, scoped specifically to TPU handshake-slot exhaustion as described in the question.

### Likelihood Explanation
No privileged capability, staked key, or special config is required — any network-capable unprivileged attacker can open raw QUIC/UDP connections to the public TPU QUIC port and simply stall the TLS handshake (e.g., withhold the final handshake flight) until the fixed 2-second `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` elapses, then repeat. Because the rate limiters never actually decrement for such attempts, the attack is repeatable indefinitely and does not even require IP rotation or spoofing (unlike what the surrounding code comments assume is necessary for such an attack), making it straightforward and highly feasible under default validator configuration.

### Recommendation
Make the pre-accept admission decision consume the same tokens it inspects, rather than only peeking: call `overall_connection_rate_limiter.consume_tokens(1)` and `rate_limiter.register_connection(...)`-equivalent logic at the `Incoming` stage (before spawning `setup_connection`), and refund/re-credit the token if the connection subsequently completes successfully (or simply keep the debit — completed connections are rarer than attempts and this is the safer failure mode). Additionally, consider tracking and bounding outstanding (not-yet-handshaken) attempts per source IP independently of the post-handshake bucket, so a single IP cannot occupy an unbounded share of `qos.max_concurrent_connections()` slots purely with stalled handshakes.

// Pseudocode illustrating the exploit path; a full PoC requires a custom
// quinn client that sends only the Initial packet and never proceeds with
// address validation / TLS completion.

#[tokio::test]
async fn test_stalled_handshake_bypasses_rate_limiters_and_starves_legit_clients() {
    // 1. Start server via run_server(...) with default SwQosConfig
    //    (default max_concurrent_connections, default rate limiter params).

    // 2. Spawn N "slow handshake" clients from the SAME source IP, each of which:
    //    - opens a quinn::Endpoint::connect(...) to the server
    //    - never completes the handshake (e.g. drop the connecting future's
    //      driver task after sending Initial, or use a custom UDP socket that
    //      sends only a crafted Initial packet)
    //    Repeat at a rate > qos.max_concurrent_connections() / 2s.

    // 3. Assert:
    //    - stats.connection_rate_limited_across_all stays at 0 (global bucket
    //      never actually triggers, because tokens are never consumed by
    //      stalled attempts)
    //    - stats.connection_rate_limited_per_ipaddr stays at 0 for the
    //      attacking IP for the same reason
    //    - stats.refused_connections_too_many_open_connections increases
    //      once qos.max_concurrent_connections() is reached
    //    - a legitimate client attempting Endpoint::connect(...).await times
    //      out / is refused (Incoming::refuse()) during the flood, while the
    //      flood is sustained indefinitely.
}
```
Expected result: `stats.refused_connections_too_many_open_connections` rises continuously while `connection_rate_limited_across_all` / `connection_rate_limited_per_ipaddr` remain at 0, demonstrating the rate limiters never engage against the stalled-handshake flood, and legitimate connection attempts are refused.

impl Drop for ClientConnectionTracker {
    /// When this is dropped, reduce the open connection count.
    fn drop(&mut self) {
        self.stats.open_connections.fetch_sub(1, Ordering::Relaxed);
    }
}

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
