Unprivileged front-running of `create` lets anyone deploy a victim's derived lockup address with attacker-chosen terms - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` computes the lockup account deterministically as `hex::encode(&env::sha256(owner_account_id)[..20]).<factory>` and deploys it there without any check that the caller is the foundation, the owner, or otherwise entitled to create a lockup for that `owner_account_id`. Since NEAR account creation is a race (first writer wins), any unprivileged account can call `create` with a victim's `owner_account_id` and attacker-chosen `vesting_schedule`, `lockup_duration`, `lockup_timestamp`, `release_duration`, and `whitelist_account_id`, permanently occupying the address the real grantor would have used and locking in attacker-controlled terms.

### Finding Description
The invariant that should hold is:
`lockup_account(owner) == deploy(terms chosen by owner's legitimate grantor)`,
i.e. for a given `owner_account_id`, the only `LockupArgs` ever installed at `hex::encode(&sha256(owner_account_id)[..20]).<factory>` are the ones the grantor (normally the NEAR Foundation, calling `create` with the intended vesting/whitelist parameters) selected.

In `create` [1](#0-0)  the lockup account id is derived purely from `owner_account_id`: [2](#0-1) 

There is no `assert_called_by_foundation`, no owner check, and no `assert_self` guard on `create` itself (only the `on_lockup_create` callback is gated with `assert_self()` at [3](#0-2) ). The only requirement is `env::attached_deposit() >= MIN_ATTACHED_BALANCE` (3.5 NEAR) [4](#0-3) . The `foundation_account_id` field stored on the factory is only used to populate `LockupArgs.foundation_account_id` when a vesting schedule is present [5](#0-4)  — it is never compared against `env::predecessor_account_id()`.

Exploit flow:
1. Attacker learns (or predicts) a victim `owner_account_id` for whom the Foundation intends to create a lockup with specific vesting terms, but the Foundation has not yet called `create`.
2. Attacker calls `create(owner_account_id, lockup_duration=attacker_choice, lockup_timestamp=attacker_choice, vesting_schedule=attacker_choice_or_none, release_duration=attacker_choice, whitelist_account_id=Some(attacker_controlled_whitelist_contract))` with `MIN_ATTACHED_BALANCE` attached.
3. `Promise::new(lockup_account_id).create_account().deploy_contract(CODE).transfer(...).function_call("new", LockupArgs{...})` succeeds because the deterministic account does not yet exist.
4. When the Foundation later calls `create` with the same `owner_account_id` and the correct terms, `create_account()` on the already-existing account fails; `on_lockup_create`'s `is_promise_success()` check returns `false`, the deposit is refunded to the Foundation, and the legitimate deployment never lands [6](#0-5) .
5. The account permanently occupying the owner's expected address now carries attacker-chosen `lockup_duration`/`release_duration`/`lockup_timestamp` (able to delay or manipulate the release schedule) and, more critically, an attacker-controlled `staking_pool_whitelist_account_id` [7](#0-6) . Because the lockup contract only allows staking to pools present on this whitelist contract, the attacker's own whitelist can list only the attacker's malicious staking pool, so when the legitimate owner eventually gains control of "their" lockup and delegates, they are steered into an attacker-operated pool that the lockup treats as trusted.

None of the guard functions the audit rubric checks (`assert_owner`, `assert_called_by_foundation`, `assert_self`, `is_promise_success`, `assert_one_yocto`, etc.) protect `create`; `assert_self()` only fires in the callback after the damage (account claim) is already done, and `is_promise_success()` only determines refund vs. no-refund for the *later, legitimate* caller — it does not prevent or roll back the attacker's successful deployment.

### Impact Explanation
This matches the Critical category explicitly listed in scope: "a lockup deployed with parameters its rightful creator never chose." The attacker permanently seizes the deterministic address for an arbitrary `owner_account_id`, fixing `lockup_duration`, `release_duration`, `lockup_timestamp`, and — most severely — the `staking_pool_whitelist_account_id`, which governs which staking pools the eventual owner's funds can be delegated to. Because the whitelist contract address is fully attacker-chosen, the attacker can point the victim's future delegations at a pool they control, enabling fee-skimming or non-return of staked NEAR once the owner (unaware the lockup was pre-seeded) transfers funds in and stakes. This is repeatable for any `owner_account_id` not yet claimed, i.e., the entire pre-launch/pre-grant population of intended lockup recipients is exposed until the Foundation successfully claims each one first.

### Likelihood Explanation
The precondition is simply that the attacker learns an `owner_account_id` the Foundation plans to grant a lockup to before the Foundation's `create` transaction lands — plausible given that grant recipients (employees, investors) are typically known publicly or contractually before the on-chain lockup is created. Attacker cost is only `MIN_ATTACHED_BALANCE` (3.5 NEAR) plus gas, no privileged role is required, and the race is won by whoever submits first (a normal NEAR account-creation race, not requiring any special timing beyond speed). This is straightforward to reproduce deterministically in a unit test.

### Recommendation
Restrict `create` (or at least restrict setting non-default `vesting_schedule`/`whitelist_account_id`/custom durations) to `self.foundation_account_id` via an `assert_called_by_foundation()`-style check, mirroring the guard already conceptually present via `foundation_account_id` field but never enforced. Alternatively/additionally, incorporate a value only the legitimate grantor can supply (e.g., a Foundation signature, or restrict `predecessor_account_id` to a known allow-list of grantor accounts) into the derivation or into an explicit access check before deployment.

```rust
// lockup-factory/src/lib.rs tests module (near-sdk testing_env!)
#[test]
fn test_attacker_frontruns_victim_lockup() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    let lockup_duration_legit: WrappedTimestamp = 63036000000000000u64.into(); // 24 months, foundation's intended term
    let lockup_duration_attacker: WrappedTimestamp = 1u64.into(); // attacker's chosen term
    let malicious_whitelist = ValidAccountId::try_from("attacker-whitelist.near").unwrap();

    // Step 1: attacker calls create() first for the victim's owner_account_id,
    // with attacker-chosen duration and a malicious whitelist contract.
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(),          // victim's owner_account_id
        lockup_duration_attacker,        // attacker's term, not the foundation's
        None,
        None,
        None,
        Some(malicious_whitelist),       // attacker-controlled "trusted" whitelist
    );

    // Simulate successful account creation at the deterministic address.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let attacker_result = contract.on_lockup_create(
        lockup_account(), // hex::encode(sha256(owner_account_id))[..20].<factory>
        ntoy(30).into(),
        String::from("attacker.near"),
    );
    assert_eq!(attacker_result, true, "attacker's lockup claim must succeed first");

    // Step 2: the legitimate foundation later tries to create the SAME owner's lockup
    // with the correct terms - this must now fail because the account already exists.
    context.predecessor_account_id = String::from("foundation.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration_legit, None, None, None, None);

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed); // create_account fails: name taken
    let legit_result = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from("foundation.near"),
    );

    // Binding under test: lockup_account(owner) should carry the FOUNDATION's terms.
    // Assertion demonstrating the break: the legitimate creation is rejected/refunded,
    // while the account at the owner's derived address is permanently the attacker's.
    assert_eq!(legit_result, false, "legitimate foundation creation is blocked by the squat");
}
```
This demonstrates that the address `hex::encode(&env::sha256(owner_account_id)[..20])` ends up permanently bound to attacker-chosen `LockupArgs` (duration, whitelist) rather than the terms the Foundation intended, violating the stated invariant.
