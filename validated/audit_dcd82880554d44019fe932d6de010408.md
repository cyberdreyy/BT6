### Title
Authentication bypass via LDAP "unauthenticated bind" — missing empty-password check in `CreateSession` - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.CreateSession` forwards the raw `sr.Password` value from the unauthenticated `POST /sessions` request directly into `conn.Bind(searchBaseDN, sr.Password)` with no check that the password is non-empty. Per RFC 4513 §5.1.2, an LDAP `simple bind` with a valid DN and a zero-length password is defined as an "unauthenticated bind," which many LDAP servers accept (return code 0 / success) without validating any password at all, unless the server operator has explicitly disabled that behavior.

### Finding Description
The route `POST /sessions` is handled by `SessionsController.Create` in [1](#0-0) , which is reachable by any unauthenticated client (it's the login endpoint itself, gated by no prior auth). It binds the JSON body directly into `clsessions.SessionRequest{Email, Password}` and calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` with no validation on `Password`.

In `CreateSession`:
```go
escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
    ...
}
``` [2](#0-1) 

There is no guard rejecting `sr.Password == ""` before this bind call. If the underlying LDAP server treats a simple bind with an empty password as an "unauthenticated bind" (RFC 4513 default-permitted behavior unless the operator has hardened the directory to reject it), `conn.Bind` returns `nil` error for *any* valid, guessable `searchBaseDN` (i.e., any known/guessable email), regardless of the actual account password. The code then proceeds to call `l.FindUser(ctx, escapedEmail)` and, on success, creates a fully valid `ldap_sessions` row and returns a session ID — effectively logging the attacker in as that user with their real assigned role, without any credential knowledge.

This differs from the local fallback path (`localLoginFallback`), which correctly compares against a stored hashed password via `utils.CheckPasswordHash` — no such protection is applied on the primary LDAP bind path.

### Impact Explanation
If the upstream LDAP/AD server permits unauthenticated binds (a common default posture unless explicitly hardened), an attacker who only knows or guesses a valid user's email (e.g. `admin@company.com`) can obtain a fully authenticated Chainlink node session with that user's role (up to Admin) by submitting an empty password. This maps to the Chainlink bounty impact class of **authentication bypass / unauthorized privileged session creation**, potentially leading to full node compromise (job management, key access, fund-moving actions) depending on the impersonated user's role.

### Likelihood Explanation
- Precondition: LDAP authentication must be enabled on the node (`ldapauth` driver configured), and the upstream directory server must permit unauthenticated/anonymous binds for the bind DN pattern used (not universally true, but a known common default per RFC 4513 unless explicitly disabled by directory hardening).
- No credentials, tokens, or prior access are required — a single unauthenticated HTTP POST to `/sessions` with `{"email":"<target>","password":""}` is sufficient.
- Fully repeatable and scriptable; requires only knowledge/guessing of a valid registered email.
- This is a defense-in-depth gap in the application code itself: regardless of server posture, well-audited LDAP client integrations explicitly reject empty passwords before calling `Bind` to avoid depending on server-side hardening.

### Recommendation
In `ldapAuthenticator.CreateSession` (and `TestPassword`, which has the identical pattern), explicitly reject empty/blank passwords before calling `conn.Bind`:
```go
if strings.TrimSpace(sr.Password) == "" {
    return "", errors.New("unable to log in with LDAP server. Check credentials")
}
```
Apply the same guard in `TestPassword` (core/sessions/ldapauth/ldap.go, lines 504-530) which has the same unguarded `conn.Bind(searchBaseDN, password)` call.

### Proof of Concept
Go handler/unit test plan (using the existing `ldap_test.go` mock `LDAPClient`/`LDAPConn` fixtures):
1. Configure a mock `LDAPConn.Bind` that mimics RFC-4513 unauthenticated-bind semantics: return `nil` (success) whenever the password argument is `""`, regardless of the DN.
2. Call `ldapAuthenticator.CreateSession(ctx, sessions.SessionRequest{Email: "victim@example.com", Password: ""})`.
3. Assert: current behavior returns a valid, non-empty session ID and no error (`err == nil`), and a row is inserted into `ldap_sessions` for `victim@example.com` — demonstrating the bypass.
4. After applying the recommended fix, re-run the same test and assert `CreateSession` returns an error and no session is persisted.
5. Optionally add a handler-level integration test against `SessionsController.Create` using `internal/cltest` harness, posting `{"email":"victim@example.com","password":""}` to `/sessions` and asserting `401` after the fix (versus `200`/valid cookie before the fix).
