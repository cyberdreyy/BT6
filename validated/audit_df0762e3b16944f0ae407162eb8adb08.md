Based on the investigation, the hardcoded `BUILTIN_INSTRUCTION_COSTS` table (composed of `NON_MIGRATING_BUILTINS_COSTS` and `MIGRATING_BUILTINS_COSTS`) is inconsistent with the actual set of registered builtin programs/precompiles in the runtime, mirroring the RocketPool bug class of a hardcoded protection/classification list drifting out of sync with the live registry.

### Title
Inconsistent hardcoded builtin-cost classification list causes default compute-unit under-allocation for unlisted builtins/precompiles - ([File: builtins-default-costs/src/lib.rs])

### Summary
`BUILTIN_INSTRUCTION_COSTS`, frozen with a `// DO NOT ADD MORE ENTRIES TO THIS MAP` directive, only contains `system_program`, `compute_budget`, the three loader IDs, `loader_v4`, `secp256k1_program`, `ed25519_program`, and (migrating) `vote`. It does **not** include several other program IDs that are registered as actual builtins or precompiles elsewhere in the codebase: `secp256r1_program` (a precompile in `precompiles/src/lib.rs`), and `address_lookup_table`, `config`, `feature`, `stake` (Core BPF migrated builtins in `program-binaries/src/lib.rs` and reserved in `reserved-account-keys/src/lib.rs`). This is the same bug class as RocketPool's `upgradeContract` blacklist: a hardcoded, unmaintainable classification list that can silently diverge from the live set of "special" program IDs registered elsewhere in the system.

### Finding Description
`BUILTIN_INSTRUCTION_COSTS` is used by `MAYBE_BUILTIN_KEY` and `get_builtin_migration_feature_index` (`builtins-default-costs/src/lib.rs:126-150`) to classify an instruction's target program as `Builtin`, `MigratingBuiltin`, or `NotBuiltin` in `BuiltinProgramsFilter::check_program_kind` (`compute-budget-instruction/src/builtin_programs_filter.rs:46-60`). This classification directly feeds `ComputeBudgetInstructionDetails::calculate_default_compute_unit_limit` (`compute-budget-instruction/src/compute_budget_instruction_details.rs:196-219`), which computes the *default* compute-unit limit for a transaction that does not explicitly request one: [1](#0-0) 

- Programs classified `Builtin`/`MigratingBuiltin-not-yet-migrated` get `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` (3,000 CU) per instruction.
- Programs classified `NotBuiltin` get `DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` (200,000 CU) per instruction. [2](#0-1) 

Because `secp256r1_program`, `address_lookup_table`, `config`, `feature`, and `stake` are absent from `BUILTIN_INSTRUCTION_COSTS`, they are classified `NotBuiltin`, exactly as a generic user BPF program would be, even though they are actually registered builtins/precompiles/Core-BPF-migrated programs elsewhere: [3](#0-2) [4](#0-3) [5](#0-4) 

The comment at `builtins-default-costs/src/lib.rs:30-35` explicitly documents the required-but-manual synchronization step ("when a builtin is migrated to sbpf, please add its corresponding migration feature ID to `BUILTIN_INSTRUCTION_COSTS`... move it from `NON_MIGRATING_BUILTINS_COSTS` to `MIGRATING_BUILTINS_COSTS`"), confirming this is a hand-maintained, easily-drifting list exactly like RocketPool's `upgradeContract` blacklist. [6](#0-5) 

### Impact Explanation
For `stake`, `config`, `feature`, and `address_lookup_table` this currently results in *over*-allocation (200,000 CU default instead of 3,000), which is conservative and not directly exploitable — it only wastes block cost budget. However:
- `secp256r1_program` is a precompile that consumes essentially zero VM compute during actual execution (its verification happens outside the VM, at sigverify time), yet a caller who omits an explicit `ComputeBudgetInstruction::set_compute_unit_limit` gets charged the full 200,000 CU `DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` for it instead of the intended `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` (3,000 CU) that `secp256k1_program`/`ed25519_program` receive for the same class of instruction (confirmed by the `test_builtin_ix_precompiled` test at `core/tests/scheduler_cost_adjustment.rs:381-402`, which is only exercised for `secp256k1_program`). This is an inconsistency in the classification table rather than a security control breach, and it manifests as a fairness/cost-estimation bug (inflated default-cost estimation, not a bypass), not unauthorized fund movement or consensus divergence. There is no path by which an attacker can *reduce* required compute allocation below actual execution needs — the classification list only affects the *default* (unspecified) CU limit, and a user can always specify an explicit `compute_unit_limit`, so it is not usable to starve blocks or under-charge fees for real BPF execution.

### Likelihood Explanation
Any transaction invoking `secp256r1_program`, `stake`, `config`, `feature`, or `address_lookup_table` without an explicit `ComputeBudgetInstruction::set_compute_unit_limit` reaches this code path deterministically. This is a reachable, unprivileged path (ordinary user transaction, no special permissions needed), but the resulting effect is only an inconsistent/inflated default cost, not a security bypass with concrete unauthorized fund/state mutation, metering *bypass*, or consensus divergence given the current `NON_MIGRATING_BUILTINS_COSTS`/`MIGRATING_BUILTINS_COSTS` entries are all skewed toward over-charging, not under-charging.

### Recommendation
- Establish process/tests to keep `BUILTIN_INSTRUCTION_COSTS` synchronized with the authoritative sources of truth for builtins/precompiles/migrated programs (`BUILTINS` in `builtins/src/lib.rs`, `PRECOMPILES` in `precompiles/src/lib.rs`, `CORE_BPF_PROGRAMS` in `program-binaries/src/lib.rs`, and `RESERVED_ACCOUNTS` in `reserved-account-keys/src/lib.rs`), e.g. via a compile-time or CI cross-check asserting set consistency.
- Consider deriving `BUILTIN_INSTRUCTION_COSTS`-membership programmatically from these authoritative lists rather than maintaining a separately hand-curated, frozen array, mirroring the report's recommendation to prefer a well-defined whitelist mechanism tied to the actual registry over an easily-stale hardcoded list.

### Proof of Concept
Not applicable as a directly exploitable PoC — this is a classification-consistency defect, not a state-mutation or fund-theft bug. The observable effect can be demonstrated by comparing `test_builtin_ix_precompiled` (`core/tests/scheduler_cost_adjustment.rs:381-402`, using `secp256k1_program`, cost_adjustment = 3,000) against an equivalent transaction using `secp256r1_program::id()` in place of `secp256k1_program::id()`, which would show `cost_adjustment` computed against `DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` (200,000) instead of `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` (3,000), confirming the inconsistent classification.
