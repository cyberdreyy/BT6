### Title
Removed multisig members' stale confirmations still count toward execution threshold - ([File: multisig2/src/lib.rs])

### Summary
In `multisig2`, `delete_member()` clears pending requests and confirmations only for the request that the removed member itself created, but never scrubs that member's confirmation entries from the `confirmations` set of *other* pending requests that they had already confirmed as a co-signer. As a result, a removed member's confirmation permanently remains counted toward the `num_confirmations` threshold for any request they confirmed before removal, even though they are no longer a live member of the multisig.

### Finding Description
`confirm()` computes whether a request has reached quorum purely by counting entries already stored in `self.confirmations.get(&request_id)` plus the new confirmer, with no re-validation that each stored confirmer is still a current member: [1](#0-0) 

`delete_member()` only removes pending requests/confirmations where the removed member was the *requester* (`r.member == member`), not requests where the removed member appears only as a *confirmer* inside the stored `confirmations` HashSet: [2](#0-1) 

Because confirmations are stored as plain strings (`member.to_string()`) inside an `UnorderedMap<RequestId, HashSet<String>>` with no back-reference to `self.members`, once a confirmation is recorded it is never invalidated by a later membership change. The binding that should hold is:

`live_confirmations(request) == confirmations_from_current_members(request)`

but the actual state after a `DeleteMember` action is:

`stored_confirmations(request) ⊇ confirmations_from_removed_members(request) ∪ confirmations_from_current_members(request)`

so a removed member's earlier "vote" is still counted as if they were a live signer.

### Impact Explanation
This breaks the "confirmations counted versus live members" custody binding directly: it lets a request execute (including `Transfer`, `AddKey`/`AddMember`, `FunctionCall`, etc.) with fewer than `num_confirmations` *live* members actually agreeing, because one or more of the counted confirmations belong to accounts/keys that have since been removed from the multisig. This is a threshold-bypass — a multisig configured for K-of-N effectively degrades to (K-1)-of-(N-1) or worse whenever a confirming member is later removed while their confirmation on an unrelated pending request is still outstanding. Since multisig contracts on NEAR directly control fund transfers and key/member management, this can lead to a `Transfer` or account-modifying action being executed below the intended threshold — a Critical impact per the rules ("a multisig request executed below threshold").

### Likelihood Explanation
This requires no attacker privilege beyond normal multisig operation timing: any legitimate member confirms a pending request (but does not push it over threshold), and then, through the normal course of multisig governance, that same member is later removed via a `DeleteMember` request. No malicious multisig member, foundation action, or redeploy is required — it is a consequence of ordinary sequences of legitimate requests, and the remaining members are unaware their effective threshold has silently dropped by one for that specific pending request. The window is not contrived: it only needs one pending, not-yet-executed request to overlap with a subsequent membership change.

### Recommendation
When deleting a member in `delete_member()`, iterate over **all** pending requests' `confirmations` sets (not just requests authored by the removed member) and remove the member's string identifier from each, e.g.:
```rust
for (request_id, mut confirmations) in self.confirmations.iter() {
    if confirmations.remove(&member.to_string()) {
        self.confirmations.insert(&request_id, &confirmations);
    }
}
```
Alternatively (and more robustly against future membership changes), re-validate at `confirm()` time that every entry in the stored confirmation set still belongs to `self.members` before counting it toward `num_confirmations`, discarding stale entries lazily.

### Proof of Concept
1. Deploy `multisig2` with 3 members `A, B, C` and `num_confirmations = 2`.
2. Member `B` calls `add_request` to create request `R1` (e.g., `Transfer` to some attacker-controlled/unrelated account), authored by `B`.
3. Member `A` calls `confirm(R1)`. Now `confirmations[R1] = {A}` (1 of 2 needed) — `R1` is *not* executed yet.
4. Separately, via a fully confirmed `DeleteMember { member: A }` request, `A` is removed from the multisig (`self.members` no longer contains `A`). `delete_member()` only clears requests where `r.member == A` (i.e., requests *authored* by `A`); `R1` was authored by `B`, so it and its confirmations set `{A}` are left untouched.
5. Member `C` calls `confirm(R1)`. `confirmations.len() + 1 == 2 >= num_confirmations(2)` → `R1` executes with `C` as the only live confirming member (`A`'s confirmation is stale/counted-only).
6. Result: a transfer/action requiring 2-of-3 live members executed with effectively 1 live confirmation (`C`) plus a phantom confirmation from a removed member (`A`), demonstrating the threshold bypass described above. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
