### Title
Post-default withdraw requests drain the fixed default recovery reserve, shortchanging defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
After `finalizeDefaultRecovery` fixes `defaultRecoveryReserve`/`defaultRecoveryPrice` for defaulted-epoch receipts, `requestWithdraw` lets any user open `postDefaultRequests` that are later paid **1:1 out of that same reserve** via `_transferDefaultRecovery`. The reserve was sized only for pre-finalization claims; post-default payouts dilute it, so defaulted-epoch claimants (and the CDO recovery bucket) end up underpaid — a direct transfer of recovery funds to later claimants.

### Finding Description
`finalizeDefaultRecovery` computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and divides it by `totalBasis` (active basis + pending receipt basis) to set `defaultRecoveryPrice` [1](#0-0) . This reserve is the whole recovery pie for defaulted-epoch receipts (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) which pay `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from it [2](#0-1) .

After finalization, `requestWithdraw` still accepts new requests: it burns the CDO's strategy tokens, mints a receipt to the user, and sets `postDefaultRequests[_user] = _amount` [3](#0-2) . These receipts are then paid at par from the reserve: `_claimPostDefaultWithdrawRequest` calls `_burn(_user, amount)` and `_transferDefaultRecovery(_user, amount)` with no haircut and — critically — no corresponding reserve contribution, since the request path only moves strategy tokens, not underlying into `defaultRecoveryReserve` [4](#0-3) .

Even though the code comments claim post-default receipts are "already priced after the haircut and backed by the reserve" [5](#0-4) , the reserve was fixed at finalization against only the *defaulted* claim basis. Each post-default payout reduces the same reserve that `defaultRecoveryPrice` promised to defaulted-epoch claimants, so those claimants recover strictly less than the finalized ratio — and late claimants may find the reserve depleted entirely.

### Impact Explanation
Direct theft / dilution of recovery funds. Any unprivileged tranche holder (including a fresh post-default depositor, since only `isWalletAllowed`/KYC gating applies) can create a post-default receipt and pull underlying at par from a reserve that was cryptographically sized for someone else's losses. Quantified: each unit of `postDefaultRequests` claimed steals `1` underlying unit from the defaulted-epoch recovery allocation; with `defaultRecoveryPrice < 1e18` the attacker pays a haircut-priced amount via `requestWithdraw` but receives full value — an arbitrage against the recovery pool up to its full size.

### Likelihood Explanation
Requires a finalized borrower default (honest-manager-driven, allowed by the rules) and an attacker able to hold tranche tokens post-default. No privileged action needed: `requestWithdraw`→`claimWithdrawRequest`→`_claimPostDefaultWithdrawRequest` is a two-transaction user flow with no epoch-wait gate on the post-default path (the `epochNumber <= lastWithdrawRequest` check is bypassed because `_claimPostDefaultWithdrawRequest` returns early) [6](#0-5) .

### Recommendation
Fund post-default claims from their own deposit backing rather than `defaultRecoveryReserve`: either (a) require the CDO to transfer the request's underlying into the strategy and account it separately (e.g., a `postDefaultReserve` increased at request time), or (b) route post-default payouts through `_transferFundedClaim` while segregating unclaimed reserve, and have `_transferDefaultRecovery` decrement `defaultRecoveryReserve` so any drain reverts instead of silently diluting defaulted claimants.

### Proof of Concept
Foundry fork PoC sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol:4621-4653`):

```solidity
// 1. Deposit victim + attacker, run epoch, borrower defaults.
_depositWithUser(victim, 100_000e6, true);
_depositWithUser(attacker, 100_000e6, true);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr, 0); // default
_checkDefault();

// 2. Manager finalizes recovery at e.g. 50% -> reserve sized only for pending basis.
deal(defaultUnderlying, manager, recovered);
vm.startPrank(manager);
IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
cdoEpoch.finalizeDefault(recovered, manager);
vm.stopPrank();
uint256 reserveBefore = strategy.defaultRecoveryReserve();

// 3. Attacker creates a post-default request (haircut-priced in, par out).
uint256 victimReceipt = strategy.withdrawsRequests(victim); // defaulted-epoch basis
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();          // clear any old claims
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, AAtranche);   // postDefaultRequests[attacker] = haircutAmt
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();          // pays 1:1 via _transferDefaultRecovery

// 4. Victim's defaulted-epoch claim now receives less than
//    claimBasis * defaultRecoveryPrice / 1e18, or reverts on depleted reserve.
uint256 expected = victimReceipt * strategy.defaultRecoveryPrice() / 1e18;
uint256 balPre = underlying.balanceOf(victim);
vm.prank(victim);
cdoEpoch.claimWithdrawRequest();
assertLt(underlying.balanceOf(victim) - balPre, expected, "reserve not diluted");
```

*Uncertainty note:* I was unable to read `_transferDefaultRecovery`/`_transferFundedClaim` bodies in the available iterations; the finding assumes (as the code comments state) that post-default claims are "backed by the reserve" without an offsetting reserve deposit. If `_transferDefaultRecovery` does not decrement `defaultRecoveryReserve` and a separate funding path exists, severity reduces to accounting inconsistency; a confirming Devin session should verify those two functions before reporting.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }
