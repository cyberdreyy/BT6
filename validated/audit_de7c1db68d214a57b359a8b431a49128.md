Based on my research, I found a concrete analog to the CRLF injection bug class: an unauthenticated field embedded alongside a signed field, letting a relayed message be tampered with while its signature still verifies.

### Title
Unauthenticated `reason`/`reason_code`/`response_data`/`chain_id` fields in `BlockRejection` let any relayer tamper with a signer's rejection metadata without invalidating the signature - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` computes the signature preimage from only the `signer_signature_hash` field via `make_structured_data_domain`/`structured_data_message_hash`, not from `reason`, `reason_code`, `chain_id`, `metadata`, or `response_data` (which carries `reject_reason`, `tenure_extend_timestamp`, `failed_txid`, etc.). Any node relaying/re-broadcasting the message (a miner or any signer building the StackerDB chunk) can rewrite those fields while the ECDSA signature over the (unchanged) hash still verifies successfully.

### Finding Description
`BlockRejection::hash()`: [1](#0-0) 
only commits to `self.signer_signature_hash`. `sign()`/`verify()`/`recover_public_key()` all operate over this same narrow hash: [2](#0-1) 

But the full struct carries many more fields that travel with the signature and are trusted by receivers: [3](#0-2) 

Because none of `reason`, `reason_code`, `chain_id`, `metadata`, or `response_data` (including `reject_reason`) is part of the signed preimage, a party that can place a chunk into `.signers` StackerDB under an unchanged signature — i.e. any signer, including a compromised/malicious one relaying, or a miner-adjacent observer replaying a captured message — can substitute a different `reason_code`/`reject_reason`/`chain_id` for the *same* `signer_signature_hash` and the *same* signature bytes, and `verify()` will still return `Ok(true)`.

This is directly analogous to the Netty CRLF bug class: a field that travels alongside an authenticated/structural element is not itself covered by the integrity mechanism, so a relay can splice in different content that downstream logic (here, `handle_block_rejection`) will treat as if it came unmodified from the signer who actually produced the signature.

### Impact Explanation
Downstream, `reject_reason`/`reason_code` from an accepted-as-valid-signature `BlockRejection` feeds tallying and state-machine decisions (e.g., counting weight toward 70% global rejection, and, in non-global-state versions, updating miner-invalid status per the `ReorgNotAllowed` reason as documented in `docs/signer-flows.md` section 6). A tampered `reason_code`/`reject_reason` on an otherwise-validly-signed rejection could cause peer signers to draw an incorrect conclusion about *why* a peer rejected a block (e.g., turning a benign `RejectedInPriorRound` into `ReorgNotAllowed`, or vice versa) while the signature check gives false assurance that the entire message is authentic. Because signature validity is the only gate applied before this data is trusted, this breaks the implicit equality "signed content == validated content" for everything except the hash field itself.

That said, I was not able to fully trace every consumer of `BlockRejection.response_data.reject_reason` inside `handle_block_rejection`/`store_and_process_block_rejection` in the given context window to confirm a Critical/High-severity state transition (e.g., an incorrectly forced `mark_globally_rejected` or miner-invalidation) results purely from this field without also requiring the 30%+ rejection weight threshold, which would put it outside the "no majority needed" constraint. The weight tally itself (`reason_code`-independent) is unaffected — only the *reason* attached to an already-counted rejection is spoofable. This limits the confirmed impact to metadata/observability corruption rather than a proven consensus-safety break, unless further review of `handle_block_rejection` shows some code path branches on `reject_reason` before/without the weight threshold.

### Likelihood Explanation
Any StackerDB participant who can read a legitimately broadcast `BlockRejection` chunk (all signers can) and re-submit a modified copy under their own StackerDB slot, or a relay that mutates in transit, can perform this without needing any signer's private key, a majority of signers, or the auth token — the signature bytes and `signer_signature_hash` are simply copied verbatim while other fields are edited.

### Recommendation
Include `reason`, `reason_code`, `chain_id`, and `response_data` (and `metadata` if it should be authenticated) in the structured-data hash preimage computed by `BlockRejection::hash()`, so the signature covers the entire semantically meaningful content of the rejection, not just the block hash being rejected.

### Proof of Concept
1. Capture a legitimately signed `BlockRejection` chunk observed on `.signers-N-M` StackerDB, e.g. one with `reason_code = RejectCode::RejectedInPriorRound`, `signer_signature_hash = H`, `signature = S`.
2. Construct a new `BlockRejection` with the same `signer_signature_hash = H` and `signature = S`, but `reason_code = RejectCode::ValidationFailed(ValidateRejectCode::BadTransaction)` (or any other code) and a different `reason` string / `response_data.reject_reason`.
3. Call `BlockRejection::verify(&public_key)` — per the `hash()` implementation in [1](#0-0)  the check still succeeds because it recomputes the hash from `signer_signature_hash` alone, ignoring the tampered fields.
4. Broadcast the doctored message; peers that trust `verify() == true` will attribute the forged reason/reject_reason to the original signer's signature.

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
