### Title
Unauthenticated disclosure of LOOP plugin Prometheus metrics via `/plugins/:name/metrics` - ([File: core/web/router.go, core/web/loop_registry.go])

### Summary
The `/discovery` and `/plugins/:name/metrics` (and pprof forwarding) routes are registered on the unauthenticated `api` router group in `loopRoutes`, with no `auth.Authenticate` middleware applied, unlike other sensitive routes such as `/debug/vars`. Any unauthenticated network client can enumerate plugin names via `/discovery` and then fetch each plugin's internal Prometheus metrics via `/plugins/:name/metrics`.

### Finding Description
`NewRouter` builds the `api` group with only rate-limiting and session middleware (`core/web/router.go:78-85`), then calls `loopRoutes(app, api)` (`core/web/router.go:91`) without any additional auth wrapper — contrast with `debugRoutes`, which explicitly requires `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` before exposing `/debug/vars` (`core/web/router.go:180-183`). `loopRoutes` registers `r.GET("/discovery", ...)`, `r.GET("/plugins/:name/metrics", loopRegistry.pluginMetricHandler)`, and pprof forwarding routes directly on the unauthenticated group (`core/web/router.go:230-236`). `pluginMetricHandler` (`core/web/loop_registry.go:96-128`) looks up the plugin by name in the registry and proxies an HTTP GET to the plugin's internal `/metrics` endpoint, returning the raw body to the caller with no authentication check performed in the handler itself. `discoveryHandler` similarly exposes the full list of registered plugin names with no auth (`core/web/loop_registry.go:53-81`), giving an attacker the exact plugin names needed for the `/plugins/:name/metrics` route.

### Impact Explanation
An unauthenticated remote attacker can retrieve internal Prometheus metrics for any registered LOOP plugin (e.g., Median, Solana, Starknet relayer plugins), which can include operational counters, internal state, timing/latency histograms, and potentially identifying labels that aid further reconnaissance or targeted attacks against the node. This falls under information disclosure / metrics exposure, a lower-severity but real unauthenticated data-disclosure issue.

### Likelihood Explanation
Fully feasible and repeatable: no credentials, tokens, or session are required. An attacker only needs network access to the node's HTTP port and either guesses a plugin name or first calls the equally unauthenticated `/discovery` endpoint to enumerate exact names, then issues a plain `GET /plugins/<name>/metrics`.

### Recommendation
Require authentication (or restrict to trusted network/reverse-proxy scraping only) for `/plugins/:name/metrics`, `/discovery`, and the pprof forwarding routes — e.g., wrap them with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` similar to `debugRoutes`, or gate them behind a separate internal-only listener/port not exposed publicly, consistent with how Prometheus scrape endpoints are typically isolated from the main authenticated API surface.

### Proof of Concept
Extend `core/web/loop_registry_test.go`'s `TestLoopRegistry` (or add a new handler-level test) to build the router via `NewRouter` and, using a plain `http.Client` with **no** session cookie or auth header, perform:
1. `GET /discovery` — assert `200 OK` and that the response JSON contains the registered plugin's `__meta_plugin_name` label (already effectively demonstrated by the existing test at `core/web/loop_registry_test.go:101-122`, run with an unauthenticated client).
2. `GET /plugins/<discovered-name>/metrics` — assert `200 OK` and that the body contains the plugin's Prometheus metric (as in `core/web/loop_registry_test.go:124-140`), confirming no `401 Unauthorized`/`403 Forbidden` is returned despite the absence of any session or API token in the request.
3. Table-test iterating multiple known/guessed plugin names against a router built with `auth.Authenticate` middleware present on other routes (e.g., `/debug/vars`) to contrast expected `401` there vs actual `200` on `/plugins/:name/metrics`.

func (l *LoopRegistryServer) pluginMetricHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/metrics", l.loopHostName, p.EnvCfg.PrometheusPort)
	req, err := http.NewRequestWithContext(gc.Request.Context(), http.MethodGet, pluginURL, nil)
	if err != nil {
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "error creating plugin metrics request: %s", err))
		return
	}
	res, err := l.promClient.Do(req)
	if err != nil {
		msg := "plugin metric handler failed to get plugin url " + html.EscapeString(pluginURL)
		l.logger.Errorw(msg, "err", err)
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "%s: %s", msg, err))
		return
	}
	defer res.Body.Close()
	b, err := io.ReadAll(res.Body)
	if err != nil {
		msg := fmt.Sprintf("error reading plugin %q metrics", html.EscapeString(pluginName))
		l.logger.Errorw(msg, "err", err)
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "%s: %s", msg, err))
		return
	}

	gc.Data(http.StatusOK, "text/plain", b)
}
