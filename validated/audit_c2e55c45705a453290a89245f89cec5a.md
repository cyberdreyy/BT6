### Title
Unsanitized absolute/traversal `zip.File.Name` in `ExtractZipArchive` allows path escape outside build/cache/artifact directory - ([File: helpers/archives/zip_extract.go])

### Summary
`ExtractZipArchive` and its helpers (`extractZipFile`, `extractZipDirectoryEntry`, `extractZipSymlinkEntry`, `extractZipFileEntry`) use `file.Name` directly with no `filepath.Clean`, no rejection of absolute paths, and no check that the resolved path stays within the intended extraction root, then call `os.MkdirAll(filepath.Dir(file.Name), 0o777)` and later `lchmod(file.Name, ...)`. This confirms the described root cause exists in the reviewed code.

### Finding Description
`extractZipFile` (`helpers/archives/zip_extract.go:61-83`) does:
```go
err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
```
followed by dispatch to `extractZipDirectoryEntry`/`extractZipSymlinkEntry`/`extractZipFileEntry`, all of which pass `file.Name` straight to `os.Mkdir`, `os.Symlink`, or `os.OpenFile` [1](#0-0) . `ExtractZipArchive` then also calls `lchmod(file.Name, file.Mode())` for every entry [2](#0-1) . The only validation applied anywhere in this file is `errorIfGitDirectory`, which only checks whether the cleaned path's first component is `.git` — it does not reject absolute paths or `..` traversal [3](#0-2) . There is no `filepath.IsAbs` check, no `filepath.Rel`/containment check against a base directory, and no chroot/jail applied before or during extraction.

However, to actually exploit this, the attacker needs a code path that feeds an attacker-influenced zip (with an absolute-path `zip.File.Name`) into `ExtractZipArchive`. The two callers found are `ExtractZipFile` (opens an on-disk zip and calls `ExtractZipArchive`) and `ziplegacy.extractor.Extract` (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go:26-32`), which is used by GitLab Runner's own cache/artifact extraction helper commands. Critically, the zip *archives* consumed here are created by Runner itself via `CreateZipArchive`/`createZipEntry` (`helpers/archives/zip_create.go:52-83`), where `fh.Name = fileName` is set from the file paths **as resolved on disk relative to the job's build directory** at archive-creation time (i.e., the paths come from `cache:paths`/`artifacts:paths` globbing against the local filesystem, not arbitrary attacker strings baked directly into zip headers). For a job to produce a zip entry with `Name = "/etc/cron.d/x"`, it would need to either (a) get Runner to archive a file whose on-disk path is literally `/etc/cron.d/x` (which requires already having write access outside the build dir — not a privilege escalation via this bug, since the job would need that access to create the file in the first place), or (b) supply/upload a pre-built malicious zip file that is later extracted by `ExtractZipArchive` without Runner regenerating the header names.

This second path is the actual concern: whether the CI job can control archive contents that get extracted later without the extraction code revalidating/re-deriving names from a trusted list, and whether that extraction happens in a way that crosses the job's own project sandbox. The code inspected here does not perform this revalidation — it trusts `file.Name` verbatim. But confirming an exploitable path requires knowing whether attacker-uploaded artifact/cache zips are ever fed into `ExtractZipArchive` without server-side/agent-side sanitization of entry names, and whether any wrapping code (upload/download endpoints, cache_extractor, artifacts extractor commands) sets/enforces a working directory or applies its own path-containment check before calling into `archives.ExtractZipArchive`. I was not able to locate such a validation layer in the reachable code (`commands/helpers/cache_extractor_test.go`, `commands/multi.go` references were found but their contents were not inspected due to iteration limits), so I cannot fully rule out or confirm whether a wrapping caller mitigates this.

### Impact Explanation
If reachable without a mitigating wrapper, this allows an unprivileged job to write or overwrite arbitrary files (with attacker-chosen mode via `lchmod`) anywhere on the filesystem the Runner process can write to, using only a crafted zip archive — a classic zip-slip/absolute-path extraction vulnerability. This would violate the "extraction stays within intended root" invariant and could enable host file writes (e.g., cron jobs, SSH authorized_keys) depending on Runner process privileges, which is a severe and concrete impact if the path is reachable.

### Likelihood Explanation
The vulnerable code (`extractZipFile`, `ExtractZipArchive`) unconditionally trusts `file.Name`, so the low-level primitive is real and trivially reproducible in isolation. The likelihood of full end-to-end exploitation depends entirely on whether any caller in the artifact/cache download-and-extract flow passes a genuinely attacker-controlled zip (as opposed to one Runner built itself from local files) into this function without prior sanitization — this could not be conclusively verified with the available context (callers `commands/helpers/cache_extractor.go`/`artifacts_extractor.go` were not fully inspected).

### Recommendation
Regardless of whether an external wrapper currently mitigates this, harden `extractZipFile`/`ExtractZipArchive` defensively:
- Reject or sanitize any `file.Name` that is absolute (`filepath.IsAbs`) or that, after `filepath.Clean(filepath.Join(root, file.Name))`, does not remain under the intended extraction `root`.
- Apply this check once per entry before both the extraction pass and the `lchmod` pass in `ExtractZipArchive`.
- Treat violations the same way `errorIfGitDirectory` is treated (skip entry, log warning) rather than silently proceeding.

### Proof of Concept
```go
func TestExtractZipArchive_RejectsAbsolutePath(t *testing.T) {
    tmpDir := t.TempDir()
    origWd, _ := os.Getwd()
    require.NoError(t, os.Chdir(tmpDir))
    defer os.Chdir(origWd)

    escapeTarget := filepath.Join(t.TempDir(), "escape") // outside tmpDir tree

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    fh := &zip.FileHeader{Name: escapeTarget}
    fh.SetMode(0o644)
    w, _ := zw.CreateHeader(fh)
    _, _ = w.Write([]byte("pwned"))
    require.NoError(t, zw.Close())

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    _ = archives.ExtractZipArchive(zr)

    _, err = os.Stat(escapeTarget)
    assert.True(t, os.IsNotExist(err), "file should not have been created outside extraction root, but was: %v", err)
}
```
Expected current behavior: the assertion fails because `os.Stat(escapeTarget)` succeeds, proving `extractZipFile`/`extractZipFileEntry` write outside any intended root when given an absolute `zip.File.Name`. This confirms the primitive-level flaw in `helpers/archives/zip_extract.go`; a full severity determination requires additionally tracing the artifact/cache download commands to confirm whether attacker-supplied zip bytes reach `ExtractZipArchive` unmediated.

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}

	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
