Confirmed: same pattern exists in both `multisig/src/lib.rs` (`DeleteKey` action) and `multisig2/src/lib.rs` (`DeleteMember` action) — removal of an access key/member only purges requests *created* by that key/member, not confirmations they placed on *other* still-active requests. I'll report the `multisig2` version as primary since it's the more general, currently maintained implementation.

### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing requests to execute below the configured threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` decides whether to execute a pending request purely by comparing the size of the `confirmations` `HashSet<String>` against `num_confirmations`, without verifying that every entry in that set still corresponds to a current member of `self.members`. `delete_member` only purges requests *created* by the removed member and their confirmation sets — it never scans other pending requests to strip out confirmations that member had cast on requests created by someone else. This lets a request execute with fewer live-member approvals than the contract's own `num_confirmations` threshold requires.

### Finding Description
`confirm()` is implemented as: [1](#0-0) 

It checks `confirmations.len() as u32 + 1 >= self.num_confirmations` and executes the request if true, only validating that the *current* caller is a member via `assert_valid_request`/`current_member()`; it never re-validates the *other* addresses already recorded in the `confirmations` set. [2](#0-1) 

`delete_member` is the only place that ever prunes confirmation data, and it does so by filtering `self.requests` for entries whose *creator* (`r.member`) equals the member being removed — confirmations that the removed member cast on requests created by *other* members are left untouched in the `confirmations: LookupMap<RequestId, HashSet<String>>` map: [3](#0-2) 

Binding that should hold: `confirmations.len()` (weight counted toward threshold) == number of *currently live* members who approved the request. Because `delete_member` doesn't scan and clean every other request's confirmation set, this binding breaks: `confirmations.len()` can include members no longer in `self.members`, so `confirmations.len() >= num_confirmations` no longer implies `num_confirmations` *live* members approved.

The identical structural bug exists in the legacy `multisig/src/lib.rs` for the `DeleteKey` action, which likewise only removes requests created by the deleted key, not that key's confirmations on other requests: [4](#0-3) 

### Impact Explanation
This is a Critical-impact finding under "a multisig request executed below threshold." A request can be executed (including `Transfer`, `AddKey`/`AddMember`, `DeployContract`, or arbitrary `FunctionCall` to the contract's own account) with fewer genuinely live approving members than `num_confirmations` mandates, because a stale confirmation from a since-removed member is still counted. This effectively lowers the real security threshold of the multisig without anyone explicitly authorizing that change via `SetNumConfirmations`, directly undermining the k-of-n custody guarantee that funds/administrative actions require k *live* member approvals.

### Likelihood Explanation
This requires no compromise of any key beyond normal multisig operation: a member confirms a pending request (as they are entitled to do), and at some later point — for entirely legitimate governance reasons (key rotation, offboarding, suspected compromise) — the multisig later removes that member via a separate `DeleteMember`/`DeleteKey` request. Both actions are ordinary, expected multisig operations; the bug is that the system does not clean up the first member's leftover confirmation weight when the second action occurs. Any multisig that rotates members while requests are outstanding is exposed, which is a realistic and even encouraged security practice (rotating a suspected-compromised key).

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), scan every entry in the `confirmations` map (not just requests created by that member) and remove the member's entry from each request's confirmation set. Alternatively/additionally, change `confirm()` to recompute the "live" confirmation count by filtering `confirmations` against `self.members.contains(...)` before comparing against `num_confirmations`, so stale entries can never count toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A.add_request(request)` — creates `request_id` with an empty confirmation set (`request.member == A`).
3. `B.confirm(request_id)` → `confirmations = {B}` (len 1, `1+1 < 3`, not yet executed).
4. `C.confirm(request_id)` → `confirmations = {B, C}` (len 2, `2+1 < 3`... wait note: check is `len()+1>=num_confirmations`, so at len 2 the check `2+1>=3` is true and it would execute already after 2 confirmations plus the caller — this is intentional design: the 3rd confirming caller is counted implicitly). For clarity, use a fresh unconfirmed request and stop after step 3 with only `{B}` confirmed (len 1).
5. Separately, D and A submit and confirm a `DeleteMember { member: C }` action (self-request), reaching quorum through 3 approvals unrelated to the pending Transfer request; this executes and removes C from `self.members`, but C never confirmed the Transfer request in this run so nothing to clean up — to hit the real bug, instead have **C** (not B) confirm the pending Transfer request before being removed.
6. Correct sequence: `A.add_request(transferRequest)`; `C.confirm(transferRequest_id)` → `confirmations = {C}`. Then members vote to remove C via `DeleteMember{member: C}` (a separate request reaching 3 confirmations from A, B, D) — `delete_member` only inspects `self.requests` for requests created by C (none, since A created the transfer request), so `confirmations = {C}` on `transferRequest_id` is left untouched even though C is now not in `self.members`.
7. Now only B and D are eligible live confirmers, yet `confirmations` already contains stale `C`. `B.confirm(transferRequest_id)` → `confirmations.len() = 2`, check `2+1 >= 3` → true → `execute_request` runs the `Transfer`, even though only **B** and (the confirming caller) are truly live approvers plus the stale C — i.e., the transfer executes with effectively 2 live confirmations (B and the implicit self-count) against a configured threshold of 3, because C's stale vote is still counted.     /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
