### Title
Global `maxCacheSize` limit in `requestCache.NewRequest` allows unauthenticated flood of distinct-sender requests to exhaust shared cache capacity, denying legitimate requests - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces only a single global cache-size ceiling (`len(c.cache) >= int(c.maxCacheSize)`) with no per-sender quota or rate limiting. Any party able to submit syntactically valid, distinct `Sender`/`MessageId` gateway messages can fill the shared cache to `maxCacheSize`, causing subsequent legitimate callers' `NewRequest` calls to fail with `"request cache is full"`.

### Finding Description
In `core/services/gateway/handlers/common/requestcache.go`, `NewRequest` (lines 50-76) keys entries by `globalId{sender, id}` [1](#0-0)  and admits a new entry as long as the total cache size is below `maxCacheSize`, with no accounting or limit tied to `request.Body.Sender`: [2](#0-1) . There is no per-sender bucket, weight, or fairness mechanism anywhere in this file — capacity is a single shared pool across all senders. Handlers that use `RequestCache[T]` (e.g. vault, capabilities handlers) call this generic interface; I could not confirm from the indexed code that any of these call sites impose a pre-check that limits how many *outstanding* entries a single sender can hold in the cache before calling `NewRequest` — the interface itself provides no such hook, and the search for per-sender allowlist/quota logic inside the gateway handler packages returned no matches tying sender identity to cache occupancy. If message authentication (signature verification) happens upstream of `NewRequest`, it only proves message integrity/origin, not that the sender is entitled to a fair share of cache slots — it does not stop a sender from legitimately generating many distinct signed messages with unique `MessageId`s to occupy the entire pool.

### Impact Explanation
This is a capacity-exhaustion / denial-of-service issue: an attacker with the ability to produce valid signed gateway messages (which per the audit's stated precondition is free/self-serve for any EOA) can pre-empt the shared request cache, causing other users' legitimate `NewRequest` calls to be rejected with `"request cache is full"` until attacker entries time out. This matches a capacity-theft/DoS impact class rather than a direct authentication or fund-movement bypass — no secrets or unauthorized job execution are obtained, but service availability/fairness for other tenants of the gateway is denied.

### Likelihood Explanation
Feasibility is high assuming the precondition holds (attacker can freely generate signed messages with unique sender/message IDs) and no external layer (e.g. per-sender rate limiter, gateway-level allowlist quota) exists in front of the shared `RequestCache`. I was unable to fully verify all call sites (e.g. `core/services/gateway/handlers/vault/handler.go`, `capabilities/handler.go`) to confirm whether some external per-sender throttling wraps calls into this cache, as those files did not directly reference `RequestCache`/`NewRequest` by name in the areas grep matched, suggesting cache usage may be through an intermediate abstraction not fully traced here. This uncertainty should be resolved with a live test.

### Recommendation
Add per-sender quota enforcement inside `requestCache.NewRequest` (e.g., track counts per `request.Body.Sender` and cap them independently of the global `maxCacheSize`), or enforce sender-based rate limiting/allowlisting upstream of the cache so that no single sender can occupy more than a fair share of total slots.

### Proof of Concept
Go unit test plan (extending `core/services/gateway/handlers/common/requestcache_test.go`):
1. Construct `requestCache := NewRequestCache[SomeState](timeout, maxCacheSize)` with small `maxCacheSize` (e.g., 3).
2. In a loop, call `requestCache.NewRequest(lggr, &api.Message{Body: api.MessageBody{Sender: "attacker-N", MessageId: "id-N"}}, callback, &state)` for N = 1..maxCacheSize, asserting each returns `nil` error.
3. Call `requestCache.NewRequest(lggr, &api.Message{Body: api.MessageBody{Sender: "victim", MessageId: "victim-1"}}, callback, &state)` and assert it returns error `"request cache is full"`, proving a single attacker occupying all slots denies an unrelated victim sender.
4. Optionally assert that entries from different attacker "sub-identities" are all distinct keys (no dedup across sender-1..sender-N), confirming there is no shared per-sender budget preventing this.
