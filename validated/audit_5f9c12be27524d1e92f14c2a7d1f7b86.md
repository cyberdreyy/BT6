### Title
Removing a multisig key does not purge its stale confirmations on other pending requests, allowing a request to execute below the real confirmation threshold - (File: multisig/src/lib.rs)

### Summary
The `MultiSigContract::confirm()` function counts confirmations by public key stored in an `UnorderedMap<RequestId, HashSet<PublicKey>>`. When a key is removed via the `DeleteKey` action, only requests that were *added* by that key are purged; any confirmations that key previously cast on requests *added by other signers* are left untouched. Those stale confirmations still count toward `num_confirmations` when a later `confirm()` call is made, allowing a request to execute with fewer genuinely live approvals than `num_confirmations` requires.

### Finding Description
`confirm()` treats reaching `num_confirmations` distinct public keys in the `confirmations` set as sufficient to execute a request immediately: [1](#0-0) 

The binding that should hold is: `confirmations.len() == number of currently-authorized keys that approved`. But when a key is deleted via the `DeleteKey` action, the cleanup logic only removes *requests originally added by that key* — it does not scan and strip that key from the `confirmations` sets of other outstanding requests: [2](#0-1) 

So if key `C` confirms request `R1` (added by key `A`), and `C` is later removed from the multisig via a separate, properly-confirmed `DeleteKey{C}` request, `R1`'s confirmation set still contains `C`'s stale entry. `assert_valid_request` (called before `confirm`) only checks that the caller is `current_account_id == predecessor_account_id`; it does not re-validate that previously stored confirmations still belong to currently authorized keys: [3](#0-2) 

As a result, when a remaining live key (e.g. `A`) calls `confirm(R1)`, the stale `C` entry plus the new live confirmation can reach `num_confirmations`, and `execute_request` fires even though only one truly authorized key actually confirmed.

### Impact Explanation
This breaks the "confirmations counted versus live signers" custody binding: `execute_request` can be triggered by fewer genuinely authorized approvals than `num_confirmations` mandates. Per the scope's impact categories, this is a **Critical** finding — "a multisig request executed below threshold" — because arbitrary `Transfer`, `AddKey`, `FunctionCall`, etc. actions can be pushed through with insufficient live approval, potentially moving NEAR out of the multisig account without the intended quorum.

### Likelihood Explanation
No privileged or out-of-scope actor is required. All actions involved (`add_request`, `confirm`, and the `DeleteKey` action itself) are ordinary multisig operations performed by legitimate keyholders in the normal course of key rotation (e.g., revoking a compromised or departing signer). Any time a key is removed after having confirmed—but not yet triggered execution of—an outstanding request, the vulnerability is live; no special timing, front-running, or attacker-controlled deployment is needed.

### Recommendation
When executing the `DeleteKey` action, iterate over all entries in `self.confirmations` (not just requests whose `signer_pk` matches the deleted key) and remove the deleted public key from every confirmation set. Alternatively, validate at `confirm()`/`execute_request()` time that every public key present in a request's confirmation set still corresponds to a currently valid access key on the account before counting it toward `num_confirmations`.

### Proof of Concept
1. Multisig initialized with `num_confirmations = 2` and keys `A`, `B`, `C`.
2. `A` calls `add_request(R1 = Transfer{...})` (unconfirmed, `confirmations[R1] = {}`).
3. `C` calls `confirm(R1)` → `confirmations[R1] = {C}` (count 1 < 2, not executed).
4. `A` calls `add_request_and_confirm(R2 = DeleteKey{C})` → `confirmations[R2] = {A}`.
5. `B` calls `confirm(R2)` → count reaches 2, `execute_request` runs `DeleteKey{C}`: the loop at multisig/src/lib.rs:198-216 only deletes requests whose `signer_pk == C` (none, since `R1.signer_pk == A`), so `confirmations[R1] = {C}` is left intact even though `C` is no longer a valid key.
6. `A` calls `confirm(R1)` → `confirmations[R1].len() + 1 = 2 >= num_confirmations(2)` → `execute_request(R1)` fires the `Transfer`, even though only `A` (one live key) actually approved it — the request executed below the real quorum of live signers.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
