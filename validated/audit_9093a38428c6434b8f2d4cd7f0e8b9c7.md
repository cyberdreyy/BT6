The `WorkflowMetadataHandler.Authorize` function in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go` has a classic TOCTOU (check-then-act) gap that is directly analogous to the reported vulnerability: a shared piece of state (`amtETH`/divisor in the report; here, the JWT-replay cache) is *checked* before the expensive/concurrent work is done, but the state-mutating write (`recordUsage`) only happens *after* all the checks pass — with no atomicity between the read and the write, and no lock held across the whole authorize-and-consume operation.

### Title
JWT Replay-Cache Check-Then-Act Race Enables Concurrent Reuse of a Single-Use Gateway Auth Token - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`Authorize()` verifies a JWT, checks `h.jwtCache.isReplay(claims.ID)`, then—only if the JWT hasn't been seen—later calls `h.jwtCache.recordUsage(claims.ID)` to mark it used. Because `isReplay` and `recordUsage` are two independent lock acquisitions rather than a single atomic check-and-set, an unprivileged client (any HTTP-trigger caller reaching the gateway) that fires the same signed JWT concurrently can pass the `isReplay` check multiple times before any goroutine calls `recordUsage`.

### Finding Description
`Authorize` (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:80-108`) does:
1. `h.jwtCache.isReplay(claims.ID)` — acquires `cache.mu.RLock()`, checks map, releases lock.
2. Authorized-key lookup (map reads under `h.mu`... actually unguarded map read here).
3. `h.jwtCache.recordUsage(claims.ID)` — acquires `cache.mu.Lock()`, inserts entry, releases lock.

Between steps 1 and 3 there is no lock held that would serialize concurrent invocations of `Authorize` with the same `jti`. This mirrors the root cause in the external report precisely: a value used to gate/compute an action (`amtETH`/`isReplay`) is read once, an action proceeds based on that stale read, and the state used for the gate is only updated *after* the action, allowing multiple concurrent invocations to all observe the "not yet used" state.

`Authorize` is invoked from `httpTriggerHandler.authorizeRequest` (`http_trigger_handler.go:361-369`), which is directly reachable by any external, unauthenticated-except-for-signature caller sending an HTTP trigger request to the gateway (`HandleUserTriggerRequest`, `http_trigger_handler.go:88-140`). This is exactly the "internet-facing gateway" / message-envelope authentication path called out as in-scope. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Impact Explanation
The JWT replay cache exists specifically to prevent an intercepted/observed single-use signed authorization token from being reused to trigger a workflow execution more than once. If an attacker (or a legitimate but malicious caller) replays the exact same signed request concurrently (e.g., dozens of parallel HTTP connections), the race allows multiple `HandleUserTriggerRequest` calls to pass `authorizeRequest` before `recordUsage` commits, each proceeding to `checkRateLimit` and then fanning the request out to all DON nodes (`sendWithRetries`). This defeats the single-use guarantee of the token, effectively duplicating workflow-execution requests that should be authorized exactly once — a request-impersonation/replay-bypass analogous to Bob's ability to mint disproportionate LP shares by re-entering before `Vaults[vid].amtETH` was updated.

### Likelihood Explanation
Exploitation only requires the attacker to already possess one valid, unexpired signed JWT (which they would, being the legitimate/observing caller) and to issue the same request several times in quick succession/parallel — a trivial network-level operation, no special privileges needed. The rate limiter (`checkRateLimit`) is a separate, independent check and does not close this specific replay-cache race window.

### Recommendation
Make the "check unused and mark used" operation atomic under a single lock (or use a `sync.Map`/single mutex-protected read-modify-write, e.g., `LoadOrStore` semantics) so that `isReplay` and `recordUsage` cannot be observed as both "not present" by two concurrent callers for the same `jti`. For example, collapse `isReplay` + `recordUsage` into one method (`claimIfUnused(jti) bool`) that holds `cache.mu.Lock()` for the entire check-and-insert.

### Proof of Concept
1. Obtain (or sign) one valid `jti`-bearing JWT for a registered workflow's HTTP trigger.
2. Send N (e.g., 20) concurrent POST requests to the gateway's HTTP trigger endpoint using the identical JWT/request payload.
3. Observe that more than one request passes `Authorize` (no "JWT token has already been used" error) and is forwarded to the DON, i.e., more than one execution is dispatched from a token meant to authorize exactly one execution — directly analogous to the PoC in the report where concurrent reentrant calls bypass the intended single-shot accounting because the guard state is updated only after the protected action begins.

Note: I could not fully verify whether a downstream, execution-ID-based dedup exists elsewhere in the pipeline (e.g., in `httpTriggerHandler.setupCallback`/`sendWithRetries` or at the workflow engine) that might independently collapse duplicate executions before they cause double billing/side effects; this would need to be checked in a live session to confirm end-to-end impact severity.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
