### Title
BlockAccepted/BlockRejection message signatures do not cover their own payload fields (reason/response_data), allowing signature-preserving tampering of signer response content - (File: `libsigner/src/v0/messages.rs`)

### Summary
Analogous to the SeaDrop `mintSigned` bug (a struct's fields aren't fully hashed into the EIP-712 digest, so an attacker can vary the un-hashed fields while keeping a "valid" signature), the Stacks v0 signer messages `BlockAccepted` and `BlockRejection` compute their signed digest over only a small subset of their own struct fields, leaving other semantically meaningful fields (`response_data`, `metadata`, and for rejections `reason`/`reason_code`) completely outside the signature. Anyone who observes one validly signed message from a signer can therefore construct a different message (different rejection reason/code, different `failed_txid`, different tenure/read-count extend timestamps) that still passes `verify()`/`recover_public_key()` against that signer's real key.

### Finding Description
`BlockRejection::hash()` builds the signed digest from only the `signer_signature_hash` field plus a domain string keyed by `chain_id`: [1](#0-0) 

```
pub fn hash(&self) -> Sha256Sum {
    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
    let signature_hash = self.hash();
    self.signature = private_key.sign(signature_hash.as_bytes())?;
    Ok(())
}
```

But the `BlockRejection` struct itself carries much more semantic content that is never folded into this digest — `reason` (free-form string), `reason_code` (`RejectCode`, including `ValidationFailed(ValidateRejectCode)` variants), and `response_data` (`BlockResponseData`, containing `reject_reason`, `tenure_extend_timestamp`/read-count extend timestamp equivalents, and `failed_txid`): [2](#0-1) 

`verify()`/`recover_public_key()` only re-derive `hash()`, so they cannot detect if `reason`, `reason_code`, or `response_data` were altered after the honest signer produced the signature: [3](#0-2) 

The `BlockAccepted` case is worse: its signature is computed directly over the raw `signer_signature_hash` bits with no domain separation and, critically, without covering `response_data` (`full_extend_ts`/`read_count_extend_ts`) or `metadata` at all: [4](#0-3) 

and it is verified the same bare way on the receiving/miner side: [5](#0-4) 

Because `response_data` (tenure-extend timestamp and read-count-extend timestamp) rides along in the serialized `SignerMessage` but is never part of what is signed, any party capable of re-emitting the (StacksSignature-bearing) message bytes — including anyone forwarding, relaying, or re-broadcasting a signer's already-published StackerDB chunk — can rewrite these timestamps to arbitrary values while the accompanying `signature`/`signer_signature_hash` pair still verifies as authentic for that signer.

This matches the reported bug class precisely: the digest is computed over an incomplete representation of the "struct," so fields outside it are free to vary without invalidating the signature (i.e., a form of cross-content/cross-context-valid signature, since the same signature validates for many different asserted `reason_code`/`response_data` payloads).

### Impact Explanation
The immediate consequence is that the semantic payload of a signer's block-response message (why it rejected a block, which transaction it flagged as problematic, or how long a tenure/read-count extension it is granting) is not cryptographically bound to that signer's identity. Downstream consumers key decisions off these unauthenticated fields:
- `stacks-node/src/nakamoto_node/stackerdb_listener.rs` tallies `failed_txids` weight and "problematic transaction" weight per `reason_code`/`response_data.failed_txid` from `BlockRejection` messages to decide which transactions to treat as problematic: [6](#0-5) 
- `BlockAccepted.response_data` extend-timestamp fields are extracted and used by the listener as `tenure_extend_timestamp`/`read_count_extend_timestamp`: [7](#0-6) 

Since none of this data is signed, it can be modified without the signer's key while still presenting a "valid" signature over the associated `signer_signature_hash`, which can mislead the miner's transaction-problematic-tracking and tenure/read-count extension logic. I was not able to fully trace, within the available index, a concrete unauthenticated network path (outside the StackerDB chunk itself, which is separately signed by the slot owner) through which a third party — rather than the legitimate slot owner — could inject a tampered payload; this limits me to asserting a **cross-context-valid signature / incomplete digest** defect at the message layer rather than a demonstrated majority-free full end-to-end forgery by an unrelated party. Given the analog report's own framing (an under-covered digest is the bug, independent of a demonstrated end-to-end exploit chain), and the direct in-repo consequences on transaction-problematic tracking and tenure-extension bookkeeping, I rate this Medium/borderline for the "cross-context-valid signature" bucket, but flag the caveat above rather than asserting Critical impact with full confidence.

### Likelihood Explanation
Any signer, or any process capable of copying and re-serializing a previously broadcast `BlockRejection`/`BlockAccepted` message (which, once posted to StackerDB, is public information visible to all participants including miners and other signers), can trivially construct alternate byte-identical-signature messages with different `reason_code`/`response_data`/`metadata` content and have them accepted by `verify()`. No majority collusion, node access, or key compromise is required to produce a payload-mutated-but-signature-valid message once one genuine signature exists for a given `signer_signature_hash`.

### Recommendation
Include all semantically load-bearing fields of `BlockRejection` and `BlockAccepted` in the signed digest — not just `signer_signature_hash`/`chain_id`. Concretely:
- For `BlockRejection::hash()`, fold `reason_code` (or better, the full `RejectCode`/`RejectReason` discriminant and payload) and `response_data` (all of `reject_reason`, `tenure_extend_timestamp`-equivalent, `failed_txid`) into the Clarity tuple/`Value` that gets hashed via `structured_data_message_hash`, analogous to computing a proper `hashStruct` over the complete message.
- For `BlockAccepted`, replace signing raw `signer_signature_hash.bits()` with a digest that also commits to `response_data` (`full_extend_ts`, `read_count_extend_ts`) so tampering with the extend timestamps invalidates the signature.
- Add a discriminant/domain tag distinguishing "accepted" vs "rejected" content types in the digest itself, so accept/reject signatures cannot be structurally confused even if algorithms are later unified.

### Proof of Concept
Conceptual (cannot fully execute without a running node/testnet, but demonstrable purely from the code above):
1. Signer `S` legitimately rejects block `B` (hash `H`) with `RejectReason::ConnectivityIssues`, producing `BlockRejection { reason_code: ConnectivityIssues, response_data: { reject_reason: ConnectivityIssues, failed_txid: None, .. }, signature: sig, signer_signature_hash: H, chain_id, .. }`. `sig = private_key_S.sign(hash(H, chain_id))`.
2. Any observer of this broadcast message constructs `BlockRejection' { reason_code: ValidationFailed(ProblematicTransaction), response_data: { reject_reason: ValidationFailed(ProblematicTransaction), failed_txid: Some(some_target_txid), .. }, signature: sig (unchanged), signer_signature_hash: H (unchanged), chain_id (unchanged) }`.
3. `BlockRejection'.verify(&S_pubkey)` calls `hash()`, which only re-derives `structured_data_message_hash(H, chain_id-domain)` — identical to step 1's digest — so `verify()` returns `true`, i.e., `BlockRejection'` is accepted as an authentic message from `S` asserting that `some_target_txid` is problematic, which `S` never actually signed.         self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }
