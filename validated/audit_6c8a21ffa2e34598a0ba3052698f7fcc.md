### Title
`stopEpoch` pays only `epochDuration` of interest regardless of how long the epoch actually ran, so late epoch closes give the borrower free usage time and dilute tranche APR - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The external Zivoe bug — yield targets computed on a fixed `daysBetweenDistributions` while `distributeYield()` can be called late — maps directly onto the Idle epoch vault: expected epoch interest is fixed at `startEpoch` as `NAV * apr * epochDuration / 365 days`, while `stopEpoch` only requires `block.timestamp >= epochEndDate` and never re-prorates interest for the actual elapsed time. Any delay in stopping the epoch (keeper lag, borrower late repayment window, network congestion) means tranche holders earn the same absolute interest over a longer period, i.e. a permanently lower realized APR, while the borrower enjoyed the principal for free during the overrun.

### Finding Description
At `startEpoch`, the interest the borrower must return is locked in:

```solidity
int256 adjustedActiveInterest = int256(_calcInterest(getContractValue())) + interestForOverUnderPerformance;
expectedEpochInterest = pendingWithdrawFees + uint256(adjustedActiveInterest);
epochEndDate = block.timestamp + _epochDuration;
``` [1](#0-0) 

`_calcInterest` uses the configured `epochDuration`, not real elapsed time:

```solidity
return _amount * (_apr / 100) * epochDuration / (365 days * ONE_TRANCHE_TOKEN);
``` [2](#0-1) 

`stopEpoch` only checks that the end date has passed — there is no upper bound and no re-computation:

```solidity
!isEpochRunning || block.timestamp < epochEndDate || _pendingInstant() != 0 || ...
``` [3](#0-2) 

The borrower is then pulled `_expectedInterest` (or strategy tokens are minted in `isInterestMinted` mode), an amount fixed for `epochDuration` even if `block.timestamp - epochStart` is much larger [4](#0-3) .

The asymmetry is worsened because management fees *do* accrue on real elapsed time: `_accrueManagementFee` is checkpointed before the pull [5](#0-4) , and `IdleCreditVaultImpliedPrice` computes accrued management fee from `block.timestamp - latestHarvestBlock` while capping the interest accrual at `duration` [6](#0-5) . So during the overrun, fees keep growing while tranche yield is frozen, further eroding the tranche share.

By contrast, the programmable-borrower path is immune to this class because `ProgrammableBorrower._pendingBorrowerInterest` accrues on actual elapsed time [7](#0-6)  — confirming the fixed-duration model is a design choice, not a necessity.

### Impact Explanation
Identical loss math to the Zivoe finding: realized APR = target APR × `epochDuration / actualElapsed`. For a 30-day epoch stopped 1 day late, tranche holders lose ~3.2% of that epoch's yield; a 1-hour delay is ~0.14%. The loss is permanent for that epoch (the next epoch's interest is computed fresh from NAV) and the surplus effectively accrues to the borrower, who held the principal longer at no extra cost. There is no attacker profit requirement — unprivileged users are the victims; the trigger is ordinary operational delay of an honest manager/keeper or late borrower repayment, which cannot be prevented by users since `stopEpoch` is owner/manager-gated [8](#0-7) .

### Likelihood Explanation
Medium-low per instance but recurring: `stopEpoch` is a privileged, externally-triggered call subject to keeper lag, gas spikes, and multisig timing. Unlike Zivoe, users cannot self-serve the call. The borrower also has an instant-withdraw repayment window (`instantWithdrawDeadline`) that already tolerates intra-epoch delay [9](#0-8) , and nothing penalizes stopping late. Each epoch is an independent opportunity for drift, so cumulative APR erosion compounds across epochs.

### Recommendation
Prorate interest to actual elapsed time at `stopEpoch`: record `epochStartDate = block.timestamp` in `startEpoch`, and in `_stopEpoch` compute `elapsed = block.timestamp - epochStartDate` and pull `_calcInterestWithApr(getContractValue(), apr) * elapsed / epochDuration` (or store a per-second rate), instead of the fixed `expectedEpochInterest` when `_interest` is not overridden. Alternatively, apply a late-stop penalty rate to the borrower for time past `epochEndDate`. Ensure the management-fee checkpoint and `prepareStopEpochWithApr0` use the same elapsed basis to keep fee and interest accrual consistent.

### Proof of Concept
Foundry fork sketch against `IdleCDOEpochVariant` + `IdleCreditVault`:

```solidity
// deposits already made, buffer passed
vm.prank(manager);
cdoEpoch.startEpoch();                        // expectedEpochInterest = NAV*apr*30d/365d
uint256 expected = cdoEpoch.expectedEpochInterest();

// borrower repays late: warp 10 days past epochEndDate
vm.warp(cdoEpoch.epochEndDate() + 10 days);
deal(underlying, borrower, expected + pending);
vm.prank(manager);
cdoEpoch.stopEpoch(newApr, 0);                // pulls only `expected` (30 days of interest)

// NAV accrues 30 days of interest over a 40-day epoch => realized APR = 0.75 * target
assertLt(cdoEpoch.virtualPrice(AA), priceIfElapsedProrated);
```

Compare against a control run warped exactly to `epochEndDate`: `virtualPrice` is identical in both runs despite the extra 10 days of borrower usage, demonstrating that elapsed time is ignored.
