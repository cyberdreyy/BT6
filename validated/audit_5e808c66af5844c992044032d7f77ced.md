## Analysis

The `LendingPoolAddBank` accounts struct in `programs/marginfi/src/instructions/marginfi_group/add_pool.rs` derives all three vault token accounts as PDAs using only `bank.key()` as a seed component, with `bank` itself being an `init`-ed `AccountLoader` (i.e., a fresh keypair chosen and signed off-chain before the transaction is submitted): [1](#0-0) [2](#0-1) 

Since `LIQUIDITY_VAULT_SEED`/`INSURANCE_VAULT_SEED`/`FEE_VAULT_SEED` derivations depend only on the caller-chosen `bank` public key [3](#0-2) , once the `bank` keypair's public key is observable (e.g., visible in a simulated or pending transaction before confirmation), the three vault PDA addresses become fully computable off-chain by anyone. On Solana, `system_program::create_account` (used internally by Anchor's `init` for these PDA-seeded token accounts) fails with `AccountAlreadyInUse` if the destination address already holds a nonzero lamport balance. A third party can therefore send a trivial `SystemProgram::transfer` to one of the derived vault addresses between observation and confirmation, causing the subsequent `init` constraint to fail on-chain.

The instruction itself is gated by `has_one = admin @ MarginfiError::Unauthorized` on `marginfi_group` [4](#0-3) , so this is an admin-adjacent action, but the pre-funding transfer itself requires no privilege — any unprivileged actor with knowledge of the pending `bank` pubkey can perform it.

However, the practical impact is narrowly bounded: the `bank` account is a fresh, arbitrary keypair chosen freshly for each attempt (not a deterministic seed derived from mint or group), so the admin/caller can simply discard the griefed keypair and retry `lending_pool_add_bank` with a brand-new keypair, defeating the griefing at negligible cost (one new keypair, no funds lost, no partial state persists since `bank.load_init()` and vault inits either all succeed or the transaction reverts atomically). No value redirection, authorization bypass, or protocol-level freeze occurs — only a single disposable keypair is burned per attack attempt, and the attacker must expend lamports (griefing cost) for each attempt with no ability to recover them.

### Title
Front-runnable PDA pre-funding griefs a specific `LendingPoolAddBank` bank keypair attempt - (File: programs/marginfi/src/instructions/marginfi_group/add_pool.rs)

### Summary
The `liquidity_vault`, `insurance_vault`, and `fee_vault` PDAs in `LendingPoolAddBank` are derived solely from the caller-supplied `bank` pubkey, which is known before transaction confirmation. An unprivileged observer can pre-fund one of these PDAs with lamports to trigger Anchor's `init` constraint failure (`AccountAlreadyInUse`), blocking that specific bank-creation attempt.

### Finding Description
`bank` is an `init` `AccountLoader<Bank>` funded by a fresh keypair chosen client-side [5](#0-4) . The three vault accounts use `seeds = [..., bank.key().as_ref()]` with `init` [1](#0-0) . Because `bank.key()` is fixed and observable prior to confirmation (mempool/simulation), the vault addresses are fully predictable. A `system_transfer` of lamports to any one of these PDAs before the `lending_pool_add_bank` transaction lands causes the corresponding `init` account creation to fail with `AccountAlreadyInUse`, reverting the whole transaction (Anchor's `init` requires a zero-lamport, unallocated destination for the underlying `create_account` CPI). No signer, seed, or ownership check in the instruction defends against this because the vulnerability lies in generic Solana account-creation semantics, not in marginfi's authorization logic.

### Impact Explanation
The impact is limited to griefing a single, disposable `bank` keypair attempt. Because `bank` is a fresh arbitrary keypair (not a deterministic/seeded PDA tied to the mint or group), the admin/fee-payer can simply generate a new keypair and retry `lending_pool_add_bank` at negligible cost. No funds, authorization state, or persistent protocol state are affected; the transaction reverts atomically with no partial state, as the proof idea itself confirms (NO_VALUE_REDIRECTION). This does not durably block bank creation for a mint — only that one keypair is burned.

### Likelihood Explanation
Feasible in principle (requires observing the pending transaction's `bank` pubkey and racing a `system_transfer`), but each attempt only costs the attacker lamports with no way to recoup them, and the defender's remedy (pick a new keypair) is free and instantaneous. Repeated griefing does not scale into a durable protocol-level denial of service against admin bank creation.

### Recommendation
No protocol-level fix is required since the admin can trivially bypass this by using a fresh keypair per attempt; if desired, this could be documented as a known Solana account-creation quirk, or the instruction could optionally check vault-PDA lamport balance and emit a clearer error/retry hint. This is best characterized as a low-severity/informational griefing note rather than an exploitable protocol vulnerability.

### Proof of Concept
Integration test: (1) generate a `bank` keypair and compute the `liquidity_vault` PDA from `LIQUIDITY_VAULT_SEED` + `bank.pubkey()`; (2) send a `SystemProgram::transfer` of 1 lamport to that PDA address; (3) call `lending_pool_add_bank` with the same `bank` keypair and assert the transaction fails with `AccountAlreadyInUse`; (4) assert `bank` account remains uninitialized and no vault accounts were created (no partial state); (5) retry step 3 with a brand-new `bank` keypair and assert success, demonstrating trivial recovery.
