### Title
TOCTOU race in `Store.Open` allows two concurrent openers of the same masking store to derive different encryption keys - ([File: commands/helpers/internal/store/store.go])

### Summary
`store.Open(dir)` uses an unsynchronized check-then-act sequence across two separate files (`masking.db` and the derived `keyPath` key file) to bootstrap the encryption key used by `chacha20poly1305`. When two goroutines/processes call `Open` on the same `dir` concurrently on first creation, the `key2` file (`keyPath`) can be overwritten by the second caller after the first caller has already read it to derive its key, producing two different final keys for the same `masking.db` content.

### Finding Description
In `Open` [1](#0-0) , the existence check for `masking.db` and the writing of `keyPath` are not atomic with respect to a second concurrent caller. Consider two callers A and B that both call `Open(dir)` for the same `dir` (e.g., two `proxy-exec` invocations sharing `RUNNER_TEMP_PROJECT_DIR` for parallel job steps) at the moment `masking.db` does not yet exist:

1. A and B both `os.Stat(pathname)` and both see it does not exist.
2. A writes `keyPath` with `KA` (`os.WriteFile(keyPath, generateKey())`).
3. A calls `openFile(pathname)`, which creates the file; `f.Stat().Size()==0` is true, so A writes 32 random bytes (`K1`) into `masking.db`, seeks to 0, and syncs.
4. A calls `deriveEncryptionKey(f, keyPath)` [2](#0-1) , reading `K1` from the file and `KA` from `keyPath`. A's key becomes `K1 XOR KA`, and `Open` returns successfully to A.
5. B then executes its earlier-queued `os.WriteFile(keyPath, generateKey())`, overwriting `keyPath` with a new value `KB` (this branch was already selected by B in step 1, before A had created `masking.db`).
6. B calls `openFile(pathname)`; the file now exists with `K1` inside it (created by A), so the `info.Size() == 0` check is false and B does not rewrite the key material in `masking.db`.
7. B calls `deriveEncryptionKey`, reading the same `K1` from `masking.db` but reading `KB` (not `KA`) from `keyPath`. B's key becomes `K1 XOR KB`.

Because `KA != KB`, A and B end up with **different** `chacha20poly1305` keys for the same `masking.db`, even though both Stores point at the identical underlying file. There is no locking, no atomic rename for `keyPath`, and no re-validation of consistency between the two files — the check-then-act sequence spans `os.Stat`, `os.WriteFile`, `f.Stat().Size()`, `f.Write`, and a separate `os.ReadFile`, none of which are guarded by any mutex/file-lock across processes or goroutines.

### Impact Explanation
`masking.db` backs the phrase-masking store used by the `addmask` package to mask secrets in job trace output (`NewProxy` -> `addmask.New(db, stdout, stderr)`, `commands/helpers/proxy_exec.go` lines 45-59). If two `Store` handles for the same `dir` end up with different keys:
- Entries (`Add`) written using key `K1^KA` cannot be authenticated/decrypted by a `Store` using key `K1^KB` — `chacha20poly1305`'s AEAD `Open` call in `List` will fail with an "opening encrypted message" error (`commands/helpers/internal/store/store.go` lines 103-106), rather than silently decrypting to garbage.
- If that error is not fatal to the masking consumer (i.e., masking simply produces an incomplete/failed phrase list on error), secrets that were successfully registered by one proxy-exec process become unavailable to the masking engine used by the other process, so those secret phrases are not masked in the second process's stdout/stderr stream — resulting in secrets leaking into the job trace unmasked.

This matches the scoped impact class (secret masking exposing protected values in trace output).

### Likelihood Explanation
This requires: (1) two `proxy-exec` invocations (or two `Open` calls) targeting the exact same `dir` (the same `RUNNER_TEMP_PROJECT_DIR`) concurrently, and (2) the race window occurring specifically on the very first creation of `masking.db` — a narrow window that exists only once per job/dir, and only if two processes start `Open` before either has finished creating `masking.db`. This is plausible in scenarios where a job runs multiple steps or commands in parallel via `proxy-exec` sharing the same temp directory, but the race window is small (limited to first-time bootstrap) and timing-dependent, so it's a low-probability, hard-to-reliably-reproduce race rather than a deterministically triggerable exploit. I was not able to fully confirm from the available code how many parallel `proxy-exec` processes are typically spawned per job/step or whether the runner architecture guarantees serialized `dir` creation elsewhere (e.g., a step always calls bootstrap once before spawning proxies) — this would need further investigation to assess real-world exploitability precisely.

### Recommendation
Serialize `Store.Open` per `dir` using an OS-level file lock (e.g., `flock`) around the entire check-then-act sequence (stat/create `masking.db`, write/read `keyPath`), or use an atomic "create keyPath exclusively with `O_CREATE|O_EXCL`, and if it already exists, read the existing value" pattern instead of unconditionally overwriting `keyPath` when `masking.db` doesn't yet exist. This ensures every concurrent `Open` call for the same `dir` converges on the same `key2` value.

### Proof of Concept
```go
func TestStore_ConcurrentOpen_KeyConsistency(t *testing.T) {
    dir := t.TempDir()

    var wg sync.WaitGroup
    stores := make([]*Store, 2)
    errs := make([]error, 2)

    // Artificially widen the race window by having both goroutines
    // race through Open() concurrently on first creation.
    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func(i int) {
            defer wg.Done()
            stores[i], errs[i] = Open(dir)
        }(i)
    }
    wg.Wait()

    require.NoError(t, errs[0])
    require.NoError(t, errs[1])
    defer stores[0].Close()
    defer stores[1].Close()

    require.NoError(t, stores[0].Add("secret-from-A"))
    require.NoError(t, stores[1].Add("secret-from-B"))

    listA, errA := stores[0].List()
    listB, errB := stores[1].List()

    // Expected (bug): with racing keys, one of these List() calls fails
    // to decrypt entries written by the other store, or returns different
    // sets, proving key inconsistency for the SAME masking.db.
    require.NoError(t, errA)
    require.NoError(t, errB)
    require.ElementsMatch(t, []string{"secret-from-A", "secret-from-B"}, listA)
    require.ElementsMatch(t, []string{"secret-from-A", "secret-from-B"}, listB)
}
```
Note: because the race window is narrow, reliably triggering it may require injecting synchronization points (e.g., a test-only hook between `os.Stat(pathname)` and `os.WriteFile(keyPath, ...)`) to force the interleaving described above, rather than relying purely on goroutine scheduling.

func Open(dir string) (*Store, error) {
	pathname := filepath.Join(dir, "masking.db")
	sum := sha256.Sum256([]byte(pathname))
	keyPath := filepath.Join(dir, "runner"+hex.EncodeToString(sum[:]))

	_ = os.MkdirAll(filepath.Dir(pathname), 0o755)
	_, err := os.Stat(pathname)
	if err != nil {
		// store file doesn't exist, so re-generate key
		if err := os.WriteFile(keyPath, generateKey(), 0o644); err != nil {
			return nil, fmt.Errorf("writing key: %w", err)
		}
	}

func deriveEncryptionKey(f *os.File, keyPath string) ([]byte, error) {
	var key1 [32]byte
	if _, err := io.ReadFull(f, key1[:]); err != nil {
		return nil, err
	}

	key2, err := os.ReadFile(keyPath)
	if err != nil {
		return nil, err
	}

	if len(key2) < len(key1) {
		return nil, fmt.Errorf("key1 and key2 not the same size")
	}

	for i := 0; i < len(key1); i++ {
		key1[i] ^= key2[i]
	}

	return key1[:], nil
}
