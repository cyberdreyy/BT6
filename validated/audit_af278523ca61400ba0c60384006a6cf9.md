### Title
Second-pass `lchmod` in `ExtractZipArchive` can chmod an attacker-chosen symlink target instead of the original file - ([File: helpers/archives/zip_extract.go])

### Summary
`ExtractZipArchive` performs a two-pass extraction: pass 1 writes every file/symlink by `file.Name`, and pass 2 later re-iterates `archive.File` calling `lchmod(file.Name, file.Mode())` and `processZipExtra`. If two entries share the same `Name` — a regular file entry followed by a symlink entry — pass 1 leaves the path as a symlink, but pass 2's `lchmod` call for the earlier (regular-file) entry still uses that entry's non-symlink `Mode()`, causing the “no-symlink” guard in `lchmod` to be bypassed and the chmod to follow the symlink to whatever target the attacker specified.

### Finding Description
In `ExtractZipArchive` ( [1](#0-0) ), the first loop calls `extractZipFile` for every entry in order, and the second loop later calls `lchmod(file.Name, file.Mode())` for every entry, in the *original* archive order, independent of the final on-disk state.

`extractZipSymlinkEntry` explicitly removes whatever exists at `file.Name` and replaces it with a symlink ( [2](#0-1) ). So if the archive contains entry A (`Name="shared"`, regular file) followed by entry B (`Name="shared"`, symlink to some target path), after pass 1 the path `shared` is a symlink pointing to the attacker-chosen target, not a regular file.

In pass 2, `lchmod("shared", A.Mode())` is executed for entry A using A's original (regular-file) `os.FileMode`. On Linux, `lchmod` ( [3](#0-2) ) only skips the operation when `mode&os.ModeSymlink != 0`; since A's mode is a regular-file mode, this guard does not trigger, and `flags` remains `0` (no `AT_SYMLINK_NOFOLLOW` is set on Linux at all — it's only set in the non-Linux `else` branch). `unix.Fchmodat(unix.AT_FDCWD, "shared", uint32(A.Mode().Perm()), 0)` therefore follows the symlink and applies A's permission bits to whatever file the symlink (created later by entry B) points to. The symlink target string comes from B's file content and is never validated to stay within the extraction root (no check comparable to the `Name` sanitation logic exists for symlink target data). `processZipExtra`/`processZipTimestampField` similarly operates on `file.Name` using `os.Chtimes`, which also follows symlinks, compounding the issue for timestamp tampering on the same target.

This is a genuine ordering/TOCTOU bug: the second pass assumes each entry's `Name` still refers to the same object it created in the first pass, but a colliding `Name` from a later symlink entry invalidates that assumption for chmod/chtimes calls belonging to earlier entries.

### Impact Explanation
An attacker who controls the contents of a cache/artifact zip archive extracted by GitLab Runner (job cache download, artifact extraction) can craft an archive with a same-named regular-file entry followed by a symlink entry pointing to a path reachable by the runner process (e.g., a file inside the build directory tree, or, if the extraction root/CWD or relative traversal allows it, any file writable-then-followable by the runner user). The impact is limited to arbitrary `chmod`/`chtimes` (mode and mtime) on the symlink target with the mode bits from the unrelated first entry — not arbitrary write of content, since only chmod/chtimes cross the symlink, not the earlier `extractZipFileEntry` content write. This can be used to relax or tighten permissions on files reachable from the symlink target, e.g., making an existing world-writable/executable file the attacker can later abuse, within whatever filesystem privileges the runner process already has for that target.

### Likelihood Explanation
Reproducible deterministically: it only requires crafting a zip archive with two entries sharing an identical `Name`, ordered file-then-symlink, and controlling the symlink target string and the first entry's mode bits — all attacker-controlled inputs when the runner extracts an artifact/cache zip. No race condition or timing dependency is needed since it is enforced by the two fixed, sequential loops.

### Recommendation
In the second pass, `lstat` the path (or the `os.FileInfo` returned from the just-created object in pass 1) before calling `lchmod`/`processZipExtra`, and skip (or explicitly use `AT_SYMLINK_NOFOLLOW`/`Lchtimes`-style non-following) the operation whenever the on-disk entry at `file.Name` is currently a symlink, regardless of the *archive entry's* declared mode. Alternatively, track a mapping from `Name` to the specific object created for that Name (last write wins) and only apply chmod/chtimes metadata from the winning entry, or reject archives containing duplicate `Name` entries where types differ.

### Proof of Concept
```go
func TestExtractZipArchive_ChmodFollowsLaterSymlinkForSameName(t *testing.T) {
    dir := t.TempDir()
    victim := filepath.Join(dir, "victim")
    require.NoError(t, os.WriteFile(victim, []byte("data"), 0600))

    var buf bytes.Buffer
    zw := zip.NewWriter(&buf)

    // Entry A: regular file "shared" with permissive/unexpected mode
    fh := &zip.FileHeader{Name: "shared", Method: zip.Deflate}
    fh.SetMode(0644)
    w, _ := zw.CreateHeader(fh)
    _, _ = w.Write([]byte("content"))

    // Entry B: symlink "shared" -> victim, created after A
    sh := &zip.FileHeader{Name: "shared", Method: zip.Store}
    sh.SetMode(os.ModeSymlink | 0777)
    sw, _ := zw.CreateHeader(sh)
    _, _ = sw.Write([]byte(victim))

    zw.Close()

    old, _ := os.Getwd()
    _ = os.Chdir(dir)
    defer os.Chdir(old)

    r, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, ExtractZipArchive(r))

    info, err := os.Stat(victim)
    require.NoError(t, err)
    // Assert victim's mode was changed to A's 0644 via the symlink,
    // proving pass-2 lchmod for entry A crossed into entry B's symlink target.
    assert.Equal(t, os.FileMode(0644), info.Mode().Perm())
}
```
Expected assertion: `victim`'s permissions become `0644` (A's declared mode) purely because of the `lchmod("shared", A.Mode())` call in pass 2, despite `victim` never being named directly by any archive entry — confirming the cross-entry chmod redirection via a same-named, later-created symlink.

```go
func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}
```

```go
func lchmod(name string, mode os.FileMode) error {
	var flags int

	if runtime.GOOS == "linux" {
		// Linux does not support changing modes on symlinks.
		if mode&os.ModeSymlink != 0 {
			return nil
		}
	} else {
		flags = unix.AT_SYMLINK_NOFOLLOW
	}

	err := unix.Fchmodat(unix.AT_FDCWD, name, uint32(mode.Perm()), flags)
	if err != nil {
		return &os.PathError{Op: "lchmod", Path: name, Err: err}
	}
	return nil
}
```
