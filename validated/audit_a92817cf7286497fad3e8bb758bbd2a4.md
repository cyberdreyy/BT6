### Title
Missing upper-bound validation on attacker-controlled deposit `gas_limit` allows a forced, un-skippable deposit transaction to permanently halt L2 block derivation — ([File: crates/consensus/protocol/src/deposits.rs])

### Summary
`Deposits::unmarshal_v0` decodes the `gas_limit` field of an L1 `TransactionDeposited` event directly into the L2 `TxDeposit` with no upper-bound check against the L2 block gas limit. This deposit is then unconditionally placed into the derived block's forced (`no_tx_pool = true`) transaction list, which both the sequencer/builder and the verifier/proof executor are required to execute in full and cannot skip on failure — mirroring the ZetaChain report's root cause of an unvalidated, chain-specific outbound parameter that gets pushed into a mandatory processing queue and errors out downstream, blocking everything after it.

### Finding Description
`Deposits::unmarshal_v0` reads the `gas_limit` as a raw `u64` from L1-log-controlled bytes with no bound check: [1](#0-0) 

This deposit transaction is unconditionally appended to the derived L2 block's transaction list by the attributes builder (mandatory, not optional): [2](#0-1) 

When these attributes are executed with `no_tx_pool = true` (the normal derivation mode for non-sequencer-sourced transactions), any execution error — including a deposit whose `gas_limit` exceeds the available block gas — is propagated as a **fatal** error rather than silently skipped, by explicit design: [3](#0-2) [4](#0-3) 

Post-Regolith, deposits are subject to the same block-gas-limit check as ordinary transactions, and a deposit that exceeds the block's available gas triggers `TransactionGasLimitMoreThanAvailableBlockGas` / `BlockGasLimitExceeded`: [5](#0-4) [6](#0-5) 

The proof/verifier driver has a Holocene "deposit-only retry" fallback for exactly this class of failure, but it strips only *non-deposit* transactions and re-includes deposits unchanged: [7](#0-6) 

Because the poisoned transaction *is itself* a deposit, the deposit-only retry re-executes the same oversized-gas deposit and fails again, and the driver returns `DriverError::Executor(e)` — a hard failure with no further fallback: [8](#0-7) 

Since this L1 epoch's deposit must be included at a fixed position (deposits cannot be reordered or dropped like pool transactions), every subsequent L2 block that depends on this epoch/derivation step is blocked — this is the structural analog to the ZetaChain bug: an attacker-controlled, insufficiently-validated field forces itself into a strict, un-skippable processing queue and the resulting execution error blocks all subsequent processing.

The project's own internal review guide explicitly flags this exact failure class as a known critical pattern ("Strict derived-attributes / `no_tx_pool=true` path... Do not silently skip consensus-derived invalid input... Divergence is critical"), corroborating that this is a recognized, high-severity risk surface rather than a benign design choice: [9](#0-8) 

### Impact Explanation
If an unbounded/oversized `gas_limit` deposit (from any depositor calling the L1 deposit contract) is not otherwise bounded before this L2 derivation stage, it produces a mandatory, un-skippable transaction that fails execution both in the sequencer/builder and — critically — in the verifier/proof-executor's deposit-only fallback. This halts L2 derivation and the fault-proof program's execution of that epoch, i.e. a node/chain halt and a stuck safe/fault-proof pipeline, matching the accepted impact classes (node halt, wrong/unattainable provable output).

### Likelihood Explanation
Reaching this path only requires an unprivileged L1 depositor to submit a deposit whose opaque-data-encoded `gas_limit` is large; I could not verify from this repository (which contains only the L2 rollup-node/derivation code, not the L1 `OptimismPortal`-equivalent Solidity contract) whether an upstream L1 contract already bounds the deposit `gas_limit` via resource metering before emission. Per the task's explicit scope, "derivation of attacker-written L1 deposit ... data" is to be treated as an in-scope, attacker-controlled input, and no bound is enforced anywhere in the L2 derivation/decoding code shown above (`unmarshal_v0`, `derive_deposits`, the attributes builder). This uncertainty about L1-side enforcement is the main open question I could not resolve with the available tools.

### Recommendation
Add an explicit upper-bound check on `TxDeposit.gas_limit` during deposit decoding/derivation (e.g., in `Deposits::unmarshal_v0` or immediately after, in `derive_deposits`), rejecting or clamping deposits whose gas limit exceeds a safe fraction of the L2 block gas limit, so that a single malformed/adversarial deposit cannot become an un-skippable, block-halting transaction in either the sequencer/builder or the fault-proof executor paths.

### Proof of Concept
Conceptual (repository-derived) PoC:
1. An L1 depositor calls the deposit contract with opaque data encoding `gas_limit = u64::MAX` (or any value greater than the L2 block gas limit).
2. `Deposits::decode` / `unmarshal_v0` accepts this value unchecked and produces a `TxDeposit` with that `gas_limit`.
3. `derive_deposits`/`prepare_payload_attributes` forces this deposit into the next L2 block's transaction list with `no_tx_pool = true`.
4. During execution (`execute_sequencer_transactions`, post-Regolith), the reserved gas exceeds the block's available gas, producing a fatal `BlockGasLimitExceeded`/`TransactionGasLimitMoreThanAvailableBlockGas` error, which propagates as `PayloadBuilderError::EvmExecutionError` rather than being skipped.
5. On the proof/verifier side, `execute_payload` fails, the Holocene deposit-only retry re-includes the same failing deposit and fails again, and `DriverError::Executor(e)` is returned, halting derivation for that epoch and all subsequent blocks depending on it.

    pub fn execute_transaction(&mut self, tx: &Recovered<BaseTxEnvelope>) -> HandlerResult<()> {
        let ty = tx.ty();
        let is_deposit = tx.is_deposit();
        let signer = tx.signer();

        // Reject a transaction whose reserved gas exceeds the block's remaining gas, before
        // executing it. For an EIP-8130 transaction the reservation adds the payer's worst-case
        // authentication gas (metered on top of the sender-signed gas limit), matching the
        // reference `reserved_block_gas`. Pre-Regolith deposits are exempt (matching the reference's
        // `is_regolith || !is_deposit` guard); every other transaction is checked.
        let mut reserved_gas = tx.gas_limit();
        if let Some(signed) = tx.as_eip8130() {
            let payer_auth =
                IntrinsicGas::max_payer_auth_cost(signed).map_err(HandlerError::external)?;
            reserved_gas = reserved_gas.saturating_add(payer_auth);
        }
        let block_gas_limit = self.evm.block().gas_limit.saturating_to::<u64>();
        let block_available_gas = block_gas_limit.saturating_sub(self.gas_used);
        let is_regolith =
            (self.evm.config_spec_id().upgrade() as u8) >= (BaseUpgrade::Regolith as u8);
        if reserved_gas > block_available_gas && (is_regolith || !is_deposit) {
            return Err(HandlerError::external(BlockGasLimitExceeded {
                transaction_gas_limit: reserved_gas,
                block_available_gas,
            }));
        }
