### Title
`collectWithdrawFunds` applies the stop-epoch loss haircut to aggregate `pendingWithdraws`, but `lossRecoveryPriceByEpoch` and the claim path are keyed to a single epoch — earlier-epoch receipts claim at par and drain funds owed to haircutted claimants - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
When `stopEpochWithDuration` realizes a loss, `IdleCreditVault.collectWithdrawFunds` computes one `lossRecoveryPrice` over the **aggregate** `pendingWithdraws` basis (all unclaimed receipts from all epochs) but stores it under only the current `epochNumber`. Claims resolve haircuts strictly per request-epoch key: a receipt booked under an earlier epoch finds `lossRecoveryPriceByEpoch[oldEpoch] == 0` and falls through to `_claimFundedWithdrawRequest`, which pays the full par basis from the same underfunded strategy balance. The overpayment is a direct transfer from the haircutted claimants' funded pool — an exact analog of a settlement routine that treats an aggregate bitmap uniformly at one step (funding) while demanding exact per-bucket membership at another (claiming).

### Finding Description
- `requestWithdraw` records receipts per epoch: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `lastWithdrawRequest[_user] = currentEpoch` (`contracts/strategies/idle/IdleCreditVault.sol:282-293`). Nothing forces a user to claim a *fully funded* receipt before requesting again; the re-request guard at lines 263-271 only fires when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`.
- At `stopEpochWithDuration(_lossAmount)`, `previewLossAdjustedWithdrawFunds` splits the loss pro rata over `activeBasis + pendingBasis` where `pendingBasis = pendingWithdraws` is the sum of **all** unclaimed receipts across epochs (lines 440-459). `collectWithdrawFunds` then stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` under a single key and zeroes the whole `pendingWithdraws` aggregate (lines 411-421).
- On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 789-800). A user whose receipt sits in an earlier epoch `E1` (whose `lastWithdrawRequest` was overwritten to `E2`, or a different user whose `lastWithdrawRequest` is `E1`) finds a zero price under `E1`, returns 0, and `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` in full (lines 319-349) — even though the underlying collected from the borrower only covers `lossRecoveryPrice` of that aggregate basis.
- Concretely: user A requests in epoch E1 and does not claim after the E1 stop (claims are permissionless afterward, line 320-324). In epoch E2, A (or B) requests again; `pendingWithdraws = A_E1 + X_E2`. A loss at the E2 stop funds only `(A_E1 + X_E2) * p`. A claims: `_clearWithdrawClaimForEpoch(E2)` pays `X_E2 * p`, then `_claimFundedWithdrawRequest` pays `A_E1` at par — but only `A_E1 * p` was funded for it. Total paid exceeds `defaultRecoveryReserve`-guarded funded balance accounting only via raw `safeTransfer`, so the excess comes out of underlying reserved for the remaining haircutted claimants, who then cannot be paid in full.

### Impact Explanation
Direct theft / insolvency of pending-withdrawal funds: the claimant with a pre-loss-epoch receipt receives `(1 - lossRecoveryPrice) * priorEpochBasis` more than was funded, permanently reducing the strategy balance available to pay other loss-adjusted receipts. The `_transferFundedClaim` reserve guard (lines 897-907) only protects `defaultRecoveryReserve`, not the loss-adjusted pool, so it does not stop the overpayment.

### Likelihood Explanation
Requires no attacker privilege beyond being a lender: (1) request withdraw in epoch E1 and let the E1 stop fund it fully without claiming (permitted indefinitely); (2) any loss-realizing `stopEpochWithDuration` in a later epoch while that receipt is still pending. The funding haircut then silently under-covers the E1 receipt while the claim path pays it at par. Any haircut `p < 1` quantifies the theft as `(1-p)` times the stale receipt basis.

### Recommendation
Track the loss-adjusted basis per epoch instead of per aggregate: in `collectWithdrawFunds`, store the haircut alongside the set of pending epochs (or store a global `pendingWithdraws` that excludes already-funded prior-epoch receipts and apply the haircut only to the current epoch's `withdrawsRequestsByEpoch`/`apr0` buckets). Alternatively, snapshot each user's aggregate basis into their latest request epoch at `stopEpoch` time so every receipt contributing to `pendingBasis` resolves under the epoch key that stores `lossRecoveryPrice`, or require claim of all funded receipts before any later request (extend the guard at lines 263-271 to `withdrawsRequests[_user] != 0`).

### Proof of Concept
Foundry fork scenario (sketch):
```solidity
// Setup: credit vault + epoch CDO, lender A and B whitelisted.
// Epoch E1: A deposits, epoch runs, stops cleanly. A requestWithdraw(amountA) in buffer -> E1.
// E1 stop already happened; A's receipt recorded under epochNumber = N.
// Next: B deposits; startEpoch (epoch N). During buffer of epoch N+1 A does NOT claim;
// B requestWithdraw(amountB) in epoch N+1 buffer? Simpler: A requests again in epoch N+1
// after N's stop bumped epochNumber to N+1 (lastWithdrawRequest[A] := N+1).
// Manager calls stopEpochWithDuration(newApr, 0, duration, lossAmount) with lossAmount>0:
//   pendingBasis = A_E(N) + A_E(N+1); price p = funded/pendingBasis stored under key N+1.
// A calls claimWithdrawRequest():
//   _claimLossAdjustedWithdrawRequest uses lastWithdrawRequest = N+1 -> pays A_E(N+1)*p.
//   _claimFundedWithdrawRequest pays withdrawsRequestsByEpoch[A][N] remainder at par.
// Assert: A received A_N + A_{N+1}*p > p*(A_N + A_{N+1}); strategy balance now < sum of
// remaining haircutted claims (insolvency), quantified loss = (1-p)*A_N.
```
The invariant `sum(funded) == sum(loss-adjusted claims)` breaks because funding is aggregate while the haircut lookup is keyed to exactly one epoch — mirroring the Notional bug where boundary settlement assumed exact bit alignment for some assets but not others.
