## Finding Assessment: Valid, but different mechanism than proposed

The specific claim in the question — that `switch_operator_with_same_commission` mixes two operators' distributions in one `pool_u64` such that "which recipient can withdraw which portion" becomes corrupted — is **not** accurate as stated. `pool_u64::Pool` (and the `distribution_pool` in `StakingContract`) is explicitly designed to hold multiple independent shareholders (staker address, operator address) simultaneously; `shares`/`redeem_shares`/`buy_in` are keyed per-address and each shareholder's balance is isolated, as shown by `pool_u64.move`'s own multi-shareholder tests. [1](#0-0) [2](#0-1) 

However, there is a real, related accounting flaw triggered by the same code path: `switch_operator_with_same_commission` moves the `StakingContract` (and its `distribution_pool`) from the `old_operator` key to the `new_operator` key, while any not-yet-redeemed commission shares owned by `old_operator` remain in the pool under `old_operator`'s address. [3](#0-2) 

`update_distribution_pool` — invoked on every subsequent `add_distribution`/`distribute_internal` call with the *current* operator address as a parameter — charges "commission" on any balance growth to every shareholder **except** the address equal to the currently passed-in `operator`: [4](#0-3) 

Since `old_operator`'s un-redeemed shares are indistinguishable (by address) from a regular staker's shares once the contract is re-keyed to `new_operator`, any subsequent pool-value growth (e.g. more stake becoming inactive because the staker calls `unlock_stake`, or the new operator calls `request_commission`) causes `old_operator`'s already-earned, unpaid commission to be silently diluted/transferred to `new_operator` via `pool_u64::transfer_shares` inside `update_distribution_pool`. This happens purely because the dilution-exemption check compares against the *current* `operator` argument, not against "is this shareholder actually a past-or-present operator entitled to their own commission."

This is reachable purely by an unprivileged staker's normal sequence of calls (`switch_operator_with_same_commission` followed by ordinary `unlock_stake`/`add_stake`/`request_commission` activity) with no special privilege beyond staker ownership of their own `StakingContract`, and it changes who ultimately receives commission value, matching the "commission state must preserve value" requirement.

### Title
Unclaimed operator commission is misattributed to the new operator after `switch_operator_with_same_commission` due to address-based dilution check in `update_distribution_pool` - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`switch_operator_with_same_commission`/`switch_operator` re-key a `StakingContract`'s `distribution_pool` from `old_operator` to `new_operator` while leaving `old_operator`'s pending, un-redeemed commission shares inside the same pool. `update_distribution_pool` only exempts the address matching the *currently invoked* operator parameter from commission dilution, so subsequent pool growth silently transfers part of `old_operator`'s already-earned commission to `new_operator`.

### Finding Description
`request_commission_internal` records the operator's earned commission as pool shares keyed by the operator's address via `add_distribution`/`buy_in`. [5](#0-4) 
When `switch_operator*` is called, `distribute_internal` and `request_commission_internal` are run once for `old_operator` before the `StakingContract` struct (including its `distribution_pool`) is moved to the `new_operator` key. [3](#0-2) 
If `old_operator`'s just-requested commission has not yet fully unlocked/been redeemed, its shares remain in the pool under `old_operator`'s address. Every later `add_distribution`/`distribute_internal` call (invoked with `operator = new_operator`) runs `update_distribution_pool`, which walks all shareholders and, for every shareholder whose address differs from the passed-in `operator`, computes commission on any balance growth and transfers those shares to `operator`. [4](#0-3) 
Since `old_operator` no longer equals the current `operator` parameter, its leftover commission shares are treated like ordinary staker principal and get partially transferred to `new_operator`.

### Impact Explanation
This misroutes already-earned commission value from a former operator to whichever operator currently controls the (re-keyed) `StakingContract`, without either party's consent, each time the pool's `total_coins` changes after a switch. This directly violates the requirement that commission accounting preserve value and rightful withdrawal recipients across role/epoch transitions.

### Likelihood Explanation
Reachable with only staker-level privileges: it requires the staker to call `switch_operator_with_same_commission` (or `switch_operator`) while the old operator has pending, unredeemed commission, followed by ordinary subsequent activity (`unlock_stake`, `add_stake`, or the new operator's own `request_commission`) that increases the pool's `total_coins`. No governance or pool-ownership privilege is needed beyond what a staker already has over their own contract.

### Recommendation
`update_distribution_pool`'s dilution-exemption should track which shareholder addresses represent "past or present operator commission" entries explicitly (e.g., tag shares by role rather than by comparing to the single current `operator` parameter), or `old_operator`'s pending shares should be force-redeemed/paid out (not merely have `distribute_internal`/`request_commission_internal` invoked, but fully drained/settled) before the `StakingContract` is re-keyed to `new_operator`.

### Proof of Concept
1. Staker creates a staking contract with `operator_1`, accrues rewards.
2. `operator_1` (or staker via `unlock_stake`) triggers `request_commission_internal` implicitly with a pending, not-yet-inactive commission amount for `operator_1`.
3. Staker calls `switch_operator_with_same_commission(staker, operator_1, operator_2)` — this force-runs `distribute_internal`+`request_commission_internal` for `operator_1`, leaving unredeemed shares under `operator_1`'s address inside the pool now keyed to `operator_2`.
4. Advance an epoch so more stake becomes inactive/pending_inactive; staker calls `unlock_stake(staker, operator_2, amount)`, which calls `add_distribution`→`update_distribution_pool` with `operator = operator_2` and a larger `updated_total_coins`.
5. Assert: `pool_u64::balance(distribution_pool, operator_1)` after step 4 is less than what it was right after step 3 (i.e., `operator_1`'s recorded commission balance shrank), while `pool_u64::balance(distribution_pool, operator_2)` increased correspondingly — demonstrating value leaked from the old operator to the new operator purely due to the address-based exemption check in `update_distribution_pool`.

    fun update_distribution_pool(
        distribution_pool: &mut Pool,
        updated_total_coins: u64,
        operator: address,
        commission_percentage: u64
    ) {
        // Short-circuit and do nothing if the pool's total value has not changed.
        if (distribution_pool.total_coins() == updated_total_coins) { return };

        // Charge all stakeholders (except for the operator themselves) commission on any rewards earnt relatively to the
        // previous value of the distribution pool.
        let shareholders = &distribution_pool.shareholders();
        shareholders.for_each_ref(
            |shareholder| {
                let shareholder: address = *shareholder;
                if (shareholder != operator) {
                    let shares = pool_u64::shares(distribution_pool, shareholder);
                    let previous_worth = pool_u64::balance(distribution_pool, shareholder);
                    let current_worth =
                        pool_u64::shares_to_amount_with_total_coins(
                            distribution_pool, shares, updated_total_coins
                        );
                    let unpaid_commission =
                        (current_worth - previous_worth) * commission_percentage / 100;
                    // Transfer shares from current shareholder to the operator as payment.
                    // The value of the shares should use the updated pool's total value.
                    let shares_to_transfer =
                        pool_u64::amount_to_shares_with_total_coins(
                            distribution_pool, unpaid_commission, updated_total_coins
                        );
                    pool_u64::transfer_shares(
                        distribution_pool, shareholder, operator, shares_to_transfer
                    );
                };
            }
        );

        distribution_pool.update_total_coins(updated_total_coins);
