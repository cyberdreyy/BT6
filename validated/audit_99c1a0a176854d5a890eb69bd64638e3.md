### Title
Unprivileged APR0 withdraw request permanently bricks `stopEpoch` once APR is raised above 0 - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`, but the only code path that clears `apr0TotalPrincipal` sits after that same revert. Any lender can open a dust-size withdraw request during an APR-0 period, and every subsequent `stopEpoch` called while `unscaledApr` is non-zero reverts. Epoch settlement, interest accrual, and all pending withdrawal claims stall until the manager lowers APR back to 0 and successfully stops an epoch.

### Finding Description
In `IdleCreditVault.sol`, a withdraw request made while `unscaledApr == 0` is routed to `_requestWithdrawApr0`, which adds `_amount` to the global `apr0TotalPrincipal` bucket ( [1](#0-0) , [2](#0-1) ). At `stopEpoch`, `prepareStopEpochWithApr0` computes the APR0 interest allocation. It contains a livelock:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
...
// Close current APR0 bucket so it cannot accrue again on later stopEpoch calls.
apr0TotalPrincipal = 0;
``` [3](#0-2) [4](#0-3) 

The bucket is only zeroed on the success path, after the `unscaledApr != 0` revert. So once (a) any user holds an open APR0 request and (b) APR is non-zero, `prepareStopEpochWithApr0` reverts on every call, `apr0TotalPrincipal` is never cleared, and the condition remains true forever. This is the credit-vault analog of the reported NULL-deref/UAF availability flaw: a single authenticated, unprivileged action poisons shared state so that a routine privileged operation deterministically crashes (reverts).

The attacker needs nothing special: `_requestWithdrawApr0` is reached by any KYC-passing lender calling `IdleCDOEpochVariant.requestWithdraw` while `unscaledApr == 0`, even for 1 wei of tranche tokens ( [5](#0-4) ). No existing guard prevents it — `requestWithdraw`'s NotAllowed checks only cover duplicate receipts/loss epochs, and nothing validates that APR0 requests must be claimed before APR can rise. `_settleApr0` deliberately leaves the bucket untouched when `principalEpoch >= epochNumber` ( [6](#0-5) ), so claiming the receipt before the request epoch ends does not remove the pending principal either.

### Impact Explanation
Temporary freezing of the entire vault. While the condition holds:

- `stopEpoch` always reverts, so `epochNumber` never increments, `expectedEpochInterest` is never paid out, and the epoch state machine halts mid-epoch.
- All `claimWithdrawRequest` calls revert at the `epochNumber <= lastWithdrawRequest[_user]` gate ( [7](#0-6) ), so every pending receipt (principal + interest, net of fees) is frozen regardless of attacker size.
- A dust request (e.g. 1 wei of underlying equivalent) freezes the whole TVL plus all pending receipts.

Recovery requires the honest manager to notice, call `setAprs(0, 0)`, and run a full epoch at 0% APR to clear the bucket — meaning lenders lose at least one epoch of yield and borrowers/managers lose the ability to run a non-zero-APR epoch on schedule. An attacker can also re-poison the bucket each APR0 epoch at near-zero cost, repeatedly stalling rate changes.

### Likelihood Explanation
High triggerability, moderate occurrence in practice. The preconditions — an APR-0 epoch followed by the manager raising APR — are a normal operational transition (protocols routinely move off 0% promotional/distressed rates). Any single lender (including a griefing attacker with dust) can arm the trap during the APR0 window, and there is no warning or guard: the first `stopEpoch` under the new APR simply reverts, as does every retry. Cost to the attacker is gas plus a dust deposit; cost to the protocol is a stalled epoch and frozen claims.

### Recommendation
Decouple the liveness of `stopEpoch` from the APR-transition invariant. Concretely:

- In `prepareStopEpochWithApr0`, do not revert when `unscaledApr != 0`. Instead, settle the APR0 bucket with zero rate for the new epoch (the requests were priced under APR 0; they should simply accrue no APR0 interest for epochs where APR > 0, matching the comment that the bucket "is only valid while APR is 0"), then clear `apr0TotalPrincipal`.
- Alternatively, move `apr0TotalPrincipal = 0` before the revert check and skip only the interest allocation, so the bucket always closes at the epoch boundary.
- Optionally record the APR at request time in `Apr0UserData`/`apr0RateByEpoch` so APR0 requests accrue only for epochs in which APR was actually 0.

### Proof of Concept
Foundry fork test sketch (extends the existing `IdleCreditVault.t.sol` harness):

```solidity
function testApr0DustRequestBricksStopEpochAfterAprRaise() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // APR = 0 epoch

    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // run epoch 0
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, 0);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // attacker: dust withdraw request during buffer (unscaledApr still 0)
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // tiny amount, adds to apr0TotalPrincipal

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    assertGt(vault.apr0TotalPrincipal(), 0);

    // start epoch 1, manager restores APR > 0 for the next epoch
    _startEpochAndCheckPrices(1);
    vm.prank(manager);
    vault.setAprs(initialProvidedApr, initialProvidedApr);

    // every stopEpoch now reverts in prepareStopEpochWithApr0 -> funds frozen
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // all pending withdraw claims are stuck (epochNumber cannot advance)
    vm.prank(attacker);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
}
```

Note on confidence: the revert path in `prepareStopEpochWithApr0` is verified directly in the source. The exact call ordering inside `stopEpoch`/`setAprs` in `IdleCDOEpochVariant` was not fully re-verified line-by-line within the tool budget; the PoC assumes `setAprs` is callable between epochs by the manager (as in existing tests, e.g. `testApr0WithdrawGetsInterestAtStopEpoch`) and that `stopEpoch` invokes `prepareStopEpochWithApr0` unconditionally. The fix direction holds regardless of ordering, since the bucket can only be cleared on the reverting path.
