### Title
`parse_signers` misreports single-key `authority`/`owner` as `multisigAuthority`/`multisigOwner` based on account-count heuristic instead of on-chain multisig state - (File: transaction-status/src/parse_token.rs)

### Summary
`parse_signers` in `transaction-status/src/parse_token.rs` decides whether a Transfer/Approve/Revoke/etc. authority is a multisig by comparing the number of accounts supplied in the *instruction* to a fixed minimum, not by checking whether the authority account is actually a `Multisig`-owned account on-chain. An attacker can submit a valid, successfully-executing SPL Token instruction that uses a plain single-key authority but includes one or more extra, unused account references, causing the JSON-parsed RPC response to mislabel the authority as a multisig and fabricate a bogus `signers` list.

### Finding Description
`parse_token` calls `check_num_token_accounts(&instruction.accounts, N)` which only enforces `accounts.len() >= N` [1](#0-0) . For `Transfer`, `Approve`, `Revoke`, `Burn`, `MintTo`, `CloseAccount`, etc., after this minimum-length check, `parse_signers` is invoked with `last_nonsigner_index` set to the last "fixed" account index (e.g. 2 for `Transfer`) [2](#0-1) .

`parse_signers` itself makes the multisig-vs-single-owner decision purely from the instruction's account-list length:
```
if accounts.len() > last_nonsigner_index + 1 {
    // treat accounts[last_nonsigner_index] as the multisig account
    // and accounts[last_nonsigner_index+1..] as signers
} else {
    // treat accounts[last_nonsigner_index] as the plain owner/authority
}
``` [3](#0-2) 

This does not match how the real SPL Token program determines multisig status at runtime: the token program's `validate_owner` logic checks whether the authority account itself is owned by the token program and has the `Multisig` account layout (an on-chain state check), and only then consumes the "remaining accounts" as signer inputs; it does not care how many extra account metas were included in the instruction. Consequently, a transaction can legally include extra, unused account references after the fixed set of accounts required by an instruction (Solana's runtime does not require that every referenced account key actually be consumed by the invoked instruction handler). Such a transaction:
- Uses a normal single-key (non-multisig) authority at `accounts[last_nonsigner_index]`, which is a signer of the transaction and satisfies the token program's non-multisig `is_signer` check.
- Includes one or more additional account keys (`accounts[last_nonsigner_index+1..]`) that are never read or validated by the token program for this instruction.

Because `check_num_token_accounts` only enforces a minimum, and `parse_signers` only compares lengths, this extra padding account causes `parse_signers` to take the "multisig" branch: it reports the real (single-key) authority under `multisigAuthority` instead of `authority`/`owner`, and fabricates a `signers` array containing the padding account keys, even though the token program never checked or required those keys as signers.

### Impact Explanation
This is a decoder misreporting bug matching the stated bounty scope: "An unprivileged attacker can decode instruction ... data into an incorrect but plausible parsed result, misreporting ... authority ... to downstream integrators." Any client calling `getTransaction`/`getConfirmedTransaction`/`getBlock` with `encoding: jsonParsed` for such a transaction will receive a `parsed` instruction object with the wrong classification of authorization scheme (`multisigAuthority`/`signers` instead of `authority`), which can mislead wallets, explorers, or accounting/compliance tooling into believing a multisig-controlled transfer occurred with specific co-signers, when in fact a single key authorized it and the listed "signers" played no cryptographic role in the transfer's authorization.

### Likelihood Explanation
Fully attacker-controlled and requires no special privileges: the attacker only needs to construct and submit (via a single `sendTransaction` call) an SPL Token instruction (e.g. `Transfer`) with one extra, unused account key appended to the instruction's account list, then later query it via a single `getTransaction(jsonParsed)` RPC call. This is deterministic and 100% repeatable for any instruction type that funnels through `parse_signers` (`Transfer`, `Approve`, `Revoke`, `Burn`, `MintTo`, `CloseAccount`, `FreezeAccount`, `ThawAccount`, `SetAuthority`, `*Checked` variants, `WithdrawExcessLamports`, `UnwrapLamports`). The only precondition is that the underlying SPL Token program permits extra unused account metas in the instruction (which it does, since it simply iterates accounts it needs and ignores the rest).

### Recommendation
`parse_signers` (and the RPC-facing parsers in general) cannot reliably determine multisig status without reading the actual account data of the authority account, which is not available to this pure instruction-decoding code. Two options:
1. Document explicitly that the "multisig" heuristic is best-effort and can be wrong when transactions include extra/unused account references, and treat `parse_token` output as advisory only (least invasive, matches existing architecture).
2. If stronger correctness is desired, have callers with account-state access (e.g., in `solana-account-decoder`/RPC context where account data can be fetched) verify that the account at `accounts[last_nonsigner_index]` is actually program-owned and matches the `Multisig` account layout before labeling it `multisigAuthority`, falling back to `authority` otherwise. This requires plumbing account state into the parser, which is a larger architectural change.

// transaction-status/src/parse_token.rs (test module)
#[test]
fn test_parse_signers_misreports_padded_transfer_as_multisig() {
    use {
        super::*, solana_instruction::Instruction, solana_message::Message,
        solana_pubkey::Pubkey,
    };

    let source = Pubkey::new_unique();
    let destination = Pubkey::new_unique();
    let authority = Pubkey::new_unique(); // single-key authority, IS a signer
    let padding_account = Pubkey::new_unique(); // never checked by token program

    // Build a Transfer instruction manually with an extra, unused account
    // appended after [source, destination, authority].
    let program_id = spl_token_2022_interface::id();
    let mut ix = spl_token_2022_interface::instruction::transfer(
        &program_id, &source, &destination, &authority, &[], 100,
    )
    .unwrap();
    ix.accounts.push(solana_instruction::AccountMeta::new_readonly(padding_account, false));

    let message = Message::new(&[ix], None);
    let compiled_instruction = &message.instructions[0];
    let account_keys = AccountKeys::new(&message.account_keys, None);

    let parsed = parse_token(compiled_instruction, &account_keys).unwrap();
    let info = parsed.info.as_object().unwrap();

    // BUG: the parser reports the plain single-key authority as a multisig
    // authority and invents a "signers" list, even though `padding_account`
    // was never validated as a signer by the SPL Token program.
    assert!(info.contains_key("multisigAuthority"), "expected mislabeled multisigAuthority");
    assert!(info.contains_key("signers"));
    assert!(!info.contains_key("authority"), "real 'authority' field is missing/mislabeled");

    // Desired (currently failing) invariant: for a non-multisig authority,
    // the reported field should be "authority", equal to `authority`, and
    // there should be no fabricated "signers" list.
    // assert_eq!(info["authority"], authority.to_string());
    // assert!(!info.contains_key("multisigAuthority"));
}
```
Additional invariant test: enumerate `accounts.len()` from the minimum required (e.g. 3 for `Transfer`) up to +3 extra padding accounts, and assert that `parse_signers`'s classification (`owner_field_name` vs `multisig_field_name`) only changes based on whether the authority account is truly a `Multisig`-owned account on-chain — which this pure length-based heuristic in `transaction-status/src/parse_token.rs` cannot verify, demonstrating the misclassification for every padded, non-multisig case.

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
