### Title
Response cache key in the HTTP capability gateway handler is not scoped by `WorkflowID`, causing cross-workflow response cache confusion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's outbound HTTP response cache is documented as being "scoped by workflow ID to prevent cross-workflow data leakage," but the actual cache key (`OutboundHTTPRequest.Hash()`) excludes `WorkflowID` and only includes method, URL, headers, body, and `WorkflowOwner`. As a result, an outbound HTTP action request from one workflow can be served the cached response that was fetched and stored on behalf of a completely different workflow (same owner), analogous to the referenced report where a user ends up receiving a completely different result than the one they specifically requested, due to a lack of a binding/identity check tying the request to the exact context that produced it.

### Finding Description
The `responseCache` explicitly documents itself as keying by "method, URL, headers, body, workflowOwner": [1](#0-0) 

The `Fetch` and `Set` operations both key strictly off `req.Hash()`: [2](#0-1) [3](#0-2) 

The handler's own README, however, states the opposite guarantee: that the cache key is "generated from workflow ID and request hash" and is "scoped by workflow ID to prevent cross-workflow data leakage": [4](#0-3) 

The test suite confirms the actual (undocumented) behavior directly contradicts this: two requests differing only by `WorkflowID` hash to the *same* key, while `WorkflowOwner` is what actually differentiates the hash: [5](#0-4) 

The outbound path (`makeOutgoingRequest`) reads the `OutboundHTTPRequest` (including `WorkflowID`) submitted by a workflow-DON node and, when `CacheSettings.MaxAgeMs > 0`, calls `h.responseCache.Fetch(...)` keyed purely on `req.Hash()`: [6](#0-5) 

Because `WorkflowID` is not part of the hash, any two distinct workflows belonging to the same `WorkflowOwner` that happen to issue an outbound HTTP action with the same method/URL/headers/body will collide on the same cache entry. Whichever workflow's request populates the cache first "wins," and every other (unrelated) workflow with matching cache key parameters will receive that first workflow's cached response instead of making its own fetch — even though `CacheSettings.Store`/`MaxAgeMs` were set per-request by each individual workflow expecting workflow-scoped isolation.

### Impact Explanation
This breaks the workflow isolation the caching layer explicitly claims to provide. A workflow that expects a fresh, workflow-specific outbound HTTP response (e.g., because different workflow logic depends on identical-looking requests returning different results at different times, or because it wrongly assumes per-workflow isolation as documented) can instead be served stale/foreign data originating from another workflow under the same owner. This is a direct cross-workflow response-confusion bug: unprivileged workflow-DON traffic under a single owner can silently pollute or "poison" the shared cache entry consumed by sibling workflows, undermining data integrity guarantees the system advertises, and potentially causing a workflow to act on data it never actually requested/received from the external endpoint — mirroring the "different tray than the one you tried to acquire" class of bug (the caller ends up bound to someone else's produced result with no check tying the response back to the originating context).

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where a single workflow owner runs multiple distinct workflows that call the same external endpoint/method/body/headers with `CacheSettings.Store=true` and `MaxAgeMs>0` (a documented, encouraged usage pattern for reducing redundant outbound calls). No malicious or privileged actor is required — this occurs from normal concurrent usage by legitimate workflow nodes, and is deterministic given matching cache-key fields, not merely a theoretical race.

### Recommendation
Include `WorkflowID` in the cache key computation (`OutboundHTTPRequest.Hash()`), or otherwise namespace the cache map by `WorkflowID` (and/or `WorkflowExecutionID`, if per-execution granularity is desired) in addition to `WorkflowOwner`, method, URL, headers, and body. Update the README documentation to match the corrected, enforced isolation guarantee, and extend `response_cache_test.go` so it asserts that different `WorkflowID`s produce different hashes rather than asserting they collide.

### Proof of Concept
1. Workflow A (`WorkflowID = "wf-A"`, `WorkflowOwner = "0xabc"`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings:{Store:true, MaxAgeMs: 600000}}` and receives/caches response `R1`.
2. Workflow B (`WorkflowID = "wf-B"`, same `WorkflowOwner = "0xabc"`, same method/URL/headers/body/CacheSettings) issues the identical outbound request shortly after.
3. Per `TestRequestHash` (`response_cache_test.go` lines 139-149), `req.Hash()` for A and B are identical because `WorkflowID` is excluded from the hash. `Fetch` (response_cache.go lines 66-77) returns the cached entry keyed from Workflow A's request — Workflow B receives `R1` instead of making its own live request or getting a workflow-B-scoped result, despite the README's guarantee of workflow-ID cache isolation.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)

		if req.CacheSettings.MaxAgeMs > 0 {

		} else {

			if req.CacheSettings.Store {
