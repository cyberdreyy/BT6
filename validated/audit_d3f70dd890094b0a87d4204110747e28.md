### Title
Reverting `onStopEpoch` vault withdrawal permanently blocks `stopEpoch` and the default path, freezing all LP funds - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
In programmable-borrower mode, `IdleCDOEpochVariant._stopEpoch` calls `IProgrammableBorrower.onStopEpoch` and deliberately lets its reverts bubble. `ProgrammableBorrower.onStopEpoch` wraps `vault.withdraw(shortfall, ...)` in a try/catch that rethrows `StopEpochVaultLiquidityUnavailable` whenever the ERC4626 vault cannot service the withdrawal. An unprivileged user of that ERC4626 vault (an allowed attacker class: "a user of the programmable borrower's ERC4626 vault") can drain or keep the vault's liquidity exhausted, so every `stopEpoch` call reverts. Because the epoch never stops, `defaulted` is never set, `finalizeDefault`/`finalizeDefaultRecovery` cannot run, and no withdrawal receipt can ever be funded or claimed. This mirrors CVE-2026-29905: an unvalidated/unchecked external failure path turns a transient third-party error into a persistent protocol DoS.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` at lines 395-404 calls the borrower hook before the try/catch that triggers `_handleBorrowerDefault`: [1](#0-0) 

Inside `ProgrammableBorrower.onStopEpoch`, the economic shortfall check (`shortfall > _currentVaultAssets()` → `return true` → `transferFrom` fails → default) only covers the case where the *share valuation* is insufficient. When shares are sufficient but the vault's `withdraw` reverts (no liquid assets, paused markets, or a deliberately drained Morpho-style vault), the catch reverts instead of returning `false`: [2](#0-1) 

The comment says reverts "bubble so transient ERC4626 liquidity failures can be retried", but nothing distinguishes a transient failure from a persistent one. There is no retry budget, no fallback to default, and the owner cannot escape: `setIsProgrammableBorrower(false)` reverts while `isEpochRunning` (line 178), `stopEpoch` is the only way to clear that flag, and `_emergencyShutdown`/guardian flows pause the pool but do not fund or release withdrawal receipts.

### Impact Explanation
An attacker who is an ordinary ERC4626 vault user borrows/removes the vault's available liquidity (e.g., maxing out borrowable assets in the underlying Morpho markets) right before `epochEndDate`, then keeps it drained with minimal cost whenever liquidity returns. Every `stopEpoch`/`stopEpochWithDuration` call reverts with `StopEpochVaultLiquidityUnavailable`. Consequences:

- `isEpochRunning` stays `true` → `startEpoch`, `setEpochParams`, `setIsProgrammableBorrower`, `claimWithdrawRequest` (epoch gating at `IdleCreditVault.sol:326`) all blocked.
- `defaulted` never becomes `true` → the entire recovery machinery (`finalizeDefault`, `finalizeDefaultRecovery`, `defaultRecoveryReserve`, `DefaultDistributor`) is unreachable even though the borrower-side funds are economically recoverable.
- All pending normal withdraw receipts (`pendingWithdraws`), instant receipts, and the full active NAV of AA and BB tranche holders remain frozen — quantified loss equals the entire pool TVL plus accrued interest for as long as the attacker maintains the liquidity squeeze, which is permanent if the vault is structurally illiquid.

This satisfies the "temporary freezing" (and effectively permanent for a persistently illiquid vault) acceptance criterion with direct fund impact.

### Likelihood Explanation
Requires a programmable-borrower deployment whose idle funds sit in an ERC4626 vault with borrowable/variable liquidity — exactly the MetaMorpho-style setup exercised in `ProgrammableBorrowerCreditVault.t.sol`. The attacker needs only to be a vault participant (or to time a natural liquidity crunch), no privileged role. The cost is the interest/opportunity cost of holding the vault's borrowed liquidity; for morpho vaults this can be sustained cheaply during the narrow window each epoch when `stopEpoch` must execute, and a grieving attacker only needs to keep liquidity below `shortfall` at the moments the manager calls `stopEpoch`. Likelihood is moderate: it depends on a programmable deployment and a liquidity-manipulable vault, but within those deployments no privileged action is needed.

### Recommendation
Do not let hook reverts bubble indefinitely. In `ProgrammableBorrower.onStopEpoch`, convert the `vault.withdraw` catch into a graceful failure path, or in `IdleCDOEpochVariant._stopEpoch` wrap the `onStopEpoch` call in try/catch and treat failure the same as `success == false` (route to `_handleBorrowerDefault`), since `onDefault()` is explicitly designed to run without live vault valuation. Alternatively add a bounded retry: after N failed `stopEpoch` attempts or a grace period past `epochEndDate`, allow the manager to force-default the facility so recovery accounting can proceed.

```solidity
// test/foundry/PoCStopEpochVaultDoS.t.sol — fork test extending ProgrammableBorrowerCreditVault setup
function testPoCStopEpochBlockedByVaultIlliquidity() external {
    uint256 amount = 10_000 * oneScale;
    uint256 drawAmount = 5_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);            // honest KYC lender deposits
    _startEpochAndCheckPrices(0);         // epoch running; idle cash parked in Morpho vault

    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(drawAmount);

    // ATTACKER: ordinary Morpho vault user drains borrowable liquidity so that
    // vault.withdraw(shortfall) reverts while the borrower's shares still cover it
    // (shortfall <= _currentVaultAssets(), so the `return true` branch is NOT taken).
    // e.g. borrow all market liquidity on Morpho, or on a live fork warp to a state
    // where the vault's markets are fully utilized.

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // honest manager tries to stop the epoch — reverts, bubbles out of stopEpoch
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // retrying never helps while vault is illiquid; epoch stays running forever
    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());           // default path unreachable
    // finalizeDefault cannot run on a non-defaulted pool; pendingWithdraws unfunded;
    // owner cannot disable programmable mode because isEpochRunning is still true
    vm.prank(owner);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.setIsProgrammableBorrower(false);
}
```
