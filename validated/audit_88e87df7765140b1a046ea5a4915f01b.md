### Title
Unfunded instant-withdraw receipts from pre-default epochs escape the default recovery haircut and drain funded backing at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` segregates instant-withdraw claims by epoch for default accounting, but the aggregate `pendingInstantWithdraws` counter and the aggregate `instantWithdrawsRequests[_user]` receipt are not segregated. When the default is finalized, `defaultPendingClaimBasis()` only includes `instantWithdrawClaimsByEpoch[epochNumber]` (current epoch) [1](#0-0) , and `_claimDefaultedInstantWithdrawRequest` only clears receipts keyed to `defaultRecoveryEpoch` [2](#0-1) . Any still-unfunded instant receipt created in an earlier epoch therefore escapes the recovery haircut and is later paid 1:1 via `claimInstantWithdrawRequest` → `_transferFundedClaim` [3](#0-2) . This is the same bug class as the Rebirthday Attack: a shared claim namespace that is not fully segregated by "outgoing context" (request epoch) lets a poisoned/out-of-scope claim consume the honest claimants' payout pool.

### Finding Description
`requestInstantWithdraw` records receipts twice: per-epoch in `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and in the aggregate `instantWithdrawsRequests[_user]`/`pendingInstantWithdraws` [4](#0-3) . `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` by whatever amount the CDO collects, so a partially funded queue can carry unfunded instant receipts across epochs [5](#0-4) .

At default, `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` where `totalBasis` includes only the current epoch's instant claims via `defaultPendingClaimBasis` [6](#0-5) . Two correlated errors follow:

1. **Basis exclusion**: older unfunded instant receipts are absent from `totalBasis`, so the haircut is computed over too small a base while those receipts still exist as claims.
2. **Reserve understatement**: `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`, which is ≤ 0 when older-epoch claims inflate `pendingInstantWithdraws`, so already-held prefunded backing is not credited to `reserveAmount`, further depressing `defaultRecoveryPrice` [7](#0-6) .

After finalization, `claimInstantWithdrawRequest` clears only the `defaultRecoveryEpoch` receipt when `defaultInstantWithdrawsFinalized` is set, then pays the full remaining `instantWithdrawsRequests[_user]` at par through `_transferFundedClaim` [8](#0-7) . `_transferFundedClaim` only protects `defaultRecoveryReserve`; it freely spends any other strategy balance, including underlying that backs funded normal withdraw receipts [9](#0-8) .

### Impact Explanation
An unprivileged tranche holder whose instant-withdraw request was only partially funded can, after the borrower defaults and `finalizeDefaultRecovery` runs, claim that older receipt at 100% instead of the recovery ratio. Direct consequences:

- The par payout consumes underlying backing funded normal withdraw receipts and/or pushes total payouts above `reserveAmount`, so subsequent defaulted-epoch claimants' `_transferDefaultRecovery` or funded claimants' transfers revert on insufficient balance — permanent freezing of their claims [10](#0-9) .
- Because `totalBasis` and `reserveAmount` are both understated, `defaultRecoveryPrice` is lower than the economically correct ratio: every honest defaulted claimant is underpaid while the out-of-namespace receipt is paid in full — a direct wealth transfer and reserve insolvency. Loss is bounded by the stale instant receipt amount and is unilateral.

### Likelihood Explanation
Requires: (a) an epoch where `collectInstantWithdrawFunds` collects less than `pendingInstantWithdraws` (the code explicitly documents partial prefunding as a supported state [11](#0-10) ), (b) at least one further `stopEpoch`/`startEpoch` so the stale receipt's epoch ≠ finalization epoch, and (c) a borrower default. The attacker only needs to hold a tranche position and request an instant withdraw — all unprivileged actions. No privileged misbehavior is required; honest borrower/manager sequencing produces the state.

### Recommendation
Make the default-claim namespace fully epoch-segregated, mirroring the fix pattern used for normal withdraws:

- Include **all** unfunded instant claims in `defaultPendingClaimBasis`, not only `instantWithdrawClaimsByEpoch[epochNumber]` — e.g., track a separate `pendingInstantClaims` basis (distinct from the funded-remainder counter) and add it to `basis`.
- In `_claimDefaultedInstantWithdrawRequest`/`claimInstantWithdrawRequest`, haircut any instant receipt that was still unfunded at finalization, regardless of its request epoch; only receipts whose funding was actually collected should pay at par.
- Fix `_defaultPrefundedInstantReserve` to account for prefunded backing of older-epoch instant claims, or store the funded portion per epoch explicitly.

### Proof of Concept
Reproducible Foundry fork PoC sketch:

```solidity
// Setup: KYC'd attacker deposits AA, epoch running.
// 1. attacker calls cdoEpoch.requestInstantWithdraw(X) -> instantWithdrawsRequestsByEpoch[attacker][N] = X
// 2. borrower partially repays; stopEpoch collects only part of pendingInstantWithdraws (funding shortfall).
//    pendingInstantWithdraws == X - funded > 0 carries into epoch N+1.
// 3. startEpoch() runs; epochNumber = N+1. Attacker's receipt is now keyed to epoch N.
// 4. Borrower defaults; finalizeDefaultRecovery executes:
//    - defaultPendingClaimBasis() adds instantWithdrawClaimsByEpoch[N+1] (attacker's X excluded).
//    - _defaultPrefundedInstantReserve(): instantBasis(N+1) - pendingInstant <= 0 -> reserve understated.
//    - defaultRecoveryPrice set too low; defaultInstantWithdrawsFinalized = true.
// 5. attacker calls cdoEpoch.claimInstantWithdrawRequest():
//    - _claimDefaultedInstantWithdrawRequest clears only epoch N+1 (attacker's basis there is 0).
//    - instantWithdrawsRequests[attacker] = X paid at par via _transferFundedClaim,
//      spending underlying earmarked for funded normal withdraw receipts.
// Assert: attacker received X * RECOVERY_FULL while defaulted claimants receive X * recoveryPrice,
// and a later funded claimant's claimWithdrawRequest() reverts on insufficient balance.
```

Uncertainty note: I could not fully verify `IdleCDOEpochVariant`'s `stopEpoch`/`collectInstantWithdrawFunds` sequencing to confirm a partially funded instant queue persists across `startEpoch` (the grep returned match counts only). The strategy's own comments document partially funded instant requests as a real state, and nothing in `requestInstantWithdraw` or the claim path restricts receipts to the current epoch, so the cross-epoch condition is consistent with the design as written.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
