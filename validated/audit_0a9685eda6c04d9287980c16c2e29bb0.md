### Title
`setFeeParams` applies the new performance `fee` retroactively to gains accrued under the old rate — (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault.setFeeParams` updates the performance fee `fee` (and `feeSplit`) without first settling the accrued-but-unsplit gain. Because the performance fee is charged lazily inside `_updateAccounting` as `(nav - lastNAV) * fee / FULL_ALLOC`, any gain accumulated since the last deposit/withdraw is fee'd at the *new* rate rather than the rate in force while it accrued. The function does correctly checkpoint the timestamp-based management fee via `_accrueManagementFee()` (lines 466, 552–555), but it does **not** checkpoint the gain-based performance fee, which is the exact analog of the reported `updateFeePerSecond`/`lastFeeCollected` bug.

### Finding Description
The fee-accrual surface has two parts:

- Management fee: `_accrueManagementFee` adds `nav * managementFee * elapsed / (FULL_ALLOC * 365 days)` to `unclaimedFees` and resets `latestHarvestBlock` (lines 552–555). `setFeeParams` calls it before overwriting `managementFee`, so that rate transition is safe.
- Performance fee: inside `_updateAccounting`, on every deposit/withdraw the contract computes `unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC` for the *entire* gain since the last interaction, using the *current* `fee` (line 231), and `_virtualPriceAux` also strips `totalGain * fee / FULL_ALLOC` from the pending gain before splitting it between AA and BB (lines 311–314).

`setFeeParams` (lines 461–470) assigns `fee = _fee` without invoking `_updateAccounting()`, so there is no settlement of pending gains at the old rate.

**Sequence:**

1. Users deposit; `lastNAV`/`lastNAVAA`/`lastNAVBB` are checkpointed and `fee = 10%`.
2. Time passes, yield accrues; `nav - lastNAV = G` of pending gain, still unfee'd.
3. Honest owner calls `setFeeParams` raising `fee` to 50% (allowed up to `MAX_FEE`).
4. The next user deposit/withdraw triggers `_updateAccounting`, which charges `G * 50%` instead of `G * 10%` for the whole pre-update accrual period, moving `G * 40% / FULL_ALLOC` of user yield into `unclaimedFees`.
5. The accrued `unclaimedFees` are then split between `feeReceiver` and `owner()` at the *new* `feeSplit` via `_feeReceiverAmount`/`_transferFeeUnderlyings` (lines 587–598), so raising `feeSplit` also retroactively reroutes fees accrued under the old split.

An unprivileged tranche holder cannot prevent this: the pending-gain window is fully repriced at whatever rate the honest owner next sets, and a user who front-runs the owner's transaction with a deposit only checkpoints the fee at the old rate for themselves while leaving every other holder's share exposed.

### Impact Explanation
Quantified loss = `(newFee - oldFee) * pendingGain / FULL_ALLOC` of user yield transferred to `feeReceiver`/`owner` (if `fee` is raised), or the symmetric under-charge to the protocol (if `fee` is lowered, which socializes the shortfall onto `feeReceiver`/owner). With `fee` capped at `MAX_FEE`, a raise from e.g. 10% to 80% on a vault with a large pending gain extracts up to 70% of all yield accrued since the last interaction from tranche holders. The yield-split invariant — gains are fee'd at the rate in force when they accrued — is broken. No guard prevents this: `_accrueManagementFee` only covers `managementFee`, and `_updateAccounting`/`_virtualPriceAux` unconditionally use the freshly stored `fee`.

### Likelihood Explanation
Likelihood is moderate: it requires an honest owner fee change while a non-trivial gain is pending, which is a routine administrative action (the same privileged-but-honest trigger as the external report). No attacker transaction is needed beyond normal deposit/withdraw flow; the mispricing is deterministic once `setFeeParams` lands with `nav > lastNAV`.

### Recommendation
Settle pending gains at the old rate before overwriting `fee`/`feeSplit`. In `setFeeParams` (contracts/IdleCDOCreditVault.sol:461–470), call `_forceUpdateAccounting()` (or `_updateAccounting()` guarded against the `Default` revert path) immediately after `_accrueManagementFee()` and before the assignments, so `unclaimedFees` is incremented with the *old* `fee` and `lastNAVAA`/`lastNAVBB` are checkpointed:

```solidity
function setFeeParams(address _feeReceiver, uint256 _fee, uint256 _feeSplit, uint256 _managementFee) external {
    _checkOnlyOwner();
    _checkAmountTooHigh(_fee > MAX_FEE || _feeSplit > FULL_ALLOC || _managementFee > MAX_FEE / 10);
    _checkIs0((feeReceiver = _feeReceiver) == address(0));

    _accrueManagementFee();
    _forceUpdateAccounting(); // settle pending gain at old `fee` before repricing
    fee = _fee;
    feeSplit = _feeSplit;
    managementFee = _managementFee;
}
```

### Proof of Concept
A reproducible Foundry fork test (in the style of `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Setup: credit vault with strategy, fee = 10_000 (10%), nonzero feeReceiver
// 1. lender deposits AA and BB (depositAA/depositBB) -> lastNAV checkpointed
// 2. warp forward / donate yield to strategy so nav - lastNAV = G > 0
// 3. record unclaimedFees0 = vault.unclaimedFees()
// 4. vm.prank(owner); vault.setFeeParams(feeReceiver, 80_000, feeSplit, mgmtFee);
// 5. any user calls depositAA(1) to trigger _updateAccounting
// 6. assert: unclaimedFees - unclaimedFees0 ≈ G * 80_000 / FULL_ALLOC
//    expected under correct accounting: G * 10_000 / FULL_ALLOC
// The excess ~ G * 70_000 / FULL_ALLOC was taken from tranche holders' pending gain.
```

A variant lowering `fee` shows the symmetric under-charge to `feeReceiver`. The PoC passes today because nothing between steps 4 and 5 reprices the pending gain at the old rate.

*Uncertainty note:* I did not trace every call site of `unclaimedFees` claim logic in `IdleCDOEpochVariant.sol`, but the accounting flaw in `IdleCDOCreditVault` stands independently of when fees are eventually claimed.
