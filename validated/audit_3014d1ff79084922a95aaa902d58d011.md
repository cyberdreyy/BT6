Confirmed: `broadcast_signed_block` unconditionally calls `handle_post_block` which POSTs the block to the stacks node, regardless of the earlier `mark_locally_accepted` result.### Title
Stale/replayed `BlockAccepted` re-tallies toward the 70% threshold and pushes a block after `mark_globally_rejected`, because `store_and_process_block_signature` never checks `has_reached_consensus()` before broadcasting - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_signature` (the handler reached via `handle_block_response`/`BlockResponse::Accepted`/`handle_block_signature`) tallies `block_signatures` rows and, once the recomputed weight crosses the 70% threshold, unconditionally calls `insert_block` and `broadcast_signed_block` → `handle_post_block`, which POSTs the block to the node. Unlike its sibling `store_and_process_block_rejection`, which explicitly returns early with `if block_info.has_reached_consensus() { return; }`, the acceptance path has no such guard, and the one state-transition attempt it does make (`mark_locally_accepted`) has its `Err` result swallowed with only a (sometimes suppressed) log line, never gating the subsequent broadcast.

### Finding Description
The broken equality: a signature counted toward the 70% acceptance threshold must be re-validated against the block's CURRENT `BlockState` (specifically, must not be `GloballyRejected`) before it is tallied and acted upon. This does not hold.

Path traced in `stacks-signer/src/v0/signer.rs`:
- `handle_block_response` → `BlockResponse::Accepted(accepted)` → `handle_block_signature` (`stacks-signer/src/v0/signer.rs:2372`) → `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2443`).
- `add_block_signature` in `stacks-signer/src/signerdb.rs:1871` is `INSERT OR IGNORE` after first `DELETE`-ing any conflicting `block_rejection_signer_addrs` row for the same `(signer_signature_hash, signer_addr)`. This mutual exclusivity is exercised by the existing `reject_then_accept`/`accept_then_reject` tests (`stacks-signer/src/signerdb.rs:3234-3298`), confirming that a later message of one kind erases the opposite kind for that signer/hash pair at the DB row level - it is not scoped by, or aware of, the aggregate `BlockState`.
- `store_and_process_block_signature` then only checks `block_info.signed_group.is_some()` (already-broadcast guard) before recomputing `total_signature_weight` from all currently-stored `block_signatures` rows and comparing to `min_weight`. It never checks `block_info.has_reached_consensus()` (i.e., `GloballyAccepted`/`GloballyRejected`), even though this exact check exists one function earlier, in `store_and_process_block_rejection` (`stacks-signer/src/v0/signer.rs:2290`).
- If the threshold is met, the code does:
```
if let Err(e) = block_info.mark_locally_accepted(true) {
    if !block_info.has_reached_consensus() { warn!(...); }
}
let _ = self.signer_db.insert_block(block_info)...;
self.broadcast_signed_block(stacks_client, block_info.block.clone(), &addrs_to_sigs);
```
`mark_locally_accepted` internally calls `move_to(LocallyAccepted)`, gated by `BlockInfo::check_state` (`stacks-signer/src/signerdb.rs:314-329`), which forbids `GloballyRejected → LocallyAccepted`. So if the block is already `GloballyRejected`, that call returns `Err` - but the `Err` is only logged (and the warning is even suppressed because `has_reached_consensus()` is true), and execution falls through unconditionally to `insert_block` and `broadcast_signed_block` → `handle_post_block`, which calls `stacks_client.post_block(block)`, i.e. pushes the block to the node.

Attacker's exact message and flow: the attacker needs no keys, only gossip relay of a StackerDB/signer message. A legitimate signer X may first send `BlockAccepted(H)` and later, on re-evaluation (the documented `LocallyAccepted → LocallyRejected` re-evaluation transition), send `BlockRejected(H)`. Once enough other signers' rejections push the local/network view of block H to `GloballyRejected` (>30% reject weight per `store_and_process_block_rejection`), the attacker simply rebroadcasts/replays X's earlier, validly-signed `BlockAccepted(H)` message. On the victim signer:
1. `add_block_signature` deletes X's stored rejection row and re-inserts X's (old) acceptance signature as "new" (since it had been deleted by the rejection).
2. If X is not `self` and a pre-commit from X was already recorded (`has_committed` true, which is the normal case since pre-commit precedes signing in the protocol), the code falls through to the tally instead of being diverted into `handle_block_pre_commit`.
3. `block_info.signed_group` is `None` (never reached, since consensus was reached via rejection, not acceptance) so the tally proceeds.
4. If X's re-added weight, combined with previously-recorded (never-withdrawn) acceptances from other signers, crosses 70%, `mark_locally_accepted` fails silently (state stays `GloballyRejected`) but `broadcast_signed_block`/`handle_post_block` still runs and POSTs the block to the node.

Existing guards that were checked and do not prevent this: the DB-level `has_committed`/pre-commit gate only reroutes truly-unknown-peer acceptances into the pre-commit path, it doesn't protect against replay of an already-pre-committed peer's stale acceptance; `check_state`'s transition table correctly rejects the `GloballyRejected → LocallyAccepted` state mutation, but its `Err` is not used to gate the broadcast call; there is no signature freshness/nonce/timestamp binding a `BlockAccepted` message to a particular round that would make a replay distinguishable from a fresh acceptance.

### Impact Explanation
This breaks the fail-closed safety property that a globally-rejected block cannot be resurrected and pushed to the node: "a rejection recounted as acceptance" is explicitly listed as Critical severity in the prompt's rules. If `stacks_client.post_block` on the node side accepts and processes this block despite majority signer rejection, it finalizes a block the network deliberately rejected, undermining the >30%-blocks-70% safety guarantee the whole pre-commit/signature protocol is built on. The exploit is repeatable for any block where signer opinions have flipped near the 70/30 boundary and is triggerable purely by an unprivileged party replaying gossip they can observe - no key material or majority control is required.

### Likelihood Explanation
Preconditions: (1) at least one signer must have equivocated from Accept to Reject for the same block hash during re-evaluation (a state transition the code explicitly supports and tests), (2) the flipped signer's cumulative weight, when restored, must be enough to cross the local 70% threshold, and (3) the victim signer must already have recorded a pre-commit from that signer (typical in normal protocol operation). None of these require majority-signer control, node-operator access, or the auth_token — only gossip relay of an already-existing, validly signed message plus the attacker's own one miner/signer slot's worth of participation, matching the allowed threat model. The scenario is somewhat timing-dependent (needs the equivocation + threshold-crossing math to align) but is not inherently rare, and is deterministically reproducible in a unit test that manually seeds a `GloballyRejected` `BlockInfo`, calls `add_block_rejection_signer_addr`/`add_block_signature` in the described order, and drives `store_and_process_block_signature` directly.

### Recommendation
In `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2443`), add an early return mirroring `store_and_process_block_rejection`'s guard: `if block_info.has_reached_consensus() { return; }` immediately after loading `block_info` and before (or right after) recording the signature, so a globally-decided block can never be re-tallied. Additionally, make the `broadcast_signed_block`/`insert_block` calls conditional on `mark_locally_accepted` succeeding, rather than falling through unconditionally after logging a swallowed error.

### Proof of Concept
Rust test plan for `stacks-signer/src/v0/tests.rs` (or a `signerdb.rs`-level unit test driving `Signer::store_and_process_block_signature` directly):
1. Construct a `BlockInfo` for block `H`, insert it, and drive it to `GloballyRejected` via `store_and_process_block_rejection` calls simulating >30% weight rejecting, including a rejection from signer `X` (who previously had an `Accepted` signature recorded, then a `Rejected` message overwrote it per DB mutual-exclusion behavior demonstrated in `accept_then_reject`).
2. Assert `block_info.state == BlockState::GloballyRejected` and `get_block_rejection_signer_addrs` contains `X`.
3. Replay `X`'s original, valid `BlockAccepted(H)` signature by calling `handle_block_signature`/`store_and_process_block_signature` again with the stale acceptance.
4. Assert (equality check, both sides):
   - Before: `block_info.state == GloballyRejected`, `get_block_rejection_signer_addrs` contains `X`.
   - After replay: `get_block_rejection_signer_addrs` no longer contains `X` (row deleted) and `get_block_signatures` now contains `X`'s signature (row re-inserted) — demonstrating the DB-level corruption.
   - Critical assertion: no call to `handle_post_block`/`broadcast_signed_block` occurs, and the persisted `BlockInfo.state` fetched fresh from `signer_db` remains `GloballyRejected` (not reverted to `LocallyAccepted`/pushed). With the current code, if the crossed-threshold condition is engineered (e.g., by seeding enough other never-withdrawn acceptances), `broadcast_signed_block` fires and `handle_post_block` is invoked despite `state == GloballyRejected`, which the test should assert as the bug (currently failing this assertion, confirming the vulnerability).
