### Title
Unrestricted capability execution via `/v2/execute_capability` for any run-role user - ([File: core/web/capability_controller.go])

### Finding Description
The route `authv2.POST("/execute_capability", auth.RequiresRunRole(capContr.ExecuteCapability))` (registered in `core/web/router.go`) is gated only by `auth.RequiresRunRole`, the lowest privilege tier above `view` [1](#0-0) . `CapabilityController.ExecuteCapability` accepts a JSON body containing an arbitrary `CapabilityName` string and an opaque `CapabilityRequest` byte blob, looks up the executable purely by name from the global `capabilitiesRegistry` (`capabilityRegistry.GetExecutable(ctx, capabilityRequestOuter.CapabilityName)`), unmarshals the request, and directly calls `capability.Execute(ctx, capabilityRequest)` — with no check that the authenticated caller (or the capability request's target ID/workflow ID inside the opaque protobuf blob) belongs to that user [2](#0-1) . There is no ownership/ACL binding between the `SessionUserKey` set by `RequiresRunRole` and the workflow, job, or credential referenced inside `CapabilityRequest`. Additionally, `AuthenticateExternalInitiator` automatically assigns any external-initiator token holder the `UserRoleRun` role [3](#0-2) , meaning even an external-initiator credential (not a full node user) can hit this endpoint.

### Impact Explanation
Any principal holding run-role credentials (including an external-initiator token, which is a lower-trust credential type meant only to trigger job runs) can invoke `capability.Execute` for any registered capability by name and supply arbitrary request payloads. Since the request payload is opaque bytes controlled entirely by the caller and the handler performs no cross-check against the caller's own jobs/workflows, an attacker could target capabilities/workflows that reference other users' secrets, targets, or on-chain actions if the underlying capability implementation trusts the caller-supplied identifiers embedded in the request. This is a role/authorization bypass class of impact — a low-privilege credential is able to invoke functionality intended to be scoped to the specific workflow/job owner, potentially causing unauthorized job execution or cross-user action, matching Chainlink's "unauthorized job run" / authorization bypass impact class.

### Likelihood Explanation
Preconditions: attacker needs only a run-role API token or an external-initiator credential — no admin/edit privileges required. The request format is a simple documented JSON POST with attacker-controlled `capabilityName` and `capabilityRequest` bytes, so this is trivially repeatable and requires no special network position. The primary uncertainty is whether the concrete capability implementations behind `GetExecutable` themselves validate ownership of referenced IDs inside the protobuf `CapabilityRequest` — that logic lives outside this reviewed file/handler and was not available for inspection, so exploitability ultimately depends on whether any concrete capability trusts caller-supplied IDs without an independent ownership check.

### Recommendation
Bind the capability execution request to the authenticated caller: derive the workflow/job/target identifier from server-side state associated with the authenticated user (or require `RequiresEditRole`/per-resource ACL check) rather than trusting an opaque request the caller controls end-to-end. At minimum, have `ExecuteCapability` verify that the resolved `CapabilityRequest`'s target/workflow ID is owned by (or explicitly authorized for) the authenticated `SessionUserKey` before calling `capability.Execute`, and consider excluding external-initiator-derived sessions from this endpoint entirely.

### Proof of Concept
1. Handler-level Go test in `core/web/capability_controller_test.go` style: set up two "workflow" fixtures/capabilities — one owned by `userA`, one by `userB`.
2. Authenticate as `userB` with run-role credentials (via `RequiresRunRole` middleware chain, using a test session/API key with `UserRoleRun`).
3. POST to `/v2/execute_capability` with `capabilityName` pointing to `userA`'s capability and a `capabilityRequest` payload referencing `userA`'s workflow/target ID.
4. Assert that the current implementation returns `200 OK` with a successful `capabilityResponse` (proving no ownership check), where the expected/fixed behavior should be `403 Forbidden`/`401 Unauthorized` when the target does not belong to the authenticated run-role user.
5. Repeat using an external-initiator token (via `AuthenticateExternalInitiator`) to confirm it too receives `UserRoleRun` and can reach the same unrestricted execution path.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (cc *CapabilityController) ExecuteCapability(c *gin.Context) {
	body := c.Request.Body
	if body == nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("missing request body"))
		return
	}

	capabilityRegistry := cc.App.GetCapabilitiesRegistry()
	if capabilityRegistry == nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.New("capability registry not initialized"))
		return
	}
	var capabilityRequestOuter CapabilityRequestOuter
	if err := c.BindJSON(&capabilityRequestOuter); err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	capability, err := capabilityRegistry.GetExecutable(c.Request.Context(), capabilityRequestOuter.CapabilityName)
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	capabilityRequest, err := pb.UnmarshalCapabilityRequest(capabilityRequestOuter.CapabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	resp, err := capability.Execute(c.Request.Context(), capabilityRequest)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	responseBytes, err := pb.MarshalCapabilityResponse(resp)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	c.JSON(http.StatusOK, gin.H{"capabilityResponse": responseBytes})
