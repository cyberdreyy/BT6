### Title
Unchecked subtraction in JSON-RPC `getSupply` can panic and crash the RPC service - ([File: rpc/src/rpc.rs])

### Summary
The `getSupply` JSON-RPC method computes `circulating = total_supply - non_circulating_supply.lamports` using plain integer subtraction with no overflow protection [1](#0-0) . `total_supply` is `bank.capitalization()`, an atomically-tracked counter maintained incrementally across many independent code paths, while `non_circulating_supply.lamports` is computed by a separate live scan of specific accounts (stake accounts plus a hardcoded list) via `calculate_non_circulating_supply` [2](#0-1) . These two values are derived through entirely independent mechanisms and rely on an implicit invariant (`non_circulating <= total`) that is never explicitly enforced before the subtraction — the exact bug class described in the Velocimeter `circulating_supply()` report, where two independently-tracked supply figures are subtracted without validating their relative ordering.

### Finding Description
`capitalization` is a running `AtomicU64` counter updated incrementally by many call sites throughout the runtime (e.g. `store_account_and_update_capitalization`, `distribute_epoch_rewards_in_partition`, core-BPF migration) [3](#0-2) [4](#0-3) . In contrast, `non_circulating_supply.lamports` is recomputed at query time by summing `bank.get_balance(pubkey)` over a filtered account set [5](#0-4) . Nothing in `get_supply` validates that `total_supply >= non_circulating_supply.lamports` before subtracting; the code simply computes `total_supply - non_circulating_supply.lamports` [6](#0-5) .

Notably, the codebase itself acknowledges this subtraction is not provably safe: the equivalent REST endpoint (`/v0/circulating-supply`) performs the same calculation but explicitly uses `saturating_sub` instead of raw subtraction [7](#0-6) , showing the developers recognized the risk in one code path but not in the JSON-RPC `getSupply` handler in `rpc.rs`. If `bank.capitalization()` ever drifts below the sum of currently-scanned non-circulating balances — for instance, transiently during any bug/edge-case in the many independent capitalization-mutating code paths, or due to any staleness/race between the atomic counter and a fresh accounts scan performed under a different bank/lock context — this subtraction underflows.

### Impact Explanation
An unchecked `u64` subtraction underflow triggers an arithmetic overflow panic in debug builds and silently wraps in release builds (since the workspace does not set `overflow-checks = true` for release profiles, per repository search). A panic in the RPC request handler thread for `getSupply` would crash or poison that request path, and a silent wraparound would return a wildly incorrect (near-`u64::MAX`) circulating supply figure to any caller — corrupting a widely consumed public API used by explorers, exchanges, and wallets. This is a public, unauthenticated JSON-RPC method reachable by any client, making it a low-effort, high-visibility denial-of-service / data-integrity vector on RPC nodes.

### Likelihood Explanation
`getSupply` is a normal, frequently-polled RPC method with no special permissions required, so it is trivially reachable by any client. The likelihood of the underlying invariant violation (capitalization dipping below the non-circulating scan total) depends on cluster-specific accounting edge cases, but the code's own defensive use of `saturating_sub` on an equivalent path is direct evidence that the invariant is not treated as unconditionally guaranteed elsewhere in the same codebase.

### Recommendation
Replace the raw subtraction in `get_supply` with a saturating (or checked, with explicit error handling) subtraction, consistent with the REST endpoint's `saturating_sub` usage:
```rust
circulating: total_supply.saturating_sub(non_circulating_supply.lamports),
```
at [8](#0-7) .

### Proof of Concept
1. Call the `getSupply` JSON-RPC method on a validator's RPC endpoint.
2. Internally, `get_supply` computes `total_supply = bank.capitalization()` [9](#0-8)  and `non_circulating_supply` via a live account scan [10](#0-9) .
3. If at query time `non_circulating_supply.lamports > total_supply` (due to a divergence between the incrementally-tracked capitalization counter and the live-scanned balance total), the expression `total_supply - non_circulating_supply.lamports` [8](#0-7)  underflows, panicking the handling thread (debug/overflow-checked builds) or returning a corrupted near-`u64::MAX` circulating supply (release/wrapping builds) to every caller of `getSupply`.

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };
