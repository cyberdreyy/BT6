### Title
Stake-account JSON-parsed RPC responses expose a stale `rentExemptReserve` value that no longer reflects the cluster's actual `Rent` parameters - (File: `account-decoder/src/parse_stake.rs`)

### Summary
This is analogous to the reported bonding-curve bug: an on-chain parameter (the reserve/pricing input) can be changed cluster-wide, but a downstream consumer keeps using an old, hardcoded value instead of recomputing from the authoritative current state, producing incorrect output at the boundary conditions where it matters most.

### Finding Description
When a stake account is decoded for JSON-RPC responses (e.g. `getAccountInfo`/`getProgramAccounts` with `jsonParsed` encoding), `parse_stake` in `account-decoder/src/parse_stake.rs` converts the on-chain `Meta.rent_exempt_reserve` field directly into the `UiMeta.rent_exempt_reserve` string, verbatim from account data: [1](#0-0) 

That field is explicitly documented as unreliable: [2](#0-1) 

`Rent.lamports_per_byte` (the parameter that determines the correct rent-exempt minimum) is not a fixed constant: it is mutated cluster-wide by multiple feature-gated protocol changes at epoch boundaries (`set_lamports_per_byte_to_6333`, `_5080`, `_2575`, `_1322`, `_696`, and the `set_lamports_per_byte_to_6960` safeguard), all of which call `self.update_rent()` on the bank: [3](#0-2) 

However, an individual stake account's stored `meta.rent_exempt_reserve` field (set once at account creation, e.g. in `runtime/src/stake_utils.rs::create_stake_account`) is never rewritten in the account data itself when `Rent.lamports_per_byte` changes cluster-wide: [4](#0-3) 

The correct/current value must instead be derived from the live `Rent` sysvar (`bank.rent_collector().rent.minimum_balance(...)`), as done internally by validator logic such as reward distribution: [5](#0-4) 

Because the JSON-parsed account decoder (`parse_stake`) simply echoes the account's stale, embedded field rather than recomputing it from the bank's current `Rent` parameters, any unprivileged RPC client requesting `jsonParsed` stake account data receives an incorrect `rentExemptReserve` once a rent-parameter feature activates after the account was created — exactly the "hardcoded, stale calculation not updated with the new implementation/parameters" bug class from the report, manifesting here as wrong account data returned by an RPC query.

### Impact Explanation
Any RPC consumer, wallet, staking dashboard, or exchange relying on `jsonParsed` `rentExemptReserve` for a stake account will receive a numerically wrong value once `Rent.lamports_per_byte` has been adjusted by any of the SIMD-043x feature activations, since the decoder never recalculates it from the authoritative, current `Rent` sysvar/bank state. This is a case of an RPC query returning wrong account data to an unprivileged caller, matching the "wrong-slot/fork/account data returned" acceptance criterion.

### Likelihood Explanation
Multiple rent-parameter-changing features (`set_lamports_per_byte_to_6333/5080/2575/1322/696/6960`) already exist in the codebase and are expected to activate over time per the SIMD-0437/0438 rollout; every stake account created before such activation will carry a stale reserve value that the decoder will continue to serve to any caller of the standard JSON-RPC account endpoints indefinitely, without any special conditions required from the requester.

### Recommendation
In `parse_stake` (or its caller in `account-decoder/src/parse_account_data.rs`), stop echoing the account's embedded `rent_exempt_reserve` verbatim; instead recompute the value using the caller-supplied current `Rent` (already threaded through `additional_data` for other account types, e.g. SPL token decimals) via `Rent::minimum_balance(StakeStateV2::size_of())`, consistent with how validator-internal code (e.g. `vote_reward.rs`) already derives the correct value. Alternatively, deprecate/omit the field entirely from the parsed response as the existing `#[deprecated]` annotation suggests was intended.

### Proof of Concept
1. Create a stake account when `Rent.lamports_per_byte` = X; the account's `Meta.rent_exempt_reserve` is persisted as `rent.minimum_balance(StakeStateV2::size_of())` at that time (see `runtime/src/stake_utils.rs::create_stake_account`, lines 44-54).
2. Advance epochs until a rent-lowering (or raising) feature such as `set_lamports_per_byte_to_2575` activates, which updates `bank.rent_collector.rent.lamports_per_byte` cluster-wide via `runtime/src/bank.rs` lines 6159-6186, without touching any already-created stake account's data.
3. Call `getAccountInfo` (or `getProgramAccounts`) with `encoding: "jsonParsed"` on that stake account.
4. Observe that the returned `parsed.info.meta.rentExemptReserve` still reflects the old `lamports_per_byte` value X, not the bank's current `Rent` parameters — a stale/incorrect value served directly from `account-decoder/src/parse_stake.rs` lines 59-67.
