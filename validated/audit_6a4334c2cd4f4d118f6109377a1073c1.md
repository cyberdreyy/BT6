Based on the code, the weight-aggregation logic does **not** exhibit the described flaw.

In `stackerdb_listener.rs`, the `StackerDBListener::poll`-driven message handler processes `BlockResponse::Accepted` by first looking up the **expected signer's public key for that specific slot** from `self.signer_entries` (built from the reward set at construction time, keyed by `slot_id`), and then verifying the received `signature` against *that* pubkey: [1](#0-0) 

Critically, this is **key-specific signature verification** (`signer_pubkey.verify(block_sighash.bits(), &signature)`), not signature-recovery-then-dedup-by-recovered-key. The pubkey used for verification is fixed per slot from the reward set, not derived from the signature itself. Weight is only credited to a slot once the signature is proven valid *under that slot's registered key*: [2](#0-1) 

For the `BlockResponse::Rejected` path, recovery is used, but only as an additional consistency check — the recovered pubkey is compared against the slot's pre-registered pubkey and the message is dropped on mismatch: [3](#0-2) 

**Why the attack fails:** To make the aggregator credit weight to an idle slot X with signer Y's identity, the attacker would need to produce a `signature` over `block_sighash` that verifies against slot X's registered public key (which belongs to honest signer Y, not the attacker). This requires signer Y's private key. Per the stated preconditions, the attacker controls at most their own single signer's weight and holds no other signer's key. Placing a chunk in slot X with a signature only valid under signer Y's key is not producible without Y's private key — the `verify()` call at line 411 will simply fail and the message is ignored (`continue`). There is no code path where the aggregator recovers a pubkey from an accepted-signature and credits weight based purely on that recovered identity while ignoring the slot-to-pubkey binding; the binding is enforced first, before any weight is added.

The `duplicate_signers` test in `stacks-node/src/tests/signer/v0/mod.rs` (lines 4418-4514) demonstrates a related but distinct scenario — where the *reward set itself* legitimately registers the same public key under two different slots (a registration-time condition, not an attacker-forged message) — which is out of scope here since it requires no forged signature and is not attacker-controlled gossip injection.
