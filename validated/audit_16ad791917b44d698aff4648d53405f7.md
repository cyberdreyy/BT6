### Title
External Initiator credential authorizes arbitrary integer JobID runs via the user-only code path - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets a synthetic `*clsessions.User{Role: clsessions.UserRoleRun}` on `SessionUserKey` for EI-authenticated requests, and `GetAuthenticatedUser` only performs a type assertion without checking `Email`/DB identity. This causes `PipelineRunsController.Create`'s `isUser` branch — nominally reserved for logged-in dashboard users — to treat the EI credential as a real user and call `prc.App.RunJobV2` for any attacker-supplied integer job ID.

### Finding Description
`AuthenticateExternalInitiator` (core/web/auth/auth.go:119-151) authenticates the EI AccessKey/Secret against the DB-stored `ExternalInitiator`, then unconditionally sets: [1](#0-0) 

`GetAuthenticatedUser` (core/web/auth/auth.go:178-187) merely does `obj.(*clsessions.User)` and returns `ok=true` for any `*clsessions.User`, including the synthetic run-role user with empty `Email` and no DB row: [2](#0-1) 

`PipelineRunsController.Create` (core/web/pipeline_runs_controller.go:89-128) explicitly comments "only users are allowed to run jobs using int IDs - EIs not allowed", then gates that logic on `isUser` from `auth.GetAuthenticatedUser(c)`: [3](#0-2) 

Because the synthetic EI user is indistinguishable from a real user at this check, an EI credential holder satisfies `isUser == true` and can supply an arbitrary `int32` job ID in the URL path, causing `prc.App.RunJobV2(ctx, jobID, nil)` to execute for any job — not just the job bound to that initiator. There is no lookup verifying the external initiator is associated with the requested job.

### Impact Explanation
This is an authorization/principal-binding bypass: an EI credential intended only to trigger its own registered webhook job can instead trigger `RunJobV2` for any job on the node by integer ID, matching the "unauthorized job run" bounty impact class. Depending on job configuration, this could execute pipelines involving other users' bridges, external adapters, or on-chain transaction tasks, causing unintended fund movement or unauthorized external calls.

### Likelihood Explanation
The only precondition is possession of any valid External Initiator AccessKey/Secret pair (a low-privilege credential type), and knowledge/guessing of a target integer job ID (job IDs are small sequential integers, easily enumerable). No user session, API token, or admin access is required. The request is a single `POST /v2/jobs/:ID/runs` with EI headers — trivially repeatable.

### Recommendation
Do not reuse `SessionUserKey`/`GetAuthenticatedUser` to represent EI principals. Either:
1. Have `PipelineRunsController.Create` check `auth.GetAuthenticatedExternalInitiator(c)` first, and if present, reject int-ID job runs entirely (consistent with the code's own comment), or
2. Distinguish the synthetic EI user via a dedicated marker/role (not just `UserRoleRun`, which is also used by real low-privilege users) and explicitly exclude it from `isUser` in `Create`, restricting EI-triggered runs to the specific job UUID bound to that initiator via the webhook lookup path.

### Proof of Concept
Go handler-level integration test:
1. Build a test app in non-prod mode with `PipelineRunsController` wired to the same router as production (via `router.go`), an `ExternalInitiator` record created and bound to Job A, and a separate Job B (different integer ID) created by another means.
2. Send `POST /v2/jobs/<JobB-int-ID>/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers matching the EI credential for Job A (not Job B).
3. Assert: `auth.GetAuthenticatedUser(c)` returns `ok=true` inside `Create`; the `isUser` branch executes; `prc.App.RunJobV2` is invoked with Job B's ID; response is `200`/`201` with a created pipeline run — demonstrating that the EI credential bound to Job A successfully triggered a run of an unrelated Job B.
