# Title

Instant-withdraw per-epoch receipt counters are never cleared on claim, corrupting default recovery accounting — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary

Analogous to "votes not reset between milestones" in `RFPCommitteeStrategy`, `IdleCreditVault.claimInstantWithdrawRequest` clears only the flat aggregate `instantWithdrawsRequests[_user]` but never decrements the per-epoch receipt mappings `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. Those per-epoch counters are the exact "votes" consumed later by `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve` and `_claimDefaultedInstantWithdrawRequest` when a default is finalized in the same strategy epoch. Already-paid claims are therefore counted again as outstanding basis.

### Finding Description

`requestInstantWithdraw` records three pieces of state: `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` [1](#0-0) .

On the funded claim path, only the aggregate is cleared: [2](#0-1) 

Neither `instantWithdrawsRequestsByEpoch[_user][epoch]` nor `instantWithdrawClaimsByEpoch[epoch]` is decremented. Instant claims are funded and paid during the *same* `epochNumber` in which they were requested (`epochNumber` only increments via `deposit()` during `stopEpoch` [3](#0-2) ), so the stale entries sit exactly in the bucket that default finalization later reads.

If the borrower then fails to fund `stopEpoch` and the CDO finalizes a default while `pendingInstantWithdraws != 0`, three accounting errors follow:

1. `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still contains already-paid claims — to the recovery basis, inflating `totalBasis` [4](#0-3) .
2. `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` as "funds already held by the strategy", but part of that basis was already paid out to users. The phantom amount is added into `reserveAmount` and stored as `defaultRecoveryReserve` [5](#0-4) , so the reserve exceeds the strategy's real underlying balance.
3. `_claimDefaultedInstantWithdrawRequest` pays claimants against `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and debits the inflated reserve [6](#0-5) ; a user holding sufficient receipt tokens from a second pending request can even re-claim an already-paid receipt.

### Impact Explanation

`defaultRecoveryReserve` is credited for phantom already-paid funds, so `defaultRecoveryPrice` is miscomputed and the reserve accounting is insolvent: `defaultRecoveryReserve > underlyingToken.balanceOf(strategy)`. As recovery claimants draw the reserve down via `_transferDefaultRecovery`, the last claimants' `safeTransfer` reverts — permanent freezing of unclaimed recovery yield, quantified as the total already-claimed instant-withdraw amount in the defaulted epoch. Conversely, an attacker with two same-epoch instant receipts (one funded+claimed, one unfunded) can submit the stale per-epoch receipt again and extract an extra payout worth `claimedAmount * defaultRecoveryPrice` from the reserve, directly stealing recovery funds belonging to other claimants.

### Likelihood Explanation

Requires: (a) at least one instant withdraw request is funded and claimed during an epoch while another instant claim remains unfunded (`pendingInstantWithdraws != 0`), and (b) the epoch ends in a borrower default that is finalized. Instant withdraws are a normal, manager-enabled pool feature, and borrower default is the vault's designed-for failure mode (`_handleBorrowerDefault`/`finalizeDefaultRecovery` exist precisely for it). No privileged misbehavior is needed; the attacker is just a KYC-passed lender exercising ordinary instant-withdraw claims.

### Recommendation

Mirror the fix suggested in the external report — keep per-epoch state in sync with the aggregate on every claim. In `claimInstantWithdrawRequest`, before clearing `instantWithdrawsRequests[_user]`, iterate or track the user's request epochs and decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amounts. Since the code comment states per-user aggregate is kept only "for compatibility", the per-epoch mappings must become the source of truth and be cleared exactly like `withdrawsRequestsByEpoch` is cleared in `_clearWithdrawClaimForEpoch` [7](#0-6) . Additionally, assert in `finalizeDefaultRecovery` that `defaultRecoveryReserve <= underlyingToken.balanceOf(address(this))` to catch any residual phantom reserve.

### Proof of Concept

```solidity
// Foundry fork test against mainnet deployment (contracts/strategies/idle/IdleCreditVault.sol)
function testStaleInstantClaimsInflateRecoveryReserve() public {
    // Pool running in fixed-APR mode, instant withdraws enabled by manager.
    // Epoch N starts. Attacker (KYC'd lender) requests instant withdraw of X.
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(X, AAtranche);  // instantWithdrawClaimsByEpoch[N] += X

    // Manager/CDO funds and attacker claims during epoch N.
    vm.prank(manager);
    cdoEpoch.claimInstantWithdrawRequest();          // attacker paid X; per-epoch counters untouched

    // Second lender also has an unfunded instant request so pendingInstantWithdraws != 0.
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(Y, AAtranche);

    // Borrower (honest) fails to fund stopEpoch -> default path -> finalizeDefaultRecovery.
    deal(underlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr, lossOrZero);             // triggers _handleBorrowerDefault
    vm.prank(owner);
    cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);

    // BUG: defaultRecoveryReserve includes phantom X already paid to attacker.
    uint256 reserve = strategy.defaultRecoveryReserve();
    uint256 real = IERC20(underlying).balanceOf(address(strategy));
    assertGt(reserve, real);                          // reserve insolvency

    // Victim's recovery claim reverts once honest claimants drain the real balance,
    // or attacker re-claims via stale instantWithdrawsRequestsByEpoch[attacker][N].
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Note: due to index size limits I could not trace the exact `epochNumber` value at `finalizeDefaultRecovery` call time inside `IdleCDOEpochVariant`; if `epochNumber` is bumped before finalization the stale-entry window shifts, but the missing per-epoch clearing in `claimInstantWithdrawRequest` remains a concrete accounting defect worth a full Devin session to confirm end-to-end.
