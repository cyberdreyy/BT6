### Title
`index_scan_accounts` can return data from a rooted slot later than the reported `context.slot` because it lacks the `ancestors.min_slot()` bound used by `scan_accounts` - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::index_scan_accounts` (used by `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByMint` when a secondary index is enabled and applicable) falls back to `Ancestors::from(vec![scan_guard.max_root()])` whenever the queried bank's own ancestor set does not contain the freshly captured `scan_guard.max_root()`. Unlike the sibling `scan_accounts` path, it does not clamp this fallback by `ancestors.min_slot()`, so if a new root is added to `AccountsDb` between the RPC picking its `Arc<Bank>` (which fixes `context.slot`) and `index_scan_accounts` executing, `do_load` will read using the newer root and can return account state from a slot strictly later than `context.slot`.

### Finding Description
In `AccountsDb::index_scan_accounts` (accounts-db/src/accounts_db.rs:3358-3421), a `ScanGuard` is created capturing `self.max_root()` at call time, then:
```
let max_root_ancestors = Ancestors::from(vec![scan_guard.max_root()]);
let ancestors = if scan_guard.should_use_ancestors(ancestors) { ancestors } else { &max_root_ancestors };
```
`ScanGuard::should_use_ancestors` (accounts-db/src/accounts_scan.rs:232-234) returns `false` when `max_root` is not in the bank's ancestor set — which, per its own doc comment (lines 170-172), covers the case where "the bank is ... an ancestor of `max_root`," i.e., the queried bank's slot is older than a root that has advanced past it on the same fork. In that branch the loop uses only `[scan_guard.max_root()]` as the ancestor set for every subsequent `self.do_load(...)` call (line 3402), with no bound tying it back to the bank's own slot.

By contrast, the sibling `scan_accounts` (accounts-db/src/accounts_db.rs:3259-3356) explicitly clamps: `max_root = max_root.min(ancestors.min_slot())` (lines 3311-3316) before scanning the index, deliberately avoiding surfacing state from any root beyond the bank's own ancestor chain. `index_scan_accounts` has no equivalent clamp.

The RPC entry points (`rpc/src/rpc.rs::get_program_accounts` and `get_token_accounts_by_owner`) fetch `bank = self.get_bank_with_config(...)` once, then eventually call `new_response(&bank, accounts)` which reports `bank.slot()` as `context.slot`. That `bank.slot()` is fixed at fetch time and does not track subsequent rooting. If, during the window between fetching `bank` and the (async, potentially delayed by `spawn_blocking` scheduling) execution of `index_scan_accounts`, `AccountsDb::add_root` advances `max_root` past `bank.slot()` on the same fork, the scan uses `[new_max_root]` as ancestors instead of `bank`'s own ancestor chain, and `do_load` can return the pubkey's state as of the newer root — while the response still reports the old `bank.slot()`.

### Impact Explanation
This causes wallets/dApps calling `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByMint` against secondary-indexed keys to receive account data corresponding to a slot later than the reported `RpcResponseContext.slot`, breaking the invariant that returned data matches the requested/reported commitment slot. This matches the "wrong-slot/fork/account data returned" bounty category.

### Likelihood Explanation
Requires: (1) secondary indexes enabled (`--account-index program-id` / `spl-token-owner` / `spl-token-mint`), (2) the attacker's account owner/mint/owner-key is present in that index (trivially true for common program ids like the SPL Token program), (3) a root advances past the bank's slot during the small window between bank selection and scan execution — plausible under normal validator operation since roots are continuously advancing and RPC processing is asynchronous (`spawn_blocking`). No special privileges beyond a single RPC call are needed.

### Recommendation
Apply the same bound used in `scan_accounts` to `index_scan_accounts`: clamp the fallback ancestor slot to `ancestors.min_slot()` (or otherwise refuse to use a `max_root` beyond the queried bank's own ancestor chain), ensuring `do_load` never returns state from a root that postdates the bank used to compute `context.slot`.

2. Build `bank_ancestors = Ancestors::from(vec![0, 1])` representing an RPC bank frozen at slot 1.
3. In a separate thread, after a synchronization signal, call `db.store_for_tests((2, ...))` updating A's data and `db.add_root_and_flush_write_cache(2)`, simulating a root advancing past the RPC bank's slot while the scan runs.

    pub(crate) fn index_scan_accounts<F>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        index_key: IndexKey,
        mut scan_func: F,
        config: &ScanConfig,
    ) -> ScanResult<bool>
    where
        F: FnMut(Option<(&Pubkey, AccountSharedData, Slot)>),
    {
        let key = match &index_key {
            IndexKey::ProgramId(key) => key,
            IndexKey::SplTokenMint(key) => key,
            IndexKey::SplTokenOwner(key) => key,
        };
        if !self.account_indexes.include_key(key) {
            // the requested key was not indexed in the secondary index, so do a normal scan
            let used_index = false;
            self.scan_accounts(ancestors, bank_id, scan_func, config)?;
            return Ok(used_index);
        }

        // Register this scan so that slots needed by the scan are not cleaned out from under us.
        let scan_guard = ScanGuard::try_new(&self.scan_tracker, bank_id, || self.max_root())
            .ok_or(ScanError::SlotRemoved {
                slot: ancestors.max_slot(),
                bank_id,
            })?;

        // If the scan's ancestors are all rooted, drop them and scan roots only
        // Scan Guard max root must be used as the scan guard guarantees that
        // the account state as of max root is persisted in the database
        let max_root_ancestors = Ancestors::from(vec![scan_guard.max_root()]);
        let ancestors = if scan_guard.should_use_ancestors(ancestors) {
            ancestors
        } else {
            &max_root_ancestors
        };

        for pubkey in self.accounts_index.get_index_key_pubkeys(&index_key) {
            if config.is_aborted() {
                break;
            }
            if let Some((account, slot)) = self.do_load(
                ancestors,
                &pubkey,
                LoadHint::Unspecified,
                PopulateReadCache::False,
            ) {
                scan_func(Some((&pubkey, account, slot)));
            }
        }

        // Check whether the bank was removed while the scan was in progress.
        if scan_guard.was_scan_corrupted() {
            return Err(ScanError::SlotRemoved {
                slot: ancestors.max_slot(),
                bank_id,
            });
        }
        let used_index = true;
        Ok(used_index)
    }

    /// Returns true if ancestors should be used, or false if the scan's bank
    /// is not descended from `max_root` (different fork or ancestor of
    /// `max_root`).
    ///
    /// For any bank `B` descended from the current `max_root`, it must be true
    /// that `B.ancestors.contains(max_root)`, regardless of squash behavior.
    /// (Proof: at startup max_root is the greatest root from the snapshot, and
    /// on each `set_root(R_new)` where `R_new > R`, every surviving descendant
    /// of `R_new` was also a descendant of `R` and therefore has `R_new` in its
    /// ancestors.)
    ///
    /// If `max_root` is **not** in `ancestors`, the bank is either:
    /// 1. on a different fork, or
    /// 2. an ancestor of `max_root`.
    ///
    /// In both cases the provided ancestors may reference slots that have
    /// already been cleaned, so we fall back to an empty ancestor set and rely
    /// only on roots (bounded by `max_root`).
    ///
    /// ```text
    ///             slot 0
    ///               |
    ///             slot 1
    ///           /        \
    ///      slot 2         |
    ///         |       slot 3 (max root)
    ///     slot 4 (scan)
    /// ```
    ///
    /// By the time the scan on slot 4 is called, slot 2 may already have been
    /// cleaned by a clean on slot 3, but slot 4 may not have been cleaned.
    /// The state in slot 2 would have been purged and is not saved in any roots.
    /// In this case, a scan on slot 4 wouldn't accurately reflect the state
    /// when bank 4 was frozen, so we default to a scan on the latest roots by
    /// removing all `ancestors`.
    ///
    /// After calling this, there are two cases:
    ///
    /// 1) **Ancestors is empty** (this method returned `false`): the scan behaves
    ///    like a scan on a rooted bank. `ongoing_scan_roots` protects the roots
    ///    needed by the scan, and passing `max_root` to the scan ensures newer
    ///    roots don't appear in the results.
    ///
    /// 2) **Ancestors is non-empty** (this method returned `true`): the fork
    ///    structure must look something like:
    ///
    /// ```text
    ///            slot 0
    ///              |
    ///        slot 1 (max_root)
    ///        /            \
    ///   slot 2              |
    ///      |            slot 3 (potential newer max root)
    ///    slot 4
    ///      |
    ///   slot 5 (scan)
    /// ```
    ///
    ///    Consider both types of ancestors, `ancestor <= max_root` and
    ///    `ancestor > max_root`, where `max_root == 1` as illustrated above.
    ///
    ///    a) The set of `ancestors <= max_root` are all rooted, which means their
    ///       state is protected by the same guarantees as case 1.
    ///
    ///    b) The `ancestors > max_root` have at least one reference discoverable
    ///       through the chain of `Bank::BankRc::parent` starting from the calling
    ///       bank. For instance bank 5's parent reference keeps bank 4 alive, which
    ///       prevents `Bank::drop()` from running and cleaning up bank 4.
    ///       Furthermore, no cleans can happen past the saved `max_root == 1`, so a
    ///       potential newer max root at slot 3 will not clean up any of the
    ///       ancestors > 1, and slot 4 will not be cleaned in the middle of the
    ///       scan either. (NOTE: similar reasoning is employed for the `assert!()`
    ///       justification in `AccountsDb::retry_to_get_account_accessor`.)
    pub(crate) fn should_use_ancestors(&self, ancestors: &Ancestors) -> bool {
        ancestors.contains_key(&self.max_root)
    }
