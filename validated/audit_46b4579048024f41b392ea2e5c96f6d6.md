### Title
Uncapped `BuilderPendingWithdrawal.amount` committed to the execution layer while the CL deduction is silently capped — Gwei minted without backing - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` copies the *requested* amount from `state.builder_pending_withdrawals` directly into the `Withdrawal.amount` field that becomes part of `state.payload_expected_withdrawals` — the canonical, EL-binding withdrawal list. The actual balance deduction, performed later in `apply_withdrawals`, is silently capped to `min(withdrawal.amount, builder_balance)`. If a builder's balance is insufficient to cover a queued pending withdrawal at the moment `process_withdrawals` runs, the CL only removes the capped (smaller) amount from the builder, but the committed `Withdrawal` object — which the execution layer is required to honor verbatim — still states the full, uncapped requested amount.

### Finding Description
`get_builder_withdrawals` builds the withdrawal objects straight from the queue without checking builder balance: [1](#0-0) 

The actual state mutation, in `apply_withdrawals`, caps the deduction to what the builder actually has: [2](#0-1) 

The spec's own note on `process_withdrawals` states that "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer," i.e. the EL must credit `fee_recipient` with exactly `withdrawal.amount`: [3](#0-2) 

So whenever `withdrawal.amount > builder.balance` at processing time, the recorded (and EL-binding) amount and the CL-side balance decrease diverge: the CL only destroys `builder.balance` worth of Gwei, but the committed `Withdrawal` instructs the EL to mint/credit the full, larger requested amount to `fee_recipient`. This is confirmed as expected (not accidental) test behavior — the test suite explicitly asserts `withdrawal.amount` equals the "requested amount" while the builder balance is drained to `0` ("deduction capped to available balance"): [4](#0-3) 

This is structurally the same bug class as the Trident report: a committed/requested amount is used downstream as the executed value, while the actual available balance at execution time is smaller (state changed between commitment and execution) — creating a surplus that is paid out but not backed by any corresponding decrease on the source side.

A concrete path to trigger `withdrawal.amount > builder.balance`: a builder can have multiple entries queued in `state.builder_pending_withdrawals` (each added by `process_builder_pending_payments` when a bid's payment quorum is reached) whose amounts, summed, exceed the builder's current balance — e.g. several bids accepted across different slots before any of them settle, or a builder's balance being reduced between the bid being accepted and the payment being processed. `apply_withdrawals` processes the list sequentially, re-reading `builder.balance` each iteration, so only the first entries fully use up the available balance while later entries are increasingly under-collateralized, yet each still contributes its full requested `amount` to `state.payload_expected_withdrawals`.

### Impact Explanation
This breaks the equality "Gwei destroyed on the consensus layer == Gwei credited on the execution layer" for builder withdrawals. Because the execution layer is contractually bound to honor `state.payload_expected_withdrawals` verbatim, the shortfall is minted on the EL side without any matching CL-side balance decrease — a form of unauthorized Gwei creation / inflation, and effectively a payment made that is not actually backed by the builder's own funds. This falls in the "Critical" bucket (Gwei created and paid to a party) as defined in the validation rubric.

### Likelihood Explanation
No adversarial validator/proposer action or majority stake is required — the discrepancy is realized as a natural consequence of ordinary state transitions once a builder's balance falls short of its queued pending-withdrawal total, which can occur through normal builder bidding/payment-settlement activity described above. This makes it a spec-level correctness issue in `process_withdrawals`/`get_builder_withdrawals`, reachable purely by spec-following state transitions.

### Recommendation
In `get_builder_withdrawals`, set `Withdrawal.amount` to the same capped value (`min(withdrawal.amount, current builder.balance, considering amounts already allocated to prior withdrawals for the same builder within this call)`) that `apply_withdrawals` will actually deduct, so the value committed to the execution layer always matches the CL-side balance decrease. Alternatively, disallow builder balances from ever being insufficient for already-queued pending withdrawals (e.g., reserve/earmark balance at the time a `BuilderPendingWithdrawal` is queued, similar to how bids check `can_builder_cover_bid`), so the capping branch in `apply_withdrawals` becomes unreachable.

### Proof of Concept
Using state values equivalent to the existing spec test `test_builder_withdrawal_insufficient_balance`:
1. `state.builders[0].balance = 1_000_000_000` Gwei (1 ETH).
2. `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, fee_recipient=X, amount=5_000_000_000)]` (5 ETH requested).
3. Call `process_withdrawals(state)`.
4. `get_builder_withdrawals` produces `Withdrawal(validator_index=builder_0, address=X, amount=5_000_000_000)`, which is stored in `state.payload_expected_withdrawals` — the EL-binding commitment.
5. `apply_withdrawals` executes `state.builders[0].balance -= min(5_000_000_000, 1_000_000_000)`, leaving `state.builders[0].balance == 0` — only 1 ETH actually destroyed on the CL.
6. The execution layer, bound to honor `state.payload_expected_withdrawals` verbatim, credits `X` with the full 5 ETH.
Net effect: 4 ETH credited to `X` with no corresponding CL-side balance destruction — Gwei created out of thin air. [5](#0-4)

```markdown
##### Modified `process_withdrawals`

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
before `process_execution_payload_bid` as the latter function affects validator
balances.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.

```
