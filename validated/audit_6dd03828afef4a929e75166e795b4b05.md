### Title
Stale scaled APR after epoch-duration update inflates withdrawal receipts - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary

`setEpochParams` can replace `epochDuration` and `bufferPeriod` while the pool is stopped, but it does not recalculate the strategy APR stored in `IdleCreditVault.lastApr`. The existing `lastApr` was scaled using the previous duration and buffer through `_setScaledApr`, so an unprivileged lender can request a withdrawal after a parameter update and lock interest calculated with mismatched old and new epoch parameters. [1](#0-0) [2](#0-1) 

### Finding Description

`IdleCreditVault.setAprsWithBuffer` stores the unscaled APR in `unscaledApr` and stores `unscaledApr * (_duration + _buffer) / _duration` as `lastApr`. [3](#0-2) 

`stopEpochWithDuration` normally keeps these values synchronized by first invoking `setEpochParams` and then `_setScaledApr`. [4](#0-3) 

A direct owner or manager call to `setEpochParams`, however, updates only `epochDuration` and `bufferPeriod`; it does not call `_setScaledApr`. [1](#0-0) 

The vulnerability is the resulting inconsistent triple:

```text
lastApr        = unscaledApr * (oldDuration + oldBuffer) / oldDuration
epochDuration  = newDuration
bufferPeriod   = newBuffer
```

When a lender calls `requestWithdraw`, `_calcInterestWithdrawRequest` first uses stale `lastApr` with the new `epochDuration`, and then removes the new buffer component by multiplying by `newDuration / (newDuration + newBuffer)`. [5](#0-4) 

For example, assume `unscaledApr = 10%`, `oldDuration = 30 days`, `oldBuffer = 5 days`, and a subsequent parameter update to `newDuration = 60 days`, `newBuffer = 5 days`. The stored scaled APR remains `10% * 35 / 30 = 11.6667%`, but withdrawal accounting converts it back using the new `60/65` ratio, producing an effective APR of approximately `10.7692%` rather than `10%`. [6](#0-5) 

`requestWithdraw` adds that inflated projected interest to the requested amount and records the result as a funded withdrawal receipt. [7](#0-6) [8](#0-7) 

### Impact Explanation

An unprivileged KYC-passing tranche holder can front-run the next epoch after an honest parameter update and mint a withdrawal receipt above the amount implied by the configured APR. [9](#0-8) 

For a 1,000,000-USDC AA position in the example above, the inflated receipt exceeds the intended projected interest by approximately:

```text
1,000,000 * (10.769230% - 10%) * 60 / 365
≈ 1,264 USDC
```

This breaks fair burn and payout accounting because the receipt was created using an APR scaled for obsolete epoch parameters but then settled under the new parameters. [10](#0-9) 

At the following `stopEpoch`, the CDO attempts to collect both active interest and `pendingWithdraws` from the borrower and forwards the funded pending amount to the strategy. [11](#0-10) 

If the honest borrower funds the amount, the attacker receives the excess at claim; if the borrower does not fund the inflated obligation, repayment fails and the default path can socialize the resulting loss. [12](#0-11) [13](#0-12) 

### Likelihood Explanation

The exploit requires an honest owner or manager to change `epochDuration` or `bufferPeriod` during the buffer phase, followed by an attacker withdrawal request before a corresponding APR correction. [1](#0-0) 

`stopEpochWithDuration` mitigates its own duration changes by immediately rescaling the APR, but that protection does not cover the public standalone `setEpochParams` path. [4](#0-3) 

The code comments specifically warn that changing `bufferPeriod` can corrupt interest calculations, which reduces the likelihood for that parameter; however, `epochDuration` has the same stale-scaled-APR issue and is an intended configurable value exposed through both the CDO and orchestrator. [14](#0-13) [15](#0-14) 

### Recommendation

Make epoch parameters and APR scaling atomic.

1. Require `setEpochParams` to receive the next unscaled APR and call `setAprsWithBuffer(_unscaledApr, _epochDuration, _bufferPeriod)` in the same transaction.
2. Alternatively, preserve `unscaledApr` and automatically call `IdleCreditVault(strategy).setAprsWithBuffer(unscaledApr, _epochDuration, _bufferPeriod)` inside `setEpochParams`.
3. If preserving the current API is required, temporarily disable withdrawal requests whenever duration or buffer changes until the manager explicitly rescales the APR.
4. Add a regression test that changes only `epochDuration` between epochs and verifies that the effective withdrawal APR remains equal to `unscaledApr`. [3](#0-2) 

### Proof of Concept

The following Foundry regression test is designed for the existing `TestIdleCreditVault` mainnet-fork harness, where fees are configured as zero and AA receives the full interest split. [16](#0-15) [17](#0-16) 

```solidity
function testStaleScaledAprInflatesWithdrawRequest() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    address attacker = makeAddr("attacker");
    uint256 principal = 1_000_000 * ONE_SCALE;

    // Start with an intended 10% APR over a 30-day epoch + 5-day buffer.
    vm.prank(cdoEpoch.owner());
    cdoEpoch.setEpochParams(30 days, 5 days);

    _depositWithUser(attacker, principal, true);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    uint256 borrowerPayment = _expectedFundsEndEpoch();
    deal(defaultUnderlying, borrower, borrowerPayment);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), borrowerPayment);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // Honest parameter update during the buffer. This changes duration to 60 days
    // but leaves lastApr scaled for the old 35/30 ratio.
    vm.prank(manager);
    cdoEpoch.setEpochParams(60 days, 5 days);

    vm.prank(attacker);
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

    uint256 correctInterest =
        principal *
        (initialProvidedApr / 100) *
        60 days /
        (365 days * ONE_TRANCHE);

    uint256 inflatedInterest =
        principal *
        ((initialProvidedApr * 35 days / 30 days) / 100) *
        60 days /
        (365 days * ONE_TRANCHE) *
        60 days /
        65 days;

    assertGt(inflatedInterest, correctInterest);
    assertEq(receipt, principal + inflatedInterest);
    assertEq(vault.pendingWithdraws(), receipt);
    assertApproxEqAbs(
        receipt - principal - correctInterest,
        1_264 * ONE_SCALE,
        2 * ONE_SCALE
    );
}
```

The important assertion is that the stored receipt exceeds `principal + correctInterest`, even though the active `unscaledApr` remains 10%. [10](#0-9) [18](#0-17)

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }
