### Title
External Initiator credentials bypass the "EI not allowed" restriction in `PipelineRunsController.Create` via identity confusion, allowing arbitrary job runs by integer ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` intends to allow only real users (not External Initiators) to trigger job runs via integer job IDs, but the check it uses (`auth.GetAuthenticatedUser`) cannot distinguish a real user from the synthetic `User{Role: UserRoleRun}` object that `AuthenticateExternalInitiator` injects into the same context key for every EI request. As a result, any EI credential holder can hit `POST /v2/jobs/:ID/runs` with an arbitrary integer job ID and trigger `ctrl.App.RunJobV2` on a job it was never provisioned for, since there is no ownership/binding check between the `ExternalInitiator` entity and the job ID at all.

### Finding Description
The route is registered in the `userOrEI` group: [1](#0-0) 

`auth.AuthenticateExternalInitiator` authenticates the EI header credentials and then sets the exact same context key (`SessionUserKey`) that real session/token authentication uses, with a synthetic `Role: UserRoleRun` user: [2](#0-1) 

`RequiresRunRole` only checks `user.Role != UserRoleView`, so this synthetic user passes: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code comment explicitly states the intent — "only users are allowed to run jobs using int IDs - EIs not allowed" — and gates on `isUser, _ := auth.GetAuthenticatedUser(c)`: [4](#0-3) 

However, `GetAuthenticatedUser` simply reads the `SessionUserKey` from context and cannot tell whether it was set by `AuthenticateBySession`/`AuthenticateByToken` (real user) or by `AuthenticateExternalInitiator` (synthetic run-role user): [5](#0-4) 

There is a separate accessor, `GetAuthenticatedExternalInitiator`, that could be used to detect and reject EI-originated requests, but `Create()` never calls it: [6](#0-5) 

Additionally, the historical binding mechanism that tied an `ExternalInitiator` to a specific job (webhook job spec's `externalInitiators` list, matched by name/UUID) has been removed — `job.Webhook` job type is rejected with `job.ErrJobTypeRemoved`, and `Create()` explicitly rejects UUID-style IDs: [7](#0-6) 

So even the one prior mechanism that could have enforced "EI is bound to one job" no longer exists for the surviving int32-ID code path. This confirms there is no per-EI job-ownership check anywhere in this flow — any EI credential that authenticates successfully can attempt `RunJobV2` against any integer job ID.

`RunJobV2` itself has no caller-based authorization check either; it directly loads the job by ID and executes/records a pipeline run: [8](#0-7) 

Note: `RunJobV2` is gated by `build.IsProd()`, returning an error ("manual job runs not supported on secure builds") when compiled for production/secure builds: [9](#0-8) 
I was unable to locate the definition of `build.IsProd`/`build.IsDev` in the indexed codebase to confirm exactly which build tags/environment enable or disable this gate; this is a meaningful caveat on real-world exploitability in production deployments — if `build.IsProd()` is true, the request fails at `RunJobV2` regardless of the authorization confusion described above.

### Impact Explanation
This is an authorization-bypass / cross-tenant job-run issue: an EI credential (a lower-trust, narrower-purpose credential intended only to trigger its own bound job) can invoke `RunJobV2` against any job ID in the node, in any environment where `build.IsProd()` does not gate it (e.g., non-production/dev builds, or any deployment where that build flag is not set as expected). This can trigger pipeline execution on jobs unrelated to the EI (potential unintended on-chain transaction submission for jobs with `ETH` tasks, VRF fulfillment triggers, etc.), and inserted pipeline runs are persisted and readable via `/v2/jobs/:ID/runs`. This matches the bounty impact class of "unauthorized action on another user's job" / authorization bypass.

### Likelihood Explanation
The only precondition is possession of one valid `ExternalInitiator` access-key/secret pair (a credential class explicitly designed to be low-privilege and job-specific). No admin/edit role, no knowledge of the target job's owner or the EI's originally intended job, is required — just any positive integer that resolves to an existing job via `FindJob`. It is fully repeatable and requires no timing or race condition, only that the build does not have the `build.IsProd()` gate active.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests authenticated as an `ExternalInitiator` using `auth.GetAuthenticatedExternalInitiator(c)` before allowing the integer-ID run path, instead of relying on `GetAuthenticatedUser` returning `ok`. Alternatively, differentiate context keys/types between "real user" and "EI-as-run-role" identities so `GetAuthenticatedUser` cannot be satisfied by EI authentication, restoring the intended EI/user separation stated in the code comment.

### Proof of Concept
Handler-level integration test plan (Go, using `cltest` helpers similar to `router_test.go`/`pipeline_runs_controller_test.go`):
1. Start an app (`cltest.NewApplicationWithConfig`), create Job A via `cltest.MustInsertV2JobSpec` (or similar) getting `jobA.ID`.
2. Create an `ExternalInitiator` credential EI-A via `cltest.CreateExternalInitiatorViaWeb` (unrelated conceptually to Job A/B, since no job-binding for EI exists in current codebase for non-webhook job types).
3. Send `POST /v2/jobs/<jobA.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to EI-A's credentials (using `cltest.UnauthenticatedPost` with these headers, mirroring `TestRunner_WebhookJobRemoved`).
4. Assert that in a build where `build.IsProd()==false` (test/dev build, the default for `go test`), the response is `201 Created` with a pipeline run resource — demonstrating that an unrelated EI credential can run Job A, which it has no legitimate association to; expected/desired behavior per the code comment ("EIs not allowed" to run by int ID) would be `401`/`403`.
5. Compare with a real logged-in run-role user under `TestRBAC_Routemap_Run` semantics, confirming the same code path (`isUser==true`) is taken for both, proving the identity-confusion root cause.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (app *ChainlinkApplication) RunJobV2(
	ctx context.Context,
	jobID int32,
	meta map[string]any,
) (int64, error) {
	if build.IsProd() {
		return 0, errors.New("manual job runs not supported on secure builds")
	}
	jb, err := app.jobORM.FindJob(ctx, jobID)
	if err != nil {
		return 0, errors.Wrapf(err, "job ID %v", jobID)
	}
	var runID int64

	// Some jobs are special in that they do not have a task graph.
	isBootstrap := jb.Type == job.OffchainReporting && jb.OCROracleSpec != nil && jb.OCROracleSpec.IsBootstrapPeer
	if jb.Type.RequiresPipelineSpec() || !isBootstrap {
		var vars map[string]any
		var saveTasks bool
		if jb.Type == job.VRF {
			saveTasks = true
			// Create a dummy log to trigger a run
			testLog := types.Log{
				Data: bytes.Join([][]byte{
					jb.VRFSpec.PublicKey.MustHash().Bytes(),  // key hash
					common.BigToHash(big.NewInt(42)).Bytes(), // seed
					evmutils.NewHash().Bytes(),               // sender
					evmutils.NewHash().Bytes(),               // fee
					evmutils.NewHash().Bytes(),
				}, // requestID
					[]byte{}),
				Topics:      []common.Hash{{}, jb.ExternalIDEncodeBytesToTopic()}, // jobID BYTES
				TxHash:      evmutils.NewHash(),
				BlockNumber: 10,
				BlockHash:   evmutils.NewHash(),
			}
			vars = map[string]any{
				"jobSpec": map[string]any{
					"databaseID":    jb.ID,
					"externalJobID": jb.ExternalJobID,
					"name":          jb.Name.ValueOrZero(),
					"publicKey":     jb.VRFSpec.PublicKey[:],
					"evmChainID":    jb.VRFSpec.EVMChainID.String(),
				},
				"jobRun": map[string]any{
					"meta":           meta,
					"logBlockHash":   testLog.BlockHash[:],
					"logBlockNumber": testLog.BlockNumber,
					"logTxHash":      testLog.TxHash,
					"logTopics":      testLog.Topics,
					"logData":        testLog.Data,
				},
			}
		} else {
			vars = map[string]any{
				"jobRun": map[string]any{
					"meta": meta,
				},
			}
		}
		runID, _, err = app.pipelineRunner.ExecuteAndInsertFinishedRun(ctx, *jb.PipelineSpec, pipeline.NewVarsFrom(vars), saveTasks)
	}
	return runID, err
}
