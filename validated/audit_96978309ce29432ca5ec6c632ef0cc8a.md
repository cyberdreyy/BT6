### Title
Native NEAR becomes permanently stuck in `MultisigFactory` when deployment fails - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` forwards the caller's full `attached_deposit` into a single cross-contract receipt (`create_account` → `deploy_contract` → `transfer` → `function_call`) but, unlike the sibling factories in this codebase (`lockup-factory`, `staking-pool-factory`), it registers **no callback** to check whether that receipt succeeded. If the deployment fails for any reason, the transferred NEAR is never returned to the caller and is permanently stuck with no recovery path, breaking the same "value debited == value delivered" custody binding that the `ASDRouter` report describes for stuck `CANTO`.

### Finding Description
`lockup-factory` and `staking-pool-factory` both follow the same pattern: create the sub-account, transfer the attached deposit, then attach a `.then(ext_self::on_X_create(...))` callback that inspects `is_promise_success()`. If the account creation failed, the callback explicitly returns the `attached_deposit` to the original `predecessor_account_id`: [1](#0-0) [2](#0-1) 

`MultisigFactory::create`, however, performs the identical create/deploy/transfer/function_call sequence but has **no `.then(...)` callback at all**: [3](#0-2) 

Because `create` is `#[payable]`, the caller's `attached_deposit` is added to the `MultisigFactory` contract's own balance the moment the top-level function call executes. The `Promise` chain (`create_account`, `deploy_contract`, `transfer`, `function_call`) is a single outgoing receipt executed atomically: if any action in it fails (e.g. `create_account` fails because the `name.multisig_factory` account already exists, or the `new` init call on `multisig2` panics because of invalid `members`/`num_confirmations` arguments), the whole receipt's actions — including the `transfer` — are rolled back. The NEAR that was moved into the factory's balance by the `#[payable]` attribute is **not** returned to that receipt's originator; it simply remains sitting in the `MultisigFactory` contract's own account balance.

Unlike `lockup-factory`/`staking-pool-factory`, there is no callback to detect this failure and no method on `MultisigFactory` to withdraw or refund that residual balance to the original caller — the deposit is permanently unreachable, exactly mirroring the `ASDRouter._sendASD` bug where excess `msg.value` is not refunded and becomes permanently stuck with "no viable way to safely recover the native tokens."

### Impact Explanation
This breaks the equality `attached_deposit sent by caller == value delivered to the newly created multisig (or refunded to caller)`. Any unprivileged caller who supplies a `name` that collides with an already-created sub-account (a condition fully controllable/triggerable by any user, since `MultisigFactory::create` performs no existence check before issuing the `create_account` action) or otherwise causes the deployment receipt to fail loses their attached NEAR permanently, with the balance getting trapped in the `MultisigFactory` contract with no recovery mechanism. This matches the report's "Critical — funds permanently frozen" impact category.

### Likelihood Explanation
High. Triggering the failure path requires nothing more than calling `create` with a `name` that is already taken (which any user could pre-emptively deploy) or a `members`/`num_confirmations` combination that `multisig2::new` rejects. No privileged access, redeploy, or social engineering is needed — the caller only needs to attach NEAR and call the public `create` method.

### Recommendation
Add a callback to `MultisigFactory::create`, mirroring `on_lockup_create` / `on_staking_pool_create`: chain a `.then(ext_self::on_multisig_create(...))` that checks `is_promise_success()` and, on failure, transfers the deposit back to `env::predecessor_account_id()`. Alternatively, validate account-existence and input arguments before initiating the transfer so that failures cannot occur after the deposit has left the caller's control.

### Proof of Concept
1. Call `MultisigFactory::create` once with `name = "team"`, valid `members`, and `num_confirmations`, attaching e.g. 5 NEAR — this deploys `team.multisig_factory.near` successfully.
2. Call `MultisigFactory::create` again with the **same** `name = "team"` (or any name whose sub-account already exists), attaching another 5 NEAR.
3. The `create_account` action in the resulting receipt fails because the account already exists; per NEAR's atomic-receipt semantics, all actions in that receipt (including the `transfer`) are rolled back.
4. Because there is no `.then(...)` callback (unlike `on_lockup_create`/`on_staking_pool_create`), the 5 NEAR that was added to `MultisigFactory`'s balance by the `#[payable]` call is never returned to the caller, and `MultisigFactory` has no method to withdraw or forward this balance — it is permanently stuck.

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
