All the promise-callback sites in `lockup/src/owner_callbacks.rs` and `lockup/src/foundation_callbacks.rs` that update accounting after a transfer/stake/unstake/withdraw call to the staking pool properly gate the state update behind `is_promise_success()` (e.g. `on_staking_pool_deposit` [1](#0-0) , `on_staking_pool_deposit_and_stake` [2](#0-1) , `on_staking_pool_withdraw` [3](#0-2) , `on_staking_pool_stake`/`on_staking_pool_unstake`/`on_staking_pool_unstake_all` [4](#0-3) , and the termination-path callbacks in `foundation_callbacks.rs` [5](#0-4) [6](#0-5) ). This is the NEAR-equivalent safeguard to checking an ERC20 `transfer` return value, and it is present consistently.

The native NEAR `transfer()` method used in `lockup/src/owner.rs::transfer` and `w-near/src/w_near.rs::near_withdraw` uses `Promise::new(receiver_id).transfer(amount)` [7](#0-6) [8](#0-7) , which is a native runtime action, not an external contract call with a boolean-style return value — there is no analogous "unchecked return value" pattern here since native NEAR transfers either succeed at the protocol level or the whole transaction fails; there is no silent-failure return value to check, unlike a non-compliant ERC20 `transfer`.

    pub fn transfer(&mut self, amount: WrappedBalance, receiver_id: AccountId) -> Promise {
        self.assert_owner();

        self.assert_no_termination();
        assert!(
            self.get_liquid_owners_balance().0 >= amount.0,

            self.get_liquid_owners_balance().0,
            amount.0,
        );

        env::log(format!("Transferring {} to account @{}", amount.0, receiver_id).as_bytes());

        Promise::new(receiver_id).transfer(amount.0)
    }
