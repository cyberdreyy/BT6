### Title
Global-contract `AccountId` identifier binding survives account deletion, letting a new controller of a recreated `AccountId` silently redeploy code for all prior opted-in accounts - ([File: runtime/runtime/src/global_contracts.rs], [File: core/store/src/utils/mod.rs])

### Summary
`GlobalContractIdentifier::AccountId(id)` code is stored under `TrieKey::GlobalContractCode { identifier: GlobalContractCodeIdentifier::AccountId(id) }`, a namespace that is completely disjoint from `TrieKey::Account`/`TrieKey::ContractCode`. `action_delete_account`'s `remove_account` helper does not clear this key, so the global-contract entry outlives the account that created it. Because `action_deploy_global_contract`/`initiate_distribution` binds the identifier only to "whoever is currently the signer of account `id`" with no continuity check, a new, unrelated party who later obtains the same `AccountId` string can redeploy different code under that identifier and silently substitute it for every account that previously opted in via `UseGlobalContractAction` and never re-signed.

### Finding Description
- `GlobalContractIdentifier::AccountId(account_id)` is turned into the trie key `TrieKey::GlobalContractCode { identifier }` both on deploy (`apply_distribution_current_shard`, `runtime/runtime/src/global_contracts.rs:190-234`, writing at line 209-211) and on lookup (`use_global_contract`, `runtime/runtime/src/global_contracts.rs:75-97`, and `GlobalContractAccessExt::code`/`hash` in `runtime/runtime/src/contract_code.rs:91-117`). [1](#0-0) 
- `action_delete_account` computes storage usage to refund/subtract but ultimately delegates removal to `remove_account` (`core/store/src/utils/mod.rs:504-575`), which removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys, gas-key nonces, and contract data - but never touches `TrieKey::GlobalContractCode` or `TrieKey::GlobalContractNonce`. [2](#0-1) 
- `initiate_distribution` (`runtime/runtime/src/global_contracts.rs:142-170`) computes the identifier for `deploy_mode: AccountId` purely as `GlobalContractIdentifier::AccountId(account_id.clone())` - i.e. whichever account currently signs the deploy - with no check that this is the "original" or "same-key" owner of a pre-existing identifier of the same name. [3](#0-2) 
- `use_global_contract` only checks `state_update.contains_key(&key, ...)` for the `GlobalContractCode` trie key; it has no notion of "the account this identifier names is still alive" or "is still controlled by the same key" (`runtime/runtime/src/global_contracts.rs:75-97`). [4](#0-3) 
- Attack flow: (1) account `A` deploys a global contract with `deploy_mode: AccountId`, publishing code under identifier `AccountId(A)`. (2) Victim `V` submits `UseGlobalContractAction{contract_identifier: AccountId(A)}`, which sets `V.contract = AccountContract::GlobalByAccount(A)`. (3) `A`'s controller submits `DeleteAccountAction`; `A`'s `Account`/`ContractCode`/keys are removed, but the `GlobalContractCode{AccountId(A)}` and `GlobalContractNonce{AccountId(A)}` trie entries remain. (4) An unrelated attacker recreates an account literally named `A` (permissionless for sufficiently long top-level names, or as a sub-account under an attacker-controlled parent) and signs `DeployGlobalContractAction{deploy_mode: AccountId}` with new code. Since `initiate_distribution` only looks at "who is the current signer of account named `A`", this succeeds and overwrites `GlobalContractCode{AccountId(A)}`. (5) `V`'s contract resolution (`RuntimeContractIdentifier::resolve` / `GlobalContractAccessExt::code`) still points at `AccountContract::GlobalByAccount(A)` → identifier `AccountId(A)`, which now resolves to the attacker's new code, without `V` ever re-signing anything.
- None of the existing checks (signature verification, nonce monotonicity, access-key permissions, storage staking, `ContractSizeExceeded`) address this because they only protect the *current* transaction's signer/account, not the semantic continuity of the `AccountId`-keyed global-contract identity across account lifecycle events.

### Impact Explanation
This breaks authorization exactness: a victim account's executable code identity can be silently swapped by an unrelated third party without the victim's consent, after the victim had already opted in once. Since the substituted code fully controls the victim account's execution (function calls, promises, transfers), this enables theft of funds or arbitrary state manipulation on any account that used `UseGlobalContractAction{AccountId(A)}` prior to `A`'s deletion and recreation - matching "Contracts execution flows / Stealing or loss of funds."

### Likelihood Explanation
Preconditions: the attacker needs (a) to observe an existing `AccountId`-mode global contract, (b) wait for or induce the owning account's deletion (deletion is a self-inflicted or voluntarily-triggered action by the original owner, but once done, the window is open indefinitely since the stale trie entry never expires), and (c) recreate an account with the exact same name, which is permissionless either as a sufficiently-long top-level account or as a sub-account under a parent the attacker controls. All of this uses ordinary signed transactions available to any funded account; no validator/node privilege is required, no cost beyond standard account-creation and deploy fees. It is fully repeatable.

### Recommendation
Bind `AccountId`-mode global contract identity to something durable and non-reusable rather than the raw account-id string, e.g.:
- On `action_delete_account`, also clear (or invalidate) `TrieKey::GlobalContractCode`/`TrieKey::GlobalContractNonce` entries keyed by `GlobalContractCodeIdentifier::AccountId(account_id)` if that account owns such an identifier, or
- Track a distinct, immutable "owner generation"/account creation nonce as part of the `AccountId`-based identifier so a recreated account cannot silently inherit the previous incarnation's global-contract identity, or
- Disallow `UseGlobalContractAction`/contract resolution against an `AccountId` identifier whose owning account no longer exists or has been recreated since the victim's opt-in, forcing consumers to re-opt-in explicitly.

### Proof of Concept
Runtime/test-loop integration test (extending `test-loop-tests/src/tests/global_contracts.rs`):
1. Create account `A` (long top-level or attacker-parent subaccount) and victim `V`; fund both.
2. `A` submits `DeployGlobalContractAction{deploy_mode: AccountId, code: v1}`.
3. `V` submits `UseGlobalContractAction{contract_identifier: AccountId(A)}`; assert `V`'s `AccountContract` is `GlobalByAccount(A)` and calling `V`'s method returns v1 behavior.
4. `A`'s controller submits `DeleteAccountAction{beneficiary: A}`. Assert `TrieKey::Account{A}` is gone, but `store.get(&TrieKey::GlobalContractCode{identifier: AccountId(A)})` still returns v1 code.
5. A different, unrelated signer creates a new account literally named `A` (or a controlled-parent subaccount with the same leaf label to reproduce the same `AccountId` string) and submits `DeployGlobalContractAction{deploy_mode: AccountId, code: v2}` from that new account.
6. Without `V` signing anything further, call `V`'s method again and assert the result now reflects `v2` (e.g. via `RuntimeContractIdentifier::resolve` for `V` returning the new code hash, or via `ViewGlobalContractCodeByAccountId{account_id: A}` returning `v2`), proving the victim's bound global contract identity was silently hijacked.

    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,

    let identifier = match &global_contract_data.id() {
        GlobalContractIdentifier::CodeHash(hash) => GlobalContractCodeIdentifier::CodeHash(*hash),
        GlobalContractIdentifier::AccountId(account_id) => {
            GlobalContractCodeIdentifier::AccountId(account_id.clone())
        }
    };

    let is_nonce_fresh = check_and_update_nonce(global_contract_data, &identifier, state_update)?;
    if !is_nonce_fresh {
        return Ok(0);
    }

    let config = apply_state.config.wasm_config.clone();
    let trie_key = TrieKey::GlobalContractCode { identifier };
    let code_len = global_contract_data.code().len() as u64;

    state_update.commit(StateChangeCause::ReceiptProcessing { receipt_hash: receipt.get_hash() });
    let code_hash = match global_contract_data.id() {
        GlobalContractIdentifier::CodeHash(hash) => Some(*hash),
        GlobalContractIdentifier::AccountId(_) => None,
