### Title
Confirmations from a deleted multisig member remain counted toward `num_confirmations`, allowing a request to execute below the effective live-member threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
In both the `multisig` and `multisig2` contracts, when a member/key is removed via `DeleteKey` (v1) or `DeleteMember` (v2), the code only purges outstanding *requests originally authored by* that member — it never scrubs that member's prior *confirmations* left on other members' still-pending requests. Since `confirm()` counts raw set size (`confirmations.len()`) without validating that each recorded confirmer is still a current member, a stale confirmation from an already-removed member can still count toward reaching `num_confirmations`, letting a request execute with fewer *live* confirming members than the configured threshold.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` (and analogously `multisig/src/lib.rs`) executes a request once the confirmation set size reaches `num_confirmations`: [1](#0-0) 

The confirmation set is a plain `HashSet<String>` keyed by member identity, with no re-validation against the current `members` set at confirm-time or execute-time.

When a member is deleted, cleanup only targets requests where that member was the *original signer* (`r.member == member`), and only removes `num_requests_pk`/that member's own authored requests — not confirmations they placed on other members' requests: [2](#0-1) 

The v1 contract has the identical gap in the `DeleteKey` action handler, which filters outstanding requests by `r.signer_pk == pk` (the request's original signer) and removes that key's own request bookkeeping, but does not scan `confirmations` for entries where the deleted key had confirmed someone *else's* request: [3](#0-2) 

Because of this, the binding "confirmations counted == confirmations from live members" is broken: a confirmation recorded before a member's removal persists in state and is still summed by `confirm()`'s threshold check, `confirmations.len() as u32 + 1 >= self.num_confirmations`, even though that member no longer holds any authority (their access key/account has been deleted from the multisig).

### Impact Explanation
This falls under the Critical category "a multisig request executed below threshold": an attacker (or a colluding subset of members) can get a request executed with fewer currently-authorized approvals than `num_confirmations` requires, because a stale confirmation from a removed member is silently counted as if it were live. This directly weakens the K-of-N security guarantee the contract is designed to provide for high-value operations (transfers, key additions, contract upgrades, etc.).

### Likelihood Explanation
The precondition — a member confirming someone else's pending request and later being removed from the multisig before that request is confirmed by enough remaining members — is a plausible operational sequence in any active multisig with request cooldowns and multiple concurrently pending requests. No special privilege beyond being an unprivileged/former member is required to have left the stale confirmation; exploitation only requires the remaining members (who may not even realize a stale approval is counted) to push the request over threshold. This is a realistic misconfiguration/oversight scenario rather than a purely theoretical one, though it does require a `DeleteMember`/`DeleteKey` action to have been executed while another request was outstanding with that member's confirmation attached.

### Recommendation
On any member/key removal (`DeleteMember` in `multisig2`, `DeleteKey` in `multisig`), iterate over `requests`/`confirmations` for **all** outstanding requests (not just those authored by the removed member) and strip the removed member's entry from each request's confirmation set. Alternatively, validate at `confirm()`/execution time that every entry in `confirmations` still corresponds to a current member of `self.members`, discarding stale entries before comparing the count to `num_confirmations`.

### Proof of Concept
1. Initialize `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. Member `A` calls `add_request_and_confirm` for request `R` (transfer), yielding `confirmations[R] = {A}`.
3. Member `B` calls `confirm(R)` → `confirmations[R] = {A, B}` (still below 3, not executed).
4. Members `C` and `D` (or any 3 members reaching threshold on a separate self-request) execute a `DeleteMember { member: B }` request — this only removes requests where `r.member == B` (i.e., requests *authored* by B); it does not touch `confirmations[R]` since `R` was authored by `A`, so `confirmations[R]` still equals `{A, B}` even though `B` is now removed via `self.members.remove(&member)`. [4](#0-3) 
5. Member `C` (a genuine live member) calls `confirm(R)`. `confirmations.len() as u32 + 1 = 3 >= num_confirmations (3)` → `execute_request(R)` runs. [5](#0-4) 
6. Result: request `R` executed with confirmations from only 2 currently-live members (`A`, `C`) plus one stale confirmation from removed member `B`, even though the contract is configured to require 3 live confirmations.

Note: I was unable to execute this scenario against a live/compiled environment in this session (read-only code review only); the trace above is derived directly from the cited source and should be validated with an actual unit/integration test run (e.g., in `multisig2/src/lib.rs` test module) before treating it as confirmed-exploitable in production.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
