### Title
Unguarded `initializeConfig(address(0))` Permanently Bricks Bridge Committee — (`File: bridge/evm/contracts/BridgeCommittee.sol`)

### Summary

`BridgeCommittee.initializeConfig` is a public, access-control-free function that accepts a `_config` address without validating it against `address(0)`. Any unprivileged caller can invoke it with `address(0)` before the legitimate deployer does, permanently setting `committee.config` to the zero address and making every downstream bridge operation revert.

### Finding Description

`BridgeCommittee.initializeConfig` is declared `external` with no `onlyOwner`, no `onlyCommittee`, and no role guard of any kind. [1](#0-0) 

```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

The only guard is the idempotency check `address(config) == address(0)`, which is satisfied exactly once — during the deployment window between `BridgeCommittee.initialize` and the legitimate `initializeConfig` call. There is no `require(_config != address(0))` guard.

An attacker who observes the deployer's pending `initializeConfig(legitimateConfig)` transaction in the mempool can front-run it with `initializeConfig(address(0))`. Because `config` is still zero at that moment, the attacker's call succeeds and writes `IBridgeConfig(address(0))` into storage. The deployer's subsequent call then reverts with `"BridgeCommittee: Config already initialized"`, and the zero-address value is locked in permanently — there is no setter to overwrite it.

Every bridge operation that reaches `committee.config()` then calls a method on `address(0)`, which reverts: [2](#0-1) 

```solidity
IBridgeConfig config = committee.config();
// ...
require(
    tokenTransferPayload.targetChain == config.chainID(), ...
);
``` [3](#0-2) 

```solidity
address tokenAddress = committee.config().tokenAddressOf(tokenID);
// ...
return amount * committee.config().tokenPriceOf(tokenID) / (10 ** decimals);
```

### Impact Explanation

Once `config` is set to `address(0)`:

- `SuiBridge.transferBridgedTokensWithSignatures` reverts on `config.chainID()` — no EVM-side token unlocks are possible.
- `SuiBridge.bridgeERC20` / `bridgeETH` revert on `config.isTokenSupported` / `config.chainID()` — no new deposits are accepted.
- `BridgeLimiter.willAmountExceedLimit` and `recordBridgeTransfers` revert — the limiter modifier blocks all transfers.
- `BridgeConfig.updateTokenPriceWithSignatures` and `addTokensWithSignatures` revert — governance operations fail.
- `CommitteeUpgradeable.upgradeWithSignatures` still calls `verifyMessageAndSignatures`, which internally calls `committee.verifySignatures`; that function does not use `config`, so the upgrade path is technically reachable — but the upgraded implementation would still inherit the poisoned `config` slot.

Any ERC-20 or ETH already deposited into `BridgeVault` before the attack becomes permanently unclaimable on the EVM side, satisfying the "permanent fund lock" impact class. [4](#0-3) 

### Likelihood Explanation

The attack window is the block interval between `BridgeCommittee.initialize` and `initializeConfig`. On Ethereum mainnet this is a single-block front-run opportunity visible to any mempool observer. The attacker needs only a standard EOA and enough gas — no special privilege, no stake, no committee membership. The cost is one transaction; the damage is irreversible.

### Recommendation

Add a non-zero address check and restrict the caller to the contract owner or a trusted deployer role:

```solidity
function initializeConfig(address _config) external onlyOwner {
    require(_config != address(0), "BridgeCommittee: Invalid config address");
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

Alternatively, pass `_config` directly into `initialize` and remove `initializeConfig` entirely, eliminating the two-step race condition.

### Proof of Concept

1. Deployer broadcasts `BridgeCommittee.initialize(members, stakes, minStake)` — succeeds.
2. Deployer broadcasts `BridgeCommittee.initializeConfig(0xLegitimateConfig)`.
3. Attacker observes the pending tx and broadcasts `BridgeCommittee.initializeConfig(address(0))` with higher gas.
4. Attacker's tx is mined first: `config = IBridgeConfig(address(0))` is written; event emitted with zero address.
5. Deployer's tx reverts: `"BridgeCommittee: Config already initialized"`.
6. Any subsequent call to `SuiBridge.transferBridgedTokensWithSignatures` reaches `committee.config().chainID()`, which is a call to `address(0)`, and reverts — all vault funds are permanently locked. [1](#0-0) [5](#0-4) [2](#0-1)
