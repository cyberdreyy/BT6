### Title
Reorg-timing check can be bypassed via `saturating_sub` clock-order flip, permitting an unwarranted tenure reorg - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg a prior tenure that already produced a globally-accepted block. The decision hinges on how much time passed between this signer's approval of that tenure's first block and the arrival of the reorging sortition's burn block. Because the elapsed time is computed with `saturating_sub`, a reversed ordering of the two timestamps (approval recorded *after* the new burn block was already seen) silently clamps to zero, which the code interprets as "the block was approved right on top of the sortition" — the exact signature of a poorly-timed, RBF-vulnerable tenure — and wrongly grants the reorg permit. This is the same class of bug as the reported liquidation issue: a decision threshold (`first_proposal_burn_block_timing`) is evaluated against a value that can silently become "0" without any real grace period, letting a subsequent miner cash in on a reorg that should have been rejected.

### Finding Description
In `check_parent_tenure_choice`: [1](#0-0) 

```

    let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
```

`sortition_state_received_time` is when *this signer* observed the new (reorging) burn block, taken from `signer_db.get_burn_block_receive_time`. `approved_at` is `local_block_info.approved_time`, stamped when this signer pre-committed or locally accepted the tenure's first block [2](#0-1) . The code assumes `sortition_state_received_time >= approved_at` (the block was approved before the next sortition). But block validation is asynchronous and can take up to `block_proposal_validation_timeout` (default 120s) [3](#0-2) , while a new Bitcoin block can legitimately arrive sooner. If the new burn block is observed by this signer *before* it finishes pre-committing/accepting the prior tenure's first block, `approved_at > sortition_state_received_time`, and `saturating_sub` returns `0` instead of a (meaningless) negative duration. `Duration::from_secs(0) < first_proposal_burn_block_timing` is then always true, so the tenure is treated as "poorly timed" and the reorg is granted — `record_superseded_tenure` is called, which subsequently makes any signature this signer holds over that tenure's block stop counting as a conflict (`reorg_permit_stands`) [4](#0-3) .

This function is invoked both from the proposal path and from `validate_tenure_change_payload`, i.e. it directly gates whether a signer will sign a tenure-change block that reorgs an already-established (possibly globally accepted) tenure: [5](#0-4) [6](#0-5) .

### Impact Explanation
This flips the reorg-timing safety check — meant to protect a tenure that had *plenty* of time before being reorged (i.e. "established long enough for the incoming miner to RBF any outdated commit" per the config docs) [7](#0-6)  — into a check that fires open exactly when the opposite is true. A miner that simply wins the very next sortition while another signer's validation of the prior tenure's first block is still pending can have that tenure treated as "poorly timed" and get it superseded, clearing the way for this signer to contribute its signature toward reorging away an already-approved/globally-accepted block. This falls under signing a non-canonical/conflicting block — a Critical-class outcome — since it undermines the equivocation/conflict guard that the whole reorg-timing and `reorg_permit_stands` mechanism exists to enforce, from a single miner's ordinary timing rather than any majority collusion.

### Likelihood Explanation
No adversarial clock manipulation is required — only ordinary asynchronous latency between burn-block delivery and block-proposal validation completion, which is entirely plausible given validation timeouts of up to 120s versus Bitcoin's natural block-time variance (Poisson-distributed; sub-minute blocks are not rare). A single next-sortition miner (no majority of signers, no key compromise) simply needs to propose a reorging tenure-change block after this ordering coincidence occurs on some subset of signers.

### Recommendation
Do not use `saturating_sub` here to compute the interval; explicitly detect and handle the case where `approved_at > sortition_state_received_time` (e.g., treat it as "not poorly timed" / reject the reorg, or use a signed/optional duration and short-circuit to `false` when the values are reversed) so that a delayed-validation ordering can never be mistaken for a fast, RBF-vulnerable proposal.

### Proof of Concept
1. Miner A wins a sortition and proposes tenure A's first (and only) block; this signer receives it and begins validating.
2. Validation is slow (near `block_proposal_validation_timeout`); before it completes, Miner B wins the next sortition. This signer's burn-block-arrival handler records `sortition_state_received_time` for the new sortition.
3. Validation then completes and this signer pre-commits/accepts tenure A's block, stamping `approved_time` *after* `sortition_state_received_time`.
4. Miner B proposes a tenure-change block whose parent tenure is not A's, i.e. a reorg of tenure A.
5. `check_parent_tenure_choice` computes `sortition_state_received_time.saturating_sub(approved_at) == 0`, which is `< first_proposal_burn_block_timing`, so the reorg is granted and tenure A is marked superseded — even though tenure A was legitimately established, with the signer's own delayed processing being the only reason the check triggered.

```rust
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
```
