### Title
ETH sent with a withdraw request is permanently locked in the ephemeral `EthenaCooldownRequest` clone - (File: contracts/IdleCDOEthenaVariant.sol)

### Summary
`IdleCDOEthenaVariant._withdraw` forwards `msg.value` into the freshly created `EthenaCooldownRequest` clone, but neither the clone nor the CDO has any path to return native ETH to the user. The clone's only sweep function, `rescue`, is restricted to `TL_MULTISIG` and only transfers ERC20 balances, so any ETH sent along with `withdrawAA`/`withdrawBB` is permanently locked.

### Finding Description
In `IdleCDOEthenaVariant._withdraw` (contracts/IdleCDOEthenaVariant.sol:42-92), after burning tranche tokens and computing `SUSDeRedeemed`, the contract deploys a per-request clone and forwards the call's full `msg.value`:

```solidity
EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
  abi.encodePacked(address(this), msg.sender),
  msg.value
));
``` [1](#0-0) 

ETH plays no role in the withdraw flow: the cooldown operates entirely on sUSDe/USDe (`strategyToken` is transferred separately at line 87). The bug mirrors the external report's pattern — a payable function accepts ETH even though the operation does not require it, and there is no refund path.

The receiving clone, `EthenaCooldownRequest` (contracts/strategies/ethena/EthenaCooldownRequest.sol), exposes only three state-changing functions: `startCooldown` (callable only by the CDO), `unstake` (sends sUSDe proceeds to the user), and `rescue`:

```solidity
function rescue(address _token) external {
  require(msg.sender == TL_MULTISIG, '6');
  IERC20Detailed(_token).transfer(msg.sender, IERC20Detailed(_token).balanceOf(address(this)));
}
``` [2](#0-1) 

`rescue` treats `_token` as ERC20 and calls `balanceOf`/`transfer`, so native ETH in the clone cannot be recovered through it. There is no `receive`/fallback logic returning ETH, no `selfdestruct`, and no payable-sending function. The clone address is deterministic per `(cdo, user)` immutable args, but a user issuing multiple withdraws gets a distinct clone each time, each capable of holding stranded ETH.

### Impact Explanation
Permanent freezing of user funds. Any ETH attached to `withdrawAA`/`withdrawBB` is locked forever in the clone contract: the user cannot withdraw it, and even the honest `TL_MULTISIG` cannot recover it because `rescue` only handles ERC20 tokens. Loss equals the full `msg.value` sent.

### Likelihood Explanation
Moderate. It requires a user (or a frontend/router batching calls) to attach ETH to a withdraw transaction — a plausible mistake since deposit flows on related gateways (`LidoCDOTrancheGateway.depositAAWithEth`) are payable and users may assume withdraws also interact with ETH. The contract gives no revert or warning; `msg.value` is silently forwarded into an unrecoverable address.

### Recommendation
Either reject ETH on the withdraw path (`require(msg.value == 0)`) or pass `0` as the clone creation value instead of `msg.value`. Alternatively, add an ETH sweep in `EthenaCooldownRequest` payable to `_getUser()`.

### Proof of Concept
Foundry fork test (mainnet fork, Ethena sUSDe variant pool):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../contracts/IdleCDOEthenaVariant.sol";
import "../contracts/strategies/ethena/EthenaCooldownRequest.sol";

contract LockedEthPoC is Test {
    IdleCDOEthenaVariant cdo; // deployed variant instance
    address user = address(0xA11CE);

    function test_ethLockedInCooldownClone() public {
        // user holds AA tranche tokens; sUSDe cooldownDuration != 0
        uint256 trancheBal = IERC20Detailed(cdo.AATranche()).balanceOf(user);
        vm.deal(user, 1 ether);

        // predict clone address via CREATE2 / clones-with-immutable-args formula,
        // or capture it from the NewCooldownRequestContract event
        vm.recordLogs();
        vm.prank(user);
        cdo.withdrawAA{value: 1 ether}(0); // redeem full balance, attach 1 ETH

        // parse emitted clone address
        Vm.Log[] memory logs = vm.getRecordedLogs();
        address clone;
        for (uint i; i < logs.length; i++) {
            if (logs[i].topics[0] == keccak256("NewCooldownRequestContract(address,address,uint256)")) {
                clone = address(uint160(uint256(logs[i].topics[1])));
            }
        }

        // ETH is stuck in the clone
        assertEq(clone.balance, 1 ether);
        assertEq(user.balance, 0);

        // no user-callable path returns ETH:
        // unstake() only moves sUSDe proceeds; rescue() is TL_MULTISIG-only and ERC20-only
        vm.prank(user);
        EthenaCooldownRequest(clone).unstake(); // reverts until cooldown ends; never touches ETH
        assertEq(clone.balance, 1 ether); // ETH permanently locked
    }
}
```

Note: this PoC assumes `withdrawAA`/`withdrawBB` on the variant are payable (required for `msg.value` to be non-zero). I was unable to fully confirm the `payable` modifier on the external withdraw entry points in `IdleCDO.sol` within the available search context; if they are non-payable, `msg.value` is always zero and the issue is unreachable — that signature should be verified before finalizing severity.
