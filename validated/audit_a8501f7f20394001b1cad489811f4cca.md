### Title
BridgeResource.Show leaks plaintext bridge OutgoingToken to view-role users - ([File: core/web/presenters/bridges.go])

### Summary
`BridgeTypesController.Show` (`GET /v2/bridge_types/:BridgeName`) is mounted with no role restriction beyond basic authentication, and `presenters.NewBridgeResource` always populates `OutgoingToken` (JSON tag `outgoingToken`, no `omitempty`) from the plaintext `bridges.BridgeType.OutgoingToken` field stored in the DB. Any authenticated user with the lowest privilege (`view` role) or a valid API token can retrieve this secret for any bridge by name.

### Finding Description
The route table wires `bt.Show` directly under the generic `authv2` group without `auth.RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole`, unlike `Create`, `Update`, and `Destroy` which require edit role: [1](#0-0) . `BridgeTypesController.Show` calls `presenters.NewBridgeResource(bt)` and returns it directly: [3](#0-2) . `NewBridgeResource` copies `b.OutgoingToken` (plaintext, stored as-is in `BridgeType.OutgoingToken`) into the resource's `OutgoingToken` field, which is serialized unconditionally (`json:"outgoingToken"`, no `omitempty`), unlike `IncomingToken` which does have `omitempty` and is only populated by the `Create` handler: [4](#0-3) . `bridges.BridgeType` stores `OutgoingToken` in plaintext (not hashed, unlike `IncomingTokenHash`+`Salt`): [5](#0-4) . Since `RequiresRunRole` and `RequiresEditRole` are the only functions that reject `UserRoleView`, and `Show` uses neither, a `view`-role session or API token is sufficient to hit this endpoint and receive the bridge's `OutgoingToken` in the response body.

### Impact Explanation
`OutgoingToken` is a credential the node uses when calling out to the external bridge/adapter (used for outbound authentication to the adapter). Disclosure of it to a low-privileged (`view`-role) user lets that user impersonate the node's authenticated calls to the external adapter, or use it to probe/abuse the adapter's API under the node's identity — a credential/secret disclosure impact scoped to bridge external-initiator/adapter secrets. This is exactly the invariant the question highlights: like `UserResource` must never leak `TokenKey`/`HashedPassword`, `BridgeResource` should not leak `OutgoingToken` to users below edit/admin privilege.

### Likelihood Explanation
Trivially reachable: any valid authenticated principal (session cookie or API token) with only `view` role can issue `GET /v2/bridge_types/<name>` for any bridge name (bridge names are typically discoverable via `GET /v2/bridge_types` index, which is also unauthenticated-by-role — only requires general auth). No additional bypass or timing is needed; it's deterministic and repeatable for every existing bridge.

### Recommendation
Redact `OutgoingToken` (and any other bridge secret) from `BridgeResource` when the requesting user's role is below `edit`/`admin`, or remove `OutgoingToken` from the `Show`/`Index` response entirely and only return connection metadata (name, URL, confirmations), mirroring how `IncomingToken` is only ever returned once at creation time via `BridgeTypeAuthentication`. Alternatively, gate `bt.Show` (and `Index`) behind `auth.RequiresEditRole` similar to `Create`/`Update`/`Destroy`.

### Proof of Concept
Go handler-level integration test plan (extending `TestBridgeController_Show` in `core/web/bridge_types_controller_test.go`):
1. Create an admin-role test app/DB and a bridge via `app.BridgeORM().CreateBridgeType` with a known `OutgoingToken`.
2. Create a second user with `sessions.UserRoleView` (or an API token scoped to view role) using existing test helpers (e.g. `cltest.MustRandomUser` with role `view` + `client.NewHTTPClient` sessioned as that view user).
3. As the view-role client, issue `GET /v2/bridge_types/<bridgeName>`.
4. Assert HTTP 200 and parse the JSONAPI response into `presenters.BridgeResource`.
5. Assert `resource.OutgoingToken` equals the plaintext token created in step 1 (proving disclosure) — expected/fixed behavior should instead assert `resource.OutgoingToken` is empty/masked for a view-role caller, analogous to `UserResource` never exposing `HashedPassword`/`TokenKey`.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
