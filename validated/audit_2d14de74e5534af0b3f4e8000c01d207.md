### Title
Stale-Reject Weight Never Cleared When a Signer Flips to Accept, Corrupting the Node's Aggregated Rejection/Acceptance Tally - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node-side `StackerDBListener` maintains two independent weight counters per proposed block, `total_weight_approved` and `total_weight_rejected`, keyed off a single `responded_signers` set that is supposed to make each signer's vote count exactly once [1](#0-0) . The guard only works in one direction: for a `Rejected` message the code checks `block.responded_signers.insert(slot_id)` before adding to `total_weight_rejected`, but for an `Accepted` message it checks a *different* set, `block.gathered_signatures.contains_key(&slot_id)`, before adding to `total_weight_approved` [2](#0-1) [3](#0-2) . If a signer first rejects a block (its weight is added to `total_weight_rejected` and its slot is marked in `responded_signers`) and later legitimately re-evaluates and signs the same block (a transition the signer state machine explicitly allows: `LocallyRejected --> LocallyAccepted : re-evaluated`, per the signer flow documentation and `BlockInfo::check_state`), the node adds that signer's weight into `total_weight_approved` as well, without ever removing it from `total_weight_rejected`. The same signer's weight is now double-counted across both tallies.

### Finding Description
The signer-side state machine documented in `docs/signer-flows.md` explicitly allows a block to move `LocallyRejected --> LocallyAccepted` on re-evaluation (e.g. when `should_reevaluate_reject_reason` decides an earlier rejection reason no longer applies) [4](#0-3) . When that happens the signer broadcasts a fresh `BlockResponse::Accepted` for the very same `signer_signature_hash` it had previously rejected.

On the node side, `SignerCoordinator`/`StackerDBListener` tallies these responses to decide whether to keep waiting, treat the block as accepted, or abandon it as rejected [5](#0-4) . The bookkeeping for `Rejected` correctly uses a "have we already counted this slot" gate via `responded_signers.insert(slot_id)`, returning `true` only the first time a given slot is recorded [3](#0-2) . But the `Accepted` branch checks membership in `gathered_signatures` — a completely different map that is empty until an *accept* is received — so a slot that is already present in `responded_signers` (because it previously rejected) is *not* excluded here [6](#0-5) . The result: the signer's weight is added into `total_weight_approved` while remaining stuck in `total_weight_rejected`.

This breaks the intended equality that "aggregated weight == sum of currently-valid votes." After the flip, `total_weight_approved + total_weight_rejected` can exceed `total_weight` for that signer's contribution, i.e., the same signer's weight is simultaneously counted as an accept and a reject. This corrupts both the "70% approved -> accept" and the "30%+ rejected -> abandon" decisions made in `get_block_status`/`propose_block` [7](#0-6) : a block can simultaneously appear to be crossing the rejection-abandon threshold (using stale reject weight from a signer who has since accepted) while also genuinely accumulating approvals, and the node has no way to tell which of the two counters reflects the signer's *current* vote.

### Impact Explanation
This falls under the "aggregated-weight vs verified-accepts" equality break category. The observable consequence is a miscounted response: a signer's rejection is retained in the tally even after that same signer legitimately accepted the block, inflating `total_weight_rejected` beyond the number of signers who currently reject the block. Depending on signer-weight distribution, this stale rejection weight can push `total_weight_rejected` over `total_weight - weight_threshold`, causing the coordinator to return `NakamotoNodeError::SignersRejected` and abandon a block proposal that a real supermajority has (or is about to) accept — a liveness wedge on that specific tenure/block. It does not require compromising any signer key, colluding with a majority, or bypassing signature verification: it is triggered purely by the sanctioned reject→accept re-evaluation path combined with the listener's asymmetric bookkeeping.

### Likelihood Explanation
The `LocallyRejected -> LocallyAccepted` re-evaluation transition is a normal, expected part of the signer state machine (not an edge case requiring an attacker) — it happens whenever a rejection reason becomes stale/re-evaluable (`should_reevaluate_reject_reason`) while the block is still alive, which is explicitly designed for and exercised in the codebase's block lifecycle documentation. Any single honest signer that reconsiders after an initial reject during a live tenure (a scenario the protocol wants to support so that borderline rejections don't permanently kill a block) will trip this bug against the node it is talking to. No majority collusion or key compromise is needed — it is a single-signer, single-message-pair trigger plus normal gossip/relay of that signer's two responses to the coordinating node.

### Recommendation
Track a single per-slot "current vote" state (e.g., an enum `Accepted`/`Rejected` keyed by `slot_id`) instead of the two independently-gated counters `gathered_signatures`/`responded_signers` vs. `total_weight_rejected`. When a new response arrives for a slot that already has a recorded vote, first back out the previous vote's weight from whichever tally it was counted in, then add the new vote's weight to the correct tally, ensuring a signer's weight is reflected in at most one of `total_weight_approved` / `total_weight_rejected` at any time.

### Proof of Concept
1. Node proposes block `B` (`signer_signature_hash = H`) to the signer set via `SignerCoordinator::propose_block`.
2. Signer `S` (weight `w`) initially rejects `B` for some reason later deemed stale (e.g., a transient chainstate mismatch) and broadcasts `BlockResponse::Rejected` for `H`. `StackerDBListener` processes this: `responded_signers.insert(slot_S)` succeeds, `total_weight_rejected += w` [3](#0-2) .
3. `S`'s local state machine re-evaluates `B` via `should_reevaluate_reject_reason`/`should_reevaluate_block` and transitions `LocallyRejected -> LocallyAccepted`, broadcasting `BlockResponse::Accepted` for the same `H`.
4. `StackerDBListener` processes the accept: `gathered_signatures.contains_key(slot_S)` is `false` (this is the first accept from `S`), so `total_weight_approved += w` is executed [2](#0-1) . `total_weight_rejected` is never decremented.
5. Now `S`'s weight `w` is counted in both `total_weight_approved` and `total_weight_rejected` for block `B` simultaneously, even though `S` currently only endorses `B`. If enough other signers also reject (independently, honestly) such that `total_weight_rejected > total_weight - weight_threshold`, `get_block_status` returns `Err(NakamotoNodeError::SignersRejected { .. })` [7](#0-6) , abandoning the block proposal even though the "current" rejecting weight (excluding `S`, who has since accepted) may be below the abandon threshold.

Note: full confirmation of the exact `should_reevaluate_reject_reason` trigger conditions and every caller of `SignersRejected` in `miner.rs` was constrained by the available tool budget; the state-transition existence (`LocallyRejected -> LocallyAccepted`) is documented explicitly in `docs/signer-flows.md`, and the asymmetric counter logic in `stackerdb_listener.rs` was directly read and confirmed.
