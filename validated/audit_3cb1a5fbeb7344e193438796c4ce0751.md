### Title
Gateway Message replay within the freshness window causes repeated web_api_trigger fan-out with no per-message dedup - ([File: core/services/gateway/api/message.go])

### Summary
`Message.Validate()` in `core/services/gateway/api/message.go` only checks field lengths/format and recovers the signer via `ExtractSigner()`; it performs no nonce, timestamp, or digest freshness check. The only freshness control in the call path is an application-level timestamp staleness check inside the web-API-trigger handler, but that check tolerates exact replays within its configured window and there is no message-ID/digest dedup at the gateway or handler layer for this flow.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) decodes the raw bytes, and for legacy messages calls `msg.Validate()` (`core/services/gateway/api/message.go:54-88`), which only validates lengths/null-suffixes and extracts/attaches the signer address — it stores no record of previously-seen `(Signature, Body)` pairs, so a byte-identical resend passes `Validate()` every time.

The request is then routed to the DON handler via `HandleLegacyUserMessage`. For the capabilities/web-API-trigger handler (`core/services/gateway/handlers/capabilities/handler.go:341-421`), the only freshness gate is the payload's own `Timestamp` field: [1](#0-0) 
This rejects messages older than `MaxAllowedMessageAgeSec`, but it does **not** reject a message that is replayed again *within* that window. The handler unconditionally records the (possibly overwritten) callback and re-broadcasts to every DON member on each call: [2](#0-1) 
The adjacent `// TODO: apply allowlist and rate-limiting here` comment confirms no such control exists yet.

By contrast, other subsystems in the same codebase (e.g. the Vault gateway processor) explicitly implement a `RequestReplayGuard` that deduplicates by request digest with expiry — showing the team is aware of, and mitigates, exactly this class of issue elsewhere, but not for the legacy `web_api_trigger` message path validated by `api.Message`. Downstream, only the V2 workflow execution engine independently deduplicates by `TriggerEventID`/workflow via `ExecutionsStore.Add` returning `ErrDuplicateExecution` (`core/services/workflows/v2/engine.go:769-790`); this protects V2 workflow executions specifically but is not a property of the gateway/message layer itself, and any consumer of `HandleLegacyUserMessage`/`processTrigger` that does not route through that specific execution-store check has no replay protection at all.

### Impact Explanation
An attacker holding one previously captured signed `Message` (same `Signature`, same `Body`) can resend the identical raw bytes to `gateway.ProcessRequest` repeatedly for the remainder of the `MaxAllowedMessageAgeSec` window. Each resend passes `Validate()`, is fanned out to every DON member again, and consumes gateway/DON processing resources (repeated signature verification, HTTP work in `sendHTTPMessageToClient`, node bandwidth) — this maps to the "unauthorized/duplicate job triggering" and resource-exhaustion impact classes. Actual duplicate pipeline execution is only prevented where a downstream consumer independently implements idempotency (as the V2 engine does); the gateway/message layer itself provides no such guarantee.

### Likelihood Explanation
Precondition is trivial: any captured legitimate signed message (sniffed, logged, or given by a user) can be replayed by an unauthenticated party any number of times before it becomes stale. No additional privilege is required, and the attack is fully repeatable within the freshness window.

### Recommendation
Add replay protection at the `api.Message`/gateway layer analogous to the Vault `RequestReplayGuard` (digest of `Signature`+`Body`, or `Sender`+`MessageId`, tracked with TTL) and reject duplicates in `Message.Validate()` or in `gateway.ProcessRequest` before dispatch to handlers, rather than relying solely on handler-specific timestamp staleness checks or downstream execution-store dedup.

### Proof of Concept
Go test in `core/services/gateway/gateway_test.go`:
1. Build a signed legacy `web_api_trigger` message with a valid `Timestamp` using `newSignedLegacyRequest`.
2. Call `gw.ProcessRequest(ctx, rawBytes, "")` once against a mock handler; assert the handler's `HandleLegacyUserMessage` is invoked and returns success.
3. Call `gw.ProcessRequest(ctx, rawBytes, "")` again with the exact same `rawBytes` (unchanged) before the timestamp exceeds `MaxAllowedMessageAgeSec`.
4. Assert the second call is **not** rejected (i.e., `HandleLegacyUserMessage`/`don.SendToNode` is invoked a second time) — demonstrating no duplicate/stale rejection exists at the gateway/handler layer for identical replayed bytes.
