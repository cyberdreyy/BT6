### Title
Post-default instant-withdraw requests are written into the finalized default epoch's claim bucket, letting new receipts spend recovery reserve and freezing legitimate claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` has no post-default branch (unlike `requestWithdraw`, which routes into `postDefaultRequests`). After `finalizeDefaultRecovery`, `epochNumber` no longer advances, so a new instant request is recorded in `instantWithdrawsRequestsByEpoch[user][epochNumber]` where `epochNumber == defaultRecoveryEpoch`. On claim, `_claimDefaultedInstantWithdrawRequest` treats that bucket as defaulted-epoch basis and pays it from `defaultRecoveryReserve` — reserve that `finalizeDefaultRecovery` sized only for pre-default claims. The CVE analog (backward-mode bitblt writing outside the intended copy region) maps directly: a "copy" that writes into an already-finalized region, corrupting accounting past its boundary.

### Finding Description
- `requestInstantWithdraw` mints a receipt and increments `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `pendingInstantWithdraws` with no `defaultRecoveryFinalized` check. [1](#0-0) 
- `finalizeDefaultRecovery` snapshots `defaultRecoveryEpoch = epochNumber` and computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` from only pre-default basis. [2](#0-1) 
- On claim, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` — which now includes the attacker's post-default request — burns the receipt and calls `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve`. [3](#0-2) 
- It also saturates `pendingInstantWithdraws` (`claimBasis >= pending ? 0 : pending - claimBasis`), hiding the inflation. [4](#0-3) 

Because the reserve was sized only for the pre-default basis, every post-default instant claim paid through `_transferDefaultRecovery` consumes reserve belonging to legitimate defaulted claimants. Once the reserve is depleted, later `_transferDefaultRecovery` calls underflow and revert, permanently freezing the unclaimed recovery. [5](#0-4) 

Additionally, `postDefaultRequests` users are blocked from re-requesting if `instantWithdrawsRequests[user] != 0`, but instant requesters get no equivalent funded path — their claim is forced through the defaulted-epoch haircut bucket.

### Impact Explanation
Theft and permanent freezing of unclaimed default-recovery funds. The attacker deposits pre-default (or holds tranche tokens), waits for default finalization, then calls `requestInstantWithdraw` for amount X and claims it at `defaultRecoveryPrice` from the reserve — extracting recovery funds earmarked for defaulted-epoch claimants. When legitimate claimants later call `claimWithdrawRequest`/`claimInstantWithdrawRequest`, `defaultRecoveryReserve -= amount` reverts, freezing their recovery permanently. Loss is bounded by the attacker's tranche holdings but directly drains the isolated reserve, breaking the "one receipt one payout" and donation-isolation invariants.

### Likelihood Explanation
Requires: a pool that has defaulted and been finalized via `finalizeDefaultRecovery`, and the CDO forwarding `requestInstantWithdraw` post-default. The strategy itself places no post-default guard on this path (contrast with `requestWithdraw`'s explicit `defaultRecoveryFinalized` branch), suggesting the flow is reachable whenever the CDO exposes it — e.g., pool-closed/emergency sequences where instant withdrawals remain enabled. If the CDO reverts all instant requests once `defaulted()`, the finding reduces to defense-in-depth; that gating could not be fully confirmed in this pass.

### Recommendation
In `requestInstantWithdraw`, revert when `defaultRecoveryFinalized` is true, or route post-default instant receipts into a separate post-default bucket (mirroring `postDefaultRequests`) so they can never land in `defaultRecoveryEpoch`'s claim basis. Independently, make `_claimDefaultedInstantWithdrawRequest` use a per-epoch basis recorded strictly before finalization (snapshot `instantWithdrawClaimsByEpoch` at finalize time) rather than the live mapping.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }
```
