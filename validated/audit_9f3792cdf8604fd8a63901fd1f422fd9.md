### Title
Cross-user response hijacking via unauthenticated `MessageId` collision in `savedCallbacks` - (`core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`h.savedCallbacks` is keyed solely by the client-supplied `msg.Body.MessageId` string, and `HandleLegacyUserMessage` writes to that map with no existence/ownership check before overwriting an entry. An unprivileged gateway client who submits a second legacy `web_api_trigger` request using the same `message_id` as another user's still-pending request silently replaces the victim's callback, so when the node's real response for that `MessageId` arrives, `handleWebAPITriggerMessage` delivers it to the attacker instead of the victim.

### Finding Description
`MessageId` originates entirely from the client-controlled JSON body field `message_id` (`core/services/gateway/api/message.go` MessageBody.MessageId, json tag `message_id`), and is not gateway-generated or bound to a specific session/user: [1](#0-0) 

When a legacy user request is processed in `gateway.ProcessRequest`, the handler for the request's `DonId` is invoked with the client's message as-is: [2](#0-1) 

`HandleLegacyUserMessage` then stores the user's callback in `h.savedCallbacks` keyed by this attacker/user-controlled `MessageId`, with **no check whether the key already exists**: [3](#0-2) 

If Victim A already has a pending trigger request with `MessageId = X` sitting in `savedCallbacks["X"]`, Attacker B can submit their own (independently, validly signed with B's own key) `web_api_trigger` request that also sets `message_id = "X"`. Because the map write is unconditional, B's callback silently overwrites A's in `savedCallbacks["X"]`.

Later, when a legitimate DON node responds to A's original request, its response message still carries `MessageId = "X"` (nodes echo back the ID they received). `HandleNodeMessage` only validates that `msg.Body.Sender == nodeAddr` (i.e., that the response really came from that connected node) — it does not validate that the response corresponds to the request that created that `savedCallbacks` entry: [4](#0-3) 

`handleWebAPITriggerMessage` then looks up `savedCallbacks["X"]`, finds B's callback (which overwrote A's), and forwards A's response — including whatever payload the trigger produced — to B: [5](#0-4) 

There is no verification that `msg.Body.Sender`/`Receiver` or any request-scoped nonce ties the response back to the exact HTTP client session that submitted it; the only binding key is the attacker-controlled `MessageId` string, and there is no collision protection on that key. A code comment in the test suite even flags this exact gap: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` (`core/services/gateway/handlers/capabilities/handler_test.go:365`).

### Impact Explanation
This allows an unauthenticated/unprivileged gateway client to hijack another user's webAPI trigger response by colliding on `MessageId`, resulting in cross-user response/data leakage — matching the "cross-user response confusion" / unauthorized disclosure of another user's response data impact class. Depending on what data the trigger payload carries back (e.g., workflow trigger acknowledgement content), this can leak information intended only for the victim's HTTP client.

### Likelihood Explanation
Exploitability requires only: (1) knowledge or predictable guessing of a pending `MessageId` (client-chosen strings up to 128 bytes, no server-side randomization enforced) and (2) knowledge of a valid `DonId` (generally not secret — DON IDs are part of node/gateway config and often discoverable). No node, operator, or admin access is needed — just a valid keypair to sign an otherwise well-formed legacy `web_api_trigger` request, i.e., the same capability any regular gateway client already has. The race window is bounded by `CallbackMaxAgeSec` (default 120s), which is generous enough for a targeted collision attempt.

### Recommendation
- Reject (or fail loudly on) `HandleLegacyUserMessage` calls whose `MessageId` already exists in `h.savedCallbacks`, rather than silently overwriting.
- Generate/derive `MessageId` (or an internal correlation key) server-side per accepted request instead of trusting the raw client-supplied value for map indexing, or namespace the key by `(Sender, MessageId)`/session token.
- In `handleWebAPITriggerMessage`, additionally verify that the responding node was actually one of the DON members the original request was fanned out to for that saved callback (bind DON membership/request context to the saved callback, not just the raw ID).

### Proof of Concept
Go unit test plan (in `core/services/gateway/handlers/capabilities/handler_test.go` style, using `setupHandler`):
1. Build `victimMsg := triggerRequest(t, nodes[0].PrivateKey, ..., messageID="X", ...)` and call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`; assert `handler.savedCallbacks["X"]` is `victimCallback`'s entry.
2. Build `attackerMsg` signed with a *different* private key (attacker's own key, still validly signed) but with the same `Body.MessageId = "X"`; call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)`.
3. Assert `handler.savedCallbacks["X"]` now points to `attackerCallback` (overwrite confirmed, no error returned).
4. Simulate the legitimate node response for the victim's original request: `resp, _ := hc.ValidatedResponseFromMessage(victimMsg)`; call `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)`.
5. Assert `attackerCallback.Wait(ctx)` returns the victim's response payload, while `victimCallback.Wait(ctx)` times out/never resolves — proving cross-user response delivery with no sender/DON binding check.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	msg, err := common.ValidatedMessageFromResp(resp)
	if err != nil {
		return err
	}
	if msg.Body.Sender != nodeAddr {
		return errors.New("message sender mismatch when reading from node ")
	}
	start := time.Now()
	switch msg.Body.Method {
	case MethodWebAPITrigger:
		err = h.handleWebAPITriggerMessage(ctx, msg, nodeAddr)
	case MethodWebAPITarget, MethodComputeAction, MethodWorkflowSyncer:
		err = h.handleWebAPIOutgoingMessage(ctx, msg, nodeAddr)
	default:
		err = fmt.Errorf("unsupported method: %s", msg.Body.Method)
	}
	h.metrics.recordHandleDuration(ctx, time.Since(start), msg.Body.Method, err == nil)
	return err
}
