### Title
ETH Decimal Truncation in `bridgeETH`/`bridgeETHV2` Permanently Locks User Funds in BridgeVault — (File: `bridge/evm/contracts/SuiBridge.sol`, `bridge/evm/contracts/SuiBridgeV2.sol`)

---

### Summary

`bridgeETH` and `bridgeETHV2` forward the full `msg.value` to the `BridgeVault`, then compute the on-Sui amount by integer-dividing by `10^10` (the 18→8 decimal factor). Any sub-`10^10`-wei remainder is silently discarded from the bridge message and permanently locked in the vault as WETH, with no refund path and no recovery mechanism.

---

### Finding Description

`BridgeUtils.convertERC20ToSuiDecimal` performs integer division without a remainder check:

```solidity
// bridge/evm/contracts/utils/BridgeUtils.sol  lines 141-142
uint256 factor = 10 ** (erc20Decimal - suiDecimal);   // 10^10 for ETH
amount = amount / factor;                              // truncates silently
``` [1](#0-0) 

`bridgeETH` (V1 and V2) forwards the entire `msg.value` to the vault **before** the conversion is computed:

```solidity
// bridge/evm/contracts/SuiBridge.sol  lines 207-221
uint256 amount = msg.value;
(bool success,) = payable(address(vault)).call{value: amount}("");   // full ETH in
require(success, "SuiBridge: Failed to transfer ETH to vault");

uint64 suiAdjustedAmount = BridgeUtils.convertERC20ToSuiDecimal(
    IERC20Metadata(config.tokenAddressOf(BridgeUtils.ETH)).decimals(),
    config.tokenSuiDecimalOf(BridgeUtils.ETH),
    amount                                                            // truncated here
);
emit TokensDeposited(..., suiAdjustedAmount, ...);                   // only truncated amount recorded
``` [2](#0-1) 

The same pattern is present in `SuiBridgeV2.bridgeETHV2`: [3](#0-2) 

The vault's `receive()` immediately wraps any incoming ETH into WETH:

```solidity
// bridge/evm/contracts/BridgeVault.sol  lines 68-72
receive() external payable {
    if (msg.sender != address(wETH)) {
        wETH.deposit{value: msg.value}();
    }
}
``` [4](#0-3) 

`BridgeVault.transferETH` and `transferERC20` are `onlyOwner` (the bridge contract), and the bridge contract only calls them when processing a verified claim from Sui. Because the truncated wei is never recorded in any bridge message, it can never be claimed and is permanently locked. [5](#0-4) 

---

### Impact Explanation

Every call to `bridgeETH`/`bridgeETHV2` with an ETH amount that is not an exact multiple of `10^10` wei permanently locks up to `10^10 − 1` wei (≈ 9.99 Gwei) in the vault. The bridge message records only the truncated Sui-decimal amount; the remainder is wrapped into WETH inside the vault and has no claim path. This is a **permanent fund lock** matching the "High or Medium" impact class. The loss per transaction is small but real, irrecoverable without a privileged vault-owner action, and accumulates across all ETH bridge deposits.

---

### Likelihood Explanation

Any ordinary bridge user who sends ETH with a non-round wei value (e.g., any amount not divisible by `10^10`) triggers the lock. Because ETH amounts are typically specified in ether or Gwei by wallets and CLIs, sub-`10^10`-wei remainders are routine. The `bridgeETH` function is public and payable; no special role is required. [6](#0-5) 

---

### Recommendation

Before forwarding ETH to the vault, compute the truncated amount and refund the remainder to `msg.sender`:

```solidity
uint256 factor = 10 ** (erc20Decimal - suiDecimal);   // 10^10 for ETH
uint256 truncated = (amount / factor) * factor;
uint256 dust = amount - truncated;

(bool ok,) = payable(address(vault)).call{value: truncated}("");
require(ok, "SuiBridge: Failed to transfer ETH to vault");

if (dust > 0) {
    (bool refunded,) = payable(msg.sender).call{value: dust}("");
    require(refunded, "SuiBridge: Failed to refund dust");
}
```

Alternatively, revert if `amount % factor != 0`, forcing callers to supply exact amounts.

---

### Proof of Concept

1. User calls `bridgeETH{value: 1 ether + 1 wei}(recipientAddress, destinationChainID)`.
2. Vault receives `1_000_000_000_000_000_001` wei; `receive()` wraps it all into WETH.
3. `convertERC20ToSuiDecimal(18, 8, 1_000_000_000_000_000_001)` = `1_000_000_000_000_000_001 / 10^10` = `100_000_000` (truncated; `1 wei` discarded).
4. `TokensDeposited` emits `suiAdjustedAmount = 100_000_000` (1 ETH in Sui decimals).
5. Bridge mints exactly 1 ETH worth of tokens on Sui.
6. The `1 wei` is permanently locked in the vault as WETH — no bridge message references it, no claim path exists.

The same applies to `bridgeETHV2` in `SuiBridgeV2.sol` and to `bridgeERC20`/`bridgeERC20V2` when called with WETH (18-decimal ERC-20), where the user-specified amount may also carry a sub-`10^10`-wei remainder. [7](#0-6) [8](#0-7)

    function convertERC20ToSuiDecimal(uint8 erc20Decimal, uint8 suiDecimal, uint256 amount)
        internal
        pure
        returns (uint64)
    {
        if (erc20Decimal == suiDecimal) {
            // ensure provided amount is greater than 0
            require(amount > 0, "BridgeUtils: Insufficient amount provided");
            // Ensure converted amount fits within uint64
            require(amount <= type(uint64).max, "BridgeUtils: Amount too large for uint64");
            return uint64(amount);
        }

        require(erc20Decimal > suiDecimal, "BridgeUtils: Invalid Sui decimal");

        // Difference in decimal places
        uint256 factor = 10 ** (erc20Decimal - suiDecimal);
        amount = amount / factor;

        // Ensure the converted amount fits within uint64
        require(amount <= type(uint64).max, "BridgeUtils: Amount too large for uint64");

        // Ensure the converted amount is greater than 0
        require(amount > 0, "BridgeUtils: Insufficient amount provided");

        return uint64(amount);
    }
