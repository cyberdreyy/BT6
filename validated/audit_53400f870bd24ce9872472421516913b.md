### Title
`MultisigFactory::create` Has No Failure Callback — Front-Running the Sub-Account Name Permanently Freezes the Caller's Attached NEAR - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` issues a single promise batch (`create_account` → `deploy_contract` → `transfer` → `function_call`) to a deterministic sub-account name (`{name}.{factory}`), but unlike the sibling factories in this repo it has **no callback** to detect failure and refund the caller. An unprivileged attacker can pre-create the target sub-account name, causing the victim's later `create` call to fail atomically on-chain (since `create_account` cannot succeed on an already-existing account). Because the failed receipt's refund is returned to the predecessor of that failed receipt — the `MultisigFactory` contract itself, not the original caller — and the `MultisigFactory` struct exposes no other method to recover or forward that balance, the victim's attached NEAR becomes permanently stuck in the factory contract.

### Finding Description
`create` builds one promise batch and returns it directly, with no `.then(ext_self::on_create(...))` callback: [1](#0-0) 

Compare this to `staking-pool-factory`, which performs the identical account-creation pattern but adds a callback (`on_staking_pool_create`) that checks `is_promise_success()` and, on failure, explicitly refunds the `attached_deposit` back to `predecessor_account_id` (the original caller): [2](#0-1) 

In `MultisigFactory::create`, `env::attached_deposit()` is transferred as part of the same promise batch that also runs `create_account()`. If the target account (`{name}.{factory}`) already exists — e.g., because an attacker submitted their own `create` call with the same `name` first — the `create_account()` action fails, and NEAR fails the entire batch atomically. The refund for the failed receipt's actions goes to the predecessor of that receipt, which is the `MultisigFactory` contract account (the entity that issued the promise), not the original transaction signer. Since `MultisigFactory` has no owner, no withdrawal method, and no callback logic at all, that NEAR has no code path to ever be returned to the victim or withdrawn by anyone.

This breaks the custody binding: value debited from the victim (the attached deposit charged on their `create` transaction) is not equal to value delivered (0 — no multisig created, no refund reaching the victim); the difference is permanently trapped in the factory contract.

### Impact Explanation
This is Critical: an unprivileged attacker, by simply front-running a `create` call with the same `name` parameter (no elevated privileges required), can cause any user's attached NEAR deposit to be permanently frozen with no recovery path, since `MultisigFactory` exposes no method to move or refund funds sitting on its own account. This differs from mere gas griefing/DoS (which is out of scope) because actual NEAR value is irrecoverably lost, not just wasted gas — the victim can retry with a different name, but the deposit from the failed attempt stays locked in the factory contract forever.

### Likelihood Explanation
Any account can call `create` with an arbitrary `name`; observing a pending `create` transaction (e.g. via a public RPC/mempool) and submitting a competing transaction with the same `name` and sufficient gas/priority to land first is a purely mempool-front-running action requiring no privileged role, no victim key, and no protocol/node compromise — well within the "unprivileged attacker" scope.

### Recommendation
Add a callback analogous to `staking-pool-factory::on_staking_pool_create` / `lockup-factory::on_lockup_create`: split `create` into the account-creation promise followed by `.then(ext_self::on_create(deployed_account_id, attached_deposit, predecessor_account_id, ...))`, and in the callback check `is_promise_success()`; on failure, explicitly `Promise::new(predecessor_account_id).transfer(attached_deposit)` to return the funds to the original caller.

### Proof of Concept
1. Victim signs a transaction calling `MultisigFactory::create(name: "orgA", members: [...], num_confirmations: 1)` with an attached deposit of e.g. 50 NEAR, targeting sub-account `orgA.factory`.
2. Before the victim's transaction is included, an attacker submits their own `create` call with `name: "orgA"` (any `members`/deposit), which is included first and successfully creates `orgA.factory`.
3. The victim's transaction executes on-chain: `create()` itself doesn't revert (no validation on `name` uniqueness), so the deposit is charged to the victim and forwarded into the outgoing promise batch. That batch's `create_account()` action on `orgA.factory` fails because the account already exists, so the whole receipt (including the `transfer(attached_deposit)` action) fails atomically.
4. Per NEAR protocol refund semantics, the failed receipt's balance is refunded to its predecessor — the `MultisigFactory` contract account — not to the victim.
5. `MultisigFactory` has no method to move, withdraw, or forward that balance (`multisig-factory/src/lib.rs` defines only `create`), so the victim's 50 NEAR is permanently stuck in the factory contract.

    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
