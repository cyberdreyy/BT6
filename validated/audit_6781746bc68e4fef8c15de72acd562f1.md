### Title
Stale confirmations from removed multisig members still count toward execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges confirmations for requests that the removed member *authored*, but it never scans the `confirmations` map to strip that member's entry from requests **authored by other members that the removed member had already confirmed**. Because `confirm()` simply counts the size of the stored `HashSet<String>` against `self.num_confirmations` without re-validating that every entry still belongs to a current member, a removed member's stale confirmation continues to count toward the K-of-N threshold, allowing a request to execute with fewer *live* confirmations than the configured `num_confirmations`.

### Finding Description
The multisig's core custody binding is: `live confirmations on a request >= num_confirmations` before `execute_request` runs. `confirm()` enforces this only in terms of raw set size: [1](#0-0) 

`delete_member` is supposed to keep the confirmation bookkeeping consistent with the member set, but its cleanup is scoped only to requests where `r.member == member`, i.e. requests the removed member *created*: [2](#0-1) 

It removes the member from `self.members` and deletes the member's own outstanding requests, but it does **not** iterate `self.confirmations` to remove the departing member's identifier from confirmation sets of requests that were created by *other* members. `assert_valid_request` (called from `confirm`) also never re-validates the identities already stored inside an existing confirmation set — it only checks that the *current caller* is a member: [3](#0-2) 

So a confirmation recorded by a member before that member was removed remains valid forever, silently counted alongside confirmations from members still active.

### Impact Explanation
This breaks the equality "confirmations counted == confirmations from live members," which is exactly the custody boundary the K-of-N multisig scheme exists to enforce. A request (e.g. a `Transfer` action moving NEAR out of the multisig account) can be executed with contributions from a member who has since been removed, effectively lowering the real threshold below the configured `num_confirmations`. Per the rules, "a multisig request executed below threshold" is a **Critical** impact: it allows an unauthorized or under-authorized transfer of funds out of the multisig account.

### Likelihood Explanation
No malicious member action is required — this is triggered purely by the contract's own documented lifecycle: create request → some members confirm → membership changes (a normal `DeleteMember` request, which is a routine operation the README documents, e.g. offboarding a departed team member or rotating a compromised key) → remaining/new members finish confirming. The bug is deterministic and reproducible in every deployment of `multisig2` that ever removes a member while other requests are pending.

### Recommendation
When deleting a member, iterate over all entries in `self.confirmations` and remove the departing member's identifier from every confirmation set (not just requests it authored), or alternatively validate on every `confirm()` call that all existing entries in the confirmation set still correspond to current `self.members` before comparing the count to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request(R)` to transfer funds to an external account (not auto-confirmed).
3. `B` calls `confirm(R)` → confirmations = `{B}`.
4. `C` calls `confirm(R)` → confirmations = `{B, C}` (2 of 3, request stays pending).
5. Members legitimately submit and confirm a separate `DeleteMember { member: C }` request that reaches quorum and executes: `C` is removed from `self.members`, but `delete_member` only cleans requests authored by `C`; `R` was authored by `A`, so `R`'s confirmation set `{B, C}` is untouched.
6. `D` calls `confirm(R)` → confirmations = `{B, C, D}`, size 3 ≥ `num_confirmations` (3) → `execute_request` runs and the transfer executes, even though only `B` and `D` are still legitimate members confirming (2 live confirmations), one short of the intended 3-of-4 threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
