## Title
Non-atomic secondary account fetch during SPL-token JSON-parsing yields inconsistent balance/interest-rate data for a single reported slot - (File: `rpc/src/parsed_token_accounts.rs`)

### Summary
`get_parsed_token_account` and `get_parsed_token_accounts` decode an SPL-token account's UI balance using "additional data" (decimals, `InterestBearingConfig`, `ScaledUiAmountConfig`) fetched from the token's **mint account in a second, independent bank read**, performed strictly after the token account itself was already read. When the RPC caller uses `processed` commitment, the `bank` handed to these functions is the still-mutating "working bank" (not yet frozen), so a market/mint authority can update the mint's extension state between the two reads within the same RPC call, causing the JSON-parsed response to combine a token-account balance from time T1 with mint metadata from time T2 while reporting both under one `context.slot`.

### Finding Description
`get_parsed_token_account` in [1](#0-0)  takes an already-fetched `account`, extracts the mint pubkey from its raw bytes, and then performs a **separate** lookup of the mint account via `account_resolver::get_account_from_overwrites_or_bank(&mint_pubkey, bank, overwrite_accounts)`, later calling `get_additional_mint_data(bank, mint_account.data())` which reads `bank.clock().unix_timestamp` and extension fields such as `InterestBearingConfig`/`ScaledUiAmountConfig` [2](#0-1) . This is invoked from `get_encoded_account` for `getAccountInfo`/`getMultipleAccounts` [3](#0-2) , and the batched variant `get_parsed_token_accounts` is used for `getProgramAccounts`, `getTokenAccountsByOwner/Delegate`, and pubsub program/account subscriptions [4](#0-3) [5](#0-4) [6](#0-5) .

The `bank` used is selected by `JsonRpcRequestProcessor::bank()`, which for non-`confirmed` commitment levels returns whatever bank `BankForks` reports at the computed slot [7](#0-6) . For `processed` commitment this resolves to the current *working* (leader/replay) bank, which is explicitly **not frozen** while transactions continue to be applied to it — `BankForks::working_bank()` simply returns the bank at `highest_slot()` regardless of freeze state [8](#0-7) , and other code paths explicitly guard against concurrent mutation of the same working bank via a `freeze_lock()` precisely because "the bank forks lock released ... the bank can not be frozen until this tx batch has been processed" while it is still being written to concurrently [9](#0-8) .

Because `get_parsed_token_account`/`get_parsed_token_accounts` issue two independent, unsynchronized reads (token account, then mint account) against this same mutable working bank with no lock held across both reads, a mint authority instruction that updates `ScaledUiAmountConfig`/`InterestBearingConfig` (or otherwise re-initializes the mint) executed by the working bank in between the two reads is visible to the second read but not the first. The RPC response nonetheless wraps both values in a single `RpcResponse` whose `context.slot` implies one consistent snapshot (`new_response(&bank, ...)`), and pubsub notifications likewise report a single `slot` for the combined value [10](#0-9) .

### Impact Explanation
This produces a decoder that silently **misreports** account data: the returned `UiTokenAmount`/`uiAmount` (and derived interest/scaled-multiplier fields) can reflect a combination of token-account and mint state that never coexisted at any single bank slot, even though the response claims a single consistent `context.slot`. Any unprivileged client using `processed` commitment (the default for many wallets/indexers) for `getAccountInfo`, `getMultipleAccounts`, `getProgramAccounts`, `getTokenAccountsByOwner/Delegate`, or `accountSubscribe`/`programSubscribe` with `jsonParsed` encoding can receive and act on this internally-inconsistent, mis-reported value — falling squarely under "decoder panic and misreporting" / "wrong ... account data returned" from a query.

### Likelihood Explanation
Any account/program owner authorized to update mint extension config (e.g., `ScaledUiAmountConfig` rate authority) can trigger this simply by submitting an update transaction that lands in the same slot as a client's `processed`-commitment query; no special validator/operator privilege is required to observe the effect, and `processed` is a normal, commonly-used commitment level.

### Recommendation
Snapshot the token account and its mint account from the same bank state atomically (e.g., resolve both pubkeys' accounts in a single indexed read, or reject/normalize `processed` commitment for `jsonParsed` encoding, mirroring the existing `check_is_at_least_confirmed` guard used elsewhere) so a single response cannot mix account and mint states observed at different points during an unfrozen bank's execution.

### Proof of Concept
1. Create an SPL-Token-2022 mint with a `ScaledUiAmountConfig` extension and an authority able to update the multiplier.
2. A client repeatedly calls `getAccountInfo`/`accountSubscribe` for a token account of that mint with `{"encoding":"jsonParsed","commitment":"processed"}`.
3. Concurrently, the mint authority submits an `UpdateMultiplier` (or equivalent) instruction that lands in the same, still-unfrozen working bank being used to serve the RPC request.
4. Depending on scheduling, `get_token_account_mint`/first read in `get_parsed_token_account` happens before the update while the subsequent `bank.get_account(mint)` happens after it (or vice versa), so the returned `tokenAmount`/`uiAmount` is computed from a decimal/multiplier value that did not correspond to the token balance actually stored at the reported `context.slot`.

pub fn get_parsed_token_account(
    bank: &Bank,
    pubkey: &Pubkey,
    account: AccountSharedData,
    // only used for simulation results
    overwrite_accounts: Option<&HashMap<Pubkey, AccountSharedData>>,

        .and_then(|mint_pubkey| {

            spl_token_additional_data: Some(data),
        });

    encode_ui_account(
        pubkey,
        &account,
        UiAccountEncoding::JsonParsed,
        additional_data,
        None,
    )
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}

fn get_encoded_account(
    bank: &Bank,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
    // only used for simulation results
    overwrite_accounts: Option<&HashMap<Pubkey, AccountSharedData>>,
) -> Result<Option<UiAccount>> {
    match account_resolver::get_account_from_overwrites_or_bank(pubkey, bank, overwrite_accounts) {
        Some(account) => {
            let response = if is_known_spl_token_id(account.owner())
                && encoding == UiAccountEncoding::JsonParsed
            {
                get_parsed_token_account(bank, pubkey, account, overwrite_accounts)
            } else {
                encode_account(&account, pubkey, encoding, data_slice)?
            };
            Ok(Some(response))
        }
        None => Ok(None),
    }
}
