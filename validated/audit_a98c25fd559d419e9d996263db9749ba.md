### Title
Instant-withdraw path in `requestWithdraw` skips management and performance fees entirely, letting a lender exit fee-free while normal withdrawers pay - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.requestWithdraw` has two branches. The normal branch computes `_totalWithdrawFees(principal, interest)` (upfront management fee plus net performance fee) and deducts it from the receipt. The instant-withdraw branch — taken when the new epoch APR dropped more than `instantWithdrawAprDelta` — calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` on the full tranche value and returns early, before any fee is computed. The result is the same bug class as the external report: a conditional branch applies a different effective fee rate, so the party that should have collected the fee (the honest `feeReceiver`/`owner`) loses it.

### Finding Description
In `IdleCDOEpochVariant.sol`:

```solidity
if (_isInstantWithdrawEnabled()) {
  uint256 currentApr = creditVault.unscaledApr();
  if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
    creditVault.requestInstantWithdraw(_underlyings, msg.sender);
    _withdrawOps(_amount, _underlyings, _tranche);
    return _underlyings;   // <-- no _totalWithdrawFees, no pendingWithdrawFees
  }
}
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
``` [1](#0-0) 

The documented rationale for the upfront management fee is that "Receipts leave live NAV at request time but can be claimed only after the next epoch settles", so they are charged for the time spent outside live NAV. Instant receipts also leave live NAV and sit unfunded for `instantWithdrawDelay` (claimable only after `getInstantWithdrawFunds`), yet pay zero management fee and zero performance fee. Every other withdrawal path — normal requests, APR0 requests (`_requestWithdrawApr0` receives `_amount` already net of the upfront management fee) — charges the fee.

### Impact Explanation
A KYC-passed lender can avoid all withdrawal fees simply by timing `requestWithdraw` for the buffer window right after `stopEpoch` sets a lower `unscaledApr` (a recurring, honest manager action once per epoch whenever rates drop). The evaded amount is `_calculateManagementFee(principal, duration)` plus the performance fee that would otherwise accrue to `feeReceiver`/`owner` — on a 1M USDC principal with a 1% mgmt fee and a ~5-day delay this is on the order of ~140 USDC per withdrawal, repeatable every epoch across all tranche holders. Loss accrues to the honest fee recipients; this is theft of unclaimed yield, not a rounding dust issue.

### Likelihood Explanation
Triggering conditions are all external/honest-driven: instant withdraws enabled (`disableInstantWithdraw == false`, non-programmable borrower) and an APR decrease exceeding `instantWithdrawAprDelta`, both caused by the honest manager's `stopEpoch`. Any allowed wallet can then call `requestWithdraw`. No privileged misbehavior required. The only caveat is whether fee-free instant exits are intentional design; the code contains no comment exempting instant receipts from fees, while the fee's own justification (time spent outside live NAV) applies equally to instant receipts waiting `instantWithdrawDelay`.

### Recommendation
Apply the same fee logic before branching: compute `totalFees = _totalWithdrawFees(principal, interest)` (or at minimum the management fee for the `instantWithdrawDelay` wait), subtract it from `_underlyings`, and add it to `pendingWithdrawFees` before calling `requestInstantWithdraw`, so both exit paths charge a consistent effective fee rate.

### Proof of Concept
A Foundry fork PoC would: (1) deposit AA for an attacker wallet, (2) run `startEpoch`, (3) `stopEpoch` with `newApr = lastApr - instantWithdrawAprDelta - 1`, (4) call `cdoEpoch.requestWithdraw(attackerBal, AATranche)` in the buffer — the returned amount equals full principal with `pendingWithdrawFees` unchanged, while an identical-sized normal `requestWithdraw` (or the same request one block earlier with APR unchanged) returns `principal + interest - _totalWithdrawFees` and increments `pendingWithdrawFees`. Assert `requestedInstant == principal` and `pendingWithdrawFees == 0` versus the non-zero fee on the normal path to demonstrate the skipped charge.

Note: I could not fully confirm within the available context that skipping fees on instant withdrawals is unintended rather than a deliberate design choice; if intended, no valid analog exists.
