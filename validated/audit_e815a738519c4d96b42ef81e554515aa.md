### Title
`claimInstantWithdrawRequest` pays unfunded instant receipts without verifying funding, draining earmarked normal-claim funds and leaving the request double-counted - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2016-4951 (dump operation on a socket whose existence was never verified), `IdleCreditVault.claimInstantWithdrawRequest` pays out `instantWithdrawsRequests[_user]` whenever the strategy holds underlying, without checking that the request was actually funded — i.e., that `collectInstantWithdrawFunds` ran and decremented `pendingInstantWithdraws`. An unfunded instant receipt survives across epochs and can be claimed during the buffer phase right after `stopEpoch`, when the strategy balance contains funds earmarked for normal withdraw claimants. The instant request remains in `pendingInstantWithdraws` / `instantWithdrawClaimsByEpoch`, so it is funded again later — a double spend that steals other claimants' money.

### Finding Description
`requestInstantWithdraw` mints a strategy-token receipt and bumps `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]` and `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). Funding happens separately when the CDO calls `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls underlying into the strategy (lines 398-403).

`claimInstantWithdrawRequest` (lines 380-393) does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

There is no check that the receipt's epoch was funded — no `epochNumber > requestEpoch` gate like `_claimFundedWithdrawRequest` has (line 326), no per-epoch funded flag, and `_transferFundedClaim` (lines 897-907) only guards the `defaultRecoveryReserve`, not normal-claim earmarked balances. The CDO-side wrapper `IdleCDOEpochVariant.claimInstantWithdrawRequest` only checks the `allowInstantWithdraw` flag (IdleCDOEpochVariant.sol:975-978), so it is callable in any epoch phase, including buffer.

Consequences when an instant receipt is claimed before being funded:
- It consumes underlying that `collectWithdrawFunds` placed in the strategy for *normal* withdraw claimants (lines 411-430), so the last normal claimant's transfer reverts — direct theft of their funded claim.
- `pendingInstantWithdraws`, `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are not cleared, so the request is still counted: a later `collectInstantWithdrawFunds` pulls the amount again from the CDO (double funding), and on default `instantWithdrawClaimsByEpoch[epochNumber]` inflates `_defaultPrefundedInstantReserve`/`defaultPendingClaimBasis`, mispricing `defaultRecoveryPrice` (lines 685-696, 716-723).

### Impact Explanation
Direct theft / insolvency. An unprivileged lender (tranche holder, KYC'd or not depending on pool config) requests an instant withdraw in a running epoch and does not wait for `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`. If the epoch stops before funding is collected, the strategy holds the normal claimants' freshly collected `pendingWithdraws`; the attacker calls `claimInstantWithdrawRequest` during the buffer and receives up to that balance. The same request is then funded again at the next `collectInstantWithdrawFunds`, so the vault pays the receipt twice: once out of normal claimants' earmarked funds and once out of borrower repayments, breaking the "one receipt one payout" invariant and the solvency of the funded-claim bucket. Loss is bounded by the attacker's instant request size, capped by the funded normal-claim balance.

### Likelihood Explanation
Requires only that an instant withdrawal is left unfunded through an epoch boundary — e.g., the request was made inside `instantWithdrawDelay` so `getInstantWithdrawFunds` could not run before `stopEpoch`, or manager timing simply lapsed. All actor calls involved (requestInstantWithdraw via `cdoEpoch.requestWithdraw` in instant mode, `claimInstantWithdrawRequest`) are unprivileged. The claim path has no phase gate beyond `allowInstantWithdraw`, which must already be enabled for the request to exist. Uncertainty: I could not fully verify that `stopEpoch`/`getInstantWithdrawFunds` never force-collects `pendingInstantWithdraws` at epoch end; if it does, the exploit window narrows to cases where funding reverted or was skipped.

### Recommendation
In `claimInstantWithdrawRequest`, verify existence-and-funding before paying: track a funded epoch/marker (e.g., require `epochNumber > requestEpoch` or a per-epoch `instantFunded` flag set by `collectInstantWithdrawFunds`), and clear `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]` and `pendingInstantWithdraws` when a receipt is consumed so a paid receipt cannot be funded again.

### Proof of Concept
Foundry fork skeleton (mainnet fork per existing tests in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. Buffer: user deposits AA, epoch starts (fixed-APR mode, instant enabled via
//    cdoEpoch.setInstantWithdrawParams by manager, honest).
// 2. Running epoch: attacker calls cdoEpoch.requestWithdraw(amount, AAtranche)
//    inside instantWithdrawDelay window -> strategy.requestInstantWithdraw mints
//    receipt, pendingInstantWithdraws += amount. Manager does NOT call
//    getInstantWithdrawFunds (or delay not yet elapsed when stopEpoch hits).
// 3. Honest manager stops epoch; borrower repays; collectWithdrawFunds pulls
//    normal pendingWithdraws underlying into the strategy.
// 4. Buffer: attacker calls cdoEpoch.claimInstantWithdrawRequest()
//    -> IdleCreditVault.claimInstantWithdrawRequest burns the receipt and
//    _transferFundedClaim transfers `amount` of the normal claimants' funds.
//    assert: attacker underlying balance increased; pendingInstantWithdraws
//    still includes `amount`; instantWithdrawClaimsByEpoch[epoch] unchanged.
// 5. Next getInstantWithdrawFunds/stopEpoch collects `amount` again for the
//    already-paid receipt -> the pool paid twice; the last normal claimant's
//    claimWithdrawRequest reverts on insufficient strategy balance.
```

Note: full PoC requires confirming `stopEpoch` does not force-settle `pendingInstantWithdraws` — that call path in `IdleCDOEpochVariant` could not be fully read within this session.
