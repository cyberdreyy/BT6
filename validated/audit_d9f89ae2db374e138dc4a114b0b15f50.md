### Title
Unbounded `activeRequests` map growth in the Confidential Relay gateway handler enables a request-flooding DoS via unauthenticated/unprivileged JSON-RPC calls - (File: core/services/gateway/handlers/confidentialrelay/handler.go)

### Summary
The `processFees()` bug class is an unbounded-array-growth DoS: an attacker-influenced storage collection (`_heldFeesOf[_projectId]`) grows without any cap check, and a periodic function iterates over the whole collection, eventually exceeding the gas limit and bricking fee distribution. The Chainlink Gateway's `confidentialrelay` handler has the same root-cause shape in Go: `activeRequests` is a map keyed by attacker-supplied request IDs with no maximum-size enforcement, and two periodic goroutines (`removeExpiredRequests`, `forwardGracedRequests`) fully scan this map on every tick.

### Finding Description
`handler.HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 characters before calling `h.newActiveRequest(req, callback)`, which unconditionally inserts a new entry into `h.activeRequests` keyed by the caller-supplied `req.ID`: [1](#0-0) [2](#0-1) 

Unlike the generic `RequestCache` abstraction used elsewhere in the gateway, which explicitly caps the number of pending entries and rejects new ones once full: [3](#0-2) 

`newActiveRequest` in `confidentialrelay/handler.go` performs no equivalent `len(h.activeRequests) >= max` check — the only rejection path is a duplicate-ID collision. There is also no user-facing/per-sender rate limiter guarding `HandleJSONRPCUserMessage` itself; the only rate limiters present (`globalNodeRateLimiter`, `perNodeRateLimiters`) are applied to *node* responses in `HandleNodeMessage`, not to incoming user requests: [4](#0-3) 

Entries only leave the map after `requestTimeout` (default 30s) via the periodic `removeExpiredRequests` sweep, which itself does a full linear scan of `activeRequests` under a lock every `defaultCleanUpPeriod` (1 second): [5](#0-4) [6](#0-5) 

`forwardGracedRequests`, invoked on the same ticker, performs an identical full scan: [7](#0-6) 

Because request IDs are attacker-chosen and unbounded in count (only length-capped per ID), a caller able to reach the gateway's confidential-relay method (`MethodSecretsGet` / `MethodCapabilityExec`) can submit an arbitrarily large number of distinct-ID requests within the 30-second timeout window, each allocating a map entry, a `sync.Mutex`, and triggering a full `fanOutToNodes` broadcast to every DON member. This directly mirrors the `_heldFeesOf` growth pattern from the report: an externally-triggered collection that grows unboundedly and is fully iterated by a periodic maintenance routine, degrading to a DoS as the collection size increases (memory growth plus O(n) lock-held scans every second, and quadratic-ish load on the DON via repeated fan-outs).

### Impact Explanation
Sustained request flooding causes: (1) unbounded heap growth in `activeRequests` bounded only by 30s worth of attacker throughput, (2) the per-second cleanup ticker holding `h.mu` (RLock then a second Lock pass) while scanning an ever-larger map, increasingly delaying legitimate `HandleNodeMessage`/`HandleJSONRPCUserMessage` calls that also take `h.mu`, and (3) amplification, since every accepted request triggers `fanOutToNodes` to all DON members, multiplying attacker traffic by DON size. This is a service-availability (DoS) issue against the gateway's confidential-relay capability, not a fund-loss or key-disclosure bug, so impact is bounded to availability degradation of that specific gateway handler.

### Likelihood Explanation
Likelihood depends on what network/auth layer sits in front of this handler (e.g., whether the gateway's HTTP endpoint requires a signed/authenticated `Sender` before dispatch). I could not fully confirm within the available index whether an anonymous internet client can reach `confidentialrelay.HandleJSONRPCUserMessage` without prior DON/workflow authentication, since the top-level `gateway.ProcessRequest` decode/auth path (`jsonrpc2.DecodeRequest`) is defined outside the indexed portion of this repo. Compared to the `vault` handler, which requires `requestProcessor.ProcessRequest` authorization before calling `newActiveRequest` for all methods except the aggressively-cached `MethodPublicKeyGet`, the `confidentialrelay` handler performs no equivalent authorization/allowlist check before admitting a request into `activeRequests`. If the gateway's front door allows any DON member sender (not a privileged/admin-only actor) to hit this method, the flood is trivially reachable from an unprivileged client.

### Recommendation
Add an explicit cap on `len(h.activeRequests)` in `newActiveRequest` (mirroring `requestCache.maxCacheSize`), reject new requests once the cap is reached, and/or add a per-sender/global incoming rate limiter to `HandleJSONRPCUserMessage` analogous to the ones already applied to node responses in `HandleNodeMessage`.

### Proof of Concept
Not independently exploitable/verifiable from static code alone since I could not confirm the exact authentication requirements upstream of `HandleJSONRPCUserMessage` for this handler in the indexed codebase. Conceptually: repeatedly send JSON-RPC requests with method `MethodSecretsGet`/`MethodCapabilityExec` and unique `req.ID` values (≤200 chars) faster than the 30s `requestTimeout` can expire them; each call inserts an entry via `newActiveRequest` with no cap check, growing `h.activeRequests` and forcing full-map scans in `removeExpiredRequests`/`forwardGracedRequests` every second while fanning out to every DON member per request.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) forwardGracedRequests(ctx context.Context) {
	h.mu.RLock()
	var graced []*activeRequest
	now := h.clock.Now()
	for _, ar := range h.activeRequests {
		if ar.graceElapsed(now) {
			graced = append(graced, ar)
		}
	}
	h.mu.RUnlock()

	for _, ar := range graced {
		h.forwardAfterGrace(ctx, ar)
	}
}
