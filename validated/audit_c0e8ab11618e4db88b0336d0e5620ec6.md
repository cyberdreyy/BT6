### Title
A dust-sized APR0 withdraw request permanently bricks `stopEpoch` if the manager later sets a non-zero APR, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In `IdleCreditVault`, `prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` [1](#0-0) . Any unprivileged lender can open an APR0-mode withdraw request of arbitrary (even dust) size via `requestWithdraw` → `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` [2](#0-1) [3](#0-2) . If the honest manager subsequently configures a non-zero APR (a routine `setAprsWithBuffer` call, line 217-220), every later `stopEpoch` call reverts at the guard, `epochNumber` can never advance, and `apr0TotalPrincipal` can never be cleared because the only line that resets it (`apr0TotalPrincipal = 0`, line 540) sits after the reverting check. This mirrors the GnuPG bug class: one attacker-planted "poison" record makes a shared verification/settlement path unusable for everyone.

### Finding Description
- Epoch phase: during a running epoch with `unscaledApr == 0`, the attacker calls `cdoEpoch.requestWithdraw(dust, tranche)`. The CDO calls `requestWithdraw`, which mints a receipt and routes to `_requestWithdrawApr0`, setting `apr0Users[attacker].principal = dust`, `principalEpoch = epochNumber`, and `apr0TotalPrincipal = dust` [4](#0-3) .
- The manager later calls `setAprsWithBuffer(nonZeroApr, ...)`, which is an honest, expected operation (APR changes between epochs).
- At the next `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`. `_principal = apr0TotalPrincipal != 0`, so the fast path is skipped, then `unscaledApr != 0` triggers `revert NotAllowed()` [5](#0-4) .
- `stopEpoch` can never succeed again: the attacker cannot settle because `_settleApr0` returns early while `_reqEpoch >= epochNumber` [6](#0-5) , and `epochNumber` only advances in `deposit`/`stopEpoch` flows that are all gated behind a successful epoch stop. `apr0TotalPrincipal` is only reset at line 540, unreachable past the revert.
- No existing guard prevents this: the attacker needs no privilege beyond being an allowed tranche holder (KYC'd lender is in-scope per rules), `requestWithdraw` has no minimum amount (`_amount == 0` returns early but `_amount == 1` is accepted, line 246), and no path lets the attacker or manager remove the dust principal outside a successful `stopEpoch` or a borrower default.

### Impact Explanation
Permanent freezing of all vault funds. With `stopEpoch` bricked, pending withdraw receipts can never be funded (`collectWithdrawFunds` is only invoked from stopEpoch flow), matured claims never become payable (`epochNumber <= lastWithdrawRequest` forever, line 326), and active deposits are trapped since tranche redemptions route through epoch processing. The attacker pays only dust + gas. This qualifies as permanent freezing with total TVL at risk, not a gas/availability-only DoS.

### Likelihood Explanation
Medium-low: it requires (a) the vault operating in APR0 mode while the attacker requests, and (b) the honest manager later setting a non-zero APR — both plausible operational events rather than adversarial timing. Attack cost is negligible (1 wei request). The `revert` itself was presumably intended as an invariant check but converts a benign accounting edge into an unrecoverable halt, exactly like the upstream "import once, verify never again" pattern.

### Recommendation
Do not hard-revert on the `unscaledApr != 0` + pending-APR0-principal combination. Instead, settle the stale bucket deterministically inside `prepareStopEpochWithApr0` before applying the guard — e.g., record `apr0RateByEpoch[epochNumber] = 0` (or pro-rata at the old rules), move `apr0TotalPrincipal` into `pendingWithdraws`, and clear `apr0TotalPrincipal` unconditionally so the epoch can always advance. Alternatively, block APR changes while `apr0TotalPrincipal != 0` inside `setAprsWithBuffer`/`setApr` so the poisoned state can never be created.

### Proof of Concept
Foundry fork PoC sketch (against the existing `IdleCreditVault.t.sol` harness):

```solidity
// Setup: epoch running with unscaledApr == 0
uint256 attackerShares = cdoEpoch.depositAA(1e6); // attacker, any allowed lender
cdoEpoch.startEpoch(); // manager, epoch N running

// Poison: dust-sized APR0 withdraw request
vm.prank(attacker);
cdoEpoch.requestWithdraw(1, address(AAtranche));
assertEq(strategy.apr0TotalPrincipal(), 1);

// Honest manager later configures a non-zero APR
vm.prank(manager);
strategy.setAprsWithBuffer(5e18, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());

// stopEpoch permanently reverts
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(...);
// Every subsequent attempt reverts identically; apr0TotalPrincipal can never be
// cleared and epochNumber never advances -> all LP funds frozen.
```

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
