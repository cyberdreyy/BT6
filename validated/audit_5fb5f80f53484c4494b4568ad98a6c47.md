## Valid Analog Found

The ETH-theft pattern in the report — an unprotected sweep function that moves value out of a contract with **no ownership/authority check** — has a direct analog in the `bpf_loader_upgradeable` program's `Close` instruction handler in agave.

### Title
Unauthenticated lamport theft from `Uninitialized` loader-owned accounts via `UpgradeableLoaderInstruction::Close` - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `Close` instruction of `bpf_loader_upgradeable` has three branches depending on the state of the account being closed: `Uninitialized`, `Buffer`, and `ProgramData`. The `Buffer` and `ProgramData` branches correctly delegate to `common_close_account`, which validates that an authority account is present, matches the stored authority, and has signed the transaction [1](#0-0) . The `Uninitialized` branch, however, skips all of that and unconditionally transfers every lamport from the closed account to the recipient account with **no signer or authority check whatsoever**: [2](#0-1) 

### Finding Description
`UpgradeableLoaderInstruction::Close` only requires 2 accounts and checks that the account being closed and the recipient are not the same key [3](#0-2) . For the `UpgradeableLoaderState::Uninitialized` state, it directly does:
```rust
let mut recipient_account = instruction_context.try_borrow_instruction_account(1)?;
recipient_account.checked_add_lamports(close_account.get_lamports())?;
close_account.set_lamports(0)?;
```
There is no check that any authority signed, no check that the caller has any relationship to the account, and no check tying `close_account` to any signer at all — this mirrors exactly the missing-access-control pattern from the Kyber report (`refundEth`/`unwrapWeth` sweeping any balance to `msg.sender` with no ownership validation).

Any account owned by `bpf_loader_upgradeable` that is in the `Uninitialized` state and holds lamports is a valid target for this branch. Such accounts legitimately exist in transient states, most notably:
- A buffer/programdata account created via `system_instruction::create_account` (funded with rent-exempt lamports, owner set to `bpf_loader_upgradeable`) but not yet initialized with `InitializeBuffer`/`DeployWithMaxDataLen` — its on-chain data is all-zero, which deserializes as `UpgradeableLoaderState::Uninitialized`.
- Any account previously deinitialized by a legitimate `Close` (which explicitly leaves it `Uninitialized`) that later receives additional lamports via a plain system transfer.

### Impact Explanation
An attacker constructs a single transaction invoking `bpf_loader_upgradeable`'s `Close` instruction with:
- account[0] (writable, **not required to be a signer**) = the victim's `Uninitialized`, lamport-funded, loader-owned account,
- account[1] (writable) = the attacker's own account.

Because `try_borrow_instruction_account` only enforces writability (which the attacker fully controls via the instruction's `AccountMeta`), not signer status, for this branch, the lamports are unconditionally moved to the attacker. This is concrete, unsigned, unauthorized fund movement reachable from a single submitted transaction — exactly the severity class called for in the rules (unsigned fund movement).

### Likelihood Explanation
Reachability is straightforward: no privileged role, leader behavior, or multi-party interaction is required — any transaction sender can build and submit the `Close` instruction against any known account address in the `Uninitialized` loader state. The most realistic exploitation window is the common multi-transaction program-deploy flow, where a buffer account is created and funded in one transaction and only initialized in a later transaction (as done by CLI tooling, e.g. `close_any`/`Close` usage seen in `cli/src/program.rs`), leaving a public window where the account is `Uninitialized` with nonzero lamports.

### Recommendation
Require an explicit authority account and signer check for the `Uninitialized` branch of `Close`, mirroring `common_close_account`'s pattern — e.g., require the account creator/original funder (or an authority passed and validated) to sign before lamports can be swept out, instead of unconditionally crediting `recipient_account`.

### Proof of Concept
1. Attacker (or victim's own client, mid-deploy) executes `system_instruction::create_account` creating account `A`, owner = `bpf_loader_upgradeable::id()`, funded with rent-exempt lamports, data zero-initialized (`UpgradeableLoaderState::Uninitialized`).
2. Before `A` is initialized via `InitializeBuffer`/`DeployWithMaxDataLen`, an attacker submits a transaction invoking `bpf_loader_upgradeable` with `UpgradeableLoaderInstruction::Close`, `instruction_accounts = [ {A, signer:false, writable:true}, {attacker_account, signer:false, writable:true} ]`.
3. Processing hits the `UpgradeableLoaderState::Uninitialized` branch at [2](#0-1) , moving all of `A`'s lamports to `attacker_account` and zeroing `A`, with no signature from anyone associated with `A`'s funding.
4. Confirmed by the existing unit test `test_bpf_loader_upgradeable_close`, which drives the "close an uninitialized account" case with `authority_meta` present in the `instruction_accounts` list purely by convention — the code path itself never reads or validates that authority account for the `Uninitialized` branch [4](#0-3) .

fn common_close_account(
    authority_address: &Option<Pubkey>,
    instruction_context: &InstructionContext,
    log_collector: &Option<Rc<RefCell<LogCollector>>>,

    if authority_address.is_none() {

        ic_logger_msg!(log_collector, "Authority did not sign");
