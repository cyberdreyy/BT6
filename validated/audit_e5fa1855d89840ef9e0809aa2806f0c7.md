### Title
Response cache key omits `WorkflowID`, allowing cross-workflow HTTP response leakage between workflows sharing the same owner - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
`responseCache.Fetch`/`Set` key the cache exclusively on `gateway.OutboundHTTPRequest.Hash()`, and the test suite explicitly documents that this hash is identical regardless of `WorkflowID`, differing only by method/URL/headers/body/`WorkflowOwner`. This contradicts the README claim that "Cache entries are scoped by workflow ID" and lets one workflow read another workflow's cached outbound HTTP response as long as both workflows share the same `WorkflowOwner` and issue an identical request (method/URL/headers/body).

### Finding Description
`gatewayHandler.makeOutgoingRequest` unmarshals the node-supplied `OutboundHTTPRequest` (`req.WorkflowID`, `req.WorkflowOwner`, `req.Method`, `req.URL`, headers, body, `CacheSettings`) directly from an untrusted node message and calls `h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)` when `CacheSettings.MaxAgeMs > 0` [1](#0-0) .

Inside `responseCache.Fetch`, the cache key is computed purely as `req.Hash()` [2](#0-1) , and the same key is used to store the response in `Set` [3](#0-2) .

`response_cache_test.go` contains an explicit table test proving that `Hash()` ignores `WorkflowID`:
- "having different workflowID results in same Hash" — sets `req1.WorkflowID = "workflow-123"`, `req2.WorkflowID = "workflow-456"`, and asserts `require.Equal(t, hash1, hash2, ...)` [4](#0-3) .
- By contrast, "having different workflowOwner results in different Hash" confirms `WorkflowOwner` (not `WorkflowID`) is the isolation dimension actually baked into the hash [5](#0-4) .

The struct-level comment on `responseCache` corroborates this: "keyed by a hash of the request (method, URL, headers, body, workflowOwner)" — `workflowID` is conspicuously absent from that list [6](#0-5) .

However, the project's own README states the invariant that is supposed to hold: "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [7](#0-6) . The implementation does not meet this documented invariant — it only isolates by `WorkflowOwner`, not `WorkflowID`.

Exploit flow: a single owner authorized to run multiple distinct workflows (a normal, expected scenario — one workflow operator/owner commonly deploys several separate workflows) can have Workflow A make an outbound HTTP request with `CacheSettings.Store=true` to some URL that returns a sensitive response (e.g., containing a token echoed by an external API, or data scoped to be visible only to Workflow A's logic). Because `WorkflowID` is not part of the cache key, Workflow B — a different workflow under the *same owner* — issuing an outbound HTTP action with the identical method/URL/headers/body will hit `Fetch` and receive Workflow A's previously cached `OutboundHTTPResponse` via the fast path at line 74-77, without a fresh request ever being sent to the external endpoint, and without the gateway itself performing any additional per-workflow scoping check.

This is a genuine violation of the documented isolation invariant (workflow-ID scoping), even though it is not a full cross-owner leak since `WorkflowOwner` is still included in the hash.

### Impact Explanation
This constitutes cross-workflow response confusion/disclosure: outbound HTTP action results (which may include response bodies/headers from third-party APIs, potentially containing per-workflow secrets, tokens, or personalized data) intended to be isolated per workflow ID are shared across all workflows belonging to the same owner. This matches the "cross-user/cross-workflow response confusion" impact class in scope, since an attacker's low-privileged workflow (assuming it is co-owned or otherwise reaches a colliding cache key) can read data produced by another workflow's outbound request instead of that workflow.

### Likelihood Explanation
Preconditions: attacker must control a workflow whose `OutboundHTTPRequest.WorkflowOwner` matches the victim workflow's owner (i.e., another workflow under the same owner/account) and can predict or guess the exact method/URL/headers/body of the victim workflow's cached request; the victim request must have used `CacheSettings.Store=true` (or been fetched via `Fetch` with a positive `MaxAgeMs`) so an entry exists in the cache, and the attacker's own request must set `CacheSettings.MaxAgeMs > 0` to route through `Fetch`. Given that a single workflow owner routinely manages multiple deployed workflows and outbound HTTP action parameters (URL/method) are often static/predictable (e.g., calling the same well-known third-party API), this is realistically triggerable and fully repeatable, as demonstrated directly by the existing unit test assertions.

### Recommendation
Include `WorkflowID` (in addition to `WorkflowOwner`) in the `OutboundHTTPRequest.Hash()` computation (in `chainlink-common/pkg/types/gateway`) so that cache keys are scoped per-workflow as documented, not merely per-owner. Update the `responseCache` struct comment and README to accurately reflect the isolation dimension once fixed, and add/adjust the existing `TestRequestHash` case ("having different workflowID results in same Hash") to assert `NotEqual` instead, matching the intended invariant.

### Proof of Concept

```go
func TestFetch_CrossWorkflowLeakage_SameOwner(t *testing.T) {
    testMetrics := createCacheTestMetrics(t)
    cache := newResponseCache(logger.Test(t), 60000, testMetrics)

    reqA := createTestRequest("GET", "https://victim-api.example.com/data")
    reqA.WorkflowOwner = "shared-owner"
    reqA.WorkflowID = "workflow-A"
    reqA.CacheSettings = gateway_common.CacheSettings{MaxAgeMs: 60000, Store: true}

    victimResp := createTestResponse(200, `{"secret":"victim-only-data"}`)
    fetchCount := 0
    victimFetch := func() gateway_common.OutboundHTTPResponse {
        fetchCount++
        return victimResp
    }
    got := cache.Fetch(t.Context(), reqA, victimFetch, true)
    require.Equal(t, victimResp, got)
    require.Equal(t, 1, fetchCount)

    // Attacker's workflow: same owner, DIFFERENT workflowID, identical method/URL/headers/body
    reqB := createTestRequest("GET", "https://victim-api.example.com/data")
    reqB.WorkflowOwner = "shared-owner"
    reqB.WorkflowID = "workflow-B-attacker"
    reqB.CacheSettings = gateway_common.CacheSettings{MaxAgeMs: 60000, Store: true}

    attackerFetchCalled := false
    attackerFetch := func() gateway_common.OutboundHTTPResponse {
        attackerFetchCalled = true
        return createTestResponse(200, `{"fresh":"attacker-data"}`)
    }
    result := cache.Fetch(t.Context(), reqB, attackerFetch, true)

    // EXPECTED (secure) behavior: attacker's fetch should be invoked, victim's data must not leak
    require.True(t, attackerFetchCalled, "expected a fresh fetch for a different WorkflowID")
    require.NotEqual(t, victimResp, result, "attacker must not receive victim workflow's cached response")

    // ACTUAL (current, vulnerable) behavior demonstrated by existing TestRequestHash:
    // reqA.Hash() == reqB.Hash() because WorkflowID is excluded, so result == victimResp
    // and attackerFetchCalled == false.
}
```
Run against current code to confirm `attackerFetchCalled == false` and `result == victimResp`, proving the leak; then apply the recommended fix (include `WorkflowID` in `Hash()`) and re-run to confirm isolation.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
