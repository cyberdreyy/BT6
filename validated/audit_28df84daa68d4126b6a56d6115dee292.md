## Title
Fail-Open on Node Connectivity Failure in `check_latest_block_in_tenure` Lets a Signer Sign a Conflicting/Non-Canonical Block - (File: `stacks-signer/src/chainstate/mod.rs`)

## Summary
`SortitionData::check_latest_block_in_tenure`, the shared "does this proposal confirm the tenure's latest signed block?" check used both at proposal arrival and — critically — at the final re-check immediately before a signer commits its signature, fails open when the query to the stacks-node (`client.get_tenure_tip`) errors: it returns `Ok(true)` (i.e., "confirmed"), the same result as a genuinely successful confirmation. This mirrors the reported Uniswap bug class exactly: a verification path that should block on inability-to-verify instead defaults to the "trusted"/passing outcome on failure.

## Finding Description
`check_latest_block_in_tenure` asks the node for the tenure's tip to decide whether a proposed block legitimately confirms it: [1](#0-0) 

```rust

    Ok(tip) => tip.anchored_header,
    Err(e) => {
        warn!(
            "Failed to fetch the tenure tip for the parent tenure: {e:?}. Assuming proposal is higher than the parent tenure for now.";
            ...
        );
        return Ok(true);
    }
};
...
Ok(tip.height() < block.header.chain_length)
``` [2](#0-1) 

This function backs both `check_tenure_change_confirms_parent` and `confirms_latest_block_in_same_tenure` [3](#0-2) , which are used in three places per `docs/signer-flows.md`: at proposal arrival (`check_proposal`), after node validation succeeds, and — the important one — at the pre-commit-threshold re-check right before the signer actually signs, via `check_block_against_signer_db_state`: [4](#0-3) 

```rust
match SortitionData::check_latest_block_in_tenure(
    &proposed_block.header.consensus_hash,
    proposed_block,
    &mut self.signer_db,
    stacks_client,
    ...
) {
    Ok(is_latest) => {
        if !is_latest {
            ... // rejected
        } else {
            None // passes, signer proceeds to sign
        }
    }
    ...
}
```

This last re-check exists specifically to catch the case where the local DB state changed between the node's OK verdict and the pre-commit threshold being reached (e.g. a conflicting block in the same tenure got signed meanwhile). If, at that exact moment, `client.get_tenure_tip` fails for any reason — the local stacks-node being briefly overloaded, a transient RPC/network blip, or a targeted denial against just the `/v3/tenures/tip` endpoint on this signer's node — the function returns `Ok(true)` instead of propagating an error/blocking. The caller then treats that as "confirmed," skips the `SortitionViewMismatch` rejection, and the signer proceeds to `mark_pre_committed` / sign.

This directly parallels the reported bug's second flaw ("fail-open architecture on verification failure"): both instant-price fallback and `get_tenure_tip` fallback treat "I could not verify" as "verification passed," rather than "fail closed / block."

The docs explicitly acknowledge this design choice ("assume higher — node's proposal endpoint is the backstop") [5](#0-4) , but that backstop only covers the *first* node validation call, not this specific last-mile re-check whose entire purpose is to catch races the first validation cannot see.

## Impact Explanation
If the connectivity failure occurs precisely during the pre-commit re-check window, a signer can sign a block that does not actually confirm the tenure's latest signed block — i.e., a conflicting/non-canonical block — breaking the "signer signing an invalid/non-canonical/conflicting block" invariant. Because the re-check is the only gate here (the underlying node validation already returned OK earlier and cannot be re-run), fail-open here removes the sole safeguard against a race the mechanism was designed to close.

## Likelihood Explanation
Exploitability depends on transient node/RPC failure coinciding with the pre-commit threshold window — this can occur naturally under load or be encouraged by a miner/attacker timing conflicting proposals around network hiccups or by degrading the signer's connection to its own node during the narrow re-check window. It does not require a majority of signers, another signer's key, or the auth_token, only ordinary node unavailability at the right moment, which is a realistic, not purely theoretical, condition on a distributed system.

## Recommendation
Change `check_latest_block_in_tenure` to fail closed on node-query failure at line 456-460 (`stacks-signer/src/chainstate/mod.rs`): propagate the `ClientError` instead of returning `Ok(true)`, so that all callers — proposal-arrival `check_proposal`, validate-ok recheck, and pre-commit recheck — treat "cannot verify" as a rejection (or at minimum retry/hold) rather than as passing verification, consistent with how other connectivity failures in this same file (e.g. `RejectReason::ConnectivityIssues`) are already handled.

## Proof of Concept
1. Miner proposes tenure-change block `B1` in tenure `T`; signers validate it OK and it accumulates pre-commit weight.
2. Before `B1` reaches the 70% pre-commit threshold on signer `S`, a different conflicting block `B2` (also claiming to be the tenure-tip confirmer, or reorging `T`) gets locally accepted elsewhere, changing what `get_tenure_tip` would correctly report.
3. When `B1` crosses the pre-commit threshold on `S`, `check_block_against_signer_db_state` invokes `check_tenure_change_confirms_parent` → `check_latest_block_in_tenure`, which calls `client.get_tenure_tip(tenure_id)`.
4. If this specific RPC call to the local stacks-node errors (network blip, node restart, targeted slow-down), the function returns `Ok(true)` at `stacks-signer/src/chainstate/mod.rs:459` [6](#0-5) , bypassing the intended `SortitionViewMismatch` rejection.
5. `S` proceeds to `mark_pre_committed`/sign `B1` even though it conflicts with the tenure's true current tip, producing a signature over a non-canonical/conflicting block that the re-check was specifically designed to prevent.
