### Title
JWT replay check-then-act race allows concurrent duplicate authorization with identical `jti` - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` performs a non-atomic check-then-act sequence: it calls `jwtCache.isReplay(claims.ID)` and, only after passing all subsequent checks, calls `jwtCache.recordUsage(claims.ID)`. Because `isReplay` (RLock) and `recordUsage` (Lock) are two separate critical sections rather than a single atomic operation, two concurrent `Authorize` calls with the same captured JWT can both observe `isReplay == false` before either has recorded usage, letting both requests pass replay protection and be authorized as the legitimate signer.

### Finding Description
`Authorize` is reachable from `httpTriggerHandler.HandleUserTriggerRequest` → `authorizeRequest` → `WorkflowMetadataHandler.Authorize(workflowID, req.Auth, req)` [1](#0-0) , which is invoked for every incoming gateway HTTP trigger request from an unauthenticated/unprivileged external client holding only a previously-issued signed JWT.

Inside `Authorize`:
```go
if h.jwtCache.isReplay(claims.ID) {           // read-lock, check
    return nil, errors.New(...)
}
...
h.jwtCache.recordUsage(claims.ID)             // write-lock, record — happens later
``` [2](#0-1) 

`isReplay` and `recordUsage` are implemented as independent, separately-locked operations:
```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()
	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	cache.cache[jti] = time.Now()
}
``` [3](#0-2) 

There is no compare-and-set / atomic "check-and-insert" primitive. If two goroutines call `Authorize` with an identical `token` (same `jti`) at roughly the same time, both can execute `isReplay` and find no entry before either executes `recordUsage`. Both then proceed through the authorized-key lookup and both return the authorized `key`, succeeding. `VerifyRequestJWT` only validates signature/claims of the token itself and does not perform any replay/uniqueness enforcement [4](#0-3) , so nothing else in the path blocks the duplicate.

Downstream, `HandleUserTriggerRequest` treats each call independently and proceeds to rate-limit check, execution ID generation, and dispatch to shards via `sendWithRetries`/`sendToShard` using a per-request `req.ID` (distinct from the JWT `jti`), so a successful duplicate `Authorize` call is not blocked by the callback dedup logic in `setupCallback` (which keys on `req.ID`, not `jti`) [5](#0-4) . Consequently a single captured/replayed JWT can be used to trigger two independent, fully-authorized workflow executions concurrently.

### Impact Explanation
This breaks the intended authentication soundness invariant that a single-use signed JWT authorizes exactly one workflow-execution request. An attacker who captures or observes a valid signed JWT within its validity window (e.g., via network capture, logging, or a legitimate but untrusted intermediary) can fire two near-simultaneous requests and get both authorized as the legitimate signer, resulting in duplicate impersonated workflow executions and consumption of the victim's authorized capability/rate-limit slot twice. This matches the "request impersonation / duplicate unauthorized job run" bounty impact class since it allows action to be taken twice under someone else's authorized identity using a single token that should only be usable once.

### Likelihood Explanation
Exploitation requires only possession of one valid signed JWT (no additional privilege) and requires the attacker to race two requests within the tiny window between the `isReplay` read and the `recordUsage` write. This window is typically sub-millisecond in a single-process call, but is fully reproducible on demand by firing concurrent goroutines/HTTP requests, so while the natural race window is narrow, an attacker fully controls both request timings and can reliably win the race by issuing requests in tight parallel loops. This is a genuine TOCTOU bug rather than a rare timing accident.

### Recommendation
Make the replay check-and-insert atomic. Replace the separate `isReplay` + `recordUsage` calls with a single locked "check-and-set" method, e.g.:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	if _, exists := cache.cache[jti]; exists {
		return false // replay
	}
	cache.cache[jti] = time.Now()
	return true
}
```
and call this single method in `Authorize` before proceeding with authorization, instead of calling `isReplay` early and `recordUsage` after the authorized-key lookup.

### Proof of Concept
Go concurrency test plan (in `workflow_metadata_handler_test.go`):
1. Construct a `WorkflowMetadataHandler` with one authorized workflow ID and one authorized signer key.
2. Generate a single valid JWT token/claims (same `jti`) signed by the authorized key for a given `req`.
3. Launch two goroutines that both call `h.Authorize(workflowID, token, req)` simultaneously (synchronized start via a `sync.WaitGroup`/barrier channel).
4. Collect both `(key, err)` results.
5. Assert: exactly one call returns `err == nil` with the expected `key`, and exactly one call returns the "JWT token has already been used" error — i.e., success count == 1 and error count == 1.
6. Currently, due to the check-then-act race, both goroutines can observe `isReplay == false` and both succeed (error count == 0, success count == 2), demonstrating the vulnerability; after applying the atomic `checkAndRecord` fix, the test should deterministically show success count == 1.
