Confirmed: `mint()` in `v2.rs` (and identically in v1) always calls `B20Guards::ensure_policy_type(token, B20PolicyType::MintReceiver, to)?` regardless of the `privileged` flag [1](#0-0) . `batch_mint` runs each recipient through this same `mint` function with `privileged: true`, but that flag only skips the *role* check on the caller — the per-recipient `MintReceiver` policy check is unconditional and still runs for every recipient in the loop [2](#0-1) .

This reproduces the exact bug class from the report: a loop that performs an unconditional external-state check (policy/blocklist gate) per item, where a single blocked address in the batch causes the entire loop to `?`-propagate and abort the whole operation — denying service to every other (unrelated, non-blocked) recipient in the same batch.

### Title
`batchMint` DoS: a single `MintReceiver`-blocked recipient reverts the entire batch, denying mint to all other recipients - (File: `crates/common/precompiles/src/b20_asset/logic/v2.rs`)

### Summary
`Asset::batch_mint` iterates over attacker/caller-supplied `recipients`/`amounts` and calls `self.mint(..., true)` for each one [3](#0-2) . Inside `mint`, even though `privileged=true` skips the `MINT_ROLE` check, the `MintReceiver` policy guard is always enforced: `B20Guards::ensure_policy_type(token, B20PolicyType::MintReceiver, to)?` [4](#0-3) . If any single `to` address in the batch is not authorized under the configured `MintReceiver` policy (e.g. it's on a `BLOCKLIST` policy, or absent from an `ALLOWLIST` policy — both are supported policy types on the B20 precompile [5](#0-4) ), the `?` propagates the error out of the `for` loop and aborts the entire `batch_mint` call, reverting the whole transaction.

### Finding Description
This is the same DoS pattern as the referenced `AccountingManager.executeWithdraw` finding: a single-transaction batch operation that services multiple third-party addresses uses an all-or-nothing loop, and per-item authorization/compliance checks (blocklist/allowlist policy) are not isolated per iteration. Because the token's `MintReceiver` policy is admin-configurable (`updatePolicy`/`updateBlocklist`/`updateAllowlist` via `PolicyRegistry`) and can change state independently of the batch caller's intent, any account that has been removed from an allowlist or added to a blocklist for `MintReceiver` — even unintentionally included by a well-meaning batch submitter, or maliciously included by an attacker who knows an account will be added to a blocklist — will cause `batch_mint` to revert entirely, rather than skipping just that recipient.

### Impact Explanation
An operator issuing a `batchMint` to legitimate recipients can have the entire batch blocked indefinitely if even one recipient becomes non-compliant with the `MintReceiver` policy (e.g. sanctioned/blocklisted after being queued, or removed from an allowlist). This can be used to grief/DoS token issuance operations bundling many recipients in a single call, and — depending on how mint batches are constructed by the operator/backend — could be leveraged by an attacker who can influence the recipient list (e.g. a compromised or malicious front-end submission) to permanently block minting to unrelated legitimate users in the same batch. This matches the "Medium/High" severity class of the analog: unauthorized denial of a batched fund-distribution operation for uninvolved parties.

### Likelihood Explanation
Likelihood depends on the `MintReceiver` policy actually being configured to a non-`ALWAYS_ALLOW` policy (`ALLOWLIST`/`BLOCKLIST`/`ALWAYS_BLOCK`) — which is an admin-controlled setting exposed via `updatePolicy` and is explicitly supported for `MintReceiver` per the `PolicyType` enum and V1 `ensure_supported_policy_type` allowlist [6](#0-5) . Any regulated/stablecoin-style B20 token that uses blocklist/allowlist policies on minting is directly exposed; batch operations bundling multiple recipients are a normal, expected use case for token issuers, based on the existing `golden_batch_mint` test coverage using multiple recipients [7](#0-6) .

### Recommendation
For `batch_mint`, either: (1) pre-validate all recipients against the `MintReceiver` policy before mutating any state and revert with a clear per-recipient error (current all-or-nothing semantics preserved but explicit), or (2) change semantics to skip/continue past blocked recipients (emitting a `MintSkipped`-style event) rather than aborting the whole batch, mirroring the original report's suggested mitigation of `continue`-ing instead of reverting on a blocked participant. If all-or-nothing is the intended design, this should be explicitly documented as a known limitation so operators pre-filter recipients client-side; however, note that the policy state can change between batch construction and execution (front-running by an admin's `updateBlocklist` call), so pre-filtering does not fully close the race.

### Proof of Concept
1. Token admin creates a `BLOCKLIST` (or `ALLOWLIST`) policy and wires it to `MintReceiver` via `updatePolicy` (as shown for `TransferSender`/`TransferReceiver` in `actions/harness/tests/beryl/b20_policy.rs`).
2. Token admin/backend submits `batchMint(recipients=[alice, bob, blockedCarol], amounts=[a1,a2,a3])`.
3. Inside `batch_mint`, iteration reaches `blockedCarol`; `mint()` calls `ensure_policy_type(MintReceiver, blockedCarol)` which reverts with `PolicyForbids`.
4. The `?` on `self.mint(...)` inside the `for` loop [8](#0-7)  propagates the error out of `batch_mint`, and the entire transaction reverts — `alice` and `bob` receive nothing even though they were fully compliant, exactly mirroring the `executeWithdraw` blacklist-DoS pattern from the external report.

/// BLOCKLIST policy wired to `TransferSender` blocks listed accounts from sending.
///
/// 1. Alice seeds bob with tokens (default `ALWAYS_ALLOW` policy, succeeds).
/// 2. Create BLOCKLIST policy; wire it to `TransferSender`.
/// 3. Bob transfers; succeeds (not in blocklist).
/// 4. Admin adds bob to the blocklist.
/// 5. Bob tries to transfer; reverts.
#[tokio::test]
async fn b20_blocklist_sender_policy_blocks_listed_accounts() {
    let mut scenario = B20PolicyScenario::new().await;

    let seed_bob =
        scenario.token_tx(IB20::transferCall { to: BerylTestEnv::bob(), amount: SEED_AMOUNT });
    let block = scenario.build_block(vec![seed_bob]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "seeding bob must succeed");
    scenario.assert_balance(BerylTestEnv::alice(), BerylTestEnv::B20_INITIAL_SUPPLY - 100_000);
    scenario.assert_balance(BerylTestEnv::bob(), 100_000);

    let blocklist_id = BerylTestEnv::policy_id(IPolicyRegistry::PolicyType::BLOCKLIST, 2);
    let create_policy = scenario.policy_tx(IPolicyRegistry::createPolicyCall {
        admin: BerylTestEnv::alice(),
        policyType: IPolicyRegistry::PolicyType::BLOCKLIST,
    });
    let block = scenario.build_block(vec![create_policy]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "createPolicy(BLOCKLIST) must succeed");

    let wire = scenario.token_tx(IB20::updatePolicyCall {
        policyScope: B20PolicyType::TransferSender.id(),
        newPolicyId: blocklist_id,
    });
    let block = scenario.build_block(vec![wire]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "updatePolicy must succeed");

    let first_transfer = scenario
        .bob_token_tx(IB20::transferCall { to: BerylTestEnv::carol(), amount: TRANSFER_AMOUNT });
    let block = scenario.build_block(vec![first_transfer]).await;
    assert!(
        scenario.env.user_tx_succeeded(&block, 0),
        "transfer from non-blocked account must succeed"
    );
    scenario.assert_balance(BerylTestEnv::bob(), 99_999);
    scenario.assert_balance(BerylTestEnv::carol(), 1);

    let block_bob = scenario.policy_tx(IPolicyRegistry::updateBlocklistCall {
        policyId: blocklist_id,
        blocked: true,
        accounts: vec![BerylTestEnv::bob()],
    });
    let block = scenario.build_block(vec![block_bob]).await;
    assert!(scenario.env.user_tx_succeeded(&block, 0), "updateBlocklist must succeed");

    let blocked = scenario
        .bob_token_tx(IB20::transferCall { to: BerylTestEnv::carol(), amount: TRANSFER_AMOUNT });
    let block = scenario.build_block(vec![blocked]).await;
    assert!(
        !scenario.env.user_tx_succeeded(&block, 0),
        "transfer from blocked account must revert"
    );
    scenario.assert_balance(BerylTestEnv::bob(), 99_999);
    scenario.assert_balance(BerylTestEnv::carol(), 1);

    scenario.derive().await;
}
