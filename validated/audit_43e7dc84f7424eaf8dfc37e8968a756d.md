### Title
`check_parent_tenure_choice` treats "we never personally signed the reorged tenure's first block" as proof of poor timing, letting a miner reorg an already-canonical tenure and get a signer to endorse a conflicting block - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` is the reorg gate that decides whether a miner is allowed to build off something other than the prior sortition. It is meant to allow a reorg only when the tenure being replaced produced its first block "too close" to the next sortition to have had a fair chance to RBF. When computing that timing, if the local signer simply never signed the reorged tenure's first block, the code substitutes a hardcoded `proposal_to_sortition = 0`, which by construction is always less than `first_proposal_burn_block_timing`, so the reorg is unconditionally allowed regardless of how much real time actually elapsed.

### Finding Description
`check_parent_tenure_choice` computes, per reorged tenure, whether that tenure's first block was "poorly timed" and therefore fair game to reorg: [1](#0-0) 

The relevant branch:
```
let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
    sortition_state_received_time.saturating_sub(approved_at)
} else {
    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
    0
};
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    ...
    superseded_tenures.push(tenure);
    continue;
}
```

The intended semantics (per the docs and the two paired tests `check_parent_tenure_choice_reorg_timing_bad`/`_ok`) are: only allow a reorg if the *actual* wall-clock gap between when the tenure's first block was approved and when the next sortition arrived was smaller than `first_proposal_burn_block_timing` (default 60s) — i.e. the previous miner genuinely had no time to react. [2](#0-1) 

However, when `local_block_info.approved_time` is `None`, the code does not fail closed or fall back to a real timestamp; it hardcodes `proposal_to_sortition = 0`, which trivially satisfies `< first_proposal_burn_block_timing` for any nonzero timeout, so the reorg is always permitted along this path. `approved_time` can legitimately be `None` on a `BlockInfo` that this specific signer never itself pre-committed to or locally accepted (e.g. it joined late, restarted and rebuilt its local state, or was offline during the tenure but has since caught up and knows the tenure produced a block via `get_first_approved_block_in_tenure`). In none of those cases has the tenure's block actually been "poorly timed" in the way the check is supposed to measure — the signer simply lacks its *own* timestamp for it.

Because this is a per-signer local decision (each signer independently evaluates `check_parent_tenure_choice` against its own DB state), a miner (or a colluding signer subset) can specifically target signers whose local `signerdb` lacks an `approved_time` for the previously-canonical tenure's block — for instance a signer that just restarted, or was offline when the original tenure's block was proposed and only learned about it later via a node-reported tip (which populates `signerdb` without going through the pre-commit/local-acceptance code paths that stamp `approved_time`). That signer will then treat *any* prior, already-established (potentially globally-accepted, canonical) tenure as reorgable and go on to sign a competing/conflicting block for the new tenure, in violation of the equality the reorg-timing rule is meant to enforce (a genuinely well-established tenure must never be legitimately reorg-able).

This directly breaks the "approved-parent vs canonical" equality: the signer's approval decision is supposed to be gated on a real elapsed-time proof, but instead defaults to an always-true condition when its own bookkeeping is incomplete, letting the signer sign a block that reorgs a tenure it (and possibly the rest of the network) had already accepted.

### Impact Explanation
This falls under the Critical impact bucket: a signer can be induced to sign a non-canonical/conflicting block. If enough signers hit this state (e.g., after a coordinated restart, resync, or an attacker who times an attack around signer downtime/catch-up), the network could accept a reorg of an already-canonical tenure that should have been rejected under the reorg-timing rules, which is exactly the invariant `check_parent_tenure_choice` and `first_proposal_burn_block_timing` exist to prevent.

### Likelihood Explanation
Likelihood is moderate to high in practice: `approved_time` being `None` for a block that `get_first_approved_block_in_tenure` still returns is a reachable, non-adversarial state (signer restarts, resyncs, or otherwise did not participate in the block's original approval flow), and it requires no majority collusion or key compromise — a single miner racing a sortition against a signer's incomplete local record is sufficient to trigger the branch on that signer. The severity scales with how many signers are simultaneously missing that local timestamp (e.g., after a coordinated software upgrade/restart across the fleet), which is a realistic operational scenario rather than a purely theoretical one.

### Recommendation
Do not default `proposal_to_sortition` to `0` (i.e., "always poorly timed") when `local_block_info.approved_time` is missing. Instead:
- Fail closed: treat a missing local timestamp as "cannot prove poor timing" and reject the reorg (return `Ok(false)`) unless a node-verified/global timestamp for the block's approval can be substituted, or
- Query the stacks-node for the actual timing of the tenure's first block (e.g., via block-received/propagation records) rather than relying solely on this signer's own possibly-incomplete `signerdb` bookkeeping, similar to how `check_latest_block_in_tenure` falls back to the node's view when local state is stale.

### Proof of Concept
1. Signer S restarts (or joins late) and its `signerdb` has no `approved_time` recorded for tenure T's first (and only) globally-accepted block, though `get_first_approved_block_in_tenure` still returns that `BlockInfo` (its `state`/first-block bookkeeping is otherwise present).
2. A miner produces a new sortition whose tenure change reorgs tenure T, well after T's block was originally established (i.e., genuinely *not* poorly timed).
3. On signer S, `check_parent_tenure_choice` computes `local_block_info.approved_time == None`, sets `proposal_to_sortition = 0`, and since `Duration::from_secs(0) < first_proposal_burn_block_timing` is always true, the reorg is accepted and T is marked superseded on S.
4. S goes on to sign the new tenure's competing block, having permitted a reorg of a tenure that had already been established/possibly canonical — a decision other honest signers with complete local records would have rejected. [3](#0-2)

One decision does have to be recorded, because it is ours rather than the
node's. When a miner builds off something other than the prior sortition,
`check_parent_tenure_choice` decides whether the reorg is allowed: it is, if
every tenure being reorged has at most one globally accepted block and produced
its first block too close to the next sortition to count
(`first_proposal_burn_block_timing`). Having sanctioned that replacement, the
signer records those tenures as **superseded** (`mark_tenure_superseded`), so its
own signature over what they built does not then block the replacement it just
permitted — the node cannot answer this one at signing time, since it still
serves the reorged tenure as fully live until the replacement lands. What _is_
still derived from the node is the permit's own validity: the record carries the
permitting tenure's sortition, and it only excludes conflicts while that
sortition remains canonical (section 5, `reorg_permit_stands`), so a burnchain
fork that orphans the permitting tenure automatically voids the permit. A record
more than `MAX_FORK_DEPTH` (100) burn blocks below the tip is dropped; a fork
that deep would cause far bigger problems than a stale conflict.
