### Title
Permissionless `lending_pool_emissions_deposit` lets an early depositor inflate `asset_share_value` without bound, bricking the bank for all subsequent depositors - (File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs)

### Summary
The Reserve `RToken.melt()` bug lets an early user manipulate `basketsNeeded / totalSupply` to an extreme value by shrinking `totalSupply` to near-zero, because `requireValidBUExchangeRate()` only checks the ratio when it changes but the ratio itself can be pushed to its allowed extreme (`1e27`), after which further legitimate operations that would *increase* the ratio revert, bricking `issue()`/`mint()`/`melt()`. The root cause is: (1) a share-value ratio computed as `numerator/total_shares`, (2) permissionless ability to shrink `total_shares` to a tiny value, and (3) no floor/ceiling protection once the ratio has been pushed to an extreme, so future arithmetic on that ratio reverts or produces a durable DoS.

marginfi has a directly analogous mechanism: `Bank.asset_share_value = total_assets / total_asset_shares` (`type-crate/src/types/bank.rs:41-45`), and this ratio is set with **no upper-bound check** by `lending_pool_emissions_deposit`, a function explicitly documented as permissionless.

### Finding Description
`Bank::get_asset_amount` / `get_asset_shares` convert between shares and underlying value using `asset_share_value` [1](#0-0) . This is structurally identical to RToken's `basketsNeeded/totalSupply` BU exchange rate.

`lending_pool_emissions_deposit` recomputes `asset_share_value` directly from `total_assets / total_asset_shares` after an arbitrary token transfer, and is explicitly documented as permissionless: [2](#0-1) 

The only guard present is `total_asset_shares > 0` (`EmissionsUpdateError`) — there is **no upper bound** on the resulting `asset_share_value`, unlike RToken's `requireValidBUExchangeRate()` which at least bounds the ratio to `[1e-9, 1e9]`.

A user who is the sole/early depositor of a bank can withdraw down to a minimal remaining `total_asset_shares` (partial `lending_account_withdraw`, not `withdraw_all`, to avoid closing the balance and zeroing `total_asset_shares`) [3](#0-2) . With `total_asset_shares` reduced to a small residual value, calling the permissionless `lending_pool_emissions_deposit` with a large `amount` will set `asset_share_value` to an extreme value:

```
bank.asset_share_value = (total_assets_before + amount) / total_asset_shares
```

Once `asset_share_value` is astronomically large, subsequent `get_asset_shares(value)` calls (`value.checked_div(asset_share_value)`) for any normal-sized deposit will floor to zero shares or hit `math_error!()` (I80F48 precision underflow), because I80F48 has fixed precision (48 fractional bits) and cannot represent share counts far below its resolution. This mirrors the RToken scenario where subsequent `issue()`/`mint()` calls revert because the ratio is stuck at an unusable extreme, and mirrors the "small `totalSupply()`" root cause path called out by the reporter and in Reserve's own mitigation (require minimum supply before allowing `melt()`).

### Impact Explanation
If exploitable, this permanently bricks deposits (and by extension the entire bank's usability, since deposit is a prerequisite for essentially every other lending action) for a specific bank, without requiring any privileged role — matching the "durable freeze/inconsistency with financial effect" acceptance criterion. Depositors who deposited before the attack would still be able to withdraw at the (now correct, if extreme) share value, similar to Reserve's finding where `redeem()`/`melt()` continued to work while `issue()`/deposit-side functionality broke. The severity is bounded by the same considerations noted in the original report (no direct fund theft, but a durable protocol-usability DoS on a per-bank basis), consistent with Reserve's "Medium" categorization for the analogous issue.

### Likelihood Explanation
Likelihood is uncertain because two preconditions in this codebase could not be fully verified with the tools available in this session:
1. Whether `lending_pool_emissions_deposit`'s `Accounts` struct (specifically the `depositor`/`emissions_funding_account` fields) truly allows an arbitrary unprivileged signer to call it, or whether it is gated by `has_one = admin` similar to `LendingPoolConfigureBank`. Only the function body and its doc-comment ("Permissionlessly deposit...") were retrieved; the full `#[derive(Accounts)]` struct for this specific instruction was not returned by search.
2. Whether `ZERO_AMOUNT_THRESHOLD` or another dust-floor check elsewhere prevents `total_asset_shares` from being reduced to a small-enough residual via partial withdraw without triggering `close_balance`/`withdraw_all` (which would zero the balance and reset the bank to an empty state rather than a "near-zero but nonzero" state).

Because these two facts materially determine whether the attack path is reachable by an unprivileged actor, this should be treated as a **candidate for verification** rather than a confirmed finding.

### Recommendation
- Confirm the actual signer/permission requirements on `LendingPoolEmissionsDeposit`'s accounts; if `depositor` can be any unprivileged token holder, restrict it to the group admin or require a minimum floor on `total_asset_shares`/`total_assets` before allowing the ratio-affecting deposit.
- Add an explicit bound (analogous to RToken's `requireValidBUExchangeRate`) on `asset_share_value` (and `liability_share_value`) after every write path that can change it, rejecting updates that push the ratio outside a sane range (e.g., reject if resulting `asset_share_value` exceeds some `MAX_SHARE_VALUE` given `mint_decimals`).
- Enforce a minimum residual `total_asset_shares`/`total_assets` floor (similar to Reserve's PR #619 minimum-supply mitigation) so a bank cannot be driven into a near-zero-share state via partial withdrawals while remaining "open."

### Proof of Concept
Conceptual sequence (pending confirmation of `LendingPoolEmissionsDeposit`'s permission model):
1. Attacker is first/only depositor of a fresh bank: deposits `1_000_000` tokens → `total_asset_shares = 1_000_000`, `asset_share_value = 1` (see first-deposit 1:1 share issuance) [4](#0-3) .
2. Attacker partially withdraws `999_999` tokens via `lending_account_withdraw` (not `withdraw_all`), leaving `total_asset_shares ≈ 1`.
3. Attacker (or anyone, if unprivileged) calls `lending_pool_emissions_deposit` with a very large `amount`, causing:
   `bank.asset_share_value = (1 + amount) / 1 = 1 + amount` — an astronomically large share value [5](#0-4) .
4. Any subsequent user calling `lending_account_deposit` computes `share_amount = bank_account.deposit(...)`, which internally divides by `asset_share_value`; for normal deposit sizes this either floors to zero shares (silent loss) or triggers `math_error!()` on the checked division, bricking deposits into this bank for all future users, matching the "issue() permanently fails" outcome in the original RToken finding.

Note: Steps 2–3 are unverified against the exact account constraints of `LendingPoolEmissionsDeposit` and any dust-floor protections on partial withdraw; a Devin session with full repo access should confirm these before treating this as a confirmed, exploitable finding.

```rust
/// Permissionlessly deposit same-mint emissions directly into the bank liquidity vault,
/// increasing depositor value through asset share value.
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```
