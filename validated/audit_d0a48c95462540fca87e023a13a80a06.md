### Title
Unauthenticated attacker can hijack another user's in-flight WebAPI trigger response via `MessageId` collision in Gateway capabilities handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Chainlink Gateway's public-facing WebAPI capabilities handler stores a pending user callback in a shared, unauthenticated `map[string]*savedCallback` keyed solely by an attacker-controlled `MessageId` field taken directly from the incoming HTTP request body, with no uniqueness check before insertion and no binding to the request's source/session.

### Finding Description
The Gateway exposes an unauthenticated HTTP endpoint (`gateway.ProcessRequest`) that parses an untrusted JSON body into an `api.Message`, whose `MessageBody.MessageId` is fully caller-supplied and only checked for length/format, not uniqueness or unpredictability: [1](#0-0) [2](#0-1) 

When a legacy WebAPI trigger request arrives, `HandleLegacyUserMessage` stores the caller's `handlers.Callback` in `h.savedCallbacks` keyed by `msg.Body.MessageId` with an unconditional write, silently overwriting any pre-existing entry for the same key: [3](#0-2) 

When a DON node later responds, `handleWebAPITriggerMessage` looks the callback up purely by `MessageId` and delivers the response to whichever callback currently occupies that map slot — there is no check that the responding node's answer corresponds to the same original requester/session: [4](#0-3) 

Because `MessageId` is chosen entirely by the client and the map has no per-caller/session scoping, an unprivileged attacker can submit a second request reusing the same `MessageId` as a legitimate in-flight request. This is directly analogous to the `VaderPoolV2.mintFungible` "unlimited slippage" bug class: in both cases, a value/state-mutating action lacks a bound or uniqueness guarantee (`minLiquidity` vs. unique/authenticated `MessageId`), letting an unprivileged party race and manipulate shared intermediate state to redirect value/outcome that another user should have exclusively received.

### Impact Explanation
If an attacker can predict or observe a victim's `MessageId` (e.g., low-entropy client-generated IDs, replay of an ID seen elsewhere, or simply racing with a known/expected value), they can:
- Overwrite the victim's callback entry, causing the victim's request to hang until timeout (denial of service for that request), and
- Receive the DON's actual computed response intended for the victim when it arrives, since `handleWebAPITriggerMessage` matches purely on `MessageId` — a cross-user response confusion / response hijack.

This can leak potentially sensitive computed output (workflow trigger results) to an unauthorized party and disrupt the legitimate user's request, without requiring any authentication, node compromise, or privileged access — it is reachable purely as an unprivileged HTTP client of the Gateway's public endpoint.

### Likelihood Explanation
Exploitability depends on the attacker's ability to guess or observe the victim's `MessageId` before the DON responds (a race window). If client tooling uses predictable, sequential, or low-entropy IDs, or if IDs are otherwise observable (e.g., logged, echoed, or reused by the calling application), this is straightforward to exploit from an unauthenticated network position. If IDs are always high-entropy random UUIDs and never leaked, exploitation likelihood drops but the underlying missing uniqueness/ownership check remains a structural weakness rather than a defense.

### Recommendation
- Reject `HandleLegacyUserMessage` requests whose `MessageId` already exists in `savedCallbacks` instead of silently overwriting them.
- Bind the callback entry to the original caller's identity/session (not just the bare `MessageId`) so a colliding ID from a different, unauthenticated caller cannot be used to claim another user's response slot.
- Consider generating/validating `MessageId` server-side (or combining it with a server-generated nonce/session token) rather than trusting a fully client-supplied value for map-keyed callback resolution.

### Proof of Concept
1. Attacker observes or predicts a `MessageId` that a victim is about to use (or is currently using) to trigger a WebAPI job via the Gateway's public HTTP endpoint (`gateway.ProcessRequest`).
2. Victim sends request A with `MessageId = X`; `HandleLegacyUserMessage` stores victim's callback at `h.savedCallbacks["X"]`. [5](#0-4) 
3. Before the DON responds, attacker sends request B, also with `MessageId = X`; this overwrites `h.savedCallbacks["X"]` with the attacker's own callback (no collision check exists at line 412).
4. When the DON node eventually replies for the original request, `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds the attacker's callback, deletes the entry, and delivers the victim's response to the attacker. [6](#0-5) 
5. The victim's original HTTP request hangs and eventually times out (`callback.Wait(ctx)` deadline in `gateway.go`), while the attacker receives the victim's intended response. [7](#0-6)

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
