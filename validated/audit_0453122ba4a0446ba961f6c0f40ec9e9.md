### Title
Post-threshold minority rejections can permanently and irreversibly flip a signer's local view of an already-broadcast (`LocallyAccepted`) block to `GloballyRejected` - ([File: stacks-signer/src/v0/signer.rs])

### Summary
### Finding Description
Once a block's signature weight crosses the 70% acceptance threshold, `store_and_process_block_signature` marks it `LocallyAccepted` and immediately pushes it to the stacks-node via `broadcast_signed_block` → `handle_post_block`: [1](#0-0) 

At this point the block is functionally "ready to execute" — analogous to the Llama action's `minExecutionTime` having passed — but the signer's local `BlockState` is only `LocallyAccepted`, not `GloballyAccepted`. `has_reached_consensus()` only treats `GloballyAccepted`/`GloballyRejected` as final: [2](#0-1) 

Because of this, `store_and_process_block_rejection` continues to process rejection votes for a block that is already `LocallyAccepted` and already broadcast, since `has_reached_consensus()` returns `false` for that state: [3](#0-2) 

If rejection weight from a minority (only `>30%` weight is required — `total_weight - min_weight`, not a majority) accumulates, `mark_globally_rejected()` is called. The state-transition guard `check_state` permits `LocallyAccepted -> GloballyRejected` — it only forbids this transition from `GloballyAccepted`: [4](#0-3) 

The bug: there is a code path (`check_latest_block_in_tenure`) designed to self-correct exactly this kind of stale local state once the node's canonical tip proves the block was actually accepted — it looks the block up and calls `mark_globally_accepted()`: [5](#0-4) 

But `check_state` also forbids `GloballyRejected -> GloballyAccepted` transitions (`GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected)`), so once a block is (incorrectly) flipped to `GloballyRejected`, this self-correction silently fails and only logs a warning: [6](#0-5) 

The result: the local `state` field becomes permanently and irreversibly stuck at `GloballyRejected` for a block that the real network (weighted 70% signature threshold, verified by `NakamotoBlockHeader::verify_signer_signatures` on-chain) actually accepted and that this signer's own node processed into its canonical chain.

Note: the codebase is aware of a related risk (a signer double-signing a conflicting sibling because it thinks its own signed block was "rejected") and explicitly guards against it — `has_signed_block_in_tenure`/`get_last_signed_block` are documented and tested to keep counting a block as signed even after `mark_globally_rejected`, specifically to prevent that: [7](#0-6) 

So the double-signing/equivocation angle appears mitigated by design. What remains unmitigated is the `state` field itself getting stuck at `GloballyRejected`, which is consumed elsewhere (e.g. `globally_approved_and_responded()`, and any logic gating on `BlockState::GloballyAccepted` for tenure/tip decisions) and can never be corrected back once the node/network has actually finalized the block.

### Impact Explanation
This is a liveness wedge (High-severity criterion: "a signer wedged into never signing valid blocks, acting on a stale reward set/threshold"). A signer whose local record for a genuinely-accepted, canonical block is stuck at `GloballyRejected`:
- Will never re-mark it `GloballyAccepted` (blocked transition), permanently diverging its local bookkeeping from the true canonical chain state for that block/tenure.
- Any downstream logic that gates behavior on `state == GloballyAccepted` (rather than on `signed_self`/`signed_group` timestamps, which are correctly preserved) will treat a canonical, finalized block as rejected, which can cause the signer to refuse to build/sign on top of it, or misinterpret the tenure's canonical history — a wedge that requires operator intervention (DB edit/restart) to clear, since no code path can flip `GloballyRejected` back to `GloballyAccepted`.

I could not fully trace every downstream consumer of `BlockInfo.state == GloballyAccepted` within the tool budget available, so I cannot exhaustively enumerate every consequence; this should be verified against all call sites of `mark_globally_accepted`/`state == BlockState::GloballyAccepted` before treating severity as final.

### Likelihood Explanation
Only requires a coalition (not a majority) with `>30%` signing weight to send rejection votes after a block has crossed the 70% acceptance threshold and been broadcast — but before this signer observes global confirmation (`NewBlock` event / tenure tip advancing). This window (between `LocallyAccepted` broadcast and the node's `NewBlock` confirmation) is realistically racy on every accepted block, not a rare edge case, and requires no majority, no other signer's key, and no special role — matching the reachable, one-tier-of-signers threat model of the original Llama disapproval-griefing report.

### Recommendation
- Treat `LocallyAccepted` (post-threshold, already-broadcast) blocks as consensus-final for the purposes of accepting further rejection votes, similar to how `has_reached_consensus()` already excludes `GloballyAccepted`/`GloballyRejected` — i.e., stop counting rejections once `signed_group` is set (block already crossed the 70% signature threshold and was broadcast), not just once `state == GloballyAccepted`.
- Alternatively/additionally, allow `check_state` to permit `GloballyRejected -> GloballyAccepted` when driven by trusted signals (the node's own canonical tip advancing over the block, as in `check_latest_block_in_tenure`), so the self-correction path in `stacks-signer/src/chainstate/mod.rs` is not silently blocked.

### Proof of Concept
1. Block B receives signatures from signers totaling ≥70% weight; `store_and_process_block_signature` calls `mark_locally_accepted(true)` and `broadcast_signed_block` pushes B to the stacks-node (`stacks-signer/src/v0/signer.rs:2525-2538`).
2. Before this signer observes the node's `NewBlock` event / tenure tip advancing past B, a coalition of signers with `>30%` weight (some of whom may have already signed acceptance, since acceptance and rejection are tracked independently) send `BlockResponse::Rejected` for B.
3. `store_and_process_block_rejection` sees `block_info.has_reached_consensus() == false` (state is `LocallyAccepted`, not yet `GloballyAccepted`) and proceeds; once `total_reject_weight + min_weight > total_weight`, it calls `mark_globally_rejected()` (`stacks-signer/src/v0/signer.rs:2290-2337`), which `check_state` permits from `LocallyAccepted`.
4. The stacks-node processes B into the canonical chain regardless (it independently verified the 70% signature threshold via `verify_signer_signatures`).
5. When this signer later observes B in the canonical tip, `check_latest_block_in_tenure` attempts `block_info.mark_globally_accepted()` (`stacks-signer/src/chainstate/mod.rs:462-476`), but `check_state` blocks `GloballyRejected -> GloballyAccepted`, so the call fails silently (only a `warn!`), leaving the signer's local state permanently `GloballyRejected` for a block that is actually canonical.

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
