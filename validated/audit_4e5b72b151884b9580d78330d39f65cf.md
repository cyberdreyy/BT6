### Title
Unbounded recursive JSON parsing of attacker-controlled Config-program `config_data` in `parse_config` causes RPC-thread stack overflow - (File: `account-decoder/src/parse_config.rs`)

### Summary
`parse_config` in `account-decoder/src/parse_config.rs` decodes a Config-program account's bincode payload into a raw `String` and then feeds that string directly into `serde_json::from_str` with no depth or size limiting. Because `serde_json`'s default parser recurses once per nested JSON container, an attacker who creates a `validator-info` Config account containing a maximal-size, deeply-nested JSON string (e.g. thousands/millions of `[` characters) can trigger a stack overflow on the thread handling a single `getAccountInfo`/`getProgramAccounts` (`jsonParsed`) RPC call.

### Finding Description
The relevant code path is: [1](#0-0) 

`parse_config` first bincode-deserializes `ConfigKeys` from the account, and if `keys[0].0 == validator_info::id()` it calls `parse_config_data::<String>`, which bincode-deserializes the remaining account bytes (via `get_config_data`) into a plain `String`: [2](#0-1) 

The resulting string (`validator_info.config_data`) is then passed unmodified into `serde_json::from_str`: [3](#0-2) 

Nothing upstream constrains the *content* of this string — only the CLI-side publisher path (`cli/src/validator_info.rs`) enforces `MAX_VALIDATOR_INFO`/`MAX_LONG_FIELD_LENGTH` limits, but those are client-side conventions, not on-chain/program-level enforcement: [4](#0-3) 

An attacker does not need to use the CLI publisher at all. Any account owned by the Config program whose bincode-decoded `ConfigKeys.keys[0].0` equals `validator_info::id()` and whose subsequent bytes bincode-decode as a `String` will be treated as validator info. The attacker fully controls the account's raw byte content (up to `MAX_PERMITTED_DATA_LENGTH`), so they can construct a payload whose "string" content is a deeply nested JSON document (e.g., `"[[[[[...]]]]]"`). `serde_json`'s recursive-descent parser has no built-in recursion-depth cap, so each nesting level consumes additional native stack frames; with enough nesting within the 10MiB account-size budget, this exhausts the RPC-handling thread's stack.

This is reached from JSON-RPC account/program-account queries via `parse_account_data_v3`, which dispatches Config-owned accounts to `parse_config`: [5](#0-4) 

`rpc/src/rpc.rs` calls into this encoding path when a client requests `jsonParsed` encoding for `getAccountInfo`/`getProgramAccounts`. There is no `catch_unwind` wrapping this decode logic in the RPC layer (confirmed no `catch_unwind` usage near `parse_account_data_v3`/`encode_account` call sites), so a stack overflow here aborts the whole validator process rather than being caught and converted into an RPC error.

### Impact Explanation
A single unprivileged client can create one on-chain Config account (paying only normal account-creation rent) containing a maliciously nested JSON payload, then issue one `getAccountInfo`/`getProgramAccounts` call with `encoding: "jsonParsed"` against that pubkey. This triggers an uncatchable stack overflow that aborts the entire validator process, not merely the requesting connection — matching the "validator-process crash from one request" bounty category, and specifically the audit's scoped impact of "single-client stack exhaustion or crash while decoding one config account."

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: build a Config-program account (owned by the Config program) whose `ConfigKeys.keys[0].0` bincode-decodes to `validator_info::id()`, followed by a bincode-encoded `String` consisting of deeply nested JSON brackets, sized up to `MAX_PERMITTED_DATA_LENGTH`. No special privileges, staking, or leader control are required — only a normal transaction creating/writing the account and one subsequent RPC read. This is fully repeatable and deterministic.

### Recommendation
Do not call `serde_json::from_str` on unbounded, attacker-controlled account content without a recursion/depth guard. Options:
- Use a depth-limited JSON parser (e.g., configure `serde_json` with `serde_stacker` to grow the stack dynamically, or use a bounded iterative parser) before returning `ConfigAccountType::ValidatorInfo`.
- Enforce a maximum length/depth check on `config_data` in `parse_config`/`parse_config_data` prior to JSON parsing, rejecting (returning `ParseAccountError::AccountNotParsable`) any string exceeding a sane bound (e.g., `MAX_VALIDATOR_INFO`-like limit) rather than trusting the CLI-only convention.
- Wrap the account-decoding dispatch in `parse_account_data_v3` (or its RPC call sites) with a size-limited worker/`catch_unwind` boundary so a decode-time panic/overflow cannot take down the whole process.

    let nested = "[".repeat(depth) + &"]".repeat(depth);

    let validator_info = ValidatorInfo { info: nested };

    let mut data = serialize(&ConfigKeys {

    .unwrap();
    data.extend_from_slice(&serialize(&validator_info).unwrap());

    // returning Err(ParseAccountError::AccountNotParsable).
    let _ = parse_config(&data, &info_pubkey);

pub fn parse_config(data: &[u8], _pubkey: &Pubkey) -> Result<ConfigAccountType, ParseAccountError> {
    let parsed_account = deserialize::<ConfigKeys>(data).ok().and_then(|key_list| {
        if !key_list.keys.is_empty() && key_list.keys[0].0 == validator_info::id() {
            parse_config_data::<String>(data, key_list.keys).and_then(|validator_info| {
                Some(ConfigAccountType::ValidatorInfo(UiConfig {
                    keys: validator_info.keys,
                    config_data: serde_json::from_str(&validator_info.config_data).ok()?,
                }))
            })
        } else {
            None
        }
    });
    parsed_account.ok_or(ParseAccountError::AccountNotParsable(
        ParsableAccount::Config,
    ))
}

fn parse_config_data<T>(data: &[u8], keys: Vec<(Pubkey, bool)>) -> Option<UiConfig<T>>
where
    T: serde::de::DeserializeOwned,
{
    let config_data: T = deserialize(get_config_data(data).ok()?).ok()?;
    let keys = keys
        .iter()
        .map(|key| UiConfigKey {
            pubkey: key.0.to_string(),
            signer: key.1,
        })
        .collect();
    Some(UiConfig { keys, config_data })
}
