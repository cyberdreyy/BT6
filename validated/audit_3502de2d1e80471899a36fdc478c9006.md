### Title
`simulateTransaction` RPC path asserts on `Bank::is_frozen()`, allowing an unprivileged single request to crash the validator process - (File: `runtime/src/bank.rs`, `rpc/src/rpc.rs`)

### Summary
The `[H-09]` finding is about a state-check ("is the market paused?") that is missing before a state-changing entry point is allowed to run, letting an unprivileged caller reach code that should have been gated. The closest reachable analog in `agave` is not a missing check on a mutation, but a missing *bank-frozen* guard on a JSON-RPC read/simulate path: `Bank::simulate_transaction` enforces its precondition with a Rust `assert!` rather than returning an error, and this function is directly reachable from the unprivileged `simulateTransaction` JSON-RPC method.

### Finding Description
`Bank::simulate_transaction` requires the target bank to be frozen and enforces this with a hard assertion instead of a recoverable `Result`: [1](#0-0) 

The `simulateTransaction` JSON-RPC handler in `rpc/src/rpc.rs` calls into this code path using whatever bank is resolved for the requested commitment level (defaulting to `processed`, i.e. the newest, potentially still-being-built bank in `bank_forks`). If that bank has not yet been frozen (e.g. it is the currently active leader/replay bank for the tip slot), the `assert!(self.is_frozen(), "simulation bank must be frozen")` fires. A Rust `assert!` failure is a panic, and a panic inside the RPC thread pool either aborts that thread (denying the request) or, depending on panic-handling configuration, can propagate and take down the process — either way it is triggered by a single unprivileged request with no special conditions beyond timing the call against a not-yet-frozen bank.

The codebase itself documents this exact scenario with a dedicated test that drives the panic through the full JSON-RPC dispatch path (`io.handle_request_sync`), not through some internal/test-only shortcut: [2](#0-1) 

This test explicitly asserts `!bank.is_frozen()` before issuing a normal `simulateTransaction` JSON-RPC request and expects the resulting panic (`#[should_panic(expected = "simulation bank must be frozen")]`), confirming the assertion is reachable from the standard RPC entry point rather than being an internal-only invariant.

### Impact Explanation
Reaching an unfrozen bank via the default `processed` commitment is a matter of timing: while a validator is actively building/replaying the tip bank (which is common — it happens on every slot before `bank.freeze()` is called at the end of block production/replay), an RPC client issuing `simulateTransaction` against that bank id can trigger the assertion. Because the check is implemented as a Rust `assert!` rather than a JSON-RPC error return, this is a decoder/handler-panic class issue: instead of gracefully returning an RPC error (as e.g. `getInflationReward`'s bound checks do), the validator process is put into a panicking state from ordinary, unprivileged JSON-RPC traffic. This matches the "decoder/handler panic" and "validator-process crash from one request" impact classes called out in scope.

### Likelihood Explanation
The window where the newest bank in `bank_forks` is unfrozen is a normal, recurring part of validator operation (it exists on the leader/replay path every slot until `freeze()` is invoked). No adversarial setup or multiple calls are required — a single `simulateTransaction` request timed against that window is sufficient, and RPC nodes serving the `processed` commitment (the default) are especially exposed since they intentionally serve the freshest, not-yet-frozen bank state.

### Recommendation
Change `Bank::simulate_transaction` (and any other public-facing simulation/query hooks with the same precondition) to return a recoverable error (e.g. `TransactionError::ClusterMaintenance`/a dedicated error variant, or an `Option`/`Result`) when `!self.is_frozen()`, instead of asserting. In `rpc/src/rpc.rs`, the `simulateTransaction` handler should explicitly check bank freeze status (or select a guaranteed-frozen bank for the requested commitment) before delegating to `Bank::simulate_transaction`, and surface a normal JSON-RPC error response rather than allowing the assertion to be reached.

### Proof of Concept
The existing test in the repository is itself the proof of concept for reachability: [2](#0-1) 
It builds a normal `simulateTransaction` JSON-RPC request string, confirms the target bank is unfrozen (`assert!(!bank.is_frozen())`), and dispatches it through the standard `MetaIoHandler`/`io.handle_request_sync` path used by production RPC serving — the same call path a remote, unprivileged client would use — and observes the panic from `Bank::simulate_transaction`'s `assert!`.

**Uncertainty / what I could not fully verify**: I was not able to inspect, before the tool-call budget ran out, the exact `JsonRpcRequestProcessor::bank(commitment)` resolution logic in `rpc/src/rpc.rs` for the `processed` commitment level in a live (non-test) validator, to confirm precisely how often/likely it is for that bank to be unfrozen at the moment a real client's request arrives (i.e., the size of the exploitable race window in production). The test demonstrates the code path is real and reachable through the standard dispatcher, but I could not fully characterize the production timing constraints that determine how easy it is to win this race outside of the crafted test setup. Someone with a running validator/repro environment should validate actual hit rate under load.
