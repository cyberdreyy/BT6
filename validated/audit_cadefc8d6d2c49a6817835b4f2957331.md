### Title
Missing lower-bound validation on `num_confirmations` in `MultiSigContract::new` allows deployment of a multisig with threshold `0`, letting any single key execute requests without multi-party confirmation - (File: multisig/src/lib.rs)

### Summary
The `SophonFarming.sol` report flagged that owner-controlled numeric parameters (`pointsPerBlock`, `boosterMultiplier`) were unbounded `uint256` values with no validation, which could break accounting invariants. The same bug class exists in `multisig/src/lib.rs`: the `num_confirmations` field, which defines the "k" in the "k-of-n" confirmation threshold that gates every fund transfer, key addition, or contract upgrade the multisig can perform, is accepted at initialization with no lower-bound (or any) validation.

### Finding Description
`MultiSigContract::new` takes `num_confirmations: u32` and stores it verbatim with the only guard being `assert!(!env::state_exists(), ...)`: [1](#0-0) 

There is no check that `num_confirmations > 0`, nor any check relating it to the number of access keys/members that will actually be attached to the account. Contrast this with the newer `multisig2` contract, whose `new` explicitly requires `members.len() >= num_confirmations`: [2](#0-1) 

and whose `SetNumConfirmations` handling for member-count invariants is enforced elsewhere via `delete_member`: [3](#0-2) 

The v1 `multisig` contract (`multisig/src/lib.rs`) has no equivalent safeguard at all: `num_confirmations` can be `0`. The confirmation/execution logic (shared architecture, described identically in the `multisig` and `multisig2` READMEs, and concretely implemented in `multisig2::confirm`) executes a request once accumulated confirmations reach the threshold: [4](#0-3) 

Specifically the guard is `if confirmations.len() as u32 + 1 >= self.num_confirmations { ... execute_request(...) }`. If `num_confirmations` is `0`, this condition (`0 + 1 >= 0`) is trivially true for the very first confirmation from any single access key, regardless of how many keys the account has. The intended custody binding — "a request requires `num_confirmations` independent confirmations before funds move" — collapses to "a request requires 1 confirmation," i.e., the multisig silently downgrades from k-of-n to 1-of-n.

### Impact Explanation
This directly matches the report's "Critical" bucket: "a multisig request executed below threshold." A multisig deployed (or misconfigured) with `num_confirmations = 0` effectively grants any single holder of one of the multisig's access keys full unilateral control over `Transfer`, `AddKey`, `DeployContract`, and `FunctionCall` actions — actions that were supposed to require independent multi-party agreement. Since `multisig` contracts are typically used to hold pooled or foundation-controlled NEAR, a single compromised or malicious keyholder could move funds that should require consensus, with no code-level defense.

### Likelihood Explanation
The value is fully attacker/deployer-controlled at `new()` time with zero validation, so likelihood of the invalid value being set is entirely a function of whether the deployer notices the omission — there is no on-chain safeguard preventing it. Given the report's precedent (the same bug class was found and had to be patched in `SophonFarming.sol` for `pointsPerBlock`/`boosterMultiplier`), this is a realistic oversight, especially since the sibling `multisig2` contract already recognizes the need for such a check (`members.len() >= num_confirmations`) while the original `multisig` contract lacks it entirely.

### Recommendation
Add input validation in `multisig::MultiSigContract::new` (and defensively in `confirm`/`SetNumConfirmations` handling) to require `num_confirmations >= 1`, and ideally bound it against the number of full-access keys attached to the account (mirroring the `multisig2` check `members.len() >= num_confirmations`). Reject `SetNumConfirmations` requests that would set the threshold to `0` or above the number of live keys.

### Proof of Concept
1. Deploy the `multisig` contract with three access keys, calling `new({"num_confirmations": 0})` — no assertion prevents this.
2. Any one of the three keyholders calls `add_request_and_confirm` with a `Transfer` action to their own account.
3. In `add_request_and_confirm` → `add_request` → `confirm`, the check `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates `0 + 1 >= 0 = true` on the first confirmation, so `execute_request` runs immediately and the transfer is sent — despite the multisig being nominally "3 keys" and no threshold of independent approval having actually been met.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
