### Title
User enumeration via timing side channel in `CreateSession` (bcrypt only executes when email exists) - ([File: core/sessions/localauth/orm.go])

### Summary
`CreateSession` performs a DB lookup (`FindUser`) and, only if the user exists, calls the expensive `utils.CheckPasswordHash` (bcrypt) before rejecting a bad password. A request for a non-existent email returns immediately after a fast SQL miss, while a request for a valid email with a wrong password additionally pays the full bcrypt cost. This produces a measurable latency gap that lets an unauthenticated attacker distinguish "email exists" from "email does not exist."

### Finding Description
In `CreateSession`, the flow is: `FindUser` → (if found) `constantTimeEmailCompare` → `utils.CheckPasswordHash` (bcrypt) → MFA lookup [1](#0-0) . If `FindUser` fails (e.g. `sql.ErrNoRows` for an unknown email), the function returns immediately at line 147, without ever invoking bcrypt [2](#0-1) . If the email does exist, `utils.CheckPasswordHash` runs bcrypt's `CompareHashAndPassword`, which always recomputes the full hash at the stored cost factor before comparing — this is inherently slow (tens to low-hundreds of milliseconds depending on cost) regardless of whether the password matches.

The `constantTimeEmailCompare` function itself is not the timing leak (its purpose is only to prevent a length/content-based comparison leak on the email string, and it is functionally almost a no-op here since `findUser`'s SQL already does a case-insensitive exact match) [3](#0-2) . The premise in the question that `utils.CheckPasswordHash` "short-circuits early on bcrypt mismatch length" is not accurate to how `golang.org/x/crypto/bcrypt.CompareHashAndPassword` works — it does not skip work based on password length vs. hash length; it always performs the full hash computation and a final constant-time byte comparison. So the specific mechanism alleged (an early bcrypt short-circuit) is not present.

However, the underlying observable effect described — that response timing differs between "known email + wrong password" and "unknown email" — is real, just for a different and more fundamental reason: bcrypt is only invoked at all on the "user exists" path. This is a standard, well-documented timing side channel pattern for login endpoints.

### Impact Explanation
This enables unauthenticated user enumeration: an attacker can iterate emails (e.g., candidate admin emails) and use response latency of `CreateSession` (reached via the login HTTP handler in `core/web/sessions_controller.go`) to determine whether an account exists, aiding targeted credential stuffing / password spraying. This is a lower-severity precursor to compromise, not a direct authentication bypass or data disclosure, and requires precise timing measurement over the network, which is noisy in practice.

### Likelihood Explanation
No credentials required — reachable by any unauthenticated client hitting the session/login endpoint. Feasibility depends on the attacker's ability to obtain a stable, low-noise timing signal from the server (e.g., low network jitter, repeated sampling/statistics to overcome jitter), which is a real but non-trivial precondition. The signal magnitude here is large (bcrypt cost, typically tens of ms) compared to typical network jitter, which makes it more feasible than sub-millisecond leaks, but this is still classified as a hardening/defense-in-depth issue rather than a direct compromise.

### Recommendation
Always perform a constant-cost password comparison regardless of whether the user was found, e.g., when `FindUser` fails, run `utils.CheckPasswordHash` against a fixed dummy bcrypt hash before returning the "Invalid email" error, so both branches pay equivalent bcrypt cost. Additionally consider rate-limiting/backoff on the login endpoint independent of timing concerns.

### Proof of Concept
Go benchmark/table test in `core/sessions/localauth/orm_test.go`:
1. Seed one user with a known email/bcrypt-hashed password.
2. Benchmark `orm.CreateSession` with `{Email: knownEmail, Password: "wrongpassword"}` over N iterations, record mean latency.
3. Benchmark `orm.CreateSession` with `{Email: "doesnotexist@example.com", Password: "wrongpassword"}` over N iterations, record mean latency.
4. Assert the mean latency difference between the two groups is statistically significant (e.g., > several standard deviations, or bcrypt-cost-order-of-magnitude difference), demonstrating the enumeration channel exists because bcrypt is skipped entirely on the "no such user" path.

Note: this confirms the enumeration-via-latency effect exists, but the root cause is "bcrypt is skipped when the user isn't found," not the length-based bcrypt short-circuit alleged in the question.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

func constantTimeEmailCompare(left, right string) bool {
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}
