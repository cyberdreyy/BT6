### Title
Lockup owner can supply a self-controlled whitelist contract to bypass Foundation-approved staking-pool validation, enabling early release of locked/unvested NEAR - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` lets the caller who pays for and becomes owner of the new lockup contract override the `staking_pool_whitelist_account_id` that will be hard-coded into the deployed lockup, instead of always using the Foundation-controlled whitelist set at factory `new()`. The same account later becomes the lockup's `owner_id` and is the only party allowed to call `select_staking_pool`, `deposit_and_stake`, etc. Because the owner can choose which "whitelist" contract the lockup will trust, the owner-only staking flow can be pointed at an attacker-deployed pass-through "whitelist" and an attacker-deployed fake "staking pool", letting the owner move locked/unvested NEAR out of the vesting schedule early.

### Finding Description
`create()` in `lockup-factory/src/lib.rs` accepts an optional `whitelist_account_id` parameter supplied by the caller (the future owner) and, if present, uses it instead of the factory's own `whitelist_account_id` when constructing `LockupArgs`: [1](#0-0) 

This value becomes the immutable `staking_pool_whitelist_account_id` field baked into the freshly deployed lockup contract at `new` time: [2](#0-1) 

The lockup contract's owner-only `select_staking_pool` uses exactly this stored account to decide whether a staking pool may be selected, before any deposit/stake/withdraw operations are permitted: [3](#0-2) 

The intended custody binding is: *"account trusted as a whitelist" == the Foundation's `WhitelistContract`, which only the Foundation or a Foundation-approved factory may add pools to* (see `whitelist/src/lib.rs`, `assert_called_by_foundation` / `factory_whitelist` gating): [4](#0-3) 

Because `create()` lets the paying/owning caller substitute this trust anchor with any account ID they control, the same person restricted by `assert_owner()` in the lockup can also be the author of the "whitelist" that `assert_owner`-gated staking calls rely on. A caller can deploy a trivial contract exposing `is_whitelisted` that always returns `true`, pass its account ID as `whitelist_account_id` to `create()`, then call `select_staking_pool` pointing at a second self-controlled contract that mimics the staking-pool interface (`deposit`, `deposit_and_stake`, `withdraw`, `get_account_total_balance`, etc.) but simply forwards received NEAR to an address of the owner's choosing instead of behaving like an audited staking pool. `deposit_and_stake`/`withdraw_from_staking_pool` then transfer locked/unvested NEAR out of the lockup account under owner control, without any Foundation whitelist vetting the destination contract: [5](#0-4) [6](#0-5) 

None of these owner methods independently re-validate that the selected staking pool is Foundation-whitelisted beyond the one-time `is_whitelisted` check gated by the caller-chosen whitelist contract, so the entire protection collapses to "trust whatever whitelist the owner supplied at creation time."

### Impact Explanation
This breaks the custody binding "a lockup's releasable amount versus its schedule": vesting/lockup schedules exist to prevent the owner from accessing NEAR before it vests, yet the owner can self-select the trust anchor that gates movement of the underlying escrowed NEAR to an external, owner-controlled contract, in effect releasing locked/unvested tokens early. This matches the Critical impact category "locked or unvested tokens released early" / "a wrongly whitelisted or wrongly parameterised deployment."

### Likelihood Explanation
Any account that pays the `MIN_ATTACHED_BALANCE` and calls `LockupFactory::create` with vesting/lockup terms can supply its own `whitelist_account_id`; no additional privilege, redeploy of the factory, or Foundation cooperation is required. Deploying two small helper contracts (fake whitelist + fake "staking pool") is trivial and fully within an ordinary user's capability.

### Recommendation
Do not allow the lockup creator/owner to control the `staking_pool_whitelist_account_id` used by their own lockup contract. Remove the `whitelist_account_id` override parameter from `LockupFactory::create` (or restrict it to Foundation-only callers) and always use the factory's own, Foundation-configured `whitelist_account_id` when constructing `LockupArgs`, matching the trust model already enforced in `whitelist/src/lib.rs`.

### Proof of Concept
1. Attacker deploys `FakeWhitelist` contract implementing `is_whitelisted(account_id) -> bool` that always returns `true`.
2. Attacker deploys `FakePool` contract implementing the staking-pool interface (`deposit_and_stake`, `withdraw`, etc.) that simply forwards attached/held NEAR to the attacker's own separate wallet instead of behaving like a real staking pool.
3. Attacker calls `LockupFactory::create(owner_account_id = attacker, ..., vesting_schedule = Some(...), whitelist_account_id = Some(FakeWhitelist))`, per `lockup-factory/src/lib.rs::create` (lines 107-166), becoming the owner of a freshly deployed lockup contract whose `staking_pool_whitelist_account_id` is `FakeWhitelist`.
4. As owner, attacker calls `select_staking_pool(FakePool)`; the lockup queries `FakeWhitelist::is_whitelisted(FakePool)`, which returns `true` (`lockup/src/owner.rs` lines 12-41), so `FakePool` becomes the selected staking pool with no Foundation vetting.
5. Attacker calls `deposit_and_stake(amount)` where `amount` is locked/unvested NEAR; the lockup transfers this NEAR to `FakePool`, which the attacker fully controls, achieving early access to unvested funds outside the intended vesting schedule.

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,

        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

    /// Adds the given staking pool account ID to the whitelist.
    /// Returns `true` if the staking pool was not in the whitelist before, `false` otherwise.
    /// This method can be called either by the NEAR foundation or by a whitelisted factory.
    pub fn add_staking_pool(&mut self, staking_pool_account_id: AccountId) -> bool {
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The given account ID is invalid"
        );
        // Can only be called by a whitelisted factory or by the foundation.
        if !self
            .factory_whitelist
            .contains(&env::predecessor_account_id())
        {
            self.assert_called_by_foundation();
        }
        self.whitelist.insert(&staking_pool_account_id)
    }
