### Title
Session server's shared `http.Server` lacks read/header timeouts and size limits, allowing one job's stalled/oversized session request to exhaust server-wide resources - ([File: session/server.go])

### Summary
`NewServer` constructs `s.httpServer` as a bare `&http.Server{}` with only `Handler` set, leaving `ReadTimeout`, `ReadHeaderTimeout`, `WriteTimeout`, `IdleTimeout`, and `MaxHeaderBytes` at Go's defaults (no read/header timeout, default 1MB `MaxHeaderBytes`). This server is shared process-wide across all jobs' sessions dispatched through `handleSessionRequest`, so a slow-trickling client on one job's session endpoint can tie up an accepted connection/goroutine indefinitely without bound, and cancelling that job does not close the underlying `net.Conn`.

### Finding Description
`NewServer` in `session/server.go` creates the shared HTTP server that serves every job's session traffic (terminal `exec`, proxy) through a single `tlsListener` and a single `http.Server` instance: [1](#0-0) 
No `ReadHeaderTimeout`, `ReadTimeout`, or `MaxHeaderBytes` are set before `Serve` is called: [2](#0-1) 
Each accepted connection spawns a goroutine in `net/http` that blocks on reading headers/body from the client if the attacker trickles bytes slowly; with no `ReadHeaderTimeout`, that goroutine (and its underlying `net.Conn`) can be held open indefinitely, consuming a file descriptor and a goroutine that would otherwise service other jobs' session requests on the same listener.

Regarding cancellation: `Build.waitForTerminal` only calls `s.Session.Kill()`, which closes the *terminal* connection object (`terminalConn.Close()` in `session/session.go`): [3](#0-2) 
This closes the terminal's internal connection (e.g., docker exec attach) but does not close or interrupt the raw HTTP `net.Conn`/goroutine that `http.Server` is managing for that request — the HTTP server's `Serve` loop and per-connection goroutine lifecycle are entirely internal to `net/http` and are not exposed to `Session.Kill()`. If a client stalls sending headers/body before the handler is even reached (i.e., before `execHandler`/`proxyHandler` runs), `Session.Kill()` has no connection object to act on at all — the stalled read is happening inside `net/http`'s per-connection goroutine, unreachable from the session/build layer.

Existing checks that might mitigate this were reviewed:
- `withAuthorization` gates access to `s.mux` handlers, but this middleware only runs after the HTTP layer has already read/parsed headers — it cannot prevent a slow-header attack, since the request never reaches the handler in that case.
- There is no `Close()` on individual connections tied to job cancellation; `Server.Close()` in `session/server.go` closes the entire shared server (all jobs), not a single connection.

Given all jobs' session traffic flows through this one shared listener and `http.Server`, a single job's slow/abusive session client can degrade or exhaust available server resources for concurrently running sessions of unrelated projects/jobs on the same runner host.

### Impact Explanation
Because `httpServer` and `tlsListener` are singletons for the whole runner process (all jobs share the same session-server listen address), a single malicious/careless job (unprivileged pipeline author who can request a session URL for their own job) can hold open enough slow connections to consume available file descriptors/goroutines, degrading or blocking session establishment (terminal, proxy) for other unrelated jobs running concurrently on the same runner. This is a process-wide resource-exhaustion/DoS impact scoped to the session subsystem, not sandbox escape or cross-project data access.

### Likelihood Explanation
Preconditions are realistic: `session_server` is a commonly enabled, non-hardened feature (interactive web terminals/proxying), and the vulnerable code (`NewServer`) is the only construction path for `httpServer`, used unconditionally. Any user able to trigger a job's interactive session (terminal endpoint) can act as the attacking client against their own session URL, and since the server serves multiple jobs' endpoints via one listener/`Serve` loop, the resource exhaustion is not confined to that job. No special privileges are needed beyond running a normal CI job with interactive web terminal/session enabled — repeatable at will by opening many stalled connections.

### Recommendation
Harden the shared `http.Server` in `NewServer` with bounded limits before `Serve` is called, e.g.:
- Set `ReadHeaderTimeout` and `ReadTimeout` (and ideally `WriteTimeout`/`IdleTimeout`) to reasonable bounds.
- Set `MaxHeaderBytes` explicitly to a small bound.
- Consider wrapping accepted connections with `netutil.LimitListener` or per-connection deadlines tied to job lifecycle, and ensure that on session/job cancellation the underlying `net.Conn` for in-flight requests is force-closed (e.g., via `http.Server.ConnState` hook tracking connections per session and calling `conn.Close()` on `Session.Kill()`), not just the higher-level terminal `Conn`.

### Proof of Concept
Go integration test in `session` package:
```go
func TestSessionServerSlowHeaderDoS(t *testing.T) {
    srv, err := session.NewServer(cfg, logger, certGen, sessionFinder)
    require.NoError(t, err)
    go srv.Start()
    defer srv.Close()

    // Open N raw TCP+TLS connections to srv.tlsListener's address,
    // send a partial HTTP request line/header very slowly (e.g. 1 byte
    // every few seconds), and never complete it.
    for i := 0; i < N; i++ {
        conn := dialSlowClient(t, srv.AdvertiseAddress)
        go trickleBytes(conn, "GET /session-a/exec HTTP/1.1\r\n", 5*time.Second)
    }

    // Simulate cancellation of the originating build/session (job-a),
    // e.g. call build.Session.Kill() or cancel job context.
    cancelJobA()

    // Assert: a fresh, well-behaved request to a *different* job's
    // session endpoint completes within a bounded time (e.g. 2s),
    // proving the listener/goroutine pool wasn't starved.
    start := time.Now()
    resp, err := newSessionClient().Get(sessionBURL)
    require.NoError(t, err)
    require.Less(t, time.Since(start), 2*time.Second)
}
```
Expected current behavior (bug present): with default `http.Server{}` settings and no forced `net.Conn` closure on `Kill()`, the slow connections remain open past job-a cancellation, and under sufficient `N` the assertion on session-b's bounded response time fails or the server runs out of file descriptors/goroutines. After adding `ReadHeaderTimeout`/`MaxHeaderBytes` and conn-tracking cancellation, the slow connections are dropped promptly and the test passes.

	if s.httpServer == nil {
		return errors.New("http server not set")
	}

	err := s.httpServer.Serve(s.tlsListener)

	// ErrServerClosed is a legitimate error that should not cause failure
	if err == http.ErrServerClosed {
		return nil
	}
	return err
}

func (s *Session) Kill() error {
	s.lock.Lock()
	defer s.lock.Unlock()

	if s.terminalConn == nil {
		return nil
	}

	err := s.terminalConn.Close()
	s.terminalConn = nil

	return err
}
