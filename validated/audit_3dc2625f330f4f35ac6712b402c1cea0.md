## Analysis

The reported bug class is a "lookup drift": a security check pattern-matches against an **under-inclusive identifier** (`NID_undef`) instead of the intended exact match, silently falling back to a weaker/wrong equivalent (`NULL` cipher) that a supermajority never sanctioned. The strongest reachable analog in this repo is a duplicate-tenure-block check that queries an **under-inclusive predicate** (`GloballyAccepted` only) instead of the correct one (`GloballyAccepted OR LocallyAccepted`), letting a signer double-sign a competing tenure-start block within a tenure it already signed.

### Root cause

`SortitionsView::validate_tenure_change_payload` (v1 chainstate, still in the active v1 protocol path) guards against re-signing a competing tenure-change block in the same tenure by querying only globally-accepted blocks: [1](#0-0) 

```rust
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)
```

`get_last_globally_accepted_block` only matches `BlockState::GloballyAccepted`, and deliberately excludes `LocallyAccepted` — i.e. a block this very signer has already put its own signature over but that the network hasn't yet gathered a 70% threshold for. [2](#0-1) 

The v2 equivalent (`GlobalStateView::validate_tenure_change_payload`) was already fixed to use `get_last_signed_block`, which covers both `GloballyAccepted` and `LocallyAccepted`: [3](#0-2) 

And a regression test explicitly documents this exact class of bug and its fix on the v2 path, with the comment stating the pre-fix behavior "would have incorrectly passed because `get_last_globally_accepted_block` would not find the locally-accepted block": [4](#0-3) 

The v1 path (`stacks-signer/src/chainstate/v1.rs`) still uses the narrower `get_last_globally_accepted_block` predicate — the same class of miss the v2 fix addressed.

### Title
Under-inclusive duplicate-tenure check in v1 signer chainstate lets a signer double-sign a tenure - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionsView::validate_tenure_change_payload` (v1) checks for a prior signed block in the same tenure using `SignerDb::get_last_globally_accepted_block`, which only matches `BlockState::GloballyAccepted`. It misses blocks the signer has already put a signature over but that have only reached `BlockState::LocallyAccepted` (i.e., signed by this signer, group threshold not yet observed). This is analogous to the CVE's NID_undef→NULL-cipher fallback: an identity/predicate check silently matches a weaker equivalence class than the one that was actually intended, letting through what should have been rejected.

### Finding Description
A miner controlling one slot can, within a single tenure:
1. Propose tenure-start block `A`. The signer validates it, pre-commits, and — once the local pre-commit threshold is reached — signs it (`mark_locally_accepted`), moving it to `BlockState::LocallyAccepted`. This is a real signature the signer has committed, but it may not yet have reached the network-wide 70% acceptance threshold (e.g. other signers are slow, partitioned, or the miner never gathers/broadcasts enough acceptances).
2. Before `A` is globally accepted, the miner proposes a second, conflicting tenure-start block `B` for the *same tenure* (same `consensus_hash`), e.g. with different transactions.
3. `validate_tenure_change_payload` in `chainstate/v1.rs` calls `get_last_globally_accepted_block(&block.header.consensus_hash)`. Since `A` is only `LocallyAccepted`, not `GloballyAccepted`, this returns `None`.
4. The `DuplicateBlockFound` rejection is never triggered, and block `B` passes this check as if no signed block existed yet in the tenure.
5. If `B` subsequently passes node validation and the pre-commit/signature aggregation logic (`store_and_process_block_signature`, `stacks-signer/src/v0/signer.rs`), the signer can end up putting a signature over two distinct, conflicting blocks at the same height/tenure — breaking the "one signed block per tenure" equality that the v2 code path was explicitly hardened against.

This is a strict regression relative to v2, which fixed the identical issue by switching to `get_last_signed_block` (covers `GloballyAccepted` + `LocallyAccepted`).

### Impact Explanation
This breaks a core safety invariant: a signer signing a conflicting/duplicate block within a tenure it has already signed. Under the rules given (Critical: "a signer signing an invalid, non-canonical, or conflicting block"), this is a Critical-class break, though it is scoped to the legacy/v1 signer protocol path rather than the currently-hardened v2 path.

### Likelihood Explanation
Requires only a single miner slot (no majority of signers, no other signer's key) and exploits a timing window that is a normal part of the two-phase-commit flow — a locally-accepted-but-not-yet-globally-accepted block is an expected, frequently-occurring intermediate state, not an edge case requiring adversarial network control. The only precondition is that the signer is still running the v1 chainstate path (pre `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`); this is directly analogous to how the OpenSSL bug required use of the legacy `EVP_CIPHER_meth_new` API path rather than the new provider mechanism.

### Recommendation
In `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`, replace `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` with `signer_db.get_last_signed_block(&block.header.consensus_hash)`, matching the fix already applied on the v2 path, so that any block the signer has signed (locally or globally accepted) blocks a conflicting tenure-change proposal.

### Proof of Concept
1. Boot a v1-protocol signer (pre-`GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`).
2. Miner proposes tenure-start block `A`; drive the signer through pre-commit and local signature (`mark_locally_accepted`) without letting the network reach the 70% global-acceptance threshold (e.g. stall/ignore other signers' pre-commits, as done in existing test helpers such as `TEST_IGNORE_ALL_BLOCK_PROPOSALS` / `TEST_SIGNERS_IGNORE_PRE_COMMITS`).
3. Miner proposes a second tenure-start block `B` for the same `consensus_hash` with different transactions.
4. Call `SortitionsView::check_proposal` → `validate_tenure_change_payload` on `B`; observe it returns `Ok(())` instead of `Err(RejectReason::DuplicateBlockFound)`, because `get_last_globally_accepted_block` does not see `A` (which is only `LocallyAccepted`). This mirrors the exact scenario reproduced against the v2 path in `check_tenure_change_rejects_when_locally_accepted_block_exists` before its fix.

            tenure,
            &BlockState::GloballyAccepted.to_string(),

    }
