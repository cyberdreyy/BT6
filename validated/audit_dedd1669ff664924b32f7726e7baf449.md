### Title
Stale confirmations from removed multisig members remain counted toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` (`multisig2/src/lib.rs:355-379`) only purges requests and confirmations that were *created* (`r.member == member`) by the removed member, but does not scrub confirmations that member previously *cast* on requests created by other members. Those stale confirmations remain in the `confirmations: LookupMap<RequestId, HashSet<String>>` map and continue to be counted by `confirm()` toward `num_confirmations` after the member has been removed from the trusted set.

### Finding Description
The contract's core invariant is a K-of-N scheme: "Any of the access keys or set of specified accounts can confirm, until the required number of confirmation achieved" (`multisig2/README.md:8`). `confirm()` counts entries in `self.confirmations.get(&request_id)` against `self.num_confirmations` without verifying that every entry in that `HashSet<String>` still corresponds to a *current* member [1](#0-0) .

`delete_member` is the only place member removal is handled, and its cleanup logic filters `self.requests` by `r.member == member` (the *creator* of the request), removing those requests' confirmation sets entirely. It never scans other, unrelated requests' confirmation sets for stale entries left by the removed member: [2](#0-1) 

Sequence:
1. Members A, B, C, D with `num_confirmations = 3`.
2. Member B creates Request X (`add_request`), and member A confirms it (`confirm`) — the set `confirmations[X] = {"A"}`.
3. Members later execute a separate request that removes A from the multisig (`DeleteMember { member: A }`), because A's key was compromised or A left the organization. `delete_member` runs, but since A did not create Request X, the `{"A"}` entry inside `confirmations[X]` is never cleared.
4. Now only C and D remain as live members besides B. When C and D each call `confirm(X)`, `confirmations[X].len()` becomes 3 (`{"A","C","D"}`) which is `>= num_confirmations (3)`, so `execute_request` fires — even though only 2 *current* members (C, D) actually voted.

This breaks the equality the system is supposed to guarantee: `live-member confirmations counted == confirmations required`. Instead, `confirmations counted (including departed members) == confirmations required`, letting a request execute with fewer currently-authorized signers than the configured threshold.

### Impact Explanation
This directly matches the "Critical" impact class: a multisig request executed below the effective threshold. A `Transfer`, `AddKey`/`AddFullAccessKey`, `DeployContract`, or `AddMember` (re-adding a colluding party) action can be pushed through with the deliberately-removed member's phantom vote, allowing NEAR to move, keys to be added, or code to be deployed without the number of currently-trusted approvals the multisig was configured to require.

### Likelihood Explanation
The precondition (a member confirms a request, and is later removed while that request is still outstanding) is a realistic and even expected operational pattern — member removal is the standard incident-response action after a suspected key compromise or personnel change, and pending requests routinely stay open (the contract enforces `REQUEST_COOLDOWN` and an `active_requests_limit`, implying requests are expected to live for a while before being confirmed/deleted). No unusual privilege beyond ordinary use of the contract's own `add_request`/`confirm`/`DeleteMember` flow is needed; the bug is in the cleanup logic itself, not in any single actor exceeding their authority.

### Recommendation
When removing a member in `delete_member`, iterate over all outstanding requests' confirmation sets (not just those created by the removed member) and strip the removed member's string entry from each. Alternatively, validate membership of every entry in a request's confirmation set at `confirm()`-time (recomputing effective confirmation count from only current members) before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. As `B`: `add_request` for `Transfer { amount }` to some receiver → `request_id = X`.
3. As `A`: `confirm(X)` → `confirmations[X] = {A}` (1/3).
4. As B, C, D collectively reach 3 confirmations on a `DeleteMember{ member: A }` request and execute it → A removed from `members`; `confirmations[X]` is untouched because request X was created by B, not A (`delete_member` filter `r.member == member` does not match X).
5. As `C`: `confirm(X)` → `confirmations[X] = {A, C}` (2/3, still below threshold, request not yet executed).
6. As `D`: `confirm(X)` → `confirmations[X] = {A, C, D}` → `len() + 1 >= 3` triggers `execute_request`, transferring funds — despite only 2 live members (C, D) having actually approved after A's removal. [2](#0-1) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
