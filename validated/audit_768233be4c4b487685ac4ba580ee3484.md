### Title
Stale rejection weight is never retracted when a signer flips from Rejected to Accepted, corrupting the miner's approve/reject tally - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` maintains, per proposed block, two independent running counters — `total_weight_approved` and `total_weight_rejected` — inside `BlockStatus` [1](#0-0) . When a signer later changes its vote from `Rejected` to `Accepted` for the *same* block (a state transition the signer state machine explicitly allows via `LocallyRejected --> LocallyAccepted : re-evaluated`), the listener adds that signer's weight into `total_weight_approved` but never removes it from `total_weight_rejected`. The two tallies are updated by disjoint dedupe keys (`gathered_signatures` for approvals vs. `responded_signers` for the very first response of either kind), so nothing in this file ever decrements a bucket once weight has been added to it. This is the same class of bug as the reported `totalDeposited` issue: a value that must be adjusted on a later event is left stale, corrupting an aggregate that downstream logic treats as ground truth.

### Finding Description
The accept path only guards against double counting the *same* kind of response:
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
}
...
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [2](#0-1) 

The reject path guards on the shared `responded_signers` set:
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [3](#0-2) 

Consider the sequence:
1. Signer S rejects the block first: `responded_signers.insert(slot_id)` succeeds (true), so `total_weight_rejected += weight(S)`.
2. S later re-evaluates (as designed by `should_reevaluate_block`/`BlockInfo::check_state`, which permits `LocallyRejected → LocallyAccepted`) and sends `Accepted`.
3. In the accept handler, the check is `!gathered_signatures.contains_key(slot_id)`, which is still `true` (S never signed before), so `total_weight_approved += weight(S)` as well.
4. Nothing in this file ever subtracts `weight(S)` back out of `total_weight_rejected`.

The consequence is that `weight(S)` is now counted in **both** buckets simultaneously, so `total_weight_approved + total_weight_rejected` can exceed the true, mutually-exclusive `total_weight` of the reward set. This is analogous to the Omnipool `totalDeposited` bug: the value is not adjusted for a state change (fee/withdrawal there, vote-flip here), leaving a downstream consumer with a corrupted aggregate.

The corrupted `total_weight_rejected` feeds directly into the block-push decision in `signer_coordinator.rs`, which is evaluated on every poll of the same `BlockStatus`:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ...
    return Err(NakamotoNodeError::SignersRejected { .. });
} else if block_status.total_weight_approved >= self.weight_threshold {
    return Ok(block_status.gathered_signatures.values().cloned().collect());
}
``` [4](#0-3) 

Because the rejection check is evaluated first and is never allowed to shrink, stale weight from a signer who has *already* switched its vote to Accepted can push `total_weight_rejected` past the 30% blocking-minority threshold even though, from the true/current state of all signers, fewer than 30% weight actually still rejects the block. The miner will then declare the block dead (`SignersRejected`) and discard it, even though the block may in truth carry ≥70% real, current approval weight.

### Impact Explanation
This breaks the equality the coordinator relies on — "aggregated rejected/approved weight" vs. "verified, current votes of the signer set" — by allowing one signer's stale, superseded rejection to be permanently double-counted alongside its own subsequent acceptance. The direct consequence is the miner discarding/aborting the assembly of a validly, sufficiently-signed block (a liveness wedge on block production), matching the "High" impact bucket (a component acting on stale/incorrect aggregated state rather than the verified accept/reject set). It does not require a majority of colluding signers — it only requires one signer (of sufficient weight, in combination with organically occurring rejections from others near the blocking-minority threshold) to legitimately reconsider its vote, a normal and expected occurrence given the state machine's own re-evaluation design.

### Likelihood Explanation
Vote flip-flopping (`LocallyRejected → LocallyAccepted`) is an explicitly supported, non-adversarial transition in the signer state machine (`BlockInfo::check_state`, `should_reevaluate_block`), triggered whenever a previously invalid-looking proposal becomes valid again (chain tip catches up, sortition context resolves, etc.). This is a routine occurrence under normal network conditions (e.g., transient validation races, timing skew between chainstate view updates), not a crafted attack, making the corrupted tally realistically reachable during ordinary operation rather than only under contrived conditions.

### Recommendation
Track each signer's current vote (Accept/Reject) as a single authoritative entry (e.g., `HashMap<slot_id, VoteKind>`) instead of two independently-incrementing counters guarded by different dedupe sets. When a signer's vote flips, subtract the previous contribution from its old bucket before adding to the new one, e.g.:
```rust
if let Some(prev) = block.votes.insert(slot_id, VoteKind::Accepted) {
    if prev == VoteKind::Rejected {
        block.total_weight_rejected = block.total_weight_rejected.saturating_sub(signer_entry.weight);
    }
}
block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
```
and symmetrically for the reject path, so `total_weight_approved` and `total_weight_rejected` always reflect the current, mutually exclusive state of each signer's most recent response.

### Proof of Concept
1. Miner proposes block B; `StackerDBListener` creates `BlockStatus` for `B` with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight W_S) sends `BlockResponse::Rejected` for B → `responded_signers.insert(S)` succeeds → `total_weight_rejected += W_S` [3](#0-2) .
3. Enough additional (legitimately rejecting) signer weight `W_other` arrives such that `W_S + W_other` is just under the blocking-minority threshold (`total_weight - weight_threshold`).
4. S re-validates the same block per the normal chainstate re-check flow and now sends `BlockResponse::Accepted` for B. Because `gathered_signatures` never contained S, the accept handler adds `total_weight_approved += W_S` [5](#0-4) , but `total_weight_rejected` is left at `W_S + W_other` — unchanged.
5. If any further signer (weight `W_extra`) rejects B for unrelated legitimate reasons such that `W_S + W_other + W_extra` crosses the blocking-minority threshold, `signer_coordinator.rs`'s `wait_for_signer_blocks_responses` observes `total_weight_rejected + weight_threshold > total_weight` and returns `SignersRejected`, discarding block B [6](#0-5)  — even though S's current vote is Accepted, and the *true* current rejecting weight (`W_other + W_extra`, excluding S) may be below the 30% blocking minority.

This was analyzed statically from the code paths above; I was not able to run the actual test harness to trigger the exact numeric scenario, so the concrete weight values above are illustrative rather than an executed reproduction.
