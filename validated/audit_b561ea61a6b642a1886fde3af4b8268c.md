### Title
Unbounded zip decompression in `extractZipFileEntry` enables disk-exhaustion DoS - (File: `helpers/archives/zip_extract.go`)

### Summary
`extractZipFileEntry` copies decompressed zip entry content via `io.Copy(out, in)` with no ceiling on output size, and this function is reached from both cache and artifact extraction paths that operate on attacker-controlled archive content. A crafted highly-compressed zip entry (zip bomb) can therefore cause the runner to write unbounded data to disk during extraction, exhausting shared host disk space.

### Finding Description
`extractZipFile` dispatches regular file entries to `extractZipFileEntry`, which opens the compressed entry and calls `_, err = io.Copy(out, in)` with no size tracking or limit [1](#0-0) . This is invoked per-file from `ExtractZipArchive`, which iterates over all entries in the archive without any aggregate or per-file decompressed-size check [2](#0-1) . The legacy zip extractor (`ziplegacy.extractor.Extract`) wraps this exact code path and is used by `commands/helpers/cache_extractor.go` and `commands/helpers/artifacts_downloader.go` to extract cache and artifact archives that a job/pipeline author fully controls the contents of [3](#0-2) . The alternate `fastzip` extractor used when `FF_USE_FASTZIP` is enabled delegates to the third-party `saracen/fastzip` library with no size-limiting option configured either — only extractor concurrency is configurable [4](#0-3) . There is a `MaxUploadedArchiveSize` control, but it only bounds the *compressed* archive size on upload to cloud storage — it does nothing to bound decompressed output during extraction, and by design compressed size is exactly what a zip bomb keeps small while decompressed size explodes. No other size/quota check exists in this code path for shell/generic executors that don't provide their own OS-level ephemeral-storage quota (only the Kubernetes executor optionally exposes `ephemeral_storage_limit`, and that is an admin-configured, opt-in control, not a Runner-enforced invariant).

### Impact Explanation
On a shared runner host (e.g. shell/docker executor without a per-job filesystem quota), a job that pushes a specially crafted cache or artifact zip can cause the runner's extraction step (during a later job restore) to write far more data to disk than the compressed size implies, filling the shared disk/inode budget and causing concurrently running or subsequently scheduled jobs from *other* projects on the same host to fail (out of disk space, failed writes, cache/artifact upload failures). This matches the scoped "persistent multi-tenant disruption" impact since disk exhaustion outlives the single job and affects unrelated tenants until disk space is manually reclaimed.

### Likelihood Explanation
This is straightforward for any unprivileged pipeline author to trigger: standard zip bomb techniques (e.g. nested zips or highly repetitive DEFLATE streams) reliably achieve compression ratios in the thousands-to-one range, so a small artifact/cache upload (well within typical size limits) can decompress to many gigabytes. The only precondition is a shared, non-quota-isolated runner host (shell executor, or docker/kubernetes executors without explicit disk quota configuration), which is a common and realistic deployment. No authentication bypass or additional privilege is needed — this uses the normal cache/artifact upload/download flow.

### Recommendation
Enforce a configurable maximum decompressed size while extracting, tracked cumulatively across all entries in `ExtractZipArchive`/`extractZipFileEntry` (e.g. wrap `io.Copy` with `io.CopyN`/a limited writer and abort with an error once a threshold is exceeded), and apply an equivalent limit option to the `fastzip` extractor path. Also consider validating declared uncompressed sizes in zip headers against a sane cap before beginning extraction, as a cheap pre-check.

### Proof of Concept
Go unit test in `helpers/archives`:
1. Build an in-memory zip (`archive/zip.Writer`) containing one file entry whose content is a long run of a repeated byte (e.g. 2 GB of zeros), which DEFLATE compresses to a tiny compressed size.
2. Call `archives.ExtractZipArchive` on this archive from a temp directory, with the process's working directory limited by a small disk quota (e.g. a tmpfs/loop-mounted filesystem with a 100 MB limit, or `syscall.Setrlimit(RLIMIT_FSIZE, ...)` on Linux).
3. Assert that today, extraction either fills the disk / hits the rlimit uncontrolled (proving no cap exists), versus after a fix, `ExtractZipArchive` returns an error once a configured decompressed-size cap (e.g. 500 MB) is exceeded, and confirm via `os.Stat` that the partially-written file size never exceeds the cap.

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}

func (e *extractor) Extract(ctx context.Context) error {
	opts, err := getExtractorOptionsFromEnvironment()
	if err != nil {
		return err
	}

	extractor, err := fastzip.NewExtractorFromReader(e.r, e.size, e.dir, opts...)
	if err != nil {
		return err
	}
	defer extractor.Close()

	return extractor.Extract(ctx)
}

func getExtractorOptionsFromEnvironment() ([]fastzip.ExtractorOption, error) {
	var opts []fastzip.ExtractorOption

	if val := os.Getenv(extractorConcurrency); val != "" {
		concurrency, err := strconv.ParseInt(val, 10, 64)
		if err != nil {
			return nil, fmt.Errorf("fastzip extractor concurrency: %w", err)
		}

		opts = append(opts, fastzip.WithExtractorConcurrency(int(concurrency)))
	}

	return opts, nil
}
