#### Title
Unbounded job-controlled `CACHE_REQUEST_TIMEOUT` produces arbitrarily long-lived Azure SAS tokens - (File: cache/azure/adapter.go)

### Summary
The Azure cache adapter's `generateSASToken` sets the SAS token expiry directly from `a.timeout`, which originates from the job-controllable `CACHE_REQUEST_TIMEOUT` CI variable with no upper bound enforced anywhere in the chain, unlike other similar settings that are clamped to `[1,10]`. A pipeline author can therefore mint a cache-access SAS token whose validity window is far larger than the intended request/job duration.

### Finding Description
`CACHE_REQUEST_TIMEOUT` is read as a raw job variable and stored as `b.buildSettings.CacheRequestTimeout` via `validate(variables, "CACHE_REQUEST_TIMEOUT", &b.buildSettings.CacheRequestTimeout, DefaultCacheRequestTimeout)` [1](#0-0) . The generic `*int` parse path in `validate` only does `strconv.ParseInt` with no min/max bounds check [4](#0-3) , in contrast to `validateAttemptSettings`, which explicitly clamps other integer settings to `[1,10]` [2](#0-1) . This timeout eventually reaches `cache.GetAdapter(config, timeout, ...)` → `createAdapter(config, timeout, fullPath)` → the registered factory `New(config, timeout, objectName)` for the Azure adapter, which stores it verbatim as `a.timeout` [5](#0-4) . In `generateSASToken`, `a.timeout` is passed straight into `signedURLOptions.Timeout` [6](#0-5) , which downstream (per the `sas.BlobSignatureValues` logic referenced in the question) becomes the SAS token's expiry (`now + timeout`). No cap is applied at any point in this path.

### Impact Explanation
Because the SAS token's expiry is derived from an attacker/job-controlled integer with no maximum enforced, a pipeline author can set `CACHE_REQUEST_TIMEOUT` to an extremely large value, causing the generated SAS token to remain valid for a duration vastly exceeding the actual job/cache operation window. If that token is later exposed through any secondary channel (trace log, debug output, artifact, etc.), an unrelated actor could use it to access the project's cache blob in Azure Storage after the job that generated it has completed — a persistent post-job unauthorized access window that would not exist if expiry were capped near actual operation time.

### Likelihood Explanation
Setting a CI/CD variable such as `CACHE_REQUEST_TIMEOUT` is trivially available to any pipeline author with `.gitlab-ci.yml` write access or protected/unprotected variable definition rights — it requires no special runner or admin privilege. The lack of bounds validation is straightforward to trigger deterministically and repeatably; every job run with an inflated value produces an equally inflated SAS expiry. The only remaining uncertainty (not verifiable from the files available in this index) is the exact expiry computation inside the underlying `sas.BlobSignatureValues`/`getSASToken` helper — this repo did not surface that file in the index, so the precise `now+timeout` arithmetic and any additional caps applied there could not be directly confirmed and should be checked in a live checkout.

### Recommendation
Clamp `CacheRequestTimeout` to a sane bounded range (similar to the `[1,10]` pattern used for attempt-count settings) in `validateAttemptSettings`/`validateVariables` in `common/build_settings.go`, and/or enforce a hard maximum SAS token lifetime independent of caller-supplied timeout inside `azureAdapter.generateSASToken` (e.g., `min(a.timeout, maxSASLifetime)`) before constructing `signedURLOptions.Timeout`.

### Proof of Concept
Unit test in `cache/azure/adapter_test.go`:
1. Construct an `azureAdapter` with `timeout` set to an extreme value (e.g., `1000 * time.Hour`), mirroring a job setting `CACHE_REQUEST_TIMEOUT=3600000`.
2. Call `generateSASToken` (with a stub `blobTokenGenerator` capturing the `signedURLOptions` passed to it).
3. Assert `options.Timeout` (and, in an integration test against the real `getSASToken`, the resulting SAS `se` query parameter parsed from the token URL) does **not** exceed a fixed, hard-coded maximum (e.g., 1 hour), regardless of the input timeout.
4. Additionally, add a test in `common/build_settings_test.go` asserting that `CACHE_REQUEST_TIMEOUT` values above an intended maximum are clamped, analogous to existing `EXECUTOR_JOB_SECTION_ATTEMPTS` clamp tests.

func (b *Build) validateAttemptSettings() []error {
	var errs []error

	clamp := func(variable *int, varName string) {
		const minAttempts, maxAttempts = 1, 10
		val := max(minAttempts, min(maxAttempts, *variable))
		if val != *variable {
			*variable = val
			errs = append(errs, fmt.Errorf("%s: number of attempts out of the range [%d, %d], clamping to: %d", varName, minAttempts, maxAttempts, *variable))
		}
	}

	clamp(&b.buildSettings.ExecutorJobSectionAttempts, "EXECUTOR_JOB_SECTION_ATTEMPTS")
	clamp(&b.buildSettings.GetSourcesAttempts, "GET_SOURCES_ATTEMPTS")
	clamp(&b.buildSettings.ArtifactDownloadAttempts, "ARTIFACT_DOWNLOAD_ATTEMPTS")
	clamp(&b.buildSettings.RestoreCacheAttempts, "RESTORE_CACHE_ATTEMPTS")
	clamp(&b.buildSettings.SecretsRetrievalAttempts, "SECRETS_RETRIEVAL_ATTEMPTS")

	return errs
}

func (a *azureAdapter) generateSASToken(ctx context.Context, upload bool) (string, error) {
	method := http.MethodGet
	if upload {
		method = http.MethodPut
	}

	signer := a.getSigner()
	if signer == nil {
		return "", nil
	}

	t, err := a.blobTokenGenerator(ctx, a.objectName, &signedURLOptions{
		ContainerName: a.config.ContainerName,
		Signer:        signer,
		Method:        method,
		Timeout:       a.timeout,
	})
	if err != nil {
		logrus.WithError(err).Errorf("error generating Azure SAS token")
		return t, err
	}

	return t, nil
}
