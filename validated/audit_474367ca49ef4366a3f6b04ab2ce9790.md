### Title
Post-default instant-withdraw receipts paid at par, draining the default recovery reserve — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` only clears the defaulted-epoch instant receipt when *both* `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized` are set. Any instant-withdraw basis that is not attributable to `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` falls through to `_transferFundedClaim(_user, amount)`, which pays the *entire* `instantWithdrawsRequests[_user]` balance 1:1 in underlying. An unprivileged tranche holder can therefore obtain an unhaircutted payout from the same underlying balance that backs `defaultRecoveryReserve`, stealing value owed to defaulted-epoch claimants. This is the direct analog of a data race: the claim path reads a stale/unsynchronized flag combination and one shared aggregate (`instantWithdrawsRequests`) without first reconciling the per-epoch ledger, so two "writers" (default finalization vs. instant-request accounting) interleave incorrectly.

### Finding Description
In `requestInstantWithdraw`, the strategy burns the CDO's strategy tokens and mints receipt tokens to the user, then increments both the aggregate `instantWithdrawsRequests[_user]` and the per-epoch `instantWithdrawsRequestsByEpoch[_user][epochNumber]` / `instantWithdrawClaimsByEpoch[epochNumber]` ledgers (`IdleCreditVault.sol:356-375`).

In `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`):

```solidity
if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
  _claimDefaultedInstantWithdrawRequest(_user);
}
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Two order-dependent flaws exist:

1. **Unfinalized window.** The code itself anticipates `defaultRecoveryFinalized == true` while `defaultInstantWithdrawsFinalized == false` (otherwise the conjunction would be redundant). In that window a defaulted-epoch instant receipt is *not* haircutted: `_claimDefaultedInstantWithdrawRequest` is skipped, and the whole `instantWithdrawsRequests[_user]` — including basis that should be paid at `defaultRecoveryPrice` — is paid at par via `_transferFundedClaim`, which draws from the strategy's underlying balance, i.e. the same pot that collateralizes `defaultRecoveryReserve`.

2. **Post-default receipts bypass the haircut permanently.** After `defaultRecoveryFinalized`, `requestInstantWithdraw` still records new receipts under the *current* `epochNumber`, not `defaultRecoveryEpoch`. When `claimInstantWithdrawRequest` runs, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844), finds 0 for a post-default request, and returns; the aggregate `instantWithdrawsRequests[_user]` then pays the new receipt in full at par from the reserve-backed balance. The per-epoch ledger was introduced precisely to distinguish default-epoch receipts from funded ones (`IdleCreditVault.sol:368-371`), but the claim path only consults it for the single `defaultRecoveryEpoch` bucket — a classic read/write race between the aggregate counter and the per-epoch attribution.

By contrast, the normal-withdraw path discriminates correctly: `claimWithdrawRequest` routes through `_claimPostDefaultWithdrawRequest` (reserve-backed, haircut applied at request time) before `_claimDefaultedWithdrawRequest` and `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:301-314`). The instant path has no equivalent `postDefault` bucket, so haircut isolation is broken only there.

### Impact Explanation
Direct theft of user funds. An attacker holding tranche tokens requests an instant withdraw through the CDO in the window where default recovery is finalized (or while finalization has not yet folded instant receipts into the recovery accounting). They receive underlying at 100% instead of `defaultRecoveryPrice`, paid out of the balance reserved for defaulted-epoch claimants. Loss per call ≈ `receiptAmount × (1 − defaultRecoveryPrice / 1e18)`; repeatable across multiple attacker-controlled addresses (receipts are per-user) until the reserve is depleted, causing insolvency for legitimate `_claimDefaultedWithdrawRequest` / `DefaultDistributor.claim` users.

### Likelihood Explanation
- Attacker needs only tranche tokens and a KYC-passed wallet — both unprivileged.
- Requires a borrower default (an event the protocol explicitly supports via `_handleBorrowerDefault`/`finalizeDefaultRecovery`), then either (a) finalization ordering that leaves `defaultInstantWithdrawsFinalized` false while claims are live, or (b) the CDO still permitting instant-withdraw requests post-finalization while the strategy's `requestInstantWithdraw` happily mints receipts. No guard in `requestInstantWithdraw` checks `defaultRecoveryFinalized` (`IdleCreditVault.sol:356-358` calls only `_onlyIdleCDO` and `_ensureDefaultRecoveryInitialized`).
- `nonReentrant` does not help: this is same-transaction, cross-function stale-state accounting, not reentrancy.

### Recommendation
- In `requestInstantWithdraw`, revert (or route into a reserve-priced `postDefault`-style bucket) once `defaultRecoveryFinalized` is true.
- In `claimInstantWithdrawRequest`, block par payout of any instant basis requested in or after `defaultRecoveryEpoch` unless it was included in recovery accounting: e.g. require `defaultInstantWithdrawsFinalized` before paying when `defaultRecoveryFinalized`, and deduct `instantWithdrawsRequestsByEpoch[_user][e]` for every epoch `e >= defaultRecoveryEpoch` from the funded amount.
- Keep per-epoch and aggregate instant ledgers atomically consistent: settle `instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws` for *all* outstanding epochs during `finalizeDefaultRecovery`, not only the default epoch.

### Proof of Concept
Foundry fork sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol` / `IdleCDOEpochQueue.t.sol`):

```solidity
// 1. Deposit via AA tranche (KYC'd attacker wallet), epoch runs, borrower defaults.
cdoEpoch.depositAA(trancheAmount);
// manager: startEpoch(); warp past epochEndDate; borrower repays nothing
// manager: stopEpoch triggers _handleBorrowerDefault -> finalizeDefaultRecovery
//         sets defaultRecoveryFinalized, defaultRecoveryEpoch, defaultRecoveryPrice < 1e18

// 2a. Unfinalized-instant window (variant A):
// attacker requested instant withdraw in default epoch; before
// defaultInstantWithdrawsFinalized is set, call:
strategy.claimInstantWithdrawRequest(attacker); // via CDO
// pays instantWithdrawsRequests[attacker] at par instead of * defaultRecoveryPrice

// 2b. Post-default request (variant B):
// CDO still allows requestInstantWithdraw (APR drop after default):
cdoEpoch.requestInstantWithdraw(attackerTrancheBal, tranche); // mints receipt @ current epoch
strategy.claimInstantWithdrawRequest(attacker);
// _claimDefaultedInstantWithdrawRequest reads byEpoch[attacker][defaultRecoveryEpoch] == 0
// -> full amount paid via _transferFundedClaim from reserve-backed balance

assertGt(attackerPayout, expectedHaircutted);
assertLt(strategy.defaultRecoveryReserve backing, honestClaimantsOwed);
```

Caveat: variant A depends on whether `finalizeDefaultRecovery` always sets `defaultInstantWithdrawsFinalized` atomically; variant B depends on the CDO permitting instant requests post-default. Both gating conditions live in code paths I could not fully enumerate within this scan (`finalizeDefaultRecovery` body and the CDO-side instant-request guard); if either path is reachable, the par payout is unconditional in `claimInstantWithdrawRequest`.
