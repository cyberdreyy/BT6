Based on the investigation, I found a structural analog to the SteadeFi bug: a validity check that is present on one code path but silently absent on the equivalent path in a different (newer) architecture that ultimately feeds the same trust decision.

### Title
Signer state machine's `bitcoin_block_arrival`/`make_miner_state` path (v2 global-state model) never runs `check_parent_tenure_choice`, so a miner's illegitimate reorg of the parent tenure is accepted without the "at most one globally-accepted block, too-close-to-next-sortition" guard that v1 enforces - ([File: stacks-signer/src/v0/signer_state.rs])

### Summary
In the pre-global-state (v1) code path, `SortitionsView::check_proposal` → `validate_tenure_change_payload` explicitly calls `SortitionData::check_parent_tenure_choice` before accepting a tenure-change block that reorgs off a tenure other than the immediately prior one [1](#0-0) . That helper is documented as the one signer-local decision that sanctions a reorg: it is only allowed "if every tenure being reorged has at most one globally accepted block and produced its first block too close to the next sortition to count" [2](#0-1) .

In the global-state (v2) model, the equivalent trust anchor is `MinerState::ActiveMiner.parent_tenure_id`, which is populated by `LocalStateMachine::make_miner_state` directly from `SortitionData::parent_tenure_id` returned by the node [3](#0-2) , with no call to `check_parent_tenure_choice` anywhere in `signer_state.rs`. `GlobalStateView::validate_tenure_change_payload` (v2's block-level check) only verifies that the tenure-change's `prev_tenure_consensus_hash` matches this already-adopted `parent_tenure_id` [4](#0-3)  — it never independently asks whether that parent-tenure choice was itself a legitimate reorg (the "at most one globally accepted block" rule). Grepping the whole repo shows `check_parent_tenure_choice` is only referenced in `chainstate/v1.rs`, `chainstate/mod.rs` (definition), `chainstate/tests/v2.rs` (unit tests of the helper itself), and `v0/signer.rs`; it is never invoked from `v0/signer_state.rs`, which is the code that actually builds `MinerState`/`parent_tenure_id` for the v2 (global-state) protocol version.

### Finding Description
This mirrors the SteadeFi pattern exactly: a critical post/side-check (`afterWithdrawChecks` / `check_parent_tenure_choice`) is applied on one branch (`if user withdraws in tokenA/B` / v1's per-proposal `validate_tenure_change_payload`) but is missing on the sibling branch that reaches the same sensitive state transition (LP-token withdrawal / v2's `make_miner_state` → `MinerState::ActiveMiner`). Because the v2 protocol is the currently active/newer path (`uses_global_state()` gate in `check_block_against_state`, `stacks-signer/src/v0/signer.rs:865-869`), a single malicious miner can commit to a `prev_tenure_consensus_hash` skipping over a tenure that has more than one globally accepted block, or one that started well before the next sortition — conditions v1 would reject as `RejectReason::ReorgNotAllowed` — and v2 signers will locally adopt that parent tenure via `make_miner_state` with no rejection, then sign a tenure-change block confirming it as long as `check_tenure_change_confirms_parent`/`confirms_expected_parent` (a simple height/freshness check, not a legitimacy check) passes.

### Impact Explanation
This breaks the "approved-parent vs. canonical" equality: a signer under the v2/global-state protocol can be induced by a single miner to sign a tenure-change block that reorgs off a tenure the protocol explicitly intended to protect (one with more than one globally-accepted block, i.e. a tenure that already had meaningful consensus behind it), something v1 signers running the same fork would reject. This is a "signer signing an invalid/non-canonical/conflicting block" class issue (Critical), since the missing check specifically exists to prevent silently discarding globally-accepted work via reorg.

### Likelihood Explanation
Reachable by a single miner slot: the attacker only needs to win a sortition, then broadcast a tenure-change block whose `prev_tenure_consensus_hash` points to a tenure that itself violates the `check_parent_tenure_choice` legitimacy rule. No majority-signer collusion, no other signer's key, and no local access are required — every v2 signer independently builds its `MinerState` via `make_miner_state`/`bitcoin_block_arrival` from the node's sortition data without ever calling the missing check.

### Recommendation
Add an equivalent legitimacy check to the v2/global-state path: either invoke `check_parent_tenure_choice` inside `LocalStateMachine::make_miner_state` (or `bitcoin_block_arrival`) before adopting a `parent_tenure_id` that differs from the immediately-preceding tenure, or invoke it inside `GlobalStateView::validate_tenure_change_payload` before trusting `parent_tenure_id` from `MinerState::ActiveMiner`, mirroring what `stacks-signer/src/chainstate/v1.rs:496-504` already does for the v1 path.

### Proof of Concept
1. Attacker mines sortition N+2, deliberately building on the sortition N tenure's last block rather than N+1's (a reorg of N+1).
2. Assume tenure N+1 already has ≥2 globally accepted blocks and did not start "too close" to the next sortition — under `check_parent_tenure_choice`'s rule this reorg should be `ReorgNotAllowed`.
3. All v2/global-state signers process the burn block; `LocalStateMachine::make_miner_state` sets `parent_tenure_id = N` unconditionally (no legitimacy check) [5](#0-4) .
4. The attacker proposes a tenure-change block whose `TenureChangePayload.prev_tenure_consensus_hash == N`. `GlobalStateView::validate_tenure_change_payload` only checks this matches the locally-adopted `parent_tenure_id` and that `check_tenure_change_confirms_parent` passes (a height/freshness check) [6](#0-5)  — both succeed.
5. Signers sign the block, orphaning tenure N+1's globally-accepted work, something a v1 signer facing the identical fork would have rejected via `ReorgNotAllowed`.

Note: I was not able to execute this scenario in a live cluster; this analysis is based on static code-path comparison between `chainstate/v1.rs`, `chainstate/v2.rs`, and `v0/signer_state.rs`, and the repository's own `docs/signer-flows.md` description of what `check_parent_tenure_choice` is supposed to guarantee.

            config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
