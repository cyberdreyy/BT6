### Title
Stale per-epoch instant-withdraw receipts inflate default-recovery basis and brick reserve claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` and never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. A user who claims a funded instant withdrawal and re-requests inside the same epoch leaves phantom receipt basis that poisons `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` at default finalization, then underflows in `_claimDefaultedInstantWithdrawRequest`, permanently freezing recovery funds for honest claimants.

### Finding Description
The CVE analog is a bounds/accounting-corruption flaw: the per-epoch receipt "buffers" are written on `requestInstantWithdraw` but never cleared on claim, so later accounting reads stale out-of-bounds data.

- `requestInstantWithdraw` writes both `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`. [1](#0-0) 
- `claimInstantWithdrawRequest` burns the receipt and sets only `instantWithdrawsRequests[_user] = 0`; neither per-epoch mapping is touched. [2](#0-1) 
- After a default, `defaultPendingClaimBasis` adds the stale `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis. [3](#0-2) 
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` and treats already-paid-out funds as a held reserve. [4](#0-3) 
- `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch value as `claimBasis` and does `instantWithdrawsRequests[_user] -= claimBasis` and `_burn(_user, claimBasis)`, which underflow when the user already claimed part of that epoch's receipts. [5](#0-4) 

Attack sequence (running epoch N, honest borrower/manager):
1. Attacker calls `requestInstantWithdraw(100)` via the CDO; the CDO collects the funded 100 (`collectInstantWithdrawFunds` decrements `pendingInstantWithdraws`).
2. Attacker calls `claimInstantWithdrawRequest` and receives 100. `instantWithdrawsRequestsByEpoch[attacker][N]` stays 100 and `instantWithdrawClaimsByEpoch[N]` stays 100.
3. Still in epoch N, attacker calls `requestInstantWithdraw(50)`. Now `instantWithdrawClaimsByEpoch[N] = 150`, attacker per-epoch = 150, `pendingInstantWithdraws = 50`.
4. Borrower defaults in epoch N; `finalizeDefaultRecovery` runs. `defaultPendingClaimBasis` includes the phantom 100; `_defaultPrefundedInstantReserve` counts `150 - 50 = 100` phantom tokens as reserve that was already paid out. `defaultRecoveryReserve` and `totalBasis` are both corrupted.
5. Attacker's own `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = 150` but `_burn(_user, 150)` reverts on the 50-token receipt (DoS on their claim — acceptable collateral damage for the attacker).
6. Worse, every other defaulted claimant draws from a `defaultRecoveryReserve` inflated by phantom basis; `_transferDefaultRecovery` decrements reserve and transfers underlying that does not exist for the last claimants → their claims revert permanently.

### Impact Explanation
Permanent freezing/theft of recovery funds: phantom receipt basis inflates `totalBasis` (diluting `defaultRecoveryPrice` for all active LPs and pending redeemers) and inflates `defaultRecoveryReserve` by funds already paid out, so later legitimate claims revert on `safeTransfer`/underflow, permanently locking underlying in the strategy. The broken invariant is "one receipt, one payout" plus isolation of the recovery reserve.

### Likelihood Explanation
Requires only an unprivileged tranche holder doing request → funded claim → re-request inside one epoch, plus a borrower default — an ordinary, honest-sequence event. No privileged misbehavior needed; guards (`_onlyIdleCDO`, `defaultRecoveryFinalized` checks) do not stop it.

### Recommendation
In `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (or per request epoch) and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, mirroring `_clearWithdrawClaimForEpoch`. Alternatively, in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`, cap `instantBasis` at the sum of unfunded receipts rather than the cumulative epoch counter.

### Proof of Concept
```solidity
// fork test: running epoch N on IdleCDOEpochVariant + IdleCreditVault
// 1) attacker deposits AA, requests instant withdraw
cdoEpoch.requestInstantWithdraw(attackerShares, attacker); // per-epoch = 100
// 2) manager funds it; attacker claims
vm.prank(manager); cdoEpoch.getInstantWithdrawFunds(); // collectInstantWithdrawFunds(100)
vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest(); // pays 100, stale per-epoch remains
// 3) attacker re-requests 50 in the SAME epoch N
cdoEpoch.requestInstantWithdraw(moreShares, attacker);
// instantWithdrawClaimsByEpoch[N] == 150, pendingInstantWithdraws == 50
// 4) borrower defaults; owner finalizes
vm.prank(owner); cdoEpoch.finalizeDefault(...);
cdoEpoch.finalizeDefaultRecovery(recovered, source);
// assert: instantWithdrawClaimsByEpoch[N] counted 150, prefundedReserve counted 100 phantom
// 5) attacker claim reverts (burn underflow); honest claimants' claims revert on safeTransfer
vm.expectRevert(); vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest();
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
