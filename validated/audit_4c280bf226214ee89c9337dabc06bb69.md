### Title
Miner activity is renewed by cheap, self-triggered reorg-attempt proposals, letting an unresponsive/malicious tenure miner indefinitely block signer fallback to the prior tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_latest_block_in_tenure` treats *any* conflicting/rejected block proposal that arrives inside `reorg_attempts_activity_timeout` (or that conflicts with a fresh pre-commit) as valid "miner activity" and calls `signer_db.update_last_activity_time(...)`, resetting the clock that `SortitionState::is_timed_out` uses to decide whether to fall back to the prior tenure's miner. A single miner (one slot, no signer majority needed) that has *not yet* had any block signed for its tenure can keep this clock alive indefinitely by simply re-broadcasting cheap, doomed-to-be-rejected block proposals at the sortition/tenure it controls, without ever producing a block the signers will actually approve. [1](#0-0) 

### Finding Description
`check_latest_block_in_tenure` is the shared chainstate check run at proposal time, at validate-ok, and at signing. When a proposed block does not confirm as many blocks as the signer expects (i.e., it conflicts with/reorgs an already-signed or pre-committed block in the tenure), the function does not simply reject it — it also calls `update_last_activity_time` for the tenure's `consensus_hash`, as long as the conflicting reorg attempt is "fresh" (within `reorg_attempts_activity_timeout` of the last signed/group time), or as long as it conflicts with a still-fresh pre-commit: [2](#0-1) 

This activity timestamp is exactly the value `SortitionState::is_timed_out` (v1) reads to decide whether the current tenure's miner has gone inactive and the signer should fall back to the prior tenure: [3](#0-2) 

The equality being protected is: *"has the current miner been silent for more than `block_proposal_timeout`?"* — `elapsed > block_proposal_timeout`, where `elapsed` is measured from `last_activity_time`. That value is supposed to reflect genuine, useful miner activity. But the code path that updates it is reachable purely by the miner proposing blocks that the signer set will always reject (e.g., a stale/duplicate-height proposal, or a proposal conflicting with a block the signer already pre-committed to). No majority of signers, no valid block, and no other signer's cooperation is required — only the tenure's own miner (or anyone able to relay a signed block proposal for that miner's tenure over the gossip/StackerDB channel) repeatedly emitting cheap proposals within the timeout window.

This is the structural analog of the reported bug class: just as the vault penalty computation in the external report depended on a value (`_totalAssets()`) that the caller could cheaply and temporarily inflate within one transaction to defeat a penalty/threshold check, here the liveness threshold (`elapsed > block_proposal_timeout`) depends on `last_activity_time`, a value the very miner being judged can cheaply and repeatedly refresh via self-generated, guaranteed-to-be-rejected proposals, defeating the intended penalty (falling back to a better miner).

The documented mitigation for this exact scenario is a 30%-rejection-weight rule that marks the miner invalid once enough signers reject a reorg attempt — but per the signer-flow documentation, this specific safety valve is skipped once the active protocol uses global signer state (v2): [4](#0-3) 

I was not able to fully trace, within the remaining tool budget, the exact `store_and_process_block_rejection`/`handle_block_rejection` code path in `stacks-signer/src/v0/signer.rs` that implements or skips this "mark miner invalid on 30% `ReorgNotAllowed` rejection" behavior under the global-state protocol version — this is a gap in my verification and should be confirmed directly in that file before treating the "safety valve is skipped in v2" claim as conclusively proven, even though it is stated explicitly in the repo's own flow documentation.

### Impact Explanation
If confirmed, this is a liveness wedge: signers running the affected protocol version can be kept waiting on a non-performing or adversarial miner's tenure indefinitely, refusing to fall back to `make_miner_state(prior sortition)`, because `is_timed_out` never observes `elapsed > block_proposal_timeout`. This matches the in-scope "High" impact category: a signer wedged into never signing valid blocks (from the *next* legitimate miner) because its state machine is stuck honoring an inactivity grace period that the current miner can renew at will.

### Likelihood Explanation
The action needed — proposing additional blocks at the same or lower height, which the signer's own logic already predicts will be rejected — is cheap, requires no stake, no majority, and no cooperation from other signers; it is entirely within the capability of a single tenure's miner (one slot) using ordinary gossip/proposal broadcast. The mitigating 30%-rejection-invalidate-miner rule, if indeed skipped under the global-state protocol path as the documentation states, would make this fully exploitable under that configuration; if the mitigation is not actually skipped (which I could not fully verify), the severity is reduced to a bounded/rate-limited nuisance rather than an unbounded wedge.

### Recommendation
- Do not let `update_last_activity_time` be refreshed by proposals that the signer's own logic will always reject (e.g., stale-height reorg attempts, or proposals conflicting with a pre-commit that has already been superseded), or cap the number/rate of times a single miner can renew activity this way within one tenure.
- Verify and, if necessary, restore the "30% rejection weight marks the miner invalid" safety valve uniformly across all supported signer protocol versions (including the global-state/v2 path), so that an unresponsive miner cannot indefinitely postpone fallback merely by keeping the activity timer warm.
- Add an explicit upper bound (independent of `last_activity_time`) on how long a signer will wait on a tenure that has never produced a signed block, so that renewed "activity" from rejected proposals cannot defeat the fallback timeout entirely.

### Proof of Concept

    pub fn check_latest_block_in_tenure(
        tenure_id: &ConsensusHash,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,
    ) -> Result<bool, ClientError> {
        let last_block_info = SortitionData::get_tenure_last_block_info(
            tenure_id,
            signer_db,
            tenure_last_block_proposal_timeout,
        )?;

        if let Some(info) = last_block_info {
            // N.B. this block might not be the last globally accepted block across the network;
            // it's just the highest one in this tenure that we know about.  If this given block is
            // no higher than it, then it's definitely no higher than the last globally accepted
            // block across the network, so we can do an early rejection here.
            if block.header.chain_length <= info.block.header.chain_length {
                warn!(
                    "Miner's block proposal does not confirm as many blocks as we expect";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "expected_at_least" => info.block.header.chain_length + 1,
                );
                if info.signed_group.is_none_or(|signed_time| {
                    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
                }) {
                    // Note if there is no signed_group time, this is a locally accepted block (i.e. tenure_last_block_proposal_timeout has not been exceeded).
                    // Treat any attempt to reorg a locally accepted block as valid miner activity.
                    // If the call returns a globally accepted block, check its globally accepted time against a quarter of the block_proposal_timeout
                    // to give the miner some extra buffer time to wait for its chain tip to advance
                    // The miner may just be slow, so count this invalid block proposal towards valid miner activity.
                    if let Err(e) = signer_db.update_last_activity_time(
                        &block.header.consensus_hash,
                        get_epoch_time_secs(),
                    ) {
                        warn!("Failed to update last activity time: {e}");
                    }
                }
                return Ok(false);
            }
        }

        // A block we have only pre-committed to must NOT veto this proposal, but, similar to above
        // this should still count as activity for the miner.
        let last_accepted_block = signer_db
            .get_last_accepted_block(tenure_id)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;
        if let Some(info) = last_accepted_block {
            let is_fresh_pre_commit = info.state == BlockState::PreCommitted
                && info.approved_time.is_some_and(|approved_time| {
                    approved_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
                        > get_epoch_time_secs()
                });
            if is_fresh_pre_commit && block.header.chain_length <= info.block.header.chain_length {
                info!(
                    "Miner's block proposal conflicts with a block we have only pre-committed to. Counting it as miner activity, but not rejecting the proposal.";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "pre_committed_signer_signature_hash" => %info.block.header.signer_signature_hash(),
                    "pre_committed_chain_length" => info.block.header.chain_length,
                );
                if let Err(e) = signer_db
                    .update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())
                {
                    warn!("Failed to update last activity time: {e}");

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
