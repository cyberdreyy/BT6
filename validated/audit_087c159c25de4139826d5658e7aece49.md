### Title
Front-runnable deterministic lockup account address in `LockupFactory::create` lets an attacker pre-empt the Foundation's vesting configuration and cause locked/unvested tokens to be released early - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the to-be-deployed lockup contract's account ID *solely* from the caller-supplied `owner_account_id` (`sha256(owner_account_id)` + factory account), and imposes no restriction on who may call it or what `vesting_schedule`/`lockup_duration` they may pass for that `owner_account_id`. [1](#0-0)  Because the address is fully predictable and permissionless, any unprivileged account can front-run the NEAR Foundation's intended vesting-lockup deployment for a given employee and instead create a fully-liquid, no-vesting/no-lockup contract at that exact address first. This mirrors the DeGate `registerToken` finding: which "bucket" (vested vs. non-vested) an account lands in is decided by a race rather than by the privileged caller's intent, and once the account exists it cannot be re-created or corrected.

### Finding Description
`create()` computes the deterministic child account:
```
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
``` [2](#0-1) 
and only sets `foundation_account_id` (and therefore grants the Foundation vesting-termination rights) when the caller-supplied `vesting_schedule` is `Some(..)`:
```
let mut foundation_account: Option<AccountId> = None;
if vesting_schedule.is_some() {
    foundation_account = Some(self.foundation_account_id.clone());
};
``` [3](#0-2) 

`create` is `#[payable]` with no caller/owner check, so any account can invoke it for an arbitrary `owner_account_id` as long as it attaches `MIN_ATTACHED_BALANCE`. [4](#0-3) 

In the deployed `LockupContract::new`, the amount considered "locked" is fixed at initialization to whatever balance the account holds at that moment, and if no vesting schedule is supplied, `vesting_information` is set to `None`:
```
let lockup_information = LockupInformation {
    lockup_amount: env::account_balance(),
    ...
};
let vesting_information = match vesting_schedule {
    None => {
        assert!(foundation_account_id.is_none(), ...);
        VestingInformation::None
    }
    ...
};
``` [5](#0-4) 

Per the contract's own documentation, when neither lockup nor vesting mechanisms are configured, tokens become liquid as soon as transfers are enabled: [6](#0-5)  — and `LockupFactory::create` hardcodes `transfers_information` to already-enabled: [7](#0-6) .

**Attack path:** The equality that should hold is `{owner_account_id, vesting terms actually deployed at the deterministic address} == {owner_account_id, vesting terms the Foundation intended to deploy}`. An unprivileged attacker who observes (or predicts) that the Foundation is about to deploy a vested lockup for `owner_account_id = victim` can front-run the Foundation's `create` call with the identical `owner_account_id` but `vesting_schedule = None`, `lockup_duration = 0`, `release_duration = None`, paying only `MIN_ATTACHED_BALANCE`. This wins the account-creation race (NEAR account IDs are globally unique), permanently occupying the deterministic address with a no-vesting, fully-liquid, foundation-less contract. The Foundation's subsequent legitimate `create()` for the same `owner_account_id` fails at the `create_account` action (name already taken) and refunds via `on_lockup_create`. [8](#0-7) . If the Foundation does not notice the pre-existing account and instead funds the vesting position by transferring NEAR directly to the now attacker-configured `lockup_account_id`, those funds land in a contract with `vesting_information::None`/`lockup_duration = 0` and become immediately withdrawable by the owner — an early release of what was meant to be locked/unvested NEAR.

### Impact Explanation
This matches the "Critical - locked or unvested tokens released early" impact category: an unprivileged party can dictate, ahead of the Foundation, whether a specific employee's lockup account enforces any vesting/lockup schedule at all, at an address the Foundation cannot avoid because it is a deterministic function of public information (`owner_account_id`). Once occupied, the account name cannot be reclaimed or fixed by the Foundation (NEAR account creation is one-shot), which is the exact "cannot be removed once registered" characteristic called out in the source report.

### Likelihood Explanation
The `create` function is fully permissionless (no owner/foundation check), requires only `MIN_ATTACHED_BALANCE` of NEAR, and the target address is trivially computable off-chain from `sha256(owner_account_id)`. [9](#0-8)  An attacker only needs to observe or anticipate a Foundation `create` transaction (e.g., via mempool/public announcement of a new hire) and submit a competing transaction with higher gas price/priority, a standard front-running technique.

### Recommendation
**Short term:** Restrict `LockupFactory::create` (or at minimum the branch that would set `vesting_schedule`) so that only the Foundation account can create a lockup with a given `owner_account_id` when a vesting schedule is intended, or require the Foundation to pre-reserve/pre-register the `owner_account_id` before permissionless creation is allowed for it. Alternatively, make the deterministic address depend on a value only the Foundation controls (e.g., a Foundation-issued nonce/signature) rather than solely on the public `owner_account_id`.

**Long term:** Document explicitly that `owner_account_id` → lockup-account derivation is public/predictable and audit all flows (Foundation tooling) to ensure they check `lockup_account_id`'s existence and configuration before transferring vesting funds to it, rather than assuming a successful `create` call.

### Proof of Concept
1. Foundation intends to create a vested lockup for `victim.near` and prepares a transaction: `create(owner_account_id="victim.near", ..., vesting_schedule=Some(schedule), ...)`.
2. Attacker computes `lockup_account_id = sha256("victim.near")[:20] + "." + factory_account` off-chain and submits `create(owner_account_id="victim.near", lockup_duration=0, lockup_timestamp=None, vesting_schedule=None, release_duration=None, whitelist_account_id=None)` with `MIN_ATTACHED_BALANCE` attached, with higher gas price to land first.
3. Attacker's transaction succeeds: `lockup_account_id` is created with `vesting_information::None`, `lockup_duration=0`, and `transfers_information::TransfersEnabled` (hardcoded) — i.e., no lock at all, owner = `victim.near`. [10](#0-9) [11](#0-10) 
4. The Foundation's original `create` call now fails at `create_account` (name taken), and its deposit is refunded via `on_lockup_create`. [8](#0-7) 
5. If the Foundation instead directly transfers the intended vesting NEAR balance to `lockup_account_id` (believing the account is correctly configured), the owner (`victim.near`) can immediately withdraw the full amount since no vesting/lockup restriction exists, per the documented liquidity rule for accounts with neither mechanism configured. [6](#0-5)

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
