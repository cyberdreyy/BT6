### Title
Unprivileged ERC4626 vault user can freeze `stopEpoch` indefinitely by draining vault liquidity, trapping all LP funds in the running epoch - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` unconditionally attempts `vault.withdraw(shortfall, ...)` whenever the vault's *accounting* value covers the shortfall, and reverts the whole `IdleCDOEpochVariant.stopEpoch` call with `StopEpochVaultLiquidityUnavailable` on failure. Any user of the shared ERC4626 vault (e.g. a borrower in the underlying Morpho markets) can withdraw/borrow all available liquidity so the withdraw reverts, repeatedly blocking epoch settlement and freezing every LP's funds.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, before pulling funds the CDO calls `IProgrammableBorrower.onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)` and lets hook reverts bubble up ("Hook reverts bubble so transient ERC4626 liquidity failures can be retried") [1](#0-0) .

Inside `onStopEpoch`, when `onHand < _amountRequired` the contract computes `shortfall` and only short-circuits to `return true` when `shortfall > _currentVaultAssets()` — i.e. when the shares' *convertToAssets value* is insufficient. It then calls `vault.withdraw(shortfall, address(this), address(this))` inside a try/catch that reverts with `StopEpochVaultLiquidityUnavailable` [2](#0-1) .

The flaw is the conflation of *economic coverage* (`convertToAssets`) with *withdrawable liquidity*. In lending-pool-backed ERC4626 vaults (Morpho/ERC4626-style, exactly what the foundry test uses via `IMMVault`), an unprivileged market participant can borrow or withdraw essentially all underlying liquidity without changing `convertToAssets` — the shares still price the claim on lent-out assets. Result:

- `shortfall <= _currentVaultAssets()` → the early `return true` is not taken,
- `vault.withdraw` reverts with liquidity insufficiency,
- `StopEpochVaultLiquidityUnavailable` propagates through `onStopEpoch` → `_stopEpoch` → `stopEpoch`/`stopEpochWithDuration`,
- the epoch stays running: no `collectWithdrawFunds`, no `expectedEpochInterest` settlement, no price update, and no `allowInstantWithdraw` path (instant withdraws are disabled in programmable mode anyway [3](#0-2) ).

The honest manager can only retry while liquidity is available; the attacker can keep utilization pinned at 100% (rolling or topping-up the borrow) for as long as they are willing to pay borrow interest.

### Impact Explanation
All LP funds are temporarily frozen for the duration of the attack: pending withdraw requests can never be claimed (they mature only through `stopEpoch` → `collectWithdrawFunds`), new deposits are paused while the epoch runs, and the pool cannot be stopped, repriced, or closed. The attacker is a plain ERC4626 vault user with no privileged role, matching the "user of the programmable borrower's ERC4626 vault" threat model. Cost to attacker is only borrow interest on the drained liquidity; frozen principal is the entire pool TVL plus pending requests.

### Likelihood Explanation
The attack requires a programmable-borrower deployment whose ERC4626 vault shares liquidity with public markets (the intended design — idle funds are parked in a yield vault). Liquidity can be fully utilized either deliberately (attacker borrows the residual) or even organically during market stress, which also blocks settlement. No privileged role, no timing race against an honest call, and no economic prerequisite beyond the borrow cost. The trigger is one normal market transaction against the shared vault.

### Recommendation
Make `onStopEpoch` degrade instead of reverting: withdraw `min(shortfall, vault.maxWithdraw(address(this)))` (or catch the withdrawal failure and return `true`/partial), letting IdleCDO's subsequent `transferFrom` pull whatever is actually on hand and route a real shortfall into the existing `_handleBorrowerDefault` path rather than a permanently reverting state. Alternatively, treat a covered-but-illiquid vault as a soft failure that sets a retry flag while still allowing the bookkeeping (`epochAccountingActive = false`, baselines reset) to complete, so a later `getInstantWithdrawFunds`-style pull can settle claims without replaying the full stop sequence.

### Proof of Concept
Foundry fork PoC sketch (modeled on `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, which uses a real Morpho-style vault at `vaultAddress`):

```solidity
// setup: depositAA, startEpoch; ProgrammableBorrower parks pool funds in vault
idleCDO.depositAA(amount);
cdoEpoch.startEpoch(...);

// ATTACKER: unprivileged user of the same ERC4626 vault drains liquidity.
// For a Morpho-style vault this is a market borrow that leaves ~0 liquid assets.
// convertToAssets(programmableBorrower shares) is unchanged (claims on lent assets).
uint256 liquid = underlying.balanceOf(address(morphoMarket));
vm.prank(attacker);
morphoMarket.borrow(liquid, ...);   // vault.maxWithdraw(pb) -> ~0

// advance past epochEndDate; manager tries to settle
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);

// repeat: every subsequent stopEpoch reverts while attacker keeps utilization = 100%
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);

// pending withdraw requests stay unclaimable; LP funds frozen until attacker repays
assertEq(strategy.pendingWithdraws() /* unchanged */, pendingBefore);
assertTrue(cdoEpoch.isEpochRunning());
```

Key assertion: `vault.convertToAssets(pbShares) >= shortfall` (early-return not taken) while `vault.maxWithdraw(address(programmableBorrower)) == 0`, so the revert is guaranteed purely by liquidity state the attacker controls.
