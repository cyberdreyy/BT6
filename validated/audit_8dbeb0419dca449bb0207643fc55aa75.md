### Title
Mid-epoch depositor can immediately request withdrawal and lock a full epoch's interest, diluting existing stakers — (`contracts/IdleCDOEpochVariant.sol`)

### Summary
The external bug is "new positions earn the same reward distribution as old positions". The direct analog exists between `depositDuringEpoch` (which correctly prices a mid-epoch deposit by minting discounted shares that only capture *prorated* interest) and `requestWithdraw` / `_calcInterestWithdrawRequest` (which computes the interest owed on a withdrawal receipt as a pro-rata share of the **entire epoch's** tranche interest, with no notion of when the underlying position was created). A KYC'd lender can deposit near the end of an epoch via `depositDuringEpoch`, immediately call `requestWithdraw`, and receive a receipt paying full-epoch interest on their principal — interest that was funded by the borrower only for the whole epoch and was priced into existing holders' shares.

### Finding Description
`depositDuringEpoch` mints shares so the depositor only earns interest for `remaining + buffer` over `epochDuration + buffer` (i.e. only the time actually in the pool):

```solidity
uint256 interest = _calcInterest(_amount) *
  (remaining + buffer) /
  (epochDuration + buffer);
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
``` [1](#0-0) 

No deposit timestamp is stored. In `requestWithdraw`, the receipt interest is computed via `_calcInterestWithdrawRequest`, which distributes the *whole epoch's* tranche interest pro-rata over tranche NAV:

```solidity
uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
uint256 _trancheBal = _lastSavedNAV(_tranche);
_interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
``` [2](#0-1) 

`_amount` here is the requester's principal (`_trancheToUnderlyings` of their tranche balance), and the result is fixed into the withdrawal receipt at request time (`_underlyings = principal + interest - totalFees` at line 776). Since the mid-epoch depositor's principal is added to `lastNAVAA`/`lastNAVBB` (confirmed by the test asserting `lastNAVBB + depositAmount`), their receipt is entitled to roughly `amount * totTrancheInterest / trancheNAV` — the same full-epoch interest share as a holder who was in the pool since `startEpoch`, even though they entered one block before `epochEndDate`.

The gated pieces that would normally block this do not:
- `depositDuringEpoch` is enabled when `isDepositDuringEpochDisabled == false`, AYS is off, borrower is not programmable, and `block.timestamp < epochEndDate` — all consistent with depositing seconds before epoch end (line 667 only requires `block.timestamp < epochEndDate`). [3](#0-2) 
- `requestWithdraw` only requires `allowAA/BBWithdrawRequest` and `isWalletAllowed`; both are (re)enabled after `stopEpoch` and during the running epoch, and there is no minimum-holding-period check. [4](#0-3) 
- `_skimDonatedAssets` only sweeps raw token donations, not share-based dilution. [5](#0-4) 

Because pending withdrawals are paid out of the epoch's gross interest before remaining holders' NAV is updated (pending receipts share of `_grossInterest` is carved out in `_stopEpoch`, lines 452–463), the excess interest granted to the attacker is directly subtracted from what long-term holders receive — identical mechanics to the MlumStaking dilution: a 1-second-old position claiming the same reward-per-unit as a year-old one.

### Impact Explanation
Direct theft of yield from honest tranche holders. The attacker extracts approximately `amount * trancheInterestShare * elapsedFraction` of unearned epoch interest (the difference between full-epoch interest on their principal and the prorated interest they actually funded). With a large deposit relative to tranche TVL, this siphons a corresponding fraction of the epoch's interest — e.g. depositing an amount equal to 50% of tranche NAV in the last block of the epoch grants the attacker ~1/3 of that tranche's epoch interest while contributing essentially none of it. The attack is repeatable each epoch and scales linearly with deposited capital.

### Likelihood Explanation
Requires: KYC'd wallet (`isWalletAllowed`), `isDepositDuringEpochDisabled == false`, AYS inactive, non-programmable borrower, and a running epoch — all normal operating conditions for pools that enable mid-epoch deposits. The action is a two-transaction sequence (`depositDuringEpoch` → `requestWithdraw`) executable by any allowed lender in a single block near `epochEndDate`, with no privileged role needed. No capital at risk beyond gas, since the receipt is redeemable for principal + interest after settlement.

### Recommendation
Track a per-position (or per-account) "interest-eligible" basis. Two options:
1. Store the minted shares from `depositDuringEpoch` in a separate pending bucket (analogous to the report's "queued shares"): tranche tokens that can transfer/vote but whose withdrawal requests use `interest = 0` for the current epoch — i.e. `_calcInterestWithdrawRequest` should return only the prorated `trancheInterest` already credited at mint time, not a pro-rata share of `totTrancheInterest`.
2. Alternatively, record `depositTimestamp` (or epoch number) per position and scale `_interest` in `_calcInterestWithdrawRequest` by `min(elapsedHeld, epochDuration) / epochDuration`.

A simpler mitigation is to revert `requestWithdraw` for shares minted via `depositDuringEpoch` within the same epoch (force them to wait until `epochEndDate` passes and a new epoch starts).

### Proof of Concept
Foundry test sketch (drop into `test/foundry/IdleCreditVault.t.sol` style setup):

```solidity
function testMidEpochDepositWithdrawDilution() external {
    uint256 amountAA = 10000 * ONE_SCALE;
    idleCDO.depositAA(amountAA);
    idleCDO.depositBB(amountAA);

    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    _startEpochAndCheckPrices(0);

    // warp to near epoch end
    vm.warp(cdoEpoch.epochEndDate() - 1 days);
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    // attacker deposits ~same size as existing tranche, 1 day before end
    address bob = makeAddr('bob');
    uint256 dep = 20000 * ONE_SCALE;
    deal(defaultUnderlying, bob, dep);
    vm.startPrank(bob);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), dep);
    cdoEpoch.depositDuringEpoch(dep, address(BBtranche));
    uint256 rcpt = cdoEpoch.requestWithdraw(0, address(BBtranche)); // all shares
    vm.stopPrank();

    // Bob's receipt carries ~full-epoch BB interest on `dep`,
    // while he funded only ~1/(epochDuration+buffer) of it
    uint256 fairInterest = _calcInterest(dep) * (1 days + cdoEpoch.bufferPeriod())
        / (cdoEpoch.epochDuration() + cdoEpoch.bufferPeriod());
    // rcpt - dep >> fair share => stolen yield from existing BB holders
    assertGt(rcpt - dep, fairInterest);
}
```

Expected outcome: `requestWithdraw` returns `principal + full-epoch-proportional interest`, exceeding the prorated `trancheInterest` the deposit actually contributed to `expectedEpochInterest`; the difference is paid out of the epoch's gross interest owed to long-term holders.
