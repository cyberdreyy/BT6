### Title
Missing sender allowlist enforcement in gateway legacy trigger request path allows unauthorized workflow trigger submission - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` verifies only that the incoming message has a well-formed, self-consistent ECDSA signature (via `msg.Validate()` in `Message.Validate()` and `ExtractSigner()`), but never checks that the recovered `msg.Body.Sender` belongs to any allowlist, subscription, or workflow-owner registry before broadcasting the request to every DON member via `don.SendToNode`. Any party who can generate an ECDSA keypair can sign and submit a structurally valid `web_api_trigger` request that will be forwarded to the entire DON as if it came from an authorized/subscribed sender.

### Finding Description
The gateway's `ProcessRequest` (`core/services/gateway/gateway.go:250-269`) decodes the legacy request, calls `msg.Validate()` (`core/services/gateway/api/message.go:54-88`), which only checks field lengths and recovers `Body.Sender` from the ECDSA signature via `ExtractSigner()` — it performs no lookup against any registered/allowlisted sender set. It then dispatches to `h.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341`).

Inside `HandleLegacyUserMessage`, the checks performed are: payload decodability, `payload.Timestamp != 0`, message staleness (`MaxAllowedMessageAgeSec`), and `msg.Body.Method == MethodWebAPITrigger`. Immediately preceding the method check is the explicit marker of the gap: [1](#0-0) 
No code path in this function inspects `msg.Body.Sender` against `h.donConfig`, a workflow-owner registry, or any capability/subscription allowlist. After `common.ValidatedRequestFromMessage` converts the message to a JSON-RPC request, the handler unconditionally fans it out: [2](#0-1) 

The existing test suite for this handler explicitly documents this as an unresolved gap rather than a covered/mitigated case: [3](#0-2) 

Because signature validation only proves "some keypair signed this," and any attacker can generate a keypair for free, the check is insufficient to establish that the sender is a subscribed workflow owner or otherwise authorized to trigger DON-side workflow execution.

### Impact Explanation
This allows an unprivileged, unauthenticated attacker (anyone able to reach the gateway's `ProcessRequest`/legacy JSON-RPC endpoint) to have arbitrary trigger payloads delivered to and processed by every node in the DON, impersonating a legitimate workflow owner/subscriber. Depending on what the DON-side `web_api_trigger` capability does with an unauthorized trigger (e.g., initiating workflow executions, consuming compute/action capability resources, or invoking further capabilities), this can result in unauthorized workflow execution, resource exhaustion/DoS on DON nodes, and cross-tenant confusion where a node treats attacker-supplied data as coming from a trusted, subscribed owner. This maps to a "request impersonation / authorization bypass leading to unauthorized job/workflow trigger" bounty impact class.

### Likelihood Explanation
Trivial to exploit and fully repeatable: an attacker only needs to generate an ECDSA keypair (`crypto.GenerateKey()`), construct a `TriggerRequestPayload` with a valid non-zero, non-stale `Timestamp`, sign it per `Message.Sign`, and submit it through the gateway's legacy JSON-RPC path with `Method = MethodWebAPITrigger`. No credentials, registration, or prior interaction with the DON is required — all downstream checks (`Validate()`, timestamp, method match) are satisfiable by any attacker.

### Recommendation
Before forwarding to `don.SendToNode`, `HandleLegacyUserMessage` (or a wrapper called from it) must resolve `msg.Body.Sender`/the trigger's declared owner against an authoritative allowlist/subscription registry (e.g., the DON's configured workflow owners or capability subscribers) and reject/return `api.UnauthorizedError`-style responses for unregistered senders, in addition to implementing per-sender rate-limiting as the TODO comment indicates.

### Proof of Concept
Go handler-level test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` with a `donConfig` and a mocked `handlers.DON` (`mocks.DON`) that records `SendToNode` calls.
2. Generate a fresh, never-registered ECDSA key via `crypto.GenerateKey()` (not one of the `nodes[]` fixtures/no association with any workflow owner config).
3. Build a valid `TriggerRequestPayload` (non-zero, fresh `Timestamp`, valid trigger IDs) and sign it via `msg.Sign(unregisteredKey)`, producing a message that passes `msg.Validate()`.
4. Call `handler.HandleLegacyUserMessage(ctx, msg, callback)`.
5. Assert: `don.SendToNode` mock was invoked once per `donConfig.Members` entry (i.e., `len(donConfig.Members)` times) with the attacker's forged request, and that `callback` received no rejection/authorization error — demonstrating that an unregistered sender's trigger request is fully propagated to the DON.
