### Title
Cache key for outbound HTTP action responses omits `WorkflowID`, allowing cross-workflow response confusion when scoped by `WorkflowOwner` alone - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The Lend `borrowWithInterest()` bug used the wrong scoping parameter (same-chain LToken index) for a cross-chain calculation, causing state to be miscomputed across trust/execution boundaries that should have remained isolated. The Chainlink HTTP Handlers V2 gateway `responseCache` exhibits the same root-cause pattern: the documented isolation boundary is per-*workflow*, but the actual cache-key computation `OutboundHTTPRequest.Hash()` does not incorporate `WorkflowID` at all — only `WorkflowOwner` (plus method/URL/headers/body) is mixed into the key.

### Finding Description
The `responseCache` type comment explicitly states the cache is "keyed by a hash of the request (method, URL, headers, body, workflowOwner)" [1](#0-0) , and `Fetch`/`Set` both use `req.Hash()` as the sole cache key [2](#0-1) .

However, the module's own README documents the intended security/isolation property as being scoped by **workflow ID**: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [3](#0-2) .

The test suite proves the actual behavior contradicts this documented guarantee: a test explicitly asserts "having different workflowID results in same Hash" — i.e., two requests that are otherwise identical but belong to different `WorkflowID`s produce the **same** cache hash [4](#0-3) , while only `WorkflowOwner` differences change the hash [5](#0-4) .

This cache is populated and read from `makeOutgoingRequest`/`createHTTPRequestCallback`, which is reachable from `HandleNodeMessage` processing HTTP action responses (`gateway_common.OutboundHTTPRequest`) originating from workflow nodes in the DON that unmarshal directly from node-supplied JSON-RPC results [6](#0-5) .

Because `WorkflowOwner` is a single identity (an EOA/org) that can own **multiple distinct workflows** (`WorkflowID`s), any two workflows owned by the same `WorkflowOwner` that happen to issue an HTTP action request with identical method/URL/headers/body will collide in the cache and share a cached response — even though they are different workflows and the README states isolation should be per-workflow. This is precisely analogous to the Lend bug: the code implements isolation/accrual using the wrong scoping identifier (owner instead of workflow — analogous to same-chain LToken index instead of cross-chain borrow index), silently breaking a cross-boundary isolation guarantee that is documented and relied upon elsewhere in the system.

### Impact Explanation
If two different workflows (same owner, e.g. rotated/duplicate deployments, staging vs prod workflow of the same owner, or multiple concurrently registered workflows) make outbound HTTP requests with identical request parameters (URL/method/headers/body) but expect different responses (e.g., due to different external endpoint routing that is not reflected in the request itself, or timing-sensitive data), one workflow could receive a stale/foreign cached response intended for a different workflow's request. This is a cross-workflow response confusion bug within the gateway's own trust boundary (impacts data returned to workflow executions, which can feed into consensus-driven on-chain actions), not a purely cosmetic issue, though its practical severity depends on how often identical requests are issued by distinct workflows under the same owner and how significant a stale-but-plausible HTTP response is to the affected workflow logic.

### Likelihood Explanation
Reachable from a legitimate/unprivileged DON member response path (`HandleNodeMessage`), not requiring any malicious actor — a normal operating condition (two workflows under the same owner polling the same fixed endpoint) can trigger the collision. It requires the `CacheSettings.Store`/`MaxAgeMs` to be enabled by the workflow author and identical request signatures across workflows, which somewhat narrows likelihood, but it does not require any special privilege or attack — it is a straightforward violation of the documented workflow-level isolation guarantee.

### Recommendation
Include `WorkflowID` (not just `WorkflowOwner`) in the `OutboundHTTPRequest.Hash()` computation used as the `responseCache` key, matching the documented "workflow ID and request hash" cache-key design, and update/verify the existing test (`response_cache_test.go` "having different workflowID results in same Hash") to instead assert isolation by `WorkflowID`.

### Proof of Concept
Not executed (static analysis only, per report rules). The `Hash()` implementation itself (defining exactly which fields are combined) lives in the `gateway_common`/`chainlink-common` package (`gateway.OutboundHTTPRequest.Hash`) which was not found within the size-limited index for this repo — I was unable to directly view its source to confirm the exact hashing implementation and cannot rule out that `WorkflowID` is intentionally excluded for some other reason (e.g., de-duplication across workflow "versions" of the same ID sharing content). This is inferred from the test assertions and README documentation and should be verified against the actual `Hash()` source before treating as confirmed; a Devin session with full repo access could confirm the source and validate exploitability with a concrete reproduction.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)

			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
