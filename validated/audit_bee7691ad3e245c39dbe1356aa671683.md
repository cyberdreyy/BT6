### Title
Cross-workflow HTTP action response cache poisoning due to `WorkflowID` omitted from cache key - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's HTTP Handlers V2 response cache for outbound HTTP actions caches responses using a key derived from `OutboundHTTPRequest.Hash()`. This hash intentionally includes `WorkflowOwner` but explicitly excludes `WorkflowID`, meaning two distinct workflows belonging to the same owner that issue an HTTP action with the same method/URL/headers/body will collide on the same cache entry and receive each other's cached (and potentially stale/mismatched) response, contradicting the documented "workflow isolation" guarantee.

### Finding Description
The `responseCache` type documents itself as keying cache entries "by a hash of the request (method, URL, headers, body, workflowOwner)" [1](#0-0) , and the `Fetch`/`Set` paths both key exclusively off `req.Hash()` [2](#0-1) [3](#0-2) .

The module's own README states that caching is meant to be workflow-scoped: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [4](#0-3) .

However, the actual unit tests for `Hash()` confirm the opposite behavior: differing `WorkflowID` values produce the *same* hash, while differing `WorkflowOwner` values produce *different* hashes: [5](#0-4) [6](#0-5) 

The gateway processes outbound HTTP action requests originating from workflow (capability) nodes acting on behalf of arbitrary CRE workflows/users. In `makeOutgoingRequest`, the entire `req` (unmarshalled directly from a node message) is passed straight to `responseCache.Fetch`/`Set` without any workflow-ID-aware key derivation [7](#0-6) . Because `WorkflowID` is not part of the cache key, any two different workflows owned by the same `WorkflowOwner` (or under any caller-controlled/omitted `WorkflowOwner` value) that issue a request with identical method/URL/headers/body will read and write the same cache slot, regardless of `WorkflowID`.

### Impact Explanation
This breaks the intended per-workflow cache isolation. A workflow's outbound HTTP action can receive a cached response that was actually fetched for, and intended only for, a different workflow under the same owner (or share cache pollution/DoS potential if attacker-controlled workflows deliberately populate the shared cache key with attacker data before the victim's own request runs, similarly to the classic stale/incorrect-data-trust bug class highlighted in the source report). Depending on how the returned HTTP body is consumed downstream (e.g., feeding it into further workflow logic, on-chain reports, or decision-making), this constitutes response confusion across workflows and can leak or substitute data between execution contexts that are supposed to be isolated.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires two workflows under the same `WorkflowOwner` to issue an HTTP action with identical `Method`+`URL`+`Headers`+`Body`+`CacheSettings.Store=true` (and one of them sets `CacheSettings.MaxAgeMs>0`). This is plausible in shared/templated workflow deployments or where multiple workflow instances hit the same well-known external endpoint (e.g., shared price/data provider) with identical parameters — a realistic scenario for CRE workflows built from common templates.

### Recommendation
Include `WorkflowID` (in addition to `WorkflowOwner`) in the `OutboundHTTPRequest.Hash()` computation so that cache keys are unique per workflow, matching the documented behavior in the README ("Cache Key: Generated from workflow ID and request hash"). Add/adjust a unit test asserting that differing `WorkflowID` values produce different hashes, and audit any other consumers relying on `Hash()` for isolation guarantees.

### Proof of Concept
1. Workflow A (WorkflowID = "workflow-123", WorkflowOwner = "owner-1") issues an HTTP action: `GET https://example.com/data` with `CacheSettings{Store: true, MaxAgeMs: 60000}`. The gateway fetches fresh data and caches it under `req.Hash()` (which does not incorporate `WorkflowID`) via `Set`/`Fetch` in `response_cache.go` [8](#0-7) .
2. Workflow B (WorkflowID = "workflow-456", same WorkflowOwner = "owner-1") issues the identical `GET https://example.com/data` request shortly after, also with `MaxAgeMs>0`.
3. Because `Hash()` ignores `WorkflowID` (confirmed by `TestRequestHash` — "having different workflowID results in same Hash" [5](#0-4) ), Workflow B's request hits the cache entry populated by Workflow A and receives Workflow A's cached response instead of making its own fresh request — violating the documented per-workflow cache isolation.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
