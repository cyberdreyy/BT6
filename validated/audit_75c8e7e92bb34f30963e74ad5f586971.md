### Title
Miner-controlled `burn_height`/`chain_length` overflow crashes signer on unchecked `insert_block` before `check_static_valid_block` - (File: stacks-signer/src/v0/signer.rs)

### Summary
`handle_block_proposal` calls `self.signer_db.insert_block(&block_info)` at the end of the non-rejected path *before* `check_static_valid_block` is ever invoked on this `BlockInfo`, unlike the later `handle_block_validate_ok` path which explicitly checks `block_info.check_static_valid_block()` before storing. `insert_block` binds `reward_cycle`, `burn_block_height`, and `chain_length` through `u64_to_sql`, which fails for values `>= i64::MAX`. Any failure from `insert_block` (a `DBError`) is routed to `handle_insert_block_error`, which calls `panic!`. [1](#0-0) [2](#0-1) 

### Finding Description
A `BlockProposal` message carries miner-controlled fields — most notably `burn_height` (part of the message itself, not covered by any header signature check at this point in the flow) and `block.header.chain_length` — that are stored via `insert_block`: [3](#0-2) 

This call binds `u64_to_sql(block_info.reward_cycle)`, `u64_to_sql(block_info.burn_block_height)`, and `u64_to_sql(block_info.block.header.chain_length)`. The codebase already recognizes that these three fields must be bounded below `i64::MAX` before being written to SQLite, and encodes that invariant in `check_static_valid_block`: [4](#0-3) 

That check is enforced on the `handle_block_validate_ok` path: [5](#0-4) 

But `handle_block_proposal` — which runs first, immediately on proposal receipt, and stores every non-provably-invalid proposal — never calls `check_static_valid_block` before its own `insert_block` call: [6](#0-5) 

If `u64_to_sql` returns an error (value out of `i64` range), `insert_block` returns `Err(DBError::...)`, which is routed straight into `handle_insert_block_error`: [2](#0-1) 

`handle_insert_block_error` unconditionally `panic!`s the signer process. This is structurally the same bug class as the TFLite advisory: code assumes a value is always within an expected numeric range (sub-`i64::MAX`) and hard-aborts the process when that assumption is violated by attacker-supplied input, instead of gracefully rejecting the malformed input.

### Impact Explanation
A single miner (the only entity that produces `BlockProposal` messages, per the "one-slot miner (plus gossip)" threat model) can craft a proposal with `burn_height` or `block.header.chain_length` set near `u64::MAX` and broadcast it to the signer set. Every signer that reaches this code path with `check_block_against_state` returning `None` (i.e., the proposal is "not provably invalid" against basic consensus checks — nothing here validates the magnitude of `chain_length`/`burn_height` against real chain state before this point) will panic and crash. Because this affects every signer in the set simultaneously (all subscribe to the same StackerDB proposal), it is a liveness wedge that meets the "High — a signer wedged into never signing valid blocks" bar without needing a majority of signers or any signer key. This matches the CVSS profile of the analog: low complexity, no privileges beyond message delivery, availability impact only.

### Likelihood Explanation
Likelihood is high for the trigger condition (any single miner or, if slot access isn't enforced before this handler, a StackerDB gossip actor able to write to the miner's proposal slot) but is gated on whether `check_block_against_state`'s constituent checks (`check_proposal`, static consensus checks, `ProblematicTransactions`) reject an obviously nonsensical `chain_length`/`burn_height` earlier. I was not able to fully trace every branch of `check_block_against_state` / v1 `SortitionsView::check_proposal` / v2 `GlobalStateView::check_proposal` to confirm none of them independently bounds `chain_length` or `burn_height` before the `insert_block` call — this is a limitation of what the index surfaced. If those checks already reject implausible heights, the practical likelihood drops; if not, exploitation is straightforward with a single crafted proposal.

### Recommendation
Call `block_info.check_static_valid_block()` in `handle_block_proposal` before the first `insert_block` call (mirroring the guard already present in `handle_block_validate_ok`), and reject/log-and-drop rather than store or panic when it fails. More broadly, `handle_insert_block_error`'s `panic!` should not be reachable via genuinely miner-influenced numeric fields; either validate all such fields before every `insert_block` call site, or make `insert_block` itself defensively clamp/reject oversized values without propagating a panic-inducing error.

### Proof of Concept
1. As the tenure's miner, construct a `BlockProposal` with `burn_height = u64::MAX - 1` (or `block.header.chain_length = u64::MAX - 1`), otherwise consistent enough with current sortition state to not be caught by `check_block_against_state`'s existing checks (protocol version, consensus hash, no problematic txs).
2. Broadcast it as `SignerMessage::BlockProposal` over the miner's StackerDB slot to the signer set.
3. Each signer's `handle_block_proposal` reaches the `insert_block` call at signer.rs:1717-1719 before any `check_static_valid_block` gate.
4. `u64_to_sql(block_info.burn_block_height)` (or the `chain_length` equivalent) fails because the value exceeds `i64::MAX`; `insert_block` returns `Err`.
5. `handle_insert_block_error` panics, crashing every signer process that processed the proposal — a liveness wedge for the signer set until manually restarted.

    /// Perform static checks on the BlockInfo and determine if it is syntactically valid.
    /// Specifically, all integer values must be less than i64::MAX, since these values get stored
    /// in the sqlite DB via u64_to_sql()
    pub fn check_static_valid_block(&self) -> bool {
        let max_val = u64::try_from(i64::MAX).expect("infallible");
        if self.block.header.chain_length >= max_val {
            return false;
        }
        if self.burn_block_height >= max_val {
            return false;
        }
        if self.reward_cycle >= max_val {
            return false;
        }
        true
    }
