### Title
Unauthorized cross-owner secret deletion via missing owner re-stamping in Vault gateway `SecretsDelete` path - (File: `core/capabilities/vault/gw_handler.go`, `core/capabilities/vault/gateway_vault_request_processor.go`)

### Summary
The Vault gateway handler enforces the authorized request owner for `SecretsList` by forcibly overwriting the client-supplied owner field with the value returned by the allowlist/JWT authorizer, but the equivalent enforcement is missing for `SecretsDelete`. The delete path only guarantees internal uniformity of the `Owner` field across the batch of `SecretIdentifier`s, never that the batch owner equals the owner the caller was actually authorized for.

### Finding Description
`handleSecretsList` explicitly re-stamps the caller-authorized owner onto the outgoing request before calling the secrets service: [1](#0-0) 

`handleSecretsDelete`, in contrast, unmarshals the request straight from the JSON-RPC params and forwards it to the secrets service without ever substituting `authResult.AuthorizedOwner()`: [2](#0-1) 

Upstream, `GatewayVaultRequestProcessor.processDeleteSecretsRequest` runs `AuthorizeRequest` and prefixes the request ID with the authorized owner, but the "stamp" callback for delete only normalizes namespace defaults on the identifiers — it never rewrites the `Owner` field on each `SecretIdentifier`: [3](#0-2) 

Compare this with the `SecretsList` path in the same processor and with `handleSecretsList`, both of which authoritatively fix the owner from the auth result rather than trusting client input.

On the DON side, `Capability.DeleteSecrets` only validates that all identifiers in the request share the *same* owner among themselves (`validateSecretIdentifiersUniformOwners`); it does not check that owner against any authorized/workflow owner: [4](#0-3) [5](#0-4) 

This is unlike the `Execute` (`GetSecrets`) path, which explicitly rejects a request whose secret owner does not match `request.Metadata.WorkflowOwner`: [6](#0-5) 

Because `SecretsDelete` never receives this owner-vs-authorized-owner cross-check, a caller who is authorized (allowlisted/JWT-verified) for owner `A` can submit a `DeleteSecretsRequest` whose `Ids[].Owner` field is set to owner `B`, and — as long as the batch is internally uniform — the request will pass all visible validation/authorization gates and reach `secretsService.DeleteSecrets` with owner `B`'s identifiers.

### Impact Explanation
If this path is exploitable, an unprivileged/authenticated party could delete secrets belonging to a different user/owner (`B`) despite only being authorized for their own owner (`A`). Deleting another owner's vault secrets used by their workflows could break workflow execution or destroy security-critical secrets — a request-impersonation / unauthorized-fund(-resource)-movement analog directly mirroring the external report's root cause (a conditional/branch that fails to account for the "should not proceed for this actor" case, allowing consequences to land on the wrong, uninvolved party).

### Likelihood Explanation
Likelihood is Low-Medium: exploitation requires the attacker to already hold a valid, allowlisted/JWT-authorized vault request context for *some* owner, and then craft a delete request whose secret identifiers reference a different owner value. This is a low-effort, purely client-side parameter change since the gateway/DON never overwrites or cross-checks the owner field for deletes, unlike for list/get. I was not able to fully inspect `core/capabilities/vault/validator.go` (`ValidateDeleteSecretsRequest`) in this pass to conclusively rule out an owner-vs-authorized-owner check happening there; this should be confirmed before treating the finding as definitive.

### Recommendation
Mirror the `SecretsList` enforcement pattern for `SecretsDelete`: after authorization, overwrite/validate every `SecretIdentifier.Owner` in the delete request against `authResult.AuthorizedOwner()` (either in `authorizeAndStamp`'s stamp callback in `gateway_vault_request_processor.go`, or in `handleSecretsDelete`/`Capability.DeleteSecrets`), rejecting the request if any identifier's owner does not match the authorized owner — consistent with the check already performed in `Capability.Execute` for `GetSecrets`.

### Proof of Concept
1. Obtain gateway/DON authorization as owner `A` (e.g., via a legitimately allowlisted workflow request) so `AuthorizeRequest` returns `AuthorizedOwner() == "A"`.
2. Submit a `vaulttypes.MethodSecretsDelete` JSON-RPC request whose `DeleteSecretsRequest.Ids` all carry `Owner: "B"` (uniform, so `validateSecretIdentifiersUniformOwners` passes).
3. Trace the call: `GatewayHandler.HandleGatewayMessage` → `requestProcessor.ProcessRequest` → `processDeleteSecretsRequest` → `authorizeAndStamp` (only ID prefix changes, `Ids[].Owner` untouched) → `handleSecretsDelete` (uses `r` as unmarshaled, no owner override) → `secretsService.DeleteSecrets(ctx, r)` → `Capability.DeleteSecrets` → `ValidateDeleteSecretsRequest` + `validateSecretIdentifiersUniformOwners` (no cross-owner check) → secrets for owner `B` get deleted despite the request only being authorized for owner `A`.

func (h *GatewayHandler) handleSecretsDelete(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.DeleteSecretsRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized delete secrets request", "request", r.String())
	resp, err := h.secretsService.DeleteSecrets(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to delete secrets: %w", err))
	}

	resultBytes, err := resp.ToJSONRPCResult()
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&resultBytes),
	}
}

func (p *GatewayVaultRequestProcessor) processDeleteSecretsRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
) (*AuthorizedGatewayVaultRequest, error) {
	if req.Params == nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: errors.New("request params must not be nil")}
	}

	var deleteReq vaultcommon.DeleteSecretsRequest
	if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
	}
	if p.stripOwnerPrefixForAuth {
		deleteReq.RequestId = req.ID
		if err := marshalVaultParams(req, &deleteReq); err != nil {
			return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
		}
	} else {
		deleteReq.RequestId = coalesceRequestID(deleteReq.RequestId, req.ID)
	}

	if err := p.validator.ValidateDeleteSecretsRequest(ctx, &deleteReq); err != nil {
		return nil, p.validationError(req, err)
	}

	return p.authorizeAndStamp(ctx, req, func(prefixedRequestID string) error {
		deleteReq.RequestId = prefixedRequestID
		vaultutils.ApplySecretIdentifierNamespaceDefaults(deleteReq.Ids)
		return marshalVaultParams(req, &deleteReq)
	})
}

func (s *Capability) DeleteSecrets(ctx context.Context, request *vaultcommon.DeleteSecretsRequest) (*vaulttypes.Response, error) {
	s.lggr.Debugw("received delete secrets request", "requestID", request.RequestId, "request", request.String())
	err := s.ValidateDeleteSecretsRequest(ctx, request)
	if err != nil {
		s.lggr.Debugw("failed validation checks", "requestID", request.RequestId, "request", request.String(), "err", err)
		return nil, err
	}
	if err := validateSecretIdentifiersUniformOwners(request.Ids); err != nil {
		s.lggr.Debugw("failed uniform owner checks", "requestID", request.RequestId, "request", request.String(), "err", err)
		return nil, err
	}
	return s.handleRequest(ctx, request.RequestId, request)
}

func validateSecretIdentifiersUniformOwners(ids []*vaultcommon.SecretIdentifier) error {
	var owner string
	for idx, id := range ids {
		if id == nil {
			continue
		}
		if owner == "" {
			owner = id.Owner
			continue
		}
		if vaultutils.NormalizeOwner(id.Owner) != vaultutils.NormalizeOwner(owner) {
			return fmt.Errorf("secret identifier owner at index %d %q does not match batch owner %q", idx, id.Owner, owner)
		}
	}
	return nil
}
