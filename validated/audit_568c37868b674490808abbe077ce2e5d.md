### Title
Unconditional `cooldownDuration` check permanently freezes withdrawals when sUSDe cooldown is disabled - (File: contracts/IdleCDOEthenaVariant.sol)

### Summary
`IdleCDOEthenaVariant._withdraw` begins with `require(IStakedUSDeV2(strategyToken).cooldownDuration() != 0, '9')` before any other logic. The commented-out code directly above shows the intended behavior: when the external staking contract has no cooldown configured, the normal `IdleCDO._withdraw` path should be used. Because the check is applied unconditionally to every withdrawal instead of only gating the cooldown-request path, all withdrawals revert whenever sUSDe's `cooldownDuration` is `0`, even though funds are fully liquid and redeemable through the standard path.

### Finding Description
In `contracts/IdleCDOEthenaVariant.sol:42-47`:

```solidity
function _withdraw(uint256 _amount, address _tranche) override internal nonReentrant returns (uint256 toRedeem) {
    // if no cooldown is set we can use the normal path
    // if (IStakedUSDeV2(strategyToken).cooldownDuration() == 0) {
    //   return super._withdraw(_amount, _tranche);
    // }
    require(IStakedUSDeV2(strategyToken).cooldownDuration() != 0, '9');
```

Mirroring the reported bug (an unconditional `blockLock` check that should only apply to the sub-path that actually needs it), the cooldown guard is hoisted to the top of the function when it only makes sense for the cooldown-request flow implemented below. When `StakedUSDeV2.cooldownDuration()` returns `0` (no cooldown required — instant unstaking enabled), the contract:

- still creates cooldown-request clones that cannot ever be claimed (there is nothing to cool down),
- and worse, reverts outright on `require(... != 0, '9')` for every `withdrawAA`/`withdrawBB` call.

No user action can bypass this: both tranche withdrawals funnel through `_withdraw`, and there is no alternative exit path in the variant. Deposits continue to work, so new funds can still be locked in.

### Impact Explanation
Temporary-to-permanent freezing of all user funds (principal + accrued yield) in the vault for as long as the underlying sUSDe contract has `cooldownDuration == 0`. The loss equals 100% of vault NAV during that window. If Ethena were to ever disable the cooldown (a config change outside Idle's control and outside the attacker's control), every withdrawal bricks. Conversely, the intended design (per the commented code) is that `cooldownDuration == 0` is a supported, normal mode — meaning the contract is defective in a state its own authors anticipated.

### Likelihood Explanation
Depends on Ethena's staking configuration, not on attacker action. `cooldownDuration` is an admin-set value on `StakedUSDeV2`; it has been `0` and non-zero at different times historically, and Ethena governance can change it. An unprivileged attacker cannot force the condition, so likelihood is conditional rather than actively exploitable — but the failure mode is total and the invariant broken (users can always redeem tranche tokens for underlying) is core to the CDO.

### Recommendation
Restore the commented-out early return so the normal withdrawal path is used when no cooldown is required:

```solidity
if (IStakedUSDeV2(strategyToken).cooldownDuration() == 0) {
    return super._withdraw(_amount, _tranche);
}
```

and remove the unconditional `require`. The cooldown-request machinery should only run when a cooldown actually exists.

### Proof of Concept
Fork mainnet with sUSDe configured (or mock `StakedUSDeV2.cooldownDuration()` returning `0`):

```solidity
function test_WithdrawFrozenWhenCooldownZero() public {
    // Arrange: cooldown disabled on sUSDe
    vm.mockCall(
        strategyToken,
        abi.encodeWithSelector(IStakedUSDeV2.cooldownDuration.selector),
        abi.encode(uint256(0))
    );

    // Deposit works
    uint256 minted = cdo.depositAA(1000e18);

    // Any withdraw reverts with '9' even though liquidity is available
    vm.expectRevert(bytes("9"));
    cdo.withdrawAA(minted);
}
```

A real PoC requires a Foundry fork of mainnet with the deployed `IdleCDOEthenaVariant` and `StakedUSDeV2` addresses; mocking `cooldownDuration` to `0` demonstrates the unconditional revert.

Note: I was unable to inspect the full body of `IdleCDOCreditVault.sol` (index returned match counts only, not contents), so I cannot rule out a stronger analog in the credit-vault withdraw-request flow. The above finding stands on the Ethena variant's own code.
