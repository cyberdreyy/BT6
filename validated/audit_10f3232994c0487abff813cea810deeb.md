### Title
Withdrawals from banks backed by compliance-restricted Token-2022 mints (e.g. transfer hooks enforcing a minimum sender balance) can unexpectedly revert, durably freezing legitimate withdrawals — (File: `programs/marginfi/src/state/bank.rs`, `programs/marginfi/src/instructions/marginfi_account/withdraw.rs`)

### Summary
Marginfi generically supports Token-2022 mints with arbitrary transfer-hook programs as bank collateral/liability assets. `withdraw_spl_transfer` and `deposit_spl_transfer` simply forward the transfer (with any extra-account-metas resolved generically) to the token program without any protocol-side accounting for compliance rules a hook may enforce on the *source* account (the bank's `liquidity_vault`). This is the exact analog of the Ondo/BUIDL `minUSTokens` finding: an external token can enforce "the sender must retain at least X tokens after any transfer," and the integrating protocol does not pre-check or reserve for this, so a legitimate, fully-collateralized withdrawal can revert unexpectedly once the vault balance would drop below the externally-enforced floor.

### Finding Description
`Bank::withdraw_spl_transfer` performs the on-chain SPL transfer from the `liquidity_vault` to the destination using `transfer_checked`/`invoke_transfer_checked`, delegating entirely to the token program (and, for Token-2022, to any active transfer hook) for the transfer's validity: [1](#0-0) 

Marginfi explicitly supports Token-2022 mints with a `TransferHook` extension as first-class bank assets — this is exercised generically (not restricted like the emissions path) through deposit/withdraw/borrow/repay/liquidation, resolving the hook's extra account metas dynamically: [2](#0-1) [3](#0-2) 

By contrast, marginfi is careful to *reject* deposit-like flows (emissions funding) if a fee/hook could alter the transferred amount, but no equivalent check or accounting exists for a hook that instead rejects the transfer entirely based on a minimum-balance-after-transfer rule enforced on the *sender* (the vault): [4](#0-3) 

The core withdraw instruction computes the withdrawal amount purely from marginfi's internal share accounting and then blindly calls the SPL transfer, with no allowance for a token-level "vault must retain minimum balance ≥ N" compliance rule (analogous to BUIDL's `getMinUSTokens()` check applied to the sender in `ServiceRegulated.sol`): [5](#0-4) 

If a bank's underlying mint is a compliance-gated RWA-style Token-2022 asset whose transfer hook enforces a minimum balance requirement on the sending account (the bank's `liquidity_vault`, which is exactly the kind of address such compliance tokens apply rules to, since it is itself a holder/whitelisted account), any withdrawal that would push the vault below that floor reverts — even though the requesting user's share of the vault is fully solvent and otherwise redeemable. Because the check is enforced by the external token program on every transfer and marginfi has no path to account for or reserve against it, this is not a one-off revert: it becomes a durable inability to withdraw the "last" tranche of liquidity for as long as the vault balance sits within the enforced buffer, with no fallback recorded/handled on the marginfi side (unlike the transfer-fee case, which is exactly modeled and accounted for via `has_transfer_fee`/pre-fee calculations).

### Impact Explanation
This is a durable freeze/inconsistency with financial effect: legitimate depositors of a bank backed by a compliance-enforcing Token-2022 mint can be permanently unable to withdraw funds they are otherwise entitled to and fully collateralized for, whenever the vault balance nears the externally mandated minimum. Since the freeze condition is driven by third-party (mint-admin-controlled) compliance parameters that can change after the bank is created and integrated, users' redeemable value can become stuck with no recovery path in the current code (no reserve/buffer accounting, no alternate redemption route). This mirrors the acknowledged BUIDL integration risk but is broader in marginfi because arbitrary hook programs — not just the specific BUIDL contract — are supported generically for bank assets.

### Likelihood Explanation
Likelihood depends on marginfi (or a permissionless bank-adder) onboarding a Token-2022 mint whose transfer hook enforces a minimum-balance rule on the vault, and on the vault balance later approaching that minimum (e.g., after other depositors have withdrawn or as the compliance minimum is raised by the mint authority, exactly as BlackRock/Ondo's postmortem describes for `minUSTokens`). Given marginfi actively markets/tests broad Token-2022 extension support (fees, hooks, permanent delegate, etc.) as a supported integration surface, and hook parameters are entirely outside marginfi's control, this is a realistic — not purely theoretical — integration risk for any future RWA/compliance-gated asset bank.

### Recommendation
- For banks whose mint carries an active transfer hook (`has_transfer_hook` already detects this), add an explicit, queryable "minimum vault balance" concept (either passed in remaining accounts, fetched via a well-known compliance interface, or configured as a bank parameter) and clamp/guard `withdraw_spl_transfer` so it never attempts to draw the vault below that floor; return a clear, actionable error instead of relying on the CPI failing deep inside the token program.
- Alternatively, disallow banks backed by mints exposing minimum-balance-style transfer hooks unless the hook's rule can be verified/queried on-chain and reserved for in `Bank::get_asset_amount`/withdrawal accounting, similar to how `has_transfer_fee` is modeled explicitly for fee-bearing mints.
- Document this constraint clearly for future integrations analogous to the Ondo/BUIDL disclosure so bank admins can evaluate mint compliance behavior before permissionlessly (or admin-)adding such a bank.

### Proof of Concept
1. Deploy a Token-2022 mint with `TransferHook` extension whose hook program enforces: "reject transfer if `source.amount - transfer_amount < MIN_BALANCE`" (mirroring BUIDL's `minUSTokens` check applied to the sender), matching the pattern already used in marginfi's own `test_transfer_hook` program and `SupportedExtension::TransferHook` test fixtures: [6](#0-5) 
2. Create a marginfi bank with this mint (supported generically, as shown by the liquidation success tests using `SupportedExtension::TransferHook`): [3](#0-2) 
3. Have a user deposit into the bank so the `liquidity_vault` balance sits at/near `MIN_BALANCE`.
4. Call `lending_account_withdraw` for an amount that would leave the vault below `MIN_BALANCE`. The CPI transfer inside `withdraw_spl_transfer` reverts due to the hook's compliance check, even though marginfi's internal share accounting shows the user is fully entitled to withdraw, and no marginfi-side error or fallback communicates or resolves the condition — reproducing the exact "unexpected revert on otherwise valid redemption" behavior described in the Ondo/BUIDL report.

/// Returns `true` if the given mint has an active transfer hook program.
/// If the hook is present but no program is active it would return false.
pub fn has_transfer_hook(mint_ai: AccountInfo) -> MarginfiResult<bool> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(false);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    if let Ok(hook) = mint.get_extension::<TransferHook>() {
        let program_id: Option<Pubkey> = Option::from(hook.program_id);
        return Ok(program_id.is_some());
    }

    Ok(false)
}
