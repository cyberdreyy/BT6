### Title
Post-default withdraw requests drain the fixed default-recovery reserve at par, leaving defaulted-epoch claimants unpayable - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analog to CVE-2021-45932 (decoder reads past the real buffer): `claimWithdrawRequest` "decodes" a claim larger than the funded buffer. After `finalizeDefault`, `defaultRecoveryReserve` is sized exactly to cover the defaulted-epoch claim basis (`totalBasis * recoveryPrice`), but post-default withdraw requests (`postDefaultRequests`) are paid 1:1 out of that same reserve, which was never sized for them. Each post-default claim over-consumes the reserve, so honest holders of defaulted receipts either receive nothing or revert on the `defaultRecoveryReserve -= _amount` underflow, permanently freezing their recovery.

### Finding Description
`finalizeDefaultRecovery` computes the reserve as `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and the price as `reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis` is only active LP basis plus defaulted pending receipts [1](#0-0) . The reserve is therefore exactly exhausted once all defaulted receipts claim their haircut amount.

After finalization, any tranche holder can call `requestWithdraw`, which mints a `postDefaultRequests[_user]` receipt of `_amount` underlyings [2](#0-1) . When they claim, `_claimPostDefaultWithdrawRequest` pays that full amount via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` [3](#0-2) [4](#0-3) . Nothing adds backing for these post-default claims — the burned/minted strategy tokens create no underlying — so they spend reserve earmarked for `pendingWithdraws` and instant-receipt claimants.

### Impact Explanation
The sum of legitimate defaulted claims equals ~`reserveAmount`. Every post-default claim of `x` shrinks the reserve below what the remaining defaulted basis requires. The last defaulted claimant(s) either receive `claimBasis * price` less than owed or revert with an arithmetic underflow in `_transferDefaultRecovery`, permanently freezing their unclaimed recovery inside the strategy. An unprivileged tranche holder can extract recovery funds belonging to others by sandwiching claims: request post-default withdraw, claim before honest users, receive full par payout while honest defaulted receipts become unpayable.

### Likelihood Explanation
Requirements are minimal: a hard default must be finalized (manager/owner action, honest per rules), and the attacker only needs to hold any amount of tranche tokens — obtainable as a normal KYC-passing lender. `requestWithdraw` post-default has no allowlist gate beyond `isWalletAllowed` and the revert on *unclaimed prior receipts* only; a fresh account or an account with no open receipt passes. The larger the post-default withdraw volume relative to reserve, the more honest claims freeze.

### Recommendation
Do not pay `postDefaultRequests` from `defaultRecoveryReserve`. Either fund post-default receipts from a separately accounted bucket (e.g., new borrower repayments / post-default inflows tracked in a distinct counter), or increase `defaultRecoveryReserve`/basis accounting so post-default claims cannot consume defaulted-epoch recovery. Alternatively route post-default payouts through `_transferFundedClaim` semantics with an explicit non-reserve funding source.

### Proof of Concept
Foundry fork PoC sketch (pattern follows `testPostDefaultWithdrawRequiresClaimingOpenPriorReceipt` in `test/foundry/IdleCreditVault.t.sol:4619`):

```solidity
// Setup: AA and BB deposits, start epoch 0, stop epoch -> borrower defaults (deal borrower 0)
// pendingUser has a normal withdraw request pending (claimBasis = P)
uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees();
uint256 recovered = activeBasis * recoveryRatio / ONE_TRANCHE; // e.g. 70%

// manager finalizes default; reserve = recovered (exactly covers basis * price)
deal(defaultUnderlying, manager, recovered);
vm.startPrank(manager);
IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
cdoEpoch.finalizeDefault(recovered, manager);
vm.stopPrank();
// creditVault.defaultRecoveryFinalized() == true; reserve sized for defaulted claims only

// Attacker: fresh tranche holder, no open receipts
address attacker = makeAddr('attacker');
_depositWithUser(attacker, amount, true); // deposits pre-default; or transfer tranche tokens post-default
vm.prank(attacker);
uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche)); // postDefaultRequests[attacker] = receipt

vm.prank(attacker);
cdoEpoch.claimWithdrawRequest(); // pays `receipt` 1:1 from defaultRecoveryReserve

// Victim: honest defaulted pending-withdraw claimant
vm.prank(pendingUser);
cdoEpoch.claimWithdrawRequest(); // either underflows on defaultRecoveryReserve -= amount
                                 // or transfers less than P * recoveryPrice / RECOVERY_FULL
```

Expected: attacker's claim succeeds at par, while `pendingUser`'s haircut claim reverts (reserve underflow) or is short by exactly the attacker's claimed amount — i.e., reserve consumption exceeds the funded buffer it was sized for.

  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
