### Title
Unbounded per-sender EIP-8130 nonce-channel lanes let a single attacker balloon `TwoDNoncePool`, forcing O(n) work on every pending-tx/`best_transactions` snapshot the builder takes - ([File: crates/execution/txpool/src/two_d_nonce_pool.rs])

### Summary
The Sherlock report's root cause is a native (unmetered) loop whose iteration count is driven by attacker-accumulated on-chain/in-pool state that grows unboundedly with no per-round or per-entity cap, executed on a hot path required for the system to make forward progress. The closest reachable analog on Base is `TwoDNoncePool`, the sidecar the transaction pool uses for EIP-8130 channelized transactions: each distinct `(sender, nonce_key)` pair becomes its own persistent `lanes` entry, and there is no cap on how many distinct `nonce_key` channels a single sender may open.

### Finding Description
`TwoDNoncePool` stores one `NonceLane` per `(Address, U256 nonce_key)` pair in `self.lanes: HashMap<LaneId, NonceLane<T>>` [1](#0-0) . `insert_validated` creates a brand-new lane on demand for any `nonce_key` the sender chooses, with no bound on the number of distinct lanes per sender: [2](#0-1) 

Every one of these lanes then participates, unconditionally, in operations that must run to keep block production and pool bookkeeping moving:

- `pending_and_queued_txn_count`, `pending_transactions`, `queued_transactions`, `all_transactions`, `all_hashes`, `transactions_by_sender`, `pending_transactions_by_sender`, `queued_transactions_by_sender`, `unique_senders` all iterate `for lane in self.lanes.values()` / `self.lanes.iter()` - i.e. every lane, every call: [3](#0-2) 
- `best_transactions` (invoked by the builder on essentially every block/flashblock build attempt) constructs a fresh `BestTwoDTransactions` snapshot that walks **every** lane in `self.lanes` to materialize its contiguous head, builds per-lane index maps, and seeds a binary heap with one entry per lane: [4](#0-3) 

None of these paths cap the number of lanes examined - the entire `self.lanes` map is walked regardless of the caller's requested transaction count (`pending_transactions_max` on the wrapping pool trims *after* the fact, per `crates/execution/txpool/src/pool.rs:1136-1149`, but the sidecar's own methods have no equivalent limit). The pool's admission-time caps only bound the *shape of a single transaction* (`MAX_ACCOUNT_CHANGES_PER_TX`, `MAX_CONFIG_CHANGES_PER_TX`, `MAX_ACTORS_PER_ENTRY`, `MAX_ACTOR_CHANGES_PER_CONFIG` in `crates/execution/txpool/src/validator.rs`), not the number of distinct `nonce_key` lanes a sender may accumulate over time. A test in the same file already measures and documents that `best_transactions` cost scales with lane count (`best_transactions_evaluates_each_lane_head_once`, `run_best_transactions_wall_clock`) [5](#0-4) , confirming the maintainers are aware the cost is linear in lane count but no cap exists in the production code path shown.

This mirrors the Sherlock bug class exactly: state that grows unboundedly under attacker control (wounded agents vs. per-sender nonce-channel lanes) is fully walked, with no pagination or cap, on a path the system depends on to keep progressing (starting a new round vs. building every block/flashblock). Because Base's builder calls `best_transactions`/`pending_transactions` on essentially every payload-build and flashblock-build attempt (multiple times per 2-second block via flashblocks), an attacker who opens a large number of distinct `nonce_key` channels for one sender (each requires only a minimal-fee EIP-8130 transaction, not an expensive on-chain loop) forces that native, unmetered walk to repeat continuously for the life of those lanes, since lanes are removed only when their transactions are fully mined/pruned (`remove_hash`) - an attacker can keep a lane alive by submitting a fresh cheap transaction at `next_nonce` faster than it gets mined, or by simply leaving many single-tx lanes queued.

### Impact Explanation
This does not by itself corrupt state or forge value, but it directly threatens block-production availability, which the repo's own review guidance (`docs/guides/BLOCK_PRODUCTION_REVIEW.md`) classifies as Critical: "Resource starvation and transaction-pool exclusion... Builder can repeatedly produce empty or underfilled flashblocks/blocks, or valid transactions can be excluded" and "Flashblock loop, deadline, and publish failures... Flashblocks stop, payload finalization can be skipped or delayed." A sender who accumulates a large number of persistent lanes imposes a per-snapshot cost on every `best_transactions()`/`pending_transactions()` call proportional to the total lane count across *all* senders in the pool (since the walk is over the whole `self.lanes` map, not scoped to one sender), degrading builder responsiveness for every subsequent payload/flashblock attempt system-wide, potentially causing missed flashblock deadlines or slower block assembly under the node's time budget - a resource-starvation condition on the sequencer/builder, not merely a "resource-only" issue local to the attacker, since it degrades shared pool operations relied on by block production.

### Likelihood Explanation
Reachable by a single unprivileged EIP-8130 transaction sender: opening a new `nonce_key` costs only the gas/fee of one minimal transaction, and nothing in `validator.rs`'s admission checks bounds the number of distinct channels a sender may open over time (only per-transaction shape is capped). The attack requires sustained cheap transactions rather than a single call, and its effect (slower snapshots) is probabilistic/latency-based rather than an outright halt, so likelihood is real but not guaranteed to cause a full node halt on its own - it is a genuine but softer DoS/performance-degradation vector.

### Recommendation
Bound the total number of live `(sender, nonce_key)` lanes retained per sender (and/or in aggregate) in `TwoDNoncePool`, evicting or rejecting new channel creation once the cap is hit, mirroring the existing per-transaction caps in `crates/execution/txpool/src/validator.rs`. Additionally consider making `best_transactions`/`pending_transactions`/`all_transactions` respect a `max` budget when walking `self.lanes`, so a single sender's lane count cannot dominate per-snapshot cost for the whole pool.

### Proof of Concept
Not independently verifiable without live-node profiling; the codebase's own `best_transaction_priority_evaluations`/`run_best_transactions_wall_clock` tests in `crates/execution/txpool/src/two_d_nonce_pool.rs:795-847` already demonstrate the linear-in-lane-count cost of `best_transactions`, which is the mechanism this analog relies on - scaling that lane count to attacker-controlled magnitudes (many cheap distinct `nonce_key` channels from one sender, sustained over time) is the proposed exploitation path, but I could not confirm at what lane count real wall-clock/flashblock-deadline impact becomes severe, since that requires running the ignored wall-clock diagnostic test or a live builder benchmark, which is outside what static code review can establish with certainty.

    /// Returns the number of pending and queued transactions.
    pub(crate) fn pending_and_queued_txn_count(&self) -> (usize, usize) {
        let mut pending = 0;
        let mut queued = 0;
        for lane in self.lanes.values() {
            let pending_in_lane = lane.consecutive_pending_len();
            let live_in_lane = lane.live_transactions().count();
            pending += pending_in_lane;
            queued += live_in_lane.saturating_sub(pending_in_lane);
        }
        pending += self.nonce_free.len();
        (pending, queued)
    }

    /// Returns all pending transactions.
    pub(crate) fn pending_transactions(&self) -> Vec<Arc<ValidPoolTransaction<T>>> {
        let mut transactions = Vec::new();
        for lane in self.lanes.values() {
            for transaction in lane.consecutive_pending_transactions() {
                transactions.push(Arc::clone(transaction));
            }
        }
        transactions.extend(self.nonce_free.values().cloned());
        transactions
    }

    /// Returns all queued transactions.
    pub(crate) fn queued_transactions(&self) -> Vec<Arc<ValidPoolTransaction<T>>> {
        let mut transactions = Vec::new();
        for lane in self.lanes.values() {
            for transaction in lane.queued_transactions() {
                transactions.push(Arc::clone(transaction));
            }
        }
        transactions
    }

    /// Returns all transactions in the sidecar.
    pub(crate) fn all_transactions(&self) -> Vec<Arc<ValidPoolTransaction<T>>> {
        let mut transactions = Vec::new();
        for lane in self.lanes.values() {
            transactions.extend(lane.live_transactions().cloned());

impl<T: BasePooledTx, O> BestTwoDTransactions<T, O>
where
    O: TransactionOrdering<Transaction = T>,
{
    fn new(
        lanes: &HashMap<LaneId, NonceLane<T>>,
        nonce_free: &B256Map<Arc<ValidPoolTransaction<T>>>,
        ordering: O,
        base_fee: u64,
    ) -> Self {
        let mut lanes: Vec<_> = lanes
            .iter()
            .filter_map(|(id, lane)| {
                let mut next_nonce = lane.next_nonce;
                let mut transactions = Vec::new();
                while let Some(transaction) = lane.transactions.get(&next_nonce) {
                    transactions.push(Arc::clone(transaction));
                    let Some(incremented_nonce) = next_nonce.checked_add(1) else {
                        break;
                    };
                    next_nonce = incremented_nonce;
                }
                (!transactions.is_empty()).then(|| LaneIterator {
                    id: *id,
                    transactions,
                    index: 0,
                    invalidated: false,
                })
            })
            .collect();
        let finite_lane_count = lanes.len();
        lanes.extend(nonce_free.values().map(|transaction| LaneIterator {
            id: (transaction.sender(), Eip8130Constants::NONCE_KEY_MAX),
            transactions: vec![Arc::clone(transaction)],
            index: 0,
            invalidated: false,
        }));
        let lane_indexes = lanes[..finite_lane_count]
            .iter()
            .enumerate()
            .map(|(index, lane)| (lane.id, index))
            .collect();
        let nonce_free_indexes = lanes[finite_lane_count..]
            .iter()
            .enumerate()
            .map(|(offset, lane)| (*lane.transactions[0].hash(), finite_lane_count + offset))
            .collect();
        let candidates = BinaryHeap::from(
            lanes
                .iter()
                .enumerate()
                .map(|(index, lane)| {
                    (
                        BestTransactionPriority::new(&ordering, &lane.transactions[0], base_fee),
                        index,
                    )
                })
                .collect::<Vec<_>>(),
        );
        Self { candidates, lanes, lane_indexes, nonce_free_indexes, ordering, base_fee }

    fn best_transaction_priority_evaluations(lane_count: usize) -> usize {
        let mut pool = TwoDNoncePool::new(PriceBumpConfig::default());
        let signer = signer();
        for nonce_key in 1..=lane_count {

        let ordering = CountingOrdering::default();
        let priority_evaluations = Arc::clone(&ordering.priority_evaluations);
        let yielded = pool.best_transactions(ordering, 0).count();

        assert_eq!(yielded, lane_count);
        priority_evaluations.load(Ordering::Relaxed)
    }
