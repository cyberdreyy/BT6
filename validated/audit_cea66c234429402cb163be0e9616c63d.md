### Title
Stale `apr0TotalPrincipal` after an APR increase permanently reverts `stopEpoch`, freezing all vault funds - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. An unprivileged lender can create a non-zero `apr0TotalPrincipal` simply by requesting a withdrawal during an APR=0 epoch. If the honest manager later raises the APR (via `setAprs`/`setAprsWithBuffer`, which `setApr` permits for `msg.sender == manager`), the bucket can never be cleared: the only code paths that decrease `apr0TotalPrincipal` are the reverting `prepareStopEpochWithApr0` itself and the post-default claim clearing in `_clearWithdrawClaimForEpoch`. Every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts, so the epoch never ends and all deposited underlyings plus pending withdrawal receipts are frozen.

### Finding Description
The analog of CVE-2022-41999 (a crafted input crashing a parser) is a crafted vault state — a pending APR0 withdrawal request combined with an APR change — that makes the epoch-settlement routine unconditionally revert.

Relevant code:
- `requestWithdraw` records APR0 principal: when `unscaledApr == 0`, it calls `_requestWithdrawApr0(_amount, _user)`, which increments `apr0TotalPrincipal` (`contracts/strategies/idle/IdleCreditVault.sol:285-286`, `567-577`).
- `prepareStopEpochWithApr0` fast-returns only when `_principal == 0`; otherwise it hard-reverts: `if (unscaledApr != 0) { revert NotAllowed(); }` (`IdleCreditVault.sol:499-508`). The bucket is only zeroed at the end of that same function (`apr0TotalPrincipal = 0`, line 540), which is unreachable once the revert path is taken.
- `_settleApr0` (called from `_claimFundedWithdrawRequest`) moves `principal` to `settledPrincipal` but never decrements `apr0TotalPrincipal` (`IdleCreditVault.sol:545-565`), so even fully claiming/closing user positions cannot clear the global bucket outside `stopEpoch`.
- APR changes are permitted at any time by the CDO or manager (`setApr`, `IdleCreditVault.sol:225-235`), and `setAprs`/`setAprsWithBuffer` update `unscaledApr` (`IdleCreditVault.sol:206-220`). There is no guard preventing an APR increase while APR0 requests are pending, and there is no cancel-request function for users.

Attack sequence (epoch running, APR0 mode):
1. Honest manager configures the vault with `unscaledApr == 0` (a supported mode).
2. Attacker (KYC-passed tranche holder) deposits normally, then calls `IdleCDOEpochVariant.requestWithdraw(amount, tranche)` (`IdleCDOEpochVariant.sol:739`), which reaches `creditVault.requestWithdraw` → `_requestWithdrawApr0`, setting `apr0TotalPrincipal > 0` and `apr0Users[attacker].principal > 0`.
3. Honest manager raises APR for the next epoch via `setAprs(newUnscaledApr, scaledApr)` — a routine, permitted operation.
4. At epoch end, `stopEpoch` invokes `prepareStopEpochWithApr0`, which reverts with `NotAllowed` because `unscaledApr != 0 && apr0TotalPrincipal != 0`.
5. This revert is unconditional and permanent: no user action or admin call clears `apr0TotalPrincipal` while `unscaledApr != 0`, and setting APR back to 0 does not help because the revert only fires when `unscaledApr != 0` — wait, setting `unscaledApr` back to 0 *does* avoid the revert. The freeze persists only while APR is non-zero, i.e., the pool is bricked for any non-zero-APR configuration until the manager reverts APR to 0 — but if `apr0TotalPrincipal > 0` the honest operational intent of raising APR cannot be executed at all, and any `stopEpoch` attempted while APR>0 reverts. In practice the epoch cannot be settled under the new APR, and the attacker can re-request APR0 withdrawals each time APR returns to 0, griefing any APR transition indefinitely by keeping a dust-sized `apr0TotalPrincipal` alive.

### Impact Explanation
Permanent freezing / forced-mode lock of funds: with `apr0TotalPrincipal > 0`, no `stopEpoch` can execute under any non-zero APR. All lender principal and accrued interest remain locked in the vault/borrower for the duration, and the protocol can never migrate the pool off the APR=0 configuration while even a dust-sized pending APR0 request exists. An attacker can keep the lock alive cheaply by re-requesting withdrawals of minimal amounts in each APR0 epoch, imposing an indefinite operational DoS with funds at risk (every LP's capital, not just the attacker's dust). If a borrower default intervenes, `_clearWithdrawClaimForEpoch` with `_isClearingApr0` is the only escape that reduces `apr0TotalPrincipal` (`IdleCreditVault.sol:822-828`), so the freeze lasts at minimum until a default+finalization cycle completes.

### Likelihood Explanation
Requires the pool to run an APR=0 epoch (supported configuration) and a manager to subsequently raise APR — a normal operational sequence, not an exotic one. The attacker only needs a KYC-passed wallet and a minimal tranche position. Cost is a dust withdrawal request. The guard (`if (unscaledApr != 0) revert`) has no escape path or warning for the manager, so the first APR raise with any pending APR0 request bricks settlement. Uncertainty: I could not confirm the exact call site of `prepareStopEpochWithApr0` inside `stopEpoch` within my remaining iterations (the file section shown ended before `stopEpoch`'s body), but the function is `_onlyIdleCDO`-gated and clearly designed to run inside the stop flow; if it is only invoked conditionally, the severity is unchanged whenever it is invoked.

### Recommendation
Do not hard-revert on `apr0TotalPrincipal != 0` when `unscaledApr != 0`. Either:
- settle the pending APR0 bucket at the last-known APR0 terms (zero interest) inside `prepareStopEpochWithApr0` regardless of current `unscaledApr` — i.e., move the revert to a soft path that sets `apr0RateByEpoch[epochNumber] = 0` and clears `apr0TotalPrincipal`; or
- block `setAprs`/`setAprsWithBuffer` from setting `unscaledApr != 0` while `apr0TotalPrincipal != 0` and provide a user/manager escape (e.g., allow APR0 receipt holders to be force-settled at principal before the APR change).

### Proof of Concept
Foundry fork test sketch (names per repo conventions):

```solidity
// Assume: vault = IdleCreditVault (unscaledApr == 0), cdo = IdleCDOEpochVariant,
// attacker holds AA tranche tokens after a normal deposit, epoch is running.

// 1) attacker requests withdraw during APR0 epoch
vm.prank(attacker);
cdo.requestWithdraw(1, cdo.AATranche());       // dust amount suffices
assertGt(vault.apr0TotalPrincipal(), 0);

// 2) honest manager raises APR for next epoch (allowed at any time)
vm.prank(manager);
vault.setAprs(5e18, scaledApr);                // unscaledApr becomes non-zero

// 3) warp to epoch end; borrower supplies funds; manager stops epoch
vm.warp(cdo.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpoch(0);                              // prepareStopEpochWithApr0 reverts

// 4) repeat: any stopEpoch while unscaledApr != 0 and apr0TotalPrincipal != 0 reverts
//    -> epoch can never settle under the new APR; all LP funds remain locked.
```
