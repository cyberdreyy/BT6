### Title
Confirmations from a deleted multisig key remain counted toward the confirmation threshold on pending requests - ([File: multisig/src/lib.rs])

### Summary
The `DeleteKey` action in `execute_request` only purges requests that were *created* by the removed public key, but it does not scrub that key's confirmation entries from `confirmations` on other pending requests that the key had already confirmed. `confirm()` later counts `confirmations.len()` against `num_confirmations` without checking whether each entry corresponds to a currently valid signer, so a stale confirmation from a removed key still counts toward execution.

### Finding Description
`confirm()` treats `self.confirmations.get(&request_id)` as the authoritative set of "live" approvals and executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

When a key is removed via `MultiSigRequestAction::DeleteKey`, the contract only removes *requests whose `signer_pk` equals the deleted key* (i.e. requests that key itself created), and clears the `num_requests_pk` counter for that key: [2](#0-1) 

It does **not** iterate over `self.confirmations` to strip the deleted key from confirmation sets of *other* outstanding requests (requests created by a different signer that the now-deleted key had already confirmed via `confirm()`). Those confirmation sets are plain `HashSet<PublicKey>` stored independently of key validity: [3](#0-2) 

The binding the contract is supposed to maintain is: `confirmations.len() (live valid signers who approved) == confirmations counted toward num_confirmations threshold`. After a `DeleteKey` execution, this becomes `confirmations counted > live valid signers who approved`, because a removed key's approval is still present in the set.

### Impact Explanation
This breaks the authorization threshold guarantee of the multisig: a request can execute with fewer *currently authorized* signers than `num_confirmations` requires, because one of the counted confirmations belongs to a key that has since been revoked (e.g., a compromised or offboarded signer). Since multisig actions include `Transfer`, `FunctionCall`, `AddKey`, and `DeployContract`, this can let NEAR move, or governance-level state changes execute, at an effectively lower/broken threshold than configured — i.e., "a multisig request executed below threshold," matching the Critical impact class defined for this scope.

### Likelihood Explanation
Exploitation requires no privileged access beyond being any current multisig signer to submit the final confirming transaction; the precondition (a key that had confirmed a pending request being later removed via `DeleteKey`) is a normal operational event (key rotation, revoking a departing member, responding to key compromise) rather than an attack on its own. Any remaining signer(s) can complete execution using the stale confirmation, so likelihood is moderate-to-high in any deployment that rotates keys while requests are outstanding.

### Recommendation
When executing `MultiSigRequestAction::DeleteKey`, iterate over all entries in `self.confirmations` and remove the deleted public key from every confirmation set (not just requests where it is the `signer_pk`), or alternatively validate confirmation-set membership against the currently active key set at `confirm()`-time rather than trusting a cached `HashSet`.

### Proof of Concept
1. Contract initialized with `num_confirmations = 2` and keys A, B, C.
2. Key A calls `add_request` to create request R1 (targeting a `Transfer`).
3. Key B calls `confirm(R1)` → `confirmations[R1] = {B}` (size 1 < 2, so it just records the confirmation). [1](#0-0) 
4. Separately, an already-confirmed multisig request executes `DeleteKey { public_key: B }` to revoke B (e.g., B left the org). Only requests where `signer_pk == B` are purged; R1 (signed by A) is untouched, and `confirmations[R1]` still contains B. [2](#0-1) 
5. Key A now calls `confirm(R1)`. `confirmations.len() (1, still containing revoked B) + 1 >= 2` → request executes, even though only one *currently valid* key (A) ever confirmed it after B's removal. [4](#0-3) 

This demonstrates a 2-of-3 request executing with effectively 1 live confirming key, violating the configured threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
