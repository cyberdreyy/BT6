### Title
Stale per-epoch instant-withdraw accounting after funded claims causes underflow revert and permanently freezes legitimate claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Duktape bug class — accumulated state that is never popped, eventually crashing the consumer — maps to `IdleCreditVault`'s per-epoch instant-withdraw receipt bookkeeping. `requestInstantWithdraw` increments both the aggregate `instantWithdrawsRequests[_user]` and the per-epoch `instantWithdrawsRequestsByEpoch[_user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]` counters (lines 366-374). The normal funded-claim path `claimInstantWithdrawRequest` resets only the aggregate (lines 387-392) and never clears the per-epoch entries. Once `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, every call to `claimInstantWithdrawRequest` first runs `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844) and subtracts that basis from the aggregate (line 848). A user who claimed an instant withdrawal earlier in the same epoch that defaults carries a stale per-epoch basis larger than their remaining aggregate, so the subtraction underflows and the claim function reverts forever.

### Finding Description
Sequence during a running epoch E (instant withdrawals are serviced while the epoch runs, `epochNumber` stays E):

1. User requests instant withdraw of 100 via `IdleCDOEpochVariant.requestInstantWithdraw` → `IdleCreditVault.requestInstantWithdraw`: `instantWithdrawsRequestsByEpoch[user][E] = 100`, `instantWithdrawsRequests[user] = 100`, `instantWithdrawClaimsByEpoch[E] = 100`, receipt tokens minted to user.
2. CDO funds the request via `collectInstantWithdrawFunds` (line 398); user calls `claimInstantWithdrawRequest`, receives 100 underlying. `instantWithdrawsRequests[user] = 0`, but `instantWithdrawsRequestsByEpoch[user][E]` and `instantWithdrawClaimsByEpoch[E]` remain 100 — stale.
3. Same epoch E: user requests another instant withdraw of X → `instantWithdrawsRequestsByEpoch[user][E] = 100 + X`, `instantWithdrawsRequests[user] = X`.
4. Borrower defaults in epoch E; finalization sets `defaultRecoveryEpoch = E`, `defaultRecoveryFinalized = defaultInstantWithdrawsFinalized = true`.
5. User calls `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = 100 + X`, then executes `instantWithdrawsRequests[user] -= claimBasis` → `X - (100 + X)` underflows (Solidity 0.8 checked arithmetic) → revert. This revert happens on every subsequent call, before the funded-claim tail at lines 387-392 can run.

Because `claimBasis` for the default epoch always includes the already-paid stale amount, `instantWithdrawsRequests[_user] >= claimBasis` can never be restored within that epoch (every new request increases the per-epoch entry by the same amount). The revert is permanent. Additionally, `instantWithdrawClaimsByEpoch[E]` is never decremented by funded claims, so the epoch-level total used by default finalization overstates real outstanding instant claims by all amounts already paid at par — the attacker can inflate it arbitrarily by cycling large instant request → fund → claim in the epoch that ends up defaulting.

### Impact Explanation
- Permanent freezing: any user with a funded-then-claimed instant withdrawal in the epoch that defaults can never execute `claimInstantWithdrawRequest` again; their remaining legitimate instant receipts (and any newly funded ones) are locked in the strategy. The receipt tokens were already minted to the user and cannot be redeemed through any other path.
- Recovery-accounting distortion: `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` counts phantom (already-paid) claims. Where finalization sizes `defaultRecoveryReserve` or validates pending claims from this total, the reserve is either over-allocated (stranding underlying that honest claimants cannot reach, since the stale entries can never be collected past the underflow) or the recovery price is diluted against claims nobody can execute — in both cases value owed to honest defaulted-epoch claimants is permanently impaired or frozen.
- Broken invariant: one receipt one payout / conservation — the same instant-withdraw basis is counted twice (once paid at par pre-default, once carried into default-epoch claim totals), and the aggregate-vs-per-epoch accounting diverges irreversibly.

No existing guard stops this: `_ensureDefaultRecoveryInitialized` only checks pending totals (lines 924-930), the `_onlyIdleCDO` guard is irrelevant, and there is no code path that clears `instantWithdrawsRequestsByEpoch` or decrements `instantWithdrawClaimsByEpoch` outside of `_claimDefaultedInstantWithdrawRequest` itself (which is unreachable past the underflow).

### Likelihood Explanation
Requires a borrower default in the same epoch during which an instant withdrawal was requested, funded, and claimed — instant withdrawals are processed while epochs run, so this ordering is realistic. The inflation of `instantWithdrawClaimsByEpoch` is fully attacker-controllable: an unprivileged KYC-passing lender can cycle arbitrarily large instant request/claim volumes within a single epoch at only gas cost, since instant withdrawals are designed to be serviced immediately from available liquidity. The freeze impact on individual users needs no attacker at all — it is triggered by ordinary protocol usage followed by a default.

### Recommendation
Mirror the clearing done for normal withdraws in `_clearWithdrawClaimForEpoch`: when `claimInstantWithdrawRequest` pays a funded claim, clear `instantWithdrawsRequestsByEpoch[_user][epoch]` for the relevant epoch(s) and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount. Since the aggregate mixes epochs, either track per-epoch funding status or clear the entries for all epochs ≤ current epoch on successful funded claim. Add a regression test covering: request → fund → claim → new request → same-epoch default → `claimInstantWithdrawRequest` must not revert and must pay exactly the outstanding basis.

### Proof of Concept
Foundry fork PoC outline against `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
function testStaleInstantEntryBlocksPostDefaultClaim() external {
    // epoch running; user has tranche tokens
    uint256 amt1 = 100 * ONE_SCALE;
    cdoEpoch.requestInstantWithdraw(amt1, address(AAtranche)); // via CDO -> strategy.requestInstantWithdraw
    // manager/borrower funds instant liquidity; CDO calls collectInstantWithdrawFunds
    _fundInstant(amt1);
    cdoEpoch.claimInstantWithdrawRequest();              // paid at par; per-epoch entry NOT cleared

    uint256 amt2 = 50 * ONE_SCALE;
    cdoEpoch.requestInstantWithdraw(amt2, address(AAtranche));

    // borrower defaults in the SAME epoch -> finalizeDefault + instant finalization
    _handleBorrowerDefaultAndFinalize();

    vm.expectRevert(); // underflow: instantWithdrawsRequests(50) -= claimBasis(150)
    cdoEpoch.claimInstantWithdrawRequest();
    // instantWithdrawsRequestsByEpoch[user][epoch] == 150 forever; user's 50 is frozen
}
```
