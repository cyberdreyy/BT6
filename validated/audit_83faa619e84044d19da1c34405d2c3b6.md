### Title
Missing MessageId uniqueness check in `HandleLegacyUserMessage` allows cross-user callback hijacking / response confusion - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage()` in the WebAPI gateway capabilities handler stores an incoming request's callback keyed only by the client-supplied `MessageId`, without ever checking whether an entry for that ID already exists. This lets a second (unrelated) unprivileged request silently overwrite the in-flight callback of a first request, so the eventual DON node response gets delivered to the wrong caller (or the original caller is dropped entirely). This mirrors the reported bug class: a state slot (there, the packet's burn state; here, the `savedCallbacks[MessageId]` slot) can be re-entered/overwritten mid-flight by another actor-controlled operation before the original operation completes, causing response/asset misdelivery.

### Finding Description
The gateway is an internet-facing entry point: `gateway.ProcessRequest()` decodes an inbound JSON-RPC request and, for legacy DON-routed messages, calls `h.HandleLegacyUserMessage(ctx, msg, callback)`: [1](#0-0) 

In `HandleLegacyUserMessage`, after validating payload/timestamp/method, the handler stores the caller's callback directly into the shared `savedCallbacks` map keyed by `msg.Body.MessageId`, with **no existence check**: [2](#0-1) 

`MessageId` is attacker-controlled: it is part of `MessageBody`, only constrained by length/null-byte checks in `Message.Validate()`, and is not tied to session or sender identity: [3](#0-2) 

When a DON node later responds, `handleWebAPITriggerMessage` looks up and deletes the entry by `MessageId` and forwards the response to whichever callback currently occupies that slot: [4](#0-3) 

By contrast, the newer v2 HTTP trigger handler (`http_trigger_handler.go`) explicitly guards against this exact scenario by rejecting a request whose `requestID` already has an in-flight callback: [5](#0-4) 

The legacy handler lacks this check, so two different unprivileged clients (or a malicious client racing a legitimate one) that submit requests with the same `MessageId` will cause the second submission to overwrite the first's callback in `savedCallbacks`. The eventual node response correlated to that `MessageId` is delivered only to whoever "wins" the map slot — the original requester's response can be silently redirected to the attacker, or the original requester never receives a response (until the 2-minute prune timeout).

### Impact Explanation
This is a concrete cross-user response confusion / hijack: an unprivileged party interacting with the internet-facing gateway can capture or blackhole another user's pending webhook/trigger response by racing a request with a colliding `MessageId`. Depending on payload content returned by the DON (e.g., trigger execution results), this can leak the victim's response data to the attacker, or cause a denial of service for the victim's request (silently dropped, no error surfaced until timeout). This does not require any special privilege beyond being able to send a signed request routed by DON ID (the legacy path), which is reachable from the internet-facing gateway HTTP endpoint.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to guess or observe a target `MessageId` and win a race to submit a colliding request before the legitimate node response arrives. Since `MessageId` is fully attacker-chosen and not validated for uniqueness or freshness against in-flight callbacks (unlike the v2 handler's explicit check), an attacker controlling their own signed messages can deliberately choose IDs likely to collide (e.g., sequential/predictable IDs used by a legitimate integration) or can simply flood with common/short IDs to increase collision probability within the response window.

### Recommendation
Add the same idempotency/uniqueness guard used in the v2 handler (`setupCallback`) to `HandleLegacyUserMessage`: reject (or return a conflict error to) any incoming message whose `MessageId` already has a live entry in `savedCallbacks`, instead of unconditionally overwriting it. Additionally, consider scoping the `savedCallbacks` key to `(Sender, MessageId)` rather than `MessageId` alone, so that different senders cannot collide on the same identifier at all.

### Proof of Concept
1. Attacker learns/predicts the `MessageId` a victim's external initiator will use for a legitimate `web_api_trigger` request (e.g., a fixed or sequential ID scheme).
2. Victim submits their request; gateway calls `HandleLegacyUserMessage`, storing `savedCallbacks["X"] = victimCallback` and forwarding to DON nodes.
3. Before the DON node responds, attacker submits their own signed request with the same `MessageId = "X"` (any DonId/method they can access). `HandleLegacyUserMessage` overwrites `savedCallbacks["X"] = attackerCallback` with no conflict check.
4. When the DON node responds for message `"X"` (intended for the victim's original request), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds the attacker's callback, deletes the entry, and delivers the victim's response to the attacker via `savedCb.SendResponse(...)`.
5. The victim's original request either receives no response (dropped) or an unrelated response, depending on timing — demonstrating cross-user response confusion caused by the missing uniqueness check identified at [6](#0-5) .

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
