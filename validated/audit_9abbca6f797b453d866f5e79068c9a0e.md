Found a concrete analog in the multisig contracts: stale confirmations from a removed member continue to count toward the confirmation threshold, allowing a request to execute below the configured `num_confirmations` — mirroring the report's core pattern of an accounting record (confirmations) diverging from the actual entitled parties (live members) and being trusted for a settlement action (executing a fund transfer).

### Title
Stale confirmations from removed multisig members allow request execution below `num_confirmations` threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts entries in the `confirmations` set for a request without verifying that each entry still corresponds to a current member of the multisig. When a member is removed via `DeleteMember`/`DeleteKey`, only requests *originated* by that member are purged; confirmations that member previously cast on *other* still-pending requests are never cleaned up. Those stale confirmations remain in the `confirmations: LookupMap<RequestId, HashSet<String>>` map and are still counted by `confirm()`'s `confirmations.len() as u32 + 1 >= self.num_confirmations` check, so a request can execute with fewer live-member confirmations than the threshold requires.

### Finding Description
`confirm()` in [1](#0-0)  only checks that the caller is a current member and that they haven't confirmed yet; it never re-validates the *existing* confirmations already stored for the request against the current member set before comparing the count to `num_confirmations`.

`delete_member()` [2](#0-1)  removes a departing member's own *outstanding requests* (`r.member == member`) and their `num_requests_pk` entry, and revokes their access key, but it does not scan `self.confirmations` to strip that member's `String` entry from any other request's confirmation set. The equivalent logic in the original multisig, `DeleteKey`, has the identical gap: [3](#0-2) , and its `confirm()` has the same unconditioned count check: [4](#0-3) .

The custody binding broken is: `confirmations counted == live members who confirmed`. After a member removal this becomes `confirmations counted > live members who confirmed`, so a request can cross the `num_confirmations` threshold using a mix of live and stale (no-longer-authorized) confirmations.

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`, or `DeployContract` action can be executed against the multisig's own account (which typically custodies NEAR or controls other contracts) with effectively fewer independent, currently-authorized confirmations than `num_confirmations` mandates, undermining the entire security guarantee of the k-of-n scheme.

### Likelihood Explanation
No foundation, victim key, redeploy, or external actor is required — only normal multisig member turnover (a routine `DeleteMember`/`DeleteKey` request executed through the normal confirmation flow) combined with a pending request that the departing member had previously confirmed. Membership changes are an expected, unprivileged (from the perspective of remaining members) operational event in any long-lived multisig, making this reachable in ordinary usage rather than a contrived edge case.

### Recommendation
When removing a member (`delete_member` in multisig2, `DeleteKey` in multisig), iterate over all entries in `self.confirmations` and remove the departing member's identifier from every request's confirmation set, not just requests they authored. Alternatively, in `confirm()`, recompute/filter the confirmations set against `self.members` (or the live public-key set) before comparing its size to `num_confirmations`.

### Proof of Concept
1. Deploy a 2-of-3 multisig with members A, B, C (`num_confirmations = 2`), per `MultiSigContract::new` [5](#0-4) .
2. A calls `add_request` for a `Transfer` (request X) to an account A controls. `confirmations[X] = {}`.
3. B calls `confirm(X)`. `confirmations[X] = {"B"}` (1 < 2, so it is stored, not executed) — see `confirm()` [1](#0-0) .
4. Separately, members confirm and execute a `DeleteMember { member: B }` request, removing B from the multisig via `delete_member()` [2](#0-1) . Because request X was authored by A (not B), it is not touched, and B's stale `"B"` entry remains in `confirmations[X]`.
5. A now calls `confirm(X)` again. `confirmations[X]` still contains `"B"`, so `confirmations.len() (1) + 1 >= num_confirmations (2)` is true, and the transfer executes — funded by only one truly live, current-member confirmation (A) plus one stale confirmation from a removed member (B), instead of the required 2 live confirmations.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
