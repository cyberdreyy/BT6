### Title
`check_parent_tenure_choice` treats a missing local `approved_time` as "poorly timed", silently disabling the reorg-timing safeguard - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` is the only guard standing between an ordinary "poorly-timed tenure" reorg and a reorg of an already-established tenure. Its decision hinges on measuring how long elapsed between the reorged tenure's first block being locally approved and the new sortition arriving. When this signer's local database has no `approved_time` for that block, the code does not treat this as "unknown" — it treats it as `0` seconds, i.e. maximally poorly-timed, and unconditionally permits the reorg regardless of how long the tenure had actually been live.

### Finding Description

`approved_time` on a `BlockInfo` is only stamped when *this* signer itself pre-committed the block (`mark_pre_committed`), as documented on the struct: [2](#0-1) 

If this signer never pre-committed the reorged tenure's first block — because it rejected the proposal, was offline/restarted and lost its local `signerdb` state, or simply received/processed the proposal too late relative to its own clock — `local_block_info.approved_time` is `None`. The `else` branch then substitutes `proposal_to_sortition = 0`, which is by construction always `< first_proposal_burn_block_timing`, so the tenure is unconditionally classified as "poorly timed" and pushed into `superseded_tenures`, regardless of the real-world elapsed time since the block was proposed and possibly globally accepted by the rest of the signer set.

This is the same failure mode as the external report's core complaint about front-running/timing: a value meant to gate a state transition behind a time window (`first_proposal_burn_block_timing`, described in the config docs as guarding against reorgs of tenures that "were established long enough for the incoming miner to RBF any outdated commit") can be bypassed — here not via administrator front-running, but via an ordinary local-state gap that a miner's proposal timing (plus normal network/gossip delay or a signer restart) can produce on any individual signer, with no majority collusion required.

Once a tenure is (incorrectly) recorded as superseded via `record_superseded_tenure`/`mark_tenure_superseded`, this signer's own earlier signature over that tenure's block no longer counts as a conflict against the replacement tenure, per the "reorg permit" mechanism described in the flow docs: [3](#0-2) 

### Impact Explanation
If this signer had already signed or accepted the original tenure's block (or such a block reached global acceptance via other signers) while this signer itself lacks a local `approved_time` record for it, this bug removes the intended timing protection and lets the signer treat a *not actually poorly-timed* competing tenure as an allowed reorg target. The signer can then go on to sign a block in the competing (reorg) tenure, producing a signature over a tenure that the timing rule was specifically designed to disallow reorging — i.e., the signer ends up signing off on a conflicting/non-canonical replacement of an already-established tenure. This falls under "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
The trigger condition — a signer missing `approved_time` for a tenure's first block — is not exotic: it occurs whenever a signer's local DB doesn't have a pre-commit record for that specific block (rejected it initially, was offline, restarted and lost recent state, or received/validated it too late to pre-commit before the tenure changed). No majority collusion or privileged access is needed; a single miner racing a subsequent sortition while some signers are in this state is sufficient to have those specific signers wrongly classify the reorg as permitted.

### Recommendation
Distinguish "unknown/no local record" from "known and zero elapsed time." When `approved_time` is unavailable, the signer should not assume the most permissive case (immediate elapse); instead it should either query the node/other signers for the block's actual proposal/acceptance timing before deciding, or conservatively refuse the reorg (return `Ok(false)`) rather than defaulting to `0`, mirroring the existing conservative branches elsewhere in this same function (e.g. the "no local knowledge for that tenure's block timing" case a few lines above, which already returns `Ok(false)` rather than guessing).

### Proof of Concept
1. Tenure T1 (miner A) proposes its first (and only) block; it is globally accepted by a threshold of the signer set (e.g. via `get_globally_accepted_block_count_in_tenure`), but signer S never pre-commits it locally (S rejected the initial proposal, or S restarted and lost its `signerdb` state right after boot, or the proposal simply reached S after it had already moved on).
2. A short time later, Bitcoin produces a new sortition; miner B wins and proposes a tenure-start block whose `parent_tenure_id` reorgs away T1 (well after any reasonable "poorly timed" window has passed in real-world terms — but `first_proposal_burn_block_timing` is measured from `S`'s local `approved_time`, which is absent).
3. On signer S, `check_proposal` (v1) / `check_proposal` wrapper (v2) invokes `check_parent_tenure_choice`, which finds `local_block_info.approved_time == None` for T1's first block, sets `proposal_to_sortition = 0`, and since `0 < first_proposal_burn_block_timing`, marks T1 as superseded and returns `Ok(true)`.
4. Signer S now accepts miner B's tenure-start proposal as valid despite T1 having been live/globally accepted for far longer than `first_proposal_burn_block_timing` should have allowed, and may go on to sign blocks in miner B's tenure that conflict with T1 — a reorg the timing safeguard was explicitly designed to prevent.

One decision does have to be recorded, because it is ours rather than the
node's. When a miner builds off something other than the prior sortition,
`check_parent_tenure_choice` decides whether the reorg is allowed: it is, if
every tenure being reorged has at most one globally accepted block and produced
its first block too close to the next sortition to count
(`first_proposal_burn_block_timing`). Having sanctioned that replacement, the
signer records those tenures as **superseded** (`mark_tenure_superseded`), so its
own signature over what they built does not then block the replacement it just
permitted — the node cannot answer this one at signing time, since it still
serves the reorged tenure as fully live until the replacement lands. What _is_
still derived from the node is the permit's own validity: the record carries the
permitting tenure's sortition, and it only excludes conflicts while that
sortition remains canonical (section 5, `reorg_permit_stands`), so a burnchain
fork that orphans the permitting tenure automatically voids the permit. A record
more than `MAX_FORK_DEPTH` (100) burn blocks below the tip is dropped; a fork
that deep would cause far bigger problems than a stale conflict.
