### Title
Missing state-transition check on `ExecutionPayloadBid.execution_payment` lets an untrusted builder authorize an unaccounted execution-layer payment - (File: specs/gloas/beacon-chain.md)

### Summary
`process_execution_payload_bid` in `specs/gloas/beacon-chain.md` validates and settles the *consensus-accounted* builder payment field `bid.value` (deducting from the builder's balance / creating a `BuilderPendingPayment`), but never validates the sibling field `bid.execution_payment`, which the spec's own builder documentation defines as authorizing a "trusted execution-layer payment" that only self-builds are allowed to set non-zero.

### Finding Description
The `ExecutionPayloadBid` container carries two independent value fields: [1](#0-0) 

`builder.md` defines the trust boundary for `execution_payment` explicitly: it must be zero for any bid meant to be publicly gossiped/used by an untrusted builder, and a non-zero value signals a "trusted execution-layer payment": [2](#0-1) 

The *only* place this invariant is enforced is the p2p gossip validator, which is a network-propagation filter, not a state-transition validity rule: [3](#0-2) 

The actual consensus state-transition function, `process_execution_payload_bid`, only reads/validates `amount = bid.value` for balance sufficiency, self-build zero-value/signature checks, and pending-payment bookkeeping. `bid.execution_payment` is never asserted to be zero for the external-builder branch, and is simply cached into `state.latest_execution_payload_bid` unmodified: [4](#0-3) 

Because gossip-only enforcement is not a consensus rule, any block that reaches a proposer through an out-of-gossip channel (private builder/relay submission, local mempool of bids, etc.) with a non-zero `execution_payment` from a non-self-build (`builder_index != BUILDER_INDEX_SELF_BUILD`) bid will pass `process_execution_payload_bid` and be accepted by every spec-following node, since no assertion in the state-transition function rejects it.

### Impact Explanation
This breaks the equality between what the beacon-chain accounting says the block committed to paying (`bid.value`, debited from the builder's tracked balance and recorded in `builder_pending_payments`/`builder_pending_withdrawals`) and what the block actually authorizes at the execution layer (`bid.execution_payment`, which by the spec's own semantics signals a *trusted* EL-level payment). An untrusted, non-self-build builder can smuggle a non-zero `execution_payment` into a canonical, valid block. Since the field is explicitly defined as a flag that indicates a legitimate EL-level payment (as opposed to `value`, which is beacon-chain-Gwei-accounted), a non-zero value slipping through consensus validation is a payment/payload authorization that the accounted portion of the block does not commit to — falling into the "payload or payment applied that the block did not commit to" / "Gwei... paid to a non-owner" impact category.

### Likelihood Explanation
Likelihood depends on whether an implementer's block-import path enforces the p2p gossip rule as if it were a validity rule (many implementations conflate "accept for gossip" and "accept for import"), and whether any out-of-band bid submission (private relay, local builder) is used, which the spec explicitly allows ("The block proposer MAY obtain these signed messages by other off-protocol means" — `specs/gloas/validator.md` lines 201-203). Because the specification text itself omits the check from the canonical state-transition function, this is a genuine spec gap rather than a client implementation bug, and any node importing a block via `state_transition`/`process_execution_payload_bid` alone (without separately replaying gossip validation) is exposed.

### Recommendation
Add an explicit assertion in `process_execution_payload_bid` (specs/gloas/beacon-chain.md) mirroring the gossip check, e.g.:
```python
def process_execution_payload_bid(state: BeaconState, signed_bid: SignedExecutionPayloadBid) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        assert bid.execution_payment == 0  # non-self-builds must not carry a trusted EL payment
        assert is_active_builder(state, builder_index)
        ...
```
This ensures the trust boundary documented in `builder.md` (non-zero `execution_payment` only for self-builds) is enforced as a consensus rule, not merely as a gossip-propagation heuristic.

### Proof of Concept
1. A non-self-build builder constructs a valid `ExecutionPayloadBid` with `builder_index = <external builder>`, a correctly signed BLS signature, `value = X` (satisfying `can_builder_cover_bid`), but sets `execution_payment = Y > 0`.
2. Instead of broadcasting on the `execution_payload_bid` gossip topic (where `validate_execution_payload_bid_gossip` would reject it per `specs/gloas/p2p-interface.md` lines 935-937), the builder sends the signed bid directly to the proposer via a private/relay channel, as explicitly permitted by `specs/gloas/validator.md` lines 201-203.
3. The proposer includes it in `block.body.signed_execution_payload_bid` and produces a block.
4. Every spec-following node runs `process_execution_payload_bid` (specs/gloas/beacon-chain.md lines 2087-2141) on this block. All assertions pass (active builder, sufficient balance for `value`, valid signature); `execution_payment` is never checked and is cached verbatim into `state.latest_execution_payload_bid`.
5. The block is accepted as canonical by all conforming nodes, with a "trusted execution-layer payment" flag set by an untrusted party — a payment authorization the accounted (`value`-based) bookkeeping never reflects.

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
