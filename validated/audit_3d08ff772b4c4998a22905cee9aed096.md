### Title
`should_reevaluate_block` omits a `GloballyRejected` guard, letting a re-proposed block bypass the terminal rejection state via a fresh `BlockInfo` - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`should_reevaluate_block` only refuses re-evaluation when the tracked block is `globally_approved_and_responded()`; it has no symmetric check for `BlockState::GloballyRejected`. Combined with `should_reevaluate_reject_reason` returning `true` for transient/local reasons like `ConnectivityIssues` and `NoSignerConsensus`, a re-proposal of the identical block causes `handle_block_proposal` to build a brand-new `BlockInfo` (state reset to `Unprocessed`), completely discarding the previously persisted `GloballyRejected` verdict and its terminal-state protection.

### Finding Description
The invariant that should hold is: once a signer has locally recorded a block as `GloballyRejected`, that decision is terminal and can never be recounted as an acceptance. This is enforced by `BlockInfo::check_state` in `stacks-signer/src/signerdb.rs:313-329`, which explicitly forbids `GloballyRejected -> LocallyAccepted/LocallyRejected` transitions on a given `BlockInfo` instance [1](#0-0) , and by the doc-stated rule that "Global states are terminal against each other" (`docs/signer-flows.md:135`).

However, `should_reevaluate_block` (`stacks-signer/src/v0/signer.rs:1483-1572`) only special-cases the *accepted* terminal state:
```
if block_info.globally_approved_and_responded() { ... return false; }
if !should_reevaluate_reject_reason(block_info) { ... }
``` [2](#0-1) 

There is no analogous `block_info.state == BlockState::GloballyRejected` short-circuit. `should_reevaluate_reject_reason` (`stacks-signer/src/v0/signer.rs:2706-2739`) treats `RejectReason::ConnectivityIssues(_)` and `RejectReason::NoSignerConsensus` (among others) as re-evaluable, on the premise these are transient/local failures unrelated to block content [3](#0-2) .

When a `BlockInfo` whose `reject_reason` is `ConnectivityIssues`/`NoSignerConsensus` has already been promoted to `GloballyRejected` (via `store_and_process_block_rejection`'s `mark_globally_rejected()` call once other signers' rejection gossip crossed the blocking-minority weight, `stacks-signer/src/v0/signer.rs:2335`) [4](#0-3) , a re-proposal of the *same* block causes `should_reevaluate_block` to return `true` anyway, since it never inspects `state` for the rejected case — only the reject reason.

Back in `handle_block_proposal`, once re-evaluation is allowed, the code discards the old `BlockInfo` entirely and constructs a fresh one:
```
let mut block_info = BlockInfo::from(block_proposal.clone());
``` [5](#0-4) 
This new object starts at `state = Unprocessed` with `reject_reason = None`, so the `check_state` terminal-state guard never fires — the protection is bypassed at the object-construction layer, not defeated through an illegal transition. The fresh object then runs through `check_block_against_state` → `check_block_against_global_state`/`check_block_against_local_state` (`stacks-signer/src/v0/signer.rs:811-999`), neither of which consults the persistent `block_rejection_signer_addrs` table or the prior `GloballyRejected` marking for this `signer_signature_hash` — that bookkeeping lives entirely in `store_and_process_block_rejection`'s `has_reached_consensus()` short-circuit (`stacks-signer/src/v0/signer.rs:2290`), which only guards the *same* in-memory `block_info` instance, not a freshly created one [6](#0-5) .

If the fresh check passes (plausible for `ConnectivityIssues`, since it's a node/RPC-transient failure independent of block content, and for `NoSignerConsensus`, since the protocol-version view may since have been resolved), the block proceeds to submission, validation, pre-commit and — once pre-commit/acceptance weight from this signer's own gossip re-accumulates — signing, via `mark_locally_accepted` / `mark_pre_committed`. The resulting `insert_block` call then overwrites the signerdb row for that `signer_signature_hash`, replacing the previously stored `GloballyRejected` state with `LocallyAccepted`/`PreCommitted`, and the signer emits `BlockResponse::Accepted`.

### Impact Explanation
This breaks the fail-closed safety property that a rejection is never recounted as an acceptance for the same block hash. If enough signers hit this same condition (each independently missed the global-rejection gossip while sitting on a re-evaluable local reject reason), the block could re-accumulate acceptance weight after having already been finalized as rejected by the network, corrupting the signerdb equivocation record and potentially contributing a conflicting/duplicate signature for a block the network already discarded — a chain-safety issue (Critical: rejection recounted as acceptance).

### Likelihood Explanation
Preconditions: (1) this signer's local `BlockInfo.reject_reason` for the block must already be one of the re-evaluable variants (`ConnectivityIssues`, `NoSignerConsensus`, `NoSortitionView`, etc.) — plausible any time the node RPC briefly errors or protocol-version consensus is momentarily unclear; (2) other signers (independently, not the attacker) must have driven the block to `GloballyRejected` weight while this signer missed/hadn't yet processed enough of that gossip. The attacker (a single miner slot) only needs to re-broadcast the identical, already-signed `BlockProposal` — something a miner naturally does when a proposal times out or a "propose again" loop fires — no majority signer control, no auth_token, and no privileged access is required. It is repeatable per re-proposal.

### Recommendation
Add a `GloballyRejected` check to `should_reevaluate_block` mirroring the existing `globally_approved_and_responded()` check, e.g. refuse re-evaluation (or at minimum resend the persisted rejection) whenever `block_info.state == BlockState::GloballyRejected`, regardless of the stored `reject_reason`. Additionally, when constructing the "fresh" `BlockInfo` in the re-evaluation path, preserve/consult the existing persisted terminal state (or re-fetch it from signerdb) before overwriting it via `insert_block`, so a brand-new object can never silently supersede a previously durable `GloballyRejected`/`GloballyAccepted` verdict for the same `signer_signature_hash`.

### Proof of Concept
Rust test in `stacks-signer` driving the v0 signer state machine directly (unit-level, not requiring bitcoind):
1. Construct a `BlockProposal` for block `B` and feed it to `handle_block_proposal`; force `check_block_against_state` to fail with `RejectReason::ConnectivityIssues("...")` (e.g. via existing test hooks like `TEST_REJECT_ALL_BLOCK_PROPOSAL`/mock stacks-client), producing a stored `BlockInfo` with `state = LocallyRejected`, `reject_reason = ConnectivityIssues`.
2. Synthesize `BlockRejection` gossip messages from a blocking-minority-plus-one of other signer addresses for the same `signer_signature_hash`, feeding them through `handle_block_rejection` → `store_and_process_block_rejection`, driving `block_info.state` to `GloballyRejected` (assert via `signer_db.block_lookup(...)`).
3. Re-propose the identical `BlockProposal` `B` again into `handle_block_proposal`.
4. Assert that `should_reevaluate_block` returns `false` (fix) instead of `true` (current bug), and that no subsequent `BlockResponse::Accepted` is ever emitted for `signer_signature_hash` — i.e. after mocking a passing validation response, assert the signerdb row for that hash remains `GloballyRejected` and `send_block_response` is never called with an `Accepted` variant.
