## Title
Multisig `DeleteKey`/`DeleteMember` fails to purge the deleted key's confirmations from *other* pending requests, allowing execution below the configured threshold - ([File: multisig/src/lib.rs], [File: multisig2/src/lib.rs])

### Summary
Both the V1 (`multisig`) and V2 (`multisig2`) contracts confirm a request by comparing the size of a `confirmations` set against `num_confirmations` at call time, without re-validating that every entry in that set still corresponds to a *currently live* signer/member. When a key/member is removed, the cleanup logic only deletes requests that the removed key **originated**, but never scrubs the removed key from `confirmations` sets of *other* pending requests it had already confirmed. Those stale confirmations continue to count toward the threshold, so a request can later execute with fewer live approvals than `num_confirmations` requires.

### Finding Description
`confirm()` decides to execute a request purely from set cardinality: [1](#0-0) [2](#0-1) 

When a member/key is removed via `DeleteMember` (V2) or `DeleteKey` (V1), the cleanup only removes requests **created by** that member/key — it filters by `r.member == member` (V2) / `r.signer_pk == pk` (V1) — and only clears `num_requests_pk`/`num_requests_pk` entries for that signer: [3](#0-2) [4](#0-3) 

Neither routine scans the `confirmations` map to strip the removed key/member from confirmation sets of requests it merely **confirmed but did not create**. `execute_request`'s `DeleteKey`/`DeleteMember` handling (a self-request requiring the same `confirm()` threshold check) never touches unrelated requests' confirmation sets either.

The custody binding that should hold is: *confirmations counted == confirmations from currently-live members*. After a deletion, this diverges: `confirmations counted > confirmations from currently-live members`, because a stale entry from the now-removed key/member remains in the set and is still summed in `confirmations.len() as u32 + 1 >= self.num_confirmations`.

### Impact Explanation
This lets a request execute (e.g., `Transfer`, `AddKey`/`AddMember`, `FunctionCall`, `DeployContract`) with fewer live-member approvals than the contract's own `num_confirmations` policy demands — i.e., "a multisig request executed below threshold," which is explicitly called out as a Critical-severity impact. Funds can move, or a new full-access key/member can be added, without the intended number of currently-trusted parties agreeing, undermining the entire security model that `num_confirmations` is supposed to enforce.

### Likelihood Explanation
Exploitation only requires the normal governance lifecycle of any long-lived multisig: (1) a request is opened and partially confirmed by several members, (2) later — independently — the multisig votes to remove one of those confirming members/keys (a routine key-rotation/offboarding action, not an attack in itself), and (3) the still-pending earlier request is confirmed by a remaining live member. No out-of-band or unprivileged capability is needed beyond what any long-running multisig eventually does (member turnover). The bug is deterministic given standard reachable code paths (`add_request` → `confirm` → `DeleteMember`/`DeleteKey` → `confirm`), so likelihood is high wherever membership changes over the life of the contract while requests are outstanding.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over **all** entries in the `confirmations` map (not just requests created by that member/key) and remove the deleted member's/key's entry from every confirmation set. Alternatively, re-validate at `confirm()` time that every already-recorded confirmation still corresponds to a member in `self.members` (V2) or a valid signer key (V1) before counting it toward the threshold, discarding stale entries lazily.

### Proof of Concept
1. Deploy `multisig2` with 3 members `A`, `B`, `C` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` on a `Transfer` request → `confirmations = {A}`.
3. `B` calls `confirm(request_id)` → `confirmations = {A, B}` (2 < 3, stays pending).
4. Separately, the multisig approves a `DeleteMember{member: B}` request (a normal, fully-threshold-approved action) — `B` is removed from `self.members`, but the pending `Transfer` request from step 2/3 is untouched because it was not *created by* `B`; `confirmations` for it still contains `B`.
5. `C` calls `confirm(request_id)`. `confirmations.len() as u32 + 1 == 3 >= num_confirmations (3)` → the request executes, transferring funds, even though only `A` and `C` are actually live members — one fewer live approval than the policy of 3 requires. [5](#0-4) [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
