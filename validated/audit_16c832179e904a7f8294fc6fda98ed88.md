### Title
Instant-withdraw claims pay unfunded receipts because `claimInstantWithdrawRequest` never matches the receipt to its funded epoch - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug class is a response arriving under a mismatched identifier being treated as the answer to the request. The credit-vault analog lives in `IdleCreditVault.claimInstantWithdrawRequest`: normal withdraw claims are bound to their request epoch (`epochNumber <= lastWithdrawRequest` reverts) and loss/default claims clear per-epoch basis (`withdrawsRequestsByEpoch[user][epoch]`, `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`), but the instant claim path reads only the aggregate `instantWithdrawsRequests[_user]` and pays it in full with no check that the corresponding epoch's receipts were actually funded via `collectInstantWithdrawFunds`. The claim "response" is accepted without matching it to a funded request epoch.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestInstantWithdraw` mints receipt strategy tokens and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `pendingInstantWithdraws` (lines 356-375). Funds only arrive later when the CDO calls `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls underlying (lines 398-403).
- `claimInstantWithdrawRequest` (lines 380-393) burns the full receipt balance and calls `_transferFundedClaim(_user, amount)` with no epoch-maturity check, no `pendingInstantWithdraws` check, and no per-epoch matching. Contrast `_claimFundedWithdrawRequest` (lines 319-350), which reverts while `epochNumber <= lastWithdrawRequest[_user]`, and `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`.
- `_transferFundedClaim` (lines 897-907) guards only `defaultRecoveryReserve`; it does not protect underlying collected for other users' funded normal/loss-adjusted claims (`collectWithdrawFunds`, lines 411-430) or other users' funded instant claims.

The result: a user can request an instant withdraw and immediately claim it before the borrower funds that receipt, spending underlying that was collected to back other users' pending claims. The CDO entrypoint (`IdleCDOEpochVariant.claimInstantWithdrawRequest`, lines 975-979) adds only the `allowInstantWithdraw` flag check — no funding check.

### Impact Explanation
Direct theft/insolvency: an attacker KYC-passes, deposits during the buffer, requests an instant withdraw, and claims the full receipt amount in the same window. The payout comes from the strategy's underlying balance, which at that point contains funds reserved for previously funded withdraw receipts. When those earlier claimants later call `claimWithdrawRequest`, the balance is short by the stolen amount; the last claimants' `_transferFundedClaim` transfers revert (permanent loss for them) or the reserve guard reverts. Loss is bounded by the attacker's deposit size but is repeatable while any funded-but-unclaimed balance exists.

### Likelihood Explanation
Requires only an unprivileged allowed user and an epoch phase where the vault holds funded-but-unclaimed underlying while `allowInstantWithdraw` is enabled — a routine state, since funded receipts are claimable at any later time. No privileged misbehavior needed; sequencing is entirely attacker-controlled between `requestInstantWithdraw`/`claimInstantWithdrawRequest` and the honest `collectInstantWithdrawFunds` call inside `stopEpoch`.

Caveat: I was unable to read the full `stopEpoch`/`getInstantWithdrawFunds` flow in `IdleCDOEpochVariant.sol` to confirm whether the CDO prefunds instant receipts at `startEpoch` (in which case the strategy balance would already hold the backing and the residual attack window is the pre-funding gap only). If instant liquidity is always pulled into the CDO before requests are allowed, this degrades to a per-epoch accounting mismatch rather than theft.

### Recommendation
Bind instant claims to funded epochs the same way default claims are: track funded instant basis per epoch (e.g., decrement `instantWithdrawsRequestsByEpoch`/`instantWithdrawsRequests[_user]` against amounts actually pulled by `collectInstantWithdrawFunds`), or gate `claimInstantWithdrawRequest` on the request's epoch having been funded. Minimally, add an epoch/funding check mirroring `epochNumber <= lastWithdrawRequest` or assert `pendingInstantWithdraws` coverage before paying the aggregate.
