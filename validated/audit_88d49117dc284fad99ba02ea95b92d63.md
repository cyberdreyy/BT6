## Title
Deleting a multisig member does not purge that member's stale confirmations from pending requests, allowing a request to execute with fewer live-member confirmations than `num_confirmations` requires - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only deletes the outstanding *requests* that were originally created by the deleted member, and clears that member's `num_requests_pk` entry. It never scans other members' pending requests to remove the deleted member's `confirm()` votes. Because `confirm()` counts entries in the `confirmations` `HashSet<String>` (keyed by serialized member) without checking whether each entry is still a current member, a confirmation cast by a member before removal continues to count toward the `num_confirmations` threshold after that member is deleted.

### Finding Description
`confirm()` computes whether a request should execute purely from the *size* of the stored confirmation set: [1](#0-0) 

`delete_member` removes only requests keyed to the member being deleted (`r.member == member`, i.e. requests the member itself originally created) and clears `num_requests_pk` for that member; it never removes the member's entries from the `confirmations` sets of requests created by *other* members: [2](#0-1) 

`current_member()` is only used to authorize the *caller* of `confirm`/`add_request`, and is never re-applied to already-stored confirmations: [3](#0-2) 

The intended invariant is: *a request executes only once `num_confirmations` distinct **current** members have confirmed it* (confirmations counted == live members who confirmed). The bug breaks this equality: `confirmations.len()` can include serialized-member strings for accounts/keys that are no longer in `self.members`, so `confirmations.len() >= num_confirmations` no longer implies `num_confirmations` live members approved the action.

Concrete scenario:
1. Multisig has members `{A, B, C, D}`, `num_confirmations = 3`.
2. Member `B` creates request `R` (e.g. a `Transfer` or `FunctionCall`) via `add_request`.
3. Member `C` calls `confirm(R)` — `confirmations[R] = {C}` (1 of 3).
4. Members execute a separate, fully-confirmed `DeleteMember` request removing `C` (e.g. because `C`'s key was compromised or `C` left the org). `delete_member` only cleans up requests where `r.member == C` (requests `C` created); `R` was created by `B`, so `confirmations[R] = {C}` is left untouched. `C` is now removed from `self.members`.
5. Members `A` and `D` (2 more, both still live) call `confirm(R)`. `confirmations[R]` grows to `{C, A}` then `{C, A, D}` — reaching `3 >= num_confirmations`, and `R` executes.

Only 2 genuinely current members (`A`, `D`) approved `R`, yet the contract treats it as satisfying a 3-of-4 threshold, because the stale vote from the removed member `C` is still counted.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." An arbitrary action authorized by the multisig (`Transfer`, `FunctionCall`, `AddKey`/full-access-key grant, `DeployContract`, further `AddMember`/`DeleteMember`) can be pushed through with fewer live confirmations than the configured `num_confirmations`, effectively lowering the real security threshold of the account any time membership changes while requests are outstanding. This can lead to unauthorized fund transfers or unauthorized code/key changes on the multisig account.

### Likelihood Explanation
Likelihood is Low/Medium: it requires (a) an outstanding, partially-confirmed request from one member and (b) a subsequent, legitimate `DeleteMember` action removing a *different* member who had confirmed that outstanding request (e.g. routine key rotation, offboarding, or key-compromise response). This is a realistic multisig lifecycle event (rotating out a member), not an exotic attacker-controlled setup, and no foundation/owner/redeploy assumption is required — it only requires normal multisig governance operations that the contract's own members can already perform.

### Recommendation
When deleting a member, `delete_member` should also strip that member's string from `confirmations` of every other outstanding request (not just delete requests the member itself created), e.g.:
```rust
for (request_id, mut confirmations) in self.confirmations.iter() {
    if confirmations.remove(&member.to_string()) {
        self.confirmations.insert(&request_id, &confirmations);
    }
}
```
Alternatively, `confirm()` should filter `confirmations` against `self.members` before comparing its length to `num_confirmations`, so stale (non-member) confirmations never count toward the threshold.

### Proof of Concept
Given the existing test harness (`multisig2/src/lib.rs` tests module), the scenario above can be reproduced by:
1. `MultiSigContract::new(members(), 3)` with 4 members.
2. Have member `B` call `add_request` for a `Transfer`.
3. Have member `C` call `confirm(request_id)` (confirmations = 1).
4. Have members execute a separate `DeleteMember{ member: C }` request (fully confirmed by 3 members), removing `C` from `self.members`.
5. Assert `get_confirmations(request_id)` still contains `C`'s serialized identity (`assert!(c.get_confirmations(request_id).contains(&member_c_string))`), proving the stale entry survives removal.
6. Have members `A` and `D` call `confirm(request_id)`; observe the request executes (`requests.len() == 0`, promise scheduled) after only 2 confirmations from currently-live members plus the stale one from removed member `C`. [2](#0-1) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

        }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
