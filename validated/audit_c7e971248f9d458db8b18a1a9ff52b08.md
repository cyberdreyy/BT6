### Title
Gateway `savedCallbacks` map keyed only by attacker-controlled `MessageId` allows callback overwrite / cross-user response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each caller's `handlers.Callback` in `h.savedCallbacks[msg.Body.MessageId]` without checking whether an entry for that `MessageId` already exists, and `MessageId` is a fully attacker-controlled string with no binding to the sender's identity. Any unauthenticated signer can register a request whose `MessageId` collides with another caller's still-pending request, silently overwriting that caller's callback so the DON's eventual response is delivered to the attacker instead of the original caller.

### Finding Description
`api.MessageBody.MessageId` is an arbitrary client-supplied string (max 128 bytes) that is only length/suffix validated in `Message.Validate()`; it is not derived from the sender's address, a nonce, or any per-sender namespace. [1](#0-0) [2](#0-1) 

When a signed gateway message reaches `HandleLegacyUserMessage`, after basic payload/timestamp/method validation, the handler unconditionally writes the caller's callback into the shared map keyed purely by `msg.Body.MessageId`: [3](#0-2) 

There is no check for an existing entry before this assignment. Later, when a DON node responds, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId`, then invokes whichever callback is currently registered: [4](#0-3) 

Exploit flow: caller A (any identity, e.g. a legitimate/higher-privileged user) sends a validly signed `web_api_trigger` message with `MessageId = "X"`; the gateway registers A's callback and fans the request out to DON members. Before the DON responds (window is up to `CallbackMaxAgeSec`, default 120s), attacker B — an unrelated, unprivileged signer — sends their own validly signed message reusing the same `MessageId = "X"`. Nothing in `HandleLegacyUserMessage` rejects the collision or namespaces the key by sender; B's callback overwrites A's entry at line 412. When the DON later responds to the original request (which still carries `MessageId = "X"`), `handleWebAPITriggerMessage` delivers the DON's response to B's callback, and A's `callback.Wait()` in `gateway.ProcessRequest` times out and never receives a response. [5](#0-4) 

The confidential-relay handler in the same package explicitly guards against this class of bug by rejecting duplicate request IDs ("request ID already exists"), demonstrating this protection is a known/expected control that is missing here: [6](#0-5) 

### Impact Explanation
This is cross-user response confusion: an unprivileged, unauthenticated (from the node's perspective) signer can hijack another caller's pending gateway response by simply reusing that caller's `MessageId`. The victim's DON response (which may contain sensitive trigger/action results intended only for them) is delivered to the attacker's callback instead, while the victim silently times out. This matches the "attacker-controlled data returned to another user" / cross-user data confusion impact class called out in the rules.

### Likelihood Explanation
Preconditions: attacker needs only a valid signing key (any address) — no DON/gateway role, no privileged credential — and must know or guess the victim's in-flight `MessageId` within the callback lifetime window (default 120 seconds, configurable via `CallbackMaxAgeSec`). This is fully repeatable and requires no race beyond submitting a second signed request before the DON replies to the first; predictable or fixed `MessageId` schemes used by legitimate integrators (sequential IDs, idempotency keys, or well-known constants) make guessing practical.

### Recommendation
Reject `HandleLegacyUserMessage` requests whose `MessageId` already has a live entry in `h.savedCallbacks` (returning a duplicate-ID error, mirroring the confidential-relay handler's behavior), or namespace the `savedCallbacks` key by `(Sender, MessageId)` so collisions across different senders cannot overwrite each other's callbacks.

### Proof of Concept
1. In `core/services/gateway/handlers/capabilities/handler_test.go`, extend `setupHandler` test to create two distinct signing keys (`keyA`, `keyB`) and two `handlers.Callback` spies (`cbA`, `cbB`) via `hc.NewCallback()`.
2. Build `msgA := triggerRequest(t, keyA, ..., messageID="X", ...)` and call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)`; assert `h.savedCallbacks["X"]` is set.
3. Build `msgB := triggerRequest(t, keyB, ..., messageID="X", ...)` (same `MessageId`, different signer) and call `handler.HandleLegacyUserMessage(ctx, msgB, cbB)`.
4. Assert `h.savedCallbacks["X"].Callback == cbB` (overwritten), i.e., `cbA`'s entry was replaced.
5. Simulate a DON node response for `MessageId="X"` via `handler.HandleNodeMessage(ctx, resp, nodeAddr)` and assert only `cbB.Wait(ctx)` receives the response payload while `cbA.Wait(ctx)` times out/never resolves — proving the attacker (`cbB`) received the response intended for the original caller (`cbA`).

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
