Session ID is a cryptographically random 32-byte ID, so even though the code creates a dangling `oidc_sessions` row, the attacker cannot feasibly guess it and the `Set-Cookie` header set later (after `c.String` already flushed a 500 response) would not reliably reach the client. However, the core control-flow defect the question asks about is real and independently verifiable in the code, regardless of that secondary nuance.

### Title
Missing `return` after failed email-claim type assertion allows session creation to continue for empty/invalid email - ([File: core/sessions/oidcauth/oidc.go])

### Summary
In `handleTokenExchange`, when the `email` claim from the verified OIDC ID token is absent or not a string, the code logs an error and writes an error response via `c.String` at line 229 but does not `return`, so execution falls through and proceeds to derive a role and insert a new row into `oidc_sessions` with an empty `user_email` and continues attempting to establish/save a session. This violates the intended fail-closed behavior of the authentication handler.

### Finding Description
At [1](#0-0)  the handler performs `email, ok := claims["email"].(string)` and on failure only logs and writes an error string, without a `return` statement, unlike every other validation failure in the same function (e.g. the `id_token` extraction failure at [2](#0-1)  and the claim-parsing failure at [3](#0-2) , which both `return` immediately). Because of this, execution proceeds to `IDClaimsToUserRole` and then inserts a new `oidc_sessions` row keyed by `strings.ToLower(email)` (empty string) and the derived role at [4](#0-3) , calls `oi.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, ...)` at line 262, and attempts to set/save the gin session cookie at [5](#0-4) , finally returning a success `ExchangeTokenResponse{Success: true}` JSON body at [6](#0-5) . This means an ID token that passes signature verification (`idToken.Verify`) but that lacks an `email` claim (or has it as a non-string type) still results in a persisted, role-bearing session record and a code path that behaves as a successful login, rather than aborting.

### Impact Explanation
This is an authentication-soundness / fail-open control-flow defect (CWE-705 Incorrect Control Flow Scope): a validation failure branch does not halt processing, letting the function continue to grant/attempt to grant an authenticated session and role for a user identity that failed validation. Combined with `IDClaimsToUserRole`, the role granted depends purely on group claims independent of the (missing/invalid) email, so a caller whose OIDC token satisfies an elevated role claim (e.g., Admin) but omits `email` still produces an `oidc_sessions` row with that elevated role and an empty email, and the code proceeds down the "success" path (audit log `AuthLoginSuccessNo2FA`, attempted cookie `Save()`, `Success: true` JSON) instead of aborting. Practical delivery of the session cookie is impacted by the earlier `c.String` call already committing HTTP headers, which reduces (but does not eliminate, depending on server/framework buffering behavior) the chance the `Set-Cookie` header reaches the client in a given deployment; the DB-level and control-flow soundness violation exists regardless.

### Likelihood Explanation
Exploitation requires the attacker to complete a valid OAuth2 code exchange and produce (or replay) an ID token that passes provider signature verification but whose `email` claim is missing or of the wrong JSON type — achievable by a user of a self-service/misconfigured OIDC provider, a compromised/malicious upstream IdP, or a token-replay scenario where a token issued for a different scope (without `email` scope) is submitted. No admin/host access is required; only the ability to complete the standard `/oidc-exchange` flow. It does not require compromising the node itself.

### Recommendation
Add an explicit `return` immediately after writing the error response in the `email` type-assertion failure branch, matching the pattern used elsewhere in the function:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```

### Proof of Concept
Go handler-level integration test plan:
1. Stand up `oidcAuthenticator` with a stubbed `oidc.Provider`/verifier that returns a valid-signature ID token whose claims map contains the configured group claim name with an admin-role group value, but omits the `email` key entirely (or sets it to a non-string, e.g. `123`).
2. Drive `handleTokenExchange` via a gin test router: perform `/oidc-login` to seed `state` in session, then POST `/oidc-exchange` with matching `state` and a `code` that the stubbed `oauth2Config.Exchange`/verifier will accept.
3. Assert that no row is inserted into `oidc_sessions` (query `SELECT count(*) FROM oidc_sessions`) — expected to fail on current code since a row with `user_email=''` and the admin role is inserted.
4. Assert the HTTP response terminates with the email-failure error and does not proceed to set `ExchangeTokenResponse{Success:true}` or call `ginSession.Save()`/`audit.AuthLoginSuccessNo2FA`.
