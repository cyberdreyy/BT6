### Title
Multisig executes requests below the live confirmation threshold because stale confirmations from removed members are not purged - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` decides whether a request has reached `num_confirmations` by counting entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` map for that request [1](#0-0) . `delete_member`, however, only purges confirmations for requests that the removed member *originally proposed* (`r.member == member`); it never scans other pending requests to strip confirmations the removed member previously cast as a *confirmer* [2](#0-1) . As a result, a confirmation recorded by a member who is later removed from `self.members` still counts toward the K-of-N threshold on any request they were not the original proposer of, letting a request execute with fewer than K *live* approving members.

### Finding Description
The intended invariant is: `confirmations_counted_for_request == number_of_currently_authorized_members_who_approved_it`. The contract instead computes `confirmations.get(&request_id).len() + 1 >= self.num_confirmations` purely from a persisted string set that is never revalidated against the live `members` set at confirm time [3](#0-2) .

`assert_valid_request`, called at the top of `confirm`, only checks that the *caller* (predecessor/signer) is currently a member and that the request/confirmations record exists — it does not re-validate that every account already present in the stored `confirmations` set is still a member [4](#0-3) .

`delete_member`'s cleanup logic is scoped incorrectly: it filters `self.requests` for `r.member == member` (i.e., requests *proposed by* the removed member) and clears confirmations only for those, then removes the member from `self.members` [5](#0-4) . It does not iterate `self.confirmations` to strip the removed member's string entry from every other pending request they had merely confirmed. This is structurally the same class of bug as the CF check-before-mint report: a security-relevant threshold (`num_confirmations` in the analog, `CF > warningCF` in the original) is checked using state that can silently diverge from live/ current reality (removed-member confirmations lingering, vs. mint amount pushing CF far past the warning boundary) — the check is evaluated against stale/pre-action data instead of being reconciled against the current authorized state before the privileged action (`execute_request`) fires.

### Impact Explanation
This allows a `MultiSigRequestAction` (including `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc.) to be executed by `execute_request` [6](#0-5)  with fewer than `num_confirmations` currently-authorized members actually agreeing, because one or more of the counted confirmations belongs to an account that has since been removed via `DeleteMember`. This directly matches the "Critical" impact category: a multisig request executed below threshold, enabling unauthorized transfer of NEAR or execution of privileged actions on the multisig account.

### Likelihood Explanation
Requires: a pending request that has partial confirmations from an account that is subsequently removed as a member (a normal, expected multisig operational event — e.g. compromised key rotation, member offboarding), followed by confirmation from another live member. This is a realistic operational sequence for any long-lived multisig with pending, not-yet-executed requests, and does not require any privileged action beyond normal `confirm`/`DeleteMember` usage by existing members.

### Recommendation
When counting confirmations in `confirm`, filter the stored confirmation set to only members currently present in `self.members` (or actively prune confirmations for all pending requests, not just those proposed by the removed member, inside `delete_member`/`add_member`-triggered membership changes) before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}`, `num_confirmations = 2`.
2. `A` calls `add_request` to propose a `Transfer` request `R` (self-proposed, not confirmed).
3. `B` calls `confirm(R)`; since `confirmations.len()+1 == 1 < 2`, it is stored: `confirmations[R] = {B}` [7](#0-6) .
4. The group legitimately executes a separate `DeleteMember { member: B }` request (2-of-3 confirmed) to remove `B`. `delete_member` only clears confirmations for requests where `r.member == B` (requests B proposed); `R` was proposed by `A`, so `confirmations[R] = {B}` is left intact [5](#0-4) .
5. `A` (or `C`) now calls `confirm(R)`. `confirmations.len() + 1 == 2 >= num_confirmations (2)`, so `execute_request` fires the `Transfer` [8](#0-7) , even though only one currently-live member (`A`) actually approved it — the second "confirmation" came from `B`, who is no longer a member.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
