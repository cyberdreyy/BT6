### Title
Permanent Denial-of-Service via Lamport Pre-Funding of Deterministic Account Addresses Before `CreateAccount` - (File: `programs/system/src/system_processor.rs`)

### Summary
Any unprivileged user can send lamports (via a plain `SystemInstruction::Transfer`) to a deterministic, not-yet-created account address (e.g., a PDA or a keypair address whose pubkey is already known/computed off-chain) before the legitimate program executes `SystemInstruction::CreateAccount` for it. Because `create_account` unconditionally rejects any destination account with `lamports > 0`, this "griefing" transfer permanently blocks the account from ever being created at that fixed address, mirroring the Notional fCash bug class: sending something to a deterministic address before the "real" initialization logic runs, later causing initialization to always fail.

### Finding Description
The system program's `create_account` handler bails out whenever the destination account already holds any lamports, regardless of who sent them: [1](#0-0) 

Because Solana account addresses derived via `Pubkey::create_with_seed`/`find_program_address`, or simply generated ahead of time off-chain, are fully deterministic and public before the account is actually created, any third party can front-run the intended `CreateAccount` CPI/instruction with a trivial `SystemInstruction::Transfer` of even 1 lamport to that address. From that point forward, every attempt by the legitimate program/user to run `SystemInstruction::CreateAccount` targeting that address will hit the `to.get_lamports() > 0` check and return `SystemError::AccountAlreadyInUse`, exactly as validated by the existing test: [2](#0-1) 

This is the direct on-chain analog of the Notional report: a malicious actor sends something to a deterministically-computable address before the legitimate "deployment"/initialization step runs; afterward, the legitimate initialization logic unconditionally reverts because it now observes unexpected pre-existing state at that address, permanently blocking the operation ("minting"/account creation) that depends on that address being freshly created.

Agave itself acknowledges this exact bug class: it recently introduced `SystemInstruction::CreateAccountAllowPrefund`, gated behind the `create_account_allow_prefund` feature, specifically to allow accounts that were prefunded with lamports before creation to still be initialized successfully: [3](#0-2) [4](#0-3) 

However, this new instruction is strictly opt-in — it requires the calling program to explicitly switch from `system_instruction::create_account` to the new `create_account_allow_prefund` API, and requires the network-wide feature to be activated. The vast majority of existing and future deployed programs that still call the standard `create_account`/`create_account_with_seed` path (via CPI, as generated by `solana-program`'s `system_instruction::create_account`) remain fully exposed to this front-running/pre-funding griefing vector.

### Impact Explanation
This is a loss-of-availability bug matching the judged severity of the original report: no funds are stolen or lost (the griefed lamports actually increase the account's balance), but any protocol relying on deterministic addresses (vaults, escrow accounts, associated-account-style PDAs, staking/derivative wrapper accounts, etc.) can be permanently prevented from initializing that specific account once an attacker front-runs it with a 1-lamport transfer. Because the address is fixed by design (seed-derived or otherwise pre-announced), the legitimate party cannot simply pick a new address to route around the block — the specific intended account becomes permanently unusable for its designed purpose, which can break higher-level protocol invariants (e.g., a protocol that assumes address-to-account correspondence for asset custody) exactly as in the referenced Notional report.

### Likelihood Explanation
The attack is unprivileged, requires no special access, and costs the attacker only the ability to send a trivial `SystemInstruction::Transfer` (a single lamport) plus normal transaction fees. Any address that can be predicted ahead of time — which is inherent to PDA design and to many UX flows that precompute a keypair's pubkey before submitting the creation transaction — is a valid target. This is a well-known "gotcha" in the Solana ecosystem, evidenced by Agave itself shipping a dedicated mitigation (`CreateAccountAllowPrefund`) for it, confirming both that the underlying `create_account` behavior is genuinely exploitable and that adoption of the fix is optional and incomplete across the ecosystem.

### Recommendation
- Encourage/require programs to migrate to `SystemInstruction::CreateAccountAllowPrefund` (once its feature is activated) wherever they create accounts at deterministic addresses that could be observed/front-run ahead of time.
- Consider extending the fix so the ordinary `CreateAccount`/`CreateAccountWithSeed` paths also tolerate a lamports-only "prefund" without requiring a distinct opt-in instruction, since that is the least-privileged reachable state a griefer can create (they cannot write data or change owner without another program's cooperation).
- Document the caveat prominently in SDK-level `system_instruction::create_account` docs so downstream program authors are aware of the DoS class before this feature is universally adopted.

### Proof of Concept
1. Off-chain, compute the target account address ahead of time (e.g., a PDA via `find_program_address`, or simply observe a not-yet-submitted `CreateAccount` transaction's destination pubkey in the mempool/via QUIC ingest).
2. Submit an ordinary `SystemInstruction::Transfer` of 1 lamport to that address before the legitimate `CreateAccount` transaction lands.
3. When the legitimate transaction executes `create_account`, the check at [5](#0-4)  observes `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, permanently failing that specific `CreateAccount` invocation and, by extension, any retry using the identical address — reproduced by the repository's own `test_create_already_in_use` test case at [2](#0-1) .

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
