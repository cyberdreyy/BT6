### Title
Float-based stake-threshold rounding lets a single vote falsely cross optimistic-confirmation / duplicate-confirmation thresholds when total epoch stake is small - (File: core/src/consensus/vote_stake_tracker.rs)

### Summary
`VoteStakeTracker::add_vote_pubkey` computes each stake threshold as `(total_stake as f64 * threshold) as u64` and then checks whether the newly accumulated stake crosses that computed integer boundary. [1](#0-0) 
When `total_stake` is small, `threshold_stake` can truncate to `0`, so a single vote (`old_stake <= 0 && 0 < new_stake`) will immediately report the threshold as "reached" regardless of the actual configured fraction (e.g. `VOTE_THRESHOLD_SIZE`, `DUPLICATE_THRESHOLD`, or the supermajority threshold used for optimistic confirmation). This directly mirrors the reported bug class: a percentage/bps-style calculation (`stake * fraction`) that rounds down to zero when the "total" quantity is low, causing a threshold check that is supposed to gate quorum/proposal-like decisions to be trivially satisfiable.

### Finding Description
`VoteStakeTracker` is the primitive used by `cluster_info_vote_listener.rs` to decide when accumulated vote stake for a bank/slot crosses configured thresholds (used for duplicate-confirmed and optimistic-confirmation signaling). [2](#0-1) 
The core arithmetic is:
```rust
let threshold_stake = (total_stake as f64 * threshold) as u64;
old_stake <= threshold_stake && threshold_stake < new_stake
``` [1](#0-0) 
For any `threshold < 1.0`, if `total_stake` is small enough that `total_stake as f64 * threshold` rounds down below `1`, `threshold_stake` becomes `0`. In that state, the very first non-zero `stake` added (`old_stake = 0`, `new_stake = stake > 0`) satisfies `0 <= 0 && 0 < new_stake`, marking the threshold as newly reached — even though the vote represents nowhere near the intended fraction of `total_stake`. This is functionally identical to the reported `bps2Uint()` rounding-to-zero issue: a percentage-of-total computation that silently degenerates to "any nonzero amount passes" when the total is small.

The unit test in the same file only exercises `total_epoch_stake = 10`, which is large enough relative to the thresholds tested (`0.0` and `VOTE_THRESHOLD_SIZE`) to avoid the truncation-to-zero edge case, so the rounding hazard is not covered. [3](#0-2) 

### Impact Explanation
If total active stake for an epoch/bank is low (e.g., very early network bootstrap, a small permissioned/test cluster, or a heavily stake-concentrated/degraded cluster where `total_stake` used in this calculation is small), a single or a few validator votes could cause `check_vote_stake_thresholds`-style consumers (duplicate-confirmed / optimistic-confirmation signaling in `cluster_info_vote_listener.rs`) to falsely believe a supermajority-like threshold was crossed. This can lead to premature/incorrect duplicate-confirmed or optimistically-confirmed status being reported for a slot, which downstream consumers (e.g., commitment reporting, RPC clients, or components relying on `optimistic_confirmation_verifier.rs`) may treat as a strong finality signal it does not actually represent — a consensus-signal integrity issue rather than a hard divergence, but it undermines the security guarantee the threshold is meant to provide.

### Likelihood Explanation
Likelihood is low-to-moderate and configuration-dependent: on a large, healthy mainnet-scale cluster with high total stake, `total_stake as f64 * threshold` will not truncate to zero for the standard threshold constants. However, the code path is reachable without any privileged access — it is driven purely by ordinary validator votes ingested via gossip/vote listener — and the risk is concrete during network bootstrap, on small test/private clusters, or in any deployment where `total_stake` passed into `VoteStakeTracker` is small, matching exactly the "early stage, low total voting power" scenario described in the source report.

### Recommendation
Replace the floating point `(total_stake as f64 * threshold) as u64` computation with an integer/rational computation that avoids truncation-to-zero, or explicitly guard against `threshold_stake == 0` when `threshold > 0.0` (e.g., round up, or require `threshold_stake >= 1` before treating any nonzero vote as crossing a positive threshold). Additionally, add tests exercising `total_stake` values small enough to trigger truncation to confirm the fix.

### Proof of Concept
1. Construct a `VoteStakeTracker` with `total_stake = 2` and `thresholds_to_check = [0.67]` (mirrors `VOTE_THRESHOLD_SIZE`-style fraction).
2. `threshold_stake = (2.0 * 0.67) as u64 = (1.34) as u64 = 1`. Add a vote with `stake = 1`: `old_stake = 0`, `new_stake = 1`; check `old_stake(0) <= threshold_stake(1) && threshold_stake(1) < new_stake(1)` → `1 < 1` is false, so this particular case does not trigger — but with `total_stake = 1` (or any value where `total_stake * threshold < 1`), `threshold_stake = 0`, and any vote with `stake >= 1` satisfies `0 <= 0 && 0 < new_stake`, immediately reporting the 67%-threshold as reached from a single voter holding a tiny fraction of total stake.
3. This can be directly reproduced by calling `VoteStakeTracker::add_vote_pubkey(pubkey, 1, 1, &[0.67])` and observing `reached_threshold_results == [true]` despite only 100% (or, more generally, an arbitrarily small fraction when scaled) of a trivially small `total_stake` having voted — demonstrating the threshold rounds to zero and is bypassed.     pub fn add_vote_pubkey(
        &mut self,
        vote_pubkey: Pubkey,
        stake: u64,
        total_stake: u64,
        thresholds_to_check: &[f64],
    ) -> (Vec<bool>, bool) {
        let is_new = !self.voted.contains(&vote_pubkey);
        if is_new {
            self.voted.insert(vote_pubkey);
            let old_stake = self.stake;
            let new_stake = self.stake + stake;
            self.stake = new_stake;
            let reached_threshold_results: Vec<bool> = thresholds_to_check
                .iter()
                .map(|threshold| {
                    let threshold_stake = (total_stake as f64 * threshold) as u64;
                    old_stake <= threshold_stake && threshold_stake < new_stake
                })
                .collect();
            (reached_threshold_results, is_new)
        } else {
            (vec![false; thresholds_to_check.len()], is_new)
        }
    }

    #[test]
    fn test_add_vote_pubkey() {
        let total_epoch_stake = 10;
        let mut vote_stake_tracker = VoteStakeTracker::default();
        for i in 0..10 {
            let pubkey = solana_pubkey::new_rand();
            let (is_confirmed_thresholds, is_new) = vote_stake_tracker.add_vote_pubkey(
                pubkey,
                1,
                total_epoch_stake,
                &[VOTE_THRESHOLD_SIZE, 0.0],
            );
            let stake = vote_stake_tracker.stake();
            let (is_confirmed_thresholds2, is_new2) = vote_stake_tracker.add_vote_pubkey(
                pubkey,
                1,
                total_epoch_stake,
                &[VOTE_THRESHOLD_SIZE, 0.0],
            );
            let stake2 = vote_stake_tracker.stake();

            // Stake should not change from adding same pubkey twice
            assert_eq!(stake, stake2);
            assert!(!is_confirmed_thresholds2[0]);
            assert!(!is_confirmed_thresholds2[1]);
            assert!(!is_new2);
            assert_eq!(is_confirmed_thresholds.len(), 2);
            assert_eq!(is_confirmed_thresholds2.len(), 2);

            // at i == 6, the voted stake is 70%, which is the first time crossing
            // the supermajority threshold
            if i == 6 {
                assert!(is_confirmed_thresholds[0]);
            } else {
                assert!(!is_confirmed_thresholds[0]);
            }

            // at i == 6, the voted stake is 10%, which is the first time crossing
            // the 0% threshold
            if i == 0 {
                assert!(is_confirmed_thresholds[1]);
            } else {
                assert!(!is_confirmed_thresholds[1]);
            }
            assert!(is_new);
        }
    }
