### Title
Unprivileged front-running/squatting of the deterministic lockup address strips foundation vesting oversight - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the lockup account id deterministically from only `owner_account_id` (`sha256(owner_account_id)` + factory suffix), and lets any caller supply `vesting_schedule` and thus control whether `foundation_account_id` is set. Because there is no restriction on who may call `create` for a given `owner_account_id`, an unprivileged attacker can pre-emptively deploy the lockup at `victim.near`'s deterministic address with `vesting_schedule = None`, permanently occupying that address with `VestingInformation::None` and no foundation oversight before the legitimate vesting grant is ever created there.

### Finding Description
The broken binding is:
`lockup_information/vesting_information.foundation_account_id persisted at sha256(owner_account_id).factory == the oversight arrangement the real grantor and foundation agreed for owner_account_id`.

The lockup address is computed purely from `owner_account_id`: [1](#0-0) 

`create` is `#[payable]` with no caller/owner check — any account can invoke it for any `owner_account_id` as long as it attaches `MIN_ATTACHED_BALANCE`: [2](#0-1) 

The caller also fully controls `vesting_schedule`, and `foundation_account_id` is derived solely from whether `vesting_schedule.is_some()`: [3](#0-2) 

Exploit flow: the attacker calls `create(owner_account_id="victim.near", ..., vesting_schedule=None, ...)` before the real grantor/foundation does. This deploys a contract at `sha256("victim.near")[..20].factory` via `Promise::new(lockup_account_id).create_account()...`: [4](#0-3) 

Because `vesting_schedule=None`, the deployed lockup's `LockupArgs.foundation_account_id` is `None`, so the lockup contract stores `VestingInformation::None` — permanently removing foundation termination rights at that specific address. When the legitimate grantor later attempts the real call with `vesting_schedule=Some(...)` for the same `owner_account_id`, `create_account()` on the already-existing account fails, the whole promise chain fails, and `on_lockup_create` simply refunds the deposit to whoever called it: [5](#0-4) 

No guard (`assert_owner`, `assert_called_by_foundation`, or any allowlist keyed on `owner_account_id`) exists to prevent an arbitrary caller from claiming any `owner_account_id` first. The lockup contract's own `new()`/init would also reject re-initialization only because `create_account` already failed at the NEAR runtime level — the vulnerability is not in a state-overwrite, but in that the deterministic, permanent address is squatted with attacker-chosen parameters that were never authorized by the real grantor.

### Impact Explanation
The address permanently associated with `victim.near`'s lockup ends up deployed with `VestingInformation::None` chosen by an attacker rather than the parameters the real grantor/foundation intended. This matches the Critical category "a lockup deployed with parameters its rightful creator never chose." If any sponsor is later induced to fund that address believing it is `victim.near`'s official vesting lockup (a reasonable expectation given the address is deterministically tied to the owner), the foundation has no termination/clawback right, and unvested tokens sent there can never be recovered by the foundation. This is repeatable against any account name not yet squatted, at the attacker's discretion, at any time before the legitimate grantor acts.

### Likelihood Explanation
The attacker only needs to know (or predict) the intended owner account name (e.g. `victim.near`) and attach `MIN_ATTACHED_BALANCE` (3.5 NEAR) — a fully public, unauthenticated call requiring no privileged role, no victim key, and no owner/foundation status. This is cheap, fully attacker-controlled, and can be executed proactively for any future/expected grantee name.

### Recommendation
Restrict which accounts may create a lockup for a given `owner_account_id` — e.g. require `assert_called_by_foundation()`/an allowlist check, or require the transaction's `predecessor_account_id` (or a signed authorization from it) to match `owner_account_id`, before allowing `create` to proceed; alternatively, derive the lockup address from a foundation-issued nonce/allowlist entry rather than purely from `owner_account_id`, so the address cannot be squatted ahead of the authorized grant.

### Proof of Concept
```rust
#[test]
fn test_omitting_vesting_schedule_strips_foundation_oversight() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker (not the foundation, not victim, not owner) squats victim.near's
    // deterministic lockup address with vesting_schedule = None.
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // stands in for "victim.near"
        lockup_duration,
        None,
        None,   // vesting_schedule = None, attacker-chosen
        None,
        None,
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    contract.on_lockup_create(
        lockup_account(),
        ntoy(30).into(),
        String::from("attacker.near"),
    );

    // Assert: foundation_account_id sent in LockupArgs is None (not Some(foundation)),
    // i.e. VestingInformation::None will be persisted at victim.near's deterministic
    // lockup address, even though the real grant required Some(VestingHash(...)) with
    // foundation oversight. Contrast with test_create_lockup_with_vesting_success
    // where vesting_schedule=Some(...) yields foundation_account_id=Some(foundation).
}

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
