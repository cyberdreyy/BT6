### Title
View-role user can read a bridge's plaintext `OutgoingToken` credential via GET /v2/bridge_types - ([File: core/web/presenters/bridges.go])

### Summary
`BridgeTypesController.Index` and `.Show` build API responses with `presenters.NewBridgeResource`, which copies the bridge's persisted `OutgoingToken` field verbatim into the JSON-serialized `BridgeResource.OutgoingToken` attribute without redaction or an `omitempty`/role check. Because these are `GET` routes reachable by any authenticated session (including `UserRoleView`), a view-only user can read the bridge's outgoing authentication token for any configured bridge.

### Finding Description
`BridgeType` (the persisted model) stores `IncomingTokenHash` (hashed, safe) but stores `OutgoingToken` in plaintext: [1](#0-0) 

`presenters.NewBridgeResource` copies this plaintext value directly into the response resource: [2](#0-1) 

Note the JSON tags: `IncomingToken` has `omitempty` and is only ever populated by the `Create` handler (using the ephemeral plaintext returned once from `bridges.NewBridgeType`), so it correctly does not leak on `Index`/`Show`. However `OutgoingToken` has **no** `omitempty` and is set unconditionally from the persisted `bridges.BridgeType.OutgoingToken` for every resource construction — including in `Index` and `Show`: [3](#0-2) [4](#0-3) 

These two handlers are wired to the router without any privileged-role gate beyond generic session authentication, so a view-role session (or any role sufficient to hit the authenticated `/v2/...` group) can call `GET /v2/bridge_types` (paginated list, via `paginatedRequest` wrapper) or `GET /v2/bridge_types/:BridgeName` and receive the plaintext `outgoingToken` attribute for every bridge in the response body. This is confirmed by the existing test fixture `TestBridgeResource`, which shows `outgoingToken` present in the marshaled JSON attributes with no incoming-token gating: [5](#0-4) 

Unlike the `IncomingToken` (which is validated/authenticated via a hash comparison in `AuthenticateBridgeType` and never persisted in plaintext), the `OutgoingToken` is a bearer credential the node itself sends to the external bridge adapter when delivering job run callbacks — it is a genuine secret whose disclosure lets a low-privileged view-role user impersonate the node when calling back into the external adapter, or otherwise misuse the bridge's trust relationship.

### Impact Explanation
A view-role user (lowest authenticated privilege, `UserRoleView`) gains disclosure of a live credential (`OutgoingToken`) for every bridge configured on the node, without needing edit/admin rights. This matches the Chainlink bounty "credential/secret disclosure to unauthorized/lower-privileged party" impact class — it does not grant fund movement directly, but exposes a secret meant to be scoped to bridge operators/admins, enabling downstream request forgery/impersonation against the external bridge endpoint.

### Likelihood Explanation
Fully feasible with only a `UserRoleView` session — no special preconditions beyond existing bridges configured with a non-empty `OutgoingToken` (true for every bridge, since `NewBridgeType` always generates one). The endpoint is a plain, unauthenticated-beyond-login `GET`, trivially repeatable, and requires no timing or race conditions.

### Recommendation
Add `json:"-"` or `omitempty` plus role-gating to `BridgeResource.OutgoingToken` in `core/web/presenters/bridges.go`, or strip/redact it in `NewBridgeResource` for `Index`/`Show` paths, only surfacing it (like `IncomingToken`) at creation/update time to editor/admin roles, or not returning it via read-list/show endpoints at all.

### Proof of Concept
Go handler-level integration test plan (in `core/web/bridge_types_controller_test.go` style):
1. Set up test app and ORM; create a bridge via `bridges.NewBridgeType` and `orm.CreateBridgeType`, capturing the generated `bta.OutgoingToken`.
2. Create an authenticated session/session cookie for a user with `sessions.UserRoleView`.
3. Issue `GET /v2/bridge_types` using the view-role session.
4. Assert HTTP 200 and parse the JSON-API response body.
5. Assert the response contains `attributes.outgoingToken == bta.OutgoingToken` (proving disclosure) — currently this assertion **passes**, confirming the vulnerability, whereas the expected secure behavior would be that this attribute is absent or redacted for view-role.
6. Repeat for `GET /v2/bridge_types/:BridgeName` (Show) with the same assertion.

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
