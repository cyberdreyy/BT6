### Title
Cross-User Response Hijacking via Unvalidated, Attacker-Chosen MessageId in Gateway Legacy Handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The legacy WebAPI gateway handler's `HandleLegacyUserMessage` stores a per-request callback keyed only by the client-supplied `MessageId`, with no check for an already in-flight request using the same ID. An unprivileged external client can submit a request whose `MessageId` collides with another user's still-pending request, silently overwriting the victim's saved callback. When a DON node later responds with that `MessageId`, the response is delivered to the attacker's callback instead of the legitimate requester, while the legitimate requester's HTTP call is left to time out with no valid response. This mirrors the external report's bug class: an attacker-controllable/collidable identifier used to route a sensitive pending operation to whichever party currently "owns" that identifier, enabling unauthorized interception (there: fund theft via a colliding `versionedHash`/target; here: cross-user response hijacking).

### Finding Description
`HandleLegacyUserMessage` unconditionally writes into the shared `savedCallbacks` map keyed by `msg.Body.MessageId`, without first checking whether an entry already exists for that ID: [1](#0-0) 

The only validation performed on `MessageId` is length/format-based, in `api.Message.Validate()` — there is no uniqueness or ownership check: [2](#0-1) 

Because `MessageId` is fully attacker-controlled (it is taken directly from the incoming request/`jsonRequest.ID`, per `ValidatedMessageFromReq`): [3](#0-2) 

...a second, unrelated user can pick the same `MessageId` as a currently pending request from a different user. The second call to `HandleLegacyUserMessage` overwrites `h.savedCallbacks[msg.Body.MessageId]` with the attacker's own `Callback`. When the DON node eventually replies with that `MessageId` (matched only by `MessageId`, not by original caller identity), `handleWebAPITriggerMessage` looks up the (now attacker-owned) entry and delivers the node's response to the attacker instead of the original user: [4](#0-3) 

Notably, the newer v2 HTTP trigger handler explicitly guards against exactly this class of bug by rejecting duplicate/in-flight request IDs with a `Conflict` error before registering a callback: [5](#0-4) 

The legacy handler (`core/services/gateway/handlers/capabilities/handler.go`) and the `dummyHandler` (`core/services/gateway/handlers/handler.dummy.go`) both lack this protection.

### Impact Explanation
This is reachable by any unauthenticated/unprivileged external client hitting the gateway's public user-facing HTTP endpoint (`gateway.ProcessRequest` → `HandleLegacyUserMessage`) — no operator, node, or peer privilege is required. Impact:
- Cross-user response confusion: an attacker receives another user's DON/workflow trigger response payload, which may contain sensitive workflow output data intended only for the victim.
- Denial of service for the legitimate caller: the victim's original request never resolves via its own callback (it is deleted/overwritten), resulting in a timeout error for a request that may have otherwise succeeded server-side.
- Potential for triggering unintended downstream effects/misuse if webhook/trigger responses are treated as authoritative results tied to `MessageId` by calling systems.

### Likelihood Explanation
Exploitation requires only that an attacker know (or guess/collide with) a `MessageId` used by a concurrently pending legacy request and submit a request with the identical ID before the original completes — no signature bypass or race beyond simple timing is needed, since `MessageId` is entirely client-chosen and unauthenticated ownership is never verified. This is straightforward for any client capable of observing or predicting IDs (e.g., low-entropy or predictable IDs used by some integrations), making likelihood moderate to high depending on how calling systems generate `MessageId`.

### Recommendation
In `HandleLegacyUserMessage` (and the `dummyHandler` equivalent), reject the request with a conflict error if `h.savedCallbacks[msg.Body.MessageId]` already exists, mirroring the guard already implemented in `v2/http_trigger_handler.go`'s `setupCallback`. Additionally, consider binding the saved callback to the original sender (e.g., a signature/session-derived identity) so that even non-colliding but adversarial reuse cannot cross callback boundaries.

### Proof of Concept
1. User A sends a legacy gateway request with `MessageId = "X"` to a DON member; `handler.HandleLegacyUserMessage` stores `savedCallbacks["X"] = CallbackA` and forwards the request to all DON members (`core/services/gateway/handlers/capabilities/handler.go:411-419`).
2. Before a node responds, Attacker sends another legacy request also using `MessageId = "X"`; this overwrites the map entry to `savedCallbacks["X"] = CallbackAttacker`.
3. A DON node responds to `MessageId = "X"` (originally intended for User A's request); `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `CallbackAttacker`, and delivers the node's response there (`handler.go:148-162`).
4. Attacker receives the response payload meant for User A; User A's original HTTP request times out.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	return nil
}

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}
