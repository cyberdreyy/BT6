### Title
Unfunded instant-withdraw receipts can be claimed against vault liquidity — declared receipt amount is paid without checking actual funding (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the MOOS-IvP decoder bug — a declared length/amount field is trusted without validating it against the actual data — `IdleCreditVault.requestInstantWithdraw` mints a receipt recording a *declared* claim (`instantWithdrawsRequests`), while `claimInstantWithdrawRequest` pays that declared amount in full from the vault's underlying balance without verifying that the corresponding funds were ever collected via `collectInstantWithdrawFunds`. The funding side is tracked only by the aggregate counter `pendingInstantWithdraws`, which is decremented in `collectInstantWithdrawFunds` but never checked in the claim path.

### Finding Description
The relevant flow:

- `requestInstantWithdraw` (invoked by the CDO from `requestWithdraw` when `lastEpochApr > currentApr + instantWithdrawAprDelta`) burns `_amount` strategy tokens from the CDO, mints receipt tokens to the user, and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` — but moves **zero** underlying into the vault [1](#0-0) .
- The only funding path is `collectInstantWithdrawFunds`, callable at epoch stop, which does `pendingInstantWithdraws -= _amount` and pulls underlying from the CDO [2](#0-1) .
- `claimInstantWithdrawRequest` burns the user's receipts and calls `_transferFundedClaim(_user, amount)`, which only guards against spending `defaultRecoveryReserve` — it never checks that the vault balance covering the claim corresponds to collected instant-withdraw funds [3](#0-2) [4](#0-3) .

So a receipt's *declared* amount is paid out even when the *actual* funded amount for it is zero. Any underlying sitting in the vault — repaid borrower funds awaiting epoch settlement, liquidity buffer, or funds earmarked for other funded claimants — can be consumed by a claim that was never funded.

### Impact Explanation
A KYC-passing lender (unprivileged attacker) holding tranche tokens triggers `requestWithdraw` during the buffer/running phase in a deployment where instant withdraws are enabled and the APR dropped by more than `instantWithdrawAprDelta`. The CDO burns their tranches and the vault mints receipts; the attacker then calls the CDO's `claimInstantWithdrawRequest` path in the same transaction/epoch, before any `collectInstantWithdrawFunds` has occurred, and `_transferFundedClaim` transfers real underlying out of the vault. Loss is bounded by the vault's liquid underlying balance at that moment, which can equal the full amount of borrower repayments or uninvested deposits — direct theft of other LPs' or funded claimants' assets, breaking the "one receipt, one funded payout" invariant.

### Likelihood Explanation
Requires a deployment in instant-withdraw mode with a qualifying APR drop (governed by `lastEpochApr`/`instantWithdrawAprDelta`, set by the honest manager/keeper cadence) and non-zero liquid underlying in the vault. Whether the CDO-side wrapper (`IdleCDOEpochVariant.claimInstantWithdrawRequest`) independently gates claims until post-`stopEpoch` funding could not be fully confirmed in this pass; if it does gate on epoch state, this specific path reduces to only the still-open window where receipts exist but funding has been partially collected (`collectInstantWithdrawFunds` may under-collect vs `pendingInstantWithdraws`, leaving aggregate claims larger than collected cash while `claimInstantWithdrawRequest` still pays the full declared amount). Note `collectInstantWithdrawFunds` happily collects any `_amount` less than `pendingInstantWithdraws` with no loss-price accounting — unlike `collectWithdrawFunds`, which stores a `lossRecoveryPriceByEpoch` haircut — so under-collected instant claims are also paid at par until the balance runs dry [5](#0-4) .

### Recommendation
- Gate `claimInstantWithdrawRequest` on actual funding: track `instantWithdrawFundedByEpoch`/`fundedInstantWithdraws` incremented in `collectInstantWithdrawFunds`, and pay claims only from that funded bucket.
- Mirror the `collectWithdrawFunds` design: if collected amount < pending instant basis, store a recovery price per epoch and haircut claims instead of paying declared amounts FIFO.
- Add a reserve-conservation check in `_transferFundedClaim` that excludes both `defaultRecoveryReserve` and the unfunded remainder of `pendingInstantWithdraws`.

### Proof of Concept
Foundry fork test outline (pattern follows `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: epoch-mode vault, instant withdraw enabled, underlying dealt to vault as
// liquidity/repayment buffer (e.g. borrower repayment pulled into strategy)
uint256 vaultFloat = underlying.balanceOf(address(strategy)); // > 0

// attacker: KYC'd lender
uint256 mintedAA = idleCDO.depositAA(amount);
// manager/keeper sets a lower APR so lastEpochApr > unscaledApr + instantWithdrawAprDelta
_setLowerApr(); // honest manager action sequencing only

uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.requestWithdraw(mintedAA, address(AAtranche)); // mints instant receipts, moves 0 underlying

// claim before stopEpoch / collectInstantWithdrawFunds funds the request
cdoEpoch.claimInstantWithdrawRequest();
assertGt(underlying.balanceOf(attacker) - balPre, 0);      // paid declared amount
assertLt(underlying.balanceOf(address(strategy)), vaultFloat); // drained vault liquidity
```

Uncertainty: the PoC depends on the CDO wrapper not reverting pre-`stopEpoch`. If it does, the under-collection variant (collect < pending, then claims still paid at par) remains reproducible by having the honest manager fund less than `pendingInstantWithdraws` at `stopEpoch`.

    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
