### Title
Unvalidated `recent_blockhash` causes `unwrap()` panic in `BanksServer::process_transaction_with_commitment_and_context` - ([File: banks-server/src/banks_server.rs])

### Summary
`process_transaction_with_commitment_and_context` sanitizes and verifies signatures on the client-supplied `VersionedTransaction`, but neither `SanitizedTransaction::try_create` nor `.verify()` check that `message.recent_blockhash()` is actually present in the bank's blockhash queue. An attacker can sign a transaction whose `recent_blockhash` field is a value that was never issued by `get_latest_blockhash_with_context`, causing `get_blockhash_last_valid_block_height(&blockhash).unwrap()` to panic on `None`.

### Finding Description
In `banks-server/src/banks_server.rs`: [1](#0-0) 

The handler flow is:
1. `blockhash = *transaction.message.recent_blockhash();` — taken verbatim from the attacker-supplied transaction.
2. `SanitizedTransaction::try_create(...)` — only sanitizes message structure, resolves account keys, and checks reserved accounts; it does not validate blockhash freshness/existence in the bank's blockhash queue.
3. `sanitized_transaction.verify()` — only checks that signatures are cryptographically valid for the signed message (which includes the attacker-chosen blockhash, since the attacker controls and signs their own message).
4. `self.bank(commitment).get_blockhash_last_valid_block_height(&blockhash).unwrap()` — looks up the blockhash in the bank's `blockhash_queue`. This queue only retains a bounded, recent set of hashes (`MAX_RECENT_BLOCKHASHES`); if the blockhash was never produced by the bank (or has since aged out), this returns `None`, and `.unwrap()` panics.

Because a client fully controls the transaction's `recent_blockhash` field and can sign the message with its own keypair (satisfying `verify()`), it can trivially pick a blockhash that is guaranteed to never appear in the bank's blockhash queue (e.g., `Hash::new_unique()` or `Hash::default()`), bypassing every check performed before the `unwrap()`.

### Impact Explanation
A single crafted `VersionedTransaction` sent through the banks RPC `process_transaction_with_commitment_and_context` handler panics the async task handling the request. Since this is a `tokio`/`tarpc` service handler, an unhandled panic in the task can abort the serving process for that connection/service instance, denying banks-service functionality with a single request from an unprivileged client — matching the DoS bounty category ("real validator/service crash from one request").

### Likelihood Explanation
Fully feasible and repeatable: no privileged access, staking, or special config is required. An attacker only needs to:
- Build any `VersionedTransaction` with a `recent_blockhash` not present in the target bank's blockhash queue.
- Sign it with a normal (even self-owned) keypair so `.verify()` passes.
- Submit it once via the banks-client/server RPC path.

Every such call triggers the panic deterministically, since the check ordering in the code guarantees `try_create`/`verify` succeed before the vulnerable `unwrap()` executes.

### Recommendation
Replace the `.unwrap()` with proper error handling: use `get_blockhash_last_valid_block_height` and return `Some(Err(TransactionError::BlockhashNotFound))` (or equivalent) when the lookup returns `None`, mirroring how `rpc/src/rpc.rs` handles the same lookup defensively instead of unwrapping.

async fn test_process_transaction_with_unknown_blockhash_does_not_panic() {

    let banks_server = start_local_server(bank_forks, ...).await;

    // Fund payer via bank setup as needed.

    // Use a blockhash guaranteed to never be in the bank's blockhash queue.
    let bogus_blockhash = Hash::new_unique();

        &[system_instruction::transfer(&payer.pubkey(), &Pubkey::new_unique(), 1)],
        Some(&payer.pubkey()),
        &bogus_blockhash,
    );
    let tx = Transaction::new(&[&payer], message, bogus_blockhash);
    let versioned_tx = VersionedTransaction::from(tx);

    // This call is expected to return an error (e.g., BlockhashNotFound)
    // instead of panicking the server task.
    let result = client
        .process_transaction_with_commitment(versioned_tx, CommitmentLevel::Processed)
        .await;

    assert!(result.is_err() || matches!(result, Ok(Err(TransactionError::BlockhashNotFound))));

Expected current behavior: the server-side task panics inside `get_blockhash_last_valid_block_height(&blockhash).unwrap()`, and the client observes a connection/RPC failure rather than a clean `TransactionError`. After the fix, the call should return a normal `Err(TransactionError::BlockhashNotFound)` without panicking.
