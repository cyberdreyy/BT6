### Title
Withdraw-request claims skip the `isWalletAllowed` KYC check enforced at request time — a revoked lender can still be paid out (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The epoch-based credit vault performs the Keyring KYC gate (`isWalletAllowed`) when a withdraw or deposit request is *created*, but never repeats it when the request is *settled* — i.e., at `claimWithdrawRequest`, `claimInstantWithdrawRequest`, and at the aggregated queue claim `IdleCDOEpochQueue.claimWithdrawRequest`. This mirrors the reported bug class exactly: state (KYC credential) is validated at request creation and assumed unchanged at settlement, so a lender whose credential is revoked after requesting still receives the underlying payout.

### Finding Description
`IdleCDOEpochVariant.requestWithdraw` gates the caller with `!isWalletAllowed(msg.sender)` inside `_checkNotAllowed` (contracts/IdleCDOEpochVariant.sol, lines 741–744), and `_deposit`/`depositDuringEpoch` do the same (lines 645, 668). The tranche tokens are burned and a strategy-token receipt is minted to the user inside `IdleCreditVault.requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol, lines 273–275).

However, the settlement side has no credential check:

- `claimWithdrawRequest()` (IdleCDOEpochVariant.sol, lines 967–971) forwards directly to `IdleCreditVault.claimWithdrawRequest(msg.sender)`, which burns the receipt and transfers underlyings via `_claimFundedWithdrawRequest`/`_claimLossAdjustedWithdrawRequest`/`_claimDefaultedWithdrawRequest`/`_claimPostDefaultWithdrawRequest` — none of which consult `isWalletAllowed` (IdleCreditVault.sol, lines 301–349, 760–784).
- `claimInstantWithdrawRequest()` (lines 975–978) only checks `allowInstantWithdraw`.
- `IdleCDOEpochQueue.claimWithdrawRequest(uint256 _epoch)` (contracts/IdleCDOEpochQueue.sol, lines 393–411) pays `msg.sender` against `epochWithdrawPrice` with no `isWalletAllowed` check, even though queue deposits/withdraw requests were gated by `_checkAllowed` → `cdoEpoch.isWalletAllowed(wallet)` (lines 415–421).
- Post-default paths (`_claimPostDefaultWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `DefaultDistributor.claim`) likewise pay out to whoever holds the receipt without a credential check.

Because the receipt is minted to the user and the payout amount was fixed at request time, the only thing standing between a revoked user and the funded underlyings is a check that does not exist at claim time.

### Impact Explanation
The compliance invariant "only wallets currently passing `keyring.checkCredential` may interact with the fund" is broken at settlement. A lender who is off-boarded by the Keyring admin (AML trigger, sanction, expired credential) after opening a withdraw request — normal, instant, queue-mediated, or post-default — can still call the claim functions and receive the full funded/haircut-adjusted underlying amount. Where revocation is intended as a freeze, pending requests effectively defeat it: the revoked account continues to interact with the system and extract funds. The lost value is bounded by the claimant's funded receipts (up to their full deposited balance plus accrued interest), but the impact is an unconditional bypass of the access-control layer on every settlement path.

### Likelihood Explanation
Likelihood is moderate. It requires a lender with an open withdraw request (or queue position) to have their credential revoked before claiming — a routine event whenever offboarding happens during the buffer/epoch wait that the two-step withdrawal design deliberately imposes. Because every settlement path lacks the check, no special timing or privileged misbehavior is needed; the exploit works in fixed-APR, APR0, instant, and defaulted/recovery modes. Note that the same reasoning applies to a malicious user front-running a known revocation by submitting a withdraw request first — exactly the report's exploit scenario of queuing transfers before a freeze.

### Recommendation
Re-validate `isWalletAllowed` at settlement on every payout path:

- Add `_checkNotAllowed(!isWalletAllowed(msg.sender))` to `claimWithdrawRequest()` and `claimInstantWithdrawRequest()` in `IdleCDOEpochVariant`, and to `claimWithdrawRequest(uint256)` / `claimDepositRequest(uint256)` in `IdleCDOEpochQueue`.
- Decide and document the policy for post-default recovery claims (`_claimPostDefaultWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `DefaultDistributor.claim`): whether revoked wallets should be blocked there too or treated as a special case.
- Add Foundry tests covering: request → credential revocation → claim must revert; and claim still succeeds for non-revoked users across normal, instant, loss-adjusted, and post-default receipts.

### Proof of Concept
Foundry fork PoC (mainnet fork with an existing `IdleCDOEpochVariant` + `IdleCreditVault` deployment, using the existing test harness style from `test/foundry/IdleCDOEpochQueue.t.sol`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

import "forge-std/Test.sol";

interface IKeyring {
    function checkCredential(uint256 policyId, address user) external view returns (bool);
}

contract ClaimWithoutKycTest is Test {
    // Deployed addresses filled from fixture
    IdleCDOEpochVariant cdoEpoch;
    IdleCreditVault strategy;
    IERC20Detailed underlying;
    MockKeyring keyring; // or real Keyring admin prank to revoke

    function testRevokedUserStillClaims() external {
        address user = makeAddr("user");

        // 1. User is KYC-approved, deposits and receives tranche tokens
        keyring.setAllowed(user, true);
        uint256 tranches = _depositWithUser(user, 100e6);

        // 2. Epoch runs; user opens a withdraw request (isWalletAllowed passes)
        vm.prank(manager);
        cdoEpoch.startEpoch();
        _requestWithdrawWithUser(user, tranches);

        // 3. Manager/owner stops epoch; receipts get funded at stop/startEpoch
        _stopCurrentEpochWithApr(1e18);

        // 4. Keyring admin (or mock) revokes the user's credential AFTER the request
        keyring.setAllowed(user, false);
        assertFalse(cdoEpoch.isWalletAllowed(user));
        // sanity: a new request is now blocked
        vm.prank(user);
        vm.expectRevert(); // requestWithdraw reverts on !isWalletAllowed
        cdoEpoch.requestWithdraw(0, address(AATranche));

        // 5. BUG: claim still succeeds and pays underlying to the revoked wallet
        uint256 balPre = underlying.balanceOf(user);
        vm.prank(user);
        cdoEpoch.claimWithdrawRequest(); // no isWalletAllowed check on this path
        assertGt(underlying.balanceOf(user), balPre, "revoked user was paid out");
    }

    function testRevokedUserStillClaimsViaQueue() external {
        address user = makeAddr("user");
        keyring.setAllowed(user, true);
        _depositToQueue(user, 50e6);
        vm.prank(manager);
        cdoEpoch.startEpoch();
        _queueRequestWithdraw(user);
        _stopCurrentEpochWithApr(1e18);
        queue.processWithdrawRequests();
        // advance to claimable epoch
        _stopCurrentEpochWithApr(1e18);
        queue.processWithdrawalClaims(epoch);

        keyring.setAllowed(user, false);
        uint256 balPre = underlying.balanceOf(user);
        vm.prank(user);
        queue.claimWithdrawRequest(epoch); // pays out despite revoked credential
        assertGt(underlying.balanceOf(user), balPre);
    }
}
```

The key assertions: `requestWithdraw` correctly reverts after revocation (proving the gate is intended), while `claimWithdrawRequest` / `queue.claimWithdrawRequest` succeed and transfer underlyings to the revoked wallet (proving the missing settlement-time check).
