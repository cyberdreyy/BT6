### Title
Job-run lookup ignores `:ID` job path parameter, allowing cross-job pipeline run disclosure - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Show` parses only the `:runID` path parameter and calls `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)` without ever validating that the resolved run actually belongs to the job identified by `:ID` in the same URL. Any caller authorized to view runs for one job can substitute an arbitrary numeric `runID` and retrieve pipeline run data (including task inputs/outputs) belonging to a different job.

### Finding Description
`Show` is registered at `GET /v2/jobs/:ID/runs/:runID` [1](#0-0)  but the handler body never reads `c.Param("ID")`; it only uses `c.Param("runID")` to build the lookup key and fetch the run directly from the ORM: [2](#0-1) 
Compare this to `Index`, which does correctly scope by job ID when present, by passing `&jobSpec.ID` into `PipelineRuns` [3](#0-2) . `Show` has no equivalent scoping — `FindRun` is looked up purely by run ID with no join/filter against the job in the URL, and the returned resource is serialized and returned as-is by `presenters.NewPipelineRunResource`. Since there is no ownership check between `:ID` and the run's `PipelineSpecID`/job, a request for `/v2/jobs/{jobA}/runs/{jobB_runID}` will succeed and return `jobB`'s run data as long as the caller has any role permitted to hit this route (the route requires only the generic session/API-token auth applied by the router, not per-job authorization — Chainlink core does not have per-job ACLs at all, all authenticated node users can see all jobs' run lists via `Index`, but the `:ID`/`:runID` mismatch means the response is not even scoped as `Index` intends).

### Impact Explanation
This allows cross-job data confusion: a request that appears scoped to one job in the URL will silently return run data — including task run inputs and outputs, which can contain response bodies from bridges or other job-specific parameters — for a run under a completely different, unrelated job. This maps to Chainlink's "cross-user response confusion / unauthorized read of another job's data" bounty class, though its severity is bounded by the fact that Chainlink node API authentication is global (any authenticated user already has visibility into all jobs/runs on that node instance via `Index`); the concrete exploitable delta here is the broken URL-to-resource binding for `Show`, which could mislead API consumers or downstream authorization logic that trusts `:ID` as an access-control boundary.

### Likelihood Explanation
Exploitation requires only a valid, authenticated node API session or API token (no elevated role beyond whatever role is normally required to call `GET /v2/jobs/:ID/runs/:runID`), and a guessable/enumerable numeric `runID`. Since run IDs are sequential integers, enumeration is trivial once a caller has any authenticated access to the node's web API.

### Recommendation
Have `Show` parse `c.Param("ID")` into a job ID (as `Index` does), and either (a) query `FindRun` with an additional constraint that the run's `PipelineSpecID` maps to a `job.Job` with that ID, or (b) after fetching the run, verify the run's job/spec ownership matches the parsed `:ID` and return 404 on mismatch.

### Proof of Concept
1. Handler-level integration test (extending `core/web/pipeline_runs_controller_test.go`): create `jobA` and `jobB` with distinct pipeline specs, trigger a run under each to get `jobA_runID` and `jobB_runID`.
2. Issue `GET /v2/jobs/{jobA.ID}/runs/{jobB_runID}` with a normally-authenticated session.
3. Assert current (vulnerable) behavior: HTTP 200 with a `pipelineRun` resource whose underlying `PipelineSpecID`/job actually belongs to `jobB`, proving the `:ID` path segment was not enforced.
4. After fix: assert the same request returns 404/422, and only `GET /v2/jobs/{jobB.ID}/runs/{jobB_runID}` succeeds.

// Show returns a specified pipeline run.
// Example:
// "GET <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
