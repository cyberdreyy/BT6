### Title
Silent wrong-block-hash return from EIP-2935 ring-buffer lookup during fault-proof L2 history walk-back - ([File: crates/proof/proof/src/eip2935.rs])

### Summary
The Ion Protocol report describes a Uniswap v3 TWAP oracle whose observation ring buffer (cardinality) is smaller than the intended lookback window, so a query for a historical price can silently read a stale/uninitialized slot instead of failing. Base's fault-proof L2 chain provider contains the same class of bug: `eip_2935_history_lookup` uses a fixed-size ring buffer (`HISTORY_SERVE_WINDOW = 8191`) to jump back through L2 block hashes, but it validates "in window" purely by arithmetic distance (`header.number - block_number <= HISTORY_SERVE_WINDOW`) without verifying that the EIP-2935 history contract has actually been populated that far back since the Isthmus activation. This can cause the function to read a slot that was overwritten by a later, unrelated block and return the wrong block hash instead of erroring.

### Finding Description
`eip_2935_history_lookup` computes the storage slot as `block_number % HISTORY_SERVE_WINDOW` whenever the caller's header is within `HISTORY_SERVE_WINDOW` blocks of the target, and fetches whatever hash is stored at that ring slot: [1](#0-0) 

The EIP-2935 history-storage contract is only written to per-block starting at Isthmus activation; slots for pre-activation block numbers are never populated by an activation-time write. If Isthmus has been active for fewer than `HISTORY_SERVE_WINDOW` (8191) blocks, then for a target `block_number` that predates activation but still satisfies the "within window" distance check relative to the current walk-back header, the slot `block_number % HISTORY_SERVE_WINDOW` can coincide with the slot later overwritten by some post-activation block `block_number + 8191*k`. In that case the trie lookup succeeds (the slot is not empty, so no `TrieNodeError::KeyNotFound` is raised) but returns the hash of a completely unrelated block, silently, rather than raising an error.

This function is the sole consumer of the module and is invoked by the L2 chain provider used in the fault-proof program's derivation pipeline to walk back from the safe head to a target block number: [2](#0-1) 

Only an oracle error (e.g. `KeyNotFound`) triggers the safe linear-walk-back fallback; a *wrong but present* value is accepted as correct and the walk continues from the wrong header, exactly analogous to the Uniswap oracle silently using stale/insufficient-cardinality data instead of reverting.

### Impact Explanation
If the derivation pipeline (used both for online L2 sync when Isthmus is active and for the fault-proof program that recomputes an output root during dispute-game resolution) walks back using a wrong block hash, it will fetch and process the wrong header/block for that historical query — corrupting `system_config_by_number`/`block_info_by_number` derivation input. In the fault-proof program context this can lead to computing an incorrect output root against the wrong parent chain of headers, i.e. a wrong provable output root being derived during dispute-game trace generation, which is one of the explicitly accepted high-impact outcomes (wrong provable output root).

### Likelihood Explanation
This requires a narrow but realistic window: shortly after the Isthmus hardfork activates on a given Base chain (mainnet, testnet, or devnet), before 8191 L2 blocks (roughly a few hours at Base's block time) have elapsed, plus a query that targets a specific pre-activation block number reachable via the "in window" arithmetic check. Because hardfork activation happens on every new network and dispute games/derivation can reference historical blocks spanning the activation boundary, this condition is reachable without any special privileges — it occurs naturally from ordinary fault-proof program execution / derivation replay during the vulnerable time window, not from attacker-crafted transactions. I could not verify within the available context whether the fault-proof program restricts the input range of `block_number` to strictly post-Isthmus blocks elsewhere (e.g., in the pipeline cursor or boot info validation), which would mitigate this; that check was not found in the reachable code paths I inspected.

### Recommendation
Track (or derive from `rollup_config`) the Isthmus activation block number and require that `header.number.saturating_sub(activation_block) >= (header.number - block_number)` (i.e., the ring has genuinely accumulated enough history since activation) before trusting the EIP-2935 slot value, in addition to the existing distance check. If the accumulated history is insufficient, immediately fall back to the linear walk-back path instead of trusting the ring-buffer slot.

### Proof of Concept
Not independently reproducible from static analysis alone — reproducing requires running the fault-proof program (or online derivation) against an L2 chain within `HISTORY_SERVE_WINDOW` (8191) blocks of Isthmus activation and requesting a `block_number` that predates activation but is within the naive distance check in `eip_2935_history_lookup` (crates/proof/proof/src/eip2935.rs:39-43), then observing that the returned hash corresponds to a later, unrelated block rather than an error.

    // oldest block in the window.

        block_number
    } else {
