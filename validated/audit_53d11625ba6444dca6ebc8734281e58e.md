### Title
Stale confirmations from a removed multisig member still count toward the confirmation threshold, allowing a request to execute with fewer live signers than `num_confirmations` - (File: multisig2/src/lib.rs)

### Summary
This is a structural analog of the reported bug class: a value that should be revoked/rebound when a trusted party changes (the ERC20 allowance to the old `platform`) is instead left stale, letting an entity that no longer holds the relevant privilege still exert its old effect. In `multisig2`, `DeleteMember` clears only the *requests created by* the removed member, but never strips that member's already-recorded *confirmations* on other pending requests they had merely signed. Those stale confirmations continue to count toward `num_confirmations`, letting a request execute with fewer currently-live members than the configured threshold.

### Finding Description
`confirm` adds the calling member's identity to a `HashSet<String>` of confirmations for a request, and once `confirmations.len() + 1 >= self.num_confirmations` the request is removed and executed: [1](#0-0) 

When a member is removed via `MultiSigRequestAction::DeleteMember`, `delete_member` only removes outstanding *requests that member itself created* (`r.member == member`) and clears their `num_requests_pk` entry and access key. It does not scan `self.confirmations` for other pending requests where this member's confirmation was recorded as an approver: [2](#0-1) 

Consequently, a request `R` created by member `A` and already confirmed by member `B` (confirmations = {A, B}, still below threshold `K`) survives `B`'s removal untouched. After `B` is removed, `B`'s confirmation weight is still present in `R`'s confirmation set. A subsequent `confirm` call from a legitimately remaining member `C` can push `confirmations.len()+1 >= K`, and `R` executes — even though only `A` and `C` are actually live members at execution time, i.e., fewer than `K` live signers authorized it.

Binding broken (as an equality that should hold but doesn't):
`count(confirmations recorded on request R that belong to currently-live members) == count(confirmations required to execute R)`

After a member removal, the left side can be `K-1` (or less) live signers while the recorded/counted confirmations on the stale set still equal `K`, so the request executes.

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold." A request (e.g., `Transfer`, `FunctionCall`, `AddKey`, `AddMember`) can be executed with confirmation weight partially supplied by a member who has already been removed (e.g., because their key was known to be compromised or they were maliciously colluding before being kicked out). This defeats the core security guarantee of the K-of-N multisig — that K *currently trusted* members must approve — and can lead to unauthorized transfers or account takeover actions being pushed through with insufficient live approval.

### Likelihood Explanation
The precondition is realistic and does not require any privileged foundation/owner action beyond normal multisig operation: any request left pending (unconfirmed to completion) at the time a member is removed will retain that member's confirmation weight. Multisig members routinely leave partially-confirmed requests open (that's the entire purpose of the K-of-N flow), and member removal (e.g., in response to a suspected compromised or malicious key) is an expected, not rare, operational event. No special permissions beyond being a former member are needed for the stale weight to be exploited by the remaining members completing the threshold.

### Recommendation
When executing `DeleteMember`, iterate over all pending requests' confirmation sets and remove the departing member's identifier from every one of them (not just requests they authored), re-evaluating whether any request now has fewer confirmations recorded than actually held by live members. Alternatively, validate at `confirm`-time / execution-time that every entry in a request's confirmation set still corresponds to a current member of `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 3` and members `{A, B, C, D}`.
2. `A` calls `add_request_and_confirm(R)` for some sensitive action (e.g., `Transfer`). `confirmations(R) = {A}`.
3. `B` calls `confirm(R)`. `confirmations(R) = {A, B}` (2 < 3, not yet executed) — see `confirm` logic: [1](#0-0) .
4. The group discovers `B`'s key is compromised and submits/confirms a `DeleteMember{B}` request (requires 3 of the remaining 3 confirms, satisfied since `members.len()-1 (=3) >= num_confirmations (=3)`), removing `B` — see `delete_member`: [2](#0-1) . Note this only clears requests `B` *created*; `R` (created by `A`) is untouched, and `confirmations(R)` still contains `B`.
5. `C` calls `confirm(R)`. `confirmations(R).len() + 1 == 3 >= num_confirmations`, so `R` executes — despite only `A` and `C` being live members who actually approved it at execution time, one fewer live signer than the configured threshold of 3.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
