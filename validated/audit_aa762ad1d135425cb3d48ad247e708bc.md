### Title
Deterministic lockup address squatting via unchecked `whitelist_account_id` override lets attacker install a rogue staking-pool whitelist for a victim's future lockup - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the new lockup's account ID solely from `sha256(owner_account_id)[..20]` and lets the caller freely pass `whitelist_account_id`, defaulting to `self.whitelist_account_id` only when `None`. An attacker can pre-create the victim's deterministic lockup address with a self-controlled fake whitelist contract before the legitimate issuer's `create()` call for that same `owner_account_id` lands, causing the legitimate call to fail (`create_account()` on an already-existing account) and refund, while the victim's lockup permanently trusts the attacker's whitelist.

### Finding Description
The broken binding: `deployed_lockup.staking_pool_whitelist_account_id == self.whitelist_account_id` (the factory's configured, foundation-controlled whitelist) is expected to always hold for every lockup created via the factory, but is not enforced.

In `lockup-factory/src/lib.rs`, `create` computes the account deterministically from only the `owner_account_id`: [1](#0-0) 
and takes an attacker-controllable override for the whitelist: [2](#0-1) 
There is no restriction (e.g., `assert_called_by_foundation`, or forcing `whitelist_account_id` to always be `self.whitelist_account_id`) on who may supply `whitelist_account_id`, and no uniqueness/ownership check tying the `owner_account_id` argument to the caller (`predecessor_account_id`) before the account is created. Anyone can call `create(owner_account_id=<victim>, ..., whitelist_account_id=Some(<attacker_fake_whitelist>))`, attaching the minimum deposit, and have `Promise::new(lockup_account_id).create_account()...` execute first if it lands before the legitimate issuer's transaction.

Because `create_account()` on an already-existing NEAR account fails, the legitimate issuer's later `create()` call for the same `owner_account_id=<victim>` (with `whitelist_account_id=None`, intending to use the true `self.whitelist_account_id`) will fail at `create_account()`; `on_lockup_create`'s `is_promise_success()` check detects this and refunds the deposit to the caller: [3](#0-2) 
(the attacker's earlier deployment remains permanently in place).

The victim, once they gain control of the lockup as owner, will later call `select_staking_pool`, which queries `ext_whitelist::is_whitelisted` against `self.staking_pool_whitelist_account_id` — now the attacker's fake whitelist contract, not the foundation's: [4](#0-3) 
None of the existing guards (`assert_owner`, `is_valid_account_id`, `assert_staking_pool_is_not_selected`, `assert_no_termination`) check that the whitelist contract itself is the legitimate one; they only validate the staking pool ID format and lockup state, not the identity of the whitelist source.

### Impact Explanation
If the attacker's fake whitelist unconditionally returns `true` from `is_whitelisted`, the victim's `select_staking_pool` call will accept an attacker-controlled staking pool as "whitelisted," even though it was never actually approved by the foundation's real whitelist. This satisfies the "lockup deployed with parameters its rightful creator never chose" and "an account whitelisted... that its rightful creator never chose" Critical criteria: the victim's locked/vesting NEAR can subsequently be deposited/staked into a pool entirely controlled by the attacker via `deposit_and_stake`, from which the attacker (as the pool operator) can withhold rewards or otherwise misappropriate funds once staked. The blast radius is any `owner_account_id` whose lockup has not yet been created — i.e., every future grant recipient is squattable, and the attack is repeatable across arbitrary victim accounts at low, fixed cost (`MIN_ATTACHED_BALANCE` = 3.5 NEAR per attempt, refunded to the real issuer but the attacker's account creation deposit stays sunk into the squatted lockup they now control the whitelist for).

### Likelihood Explanation
The precondition is simply that the attacker learns (or predicts) an `owner_account_id` that a legitimate grant issuer intends to use, and races to call `create` first with that owner and their own fake whitelist contract before the real issuer's transaction is included. Since intended grant recipients are often publicly known in advance (e.g., team/investor accounts, or predictable naming conventions), and NEAR mempool ordering does not guarantee the "real" issuer's transaction lands first, this is practically feasible for any account whose lockup has not yet been deployed. Attacker cost is limited to the `MIN_ATTACHED_BALANCE` plus deploying two contracts (a fake whitelist and, later, a fake staking pool) — both fully within the described unprivileged attacker capability set (deploy contracts they name/control). This is repeatable per victim account.

### Recommendation
Remove attacker control entirely: `LockupFactory::create` should ignore any caller-supplied `whitelist_account_id` and unconditionally set `staking_pool_whitelist_account_id = self.whitelist_account_id.clone()`, or restrict the parameter to be settable only when `predecessor_account_id == self.foundation_account_id` (mirroring `assert_called_by_foundation`-style checks used elsewhere in this repo family). This removes the ability for arbitrary unprivileged callers to inject a malicious whitelist into any lockup, including squatted ones.

### Proof of Concept
Using `near-sdk-sim` (or the existing `test_create_lockup_with_custom_whitelist_success` pattern in `lockup-factory/src/lib.rs`'s test module as a base):
1. Deploy `LockupFactory` with `whitelist_account_id = real_whitelist`.
2. Deploy a fake whitelist contract `attacker_fake_whitelist` whose `is_whitelisted` always returns `true`.
3. As `attacker`, call `factory.create(owner_account_id = victim, ..., whitelist_account_id = Some(attacker_fake_whitelist))` with `MIN_ATTACHED_BALANCE` attached; assert the resulting lockup account `sha256(victim)[..20].factory` is created successfully (`on_lockup_create` returns `true`).
4. As `real_issuer`, call `factory.create(owner_account_id = victim, ..., whitelist_account_id = None)` with sufficient deposit; assert the promise's `create_account()` fails (account already exists) and `on_lockup_create` logs the failure and refunds, returning `false`.
5. Read the deployed lockup's state (`staking_pool_whitelist_account_id`) and assert `staking_pool_whitelist_account_id == attacker_fake_whitelist`, i.e., `!= real_whitelist` — violating the intended binding `deployed_lockup.staking_pool_whitelist_account_id == factory.whitelist_account_id`.
6. As `victim` (now owner of the squatted lockup), call `select_staking_pool(attacker_fake_pool)`; assert the callback approves the pool despite it never being registered on `real_whitelist`, demonstrating the victim's funds are now eligible to be staked into an attacker-controlled pool.
