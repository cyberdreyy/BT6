### Title
Loss haircut on pending withdraw receipts is keyed to the post-increment epoch, so defaulted/loss-adjusted receipts claim at par — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.collectWithdrawFunds` records a stop-epoch loss haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is already incremented inside `deposit()` when the CDO deposits during `stopEpoch` (while `isEpochRunning()` is still true). User receipts and `lastWithdrawRequest` are keyed to the request epoch. The result is a permanent off-by-one between the epoch that stores the haircut and the epoch the claim path looks up: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` (the request epoch), finds `0`, skips the haircut, and `_claimFundedWithdrawRequest` then pays the full un-haircutted basis at par even though the borrower only funded `pendingBasis * lossRecoveryPrice`. This is the same shape as the FFmpeg bug: an accounting buffer ("how much was funded") sized by an initial/stale frame, then a larger later frame (the full receipt basis) written/claimed against it.

### Finding Description
- `requestWithdraw` stores receipts under the current epoch: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `lastWithdrawRequest[_user] = currentEpoch` where `currentEpoch = epochNumber` at request time (IdleCreditVault.sol:260-293).
- In `deposit()`, when the CDO deposits during a running epoch (the `stopEpoch` deposit), the strategy executes `epochNumber += 1` (IdleCreditVault.sol:607-610).
- In `collectWithdrawFunds`, called by the CDO during the same `stopEpoch`/`stopEpochWithDuration` flow after the deposit leg, a shortfall stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (IdleCreditVault.sol:411-421) — i.e., under the already-incremented epoch N+1, not the request epoch N.
- The claim side resolves the loss via `lossEpoch = lastWithdrawRequest[_user]` (IdleCreditVault.sol:790-791), which is N. `lossRecoveryPriceByEpoch[N]` is `0`, so `_claimLossAdjustedWithdrawRequest` returns `0` without burning anything.
- `_claimFundedWithdrawRequest` then only requires `epochNumber > lastWithdrawRequest[_user]` (N+1 > N, true) and pays `withdrawsRequests[_user]` in full via `_transferFundedClaim` (IdleCreditVault.sol:326-349).
- The pre-request guard that is supposed to force claiming a loss-adjusted receipt first has the same keying bug: it checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (epoch N), which is never set, so a user can even stack new requests on top without ever triggering it (IdleCreditVault.sol:261-271).

Net effect: `pendingWithdraws` is zeroed and only `_amount < pendingBasis` underlying was pulled into the strategy, yet every pending receipt is paid at `claimBasis * 1.0`. The strategy's underlying balance is drained by the first claimers; later claimers (including other tranche holders' funded receipts and instant-withdraw claimants) revert on insufficient balance — direct theft from later claimants plus permanent freezing of their claims.

### Impact Explanation
Critical solvency/fair-payout break. Any `stopEpochWithDuration` (or default-lite path) that funds pending withdrawals below basis creates receipts payable at par from a partially funded pool. First-come claimants extract more than funded; the deficit lands on remaining claimants whose withdrawals permanently revert. Quantified loss equals `pendingBasis - amountFunded` taken by early claimers, and an equal amount of frozen claims for the rest. The analogous guards (`lossRecoveryPrice` non-zero check, `lastWithdrawRequest` gating, `NotAllowed` on re-request) all index the wrong epoch and never fire.

### Likelihood Explanation
Requires a borrower-funded shortfall at `stopEpoch` (a realized loss event — the mechanism explicitly exists via `stopEpochWithDuration(_lossAmount)` and `previewLossAdjustedWithdrawFunds`, so it is an intended, reachable mode, not an edge case). Attacker is any tranche-token holder with a pending withdraw request; no privileged role needed. The trigger (a loss epoch) is a normal operating condition for a credit vault.

### Recommendation
Key the haircut by the request epoch, not the post-increment epoch. Either store `lossRecoveryPriceByEpoch[epochNumber - 1]` in `collectWithdrawFunds`, or record the request-side epoch consistently (e.g., store pending receipts under `epochNumber` evaluated the same way at funding time). Additionally, keep a per-epoch aggregate of pending basis so the claim path can verify the haircut applies to exactly the receipts funded in that epoch.

### Proof of Concept
Foundry fork PoC sketch (against `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
// test/foundry/LossEpochKeyMismatch.t.sol
function testLossHaircutKeyedToWrongEpoch() external {
    // epoch 0 buffer: userA and userB deposit into AA tranche
    uint256 amtA = 100e6; uint256 amtB = 100e6;
    uint256 tA = _depositWithUser(userA, amtA);
    uint256 tB = _depositWithUser(userB, amtB);
    vm.prank(manager); cdoEpoch.startEpoch();          // epoch 1 running

    // both request withdraw during epoch 1 -> lastWithdrawRequest = 1
    _requestWithdrawWithUser(userA, tA);
    _requestWithdrawWithUser(userB, tB);

    // borrower realizes a loss: stopEpochWithDuration funds only 50% of pending
    uint256 pending = strategy.pendingWithdraws();     // = tA + tB basis
    uint256 fund = pending / 2;
    _fundBorrower(fund + expectedInterest);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(loss, duration);    // epochNumber -> 2,
    // collectWithdrawFunds stores lossRecoveryPriceByEpoch[2] = 0.5e18

    // BUG: userA claims FULL basis, not 50%
    vm.prank(address(cdoEpoch)); // via CDO claim path / withdraw flow
    uint256 paidA = strategy.claimWithdrawRequest(userA);
    assertEq(paidA, tA);                               // par payout, haircut skipped
    // lossRecoveryPriceByEpoch[1] == 0 -> _claimLossAdjustedWithdrawRequest no-op
    assertEq(strategy.lossRecoveryPriceByEpoch(1), 0);
    assertEq(strategy.lossRecoveryPriceByEpoch(2), 5e17);

    // userB's claim now reverts/strategy undercollateralized:
    vm.expectRevert();                                  // insufficient underlying
    vm.prank(address(cdoEpoch));
    strategy.claimWithdrawRequest(userB);
}
```

Uncertainty note: this conclusion depends on `collectWithdrawFunds` being invoked inside `stopEpoch` after the strategy `deposit` call that performs `epochNumber += 1` (IdleCreditVault.sol:610). I verified the increment site and the claim-side lookups, but the final-iteration limit prevented me from confirming the exact call order inside `IdleCDOEpochVariant.stopEpoch`/`_afterStopEpochWithDuration`. If `collectWithdrawFunds` were instead invoked strictly before any running-epoch deposit, the keying would be consistent and this finding would not hold — the ordering should be confirmed there before relying on the PoC.
