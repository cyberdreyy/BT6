## Finding

### Title
v1 signers can equivocate (sign two conflicting tenure-start blocks) because the tenure-duplicate check only looks at globally-accepted state - ([File: `stacks-signer/src/chainstate/v1.rs`])

### Summary
The Morpho report's root cause is a "has this already been created/finalized" check that is satisfied too late: the guard only fires once state is *fully* committed, leaving a window where a second, conflicting object can be pushed through and accepted. The v1 signer chainstate has the same class of gap in `validate_tenure_change_payload`: it treats a tenure-start block as "already claimed" only once it is **globally accepted** (i.e., the stacks-node has actually seen/confirmed it), not once the signer itself has already signed it locally. A miner (or a byzantine/timing-favorable network condition) can exploit the gap between "signer signed it" and "node confirmed it" to get a second, different tenure-start block through the same signer.

### Finding Description
In `stacks-signer/src/chainstate/v1.rs`, `SortitionsView::validate_tenure_change_payload` rejects a tenure-change proposal as a duplicate only if: [1](#0-0) 

i.e. it calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`. A block only becomes `GloballyAccepted` once the node reports the chain tip has actually advanced to it (`stacks_block_arrival` / `NewBlock` handling), which happens strictly after the signer has already produced its own signature (`LocallyAccepted`/`signed_group`).

By contrast, the v2 equivalent was explicitly hardened to close exactly this hole, using `get_last_signed_block` (which counts *locally or globally* accepted blocks): [2](#0-1) 

and this fix is pinned by a regression test whose comment states the bug directly: *"Before the fix, this would have incorrectly passed because `get_last_globally_accepted_block` would not find the locally-accepted block."* [3](#0-2) 

v1 was never given the same fix, so the same incorrect-pass condition still exists there.

The only remaining backstop is the pre-commit-time "own tenure conflict" guard in `handle_block_pre_commit`, but it is a node-state query, not a self-consistency check against the signer's own prior signature: [4](#0-3) 

It only refuses to sign the second (conflicting) block if `stacks_client.get_tenure_tip(consensus_hash)` reports a tip **at or above** the proposed height. If the node has not yet observed/confirmed the first (already-signed) block — e.g. because it hasn't propagated back into this node yet, or the query errors — the code explicitly treats the tenure "as unconfirmed" and proceeds to sign the conflicting block anyway.

### Impact Explanation
This lets a single v0/v1-protocol signer place its signature on two different, conflicting tenure-start blocks for the same tenure/height — an equivocation. That is a direct safety break: "a signer signing an invalid, non-canonical, or conflicting block" (Critical per the rules), not merely a liveness nuisance. It undermines the one-signature-per-height guarantee the whole pre-commit/conflict-tracking design (documented in `docs/signer-flows.md` section 5) is built to preserve.

### Likelihood Explanation
No majority or another signer's key is required — only:
1. A single miner (which may simply be slow/lagging in relaying blocks to this particular node, or can deliberately delay it) proposing block A, tenure-start for tenure T.
2. This signer validating and locally-accepting/signing A (reaching `LocallyAccepted`/`signed_group`) before the stacks-node client this signer talks to has actually confirmed A on its own chain tip (a normal, common propagation-delay window, not an edge case).
3. The same or a colluding miner then proposing a different tenure-start block B for the same tenure T (e.g. different transaction set) before the node's tenure tip catches up to A.

Because the check in v1 (`get_last_globally_accepted_block`) and the pre-commit backstop (`get_tenure_tip`) both key off the *node's* observed state rather than the signer's own already-issued signature, B passes both gates and gets signed too. This is realistic under ordinary network latency, not just an adversarial edge case, which raises the likelihood above "requires a majority of signers" — it needs none.

### Recommendation
In `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`, replace `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` with `signer_db.get_last_signed_block(&block.header.consensus_hash)` (the same query already used by v2), so a tenure-start duplicate is rejected as soon as this signer has locally accepted any block in that tenure, not only once the node confirms it. Additionally, harden the pre-commit "own-tenure" fallback guard in `stacks-signer/src/v0/signer.rs` (`handle_block_pre_commit`) to also consult the signer's own local record of a previously signed block in the same tenure (not only the node's `get_tenure_tip`), so an unresponsive/lagging node cannot be used to bypass the equivocation guard.

### Proof of Concept
1. Signer (protocol v1) receives tenure-start proposal A for tenure `T` (with `TenureChangeCause::BlockFound` + coinbase). It validates, pre-commits, and — with enough pre-commit weight (single/low-weight signer works) — signs A: `BlockInfo::mark_locally_accepted`, state becomes `LocallyAccepted` (see the analogous test setup pattern in `stacks-signer/src/chainstate/tests/v2.rs:772-803`, minus the fix).
2. Before this signer's stacks-node has processed a `NewBlock` event for A (i.e., A is not yet `GloballyAccepted`, and `get_tenure_tip(T)` still returns the parent tip), the miner proposes a second tenure-start block B for the same tenure `T` (different transactions/timestamp).
3. `SortitionsView::check_proposal` → `validate_tenure_change_payload` (v1.rs:461-520) calls `get_last_globally_accepted_block(T)`, which returns `None` (A is only locally accepted) → no `DuplicateBlockFound`, proposal accepted.
4. B is submitted for validation, reaches pre-commit; `handle_block_pre_commit` finds A as a fresh conflict via `get_signed_conflicts`, but since `stacks_client.get_tenure_tip(T)` still reports the pre-A tip (height below B's proposed height), the "still blocks" branch in `stacks-signer/src/v0/signer.rs:1436-1447` does not trigger, and the code falls through to `mark_locally_accepted` and signs B.
5. The signer has now produced signatures over two conflicting blocks (A and B) for tenure `T` at the same height.
