### Title
EI credentials can invoke RunJobV2 on any job by numeric ID due to shared SessionUserKey between user and EI auth - ([File: core/web/router.go], [File: core/web/pipeline_runs_controller.go], [File: core/web/auth/auth.go])

### Summary
`userOrEI.POST("/jobs/:ID/runs")` is wrapped only in `auth.RequiresRunRole`, which just checks role level, not identity/binding to a specific job or EI. The `PipelineRunsController.Create` handler additionally tries to gate integer-ID job runs to "users only, not EIs" via `auth.GetAuthenticatedUser(c)`, but `AuthenticateExternalInitiator` also sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}`, making that check ineffective — an EI-authenticated request is indistinguishable from a real user for this purpose.

### Finding Description
The route is registered as: [1](#0-0) 

`auth.Authenticate` tries `AuthenticateExternalInitiator`, `AuthenticateByToken`, `AuthenticateBySession` in order and succeeds on the first that doesn't fail with `auth.ErrorAuthFailed`: [2](#0-1) 

For a valid EI credential, `AuthenticateExternalInitiator` sets **both** `SessionExternalInitiatorKey` and `SessionUserKey` to a synthetic run-role user: [3](#0-2) 

`RequiresRunRole` only checks that a `SessionUserKey` object exists and its role is not `View` — it has no notion of EI vs. real user, and no job-binding check: [4](#0-3) 

In `PipelineRunsController.Create`, the code explicitly intends "only users are allowed to run jobs using int IDs - EIs not allowed", implemented via `auth.GetAuthenticatedUser(c)`: [5](#0-4) 

Because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `GetAuthenticatedUser(c)` returns `ok=true` for an EI-authenticated request as well as a real user session — the intended restriction is bypassed. Once `isUser` is `true`, the handler parses `idStr` as an arbitrary `int32` and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly, with **no lookup or verification that the job belongs to, or is associated with, the authenticated EI's webhook spec**: [6](#0-5) 

`RunJobV2` itself only checks `build.IsProd()` and then unconditionally fetches and runs the job by ID — it performs no EI/job ownership check either.

### Impact Explanation
An attacker holding valid, restricted EI credentials (which are meant to be scoped to triggering runs for their own registered webhook job) can request pipeline runs for **any** job on the node by supplying arbitrary numeric job IDs — including bridge/OCR/VRF/other jobs unrelated to their EI registration. This breaks isolation between external initiators and allows unauthorized execution of arbitrary jobs (e.g., forcing pipeline runs, consuming task/bridge resources, potentially interacting with fund-moving tasks depending on job graph), matching Chainlink's "unauthorized job run" impact class. Note this path is also gated by `build.IsProd()` inside `RunJobV2`, so it is a manual/dev-testing capability; however, on non-production builds it directly enables cross-EI job execution without any additional check.

### Likelihood Explanation
Requires only a valid, low-privilege EI credential pair (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret`), obtainable by any party who has been issued an external initiator token via `/v2/external_initiators` (an edit-role action performed by an operator, but the resulting EI credential itself is meant to be a restricted, low-trust credential distributed to third parties). Given the credential, the attack is a single unauthenticated-role-elevation-free HTTP POST with a crafted integer path parameter — fully reproducible and repeatable against every job ID on the node.

### Recommendation
- Distinguish EI-authenticated requests from real user sessions structurally: do not reuse `SessionUserKey` for EI auth, or add a distinct marker/flag consulted by `PipelineRunsController.Create` (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` presence and reject/route separately rather than relying on `GetAuthenticatedUser`).
- If EI-triggered job runs via numeric ID are intentionally disallowed (per the existing code comment), enforce it by checking `_, isEI := auth.GetAuthenticatedExternalInitiator(c); if isEI { reject }` in `PipelineRunsController.Create`, in addition to (or instead of) the `isUser` check.
- If EI job runs by ID should be allowed for their own job only, validate that the resolved job's `ExternalInitiatorWebhookSpecs` matches the authenticated EI ID before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test plan (Go, using existing test helpers like `cltest.CreateExternalInitiatorViaWeb`, `cltest.MustInsertWebhookSpec`, `cltest.UnauthenticatedPost`):
1. Create EI "ei-A" via `/v2/external_initiators`; capture `AccessKey`/`Secret`.
2. Create job A (webhook spec bound to ei-A) and an unrelated job B (e.g., a different webhook or non-EI job) with integer IDs `A.ID` and `B.ID`.
3. Using ei-A's credentials (`ExternalInitiatorAccessKeyHeader`/`ExternalInitiatorSecretHeader`), send `POST /v2/jobs/{B.ID}/runs` (job B's numeric ID, not associated with ei-A).
4. Assert current (vulnerable) behavior: request succeeds (200/201) and a pipeline run row is created for job B — i.e., `isUser` becomes true because `AuthenticateExternalInitiator` set `SessionUserKey`, bypassing the "EIs not allowed" comment/intent, and no job-EI binding check occurs.
5. Expected secure behavior (assertion for the fix): response should be `401 Unauthorized` or `422 Unprocessable Entity`, and `pipeline_runs` count should not increase (use `cltest.AssertCountStays`), for any job ID not bound to the requesting EI's webhook spec.
6. Table-test iterating multiple job IDs (owned by unrelated specs, plus the EI's own job) under the same EI session, asserting isolation holds only for the fixed code.

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
