### Title
Non-atomic `declare_work()` + channel `send()` in `TransactionStatusSender::send_transaction_status_batch` lets `DependencyTracker` mark unfinished work as processed, exposing stale Blockstore reads - (File: runtime/src/transaction_execution.rs, runtime/src/dependency_tracker.rs)

### Summary
`TransactionStatusSender::send_transaction_status_batch` calls `DependencyTracker::declare_work()` (an atomic counter fetch-add) and then separately calls `crossbeam_channel::Sender::send()` with no lock spanning both operations. Because `TransactionStatusSender` (and its internal `Arc<DependencyTracker>` / `Sender`) is cloned into multiple concurrent banking-stage/replay-stage worker threads, two threads can acquire work ids `N` and `N+1` in one order but enqueue their `TransactionStatusMessage::Batch` in the opposite order, breaking the dependency-tracker's documented invariant that "notifying id `s` implies all ids `< s` are processed."

### Finding Description
`send_transaction_status_batch` does: [1](#0-0) 
i.e. `declare_work()` then `self.sender.send(...)` with no synchronization tying the two together. `DependencyTracker::declare_work` is just an atomic `fetch_add`: [2](#0-1) 
and `mark_this_and_all_previous_work_processed` only compares the numeric id value, with no knowledge of arrival order: [3](#0-2) 

`TransactionStatusSender` is `Clone` and is handed out to every `ConsumeWorker`/`Committer` in the central-scheduler banking stage, so multiple OS threads hold live clones of the same underlying channel `Sender` and `Arc<DependencyTracker>`: [4](#0-3) [5](#0-4) 

Per-worker commit/send is guarded only by `bank.freeze_lock()`, which is an `RwLock` read lock allowing concurrent commits from multiple workers (it only blocks against a concurrent freeze, not against other workers): [6](#0-5) 
There is no global mutex spanning `declare_work()` + `send()` across workers, so thread A can call `declare_work()` (getting id `N`), be preempted, while thread B calls `declare_work()` (getting `N+1`) and completes `sender.send()` first. `TransactionStatusService` processes messages strictly in the order it dequeues them from the channel (FIFO of arrival, not of `work_id`): [7](#0-6) 
so it writes batch `N+1` and calls `mark_this_and_all_previous_work_processed(N+1)` while batch `N` (containing the earlier transaction, e.g. an `InitializeMint`/`SetAuthority`/`MintTo`) is still sitting unsent/unprocessed.

Separately, `OptimisticallyConfirmedBankTracker`'s notifier captures a "current declared work" snapshot (not a fresh `declare_work()` call) to gate delivery of `BankNotification::OptimisticallyConfirmed`: [8](#0-7) 
and that gate is enforced via `wait_for_dependency`, whose correctness depends entirely on the now-broken ordering invariant: [9](#0-8) [10](#0-9) 
If `mark_this_and_all_previous_work_processed(N+1)` fires before batch `N` is actually persisted, `wait_for_dependency(N)` (or any waiter requesting id `≤ N`) returns immediately even though the corresponding Blockstore write for `N` has not happened, since the comparison in `less_than` only checks numeric value, not real completion order.

### Impact Explanation
An RPC client's `getTransaction`/`getTokenAccountBalance`/subscription can be served a response computed from Blockstore state that lacks the mint-initializing/authority-setting transaction that was supposed to have already been committed according to the confirmation notification it just received, causing `parse_token.rs` (SPL Token decoding) to report stale or default (wrong) decimals/authority. This is a wrong-slot/fork/account-data-returned class issue against the RPC read path, driven purely by a leader-internal race that any transaction submitter can help trigger by causing concurrent banking-stage batches.

### Likelihood Explanation
Requires: (1) `dependency_tracker: Some(...)` configured (only enabled when the relevant notifier path is wired in), (2) multiple concurrent banking-stage/replay workers processing batches for the same or adjacent leader slots — a normal condition under load with the central multi-worker banking-stage scheduler, and (3) an unlucky-but-plausible thread preemption window between `declare_work()` and `sender.send()`. This is a genuine, narrow timing race dependent on OS thread scheduling that the attacker cannot directly control or reliably trigger on demand; it can only be encouraged (not guaranteed) by submitting many concurrent transactions to increase the chance of the interleaving. Reproducibility in production is probabilistic, though it is deterministically reproducible in a unit test using an explicit barrier as suggested.

### Recommendation
Make `declare_work()` and the corresponding channel `send()` atomic with respect to other producers — e.g., protect both steps with a single `Mutex` inside `TransactionStatusSender`/`DependencyTracker`, or restructure so the work id is assigned only inside a critical section that also performs the enqueue (e.g., have the channel itself hand back a strictly increasing sequence at send time rather than pre-declaring it). Alternatively, have `TransactionStatusService` track "processed" using a monotonically increasing counter of messages actually dequeued (in arrival order) rather than trusting the externally-declared numeric `work_id`, or make `wait_for_dependency` also verify the target id was truly dequeued, not just numerically superseded.

### Proof of Concept
Unit test in `runtime/src/dependency_tracker.rs` (or a new integration test alongside `rpc/src/transaction_status_service.rs`'s `test_event_synchronization`):
1. Create one `DependencyTracker` and one bounded `crossbeam_channel`.
2. Spawn thread A: call `declare_work()` (gets `N`), block on a `Barrier` before calling `send()`.
3. Spawn thread B: call `declare_work()` (gets `N+1`), immediately `send()` its message, then call (simulating `TransactionStatusService`) `mark_this_and_all_previous_work_processed(N+1)`.
4. Release the barrier so thread A finally sends its `N` message afterward.
5. Assert: at the moment `mark_this_and_all_previous_work_processed(N+1)` was called, the channel/Blockstore stub had not yet received/persisted message `N` — i.e., a waiter calling `wait_for_dependency(N)` unblocks before message `N`'s payload (e.g., simulated Blockstore write) is visible, demonstrating violation of "notifying id `s` implies all ids `< s` are processed."

    /// Notify all waiting threads that a work has been processed with the given work id.
    /// This function will update the processed work id and notify all waiting threads only if the work
    /// id is greater than the procsessed work id. Notify a work of id number 's' will
    /// implicitly imply that all work with id number less than 's' have been processed.
    pub fn mark_this_and_all_previous_work_processed(&self, work_id: u64) {
        let mut processed_work_id = self.processed_work_id.lock().unwrap();
        if less_than(&processed_work_id, work_id) {
            *processed_work_id = Some(work_id);
            self.condvar.notify_all();
        }
    }

    /// To wait for the dependency work with 'work_id' to be processed.
    pub fn wait_for_dependency(&self, work_id: u64) {
        if work_id == 0 {
            return; // No need to wait for work id 0 as real work starts from 1.
        }
        let mut processed_work_id = self.processed_work_id.lock().unwrap();
        while less_than(&processed_work_id, work_id) {
            processed_work_id = self.condvar.wait(processed_work_id).unwrap();
        }
