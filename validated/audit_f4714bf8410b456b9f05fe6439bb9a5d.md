### Title
Job command can disable the SIGTERM guard via `trap - TERM`, re-exposing bash's script-dump-on-cancellation leak - ([File: functions/script_legacy/internal/script_header.go])

### Summary
`ScriptHeader.Generate` installs `trap exit 1 TERM` once at the top of the generated script, but the user-authored commands from the `script` input run directly in that same top-level shell (no subshell isolation), so a job command such as `trap - TERM` can remove the guard for the remainder of the script. `functions/script_legacy/internal/executor.go` then runs the whole file directly with `bash tmpFile.Name()` via `gracefulexitcmd`, which sends SIGTERM to the process group on cancellation, so a subsequent cancellation SIGTERM hits an unguarded bash process.

### Finding Description
`ScriptHeader.Generate` writes a single top-level trap: `trap exit 1 TERM` [1](#0-0) . `ScriptGenerator.GenerateScript` appends the optional `GITLAB_ENV` sourcing preamble and then writes each job command from the `script` input directly into the same buffer via `CommandProcessor.ProcessCommand` — there is no `eval`, no subshell, and no per-command trap re-installation [2](#0-1) . The job's `script` array is fully attacker-controlled input from `builtinCtx.GetInput("script", ...)` in `script_legacy.go`'s `Run` [3](#0-2) .

Because trap state in bash is shell-global and every job command executes at top level in the very shell where the header set the trap, any authored line that is (or contains) `trap - TERM`, `trap '' TERM`, or a redefinition of the TERM handler overwrites the header's trap for the rest of the script. Unlike the fixed path in `functions/concrete/run/stages/internal/scriptwriter/scriptwriter.go`, which deliberately wraps the user script body in `(trap 'exit 1' TERM; eval ...) < /dev/null` specifically to re-establish the trap inside an isolated subshell so it cannot be undone by user code (per the comment referencing gitlab-runner#39005) [4](#0-3) , the `script_legacy` generator never isolates user commands from the guard trap at all.

The generated script is written to a temp file and run directly as `bash <tmpFile>` by `Executor.Execute`, using `gracefulexitcmd.New`, which is the mechanism that delivers SIGTERM to the process on cancellation [5](#0-4) . If the trap has been cleared by a prior job command, a cancellation-triggered SIGTERM reaches bash with no handler installed. The documented rationale in `shells/bash.go` explains the underlying bash behavior this guards against: on bash <4.4 a process killed by SIGTERM with no trap prints its current command, and on bash 5.3+ the parent shell prints the failed pipeline text when reaping a signal-killed child [6](#0-5) . Since `GITLAB_ENV` is sourced via a `while read` loop directly in the top-level script body (not an eval'd string), the specific "print the eval'd string" variant is less directly applicable here, but the general uncaught-SIGTERM print-current-command/pipeline behavior documented for bash still applies to whatever line was executing at the moment of the signal, which could include lines built from job/stage variables (e.g., the `while read -r line; do export "$line"` loop processing `GITLAB_ENV` content, or any subsequent authored command using masked/secret variables).

### Impact Explanation
If an authored job command clears the TERM trap and the runner later cancels the job, bash may print the currently-executing command/pipeline to stdout/stderr on termination instead of exiting cleanly, per the documented bash behavior this trap exists to prevent. Depending on what line bash was executing at the moment of the signal, this could reveal the literal text of the command being run — which could itself contain expanded variable values if the command line at that point references `GITLAB_ENV`-sourced variables or other job variables — landing in the job trace. This is a variable-leak/trace-hygiene issue rather than a sandbox escape.

### Likelihood Explanation
This requires an attacker who already controls the `script` input to the `script_legacy` builtin function (a normal pipeline author writing CI job script lines) and requires the runner-issued cancellation SIGTERM to arrive after the trap-clearing command executes but before the job finishes — both are realistic and fully attacker/timing-controllable (the author can loop, sleep, or otherwise structure their script to keep the window open, and cancellation timing can be induced by the job author themselves via `gitlab-ci-multi-runner cancel` equivalents or Web UI "Cancel" during a self-controlled sleep). No other guard (masking, sandbox, or a per-command subshell trap) exists in this code path to stop it, unlike the `scriptwriter.go` path, which was already hardened against exactly this scenario.

### Recommendation
Mirror the fix already applied in `functions/concrete/run/stages/internal/scriptwriter/scriptwriter.go`: run the user-authored commands inside an isolated subshell/`eval` block that re-installs `trap 'exit 1' TERM` inside that subshell (with stdin closed), so that any `trap` manipulation performed by job commands cannot escape the subshell boundary and cannot undo the outer guard. Apply the same pattern to `ScriptGenerator.GenerateScript` / `ScriptHeader.Generate` in `functions/script_legacy/internal`.

### Proof of Concept
Go integration test in `functions/script_legacy/internal` (build tag `integration`):
1. Build config with `commands := []string{"trap - TERM", "sleep 30"}`.
2. Call `NewScriptGenerator(config).GenerateScript(commands)` and run it through `Executor.Execute` with a cancellable `context.Context`.
3. After a short delay (once inside `sleep 30`), cancel the context so `gracefulexitcmd` sends SIGTERM.
4. Assert captured stdout/stderr does NOT contain script source text such as `"sleep 30"` or `"trap - TERM"`, and does NOT contain sourced `GITLAB_ENV` content, only clean termination.
5. As a control, run the same test without the `trap - TERM` line and confirm no leak occurs (validating the header's trap works when not tampered with), demonstrating the guard is bypassable specifically because of the missing subshell isolation.

func (g *ScriptGenerator) GenerateScript(commands []string) string {
	var buf strings.Builder

	buf.WriteString(g.header.Generate())

	if g.gitLabEnvFile != "" {
		// Export GITLAB_ENV so user commands can append KEY=VALUE pairs to it,
		// then source any variables written by previous stages. This mirrors
		// what AbstractShell.writeExports does for the legacy shell path.
		fmt.Fprintf(&buf, "export GITLAB_ENV=%q\n", g.gitLabEnvFile)
		fmt.Fprintf(
			&buf,
			"if [ -f %q ]; then while read -r line; do export \"$line\" || true; done < %q; fi\n\n",
			g.gitLabEnvFile,
			g.gitLabEnvFile,
		)
	}

	for i, cmd := range commands {
		g.processor.ProcessCommand(&buf, i, cmd)
	}

	return buf.String()
```

func (e *Executor) Execute(ctx context.Context, script string) error {
	tmpFile, err := os.CreateTemp("", "step-runner-script-*.sh")
	if err != nil {
		return fmt.Errorf("creating temporary script file: %w", err)
	}
	defer func() {
		_ = os.Remove(tmpFile.Name())
	}()

	if _, err := tmpFile.WriteString(script); err != nil {
		_ = tmpFile.Close()
		return fmt.Errorf("writing script to temporary file: %w", err)
	}

	if err := tmpFile.Chmod(0700); err != nil {
		_ = tmpFile.Close()
		return fmt.Errorf("making script executable: %w", err)
	}

	if err := tmpFile.Close(); err != nil {
		return fmt.Errorf("closing temporary script file: %w", err)
	}

	cmd := gracefulexitcmd.New(ctx, e.config.GracefulExitDelay, e.config.ShellPath, tmpFile.Name())

	cmd.Stdout = e.config.Stdout
	cmd.Stderr = e.config.Stderr
	cmd.Env = e.config.Env
	cmd.Dir = e.config.WorkDir

	return normalizeExitError(cmd.Run(), cmd.ProcessState)
```

	// Two separate bash code paths can dump the executed script body to
	// the job log when the cancellation kill loop signals a stage script:
	//
	//   - bash <4.4: a process killed by SIGTERM with no trap prints its
	//     current command before terminating (suppressed upstream in
	//     bash 4.4 by the DONT_REPORT_SIGTERM define).
	//   - bash 5.3+: the parent shell, on reaping a child that was killed
	//     by a signal, prints the failed pipeline's text — see the new
	//     print_pipeline call inside notify_of_job_status.
	//
	// With this trap installed both in the outer shell AND inside the
	// eval-subshell (traps reset to defaults across the subshell
	// boundary), SIGTERM in either context triggers a clean `exit 1`
	// instead of a signal-induced death, so neither code path fires. See
	// https://gitlab.com/gitlab-org/gitlab-runner/-/issues/39005.
	bashExitOnScriptTerminationSignal = `trap 'exit 1' TERM`
