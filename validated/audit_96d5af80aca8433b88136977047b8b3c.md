### Title
Stale per-epoch instant-withdraw receipt is never cleared on the funded-claim path, corrupting default recovery and permanently freezing claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug is a counter decremented on a shared exit path that one early-return path never incremented. The analog in `IdleCreditVault` is the inverse asymmetry on the same axis: the funded instant-withdraw claim path clears `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. The defaulted-epoch claim path later reads and decrements those stale counters unconditionally, causing underflow reverts, inflated default-claim basis, and permanently stuck recovery funds.

### Finding Description
`requestInstantWithdraw` records three paired pieces of state (`contracts/strategies/idle/IdleCreditVault.sol:356-375`):
- `instantWithdrawsRequests[_user] += _amount`
- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`
- `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` and `pendingInstantWithdraws += _amount`

On the normal (funded) path, `claimInstantWithdrawRequest` only zeroes the first counter (`IdleCreditVault.sol:387-392`); the two per-epoch counters remain populated after the receipt tokens are already burned and paid out.

After a borrower default and `finalizeDefaultRecovery`, `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:382-385`), which treats the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` as a live claim (`IdleCreditVault.sol:842-856`):

- `instantWithdrawsRequests[_user] -= claimBasis` underflows when the stale basis exceeds any new pending receipt (already-paid basis is counted a second time).
- `_burn(_user, claimBasis)` reverts because the receipt tokens were already burned at the funded claim.
- `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` succeeds only because the counter was also left stale, but the same staleness inflates `defaultPendingClaimBasis()` (`IdleCreditVault.sol:644-649`), which includes `instantWithdrawClaimsByEpoch[epochNumber]` while `pendingInstantWithdraws != 0`. Already-claimed-at-par receipts enter the recovery basis and dilute `defaultRecoveryPrice` for every genuine claimant.

Sequence (running epoch, non-programmable mode, unprivileged KYC'd lender):
1. Epoch N running, APR decreased → user calls `requestWithdraw`, gets an instant receipt via `requestInstantWithdraw`.
2. Manager calls `getInstantWithdrawFunds`; `collectInstantWithdrawFunds` funds the request (`pendingInstantWithdraws` → 0).
3. User calls `claimInstantWithdrawRequest` and is paid at par. `instantWithdrawsRequestsByEpoch[user][N]` and `instantWithdrawClaimsByEpoch[N]` stay non-zero.
4. Borrower fails to repay at `stopEpoch`; `_handleBorrowerDefault` fires and `finalizeDefaultRecovery` computes `defaultRecoveryPrice` over an inflated basis that includes step-3's already-paid receipt.
5. User makes (or already holds) a second instant receipt in epoch N smaller than the stale+new per-epoch sum. `_claimDefaultedInstantWithdrawRequest` reverts inside `claimInstantWithdrawRequest`, so the user's still-funded receipt can never be claimed. Meanwhile every other defaulted-epoch instant claimant's payout is haircut by the phantom basis.

### Impact Explanation
Two effects: (a) permanent freezing — any user who claimed a funded instant receipt and then holds another receipt in the same epoch can never execute `claimInstantWithdrawRequest` after default finalization because `_claimDefaultedInstantWithdrawRequest` always reverts first (underflow on `instantWithdrawsRequests[_user]` or `_burn` on already-burned receipts); their strategy-token receipt becomes unspendable. (b) Recovery dilution — already-settled claims are double-counted in `defaultPendingClaimBasis`, lowering `defaultRecoveryPrice` for all legitimate defaulted-epoch claimants; the excess reserve becomes unclaimable dust. Loss is bounded by the aggregate of instant withdrawals funded and claimed within the defaulting epoch.

### Likelihood Explanation
Requires instant withdrawals enabled (non-programmable deployment), a funded instant claim, and a borrower default within the same epoch — the same epoch index is retained because `epochNumber` only increments on a successful `stopEpoch` deposit, so no epoch boundary is needed between the claim and the default. The trigger path uses only ordinary lender actions; the second receipt can arise naturally since instant requests remain open during a running epoch. No privileged or malicious role is needed.

### Recommendation
In `claimInstantWithdrawRequest` (or a dedicated internal clear), mirror the decrement pattern used elsewhere: when paying a funded receipt, also subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`, analogous to how `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws`. Alternatively, have `_claimDefaultedInstantWithdrawRequest` skip users whose `instantWithdrawsRequests[_user]` no longer covers the per-epoch basis, but clearing the per-epoch entries at claim time is the consistent fix since `defaultPendingClaimBasis` relies on them being accurate.

### Proof of Concept
A Foundry fork PoC on the credit-vault deployment would: (1) start an epoch with AA deposits, drop APR so `requestWithdraw` routes to `requestInstantWithdraw`; (2) call `getInstantWithdrawFunds` then `claimInstantWithdrawRequest`, asserting `instantWithdrawsRequestsByEpoch(user, epochNumber)` is still non-zero; (3) open a second, smaller instant request in the same epoch; (4) make the borrower fail repayment at `stopEpoch`, run `finalizeDefaultRecovery`; (5) show `claimInstantWithdrawRequest` reverts for the user and that `defaultRecoveryPrice` is lower than the price computed without the stale basis. Uncertainty: I could not fully trace `finalizeDefaultRecovery`/`_defaultPrefundedInstantReserve` within the iteration budget — whether the prefunded-reserve accounting partially offsets the inflated basis should be confirmed when writing the PoC.
