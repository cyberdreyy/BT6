### Title
Withdrawal receipts act as non-expiring sessions — revoked/delisted wallets can still claim funds after Keyring credential revocation - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` enforces the Keyring KYC credential via `isWalletAllowed` on every *entry* path (`_deposit`, `depositDuringEpoch`, `requestWithdraw`), but never re-validates the credential on the *exit* path. `claimWithdrawRequest` and `claimInstantWithdrawRequest` forward straight to `IdleCreditVault` with no `isWalletAllowed(msg.sender)` check, and the vault itself performs no credential check either. A withdraw receipt therefore behaves exactly like a non-expiring session cookie: once issued, it authenticates the holder's payout "as long as the account exists," regardless of subsequent credential revocation.

### Finding Description
- `isWalletAllowed` checks `IKeyring(keyring).checkCredential(keyringPolicyId, _user)` [1](#0-0) .
- Deposits enforce it: `_deposit` reverts if `!isWalletAllowed(msg.sender)` [2](#0-1) , as does `depositDuringEpoch` [3](#0-2) .
- `claimWithdrawRequest` (and `claimInstantWithdrawRequest`) contain only the instant-withdraw flag check — no credential check [4](#0-3) .
- The vault-side `claimWithdrawRequest` burns the user's receipt tokens and pays out purely from the `withdrawsRequests`/`apr0Users` accounting keyed to the address, with no KYC gate [5](#0-4) .
- Funded receipts remain claimable forever — the epoch gate (`epochNumber <= lastWithdrawRequest`) only enforces a *minimum* wait, never an expiry [6](#0-5) .

Analog to CVE-2022-2888: the session (withdraw receipt) is established under a valid credential and is then usable indefinitely — revocation of the underlying credential never invalidates it.

### Impact Explanation
Consider the standard Keyring compromise response: a lender's wallet key is compromised and the lender (or Keyring admin) revokes that wallet's credential so the attacker cannot interact with the vault. The revocation successfully blocks new deposits and new withdraw requests from the compromised wallet — but any already-matured withdraw receipt the victim holds remains claimable. The attacker, controlling the revoked wallet, calls `claimWithdrawRequest()` and receives the full funded payout (principal + accrued interest, or the haircutted recovery amount post-default). Funds that revocation was meant to freeze are drained to the attacker — direct theft of unclaimed principal and yield, quantified as the victim's entire `withdrawsRequests[user] + apr0 settled amounts` balance.

### Likelihood Explanation
Requires (a) a lender wallet with a matured, unclaimed withdraw receipt, and (b) compromise of that wallet followed by credential revocation. Wallet compromise is the canonical scenario Keyring revocation exists for, and receipts are designed to sit unclaimed for arbitrary durations ("old requests can still be claimed"), so the exposure window is permanent by design. The attacker needs no privileged role — they are merely a (formerly) KYC-passing lender's compromised key.

### Recommendation
Add `isWalletAllowed(msg.sender)` validation to `claimWithdrawRequest` and `claimInstantWithdrawRequest` in `IdleCDOEpochVariant`, or alternatively provide an escape hatch (e.g., guardian-assisted `claimFor` to a re-KYC'd wallet) so revocation freezes payouts without permanently stranding honest users' funds.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
// Foundry fork test against IdleCDOEpochVariant + IdleCreditVault
function testRevokedWalletStillClaims() public {
    // 1. KYC'd user deposits and requests withdraw during buffer
    _depositWithUser(victim, 10_000e6, true);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(victimAAbal, address(AAtranche));

    // 2. Epoch runs, borrower repays, stopEpoch funds the receipt
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, apr, fundsNeeded);

    // 3. Victim's key is compromised; Keyring revokes the credential
    vm.mockCall(
        keyring,
        abi.encodeWithSelector(IKeyring.checkCredential.selector, policyId, victim),
        abi.encode(false)
    );
    assertFalse(cdoEpoch.isWalletAllowed(victim)); // credential revoked

    // 4. Attacker (controlling victim key) cannot deposit or request...
    vm.prank(victim);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.depositAA(1e6);

    // ...but the stale "session" (receipt) still authenticates the payout
    uint256 balPre = underlying.balanceOf(victim);
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest(); // succeeds despite revocation
    assertGt(underlying.balanceOf(victim), balPre, "revoked wallet drained funded claim");
}
```

*Uncertainty note:* whether this crosses the severity bar depends on treating the compromised wallet's pending claim as stealable yield — the receipt is owed to that address regardless, so the loss materializes only in the compromise-and-revoke scenario above rather than for arbitrary attackers. If the intended design is that claims are unconditionally address-bound, the gap is that credential revocation provides no protection at all for the largest single payout a lender ever receives.

  function claimWithdrawRequest(address _user) external returns (uint256 amount) {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized) {
      // Post-default requests are already priced after the haircut and backed by the reserve,
      // so they must not fall through to the defaulted-epoch receipt logic.
      amount = _claimPostDefaultWithdrawRequest(_user);
      if (amount != 0) return amount;
      // Only receipts created in the defaulted epoch are haircutted here; old fulfilled
      // receipts are handled below at par if they were already funded before default.
      amount = _claimDefaultedWithdrawRequest(_user);
    }
    amount += _claimLossAdjustedWithdrawRequest(_user);
    return amount + _claimFundedWithdrawRequest(_user);
  }

  /// @notice Claim a funded non-default withdraw request at par.
  /// @param _user address of the user
  /// @return amount amount claimed
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
