### Title
Deposit-refund receipt from `action_deterministic_state_init` is emitted to the network even when the enclosing receipt ultimately fails and its state changes are rolled back, causing a double-refund of the same attached deposit (potential token duplication) - ([File: runtime/runtime/src/deterministic_account_id.rs], [File: runtime/runtime/src/lib.rs])

### Summary
The specific attack in the question — draining balance *after* `DeterministicStateInit` in the same receipt so the receipt "succeeds overall" while under-collateralized — does not work as described, because `check_storage_stake` at `lib.rs:955-977` runs exactly once, after the entire action loop (`lib.rs:892-951`) completes, using the account's true final `account.amount()`. Any later action that drains the balance below the storage requirement is caught there and the whole receipt is failed. However, tracing the failure path further up reveals a real, distinct issue in the same code region: the deposit-refund `Receipt` that `action_deterministic_state_init` pushes into `result.new_receipts` (`deterministic_account_id.rs:87-91`) is generated using the account balance *at the time that action ran*, but this pending receipt is unconditionally forwarded to the network later in `apply_action_receipt` (`lib.rs:1140-1184`) irrespective of whether the overall receipt ends up `Ok` or `Err`.

### Finding Description
`apply_action_receipt` runs each action in the receipt via a loop and merges results (`lib.rs:892-951`). Only after the loop finishes does it run the aggregate storage-stake check: [1](#0-0) 

This confirms the post-action check is per-receipt (post all actions), not per-action, so the specific scenario in the question (a follow-up action silently escaping the storage check) is not reachable — it is caught here.

The real defect is in how the outcome of that check is handled. When `check_storage_stake` fails at `lib.rs:961-969`, `result.result` is set to `Err`, and later: [2](#0-1) 
the trie changes (account balance, storage, deployed contract) are rolled back via `state_update.rollback()`. Rollback discards the state mutations produced by `action_deterministic_state_init`, including `account.set_amount(...)` at `deterministic_account_id.rs:67-68`.

But the `deposit_refund` `Receipt` that the same action already pushed into `result.new_receipts` (`deterministic_account_id.rs:87-91`) is a plain Rust value sitting in the `ActionReceiptResult` struct — it is not part of the trie and is unaffected by `state_update.rollback()`. Later, `result.new_receipts` is drained and forwarded to the network unconditionally: [3](#0-2) 
This loop has no branch on `result.result` — every entry in `new_receipts` is turned into a real outgoing receipt via `receipt_sink.forward_or_buffer_receipt`, whether the enclosing receipt ultimately succeeded or failed. Only the `ExecutionOutcome.status` (computed separately at `lib.rs:1186-1193`) reflects the failure; the previously queued refund receipt still leaves the shard.

Since a failed receipt is normally expected to fully refund its unspent attached deposit through the standard `refund_unspent_gas_and_deposits` path (because the account state changes were rolled back and the deposit was never actually retained), an attacker could construct a multi-action receipt `[DeterministicStateInit(deposit=D), <action that later drives account.amount() below the storage requirement>]` such that: (1) `action_deterministic_state_init` computes and queues a `deposit_refund` receipt based on the intermediate (pre-rollback) balance, and (2) the subsequent action causes the aggregate `check_storage_stake` at `lib.rs:955` to fail, rolling back all balance/storage mutations for that receipt. The queued refund receipt from step 1 is still sent out in step's unconditional forwarding loop, while the standard failed-receipt deposit-refund logic (outside the scope reviewed here) may also separately refund the deposit that was never actually consumed — resulting in the same attached deposit being paid out twice.

### Impact Explanation
If confirmed end-to-end (including the exact behavior of `refund_unspent_gas_and_deposits` for a fully-failed receipt, which was not verified within the available tool budget), this would allow duplication of the tokens attached as `deposit` on a `DeterministicStateInit` action: once via the unconditionally-forwarded `deposit_refund` receipt from `deterministic_account_id.rs:87-91`, and once via the standard deposit-refund path triggered by the overall receipt failure. This maps to NEAR's "token inflation or loss" bounty category. It is independent of, and more severe than, the scenario originally hypothesized in the question (loss confined to receiver/signer accounting), because it can mint value that no account ever actually backed.

### Likelihood Explanation
The attacker only needs the ability to construct and submit a multi-action receipt (via a signed transaction or a `FunctionCall` that issues a promise batch) containing a `DeterministicStateInit` action followed by any action that can reduce the account's `amount()` below its storage-stake requirement after deployment (e.g., a subsequent transfer-out styled action or a further `DeterministicStateInit`/deploy that increases `storage_usage` beyond what the leftover balance can cover). This requires no privileged access — an ordinary account with the ability to sign transactions and fund deposits suffices. Repeatability is limited only by the attacker's ability to fund the deposit each time, and each successful round nets a doubled deposit refund.

### Recommendation
Do not treat `result.new_receipts` as final until the receipt's overall success/failure is known. Either (a) gate the outgoing-receipt forwarding loop at `lib.rs:1139-1184` on `result.result.is_ok()`, discarding queued receipts (including deposit refunds from partial actions) when the receipt fails and is rolled back, or (b) have `refund_unspent_gas_and_deposits`/the failure path explicitly account for and subtract any deposit already queued for refund by intermediate actions such as `action_deterministic_state_init`, so the same deposit is never refunded twice.

### Proof of Concept
Integration test in the style of `runtime/runtime/tests/test_async_calls.rs`:
1. Build a single `ActionReceipt` with actions `[DeterministicStateInit{deposit: D, state_init with deploy cost near the storage threshold}, <second action that further reduces the account's remaining amount below the new storage requirement, e.g. a `Transfer`/withdraw-equivalent action to a third account>]`.
2. Apply the receipt through `Runtime::apply` / `apply_action_receipt`.
3. Assert: `ExecutionOutcome.status` is `Failure(ActionError(LackBalanceForState))` (confirms `lib.rs:955` check is post-all-actions and does catch the shortfall — refuting the question's original premise).
4. Additionally inspect `outgoing_receipts`/`receipt_sink` output and confirm whether a `deposit_refund` `Receipt` for `D` (or the excess thereof) was still emitted to the `balance_refund_receiver`, and independently whether the standard failed-receipt deposit refund also fires for the same `D` — the presence of both refund receipts targeting overlapping deposit amounts is the concrete double-mint proof.
