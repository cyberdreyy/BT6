### Title
Broken/stale liability oracle in a single bank permanently bricks withdrawals of unrelated collateral from a marginfi account - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
Marginfi accounts can hold balances across many banks simultaneously (up to `MAX_LENDING_ACCOUNT_BALANCES`), analogous to a multi-market vault. The risk engine deliberately tolerates broken/stale **asset** oracles by zeroing that balance's contribution, but it does **not** extend the same tolerance to **liability** oracles — any oracle error on a bank where the account has an outstanding borrow is propagated as a hard error that aborts the entire health check. Since `check_account_init_health` is required (and must price every active balance) on `lending_account_withdraw`/`lending_account_borrow` (and the equivalent Kamino/Drift/Solend/JupLend paths), a single permanently-broken oracle on a bank the user has borrowed from freezes the user's ability to withdraw collateral from every *other*, unrelated, and otherwise healthy bank in the same account — mirroring the Perennial `BalancedVault` M-16 bug class where one broken market permanently locks funds across the whole multi-market position.

### Finding Description
The risk engine computes account health balance-by-balance via `calc_weighted_value_for_balance` / `calc_weighted_value_standalone` [1](#0-0) .

For **assets**, an oracle failure is explicitly forgiven — the balance is skipped and priced as zero rather than aborting the whole call: [2](#0-1) 

This lenient behavior is also documented at the `HealthCache` level: "Errors in asset oracles are ignored (with prices treated as zero)" [3](#0-2) .

For **liabilities**, the same function does the opposite: it explicitly re-raises the underlying oracle error instead of tolerating it: [4](#0-3) 

Because Rust's `?`/`return Err` propagates out of `calc_weighted_value_for_balance` and up through `get_health_components`'s per-balance loop [5](#0-4) , any single active liability balance whose bank oracle is broken (stale Pyth/Switchboard feed, wrong oracle keys, deprecated/delisted feed with no admin able to fix it) causes `check_account_init_health` to fail unconditionally, for the whole account, regardless of how healthy the account's other balances are.

`check_account_init_health` (and thus this failure mode) gates every outflow instruction: `lending_account_withdraw` [6](#0-5) , `lending_account_borrow`, and the integration-specific withdraw paths (Drift, JupLend, Solend, Kamino) which all call the identical `check_account_init_health` gate before releasing funds [7](#0-6) [8](#0-7) [9](#0-8) .

The protocol's own documentation confirms the design assumption that all banks/oracles for all balances must be priceable for the check to succeed: "Accounts requiring the Risk Engine check must pass all Banks and Oracles involved in the user's Balances in remaining accounts" [10](#0-9) . There is no partial/emergency withdrawal path that lets a user pull collateral out of unaffected banks while excluding the bank with the broken liability oracle — every one of these instructions requires the full liability set to resolve to a price.

### Impact Explanation
If any bank a user has borrowed from suffers a permanent/irrecoverable oracle failure (e.g., a Pyth push feed for a delisted/failed asset stops updating forever, or oracle configuration becomes unfixable), the user's entire marginfi account becomes frozen for outflows:
- They cannot `lending_account_withdraw` collateral from any other, unrelated, healthy bank.
- They cannot `lending_account_borrow` against other collateral.
- Repay is nominally risk-free, but if the user lacks idle funds and must first withdraw/sell other collateral to source repayment, they cannot do so, since that withdrawal itself requires the now-permanently-failing health check.

This is a durable freeze of user funds with financial effect: collateral deposited in fully solvent, unrelated banks becomes permanently inaccessible as a side effect of a single bank's oracle breaking — the same failure mode Sherlock accepted as Medium severity in the Perennial `BalancedVault` case ("a vault with n markets is exposed to 2n possible problems... if even only one of the products is paused/breaks, the vault would jam, with no contingency measures").

### Likelihood Explanation
This requires no privileged action or admin cooperation to trigger the *freeze condition* once an oracle is genuinely broken (delisted feed, permanently stale, or misconfigured with no fix available) — an ordinary unprivileged borrower is affected purely by holding a position in the affected bank. Given marginfi's permissionless bank creation model (any asset/oracle can get a bank), and reliance on third-party oracle infrastructure (Pyth admin-maintained feeds, Switchboard cranking) that is explicitly called out in project docs as a source of risk, this is a realistic, reachable scenario rather than a purely theoretical one.

### Recommendation
Apply the same tolerant treatment used for broken asset oracles to liability oracles when computing account health for **outflow** instructions unrelated to the broken bank: e.g., allow the health check to proceed (using a fallback high/conservative valuation, or the last-cached price) for a liability whose oracle is unreadable, or provide an explicit isolated/partial-withdraw path that lets users pull collateral from banks unrelated to the broken liability, consistent with the recommendation from the original Perennial finding (implement a partial/emergency withdrawal, or document/bound the blast radius of one bank's oracle failure).

### Proof of Concept
1. User deposits collateral (Token A) into Bank A and borrows USDC from Bank B.
2. Bank B's oracle enters a permanently broken state (e.g., stale Pyth push price with no further updates, per `calc_weighted_liab_value_standalone`'s propagated `PythPushStalePrice`/`SwitchboardStalePrice` errors) [4](#0-3) .
3. User calls `lending_account_withdraw` to withdraw excess Token A collateral from Bank A (unrelated to the broken oracle).
4. `check_account_init_health` iterates all active balances, including the USDC liability in Bank B; pricing that liability returns `Err`, which propagates and the whole instruction reverts [11](#0-10) .
5. The user's Token A collateral in the healthy Bank A remains permanently locked as long as Bank B's oracle stays broken, with no alternative code path to isolate/exit the unaffected position.

fn calc_weighted_value_for_balance(
    balance: &Balance,
    bank: &Bank,
    price_adapter_result: &MarginfiResult<OraclePriceFeedAdapter>,
    requirement_type: RequirementType,
    emode_config: &EmodeConfig,
    liq_cache: &mut Option<&mut LiquidationPriceCache>,
    position_index: usize,
) -> MarginfiResult<(I80F48, I80F48, I80F48, u32)> {
    match balance.get_side() {
        Some(side) => match side {
            BalanceSide::Assets => {
                let (value, price, err_code) = calc_weighted_asset_value_standalone(
                    balance,
                    bank,
                    price_adapter_result,
                    requirement_type,
                    emode_config,
                    liq_cache,
                    position_index,
                )?;
                Ok((value, I80F48::ZERO, price, err_code))
            }
            BalanceSide::Liabilities => {
                let (value, price) = calc_weighted_liab_value_standalone(
                    balance,
                    bank,
                    price_adapter_result,
                    requirement_type,
                    liq_cache,
                    position_index,
                )?;
                Ok((I80F48::ZERO, value, price, 0))
            }
        },
        None => Ok((I80F48::ZERO, I80F48::ZERO, I80F48::ZERO, 0)),
    }
}
