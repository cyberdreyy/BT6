### Title
Claimed instant-withdraw receipts are never removed from the epoch index, inflating default-recovery basis and permanently stranding recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears the aggregate receipt counters (`instantWithdrawsRequests[user]`) but never refreshes the per-epoch slot `instantWithdrawsRequestsByEpoch[user][epochNumber]` nor decrements `instantWithdrawClaimsByEpoch[epochNumber]` — the direct analog of the msl.c bug where a stale stack index leaves an image in the wrong slot, never freed. If the epoch later defaults, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` count already-claimed receipts as live claims and already-held reserve, so `finalizeDefaultRecovery` computes a wrong `defaultRecoveryPrice`, and the phantom claims' reserve share is locked in the strategy forever.

### Finding Description
When a user requests an instant withdraw, the strategy records the receipt in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366–374). [1](#0-0) 

When the claim is funded, `claimInstantWithdrawRequest` only zeroes `instantWithdrawsRequests[_user]` and pays out; the two per-epoch entries are left stale:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

`collectInstantWithdrawFunds` likewise decrements `pendingInstantWithdraws` but never touches `instantWithdrawClaimsByEpoch`. [3](#0-2) 

If the borrower then defaults in the same epoch, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still contains the already-paid receipt — into the recovery basis. [4](#0-3)  Simultaneously `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstantWithdraws` (which includes the paid-out amount) as underlying still held by the strategy, inflating `reserveAmount` in `finalizeDefaultRecovery`. [5](#0-4) [6](#0-5) 

The stale slot can never be claimed a second time: `_claimDefaultedInstantWithdrawRequest` would underflow on `instantWithdrawsRequests[_user] -= claimBasis` for the already-paid user (receipt tokens were burned). [7](#0-6) 

### Impact Explanation
Two concrete effects after `finalizeDefaultRecovery`:

1. **Permanent freezing / leaked reserve.** The ghost claim basis of already-paid users inflates `totalBasis`. Their share of `defaultRecoveryReserve` is budgeted but never claimable (no receipt tokens exist), so a proportional slice of every recovered token is stranded in the strategy with no withdrawal path.
2. **Insolvency/dilution of honest claimants.** `defaultRecoveryPrice = reserveAmount / totalBasis` is computed with a phantom denominator (and a phantom prefunded-reserve numerator for funds already transferred out), so real defaulted-epoch withdraw and instant-withdraw claimants recover less than the true pro-rata share — a direct loss proportional to the previously claimed instant volume.

Example: epoch N, users request 1,000 of instant withdrawals; 600 are funded and claimed (paid out), 400 remain pending. Borrower defaults, 200 is recovered. Correct basis ≈ active + 400; actual basis includes +600 ghost claims, and `prefundedReserve` credits the strategy with +1000−400=600 "held" funds that are in fact gone. The 600-basis reserve share is permanently locked and the price misprices every real claim.

### Likelihood Explanation
Requires a borrower default in an epoch where some instant-withdraw receipts were funded and claimed while others remained pending (`pendingInstantWithdraws != 0` at `finalizeDefaultRecovery`, making `defaultInstantWithdrawsFinalized` true). This is a normal, expected sequence — partial instant funding followed by default — with no attacker privilege needed; any KYC'd lender triggers the stale-slot state simply by claiming a funded instant withdrawal before the default. The bug is deterministic once that sequence occurs.

### Recommendation
Keep the per-epoch index in sync with the aggregate counters. In `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount (tracking the request epoch per user if requests can span epochs). Alternatively, decrement `instantWithdrawClaimsByEpoch` inside `collectInstantWithdrawFunds` so the epoch basis reflects only unclaimed receipts, and reconcile `_defaultPrefundedInstantReserve` with actual held balance.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
