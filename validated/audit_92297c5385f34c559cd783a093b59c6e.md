## Title
Signed-to-unsigned timestamp conversion in gateway staleness check allows bypass of anti-replay validation - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The `HandleLegacyUserMessage` staleness check in the gateway's WebAPI capabilities handler performs unsigned integer arithmetic on an attacker-controlled, signed `Timestamp` field without validating its sign or range first. This is the same bug class as the reported `abs()` issue: an unchecked signed→unsigned conversion of an extreme/negative input value causes silent wraparound, defeating a security-relevant check instead of erroring out.

### Finding Description
`HandleLegacyUserMessage` decodes a `webapicap.TriggerRequestPayload` (whose `timestamp` field is a signed `int64`, per the schema) directly from the untrusted message body sent by an external client to the gateway: [1](#0-0) 

It then validates freshness with: [2](#0-1) 

The relevant check is:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
``` [3](#0-2) 

`payload.Timestamp` is declared as a signed 64-bit integer in the trigger schema: [4](#0-3) 

If an attacker supplies a negative `Timestamp` (or one far outside a realistic Unix-time range), `uint(payload.Timestamp)` performs a raw bit-reinterpretation, producing a value close to `math.MaxUint64` (analogous to how negating `math.MinInt256` in the `abs` bug silently produces the same negative value instead of erroring). Because the left side (`uint(now) - maxAge`) is a normal, small Unix-timestamp-scaled number, the comparison `LHS > hugeRHS` is always false — the staleness check never triggers, regardless of the actual configured `MaxAllowedMessageAgeSec`.

### Impact Explanation
This check is the only guard against "stale message" replay for legacy user messages accepted by the gateway before they are forwarded to every DON member: [5](#0-4) 
An unprivileged client can craft a `web_api_trigger` request with a negative or otherwise malformed `timestamp` to unconditionally bypass this freshness/anti-replay validation, allowing replay or injection of trigger events with arbitrary claimed ages into the DON, undermining the intended request-freshness security property enforced at the internet-facing gateway boundary.

### Likelihood Explanation
The `HandleLegacyUserMessage` path is reachable directly from any external, unauthenticated caller sending JSON payloads to the gateway (no allowlist/authorization is applied before this timestamp check — the code even notes "TODO: apply allowlist and rate-limiting here" further down): [6](#0-5) 
Triggering it only requires setting a negative or out-of-range integer in the JSON `timestamp` field, which is trivial for any client capable of sending a request.

### Recommendation
Validate `payload.Timestamp` is non-negative (and within a sane bound) before converting to `uint`, or perform the comparison entirely in signed 64-bit arithmetic (e.g. compare `time.Now().Unix() - int64(h.config.MaxAllowedMessageAgeSec)` against `payload.Timestamp` as `int64`), rejecting the message if `payload.Timestamp < 0` or if the subtraction/comparison indicates staleness — mirroring the recommended fix in the original report of using a safe/checked operation rather than raw signed-to-unsigned conversion.

### Proof of Concept
1. Send a `web_api_trigger` message to the gateway with payload `{"trigger_id": "...", "trigger_event_id": "...", "timestamp": -1, "topics": [...], "params": {}}`.
2. `payload.Timestamp` is `-1` (int64); `uint(payload.Timestamp)` evaluates to `18446744073709551615` (max uint64).
3. `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec` is a small number (~1.7 billion), which is never greater than the wrapped value, so the "stale message" branch at [7](#0-6)  is never taken, and the forged/expired message is forwarded to all DON members unchecked.

**Note:** I was unable to directly view the Go struct definition for `webapicap.TriggerRequestPayload` (only the generated file names matched, not their contents in the index), so the `int64` type of `Timestamp` is inferred from the JSON schema (`"format": "int64"`) rather than confirmed against the generated Go source directly. If the underlying Go field were unexpectedly declared as `uint64` instead, this specific analog would not apply — a Devin session with full repo access could confirm the generated struct definition to remove this uncertainty.

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	body := msg.Body
	var payload webapicap.TriggerRequestPayload
	codec := api.JsonRPCCodec{}
	err := json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}
