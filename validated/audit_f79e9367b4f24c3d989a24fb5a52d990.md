### Title
`claimInstantWithdrawRequest` pays unfunded instant receipts, letting one funded receipt (or any strategy balance) authenticate payout of the whole receipt set - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Hickory bug authenticates an entire RRset once a single DNSKEY is verified. The analog lives in `IdleCreditVault.claimInstantWithdrawRequest`: the strategy tracks per-epoch instant-receipt basis (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) and an unfunded remainder (`pendingInstantWithdraws`), but the claim path verifies none of that. It burns the user's aggregate `instantWithdrawsRequests` balance and pays it in full from whatever underlying the strategy holds. A single funded receipt — or even a purely unfunded receipt claimed early — therefore "authenticates" the whole receipt set, and unfunded claims are paid with funds reserved for funded claimants.

### Finding Description
`requestInstantWithdraw` mints a 1:1 strategy-token receipt and records per-epoch basis plus the global `pendingInstantWithdraws`. Funding arrives later via `collectInstantWithdrawFunds`, which pulls underlying from the CDO and decrements `pendingInstantWithdraws` — but never marks *which* receipts were funded. The code explicitly contemplates partial funding: `_defaultPrefundedInstantReserve` handles the case where "cash covered only part of the instant queue".

`claimInstantWithdrawRequest` then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` only guards `defaultRecoveryReserve` — nothing checks that the user's receipts were actually funded. So while `pendingInstantWithdraws > 0` (i.e., the instant queue is underfunded), any holder of an instant receipt can claim 100% of it, spending underlying that economically belongs to the funded subset of `instantWithdrawClaimsByEpoch`. The "verify one element, trust the whole set" flaw appears in two forms:

- **Cross-user**: an attacker whose receipt is part of the unfunded remainder claims before honest funded claimants, stealing their payout; later claims revert or underpay.
- **Within one user**: a funded receipt from an earlier epoch legitimizes a later, unfunded receipt in the same aggregate `instantWithdrawsRequests` balance.

### Impact Explanation
Direct theft. The stolen amount is bounded by the unfunded remainder `pendingInstantWithdraws` (equivalently `instantWithdrawClaimsByEpoch[epochNumber]` minus funded cash). Every wei paid to an unfunded receipt is taken from funded claimants (or, after default finalization would have occurred, from what should have become `defaultRecoveryReserve`/prefunded reserve). Loss is quantifiable as `min(attackerReceipt, strategyUnderlyingBalance - defaultRecoveryReserve)` while the queue is underfunded.

### Likelihood Explanation
Requires an epoch phase where instant withdraws are only partially funded — the code's own comments (`_defaultPrefundedInstantReserve`, "cash covered only part of the instant queue") confirm this state is reachable when the CDO lacks sufficient liquid balance at `startEpoch`/funding time. The attacker is any unprivileged tranche holder with an instant receipt; claiming is permissionless via `IdleCDOEpochVariant.claimInstantWithdrawRequest`. No privileged misbehavior is needed — honest manager/borrower simply underfund because liquidity is lent out. Ordering is the only race factor, favoring whoever claims first.

### Recommendation
Track funded vs. unfunded instant receipts per epoch (a `fundedInstantClaimsByEpoch` or per-user funded basis) and, in `claimInstantWithdrawRequest`, pay only the funded portion — e.g., `min(instantWithdrawsRequests[_user], fundedBasis)` — or revert while `pendingInstantWithdraws` still covers the user's epoch basis. Alternatively, extend `_transferFundedClaim` to also exclude underlying earmarked for still-unfunded instant claims, mirroring the `defaultRecoveryReserve` guard.

### Proof of Concept
Foundry fork test (mainnet fork, same setup style as `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testUnfundedInstantReceiptStealsFundedClaims() public {
    // setup: victim and attacker are KYC'd LPs holding AA tranche tokens
    // epoch is running; both request instant withdraws
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(100e6, address(AAtranche)); // or the epoch-variant entry point
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(100e6, address(AAtranche));

    // strategy state: instantWithdrawClaimsByEpoch[epoch] = 200e6
    // borrower/CDO only has 100e6 liquid -> collectInstantWithdrawFunds(100e6)
    // pendingInstantWithdraws = 100e6 (half the queue unfunded)

    // attacker claims first: receives full 100e6 despite receipt being unfunded
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - pre, 100e6);

    // victim's funded receipt can no longer be paid in full
    vm.prank(victim);
    vm.expectRevert(); // underflow / insufficient balance
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Note: I was unable to fully trace `startEpoch`/`collectInstantWithdrawFunds` call sites in `IdleCDOEpochVariant` within this session, so the exact entry-point names for requesting instant withdraws and the precise conditions under which partial funding occurs should be confirmed against `contracts/IdleCDOEpochVariant.sol` (`getInstantWithdrawFunds` / `_startEpochProgrammableBorrower` paths). If the funding call always collects the full `pendingInstantWithdraws` or reverts atomically, the underfunded state — and hence this attack — would be unreachable outside the already-handled default path.
