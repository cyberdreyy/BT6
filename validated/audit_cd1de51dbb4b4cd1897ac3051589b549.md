## Analog Found

### Title
Internal Provider/Database Error Details Leaked in `base_meterBundle`/`base_meterBlockBy*` RPC Error Responses - (File: crates/execution/metering/src/rpc.rs)

### Summary
The `base` namespace metering RPC methods (`base_meterBundle`, `base_meterBlockByHash`, `base_meterBlockByNumber`) format raw internal error values (from `reth_provider`/state-provider/database layers) directly into the JSON-RPC error `message` field returned to the caller, instead of returning a generic, redacted error like the pattern used elsewhere in the codebase (e.g. consensus `admin.rs` or `tx-manager` error classification).

### Finding Description
`MeteringApiImpl::meter_bundle`, `get_l1_block_info`, and `meter_block_internal` wrap fallible provider/database calls and interpolate the underlying error `Display` output straight into an `ErrorObjectOwned` message sent back over JSON-RPC: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

These handlers accept attacker-supplied input (an arbitrary RLP-encoded transaction bundle in `meter_bundle`, or arbitrary block hash/number in `meter_block_by_hash`/`meter_block_by_number`) and, on failure paths triggered by malformed or edge-case input, echo the raw `{e}` (e.g. `reth_provider::ProviderError`, MDBX/database backend errors, state-provider errors) back to the caller. This is the same bug class as CVE-2024-52893: a detailed technical error message returned to an unauthenticated/unprivileged remote client, which can reveal internal implementation details (database backend errors, internal paths, state layout hints) useful for further attacks.

Crucially, `base_meterBundle`/`base_meterBlockByHash`/`base_meterBlockByNumber` are explicitly routed to the public/`client` method-permission tier in the reference proxy configuration, confirming this is reachable by anonymous RPC clients, not just operators: [6](#0-5) 

This is in sharp contrast to the deliberate error-sanitization pattern used elsewhere in the same repository, showing the project is aware of and normally guards against this exact issue class — e.g. the consensus admin RPC explicitly redacts internal failure details: [7](#0-6) 
and its own tests assert that internal details are redacted: [8](#0-7) 
Similarly, the tx-manager RPC error classifier intentionally avoids echoing raw transport error text because it "may expose credentials in RPC URLs": [9](#0-8) 
and `proof/rpc/src/error.rs` explicitly truncates/bounds error message length to avoid propagating large internal payloads: [10](#0-9) 

The metering RPC module does not follow this established pattern; it is a public-facing outlier that verbatim forwards internal error text.

### Impact Explanation
An unprivileged, anonymous JSON-RPC caller can trigger provider/database errors (e.g. by supplying a malformed bundle, a bogus block hash, or hitting edge conditions such as "no L1 block info" or storage read failures) and receive back the internal `Display` representation of `reth_provider`/database errors. This can leak internal implementation details (storage backend error strings, potentially internal paths or state details) that aid an attacker in fingerprinting the node internals or crafting follow-on attacks against the execution client — matching the CVE-2024-52893 bug class (sensitive information disclosure via detailed technical error messages).

### Likelihood Explanation
High reachability: `base_meterBundle`, `base_meterBlockByHash`, and `base_meterBlockByNumber` are documented public/client-tier RPC methods reachable by any anonymous JSON-RPC caller when metering is enabled (`--enable-metering`), as shown by the proxyd client-tier routing config and the metering README describing these as externally exposed JSON-RPC endpoints: [11](#0-10) 
Triggering the error paths (e.g. malformed transaction bytes, unknown block hash/number, or a chain state with no L1 deposit transaction) requires no special privileges and no valid signature — a single crafted RPC request suffices.

### Recommendation
Sanitize the metering RPC error paths to match the pattern already used in `crates/consensus/rpc/src/admin.rs` and `crates/utilities/tx-manager/src/error.rs`: return a fixed, generic internal-error message to the RPC caller (e.g. `"failed to get canonical block header"`, `"failed to get state provider"`, `"block metering failed"`) while logging the detailed `{e}` only server-side via `error!`/`debug!`. Optionally gate any additional detail behind a debug-only build flag, and apply the same truncation/redaction helper pattern used in `crates/proof/rpc/src/error.rs`.

### Proof of Concept
1. Run a Base execution node with `--enable-metering` (as documented, exposing `base_meterBundle` on the public JSON-RPC endpoint).
2. Send `base_meterBundle` with an intentionally malformed/empty bundle against a chain state lacking an L1 info deposit transaction, or a `base_meterBlockByHash`/`base_meterBlockByNumber` request for a block hash/number chosen to trigger a provider/database read failure (e.g. concurrent pruning/compaction, or a corrupted range).
3. Observe the JSON-RPC error response's `message` field contains the raw internal error string produced by `format!("Failed to get state provider: {e}")` / `format!("Failed to get canonical block header: {e}")` / `format!("Block metering failed: {e}")`, i.e. verbatim internal `reth_provider`/database error text, rather than a generic error — confirming the information-disclosure class matching CVE-2024-52893.

impl RpcError {
    /// Maximum length for error messages stored in [`RpcError`] variants.
    ///
    /// RPC error payloads (e.g. from `debug_executionWitness`) can contain multi-MB
    /// JSON responses. Truncating at the conversion boundary prevents large strings
    /// from propagating through retry loops, log lines, and error chains.
    pub const MAX_ERROR_MSG_LEN: usize = 500;

    /// Truncates a string to [`Self::MAX_ERROR_MSG_LEN`], appending a `(truncated)`
    /// suffix if it exceeds the limit.
    pub fn truncate_msg(mut msg: String) -> String {
        if msg.len() > Self::MAX_ERROR_MSG_LEN {
            let end = msg.floor_char_boundary(Self::MAX_ERROR_MSG_LEN);
            msg.truncate(end);
            msg.push_str("... (truncated)");
        }
        msg
    }

# `base-metering`

Metering RPC for Base node. Provides RPC methods for measuring transaction and block execution timing.

## Overview

Exposes JSON-RPC endpoints for profiling transaction and block execution on the Base node.
`base_meterBundle` simulates a bundle against latest canonical state and returns
per-transaction gas, opcode, and timing metrics.
`base_meterBlockByHash` and `base_meterBlockByNumber` re-execute a historical block and return
a breakdown of signer recovery and EVM execution times.
