### Title
Silent skip of TDH2 ciphertext owner-label validation when master public key is uncached allows owner/label mismatch on `SecretsCreate`/`SecretsUpdate` — ([File: core/capabilities/vault/gateway_vault_request_processor.go])

### Summary
When the gateway/node hasn't yet cached the vault master public key (`publicKey == nil`), the `GatewayVaultRequestProcessor.processCreateSecretsRequest`/`processUpdateSecretsRequest` silently sets `skipLabelValidation := publicKey == nil` [1](#0-0)  and passes it into `RequestValidator.validateWriteRequest`, which then skips `EnsureRightLabelOnSecret` (the check that the TDH2 ciphertext's cryptographic label matches the claimed `SecretIdentifier.Owner`) [2](#0-1) . No error is surfaced to the caller in this path — the request proceeds as if the check passed.

### Finding Description
The vault write-path validator performs two mutually-exclusive checks depending on a boolean flag:
- when `skipLabelValidation` is false, `EnsureRightLabelOnSecret` enforces that the ciphertext's embedded label equals `WorkflowOwnerToLabel(owner)` [3](#0-2) .
- when `skipLabelValidation` is true, only `verifyEncryptedSecret` (structural/signature check, no owner binding) runs [4](#0-3) [5](#0-4) .

The flag is derived purely from whether the node has a cached public key, a condition outside any client-observable contract, and is set unconditionally by the processor without notifying the client that owner/label binding was not enforced [6](#0-5)  and [7](#0-6) . This mirrors the report's bug class: a security-relevant check (there, "transfer vs. cash-out"; here, "owner label must match ciphertext label") is silently bypassed under an internal state condition, and the caller receives a success response with no indication that the protective check was skipped. Test coverage explicitly demonstrates the divergence: the same request that fails with `"doesn't have owner as the label"` when `skipLabelValidation=false` succeeds with `require.NoError` when `skipLabelValidation=true`, even though the ciphertext is provably labeled for a different address (`ownerB`) than the claimed identifier owner (`ownerA`) [8](#0-7) .

### Impact Explanation
If a node's public-key cache is momentarily empty (the code comment notes this "can happen... immediately after gateway reboots" [9](#0-8) ), `SecretsCreate`/`SecretsUpdate` requests will accept ciphertexts whose cryptographic label does not match the caller-declared owner, without any error to the caller. Because owner-binding is the mechanism preventing one caller from associating/storing a secret payload under another owner's key material, a mismatch here breaks the guarantee that a stored `EncryptedSecret` is provably encrypted for the owner it's filed under — a form of cross-user identity confusion in an unprivileged-actor-reachable path (the JSON-RPC vault gateway endpoint). The code comments assert redundancy ("this validation also runs on Vault Nodes" [10](#0-9) ), but the primary caller-facing gateway layer offers no signal that this defense-in-depth check was bypassed, which is the precise "no error thrown to inform them of the mistake" pattern from the source report.

### Likelihood Explanation
This is triggered purely by node/gateway operational state (public key not yet cached), not by attacker-controlled input choosing to disable a check — so it cannot be forced at will by a remote unprivileged client, but it is reachable during ordinary node restarts/bootstrap windows, and any request arriving during that window is silently subjected to the weaker validation with no observable difference in the response to the caller.

### Recommendation
Do not silently downgrade validation strength based on internal cache state. Options:
- Reject (or hold/retry) `SecretsCreate`/`SecretsUpdate` requests with a distinguishable error/response code when the master public key is not yet cached, rather than proceeding with `skipLabelValidation=true`.
- If skipping is intentional for availability reasons, surface this in the response/metrics so callers and operators can detect and audit label-unverified writes, and ensure the redundant Vault-node-side check is treated as mandatory (fail closed) rather than optional.

### Proof of Concept
1. Deploy/restart the gateway node such that `cachedMasterPublicKey` is `nil` (see `GatewayHandler.getMasterPublicKey` / `cachedMasterPublicKey` field [11](#0-10) ).
2. Submit a `MethodSecretsCreate` request with `SecretIdentifier.Owner = ownerA` but an `EncryptedSecret.EncryptedValue` cryptographically labeled for `ownerB` (as constructed in the existing unit test) [12](#0-11) .
3. Because `publicKey == nil` at request time, `processCreateSecretsRequest` sets `skipLabelValidation = true` and the request passes validation with `require.NoError` [13](#0-12) , whereas the same request with a cached key (`skipLabelValidation=false`) is rejected with `"doesn't have owner as the label"` [14](#0-13)  — confirming the caller receives a silently different (success) outcome depending on unobservable server state, exactly as `transferfCash` silently produced a different (cash-out) outcome depending on unobservable maturity state.

**Uncertainty**: I could not fully trace downstream storage/authorization code (`authorizeAndStamp`, `SecretsService.CreateSecrets`) within the available index to confirm whether any later stage re-validates the label before persisting the secret, so the ultimate persisted-state impact (e.g., whether a mismatched secret is actually stored under the wrong owner) is not fully verified — this would need further investigation via a full repository checkout.

```go
// EnsureRightLabelOnSecret verifies that the TDH2 ciphertext label matches the workflow
// owner label (Ethereum address, left-padded to 32 bytes). owner must be non-empty;
// when the public key is nil, verification is skipped for the same reasons as
// verifyEncryptedSecret.
func EnsureRightLabelOnSecret(publicKey *tdh2easy.PublicKey, secret, owner string) error {
	cipherText, err := verifyEncryptedSecret(publicKey, secret)
	if err != nil {
		return err
	}
	if cipherText == nil {
		return nil
	}
	if owner == "" {
		return errors.New("owner must not be empty for secret label verification")
	}

	expected := vaultutils.WorkflowOwnerToLabel(owner)
	secretLabel := cipherText.Label()
	if secretLabel == expected {
		return nil
	}

	return fmt.Errorf("secret label [%s] does not match workflow owner label [%s]",
		hex.EncodeToString(secretLabel[:]), hex.EncodeToString(expected[:]))
}
```

```go
func verifyEncryptedSecret(publicKey *tdh2easy.PublicKey, secret string) (*tdh2easy.Ciphertext, error) {
	cipherBytes, err := hex.DecodeString(secret)
	if err != nil {
		return nil, errors.New("failed to decode encrypted value:" + err.Error())
	}
	if publicKey == nil {
		// Public key can be nil if gateway cache isn't populated yet (immediately after gateway reboots).
		// Ok to not validate in such cases, since this validation also runs on Vault Nodes.
		return nil, nil
	}

	cipherText := &tdh2easy.Ciphertext{}
	if err := cipherText.UnmarshalVerify(cipherBytes, publicKey); err != nil {
		return nil, errors.New("failed to verify encrypted value:" + err.Error())
	}
	return cipherText, nil
```
