### Title
Instant-withdrawal path in `requestWithdraw` bypasses management and performance fees, letting the withdrawer receive a higher net amount than the fee design intends - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external report describes an order-creation flow where fee parameters exist but are not enforced, so a user can end up with a payout that skips protocol/integrator fees. The closest analog in idle-tranches is the instant-withdrawal branch of `IdleCDOEpochVariant.requestWithdraw`. The normal (queued) path computes `_totalWithdrawFees(principal, interest)` — an upfront management fee plus a net performance fee — deducts them from the user's claim, and accrues them into `pendingWithdrawFees` for the fee receivers. The instant-withdraw path returns the same `_underlyings` amount gross, never calls `_totalWithdrawFees`, never touches `pendingWithdrawFees`, and burns the tranche tokens via `_withdrawOps`. A lender exiting through this branch therefore keeps 100% of the fees the protocol intended to collect.

### Finding Description
In `requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739-780), after `_underlyings = _trancheToUnderlyings(_amount, _tranche)` the code checks `_isInstantWithdrawEnabled()` and `lastEpochApr > currentApr + instantWithdrawAprDelta`. If both hold, it executes:

```
creditVault.requestInstantWithdraw(_underlyings, msg.sender);
_withdrawOps(_amount, _underlyings, _tranche);
return _underlyings;
```

and returns early. The fee logic that immediately follows — `_calcInterestWithdrawRequest`, `_totalWithdrawFees(principal, interest)`, `pendingWithdrawFees += totalFees`, and the reduction `_underlyings = principal + interest - totalFees` — is skipped entirely.

The skipped fees are not optional/user-supplied parameters: `fee` (performance fee), `feeSplit`, `managementFee` and `feeReceiver` are owner-set protocol parameters enforced on-chain in every other flow (`_updateAccounting`, `_accrueManagementFee`, `stopEpoch` fee transfers, `IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` which applies `exitFee` on the fulfiller's payment). Only this branch silently waives them. `_withdrawOps` also reduces `lastNAVAA`/`lastNAVBB` by the full gross `_underlyings`, so the NAV accounting treats the unpaid fees as if they were paid to the user — the fee revenue is permanently forfeited rather than deferred into `unclaimedFees`/`pendingWithdrawFees`.

### Impact Explanation
When the APR-drop condition is met, every holder who calls `requestWithdraw` receives `principal + accruedInterest` gross instead of `principal + interest - (managementFee + performanceFee)`. The protocol loses the entire withdraw fee on that amount (`_totalWithdrawFees(principal, interest)`), and the withdrawer is overpaid by exactly that quantity relative to what the queued path would grant on identical NAV. Because the fee is never accrued into `pendingWithdrawFees`, this is a permanent loss of feeReceiver/owner revenue, not a timing difference. With e.g. a 1% management fee and 10% performance fee, a 1M-underlying exit leaks on the order of tens of thousands of underlying units of intended fees per withdrawal.

### Likelihood Explanation
The branch requires `disableInstantWithdraw == false`, `isEpochRunning` semantics allowing requests, and `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, i.e. the manager must have lowered the vault APR by more than the configured delta at `stopEpoch`/`setApr`. This is a normal operating event (APR cuts are a routine epoch parameter change), not an edge case, and once triggered it applies automatically to *every* `requestWithdraw` — the withdrawer does not need to do anything special; the gross payout is the default behavior of the path. The attacker is an ordinary KYC-passing tranche holder (allowed: `isWalletAllowed(msg.sender)` gate is passed the same way as any withdrawal). No privileged role is required.

### Recommendation
Apply the same fee accounting in the instant-withdraw branch as in the queued path: compute `interest`/`diff` via `_calcInterestWithdrawRequest`, calculate `totalFees = _totalWithdrawFees(principal, interest)`, pass only `_underlyings - totalFees` (or the net claim amount) to `requestInstantWithdraw`/`_withdrawOps` consistent with the NAV semantics, and accrue `totalFees` into `pendingWithdrawFees` (or `unclaimedFees`) so fee receivers still collect. If skipping fees on instant exits is intentional design (e.g., to compensate users for an APR cut), document it explicitly and bound the waiver; otherwise enforce the fees on-chain rather than relying on the path distinction.

### Proof of Concept
Foundry fork scenario:

```solidity
// Setup: deposit into AA tranche during buffer, start epoch
idleCDO.depositAA(amount);
// manager runs epoch
vm.prank(manager); cdoEpoch.setEpochParams(365 days, 0);
vm.prank(manager); IdleCreditVault(strategy).setAprs(apr, apr);
vm.prank(manager); cdoEpoch.startEpoch();

// Fee params: nonzero performance and management fees
_setFeeParams(feeReceiver, 10_000 /*perf*/, FULL_ALLOC, 1_000 /*mgmt*/);

// Warp to mid-epoch, borrower funded, then manager stops epoch
// with a NEW APR lower than lastEpochApr by more than instantWithdrawAprDelta
deal(underlying, borrower, expectedInterest);
vm.warp(cdoEpoch.epochEndDate());
vm.prank(manager); cdoEpoch.stopEpoch(lowerApr, 0);

// Holder requests withdraw -> instant path taken
uint256 requested = cdoEpoch.requestWithdraw(trancheBal, AATranche);

// BUG: pendingWithdrawFees == 0 and 'requested' equals gross
// _trancheToUnderlyings, whereas the queued formula would have been
// principal + interest - _totalWithdrawFees(principal, interest)
assertEq(cdoEpoch.pendingWithdrawFees(), 0);            // fees never accrued
assertGt(requested, expectedNetClaimAmount);            // user overpaid by totalFees
```
