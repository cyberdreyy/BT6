### Title
Sender-signed `max_fee_per_gas` does not bound the operator fee or L1 data fee, so a `SystemConfig`-driven fee increase can charge more than the user consented to - ([File: crates/common/l1-fees/src/params.rs])

### Summary
Base transactions cap their gas cost via the signed `max_fee_per_gas`/`max_priority_fee_per_gas` fields, but the additional OP-stack **L1 data fee** and **Isthmus operator fee** are computed separately from `SystemConfig` parameters (`operator_fee_scalar`, `operator_fee_constant`, L1 base-fee scalars) that a privileged L1 party (the `SystemConfig` contract owner) can update at any time. A user has no on-chain mechanism to cap these components, so a fee-parameter increase committed on L1 between the moment a user signs a transaction and the moment it is included can charge the user materially more than they intended — the same bug class as the reported `PortalV2.unlock()`/`Whitelist` issue, where an admin-adjustable fee with no user-settable ceiling can affect a transaction already in flight.

### Finding Description
The operator fee is derived purely from `SystemConfig` fields that are updated by `ConfigUpdate` logs emitted from L1 and applied unconditionally to the L2 `SystemConfig`/`L1BlockInfo`: [1](#0-0) [2](#0-1) 

These parameters feed `operator_fee_charge_inner`, which is combined with the L1 data fee into `tx_cost`/`operator_fee_charge`, both used at execution time and at admission time: [3](#0-2) [4](#0-3) 

Crucially, the sender's signed fee cap (`max_fee_per_gas`) only bounds the gas-price component of the charge — it plays no role in bounding the L1 fee or operator fee. The affordability check in the handler explicitly sums `gas_limit * max_fee_per_gas + value + l1_fee + operator_fee`, but the operator/L1 fee terms are computed independently of anything the sender agreed to: [5](#0-4) 

The txpool mirrors this at admission time and even has an explicit regression test (HackerOne #74725) confirming that a sender who is *not* funded for the operator fee is rejected — this demonstrates the operator fee is treated as an unavoidable, non-capped surcharge layered on top of whatever `max_fee_per_gas` the sender chose: [6](#0-5) [7](#0-6) 

Because `operator_fee_scalar`/`operator_fee_constant` (and the L1 base-fee scalars) can be raised via an L1 `ConfigUpdate` transaction controlled by the `SystemConfig` owner, and the derivation pipeline applies the new values to all subsequently-derived L2 blocks once the L1 epoch advances, any transaction signed under the old (lower) fee assumption but included after the update takes effect will be charged the new, higher operator/L1 fee — with no field in the transaction that lets the sender declare "do not execute if the operator/L1 fee exceeds X": [8](#0-7) 

This is structurally identical to the reported issue: a privileged party can raise a fee applied inside a "bridge"/settlement path, and the unprivileged sender has no way to cap it before submission.

### Impact Explanation
An unprivileged transaction sender can have more ETH deducted than they intended for a pending transaction if the `SystemConfig` owner raises the operator fee scalar/constant (or L1 fee scalars) between signing and inclusion. Unlike the base fee (which is bounded by `max_fee_per_gas`), there is no user-supplied ceiling on the operator fee or L1 data fee component, so the amount debited from the sender's balance and routed to `OPERATOR_FEE_VAULT`/`L1_FEE_VAULT` can silently exceed the sender's expectation. This is a fund-drain-by-surprise-fee issue rather than outright unauthorized transfer of a specific victim's funds, and it requires a privileged L1 config update to trigger.

### Likelihood Explanation
Low-to-medium likelihood: it requires the `SystemConfig` owner (a privileged, trusted L1 role) to change the operator fee or L1 fee scalars, and the change only takes effect for L2 blocks once the L1 epoch advances (a delay of at least one L1 block, typically ~12s, but batched processing means users generally have some visibility). There is no on-chain enforcement preventing an honest-but-mistaken or compromised `SystemConfig` owner from making a large jump, and pending transactions cannot express a fee ceiling to protect against it.

### Recommendation
Consider one of the mitigations proposed in the original report, adapted to this architecture:
- Allow transactions (or the txpool at admission) to specify a maximum acceptable operator/L1 fee, and reject/hold execution if the fee at inclusion time exceeds it.
- Alternatively, enforce a notice/delay period for `ConfigUpdate(OperatorFee)` (and L1 fee scalar) changes larger than a defined bound, so already-broadcast transactions have a guaranteed window before the new fee parameters take effect.
- At minimum, document/expose the current operator-fee/L1-fee parameters and pending updates so that RPC clients/wallets can warn users before signing if a fee-parameter change is already committed on L1 but not yet reflected in the L2 chain.

### Proof of Concept
1. A user submits an EIP-1559 transaction with `max_fee_per_gas` sized purely for the expected gas price, relying on the current `operator_fee_scalar`/`operator_fee_constant` in `SystemConfig` for the additional surcharge (as demonstrated in `eip8130_payer_max_cost_includes_l1_and_operator_fees`, `crates/execution/txpool/src/validator.rs:3522-3581`, where `payer_max_cost = gas_charge + l1/operator fee`).
2. Before the transaction is included, the `SystemConfig` owner emits a `ConfigUpdate(OperatorFee)` log on L1 raising `operator_fee_scalar`/`operator_fee_constant` (see `enqueue_operator_fee_update`, `actions/harness/src/l1/miner.rs:373-400`).
3. Once the L1 epoch advances, `SystemConfig::update_with_receipts`/`OperatorFeeUpdate::apply` (`crates/common/genesis/src/system/config.rs:130-154`, `crates/common/genesis/src/updates/operator_fee.rs:19-24`) applies the new scalar/constant to subsequent L2 blocks, as verified end-to-end in `operator_fee_config_update_propagates_to_l1_info` (`actions/harness/tests/upgrade/operator_fees.rs:578-687`).
4. The user's still-pending transaction, when finally included, is charged the new (higher) operator fee via `operator_fee_charge`/`settle_fees` (`crates/common/evm/src/eip8130.rs:1540-1610`), debiting more ETH than the user calculated when signing — with no transaction field able to have prevented this.

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }

    /// Rejects the transaction when `caller` cannot cover the full upfront charge — the maximum
    /// gas cost, the transferred value, and the OP-stack L1 data and operator fees.
    ///
    /// The framework's `validate_sender` already rejects a caller that cannot cover the gas cost
    /// and value, but it is unaware of the L1 and operator fees charged here, and
    /// [`charge_upfront`] deducts with wrapping arithmetic. Without this guard an underfunded
    /// caller would silently wrap to a spurious balance instead of the transaction failing; this
    /// mirrors the revm reference, which rejects such a caller with `LackOfFundForMaxFee`.
    ///
    /// A no-op for deposits (funded on L1 and exempt) and when fee charging or balance checks are
    /// disabled (e.g. `eth_call` simulation), matching the conditions under which `validate_sender`
    /// and `charge_upfront` themselves enforce balances.
    fn ensure_can_pay_fees(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        l1_fee: U256,
        operator_fee: U256,
    ) -> HandlerResult<()> {
        let Some(tx) = envelope.as_standard() else {
            return Ok(());
        };
        if !host.feature(EvmFeatures::FEE_CHARGE) || !host.feature(EvmFeatures::BALANCE_CHECK) {
            return Ok(());
        }
        let required = U256::from(tx.gas_limit())
            .saturating_mul(U256::from(tx.max_fee_per_gas()))
            .saturating_add(tx.value())
            .saturating_add(l1_fee)
            .saturating_add(operator_fee);
        let balance =
            host.state_mut().account(&caller, false).map_err(HandlerError::Fatal)?.balance();
        if balance < required {
            return Err(HandlerError::InsufficientFunds);
        }
        Ok(())
    }
