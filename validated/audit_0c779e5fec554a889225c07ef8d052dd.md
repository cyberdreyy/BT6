### Title
Post-default instant-withdraw requests bypass recovery haircut and are paid at par from `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the OpenClaw reconnect-escalation bug (a previously-authenticated session regaining a broader command scope without re-clearing the pairing gate), `IdleCreditVault.requestInstantWithdraw` lets a tranche holder create a *new* instant-withdraw receipt after `defaultRecoveryFinalized`, and `claimInstantWithdrawRequest` then pays that receipt at par via `_transferFundedClaim` — the same payout path reserved for fully funded claims — even though no funding was ever collected for it and it was never haircut by `defaultRecoveryPrice`. The funds come out of the vault's underlying balance, i.e. the `defaultRecoveryReserve` earmarked for haircutted defaulted-epoch claimants.

### Finding Description
In `requestInstantWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:356-375) there is no `defaultRecoveryFinalized` guard. It only calls `_onlyIdleCDO()` and `_ensureDefaultRecoveryInitialized()`, then burns CDO-held strategy tokens, mints a receipt to the user, and increases `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws`.

After default finalization, `claimInstantWithdrawRequest` (lines 380-393) first calls `_claimDefaultedInstantWithdrawRequest`, which only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and decrements `instantWithdrawsRequests[_user]` by that defaulted-epoch basis. Any receipt recorded in a *later* epoch is untouched by the haircut logic and is then paid in full:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

The post-finalization receipt is therefore redeemed at par from the reserve. Unlike the normal-request path, `requestWithdraw` contains a dedicated post-default branch (`postDefaultRequests`, line 247-257) that explicitly re-checks for open receipts and routes claims through the haircut-aware `_claimPostDefaultWithdrawRequest`; `requestInstantWithdraw` has no equivalent scoping, so the "re-pairing" gate — recovery-price application — is skipped for reconnecting claims.

### Impact Explanation
`finalizeDefault` sizes `defaultRecoveryReserve` so that all pending claims share the recovery pro rata (`defaultPendingClaimBasis` accounting in `finalizeDefault`/`_claimDefaulted*` paths). An attacker holding tranche tokens (or strategy-token receipts) after `finalizeDefault` can:

1. Call `cdoEpoch.requestWithdraw` while `allowInstantWithdraw == true` (which remains enabled when defaulted instant claims were fully funded — see test at `IdleCreditVault.t.sol:2716`), routing into `requestInstantWithdraw`.
2. Call `cdoEpoch.claimInstantWithdrawRequest`, which burns the freshly minted receipt and transfers underlying at par from the vault.

Each unit withdrawn at par depletes `defaultRecoveryReserve` meant to pay all defaulted claimants at `defaultRecoveryPrice`, directly stealing the haircut borne by honest claimants and/or leaving the last claimants unable to withdraw (insolvency of the reserve). Loss is bounded by the reserve size but is a direct theft of unclaimed recovery, satisfying the impact bar.

### Likelihood Explanation
Requirements: pool defaulted, `finalizeDefault` executed, and `allowInstantWithdraw` enabled (true when the defaulted epoch's instant claims were prefunded, or re-enabled by mode). The attacker needs only to be a tranche-token holder with non-zero balance — an unprivileged user. No privileged role misbehavior is required; sequencing is around honest manager calls (`stopEpoch`, `finalizeDefault`).

Caveat: the exploitability depends on the CDO-side routing of `requestWithdraw` to the instant path while `allowInstantWithdraw` is set and on `_transferFundedClaim` drawing from the vault's general underlying balance rather than a segregated bucket — the latter was not fully confirmed from the indexed excerpt. If `allowInstantWithdraw` is forced false in all post-default configurations, the request path would be unreachable and the finding degrades to a freeze of `pendingInstantWithdraws` accounting rather than theft.

### Recommendation
Mirror the `requestWithdraw` post-default branch: in `requestInstantWithdraw`, when `defaultRecoveryFinalized`, either revert outright (preferred — post-default exits should go through `postDefaultRequests`/haircut-aware normal claims) or record the receipt under `postDefaultRequests` semantics so `claimInstantWithdrawRequest` cannot pay it via `_transferFundedClaim`. Additionally, gate the par payout on `pendingInstantWithdraws`/funded status rather than the raw `instantWithdrawsRequests` aggregate, so unfunded receipts can never be paid at par from recovery funds.

### Proof of Concept
A Foundry fork test would: (1) deposit AA tranche for attacker and victim; (2) run epochs until an instant-withdraw-enabled epoch where instant claims are prefunded so `allowInstantWithdraw` stays true; (3) trigger default via `stopEpoch` with insufficient borrower repayment; (4) `finalizeDefault(recovered, manager)` with `recoveryRatio < 1`; (5) attacker calls `cdoEpoch.requestWithdraw(0, AATranche)` then `claimInstantWithdrawRequest()` in the same post-finalization phase, receiving underlying at par while `defaultRecoveryReserve` decreases, then assert `creditVault.defaultRecoveryReserve()` dropped by the full claim and a second victim's `claimWithdrawRequest` reverts or pays less than `basis * defaultRecoveryPrice / RECOVERY_FULL`. Because the CDO-side dispatch conditions and `_transferFundedClaim`'s funding source could not be fully confirmed from the indexed code, this PoC step should be validated against the full repo before final reporting.
