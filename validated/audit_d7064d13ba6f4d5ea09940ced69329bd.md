### Title
Unvalidated client-supplied blockhash causes panic in `send_transaction_with_context` - ([File: banks-server/src/banks_server.rs])

### Summary
`send_transaction_with_context` extracts `recent_blockhash` directly from the client-supplied `VersionedTransaction` and passes it to `get_blockhash_last_valid_block_height`, then immediately `.unwrap()`s the `Option` result. Since the blockhash is entirely attacker-controlled and not validated before this call, a garbage/unregistered hash causes `None` to be returned and the process to panic.

### Finding Description
In `banks-server/src/banks_server.rs`, the `send_transaction_with_context` RPC handler does: [1](#0-0) 

```rust
async fn send_transaction_with_context(self, _: Context, transaction: VersionedTransaction) {
    let message_hash = transaction.message.hash();
    let blockhash = transaction.message.recent_blockhash();
    let last_valid_block_height = self
        .bank_forks
        .read()
        .unwrap()
        .root_bank()
        .get_blockhash_last_valid_block_height(blockhash)
        .unwrap();
```

`get_blockhash_last_valid_block_height` in `runtime/src/bank.rs` looks up the hash in the bank's blockhash queue and returns `None` if the hash is not found/expired. `blockhash` here comes directly from the deserialized, attacker-supplied `VersionedTransaction` — there is no sanitization, verification, or fallback check performed before the lookup, unlike `process_transaction_with_commitment_and_context` which at least sanitizes and verifies the transaction (though that path has the same `.unwrap()` pattern later at line 343-346). Any client that calls this unary RPC with a `VersionedTransaction` whose `recent_blockhash` is set to a random/never-registered `Hash` (e.g., `Hash::new_unique()`) triggers `None.unwrap()`, panicking the async task. Depending on the tarpc runtime/executor configuration, this can abort the serving task or the entire process for that channel, since there is no `catch_unwind`/`panic::catch_unwind` boundary shown around request dispatch in this file.

### Impact Explanation
A single unprivileged banks-server client can panic the request-handling task by sending one `send_transaction_with_context` call carrying a bogus `recent_blockhash`. This denies subsequent RPC calls for that channel/client (balance, status, account reads), matching the described single-request DoS scoped impact against banks-server (used in `solana-test-validator`/local test harnesses and BanksClient-based testing tooling).

### Likelihood Explanation
Trivial and fully attacker-controlled: the transaction's `recent_blockhash` field is directly deserialized from client input and used unchecked. No special privileges, prior state, or multiple calls are needed — one call with `Hash::new_unique()` (or any hash absent from the root bank's blockhash queue, e.g., a very old blockhash that's aged out) reliably reproduces the panic every time.

### Recommendation
Handle the `None` case from `get_blockhash_last_valid_block_height` gracefully instead of unwrapping — e.g., return an error/`None` result to the client (mirroring how `get_latest_blockhash_with_commitment_and_context` uses `?` on the `Option`), for both occurrences in `send_transaction_with_context` (line 230) and `process_transaction_with_commitment_and_context` (line 345).
