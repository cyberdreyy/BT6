### Title
Stale confirmations from deleted keys/members are still counted toward the confirmation threshold - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
When a multisig key (or member, in `multisig2`) is removed via `DeleteKey`/`DeleteMember`, the contract only deletes requests *created* by that key/member and its `num_requests_pk` entry. It does not scan and purge that key's/member's confirmation entries from the `confirmations` map for requests it merely confirmed (but did not create). Those stale confirmations remain in the `HashSet` and continue to count toward `num_confirmations` in the subsequent `confirm()` calls.

### Finding Description
The binding that should hold is: *confirmations counted == confirmations from currently-live signers*. `confirm()` only checks `!confirmations.contains(&signer_pk)` and then compares `confirmations.len() + 1 >= self.num_confirmations` [4](#0-3) . It never re-validates that every public key already present in the `confirmations` set for that request is still an active access key on the account. `DeleteKey`'s cleanup logic filters `self.requests` by `r.signer_pk == pk` (the request *creator*) and removes the corresponding entries — it does not touch the `confirmations` sets of requests created by *other* keys that the deleted key had confirmed [1](#0-0) . Thus if key A creates request R and key B (non-creator) confirms it, then key B is removed from the account, R's `confirmations` set still contains B's public key, and it will still count toward the threshold when a later confirmation pushes the count to `num_confirmations`. The same gap exists in `multisig2::delete_member`, which filters `self.requests` by `r.member == member` and removes those requests/confirmations, but leaves confirmations by that member on requests created by others intact [3](#0-2) .

### Impact Explanation
This breaks the "confirmations counted vs. live members" equality that the K-of-N threshold model depends on. A request can be executed (transferring NEAR, deploying a contract, adding a full-access key, etc.) with fewer *currently authorized* signers than `num_confirmations` requires, because one of the counted confirmations belongs to a key/member that has since been removed. This matches the Critical impact category: "a multisig request executed below threshold."

### Likelihood Explanation
This requires no privileged action beyond the normal, expected multisig workflow: a member confirms a pending request, is later removed as a signer (a routine key-rotation/membership-change operation performed by the multisig itself), and the previously-confirmed request is executed afterward by the remaining members reaching only `num_confirmations - 1` *live* confirmations. No malicious deployment, redeploy, or out-of-scope precondition is needed — it is a straightforward consequence of the existing `DeleteKey`/`DeleteMember` cleanup logic being incomplete.

### Recommendation
When executing `DeleteKey` (or `DeleteMember` in `multisig2`), iterate over all entries in `self.confirmations` (not just `self.requests` filtered by creator) and remove the deleted key/member's entry from every confirmation `HashSet`. Alternatively, validate at `confirm()` time (or at execution time) that every public key/member counted in a request's confirmation set is still a currently valid signer before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize multisig with `num_confirmations = 2` and 3 keys: A, B, C.
2. A calls `add_request_and_confirm(request)` → request R has confirmations `{A}`.
3. B calls `confirm(R)` → confirmations `{A, B}`, but since `len()+1 (2) >= num_confirmations (2)` is evaluated at B's own call before adding B (`confirmations.len() as u32 + 1 >= self.num_confirmations` → `1 + 1 >= 2`), R actually executes on B's confirmation without ever persisting `{A,B}` — so for this PoC assume `num_confirmations = 3` instead, with keys A, B, C, D (4 keys) and threshold 3.
4. A creates request R (creator A). B confirms → confirmations `{A? no—only confirmer set, A as creator did not auto confirm unless add_request_and_confirm}`; assume A uses `add_request_and_confirm` so confirmations = `{A}`. B confirms → confirmations `{A,B}` (2 < 3, not executed yet).
5. Multisig executes a separate request (via `DeleteKey`) removing key B from the account (B is no longer a valid signer).
6. C now calls `confirm(R)`. The check only looks at `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → executes R, counting B's stale confirmation even though B has been removed and never re-confirmed. R executes with only 2 genuinely live confirmations (A, C) instead of the required 3.

**Note on verification limits:** I was not able to run this scenario against a live/simulated environment (no execution tooling in this session); the PoC is derived purely from static analysis of the confirmation/removal code paths cited above. The core logical gap (confirmations map not purged of non-creator entries on key/member removal) is directly supported by the cited code.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
