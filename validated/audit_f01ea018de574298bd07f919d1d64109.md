### Title
Attacker script can trap SIGTERM and self-raise SIGUSR1 to launder a canceled build into a reported success - ([File: functions/script_legacy/internal/normalize_exit_error.go])

### Summary
`normalizeExitError` deliberately lets cancellation-driven `SIGTERM` propagate as a failure, but relies on `isNonFatalUserSignal` (`functions/script_legacy/internal/signals_unix.go`), which only inspects the *final* terminating signal recorded in `ps.Sys().(syscall.WaitStatus).Signal()`. A user script that traps `SIGTERM` and, inside the trap, self-signals `SIGUSR1` (`trap 'kill -USR1 $$' TERM`) causes the outer shell process to actually die from `SIGUSR1`, not `SIGTERM`. Since Go's `os.ProcessState`/`syscall.WaitStatus` only records the signal that caused termination and not the causal signal history, `isNonFatalUserSignal` returns `true`, and `normalizeExitError` swallows the cancellation, returning `nil` (success) instead of propagating the cancellation error.

### Finding Description
`Executor.Execute` (`functions/script_legacy/internal/executor.go:63-70`) runs the user script via `gracefulexitcmd.New(ctx, ...)` and calls `normalizeExitError(cmd.Run(), cmd.ProcessState)`. When the job's context is canceled, `gracefulexitcmd.Cmd.Cancel` sends `SIGTERM` to the process (group), per the doc comment in `normalize_exit_error.go:31-33`, which explicitly states this must propagate as a failure so the build is "reported as canceled rather than passed silently."

However, the mechanism used to detect "benign, user-raised signal" vs. "fatal cancellation signal" is purely the terminal `WaitStatus.Signal()` value [1](#0-0) . This value only reflects whatever signal ultimately killed the process — it carries no information about *why* that signal was raised. If the outer shell script installs a trap on `SIGTERM` that reacts by self-delivering `SIGUSR1` (e.g. `trap 'kill -USR1 $$' TERM`), then:

1. The runner's cancellation logic fires `SIGTERM` at the process (per `gracefulexitcmd.Cmd.Cancel`, as documented at `normalize_exit_error.go:31-33`).
2. The script's trap intercepts `SIGTERM`, and in the handler raises `SIGUSR1` against itself.
3. `SIGUSR1` has default disposition (terminate), so the shell process dies with `WaitStatus.Signal() == SIGUSR1`.
4. `normalizeExitError` calls `isNonFatalUserSignal`, sees `SIGUSR1`, and returns `nil` — swallowing the cancellation entirely [2](#0-1) .

The identical pattern and identical root-cause logic exist in the concrete-run path at `functions/concrete/run/env/env.go:166-203`, which the code comments say are "deliberately kept in sync" with this file [3](#0-2) , so both bash-legacy and concrete/step-runner execution paths are affected.

No existing check distinguishes a "genuine benign self-signal" from a "SIGTERM-triggered self-signal impersonating one." The existing unit tests only validate the two extremes — an untouched raw `SIGTERM` (`TestNormalizeExitError_PassesThroughSIGTERM`) and an untouched raw `SIGUSR1` (`TestNormalizeExitError_UnwrapsNonFatalUserSignals`) — but never test the combined trap-and-relay scenario, so the gap is untested and unguarded.

### Impact Explanation
A job that is canceled by the platform (e.g., a user or CI system canceling the pipeline, or a timeout-driven cancellation) can be made, by an attacker-authored `.gitlab-ci.yml` script, to report as **successful** instead of **canceled**. This directly violates the stated invariant in the code ("the runner needs [SIGTERM] to propagate so the build is reported as canceled rather than passed silently") and matches the scoped impact: a canceled/aborted job impersonating a completed job's success state. This could be used to mask a job that was killed for legitimate reasons (e.g., resource abuse, policy violation) as a clean pass, undermining pipeline status integrity and any downstream automation/gating that trusts job status.

### Likelihood Explanation
This is fully within reach of an unprivileged pipeline author: no special privileges are required beyond the ability to write a `.gitlab-ci.yml` script or step definition that runs under the legacy bash executor or the concrete/step-runner executor. The technique (`trap 'kill -USR1 $$' TERM`) is standard shell scripting and highly reliable — bash trap execution for asynchronous signals occurs promptly when control returns to the shell, and since the runner's cancellation path is exactly what delivers `SIGTERM` in the first place, the race window is not adversarial timing but a deterministic trap-installation-then-wait pattern (trap installed at script start, before any cancellation can occur). It is reproducible on every run given the trap is installed early enough.

### Recommendation
Do not rely solely on the terminal `WaitStatus.Signal()` to classify a termination as benign. Options:
- Have `Executor.Execute`/`Env.Command` check `ctx.Err()` (or an explicit "was this process canceled by us" flag set by `gracefulexitcmd.Cmd.Cancel`) *before* consulting `isNonFatalUserSignal`; if the context was canceled, always propagate the cancellation error regardless of which signal the process ultimately reports.
- Alternatively, have `gracefulexitcmd.Cmd.Cancel` record that it sent `SIGTERM` for cancellation (independent of the process's actual final exit signal) and have `normalizeExitError` check that flag first, so any termination occurring after a cancellation-triggered `SIGTERM` is treated as canceled, not reclassified via signal.

### Proof of Concept
Go integration test (unix-only) to be added near `normalize_exit_error_unix_test.go`:

```go
func TestNormalizeExitError_CancelSIGTERM_LaunderedViaTrappedSIGUSR1(t *testing.T) {
    ctx, cancel := context.WithCancel(context.Background())
    script := `trap 'kill -USR1 $$' TERM; sleep 30`
    cmd := gracefulexitcmd.New(ctx, 2*time.Second, "/bin/sh", "-c", script)
    require.NoError(t, cmd.Start())

    time.Sleep(200 * time.Millisecond) // ensure trap installed
    cancel()                            // triggers gracefulexitcmd.Cmd.Cancel -> SIGTERM

    runErr := cmd.Wait()
    got := normalizeExitError(runErr, cmd.ProcessState)

    // Invariant: cancellation must always surface as canceled, never success.
    assert.Error(t, got, "canceled job laundered via trapped SIGTERM->SIGUSR1 must not report success")
}
```
Expected (buggy) result: `got` is `nil` because `WaitStatus.Signal()` reports `SIGUSR1`, violating the assertion and proving the bypass.

func isNonFatalUserSignal(ps *os.ProcessState) bool {
	ws, ok := ps.Sys().(syscall.WaitStatus)
	if !ok {
		return false
	}
	if !ws.Signaled() {
		return false
	}
	switch ws.Signal() {
	case syscall.SIGUSR1, syscall.SIGUSR2, syscall.SIGHUP, syscall.SIGPIPE:
		return true
	}
	return false
}

func normalizeExitError(err error, ps *os.ProcessState) error {
	if err == nil {
		return nil
	}

	if errors.Is(err, exec.ErrWaitDelay) && ps != nil && ps.ExitCode() == 0 {
		return nil
	}

	if ps != nil && isNonFatalUserSignal(ps) {
		return nil
	}

	return err
