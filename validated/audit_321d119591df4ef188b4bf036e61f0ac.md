### Title
Lockup Factory Lets Callers Inject an Untrusted Staking-Pool Whitelist, Enabling Early Release of Locked Tokens - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create()` accepts an optional, caller-supplied `whitelist_account_id` parameter that overrides the factory's officially configured whitelist and is baked directly into the newly deployed lockup contract's `staking_pool_whitelist_account_id` field. This lets any unprivileged caller deploy a lockup that trusts a whitelist contract of their own choosing instead of the NEAR Foundation's official `whitelist` contract, breaking the custody guarantee that only Foundation-approved staking pools can receive delegated (locked) NEAR from a lockup.

### Finding Description
`LockupFactory::create()` in [1](#0-0)  lets the caller optionally pass `whitelist_account_id`, which — if supplied — is used instead of the factory's own configured `self.whitelist_account_id`:

```rust
let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
    account_id.into()
} else {
    self.whitelist_account_id.clone()
};
```

This value is embedded in `LockupArgs.staking_pool_whitelist_account_id` and passed to the new lockup contract's `new` initializer, becoming the trust anchor the lockup uses for the entire lifetime of the contract: [2](#0-1) .

Inside the deployed lockup contract, `select_staking_pool` checks the target staking pool only against `self.staking_pool_whitelist_account_id` — whatever value was injected at creation time: [3](#0-2) . The lockup owner (who is also chosen by the same `create()` caller via `owner_account_id`) can then deposit and stake the entire unvested/locked balance to that "selected" pool via `deposit_and_stake`, which is gated only by `assert_staking_pool_is_idle`/`assert_no_termination`, not by the vesting schedule: [4](#0-3) .

The intended invariant — documented in `whitelist/README.md` — is that only NEAR-Foundation-approved staking pools can receive delegated tokens from a lockup, specifically so that "delegated tokens can not be lost or locked": [5](#0-4) . Because `create()` lets the caller substitute an arbitrary whitelist contract, this invariant is not enforced for lockups created this way — the caller can deploy their own trivial whitelist contract that always returns `true` for `is_whitelisted`, then have `select_staking_pool` "approve" an account they fully control, and stake/transfer the whole locked balance there. There is no unstake/return of funds guarantee once tokens reach an attacker-controlled account, so the tokens effectively leave lockup custody before the vesting schedule permits.

### Impact Explanation
This is a "wrongly parameterised deployment" that allows locked/unvested tokens to be released early, moving the entire locked balance out of the lockup's custody to an account the attacker controls — outside of the vesting schedule and outside the Foundation-controlled whitelist safeguard the system relies on. This matches the Critical impact category: unvested tokens released early via a wrongly parameterised deployment.

### Likelihood Explanation
Any account can call `LockupFactory::create()` — it has no access control beyond providing the minimum attached deposit, and both `owner_account_id` and `whitelist_account_id` are fully attacker-supplied arguments: [6](#0-5) . Deploying a trivial "always whitelisted" contract and a "black hole" staking pool contract are both low-effort for an attacker with a NEAR account.

### Recommendation
Remove the caller-controllable `whitelist_account_id` parameter from `LockupFactory::create()` (or restrict it to Foundation-controlled callers only) and always use the factory's own configured `self.whitelist_account_id` when constructing `LockupArgs`, so every lockup deployed by the factory is bound to the single, Foundation-approved whitelist contract.

### Proof of Concept
1. Attacker deploys `MaliciousWhitelist`, a trivial contract whose `is_whitelisted` always returns `true`.
2. Attacker deploys `MaliciousPool`, a contract that simply accepts NEAR (implements `deposit`/`deposit_and_stake` as no-ops that keep funds) with no honest unstake/withdraw path.
3. Attacker calls `LockupFactory::create(owner_account_id = attacker, ..., whitelist_account_id = Some(MaliciousWhitelist))`, per [1](#0-0) . A new lockup contract is deployed with `staking_pool_whitelist_account_id = MaliciousWhitelist`.
4. Attacker (owner of the lockup) calls `select_staking_pool(MaliciousPool)`; the check against `MaliciousWhitelist::is_whitelisted` succeeds per [3](#0-2) .
5. Attacker calls `deposit_and_stake(full_locked_balance)`, moving the entire locked/unvested balance to `MaliciousPool`, per [7](#0-6) , before the vesting schedule would have permitted any transfer.

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

    pub fn select_staking_pool(&mut self, staking_pool_account_id: AccountId) -> Promise {
        self.assert_owner();
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The staking pool account ID is invalid"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();

        env::log(
            format!(
                "Selecting staking pool @{}. Going to check whitelist first.",
                staking_pool_account_id
            )
            .as_bytes(),
        );

        ext_whitelist::is_whitelisted(
            staking_pool_account_id.clone(),
            &self.staking_pool_whitelist_account_id,
            NO_DEPOSIT,
            gas::whitelist::IS_WHITELISTED,
        )
        .then(ext_self_owner::on_whitelist_is_whitelisted(
            staking_pool_account_id,
            &env::current_account_id(),
            NO_DEPOSIT,
            gas::owner_callbacks::ON_WHITELIST_IS_WHITELISTED,
        ))
    }

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.
The staking pool should guarantee that the delegated tokens can not be lost or locked, such as the lockup contract should be
