### Title
Missing re-initialization guard in `MultiSigContract::new` allows resetting multisig members and threshold - (File: `multisig2/src/lib.rs`)

### Summary
`multisig2/src/lib.rs`'s `#[init]` constructor `new` lacks the explicit `assert!(!env::state_exists(), ...)` guard that every other `#[init]` constructor in this repository uses (`lockup-factory`, `lockup`, `multisig` v1, `staking-pool-factory`, `staking-pool`, `voting`, `whitelist`). This is the same bug class described in the external report (an `initialize`/`new` function missing the check that ensures it can only be called once).

### Finding Description
Every other in-scope contract's constructor explicitly checks that state does not already exist before initializing, e.g.: [1](#0-0) [2](#0-1) [3](#0-2) 

By contrast, `multisig2/src/lib.rs`'s `new` relies only on `#[derive(..., PanicOnDefault)]` and contains no `env::state_exists()` check: [4](#0-3) 

`PanicOnDefault` only changes the fallback behavior invoked when a non-`#[init]` method is called on state that doesn't exist yet (i.e. it makes `Default::default()` panic instead of silently constructing empty state). It does not add a guard preventing the `#[init]` method itself from being invoked again once state already exists. Since `new` is a plain public method with no `assert_eq!(predecessor, current_account)` or owner check, and no `state_exists` check, any account can call `new` again on an already-initialized multisig contract, completely overwriting `members`, `num_confirmations`, `requests`, `confirmations`, and `active_requests_limit`: [5](#0-4) 

### Impact Explanation
If `new` can be re-invoked, an attacker could call it with `members = [attacker]` and `num_confirmations = 1`, replacing the legitimate set of members and the legitimate confirmation threshold with attacker-controlled values. The attacker could then create and confirm a `Transfer` request using their single access key, executing a fund transfer with `1` confirmation instead of the originally configured `k`-of-`n` threshold, matching the report's "Critical – a multisig request executed below threshold" impact category described in the assignment rules (`confirmations counted versus live members`).

### Likelihood Explanation
Exploitation only requires an unprivileged attacker submitting a `FunctionCall` transaction invoking `new` on the deployed multisig account — no owner key, no redeploy, and no social engineering is required, assuming the deployed access keys on the account still permit calling `new` (function-call access keys on NEAR are restricted to a fixed method allow-list set at deploy time; if the granted access key's method list did not include `new`, exploitation would require a full-access key, which is out of scope). This uncertainty about the deployed access-key method list could not be resolved from the source alone, since it depends on deployment-time parameters, not code in this repository.

### Recommendation
Add an explicit `assert!(!env::state_exists(), "Already initialized")` at the start of `MultiSigContract::new` in `multisig2/src/lib.rs`, consistent with the pattern used in `multisig/src/lib.rs`, `whitelist/src/lib.rs`, `voting/src/lib.rs`, `staking-pool/src/lib.rs`, `staking-pool-factory/src/lib.rs`, and `lockup-factory/src/lib.rs`. Add unit tests asserting that calling `new` twice panics.

### Proof of Concept
Not independently verifiable from the static source alone — reachability hinges on whether the on-chain function-call access key(s) provisioned for the deployed `multisig2` contract include `new` in their method allow-list, information not present in this repository. Conceptually:
1. Deploy `multisig2` with `new(members=[A,B,C], num_confirmations=2)`.
2. Attacker (holding a key whose access-key method list includes `new`, or if `new` remains callable post-deploy) calls `new(members=[attacker], num_confirmations=1)` again.
3. State is overwritten; `members`/`num_confirmations` are now attacker-controlled.
4. Attacker submits `add_request` + `confirm` for a `Transfer` action, which now executes after only 1 confirmation instead of the original 2.

    /// Number of confirmations required.

    confirmations: LookupMap<RequestId, HashSet<String>>,

    num_requests_pk: LookupMap<String, u32>,
    /// Limit number of active requests per member.
    active_requests_limit: u32,
}

#[inline]
fn assert(condition: bool, error: &str) {
    if !condition {
        env::panic_str(error);
    }
}

#[near_bindgen]
impl MultiSigContract {
    /// Initialize multisig contract.
    /// @params members: list of {"account_id": "name"} or {"public_key": "key"} members.
    /// @params num_confirmations: k of n signatures required to perform operations.
    #[init]
    pub fn new(members: Vec<MultisigMember>, num_confirmations: u32) -> Self {
        assert(
            members.len() >= num_confirmations as usize,
            "Members list must be equal or larger than number of confirmations",
        );
        let mut multisig = Self {
            members: UnorderedSet::new(StorageKeys::Members),
            num_confirmations,
            request_nonce: 0,
            requests: UnorderedMap::new(StorageKeys::Requests),
            confirmations: LookupMap::new(StorageKeys::Confirmations),
            num_requests_pk: LookupMap::new(StorageKeys::NumRequestsPk),
            active_requests_limit: ACTIVE_REQUESTS_LIMIT,
        };
        let mut promise = Promise::new(env::current_account_id());
        for member in members {
            promise = multisig.add_member(promise, member);
        }
        multisig
    }
