### Title
Panic via TOCTOU race between two `self.bank(commitment)` calls when blockhash ages out between sanitize/verify and blockhash-height lookup - (File: banks-server/src/banks_server.rs)

### Summary
`BanksServer::process_transaction_with_commitment_and_context` fetches the commitment bank twice: once to sanitize/verify the transaction, and a second time (independently re-resolved) to compute `get_blockhash_last_valid_block_height(&blockhash).unwrap()`. Neither `SanitizedTransaction::try_create` nor `.verify()` checks that the transaction's `recent_blockhash` is present in the bank's blockhash queue, so a blockhash that ages out of the queue between the two calls causes the second lookup to return `None`, and the `.unwrap()` panics.

### Finding Description
In `process_transaction_with_commitment_and_context`: [1](#0-0) 

- Line 326 resolves `bank = self.bank(commitment)` and uses it only to sanitize (`SanitizedTransaction::try_create`) and `verify()` the transaction (signature checks) at lines 327-340.
- `verify()` does not validate `recent_blockhash` against the blockhash queue at all — blockhash-age validation normally happens later during actual transaction processing (`Bank::check_age`), not at sanitize/verify time.
- Lines 343-346 then call `self.bank(commitment)` **again**, independently, and immediately call `.get_blockhash_last_valid_block_height(&blockhash).unwrap()`.

`self.bank(commitment)` re-resolves the commitment slot each time it is called: [2](#0-1) 

For `CommitmentLevel::Processed`, `slot_with_commitment` tracks the current working/highest bank, which advances continuously as new slots are produced. Because the two `self.bank(commitment)` calls at lines 326 and 344 are not tied to the same bank snapshot, and because there is measurable time between them (sanitization + Ed25519 signature verification of `sanitized_transaction.verify()`), an attacker can submit a transaction whose `recent_blockhash` is present in the blockhash queue of the bank fetched at line 326 but has since been evicted from the queue of the (newer) bank fetched at line 344 — the blockhash queue only retains a fixed, limited window of recent hashes. When that happens, `get_blockhash_last_valid_block_height` returns `None`, and `.unwrap()` at line 346 panics, since there is no other validation step in this path that would have rejected the request earlier for exactly this reason.

### Impact Explanation
A single crafted `process_transaction_with_commitment_and_context` request (with attacker-controlled `commitment` and `recent_blockhash` fields) can panic the thread handling this async RPC. Since Agave sets up a global panic hook on the validator process to abort/crash on any unwind, this results in a full validator-process crash from a single unprivileged client call, matching the "validator crash from one request" bounty category.

### Likelihood Explanation
The precondition is a race window: the attacker must pick a `recent_blockhash` that is valid (present in queue) at the time of the first `self.bank(commitment)`/`verify()` step but is expected to be evicted by the time of the second `self.bank(commitment)` call, and must use `commitment = Processed` (or another commitment whose resolved slot advances quickly) so the two calls can resolve to different, newer banks. Because blockhash queues retain only a bounded number of recent hashes and the two lookups are not tied to the same bank instance, this is a genuine, repeatable TOCTOU condition triggerable by one client with a single request — no leader/gossip/staked control needed, only precise timing of an otherwise-legitimate transaction submission.

### Recommendation
Fetch the commitment bank once and reuse the same `Arc<Bank>` for both sanitization/verification and the `get_blockhash_last_valid_block_height` lookup, and replace the `.unwrap()` with a proper error return (e.g. `TransactionError::BlockhashNotFound`) instead of panicking when the blockhash is not found in the queue.

### Proof of Concept
Integration test plan (in `banks-server`/`banks-client` test harness):
1. Start a `BanksServer` over a `BankForks` configured to advance slots rapidly (e.g., call `bank_forks.write().unwrap().insert(...)` / roll forward many banks in a background task, simulating natural slot progression, similar to `Self::run`).
2. Build a `VersionedTransaction` whose `recent_blockhash` is valid in the current Processed bank but is close to the edge of the blockhash queue's retention window (i.e., about to be evicted, e.g. `MAX_RECENT_BLOCKHASHES - 1` hashes old).
3. Concurrently, in a background task, register a large number of new blockhashes into the working bank's queue (via `bank.register_recent_blockhash` calls across many synthetic slot advances) so that by the time `process_transaction_with_commitment_and_context` executes its second `self.bank(commitment)` call, the target blockhash has been evicted.
4. Call `banks_client.process_transaction_with_commitment(transaction, CommitmentLevel::Processed)` and assert that instead of panicking, the call returns `Err(TransactionError::BlockhashNotFound)` (currently it panics with `unwrap()` on `None` at `banks-server/src/banks_server.rs:346`).
5. Wrap the server task execution in `std::panic::catch_unwind` (or observe the tokio task's `JoinError::is_panic()`) to confirm the current code panics under this induced race, demonstrating the vulnerability before the fix.
