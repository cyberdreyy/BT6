### Title
Loss-adjusted withdrawal receipt escapes its haircut when a second request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
A `stopEpochWithDuration` loss is supposed to haircut pending withdrawal receipts through `lossRecoveryPriceByEpoch`, but `_claimLossAdjustedWithdrawRequest` looks up that haircut using only `lastWithdrawRequest[_user]` — a single mutable marker that is overwritten every time the same user submits a new `requestWithdraw`. Like the DPoP verifier that checks an attacker-modifiable field instead of the bound key, the claim path binds the loss price to a field the user controls rather than to the epoch that actually suffered the loss. The stale haircut is silently skipped and the receipt is paid at par by `_claimFundedWithdrawRequest`, stealing from the pool's funded withdrawal reserve.

### Finding Description
- `requestWithdraw` in `IdleCreditVault.sol` stores the request in `withdrawsRequestsByEpoch[_user][currentEpoch]`, aggregates it into `withdrawsRequests[_user]`, and unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` (IdleCreditVault.sol:282-293). The vault explicitly allows a second request while an earlier one is unclaimed ("he will have to wait for another epoch to claim both requests", lines 323-324).
- When a loss is applied via `stopEpochWithDuration`/`previewLossAdjustedWithdrawFunds`, the strategy records `lossRecoveryPriceByEpoch[epoch]` and `collectWithdrawFunds` pulls only the reduced amount from the borrower.
- On claim, `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest(_user)`, which computes `lossEpoch = lastWithdrawRequest[_user]` and looks up `lossRecoveryPriceByEpoch[lossEpoch]` (IdleCreditVault.sol:789-800). If a user requested in epoch A (which later got haircut) and then made any second request in epoch B, `lastWithdrawRequest` is B, `lossRecoveryPriceByEpoch[B] == 0`, and the function returns 0 — the epoch-A haircut is never applied.
- `_claimFundedWithdrawRequest` then pays the entire aggregate `withdrawsRequests[_user]` (epoch A + epoch B) at par from funded underlyings (IdleCreditVault.sol:338-349). The borrower only funded the post-loss amount, so the excess `(1 - lossRecoveryPrice) * claimBasisA` is paid out of underlying that was funded for *other* users' receipts.
- Receipt transfers are disabled (`testReceiptTransfersRemainDisabledAfterDefault`, strategy-token `_transfer` guarded), so the attacker must use two sequential requests on the same address — both are unprivileged `requestWithdraw` calls requiring only a KYC'd wallet.

### Impact Explanation
Direct theft / insolvency of the funded withdrawal reserve. The attacker redeems their loss-adjusted receipt at par, extracting `claimBasisA * (1 - lossRecoveryPrice)` of underlying that belongs to other pending withdraw requesters. With a 50% loss price on a 100k USDC receipt, ~50k USDC is stolen; the last honest claimer's `_claimFundedWithdrawRequest` underflows or `_transferFundedClaim` reverts (`balance - reserve < amount` guard), permanently freezing the residual for other claimants. Broken invariant: loss waterfall — pending receipts must share the epoch loss pro rata.

### Likelihood Explanation
Requires a loss epoch (`stopEpochWithDuration` with `_lossAmount > 0`) to be executed by the honest manager — an in-scope, documented flow. The attacker then just calls `requestWithdraw` twice across two consecutive buffer windows before claiming, both unprivileged actions with `isWalletAllowed(msg.sender)` satisfied by any KYC'd lender. No privileged cooperation is needed. Likelihood is gated by a loss event actually occurring, keeping it medium.

### Recommendation
Track per-epoch loss claims instead of keying the lookup off the mutable `lastWithdrawRequest`. Options: iterate/`pop` all epochs with entries in `withdrawsRequestsByEpoch[_user]` and apply each epoch's `lossRecoveryPriceByEpoch`, or record `lossRecoveryPriceByEpoch` per user at request time (e.g., a `receiptLossEpoch[_user]` list). At minimum, revert in `requestWithdraw` when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` and the prior receipt is unclaimed, so a haircutted receipt cannot be masked by a later request.

### Proof of Concept
Foundry fork PoC outline (mirror `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossReceiptEscapesHaircut() external {
    // honest LP provides the funded reserve the attack will drain
    _depositWithUser(honestLp, 100_000 * ONE_SCALE, true);
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);

    // epoch 0 buffer: both request full withdraw
    vm.prank(attacker); uint256 reqA = cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(honestLp); cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);
    // manager stops epoch with a loss: lossRecoveryPriceByEpoch[0] = 50%
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(newApr, expectedInt, 30 days, lossAmount);

    // epoch 1 buffer: attacker requests again (dust tranche), overwriting lastWithdrawRequest
    _depositWithUser(attacker, 1 * ONE_SCALE, true);
    vm.prank(attacker); cdoEpoch.requestWithdraw(0, address(AAtranche)); // lastWithdrawRequest = 1

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, newApr, _expectedFundsEndEpoch());

    // attacker claims: loss lookup hits lossRecoveryPriceByEpoch[1] == 0,
    // funded path pays reqA at PAR + reqB, ~50% excess on reqA stolen
    vm.prank(attacker); cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(attacker), reqA * lossPrice / 1e18); // paid above haircut

    // honest LP's claim now reverts / pays short: reserve drained
    vm.prank(honestLp);
    vm.expectRevert(); // NotAllowed from _transferFundedClaim reserve guard
    cdoEpoch.claimWithdrawRequest();
}
```

Caveat: I could not re-read the exact write site of `lossRecoveryPriceByEpoch` in this iteration to confirm the epoch key used, but `_claimLossAdjustedWithdrawRequest` at `contracts/strategies/idle/IdleCreditVault.sol:789-801` unambiguously keys the lookup on the user-controlled `lastWithdrawRequest[_user]`, and `requestWithdraw` (lines 282-293) overwrites that marker without checking for a pending loss-adjusted receipt.
