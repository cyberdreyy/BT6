### Title
Committed EIP-8130 phases are not rolled back when a later phase reverts due to a pause (or other feature) gate, permanently destroying value moved in an earlier phase — ([File: crates/common/evm/src/eip8130.rs])

### Summary
An EIP-8130 (account-abstraction) transaction's `calls` are grouped into an ordered list of phases, each executed and committed independently against a shared journal checkpoint. As documented in `execute_calls`, a phase that succeeds is merged into the parent journal via `checkpoint_commit()` and becomes durable once the transaction commits, while only a *later* reverting phase is rolled back and causes all *subsequent* phases to be skipped. Any state change (e.g., a B-20 `burn`/`transfer`/`seize` call) executed in an earlier phase therefore survives even though a later phase that was supposed to complete the user's intended operation (e.g., a `mint` gated by `IB20::PausableFeature::MINT`) fails and is discarded. This mirrors the reported Hyperlane bug class: an irreversible "burn" step can commit while the corresponding "mint"/completion step is blocked by a pause check, with no atomicity across the whole transaction and no recovery path for the value already destroyed.

### Finding Description
`Eip8130Executor::execute_calls` iterates `signed.tx().calls` phase by phase: [1](#0-0) 

Each phase opens a journal checkpoint, runs its calls, and on success calls `checkpoint_commit()`: [2](#0-1) 

The crate-level doc comment for `Eip8130Executor` explicitly states this behavior as intended: "If any call in a phase reverts (or is blocked by the policy gate), that phase's state changes are discarded and every later phase is skipped, but the gas already consumed is still charged and the transaction is still included." [3](#0-2) 

The B-20 token precompiles (reachable from ordinary EVM calls, including from within an EIP-8130 phase) gate `mint`, `burn`, `transfer`, and `seize` behind per-feature pause bits that revert with `IB20::ContractPaused` when the relevant `PausableFeature` is paused, and pausing is a normal, expected, non-exceptional admin action: [4](#0-3) [5](#0-4) 

Because each phase's success/failure is judged independently and only forward-skips later phases, a transaction whose intent is "burn token A in phase 1, then mint/receive an equivalent value in phase 2" has no cross-phase atomicity: if phase 1 succeeds (burn/transfer/seize commits) and a role holder pauses the target feature (e.g., `MINT`) for phase 2's target token before the transaction lands, phase 2 reverts with `ContractPaused`, its state is rolled back, and every subsequent phase is skipped — but phase 1's already-committed burn is not undone. The transaction is still included; the sender's nonce is consumed and fees are paid, exactly as documented. This is functionally identical to the reported bug class: an irrevocable "burn" side of a two-step value-moving operation can complete while the corresponding completion step is blocked by a pause, and there is no protocol-level guarantee of retry or reversal — the committed phase's effect (e.g., burned B-20 balance and reduced total supply) is permanently lost from the user's perspective within that transaction, with no automatic mechanism to re-run or refund it.

### Impact Explanation
Value moved in a successfully committed phase (e.g., burning a B-20 asset, transferring balance to a third party, or a `seize`-style move) is durable once the transaction is included, regardless of whether the transaction's overall (multi-phase) intent is satisfied. A user constructing a multi-phase EIP-8130 transaction that both destroys value in an early phase and expects to receive equivalent value in a later phase can suffer a permanent, unrecoverable loss of funds if an admin pauses the relevant feature between the time the transaction is simulated/signed and the time it is included in a block — the exact "burn succeeds, mint fails, no recovery" pattern described in the external report. This is a High-impact, permanent loss-of-funds class of bug because there is no compensating transaction, no atomic rollback across phases, and no retry guarantee once the transaction lands (block inclusion is final).

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires (a) a user or wallet/app to construct a multi-phase EIP-8130 transaction whose phases are causally linked (burn-then-mint / burn-then-receive pattern across phases or tokens), and (b) a pause (or other feature-gating) action to land on the relevant token/feature in the window between transaction construction/simulation and its actual block inclusion. Because pausing is a routine, expected admin operation on B-20 tokens (used for security response), and because the phased-calls design is explicitly documented as non-atomic across phases, this is a realistic race that any application composing multi-phase AA transactions with pause-gated tokens would be exposed to, without needing any privileged access from the transaction sender itself.

### Recommendation
Treat committed EIP-8130 phases as provisional until the entire transaction's `calls` sequence has evaluated successfully, or provide a way for callers to declare cross-phase dependencies that must roll back together (e.g., an "all phases succeed or entire transaction reverts" mode), rather than only rolling back the failing phase and skipping later ones while keeping earlier commits. At minimum, document and strongly warn integrators that phase commits are irreversible independent of later phase outcomes, and require pause-gated precompiles to be checked for pending pause proposals or to expose a way for a multi-phase transaction to atomically require an invariant (e.g., "target feature was active when this phase was authorized") so that a race between pause and inclusion cannot silently strand value.

### Proof of Concept
1. Admin makes B-20 token `A`'s `BURN` feature and token `B`'s `MINT` feature both active.
2. A user submits (or a wallet composes) an EIP-8130 transaction with two phases:
   - Phase 1: `IB20::burnCall` (or `transferCall`) on token `A`, destroying/moving the user's balance.
   - Phase 2: `IB20::mintCall` on token `B` to credit the user (or another linked operation intended to complete the value transfer).
   The transaction is simulated successfully via `eth_estimateGas`/`eth_call` while both features are active, matching `Eip8130Executor::simulate`.
3. Before the transaction is included, an account holding `B20TokenRole::Pause` on token `B` calls `pause` with `PausableFeature::MINT`, per `crates/common/precompiles/src/b20_asset/logic/v2.rs:368-373` / `v1.rs:337-361`.
4. The transaction is included. In `execute_calls` (`crates/common/evm/src/eip8130.rs:1214-1291`), Phase 1's burn call succeeds and is committed via `checkpoint_commit()`. Phase 2's `mint` call reverts with `IB20::ContractPaused { feature: MINT }`; its checkpoint is reverted via `checkpoint_revert`, and it is the last phase so nothing further is skipped, but Phase 1's burn remains committed.
5. Result: the user's token `A` balance is permanently burned; no token `B` was minted; the transaction is included (nonce consumed, fee paid) per the documented behavior at `crates/common/evm/src/eip8130.rs:22-30`. There is no protocol mechanism to reverse the burn or retry the mint — a permanent loss of funds structurally identical to the reported bridge issue.

    fn pause(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        features: Vec<IB20::PausableFeature>,
        privileged: bool,
    ) -> Result<()> {
        for feature in &features {
            B20PausableFeature::ensure_one_of(*feature, Self::PAUSABLE_FEATURES)?;
        }
        if !privileged {
            B20Guards::ensure_token_role(token, caller, B20TokenRole::Pause)?;
        }
        if features.is_empty() {
            return Err(BasePrecompileError::revert(IB20::EmptyFeatureSet {}));
        }
        let mut next = token.accounting().paused()?;
        for feature in &features {
            next |= B20PausableFeature::mask(*feature);
        }
        token.accounting_mut().set_paused(next)?;
        token
            .accounting_mut()
            .emit_event(IB20::Paused { updater: caller, features }.encode_log_data())
    }
