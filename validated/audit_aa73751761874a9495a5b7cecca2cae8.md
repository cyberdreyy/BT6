### Title
`EscapeForAnsiC` hex-escapes bytes for `$'...'` ANSI-C quoting, which bash re-expands back to raw bytes, letting job-controlled ESC/CSI/OSC sequences reach the trace unescaped - (`functions/script_legacy/internal/escape.go`)

### Summary
`CommandFormatter.FormatLogLine` builds a `echo $'...'` line to display the command being run, using `EscapeForAnsiC` to hex-escape control bytes (0x00-0x1F, 0x7F, >0x7F) so that "ANSI escape sequences [can't] manipulat[e] terminal" per the code's own comment. This protection is illusory: `\xHH` is the standard ANSI-C quoting escape recognized by `$'...'`, so when the generated script line is actually executed by bash, `\x1b` is expanded right back into the raw ESC byte (0x1B), fully reconstituting the original control sequence in the trace output.

### Finding Description
`FormatLogLine` builds `command = ansiGreen + "$ " + displayCommand + ansiReset` and returns `fmt.Sprintf("echo $'%s'", EscapeForAnsiC(command))` [1](#0-0) . `displayCommand` derives from the raw job-controlled command string (only collapsed to the first line if multi-line) [2](#0-1) , so an attacker fully controls arbitrary bytes inside it, including ESC (0x1B) and following CSI/OSC bytes.

`EscapeForAnsiC` hex-escapes control/non-ASCII bytes as `\xHH` and leaves the escape's "\`, `x`, hex digits" as literal printable ASCII characters in the *Go string* [3](#0-2) . The test suite confirms `\x1b[1;32mGreen\x1b[0m` becomes the literal 4-character sequence `\x1b` followed by unmodified `[1;32mGreen`, then `\x1b[0m` again [4](#0-3) .

The bug is that this output is embedded inside bash's `$'...'` ANSI-C quoting construct. Per bash semantics, `\xHH` inside `$'...'` is expanded at *shell parse/execution time* back into the literal byte `0xHH`. So when the generated line `echo $'...\x1b[1;32mGreen\x1b[0m...'` is executed, bash reconstructs the original raw ESC byte followed by the untouched `[1;32mGreen`/`[0m` text — i.e., the exact original ANSI CSI sequence is reproduced verbatim in the command's stdout, which becomes the job trace. The same applies to any attacker-supplied CSI/OSC/DCS payload (e.g., OSC 52 `\x1b]52;c;<base64>\x07`) placed in a script command: the semicolons, digits, and terminator bytes are left untouched by `EscapeForAnsiC` (only the true control bytes 0x00-0x1F/0x7F/>0x7F get the `\xHH` treatment), and `\x1b`/`\x07` are simply reconstituted by bash's ANSI-C quoting when the script runs. The escaping therefore does not remove or neutralize the sequence — it merely round-trips it through a transport encoding that bash itself undoes.

The comment in `escape.go` ("Control characters ... are hex-escaped to prevent terminal manipulation... prevents jobs from clearing screen or rewriting logs using ANSI escape sequences") states an intended invariant that the implementation does not actually enforce for the `EscapeForAnsiC`/`$'...'` path, because it conflates "safe to embed in Go source/generated script text" with "neutralized when the shell evaluates it." No other check (masking, trace filtering) intercepts this before it reaches the trace, since the escape function is the dedicated defense point per its own documentation.

### Impact Explanation
Any job whose script line (a command argument, e.g. from a `.gitlab-ci.yml` `script:` entry) contains ESC-prefixed control sequences will have those sequences reproduced verbatim in the raw job trace once the runner executes the generated `echo $'...'` command-echo line. A downstream consumer viewing raw/unprocessed trace bytes (e.g., via terminal `cat`/`tail` on the job log, or any trace viewer that does not itself sanitize control bytes) can be subjected to terminal manipulation — cursor repositioning, screen/log clearing to hide malicious output, or (on terminals/emulators supporting it) OSC 52 clipboard writes and other OSC/DCS payloads. This is a session/terminal-hijack-style impact against anyone viewing that job's trace in a raw terminal, matching the scoped impact in the question.

### Likelihood Explanation
Fully attacker-controlled and trivially reachable: any pipeline author can put an ESC-containing string into a `script:` line (this is the value passed as `commands` to `ScriptGenerator.GenerateScript`, which calls `CommandProcessor`/`CommandFormatter.FormatLogLine` for every command) [5](#0-4) . No special privileges, secrets, or admin misconfiguration are required — only the `posixMode == false` (bash) code path, which is the default/common path in this legacy script generator [6](#0-5) . This is deterministic and repeatable on every run of the affected command.

### Recommendation
Do not rely on `\xHH` hex-escaping when the destination quoting context is bash's `$'...'` ANSI-C quoting, since that context re-expands `\xHH` back to raw bytes. Instead, either: (1) switch to POSIX double-quote escaping (as already used in `EscapeForPosix`) for the command-echo line so control bytes are never given a shell-level re-expansion path, or (2) if `$'...'` must be used for coloring, strip/reject raw control bytes from the *user-controlled portion* of the command (not the trusted `ansiGreen`/`ansiReset` constants) before formatting, ensuring only the runner-injected ANSI codes reach the terminal, or (3) filter the final trace stream to prevent CSI/OSC/DCS sequences originating from job-controlled text.

### Proof of Concept
Go unit test:
```go
func TestFormatLogLine_ANSIInjection_SurvivesShellExpansion(t *testing.T) {
    formatter := NewCommandFormatter(false) // bash mode uses $'...'
    payload := "\x1b]52;c;ZXZpbA==\x07" // OSC 52 clipboard write
    line := formatter.FormatLogLine(payload)

    // Simulate bash ANSI-C quoting expansion of \xHH sequences that occurs
    // when the shell actually executes `line`.
    expanded := expandAnsiCQuoting(line) // helper reproducing bash's $'...' \xHH handling

    // The original raw ESC/BEL bytes and OSC payload are fully reconstructed,
    // proving the "escaping" does not neutralize the sequence at execution time.
    assert.Contains(t, expanded, "\x1b]52;c;ZXZpbA==\x07")
}
```
Expected assertion: the reconstructed/expanded string (mirroring what bash would actually emit to stdout/trace when running the generated `echo $'...'` line) contains the raw, unescaped OSC 52 sequence, demonstrating the control-sequence injection reaches the trace despite `EscapeForAnsiC`. An integration-level PoC job (`script: ["printf '\\x1b]52;c;ZXZpbA==\\x07'"]` equivalent, or a script line literally containing the ESC byte) run through the real runner and shell would show the raw ESC/OSC bytes in the job's raw trace log.
