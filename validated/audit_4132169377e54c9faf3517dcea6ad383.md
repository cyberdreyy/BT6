### Title
`DefaultDistributor.claim` lets a caller send the entire recovery payout to an arbitrary `_to`, enabling theft of a victim's defaulted-tranche recovery via phishing - ([File: contracts/DefaultDistributor.sol](contracts/DefaultDistributor.sol))

### Summary
`DefaultDistributor.claim` burns/pulls the caller's entire `trancheToken` balance via `safeTransferFrom(msg.sender, ...)` but sends the underlying recovery payout to an unrestricted `_to` parameter supplied by the caller. The bug class from the external report — a function that transfers the caller's assets while routing the economic benefit to a counterparty-controlled address, with no check binding the payer to the beneficiary — maps directly onto this surface. There is no `require(_to == msg.sender)` or equivalent guard.

```solidity
// contracts/DefaultDistributor.sol:35-41
function claim(address _to) external {
  require(isActive, '!ACTIVE');
  IERC20 tranche = IERC20(trancheToken);
  uint256 trancheBal = tranche.balanceOf(msg.sender);
  tranche.safeTransferFrom(msg.sender, address(this), trancheBal);
  IERC20(token).safeTransfer(_to, trancheBal * rate / ONE_TRANCHE);
}
```

### Finding Description
After `_handleBorrowerDefault`/`finalizeDefault` on `IdleCreditVault`, recovery proceeds are distributed through `DefaultDistributor`, one per tranche class. The contract is funded with all recovered `token` and `setIsActive(true)` fixes `rate` against the frozen tranche supply. A holder's entire recovery is then claimed in a single call: `claim` pulls the caller's *full* tranche balance and pays out `trancheBal * rate / ONE_TRANCHE` underlyings to `_to`.

Because `_to` is arbitrary, any claim transaction signed by a tranche holder can silently redirect their whole recovery. Attack path, by an unprivileged attacker (any EOA):

1. Borrower defaults; `finalizeDefaultRecovery` funds the `DefaultDistributor` and activates claims.
2. Victim is a tranche holder with a standing `trancheToken` approval to the distributor (required for `claim`; routinely granted as max approval when interacting, mirroring the "max approval is normal" precondition in the original report).
3. Attacker gets the victim to submit `claim(attacker)` — via a compromised/phishing frontend, a spoofed transaction, or wallet calldata injection. The calldata is a plain `claim(address)` call with one address argument and looks like a normal claim.
4. All of the victim's tranche tokens are pulled and the entire underlying recovery is paid to the attacker. The victim's claim is consumed and cannot be repeated — the mapping of payouts is per-balance, so the loss is the full claimable recovery.

The function also lacks any partial-claim or beneficiary binding, so there is no legitimate reason for `_to != msg.sender` on behalf of an EOA, exactly parallel to "there is no reason why the lender should ever call repay for the borrower."

### Impact Explanation
Direct theft of 100% of a victim's post-default recovery payout for the affected tranche class. For an AA or BB holder whose position was already impaired by the default, this confiscates whatever fraction the recovery `rate` returns — potentially the victim's entire remaining stake in the pool (all tranche tokens are pulled, not a chosen amount). Quantified loss: `victimTrancheBalance * rate / 1e18` underlying tokens per call.

### Likelihood Explanation
Requires (a) a defaulted pool with an active `DefaultDistributor`, (b) the victim holding tranche tokens with an outstanding approval to the distributor, and (c) a phishing vector (infected frontend, malicious dapp, spoofed tx). These are the same preconditions rated Medium in the source finding. Defaults are exceptional events, but they are precisely when large one-time payouts flow through a single `claim` call, and post-default UX is often ad-hoc (manual claiming rather than a polished frontend), raising the phishing surface. The pull of the *entire* balance makes one successful phish total.

### Recommendation
Restrict the beneficiary to the caller, or bind the claim to `msg.sender`:

```solidity
function claim() external {
  require(isActive, '!ACTIVE');
  IERC20 tranche = IERC20(trancheToken);
  uint256 trancheBal = tranche.balanceOf(msg.sender);
  tranche.safeTransferFrom(msg.sender, address(this), trancheBal);
  IERC20(token).safeTransfer(msg.sender, trancheBal * rate / ONE_TRANCHE);
}
```

If third-party claiming (e.g., for smart-wallet/vault receivers) must be preserved, add `require(_to == msg.sender)` as the default path or an explicit allowlist/forwarder mechanism rather than a free `_to` parameter.

### Proof of Concept
```solidity
// SPDX-License-Identifier: Apache-2.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../contracts/DefaultDistributor.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MockERC20 is ERC20 {
    constructor(string memory n, string memory s) ERC20(n, s) {}
    function mint(address to, uint256 amt) external { _mint(to, amt); }
}

contract DefaultDistributorClaimPhishTest is Test {
    MockERC20 underlying;
    MockERC20 tranche;
    DefaultDistributor distributor;

    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    function setUp() public {
        underlying = new MockERC20("USDC", "USDC");
        tranche = new MockERC20("AA tranche", "AA");

        distributor = new DefaultDistributor(
            address(underlying), address(tranche), address(this)
        );

        // Simulate post-default state: victim holds tranches,
        // distributor funded with the recovered underlying.
        tranche.mint(victim, 10_000e18);
        underlying.mint(address(distributor), 5_000e6);

        // Activate claims: rate = 5000e6 * 1e18 / 10000e18 = 0.5e6
        distributor.setIsActive(true);

        // Standing approval is a normal precondition for claim()
        vm.prank(victim);
        tranche.approve(address(distributor), type(uint256).max);
    }

    function testClaimToAttackerDrainsVictimRecovery() public {
        uint256 victimUnderlyingPre = underlying.balanceOf(victim);
        uint256 attackerPre = underlying.balanceOf(attacker);

        // Phished call: victim signs claim(attacker)
        vm.prank(victim);
        distributor.claim(attacker);

        // Victim's entire tranche balance was pulled
        assertEq(tranche.balanceOf(victim), 0, "victim tranches pulled");
        // Recovery went to attacker, victim received nothing
        assertEq(underlying.balanceOf(victim), victimUnderlyingPre, "victim got no recovery");
        assertEq(
            underlying.balanceOf(attacker) - attackerPre,
            5_000e6,
            "attacker received victim's full recovery"
        );
        // Claim cannot be repeated - loss is total and irreversible
        vm.prank(victim);
        distributor.claim(victim); // pulls 0 balance, pays 0
        assertEq(underlying.balanceOf(victim), victimUnderlyingPre, "no recovery possible");
    }
}
```

This reproduces the full loss path on a fork: deploy the real `DefaultDistributor` against the deployed tranche token after `finalizeDefaultRecovery`, grant the standing approval, and the phished `claim(attacker)` transfers the victim's entire recovery.
