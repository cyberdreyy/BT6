### Title
Unfunded instant-withdraw receipts are claimable against other users' funded reserves in `claimInstantWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` mints a receipt and queues the user in `pendingInstantWithdraws`, but `claimInstantWithdrawRequest` pays the full `instantWithdrawsRequests[_user]` balance from whatever underlying the vault happens to hold, without checking that the borrower's funding for that request (`collectInstantWithdrawFunds` → `getInstantWithdrawFunds`) ever arrived. When the vault is holding underlying that was collected to back *other* users' matured withdraw claims, an attacker can redeem an unfunded instant receipt against that reserve — the same "unscoped replay against another tenant's resource" pattern as the Trigger.dev bug, where a request scoped only by a global ID executes against state belonging to someone else.

### Finding Description
- `requestInstantWithdraw` burns the CDO's strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[_user]` and the global `pendingInstantWithdraws` — a promise that the *borrower* will fund it later. [1](#0-0) 
- `claimInstantWithdrawRequest` (reachable via `IdleCDOEpochVariant.claimInstantWithdrawRequest`, which only checks `allowInstantWithdraw` [2](#0-1) ) simply reads `instantWithdrawsRequests[_user]`, burns it, and calls `_transferFundedClaim` — with no per-epoch or per-request check that funding was collected. [3](#0-2) 
- Funding is tracked only globally: `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` and pulls tokens from the CDO; nothing marks which receipts are funded. [4](#0-3) 
- `_transferFundedClaim` guards only `defaultRecoveryReserve`; the funded reserves backing other users' matured `claimWithdrawRequest` receipts (pulled in earlier by `collectWithdrawFunds` and left in the vault until claimed) are unprotected spendable balance. [5](#0-4) 

Attack sequence (running epoch, fixed-APR mode):
1. Prior epoch(s) stopped normally; `collectWithdrawFunds` pulled underlying into the vault backing victim's matured-but-unclaimed withdraw receipt.
2. Attacker (KYC'd tranche holder) calls `requestInstantWithdraw` during the running epoch — receipt minted, `pendingInstantWithdraws` grows.
3. Attacker immediately calls `claimInstantWithdrawRequest`; the vault transfers underlying that was reserved for the victim's funded claim.
4. If the borrower later funds via `getInstantWithdrawFunds`, the reserve is replenished and the victim is only temporarily frozen; but if the epoch ends in borrower default before funding arrives, the attacker exited at par using the victim's funded reserve, while the victim's claim either reverts on insufficient balance or is forced into the haircut recovery path — permanent loss borne by the victim.

### Impact Explanation
Theft of funded withdraw reserves (or permanent freezing of victims' claims) up to the vault's unprotected underlying balance, bounded by `instantWithdrawsRequests` the attacker can create from their tranche holdings. In the default scenario the loss equals the amount of the attacker's unfunded instant receipt paid from funded reserves; victims' already-funded par claims become unpayable or recovery-haircutted.

### Likelihood Explanation
Requires `allowInstantWithdraw` enabled and the vault holding claimable reserves — a normal state between a `stopEpoch` that funded pending receipts and users actually claiming. The attacker needs only tranche tokens and a KYC'd wallet; no privileged action or timing race is needed since there is no funding gate on the claim path.

### Recommendation
Track funded vs. unfunded instant receipts (e.g., a per-user `fundedInstantWithdraws` counter incremented in `collectInstantWithdrawFunds` pro-rata or FIFO, or a per-epoch funded flag like `instantWithdrawClaimsByEpoch`), and have `claimInstantWithdrawRequest` pay only the funded portion. Alternatively, revert instant claims while `pendingInstantWithdraws` for the request's epoch is non-zero.

### Proof of Concept
A Foundry fork test mirroring `testClaimWithdrawRequestEpochRunning` in `test/foundry/IdleCreditVault.t.sol`: victim deposits AA, epoch 0 runs and stops with full funding, victim calls `requestWithdraw` (receipt funded via `collectWithdrawFunds`, left unclaimed). Epoch 1 starts; attacker deposits AA in the buffer and calls `requestInstantWithdraw`, then calls `claimInstantWithdrawRequest` before `instantWithdrawDelay` elapses and before `getInstantWithdrawFunds` runs. Assert attacker received underlying while `pendingInstantWithdraws` remains non-zero and the vault balance dropped below the victim's funded claim; then simulate default in epoch 1 and show the victim's `claimWithdrawRequest` reverts or pays less than the funded par amount.

Caveat: I could not fully confirm within the available iterations that no additional funding gate exists inside `IdleCDOEpochVariant.requestInstantWithdraw`/`getInstantWithdrawFunds` (e.g., restricting instant requests to post-stop windows only); if such gating exists, the attack window shrinks but the missing funded-check on the claim path still stands wherever vault balance is co-mingled.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
