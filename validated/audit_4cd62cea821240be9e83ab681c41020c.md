### Title
Loss-adjusted withdraw receipts keyed to a stale `epochNumber` claim at par and drain the vault - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records each withdraw receipt under the epoch in which it was requested (`lastWithdrawRequest[_user]`, `withdrawsRequestsByEpoch[_user][epoch]`), but `collectWithdrawFunds` stores the loss-recovery price under the *current* `epochNumber`, which `deposit()` has already incremented during `stopEpoch`. The receipt "objects" are therefore dereferenced through an epoch pointer that no longer matches the epoch that owns them — the on-chain analog of CVE-2022-1097's use-after-free via a stale direct reference. As a result, loss-adjusted receipts are paid at par from an underfunded reserve.

### Finding Description
`deposit()` bumps `epochNumber` whenever it is called while the epoch is still running, which per the inline comment is exactly the `stopEpoch` deposit path:

```solidity
// IdleCreditVault.sol
if (IIdleCDOEpochVariant(idleCDO).isEpochRunning()) {
    // deposit done on stopEpoch (before setting the var to false) so we reset the counter
    totEpochDeposits = 0;
    epochNumber += 1;
}
```

`requestWithdraw` pins receipts to the *pre-bump* epoch:

```solidity
uint256 currentEpoch = epochNumber;              // N
lastWithdrawRequest[_user] = currentEpoch;       // N
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;   // keyed under N
```

On a `stopEpochWithDuration` loss, `collectWithdrawFunds` runs after the stop-epoch deposit (the bump) and writes the haircut under the *new* epoch:

```solidity
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;  // keyed under N+1
```

But `_claimLossAdjustedWithdrawRequest` dereferences the price via `lastWithdrawRequest` (still `N`):

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];             // N
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];  // == 0 -> early return
```

The claim then falls through to `_claimFundedWithdrawRequest`, whose only gate is `epochNumber > lastWithdrawRequest` (`N+1 > N`, satisfied), and pays the full un-haircutted `withdrawsRequests[_user]` via `_transferFundedClaim`, burning the full receipt.

The same miskeying corrupts post-loss requests: a user who requests during epoch `N+1` gets `lastWithdrawRequest = N+1`, finds `lossRecoveryPriceByEpoch[N+1] != 0` with `withdrawsRequestsByEpoch[user][N+1] != 0`, and is forced onto the loss-adjusted path, applying epoch N's haircut to a receipt created after the loss — and `requestWithdraw` additionally reverts for that user forever until they claim (the guard at lines 263–271).

The same stale-epoch defect applies to default finalization: `defaultRecoveryEpoch = epochNumber` in `finalizeDefaultRecovery`, while `instantWithdrawsRequestsByEpoch` and `withdrawsRequestsByEpoch` were written under the pre-bump epoch, so `_claimDefaultedInstantWithdrawRequest`/`_claimDefaultedWithdrawRequest` can miss basis recorded under the old epoch.

### Impact Explanation
The loss waterfall invariant is broken: the haircut computed by `previewLossAdjustedWithdrawFunds` is never actually applied to the receipts it was charged against. Only `_amount < pendingBasis` was collected, yet each receipt claims `claimBasis` at 100%. Early claimants receive more than the funded share (stealing the loss that should be socialized), and the final claimants' transactions revert on insufficient balance — a combination of direct overpayment and permanent freezing of the remainder. Secondary impact: post-loss-epoch requesters absorb a haircut that was not theirs (unfair burn of receipt value) and are blocked from opening new requests until they claim.

### Likelihood Explanation
Requires only an unprivileged lender flow plus the honest-manager path `stopEpochWithDuration(_lossAmount)` (a real, non-default loss — explicitly in scope per the waterfall mapping). No privileged misbehavior, no oracle dependence. The trigger is any epoch that ends with `pendingWithdraws != 0` and a partial borrower repayment; the miskeying is deterministic whenever `collectWithdrawFunds` executes after the epoch-bumping `deposit` inside the same stop flow. One caveat: the exact call ordering between `deposit()` (the `epochNumber` bump) and `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpochWithDuration` could not be fully verified in the available context; if the CDO collects before depositing, the keys coincide and the bug does not manifest — the PoC should assert this ordering first.

### Recommendation
Store the recovery price under the epoch that actually owns the pending receipts, not the live counter: in `collectWithdrawFunds`, write `lossRecoveryPriceByEpoch[epochNumber - 1]` (or better, persist the epoch in which the pending bucket was formed, e.g. `pendingWithdrawsEpoch`, set when `pendingWithdraws` transitions from zero). Symmetrically, `finalizeDefaultRecovery` should snapshot `defaultRecoveryEpoch` from the request epoch, and `requestWithdraw` should validate against the same stored pending-epoch key rather than `lastWithdrawRequest`. Add invariant tests asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[u]] != 0` for every user with an unfunded receipt after a loss-adjusted stop.

### Proof of Concept
Foundry fork test outline (`test/foundry/IdleCreditVaultEpochKey.t.sol`):

1. Fork mainnet at a block with an `IdleCDOEpochVariant` + `IdleCreditVault` pair live; impersonate `manager`/`borrower` (honest, used only for sequencing).
2. Epoch N running: user `A` deposits via AA tranche; `A` calls `requestWithdraw` → `withdrawsRequestsByEpoch[A][N] = X`, `lastWithdrawRequest[A] = N`.
3. Borrower repays only `R < pendingWithdraws`-covering amount; `manager` calls `stopEpochWithDuration(_lossAmount)` where `previewLossAdjustedWithdrawFunds` returns `pendingToFund = R`.
4. Inside that same tx, `strategy.deposit` executes while `isEpochRunning()` → `epochNumber` becomes `N+1`; `collectWithdrawFunds(R)` then writes `lossRecoveryPriceByEpoch[N+1]`. Assert `lossRecoveryPriceByEpoch[N] == 0`.
5. Call `claimWithdrawRequest(A)` through the CDO: `_claimLossAdjustedWithdrawRequest` returns 0 (price lookup under `N`), `_claimFundedWithdrawRequest` pays `X` at par.
6. Second requester `B` (same epoch N) claims → transfer reverts or vault balance is exhausted before paying `B`'s haircutted share. Assert `claimed_A == X` while `lossRecoveryPriceByEpoch[N+1] * X / 1e18 < X` and `underlying.balanceOf(strategy) < B`'s claim.
7. Optional second assertion: new user `C` requests in epoch `N+1`, then attempts `requestWithdraw` again → `NotAllowed` revert, and `claimWithdrawRequest(C)` returns `X_C * lossRecoveryPriceByEpoch[N+1] / 1e18`, i.e. `C` absorbs epoch N's haircut.
