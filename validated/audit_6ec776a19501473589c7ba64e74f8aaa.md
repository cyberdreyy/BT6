### Title
External Initiator credentials can trigger job runs for arbitrary, unrelated jobs via `/v2/jobs/:ID/runs` due to missing per-resource authorization - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` always injects a fixed `clsessions.User{Role: clsessions.UserRoleRun}` into the Gin context regardless of which bridge/EI record matched, and it is indistinguishable from a real authenticated user to downstream code that calls `auth.GetAuthenticatedUser`. As a result, `PipelineRunsController.Create`'s explicit `isUser` gate ("only users are allowed to run jobs using int IDs - EIs not allowed") is bypassed by any External Initiator credential, allowing that EI to trigger a run for any job ID, not just the job/bridge tied to its own credentials.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) authenticates the EI token against the specific `bridges.ExternalInitiator` record, but then unconditionally does: [1](#0-0) 
It sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}` with no linkage to which bridge/job the EI is scoped to.

`GetAuthenticatedUser` (`core/web/auth/auth.go:178-187`) simply reads this key and returns `ok=true` whenever it is set — it cannot distinguish a genuine session/token user from a synthetic EI-derived user.

The route `POST /v2/jobs/:ID/runs` is registered under the `userOrEI` group that accepts `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`, gated only by `auth.RequiresRunRole`: [2](#0-1) 
`RequiresRunRole` only checks `user.Role != UserRoleView` — it performs no bridge/job-specific authorization [3](#0-2) .

Inside the handler, `PipelineRunsController.Create` attempts to restrict integer-ID job runs to "users" only, explicitly stating "EIs not allowed" in a comment: [4](#0-3) 
However, `isUser := auth.GetAuthenticatedUser(c)` evaluates to `true` for EI-authenticated requests as well, because `AuthenticateExternalInitiator` populated the exact same `SessionUserKey` context value. Consequently the intended EI restriction is ineffective: an EI credential holder can supply any integer job ID belonging to any job in the system and `prc.App.RunJobV2(ctx, jobID, nil)` is invoked with attacker-chosen `jobID`, with no verification that the ID corresponds to the bridge/job the EI credential was created for.

### Impact Explanation
This is an authorization bypass allowing an External Initiator credential — meant to be scoped to a specific bridge/job — to trigger pipeline runs of arbitrary unrelated jobs on the node. Depending on what those unrelated jobs do (e.g., jobs that move funds, write on-chain transactions, or call external bridges), an attacker with narrowly-scoped EI credentials can cause unauthorized execution of jobs they should have no access to, matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
The only precondition is possessing any single External Initiator's access key/secret (the minimal EI credential tier), which is a low-privilege, narrowly-scoped credential type. No admin/edit role, no other job's bridge secret, and no additional exploitation steps are required — the attacker just sends a normal `POST /v2/jobs/:ID/runs` request with a different job's numeric ID. This is fully repeatable and deterministic.

### Recommendation
Do not use the same `SessionUserKey` mechanism for EI-derived pseudo-users as for real authenticated users. Either:
- Introduce a distinct context flag/type (e.g., check `GetAuthenticatedExternalInitiator` explicitly) so `PipelineRunsController.Create` can reliably detect and reject EI-authenticated requests to the integer-ID route, restoring the intended "EIs not allowed" behavior, or
- Scope the EI's authorization to the specific bridge/job(s) it is associated with, and enforce that scoping in `PipelineRunsController.Create`/`RunJobV2` before triggering a run.

### Proof of Concept
Handler-level Go test plan:
1. Seed two jobs, Job A (bound to bridge/EI "ei-A") and Job B (unrelated, requiring only run role, e.g., webhook/cron with an int ID).
2. Create EI credentials for "ei-A" only via `bridges` ORM / `ExternalInitiatorsController`.
3. Build a Gin test router equivalent to `v2Routes`, mounting `userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))` with `auth.AuthenticateExternalInitiator` in the chain.
4. Send `POST /v2/jobs/<Job B ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to ei-A's credentials.
5. Assert: current behavior returns `200 OK` with a `pipelineRun` resource for Job B (i.e., `prc.App.RunJobV2` was called with Job B's ID) — expected/fixed behavior should return `401/403` because the EI credential for "ei-A" is not authorized to trigger Job B.

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
