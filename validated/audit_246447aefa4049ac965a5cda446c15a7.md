### Title
Node-side signer vote coordinator double-counts a flipped Reject→Accept vote, letting one signer's weight land in both `total_weight_rejected` and `total_weight_approved` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` tallies signer `BlockResponse` messages into a shared `BlockStatus` record per block. The guard that decides whether to add a signer's weight is **asymmetric** between the `Accepted` and `Rejected` branches: acceptance weight is gated on `gathered_signatures.contains_key(&slot_id)` while rejection weight is gated on `responded_signers.insert(slot_id)`. Because a single signer is allowed by its own state machine to move from `LocallyRejected` back to `LocallyAccepted` (re-evaluation), a Reject-then-Accept sequence from the same signer causes its weight to be added to `total_weight_rejected` *and* later to `total_weight_approved`, without ever being removed from the first bucket. This is a check-then-act flaw structurally analogous to the CVE's TOCTOU: the "already counted" check is scoped to the wrong piece of state, letting one vote's weight be spent twice across two mutually-exclusive tallies.

### Finding Description
`BlockStatus` tracks two independent structures for one block:
- `gathered_signatures: BTreeMap<u32, MessageSignature>` and `total_weight_approved`
- `responded_signers: HashSet<u32>` and `total_weight_rejected`

In the `Accepted` handler: [1](#0-0) 
weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, then `gathered_signatures` and `responded_signers` are both unconditionally inserted.

In the `Rejected` handler: [2](#0-1) 
weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot has "responded" at all).

Trace the two possible orderings for one signer's two messages on the same block:

- **Accept, then Reject** (correctly guarded): Accept inserts into `gathered_signatures` and `responded_signers` and adds approved weight. The later Reject calls `responded_signers.insert(slot_id)`, which now returns `false` (already present) — rejected weight is *not* added. Safe.
- **Reject, then Accept** (the flaw): Reject calls `responded_signers.insert(slot_id)` → `true` → `total_weight_rejected += weight`. The later Accept only checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (Accept never touched `gathered_signatures` before) → `total_weight_approved += weight` is added again for the *same* signer weight, and `responded_signers.insert` is called again but its return value is ignored on this path since the increment already happened unconditionally.

The signer's own lifecycle explicitly permits this ordering: a block that was locally rejected can be re-evaluated and locally accepted later (`should_reevaluate_reject_reason`, and the state machine explicitly allows `LocallyRejected --> LocallyAccepted`): [3](#0-2) [4](#0-3) 

So a single, honest-but-reconsidering signer (no majority, no key compromise) legitimately produces a Reject followed later by an Accept for the same `signer_signature_hash`, and the coordinator's bookkeeping double-attributes that one signer's weight: once as a rejection, once as an approval, with `total_weight_rejected` never decremented.

### Impact Explanation
This breaks the equality the coordinator relies on — "aggregated weight" is supposed to equal "sum of weights of signers whose current verdict is that outcome." After the flip, `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and a signer's weight is simultaneously counted toward both a live rejection tally and the acceptance tally used to gate `cvar.notify_all()` / pushing the block: [5](#0-4) 
and the symmetric rejection-threshold check: [6](#0-5) 
The literal impact category is "a rejection recounted as an accept" — one signer's stale rejection continues to count toward `total_weight_rejected` even after that signer accepted, so the node's rejected/approved math is corrupted and consensus decisions (whether to keep waiting, treat the block as dead, or accept it) are made against inflated, double-counted totals rather than the true distinct-signer weight.

### Likelihood Explanation
No majority or key compromise is required — a single signer that rejects, then legitimately reconsiders and accepts the same proposal (a normal, supported path in the signer's own re-evaluation logic), triggers the double count on the node coordinator. This requires no crafted timing beyond ordinary message gossip order, which the attacker (or simply an honest signer under normal operation, e.g. after a stale rejection is fixed and it re-signs) can influence by nothing more than the natural timing of its own two responses.

### Recommendation
Gate both branches on the same shared state. Either:
- Use `responded_signers` consistently as the single source of truth for "already counted" in both branches (check-and-set there before adding weight in either direction), or
- When a signer's response changes from Rejected to Accepted (or vice versa) for the same block, explicitly subtract the previously-counted weight from the stale bucket before adding it to the new one, keeping `total_weight_approved + total_weight_rejected` bounded per-signer to a single vote's weight at any time.

### Proof of Concept
1. A miner proposes block `B`; the node's `StackerDBListener` creates a fresh `BlockStatus` for `B`.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `B` (e.g., legitimate rejection while `check_block_against_signer_db_state` briefly failed). `responded_signers.insert(slot_S)` → `true`; `total_weight_rejected += w` (stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-518).
3. `S`'s local signer later re-evaluates `B` (its own state machine allows `LocallyRejected -> LocallyAccepted`) and broadcasts `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. The node's `Accepted` handler checks only `gathered_signatures.contains_key(&slot_S)`, which is still `false` — it adds `total_weight_approved += w` (stackerdb_listener.rs:443-446) and inserts into `gathered_signatures`/`responded_signers` (which is now a no-op re-insert since it was already `true`).
5. Result: `S`'s weight `w` is now counted in both `total_weight_rejected` and `total_weight_approved` for block `B` simultaneously; `total_weight_rejected` is never decremented despite `S` having withdrawn its rejection.
