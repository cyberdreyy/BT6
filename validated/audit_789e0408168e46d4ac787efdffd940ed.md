Based on my investigation, I found a genuine analog to the reported bug class within the compute-budget/transaction-configuration path, which is directly reachable by any submitted transaction (V1 message format).

### Title
Loaded-accounts-data-size limit is unvalidated for V1-message transactions, unlike Legacy/V0 - (File: runtime-transaction/src/transaction_meta.rs)

### Summary
`VersionedTransactionConfiguration` builds a transaction's compute-budget configuration from two paths: `LegacyAndV0`, driven by `ComputeBudgetInstructionDetails`, and `V1`, driven directly by a `TransactionConfig` field on new-format messages. The `LegacyAndV0::try_into_config` path enforces `loaded_accounts_data_size_limit != 0` via `NonZeroU32::new(...).ok_or(TransactionError::InvalidLoadedAccountsDataSizeLimit)?`, but the `V1::try_into_config` path only clamps the same field with `.min(MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES.get())` and never rejects zero.

### Finding Description
`ComputeBudgetInstructionDetails::sanitize_and_convert_to_compute_budget_limits` (the "setter"-equivalent used by legacy/v0 transactions) explicitly forbids a `requested_loaded_accounts_data_size_limit` of `0`: [1](#0-0) 

For V1-format messages, `VersionedTransactionConfiguration::from_v1_config` reads the same conceptual field straight from the message's `TransactionConfig`, defaulting to `0` when absent: [2](#0-1) 

And `try_into_config` for the `V1` variant only bounds-checks `updated_heap_bytes` (rejecting with `SanitizeFailure` if invalid/misaligned), but for `compute_unit_limit` and `loaded_accounts_data_size_limit` it merely clamps to the maximum via `.min(...)`, with no lower-bound / non-zero check analogous to the legacy path: [3](#0-2) 

This mirrors exactly the reported bug class: the "setter" path (`ComputeBudgetInstructionDetails::sanitize_and_convert_to_compute_budget_limits`) validates the parameter is non-zero, but the alternate "construction" path (V1 `TransactionConfig` → `TransactionConfiguration`) allows the same field to be `0` unchecked.

### Impact Explanation
`loaded_accounts_data_size_limit` of `0` is used downstream to bound the total loaded-account data size during transaction account loading in `svm/src/account_loader.rs` and `svm/src/transaction_processor.rs`. I was not able to fully trace, within the remaining tool budget, the exact enforcement code that consumes `loaded_accounts_bytes` in `account_loader.rs`/`transaction_processor.rs` to confirm whether a `0` limit is silently treated as "no accounts allowed" (causing spurious transaction failure — a correctness/liveness issue but not fund-unsafe) or is treated as "unbounded"/skipped (which would remove the resource-exhaustion guardrail this field is meant to enforce, a potential vector for oversized account loading). This distinction changes whether the impact is a validator resource/DoS concern (if the check is silently bypassed) or merely a self-inflicted transaction failure (if 0 causes strict rejection later). This is a genuine inconsistency in validation between the two code paths.

### Likelihood Explanation
The V1 message format's `TransactionConfig.loaded_accounts_data_size_limit` field is an `Option<u32>` fully controlled by the transaction's own signed message content, so any unprivileged transaction sender using the V1 message format can set (or omit, defaulting to `0`) this value without any enforcement rejecting the zero case, unlike the legacy/v0 path which would reject it outright with `TransactionError::InvalidLoadedAccountsDataSizeLimit`.

### Recommendation
Add the same non-zero validation to the `V1` branch of `VersionedTransactionConfiguration::try_into_config` that is applied in the `LegacyAndV0` branch — i.e., reject (or default) a `loaded_accounts_data_size_limit` of `0` the same way `NonZeroU32::new(...).ok_or(TransactionError::InvalidLoadedAccountsDataSizeLimit)` does for legacy/v0 transactions, keeping both code paths consistent.

### Proof of Concept
1. Construct a V1-format `SanitizedMessage` whose `TransactionConfig.loaded_accounts_data_size_limit` is `Some(0)` (or omitted, which defaults to `0` via `.unwrap_or(0)` in `from_v1_config`).
2. Submit the transaction; `TransactionConfiguration::try_from_sanitized_message` → `VersionedTransactionConfiguration::try_into_config` takes the `V1` branch.
3. Observe that unlike the legacy/v0 path (which would return `Err(TransactionError::InvalidLoadedAccountsDataSizeLimit)`), the V1 path succeeds and returns `TransactionConfiguration { loaded_accounts_data_size_limit: 0, .. }` uncontested.

Note: I could not fully verify within the tool budget how a `0` value for `loaded_accounts_bytes`/`loaded_accounts_data_size_limit` is consumed further downstream in `svm/src/account_loader.rs` and `svm/src/transaction_processor.rs` (whether it causes strict rejection of any account-loading or is treated as unbounded). Confirming that behavior would require deeper tracing than was possible here, and materially affects whether this is a DoS/resource-limit-bypass concern versus a benign self-inflicted-failure inconsistency.
