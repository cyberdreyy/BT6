### Title
Stale instant-withdraw receipts are counted as prefunded default reserve, inflating `defaultRecoveryPrice` and making recovery insolvent - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears the aggregate receipt (`instantWithdrawsRequests[_user] = 0`) after paying the user, but never clears the per-epoch lifecycle records `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. These "freed" receipt objects are later dereferenced by `finalizeDefaultRecovery` / `_defaultPrefundedInstantReserve` / `defaultPendingClaimBasis`, which treat already-paid-out instant claims as both outstanding claim basis and as underlying already held in the strategy. This is the direct analog of CVE-2018-17481 (object used after its lifecycle ended): a receipt whose payout already happened is reused by the default-finalization accounting.

### Finding Description
In `requestInstantWithdraw`, the vault records three lifecycle markers: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the global `instantWithdrawClaimsByEpoch[currentEpoch]`, plus `pendingInstantWithdraws` [1](#0-0) .

When the borrower/strategy funds the queue, `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` and pulls underlying into the strategy [2](#0-1) . The user then claims, which burns the receipt and zeroes only the aggregate counter — the per-epoch records keep their nonzero values forever [3](#0-2) .

If the borrower later defaults in that **same** epoch while `pendingInstantWithdraws` is still nonzero (i.e., some other instant requests were only partially funded), `finalizeDefaultRecovery` reads the stale aggregates:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still includes the fully claimed-and-paid amount [4](#0-3) .
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` and counts it as underlying already held by the strategy — but that underlying was already transferred out to the claiming user [5](#0-4) .
- `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` is inflated by ghost funds, so `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is set too high [6](#0-5) .

Additionally, `_claimDefaultedInstantWithdrawRequest` does `instantWithdrawsRequests[_user] -= claimBasis`; for the already-claimed user the aggregate is 0 while the stale per-epoch entry is positive, which reverts on underflow if they ever interact again [7](#0-6) .

No existing guard stops this: `defaultRecoveryInitialized`/`_ensureDefaultRecoveryInitialized` only gate the feature, `defaultInstantWithdrawsFinalized` merely enables the defaulted-instant path [8](#0-7) , and nothing validates that `instantWithdrawClaimsByEpoch` reflects still-unclaimed receipts.

### Impact Explanation
The ghost prefunded reserve inflates `defaultRecoveryPrice` above the ratio real held funds can support. Every defaulted-epoch receipt (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) and the active-LP NAV crystallization (`_mint`/`_burn` at finalization, `defaultBBNav` returned to the CDO) is computed against this inflated price [9](#0-8) . Early claimants — including a tranche-token holder who timed an instant withdraw earlier in the default epoch — are overpaid from the strategy's actual underlying balance, while later claimants and active LPs face insolvency (claims revert or are de facto haircut beyond the intended loss). Loss is bounded by the stale claimed amount but directly transfers real funds; it is theft-by-overpayment plus permanent under-collateralization of remaining claims.

### Likelihood Explanation
Requires a specific but plausible sequence within one epoch: (1) a user makes an instant withdraw request, (2) the CDO partially funds the instant queue (`collectInstantWithdrawFunds`) so the user can claim while `pendingInstantWithdraws` remains nonzero from other requests, (3) the borrower defaults in the same epoch and `finalizeDefaultRecovery` runs. All steps use honest privileged actors (manager/CDO) and unprivileged timing by the attacker; no malicious roles needed. The window is the partial-funding state inside a default epoch, which is exactly the stressed scenario this accounting exists for.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch lifecycle records at claim time: track the epoch(s) of the user's instant requests (e.g., a `lastInstantWithdrawEpoch` marker or iterate `instantWithdrawsRequestsByEpoch`) and decrement both `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount when burning the aggregate receipt. Alternatively, split `instantWithdrawClaimsByEpoch` into "requested" vs "outstanding/unclaimed" buckets and use only the unclaimed bucket in `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, so prefunded reserve equals underlying actually still held.

### Proof of Concept
Foundry fork sketch against the repo's own harness (`test/foundry/IdleCreditVault.t.sol` style):

```solidity
// Epoch N running, instant withdraws enabled.
// 1. Attacker (unprivileged LP) requests instant withdraw of X.
cdoEpoch.requestInstantWithdraw(X, address(AAtranche)); // or instant path used by variant

// 2. Manager/CDO partially funds the instant queue: collects only attacker's X,
//    victim's request of Y remains pending -> pendingInstantWithdraws == Y > 0.
//    (via getInstantWithdrawFunds/collectInstantWithdrawFunds flow)
// 3. Attacker claims -> instantWithdrawsRequests[attacker] = 0, paid X,
//    but instantWithdrawClaimsByEpoch[N] still == X + Y (stale).
cdoEpoch.claimInstantWithdrawRequest();

// 4. Borrower defaults inside epoch N; owner/manager finalize recovery with R.
strategy.finalizeDefaultRecovery(R, recoverySource);

// Observed:
//  - _defaultPrefundedInstantReserve() returns (X + Y) - Y = X, counting X
//    that was already paid out and is no longer held by the strategy.
//  - defaultRecoveryPrice = (R + X_ghost + reserve) / totalBasis, inflated by X.
//  - Attacker's defaulted-epoch receipts and active LP NAV are crystallized at
//    the inflated price; final claims revert from insufficient underlying, or
//    early claimants extract more than the pro-rata recovery (insolvency).
// assert underlying.balanceOf(strategy) < totalBasis * defaultRecoveryPrice / RECOVERY_FULL
```

The core assertion is that after step 3, `strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber())` still includes the fully claimed amount while `strategy.underlying balance` no longer contains it — a freed receipt reused by finalization accounting.
