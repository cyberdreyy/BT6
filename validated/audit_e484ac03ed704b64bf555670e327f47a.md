### Title
Builder withdrawal amount committed to the payload is not capped to available balance, while the CL-side balance deduction is capped — ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` builds each `Withdrawal.amount` from the *requested* `builder_pending_withdrawals[].amount` without capping it to the builder's actual balance, while `apply_withdrawals` (the function that mutates state) caps the deduction with `min(withdrawal.amount, builder_balance)`. Since the uncapped `withdrawal.amount` is exactly what is committed into `state.payload_expected_withdrawals` (and thus into the execution payload's `withdrawals` list that the execution layer unconditionally credits to `address`), any case where a builder's balance is insufficient at settlement time produces a payload that commits to paying more Gwei than is actually deducted from the builder in the consensus state — net Gwei creation.

### Finding Description
`get_builder_withdrawals` in `specs/gloas/beacon-chain.md` (~L1802-1834) constructs the `Withdrawal` objects straight from the queued `amount`: [1](#0-0) 
```
for withdrawal in state.builder_pending_withdrawals:
    ...
    withdrawals.append(
        Withdrawal(
            index=withdrawal_index,
            validator_index=convert_builder_index_to_validator_index(builder_index),
            address=withdrawal.fee_recipient,
            amount=withdrawal.amount,
        )
    )
```
There is no comparison against `state.builders[builder_index].balance` here — unlike the analogous validator-sweep and builder-sweep helpers, which cap amounts (`amount=balance - MAX_EFFECTIVE_BALANCE`, `amount=builder.balance`, etc.).

The *mutation* function `apply_withdrawals`, however, does cap: [2](#0-1) 
```
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
```

This is structurally the same bug class as the ERC4626 report: one code path (`get_builder_withdrawals`, analogous to `previewMint`/the value that gets *committed*) computes a different number than the code path that actually *executes* the effect (`apply_withdrawals`, analogous to `deposit`). The committed `Withdrawal.amount` (uncapped) is exactly what ends up in `state.payload_expected_withdrawals` via `get_expected_withdrawals`/`update_payload_expected_withdrawals`, and it is this value the execution layer is required to honor as the block's committed withdrawals list, unconditionally crediting `address` with `amount`. Meanwhile the consensus-layer bookkeeping (`state.builders[...].balance`) is only debited by the capped `min(amount, balance)`.

The project's own test suite explicitly documents and asserts this exact divergence as expected behavior: [3](#0-2) 
```
def test_builder_withdrawal_insufficient_balance(spec, state):
    ...
    Output State Verified:
        - withdrawal.amount: 5 ETH (requested amount)
        - builders[0].balance: 0 (deduction capped to available balance)
```
i.e., the committed `Withdrawal.amount` field in the payload is 5 ETH while the builder's balance is only reduced by 1 ETH (all it had).

### Impact Explanation
This directly breaks the "Gwei created ... paid to a non-owner" invariant: the fee recipient receives (on the execution layer, which mints/credits withdrawals unconditionally per the committed list) the full requested `amount`, while the consensus layer only ever debited `min(amount, balance)` from the builder. The difference is Gwei manufactured out of thin air and paid to whatever `fee_recipient` was specified in the (attacker/builder-controlled) `BuilderPendingWithdrawal`. This is a Critical-severity class of bug per the stated rubric ("Gwei created ... or paid to a non-owner", "a payload or payment applied that the block did not commit to" — here inverted: the block *commits* to paying more than it removes).

### Likelihood Explanation
Reachability depends on whether a builder's balance can legitimately become insufficient between the time a `BuilderPendingWithdrawal` is queued (with `amount = parent_bid.value`, validated at bid-acceptance time via balance checks) and the time it is dequeued/settled by `get_builder_withdrawals`/`apply_withdrawals`. Given the queue (`state.builder_pending_withdrawals`, size up to 2^20) and multi-slot/epoch delay before an entry reaches the front of the sweep, and other balance-reducing events for the same builder in between (additional builder-exit withdrawals, multiple bids being settled in the same epoch window, etc.), an insufficient-balance scenario is plausible without requiring a colluding node, client bug, or majority stake — this is exactly what the repo's own test (`test_builder_withdrawal_insufficient_balance`) constructs. I could not fully verify from the available spec text whether upstream invariants (e.g., a guarantee that a builder can never end up with multiple concurrently-pending withdrawals whose sum exceeds balance) prevent this in practice, since I was unable to inspect `settle_builder_payment` and `is_builder_payment_available` in full during this session — this should be verified before treating the finding as fully proven.

### Recommendation
`get_builder_withdrawals` should cap `amount` to `min(withdrawal.amount, state.builders[builder_index].balance)` (accounting for withdrawals already accumulated earlier in the same call via `prior_withdrawals`, similar to how `get_validators_sweep_withdrawals` computes `get_balance_after_withdrawals`), so that the value written into `state.payload_expected_withdrawals` (and thus the execution-layer-committed withdrawal) always matches exactly what `apply_withdrawals` actually deducts from the builder's balance.

### Proof of Concept
Conceptual sequence (matching the repo's own test `test_builder_withdrawal_insufficient_balance`):
1. Builder `B` has `balance = 1 ETH`.
2. A `BuilderPendingWithdrawal` for `B` with `fee_recipient = attacker_address`, `amount = 5 ETH` is queued (e.g., because balance was sufficient at bid-acceptance time but was reduced afterward by other events before settlement).
3. When `process_withdrawals` runs: `get_builder_withdrawals` emits `Withdrawal(address=attacker_address, amount=5 ETH)` into `state.payload_expected_withdrawals`.
4. `apply_withdrawals` executes `state.builders[B].balance -= min(5 ETH, 1 ETH) = 1 ETH`, leaving `balance = 0`.
5. The execution payload's withdrawals list (built from `state.payload_expected_withdrawals`) contains a 5 ETH withdrawal to `attacker_address`, which the execution layer credits in full — 4 ETH is created from nothing and paid to `attacker_address`, while only 1 ETH was ever removed from any account in the consensus state.
