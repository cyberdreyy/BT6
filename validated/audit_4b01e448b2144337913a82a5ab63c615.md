### Title
Inconsistent single-key `ConfigKeys` account parsing between `parse_config` (RPC jsonParsed) and `parse_validator_info` (CLI) - ([File: account-decoder/src/parse_config.rs])

### Summary
`parse_config` in `account-decoder/src/parse_config.rs` only checks that `key_list.keys` is non-empty and that `keys[0].0 == validator_info::id()` before decoding and returning a `ConfigAccountType::ValidatorInfo`, without requiring a second (actual validator identity) key. `cli/src/validator_info.rs::parse_validator_info` instead requires `key_list.keys.len() > 1` and reads `key_list.keys[1]` as the validator pubkey, rejecting single-key accounts outright. For identical on-chain bytes with exactly one key equal to `validator_info::id()`, the RPC `jsonParsed` path reports a valid `ValidatorInfo` record while the CLI reports "no validator info," a direct decoder-semantics discrepancy across integrator surfaces.

### Finding Description
`parse_config` performs its validity check as: [1](#0-0) 
This only requires `keys` non-empty and `keys[0].0 == validator_info::id()`; it never checks `keys.len() > 1`. `parse_config_data` is then called with the full `keys` vector (length 1 in the attack case) and simply maps whatever keys exist into `UiConfigKey`s: [2](#0-1) 
So a `ConfigKeys{ keys: [(validator_info::id(), false)] }` plus a valid bincode-encoded `String` JSON payload after the header will be decoded successfully by `parse_config`, producing `UiConfig{ keys: [ { pubkey: validator_info::id(), signer: false } ], config_data: <parsed JSON> }`.

In contrast, `cli/src/validator_info.rs::parse_validator_info` requires a second key to exist and reads it as the validator pubkey: [3](#0-2) 
With only one key present, `key_list.keys.len() > 1` is `false`, so the function returns `None`, treating the identical bytes as "not a validator info account."

Both code paths are reachable by an unprivileged actor: the RPC path is reached via `getAccountInfo`/`getProgramAccounts` with `jsonParsed` encoding dispatching to `parse_config` based on the account owner (`solana_config_interface::id()`), and the CLI path is reached via `solana validator-info get`, which also filters by the same owner check (`account.owner != solana_config_interface::id()`) before calling `parse_validator_info`. Because the two implementations encode different (and undocumented) assumptions about what a minimally valid `ConfigKeys` layout for a `ValidatorInfo` account looks like, they diverge on the same bytes.

### Impact Explanation
This is a decoder misreporting issue: for the exact same on-chain account data, the RPC `jsonParsed` decoder (`parse_config`) reports the account as a valid `ValidatorInfo` record (with a single, non-identity key list), while the CLI decoder (`parse_validator_info`) reports it as absent/invalid. Any downstream tooling, dashboards, or automation that trusts the RPC-parsed `ValidatorInfo` output would surface a spoofed or malformed "validator info" entry that the reference CLI implementation does not recognize as such, creating a real, attacker-controllable inconsistency in reported account semantics for a single on-chain account. This falls under the "decoder ... misreporting" impact category permitted by the audit scope.

### Likelihood Explanation
The precondition is trivial for anyone able to get bytes matching `ConfigKeys{ keys: [(validator_info::id(), false)] }` followed by a bincode-serialized JSON `String` written into an account owned by `solana_config_interface::id()`, then queried via `getAccountInfo(jsonParsed)` (single low-rate RPC call) versus `solana validator-info get` on the same pubkey. No validator/leader/staked-node privileges are needed; the check purely operates on account bytes already returned by permitted read APIs. The discrepancy is deterministic and 100% reproducible given the same bytes.

### Recommendation
Align the validity condition in `parse_config` with `parse_validator_info` (or vice versa, whichever is the intended canonical semantics) by requiring `key_list.keys.len() > 1` in `account-decoder/src/parse_config.rs` before treating the account as a `ValidatorInfo` record, so both code paths agree on what constitutes a valid single-identity-key `ValidatorInfo` config account.

    assert!(key_list.keys.len() <= 1);
    // => parse_validator_info would return None here, disagreeing with account-decoder.

    T: serde::de::DeserializeOwned,

    let config_data: T = deserialize(get_config_data(data).ok()?).ok()?;

fn parse_validator_info(
    account: &Account,
) -> Option<(Pubkey, bool, Map<String, serde_json::value::Value>)> {
    if account.owner != solana_config_interface::id() {
        return None;
    }
    let key_list: ConfigKeys = deserialize(&account.data).ok()?;
    if key_list.keys.len() > 1 {
        let (validator_pubkey, is_signed) = key_list.keys[1];
        let validator_info_string: String =
            get_config_data(&account.data).and_then(deserialize).ok()?;
        let validator_info: Map<_, _> = serde_json::from_str(&validator_info_string).ok()?;
        Some((validator_pubkey, is_signed, validator_info))
    } else {
        None
    }
}
