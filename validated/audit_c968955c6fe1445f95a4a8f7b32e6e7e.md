### Title
Deposit front-running lets a pubkey-holder capture a subsequent large deposit under attacker-controlled withdrawal credentials - (File: specs/phase0/beacon-chain.md, specs/electra/beacon-chain.md)

### Summary
The beacon chain's deposit-application logic (`apply_deposit` in phase0 and `apply_pending_deposit` in Electra-and-later) binds withdrawal credentials to a pubkey only on the *first* deposit seen for that pubkey. Any subsequent deposit for the same pubkey is treated as a balance top-up regardless of its own `withdrawal_credentials` field. This lets whoever gets their deposit processed first for a given pubkey permanently fix the withdrawal credentials for all later deposits to that pubkey — the exact "front-running the recipient binding" pattern described in the external report, where the first mover on a shared identifier (there: `token`/`position`, here: `pubkey`/`validator`) locks in state that a later, legitimate, larger transaction cannot override.

### Finding Description
`apply_deposit` (phase0) and its Electra successor `apply_pending_deposit` both branch on whether the pubkey is already present in `state.validators`: [1](#0-0) 

If the pubkey is new, the validator is registered with whatever `withdrawal_credentials` accompany *that* deposit (after signature verification). If the pubkey already exists, the deposit is applied purely as `increase_balance`, and the existing validator's `withdrawal_credentials` are never checked or updated: [2](#0-1) 

The Electra-and-later test suite even documents this as intended top-up behavior — "inconsistent withdrawal credentials, in top-ups, are allowed!": [3](#0-2) 

This is the beacon-chain analog of the `LockedStakingPools.participate` bug: the shared mutable resource (`validator.withdrawal_credentials`, keyed by `pubkey`) is set by whichever deposit for that pubkey lands first, and every later deposit for the same pubkey silently inherits that binding instead of being rejected or re-validated. In delegated/pooled staking setups — where a pubkey is generated for a specific depositor's stake but the depositor's real, large deposit transaction is broadcast (and thus publicly visible pre-inclusion) before it is included — anyone who can get a minimal deposit for that same pubkey processed first (e.g., the node operator who generated the key, or anyone who otherwise obtains a validly signed deposit message for that pubkey with attacker withdrawal credentials) captures control of all future funds sent to that pubkey.

The project's own EIP-8205 proposal confirms this is a real, previously-unaddressed class of issue in the shipped forks (phase0 through Gloas/Fulu), explicitly built to close it: [4](#0-3) 

### Impact Explanation
This breaks the "Gwei paid to non-owner" invariant: a large deposit intended to fund a validator under one party's withdrawal credentials instead accrues balance to a validator whose withdrawal credentials belong to a different, unauthorized party, who can eventually withdraw or otherwise control those funds. This matches the High/Critical impact category of "Gwei created, destroyed, or paid to a non-owner" and "a validator... re-credentialed without its authority" (here, credentialed adversely from inception rather than changed later).

### Likelihood Explanation
Exploitation requires the attacker to get a deposit for the *same pubkey* processed before the victim's, with a valid deposit signature over their own chosen `withdrawal_credentials`. This is only practically reachable when the pubkey's signing key is available to more than the intended fund owner — e.g., delegated/pooled staking services that generate the validator key themselves and later fund it. This is precisely the deployment scenario EIP-8205's introduction calls out ("protecting delegated staking deployments against deposit front-running"), indicating it is a recognized, realistic operational risk rather than a purely theoretical one, though it does not affect the common case where the depositor alone controls the pubkey's private key end-to-end.

### Recommendation
Adopt (or backport) the EIP-8205 preregistration mechanism — binding a pubkey to withdrawal credentials via an authenticated preregistration before/at first deposit and rejecting/discarding deposits whose credentials don't match an active binding — for all forks that support delegated key-generation staking flows, i.e., ensure `process_deposit_request`/`process_deposit` cannot silently top up a validator whose withdrawal credentials were set by an unrelated, earlier deposit for the same pubkey without an authenticated binding check.

### Proof of Concept
1. A staking pool operator generates validator pubkey `P` on behalf of user `U` and asks `U` to send a deposit transaction (large amount, `withdrawal_credentials = WC_U`, valid deposit signature for `(P, WC_U, amount)`).
2. Before `U`'s deposit is included, the operator (or anyone who can produce a validly signed deposit message for `P`, e.g. because `P`'s key was generated off-chain and its private key is available to more than `U`) submits their own deposit for `P` with `withdrawal_credentials = WC_attacker` and a minimal amount.
3. `apply_deposit`/`apply_pending_deposit` sees `P not in validator_pubkeys`, verifies the attacker's signature, and calls `add_validator_to_registry(state, P, WC_attacker, amount)` — see [5](#0-4) .
4. `U`'s subsequent large deposit for `P` is now processed via the `else` branch (`increase_balance`) since `P` is already a validator pubkey — `WC_attacker` is never checked or replaced, so `U`'s stake balance sits under `WC_attacker`.

def apply_deposit(
    state: BeaconState,
    pubkey: BLSPubkey,
    withdrawal_credentials: Bytes32,
    amount: Gwei,
    signature: BLSSignature,
) -> None:
    validator_pubkeys = [v.pubkey for v in state.validators]
    if pubkey not in validator_pubkeys:
        # Verify the deposit signature (proof of possession) which is not checked by the deposit contract
        deposit_message = DepositMessage(
            pubkey=pubkey,
            withdrawal_credentials=withdrawal_credentials,
            amount=amount,
        )
        # Fork-agnostic domain since deposits are valid across forks
        domain = compute_domain(DOMAIN_DEPOSIT)
        signing_root = compute_signing_root(deposit_message, domain)
        if bls.Verify(pubkey, signing_root, signature):
            add_validator_to_registry(state, pubkey, withdrawal_credentials, amount)
    else:
        # Increase balance by deposit amount
        index = ValidatorIndex(validator_pubkeys.index(pubkey))
        increase_balance(state, index, amount)

def apply_pending_deposit(state: BeaconState, deposit: PendingDeposit) -> None:
    """
    Applies ``deposit`` to the ``state``.
    """
    validator_pubkeys = [v.pubkey for v in state.validators]
    if deposit.pubkey not in validator_pubkeys:
        # Verify the deposit signature (proof of possession) which is not checked by the deposit contract
        if is_valid_deposit_signature(
            deposit.pubkey, deposit.withdrawal_credentials, deposit.amount, deposit.signature
        ):
            add_validator_to_registry(
                state, deposit.pubkey, deposit.withdrawal_credentials, deposit.amount
            )
    else:
        validator_index = ValidatorIndex(validator_pubkeys.index(deposit.pubkey))
        increase_balance(state, validator_index, deposit.amount)

## Introduction

This upgrade adds withdrawal credentials preregistration to the beacon chain as
part of the EIP-8205 upgrade. A preregistration binds a validator pubkey to
withdrawal credentials before the validator's first deposit is processed,
protecting delegated staking deployments against deposit front-running.

This document specifies the beacon chain changes required to support these
preregistrations. The upgrade introduces a new request type within the execution
payload, triggered by execution layer transactions, which stores a
pubkey-to-withdrawal-credentials binding in the beacon state. While a binding is
active, a deposit request for the bound pubkey is discarded unless its
withdrawal credentials match the binding and its signature is valid.
