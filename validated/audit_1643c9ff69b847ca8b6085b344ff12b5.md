### Title
Duplicate-request-ID griefing in Vault gateway handler allows an attacker to deny another user's Vault request - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
The Vault gateway handler tracks in-flight JSON-RPC requests keyed only by the caller-supplied `req.ID`, and rejects a new request whenever that ID is already present, mirroring the `LinearVesting.vestFor` "already a vester" guard from the referenced report. Because the internet-facing gateway is the entry point for unprivileged/external clients, an attacker who can predict or observe a victim's request ID before it is submitted can pre-register that ID and force the legitimate request to be denied.

### Finding Description
`newActiveRequest` in the Vault handler enforces a single-slot map keyed by `req.ID`: [1](#0-0) 
If an entry for that ID already exists, the function immediately returns `"request ID already exists"` and the caller's request is rejected — this is functionally identical to the `require(vest[user].amount == 0, ...)` guard described in the report: a pre-existing state entry blocks the legitimate write. The confirming test explicitly demonstrates this "denial by duplicate ID" behavior: [2](#0-1) 

The same "already exists"/replay-guard pattern recurs in other gateway handlers reachable from unprivileged user messages, showing this is a systemic pattern rather than an isolated instance: [3](#0-2) [4](#0-3) 

The severity depends entirely on whether the request ID namespace is properly scoped per-caller/session (which would make this a mere self-inflicted collision) or is a flat, globally-shared namespace across all callers of the gateway (which would allow cross-user griefing). I was not able to confirm the exact ID derivation/scoping logic before the request reaches `newActiveRequest` — the `HandleJSONRPCUserMessage` entry point and how `req.ID` is validated/namespaced per caller could not be retrieved due to a tool error on the final iteration, so this cannot be fully verified as cross-user-reachable.

### Impact Explanation
If the request ID namespace is shared across different callers (not strictly bound to the authenticated caller's own identity/session), any client of the gateway could grief another client's Vault operation (e.g., `ListSecretIdentifiers`, `CreateSecrets`) by submitting a request with the same ID first, causing the victim's legitimate request to fail with "request was already authorized previously" / "request ID already exists". This is a denial-of-service against a specific unprivileged client's request, analogous to vest-denial griefing in the source report. If the ID space is instead namespaced per-owner (as suggested by `expectedRequestID := owner + vaulttypes.RequestIDSeparator + requestID` in the test), the exploitability would be limited to self-collisions, significantly reducing impact.

### Likelihood Explanation
Exploitability hinges on: (1) whether an attacker can predict/observe a legitimate request's ID before submission (e.g., via correlated timing, application UX where IDs are UUIDs vs. deterministic/sequential values, or side channels), and (2) whether the map key genuinely spans multiple owners. Given the uncertainty in verifying the exact key-scoping logic, likelihood cannot be conclusively assessed and requires further code review to confirm cross-caller reachability.

### Recommendation
- Confirm and, if necessary, enforce that active-request keys are always namespaced by authenticated caller/owner (not just the raw client-supplied `req.ID`) before the `activeRequests` map lookup in `newActiveRequest`, so a collision can only occur within a single caller's own request stream.
- Consider a locking/registration primitive that binds the ID check atomically to caller identity, and expire stale entries promptly to bound the griefing window.
- Apply the same review to the other "already exists" duplicate-ID guards found in `confidentialrelay/handler.go` and `capabilities/v2/http_trigger_handler.go`, since they follow the identical pattern.

### Proof of Concept
Conceptual PoC based on the existing test coverage (not independently re-verified beyond what is cited):
1. A malicious client sends a Vault JSON-RPC request (`vaulttypes.MethodSecretsList`) with request ID `X` before the victim's legitimate request with the same ID `X` arrives at the gateway.
2. `newActiveRequest` finds `h.activeRequests[X] != nil` and returns `"request ID already exists"` for the victim's subsequent legitimate call, as shown in the duplicate-request test: [5](#0-4) 
3. The victim's intended Vault operation never completes ("denied"), matching the described vest-denial griefing pattern — though the demonstrated test uses the *same* caller replaying its own ID; whether the same effect is reachable across different, mutually-untrusted callers requires confirming the ID-scoping/ownership logic, which could not be fully verified in this session.

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
