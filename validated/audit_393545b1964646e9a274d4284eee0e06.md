### Title
Approved deposit-receiver can indefinitely re-lock a victim's entire unit balance via repeated minimal deposits - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.deposit`/`mint` accept a `receiver` parameter guarded only by `_requireValidReceiver`, which checks that the caller is either the receiver or has been granted a one-time-purpose `depositReceiverApproval` [1](#0-0) . Once granted, that approval is a persistent boolean with no scope or expiry [2](#0-1) . Every sync deposit unconditionally resets `userUnitsRefundableUntil[receiver]` to `block.timestamp + depositRefundTimeout`, and this lock applies to the receiver's *entire* unit balance, not merely the newly deposited units [3](#0-2) . This is the same class of bug as CVE-2020-10100: a permission granted for one narrow purpose (single deposit on someone's behalf) is not scoped by the invariant that actually matters (locking should be limited to what the depositor contributed / for a bounded period), letting the grantee reach far beyond the intended boundary and impact the victim's full holdings indefinitely.

### Finding Description
- `setDepositReceiverApproval(depositor, true)` lets a receiver authorize another address to call `deposit`/`mint` on their behalf — intended for a single or occasional deposit [2](#0-1) .
- `deposit(token, tokensIn, minUnitsOut, receiver)` only requires `_requireValidReceiver(receiver)` (caller == receiver OR approved) and `tokensIn > 0`, `minUnitsOut` can be set to 0 by the caller [4](#0-3) .
- `_syncDeposit` sets `userUnitsRefundableUntil[receiver] = block.timestamp + depositRefundTimeout` on **every** call, keyed purely by `receiver` address, independent of the deposited amount [3](#0-2) .
- This lock is enforced globally against the receiver in `redeem`/`withdraw` (`require(userUnitsRefundableUntil[msg.sender] < block.timestamp, ...)`) [5](#0-4) [6](#0-5) , and also blocks ERC20 `transfer`/`transferFrom` of vault units from that address in `MultiDepositorVault._update` [7](#0-6) .
- Because the approval is a persistent, unscoped flag with no amount/frequency limit, an approved depositor can call `deposit(token, 1, 0, victim)` repeatedly (cheap, minimal token cost) to perpetually push the victim's `userUnitsRefundableUntil` forward, permanently preventing the victim from redeeming, withdrawing, or transferring their entire vault position — regardless of how large that position is or how small the griefing deposit is.
- The failed guard is the absence of any bound (amount proportionality, cooldown, single-use expiry, or opt-out granularity) tying the lock side effect to the scope of the granted permission.

### Impact Explanation
This freezes a victim's entire vault unit balance (redeem/withdraw/transfer all blocked) for as long as the attacker chooses to keep re-triggering the lock, which is a live Immunefi Medium-severity "temporary freezing of user funds" impact. No privileged role, oracle manipulation, or protocol collusion is needed — only a single legitimate approval by the victim (a normal use of the `setDepositReceiverApproval` feature) followed by its abuse beyond intended scope.

### Likelihood Explanation
Preconditions: the victim must have called `setDepositReceiverApproval(attacker, true)` at some point (a supported, ordinary feature intended to let a third party deposit on the user's behalf, e.g. a custodian or automation bot). After that, the attack is trivial, cheap, and repeatable indefinitely by the approved address with no special privileges, using only `deposit`/`mint` with minimal `tokensIn`.

### Recommendation
Scope the deposit-lock side effect to the actual depositor-controlled action rather than the receiver's full balance: e.g., track lock timestamps per-deposit-hash (already available via `syncDepositHashes`) instead of a single `userUnitsRefundableUntil[user]` slot, or require that only self-deposits (`receiver == msg.sender`) refresh the lock, treating delegated deposits-on-behalf as non-lock-extending, or bound the refresh so it cannot indefinitely extend beyond the original `depositRefundTimeout` from the first pending deposit.

### Proof of Concept
1. Fork mainnet where `ProvisionerV2`/`MultiDepositorVault` are deployed; give `victim` an existing large vault unit balance.
2. `vm.prank(victim); provisioner.setDepositReceiverApproval(attacker, true);` (simulating a one-time delegated deposit authorization).
3. `vm.prank(attacker); token.approve(provisioner, type(uint256).max);` fund attacker with dust `token`.
4. `vm.prank(attacker); provisioner.deposit(token, 1, 0, victim);` — assert `provisioner.areUserUnitsLocked(victim) == true` and `userUnitsRefundableUntil(victim) == block.timestamp + depositRefundTimeout`.
5. `vm.warp(block.timestamp + depositRefundTimeout - 1);` then repeat step 4 — assert the lock is refreshed again before it can expire.
6. Attempt `vm.prank(victim); provisioner.redeem(token, victimUnits, 0, victim);` and `multiDepositorVault.transfer(other, victimUnits)` — assert both revert with `Aera__UnitsLocked()`, demonstrating indefinite freeze of the victim's full balance despite only a 1-wei deposit by the attacker each cycle.

I was unable to verify the exact numeric value of `MAX_DEPOSIT_REFUND_TIMEOUT` (the tool call to `Constants.sol` did not return content before the session ended), so the PoC should confirm the configured `depositRefundTimeout` on the deployed instance to size the griefing interval precisely.

    function _syncDeposit(IERC20 token, uint256 tokenAmount, uint256 unitAmount, address receiver) internal {
        uint256 refundableUntil = block.timestamp + depositRefundTimeout;
        bytes32 depositHash = _getDepositHash(msg.sender, receiver, token, tokenAmount, unitAmount, refundableUntil);

        // Requirements: deposit hash is not set
        require(!syncDepositHashes[depositHash], Aera__HashCollision());
        // Effects: set hash as used
        syncDepositHashes[depositHash] = true;

        // Effects: set receiver's refundable until timestamp
        userUnitsRefundableUntil[receiver] = refundableUntil;

        // Interactions: enter vault
        IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).enter(msg.sender, token, tokenAmount, unitAmount, receiver);

        // Log deposit event
        emit Deposited(msg.sender, receiver, token, tokenAmount, unitAmount, depositHash);
    }

    /// @notice Reverts if the caller is not the receiver and the receiver has not approved the caller
    /// @param receiver The address to validate
    function _requireValidReceiver(address receiver) internal view {
        // Requirements: caller is receiver or receiver has approved caller
        require(receiver == msg.sender || depositReceiverApprovals[receiver][msg.sender], Aera__ReceiverNotApproved());
    }
