### Title
Stale APR0 withdraw principal permanently reverts `stopEpoch` in any non-zero-APR epoch, freezing pool funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The analog of the gauge-controller bug is a stale scheduled accounting deduction that bricks the protocol's core time-advance function. In the external report, killing a gauge zeroes `points_sum.bias` while leaving `changes_sum` entries, so a later `_get_sum` underflows and bricks the contract. Here, an unprivileged lender can leave `apr0TotalPrincipal` non-zero by making an APR0 withdraw request and never claiming; `prepareStopEpochWithApr0` then hard-reverts in every subsequent epoch where `unscaledApr != 0`, so `stopEpoch` — the only path that settles epoch interest, processes pending withdrawals, and releases borrower funds — cannot execute.

### Finding Description
`_stopEpoch` in `IdleCDOEpochVariant` unconditionally calls `IdleCreditVault.prepareStopEpochWithApr0(_interest)` at the top of the stop flow, before any interest settlement, loss accounting, or borrower pull [1](#0-0) . Inside that function, once `apr0TotalPrincipal != 0`, the code enforces `if (unscaledApr != 0) revert NotAllowed()` [2](#0-1) .

`apr0TotalPrincipal` is populated per-user via the `apr0Users` struct (`principal`, `principalEpoch`, `settledPrincipal`, `settledInterest`) when a withdraw is requested while the epoch APR is 0, and per-epoch rates are tracked in `apr0RateByEpoch` [3](#0-2) . The principal is only cleared when the user later claims/settles the receipt; there is no path in the stop flow that force-settles or discounts stale APR0 principal — it is exactly the "slope that was never removed from `changes_sum`" pattern: an obligation scheduled against future epochs that a user can leave dangling.

Attack sequence:
1. During an epoch running with `unscaledApr == 0` (APR0 mode is a supported mode of this vault), a KYC-passing lender deposits and submits a withdraw request. `apr0TotalPrincipal` and `apr0Users[attacker].principal` become non-zero.
2. The epoch is stopped normally (APR is still 0, so `prepareStopEpochWithApr0` passes and records `apr0RateByEpoch[epoch]`). The attacker simply never calls `claimWithdrawRequest`, keeping `apr0TotalPrincipal > 0`.
3. The honest manager starts a new epoch with `unscaledApr > 0` (a normal, honest configuration change).
4. At `epochEndDate`, `stopEpoch`/`stopEpochWithDuration` is called → `prepareStopEpochWithApr0` hits `unscaledApr != 0` with `apr0TotalPrincipal != 0` → `revert NotAllowed()` [4](#0-3) . Every retry reverts identically, so interest is never settled, pending withdraws are never funded, and the borrower pull via `getFundsFromBorrower` / `collectWithdrawFunds` never runs [5](#0-4) .

This mirrors the original bug's mechanics: a leftover accounting obligation (APR0 principal / gauge slope) whose existence makes the mandatory aggregation function revert once the environment changes (non-zero APR / new votes), permanently blocking the function everything else depends on.

### Impact Explanation
Temporary-to-permanent freezing of all pool funds: while `stopEpoch` reverts, no withdraw requests can be fulfilled, no new epoch accounting settles, and lender principal plus accrued interest stay locked in the vault. Recovery requires either the attacker voluntarily claiming (they won't) or the honest manager setting `unscaledApr` back to 0 to force a stop — a workaround that misprices the epoch and still leaves `apr0TotalPrincipal` dangling for the next non-zero-APR epoch, letting the attacker re-arm the brick indefinitely at zero cost beyond the locked request amount. Quantified loss: the entire pool NAV is frozen for the duration, and the attacker controls when (if ever) it unfreezes.

### Likelihood Explanation
Preconditions are mild: the vault must run at least one APR0 epoch (an intended mode per `isInterestMinted`/APR0 flows and the invariant suite pinning `unscaledApr == 0` [6](#0-5) ), and the attacker only needs to be a KYC-passing lender making one ordinary withdraw request and abstaining from claiming — both unprivileged actions. No honest-role misbehavior is needed; the trigger (starting a normal-APR epoch) is a routine manager action the attacker sequences around. The cost is the time-value of the requested principal, which remains claimable later, so griefing is nearly free.

### Recommendation
Do not revert in `prepareStopEpochWithApr0` on the `unscaledApr != 0` combination. Instead, settle stale APR0 principal at the recorded `apr0RateByEpoch` rate (or at zero interest if the epoch lapsed), decrement `apr0TotalPrincipal`, and move the settled amounts into the user's claimable basis — i.e., remove the "slope" from the aggregate when the epoch context changes, analogous to the report's recommendation to remove `changes_sum` entries when killing a gauge. Alternatively, force-settle APR0 receipts at `stopEpoch` of the APR0 epoch itself so no principal survives into a non-zero-APR epoch.

### Proof of Concept
A Foundry fork test should: deploy `IdleCDOEpochVariant` + `IdleCreditVault`; start an epoch with `unscaledApr == 0`; have an attacker `depositAA` then `requestWithdraw` so `apr0TotalPrincipal > 0`; `stopEpoch` (succeeds); `setApr(nonZero)` and `startEpoch`; warp to `epochEndDate`; call `stopEpoch` → assert `revert NotAllowed()` and assert it keeps reverting on every subsequent epoch while the attacker never claims, with `pendingWithdraws` and lender funds stuck. Note: I could not fully verify within available iterations whether `claimWithdrawRequest` is callable by a third party on the attacker's behalf (which would let anyone clear the brick) — the PoC must confirm `apr0TotalPrincipal` is only reduced by the requester's own claim for the freeze to be attacker-controlled.
