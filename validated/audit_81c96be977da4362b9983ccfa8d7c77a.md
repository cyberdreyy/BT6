### Title
Naive single-byte overlap restart in `masker.Write()` causes complete masking bypass for self-overlapping secrets split across `Write()` boundaries - (File: `common/buildlogger/internal/masker/masker.go`)

### Summary
The overlap-restart branch at `masker.go:121-127` only checks whether the single byte that caused a mismatch equals `m.phrase[0]`, and unconditionally resets `m.matching` to `1` while flushing *all* previously tracked bytes (`m.phrase[:m.matching]`) unmasked. This is not a correct KMP failure-function restart, so when a registered secret phrase has an internal overlap longer than one byte (e.g. `"aaab"`), splitting the input at a chunk boundary that lands inside the repeated run causes the masker to lose track of the match entirely and emit the whole secret unmasked, even though the identical input processed in a single `Write()` call is masked correctly.

### Finding Description
`masker.Write()` (`common/buildlogger/internal/masker/masker.go:55-138`) advances `m.matching` while a phrase prefix keeps matching. On mismatch, if `m.matching > 0`, it flushes the entire tracked prefix `m.phrase[:m.matching]` unmodified to `m.next` (line 116), then only checks `m.phrase[0] == p[n]` to decide whether to keep exactly one byte of match state (line 122). This ignores the general case where the *last k>1* bytes of the already-matched prefix (not just the single incoming byte) could still be a valid restart point for the phrase — the correct behavior a full KMP failure function would provide.

Concretely, for `phrase = "aaab"`, split input `"aaa"` + `"ab"` (total `"aaaab"`, which genuinely contains `"aaab"` at offset 1):
- After `Write("aaa")`, `m.matching = 3` (buffered, nothing flushed yet).
- `Write("ab")`: `phrase[3:]="b"` doesn't match `p[0]='a'` → mismatch. Because `m.matching>0`, the code flushes `phrase[:3]="aaa"` **unmasked** (line 116), even though two of those three bytes ("aa") are still a valid overlapping prefix of the phrase and should remain in flight.
- It then only checks whether the new byte `p[0]='a'` equals `phrase[0]`, sets `m.matching=1`, and continues. On the next byte `'b'`, `phrase[1]='a'` doesn't match, so it flushes the last `'a'` too, and `phrase[0]!='b'` so it resets to 0 and flushes `'b'` unmasked as well.

Net result across the two `Write()` calls: `"aaaab"` is emitted **completely unmasked**. The same combined bytes processed in one `Write()` call correctly produce `"a"+"[MASKED]"`. This proves the masking result is chunk-boundary dependent and can fully fail, not merely leak a prefix.

Existing checks do not catch this: there is no verification that masking is boundary-invariant, and the fuzz harness (`common/buildlogger/internal/build_logger_fuzz.go`) uses random chunking of random input plus fixed phrases (`"secret"`, `"secret_suffix"`, `"ssecret"`, etc.) and long runs of a single repeated byte (`"A"*1024`, `"B"*4096`, `"C"*8192`), which are self-overlapping in a way that this restart branch happens to handle correctly for a single repeated character, but the fuzz corpus does not include multi-character self-overlapping phrases like `"aaab"`/`"aabaa"`, so this class of failure is not exercised.

This masker sits directly in the job log write path (`common/buildlogger/build_logger.go:213-224`, `wrap()` composes `masker.New(w, l.maskPhrases)` into the writer chain used for all job trace output), so any registered mask phrase with this structural property is exposed to this bug whenever the underlying `Write()` calls happen to split at the wrong point (e.g., from executor/process stdout streaming, buffer flushes, or `\r`-driven partial-line flushes as discussed in `common/buildlogger/innerstream/innerstream.go:17-23`, which explicitly acknowledges the masker "resets on any mismatch" and can be broken by injected write boundaries).

### Impact Explanation
A masked secret (an SSH deploy key, a `CI_JOB_TOKEN`-derived helper token, or any other value registered as a mask phrase) that happens to contain an internal repeated-byte overlap longer than one character can be fully or partially emitted **unmasked** into the job log/trace, which is visible to anyone with job-log viewing access — a direct violation of the "secrets must not leak in logs" invariant. The demonstrated PoC shows total masking bypass (worse than the "prefix leak" framed in the question), which is a strictly stronger form of the same vulnerability class rooted in the same code branch.

### Likelihood Explanation
Feasibility depends on two factors: (1) the mask phrase having a multi-byte self-overlap (plausible for many real secrets/tokens by chance, and directly achievable if the attacker influences part of the value, as the question's own precondition grants), and (2) a `Write()` chunk boundary landing inside the overlapping run. Chunk boundaries in the executor/log pipeline are influenced by streamed process output, buffer sizes, and `\r`/line-splitting behavior noted in `innerstream.go`, giving an attacker practical (if not perfectly precise) ability to influence boundaries by controlling surrounding job output length/content. This is reliably reproducible in a deterministic unit test with controlled `Write()` boundaries.

### Recommendation
Replace the naive single-byte restart with a correct partial-match recovery (e.g., a proper KMP failure-function table per phrase, or re-attempt matching the tracked-but-unflushed bytes against the phrase from every possible restart offset before flushing them as unmasked) so that flushing previously-matched bytes as "safe" is only done once it's proven no valid restart position within them exists. At minimum, before flushing `m.phrase[:m.matching]` unmasked, check all suffixes of the already-matched bytes (not just the newest byte) against the phrase prefix.

### Proof of Concept
```go
func TestMasker_SplitOverlapBypassesMask(t *testing.T) {
    buf := new(bytes.Buffer)
    w := masker.New(nopWriteCloser{buf}, [][]byte{[]byte("aaab")})

    _, err := w.Write([]byte("aaa"))
    require.NoError(t, err)
    _, err = w.Write([]byte("ab"))
    require.NoError(t, err)
    require.NoError(t, w.Close())

    // Single-call baseline: "aaaab" -> "a" + "[MASKED]"
    buf2 := new(bytes.Buffer)
    w2 := masker.New(nopWriteCloser{buf2}, [][]byte{[]byte("aaab")})
    _, _ = w2.Write([]byte("aaaab"))
    _ = w2.Close()

    // Bug: split-write leaks the full secret "aaab" unmasked,
    // while single-call write correctly masks it.
    assert.Contains(t, buf2.String(), "[MASKED]")
    assert.NotContains(t, buf.String(), "[MASKED]") // fails to mask when split
    assert.Contains(t, buf.String(), "aaab")         // secret leaked in full
}
```
Expected: the split-write case leaks `"aaab"` fully while the single-call case masks it — proving the chunk-boundary-dependent masking bypass. This can be generalized into a fuzz property (extending `common/buildlogger/internal/build_logger_fuzz.go`) that adds multi-character self-overlapping phrases (e.g. `"aaab"`, `"aabaa"`) to the `phrases` list and asserts, for every random chunking, that the masked phrase never appears in `contents`.
