### Title
Unauthenticated EI-auth error path leaks raw wrapped DB error text distinguishing failure modes - ([File: core/web/auth/auth.go], [File: core/web/auth/helpers.go])

### Summary
`AuthenticateExternalInitiator` only converts `FindExternalInitiator` failures to the generic `auth.ErrorAuthFailed` sentinel when the underlying error is exactly `sql.ErrNoRows`; any other DB error is wrapped with `errors.Wrap(err, "finding external initiator")` and returned as-is [1](#0-0) . `Authenticate()` only retries subsequent methods while `errors.Is(err, auth.ErrorAuthFailed)`, so a non-`ErrorAuthFailed` error breaks the loop immediately and is passed straight to `jsonAPIError` [2](#0-1) . `jsonAPIError` serializes `err.Error()` verbatim into the JSON response body when the error is not a `*models.JSONAPIErrors` [3](#0-2) .

### Finding Description
`FindExternalInitiator` runs `SELECT * FROM external_initiators WHERE access_key = $1` using a bound parameter [4](#0-3) , so classic SQL injection is not possible, but the raw `access_key` header value is used directly and can trigger genuine driver/DB-level errors distinct from "no rows" — e.g. a header value that violates the underlying column type/length constraints, contains invalid byte sequences for the DB encoding, or causes any other non-`sql.ErrNoRows` failure.

For a normal nonexistent-but-well-formed key, `FindExternalInitiator` returns `sql.ErrNoRows`, which `AuthenticateExternalInitiator` converts into the generic `auth.ErrorAuthFailed` ("Authentication failed") [5](#0-4)  — this reaches `jsonAPIError` only if all other auth methods also fail with `ErrorAuthFailed`, producing the standard generic 401 body.

For a key that causes any other DB-level error, the error is wrapped as `"finding external initiator: <raw db error>"` and returned directly (not as `ErrorAuthFailed`) [6](#0-5) . Because this wrapped error fails the `errors.Is(err, auth.ErrorAuthFailed)` check, the `Authenticate` loop breaks immediately and this wrapped error — containing the underlying database error text — is handed to `jsonAPIError`, which serializes `err.Error()` into the JSON response body sent to the unauthenticated caller [7](#0-6) .

This produces two observably different unauthenticated responses depending on whether the submitted AccessKey merely doesn't exist (generic "Authentication failed") versus triggers a DB error other than "no rows" (raw wrapped internal error text, e.g. Postgres driver messages). An attacker with no credentials can use this discrepancy as an oracle to fingerprint backend behavior and internal error strings, and — depending on the DB error classes reachable via header input — potentially narrow down what values of AccessKey behave differently from plain "not found," which is exactly the kind of behavioral oracle Chainlink's information-disclosure impact class targets.

### Impact Explanation
Unauthenticated clients can obtain verbatim internal database error strings via the External Initiator authentication path whenever `FindExternalInitiator` fails with anything other than `sql.ErrNoRows`. This is an information disclosure of internal error/implementation details (and a distinguishable oracle vs. the generic auth-failure response), reachable without any credentials, matching Chainlink's "sensitive information disclosure" bounty class.

### Likelihood Explanation
Precondition: unauthenticated attacker, no valid EI credentials, ability to send arbitrary `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers to any route wrapped with `auth.AuthenticateExternalInitiator` in `core/web/router.go`. The attacker only needs to find one header value that causes a DB-level error other than "no rows" (e.g., a value exceeding the `access_key` column's length/type constraints or invalid encoding) to see the wrapped raw error, versus a well-formed but nonexistent key to see the generic message — both trivially and repeatably reproducible with simple crafted requests.

### Recommendation
In `AuthenticateExternalInitiator` (`core/web/auth/auth.go`), do not propagate the wrapped underlying DB error to the HTTP response for any failure of `FindExternalInitiator`; log the detailed error server-side and return `auth.ErrorAuthFailed` (or another fixed generic sentinel) for all lookup failures, not just `sql.ErrNoRows`. Ensure `jsonAPIError`/`Authenticate` never emits raw `err.Error()` strings originating from datastore errors on the unauthenticated path.

### Proof of Concept
Table-driven Go test in `core/web/auth/auth_test.go` style:
1. Mock `Authenticator.FindExternalInitiator` to return `(nil, sql.ErrNoRows)` for case "not found" and `(nil, errors.New("pq: value too long for type character varying(64)"))` for case "malformed key db error".
2. Invoke `auth.Authenticate(store, auth.AuthenticateExternalInitiator)` as a `gin.HandlerFunc` against a `httptest.ResponseRecorder` for each case with appropriate EI headers.
3. Assert: for "not found" the response body is `{"errors":[{"detail":"Authentication failed"}]}` (status 401); for "malformed key db error" the response body currently contains `{"errors":[{"detail":"finding external initiator: pq: value too long for type character varying(64)"}]}` (status 401) — demonstrating the bodies differ, violating the expected invariant that both should be identical/generic.

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```

```go
func (o *orm) FindExternalInitiator(ctx context.Context, eia *auth.Token) (*ExternalInitiator, error) {
```
