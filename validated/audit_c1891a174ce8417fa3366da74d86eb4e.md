### Title
Withdrawal requests revert when upfront management fees exceed principal plus interest - (`contracts/IdleCDOEpochVariant.sol`)

### Summary
`IdleCDOEpochVariant.requestWithdraw()` calculates an upfront management fee over the full epoch plus any remaining buffer and subtracts it from the requested principal plus projected interest without checking whether the fee exceeds the claimable amount. [1](#0-0)   
Because `epochDuration` has no upper bound and the management fee is charged on principal for the entire receipt-waiting period, a valid configuration can make `totalFees > principal + interest`, causing a Solidity arithmetic underflow. [2](#0-1) [3](#0-2) 

### Finding Description
When a lender calls `requestWithdraw()`, the contract converts the tranche amount to underlying principal, calculates projected epoch interest, then calculates withdrawal fees. [4](#0-3)   
`_totalWithdrawFees()` returns the full management fee whenever that fee is greater than or equal to the projected interest. [2](#0-1)   
The fee duration is `epochDuration` plus the remaining buffer period, while `setEpochParams()` allows an arbitrary nonzero epoch duration. [5](#0-4) [3](#0-2)   
If the configured management fee over that duration exceeds the requested principal plus interest, line 776 underflows and the request reverts before a receipt is minted or tranche tokens are burned. [6](#0-5) 

For example, with a 50% annual management fee and an 800-day epoch, the upfront fee is approximately `principal * 50% * 800 / 365`, or about 109.6% of principal.  
With zero APR, `interest == 0`, so every withdrawal request reverts regardless of its size because the fee scales proportionally with principal.

### Impact Explanation
All normal withdrawal requests are temporarily frozen while the incompatible fee and epoch-duration configuration remains active. [7](#0-6)   
Affected lenders retain their tranche tokens but cannot create withdrawal receipts or exit through the ordinary queued withdrawal path. [8](#0-7)   
For a vault with 1,000,000 underlying in requested principal, 50% annual management fees, an 800-day epoch, and 0% APR, the entire 1,000,000 underlying cannot be requested because the calculated fee is approximately 1,095,890 underlying. [2](#0-1) 

### Likelihood Explanation
The issue requires a long fee-accrual duration or a sufficiently high management-fee rate so that the upfront fee exceeds principal plus projected interest. [2](#0-1)   
This is not prevented by `setEpochParams()`, which only rejects a zero duration and state-dependent transitions. [5](#0-4)   
The condition is easiest to reach in an APR0 or low-APR pool because projected interest contributes little or nothing toward the fee subtraction. [9](#0-8) 

### Recommendation
Bound the product of `managementFee` and `_withdrawRequestManagementFeeDuration()` so that the configured upfront fee cannot exceed principal, or explicitly reject withdrawal requests whose fee exceeds `principal + interest` with a custom error before mutating any state. [10](#0-9)   
If zero-value receipts are supported, do not simply clamp the receipt to zero without changing the flow: `IdleCreditVault.requestWithdraw()` returns early for a zero amount while `IdleCDOEpochVariant` would still execute `_withdrawOps()` and burn the user's principal. [11](#0-10) [8](#0-7) 

### Proof of Concept
Add this test to the existing `IdleCreditVault` Foundry fork test context:

```solidity
function testRequestWithdrawRevertsWhenUpfrontFeeExceedsPrincipal() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // 50% annual management fee and an 800-day fee-accrual epoch.
    _setManagementFee(50_000);
    vm.prank(owner);
    cdoEpoch.setEpochParams(800 days, 0);

    // Remove projected interest so the fee is compared against principal alone.
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // Expected fee ~= amount * 50% * 800 / 365 > amount,
    // so principal + interest - totalFees underflows.
    vm.expectRevert(stdError.arithmeticError);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
}
```

The vulnerable calculation is `principal + interest - totalFees`, where `totalFees` can exceed the two other terms. [1](#0-0)

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
