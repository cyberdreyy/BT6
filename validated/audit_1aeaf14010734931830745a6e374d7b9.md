### Title
Missing sender allowlist check in `HandleLegacyUserMessage` allows any signed message to be forwarded to DON nodes - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The web API capabilities gateway handler's `HandleLegacyUserMessage` accepts any message with a syntactically valid self-signed signature and a known `DonId`, and forwards it to every member of the targeted DON via `don.SendToNode`, with an explicit `// TODO: apply allowlist and rate-limiting here` marking the missing authorization check. This lets any unprivileged network client consume DON compute/node resources without being a subscribed/allowlisted sender.

### Finding Description
In `gateway.go` `ProcessRequest`, a legacy request (one with `msg.Body.DonId` set) is routed purely by `msg.Validate()` succeeding and `g.handlers[handlerKey]` existing: [1](#0-0) 
`msg.Validate()` in `api/message.go` only checks field lengths/format and that the signature is well-formed enough to recover a signer address via `ExtractSigner`; it does **not** check the recovered `Sender` against any per-DON allowlist or subscription set: [2](#0-1) 
Any attacker can generate their own ECDSA keypair, sign a message body themselves (`Sign`/self-signed), and the signature will pass `ExtractSigner` since it only recovers whatever address signed the data — no comparison to a known/authorized set occurs.

Once routed to the capabilities `handler`, `HandleLegacyUserMessage` performs payload/timestamp/method checks but explicitly skips authorization: [3](#0-2) 
It then unconditionally saves the callback and forwards the message to every DON member node: [4](#0-3) 
No check exists anywhere in this path comparing `msg.Body.Sender` (or `Receiver`) against `h.donConfig` members, an owner list, or a workflow-subscription allowlist before dispatch to `don.SendToNode`.

Regarding DON ID enumeration: `handlerKey` DON IDs are configuration-level identifiers (`g.handlers` keyed by `donConfig.DonId`), not secrets — they are intended to be known service identifiers for routing, so the differential `api.UnsupportedDONIdError` response at `gateway.go:258-261` does not itself disclose privileged information; DON IDs are expected to be externally known/addressable (analogous to a service name). The exploitable defect is the absence of a sender allowlist check, not the DON ID differential error.

### Impact Explanation
This corresponds to Chainlink's "unauthorized job run / allowlist bypass" impact class: an attacker with no relationship to a DON can cause every node in that DON to receive and act on a `web_api_trigger`/`web_api_target`/`compute_action`/`workflow_syncer` message, consuming node compute/network resources (outbound HTTP requests via `handleWebAPIOutgoingMessage`, workflow trigger dispatch) and potentially triggering unintended external HTTP calls or compute workflows on behalf of an unauthorized party.

### Likelihood Explanation
Feasibility is high: the attacker only needs network access to the gateway's HTTP endpoint and the ability to generate an ECDSA keypair to self-sign a message — no credentials, subscription, or knowledge of victim secrets are required, and the target `DonId` is a known routing identifier, not a secret. The code comment itself (`// TODO: apply allowlist and rate-limiting here`) confirms the gap is a known, currently-missing control rather than a subtle logic bug.

### Recommendation
Implement the allowlist/authorization check referenced by the TODO in `handler.go` before saving the callback and dispatching to nodes: verify `msg.Body.Sender` against a per-DON allowlist (e.g., workflow owner registry or subscription set) in `HandleLegacyUserMessage`, rejecting unauthorized senders with an appropriate `api.ErrorCode` (e.g., a new `UnauthorizedSenderError`) prior to any `don.SendToNode` call.

### Proof of Concept
Go handler-level integration test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` via `NewHandler` with a `donConfig` containing a fixed set of members and (in the fixed version) an allowlist that does not include a freshly generated random key's address.
2. Build a valid `api.Message` with `Body.Method = MethodWebAPITrigger`, a valid `TriggerRequestPayload` with current timestamp, and `Sign()` it with the random (non-allowlisted) private key.
3. Call `h.HandleLegacyUserMessage(ctx, msg, callback)`.
4. Assert (post-fix) that the callback receives an authorization-error response and that the mock `don.SendToNode` is never invoked; assert (pre-fix, demonstrating the bug) that `don.SendToNode` is called for every DON member despite the sender not being present in any allowlist, proving unauthorized dispatch.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
