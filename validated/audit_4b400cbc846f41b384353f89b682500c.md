### Title
`accountSubscribe`/`programSubscribe` ignore `dataSlice` and silently misreport oversized account data as base58 payload - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
The JSON-RPC HTTP methods `getAccountInfo`/`getMultipleAccounts`/`getProgramAccounts` validate base58/binary-encoded account data against `MAX_BASE58_BYTES` via the `encode_account` wrapper and return an explicit `InvalidRequest` error when the (possibly `dataSlice`-reduced) payload is too large. The pubsub notification path for `accountSubscribe` and `programSubscribe`, however, calls `encode_ui_account` directly, hard-codes `data_slice_config` to `None` (dropping the subscriber's `dataSlice` config entirely), and has no equivalent error path — so an oversized account silently returns the string `"error: data too large for bs58 encoding"` as if it were the actual account data.

### Finding Description
`rpc/src/rpc.rs`'s `encode_account` is the sanctioned entry point for encoding an account for client consumption when Binary/Base58 encoding is requested: [1](#0-0) 

It checks the *data-sliced* length against `MAX_BASE58_BYTES` and returns a JSON-RPC error (`InvalidRequest`) instead of ever calling `encode_ui_account` on oversized data.

`account-decoder/src/lib.rs`'s `encode_bs58` (called internally by `encode_ui_account`) has no error signaling capability — on overflow it just returns the literal string `"error: data too large for bs58 encoding"` as if it were valid base58-encoded data: [2](#0-1) 

This is why the HTTP RPC path wraps it with the `MAX_BASE58_BYTES` check in `encode_account` before ever calling `encode_ui_account`.

The pubsub subscription notification code path, `filter_account_result` (for `accountSubscribe`) and `filter_program_results` (for `programSubscribe`), calls `encode_ui_account` **directly**, bypassing `encode_account` entirely, and additionally hard-codes the `data_slice_config` argument to `None` instead of forwarding `params.data_slice`: [3](#0-2) 

Both call sites (`encode_ui_account(&params.pubkey, &account, params.encoding, None, None)` at line 388, and `encode_ui_account(&pubkey, &account, encoding, None, None)` at line 433) pass a literal `None` for the data slice, so any `dataSlice` a subscriber configures on `accountSubscribe`/`programSubscribe` is silently discarded (`AccountSubscriptionParams`/`ProgramSubscriptionParams` both carry a `data_slice` field that is stored but never consulted here): [4](#0-3) 

Because the slice is dropped, a subscriber cannot even work around the base58 size cap by requesting a small slice (which is exactly the technique validated at the HTTP layer, see `test_encode_account_does_not_throw_despite_data_too_large_to_base58_encode_because_dataslice_makes_it_fit`). The bug is already implicitly acknowledged by an existing unit test that asserts the corrupted output is the expected behavior: [5](#0-4) 

### Impact Explanation
Any unprivileged client can `accountSubscribe`/`programSubscribe` (default Binary encoding, or explicit `base58`) to an account/program whose account data exceeds `MAX_BASE58_BYTES` (128 bytes). Every notification for that account/program will deliver the sentinel string `"error: data too large for bs58 encoding"` in the `data` field, with a `space`/`lamports`/`owner` that otherwise look like a normal, valid response — this is a decoder misreporting condition: the client receives a syntactically valid `UiAccount` object whose `data` field is falsely presented as the base58-encoded account payload. This can mislead any downstream consumer (wallets, indexers, bots) parsing subscription payloads into treating an error string as real on-chain data. The `dataSlice` config is also completely non-functional for both subscription types, which is a further correctness/consistency bug versus the documented, sibling HTTP behavior.

### Likelihood Explanation
Trivially reachable by any JSON-RPC pubsub client with a single `accountSubscribe`/`programSubscribe` call and no special privileges — this matches the required "decoder panic and misreporting" impact class from a single low-cost, unprivileged-user request.

### Recommendation
In `filter_account_result` and `filter_program_results` (rpc/src/rpc_subscriptions.rs), forward `params.data_slice` to `encode_ui_account` instead of hard-coding `None`, and apply the same `MAX_BASE58_BYTES` validation used in `encode_account` (rpc/src/rpc.rs) — either by routing through a shared helper or by validating at subscribe time (`account_subscribe`/`program_subscribe` in rpc/src/rpc_pubsub.rs) so that a subscription configured with an encoding/dataSlice combination that would exceed the limit is rejected up front with an `InvalidParams`/`InvalidRequest` error, consistent with the HTTP `getAccountInfo`/`getProgramAccounts` behavior.

### Proof of Concept
1. Start a validator/test-validator and create an account with data length > 128 bytes (e.g., a stake or vote account).
2. Call `accountSubscribe` (or `programSubscribe` for its owning program) with default encoding (`Binary`) and no/large `dataSlice`.
3. Trigger an update to the account (e.g., a lamports transfer).
4. Observe the notification payload's `data` field equals the literal string `"error: data too large for bs58 encoding"` — reproduced by the existing test `expected2` in `rpc/src/rpc_subscriptions.rs` lines 1345-1353, which encodes this exact behavior as an assertion rather than treating it as a bug.
5. Additionally, pass a `dataSlice: { offset: 0, length: 10 }` in the same subscription — the notification will still contain full, un-sliced data (or the same error string), proving `dataSlice` is ignored for subscriptions.

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}

fn encode_bs58<T: ReadableAccount>(
    account: &T,
    data_slice_config: Option<UiDataSliceConfig>,
) -> String {
    let slice = slice_data(account.data(), data_slice_config);
    if slice.len() <= MAX_BASE58_BYTES {
        bs58::encode(slice).into_string()
    } else {
        "error: data too large for bs58 encoding".to_string()
    }
}

fn filter_account_result(
    result: Option<(AccountSharedData, Slot)>,
    params: &AccountSubscriptionParams,
    last_notified_slot: Slot,
    bank: Arc<Bank>,
) -> (Option<UiAccount>, Slot) {
    // If the account is not found, `last_modified_slot` will default to zero and
    // we will notify clients that the account no longer exists if we haven't already
    let (account, last_modified_slot) = result.unwrap_or_default();

    // If last_modified_slot < last_notified_slot this means that we last notified for a fork
    // and should notify that the account state has been reverted.
    let account = (last_modified_slot != last_notified_slot).then(|| {
        if is_known_spl_token_id(account.owner())
            && params.encoding == UiAccountEncoding::JsonParsed
        {
            get_parsed_token_account(&bank, &params.pubkey, account, None)
        } else {
            encode_ui_account(&params.pubkey, &account, params.encoding, None, None)
        }
    });
    (account, last_modified_slot)
}

fn filter_signature_result(

fn filter_program_results(
    accounts: Vec<(Pubkey, AccountSharedData)>,
    params: &ProgramSubscriptionParams,
    last_notified_slot: Slot,
    bank: Arc<Bank>,
) -> (impl Iterator<Item = RpcKeyedAccount> + use<>, Slot) {
    let accounts_is_empty = accounts.is_empty();
    let encoding = params.encoding;
    let filters = params.filters.clone();
    let keyed_accounts = accounts.into_iter().filter(move |(_, account)| {
        filters
            .iter()
            .all(|filter_type| filter_allows(filter_type, account))
    });
    let accounts = if is_known_spl_token_id(&params.pubkey)
        && params.encoding == UiAccountEncoding::JsonParsed
        && !accounts_is_empty
    {
        let accounts = get_parsed_token_accounts(bank, keyed_accounts);
        Either::Left(accounts)
    } else {
        let accounts = keyed_accounts.map(move |(pubkey, account)| RpcKeyedAccount {
            pubkey: pubkey.to_string(),
            account: encode_ui_account(&pubkey, &account, encoding, None, None),
        });
        Either::Right(accounts)
    };
    (accounts, last_notified_slot)
}
