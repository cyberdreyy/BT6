### Title
`BlockInfo::mark_locally_rejected` sets `valid=Some(false)` unconditionally, and `mark_locally_accepted(true)` never sets `valid`, letting an already-accepted block be re-processed and rejected - (File: `stacks-signer/src/signerdb.rs`)

### Summary
`BlockInfo` tracks two independent signals that are supposed to move together: the `state` enum (`Unprocessed → … → LocallyAccepted/GloballyAccepted`) and the `valid: Option<bool>` flag, which `handle_block_validate_response` uses as the guard to avoid re-processing a block validation response it already handled. Exactly like the Beacon-Kit report where `EffectiveBalance` and `Balance` are two values meant to stay in sync but only one is updated on deposit, here `state` and `valid` are two fields meant to stay in sync but the code paths that mutate them diverge.

### Finding Description
`BlockInfo::mark_locally_accepted` only sets `valid = Some(true)` on the "I signed it myself" branch; when called with `group_signed = true` (i.e. the block was accepted because a threshold of *other* signers' signatures arrived) it skips setting `valid` entirely: [1](#0-0) 

`mark_globally_accepted` likewise never touches `valid`: [2](#0-1) 

So a block can legitimately reach `state == GloballyAccepted` (via `store_and_process_block_signature` calling `mark_locally_accepted(true)` at [3](#0-2)  followed by a `NewBlock` event calling `mark_globally_accepted` at [4](#0-3) ) while `valid` is still `None`.

Meanwhile, `handle_block_validate_response` uses `valid.is_some()` as the sole guard against reprocessing a stale/duplicate node validation response: [5](#0-4) 

If this signer's own `/v3/block_proposal` submission for the same block returns late (after the block already reached `GloballyAccepted` through the other signers' signatures), `valid` is still `None`, so the guard does **not** trigger. Processing falls through to `check_block_against_signer_db_state`, and if that returns a rejection, `mark_locally_rejected` is invoked: [6](#0-5) 

```rust
pub fn mark_locally_rejected(&mut self) -> Result<(), String> {
    self.valid = Some(false);
    self.move_to(BlockState::LocallyRejected)
}
``` [7](#0-6) 

`valid` is set to `Some(false)` unconditionally, *before* `move_to` even checks whether the transition is legal. `move_to`/`check_state` correctly refuses to move a `GloballyAccepted` block to `LocallyRejected` (returning `Err`), so `state` stays `GloballyAccepted`: [8](#0-7) 

But the caller ignores that `Err` whenever `has_reached_consensus()` is true (which it is, since `state == GloballyAccepted`), and unconditionally persists the now-inconsistent `BlockInfo` (`state = GloballyAccepted`, `valid = Some(false)`) to the DB, then still calls `self.send_block_response(&block_info.block, block_rejection.into())`, broadcasting an explicit **rejection** for a block this same signer's own state machine already recognizes as globally accepted (i.e., already adopted by the node / canonical).

### Impact Explanation
This produces a signed protocol message (`BlockResponse::Rejected`) that directly contradicts the signer's own already-reached `GloballyAccepted` status for that block — a conflicting response from a signer that has already accepted the block as canonical. It also corrupts the persisted `BlockInfo` record (`valid=false` co-existing with `state=GloballyAccepted`), which other guard checks throughout `signer.rs`/`signerdb.rs` (built on the assumption that `valid` tracks `state`) rely on, undermining downstream logic such as re-evaluation (`should_reevaluate_block`) and conflict/tip queries that key off `valid`/`state` pairs. This matches the report's "Medium" severity of an unintended state divergence between two fields meant to move together, here manifesting as a spurious/duplicate rejection message rather than a fund-loss.

### Likelihood Explanation
No majority collusion or malicious key is required: the race is purely timing-based and can occur in ordinary operation whenever a supermajority of *other* signers sign/accept a block before this signer's own node validation call returns (e.g. a slow node, a busy validation queue, or a miner that intentionally delays the proposal to one signer while broadcasting group signatures quickly to it). This is a naturally reachable race in the one-slot-miner + gossip model described in scope.

### Recommendation
Set `valid = Some(true)` in `mark_locally_accepted` regardless of `group_signed`, and set it in `mark_globally_accepted` too (or, more robustly, derive the "already decided" guard in `handle_block_validate_response` from `block_info.state` — e.g. `state != Unprocessed` — rather than from the independently-mutated `valid` field). Additionally, `mark_locally_rejected`/`mark_pre_committed`/`mark_locally_accepted` should only mutate `valid`/timestamps *after* `move_to` succeeds, not before, to avoid ever persisting a `valid` value that does not correspond to the actual (unchanged) `state`.

### Proof of Concept
1. Signer S receives `BlockProposal` for block `B` and submits it to its node for validation (`submitted_block_proposal` set, `valid = None`).
2. Before S's own node responds, S receives `BlockResponse::Accepted` signatures from other signers reaching the 70% weight threshold; `store_and_process_block_signature` calls `block_info.mark_locally_accepted(true)` (group_signed path) → `state = LocallyAccepted`, `valid` stays `None`.
3. S's node subsequently reports the block as the new tip (`NewBlock` event) → `mark_globally_accepted()` → `state = GloballyAccepted`, `valid` still `None`.
4. S's originally-submitted validation for `B` finally returns as `BlockValidateOk`. `handle_block_validate_response` looks up `block_info` (state `GloballyAccepted`, `valid=None`), the `valid.is_some()` short-circuit at [5](#0-4)  is skipped, and `check_block_against_signer_db_state` is (re-)run.
5. If that recheck returns any rejection (e.g. it now perceives a different tip/conflict), `mark_locally_rejected()` sets `valid=Some(false)` unconditionally while `move_to` fails and leaves `state=GloballyAccepted`; S persists this inconsistent record and calls `send_block_response` broadcasting a `Rejected` response for block `B`, contradicting its own already-reached `GloballyAccepted` verdict.

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }

    /// Attempt to transition the block state
    pub fn move_to(&mut self, state: BlockState) -> Result<(), String> {
        if !self.check_state(state) {
            return Err(format!(
                "Invalid state transition from {} to {state}",
                self.state
            ));
        }
        self.state = state;
        Ok(())
    }
