### Title
GET /v2/external_initiators discloses AccessKey and OutgoingToken of all EIs to any authenticated view-role user, with no role restriction - ([File: core/web/router.go])

### Summary
The route registration `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` in `core/web/router.go` applies no role wrapper (unlike `Create`/`Destroy`, which use `auth.RequiresEditRole`), so any user authenticated at the lowest `view` role can enumerate all External Initiators via `ExternalInitiatorsController.Index`, and `presenters.NewExternalInitiatorResource` returns each EI's `AccessKey` and `OutgoingToken` in the response.

### Finding Description
`ExternalInitiatorsController.Index` (core/web/external_initiators_controller.go:50-59) fetches all `bridges.ExternalInitiator` rows via `eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)` and maps each to `presenters.NewExternalInitiatorResource`, which explicitly copies `AccessKey` and `OutgoingToken` into the JSON response (core/web/presenters/external_initiators.go:67-77), while omitting the salted `HashedSecret`/`Secret`.

Critically, the route is registered as `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` in core/web/router.go:264 with no `auth.RequiresEditRole` / `auth.RequiresAdminRole` wrapper — contrast with the adjacent lines for `Create` and `Destroy`, which are wrapped with `auth.RequiresEditRole`. Since `authv2` only requires generic authentication (`auth.AuthenticateByToken` or `auth.AuthenticateBySession`), any authenticated user regardless of role (`view`, `run`, `edit`, `admin`) can call `GET /v2/external_initiators` and receive `AccessKey`/`OutgoingToken` for every EI in the node, including EIs created by other (e.g., admin) users.

Regarding impersonation feasibility: EI authentication (`bridges.AuthenticateExternalInitiator`, core/bridges/external_initiator.go:61-66) still requires the correct `Secret`, which is salted and hashed (`HashedSecret`) and never returned by this endpoint. So disclosure of `AccessKey`+`OutgoingToken` alone does not directly grant EI impersonation without also possessing/brute-forcing the corresponding `Secret` — this part of the question is speculative and unconfirmed by the code (no `Secret` is disclosed anywhere in `Index`). However, the confirmed vulnerability is the credential-material disclosure itself: `AccessKey` (used as an authentication identifier/header value) and `OutgoingToken` (used by the node's outgoing webhook auth to the EI's external endpoint) are sensitive values that should be scoped to admin/edit-role users but are exposed to all view-role users.

### Impact Explanation
This is a role-authorization bypass / credential disclosure: a low-privileged `view`-role account can read `AccessKey` and `OutgoingToken` belonging to EIs it did not create. `OutgoingToken` is used by the node to authenticate itself to the external initiator's endpoint, so its disclosure lets a view-role attacker with network access to that external endpoint impersonate the node's outgoing call to that EI. `AccessKey` disclosure narrows the identity half of the EI's inbound-run credential, reducing the remaining secret space an attacker must obtain (via other means) to trigger job runs as that EI. This matches Chainlink's "unauthorized disclosure of sensitive credentials to under-privileged principal" impact class.

### Likelihood Explanation
Feasibility is high and immediately reproducible: the only precondition is possessing any valid session or API token with `view` role (the lowest role tier), which is a normal, low-trust credential intentionally provisioned for read-only dashboard access. No brute-force, timing, or race condition is needed to reach the disclosure — a single `GET /v2/external_initiators` call suffices.

### Recommendation
Wrap the `Index` route with an appropriate role check consistent with `Create`/`Destroy`, e.g. `authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))` (or `RequiresAdminRole` if EIs are considered admin-only resources). Additionally, consider whether `AccessKey`/`OutgoingToken` need to be returned at all in list views, or should be masked/redacted for all but the resource owner or admin.

### Proof of Concept
Go handler-level integration test (extending `core/web/external_initiators_controller_test.go`):
1. Set up a test app (`cltest.NewApplicationEVMDisabled` or existing test harness) and create an EI as an admin user via `POST /v2/external_initiators`, capturing the returned `AccessKey`.
2. Create a second user session/token with role `sessions.UserRoleView`.
3. Issue `GET /v2/external_initiators` authenticated as the view-role user.
4. Assert the response is `200 OK` (currently succeeds) rather than `401`/`403`.
5. Assert the JSON body contains an entry with `accessKey` matching the EI created in step 1 and `outgoingToken` populated — demonstrating disclosure to an under-privileged caller.
6. After applying the fix (wrapping `Index` with `auth.RequiresEditRole`/`RequiresAdminRole`), re-run the test and assert `403 Forbidden` for the view-role user and successful response only for edit/admin-role users.
