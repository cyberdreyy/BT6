## Finding

The bug-class match is a **counter that is incremented once and never corrected when the underlying vote changes**, exactly like `totalUnstakeFine` in the original report being incremented on `unstake` and never reduced when the fine turns out to be uncollectable. The stacks-node counterpart lives in the miner-side signer coordinator's weight tally, not the signer's own local state machine.

### Title
Stale/double-counted rejection weight in `StackerDBListener` block-response tally breaks the aggregated-weight vs. verified-accepts equality - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`BlockStatus.total_weight_rejected` is incremented when a signer's `Rejected` response is first seen, but there is no corresponding mechanism to remove that weight when the *same* signer later re-evaluates and sends an `Accepted` response for the identical block. The `Accepted` handler only guards against double counting via `gathered_signatures`, never checking (or clearing) `responded_signers`/`total_weight_rejected`, so a signer that flips its vote leaves its earlier rejection weight permanently baked into the rejected tally.

### Finding Description
In the `Accepted` branch, weight is added to `total_weight_approved` only if the slot is not already in `gathered_signatures`, then the slot is unconditionally inserted into `responded_signers`: [1](#0-0) 

In the `Rejected` branch, weight is added to `total_weight_rejected` only if `responded_signers.insert(slot_id)` returns `true` (i.e., first response ever from that slot): [2](#0-1) 

The asymmetry: if a slot rejects first (`total_weight_rejected += w`, `responded_signers` now contains the slot) and later accepts the same block hash (a legitimate, documented transition — the signer-flows doc explicitly allows `LocallyRejected -> LocallyAccepted: re-evaluated`), the `Accepted` branch adds `w` to `total_weight_approved` (correct) but **never removes `w` from `total_weight_rejected`**. There is no code path in this file that decrements `total_weight_rejected` for a slot that has switched to accept; `reset_rejections` is only invoked on an overall timeout, not per-signer vote-flip.

`signer_coordinator.rs` then treats `total_weight_rejected` as ground truth for whether >30% blocking-minority has rejected the block: [3](#0-2) 

(Note: this is the same check block shown earlier in `check_block_status_and_wait` / equivalent polling loop that returns `Err(NakamotoNodeError::SignersRejected{...})` once `total_weight_rejected + weight_threshold > total_weight`.) [4](#0-3) 

Because stale rejection weight from vote-switchers is never purged, `total_weight_rejected` can hold weight from signers who have since accepted the block. Combined with additional, unrelated rejections arriving later, the tally can cross the blocking-minority line even though the *current* set of rejecting signers is below 30%, and even though the *current* set of accepting signers may already be at/above 70%. This breaks the "aggregated-weight vs verified-accepts" equality: the aggregate no longer reflects the verified, current vote set.

### Impact Explanation
Meanwhile, on the signer side, once a signer's own local pre-commit/signature tally (independent of this miner-side coordinator) crosses 70%, it calls `broadcast_signed_block` and pushes the block directly to its node via `handle_post_block`: [5](#0-4) 

So the miner's `SigningCoordinator` can independently conclude `SignersRejected` (based on stale rejected weight) and move the miner on to build a *different* block at the same height/tenure, while the signer set — using its own, correctly-computed local tally — separately reaches consensus and pushes the *original* block into the chain. This produces two competing blocks contending for the same slot: a conflicting-block condition triggered purely by ordinary vote-flip gossip traffic that any one signer can generate (no majority collusion required, no key compromise), landing in the Critical bucket ("a rejection recounted as acceptance" / miscounted response class) via a mis-tallied aggregate rather than a forged signature.

### Likelihood Explanation
Vote flips from `LocallyRejected` to `LocallyAccepted` are an explicit, expected part of the signer's re-evaluation logic (`should_reevaluate_reject_reason`, `BlockInfo::check_state` state diagram). Any signer briefly rejecting on a transient chainstate check (timing/reorg races are exactly the kind of thing `check_block_against_signer_db_state` is designed to re-check) and then accepting after conditions resolve will trigger the accumulation described above — this requires no adversarial majority, only ordinary gossip timing.

### Recommendation
Track, per slot id, the *current* vote direction (accept/reject) rather than only membership in `responded_signers`. When a slot transitions from rejected to accepted (or vice versa), subtract its weight from the stale bucket before adding it to the new one, so `total_weight_approved` + `total_weight_rejected` always reflects the *current* vote of each responding signer rather than an append-only ratchet.

### Proof of Concept
1. Miner proposes block B; total signer weight = 100, `weight_threshold` = 70 (blocking minority = 31).
2. Signers S1 (weight 35) send `Rejected` for B due to a transient chainstate check failing (e.g., a stale conflict window). `total_weight_rejected` = 35.
3. Conditions resolve (e.g., the conflicting tenure goes stale per `conflict_still_blocks`); S1 re-evaluates and sends `Accepted` for the same B. `total_weight_approved` += 35, but `total_weight_rejected` stays at 35 (never decremented) — see `stackerdb_listener.rs` lines 443-465 vs 515-518.
4. Separately, S2 (weight 40, distinct from S1, genuinely rejecting for a different reason) sends `Rejected`. `total_weight_rejected` = 35 + 40 = 75, which exceeds `total_weight - weight_threshold` = 30, so `signer_coordinator.rs` returns `Err(SignersRejected{...})` and the miner abandons B for a new block, even though the *current* rejecting weight is only 40 (below the 31 blocking minority is already exceeded by 40 alone in this specific numeric example — adjust weights, e.g. S2=20, so current-reject=20 < 31 but stale total=55 > 31) causing a false rejection decision purely from the un-decremented stale weight of S1.
5. Meanwhile S1 and any other signers reaching their own local 70% via `store_and_process_block_signature` push B directly to their node, so B can still be finalized on-chain while the miner, believing B was rejected, has already started building a competing block — a conflicting-block condition.
