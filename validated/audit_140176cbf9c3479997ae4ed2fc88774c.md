### Title
Deleting a multisig member/key does not purge their stale confirmations from other pending requests, allowing a request to execute below the live-member threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
Both `multisig` (V1, key-centric) and `multisig2` (V2, member-centric) count confirmations for a request as the raw size of the `confirmations` `HashSet` stored for that `request_id`, without validating that each confirming key/member is still a current member at the time the threshold check runs in `confirm`. `DeleteKey`/`DeleteMember` only purge requests *originated* by the removed signer; they never scrub that signer's confirmation entries from requests originated by other members. This is directly analogous to the reported `Maker.collectFees` bug: a value recorded in the past (`asset.liq` / here, a stored confirmation) is re-used as-is by later logic (`collectFees`'s re-target / here, the threshold check in `confirm`) even though the entity it was derived from was subsequently changed (`adjustMaker` reducing liquidity / here, `delete_member` removing that signer), producing an outcome that no longer matches the current state.

### Finding Description
In `multisig2/src/lib.rs`: [1](#0-0) 
`confirm` computes `confirmations.len() as u32 + 1 >= self.num_confirmations` directly from the stored `HashSet<String>` and, if satisfied, calls `execute_request`. There is no check that every entry in `confirmations` corresponds to an account/key still present in `self.members`.

`delete_member` (invoked only through `execute_request`'s `DeleteMember` action) is the only place that mutates `confirmations`/`requests` in response to membership changes: [2](#0-1) 
It removes requests where `r.member == member` (i.e., requests the removed member *originated*), and clears `num_requests_pk` for that member. It does **not** iterate over `self.confirmations` to strip the removed member's entry from requests originated by *other* members.

The V1 contract has the identical gap in `DeleteKey`: [3](#0-2) 
Only requests signed by the deleted key are purged; confirmations the deleted key placed on requests submitted by other keys remain in `self.confirmations`.

**Binding that should hold:** `confirmations.len()` (live approvals) == number of distinct *current* members who approved the request. After a `DeleteMember`/`DeleteKey` action executes, this invariant is broken for any request where the deleted member had already confirmed but was not the request's original submitter — the stored confirmation count still includes the now-removed member, while the actual number of authorized live approvers is one less.

**Concrete break:**
- Multisig with members `{A, B, C, D}`, `num_confirmations = 3`.
- Member `A` submits request `R` (any `Transfer`/`FunctionCall`/etc.); at add time `confirmations[R] = {}`.
- Member `B` confirms `R` → `confirmations[R] = {B}` (1 < 3, not yet executed).
- Separately, members execute a `DeleteMember{member: B}` request (requires 3 confirmations, unrelated to `R`) — legitimate governance action removing `B`. `delete_member` only cleans up requests where `r.member == B` (i.e., requests *B* originated); `R` was originated by `A`, so `R`'s confirmations set `{B}` is untouched. `B`'s access key/account is now removed from `self.members`.
- Member `C` confirms `R` → `confirmations.len()==1 (stale B) + 1 (C) = 2`, still `< 3`, not executed. Member `D`... actually only 2 live confirmers (`C`,`D`) are needed together with the phantom `B` to hit 3: `C` confirms → `confirmations = {B, C}` → `len()+1 (D) ... ` — the essential point is that only **2 live signers** (e.g., `C` and `D`, or even just `C` alone plus the ghost `B`) are needed to make `confirmations.len() as u32 + 1 >= 3` true, executing a 3-of-4 policy request with only 2 genuinely authorized approvals (`B`'s prior confirmation, cast before removal, is being spent as though `B` were still a valid signer).

This lets a request (including `Transfer`, `FunctionCall`, `AddKey`, `AddMember`, etc.) execute with fewer *live* authorizing parties than `num_confirmations` mandates — an authorization-threshold bypass.

### Impact Explanation
This falls squarely under the Critical impact category defined by the scope: "a multisig request executed below threshold." An attacker (or even an ordinary confirmation flow with no malice, but exploitable deliberately) can arrange for a member removal to happen after that member has pre-confirmed several pending requests, effectively banking spendable "ghost" approvals. Once removed, those stale confirmations still count toward `num_confirmations`, letting `Transfer` or arbitrary `FunctionCall`/`AddKey` actions execute funds or state changes without the intended number of currently-trusted approvers — a direct authorization-boundary violation and potential unauthorized movement of funds held by the multisig account.

### Likelihood Explanation
Requires no privileged actor beyond ordinary participation available to any current signer: any member can confirm pending requests (unprivileged with respect to this specific flaw — confirming is a normal action any member is entitled to do), and member removal is a normal, expected multisig governance action that will happen over the contract's lifetime (key rotation, offboarding). The bug is triggered by ordinary sequencing (confirm → later unrelated member removal → additional confirms), not by any privileged bypass, redeploy, or social engineering — it is a realistic operational sequence for any long-lived multisig, making likelihood high once membership changes ever occur while other requests are outstanding.

### Recommendation
When executing `DeleteMember` (`multisig2`) / `DeleteKey` (`multisig`), iterate over all entries in `self.confirmations` and remove the deleted member/key from every confirmation set (not only requests they originated), or alternatively re-validate at `confirm`-time that every confirmer in the stored set is still `self.members.contains(...)` before counting it toward the threshold (e.g., filter live confirmers before comparing `len() >= num_confirmations`).

### Proof of Concept
Conceptual sequence (Rust-level, using `multisig2::MultiSigContract`):
1. `new(members = [A, B, C, D], num_confirmations = 3)`.
2. As `A`: `add_request_and_confirm(transfer_request)` → creates request `R1`, `confirmations[R1] = {A}`.
3. As `B`: `confirm(R1)` → `confirmations[R1] = {A, B}` (2 < 3, pending).
4. Separately get 3 confirmations to pass `DeleteMember{member: B}` (a legitimate governance action) — this calls `delete_member`, which only removes requests where `r.member == B`; since `R1.member == A`, `R1` and its `confirmations = {A, B}` are left untouched. `B` is now removed from `self.members`.
5. As `C` (still a live member): `confirm(R1)` → `confirmations.len() (2, includes stale B) + 1 >= 3` → `R1` executes via `execute_request`, even though only `A` and `C` are current, live members — one fewer live approver than `num_confirmations = 3` requires.

This cannot be fully instrumented without running the contract's test harness, but the code paths cited (`confirm` at [1](#0-0)  and `delete_member` at [2](#0-1) ) demonstrate the missing cross-request confirmation cleanup that makes this sequence possible.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
