### Title
Pending withdrawal fees are paid in full even when the withdrawal receipt is loss-adjusted - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`requestWithdraw` deducts management and performance fees from a user's receipt before the withdrawal is funded, while `stopEpochWithDuration` can later haircut that receipt for losses but still distributes the full fee to fee recipients. This leaves the user paying fees on value that was never delivered.

### Finding Description
`requestWithdraw` calculates `principal + interest - totalFees`, records only the net amount as the user's claimable receipt, and accumulates the deducted amount in `pendingWithdrawFees`. [1](#0-0) 

During a loss-adjusted epoch stop, `previewLossAdjustedWithdrawFunds` reduces the amount funded for pending withdrawals and `collectWithdrawFunds` stores the corresponding recovery price. [2](#0-1) [3](#0-2) 

However, `_stopEpoch` unconditionally transfers the full pre-loss `pendingWithdrawFees` amount to the fee recipients before users claim their reduced receipts. [4](#0-3) 

The pending user subsequently receives only `claimBasis * lossRecoveryPrice`, where `claimBasis` was already reduced by the fee. [5](#0-4) 

Thus, for a gross pending claim `P + I` and deducted fee `F`, the user receives `(P + I - F) * recoveryPrice`, while the fee recipients receive the full `F`. The user effectively pays `F` even on the portion of the withdrawal that is eliminated by the loss.

### Impact Explanation
This is a direct transfer of user value to fee recipients. The maximum user loss attributable to the missing refund is approximately `F * recoveryPrice`, while the fee recipients still receive `F` regardless of how much of the pending claim survives.

In a near-total loss, the pending user's receipt can be reduced almost to zero while the full projected withdrawal fee is still paid. The same accounting also means a defaulted pending claim retains only its fee-reduced basis in recovery accounting. [6](#0-5) 

### Likelihood Explanation
The issue requires a pending withdrawal followed by either a loss-adjusted epoch stop or borrower default. These are supported lifecycle states rather than exceptional privileged misuse: an ordinary KYC-passed tranche holder creates the pending receipt, and the honest manager later processes the realized loss or default. [7](#0-6) 

No existing guard prevents the mismatch: the loss-adjustment path explicitly allows partial pending funding, and the fee transfer is not conditioned on the pending receipt being paid at par. [8](#0-7) [9](#0-8) 

### Recommendation
Track each pending withdrawal's gross claim and deducted fee separately by epoch or user.

For loss-adjusted stops, either:

- calculate the receipt's recovery haircut before charging fees, then charge fees only on the funded claim; or
- retain the gross claim as the user's recovery basis and escrow `pendingWithdrawFees` separately, paying only the portion attributable to successfully funded value.

For borrower defaults, restore the unearned fee to the user's default claim basis or otherwise include it in the recovery allocation instead of permanently removing it from the user's claim.

### Proof of Concept
Add this test to `test/foundry/IdleCreditVault.t.sol`:

```solidity
function testPendingWithdrawFeeIsNotLossAdjusted() external {
  uint256 amount = 10_000 * ONE_SCALE;

  // Charge a 10% performance fee so the deducted withdrawal fee is easy to observe.
  _setFeeParams(TL_MULTISIG, 10_000, FULL_ALLOC, 0);

  address pendingUser = makeAddr("pending-user");
  _depositWithUser(pendingUser, amount, true);

  vm.prank(pendingUser);
  uint256 netReceipt = cdoEpoch.requestWithdraw(0, address(AAtranche));
  uint256 pendingFee = cdoEpoch.pendingWithdrawFees();

  assertGt(netReceipt, 0);
  assertGt(pendingFee, 0);

  _startEpochAndCheckPrices(0);

  IdleCreditVault creditVault = IdleCreditVault(address(strategy));
  uint256 requestEpoch = creditVault.epochNumber();
  uint256 pendingBasis = creditVault.pendingWithdraws();
  uint256 activeBasis =
    cdoEpoch.getContractValue() +
    cdoEpoch.expectedEpochInterest() -
    cdoEpoch.pendingWithdrawFees();

  // Realize a 20% loss across active backing plus pending receipts.
  uint256 lossAmount = (activeBasis + pendingBasis) / 5;
  (uint256 pendingToFund, ) = creditVault.previewLossAdjustedWithdrawFunds(lossAmount);
  assertLt(pendingToFund, pendingBasis);

  uint256 borrowerPayment = cdoEpoch.expectedEpochInterest() + pendingToFund;
  deal(defaultUnderlying, borrower, borrowerPayment, true);

  uint256 feeReceiverBefore = underlying.balanceOf(TL_MULTISIG);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), lossAmount);

  // The full pre-loss fee is paid even though the pending receipt is haircut.
  assertEq(
    underlying.balanceOf(TL_MULTISIG) - feeReceiverBefore,
    pendingFee,
    "pending withdrawal fee was not loss-adjusted"
  );

  uint256 recoveryPrice = creditVault.lossRecoveryPriceByEpoch(requestEpoch);
  assertLt(recoveryPrice, ONE_TRANCHE);

  uint256 balanceBefore = underlying.balanceOf(pendingUser);
  vm.prank(pendingUser);
  cdoEpoch.claimWithdrawRequest();
  uint256 payout = underlying.balanceOf(pendingUser) - balanceBefore;

  // The user is first charged `pendingFee`, then the reduced claim is haircut again.
  assertApproxEqAbs(
    payout,
    netReceipt * recoveryPrice / ONE_TRANCHE,
    5,
    "unexpected loss-adjusted payout"
  );

  // This is the value lost because the fee was not restored before applying the loss.
  uint256 unrefundedFeeLoss = pendingFee * recoveryPrice / ONE_TRANCHE;
  assertGt(unrefundedFeeLoss, 0);
}
```

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```
