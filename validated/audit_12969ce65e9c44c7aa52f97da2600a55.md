## Title
v1 `validate_tenure_change_payload` misses `LocallyAccepted` sibling in own-tenure duplicate check - ([File: stacks-signer/src/chainstate/v1.rs])

## Summary
`stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` checks for an already-signed block in the proposed tenure using `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0) , while the v2 equivalent uses `get_last_signed_block`, which also matches `LocallyAccepted` blocks [2](#0-1) . This means a v1-pinned signer's proposal-time duplicate-tenure-start guard misses a sibling block it has already signed locally but that has not yet reached global acceptance.

## Finding Description
The claimed equality — "a signed (`LocallyAccepted`) block in a tenure must always block a second tenure-start proposal in the same tenure" — holds for v2 (`get_last_signed_block` matches `GloballyAccepted` OR `LocallyAccepted` [3](#0-2) ) but is broken for v1, whose duplicate check queries `get_last_globally_accepted_block`, which only matches `GloballyAccepted` state and misses `LocallyAccepted` blocks entirely. This asymmetry is explicitly documented: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)" [4](#0-3) , and v2 even carries a regression test (`check_tenure_change_rejects_when_locally_accepted_block_exists`) precisely for this gap [5](#0-4) , but no analogous fix/test exists for v1's `validate_tenure_change_payload`.

However, the docs also identify that this proposal-time `DuplicateBlockFound` check is not the only guard: the pre-commit/signing path (`handle_block_pre_commit`) independently re-checks own-tenure conflicts via `get_signed_conflicts` before actually producing a signature, precisely because "the `DuplicateBlockFound` check ... lives in `check_proposal` and runs only at proposal arrival, never again" [6](#0-5) . This backstop specifically inspects signed conflicts (querying `signed_self`/`signed_group`, i.e., exactly `LocallyAccepted`/`GloballyAccepted` blocks) at or above the conflicting height, across all tenures, before the signature is emitted [7](#0-6) . I was not able to fully verify, within the available iterations, whether this second guard (`conflict_still_blocks`/`get_signed_conflicts` in `stacks-signer/src/v0/signer.rs`) reliably classifies a same-height, same-tenure sibling as a blocking conflict when the existing sibling is only `LocallyAccepted` (not yet observed by the node) — the doc's flowchart shows a branch ("no, only locally accepted and a sibling at this height" → HOLD, refuse to sign) that appears to directly cover this exact scenario, which would prevent the exploit from actually reaching a second signature despite the v1 proposal-time gap.

## Impact Explanation
If the pre-commit backstop does *not* actually cover this case (unverified), the impact would be Critical: a v1-pinned signer could sign two conflicting tenure-start blocks for the same tenure, breaking the per-tenure uniqueness/safety property and enabling a chain-safety violation from a single attacker-controlled miner slot plus ordinary StackerDB gossip. If the backstop does cover it (as its documented branch suggests), then this v1/v2 asymmetry is a latent inconsistency/documentation-mismatch bug in the proposal-time check but does not by itself allow a double signature, since the pre-commit re-check is designed as the safety net for exactly this "check only runs once" gap.

## Likelihood Explanation
Preconditions: v1 chainstate protocol version active; attacker holds a single miner slot; attacker proposes a first tenure-start block, waits for the victim signer to reach `LocallyAccepted` (but not yet `GloballyAccepted`, i.e., before 70% signature threshold is publicly observed/aggregated by the node), then broadcasts a second, competing tenure-start proposal for the same consensus hash. This is plausible to construct (a slow/partitioned round of pre-commit gathering), but whether it actually results in a second signature depends entirely on the pre-commit-time `get_signed_conflicts`/`conflict_still_blocks` guard's behavior, which I could not fully confirm within the available tool budget.

## Recommendation
Regardless of whether the pre-commit backstop already prevents exploitation, the v1/v2 inconsistency should be fixed for defense-in-depth and to match the documented invariant: change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the v2 fix, and add a `v1.rs`-analog of `check_tenure_change_rejects_when_locally_accepted_block_exists` to lock in the fix.

## Proof of Concept
Port `check_tenure_change_rejects_when_locally_accepted_block_exists` from `stacks-signer/src/chainstate/tests/v2.rs` (lines 748-850) to `stacks-signer/src/chainstate/tests/v1.rs`, using `SortitionState::check_proposal` (v1) in place of the v2 `check_proposal`: insert a `LocallyAccepted` block for a tenure via `mark_locally_accepted`, then submit a second tenure-start proposal (`TenureChangeCause::BlockFound` + coinbase) for the same consensus hash, and assert the result. Before a fix, `validate_tenure_change_payload` (v1) returns `Ok(())` (no `DuplicateBlockFound`) because `get_last_globally_accepted_block` misses the `LocallyAccepted` block; after applying the recommended fix (switching to `get_last_signed_block`), it must return `Err(RejectReason::DuplicateBlockFound)`, matching v2's behavior. Full exploitation to an actual double-signature would additionally require driving the pre-commit path (`handle_block_pre_commit`/`get_signed_conflicts`) in an integration test to determine conclusively whether that backstop already blocks the second signature — this part remains unverified.

/// Test that a tenure change proposal is rejected when a locally-accepted
/// (but not globally-accepted) block already exists in the same tenure.
///
/// This is a regression test: previously, the check used
/// `get_last_globally_accepted_block`, which would miss blocks in
/// `LocallyAccepted` or `PreCommitted` state and incorrectly allow
/// a duplicate tenure change.
#[test]
fn check_tenure_change_rejects_when_locally_accepted_block_exists() {
    let MockServerClient {
        server,
        client: stacks_client,
        config: _,
    } = MockServerClient::new();
    let rand_int = server.local_addr().unwrap().port();

    let (_stacks_client, mut signer_db, block_sk, mut block, cur_sortition, _, sortitions_view) =
        setup_test_environment(&format!("{}_{rand_int}", function_name!()));

    // Set up the block in the current tenure
    block.header.consensus_hash = cur_sortition.data.consensus_hash.clone();
    let parent_block_header = make_parent_header_meta(&block_sk, &mut block);
    let response = crate::client::tests::build_get_tenure_tip_response(&parent_block_header);

    // Insert a locally-accepted block in the same tenure (same consensus_hash).
    // This simulates a miner's first tenure-start block that the signer has
    // locally accepted but that hasn't yet gathered enough signatures to be
    // globally accepted. In practice this block would contain a tenure-change
    // and coinbase tx, but we omit them here because `get_last_accepted_block`
    // only queries by consensus_hash and block state — the block's transactions
    // are irrelevant to the duplicate check.
    let existing_block_proposal = BlockProposal {
        block: NakamotoBlock::new(
            NakamotoBlockHeader {
                version: 1,
                chain_length: 10,
                burn_spent: 10,
                consensus_hash: cur_sortition.data.consensus_hash.clone(),
                parent_block_id: StacksBlockId([0; 32]),
                tx_merkle_root: Sha512Trunc256Sum([0; 32]),
                state_index_root: TrieHash([0; 32]),
                timestamp: 11,
                miner_signature: MessageSignature::empty(),
                signer_signature: vec![],
                pox_treatment: BitVec::ones(1).unwrap(),
                problematic_txs: vec![],
            },
            vec![],
        ),
        burn_height: 2,
        reward_cycle: 1,
        block_proposal_data: BlockProposalData::empty(),
    };
    let mut existing_block_info = BlockInfo::from(existing_block_proposal);
    existing_block_info.mark_locally_accepted(false).unwrap();
    signer_db.insert_block(&existing_block_info).unwrap();

    // Now build a *second* tenure-start block proposal for the same tenure.
    // This simulates the miner attempting to replace their first block (e.g.,
    // with different transactions). The tenure change tx must have
    // cause=BlockFound with a coinbase to be recognized as a tenure-start block.
    let tenure_change_payload = TenureChangePayload {
        tenure_consensus_hash: cur_sortition.data.consensus_hash.clone(),
        prev_tenure_consensus_hash: cur_sortition.data.parent_tenure_id.clone(),
        burn_view_consensus_hash: cur_sortition.data.consensus_hash.clone(),
        previous_tenure_end: block.header.parent_block_id.clone(),
        previous_tenure_blocks: 1,
        cause: TenureChangeCause::BlockFound,
        pubkey_hash: Hash160::from_node_public_key(&StacksPublicKey::from_private(&block_sk)),
    };
    let tenure_change_tx = make_tenure_change_tx(tenure_change_payload);
    let coinbase_tx = StacksTransaction::new(
        TransactionVersion::Testnet,
        TransactionAuth::Standard(TransactionSpendingCondition::new_initial_sighash()),
        TransactionPayload::Coinbase(CoinbasePayload([0; 32]), None, Some(VRFProof::empty())),
    );
    *block.executed_and_skipped_txs_mut() = vec![tenure_change_tx, coinbase_tx];
    block.header.sign_miner(&block_sk).unwrap();

    let exit_flag = Arc::new(AtomicBool::new(false));
    let moved_exit_flag = exit_flag.clone();

    let serve = std::thread::spawn(move || {
        crate::client::tests::write_response_nonblockinig(
            &server,
            response.as_bytes(),
            moved_exit_flag,
        );
    });

    let result = sortitions_view.check_proposal(&stacks_client, &mut signer_db, &block);

    exit_flag.store(true, Ordering::SeqCst);
    serve.join().unwrap();

    // The proposal should be rejected because there's already a locally-accepted
    // block in this tenure. Before the fix, this would have incorrectly passed
    // because get_last_globally_accepted_block would not find the locally-accepted block.
    assert!(
        matches!(result, Err(RejectReason::DuplicateBlockFound)),
        "Expected DuplicateBlockFound rejection when a locally-accepted block exists in the tenure, got: {result:?}"
    );
}
