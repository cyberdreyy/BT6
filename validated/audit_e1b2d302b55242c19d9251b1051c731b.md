### Title
BlockRejection's self-declared `chain_id` domain separator is never checked against the receiver's actual network, enabling cross-context-valid rejection signatures - (File: libsigner/src/v0/messages.rs, stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`BlockRejection` computes its signing/verification hash from a SIP-018 structured-data domain that embeds a `chain_id` field taken directly from the message itself, rather than a chain_id known/enforced by the verifier:

```rust
pub fn hash(&self) -> Sha256Sum {
    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    ...
}
``` [2](#0-1) 

`self.chain_id` is set by the sender when the rejection is constructed (`CHAIN_ID_MAINNET` or `CHAIN_ID_TESTNET` based on the sender's own `mainnet` flag) [3](#0-2) , and is carried unchanged over the wire as part of the serialized message. Receivers only call `recover_public_key()`, which recomputes the hash using this attacker/sender-supplied `chain_id` field and checks the recovered key against the expected signer's public key — no explicit assertion that `chain_id` equals the receiver's own expected chain ID is performed on the consumer side (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`, `stacks-signer/src/v0/signer.rs`). This mirrors the reported bug class: a value meant to scope/validate a signed artifact into one context ("chainID") is taken at face value from untrusted input instead of being validated/derived independently by the verifier.

### Finding Description
`make_structured_data_domain` is SIP-018's domain-separation mechanism, intended so that a signature produced for one chain (e.g., a testnet deployment, or any other chain-id value) cannot be replayed as valid on another chain [4](#0-3) . For this separation to hold, the *verifier* must fix and check the expected chain_id independently — it must not trust an attacker-controlled field carried in the very message being verified.

In `BlockRejection`, the `chain_id` used to build the domain is a struct field populated by the constructor from the sender's local `mainnet` flag, but it travels with the message and is never independently re-derived or asserted by the receiving signer/node before the recovered public key is trusted:
- `BlockRejection::new`/`from_validate_rejection` set `chain_id` from the local `mainnet` bool [5](#0-4) .
- `hash()`/`verify()`/`recover_public_key()` all derive the signed message purely from `self.chain_id` (and `signer_signature_hash`) with no cross-check against the receiver's actual configured network [1](#0-0) .
- The node-side consumer (`stackerdb_listener.rs`) recovers the public key and compares only to the expected signer entry's key, tallying rejection weight if it matches — it never inspects or validates `rejected_data.chain_id` against the network's expected chain id [6](#0-5) .

Because `chain_id` is one of only two possible constants (`CHAIN_ID_MAINNET` / `CHAIN_ID_TESTNET`) in normal usage, and nothing forces the field to match the value the receiver would use, a signer's own key (recovered against a wrong-but-still-recognized chain_id) is still accepted as authenticating the rejection. This means a rejection cryptographically bound to one network's SIP-018 domain can be misattributed/accepted in a differently-configured verifier as a legitimate rejection for that signer, without the verifier ever confirming which "chain context" the signature was actually produced for.

### Impact Explanation
If a verifier does not enforce that `chain_id` matches its own expected network constant, a rejection message can be counted toward `total_weight_rejected` even though it was not produced under the domain the receiver believes it validated against. In the miner-coordinator's `stackerdb_listener.rs`, rejection weight is summed to decide when to abort a block proposal, and separately, acceptances are summed independently to decide when to declare the block signed — these two paths are otherwise supposed to be strictly reconciled with a well-defined domain per network. A break here falls under the "rejection recounted as an accept" / "cross-context-valid signature" class the task calls Critical, because it lets a signature that should only be valid in one chain context be treated as valid signer input in another, without needing a majority of signers or another signer's key — only the mismatch in domain validation needs to be exploitable by a single participant with a StackerDB write slot.

### Likelihood Explanation
This requires only a single participating signer (or a StackerDB slot writer) to submit a `BlockRejection` object with a `chain_id` field it controls, which is well within a single miner/signer's own message-construction path — no majority collusion or key compromise is needed. The main uncertainty is whether some other unseen call site (not found via the search performed) enforces `chain_id == expected constant` before trusting `recover_public_key()`'s result; I was unable to fully confirm the absence of such a check across the entire codebase within the given search budget, so this should be validated further, e.g. by grepping all callers of `BlockRejection::recover_public_key`/`verify` for an explicit `chain_id` comparison.

### Recommendation
Have the receiver assert `rejected_data.chain_id == expected_chain_id` (derived from the receiver's own mainnet/testnet configuration) before trusting the outcome of `recover_public_key()`/`verify()`, rather than trusting the `chain_id` value embedded in the untrusted message. This mirrors the recommended fix in the analog report: validate the context-defining field independently instead of trusting it as supplied by the message being verified.

### Proof of Concept
Not independently reproduced with a runnable test in this session; the finding is based on direct code inspection of `BlockRejection::hash/verify/recover_public_key` [1](#0-0)  and the consumer path in `stackerdb_listener.rs` [6](#0-5)  that never re-checks `chain_id` against the receiver's own network. A concrete PoC would construct two `BlockRejection` objects for the same `signer_signature_hash`, signing one with `CHAIN_ID_MAINNET` and one with `CHAIN_ID_TESTNET` using the same private key, and confirm both `recover_public_key()` calls return the same, valid signer pubkey with no rejection based on the differing `chain_id`, then demonstrate that a testnet-configured verifier still accepts/tallies a mainnet-domain-signed rejection weight (or vice versa) since no code path compares `chain_id` to the verifier's own expected constant.

        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }

// Helper function to generate domain for structured data hash
pub fn make_structured_data_domain(name: &str, version: &str, chain_id: u32) -> Value {
    Value::Tuple(
        TupleData::from_data(vec![
            (
                ClarityName::from_literal("name"),
                Value::string_ascii_from_bytes(name.into()).unwrap(),
            ),
            (
                ClarityName::from_literal("version"),
                Value::string_ascii_from_bytes(version.into()).unwrap(),
            ),
            (
                ClarityName::from_literal("chain-id"),
                Value::UInt(chain_id.into()),
            ),
        ])
        .unwrap(),
    )
}
