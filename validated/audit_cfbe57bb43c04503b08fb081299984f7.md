### Title
Buffer-period deposits mint tranche tokens at a `virtualPrice` that excludes accrued-but-unrealized interest, letting a late depositor harvest yield earned on earlier depositors' capital - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary

The external Blueberry bug is a *debt/value view that does not accrue pending interest*, so downstream logic (liquidation check, max-LTV check) operates on a stale, understated value. The idle-tranches analog is the mirror image on the asset side: `IdleCDOCreditVault`'s deposit/mint path prices tranche tokens using `virtualPrice` / `getContractValue`, which reflects only the last realized NAV (`lastNAV` written at `stopEpoch`), while `ProgrammableBorrower` keeps accruing real yield — vault PnL on the parked ERC-4626 sleeve and borrower contractual interest on carried `borrowerPrincipal` — that is deliberately *not* folded into the price until the next `stopEpoch` consumes `totalInterestDueNow()`. A KYC-passing lender can deposit during the buffer at the unaccrued price, receive shares as if that pending yield did not exist, and capture a slice of interest accrued entirely before they entered.

### Finding Description

`ProgrammableBorrower` accrues value continuously between epochs:

- `borrowerInterestAccruedNow()` returns `borrowerInterestAccrued + _pendingBorrowerInterest(borrowerPrincipal, lastBorrowerAccrual)` — interest keeps compounding on principal carried across epochs, regardless of epoch state.
- Vault PnL earned while the pool sits in the buffer is snapshotted at `onStopEpoch` (`bufferStartVaultAssets = _currentVaultAssets()`) and carried into the next epoch via `bufferedVaultDelta` in `onStartEpoch`, then realized into `lastEpochInterest` only at the *next* `stopEpoch`. The test `testProgrammableBorrowerBufferVaultYieldIsRealizedAtNextStop` confirms this: buffer yield raises `lastEpochInterest` at the following stop, not during the buffer.
- `totalInterestDueNow()` correctly aggregates `vaultInterest + borrowerInterestAccruedNow() + bufferInterest` — but this is only *read* by `IdleCDOEpochVariant` inside `stopEpoch`. The deposit path (`depositAA`/`depositBB` → `_deposit` → `_mintSharesAtCurrPrice` → `virtualPrice`/`getContractValue`) prices shares off realized NAV and never calls `totalInterestDueNow()` or any accrual.

The codebase even ships `IdleCreditVaultImpliedPrice.impliedVirtualPrice`, which exists precisely because `virtualPrice` understates NAV while interest accrues — it recomputes the price including `_accruedGain` from `totalInterestDueNow()`. But that corrected price is an off-chain/integration aid; the CDO's own mint path does not use it. The result is the Blueberry pattern inverted: `virtualPrice` is a "getDebtValue-equivalent" stale view, and `_mintSharesAtCurrPrice` is the "reducePosition/LTV check" that acts on it — the mint grants more tranche tokens than fair value because pending interest is invisible to pricing.

Broken invariant: fair mint/burn. Shares minted at `virtualPrice` during the buffer are claims on a NAV that is strictly larger than the price implies, by the amount of buffer-time vault yield plus borrower interest accrued since the last `stopEpoch`. When the next epoch stops and `totalInterestDueNow()` is realized, all tranche holders — including the attacker who deposited at the stale price — share that accrued yield pro-rata.

### Impact Explanation

Direct theft of unclaimed yield from existing tranche holders, quantified as:

```
stolen ≈ depositAmount × (accruedPendingYield / realizedNAV)
       ≈ depositAmount × (bufferVaultYield + borrowerInterestSinceLastStop) / poolNAV
```

For a facility with carried `borrowerPrincipal` at `borrowerApr`, the underpricing grows linearly with buffer length (`principal × apr/100 × elapsed / YEAR` per `_pendingBorrowerInterest`), plus any ERC-4626 vault yield on the parked sleeve. The attacker deposits near the end of the buffer (or immediately before `startEpoch` in a programmable facility where yield accrues continuously), waits for the next `stopEpoch` to realize the pending interest into tranche price, and withdraws/redeems at the inflated price. Loss to honest holders equals the dilution: they minted at fair price earlier and now share pre-entry yield with the attacker.

### Likelihood Explanation

- Attacker requirement is only a KYC-passing lender (`isWalletAllowed`/`KeyringIdleWhitelist`), which is an explicitly permitted attacker class.
- No privileged action is needed; `depositAA`/`depositBB` during the buffer is a normal user flow (`depositDuringEpoch` in prefunded variants covers the analogous path).
- Conditions: a buffer period during which (a) the vault sleeve earns yield, or (b) `borrowerPrincipal > 0` carries across the epoch boundary accruing `borrowerApr` — the latter is a normal state per `testProgrammableBorrowerBorrowInOneEpochAndRepayInNextEpoch`, where principal explicitly "carries into the next epoch."
- Existing guards do not stop it: deposits are not blocked during buffer (that is when deposits are intended), there is no skim for this yield (it is legitimately pool-facing, just not priced), and `virtualPrice` cannot include it because the realization is hard-wired to `stopEpoch`. `IdleCreditVaultImpliedPrice` demonstrates the protocol itself treats unaccrued `virtualPrice` as a known gap — but only for external viewers, not for its own mint.

### Recommendation

Price buffer-period mints at the accrued NAV, not `virtualPrice`. Two options:

1. Realize pending yield into `lastNAV`/tranche price at `startEpoch` (or before any deposit is accepted in the buffer) by settling `totalInterestDueNow()`-equivalent accounting on the boundary, so `virtualPrice` reflects all accrued value before new shares are minted.
2. Alternatively, route `_mintSharesAtCurrPrice` through the same accrued-gain adjustment `IdleCreditVaultImpliedPrice` computes (`_accruedGain` + `_trancheGain`), so the mint price includes buffer-time vault PnL and pending borrower interest — but ensure borrower-side `borrowerInterestAccrued` is checkpointed (`_accrueBorrowerInterest`) in the same transaction to avoid re-oracles between accrual and mint.

Option 1 is simpler and consistent with the existing "realize at stop" accounting model.

### Proof of Concept

Foundry fork test skeleton (mirroring `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup: real Morpho-style ERC4626 vault, `isInterestMinted`, programmable borrower with carried principal):

```solidity
function testBufferDepositStealsAccruedYield() external {
    uint256 amount = 10_000 * oneScale;
    uint256 drawAmount = 4_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    // Honest LP seeds the pool, epoch 0 runs, borrower draws
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);
    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(drawAmount);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    _accrueMorphoVaultInterest();
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);   // epoch-0 interest realized

    // ---- BUFFER: principal carried, interest + vault yield keep accruing ----
    vm.warp(block.timestamp + 30 days);        // long buffer
    _accrueMorphoVaultInterest();

    uint256 pendingYield =
        programmableBorrower.borrowerInterestAccruedNow()      // keeps running on carried principal
        + (_programmableVaultAssets() - programmableBorrower.bufferStartVaultAssets());
    assertGt(pendingYield, 0, "buffer yield exists");

    uint256 pricePre = cdoEpoch.virtualPrice(address(aaTranche)); // stale: excludes pendingYield

    // Attacker: KYC'd lender deposits during buffer at stale price
    uint256 attackDeposit = 10_000 * oneScale;
    deal(USDC, attacker, attackDeposit, true);
    vm.startPrank(attacker);
    IERC20Detailed(USDC).approve(address(idleCDO), attackDeposit);
    uint256 attackerShares = idleCDO.depositAA(attackDeposit);   // minted at pricePre
    vm.stopPrank();

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _accrueMorphoVaultInterest();
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);   // pendingYield now realized into tranche price

    uint256 pricePost = cdoEpoch.virtualPrice(address(aaTranche));
    assertGt(pricePost, pricePre, "price realized buffer yield");

    // Attacker redeems and captures a pro-rata slice of pre-entry yield
    uint256 attackerValue = attackerShares * pricePost / ONE_TRANCHE_TOKEN;
    assertGt(attackerValue, attackDeposit, "attacker minted below fair NAV and captured prior yield");
}
```

Key assertion: `attackerValue - attackDeposit > 0` equals attacker's pro-rata share of `pendingYield`, i.e. yield accrued entirely on capital deposited before the attacker entered — a fair-mint invariant violation analogous to Blueberry's unaccrued `getDebtValue` letting users act against an understated balance.
