### Title
Missing allowlist/quota enforcement in `HandleLegacyUserMessage` allows any signer to consume DON node resources - (`core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`handler.HandleLegacyUserMessage` validates message structure, payload freshness, and method name, then forwards the request to every DON member via `don.SendToNode`, but performs no allowlist or per-sender quota check before doing so. The only upstream check, `msg.Validate()` in `gateway.ProcessRequest`, validates the message signature format/well-formedness, not sender identity against any allowlist, meaning any address capable of producing a validly-formed signed message can trigger DON-wide fan-out of `MethodWebAPITrigger` requests.

### Finding Description
The gateway's HTTP entrypoint `gateway.ProcessRequest` [1](#0-0)  routes legacy (DON-ID-bearing) requests through `msg.Validate()` and then calls `h.HandleLegacyUserMessage(ctx, msg, callback)` [2](#0-1) . Inside `HandleLegacyUserMessage`, the handler decodes the payload, rejects stale messages, and checks the method equals `MethodWebAPITrigger` — but directly above that check sits the explicit marker `// TODO: apply allowlist and rate-limiting here` [3](#0-2) . Immediately after, regardless of sender identity, the handler builds the request via `common.ValidatedRequestFromMessage(msg)` and unconditionally loops over `h.donConfig.Members`, calling `don.SendToNode` for every member node [4](#0-3) . There is no lookup against a per-DON or per-workflow allowlist of authorized sender addresses at this stage — the `nodeRateLimiter` field that exists on `handler` is only invoked in `handleWebAPIOutgoingMessage`, which applies to node-to-gateway traffic (rate-limiting outbound HTTP requests triggered by nodes), not to inbound user messages being fanned out to nodes [5](#0-4) . Consequently, any party capable of constructing a validly-formatted signed `MethodWebAPITrigger` message — including an entirely unauthorized/freshly-generated EOA never registered with the DON — can have the gateway forward the request to every node in `donConfig.Members`, consuming those nodes' processing resources and any per-workflow trigger quota intended for legitimate allowlisted senders.

### Impact Explanation
This matches the "unauthorized job run" / resource-exhaustion class: an unprivileged, non-allowlisted signer can force the gateway to broadcast trigger messages to all DON member nodes, consuming node compute/bandwidth and potentially triggering workflow executions or callback registrations (`savedCallbacks`) that are meant to be gated by an allowlist. Because this is DON-wide fan-out per request, it also opens a resource-exhaustion vector on the entire DON.

### Likelihood Explanation
No credential beyond the ability to sign a well-formed message (any valid EOA key, freely generated, no registration needed) is required, since `msg.Validate()` upstream only enforces the message's own structural/signature validity, not sender authorization. This makes the issue trivially and repeatably exploitable by an unauthenticated remote attacker.

### Recommendation
Implement the allowlist and rate-limiting check explicitly called out by the TODO comment before dispatching to `don.SendToNode`: look up `msg.Body.Sender` (recovered from `msg.Signature`) against a configured per-DON/per-workflow allowlist and reject/`SendResponse` with an authorization error if not present; additionally apply a per-sender rate limiter (similar to `nodeRateLimiter`) scoped to inbound legacy user messages before fan-out.

### Proof of Concept
Go handler-level test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` via `NewHandler` with a `donConfig.Members` list and a mock `handlers.DON`.
2. Generate a fresh, never-configured/never-allowlisted ECDSA keypair.
3. Build a well-formed `api.Message` with `Body.Method = MethodWebAPITrigger`, a valid `webapicap.TriggerRequestPayload` (fresh `Timestamp`), and sign it with the unauthorized keypair (so `common.ValidatedRequestFromMessage` succeeds).
4. Call `h.HandleLegacyUserMessage(ctx, msg, callback)`.
5. Assert `mockDON.SendToNode` was invoked once per `donConfig.Members` entry (e.g., via `mock.AssertExpectations`/call count), and that no allowlist-rejection error/response was returned — proving requests from an unauthorized signer reach `don.SendToNode` unimpeded.
