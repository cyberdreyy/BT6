### Title
`getSupply` RPC computes `circulating = total_supply - non_circulating_supply.lamports` as a non-saturating subtraction of two values read from a mutating live bank at different instants - ([File: rpc/src/rpc.rs])

### Summary
The reported RushRouterAlpha bug is a fee-calculation subtraction/ratio built from two logically-related quantities (`totalLiquidity` snapshot vs. `outstandingLiquidity + newLiquidity` live values) that are read at different times, so the difference can go outside its expected bounds (>100%). The analogous pattern in agave is the `getSupply` JSON-RPC handler, which subtracts two quantities derived from the same `Bank` but sampled at different points while the bank can still be actively mutated.

### Finding Description
`JsonRpcRequestProcessor::get_supply` fetches a bank via `self.bank(config.commitment)` and then computes: [1](#0-0) 

```
let bank = self.bank(config.commitment);
let non_circulating_supply = self.calculate_non_circulating_supply(&bank).await...?;
let total_supply = bank.capitalization();
...
circulating: total_supply - non_circulating_supply.lamports,
``` [2](#0-1) 

`calculate_non_circulating_supply` walks all stake-program accounts and sums their *current* live balances via `bank.get_balance(pubkey)` for each pubkey in a list gathered from a scan, which can take a non-trivial time for a large validator set: [3](#0-2) [4](#0-3) 

`total_supply = bank.capitalization()` is then read *after* this scan completes, from an `AtomicU64` on the same `Bank`. Crucially, for `processed`/`confirmed` commitment, `self.bank(commitment)` does not return an immutable, frozen snapshot — it returns the currently "heaviest"/working or optimistically-confirmed bank, which can still be actively receiving new transactions from replay/banking stage while the RPC scan is running: [5](#0-4) 

Because `capitalization()` and the per-account `get_balance()` calls are independent, non-atomic reads against a bank that is concurrently mutating (fee burns can *decrease* capitalization, transfers move balances between accounts), it is not guaranteed that `total_supply` (final read) is always `>=` the sum of `non_circulating_supply.lamports` (partial reads taken earlier/at various points during the scan). The subtraction `total_supply - non_circulating_supply.lamports` is a **plain, non-saturating `u64` subtraction** — unlike the near-identical `/v0/circulating-supply` REST handler which correctly uses `saturating_sub`: [6](#0-5) 

This mirrors the audited bug class exactly: two related numeric quantities are sourced from an evolving, live state at different times and combined via unguarded arithmetic, so the invariant `non_circulating <= total` that the author assumed can be violated.

### Impact Explanation
If the underflow occurs, in a release build with wrapping arithmetic the `circulating` field returned by `getSupply` silently wraps to a near-`u64::MAX` value — wrong-data misreporting to any unprivileged client calling this public JSON-RPC method. If the validator is built/run with overflow checks enabled (e.g., debug builds, or any node running with `-C overflow-checks=on`), the same code path panics the RPC worker thread on an ordinary, unauthenticated `getSupply` call, which is a validator crash triggered by a single unprivileged JSON-RPC request.

### Likelihood Explanation
`getSupply` is public, unauthenticated, requires no special account state, and iterates over all stake accounts in `calculate_non_circulating_supply`, which naturally takes measurable wall-clock time on a live cluster with thousands of stake accounts — during which the "processed"/"confirmed" working bank keeps advancing (new transactions, fee burns) as documented in `bank()`. This is a normal, always-present race window rather than a contrived edge case, though triggering the specific underflow requires the race to land in the unfavorable direction (capitalization decreasing, e.g., via fee burn, faster than balances are summed), so it is probabilistic rather than deterministic on every call.

### Recommendation
Use `total_supply.saturating_sub(non_circulating_supply.lamports)` in `get_supply` (matching the existing `calculate_circulating_supply_async` helper), and/or capture `total_supply = bank.capitalization()` before starting the non-circulating scan (or use a single frozen/consistent bank snapshot for both reads) so the two quantities are never derived from different points in a mutating state.

### Proof of Concept
1. Run against a bank/commitment level that returns the actively-updating working bank (`processed` or `confirmed`), i.e., `self.bank(commitment)` per [7](#0-6) .
2. Concurrently with an unprivileged client repeatedly calling `getSupply`, have transaction fees be partially burned (a normal validator operation) or otherwise decrease `bank.capitalization()` while the `calculate_non_circulating_supply` scan (which sums live stake-account balances one by one) is still in flight.
3. Because `total_supply = bank.capitalization()` is read only after the scan and via plain subtraction, `total_supply - non_circulating_supply.lamports` underflows once the accumulated non-circulating sum (read from earlier, higher-capitalization moments) exceeds the final, lower `total_supply` reading, producing either a panic (overflow-checked build) or a bogus near-`u64::MAX` "circulating supply" value (release build) — both from a single unauthenticated `getSupply` call.

    fn bank(&self, commitment: Option<CommitmentConfig>) -> Arc<Bank> {
        debug!("RPC commitment_config: {commitment:?}");

        let commitment = commitment.unwrap_or_default();
        if commitment.is_confirmed() {
            let bank = self
                .optimistically_confirmed_bank
                .read()
                .unwrap()
                .bank
                .clone();
            debug!("RPC using optimistically confirmed slot: {:?}", bank.slot());
            return bank;
        }

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

async fn calculate_circulating_supply_async(bank: &Arc<Bank>) -> Result<u64, SupplyCalcError> {
    let total_supply = bank.capitalization();
    let bank = Arc::clone(bank);
    let non_circulating_supply =
        tokio::task::spawn_blocking(move || calculate_non_circulating_supply(&bank))
            .await
            .expect("Failed to spawn blocking task")
            .map_err(|e| SupplyCalcError::Scan(e.to_string()))?;

    Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
