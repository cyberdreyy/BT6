### Title
Loss haircut applies only to the latest request epoch — older pending withdraw receipts escape `lossRecoveryPriceByEpoch` and claim at par from an underfunded pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the uniget path traversal (an unsanitized index reaching outside its intended scope), `IdleCreditVault` resolves a user's loss-adjusted receipt through a single epoch pointer, `lastWithdrawRequest[_user]`. When `collectWithdrawFunds` records a stop-epoch loss in `lossRecoveryPriceByEpoch[epochNumber]`, the haircut is computed against the *entire* `pendingWithdraws` aggregate, but `_claimLossAdjustedWithdrawRequest` only clears receipts recorded under `withdrawsRequestsByEpoch[_user][lastWithdrawRequest[_user]]`. Pending receipts booked in earlier epochs are never haircut and are later paid at par through `_claimFundedWithdrawRequest`, draining funds that were only partially funded by the borrower.

### Finding Description
- `collectWithdrawFunds(_amount)` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the whole `pendingWithdraws`, zeroes `pendingWithdraws`, and stores the price only at `lossRecoveryPriceByEpoch[epochNumber]` (lines 411-421).
- `requestWithdraw` accumulates per-epoch receipts in `withdrawsRequestsByEpoch[_user][currentEpoch]` while overwriting `lastWithdrawRequest[_user] = currentEpoch` each call (lines 282-293), so a user can hold receipts across multiple epochs in the single `pendingWithdraws` bucket.
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and calls `_clearWithdrawClaimForEpoch(_user, lossEpoch, false)`, which clears *only* `withdrawsRequestsByEpoch[_user][lossEpoch]` and leaves the aggregate `withdrawsRequests[_user]` reduced by just that epoch's amount (lines 789-800, 815-820).
- The user then falls through to `claimWithdrawRequest`'s tail: `amount += _claimLossAdjustedWithdrawRequest(_user); return amount + _claimFundedWithdrawRequest(_user);` (line 312-313), where `_claimFundedWithdrawRequest` pays the *remaining* `withdrawsRequests[_user]` — i.e. the older-epoch receipts — at par via `_transferFundedClaim` (lines 338-349).

The broken invariant is the loss waterfall: a stop-epoch loss is socialized across all pending receipts pro rata, but only receipts in the user's most recent request epoch actually bear the haircut.

### Impact Explanation
Direct theft / insolvency among pending withdrawers. The vault holds only `_amount = pendingBasis * lossRecoveryPrice / RECOVERY_FULL` to cover all pending receipts. A user whose receipts span multiple epochs receives haircut on the newest-epoch portion but 100% on older portions. Every wei over-paid to such a user is a wei missing for later claimers; the last claimants' funded claims revert or underpay (permanent loss of their funded share). In a mixed-user scenario the same applies across users: any user whose *only* receipts sit in an epoch different from `epochNumber` at the loss stop (e.g. `lastWithdrawRequest` < `epochNumber` because `epochNumber` was bumped before `collectWithdrawFunds` ran) skips the loss path entirely when `lossRecoveryPriceByEpoch[lossEpoch] == 0` and claims fully at par.

### Likelihood Explanation
Requires a `stopEpochWithDuration`/`stopEpoch` with `_lossAmount > 0` while `pendingWithdraws` contains receipts from more than one epoch — a routine state: the in-code comment at lines 323-324 explicitly documents that users commonly stack requests across epochs ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests"). The attacker needs only to be a KYC-passing lender making two `requestWithdraw` calls in different epochs before a lossy stop; the borrower/manager remain honest. Guard at lines 263-271 does not help — it only blocks *new* requests after a loss is already recorded, not pre-existing multi-epoch receipts.

### Recommendation
Track per-epoch loss prices correctly for every pending receipt. Options: (a) iterate all epochs in which the user holds receipts, or store a per-user list of pending epochs, and apply each epoch's `lossRecoveryPriceByEpoch` to `withdrawsRequestsByEpoch[_user][e]`; (b) simplest: on `collectWithdrawFunds` loss, fold the haircut into the aggregate `withdrawsRequests[_user]` proportionally at claim time (e.g. store a global `lastLossRecoveryPrice` and multiply the *entire* remaining `withdrawsRequests[_user]`, not just the latest-epoch slice), while keeping `pendingWithdraws = 0`. Also extend the guard at lines 263-271 to detect any unclaimed loss-adjusted epoch, not just `lastWithdrawRequest[_user]`.

### Proof of Concept
Foundry fork test (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testLossAdjustedClaimEscapesHaircutAcrossEpochs() external {
    uint256 amountWei = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amountWei);
    idleCDO.depositBB(amountWei);

    // Epoch 0: run and stop normally
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Buffer: request withdraw in epoch N
    uint256 req1 = cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));

    // Epoch 1: run and stop normally -> req1 funded, still unclaimed
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Buffer: same user stacks a second request in epoch N+1
    uint256 req2 = cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));

    // Epoch 2: stopEpochWithDuration with a loss -> borrower underfunds pendingWithdraws.
    // collectWithdrawFunds sets lossRecoveryPriceByEpoch[epochNumber] < RECOVERY_FULL
    // computed over req1 + req2, and transfers only the haircutted amount in.
    _startEpochAndCheckPrices(2);
    // manager triggers stopEpochWithDuration with _lossAmount covering e.g. 50% of pending
    // ...

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // Expected (fair): (req1 + req2) * lossRecoveryPrice / RECOVERY_FULL
    // Actual: req2 * lossRecoveryPrice / RECOVERY_FULL + req1  (req1 paid at par)
    assertGt(paid, (req1 + req2) * strategy.lossRecoveryPriceByEpoch(epoch) / 1e18);
}
```

The assertion shows `req1` (booked in the earlier epoch) escapes the haircut while drawing from the same underfunded pool; subsequent claimers' `_transferFundedClaim` calls revert on insufficient balance, i.e. the attacker is paid with other pending withdrawers' share. One caveat I could not fully verify within the iteration budget: whether `epochNumber` increments inside `stopEpoch` before or after `collectWithdrawFunds` — either ordering preserves the bug for multi-epoch receipts, but the exact epoch index written should be confirmed against `IdleCDOEpochVariant.stopEpoch` when writing the final PoC.
