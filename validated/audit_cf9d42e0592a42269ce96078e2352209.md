### Title
Post-default withdraw receipts and defaulted-epoch receipts share `defaultRecoveryReserve` without namespace isolation, letting new claimants drain recovery funds at par - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Keycloak flaw is a shared single-use store where a key minted in one namespace is redeemable in another, producing a forged "authorization code." The analog in `IdleCreditVault` is `defaultRecoveryReserve`: `finalizeDefaultRecovery` sizes this reserve to satisfy defaulted-epoch receipts at the haircut `defaultRecoveryPrice`, but post-`defaultRecoveryFinalized` `requestWithdraw` mints an entirely new receipt type (`postDefaultRequests`) that is redeemed from the *same* reserve at 1:1. Like the missing type/namespace check in `SingleUseObjectProvider`, the claim path does not isolate "old defaulted receipts" from "newly forged post-default receipts," so the new receipt spends budget provisioned for someone else.

### Finding Description
Two receipt namespaces funnel into one payout pot:

1. `requestWithdraw` post-finalization path (`IdleCreditVault.sol:247-257`): after `defaultRecoveryFinalized`, any tranche holder with no open requests calls `requestWithdraw` via the CDO. The CDO burns `_principal` and the vault mints `_amount` receipt tokens and records `postDefaultRequests[_user] = _amount`. Critically, this path does **not** increase `pendingWithdraws` (the comment at line 252 says "without increasing borrower-facing pendingWithdraws") and no underlying is transferred in. The only justification is that `_amount` is "already-haircut" because finalization lowered `virtualPrice` — i.e., the *denomination* of the claim is discounted, but the payout is not.

2. `_claimPostDefaultWithdrawRequest` (`IdleCreditVault.sol:760-767`): pays `amount` 1:1 via `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` (`IdleCreditVault.sol:912-917`).

3. Defaulted-epoch claims (`_claimDefaultedWithdrawRequest`, `IdleCreditVault.sol:772-784`; `_claimDefaultedInstantWithdrawRequest`, `:842-856`) draw from the same `defaultRecoveryReserve`, each paying `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`.

The reserve is provisioned at finalization to cover `Σ(claimBasis_i * price)` for the default-epoch claim set. `postDefaultRequests` are never added to any provisioning: no `pendingWithdraws` bump, no `collectWithdrawFunds` funding, no reserve top-up. So every post-default claim minted after finalization is an unbudgeted draw on the reserve — a receipt minted in the "post-default" namespace redeemable in the "defaulted-epoch" namespace at full value.

### Impact Explanation
Broken invariant: one receipt one payout / solvency of the recovery reserve. An attacker who acquires tranche tokens after the default (at the post-default haircut market price) calls `requestWithdraw` to mint a `postDefaultRequests` receipt of `X` (underlying-denominated at the lowered virtualPrice), then `claimWithdrawRequest` pays `X` *at par* from `defaultRecoveryReserve`. Cost to attacker: tranches worth `X * defaultRecoveryPrice / RECOVERY_FULL` on the impaired market. Proceeds: `X`. Direct theft of `(1 − recovery price) * X`, funded by legitimate defaulted-epoch claimants. Once the attacker drains the reserve, `defaultRecoveryReserve -= _amount` underflows and honest claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` revert — their recovery is both stolen and permanently unclaimable.

### Likelihood Explanation
- Attacker profile is unprivileged: any tranche-token holder; KYC/`isWalletAllowed` is satisfied by an existing lender or by buying tranches on the open market post-default.
- No privileged collusion needed: borrower default and `finalizeDefaultRecovery` are honest calls; the attacker simply sequences `requestWithdraw` → `claimWithdrawRequest` after finalization.
- Guards do not stop it: `_onlyIdleCDO` is satisfied via the CDO's public `requestWithdraw`; the `_hasWithdrawRequest || instantWithdrawsRequests || postDefaultRequests` check (lines 249-251) only gates *repeat* requests per user, not the unbudgeted reserve draw; `_transferFundedClaim`'s reserve guard protects the reserve from *funded* claims but `_transferDefaultRecovery` intentionally bypasses it for post-default claims.
- Requires the vault to reach `defaultRecoveryFinalized` with non-zero reserve — a normal defaulted-pool state.

### Recommendation
Isolate the two claim namespaces the same way Keycloak's fix isolated `SingleUseObjectProvider` keys: give post-default receipts their own funding budget. Concretely, in the post-default branch of `requestWithdraw` either (a) fund the reserve atomically — require the CDO to transfer `amount` underlying (or `amount`-worth sourced from remaining borrower repayments) into the vault and add it to a separate `postDefaultReserve` that `_claimPostDefaultWithdrawRequest` decrements instead of `defaultRecoveryReserve`; or (b) reject post-default `requestWithdraw` entirely once `defaultRecoveryFinalized` is set, forcing users to sell tranches on the secondary market rather than minting unprovisioned claims against recovery funds.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` fixtures):

```solidity
// Setup: running epoch with attacker + victim deposits in AA tranche.
// 1) manager stops epoch with borrower underfunding -> cdoEpoch.defaulted() == true
// 2) owner/manager calls finalizeDefaultRecovery so that
//    defaultRecoveryFinalized == true and defaultRecoveryReserve = R
//    sized only for default-epoch claims at defaultRecoveryPrice < RECOVERY_FULL.
//
// 3) Attacker (fresh EOA) buys AAtranche on the market post-default at
//    the haircut price. Amount of tranches T corresponds to underlying
//    claim basis X = T * virtualPrice / ONE_TRANCHE (post-haircut).

uint256 reservePre   = strategy.defaultRecoveryReserve();
uint256 victimBasis  = /* victim's withdrawsRequestsByEpoch[user][defaultEpoch] */;

vm.prank(attacker);
uint256 amt = cdoEpoch.requestWithdraw(T, address(AAtranche));
// postDefaultRequests[attacker] == amt; no underlying enters the vault,
// pendingWithdraws unchanged.

vm.prank(attacker);
cdoEpoch.claimWithdrawRequest(...); // routes to _claimPostDefaultWithdrawRequest
assertEq(strategy.postDefaultRequests(attacker), 0);
// attacker received amt *at par* from defaultRecoveryReserve
assertEq(strategy.defaultRecoveryReserve(), reservePre - amt);
// attacker profit = amt - costOf(T) where costOf(T) ~= amt * defaultRecoveryPrice/RECOVERY_FULL

// 4) Victim tries to claim their defaulted-epoch receipt:
vm.prank(victim);
vm.expectRevert(); // underflow on defaultRecoveryReserve -= amount
cdoEpoch.claimWithdrawRequest(...); // victim's haircut recovery is unclaimable
```

Expected result: `defaultRecoveryReserve` falls below `Σ remaining defaulted claims × defaultRecoveryPrice`; attacker's payout is at `RECOVERY_FULL` while their tranche cost was haircut-priced; final claimant reverts — direct theft plus permanent freezing of remaining unclaimed recovery.

Caveat: the index did not expose the body of `finalizeDefaultRecovery`, so I could not verify whether the reserve is deliberately over-provisioned to include future post-default requests. From the code read (`requestWithdraw` at lines 252-256 explicitly avoids `pendingWithdraws`, and `_claimPostDefaultWithdrawRequest` unconditionally decrements `defaultRecoveryReserve`), no such provisioning appears to exist; the PoC should confirm by asserting `defaultRecoveryReserve` immediately after finalization equals exactly the sum of defaulted-epoch haircut claims.
