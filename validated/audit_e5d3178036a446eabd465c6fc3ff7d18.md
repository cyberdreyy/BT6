## Analysis

The Cork Protocol bug pattern — a value counted into one bucket that is never retracted/cleared when circumstances change, leaving it permanently "stuck" and miscounted — has a direct analog in the node-side signer weight tallying in `StackerDBListener`.

### Title
Stale rejection weight is never retracted when a signer flips to acceptance, letting the miner discard a validly-signed block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run()` tallies per-block signer weight in two independent counters, `total_weight_approved` and `total_weight_rejected`, guarded by two different, asymmetric membership checks. A single signer that first rejects and later accepts the *same* block (a normal, legitimate state transition of the signer's local state machine) has its weight counted into **both** totals permanently, because the acceptance path never removes/adjusts the previously recorded rejection weight.

### Finding Description
For `BlockResponse::Accepted`, the weight is added only if the slot is not already present in `gathered_signatures`: [1](#0-0) 

For `BlockResponse::Rejected`, the weight is added only if `responded_signers.insert(slot_id)` succeeds (i.e., first time this slot responds at all): [2](#0-1) 

The acceptance path *always* inserts into `responded_signers` after adding weight, so an accept-then-reject sequence is correctly guarded (the later `Rejected` message is skipped because `responded_signers.insert` returns `false`). But the acceptance path itself never checks `responded_signers`; it only checks `gathered_signatures`. So a **reject-then-accept** sequence for the same signer/slot is not guarded at all:

1. Signer S rejects block B: `responded_signers.insert(slot)` → `true`, `total_weight_rejected += S.weight`.
2. Signer S later re-evaluates and accepts B (a documented, legitimate transition — `LocallyRejected → LocallyAccepted: re-evaluated` in the block lifecycle): `gathered_signatures` does not yet contain `slot`, so `total_weight_approved += S.weight` is added anyway, and `responded_signers.insert(slot)` becomes a no-op.

`S`'s weight is now permanently counted in *both* `total_weight_rejected` and `total_weight_approved` for block B — the old rejection weight is never cleared, exactly analogous to `VaultPoolLib::reserve()` storing the leftover `Pa` and never dealing with it again once "rationed."

### Impact Explanation
`SignerCoordinator::wait_for_supermajority` (or the equivalent coordinator loop) checks rejection **before** approval: [3](#0-2) 

If enough signers independently reject-then-accept the same block (e.g. because their first validation attempt raced a transient/re-evaluable rejection reason before settling on acceptance, per `should_reevaluate_reject_reason` in the proposal-handling flow), the stale, uncleaned `total_weight_rejected` can cross the blocking-minority threshold even though the *real*, current tally of accepting signers has independently also reached the approval threshold. Because the rejection branch is evaluated first, the miner/coordinator will treat a block that in truth has valid supermajority signatures as globally rejected, discarding legitimately gathered signatures (`block_status.gathered_signatures`) and returning `NakamotoNodeError::SignersRejected`. This is a liveness wedge on block production: a properly signed, canonical block can be spuriously dropped by the coordinator due to phantom double-counted rejection weight from signers that already flipped to acceptance.

### Likelihood Explanation
This requires only ordinary, single-signer state-machine behavior (no majority collusion, no forged signatures, no auth bypass): any signer whose block verdict transitions from `LocallyRejected` to `LocallyAccepted` for the same `signer_signature_hash` — a transition explicitly supported by the signer's own state machine (`BlockInfo::check_state`, `mark_locally_rejected`/`mark_locally_accepted`) — triggers the double count. This can plausibly happen under normal network conditions (e.g., a transient validation reject reason such as `ReorgNotAllowed` becoming re-evaluable once chain state updates), making it reachable without any adversarial majority.

### Recommendation
Track a single "current verdict" state per slot (not two independently-incremented counters), or, when the `Accepted` path adds weight, first check `responded_signers` and — if the slot previously contributed to `total_weight_rejected` (and, symmetrically, to `failed_txids` entries) — subtract that weight before adding it to `total_weight_approved` (and vice-versa for a hypothetical accept→reject flip that is currently correctly blocked only by coincidence of the insertion order). The safest fix is to store the signer's most recent verdict and recompute both totals from that map rather than accumulating in two independently-guarded running counters.

### Proof of Concept
1. Reward set with weight_threshold requiring signer S's weight to tip the balance.
2. Signer S broadcasts `BlockResponse::Rejected` for block B (e.g. transient `ReorgNotAllowed`) → `stackerdb_listener` records `total_weight_rejected += S.weight`, `responded_signers = {S}`.
3. S's local state re-evaluates (chain state advances, reject reason becomes stale) and S broadcasts `BlockResponse::Accepted` for the same B → `stackerdb_listener` sees `gathered_signatures` does not contain S, so `total_weight_approved += S.weight` is added; `responded_signers.insert(S)` is a no-op; `total_weight_rejected` is **not** decremented.
4. If enough other signers accept normally, `total_weight_approved` crosses `weight_threshold` while `total_weight_rejected` (inflated by S's stale weight) also crosses the blocking-minority threshold.
5. In `signer_coordinator.rs`'s loop, the rejection branch is checked first, so the coordinator returns `SignersRejected` and drops a block that in truth carries a valid supermajority of live signatures.
