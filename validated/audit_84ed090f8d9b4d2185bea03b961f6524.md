### Title
Miner can perpetually suppress the tenure-inactivity timeout by resending conflicting block proposals, wedging signers from ever falling back to a healthy prior miner - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` calls `signer_db.update_last_activity_time` every time a conflicting or lower-height proposal for the current tenure arrives, resetting the same `last_activity_time` counter that `SortitionState::is_timed_out` uses to decide whether the tenure's miner has gone inactive. A miner (or anyone able to get the signer to see a conflicting proposal for the tenure) can keep resetting this timer with negligible-cost, rejected/no-op proposals faster than `block_proposal_timeout`, so the timeout that is supposed to demote an unresponsive/malicious miner and fall back to the prior tenure never fires — mirroring how the LiquidityPool bug let an attacker repeatedly reset `totalBorrowsSnapshotTimestamp` with free zero-amount calls.

### Finding Description
`SortitionState::is_timed_out` (v1 and v2) measures `elapsed = now - last_activity`, where `last_activity` falls back to the burn-block receive time only if no `tenure_activity` row exists, and is otherwise whatever was last written by `update_last_activity_time`: [1](#0-0) 

The only writer of that value is `check_latest_block_in_tenure`, which is invoked from the block-proposal path every time a new proposal for the tenure is evaluated. Two branches call `update_last_activity_time(consensus_hash, now)` whenever a *conflicting* (same-or-lower chain length) proposal is seen — one for a conflict with a locally/globally accepted block within `reorg_attempts_activity_timeout`, and one for a conflict with a fresh pre-commit: [2](#0-1) 

Both call sites are reachable purely by the tenure's own miner resending a proposal — signed with the miner's own key, requiring no majority, no other signer's key, and no node validation success (the proposal is simply rejected as non-advancing, but the rejection itself still counts as "activity"). `check_miner_inactivity` in `v0/signer_state.rs` uses exactly this same `is_timed_out` result as the sole gate for whether to demote the current miner and fall back to the prior tenure: [3](#0-2) 

Because `update_last_activity_time` is an unconditional `INSERT OR REPLACE` keyed only by `consensus_hash` with no rate limiting or cost: [4](#0-3) 

a miner that has stalled tenure progress (e.g., it will never actually produce/finalize a valid block, or is deliberately withholding one) can keep the appearance of "activity" alive indefinitely by re-broadcasting the same or slightly modified non-advancing block proposal faster than `reorg_attempts_activity_timeout`/`block_proposal_timeout`. This is directly analogous to the reported bug: repeated cheap calls (`borrow(0)` there, a resent conflicting `BlockProposal` here) keep resetting a snapshot timestamp that a downstream time-delta calculation depends on, defeating the intended semantics of that calculation (interest accrual there, inactivity detection here).

### Impact Explanation
This breaks the liveness guard documented explicitly in the code comments for `is_timed_out`: a pre-commit (with no signature) must not suppress the timeout "or the tenure can stall indefinitely... they could never fall back to the prior miner and the tenure could never recover." The `update_last_activity_time` calls in `check_latest_block_in_tenure` reintroduce exactly the stall the comment warns against, but via a different code path (conflicting proposals rather than pre-commits): the current miner can generate this "activity" without ever crossing the pre-commit or signature threshold. The signer set is wedged into waiting on a miner that will never produce an acceptable block, unable to fall back to the previously-active miner — matching the High-impact category of "a signer wedged into never signing valid blocks... or losing the equivocation guard," here manifesting as an indefinite tenure stall/loss of liveness.

### Likelihood Explanation
Medium-High. This requires only the tenure's own miner (a single actor, no majority, no other signer's key) to keep sending signed-but-non-advancing block proposals at an interval below `reorg_attempts_activity_timeout` (and `block_proposal_timeout`). Constructing and broadcasting such a proposal is cheap — it only needs a valid miner signature over a header that does not advance the chain length, it does not need to pass full node validation to reach `check_latest_block_in_tenure`'s activity-refresh branches.

### Recommendation
Do not let a *conflicting/non-advancing* proposal refresh the same inactivity clock used to decide whether to abandon the tenure. Options:
- Track "activity" for inactivity-fallback purposes using signature/pre-commit thresholds only (as the existing `is_timed_out` doc-comment implies), and use a separate, capped counter (e.g., limited number of resets per tenure, or requiring increasing chain length) for the reorg-attempt leniency logic in `check_latest_block_in_tenure`.
- Alternatively, bound `update_last_activity_time` so it can only push the deadline forward a limited number of times or up to a maximum total extension, preventing indefinite renewal from repeated no-op/conflicting proposals.

### Proof of Concept
1. Miner wins a tenure but never intends to get a block globally accepted.
2. Miner proposes block `B0` (chain_length N). Signers validate/pre-commit but do not reach signature threshold within `tenure_last_block_proposal_timeout`.
3. Before `reorg_attempts_activity_timeout`/`block_proposal_timeout` elapses, miner re-signs and rebroadcasts a new proposal `B1` at chain_length ≤ N (a trivial header mutation, e.g., different timestamp) targeting the same tenure.
4. Each signer's `check_latest_block_in_tenure` sees `B1.chain_length <= info.block.chain_length` (conflict with the pre-commit/locally-accepted block) and calls `signer_db.update_last_activity_time(consensus_hash, now)` — [5](#0-4)  — resetting the clock `is_timed_out` reads from.
5. Miner repeats step 3 indefinitely, faster than the timeout window.
6. `SortitionState::is_timed_out` never returns `true` because `elapsed` (now − last refreshed `last_activity`) never exceeds `block_proposal_timeout`, so `check_miner_inactivity` never falls back to the prior tenure/miner — the tenure stalls with no block being finalized, and no other miner can take over via the timeout path.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }

    pub fn check_miner_inactivity(
        &mut self,
        db: &mut SignerDb,
        client: &StacksClient,

    ) -> Result<(), SignerChainstateError> {
        let Self::Initialized(ref mut state_machine) = self else {

            // no inactivity if there's no active miner
            return Ok(());

            state_machine.active_signer_protocol_version,
        );
        let is_timed_out = SortitionState::is_timed_out(
            &version,
            tenure_id,
            db,
            client.get_signer_address(),
            proposal_config,
            eval,
        )?;

        if !is_timed_out {
            return Ok(());
        }

    /// Update the tenure (identified by consensus_hash) last activity timestamp
    pub fn update_last_activity_time(
        &mut self,
        tenure: &ConsensusHash,
        last_activity_time: u64,
    ) -> Result<(), DBError> {
        debug!("Updating last activity for tenure"; "consensus_hash" => %tenure, "last_activity_time" => last_activity_time);
        self.db.execute("INSERT OR REPLACE INTO tenure_activity (consensus_hash, last_activity_time) VALUES (?1, ?2)", params![tenure, u64_to_sql(last_activity_time)?])?;
        Ok(())
    }
