### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges requests and confirmations for requests that the removed member *originated*; it never scrubs confirmation entries that member left on *other*, still-pending requests. `confirm` then blindly counts `confirmations.len()` against `num_confirmations` without checking that each recorded confirmer is still a current member. As a result, a request can be executed with fewer live-member confirmations than `num_confirmations` requires, because a stale confirmation from an already-removed member is still counted.

### Finding Description
`confirm` treats the size of the stored confirmation set as proof of sufficient approval: [1](#0-0) 

It never re-validates that the account/key strings inside `confirmations` are still `self.members`. Meanwhile `delete_member` is supposed to keep state consistent when a member leaves, but its cleanup is scoped only to requests the removed member created (`r.member == member`), not to confirmations the removed member cast on requests created by someone else: [2](#0-1) 

Contrast this with `remove_request`/`confirm`, which store confirmer identity as a plain string in a `HashSet<String>` per request (`multisig2/src/lib.rs:294-315`, `multisig2/src/lib.rs:128`). Once a member's confirmation is written to that set for request X, it is never revisited when that member is later deleted via `DeleteMember` unless X itself was created by that same member.

This is the same class of bug as the StaderOracle report: data (a confirmation) that should have been invalidated once the "epoch" (membership state) moved on is instead left in place and gets mixed with fresh data, corrupting the tally used to decide whether the threshold `num_confirmations` was met. Here the "reportable block" is analogous to "current member set", and the "prices array" is analogous to "confirmations set".

Binding broken: `confirmations counted == live members who confirmed`. After the bug, `confirmations counted > live members who confirmed`, i.e. `count(confirmations ∩ current_members) < num_confirmations` can still trigger execution because `count(confirmations) >= num_confirmations` is checked without intersecting with `current_members`.

### Impact Explanation
This crosses the threshold-authorization boundary explicitly listed as Critical impact ("a multisig request executed below threshold"). An attacker (or a set of colluding members below the honest threshold) can get an arbitrary `MultiSigRequest` (including `Transfer`, `FunctionCall`, `AddKey`, etc.) executed using fewer genuinely live confirmations than `num_confirmations` mandates, because one or more of the counted confirmations belong to a member removed in the interim. This can move NEAR out of the multisig-controlled account, or add unauthorized keys, without the configured quorum of *currently authorized* members actually agreeing.

### Likelihood Explanation
Exploitability requires only: (1) a pending request with some confirmations below threshold, (2) a legitimate (properly-thresholded) `DeleteMember` action removing one of those confirmers for unrelated reasons (e.g., normal key rotation, offboarding a member, revoking a compromised key), and (3) any remaining member confirming again. This is a completely ordinary sequence of multisig operations (member rotation is a stated first-class use case: `AddMember`/`DeleteMember`), so this does not require a malicious deployment, contract owner, or any privileged party beyond normal multisig members acting in their expected roles. Likelihood is high given member rotation is a core, expected feature of this contract.

### Recommendation
When counting confirmations in `confirm`, intersect the stored confirmation set with `self.members` (i.e., only count confirmations from accounts/keys that are still members) rather than trusting the raw set length. Additionally, `delete_member` should scrub the removed member's entry from every entry in `confirmations` (not just requests it originated), e.g. iterate `self.confirmations` and remove `member.to_string()` from each set, or store confirmations keyed such that stale entries can never be recounted. A `mapping`-clearing approach analogous to the StaderOracle fix (deleting/rebuilding the affected data structure whenever the trust set changes) directly resolves this.

### Proof of Concept
1. Initialize the multisig with 4 members `A, B, C, D` and `num_confirmations = 3` (`MultiSigContract::new`, `multisig2/src/lib.rs:148-167`).
2. `A` calls `add_request` to create request `R1` (e.g., `Transfer`), then `confirm(R1)` — confirmations = `{A}` (1).
3. `B` calls `confirm(R1)` — confirmations = `{A, B}` (2, still below threshold 3).
4. Separately, members submit and fully confirm a `DeleteMember { member: B }` request (this is a normal, otherwise-legitimate action; members remaining = 3 which still satisfies `members.len()-1 >= num_confirmations`). `delete_member` (`multisig2/src/lib.rs:356-379`) removes `B` from `self.members` and cleans up only requests where `r.member == B` — it does **not** touch `R1`'s confirmation set, which was created by `A`, not `B`. `R1`'s confirmations remain `{A, B}` even though `B` is no longer a member.
5. `C` (a real, current member) calls `confirm(R1)`. In `confirm` (`multisig2/src/lib.rs:294-315`), `confirmations.len() as u32 + 1 = 3 >= num_confirmations (3)`, so `R1` executes — despite the fact that only `A` and `C` are actually current members who approved it; `B`'s stale confirmation was illegitimately counted toward the threshold.

This demonstrates a multisig request executed with the threshold check satisfied by a mix of live and stale (removed-member) confirmations, i.e., a request executed below the intended live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
