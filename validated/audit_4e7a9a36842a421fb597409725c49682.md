### Title
Mismatched `ConfidentialBurn` proof-offset flags vs. supplied `account_indexes` length can mislabel `permissionedBurnAuthority`/`instructionsSysvar` in parsed transaction JSON - (File: transaction-status/src/parse_token/extension/permissioned_burn.rs)

### Summary
The `PermissionedBurnInstruction::ConfidentialBurn` arm reconstructs optional account roles (`instructionsSysvar`, `equalityProofContextStateAccount`, `ciphertextValidityProofContextStateAccount`, `rangeProofContextStateAccount`, `permissionedBurnAuthority`) purely from the three proof-offset flags plus `account_indexes.len()`, using a manual walking `offset` counter guarded only by `saturating_sub(2)`/`saturating_sub(1)` bounds checks. Because both `burn_data`'s offset fields and `account_indexes`/its length are fully attacker-controlled, a non-canonical combination (declaring some proofs as context-account-based while omitting the corresponding account) causes the walk to run out of "room" prematurely and shift a proof context account slot into the `permissionedBurnAuthority` label.

### Finding Description
In the `ConfidentialBurn` arm [1](#0-0) , after decoding `burn_data`, the code computes `has_sysvar` from an OR of the three proof-instruction-offset fields, then sequentially attempts to consume `account_indexes[offset]` for the sysvar and for each proof whose corresponding offset field is `0` (meaning "context state account" rather than "instruction offset"), each gated only by `offset < account_indexes.len().saturating_sub(2)` [2](#0-1) . Finally `permissionedBurnAuthority` is assigned from `account_indexes[offset]` if `offset < account_indexes.len().saturating_sub(1)` [3](#0-2) .

`check_num_token_accounts(account_indexes, 4)` only guarantees a minimum of 4 accounts [4](#0-3) ; there is no cross-check that `account_indexes.len()` actually matches the number of optional accounts implied by the offset flags. An attacker fully controls both the raw `instruction_data` bytes (hence the three offset fields) and the `account_indexes`/`account_keys` list of a transaction they submit. By choosing, e.g., `equality_proof_instruction_offset == 0` (implying a dedicated equality-context account must exist) together with an `account_indexes` length one short of what that combination requires, the `offset < len.saturating_sub(2)` guard trips early and the code skips assigning the equality-context slot — but the counter `offset` was already incremented past the sysvar slot, so the account that (per the attacker's own declared offsets) was meant to be the equality-proof context account is instead labeled `permissionedBurnAuthority` in the resulting JSON. This is purely a display/metadata correctness issue reachable through `getTransaction`, since `parse_token` runs on any instruction bytes recorded in a block regardless of on-chain execution success.

### Impact Explanation
The impact is confined to wrong-account misreporting in `getTransaction`/`parse_token` JSON output — the field labeled `permissionedBurnAuthority` (or `instructionsSysvar`) can point at a different account than the one the attacker's own declared byte layout implies, misleading anyone reading the parsed instruction (explorers, auditors, compliance tooling). This falls under the "decoder ... misreporting" bucket named in the Validate section. It does not affect consensus, validator liveness, funds, or on-chain execution semantics, since the SPL Token-2022 program (not this parser) is what actually enforces byte/account correspondence for execution.

### Likelihood Explanation
Reachable by any unprivileged client: submit a single crafted transaction containing a `PermissionedBurnInstruction::ConfidentialBurn` instruction with a non-canonical offset/account-count combination (does not need to succeed on-chain — failed transactions are still recorded and their instructions parsed on `getTransaction`), then call `getTransaction` once. No elevated privileges, gossip, or multiple calls are required, so it is trivially and repeatably reproducible. However, it requires the attacker to intentionally construct a combination "that a real client would never produce," so it never occurs from legitimate program usage — it only affects the parser's best-effort reconstruction of an inherently ambiguous account list for a byte layout the attacker themselves invented.

### Recommendation
Add an explicit consistency check between `account_indexes.len()` and the exact number of optional accounts implied by the three offset flags before doing the positional walk; if the counts don't match the canonical expected count, fall back to omitting the optional-account labels (or the whole detailed breakdown) rather than guessing positions via `saturating_sub` guards. Alternatively, require `account_indexes.len()` to equal `4 + (has_sysvar as usize) + eq_ctx_count + val_ctx_count + rng_ctx_count` before attempting to assign any of the optional labels.

### Proof of Concept
Rust unit test extending the existing test module in `transaction-status/src/parse_token/extension/permissioned_burn.rs`:
```rust
#[test]
fn test_confidential_burn_mismatched_offsets_mislabel() {
    // Construct instruction data manually so that:
    // equality_proof_instruction_offset == 0 (implies an equality context account exists)
    // ciphertext_validity_proof_instruction_offset != 0
    // range_proof_instruction_offset != 0
    // but account_indexes supplies only 5 accounts: [account, mint, X, authority, owner]
    // i.e. one account short of the 6 required by "sysvar + eq_ctx + authority + owner".
    let account_indexes: Vec<u8> = vec![0, 1, 2, 3, 4];
    let burn_data = ConfidentialBurnInstructionData {
        new_decryptable_available_balance: Default::default(),
        equality_proof_instruction_offset: 0,
        ciphertext_validity_proof_instruction_offset: 1,
        range_proof_instruction_offset: 1,
    };
    // ... encode into instruction_data with the ConfidentialBurn discriminator ...
    let parsed = parse_permissioned_burn_instruction(&instruction_data, &account_indexes, &account_keys).unwrap();

    // Expected (per attacker's own declared offsets): index 2 should be
    // "instructionsSysvar", index 3 should be "equalityProofContextStateAccount",
    // and the real authority should be index 4.
    // Actual behavior: due to the saturating_sub(2) guard tripping early,
    // "equalityProofContextStateAccount" is never emitted and index 3
    // (intended as the equality context account) is instead labeled
    // "permissionedBurnAuthority".
    assert!(parsed.info.get("equalityProofContextStateAccount").is_none());
    assert_eq!(parsed.info["permissionedBurnAuthority"], json!(account_keys[3].to_string()));
}
```
Expected assertion failure/behavior demonstrates that the emitted `permissionedBurnAuthority` account does not correspond to the role implied by the attacker's own declared proof-offset fields, confirming the mislabeling.
