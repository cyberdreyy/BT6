### Title
Job-cancellation path lacks `WaitDelay`, letting a double-fork/`setsid` descendant race trace-writer teardown with lingering unmasked output - (`helpers/process/job_unix.go`, `helpers/process/killer_unix.go`, `helpers/process/killer.go`, `executors/shell/shell.go`)

### Summary
`unixKiller.Terminate`/`ForceKill` send signals to the negative PID (process group) via `syscall.Kill(-pid, ...)`, which only reaches processes that remain in the job's original `Setpgid` group. A job script that forks a grandchild calling `setsid()` (classic double-fork daemonization) moves that grandchild into a new session/group, so it never receives `SIGTERM`/`SIGKILL`. Because that grandchild can still hold the inherited stdout/stderr pipe write-end open, `exec.Cmd.Wait()` (and thus the `waitCh` in `executors/shell/shell.go`) can remain blocked past `GracefulKillTimeout`+`ForceKillTimeout`, at which point `KillAndWait` gives up and returns `KillProcessError`, and `shell.Run()`'s deferred `stdout.Close()/stderr.Close()` execute while the OS-level copy goroutine tied to the still-blocked `Wait()` may still be delivering trailing bytes into that same (now-closing) masking writer chain.

### Finding Description
- `helpers/process/job_unix.go` sets `Setpgid: true` on the job process so its immediate children share a process group. [1](#0-0) 
- `helpers/process/killer_unix.go` kills by negative PID, i.e., the process group, which only affects processes that stayed in that group. [2](#0-1) 
- `helpers/process/killer.go`'s `KillAndWait` sends `SIGTERM`, waits `gracefulKillTimeout`, sends `SIGKILL`, waits `forceKillTimeout`, and then **gives up**, returning `KillProcessError` regardless of whether the process tree actually terminated. [3](#0-2) 
- `executors/shell/shell.go` wires the job process's stdout/stderr directly to per-job masking writers obtained from `s.BuildLogger.Stream(...)`, waits on `waitCh` fed by a goroutine calling `c.Wait()`, and on cancellation calls `KillAndWait`; regardless of how `KillAndWait` resolves, the function returns and its `defer stdout.Close()` / `defer stderr.Close()` execute. [4](#0-3) 
- Go's `exec.Cmd.Wait()` does not return until the internal I/O-copy goroutines observe EOF on stdout/stderr pipes; EOF only occurs once **every** process holding the write end (including any descendant that escaped via `setsid()`/double-fork) closes it. The codebase explicitly documents and mitigates this exact hazard elsewhere — `commands/helpers/proxy_exec.go` sets `cmd.WaitDelay` specifically "because... a grandchild holds the write-end open" — but no equivalent `WaitDelay` (or similar bound) exists in `helpers/process/commander.go`/`job_unix.go`, which is what `shell`, `custom`, and other executors that reach `KillAndWait` actually use. [5](#0-4) 
- The masking chain (`common/buildlogger/build_logger.go`'s `wrap`, wrapping `masker.New`, `tokensanitizer.New`, etc.) is created once per `Logger`/per-job and closed via `(*Logger).Close()`/the per-stream `Close()`; `Close()` flushes any partially-matched phrase bytes and then closes the next writer in the chain, but it does not synchronize against concurrent `Write()` calls from a still-running copy goroutine. [6](#0-5) [7](#0-6) 

Combining these: because `KillAndWait` unconditionally gives up after `forceKillTimeout` even if the underlying `Wait()` goroutine is still alive and blocked on pipe EOF, `shell.Run()` proceeds to close the masking writer objects that a still-running copy goroutine may concurrently write into. This is a genuine, unsynchronized `Write`/`Close` race on the masker's internal `matching` counter and on the downstream `Trace` writer, not a theoretical concern — it is the same class of bug the `proxy_exec.go` comment explicitly calls out and fixes with `WaitDelay`, but the fix is not applied to the main job process path.

However, the specific claimed impact — that "output... is no longer matched against that job's own secrets" — is not clearly substantiated. The masker/tokensanitizer instances involved are per-job (created once in `Build.getNewLogger`/`Logger.wrap` with that job's own `maskPhrases`), not a shared/global structure that gets "torn down to free memory" and reused across jobs. Any lingering bytes racing with `Close()` still pass through the *same job's own* masker with the *same* phrase list — the race is a potential data race / partial-match corruption at the Close boundary (could theoretically cause a phrase spanning the exact byte offset of teardown to slip through partially unmasked), not a cross-job secret leak, and not a "masking context already freed for another job" scenario as hypothesized. There is no code found that tears down a shared `Masked` variable set independently of the per-job `Logger`.

### Impact Explanation
Concrete, narrower impact than claimed: a job whose script performs a double-fork/`setsid()` to escape the process group, combined with hitting `ForceKillTimeout`, can create an unsynchronized `Write()`/`Close()` race on that job's own masking writer chain, and can leave a background goroutine (and the escaped descendant) running indefinitely after the runner believes the job is done. This is a resource-leak / race-condition robustness bug. It is not demonstrated to leak secrets to an unmasked destination or across jobs, because the masking state used for any lingering bytes is still that job's own, correctly-configured masker.

### Likelihood Explanation
Requires an attacker (job author) to run a `SIGTERM`-trapping script that double-forks with `setsid()`, and requires the job to actually be canceled/timed out so `KillAndWait` executes and both `GracefulKillTimeout` and `ForceKillTimeout` elapse. This is fully attacker-controllable (script content) and reproducible, but the "trace output emitted after masking is torn down and unmasked" specific outcome is unconfirmed by the code — the masking object used would still be the correct one for that job.

### Recommendation
- Add a bound (e.g., `cmd.WaitDelay`, mirroring `commands/helpers/proxy_exec.go`) to `helpers/process` job commands so `Wait()`/`KillAndWait` cannot block indefinitely on a leaked pipe FD after `ForceKillTimeout`.
- Ensure `stdout.Close()`/`stderr.Close()` in `executors/shell/shell.go` (and analogous executors) only run after the underlying copy goroutine has actually stopped, or make the masking writer's `Close()`/`Write()` safe for concurrent use (e.g., guard with the same mutex used elsewhere, or drop/no-op writes after `Close()` instead of forwarding to a closed downstream).
- Consider explicitly killing/reaping any process outside the tracked group (e.g., via PID namespace isolation in containerized executors) rather than relying solely on process-group signaling for the shell executor.

### Proof of Concept
Using `helpers/process/killer_integration_test.go`'s `newKillerWithLoggerAndCommand` harness:
1. Build a test binary that: forks a child, in the child calls `setsid()` then forks again (double-fork), has the grandchild loop writing recognizable "secret" bytes to its inherited stdout at intervals, and has the original process trap/ignore `SIGTERM`.
2. Start the command through the harness with a very small `gracefulKillTimeout`/`forceKillTimeout`.
3. Call `k.Terminate()` then wait past both timeouts; assert `KillAndWait` returns `*KillProcessError`.
4. Concurrently, run the same read/wrap chain used by `shell.Run()` (a `masker`-wrapped writer with a known mask phrase equal to the grandchild's emitted "secret" string) and call `Close()` on it at the moment `KillProcessError` is returned, while a goroutine keeps calling `Write()` with bytes still arriving from the leaked pipe.
5. Assert with `go test -race` that no data race is reported, and assert that any bytes that do reach the trace after `Close()` are either rejected (writes after close return an error) or still contain `[MASKED]` in place of the known secret phrase — flagging failure if the raw secret string appears unmasked in the final trace buffer.

```go
func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}

// getPID will return the negative PID (-PID) which is the process group. The
// negative symbol comes from kill(2) https://linux.die.net/man/2/kill `If pid
// is less than -1, then sig is sent to every process in the process group whose
// ID is -pid.`
func (pk *unixKiller) getPID() int {
	return pk.cmd.Process().Pid * -1
}
```

```go
func (kw *osKillWait) KillAndWait(command Commander, waitCh chan error) error {
	process := command.Process()
	if process == nil {
		return ErrProcessNotStarted
	}

	log := kw.logger.WithFields(logrus.Fields{
		"PID": process.Pid,
	})

	processKiller := newProcessKiller(log, command)
	processKiller.Terminate()

	select {
	case err := <-waitCh:
		return err
	case <-time.After(kw.gracefulKillTimeout):
		processKiller.ForceKill()

		select {
		case err := <-waitCh:
			return err
		case <-time.After(kw.forceKillTimeout):
			return &KillProcessError{pid: process.Pid}
		}
	}
```

```go
func (l *Logger) Close() error {
	l.mu.Lock()
	defer l.mu.Unlock()

	if l.closed {
		return fmt.Errorf("already closed")
	}
	l.closed = true

	if l.w != nil {
		return l.w.Close()
	}

	return nil
}
```

```go
// Close flushes any remaining data and closes the underlying writer.
func (m *masker) Close() error {
	var werr error

	if m.matching == len(m.phrase) {
		// this mask is added to avoid a potential undiscovered edge-case:
		// this should be unreachable as we replace full matches immediately in
		// Write().
		_, werr = m.next.Write(mask)
	} else {
		_, werr = m.next.Write(m.phrase[:m.matching])
	}

	err := m.next.Close()
	if err == nil {
		return werr
	}

	return err
}
```
