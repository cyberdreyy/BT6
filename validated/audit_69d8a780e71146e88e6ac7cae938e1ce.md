### Title
Stale confirmations from removed multisig members are counted toward the confirmation threshold, allowing execution below the effective K-of-N quorum - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` (and the analogous `DeleteKey` handler in the older `multisig` contract) only purges pending *requests originated by* the removed member. It never scrubs that member's *confirmations* that were already recorded as an approver on other, still-pending requests. Because `confirm()` simply counts `confirmations.len()` without re-validating that every recorded confirmer is still a current member, a request can reach `num_confirmations` and execute even though one of the "confirming" identities was removed from the multisig before the threshold was met.

### Finding Description
`confirm()` accumulates approver identities in a `HashSet<String>` per request and executes once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

The only place stale confirmations are ever cleaned up is `delete_member`, and it only removes requests whose *creator* (`r.member`) matches the removed member — it does not scan or clean the `confirmations` set of requests created by *other* members that the removed member had merely confirmed: [2](#0-1) 

`current_member()` is only used to gate who is *allowed to call* `confirm`/`add_request` right now; it is never used to re-validate the members already present in a request's stored `confirmations` set: [3](#0-2) 

The intended binding is: `confirmations.len() >= num_confirmations` ⇒ that many *currently live* members approved. This invariant is broken:

1. Members A, B, C, D exist; `num_confirmations = 3`.
2. A calls `add_request` for a `Transfer` (request X, creator = A, confirmations = {}).
3. A calls `confirm(X)` → confirmations = {A} (1/3).
4. B calls `confirm(X)` → confirmations = {A,B} (2/3, not yet executed).
5. Separately, A, C, D confirm a `DeleteMember{B}` request (reaches 3/3) and it executes: `delete_member` removes B from `self.members`, deletes B's own outstanding requests, but request X (created by A, not B) is untouched — B's confirmation on X survives in the `confirmations` set.
6. C now calls `confirm(X)`. `current_member()` succeeds (C is still a member). `confirmations.len()` is 2 (A, B) + 1 (C) = 3 ≥ `num_confirmations` (3) → `execute_request` runs the `Transfer`.

Request X executed with only two *live* approving identities (A and C); B's approval is stale and B is no longer a multisig member. The same class of bug exists in the older `multisig/src/lib.rs`, where `DeleteKey` only purges requests where `r.signer_pk == pk` (the deleted key's *own* requests), leaving that key's confirmations on other pending requests intact: [4](#0-3) [5](#0-4) 

### Impact Explanation
This breaks the fundamental K-of-N custody guarantee of the multisig wallet: `num_confirmations` is meant to certify that a threshold of *currently authorized* signers approved a fund movement (Transfer, FunctionCall, AddKey, DeployContract, etc.). By keeping a member on a pending request's confirmation list after that member is removed, a transaction (including NEAR transfers) can execute with fewer live approvers than the configured threshold — "a multisig request executed below threshold," which is explicitly called out as a Critical-impact scenario for this class of contract.

### Likelihood Explanation
No malicious code or compromised key is required beyond normal multisig operation: any legitimate member can confirm a request without immediately pushing it over threshold, then be legitimately removed via a separate, correctly-executed `DeleteMember`/`DeleteKey` request, while their earlier confirmation silently remains attached to the first request. This is a straightforward sequencing of two ordinary multisig operations (partial confirmation + member removal), not an edge case requiring adversarial control of the contract or external actors.

### Recommendation
When executing `DeleteMember` (or `DeleteKey`), iterate over **all** pending requests' `confirmations` sets (not just requests the removed member created) and remove the departing member's entry, re-checking whether any request already meets/exceeds `num_confirmations` afterward (it should not auto-execute since removal should reduce, not trigger, execution). Alternatively, when `confirm()` counts confirmations, re-validate that every historical confirmer in the stored set is still `self.members.contains(...)` before comparing against `num_confirmations`, discarding stale entries so the threshold always reflects live membership.

### Proof of Concept
Using `multisig2/src/lib.rs`:
1. `new(members: [A,B,C,D], num_confirmations: 3)`.
2. As A: `add_request({receiver_id: X, actions: [Transfer{amount}]})` → `request_id`.
3. As A: `confirm(request_id)` (confirmations = {A}).
4. As B: `confirm(request_id)` (confirmations = {A,B}).
5. As A, C, D: create and confirm `add_request_and_confirm({receiver_id: multisig_account, actions: [DeleteMember{member: B}]})` until it executes (3/3) — this removes B from `members` via `delete_member` (`multisig2/src/lib.rs:356-379`), which does not touch `request_id`'s confirmations.
6. As C: `confirm(request_id)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request` fires the `Transfer`, even though only A and C are currently valid members among the counted approvers.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn current_member(&self) -> Option<MultisigMember> {
        let member = if env::current_account_id() == env::predecessor_account_id() {

                    .try_into()

                account_id: env::predecessor_account_id(),
            }
        };

            Some(member)

            None
        }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
