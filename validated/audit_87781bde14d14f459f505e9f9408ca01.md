### Title
Stale per-txid rejection-weight accumulator survives `reset_rejections`, letting a single signer's weight be double-counted across retries to force txid exclusion - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListenerComms::reset_rejections` clears `responded_signers` and `total_weight_rejected` on a `BlockStatus` timeout-retry, but never clears `failed_txids`, a `HashMap<Txid, FailedTxInfo>` that accumulates rejecting signers' weight per problematic transaction. Because the "already responded" gate (`responded_signers`) is wiped by every retry, the same signer's identical rejection is re-admitted and its weight is added to `failed_txids[txid]` again on each retry cycle, inflating that transaction's tracked weight beyond the signer's real, single unit of voting weight.

### Finding Description
`BlockStatus` (stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82) holds two logically parallel accumulators updated together when a rejection arrives:
- `total_weight_rejected` (round-scoped tally)
- `failed_txids: HashMap<Txid, FailedTxInfo>` (per-txid tally of `total_weight` / `problematic_weight`)

Both are only updated when `block.responded_signers.insert(slot_id)` returns `true`, i.e., "first response this round" [1](#0-0) .

`reset_rejections`, called by the miner-side coordinator whenever `get_block_status` times out waiting on rejections, resets `responded_signers` and `total_weight_rejected` to start a fresh round, but leaves `failed_txids` untouched [2](#0-1) .

`propose_block` in the miner-side `SignerCoordinator` resends the identical `BlockProposal` (same `signer_signature_hash`, same `BlockStatus` map entry) whenever `get_block_status` returns `NakamotoNodeError::SignatureTimeout`, looping indefinitely on timeout [3](#0-2) , and `get_block_status` itself invokes `reset_rejections` right before returning that error [4](#0-3) .

Consequently: signer S rejects the block once with reason `ValidationFailed(ProblematicTransaction)` for txid T. `responded_signers` gates the insert so S's weight w is added once to `failed_txids[T]`. The proposal round times out (a normal condition, no majority required — just network delay/slow signers), `reset_rejections` clears `responded_signers` but not `failed_txids[T]`. The miner resends the same proposal; S rejects again with the same reason; `responded_signers.insert` again returns `true` (fresh set), so w is added to `failed_txids[T]` a second time, making `failed_txids[T].total_weight = 2w` from a single signer. Repeating this over N timeout rounds inflates `failed_txids[T].total_weight` to `N·w`, which can exceed `blocking_minority = total_weight - weight_threshold` even though the *real*, deduplicated signer weight opposing T is far below the 30% blocking minority.

This directly breaks the equality between "aggregated weight tracked per txid" and "verified, distinct signer weight that actually opposes the tx" — the exact same bug shape as the external report, where a per-slot accumulator (`lastCollateralError_Offset`) is not reset when the associated round-scoped state (`indexByCollateral`) is reassigned/reset, letting stale contributions leak into a fresh accounting period.

### Impact Explanation
Once `info.total_weight > blocking_minority` (using inflated weight), `temporarily_excluded_txids` (or, if `problematic_weight` also crosses the minority via the same mechanism, `permanently_excluded_txids`) is populated and returned to the miner, which will strip that transaction from future block templates (stackslib/src/chainstate/stacks/miner.rs). A single signer — well below the real 30% blocking-minority weight — can therefore force the miner to permanently censor an arbitrary transaction simply by causing (or waiting for) repeated `SignatureTimeout` rounds and re-emitting the same rejection each time. This is a liveness/censorship break achieved without a majority of signers and without needing another signer's key, matching the "miscounted response" acceptance criterion.

### Likelihood Explanation
Likelihood is Medium-to-Low but realistic: `SignatureTimeout` rounds are a normal operational occurrence (network latency, node restarts, slow validation), and the miner's `propose_block` loop resends identical proposals indefinitely on timeout, so a single misbehaving or even just persistently-slow signer that resends its previous rejection each round will trigger the double count "for free" without any special exploit tooling — it only needs to keep rejecting the same block/txid across multiple naturally-occurring retry rounds.

### Recommendation
Clear (or decay) `failed_txids` in `reset_rejections` alongside `responded_signers` and `total_weight_rejected`, or key the per-txid tally by `(slot_id, txid)` so that a signer can only contribute weight once per outstanding proposal regardless of how many timeout/retry rounds occur:

### Proof of Concept
1. Miner proposes block B (`propose_block`, signer_coordinator.rs:279-358); `insert_block` creates a fresh `BlockStatus` for B's sighash with empty `failed_txids`.
2. Signer S sends `BlockResponse::Rejected` for B citing txid T with `RejectCode::ValidationFailed(ProblematicTransaction)`. `responded_signers.insert(S)` → true, so `failed_txids[T].total_weight += w_S`, `problematic_weight += w_S` (stackerdb_listener.rs:515-546).
3. `get_block_status` on the miner side times out waiting for the rejection threshold (`rejections_timer.elapsed() > rejections_timeout`), calls `self.stackerdb_comms.reset_rejections(&B_sighash)` (signer_coordinator.rs:443-455), which clears `responded_signers`/`total_weight_rejected` but leaves `failed_txids[T]` at `w_S`.
4. `propose_block`'s loop sees `Err(SignatureTimeout)` and resends the identical `BlockProposal` for B (signer_coordinator.rs:350-356).
5. Signer S rejects again for the same txid T with the same reason. `responded_signers.insert(S)` again returns true (set was cleared), so `failed_txids[T].total_weight += w_S` → now `2·w_S`, and `problematic_weight` similarly doubles.
6. Repeat steps 3–5 N times until `2·N·w_S` (approval loop can be sped up by network jitter or simply waiting) exceeds `blocking_minority = total_weight - weight_threshold`, even though `w_S` alone (a single signer's real weight) is well under 30% of `total_weight`.
7. `get_block_status`'s next iteration sees `block_status.failed_txids[T].problematic_weight > blocking_minority` and returns `permanently_excluded_txids = {T}` to the miner (signer_coordinator.rs:521-540), causing T to be permanently stripped from block templates — a censorship outcome forced by a single sub-minority signer through the timeout/retry path, not by an honest 30%+ rejection.
