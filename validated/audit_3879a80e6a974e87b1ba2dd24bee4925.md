### Title
Loss-adjusted withdraw receipts are paid at par after a newer request overwrites `lastWithdrawRequest` - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` locates a user's haircutted receipt solely via `lastWithdrawRequest[_user]`, which `requestWithdraw` unconditionally overwrites with the *latest* request epoch. A user whose pending receipt was haircutted by `collectWithdrawFunds`/`stopEpochWithDuration` can submit a new `requestWithdraw` in a later epoch, causing the loss-epoch lookup to return 0 and the haircutted basis to fall through to `_claimFundedWithdrawRequest`, where `withdrawsRequests[_user]` is paid at par. The unfunded loss is socialized onto other funded claimants instead of the haircutted receipt holder.

### Finding Description
The analog to the use-after-free bug class is the reuse of stale/overwritten claim-position state: the "loss receipt" object for epoch N still exists in `withdrawsRequestsByEpoch[user][N]` and `withdrawsRequests[user]`, but the single pointer used to reach its haircut price (`lastWithdrawRequest`) is "freed" (overwritten) by a newer request, letting the stale basis be consumed through the wrong (par-value) path.

Relevant code:

- `requestWithdraw` stores only the newest epoch marker: `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user] += _amount` (contracts/strategies/idle/IdleCreditVault.sol:279-294).
- On a loss stop, `collectWithdrawFunds` with `_amount < pendingBasis` zeroes `pendingWithdraws` and records `lossRecoveryPriceByEpoch[epochNumber]` — meaning the strategy holds less underlying than the aggregate receipt basis (contracts/strategies/idle/IdleCreditVault.sol:411-430).
- `claimWithdrawRequest` tries `_claimLossAdjustedWithdrawRequest` first: it reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and returns 0 when that epoch has no loss price (lines 789-801).
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` (which still includes the loss-epoch `withdrawsRequestsByEpoch` entry, since nothing removed it) at par via `_transferFundedClaim` (lines 319-350, 897-907).

Concretely:

1. User deposits and calls `requestWithdraw` during epoch N; `lastWithdrawRequest[user] = N`, `withdrawsRequestsByEpoch[user][N] = X`, `pendingWithdraws = X`.
2. Manager calls `stopEpochWithDuration(_lossAmount)`; `collectWithdrawFunds` receives `pendingToFund < X`, sets `pendingWithdraws = 0`, stores `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL`. Epoch N+1 begins.
3. During buffer/running epoch N+1 (or N+k), user calls `requestWithdraw` again with a small amount (e.g., 1 wei of tranche). `lastWithdrawRequest[user] = M > N`.
4. After epoch M ends (`epochNumber > lastWithdrawRequest`), user calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` checks `lossRecoveryPriceByEpoch[M] == 0` and returns 0. `_claimFundedWithdrawRequest` passes its gate and pays `withdrawsRequests[user] = X + dust` in full from strategy-held underlying.
5. The strategy only ever received `X * p / RECOVERY_FULL` for the epoch-N piece; the shortfall `X * (1 - p)` is paid out of funds belonging to other funded receipt holders, leaving them unpayable.

Broken invariant: the loss waterfall / "one receipt, haircutted payout". The existing guards do not stop it: `lossRecoveryPriceByEpoch` lookup keys only on the *latest* marker, `_clearWithdrawClaimForEpoch` is never invoked for epoch N, and `_transferFundedClaim` only protects `defaultRecoveryReserve`, not other funded claims.

### Impact Explanation
The user extracts `X * (1 - lossRecoveryPrice)` underlying beyond their entitlement. Since `collectWithdrawFunds` only pulled `pendingToFund` from the borrower, this excess is paid from underlying reserved for other claimants' funded receipts, producing direct insolvency of the funded-claim bucket: later claimants' `claimWithdrawRequest` calls revert on insufficient balance or are paid less than par. Loss scales with the attacker's loss-epoch receipt size and the severity of the realized loss; a whale receipt in a large-loss epoch can drain the entire funded remainder.

### Likelihood Explanation
Requires a `stopEpochWithDuration` partial-loss event (a designed flow exercised by the manager when the borrower underpays) and an attacker holding a pending receipt in that epoch. The attacker's actions — a follow-up `requestWithdraw` in any later epoch plus a normal `claimWithdrawRequest` — are ordinary unprivileged calls with no privileged cooperation, and are arguably natural user behavior (re-queuing a withdrawal), so no suspicious sequencing is needed. I could not fully verify whether `requestWithdraw` reverts during the buffer phase before the next `startEpoch`; the `IdleCDOEpochVariant` request path would need to confirm requests are accepted while `isEpochRunning()` is false, but the "wait another epoch" note in `_claimFundedWithdrawRequest` (lines 323-324) indicates overlapping unclaimed+new requests are an expected pattern.

### Recommendation
Track loss-adjusted basis per epoch instead of through a single mutable marker: in `claimWithdrawRequest`, iterate or record all epochs with a nonzero `withdrawsRequestsByEpoch[user][epoch]` and consult `lossRecoveryPriceByEpoch[epoch]` for each (e.g., keep a per-user epoch list, or store a per-epoch pending-claim index similar to `instantWithdrawClaimsByEpoch`). At minimum, `requestWithdraw` should refuse to create a new request while `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` has an uncleared claim, forcing users to claim the haircutted receipt before re-queuing.

### Proof of Concept
Foundry fork sketch against the credit-vault test harness (`test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: user deposits, requests withdraw of X tranche tokens in epoch N
_depositWithUser(attacker, amountWei, true);
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche));
uint256 requestEpoch = strategy.epochNumber();

// epoch N ends with a realized loss; borrower funds only pendingToFund < pendingBasis
uint256 loss = pendingBasis / 2; // 50% loss on pending receipts
(uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(loss);
// manager stops epoch with loss -> collectWithdrawFunds(pendingToFund)
_stopEpochWithLoss(loss); // helper calling cdoEpoch.stopEpochWithDuration / manager flow
assertLt(strategy.lossRecoveryPriceByEpoch(requestEpoch), RECOVERY_FULL);

// attacker re-queues a dust withdraw in a later epoch, moving lastWithdrawRequest
_startEpochAndCheckPrices(requestEpoch);
vm.prank(attacker);
cdoEpoch.requestWithdraw(1, address(AAtranche)); // dust amount
assertEq(strategy.lastWithdrawRequest(attacker), strategy.epochNumber());

// finish that epoch, then claim: loss-adjusted path returns 0, funded path pays par
_stopEpochAndCheckPrices(requestEpoch + 1, apr, _expectedFundsEndEpoch());
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();
// attacker received full X at par instead of X * lossRecoveryPrice / RECOVERY_FULL
assertGt(underlying.balanceOf(attacker) - balPre,
         X * strategy.lossRecoveryPriceByEpoch(requestEpoch) / RECOVERY_FULL);
// invariant: another funded claimant's claim now reverts or underpays
```

The key assertion is that `claimWithdrawRequest` pays more than `X * lossRecoveryPrice`, demonstrating the loss-epoch basis was consumed at par after `lastWithdrawRequest` was overwritten.
