### Title
`claimInstantWithdrawRequest` never clears `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`, allowing a stale instant receipt to be paid twice after borrower default — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Visor M-02 bug class is "two paths consume the same entitlement, but only one cleans the bookkeeping mapping." In `IdleCreditVault`, instant-withdraw receipts are tracked both as an aggregate (`instantWithdrawsRequests[user]`) and per request epoch (`instantWithdrawsRequestsByEpoch[user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`). The funded-claim path `claimInstantWithdrawRequest` zeroes only the aggregate and burns the receipt tokens, leaving the per-epoch basis intact. If that same epoch later defaults and default recovery is finalized, `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch entry and pays the user a second time from `defaultRecoveryReserve`, provided the user's aggregate is padded by a subsequent request so `instantWithdrawsRequests[_user] -= claimBasis` does not underflow.

### Finding Description
`requestInstantWithdraw` records receipt basis in three places (IdleCreditVault.sol:366–374):

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

The normal funded claim cleans only the aggregate (IdleCreditVault.sol:387–392):

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` are never touched — the direct analog of `transferERC721` not cleaning `timelockERC721s` while `timeUnlockERC721` does.

The stale entry becomes spendable again once `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, because `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest` (IdleCreditVault.sol:842–856), which pays `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch] * defaultRecoveryPrice / 1e18` from the reserve, does `instantWithdrawsRequests[_user] -= claimBasis`, and burns `claimBasis` receipt tokens. The only thing blocking reuse of an already-claimed entry is a subtraction underflow on the zeroed aggregate — which the attacker defeats by making a new post-default instant request (`instantWithdrawsRequests` is still usable via `requestInstantWithdraw`) of at least the stale amount before claiming.

Sequence (named phases):
1. Epoch N running, instant withdraws enabled: attacker calls `requestInstantWithdraw(X)`. Receipt tokens minted; `instantWithdrawsRequestsByEpoch[attacker][N] = X`.
2. Borrower funds instant claims (`collectInstantWithdrawFunds`); attacker calls `claimInstantWithdrawRequest`, is paid X at par. Aggregate → 0; per-epoch entry stays X.
3. Epoch N ends in borrower default; manager/owner finalize recovery (`defaultRecoveryEpoch = N`, `defaultRecoveryPrice < 1e18`, `defaultInstantWithdrawsFinalized = true`).
4. Attacker submits a new instant request of X' ≥ X (aggregate = X', new minted receipt tokens = X').
5. Attacker calls `claimInstantWithdrawRequest` again: `_claimDefaultedInstantWithdrawRequest` pays `X * defaultRecoveryPrice` from `defaultRecoveryReserve` and burns X of the new receipt; then the funded path pays `instantWithdrawsRequests = X' - X` at par. The attacker was paid twice for the epoch-N receipt, and still retains `instantWithdrawsRequestsByEpoch[attacker][N+1] = X'` basis.

### Impact Explanation
Direct theft from the default recovery reserve: every stale instant receipt of a defaulted epoch can be re-claimed at `defaultRecoveryPrice`, draining `defaultRecoveryReserve` that is meant to be shared pro-rata across all defaulted-epoch claimants (`_transferDefaultRecovery`). Other users' `_claimDefaultedWithdrawRequest`/`DefaultDistributor.claim` payouts are reduced or revert on insufficient reserve — a quantifiable loss capped by the attacker's recycled receipt size (repeatable across epochs).

### Likelihood Explanation
Requires a borrower default, which is an expected protocol state (the whole post-default recovery machinery exists for it), plus `defaultInstantWithdrawsFinalized`. The attacker is fully unprivileged (a KYC'd lender). No privileged misbehavior is needed; the trigger is ordinary default finalization. Uncertainty: I could not fully verify within the iteration budget whether default finalization clamps `instantWithdrawClaimsByEpoch`/reserve such that the stale claim is partially offset — but nothing clears the per-epoch user entry on the funded-claim path, so the double-spend surface exists regardless of reserve sizing.

### Recommendation
In `claimInstantWithdrawRequest` (or a dedicated cleanup helper), clear the funded claim's per-epoch accounting alongside the aggregate:

```solidity
instantWithdrawsRequestsByEpoch[_user][epochNumber] = 0; // and any prior open epochs
instantWithdrawClaimsByEpoch[epoch] -= amount;
```

Alternatively, record the request epoch per user (like `lastWithdrawRequest`) and zero `instantWithdrawsRequestsByEpoch` for every epoch the funded payout covers, so a claimed receipt can never re-enter the defaulted-epoch path.

### Proof of Concept
```solidity
// Foundry fork test sketch (contracts: cdoEpoch, strategy = IdleCreditVault)
// 1. Epoch N running, allowInstantWithdraw = true
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(shares);           // -> strategy.requestInstantWithdraw(X)
// 2. Borrower funds instant withdrawals; attacker claims at par
strategy.collectInstantWithdrawFunds(X);           // via CDO stop/start flow
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();            // paid X; ByEpoch[attacker][N] still X
// 3. Borrower defaults on epoch N; finalizeDefaultRecovery sets
//    defaultRecoveryEpoch = N, defaultInstantWithdrawsFinalized = true
// 4. Attacker pads aggregate with a fresh instant request X' >= X
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(Xprime);
// 5. Re-claim: stale epoch-N basis pays recovery AGAIN
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
assertGt(underlying.balanceOf(attacker) - balPre,
         Xprime - X);                              // includes X * defaultRecoveryPrice (double pay)
```

Caveat: exact sequencing of `defaultRecoveryEpoch` vs the instant request epoch should be confirmed against `finalizeDefault`/`finalizeDefaultRecovery` in `IdleCreditVault.sol`; the stale-mapping defect itself (lines 387–392 vs 371–372) is directly observable in the code above.
