## Vulnerability Found

### Title
Beneficiary/Shareholder Can Permanently Block `distribute()` and `distribute_internal()`, Freezing All Other Stakers' and Operators' Unlocked Funds - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move], [File: aptos-move/framework/aptos-framework/sources/vesting.move])

### Summary
`staking_contract::distribute_internal` and `vesting::distribute` both loop over all shareholders/beneficiaries of a shared distribution pool and call `aptos_account::deposit_coins` for each recipient in the same atomic transaction. If any single recipient address is unregistered for `AptosCoin` and has called `aptos_account::set_allow_direct_coin_transfers(false)` (a fully unprivileged, self-service call), `deposit_coins` will abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. Because the loop and payout happen in one atomic call, this single non-conforming recipient reverts the entire distribution — for every other shareholder/operator sharing that pool, every time `distribute()` is called — permanently trapping stake, rewards, and commission that would otherwise be withdrawable.

### Finding Description
`aptos_account::deposit_coins` only bypasses the opt-in gate when the recipient is already registered for the coin: [1](#0-0) 

The gate is controlled entirely by the recipient itself via the unprivileged entry function: [2](#0-1) 

`staking_contract::distribute_internal` iterates every shareholder in `distribution_pool` (which contains both the staker and, via the operator's redirect, the operator/beneficiary) and pays each out with `aptos_account::deposit_coins` inside the same transaction, with no per-recipient error isolation: [3](#0-2) 

`vesting::distribute` has the identical pattern, looping over all shareholders in `grant_pool` and calling `aptos_account::deposit_coins` for each beneficiary in one atomic loop: [4](#0-3) 

`distribute` is explicitly documented as callable by "anyone" and not restricted to staker/operator: [5](#0-4) 

Attack path: any shareholder of a `staking_contract`/`vesting` pool (or any address set as a beneficiary via `update_beneficiary`, which any admin/shareholder-influenced flow can point at an attacker-controlled address) creates a fresh account, calls `set_allow_direct_coin_transfers(false)`, and never registers a `CoinStore<AptosCoin>`. Once that address is queued as a recipient in the shared `distribution_pool`/`grant_pool` (which happens automatically the moment any coins are unlocked for it via `unlock_stake`, `unlock_rewards`, `request_commission`, or `vest`), every subsequent call to `distribute()`/`distribute_internal` will abort at that recipient, because `shareholders_count() > 0` drives a `while` loop that always resumes at index 0 of the remaining shareholder list. Since there is no way to skip or partially process the loop, and `distribute` cannot be parameterized to exclude the blocking address, the entire pool's currently-unlocked funds (staker withdrawal, operator commission, other shareholders' vested amounts) become permanently unclaimable through `distribute` for as long as the malicious/blocking recipient remains in the pool.

### Impact Explanation
This breaks the "Unlock, reactivate, withdraw, synchronize, and beneficiary-update paths must not redirect value or strand it permanently" invariant. A single unprivileged shareholder or beneficiary can strand withdrawal rights and commission payouts for every other staker/operator sharing the same `staking_contract` or `vesting` pool. This is a real value-freezing (denial of value) impact on stake, commission, and vesting balances not owned by the attacker — meeting the "Permanent lock or non-recoverable loss of claim rights" and "Operator commission ... share-accounting corruption that ... traps value" criteria.

### Likelihood Explanation
Likelihood is Medium-High: the precondition (an address that is unregistered for `AptosCoin` and has disabled direct transfers) is trivially achievable by any account with zero cost beyond gas, and becoming a shareholder/beneficiary of a shared pool is a normal, permissionless part of the staking/vesting flow (e.g., being named a vesting shareholder, or being set as an operator's beneficiary). No privileged action or race condition is required.

### Recommendation
Isolate per-recipient payout failures so a single bad recipient cannot block the whole distribution: e.g., wrap each `aptos_account::deposit_coins` call so that failures fall back to holding the recipient's share in an escrow/claimable balance (or skip and re-queue that recipient) rather than aborting the entire loop; alternatively, require recipients to pre-register for `AptosCoin` before being added to a distribution/grant pool, or validate `coin::is_account_registered` / `can_receive_direct_coin_transfers` up front and only fast-path unlock (leaving funds in the pool) for non-conforming recipients instead of atomically forcing a push payment.

### Proof of Concept
1. Staker `S` creates a `staking_contract` with operator `O` and commission.
2. Attacker `A` (any address) creates a fresh account, calls `aptos_account::set_allow_direct_coin_transfers(A, false)`, and never registers `CoinStore<AptosCoin>`.
3. `O` sets `A` as `beneficiary_for_operator` via `staking_contract::set_beneficiary_for_operator` (or, in the vesting case, `A` is simply listed as a shareholder in `create_vesting_contract`).
4. Rewards accrue; `S` or `O` calls `unlock_stake`/`request_commission`/`vest`, which calls `add_distribution`, adding `A` (as beneficiary/shareholder) into the shared `distribution_pool`/`grant_pool`.
5. Anyone calls `staking_contract::distribute(S, O)` (or `vesting::distribute(contract_address)`). The loop reaches `A`, `aptos_account::deposit_coins` hits the `!coin::is_account_registered` branch, `can_receive_direct_coin_transfers(A)` returns `false`, and the whole transaction aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. Every future call to `distribute` reproduces the same abort, since the failing shareholder is always processed in the same loop before completion — `S`'s and `O`'s own already-unlocked stake/commission (and any other shareholders' vested funds in the vesting case) can no longer be withdrawn via this pool.

**Note:** I was unable to fully verify, from indexed code alone, whether `coin::is_account_registered<AptosCoin>` behaves differently for the migrated Fungible-Asset representation of `AptosCoin` (the repo shows `aptos_account.move` has FA-specific paths like `deposit_fungible_assets`/`ensure_primary_fungible_store_exists`, but `distribute_internal`/`vesting::distribute` explicitly use the legacy `Coin<AptosCoin>`/`aptos_account::deposit_coins` path). This distinction affects exactly which precondition (unregistered legacy `CoinStore` vs. FA store creation semantics) triggers the abort in the current mainnet configuration; a Devin session with full repo/tests access would be needed to confirm this only affects legacy CoinStore-based accounts and not FA-migrated accounts.

    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
