## Determination: Valid Finding

### Title
`parse_token` misreports 2022-only extension instructions (e.g. `permissionedBurn`) as valid for the legacy spl-token program because it never checks which program id it is decoding for - (File: `transaction-status/src/parse_token.rs`)

### Summary
`parse_token` is invoked for both the legacy spl-token program and the Token-2022 program through the same `ParsableProgram::SplToken` dispatch entry, and it decodes every instruction using only `spl_token_2022_interface::instruction::TokenInstruction::unpack`, without ever inspecting or validating the actual `program_id` that was resolved for the instruction. As a result, an instruction addressed to the legacy token program but carrying a 2022-only extension discriminant (e.g. `PermissionedBurnExtension`) is parsed exactly as if it were a legitimate 2022 extension call, producing a `parsed.type` such as `"permissionedBurn"` alongside `programId` pointing at the legacy program.

### Finding Description
The dispatch table in `transaction-status/src/parse_instruction.rs` maps both legacy and 2022 token program ids to the single `ParsableProgram::SplToken` variant via `spl_token_ids()`: [1](#0-0) 

The `parse` entrypoint then calls `parse_token(instruction, account_keys)` — note it does **not** pass `program_id` into `parse_token` at all: [2](#0-1) 

Inside `parse_token`, decoding is done purely from `instruction.data` via the 2022-superset enum `spl_token_2022_interface::instruction::TokenInstruction::unpack`, with no re-derivation or check of which concrete program id (legacy vs. 2022) the instruction targets: [3](#0-2) 

Extension-only opcodes such as `PermissionedBurnExtension`, `ScaledUiAmountExtension`, `PausableExtension`, `GroupPointerExtension`, etc., are matched and parsed unconditionally: [4](#0-3) 

Because the legacy program id and the 2022 program id both key to the same `ParsableProgram::SplToken` and the same `parse_token` function, and because that function has no parameter carrying the resolved program id, there is no code path that can reject "extension discriminant + legacy program id" combinations. The outer `ParsedInstruction.program` field is always the constant string `"spl-token"` for both program ids (`format!("{program_name:?}")` on the shared enum variant), while `programId` is the real invoked address: [5](#0-4) 

**Exploit flow:** an attacker submits a transaction whose `CompiledInstruction.program_id_index` resolves to the legacy `spl_token::id()`, with instruction data whose first byte is a 2022-only extension discriminant (e.g. `PermissionedBurnExtension`'s tag). On-chain, the legacy program will fail this instruction at runtime (opcode unrecognized), but the transaction can still land in a block as a failed transaction (fee still charged), and its raw message bytes remain queryable. A subsequent `getTransaction` (or `getConfirmedTransaction`) call with `encoding: "jsonParsed"` runs this same parser over the stored message and returns a parsed instruction of type `"permissionedBurn"` (or whichever extension) attributed to `programId` = legacy spl-token address, `program` = `"spl-token"`. This misleads any downstream integrator parsing the JSON into believing the legacy program executed (or supports) a 2022-only extension instruction.

### Impact Explanation
This is a decoder misreporting bug reachable through a single, standard read-only RPC call (`getTransaction`/`jsonParsed`) after submitting one transaction, matching the "decoder panic and misreporting" category explicitly listed as in-scope in the Validate section. Impact is limited to RPC response content correctness (program/instruction semantics mislabeling) — it does not affect consensus, validator crash, or any state mutation, so it stays scoped to misreporting of `program`/`instruction_type`/account-role semantics to RPC/integrator consumers, as described in the question.

### Likelihood Explanation
Feasible and fully repeatable by any unprivileged party: no elevated permissions, staking, or leader/gossip control needed. Only requirement is fee-payer funds to submit one (failing) transaction and then issue one `getTransaction` RPC call. It is deterministic — the same discriminant/program-id combination will always produce the same misleading parse result.

### Recommendation
Thread the resolved `program_id` (or a legacy-vs-2022 flag derived from it) into `parse_token`, and reject/short-circuit with `ParseInstructionError::InstructionNotParsable` for any `TokenInstruction` variant that is not supported by the legacy `spl_token` program id (extension variants, batch, and other 2022-only opcodes) when `program_id == spl_token::id()`. Alternatively, split `ParsableProgram::SplToken` into distinct legacy/2022 dispatch variants at the `PARSABLE_PROGRAM_IDS` table level and enforce opcode-set membership per variant before decoding.

fn test_legacy_program_id_rejects_2022_only_extension_opcode() {
    use spl_token_2022_interface::extension::permissioned_burn::instruction::PermissionedBurnInstruction;

    let mint = Pubkey::new_unique();
    let account = Pubkey::new_unique();
    let owner = Pubkey::new_unique();

    // Build a raw instruction with the PermissionedBurnExtension discriminant,
    // but target the LEGACY spl-token program id.
    let mut data = vec![/* PermissionedBurnExtension discriminant byte */ 39u8];
    data.extend_from_slice(&/* inner PermissionedBurnInstruction-encoded bytes */[]);

    let legacy_program_id = spl_token_interface::id();
    let instruction = Instruction {
        program_id: legacy_program_id,
        accounts: vec![
            AccountMeta::new(account, false),
            AccountMeta::new_readonly(mint, false),
            AccountMeta::new_readonly(owner, true),
        ],
        data,
    };
    let message = Message::new(&[instruction], None);
    let compiled_instruction = &message.instructions[0];

    let result = parse_token(
        compiled_instruction,
        &AccountKeys::new(&message.account_keys, None),
    );

    // Expected (fixed) behavior: parsing must fail/err because the legacy
    // program does not support this opcode.
    assert!(
        result.is_err(),
        "parse_token must not report a 2022-only extension instruction \
         ({:?}) as valid for the legacy spl-token program id",
        result
    );
}
