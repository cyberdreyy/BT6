### Title
Unchecked `usize` addition in L1 deposit `opaqueData` length parsing can panic on attacker-controlled `TransactionDeposited` log data - (File: crates/consensus/protocol/src/deposits.rs)

### Summary
`Deposits::decode` derives an L1 `TransactionDeposited` event's `opaqueData` length directly from attacker-supplied log data (`opaque_content_len`, a full `u64` value coming from an ABI-encoded length field anyone can set by calling the deposit contract with arbitrary calldata) and then computes `64 + opaque_content_len as usize` in several places without a checked/saturating add, unlike the sibling computations in the same function that do use `checked_add`/`saturating_add`.

### Finding Description
The deposit log decode path treats `opaqueData`'s declared length as a raw, attacker-chosen `u64` (any depositor calling the L1 portal contract controls this log data completely): [1](#0-0) 

Immediately after, the code mixes safe (`saturating_add`/`checked_add`) arithmetic for `opaque_data_ceil_32` and `padding_end` with **unchecked** arithmetic for the slice bounds actually used to read `opaqueData`: [2](#0-1) 

`64 + opaque_content_len as usize` appears three times (lines 113, 124, 128) with plain `+`, while the very same value is guarded with `checked_add`/`saturating_add` two lines above for `padding_end`. This is structurally the same bug class as the reported CVE: a length/offset field taken straight from untrusted, attacker-controlled input is fed into pointer/slice-bound arithmetic without validating that the arithmetic itself cannot overflow, even though the surrounding code clearly intends to guard against exactly this (the `checked_add` calls right next to it, and the explicit `OpaqueContentOverflow`/`OpaqueDataPaddingOverflow` error variants, show the authors were aware overflow was a hazard but missed these three specific additions).

Because `opaque_content_len` can be up to `u64::MAX` (bounded only by fitting into a `u64`, per the `try_into` at line 96), `64 + opaque_content_len as usize` overflows `usize` on the three unchecked lines whenever `opaque_content_len > usize::MAX - 64`.

### Impact Explanation
- If the node binary is compiled with overflow checks enabled (Rust `debug_assertions`/`overflow-checks = true`, which some operators/CI or debug-profile builds may use for the derivation pipeline), this becomes an unconditional panic when deriving a block whose L1 receipts contain a single crafted `TransactionDeposited` log, i.e. a **node halt / crash reachable by any L1 depositor**, since every rollup node must process all deposits emitted since the last L2 block to build the next block.
- In pure release-mode builds without overflow checks, the addition silently wraps, but since `slice::get` on an inverted/invalid range returns `None` rather than panicking, this specific manifestation degrades to a decode error rather than an out-of-bounds read — meaning the immediately provable impact is a panic/DoS under overflow-checked builds, not memory corruption.

This satisfies the "node halt" impact criterion for validation, contingent on the build having overflow checks enabled, which I could not confirm or rule out because no `overflow-checks` setting was found in any workspace `Cargo.toml` (grep for `overflow-checks` returned no matches), meaning the effective setting is Cargo's default (`false` for `release`, `true` for `dev`). I could not determine which profile the production `base` node binary is built and shipped with.

### Likelihood Explanation
Triggering the vulnerable code path requires only submitting an L1 transaction that emits a `TransactionDeposited` event with a crafted `opaqueData` length field close to `u64::MAX` — trivially achievable by any external account calling the L1 deposit contract with hand-crafted calldata, at the cost of L1 gas for a single transaction. No special privileges, node compromise, or coordination with the sequencer are required. Every full node deriving the L2 chain from L1 receipts will execute `Deposits::decode` on this log.

### Recommendation
Replace the plain `+` in the three unchecked sites (`crates/consensus/protocol/src/deposits.rs:113`, `:124`, `:128`) with `checked_add`/`saturating_add`, consistent with the pattern already used for `opaque_data_ceil_32` and `padding_end` a few lines above, and return the existing `OpaqueDataOverflow`/`OpaqueDataPaddingOverflow` error variants on overflow instead of allowing the raw addition to execute.

### Proof of Concept
1. On L1, call the OptimismPortal-equivalent deposit contract's `depositTransaction` such that the emitted `TransactionDeposited` event's ABI-encoded `opaqueData` bytes field declares a length word (bytes `data[32..64]`) equal to a value like `0xFFFFFFFFFFFFFFC0` (i.e., `u64::MAX - 63`), which fits in `u64` (passes the `try_into` check at line 96) but makes `64 + opaque_content_len as usize` overflow `usize` on a 64-bit target.
2. Have a Base node ingest this L1 receipt during derivation; `Deposits::decode` is invoked with this log.
3. In a build with `overflow-checks = true` (e.g., a `dev`/debug build, or any release profile that explicitly turns overflow checks on), execution panics at the `64 + opaque_content_len as usize` expression inside the `.get(64..64 + opaque_content_len as usize)` call at line 113, aborting the derivation task/thread.

Note: I was unable to inspect the release build profile flags used for the shipped `base` binary (no `[profile.release]` `overflow-checks` setting found in the indexed files), so I cannot confirm with certainty whether the production binary panics or silently wraps; this should be verified directly against the deployed build configuration.
