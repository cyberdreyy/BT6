### Title
`lchmod` follows attacker-planted symlinks during zip extraction's chmod pass, enabling chmod of arbitrary host paths - ([File: helpers/archives/os_unix.go])

### Summary
`ExtractZipArchive` extracts every zip entry first, then in a second pass calls `lchmod(file.Name, file.Mode())` for every entry using `unix.Fchmodat(unix.AT_FDCWD, name, ..., unix.AT_SYMLINK_NOFOLLOW)`. `AT_SYMLINK_NOFOLLOW` only prevents following a symlink at the *final* path component; it does not stop intermediate path components from being resolved through symlinks. A crafted zip can create a symlink at an early path component (e.g. `a -> /etc`) in pass one, then a later entry (`a/passwd`) causes the chmod pass to resolve through that symlink and change permissions on an arbitrary host path.

### Finding Description
`extractZipSymlinkEntry` creates a symlink from arbitrary content of a zip entry via `os.Symlink(string(data), file.Name)` with no validation of the symlink target. [1](#0-0)  `extractZipFile` dispatches to it for entries whose mode is `os.ModeSymlink`, and to `extractZipFileEntry`/`extractZipDirectoryEntry` for other entries sharing the same path prefix. [2](#0-1)  `ExtractZipArchive` performs extraction of *all* entries first, then in a second loop calls `lchmod(file.Name, file.Mode())` and `processZipExtra` for every entry, in archive order: [3](#0-2) 

`lchmod` uses `unix.Fchmodat(unix.AT_FDCWD, name, uint32(mode.Perm()), unix.AT_SYMLINK_NOFOLLOW)` (non-Linux) or no flag at all on Linux path (Linux branch short-circuits only when `mode&os.ModeSymlink != 0`, i.e. only when the entry *itself* claims to be a symlink type — an entry like `a/passwd` is not a symlink type and is not skipped). [4](#0-3)  `AT_SYMLINK_NOFOLLOW` (and the Linux default, which follows all symlinks) only affects resolution of the last path component; any earlier component that is a symlink (such as `a` in `a/passwd`) is still resolved/followed by the kernel per standard path-resolution semantics. Consequently, if the archive contains a symlink entry `a -> /etc` followed by an entry named `a/passwd`, the extraction loop's second pass calls `lchmod("a/passwd", mode)`, which resolves through the `a` symlink to `/etc/passwd`, and performs a real `chmod` on that host path (subject to the permissions of the user/process running Runner's extraction code, e.g. helper container or job user).

There is no existing check that stops this: `errorIfGitDirectory`/`isPathAGitDirectory` only rejects `.git` paths, and there is no symlink/path-prefix validation, no re-check that a directory component is not a symlink, and no confinement (`chroot`/`openat`-relative-fd walking) applied before the chmod pass. [5](#0-4)  Note that pass one (`extractZipFileEntry`/`extractZipDirectoryEntry`) is already vulnerable to the same symlink-traversal issue for the write/mkdir itself since these also just call `os.OpenFile`/`os.Mkdir` on `file.Name` without resolving/validating each path component; the chmod pass in `lchmod` inherits and extends this weakness to file permission changes.

### Impact Explanation
An unprivileged pipeline author who supplies a crafted zip artifact/cache (or any zip Runner extracts, e.g. via `artifacts:` downloaded and then re-extracted, or cache restore) can cause the runner process to `chmod` an arbitrary path reachable by the process that performs extraction, limited to whatever permission bits are set on the corresponding zip entry (attacker-chosen `file.Mode()`). This is a permission-integrity violation of files outside the intended extraction root, matching the scoped impact of "permission escalation on host/helper files reachable via symlink target." The severity is bounded by the OS-level permissions of the process performing the extraction (typically the job/helper's own privileges), so it does not by itself grant privilege escalation beyond what that process can already do to files it owns, but it does allow it to alter permissions of files/directories it can traverse to but should not be able to modify from within the "extraction root" model that the invariant (`File operations must stay within intended build/cache/artifact roots`) requires.

### Likelihood Explanation
Fully attacker-controlled: any user who can supply a zip file that Runner extracts (build artifacts, cache archives) can include a symlink entry followed by a same-prefixed file/dir entry. `archive/zip` allows arbitrary entry ordering and modes, and Runner does not reject symlink entries or path entries with symlinks as intermediate components before extraction or before the chmod pass. This is a straightforward, deterministic, repeatable primitive requiring no timing race — it is a logic bug in path resolution, not a race condition (the fact that the exploit uses two static ordered zip entries makes it fully deterministic).

### Recommendation
Before calling `lchmod` (and before `extractZipFile`'s writes), verify that each path component of `file.Name`, when resolved relative to the extraction root, does not cross a symlink — e.g. use `os.Lstat` component-by-component (or `filepath.EvalSymlinks` compared against the extraction root) and reject/skip entries whose containing directory chain includes a symlink, mirroring the "zip slip" defenses already partially represented by `errorIfGitDirectory`. Alternatively, use `*at` syscalls with directory file descriptors obtained via `O_NOFOLLOW` at each path segment (openat-based path walking) rather than passing full string paths to `Fchmodat`/`OpenFile`/`Mkdir`, ensuring no intermediate symlink can redirect an operation outside the extraction directory.

### Proof of Concept
Go unit test in `helpers/archives`:
```go
func TestExtractZipArchive_SymlinkChmodEscape(t *testing.T) {
    dir := t.TempDir()
    require.NoError(t, os.Chdir(dir))

    target := filepath.Join(t.TempDir(), "victim") // stand-in for /etc
    require.NoError(t, os.WriteFile(target, []byte("data"), 0o644))

    buf := &bytes.Buffer{}
    zw := zip.NewWriter(buf)

    // symlink entry "a" -> target dir
    fh := &zip.FileHeader{Name: "a"}
    fh.SetMode(os.ModeSymlink | 0o777)
    w, _ := zw.CreateHeader(fh)
    _, _ = w.Write([]byte(filepath.Dir(target)))

    // file entry "a/victim" with attacker-chosen mode 0o000
    fh2 := &zip.FileHeader{Name: "a/victim"}
    fh2.SetMode(0o000)
    w2, _ := zw.CreateHeader(fh2)
    _, _ = w2.Write([]byte("x"))

    require.NoError(t, zw.Close())
    zr, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))

    _ = ExtractZipArchive(zr)

    info, err := os.Stat(target)
    require.NoError(t, err)
    // Assert the victim file OUTSIDE the extraction dir was not chmod'd to 0o000
    assert.NotEqual(t, os.FileMode(0o000), info.Mode().Perm())
}
```
Expected (current buggy) behavior: the assertion fails because `target`'s permissions are changed to `0o000` via the symlink traversal in `lchmod`. After the fix (component-wise symlink validation before chmod/write), the assertion should pass.

```go
func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}
```

```go
func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}
```

```go
func ExtractZipArchive(archive *zip.Reader) error {
	tracker := newPathErrorTracker()

	for _, file := range archive.File {
		if err := errorIfGitDirectory(file.Name); tracker.actionable(err) {

		}

		}

		}

		if err := processZipExtra(&file.FileHeader); tracker.actionable(err) {
			logrus.Warningf("%s: %s (suppressing repeats)", file.Name, err)
		}
	}

	return nil
}
```

```go
func lchmod(name string, mode os.FileMode) error {
	var flags int

	if runtime.GOOS == "linux" {
		// Linux does not support changing modes on symlinks.
		if mode&os.ModeSymlink != 0 {
			return nil
		}
	} else {
		flags = unix.AT_SYMLINK_NOFOLLOW
	}

	err := unix.Fchmodat(unix.AT_FDCWD, name, uint32(mode.Perm()), flags)
	if err != nil {
		return &os.PathError{Op: "lchmod", Path: name, Err: err}
	}
	return nil
}
```

```go
func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))
	if len(parts) > 0 && parts[0] == ".git" {
		return true
	}
	return false
}

func errorIfGitDirectory(path string) *os.PathError {
	if !isPathAGitDirectory(path) {
		return nil
	}

	return &os.PathError{
		Op:   ".git inside of archive",
		Path: path,
		Err:  errors.New("trying to archive or extract .git path"),
	}
}
```
