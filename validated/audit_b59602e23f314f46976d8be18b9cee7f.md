### Title
Reorg permit misapplied across unrelated tenures allows a signer to double-sign conflicting blocks - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`reorg_permit_stands` decides whether a previously-signed conflicting block should stop blocking a *new* pre-commit-threshold signature. It only checks whether the sortition recorded in `conflict.superseded_by` is still canonical — it never checks that the *currently evaluated* block proposal is actually the tenure that was granted that permit. A permit issued for tenure `B` to replace conflicting tenure `A` therefore also silently excludes `A`'s conflict when a completely unrelated tenure `C` later proposes a conflicting block at the same height, letting the signer place a second signature on a sibling block outside the reorg it actually sanctioned.

### Finding Description
`handle_block_pre_commit` re-checks conflicts before signing at the pre-commit threshold: [1](#0-0) 

The filter excludes a conflict from blocking whenever `reorg_permit_stands(stacks_client, conflict)` is true. That function's contract is documented as excluding the conflict "entirely" once the permit is standing: [2](#0-1) 

Its implementation, however, only takes the `SignedConflictInfo` (the *old* conflicting block) and asks whether `conflict.superseded_by`'s sortition is still canonical — it takes no reference to the block currently being signed, so it cannot verify that the block now crossing the pre-commit threshold is the same tenure that was actually sanctioned to replace the conflict: [3](#0-2) 

Because the exclusion is keyed purely on "is the *permitted* tenure still canonical," not "is *this* proposal the permitted tenure," a permit granted once (recorded via `check_parent_tenure_choice`/`mark_tenure_superseded` when tenure `B` was sanctioned to reorg tenure `A`) remains standing and will exclude `A`'s conflict for any later, unrelated tenure `C` that also conflicts with `A` at the same height — as long as `B`'s sortition has not itself been orphaned. This breaks the one-signature-per-height invariant that section 5 of the signer flow otherwise enforces via `conflict_still_blocks`/freshness/own-tenure checks: those guards are bypassed entirely once a standing (but contextually unrelated) permit exists.

### Impact Explanation
This is a Critical-class issue per the scope rules: it allows a single signer (with its normal weight, no majority needed) to place its signature on two conflicting blocks at the same height across different tenures, i.e., a signer signing a conflicting block that its own conflict-guard machinery was designed to prevent. If enough signers hit the same stale permit state, this contributes signatures toward two competing blocks at the same height, undermining the "signer signs at most one block per height" safety property the whole pre-commit/conflict design in `signer.rs` is built to guarantee.

### Likelihood Explanation
This requires a specific but reachable sequence with only gossip/proposals from a single (possibly the attacking) miner: (1) tenure `B` is legitimately sanctioned via `check_parent_tenure_choice`'s reorg-timing rules to replace tenure `A` (recording `superseded_by = B` on `A`'s conflict record), (2) `B`'s sortition remains canonical thereafter, and (3) a different tenure `C` later proposes a block conflicting with `A` at the same height. Steps 1–3 are all things a one-slot miner (plus normal chain activity) can arrange without cooperation from other signers, making this a realistically reachable, not purely theoretical, path.

### Recommendation
`reorg_permit_stands` should also verify that the block currently being evaluated (its `consensus_hash`/tenure) matches `conflict.superseded_by`'s recorded tenure before excluding the conflict, rather than only checking that the recorded superseding sortition remains canonical.

### Proof of Concept
Conceptually:
1. Signer signs block `A1` in tenure `A`.
2. Reorg-timing rules sanction tenure `B` to replace `A` (permit recorded, `superseded_by = B`, `B` still canonical).
3. Before/while `B` is pending, tenure `C` (a different, unrelated tenure) proposes block `C1` at the same height as `A1`, conflicting with `A1` but not `B`.
4. In `handle_block_pre_commit` for `C1`, `get_signed_conflicts` returns `A1`'s conflict record (with `superseded_by = B`); `reorg_permit_stands` returns `true` solely because `B`'s sortition is canonical, excluding `A1` from blocking — with no check that `C1` is `B`.
5. The signer proceeds to sign `C1`, now having signed two conflicting same-height blocks (`A1` and `C1`), even though only `B` was ever sanctioned to replace `A1`.

Note: I was not able to inspect the full `SignedConflictInfo`/`get_signed_conflicts`/`check_parent_tenure_choice`/`mark_tenure_superseded` implementations in `stacks-signer/src/signerdb.rs` within the available tool budget to rule out an additional tenure-matching guard elsewhere in that call chain; the finding is based on the `reorg_permit_stands` function signature and body shown above, which contain no such check.

    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
    }
