## Title
Deleting an access key via `DeleteKey` does not purge its stale confirmations from other pending requests, allowing a multisig request to execute below the live-signer threshold - (File: multisig/src/lib.rs)

## Summary
The multisig contract's `DeleteKey` action only removes requests that were *created* by the deleted key, but never scans the `confirmations` map to strip that key's approval from *other* pending requests it had merely confirmed. As a result, a confirmation cast by a key that is later removed from the multisig keeps counting toward `num_confirmations`, letting a request execute with fewer live, valid signers than the configured threshold requires.

## Finding Description
`confirm()` checks the size of the stored confirmation set against `num_confirmations` and, once satisfied, executes the request: [1](#0-0) 

The `DeleteKey` action's cleanup logic filters requests by `r.signer_pk == pk` — i.e., only requests *originated* by the deleted key — and removes confirmations for those requests only: [2](#0-1) 

It never iterates `self.confirmations` to remove the deleted key's public key from confirmation sets of requests it did not create but had already confirmed. The `MultiSigContract` stores confirmations as raw `HashSet<PublicKey>` per request, decoupled from any "is this key still a live signer" check at confirm time: [3](#0-2) 

The intended custody binding is: *a request executes only when the number of confirmations from currently-valid signers ≥ `num_confirmations`*. The actual code enforces: *a request executes when the raw stored confirmation-set size ≥ `num_confirmations`*, regardless of whether each entry's key is still a valid member of the multisig. The exact same defect exists in the successor contract's `delete_member`, which filters `r.member == member` (requests created by the removed member) without purging that member's confirmations from other requests: [4](#0-3) 

## Impact Explanation
This breaks an authorization/threshold boundary explicitly called out as Critical: "a multisig request executed below threshold." Concretely:
1. A pending request `X` (e.g., a large `Transfer`) is created and confirmed by key `A` (confirmations = `{A}`).
2. The multisig, via a separate, properly-confirmed governance request, removes key `A` (`DeleteKey`/`DeleteMember`). The cleanup only removes requests *created by* `A`; request `X` (created by someone else) still has `A` in its confirmation set even though `A` is no longer a valid signer.
3. A minority of the remaining live keys (fewer than `num_confirmations` legitimate signers) confirm `X`. Because the stale confirmation from the removed key `A` is still counted, `confirmations.len() + 1 >= num_confirmations` is satisfied and `X` executes — funds move, keys are added, or contract code is deployed with fewer live approvals than the account's security policy requires.

This is a genuine solvency/authorization violation for a NEAR account protected by this multisig: the number of NEAR-controlling parties that actually approved the fund movement is less than the configured threshold.

## Likelihood Explanation
Likelihood is Medium-to-High in any multisig that rotates keys/members over time (a normal, expected operational event, not an edge case). No external unprivileged attacker is needed — a minority coalition of remaining keyholders can exploit leftover stale confirmations from any key removed after it confirmed but before its own request was executed, effectively lowering the real threshold below the documented one for that specific pending request. The bug is purely a code-level gap in cleanup logic reachable through the contract's normal `DeleteKey`/`DeleteMember` action, not through any owner-only backdoor or off-chain assumption.

## Recommendation
When executing `DeleteKey` (or `DeleteMember` in `multisig2`), iterate over all entries of `self.confirmations` (not just requests created by the removed key/member) and remove the deleted key/member from every confirmation set it appears in. Alternatively, validate at `confirm()` time (or at execution time) that every public key/member recorded in a request's confirmation set is still a current member of the multisig before counting it toward `num_confirmations`.

## Proof of Concept
Assume a 3-of-4 multisig with keys `A, B, C, D`.
1. `D` calls `add_request` to create request `X: Transfer { amount: <all_funds>, receiver_id: attacker }`.
2. `A` calls `confirm(X)` → `confirmations[X] = {A}` (1 < 3, stored, not executed): [1](#0-0) 
3. `B` calls `confirm(X)` → `confirmations[X] = {A, B}` (2 < 3, stored, not executed).
4. A separate, fully-confirmed request `Y: DeleteKey { public_key: A }` executes, removing `A` as a valid signer. Only requests where `signer_pk == A` (i.e., requests `A` created) are purged; `X`'s confirmation set `{A, B}` is untouched: [2](#0-1) 
5. `C` (colluding with `D`, who created `X`) calls `confirm(X)`. Check: `confirmations[X].len() (=2) + 1 = 3 >= num_confirmations (3)` → request executes, transferring all funds to `attacker`, even though only `B`, `C`, and `D` are live signers who genuinely approved (and `D` created it) — `A`'s stale confirmation counted toward the threshold despite `A` no longer being a member.

## Uncertainties
I was not able to fully trace whether `add_request` combined with `confirm` in the same transaction changes the ordering enough to prevent this exact sequence in all client-side flows (e.g., whether `add_request_and_confirm` is used more commonly than plain `add_request`), but the core code-level gap — no purge of a removed key/member's confirmations on requests it did not create — is confirmed directly in both `multisig/src/lib.rs` and `multisig2/src/lib.rs`.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
