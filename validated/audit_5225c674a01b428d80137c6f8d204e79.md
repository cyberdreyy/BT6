### Title
Loss-adjusted withdraw receipts escape the haircut because `collectWithdrawFunds` records `lossRecoveryPriceByEpoch` under the post-increment `epochNumber` while receipts are indexed by the pre-increment `lastWithdrawRequest` epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In `IdleCreditVault`, pending withdraw receipts are indexed by the epoch in which they were requested (`lastWithdrawRequest[_user]`, `withdrawsRequestsByEpoch[_user][currentEpoch]`), but a realized `stopEpochWithDuration` loss is recorded in `lossRecoveryPriceByEpoch[epochNumber]` using `epochNumber` as it stands inside `collectWithdrawFunds`. `epochNumber` is incremented inside `deposit()` whenever `isEpochRunning()` is still true — i.e., during the same `stopEpoch` transaction, before the running flag is cleared. If the CDO performs its `deposit()` (buffer deposits / repaid liquidity) before calling `collectWithdrawFunds` to pull the funded withdrawal amount, the haircut is stored under the *new* epoch while every affected receipt still points at the *old* epoch. The stale index behaves exactly like the SquashFS bug class: an attacker-influenced index (`lastWithdrawRequest`) reads a slot that was never populated for that key (`lossRecoveryPriceByEpoch[oldEpoch] == 0`), the "no haircut" result is then fed into `_claimFundedWithdrawRequest`, which pays the receipt at par even though the borrower only funded `pendingToFund < pendingBasis`.

### Finding Description
- `requestWithdraw` tags each receipt with `currentEpoch = epochNumber` via `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (IdleCreditVault.sol:260-294). [1](#0-0) 
- `deposit()` increments `epochNumber` when called while `isEpochRunning()` is still true — the comment confirms this happens "on stopEpoch (before setting the var to false)" (IdleCreditVault.sol:607-611). [2](#0-1) 
- `collectWithdrawFunds` records the loss haircut under `lossRecoveryPriceByEpoch[epochNumber]` at whatever value `epochNumber` holds when it runs (IdleCreditVault.sol:411-426). [3](#0-2) 
- `_claimLossAdjustedWithdrawRequest` looks up the haircut via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the *request* epoch (IdleCreditVault.sol:789-800). [4](#0-3) 
- `_claimFundedWithdrawRequest` only blocks claims while `epochNumber <= lastWithdrawRequest[_user]`; once `epochNumber` has been bumped past the request epoch it pays `withdrawsRequests[_user]` in full at par (IdleCreditVault.sol:326-349). [5](#0-4) 

After the loss epoch ends, `epochNumber` (E+1) is strictly greater than `lastWithdrawRequest` (E), so the funded-claim gate passes; `lossRecoveryPriceByEpoch[E] == 0` so the loss-adjusted path returns 0; the user is paid `claimBasis` at par while the strategy only holds `claimBasis * lossRecoveryPrice` from that receipt. The haircut intended by `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` is silently skipped.

### Impact Explanation
Every pending receipt in the loss epoch is redeemable at par while the strategy received only the loss-adjusted funding. Early claimants drain the contract's funded balance plus any other underlying held (other funded receipts, APR0 settled amounts), and later claimants' transactions revert on insufficient balance — direct theft of other users' funded withdrawals plus protocol insolvency equal to the aggregate haircut `pendingBasis * (1 - lossRecoveryPrice)`. The `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`; it does not stop over-withdrawal of the funded bucket.

### Likelihood Explanation
The trigger requires only that `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` calls `strategy.deposit()` before `collectWithdrawFunds()` within the same transaction, which matches the documented design ("deposit done on stopEpoch") since the deposit must precede loss accounting to set the new NAV. An unprivileged lender needs only a pending withdraw request in the loss epoch — no privileged role involved. Note: I was unable to confirm the exact call order inside `IdleCDOEpochVariant.stopEpochWithDuration` within this session's tool budget; if `collectWithdrawFunds` is invoked strictly before any `deposit()` in that flow, `epochNumber` is still the request epoch and the keys match, invalidating the finding. The PoC below asserts that ordering and will fail harmlessly if the ordering is safe.

### Recommendation
In `collectWithdrawFunds`, key the haircut by the epoch the pending receipts belong to (e.g., `epochNumber - 1` when called post-increment during `stopEpoch`, or better, pass the claim epoch explicitly from the CDO), or record per-epoch pending basis via an `pendingWithdrawsByEpoch` mapping instead of relying on the implicit "all pending receipts share `epochNumber`" invariant. Alternatively, move the `epochNumber` increment out of `deposit()` into an explicit `stopEpoch` hook ordered before funding collection.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../../contracts/interfaces/IERC20Detailed.sol";

/// Fork-style PoC: loss haircut is keyed by post-increment epochNumber,
/// so loss-epoch receipts claim at par and drain other users' funds.
contract LossEpochMismatchPoC is Test {
    IdleCDOEpochVariant cdo;
    IdleCreditVault strategy;
    IERC20Detailed underlying;
    address manager;
    address borrower;
    address userA = makeAddr("userA");
    address userB = makeAddr("userB");

    function test_LossReceiptsEscapeHaircut() external {
        // 1. userA and userB deposit equal amounts during buffer, epoch starts.
        // 2. Both request withdraw of their full positions in epoch E
        //    (unscaledApr != 0 path): lastWithdrawRequest[u] = E,
        //    withdrawsRequestsByEpoch[u][E] = amount, pendingWithdraws = 2*amount.
        // 3. Manager stops the epoch with a loss:
        //    stopEpochWithDuration computes pendingToFund < pendingBasis via
        //    previewLossAdjustedWithdrawFunds; inside the same tx the CDO calls
        //    strategy.deposit(...) which bumps epochNumber to E+1 while
        //    isEpochRunning() is still true, then calls collectWithdrawFunds(pendingToFund).
        uint256 epochAtRequest = strategy.epochNumber();
        vm.prank(manager);
        // loss = 50% of pending basis
        cdo.stopEpochWithDuration(/* apr, interest, duration, _lossAmount */);

        // Assert the mismatch: haircut recorded under E+1, receipts under E.
        assertGt(strategy.lossRecoveryPriceByEpoch(epochAtRequest + 1), 0);
        assertEq(strategy.lossRecoveryPriceByEpoch(epochAtRequest), 0);
        assertEq(strategy.epochNumber(), epochAtRequest + 1);

        // 4. userA claims: loss-adjusted path reads epoch E (price 0 -> skip),
        //    funded gate sees epochNumber (E+1) > lastWithdrawRequest (E) -> passes,
        //    pays withdrawsRequests[userA] at PAR instead of * lossRecoveryPrice.
        uint256 balBefore = underlying.balanceOf(userA);
        vm.prank(userA);
        cdo.claimWithdrawRequest();
        uint256 paidA = underlying.balanceOf(userA) - balBefore;

        uint256 basisA = /* recorded basis for userA */;
        uint256 price = strategy.lossRecoveryPriceByEpoch(epochAtRequest + 1);
        // userA received full basis although only basisA*price was funded for them.
        assertEq(paidA, basisA);
        assertGt(paidA, (basisA * price) / 1e18);

        // 5. userB's identical claim now reverts on insufficient strategy balance:
        //    the contract paid out more than the funded amount -> insolvency.
        vm.prank(userB);
        vm.expectRevert(); // SafeERC20 transfer fails / NotAllowed
        cdo.claimWithdrawRequest();
    }
}
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
