### Title
JWT replay-protection race condition allows a single-use trigger JWT to authorize multiple concurrent workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The `Authorize` method of `WorkflowMetadataHandler` implements JWT single-use replay protection using two separate, non-atomic operations — `isReplay(claims.ID)` (a read-locked check) followed later by `recordUsage(claims.ID)` (a write-locked record) — with unrelated authorization logic executed in between. This is the same "check happens, but the state-mutation that closes the window is deferred" pattern from the reported `LiquidStakingManager.withdrawETHForKnot` bug: the guard against reuse is applied *after* the guarded action has already been permitted to proceed, leaving a window in which the same credential can be used more than once.

### Finding Description
`Authorize` in [1](#0-0)  is called from the internet-facing gateway's HTTP trigger path to validate an unprivileged client's signed one-time JWT before allowing a workflow-execute request to proceed. The single-use enforcement is implemented as: [2](#0-1) 

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()
	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	cache.cache[jti] = time.Now()
}
```

`Authorize` calls `isReplay` at the start, then performs signature verification and workflow-authorized-key lookups, and only calls `recordUsage` at the very end, after the caller has already been granted the authorized key: [3](#0-2) 

Because `isReplay` and `recordUsage` are two distinct lock acquisitions rather than one atomic check-and-set (as correctly implemented elsewhere in the same codebase via `RequestReplayGuard.CheckAndRecord`, which holds a single mutex across the check and the write: [4](#0-3) ), two concurrent `Authorize` calls presenting the identical JWT can both pass `isReplay` (both see "not seen yet") before either one calls `recordUsage`. This mirrors the `LiquidStakingManager` bug: the "ban" (state update marking the credential consumed) is performed only after the protected action (granting the authorized key / allowing the workflow trigger to be forwarded to nodes) has already been permitted to happen, allowing the guarded action to occur more than once for what is meant to be a strictly single-use token.

### Impact Explanation
JWTs used for HTTP-triggered workflow execution are explicitly documented as single-use, keyed by `jti`, to prevent replay: [5](#0-4) . If the check-then-record window is won by concurrent requests, an unprivileged external caller can cause a single signed trigger JWT to authorize and dispatch a workflow-execute request more than once (request impersonation/duplication using a credential intended for exactly one use). Depending on the workflow being triggered, this can cause duplicate/unintended workflow executions, resource exhaustion, or duplicate side effects downstream (e.g. duplicate on-chain or off-chain actions initiated by the workflow) — an availability/integrity impact stemming from bypassing an intended one-time-use quota/authorization guarantee at the gateway layer.

### Likelihood Explanation
Exploitation requires an attacker capable of sending the exact same signed JWT concurrently to the node's gateway-facing trigger handler (e.g., firing the same HTTP request in parallel, or a legitimate proxy/retry mechanism racing itself). Since the JWT itself is attacker/client-supplied and the race window covers full request-authorization processing (network calls, verification, key set lookups), the window is non-trivial in real-world latency, making the race plausible but not guaranteed on every attempt — it is a timing-dependent bug rather than a deterministic bypass.

### Recommendation
Replace the separate `isReplay`/`recordUsage` calls with a single atomic check-and-record operation performed under one lock acquisition, following the same pattern already used correctly by `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`. Concretely, add a method such as:

```go
func (cache *jwtReplayCache) checkAndRecord(jti string) error {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	if _, exists := cache.cache[jti]; exists {
		return errors.New("JWT token has already been used")
	}
	cache.cache[jti] = time.Now()
	return nil
}
```
and call it once, immediately, before any other authorization logic in `Authorize`, so that the "banning" of the `jti` happens atomically with the check rather than being deferred to the end of the function.

### Proof of Concept
Two goroutines calling `WorkflowMetadataHandler.Authorize(workflowID, sameTokenString, req)` concurrently with the identical signed JWT (same `jti`) can both observe `isReplay(claims.ID) == false` before either calls `recordUsage(claims.ID)`, because the two operations are separated by signature verification and map lookups and use independent lock acquisitions. Both calls would then proceed to return a valid authorized key, resulting in the same one-time JWT being accepted twice — analogous to the `NonEOARepresentative` reentrancy PoC in the reported finding, where the state-mutating "ban" happens too late relative to the already-permitted action. This could not be run against a live binary in this analysis; verification would require a concurrency test in `workflow_metadata_handler_test.go` that fires `Authorize` from two goroutines with the same token and asserts both succeed, similar in structure to the existing `TestRequestReplayGuard_ConcurrentAccess` test used for the correctly-fixed vault guard: [6](#0-5) .

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func TestRequestReplayGuard_ConcurrentAccess(t *testing.T) {
	guard := NewRequestReplayGuard()
	futureExpiry := time.Now().UTC().Unix() + 100

	const goroutines = 100
	results := make([]error, goroutines)
	var wg sync.WaitGroup
	wg.Add(goroutines)

	for i := range goroutines {
		go func(idx int) {
			defer wg.Done()
			results[idx] = guard.CheckAndRecord("same-digest", futureExpiry)
		}(i)
	}
	wg.Wait()

	successCount := 0
	duplicateCount := 0
	for _, err := range results {
		if err == nil {
			successCount++
		} else {
			require.ErrorIs(t, err, ErrRequestAlreadySeen)
			duplicateCount++
		}
	}

	assert.Equal(t, 1, successCount, "exactly one goroutine should succeed")
	assert.Equal(t, goroutines-1, duplicateCount, "all others should be rejected as duplicates")
}
