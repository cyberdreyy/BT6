### Title
Post-default claim clears `lastWithdrawRequest` before the loss-adjusted path reads it, letting a defaulted-epoch requester claim an older haircutted receipt at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`claimWithdrawRequest` settles claims in a fixed order: post-default, defaulted-epoch, loss-adjusted, then funded-at-par. The defaulted-epoch path (`_clearWithdrawClaimForEpoch`) resets `lastWithdrawRequest[_user]` to `0` when it equals the default epoch. The very next step, `_claimLossAdjustedWithdrawRequest`, derives the loss epoch from `lastWithdrawRequest[_user]` — now `0` — finds `lossRecoveryPriceByEpoch[0] == 0` and silently skips. The older, haircutted receipt basis is still inside the `withdrawsRequests[_user]` aggregate, so `_claimFundedWithdrawRequest` pays it at par. This is the direct analog of the kernel bug: state consumed after being cleared (UAF ordering), where the fix was to free `bfqq` only after `bic_set_bfqq()` used it.

### Finding Description

Relevant code in `contracts/strategies/idle/IdleCreditVault.sol`:

```solidity
// line 301-314
function claimWithdrawRequest(address _user) external returns (uint256 amount) {
  _onlyIdleCDO();
  if (defaultRecoveryFinalized) {
    amount = _claimPostDefaultWithdrawRequest(_user);
    if (amount != 0) return amount;
    amount = _claimDefaultedWithdrawRequest(_user);   // may zero lastWithdrawRequest
  }
  amount += _claimLossAdjustedWithdrawRequest(_user);  // reads lastWithdrawRequest
  return amount + _claimFundedWithdrawRequest(_user);  // pays aggregate at par
}
```

`_clearWithdrawClaimForEpoch` (lines 832-836):

```solidity
if (lastWithdrawRequest[_user] == _claimEpoch) {
  lastWithdrawRequest[_user] = 0;
}
```

`_claimLossAdjustedWithdrawRequest` (lines 789-801) keys the haircut off `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, which is `0` after the reset. Meanwhile `collectWithdrawFunds` (lines 411-430) never removes the loss-epoch basis from `withdrawsRequests[_user]` — only `_claimLossAdjustedWithdrawRequest` does that via `_clearWithdrawClaimForEpoch`. So when the loss path is skipped, `_claimFundedWithdrawRequest` (lines 319-350) sees `normalAmount = withdrawsRequests[_user]` still containing the epoch-X basis, passes the epoch check because `lastWithdrawRequest` is now `0`, burns the receipt tokens, and calls `_transferFundedClaim` for the full amount.

Attack sequence (all unprivileged):
1. Deposit into a tranche; `requestWithdraw` in epoch X.
2. `stopEpochWithDuration` realizes a loss; `collectWithdrawFunds` funds `pendingBasis * price` and stores `lossRecoveryPriceByEpoch[X]`. Do not claim.
3. Request withdraw again in a later epoch Y (`lastWithdrawRequest = Y`).
4. Borrower defaults during epoch Y; owner finalizes recovery → `defaultRecoveryEpoch = epochNumber = Y`, `defaultRecoveryFinalized = true`.
5. Call `claimWithdrawRequest`. Defaulted path clears epoch Y and zeroes `lastWithdrawRequest`; loss path is skipped; funded path pays the epoch-X basis at par instead of at `lossRecoveryPriceByEpoch[X]`.

### Impact Explanation

Direct theft / insolvency. The strategy only received `basis_X * lossRecoveryPrice` from the borrower for epoch-X receipts, but the attacker extracts `basis_X` — an overpayment of `basis_X * (1 - lossRecoveryPrice)` taken from funded underlying that belongs to other pending claimants and active LPs. With a 50% haircut on a large epoch-X request, the attacker drains roughly half of that basis from the vault's withdrawal reserve, leaving other claimants undercollateralized.

### Likelihood Explanation

Requires a `stopEpochWithDuration` loss epoch followed later by a borrower default that gets finalized — both plausible adverse-market events in a credit vault, and the attacker controls only timing of their own `requestWithdraw`/`claimWithdrawRequest` calls (standard, permitted user actions). The only precondition is holding an unclaimed haircutted receipt while making a second request in the epoch that defaults.

### Recommendation

Do not let the defaulted-epoch clearing erase the marker the loss-adjusted path depends on. Either clear the loss-adjusted claim before the defaulted claim, or have `_clearWithdrawClaimForEpoch` recompute `lastWithdrawRequest` to the user's most recent remaining non-zero `withdrawsRequestsByEpoch` entry instead of zeroing it, and/or explicitly track and settle the loss-epoch receipt during default clearing so it cannot fall through to the par-payout aggregate.

### Proof of Concept

A Foundry fork PoC should: (1) run an epoch variant with `IdleCreditVault` strategy where `defaultRecoveryInitialized` is true; (2) user deposits, calls `requestWithdraw`, then manager stops epoch via `stopEpochWithDuration(..., lossAmount)` so `lossRecoveryPriceByEpoch[e1]` is set; (3) user calls `requestWithdraw` again in epoch e2; (4) borrower fails to fund → default → `finalizeDefaultRecovery`; (5) user calls `cdoEpoch.claimWithdrawRequest()` and assert received amount equals `basis_e2 * defaultRecoveryPrice + basis_e1` (par) instead of `basis_e1 * lossRecoveryPriceByEpoch[e1]`; assert strategy underlying balance is depleted by the excess.
