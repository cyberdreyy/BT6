### Title
Unbounded zstd decompression in `UiAccountData::decode` allows single-request memory exhaustion via `simulateTransaction` account overwrites - ([File: account-decoder-client-types/src/lib.rs])

### Summary
`UiAccountData::decode` for the `Base64Zstd` variant streams a client-controlled zstd blob into `read_to_end` with no maximum output size, so a small, highly-compressible payload can force the RPC process to allocate an arbitrarily large `Vec<u8>` while decoding a single `simulateTransaction` request that supplies `accounts.overwrite` entries with `Base64Zstd`-encoded data.

### Finding Description
In `UiAccountData::decode`, the `Base64Zstd` branch does the following with zero bound on the decompressed size: [1](#0-0) 

```rust
UiAccountEncoding::Base64Zstd => {
    BASE64_STANDARD.decode(blob).ok().and_then(|zstd_data| {
        let mut data = vec![];
        zstd::stream::read::Decoder::new(zstd_data.as_slice())
            .and_then(|mut reader| reader.read_to_end(&mut data))
            .map(|_| data)
            .ok()
    })
}
```

This is invoked from `UiAccount::to_account_shared_data` / `UiAccount::to_account`: [2](#0-1) 

`read_to_end` will keep growing the output buffer and reading decompressed bytes until the compressed stream is exhausted or an allocation failure occurs — there is no ceiling tied to the account's declared/expected size or any global cap. Zstd streams can achieve extremely high compression ratios (e.g., an all-zero payload of hundreds of MB to GB compresses to a few KB), so an attacker can submit a tiny base64 blob that decompresses into a multi-gigabyte buffer, driving the process to allocate that much memory (or OOM) for a single request.

The RPC surface that reaches this code is `simulateTransaction`'s account overwrite mechanism, which parses client-supplied `UiAccount`/`UiAccountData` values from `accounts.overwrite` config and decodes them into `AccountSharedData` before executing the simulated transaction (via `get_account_from_overwrites_or_bank` and the `to_account_shared_data`/`to_account` conversion functions this decode path backs). No length or decompressed-size check exists at the RPC layer before or during this decode; the existing guard is only a JSON/base64 encoding check, not a decompressed-size limit.

### Impact Explanation
A single unprivileged JSON-RPC `simulateTransaction` call containing a crafted `Base64Zstd` account blob in `accounts.overwrite` can force the validator's RPC process to allocate an unbounded amount of memory during account decoding, potentially causing large memory pressure, OOM, or a validator/RPC process crash from a single low-rate request — falling into the "unbounded cost for a single low-rate call" / RPC DoS category.

### Likelihood Explanation
This requires no special privileges: only a properly formed `simulateTransaction` JSON-RPC call with `accounts.overwrite` entries using `"base64+zstd"` encoding, well within the "one call per `CLUSTER_SLOT_TIME_TARGET / 2`" constraint. Constructing a highly-compressible zstd stream (e.g., large run of zero bytes) is trivial and reproducible, making this readily exploitable whenever the `zstd` feature is compiled in and the RPC accepts this encoding for overwrites.

### Recommendation
Bound the decompression in `UiAccountData::decode`'s `Base64Zstd` branch, e.g., use `zstd::stream::read::Decoder` with a fixed maximum output size (read into a bounded buffer / use `Read::take(MAX_DECODED_SIZE)` before `read_to_end`, or leverage zstd's window/size limits), and reject the decode (return `None`/error) if the limit would be exceeded. The cap should be aligned with the maximum legitimate on-chain account size (`solana_sdk::system_instruction::MAX_PERMITTED_DATA_LENGTH` or similar) rather than left unbounded.

### Proof of Concept
```rust
// account-decoder-client-types/src/lib.rs (test) or a new integration test
#[test]
fn test_base64_zstd_decompression_bomb() {
    use base64::{Engine, prelude::BASE64_STANDARD};

    // Compress ~1 GiB of zeros into a tiny stream.
    let huge = vec![0u8; 1024 * 1024 * 1024]; // 1 GiB
    let mut encoder = zstd::stream::write::Encoder::new(Vec::new(), 0).unwrap();
    use std::io::Write;
    encoder.write_all(&huge).unwrap();
    let compressed = encoder.finish().unwrap();
    assert!(compressed.len() < 1024 * 1024); // a few KB/MB compressed

    let blob = BASE64_STANDARD.encode(&compressed);
    let ui_data = UiAccountData::Binary(blob, UiAccountEncoding::Base64Zstd);

    // EXPECTED (after fix): decode() should return None or an error because the
    // decompressed size exceeds a defined maximum, instead of allocating 1 GiB.
    let decoded = ui_data.decode();
    assert!(decoded.is_none(), "decode() must enforce a max decompressed-size limit");
}
```

This test should be extended into an RPC-level integration test that sends a single `simulateTransaction` call with `accounts.overwrite` containing this crafted blob and asserts the RPC server rejects or bounds the request rather than allocating unbounded memory.
