### Title
Unbounded Vec Growth via O(n) Linear-Scan Existence Check in Accounts Secondary Index - (File: `accounts-db/src/accounts_index/secondary.rs`)

### Summary
The `SecondaryIndex::insert()` function in `accounts-db/src/accounts_index/secondary.rs` uses an O(n) `Vec::contains()` scan to deduplicate the `reverse_index` entry for an account before pushing a new value, and never prunes stale values on update. An ordinary user can repeatedly change the SPL-Token "authority" (owner) field of a single token account they control (e.g. via `SetAuthority`), causing this per-account `Vec<Pubkey>` to grow without bound on any validator/RPC node running with `--account-index spl-token-owner` (or `program-id`/`spl-token-mint`) enabled. This mirrors the `PrimeStrategy._checkExists()` bug class: an attacker-controlled, ever-growing array checked with a linear scan on every insert.

### Finding Description
`AccountsIndex::update_secondary_indexes()` is invoked for every account write when secondary indexes are enabled, regardless of whether the write comes from a normal transaction, cache flush, or snapshot load: [1](#0-0) 

For SPL token accounts it extracts the packed `owner`/`mint` fields directly from account data and calls `SecondaryIndex::insert(key, pubkey)`: [2](#0-1) 

Inside `insert()`, the reverse-index entry for the account (`inner_key`) is a `RwLock<Vec<Pubkey>>` (`SecondaryReverseIndexEntry`), explicitly commented as being "rare" to grow, and deduplicated with a linear `contains()` scan before `push`: [3](#0-2) [4](#0-3) 

Critically, when the tracked value (e.g. the token account's authority) changes, the old association is **not removed** — a new outer key is simply appended if not already present. Removal from `reverse_index` (`remove_index_entries`/`remove_inner_key`) is only reachable through the dead-key purge path (`purge_secondary_indexes_by_inner_key_if`, called via `handle_dead_keys` when the account itself is fully removed from the primary index), not on ordinary value updates: [5](#0-4) 

This is validated by the test `run_test_secondary_indexes_same_slot_and_forks`, which shows that setting a second, distinct index value for the same account key causes **both** old and new values to persist simultaneously in the index rather than replacing the old one: [6](#0-5) 

Since the SPL Token `SetAuthority` instruction lets the current authority reassign the account's authority field to an arbitrary new pubkey at will, an ordinary user can drive an unbounded number of distinct historical "owner" values for a single account they control, each one adding an entry to that account's `reverse_index` `Vec`, growing it forever and making every subsequent `insert()` (and any code that calls `.len()`/iterates the Vec) progressively slower — the exact O(n) unbounded-array pattern described in the referenced report.

### Impact Explanation
This affects any validator or RPC node operator that enables `--account-index spl-token-owner` (or `program-id` / `spl-token-mint`), which is a common configuration for RPC providers serving `getTokenAccountsByOwner`/`getProgramAccounts` with index acceleration. An attacker paying only ordinary transaction fees can force unbounded, permanent (in-memory, for the life of the account until it's closed) growth of a `Vec` guarded by a global `DashMap` lock, degrading indexing performance and increasing memory usage on the affected node over time, potentially exhausting resources or slowing down index maintenance/lookups for that node. This is a Denial-of-Service class issue localized to accounts-db indexing rather than a consensus-breaking bug, since the secondary index is a local, opt-in acceleration structure and not part of consensus.

### Likelihood Explanation
Likelihood is moderate: it requires the node operator to have opted into the secondary index feature, but exploitation itself requires nothing beyond ordinary permissionless transactions (repeated `SetAuthority` calls on a self-owned token account), each of which is cheap and requires no special privilege, CPI trickery, or validator cooperation.

### Recommendation
Replace the per-account `Vec<Pubkey>` reverse-index membership check with an O(1) structure (e.g. `HashSet<Pubkey>`), and/or actively remove the previous outer-key association when a tracked field changes value (rather than only pruning on full account death), so that at most one historical association per account is retained instead of accumulating every value ever observed.

### Proof of Concept
1. Run a node with `--account-index spl-token-owner` enabled.
2. Create a single SPL Token account and become its authority.
3. Submit a sequence of `SetAuthority` (AuthorityType::AccountOwner) transactions from the current authority, each time setting a brand-new random pubkey as the new authority, repeated N times (e.g. 100,000) across different slots.
4. Each call causes `update_secondary_indexes` → `spl_token_owner_index.insert(new_owner, token_account_pubkey)` to append a new entry to `reverse_index[token_account_pubkey]` because the previous authority is never removed.
5. Observe `reverse_index` for that account key growing to N entries, with `insert()`'s `outer_keys.contains(key)` scan cost increasing linearly with N, degrading indexing throughput and increasing memory usage on the node.

        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.

            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

    /// Removes `inner_key` from `outer_key`'s map.
    ///
    /// Must only be called by remove_by_inner_key_if(), or equiv, that is
    /// holding a lock on self.reverse_index.
    fn remove_index_entries(&self, outer_key: &Pubkey, inner_key: &Pubkey) -> bool {
        let Some(inner_keys) = self.index.get_mut(outer_key) else {
            // we were told that inner_key is in the outer_key map,
            // so the outer_key map should exist!
            panic!(
                "{}: bad index: missing entry for outer_key={outer_key} (inner_key={inner_key})",
                self.metrics_name
            );
        };

        let was_removed = inner_keys.value().remove_inner_key(inner_key);
        if !was_removed {
            // we were told that inner_key is in the outer_key map,
            // so the outer_key map should contain the inner_key!
            panic!(
                "{}: bad index: missing entry for inner_key={inner_key} in map for \
                 outer_key={outer_key}",
                self.metrics_name
            );
        }

        // Before dropping the lock, check if the outer_key map is empty.
        // Because if it is *not* empty, we can skip checking again below.
        let is_outer_key_empty = inner_keys.is_empty();
        drop(inner_keys);

        if is_outer_key_empty {
            // If the outer_key map was empty, we'll check again and remove it if still empty.
            // If it is no longer empty, that is fine, it was re-added, and nothing to do here.
            self.index
                .remove_if(outer_key, |_, inner_keys| inner_keys.is_empty());
        }
        was_removed
    }
