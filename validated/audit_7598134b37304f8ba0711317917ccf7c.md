## Title
Partial withdrawals from a "tokenless-repayments-complete" bank burn shares for the full requested amount but transfer only `min(requested, vault_balance)`, silently destroying user value - ([File: programs/marginfi/src/instructions/marginfi_account/withdraw.rs])

### Summary
`lending_account_withdraw` computes the share deduction from the user-requested `amount_pre_fee` *before* checking whether the bank's liquidity vault actually holds that many tokens. When the bank has the `TOKENLESS_REPAYMENTS_COMPLETE` flag set (used after a forced deleverage/bankruptcy write-off leaves the bank's liquidity vault underfunded), the code clamps only the *transferred* amount to the vault's actual balance, but never adjusts the shares that were already burned for the original, larger requested amount. This mirrors the ReaperVaultERC4626 bug: the `value` actually transferred can be less than the `assets`/shares accounted for, and the transaction does not revert on the shortfall.

### Finding Description
In `lending_account_withdraw` [1](#0-0) , for a non-`withdraw_all` (partial) withdrawal, `amount_pre_fee` is derived directly from the user-supplied `amount`, and `bank_account.withdraw(I80F48::from_num(amount_pre_fee))` immediately burns the corresponding shares from the user's position.

Only afterwards does the code check whether the bank is in the tokenless-repayment-complete state and clamp the transfer amount to what the vault actually holds: [2](#0-1) 

The clamped, lower `amount_pre_fee` is what actually gets transferred via `bank.withdraw_spl_transfer` [3](#0-2) , but the shares burned at line 128 already reflect the original, higher requested amount. There is no re-crediting of the difference back to the user's balance, and no `require_eq!`/revert guarding the shortfall (unlike every third-party integration path — Drift, Kamino, Solend, JupLend — which explicitly `require_eq!` the actual received/transferred amount against the expected amount and revert on mismatch, e.g. [4](#0-3)  and [5](#0-4) ).

The `TOKENLESS_REPAYMENTS_COMPLETE` flag is set automatically once a deleveraged bank's liabilities are fully written off [6](#0-5) , or force-set by the `delegate_limit_admin`/`risk_admin` [7](#0-6) ; from that point on any ordinary depositor (unprivileged, using their own `authority` signature — no admin role required) can call the normal, permissionless `lending_account_withdraw` instruction. The design intent documented for `withdraw_all` in this state is "you get what's left" — an accepted, tested loss-sharing mechanism for bank sunset/bankruptcy resolution (see `tests/specs/bankruptcy/zb02_e2eSunset.spec.ts`). However, this intent is only correctly implemented for the full-withdrawal (`withdraw_all=true`) case, where `bank_account.withdraw_all()` zeroes out exactly the position being closed. For a **partial** withdrawal, the user never intended to close their whole position — they only asked for `amount`, yet if the vault's real balance is below `amount`, the difference (`amount - actual`) is burned as shares with zero token compensation and zero remaining benefit to the user's residual position. The lost value is unrecoverable and unaccounted for anywhere else in the protocol.

### Impact Explanation
This is a direct, unrecoverable loss of user funds: a depositor requesting a partial withdrawal of `X` tokens from a bank flagged `TOKENLESS_REPAYMENTS_COMPLETE` can have their shares reduced by the equivalent of `X`, while only receiving `min(X, vault_balance)` tokens, with the shortfall permanently destroyed rather than credited back to their remaining balance. Because this occurs silently (no revert, no event indicating a partial fill, no share re-credit), the on-chain state and off-chain integrations relying on `LendingAccountWithdrawEvent.amount`/`share_amount` consistency will also be misled, exactly matching the underlying EIP‑4626-style non-compliance in the referenced report (value transferred ≠ shares/assets accounted for, without reverting on shortfall).

### Likelihood Explanation
The precondition (`TOKENLESS_REPAYMENTS_COMPLETE` set on a bank whose liquidity vault is underfunded) is a real, intended and tested end-state of the deleverage/bankruptcy-sunset flow, not a purely theoretical state — it is exercised in `tests/specs/bankruptcy/zb02_e2eSunset.spec.ts`. Once a bank reaches this state, any depositor who still holds a balance and issues a normal partial withdrawal (not `withdraw_all`) for more than the vault currently holds will trigger the loss deterministically; no special privileges or race conditions are needed to trigger it, only ordinary use of the standard withdraw instruction under a known protocol state.

### Recommendation
For the `TOKENLESS_REPAYMENTS_COMPLETE` clamp path, recompute (reduce) the shares burned to match the actually-clamped/transferred `amount_pre_fee` instead of leaving the original higher-amount share burn in place — i.e., mirror the `withdraw_all` semantics for partial withdrawals too: either only burn shares proportional to what is actually transferred, or credit the shortfall back to the user's remaining balance. Alternatively, disallow partial withdrawals entirely once `TOKENLESS_REPAYMENTS_COMPLETE` is set and force all withdrawals from such banks through `withdraw_all`, consistent with the "you get what's left, once" design intent.

### Proof of Concept
1. Risk admin performs forced deleverage on Bank B until all liabilities are discharged; `repay` sets `TOKENLESS_REPAYMENTS_COMPLETE` on Bank B (as in `repay.rs` lines 142-149), while Bank B's liquidity vault holds less than the sum of remaining depositor claims (as demonstrated in `zb02_e2eSunset.spec.ts`).
2. A depositor with an active asset balance in Bank B, wanting to keep part of their position, calls `lending_account_withdraw` with `withdraw_all = false` and `amount = X`, where `X` exceeds the bank's current liquidity vault balance `V` (`X > V`).
3. `bank_account.withdraw(X)` burns shares equivalent to `X` from the depositor's position (`withdraw.rs` line 128).
4. The `TOKENLESS_REPAYMENTS_COMPLETE` branch clamps the transfer amount to `V` (`withdraw.rs` lines 134-141); `bank.withdraw_spl_transfer` sends only `V` tokens to the depositor.
5. The depositor's on-chain share balance is reduced by the value of `X`, but they only received `V` tokens — the difference `X - V` is permanently lost with no compensating credit, and the transaction succeeds without any revert or error.

pub fn lending_pool_force_tokenless_repay_complete(
    ctx: Context<LendingPoolForceTokenlessRepayComplete>,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;

    if bank.get_flag(TOKENLESS_REPAYMENTS_ALLOWED) {
        bank.update_flag(true, TOKENLESS_REPAYMENTS_COMPLETE);
    }

    Ok(())
