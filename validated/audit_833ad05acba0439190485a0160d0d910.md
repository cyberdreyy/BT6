### Title
Fee-on-transfer underlyings over-credit deposits and break withdraw claims in the credit vault - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The credit-vault accounting assumes the amount of `token` pulled equals the amount received. `depositDuringEpoch` mints tranche and strategy tokens against the nominal `_amount`, and `collectWithdrawFunds`/`collectInstantWithdrawFunds` clear `pendingWithdraws`/`pendingInstantWithdraws` by the nominal pulled amount rather than by `balanceOf` delta. With a fee-on-transfer underlying (e.g. a USDT-class token with fee enabled), each hop leaks the fee, leaving the strategy short versus its recorded obligations, so later `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on insufficient balance and the residual funds are frozen.

### Finding Description
In `IdleCDOEpochVariant.depositDuringEpoch`, the contract pulls `_amount` from the user via `_transferUnderlyingsFrom` (a raw `safeTransferFrom`, no balance delta check), then mints strategy tokens 1:1 for `_amount` via `IdleCreditVault(strategy).mintStrategyTokens(_amount)` and forwards `_amount` to the borrower. [1](#0-0) 

The minted tranche amount is also computed from the nominal `_amount`: [2](#0-1) 

Likewise `IdleCreditVault.deposit` mints strategy tokens for the nominal `_amount` after a plain `safeTransferFrom`, and `collectWithdrawFunds` / `collectInstantWithdrawFunds` decrement `pendingWithdraws`/`pendingInstantWithdraws` by the requested `_amount` while the actual received balance is `_amount` minus transfer fees: [3](#0-2) [4](#0-3) 

Claims then pay the nominal receipt amount via `_transferFundedClaim`, which reverts if the strategy balance cannot cover it: [5](#0-4) 

By contrast, `IdleCDO._deposit` correctly mints on the actual received delta (`_contractTokenBalance(_token) - _preBal`), showing the protocol is expected to tolerate fee-on-transfer behaviour at mint time, but the epoch and claim-funding paths were not given the same treatment. [6](#0-5) 

### Impact Explanation
With a fee-on-transfer underlying, the strategy's recorded obligations (`pendingWithdraws`, minted receipt strategy tokens, `lossRecoveryPriceByEpoch` computed against `_amount`) exceed its real token balance by the cumulative fees. The last claimant(s) of an epoch can never withdraw: `_transferFundedClaim` reverts because `balanceOf(this) < amount`, permanently freezing their principal/interest. The shortfall equals `fee% * (deposit hop + collection hop)` on every token moved — e.g. a 0.2% fee on a 1M USDT vault underfunds receipts by ~4k USDT across two hops, and a borrower-side repayment via a FoT token compounds it further. Funds are only recoverable if someone donates tokens directly to the strategy, exactly mirroring the reference report's stuck-collateral pattern.

### Likelihood Explanation
Likelihood depends on deployment: the underlying `token` is fixed at `initialize`, and the vault is designed for pool currencies like USDC/USDT. If a vault is ever deployed against a token that charges (or later enables, as USDT can) a transfer fee, every stop-epoch funding cycle silently creates the shortfall — no privileged misbehaviour needed, just ordinary deposits, stopEpoch collections, and claims. Any unprivileged user holding a pending receipt is then blocked.

### Recommendation
Measure received amounts instead of assuming them:
- In `depositDuringEpoch`, snapshot `balanceOf` before/after `_transferUnderlyingsFrom` and use the delta for `_minted` calculation, `mintStrategyTokens`, and the borrower transfer.
- In `IdleCreditVault.deposit`, `collectWithdrawFunds`, and `collectInstantWithdrawFunds`, compute `balanceAfter - balanceBefore` and credit only the received amount, or explicitly document and enforce that fee-on-transfer underlyings are unsupported (revert in `initialize` via a probe transfer).

```solidity
// FeeToken: ERC20 mock taking `feeBps` on transfer/transferFrom
function test_feeOnTransfer_breaksWithdrawClaims() public {
    FeeToken t = new FeeToken(20); // 0.2% fee
    // deploy IdleCDOEpochVariant + IdleCreditVault with token = t
    // 1) lender deposits via depositAA before epoch start:
    t.mint(lender, 1_000_000e6);
    vm.startPrank(lender);
    t.approve(address(cdo), type(uint256).max);
    cdo.depositAA(1_000_000e6);       // strategy.deposit pulls 1M, mints 1M strategy tokens,
                                      // but strategy received only 998k -> already underfunded
    vm.stopPrank();

    // 2) manager runs epoch, borrower repays principal+interest at stopEpoch;
    //    collectWithdrawFunds pulls `_amount` from CDO, receives `_amount` - fee,
    //    but pendingWithdraws is cleared by full `_amount`.
    // 3) lender requests withdraw, waits one epoch, then:
    vm.prank(lender);
    vm.expectRevert(); // safeTransfer fails: strategy balance < claim amount
    cdo.claimWithdrawRequest();
    // Assert: last claimant's receipt amount remains stuck in IdleCreditVault
}
```

The key assertion: after a full deposit → epoch → withdraw-request → claim cycle with a fee token, `token.balanceOf(strategy) < sum(outstanding receipts)` and the final `claimWithdrawRequest` reverts, permanently freezing the residual funds.

```text
  /// @notice collect borrower-funded withdraw receipt funds
  /// @dev Only IdleCDO can call this function. When `_amount` is lower than the
  /// pending basis, the difference is a stopEpochWithDuration loss assigned to
  /// pending receipts and users later claim through `lossRecoveryPriceByEpoch`.
  /// Reverts if the resulting recovery price rounds to zero at `RECOVERY_FULL` precision.
  /// @param _amount number of funded tokens to collect
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
