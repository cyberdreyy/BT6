### Title
Unbounded zstd compression cost in `encode_ui_account` allows CPU/memory amplification via a single `getAccountInfo(encoding=base64+zstd)` call - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account`'s `UiAccountEncoding::Base64Zstd` branch runs `zstd::stream::write::Encoder` over the full (optionally sliced) account data with no upper bound on input size, and `encode_account` in `rpc/src/rpc.rs` only enforces a size limit (`MAX_BASE58_BYTES`) for the `Binary`/`Base58` encodings, not for `Base64`/`Base64Zstd`. An attacker who owns a large on-chain account (up to the account size cap) can request it once via `getAccountInfo` with `base64+zstd` encoding and force the validator to zstd-compress the entire account contents synchronously within the RPC request handler.

### Finding Description
The compression path is:
`rpc/src/rpc.rs::get_encoded_account` → `encode_account` (rpc.rs:2575-2601) → `solana_account_decoder::encode_ui_account` (account-decoder/src/lib.rs:46-101). [1](#0-0) 

`encode_account` only checks the byte-length limit (`MAX_BASE58_BYTES`) for `Binary`/`Base58` encodings; no check is performed when `encoding == UiAccountEncoding::Base64Zstd`, so any size of `slice_data(account.data(), data_slice_config)` is passed straight into `encode_ui_account`.

Inside `encode_ui_account`, the `Base64Zstd` branch unconditionally constructs a `zstd::stream::write::Encoder` and calls `write_all` + `finish` over the entire sliced account data, with no size cap, timeout, or resource-limit check: [2](#0-1) 

Since accounts can be grown up to the maximum permitted account size (via `Allocate`/`Extend` on system/BPF-loader-owned accounts) and their contents fully attacker-controlled, an attacker can create one large account filled with data chosen to maximize zstd compressor CPU/memory work (e.g., patterns that defeat fast-path matching or force worst-case entropy coding), then issue a single `getAccountInfo` call with `encoding: "base64+zstd"` targeting that account's pubkey. The compression work is done synchronously on the RPC thread handling that single request — there is no secondary index, no multiple calls, and no `getProgramAccounts` filter bypass needed, matching the exact scoped attack requested.

The existing guard (`MAX_BASE58_BYTES` check in `encode_account`) does not apply to this encoding path, so nothing in the reachable code stops the cost of the single call from scaling with the size/content of on-chain data rather than being bounded by an explicit request-cost limit.

### Impact Explanation
This is a CPU/memory amplification vector on a single RPC read call: one `getAccountInfo` request with `encoding=base64+zstd` against an attacker-grown, adversarially-filled account causes the validator's RPC-serving thread to perform zstd compression proportional to the account's data length (up to the maximum permitted account size), consuming disproportionate CPU/memory relative to the cost of a normal single read. This falls under "unbounded cost for a single low-rate call" in the audit's accepted impact categories, and matches the Agave bug-bounty RPC DoS / resource-exhaustion category for a single call under the `CLUSTER_SLOT_TIME_TARGET / 2` rate limit.

### Likelihood Explanation
Feasible with one unprivileged attacker: creating a large account only requires paying rent/allocation costs to grow an account (e.g., via `Allocate`/system program or a BPF buffer account) up to the maximum size, and populating it with attacker-chosen bytes is free-form (no permission checks on account data content). The exploit needs a single subsequent `getAccountInfo` call, satisfying the "no more than one call per `CLUSTER_SLOT_TIME_TARGET / 2`" and "single client" constraints. It is fully repeatable — the attacker can reissue the same call at the allowed rate indefinitely, or target multiple such pre-grown accounts over time, each time forcing full-size compression.

### Recommendation
Add an explicit size guard for `UiAccountEncoding::Base64Zstd` (and ideally `Base64`) analogous to the existing `MAX_BASE58_BYTES` check in `encode_account`, rejecting or capping compression for account data (post-slice) beyond a bounded threshold, or move zstd compression to a bounded-effort implementation (e.g., streaming with a hard byte/CPU budget) so request cost is capped independent of on-chain content size.

### Proof of Concept
```rust
// account-decoder/src/lib.rs (extend existing test module)
#[test]
fn test_base64_zstd_cost_scales_unbounded_with_account_size() {
    use std::time::Instant;

    // Simulate a max-size, adversarially-filled account (e.g., near MAX_PERMITTED_DATA_LENGTH).
    let large_adversarial_data: Vec<u8> = (0..10_000_000u32)
        .map(|i| (i % 251) as u8) // low-repetition, compression-resistant pattern
        .collect();

    let account = AccountSharedData::from(Account {
        data: large_adversarial_data,
        ..Account::default()
    });

    let start = Instant::now();
    let _ = encode_ui_account(
        &Pubkey::default(),
        &account,
        UiAccountEncoding::Base64Zstd,
        None,
        None,
    );
    let elapsed = start.elapsed();

    // Expectation for a bounded-cost design: encode_ui_account should either
    // reject Base64Zstd for oversized accounts (returning an error/fallback quickly)
    // or complete within a fixed CPU/time budget regardless of data size/content.
    assert!(
        elapsed.as_millis() < 50,
        "encode_ui_account took {:?} for a single request; cost is unbounded relative to account size",
        elapsed
    );
}
```
Run this test with varying `large_adversarial_data` sizes approaching the maximum permitted account size, and with varying entropy/patterns, to demonstrate that wall-clock/CPU cost of a single `encode_ui_account` call (reachable from a single `getAccountInfo` RPC request) grows with attacker-controlled account size/content with no enforced upper bound, unlike the `Base58`/`Binary` paths which are explicitly capped by `MAX_BASE58_BYTES`.

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
