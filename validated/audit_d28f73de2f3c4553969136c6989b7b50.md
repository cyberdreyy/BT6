### Title
Unfunded instant-withdraw receipts from pre-default epochs escape the recovery haircut and are paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` burns and pays the *aggregate* `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim`. The default-aware path, `_claimDefaultedInstantWithdrawRequest`, only clears receipts tagged to `defaultRecoveryEpoch`. An instant-withdraw receipt created in an *earlier* epoch whose funding was only partially collected at `stopEpoch` (leaving `pendingInstantWithdraws > 0`) is never included in `defaultPendingClaimBasis()` — which only adds `instantWithdrawClaimsByEpoch[epochNumber]` (the current/default epoch bucket) — yet it remains inside `instantWithdrawsRequests[_user]` and is paid out 1:1 after `finalizeDefaultRecovery`. This is the idle-tranches analog of CVE-2020-25632: a dependency (the unfunded balance of an old receipt) is "unloaded" from the recovery-basis computation while still being referenced by the claim path, producing an over-par payout (the use-after-free equivalent: value freed twice from the same reserve).

### Finding Description
The bug chain:

1. `requestInstantWithdraw` tags receipts per epoch (`instantWithdrawsRequestsByEpoch[user][epochNumber]`) and adds to the global `pendingInstantWithdraws` (IdleCreditVault.sol:366-374).
2. At `stopEpoch`, `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` only by what the CDO actually funded — a partial collection is explicitly supported (IdleCreditVault.sol:398-403). If the borrower under-repays, part of an epoch-N instant receipt stays unfunded but is not deleted from `instantWithdrawsRequests[_user]`.
3. If the pool then defaults, `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *default* epoch bucket — to the haircut basis (IdleCreditVault.sol:644-649). An unfunded receipt tagged to an earlier epoch contributes `pendingInstantWithdraws` but is missing from `instantWithdrawClaimsByEpoch[defaultEpoch]`, so it is excluded from `basis` (only the `pending != 0` branch adds the current-epoch claims) and thus receives no recovery-price allocation.
4. After `finalizeDefaultRecovery`, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (IdleCreditVault.sol:842-856), then burns the *entire remaining* `instantWithdrawsRequests[_user]` and pays it at par through `_transferFundedClaim` (IdleCreditVault.sol:387-392). The unfunded remainder of the old receipt is paid 1:1 from strategy balance — i.e., from the defaulted recovery reserve / funds owed to haircutted claimants.

The invariant broken is the loss waterfall: every defaulted claim basis should be paid `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`, but the stale-epoch instant receipt is paid at `RECOVERY_FULL`.

Attacker: any KYC-passing lender holding tranche tokens (unprivileged). Honest-role sequencing required is only ordinary epoch transitions plus a default where the CDO partially funded the instant queue — the prefunded-partial path is natively supported (`_defaultPrefundedInstantReserve`, comments at 638-640 and 850-852), so this is reachable in production stop-epoch flows.

### Impact Explanation
Direct theft of recovery funds: the attacker receives `(unfunded portion) * (1 - defaultRecoveryPrice)` more than entitled, paid from the same strategy balance backing `defaultRecoveryReserve`, proportionally reducing what defaulted-epoch claimants and active LPs can recover. Loss is bounded by the attacker's own instant-withdraw amount, so severity scales with receipt size; repeated across the queue it is full insolvency for the residual reserve. Note: whether `_transferFundedClaim` subtracts `defaultRecoveryReserve` when computing spendable balance (IdleCreditVault.sol:897-900, truncated in my read) determines whether the theft hits the reserve or other funded claims — either way the payout is unbacked and comes out of someone else's claim. I could not fully verify that tail of `_transferFundedClaim` in the available iterations; if it strictly excludes the reserve, the attack instead drains legitimately funded instant receipts of other users, which is still direct theft.

### Likelihood Explanation
Requires: (a) an instant-withdraw request outstanding across a `stopEpoch` where the CDO collects less than the full `pendingInstantWithdraws` (borrower under-payment / liquidity shortfall — exactly the prefunded partial path the code handles), and (b) a subsequent default finalized via `finalizeDefaultRecovery`. The attacker controls only step (a); (b) is an external credit event, not attacker-manufacturable, which lowers likelihood but the payoff is mechanical once conditions hold. Existing guards don't stop it: `_onlyIdleCDO` is satisfied, epoch-wait checks don't apply to the instant path, and the recovery-basis function structurally omits stale-epoch claims.

### Recommendation
Attribute `pendingInstantWithdraws` to per-epoch claim buckets, or conservatively include *all* unfunded instant receipts in `defaultPendingClaimBasis()` (e.g., track a `totalInstantClaimBasis` independent of epoch tag). Correspondingly, `_claimDefaultedInstantWithdrawRequest` should clear/apply the haircut to every epoch-tagged instant receipt still counted in `pendingInstantWithdraws`, not only `defaultRecoveryEpoch`, and `claimInstantWithdrawRequest` should only pay at par the portion that was actually collected via `collectInstantWithdrawFunds`.

### Proof of Concept
Foundry fork test (mainnet, same setup pattern as `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleEpochInstantReceiptPaidAtParAfterDefault() external {
    address attacker = makeAddr("attacker");
    uint256 amount = 10_000 * ONE_SCALE;

    // Epoch N: attacker deposits and requests instant withdraw
    _depositWithUser(attacker, amount, true);
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(amount /* underlying equiv */, address(AAtranche));

    // stopEpoch N: CDO funds only half the instant queue (partial collect)
    _startEpochAndCheckPrices(0);
    uint256 pending = IdleCreditVault(address(strategy)).pendingInstantWithdraws();
    // simulate CDO holding only half the needed cash: borrower repays less
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - pending / 2);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch() - pending / 2);
    assertGt(IdleCreditVault(address(strategy)).pendingInstantWithdraws(), 0, "unfunded remainder");
    // attacker does NOT claim yet

    // Epoch N+1 defaults
    _startEpochAndCheckPrices(1);
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    // Finalize recovery at 70%
    uint256 basis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest()
        - cdoEpoch.pendingWithdrawFees()
        + IdleCreditVault(address(strategy)).defaultPendingClaimBasis();
    // KEY ASSERT: attacker's stale-epoch instant receipt basis is missing
    uint256 recovered = basis * 7e17 / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // Attacker claims: receives FULL receipt at par instead of 70% haircut
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre;

    assertGt(paid, amount * 7e17 / ONE_TRANCHE + 1, "stale instant receipt escaped haircut");
    // reserve now insufficient for remaining defaulted claimants:
    // sum of remaining claims * recoveryPrice > defaultRecoveryReserve
}
```

The pre-state assertion `pendingInstantWithdraws > 0` plus `defaultPendingClaimBasis()` excluding the attacker's old-epoch `instantWithdrawsRequestsByEpoch` value demonstrates the missing basis; the post-claim payout above `claimBasis * recoveryPrice` demonstrates the theft.
