### Title
Unbounded-length bincode deserialization in `transaction_status::parse_stake` / `parse_system` / `parse_vote` allows a single attacker-crafted on-chain transaction to crash the RPC/decoder path on every `getTransaction`/`getBlock` (`jsonParsed`) request - ([File: transaction-status/src/parse_system.rs], [transaction-status/src/parse_stake.rs], [transaction-status/src/parse_vote.rs])

### Summary
`parse_system`, `parse_stake`, and `parse_vote` deserialize raw, attacker-controlled `CompiledInstruction.data` bytes with the unbounded `bincode::deserialize` call, instead of the size-limited `limited_deserialize(data, PACKET_DATA_SIZE)` helper used for the exact same instruction types elsewhere in the codebase (`programs/system/src/system_processor.rs`, `cli-output/src/display.rs`, `vote/src/vote_parser.rs`). Because `bincode::deserialize` uses an `Infinite` size limit, a String/Vec-bearing enum variant (e.g. `SystemInstruction::CreateAccountWithSeed { seed: String, .. }`) with a forged 8-byte little-endian length prefix causes `Vec::with_capacity(len)`/allocation for the claimed length before any byte-availability check, independent of how many bytes are actually present.

### Finding Description
`parse_system` reads instruction data directly: [1](#0-0) 
and `parse_stake`/`parse_vote` do the same: [2](#0-1) [3](#0-2) 

All three use `bincode::deserialize`, which — unlike `solana_bincode::limited_deserialize` — applies an unbounded (`Infinite`) size limit. `limited_deserialize` is the pattern deliberately used elsewhere in the codebase for parsing the exact same `SystemInstruction`/`StakeInstruction`/`VoteInstruction` types from untrusted instruction bytes: [4](#0-3) [5](#0-4) [6](#0-5) 

`SystemInstruction::CreateAccountWithSeed` contains a `seed: String` field, whose bincode wire format is a `u64` length prefix followed by UTF-8 bytes: [7](#0-6) 

An attacker only needs to serialize the enum discriminant for `CreateAccountWithSeed` and then overwrite the `seed` length-prefix bytes with an arbitrary huge `u64` value (e.g. `0xFFFFFFFFFFFFFFFF`), while omitting the actual seed bytes. This keeps the whole instruction (and transaction) well within `PACKET_DATA_SIZE`, so it passes the RPC's `decode_and_deserialize` size checks and the message/transaction sanitization, and can be submitted via `sendTransaction`: [8](#0-7) 

At execution time, `system_processor.rs` uses `limited_deserialize(instruction_data, PACKET_DATA_SIZE)`, so the bogus instruction fails cleanly with a decode error inside the sandboxed limit (the instruction simply errors, e.g., `InstructionError::InvalidInstructionData`), but the transaction and its raw instruction bytes are still recorded and retrievable from the blockstore regardless of success/failure. Later, any client calling `getTransaction`/`getBlock` with `encoding: jsonParsed` triggers: [9](#0-8) 
which calls into `Encodable::encode` → `parse_ui_instruction` → `parse_instruction::parse` → `parse_system`/`parse_stake`/`parse_vote`: [10](#0-9) 

This time the deserialization uses plain `bincode::deserialize`, with no size limit tied to the actual byte buffer, so the declared `seed` length is used to allocate (via `Vec<u8>`/`String::with_capacity`) before any bounds check against remaining input bytes, causing the RPC-serving thread to attempt an oversized allocation. `Vec`/`String` allocation failures in Rust invoke `handle_alloc_error`, which aborts the process (this is not a recoverable `Result::Err`), or, for allocation sizes that succeed but are enormous, causes severe memory pressure/OOM on the validator/RPC node. This happens on every subsequent read of that confirmed transaction — a single confirmed transaction crashes every client that queries it via `jsonParsed`.

### Impact Explanation
This is a validator/RPC-process crash (or unbounded memory exhaustion) triggerable by a single, unprivileged client submitting one ordinary (non-privileged, non-consensus) transaction and then having any RPC client (including third parties) request it via a single `getTransaction`/`getBlock` call with `jsonParsed` encoding. Because the crash/allocation attempt is deterministic and repeatable on every read of the poisoned transaction, this matches the "validator/RPC process crash from a single request" bounty category, and it persistently denies service for that stored transaction to all readers, not just the attacker.

### Likelihood Explanation
- Preconditions are minimal: craft and submit any `System`, `Stake`, or `Vote` instruction whose bincode-encoded payload contains a `String`/`Vec` field, with a forged oversized little-endian length prefix, while keeping the whole transaction within `PACKET_DATA_SIZE`.
- The transaction does not need to succeed — it only needs to be included/confirmed (even failing instructions are stored with their raw byte payload and are retrievable).
- Triggering the crash requires exactly one JSON-RPC `getTransaction`/`getBlock` call with `jsonParsed` encoding — well within the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` limit.
- No validator/leader/gossip control, no privileged keys, and no dependency-internal exploitation beyond calling a standard library API (`bincode::deserialize`) that this codebase itself treats as unsafe for untrusted input elsewhere (as shown by the parallel `limited_deserialize` usages). This is highly feasible and fully repeatable.

### Recommendation
Replace the unbounded `bincode::deserialize(&instruction.data)` calls in `transaction-status/src/parse_system.rs`, `transaction-status/src/parse_stake.rs`, and `transaction-status/src/parse_vote.rs` with `solana_bincode::limited_deserialize(&instruction.data, solana_packet::PACKET_DATA_SIZE as u64)`, mirroring the pattern already used in `programs/system/src/system_processor.rs`, `cli-output/src/display.rs`, and `vote/src/vote_parser.rs`. Apply the same fix to any other decoder in `transaction-status`/`account-decoder` that calls raw `bincode::deserialize` on attacker-supplied instruction/account bytes (e.g., `parse_stake.rs`'s account-decoder counterpart also uses plain `deserialize`).

### Proof of Concept
```rust
// transaction-status/src/parse_system.rs (add to #[cfg(test)] mod test)
#[test]
fn test_parse_system_oversized_seed_length_prefix_does_not_oom() {
    use solana_message::compiled_instruction::CompiledInstruction;

    // Manually build bincode-encoded bytes for
    // SystemInstruction::CreateAccountWithSeed { base, seed: String, lamports, space, owner }
    // Variant index 3 (u32 LE) for CreateAccountWithSeed, followed by `base: Pubkey` (32 bytes),
    // then a forged String length prefix (u64 LE) of u64::MAX, with NO actual seed bytes following.
    let mut data = Vec::new();
    data.extend_from_slice(&3u32.to_le_bytes()); // CreateAccountWithSeed discriminant
    data.extend_from_slice(&[0u8; 32]);          // base pubkey
    data.extend_from_slice(&u64::MAX.to_le_bytes()); // forged seed length prefix
    // no seed bytes, no lamports/space/owner - buffer intentionally truncated

    let instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![0, 1],
        data,
    };
    let account_keys = solana_message::AccountKeys::new(
        &[solana_pubkey::Pubkey::default(), solana_pubkey::Pubkey::default()],
        None,
    );

    // Expectation for a FIXED implementation using limited_deserialize:
    // the call must return Err quickly without attempting to allocate u64::MAX bytes.
    let result = std::panic::catch_unwind(|| parse_system(&instruction, &account_keys));
    assert!(
        result.is_ok() && result.unwrap().is_err(),
        "parse_system must return Err(..) rather than aborting/allocating on oversized length prefix"
    );
}
```
Expected current behavior (vulnerable): the process attempts to allocate ~`u64::MAX` bytes for the `String` and aborts (`memory allocation of ... bytes failed`) or hangs due to massive allocation, rather than returning `Err`. Expected fixed behavior: `parse_system`/`parse_stake`/`parse_vote` return `Err(ParseInstructionError::InstructionNotParsable(..))` immediately because `limited_deserialize` rejects declared lengths that exceed the remaining `PACKET_DATA_SIZE`-bounded limit before allocating. A fuzz target (`cargo fuzz` or `proptest`) should additionally iterate random large length prefixes at every `String`/`Vec` field offset for `SystemInstruction`, `StakeInstruction`, and `VoteInstruction` and assert bounded allocation (e.g., via a custom allocator that records peak requested bytes and fails the test if it exceeds `PACKET_DATA_SIZE`).

/// Check if a transaction is a valid vote-only transaction.
/// A valid vote-only transaction must:
/// 1. Have exactly one instruction
/// 2. That instruction must be to the vote program
/// 3. That instruction must be a single vote state update (UpdateVoteState, TowerSync, etc.)
pub fn is_valid_vote_only_transaction(tx: &impl SVMTransaction) -> bool {
    let mut instructions = tx.program_instructions_iter();

    let Some((program_id, instruction)) = instructions.next() else {
        return false;
    };

    if instructions.next().is_some() {
        return false;
    }

    if !solana_sdk_ids::vote::check_id(program_id) {
        return false;
    }

    limited_deserialize::<VoteInstruction>(instruction.data, solana_packet::PACKET_DATA_SIZE as u64)
        .map(|ix| ix.is_single_vote_state_update())
        .unwrap_or(false)
}
