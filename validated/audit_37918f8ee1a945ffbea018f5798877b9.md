### Title
v1 tenure-change duplicate-block guard only checks globally accepted blocks, allowing a signer to sign two competing tenure-start blocks - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionsView::validate_tenure_change_payload` in v1.rs guards against re-signing a competing tenure-start block by calling `signer_db.get_last_globally_accepted_block`, which only returns a block once *global* acceptance has been recorded. `GlobalStateView::validate_tenure_change_payload` in v2.rs was explicitly hardened to call `get_last_signed_block` instead, which returns a block that is either locally or globally accepted. This means a v1 signer that has locally accepted (signed) a tenure-start block but not yet observed global acceptance has no guard against accepting a second, competing tenure-start proposal for the same tenure.

### Finding Description
The uniqueness property "at most one signed block per (tenure, height)" is enforced in `validate_tenure_change_payload` via a `DuplicateBlockFound` check just before returning `Ok(())`. In v1.rs: [1](#0-0) 

this check queries `get_last_globally_accepted_block(&block.header.consensus_hash)`, which by design only reflects blocks the *network* has globally accepted — not blocks this signer has merely locally signed. In v2.rs, the equivalent check was fixed to use `get_last_signed_block`, with an explicit code comment stating the rationale: [2](#0-1) 

"Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us, so it is safe to accept a competing tenure-start block in its place if it failed to reach consensus" — meaning the v2 developers deliberately closed the exact gap that persists in v1: a *signed* (locally accepted) block must block a competing tenure-start proposal, only unsigned pre-commits are safe to override.

Exploit flow under v1 (SortitionStateVersion::V1 active):
1. Miner wins the slot for tenure T and proposes tenure-start block B1.
2. The target signer runs `check_proposal` -> `validate_tenure_change_payload`, passes all checks, and signs B1 (locally accepted, `signed_self` set in `signer_db`), but B1 has not yet reached the 70% signature threshold to be recorded as globally accepted.
3. Attacker (a single miner-slot holder, or an attacker who can otherwise get a competing block gossiped as a `BlockProposal` for the same sortition/tenure before global acceptance propagates) submits a second, sibling tenure-start block B2 for tenure T.
4. The victim's `check_proposal` -> `validate_tenure_change_payload` calls `get_last_globally_accepted_block(&B2.header.consensus_hash)`, which returns `None` because only local acceptance of B1 exists, not global.
5. The `DuplicateBlockFound` check is skipped, and the signer proceeds to validate and sign B2 — a sibling of B1 at the same tenure/height.

This produces two conflicting signatures from the same signer for two distinct blocks that both claim the tenure-start slot for tenure T, breaking the equivocation/uniqueness guarantee that SignerDb's local/global-acceptance bookkeeping is meant to enforce.

### Impact Explanation
This is an equivocation by a signer: the signer produces two valid signatures for two different (conflicting) tenure-start blocks at the same tenure. If enough other signers under the same race condition also equivocate, the two signature sets could each reach threshold, causing a chain split — this matches the "Critical: a signer signing an invalid, non-canonical, or conflicting block (chain safety)" category. It is repeatable per tenure race and needs only the narrow timing window between local signing and global-acceptance propagation.

### Likelihood Explanation
Preconditions: v1 `SortitionStateVersion` active (older signer protocol still supported); a signer must have locally-but-not-yet-globally accepted a first tenure-start block for tenure T (a normal, frequently occurring state during any block-signing round, since local acceptance always precedes global acceptance by network propagation time). The attacker needs to get a second competing tenure-start proposal to the signer within that narrow window, which requires only crafting a `BlockProposal` and gossiping it (no privileged role, no auth token). This is feasible for any single miner-slot holder attempting a natural fork/race, and the gap is real given the explicit contrast with the v2 fix and its documented rationale.

### Recommendation
In `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`, replace the `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` call with `signer_db.get_last_signed_block(&block.header.consensus_hash)`, mirroring the v2.rs fix, so any locally-signed (not just globally accepted) block in the tenure blocks acceptance of a competing tenure-start proposal.

### Proof of Concept
```rust
// stacks-signer/src/chainstate/tests/v1.rs (new test)
#[test]
fn v1_duplicate_block_guard_misses_locally_accepted_only() {
    // Setup: SignerDb with V1 sortition state, tenure T.
    let mut signer_db = SignerDb::new(...);
    let block1 = make_tenure_start_block(tenure_consensus_hash, /* height */ 1);
    // Simulate local (but not global) acceptance: mark signed_self, no global-accept record.
    signer_db.insert_block(&block1_info_locally_signed_only).unwrap();

    // Sanity: get_last_globally_accepted_block returns None (bug surface)
    assert!(signer_db
        .get_last_globally_accepted_block(&tenure_consensus_hash)
        .unwrap()
        .is_none());
    // But get_last_signed_block would return Some(block1) (as v2 does)
    assert!(signer_db
        .get_last_signed_block(&tenure_consensus_hash)
        .unwrap()
        .is_some());

    // Build a sibling tenure-start block2 for the same tenure/height, different content.
    let block2 = make_conflicting_tenure_start_block(tenure_consensus_hash, /* height */ 1);
    let sortitions_view = build_v1_sortitions_view_for_tenure(tenure_consensus_hash);

    let result = sortitions_view.validate_tenure_change_payload(
        &proposed_by,
        block2.get_tenure_change_tx_payload().unwrap(),
        &block2,
        &mut signer_db,
        &client,
    );

    // BUG: this wrongly succeeds instead of returning Err(RejectReason::DuplicateBlockFound)
    assert!(result.is_ok(), "v1 guard incorrectly allows conflicting tenure-start block after only local acceptance");
    // Expected (post-fix) behavior:
    // assert_eq!(result, Err(RejectReason::DuplicateBlockFound));
}
```
