### Title
Stale instant-withdraw per-epoch claim basis is never cleared on a normal claim, corrupting default-recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The ImageMagick bug is an out-of-bounds read caused by missing boundary checks when parsing attacker input. The credit-vault analog is a missing bounds/lifecycle check on receipt state: `claimInstantWithdrawRequest` pays a user and clears `instantWithdrawsRequests[_user]`, but it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]` or `pendingInstantWithdraws`. If the borrower later defaults in the same epoch, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` read this stale claim data — treating already-paid receipts as outstanding claims backed by strategy cash — and `finalizeDefaultRecovery` computes a wrong `defaultRecoveryPrice`, permanently stranding recovery funds and underpaying honest claimants.

### Finding Description
`requestInstantWithdraw` records three pieces of state per epoch (IdleCreditVault.sol:356-375):
- `instantWithdrawsRequests[_user] += _amount`
- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`
- `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`
- `pendingInstantWithdraws += _amount`

On the normal claim path (lines 380-393) the strategy does:
```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```
It does **not** touch `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, or `pendingInstantWithdraws` (`pendingInstantWithdraws` is decremented only by `collectInstantWithdrawFunds` at funding time, line 401 — i.e., it tracks the *unfunded remainder*, not outstanding claims).

The default path assumes the per-epoch mappings only contain still-unpaid claims:
- `defaultPendingClaimBasis()` (line 644) adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery denominator whenever `pendingInstantWithdraws != 0`.
- `_defaultPrefundedInstantReserve()` (lines 716-723) computes `instantClaimsByEpoch - pendingInstantWithdraws` and counts it as cash already held for those claimants.
- `_claimDefaultedInstantWithdrawRequest` (line 842) pays `instantWithdrawsRequestsByEpoch[user][defaultEpoch] * defaultRecoveryPrice` and decrements the mappings — the only place they are ever cleared.

So if a claim is paid through the normal path while `pendingInstantWithdraws` is still non-zero (the strategy balance can satisfy it — e.g., underlyings sitting in the strategy from `deposit()` buffer flows at line 603 or a direct underlying transfer to the strategy, since `_transferFundedClaim` only ring-fences `defaultRecoveryReserve`, lines 897-906), the paid amount remains counted in the epoch claim basis forever. The paid-out cash is double-counted at finalization: once already spent by the claimant, and again inside `instantWithdrawClaimsByEpoch - pendingInstantWithdraws` as "prefunded reserve".

Broken invariant: one receipt, one payout / recovery-price solvency — `reserveAmount` and `totalBasis` are computed against phantom claims, so `defaultRecoveryPrice = reserveAmount * 1e18 / totalBasis` (line 688) is systematically mispriced, and `_transferDefaultRecovery` decrements a `defaultRecoveryReserve` that exceeds the real cash held.

### Impact Explanation
When `finalizeDefault` → `finalizeDefaultRecovery` runs with a stale instant basis:
- `totalBasis` is inflated by the already-claimed amount `X`, and `prefundedReserve` is inflated by roughly the same `X`, but the actual underlying balance is lower by `X` (it was already transferred out).
- `defaultRecoveryPrice` is therefore wrong, and `defaultRecoveryReserve` is set to a value larger than real spendable cash. Early default claimants are paid from the reserve until the real balance is exhausted; subsequent claims revert inside `_transferDefaultRecovery` (insufficient balance) or in `_burn` for claimants whose receipts were already consumed — permanently freezing the remainder of the recovery reserve.
- Loss is quantifiable: up to `X` (the stale claimed amount) of recovery value is either misdistributed to earlier claimants or locked in the strategy forever with no sweep function (`transferToken` is owner-only rescue, not a fix for the accounting).

Concrete numbers: A and B request 100 each in epoch E (`claimsByEpoch[E]=200`, `pending=200`). Funding covers 60 → `pending=140`, strategy holds 60. A direct transfer (or residual deposit cash) of ≥40 more arrives without a `collectInstantWithdrawFunds` call; A claims 100, strategy balance drops, but `claimsByEpoch[E]` stays 200 and `pending` stays 140. Borrower defaults. Finalization computes `prefundedReserve = 200-140 = 60` and `basis += 200` although only ~60 of real cash remains and only B's 100 is a live claim. `defaultRecoveryPrice` is diluted; B and active LPs recover less, and the tail of the reserve is unspendable.

### Likelihood Explanation
Requirements: instant-withdraw requests pending in the defaulted epoch, a claim paid while `pendingInstantWithdraws > 0`, and a same-epoch borrower default finalized via `finalizeDefault`. Partial instant-queue funding is an explicitly designed-for state (`instantWithdrawDeadline`, "borrower should return the difference"), and `claimInstantWithdrawRequest` has no check that the claim is actually funded through `collectInstantWithdrawFunds` — it pays whatever the strategy balance allows. Any underlying pushed into the strategy outside the funding function (direct transfers are unprivileged; buffer-mode `deposit()` cash is another source) makes a partially-funded claim payable. Borrower default with `pendingInstantWithdraws != 0` is exactly the scenario `_defaultPrefundedInstantReserve` was written for, so the corrupted path is reachable, not dead code. Likelihood is moderate: it needs the funding/balance divergence plus a same-epoch default.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch bookkeeping exactly like `_claimDefaultedInstantWithdrawRequest` does:
```solidity
uint256 amount = instantWithdrawsRequests[_user];
instantWithdrawsRequests[_user] = 0;
uint256 currentEpoch = epochNumber;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] -= amount; // or track per-claim
instantWithdrawClaimsByEpoch[currentEpoch] -= amount;
_burn(_user, amount);
_transferFundedClaim(_user, amount);
```
Alternatively, recompute `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` from live state (`instantWithdrawsRequests` aggregates rather than the epoch-scoped mappings that are never cleaned), or gate normal instant claims so they cannot execute while `pendingInstantWithdraws != 0` for their epoch.

Caveat: I could not read `getInstantWithdrawFunds` / the CDO-side instant-claim gating within the available iterations, so the precise trigger that lets a claim execute while `pendingInstantWithdraws > 0` should be confirmed in the PoC; the stale-accounting defect itself is directly visible in the code cited.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol style PoC (mainnet-fork harness)
function testStaleInstantBasisCorruptsRecoveryPrice() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // 1) Users A and B deposit AA during buffer epoch 0
    uint256 tranchesA = _depositWithUser(userA, amount, true);
    uint256 tranchesB = _depositWithUser(userB, amount, true);

    // 2) Both request instant withdrawals of 100 each during buffer
    _requestInstantWithdrawWithUser(userA, 100 * ONE_SCALE);
    _requestInstantWithdrawWithUser(userB, 100 * ONE_SCALE);

    // 3) startEpoch only partially covers the instant queue:
    //    pendingInstantWithdraws = 200e18 - funded, stays non-zero
    _startEpochAndCheckPrices(0);
    assertGt(IdleCreditVault(address(strategy)).pendingInstantWithdraws(), 0);

    // 4) Strategy balance is topped up outside collectInstantWithdrawFunds
    //    (direct underlying transfer to the strategy, an unprivileged action),
    //    enabling A's claim while pendingInstantWithdraws > 0
    deal(defaultUnderlying, address(this), 100 * ONE_SCALE);
    underlying.transfer(address(strategy), 100 * ONE_SCALE);
    // CDO-side enablement (instantWithdrawDeadline path) then A claims
    vm.prank(userA);
    cdoEpoch.claimInstantWithdrawRequest();

    // BUG: per-epoch bookkeeping is stale
    uint256 epoch = strategy.epochNumber();
    assertEq(strategy.instantWithdrawsRequestsByEpoch(userA, epoch), 100 * ONE_SCALE); // not cleared
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 200 * ONE_SCALE);           // still 200
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // 5) Borrower defaults in the same epoch; manager finalizes recovery
    _makeBorrowerDefault();
    uint256 recovered = /* partial recovery */;
    deal(defaultUnderlying, recoverySource, recovered);
    vm.prank(manager);
    cdoEpoch.finalizeDefault(recovered, recoverySource);

    // defaultRecoveryPrice / reserve computed with phantom basis:
    // totalBasis includes A's already-paid 100 and prefundedReserve counts cash
    // that A already withdrew.
    // 6) B's default claim is underpaid, and once the real cash is exhausted the
    //    remaining claimants' _transferDefaultRecovery reverts -> funds frozen.
    vm.prank(userB);
    cdoEpoch.claimInstantWithdrawRequest();
    // assert: recovered reserve dust > 0 locked forever / last claimant reverts
}
```
