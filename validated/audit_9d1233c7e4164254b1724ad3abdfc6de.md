Now checking the ordering: whether `epochNumber` is incremented before `collectWithdrawFunds` during `stopEpoch`, which determines if `lossRecoveryPriceByEpoch` is keyed differently than `lastWithdrawRequest`.### Title
Loss-adjusted withdraw receipts bypass `lossRecoveryPriceByEpoch` haircut and redeem at par via epoch-key mismatch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The CVE-2020-14163 bug class is "a key/value pair where the value backing a key is freed or rebound between the key lookup and the value lookup." The direct analog in `IdleCreditVault` is the epoch-keyed haircut ledger: `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]` using the **stop-time** `epochNumber`, while `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` using the **request-time** epoch stored at `requestWithdraw`. `epochNumber` is incremented inside `deposit()` during the stopEpoch flow (line 610), so a receipt marked in epoch N is looked up against a haircut stored under epoch N+1 — the key no longer matches the value by the time the claim reads it. The loss-adjusted branch returns 0 and `_claimFundedWithdrawRequest` then pays the receipt **at par**, even though the strategy only collected the haircut `pendingToFund`.

### Finding Description
- `requestWithdraw` stores `lastWithdrawRequest[_user] = currentEpoch` where `currentEpoch = epochNumber` read before the next `stopEpoch` (lines 260–282).
- `collectWithdrawFunds`, invoked by the CDO inside `stopEpochWithDuration`, writes `lossRecoveryPriceByEpoch[epochNumber]` (line 421). `deposit()` increments `epochNumber` "done on stopEpoch" (lines 607–610), so if the increment precedes `collectWithdrawFunds` in the same stop — consistent with the epoch-queue convention where the claim epoch is `epochNumber() + 1` at request time (see `test/foundry/IdleCDOEpochQueue.t.sol` line 862/1356) — the haircut is stored under an epoch no receipt's `lastWithdrawRequest` will ever equal.
- On `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest]` → 0 → returns early (lines 789–795). `_claimFundedWithdrawRequest` then only gates on `epochNumber <= lastWithdrawRequest` (line 326), which passes after the stop, and pays `withdrawsRequests[_user]` in full via `_transferFundedClaim` (lines 338–349).
- Result: the partial-loss haircut recorded by `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` is never applied; receipts redeem at par while the strategy holds only `pendingToFund < pendingBasis`. Early claimers drain the shortfall from later claimants and from active LP backing — direct insolvency, quantified as `pendingBasis - pendingToFund` (the intended receipt loss) per lossy epoch.

No existing guard stops this: the pre-request guard (lines 263–271) checks the same mismatched key, and `claimWithdrawRequest` has no solvency check.

### Impact Explanation
Any unprivileged tranche holder with a pending withdraw receipt in a `stopEpochWithDuration` epoch claims the un-haircut amount. The shortfall is socialized onto remaining claimants (last claimants' transfers revert — permanent freeze of the residual) or onto active tranche holders, breaking the loss-waterfall invariant that `previewLossAdjustedWithdrawFunds` was designed to enforce.

### Likelihood Explanation
The trigger is a routine partial-loss `stopEpochWithDuration` while withdraw receipts are pending — a normal, supported code path. No attacker prerequisites beyond holding a receipt; honest roles (manager, borrower) perform all privileged steps. Note: the finding is confirmed under the ordering where `deposit()`'s `epochNumber` increment executes before `collectWithdrawFunds` inside `stopEpochWithDuration`; if the CDO calls `collectWithdrawFunds` first, the keys coincide and the bug is latent rather than live — the keying should be made explicit regardless.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the same epoch identifier stored in `lastWithdrawRequest` (e.g., `epochNumber - 1` at stop time, or store `epochNumber + 1` in `lastWithdrawRequest` at request time), and add an invariant check in `_claimFundedWithdrawRequest` that reverts if `lossRecoveryPriceByEpoch` is non-zero for any uncleared receipt epoch of the user.

// test/foundry/IdleCreditVaultLossKeyMismatch.t.sol
function testLossReceiptPaysPar() external {
    // 1. LP deposits AA, epoch starts.
    uint256 minted = idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);

    // 2. Buffer: user requests withdraw -> lastWithdrawRequest[user] = epochNumber (=1).
    uint256 req = cdoEpoch.requestWithdraw(minted / 2, address(AAtranche));

    // 3. Epoch runs; borrower repays only pendingToFund (partial loss).
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = strategy.pendingWithdraws();
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(loss);
    deal(underlying, borrower, cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, 0, duration, loss); // epochNumber -> 2, price keyed [2]

    // 4. Claim: lossRecoveryPriceByEpoch[lastWithdrawRequest=1] == 0 -> funded path pays full.
    uint256 pre = underlying.balanceOf(user);
    cdoEpoch.claimWithdrawRequest(); // strategy-side via CDO
    assertEq(underlying.balanceOf(user) - pre, req); // par payout, haircut never applied
    assertGt(req, req * strategy.lossRecoveryPriceByEpoch(2) / 1e18); // funded < paid => insolvent
}
