### Title
Missing sender allowlist check in `HandleLegacyUserMessage` allows any correctly-signed EOA to consume DON node compute/quota - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` validates the message's payload structure, timestamp freshness, and method, but never checks that `msg.Body.Sender` belongs to any per-workflow/DON allowlist before fanning the request out to every node in the DON via `don.SendToNode`. This is explicitly flagged in the code itself with a `// TODO: apply allowlist and rate-limiting here` comment immediately preceding the fan-out logic.

### Finding Description
The request flow is: `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218`) decodes and validates the JSON-RPC envelope (`msg.Validate()`, which only checks structural/signature-format correctness, not sender authorization) and then dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)` for legacy DON-ID-addressed requests [1](#0-0) .

Inside `HandleLegacyUserMessage`, the handler:
1. Unmarshals the trigger payload and checks `Timestamp` is non-zero and not stale.
2. Checks `msg.Body.Method == MethodWebAPITrigger`.
3. Builds a signed request via `common.ValidatedRequestFromMessage` (this only validates that the signature matches `msg.Body.Sender`, i.e., that the sender field is self-consistent with the ECDSA signature — it does **not** check that the sender is a registered/allowlisted workflow owner).
4. Immediately above the fan-out loop there is a literal `// TODO: apply allowlist and rate-limiting here` comment.
5. It stores a callback and loops over **every** member of `h.donConfig.Members`, calling `don.SendToNode(ctx, member.Address, req)` for each one [2](#0-1) .

No allowlist/quota check on `msg.Body.Sender` exists anywhere in this path before the request is forwarded to all DON nodes. Any attacker who can generate an arbitrary ECDSA keypair, sign a well-formed `web_api_trigger` request, and produce a fresh timestamp will have that request forwarded to and processed by every node in the DON, consuming compute/quota that should be reserved for allowlisted workflow owners. Rate limiting (`nodeRateLimiter`) exists only in `handleWebAPIOutgoingMessage`, which handles node-to-gateway outbound HTTP responses, not incoming user requests to the DON — so there is also no meaningful throttling on unregistered senders at this layer.

### Impact Explanation
This matches the Chainlink bounty impact class of allowlist/quota bypass: an unprivileged attacker (any address with an EOA key, no special role) can force arbitrary DON nodes to process/execute trigger requests reserved for allowlisted workflow owners, consuming node compute resources, and potentially triggering downstream workflow executions or webhook/API calls billed or rate-limited per registered workflow. This does not require operator, node, or DON compromise — the attacker only needs to reach the gateway's user-facing HTTP port.

### Likelihood Explanation
High feasibility: the attacker needs only (a) network access to the gateway's user port, and (b) an arbitrary ECDSA private key to sign the message body per the existing signature scheme used by `common.ValidatedRequestFromMessage`. There is no allowlist gate to bypass — it simply does not exist for legacy user messages in this handler, so the attack is trivially repeatable at any request rate up to whatever node rate limiting exists on the node side (which is separate and not enforced here).

### Recommendation
Implement the allowlist check called out by the `// TODO` in `HandleLegacyUserMessage` before saving the callback and calling `don.SendToNode`: look up `msg.Body.Sender` against the DON's/workflow's configured allowlist (e.g., via `h.donConfig` or a workflow registry) and reject with an appropriate `api.HandlerError`/`api.UnauthorizedError` if the sender is not registered. Apply consistent per-sender rate limiting for inbound user messages, not just for node-originated outbound messages.

### Proof of Concept
Go handler-level test (add to `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` with a `donConfig` containing one or more DON members and a mock `handlers.DON` (`don.SendToNode` mock expecting `Times(0)`).
2. Build an `api.Message` with `Body.Method = MethodWebAPITrigger`, a valid `TriggerRequestPayload` (fresh `Timestamp`), and sign it with an arbitrary, non-registered ECDSA key so `Body.Sender` is that key's address (ensure `common.ValidatedRequestFromMessage` succeeds, proving the signature is internally consistent/valid).
3. Call `h.HandleLegacyUserMessage(ctx, msg, callback)`.
4. Assert (current buggy behavior): `don.SendToNode` is invoked for every DON member despite the sender never having been allowlisted — demonstrating the bypass.
5. After the fix: assert the mock's `SendToNode` is never called and `callback.SendResponse` returns an authorization/allowlist error code.
