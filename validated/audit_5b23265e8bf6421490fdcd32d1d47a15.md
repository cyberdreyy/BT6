### Title
Loss-adjusted withdrawal haircut is keyed only to `lastWithdrawRequest`, letting earlier-epoch pending receipts escape the loss and claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` records a single `lossRecoveryPriceByEpoch[epochNumber]` that haircuts the **entire aggregate** `pendingWithdraws` basis, but `_claimLossAdjustedWithdrawRequest` only clears the per-epoch slice stored under `withdrawsRequestsByEpoch[_user][lastWithdrawRequest[_user]]`. Any portion of the same user's pending basis recorded under earlier epochs remains in `withdrawsRequests[_user]` and is later paid at par by `_claimFundedWithdrawRequest`, even though the borrower funded only the haircutted amount. This is the direct analog of the CVE-2022-1508 out-of-bounds read: the claim path reads the haircut ledger at a stale/attacker-shaped epoch index instead of covering the whole basis the loss was computed on.

### Finding Description
- At `collectWithdrawFunds` (lines 411-421), when `_amount < pendingBasis`, the whole aggregate `pendingWithdraws` is haircut to a single recovery price saved under `lossRecoveryPriceByEpoch[epochNumber]` and `pendingWithdraws` is zeroed.
- `requestWithdraw` (lines 282-293) records each request under `withdrawsRequestsByEpoch[_user][currentEpoch]` and overwrites `lastWithdrawRequest[_user]` with the newest epoch.
- `_claimLossAdjustedWithdrawRequest` (lines 789-800) reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and calls `_clearWithdrawClaimForEpoch(_user, lossEpoch, false)`, which clears **only** `withdrawsRequestsByEpoch[_user][lossEpoch]` from the aggregate `withdrawsRequests[_user]` (lines 815-820).
- `_claimFundedWithdrawRequest` (lines 319-349) then pays the remaining `withdrawsRequests[_user]` at par via `_transferFundedClaim`.

`pendingWithdraws` is a global aggregate that can span multiple epochs: a user can request a withdrawal in epoch N, let it sit unprocessed while `stopEpoch` bumps `epochNumber` (the guard at lines 263-271 only blocks re-request when the *previous* epoch stored a loss price, not when the receipt was simply carried forward unfunded or when a new request is added in the same pending pool), then request again in epoch N+1. When epoch N+1 ends with `stopEpochWithDuration(_lossAmount)`, the loss is computed on the aggregate basis, but the user claims `withdrawsRequestsByEpoch[N+1] * lossRecoveryPrice` and then claims the epoch-N slice at 100%.

Broken invariant: one receipt, one haircut. The reserve only received `pendingToFund < pendingBasis`, yet pays out `epochN+1 amount * price + epochN amount * 1.0`, exceeding the funded amount. Excess is paid from strategy underlyings that back active tranche holders / other claimants (`_transferFundedClaim` only guards against touching `defaultRecoveryReserve`, not the funded pool of other pending claims).

### Impact Explanation
Direct theft / insolvency: the attacker withdraws more underlying than the haircutted funded amount, draining funds owed to other pending withdrawers or reducing backing for active AA/BB NAV. Quantified: attacker with `X` in an earlier pending epoch and `Y` in the loss epoch extracts `X * (1 - lossRecoveryPrice)` extra underlying versus intended.

### Likelihood Explanation
Requires an epoch ending with a partial loss via `stopEpochWithDuration(_lossAmount)` — a manager/borrower-driven honest action in scope — while the attacker has unfunded pending receipts spanning more than one epoch key. The attacker is an unprivileged tranche holder using only `requestWithdraw`/`claimWithdrawRequest` timing; no privileged role misbehavior needed. Likelihood is moderate because it needs a lossy stop while the attacker holds multi-epoch pending basis, which is achievable by simply not claiming between epochs.

### Recommendation
When a loss is applied to the aggregate `pendingWithdraws`, the per-user claim must haircut **all** of the user's pending basis, not just the slice under `lastWithdrawRequest`. Either iterate/track all epochs contributing to the user's pending claim and clear them at `lossRecoveryPrice`, or disallow creating a new `requestWithdraw` while any prior unfunded receipt still contributes to `pendingWithdraws` (extend the existing guard at lines 263-271 to check `withdrawsRequests[_user] != 0` regardless of which epoch stored the price).

### Proof of Concept
Foundry sketch (against existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. user deposits, requests withdraw in epoch N (running epoch)
// 2. stopEpoch normally so pendingWithdraws is NOT fully collected
//    (or start next epoch leaving receipt in aggregate pending)
// 3. epoch N+1 buffer: user calls cdoEpoch.requestWithdraw again
//    -> lastWithdrawRequest[user] = N+1, withdrawsRequestsByEpoch[user][N] still > 0
// 4. manager calls stopEpochWithDuration(interest, 0, duration, lossAmount)
//    -> collectWithdrawFunds(_amount < pendingBasis) stores
//       lossRecoveryPriceByEpoch[N+1] < RECOVERY_FULL
// 5. user calls cdoEpoch.claimWithdrawRequest():
//    - _claimLossAdjustedWithdrawRequest pays slice[N+1] * lossRecoveryPrice
//    - _claimFundedWithdrawRequest pays slice[N] at par
// assert: strategy underlying balance < sum of remaining legitimate claims
```

Caveat: I could not fully verify within the available iterations the exact code path that keeps epoch-N receipts inside `pendingWithdraws` across a subsequent `stopEpoch` without triggering the existing guards (the `_interest`/`isClosed` branches and queue-processing ordering matter). The core accounting asymmetry — aggregate basis haircut vs. per-epoch-keyed claim — is confirmed at `IdleCreditVault.sol:411-421` and `:789-800` / `:815-820`. If every `stopEpoch` unconditionally collects all of `pendingWithdraws`, the multi-epoch stale slice cannot form and this reduces to a non-issue; that specific funding path in `IdleCDOEpochVariant.stopEpochWithDuration` should be checked before finalizing severity.   function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
