## Finding: Valid

### Title
Stale `distribution_pool` entries keyed to a former operator bypass `beneficiary_for_operator` redirection in `distribute_internal` - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`distribute()` is an unrestricted `public entry fun` — "Allow anyone to distribute already unlocked funds" — that any unprivileged account can call for any `(staker, operator)` pair. [1](#0-0)  Inside `distribute_internal`, the code only redirects a payout to the beneficiary when the distribution-pool shareholder address exactly equals the `operator` parameter that was passed in for the *current* map entry:
```
if (recipient == operator) { recipient = beneficiary_for_operator(operator); }
``` [2](#0-1) 

### Finding Description
`switch_operator_with_same_commission`/`switch_operator` moves an entire `StakingContract` (including its `distribution_pool`) from the `old_operator` key to a `new_operator` key: `staking_contracts.remove(&old_operator)` … `staking_contracts.add(new_operator, staking_contract)`. [3](#0-2) 

Before the move, it force-distributes already-inactive funds via `distribute_internal(staker_address, old_operator, &mut staking_contract)` (which correctly resolves `beneficiary_for_operator(old_operator)` because `recipient == operator` matches), and then calls `request_commission_internal(old_operator, &mut staking_contract)`, which calls `add_distribution(old_operator, staking_contract, old_operator, commission_amount)` — this *adds a new share entry keyed to `old_operator`* to the same `distribution_pool`, representing commission that is only now being unlocked (still `pending_inactive`, subject to the stake pool's lockup) and therefore is not paid out immediately. [4](#0-3)  This newly added `old_operator` share entry is what then gets carried, unmodified, into the `StakingContract` struct that is re-added to the map under `new_operator`.

Once the stake pool's lockup expires and the previously-requested commission becomes fully `inactive`, anyone (no ownership required) can call `distribute(staker, new_operator)`. [5](#0-4)  This invokes `distribute_internal(staker, new_operator, staking_contract)`. When the loop iterates over `distribution_pool.shareholders()` and encounters the stale `old_operator` entry, the beneficiary check `recipient == operator` compares `old_operator == new_operator`, which is false — so the redirection to `beneficiary_for_operator(old_operator)` never happens, and the coins are deposited directly to the raw `old_operator` address instead. [6](#0-5) 

### Impact Explanation
If the former operator (`old_operator`) had previously called `set_beneficiary_for_operator` to redirect their commission payouts to a separate beneficiary address, that beneficiary is silently bypassed for any commission that was requested-but-still-locked at the moment of `switch_operator`. The invariant stated in the code comments — that operator commission is always attributable to `beneficiary_for_operator(operator)` — is broken for this class of stale, cross-key distribution entries, permanently misdirecting the payout to the operator's own account instead of their registered beneficiary. This matches the accepted impact category "Operator commission, beneficiary payout ... corruption that credits the wrong account."

### Likelihood Explanation
The trigger requires no privileged role: any account can call the `public entry fun distribute(staker, operator)`. [7](#0-6)  The only precondition is that the staker previously called `switch_operator`/`switch_operator_with_same_commission` while there was unpaid, still-locked commission for the old operator, and that old operator had set a beneficiary — a realistic and unprivileged sequence of normal staking operations.

### Recommendation
When moving a `StakingContract` from `old_operator` to `new_operator` in `switch_operator`/`switch_operator_with_same_commission`, either (a) fully settle/rename any remaining `distribution_pool` shares keyed to `old_operator` (e.g., re-key them to `beneficiary_for_operator(old_operator)` before the map swap), or (b) change the beneficiary check in `distribute_internal` to resolve `beneficiary_for_operator(recipient)` for every shareholder that is itself a registered operator address, rather than only for `recipient == operator` (the current map key).

### Proof of Concept
1. Staker creates a staking contract with `operator1`, `operator1` calls `set_beneficiary_for_operator(operator1, beneficiary)`.
2. Stake pool accrues rewards; commission becomes due but stake pool is still in its lockup period (so no `inactive` funds yet).
3. Staker calls `switch_operator(staker, operator1, operator2, ...)`. This calls `request_commission_internal(operator1, ...)`, adding a distribution share keyed to `operator1` inside the `distribution_pool`, which is then moved into the `StakingContract` entry now keyed by `operator2`.
4. Lockup period elapses (`stake::fast_forward_to_unlock` / epoch transition) so the requested commission becomes `inactive`.
5. Any unrelated account calls `staking_contract::distribute(staker_address, operator2)`.
6. Assert: funds for the `operator1`-keyed distribution share are deposited to `operator1`'s address directly, not to `beneficiary_for_operator(operator1)` == `beneficiary`, violating the beneficiary invariant.
