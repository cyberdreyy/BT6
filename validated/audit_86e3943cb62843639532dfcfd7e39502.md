### Title
`initialize_fee_state` accepts `fee_wallet = Pubkey::default()` / `admin_key = Pubkey::default()` with no validation, allowing SOL fees to be permanently redirected to an unrecoverable address and the admin role to become unassignable - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
`initialize_fee_state` writes attacker-supplied `admin_key` and `fee_wallet` directly into the singleton `FeeState` PDA with zero validation that either value is non-default. Since the `fee_state` account is created with Anchor's `init` constraint (one-time only, permissionless, no admin gating on the instruction itself), whoever's transaction lands first for this PDA controls these values for the lifetime of the program's fee mechanism.

### Finding Description
In `initialize_fee_state`, the accounts struct `InitFeeState` only requires a `payer: Signer` and derives `fee_state` via `init` at the fixed PDA seeds `[FEE_STATE_SEED]` — there is no `has_one`, no allow-list, and no privileged-authority check gating who may call this instruction: [1](#0-0) 

The handler blindly assigns caller-supplied values: [2](#0-1) 

There is no `require!(fee_wallet != Pubkey::default())` or equivalent check on `admin_key`. Because the PDA is derived from static seeds with no per-caller component, this instruction can only be executed successfully once program-wide (subsequent calls fail on `init` re-initialization), meaning the first successful call — which any unprivileged signer holding lamports for rent could invoke — permanently fixes `global_fee_admin` and `global_fee_wallet`.

Downstream, `global_fee_wallet` is used as the literal SOL-transfer destination, validated only via `has_one = global_fee_wallet` (i.e., "the account passed in matches whatever is stored," not "is a legitimate wallet"), e.g. in `lending_pool_add_bank`: [3](#0-2) [4](#0-3) 

If `fee_wallet` is `Pubkey::default()`, every flat SOL fee transfer (bank init fees, liquidation fees, order-init fees, etc. routed through `global_fee_wallet`) is sent to the all-zero address, which is the Solana System Program's own address — an account with no controlling keypair, from which funds cannot practically be recovered by any user-level instruction.

Separately, `global_fee_admin` gates `edit_fee_state` via `has_one = global_fee_admin @ MarginfiError::Unauthorized`: [5](#0-4) 
If `admin_key` is also left as `Pubkey::default()`, no wallet can ever produce a valid signature for that key (it has no known private key), so `edit_fee_state` becomes permanently uncallable and the corrupted `fee_wallet` can never be fixed.

### Impact Explanation
If exploited (or triggered accidentally by a misconfigured deployment script), all future SOL flat fees routed through `global_fee_wallet` are unrecoverably lost to the System Program address, and — if `admin_key` is also zeroed — there is no path to ever correct it via the intended `edit_fee_state` admin instruction, since that would require a signature from the un-ownable default pubkey. This is a durable, program-wide value-redirection/freeze bug consistent with the "NO_VALUE_REDIRECTION" and metadata-integrity invariants cited in the question.

### Likelihood Explanation
The exploit requires winning a race for the *one-time* `initialize_fee_state` call on a fresh/undeployed `fee_state` PDA — this is only feasible during the deployment window before the legitimate admin's initialization transaction confirms (e.g., a public mempool/race on mainnet before the real init lands, or if a deployment script never actually calls this ix with the intended parameters). It is not exploitable against an already-initialized production fee_state (the PDA already exists, so `init` will fail). This limits real-world likelihood to a narrow deployment/bootstrap race rather than an anytime-exploitable path against a live, fully-initialized program.

### Recommendation
Add explicit validation in `initialize_fee_state` (and equivalently in `initialize_fee_state_v2` / any similar one-shot initializer) rejecting `Pubkey::default()` for both `admin_key` and `fee_wallet`, e.g. `require_keys_neq!(admin_key, Pubkey::default(), MarginfiError::InvalidFeeAdmin)` and the analogous check for `fee_wallet` before writing them into `FeeState`. Additionally consider gating this instruction with a known upgrade/deploy authority check (e.g., requiring the payer/signer to match the program's upgrade authority) rather than leaving it fully permissionless, to eliminate the initialization race entirely.

### Proof of Concept
Rust unit/integration test plan (using the existing `test-utils` harness, e.g. patterns in `test-utils/src/marginfi_group.rs`):
1. Deploy a fresh program instance without invoking `initialize_fee_state`.
2. As an arbitrary unprivileged keypair (not the intended admin), call `initialize_fee_state` with `admin_key = Pubkey::default()` and `fee_wallet = Pubkey::default()`.
3. Assert the instruction currently succeeds (demonstrating the missing check) and that `fee_state.global_fee_wallet == Pubkey::default()` and `fee_state.global_fee_admin == Pubkey::default()`.
4. Call `lending_pool_add_bank` (or any ix that pays `bank_init_flat_sol_fee`) passing `global_fee_wallet = Pubkey::default()` (System Program address) and assert the SOL transfer succeeds and lamports land on the System Program account.
5. Attempt to call `edit_fee_state` to correct `fee_wallet`; assert it is impossible to produce a valid signer for `global_fee_admin = Pubkey::default()`, proving the corrupted state is permanently unrecoverable.
6. After applying the recommended fix, re-run step 2 and assert the instruction now fails with the new `InvalidFeeAdmin`/`InvalidFeeWallet`-style error.
