## Analysis

The external report's bug class is: a contract pays out "reward" funds without checking a precondition that should gate the payment (whether the value actually corresponds to something delivered/available), allowing funds to be paid that were never earned. Searching this repo's Gloas (`EIP7732`, ePBS) fork, I found a structurally identical pattern in the builder‑payment settlement logic: the check meant to gate builder payment (attester quorum on payload availability) is bypassed by an unconditional per‑block settlement path. [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Builder payments are settled unconditionally, bypassing the payload-availability quorum check - (File: `specs/gloas/beacon-chain.md`)

### Summary
`process_execution_payload_bid` records a `BuilderPendingPayment` whenever a bid has `amount > 0`. Two different mechanisms can later turn that pending payment into an actual `BuilderPendingWithdrawal` (i.e., a committed payment to the builder's `fee_recipient`): `process_builder_pending_payments` (epoch-boundary), which checks `payment.weight >= quorum` before paying, and `settle_builder_payment` (called every block from `apply_parent_execution_payload`), which pays out whenever `payment.withdrawal.amount > 0` with **no weight/quorum check at all**. Because `apply_parent_execution_payload` runs for a block's direct parent on the very next block — before that block's own attestations (which accumulate `payment.weight`) are processed — the unconditional block-level path always wins the race and empties the payment slot before the quorum-gated epoch path can ever apply.

### Finding Description
`process_execution_payload_bid` creates the pending payment record unconditionally for any non-zero bid: [4](#0-3) 

The intended safeguard is quorum-gated settlement in the epoch-processing path:
```python
def process_builder_pending_payments(state: BeaconState) -> None:
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)
    ...
``` [5](#0-4) 

However, `settle_builder_payment` — invoked from `apply_parent_execution_payload` on every block for its immediate parent's payment — performs no such check:
```python
def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()
``` [1](#0-0) 

`apply_parent_execution_payload` invokes this unconditionally as soon as the child block for the parent slot is processed, and there is also an unconditional fallback branch for stale (2+ epoch-old) payments that appends the withdrawal directly, again without any weight check: [6](#0-5) 

Critically, `process_block` calls `process_parent_execution_payload` (→ `apply_parent_execution_payload` → `settle_builder_payment`) **before** `process_operations` (which runs `process_attestation`, the only place that increments `payment.weight`): [7](#0-6) 

`process_attestation` only increments `payment.weight` for attestations to the parent slot's payload, gated by `is_attestation_same_slot` and `payment.withdrawal.amount > 0`: [8](#0-7) 

Since `settle_builder_payment` runs before any attestation for that slot can be included (`MIN_ATTESTATION_INCLUSION_DELAY = 1` means the earliest possible attesting block is the very block that is currently being processed, and that block's attestations are processed strictly after the settlement call), the payment for a given slot is moved into `builder_pending_withdrawals` — a firm commitment to pay the builder — before any attester vote on payload availability/timeliness has been recorded against it. The existing test suite documents this behavior as intentional/expected, confirming the withdrawal is created with no reference to `weight`/quorum at all: [9](#0-8) 

The result: the equality "a builder is paid only if a quorum of validators confirms the builder actually delivered/made available the committed payload" is broken. The per-block settlement path always fires first and empties the payment slot, making the quorum check in `process_builder_pending_payments` effectively unreachable for normal-latency blocks — the builder is paid regardless of whether the network ever confirmed the payload.

### Impact Explanation
This falls under the Critical bucket: "a payload executed or paid that the block did not commit to." A builder's bid amount is converted into a firm withdrawal commitment (later paid out to `fee_recipient` via `apply_withdrawals`) without ever verifying, at settlement time, that the payload-timeliness/attestation quorum that the protocol's incentive design relies on was reached. This decouples payment from delivery confirmation, undermining the core "pay only for delivered/attested payloads" invariant the quorum mechanism (`get_builder_payment_quorum_threshold`, `process_builder_pending_payments`) was clearly designed to enforce.

### Likelihood Explanation
This triggers on the ordinary, unprivileged, every-block code path — no coalition, malicious peer, or client bug is required. Any normal chain progression (one block followed by its child) exercises `apply_parent_execution_payload` → `settle_builder_payment` before that child's own attestations for the parent are processed, so the described bypass appears to occur unconditionally on essentially every block rather than being a rare edge case.

### Recommendation
Add a weight/quorum check to `settle_builder_payment` (and to the "stale payment" fallback branch in `apply_parent_execution_payload`) mirroring the check in `process_builder_pending_payments`, e.g., only append `payment.withdrawal` to `builder_pending_withdrawals` if `payment.weight >= get_builder_payment_quorum_threshold(state)`; otherwise drop it (as the epoch-level function does). Alternatively, defer per-block settlement so it cannot run until the relevant attestation window has closed and weight has been finalized, restoring the intended precondition before any payment commitment is made.

### Proof of Concept
1. A builder submits a non-zero-value bid for slot `S`; `process_execution_payload_bid` records `BuilderPendingPayment{weight=0, amount=V, ...}` at `SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH` (see lines 2124-2137 above).
2. No attester votes on the availability of slot `S`'s payload occur yet (earliest possible inclusion is the very next block, per `MIN_ATTESTATION_INCLUSION_DELAY`).
3. The proposer of slot `S+1` builds a block; `process_block` calls `process_parent_execution_payload` → `apply_parent_execution_payload` → `settle_builder_payment(state, payment_index)` for `S`'s payment **before** this block's `process_operations`/`process_attestation` runs.
4. `settle_builder_payment` sees `payment.withdrawal.amount == V > 0` and unconditionally appends it to `state.builder_pending_withdrawals`, clearing the payment slot — with `weight` still `0`, i.e., far below any quorum.
5. `state.builder_pending_withdrawals` is later processed by `apply_withdrawals`, decreasing `state.builders[builder_index].balance` by `V` and crediting `fee_recipient` — the builder is paid `V` despite zero attester confirmation that the payload was ever made available.

This matches the observed behavior in the existing test `test_process_parent_execution_payload__full_parent_settles_builder_payment`, which asserts the withdrawal is created purely from `parent_bid.value`, independent of any weight/quorum value. [9](#0-8) 

**Caveat / uncertainty**: I was unable to fetch the full body of `process_parent_execution_payload` (only `apply_parent_execution_payload` was retrieved) within the available search budget, so I could not fully confirm whether `process_parent_execution_payload` itself gates the call to `apply_parent_execution_payload` on `is_parent_block_full` (i.e., whether it's possible to skip payment settlement entirely when the payload was never revealed). Regardless of that gating, the core issue stands: whenever settlement does occur via `settle_builder_payment`, it never checks `payment.weight` against the quorum threshold, unlike the parallel epoch-level function `process_builder_pending_payments`, which explicitly performs that check.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def apply_parent_execution_payload(
    state: BeaconState,
    requests: ExecutionRequests,
) -> None:
    parent_bid = state.latest_execution_payload_bid
    parent_slot = state.latest_block_header.slot
    parent_epoch = compute_epoch_at_slot(parent_slot)

    assert len(requests.withdrawals) <= MAX_WITHDRAWAL_REQUESTS_PER_PAYLOAD
    assert len(requests.consolidations) <= MAX_CONSOLIDATION_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_deposits) <= MAX_BUILDER_DEPOSIT_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_exits) <= MAX_BUILDER_EXIT_REQUESTS_PER_PAYLOAD

    # Process execution requests from parent's payload. The execution
    # requests are processed at state.slot (child's slot), not the parent's slot.
    def for_ops(operations: Sequence[Any], fn: Callable[[BeaconState, Any], None]) -> None:
        for operation in operations:
            fn(state, operation)

    for_ops(requests.deposits, process_deposit_request)
    for_ops(requests.withdrawals, process_withdrawal_request)
    for_ops(requests.consolidations, process_consolidation_request)
    for_ops(requests.builder_deposits, process_builder_deposit_request)
    for_ops(requests.builder_exits, process_builder_exit_request)

    # Settle the builder payment
    if parent_epoch == get_current_epoch(state):
        payment_index = SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_epoch == get_previous_epoch(state):
        payment_index = parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_bid.value > 0:
        # Parent is older than the previous epoch, its payment entry has been
        # evicted from builder_pending_payments. Append the withdrawal directly.
        state.builder_pending_withdrawals.append(
            BuilderPendingWithdrawal(
                fee_recipient=parent_bid.fee_recipient,
                amount=parent_bid.value,
                builder_index=parent_bid.builder_index,
            )
        )

@with_gloas_and_later

def test_process_parent_execution_payload__full_parent_settles_builder_payment(spec, state):
    """
    Test that when the parent block was full with a non-zero builder payment,
    the payment is settled into ``builder_pending_withdrawals`` and the pending
    payments slot is cleared.
    """
    builder_index = 0
    value = spec.Gwei(50_000_000)
    fee_recipient = spec.ExecutionAddress(b"\xab" * 20)

    # Set the fee recipient before committing the parent requests so the pending
    # payment uses the same address.
    state.latest_execution_payload_bid.fee_recipient = fee_recipient
    _commit_parent_requests(
        spec, state, spec.ExecutionRequests(), value=value, builder_index=builder_index
    )
    parent_bid = state.latest_execution_payload_bid.copy()
    payment_idx = spec.SLOTS_PER_EPOCH + parent_bid.slot % spec.SLOTS_PER_EPOCH

    block = build_empty_block_for_next_slot(spec, state)
    pre_pending_withdrawals_len = len(state.builder_pending_withdrawals)

    spec.process_slots(state, block.slot)
    yield from run_parent_execution_payload_processing(spec, state, block)

    # A new pending withdrawal was added for the builder payment
    assert len(state.builder_pending_withdrawals) == pre_pending_withdrawals_len + 1

    assert new_withdrawal.builder_index == builder_index
    assert new_withdrawal.fee_recipient == fee_recipient

    # The pending payment slot was cleared
    assert state.builder_pending_payments[payment_idx] == spec.BuilderPendingPayment()
