### Title
Multisig executes requests below required confirmation threshold using confirmations from removed members - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The multisig contracts (`multisig/src/lib.rs` and `multisig2/src/lib.rs`) track confirmations for each pending request in a separate `confirmations` map keyed by `request_id`. When a member is removed (`delete_member` / `DeleteKey` action), the contract only deletes requests that member *created*, but never scans and strips that member's confirmations from *other* pending requests they had previously confirmed. Those stale confirmations remain counted toward the `num_confirmations` threshold in `confirm()`, allowing a request to execute with fewer live, currently-authorized members actually approving it than `num_confirmations` requires.

### Finding Description
`add_request` stores a fresh, empty `HashSet` of confirmations per `request_id` in `self.confirmations` [1](#0-0) . Any current member can add their identity to this set via `confirm()`, and once `confirmations.len() as u32 + 1 >= self.num_confirmations`, the request is executed [2](#0-1) .

When a member is removed through `delete_member`, the code only removes requests that were *created* by that member (filtering `self.requests` where `r.member == member`), clears `num_requests_pk` for them, and revokes their access key — but it never iterates `self.confirmations` to remove that member's entry from other, unrelated pending requests they had confirmed earlier: [3](#0-2) 

The same gap exists in the original `multisig` contract's `DeleteKey` action, which likewise only purges requests created by the removed key (`r.signer_pk == pk`) and leaves that key's confirmations on other requests intact: [4](#0-3) 

Because `confirm()` never re-validates that every entry already present in `confirmations` still belongs to a current member (`self.members` in `multisig2`, or a still-valid key in `multisig`), a stale confirmation from a removed member continues to count toward the threshold check in `confirm()` [5](#0-4) . This breaks the intended equality: `confirmations counted == confirmations from live members`. Instead, `confirmations counted ⊇ confirmations from live members`, so a request can be executed by fewer live members than `num_confirmations` mandates.

### Impact Explanation
This is a Critical-severity issue per the custody-binding rules: it is "a multisig request executed below threshold." An attacker (or a set of members who no longer collectively hold enough live authority) can get arbitrary `MultiSigRequestAction`s executed — including `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, `DeployContract` — by combining stale confirmations from removed members with confirmations from a minority of remaining live members, moving NEAR held by the multisig account without the number of currently-authorized approvals the contract is supposed to require.

### Likelihood Explanation
No special privileges beyond ordinary multisig membership are required to trigger this. The precondition — a member confirms a pending request, is later removed via a legitimate `DeleteMember`/`DeleteKey` governance action (a routine multisig maintenance action, e.g. key rotation or offboarding), while other requests they confirmed remain pending — is a realistic and even likely sequence of events in long-lived multisig accounts with several outstanding requests and periodic membership churn. No collusion with the foundation, no redeploy, and no validator/node compromise is needed.

### Recommendation
When a member/key is removed (`delete_member` in `multisig2`, `DeleteKey` action in `multisig`), iterate all entries in `self.confirmations` and remove the removed member's/key's confirmation from every request, not only from requests they created. Alternatively, validate at `confirm()`/execution time that every public key or account present in a request's confirmation set is still a current member before counting it toward the threshold.

### Proof of Concept
For `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`:
1. `A` calls `add_request` to create request `R` (e.g., a `Transfer` action moving funds out of the multisig account). `R`'s confirmations set is empty.
2. `B` calls `confirm(R)` → confirmations = `{B}` (1 < 3, not executed).
3. `C` calls `confirm(R)` → confirmations = `{B, C}` (2 < 3, not executed).
4. Separately, via a legitimate prior multisig action reaching the (then-current) threshold, `C` is removed as a member through `DeleteMember` → `delete_member(C)` is invoked. This only removes requests `C` *created* and revokes `C`'s key; it does **not** remove `C`'s stale confirmation entry from `R`'s confirmations set, which still equals `{B, C}` ( [6](#0-5) ).
5. `D` (a live member) calls `confirm(R)`. In `confirm()`, `confirmations.len() as u32 + 1` = `2 + 1 = 3 >= num_confirmations (3)`, so `R` executes ( [7](#0-6) ).
6. Result: `R` executed with confirmations counted as 3, but only `B` and `D` are actually live members who confirmed — `C`'s confirmation is stale/unauthorized. The request executed below the real live-member threshold, e.g. transferring funds out of the multisig with insufficient current authorization.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
