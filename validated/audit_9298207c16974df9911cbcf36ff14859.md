### Title
Suppressed `accountNotification` for a subscriber's first legitimate account update at slot 0 due to zero used as both "no data" and "genesis slot" sentinel - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
The reported Backd `AmmGauge` bug is a checkpoint-initialization bug class: a "not yet initialized" state is represented with the same value (zero) as a legitimate first real state, causing the delta/notify logic to treat the real first update as "no change" and skip crediting/notifying it. The same pattern exists in Agave's account-subscription pubsub pipeline: the "last notified slot" checkpoint defaults to `0`, and `0` is also a completely legitimate value for a genuine account modification slot (genesis slot). When these two meanings collide, the very first `accountNotification` for a subscriber can be silently dropped.

### Finding Description
When an `accountSubscribe` request is registered, `initial_last_notified_slot` computes the checkpoint slot to seed `SubscriptionInfo::last_notified_slot`: [1](#0-0) 

If the account does not yet exist as of the subscription's initial commitment slot, `bank.get_account_modified_slot(&params.pubkey)` returns `None`, `initial_last_notified_slot` propagates `None` via `?`, and the caller falls back with `.unwrap_or(0)`: [2](#0-1) 

So `last_notified_slot` starts at `0` — which is used here purely as a "not yet notified" sentinel, exactly like `AmmGauge`'s zero-staked-total sentinel.

Later, whenever `notify_watchers`/`check_commitment_and_notify` runs for that subscription, the actual current on-chain state is fetched and compared against this checkpoint in `filter_account_result`: [3](#0-2) 

The decision to emit a notification is driven entirely by `last_modified_slot != last_notified_slot`. But slot `0` (genesis) is also a fully valid, legitimate value for `last_modified_slot` — as shown by `get_account_modified_since_parent_with_fixed_root`, where a real account write in the genesis bank returns slot `0`: [4](#0-3) 

and by the generic account-fetch path used by the subscription pipeline itself: [5](#0-4) 

Consequently, if a subscriber's checkpoint is (re)initialized to the `0` sentinel and the account's true first/most-recent modification also happened to be recorded at slot `0`, `filter_account_result` computes `last_modified_slot == last_notified_slot` (`0 == 0`) and returns `None` for the account — meaning `check_commitment_and_notify` treats this as "not notified" and no `accountNotification` message is sent to the client, even though this is the client's very first observation of that account's state: [6](#0-5) 

This is structurally identical to the reported bug class: a zero-initialized checkpoint is indistinguishable from a legitimate zero-valued state, so the "first" observer for that state transition never gets the update that everyone else who established their checkpoint at a different, non-zero value would get.

### Impact Explanation
An RPC client (unprivileged, using only `accountSubscribe`) whose checkpoint slot resolves to the `0` sentinel can silently miss the first `accountNotification` for a modification that is itself recorded at slot `0`. This produces "wrong data returned to a query" behavior — the client believes the account is unchanged/absent when a real update happened — without any crash or resource exhaustion. This matches the accepted impact categories (wrong data returned from a query) and is reachable purely by an unprivileged JSON-RPC/pubsub client via `accountSubscribe`.

### Likelihood Explanation
The trigger window is narrow: it requires the subscription's initial checkpoint computation to fall back to the `0` sentinel (i.e., the account is absent as of the subscriber's initial commitment slot) and for the account's actual recorded modification slot supplied by `check_commitment_and_notify` to also be exactly `0`. In mainnet-beta operation, this is a corner case tied to genesis-slot behavior and low-slot-number activity (e.g., testing clusters, private/local test-validator networks, or accounts modified/created very early after genesis) rather than a broadly reachable steady-state bug on a live long-running cluster. This narrows likelihood substantially, similar to how the original Backd finding was judged Medium severity because it affects only the "first" state transition under specific ordering.

### Recommendation
Do not overload the value `0` to mean both "checkpoint not yet initialized" and "legitimately modified at genesis slot." Use `Option<Slot>` (or a dedicated sentinel outside the valid slot range) for `last_notified_slot` so that "never notified" and "modified at slot 0" are distinguishable, then update `filter_account_result`/`check_commitment_and_notify` to always notify on the first comparison when the checkpoint is `None`.

### Proof of Concept
Conceptual reproduction (analogous to the PoC in the source report, adapted to Agave's pubsub path):
1. Start a bank/cluster where the target account is created and modified only in the genesis bank (slot 0) — e.g., a genesis account.
2. Subscribe via `accountSubscribe` before the account exists as of the subscriber's initial checkpoint slot lookup (so `initial_last_notified_slot` returns `None` and the checkpoint defaults to `0` via `.unwrap_or(0)`).
3. Trigger `notify_watchers` for that subscription while the bank being read still reports the account's `get_account_modified_slot` as `(account, 0)`.
4. Observe that `filter_account_result` computes `last_modified_slot (0) == last_notified_slot (0)` and returns `None`, so no `accountNotification` is emitted for this update — the client never receives notice of the account's actual state, unlike a subscriber whose checkpoint happened to be non-zero.

This confirms the same "poor checkpoint / zero used as both absent-state and valid-state sentinel" root cause described in the referenced report, exploitable purely through the unprivileged `accountSubscribe` JSON-RPC/pubsub interface.

fn filter_account_result(
    result: Option<(AccountSharedData, Slot)>,
    params: &AccountSubscriptionParams,
    last_notified_slot: Slot,
    bank: Arc<Bank>,
) -> (Option<UiAccount>, Slot) {
    // If the account is not found, `last_modified_slot` will default to zero and
    // we will notify clients that the account no longer exists if we haven't already
    let (account, last_modified_slot) = result.unwrap_or_default();

    // If last_modified_slot < last_notified_slot this means that we last notified for a fork
    // and should notify that the account state has been reverted.
    let account = (last_modified_slot != last_notified_slot).then(|| {
        if is_known_spl_token_id(account.owner())
            && params.encoding == UiAccountEncoding::JsonParsed
        {
            get_parsed_token_account(&bank, &params.pubkey, account, None)
        } else {
            encode_ui_account(&params.pubkey, &account, params.encoding, None, None)
        }
    });
    (account, last_modified_slot)
}

fn initial_last_notified_slot(
    params: &SubscriptionParams,
    bank_forks: &RwLock<BankForks>,
    block_commitment_cache: &RwLock<BlockCommitmentCache>,
    optimistically_confirmed_bank: &RwLock<OptimisticallyConfirmedBank>,
) -> Option<Slot> {
    match params {
        SubscriptionParams::Account(params) => {
            let slot = if params.commitment.is_finalized() {
                block_commitment_cache
                    .read()
                    .unwrap()
                    .highest_super_majority_root()
            } else if params.commitment.is_confirmed() {
                optimistically_confirmed_bank.read().unwrap().bank.slot()
            } else {
                block_commitment_cache.read().unwrap().slot()
            };

            let bank = bank_forks.read().unwrap().get(slot)?;
            Some(bank.get_account_modified_slot(&params.pubkey)?.1)
        }
        _ => None,
    }
}
