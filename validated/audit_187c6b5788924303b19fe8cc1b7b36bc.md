### Title
Rejection weight is never retracted when a signer flips from Rejected to Accepted, letting stale rejection weight combine with fresh approval weight to falsely force a valid block into `SignersRejected` - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener`'s per-block tally (`BlockStatus`) accumulates `total_weight_rejected` and `total_weight_approved` independently, gated by two different sets (`responded_signers` for rejections, `gathered_signatures` for acceptances). A signer that first rejects and later legitimately re-evaluates and accepts the same block (a behavior explicitly supported by the signer state machine, see `should_reevaluate_reject_reason` / re-proposal flows) has its weight added to `total_weight_rejected` and, on the later Accepted message, also added to `total_weight_approved`, without ever being subtracted from `total_weight_rejected`. This breaks the invariant that `total_weight_rejected + total_weight_approved <= total_weight`, and lets the miner-side coordinator (`signer_coordinator.rs`) treat a block as having a rejecting blocking-minority when in fact a subset of that "rejecting" weight has since flipped to approving.

### Finding Description
In `stackerdb_listener.rs`, `BlockResponse::Accepted` is only guarded by:
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [1](#0-0) 

`BlockResponse::Rejected` is guarded by a separate flag:
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [2](#0-1) 

Sequence of events for a single honest-looking signer `S` with weight `w`:
1. `S` sends `Rejected` first → `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += w`.
2. The signer-side state machine (documented in `docs/signer-flows.md` §3/§6, "our rejection reason allows us to reconsider" / `should_reevaluate_reject_reason`) later re-evaluates the same block and sends `Accepted`.
3. In the listener, the guard for Accepted checks `gathered_signatures.contains_key(&slot_id)`, which is still empty for `S` (only `responded_signers` was touched on rejection, not `gathered_signatures`). The guard passes → `total_weight_approved += w`.
4. `total_weight_rejected` is never decremented. `S`'s weight `w` is now counted in **both** totals simultaneously.

This breaks the equality the whole aggregation scheme depends on: at any instant, `total_weight_rejected` and `total_weight_approved` should partition (or at least not double count) the responding weight relative to `total_weight`. With the double count, `total_weight_rejected` can retain "ghost" weight from signers who have since approved.

### Impact Explanation
`signer_coordinator.rs`'s wait loop decides the outcome purely from these two counters:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ...
    return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
    return Ok(...)
}
``` [3](#0-2) 

Because `total_weight_rejected` can retain weight from signers that have already flipped to approve, the miner/coordinator can compute a stale "blocking minority" that is no longer real, causing a **valid, sufficiently-signed block to be spuriously treated as globally rejected** (`SignersRejected`), including permanently/temporarily excluding transactions from the block based on `failed_txids` weight that also includes stale/flipped-away signers. This is a liveness wedge: mining stalls or transactions get incorrectly blacklisted even though the actual live signer set would have approved the block. It can also, in the reverse timing, let `total_weight_approved` cross the acceptance threshold using weight that logically should still be counted against approval consistency checks, muddying the aggregated-weight vs. verified-accepts invariant that downstream logic (and log/monitoring output) relies on.

Note: this requires only ordinary signer behavior (no majority collusion, no key compromise) — a single signer flipping its vote due to a legitimate re-evaluation (which the signer software explicitly supports) is enough to introduce the accounting skew; a miner or gossip-observing party does not need to force anything beyond normal message delivery/timing.

### Likelihood Explanation
Signers are documented to legitimately flip rejection → acceptance (`should_reevaluate_reject_reason`, re-proposal re-evaluation flows in `docs/signer-flows.md` §3/§6), so this isn't a contrived edge case — it is an expected operational pattern (e.g., a rejection due to a stale chain view that becomes valid again once state catches up, or a superseded reject_reason). Any natural network-delay-induced re-ordering of a signer's rejection/acceptance messages, or a benign re-evaluation, triggers the skew. No adversarial majority or key access is required, only normal message timing that a single miner/gossip participant observes and can also intentionally reorder/replay (StackerDB messages are gossiped, and message ordering as seen by the coordinator is not guaranteed).

### Recommendation
Track a single per-signer "latest response" (accept/reject) instead of two independently-accumulated, differently-gated weight tallies. When a new response for a slot supersedes a prior one, subtract the old contribution before adding the new one, e.g.:
```rust
if let Some(prev) = block.signer_last_response.get(&slot_id) {
    match prev {
        Response::Rejected => block.total_weight_rejected -= weight,
        Response::Accepted => block.total_weight_approved -= weight,
    }
}
block.signer_last_response.insert(slot_id, Response::Accepted /* or Rejected */);
block.total_weight_approved += weight; // or total_weight_rejected
```
Recompute `failed_txids` weight the same way, so a signer's txid-rejection contribution is also retracted if it later accepts the block.

### Proof of Concept
1. Configure a signer set where signer `S` has weight `w` such that `w` alone can flip the blocking-minority decision when combined with a genuinely rejecting minority (`total_weight_rejected + weight_threshold > total_weight` only when `S`'s weight is counted).
2. Have `S` send `BlockResponse::Rejected` for a proposed block (e.g., due to a transient chainstate mismatch) — `stackerdb_listener.rs` records `total_weight_rejected += w` via the `responded_signers` guard.
3. Immediately after, have `S`'s signer software re-evaluate the same block (a supported path per `should_reevaluate_reject_reason`) and broadcast `BlockResponse::Accepted` for the same `block_sighash`.
4. Observe in `stackerdb_listener.rs` that the Accepted-path guard (`gathered_signatures.contains_key(&slot_id)`) is unaffected by the earlier rejection, so `total_weight_approved += w` also occurs, while `total_weight_rejected` is untouched.
5. In `signer_coordinator.rs`'s polling loop, with other signers roughly balanced around the threshold, the stale `total_weight_rejected` (still including `w`) can push `total_weight_rejected + weight_threshold > total_weight`, causing `Err(NakamotoNodeError::SignersRejected {...})` even though the currently-live weight (excluding `S`'s stale rejection) would not cross the blocking minority — a valid, adequately-signed block is discarded and transactions may be wrongly excluded.

I was not able to execute this scenario in a live test harness (no test/terminal access in this mode); the analysis is based on static code reading of `stackerdb_listener.rs` and `signer_coordinator.rs` cited above. Confirming the exact end-to-end miner-visible effect (vs. mitigations elsewhere, e.g. re-request/retry logic) would benefit from a Devin session with test execution to reproduce this against the `stacks-node/src/tests/signer/v0/mod.rs` test harness.
