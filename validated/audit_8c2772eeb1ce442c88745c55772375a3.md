### Title
Builder pending withdrawals commit an execution-layer payment that exceeds the builder's actual balance, minting Gwei - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` builds `Withdrawal` entries directly from the requested `amount` field stored in `state.builder_pending_withdrawals`, without capping that amount to the builder's actual `balance`. This uncapped amount becomes part of `state.payload_expected_withdrawals`, which — per the Gloas spec's own documentation — the execution layer is *required* to honor exactly. Meanwhile `apply_withdrawals` only ever deducts `min(withdrawal.amount, builder_balance)` from the builder's CL-side balance. The result: the EL can be committed to paying out more Gwei to a `fee_recipient` than was ever actually backed by/deducted from the builder's stake.

### Finding Description
In `get_builder_withdrawals` (specs/gloas/beacon-chain.md:1802-1834), each entry of `state.builder_pending_withdrawals` is converted into a `Withdrawal` using the raw, unvalidated `withdrawal.amount`:

```python
withdrawals.append(
    Withdrawal(
        index=withdrawal_index,
        validator_index=convert_builder_index_to_validator_index(builder_index),
        address=withdrawal.fee_recipient,
        amount=withdrawal.amount,
    )
)
``` [1](#0-0) 

There is no check against `state.builders[builder_index].balance` at this point — contrast this with the sibling function `get_builders_sweep_withdrawals`, which correctly uses the builder's actual `balance` as the withdrawal amount: [2](#0-1) 

This uncapped withdrawal amount is placed into `state.payload_expected_withdrawals` via `update_payload_expected_withdrawals`, and the spec's own commentary states that any execution payload whose parent is this beacon block "is required to honor these withdrawals in the execution layer," and further that "the execution layer mints the full committed amount regardless" of any CL-side capping: [3](#0-2) 

However, on the CL side, `apply_withdrawals` only reduces the builder's balance by the capped amount:

```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [4](#0-3) 

So if `withdrawal.amount > builder.balance`, the CL only ever removes `builder.balance` Gwei from state, but the `Withdrawal` object committed to the execution payload (and therefore the actual ETH credited to `fee_recipient` on the EL) is the full, uncapped `withdrawal.amount`. This breaks the invariant that a committed withdrawal amount must be backed by an equal decrease on the CL side — Gwei is effectively minted and paid to `fee_recipient`, a party that need not be the builder itself (the destination is `fee_recipient`, independent of the builder's `execution_address`).

This is confirmed by the spec's own test suite, which explicitly documents this as the expected (not corrected) behavior: [5](#0-4) 

The bug-class parallel to the external report is direct: just as the hardcoded Yearn selector fixed a parameter (`maxLoss`) without validating it against the real, current on-chain state (vault losses), `get_builder_withdrawals` takes a stored, previously-computed `amount` (from `BuilderPendingWithdrawal`, itself derived from a bid `value` recorded epochs earlier) and commits it as-is to the execution layer without re-validating it against the builder's *current* balance at withdrawal-processing time. Where the Yearn bug caused an unwanted revert (DoS, out of scope here), this consensus-specs analog goes the other direction: instead of reverting, the mismatch silently inflates the ETH supply and pays out Gwei that was never actually held.

### Impact Explanation
This is a **Critical** severity issue under the given impact criteria: "Gwei created ... or paid to a non-owner." The execution layer is contractually bound (per the spec's own withdrawal-commitment semantics) to credit `fee_recipient` the full withdrawal amount, while the beacon state only ever debited the builder for the capped, actually-available balance. Any sequence of events that leaves `builder.balance < sum of pending withdrawal amounts` at the time `get_builder_withdrawals` runs (e.g., balance reduced by an exit, slashing-adjacent mechanism, or another already-processed withdrawal reducing balance before this one runs, or simply a payment from a stale/large bid value recorded before the builder's balance dropped) causes this to trigger, producing unbacked ETH on the execution layer.

### Likelihood Explanation
Moderate-to-high. `BuilderPendingWithdrawal.amount` is set once at bid-settlement time (`settle_builder_payment` / `apply_parent_execution_payload`, see specs/gloas/beacon-chain.md:1761-1770) and is not re-validated at the time it is actually processed into a withdrawal, which can be arbitrarily later (queue can hold up to `BUILDER_PENDING_WITHDRAWALS_LIMIT` = 2^20 entries per the input-space table). Any intervening reduction of `builder.balance` (e.g., other withdrawals processed earlier in the same queue drain, builder exit flows, or multiple pending payments summing to more than balance) suffices to trigger the mismatch — no malicious peer, coalition, or client bug is required; this is reachable purely by ordinary, spec-following state evolution.

### Recommendation
Cap the `amount` used when constructing the `Withdrawal` in `get_builder_withdrawals` to the builder's current balance (mirroring `get_builders_sweep_withdrawals` and the CL-side capping in `apply_withdrawals`), e.g.:
```python
balance = get_balance_after_withdrawals(...)  # or track running builder balance across all_withdrawals
amount = min(withdrawal.amount, balance)
```
so that the amount committed to the execution payload never exceeds what is actually deducted from the builder's balance in the same call.

### Proof of Concept
Concrete state:
- `state.builders[0].balance = 1 ETH`
- `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, fee_recipient=X, amount=5 ETH)]`

Execution of `process_withdrawals(state)`:
1. `get_builder_withdrawals` produces `Withdrawal(validator_index=builder_index_flagged, address=X, amount=5 ETH)` — unchanged from the requested amount.
2. This entry is placed into `state.payload_expected_withdrawals`, the field the execution payload's `withdrawals` list must equal (per `assert list(payload.withdrawals) == expected.withdrawals` pattern inherited from earlier forks / enforced via the commit relationship documented in the Gloas note).
3. `apply_withdrawals` executes `state.builders[0].balance -= min(5 ETH, 1 ETH)` → builder balance becomes `0`.

Net effect: the execution layer credits `X` with 5 ETH, while only 1 ETH was ever removed from the beacon state. 4 ETH is created from nothing and paid to `X`. This exact before/after is verified by the spec's existing test `test_builder_withdrawal_insufficient_balance`, which asserts `builder_balances={0: 0}` while `withdrawal_amounts_builders={0: 5 ETH}` — i.e., the test suite already documents the imbalance as the accepted, current behavior rather than catching it as a defect. def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

##### Modified `process_withdrawals`

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
before `process_execution_payload_bid` as the latter function affects validator
balances.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
