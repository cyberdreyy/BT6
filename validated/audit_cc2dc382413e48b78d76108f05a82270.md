### Title
Fee-on-transfer underlying breaks 1:1 strategy-token minting and mid-epoch share pricing in `IdleCDOEpochVariant.depositDuringEpoch` / `IdleCreditVault.deposit` - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
The base `IdleCDO._deposit` / `IdleCDOCreditVault._deposit` correctly mint tranche shares on the received balance delta (`_contractTokenBalance(_token) - _preBal`), but the downstream accounting ignores that delta. `IIdleCDOStrategy(strategy).deposit(_amount)` is called with the gross amount, and `IdleCreditVault.deposit` pulls `_amount` via `safeTransferFrom` and mints strategy tokens 1:1 against `_amount` rather than the amount actually received (`contracts/strategies/idle/IdleCreditVault.sol:596-617`). Similarly, `IdleCDOEpochVariant.depositDuringEpoch` mints tranche shares and computes `trancheInterest`/`expectedEpochInterest` on the gross `_amount`, then forwards the gross `_amount` to the borrower (`contracts/IdleCDOEpochVariant.sol:685-732`).

### Finding Description
- `depositDuringEpoch`: `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` is followed by share minting `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` and `IdleCreditVault(strategy).mintStrategyTokens(_amount)` plus `_transferUnderlyings(_borrower(), _amount)` — all denominated in the gross `_amount` (`contracts/IdleCDOEpochVariant.sol:685-732`). With a fee-on-transfer token, the CDO only receives `_amount - fee`, but mints shares/strategy tokens for `_amount` and pushes `_amount` to the borrower.
- `IdleCreditVault.deposit`: `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` then `_mint(msg.sender, _amount)` (`contracts/strategies/idle/IdleCreditVault.sol:603-604`). If a second fee is charged on the CDO→strategy hop, the strategy mints `_amount` strategy tokens backed by only `_amount - fee` underlying.
- Since `getContractValue` counts the strategy-token balance 1:1 (`_contractTokenBalance(strategyToken)`, `contracts/IdleCDOCreditVault.sol:125-128`), every minted-but-unbacked unit inflates NAV, and `expectedEpochInterest`/tranche prices are computed on phantom principal.

### Impact Explanation
Two failure modes depending on CDO residual balance:

1. If the CDO holds residual underlying (funds earmarked for pending instant withdrawals, repaid interest, or un-skimmed residue between `_skimDonatedAssets` and the transfer), the gross `_amount` is forwarded to the borrower/strategy anyway: the fee shortfall is silently covered by other tranche holders' funds, i.e., direct theft of `fee` amount per deposit, and the depositor receives shares priced on the gross `_amount` — minting more shares than the value contributed.
2. If the CDO holds no residual, `safeTransfer`/`safeTransferFrom` of `_amount` reverts, permanently bricking `depositDuringEpoch` and `depositAA`/`depositBB` for as long as the token charges fees — a sustained DoS of the deposit path with fund impact (frozen new capital, and inflated strategy-token supply where partial transfers succeeded).

Invariant broken: fair mint/burn and solvency — tranche shares and strategy tokens must represent actually received underlying.

### Likelihood Explanation
Requires the vault's `token` to be or become fee-on-transfer (e.g., USDT enabling its fee parameter, or a token upgrade adding fees). The vault has no allowlist excluding such tokens and no guard checking received-vs-expected deltas on these paths. The attacker needs only to be a KYC-passed lender (`isWalletAllowed`) calling `depositDuringEpoch` during a running epoch, or `depositAA`/`depositBB` — both unprivileged, honest-state flows. No privileged misbehavior is required; the bug triggers on ordinary deposits once the token charges a fee.

### Recommendation
In `depositDuringEpoch` and `IdleCreditVault.deposit`, measure the received delta (`balanceOf` before/after `safeTransferFrom`) and use the net amount for share minting, `mintStrategyTokens`, `expectedEpochInterest`, and the borrower transfer. Alternatively, document/enforce that only non-fee-on-transfer tokens are supported and revert early when the received amount differs from `_amount`.

### Proof of Concept
Foundry fork test (mainnet, USDT with fee enabled via `setParams`):

```solidity
function testFeeOnTransferDepositDuringEpoch() public {
    // fork mainnet; vault with USDT underlying, epoch running (isEpochRunning = true)
    // enable USDT fee: usdtOwner.setParams(15, 15) (~0.15%)

    uint256 amount = 1_000_000e6;
    deal(USDT, alice, amount);
    vm.prank(usdtOwner); IUSDT(USDT).setParams(15, 15);

    vm.startPrank(alice);
    IUSDT(USDT).approve(address(cdo), amount);
    uint256 minted = cdo.depositDuringEpoch(amount, AATranche);
    vm.stopPrank();

    // CDO received amount - fee, but minted shares & strategy tokens for `amount`
    uint256 received = IUSDT(USDT).balanceOf(borrower); // amount forwarded gross
    assertEq(received, amount);                        // borrower got gross
    // vault only kept amount - fee from alice; the fee delta was paid from
    // residual CDO liquidity (instant-withdraw / earmarked funds) => LP loss
    // If no residual: the _transferUnderlyings(borrower, amount) reverts => DoS.
}
```

The same mismatch applies to `IdleCreditVault.deposit` when `directDeposit` is on: `safeTransferFrom(cdo, strategy, amount)` pulls gross while minting `_mint(msg.sender, _amount)` 1:1, inflating `getContractValue` by the fee on each deposit.
