### Title
Truncation of scaled APR before multiplication underpays withdraw-request interest and diverts the residue to remaining tranche holders — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`_calcInterestWithApr` divides the scaled APR by `100` before multiplying it into the interest computation. Any APR whose scaled value is not a multiple of 100 (i.e. any fractional-percent APR, which is the norm because `stopEpoch` scales the APR by `(epochDuration + bufferPeriod) / epochDuration`) silently drops the fractional part. Withdraw-requesters are systematically credited less interest than the configured APR, and the shortfall remains in the vault and is captured pro-rata by the tranche holders who stay in through `stopEpoch`.

### Finding Description
In `IdleCDOEpochVariant._calcInterestWithApr` the epoch interest is computed as:

```solidity
// contracts/IdleCDOEpochVariant.sol:807-809
function _calcInterestWithApr(uint256 _amount, uint256 _apr) internal view returns (uint256) {
    return _amount * (_apr / 100) * epochDuration / (365 days * ONE_TRANCHE_TOKEN);
}
```

`_apr` is scaled by 100 (e.g. 10% APR = `1000`), so `(_apr / 100)` truncates all sub-1% APR resolution. The comments at `IdleCDOEpochVariant.sol:844-851` explicitly document that `stopEpoch` sets an APR inflated by the buffer ratio (example: 10% target → 11.67% scaled = `1167`), which is almost never a multiple of 100. `1167 / 100 = 11`, so the effective APR becomes 11% instead of 11.67% — a ~5.7% relative loss on every interest figure derived from it.

This value feeds two user-facing paths:

- `requestWithdraw` → `_calcInterestWithdrawRequest` (`IdleCDOEpochVariant.sol:856-877`): both `totInterest`/`totTrancheInterest` (line 865-867) and `interestWithoutSplitRatio` (line 875) are computed from the truncated APR, so the withdrawer's receipt `_underlyings = principal + interest - totalFees` (`requestWithdraw`, line 776) is under-credited by up to ~1% of the APR (~5-6% of the interest itself under typical buffer scaling).
- `depositDuringEpoch` (line 693) and `expectedEpochInterest` accounting (line 728) use the same truncated interest, understating the interest the pool expects to collect.

Because the borrower repays the true (non-truncated) interest owed — via `stopEpoch`/`stopEpochWithDuration` settlement or `ProgrammableBorrower.totalInterestDueNow()` — the truncated delta is not burned; it stays in `getContractValue()` and is split between AA/BB holders at the next `_updateAccounting`. A holder who simply stays in the tranche while other users withdraw harvests the withdrawers' forfeited yield.

### Impact Explanation
Every `requestWithdraw` made on an epoch whose scaled APR has a fractional-percent component (the standard case due to buffer scaling) is paid less interest than the configured rate. The lost amount is bounded below ~1% of APR in absolute terms but is ~5-6% of the interest owed per withdraw request for typical parameters (10% APR, 30-day epoch, 5-day buffer → scaled APR 1166.66→1166, effective 11%). The forfeited yield is not lost to the protocol — it is redistributed to remaining tranche holders at epoch end, so an attacker positioned as the residual holder extracts the underpayment as profit. This is a direct wealth transfer from withdrawers to stayers, matching the external bug class (rounding favoring the wrong party).

### Likelihood Explanation
The truncation triggers whenever `unscaledApr * (epochDuration + bufferPeriod) / epochDuration` is not divisible by 100 — i.e. essentially always when `bufferPeriod > 0` and the target APR is a round percent. No privileged action beyond the normal honest `startEpoch`/`stopEpoch` flow is needed; an unprivileged tranche holder only needs to hold through `stopEpoch` while another user calls `requestWithdraw`. Magnitude per epoch is modest (bounded by the sub-1% truncation), which keeps this at Medium severity rather than High.

### Recommendation
Remove the premature division: compute `_amount * _apr * epochDuration / (365 days * ONE_TRANCHE_TOKEN * 100)`, or keep the APR in a single fixed-point scale end-to-end so no intermediate integer division discards precision.

### Proof of Concept
Foundry fork PoC sketch (against the existing `IdleCreditVault.t.sol` harness):

```solidity
// Setup: AA deposits 10_000e6, BB deposits 10_000e6, bufferPeriod = 5 days,
// epochDuration = 30 days, target APR 10% (scaled 1000).
idleCDO.depositAA(10_000 * ONE_SCALE);
idleCDO.depositBB(10_000 * ONE_SCALE); // attacker-held BB stays in

_startEpochAndCheckPrices(0); // owner sets scaled apr = 1000 * 35/30 = 1166

// Victim requests withdrawal mid-epoch
uint256 principal = victimTrancheBal * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;
(uint256 interestActual, ) = _calcInterestWithdrawRequest(principal, address(AAtranche));

// Correct interest without the /100 truncation:
uint256 aprScaled = IdleCreditVault(address(strategy)).unscaledApr(); // 1166
uint256 interestCorrect = principal * aprScaled * cdoEpoch.epochDuration()
    / (100 * 365 days * ONE_TRANCHE_TOKEN);

// interestActual uses (aprScaled / 100) = 11 instead of 11.66
assertLt(interestActual, interestCorrect);
// => victim underpaid by ~5.7% of owed interest

// stopEpoch: borrower repays true interest; the truncated delta lands in NAV
_stopEpochAndCheckPrices(0, aprScaled, _expectedFundsEndEpoch());
// BB holder NAV increases by the AA withdrawer's forfeited interest dust
assertGt(cdoEpoch.lastNAVBB(), navBBplusItsOwnShare);
```
