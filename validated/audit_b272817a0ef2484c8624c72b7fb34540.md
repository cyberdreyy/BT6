### Title
Cross-user response hijack / DOS via unscoped `MessageId` key in gateway `WebAPIHandler.savedCallbacks` map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's legacy WebAPI capabilities handler stores pending user callbacks in a map keyed **only by the caller-supplied `MessageId`**, with no binding to the message's signer/sender. Any unprivileged, authenticated-only-by-signature client that submits a legacy user message can choose an arbitrary `MessageId` and silently overwrite another in-flight request's callback entry, causing that other user's response to be delivered to the attacker (cross-user response confusion) or to be dropped entirely (permanent DOS of that specific request), analogous to the referenced report's unprotected shared-state entry that can be clobbered by any unprivileged caller.

### Finding Description
`handler.HandleLegacyUserMessage` is the entry point for legacy user-facing gateway requests [1](#0-0) . It validates payload structure/timestamp but never restricts or checks the uniqueness/ownership of `msg.Body.MessageId` against the sender identity before registering the callback:

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [2](#0-1) 

`MessageId` is a field fully controlled by whoever signs the message (limited only by length/null-byte checks in `Message.Validate`) [3](#0-2) . It is not required to be globally unique, and the map assignment above uses plain Go map semantics — a second legacy request presenting the same `MessageId` unconditionally **overwrites** the first entry, with no existence check or error.

Later, when a DON node responds with the trigger result, the handler looks the callback up **by `MessageId` alone**, with no verification that the response actually corresponds to the sender who registered that ID:
```go
func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()
	...
``` [4](#0-3) 

By contrast, the gateway's newer/other request-tracking primitive (`common.RequestCache`) explicitly scopes cache entries by both sender **and** id to prevent exactly this class of collision:
```go
key := globalId{request.Body.Sender, request.Body.MessageId}
...
_, ok := c.cache[key]
if ok {
    return errors.New("request already exists")
}
``` [5](#0-4) 

The legacy `capabilities/handler.go` path lacks this `sender`+`id` scoping and lacks a duplicate-registration guard, meaning the invariant enforced elsewhere in the gateway is missing here.

### Impact Explanation
- **Cross-user response confusion**: if attacker A submits a legacy request with `MessageId = X` shortly after victim V's in-flight request also uses `MessageId = X` (deliberately reused by a malicious/compromised client, or a predictable/short ID scheme), A's callback entry overwrites V's. When the DON node later replies for V's original request with `MessageId = X`, `handleWebAPITriggerMessage` delivers V's response payload to A's callback instead of V's — an unauthorized disclosure of another user's response data.
- **Permanent DOS of the victim's request**: V's original `callback.Wait` in `gateway.ProcessRequest` never receives a response and blocks until the caller's own context/HTTP timeout expires, returning `RequestTimeoutError` [6](#0-5) . There is no per-request expiry timer in this handler (unlike `vault`/`confidentialrelay` handlers that use `removeExpiredRequests`); it only relies on the periodic `pruneCallbacks` sweep on `CallbackMaxAgeSec` (default 120s) [7](#0-6) , so an overwritten victim request is silently orphaned until pruned or its own client-side deadline fires.

This mirrors the external report's root cause: an unprivileged actor can, through a normal, permission-less call path, corrupt or hijack shared per-ID state belonging to another user, denying them their expected response.

### Likelihood Explanation
Requires only that an attacker be able to submit a validly-signed legacy user message to the gateway with a chosen `MessageId` — this is the unprivileged, internet-facing gateway request path (`gateway.ProcessRequest` → `HandleLegacyUserMessage`), no special role or node compromise needed [8](#0-7) . The main constraint is guessing/colliding with a target's `MessageId`; this is trivially achievable if IDs are ever predictable, reused by client SDKs, or if an attacker races many low-entropy IDs against a busy service to increase odds of hitting a real victim's in-flight ID. Given no uniqueness/ownership enforcement exists at all, likelihood is non-trivial in any deployment where ID generation isn't cryptographically random and where multiple independent legacy users share a handler.

### Recommendation
Scope `savedCallbacks` (and the corresponding lookup in `handleWebAPITriggerMessage`) by a composite key of `(Sender, MessageId)` — matching the pattern already used in `common.RequestCache` — and reject/error on `HandleLegacyUserMessage` if an entry for that composite key already exists rather than silently overwriting it. Additionally, verify the responding node's message correlates to the same DON/service and sender context before dispatching the saved callback.

### Proof of Concept
1. Victim V submits a legacy `web_api_trigger` request to the gateway with `MessageId = "shared-id"`, which is signed and validated, then stored: `h.savedCallbacks["shared-id"] = victimCallback` [2](#0-1) .
2. Before the DON responds, attacker A (any unprivileged signer) submits its own legacy request also using `MessageId = "shared-id"`. This overwrites the map entry: `h.savedCallbacks["shared-id"] = attackerCallback`.
3. The DON node responds for V's original request with `MessageId = "shared-id"`. `handleWebAPITriggerMessage` looks up `h.savedCallbacks["shared-id"]`, finds `attackerCallback`, deletes the entry, and sends V's response payload to A: [4](#0-3) .
4. V's own `callback.Wait` in `gateway.ProcessRequest` never resolves and eventually times out [6](#0-5) , while A received V's response data — demonstrating both response hijack and denial of service for the victim.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}
```

type globalId struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}
