### Title
Pending withdraw receipts can be claimed at par while the pool is defaulted but before `finalizeDefaultRecovery`, draining the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimWithdrawRequest` only branches into the haircut paths once `defaultRecoveryFinalized` is set. In the window between a defaulted `stopEpoch` and `finalizeDefault`, a user whose `lastWithdrawRequest` epoch has already ended can still reach `_claimFundedWithdrawRequest`, which pays the full receipt at par via `_transferFundedClaim`. The only time guard checks `epochEndDate() != 0 && epochNumber <= lastWithdrawRequest`, and a default stop still bumps `epochNumber`, so the receipt is considered "funded" even though the borrower never repaid and the funds in the strategy are recovery/prefunded cash meant to be split at `defaultRecoveryPrice`.

### Finding Description
Memory-safety analog: use-after-free / stale-state read — a cleared-but-not-finalized accounting state is consumed through the wrong path. The epoch transition marks the pool as defaulted, but the claim path reads a stale "funded receipt" state and pays it in full.

Relevant flow in `contracts/strategies/idle/IdleCreditVault.sol`:

- `claimWithdrawRequest` only applies default haircuts when `defaultRecoveryFinalized` is true: [1](#0-0) 
- `_claimFundedWithdrawRequest` reverts only when the request epoch is still current; after the defaulting `stopEpoch` increments `epochNumber`, the check passes and the full `withdrawsRequests[_user]` (+ settled APR0 buckets) is paid: [2](#0-1) 
- The strategy can hold non-trivial underlying at that moment: partially prefunded instant claims (`_defaultPrefundedInstantReserve`, lines 716-723) and borrower-recovered cash parked via `reserveDefaultRecovery` (lines 629-633) both sit in the strategy balance and are explicitly meant to fund `defaultRecoveryReserve` at the haircut price: [3](#0-2) 
- `finalizeDefaultRecovery` then computes `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` expecting those funds to still be present: [4](#0-3) 

An unprivileged lender (tranche holder) front-runs `finalizeDefault`:

1. Deposit, `requestWithdraw` during epoch N (buffer/running phase).
2. Epoch N `stopEpoch` defaults (borrower repays less than owed). `epochNumber` becomes N+1; `pendingWithdraws` still records the unpaid basis.
3. Before the manager calls `finalizeDefault`, the user calls `claimWithdrawRequest`. `defaultRecoveryFinalized == false`, so `_claimDefaultedWithdrawRequest` is skipped; `epochEndDate != 0 && epochNumber (N+1) > lastWithdrawRequest (N)` passes; `_transferFundedClaim` pays the receipt 1:1 from recovery-bound cash.

### Impact Explanation
Direct theft + insolvency of the recovery pool. The first claimant(s) receive 100% of their basis while the pool is known to be impaired; `finalizeDefaultRecovery` later divides a smaller `reserveAmount` over the same `totalBasis`, so every other defaulted-epoch claimant and active LP absorbs the drained amount via a lower `defaultRecoveryPrice`. Quantitatively, an attacker with receipt basis `B` in a pool with prefunded/reserved cash `R` steals `B * (1 - recoveryPrice)` relative to the fair haircut, up to draining the entire prefunded reserve.

### Likelihood Explanation
The window is every defaulted epoch — `finalizeDefault` is a separate manager transaction that must supply recovered funds, so there is always at least an inter-transaction gap (in practice it can be arbitrarily long while recovery is negotiated). The attacker only needs a KYC-passed wallet with a matured withdraw receipt — the intended role this code grants the claim to. No privileged action is required.

### Recommendation
In `claimWithdrawRequest` (and `claimInstantWithdrawRequest`), gate on the CDO's `defaulted()` flag, not only `defaultRecoveryFinalized`: while the pool is defaulted but unfinalized, either revert claims for receipts of the defaulted epoch or route them to a provisional haircut path. Keep funded receipts from strictly earlier epochs payable at par only if the strategy balance exceeds the amount reserved for default recovery (`defaultPendingClaimBasis` accounting).

### Proof of Concept

```solidity
// setup: deposit with attacker, request withdraw in epoch 0
_depositWithUser(attacker, amount, true);
vm.prank(attacker);
uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche));

// epoch 0 stopEpoch defaults: borrower repays less than owed
_startEpochAndCheckPrices(0);
// seed strategy with "prefunded" recovery cash, e.g. partial instant funding
// or borrower partial send that failed at startEpoch
_stopEpochAndCheckPrices(0, initialProvidedApr, partialRepayment);
_checkDefault();

// ATTACK: claim before finalizeDefault
uint256 balPre = underlying.balanceOf(attacker);

// attacker received `basis` at par instead of basis * defaultRecoveryPrice

// or leaves the reserve short: defaultRecoveryReserve < expected
```

```text
  function claimWithdrawRequest(address _user) external returns (uint256 amount) {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized) {
      // Post-default requests are already priced after the haircut and backed by the reserve,
      // so they must not fall through to the defaulted-epoch receipt logic.
      amount = _claimPostDefaultWithdrawRequest(_user);
      if (amount != 0) return amount;
      // Only receipts created in the defaulted epoch are haircutted here; old fulfilled
      // receipts are handled below at par if they were already funded before default.
      amount = _claimDefaultedWithdrawRequest(_user);
    }
    amount += _claimLossAdjustedWithdrawRequest(_user);
    return amount + _claimFundedWithdrawRequest(_user);
  }
```
