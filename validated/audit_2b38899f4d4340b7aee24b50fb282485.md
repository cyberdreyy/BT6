### Title
Cleanup() re-checks feature flag instead of only checking `perBuild`, allowing network removal to be skipped if the flag flips mid-job - (File: executors/docker/internal/networks/manager.go)

### Summary
`manager.Cleanup` at [1](#0-0)  gates the entire cleanup path on `m.build.IsFeatureFlagOn(featureflags.NetworkPerBuild)` before ever checking `m.perBuild`. Since `m.perBuild` is the field that actually records whether a per-build network was created (set at `Create` time), re-evaluating the feature flag at `Cleanup` time introduces a state inconsistency: if the flag was on during `Create` (network created, `m.perBuild = true`) but is off during `Cleanup`, the function returns `nil` immediately without calling `m.client.NetworkRemove`.

### Finding Description
`Create` sets `m.perBuild = true` and creates the network only when the flag is on at creation time [2](#0-1) . `Cleanup`, however, does not rely solely on `m.perBuild` to decide whether to remove the network — it first re-checks the feature flag, and only then checks `m.perBuild`: [1](#0-0) 

`IsFeatureFlagOn` is defined on `*common.Build` and (based on the standard GitLab Runner feature-flag pattern) evaluates the flag from job variables/config each time it's called rather than caching a fixed value for the whole job lifetime. If `build.Variables` (or the effective FF value derived from them) can differ between the moment `Create` runs and the moment `Cleanup` runs — for example due to variable mutation, dynamic re-evaluation, or a race with configuration reload — `Cleanup` will short-circuit at the flag check and never reach the `m.perBuild` check or `NetworkRemove` call, even though a per-build network was actually created and is tracked in `m.buildNetwork.ID`.

This is inconsistent with `Inspect`, which correctly gates only on `m.perBuild` (the actual state flag) and ignores the feature flag at inspect time [3](#0-2) . `Cleanup` should follow the same pattern but does not.

### Impact Explanation
If exploitable, the created per-build Docker network (which carries labels set via `m.labeler.Labels(...)` identifying job/project metadata) would remain on the host after the job completes, discoverable via `docker network ls`/`inspect` by later, unrelated jobs sharing the same host/executor — a cleanup-invariant violation and metadata residue issue as scoped.

### Likelihood Explanation
This requires the underlying `IsFeatureFlagOn` evaluation to actually produce different results between the `Create` and `Cleanup` calls within a single job lifecycle. `common.Build.IsFeatureFlagOn` typically reads from a project/runner-level feature-flags variable resolved once from `GetAllVariables()`; I was not able to fully confirm within the available tool budget whether this value is memoized per-build or re-computed live on every call, nor whether `build.Variables` can actually be mutated by attacker-controlled input mid-job (the CI job variables backing FF checks are normally fixed for the duration of a job run and set before `Create`/`Cleanup` are invoked from the same executor session). Based on the code available, the flag value source is the job's variable set determined at job start, not something a pipeline author can change "mid-job" between `Create` and `Cleanup` of the same manager instance in a live job. The scenario is therefore primarily a latent code-quality/defensive-programming issue (inconsistent gating logic vs. `Inspect`), not a demonstrated attacker-reachable exploit within a single job's fixed variable set, absent confirmation of a live-mutation path into `IsFeatureFlagOn`.

### Recommendation
Change `Cleanup` to gate exclusively on `m.perBuild` (matching `Inspect`), i.e. remove the redundant flag check:
```go
func (m *manager) Cleanup(ctx context.Context) error {
	if !m.perBuild {
		return nil
	}
	...
}
```
This makes cleanup depend only on actual manager state rather than a potentially re-evaluated feature flag, eliminating the theoretical inconsistency window regardless of whether it is currently reachable by attacker-controlled input.

```go
func (m *manager) Create(ctx context.Context, networkMode string, enableIPv6 bool) (container.NetworkMode, error) {
	m.networkMode = container.NetworkMode(networkMode)
	m.perBuild = false

	if networkMode != "" {
		return m.networkMode, nil
	}

	if !m.build.IsFeatureFlagOn(featureflags.NetworkPerBuild) {
		return m.networkMode, nil
	}

	if m.buildNetwork.ID != "" {
		return "", errBuildNetworkExists
	}

	networkName := m.build.GetNetworkName()

	m.logger.Debugln("Creating build network ", networkName)

	networkResponse, err := m.client.NetworkCreate(
		ctx,
		networkName,
		client.NetworkCreateOptions{
			Labels:     m.labeler.Labels(map[string]string{}),
			EnableIPv6: &enableIPv6,
			Options:    networkOptionsFromConfig(m.build.Runner.Docker),
		},
	)
	if err != nil {
		return "", err
	}

	// Inspect the created network to save its details
	m.buildNetwork, err = m.client.NetworkInspect(ctx, networkResponse.ID)
	if err != nil {
		return "", err
	}

	m.networkMode = container.NetworkMode(networkName)
	m.perBuild = true

	return m.networkMode, nil
```
