### Title
Any signer proposal from the current tenure's miner can indefinitely reset `last_activity_time`, defeating the miner-inactivity timeout and wedging failover to the fallback sortition winner - (File: `stacks-signer/src/chainstate/mod.rs`, `stacks-signer/src/chainstate/v1.rs`)

### Summary
`check_latest_block_in_tenure` unconditionally calls `signer_db.update_last_activity_time()` whenever it receives *any* block proposal for a tenure that does not beat the currently known chain length, as long as the currently known block hasn't itself timed out (or is only pre-committed). There is no check that the proposal is otherwise valid, canonical, or that it actually represents new miner progress — a stalled/misbehaving miner can keep resubmitting/re-broadcasting stale or non-advancing proposals for its own tenure purely to keep bumping this timestamp. That timestamp is exactly the value `SortitionState::is_timed_out` uses to decide whether the current miner has gone inactive and should be invalidated so that signers fail over to the previous ("last") sortition winner.

### Finding Description
`SortitionData::check_latest_block_in_tenure` in `stacks-signer/src/chainstate/mod.rs` (lines 376-478) is invoked on every incoming block proposal for a tenure that a signer already knows about. When the proposed block does not advance the chain past the last known signed block (`block.header.chain_length <= info.block.header.chain_length`), the code still calls: [1](#0-0) 

and similarly for the "conflicts with pre-commit" branch: [2](#0-1) 

This `update_last_activity_time` call is gated only by a `signed_group` freshness heuristic, not by any check that the sender is a legitimate/different participant, that the proposal is canonical, or that it represents genuine new activity — any resubmission of an old/losing/non-advancing block proposal for the tenure is treated as "valid miner activity," per the comment: "The miner may just be slow, so count this invalid block proposal towards valid miner activity."

That same `last_activity_time` value is the sole liveness signal consumed by `SortitionState::is_timed_out`: [3](#0-2) 

`is_timed_out` is what gates whether the current miner is demoted to `InvalidatedBeforeFirstBlock` in `SortitionsView::check_proposal`: [4](#0-3) 

Because the miner that owns the current sortition slot (the "one-slot miner" per scope) is the only party who can legitimately produce signed proposals referencing that tenure's `consensus_hash`, that same miner can trivially keep re-issuing (or gossiping) non-advancing/stale block proposals for its own tenure. Each such proposal — even though rejected as not advancing the chain — refreshes `last_activity_time`, resetting the clock that `is_timed_out` uses. This defeats the entire purpose of `block_proposal_timeout`: the mechanism exists specifically to detect a miner that has gone silent or is misbehaving and fail over to the last sortition's winner so the network doesn't stall. A miner who wants to withhold real progress (e.g., to extend an advantage, delay a competitor's tenure, or simply grief the network) can keep itself perpetually "active" in the eyes of every signer without ever producing a new canonical block, indefinitely preventing the fallback path in `check_proposal` (`ProposedBy::LastSortition` branch, gated on `InvalidatedBeforeFirstBlock`) from ever activating.

This is directly analogous to the QuantAMM bug: there, any caller could rewrite `lastPoolUpdateRun` (a timing gate meant to be updated only by privileged parties) to bypass/neutralize the intended minimum-interval protection. Here, the timing gate `last_activity_time` — meant to reflect genuine, validated miner progress — can be refreshed by the same actor whose inactivity it is supposed to detect, using proposals that are not canonical/advancing, breaking the "aggregated activity == verified progress" equality the timeout depends on.

### Impact Explanation
This breaks a liveness guarantee (High, per rules: "a signer wedged into never signing valid blocks" — here, generalized to the fallback mechanism being permanently disabled). The `block_proposal_timeout`/`is_timed_out` mechanism is the network's designed remedy for a stalled or adversarial miner: once triggered, signers stop treating the current miner as valid and defer to the previous sortition's winner, allowing the chain to keep progressing. If a miner can indefinitely suppress this timeout by resubmitting non-advancing proposals, signers never invalidate it, and the fallback to `last_sortition` can never occur — wedging the signer set into waiting on a miner that need never produce a valid, chain-advancing block, without any majority-signer collusion required.

### Likelihood Explanation
Likelihood is high: the only capability needed is the ability to author and gossip a block proposal for one's own currently-active tenure (a normal capability of the sortition-winning miner, i.e., a one-slot miner) — no signer collusion, no majority, and no cryptographic forgery is required. Simply re-sending an old/losing proposal (or a series of trivially different non-advancing headers) at any cadence less than `block_proposal_timeout` keeps the activity clock alive.

### Recommendation
Only advance `last_activity_time` when the proposal represents genuine new information distinguishable from mere retransmission of stale state — e.g., require that the block proposal be for a *new* candidate not previously seen/rejected for this tenure, or track activity based on validated/certifiably-new proposals (unique previously-unseen `signer_signature_hash`) rather than any resubmission of a non-advancing block. Consider decoupling the "count towards miner activity" heuristic from the timeout used for invalidation, or bound the number of times a single non-advancing proposal can refresh the timer.

### Proof of Concept
1. Miner M wins the current sortition slot and produces one initial block proposal B0 for tenure T (accepted/pre-committed/signed by some signers, or simply left as the "last known" block).
2. M deliberately does not extend the chain (e.g., withholds further valid blocks) but repeatedly re-broadcasts B0 (or crafts additional non-advancing headers with `chain_length <= B0.chain_length`) to the signer set at an interval less than `block_proposal_timeout`.
3. Each signer's `check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:390-419`) sees `block.header.chain_length <= info.block.header.chain_length`, rejects the proposal (`Ok(false)`), but still calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())`.
4. On the next proposal evaluation, `SortitionState::is_timed_out` (`stacks-signer/src/chainstate/v1.rs:55-94`) computes `elapsed` from the just-refreshed `last_activity_time`, which never exceeds `block_proposal_timeout`, so `is_timed_out` never returns `true`.
5. Consequently `SortitionsView::check_proposal` never demotes M to `InvalidatedBeforeFirstBlock`, so the fallback branch that would allow signers to consider `last_sortition`'s winner is never reached — the tenure is wedged on M indefinitely, with no way for the network to fail over.
