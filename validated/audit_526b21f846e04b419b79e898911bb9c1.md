### Title
Missing allowlist/authorization check in `HandleLegacyUserMessage` allows any signed message to trigger DON-wide execution - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` forwards any structurally-valid `MethodWebAPITrigger` message to every DON member via `don.SendToNode`, with only payload-decoding, timestamp-presence, and staleness checks performed before dispatch. There is no allowlist, sender-authorization, or subscription check — exactly as flagged by the explicit `// TODO: apply allowlist and rate-limiting here` comment — so any actor able to produce a message that passes the gateway's generic signature-format validation can force DON-wide fan-out of an attacker-chosen trigger payload.

### Finding Description
The gateway's `ProcessRequest` (`core/services/gateway/gateway.go`) decodes an incoming legacy request and calls only `msg.Validate()`, which checks structural constraints (signature hex length, ID/method/DonId lengths) and extracts the signer into `msg.Body.Sender` via `ExtractSigner()` — it does **not** check the signer/sender against any allowlist: [1](#0-0) 

`ProcessRequest` then dispatches straight into `h.HandleLegacyUserMessage(ctx, msg, callback)`: [2](#0-1) 

Inside `HandleLegacyUserMessage`, the checks performed are: payload JSON-decodes into `TriggerRequestPayload`, `Timestamp != 0`, and the message is not stale. Immediately after these checks is the explicit TODO acknowledging the missing control, followed only by a method-name check (`== MethodWebAPITrigger`) before the message is forwarded to **every** DON member: [3](#0-2) 

Since any key holder can sign an arbitrary `MethodWebAPITrigger` message with a valid-length signature (the signature just needs to be recoverable — `ExtractSigner` doesn't restrict which address signed it, and there is no lookup against a workflow/DON allowlist here, unlike the vault handler's `Authorizer.AuthorizeRequest`/allowlist-based auth flow used elsewhere in the codebase for a similar purpose), an unauthenticated/unprivileged sender can trigger delivery of a crafted trigger event to all DON nodes. The existing test suite documents this gap directly with its own TODO: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated`. [4](#0-3) 

By contrast, the analogous vault gateway path (`core/capabilities/vault/authorizer.go`, `gateway_vault_request_processor.go`) enforces `AuthorizeRequest` against an allowlist or JWT before any privileged action, showing the intended pattern that is absent here. [5](#0-4) 

### Impact Explanation
Any unprivileged sender able to sign a well-formed `web_api_trigger` message can force the gateway to broadcast an attacker-controlled `TriggerRequestPayload` (trigger ID, event ID, topics, params) to every node in the configured DON, which the DON's workflow engine will treat as a legitimate WebAPI trigger event. This is unauthorized triggering of DON/workflow execution by an unauthenticated caller — matching Chainlink's "unauthorized job/workflow execution" impact class, since it bypasses the sender/workflow allowlist that is supposed to gate who can invoke workflow triggers on a given DON.

### Likelihood Explanation
Exploitation requires no privileges: an attacker only needs any ECDSA keypair to sign a message meeting the structural `Validate()` constraints (valid hex signature length, non-empty IDs) and a valid, non-stale `Timestamp` in the payload — both trivially attacker-controlled. No prior registration, subscription, or allowlist entry is needed since none is checked. This is fully repeatable and requires only network access to the gateway's HTTP/WS endpoint.

### Recommendation
Before the `don.SendToNode` loop in `HandleLegacyUserMessage`, add an authorization step (allowlist lookup keyed by `msg.Body.Sender`/workflow owner, similar to `vault.Authorizer.AuthorizeRequest`) and reject/return an error response for unauthorized senders, and apply the `nodeRateLimiter`-style rate limiting per sender as the TODO indicates, prior to forwarding the message to DON members.

### Proof of Concept
Go unit test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Build handler via `setupHandler(t)` as in existing tests, obtaining `handler`, `don` mock, and configured `donConfig.Members`.
2. Construct a `*api.Message` using `triggerRequest(t, arbitraryUnregisteredKey, topics, "", "", "")` — signed with a private key that has **no** prior registration/allowlist entry anywhere in the test fixtures (i.e., not `nodes[i].PrivateKey`).
3. Set up `don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)` expectations for each DON member.
4. Call `err := handler.HandleLegacyUserMessage(ctx, msg, cb)`.
5. Current-behavior assertion (confirms the gap): assert `err == nil` and that `don.SendToNode` was invoked once per member in `donConfig.Members` (mirroring `TestHandlerReceiveHTTPMessageFromClient`'s "happy case" which already forwards to all DON members without any sender check) — [6](#0-5) .
6. Required-invariant assertion (post-fix): re-run the same test and assert that `HandleLegacyUserMessage` returns an authorization error via `callback.SendResponse` with an appropriate error code (e.g. a new `api.UnauthorizedSenderError`), and that `don.SendToNode` is **never** called for a sender not present in the allowlist.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
