### Title
Withdrawal receipt claims are permanently frozen for a lender blacklisted by the underlying token - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`claimWithdrawRequest()` and `claimInstantWithdrawRequest()` hardcode the payout recipient to `msg.sender`, and the receipt token (IdleCreditVault strategy token) is non-transferable. If a lender's address is blacklisted by the underlying token (e.g. USDC, USDT — common for credit-vault underlyings) after creating a withdrawal receipt, their claim always reverts inside `underlyingToken.safeTransfer(_user, ...)`, permanently locking already-funded underlying in `IdleCreditVault`.

### Finding Description
In `IdleCDOEpochVariant`, both claim entry points forward `msg.sender` as the `_user` argument and accept no recipient parameter:

```solidity
function claimWithdrawRequest() external {
  IdleCreditVault(strategy).claimWithdrawRequest(msg.sender);
}

function claimInstantWithdrawRequest() external {
  _checkNotAllowed(!allowInstantWithdraw);
  IdleCreditVault(strategy).claimInstantWithdrawRequest(msg.sender);
}
``` [1](#0-0) 

The strategy then pays out directly to that same address in `_transferFundedClaim`:

```solidity
underlyingToken.safeTransfer(_user, _amount);
``` [2](#0-1) 

Unlike the Derby `MainVault`, where `deposit`/`withdraw` accept a `_receiver` but `withdrawRewards` does not, here *no* claim path offers a recipient at all. The usual escape hatch — moving the claim to a clean address — is also closed: `IdleCreditVault._transfer` reverts unless `msg.sender == idleCDO`, and `canTransfer` can only be cleared, never enabled (`setCanTransfer` requires `_canTransfer == false`). [3](#0-2) 

The same hardcoded-`msg.sender` pattern exists in `IdleCDOCreditVault.claimWithdrawRequest` and in `IdleCDOEpochQueue.claimWithdrawRequest` (`safeTransfer(msg.sender, ...)`), so every user-facing claim surface shares the defect. [4](#0-3) 

Trace of the frozen state:
1. Buffer phase: a KYC'd lender calls `requestWithdraw(_amount, AATranche)`; the strategy mints receipt tokens to the lender and records `withdrawsRequests[lender] += _amount`. [5](#0-4) [6](#0-5) 
2. `stopEpoch` pulls funds from the borrower and `collectWithdrawFunds` moves the full `pendingWithdraws` amount into the strategy — the lender's claim is now fully backed. [7](#0-6) 
3. The lender's address is added to the underlying token's blacklist (e.g. USDC sanction). Every `claimWithdrawRequest()` call now reverts at `safeTransfer(lender, amount)`. The receipt cannot be sold or transferred, and no alternative recipient can be supplied. This applies equally to funded normal claims, loss-adjusted claims (`lossRecoveryPriceByEpoch`), instant-withdraw claims, and default/post-default recovery claims (`_transferDefaultRecovery`). [8](#0-7) 

### Impact Explanation
Permanent freezing of user funds. Once a receipt is funded, the underlying sits in `IdleCreditVault` earmarked for a blacklisted address that can never receive it; the burned principal is unrecoverable, so the loss equals the full claimed amount (`normalAmount + apr0PrincipalAmount + apr0InterestAmount`, or `instantWithdrawsRequests[_user]`, or the user's share of `defaultRecoveryReserve`). Blacklisting of real-world KYC'd lenders by upgradable stablecoins (USDC/USDT) is a realistic scenario for a credit protocol whose underlying is exactly such a token.

### Likelihood Explanation
Medium-low. It requires the external token issuer to blacklist the lender after the receipt is created — not controllable by an unprivileged attacker — but KYC'd institutional lenders are precisely the addresses most exposed to regulatory blacklisting, and the underlying (a credit-vault stablecoin such as USDC) already ships with a blacklist. Once triggered, no honest privileged action can rescue the funds either, since claims are address-bound and receipt transfers are disabled.

### Recommendation
Add a recipient parameter to the claim path, mirroring how other vaults expose `_receiver` on deposit/withdraw:
- `IdleCDOEpochVariant.claimWithdrawRequest(address _receiver)` and `claimInstantWithdrawRequest(address _receiver)` forwarding `_receiver` to the strategy, with `IdleCreditVault.claimWithdrawRequest/claimInstantWithdrawRequest` paying `_receiver` while still burning `msg.sender`'s (the CDO-recorded user's) receipt.
- Alternatively, allow `isWalletAllowed`-gated re-issuance of the receipt to a fresh address via an IdleCDO self-call (`_transfer` already permits the CDO to move receipts).

Apply the same recipient parameter to `IdleCDOCreditVault.claimWithdrawRequest` and `IdleCDOEpochQueue.claimWithdrawRequest`/`claimDepositRequest`.

### Proof of Concept
Foundry fork PoC outline (mainnet fork with USDC as `underlying`):

```solidity
function testBlacklistedLenderCannotClaim() public {
  // 1. buffer phase: whitelisted lender deposits and requests withdraw
  deal(USDC, lender, 100_000e6);
  vm.startPrank(lender);
  IERC20(USDC).approve(address(cdoEpoch), type(uint256).max);
  uint256 tranches = cdoEpoch.depositAA(100_000e6);
  cdoEpoch.requestWithdraw(tranches, cdoEpoch.AATranche());
  vm.stopPrank();

  // 2. run epoch, borrower repays, stopEpoch funds the receipt
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(borrower);
  IERC20(USDC).approve(address(cdoEpoch), type(uint256).max);
  vm.prank(manager);
  cdoEpoch.stopEpoch(newApr, 0);          // collectWithdrawFunds funds pendingWithdraws

  // 3. USDC blacklists lender (use real blacklist admin on fork)
  vm.prank(usdcBlacklister);
  IUSDC(USDC).blacklist(lender);

  // 4. claim reverts forever; funds stay in IdleCreditVault
  vm.prank(lender);
  vm.expectRevert();                       // safeTransfer to blacklisted addr reverts
  cdoEpoch.claimWithdrawRequest();

  assertGt(strategy.withdrawsRequests(lender), 0);      // receipt still owed
  assertGe(IERC20(USDC).balanceOf(address(strategy)), fundedAmt);
}
```

The same flow with `claimInstantWithdrawRequest` (epoch running, `allowInstantWithdraw == true`) and with a default-recovery claim after `finalizeDefault` demonstrates the freeze across all claim surfaces.

    }

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;

    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);

  function claimWithdrawRequest(uint256 _epoch) external {
    // check if withdraw requests were processed and claimed for the epoch
    uint256 _withdrawPrice = epochWithdrawPrice[_epoch];
    _checkNotAllowed(
      (_withdrawPrice == 0 && !isEpochWithdrawZero[_epoch]) ||
      epochPendingClaims[_epoch] != 0
    );
    // amount is in tranche tokens
    uint256 amount = userWithdrawalsEpochs[msg.sender][_epoch];
    if (amount == 0) {
      return;
    }
    // reset user withdraw request counter for the epoch
    userWithdrawalsEpochs[msg.sender][_epoch] = 0;
    // transfer underlyings to user based on the withdraw price of that epoch
    if (_withdrawPrice != 0) {
      IERC20Detailed(underlying).safeTransfer(msg.sender, amount * _withdrawPrice / ONE_TRANCHE);
    }
  }
