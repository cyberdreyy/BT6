### Title
Loss-adjusted withdraw funding is haircut globally but claimed via a single shared `lastWithdrawRequest` epoch pointer, letting older receipts drain unhaircutted funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` tracks each user's receipts under a single mutable pointer, `lastWithdrawRequest[_user]`, while the funding side (`pendingWithdraws`) is a global aggregate over *all* epochs' receipts. When `stopEpochWithDuration` realizes a loss, the borrower only funds a haircut amount proportional to the whole `pendingWithdraws` bucket, but `_claimLossAdjustedWithdrawRequest` applies `lossRecoveryPriceByEpoch` only to the epoch stored in `lastWithdrawRequest`. A user holding receipts from an epoch *earlier* than the loss epoch gets those receipts paid at par through `_claimFundedWithdrawRequest`, even though the borrower's funding for them was already haircut — the same "one shared slot for requests with different parameters" defect as the Duende token-cache race.

### Finding Description
The Duende bug: a single cached token entry is returned for concurrent requests made with different `TokenRequestParameters`. The analog here is a single accounting slot (`lastWithdrawRequest[_user]` plus the aggregate `withdrawsRequests[_user]`/`pendingWithdraws`) being reused for receipts that carry different per-epoch recovery parameters.

Mechanics in `contracts/strategies/idle/IdleCreditVault.sol`:

1. `requestWithdraw` records the basis per epoch (`withdrawsRequestsByEpoch[_user][currentEpoch]`) but keeps only one `lastWithdrawRequest[_user] = currentEpoch` pointer and adds the full `_amount` to the global `pendingWithdraws` (lines 279–293).
2. The anti-confusion guard at lines 263–271 only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e., only the *most recent* request epoch. Receipts sitting in earlier epochs are invisible to it.
3. When a loss is realized via `stopEpochWithDuration`, the borrower funds `pendingWithdraws` reduced by the loss haircut. That haircut applies to the *whole* aggregate, which can include receipts requested in earlier epochs that the user never claimed (the code comments at lines 323–325 explicitly allow stale unclaimed requests to persist).
4. At claim time, `_claimLossAdjustedWithdrawRequest` (lines 789–801) looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` only. A receipt whose basis lives in `withdrawsRequestsByEpoch[_user][E_old]` with `E_old != lastWithdrawRequest` falls through to `_claimFundedWithdrawRequest` (lines 319–350) and is paid at par — `amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount` transferred in full.

So two receipts with different loss parameters share one claim path keyed by a single pointer, and the one whose parameter (epoch) doesn't match the pointer is settled with the wrong price.

### Impact Explanation
Direct theft / insolvency. The strategy received only `pendingWithdraws * lossRecoveryPrice` of underlying for the loss epoch, yet pays `basis_E_old` at 100% plus `basis_E_loss * lossRecoveryPrice`. The excess paid to the first claimant is borne by other pending withdrawers and active tranche holders: the funded underlying pool is drained beyond what the borrower returned, breaking the "loss waterfall / fair burn" invariant — one receipt, priced-at-haircut payout. Quantified loss: `(1 - lossRecoveryPrice) * basis_in_earlier_epochs`, i.e., the entire haircut portion of every stale receipt a user (or colluding set of KYC'd lenders) holds in epochs preceding the loss epoch.

### Likelihood Explanation
Medium-low but realistic:
- The attacker only needs to be a KYC-passing lender (in-scope role) who makes withdraw requests across multiple epochs and simply does not claim — an explicitly documented, permitted state (NOTE at lines 323–325).
- It triggers in the `stopEpochWithDuration(_lossAmount)` mode, which is a designed recovery path, not an edge case.
- No privileged misbehavior required: manager/borrower act honestly; the loss epoch just needs to occur while a stale earlier receipt exists.
- The mitigation attempts visible in the code (the `lastWithdrawRequest` revert guard, `_transferFundedClaim` reserve guard) only cover the case where the stale receipt is in the *same* epoch as the pointer; they do not index `lossRecoveryPriceByEpoch` across all epochs that contribute to `withdrawsRequests[_user]`.

Caveat: I could not fully verify the exact epoch key under which `stopEpochWithDuration` writes `lossRecoveryPriceByEpoch` (whether it is the request epoch or the funding epoch) within the available iterations; if it is keyed by request epoch, the multi-epoch confusion above stands as described, since `lastWithdrawRequest` still stores only the latest one.

### Recommendation
- Iterate (or maintain a small set of) all epochs contributing to `withdrawsRequests[_user]` and settle each at its own `lossRecoveryPriceByEpoch[epoch]`, instead of relying on the single `lastWithdrawRequest` pointer.
- Alternatively, revert in `requestWithdraw` whenever `withdrawsRequests[_user] != 0` (or any `lossRecoveryPriceByEpoch` for epochs with nonzero `withdrawsRequestsByEpoch[_user][*]` is set), forcing claim-before-requeue regardless of which epoch holds the receipt — the same fix pattern Duende applied (key the result by the full request parameters rather than a shared slot).
