### Title
Signer relays and pushes to the node a block it locally marked invalid/rejected, because the signature‑tally path skips the validity check the pre‑commit/signing path enforces - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_pre_commit` — the only path that produces *this signer's own* signature — refuses to act unless `block_info.valid.unwrap_or(false)` is true, mirroring how a bucket-accounting function applies an invariant check before mutating state. `store_and_process_block_signature` — the path that tallies *other* signers' `BlockAccepted` messages and, once 70% weight is reached, calls `mark_locally_accepted` and `broadcast_signed_block` (pushing the block to this signer's own node) — never checks `block_info.valid` at all. The two functions perform the same conceptual "does this block get promoted/pushed" operation, but only one of them re-validates first, exactly like `removeQuoteToken()` checking bankruptcy while `moveQuoteToken()` (same effect, different exit path) omits it.

### Finding Description
In `stacks-signer/src/v0/signer.rs`:

- `handle_block_pre_commit` (~line 1323-1331) gates all further pre-commit/sign processing on:
```
if !block_info.valid.unwrap_or(false) {
    // We received a pre-commit for a block that we have not validated or we have already marked this block as invalid.
    ...
    return;
}
``` [1](#0-0) 
This check exists precisely to stop the signer from ever moving toward accepting a block it has already deemed invalid (via `handle_block_validate_reject`, `check_block_against_signer_db_state`, or the sibling/conflict guard) unless a fresh proposal explicitly re-opens the reject reason.

- `store_and_process_block_signature` (~line 2443-2538), the handler triggered when a peer's `BlockResponse::Accepted` message is processed via `handle_block_signature` → `store_and_process_block_signature`, has no equivalent check. It stores the signature, tallies weight, and once `total_signature_weight >= min_weight` it unconditionally calls `block_info.mark_locally_accepted(true)`, persists it, and calls `self.broadcast_signed_block(...)` which pushes the block to this signer's own node via `handle_post_block`. [2](#0-1) 

`BlockInfo::check_state` explicitly permits `LocallyRejected -> LocallyAccepted` as a valid transition (it is only blocked from/to the two `Globally*` terminal states):
```
BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
    prev_state,
    BlockState::GloballyRejected | BlockState::GloballyAccepted
),
``` [3](#0-2) 
so nothing in `mark_locally_accepted` itself blocks this transition for a block previously marked `valid = Some(false)` / `LocallyRejected`.

Concretely: a signer that has already locally rejected block `B` (e.g. because `check_block_against_signer_db_state` failed, or the conflict guard in `handle_block_pre_commit` fired) still keeps `B`'s `BlockInfo` row in its DB. If enough `BlockAccepted` messages for `B` subsequently arrive from other signers (normal gossip — no majority-key compromise, no auth-token access, nothing beyond observing StackerDB traffic that any signer already consumes), `store_and_process_block_signature` will tally them, hit the 70% threshold, and — without ever re-checking `block_info.valid`, `check_block_against_signer_db_state`, or the sibling/conflict guard — promote `B` to `LocallyAccepted` and push it to this signer's own node.

### Impact Explanation
This breaks the "signed vs validated" equality that the rest of the state machine is built to preserve: the pre-commit/sign path treats `valid == Some(false)` as a hard veto, but the tally/push path treats the same `BlockInfo` as pushable regardless of that flag. The result is this signer relaying/pushing a block to its own node that it independently determined to be invalid, non-canonical, or conflicting with a block it already signed — precisely the class of "signer acting on a block it should have rejected" that the report and the Impact criteria (a signer signing/pushing an invalid, non-canonical, or conflicting block) target. It does not require a majority of signers to be malicious or colluding — it only requires the ordinary situation where this signer's local view diverged (raced, or hit the conflict guard) from the view that let 70% of the *other* signers sign.

### Likelihood Explanation
Reachable purely through message gossip that every signer already processes (`BlockResponse::Accepted` via StackerDB), with no special privileges. Divergent local views are an expected, not rare, occurrence in this codebase: the same file spends hundreds of lines (sections 5 and 7 of `docs/signer-flows.md`, `conflict_still_blocks`, `reorg_permit_stands`, `check_block_against_signer_db_state`) specifically engineering for the case where "we may have signed a different block at the same height" or otherwise rejected a proposal that the wider set nonetheless accepts. That the tally/push path (`store_and_process_block_signature`) was left without the same `valid` gate that `handle_block_pre_commit` enforces looks like an oversight rather than a deliberate asymmetry, mirroring the `moveQuoteToken`/`removeQuoteToken` pattern where one of two structurally similar mutators forgot the invariant check the other has.

### Recommendation
In `store_and_process_block_signature`, before tallying signatures toward the acceptance threshold and before calling `mark_locally_accepted`/`broadcast_signed_block`, re-apply the same guard used in `handle_block_pre_commit`: reject/ignore locally-invalid blocks (`block_info.valid.unwrap_or(false)`), or at minimum re-run `check_block_against_signer_db_state` (and the sibling/conflict check) before pushing to the node, so a block this signer has already determined to be invalid/conflicting cannot be promoted and pushed purely by tallying other signers' acceptances.

### Proof of Concept
1. Signer `S` receives proposal `B` (tenure-start block at height `h`), validates it OK, pre-commits, and — following the sibling-conflict guard in `handle_block_pre_commit` (`conflict_still_blocks`/fresh-conflict logic) — instead signs a different, conflicting sibling `A` at the same height first, so `B`'s `BlockInfo` ends up `mark_locally_rejected()`'d (`valid = Some(false)`, `state = LocallyRejected`), as exercised by the existing test `signer_refuses_to_sign_second_sibling_tenure_start` in `stacks-signer/src/v0/tests.rs` for the symmetric case. [4](#0-3) 
2. Meanwhile, ≥70%-by-weight of the *other* signers (who saw `B` first, or whose own conflict evaluation landed differently) sign `B` and broadcast `BlockResponse::Accepted` for `B` over StackerDB.
3. `S` receives these via `handle_block_signature` → `store_and_process_block_signature`. Because that function never checks `block_info.valid`, once the tallied weight for `B` crosses `min_weight`, `S` calls `block_info.mark_locally_accepted(true)` (a transition `check_state` permits from `LocallyRejected`) [3](#0-2)  and then `broadcast_signed_block(...)`, pushing `B` — a block `S` had independently rejected — to its own node.
4. Compare with the guarded path: if `S` instead received pre-commits (not accept-signatures) for `B` crossing the same threshold, `handle_block_pre_commit`'s explicit `if !block_info.valid.unwrap_or(false) { ...; return; }` check would have stopped it. [1](#0-0)  The tally-by-acceptance path has no such stop.
