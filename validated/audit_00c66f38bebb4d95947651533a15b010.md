## Finding: JOB_OBJECT_LIMIT_BREAKAWAY_OK undermines job termination guarantee on Windows shell/custom executors

### Title
Windows Job Object created with `JOB_OBJECT_LIMIT_BREAKAWAY_OK` lets a job's child process escape termination via `CREATE_BREAKAWAY_FROM_JOB` - (File: helpers/process/job_windows.go)

### Summary
`CreateJobObject` in `helpers/process/job_windows.go` explicitly sets `windows.JOB_OBJECT_LIMIT_BREAKAWAY_OK` alongside `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which permits any process spawned within the job to opt out of the job entirely by passing `CREATE_BREAKAWAY_FROM_JOB` to `CreateProcess`. Because a pipeline author fully controls the script executed on shell/custom executors, they can spawn such a breakaway process, which will not be terminated when the job's Job Object is closed on cancellation/timeout.

### Finding Description
When `FF_USE_WINDOWS_JOB_OBJECT` is enabled, `osCmd.Start()` creates a Job Object via `CreateJobObject()` and assigns the job's process to it with `AssignPidToJobObject` [1](#0-0) . The job object is configured with:
```go
LimitFlags: windows.JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE |
    windows.JOB_OBJECT_LIMIT_BREAKAWAY_OK, // Allow subprocesses to explicitly avoid termination using CREATE_BREAKAWAY_FROM_JOB
``` [2](#0-1) 

`JOB_OBJECT_LIMIT_BREAKAWAY_OK` is a Win32 semantic that permits a child process to be created with the `CREATE_BREAKAWAY_FROM_JOB` flag, in which case Windows never associates that child (and its descendants) with the job at all. Termination relies on either:
- Graceful path: `taskTerminate` sending `CTRL_BREAK_EVENT`/`CTRL_C_EVENT` to the top-level PID [3](#0-2) , which does not propagate into unrelated/breakaway process trees, or
- Force path: `taskkill /F /T /PID` followed by `closeJobObject()` (which calls `CloseHandle` on the job, triggering `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) [4](#0-3) .

A process created with `CREATE_BREAKAWAY_FROM_JOB` is never a member of the job, so `CloseHandle`-triggered kill-on-close never reaches it — that is the entire purpose of the flag. `taskkill /T` walks parent/child ancestry rather than job membership, and is not a reliable substitute: if the breakaway process detaches (e.g., spawns its own children, redirects stdio, or the immediate parent exits first), the tree-kill can miss it. The comment in the code (`// Allow subprocesses to explicitly avoid termination using CREATE_BREAKAWAY_FROM_JOB`) shows this is a deliberate but unsafe accommodation — it directly contradicts the documented purpose of `FF_USE_WINDOWS_JOB_OBJECT` ("improve the termination of difficult-to-kill processes" [5](#0-4) ) and the general invariant that job cancellation must terminate the whole process tree it spawned.

Attacker path: a pipeline author on a shared Windows shell or custom executor host controls the job script content [6](#0-5) . Windows ships tooling (`csc.exe`/`Add-Type` in PowerShell, or a pre-built small executable fetched as part of the job) sufficient to call the Win32 `CreateProcess` API directly with `dwCreationFlags = CREATE_BREAKAWAY_FROM_JOB`. No existing Runner check (image allow-listing, path validation, masking) inspects or restricts what Win32 API flags a job's own script uses when spawning subprocesses.

### Impact Explanation
On a shared Windows shell/custom executor host, an unprivileged pipeline author can leave a persistent, unkillable-by-Runner process running after their job is cancelled/completes. That process can hold a named pipe, listen on a fixed TCP port, hold an OS mutex/lock, or lock a file that a subsequent job (potentially from a different project) needs, causing denial of service or interference for later jobs on the same runner — a persistent multi-tenant disruption as scoped.

### Likelihood Explanation
Preconditions: `FF_USE_WINDOWS_JOB_OBJECT=true` on a Windows shell or custom executor that is shared across jobs/projects (a common configuration recommended specifically to improve process termination). The attacker needs no special runner privileges — only the ability to submit a job script, which is the baseline capability of any pipeline author. Constructing the breakaway call is straightforward via PowerShell `Add-Type`/P-Invoke or a small pre-compiled helper binary, making this readily repeatable.

### Recommendation
Do not set `JOB_OBJECT_LIMIT_BREAKAWAY_OK` when creating the job object in `CreateJobObject` (`helpers/process/job_windows.go`). Without this flag, `CREATE_BREAKAWAY_FROM_JOB` requests from child processes fail, keeping all descendants bound to the job so `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` reliably terminates the entire tree on `closeJobObject()`.

### Proof of Concept
Windows integration test extending `helpers/process/killer_windows_integration_test.go`:
1. Start an `osCmd` with `UseWindowsJobObject: true` whose script (via `cmd /c` + PowerShell `Add-Type`/P-Invoke, or a bundled helper binary) calls `CreateProcess` with `CREATE_BREAKAWAY_FROM_JOB` to spawn a long-running child (e.g. a listener on a fixed TCP port or holder of a named mutex).
2. Wait for the child to report it has bound the shared resource (e.g., connect to the port).
3. Invoke `Terminate()`/`ForceKill()` (simulating job cancellation) and then `osCmd.Wait()` so `closeJobObject()` runs.
4. Assert: (a) the breakaway child process is still alive (query by PID), and (b) the shared resource (port/mutex) is still held — a second connection attempt from a simulated "next job" succeeds in reaching the stale process instead of a fresh one, proving cross-job resource contention.

func (c *osCmd) Start() error {
	setProcessGroup(c.internal, c.options.UseWindowsLegacyProcessStrategy)

	if c.options.UseWindowsJobObject {
		jobObj, err := CreateJobObject()
		if err != nil {
			return fmt.Errorf("starting OS command: %w", err)
		}
		c.jobObject = jobObj
	}

	err := c.internal.Start()
	if err != nil {
		return fmt.Errorf("starting OS command: %w", err)
	}

	if c.options.UseWindowsJobObject {
		// Any failures here are ignored, since we've already started the process running.
		if err := AssignPidToJobObject(c.internal.Process.Pid, c.jobObject); err != nil {
			c.options.Logger.Warn("assigning process to job object:", err)
		}
	}
	return nil

func (pk *windowsKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	if err := taskTerminate(pk.cmd.Process().Pid, pk.cmd.options.UseWindowsLegacyProcessStrategy); err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

	if pk.cmd.Process() == nil {
		return
	}

	err := taskKill(pk.cmd.Process().Pid)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)

}
