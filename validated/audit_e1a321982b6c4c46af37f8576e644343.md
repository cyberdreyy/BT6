### Title
External Initiator can bypass "EIs not allowed" check and trigger arbitrary job runs via `PipelineRunsController.Create` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates int-ID job runs with `isUser := auth.GetAuthenticatedUser(c)` and a comment stating "only users are allowed to run jobs using int IDs - EIs not allowed." However, `AuthenticateExternalInitiator` stores a synthetic `*clsessions.User{Role: UserRoleRun}` under the same `SessionUserKey` used by real user sessions/tokens, so `GetAuthenticatedUser` cannot distinguish an EI from a genuine user. Any holder of valid EI access-key/secret headers is therefore treated as `isUser==true` and can invoke `RunJobV2` for any numeric job ID, not just jobs bound to that initiator.

### Finding Description
The route's authentication middleware chain (per `core/web/router.go`) accepts `AuthenticateBySession`, `AuthenticateByToken`, or `AuthenticateExternalInitiator` for `/v2/jobs/:ID/runs`. In `core/web/auth/auth.go`: [1](#0-0) 

`AuthenticateExternalInitiator` explicitly comments that EI endpoints "inherently assume the role of 'run'" and sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` — the exact same context key (`SessionUserKey`) used by real session/token authentication in `AuthenticateBySession`/`AuthenticateByToken`.

`GetAuthenticatedUser` simply reads this key without any way to know whether it was populated by a genuine user auth method or by the EI's synthetic user: [2](#0-1) 

In `PipelineRunsController.Create`, the developer intent ("EIs not allowed") is enforced solely via this `isUser` boolean: [3](#0-2) 

Because `isUser` is true for both a real user and an EI, an attacker who only possesses valid EI credentials (obtained e.g. as a bridge/EI operator, not a node user) can send `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers to `POST /v2/jobs/:jobID/runs` with an arbitrary numeric `jobID`, and the handler will call `prc.App.RunJobV2(ctx, jobID, nil)` for that job — regardless of whether the job is associated with that external initiator's bridge at all. The "int IDs are user-only" restriction is therefore not actually enforced against EIs; it is enforced only against the (now-removed) UUID/webhook-run pathway.

### Impact Explanation
This allows an attacker holding only EI-scoped credentials (a much lower-privilege credential than a node user session/API token) to trigger execution of arbitrary jobs on the node by ID, without any binding to that EI's own bridge/job. This maps to Chainlink's "unauthorized job run" impact class — an attacker-controlled trigger of pipeline execution for jobs it does not own, which can cause unintended on-chain transactions, duplicate reports, resource exhaustion, or unauthorized fund-moving job execution depending on job type (e.g. direct-request write jobs), and violates the intended authorization scoping documented directly in the code comment.

### Likelihood Explanation
Exploitation requires only valid external-initiator credentials (access key + secret) for any external initiator registered on the node — a credential class explicitly lower-privileged and narrower-scoped than a full user session/API token. Job IDs are small sequential integers and are often discoverable/enumerable (e.g., via job list responses returned to lower-privileged consumers, or brute force over a small integer range). No admin/host access, no user session, and no knowledge of a target job's owning bridge are needed. This is deterministic and repeatable via a single crafted HTTP request.

### Recommendation
Do not overload `SessionUserKey`/`GetAuthenticatedUser` for external initiators. Use a distinct context flag (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` is *not* set, or introduce a separate `SessionAuthMethodKey`) so `PipelineRunsController.Create` can reliably distinguish a true user-authenticated request from an EI-authenticated one, and reject EI-authenticated requests for int-ID job runs as the existing comment intends. Additionally, if EI-triggered runs are to be supported at all, scope them explicitly to the job(s) actually associated with that external initiator rather than allowing any job ID.

### Proof of Concept
Go handler-level integration test plan (in `core/web/pipeline_runs_controller_test.go` style):
1. Register a job (e.g. a cron or OCR job) NOT associated with any external initiator/bridge, capturing its int `jobID`.
2. Register a separate `ExternalInitiator` (bridge) with its own access key/secret, unrelated to the job created in step 1.
3. Send `POST /v2/jobs/{jobID}/runs` using only `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (no session cookie, no `X-API-KEY`/`X-API-SECRET`).
4. Assert current (vulnerable) behavior: response is `200/201` and `App.RunJobV2` was invoked with `jobID`, proving the EI ran a job it has no association with.
5. Expected secure behavior: response should be `401/403`/`422` ("EIs not allowed to run jobs by int ID"), and `RunJobV2` should never be called for EI-only authenticated requests, or only ever called for jobs explicitly bound to that initiator.
