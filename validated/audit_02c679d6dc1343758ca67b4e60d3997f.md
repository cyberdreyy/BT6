### Title
Admin `lending_pool_configure_bank` can silently change `asset_tag` on a live integration bank, orphaning user funds routed through Kamino/Drift/JupLend/Kamino obligations - (File: `programs/marginfi/src/state/bank.rs`, `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
The C4 report describes a bug class where an admin-controlled binding between a lending controller (`Comptroller`) and a satellite vault (`UniV3LpVault`) can be independently changed after positions already exist, breaking the mutual reliance the two contracts have on each other for pricing/withdrawal and permanently stranding NFTs. Marginfi-v2 has a structurally identical binding: each Bank stores `config.asset_tag` plus `integration_acc_1`/`integration_acc_2` (Kamino reserve/obligation, Drift market, JupLend lending state) that route deposit/withdraw/liquidate logic to the correct integration-specific instruction and account set. `lending_pool_configure_bank` lets the group `admin` freely rewrite `asset_tag` on an already-live bank via `Bank::configure`, with no check that the bank has no active integration position/deposits, and no re-validation against `integration_acc_1`/`integration_acc_2`.

### Finding Description
`bank.configure()` unconditionally applies an admin-supplied `asset_tag` change: [1](#0-0) 

This is invoked from the always-available `lending_pool_configure_bank` admin instruction (guarded only by `has_one = admin`, not by `FREEZE_SETTINGS` for asset_tag unless that flag is set): [2](#0-1) 

Every integration-specific instruction (deposit/withdraw/liquidate) gates itself on `asset_tag` matching its expected value, e.g. Kamino withdraw requires `is_kamino_asset_tag(bank.load()?.config.asset_tag)`: [3](#0-2) 

and JupLend withdraw requires `is_juplend_asset_tag(bank.load()?.config.asset_tag)`: [4](#0-3) 

Meanwhile the standard, non-integration path (`lending_account_withdraw`) transfers directly out of `bank.liquidity_vault`: [5](#0-4) 

But per the protocol's own documentation, integration (Kamino) banks never hold custody of user funds in `liquidity_vault` — real funds live in the external venue's obligation/reserve, and `liquidity_vault` is only a pass-through: [6](#0-5) 

If the group admin runs `lending_pool_configure_bank` to flip `asset_tag` on a Kamino/Drift/JupLend bank that already has active user deposits (e.g., from `ASSET_TAG_KAMINO` to `ASSET_TAG_DEFAULT`), the integration-specific withdraw/deposit/liquidate instructions (`kamino_withdraw`, `drift_withdraw`, `juplend_withdraw`, etc.) will immediately fail their `is_X_asset_tag` constraint, cutting off the only path that actually reaches the funds held in the external venue's obligation/reserve. The "standard" `lending_account_withdraw`/`lending_account_deposit` path now accepts the bank (since it checks for `ASSET_TAG_DEFAULT`), but it only moves tokens through the essentially-empty `liquidity_vault`, so it cannot deliver the user's real balance and will either fail (insufficient vault balance) or corrupt bank share accounting. The bank test suite explicitly exercises changing `asset_tag` post-hoc, confirming this is a reachable, unguarded admin action rather than a theoretical construct: [7](#0-6) 

This mirrors the C4 root cause precisely: two components (`Bank.config.asset_tag`/`integration_acc_*` and the integration-specific instruction's account constraints) must stay in lockstep for withdrawal/valuation to work, yet the admin can independently mutate one side of that binding at any time post-creation, with no mechanism to migrate or evict existing positions first.

### Impact Explanation
Any user who has deposited into a Kamino/Drift/Solend/JupLend-wrapped bank can have their withdrawal path permanently severed by a single admin `lending_pool_configure_bank` call that changes `asset_tag`. This is a durable freeze of user funds with direct financial effect: liquidations, withdrawals, and deposits into that Balance become unusable via any documented instruction path, and depending on order of operations it can also desynchronize `bank.total_asset_shares`/`asset_share_value` from the real underlying obligation balance, corrupting accounting for all other depositors of the same bank. Whether this is intentional admin misuse or accidental misconfiguration, the program provides no safety rail (no check that `asset_tag` changes are disallowed while `total_asset_shares > 0` or while `integration_acc_1`/`integration_acc_2` are set to a live external position).

### Likelihood Explanation
This requires the group `admin` role (a privileged actor) to execute the change, so it is not an unprivileged-attacker-triggerable bug on its own. However, unlike a validator/peer/admin-only issue that should be rejected, this is squarely an authorization/state-invariant gap analogous to the referenced finding: the instruction is reachable in normal admin operation (e.g. via a benign re-configuration, a scripting mistake, or a compromised/malicious multisig signer), has no guard, and the test suite even demonstrates the exact mutation happening in practice. The "attacker" here can be a subset of admin keys in a multisig, or simple operational error, both of which the protocol should defend against per its own stated goal of `FREEZE_SETTINGS` providing "credible commitment that the bank's risk parameters ... will not change" — but `asset_tag` mutation is not covered by that same protection outside of frozen banks, and even before freezing, there is no protection while a bank has live integration deposits.

### Recommendation
In `Bank::configure` (`programs/marginfi/src/state/bank.rs`), reject `asset_tag` changes when the bank already has non-zero `total_asset_shares`/`total_liability_shares`, or when `integration_acc_1`/`integration_acc_2` are already populated with a live external position (obligation/market). At minimum, require that `asset_tag` transitions only occur between compatible values (e.g., never away from an integration tag once an obligation exists), and add a dedicated, explicitly-audited migration instruction if bank re-purposing is truly required, mirroring the C4 recommendation to disallow overwriting a binding that other instructions depend on for correctness once it is in active use.

### Proof of Concept
1. Admin creates a Kamino bank via `lending_pool_add_bank_kamino` and initializes its obligation (`kamino_init_obligation`), setting `asset_tag = ASSET_TAG_KAMINO` and populating `integration_acc_1`/`integration_acc_2`.
2. User deposits into the bank via `kamino_deposit`, creating a `Balance` with `bank_asset_tag = ASSET_TAG_KAMINO`; real funds now sit in the Kamino reserve/obligation, not in `bank.liquidity_vault`.
3. Admin calls `lending_pool_configure_bank` with `bank_config_opt.asset_tag = Some(ASSET_TAG_DEFAULT)` (as demonstrated feasible in `tests/specs/drift/d06_driftBankInit.spec.ts:290-309` for Drift banks) — this succeeds because `Bank::configure` applies `asset_tag` unconditionally.
4. User attempts `kamino_withdraw`: fails `is_kamino_asset_tag(bank.config.asset_tag)` constraint (`WrongAssetTagForKaminoInstructions`).
5. User attempts `lending_account_withdraw` instead (now "permitted" since `asset_tag == ASSET_TAG_DEFAULT`): the instruction pulls from `bank.liquidity_vault`, which never held the user's real balance (per Kamino integration design), so the withdrawal either fails for insufficient vault liquidity or, if any residual liquidity exists, distributes it incorrectly relative to actual claims on the external obligation — the user's real collateral remains locked in the untouched Kamino obligation with no instruction able to reach it under the new `asset_tag`.
