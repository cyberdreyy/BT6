### Title
Funded instant-withdraw receipts are never removed from per-epoch claim accounting, corrupting default recovery basis and freezing recovery funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug pattern — a latency-QoS request node freed on an error path without being removed from the plist, corrupting later list operations — maps directly onto `IdleCreditVault.claimInstantWithdrawRequest`. When a funded instant withdrawal is claimed, the function clears the aggregate `instantWithdrawsRequests[_user]` and burns the receipt, but never removes the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`. If the borrower defaults in that same epoch, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` treat already-paid receipts as outstanding claims, inflating the recovery reserve with phantom funds. The resulting `defaultRecoveryReserve` exceeds the strategy's actual balance, so the last default-recovery claimants' transfers revert and their recovery is permanently frozen.

### Finding Description
`requestInstantWithdraw` records three pieces of state for the same receipt: the aggregate `instantWithdrawsRequests[_user]`, the per-user/per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch total `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

On the normal claim path, `claimInstantWithdrawRequest` clears only the aggregate counter and burns the receipt tokens — the two per-epoch entries are left behind, exactly like the QoS request left on the list after its memory was freed [2](#0-1) . Compare with the default-epoch cleanup path, which does clear all three counters consistently [3](#0-2) .

Instant withdrawals are requested and claimed *within* a running epoch, so the stale entries sit under the current `epochNumber`. If the borrower defaults during that epoch and the CDO calls `finalizeDefaultRecovery`, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — including already-claimed, already-paid receipts — into `pendingBasis` whenever `pendingInstantWithdraws != 0` [4](#0-3) . Worse, `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` and treats the difference as underlying already held by the strategy [5](#0-4) . That "held" amount includes the tokens that were already transferred out to claimants, so `defaultRecoveryReserve` is set to a value larger than the strategy's real balance [6](#0-5) .

The stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` also makes a repeat claim attempt reach `_claimDefaultedInstantWithdrawRequest`, where `instantWithdrawsRequests[_user] -= claimBasis` underflows and reverts — blocking nothing new for the attacker, but confirming the accounting believes the paid receipt still exists.

### Impact Explanation
Two concrete harms, both quantified by the claimed instant amount `X`:

1. **Dilution of recovery**: `recoveryPrice = reserveAmount * 1e18 / totalBasis` uses a `totalBasis` inflated by `X` and a `reserveAmount` inflated by phantom `X`. Honest claimants (active AA/BB holders and other pending receipt holders) recover less than they should.
2. **Permanent freezing of recovery funds**: `defaultRecoveryReserve` is credited `X` more than the strategy holds. `_transferDefaultRecovery` decrements the reserve and transfers real tokens [7](#0-6) , so once the real balance is exhausted, remaining claims totaling up to `X` revert on `safeTransfer` and can never be paid — including the reserve-isolation guard in `_transferFundedClaim`, which now also blocks funded claims because `balance < reserve` [8](#0-7) .

### Likelihood Explanation
Requires only unprivileged actions: a KYC-passing lender requests an instant withdrawal and claims it after the instant delay (a normal, funded claim path during a running epoch), while any instant request remains unfunded (`pendingInstantWithdraws != 0`, which the attacker can ensure with a small second request of their own). The trigger is a borrower default in the same epoch — an external event, but the corrupted accounting is created entirely by ordinary user transactions. No privileged misbehavior is needed; the honest manager/guardian simply executes the standard default-finalization flow.

### Recommendation
In `claimInstantWithdrawRequest`, mirror the cleanup done in `_claimDefaultedInstantWithdrawRequest`: before zeroing the aggregate, clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount, so a paid receipt can never be double-counted in a later same-epoch default basis. Note `pendingInstantWithdraws` is intentionally left untouched there since it tracks the unfunded remainder reduced in `collectInstantWithdrawFunds`.

### Proof of Concept
Foundry fork sketch (build on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testStaleInstantClaimCorruptsDefaultRecovery() external {
    // Running epoch, instant withdraws enabled.
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    _depositWithUser(victim,   100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    uint256 epoch = strategy.epochNumber();

    // Attacker instant-withdraws X and claims it once funded (normal path).
    uint256 X = 50_000 * ONE_SCALE;
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(X, address(AAtranche)); // conceptually; via CDO API
    // manager fulfills instant request -> collectInstantWithdrawFunds
    // attacker claims after instantDelay
    vm.warp(block.timestamp + cdoEpoch.instantDelay() + 1);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    // Attacker leaves a tiny unfunded instant request so pendingInstantWithdraws != 0.
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(1, address(AAtranche));

    // Stale per-epoch entries remain for the already-claimed X:
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epoch), X + 1);
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), X + 1);
    // while instantWithdrawsRequests[attacker] == 1 only.

    // Borrower defaults; honest guardian runs default flow and manager finalizes.
    _handleBorrowerDefaultPath();
    // finalizeDefaultRecovery pulls recoveredAmount R.
    uint256 balBefore = underlying.balanceOf(address(strategy));
    cdoEpoch.finalizeDefaultRecovery(R, recoverySource);

    // Reserve is booked X too high vs. actual holdings (attacker's X already paid out).
    assertGt(strategy.defaultRecoveryReserve(), underlying.balanceOf(address(strategy)));

    // Honest claimants drain the real balance; the last ~X of claims revert,
    // permanently freezing that portion of the recovery.
    vm.expectRevert(); // safeTransfer fails on insufficient balance
    lastClaimant.callClaimDefaulted();
}
```

The assertion `instantWithdrawsRequestsByEpoch(attacker, epoch) > instantWithdrawsRequests(attacker)` after a fully-paid claim is the smoking gun mirroring the dangling QoS list node.
