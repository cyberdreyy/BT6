### Title
Missing exact-length enforcement in `validateHexInput`/`normalizeHex` allows negative `strings.Repeat` count and panic - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Finding Description
`validateWorkflowOwner` (line 287) calls `validateHexInput(workflowOwner, workflowOwnerLength)` (line 260), which only enforces that `len(input) > expectedLength` is rejected — it does not enforce a minimum length nor does it require the `"0x"` prefix to actually be present. It merely lower-cases-checks and hex-decodes after stripping an optional `"0x"` prefix with `strings.TrimPrefix`. [1](#0-0) 

Because `strings.TrimPrefix` is a no-op if the prefix is absent, an attacker can submit a `WorkflowOwner` value with **no `0x` prefix** that is up to `workflowOwnerLength` (42) raw characters long — i.e., up to 42 hex characters (21 bytes) instead of the expected 40 hex characters (20 bytes) that would result from a genuine `0x`-prefixed 20-byte address. This value passes `validateHexInput` as long as it is valid, lowercase, even-length hex.

Later, `resolveWorkflowID` calls `normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)`: [2](#0-1) [3](#0-2) 

`normalizeHex` computes `expectedHexLength := length - 2` (i.e., 40) and then `strings.Repeat("0", expectedHexLength-len(hexStr))`. If the un-prefixed attacker-supplied string is 41 or 42 characters long (still ≤ `workflowOwnerLength`=42, so it passes validation), `len(hexStr)` after the no-op `TrimPrefix` is 41 or 42, making `expectedHexLength-len(hexStr)` negative (-1 or -2). `strings.Repeat` panics on a negative count ("strings: negative Repeat count"), causing the goroutine handling this unauthenticated request to panic.

The request path is reachable pre-authentication: `HandleJSONRPCUserMessage` → `HandleUserTriggerRequest` → `validatedTriggerRequest` (runs `validateWorkflowOwner`) → `resolveWorkflowID` (runs `normalizeHex`), all before `authorizeRequest`'s JWT signer check. [4](#0-3) [5](#0-4) 

I was unable to fully verify, within the tool budget available, whether the goroutine that ultimately invokes `HandleJSONRPCUserMessage` (via the connector/multihandler dispatch chain) is wrapped in a `recover()` that would contain the panic to a single request versus crashing the gateway process. No `recover()` was found within `core/services/gateway/handlers/capabilities/v2` or `core/services/gateway/connector`, so this needs confirmation in the wider dispatch/connector code before confirming full process-crash impact versus a per-goroutine panic.

Regarding the second half of the question (bypassing ownership via owner/name/tag lookup without further proof): this is **not** exploitable as described — `resolveWorkflowID`'s owner/name/tag branch only returns a `workflowID` string; it does not grant any authorization. The subsequent `authorizeRequest` (line 361) independently validates the JWT signer against the resolved `workflowID`'s registered owner via `h.workflowMetadataHandler.Authorize`, so an attacker supplying a victim's owner/name/tag combination can only learn that a workflow ID exists (a workflow-ID lookup, not fund movement or execution), and cannot execute the victim's workflow without a valid signature from the true owner.

### Impact Explanation
Denial of Service: an unauthenticated gateway client can trigger a Go runtime panic via `strings.Repeat` with a negative count by supplying a malformed (missing `0x` prefix, appropriately sized) `workflowOwner` field. Depending on whether the request-handling goroutine has panic recovery upstream (unconfirmed), impact ranges from a single failed request (recovered) to gateway node crash (unrecovered), which would map to a low/medium severity DoS bounty class. There is no confirmed authentication bypass or unauthorized workflow execution — `authorizeRequest`'s JWT signer check remains a valid and necessary gate that is not bypassed by this bug.

### Likelihood Explanation
Trivially reachable: no authentication or prior workflow ownership is required to reach `resolveWorkflowID`; only the JSON-RPC `workflows.execute` trigger method needs to be invoked with a crafted `workflowOwner` string lacking the `0x` prefix and of length 41–42 characters. This is fully attacker-controlled and repeatable on every request.

### Recommendation
In `validateHexInput`, require the `"0x"` prefix to be present (reject if missing) and enforce an exact length match (`len(hexStr) == expectedHexLength-2`) rather than only an upper bound. Additionally, harden `normalizeHex` defensively: if `expectedHexLength-len(hexStr) < 0`, return an error/reject instead of calling `strings.Repeat` with a negative count.

func TestNormalizeHex_NegativeRepeatPanic(t *testing.T) {
    cases := []struct name, input string; length int }{
        {"missing 0x prefix, 41 chars", strings.Repeat("a", 41), workflowOwnerLength}, // 41 <= 42, but no 0x prefix trimmed

    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            require.NoError(t, validateHexInput(tc.input, tc.length)) // currently passes validation
            require.NotPanics(t, func() { normalizeHex(tc.input, tc.length) }) // currently panics: "strings: negative Repeat count"
        })
    }
}

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
