## Analysis: Beneficiary Bypass on Operator-Switch Pending Commission (`staking_contract.move`)

Investigating the stake/lockup analog of the storage-slot mismatch bug, I traced the operator-commission and beneficiary-redirection accounting in `staking_contract.move`. The `distribution_pool` (a `pool_u64` shares ledger keyed by recipient address) is reused across operator changes without correcting for the redirect key used at payout time, producing a genuine "wrong recipient" bug analogous to the report's "wrong slot" root cause: a stale key (`old_operator`) is looked up against a mismatched comparison key (`new_operator`), silently disabling the beneficiary indirection.

### Title
Pending operator commission bypasses `beneficiary_for_operator` redirection after `switch_operator` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` forces a fresh `request_commission_internal` call for the **old** operator right before re-keying the `StakingContract` (including its `distribution_pool`) under the **new** operator. This creates a pending distribution share keyed by `old_operator`'s address inside a `StakingContract` struct that is now stored under the `new_operator` key. When that pending share is later paid out via `distribute_internal`, the code compares the shareholder address against the *current* `operator` parameter (`new_operator`) rather than the address the share actually belongs to (`old_operator`), so the beneficiary lookup `beneficiary_for_operator(operator)` is never applied to `old_operator`'s commission.

### Finding Description [1](#0-0) 

`switch_operator` removes the `StakingContract` from the map keyed by `old_operator`, settles any already-inactive stake, then calls `request_commission_internal(old_operator, &mut staking_contract)` which unlocks the newly accrued commission and records it via `add_distribution(operator=old_operator, ..., recipient=old_operator, commission_amount)`: [2](#0-1) 

This commission is only *unlocked* (moved to `pending_inactive`), not yet withdrawable, so it remains a pending share in `distribution_pool` keyed by `old_operator`'s address. The `StakingContract` (carrying this pool) is then re-added to the map under `new_operator`: [3](#0-2) 

Later, once the lockup expires, any call to `distribute()`/`unlock_stake()`/`request_commission()` for `(staker, new_operator)` invokes `distribute_internal(staker, new_operator, staking_contract)`, which iterates all shareholders in the pool — including the stale `old_operator` entry — and only redirects to the beneficiary if the shareholder equals the function's `operator` argument: [4](#0-3) 

Since `recipient` (`old_operator`) is compared against `operator` (`new_operator`), the equality check fails, `beneficiary_for_operator(old_operator)` is never consulted, and the pending commission is deposited straight into `old_operator`'s own account instead of the address `old_operator` had explicitly configured via `set_beneficiary_for_operator`: [5](#0-4) 

### Impact Explanation
The beneficiary mechanism exists specifically so operators can route commission payouts to a separate, presumably more secure, custody/beneficiary address rather than the operator's own (often hot/validator) key. This bug silently drops that protection for exactly one in-flight distribution per operator switch, misdirecting the payout to the raw operator address. This is a real "beneficiary payout ... corruption that credits the wrong account" per the stake/lockup impact criteria, though it does not constitute outright theft by an unrelated attacker — the funds still land in an address the operator controls, just not the one they intended, and only for commission accrued in the narrow window between the last settlement and the `switch_operator` call.

### Likelihood Explanation
Low-to-moderate. It requires: (1) an operator with a configured beneficiary, (2) the staker invoking `switch_operator`/`switch_operator_with_same_commission` while unpaid commission has accrued since the last `distribute`/`request_commission` call, and (3) that commission not yet being fully withdrawn before the switch. This is a normal, unprivileged operational sequence (staker-driven), not requiring any special access beyond controlling one's own staking contract.

### Recommendation
In `switch_operator`, before reusing the `distribution_pool`, either (a) fully settle/withdraw the `old_operator`'s pending commission distribution (not just unlock it) so no stale shares carry over, or (b) make `distribute_internal`'s beneficiary check independent of the currently-active `operator` parameter — e.g., resolve `beneficiary_for_operator(recipient)` whenever `recipient` itself has a `BeneficiaryForOperator` entry, rather than only when `recipient == operator`.

### Proof of Concept
1. Staker creates a `StakingContract` with `operator = A`, `commission_percentage = 10`.
2. Operator `A` calls `set_beneficiary_for_operator(A, beneficiary_addr)`.
3. Stake pool accrues rewards over an epoch (commission becomes owed to `A`).
4. Staker calls `switch_operator(staker, A, B, new_commission)`. Internally this calls `request_commission_internal(A, ...)`, unlocking `A`'s commission and recording it in `distribution_pool` keyed by `A`, then re-keys the whole `StakingContract` (with that pool) under `B`.
5. After the stake pool's lockup expires, anyone calls `distribute(staker, B)` (or `A`/`B` calls `request_commission`, or staker calls `unlock_stake`), triggering `distribute_internal(staker, B, staking_contract)`.
6. Inside the payout loop, shareholder `A`'s pending commission is compared against `operator = B`; since `A != B`, `beneficiary_for_operator(A)` is never queried, and the funds are deposited directly to `A` instead of `beneficiary_addr`.

        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
