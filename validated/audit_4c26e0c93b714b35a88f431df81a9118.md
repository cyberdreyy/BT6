### Title
Unprotected ERC4626 vault deposit in `ProgrammableBorrower.onStartEpoch` lets an unprivileged attacker permanently block `startEpoch`, freezing all pending withdrawal claims - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary

The external dTRINITY finding is a withdraw DoS caused by an uncaught revert when surplus assets are re-deposited into an external ERC4626 vault that can refuse deposits (paused/frozen state, supply cap, or dust amounts minting 0 shares). The direct analog in idle-tranches is `ProgrammableBorrower._depositToVault`, which calls `vault.deposit(...)` with no `try/catch`. It is invoked unconditionally inside `onStartEpoch` (`contracts/strategies/idle/ProgrammableBorrower.sol:216`) and on every `_repay` during an active epoch (`:499`, `:527`). `IdleCDOEpochVariant.startEpoch` calls the borrower hook as part of the epoch-start path (`contracts/IdleCDOEpochVariant.sol:288,295`), so any revert in the vault deposit propagates and reverts the entire `startEpoch`.

### Finding Description

During the buffer phase, lender deposits, repaid borrower interest and any leftover idle underlying sit as an ERC20 balance on the `ProgrammableBorrower` contract. When the manager calls `startEpoch`, `onStartEpoch` executes:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:216
_depositToVault(underlyingToken.balanceOf(address(this)), 0);
```

and `_depositToVault` (`:378-385`) does a bare `vault.deposit(_assetAmount, address(this))`. There is no fallback: if the deposit reverts, `onStartEpoch` reverts, `startEpoch` reverts, and `isEpochRunning` stays false. While the pool is stuck in the buffer, `claimWithdrawRequest` cannot be serviced because withdrawals are only funded after a successful `stopEpoch` of a *running* epoch, and new `requestWithdraw` claims remain queued indefinitely.

An unprivileged attacker can force the deposit to revert by manipulating public vault state, exactly like the Aave-vault masks in the original report:

- **Supply cap / deposit limit:** any EOA can deposit into the underlying ERC4626 vault (e.g. a Morpho vault, as used in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`) up to its `maxDeposit` cap. Once `maxDeposit(address(programmableBorrower)) < idleBalance`, `vault.deposit` reverts.
- **Vault pause:** many ERC4626 vaults pause deposits while still allowing withdrawals; a paused vault makes every `startEpoch` revert for the duration.
- **Dust rounding:** if the idle balance is tiny (e.g. only donated dust or a small repayment), `deposit` can mint 0 shares, which several vault implementations reject — mirroring the "surplus too small → 0 shares" revert in the report.

The same path is reachable via `_repay`: a borrower repayment while `epochAccountingActive` is immediately re-deposited (`:524-527`), so a capped vault also DoSes `repay`/`executeRepay`, keeping `borrowerPrincipal`/`borrowerInterestDebt` elevated — which in turn makes `onStopEpoch` return false on close-pool (`:235`), pushing the pool toward the default path.

### Impact Explanation

Temporary freezing of all lender funds with a quantifiable loss. While `startEpoch` is blocked, tranche holders cannot exit: pending withdraw requests are only paid from funds collected at `stopEpoch`/`collectWithdrawFunds`, which require a running epoch. The attacker spends only the cost of filling the vault's remaining deposit capacity (capital cost, not burned), and can repeat the griefing each time the cap frees up. Withdrawers' funds remain locked for the duration; if the vault's cap is permanently reached or the vault is permanently paused, recovery requires the honest owner to call `setVault` (`:158`) — possible only because `vault.balanceOf(this) == 0` in the stuck state — meaning depositors rely on governance intervention to unlock funds. The repay-path DoS additionally prevents the borrower from clearing debt, risking an unwarranted default and the associated loss socialization on BB/AA tranches.

### Likelihood Explanation

Requires only an unprivileged transaction against a public ERC4626 vault (deposit up to the cap) — no privileged role, no oracle manipulation. It depends on the configured vault having a reachable deposit cap or pausable deposits, which is common for Morpho-style and Aave-style vaults, and the attack is only meaningful while the pool is in the buffer phase with a non-zero idle balance. The existing guards do not help: `setVault` cannot be preempted, `_depositToVault` has no try/catch (unlike `sendFundsToBorrower` which is wrapped in try/catch at `IdleCDOEpochVariant.sol:295`), and `onStopEpoch` only tolerates *withdraw* failures, not deposit failures.

### Recommendation

- Wrap the deposit in `_depositToVault` in a `try/catch`: on failure, keep the underlying on the contract (it is already counted by `totalUnderlying()`/`availableToBorrow()` and `onStopEpoch` only withdraws the shortfall it actually needs).
- Alternatively, cap the deposit to `vault.maxDeposit(address(this))` and hold the remainder as idle balance.
- Apply the same treatment to the `_repay` redeposit path so a capped vault cannot block debt repayment.

### Proof of Concept

Conceptual Foundry fork PoC (mainnet, USDC + a capped Morpho vault, mirroring `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testPocStartEpochDosByVaultDepositCap() external {
    _setUpProgrammableBorrowerCreditVault(GAUNTLET_FORK_BLOCK, GAUNTLET_USDC_PRIME);
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    // lender deposits during buffer; funds sit idle on ProgrammableBorrower
    idleCDO.depositAA(amount);

    // --- attacker (any EOA) fills the vault's remaining deposit capacity ---
    IERC4626 v = IERC4626(GAUNTLET_USDC_PRIME);
    address attacker = makeAddr("attacker");
    uint256 cap = v.maxDeposit(address(programmableBorrower)); // remaining capacity
    deal(USDC, attacker, cap);
    vm.startPrank(attacker);
    IERC20(USDC).approve(address(v), cap);
    v.deposit(cap, attacker); // now maxDeposit(programmableBorrower) < idle balance
    vm.stopPrank();

    // manager tries to start the epoch -> _depositToVault reverts -> startEpoch reverts
    vm.prank(manager);
    vm.expectRevert(); // ERC4626 deposit exceeds max / vault-specific error
    cdoEpoch.startEpoch();

    // epoch never runs: pending withdraw requests stay frozen, no stopEpoch possible
    assertFalse(cdoEpoch.isEpochRunning());
}
```

A dust variant uses a vault that reverts on zero-share mints: donate a few wei of underlying directly to `ProgrammableBorrower`, ensure all other balances are already in the vault, then `startEpoch` reverts on the dust `deposit`. The repay variant calls `borrower.repay(...)` during an active epoch after the attacker fills the cap, showing `repay` reverting at `:527`.

Uncertainty: I was unable to re-verify the exact `startEpoch` → `_startEpochProgrammableBorrower` call chain line numbers beyond the snippet at `IdleCDOEpochVariant.sol:288-300`, but the hook is invoked synchronously there with no surrounding `try/catch` on the `onStartEpoch` call itself (only `sendFundsToBorrower` is wrapped).
