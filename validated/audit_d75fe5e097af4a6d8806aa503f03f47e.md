### Title
Post-default instant withdraw requests are claimed against the finalized default-epoch bucket, corrupting `pendingInstantWithdraws` and paying from `defaultRecoveryReserve` at `defaultRecoveryPrice` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The upstream bug is a use-after-free: `r1_bio->bios[]` is temporarily set to the original bio, then the error path `free_r1bio()` frees every recorded entry, freeing a bio that was never allocated into that array. The structural analog in `IdleCreditVault` is a request recorded into a bucket that belongs to a *finalized* state: after `finalizeDefaultRecovery`, `epochNumber` never changes, so a new `requestInstantWithdraw` writes into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — a bucket whose basis was already crystallized and whose recovery price/reserve were fixed. On claim, `_claimDefaultedInstantWithdrawRequest` then "frees" that entry under the wrong accounting path: it pays the new full-value receipt out of `defaultRecoveryReserve` at `defaultRecoveryPrice` and clamps `pendingInstantWithdraws` to 0, even though the new request was never part of the finalized basis and was never borrower/CDO-funded.

### Finding Description
- `requestInstantWithdraw` does not check `defaultRecoveryFinalized`. It increments `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws`, and mints the user a receipt at full value [1](#0-0) .
- `epochNumber` is only bumped inside `deposit` when the epoch transitions; after a default there is no new epoch, so `epochNumber == defaultRecoveryEpoch` forever [2](#0-1) .
- Because `defaultInstantWithdrawsFinalized` was set when `pendingInstantWithdraws != 0` at finalization, `claimInstantWithdrawRequest` routes through `_claimDefaultedInstantWithdrawRequest` [3](#0-2) .
- There, `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` now includes the post-finalization request. The payout `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` is drawn via `_transferDefaultRecovery` from the reserve that was sized only for the finalized basis (`reserveAmount` covering `activeBasis + pendingBasis` at finalization time) [4](#0-3) [5](#0-4) .
- Additionally `pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis` zeroes/clamps a global counter that honest post-default instant requests just incremented, so a subsequent `collectInstantWithdrawFunds(_amount)` underflows (`pendingInstantWithdraws -= _amount`) and permanently reverts [6](#0-5) [7](#0-6) .

Contrast with the normal path: post-default `requestWithdraw` receipts are tracked separately in `postDefaultRequests` and paid 1:1 [8](#0-7) . The instant path has no equivalent separation, so the "already-freed" (finalized) epoch bucket absorbs new live claims.

### Impact Explanation
Two quantified loss modes, both reachable by an unprivileged tranche holder:

1. **Over-recovery (`defaultRecoveryPrice > RECOVERY_FULL`, explicitly supported, see `testFinalizeDefaultDistributesOverRecoveryProRata`)**: an attacker requests an instant withdraw after finalization and is paid `amount * price / 1e18 > amount` out of `defaultRecoveryReserve`, while the correct post-default path pays 1:1. Each unit of receipt drains `(price - 1)` units of surplus recovery that belongs to the finalized claimants — direct theft from the reserve.
2. **Normal/sub-par recovery**: any post-default instant request inflates `pendingInstantWithdraws`, then the first claim clamps it to 0. A later honest instant requester's `collectInstantWithdrawFunds` underflows and reverts forever — permanent freeze of the instant-withdraw funding path — and the requester's minted receipt can never be funded since the CDO can no longer transfer the underlying. Meanwhile the wrongly-paid claimant consumed reserve earmarked for finalized-basis claims, i.e. reserve insolvency for honest claimants equal to the misclassified payout.

### Likelihood Explanation
Requires only: (a) a default with `pendingInstantWithdraws != 0` at finalization (a single partially-prefunded instant receipt, a state the codebase's own tests construct), and (b) any user calling `requestInstantWithdraw` afterwards — which is unguarded and the documented way to exit in instant mode. No privileged cooperation needed; owner/manager calls are honest and sequencing-safe. The guard `if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized)` actually *forces* the buggy path rather than preventing it.

### Recommendation
- In `requestInstantWithdraw`, either `revert NotAllowed()` when `defaultRecoveryFinalized`, or record post-default instant receipts in a separate bucket (e.g. `postDefaultInstantRequests[_user]`) paid 1:1 like `postDefaultRequests`.
- In `_claimDefaultedInstantWithdrawRequest`, cap the cleared basis to what existed at finalization (snapshot per-user or per-epoch basis at `finalizeDefaultRecovery`) instead of reading the mutable per-epoch mapping that absorbs later requests.
- Do not clamp global `pendingInstantWithdraws` based on a single user's claim; decrement only the finalized basis share.

### Proof of Concept
Foundry fork PoC sketch (modeled on `testFinalizeDefaultHaircutsPendingInstantRedeems` in `test/foundry/IdleCreditVault.t.sol:4435`):

```solidity
// Setup: deposit userA + userB into AA, epoch 0 runs and stops with partial funding.
_depositWithUser(userA, 10_000e18, true);
_depositWithUser(userB, 10_000e18, true);
idleCDO.depositAA(20_000e18);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, apr, _expectedFundsEndEpoch());

// userA makes an instant request -> partially prefunded, pendingInstantWithdraws > 0
vm.prank(userA);
cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant mode
_startEpochAndCheckPrices(1);
// trigger default via getInstantWithdrawFunds failure / stopEpoch(0,0)
_checkDefault();

// finalize with over-recovery: recovered = 110% of totalBasis
uint256 totalBasis = cdoEpoch.getContractValue()
    + cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees()
    + creditVault.defaultPendingClaimBasis();
uint256 recovered = totalBasis * 11 / 10;
deal(underlying, manager, recovered);
vm.startPrank(manager);
IERC20(underlying).approve(address(creditVault), recovered);
cdoEpoch.finalizeDefault(recovered, manager);
vm.stopPrank();
assertGt(creditVault.defaultRecoveryPrice(), 1e18);

// Attacker (userB): post-default instant withdraw into the finalized epoch bucket
vm.prank(userB);
cdoEpoch.requestInstantWithdraw(amountB); // via CDO; burns CDO tokens, mints receipt

// Claim is routed through _claimDefaultedInstantWithdrawRequest
uint256 balPre = IERC20(underlying).balanceOf(userB);
uint256 reservePre = creditVault.defaultRecoveryReserve();
vm.prank(userB);
cdoEpoch.claimInstantWithdrawRequest();
uint256 paid = IERC20(underlying).balanceOf(userB) - balPre;

// Attacker is paid amount * price (> amount) from the finalized reserve,
// which was sized only for userA's basis -> reserve drained / insolvent for userA.
assertGt(paid, amountB);
assertLt(creditVault.defaultRecoveryReserve(), reservePre - amountB);

// Honest finalized claimant now underflows / receives less than basis * price.
```

The analogous sub-par variant sets `recovered = totalBasis * 7 / 10` and asserts that a second honest `requestInstantWithdraw` + `collectInstantWithdrawFunds` reverts on `pendingInstantWithdraws -= _amount` underflow after the attacker's claim clamps the counter to 0.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
