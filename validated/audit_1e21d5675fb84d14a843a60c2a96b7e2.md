### Title
No restriction bypass in `retryRequester` — retry logic is fully decoupled from JobResponse parsing/validation - (File: `network/retry_requester.go`)

### Summary
`retryRequester.Do`/`executeRequestWithRetries` operates exclusively on `*http.Request`/`*http.Response` at the transport layer, retrying only on a fixed set of HTTP status codes, and discards (closes) the body of every non-final response before retrying. It never reads, unmarshals, or otherwise inspects the JSON body itself, so it cannot smuggle a differently-configured job spec past downstream validation.

### Finding Description
`executeRequestWithRetries` (`network/retry_requester.go:78-117`) loops calling `r.client.Do(req)`, checks `shouldRetryRequest(resp)` based solely on `resp.StatusCode` against `retryStatuses`/`>=512` (`network/retry_requester.go:159-162`), and on each retriable-but-not-final iteration calls `closeResponseBody(resp, true)` (`network/retry_requester.go:107`) to fully discard that response's body before waiting and regenerating the request body for the next attempt (`network/retry_requester.go:113-115`). Only the last response (`success = true`) is returned untouched to the caller (`network/retry_requester.go:102-104`), with `defer` guaranteeing any intermediate/non-final response body is closed (`network/retry_requester.go:83-87`).

This confirms:
- No JSON decoding, field inspection, or partial reads of `resp.Body` happen inside `retryRequester` — it is a pure HTTP-status-driven retry wrapper.
- Each retry attempt re-executes the *entire* request via `r.client.Do(req)` and receives a brand-new `*http.Response`; there is no mechanism to merge, splice, or carry over data from an earlier attempt's body into the final one.
- The single `*http.Response` returned by `Do` is what callers in `network/client.go` subsequently read (via `io.ReadAll`/`json.Unmarshal`, confirmed present in that file) into a single `JobResponse` struct instance, which is then handed to executors (e.g., `executors/kubernetes.Prepare()`) for `common.VerifyAllowedImage`, pull-policy intersection, and namespace/service-account/overwrite-regex checks.

Since `retryRequester` neither retains nor exposes any data from intermediate attempts, and only the final, single `*http.Response`'s body is ever unmarshaled by the caller into the `JobResponse` that executors validate, there is no code path allowing a "second, differently-configured spec" to bypass validation via this retry mechanism.

### Impact Explanation
None — this is a negative finding. `retryRequester` sits entirely outside the enforcement path for image/service/pull-policy/namespace/volume restrictions; those checks operate on the single `JobResponse` produced after `retryRequester.Do` returns.

### Likelihood Explanation
Not applicable — no exploitable condition exists in this component. The retry logic is structurally incapable of influencing which JSON body is parsed, since only the terminal `*http.Response` is ever returned and unmarshaled.

### Recommendation
No fix required for `retry_requester.go`. Optionally document (as this analysis does) that retry/backoff logic must remain strictly transport-layer and must never gain access to decoded `JobResponse` fields, to preserve this invariant across future refactors.
