I found a concrete gap in `check_parent_tenure_choice`'s reorg-permit logic that lets a single miner (via ordinary block proposals) sanction a reorg over a tenure with **exactly one** globally accepted block, while the "empty tenure" branch of the same loop treats *any other reorged tenure in the chain* identically regardless of order — this matches the report's theme (a state-changing operation accepted without validating that the resulting view is actually consistent with what was previously committed).

### Title
Single-block tenures with a globally-accepted block can be reorged via `check_parent_tenure_choice`'s off-by-one threshold - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` only refuses a reorg when a superseded tenure has **more than one** (`> 1`) globally accepted block [1](#0-0) . A tenure with exactly one globally-accepted (i.e., fully signed, node-processed) block is treated the same as an empty tenure and can still be superseded merely by satisfying the `first_proposal_burn_block_timing` timing window [2](#0-1) .

### Finding Description
The reorg-permit routine walks every tenure between the new sortition's `parent_tenure_id` and `prior_sortition`. For each reorged tenure it should refuse the reorg outright once that tenure has produced real, network-confirmed chain state. Instead the gate is `globally_accepted_blocks > 1`, not `>= 1` [1](#0-0) . A tenure that mined exactly one block, had it signed by the group, and had that block become the network's Stacks tip (`GloballyAccepted`) falls through to the timing check instead of being an automatic refusal. If that single block was signed close enough to the next sortition (within `first_proposal_burn_block_timing`, default 60s per `sample/conf/signer/mainnet-signer-conf.toml`), the tenure is marked `superseded` and the reorg is *permitted* [3](#0-2) . Once a tenure is marked superseded, the earlier signature signers placed over its (globally accepted, chain-adopted) block no longer counts as a live conflict for the new competing chain [4](#0-3) , and signers will sign a sibling block at the same height on the new miner's fork.

This is exactly analogous to the reported bug class: an operation that mutates a shared, security-relevant piece of state (here, "which tenures may be safely replaced") is accepted based on an incomplete check of the pre-existing state (the tenure already produced a *canonically adopted* block, not just a signed-but-unconfirmed one) — the code checks "how many blocks were globally accepted" but uses the wrong threshold, silently admitting one already-finalized block into the "OK to discard" bucket.

A single miner who wins one sortition, gets a block signed and accepted by the network, then quickly wins (or colludes to quickly win) the very next sortition and proposes a competing block building off an earlier ancestor, can trigger this path purely through the normal block-proposal/tenure-change flow — no signer majority collusion is required; the signer set behaves correctly per its own rules, but those rules mis-classify a one-block, already-canonical tenure as reorg-eligible.

### Impact Explanation
This breaks the "approved-parent vs canonical" equality that section 8 of the signer design promises: a tenure that already produced a *globally accepted* (chain-adopted) block should be permanently pinned against replacement, the same way a `>1`-block tenure is. Under the `> 1` threshold, a legitimately finalized single block can be discarded and a signer will go on to sign a conflicting/non-canonical sibling block, which is the Critical-impact case defined by the rules ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
The condition is entirely miner-driven: any miner that (a) mines and gets one block globally accepted in a tenure, and (b) wins the very next sortition (or a subsequent one) within `first_proposal_burn_block_timing` of that block's finalization, reaches this branch through the standard tenure-change proposal path (`validate_tenure_change_payload` → `check_parent_tenure_choice`, called from both v1's `check_proposal` and v2's tenure-change validation) [5](#0-4) . No signer collusion, no majority, and no protocol-version-specific behavior is needed — natural mining-race timing after a fast tip-to-tip transition is sufficient.

### Recommendation
Change the threshold in `check_parent_tenure_choice` from `globally_accepted_blocks > 1` to `globally_accepted_blocks >= 1` (i.e., `> 0`), so that any tenure with even a single globally-accepted (network-confirmed) block is unconditionally refused as a reorg target, consistent with the "signature is a bearer instrument" invariant documented for reorg protection [6](#0-5) .

### Proof of Concept
1. Miner A wins sortition S1, proposes block B1 (tenure-change block). All signers sign; the node processes B1 and it becomes the canonical Stacks tip (`BlockState::GloballyAccepted`).
2. Within `first_proposal_burn_block_timing` seconds of B1's signing/acceptance, a new sortition S2 occurs (e.g., Miner A racing its own commit, or simply fast block times).
3. The new tenure's miner proposes a tenure-change block B2 whose `parent_tenure_id` points to the tenure *before* S1 (skipping S1 entirely), attempting to reorg S1's tenure.
4. `check_parent_tenure_choice` queries `get_globally_accepted_block_count_in_tenure(S1)` and gets `1`; since `1 > 1` is `false`, it does **not** hit the automatic-refusal branch [1](#0-0) .
5. It falls into the timing branch; because B1 was signed shortly before S2, `proposal_to_sortition < first_proposal_burn_block_timing` is true, so the tenure is pushed onto `superseded_tenures` and the reorg is permitted [7](#0-6) .
6. Signers mark S1's tenure superseded, no longer treat B1's signature as a conflict, and sign B2 at the same height, replacing an already chain-adopted block with a sibling — the exact scenario the `reorg_timing_ok`/`superseded` unit tests exercise for *zero*-block tenures, but which the `> 1` threshold also incorrectly allows for *one*-block, already-finalized tenures [8](#0-7) .
