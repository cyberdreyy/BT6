### Title
Post-default instant-withdraw receipts pollute the default-epoch claim bucket and drain `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault.requestWithdraw` has an explicit post-default branch (`defaultRecoveryFinalized`) that routes new receipts into `postDefaultRequests` so they can never re-enter the defaulted-epoch accounting. `requestInstantWithdraw` has no such branch: after `finalizeDefaultRecovery` freezes `epochNumber` at `defaultRecoveryEpoch`, a new instant receipt is still recorded under `instantWithdrawsRequestsByEpoch[user][epochNumber]` — i.e. inside the very epoch bucket that `_claimDefaultedInstantWithdrawRequest` pays out at `defaultRecoveryPrice` from `defaultRecoveryReserve`. This is the direct analog of prototype pollution: attacker-supplied input is written into a shared keyed structure (the default-epoch instant-claim bucket) that was already "finalized", contaminating a distribution that should be immutable.

### Finding Description

Relevant code, `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` lines 243-258: when `defaultRecoveryFinalized` is true, receipts are parked in `postDefaultRequests[_user]` and do **not** touch `withdrawsRequestsByEpoch`, `pendingWithdraws`, or the defaulted epoch.
- `requestInstantWithdraw` lines 356-375: calls `_ensureDefaultRecoveryInitialized()` but never checks `defaultRecoveryFinalized`. It executes:
  - `_mint(_user, _amount)` (line 363)
  - `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (line 371)
  - `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (line 372)
  - `pendingInstantWithdraws += _amount` (line 374)

  After default finalization, `epochNumber == defaultRecoveryEpoch` forever (the epoch state machine can never run again: `isEpochRunning` stays false, so `stopEpoch`/`epochNumber++` are unreachable).

- `claimInstantWithdrawRequest` lines 380-393: when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, it calls `_claimDefaultedInstantWithdrawRequest(_user)` (lines 842-856), which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`, then pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` via `_transferDefaultRecovery` — drawing from `defaultRecoveryReserve`, the fund meant for pre-default claimants.

So a tranche holder who still holds defaulted tranche tokens (or a fresh KYC'd depositor via `postDefaultRequests`-style deposit flow) can call `requestInstantWithdraw` (CDO-side, gated only by `allowInstantWithdraw` and tranche balance, not by `defaultRecoveryFinalized` or `isEpochRunning`), mint a receipt keyed into `defaultRecoveryEpoch`, and immediately call `claimInstantWithdrawRequest`. The claim pulls `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` underlying from `defaultRecoveryReserve` — funds reserved for legitimate defaulted-epoch claimants and the LP recovery pool.

Note the attacker's receipt is fully collateral-backed only at claim time: the `_mint`ed strategy tokens are burned at claim, but the underlying paid out comes from the recovery reserve, not from any funding of `pendingInstantWithdraws` (which post-default can never be collected — `collectInstantWithdrawFunds` is only callable via `getInstantWithdrawFunds` during a running epoch). If `defaultRecoveryPrice < RECOVERY_FULL` the attacker even mints the receipt at par and claims only the haircut — but every wei paid is pure reserve drain, since the attacker supplied zero underlying.

Caveat: I could not fully verify the CDO-side `requestInstantWithdraw` gating in `IdleCDOEpochVariant` (whether it additionally requires `isEpochRunning`). The vault-side asymmetry vs. `requestWithdraw` (which explicitly special-cases `defaultRecoveryFinalized`) strongly suggests the missing guard is unintended.

### Impact Explanation

Direct theft of the default recovery reserve. Any unprivileged tranche-token holder (the receipt only requires burning tranche tokens via the CDO) can mint an arbitrarily large instant-withdraw receipt into the finalized default epoch and claim `defaultRecoveryPrice`-haircutted underlying from `defaultRecoveryReserve`, up to draining it entirely. Legitimate defaulted-epoch claimants and post-default LPs then find the reserve depleted — their `_transferDefaultRecovery` payouts revert on insufficient balance, permanently freezing unclaimed recovery. Loss is bounded by the reserve size but scales linearly with attacker tranche holdings, and post-default tranche tokens are exactly what every defaulted LP holds.

### Likelihood Explanation

- Attacker requirements: hold tranche tokens (guaranteed for any existing LP post-default, or obtainable) and pass KYC (`isWalletAllowed`) if Keyring is set — both allowed attacker profiles.
- Preconditions: `defaultRecoveryFinalized == true`, `defaultInstantWithdrawsFinalized == true`, `allowInstantWithdraw == true` (a normal config flag, independent of epoch state), and a non-empty `defaultRecoveryReserve` — i.e. any default with partial or over-recovery.
- No privileged cooperation needed; the sequence is two attacker calls (`requestInstantWithdraw`, then `claimInstantWithdrawRequest` via `IdleCDOEpochVariant.claimInstantWithdrawRequest`, lines 975-979).

### Recommendation

In `requestInstantWithdraw`, mirror the `requestWithdraw` post-default handling: either revert when `defaultRecoveryFinalized` is true (instant withdrawals have no funding source after finalization anyway, since `collectInstantWithdrawFunds` can never run again), or route the receipt into `postDefaultRequests`/the post-default reserve path instead of `instantWithdrawsRequestsByEpoch[epochNumber]`. The revert is the safer option because instant requests post-default can never be funded through `getInstantWithdrawFunds`.

### Proof of Concept

Foundry fork test (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testPostDefaultInstantRequestDrainsRecoveryReserve() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());

    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);       // attacker tranche tokens
    _depositWithUser(makeAddr("victim"), amount, true); // honest LP

    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, 0);               // borrower repays nothing
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    // finalize with 50% recovery
    uint256 recovered = (cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest()) * 5e17 / 1e18;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 reservePre = vault.defaultRecoveryReserve();

    // attacker: instant-withdraw receipt keyed into the frozen defaultRecoveryEpoch
    vm.prank(address(this)); // holds mintedAA
    cdoEpoch.requestInstantWithdraw(mintedAA, address(AAtranche)); // or equivalent CDO entrypoint

    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 stolen = IERC20Detailed(defaultUnderlying).balanceOf(address(this)) - balPre;

    // attacker received recovery-price haircutted funds without funding pendingInstantWithdraws
    assertGt(stolen, 0);
    assertLt(vault.defaultRecoveryReserve(), reservePre);
}
```
