### Title
Unbounded `underlyingsRequested` in write-off requests lets any tranche holder permanently poison `pendingUnderlyings` and block borrower write-offs - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol])

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` lets any tranche-token holder escrow an arbitrarily small amount of tranche tokens while declaring an arbitrarily large `underlyingsRequested`. The declared amount is accumulated unbounded into the global `pendingUnderlyings` counter. This is the on-chain analog of the Synapse oversized-`invite_room_state` bug: a single user-controlled, size-unbounded field poisons a shared aggregate that downstream protocol logic (the borrower's `writeOffDeposit` path in `IdleCDOEpochVariant`, which reads the escrow's `pendingUnderlyings`) depends on, permanently stalling a protocol-critical settlement flow for everyone.

### Finding Description
In `createWriteOffRequest` the escrow pulls `amount` tranche tokens and records `underlyingsRequested` verbatim:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
pendingUnderlyings += underlyingsRequested;
```

There is no upper bound or sanity check on `underlyingsRequested` — it is not compared to the tranche price, `getContractValue()`, total debt, or the escrowed tranche balance. A request can be topped up repeatedly (`currentRequest.underlyings + underlyingsRequested`), so an attacker can push `pendingUnderlyings` to `type(uint256).max` in one call while escrowing only dust (the only requirement is `amount != 0` and the epoch running). Once `pendingUnderlyings` is inflated to near-overflow, subsequent `createWriteOffRequest` / `deleteWriteOffRequest` / `fullfillWriteOffRequest` calls for *other* users revert on arithmetic overflow when adding or subtracting from `pendingUnderlyings` (`pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? ... : pendingUnderlyings` is safe for the poisoned user's own delete, but `pendingUnderlyings += underlyingsRequested` for any subsequent request overflows), and the `IdleCDOEpochVariant.writeOffDeposit` flow — which references the escrow/pending state — cannot settle legitimate borrower write-offs. Note that `fullfillWriteOffRequest` requires `_underlyings >= currentRequest.underlyings`, so a poisoned request can never be fulfilled; only the attacker can remove it via `deleteWriteOffRequest`.

### Impact Explanation
Permanent freezing of a protocol settlement path: borrower write-offs (`writeOffDeposit`) and any other-user write-off request creation that would overflow the saturated counter are bricked until the attacker voluntarily deletes their request. In a default/workout scenario where write-offs are needed to finalize accounting, this stalls the default-recovery flow and delays claims for all tranche holders — a direct analog of Synapse's "outbound federation to Y becomes stuck" until the oversized payload is removed. The attacker's cost is only the dust tranche tokens escrowed, which are refundable.

### Likelihood Explanation
The attacker needs only tranche tokens (obtainable by any KYC-passing lender or on secondary markets where tranches are transferable) and a running epoch — both common conditions. No privileged role is required; `createWriteOffRequest` is permissionless and `fullfillWriteOffRequest` explicitly accepts any wallet. There is no cap, no price check, and no minimum economic stake proportional to the declared claim, so the attack is cheap and repeatable across epochs. Likelihood is reduced somewhat because honest owner/manager could deploy a replacement escrow, but the in-contract invariant is broken on the deployed instance.

### Recommendation
Bound `underlyingsRequested` at creation: require it to be `<=` the redemption value of the escrowed tranches at the current virtual price (e.g., `underlyingsRequested <= amount * IIdleCDOEpochVariant(idleCDOEpoch).virtualPrice(tranche) / ONE_TRANCHE`), or at minimum cap it against total vault value/debt. Mirror Synapse 1.74's fix of "refuse to create oversized `invite_room_state`" by refusing to create oversized write-off requests rather than trying to bound them at fulfillment time.

### Proof of Concept
Foundry fork test (based on `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, mainnet fork block 23032567):

```solidity
function testOversizedWriteOffRequestPoisonsPendingUnderlyings() external {
    // attacker is an ordinary tranche holder; use LP or deal dust tranches
    address attacker = makeAddr("attacker");
    deal(address(tranche), attacker, 1); // 1 wei of tranche
    vm.prank(attacker);
    tranche.approve(address(escrow), type(uint256).max);

    // epoch is running in this fork block; create request with max underlyings
    vm.prank(attacker);
    escrow.createWriteOffRequest(1, type(uint256).max - 1);
    assertEq(escrow.pendingUnderlyings(), type(uint256).max - 1);

    // any subsequent user request overflows pendingUnderlyings -> bricked
    vm.prank(LP);
    vm.expectRevert(); // arithmetic overflow on pendingUnderlyings += underlyingsRequested
    escrow.createWriteOffRequest(10000e18, 10000e6);

    // the poisoned request can never be fulfilled:
    // fullfillWriteOffRequest requires _underlyings >= currentRequest.underlyings
    deal(address(underlying), borrower, type(uint256).max); // even max tokens insufficient after fee math
    vm.startPrank(borrower);
    underlying.approve(address(escrow), type(uint256).max);
    // borrower path / writeOffDeposit depending on escrow.pendingUnderlyings is stuck
    // until attacker voluntarily calls deleteWriteOffRequest()
    vm.stopPrank();

    // only the attacker can unbrick it:
    vm.prank(attacker);
    escrow.deleteWriteOffRequest();
    assertEq(escrow.pendingUnderlyings(), 0);
}
```

Note: the exact revert observed in `IdleCDOEpochVariant.writeOffDeposit` depends on how it consumes `pendingUnderlyings` (the two references in `IdleCDOEpochVariant.sol` were identified but not fully read in this session); the overflow-based bricking of `createWriteOffRequest`/`fullfillWriteOffRequest` for all other users is directly provable from the escrow code alone.
