Checking the epochNumber increment ordering in stopEpoch vs collectWithdrawFunds.### Title
Loss-adjusted withdraw receipts bypass the haircut because `lossRecoveryPriceByEpoch` is keyed by the post-increment epoch while receipts are keyed by the request epoch — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault` records a stop-epoch loss haircut under `lossRecoveryPriceByEpoch[epochNumber]` inside `collectWithdrawFunds`, but `epochNumber` is already incremented by `deposit()` during the same `stopEpoch` call. Pending receipts were registered under the pre-increment epoch via `lastWithdrawRequest`/`withdrawsRequestsByEpoch`. The claim path therefore reads the recovery price at the wrong index — a stale/out-of-range epoch index read analogous to the LibRaw `raw_width` out-of-bounds read — finds `0` ("no loss"), and pays receipts at par.

### Finding Description
The LibRaw bug is a read past the intended buffer using an attacker/dimension-controlled index. The vault analog is a read of haircut data at the wrong epoch index:

1. A lender requests a withdraw during the buffer/running phase of epoch `N`. `requestWithdraw` stores `lastWithdrawRequest[user] = N` and `withdrawsRequestsByEpoch[user][N] += amount`, and increments `pendingWithdraws` (`IdleCreditVault.sol:282-293`).
2. At `stopEpoch`, the CDO returns borrower funds through `strategy.deposit(...)`. Because `isEpochRunning()` is still true during that call, `deposit` executes `epochNumber += 1`, moving the strategy to `N+1` (`IdleCreditVault.sol:607-610`).
3. The CDO then calls `collectWithdrawFunds(fundedAmount)` with `fundedAmount < pendingWithdraws` (a realized loss). The haircut is written as `lossRecoveryPriceByEpoch[epochNumber]` = `lossRecoveryPriceByEpoch[N+1]`, and `pendingWithdraws` is zeroed (`IdleCreditVault.sol:411-421`).
4. The user calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` = `lossRecoveryPriceByEpoch[N]` = `0` and returns 0 (`IdleCreditVault.sol:789-795`). The funded-claim gate `epochNumber <= lastWithdrawRequest` passes (`N+1 > N`), so `_claimFundedWithdrawRequest` pays the full `withdrawsRequests[user]` at par (`IdleCreditVault.sol:319-349`).

The same index skew hits the default path: `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` (already `N+1`), so `_claimDefaultedWithdrawRequest` reads `withdrawsRequestsByEpoch[user][N+1]` = 0 and skips the recovery-haircut payout entirely (`IdleCreditVault.sol:693,772-784`).

The re-request guard in `requestWithdraw` is also defeated: it checks `lossRecoveryPriceByEpoch[lastWithdrawRequest]` (`N`), which is 0, so a user can open a new request and move `lastWithdrawRequest` to `N+1` — at which point `_claimLossAdjustedWithdrawRequest` finds a non-zero price at `N+1` but `withdrawsRequestsByEpoch[user][N+1] == 0`, again yielding a par claim (`IdleCreditVault.sol:261-271,811-837`).

### Impact Explanation
The loss haircut is never applied to any pending receipt. The strategy only received `fundedAmount < pendingWithdraws` from the borrower, yet every receipt is paid 1:1. Early claimants drain the strategy at par; later claimants (or active AA/BB holders whose loss share was calculated assuming receipts absorbed `pendingLoss` in `previewLossAdjustedWithdrawFunds`) are left unpaid — direct insolvency equal to `pendingBasis - fundedAmount` per loss epoch. In the default path, defaulted-epoch receipts evade `defaultRecoveryPrice` and are paid at par from non-reserve funds, diluting the recovery reserve for all other claimants.

### Likelihood Explanation
No attacker action beyond an ordinary `requestWithdraw` during a normal epoch is needed — any KYC-passing lender triggers it. It fires whenever `stopEpochWithDuration` realizes a loss while `pendingWithdraws > 0`, or whenever default is finalized with pending receipts, i.e., exactly the scenarios the haircut machinery was built for. The guard, skim, and epoch gating cannot stop it because they all consult the same mismatched index.

### Recommendation
Key the loss haircut to the epoch that owns the receipts. Either record `lossRecoveryPriceByEpoch` before `deposit()` increments `epochNumber`, or store the pending receipts' request epoch explicitly (e.g., a `pendingWithdrawsEpoch` variable set in `requestWithdraw`) and use it in `collectWithdrawFunds`. Apply the same fix to `defaultRecoveryEpoch`/`defaultPendingClaimBasis` so recovery accounting targets the request epoch, and add a regression test asserting a receipt created in epoch `N` is paid `claimBasis * lossRecoveryPriceByEpoch[N]` after a lossy `stopEpoch`.

### Proof of Concept
```solidity
// Foundry fork test against a live IdleCreditVault deployment
function testLossHaircutEpochMismatch() public {
    // Epoch N running; lender requests withdraw during buffer
    vm.prank(lender);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // amount = X
    uint256 reqEpoch = strategy.epochNumber();       // N
    assertEq(strategy.lastWithdrawRequest(lender), reqEpoch);
    uint256 pending = strategy.pendingWithdraws();   // == X

    // Borrower repays short: realized loss L, funded = X - L
    uint256 funded = pending - LOSS;
    deal(underlying, borrower, funded);

    // stopEpoch: strategy.deposit() increments epochNumber to N+1,
    // then collectWithdrawFunds stores the haircut under N+1
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, LOSS, epochDuration);

    assertEq(strategy.epochNumber(), reqEpoch + 1);
    assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0);          // haircut misplaced
    assertGt(strategy.lossRecoveryPriceByEpoch(reqEpoch + 1), 0);      // written at wrong index

    // Lender claims: loss path reads epoch N -> 0, funded path pays par
    uint256 balPre = underlying.balanceOf(lender);
    vm.prank(lender);
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(lender) - balPre, pending); // full X, not X - L
    // Strategy paid out more than it was funded: insolvency of LOSS
}
```

Note: the finding assumes `IdleCDOEpochVariant.stopEpoch` calls `strategy.deposit()` (which increments `epochNumber`) before `collectWithdrawFunds`; I was unable to fully read the `stopEpoch` body in `contracts/IdleCDOEpochVariant.sol` within the available iterations, so that ordering should be confirmed there before finalizing the report.
