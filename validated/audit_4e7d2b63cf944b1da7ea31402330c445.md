### Title
Loss haircut is only applied to the withdraw receipt stored in `lastWithdrawRequest`; receipts from earlier epochs in the same loss epoch claim at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `collectWithdrawFunds` underfunds `pendingWithdraws`, the realized loss is recorded once per epoch in `lossRecoveryPriceByEpoch[epochNumber]` and applies pro rata to the *aggregate* pending basis. However, `_claimLossAdjustedWithdrawRequest` only haircuts the receipt slice stored under `lastWithdrawRequest[_user]` and then `_clearWithdrawClaimForEpoch` resets `lastWithdrawRequest[_user] = 0`. Any earlier-epoch receipt slice of the same user in `withdrawsRequests[_user]` then falls through to `_claimFundedWithdrawRequest`, which pays it at par in the same transaction — directly analogous to the kernel bug where `pte_wrprotect()` clears `_PAGE_DIRTY` without propagating it to `_PAGE_MODIFIED`, losing the "dirty" (here: haircut) information.

### Finding Description
1. During a buffer/running epoch, a user calls `cdoEpoch.requestWithdraw` twice across two consecutive epochs (or simply twice: `requestWithdraw` adds both into `withdrawsRequestsByEpoch[user][E1]` and `[E2]`, sets `lastWithdrawRequest = E2`, and both amounts are summed into `pendingWithdraws`). The guard at `IdleCreditVault.sol:263-271` only reverts if `lossRecoveryPriceByEpoch[lastWithdrawRequest] != 0`, which is not yet set, so stacking receipts is allowed.
2. At `stopEpochWithDuration(..., _lossAmount)`, `previewLossAdjustedWithdrawFunds` splits the loss between the aggregate `pendingWithdraws` and active LPs; `collectWithdrawFunds` funds only `pendingToFund` and stores `lossRecoveryPriceByEpoch[epochNumber] < 1e18` (`IdleCreditVault.sol:411-421`). The loss was computed against the user's *combined* basis (E1 + E2 slices).
3. The user calls `cdoEpoch.claimWithdrawRequest`. `claimWithdrawRequest` runs `_claimLossAdjustedWithdrawRequest` (`:789-801`), which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest]` — i.e. only epoch E2 — and `_clearWithdrawClaimForEpoch` zeroes only `withdrawsRequestsByEpoch[user][E2]`, decrements the aggregate by the E2 slice, and resets `lastWithdrawRequest[user] = 0` (`:811-836`).
4. Execution continues into `_claimFundedWithdrawRequest` in the same call (`:312-313`). Its epoch-wait check `epochNumber <= lastWithdrawRequest[user]` now passes trivially because the marker was cleared (`:326`), and it pays the *entire remaining* `withdrawsRequests[user]` — the E1 slice — at par via `_transferFundedClaim` (`:338-349`).

The broken invariant is "one receipt, one haircut": a pending receipt that was part of the loss-bearing `pendingWithdraws` basis escapes its haircut, while the strategy only received `pendingToFund` from the borrower.

### Impact Explanation
Direct theft from the funded loss-adjusted claim pool. If `L` is the pending loss and `P` the total pending basis, the price is `p = 1 - L/P`. An attacker with receipt `a1` in E1 and `a2` in E2 claims `a2*p + a1` instead of `(a1+a2)*p`, extracting `a1*(1-p)` excess. This drains underlyings funded for *other* users' haircutted receipts, so later claimants either receive less than their recovery price or the strategy's funded balance is exhausted (insolvency / permanent freezing of unclaimed claims for honest users). No privileged role misbehavior is needed: the attacker is an ordinary KYC'd lender making ordinary withdraw requests; owner/manager calls (`startEpoch`, `stopEpochWithDuration` with a loss) are honest and part of the normal sequence.

### Likelihood Explanation
The path requires `stopEpochWithDuration` to be called with `_lossAmount > 0` (realized borrower shortfall that does not trigger hard default — a designed flow, per `previewLossAdjustedWithdrawFunds`) while the attacker holds receipts recorded under more than one request epoch. Both conditions are reachable without attacker control of privileged calls: a user can naturally accumulate requests across two buffer periods before a lossy stop. The fix already acknowledges the single-epoch danger (the `revert NotAllowed` when re-requesting over an unclaimed loss-adjusted receipt) but does not cover the multi-epoch-within-one-loss case, which is the exploitable gap.

### Recommendation
Apply the loss price to *all* pending receipt slices of the user, not only the one in `lastWithdrawRequest`. Options: (a) in `_claimLossAdjustedWithdrawRequest`, compute `claimBasis`/`burnAmount` over the full `withdrawsRequests[user]` (and open APR0 buckets) when `lossRecoveryPriceByEpoch` for the loss epoch is set, clearing every contributing `withdrawsRequestsByEpoch` entry; or (b) track a per-user list of request epochs, or store the haircut against the aggregate per-user basis. Alternatively, revert new `requestWithdraw`s whenever the user has *any* unclaimed pending receipt while a loss epoch exists — i.e. enforce claim-before-request whenever `withdrawsRequests[user] != 0 || apr0Users[user].principal != 0` after a `lossRecoveryPriceByEpoch` was recorded.

### Proof of Concept
Foundry fork sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testLossHaircutEscapeAcrossEpochs() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 amount = 10_000 * ONE_SCALE;

    // victim and attacker deposit AA
    address victim = makeAddr('victim');
    _depositWithUser(victim, amount, true);
    uint256 attackerTranches = idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true); // attacker = this

    // epoch E1 request
    uint256 req1 = cdoEpoch.requestWithdraw(attackerTranches / 2, address(AAtranche));
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch()); // fully funded, epochNumber++

    // epoch E2 request (allowed: no loss price recorded yet for E1)
    uint256 req2 = cdoEpoch.requestWithdraw(attackerTranches / 2, address(AAtranche));
    uint256 reqV = _requestWithdrawWithUser(victim, /* victim tranches */);
    _startEpochAndCheckPrices(1);

    // lossy stop: fund only pendingToFund
    uint256 pending = vault.pendingWithdraws();
    uint256 loss = pending / 2; // 50% haircut on pending bucket
    (uint256 pendingToFund, ) = vault.previewLossAdjustedWithdrawFunds(loss);
    deal(defaultUnderlying, borrower, pendingToFund + cdoEpoch.expectedEpochInterest());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, epochDuration, loss);

    uint256 price = vault.lossRecoveryPriceByEpoch(vault.epochNumber() - 1); // < 1e18

    // attacker claims: gets req2*price + req1 at par in ONE call
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - balPre;
    assertEq(got, req1 + req2 * price / 1e18); // should have been (req1+req2)*price
    // victim now can claim less than reqV*price or reverts on insolvent funded pool
}
```

Key assertion: `got == req1 + req2*p`, whereas correct payout is `(req1+req2)*p`; excess `req1*(1-p)` is taken from the shared funded pool that backs `victim`'s haircutted claim.
