### Title
Anti-webhook UUID check in `PipelineRunsController.Create` is bypassed by using the job's numeric ID, allowing removed Webhook-type jobs to be run - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` only blocks webhook job runs when the request `:ID` parses as a UUID, but a webhook job can equally be identified by its numeric `job.Job.ID`. Any authenticated user (run-role sufficient) can call `POST /v2/jobs/<numeric-webhook-job-ID>/runs` and reach `App.RunJobV2` directly, since the numeric-ID branch performs no job-type check at all.

### Finding Description
In `Create`, the only defense against running the removed Webhook job type is: [1](#0-0) 

This guard exclusively inspects whether `idStr` parses as a `uuid.UUID`. Immediately afterward, if the caller `isUser` (i.e., holds any authenticated user session, including run-role), the code takes an entirely separate branch that parses `idStr` as an `int32` and calls `prc.App.RunJobV2(ctx, jobID, nil)` unconditionally, with no lookup of the job's type and no re-application of the `ErrJobTypeRemoved`/webhook check: [2](#0-1) 

Because a `job.Job` has both an external UUID (`ExternalJobID`) and an internal numeric `ID`, a webhook job that still exists in the `jobs` table (its type having been "removed" only in the sense that the UUID-based run path is blocked) remains fully runnable via its numeric primary key. The numeric-ID branch does not query the job spec's `Type` before invoking `RunJobV2`, so there is no code path anywhere in `Create` that prevents a numeric ID belonging to a Webhook-type job from reaching `RunJobV2`.

### Impact Explanation
This allows a lower-privileged, run-role authenticated user to trigger execution of a job type (`Webhook`) that the node operator/deployment intends to have fully disabled/removed, via an authorization/logic bypass rather than a legitimate execution path. This falls under unauthorized job execution / authorization-exactness bypass in the Chainlink bounty impact taxonomy — reintroducing deprecated pipeline behavior that could have downstream side effects (e.g., unintended external calls, fund-moving pipeline tasks) that the removal of webhook UUID-triggering was meant to prevent.

### Likelihood Explanation
Exploitation requires only: (1) a valid run-role (or higher) session on the node's web API, and (2) knowledge of the numeric ID of an existing Webhook-type job (numeric IDs are sequential/low-entropy and often discoverable via the jobs list API for users with read access). No admin/operator access, no signature forgery, and no complex setup are needed — a single POST request suffices, making this highly reproducible.

### Recommendation
In the numeric-ID branch of `Create` (and ideally centrally, e.g., inside `RunJobV2` itself), look up the job's `Type` via `JobORM().FindJob(ctx, jobID)` before calling `RunJobV2`, and reject with the same `ErrJobTypeRemoved` error if `jb.Type == job.Webhook` (or any other removed type), regardless of whether the ID supplied was a UUID or a numeric ID.

### Proof of Concept
1. Seed the ORM/test DB with a `job.Job` whose `Type` is `job.Webhook` (or whatever type the codebase marks with `ErrJobTypeRemoved`), noting its numeric `ID`.
2. Construct a Gin test router wiring `PipelineRunsController.Create` behind a run-role-authenticated test session (mirroring how `core/web/router.go` mounts `POST /v2/jobs/:ID/runs`).
3. Send `POST /v2/jobs/<numericID>/runs` with that numeric ID.
4. Assert (current buggy behavior) that the request succeeds (`200`/`201` with a pipeline run resource) instead of returning `422 Unprocessable Entity` with `ErrJobTypeRemoved`, contrasting with the same request using the job's external UUID which is correctly rejected at line 104-107 of `core/web/pipeline_runs_controller.go`.
5. Fix verification: after adding a job-type check in the numeric branch, re-run the test and assert both the UUID and numeric-ID forms return `422` with `ErrJobTypeRemoved`.
