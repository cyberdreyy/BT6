### Title
ERC4626 share inflation can steal funds deposited through `ProgrammableBorrower` - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower` deposits idle credit-vault liquidity into an arbitrary configured ERC4626 vault without requiring a minimum amount of shares or checking the value represented by the shares received. [1](#0-0) 

An unprivileged user of that ERC4626 vault can front-run `startEpoch`, perform a first-depositor/share-inflation donation, and cause the borrower adapter’s deposit to mint zero or economically inadequate shares. [2](#0-1) [3](#0-2) 

### Finding Description
During `IdleCDOEpochVariant.startEpoch`, surplus underlying is transferred to the configured borrower, and `_startEpochProgrammableBorrower` is then invoked. [4](#0-3) 

`ProgrammableBorrower.onStartEpoch` snapshots the underlying balance and deposits all of it through `_depositToVault`. [2](#0-1) 

`_depositToVault` calls `vault.deposit(_assetAmount, address(this))` and accepts whatever share amount the external vault returns, with no `minSharesOut`, maximum accepted share price, or post-deposit asset-value check. [3](#0-2) 

If the configured vault is empty or nearly empty, an attacker can first deposit one wei to mint one share and then directly donate a large amount of assets to the vault, inflating the share price. [1](#0-0) 

When `startEpoch` subsequently deposits the pool’s underlying, standard ERC4626 share rounding can mint zero shares to `ProgrammableBorrower`, while its assets remain in the vault and become redeemable by the attacker’s sole share. [5](#0-4) 

The same unchecked path is also reached when active-epoch repayments are redeployed into the vault. [6](#0-5) 

### Impact Explanation
The attacker can steal up to the entire amount deposited by `ProgrammableBorrower`, subject to vault rounding and the attacker’s inflation donation. [1](#0-0) 

For example, if the attacker creates a one-share vault position backed by `1_000_001` assets and `ProgrammableBorrower` deposits `1_000_000` assets, the deposit mints zero shares in a vault using `assets * totalSupply / totalAssets`. [3](#0-2) 

The attacker can then redeem their one share for `2_000_001` assets, extracting the entire pool deposit plus recovering the donation. [7](#0-6) 

`ProgrammableBorrower` later values its position through `vault.convertToAssets(shares)`, so a zero-share result is reported as zero vault assets and becomes vault loss/default accounting rather than a recoverable deposit. [8](#0-7) [7](#0-6) 

This results in direct theft of lender principal and can force the credit vault into borrower-default handling when the funds cannot be withdrawn for `stopEpoch`. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
The attack only requires an honest owner or manager to configure a new or empty ERC4626 vault that does not implement inflation resistance, which is a normal deployment state for many ERC4626 integrations. [11](#0-10) 

Any ERC4626 vault user can execute the initial deposit and donation, and no privileged role, borrower action, governance action, oracle manipulation, or malicious vault owner is required. [1](#0-0) 

The attack must front-run the honest `startEpoch` transaction, but this is a single transaction-ordering requirement and the deposited amount can be atomically stolen afterward by redeeming the attacker’s vault share. [12](#0-11) [13](#0-12) 

Vaults using virtual shares, non-trivial initial liquidity, or inflation-resistant share accounting reduce the practicality of the exploit, but `ProgrammableBorrower` does not enforce that the configured vault has those properties. [11](#0-10) [3](#0-2) 

### Recommendation
Add slippage protection to `_depositToVault`, such as a manager-configured minimum shares parameter or a post-deposit invariant that reverts when `vault.convertToAssets(shares)` is materially below `_assetAmount`. [1](#0-0) [7](#0-6) 

The stricter check should bound both zero-share mints and dust-share mints, because merely requiring `shares > 0` still permits large rounding losses when one share represents a manipulated amount of assets. [3](#0-2) 

`setVault` should also validate that newly configured vaults use inflation-resistant ERC4626 accounting or are pre-seeded under trusted control before public users can deposit or donate. [11](#0-10) 

### Proof of Concept
A minimal Foundry PoC can model an ERC4626 vault whose deposit conversion is `assets * totalSupply / totalAssets`, seed `ProgrammableBorrower` with the exact start-epoch cash, and invoke `onStartEpoch` as the configured CDO. [14](#0-13) [3](#0-2) 

```solidity
function testStartEpochVaultShareInflation() public {
    // ERC4626 share conversion:
    // first deposit: shares = assets
    // later deposit: shares = assets * totalSupply / totalAssets

    // Attacker is an unprivileged user of the configured ERC4626 vault.
    asset.mint(attacker, 1_000_001 ether);

    vm.startPrank(attacker);
    asset.approve(address(vault), type(uint256).max);
    vault.deposit(1, attacker);              // 1 share, 1 asset
    asset.transfer(address(vault), 1_000_000 ether); // inflate share price
    vm.stopPrank();

    // Honest CDO has sent 1,000,000 assets to ProgrammableBorrower
    // and now invokes the start-epoch hook.
    asset.mint(address(programmableBorrower), 1_000_000 ether);

    vm.prank(address(idleCDO));
    programmableBorrower.onStartEpoch(0);

    // shares = 1_000_000e18 * 1 / 1_000_001e18 == 0.
    assertEq(vault.balanceOf(address(programmableBorrower)), 0);
    assertEq(vault.convertToAssets(vault.balanceOf(address(programmableBorrower))), 0);

    // The attacker's one share redeems the donated assets plus the
    // ProgrammableBorrower deposit.
    vm.prank(attacker);
    uint256 stolen = vault.redeem(1, attacker, attacker);

    assertEq(stolen, 2_000_001 ether - 1); // less the initial 1-wei share cost
}
```

The important assertion is that `vault.deposit` succeeds while returning zero shares, after which `ProgrammableBorrower` has no ERC4626 claim despite the pool’s assets remaining in the vault. [3](#0-2) [7](#0-6)
