### Title
Mask-phrase processing before token-prefix sanitizer lets a `::add-mask::`/masked-variable phrase neutralize `glpat-` token masking, leaking secret token bytes into trace output - (File: `common/buildlogger/build_logger.go`)

### Summary
`Logger.wrap` builds the sanitizer chain so that phrase masking (`masker.New`) runs **before** the fixed token-prefix sanitizer (`tokensanitizer.New`) on every byte written to the trace. If a job author registers a masked phrase (via a masked CI/CD variable or `::add-mask::`) that is, or overlaps with, a token prefix such as `glpat-`, the phrase masker consumes and replaces that prefix text with the literal `[MASKED]` before `tokensanitizer` ever observes it, breaking the prefix-matching state machine and causing the actual secret entropy that follows the prefix to be written to the trace unmasked.

### Finding Description
`Logger.wrap` constructs the chain as: [1](#0-0) 

Because "the last added filter is the first to process data" (per the function's own comment), the actual per-byte processing order for every write to the logger is: `masker` (mask phrases) → `urlsanitizer` → `tokensanitizer` (mask prefixed tokens) → timestamper/base writer.

`maskPhrases` originates from job-controlled CI/CD masked variables and from `::add-mask::` (proxy-exec mode), both attacker-influenceable — the test helper in `common/buildtest/masking.go` shows the value is fully job-author chosen, e.g. `echo "::add-mask::ADD_MASK_SECRET_VALUE"` and `spec.Variable{..., Masked: true}`. [2](#0-1) [3](#0-2) 

The `masker` writer scans for exact literal phrase matches and, on completion, recursively emits the literal bytes `[MASKED]` to the next writer: [4](#0-3) 

Both downstream sanitizers special-case this literal to avoid re-processing it — `tokensanitizer`'s fast path forwards it untouched **without altering its internal `matching`/`masked` state**: [5](#0-4) 

The core defect: if the attacker-chosen phrase itself equals or overlaps the token prefix (e.g. `glpat-`), `masker` consumes those exact prefix bytes and replaces them with `[MASKED]` *before* `tokensanitizer` sees anything. `tokensanitizer`'s prefix-matching state machine (`m.matching`, driven by `bytes.IndexByte(p[n:], m.prefix[0])` and `bytes.HasPrefix`) never observes the `g`,`l`,`p`,`a`,`t`,`-` sequence at all for that occurrence — it only sees `[MASKED]` (bypassed) followed by whatever secret-entropy bytes trailed the prefix in the original token. Since `m.matching` stays at `0` and the prefix's first byte (`g`) is very unlikely to reappear in the residual secret bytes, `tokensanitizer` never re-arms its match, and the residual token bytes are forwarded to `urlsanitizer` and the base writer completely unmasked: [6](#0-5) [7](#0-6) 

This is a genuine violation of the stated invariant that configured masks are independent/complete: because `masker` and `tokensanitizer` are stateful stream filters applied to the *entire* logger stream (not just the attacker's own echoed line), registering one attacker-chosen phrase equal to `glpat-` (or a superset/substring containing it) neutralizes token-prefix masking for **every subsequent `glpat-` occurrence in that job's whole trace**, including tokens the job did not itself print (e.g. any other masked variable/token value beginning with `glpat-` that surfaces later via a different log line, error message, or tool output).

By contrast, the shipped `gofuzz` harness in `internal/build_logger_fuzz.go` chains the sanitizers in a *different* order (`urlsanitizer` outermost, `tokensanitizer` middle, `masker` innermost) than production's `wrap()` (`masker` outermost, `urlsanitizer` middle, `tokensanitizer` innermost): [8](#0-7) 
This means the existing fuzz coverage does not exercise the actual production ordering, so this specific interaction is not caught by existing tests.

### Impact Explanation
A job author can cause real secret token material (the entropy portion following a `glpat-`, or any other configured token prefix) to be written verbatim into the job trace, which is persisted server-side via `PatchTrace`/`UpdateJobRequest.Output`. This is a concrete partial-secret-leakage of exactly the scoped impact: masked token content ends up in permanently stored trace logs, readable by anyone with trace-read access to that job (which may exceed the set of principals entitled to know the secret).

### Likelihood Explanation
Preconditions are fully within an unprivileged job author's control: they need only (a) a masked variable or `::add-mask::` call whose value is/contains the literal token prefix string (`glpat-` is public, documented, and constant), and (b) any `glpat-`-prefixed secret appearing anywhere later in the same job's trace stream (their own printed secret, or another masked variable/token surfaced by tooling/errors). No special privileges, admin actions, or third-party compromise are required, and the effect is deterministic/repeatable given the same phrase+trailing-token byte layout.

### Recommendation
Do not let phrase masking run ahead of, and destructively overwrite, exact-prefix bytes needed by the token-prefix sanitizer. Options: (1) run `tokensanitizer` before `masker` in `Logger.wrap` so fixed-format token prefixes are masked first (reversing lines 218-220), and/or (2) reject/ignore phrase masks that exactly equal or are substrings of a configured token prefix, and/or (3) have `tokensanitizer`'s fast path for the `[MASKED]` literal explicitly retain/re-anchor `m.matching` state so a prefix broken by an intervening upstream mask doesn't silently drop detection for the remainder of that token.

### Proof of Concept
Go test added alongside `common/buildlogger/build_logger_test.go`, driving the real `Logger.wrap`/`New` chain via `buildlogger.New` (not the mismatched fuzz harness):

```go
func TestMaskPhraseOverlapWithTokenPrefixLeak(t *testing.T) {
    var buf internal.SyncBuffer // or bytes.Buffer wrapped as Trace
    trace := &fakeTrace{w: &buf}

    logger := buildlogger.New(trace, entry, buildlogger.Options{
        MaskPhrases:       []string{"glpat-"},   // attacker-registered mask phrase overlapping token prefix
        MaskTokenPrefixes: []string{"glpat-"},
    })

    secret := "glpat-SUPERSECRETENTROPY123"
    fmt.Fprintln(logger.Stream(0, buildlogger.Stdout), secret)
    logger.Close()

    out := buf.String()
    assert.NotContains(t, out, "SUPERSECRETENTROPY123", "token entropy leaked after phrase mask broke tokensanitizer's prefix match")
    assert.NotContains(t, out, secret)
}
```
Expected (bug present): the assertion fails — `out` contains `glpat-[MASKED]SUPERSECRETENTROPY123` (or similar), i.e. `SUPERSECRETENTROPY123` is present in cleartext, proving the leak.

func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
