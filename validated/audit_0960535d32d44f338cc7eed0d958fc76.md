## Analysis

The externally-reported bug class is a **configuration-parameter sandwich / TOCTOU attack**: a privileged party changes an economic parameter (auction length) *between* the moment a counterparty commits capital and the moment that parameter is used to their detriment, with the change taking effect **instantly** — no timelock protects the victim.

I searched agave's transaction-processing paths (nonce, compute-budget, fee-payer validation) for an analogous instant-effect, front-runnable parameter, and those are well protected (durable-nonce blockhash binding, compute-budget snapshot at sanitization). However, the **vote program's commission mechanism** is a much closer structural analog, and one variant of it is **not** protected the way the legacy percentage-based commission is.

- Legacy commission (`update_commission`, `programs/vote/src/vote_state/mod.rs:797-825`) is rate-limited to only increase in the first half of an epoch, and (once `delay_commission_updates` is active) its effect on **inflation rewards** is delayed a full epoch via a cached epoch-boundary snapshot (`CachedVoteAccounts`, `runtime/src/bank/partitioned_epoch_rewards/mod.rs:305-319`, used in `redeem_delegation_rewards`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:703-724`) specifically "to prevent last minute commission rugs."
- However, SIMD-0291's `update_commission_bps` (`programs/vote/src/vote_state/mod.rs:827-859`) explicitly states: *"No commission update rule, per SIMD-0249 and SIMD-0291... Updates are always allowed regardless of epoch position."* This applies to **both** `InflationRewards` and `BlockRevenue` commission kinds.
- Critically, **block-revenue commission is not covered by the epoch-delay snapshot at all** — the delay mechanism only reads `inflation_rewards_commission_bps`/legacy `commission()` from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` (`calculation.rs:709-724`). The block-revenue split (`calculate_block_reward`, `calculation.rs:173-232`) reads directly from `distribution_epoch_vote_accounts` — i.e., current, live vote-account state at the time delegator rewards are distributed, with no epoch-delay protection whatsoever.

This gives a validator (who controls the authorized withdrawer key for their own vote account) the ability to instantly change `block_revenue_commission_bps` to any value up to 10000 (100%), collect a block's transaction fees / MEV revenue that has already accumulated as `pending_delegator_rewards`, then instantly revert the commission — all within the same block/slot they produce, with no signer other than themselves and no timing restriction. This is the direct analog of the lender sandwiching the auction-length parameter around the borrower's transaction: an ordinary delegator (the "borrower" analog) has no way to protect their expected share of block revenue, because the parameter controlling their expected proceeds can be changed atomically by the counterparty just before the split is computed.

### Title
Validator can instantly rug delegators' block-revenue share via unthrottled `UpdateCommissionBps` (BlockRevenue) - (File: programs/vote/src/vote_state/mod.rs)

### Summary
`update_commission_bps` (SIMD-0291) removes all rate-limiting/timing restrictions that exist for the legacy `update_commission` instruction, and applies to both `InflationRewards` and `BlockRevenue` commission kinds. Unlike inflation-rewards commission, block-revenue commission is never passed through the epoch-delayed `CachedVoteAccounts` snapshot mechanism before being used to split `pending_delegator_rewards` between the validator and delegators.

### Finding Description
`programs/vote/src/vote_state/mod.rs:827-859` implements `update_commission_bps`, explicitly documenting "No commission update rule, per SIMD-0249 and SIMD-0291. Updates are always allowed regardless of epoch position" — only requiring the authorized withdrawer's signature (`verify_authorized_signer`). This is invoked from `VoteInstruction::UpdateCommissionBps` in `programs/vote/src/vote_processor.rs`, callable by anyone holding the withdrawer key, with no cooldown, no minimum interval, and no restriction based on slot/epoch position.

Meanwhile, the legacy `delay_commission_updates` protection (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:703-724`) only guards `inflation_rewards_commission_bps` / legacy `commission()` by substituting an epoch-old snapshot value (`CachedVoteAccounts::snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`, defined at `runtime/src/bank/partitioned_epoch_rewards/mod.rs:305-319`, whose doc comment states this exists specifically "to prevent last minute commission rugs"). `calculate_block_reward` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232`), which splits `pending_delegator_rewards` (fees/MEV accumulated over the epoch via `deposit_delegator_rewards`, `programs/vote/src/vote_state/mod.rs:935-988`) using `block_revenue_commission_bps`, reads the vote state directly from `distribution_epoch_vote_accounts` (i.e., current, undelayed state) with no equivalent snapshot substitution.

Because a validator/authorized-withdrawer can call `UpdateCommissionBps { kind: BlockRevenue }` at any time — including in the very block where reward distribution reads `pending_delegator_rewards` — they can set `block_revenue_commission_bps` to 10000 (100%) immediately before the split is computed, and revert it immediately after, capturing delegator's expected share of block revenue that had been accruing throughout the epoch, without warning and without any economic mechanism giving delegators a chance to react (undelegate, exit) beforehand.

### Impact Explanation
Delegated stakers, who have no direct way to detect or preempt this within the same slot, lose their expected share of `pending_delegator_rewards` distributed via block revenue sharing. Because commission can jump to 100% instantly and revert instantly, this is a state-mutation exploit that unfairly and unrecoverably reallocates already-accrued delegator funds to the validator, mirroring the reported bug class (instant unthrottled parameter change enabling seizure of counterparty value that was expected to remain protected).

### Likelihood Explanation
Requires only the authorized withdrawer key of the validator's own vote account (no external attacker needed — this is a validator-vs-delegator trust issue), is gated behind the not-yet-broadly-active `block_revenue_sharing` (SIMD-0123) and `commission_rate_in_basis_points` (SIMD-0291) feature flags. Given how easy and cheap it is to invoke (single signed instruction, no CPI complexity, no rate limit), likelihood is high once these features activate on mainnet, similar in spirit to well-documented "commission rug" incidents that motivated `delay_commission_updates` for the legacy path — that same protection was evidently not extended to the new basis-points/block-revenue path.

### Recommendation
Extend the epoch-delay protection currently applied only to `inflation_rewards_commission_bps`/legacy `commission()` in `redeem_delegation_rewards` to also cover `block_revenue_commission_bps` used by `calculate_block_reward`, i.e. read `block_revenue_commission_bps` from `CachedVoteAccounts::snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` rather than `distribution_epoch_vote_accounts` when `delay_commission_updates` (or an equivalent SIMD-0291-aware flag) is active. Alternatively, reintroduce a rate-limit/cooldown specifically for `BlockRevenue` commission increases in `update_commission_bps`.

### Proof of Concept
1. Enable `block_revenue_sharing`, `commission_rate_in_basis_points`, `custom_commission_collector` features; validator's vote account accrues `pending_delegator_rewards` over an epoch via `deposit_delegator_rewards` (`programs/vote/src/vote_state/mod.rs:935-988`).
2. Immediately before the block/slot in which `calculate_block_reward` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232`) runs to distribute `pending_delegator_rewards`, the validator submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::BlockRevenue }`, signed only by the authorized withdrawer (`update_commission_bps`, `programs/vote/src/vote_state/mod.rs:827-859`) — succeeds unconditionally per SIMD-0291/SIMD-0249's removed timing rule.
3. `calculate_block_reward` reads `block_revenue_commission_bps` = 10000 directly from `distribution_epoch_vote_accounts` (current state, no delay), so 100% of `pending_delegator_rewards` for that distribution is attributed to the validator commission rather than split with delegators.
4. Validator immediately calls `UpdateCommissionBps` again to restore the low commission rate, resuming normal appearance for subsequent epochs. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
