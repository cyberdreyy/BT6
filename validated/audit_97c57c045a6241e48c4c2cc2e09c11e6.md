### Title
`parse_stake` silently discards `StakeFlags`, causing `jsonParsed` `getAccountInfo`/`getProgramAccounts` output to misreport stake accounts with different activation-permission semantics as identical - ([File: account-decoder/src/parse_stake.rs])

### Summary
`parse_stake` destructures `StakeStateV2::Stake(meta, stake, _)` and discards the third tuple field (`StakeFlags`) entirely, so the resulting `UiStakeAccount` never encodes whether `StakeFlags::MUST_FULLY_ACTIVATE_BEFORE_DEACTIVATION_IS_PERMITTED` is set. Any RPC client using `jsonParsed` encoding (`getAccountInfo`, `getProgramAccounts`, `getMultipleAccounts`, account subscriptions) receives byte-identical parsed output for two accounts whose on-chain `StakeFlags` differ, hiding real program behavior differences.

### Finding Description
The relevant code is:
```rust
StakeStateV2::Stake(meta, stake, _) => StakeAccountType::Delegated(UiStakeAccount {
    meta: meta.into(),
    stake: Some(stake.into()),
}),
``` [1](#0-0) 

The `StakeFlags` value is bound to `_` and never used in constructing `UiStakeAccount`, and `UiStakeAccount` itself has no field for it at all [2](#0-1) . This means the `From<Stake>`/`From<Meta>` conversions used populate `UiStake`/`UiMeta` with no trace of the flags [3](#0-2) .

Since an unprivileged actor can write any bit pattern into an owned stake account's `StakeFlags` byte on-chain (this only affects whether deactivation is permitted before full activation, not decoding validity), then query that account via `getAccountInfo` with `jsonParsed` encoding, the RPC output for two accounts identical except for `StakeFlags` will be exactly equal — the flag bit is invisible to any downstream consumer relying on the parsed JSON representation rather than raw base64/base58 account data.

No existing guard mitigates this: the deserialization at line 13 (`bincode::deserialize`) correctly decodes all three tuple fields including `StakeFlags`, but the match arm at line 21 throws the third field away before serialization to JSON.

### Impact Explanation
This is a decoder misreporting bug: an RPC integrator that relies on `jsonParsed` `getAccountInfo`/`getProgramAccounts` output to reconstruct stake account semantics (e.g., staking pools, custodial services, explorers) cannot distinguish a stake account that requires full activation before deactivation from one that does not, since the field is completely omitted rather than defaulted safely. This matches the "wrong account data returned" / decoder misreporting category permitted by the audit scope, since it is a single read-only RPC query revealing/hiding real account state to an unprivileged caller.

### Likelihood Explanation
Fully deterministic and always reproducible: it requires no race condition, no validator control, and no special privilege — any account owned by the stake program can have arbitrary `StakeFlags` values written by its authority via normal stake-program instructions (e.g., `DeactivateDelinquent`, or accounts created directly via `bincode` for testing), and a single `getAccountInfo` call with `jsonParsed` encoding is sufficient to observe the loss.

### Recommendation
Add a `stake_flags` field (or equivalent boolean, e.g. `must_fully_activate_before_deactivation_is_permitted`) to `UiStakeAccount`/`UiStake`, capture the third tuple field in the match arm instead of discarding it with `_`, and serialize it into the parsed JSON so `jsonParsed` output faithfully reflects on-chain `StakeFlags` state.

### Proof of Concept
```rust
#[test]
fn test_parse_stake_discards_stake_flags() {
    use solana_stake_interface::stake_flags::StakeFlags;

    let pubkey = solana_pubkey::new_rand();
    let custodian = solana_pubkey::new_rand();
    let authorized = Authorized::auto(&pubkey);
    let lockup = Lockup { unix_timestamp: 0, epoch: 1, custodian };
    #[allow(deprecated)]
    let meta = Meta { rent_exempt_reserve: 42, authorized, lockup };
    let voter_pubkey = solana_pubkey::new_rand();
    let stake = Stake {
        delegation: Delegation {
            voter_pubkey,
            stake: 20,
            activation_epoch: 2,
            deactivation_epoch: u64::MAX,
            _reserved: [0; 8],
        },
        credits_observed: 10,
    };

    let state_no_flag = StakeStateV2::Stake(meta.clone(), stake.clone(), StakeFlags::empty());
    let state_with_flag = StakeStateV2::Stake(
        meta,
        stake,
        StakeFlags::MUST_FULLY_ACTIVATE_BEFORE_DEACTIVATION_IS_PERMITTED,
    );

    let data_no_flag = bincode::serialize(&state_no_flag).unwrap();
    let data_with_flag = bincode::serialize(&state_with_flag).unwrap();

    let parsed_no_flag = parse_stake(&data_no_flag).unwrap();
    let parsed_with_flag = parse_stake(&data_with_flag).unwrap();

    // Demonstrates information loss: outputs are indistinguishable despite
    // differing activation-permission semantics on-chain.
    assert_eq!(parsed_no_flag, parsed_with_flag);
}
```
Expected result: the assertion passes today, proving `parse_stake` produces identical `jsonParsed` output regardless of `StakeFlags`, confirming the information loss described above.
