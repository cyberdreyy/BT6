### Title
Cross-Chain Nonce Collision in `isTransferProcessed` Mapping Causes Permanent Fund Lock — (`bridge/evm/contracts/SuiBridge.sol`)

---

### Summary

`SuiBridge.transferBridgedTokensWithSignatures` (and its V2 counterpart) tracks processed token-transfer messages in a mapping keyed solely by `message.nonce` (`uint64`). Because the bridge is designed to accept transfers from multiple independent source chains — each maintaining its own nonce counter starting at 0 — two distinct, legitimate transfers from different source chains that happen to share the same nonce value collide in this mapping. The first one processed permanently marks that nonce as consumed, making the second transfer unclaimable and locking the user's funds forever.

---

### Finding Description

`SuiBridge` declares:

```solidity
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
``` [1](#0-0) 

In `transferBridgedTokensWithSignatures`, the replay guard reads and writes this mapping using only `message.nonce`:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
// ... transfer tokens ...
isTransferProcessed[message.nonce] = true;
``` [2](#0-1) 

The same pattern is repeated verbatim in `SuiBridgeV2.transferBridgedTokensWithSignaturesV2`: [3](#0-2) 

`message.chainID` identifies the **source chain** of the transfer. The `onlySupportedChain` modifier confirms the bridge is designed to accept transfers from multiple source chains: [4](#0-3) 

Each source chain maintains its own independent nonce counter starting at 0. Because the `isTransferProcessed` key is `nonce` alone — not `(chainID, nonce)` — nonce 1 from source chain A and nonce 1 from source chain B map to the **same slot**. Whichever transfer is processed first sets `isTransferProcessed[1] = true`, and the other is permanently rejected with `"SuiBridge: Message already processed"`.

Critically, `MessageVerifier.verifyMessageAndSignatures` deliberately skips the sequential-nonce check for `TOKEN_TRANSFER` messages, leaving `isTransferProcessed` as the **sole** replay-protection mechanism for token transfers:

```solidity
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    require(message.nonce == nonces[message.messageType], "MessageVerifier: Invalid nonce");
    nonces[message.messageType]++;
}
``` [5](#0-4) 

---

### Impact Explanation

When source chain B's transfer with nonce N is submitted after source chain A's transfer with nonce N has already been processed, the funds deposited on chain B are permanently locked: the bridge contract on the destination chain will always revert with `"SuiBridge: Message already processed"`, and there is no recovery path. This constitutes **permanent fund lock**, which falls within the High/Medium allowed impact gate.

---

### Likelihood Explanation

The bridge's `BridgeConfig` is explicitly designed to support multiple source chains via `isChainSupported`. Both source-chain nonce counters start at 0 and increment monotonically, so nonce collisions are **guaranteed** as soon as a second source chain is added and both chains have processed at least one transfer. No privileged access is required; any ordinary bridge user submitting a valid committee-signed message triggers the collision.

---

### Recommendation

Key the processed-transfer mapping by the composite `(chainID, nonce)` pair:

```solidity
// Before
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
require(!isTransferProcessed[message.nonce], ...);
isTransferProcessed[message.nonce] = true;

// After
mapping(uint8 chainID => mapping(uint64 nonce => bool isProcessed)) public isTransferProcessed;
require(!isTransferProcessed[message.chainID][message.nonce], ...);
isTransferProcessed[message.chainID][message.nonce] = true;
```

Apply the same fix to `SuiBridgeV2`.

---

### Proof of Concept

1. Bridge is configured to support two source chains: chain A (`chainID = 0`) and chain B (`chainID = 2`).
2. A user on chain B deposits tokens; the committee signs a `TOKEN_TRANSFER` message with `chainID = 2, nonce = 1`.
3. Before the user submits it, a separate user on chain A submits a valid `TOKEN_TRANSFER` message with `chainID = 0, nonce = 1`. It succeeds; `isTransferProcessed[1] = true`.
4. The chain B user now calls `transferBridgedTokensWithSignatures` with their valid, committee-signed message (`chainID = 2, nonce = 1`).
5. The call reverts: `"SuiBridge: Message already processed"`.
6. The chain B user's funds are permanently locked — there is no mechanism to re-issue the transfer with a different nonce. [6](#0-5) [7](#0-6)

    function transferBridgedTokensWithSignatures(
        bytes[] memory signatures,
        BridgeUtils.Message memory message
    )
        external
        nonReentrant
        verifyMessageAndSignatures(message, signatures, BridgeUtils.TOKEN_TRANSFER)
        onlySupportedChain(message.chainID)
    {
        // verify that message has not been processed
        require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");

        IBridgeConfig config = committee.config();

        BridgeUtils.TokenTransferPayload memory tokenTransferPayload =
            BridgeUtils.decodeTokenTransferPayload(message.payload);

        // verify target chain ID is this chain ID
        require(
            tokenTransferPayload.targetChain == config.chainID(), "SuiBridge: Invalid target chain"
        );

        // convert amount to ERC20 token decimals
        uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
            IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(),
            config.tokenSuiDecimalOf(tokenTransferPayload.tokenID),
            tokenTransferPayload.amount
        );

        _transferTokensFromVault(
            message.chainID,
            tokenTransferPayload.tokenID,
            tokenTransferPayload.recipientAddress,
            erc20AdjustedAmount
        );

        // mark message as processed
        isTransferProcessed[message.nonce] = true;

        emit TokensClaimed(
            message.chainID,
            message.nonce,
            config.chainID(),
            tokenTransferPayload.tokenID,
            erc20AdjustedAmount,
            tokenTransferPayload.senderAddress,
            tokenTransferPayload.recipientAddress
        );
    }
