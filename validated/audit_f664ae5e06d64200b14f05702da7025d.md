## Analysis

The externally reported bug class — an ignored return value causing a transfer amount to become decoupled from the actual value moved — has a structural analog in the Gloas (EIP‑7732) builder‑withdrawal path of this repo: the amount **committed** to the execution payload's `Withdrawal` object is never reconciled with the amount **actually deducted** from the builder's on-chain balance. This breaks the invariant that "Gwei paid out via an execution-layer withdrawal must equal Gwei debited from the paying account."

### Title
Builder withdrawal amount minted to EL exceeds CL balance deduction, creating Gwei out of thin air - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` builds a `Withdrawal` whose `amount` is the raw, unclamped value stored in `state.builder_pending_withdrawals[i].amount`. This `Withdrawal` is placed into `state.payload_expected_withdrawals`, which the execution layer is required to honor and mint to `withdrawal.address` in full. However, `apply_withdrawals` only deducts `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`. When the requested pending-withdrawal amount exceeds the builder's actual balance, the execution layer pays out the full requested amount while the consensus layer only debits the smaller, capped amount — creating Gwei that is backed by no corresponding balance decrease anywhere in `BeaconState`.

### Finding Description
`get_builder_withdrawals` builds each `Withdrawal.amount` directly from the pending withdrawal record, with no cap against `builder.balance`: [1](#0-0) 

`apply_withdrawals` (Modified in Gloas) then deducts only the capped amount from the builder's balance: [2](#0-1) 

`process_withdrawals` writes the *uncapped* `Withdrawal` list into `state.payload_expected_withdrawals`, and the spec's own note states the execution layer mints the full committed amount regardless of what the CL later does to balances: [3](#0-2) 

The equality that should hold is:
`sum(withdrawal.amount for withdrawal in payload_expected_withdrawals) == sum(actual balance decrease applied by apply_withdrawals)`

For builder withdrawals this equality is violated whenever `withdrawal.amount > builder.balance` at processing time: the committed (and EL-minted) amount is the full requested amount, while the CL-side decrease is `min(amount, balance)`. The spec's own test suite documents and asserts exactly this divergence as expected behavior: [4](#0-3) 

Note the comment in the test helper, which explicitly treats the "cap at available balance" as the correct behavior for the *balance decrease* — but says nothing about capping the *committed withdrawal amount* that the EL is told to pay: [5](#0-4) 

By contrast, the ordinary (non-builder) partial/full validator withdrawal path computes the withdrawal amount *from* the balance itself (`amount=balance` or `balance - MAX_EFFECTIVE_BALANCE`), so the committed amount can never exceed the balance being decremented: [6](#0-5) 

The builder path is the outlier: it takes an externally-supplied `amount` field from `BuilderPendingWithdrawal` and forwards it unclamped into the payload commitment, while only clamping the *state mutation* side.

### Impact Explanation
This falls under "Gwei created ... paid to a non-owner" / "a payload or payment applied that the block did not commit to" in the sense that the payment actually executed on the execution layer (the full requested amount) is **larger** than what consensus-layer accounting reflects. Each occurrence mints `requested_amount - actual_balance` Gwei from nothing at the fee_recipient address, inflating total supply and creating an accounting divergence between CL state and EL state that the spec text itself acknowledges only for the "balance saturates at zero" case, not for over-committing the EL payment amount. This is a Critical-severity class of bug (unauthorized Gwei creation / total-supply invariant break) if the pending withdrawal amount can exceed the builder's balance at processing time through any spec-compliant sequence of events (e.gvia multiple pending withdrawal requests, or balance depletion between the request and the processing epoch via bid payments/slashless balance reduction paths).

### Likelihood Explanation
Confirmed only at the mechanism level: the spec's own test (`test_builder_withdrawal_insufficient_balance`) proves the divergent-amount behavior is reachable and is treated as expected/valid in the current test suite, i.e., the spec explicitly allows `builder_pending_withdrawals[i].amount` to exceed `builder.balance` at processing time and does not reconcile the committed `Withdrawal.amount` down to the capped value. I was not able to fully trace, within the available iterations, every code path that inserts entries into `state.builder_pending_withdrawals` (e.g. whether amount is validated against balance strictly at insertion time and whether balance can only decrease afterward through further pending withdrawals/bid payments that are themselves already accounted for in `get_pending_balance_to_withdraw_for_builder`). This should be independently verified by reviewing all producers of `BuilderPendingWithdrawal` entries and the payment-consumption flow (`can_builder_cover_bid`, `builder_pending_payments`) to determine whether the balance-vs-requested-amount gap is reachable purely through spec-following block processing.

### Recommendation
In `get_builder_withdrawals`, clamp the committed `Withdrawal.amount` to `min(withdrawal.amount, state.builders[builder_index].balance)` (accounting for withdrawals already queued earlier in the same payload, similar to how `get_validators_sweep_withdrawals` computes `get_balance_after_withdrawals`), so that the amount minted by the execution layer can never exceed what `apply_withdrawals` actually debits from the builder's balance.

### Proof of Concept
Using the spec's own test scenario in `test_builder_withdrawal_insufficient_balance`:
1. Builder 0 has `balance = 1_000_000_000` Gwei (1 ETH).
2. `state.builder_pending_withdrawals` contains one entry for builder 0 requesting `amount = 5_000_000_000` Gwei (5 ETH).
3. `process_withdrawals(state)` is run.
4. Result (asserted by the test itself): `payload_expected_withdrawals[0].amount == 5_000_000_000` (the execution layer will mint 5 ETH to the fee_recipient), while `state.builders[0].balance == 0` (only 1 ETH was actually debited).
5. Net effect: 4 ETH is minted on the execution layer with no corresponding decrease anywhere in `BeaconState`. [7](#0-6)

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
