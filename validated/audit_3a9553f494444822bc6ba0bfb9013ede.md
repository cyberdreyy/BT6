### Title
`BlockAccepted` signature is not domain-separated by `chain_id` (unlike `BlockRejection`), enabling cross-network signature replay - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` binds a signer's rejection signature to the message type and `chain_id` via `make_structured_data_domain("block-rejection", "1.0.0", self.chain_id)` before hashing and signing. [1](#0-0) 
The acceptance path (`BlockResponse::accepted` / `BlockAccepted`), by contrast, signs the raw `signer_signature_hash` bytes directly with no domain tag and no `chain_id` binding at all, and this same raw hash is what the node ultimately re-verifies via `NakamotoBlockHeader::verify_signer_signatures`. [2](#0-1) [3](#0-2) 

### Finding Description
`NakamotoBlockHeader::signer_signature_hash()` is computed purely from block-header fields (version, chain_length, burn_spent, consensus_hash, parent_block_id, tx_merkle_root, state_index_root, timestamp, miner_signature, pox_treatment, problematic_txs) — `chain_id` is never part of the preimage. [4](#0-3) 
A signer's acceptance signature is simply `private_key.sign(signer_signature_hash.bits())`, with no domain separator distinguishing "this is a block-accept for network X" from any other raw signature over the same 32-byte digest. [5](#0-4) 
Both the peer-side consumer (`handle_block_signature`, via `Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(block_hash.bits(), signature)`) and the node's final consensus check (`verify_signer_signatures`) validate the exact same undifferentiated digest. [6](#0-5) [7](#0-6) 

This is the same bug class as the reported CSRF: a state-changing artifact (here, a cryptographic acceptance signature) is accepted without binding it to the intended execution context (network/chain), so a value collected in one context can be replayed as legitimate in a different context. The engineers already recognized this need and fixed it for `BlockRejection` (explicit `chain_id` in the signing domain) but left `BlockAccepted`/the header-level threshold signature unprotected.

### Impact Explanation
If the same signer set (or overlapping signing keys) participates in more than one network/chain that can produce an identical `signer_signature_hash` (e.g., mirrored testnet/mainnet deployments, forked chains sharing genesis/config, or any deliberately-crafted header collision by a miner across two `chain_id` contexts a signer serves), an acceptance signature harvested from one context is a valid `BlockAccepted`/header signature in the other. This breaks the "signed vs validated" equality that the whole pre-commit → signature protocol is built to guarantee (docs/signer-flows.md sections 5–6): the node's `verify_signer_signatures` would count a signature that was never actually produced with intent to approve *that* chain's block, i.e., a rejection-recounted-as-accept / cross-context-valid-signature class break, which the rules classify as Critical.

### Likelihood Explanation
Exploitability requires a scenario where the same signer key(s) sign for two chain-id contexts and an attacker (a miner with one slot plus gossip) can arrange for the header preimage to be identical (or can otherwise obtain/replay an acceptance signature across contexts) — this is a real but narrower precondition than a fully generic remote attack, and I could not find code in this repo that constructs or checks such cross-context collisions directly (this would need to be demonstrated with a concrete dual-network signer deployment to prove practical exploitation). The asymmetry with `BlockRejection`'s explicit `chain_id` domain separation is nonetheless a clear, verifiable root-cause gap in this codebase.

### Recommendation
Add the same `chain_id`-bound structured-data domain (or equivalent) used for `BlockRejection::hash()` to the acceptance signature construction in `BlockAccepted`/`BlockResponse::accepted`, and thread `chain_id` into `NakamotoBlockHeader::signer_signature_hash()` (or a parallel signed digest) so `verify_signer_signatures` cannot accept a signature that was not produced for this specific network/chain context.

### Proof of Concept
Conceptual (not directly executable from indexed code alone):
1. Operate signer keys for two chain-id contexts (e.g., a mirrored/forked deployment) such that a block header with identical `(version, chain_length, burn_spent, consensus_hash, parent_block_id, tx_merkle_root, state_index_root, timestamp, miner_signature, pox_treatment)` can be produced on both.
2. Obtain a signer's `BlockAccepted` signature over `signer_signature_hash` from context A (e.g., testnet).
3. Replay the identical `(signer_signature_hash, signature)` pair as a `BlockAccepted`/header signature for context B (e.g., mainnet); `handle_block_signature` and `NakamotoBlockHeader::verify_signer_signatures` both accept it because neither checks `chain_id`, unlike `BlockRejection::verify`, which would reject a cross-`chain_id` replay via its structured-data domain.     /// This includes all fields _except_ the stacker signature.
    fn signer_signature_hash_inner(&self) -> Result<Sha512Trunc256Sum, CodecError> {
        let mut hasher = Sha512_256::new();
        let fd = &mut hasher;
        write_next(fd, &self.version)?;
        write_next(fd, &self.chain_length)?;
        write_next(fd, &self.burn_spent)?;
        write_next(fd, &self.consensus_hash)?;
        write_next(fd, &self.parent_block_id)?;
        write_next(fd, &self.tx_merkle_root)?;
        write_next(fd, &self.state_index_root)?;
        write_next(fd, &self.timestamp)?;
        write_next(fd, &self.miner_signature)?;
        write_next(fd, &self.pox_treatment)?;
        if Self::version_includes_problematic_txs(self.version) {
            write_next(fd, &self.problematic_txs)?;
        }
        Ok(Sha512Trunc256Sum::from_hasher(hasher))
    }
