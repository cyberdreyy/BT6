## Finding [1](#0-0) 

### Title
Stale confirmations from deleted multisig keys/members are counted toward the confirmation threshold, allowing a request to execute below the required K-of-N — (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
When a key (or member) is removed from the multisig via `DeleteKey`/`DeleteMember`, the contract only purges requests and confirmations that the *removed* key itself had **created**. Any confirmation that removed key had already cast on a request **created by someone else** is left untouched inside the `confirmations` set. A later confirmation from a still-live key can push the count over `num_confirmations`, so the request executes even though it never received `K` confirmations from currently-authorized members — mirroring the reported analog of a per-item authorization (`DelegateToken.approve`) surviving revocation of the broader authorization (`setApprovalForAll`).

### Finding Description
The confirmation-count binding the contract is supposed to enforce is:

`confirmations.len() >= num_confirmations` must equal `(number of *currently live* members who confirmed) >= num_confirmations`

`confirm()` simply inserts the caller's public key/member id into a `HashSet` stored per `request_id` and executes once the set size reaches the threshold: [2](#0-1) 

When a key is deleted via `MultiSigRequestAction::DeleteKey`, the cleanup logic only removes **requests whose `signer_pk` equals the deleted key** (i.e., requests that key *created*), together with the confirmations map for those specific request ids: [1](#0-0) 

It never scans the `confirmations` map for entries where the deleted key merely **confirmed** (but didn't create) another still-pending request. Those stale votes remain in the `HashSet` forever. The same pattern exists in `multisig2/src/lib.rs`'s `delete_member`, which filters outstanding requests by `r.member == member` (creator match only) and likewise never scrubs confirmations the deleted member cast on other members' requests: [3](#0-2) 

`assert_valid_request`/`confirm` also perform no re-validation that every public key already present in the stored `confirmations` set is still a currently active key of the account: [4](#0-3) 

So exactly like the external report — where `approve()` survives `setApprovalForAll(false)` and lets a de-authorized spender still pass `revertNotApprovedOrOperator` — a revoked multisig key's earlier "approval" (confirmation) survives its own key deletion and still counts toward `num_confirmations`.

### Impact Explanation
This directly breaks the "confirmations counted versus live members" equality: a `Transfer` or other `MultiSigRequestAction` can be executed with fewer than `K` confirmations from members who are actually authorized at execution time, because one (or more) of the counted confirmations belongs to a key/member that has since been deleted for being compromised or untrusted. This is explicitly a Critical-tier impact per the rules: "a multisig request executed below threshold." An attacker who obtained a compromised or soon-to-be-revoked key can pre-confirm a malicious pending request (e.g., a large `Transfer`) before the compromise is detected and their key deleted; the stale confirmation still counts, and once the remaining legitimate signers confirm normal requests, this poisoned request can cross the threshold and drain funds.

### Likelihood Explanation
This requires no privileged access beyond that already needed to be a (soon-to-be-removed) multisig key holder — which is the exact scenario key deletion is meant to defend against (compromised/departing signer). The flow is simple: confirm a pending request, get removed via `DeleteKey`/`DeleteMember` (the intended remediation step), and the stale confirmation remains counted with no additional action from the attacker. No owner/foundation cooperation is needed beyond the deletion itself, which is the normal, expected operational action taken in response to a suspected key compromise — the very case this cleanup logic is designed, but fails, to fully close.

### Recommendation
When executing `DeleteKey`/`DeleteMember`, iterate over **all** outstanding requests' confirmation sets (not just those the deleted key/member created) and remove the deleted key/member's entry from each. Alternatively, validate at `confirm()`/execution time that every key present in a request's confirmation set still corresponds to a currently active access key/member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with `num_confirmations = 3` and keys `A, B, C, D`.
2. Key `B` calls `add_request` with `MultiSigRequestAction::Transfer{...}` → `request_id = R`.
3. Key `A` calls `confirm(R)` → `confirmations[R] = {A}`.
4. Key `C` calls `confirm(R)` → `confirmations[R] = {A, C}` (2 < 3, not yet executed).
5. Members detect key `A` was compromised and submit/confirm a separate request `MultiSigRequestAction::DeleteKey{public_key: A}` with 3 confirmations from `B, C, D` — this executes and calls the cleanup at [1](#0-0) , which only removes requests **created by** `A` (none here) — `confirmations[R]` is untouched, still `{A, C}`.
6. Key `D` calls `confirm(R)` → `confirmations[R].len() == 3 >= num_confirmations` → the `Transfer` request executes, even though the deleted key `A`'s confirmation should no longer count, and only 2 currently-live keys (`C`, `D`) actually approved it.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
