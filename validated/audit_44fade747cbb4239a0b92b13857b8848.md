### Title
Duplicate transaction execution and double fee-charge within a single leader slot via `check_transaction_without_status_cache` ingestion path and status-cache-free aged-transaction commit path - ([File: runtime/src/bank/check_transactions.rs])

### Summary
`Bank::check_transaction_without_status_cache` is explicitly documented as skipping the status-cache "already processed" check and is used only in the banking-stage packet-ingestion path (`TransactionViewReceiveAndBuffer::handle_packet_batch_message`). Because the container built from this path deduplicates only nonce-like transactions and not ordinary blockhash transactions, an attacker who resubmits the identical signed transaction can get two separate entries admitted into the scheduler's container; the second entry, when later scheduled as an "aged" transaction, is committed via `Consumer::process_and_record_aged_transactions`, which revalidates only via `Bank::resanitize_transaction_minimally` — a function that never calls `check_status_cache`.

### Finding Description
`check_transaction_without_status_cache` is documented as leader-only and deliberately omits the status-cache check [1](#0-0) . It is invoked from `TransactionViewReceiveAndBuffer::handle_packet_batch_message` to admit a transaction into the priority-queue container [2](#0-1) . The only duplicate-suppression logic in this ingestion path is nonce-specific (`drop_incoming_nonce_tx`) [3](#0-2) ; a plain blockhash-based transaction resubmitted byte-for-byte is not deduplicated and is inserted into the container again via `container.insert_map_only(state)` [4](#0-3) .

Once queued, transactions dequeued by the scheduler as "aged" work are committed through `Consumer::process_and_record_aged_transactions`, whose pre-results come from `bank.resanitize_transaction_minimally(...)`, not from `bank.check_transactions` [5](#0-4) . `resanitize_transaction_minimally` only checks vote-only-bank status, reserved-key changes across an epoch boundary, and ALT expiration — it never touches the status cache [6](#0-5) . The only per-batch duplicate protection is `try_lock_accounts_with_results`, which rejects a duplicate message hash *within the same batch* only [7](#0-6) ; it provides no protection across two different batches processed sequentially by workers.

By contrast, `Consumer::process_and_record_transactions` (used for "fresh" transactions) does call the full `bank.check_transactions`, which internally invokes `check_status_cache` [8](#0-7) [9](#0-8) . The test `test_check_transaction_without_status_cache_allows_already_processed` explicitly documents that `check_transaction_without_status_cache` returns `Ok(None)` for a transaction the full `check_transactions` would reject as `AlreadyProcessed` [10](#0-9) .

Exploit flow: attacker sends identical signed transaction T twice over QUIC within the same slot. Both copies pass `check_transaction_without_status_cache` (no dedup for non-nonce blockhash transactions) and land in the container as two entries. The first entry is scheduled, executes, commits, and updates the status cache. If the second entry is scheduled to the "aged" path afterward within the same slot, it is only checked via `resanitize_transaction_minimally` (no status-cache check) before being locked and executed again, resulting in a second fee charge and duplicate execution before any bank has recorded/enforced `AlreadyProcessed` against that second attempt.

### Impact Explanation
Concrete impact: an unprivileged attacker can cause a transaction to be executed and fees charged twice against the same fee payer within a single slot, without any additional signature or privileged access — a replay/double-charge issue matching the "REPLAY_LIVENESS" / duplicate-execution bounty category (fee double-charge, duplicate execution of an already-processed transaction).

### Likelihood Explanation
Preconditions are within reach of an unprivileged attacker: connect to TPU over QUIC and resend the same signed transaction bytes twice within the same leader slot, timed so that the second copy is picked up by the aged/resanitize commit path rather than being blocked by the status cache. Feasibility depends on scheduler/container timing (whether the container truly holds two live entries for a non-nonce duplicate, and whether the scheduler dispatches the second copy to the aged path before the slot ends) — this timing window was identified in the code but not verified end-to-end via a running scheduler/consume-worker integration test, so the exact repeatability window is uncertain without further dynamic testing.

### Recommendation
Add duplicate-message-hash detection in `TransactionViewReceiveAndBuffer::handle_packet_batch_message` for non-nonce transactions (not just nonce-like ones), so a resubmitted identical transaction is dropped or coalesced at ingestion. Additionally, have `Bank::resanitize_transaction_minimally` (or its caller `process_and_record_aged_transactions`) re-run `check_status_cache` before locking/executing aged transactions, matching the safety guarantee already provided by `process_and_record_transactions`/`check_transactions`.

```rust
// runtime/src/bank/check_transactions.rs (add near existing test)
#[test]
fn test_aged_path_skips_status_cache() {
    let (genesis_config, _mint_keypair) = solana_genesis_config::create_genesis_config(1);
    let bank = Bank::new_for_tests(&genesis_config);
    let tx = make_test_tx_with_blockhash(TransactionVersion::LEGACY, bank.last_blockhash());

    // Simulate first commit having already recorded the tx in the status cache.
    bank.status_cache.write().unwrap().insert(
        tx.recent_blockhash(),
        tx.message_hash(),
        bank.slot(),
        Ok(()),
    );

    // Full check correctly rejects replay.
    let mut ec = TransactionErrorMetrics::default();
    let full_check = bank.check_transactions(
        std::slice::from_ref(&tx),
        &[Ok(())],
        bank.max_processing_age(),
        true,
        &mut ec,
    );
    assert!(matches!(full_check.as_slice(), [Err(TransactionError::AlreadyProcessed)]));

    // The "aged"/minimal resanitize path used by process_and_record_aged_transactions
    // does not consult the status cache at all, so it would allow re-execution.
    let resanitize_result =
        bank.resanitize_transaction_minimally(&tx, bank.epoch(), bank.slot());
    assert_eq!(resanitize_result, Ok(())); // no AlreadyProcessed rejection
}
```
This test demonstrates that the code path used for aged/scheduled transactions (`resanitize_transaction_minimally`) has no equivalent of the `AlreadyProcessed` rejection that the full `check_transactions`/`check_status_cache` path enforces, confirming the gap described above.

```rust
        &self,
        tx: &impl SVMMessage,

            error_counters,
```

```rust
    pub fn try_lock_accounts_with_results(
        &self,
        txs: &[impl TransactionWithMeta],
        tx_results: impl Iterator<Item = Result<()>>,
    ) -> Vec<Result<()>> {
        let tx_account_lock_limit = self.get_transaction_account_lock_limit();

        // we must fail transactions that duplicate a prior message hash
        let mut batch_message_hashes = AHashSet::with_capacity(txs.len());
        let tx_results = tx_results
            .enumerate()
            .map(|(i, tx_result)| match tx_result {

                    // `HashSet::insert()` returns `true` when the value does *not* already exist

                        Ok(())

                        Err(TransactionError::AlreadyProcessed)
```

```rust
    pub fn resanitize_transaction_minimally(
        &self,
        transaction: &impl TransactionWithMeta,
        sanitized_epoch: Epoch,
        alt_invalidation_slot: Slot,
    ) -> Result<()> {
        if self.vote_only_bank() && !vote_parser::is_valid_vote_only_transaction(transaction) {
            return Err(TransactionError::SanitizeFailure);
        }

        // If the transaction was sanitized before this bank's epoch,
        // additional checks are necessary.
        if self.epoch() != sanitized_epoch {
            // Reserved key set may have changed, so we must verify that
            // no writable keys are reserved.
            self.check_reserved_keys(transaction)?;

            for instr in transaction.instructions_iter() {
                if instr.accounts.len() > solana_transaction_context::MAX_ACCOUNTS_PER_INSTRUCTION {
                    return Err(solana_transaction_error::TransactionError::SanitizeFailure);
                }
            }
        }

        if self.slot() > alt_invalidation_slot {
            // The address table lookup **may** have expired, but the
            // expiration is not guaranteed since there may have been
            // skipped slot.
            // If the addresses still resolve here, then the transaction is still
            // valid, and we can continue with processing.
            // If they do not, then the ATL has expired and the transaction
            // can be dropped.
            let (_addresses, _deactivation_slot) =
                self.load_addresses_from_ref(transaction.message_address_table_lookups())?;
        }

        Ok(())
    }
```
