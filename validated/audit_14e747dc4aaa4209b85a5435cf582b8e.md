### Title
Missing owner enforcement in `handleSecretsDelete` allows cross-owner secret deletion via unset `Owner` field - ([File: core/capabilities/vault/gw_handler.go])

### Finding Description
`GatewayHandler.handleSecretsList` (line 343) explicitly overwrites the client-supplied owner before forwarding to the secrets service: [1](#0-0) 

By contrast, `GatewayHandler.handleSecretsDelete` unmarshals the raw request params directly into `vaultcommon.DeleteSecretsRequest` and forwards it straight to `h.secretsService.DeleteSecrets(ctx, r)` with **no equivalent line forcing an owner/authorized-scope field from `authResult`**: [2](#0-1) 

Note that `handleSecretsDelete` in `HandleGatewayMessage`'s dispatch does not even receive the `authResult` parameter that `handleSecretsList` receives: [3](#0-2) 

Upstream in `GatewayVaultRequestProcessor.processDeleteSecretsRequest`, the delete request's identifiers go through `vaultutils.ApplySecretIdentifierNamespaceDefaults(deleteReq.Ids)`, which only fills in *empty* namespace/owner fields with defaults — it does not force-overwrite an attacker-supplied, non-empty owner/namespace value to match `authResult.AuthorizedOwner()`, the way `processListSecretIdentifiersRequest`'s `authorizeAndStamp` callback does for the list request's top-level `Owner`: [4](#0-3) 

The processor's documented invariant claims payload owners are validated against the authorized owner during `AuthorizeRequest`: [5](#0-4) 

However, I was unable to fully verify from the retrieved code whether `Authorizer.AuthorizeRequest` (in `core/capabilities/vault/authorizer.go`) actually performs a per-secret-identifier owner equality check for delete requests (as opposed to only validating the caller's DON/workflow-level authorization), since that file's contents were not fully inspected in this session. This is a material gap: if `AuthorizeRequest` only authorizes "this caller is a valid owner for some workflow" rather than "every `Ids[i].Owner`/namespace in this delete request equals `AuthorizedOwner()`", then the asymmetry described above is directly exploitable — an attacker authorized as owner A can submit `vault.secrets.delete` with `Ids` referencing owner B's namespace, and `handleSecretsDelete` will forward them to `SecretsService.DeleteSecrets` unmodified.

### Impact Explanation
If confirmed exploitable, this allows an authorized-but-unprivileged workflow owner to delete another owner's vault secrets by supplying identifiers scoped to a different owner/namespace in the `vault.secrets.delete` request, since no code path forces the identifiers to be re-scoped to the caller's authorized owner (unlike the list path). This is a destructive cross-tenant action (unauthorized secret deletion), a serious SECRET_CONFINEMENT violation, matching a "cross-user unauthorized action on another user's secret / disclosure-adjacent" impact class.

### Likelihood Explanation
Requires only a valid, unprivileged owner authorization (precondition already satisfied by any legitimate workflow owner/DON caller reaching the gateway) — no elevated privileges are needed beyond what's needed to submit any vault write request. Exploitability hinges entirely on whether `authorizer.AuthorizeRequest` enforces per-identifier owner matching for delete requests, which could not be conclusively confirmed with the available context.

### Recommendation
In `GatewayHandler.handleSecretsDelete`, explicitly force every identifier's owner/namespace (and any top-level owner field on `DeleteSecretsRequest`) to `authResult.AuthorizedOwner()` before calling `h.secretsService.DeleteSecrets`, mirroring the pattern already used in `handleSecretsList` (`r.Owner = authResult.AuthorizedOwner()`). Additionally, pass `authResult` into `handleSecretsDelete`'s signature (it is currently omitted from the dispatch call) so this enforcement is possible, and add a defensive check inside `SecretsService.DeleteSecrets`/`ValidateDeleteSecretsRequest` that rejects any identifier whose owner does not match the authorized caller, independent of the gateway/node-handler code path.

### Proof of Concept
Go handler-level test plan in `core/capabilities/vault/gw_handler_test.go`:
1. Construct a `GatewayHandler` with a mock `Authorizer` that returns `AuthResult{owner: "ownerA"}` for any authenticated request.
2. Build a `vault.secrets.delete` JSON-RPC request whose `DeleteSecretsRequest.Ids` reference `Owner/Namespace: "ownerB"`.
3. Call `HandleGatewayMessage` and inspect the `*vaultcommon.DeleteSecretsRequest` argument passed to a mocked `vaulttypes.SecretsService.DeleteSecrets` (via `vaulttypes/mocks`).
4. Assert whether the mock receives `Ids` still scoped to `"ownerB"` (vulnerable) or forcibly rewritten to `"ownerA"` (safe) — mirror this assertion against `handleSecretsList`, which is expected to always rewrite `r.Owner` to `"ownerA"` regardless of client input, exposing the asymmetry.
5. Cross-check by also unit-testing `Authorizer.AuthorizeRequest` directly with mismatched-owner delete params to determine whether it independently rejects the request before reaching `handleSecretsDelete`.

func (h *GatewayHandler) handleSecretsDelete(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.DeleteSecretsRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized delete secrets request", "request", r.String())
	resp, err := h.secretsService.DeleteSecrets(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to delete secrets: %w", err))
	}

	resultBytes, err := resp.ToJSONRPCResult()
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&resultBytes),
	}
}

func (p *GatewayVaultRequestProcessor) processListSecretIdentifiersRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
) (*AuthorizedGatewayVaultRequest, error) {
	if req.Params == nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: errors.New("request params must not be nil")}
	}

	var listReq vaultcommon.ListSecretIdentifiersRequest
	if err := json.Unmarshal(*req.Params, &listReq); err != nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
	}
	if p.stripOwnerPrefixForAuth {
		listReq.RequestId = req.ID
		if err := marshalVaultParams(req, &listReq); err != nil {
			return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
		}
	} else {
		listReq.RequestId = coalesceRequestID(listReq.RequestId, req.ID)
	}

	if err := p.validator.ValidateListSecretIdentifiersRequest(ctx, &listReq); err != nil {
		return nil, p.validationError(req, err)
	}

	return p.authorizeAndStamp(ctx, req, func(prefixedRequestID string) error {
		listReq.RequestId = prefixedRequestID
		if listReq.Namespace == "" {
			listReq.Namespace = vaulttypes.DefaultNamespace
		}
		return marshalVaultParams(req, &listReq)
	})
