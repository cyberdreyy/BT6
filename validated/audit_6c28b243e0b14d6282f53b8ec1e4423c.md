### Title
Malicious/compromised curve admin can front-run a borrower's `lending_account_borrow` to inflate `protocol_origination_fee` with no user-specified cap - (File: programs/marginfi/src/instructions/marginfi_account/borrow.rs)

### Summary
`lending_account_borrow` fetches `bank.config.interest_rate_config.protocol_origination_fee` at execution time and applies it directly to the unprivileged borrower's transaction with no maximum-fee parameter supplied by the user, no slippage/consent check, and no timelock on the admin-controlled fee value. This is the same bug class as Teller Finance's M-10 (`lenderAcceptBid` reading a mutable marketplace fee at execution time).

### Finding Description
In `lending_account_borrow`, the origination fee rate is read live from bank state right before it's applied to the borrower's principal: [3](#0-2) 

This `protocol_origination_fee` field is mutable at any time via `lending_pool_configure_bank_interest_only`, callable by either the group `admin` or the scoped `delegate_curve_admin` role, with immediate effect (no delay unless `FREEZE_SETTINGS` is set, which is itself admin-controlled and can be toggled): [4](#0-3) 

Because Solana transactions can be observed in the mempool/leader schedule before landing, a malicious or compromised `delegate_curve_admin`/`admin` can observe a pending `lending_account_borrow` transaction and submit a `lending_pool_configure_bank_interest_only` transaction (or the equivalent through `LendingPoolConfigureBank`) raising `protocol_origination_fee` so it lands first, causing the borrower's transaction to be charged a higher fee than they intended when they signed it — exactly the Teller M-10 pattern of a privileged party changing a fee parameter that an in-flight unprivileged user transaction consumes without any user-side cap.

The `lending_account_borrow` instruction takes only an `amount` parameter — the borrower never gets to specify the maximum fee rate they're willing to accept: [5](#0-4) 

### Impact Explanation
A borrower can be charged an arbitrarily higher origination fee than expected (bounded only by `InterestRateConfigOpt::validate()` sanity limits, not by any per-transaction user consent). This constitutes value extraction from an unprivileged user by a privileged-but-scoped role without requiring full group-admin compromise — the `delegate_curve_admin` role exists specifically to be delegated to a separate party (e.g. a rate committee) with narrower trust assumptions than full admin, per the permissions documentation. [6](#0-5) 

### Likelihood Explanation
Requires control of the `delegate_curve_admin` (or `admin`) key and the ability to observe/front-run a specific pending borrow transaction — a real but bounded threat model (compromised or malicious delegated key), consistent with the original Teller finding where a market owner (a privileged-but-limited role) could exploit borrowers.

### Recommendation
Add a `max_origination_fee` (or similar max-fee bound) parameter to `lending_account_borrow` that the borrower signs, and revert if the live `protocol_origination_fee` exceeds it at execution time. Alternatively, introduce a timelock/delay for any change to `protocol_origination_fee` (and other borrower-facing fee fields) via `lending_pool_configure_bank_interest_only`/`LendingPoolConfigureBank`, so in-flight borrow transactions cannot be front-run by a fee increase.

### Proof of Concept
1. Group `admin` sets `delegate_curve_admin` to an untrusted or later-compromised key.
2. Borrower submits `lending_account_borrow` for a given `amount`, expecting the currently-published `protocol_origination_fee` (e.g. 0%).
3. Before the borrower's transaction lands, `delegate_curve_admin` submits `lending_pool_configure_bank_interest_only` raising `protocol_origination_fee` to a much higher value (bounded only by validation limits).
4. If the admin's transaction lands first, the borrower's subsequent `lending_account_borrow` call computes `origination_fee` using the new, higher rate [7](#0-6) , causing the borrower to incur more debt/fee than they agreed to when signing the transaction.

pub fn lending_pool_configure_bank_interest_only(
    ctx: Context<LendingPoolConfigureBankInterestOnly>,
    interest_rate_config: InterestRateConfigOpt,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;
    msg!(
        "Configuring bank: {:?} mint: {:?}",
        ctx.accounts.bank.key(),
        bank.mint
    );

    // If settings are frozen, interest rates can't update.
    if bank.get_flag(FREEZE_SETTINGS) {
        msg!("WARN: Bank settings frozen, did nothing.");
    } else {
        bank.config
            .interest_rate_config
            .update(&interest_rate_config);
        bank.config.interest_rate_config.validate()?;
        msg!("Bank configured!");
    }

    Ok(())
}
