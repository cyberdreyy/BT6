## #Vulnerability found

### Title
Lockup Factory lets caller inject an arbitrary `whitelist_account_id`, letting an attacker deploy a "trusted" lockup whose staking-pool whitelist check is fully attacker-controlled - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` accepts a caller-supplied, optional `whitelist_account_id` and, when present, bakes it directly into the deployed lockup contract's `staking_pool_whitelist_account_id` field instead of forcing the factory's own vetted whitelist. This is the same bug class as the reported Uniswap-style `Uniproxy.depositSwap` issue: a trust-anchor address (there: `_router`; here: the staking-pool whitelist) is supplied by the caller instead of coming from a fixed, trusted storage value, letting the caller substitute a "fake" contract that the victim (the lockup owner) will implicitly trust.

### Finding Description
`create` is unprivileged/callable by anyone with the minimum attached deposit: [1](#0-0) 

The `staking_pool_whitelist_account_id` used to initialize the new lockup is taken from the caller argument `whitelist_account_id` when supplied, only falling back to the factory's own address otherwise: [2](#0-1) 

The lockup contract's `new()` only checks that this value is a *syntactically valid* account ID — it never checks that it is the NEAR Foundation's real whitelist: [3](#0-2) 

That value is stored as `staking_pool_whitelist_account_id` and later used, unconditionally trusted, whenever the lockup owner calls `select_staking_pool`: [4](#0-3) 

The whole point of this call is documented in the whitelist contract's own README: only whitelisted staking pools are supposed to be trustable because "the staking pool should guarantee that the delegated tokens can not be lost or locked ... In order to enforce this, only approved (whitelisted) accounts of staking pool contracts can receive delegated tokens from lockup contracts." [5](#0-4) 

Because `create` lets the caller pick this "trust anchor" freely, an attacker can deploy a lockup where `is_whitelisted()` is served by a contract the attacker fully controls (e.g., one that always returns `true`), completely defeating the safety guarantee that the whitelist is supposed to provide, exactly analogous to letting `_router` be attacker-supplied in the reported Solidity bug.

### Impact Explanation
This falls squarely under the explicitly listed Critical impact: "a wrongly whitelisted or wrongly parameterised deployment." Once such a lockup is deployed:
- The owner (who may reasonably assume `select_staking_pool` enforces the Foundation-vetted whitelist, since that's the documented guarantee of the whole system) will have any staking pool account ID accepted as "whitelisted," including one that never returns delegated NEAR (`deposit_and_stake`/`withdraw` simply never honored).
- All NEAR later delegated by that lockup's owner through `deposit_to_staking_pool`/`deposit_and_stake` can be permanently routed to and frozen/stolen by an attacker-controlled "staking pool," because the on-chain safety check (`is_whitelisted`) that was supposed to gate this action is attacker-controlled from the moment of lockup creation.

### Likelihood Explanation
Likelihood is high for the mechanism itself: any unprivileged account can call `create` with a custom `whitelist_account_id` right now, with no additional authorization — the `create_lockup_with_custom_whitelist_success` test in the same package demonstrates the parameter is fully functional: [6](#0-5) 

The realistic exploitation path (someone accepting a lockup deployment from an untrusted "lockup provisioning" flow, or a phishing scenario where a victim is told to use a particular factory-like frontend) requires social packaging but no additional protocol-level privilege — the contract itself offers no protection whatsoever against a caller substituting the whitelist trust anchor.

### Recommendation
Remove the `whitelist_account_id` parameter from `LockupFactory::create` (or, if custom whitelists must be supported, restrict who may specify them, e.g., only the Foundation-controlled `foundation_account_id`), and always initialize new lockups with the factory's own `self.whitelist_account_id` storage value, mirroring the recommended fix for the Uniproxy report (use a storage value set at construction, not a caller-supplied parameter).

### Proof of Concept
1. Attacker deploys a minimal "fake whitelist" contract exposing `is_whitelisted(staking_pool_account_id) -> bool` that always returns `true`.
2. Attacker (or an unsuspecting funder) calls `lockup-factory::create` with `owner_account_id = victim`, `whitelist_account_id = Some(fake_whitelist_account)`, and the minimum attached deposit — see `LockupFactory::create` at `lockup-factory/src/lib.rs:107-134` — which is invoked with no `assert_owner`/foundation check.
3. The resulting lockup contract is initialized (`lockup/src/lib.rs:180-207`) with `staking_pool_whitelist_account_id = fake_whitelist_account`.
4. Victim owner later calls `select_staking_pool(attacker_pool)` (`lockup/src/owner.rs:12-41`); the cross-contract call to `fake_whitelist_account::is_whitelisted` returns `true` unconditionally, so `on_whitelist_is_whitelisted` accepts the attacker's pool as legitimate.
5. Victim deposits/stakes NEAR into `attacker_pool` via `deposit_and_stake`; the attacker's pool contract never honors `withdraw`, permanently freezing/stealing the delegated NEAR.
