## Title
Truncated index in `MerkleStorageInvalidator.takerInteraction` lets an unprivileged taker spoof the stored fill-progress index and unlock a full-order escrow with an already-revealed early secret - (File: `contracts/MerkleStorageInvalidator.sol`)

### Summary
The multiple-fills mechanism binds a Merkle-proven secret index to the fraction of the order being filled via `_isValidPartialFill`. The Merkle-leaf hash is computed from a **truncated** `uint64(idx)`, while the value persisted for downstream authorization (`lastValidated[key].index`) uses the **full untruncated `uint256 idx`**. Because `idx` is fully attacker-controlled calldata, an unprivileged taker can add any multiple of `2^64` to a genuine, already-public index and still pass Merkle-proof verification, while making the stored `validated.index` equal to whatever value is required to satisfy the full-order-completion check in `_isValidPartialFill`. This is the same root cause described in the report: a value that is supposed to be constrained/bound to a specific narrow domain (the SMT `rkeyBit`, here the on-chain `idx`) is left unconstrained across two different consumers of that value (the proof-hash computation vs. the persisted authorization state), letting the attacker "fake the binding" between the proven leaf and the state that gates fund release.

### Finding Description
`MerkleStorageInvalidator.takerInteraction` decodes taker-supplied calldata (`TakerData.idx` is `uint256`) and: [1](#0-0) 

```
uint240 rootShortened = uint240(uint256(extraDataArgs.hashlockInfo));
bytes32 key = keccak256(abi.encodePacked(orderHash, rootShortened));
bytes32 rootCalculated = takerData.proof.processProofCalldata(
    keccak256(abi.encodePacked(uint64(takerData.idx), takerData.secretHash))
);
if (uint240(uint256(rootCalculated)) != rootShortened) revert InvalidProof();
lastValidated[key] = ValidationData(takerData.idx + 1, takerData.secretHash);
```

The leaf hash used for Merkle-proof verification only depends on `uint64(takerData.idx)` (the low 64 bits), but the value stored for later authorization is `takerData.idx + 1` (the full 256-bit value). Because indices in the tree are always small (`partsAmount` is derived from a 16-bit field, see `BaseEscrowFactory._postInteraction`), any legitimate `(index, hashedSecret)` pair from the fully-public Merkle tree — which every resolver already possesses per the project's own documentation ("Each Resolver has a copy of the created Merkle tree") — can be replayed with `idx = realIndex + k·2^64` for an attacker-chosen `k`. The truncated hash still matches the real leaf and the proof still verifies against the root, but the persisted `lastValidated[key].index` becomes `realIndex + k·2^64 + 1`, a value fully controlled by the attacker.

This stored `validated.index` is the sole "proof of fill progress" trusted by `_isValidPartialFill`: [2](#0-1) 

An attacker can therefore pick `k` so that `validated.index` satisfies `calculatedIndex + 2 == validatedIndex` (the full-completion branch) while only presenting the earliest, publicly-known leaf `hashedSecrets[0]` — the secret index intended to gate only the first small percentage of the fill. `BaseEscrowFactory._postInteraction` will then create the source escrow with `hashlock = validated.leaf = hashedSecrets[0]` but `immutables.amount = makingAmount` equal to the *entire order amount*: [3](#0-2) 

Per the project's own README, the first-tranche secret is the earliest one revealed/leaked during normal operation (and can also be recovered from the `EscrowDst.publicWithdraw` event as documented). Consequently, once that early secret becomes known (as intended, for the small partial fill), it can be used to withdraw the *entire* order amount from an escrow that was fraudulently created for the full amount but gated by that early, already-exposed hashlock — completely bypassing the progressive-reveal invariant that the Merkle multi-fill design exists to enforce.

### Impact Explanation
This breaks the core invariant of the multi-fill mechanism: that the amount unlockable by a given secret is proportional to that secret's index. By forging the stored index, an unprivileged taker can bind the *entire* order's funds to a hashlock whose preimage is already or will soon be publicly known (as part of the normal, documented reveal flow), enabling direct theft of the full escrowed amount rather than only the fraction the early secret was meant to authorize. This is a Critical impact under the bounty scope: direct theft of user (maker) funds at rest via a live, production, unprivileged code path (`fillOrderArgs` → `_postInteraction` → `takerInteraction`).

### Likelihood Explanation
The `idx` field is directly taker-supplied calldata with no additional constraint tying it to the low-64-bit domain used for hashing; the Merkle tree (all leaves/indices) is publicly distributed to every resolver by design, so no privileged knowledge is required — only arithmetic to choose `k`. This makes the attack straightforward and fully reachable by any unprivileged taker participating in the standard order-fill flow.

### Recommendation
Constrain `idx` to the same domain used in the leaf-hash computation before persisting it, e.g. validate `takerData.idx <= type(uint64).max` (revert otherwise), or consistently use the same width (`uint64`) both for leaf hashing and for the value stored in `lastValidated`, eliminating any truncation mismatch between the two usages of `idx`.

### Proof of Concept
1. Attacker (any taker) obtains the fully-public Merkle tree of `(index, hashedSecret)` pairs for an order that allows multiple fills (already available to all resolvers per design).
2. Attacker computes the `idx` value required so that `validated.index == calculatedIndex + 2` for a 100%-fill scenario, using `idx = 0 + k * 2^64 - 1` where `k` is chosen to hit the exact target index for full completion, and `secretHash = hashedSecrets[0]`.
3. Attacker calls `fillOrderArgs` with `makingAmount = order.makingAmount` (full order) and interaction data `(proof0, idx, hashedSecrets[0])`.
4. `takerInteraction` verifies `keccak256(abi.encodePacked(uint64(idx), hashedSecrets[0]))` against `proof0` and the root — this succeeds since `uint64(idx) == 0`, matching the genuine leaf 0.
5. `lastValidated[key]` is set to `(idx + 1, hashedSecrets[0])`, an attacker-chosen large value.
6. `_postInteraction` computes `_isValidPartialFill(..., validated.index)` which returns `true` because `validated.index` was crafted to equal `calculatedIndex + 2`.
7. `EscrowSrc` is deployed funded with the **full** order amount but hashlock `hashedSecrets[0]`.
8. Once the secret for index 0 is revealed (as intended for the small first tranche, or leaked via the `publicWithdraw` event as documented), it unlocks withdrawal of the **entire** escrowed amount, not just the fraction it was meant to authorize. [4](#0-3)

```text
    function _isValidPartialFill(
        uint256 makingAmount,
        uint256 remainingMakingAmount,
        uint256 orderMakingAmount,
        uint256 partsAmount,
        uint256 validatedIndex
    ) internal pure returns (bool) {
        uint256 calculatedIndex = (orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount / orderMakingAmount;

        if (remainingMakingAmount == makingAmount) {
            // If the order is filled to completion, a secret with index i + 1 must be used
            // where i is the index of the secret for the last part.
            return (calculatedIndex + 2 == validatedIndex);
        } else if (orderMakingAmount != remainingMakingAmount) {
            // Calculate the previous fill index only if this is not the first fill.
            uint256 prevCalculatedIndex = (orderMakingAmount - remainingMakingAmount - 1) * partsAmount / orderMakingAmount;
            if (calculatedIndex == prevCalculatedIndex) return false;
        }

        return calculatedIndex + 1 == validatedIndex;
    }
```
