### Title
Multisig request executes with confirmations from deleted keys, bypassing the live-key K-of-N threshold - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig/src/lib.rs` counts every public key ever inserted into a request's `confirmations` set, without revalidating that each confirming key is still a live access key on the multisig account at execution time. `DeleteKey` only purges requests and confirmations *authored* by the deleted key, not confirmations that key placed on other, still-pending requests. This lets a request execute using a mix of live and already-revoked confirmations, breaking the intended "K distinct, currently-authorized keys" invariant — directly analogous to the Ajna report's core defect: a numeric threshold check that silently drifts from the real-world entity set it's supposed to represent (there: vote percentage vs. shrinking non-treasury base; here: confirmation count vs. shrinking live-key set).

### Finding Description
The intended custody binding for the multisig is:

`confirmations from members that are currently valid access keys on the account >= num_confirmations`

The actual implementation checks:

`confirmations.len() (all public keys ever inserted for this request_id) >= num_confirmations` [1](#0-0) 

When a `DeleteKey` action is executed, the cleanup logic only removes **requests and confirmation sets whose original signer (`signer_pk`) is the deleted key** — i.e. requests that key itself created via `add_request`: [2](#0-1) 

It does **not** scan other pending requests' `confirmations` HashSets to strip out entries belonging to the deleted key. `assert_valid_request` also performs no live-membership check on the historical confirmers — it only checks that the request exists and the caller routes through the multisig account: [3](#0-2) 

So a stale confirmation from a key that was later revoked remains permanently counted toward that request's threshold.

### Impact Explanation
This falls under the Critical bucket "a multisig request executed below threshold." A pending, unrelated request can accumulate a confirmation from a key that is subsequently deleted (via a separate, legitimately-confirmed `DeleteKey` request), and later be pushed over `num_confirmations` and executed using fewer live/current keys than the configured threshold actually requires — e.g. any privileged action (`Transfer`, `AddKey`, `FunctionCall`, etc.) can be executed with effectively `num_confirmations - 1` live signers instead of `num_confirmations`.

### Likelihood Explanation
No owner, foundation, or victim key compromise is needed — this only requires an ordinary sequence of legitimate multisig operations (two concurrently pending requests, one of which deletes a key that had confirmed the other). Any of the multisig's own key holders acting adversarially (or simply key rotation happening at an inopportune time) can trigger it, since the confirmation bookkeeping is never reconciled against currently valid keys.

### Recommendation
When executing `DeleteKey` (or an equivalent member-removal action in `multisig2`), iterate over all pending requests' `confirmations` sets and remove the deleted public key from each, not just from requests it authored. Alternatively, revalidate at `confirm()`/execution time that every public key in the `confirmations` set is still a currently valid access key on the account before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` and add 4 full-access keys: `A, B, C, D` (K=3 of N=4).
2. `A` calls `add_request_and_confirm(R1)` for a `Transfer` request → `confirmations(R1) = {A}`.
3. `B` calls `confirm(R1)` → `confirmations(R1) = {A, B}` (2 < 3, not yet executed).
4. Separately, `A` calls `add_request_and_confirm(R2)` with action `DeleteKey{public_key: B}`; `C` and `D` confirm R2, reaching 3 confirmations → R2 executes, `B`'s key is deleted from the account. `execute_request`'s `DeleteKey` branch only clears requests where `signer_pk == B` (none, since B never authored a request here), so `confirmations(R1)` is untouched and still contains `B`.
5. `C` calls `confirm(R1)` → `confirmations(R1).len() + 1 = 3 >= num_confirmations (3)` → R1 executes, even though `B`'s key no longer exists on the account and only `A` and `C` are live confirming keys. [4](#0-3) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
