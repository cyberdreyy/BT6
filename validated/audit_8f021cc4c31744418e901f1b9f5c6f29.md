### Title
Stale per-epoch instant-withdraw receipts are excluded from default-recovery accounting and become permanently unfundable - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug binds a resource's cleanup to the wrong lifetime, leaving a stale pointer (`drm_connector.ddc` → freed I2C adapter). The analog in idle-tranches is a stale per-epoch receipt reference: instant-withdraw receipts are tracked per request epoch (`instantWithdrawsRequestsByEpoch[user][epoch]`), but default recovery accounting only ever looks at the epoch that is current *at finalization* (`instantWithdrawClaimsByEpoch[epochNumber]` / `defaultRecoveryEpoch`). Unfunded instant receipts created in an earlier epoch keep contributing to `pendingInstantWithdraws` and `instantWithdrawsRequests[user]` — the "dangling" aggregate — while no epoch-keyed entry remains that recovery can resolve them through. After `finalizeDefault`, they can neither be haircut-paid from the reserve nor paid at par, because `_transferFundedClaim` forbids spending the reserve. They are permanently frozen.

### Finding Description
`requestInstantWithdraw` records receipts under the *current* epoch key: `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` (IdleCreditVault.sol:367-372). Funding is aggregate: `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` (IdleCreditVault.sol:398-403) — the per-epoch keys are never touched, so a partially funded instant queue leaves the old epoch's claim basis intact while `epochNumber` later advances in `deposit` during `stopEpoch` (IdleCreditVault.sol:607-611).

On default finalization:
- `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *finalization* epoch — when `pendingInstantWithdraws != 0` (IdleCreditVault.sol:644-649). Receipts keyed to an older epoch contribute nothing to `totalBasis`, so no reserve is allocated to them.
- `_defaultPrefundedInstantReserve` likewise only credits `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` (IdleCreditVault.sol:716-723); cash already held for the stale receipts is not reserved.
- `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (IdleCreditVault.sol:842-856), so the stale remainder stays in `instantWithdrawsRequests[_user]`.
- The remainder then falls through to `_transferFundedClaim` (IdleCreditVault.sol:387-392), which reverts when `balance - defaultRecoveryReserve < amount` (IdleCreditVault.sol:899-905). Post-default there is no funding path left (`epochDuration = 0`, `epochEndDate = 0`, no further `stopEpoch`), so the receipt is frozen forever.

Concretely: buffer of epoch N — user A instant-requests 100. `startEpoch` partially funds the instant queue (borrower cash short: `pendingInstant > totUnderlyings`, early return at IdleCDOEpochVariant.sol:286-289) leaving 40 pending. Epoch N+1 runs and stops; `epochNumber` is now N+1. Borrower defaults during epoch N+1 and `finalizeDefault` runs. A's 40-claim lives under epoch key N, but only `instantWithdrawClaimsByEpoch[N+1]` enters the basis. A's receipt receives zero recovery allocation and can never be claimed: the haircut path misses it (wrong epoch key) and the par path reverts on the reserve guard.

### Impact Explanation
Permanent freezing of user funds: an unprivileged lender's unfunded instant-withdraw receipt becomes unclaimable after default finalization, with loss equal to the unfunded receipt amount (the full 40 in the example). The reserve guard that protects recovery claimants simultaneously dooms the orphaned receipt, mirroring the kernel bug's stale `ddc` pointer — the aggregate `instantWithdrawsRequests`/`pendingInstantWithdraws` still "references" a receipt that the per-epoch recovery structures no longer can resolve. If residual non-reserve balance does exist, the stale receipt instead pays at *par*, ahead of haircutted default claimants — a fairness/insolvency leak of the same root cause.

### Likelihood Explanation
Requires: instant withdrawals enabled (`disableInstantWithdraw = false`), an APR drop triggering instant requests, a `startEpoch` where contract cash is insufficient to fund the whole instant queue (leaving `pendingInstantWithdraws > 0`), and a subsequent borrower default. All steps use only honest manager calls plus ordinary unprivileged user requests; the sequence is realistic whenever the borrower is slow to top up instant liquidity. No attacker control is needed — the victim is the requester.

### Recommendation
Resolve stale instant receipts by aggregate, not by current-epoch key: either track a single unfunded-instant claim basis (or iterate `instantWithdrawClaimsByEpoch` over all epochs with nonzero `pendingInstantWithdraws`) when computing `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, and make `_claimDefaultedInstantWithdrawRequest` clear the user's entire remaining `instantWithdrawsRequests` at `defaultRecoveryPrice` rather than only the `defaultRecoveryEpoch` slice.

### Proof of Concept
Foundry fork sequence (against `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
// setup: instant withdraws enabled, epoch N running and stopped normally,
//        epochNumber == N in buffer
vm.prank(lp);
cdoEpoch.requestWithdraw(shares, address(AAtranche)); // routes to instant (lastEpochApr > apr+delta)

// startEpoch with contract cash < pendingInstant -> partial funding, early return
deal(underlying, address(cdoEpoch), pendingInstant - 40e18);
vm.prank(manager);
cdoEpoch.startEpoch();
assertEq(strategy.pendingInstantWithdraws(), 40e18); // stale receipt survives under epoch key N

// run and stop epoch N+1 (epochNumber now N+1), then borrower defaults
... stopEpoch ...; // epochNumber incremented via strategy.deposit
vm.prank(manager); // borrower underfunds -> defaulted
cdoEpoch.stopEpoch(0, 0);
assertTrue(cdoEpoch.defaulted());

vm.prank(manager);
cdoEpoch.finalizeDefault(recovered, recoverySource);

// victim claim: defaulted-epoch slice is 0, remainder hits _transferFundedClaim
vm.prank(lp);
vm.expectRevert(); // NotAllowed: balance - reserve < 40e18
cdoEpoch.claimInstantWithdrawRequest();
// pendingInstantWithdraws stays >0 forever; receipt unclaimable and unhaircutted
assertEq(strategy.instantWithdrawsRequests(lp), 40e18);
```

Uncertainty note: exact accounting of the partially prefunded cash held for the stale receipt depends on the order of `collectInstantWithdrawFunds` relative to the epoch advance; the PoC should assert both outcomes (frozen via `_transferFundedClaim` revert, or par payment draining non-reserve balance ahead of recovery claimants). Either outcome violates the recovery invariant and traces to the same epoch-keyed stale reference.
