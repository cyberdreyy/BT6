### Title
Stale confirmations from deleted multisig keys are still counted toward quorum, allowing requests to execute below the configured `num_confirmations` threshold - (File: `multisig/src/lib.rs`)

### Summary
The `MultiSigContract`'s `confirm()` function counts confirmations stored in the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map without validating that each confirming key is still an active key on the account at execution time. When a key is removed via `DeleteKey`, its previously-recorded confirmations on *other* pending requests are never purged, so a request can execute once the "confirmations" set reaches `num_confirmations` even though one or more of those confirming keys no longer exist. This breaks the intended equality `confirmations counted == live members who confirmed`, mirroring the reported class of bug where quorum accounting is not kept synchronized with the actual set of authorized signers (guardians/members).

### Finding Description
`confirm()` increments/checks the size of the `confirmations` set and executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

The only cleanup of confirmations tied to a specific key happens in the `DeleteKey` action handler, and it only removes **requests originally added by** the deleted key (matched via `r.signer_pk == pk`) — it does not scan and purge that key's *confirmations* on requests added by other keys: [2](#0-1) 

Sequence that breaks the binding:
1. Multisig is initialized with `num_confirmations = 3` and keys `A, B, C, D`.
2. Member `A` calls `add_request` to create request `R` (e.g., a `Transfer`).
3. Member `D` calls `confirm(R)` — now `confirmations(R) = {D}`.
4. Members execute (via a separate, already-confirmed request) a `DeleteKey { public_key: D }` action to remove `D` from the account's access keys. This only removes requests where `D` was the *original signer*; it does **not** touch `confirmations(R)`, which still contains `D`'s key.
5. Later, members `B` and `C` confirm `R`. `confirmations(R)` now has 3 entries (`D, B, C`) even though `D` is no longer a valid key on the account, so `confirm()` executes `R` with effectively only 2 *live* signers' consent.

This is the direct analog of the reported issue: the quorum-counting logic (`num_confirmations` vs. the size of the `confirmations` set) is decoupled from the actual, current set of authorized signers, exactly as the guardian `quorum` value was decoupled from the live `guardians` array in the original report.

### Impact Explanation
This allows a multisig-controlled account (e.g., holding NEAR, an upgradeable contract, or key-management rights) to have a sensitive request — a `Transfer`, `DeployContract`, `AddKey`/`DeleteKey`, `FunctionCall`, or even `SetNumConfirmations` — executed with fewer live signer confirmations than the configured threshold requires. This matches the "Critical" impact criterion: "a multisig request executed below threshold."

### Likelihood Explanation
This does not require any attacker-controlled deployment or ignoring documented initialization — it is a normal operational sequence (confirm a pending request, then rotate/remove a key before the request finishes collecting confirmations) that any multisig using key rotation would naturally encounter, since key rotation is an explicitly supported feature (`AddKey`/`DeleteKey`). No malicious member action or foundation privilege is required beyond routine, expected multisig administration and pending-request lifecycles that are part of normal usage.

### Recommendation
When executing `DeleteKey` (and the analogous `DeleteMember` in `multisig2`), iterate over **all** pending requests' `confirmations` sets (not just those the key originally added) and remove the deleted key/member from each. Alternatively, at `confirm()` time, re-validate that every public key recorded in the request's confirmation set is still a currently valid access key/member before counting it toward `num_confirmations`.

### Proof of Concept
```
// num_confirmations = 3, keys = {A, B, C, D}
1. A: add_request(R)                    // confirmations(R) = {}
2. D: confirm(R)                        // confirmations(R) = {D}
3. (separately confirmed) execute DeleteKey{D}
   -> requests originally added by D are purged
   -> confirmations(R) still contains D  (BUG: not purged)
4. B: confirm(R)                        // confirmations(R) = {D, B}
5. C: confirm(R)                        // confirmations(R).len()+1 >= 3 -> executes R
   // R executes with only B and C as live signers (2 of 4 remaining keys),
   // not the intended 3-of-4 quorum.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
