### Title
Prefunded deposit queue can permanently block `stopEpoch` if the TVL `limit` is lowered after deposits are queued - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
In the prefunded AA queue, `requestDeposit` validates the queued amount against the current TVL limit via `checkPrefunding` at deposit time, and `processDepositsToBorrower` re-validates the same check at prefunding time. If `limit` is lowered between queueing and prefunding, `processDepositsToBorrower` reverts, `epochPendingDeposits` can never be cleared, and `prefundedDepositsToProcess` then makes `stopEpochWithDuration` revert unconditionally — freezing the epoch and all pool funds.

### Finding Description
The prefunded variant enforces the guarded-launch TVL limit twice for the same funds:

1. At queue time in `requestDeposit`: `checkPrefunding(epochPendingDeposits[nextEpoch] + amount)` calls `_guarded(_amount)` inside `checkPrefunding`, reverting if the new total would exceed `limit` [1](#0-0) [2](#0-1) 
2. At prefunding time in `processDepositsToBorrower`: `checkPrefunding(_pending)` re-checks the aggregate queued amount against the *current* `limit`, with the comment "Recheck after the cutoff because emergency state or the TVL limit can change while queued" [3](#0-2) 

This is the same structural bug as the Carousel `relayerFee` issue: a mutable parameter is validated when a request enters the queue and re-validated (with a stricter value) when the queue is drained. If `limit` is lowered below `contractValue + _pending` — a routine risk-reduction action by the honest owner — `processDepositsToBorrower` always reverts, so the queued deposits can never be forwarded to the borrower.

The consequence is worse than in Carousel. The prefunded stop flow requires `epochPendingDeposits[_epoch] == 0`: `prefundedDepositsToProcess` reverts on nonzero pending deposits [4](#0-3) , and `_afterStopEpochWithDuration` invokes it unconditionally whenever an `epochQueue` is configured [5](#0-4) . Since `stopEpochWithDuration` is the only way to end an epoch on the prefunded variant (the direct `stopEpoch` selector is blocked in `_beforeStopEpoch`), the epoch can never be stopped.

The only escape hatch is `deleteRequest`, which lets each user pull back their own queued amount and decrement `epochPendingDeposits` [6](#0-5) . But this requires *every* queued depositor to act. A single unresponsive — or malicious — depositor with a dust deposit permanently blocks epoch termination. There is no privileged path to force-clear `epochPendingDeposits` or bypass `checkPrefunding`.

### Impact Explanation
Permanent freezing of all pool funds. Once `epochPendingDeposits[_epoch] > 0` and the limit check fails, `stopEpochWithDuration` reverts forever: borrower principal cannot be recalled, interest cannot be settled, withdrawal claims cannot be processed, and the pool is stuck with `isEpochRunning == true`. Because `isEpochRunning` blocks `_beforeUnpause` [7](#0-6) , even emergency unpause/recovery paths that depend on the epoch ending are unreachable. An attacker needs only a dust-sized queued deposit (plus KYC) to hold the entire pool hostage.

### Likelihood Explanation
Requires two conditions: (1) the prefunded AA queue holds nonzero pending deposits, and (2) `limit` is reduced (or `checkPrefunding` otherwise starts failing, e.g., `priceAA == 0`) before `processDepositsToBorrower` runs. Lowering a guarded-launch cap in response to market conditions is a plausible honest owner action, and the attacker can pre-position a dust deposit and simply never call `deleteRequest`. Unlike Carousel, no per-item iteration is needed — the aggregate re-check means any single queued deposit below the threshold still poisons the whole epoch.

### Recommendation
Do not let `prefundedDepositsToProcess` hard-revert on leftover `epochPendingDeposits`; either allow `stopEpochWithDuration` to proceed while leaving un-prefunded deposits claimable/refundable from the queue, or give the owner a forced refund path that sweeps `epochPendingDeposits` back to depositors. Alternatively, snapshot the limit at prefunding-commit time, or treat the limit re-check failure as "keep deposits in queue for refund" rather than blocking settlement.

### Proof of Concept
```solidity
// Fork test against the prefunded variant (IdleCDOEpochVariantPrefunded + AA epochQueue)
function testPrefundedQueueLimitDecreaseBlocksStop() external {
    // 1. Epoch running; honest user and attacker queue AA deposits
    _depositToAAQueue(user1, 100e6);
    _depositToAAQueue(attacker, 1); // dust, KYC'd wallet

    // 2. Honest owner lowers the guarded-launch limit below contractValue + pending
    vm.prank(owner);
    cdoEpoch._setLimit(cdoEpoch.getContractValue()); // excludes queued 100e6 + 1

    // 3. Prefunding can never happen: aggregate re-check reverts
    vm.expectRevert(); // _guarded inside checkPrefunding
    vm.prank(manager);
    queue.processDepositsToBorrower();

    // 4. Attacker refuses deleteRequest; epochPendingDeposits stays > 0
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector)); // prefundedDepositsToProcess
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(newApr, interest, loss);

    // 5. Pool is permanently frozen unless user1 *and* attacker both call deleteRequest
}
```

Uncertainty note: the exact body of `GuardedLaunchUpgradable._guarded`/`_setLimit` was not retrieved before the analysis cutoff; the finding assumes the standard semantics (`contractValue + amount > limit` reverts), which is consistent with its usage in `depositDuringEpoch` and the `testDepositDuringEpochSkimsDonationBeforeLimitCheck` test. The blocking chain through `prefundedDepositsToProcess` → `_afterStopEpochWithDuration` → `stopEpochWithDuration` is fully confirmed from the source.

  function _afterStopEpochWithDuration() internal override {
    address _queue = epochQueue;
    if (_queue == address(0)) return;

    IIdleCDOEpochQueuePrefunded _epochQueue = IIdleCDOEpochQueuePrefunded(_queue);
    uint256 _prefunded = _epochQueue.prefundedDepositsToProcess();
    if (_prefunded == 0) return;
    // A zero post-loss AA price cannot safely mint new shares into the same tranche token.
    _checkNotAllowed(priceAA == 0);

    // Prefunded deposits already reached the borrower, so they must join AA even if stop defaulted.
    // Mint tranche shares at the post-stop price and mirror the same amount in strategy tokens,
    // so the queue can later distribute shares to users at the epoch price.
    uint256 _prefundedMinted = _mintSharesAtCurrPrice(_prefunded, _queue, AATranche);
    IdleCreditVault(strategy).mintStrategyTokens(_prefunded);
    // Finalize the prefunded epoch in the queue by storing the epoch price and clearing state.
    _epochQueue.processPrefundedDeposits(_prefundedMinted);
  }
