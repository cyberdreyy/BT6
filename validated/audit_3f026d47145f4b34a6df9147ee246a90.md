## Title
Dilution of Donations via Sandwiching `lending_pool_emissions_deposit` — (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

## Summary
`lending_pool_emissions_deposit` is a permissionless "donation" instruction that adds tokens directly to a bank's liquidity vault and raises `asset_share_value` proportionally across **all** currently outstanding `total_asset_shares`, exactly like the Arcadia `donateToTranche` bug class. Because `lending_account_deposit`/`lending_account_withdraw` have no cooldown or lockup, an attacker can atomically sandwich a pending emissions deposit (e.g. via a Jito bundle: deposit → emissions deposit → withdraw) to capture a pro-rata share of the donation that should have gone to existing depositors, diluting their reward.

## Finding Description
`lending_pool_emissions_deposit` snapshots `total_asset_shares` *before* adding the donated amount, then recomputes `asset_share_value` as `(total_assets + amount) / total_asset_shares`, crediting the gain to every currently outstanding asset share: [1](#0-0) 

This is functionally identical to the Arcadia `donateToTranche` mechanism cited in the report: a non-atomic, share-based donation that any liquidity provider present at donation time benefits from, regardless of how recently they acquired their shares. The instruction is explicitly documented and implemented as **permissionless** — any signer can call it: [2](#0-1) 

The counterpart deposit/withdraw instructions used to execute the sandwich have no minimum holding period, timelock, or snapshot mechanism — `lending_account_withdraw` executes immediately subject only to a standard risk-engine health check: [3](#0-2) 

Attack sequence (mirroring the M-5 report's front-run/back-run pattern, but strengthened by Solana's ability to bundle transactions atomically via Jito):
1. Attacker observes a pending `lending_pool_emissions_deposit` transaction (e.g. a project funding a same-bank emissions round) targeting a specific bank.
2. Attacker front-runs with `lending_account_deposit` of a large amount into that same bank, minting `asset_shares` at the pre-donation `asset_share_value`.
3. The emissions deposit lands, uniformly raising `bank.asset_share_value` for every share holder, including the attacker's freshly minted shares.
4. Attacker back-runs with `lending_account_withdraw`/`withdraw_all`, redeeming shares at the inflated share value and extracting a portion of the donation proportional to their temporarily inflated share of `total_asset_shares`.

Since deposit → donation → withdraw can be packaged into a single atomic Solana bundle, this is strictly easier to execute risk-free than the EVM mempool sandwich described in the original report (which required separate blocks/backruns due to non-atomicity concerns raised in that discussion).

## Impact Explanation
Legitimate long-term depositors receive a diluted share of any `lending_pool_emissions_deposit`-funded reward, while the attacker extracts value with a purely transient, risk-free capital deployment (same-block/bundle in, same-block/bundle out). The magnitude of loss scales with the size of the emissions deposit relative to the attacker's capital versus the bank's total_asset_shares — for a bank with modest existing TVL and a sizeable emissions top-up, the attacker can capture a large fraction of the donation. This is a direct value-redirection/misvaluation bug with financial effect on depositors, matching Sherlock's medium-severity criteria applied in the referenced judgment ("causes a loss of funds but requires certain external conditions... losses must exceed a small, finite amount").

## Likelihood Explanation
The instruction is unprivileged/permissionless on both sides (the donation call and the deposit/withdraw calls), requiring no admin cooperation. The only precondition is visibility of a pending `lending_pool_emissions_deposit` transaction and sufficient capital to temporarily dominate the target bank's shares — both are realistic on a public, permissionless protocol, and Solana bundling (Jito) makes the whole exploit atomic and essentially risk-free once triggered.

## Recommendation
- Track a per-account minimum holding period (or snapshot-based accrual) for emissions/donation distributions instead of instantly diluting across the live `total_asset_shares` set.
- Alternatively, restrict `lending_pool_emissions_deposit` (or any future "donation" style instruction) to distribute pro-rata based on a snapshot of balances taken before the donating transaction is even broadcast, or require a lock on newly deposited shares before they become eligible for emissions distributions.
- Consider adding a minimum notice/delay between deposit and eligibility for any bank-wide value injection to prevent capital from being able to enter and exit atomically around such events.

## Proof of Concept
1. Bank X has `total_asset_shares = S`, `asset_share_value = V`, held entirely by long-term depositor D.
2. Attacker submits (in one atomic bundle):
   - `lending_account_deposit(bank X, amount = A)` — mints `A/V` new shares for the attacker.
   - Waits for the pending `lending_pool_emissions_deposit(bank X, amount = E)` to execute — this recomputes `bank.asset_share_value = (S*V + A + E) / (S + A/V)`, per [4](#0-3) .
   - `lending_account_withdraw(bank X, withdraw_all = true)` — redeems attacker's shares at the new, inflated `asset_share_value`.
3. Attacker's net gain equals `(A/V) * new_share_value - A`, a positive value drawn directly from the emissions deposit `E`, at the expense of depositor D's expected share of `E`.

```rust
/// Permissionlessly deposit same-mint emissions directly into the bank liquidity vault,
/// increasing depositor value through asset share value.
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```
