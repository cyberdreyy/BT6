### Title
Borrower `repay` reverts while an epoch is active when the ERC4626 vault rejects deposits, forcing an unnecessary default - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The external bug is "a state that should allow repayment still reverts because the repay path performs an unnecessary external call that the restricted state forbids." The direct analog lives in `ProgrammableBorrower._repay`: repayment is intentionally allowed at any time (it is the honest-borrower path and is also the prerequisite for a clean close-pool `stopEpoch(..., 1)`), but whenever `epochAccountingActive` is true the function unconditionally re-deposits the full repaid amount into the configured ERC4626 vault via `_depositToVault`. If that vault cannot accept the deposit (paused vault, deposit cap reached, revert in `deposit`), the entire `repay`/`executeRepay` transaction reverts even though the borrower already pulled the tokens with `safeTransferFrom`. The borrower is then unable to clear `borrowerPrincipal`/`borrowerInterestDebt`, and the next `stopEpoch` will route through `onStopEpoch` → `getFundsFromBorrower` failure → `_handleBorrowerDefault`, converting a willing repayment into a hard borrower default.

### Finding Description
In `contracts/strategies/idle/ProgrammableBorrower.sol` the repayment waterfall at lines 482-532 ends with:

```solidity
// ProgrammableBorrower.sol:524-532
if (epochAccountingActive) {
    // Current-epoch borrower interest must remain visible as profit at stopEpoch, while principal,
    // previously-fronted debt, and any excess repayment should only extend the epoch principal baseline.
    _depositToVault(totalRepaidAssets, totalRepaidAssets - currentEpochInterestPaid);
}
```

`_depositToVault` (lines 378-385) only short-circuits on `_assetAmount == 0`; any nonzero repayment performs `vault.deposit(_assetAmount, address(this))` with no try/catch:

```solidity
// ProgrammableBorrower.sol:378-385
function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
    if (_assetAmount == 0) return;
    uint256 shares = vault.deposit(_assetAmount, address(this));
    ...
}
```

Mirroring the M-4 root cause (`realizeRestakerInterest` unconditionally calling `vault.borrow(0)` which reverts on `AssetPaused`), here the protocol *design* clearly wants repayment to be always possible:

- `repay`/`executeRepay` carry no epoch-phase or health gate beyond `msg.sender == borrower` / authorized executor (lines 419-432).
- `onStopEpoch` explicitly treats "borrower repaid everything" as the success case for pool closing (lines 234-237), so repaying mid-epoch is the sanctioned way to reach a clean close.
- The vault deposit is an accounting convenience, not a requirement of repayment correctness: the same repayment could settle the debt ledgers (`borrowerInterestDebt`, `borrowerInterestAccrued`, `borrowerPrincipal` at lines 487-521) while leaving funds on-hand; `onStopEpoch` already handles on-hand liquidity (`uint256 onHand = underlyingToken.balanceOf(address(this));` line 239) and IdleCDO pulls by `transferFrom`, which does not care whether the cash sits in the vault or on the contract.

Therefore any revert inside `vault.deposit` (vault paused, `maxDeposit` cap, slippage/health checks in the underlying market) makes `repay` permanently revert for the remainder of the epoch, exactly like the paused-asset borrow in the reference finding blocks `lender.repay`.

### Impact Explanation
Direct, quantified consequence: an honest borrower (or executor) who wants to repay mid-epoch cannot do so while the configured ERC4626 vault rejects deposits. Since the programmable borrower is the only fund source for `stopEpoch`, at `epochEndDate` the manager calls `stopEpoch`; `onStopEpoch` then cannot return cash (it can only withdraw from the vault up to what the vault allows and the debt ledger still shows outstanding principal), `getFundsFromBorrower` fails in `IdleCDOEpochVariant._stopEpoch` (lines 408, 501-505) or `onStopEpoch` returns `false` in close-pool mode (lines 235-237), and `_handleBorrowerDefault` fires (lines 577-599). The result is a spurious `BorrowerDefault` on a borrower who had funds and willingness to pay: the pool enters `defaulted`, withdraw requests are disabled, and all LPs are pushed into the loss-socialization / `finalizeDefaultRecovery` flow, with tranche prices crystallizing a haircut that should never have existed. Loss magnitude: up to the full recorded default amount `_amountToPullFromBorrower + _pendingWithdraws` (lines 401, 504) being treated as defaulted debt until manual recovery.

### Likelihood Explanation
Likelihood depends on the configured ERC4626 vault's deposit-side restrictions, but the trigger is common and not attacker-dependent:

- Many ERC4626 venues (Morpho-style markets, vaults with supply caps, pausable wrappers) can legitimately reject `deposit` while still allowing `withdraw`. Repay-blocking needs only `vault.deposit` to revert; `vault.withdraw` used by `onStopEpoch` (line ~240) may still work.
- The condition persists for the entire active epoch (`epochAccountingActive`), which is the only window in which repayment is meaningful for avoiding default. A supply-cap vault where the borrower's own draw plus yield pushes `totalAssets` over the cap is a natural occurrence, not an attack.
- The honest privileged roles (borrower, executor, manager) cannot route around it: there is no alternative repay path that skips the vault deposit, and `emergencyExitVault` only redeems shares, it does not settle the debt ledgers. `setAuthorizedExecutor`, `setBorrower` and other owner functions do not provide a bypass.

Unlike the reference bug, no asset is literally "paused" inside this codebase, but the code shape is identical: an always-allowed action (repay) unconditionally performs a restricted action (vault deposit) it does not need, so the whole operation reverts.

### Recommendation
Make the vault re-deposit best-effort or deferred so repayment itself cannot be blocked:

```diff
// contracts/strategies/idle/ProgrammableBorrower.sol
     emit Repaid(interestPaid + principalPaid, interestPaid, principalPaid);
     if (epochAccountingActive) {
-        _depositToVault(totalRepaidAssets, totalRepaidAssets - currentEpochInterestPaid);
+        try vault.deposit(totalRepaidAssets, address(this)) returns (uint256 shares) {
+            if (totalRepaidAssets != currentEpochInterestPaid) {
+                epochDepositedToVault += totalRepaidAssets - currentEpochInterestPaid;
+            }
+            emit DepositedIntoVault(totalRepaidAssets, shares);
+        } catch {
+            // Leave the cash on hand; onStopEpoch already sources on-hand balance first.
+        }
     }
```

Alternatively, accumulate repaid principal on hand and only call `_depositToVault` lazily (e.g., in `onStopEpoch`/`onStartEpoch`), which keeps the vault-deposit off the repay critical path entirely. The same guard should be applied to the early-return branch at lines 496-500.

### Proof of Concept
Foundry test against the existing harness (`test/foundry/ProgrammableBorrowerCreditVault.t.sol` style; assumes the mock vault exposes a deposit-pause flag, e.g. `vault.setDepositPaused(bool)` equivalent to the existing `setWithdrawLimit`/`setRevertConvertToAssets` toggles used in `test/foundry/ProgrammableBorrowerAccountingInvariant.t.sol:700`):

```solidity
function testRepayRevertsWhenVaultDepositPausedCausesDefault() external {
    uint256 amount = 10_000 * oneScale;
    uint256 drawAmount = 4_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0); // epochAccountingActive = true

    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(drawAmount);

    // Vault enters a state where deposits revert but withdrawals still work.
    vault.setDepositPaused(true); // analog of AssetPaused on mint/borrow

    // Borrower has funds and allowance, wants to repay in full.
    uint256 totalOwed = programmableBorrower.borrowerPrincipal()
        + programmableBorrower.borrowerInterestOwedNow();
    deal(USDC, revolvingBorrower, totalOwed, true);
    vm.prank(revolvingBorrower);
    underlying.approve(address(programmableBorrower), totalOwed);

    // Repay reverts even though repayment itself should be allowed.
    vm.expectRevert(); // vault.deposit reverts inside _depositToVault
    vm.prank(revolvingBorrower);
    programmableBorrower.repay(0);

    // Debt ledger still shows full obligation -> stopEpoch cannot settle cleanly.
    assertEq(programmableBorrower.borrowerPrincipal(), drawAmount);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1); // close-pool

    // Spurious default: borrower was able and willing to repay.
    assertEq(cdoEpoch.defaulted(), true);
}
```

After the suggested fix (best-effort deposit), the same sequence repays successfully, `borrowerPrincipal == 0`, and `stopEpoch(0, 1)` closes the pool without `BorrowerDefault`.
