### Title
Closed-pool `requestWithdraw` mints unbacked receipts that drain funded withdraw reserves — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
When the IdleCDOEpochVariant pool is closed (`epochEndDate() == 0`), `IdleCreditVault.requestWithdraw` still burns the CDO's strategy tokens, mints a 1:1 receipt to the user, and records `withdrawsRequests[_user] += _amount`, but deliberately skips `pendingWithdraws += _amount` (lines 259–294). Because no `stopEpoch` will ever run again, nothing ever funds this new receipt via `collectWithdrawFunds`. Yet `claimWithdrawRequest` → `_claimFundedWithdrawRequest` skips the epoch-wait check when `epochEndDate() == 0` (line 326) and pays the claim out of the strategy's raw underlying balance through `_transferFundedClaim`, which only exempts `defaultRecoveryReserve` (lines 897–907). Any underlying held in the strategy to back *other* users' already-funded, not-yet-claimed withdraw receipts can therefore be claimed immediately by a fresh closed-pool requester.

This mirrors the LightLLM bug class: an externally supplied value (`_amount`/`_principal` forwarded by the CDO on behalf of an unprivileged tranche holder) is accepted into accounting and immediately "executed" as a payout with no validation that it was ever funded — the missing step analogous to missing authentication/validation before `pickle.loads`.

### Finding Description
- `requestWithdraw` (lines 243–295): in closed mode `isClosed == true`, so `pendingWithdraws` is not increased and the APR0 path is skipped, but `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch` are still incremented and a receipt is minted.
- `_claimFundedWithdrawRequest` (lines 319–350): the gating check `epochEndDate() != 0 && epochNumber <= lastWithdrawRequest` passes immediately in closed mode, so the brand-new receipt is claimable in the same transaction.
- `_transferFundedClaim` (lines 897–907): pays `underlyingToken.safeTransfer(_user, _amount)` from the contract balance, only protecting `defaultRecoveryReserve`. Underlying previously pulled in by `collectWithdrawFunds` to back other users' funded receipts is unprotected.
- No skim/donation-isolation guard exists on the strategy balance; the solvency invariant "one funded receipt, one payout" is broken because the new receipt was never funded.

### Impact Explanation
A tranche-token holder in a closed vault can call the CDO's withdraw-request flow and immediately claim, receiving underlying at par that economically belongs to earlier requesters whose funded receipts remain unclaimed. Loss is bounded by the strategy's residual underlying balance, which in a closed pool can be the full recalled loan value awaiting distribution. This is direct theft / insolvency for honest claimants.

### Likelihood Explanation
Requires the vault to be in the closed state (`epochEndDate() == 0`) with residual strategy balance covering older unclaimed receipts, and an attacker holding tranche tokens — all unprivileged, in-scope conditions. No privileged actor misbehavior is needed; the honest CDO relays the request.

### Recommendation
In `requestWithdraw`, either revert when `epochEndDate() == 0` and route closed-pool exits through a dedicated funded path, or require the CDO to transfer underlying covering `_amount` in the same call before minting the receipt. Additionally, track a `fundedButUnclaimed` counter so `_transferFundedClaim` can only spend balance explicitly reserved per receipt rather than any residual balance.

### Proof of Concept
Foundry fork outline (against `IdleCDOEpochVariant` + `IdleCreditVault` on a closed credit vault):

```solidity
// state: vault closed (epochEndDate() == 0), strategy holds underlying
// backing victim's previously funded, unclaimed withdraw request.

// 1. attacker (tranche holder) calls CDO -> strategy.requestWithdraw(amount, attacker, principal)
//    - burns principal strategy tokens from CDO, mints `amount` receipt to attacker
//    - pendingWithdraws unchanged, withdrawsRequests[attacker] = amount

// 2. same tx: attacker calls CDO -> strategy.claimWithdrawRequest(attacker)
//    - epochEndDate()==0 skips the wait check in _claimFundedWithdrawRequest
//    - _transferFundedClaim pays `amount` from strategy balance

assertEq(underlying.balanceOf(attacker), amount);            // attacker paid at par
// victim's later claimWithdrawRequest reverts/underpays: strategy balance drained
```

Uncertainty note: I could not fully trace `IdleCDOEpochVariant`'s closed-pool withdraw path to confirm whether it forwards `requestWithdraw` while closed and whether recalled funds sit in the strategy versus the CDO. If the CDO blocks requests once closed or holds all residual funds itself, this vector is not reachable; a fork PoC against a real closed vault deployment is needed to confirm.
