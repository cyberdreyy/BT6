### Title
v1 `validate_tenure_change_payload` allows a signer to sign two conflicting tenure-start blocks for the same tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
The v1 signer evaluator's duplicate-tenure-start-block guard checks only `signer_db.get_last_globally_accepted_block` [1](#0-0) , while the v2 evaluator's equivalent guard checks `signer_db.get_last_signed_block`, which covers both locally- and globally-accepted blocks [2](#0-1) . This asymmetry means a v1 signer that has only *locally* accepted a first tenure-start block (never reaching global-acceptance threshold) will not detect a second, conflicting tenure-start block for the same tenure as a duplicate, and can go on to sign it.

### Finding Description
The claimed uniqueness property is: *at most one tenure-start block gets signed by a given signer for a given tenure*. Both evaluators implement this via a lookup keyed on `block.header.consensus_hash` at the end of `validate_tenure_change_payload`:

- v2: `signer_db.get_last_signed_block(&block.header.consensus_hash)` — locally OR globally accepted blocks count [3](#0-2) 
- v1: `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` — ONLY globally accepted blocks count [1](#0-0) 

If a v1-protocol signer has already locally accepted (voted/signed) a first tenure-start block A for consensus hash `CH`, but the round never reached the global-acceptance threshold (e.g., split votes, competing proposal, network delay), `get_last_globally_accepted_block(CH)` returns `None` on that signer's own database. The attacker (the sole miner who won the slot) can then gossip a second, distinct tenure-start block B also targeting `CH` (same `prev_tenure_consensus_hash`, satisfying the parent-tenure and parent-choice checks that precede this guard). Because `last_in_current_tenure` is `None`, the `DuplicateBlockFound` branch is skipped and `Ok(())` is returned, so the v1 signer proceeds to evaluate/sign block B — even though it already signed block A for the same tenure.

Call sequence: `SortitionsView::check_proposal` (v1) → `validate_tenure_change_payload` (v1.rs:461-520) → `signer_db.get_last_globally_accepted_block` (v1.rs:505) → misses the local-only acceptance of A → `Ok(())` → signer proceeds to sign B.

This is reachable purely by the attacker's own miner-slot block proposals plus StackerDB/gossip that a signer already consumes, with no elevated access: propose A, get enough of a subset of v1 signers to locally accept it (below global threshold), then propose B for the same tenure to those same v1 signers.

### Impact Explanation
This breaks the uniqueness/chain-safety property for tenure-start blocks: a single v1 signer can end up having signed two conflicting tenure-start blocks for the same tenure. In a mixed-version signer set (`SortitionStateVersion::from_protocol_version` selecting v1 vs v2 evaluators during an upgrade window), disjoint subsets of signers could independently accumulate signature weight on two different tenure-start blocks for the same tenure — the v2 signers protected by the stronger local-accept check, but the v1 signers not. If the v1-signed weight combines with signatures obtained through any other channel to reach threshold on block B while block A also carries weight, two conflicting blocks for the same tenure could each gather partial signature sets, which is a Critical chain-safety violation (conflicting/duplicate canonical blocks). The exploit is repeatable for every tenure boundary during the mixed-version window.

### Likelihood Explanation
Preconditions: mid-upgrade period with some signers still evaluating under the v1 protocol version (`SortitionStateVersion::from_protocol_version`) and the first tenure-start block only reaching local (not global) acceptance among at least one v1 signer — a realistic and common transient state (network delays, disagreement, or an attacker deliberately splitting the vote by racing two proposals). Attacker cost is minimal: win one miner slot, craft and gossip two competing tenure-start block proposals for the same tenure — exactly within the stated unprivileged attacker capability (one miner slot + gossip of proposals/StackerDB messages a signer already consumes). No signer key, auth_token, or majority control is required.

### Recommendation
Change v1's `validate_tenure_change_payload` duplicate check to use `signer_db.get_last_signed_block` (locally or globally accepted) instead of `get_last_globally_accepted_block`, matching v2's semantics, so that a v1 signer's own local acceptance of a prior tenure-start block also blocks it from signing a second, conflicting tenure-start block for the same tenure.

### Proof of Concept
Rust test to add in `stacks-signer/src/chainstate/tests/v1.rs`, mirroring the v2 test `check_tenure_change_rejects_when_locally_accepted_block_exists` referenced in `stacks-signer/src/chainstate/tests/v2.rs`:

1. Set up a `SignerDb` and `SortitionsView` (v1) with a valid current sortition and miner.
2. Construct tenure-start block A for consensus hash `CH`; call `signer_db` methods to record A as **locally accepted only** (not globally accepted) — e.g., the same helper used by the v2 test to seed a locally-accepted (non-global) block record.
3. Construct a second, distinct tenure-start block B, also targeting `CH`, with the same `prev_tenure_consensus_hash`/parent-tenure fields so it passes the earlier checks in `validate_tenure_change_payload`.
4. Call `SortitionsView::check_proposal(..., block=B, ...)` (v1) and assert the result:
   - Expected (secure) behavior: `Err(RejectReason::DuplicateBlockFound)`.
   - Actual (vulnerable) behavior: `Ok(())`, proving the v1 evaluator misses the locally-accepted duplicate that the v2 evaluator (`get_last_signed_block`) would have caught.
5. Add a companion assertion running the same scenario through `GlobalStateView::check_proposal` (v2) confirming it correctly returns `DuplicateBlockFound`, demonstrating the asymmetry side-by-side.
