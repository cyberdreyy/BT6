### Title
Owner can create a lockup with `VestingScheduleOrHash::VestingHash` and immediately withdraw the full lockup amount, bypassing the private (hidden) vesting cliff/schedule - (File: `lockup/src/getters.rs`, `lockup-factory/src/lib.rs`)

### Summary
`get_locked_amount` in `lockup/src/getters.rs` treats a private `VestingInformation::VestingHash` as always fully vested (`unvested_amount = U128(0)`), based on the documented assumption that hash-based vesting "started before lockup and transfers were enabled." That assumption is not enforced anywhere and is explicitly broken by `lockup-factory`, which always creates lockups with `TransfersInformation::TransfersEnabled { transfers_timestamp: TRANSFERS_STARTED }` (a fixed 2020 timestamp already in the past), and lets the caller freely choose `lockup_duration`/`lockup_timestamp`/`VestingScheduleOrHash::VestingHash`. The codebase's own test suite even acknowledges this ("Vesting post transfers is not supported by Hash vesting") [1](#0-0) , but nothing prevents it from being used that way in production.

### Finding Description
The broken binding: for a `VestingHash` schedule with a real (hidden) vesting cliff/end far in the future, `get_locked_amount()` should equal `unvested_amount(real_schedule)` (as it does for an explicit `VestingSchedule`, per `get_unvested_amount`), but instead it always returns `U128(0)` for the vesting component:

```rust
let unvested_amount = match &self.vesting_information {
    VestingInformation::VestingSchedule(vs) => self.get_unvested_amount(vs.clone()),
    VestingInformation::Terminating(terminating) => terminating.unvested_amount,
    // Vesting is private, so we can assume the vesting started before lockup date.
    _ => U128(0),
};
``` [2](#0-1) 

This is a documented, unenforced assumption baked into `VestingInformation::VestingHash`: "The contract assume[s] the vesting schedule doesn't affect lockup release and duration, because the vesting started before transfers were enabled" [3](#0-2) . `LockupContract::new` performs no validation that ties this assumption to the actual `transfers_information`/`lockup_timestamp`; it simply stores whatever `VestingScheduleOrHash::VestingHash(hash)` is passed in as `VestingInformation::VestingHash(hash)` with only a foundation-account presence check [4](#0-3) .

`lockup-factory`'s public, permissionless `create()` entrypoint always sets transfers as already enabled from a fixed past timestamp:
```rust
const TRANSFERS_STARTED: u64 = 1602614338293769340; /* 13 October 2020 */
...
transfers_information: TransfersInformation::TransfersEnabled { transfers_timestamp: transfers_enabled }
``` [5](#0-4) [6](#0-5) 
and lets the caller freely pick `lockup_duration`, `lockup_timestamp`, and `vesting_schedule: Option<VestingScheduleOrHash>` (including `VestingHash`) [7](#0-6) . Any account can call `create()` with `lockup_duration = 0`, no `release_duration`, and a `VestingScheduleOrHash::VestingHash(hash)` whose real, hidden `vesting_schedule` has a cliff/end far in the future.

Once created, `get_locked_amount()` evaluates: `lockup_timestamp = max(TRANSFERS_STARTED + 0, 0) = TRANSFERS_STARTED`, which is already `<= block_timestamp` (a 2020 date), so the lockup-gate branch fires immediately. `unreleased_amount = 0` (no `release_duration`), and `unvested_amount = U128(0)` because the vesting is `VestingHash`. Therefore `get_locked_amount() = 0` from the moment the contract exists, even though the true (hidden) vesting schedule may have 100% of tokens unvested. `get_owners_balance`/`get_liquid_owners_balance` then report the entire deposited balance as immediately transferable [8](#0-7) , and `transfer()` (an owner method gated only by `assert_owner`/liquid balance, not by revealing the true schedule) lets the owner move the full amount out.

The only real backstop is the NEAR Foundation calling `terminate_vesting`, which requires the caller to reveal the true `VestingScheduleWithSalt` and recomputes `unvested_amount` from the real schedule [9](#0-8) . But that only runs if/when the foundation acts — by which time the owner may already have transferred the unvested tokens out via `transfer()`, since `get_locked_amount` (the gate every owner/staking method relies on) never blocked it.

### Impact Explanation
Any account that creates its own lockup through the public `lockup-factory.create()` with a `VestingScheduleOrHash::VestingHash` and `lockup_duration = 0` (no `release_duration`) obtains a lockup contract whose entire deposited balance is reported as unlocked/liquid from creation, regardless of the real vesting schedule encoded in the hash. This is "locked or unvested tokens released early," a listed Critical impact. If a real employer/foundation relies on the (deprecated but still accepted) `VestingHash` mechanism to enforce a genuine vesting cliff for an employee-owned lockup created post-transfer via this factory, the employee can withdraw the entire unvested balance immediately via `transfer()`, leaving nothing for the foundation to claw back via `terminate_vesting` upon early termination — a deficit the foundation discovers only after the funds are gone.

### Likelihood Explanation
The attack requires only: (1) permissionless use of `lockup-factory.create()` — anyone can call it and attach `MIN_ATTACHED_BALANCE`; (2) choosing `vesting_schedule = VestingScheduleOrHash::VestingHash(hash)` with `lockup_duration = 0` and no `release_duration`. Both are ordinary, documented parameters of a public entrypoint, requiring no privileged role. The only friction is that this specific misuse (VestingHash combined with post-transfer creation) is already called out as unsupported in the code's own tests, meaning the security-relevant assumption is well-known internally but not enforced at the contract level.

### Recommendation
Enforce the `VestingHash` assumption at contract construction time in `LockupContract::new`: reject `VestingScheduleOrHash::VestingHash` when `transfers_information` is `TransfersEnabled` (or generally disallow `VestingHash` for any lockup created after transfers have started), forcing new lockups to use only the explicit `VestingSchedule` variant so `get_locked_amount` can correctly compute `unvested_amount` without relying on an unverifiable assumption. Alternatively, remove the `VestingHash` code path entirely from newly created lockups (keep it only for pre-existing/legacy state via migration) and have `lockup-factory` refuse to pass through `VestingScheduleOrHash::VestingHash`.

### Proof of Concept
```rust
// lockup/src/lib.rs (add to #[cfg(test)] mod tests)
#[test]
fn test_vesting_hash_post_transfers_releases_early() {
    let mut context = basic_context(); // block_timestamp before GENESIS_TIME_IN_DAYS
    testing_env!(context.clone());

    // Real hidden schedule: nothing vests until far in the future.
    let real_schedule = new_vesting_schedule(4 * YEAR); // cliff/end far after "now"

    let contract = LockupContract::new(
        account_owner(),
        0.into(),                     // lockup_duration = 0
        None,                         // no lockup_timestamp
        TransfersInformation::TransfersEnabled {
            transfers_timestamp: to_ts(GENESIS_TIME_IN_DAYS - 1).into(), // already enabled, in the past
        },
        Some(VestingScheduleOrHash::VestingHash(
            VestingScheduleWithSalt { vesting_schedule: real_schedule.clone(), salt: SALT.to_vec().into() }
                .hash()
                .into(),
        )),
        None,                          // no release_duration
        AccountId::from("whitelist"),
        Some(account_foundation()),
    );

    context.is_view = true;
    context.block_timestamp = to_ts(GENESIS_TIME_IN_DAYS); // "now", long before real cliff
    testing_env!(context.clone());

    // BROKEN BINDING: get_locked_amount() should equal
    // get_unvested_amount(real_schedule) (~lockup_amount, since cliff hasn't passed),
    // but instead returns 0 because VestingHash is treated as fully vested.
    assert_eq!(contract.get_locked_amount().0, 0);
    assert_eq!(
        contract.get_unvested_amount(real_schedule.clone()).0,
        to_yocto(1000) // full amount still unvested per the real, hidden schedule
    );
    // Owner can withdraw everything now via transfer(), even though the
    // real schedule says 100% is unvested.
    assert_eq!(contract.get_owners_balance().0, to_yocto(1000) /* approx, minus storage */);
}
```
This demonstrates `get_locked_amount() (0) != get_unvested_amount(real_schedule) (to_yocto(1000))` while the real vesting schedule (recoverable only by revealing salt) still has the entire balance unvested, confirming the owner's ability to call `transfer()` and remove funds that should remain locked.
