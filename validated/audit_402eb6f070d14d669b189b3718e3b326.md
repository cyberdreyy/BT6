### Title
Deterministic, creator-independent lockup address enables front-running/squatting of a victim's lockup with attacker-chosen vesting/release parameters, defeating foundation oversight - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the sub-account name solely from `sha256(owner_account_id)` and the factory account, with no dependency on the caller/predecessor, and only sets `foundation_account_id` to `Some(..)` when `vesting_schedule.is_some()`. An unprivileged attacker can pre-empt the deterministic address for `owner_account_id = <victim>` and supply a bogus vesting hash plus `release_duration = 1`, producing a lockup whose released-balance trajectory the real grantor never authorized, while the legitimate creation transaction for the same owner permanently fails.

### Finding Description
Binding claimed: `locked_amount(T) == get_balance() - available(T)` should reflect the vesting/lockup schedule that the rightful grantor of `owner_account_id`'s tokens actually chose.

The lockup account id is computed purely from the `owner_account_id` argument: [1](#0-0) 
There is no dependency on `env::predecessor_account_id()` or any attacker-supplied salt, so the target account name for a given `owner_account_id` is identical no matter who calls `create`. `foundation_account_id` is only populated when `vesting_schedule.is_some()` — any `Some(..)` value (including an attacker-fabricated `VestingScheduleOrHash::VestingHash`) satisfies this and yields `Some(self.foundation_account_id.clone())`, i.e. the presence check gives no guarantee that the disclosed/undisclosed schedule is one the real grantor authorized.

Since the lockup account is created via `create_account()` inside the batched `Promise`, the second (legitimate) call to `create` for the same `owner_account_id` will fail at `create_account` (account already exists) and the whole promise batch fails; `on_lockup_create` then refunds the *legitimate* caller's deposit via `is_promise_success()`: [2](#0-1) 
So the attacker's transaction — the first to land — permanently claims the deterministic address, and the rightful creator's transaction can never succeed for that `owner_account_id`.

Once deployed with the attacker's parameters (`vesting_schedule = Some(VestingHash(<garbage hash>))`, `release_duration = 1`), `get_locked_amount` computes the locked balance as `max(unreleased_amount, unvested_amount)`. Because the vesting schedule is stored only as an undisclosed hash, `unvested_amount` falls into the private-vesting fallback and evaluates to `0`: [3](#0-2) 
so `get_locked_amount()` is governed entirely by `unreleased_amount`, which under `release_duration = 1` collapses to `0` almost immediately after `lockup_timestamp`: [4](#0-3) 
This means the victim's lockup balance becomes fully "released"/liquid almost immediately, independent of whatever multi-year schedule the real grantor intended.

Even if the foundation later attempts `terminate_vesting` to claw back unvested funds, it must supply a `VestingScheduleWithSalt` whose hash matches the one embedded at creation: [5](#0-4) 
Since the hash stored was chosen by the attacker (not corresponding to any real schedule the foundation holds), the foundation can never produce a matching disclosure, and even if it somehow could, `get_locked_amount`/`get_unvested_amount` already show nothing left to claw back due to the collapsed `release_duration`. `assert_called_by_foundation` restricts *who* can call `terminate_vesting`, but does nothing to validate that the *parameters embedded at creation* correspond to a real, foundation-approved vesting agreement — which is exactly what was subverted.

### Impact Explanation
A lockup account intended for `owner_account_id = <victim>` is deployed with `lockup_duration`, `vesting_schedule`, and `release_duration` chosen entirely by an unprivileged attacker rather than by the real grantor (e.g., NEAR Foundation's provisioning process). This directly matches the Critical category "a lockup deployed with parameters its rightful creator never chose." Practically, funds intended to be subject to multi-year vesting/foundation clawback become liquid almost immediately, and the legitimate creation attempt is permanently blocked for that account name (its deposit is refunded, but the intended lockup never exists with the correct terms). This is repeatable against any `owner_account_id` the attacker can predict/target before the legitimate creator submits their transaction, and the cost is only `MIN_ATTACHED_BALANCE` (3.5 NEAR) plus gas.

### Likelihood Explanation
The precondition is simply that the attacker submits `create(owner_account_id = <victim>, ...)` before the legitimate grantor's transaction for the same `owner_account_id` is included on-chain — a classic front-running/mempool race that requires no special privilege, key, or foundation role, matching the allowed attacker capabilities ("create their own lockup ... through the public factories with chosen arguments"). The attacker only needs to know or predict which `owner_account_id` will be used for a future legitimate lockup (e.g., public token-grant recipients, which are frequently known in advance). The attached-deposit requirement (3.5 NEAR) is a modest, one-time cost.

### Recommendation
Bind the lockup account address (or add an authorization check) to something the attacker cannot control independently of the legitimate grantor — e.g., require the factory to be called only by a trusted/foundation-controlled account (`assert_called_by_foundation`-style gate on `create`), or derive the account id / require a commitment (salt known only to the legitimate creator) so a squatter cannot pre-empt the deterministic address for an arbitrary `owner_account_id`. Additionally, do not treat "`vesting_schedule.is_some()`" as sufficient to set `foundation_account_id`; the presence of *any* schedule/hash should not be conflated with a foundation-approved agreement.
