### Title
Unbounded tar+zstd extraction allows decompression-bomb disk/inode exhaustion on the runner host - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
`extractor.Extract` decompresses a zstd stream and writes every tar entry to disk without any cap on total decompressed size, per-file size, or entry count. Only a context-cancellation check exists, so a small, highly compressible cache/artifact archive can be crafted to expand to an enormous amount of data or an enormous number of files, exhausting disk space or inodes on the runner/helper filesystem.

### Finding Description
In `Extract` (commands/helpers/archive/tarzstd/tarzstd_extractor.go:33-105), the zstd reader is opened with only `zstd.WithDecoderLowmem(true)` [1](#0-0) , which limits memory usage per decoder window but does not bound total output bytes. The subsequent loop calls `tr.Next()`, creates a file with `os.Create`, and streams the entry with `io.Copy(f, tr)` for every regular file, with no running total of bytes written and no limit on the number of tar headers processed [2](#0-1) . The only guard against runaway execution is `ctx.Err()`, checked once per header before the switch statement [3](#0-2) , which only detects cancellation/timeout — it does nothing to stop a single `io.Copy` call from writing gigabytes for one oversized entry, nor does it cap how many small files/directories get created before a timeout fires.

The call path is reachable from unprivileged job input: `CacheExtractorCommand.Execute` opens the archive via `openArchive(c.File)` and calls `extractor.Extract(context.Background())` with a background context that has no deadline at all [4](#0-3) , so the `ctx.Err()` check is entirely inert for the cache-restore path — there's no cancellation to ever trigger it. A pipeline author can set `CACHE_COMPRESSION_FORMAT: tarzstd` [5](#0-4)  and push an attacker-crafted cache archive; when it's fetched back down and extracted by `cache-extractor`, the `Extract` loop will materialize whatever the archive decompresses to, with only `MkdirAll`/path-traversal checks and no size/inode budget. `MaxUploadedArchiveSize` only bounds the *upload* size of the archive going to cache storage [6](#0-5) ; it is not applied on extraction, so it does nothing to cap the decompressed output size that `tarzstd_extractor.go` writes to disk.

### Impact Explanation
On a shared runner host or helper container where multiple jobs (potentially from different tenants) share a filesystem or the same node, decompression of an attacker-controlled cache/artifact archive can write until disk space or inodes are exhausted. This can starve other jobs scheduled on the same host/container of disk space, causing job failures unrelated to the attacker's own job, and the exhausted disk state can persist after the attacker's job is cancelled or times out, since nothing tracks or caps bytes/files already written to disk.

### Likelihood Explanation
This requires only that an unprivileged pipeline author control the contents of a project's cache (trivial — caches are populated by job scripts) and that the runner be configured to use `tarzstd` cache compression, which is a documented, user-selectable option via `CACHE_COMPRESSION_FORMAT`. No admin privilege or special executor configuration is needed beyond the compression format choice, and zstd's compression ratio makes constructing a small archive that expands to a very large tar stream straightforward and repeatable.

### Recommendation
Track cumulative bytes written and file/directory count during extraction and abort once configurable thresholds are exceeded (similar to zip-bomb protections used elsewhere, e.g., a max-decompressed-size and max-entry-count check inside the `for` loop before/while calling `io.Copy`). Also plumb a context with a deadline (or an explicit size/time budget) into `CacheExtractorCommand.Execute`'s call to `extractor.Extract` rather than `context.Background()`, and apply the same accounting to the other extractors (`zipzstd`, `zip`) that share this pattern.

### Proof of Concept
Go test outline in `commands/helpers/archive/tarzstd`:
1. Build a `.tar.zst` fixture where a handful of tar entries each contain many megabytes of a single repeated byte (zstd will compress this to a few KB), producing e.g. a 10 GB decompressed payload from a <1 MB archive.
2. Call `NewExtractor(reader, size, tmpDir).Extract(context.Background())`.
3. Assert that, absent a fix, extraction proceeds and fills the temp filesystem (or hits an `ENOSPC`/disk-full error) rather than terminating early with a bounded-resource error.
4. After adding a size/file-count budget, add an assertion that `Extract` returns a specific "extraction limit exceeded" error once the configured byte/file threshold is crossed, well before disk exhaustion.
