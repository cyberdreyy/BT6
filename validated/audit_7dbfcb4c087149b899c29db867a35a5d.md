### Title
Stale confirmations from removed multisig members are never purged, allowing requests to execute below the configured `num_confirmations` threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts every entry in a request's `confirmations` set toward the `num_confirmations` threshold, but `delete_member` (v2) / `DeleteKey` (v1) only purge confirmation state for requests that were *created* by the removed member — not for requests where the removed member merely *confirmed*. A member's approval therefore behaves like the "stale bid" in the analog report: once cast it never expires and is never invalidated when the underlying trust relationship (multisig membership) ends, letting a request execute with fewer live-member approvals than the configured threshold.

### Finding Description
The multisig's core invariant is: a request only executes once **K distinct, currently-trusted members** have approved it (`num_confirmations` = K). This is enforced in `confirm()`: [1](#0-0) 

The check `confirmations.len() as u32 + 1 >= self.num_confirmations` blindly trusts every account-id/public-key string already stored in the `confirmations: LookupMap<RequestId, HashSet<String>>` map, with no re-validation that those entries still belong to `self.members`.

When a member is removed via `DeleteMember`, cleanup only targets requests *authored* by that member: [2](#0-1) 

```rust
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```

Any request created by a *different* member that the now-removed member previously confirmed is never touched — the removed member's entry silently remains inside that request's `confirmations` HashSet and keeps counting toward quorum. The legacy `multisig/src/lib.rs` contract has the identical gap in its `DeleteKey` handler: [3](#0-2) 

This breaks the equality the contract is supposed to guarantee: `confirmations recorded for a request == approvals from members who are members at execution time`. Instead, `confirmations recorded ⊇ approvals from currently-live members`, with the extra entries coming from anyone ever removed after confirming.

### Impact Explanation
This directly matches the listed Critical impact "a multisig request executed below threshold." A pending request can be executed with strictly fewer live-member approvals than `num_confirmations` requires, because a stale confirmation from a removed member is counted as if it were still valid. Since multisig contracts in this repo are used to hold and move NEAR/treasury funds (`Transfer`, `FunctionCall`, `AddKey`/`AddMember` actions execute through the same `confirm` path), this can result in an unauthorized transfer, key addition, or contract upgrade being pushed through with an insufficient number of currently-trusted approvers.

### Likelihood Explanation
This requires no external/privileged capability beyond the multisig's own normal lifecycle: member turnover (removing a compromised or departing member) plus a request that was already partially confirmed by that member before removal. Member churn is an expected, routine multisig operation, and the described sequence is a completely ordinary usage pattern — no key theft, redeploy, or malicious validator is required.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), scan all outstanding requests' `confirmations` sets and strip the removed member's identifier from every one of them (not just requests they authored), or re-validate every confirmation entry against current `members` at the time `confirm()` computes the threshold (e.g., filter `confirmations` to intersect with `self.members` before comparing length to `num_confirmations`).

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `B` calls `add_request` with a malicious `Transfer`/`AddKey` action → `request_id = X`, `confirmations(X) = {}`.
3. `A` calls `confirm(X)` → `confirmations(X) = {A}` (1/3, not executed).
4. Members legitimately decide to remove `A` (e.g. compromised key) via `AddMember`/`DeleteMember{A}` request, confirmed by `B, C, D` → executes `delete_member`. Per `delete_member`'s filter (`r.member == member`), only requests *created by A* are purged; request `X` (created by `B`) is untouched, so `confirmations(X)` still equals `{A}`.
5. `members` is now `{B, C, D}`, `num_confirmations` unchanged at 3.
6. `B` calls `confirm(X)` → `confirmations(X) = {A, B}` (len 2, check `1+1>=3` false before insert).
7. `C` calls `confirm(X)` → check `2+1>=3` → true → `execute_request(X)` runs.

Only `B` and `C` — 2 of the 3 currently live members — actually approved `X`; the third "confirmation" came from `A`, who was removed before ever re-confirming. The request executed despite not meeting the unanimous 3-of-3 threshold required among live members, demonstrating a multisig request executed below its configured threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
