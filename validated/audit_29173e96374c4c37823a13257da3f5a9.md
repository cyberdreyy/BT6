### Title
Loss-adjusted withdrawal haircut is keyed to the wrong epoch — `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch` under the post-increment `epochNumber` while claims read it under the pre-increment `lastWithdrawRequest` — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.requestWithdraw` records a user's receipt under the *current* `epochNumber` (`withdrawsRequestsByEpoch[_user][currentEpoch]`, `lastWithdrawRequest[_user] = currentEpoch`). During `stopEpochWithDuration`, the strategy `deposit()` call increments `epochNumber` first (the `isEpochRunning()` branch in `deposit`), and only then does the CDO call `collectWithdrawFunds`, which stores the haircut as `lossRecoveryPriceByEpoch[epochNumber]` — i.e., under the **new** epoch index, not the epoch that owns the pending receipts. The claim path (`_claimLossAdjustedWithdrawRequest`) and the re-request guard in `requestWithdraw` both look up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, which is the **old** index and is therefore always `0`. The haircut is written to a slot nobody reads — a stale/adjacent-index read, the direct analog of the admesh out-of-bounds read over connectivity state in `stl_update_connects_remove_1`.

### Finding Description
Relevant code:

- `requestWithdraw` (`IdleCreditVault.sol:260-293`): `currentEpoch = epochNumber`; stores `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`.
- `deposit` (`IdleCreditVault.sol:607-611`): when `isEpochRunning()` (the borrower-repayment deposit inside `stopEpoch`), executes `epochNumber += 1`.
- `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`): when `_amount < pendingBasis`, computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` and stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice`. Because the epoch-bumping `deposit` precedes it within the same `stopEpoch` flow, this is `epochNumber = requestEpoch + 1`.
- `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-801`): reads `lossEpoch = lastWithdrawRequest[_user]` (the *request* epoch), so `lossRecoveryPrice == 0` → early return, no haircut applied.
- `requestWithdraw` guard (`IdleCreditVault.sol:261-271`): checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, which is `0`, so the "must claim loss-adjusted receipt first" protection never triggers either.

Sequence:

1. Epoch N (running/buffer): user calls `cdoEpoch.requestWithdraw(...)`. `lastWithdrawRequest[user] = N`, `withdrawsRequestsByEpoch[user][N] = amount`, `pendingWithdraws += amount`.
2. Manager calls `stopEpochWithDuration(_lossAmount)` after `epochEndDate`. The strategy `deposit` bumps `epochNumber` to N+1, then `collectWithdrawFunds(pendingToFund)` stores `lossRecoveryPriceByEpoch[N+1] = price < 1e18` and zeroes `pendingWithdraws`.
3. User calls `cdoEpoch.claimWithdrawRequest()`. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N]` → `0` → returns 0. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[user]` **at par** (full `amount`, no haircut) via `_transferFundedClaim`.

The broken invariant is the loss waterfall: `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` deliberately socializes a pro-rata share of the realized loss onto pending receipts, but the haircut is stored at index N+1 while every reader uses index N.

There is a second, symmetric consequence: a *new* request made in epoch N+1 sets `lastWithdrawRequest[user] = N+1`. Any user whose request lands in epoch N+1 will have `lossRecoveryPriceByEpoch[N+1] != 0` and `withdrawsRequestsByEpoch[user][N+1] != 0`, so **their** claim gets haircut by a loss that occurred before they even requested (and the re-request guard at `IdleCreditVault.sol:263-271` will revert their later requests until they claim the wrongly-haircut receipt). The price is applied to the wrong cohort both ways.

Existing guards do not stop this: `isEpochWithdrawZero`/price-zero checks only reject a rounded-to-zero price; `epochNumber <= lastWithdrawRequest` gating in `_claimFundedWithdrawRequest` only enforces the one-epoch wait; nothing validates that the price key matches the request epoch. No privileged or dishonest actor is needed — only an honest manager calling `stopEpochWithDuration` with a partial loss.

### Impact Explanation
Direct theft / broken loss socialization with quantifiable loss. Every pending withdrawer from the loss epoch claims 100% instead of `lossRecoveryPrice`. The strategy actually received only `_amount < pendingBasis` from the borrower, so paying full `pendingBasis` drains underlying that backs active tranche holders — the pending cohort's loss share (`pendingLoss = _lossAmount * pendingBasis / totalBasis` per `previewLossAdjustedWithdrawFunds`) is transferred to active AA/BB LPs and/or later claimers, and if reserves are insufficient, later claims revert (permanent freezing of unclaimed funds). Symmetrically, epoch N+1 requesters are over-haircut (unjustified loss). Severity scales with `pendingWithdraws` and `_lossAmount`; e.g., with 1M USDC pending and a 20% total-basis loss split, pending withdrawers collectively over-claim their pro-rata share (~200k-weighted) at the expense of the pool.

### Likelihood Explanation
Requires `stopEpochWithDuration` (partial-loss stop, e.g., borrower underpays or a loss is realized) while `pendingWithdraws > 0` — a normal, honest-manager code path explicitly built for this scenario, not an edge case. Any user with a pending request in that epoch triggers it by simply claiming. Likelihood is moderate: it needs a loss event with pending receipts, but when that occurs the bug fires deterministically for every claimer.

### Recommendation
Store the haircut under the epoch that owns the receipts, i.e., in `collectWithdrawFunds` use `lossRecoveryPriceByEpoch[epochNumber - 1]` (or pass the request epoch from the CDO / snapshot `epochNumber` before the incrementing `deposit`). Equivalently, make the claim path read `lossRecoveryPriceByEpoch` keyed consistently — but since `lastWithdrawRequest` and `withdrawsRequestsByEpoch` are both keyed by request epoch, keying the write by request epoch is the minimal fix. Add a regression test: request in epoch N → `stopEpochWithDuration(loss)` → claim pays `amount * lossRecoveryPrice / 1e18`, and a fresh epoch-N+1 requester is not haircut.

### Proof of Concept
Foundry fork test (against the `IdleCreditVault`/`IdleCDOEpochVariant` harness used in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossRecoveryPriceWrongEpochKey() external {
    address user = makeAddr('victim');
    _depositWithUser(user, 10_000 * ONE_SCALE, true);

    // epoch N: request withdraw during buffer
    vm.prank(user);
    uint256 claimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));
    uint256 requestEpoch = strategy.epochNumber();
    assertEq(strategy.lastWithdrawRequest(user), requestEpoch);

    // borrower underpays: manager stops epoch with a realized loss
    _startEpochAndCheckPrices(0);
    uint256 loss = claimBasis / 2; // partial loss covering pending basis
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - loss);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, loss); // deposit() bumps epochNumber to N+1 first

    // haircut was stored under N+1, not N
    assertGt(strategy.lossRecoveryPriceByEpoch(requestEpoch + 1), 0);
    assertEq(strategy.lossRecoveryPriceByEpoch(requestEpoch), 0); // claim-side key is empty

    // user claims FULL amount at par — haircut never applied
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(user) - balPre, claimBasis); // expected: claimBasis * price / 1e18
}
```

Note: I verified the read/write key asymmetry in `IdleCreditVault.sol` directly; the precise ordering of `deposit` (epoch bump) vs `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpochWithDuration` could not be fully re-confirmed within this session's tool budget — if `collectWithdrawFunds` were invoked strictly *before* the epoch increment, the keys would match and the bug would not hold. The PoC's `assertEq(lossRecoveryPriceByEpoch[requestEpoch], 0)` line is the decisive check either way.
