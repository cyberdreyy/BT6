### Title
Claimed instant-withdraw receipts stay in `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`, inflating the default claim basis and enabling a second default-recovery claim - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external AuraLocker bug is a denominator mismatch: a global counter (`getPastTotalSupply`) counts *all* locked balances while the per-account measure (`getPastVotes`) counts only a subset (delegated balances), so any proportional distribution computed against the global total is skewed. The same class exists in `IdleCreditVault`: the per-epoch instant-withdraw aggregates `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are only ever incremented (request time) and decremented (default-recovery claim time), but **never cleared when a user successfully claims through the normal funded path** `claimInstantWithdrawRequest`. The per-epoch "total" therefore counts receipts whose holders already exited, while per-user claimability should only cover unclaimed receipts.

### Finding Description
`requestInstantWithdraw` records three pieces of state (IdleCreditVault.sol:365-375):
- `instantWithdrawsRequests[_user] += _amount`
- `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount`
- `instantWithdrawClaimsByEpoch[epochNumber] += _amount`

`claimInstantWithdrawRequest` (lines 380-393) pays the user, burns the receipt, and resets `instantWithdrawsRequests[_user]` to 0 — but it leaves both per-epoch entries untouched. There is no other code path that clears `instantWithdrawsRequestsByEpoch` outside of `_claimDefaultedInstantWithdrawRequest` (line 847), which only runs after `defaultRecoveryFinalized`.

Two consequences follow:

1. **Inflated default claim basis.** `defaultPendingClaimBasis()` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`. This includes receipts that were already fully claimed. `finalizeDefaultRecovery` (line 688) divides the real reserve by this inflated `totalBasis`, so `defaultRecoveryPrice` is set too low. Every legitimate claimant (normal withdraw receipts, unfunded instant receipts, active LPs via the mint/burn at lines 701-705) gets a smaller payout than the true pro-rata share, and the excess `defaultRecoveryReserve` has no sweep function — it is permanently locked in the strategy.

2. **Double claim on the defaulted epoch.** `_claimDefaultedInstantWithdrawRequest` (lines 842-856) computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — which still holds the already-claimed amount — burns `claimBasis` strategy tokens from `_user` and pays `claimBasis * defaultRecoveryPrice`. A user who already claimed their instant receipt can claim the same basis a second time if they hold (or re-acquire, e.g. via a fresh post-default `requestWithdraw` that mints receipt tokens at line 255, or a donated/transferred balance) enough strategy tokens to satisfy the `_burn`. This is a direct theft of recovery funds owed to other claimants.

Attack path (unprivileged lender, epoch running): deposit AA, trigger the instant-withdraw path via `IdleCDOEpochVariant.requestWithdraw` when APR dropped (lines 761-768 of IdleCDOEpochVariant), wait for funding, call `claimWithdrawRequest`/`claimInstantWithdrawRequest` and receive full payout. The stale per-epoch entries persist. When the borrower later defaults in that same epoch number context and `finalizeDefaultRecovery` runs, the attacker's stale basis both dilutes `defaultRecoveryPrice` for everyone and remains claimable a second time.

### Impact Explanation
- Every honest defaulted-epoch claimant and every active tranche holder receives `reserveAmount / inflatedBasis` instead of `reserveAmount / realBasis`. If claimed instant receipts are fraction `f` of the recorded instant basis, all recovery payouts are scaled down by up to that factor; the unclaimed remainder is locked in `defaultRecoveryReserve` forever (no owner/manager sweep exists — direct theft + permanent freezing of recovery funds).
- The double-claim path lets the attacker withdraw `claimBasis * defaultRecoveryPrice` a second time, paid from the same reserve, further reducing honest payouts one-for-one.

### Likelihood Explanation
- Instant withdrawals trigger automatically whenever `lastEpochApr > currentApr + instantWithdrawAprDelta` (IdleCDOEpochVariant.sol:763), a normal market event, not privileged misconfiguration.
- Claiming before a default is the expected user flow; nothing warns or blocks it.
- The second claim requires the attacker to hold strategy tokens again, which is achievable through the post-default `requestWithdraw` mint path (line 255) or any balance acquired from another receipt holder, since receipt tokens are ordinary ERC20 balances.
- No existing guard stops it: `_ensureDefaultRecoveryInitialized`, `defaultInstantWithdrawsFinalized`, and the `pendingInstantWithdraws != 0` gate all still pass, because the staleness is precisely in the per-epoch counters those checks rely on.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting for the epochs being paid out, mirroring `_clearWithdrawClaimForEpoch`: subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (tracking the request epoch per user, e.g. via a `lastInstantWithdrawRequest` marker or by clearing all non-zero epochs), so that `defaultPendingClaimBasis` reflects only genuinely unclaimed receipts and `_claimDefaultedInstantWithdrawRequest` finds zero basis for already-paid users.

### Proof of Concept
```solidity
// Fork test sketch (Foundry), contracts: IdleCDOEpochVariant + IdleCreditVault
// Setup: AA deposit, epoch running, force APR drop so requestWithdraw takes
// the instant path.
uint256 trancheAmt = idleCDO.depositAA(10_000e6);
// manager lowers apr beyond instantWithdrawAprDelta
vm.prank(manager); strategy.setAprsWithBuffer(0, epochDur, buffer);
uint256 requested = cdoEpoch.requestWithdraw(trancheAmt, address(AAtranche));

// CDO funds the instant request; user claims normally
// ... collectInstantWithdrawFunds path ...
cdoEpoch.claimInstantWithdrawRequest(); // or strategy.claimInstantWithdrawRequest via CDO
uint256 balAfterFirstClaim = underlying.balanceOf(user);

// BUG: per-epoch entries still hold the claimed basis
uint256 epoch = strategy.epochNumber();
assertEq(strategy.instantWithdrawsRequestsByEpoch(user, epoch), requested); // stale
assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), requested);          // stale

// Trigger a second pending instant receipt (so pendingInstantWithdraws != 0)
// then simulate borrower default in this epoch and finalize:
//   strategy.defaultPendingClaimBasis() == pendingWithdraws + requested (inflated)
//   finalizeDefaultRecovery => defaultRecoveryPrice diluted
//   user calls claimInstantWithdrawRequest again =>
//     _claimDefaultedInstantWithdrawRequest pays claimBasis * defaultRecoveryPrice
//     provided user holds >= claimBasis receipt tokens
assertGt(underlying.balanceOf(user), balAfterFirstClaim); // second payout
```
