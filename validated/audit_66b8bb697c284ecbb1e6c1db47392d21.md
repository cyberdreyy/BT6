### Title
Protocol-version asymmetry in duplicate tenure-start detection lets a v1 signer sign a conflicting tenure-change block that v2 signers already signed - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`validate_tenure_change_payload` is the proposal-time check that stops a miner from getting two different tenure-start blocks signed for the same tenure (`DuplicateBlockFound`). The repository's own design documentation states this check uses different "already accepted" definitions per signer protocol version: v2 treats a block as blocking a duplicate tenure-start if it is *locally or globally accepted* (`get_last_signed_block`), while v1 only blocks on a *globally accepted* block (`get_last_globally_accepted_block`). [1](#0-0) 

This is structurally the same class of bug as the external report: two logically-parallel code paths ("vaults" there, "signer protocol versions" here) use inconsistent criteria to answer the same equality question ("has this tenure already produced an accepted/valued block?"), and the less-strict path can be exploited to produce a divergent outcome.

### Finding Description
`check_proposal` for both protocol versions calls into version-specific `validate_tenure_change_payload` when a proposed block carries a tenure-change transaction: [2](#0-1) [3](#0-2) 

Per the maintainers' own architecture notes, the duplicate-tenure-start guard inside these two functions is intentionally asymmetric:
- v2's `validate_tenure_change_payload` counts a tenure as already started if there is a *locally or globally accepted* block in it (`get_last_signed_block`).
- v1's `validate_tenure_change_payload` counts a tenure as already started only if there is a *globally accepted* block in it (`get_last_globally_accepted_block`). [4](#0-3) 

Both `get_last_signed_block` and `get_last_globally_accepted_block` exist as distinct queries in `signerdb.rs`, confirming the two functions genuinely read different acceptance states rather than being an equivalent alias. [5](#0-4) 

The documentation also states this duplicate check runs **only at proposal arrival** and is never re-run at validate-ok or at signing time: [6](#0-5) 

The only later backstop is the pre-commit "own-tenure conflict" guard, which is scoped to conflicts the *evaluating signer itself* has already signed (`get_signed_conflicts`) — it cannot see that a *different* signer (running v2) has already signed a rival tenure-start block: [7](#0-6) [8](#0-7) 

Concretely, during a period where the signer set contains both v1 and v2 signers (e.g. mid-upgrade), a miner (or a miner racing with normal network delay) can:
1. Propose tenure-start block `A` for tenure `T`. v2 signers locally accept and sign `A` quickly (this is enough to satisfy v2's stricter `get_last_signed_block` check against a second proposal, but `A` may not yet be *globally* accepted, i.e., not yet reached the network's stacks tip).
2. Propose a second, different tenure-start block `B` for the same tenure `T` before `A` becomes globally accepted.
3. v1 signers evaluating `B` call `validate_tenure_change_payload`, which only checks `get_last_globally_accepted_block` — finds none for tenure `T` (because `A` is only locally accepted so far) — and so does **not** reject `B` as a duplicate.
4. Those v1 signers proceed through pre-commit and signing for `B`. The subsequent own-tenure conflict guard only stops a signer from contradicting *its own* prior signature, so a v1 signer that never signed `A` has nothing to detect the conflict with `B`.

The result is two different blocks (`A`, signed by v2 signers, and `B`, signed by v1 signers) both accumulating valid signer signatures for the same tenure start, from disjoint subsets of the signer set.

### Impact Explanation
This breaks the "one accepted (canonical) block per tenure/height" equality that the signer protocol is meant to guarantee. If each of the two conflicting blocks can independently accumulate ≥70% weight support (from the v1-following vs v2-following portions of the signer set respectively), `NakamotoBlockHeader::verify_signer_signatures` on the node side would accept whichever block arrives with enough weight, and the network could end up with two live, mutually exclusive, signer-endorsed proposals for the same tenure. This matches the required Critical impact category: a signer signing a conflicting block. [9](#0-8) 

### Likelihood Explanation
The condition requires a signer set that is not uniformly on the same signer-protocol version (a real, if transient, situation during rolling signer upgrades), plus a miner proposing two competing tenure-start blocks in quick succession before global acceptance of the first propagates. This is plausible for a single miner plus normal StackerDB gossip latency, without needing a majority of signers or any signer's key — only the natural asymmetric weight split between v1-run and v2-run signers.

### Recommendation
Make the duplicate tenure-start detection in `validate_tenure_change_payload` consistent across `stacks-signer/src/chainstate/v1.rs` and `stacks-signer/src/chainstate/v2.rs`: both should key off the same acceptance definition (locally-or-globally accepted, i.e. `get_last_signed_block`), so that a v1 signer refuses to sign a second tenure-start block whenever any signer (v1 or v2) has already signed a first one for that tenure. Additionally, consider re-running the duplicate-tenure check at pre-commit/signing time (not only at proposal arrival) so a signature cast against a rival cannot slip through the widened proposal-time window.

### Proof of Concept
Not independently executable from the index; this is based on the documented asymmetry between the two `validate_tenure_change_payload` implementations and the confirmed existence of distinct `get_last_signed_block` / `get_last_globally_accepted_block` queries in `signerdb.rs`. I was not able to retrieve the full bodies of `validate_tenure_change_payload` in `v1.rs`/`v2.rs` or the exact SQL of the two `signerdb.rs` queries within the available tool budget to show the byte-level diff; the finding rests on the explicit statement of this asymmetry in the repository's own architecture documentation (`docs/signer-flows.md`) plus confirmed call sites and confirmed distinct function names. A Devin session with full file access could pull the exact function bodies to construct a concrete two-signer-version integration test reproducing the double-signature scenario described above.
