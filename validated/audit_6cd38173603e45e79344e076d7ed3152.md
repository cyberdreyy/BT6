### Title
Re-requesting a withdrawal after a loss-adjusted epoch erases the haircut key and lets the receipt claim at par, draining funds reserved for other claimants — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault` supports `stopEpochWithDuration`-style partial funding: when the borrower funds less than `pendingWithdraws`, `collectWithdrawFunds` stores a haircut in `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` (`IdleCreditVault.sol:411-430`). The user's loss-adjusted payout is later located exclusively via `lastWithdrawRequest[_user]` as the epoch key (`IdleCreditVault.sol:789-801`). A user who files a *second* `requestWithdraw` in a later epoch — an explicitly supported action ("if a user does not claim... he will have to wait for another epoch to claim both requests", `IdleCreditVault.sol:323-324`) — overwrites `lastWithdrawRequest[_user]`. The loss-epoch key is then unreachable: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[newEpoch] == 0` and falls through to `_claimFundedWithdrawRequest`, which pays the *aggregate* `withdrawsRequests[_user]` (still containing the haircutted epoch's amount, since `_clearWithdrawClaimForEpoch` never ran for it) at full par (`IdleCreditVault.sol:319-350`).

### Finding Description
Invariants broken: one-receipt-one-priced-payout and loss socialization. Sequence:

1. Epoch N is running (`epochNumber == N`). Attacker (any KYC'd tranche holder) calls `IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw` mints a receipt, sets `withdrawsRequests[attacker] += X`, `withdrawsRequestsByEpoch[attacker][N] += X`, `lastWithdrawRequest[attacker] = N`, `pendingWithdraws += X`.
2. Honest borrower returns less than owed; `stopEpoch`/`stopEpochWithDuration` calls `collectWithdrawFunds(funded < pendingBasis)`. Since `funded < pending`, it sets `lossRecoveryPriceByEpoch[N'] = funded*RECOVERY_FULL/pendingBasis` and `pendingWithdraws = 0`. Only `funded` underlying is pulled into the strategy.
3. In a later epoch M (or even the immediately following buffer, while the claim is still pending), the attacker calls `requestWithdraw` again with a dust amount (1 wei of tranche). `lastWithdrawRequest[attacker]` is overwritten to M.
4. After one epoch, the attacker calls `claimWithdrawRequest` via the CDO. `_claimLossAdjustedWithdrawRequest` computes `lossRecoveryPriceByEpoch[M] == 0` and returns 0; `_claimFundedWithdrawRequest` passes its epoch gate and pays `withdrawsRequests[attacker]` — which includes the full pre-haircut `X` — at par via `_transferFundedClaim`.

The strategy only ever received `funded < X` for that receipt bucket, so the excess over the haircut is paid out of underlyings reserved for other pending/funded claimants. `_transferFundedClaim`'s reserve guard (`IdleCreditVault.sol:897-907`) only protects `defaultRecoveryReserve`; the loss-funded balance has no such isolation. Subsequent legitimate claimants' `safeTransfer` calls revert → their funded receipts are permanently underfunded (insolvency / theft of unclaimed withdrawals).

### Impact Explanation
Direct theft and insolvency: the attacker extracts `X * (1 - lossRecoveryPrice)` more than funded. Because strategy tokens are burned 1:1 against a claim that was only haircut-funded, the strategy's underlying balance is depleted below the sum of remaining receipts; the last claimant(s) lose that amount permanently. Quantification: with pendingBasis = 100k USDC, funded = 60k (recovery price 0.6), an attacker holding 50k of receipts re-requests once and claims the full 50k instead of 30k — a 20k USDC overdraw borne by other claimants.

### Likelihood Explanation
Requires a loss-adjusted `collectWithdrawFunds` (partial borrower funding at stop), an unlocked receipt in that epoch, and one extra `requestWithdraw` — all unprivileged actions on documented paths. No privileged actor misbehavior is needed; the trigger is a single cheap dust re-request during any later epoch/buffer, which the code comments explicitly bless. Likelihood is gated mainly on a partial-funding event occurring while the attacker holds a receipt.

### Recommendation
Key loss-recovery claims off per-epoch data instead of the mutable `lastWithdrawRequest`. Concretely: in `_claimLossAdjustedWithdrawRequest`, iterate or check `withdrawsRequestsByEpoch[_user]` against all epochs that have `lossRecoveryPriceByEpoch` set (or store the loss epoch per user at request time / at `collectWithdrawFunds` time), and block `requestWithdraw` while the user holds an unclaimed receipt in a loss-adjusted epoch. Alternatively, settle the haircutted portion of `withdrawsRequests[_user]` to its recovered value when the second request is made.

### Proof of Concept
Foundry fork PoC (against the existing `IdleCreditVault.t.sol` harness):

```solidity
function testReRequestEscapesLossHaircut() external {
  uint256 amount = 100_000 * ONE_SCALE;
  idleCDO.depositAA(amount); // attacker-held AA tranches

  _startEpochAndCheckPrices(0);
  // attacker requests withdraw of all tranches in epoch 0
  cdoEpoch.requestWithdraw(IERC20Detailed(AAtranche).balanceOf(address(this)), address(AAtranche));

  // borrower repays only 60% at stopEpoch -> collectWithdrawFunds stores lossRecoveryPriceByEpoch
  uint256 owed = _expectedFundsEndEpoch();
  deal(address(underlying), borrower, owed * 6 / 10, true);
  vm.prank(borrower); underlying.approve(address(cdoEpoch), owed * 6 / 10);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  cdoEpoch.stopEpoch(0, durationLoss); // stopEpochWithDuration path, partial funding

  // epoch rolls; attacker files a dust re-request, overwriting lastWithdrawRequest
  _startEpochAndCheckPrices(1);
  vm.prank(address(this));
  cdoEpoch.requestWithdraw(1, address(AAtranche));
  _stopEpochAndCheckPrices(1, apr, fullFunding);

  // claim: loss-adjusted lookup misses (key = new epoch), funded path pays par
  uint256 balPre = underlying.balanceOf(address(this));
  cdoEpoch.claimWithdrawRequest();
  // received > attackerBasis * lossRecoveryPrice / RECOVERY_FULL  -> overpayment
  assertGt(underlying.balanceOf(address(this)) - balPre, expectedHaircutPayout);
}
```

Uncertainty: the exact epoch index used as the `lossRecoveryPriceByEpoch` key relative to `lastWithdrawRequest` should be confirmed in the PoC (epoch counter is bumped inside `deposit` during stop processing, `IdleCreditVault.sol:607-616`); if they coincide, the bug requires the re-request to shift `lastWithdrawRequest` off that key, which is the core flaw either way.
