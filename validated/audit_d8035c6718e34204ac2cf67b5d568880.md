### Title
Denial-of-Service via lamport pre-funding griefing of `SystemInstruction::CreateAccount` - (File: `programs/system/src/system_processor.rs`)

### Summary
The system program's `create_account` function treats a nonzero lamport balance on the destination account as proof that the account is "already in use," and unconditionally rejects the instruction in that case. Because `SystemInstruction::Transfer` only requires the *sender* to sign (the recipient does not need to sign or even exist as a keypair-controlled account), any unprivileged transaction sender can send a trivial amount of lamports to an arbitrary address before its intended owner submits a `CreateAccount` transaction for that same address. This permanently breaks the invariant `to.get_lamports() == 0` that `create_account` relies on, causing every future `CreateAccount` attempt at that address to fail with `SystemError::AccountAlreadyInUse` — an exact analog of the reported `AccountantDelegate.sweepInterest` bug, where a third party donates tokens to `treasury` and breaks the "balance must be zero" invariant checked after the fact.

### Finding Description
In `create_account`, before allocating space and assigning the owner, the code checks:

```rust
let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
if to.get_lamports() > 0 {
    ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
    return Err(SystemError::AccountAlreadyInUse.into());
}
allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
``` [1](#0-0) 

This assumes the destination account can only carry a nonzero balance if it has legitimately been created/used before. That assumption is false: `transfer`/`transfer_verified` only requires the `from` account to sign, and moves lamports into `to` unconditionally:

```rust
fn transfer(from_account_index, to_account_index, lamports, invoke_context, instruction_context) -> Result<(), InstructionError> {
    if !instruction_context.is_instruction_account_signer(from_account_index)? {
        ...
        return Err(InstructionError::MissingRequiredSignature);
    }
    transfer_verified(from_account_index, to_account_index, lamports, invoke_context, instruction_context)
}
``` [2](#0-1) 

Any unprivileged account holder can therefore send even 1 lamport to any target pubkey with zero cooperation from that pubkey's owner. If a dApp, wallet, or program later attempts to `CreateAccount` at that same address (e.g., to onboard a new user, or in a deterministic-address flow), the transaction will deterministically fail with `AccountAlreadyInUse`, exactly mirroring the external report's pattern where a griefer breaks an "expected zero balance" invariant relied upon by downstream logic.

The Agave team's own fix acknowledges this exact bug class: a new `SystemInstruction::CreateAccountAllowPrefund` instruction was added, explicitly to allow account creation "without checking for 0 lamports," gated behind the `create_account_allow_prefund` feature (SIMD-0312):

```rust
/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
fn create_account_allow_prefund(...) -> Result<(), InstructionError> { ... }
``` [3](#0-2) [4](#0-3) 

This confirms the vulnerability is real and previously unmitigated: the legacy, still-widely-used `CreateAccount` instruction remains fully susceptible to lamport-prefund griefing for any caller who has not switched to the new instruction (which itself is feature-gated and not yet universally usable/adopted).

### Impact Explanation
Any address that a program or user intends to initialize via the plain `CreateAccount` path can be permanently denied by anyone sending it a trivial lamport transfer beforehand. This is a low-cost, unprivileged, transaction-triggered DoS against arbitrary target accounts — analogous in class and severity reasoning to the High-severity finding in the report (broken invariant leading to permanent bricking of a critical code path, with no alternate recovery for the legacy instruction path). It can be used to grief user onboarding, PDA-adjacent address creation flows, or any protocol relying on deterministic `CreateAccount` calls, and can also disrupt transaction fee/compute accounting expectations for programs that assume a successful creation.

### Likelihood Explanation
High. The attack requires only a signed `SystemInstruction::Transfer` from the attacker's own funded account to the victim address — no special privileges, no cooperation from the target, and negligible cost (as little as 1 lamport, though rent-exemption thresholds make griefing cheap but not free for account resurrection purposes). This is fully reachable from a single unprivileged transaction sender.

### Recommendation
For code paths that still rely on `SystemInstruction::CreateAccount`, migrate to `SystemInstruction::CreateAccountAllowPrefund` once the `create_account_allow_prefund` feature is active cluster-wide, since it removes the flawed "lamports == 0 implies unused" check while preserving the other safety checks (data emptiness, ownership). Until then, document this griefing vector clearly for downstream program authors and consider deprecating the strict lamport check in `create_account` in favor of the emptiness/ownership checks alone, matching the semantics already implemented in `create_account_allow_prefund`.

### Proof of Concept
1. Attacker generates target address `T` (e.g., a keypair the victim intends to use, or a deterministic address the victim will later submit a `CreateAccount` transaction for).
2. Attacker submits `SystemInstruction::Transfer { lamports: 1 }` from their own signer account to `T`, requiring only the attacker's signature per `transfer` in `programs/system/src/system_processor.rs` (lines 245-268).
3. Victim later submits `SystemInstruction::CreateAccount { lamports, space, owner }` targeting `T`.
4. `create_account` observes `to.get_lamports() > 0` (now `1`) and returns `SystemError::AccountAlreadyInUse`, permanently failing account creation at `T` for as long as the attacker keeps re-funding it (or indefinitely if the victim has no fallback), as shown in `programs/system/src/system_processor.rs` lines 161-171.

#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
