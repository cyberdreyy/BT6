Confirmed: `delete_member` (`multisig2/src/lib.rs:356-379`) only purges requests *created by* the deleted member — it removes `requests` where `r.member == member`, but never scans the `confirmations` sets of *other* requests for a matching entry from the deleted member. This produces a stale-cache-vs-live-state divergence directly analogous to the Redstone `cacheUpdatedAt`/`maxCacheStaleness` bug: a confirmation "cached" at threshold-count time is never invalidated when the underlying trusted set (live members) changes.

### Title
Stale confirmations from removed members still count toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`confirm` (`multisig2/src/lib.rs:294-315`) tallies `HashSet<String>` confirmations against the *current* `num_confirmations` but the confirmations set for a request is never re-validated against the live `members` set. When a member is deleted via `DeleteMember`, `delete_member` only cleans up requests **authored** by that member and their `num_requests_pk` entry; it does not scan `confirmations` on other pending requests for entries from the removed member. [1](#0-0) 

### Finding Description
The binding that should hold is: `confirmations counted for request R == confirmations from accounts that are currently live members`. This breaks because `delete_member` filters requests by `r.member == member` (the request's *author*) — i.e., requests created by the removed member — while leaving every confirmation the removed member cast on *other* still-pending requests untouched in the `confirmations` LookupMap. [2](#0-1) 

Concretely: request R (authored by member A) receives a confirmation from member B. Later, a separate `DeleteMember{member: B}` request executes and passes threshold (removing B). R still exists with B's confirmation baked into its `confirmations` set, since `delete_member` never touched R (R.member == A, not B). If enough of the remaining live members confirm R afterward, `confirm` (`multisig2/src/lib.rs:304`) will count B's stale confirmation toward `num_confirmations`, allowing R to execute with confirmations from a set that includes a member no longer authorized — i.e., execution below the *live* member threshold. [3](#0-2) 

### Impact Explanation
This is a Critical-tier binding violation per the rules: "a multisig request executed below threshold." Any pending `Transfer`, `AddKey`, `FunctionCall`, etc. request can be executed with one fewer *live* confirmation than intended, effectively lowering the real security threshold of the multisig without an explicit `SetNumConfirmations` action — using stale approval from an account that has since been un-trusted.

### Likelihood Explanation
Likelihood is contingent on a member being removed while unrelated requests remain pending with that member's confirmation attached — a state easily reachable in normal operation: any member can `add_request`/`confirm` and requests persist until executed or explicitly deleted (with a 15-minute cooldown, `REQUEST_COOLDOWN`). No malicious/off-path action is required beyond ordinary confirm/delete-member flows already exposed to all members; this is fully reachable by unprivileged (from the perspective of "not entitled to that specific request") members acting through the normal API.

### Recommendation
When executing `DeleteMember`, iterate over all pending `requests`/`confirmations` and strip the removed member's entry from every confirmations set (not just requests they authored), or alternatively re-validate on `confirm`/execution that every account in a request's stored confirmations set is still a current member before counting it toward the threshold.

### Proof of Concept
1. Initialize multisig with members `[A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request` for `Transfer{amount}` targeting some receiver → request `R1` (author A, 0 confirmations).
3. `B` calls `confirm(R1)` → `confirmations[R1] = {B}` (1/3).
4. Separately, `A`, `C`, `D` submit and confirm a `DeleteMember{member: B}` request, which executes (3 live confirmations, unrelated to R1) and removes `B` from `members`. `delete_member` only inspects requests where `r.member == B` (i.e., requests **authored** by B) — `R1` is authored by `A`, so it is untouched; `confirmations[R1]` still contains `B`.
5. `C` calls `confirm(R1)` → `confirmations[R1].len() + 1 == 2 + 1 == 3 >= num_confirmations(3)` → `R1` executes with counted confirmations `{B, C}` plus the executor, even though `B` is no longer a member — i.e., only 2 *live* members (A initiated but didn't confirm; only C confirmed plus the stale B) actually authorized `R1`, below the real 3-of-4 threshold.     pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);

            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
