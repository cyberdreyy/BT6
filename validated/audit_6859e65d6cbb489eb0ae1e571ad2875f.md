### Title
Front-running griefing of EIP-8130 counterfactual `Create` permanently blocks a victim's account-creation transaction - (File: `crates/execution/eip8130/src/apply.rs`)

### Summary
`AccountChangeApplier::apply_create` derives the CREATE2 address for a new EIP-8130 smart account deterministically from `(user_salt, code, initial_actors)` and rejects the operation with `ApplyError::AlreadyInitialized` if that address already carries EIP-8130 state [1](#0-0) . Because a signed `Create` account-change (including its `user_salt`, `code`, and `initial_actors`) is fully visible in the public mempool before inclusion, an attacker can copy those exact fields into their own transaction and get it included first, causing the victim's original transaction to fail at admission/inclusion with `AlreadyInitialized`, exactly mirroring the `LockedStakingPools.participate` griefing pattern (attacker front-runs with the victim's own parameters to trip a "state already set" guard).

### Finding Description
The counterfactual account-creation flow works as follows:
1. `AccountChangeApplier::compute_address` derives the CREATE2 address as `keccak256(0xff || ACCOUNT_CONFIG || effective_salt || code_hash)`, where `effective_salt = keccak256(user_salt || actors_commitment(initial_actors))` [2](#0-1) .
2. `apply_create` reads the account's current `AccountState` at that derived address and errors with `ApplyError::AlreadyInitialized` if `state.is_initialized()` is already true [3](#0-2) .
3. Both mempool admission (`BaseTransactionValidator::validate_eip8130_full` → `TransactionAuthorizer::authorize_and_apply` → `apply_create`) and block inclusion run through this exact same choke point [4](#0-3) [5](#0-4) .
4. The pool explicitly maps a failed `apply_create` due to `AlreadyInitialized` to the rejection reason `"create account already exists"` [6](#0-5) .

An attacker observing a pending, signed EIP-8130 `Create` transaction in the mempool can extract its `user_salt`, `code`, and `initial_actors` verbatim (these are public calldata fields of the pending, valid-but-unmined transaction) and submit their own transaction containing an identical `Create` entry with a higher fee/priority. Because the derived CREATE2 address is a pure function of those three fields, the attacker's copy resolves to the *same* address. When the attacker's transaction lands first, it sets `state.local_sequence = 1` and installs the identical `initial_actors` at that address [7](#0-6) . The victim's original transaction, which arrives afterward, is then rejected with `AlreadyInitialized` — permanently, since the guard is unconditional and does not distinguish "attacker front-run with identical parameters" from any other double-create attempt; the victim cannot resubmit the same create and must instead craft a brand-new salt, changing the resulting account address entirely.

This is structurally analogous to the reported `LockedStakingPools.participate` bug: the victim's transaction updates/creates state gated by an "already set" check (`position.amount != 0` there, `state.is_initialized()` here), and an attacker who can observe the victim's intended parameters before inclusion front-runs with those same parameters purely to trip the guard and grief the legitimate transaction.

### Impact Explanation
Any transaction whose `account_changes` bundles the `Create` together with a subsequent `ConfigChange` or with `calls` targeting the freshly created account (a common integration pattern explicitly exercised in this codebase's own tests, e.g. `create_then_config_change_authorizes_against_freshly_created_account` [8](#0-7) ) is atomic: if the `Create` sub-step fails, the whole transaction is rejected/reverted and none of the intended setup (actor authorization, funding calls, etc.) happens. An attacker can repeatedly front-run the same victim's resubmitted create attempts as long as the victim keeps reusing the same `(user_salt, code, initial_actors)` tuple, indefinitely denying that specific counterfactual account from ever being created by the intended party via that transaction, and wasting the victim's transaction-preparation/gas-estimation cycles. This is a denial-of-service/griefing vector reachable from a single unprivileged transaction sender against a specific target transaction visible in the public mempool, consistent with a "High" severity griefing classification in the original report's terms.

### Likelihood Explanation
Likelihood is directly tied to mempool visibility: any signed, not-yet-included EIP-8130 transaction with a `Create` account change is public before inclusion, and the attack requires no special access, roles, or capital beyond outbidding the victim's fee — a standard front-running primitive already assumed reachable by "an unprivileged transaction sender" per the scope of this analysis. No cryptographic secrets are needed because `user_salt`, `code`, and `initial_actors` are plaintext transaction fields.

### Recommendation
Bind the derived CREATE2 address (or the `AlreadyInitialized` guard) to the intended sender/owner identity rather than purely to `(user_salt, code, initial_actors)`, e.g. by requiring the create's signing actor to match on a re-submission, or by allowing a `Create` that targets an address already initialized with an *identical* actor set and code (i.e., idempotent re-creation) to succeed as a no-op instead of hard-erroring, so an attacker's copy cannot be weaponized purely to block the legitimate submitter. Alternatively, incorporate a value derived from the signer's own authentication (already bound at the final sender-authentication step) earlier into the address derivation so a third party cannot reproduce the same derived address without also being able to authenticate as that actor.

### Proof of Concept
1. Victim signs and broadcasts an `Eip8130Signed` transaction containing `AccountChange::Create(CreateEntry { user_salt, code, initial_actors })` plus a following `AccountChange::ConfigChange` (as in the codebase's own `create_then_config_change_authorizes_against_freshly_created_account` test pattern) [9](#0-8) .
2. Attacker observes the pending transaction in the mempool and extracts `user_salt`, `code`, `initial_actors`.
3. Attacker crafts and signs their own `Eip8130Signed` transaction with an identical `AccountChange::Create(CreateEntry { user_salt, code, initial_actors })` (attacker can be its own signer for a different `sender`/actor scope as long as the `Create` entry's fields, which alone drive `compute_address`, are copied) with a higher fee, and submits it.
4. Attacker's transaction is included first; `apply_create` succeeds, setting `state.local_sequence = 1` and installing `initial_actors` at the derived address [7](#0-6) .
5. Victim's original transaction is later processed; `apply_create` now finds `state.is_initialized()` true and returns `ApplyError::AlreadyInitialized`, which propagates through `TransactionAuthorizer::authorize_and_apply` as `TxAuthError::Apply` [10](#0-9) , causing pool rejection (`"create account already exists"`) or inclusion failure of the victim's transaction, including any bundled `ConfigChange`/`calls` that depended on that create succeeding.

    pub fn apply_create(
        storage: &mut AccountConfigurationStorage<'_>,
        entry: &CreateEntry,
    ) -> Result<CreatedAccount, ApplyError> {
        // Validate the runtime before deriving the address so every caller (pool
        // admission and block inclusion) rejects the same set of malformed
        // runtimes at the shared choke point, matching the reference contract's
        // CREATE2 deploy (EIP-170 size, EIP-3541 leading-byte).
        Self::validate_create_runtime(&entry.code)?;
        let address = Self::compute_address(entry.user_salt, &entry.code, &entry.initial_actors)?;
        // Block re-initialization of an account that already holds EIP-8130 state.
        // `local_sequence` doubles as the created/imported flag; `local_epoch`
        // covers an account whose sequence was reset to 0 by `IncrementLocalEpoch`;
        // and `multichain_sequence` guards an account that established state via a
        // global (chain_id 0) config change without ever being created/imported.
        // Defer to the shared [`AccountState::is_initialized`] predicate so this
        // guard can't drift from it. This must be explicit now that
        // `authorize_actor` is an upsert and no longer reverts on a duplicate
        // initial actor (mirrors `createAccount`'s guard).
        let mut state = storage.get_account_state(address)?;
        if state.is_initialized() {
            return Err(ApplyError::AlreadyInitialized { account: address });
        }

    /// Computes the counterfactual CREATE2 address for a created account. Mirrors
    /// `computeAddress`.
    pub fn compute_address(
        user_salt: B256,
        code: &[u8],
        initial_actors: &[InitialActor],
    ) -> Result<Address, ApplyError> {
        let effective_salt = Self::effective_salt(user_salt, initial_actors);
        let code_hash = keccak256(Self::build_deployment_code(code)?);
        let mut buf = Vec::with_capacity(1 + 20 + 32 + 32);
        buf.push(0xff);
        buf.extend_from_slice(Eip8130Contracts::ACCOUNT_CONFIG.as_slice());
        buf.extend_from_slice(effective_salt.as_slice());
        buf.extend_from_slice(code_hash.as_slice());
        Ok(Address::from_word(keccak256(buf)))
    }

    /// The CREATE2 salt: `keccak256(user_salt || actors_commitment)`. Mirrors
    /// `_computeEffectiveSalt`.
    fn effective_salt(user_salt: B256, initial_actors: &[InitialActor]) -> B256 {
        // Exactly 64 bytes: `user_salt` (32) || `actors_commitment` hash (32).
        let mut packed = Vec::with_capacity(64);
        packed.extend_from_slice(user_salt.as_slice());
        packed.extend_from_slice(Self::actors_commitment(initial_actors).as_slice());
        keccak256(packed)
    }

    #[test]
    fn create_then_config_change_authorizes_against_freshly_created_account() {
        // A Create followed by a ConfigChange in the same transaction: the config
        // change must authorize against the *post-create* actor set (the initial
        // actor is installed as an unrestricted owner), proving authorize-and-apply
        // interleaves the two against an evolving state rather than reading a
        // pre-transaction snapshot where the account does not yet exist.
        let k = key(0xc5);
        let signer_addr = addr(&k);
        let actor_id_val = B256::from_slice(&{
            let mut id = [0u8; 32];
            id[12..].copy_from_slice(signer_addr.as_slice());
            id
        });
        let initial_actors = vec![InitialActor::owner(actor_id_val, K1)];
        // Non-empty code: codeless creates are rejected by the structural
        // validator before this path, and `apply_create` now enforces the same
        // `EmptyBytecode` invariant.
        let create = CreateEntry {
            user_salt: B256::ZERO,
            code: Bytes::from_static(&[0x60, 0x00]),
            initial_actors: initial_actors.clone(),
        };
        let derived = AccountChangeApplier::compute_address(
            create.user_salt,
            create.code.as_ref(),
            &initial_actors,
        )
        .expect("address derivation");

        // Config change signed by the initial actor, bound to the derived account
        // at the multichain channel's first sequence.
        let cc = signed_change(derived, K1, &k, AccountChangeChannel::Multichain, 0, vec![]);
        let tx = TxEip8130 {
            chain_id: LOCAL,
            sender: Some(derived),
            nonce_key: U256::ZERO,
            nonce_sequence: 0,
            valid_after: 0,
            valid_before: 0,
            max_priority_fee_per_gas: 1_000_000_000,
            max_fee_per_gas: 5_000_000_000,
            gas_limit: 250_000,
            account_changes: vec![AccountChange::Create(create), AccountChange::ConfigChange(cc)],
            calls: vec![],
            metadata: Bytes::new(),
            payer: None,
        };
        let hash = tx.sender_signature_hash();
        let signed = Eip8130Signed::new(tx, auth_blob(K1, &sig(&k, hash)), Bytes::new());

        with_storage(|acc| {
            let out = TransactionAuthorizer::authorize_and_apply(&signed, acc, LOCAL, NOW)
                .expect("create + config change must authorize against post-create state");
            assert_eq!(out.actors.sender.account, derived);
            assert_eq!(out.config_changes.len(), 1, "config change applied after create");
            assert!(out.applied.created.is_some(), "create entry applied");
            // `apply_create` sets `local_sequence = 1` as its created/imported
            // flag; the single multichain config change then advances the
            // multichain channel to 1 — hence `(multichain, local) == (1, 1)`.
            assert_eq!(acc.get_change_sequences(derived).unwrap(), (1, 1));
        });
