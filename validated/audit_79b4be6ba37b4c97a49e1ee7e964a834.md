### Title
Permanent freezing of maker's collateral when the source-chain refund recipient is blacklisted by the token contract - (File: contracts/EscrowSrc.sol)

### Summary
`EscrowSrc.cancel()` and `EscrowSrc.publicCancel()` both refund the maker's locked collateral by hardcoding the recipient to `immutables.maker.get()`, with no mechanism to redirect the transfer to another address, unlike the `withdraw` path which explicitly provides `withdrawTo` for this exact purpose.

### Finding Description
`EscrowSrc` implements two withdrawal-style exit paths for the maker's locked source tokens: withdrawal (secret-gated, benefiting the taker) and cancellation (time-gated, benefiting the maker). For the withdrawal path, the protocol explicitly anticipated recipient-related transfer issues and added `withdrawTo(bytes32 secret, address target, Immutables calldata immutables)` so the taker can redirect ERC20 proceeds to any address they control. [1](#0-0) 

No equivalent exists for the cancellation path. `cancel()` and `publicCancel()` both call the internal `_cancel` helper, which unconditionally performs `safeTransfer` of `immutables.amount` to `immutables.maker.get()`: [2](#0-1) 

If the maker's address is blacklisted by the source-chain ERC20 (e.g. a USDC-style token with a compliance blacklist), `IERC20.safeTransfer` reverts every time it targets that address. Because `_cancel` performs the transfer directly to the hardcoded maker address with no alternate recipient parameter, every call to `cancel()` (by the taker) and `publicCancel()` (by any access-token holder) will revert for as long as the maker remains blacklisted. The only other codepath able to move the balance out of the clone is `rescueFunds`, which is restricted to the taker (`onlyCaller(immutables.taker.get())`) and only available after `RESCUE_DELAY`: [3](#0-2) 

Since taker/resolver-privileged recovery is explicitly out of scope for this analysis, from the perspective of the unprivileged maker there is no way to ever retrieve the collateral once refund becomes required and the maker's address is blacklisted — the funds are stuck in the `EscrowSrc` clone's balance permanently.

### Impact Explanation
This is a direct structural analog to the original report's `repay()` freezing issue: a "predetermined recipient" transfer with no redirect option, in a flow that returns principal collateral to its rightful owner. If the maker becomes blacklisted before cancellation, their entire locked collateral (`immutables.amount`) is permanently unrecoverable through the intended, unprivileged flow, matching the "permanent freezing of funds" / "smart contract unable to operate because required token balances can be broken by an unprivileged actor (the blacklisting entity)" categories in the bounty scope.

### Likelihood Explanation
Low-to-moderate: it requires the maker's own address to be independently blacklisted by the specific ERC20 token used as collateral (as in the original Sherlock report, this is a known but infrequent real-world event for regulated stablecoins like USDC/USDT). It requires no malicious action by any protocol participant — only an external compliance/blacklist event on the token contract — consistent with the "unprivileged actor" trigger model.

### Recommendation
Mirror the `withdraw`/`withdrawTo` pattern for the cancellation path: add a `cancelTo(address target, Immutables calldata immutables)` variant (callable only by the maker, or by the taker on the maker's authorized instruction) that allows the collateral to be redirected to an address of the maker's choosing, analogous to:
```solidity
function cancelTo(address target, Immutables calldata immutables)
    external
    onlyValidImmutables(immutables.hash())
    onlyAfter(immutables.timelocks.get(TimelocksLib.Stage.SrcCancellation))
{
    IERC20(immutables.token.get()).safeTransfer(target, immutables.amount);
    _ethTransfer(msg.sender, immutables.safetyDeposit);
    emit EscrowCancelled();
}
```
with appropriate authorization (e.g., only maker-signed or maker-invoked) to prevent misdirection by unrelated callers.

### Proof of Concept
1. Alice (maker) signs an order; `EscrowSrc` clone is deployed and funded with her `MAKING_AMOUNT` of a blacklist-capable token (e.g., USDC-like mock) via `postInteraction`.
2. Before the swap completes, the token issuer blacklists Alice's address (external event, no attacker action needed).
3. The withdrawal window elapses without secret reveal (or resolver never withdraws); `SrcCancellation` timelock is reached.
4. Taker (or any access-token holder) calls `cancel()`/`publicCancel()`; `_cancel` attempts `IERC20(token).safeTransfer(alice, immutables.amount)`, which reverts due to the blacklist.
5. Every subsequent call to `cancel()`/`publicCancel()` reverts identically; `withdraw()` is no longer callable since the withdrawal timelocks have passed. Alice's collateral is now permanently trapped in the `EscrowSrc` clone (only reachable by the taker after `RESCUE_DELAY` via the privileged `rescueFunds`, out of scope for the unprivileged actor model).
