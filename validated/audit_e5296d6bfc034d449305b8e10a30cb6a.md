### Title
`claimInstantWithdrawRequest` never clears `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, so a re-request in the same epoch re-registers already-paid basis and corrupts default recovery — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a clearing path that deletes the record but leaves a state flag set, so the next lifecycle reuses stale state. In `IdleCreditVault`, `claimInstantWithdrawRequest` burns the receipt and zeroes the aggregate `instantWithdrawsRequests[_user]` but never touches the per-epoch ledgers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. A user who requests, claims, and re-requests an instant withdrawal inside the same epoch leaves the already-paid basis permanently counted in that epoch's claim bucket. If the epoch later defaults and is finalized, the inflated `instantWithdrawClaimsByEpoch[epochNumber]` is added to `defaultPendingClaimBasis()`, diluting `defaultRecoveryPrice` for every claimant, and the victim's own defaulted claim burns/claims the stale amount again.

### Finding Description
`requestInstantWithdraw` records receipts in three places: the aggregate `instantWithdrawsRequests[_user]`, the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch total `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

`claimInstantWithdrawRequest` only burns the aggregate amount and sets `instantWithdrawsRequests[_user] = 0`; the two per-epoch mappings are never decremented [2](#0-1) . The only place `instantWithdrawsRequestsByEpoch` is cleared is the default-claim path `_claimDefaultedInstantWithdrawRequest`, which subtracts the stale (inflated) value from `instantWithdrawsRequests`, `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch` [3](#0-2) .

At finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, so the ghost basis enters `totalBasis` and lowers `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` for all defaulted claimants and active LPs [4](#0-3) [5](#0-4) .

Attack sequence (running epoch with instant withdraws enabled):
1. Epoch N running. Attacker calls `requestInstantWithdraw(X)`. `instantWithdrawsRequestsByEpoch[A][N] = X`, `instantWithdrawClaimsByEpoch[N] = X`.
2. Funds are collected (`collectInstantWithdrawFunds`) and attacker calls `claimInstantWithdrawRequest`. Paid X, aggregate zeroed — but `instantWithdrawsRequestsByEpoch[A][N]` stays `X` and `instantWithdrawClaimsByEpoch[N]` stays `X`.
3. Still epoch N: attacker calls `requestInstantWithdraw(Y)` again. Now `instantWithdrawsRequestsByEpoch[A][N] = X + Y`, `instantWithdrawClaimsByEpoch[N] = X + Y`, while only Y is unfunded.
4. Borrower repayment fails; `_handleBorrowerDefault` runs and `finalizeDefaultRecovery` executes while `pendingInstantWithdraws != 0` (Y unfunded). The basis includes ghost X, so `defaultRecoveryPrice` is understated — every other pending receipt and active LP is over-haircut.
5. When the attacker claims, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = X + Y` and calls `_burn(_user, X + Y)`, but the attacker only holds a Y receipt — the claim reverts, permanently freezing the attacker's own receipt (or, if the attacker first requests a large enough Y to cover the burn, they withdraw `X + Y` of recovery they were only owed `Y` on).

This mirrors the OtterSec bug exactly: a clearing path deletes one state record (`instantWithdrawsRequests[_user]` / `loans[nft][id]`) while leaving the companion state (`instantWithdrawsRequestsByEpoch` / `loanDeployed[nft][id]`) stale, corrupting the next lifecycle.

### Impact Explanation
Direct theft and permanent freezing: the ghost basis is counted in `defaultPendingClaimBasis`, so the finalized `defaultRecoveryPrice` is strictly lower than the true ratio — an insolvency-adjacent haircut transfer where all defaulted-epoch claimants and active LPs lose recovery value proportional to `X / totalBasis`. If the attacker keeps their real receipt ≥ the inflated basis, they extract the already-paid X a second time from `defaultRecoveryReserve`; otherwise their own claim reverts permanently since there is no other path that clears `instantWithdrawsRequestsByEpoch`.

### Likelihood Explanation
Requires (a) instant withdraws enabled via `setInstantWithdrawParams`, (b) request → funded claim → second request within the same epoch (instant claims are serviced inside the request epoch, per the epoch-2 claims in `testProcessWithdrawalClaimsInstantEpoch`), and (c) a default on that same epoch's `stopEpoch` with unfunded instant remainder. No privileged-role misbehavior is needed: the attacker only uses public request/claim flows; the default trigger is the honest borrower failing to repay, which is an anticipated protocol event.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers for the epoch(s) being paid, mirroring `_claimDefaultedInstantWithdrawRequest`:

```solidity
uint256 currentEpoch = epochNumber; // or the stored request epoch
instantWithdrawsRequestsByEpoch[_user][currentEpoch] = 0; // or -= amount
instantWithdrawClaimsByEpoch[currentEpoch] -= amount;
instantWithdrawsRequests[_user] = 0;
```

If receipts can span multiple epochs, iterate the request epochs or store per-epoch claimability so `instantWithdrawClaimsByEpoch` always equals the sum of outstanding per-epoch receipts.

### Proof of Concept
Foundry fork PoC outline (against `IdleCreditVault.t.sol` harness):

```solidity
// epoch N running, instant withdraws enabled
vm.prank(attacker); cdoEpoch.requestInstantWithdraw(X);            // byEpoch[A][N] = X
// manager/CDO funds instant claims, then:
vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest();       // paid X; byEpoch NOT cleared
vm.prank(attacker); cdoEpoch.requestInstantWithdraw(Y);           // byEpoch[A][N] = X+Y, claimsByEpoch[N] = X+Y
// borrower underfunds stop -> default; leave Y unfunded so pendingInstantWithdraws != 0
_stopEpochDefaulted();
vm.prank(manager); cdoEpoch.finalizeDefault(recovered, manager);
// assert: strategy.instantWithdrawClaimsByEpoch(N) > pendingInstantWithdraws basis
// assert: defaultRecoveryPrice < honest price (ghost X diluted)
vm.prank(attacker); vm.expectRevert(); cdoEpoch.claimInstantWithdrawRequest(); // burn(X+Y) > receipt Y
```

Uncertainty: I was unable to fully confirm within the iteration budget whether the CDO permits a second `requestInstantWithdraw` while `instantWithdrawsRequests[_user] == 0` but a per-epoch entry already exists in the same epoch (no explicit guard was found in `requestInstantWithdraw`), and whether instant claims always settle in the request epoch under the configured `instantWithdrawDelay`. If a guard exists elsewhere blocking same-epoch re-request, the same stale-state exposure still applies across the default boundary via `instantWithdrawClaimsByEpoch` never being decremented on ordinary claims.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
