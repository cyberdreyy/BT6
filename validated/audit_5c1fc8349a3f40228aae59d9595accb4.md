### Title
Signer weight double-counted across the accept and reject tallies lets a stale rejection overturn an already-signed block - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_rejection` computes `total_reject_weight` purely from the `block_rejection_signer_addrs` table and independently marks a block `GloballyRejected` once that tally crosses the blocking-minority threshold. Nothing in this path (or in `add_block_rejection_signer_addr`) removes a signer's prior entry from the `block_signatures` table, and the codebase explicitly documents that a signature is treated as a permanent "bearer instrument" that a later rejection from the same signer does not revoke. The same signer's weight can therefore be counted simultaneously toward the acceptance side (via their stored signature) and the rejection side (via their later rejection), the mirror image of the `NativeVault` bug where a transferred balance is counted on both the sender and recipient side of an accounting equation.

### Finding Description
Two independent tallies are supposed to be mutually exclusive views of the same signer set weight:

- Acceptance weight is derived from rows in `block_signatures`, added via `add_block_signature`, which explicitly deletes any prior rejection row for that signer when a signature arrives: [1](#0-0) 
- Rejection weight is derived from rows in `block_rejection_signer_addrs`, added via `add_block_rejection_signer_addr` and tallied in `store_and_process_block_rejection`, which recomputes `total_reject_weight` from `get_block_rejection_signer_addrs` alone: [2](#0-1) 

The reject→accept direction is guarded (a signature clears a prior rejection), but there is no symmetric guard clearing a prior signature when a rejection later arrives from the same signer. The design docs confirm this is intentional and not merely an oversight: a signature, once observed, keeps counting toward the 70% threshold even after a "global" rejection, because "a rejection is a revocable opinion, while a signature is a bearer instrument that can still be aggregated toward the 70% threshold": [3](#0-2) 

This means a signer that first signs (Accept) and later sends a Reject for the same block has its weight retained in the acceptance tally (their `block_signatures` row is never removed by a rejection) while also being freshly added to the rejection tally. The signer's weight is thus counted on both sides of the equality that `BlockState` transition logic assumes is mutually exclusive.

Crucially, the `BlockState` transition rules allow a block that is already `LocallyAccepted` (i.e., already reached the 70% local signing threshold and been broadcast toward the node) to still be moved to `GloballyRejected`, because `check_state` only forbids that transition once the block is already `GloballyAccepted`: [4](#0-3)  and `has_reached_consensus` — the guard that `store_and_process_block_rejection` checks before even bothering to tally — only short-circuits for the two *global* terminal states, not `LocallyAccepted`: [5](#0-4) 

So in the window between a signer locally accepting a block (having reached 70% signature weight) and the node actually processing it into `GloballyAccepted`, rejection messages — including one from a signer who already contributed to the accept side — keep being tallied and can still push the block state to `GloballyRejected` via `mark_globally_rejected`: [6](#0-5) 

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality the protocol depends on: the sum of the accept tally and the reject tally is no longer bounded by `total_weight`, because a single signer's weight can be double-counted. In the vulnerable window (after 70% signature weight is reached locally but before global acceptance is confirmed by the node), this double counting makes it easier for a rejecting minority to cross the 30% blocking threshold and drive the local `BlockState` to `GloballyRejected` for a block that, from the node's perspective, may still become canonical/`GloballyAccepted`. That is a High-severity liveness/consistency wedge: a signer's local state machine can reach a terminal "rejected" verdict inconsistent with the actual outcome, and `store_and_process_block_rejection`'s reorg-related side effects (marking the miner invalid on `ReorgNotAllowed` rejections) can then fire based on this inflated tally.

### Likelihood Explanation
The trigger requires only a single signer to submit an Accept and later a Reject for the same block signature hash — no majority collusion is needed, and both messages are individually valid signer-authenticated messages that pass `is_valid_signer` checks in `handle_block_signature`/`handle_block_rejection`. The race window (between reaching local accept threshold and the node's `NewBlock` event marking global acceptance) is a normal part of block finalization, making this reachable under ordinary asynchronous network conditions plus one signer sending a contradictory follow-up message.

### Recommendation
When tallying rejection weight in `store_and_process_block_rejection`, exclude (or subtract) the weight of any signer address that already has a recorded row in `block_signatures` for the same block, mirroring the existing reject→accept guard in `add_block_signature`. Alternatively, treat `LocallyAccepted` (once the local 70% threshold has actually been reached) as consensus-reached for the purposes of `has_reached_consensus`, so that no further rejection processing can transition the block to `GloballyRejected` after this signer has already committed a signature.

### Proof of Concept
1. Signer set of weight 100; threshold 70.
2. Signer A (weight 40) and others sign Accept, reaching total signature weight 70 → block moves to `LocallyAccepted` via `mark_locally_accepted` and is broadcast toward the node (`stacks-signer/src/v0/signer.rs` BCAST path, see docs/signer-flows.md:363-372).
3. Before the node's `NewBlock` event confirms global acceptance, Signer A (already counted for 40 weight in `block_signatures`) also sends a Reject for the same `signer_signature_hash`.
4. `handle_block_rejection` → `store_and_process_block_rejection` inserts A's rejection into `block_rejection_signer_addrs` (`stacks-signer/src/v0/signer.rs:2278-2288`), and computes `total_reject_weight` including A's full weight, without removing A's earlier signature row.
5. With a few more genuinely rejecting signers reaching the remaining ~30-40 weight needed, `total_reject_weight.saturating_add(min_weight) > total_weight` becomes true even though A's weight is simultaneously still backing the 70% acceptance that already happened, and `mark_globally_rejected` fires (`stacks-signer/src/v0/signer.rs:2335-2341`), which `check_state` permits from `LocallyAccepted` (`stacks-signer/src/signerdb.rs:319-328`). [7](#0-6)

    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
