### Title
Front-runnable, permissionless `init_global_fee_state` allows attacker to seize the global `FeeState` singleton (`global_fee_admin`/`global_fee_wallet`) — (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
`init_global_fee_state` is a "runs once per program" instruction that creates the single, global `FeeState` PDA (seeded only by `FEE_STATE_SEED`, no admin-derived seed) and sets `global_fee_admin`/`global_fee_wallet` to arbitrary values taken directly from instruction arguments, with no access-control check on who may call it. This is the same root cause the external report flags for the EasyTrack implementation contract: a privileged, singleton state object that anyone can initialize, letting whoever calls it first seize the global admin role, with no safeguard against front-running the legitimate deployer's initialization transaction.

### Finding Description
`InitFeeState` only requires a fee-paying `Signer`, and the `fee_state` account uses Anchor's `init` constraint keyed solely on `FEE_STATE_SEED` — there is no constraint requiring the payer/admin to be an expected key: [1](#0-0) [2](#0-1) 

`admin_key` and `fee_wallet` are taken verbatim from caller-supplied instruction arguments and written into the account with no validation that the caller is the intended deployer: [3](#0-2) 

This is exactly the class of bug in the report: a globally-shared, privileged state object left without protection against being initialized by an unintended party, and (per the report's own recommended fix) vulnerable to "front-running the initialize should the deployment script deploy and execute in separate transactions." Because the `FeeState` PDA is derived purely from a static seed (`FEE_STATE_SEED`) and the program ID, its address is fully predictable before deployment; an attacker who observes the program's initial deployment/initialization transactions in the mempool (or a validator leader) can submit their own `init_global_fee_state` call first, since the `init` Anchor constraint only requires the account not already exist — it does not care who created it.

Once seized, the attacker-controlled `global_fee_admin` becomes the sole authority (via `has_one = global_fee_admin`) over all subsequent mutations of the `FeeState` account, including:
- `edit_fee_state` — can rewrite `global_fee_admin`, `global_fee_wallet`, and every protocol-wide fee parameter at will: [4](#0-3) 
- `config_group_fee` — toggle whether program fees are charged on any group: [5](#0-4) 
- `panic_unpause` — control over protocol pause/unpause state gated by `global_fee_admin`: [6](#0-5) 

Because these downstream instructions all check `has_one = global_fee_admin @ MarginfiError::Unauthorized` against the attacker-set value, the legitimate protocol team has no on-chain path to reclaim control once the PDA is initialized with the wrong admin — the account can never be re-initialized (Anchor `init` fails once it exists), and only the current `global_fee_admin` can call `edit_fee_state` to change it back.

### Impact Explanation
The most direct and severe consequence is `global_fee_wallet` redirection: `init_global_fee_state` lets the caller set `fee_wallet` to any address, and every subsequent protocol-fee-generating instruction across the entire marginfi program forwards fees to whatever `global_fee_wallet` is cached from this account (via `fee_state_cache` propagated into every `MarginfiGroup`, seen in `initialize_group`: [7](#0-6) ). An attacker who wins the initialization race permanently diverts protocol-wide fee revenue to their own wallet and gains a persistent, unrecoverable-on-chain administrative foothold (pause/unpause control, ability to rewrite all fee parameters). This is a durable, protocol-wide financial redirection with no legitimate recovery path short of redeploying the program under a new program ID.

### Likelihood Explanation
Exploitation requires only submitting a single permissionless transaction before the legitimate deployment script's `init_global_fee_state` call lands — the PDA address is deterministic and publicly derivable ahead of time from `FEE_STATE_SEED` and the known program ID. On Solana, deploy scripts commonly separate "deploy program" and "run initialization instructions" into distinct transactions/steps (as this codebase's own test fixtures do — see the two-step flow in `test-utils/src/marginfi_group.rs` initializing fee state and group in separate/racing transactions: [8](#0-7) ), which is precisely the "deploy and execute in separate transactions" scenario the original report calls out as exploitable by front-running. This makes the race practically feasible for any attacker monitoring new/upgraded program deployments.

### Recommendation
- Bind `init_global_fee_state` to a hardcoded, build-time-known authority (e.g., the program's upgrade authority or a compile-time constant pubkey) enforced via an `Accounts` constraint, rather than trusting caller-supplied `admin_key`.
- Where possible, perform the `FeeState` initialization atomically within the same transaction as program deployment/upgrade, eliminating the window for front-running.
- Add an explicit constraint requiring `ctx.accounts.payer.key() == expected_deployer` (or equivalent multisig/governance-controlled key) before allowing the one-time `init` to proceed.

### Proof of Concept
1. Before/during marginfi program deployment, derive the deterministic PDA: `Pubkey::find_program_address(&[FEE_STATE_SEED.as_bytes()], &marginfi::ID)` (publicly computable by anyone once the program ID is known, e.g., from the deploy transaction or on-chain program account).
2. Attacker constructs and submits an `init_global_fee_state` instruction (`InitFeeState` accounts: `payer` = attacker, `fee_state` = the derived PDA, `system_program`) with `admin_key = attacker_pubkey`, `fee_wallet = attacker_pubkey`, before the legitimate deploy script's own `init_global_fee_state` transaction lands, as shown in [1](#0-0) .
3. Anchor's `init` constraint succeeds because the PDA does not yet exist; the legitimate team's later attempt to call `init_global_fee_state` for the same PDA now fails (`init` requires the account not exist).
4. From this point, `fee_state.global_fee_admin == attacker`, `fee_state.global_fee_wallet == attacker`; all protocol fees route to the attacker's wallet, and only the attacker can call `edit_fee_state`, `config_group_fee`, or `panic_unpause`/`panic_pause` against this `FeeState`, as enforced by `has_one = global_fee_admin` in [4](#0-3)  and [5](#0-4) .
