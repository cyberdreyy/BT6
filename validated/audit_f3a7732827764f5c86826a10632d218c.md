### Title
Unprivileged user can permanently brick `stopEpoch` by leaving an open APR0 withdraw request — any later non-zero APR makes `prepareStopEpochWithApr0` always revert, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` contains a hard `revert NotAllowed()` that is enforced on every `stopEpoch` call whenever a global APR0 principal bucket is non-zero and `unscaledApr != 0`. An unprivileged, KYC-passed lender can open an APR0 withdraw request while APR is 0; once the (honest) manager later sets a non-zero APR — a routine operation — every subsequent `stopEpoch` reverts. Because the only code paths that clear `apr0TotalPrincipal` are the reverting function itself and the default-claim path (which requires an already-advanced/finalized epoch), the revert is unrecoverable: the epoch can never close again. This mirrors the TensorFlow bug class: a crafted input drives a mandatory pass into a `CHECK`-failure abort, converting a reachable revert into a system-wide halt — here, permanent freezing of all user funds.

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `unscaledApr == 0`, a user request is routed to `_requestWithdrawApr0`, which adds the amount to the global `apr0TotalPrincipal` bucket. At epoch close, `IdleCDOEpochVariant.stopEpoch` calls `prepareStopEpochWithApr0`, which executes:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
``` [1](#0-0) 

Key facts making the deadlock unrecoverable:

1. `apr0TotalPrincipal` is only zeroed at the end of `prepareStopEpochWithApr0` (line 540) — the same function that reverts — or decremented per-user in `_clearWithdrawClaimForEpoch` during **default** claims.
2. `_clearWithdrawClaimForEpoch`/`_settleApr0` are reached via `claimWithdrawRequest` → `_claimFundedWithdrawRequest`, which reverts while `epochNumber <= lastWithdrawRequest[_user]` — i.e., the user cannot clear their own request until `stopEpoch` succeeds. `stopEpoch` can never succeed → circular dependency → permanent freeze.
3. `requestWithdraw` contains no revert preventing new requests in this state, so the attacker can also re-open an APR0 request any time APR returns to 0, re-arming the trap indefinitely.
4. Even emergency/default handling does not rescue it cleanly: `_handleBorrowerDefault` → `finalizeDefaultRecovery` still depends on epoch state advanced via `stopEpoch`, and forced default is a drastic, loss-inducing action rather than a fix.

The existing test `testApr0InvariantRevertsIfAprChangesAfterApr0Request` confirms the revert exists by design (`contracts/../test/foundry/IdleCreditVault.t.sol:3306-3338`) but treats it as an invariant enforcement, missing that the attacker is the one who creates the APR0 request while the manager's routine APR change is the trigger — turning a defensive `CHECK` into a remotely-armed kill switch.

### Impact Explanation
Permanent freezing of all user funds. While `stopEpoch` reverts, `epochNumber` never advances, so:

- No pending withdraw receipt (`withdrawsRequests`, `instantWithdrawsRequests`, APR0 buckets) can ever be claimed — `_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest[_user]`.
- No new epoch can start; queued deposits/withdrawals in `IdleCDOEpochQueue` are frozen since `processWithdrawRequests`/`processWithdrawalClaims` depend on epoch progression.
- All underlying remains locked with the borrower or in the vault with no redemption path, short of a contract upgrade or a forced borrower default (itself loss-inducing).

Quantified: 100% of vault TVL is frozen indefinitely (permanent freezing, worst accepted impact class).

### Likelihood Explanation
- Attacker cost is trivial: a single `requestWithdraw` while APR is 0. The attacker can use dust amounts and multiple wallets.
- The trigger condition — manager later setting a non-zero APR — is a routine, honest operation (APRs are re-priced between epochs by design). The attacker does not need to influence it, only to keep an open APR0 request while APR is 0 and wait.
- No guard prevents this: `requestWithdraw` doesn't block APR0 requests near epoch end, `setAprs` doesn't check `apr0TotalPrincipal`, and no "clear and retry" escape exists for the manager.
- The only mitigation is operational (manager must never raise APR while an APR0 request is open, forever) — an invariant the contracts fail to enforce on the privileged side while leaving the attacker side free.

### Recommendation
Make the APR0 lifecycle invariant enforceable rather than fatal:

- In `setAprs` (or wherever `unscaledApr` is changed), revert if `apr0TotalPrincipal != 0`, so the invariant is checked on the privileged side where it can be avoided, instead of inside the mandatory `stopEpoch` path where it is fatal.
- Alternatively/additionally, allow an APR0 request to be cancelled or force-settled: e.g., in `prepareStopEpochWithApr0`, when `unscaledApr != 0`, migrate the open APR0 bucket into a normal withdraw receipt (settle at principal, no interest) instead of reverting — converting the `CHECK`-failure into defined behavior.
- Add a revert in `requestWithdraw`/`_requestWithdrawApr0` when `unscaledApr == 0` but a pending non-zero-APR transition is scheduled, if such a mechanism exists.

### Proof of Concept
Foundry fork PoC (mirroring the existing test setup in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testApr0RequestPermanentlyBricksStopEpoch() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // APR 0

    // attacker (KYC'd lender) deposits and requests withdraw while APR == 0
    address attacker = makeAddr('attacker');
    uint256 dust = 1e6;
    _depositWithUser(attacker, dust, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(attacker), address(AAtranche));
    // apr0TotalPrincipal > 0, attacker never claims (and cannot, epochNumber won't advance)

    // honest manager later raises APR for the new epoch — routine operation
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(1e18, 1e18);

    // every subsequent stopEpoch reverts in prepareStopEpochWithApr0 — forever
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 expectedInterest = cdoEpoch.expectedEpochInterest();
    deal(defaultUnderlying, borrower, expectedInterest);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // no recovery: attacker cannot claim (epochNumber stuck), manager cannot clear
    // apr0TotalPrincipal, epoch cannot close → all TVL permanently frozen
    vm.prank(attacker);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
}
```

Note: I verified the revert site, the circular claim dependency, and the absence of a cancel path in the indexed code; I did not fully trace `IdleCDOEpochVariant.stopEpoch`'s call ordering or `_requestWithdrawApr0`'s exact bookkeeping, so the PoC's concrete helper names may need minor adjustment to match the repo's test harness.
