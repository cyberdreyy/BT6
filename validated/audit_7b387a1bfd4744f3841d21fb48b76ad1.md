### Title
External Initiator credentials can trigger runs on arbitrary jobs via `POST /v2/jobs/:ID/runs` because `isUser` gate does not distinguish EI from User sessions - (File: `core/web/pipeline_runs_controller.go`, `core/web/auth/auth.go`)

### Summary
`AuthenticateExternalInitiator` sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}` in addition to `SessionExternalInitiatorKey`, so `auth.GetAuthenticatedUser(c)` returns `ok=true` for both real users and EI-authenticated requests. `PipelineRunsController.Create` uses exactly that `ok` value as its "only users are allowed... EIs not allowed" gate, so the gate is a no-op and any valid EI credential can trigger `RunJobV2` on any numeric job ID, with no check that the target job is the one bound to that EI.

### Finding Description
The route is registered as: [1](#0-0) 

`Authenticate()` tries methods in order and stops at the first non-`ErrorAuthFailed` result: [2](#0-1) 

When an EI's `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers validate, `AuthenticateExternalInitiator` sets **both** the EI key and a fabricated `User` object with `UserRoleRun` into the session context: [3](#0-2) 

`RequiresRunRole` then passes because the fabricated user has `UserRoleRun`: [4](#0-3) 

Inside `Create`, the code comment claims EIs are excluded from the int32 path, but the check only asks whether *any* `SessionUserKey` object exists, which is now always true for a successfully authenticated EI too: [5](#0-4) 

Because `job.Webhook` type has been removed (per the comment/`job.ErrJobTypeRemoved` at line 105 of the same file), the code path that historically bound an EI's identity (`Name`/`URL`) to a specific webhook job's UUID no longer exists anywhere in this handler. There is no lookup of `auth.GetAuthenticatedExternalInitiator(c)` and no comparison against the target job's initiator spec before calling `prc.App.RunJobV2(ctx, jobID, nil)`. As a result, any EI credential that successfully authenticates can invoke `RunJobV2` against *any* job ID on the node, not just a job bound to that EI.

### Impact Explanation
This is an authorization bypass allowing an unprivileged, restricted-scope external-initiator credential holder to trigger execution ("unauthorized job run") of arbitrary jobs on the node — jobs the EI was never bound to. Depending on job type this can cause unwanted on-chain transactions, resource exhaustion, or triggering of jobs that move funds or perform privileged pipeline tasks, matching the bounty's "unauthorized job run" impact class.

### Likelihood Explanation
Preconditions: attacker only needs a valid but restricted External Initiator credential pair (a "Run"-scoped credential explicitly listed as an in-scope unprivileged attacker in this audit). No admin/edit privileges, no forged/stolen tokens for other users, and no header-confusion trick with `AuthenticateByToken` are required — the bug is triggered directly and deterministically by `AuthenticateExternalInitiator` itself. This is fully reproducible with any valid EI key/secret pair against any numeric job ID.

### Recommendation
In `PipelineRunsController.Create`, distinguish EI-derived pseudo-users from real users, e.g. by checking `auth.GetAuthenticatedExternalInitiator(c)` explicitly and rejecting EI-authenticated requests (as the comment intends), or by not overloading `SessionUserKey` in `AuthenticateExternalInitiator` for identity purposes. If EI-triggered runs are still meant to be supported for specific jobs, reintroduce a binding check comparing the authenticated EI's identity to the target job's associated initiator before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
1. Create a job with a numeric ID owned by no external initiator (e.g., a keeper/OCR job).
2. Create an unrelated External Initiator record (`Name`, `URL`, valid access key/secret).
3. Send `POST /v2/jobs/:ID/runs` with only the EI's `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers (no session cookie, no `X-API-KEY`).
4. Assert the request succeeds (HTTP 200, `pipelineRun` resource returned) rather than being rejected — proving that a Run-role EI credential can invoke `RunJobV2` on a job it has no binding to.
5. Add a companion assertion verifying `auth.GetAuthenticatedExternalInitiator(c)` is non-nil while `Create` still treated `isUser` as true, demonstrating the root cause in `auth.go`/`pipeline_runs_controller.go`.

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
