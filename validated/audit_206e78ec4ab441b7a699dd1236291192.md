### Title
Loss-adjusted withdraw receipts bypass their haircut when the user places a later request in a subsequent epoch — underfunded claims paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the flash-loan/order-ID mismatch in the external report, `IdleCreditVault._claimLossAdjustedWithdrawRequest` binds a claim's loss price to `lastWithdrawRequest[_user]` — a single slot storing only the **latest** request epoch — instead of looking up each per-epoch receipt in `withdrawsRequestsByEpoch`. A user who holds a receipt from a loss epoch can overwrite that marker by making a new withdraw request in a later epoch, causing the loss-adjusted claim path to be skipped entirely so the haircut receipt is paid out at par by `_claimFundedWithdrawRequest`.

### Finding Description
`requestWithdraw` records each request per-epoch via `withdrawsRequestsByEpoch[_user][currentEpoch]` but stores only the newest epoch in `lastWithdrawRequest[_user]` [1](#0-0) .

When a `stopEpochWithDuration` loss is realized, `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber] < RECOVERY_FULL`; the borrower only funds the haircut amount [2](#0-1) .

On claim, `_claimLossAdjustedWithdrawRequest` derives the loss epoch solely from `lastWithdrawRequest[_user]` [3](#0-2) . If the user's latest request is in a later epoch E2, `lossRecoveryPriceByEpoch[E2] == 0` and the function returns 0 — the epoch-E1 receipt is never cleared via `_clearWithdrawClaimForEpoch`, never burned at its haircut basis, and remains inside the aggregate `withdrawsRequests[_user]`. `_claimFundedWithdrawRequest` then pays `normalAmount` (which still includes the E1 receipt) at full par and burns the full receipt amount [4](#0-3) .

The "receipt → epoch/price" binding (the analog of `order_id` in the receipt) is missing for any non-latest loss epoch. Multiple pending requests are explicitly allowed — the code comments note that a second request just delays the claim [5](#0-4) .

### Impact Explanation
The strategy contract only holds `receipt_amount * lossRecoveryPrice / RECOVERY_FULL` for the epoch-E1 receipt. Paying it at par transfers the haircut difference to the attacker, funded by underlyings reserved for other pending/funded receipt holders. This is direct theft / insolvency equal to `receipt * (1 - lossRecoveryPrice)` per exploited receipt, and it leaves the last legitimate claimants unable to withdraw (permanent freezing of their funds once the balance is drained below obligations). The `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, not other users' funded claims [6](#0-5) .

### Likelihood Explanation
Requires only an unprivileged KYC-passed lender/tranche holder and a `stopEpochWithDuration` loss event (honest manager/borrower sequencing — a partial borrower repayment), which is a normal supported mode. The attacker just needs two `requestWithdraw` calls in consecutive epochs; no privileged action and no reliance on defaults. The symmetric case (latest epoch has the loss, older receipt doesn't) instead over-haircuts the user, so the profitable direction is available whenever a loss epoch is followed by a normal epoch with pending receipts.

### Recommendation
Track every epoch in which a user has a pending receipt (e.g., an enumerable set or a second marker `earliestLossRequestEpoch`), or iterate `withdrawsRequestsByEpoch` for all epochs with a non-zero `lossRecoveryPriceByEpoch` during claim rather than only `lastWithdrawRequest[_user]`. Concretely, in `_claimLossAdjustedWithdrawRequest`/`claimWithdrawRequest`, clear and price each loss-epoch receipt individually (the analog of asserting `order_id == id(limit_order)`), so a later request cannot mask an earlier haircut receipt.

function testLossReceiptPaysAtParAfterLaterRequest() external {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");
    uint256 amount = 10_000 * ONE_SCALE;

    // Both deposit; both request withdraw in epoch 0
    _depositWithUser(victim, amount, true);
    _depositWithUser(attacker, amount, true);
    uint256 victimTranches = IERC20(AAtranche).balanceOf(victim);
    uint256 atkTranches = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(victim);   cdoEpoch.requestWithdraw(victimTranches, address(AAtranche));
    vm.prank(attacker); cdoEpoch.requestWithdraw(atkTranches,   address(AAtranche));

    _startEpochAndCheckPrices(0);

    // stopEpochWithDuration with a realized loss: borrower underfunds pending receipts
    // -> collectWithdrawFunds sets lossRecoveryPriceByEpoch[1] = p < RECOVERY_FULL
    // and pendingWithdraws = 0 (only p% funded).
    _stopEpochWithLoss(/* loss covering e.g. 50% of pending basis */);

    // Attacker makes a NEW request in epoch 1 buffer, overwriting
    // lastWithdrawRequest[attacker] = 2.
    _startEpochAndCheckPrices(1);
    // attacker still holds tranches? If none left, attacker deposits again and requests.
    uint256 atkTranches2 = _depositWithUser(attacker, amount, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(atkTranches2, address(AAtranche));

    // Epoch 1 ends fully funded (lossRecoveryPriceByEpoch[2] == 0).
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Claim: _claimLossAdjustedWithdrawRequest looks up epoch 2 -> price 0 -> skipped.
    // _claimFundedWithdrawRequest pays the ENTIRE aggregate (epoch-1 haircut receipt
    // + epoch-2 receipt) at par.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // Attacker received epoch-1 receipt at par instead of at p% — excess equals
    // receipt1 * (RECOVERY_FULL - p) / RECOVERY_FULL, stolen from funds owed to victim.
    uint256 haircutBasis = /* epoch-1 receipt amount */;
    uint256 expectedHonest = atkTranches2Price + haircutBasis * p / RECOVERY_FULL;
    assertGt(got, expectedHonest);

    // Victim's identical loss-epoch receipt now cannot be fully paid:
    // contract balance is short by the amount the attacker over-claimed.
    vm.prank(victim);
    vm.expectRevert(); // or assert balance shortfall
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertion: `lastWithdrawRequest[attacker]` points to epoch 2, `lossRecoveryPriceByEpoch[2] == 0`, so the epoch-1 loss receipt escapes `_clearWithdrawClaimForEpoch` and is paid in full by `_claimFundedWithdrawRequest`, leaving the vault short for remaining claimants.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
