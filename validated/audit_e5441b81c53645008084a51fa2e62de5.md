### Title
Fresh-PreCommit carve-out in `check_latest_block_in_tenure` records activity but never vetoes a stale-parent proposal - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_latest_block_in_tenure` (the sole parent-freshness check reached for non-tenure-change blocks via `confirms_latest_block_in_same_tenure`) only rejects a proposal outright when a *signed* block of equal-or-greater height exists in the tenure. When the tenure's true tip is merely `PreCommitted` (not yet signed), the "fresh pre-commit" branch logs miner activity but explicitly does not return `false`, so control falls through to the node `get_tenure_tip` comparison, which can still return `true` for a stale sibling proposal.

### Finding Description
The check flow in `SortitionData::check_latest_block_in_tenure` [1](#0-0)  is:

1. `get_tenure_last_block_info` looks up `get_last_signed_block` — i.e., only a block that has actually been *signed* (self or group) counts here. [2](#0-1)  If a signed block of height ≥ the proposal exists, the proposal is correctly rejected.
2. If there is no qualifying signed block (e.g. the true tip is only `PreCommitted`), that veto is skipped entirely.
3. The pre-commit branch then runs, but it is explicitly documented and coded to be non-vetoing: [3](#0-2)  "must NOT veto this proposal" — it only calls `update_last_activity_time` and falls through.
4. Execution proceeds to compare against `client.get_tenure_tip(tenure_id)`, the node's on-chain view [4](#0-3) . Because a pre-committed (unsigned) block by definition has not been accepted by the node yet, the node's tenure tip is still behind it. If the node's tip height is below the *stale* proposal's height too (which is guaranteed whenever the stale height is above whatever the node has processed), the function returns `Ok(true)` — i.e., "confirms latest block in tenure" — even though a fresher block already exists locally, pre-committed and awaiting only enough signatures.

So the invariant "approved parent == tenure's actual highest known-and-endorsed block" is not enforced by this function once the highest known block for the tenure is unsigned. The pre-commit-freshness carve-out was added purely to keep the pre-committing signers' inactivity timer alive (per the code comments), not as a canonicity gate, and there is no other call in `check_proposal` (v1.rs:319-339) that re-checks tenure-height freshness against a locally pre-committed-but-unsigned block for non-tenure-change proposals.

### Impact Explanation
This can cause an individual signer to sign (or continue processing towards signing) a non-canonical, stale sibling block within the same tenure while a fresher block is already mid-pre-commit, undermining per-tenure block-height monotonicity/canonicity that `check_latest_block_in_tenure` is meant to guarantee. In isolation this is a single-signer local mis-evaluation; it does not itself forge a threshold signature, since the offending signer is only one vote among the signer set and other signers who already pre-committed to the fresher block would (in principle) reject the stale sibling via their own local state. The severity is bounded by the fact that it requires the specific race window (tip pre-committed but not yet signed) and only affects the affected signer's individual response, not automatically a network-wide equivocation.

### Likelihood Explanation
Reaching this window requires that a block in the tenure has reached `PreCommitted` state (locally, via the signer's own state machine) but has not yet accumulated a threshold of signatures (`signed_self`/`signed_group` both unset) — a state that occurs naturally during the normal window between pre-commit and group-signature completion. An attacker only needs to gossip a competing `BlockProposal` for a lower/stale height during that window and does not need majority signer weight, a compromised key, or node/local access — this fits the constrained "single miner slot + gossip" attacker model.

### Recommendation
Make the pre-commit freshness check an actual veto, not just an activity update: if `is_fresh_pre_commit` is true, and `block.header.chain_length <= info.block.header.chain_length`, the function should return `Ok(false)` (after recording activity) instead of falling through to the node-tip comparison.

### Proof of Concept
Rust test outline in `stacks-signer/src/chainstate/tests/`:
1. Set up a `SignerDb` and `StacksClient` mock/fixture with a single tenure `consensus_hash`.
2. Insert a `BlockInfo` at chain height N with `state = BlockState::PreCommitted`, `approved_time = Some(now)`, and `signed_self = None`, `signed_group = None` (i.e., not yet signed), via `signer_db.insert_block`.
3. Configure the mock `client.get_tenure_tip` to return a node tip at height N-3 (simulating the node not having observed the pre-committed block).
4. Construct a sibling `NakamotoBlock` for the same tenure at height N-2 (stale, below the pre-committed tip).
5. Call `SortitionData::check_latest_block_in_tenure(&consensus_hash, &stale_block, &mut signer_db, &client, tenure_last_block_proposal_timeout, reorg_attempts_activity_timeout)`.
6. Assert the current (buggy) behavior returns `Ok(true)` due to the CARVE->NODE fallthrough, demonstrating the fail-open; after the fix, assert it returns `Ok(false)`. [5](#0-4)

    pub fn check_latest_block_in_tenure(
        tenure_id: &ConsensusHash,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,
    ) -> Result<bool, ClientError> {
        let last_block_info = SortitionData::get_tenure_last_block_info(
            tenure_id,
            signer_db,
            tenure_last_block_proposal_timeout,
        )?;

        if let Some(info) = last_block_info {
            // N.B. this block might not be the last globally accepted block across the network;
            // it's just the highest one in this tenure that we know about.  If this given block is
            // no higher than it, then it's definitely no higher than the last globally accepted
            // block across the network, so we can do an early rejection here.
            if block.header.chain_length <= info.block.header.chain_length {
                warn!(
                    "Miner's block proposal does not confirm as many blocks as we expect";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "expected_at_least" => info.block.header.chain_length + 1,
                );
                if info.signed_group.is_none_or(|signed_time| {
                    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
                }) {
                    // Note if there is no signed_group time, this is a locally accepted block (i.e. tenure_last_block_proposal_timeout has not been exceeded).
                    // Treat any attempt to reorg a locally accepted block as valid miner activity.
                    // If the call returns a globally accepted block, check its globally accepted time against a quarter of the block_proposal_timeout
                    // to give the miner some extra buffer time to wait for its chain tip to advance
                    // The miner may just be slow, so count this invalid block proposal towards valid miner activity.
                    if let Err(e) = signer_db.update_last_activity_time(
                        &block.header.consensus_hash,
                        get_epoch_time_secs(),
                    ) {
                        warn!("Failed to update last activity time: {e}");
                    }
                }
                return Ok(false);
            }
        }
