### Title
Out-of-range signer slot in a StackerDB signer-message event permanently kills the miner's `StackerDBListener`, wedging block-signature collection for the tenure - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run()` processes every `SignerMessageV0` in an incoming StackerDB event by looking up the sender's `slot_id` in `self.signer_entries`, a `HashMap<u32, NakamotoSignerEntry>` built once at listener construction from the *current* reward cycle's signer set. If a message arrives whose `slot_id` is not a key in that map, the handler does not skip/ignore the message — it returns `Err(NakamotoNodeError::SignerSignatureError(...))` from the entire `run()` function, terminating the listener thread outright.

### Finding Description
`StackerDBListener::new` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:189-283`) builds `signer_entries` strictly from `reward_set.signers()` for the reward cycle active when the listener was created, keyed by slot index `0..reward_set_signers.len()`: [1](#0-0) 

Inside the main event loop, messages are matched against `self.signer_set` (only the reward-cycle *parity*, 0 or 1 — not the exact reward cycle number): [2](#0-1) 

Then, for every message that passes that parity check, the slot lookup is done with a hard failure on miss: [3](#0-2) 

That `return Err(...)` propagates out of `run()`, and the thread that was spawned to run it only logs the error and exits — it is never respawned: [4](#0-3) 

The equality being broken: "signer_set matches → every message from that boot contract carries a `slot_id` inside `signer_entries`'s domain" is **not actually guaranteed**. The only filter applied is `signer_set == self.signer_set`, i.e. `reward_cycle % 2` equality, not "same reward cycle as when this listener booted." Two different `.signers-<cycle>-<lane>` boot contracts with the same parity but a different (larger) signer-set size can both satisfy the parity check while producing chunk events with `slot_id` values that don't exist in the currently-loaded `signer_entries` (built for a smaller reward cycle's signer count). Sources of a mismatched slot include:
- Late-arriving/gossiped chunks from the *previous* same-parity reward cycle's `.signers` contract during the boundary window where the new miner tenure's `SignerCoordinator`/listener has already been constructed for the new cycle but StackerDB events for the old contract are still being forwarded/observed (the contract-name/parity check at line 356 does not reject these if parity happens to match and `event.contract_id.name.starts_with(SIGNERS_NAME)` at line 332-333 is satisfied for any `.signers-*` contract).
- Any legitimate signer whose message happens to be relayed with a `slot_id` beyond the current cycle's signer count (e.g., if the signer set shrank between cycles of matching parity).

Because this check treats an unrecognized slot as a fatal, thread-terminating condition (`return Err`) rather than a skip/`continue` (as every other malformed-input case in the same loop does — see e.g. the "Signer entry not found"-adjacent `continue` patterns for bad-signature/unknown-block cases used elsewhere in the same function), a single out-of-range chunk permanently kills signature/rejection aggregation for the rest of the tenure with no automatic recovery.

### Impact Explanation
This is a High-severity liveness wedge: it does not require a majority of signers, forged keys, or access to `auth_token`. Once the listener thread dies, `StackerDBListenerComms` (shared via `Arc`) stops receiving any further `total_weight_approved`/`total_weight_rejected` updates for the block-status map, `signer_idle_timestamps`, `signer_read_count_timestamps`, and the `global_state_evaluator` — the very state the coordinator polls (`signer_coordinator.rs:512-562`) to decide whether a block reached the 70% signature threshold, was rejected, or timed out. From that point on, the coordinator can never observe new signatures for the current tenure and the miner treats it as `NakamotoNodeError::SignatureTimeout`/`SignersRejected` for every subsequent block it proposes, per `run_miner`'s single early-return-and-abort structure (`miner.rs:611-622`), which additionally tears down the whole miner thread rather than only the listener. This directly matches the "High – signer/coordinator wedged into never signing/collecting valid signatures" impact class: the node effectively stalls tenure block production until a fresh miner thread with a fresh, correctly-scoped listener is started (next tenure/burn block), not from any code path within the current one.

### Likelihood Explanation
Reachability only requires one instance of a StackerDB signer-message chunk being routed to the running listener with a `slot_id` outside the currently loaded `signer_entries` domain while `signer_set` (parity) still matches — a condition plausible during ordinary reward-cycle boundaries/gossip replay, and trivially reproducible without any privileged access, majority collusion, or valid signing key: the attacker only needs to get a `.signers-*` boot-contract chunk (of matching parity) accepted into StackerDB with an out-of-range slot id in its physical location, which is a property of *which slot* the chunk was written to (a boundary/relay condition), not of message content requiring a valid key.

### Recommendation
Change the failure mode at `stacks-node/src/nakamoto_node/stackerdb_listener.rs:372-377` (and the analogous check at line 378-383) from `return Err(...)` to `continue`/`warn!` + skip, consistent with how every other "unrecognized" input in this same loop (unknown block, bad rejection signature, etc.) is handled. Additionally/alternatively, key `signer_entries` (and the parity filter) by the exact reward-cycle identifier rather than only its parity, so that stale or foreign `.signers-*` contract events cannot reach this code path at all.

### Proof of Concept
1. Start a miner tenure; `SignerCoordinator::new` constructs `StackerDBListener` with `signer_entries` sized to the current reward cycle's signer count (e.g., 5 signers, slots 0-4).
2. Have any actor (a decommissioned signer from the previous same-parity reward cycle, or a relayed/gossiped stale chunk) cause a StackerDB event for a `.signers-*` boot contract of the same parity to be delivered to the running coordinator with `chunk.slot_id == 7` (out of the current 0-4 range) carrying any valid `SignerMessageV0` (e.g. a `BlockResponse::Accepted`).
3. `SignerEvent::<SignerMessageV0>::try_from` parses it successfully (`signer_set` parity check at line 356 passes because it only compares `% 2`).
4. In the loop at line 372-377, `self.signer_entries.get(&7)` returns `None`, and `run()` returns `Err(NakamotoNodeError::SignerSignatureError("Signer entry not found"))`.
5. The spawned thread in `signer_coordinator.rs:174-178` logs the error and exits; no other code respawns it. All subsequent legitimate signer block-acceptance/rejection messages for the remainder of the tenure are never processed by the coordinator, wedging block production until the tenure ends.
