### Title
Unfrozen working bank passed to `Bank::simulate_transaction()` panics the validator process from a single `simulateTransaction` RPC call - (File: rpc/src/rpc.rs, runtime/src/bank.rs)

### Summary
`Bank::simulate_transaction()` unconditionally asserts that the bank is frozen and panics otherwise: `assert!(self.is_frozen(), "simulation bank must be frozen");` [1](#0-0) . The JSON-RPC `simulateTransaction` handler obtains its bank via `meta.get_bank_with_config(RpcContextConfig { commitment, min_context_slot })` and passes it straight into `bank.simulate_transaction(&transaction, enable_cpi_recording)` [2](#0-1) . Nothing in the RPC handler guarantees the returned bank is frozen before this call. This mirrors the reported bug class: a check that exists in some code paths (bank freezing/validator-frozen checks) is missing/insufficient on a specific caller, letting an unprivileged actor drive execution into a state the check was meant to prevent — here causing a hard `assert!` panic instead of a graceful error.

### Finding Description
The unit test suite itself demonstrates the danger of this pattern:
- `test_rpc_simulate_transaction_panic_on_unfrozen_bank` explicitly shows that calling `simulateTransaction` against an unfrozen bank produces a panic with message "simulation bank must be frozen" [3](#0-2) .
- Every other `test_rpc_simulate_transaction*` test manually calls `bank.freeze()` before issuing the RPC request, with an explicit comment "Simulation bank must be frozen" [4](#0-3) [5](#0-4) [6](#0-5) .
- `test_rpc_send_transaction_preflight` freezes bank 0 up front with the comment "Freeze bank 0 to prevent a panic in `run_transaction_simulation()`" [7](#0-6) , confirming that the preflight-simulation path inside `sendTransaction` relies on the same unguarded `bank.simulate_transaction()` call.

In production, the bank handed to the RPC handler comes from `meta.get_bank_with_config(...)`, which for `processed`/default commitment typically resolves to the current working (tip) bank of `BankForks` — i.e., the bank actively being built by the leader/replay pipeline, which is *not yet frozen* until the block is finished. Whether a given RPC request's bank happens to already be frozen depends on validator-internal timing (whether the tip bank has been frozen yet when the RPC thread reads it), not on anything the RPC layer verifies or the caller controls. There is no check comparable to those on sibling code paths (e.g. the tests explicitly call `.freeze()` to avoid this) inside `rpc.rs`'s `simulate_transaction` or in `bank.simulate_transaction` for the case where it's invoked with an unfrozen bank via the public RPC path — it is instead a hard `assert!` that aborts the whole process (Rust panics in library code without `panic = "unwind"`-safe boundaries typically bring down the process/thread group in this codebase's server context).

### Impact Explanation
A single unprivileged `simulateTransaction` (or `sendTransaction` with preflight, which calls the same underlying `simulate_transaction`) JSON-RPC call, if it happens to race the bank-freezing sequence and obtain a not-yet-frozen working bank, triggers `assert!(self.is_frozen(), ...)` and panics. This matches the "concrete validator-process crash ... from one request" criterion: an ordinary RPC client (no validator/operator privileges) can crash the RPC-serving validator process merely by sending a normal-looking transaction for simulation at the wrong moment, denying service to the whole node.

### Likelihood Explanation
This requires no crafted/malicious transaction — the panic is purely a function of bank-freeze timing at the moment `get_bank_with_config` resolves and `simulate_transaction` is invoked, which is outside caller control but is a normal state during block production. Because the working (unfrozen) bank window recurs every slot, an attacker or even ordinary traffic sending `simulateTransaction` calls at high frequency will eventually race the freeze boundary and hit the panic. The consistent test-suite workaround of manually freezing the bank before every simulate test is strong evidence that unfrozen-bank invocation is a real, easily reachable condition rather than a purely theoretical one.

### Recommendation
In `rpc/src/rpc.rs`'s `simulate_transaction` (and any other caller of `Bank::simulate_transaction`), explicitly check `bank.is_frozen()` after obtaining the bank from `get_bank_with_config` and, if unfrozen, either wait/retry for the bank to freeze or fall back to `simulate_transaction_unchecked` (which is documented as safe for use without a frozen bank) instead of relying on the internal `assert!` to enforce this invariant. Alternatively, change `Bank::simulate_transaction` to return a `Result`/`RpcCustomError` when unfrozen rather than panicking, so a single caller's request cannot bring down the entire RPC-serving process.

### Proof of Concept
1. Start a validator RPC endpoint and observe the tip bank is periodically unfrozen while block production is in progress.
2. Send `simulateTransaction` requests continuously (as any unprivileged client) against `commitment: "processed"`.
3. When `meta.get_bank_with_config` resolves to the still-unfrozen working bank at the moment the RPC thread executes `bank.simulate_transaction(...)`, the process hits `assert!(self.is_frozen(), "simulation bank must be frozen")` in [1](#0-0)  and panics — exactly the scenario the repo's own test `test_rpc_simulate_transaction_panic_on_unfrozen_bank` reproduces deterministically by explicitly using an unfrozen bank [3](#0-2) .
