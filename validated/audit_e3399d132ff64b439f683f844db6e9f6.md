### Title
Loss-adjusted withdraw factor `lossRecoveryPriceByEpoch` is written under the post-increment epoch and never read, so haircut receipts claim at par and strand later claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the GMX `claimableCollateralFactorKey` never being initialized, `IdleCreditVault` stores the per-epoch loss recovery multiplier under an epoch key that no claim path ever looks up. As a result, a `stopEpochWithDuration`-style partial funding never applies the haircut: the loss-adjusted claim path always reads a zero price, and receipts fall through to the par claim path even though only a fraction of `pendingWithdraws` was funded. Early claimants overpay out of the pool; later claimants' claims revert for lack of underlying.

### Finding Description
`requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` (the pre-stop epoch, e.g. `N`) [1](#0-0) .

During `stopEpoch`, the CDO calls `strategy.deposit(...)` to pull borrower funds, and `deposit` increments `epochNumber` while `isEpochRunning()` is still true, moving it to `N+1` [2](#0-1) . `collectWithdrawFunds(_amount)` necessarily runs after that deposit (it collects the funds just deposited and `safeTransferFrom`s them), so when `_amount < pendingBasis` it writes `lossRecoveryPriceByEpoch[epochNumber]` — i.e. under key `N+1` [3](#0-2) .

`_claimLossAdjustedWithdrawRequest`, however, looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — key `N` — which is always zero, so it returns 0 [4](#0-3) . The claim then proceeds to `_claimFundedWithdrawRequest`, whose gate (`epochNumber <= lastWithdrawRequest[_user]` → `N+1 <= N`) now passes, and which pays `withdrawsRequests[_user]` **at par** via `_transferFundedClaim` [5](#0-4) .

### Impact Explanation
The loss-waterfall invariant is broken: pending receipts that should be paid `claimBasis * lossRecoveryPrice / RECOVERY_FULL` are paid 1:1. Only `pendingToFund < pendingBasis` underlying was collected, so the aggregate payouts exceed the funded amount; the first claimants extract other claimants' share and the last claimant(s) `claimWithdrawRequest` reverts on the underflow/shortfall, permanently freezing their funds in the vault. Loss equals the unrecovered `pendingBasis - pendingToFund` portion, transferred from late claimants to early ones.

### Likelihood Explanation
Requires only the documented partial-funding path (`previewLossAdjustedWithdrawFunds` / `collectWithdrawFunds` with `_amount < pendingBasis`), i.e. a `stopEpochWithDuration` loss or partial borrower repayment — an unprivileged-facing flow whenever the borrower underpays and the honest manager finalizes the epoch. No attacker privilege needed; the first pending receipt holder to call `claimWithdrawRequest` takes the excess.

### Recommendation
Store the recovery price under the request epoch being funded (e.g. the epoch recorded in the pending receipts, or `epochNumber - 1` post-increment), or look up `lossRecoveryPriceByEpoch` consistently on both write and read. Alternatively, carry the funded-vs-basis ratio alongside `pendingWithdraws` rather than in an epoch-keyed map. A regression test should assert that after a partial `collectWithdrawFunds`, each receipt pays exactly `basis * fundedAmount / pendingBasis`.

### Proof of Concept
Foundry fork sketch (adapt existing helpers in `test/foundry/IdleCreditVault.t.sol`, e.g. `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
// 1. Deposit for userA and userB; both call requestWithdraw in epoch 0
//    => lastWithdrawRequest[user] == 0, pendingWithdraws == PA + PB.
// 2. startEpoch(0); warp past epochEndDate.
// 3. Manager calls stopEpoch with a loss so that collectWithdrawFunds
//    receives pendingToFund < pendingBasis.
//    Assert: strategy.epochNumber() == 1, and
//    strategy.lossRecoveryPriceByEpoch(0) == 0   // read key
//    strategy.lossRecoveryPriceByEpoch(1) > 0    // write key — mismatch
// 4. userA calls cdoEpoch.claimWithdrawRequest()
//    Assert: userA received PA (par), not PA * lossRecoveryPrice / 1e18.
// 5. userB calls claimWithdrawRequest()
//    Assert: reverts (SafeERC20 underflow / insufficient balance),
//    userB's funds permanently frozen in IdleCreditVault.
```

Caveat: the write/read epoch-key mismatch hinges on `deposit()` (which increments `epochNumber`) executing before `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpoch`; the collection must happen after the deposit that supplies the funds, but the exact call ordering in `IdleCDOEpochVariant.sol` should be confirmed against that file before finalizing the PoC.

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
