### Title
Borrower repayments made after `finalizeDefault` are stranded in `ProgrammableBorrower` and can never reach LPs - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The external report describes `SwapperImpl.setTokenToBeneficiary()`: funds that legitimately arrived under one configuration (ETH) can no longer be forwarded to the beneficiary after the payout token is switched, so they sit in the contract forever. The same bug class exists in this codebase: `ProgrammableBorrower.repay()` remains fully functional after a hard default has been finalized, but `IdleCreditVault.finalizeDefaultRecovery()` is a one-time, capped distribution. Any principal/interest the borrower repays after finalization lands on the `ProgrammableBorrower` contract with no accounting path that routes it to tranche holders — the recovery analogue of "payback" — has already run and cannot be topped up.

### Finding Description
`repay()`/`_repay()` has no state gate tied to default finalization:

- `repay()` only checks `msg.sender != borrower` (`ProgrammableBorrower.sol:419-422`). `_repay()` pulls `assets` from the borrower and either re-deposits to the vault (if `epochAccountingActive`) or increments `bufferInterest` (`ProgrammableBorrower.sol:524-532`).
- On default, `onDefault()` only clears epoch accounting flags and baselines (`ProgrammableBorrower.sol:289-301`). It does **not** zero `borrowerPrincipal`, `borrowerInterestDebt`, or `borrowerInterestAccrued`, so `totalOwed` in `_repay()` stays non-zero and repayments keep succeeding.
- On the CDO side, `IdleCDOEpochVariant.finalizeDefault()` calls `IdleCreditVault(strategy).finalizeDefaultRecovery(_recoveredAmount, _recoverySource)`, which is documented as "one-time and cannot be topped up through this recovery path" (`IdleCDOEpochVariant.sol:194-199`). Recovered funds must enter via `transferFrom(_recoverySource)` into the strategy recovery reserve; the function reads nothing from `ProgrammableBorrower`'s on-hand balance.

Concrete trace:
1. Pool is in a running epoch, borrower has drawn `borrowerPrincipal > 0`.
2. `stopEpoch` fails to pull funds → `_handleBorrowerDefault` → `ProgrammableBorrower.onDefault()` (borrower debt stays on the books).
3. Owner calls `finalizeDefault(recoveredAmount, recoverySource)`; `defaultRecoveryInitialized` is set and the receipt claims are priced once.
4. The borrower later calls `repay(0)` (or anyone with a prior allowance gets `executeRepay` triggered). `transferFrom` succeeds, `borrowerPrincipal`/`borrowerInterestDebt` are cleared, and because `epochAccountingActive == false` the tokens remain as a raw on-hand balance with only `bufferInterest` bumped — a counter nothing reads post-default (`totalInterestDueNow` is only consumed at `stopEpoch`, which can no longer occur).
5. The repaid underlying is excluded from the already-finalized recovery multiplier and is unreachable by `claimDefaulted*`/`DefaultDistributor.claim` payouts. The only exit is the owner-trusted `rescueTokens()` (`ProgrammableBorrower.sol:602-605`), which sends funds to an arbitrary owner-chosen address, not to the LP distribution — analogous to the external report's stuck ETH.

The broken invariant is "recovery flows must reach the defaulted receipt/LP payout path": post-finalization repayments bypass it entirely.

### Impact Explanation
Permanent misrouting of repayment value. After `finalizeDefault`, every underlying unit the borrower repays (potentially the entire defaulted principal plus interest) is diverted away from the one-time recovery distribution. LPs and defaulted-receipt holders who were promised recovery via the aggregate multiplier receive only `_recoveredAmount`; genuinely returned borrower funds accumulate in `ProgrammableBorrower` where they are either permanently locked or recoverable only at the owner's discretion — matching the "funds stuck / sent to wrong destination after a state transition" impact of the Splits finding. Quantified loss: up to 100% of post-finalization borrower repayments (the whole remaining `borrowerPrincipal + borrowerInterestDebt + accrued`).

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that uses the programmable-borrower path and suffers a default: borrowers routinely cure or partially repay after default, and `repay()` is the documented, un-reverted route to do so (it is not blocked by `onDefault`). No privileged misbehavior is required — the honest borrower simply repays, an authorized executor can even trigger it, and the code silently accepts funds it can no longer distribute. The only mitigant is discretionary owner rescue, which is exactly the "stuck until admin intervention" pattern the source finding was rated Medium for.

### Recommendation
Gate repayment on the facility's default/finalization state so post-finalization repayments are routed into (or blocked from) the recovery distribution:

```diff
// ProgrammableBorrower.sol
+ bool public defaultedFinalized; // set via new hook from IdleCDO

function _repay(uint256 assets) internal returns (uint256 interestPaid, uint256 principalPaid) {
+   if (defaultedFinalized) {
+       // route repaid funds directly to the recovery source/reserve, or revert
+       underlyingToken.safeTransferFrom(borrower, recoverySink, assets);
+       return (0, 0);
+   }
    ...
}
```

Alternatively, add an `onDefaultFinalized()` hook called by `IdleCDOEpochVariant.finalizeDefault()` that makes `repay`/`executeRepay` revert, forcing the borrower to fund `finalizeDefaultRecovery` via `_recoverySource` before finalization — mirroring the Splits fix of draining the old-token balance before the switch is allowed to take effect.

### Proof of Concept
Foundry fork PoC sketch (repository test scaffolding under `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function test_RepayAfterFinalizeDefault_Stranded() public {
    // 1. Start epoch; borrower draws principal
    vm.prank(cdo); borrowerAdapter.onStartEpoch(0);
    vm.prank(borrower); borrowerAdapter.borrow(drawAmount);

    // 2. Epoch stop fails (borrower won't pay) -> default
    vm.prank(cdo); borrowerAdapter.onDefault();

    // 3. Owner finalizes default with partial recovery from a recoverySource
    deal(underlying, recoverySource, recovered);
    vm.prank(recoverySource); IERC20(underlying).approve(strategy, recovered);
    vm.prank(owner); cdo.finalizeDefault(recovered, recoverySource);

    // 4. Borrower repays full remaining obligation post-finalization
    deal(underlying, borrower, owed);
    vm.prank(borrower); IERC20(underlying).approve(address(borrowerAdapter), owed);
    vm.prank(borrower); borrowerAdapter.repay(0);

    // 5. Funds sit in ProgrammableBorrower; no LP-facing path claims them
    assertEq(IERC20(underlying).balanceOf(address(borrowerAdapter)), owed);
    // second finalizeDefault / recovery top-up is impossible (one-time)
    vm.expectRevert();
    vm.prank(owner); cdo.finalizeDefault(owed, address(borrowerAdapter));
}
```

Uncertainty note: I could not fully read `IdleCreditVault.finalizeDefaultRecovery` and the `_claimDefaulted*` paths within the available iterations, but the doc comment on `IdleCDOEpochVariant.finalizeDefault` explicitly states recovery "cannot be topped up through this recovery path" and must "enter through the strategy," which combined with `repay()` having no default gate establishes the stranding. If `finalizeDefaultRecovery` accepts `ProgrammableBorrower` itself as `_recoverySource` after repayments, the issue would partially reduce to ordering risk, but nothing currently forces repayment to happen before finalization.
