### Title
Builder pending-withdrawal amount is not capped to builder balance before being committed to the execution payload, allowing execution-layer payment to exceed the consensus-layer balance decrease - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` builds `Withdrawal` objects using the raw, uncapped `builder_pending_withdrawals[i].amount`, while the corresponding balance mutation in `apply_withdrawals` caps the deduction to `min(withdrawal.amount, builder.balance)`. The value committed to the execution payload (and therefore what the EL must pay to `fee_recipient`) can exceed what is actually removed from the builder's stake.

### Finding Description
`get_builder_withdrawals` in `specs/gloas/beacon-chain.md` iterates `state.builder_pending_withdrawals` and appends: [1](#0-0) 
with `amount=withdrawal.amount` — the value stored when the payment was queued (e.g. in `settle_builder_payment`/`process_builder_pending_payments`), not re-checked against the builder's current balance.

This `Withdrawal` list becomes `state.payload_expected_withdrawals`, the field the execution layer is required to honor exactly (per the withdrawals commitment invariant described in the "Modified `process_withdrawals`" note): [2](#0-1) 

Separately, `apply_withdrawals` performs the consensus-side balance mutation: [3](#0-2) 
which deducts only `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`.

If a builder's balance has decreased between when the `BuilderPendingWithdrawal` was queued (bid time, in `process_execution_payload_bid`) and when it is actually swept in `process_withdrawals` (e.g. due to an intervening builder exit/other withdrawal draining balance, or `builder_pending_withdrawals` accumulating multiple entries whose sum exceeds current balance — which the test suite explicitly exercises as "capped" behavior), then:
- `withdrawal.amount` (uncapped) is committed to the execution payload and paid to `fee_recipient` on the EL.
- `state.builders[builder_index].balance` is only decreased by the capped amount.

This breaks the equality that a payload payment must be exactly backed by an equivalent balance decrease. The existing test suite (`test_builder_withdrawal_insufficient_balance`) explicitly documents and accepts this cap: [4](#0-3) 
where `withdrawal.amount` stays at the full requested 5 ETH while `builders[0].balance` is capped to 0 — i.e. the withdrawal object (and thus the EL payment) is 4 ETH larger than what was actually deducted.

### Impact Explanation
This matches the Critical category "Gwei created ... or paid to a non-owner / a payload executed or paid that the block did not commit to" being inverted: here the block *does* commit (via `payload_expected_withdrawals`) to paying an amount that is not matched by the builder's actual balance decrease. The recipient (`fee_recipient`) receives real ETH on the execution layer that was never actually subtracted from any account's consensus-layer balance in full, i.e. Gwei is effectively created out of the protocol's accounting.

### Likelihood Explanation
This requires only an unprivileged sequence of events reachable by ordinary protocol operation — no special validator authority or coalition is needed:
1. A builder's balance drops below the sum of amounts already queued in `state.builder_pending_withdrawals` for that builder (achievable via ordinary builder exits/other withdrawal sweeps depleting balance, or multiple payments queued against the same builder as shown in `test_duplicate_builder_index_in_pending_withdrawals`).
2. `process_withdrawals` then sweeps those pending withdrawals, uncapped, into the payload commitment.

Because the spec's own capping logic (`min(...)`) already anticipates the balance-insufficiency scenario, the discrepancy between the payload commitment and the balance decrease is a design/spec inconsistency rather than a purely theoretical edge case.

### Recommendation
Cap the `amount` field of the `Withdrawal` constructed in `get_builder_withdrawals` (and in `get_builders_sweep_withdrawals`, which already correctly uses `builder.balance` directly) to `min(withdrawal.amount, builder.balance)` at construction time, so the value committed to `payload_expected_withdrawals` is always consistent with the amount actually deducted in `apply_withdrawals`.

### Proof of Concept
1. Queue a `BuilderPendingWithdrawal` for `builder_index=B` with `amount = X` (via a settled builder-payment bid).
2. Before this withdrawal is swept, reduce `state.builders[B].balance` below `X` (e.g., through a separate builder-exit sweep withdrawal or an additional pending withdrawal entry for the same builder that gets processed first, as in `test_duplicate_builder_index_in_pending_withdrawals`).
3. Run `process_withdrawals(state)`.
4. Observe: `state.payload_expected_withdrawals` contains a `Withdrawal(address=fee_recipient, amount=X)` (uncapped, per `get_builder_withdrawals` at [1](#0-0) ), while `state.builders[B].balance` decreases only by `min(X, balance) < X` (per `apply_withdrawals` at [3](#0-2) ). The execution layer pays out `X` to `fee_recipient` while the consensus layer only removed `min(X, balance)` from the builder — a net Gwei creation of `X - min(X, balance)`.
