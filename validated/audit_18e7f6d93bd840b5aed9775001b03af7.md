### Title
Attacker-controlled L1 deposit fields can panic the Base EVM handler via unchecked `.expect()` on `effective_balance_spending` overflow - (File: `crates/common/evm/src/handler.rs`)

### Summary
The reported FAAD2 CVE is a NULL-pointer dereference triggered by malformed input reaching unguarded logic, causing a crash/DoS. The closest reachable analog in this codebase is a `.expect()` call in the deposit-transaction fee/balance path of `BaseHandler::validate_against_state_and_deduct_caller`, which will panic the node process if the arithmetic it wraps ever overflows, rather than returning a typed error.

### Finding Description
In `crates/common/evm/src/handler.rs`, the deposit-transaction branch of `validate_against_state_and_deduct_caller` computes: [1](#0-0) 

```rust
if tx.tx_type() == DEPOSIT_TRANSACTION_TYPE {
    let basefee = block.basefee() as u128;
    let blob_price = block.blob_gasprice().unwrap_or_default();
    let mut caller = journal.load_account_with_code_mut(tx.caller())?.data;
    let effective_balance_spending = tx
        .effective_balance_spending(basefee, blob_price)
        .expect("Deposit transaction effective balance spending overflow")
        - tx.value();
```

`tx.effective_balance_spending` is expected to compute something like `gas_limit * effective_gas_price + value` (I was not able to locate/confirm the exact `effective_balance_spending` trait implementation before running out of tool budget, so the precise overflow conditions and existing bounds checks on `gas_limit`/`basefee`/`value` for deposit transactions are unverified). If that computation can overflow `u128`/`U256` arithmetic for any combination of attacker-influenced deposit fields (`gas_limit`, `value`, `mint`) that originate from an L1 `TransactionDeposited` log — decoded via `Deposits::decode`/`Deposits::unmarshal_v0` in `crates/consensus/protocol/src/deposits.rs` — the `.expect()` converts that overflow into an unconditional panic rather than a recoverable error, unlike every other error path in this same function which returns `InvalidTransaction`/`Err(...)` instead of panicking.

This is directly analogous to the FAAD2 bug class: a crafted/malformed but externally-reachable input (there, an audio stream; here, an L1 deposit log decoded into a deposit transaction) reaches an unguarded low-level operation (there, a null dereference; here, an arithmetic overflow guarded only by `.expect()`), producing a crash instead of a handled error.

### Impact Explanation
If reachable, this would allow an L1 depositor (or a malicious/compromised L1 deposit-contract emitter) to submit a deposit whose fields drive `effective_balance_spending` to overflow, panicking every L2 node (sequencer and all validators) that processes the block containing this deposit during `validate_against_state_and_deduct_caller`. This matches the "node halt / chain split" impact class called out in scope — sequencer stops producing blocks, and validators re-executing the same block also crash, since deposits are derived deterministically from L1 and must be processed by every node.

### Likelihood Explanation
I could not verify, within the available tool budget, (a) the exact definition of `effective_balance_spending` for `TxDeposit`, (b) whether `basefee`/`blob_price`/`gas_limit`/`value` are already range-limited elsewhere (e.g., by the deposit contract's L1-side gas/value limits, or by `unmarshal_v0`'s decoding constraints) such that overflow is actually unreachable, or (c) whether this code path (`crates/common/evm`, the "reth"-based handler) is still on the production execution path versus the newer `crates/common/evm2` registry-based executor (which has a separate, non-panicking deposit handler in `crates/common/evm2/src/registry.rs`). Given the extensive use of `saturating_add`/`saturating_sub` and `checked_sub` elsewhere in this exact function for the non-deposit path, and given `docs/guides/BLOCK_PRODUCTION_REVIEW.md`'s explicit "Production panics or unchecked assumptions" critical scenario calling out exactly this file/pattern, this `.expect()` looks like a deliberate or historical gap rather than a proven-safe invariant, but I cannot confirm actual overflow reachability without seeing the `effective_balance_spending` implementation and the deposit value/gas bounds enforced upstream.

### Recommendation
- Locate and review the `effective_balance_spending` implementation for `TxDeposit` (and its non-deposit counterpart) to determine the maximum possible operand values reachable from an L1 `TransactionDeposited` log.
- If overflow is reachable for any valid decoded deposit, replace the `.expect(...)` with a typed, non-panicking error path (as is already done for `chain.tx_cost_with_tx` and `balance.checked_sub` a few lines below in the same function) so a pathological deposit fails the transaction/block build instead of crashing the process.
- Add a regression test that constructs a `TxDeposit` with `gas_limit`, `basefee`, and `value` chosen to overflow `effective_balance_spending`, and assert the handler returns an error rather than panicking.
- Confirm whether `crates/common/evm2`'s deposit handler (`registry.rs`) is the actual production path superseding `crates/common/evm`; if so, this finding may already be moot for production and the older `crates/common/evm` crate should be flagged for removal or explicit non-production status.

### Proof of Concept
Not constructed — I was unable to confirm the operand ranges and the `effective_balance_spending` formula needed to demonstrate a concrete overflow trigger within the available investigation. A PoC would require: (1) confirming the formula, (2) confirming which of `gas_limit`, `value`, `basefee`, or `blob_price` are attacker/L1-controlled without an existing upstream bound sufficient to prevent overflow, and (3) crafting a `TransactionDeposited` L1 log whose decoded `TxDeposit` fields drive the computation past the integer's max value.
