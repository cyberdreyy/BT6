### Title
Cross-user response hijacking via `MessageId` collision in gateway legacy handler `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`core/services/gateway/handlers/capabilities/handler.go`'s `HandleLegacyUserMessage` stores a per-request `Callback` in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageId`, with no check for an existing in-flight entry and no binding to the requester's signer/sender identity. Because `MessageId` is fully attacker-chosen (bounded only by length/format checks in `api.Message.Validate`), an unprivileged client can submit a request whose `MessageId` collides with another user's in-flight request, silently overwriting the victim's saved callback so the DON's later response is delivered to the attacker instead. Note: the question's cited file `core/web/cookies.go` does not contain this logic — the actual vulnerable code lives in the gateway capabilities handler cited above; `core/web/cookies.go` is unrelated to gateway message handling.

### Finding Description
The gateway entry point `gateway.ProcessRequest` in `core/services/gateway/gateway.go` decodes an incoming `api.Message`, validates it with `msg.Validate()` (signature format, ID length/charset — but no uniqueness or per-sender scoping), creates a fresh `handlerscommon.NewCallback()`, and calls `h.HandleLegacyUserMessage(ctx, msg, callback)` [1](#0-0) .

In `HandleLegacyUserMessage`, after validating payload fields, the handler unconditionally does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [2](#0-1) 

There is no check for whether `msg.Body.MessageId` already has a live entry in the map, and no binding of the map entry to `msg.Body.Sender` (the signer address recovered during `Validate()`). `api.Message.Validate()` only checks length/format of `MessageId`, not uniqueness or ownership [3](#0-2) .

When a DON node later responds, `HandleNodeMessage` routes to `handleWebAPITriggerMessage`, which looks the callback up **purely by `MessageId`**, with no cross-check against the sender/signer of the original saved request:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()
if found {
    return savedCb.SendResponse(...)
}
``` [4](#0-3) 

Exploit flow:
1. Victim sends `msg_A{MessageId: "X", ...}`; handler stores `savedCallbacks["X"] = victimCallback` and forwards to all DON members [5](#0-4) .
2. Before any node responds, attacker (any holder of a valid ECDSA keypair, no role/session needed) sends `msg_B{MessageId: "X", ...}` signed with their own key. `msg.Validate()` passes since `MessageId` uniqueness is never checked. The handler overwrites `savedCallbacks["X"] = attackerCallback`.
3. A DON node responds to request ID `"X"` (either the original trigger response tied to msg_A's content, since the gateway forwards a message with `MessageId "X"` to nodes based on whichever the node happens to process/echo). `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds the attacker's callback (last writer wins), deletes the entry, and delivers the victim's response payload to `attackerCallback.SendResponse(...)`.
4. The attacker's `callback.Wait(ctx)` in `gateway.ProcessRequest` receives the victim's response data [6](#0-5) .

The existing test suite only validates the happy path and error paths not leaving stale entries in `savedCallbacks` [7](#0-6)  — it never covers the collision/overwrite scenario, and no code path prevents it.

### Impact Explanation
This is a cross-user response confusion / request impersonation: an attacker with no privileges beyond an arbitrary keypair can intercept another user's DON response data (e.g., trigger execution results, secrets embedded in workflow trigger responses via `webapicap.TriggerRequestPayload` flows) by winning a race on a colliding, self-chosen `MessageId`. This matches the Chainlink bounty impact class of "unauthorized access to another user's request/response data" (cross-user data leakage), scoped to whatever data flows through the `MethodWebAPITrigger` response payload.

### Likelihood Explanation
Precondition is minimal: attacker needs only a valid ECDSA keypair to sign an `api.Message` (no session, role, or allowlist entry is enforced at this stage — the code comment even notes `// TODO: apply allowlist and rate-limiting here` at line 384 of `handler.go`). The attacker must know or guess the victim's `MessageId` and race it before the DON responds; since `MessageId` values are often short/sequential/predictable (test fixtures use `"12345"`), and the attacker only needs to send after the victim's request is recorded but before the node's response returns, this is a feasible and repeatable race, especially against high-latency DON round trips.

### Recommendation
Bind `savedCallbacks` entries to the requester's identity, not just `MessageId`: key the map by `(Sender, MessageId)` or reject/queue a new `HandleLegacyUserMessage` call if `msg.Body.MessageId` already has a live entry (return an error instead of silently overwriting). Additionally, validate on `handleWebAPITriggerMessage`/`HandleNodeMessage` that the response's implied original sender matches the sender recorded in the `savedCallback` before delivering the payload.

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build handler via `setupHandler(t)`.
2. Create `msgA := triggerRequest(t, victimKey, ..., "sharedID", ...)` and `cbA := hc.NewCallback()`; call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)`.
3. Before responding, create `msgB := triggerRequest(t, attackerKey, ..., "sharedID", ...)` (same `MessageId`, different signer) and `cbB := hc.NewCallback()`; call `handler.HandleLegacyUserMessage(ctx, msgB, cbB)`.
4. Assert `handler.savedCallbacks["sharedID"]` now references `cbB`, not `cbA`.
5. Simulate node response for `msgA` (`hc.ValidatedResponseFromMessage(msgA)`), call `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)`.
6. Assert `cbB.Wait(ctx)` returns the response encoding `msgA` (victim's payload delivered to attacker's callback), while `cbA.Wait(ctx)` times out / never receives a response — proving cross-user leakage.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response

		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
