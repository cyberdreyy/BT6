### Title
Block-rejection dedup keyed only on `signer_addr` causes cross-block rejection-weight loss, wedging the reject-threshold consensus check - (File: `stacks-signer/src/signerdb.rs`)

### Summary
The `block_rejection_signer_addrs` table, which is meant to track which signer addresses rejected *a specific block*, uses `PRIMARY KEY (signer_addr)` instead of a composite key over `(signer_signature_hash, signer_addr)`. This is the same bug class as the external report: an identifier that should be scoped to a specific context (there: a path confined to a root directory; here: a rejection confined to a specific block) is instead used unscoped, so state belonging to one context leaks into / collides with another. Here the collision means a signer's rejection vote gets attributed to at most one `signer_signature_hash` ever, silently dropping its weight from every other block it also rejects, permanently corrupting the rejection-weight tally used to decide `mark_globally_rejected`.

### Finding Description
The table is created with: [1](#0-0) 

Note the comment explicitly says the `signer_signature_hash` "uniquely identif[ies] the block," yet the actual `PRIMARY KEY` is only `signer_addr`, dropping the block identity entirely from the uniqueness constraint. Compare this with the sibling `block_signatures` table just above it, where the natural per-signature uniqueness of an ECDSA signature happens to mask an equivalent design mistake (`PRIMARY KEY (signature)`), because two different (block, signer) pairs essentially never produce the same signature — but a `signer_addr` is *guaranteed* to repeat across many different blocks over the lifetime of the signer, so this weakness is actually triggered in normal operation.

The write/dedup path is: [2](#0-1) 

`add_block_rejection_signer_addr` is called per rejection and is expected to return `Ok(true)` for a new, distinct rejection and `Ok(false)` only when "we already have this signature" for *the same block*. Because the underlying table's primary key is `signer_addr` alone, an insert-dedup (`INSERT OR IGNORE`/conflict check) on that key will treat a rejection of block `B` by signer `S` as a duplicate of any *prior* rejection recorded by `S` against a completely unrelated block `A`, even though `A ≠ B`. The row keyed by `signer_addr = S` can only ever be associated with one `signer_signature_hash` at a time (whichever was inserted first, or last, depending on ignore-vs-replace semantics) — it can never simultaneously represent "S rejected A" and "S rejected B".

This directly corrupts the read path used to compute rejection weight: [3](#0-2) 

`get_block_rejection_signer_addrs(block_hash)` filters `WHERE signer_signature_hash = ?`, so any signer whose single global row has been claimed by a *different* block's hash is invisible to this query for the current block, and `total_reject_weight` is computed strictly from whatever rows still happen to point at `block_hash`. The equality that should hold — "the tallied rejection weight for block X equals the true weight of all signers who rejected X" — is broken as soon as any of those signers has ever rejected a different block, which is routine (a one-slot miner that repeatedly proposes invalid/conflicting blocks in the same tenure, or a node under normal operation over its lifetime, will produce exactly this pattern).

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality identified in scope: the locally-computed rejection tally used to decide `mark_globally_rejected` (and, pre-global-state, to invalidate a reorg-attempting miner) is silently and permanently under-counted for any signer address that has rejected more than one block. Practically:
- A block that a real supermajority (>30% blocking weight) has rejected may never reach the local `total_reject_weight` threshold needed to call `block_info.mark_globally_rejected()`, because some rejecting signers' weight is "stuck" attributed to an earlier block.
- This is a liveness wedge: the signer keeps waiting on `check_submitted_block_proposal`/pending state for a block that should have already been resolved as rejected, and the `ReorgNotAllowed`-based miner-invalidation path (`RejectReasonPrefix::ReorgNotAllowed` tally at lines 2354-2367) is likewise starved of weight it should have received, allowing an invalid-reorg-attempting miner to avoid being marked invalid.

This does not itself make a signer sign an invalid block, but it does wedge the local rejection-consensus bookkeeping, matching the in-scope "liveness wedge" impact bucket (a signer failing to converge on the correct globally-rejected verdict / failing to invalidate a misbehaving miner because the weight accounting silently drops votes it should have counted).

### Likelihood Explanation
High reachability: no majority collusion or privileged access is required. Any single miner that produces more than one invalid/conflicting block proposal within a signer's lifetime (a completely ordinary "one-slot miner" scenario explicitly in scope) causes honest signers to reject multiple distinct blocks over time, which is exactly the trigger condition — the second and subsequent rejections by the same signer address collide on the shared primary key regardless of block. This requires no cryptographic forgery, no majority signer compromise, and no external actor at all; it is a bookkeeping defect triggered by ordinary honest signer behavior.

### Recommendation
Change `block_rejection_signer_addrs`'s primary key to the composite `(signer_signature_hash, signer_addr)` (mirroring the doc comment's stated intent), and add a corresponding migration to backfill/repair existing rows. Audit `add_block_rejection_signer_addr`'s SQL to ensure the dedup/conflict check is scoped to both columns, not `signer_addr` alone, so that `get_block_rejection_signer_addrs(block_hash)` returns a complete and correct set of rejecting addresses for that specific block.

### Proof of Concept
1. Miner proposes invalid block `A` in a tenure; honest signer `S` (and enough others to be significant, but not by itself decisive) locally rejects `A`, calling `add_block_rejection_signer_addr(hash_A, S, ...)`. This inserts the only row for `signer_addr = S` (`hash_A`, `S`).
2. Later in the same or a later tenure, the same miner (or any miner) proposes a second invalid/conflicting block `B`. Signer `S` rejects `B` too, calling `add_block_rejection_signer_addr(hash_B, S, ...)`.
3. Because `PRIMARY KEY (signer_addr)` (`stacks-signer/src/signerdb.rs:514-524`) allows only one row per `signer_addr` in the whole table, this second call either silently no-ops (if the insert is `INSERT OR IGNORE`) — leaving `S`'s vote permanently attached to `A` and absent from `B` — or overwrites the row to point at `B`, retroactively erasing `S`'s vote against `A`.
4. Either way, `get_block_rejection_signer_addrs(hash_B)` (or `hash_A`, in the overwrite case) at `stacks-signer/src/v0/signer.rs:2297` fails to return `S`'s address for one of the two blocks, so `total_reject_weight` for that block undercounts by `S`'s weight — repeatable for every signer address that rejects more than one block, compounding the undercount and potentially keeping a block that should be globally rejected from ever reaching that state via `mark_globally_rejected` at `stacks-signer/src/v0/signer.rs:2335`.
