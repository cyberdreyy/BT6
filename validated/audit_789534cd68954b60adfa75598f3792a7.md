## Analysis

The reported bug class is: a fixed-size lookup/index table that does not cover the full range of possible values for an on-chain field, so indexing it with an out-of-range value silently returns wrong data or corrupts the calculation, denying rewards/value to the affected users.

In `marginfi-v2` the closest analog to this pattern is the `EXP_10_I80F48` decimal-scaling table, which is used to convert token amounts to/from their underlying mint decimal precision throughout the accounting and health-check code.

`EXP_10_I80F48` is defined with only 24 entries (indices `0..=23`): [1](#0-0) 

The codebase is aware that a raw index derived from an untrusted/external `u8` decimals value can exceed this table, and it defends against it in several places using `.get()` with explicit bounds handling: [2](#0-1) [3](#0-2) [4](#0-3) 

However, the core value-calculation routine `calc_value`, which is invoked for **every** asset and liability balance during health checks (deposit, withdraw, borrow, repay, liquidation), performs an **unchecked, direct index** into the same table using `mint_decimals` taken straight from the `Bank` account: [5](#0-4) 

The same unguarded pattern also exists in the Pyth price-exponent conversion helper, which indexes the table using an oracle-supplied exponent: [6](#0-5) 

`mint_decimals` is a `u8` (theoretically `0..=255` for SPL Token / Token-2022 mints), but the table only has 24 valid slots. If a bank is ever created/cloned for a mint whose decimals value is `>= 24` (or an integration path — Kamino/Drift/Solend/JupLend adapters compute `BankConfig`/`Bank.mint_decimals` from externally-sourced reserve/market metadata, see e.g. `to_bank_config` in `programs/marginfi/src/state/kamino.rs`, `drift.rs`, `juplend.rs`), then `calc_value` panics on out-of-bounds array access instead of returning a safe error like the `.get()`-based call sites do elsewhere in the same codebase.

### Title
Unchecked `EXP_10_I80F48` table indexing by `mint_decimals` in `calc_value` can panic and durably freeze health checks for a bank - (File: `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
`calc_value()` scales token amounts using `EXP_10_I80F48[mint_decimals as usize]`, a fixed 24-entry lookup table, but does not validate that `mint_decimals` (a `u8`, up to 255) is within the table's bounds, unlike equivalent lookups elsewhere in the codebase (`price.rs::scale_supplies`, `price.rs::convert_decimals`, `p0-cli/src/output.rs::safe_decimals`) which all use `.get()`/clamping with explicit bounds handling.

### Finding Description
`calc_value` is the central USD-value calculation routine used by both asset and liability weighted-value paths in health checks: [7](#0-6) 

It indexes the scaling table directly with the bank's stored `mint_decimals` value: [8](#0-7) 

`EXP_10_I80F48` only defines 24 entries (`10^0`..`10^23`), but nothing in `BankConfig`/`Bank` enforces `mint_decimals < 24` at bank-creation or clone time. Integration adapters populate `mint_decimals`/decimal-dependent fields from externally supplied CPI data (Kamino reserve, Drift spot market, Solend reserve, JupLend lending state), and `clone_bank.rs` propagates mint metadata as-is. This mirrors the root cause of the reported bug: a table sized for an assumed-complete set of values is indexed with a value from a field whose full range was not accounted for.

### Impact Explanation
If a bank's `mint_decimals` ever reaches or exceeds 24, every call to `calc_value` for that bank's balances panics. Since `calc_value` runs inside the mandatory health-check path invoked on deposit, withdraw, borrow, repay, and liquidation for **any account holding a balance in that bank**, the panic aborts the transaction. This produces a durable denial-of-service: user funds already deposited in (or borrowed against) the affected bank become permanently un-withdrawable and unliquidatable, a freeze with direct financial impact, until a program upgrade intervenes. This is a stronger effect than the original report's "receives zero reward"; it is a full asset freeze rather than a missed reward.

### Likelihood Explanation
Triggering this requires a bank to exist with `mint_decimals >= 24`, which is not enforced anywhere in bank creation/configuration code that was found. Real-world SPL/Token-2022 mints normally use ≤ 9 decimals, so likelihood via a "normal" token is low, but the field is a raw `u8` with no validation, and several code paths (including integration adapters that read decimals from external protocol accounts) populate it without a range check — the same class of "unaudited assumption about a bounded range" that caused the original Mythical-weapon bug. This is a latent correctness/robustness gap rather than a trivially-triggerable exploit, so likelihood is best characterized as low-to-medium, contingent on either an admin/adapter path introducing an anomalous mint or an upstream integration protocol exposing an out-of-range decimals value.

### Recommendation
Replace the raw index `EXP_10_I80F48[mint_decimals as usize]` in `calc_value` (and similarly in `pyth_price_components_to_i80f48`) with the same safe pattern already used elsewhere in the repo (`EXP_10_I80F48.get(idx).ok_or(...)`), returning a `MarginfiError` instead of panicking, and/or explicitly validate `mint_decimals < EXP_10_I80F48.len()` when a bank is created, cloned, or its config updated (including all Kamino/Drift/Solend/JupLend `to_bank_config` conversions).

### Proof of Concept
1. Construct/onboard a `Bank` (directly or via one of the integration `to_bank_config` converters) whose underlying mint/reserve reports `decimals = 24` or higher.
2. Deposit or otherwise create a non-zero balance for that bank on a `MarginfiAccount`.
3. Trigger any instruction that performs a health check (e.g., `lending_account_borrow`, `lending_account_withdraw`, or liquidation) touching that balance.
4. `calc_weighted_asset_value_cached_standalone`/`calc_weighted_liab_value_cached_standalone` call `calc_value`, which executes `EXP_10_I80F48[24]` — out of bounds for the 24-element array — causing the instruction to panic and abort, and every subsequent health-check-requiring instruction on that account/bank to fail identically.

pub fn convert_decimals(n: I80F48, from_dec: u8, to_dec: u8) -> Option<I80F48> {
    if from_dec == to_dec {
        return Some(n);
    }

    let diff = (to_dec as i32) - (from_dec as i32);

    if abs > 23 {
        return None;
    }

    let scale: I80F48 = EXP_10_I80F48[abs];

#[inline(always)]
fn pyth_price_components_to_i80f48(price: I80F48, exponent: i32) -> MarginfiResult<I80F48> {
    let scaling_factor = EXP_10_I80F48[exponent.unsigned_abs() as usize];

    let price = if exponent == 0 {
        price
    } else if exponent < 0 {
        price
            .checked_div(scaling_factor)
            .ok_or_else(math_error!())?
    } else {
        price
            .checked_mul(scaling_factor)
            .ok_or_else(math_error!())?
    };

    Ok(price)
}
