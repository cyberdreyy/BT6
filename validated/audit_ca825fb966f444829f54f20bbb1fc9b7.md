## Title
Permanent DoS of stake/vesting commission and reward distribution via griefer blocking `aptos_account::deposit_coins` in shared shareholder loops - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`, `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`staking_contract::distribute_internal` and `vesting::distribute` each pay out withdrawable stake to *every* shareholder/recipient of a shared pool in a single atomic transaction, using `aptos_account::deposit_coins` for each payout. `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient account exists, has not registered a `CoinStore<AptosCoin>`, and has called the permissionless `aptos_account::set_allow_direct_coin_transfers(false)`. Because any shareholder can independently configure their own account this way, and because the distribution functions do not use a safe/try-transfer pattern (the class of bug flagged for the SafeERC20 report), a single unprivileged shareholder or commission beneficiary can permanently block distribution to *all* other shareholders sharing the same `StakingContract`/vesting pool.

### Finding Description
`staking_contract::distribute_internal` withdraws the pool's total inactive/pending_inactive stake and then loops over every shareholder in `staking_contract.distribution_pool`, redeeming their shares and calling `aptos_account::deposit_coins(recipient, ...)`: [1](#0-0) 

`vesting::distribute` similarly iterates `grant_pool.shareholders()` and calls `aptos_account::deposit_coins` for each shareholder (or their beneficiary): [2](#0-1) 

`aptos_account::deposit_coins` aborts when the recipient is registered as an account but has opted out of un-registered direct transfers via `set_allow_direct_coin_transfers(false)` and has no `CoinStore<AptosCoin>`: [3](#0-2) 

`set_allow_direct_coin_transfers` is a fully permissionless, unprivileged entry function that any account (any shareholder, delegator, or operator beneficiary) can call on itself at any time: [4](#0-3) 

Because `distribute_internal`/`distribute` process **all** recipients of the shared pool within one atomic transaction and do not skip or isolate a failing recipient, if any single shareholder (attacker) sets `allow_arbitrary_coin_transfers = false` and never registers `CoinStore<AptosCoin>`, every subsequent call to `distribute`/`vest`/`unlock_stake`/`switch_operator`/`update_commision` (all of which internally call `distribute_internal`) will abort at that shareholder's payout, reverting the whole transaction. This blocks reward/commission withdrawal for every other, non-malicious shareholder/operator sharing that `StakingContract` or vesting pool, since there is no mechanism to remove a shareholder from `distribution_pool`/`grant_pool` or to skip a failing payout.

### Impact Explanation
This is a self-inflicted-but-shared-state griefing vector: an unprivileged delegator/shareholder can permanently freeze distribution of already-unlocked/inactive stake and commission for every other participant of the same staking contract or vesting pool, meeting the "Permanent lock or non-recoverable loss of claim rights" and "Operator commission/beneficiary payout... traps value" categories in the required impact list. Because `distribute` is `public entry` and callable by anyone, but always fails once the griefer's condition is set, the trapped value (inactive/pending_inactive stake owed to legitimate co-shareholders and the operator's commission) cannot be recovered through any code path in the module — there is no admin override, no forced removal of a shareholder from the distribution/grant pool, and no partial/best-effort distribution logic.

### Likelihood Explanation
Setting the precondition requires only two calls the attacker fully controls on their own account: `aptos_account::set_allow_direct_coin_transfers(signer, false)` and simply never registering `CoinStore<AptosCoin>` (default state for many accounts, especially post-FA-migration users who hold no legacy `Coin<AptosCoin>` store). No special role, capital, or privileged access is required — only being a shareholder of the shared distribution/grant pool (which can be as ordinary as unlocking any stake through a `staking_contract` or being a vesting shareholder). This makes the likelihood high for staking contracts/vesting pools with multiple shareholders, and it is trivially and cheaply repeatable.

### Recommendation
Use a "pull" rather than "push" distribution pattern, or wrap each `aptos_account::deposit_coins` call in the shareholder loop so that a failing transfer does not abort the whole batch (e.g., catch the failure and instead credit the amount to a per-recipient claimable balance that the recipient can withdraw once eligible, analogous to using SafeERC20's checked-transfer pattern but with graceful fallback rather than abort-on-failure for third-party recipients). At minimum, skip/queue distributions to recipients that cannot currently accept direct transfers instead of reverting the entire multi-recipient transaction.

### Proof of Concept
1. Staker creates a `StakingContract` with operator `O`; delegator/shareholder `A` (attacker) and shareholder `B` (victim) both accrue a distribution entry in `staking_contract.distribution_pool` (e.g., via partial `unlock_stake` calls that call `add_distribution` for each staker/recipient).
2. `A` calls `aptos_account::set_allow_direct_coin_transfers(A_signer, false)` and never calls `coin::register<AptosCoin>(A_signer)` (default state).
3. Stake pool accrues inactive/pending_inactive funds; anyone calls `staking_contract::distribute(staker, operator)`.
4. `distribute_internal`'s while-loop reaches recipient `A`; `aptos_account::deposit_coins` hits the `!coin::is_account_registered<AptosCoin>(A)` branch, calls `can_receive_direct_coin_transfers(A)`, which returns `false` (per step 2), so the `assert!` at [5](#0-4) 
aborts the entire transaction with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. `B`'s legitimate, already-unlocked stake and the operator's commission remain permanently stuck in the pool: every future call to `distribute`, `vest`, `unlock_stake`, `switch_operator`, or `update_commision` re-enters `distribute_internal`/`distribute` and fails at the same point, with no code path to exclude `A` from the shareholder set.

Note: I was not able to fully trace whether the AptosCoin fungible-asset migration (`coin::maybe_convert_to_fungible_store`, `primary_fungible_store`) changes `is_account_registered<AptosCoin>` semantics in a way that could bypass this specific `assert!` for the native AptosCoin type on current mainnet state; the framework code paths I reviewed (`aptos_account::deposit_coins`, `coin::is_account_registered`) still show the guarded, abort-capable branch for accounts without a `CoinStore`. This should be independently confirmed against the exact on-chain `AptosFramework` release before treating this as conclusively exploitable in production, given index/coverage limits on `coin.move`'s FA-migration internals — a Devin session with full repo access could verify this precisely.

    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
