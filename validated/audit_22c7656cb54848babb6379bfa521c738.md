### Title
Loss-adjusted withdraw receipts are paid at par after a later request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, pending withdraw receipts are only partially funded and the haircut is recorded in `lossRecoveryPriceByEpoch[epochNumber]`. The loss-adjusted claim path, `_claimLossAdjustedWithdrawRequest`, looks up the haircut exclusively via `lastWithdrawRequest[_user]` — a single per-user scalar that `requestWithdraw` overwrites on every new request. A user whose epoch-N receipt was haircutted can simply request another withdraw in epoch N+1; the stale receipt for epoch N is then invisible to the loss path and is paid at full par by `_claimFundedWithdrawRequest`, even though only `claimBasis * lossRecoveryPrice / RECOVERY_FULL` was ever funded.

### Finding Description
The kernel bug class is a lifetime mismatch: `fl->opt` is freed while the containing flowlabel remains reachable, so a later reader dereferences stale/freed state. The analog here is a receipt that outlives its funding basis: after a loss-adjusted `collectWithdrawFunds`, `pendingWithdraws` is zeroed and only `lossRecoveryPriceByEpoch[epochNumber]` remembers that epoch-N receipts are worth less than par.

The relevant flow:

- `requestWithdraw` records `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, aggregates into `withdrawsRequests[_user]`, and unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) 
- `collectWithdrawFunds` on a shortfall stores `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` [2](#0-1) 
- `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and returns 0 if `lossRecoveryPriceByEpoch[lossEpoch] == 0` — it never scans other epochs with receipts [3](#0-2) 
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still contains the epoch-N receipt — at par [4](#0-3) 

Because `_clearWithdrawClaimForEpoch` is never reached for epoch N, `withdrawsRequestsByEpoch[_user][N]` and its share of `withdrawsRequests[_user]` remain intact, and the strategy only holds `amount * lossRecoveryPrice / RECOVERY_FULL` of underlying for that receipt. The claim pays the full `amount`, extracting the haircut difference from the shared funded-claim reserve.

No existing guard stops this: the `epochNumber <= lastWithdrawRequest` gate only enforces a one-epoch wait, `isEpochWithdrawZero`/price checks are in the separate epoch-queue contract, and `lossRecoveryPriceByEpoch` is never consulted for epochs other than `lastWithdrawRequest`.

### Impact Explanation
Direct theft / insolvency. The attacker receives `claimBasis_N * (1 - lossRecoveryPrice) / RECOVERY_FULL` more underlying than was funded for their receipt. That excess is drawn from the strategy's funded-claim balance, so other pending claimants (funded receipts, post-loss withdrawers) are left short — a permanent loss socialized onto honest users. With a 50% recovery price and a 100k USDC receipt, the attacker extracts ~50k USDC of unfunded payout.

### Likelihood Explanation
Requirements: a `stopEpochWithDuration` loss occurs (manager/borrower-driven, honest), and the attacker is any KYC'd tranche holder with a pending receipt in the loss epoch plus a small second deposit to re-request withdraw in a later epoch. No privileged role, no oracle manipulation, no timing race — just two ordinary `requestWithdraw` calls and waiting two epochs. Any loss epoch creates the condition for all affected receipt holders simultaneously.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, do not key the loss lookup solely on `lastWithdrawRequest[_user]`. Either iterate/track all epochs with non-zero `withdrawsRequestsByEpoch[_user]` that have a `lossRecoveryPriceByEpoch` entry, or subtract the haircutted basis from `withdrawsRequests[_user]` at `collectWithdrawFunds` time so the funded path can never pay it at par. At minimum, when processing a claim, check every epoch `e` with `withdrawsRequestsByEpoch[_user][e] != 0` for a recorded `lossRecoveryPriceByEpoch[e]` before letting the balance reach `_claimFundedWithdrawRequest`.

function testLossReceiptPaidAtPar() public {
    // epoch N running; attacker holds tranche tokens
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(ATTACKER_TRANCHES, address(tranche));

    // borrower funds only partially; manager stops epoch with loss
    // -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[N] = 0.5e18-ish
    _stopEpochWithLoss(lossAmount); // honest manager/borrower sequence

    // new epoch starts; attacker re-requests withdraw with a second deposit
    vm.prank(manager);
    cdoEpoch.startEpoch();
    _depositWithUser(attacker, smallAmount);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(newTranches, address(tranche)); // lastWithdrawRequest -> N+1

    // epoch N+1 ends normally, fully funded
    _stopCurrentEpochFullyFunded();

    // claim: loss path sees lossRecoveryPriceByEpoch[N+1] == 0 -> skip
    // funded path pays withdrawsRequests[attacker] (incl. epoch-N receipt) at par
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest(attacker);

    // attacker received full epoch-N basis despite only ~50% being funded;
    // strategy underlying is short by claimBasis_N * (1 - lossRecoveryPrice)
    assertGt(underlying.balanceOf(attacker), fundedEntitlement);
}

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
