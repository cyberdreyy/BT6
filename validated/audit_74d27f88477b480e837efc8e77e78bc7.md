### Title
Attacker-chosen request ID reuse in confidentialrelay handler allows stale node responses from a prior (different user's) request to be captured into an attacker's new bundle - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`h.activeRequests` is keyed solely by the client-supplied `req.ID` string, with uniqueness enforced only for the duration the request is active. `HandleNodeMessage` routes any incoming node response to whatever `activeRequest` currently occupies that ID slot. Because `sendResponseAndClearRequest` deletes the map entry for `req.ID` as soon as a request completes, an attacker who controls request IDs (`HandleJSONRPCUserMessage` accepts arbitrary non-empty IDs up to 200 chars) can immediately re-register the same ID and race a still-in-flight, legitimately signed response addressed to the prior (victim) request into their own bundle.

### Finding Description
`newActiveRequest` only rejects an ID if it is *currently* present in `h.activeRequests`; it does not track that an ID was recently used by another (victim) request: [1](#0-0) 

`HandleNodeMessage` looks up the `activeRequest` purely by the response's `ID` field, with no binding to the specific request instance/nonce or to node send timing: [2](#0-1) 

`sendResponseAndClearRequest` deletes the map entry for `ar.req.ID` right after claiming completion, freeing the ID for reuse while a node response addressed to the just-completed request may still be in transit (e.g., delayed by network jitter, or sent right at the `nodeSendTimeout`/`requestTimeout` boundary): [3](#0-2) 

Sequence:
1. Victim (or attacker acting first) submits request via `HandleJSONRPCUserMessage` with `req.ID = "X"`, creating `ar1`; the DON fans out and a node's response is in flight.
2. `ar1` completes/expires and is deleted from `h.activeRequests["X"]` by `sendResponseAndClearRequest`.
3. Attacker immediately calls `HandleJSONRPCUserMessage` with the same `ID = "X"` (same `Method`, e.g. `MethodSecretsGet`), creating `ar2` and re-occupying the map slot.
4. The delayed node response for the original `ar1` request arrives at `HandleNodeMessage` with `resp.ID = "X"`; `getActiveRequest("X")` now returns `ar2`, so `ar2.addResponseForNode` captures it into the attacker's bundle.

The bundler only decodes structurally-typed payloads (`SignedSecretsResponseResult`/`SignedCapabilityResponseResult`) and adds any node response that decodes successfully, without checking that the signed payload corresponds to the specific request's params/owner — it is intentionally a "dumb fan-in" that defers all correctness/authorization checks to the enclave: [4](#0-3) [5](#0-4) 

Whether this results in real cross-user data leakage depends entirely on downstream enclave verification (outside this repo/scope) actually checking that each signed node response's content (e.g., specific owner/job/secret identifiers) matches what the *current* request `X` is asking for, rather than trusting because it decoded and is well-signed. That verification code is not present in `core/services/gateway/handlers/confidentialrelay/`, so it cannot be confirmed here.

### Impact Explanation
If the enclave trusts the gateway's per-response bundle keyed by `ID` without independently re-deriving/validating that every signed response's content matches the specific query parameters of the request it is being counted toward, an attacker gains a mechanism to (a) contaminate their own bundle with genuine signed responses that were destined for another user's request, potentially padding quorum toward including secrets or capability results with content the attacker didn't request but which the enclave might process, or (b) cause the victim's stale response to instead be silently absorbed by the attacker's request. This maps to "cross-user response confusion" as scoped, but full exploitation into secret disclosure or unauthorized fund/job action requires an enclave-side gap that is not visible in this repository.

### Likelihood Explanation
Requires only an unauthenticated/low-privilege gateway client able to submit `HandleJSONRPCUserMessage` requests with attacker-chosen IDs — no operator or node-level access. The race window is narrow (must reuse the ID within the small gap between `sendResponseAndClearRequest`'s delete and any straggling node response), but is repeatable: an attacker could flood many IDs, or intentionally trigger fast completion (e.g., malformed error bundle path) on their own victim-adjacent probe requests and immediately reclaim the ID, making the race practically achievable over many attempts even without control over the exact timing of the victim's traffic.

### Recommendation
Bind node responses to the specific request instance rather than only the string ID: include a per-request unpredictable nonce/opaque handle (embedded in the request forwarded to the DON, e.g. via `jsonrpc.Request.ID` composed as `<clientID>:<uuid>` or a separate correlation field checked in `HandleNodeMessage`), and verify in `HandleNodeMessage`/`addResponseForNode` that the response corresponds to the exact `activeRequest` pointer that sent it (e.g., store a monotonically-increasing generation/epoch counter per ID and compare it, or don't reuse IDs at all until a cooldown period equal to `nodeSendTimeout` has elapsed since deletion). Also consider partitioning `activeRequests` per authenticated caller/session so ID collisions cannot cross user boundaries.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/confidentialrelay/handler_test.go`:
1. Construct a `handler` with a fake `clock`, DON, and bundler stub.
2. Call `h.newActiveRequest(reqVictim{ID:"X", Method: MethodSecretsGet, Params: victimParams}, victimCallback)` to create `ar1`; do not call `fanOutToNodes` (simulate node response arriving later).
3. Directly call `h.sendResponseAndClearRequest(ctx, ar1, somePayload)` to simulate ar1 completing and being removed from `h.activeRequests`.
4. Immediately call `h.newActiveRequest(reqAttacker{ID:"X", Method: MethodSecretsGet, Params: attackerParams}, attackerCallback)` to create `ar2`, confirming `h.getActiveRequest("X") == ar2`.
5. Construct a `jsonrpc.Response[json.RawMessage]{ID:"X", Result: victimSignedResult}` simulating the stale node response originally destined for `ar1`, and call `h.HandleNodeMessage(ctx, resp, nodeAddr)`.
6. Assert `ar2.addResponseForNode` succeeded (returned `true`) and that `ar2.copiedResponses()` now contains the victim's signed response — proving the attacker's bundle absorbed data intended for a different, already-completed request, violating the request-binding invariant.

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	l := logger.With(h.lggr, "method", resp.Method, "requestID", resp.ID, "nodeAddr", nodeAddr)
	l.Debugw("handling node response")

	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		l.Debugw("node is rate limited", "nodeAddr", nodeAddr)
		return nil
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		l.Debug("global relay rate limit exceeded")
		return nil
	}

	ar := h.getActiveRequest(resp.ID)
	if ar == nil {
		l.Debugw("no pending request found for ID")
		return nil
	}

	added := ar.addResponseForNode(nodeAddr, resp)
	if !added {
		l.Errorw("duplicate response from node, ignoring", "nodeAddr", nodeAddr)
		return nil
	}

// sendResponseAndClearRequest claims the request, sends payload, and removes it from
// activeRequests. Concurrent completion paths (node-message forward,
// terminal-state forward, quorum grace, expiry) may all race here; only the first
// claimer sends. Metrics are recorded only after a successful send so losers do not
// double-count.
func (h *handler) sendResponseAndClearRequest(ctx context.Context, ar *activeRequest, payload gwhandlers.UserCallbackPayload) error {
	if !ar.completed.CompareAndSwap(false, true) {
		// Another path already answered this request.
		return nil
	}

	sendErr := ar.SendResponse(payload)

	h.mu.Lock()
	delete(h.activeRequests, ar.req.ID)
	h.mu.Unlock()

	if sendErr != nil {
		h.lggr.Errorw("error sending response to user", "requestID", ar.req.ID, "error", sendErr)
		return sendErr
	}

	h.recordMetrics(ctx, payload.ErrorCode)
	h.lggr.Debugw("response sent to user", "requestID", ar.req.ID, "errorCode", payload.ErrorCode)
	return nil
}

// bundler assembles the gateway's response to the enclave. The gateway is a dumb
// fan-in: it forwards every per-node signed response it collected, in one bundle,
// without verifying signatures, checking signer membership, or deciding quorum.
//
// The enclave is the sole trust anchor. It groups the bundle by response hash,
// verifies each signature against the relay-DON signer set, and accepts the result
// backed by F+1 valid distinct signers. Because responses are keyed upstream by the
// gateway-authenticated node address (one response per node), a single compromised
// relay node can contribute at most its own one response to the bundle. It cannot
// manufacture quorum by fabricating signer identities; the worst it can do is add
// noise the enclave discards. This is what closes the prior liveness gap, where the
// gateway counted unverified, attacker-controlled signer identities toward quorum
// and could commit to a forged response, starving the enclave of the real one.
type bundler struct{}

func (b *bundler) Bundle(req jsonrpc.Request[json.RawMessage], resps map[string]jsonrpc.Response[json.RawMessage], l logger.Logger) (*BundleSummary, error) {
	summary := newBundleSummary(len(resps))

	switch req.Method {
	case relaytypes.MethodSecretsGet:
		out := make([]relaytypes.SignedSecretsResponseResult, 0, len(resps))
		for nodeAddr, r := range resps {
			if r.Error != nil || r.Result == nil {
				summary.addError(nodeAddr, r.Error)
				continue
			}
			var signed relaytypes.SignedSecretsResponseResult
			if err := json.Unmarshal(*r.Result, &signed); err != nil {
				summary.addUndecodable()
				l.Warnw("skipping undecodable secrets response from node", "nodeAddr", nodeAddr, "error", err)
				continue
			}
			out = append(out, signed)
		}
		encoded, err := json.Marshal(relaytypes.SignedSecretsResponseBundle{Responses: out})
		if err != nil {
			return nil, fmt.Errorf("failed to encode secrets response bundle: %w", err)
		}
		summary.setSignedResponse(wrapBundle(req, encoded), len(out))
		return summary, nil
