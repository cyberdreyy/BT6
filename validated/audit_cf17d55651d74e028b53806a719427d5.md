### Title
Rejections from `check_block_against_signer_db_state` never set `reject_reason`, permanently wedging the signer from ever re-considering an otherwise-signable block - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The signer re-validates a block's chainstate consistency (`check_block_against_signer_db_state`) at two points after the initial proposal-time check: when the node's validation comes back OK (`handle_block_validate_ok`) and when the pre-commit weight threshold is reached (`handle_block_pre_commit`). Both re-checks are explicitly documented as *transient*: the conflict they detect ("may sign once conflict is stale") can clear later, and the whole design of section 5 (`conflict_still_blocks`, freshness cutoffs) exists to let a signer reconsider a previously-blocked block once the world changes. However, in both of these re-check paths the code marks the block `LocallyRejected` and stores it **without ever populating `block_info.reject_reason`**, unlike the direct-from-node rejection path (`handle_block_validate_reject`), which does set it.

### Finding Description
`should_reevaluate_reject_reason` decides whether a re-proposal of an already-tracked block is worth re-running through the full evaluation pipeline: [1](#0-0) 

If `block_info.reject_reason` is `None`, the function falls into the `else` branch and returns `false` — i.e. "not re-evaluable" — exactly like the sticky, intentionally non-reevaluable reasons (`DuplicateBlockFound`, `SortitionViewMismatch`, etc.).

But the two chainstate re-check call sites never set `reject_reason` before persisting the rejection:

- Pre-commit threshold re-check: [2](#0-1) 

- Validate-ok re-check: [3](#0-2) 

Compare with the one path that *does* set it, `handle_block_validate_reject` (the node-rejected path): [4](#0-3) 

Because `reject_reason` stays `None` for blocks rejected via `check_block_against_signer_db_state`, a subsequent re-proposal of the *same* block hash is routed by `handle_block_proposal`'s `should_reevaluate_block`/`should_reevaluate_reject_reason` logic into the "not re-evaluable" branch. Since the block's state is `LocallyRejected` (not `PreCommitted`), it does not go through the pre-commit resend path either — it just resends the stale, previously-computed rejection: [5](#0-4) 

The documentation makes explicit that this class of chainstate check is meant to be transient and re-derived per evaluation, precisely so a signature/consideration isn't lost forever when a conflict later resolves: [6](#0-5) [7](#0-6) 

The missing `reject_reason` assignment breaks that intended self-correction: once a signer hits this rejection (which can legitimately be a race — e.g. the local signerdb momentarily disagreeing with a freshly-signed sibling, or the node's tenure tip not yet catching up, both explicitly called out in section 7 of the docs as normal/expected transient states), the exact same block can never be reconsidered by that signer again, even after the conflicting condition clears and the block would otherwise be signable.

### Impact Explanation
This is a liveness wedge on the affected signer for the specific block: the signer is stuck permanently re-sending a rejection for a block it might legitimately be able to sign once conditions change, rather than re-deriving the check as the rest of the design intends. If the miner keeps re-proposing that same block (as they do while awaiting more signatures/timeouts), the signer contributes no further useful vote toward it even though its rejection basis was transient. This fits the "signer wedged into never signing a valid block" class (High) rather than a per-block DoS, since it can only be cured by the miner constructing a materially different block (new hash) for that height/tenure.

### Likelihood Explanation
The two re-check call sites are hit whenever `check_block_against_signer_db_state` fails after node validation succeeded or after crossing the pre-commit threshold — situations the code comments themselves describe as expected/normal (races between validation, threshold-crossing, and other blocks being signed). No majority collusion or privileged access is required; it can be triggered by ordinary tenure-change or reorg-adjacent timing on a single node/signer.

### Recommendation
Populate `block_info.reject_reason` with the reason returned from `check_block_against_signer_db_state` in both `handle_block_pre_commit` and `handle_block_validate_ok` before calling `mark_locally_rejected()`/`insert_block`, mirroring what `handle_block_validate_reject` already does — and ensure the corresponding `RejectReason` variants (`SortitionViewMismatch`, `ConnectivityIssues`) are included in the re-evaluable set in `should_reevaluate_reject_reason` where a stale/transient reason is possible, so a future re-proposal or timeout-driven re-send can re-derive the check.

### Proof of Concept
1. Signer S validates block B via the node (`handle_block_validate_ok`), and at that moment `check_block_against_signer_db_state` fails (e.g. S's signerdb briefly disagrees with a sibling that was just locally signed, or the node's tenure tip hasn't caught up yet — both are explicitly-anticipated transient states per `docs/signer-flows.md` section 7).
2. S calls `mark_locally_rejected()` and `insert_block(&block_info)` without ever writing `block_info.reject_reason` (lines 1946–1959 of `stacks-signer/src/v0/signer.rs`).
3. The transient condition clears (e.g. the sibling's signature goes stale, or the node catches up).
4. The miner re-proposes the identical block B (same `signer_signature_hash`) as tenure proposals normally do while awaiting signatures.
5. `handle_block_proposal` → `should_reevaluate_block` → `should_reevaluate_reject_reason(block_info)` sees `reject_reason == None`, returns `false` ("not re-evaluable"); since state is `LocallyRejected` (not `PreCommitted`), S just re-sends its old rejection instead of re-running `check_block_against_signer_db_state`.
6. S never signs B again for the rest of its lifetime, even though the underlying reason for the rejection is gone.

fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }

Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.
