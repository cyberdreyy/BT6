### Title
Claimed instant-withdraw epoch entries are retained and later counted as recovery collateral - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests` balance but leaves both `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` populated. If the same strategy epoch later defaults while another instant request is pending, the already-paid receipt is treated as prefunded recovery collateral, inflating `defaultRecoveryReserve` and `defaultRecoveryPrice`; the stale user entry can also make the claimant’s default claim underflow and revert. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`requestInstantWithdraw` records the same instant receipt in an aggregate user counter, a per-user/per-epoch ledger, and a per-epoch total. [4](#0-3) 

After the request is funded, `claimInstantWithdrawRequest` burns the receipt and clears only `instantWithdrawsRequests[_user]`; it does not clear either epoch-scoped accounting entry. [5](#0-4) 

During default finalization, `_defaultPrefundedInstantReserve` subtracts only the unfunded `pendingInstantWithdraws` from the full per-epoch total. Because already-claimed receipts remain in that total, they are counted as underlying still held by the strategy. [6](#0-5) [3](#0-2) 

The phantom amount is then added to `defaultRecoveryReserve` and included in the `defaultRecoveryPrice` calculation. [7](#0-6) 

For a user who claimed one receipt and opened another instant receipt in the same epoch, `_claimDefaultedInstantWithdrawRequest` reads the stale cumulative epoch amount and subtracts it from an aggregate that no longer contains the claimed amount, causing an arithmetic underflow under Solidity 0.8.10. [8](#0-7) [9](#0-8) 

### Impact Explanation

The stale entries break the “one receipt, one payout” and recovery-solvency invariants. Already-paid instant principal is counted as available prefunded collateral, so recovery is distributed using an inflated reserve and recovery price. [10](#0-9) 

A pending instant claimant in that epoch can receive more than the intended recovery share, consuming underlying that belongs to other funded or recovery claimants. If insufficient underlying exists, later claims become insolvent and revert. [11](#0-10) 

For a user with a claimed first receipt and a pending second receipt, the stale per-user epoch amount also permanently blocks their defaulted receipt because `instantWithdrawsRequests[_user] -= claimBasis` underflows. [8](#0-7) 

For example, with a claimed 100-unit receipt and a pending 100-unit receipt, `instantWithdrawClaimsByEpoch` remains 200 while `pendingInstantWithdraws` is 100. Finalization adds a nonexistent 100-unit prefunded reserve; a 50-unit external recovery therefore produces a 150-unit recovery reserve instead of the intended 50 units attributable to the pending claim, excluding any active-position basis. [7](#0-6) 

### Likelihood Explanation

The sequence requires an instant-withdraw request to be funded and claimed, another instant request to remain pending, and a borrower default before the strategy epoch advances. Instant requests can be made by ordinary tranche holders, while the default is an honest borrower outcome rather than attacker-controlled privileged behavior. [12](#0-11) [13](#0-12) 

Existing guards do not prevent the issue: `collectInstantWithdrawFunds` only decreases the global pending amount, while `claimInstantWithdrawRequest` clears neither the user epoch entry nor the epoch total. [14](#0-13) [2](#0-1) 

### Recommendation

When a funded instant receipt is claimed, clear its per-user epoch entry and decrement `instantWithdrawClaimsByEpoch[currentEpoch]` by the claimed amount.

Because claims may combine receipts from multiple epochs, retain per-epoch claim weights or iterate the user’s outstanding epoch entries rather than assuming all `instantWithdrawsRequests[_user]` belong to `epochNumber`. The cleanup should:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
uint256 currentEpoch = epochNumber;
uint256 currentEpochAmount = instantWithdrawsRequestsByEpoch[_user][currentEpoch];

if (currentEpochAmount != 0) {
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] = 0;
    instantWithdrawClaimsByEpoch[currentEpoch] -= currentEpochAmount;
}
```

That direct cleanup is sufficient only when the entire aggregate claim belongs to the current epoch; otherwise the cleanup must clear exactly the funded epoch entries being paid. Default finalization should also derive prefunded instant collateral from outstanding, unclaimed receipts rather than cumulative historical request totals.

### Proof of Concept

This Foundry test is intended for the existing `test/foundry/IdleCreditVault.t.sol` fork harness and helpers. It demonstrates the stale-ledger invariant violation and the resulting inflated reserve.

```solidity
// test/foundry/IdleCreditVault.t.sol
function testClaimedInstantReceiptIsCountedAsDefaultReserve() external {
    uint256 instantDelay = cdoEpoch.instantWithdrawDelay();
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 1000, false);

    address firstUser = makeAddr("claimed-instant-user");
    address secondUser = makeAddr("pending-instant-user");

    _depositWithUser(firstUser, 10_000 * ONE_SCALE, true);
    _depositWithUser(secondUser, 10_000 * ONE_SCALE, true);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Epoch 1: first user creates the instant receipt.
    uint256 firstBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(1);

    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds();

    // The funded receipt is paid, but its epoch accounting is not removed.
    vm.prank(firstUser);
    cdoEpoch.claimInstantWithdrawRequest();

    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    uint256 epoch = creditVault.epochNumber();
    assertEq(creditVault.instantWithdrawsRequests(firstUser), 0);
    assertEq(
        creditVault.instantWithdrawsRequestsByEpoch(firstUser, epoch),
        firstBasis,
        "claimed per-user epoch receipt was leaked"
    );
    assertEq(
        creditVault.instantWithdrawClaimsByEpoch(epoch),
        firstBasis,
        "claimed epoch claim basis was leaked"
    );

    // A second request in the same strategy epoch remains pending.
    uint256 secondBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(creditVault.pendingInstantWithdraws(), secondBasis);

    // Borrower fails to provide the second instant funding.
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();
    _checkDefault();

    uint256 activeBasis =
        cdoEpoch.getContractValue() +
        cdoEpoch.expectedEpochInterest() -
        cdoEpoch.pendingWithdrawFees();
    uint256 pendingBasis = creditVault.defaultPendingClaimBasis();
    assertEq(pendingBasis, secondBasis, "default basis unexpectedly includes claimed receipt");

    uint256 recovered = (activeBasis + pendingBasis) / 2;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // The already-paid firstBasis is added as though it were still held by the strategy.
    assertEq(
        creditVault.defaultRecoveryReserve(),
        recovered + firstBasis,
        "claimed receipt was double counted as prefunded reserve"
    );

    uint256 expectedPrice = recovered * 1e18 / (activeBasis + pendingBasis);
    assertEq(
        creditVault.defaultRecoveryPrice(),
        (recovered + firstBasis) * 1e18 / (activeBasis + pendingBasis),
        "recovery price was inflated by claimed collateral"
    );
    assertGt(creditVault.defaultRecoveryPrice(), expectedPrice);
}
```

If the first user also creates the second request, the subsequent `claimInstantWithdrawRequest` reverts because `claimBasis` becomes `firstBasis + secondBasis` while `instantWithdrawsRequests[firstUser]` contains only `secondBasis`. [8](#0-7)

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
