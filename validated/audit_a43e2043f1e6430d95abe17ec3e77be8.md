### Title
pprof debug endpoints under `/v2/debug/pprof` reachable by any authenticated low-privilege API key/session (view/run role) instead of requiring admin - ([File: core/web/router.go])

### Summary
The `/v2/debug/pprof/*` routes are registered via `metricRoutes(authv2)` inside the `authv2` group, which is protected only by `auth.Authenticate` (session or API token) with no role gate such as `auth.RequiresAdminRole`. Any holder of a valid API access-key/secret pair — even a restricted "view" or "run" role account — can reach full pprof introspection endpoints (`cmdline`, `heap`, `goroutine`, `profile`, `trace`, `allocs`, etc.), leaking process memory, goroutine stacks, and process command-line arguments.

### Finding Description
In `core/web/router.go`, the `v2Routes` function builds `authv2` as: [1](#0-0) 
which wraps every route in the group with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)`. This authentication step (`core/web/auth/auth.go`, `AuthenticateByToken`) only checks that the API access key/secret pair belongs to *some* valid user; it does not check the user's `Role`: [2](#0-1) 

Near the end of `v2Routes`, debug/metric routes are attached directly to this authenticated-but-role-agnostic group with a misleading comment implying this is acceptable: [3](#0-2) 

`metricRoutes` itself registers the pprof handlers on a sub-group of whatever `RouterGroup` is passed in, inheriting the parent's middleware (i.e., just `auth.Authenticate`) with **no** `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole` wrapper, unlike nearly every other sensitive `authv2` route (e.g. `/users`, `/transfers`, `/vault/dkg_results/*`, which explicitly use `auth.RequiresAdminRole`/`auth.RequiresEditRole`): [4](#0-3) 

Compare this to the admin-only routes correctly gated in the same function: [5](#0-4) [6](#0-5) 

Because `metricRoutes(authv2)` is called without any role wrapper, a request such as `GET /v2/debug/pprof/heap` or `GET /v2/debug/pprof/cmdline` with valid `X-API-KEY`/`X-API-SECRET` headers belonging to a view-role (or run-role) user passes `AuthenticateByToken` successfully (since it only validates credentials, not role) and directly invokes the raw `net/http/pprof` handlers, which have no additional authorization logic of their own.

### Impact Explanation
This exposes runtime memory (`/debug/pprof/heap`), full goroutine stack dumps (`/debug/pprof/goroutine?debug=2`), CPU/execution traces (`/debug/pprof/profile`, `/debug/pprof/trace`), and process command-line arguments (`/debug/pprof/cmdline`) to any restricted API key/secret holder. Heap and goroutine dumps of a Chainlink node commonly contain in-memory secrets such as decrypted key material, DB credentials, or other node secrets that pass through application memory, and `cmdline` can reveal secrets passed as process flags. This matches the "Critical - server credential/key theft" impact class since it allows a low-privileged credential holder to escalate to full memory/process introspection without needing admin role.

### Likelihood Explanation
The only precondition is possession of any valid API access-key/secret pair (any role, e.g. `view`) or a valid session, which is the standard low-privilege credential Chainlink issues to non-admin users/read-only clients. No additional exploitation steps, race conditions, or special configuration are required — the debug routes are always mounted whenever the node is running with the standard web server, since `metricRoutes` is unconditionally called from `v2Routes`. The attack is trivially repeatable via a single authenticated HTTP GET request.

### Recommendation
Wrap `metricRoutes(authv2)` with `auth.RequiresAdminRole` (mirroring `/debug/vars`'s intent and other admin-only routes), i.e. register each pprof handler through `auth.RequiresAdminRole(...)`, or move `metricRoutes` into a dedicated router group that requires the admin role before the pprof handlers are attached, consistent with how `/users`, `/transfers`, and `/vault/dkg_results/*` are protected.

### Proof of Concept
Go handler-level integration test plan (in `core/web` test package, following existing patterns in `core/web/router_test.go` or equivalent):
1. Set up a test app via the standard `web.SetupTestApp` helper (or equivalent used elsewhere in `core/web/*_test.go`), creating one admin user (to generate an API token) and one "view"-role user.
2. Create an API token for the view-role user via `POST /v2/user/token` while authenticated as that user, obtaining `X-API-KEY`/`X-API-SECRET`.
3. Issue `GET /v2/debug/pprof/heap` and `GET /v2/debug/pprof/cmdline` with the view-role user's `X-API-KEY`/`X-API-SECRET` headers set.
4. Assert the response status is `200 OK` (reproducing the vulnerability) rather than the expected `403 Forbidden` that would result if `auth.RequiresAdminRole` were applied.
5. Repeat with no credentials at all to confirm `401 Unauthorized` (baseline sanity check that at least authentication, but not authorization by role, is enforced).
6. Add a regression assertion that after the fix, the view-role request returns `403 Forbidden` with the "Forbidden" error body produced by `auth.RequiresAdminRole`.

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
