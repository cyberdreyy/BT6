### Title
Stale confirmations from removed multisig members are not purged, allowing requests to execute below the effective live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member()` in the v2 multisig contract only purges confirmations for requests that were *created* by the removed member; it does not scan and strip that member's confirmation entries from other pending requests they had merely *confirmed*. Those stale confirmations remain counted when `confirm()` later checks `confirmations.len() as u32 + 1 >= self.num_confirmations`, so a request can execute using a signature from an account that is no longer a member — the K-of-N binding between "confirmations counted" and "live members" is broken.

### Finding Description
`delete_member()` builds `request_ids` by filtering only requests where `r.member == member`, i.e. requests the removed member originally submitted, and clears `self.confirmations` only for those: [1](#0-0) 

Any *other* pending request (created by a different member, but earlier confirmed by the member now being deleted) keeps the deleted member's entry inside its `HashSet<String>` stored in `self.confirmations`. `confirm()` never re-validates that existing confirmation entries still belong to current `self.members` — it simply counts set size: [2](#0-1) 

`self.members` is checked only for the *currently confirming* caller via `current_member()`: [3](#0-2) 

so a stale confirmation from a former member silently continues to count toward `num_confirmations`.

This is structurally the same class of bug as the Union Finance report: a loop/cleanup path (`updateLocked`, here `delete_member`) that is written for one narrow accounting purpose (purging a member's *own* submitted requests) is reused as the sole mechanism for a broader invariant (all confirmations must come from currently live members), and it silently stops short of the entries that matter for other parties.

### Impact Explanation
This breaks the core multisig guarantee stated in the contract's own README: "K of N multi sig scheme... Any of the access keys or set of specified accounts can confirm, until the required number of confirmation achieved." If a member is removed (e.g., because their key/account is considered compromised or untrusted — the entire reason `DeleteMember` exists), any request they had already confirmed still carries their vote. Once the remaining live members add just enough confirmations to reach `num_confirmations`, the request executes — even though one of the confirmations effectively "counted" belongs to a party that is no longer part of the trust set. This is a multisig request executed with a confirmation set that does not reflect the current, live membership — matching the "Critical: a multisig request executed below threshold" impact category, since the threshold is nominally K live confirmations but here can include a confirmation from an account that has since been un-trusted and removed.

### Likelihood Explanation
This requires no attacker privilege beyond being (or having been) an ordinary multisig member — exactly the kind of unprivileged actor path this analog scan looks for. Any legitimate multisig operation flow naturally produces this state: member confirms a pending request, then is later removed via a normal `DeleteMember` request (a supported, expected governance action, not requiring the foundation or any out-of-scope actor). No malicious deployment, redeploy, or victim key compromise is needed — only the ordinary sequence of "confirm, then remove that member," which is a realistic operational scenario.

### Recommendation
When removing a member in `delete_member()`, iterate over *all* pending requests' confirmation sets (not just the ones the member itself submitted) and remove the member's entry from each. Alternatively, when checking the threshold in `confirm()`, filter the confirmations set against `self.members` before comparing its length to `num_confirmations`, so stale confirmations from removed members never count.

### Proof of Concept
1. Multisig initialized with members `[Alice, Bob, Carol, Dave]`, `num_confirmations = 3`.
2. Alice calls `add_request` to create request `R` (e.g. a `Transfer`). Bob calls `confirm(R)` — confirmations = `{Bob}` (1 of 3).
3. Governance decides to remove Bob (e.g. suspected compromised key) via a separate request, which reaches 3 confirmations and executes `delete_member(Bob)`. Per [4](#0-3) , only requests where `r.member == Bob` (i.e., requests Bob himself created) have their confirmations wiped — `R`, created by Alice, is untouched, so `confirmations[R]` still contains `{Bob}`.
4. `self.members` is now `[Alice, Carol, Dave]`, `num_confirmations` is still 3.
5. Carol calls `confirm(R)` → confirmations become `{Bob, Carol}`, size 2, `2+1 >= 3` is false, so it doesn't execute yet.
6. Dave calls `confirm(R)` → confirmations become `{Bob, Carol, Dave}` before the check; `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates using the pre-insert length (2) so `2+1>=3` is true — `R` executes.
7. `R` executed with confirmations from Dave, Carol, and the *stale* entry for Bob — a removed, no-longer-trusted member — meaning only 2 genuinely live members actually authorized it, one short of the intended 3-of-N live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

                    .try_into()

            }

                account_id: env::predecessor_account_id(),
            }
        };

            Some(member)

            None
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
