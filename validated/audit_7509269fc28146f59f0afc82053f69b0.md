### Title
Missing `return` after failed email-claim extraction in OIDC token exchange allows authenticated session creation with an empty/attacker-influenced email - (File: `core/sessions/oidcauth/oidc.go`)

### Summary
The reported bug class is about code that ignores a boolean/error failure signal (an ERC20 `transfer`/`transferFrom` call that doesn't revert but also doesn't confirm success) and proceeds as though the operation succeeded. The direct analog in this codebase is in `oidcAuthenticator.handleTokenExchange`, the unprivileged, internet-facing OIDC callback handler that turns an authorization code into an authenticated Chainlink Node session. When the type assertion on the `email` claim fails, the code logs the failure and writes an HTTP error response, but — unlike every other failure branch in the same function — it does **not** `return`, so execution falls through and completes session creation as if the extraction had succeeded.

### Finding Description
In `handleTokenExchange`, every prior failure path (`ShouldBindJSON`, state mismatch, OAuth exchange, missing `id_token`, ID-token verification, claim parsing, `ExtractIDClaimValues`) follows the pattern: log error, write HTTP error response, `return`. The email-claim branch breaks this pattern: [1](#0-0) 

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
oi.lggr.Tracef("Received and validated ID claims: %v\n", idClaims)
```

There is no `return` statement after `c.String(...)`, so when `ok` is `false` (the identity provider's ID token/claims payload lacks an `email` string field — which is attacker/IdP-controllable since it comes straight from the OIDC token exchange), `email` silently retains its Go zero value (`""`) and control flow continues into the role-mapping and session-persistence logic: [2](#0-1) 

The role (`role`) is derived independently from `idClaims` via `oi.IDClaimsToUserRole`, which does not depend on `email` being present. The code then:
1. Inserts a new row into `oidc_sessions` with `user_email = ''` and the resolved `role`.
2. Emits an `AuthLoginSuccessNo2FA` audit log entry with `email: ""`.
3. Sets the session cookie (`ginSession.Set(webauth.SessionIDKey, clSession.ID)`) and saves it, handing the caller a valid, authenticated session ID.
4. Finally returns `200 OK` with `{"success": true}` (`c.JSON(http.StatusOK, ...)` at line 273), overriding/duplicating whatever the earlier, un-returned `c.String(http.StatusInternalServerError, ...)` wrote.

This is structurally the same defect class as the reported "unsafe ERC20 usage": a failure/false signal is observed, logged, and even used to attempt an error response, but the code does not halt on it — it treats the failure as if it were success and proceeds to grant a privileged outcome (here, a valid authenticated session instead of a token transfer).

The same missing-`return` pattern also exists a few lines later for the DB insert failure: [3](#0-2) 
If `oi.ds.ExecContext` fails to insert the session row, the code logs and writes an error response but still falls through to set the session cookie and return `200 success`, even though no session row exists in `oidc_sessions` for that session ID.

### Impact Explanation
An unprivileged caller who can influence or control the IdP-issued ID token/claims for the OIDC exchange (e.g., a malicious/compromised IdP, or a permissive/self-hosted OIDC provider misconfiguration that omits `email`) reaches `handleSignIn` → `handleTokenExchange`, and can obtain a valid, cookie-backed Chainlink node session tied to an empty-email "user" with a role determined purely from group claims. Because `AuthorizedUserWithSession` and `FindUser` for local session validation trust the `oidc_sessions` row created here, this results in cross-user session confusion (multiple empty-email "logins" collapse into the same identity) and an authenticated session being granted to a client whose identity verification step explicitly failed — an authentication bypass in the internet-facing OIDC login/session flow.

### Likelihood Explanation
This is reachable via the standard, unauthenticated OIDC callback endpoint (`/oidc/token`-style exchange handled by `handleTokenExchange`) that any client completing the authorization-code flow will hit. It requires only that the ID token's claims map lack an `email` string field — a condition entirely dependent on the IdP's token contents, not on any additional privilege. No source-code changes or internal access are needed to trigger it; it is a straightforward control-flow bug in a widely reachable authentication code path.

### Recommendation
Add `return` immediately after writing the error response in the `!ok` branch for the `email` claim (mirroring every other failure branch in the function), and likewise add `return` after the `ExecContext` failure branch for the session insert, so that a failed email extraction or failed session-row insert never falls through to session-cookie creation and the `200 success` response.

### Proof of Concept
1. Stand up (or compromise) an OIDC provider whose ID token/UserInfo claims omit the `email` field but do include the configured group/role claim (e.g., the configured `EditClaim` group).
2. Complete the standard `handleSignIn` → provider consent → `handleTokenExchange` flow with `code`/`state` valid.
3. In `handleTokenExchange`, `claims["email"].(string)` fails (`ok == false`); the function logs and writes a `500` body but does not return.
4. Execution proceeds through `IDClaimsToUserRole` (succeeds via group claim), inserts an `oidc_sessions` row with `user_email = ''`, sets `ginSession[webauth.SessionIDKey] = clSession.ID`, saves the session, and finally responds `200 {"success": true}`.
5. The client now holds a valid session cookie that `AuthenticateBySession` / `AuthorizedUserWithSession` will accept for subsequent API calls, despite the identity/email verification step having explicitly failed.
