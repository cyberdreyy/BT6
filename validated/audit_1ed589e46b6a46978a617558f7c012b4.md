Confirmed: `LockupContract::new` sets `lockup_information.lockup_amount = env::account_balance()` at init time [1](#0-0)  — this is fixed at deployment and doesn't retroactively grow if more NEAR is deposited afterward, so my "top-up gets released early" theory for later legitimate deposits doesn't hold as I speculated. That weakens the "funds unlocked early" angle of the lockup-factory address-squatting analog.

### Title
Permissionless, front-runnable lockup account creation lets an attacker deploy a wrongly-parameterized lockup at the deterministic address the Foundation intends to use for a given employee - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` computes the lockup account address purely as a deterministic function of `owner_account_id` (`sha256(owner_account_id)[..20]` + factory suffix) and lets any unprivileged caller invoke it with attacker-chosen `vesting_schedule`, `lockup_duration`, `release_duration`, and `whitelist_account_id`, as long as `MIN_ATTACHED_BALANCE` (3.5 NEAR) is attached [2](#0-1) . Since NEAR only allows the parent account (`factory`) to create a given subaccount once, whoever calls `create()` first for a given `owner_account_id` permanently claims that address and its parameters; a legitimate, later call by the Foundation with the intended vesting schedule for the same employee fails and is refunded [3](#0-2) .

### Finding Description
`create()` derives the lockup account id solely from `owner_account_id`, with no nonce, no caller-based salt, and no reservation/permission check tying the call to the Foundation:
```
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
``` [4](#0-3) 

Any account can call `create(owner_account_id, ...)` for any `owner_account_id` value, supplying its own `vesting_schedule`/`lockup_duration`/`release_duration`/`whitelist_account_id`, as long as it pays the ≥3.5 NEAR minimum deposit [5](#0-4) . The `foundation_account_id` embedded in the lockup is only set to the real Foundation if the *caller* chooses to pass a `vesting_schedule`; if the attacker omits it, no foundation control is attached at all [6](#0-5) .

Binding broken: the account address that the protocol/Foundation implicitly treats as "the lockup for `owner_account_id`" (`address(owner_account_id) == deterministic_hash(owner_account_id)`) is not bound to "created with the Foundation-intended parameters." An attacker can satisfy the address equality while supplying arbitrary parameters, because NEAR's `CreateAccount` action is first-come-first-served and irreversible for that exact account id — the legitimate `create()` call from the Foundation for the same `owner_account_id` will simply fail at `Promise::new(lockup_account_id).create_account()` and the deposit is refunded via `on_lockup_create` [3](#0-2) .

### Impact Explanation
This matches the "wrongly-parameterised deployment" class from the analog report: the pre-created account occupies the exact address that all downstream tooling/scripts (e.g. `scripts/deploy_lockup.sh`, which explicitly checks "the new account doesn't exist" before deploying [7](#0-6) ) expects to correspond to the employee's real vesting lockup. Once squatted with attacker-chosen (e.g., no) vesting schedule, weaker/no foundation termination rights, or a malicious `staking_pool_whitelist_account_id`, the Foundation cannot deploy the intended lockup at that address at all — the real vesting/lockup terms for that employee can never be established through the factory for that `owner_account_id`.

However, I could not confirm a path by which additional NEAR later sent to this squatted account would be treated as "already vested" or otherwise released early: `LockupInformation.lockup_amount` is fixed to `env::account_balance()` at `new()`-time and is not recomputed from subsequent balance changes [1](#0-0) , so a naïve "attacker pre-deploys with a fully-vested schedule then the Foundation transfers real funds into it" scenario does not straightforwardly yield an early release of Foundation-transferred funds — this needs to be checked against how the Foundation actually funds the account (whether via `create()`'s deposit, which is fixed at creation, or via a separate transfer after the fact, which the codebase indexed here does not show).

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the attacker to know or guess a specific `owner_account_id` that the Foundation intends to onboard via the factory, and to front-run the Foundation's `create()` call for that exact account before it lands — plausible on a public testnet/mainnet where onboarding announcements or predictable naming conventions leak the target `owner_account_id` in advance, but it is a griefing/denial-of-service outcome (address permanently squatted, transaction refunded, no direct fund theft) rather than a clear fund-diversion or early-release exploit given the `lockup_amount` semantics above.

### Recommendation
- Bind the deterministic lockup address to more than just `owner_account_id` (e.g., include a Foundation-supplied nonce/salt or require the call to be signed/authorized by the Foundation account) so an unprivileged third party cannot pre-claim the address.
- Alternatively, require `create()` to be restricted to (or co-signed by) `foundation_account_id` when a vesting schedule is intended, and have the factory verify `factory.get_foundation_account_id() == predecessor` before allowing `foundation_account_id: Some(...)`-carrying deployments for a given `owner_account_id`.
- Add a check reserving `owner_account_id -> lockup_account_id` mappings (e.g., in a persistent set) so a second `create()` call for an already-used `owner_account_id`, regardless of on-chain account existence, is explicitly rejected with a clear error rather than silently refunding.

### Proof of Concept
1. Attacker learns the Foundation intends to create a vesting lockup for `alice.near` via the factory.
2. Attacker computes `lockup_account_id = hex(sha256("alice.near")[..20]) + "." + factory_account_id` (same formula as `create()`).
3. Attacker calls `factory.create(owner_account_id="alice.near", lockup_duration=0, lockup_timestamp=None, vesting_schedule=None, release_duration=None, whitelist_account_id=None)` with `MIN_ATTACHED_BALANCE` (3.5 NEAR) attached [5](#0-4) .
4. `on_lockup_create` confirms success and the lockup account now exists at the deterministic address with no vesting schedule and no foundation account attached [3](#0-2) .
5. When the Foundation later calls `factory.create(owner_account_id="alice.near", ..., vesting_schedule=Some(real_schedule))`, the `Promise::new(lockup_account_id).create_account()` action fails because the account already exists; `on_lockup_create` detects failure via `is_promise_success()` and refunds the Foundation's deposit [3](#0-2) , leaving `alice.near`'s intended vesting lockup permanently un-deployable at that address.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(

                    .as_bytes(),
            );
            true

                    lockup_account_id, attached_deposit.0, predecessor_account_id

                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
