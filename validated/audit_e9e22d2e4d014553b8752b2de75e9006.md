### Title
Instant-withdraw claims pay out without verifying the borrower actually funded the receipt — unfunded `instantWithdrawsRequests` can drain underlyings belonging to other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the Pillow BLP bug — where `BlpImagePlugin` jumped to file offsets and never verified that the subsequent reads returned data, letting the decoder run on empty data — `IdleCreditVault.claimInstantWithdrawRequest` pays out a user's instant-withdraw receipt without ever verifying that the corresponding funds were actually collected from the borrower via `collectInstantWithdrawFunds`. The claim "decodes" an unfunded receipt as if it were funded: it burns the receipt tokens and calls `_transferFundedClaim`, which only enforces the `defaultRecoveryReserve` isolation check and otherwise happily transfers whatever underlying balance the strategy holds — including underlyings that were collected for *other* users' funded withdraw/instant receipts.

### Finding Description
- `requestInstantWithdraw` burns CDO strategy tokens, mints the user a receipt, and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` [1](#0-0) .
- Funds for pending instant withdrawals only arrive later, when the CDO calls `collectInstantWithdrawFunds` (decrementing `pendingInstantWithdraws` and pulling underlying from the CDO) [2](#0-1) .
- `claimInstantWithdrawRequest` never consults `pendingInstantWithdraws` or `instantWithdrawsRequestsByEpoch` to check that this receipt was funded; it burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim` [3](#0-2) .
- `_transferFundedClaim` only guards the `defaultRecoveryReserve` bucket; when `reserve == 0` it transfers any strategy balance to the claimant [4](#0-3) .
- Meanwhile, funded normal withdraw receipts are delivered to the strategy's own balance by `collectWithdrawFunds` and sit there until claimed [5](#0-4) . There is no accounting separation between "underlying held for user A's funded claim" and "underlying available to pay user B's unfunded instant claim".

Attack sequence (buffer phase, instant mode enabled because APR dropped by more than `instantWithdrawAprDelta`):
1. In a prior stop, `collectWithdrawFunds` funds pending normal receipts; that underlying sits in the strategy awaiting `claimWithdrawRequest`.
2. Attacker (KYC'd tranche holder) calls `cdoEpoch.requestWithdraw(0, tranche)`; since `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, `requestInstantWithdraw` mints them a receipt [6](#0-5) .
3. Before `instantWithdrawDelay` elapses and before anyone calls `getInstantFunds`/`collectInstantWithdrawFunds` (`pendingInstantWithdraws > 0`, i.e., the "read returned empty data"), attacker calls `cdoEpoch.claimInstantWithdrawRequest()` — gated only by `allowInstantWithdraw` [7](#0-6) .
4. `_transferFundedClaim` sends the attacker underlying belonging to the still-unclaimed funded receipts of other users.

### Impact Explanation
Direct theft: the attacker extracts up to `min(instantReceipt, strategyBalance - defaultRecoveryReserve)` underlying that was earmarked for other users' funded claims, who are then permanently frozen out of their payouts (their claims revert on insufficient balance). Broken invariant: one receipt — one payout; a receipt must only be payable once it is funded.

### Likelihood Explanation
Requires (a) a buffer/stopped phase with instant withdrawals enabled (APR dropped > `instantWithdrawAprDelta`), and (b) the strategy holding unfinalized funded underlying (funded `pendingWithdraws` claims or previously collected instant funds not yet claimed) at the moment the attacker's receipt is unfunded. Both conditions occur in normal operation — the test suite itself documents the "no underlyings available" claim window [8](#0-7) , showing that before `getInstantFunds` the receipt exists but is unfunded; the only thing standing between the attacker and the payout is whether the strategy's raw balance happens to cover it.

### Recommendation
In `claimInstantWithdrawRequest`, verify funding before paying — e.g., require `instantWithdrawsRequests[_user]` to be backed by collected funds (track a per-user/per-epoch funded flag or require the relevant epoch's `instantWithdrawClaimsByEpoch` to have been funded via `collectInstantWithdrawFunds` before allowing claims), or at minimum debit `pendingInstantWithdraws` only when the corresponding collection occurred and otherwise revert `NotAllowed`.

```solidity
// Foundry fork PoC sketch (based on test/foundry/IdleCreditVault.t.sol helpers)
function testUnfundedInstantClaimDrainsFundedReceipts() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    idleCDO.depositBB(amount);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // Victim makes a normal withdraw request in the buffer
    address victim = makeAddr('victim');
    _depositWithUser(victim, amount, true); // give victim tranches beforehand in practice
    uint256 victimReq = ...; // victim calls cdoEpoch.requestWithdraw(...)

    // Next epoch runs; borrower funds victim's receipt at stopEpoch -> collectWithdrawFunds
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    // stop with APR lowered > instantWithdrawAprDelta so instant mode is enabled,
    // and funded underlying for victim's receipt now sits in the strategy
    cdoEpoch.stopEpoch(initialProvidedApr / 4, _expectedFundsEndEpoch());
    // victim does NOT claim yet -> strategy holds their funded underlying

    // Attacker requests an instant withdraw in the new buffer
    uint256 attackerReq = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).pendingInstantWithdraws(), 0); // unfunded

    // Do NOT warp past instantWithdrawDelay / do NOT call getInstantFunds.
    // Strategy balance still covers the claim via victim's funded underlying:
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(address(this)) - balPre, attackerReq); // theft succeeds

    // Victim's later claim now reverts on insufficient strategy balance.
}
```

**Caveat:** I verified the missing funded-check in `claimInstantWithdrawRequest`/`_transferFundedClaim` and the absence of any `pendingInstantWithdraws` gate on the claim path, but I could not exhaustively confirm within the available iterations that no additional gating exists in `IdleCDOEpochVariant`'s buffer-phase flow (e.g., in `getInstantFunds` timing or `allowInstantWithdraw` deactivation) that would make the strategy's balance always zero at the vulnerable moment. If such sequencing always drains the strategy balance before unfunded instant receipts exist, this degrades to a non-issue; otherwise the accounting gap above is directly exploitable as described.

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
