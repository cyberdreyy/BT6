### Title
Docker interactive web terminal execs into the build container's real environment and streams it unmasked, bypassing all trace masking — (File: `executors/docker/terminal.go`)

### Summary
The docker executor's `terminalConn.Start` (`executors/docker/terminal.go:101-151`) calls `ContainerExecCreate`/`ContainerExecAttach` against the already-running build container without overriding its environment, so the exec session inherits the full job environment — including `CI_JOB_TOKEN` and masked CI/CD variables — that was set via `Env: jobVars.StringList()` in `createContainerConfig` (`executors/docker/docker.go:1017-1034`). Output from that exec session is proxied raw via `terminalsession.ProxyTerminal` → `terminal.ProxyStream` (`session/terminal/terminal.go:17-36`, `executors/docker/terminal.go:143-150`), which contains no masking, tokensanitizer, or urlsanitizer stage, unlike the job trace path (`common/buildlogger/build_logger.go:213-224`) which explicitly wraps writes through `masker.New`, `tokensanitizer.New`, and `urlsanitizer.New`.

### Finding Description
`e.prepareContainerEnvVariables()` / `createContainerConfig` sets the build container's `Env` to `e.Build.GetAllVariables().StringList()` [1](#0-0)  — this includes masked variables and `CI_JOB_TOKEN`, unfiltered, because Docker containers have no concept of masking; masking is purely a job-trace/log presentation concern implemented in `buildlogger` [2](#0-1) .

When a user opens the interactive web terminal, `TerminalConnect` waits for the running build container and builds a `terminalConn` bound to that same `containerID` [3](#0-2) . `Start` then calls `ContainerExecCreate`/`ContainerExecAttach` with only `TTY`/`Attach*`/`Cmd` set — no `Env` override — so the new exec process inherits the container's full environment, including all job variables [4](#0-3) . The raw TTY bytes are then proxied directly to the websocket client via `terminal.ProxyStream(w, r, dockerTTY, proxy)` inside `terminalsession.ProxyTerminal`, which contains no masking logic whatsoever — it is purely a disconnect/timeout coordination wrapper around a raw I/O proxy function [5](#0-4) [6](#0-5) .

This is fundamentally different from the job trace path, where every write goes through `Logger.wrap`, applying `tokensanitizer`, `urlsanitizer`, and `masker` in sequence before reaching the trace sink [7](#0-6) . The masker itself is proven effective in unit/fuzz tests (`TestMasking`, `build_logger_fuzz.go`) — but that protection is entirely absent from the terminal code path. An attacker with `env`/`printenv` access inside the terminal session can therefore read `CI_JOB_TOKEN` and any masked variable in cleartext through the websocket stream, even though the identical value would be masked as `[MASKED]` if echoed into the job's standard trace.

No existing check intercepts this: there is no allow-list of commands, no output filter, and no environment-scrubbing step in `terminalConn.Start` or in `ProxyTerminal`.

### Impact Explanation
Concrete secret exfiltration: any job with the docker interactive web terminal enabled exposes `CI_JOB_TOKEN` and every masked CI/CD variable in cleartext to whoever holds a valid terminal session token, via a channel (`env`/`printenv` over the exec TTY) that completely bypasses the runner's masking guarantees applied to the primary job trace. This directly violates the stated invariant that "masked values must never appear in cleartext through ANY runner-exposed I/O channel."

### Likelihood Explanation
Preconditions are realistic and match common configurations: masked CI/CD variables set (default for protected variables/tokens) and the docker executor's interactive web terminal feature enabled (an opt-in, documented, user-facing GitLab feature). Any pipeline author who can open a terminal session on their own job (the intended, authorized use case for this feature) can trivially run `env` and read the values — no privilege escalation or additional exploit chaining is needed, making this fully and repeatably reachable by an ordinary authorized user of the feature.

### Recommendation
Either (a) explicitly document that the interactive web terminal is an unfiltered raw shell and secrets should not be assumed protected there (if this is accepted, intended behavior), or (b) if masking parity is desired, scrub the exec environment for masked variable names before `ContainerExecCreate` (e.g., pass an explicit `Env` for the exec session that excludes `CI_JOB_TOKEN` and variables flagged `Masked`), and/or insert a masking writer between `dockerTTY` and `terminal.ProxyStream` analogous to `buildlogger`'s wrap chain.

### Proof of Concept
Extend `executors/docker/terminal_test.go`'s `TestTerminalConn_Start`:
1. Set `ExecutorOptions.Shell.Build` with a masked variable, e.g. `Build.Variables = append(..., spec.Variable{Key: "CI_JOB_TOKEN", Value: "s3cr3t-token", Masked: true})`.
2. Mock `ContainerExecCreate` to capture the `ExecCreateOptions` passed and assert it contains no `Env` override that would strip the masked variable (demonstrating the exec inherits the container's real `Env`, which was built from `GetAllVariables()` including the masked value).
3. Mock `ContainerExecAttach`'s `HijackedResponse.Reader` to emit bytes equivalent to `env`'s output including `CI_JOB_TOKEN=s3cr3t-token`.
4. Read from the client-side websocket connection returned by `websocket.DefaultDialer.Dial` and assert the raw stream contains `s3cr3t-token` (i.e., `assert.Contains(t, string(streamed), "s3cr3t-token")`), demonstrating no masking occurs — proving the invariant violation as opposed to a filtered/masked assertion.

// wrap wraps the underlying writer with "filters". Order here somewhat
// matters, and the order they're instantiated in is the reverse order in which
// writes are processed, e.g. last added filter is the first to process data.
//
// order:
// - sync writer to ensure that multiple writes cannot happen concurrently
// - mask phrases (masker.New)
// - mask sensitive URL parameters (urlsanitizer.New)
// - mask secrets with a prefixed token (tokentanitizer.New)
// - split log lines and add timestamps (timestamper.New)
func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
	if l.timestamping {
		w = timestamper.New(w, timestamper.StreamType(streamType), uint8(streamID), true)
	}

	w = tokensanitizer.New(w, l.maskTokenPrefixes)
	w = urlsanitizer.New(w)
	w = masker.New(w, l.maskPhrases)
	w = internal.NewSync(w)

	return w
}

func (t terminalConn) Start(w http.ResponseWriter, r *http.Request, timeoutCh, disconnectCh chan error) {
	execConfig := client.ExecCreateOptions{
		TTY:          true,
		AttachStdin:  true,
		AttachStderr: true,
		AttachStdout: true,
		Cmd:          t.shell,
	}

	exec, err := t.client.ContainerExecCreate(t.ctx, t.containerID, execConfig)
	if err != nil {
		t.logger.Errorln("Failed to create exec container for terminal:", err)
		http.Error(w, "failed to create exec for build container", http.StatusInternalServerError)
		return
	}

	execStartCfg := client.ExecAttachOptions{TTY: true}

	resp, err := t.client.ContainerExecAttach(t.ctx, exec.ID, execStartCfg)
	if err != nil {
		t.logger.Errorln("Failed to exec attach to container for terminal:", err)
		http.Error(w, "failed to attach tty to build container", http.StatusInternalServerError)
		return
	}

func ProxyTerminal(timeoutCh, disconnectCh, proxyStopCh chan error, proxyFunc func()) {
	disconnected := make(chan bool, 1)
	// terminal exit handler
	go func() {
		// wait for either session timeout or disconnection from the client
		select {
		case err := <-timeoutCh:
			proxyStopCh <- err
		case <-disconnected:
			// forward the disconnection event if there is any waiting receiver
			nonBlockingSend(
				disconnectCh,
				errors.New("finished proxying (client disconnected?)"),
			)
		}
	}()

	proxyFunc()
	disconnected <- true
}
