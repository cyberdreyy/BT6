### Title
APR0 withdraw request permanently reverts `stopEpoch` once APR is set non-zero, freezing all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the Zephyr bug — where a single malformed Connection Request crashes the peripheral and makes it permanently unconnectable — a single valid `requestWithdraw` made while `unscaledApr == 0` puts `IdleCreditVault` into a state where `stopEpoch`/`stopEpochWithDuration` revert unconditionally as soon as the APR is raised above zero, freezing every lender's funds in the epoch.

### Finding Description
`IdleCreditVault.requestWithdraw` routes requests to the APR0 bucket whenever `unscaledApr == 0`, incrementing `apr0TotalPrincipal` via `_requestWithdrawApr0` [1](#0-0) . Later, `prepareStopEpochWithApr0` — called by the CDO inside `stopEpoch` — reverts `NotAllowed` whenever `apr0TotalPrincipal != 0 && unscaledApr != 0` [2](#0-1) .

There is no code path that clears `apr0TotalPrincipal` other than a successful `prepareStopEpochWithApr0` (line 540 sets it to 0 only after the APR check passes). Therefore, once a manager or the CDO has set `unscaledApr` to a non-zero value through `setAprs`/`setAprsWithBuffer` [3](#0-2) , every subsequent `stopEpoch` call reverts while APR remains non-zero — a state-dependency crash exactly mirroring the malformed-request crash: one edge-case input (a withdraw requested at APR 0) makes the core state transition unusable.

Sequence:
1. Pool is at `unscaledApr == 0` (paused lending APR). Attacker — any KYC-passing lender — calls `IdleCDOEpochVariant.requestWithdraw(amount, tranche)` [4](#0-3) , which lands in `_requestWithdrawApr0` and sets `apr0TotalPrincipal > 0` [5](#0-4) .
2. Honest manager raises APR (`setAprs`/`setAprsWithBuffer`) to restart lending, or the CDO's `stopEpoch` path sets the next-epoch scaled APR.
3. Manager calls `stopEpoch` → `prepareStopEpochWithApr0` reverts `NotAllowed` → epoch can never close while APR > 0.

### Impact Explanation
All funds deployed to the borrower plus all pending receipts are frozen: no `stopEpoch`, no interest settlement, no claim of `withdrawsRequests`/`instantWithdrawsRequests` that require an epoch bump (`epochNumber <= lastWithdrawRequest` gate at [6](#0-5) ). The freeze is recoverable only if the honest manager notices and calls `setAprs(0, …)` to restore `unscaledApr == 0` before stopping — so it is a temporary-but-unbounded freeze of user funds gated on privileged intervention, not a permanent loss. If the manager key is unavailable or the APR was set inside the same transaction/epoch logic such that `unscaledApr` cannot be returned to 0 without reverting accounting elsewhere, the freeze becomes permanent for that epoch.

### Likelihood Explanation
Requires only an unprivileged lender action at a specific state (APR == 0). The manager setting a non-zero APR afterward is the normal, expected way to restart a paused pool, so the trap is triggered by honest operator behavior rather than attacker control of privileged calls. No guard warns the manager or blocks `setAprs` while `apr0TotalPrincipal != 0`; the `setApr` max-APR check does not cover this.

### Recommendation
Either block APR changes while `apr0TotalPrincipal != 0` (revert in `setAprs`/`setAprsWithBuffer` when `_unscaledApr != 0 && apr0TotalPrincipal != 0`), or in `prepareStopEpochWithApr0` handle `unscaledApr != 0` gracefully by settling the APR0 bucket at zero interest and clearing `apr0TotalPrincipal` instead of reverting. Add a test covering: request at APR 0 → `setAprs(nonZero)` → `stopEpoch` must not revert.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// setup: vault at unscaledApr == 0, attacker holds tranche tokens
vm.prank(manager);
strategy.setAprs(0, 0);

// attacker: KYC'd lender requests withdraw during APR0 window
vm.prank(attacker);
cdoEpoch.requestWithdraw(attackerTrancheBal, address(AAtranche));
assertGt(strategy.apr0TotalPrincipal(), 0);

// honest manager restarts lending
vm.prank(manager);
strategy.setAprs(5e18, 5e18 * (epochDur + buffer) / epochDur);

// borrower repays, manager attempts to close the epoch
deal(underlying, borrower, owed);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(0, 0); // always reverts while unscaledApr != 0
```

Uncertainty note: I could not fully verify the exact ordering inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` (whether the new APR is applied before `prepareStopEpochWithApr0` in the same call); if `stopEpoch` sets `unscaledApr` itself, the revert occurs on the very first stop attempt after the APR0 request whenever a non-zero APR is passed, strengthening the finding.

    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;

  function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256 _underlyings) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter
    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the
    /// expectedEpochInterest at the startEpoch.
    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest
    interestForOverUnderPerformance += diff;

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);
  }
