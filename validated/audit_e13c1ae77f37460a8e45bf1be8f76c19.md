### Title
Stale per-epoch instant-withdraw aggregates after a normal claim permanently corrupt default-recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
This is the same bug class as the GaugeController report: a user-level counter is cleared on claim while the related aggregate ledger is never updated, leaving a permanently stale total that downstream accounting treats as the sum of its parts.

In `requestInstantWithdraw`, the vault maintains three coupled ledgers: per-user `instantWithdrawsRequests[_user]`, per-user-per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and global-per-epoch `instantWithdrawClaimsByEpoch[currentEpoch]` (plus `pendingInstantWithdraws`). In `claimInstantWithdrawRequest` (lines 380-393) only `instantWithdrawsRequests[_user]` is zeroed and receipt tokens are burned — `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are left permanently non-zero. The only code path that ever decrements them is `_claimDefaultedInstantWithdrawRequest` (lines 842-856). This mirrors the report exactly: `gaugeVotes` updated while `typeVotes` (the aggregate) is not, here the funded-claim path updates the user balance while the epoch aggregates it should roll up into are never reconciled.

### Finding Description
```solidity
// contracts/strategies/idle/IdleCreditVault.sol
function requestInstantWithdraw(uint256 _amount, address _user) external {
    ...
    instantWithdrawsRequests[_user] += _amount;                       // line 366
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;  // line 371
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;            // line 372
    pendingInstantWithdraws += _amount;                               // line 374
}

function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
        _claimDefaultedInstantWithdrawRequest(_user);                 // line 385
    }
    uint256 amount = instantWithdrawsRequests[_user];
    _burn(_user, amount);                                             // line 389
    instantWithdrawsRequests[_user] = 0;                              // line 391
    _transferFundedClaim(_user, amount);                              // line 392
    // instantWithdrawsRequestsByEpoch / instantWithdrawClaimsByEpoch never cleared
}
```

The broken invariant is `Σ_user instantWithdrawsRequestsByEpoch[user][epoch] == instantWithdrawClaimsByEpoch[epoch]` and `instantWithdrawClaimsByEpoch[epoch] == outstanding instant receipt basis for that epoch`. After any successful normal instant claim, both per-epoch aggregates remain inflated by the claimed amount forever — there is no other code path that reduces them outside default finalization.

### Impact Explanation
When `finalizeDefault` / `finalizeDefaultRecovery` computes the default recovery for the defaulted epoch, it uses `instantWithdrawClaimsByEpoch[defaultEpoch]` as the total basis of unfunded default-epoch instant receipts (`defaultInstantWithdrawsFinalized` flag and the comment at lines 100-101 confirm this ledger drives recovery accounting). Receipts that were already funded and claimed normally are still counted, so:

- The haircut (`defaultRecoveryPrice`) and/or reserve sizing (`defaultRecoveryReserve`) is computed against an overstated denominator, diluting real pending claimants or over-reserving underlying that honest recovery claimants never receive.
- `_claimDefaultedInstantWithdrawRequest` additionally does `_burn(_user, claimBasis)` on the stale basis; for an already-claimed user whose receipt tokens were burned, this reverts, which can wedge the `claimInstantWithdrawRequest` path during the post-default claim flow for affected users.

Depending on how the CDO funds `defaultRecoveryReserve`, the net effect is either unclaimed yield permanently locked in the reserve or a reduced recovery ratio for legitimate defaulted-epoch claimants — a quantified loss equal to the stale claimed amount times `defaultRecoveryPrice`.

### Likelihood Explanation
Requires an instant-withdraw claim to complete normally (instant withdrawals must be enabled and the delay elapsed) in an epoch that later defaults and is finalized via `finalizeDefaultRecovery`. Both are ordinary, unprivileged-protocol flows; the attacker surface is just a lender using instant withdrawals, and the stale-aggregate condition is deterministic once a claim succeeds.

### Recommendation
Track the request epoch per user (or iterate it) and clear the per-epoch aggregates in the normal claim path as well:

```solidity
uint256 reqEpoch = /* epoch the user's instant request was recorded in */;
instantWithdrawsRequestsByEpoch[_user][reqEpoch] = 0;
instantWithdrawClaimsByEpoch[reqEpoch] -= amount;
```

Alternatively, store `lastInstantWithdrawRequest[_user] = currentEpoch` at request time (mirroring `lastWithdrawRequest`) so `claimInstantWithdrawRequest` can locate and clear the per-epoch entries.
