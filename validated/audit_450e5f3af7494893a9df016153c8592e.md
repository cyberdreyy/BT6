### Title
Cross-user response confusion via client-controlled message_id collisions in Gateway legacy handler callback map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The Web API capabilities Gateway handler keys pending user callbacks in an in-memory map by `msg.Body.MessageId`, which is derived directly from the caller-supplied JSON-RPC request `ID` field with no per-user/per-connection namespacing. Any unprivileged client that submits a request can choose an arbitrary `MessageId`/request `ID` string. If a second, unrelated client happens to submit (or an attacker deliberately submits) a request with the same ID while a legitimate request is still in flight, the second `savedCallbacks[msg.Body.MessageId]` write silently overwrites the first entry, and the eventual node response gets delivered to the second (attacker-controlled) callback instead of the original caller — an unprivileged-actor cross-user response confusion, structurally analogous to the reported LayerZero bug where a value/response intended for the initiating party was misdirected to the wrong recipient due to using the wrong identity as the routing key.

### Finding Description
`HandleLegacyUserMessage` stores each inbound user request's callback in a shared map keyed solely by the message ID taken from user input: [1](#0-0) 

That message ID originates from the JSON-RPC request `ID` field supplied by the calling client, with no server-side uniqueness enforcement across different callers: [2](#0-1) 

The only validation performed on `MessageId` is a length/null-byte check; there is no assertion of uniqueness or binding to the connecting client/session: [3](#0-2) 

When a node eventually responds, the handler looks up and deletes the callback purely by this same client-chosen key and delivers the raw node response to whichever callback is currently registered under that key: [4](#0-3) 

The identical pattern (map keyed by attacker-influenced `MessageId`, first node response wins, no ownership check) also exists in the generic dummy handler used for the same class of user-triggered requests: [5](#0-4) 

Because the map is shared across all connected/unprivileged clients hitting the same DON's Web API handler, and the key is entirely attacker-controllable, a second party's request can silently displace an in-flight legitimate request's callback registration. This mirrors the reported bug class: a value/response that should route back to the original initiating party (`msg.sender`/the true caller) is instead routed based on an incorrect or attacker-influenced identifier, causing a cross-party misdirection of the outcome.

### Impact Explanation
If exploited, an unprivileged client could receive another user's Web API trigger/target response payload (potentially including data returned from webhook/API calls initiated by another user's workflow), or cause a legitimate user's response to be swallowed/redirected, resulting in cross-user response confusion within the gateway's internet-facing path. Because this is a race/collision-dependent scenario rather than a deterministic bypass, actual exploitation requires guessing or brute-forcing an in-flight message ID window (bounded by `defaultCallbackMaxAgeSec` = 120s) or triggering an intentional collision, which the likelihood section reflects.

### Likelihood Explanation
Medium-Low: exploitation is only possible during the roughly 2-minute window a legitimate request's callback is registered (`defaultCallbackMaxAgeSec`) and requires the attacker to submit a request with a colliding `MessageId`/`ID`. IDs are typically UUIDs generated client-side by the SDK, so successful collision against a specific victim generally requires either weak/predictable ID generation by a client, or an attacker able to observe/replay an ID (e.g., from logs, retried requests, or an SDK that reuses deterministic IDs), rather than being trivially forgeable at will against an arbitrary target.

### Recommendation
Namespace `savedCallbacks` (and the equivalent map in `handler.dummy.go`) by a value that is not solely attacker-supplied — e.g., combine the client-chosen `MessageId` with a server-generated, per-connection or per-request unique identifier (similar to how the Vault handler prefixes responses with `owner + RequestIDSeparator + requestID`, as seen in `core/services/gateway/handlers/vault/handler.go`), and reject/collision-check duplicate in-flight IDs from different senders instead of silently overwriting the map entry.

### Proof of Concept
Conceptual (not verified end-to-end due to index limitations on full request-generation path):
1. Client A sends a legacy Web API trigger request with `message_id`/JSON-RPC `ID = "X"` to a DON handler; the gateway registers `savedCallbacks["X"] = ClientA.callback` in `HandleLegacyUserMessage`.
2. Before a node responds (within the ~120s callback TTL), Client B (unprivileged, unrelated) sends a request that results in the same `message_id = "X"` (e.g., replaying an observed ID or exploiting a predictable client-side ID generator), causing `savedCallbacks["X"] = ClientB.callback` to overwrite Client A's entry.
3. When a DON node responds with `MessageId = "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, now bound to Client B, and delivers Client A's response data to Client B via `savedCb.SendResponse(...)`.

Note: I was not able to fully trace the exact HTTP/JSON-RPC ingress code that assigns/validates the request `ID` before it reaches `HandleJSONRPCUserMessage`/`HandleLegacyUserMessage` due to index size limits; confirming whether IDs are always attacker-supplied strings (vs. server-enforced UUIDs) would require inspecting the full gateway HTTP listener code in a live session.

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}

func (d *dummyHandler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback Callback) error {
	d.mu.Lock()
	d.savedCallbacks[msg.Body.MessageId] = &savedCallback{msg.Body.MessageId, callback}
	don := d.don
	d.mu.Unlock()
	params, err := json.Marshal(msg)
	if err != nil {
		return err
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageId,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	for _, member := range d.donConfig.Members {
		err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
	}
	return err
}

func (d *dummyHandler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	var msg api.Message
	err := json.Unmarshal(*resp.Result, &msg)
	if err != nil {
		return err
	}
	msg.Body.MessageId = resp.ID
	err = msg.Validate()
	if err != nil {
		return err
	}
	if nodeAddr != msg.Body.Sender {
		return fmt.Errorf("node address %s does not match message sender %s", nodeAddr, msg.Body.Sender)
	}
	d.mu.Lock()
	savedCb, found := d.savedCallbacks[msg.Body.MessageId]
	delete(d.savedCallbacks, msg.Body.MessageId)
	d.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(&msg), ErrorCode: api.NoError})
	}
	return nil
}
