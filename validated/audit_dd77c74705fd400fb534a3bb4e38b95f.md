### Title
Instant-withdraw claims keyed to a single epoch index let pre-default unfunded receipts skip the recovery haircut or freeze funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault` tracks instant-withdraw receipt basis per epoch (`instantWithdrawClaimsByEpoch`) but the default-recovery path only reads the entry for the current `epochNumber`. A receipt whose funding is split across an epoch boundary (partially funded in epoch N, still unfunded when the borrower defaults in epoch N+1) is invisible to the default-epoch index — the analog of an out-of-bounds/stale-index read. That receipt is then paid at par through the funded-claim path (escaping the recovery haircut that all other claimants take) or, when the strategy's free balance is insufficient, its claim reverts permanently because `claimInstantWithdrawRequest` always pays the full aggregate amount.

### Finding Description
`defaultPendingClaimBasis` adds only the current-epoch instant basis when `pendingInstantWithdraws != 0`:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
``` [1](#0-0) 

and `_defaultPrefundedInstantReserve` similarly computes the already-held reserve from `instantWithdrawClaimsByEpoch[epochNumber]` minus `pendingInstantWithdraws`, where `pendingInstantWithdraws` is a *global* counter that includes receipts from earlier epochs: [2](#0-1) 

After `finalizeDefaultRecovery`, `_claimDefaultedInstantWithdrawRequest` looks up the user's basis only at `defaultRecoveryEpoch`: [3](#0-2) 

A user whose instant request was recorded in `instantWithdrawsRequestsByEpoch[user][N]` and partially funded (so `pendingInstantWithdraws > 0` carried into epoch N+1) has zero basis at the default epoch. Their entire `instantWithdrawsRequests[user]` balance — funded plus unfunded portions — then falls through to `claimInstantWithdrawRequest`'s par payout: [4](#0-3) 

which pays the full amount 1:1 via `_transferFundedClaim`, guarded only by `balance - reserve >= amount`. Two outcomes, both broken:

- If free balance ≥ the request: the user is paid in full while every other defaulted claimant receives `defaultRecoveryPrice` — a haircut escape that consumes underlyings which `finalizeDefaultRecovery` implicitly attributed to recovery but failed to reserve because `instantWithdrawClaimsByEpoch[currentEpoch]` excluded them.
- If free balance < the request: the claim reverts forever (claims are all-or-nothing; `instantWithdrawsRequests` is never reduced below the full amount), permanently freezing even the genuinely prefunded portion.

The comments acknowledge "partially prefunded instant requests" as a supported state, and `collectInstantWithdrawFunds` reduces `pendingInstantWithdraws` incrementally, so an epoch can stop and a new epoch start with a partially funded instant receipt outstanding.

### Impact Explanation
Broken invariants: "one receipt one payout at the recovery ratio" and loss socialization. An attacker (any unprivileged tranche holder who makes an instant-withdraw request) obtains up to 100% recovery while all other defaulted receipt holders and active LPs receive `defaultRecoveryPrice < RECOVERY_FULL`, directly extracting value from the same finite recovered pool; equivalently, when the reserve guard blocks the par payout, the user's legitimately funded portion is permanently frozen. The loss equals the haircut differential on the receipt amount, bounded only by the size of the instant request the attacker can create (their own deposit).

### Likelihood Explanation
Requires: instant-withdraw enabled (non-programmable deployment), an epoch transition while `pendingInstantWithdraws > 0` (happens whenever `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` under-funds the queue, e.g. insufficient liquidity recalled), and a subsequent borrower default finalized via `finalizeDefaultRecovery`. The sequencing needs only the honest manager's normal `startEpoch`/`stopEpoch` calls plus an exogenous default — no privileged misbehavior. The attacker controls the request timing and size.

### Recommendation
Track pending instant basis globally or per-user across epochs rather than reading only `instantWithdrawClaimsByEpoch[epochNumber]`:

- In `defaultPendingClaimBasis`, include the total outstanding instant claim basis (e.g. maintain an aggregate `instantWithdrawClaims` counter decremented on each claim) instead of the current-epoch entry.
- In `_claimDefaultedInstantWithdrawRequest`, clear *all* of the user's instant receipt basis (sum over epochs, or the aggregate `instantWithdrawsRequests[user]` unfunded portion) at `defaultRecoveryPrice`, not only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`.
- Ensure `_defaultPrefundedInstantReserve` uses the same global basis so already-held instant funding is correctly reserved.

### Proof of Concept
Foundry fork PoC (schematic, modeled on `test/foundry/IdleCreditVault.t.sol` epoch helpers):

```solidity
function testInstantReceiptSkipsDefaultHaircut() external {
  uint256 amount = 100_000 * ONE_SCALE;
  idleCDO.depositAA(amount);
  _startEpochAndCheckPrices(0);

  // Attacker (any KYC'd wallet) requests instant withdraw of 10_000
  address attacker = address(0xBEEF);
  deal(defaultUnderlying, attacker, 10_000 * ONE_SCALE);
  vm.startPrank(attacker);
  underlying.approve(address(idleCDO), type(uint256).max);
  idleCDO.depositAA(10_000 * ONE_SCALE);           // ensure attacker holds tranche tokens
  cdoEpoch.requestWithdraw(0, address(AAtranche)); // routes to requestInstantWithdraw when APR dropped
  vm.stopPrank();

  // Manager partially funds the instant queue, then stops/starts a new epoch
  // (collectInstantWithdrawFunds called with < pendingInstantWithdraws)
  // ... drive epoch N -> N+1 via manager stopEpoch/startEpoch ...

  // Borrower defaults in epoch N+1; finalizeDefaultRecovery sets recoveryPrice < 1e18
  // ... trigger default and finalize ...

  uint256 balBefore = underlying.balanceOf(attacker);
  vm.prank(address(idleCDO));
  // Old-epoch basis is not haircutted: attacker claims the FULL receipt at par
  IdleCreditVault(address(strategy)).claimInstantWithdrawRequest(attacker);
  assertGt(underlying.balanceOf(attacker) - balBefore,
           /* full amount */ 10_000 * ONE_SCALE * cdoEpoch.defaultRecoveryPrice() / 1e18);
}
```

Key assertion: the attacker receives `instantWithdrawsRequests` at 1:1 while `defaultRecoveryPrice` applied to all other claimants is strictly below `RECOVERY_FULL`; or, when free balance is short, the call reverts and even the funded portion is frozen permanently.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
