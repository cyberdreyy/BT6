### Title
Fee-on-transfer repayment triggers false borrower default and repaid funds are skimmed as donations - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external bug class is "pull-based inflows that credit the requested `_amount` instead of the amount actually received, so a fee-on-transfer token silently shrinks what the contract can pay out." In idle-tranches the strongest analog is `IdleCDOEpochVariant._stopEpoch`: it pulls the borrower repayment with a blunt `_transferUnderlyingsFrom(..., _amount)` inside a try/catch that treats *any* revert as a borrower default. With a fee-on-transfer underlying, the pull succeeds but delivers less than requested, the subsequent internal transfers then revert on insufficient balance, the catch arm flags a permanent default, and the honestly repaid funds are later skimmed to `feeReceiver` as "donations" while users only recover via `finalizeDefault`. The analogous `depositDuringEpoch` pull (line 685) uses `_amount` (not the received delta) for minting and NAV, but its forward to the borrower reverts, so it degrades to DoS and is not the primary issue.

### Finding Description
`getFundsFromBorrower` does an unmeasured `safeTransferFrom` of the full requested amount:

```solidity
function getFundsFromBorrower(uint256 _amount) external {
  _checkNotAllowed(msg.sender != address(this));
  _transferUnderlyingsFrom(_borrower(), address(this), _amount);
}
``` [1](#0-0) 

Inside `_stopEpoch` the repayment is wrapped in `try this.getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws)`, and on success the contract immediately pushes funds out again: `collectWithdrawFunds(_pendingWithdraws)`, `_transferFeeUnderlyings(_pendingWithdrawFees)`, optionally `_transferUnderlyings(strategy, _totBorrowed)`, `_transferFeeUnderlyings(_fees)`, and `_strategy.deposit(netInterest)`. The aggregate outflow equals the requested pull, so any transfer-fee haircut makes a later transfer revert, the whole try block rolls back, and the catch arm runs `_handleBorrowerDefault`.

`_handleBorrowerDefault` sets `defaulted = true`, pauses the vault, stops the epoch, and disables all withdrawal requests; `restoreOperations` and `setEpochParams` both revert on `defaulted`, so this state is permanent through normal operations.

```solidity
} catch {
  _handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws);
}
``` [2](#0-1) 

The partially received repayment then sits as raw `token` balance on the CDO. `finalizeDefault` (the only recovery path) first calls `_skimDonatedAssets()`, which sends *all* raw underlyings to `feeReceiver`, and only credits users via the externally supplied `_recoveredAmount`:

```solidity
_skimDonatedAssets();
uint256 defaultBBNav = IdleCreditVault(strategy).finalizeDefaultRecovery(_recoveredAmount, _recoverySource);
``` [3](#0-2) 

By contrast, the normal deposit path is already safe: `_deposit` in `IdleCDOCreditVault` measures the real received delta (`_contractTokenBalance(_token) - _preBal`) before minting, so shares are only minted for tokens actually received. [4](#0-3) 

### Impact Explanation
If the vault's underlying is (or becomes, e.g. via a token upgrade) a fee-on-transfer token, an honest borrower's epoch-end repayment is recorded as a full default: all tranche holders' pending withdrawal receipts become unclaimable, deposits/requests stay disabled, and the repaid cash sitting on the CDO is classified as a donation and redirected to `feeReceiver` during `finalizeDefault`. Users must be made whole a second time from an external recovery source while their actual repayment was diverted — a direct loss of repaid principal/interest plus permanent freezing of the normal claim flow. The broken invariant is "one receipt one payout" / solvency: the contract assumes received == requested, and when that fails, the honest repayment is confiscated rather than credited.

### Likelihood Explanation
Low-to-medium: it requires deploying/operating a credit vault whose underlying charges transfer fees (the vault codebase is token-agnostic, and the original finding was accepted on the same "external requirements" basis). No attacker action is needed — a single honest borrower repayment deterministically bricks the vault's repayment path and diverts the funds to `feeReceiver`. A similar false-default can be induced by any repayment-path revert, but the FoT case is the concrete, quantified trigger. Loss magnitude is the token's transfer-fee percentage of the epoch repayment, plus the operational cost of a forced default on an otherwise solvent pool.

### Recommendation
Measure the actual received amount around every underlying pull rather than assuming `_amount`, e.g. in `getFundsFromBorrower`/`_stopEpoch` record `balanceBefore`/`balanceAfter` and reconcile the subsequent disbursements (withdrawals, fees, strategy deposit) against the received delta — or revert cleanly *before* mutating epoch state, and distinguish "repayment transfer failed" from "post-repayment accounting failed" so an under-delivery does not silently fall into `_handleBorrowerDefault`. Apply the same balance-delta pattern used in `_deposit` to `depositDuringEpoch` and `IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` (which also credits `_underlyings` then pays out the full amount). Alternatively, explicitly document/enforce that fee-on-transfer underlyings are unsupported and revert early.

### Proof of Concept
Foundry fork outline (no code executed; describe steps):

1. Deploy `IdleCDOEpochVariant` + `IdleCreditVault` with a mock ERC20 `token` that burns `f` bps on every `transfer`/`transferFrom` (e.g. 200 bps). KYC a lender via the `keyring` mock, deposit into AA, run `startEpoch()` so all underlyings go to the borrower.
2. After `epochEndDate`, have the (honest) borrower approve and the manager call `stopEpoch(0, interest)` where `interest = expectedEpochInterest + pendingWithdraws` as normal.
3. `getFundsFromBorrower` receives only `amount * (1 - f)`. The subsequent `collectWithdrawFunds`/`_transferFeeUnderlyings`/`deposit` chain exceeds the actual balance → revert → catch → `_handleBorrowerDefault`.
4. Assert: `defaulted == true`, `paused() == true`, `allowAAWithdrawRequest == false`, `claimWithdrawRequest` reverts for pending receipts, `restoreOperations()` reverts.
5. Call `finalizeDefault(R, source)`; assert the repaid balance was sent to `feeReceiver` via `_skimDonatedAssets` and users receive only the externally supplied `R` — demonstrating the repaid funds were diverted.

Uncertainty note: I verified the pull, catch-default, skim, and `restoreOperations`-reverts-on-default logic statically; I did not re-check `IdleCreditVault.collectWithdrawFunds`/`prepareStopEpochWithApr0` internals line-by-line, but the revert path only requires the aggregate outflow to exceed the received balance, which the FoT haircut guarantees.
