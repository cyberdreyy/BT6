The relevant vulnerability is in the node-side StackerDB listener, which tallies signer weights using two separate, inconsistent membership checks for `Accepted` vs `Rejected` responses. This lets a single signer's weight be counted in **both** the approval and rejection tallies if they flip their vote, mirroring the "cache balances before decrement/increment causes a self-transfer to duplicate value" bug class from the report.

### Title
Signer weight double-counted across approval and rejection tallies on vote-flip - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` maintains per-block tallies `total_weight_approved` and `total_weight_rejected` guarded by two *different* data structures: the `Accepted` branch checks `gathered_signatures` (a `BTreeMap<slot_id, signature>`) before adding weight, while the `Rejected` branch checks `responded_signers` (a `HashSet<slot_id>`) before adding weight [1](#0-0) [2](#0-1) . Because these two guards track different keyspaces for the same conceptual "has this signer already been counted" question, a signer who first rejects a block and later accepts the same block gets their weight added to `total_weight_rejected` on the reject, and then *also* added to `total_weight_approved` on the accept, since `gathered_signatures` was never touched by the rejection path.

### Finding Description
`handle_signer_message`'s `Rejected` branch only guards against double counting via `responded_signers.insert(slot_id)` [2](#0-1) . The `Accepted` branch, however, guards against double counting via `!block.gathered_signatures.contains_key(&slot_id)` [3](#0-2) , and only afterwards inserts into `responded_signers` [4](#0-3) .

Sequence that breaks the invariant "a signer's weight counts toward at most one of approve/reject":
1. Signer S (slot `k`, weight `w`) sends `BlockResponse::Rejected` for hash `H`. `responded_signers.insert(k)` succeeds, `total_weight_rejected += w` [2](#0-1) .
2. The same signer S later sends `BlockResponse::Accepted` for the same hash `H` (a legitimate protocol flow — the v0 signer state machine explicitly supports "re-evaluated" transitions, and `LocallyRejected --> LocallyAccepted` is a valid transition per `BlockInfo::check_state` [5](#0-4) ).
3. In the listener, `gathered_signatures.contains_key(&k)` is `false` (this map was never touched by the reject path), so `total_weight_approved += w` runs again [3](#0-2) .

The result: signer S's weight `w` is now present in **both** `total_weight_rejected` and `total_weight_approved` simultaneously — the exact "duplication" pattern from the report, where a cached/gated value is incremented into two places because the equality check used for one side does not reflect state already recorded by the other side.

### Impact Explanation
This breaks the coordinator's core safety invariant that `total_weight_approved` and `total_weight_rejected` are drawn from disjoint signer sets, since `total_weight_approved + total_weight_rejected` can now exceed `total_weight` for the honest signer set. The `SignerCoordinator::wait_for_block_signer_signature` loop (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) uses `total_weight_approved >= self.weight_threshold` directly to decide the block has been approved [6](#0-5) , and the same `total_weight_rejected` value independently gates the "block globally rejected" branch [7](#0-6) . A rejecting signer's weight is thus recounted as an acceptance in the coordinator's own bookkeeping — precisely the "rejection recounted as an accept" impact class. This can cause the miner to believe the acceptance threshold was reached using weight that a signer has explicitly withdrawn/rejected, corrupting the coordinator's view of consensus and triggering premature block assembly/broadcast attempts (and correspondingly can also distort the rejection-timeout step logic, since `rejections` is read from the same poisoned `total_weight_rejected`/`total_weight_approved` pair).

### Likelihood Explanation
Reachable by a single signer (their own key only), with no majority required: the signer just needs to broadcast a `Rejected` response followed later by an `Accepted` response for the same `signer_signature_hash`, which the v0 signer state machine explicitly permits as a legitimate re-evaluation path (`LocallyRejected -> LocallyAccepted`). No cooperation from other signers, no node compromise, and no auth token is needed.

### Recommendation
Use a single, shared per-signer "already counted" gate for both branches (e.g., check/insert into `responded_signers` in the `Accepted` branch too, or track a signer's current vote per block and subtract/adjust the opposing tally when a signer flips), so a signer's weight can only ever contribute to one of `total_weight_approved` / `total_weight_rejected` at a time.

### Proof of Concept
1. Miner proposes block `B` (hash `H`) to reward-cycle signer set including signer `S` (slot `k`, weight `w`).
2. `S` sends `SignerMessage::BlockResponse(BlockResponse::Rejected(...))` for `H`. Listener: `responded_signers = {k}`, `total_weight_rejected = w`.
3. `S`'s local signer state machine re-evaluates (e.g. after a new pre-commit or a re-proposed identical block) and moves to `LocallyAccepted`, sending `SignerMessage::BlockResponse(BlockResponse::Accepted(...))` for the same `H`.
4. Listener processes the `Accepted` message: `gathered_signatures.contains_key(&k)` is `false` (unaffected by step 2), so `total_weight_approved += w` executes, yielding `total_weight_approved = w` and `total_weight_rejected = w` simultaneously for the same signer's weight.
5. If enough other signers behave normally, `total_weight_approved` can cross `weight_threshold` using `w` that logically should be excluded (it was already committed to the rejection side), causing `SignerCoordinator::wait_for_block_signer_signature` to return early believing consensus was reached.
