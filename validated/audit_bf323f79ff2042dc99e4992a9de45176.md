### Title
Stale per-epoch instant-withdraw entries cause underflow revert in `_claimDefaultedInstantWithdrawRequest`, permanently freezing instant claims after default - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` records receipts twice: in the aggregate `instantWithdrawsRequests[_user]` and per-epoch in `instantWithdrawsRequestsByEpoch[_user][epochNumber]`. When a funded instant receipt is claimed via `claimInstantWithdrawRequest`, only the aggregate is cleared — the per-epoch entry is left stale. If the borrower defaults in that same epoch, `_claimDefaultedInstantWithdrawRequest` re-reads the stale per-epoch entry and subtracts it from the now-smaller aggregate, causing an arithmetic underflow that reverts every `claimInstantWithdrawRequest` for that user — and, critically, for the `IdleCDOEpochQueue` contract — forever. This is the on-chain analog of the nanopb bug: the same "submessage" (receipt) is processed twice because it is never freed from the per-epoch ledger.

### Finding Description
- `requestInstantWithdraw` increments both `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` plus `instantWithdrawClaimsByEpoch[currentEpoch]` and `pendingInstantWithdraws`. [1](#0-0) 
- `claimInstantWithdrawRequest` burns and zeroes only `instantWithdrawsRequests[_user]`; `instantWithdrawsRequestsByEpoch[_user][epoch]` is never decremented. [2](#0-1) 
- After default finalization with `defaultInstantWithdrawsFinalized == true` (i.e. `pendingInstantWithdraws != 0`, meaning some same-epoch instant receipt was unfunded), `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest`, which loads `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and executes `instantWithdrawsRequests[_user] -= claimBasis`. [3](#0-2) 
- A same-epoch already-claimed receipt inflates `claimBasis` above the live aggregate, so the subtraction underflows and the whole claim reverts. Because the state is never cleared, the revert is permanent for that epoch.

Attack sequence (single epoch N, instant mode enabled, prefunded variant):
1. Queue/user calls `requestInstantWithdraw(A)` — funded instantly by idle liquidity; calls `claimInstantWithdrawRequest` and receives `A`. Aggregate = 0, but `instantWithdrawsRequestsByEpoch[user][N] = A` remains.
2. Same epoch N: `requestInstantWithdraw(B)` — borrower liquidity is now insufficient, so `pendingInstantWithdraws = B > 0`; aggregate = B.
3. Borrower defaults during epoch N; `finalizeDefault` / `finalizeDefaultRecovery` set `defaultRecoveryEpoch = N`, `defaultInstantWithdrawsFinalized = true`. [4](#0-3) 
4. Any `claimInstantWithdrawRequest` for that user now computes `claimBasis = A + B > B = instantWithdrawsRequests[user]` → underflow → revert, permanently.

Additionally, `defaultPendingClaimBasis` double-counts the stale `A` in `instantWithdrawClaimsByEpoch[epochNumber]` (it is added to the basis but was already paid out as funded cash, not part of the reserve), diluting `defaultRecoveryPrice` for all pending claimers. [5](#0-4) 

### Impact Explanation
Permanent freezing of unclaimed funds. For a direct user, their legitimate pending receipt `B` can never be claimed. For `IdleCDOEpochQueue`, which is the `_user` of record for aggregated instant withdrawals, the revert bricks `processWithdrawalClaims` (which calls `claimInstantWithdrawRequest`), leaving `epochPendingClaims[_epoch]` and `pendingClaims` stuck — this blocks processing of all subsequent epochs for every queued user, not just the attacker. [6](#0-5)  The basis inflation also steals recovery value: the already-paid `A` is haircutted as if still owed, lowering `defaultRecoveryPrice` paid to genuine defaulted claimers.

### Likelihood Explanation
Medium. Requires (a) instant withdrawals enabled, (b) two instant receipts from the same account/queue in the default epoch with the second left unfunded, and (c) a borrower default finalized in that same epoch. The attacker only needs to be an unprivileged user of the instant flow; condition (c) depends on borrower behavior but the vault explicitly supports mid-epoch default handling. No privileged action is needed to arm the stale entry — normal funded instant claims create it.

### Recommendation
In `claimInstantWithdrawRequest`, also clear the per-epoch ledger for the receipt's epoch(s) (e.g. `instantWithdrawsRequestsByEpoch[_user][epoch]` for each open epoch, or track and deduct per-epoch on funded claims), symmetrically to how `_clearWithdrawClaimForEpoch` clears `withdrawsRequestsByEpoch`. Alternatively, have `_claimDefaultedInstantWithdrawRequest` cap `claimBasis` at `instantWithdrawsRequests[_user]` and use the per-epoch map only when it matches the live aggregate.

### Proof of Concept
Foundry fork PoC sketch (prefunded variant, instant enabled via `setInstantWithdrawParams`):

```solidity
function testStaleInstantEpochEntryBlocksDefaultClaim() external {
    // epoch N running; user = the queue contract or an EOA lender
    // 1) funded instant request + claim (pendingInstantWithdraws returns to 0)
    cdoEpoch.requestInstantWithdraw(A, tranche);
    cdoEpoch.claimInstantWithdrawRequest();          // aggregate cleared, by-epoch[N] = A remains

    // 2) second instant request in same epoch N, unfunded
    cdoEpoch.requestInstantWithdraw(B, tranche);     // pendingInstantWithdraws = B

    // 3) borrower defaults; finalizeDefaultRecovery called in epoch N
    _handleBorrowerDefaultAndFinalize();

    // 4) claim reverts permanently: claimBasis = A + B > aggregate = B
    vm.expectRevert(); // arithmetic underflow in instantWithdrawsRequests[_user] -= claimBasis
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Uncertainty note: the exploit assumes `finalizeDefaultRecovery` can run while `epochNumber` still equals the epoch in which the instant receipts were created (i.e., default before `stopEpoch` bumps the epoch). If default handling always increments `epochNumber` first, `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` would miss the stale entry and the bug degrades to basis inflation only; this timing should be confirmed against `_handleBorrowerDefault`/`finalizeDefault` in `IdleCDOEpochVariant` during PoC development.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
