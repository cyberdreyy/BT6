### Title
`kamino_deposit` computes expected collateral from a stale reserve exchange rate before optionally refreshing it, causing legitimate deposits to revert - (File: `programs/marginfi/src/instructions/kamino/deposit.rs`)

### Summary
The TridentRouter finding describes a router that pre-computes an expected liquidity-provision outcome from a stale pool price and then reverts when the actual outcome (computed at execution using the live/updated price) doesn't match, with no tolerance/slippage handling. `marginfi-v2`'s Kamino deposit integration has an analogous pattern: it snapshots the reserve's liquidity-to-collateral conversion rate, optionally refreshes that rate via CPI, executes the deposit against the now-possibly-different rate, and then requires the actual outcome to match the pre-refresh expectation within a tolerance of only 1 native token unit.

### Finding Description
In `kamino_deposit`, the expected collateral amount is computed from `integration_acc_1` (the Kamino reserve account) **before** the optional reserve refresh: [1](#0-0) 

```
let expected_collateral_amount = ctx.accounts.integration_acc_1.load()?.liquidity_to_collateral(amount)?;
if refresh_reserve {
    ctx.accounts.cpi_refresh_reserve()?;
}
```

If the caller passes `refresh_reserve = true` (which is the documented/recommended path to ensure oracle/interest freshness before risk-sensitive operations), the CPI to Kamino's `refresh_reserves_batch` updates the reserve's internal liquidity/collateral exchange rate to account for accrued interest. The actual deposit is then executed against this newly refreshed rate: [2](#0-1) 

The resulting `obligation_collateral_change` (computed from the real, post-refresh Kamino CPI outcome) is then checked against the `expected_collateral_amount` computed from the **pre-refresh** rate, using `assert_within_one_token`, which allows a tolerance of exactly 1 native token unit: [3](#0-2) 

For any reserve where interest has accrued since the reserve's `last_update` slot (i.e. the reserve was stale, which is precisely the scenario `refresh_reserve=true` exists to handle), the collateral:liquidity exchange rate shifts. For deposits of meaningful size, or reserves with any non-trivial accrued interest, the shift in collateral output can easily exceed 1 native unit, causing `assert_within_one_token` to fail and the whole deposit transaction to revert with `MarginfiError::KaminoDepositFailed`.

This is the same bug class as the TridentRouter issue: an amount expectation computed from one price/rate snapshot is rigidly checked against the actual outcome computed from a different (updated) price/rate snapshot, with no user-supplied slippage tolerance and only a hardcoded razor-thin tolerance, causing otherwise valid transactions to unexpectedly fail.

### Impact Explanation
This is a liveness/availability bug rather than a fund-loss bug: no funds are misappropriated, but legitimate user deposits into Kamino-wrapped banks will revert whenever the caller sets `refresh_reserve = true` and the reserve has accrued more than a negligible (~1 unit) amount of interest since its last refresh. Because refreshing the reserve before risk-sensitive operations is the documented safe practice (analogous to `updateRate` in other integrations), this makes normal, "correctly used" deposit flows unreliable, particularly for reserves with high-interest-rate or long staleness windows, and for larger deposit amounts where 1-unit tolerance is trivially exceeded by rate-shift-derived rounding.

### Likelihood Explanation
Likelihood is moderate-to-high for any bank/reserve pair that accrues meaningful interest between refreshes, since `refresh_reserve=true` is the intended flag for ensuring freshness and integrators are expected to use it. The bug reproduces deterministically (not merely under adversarial front-running) any time the reserve is stale enough that its rate shift, when applied to the deposit amount, exceeds 1 native unit — this scales with deposit size, so larger deposits are more likely to trigger the revert.

### Recommendation
Compute `expected_collateral_amount` **after** the optional `cpi_refresh_reserve()` call (i.e., reload `integration_acc_1` post-refresh) so the expectation and the actual CPI outcome are computed against the same rate. Alternatively/additionally, expose a caller-supplied `min_collateral_out` (or `max_slippage_bps`) parameter so callers can explicitly bound acceptable deviation instead of relying on a fixed 1-unit tolerance, consistent with how `deposit_with_min_amount_out` is exposed by the JupLend integration's IDL.

#[inline]
pub fn assert_within_one_token(actual: u64, expected: u64, err: MarginfiError) -> MarginfiResult {
    // Should be sufficient tolerance for 99.999999% of cases
    const TOKEN_AMOUNT_TOLERANCE: u64 = 1;

    let diff = actual.abs_diff(expected);
    if diff > TOKEN_AMOUNT_TOLERANCE {
        msg!(
            "Amount mismatch → actual: {}, expected: {}, diff: {}",
            actual,
            expected,
            diff
        );
        return Err(err.into());
    }
    Ok(())
