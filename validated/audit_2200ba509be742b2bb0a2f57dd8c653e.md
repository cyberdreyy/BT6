### Title
Stale `lastWithdrawRequest` overwrites the loss-adjusted epoch marker, letting a user claim a haircutted receipt at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2022-0847 (stale, improperly initialized per-struct flags letting a write hit read-only state), `IdleCreditVault` keys the loss-adjusted claim path to a single mutable marker, `lastWithdrawRequest[_user]`, which `requestWithdraw` unconditionally overwrites with `currentEpoch`. A user holding a loss-adjusted receipt for epoch N (priced by `lossRecoveryPriceByEpoch[N]`) can make a tiny second `requestWithdraw` in epoch N+1, moving the marker so `_claimLossAdjustedWithdrawRequest` misses their epoch-N receipt, which is then paid at par by `_claimFundedWithdrawRequest` instead of at the haircut price.

### Finding Description
In `requestWithdraw`, `lastWithdrawRequest[_user] = currentEpoch` is set for every request (line 282). `_claimLossAdjustedWithdrawRequest` only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the *latest* epoch only (lines 789-792). `_clearWithdrawClaimForEpoch` clears `withdrawsRequestsByEpoch` per epoch but leaves the aggregate `withdrawsRequests[_user]` containing every epoch's basis (lines 815-819), and `_claimFundedWithdrawRequest` pays the whole aggregate `normalAmount = withdrawsRequests[_user]` at par once `epochNumber > lastWithdrawRequest[_user]` (lines 326-343). There is no per-epoch iteration over `lossRecoveryPriceByEpoch`, so any loss-epoch receipt not reachable via the current marker is silently reclassified as fully funded.

### Impact Explanation
Broken invariant: loss waterfall / one-receipt-correct-payout. After `stopEpochWithDuration(_lossAmount)` sets `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL`, the borrower funds only the haircutted total. A user who re-requests in epoch N+1 and waits for epoch N+2 claims `claimBasis` at 100% rather than at `lossRecoveryPrice`, over-withdrawing from the strategy's funded balance. The excess is paid from underlyings belonging to other claimants/depositors (direct theft / insolvency of the funded bucket); `_transferFundedClaim`'s reserve guard only protects `defaultRecoveryReserve`, not this bucket. Quantified loss: `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL`.

### Likelihood Explanation
Requires only an unprivileged tranche holder (KYC-passing lender) acting in normal epoch phases around honest manager calls: request in epoch N, manager stops with a partial loss, attacker submits a dust `requestWithdraw` in the next buffer, waits one epoch, calls `claimWithdrawRequest` via the CDO. No privileged role, default, or timing race is needed.

### Recommendation
Track loss-adjusted receipts per epoch instead of via the single `lastWithdrawRequest` marker: iterate `lossRecoveryPriceByEpoch` over the user's request epochs (or store a per-user set of loss epochs), and make `_claimFundedWithdrawRequest` exclude any epoch basis for which `lossRecoveryPriceByEpoch[epoch] != 0`. Alternatively, in `requestWithdraw`, refuse or settle any outstanding receipt from an epoch with a nonzero `lossRecoveryPriceByEpoch` before overwriting `lastWithdrawRequest[_user]`.
