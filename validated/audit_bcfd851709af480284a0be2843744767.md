### Title
Node-side weight double-counting lets a re-evaluating signer's weight land in both the rejection and acceptance tallies for the same block — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies `BlockResponse::Accepted` and `BlockResponse::Rejected` messages from signers into two independent counters, `total_weight_approved` and `total_weight_rejected`, that the mining coordinator treats as mutually exclusive shares of `total_weight` (a signer's weight should count toward exactly one side). The two handlers guard against double-counting using two *different* sets — `gathered_signatures` for the accept path and `responded_signers` for the reject path — and these sets are not kept in sync. A signer that first rejects, then legitimately re-evaluates and accepts the same block (a flow the protocol explicitly supports, see `signer_can_accept_rejected_block` / `should_reevaluate_reject_reason`) has its weight added to `total_weight_rejected` and *also* later added to `total_weight_approved`, without the stale rejection ever being removed.

### Finding Description
In the Accepted branch: [1](#0-0) 
weight is added to `total_weight_approved` guarded only by `!block.gathered_signatures.contains_key(&slot_id)`; `responded_signers.insert(slot_id)` is then called unconditionally, *after* the accept weight has already been added.

In the Rejected branch: [2](#0-1) 
weight is added to `total_weight_rejected` guarded by `block.responded_signers.insert(slot_id)` (true only the first time this slot is seen at all, regardless of vote kind).

Because these are two distinct sets:
- Reject → Accept (same slot, same block): reject path sets `responded_signers`; when the later Accept arrives, the guard checked is `gathered_signatures.contains_key(slot_id)`, which is still false (that map is only populated by the accept path itself), so the weight is added to `total_weight_approved` a second time — on top of the weight already sitting in `total_weight_rejected`, which is never decremented or cleared.
- Accept → Reject is correctly blocked, since `responded_signers` already contains the slot when the reject arrives, so the asymmetry only manifests in one direction.

This breaks the implicit accounting invariant the coordinator relies on — that a signer's weight is exclusively credited to one side of the vote for a given block — analogous to two accounting pools drawing from the same underlying budget without deducting what the other already claimed.

The coordinator consumes these two counters as if they partition `total_weight`: [3](#0-2) 
Reject-crossing-30%-blocking-minority is checked first and returns `NakamotoNodeError::SignersRejected`, aborting the tenure/block and permanently or temporarily excluding txids the rejecting minority flagged, using `block_status.total_weight_rejected`.

### Impact Explanation
Because stale rejection weight from a signer who has since switched to acceptance is never cleared, `total_weight_rejected` can remain artificially inflated for the lifetime of that block's tracking entry. If enough of this stale weight plus genuinely-still-rejecting signers crosses the blocking-minority threshold, the coordinator declares the block globally rejected (`SignersRejected`) and can permanently ban transactions (`permanently_excluded_txids`) — even though the true, current state of signer opinion (including a valid, verified signature from the "flipped" signer) may already or would soon legitimately reach the 70% acceptance threshold. This is a liveness wedge on the miner/coordinator: a signer set that has, in aggregate, actually reached consensus to sign can be denied that outcome because of leftover weight from an outdated rejection that the bookkeeping never retracts. It also generally corrupts the approve/reject totals reported and logged, undermining any consumer (miner logic, monitoring) that assumes `total_weight_approved + total_weight_rejected` reflects distinct, current per-signer votes.

### Likelihood Explanation
This requires only a single signer naturally exercising a protocol-supported behavior — rejecting a block proposal and later switching to acceptance after a re-proposal or re-evaluation (explicitly tested by `signer_can_accept_rejected_block`) — observed by the miner's `StackerDBListener` over ordinary StackerDB gossip. No majority collusion, no forged signatures, and no out-of-scope transport exploitation is needed; it is a bookkeeping defect triggered by legitimate single-signer message ordering.

### Recommendation
Use a single per-slot "current vote" map (or track vote kind alongside weight) instead of two independently-guarded sets (`gathered_signatures` vs `responded_signers`). When a slot's vote changes from Rejected to Accepted (or vice versa), subtract the previously counted weight from the old bucket before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` always remain a true, mutually-exclusive partition of at most `total_weight`.

### Proof of Concept
1. Miner proposes block `B`; `StackerDBListener` creates a `BlockInfo`-like tracking entry with `total_weight_approved = 0`, `total_weight_rejected = 0`, empty `gathered_signatures` and `responded_signers`.
2. Signer `S` (weight `w`) initially rejects `B` (e.g. due to a transient/test condition). `stackerdb_listener.rs:515` fires: `responded_signers.insert(slot_S)` succeeds → `total_weight_rejected += w`.
3. `B` is re-proposed/re-validated and deemed legitimate (matching `signer_can_accept_rejected_block`); `S` now sends `BlockResponse::Accepted(B)`.
4. In the Accepted handler, `block.gathered_signatures.contains_key(&slot_S)` is `false` (never populated by the reject path) so the guard at line 443 passes → `total_weight_approved += w` a second time for the same signer, while `total_weight_rejected` still holds `w` from step 2, uncorrected.
5. `total_weight_approved + total_weight_rejected` now exceeds what distinct signer weights actually justify; depending on other signers' votes, this can either falsely trip `SignersRejected` in `signer_coordinator.rs` (killing an otherwise-signable block and excluding txids) or falsely inflate the reported approval percentage, both a divergence from the true, current per-signer tally.
