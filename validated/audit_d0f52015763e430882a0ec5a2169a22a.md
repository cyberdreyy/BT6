## Analysis

The reported bug class — attacker observes/guesses a caller-chosen unique identifier and preemptively claims it in a globally-shared map before the legitimate owner does, causing a permanent “ID already exists” rejection for the legitimate request (DoS) — has a direct analog in the Chainlink gateway-side capability handlers, which key pending-request state by a client-supplied `Request.ID` in a single global map shared by all unprivileged callers of the gateway.

### Title
Unprivileged client can DoS another user's gateway request by squatting on its `Request.ID` before the legitimate request arrives - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
The Vault gateway handler's `newActiveRequest` and the Confidential Relay gateway handler's `newActiveRequest` both register in-flight requests in a single process-wide `activeRequests map[string]*activeRequest` keyed purely by the client-controlled JSON-RPC `Request.ID` string. Any unprivileged client connected to the gateway can submit a request using the same `ID` value that another legitimate, not-yet-arrived request will use. Because insertion is a simple existence check with no per-caller/per-owner namespacing at that point, whichever request reaches `newActiveRequest` first wins the slot and the second one is unconditionally rejected with `"request ID already exists"`.

### Finding Description

This mirrors the Cauldron finding precisely: a user-chosen identifier (`vaultID` ↔ `Request.ID`) is used as the sole key to a shared registry (`vaults` mapping ↔ `activeRequests` map), and whichever party's transaction/request reaches the registry first claims the slot, permanently blocking the legitimate owner's identically-IDed operation for the lifetime of that slot (until it expires/times out, per `removeExpiredRequests`).

### Impact Explanation
If an unprivileged attacker can predict or observe the `Request.ID` a victim is about to use (e.g., deterministic/sequential IDs used by a workflow SDK, retried requests, or IDs derived from public/observable data such as a workflow execution ID), the attacker can pre-register that ID with a garbage/no-op request. The victim's genuine request is then hard-rejected by `newActiveRequest` with "request ID already exists" and never reaches the DON nodes, denying that specific operation (e.g., a `secrets_create`/`secrets_update`/`secrets_delete` call or confidential-relay call) until the squatted entry expires. This is a targeted denial-of-service against specific, callable gateway operations without needing to compromise authentication or bypass the allowlist.

### Likelihood Explanation
Likelihood depends entirely on whether `Request.ID` values used by legitimate clients are unpredictable/high-entropy (e.g., random UUIDs) at the call sites that construct these requests. Where clients generate IDs randomly per call, likelihood is low. Where a client reuses a fixed, predictable, or low-entropy ID (e.g., retries with the same ID, or IDs correlated to public data), likelihood rises significantly, matching the low-likelihood/high-impact medium-severity profile of the original report. No code in `HandleJSONRPCUserMessage` or `newActiveRequest` enforces ID unpredictability, per-owner ID namespacing, or rate limiting the number of distinct `activeRequests` entries an unauthorized/unauthenticated caller can occupy before authorization succeeds (in `vault/handler.go`, `newActiveRequest` is called only after `ProcessRequest`/authorization succeeds for secrets methods, but the public-key-get code path and the confidential-relay handler call it with no authorization gate at all).

### Recommendation
- Do not use the raw, client-supplied `Request.ID` as the sole key into a globally shared `activeRequests` map. Namespace the map key by authenticated/authorized identity (e.g., the owner-prefixed ID scheme already used internally, such as `owner + RequestIDSeparator + req.ID` seen in `sendSuccessResponse`/`errorResponse`) *before* the collision check, not only for downstream forwarding.
- Perform the collision check after authorization (as already partially done for secrets methods) so that unauthenticated callers cannot occupy slots at all, and ensure the collision key itself binds to the authorized owner so two different owners can never collide on the same raw ID.
- Consider rejecting or aging out squatted entries faster, and emitting metrics on `newActiveRequest` failures per caller to detect id-squatting DoS attempts.

### Proof of Concept
1. Attacker (unprivileged workflow owner) predicts or learns the `Request.ID` value `X` that a victim's client is about to use for a `secrets_create`/confidential-relay call to the gateway (e.g., because the SDK derives it deterministically or the attacker observes it via a shared/predictable naming scheme).
2. Attacker races the gateway by sending any authorized-looking request (for `vault/handler.go`, the attacker must itself be authorized for *some* request, but can use their own owner/allowlist entry and a different method that still exercises `newActiveRequest` with `ID = X`; for `confidentialrelay/handler.go`, no authorization is required at all) with `ID = X`.
3. `newActiveRequest` inserts `X` into `h.activeRequests` and returns success to the attacker.
4. The victim's genuine request with `ID = X` arrives shortly after; `newActiveRequest` finds `h.activeRequests[X] != nil` and returns `"request ID already exists: X"`, and `HandleJSONRPCUserMessage` propagates this error, so the victim's request is never forwarded to the DON — reproducing the same "request ID already claimed by attacker" denial-of-service pattern described in the Cauldron `vaultID` report.

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}
