### Title
Confirmations from a deleted multisig member remain counted toward `num_confirmations`, allowing requests to execute with fewer live-member approvals than the configured threshold - (File: multisig2/src/lib.rs)

### Summary
This is the same "stale state used for a threshold/accounting decision" bug class as H-14 (borrowing fee not recalculated after margin update lets a trader settle against an outdated leverage figure). Here, `MultiSigContract::confirm` in `multisig2/src/lib.rs` counts confirmations stored in `self.confirmations` toward `self.num_confirmations` without verifying that every counted confirmer is still a current member of `self.members`. `delete_member` only purges confirmations/requests that a departing member originally *submitted*, not confirmations that member cast on other members' requests, so a removed member's vote silently continues to count toward the execution threshold.

### Finding Description
`confirm()` reads the stored confirmation set for a request and compares `confirmations.len() + 1` directly against `self.num_confirmations`: [1](#0-0) 

Nothing in this function re-validates that the public keys/accounts already present in `confirmations` are still members of `self.members` at execution time — it only checks that the *newly confirming* caller (`self.current_member()`) is currently valid.

The only place that cleans up confirmations tied to a member removal is `delete_member`: [2](#0-1) 

This filters `self.requests` by `r.member == member` — i.e. it only removes requests (and their confirmation sets) that the *departing member itself submitted* (`MultiSigRequestWithSigner.member` records the original requester, set in `add_request`): [3](#0-2) 

If the departing member instead confirmed a request that a *different, still-valid* member submitted, that confirmation entry is never removed from `self.confirmations`. The equality this breaks is:

`confirmations counted toward num_confirmations == confirmations cast by accounts that are members of self.members at execution time`

After a member is deleted, the left-hand side can exceed the right-hand side, because stale confirmations from ex-members remain in the set.

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold." Concretely: with `num_confirmations = 3` and members {A, B, C, D}, suppose A submits a sensitive request (e.g. `Transfer`, `AddKey`, `FunctionCall`) and B, C confirm it (2/3, request stays pending). Before the third confirmation arrives, the multisig executes a separate governance request to remove C (e.g. because C's key was compromised or C left the organization) via `DeleteMember`. `delete_member` does not touch the pending request from A because `r.member == A ≠ C`, so C's stale confirmation remains. Now only D — a single live member — needs to confirm, and the request executes with only A (submitter, uncounted directly but effectively the originator) + D + a stale C-confirmation, i.e. only 2 genuinely live confirmations instead of the required 3. Funds can move, keys can be added/removed, or arbitrary function calls can execute on behalf of the multisig with an effective threshold lower than configured, undermining the very custody guarantee (`k`-of-`n` approval) that this contract exists to enforce.

### Likelihood Explanation
This requires no privileged access beyond being (or having been) a legitimate multisig member at some point, or simply timing: any of the existing members can confirm a pending request, and any governance action that removes a member (a normal, expected operational event — e.g. offboarding, key rotation, compromised-key response) triggers the flaw automatically without any special malicious action needed on the deletion transaction itself. The scenario is a foreseeable operational sequence (pending unconfirmed requests + membership change), not a contrived edge case, making it reasonably likely to occur in production multisig usage over the contract's lifetime.

### Recommendation
When removing a member, iterate over all outstanding requests (not just ones the departing member submitted) and strip that member's key/account from every stored confirmation set, or alternatively validate at `confirm()`/execution time that every principal recorded in `confirmations` is still present in `self.members`, only counting live confirmations toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. As A: `add_request_and_confirm` a sensitive `Transfer`/`FunctionCall` request `R` (receiver `current_account_id`, or any receiver) — R now has 1 confirmation (A).
3. As B: `confirm(R)` — R now has 2 confirmations (A, B); execution not yet triggered.
4. As C: `confirm(R)` — R now has 3 confirmations… *(to keep R pending for this PoC, instead have C confirm a different placeholder request, or assume `num_confirmations = 4` and members `[A,B,C,D,E]` so R sits at 3/4)*. Concretely: use `num_confirmations = 4`, members `[A,B,C,D,E]`; A submits+confirms R, B confirms R, C confirms R → 3/4 confirmations stored for R, `self.confirmations[R] = {A,B,C}`.
5. Submit and confirm (via required threshold using D and E, or via a separate flow) a `DeleteMember { member: C }` request that executes and removes C from `self.members`. Verify via `delete_member` code path that `self.requests` filter only matches requests where `r.member == C` (i.e., requests C itself submitted) — R was submitted by A, so it is untouched and `self.confirmations[R]` still contains C's entry.
6. As D: `confirm(R)`. `confirm()` computes `confirmations.len() as u32 + 1 = 3 + 1 = 4 >= num_confirmations (4)`, so `execute_request(R)` runs — even though only A, B, and D are genuinely live members who approved (C's approval is stale/invalid), satisfying the threshold with effectively 3 live confirmations instead of the required 4.

This demonstrates that `self.confirmations` is never reconciled against the live `self.members` set outside of the narrow "requests submitted by the removed member" case, allowing execution below the configured live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
