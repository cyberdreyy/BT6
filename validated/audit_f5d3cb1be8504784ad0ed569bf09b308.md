### Title
Panics via `.expect()`/`.unwrap()` in `generated::ConfirmedTransaction`/`generated::Transaction` → `TransactionWithStatusMeta` conversion cause validator process crash on read - ([File: storage-proto/src/convert.rs])

### Summary
`generated::ConfirmedBlock` bytes that decode successfully via `prost::Message::decode` (a syntactically valid protobuf with an unset optional `transaction` field, or with a `signatures` entry whose byte length is not exactly 64) pass `T::decode` without error, but the subsequent `TryFrom<generated::ConfirmedTransaction> for TransactionWithStatusMeta` and `From<generated::Transaction> for VersionedTransaction` conversions call `.expect(...)` and `.unwrap()` respectively, which panic instead of returning `Err`.

### Finding Description
The call path `get_confirmed_transaction` → `get_confirmed_block(slot)` → `bigtable::CellData::Protobuf(block).try_into()` invokes `TryFrom<generated::ConfirmedBlock> for ConfirmedBlock`, which maps each `generated::ConfirmedTransaction` through `tx.try_into()`: [1](#0-0) 

That inner conversion is: [2](#0-1) 

`value.transaction` is `Option<generated::Transaction>` in the prost message; a protobuf encoder can legally omit this optional field, causing `decode()` to succeed with `transaction: None`. The code then calls `.expect("transaction is required")`, which panics rather than propagating a `DecodeError`.

Similarly, once a `generated::Transaction` is present, converting it to `VersionedTransaction` does: [3](#0-2) 

Here `Signature::try_from` is applied to each raw signature byte vector; if any encoded signature is not exactly 64 bytes (which is trivially producible by an attacker constructing/uploading a `generated::Transaction` with a malformed `signatures` field, or corrupting stored bytes prior to a later read), the `Result::collect().unwrap()` panics.

The outer call site in `storage-bigtable/src/lib.rs` only guards the top-level `Result` from `try_into()`: [4](#0-3) 

`.map_err()` only converts an `Err` value into `Error::ObjectCorrupt`; it does nothing to catch a panic unwinding from inside `try_into()`. Because `deserialize_protobuf_or_bincode_cell_data` only validates that `T::decode` succeeds (i.e., the bytes are well-formed protobuf), it never validates domain invariants (required sub-messages present, signature byte lengths correct) before invoking these `.expect()`/`.unwrap()` calls, so a decodable-but-semantically-invalid `ConfirmedBlock` reaches the panicking conversion code.

### Impact Explanation
A single `getTransaction` or `getBlock` RPC call that resolves to a bigtable-stored block containing a `generated::ConfirmedTransaction` with a missing `transaction` field, or a `generated::Transaction` with a malformed-length signature, will panic the calling thread inside the RPC/ledger-tool process instead of returning a JSON-RPC error. This matches the "decoder panic and misreporting" / single-call DoS category in scope. The panic occurs during a normal read RPC path (`get_transaction` → `bigtable_ledger_storage.get_confirmed_transaction`), which corresponds to [5](#0-4)  for RPC entrypoint, then [6](#0-5)  for the bigtable read.

### Likelihood Explanation
This requires attacker-controlled or corrupted bytes to already exist in the BigTable `blocks` cell for a slot that a later `getTransaction`/`getBlock` call will read — consistent with the stated precondition ("attacker-influenced upload path or corrupted cell content preserved from earlier upload"). Given that precondition, triggering the panic requires only a single subsequent read-only RPC call, satisfying the single-call-per-`CLUSTER_SLOT_TIME_TARGET/2` constraint. The `nth(index as usize)` lookup itself is safe (`None` is handled), but the panics occur earlier, in the protobuf→domain-type conversion that runs before `nth()` is ever reached.

### Recommendation
Replace all `.expect()`/`.unwrap()` calls in the `generated::ConfirmedTransaction`/`generated::Transaction` conversion paths (`storage-proto/src/convert.rs` lines 254, 260, 299–300, 301) with proper `Result`-returning validation that surfaces a `DecodeError`, so `try_into()` at the `get_confirmed_block` call site returns `Err` (already handled via `.map_err()`) instead of panicking. Specifically:
- `value.transaction.ok_or(DecodeError{..})?` instead of `.expect(...)`.
- `Signature::try_from(bytes).map_err(|_| DecodeError{..})?` collected into a `Result<Vec<_>, _>` propagated with `?` instead of `.unwrap()`.
- `value.message.ok_or(DecodeError{..})?` instead of `.expect(...)`.
- The `into_legacy_transaction().expect(...)` in the `None` meta branch should also return an `Err(DecodeError)` rather than panicking.

### Proof of Concept
```rust
// storage-proto/src/convert.rs (or a new test module)
use solana_storage_proto::convert::generated;
use prost::Message;
use std::convert::TryInto;
use solana_transaction_status::TransactionWithStatusMeta;

#[test]
fn missing_transaction_field_should_not_panic() {
    // Construct a ConfirmedTransaction with transaction: None (valid protobuf, no fields set)
    let malformed = generated::ConfirmedTransaction {
        transaction: None,
        meta: Some(generated::TransactionStatusMeta::default()),
    };
    let mut buf = Vec::new();
    malformed.encode(&mut buf).unwrap();

    // Decoding succeeds
    let decoded = generated::ConfirmedTransaction::decode(&buf[..]).expect("decode should succeed");

    // This should return Err, not panic
    let result: Result<TransactionWithStatusMeta, _> = decoded.try_into();
    assert!(result.is_err(), "conversion panicked instead of returning Err");
}

#[test]
fn malformed_signature_length_should_not_panic() {
    let malformed_tx = generated::Transaction {
        signatures: vec![vec![0u8; 10]], // not 64 bytes
        message: Some(generated::Message::default()),
    };
    let confirmed_tx = generated::ConfirmedTransaction {
        transaction: Some(malformed_tx),
        meta: Some(generated::TransactionStatusMeta::default()),
    };
    let mut buf = Vec::new();
    confirmed_tx.encode(&mut buf).unwrap();
    let decoded = generated::ConfirmedTransaction::decode(&buf[..]).unwrap();

    let result: Result<TransactionWithStatusMeta, _> = decoded.try_into();
    assert!(result.is_err(), "conversion panicked on malformed signature length");
}
```
Run with `cargo test -p solana-storage-proto missing_transaction_field_should_not_panic malformed_signature_length_should_not_panic`; both currently panic (`thread panicked at 'transaction is required'` / `called Result::unwrap() on an Err value`) rather than returning `Err`, confirming the vulnerability. A fuzz target feeding arbitrary bytes into `generated::ConfirmedBlock::decode` followed by `TryInto<ConfirmedBlock>` should assert only `Ok`/`Err`, never a panic, across all fields.

impl TryFrom<generated::ConfirmedTransaction> for TransactionWithStatusMeta {
    type Error = DecodeError;
    fn try_from(value: generated::ConfirmedTransaction) -> std::result::Result<Self, Self::Error> {
        let meta = value.meta.map(|meta| meta.try_into()).transpose()?;
        let transaction = value.transaction.expect("transaction is required").into();

            Some(meta) => Self::Complete(VersionedTransactionWithStatusMeta { transaction, meta }),
