Missing Zero Address Validation for Fee Recipients in Escrow Factory and Destination Escrow - (contracts/BaseEscrowFactory.sol)

### Summary
The `BaseEscrowFactory._postInteraction` function extracts `integratorFeeRecipient` and `protocolFeeRecipient` from the `extraData` provided by the taker during an order fill. These addresses are not validated for the zero address. Since these addresses are baked into the deterministic salt/immutables of the destination escrow, a malicious or negligent taker can set them to `address(0)`. This results in either the permanent loss of fees (sent to the zero address) or the permanent freezing of all funds in the destination escrow if the underlying token's `transfer` function reverts on zero-address recipients. [6](#0-5) 

### Finding Description
In the 1inch Cross-chain Swap protocol, the taker triggers the creation of the source escrow by filling an order via the Limit Order Protocol. The `BaseEscrowFactory._postInteraction` function is called, which parses `extraData` to determine fee recipients and amounts. [7](#0-6) 

The code directly casts the first 40 bytes of `extraData` to address types for the integrator and protocol fee recipients. [1](#0-0)  These addresses are then included in the `parameters` field of the `DstImmutablesComplement` struct, which is used to generate the deterministic address of the `EscrowDst` contract on the destination chain. [2](#0-1) 

When a withdrawal is attempted on the destination chain via `EscrowDst.withdraw`, the contract attempts to transfer the fees to these recipients. [8](#0-7)  If the token being swapped is the native token (e.g., ETH), `_ethTransfer` is used, which succeeds when sending to `address(0)`, effectively burning the fees. [5](#0-4)  If the token is an ERC20, many implementations (and OpenZeppelin's `SafeERC20`) will revert on a transfer to `address(0)`, making the `_withdraw` function uncallable and freezing the maker's funds and taker's safety deposit inside the escrow forever. [9](#0-8) 

### Impact Explanation
- **High**: Permanent loss of unclaimed fee-like value (protocol and integrator fees) if the swap involves native tokens.
- **Critical**: Permanent freezing of user funds (the swap amount and safety deposit) if the swap involves ERC20 tokens that revert on zero-address transfers, as the `withdraw` and `publicWithdraw` functions will always fail. [10](#0-9) 

### Likelihood Explanation
The likelihood is medium. While a taker would typically want the swap to succeed, an unprivileged user (taker) has full control over the `extraData` passed to the `fillOrder` function. A taker could maliciously choose to freeze a maker's funds or accidentally provide malformed data, leading to the same result due to the lack of validation in the factory.

### Recommendation
Add zero-address checks for `integratorFeeRecipient` and `protocolFeeRecipient` in the `_postInteraction` function of `BaseEscrowFactory.sol`.
```solidity
address integratorFeeRecipient = address(bytes20(extraData[:20]));
address protocolFeeRecipient = address(bytes20(extraData[20:40]));
if (integratorFeeRecipient == address(0) || protocolFeeRecipient == address(0)) revert InvalidFeeRecipient();
```

### Proof of Concept
1. An attacker (Taker) identifies a Limit Order on the source chain.
2. The Taker calls `fillOrder` on the Limit Order Protocol, providing `extraData` where the first 40 bytes are all zeros.
3. `BaseEscrowFactory._postInteraction` parses these as `address(0)` for both fee recipients. [6](#0-5) 
4. The source escrow is created, and the `SrcEscrowCreated` event is emitted with `parameters` containing the zero addresses. [11](#0-10) 
5. On the destination chain, the `EscrowDst` is deployed using these parameters.
6. When the time comes to `withdraw` the funds on the destination chain, `EscrowDst._withdraw` is called. [12](#0-11) 
7. The call to `_uniTransfer(token, address(0), feeAmount)` is made. [13](#0-12) 
8. If the token is USDC or another standard ERC20, the transaction reverts, and the funds are locked in the contract.
