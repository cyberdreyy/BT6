### Title
Unbounded index-scan result accumulation in `getTokenAccountsByOwner` can OOM-abort the validator process when `scan_results_limit_bytes` is left at its default `None` - (File: `validator/src/commands/run/args/json_rpc_config.rs`)

### Summary
When the `SplTokenOwner` secondary index is enabled but the operator does not additionally pass `--accounts-index-scan-results-limit-mb`, `JsonRpcConfig::scan_results_limit_bytes` stays `None`. In that state, `Accounts::accumulate_and_check_scan_result_size` never returns `true`, so `load_by_index_key_with_filter`'s `ScanConfig::abort()` is never invoked, and a single `getTokenAccountsByOwner` request will materialize every matching account into an unbounded `Vec<KeyedAccountSharedData>`, sized only by how much on-chain data the attacker previously wrote under that owner key.

### Finding Description
The call chain is:
- `rpc/src/rpc.rs::get_token_accounts_by_owner` -> `get_filtered_spl_token_accounts_by_owner` [1](#0-0) , which, when `AccountIndex::SplTokenOwner` is enabled, calls `get_filtered_indexed_accounts`.
- `JsonRpcRequestProcessor::get_filtered_indexed_accounts` reads `self.config.scan_results_limit_bytes` and forwards it unchanged as `byte_limit_for_scans` into `bank.get_filtered_indexed_accounts` [2](#0-1) .
- This flows into `Accounts::load_by_index_key_with_filter`, which for every matching account calls `accumulate_and_check_scan_result_size(&sum, account, &byte_limit_for_scan)` and only calls `config.abort()` if that returns `true` [3](#0-2) .
- `accumulate_and_check_scan_result_size` explicitly returns `false` unconditionally when `byte_limit_for_scan` is `None`, i.e. no accumulation check happens at all [4](#0-3) .
- `scan_results_limit_bytes` is populated from the CLI flag `accounts_index_scan_results_limit_mb`, which has no `default_value(...)` set (unlike, e.g., `rpc_max_request_body_size`), so `value_t!(...).ok()` yields `None` unless the operator explicitly passes `--accounts-index-scan-results-limit-mb` [5](#0-4) [6](#0-5) . `JsonRpcConfig::default()` also sets `scan_results_limit_bytes: Option::default()` (i.e. `None`) [7](#0-6) .

Because the collector `Vec<KeyedAccountSharedData>` grows for every matched account/data byte with no size ceiling in this default state, an attacker who has previously funded and created many/large SPL-token accounts all owned by one pubkey can trigger a single `getTokenAccountsByOwner` RPC call that allocates memory proportional to that on-chain data rather than to any explicit RPC-side limit, matching the tested invariant violation.

### Impact Explanation
A single low-rate RPC call (`getTokenAccountsByOwner`) can force the validator's RPC-serving thread to allocate an amount of memory equal to the total size of attacker-controlled on-chain token accounts under one owner, with no explicit per-request cap unless the operator has opted into `--accounts-index-scan-results-limit-mb`. If the accumulated size is large enough relative to available memory, the allocation can exhaust memory and abort/crash the validator process, denying service via a single request. This falls into the "unbounded cost for a single low-rate call" / single-request process abort category.

### Likelihood Explanation
Requires: (1) validator running with `SplTokenOwner` secondary index enabled (a normal/encouraged RPC feature, not attacker-controlled), and (2) the operator not separately setting `--accounts-index-scan-results-limit-mb`, which is the default state since the flag has no default value. Given these two common conditions, the attacker only needs to fund and create enough token accounts under one owner key on-chain and issue one RPC call — no privileged access is required. The main mitigating cost to the attacker is the rent/storage cost of creating enough on-chain data to threaten the target's memory budget, but the flaw is structural: the request cost is bound only by attacker-authored data volume, not any server-enforced limit.

### Recommendation
Set a sane non-`None` default for `scan_results_limit_bytes` (e.g., give `accounts_index_scan_results_limit_mb` a `default_value` similar to `rpc_max_request_body_size`), so index scans are bounded out-of-the-box regardless of whether the operator explicitly configures the flag, and document/enforce this as a required safety default whenever a secondary index is enabled.

### Proof of Concept
Integration test outline (in `rpc/src/rpc.rs` test module or a new integration test):
1. Configure a `Bank`/`JsonRpcRequestProcessor` with `AccountSecondaryIndexes` containing `SplTokenOwner`, and `JsonRpcConfig::scan_results_limit_bytes = None` (the default).
2. Store N large SPL-token accounts (e.g., token-2022 accounts with extensions padded to tens of MB each) all with the same owner field at `SPL_TOKEN_ACCOUNT_OWNER_OFFSET`, summing to multiple GB.
3. Issue a single `getTokenAccountsByOwner` RPC call for that owner.
4. Assert expectation: either the call returns an error / is capped (desired fixed behavior), or, on the current vulnerable code, observe that `Accounts::load_by_index_key_with_filter`'s collector `Vec` grows to the full multi-GB size and the process's memory usage is unbounded by any configured limit (measure RSS before/after, or directly call `Accounts::accumulate_and_check_scan_result_size` in a unit test with `byte_limit_for_scan = None` and confirm it always returns `false` regardless of accumulated `sum`, as already partially demonstrated in `test_accumulate_and_check_scan_result_size` at `accounts-db/src/accounts.rs:1563-1565`, extended to show no upper bound is ever enforced in the `None` branch).

    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }
