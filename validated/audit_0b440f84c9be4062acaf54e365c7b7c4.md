### Title
Job-controlled pwsh script line can absorb the runner's `$?`/`$LASTEXITCODE` check into its own statement via backtick line-continuation - ([File: functions/concrete/run/stages/internal/scriptwriter/scriptwriter.go])

### Summary
`Builder.buildPwshScript` concatenates each job-controlled script line directly with the runner-injected `checkErr` text (`if(!$?) { Exit ... }`) using nothing but an EOL separator, and normalizes the line only with `strings.TrimSpace`. Because PowerShell treats a trailing backtick immediately followed by a newline (or an unterminated double-quoted string containing an embedded backtick-newline) as a statement/string continuation, an attacker-controlled `Step.Script` entry can make the following `checkErr`/`$global:LASTEXITCODE` assignment lines become inert text (part of a string literal or a harmless appended clause) instead of being parsed and executed as the intended control-flow check.

### Finding Description
`Step.Run` (`functions/concrete/run/stages/step.go:41`) passes `s.Script` — a job-author-controlled list of CI script lines (which, per GitLab CI YAML, may themselves contain embedded newlines via block-scalar syntax) — directly into `scriptwriter.Builder.Build`, which dispatches to `buildPwshScript` when `e.Shell` is `pwsh`/`powershell` [1](#0-0) .

In `buildPwshScript`, each line is only `strings.TrimSpace`-d, and the runner's per-line exit-check block is appended immediately after it with no syntactic isolation: [2](#0-1) [3](#0-2) 

`TrimSpace` strips trailing whitespace/newlines from the whole multi-line string but does not touch a trailing backtick, so a job line crafted to end in a bare backtick (PowerShell's line-continuation escape character) survives trimming as the literal last character. When `line + checkErr` is concatenated, `checkErr` begins with the shell's EOL (`eol := "\r\n"`/`"\n"`, `scriptwriter.go:151-156`), so the result is exactly `...<backtick><EOL>if(!$?) { Exit ... }` — the canonical PowerShell line-continuation sequence. This merges the physical line boundary the runner relies on to make `if(!$?) {...}` its own statement into whatever expression/string the attacker's line was constructing.

Concretely, if the attacker's line opens an unterminated double-quoted string ending in a trailing backtick (e.g., `` "marker `` ``), the backtick-escaped newline inside a PowerShell double-quoted string causes the string to continue onto the next physical line, silently absorbing the runner's injected `$global:LASTEXITCODE = $_runner_exit_code` and `if(!$?) { Exit ... }` text as literal string content rather than executable code. Because subsequent `lines[]` entries are all concatenated into the same `body` builder without any runner-enforced statement boundary beyond text, a job author who fully controls consecutive `Step.Script` entries can keep the string open across several injected checks/echoes and close it later with their own code, effectively neutralizing the exit-code enforcement for an attacker-chosen span of the script while resuming normal-looking execution afterward (including subsequent lines that may reference `$env:CI_JOB_TOKEN` or other secrets injected into the job environment).

No other check in this path validates or escapes job script content for PowerShell's continuation/quoting metacharacters — `buildPwshScript` performs no PowerShell-aware tokenization or quoting of `line` itself (only the runner's own echoed trace text is escaped via `psQuoteVariable`); the job's literal command text is emitted verbatim into the script body.

### Impact Explanation
This lets an unprivileged pipeline author neutralize the runner's own `pwsh`/`powershell` failure-propagation mechanism (`ExitCodeCheck`/`if(!$?) { Exit ... }`) for one or more of their own script lines, allowing job execution to continue past a command that the runner intended to treat as fatal. Since job environment (including `CI_JOB_TOKEN` and other job variables) remains accessible to all subsequent statements in the same script, this converts what should be a hard stop into continued execution with full access to the job's secrets/environment — matching the scoped impact of bypassing the failure-propagation invariant.

### Likelihood Explanation
Preconditions are fully attacker-controlled and cheap: the job author only needs `shell: pwsh` (or `powershell`) and a `script:` entry (or entries) ending in a trailing backtick / containing an unterminated PowerShell string with an embedded backtick-newline — no special runner configuration, privileged access, or third-party compromise is required. `ScriptSections` true/false does not change the vulnerable concatenation pattern (both branches append `line + checkErr` the same way). This is deterministically reproducible for any PowerShell-enabled shell executor (shell, docker-windows, kubernetes, custom) that reaches `Step.Run`.

### Recommendation
Do not rely on plain string concatenation with EOL separation to delimit runner-injected control-flow from job-controlled text. Either:
- Statically reject/normalize job script lines whose trailing content (after trimming) ends in an odd number of backticks or leaves an open string/scriptblock (requires a PowerShell-aware tokenizer, not just `TrimSpace`), or
- Wrap each job-controlled line in its own isolated `& { <line> }` invocation whose result/exit is captured via a mechanism that cannot be lexically absorbed by the line's trailing tokens (e.g., emit the check via a separately invoked script block or a `Invoke-Command`/`&` boundary that forces a statement terminator PowerShell cannot escape across), or
- Insert an explicit, unconditionally-terminating separator that cannot be neutralized by a trailing backtick, such as ensuring the line's own last character is forcibly neutralized (e.g., append a real terminator via a construct PowerShell must parse as a new statement rather than plain EOL, such as inserting `;` plus a comment-safe boundary and validating the line parses standalone via `System.Management.Automation.Language.Parser.ParseInput` before embedding it, failing the build if parse errors/unclosed tokens are detected).

### Proof of Concept
Go test (place in `functions/concrete/run/stages/internal/scriptwriter/scriptwriter_test.go`, mirroring `TestPwshScript`):

```go
func TestPwshScript_BacktickAbsorbsExitCheck(t *testing.T) {
    requireShell(t, ShellPwsh)

    // Attacker-controlled line: opens an unterminated double-quoted string
    // ending in a trailing backtick, so the runner's injected checkErr text
    // (starting with EOL) is swallowed as string content instead of being
    // parsed as a fresh `if` statement.
    lines := []string{
        "$x = \"marker `",
        "closing\"; Write-Host DID-NOT-STOP",
    }

    b := newBuilder(ShellPwsh, withExitCodeCheck /* or default */)
    b.ExitCodeCheck = true
    script := b.Build(lines)

    // Assert the generated script, when parsed/executed, does not contain
    // the check as an independent, reachable statement between the two
    // job lines -- i.e. it got merged into the string literal.
    // A parser-based assertion using PowerShell's own parser is stronger:
    //   pwsh -Command "[System.Management.Automation.Language.Parser]::ParseInput(...)"
    // and checking that the `if(!$?)` block is inside a StringConstantExpressionAst
    // rather than an IfStatementAst.

    out, code := runPwsh(t, script) // helper analogous to runBash
    assert.Contains(t, out, "DID-NOT-STOP",
        "expected the exit-code check to have been bypassed via backtick absorption; script:\n%s", script)
    assert.NotEqual(t, 0, code == 0, "job continued past what should be an enforced failure")
}
```

Expected assertion: on the vulnerable code, `DID-NOT-STOP` is printed (execution continued past the point the exit-code check should have enforced a stop), whereas a corrected implementation would either fail the script build (parser validation) or execute the check as an independent statement, halting before `Write-Host DID-NOT-STOP` runs when a prior intentional failure occurred.
