Found the analog. `calculate_block_reward` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` implements exactly the LoopFi rounding-loss pattern: `pending_delegator_rewards` (the vote account's undistributed reward pool, i.e. the "lastBalance"/accrued-funds analog) is a fixed running balance that only ever increases via `add_pending_delegator_rewards` (`programs/vote/src/vote_state/handler.rs:196-209`), while each stake account's share is computed by floor division `pending_delegator_rewards * stake / total_active_stake` every epoch. When an individual stake's share rounds down to `0` (small `stake` relative to `total_active_stake`, or `pending_delegator_rewards` too small relative to the number of delegators), that stake gets `block_reward = 0` — but `pending_delegator_rewards` itself is **never decremented** by the amount actually distributed. This is the inverse of LoopFi's exact defect shape (their bug was "lastBalance advances without index advancing"; here "pending_delegator_rewards balance never advances down even though each reward calc consumed a share of it"), but the same underlying root cause: per-delegator floor-division dust is not reconciled against the shared balance, so it can never be reclaimed or fairly redistributed — it is stuck forever in `pending_delegator_rewards`, and successive `getRewards`/epoch-reward computations keep re-dividing the same un-decremented total, systematically under-paying every remaining delegator each epoch. Given `total_active_stake` can be very large relative to any single small delegator's `stake` (analogous to USDC's low decimals vs. `totalShares` in the report), and epoch reward computation happens automatically every epoch (analogous to frequent `getRewards()` calls), the dust-loss compounds every epoch that a small-stake delegator is rewarded from a validator with large aggregate active stake.

### Title
Undecremented `pending_delegator_rewards` causes permanent reward-dust loss via floor-division sharing - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`calculate_block_reward` distributes a validator's `pending_delegator_rewards` pool to each delegating stake account via floor division by `total_active_stake`, but the pool balance is never reduced by the amounts actually paid out to individual stakes. Rounding remainders from every stake's share calculation are silently discarded rather than being carried forward or reconciled, permanently trapping small amounts of lamports that should belong to delegators.

### Finding Description
`calculate_block_reward` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232`) computes each stake's block-revenue-sharing reward as: [1](#0-0) 

The per-stake reward is `pending_delegator_rewards * stake / total_active_stake`, an integer (floor) division. `pending_delegator_rewards` is a validator-level pool that is only ever incremented via `DepositDelegatorRewards`/`add_pending_delegator_rewards`: [2](#0-1) 

At epoch-reward calculation time, `calculate_stake_rewards_and_commissions` calls `calculate_block_reward` once per stake delegation, and the resulting `block_reward` amounts are summed and separately distributed to each stake account: [3](#0-2) 

At no point in this path is `pending_delegator_rewards` reduced by the sum of the `block_reward` amounts actually paid out (unlike `distributed_rewards`/`total_stake_rewards_lamports`, which are tracked for the separate inflation-reward pool, e.g. `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:916-937`). Each epoch, the same (undiminished) `pending_delegator_rewards` value is used again as the numerator for every remaining/future stake's block-reward calculation, and the per-stake `stake/total_active_stake` fraction floors to zero whenever `stake` is small relative to `total_active_stake` (this is explicitly demonstrated in `test_calculate_block_reward_specific`'s "truncated" case, `get_block_reward_for_test(1, 10, 9, 0) == 0`): [4](#0-3) 

This is structurally identical to the LoopFi finding: a shared "already-accounted" balance (`pending_delegator_rewards` ≈ `lastBalance`) is used to compute a per-unit share (`stake/total_active_stake` ≈ `accrued/totalShares`) that can floor to zero for small holders, while the shared balance itself is not adjusted to reflect what was (or wasn't) actually paid out — so the floor-division remainder is neither returned to the pool nor redistributed; it is simply lost from the accounting of what delegators are owed.

### Impact Explanation
Delegators with stake that is small relative to a validator's total active stake systematically receive `0` block-revenue reward every epoch, while the validator's `pending_delegator_rewards` figure (visible via RPC/CLI as `pending_delegator_rewards`, cited in `cli/src/vote.rs:1674` and `account-decoder/src/parse_vote.rs:47`) is never reduced to reflect that these dust amounts were "spent" against the theoretical distribution. Over many epochs this compounds into a measurable amount of lamports that are permanently unrecoverable by any delegator — a quiet loss of funds that should belong to stakers, without any explicit accounting of burned/undistributed dust (contrast with the inflation-reward path, which tracks `distributed_rewards`/burn explicitly). This is a fund-loss/accounting-divergence bug rather than a memory-safety or consensus-halting one, but it is deterministic and reproducible on every affected epoch for validators with many small delegators.

### Likelihood Explanation
High likelihood of occurrence in practice: any validator with numerous small-stake delegators relative to its total active stake will trigger `stake * pending_delegator_rewards / total_active_stake == 0` for those delegators on essentially every epoch that block-revenue-sharing is active (feature `block_revenue_sharing`), exactly analogous to the report's USDC/`totalShares` scenario. No malicious actor is even required — ordinary epoch-boundary reward computation (`calculate_stake_rewards_and_commissions`, invoked automatically by the bank at every epoch boundary) reproduces the loss deterministically each epoch.

### Recommendation
Track the amount actually paid out of `pending_delegator_rewards` (e.g., sum of `block_reward` across all stakes in the epoch, similar to `total_stake_rewards_lamports`/`distributed_rewards`) and decrement `pending_delegator_rewards` by that exact amount rather than leaving it unchanged. Alternatively, compute each delegator's share using a running remainder/deficit-carry technique (e.g., largest-remainder method or "streaming" division with a carried fractional remainder) so that floor-division dust is either fully distributed over time or explicitly and intentionally reserved/burned with visible accounting, rather than silently and permanently orphaned inside `pending_delegator_rewards`.

### Proof of Concept
Using the existing test harness `get_block_reward_for_test` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:4246-4318`): [5](#0-4) 
`get_block_reward_for_test(1, 10, 9, 0)` returns `0` — a delegator with `stake=1` out of `total_stake=10` gets nothing from a `pending_delegator_rewards=9` pool. Because `calculate_block_reward` is a pure read of `pending_delegator_rewards` with no corresponding decrement anywhere in the calculation/distribution path (`calculate_stake_rewards_and_commissions` → `store_stake_accounts_in_partition`), running this scenario repeatedly across epochs (each epoch depositing a similarly small amount relative to `total_active_stake`) shows the `pending_delegator_rewards` balance is never reduced by the dust that should have gone to the small delegator, while other delegators' shares are computed against the same un-decremented balance — reproducing the "index/lastBalance" desynchronization described in the reference finding.
