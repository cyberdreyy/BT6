### Title
Stale cross-tenure conflicts bypass node-confirmed death checks, allowing double-signing at the same height - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`Signer::handle_block_pre_commit` clears a signed conflict from a *different* tenure purely because its `last_endorsed` timestamp is older than `freshness_cutoff` — without ever calling `conflict_still_blocks` (i.e. without querying `get_sortition_by_burn_hash`/`get_tenure_tip` for that conflict's tenure). This lets a signer sign a second, sibling block at the same height once the first conflicting signature simply ages out, with no proof the first block is actually dead.

### Finding Description
`get_signed_conflicts` returns every block ever signed at height ≥ H across all tenures [1](#0-0) . In `handle_block_pre_commit`, this list is filtered twice:

1. A `find` over conflicts with `last_endorsed > freshness_cutoff` that are not permitted and still `conflict_still_blocks` — this is the only place `conflict_still_blocks` (which calls `get_sortition_by_burn_hash`/`get_tenure_tip`) is invoked [2](#0-1) .
2. A second `any` check that only matches conflicts whose `consensus_hash == block_info.block.header.consensus_hash` (i.e. same tenure), regardless of freshness, checking the node's live tenure tip [3](#0-2) .

A conflicting block B that lives in a *different* tenure than the proposed block C, once B's `last_endorsed` falls behind `freshness_cutoff`, matches neither filter: it fails check 1 (not fresh) and fails check 2 (different `consensus_hash`). Execution falls through to `if !conflicts.is_empty() { info!(...) }` and then unconditionally signs C via `mark_locally_accepted` [4](#0-3) .

This is a real, reachable scenario: two miners can legitimately race to start the next tenure on the same parent block (both craft tenure-start blocks B and C at the same height H off the same parent). `check_block_against_signer_db_state`/`check_latest_block_in_tenure`, which runs before the conflict check, only inspects the *parent* tenure's tip for a tenure-change block — B's own tenure (a sibling, not the parent) is invisible to it, a blind spot the code's own comments acknowledge [5](#0-4) . The codebase has an explicit test proving the FRESH cross-tenure case is correctly blocked via a node query (`fresh_conflict_in_another_tenure_blocks_signing`, using `TenureAFate::Live`) [6](#0-5) , but there is no equivalent test for the same scenario once B's signature has gone stale, and the code path traced above shows no node query happens in that case.

Concretely: victim signer signs/locally-accepts B (reaches local 70% pre-commit threshold) but B is not yet globally accepted (not yet handed to the node — this is explicitly a normal, expected window per the docs). Before B is pushed to the node, `tenure_last_block_proposal_timeout` elapses. The attacker (or any second miner) then gets C — a sibling tenure-start block at the same height off the same parent — through pre-commit threshold. `handle_block_pre_commit(C)` finds B in `get_signed_conflicts`, excludes it purely because `last_endorsed <= freshness_cutoff`, never calls `conflict_still_blocks`, and signs C.

### Impact Explanation
This breaks the uniqueness/non-equivocation guarantee that section 5 of the signer flow is specifically designed to enforce: the same signer places valid signatures on two conflicting blocks (B and C) at the same height in different tenures, without ever confirming from the node that B is dead. If B is (or becomes) canonical while C also carries this signer's signature toward the 70% aggregate threshold, this materially contributes to a chain fork/equivocation — a Critical chain-safety violation. The bug is repeatable any time a stale, cross-tenure, not-yet-globally-accepted conflict exists at pre-commit time.

### Likelihood Explanation
The trigger requires: (1) a signed block B that reached local pre-commit threshold but has not yet been handed to the node (a normal, not attacker-forced condition — the docs describe this window as expected), (2) `tenure_last_block_proposal_timeout` elapsing before B reaches the node, and (3) a sibling tenure-start proposal C at the same height, which an unprivileged miner can craft with a single BTC-won slot and gossip normally. No majority-signer collusion, node operator access, or auth token is required — the attacker only needs to win one sortition slot and propose a colliding tenure-start block after the timeout. The exact timing window depends on the configured `tenure_last_block_proposal_timeout` value, but the vulnerability exists for any finite timeout.

### Recommendation
Remove the tenure-scoping in the second (post-freshness) conflict check, or extend `conflict_still_blocks` to also be invoked for stale, cross-tenure conflicts before excluding them — i.e., staleness alone should never be sufficient to drop a conflict from consideration; a node-derived death check (sortition orphaned, or globally-accepted-then-reorged) should still be required, matching the guarantee already implemented for the fresh path and for stale same-tenure conflicts.

### Proof of Concept
Extend `run_cross_tenure_scenario` (or add a new test) with a short `tenure_last_block_proposal_timeout` (e.g. `Duration::ZERO` or a few seconds) instead of `Duration::from_secs(100_000)`, keep `TenureAFate::Live` (node never served either tenure — B not yet globally accepted), and sleep past the timeout before B's proposal is evaluated:
1. Sign/pre-commit block A (tenure 1) to `LocallyAccepted`.
2. Sleep past `tenure_last_block_proposal_timeout`.
3. Feed block B (tenure 2, same height, same parent) through `process_event` to cross pre-commit threshold.
4. Assert `info_b.state == BlockState::LocallyAccepted` and `info_b.signed_self.is_some()` (currently expected to pass, demonstrating the bug), while asserting the mock node's `/v3/sortitions/burn/*` and `/v3/tenures/tip_metadata/{tenure_a}` endpoints were never queried (e.g., via a call-count assertion on the mock node), proving `conflict_still_blocks` was never invoked for tenure A before signing B.
