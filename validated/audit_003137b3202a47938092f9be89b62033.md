### Title
Non-atomic supply calculation in `getSupply` RPC handler can produce an incorrect `circulating` value via unchecked subtraction - (File: `rpc/src/rpc.rs`)

### Summary
The JSON-RPC `getSupply` handler computes `circulating = total_supply - non_circulating_supply.lamports` with a plain, non-saturating `u64` subtraction. This is the same class of bug as the referenced Yieldy report: a derived value (`rebasePercent`/`circulating`) is computed from two quantities that are not guaranteed to be mutually consistent at the moment of subtraction, so the subtraction can behave incorrectly.

### Finding Description
`get_supply` in `rpc/src/rpc.rs` obtains a bank via `self.bank(config.commitment)` [1](#0-0)  then performs two temporally separate reads against that same `Arc<Bank>`:

1. `calculate_non_circulating_supply(&bank)` — spawned onto a blocking thread, which first scans all stake-program accounts and then, in a second separate pass, re-reads each account's balance via `bank.get_balance(pubkey)` to sum `non_circulating_supply.lamports` [2](#0-1) .
2. `bank.capitalization()`, read only *after* the scan completes [3](#0-2) .

With default/`processed` commitment, `self.bank()` returns "the heaviest slot" bank, which is **not necessarily frozen** — it can still be actively mutated by the replay/banking stage while the RPC scan is running in its own blocking task [4](#0-3) . Because the stake-account scan and the final `capitalization()` read are two independent, non-atomic observations of a bank that is concurrently changing, the resulting `non_circulating_supply.lamports` (an aggregate of individually-read balances taken at different instants) is not guaranteed to be `<= total_supply` (a single scalar read at yet another instant).

The result is then combined with plain subtraction:
```rust
circulating: total_supply - non_circulating_supply.lamports,
``` [5](#0-4) 

Notably, the equivalent REST endpoint that performs the *same* computation (`/v0/circulating-supply`) explicitly uses `saturating_sub` for this exact case: `Ok(total_supply.saturating_sub(non_circulating_supply.lamports))` [6](#0-5) . The presence of `saturating_sub` in the sibling implementation but not in `get_supply` demonstrates that the underflow scenario is a recognized concern that was inconsistently mitigated — this mirrors the Yieldy issue's flaw, where a derived value's dependent adjustment was omitted in one place.

### Impact Explanation
In release builds (the default Cargo profile, since no repo-level `overflow-checks` setting was found), an underflow of `total_supply - non_circulating_supply.lamports` silently wraps to a value near `u64::MAX`. This is returned directly to any unprivileged RPC client calling `getSupply`, producing wildly wrong/misreported circulating-supply data (a value close to `u64::MAX` lamports) — a direct analog to the original report's "incorrect rebase percentage calculation," where an internal accounting invariant silently breaks and the caller-facing derived value becomes wrong. If overflow checks were ever enabled (e.g., in debug/test builds or a hardened profile), the same code path would instead panic the async task handling the request.

### Likelihood Explanation
This requires only a single unprivileged `getSupply` JSON-RPC call (default `processed` commitment is used if the caller doesn't override it) hitting a validator while it is actively processing/replaying blocks — a state the RPC-serving bank is normally in. No special account setup, malicious data, or privileged role is required, only a race between the RPC's own scan and normal, expected chain progression. However, `capitalization()` should equal the deterministic global lamport total, and observing a large enough discrepancy between the (unsynchronized) sum of non-circulating balances and that snapshot requires the racing window between the two reads to coincide with a sufficiently large lamport movement between/among stake accounts — this timing dependency is not experimentally verified here and would need to be reproduced against a live, mutating bank rather than a static test bank (the existing unit test `test_get_supply` only exercises a frozen bank and does not exercise this race) [7](#0-6) .

### Recommendation
Use `total_supply.saturating_sub(non_circulating_supply.lamports)` in `get_supply`, matching the existing `calculate_circulating_supply_async` implementation, so a transient inconsistency between the two non-atomic reads cannot produce a wrapped/incorrect `circulating` value or a panic.

### Proof of Concept
Conceptual reproduction (cannot fully exercise timing without a running cluster):
1. Run a validator RPC node with default `processed` commitment enabled.
2. Continuously submit transactions that move lamports among/through stake-program accounts (creating/splitting/merging stake accounts) so that the stake-account scan and the balance sum in `calculate_non_circulating_supply` observe a transient state.
3. Concurrently issue repeated `getSupply` JSON-RPC calls.
4. Because `bank.capitalization()` is read strictly after the (non-atomic, multi-account) balance scan against a still-mutating bank [3](#0-2) , under the right timing the sum of non-circulating balances can momentarily exceed the later-read `total_supply`, causing `total_supply - non_circulating_supply.lamports` to underflow, which either wraps to near-`u64::MAX` (release) or panics the request-handling task (overflow-checked builds).

async fn calculate_circulating_supply_async(bank: &Arc<Bank>) -> Result<u64, SupplyCalcError> {
    let total_supply = bank.capitalization();
    let bank = Arc::clone(bank);
    let non_circulating_supply =
        tokio::task::spawn_blocking(move || calculate_non_circulating_supply(&bank))
            .await
            .expect("Failed to spawn blocking task")
            .map_err(|e| SupplyCalcError::Scan(e.to_string()))?;

    Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
