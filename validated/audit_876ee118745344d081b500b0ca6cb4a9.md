### Title
`v1` chainstate uses a weaker duplicate-tenure-block check than `v2`, letting a miner get a second tenure-start block signed for a tenure that already has a locally-accepted (unsigned-by-quorum) block - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` and `stacks-signer/src/chainstate/v2.rs::validate_tenure_change_payload` are supposed to enforce the same invariant - "reject a tenure-change (tenure-start) block if this signer already has a block confirmed in this tenure" - but they check it with two different (non-equal) predicates, exactly analogous to the reported `MaximumLTV` (80%) vs `LiquidationThreshold` (90%) mismatch between `borrow()` and `withdraw()`.

### Finding Description
`v2::validate_tenure_change_payload` rejects a duplicate tenure-start proposal if `signer_db.get_last_signed_block(&block.header.consensus_hash)` returns `Some(_)`, i.e. if this signer has **locally or globally accepted** any block in the tenure: [1](#0-0) 

`v1::validate_tenure_change_payload`, however, uses `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` - it only rejects the duplicate if the *first* tenure-start block has already reached **global** acceptance (70% signature weight observed and reflected in the DB): [2](#0-1) 

`SignerDb::get_last_signed_block` returns a block whose state is `LocallyAccepted` or `GloballyAccepted`, whereas `get_last_globally_accepted_block` (used by v1) only matches `GloballyAccepted`: [3](#0-2) 

The project's own regression test and changelog entry document that `get_last_globally_accepted_block` was previously used for this exact check and was insufficient - it "would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change" - and was fixed for the `v2` path: [4](#0-3) [5](#0-4) 

The fix was applied only to `v2::validate_tenure_change_payload`; `v1::validate_tenure_change_payload` still uses the weaker, previously-flagged-as-buggy `get_last_globally_accepted_block` check. The design docs explicitly confirm this asymmetry is present today, not accidental drift: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)": [6](#0-5) 

**Why this breaks the intended equality/guard, mirroring the LTV analog:** the invariant "one canonical tenure-start block per tenure per signer" is supposed to be enforced identically regardless of which chainstate module (v1 vs v2) is currently active, just as `MaximumLTV` was supposed to gate both `borrow()` and a combined `borrow()+withdraw()` sequence. Instead, a signer running the `v1` protocol path will happily approve (pre-commit/sign) a second, distinct tenure-start block for the same tenure as long as the first tenure-start block never crossed the *global* 70%-signed threshold - even if this very signer already locally-accepted (signed) the first one. This is the single-signer-controllable analog of borrowing past `MaximumLTV` via the higher `LiquidationThreshold` path: the attacker (the block proposer/miner, potentially with only ordinary network visibility) routes the proposal through the weaker `v1` check to get a signature that the stronger `v2` check would have refused.

Because a signer's own `signed_self` timestamp is stamped the moment it produces `mark_locally_accepted`, and this same signer's `get_last_signed_block` predicate (`LocallyAccepted OR GloballyAccepted`) would have blocked a second proposal, but `get_last_globally_accepted_block` (state must literally equal `GloballyAccepted`) will not, a miner can:
1. Propose tenure-start block A. Enough signers locally-accept/sign it (but not yet 70% observed by the node/quorum, or block A stalls / never gets broadcast/adopted).
2. Immediately propose a second, different tenure-start block B for the *same* tenure (e.g. with a different transaction set), specifically to a signer running the `v1` code path.
3. Under `v1`, `validate_tenure_change_payload` calls `get_last_globally_accepted_block`, which returns `None` (A is only `LocallyAccepted`), so the `DuplicateBlockFound` rejection is skipped and the signer proceeds to sign B.
4. That signer has now signed two conflicting tenure-start blocks (A and B) for the same tenure - a rival-block/equivocation exactly like the class this scan is supposed to catch ("a signer signing an invalid/non-canonical/conflicting block").

### Impact Explanation
This meets the "Critical" bar defined by the rules: a single miner, without needing a majority of signers or any signer's key, can induce a `v1`-protocol signer into placing its signature over two conflicting tenure-start blocks for one tenure. That is a conflicting-signature / equivocation outcome, which the task rules classify as Critical ("a signer signing an invalid, non-canonical, or conflicting block").

### Likelihood Explanation
The pre-commit/handle_block_pre_commit re-check does re-derive conflicts via `get_signed_conflicts`/`conflict_still_blocks`, which is the documented "backstop." However, that backstop is scoped explicitly to *"either a tenure-change block's parent, or any other block's own"* tenure and the `DuplicateBlockFound` check in `validate_tenure_change_payload` is the only place that specifically targets *this tenure's own duplicate tenure-start* case at proposal time - the docs state the duplicate check "never runs again" after proposal. The signing-time backstop is intended to cover exactly this gap for `v2` semantics; for `v1` the intentionally-different (weaker) predicate at proposal time means the miner can exploit the window between the first block's local acceptance and its global acceptance being observed, which the docs' own historical changelog entry shows was previously exploitable in production ("occasionally shows up on mainnet"/stall bug that motivated the `v2` fix). Since `v1` is a "protocol-version-specific" path still compiled and dispatched based on the negotiated/global-consensus signer protocol version (`determine_active_signer_protocol_version`/`uses_global_state()`), this is reachable whenever `v1` semantics are in effect for the network, without requiring anything beyond normal miner proposal behavior.

### Recommendation
Make `v1::validate_tenure_change_payload`'s duplicate check use the same predicate as `v2`: replace `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` with `signer_db.get_last_signed_block(&block.header.consensus_hash)`, matching the fix already applied to `v2` and documented in the changelog ("ensure there are no locally accepted blocks in the tenure, not just globally accepted blocks"). If `v1`'s weaker behavior is believed to be intentional for backward-compatibility reasons, that assumption should be re-validated, since the equivalent `v2` behavior was explicitly labeled a bug fix in this same codebase.

### Proof of Concept
Conceptual PoC (structurally mirrors the existing regression test for `v2`, `check_tenure_change_rejects_when_locally_accepted_block_exists`, but run against the `v1::SortitionState`/`validate_tenure_change_payload` path instead):
1. Insert into `SignerDb` a `BlockInfo` for tenure `T` in state `LocallyAccepted` (via `mark_locally_accepted`), simulating that this signer already signed a first tenure-start block for `T`. [7](#0-6) 
2. Construct a second, distinct tenure-start proposal (`TenureChangeCause::BlockFound` + coinbase) for the same consensus hash `T`.
3. Call the `v1` proposal path (`SortitionState`/`validate_tenure_change_payload` for v1, reachable via `check_proposal` in `v1.rs`) instead of `v2`'s `sortitions_view.check_proposal`.
4. Observe that, unlike the `v2` test which asserts `RejectReason::DuplicateBlockFound`, the `v1` path returns `Ok(())` because `get_last_globally_accepted_block` finds nothing for a merely `LocallyAccepted` block, letting the second tenure-start block proceed to be pre-committed/signed.

Note: I was not able to execute this PoC in a sandbox; this is derived from reading the `v1`/`v2` implementations, the shared `SignerDb` query helpers, and the codebase's own regression test/changelog entry documenting that exact predicate as previously-buggy for `v2`. Confirming end-to-end exploitability (i.e., that no other guard in `v1`'s proposal-time or pre-commit-time flow independently blocks this specific scenario) would benefit from running the actual test suite, which requires a full Devin session with repository access.

    /// Return the last signed block in a tenure (identified by its consensus hash).
    /// A block is considered signed if it is locally or globally accepted. Blocks that
    /// have only been pre-committed are excluded, because a pre-commit does not put a
    /// signature over the block and may be safely superseded by a competing proposal.
    ///
    /// This answers "what is the tenure's signed tip?", a different question from
    /// [`SignerDb::has_signed_block_in_tenure`]'s "does a signature bind us to this tenure?",
    /// which is why the predicates deliberately differ on rejected blocks (see there).
    pub fn get_last_signed_block(
        &self,
        tenure: &ConsensusHash,
    ) -> Result<Option<BlockInfo>, DBError> {
        let query = "SELECT block_info FROM blocks WHERE consensus_hash = ?1 AND state IN (?2, ?3) ORDER BY stacks_height DESC LIMIT 1";
        let args = params![
            tenure,
            &BlockState::GloballyAccepted.to_string(),
            &BlockState::LocallyAccepted.to_string(),
        ];
        let result: Option<String> = query_row(&self.db, query, args)?;

        try_deserialize(result)
    }
