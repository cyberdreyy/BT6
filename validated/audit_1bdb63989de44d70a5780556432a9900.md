### Title
Instant-withdraw receipts created mid-epoch claim immediately from commingled vault cash, draining funded withdraw receipts — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` mints a receipt and increments `pendingInstantWithdraws`, while `claimInstantWithdrawRequest` pays the full `instantWithdrawsRequests[_user]` from the vault's underlying balance without checking that the collected instant-withdraw funds actually cover that receipt. Because `IdleCDOEpochVariant.requestWithdraw` can mint a new instant receipt at any point while `allowInstantWithdraw` is true (APR-drop condition), an unprivileged tranche holder can create a receipt after instant liquidity was already pulled and claim it immediately, paid out of cash that was collected via `collectWithdrawFunds` to back matured normal withdraw receipts of other users.

### Finding Description
Two facts combine into the bug:

1. In `IdleCDOEpochVariant.startEpoch`, when new deposits cover pending instant requests, `allowInstantWithdraw = true` is set and stays true for the whole epoch [1](#0-0) . Similarly `getInstantWithdrawFunds` sets `allowInstantWithdraw = true` mid-epoch after pulling `pendingInstantWithdraws` from the borrower [2](#0-1) .
2. `requestWithdraw` routes to the instant path whenever `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, burning tranche tokens and minting an instant receipt via `IdleCreditVault.requestInstantWithdraw` — with no check that instant funding was already collected [3](#0-2) .
3. `IdleCreditVault.claimInstantWithdrawRequest` burns the user's receipt tokens and calls `_transferFundedClaim(_user, amount)` for the full `instantWithdrawsRequests[_user]`, paying from the vault's aggregate underlying balance [4](#0-3) . That balance is commingled: `collectWithdrawFunds` transfers underlying for matured normal receipts into the same vault [5](#0-4) , and `collectInstantWithdrawFunds` only decrements the aggregate `pendingInstantWithdraws` counter — it never earmarks cash per receipt [6](#0-5) .

So once `allowInstantWithdraw` is on, a *newly created* instant receipt is immediately claimable even though zero underlying was collected for it. The payout is sourced from whatever cash sits in `IdleCreditVault`, which includes funds already collected to back other users' matured `withdrawsRequests`/`apr0Users` receipts.

### Impact Explanation
Direct theft of funded withdraw receipts. An attacker (any KYC-passed tranche holder) who waits until `allowInstantWithdraw` is true during a running epoch with a lowered APR can call `requestWithdraw(0, BBTranche)`, receive an instant receipt valued at current tranche price, and call `claimInstantWithdrawRequest` in the same transaction. The vault pays the full receipt amount out of cash reserved for other users' already-funded normal withdraw claims. When those users later call `claimWithdrawRequest`, `_transferFundedClaim` fails or pays less — the attacker has permanently extracted their escrowed principal and interest. Loss is bounded by the funded-claim cash held in the vault, up to the attacker's tranche balance converted at current price.

### Likelihood Explanation
Requirements: a non-programmable deployment, instant withdraws enabled (`isInstantWithdrawEnabled`), and an epoch where `lastEpochApr > unscaledApr + instantWithdrawAprDelta` — i.e., any epoch started after the honest manager lowered the APR, which is exactly the configuration the instant-withdraw feature exists for. `allowInstantWithdraw` becomes true either at `startEpoch` (when deposits cover pending instant requests) or after the honest manager's routine `getInstantWithdrawFunds` call past `instantWithdrawDeadline`. Both are normal operating states, not attacker-arranged edge cases. The attacker only needs a tranche position and one transaction.

### Recommendation
In `IdleCreditVault`, track funded instant liquidity separately from other claim cash (e.g., a `fundedInstantWithdraws` balance incremented by `collectInstantWithdrawFunds`), and have `claimInstantWithdrawRequest` pay only `min(instantWithdrawsRequests[_user], fundedInstantWithdraws)` or revert when unfunded. Alternatively, in `IdleCDOEpochVariant.requestWithdraw`, reject new instant receipts once instant funding for the epoch has been collected (compare against a snapshot of funded instant claims), so receipts created after funding must wait for the next funding round.

### Proof of Concept
Foundry fork test on the credit-vault deployment (skeleton — exact addresses from `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testInstantReceiptDrainsFundedClaims() external {
    // Setup: userA deposits AA, requests normal withdraw, epoch runs,
    // manager stops epoch with LOWER apr (instant delta condition now true),
    // borrower repays -> collectWithdrawFunds funds userA's receipt into IdleCreditVault.
    // Manager starts next epoch; allowInstantWithdraw == true (deposits covered pending instant).

    // Attacker (KYC'd, holds BB tranches) acts mid-epoch:
    vm.startPrank(attacker);
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(BBtranche)); // instant path
    // No underlying was collected for this new receipt, but claim pays in full
    // from IdleCreditVault cash that belongs to userA's funded receipt.
    cdoEpoch.claimInstantWithdrawRequest();
    vm.stopPrank();

    // userA's matured, fully-funded receipt can no longer be paid in full.
    vm.prank(userA);
    vm.expectRevert(); // _transferFundedClaim underflows / safeTransfer fails
    cdoEpoch.claimWithdrawRequest();
}
```

Caveat I could not fully verify within the tool budget: the exact gating inside `IdleCDOEpochVariant.claimInstantWithdrawRequest` (it reverts when `allowInstantWithdraw` is false and when the vault lacks balance — confirmed by `testClaimInstantWithdrawRequestAfterAnEpoch`). If that function also re-checks per-epoch funded instant totals, the window narrows to receipts created between funding collection and the next `startEpoch`; the commingled-cash accounting gap in `claimInstantWithdrawRequest`/`collectInstantWithdrawFunds` remains the root cause either way.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
