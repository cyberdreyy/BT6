### Title
APR0 withdraw request permanently bricks `stopEpoch` once APR returns to non-zero - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal > 0` and `unscaledApr != 0` [1](#0-0) . Any unprivileged, KYC-passed lender can force `apr0TotalPrincipal` non-zero by calling `requestWithdraw` with a dust amount while the vault's APR is 0, because `requestWithdraw` unconditionally routes to `_requestWithdrawApr0` when `unscaledApr == 0` [2](#0-1)  and `_requestWithdrawApr0` increments the global bucket [3](#0-2) . Crucially, `apr0TotalPrincipal` is only ever cleared inside `prepareStopEpochWithApr0` itself — at the very end, after the revert check [4](#0-3) . `_settleApr0` settles per-user principal but never decrements the global bucket [5](#0-4) . Therefore, once the honest manager sets a non-zero APR (a routine configuration change via `setAprs`/`setAprsWithBuffer`), every subsequent `stopEpoch` call reverts before reaching the reset line — permanently.

### Finding Description
The bug-class analog to CVE-2026-34267 (a reachable server crash/DoS) is a state-transition liveness failure: an attacker-controlled, unrecoverable revert in the epoch state machine.

Sequence:

1. Vault is in an APR=0 configuration (`unscaledApr == 0`), which is a supported mode (`_requestWithdrawApr0` exists specifically for it).
2. Attacker (any allowed lender holding tranche tokens, or the `IdleCDOEpochQueue` indirectly) calls `IdleCDOEpochVariant.requestWithdraw` with `1 wei` of tranches. `IdleCreditVault.requestWithdraw` burns principal, mints a receipt, and calls `_requestWithdrawApr0`, setting `apr0TotalPrincipal = 1` [3](#0-2) .
3. The attacker can even claim/settle their own request — `_settleApr0` zeroes `apr0Users[user].principal` but leaves `apr0TotalPrincipal` untouched [6](#0-5) . There is no code path that decrements `apr0TotalPrincipal` other than the tail of `prepareStopEpochWithApr0`.
4. The honest manager later re-enables a positive APR (`setAprs`/`setAprsWithBuffer` via `IdleCDOEpochVariant.stopEpoch` APR update or directly) — normal operations.
5. The next `stopEpoch` calls `prepareStopEpochWithApr0`, which hits `if (unscaledApr != 0) revert NotAllowed()` [7](#0-6)  before reaching `apr0TotalPrincipal = 0` [8](#0-7) . The call reverts, `epochNumber` never bumps, and every future `stopEpoch` reverts identically. The attacker cannot remove the poison even voluntarily, since there is no decrement path.

Existing guards do not help: the dust request is a legitimate withdrawal, KYC/`isWalletAllowed` is satisfied, `_onlyIdleCDO` is satisfied, and the manager role is honest — the DoS is triggered purely by sequencing an honest APR change after a dust APR0 request.

### Impact Explanation
Permanent freezing of all vault funds. `stopEpoch` is the only path that repays the borrower funding, settles `pendingWithdraws` via `collectWithdrawFunds`, increments `epochNumber`, and lets users pass the `epochNumber <= lastWithdrawRequest[_user]` claim gate in `_claimFundedWithdrawRequest` [9](#0-8) . With `stopEpoch` bricked, every pending and future withdrawal is frozen indefinitely; the only escape is a contract upgrade or `_emergencyShutdown`, i.e., a permanent-freeze severity outcome costing 1 wei to trigger.

### Likelihood Explanation
Requires a specific configuration sequence (APR=0 period followed by a non-zero APR), but both are honest-manager operations the codebase explicitly supports — the `apr0` flow exists precisely for the zero-APR regime, and resuming a positive APR is routine. The attacker action is a single dust `requestWithdraw` by any allowed lender, costing only gas plus the (recoverable or dust-sized) receipt. Likelihood is moderate: it needs an APR transition while the poisoned bucket is pending, but the poison persists across epochs and even across the attacker's own claim, giving an unbounded window.

### Recommendation
Decouple the two concerns in `prepareStopEpochWithApr0`: move `apr0TotalPrincipal = 0` (and any per-epoch rate write) before the `unscaledApr != 0` check, or replace the revert with "skip APR0 interest accrual and still close the bucket". Additionally, decrement `apr0TotalPrincipal` inside `_settleApr0` when a user's open APR0 principal settles, so the global bucket reflects genuinely outstanding principal rather than a monotonically latched value.

### Proof of Concept
Foundry fork outline (mirroring `test/foundry/IdleCreditVault.t.sol` helpers such as `_setFeeParams`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testApr0PoisonBricksStopEpoch() external {
    // arrange: zero fees, set APR to 0
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);

    // attacker: dust withdraw request while unscaledApr == 0
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    assertEq(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 1);

    // honest manager resumes a positive APR (routine ops)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(5e18, 5e18);

    // borrower repays; manager tries to stop the epoch — reverts forever
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + amount);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // still bricked on retry and after the attacker claims their own receipt
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);
}
```

Caveat: I was unable to verify the exact call site ordering inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` (that `prepareStopEpochWithApr0` is invoked unconditionally and its revert propagates) within the available search budget; the grep confirms `prepareStopEpochWithApr0` is called from `IdleCDOEpochVariant.sol`, and the strategy-level revert plus monotonic `apr0TotalPrincipal` are directly verified in the source above.

```text
  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
  }
```

```text
  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
    apr0TotalPrincipal += _amount;
  }
```
