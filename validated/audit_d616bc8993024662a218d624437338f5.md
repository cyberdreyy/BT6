### Title
Defaulted-epoch withdraw receipts are keyed under the request epoch but looked up under `defaultRecoveryEpoch`, so pending receipts escape the recovery haircut and are paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In `IdleCreditVault`, `requestWithdraw` indexes a user's pending receipt by the epoch number at request time (`withdrawsRequestsByEpoch[_user][currentEpoch]`, `lastWithdrawRequest[_user] = currentEpoch`), while `_claimDefaultedWithdrawRequest` only clears receipts indexed under `defaultRecoveryEpoch = epochNumber` at finalization. Because `epochNumber` is incremented by `deposit()` during `stopEpoch` (before default finalization), every pending receipt recorded in the request epoch misses the haircut lookup, falls through to `_claimFundedWithdrawRequest`, and is paid at 100% from the strategy balance that *is* the recovery reserve. First claimers drain the reserve at par; later claimants (including the honest `IdleCDOEpochQueue` path) receive nothing.

### Finding Description
The analog of "unexpectedly high interrupt number → wrong index → privilege/gain" is an epoch-index mismatch between receipt recording and receipt clearing:

1. `requestWithdraw` stores the receipt under the *current* `epochNumber` (lines 260, 282, 293):
   - `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`
   - `lastWithdrawRequest[_user] = currentEpoch`
   - `pendingWithdraws += _amount` (so the basis is included in `defaultPendingClaimBasis`, line 645)
2. `epochNumber += 1` happens inside `deposit()` when an epoch is running (line 610), i.e. during the `stopEpoch` flow — *before* the default is detected/finalized.
3. `finalizeDefaultRecovery` then sets `defaultRecoveryEpoch = epochNumber` (line 693), which is now **one higher** than the epoch under which the pending receipts were recorded.
4. On `claimWithdrawRequest`, `_claimDefaultedWithdrawRequest` calls `_clearWithdrawClaimForEpoch(_user, defaultRecoveryEpoch, true)` (line 774), which reads `withdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — a slot that is `0` for all defaulted-epoch receipts — so `claimBasis == 0` and it returns without paying (lines 812-815).
5. Execution continues to `_claimLossAdjustedWithdrawRequest` (keyed on `lastWithdrawRequest[_user]` = request epoch; `lossRecoveryPriceByEpoch[requestEpoch]` is `0` since no partial `collectWithdrawFunds` occurred) and then `_claimFundedWithdrawRequest`.
6. `_claimFundedWithdrawRequest`'s gate `epochNumber <= lastWithdrawRequest[_user]` is `N+1 <= N` = false, so it pays the full aggregate `withdrawsRequests[_user]` at par via `_transferFundedClaim` (lines 326-349), burning only the receipt tokens.

The reserve was sized as `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` with `totalBasis` including `pendingWithdraws` (lines 679-688). Paying pending receipts at 100% instead of `recoveryPrice` therefore overdrawing exactly that basis — the strategy's underlying balance is the same pot `defaultRecoveryReserve` accounts for, so each par claim steals the haircut from every other defaulted-epoch claimant and from active-LP recovery dust. Once the balance is exhausted, `underlyingToken.safeTransfer` reverts for all remaining claimants: permanent freezing/theft of their claims.

`instantWithdrawsRequestsByEpoch` has the symmetric issue: `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (line 844), so instant receipts recorded pre-increment also fall through to the par payout at lines 387-392.

### Impact Explanation
Direct theft plus permanent freezing of unclaimed recovery. The first defaulted-epoch withdrawer to call `claimWithdrawRequest` (through `IdleCDOEpochVariant.claimWithdrawRequest`, which is permissionless for any user) receives `withdrawsRequests[_user]` at par instead of `* defaultRecoveryPrice / RECOVERY_FULL`. With e.g. `recoveryPrice = 0.5e18` and a `pendingWithdraws` basis of 1M USDC, the first claimant with a large receipt can extract up to ~500k USDC more than entitled, leaving later claimants' `safeTransfer` to revert forever — the recovery reserve is insolvent by exactly the escaped haircut amount. `pendingWithdraws -= claimBasis` at line 778 is also skipped, corrupting the global invariant.

### Likelihood Explanation
Requires only a borrower default (an expected protocol event with a dedicated flow: `stopEpoch` → `defaulted()` → `finalizeDefaultRecovery`) and one normal withdraw request made during the epoch that ends in default — the most common receipt scenario, exercised in `test/foundry/IdleCDOEpochQueue.t.sol:testProcessPostDefaultWithdrawalAsNormalClaim` (which only asserts payout `> 0`, so it does not catch the par-vs-haircut overpayment). No privileged misbehavior, no timing race beyond being an early claimer. The attacker is an ordinary KYC-passed withdrawer.

### Recommendation
Index defaulted-epoch receipts consistently: either record `withdrawsRequestsByEpoch`/`instantWithdrawsRequestsByEpoch` under the epoch the claim will be settled in (post-increment), or make `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` clear receipts for *all* epochs `<= defaultRecoveryEpoch` that are still reflected in `withdrawsRequests[_user]`/`instantWithdrawsRequests[_user]`. Simplest fix: in `_claimDefaultedWithdrawRequest`, fall back to `lastWithdrawRequest[_user]` (and the aggregate `withdrawsRequests[_user]` basis) when the `defaultRecoveryEpoch` lookup returns zero but the user still has an unfunded pending receipt, and symmetrically in `_claimDefaultedInstantWithdrawRequest` check `instantWithdrawsRequests[_user]` against the unsettled remainder of `pendingInstantWithdraws`. Also skip `_claimFundedWithdrawRequest` for any receipt whose basis was included in `defaultPendingClaimBasis`.

### Proof of Concept
Foundry fork test (extends the existing `test/foundry` harness, mainnet USDC vault as in `IdleCreditVault.t.sol`):

```solidity
function testDefaultedReceiptPaidAtParDrainsReserve() public {
    // users A and B deposit, epoch starts, both request withdraw of tranche tokens
    _depositWithUser(A, 1000e6);
    _depositWithUser(B, 1000e6);
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(A, trancheA);
    _requestWithdrawWithUser(B, trancheB);

    // epoch ends with borrower default; epochNumber increments inside stopEpoch->deposit
    _stopCurrentEpochWithApr(10e18);
    vm.prank(manager); cdoEpoch.startEpoch();
    deal(address(underlying), strategy.borrower(), 0, true);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(cdoEpoch.owner()); cdoEpoch.stopEpoch(0, 0); // defaulted
    assertTrue(cdoEpoch.defaulted());

    // finalize recovery at ~50%
    uint256 basis = strategy.defaultPendingClaimBasis(); // includes A+B pendingWithdraws
    uint256 recovered = basis / 2;
    deal(address(underlying), manager, recovered, true);
    vm.startPrank(manager);
    underlying.approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();
    // epochNumber is now requestEpoch + 1 == strategy.defaultRecoveryEpoch()

    // A claims: defaulted-epoch lookup on epochNumber returns 0 basis,
    // funded path pays withdrawsRequests[A] at par instead of ~50%
    uint256 preA = underlying.balanceOf(A);
    vm.prank(A); cdoEpoch.claimWithdrawRequest(A); // via IdleCDOEpochVariant
    uint256 gotA = underlying.balanceOf(A) - preA;

    assertGt(gotA, basis_A * strategy.defaultRecoveryPrice() / 1e18); // overpaid
    // B's claim now reverts on safeTransfer or gets dust: reserve insolvent
    vm.prank(B);
    vm.expectRevert(); // or assertLt(gotB, expectedHaircut)
    cdoEpoch.claimWithdrawRequest(B);
}
```

Expected result: `gotA` equals A's full requested amount (par) rather than `* defaultRecoveryPrice / RECOVERY_FULL`, and B's claim reverts or pays ~0, demonstrating one-receipt-one-payout and reserve-solvency breakage.

Note: I verified the index mismatch statically; the exact `epochNumber` value at finalization relative to the request epoch depends on whether `deposit()` is invoked during the defaulted `stopEpoch` before `finalizeDefaultRecovery`. If the codebase guarantees `defaultRecoveryEpoch == requestEpoch` in every path (e.g. increment happens strictly after finalization), this specific instance does not trigger — I could not fully confirm the call ordering inside `IdleCDOEpochVariant.stopEpoch` within the available iterations.
