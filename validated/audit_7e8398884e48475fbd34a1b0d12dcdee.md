### Title
`internal_withdraw` decrements `last_total_balance` before the outgoing transfer is confirmed, letting the balance permanently drift below reality - (File: `staking-pool/src/internal.rs`)

### Summary
`StakingContract::internal_withdraw` fires `Promise::new(account_id).transfer(amount)` and immediately subtracts `amount` from `self.last_total_balance` in the same synchronous call, without ever checking whether the transfer promise actually succeeds. Because a plain NEAR `Transfer` action can only fail if the destination account does not exist when the outgoing receipt is processed, an attacker who deletes their own throwaway account right after calling `withdraw`/`withdraw_all` can make the transfer bounce back to the pool while the recorded `last_total_balance` stays permanently lowered.

### Finding Description
The invariant claimed is:
`last_total_balance == env::account_balance() + env::account_locked_balance()` after every state-changing call.

`internal_withdraw` breaks this unconditionally: [1](#0-0) 

There is no `is_promise_success()` guard and no callback attached to the transfer, unlike the pattern used elsewhere in the same repo for cross-contract withdrawals (e.g. `lockup/src/owner_callbacks.rs::on_staking_pool_withdraw`, which does check `is_promise_success()` before mutating `deposit_amount`) — that pattern is absent here.

Root cause: the `Transfer` action created by `Promise::new(account_id).transfer(amount)` is dispatched as an asynchronous outgoing receipt processed after the current function call returns. Its only failure mode is `AccountDoesNotExist` for `account_id`. Since `account_id = env::predecessor_account_id()`, the account must exist at the moment `withdraw` is called (it signed/forwarded the call), but nothing stops the attacker from deleting that very account (via `delete_account`, refunding its balance to a beneficiary they control) before the outgoing transfer receipt is processed. When that happens the runtime refunds the failed transfer's NEAR back to the staking-pool contract's own balance, restoring `env::account_balance()`, while `self.last_total_balance -= amount` was already applied and is never restored.

Exploit flow:
1. Attacker creates a disposable sub-account, calls `deposit()` (no staking, no minimum enforced, no unstaking delay since `unstaked_available_epoch_height` defaults to 0) to obtain a withdrawable `unstaked` balance.
2. Attacker calls `withdraw(dust_amount)` from that account, which schedules `Promise::new(account_id).transfer(dust_amount)` and immediately does `self.last_total_balance -= dust_amount`.
3. Before that outgoing receipt is applied, attacker submits `delete_account` on the same sub-account.
4. The transfer receipt fails (`AccountDoesNotExist`); the dust NEAR is refunded to the staking-pool contract, so `env::account_balance()` is unaffected, but `last_total_balance` stayed reduced.
5. Repeat with fresh disposable sub-accounts, thousands of times within a single epoch, to accumulate an ever-growing gap between `last_total_balance` and the real backing balance.

No existing guard catches this: `internal_ping` only asserts `total_balance >= self.last_total_balance` [2](#0-1) , which still holds since real balance is *higher* than the drifted-down `last_total_balance`, not lower — the assert can't fire on this side of the drift.

### Impact Explanation
At the next epoch's `internal_ping`, `total_reward = total_balance - self.last_total_balance` is inflated by the accumulated dust drift [3](#0-2) . This phantom "reward" is added to `total_staked_balance` and converted into owner stake shares, even though no real validator/staking reward backs it. This inflates `total_staked_balance`/`total_stake_shares` claims against real NEAR held by the pool — an accounting divergence where delegators and the owner are credited more stake value than the contract actually holds, i.e. claims exceeding actual holdings (Critical: accounting value diverging from reality that other parties settle on).

### Likelihood Explanation
The attacker needs only: the ability to create/fund/delete disposable NEAR accounts (cheap, largely refunded via the delete beneficiary) and the ability to time a `delete_account` transaction to land before the withdraw's outgoing transfer receipt is processed. No privileged role, owner access, or foundation permission is required — this is fully within the "unprivileged attacker" capabilities described (create accounts, call open methods, withdraw from any pool). Each cycle costs only gas; the drift is directly proportional to the number of repetitions, which is explicitly described as feasible "thousands of times... inside one epoch."

### Recommendation
Do not mutate `self.last_total_balance` optimistically in `internal_withdraw`. Attach a callback to the transfer `Promise` and only finalize the `last_total_balance` reduction (or, alternatively, restore `account.unstaked` and re-credit `last_total_balance`) after confirming `is_promise_success()`, mirroring the pattern already used in `lockup/src/owner_callbacks.rs::on_staking_pool_withdraw`.

### Proof of Concept
Using `near-sdk-sim` / `RuntimeStandalone`:
1. Deploy the staking-pool contract; call `deposit()` from a disposable sub-account with a small deposit.
2. Call `withdraw(dust_amount)` from that sub-account; capture `last_total_balance` immediately after (via a view or by exposing it in test build) — assert it decreased by `dust_amount`.
3. Simulate the outgoing transfer receipt failing by deleting the sub-account before the transfer receipt executes (or, in `testing_env!`, directly simulate `PromiseResult::Failed` for the transfer action and confirm the contract does nothing to compensate `last_total_balance`).
4. Assert that `env::account_balance() + env::account_locked_balance() != last_total_balance` after the failed transfer resolves — the binding `last_total_balance == env::account_balance() + env::account_locked_balance()` fails, with `last_total_balance` strictly smaller than reality.
5. Call `ping()` in the following epoch and assert `total_staked_balance` increases by more than the real reward earned, demonstrating the inflated claim against actual contract balance.

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }
