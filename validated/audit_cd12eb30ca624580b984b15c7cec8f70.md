## Analysis Result: Valid vulnerability

The question correctly identifies a real gap: `createDstEscrow` performs **no validation at all** on the `parameters` blob or on the relationship between fee amounts and `amount`, unlike the source-chain path.

### Title
Missing fee/parameters validation in `createDstEscrow` permanently bricks `withdraw`/`publicWithdraw` on `EscrowDst` - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
Any unprivileged address can call `BaseEscrowFactory.createDstEscrow` directly, supplying an arbitrary `Immutables.parameters` blob and funding the escrow itself. Unlike the source-chain fill path (`_postInteraction`), which enforces `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();`, `createDstEscrow` performs no check on `parameters.length` or on the fee-amount/`amount` relationship before deploying and funding the clone. [1](#0-0) 

### Finding Description
`EscrowDst._withdraw` (shared by both `withdraw` and `publicWithdraw`) unconditionally decodes fee metadata from `immutables.parameters`: [2](#0-1) 

`ImmutablesLib`'s calldata accessors each independently gate on a minimum `parameters.length`: `0x20` for `protocolFeeAmountCd`, `0x40` for `integratorFeeAmountCd`, `0x60` for `protocolFeeRecipientCd`, `0x80` for `integratorFeeRecipientCd`. [3](#0-2) 

If an attacker crafts a `parameters` blob of exactly 65 bytes with a non-zero value at offset `0x20` (so `integratorFeeAmountCd()` returns a large fee, e.g. near the full `amount`), the length check for `integratorFeeAmountCd` (`>= 0x40`) passes, but the subsequent call to `integratorFeeRecipientCd()` (`>= 0x80`) always reverts with `IndexOutOfRange`. Because `_withdraw` is the single internal function used by both `withdraw` (private, `onlyCaller(taker)`) and `publicWithdraw` (`onlyAccessTokenHolder`), **both** the private and the public withdrawal paths are bricked — exactly as the question describes. Since `createDstEscrow` never validates `parameters` at deployment time, this malformed escrow can still be funded and become CREATE2-deterministic and "valid" per `onlyValidImmutables`.

Notably, `cancel()` does not touch fee decoding at all and simply refunds the full `amount` to `immutables.taker`: [4](#0-3) 

So the escrow creator (attacker, who is also `taker` since nothing enforces `msg.sender == immutables.taker` in `createDstEscrow`) can always recover 100% of their own deposited funds via `cancel()` once the cancellation timelock passes, while the maker's payout via `withdraw`/`publicWithdraw` is permanently unreachable for the life of the escrow.

### Impact Explanation
This breaks the stated invariant: "If a destination escrow was funded and the secret is known, the public withdrawal path should still be able to finalize." The maker's expected destination-chain payout is frozen for the full withdrawal/public-withdrawal window and can never be released through the withdraw path — it is only recoverable back to the attacker-controlled `taker` via `cancel()`. This fits the bounty's "Temporary freezing of funds" (High) impact during the live swap lifecycle, and depending on whether a real maker's secret gets exposed against such a malformed escrow, can escalate toward direct loss for the counterparty since the deposited tokens end up back with the taker rather than reaching the maker.

### Likelihood Explanation
`createDstEscrow` is a permissionless, unprivileged entrypoint — the caller only needs to supply the correct `msg.value`/token balance for their own chosen `Immutables`, with no privileged-resolver or governance gate. Crafting a 65-byte `parameters` blob with a non-zero integrator-fee word is trivial and entirely attacker-controlled at escrow-creation time. No off-chain trust bypass is required for the on-chain revert itself; the freeze occurs purely from decoding logic once a valid secret is presented to `withdraw`/`publicWithdraw`.

### Recommendation
Add explicit validation in `createDstEscrow` (and/or in `EscrowDst._withdraw`) that: (1) `dstImmutables.parameters.length` equals the expected fixed size (`0x80`, i.e., exactly protocol fee + integrator fee + two recipient addresses), and (2) `integratorFeeAmount + protocolFeeAmount < amount`, mirroring the check already performed in `BaseEscrowFactory`'s `_postInteraction` path for the source escrow. This should revert at creation time rather than allowing a permanently stuck escrow to be funded.

### Proof of Concept
1. Attacker calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.parameters` set to a crafted 65-byte blob (`abi.encodePacked` truncated ABI encoding) where bytes `[32:64]` encode a large `integratorFeeAmount` (e.g. near full `amount`), funding the ERC20/native amount and safety deposit themselves.
2. `createDstEscrow` deploys and funds the clone with no validation on `parameters`.
3. Warp to `DstWithdrawal` — call `withdraw(secret, immutables)` as `taker`: reverts with `IndexOutOfRange` inside `integratorFeeRecipientCd()` because `parameters.length (65) < 0x80`.
4. Warp to `DstPublicWithdrawal` — call `publicWithdraw(secret, immutables)` as an access-token holder with the correct secret: reverts identically.
5. Only after `DstCancellation`, `taker` (the attacker) can call `cancel()` to reclaim the full deposited `amount` and safety deposit, while the maker never receives any payout through the withdraw path. [2](#0-1) [5](#0-4) [1](#0-0)

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function protocolFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;
        if (parameters.length < 0x20) revert IndexOutOfRange();
        assembly ("memory-safe") {
            ret := calldataload(parameters.offset)
        }
    }
