### Title
Builder withdrawal amount sent to the execution layer is not capped to the builder's actual balance, minting Gwei without CL-side backing - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas fork, `get_builder_withdrawals` copies the *requested* `BuilderPendingWithdrawal.amount` verbatim into the `Withdrawal` object that is committed to the execution layer, without capping it to the builder's actual `balance`. The consensus-layer accounting in `apply_withdrawals`, however, deducts only `min(withdrawal.amount, builder_balance)` from the builder. When a builder's balance is insufficient to cover a pending withdrawal, the execution layer still mints the full requested amount to the withdrawal's `fee_recipient`, while the consensus layer only debits what the builder actually had. The difference is Gwei created out of thin air and paid to the withdrawal's `fee_recipient` — an accounting mismatch of the same class as the PoolTogether "trapped sponsorship" bug (input amount and output amount silently diverge), except here it inflates supply instead of trapping funds.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md) builds the `Withdrawal` entries that make up `state.payload_expected_withdrawals`, which the execution layer is required to honor exactly as specified: [1](#0-0) 

Note that `amount=withdrawal.amount` is taken directly from `BuilderPendingWithdrawal.amount` with no `min(...)` against `state.builders[builder_index].balance`.

Later, when the withdrawals are actually applied to consensus-layer state, the deduction *is* capped: [2](#0-1) 

`state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)` — so if `builder_balance < withdrawal.amount`, the CL only removes `builder_balance` (down to 0), yet the `Withdrawal` object dispatched to the EL still says `amount = withdrawal.amount` (the full, uncapped requested amount). Since execution-layer withdrawal processing unconditionally credits `withdrawal.amount` Gwei to the specified address (withdrawals have no "insufficient balance" check on the EL side — that's the entire point of the CL-computed withdrawal amounts model), the recipient receives more Gwei than was ever debited from the builder.

This exact scenario is explicitly covered by the repository's own tests, which assert this behavior as "expected" rather than treating it as a bug: [3](#0-2) 

The test confirms: `withdrawal.amount` sent to the EL/payload is the full requested `5_000_000_000` Gwei, while `builders[0].balance` (the CL-side deduction) drops only from `1_000_000_000` to `0`. That leaves a `4_000_000_000` Gwei gap between what is minted on the EL side and what was actually removed from the builder's CL balance.

Contrast this with the equivalent handling for validator partial/full withdrawals and the builder *sweep* withdrawals, both of which explicitly cap the withdrawal amount to the available balance before it is placed in the output list (e.g. `amount=balance - get_max_effective_balance(validator)` bounded by the balance check, or `amount=builder.balance` for sweep withdrawals, which is exact and cannot exceed what exists). Only the `get_builder_withdrawals` (pending, non-sweep) path fails to perform this capping before emission.

### Impact Explanation
This breaks the core invariant that "Gwei sent to the execution layer must equal Gwei removed from the source." If a builder's committed pending withdrawal amount can exceed its current balance at processing time (e.g. because multiple withdrawal requests stack up, or the balance is reduced by other spent bid payments processed between the withdrawal being queued and being swept), the recipient `fee_recipient` is credited with the full uncapped amount on L1, while the CL only reflects the smaller, balance-capped deduction. This is Gwei created and paid to a party without any corresponding debit — a direct violation of the "Gwei created ... paid to a non-owner" Critical impact category.

### Likelihood Explanation
This requires no malicious peer, coalition, or client bug — it is a deterministic consequence of the spec logic whenever a `BuilderPendingWithdrawal.amount` exceeds the builder's balance at the time `get_builder_withdrawals` runs. The repo's own test suite demonstrates the condition is reachable and even exercises it directly (`test_builder_withdrawal_insufficient_balance`), and the "realistic bounds" variant shows it is not merely an artificial edge case (off by a small margin from `MIN_DEPOSIT_AMOUNT`). Whether the requesting mechanism validates `amount` against `builder.balance` strictly enough to make this unreachable in honest operation could not be fully confirmed in this pass; the enclosing gating (`can_builder_cover_bid`) protects new *bid acceptance*, not necessarily the state of `builder_pending_withdrawals` amounts by the time `process_withdrawals` runs, given the balance can move between queuing and processing.

### Recommendation
Cap the amount placed into the emitted `Withdrawal` in `get_builder_withdrawals` to the builder's actual available balance (mirroring what `get_builders_sweep_withdrawals` and the validator partial-withdrawal paths already do), i.e. `amount=min(withdrawal.amount, builder.balance)`, and keep the `state.builder_pending_withdrawals` slicing/queue removal unchanged so the request is still fully consumed. This makes the amount minted on the EL side always equal to the amount actually debited from the builder's CL balance.

### Proof of Concept
Using the repository's own test as a concrete demonstration:
1. Set `state.builders[0].balance = 1_000_000_000` (1 ETH).
2. Queue `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5_000_000_000, fee_recipient=addr)]`.
3. Run `process_withdrawals(state)`.
4. Result: `payload_expected_withdrawals[0].amount == 5_000_000_000` (what the EL will mint to `addr`), while `state.builders[0].balance == 0` (only 1 ETH actually removed).
5. Net effect: 4 ETH (`4_000_000_000` Gwei) is minted to `addr` on the execution layer with no corresponding consensus-layer debit — see the assertions in [4](#0-3) .

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
