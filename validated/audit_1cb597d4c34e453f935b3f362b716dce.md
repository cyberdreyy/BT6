### Title
Signer re-validation gap allows signing/pre-committing a block whose parent-tenure choice becomes invalid after proposal-time checks - (File: stacks-signer/src/v0/signer.rs)

### Summary
The full proposal-time validity check (`SortitionsView::check_proposal` in `chainstate/v1.rs` / `GlobalStateView::check_proposal` in `v2.rs`, invoked from `check_block_against_state`) evaluates several miner/tenure legitimacy rules — including the expensive `check_parent_tenure_choice` reorg-timing check — only once, when the proposal first arrives [1](#0-0) . Later re-validation points (`handle_block_validate_ok` and the pre-commit-threshold path in `handle_block_pre_commit`) call only `check_block_against_signer_db_state`, a strictly narrower check that re-verifies only "does this block confirm the tenure tip we expect" (`check_latest_block_in_tenure` / `check_tenure_change_confirms_parent`) and nothing about parent-tenure legitimacy [2](#0-1) .

### Finding Description
`check_block_against_state` (proposal arrival) delegates to `check_block_against_local_state`/`check_block_against_global_state`, which call the full `check_proposal` routine [3](#0-2) . In the v1 path, `check_proposal` runs `check_parent_tenure_choice` when the current sortition's consensus hash doesn't match the canonical tip and its `parent_tenure_id` doesn't match the tip's tenure — an "expensive check" done "only if we need to" — to decide if the sortition's chosen parent tenure is a legitimate (non-reorging) choice, marking the miner `InvalidatedBeforeFirstBlock`/rejecting with `ReorgNotAllowed` if not [4](#0-3) .

This check is time-sensitive: it factors in `first_proposal_burn_block_timing`, i.e., how much time has passed since the first proposal in a tenure, and can plausibly evaluate differently as time passes and the signer's view of competing tenures/sortitions accumulates.

However, `docs/signer-flows.md` explicitly documents that only `check_latest_block_in_tenure` is re-run at validate-ok time and at the moment of signing, never the full `check_proposal`/`check_parent_tenure_choice` logic [5](#0-4) , and that the tenure-change duplicate-block check is likewise "not re-run at validate-ok or at signing" [6](#0-5) . Concretely, `check_block_against_signer_db_state` implements only the tenure-change-confirms-parent and latest-block-in-tenure checks and returns `None` (pass) for everything else [7](#0-6) , and this is the *only* re-check performed both at `handle_block_validate_ok`'s recheck step and at the pre-commit-threshold recheck inside `handle_block_pre_commit` before a signature is produced [8](#0-7) .

Because the pre-commit round can take "minutes" between proposal-time validation and reaching the 70% threshold (explicitly called out in code comments) [9](#0-8) , the window during which `check_parent_tenure_choice`'s conclusion could change (e.g. because additional burn/sortition information arrives, or `first_proposal_burn_block_timing` elapses one way in the interim) is never re-examined before the signer commits to `mark_pre_committed` or `mark_locally_accepted`/signs.

### Impact Explanation
This is analogous to the vesting contract's `updateUserDeposit`/`claim` inconsistency: one code path (`claim`) is guarded by an `address(1)` check, but the companion path (`updateUserDeposit`) omits the equivalent check, breaking the intended equality between "ETH mode" and its supporting logic. Here, the proposal-time path (`check_block_against_state`/`check_proposal`) enforces the parent-tenure-choice/reorg-legitimacy invariant, but the two downstream paths that lead to an irreversible action (a signature) — `handle_block_validate_ok`'s recheck and the pre-commit-threshold recheck in `handle_block_pre_commit` — do not re-enforce that same invariant via `check_block_against_signer_db_state`. If the legitimacy of the parent-tenure choice can flip between proposal time and signing time, a signer could sign a block whose parent-tenure choice would have been rejected (`RejectReason::ReorgNotAllowed`) had the full check been re-run, i.e., a signer signing a block that is no longer valid under its own state-machine rules — matching the "signer signing an invalid/non-canonical/conflicting block" Critical impact class.

### Likelihood Explanation
Likelihood is limited by the fact this requires the underlying sortition/tenure state to genuinely change between proposal-time and pre-commit-threshold time (a normal consequence of chain activity and timing windows, not requiring a majority of signers or another signer's key), and by the fact that `handle_block_pre_commit`'s recheck already re-runs `check_block_against_signer_db_state`'s tenure-tip check, and a separate own-tenure/any-tenure conflict guard (`get_signed_conflicts`) runs at the pre-commit threshold as a partial substitute. I could not fully verify from the available code slices whether `check_parent_tenure_choice`'s specific reorg-legitimacy conclusion is otherwise made redundant by the conflict-guard step at signing (section 5 of the flow doc) or by node-side validation — this needs further tracing of `get_signed_conflicts`/`reorg_permit_stands` semantics against `check_parent_tenure_choice`'s specific invalidation trigger, which the current index did not fully expose.

### Recommendation
Re-run the full `check_proposal` (or at minimum the `check_parent_tenure_choice`/miner-status invalidation logic) as part of `check_block_against_signer_db_state`, both at `handle_block_validate_ok` and immediately before signing in `handle_block_pre_commit`, rather than relying solely on the narrower tenure-tip check, so that a change in parent-tenure legitimacy during the pre-commit window is caught before a signature is produced.

### Proof of Concept
Not independently reproducible from the available index: exploiting this requires driving the signer's local view of `first_proposal_burn_block_timing` / competing sortition data to change between proposal arrival and pre-commit-threshold crossing, which depends on live chain/burn-block timing not fully observable in the indexed code. This should be validated with a Devin session that can run the existing signer integration test harness (e.g. patterns similar to `stacks-node/src/tests/signer/v0/mod.rs`'s `block_proposal_rejection`) to attempt forcing a parent-tenure-choice flip mid pre-commit-round and confirm whether a signature is produced despite the flip.

```rust
                    })
                    .ok();
        }

        // Check if proposal can be rejected now if not valid against sortition view
        if let Some(sortition_state) = sortition_state {
            match sortition_state.check_proposal(

                block,
                true,
                self.global_state_evaluator
                    .get_global_tx_replay_set()
                    .unwrap_or_default(),
            ) {
                // Error validating block

                    warn!(

                    );
                    Some(self.create_block_rejection(RejectReason::ConnectivityIssues(e), block))

                Ok(_) => None,
            }
```

```rust
    fn check_block_against_signer_db_state(
        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,
                self.proposal_config.tenure_last_block_proposal_timeout,
                self.proposal_config.reorg_attempts_activity_timeout,
            ) {
                Ok(true) => return None,
                Ok(false) => {
                    return Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                }
                Err(e) => {
                    warn!("{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %proposed_block.block_id()
                    );
                    return Some(self.create_block_rejection(
                        RejectReason::ConnectivityIssues(
                            "error checking block proposal".to_string(),
                        ),
                        proposed_block,
                    ));
                }
            }
        }

        // Ensure that the block is the last block in the chain of its current tenure.
        match SortitionData::check_latest_block_in_tenure(
            &proposed_block.header.consensus_hash,
            proposed_block,
            &mut self.signer_db,
            stacks_client,
            self.proposal_config.tenure_last_block_proposal_timeout,
            self.proposal_config.reorg_attempts_activity_timeout,
        ) {
            Ok(is_latest) => {
                if !is_latest {
                    warn!(
                        "Miner's block proposal does not confirm as many blocks as we expect";

                        "proposed_block_signer_signature_hash" => %signer_signature_hash,

                        proposed_block,
                    ))
                } else {
                    None
                }
```

```markdown
`check_latest_block_in_tenure` answers "does this block confirm the tip we
expect?" and it runs in three places: at proposal arrival (inside
`check_proposal`), at validate-ok, and at the moment of signing. _Which_ tenure
it is asked about depends on the block: a tenure-change block is checked against
its **parent** tenure, every other block against its **own**. Never both. The
pivotal helper is `get_tenure_last_block_info`, which considers only blocks that
carry a signature (`get_last_signed_block`): a pre-commit never vetoes anything,
it only counts as miner activity.
```
