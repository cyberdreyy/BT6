### Title
Signer vote-flip lets a rejected block's counters wedge acceptance/rejection accounting - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` maintains a per-block `BlockStatus` with independent running counters `total_weight_approved` / `total_weight_rejected`, gated by two different collections (`gathered_signatures` for accept, `responded_signers` for reject-gating). A single signer that first broadcasts a rejection and later broadcasts a valid acceptance for the same block (a legitimate, permitted vote change, as documented in `docs/signer-flows.md`'s pre-commit/re-evaluation model) has its weight added to `total_weight_approved` without the earlier contribution ever being removed from `total_weight_rejected`. The two tallies are never reconciled against each other.

### Finding Description
In the accept branch of `StackerDBListener`'s message loop: [1](#0-0) 

weight is added to `total_weight_approved` gated solely by `block.gathered_signatures.contains_key(&slot_id)` — a map that is disjoint from `responded_signers`.

In the reject branch: [2](#0-1) 

weight is added to `total_weight_rejected` gated by `block.responded_signers.insert(slot_id)`.

Because `responded_signers` is shared as the reject-gate but the accept path never checks it (and never decrements `total_weight_rejected`), the following sequence is possible with a single signer's own two legitimately-signed messages:

1. Signer S rejects block B → `total_weight_rejected += S.weight`, `responded_signers` now contains S's slot.
2. Signer S later (still validly, per the documented reconsideration/reproposal flow, e.g. `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`) sends `BlockResponse::Accepted` for the same block → `total_weight_approved += S.weight` (via `gathered_signatures.contains_key` check, independent of `responded_signers`).

`total_weight_rejected` is never decremented, so S's weight is now counted simultaneously toward both the rejection tally and the acceptance tally in `BlockStatus`, which `signer_coordinator.rs` reads directly: [3](#0-2) 

This breaks the equality the coordinator relies on: `total_weight_approved` and `total_weight_rejected` are supposed to represent disjoint, currently-held positions of the signer set (their sum should never exceed `total_weight`), but the counters can now double-count one signer's weight across both camps. This stale-rejection accounting can cause the rejection branch (`total_weight_rejected + weight_threshold > total_weight`) to fire and hand back `NakamotoNodeError::SignersRejected` for a block that a signer has already switched to approving, permanently discarding a proposal (and its potentially-valid transactions/txid exclusions) that should have been eligible to reach the real 70% acceptance weight.

### Impact Explanation
This is a liveness wedge: a single signer's ordinary vote reconsideration (rejection followed later by acceptance, which the documented signer state machine explicitly permits and expects — see `should_reevaluate_reject_reason`/`should_reevaluate_block` in `docs/signer-flows.md` section 3) leaves stale weight in `total_weight_rejected` that the coordinator never purges. If enough vote-flips accumulate (even without malicious intent — normal chain-conflict resolution churn is exactly what section 5 of the docs describes as expected), the rejection threshold can be satisfied on stale data, causing the miner to treat a block as globally rejected and drop it, stalling tenure/block production without requiring any signer majority or key compromise — only the ordinary behavior of one signer changing its mind once.

### Likelihood Explanation
The reject→accept sequence is exactly the behavior the signer protocol is designed to allow (a signer initially rejects due to a transient condition, e.g. `NoSignerConsensus`/`ConnectivityIssues`, then later validates and accepts once conditions change, or reconsiders per `should_reevaluate_reject_reason`). No adversarial coordination, key compromise, or majority is required — it is a single well-behaved signer's second, later, validly-signed message that triggers the stale counter. This makes the likelihood high under ordinary operating conditions (e.g., transient node connectivity issues during the pre-commit window described in `docs/signer-flows.md` section 5).

### Recommendation
Track each slot's current vote (accept/reject) rather than two independently-gated monotonic counters. On receiving a new response for a slot that already has a recorded opposite response, first back out the previous contribution from the opposing tally before adding the new one — e.g. maintain a `HashMap<u32, Vote>` per block and recompute `total_weight_approved`/`total_weight_rejected` from that map, or explicitly subtract `signer_entry.weight` from `total_weight_rejected` when a slot that is present in `responded_signers` (from a prior reject) now submits an accept, and symmetrically remove from `gathered_signatures`/`total_weight_approved` if a slot that previously accepted now rejects.

### Proof of Concept
Not independently reproduced in this session (no test harness was executed); the flow is derived purely from static analysis of `StackerDBListener`'s message-handling branches shown above. A concrete PoC would:
1. Stand up a `StackerDBListener`/`SigningCoordinator` test harness with a small signer set.
2. Have signer S1 send `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for block B.
3. Have signer S1 later send `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same B.
4. Assert `block.total_weight_approved + block.total_weight_rejected` exceeds the weight that should be attributable given only one signer has ever responded, and that `total_weight_rejected` still includes S1's weight after S1's accept.

**Caveat**: I was not able to fully verify whether some other layer above `StackerDBListener` (e.g., in `stacks-signer` itself) prevents a signer from ever sending an Accept after a Reject for the same block hash (as opposed to only preventing accept-after-accept or reject-after-reject). The `stacks-signer/src/v0/signer.rs` state machine (`BlockInfo::check_state`) governs the *local* state transitions of the signer producing the message, and `should_reevaluate_reject_reason`/re-proposal handling suggested a reject→accept path is possible for certain reject reasons, but I did not exhaustively trace every `RejectReason` variant's re-evaluability. If it turns out no `RejectReason` ever permits moving from `LocallyRejected` to a subsequent local acceptance for the *same* block object, the practical trigger would be narrower than described (though the stale-counter code path in `stackerdb_listener.rs` itself is unconditional and does not check that on the node side).
