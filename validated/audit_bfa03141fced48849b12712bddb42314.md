### Title
GET /v2/external_initiators discloses `OutgoingToken` for all initiators regardless of ownership - ([File: core/web/external_initiators_controller.go])

### Finding Description
`ExternalInitiatorsController.Index` (`core/web/external_initiators_controller.go:50-59`) calls `eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)` with no per-caller ownership filter, then maps every returned record through `presenters.NewExternalInitiatorResource` (`core/web/presenters/external_initiators.go:67-77`). That presenter serializes `Name`, `URL`, `AccessKey`, `OutgoingToken`, `CreatedAt`, `UpdatedAt` for every initiator in the store — i.e. any caller permitted to hit this endpoint sees the `OutgoingToken` of every external initiator registered on the node, not just their own.

However, the specific claim in the question — that `OutgoingSecret`, `HashedSecret`, and `Salt` also leak through this endpoint — is not supported by the code. `ExternalInitiatorResource` (`core/web/presenters/external_initiators.go:57-65`) deliberately omits `OutgoingSecret`, `Salt`, and `HashedSecret`; only `ExternalInitiatorAuthentication` (used solely by `Create`, `core/web/external_initiators_controller.go:98`) carries those fields, and it is returned only once, at creation time, to the creator.

Additionally, the premise that a "Run-role EI holder" can invoke this route as an attacker does not match the authentication model: `GET /v2/external_initiators` is gated by the node's session/API-token authenticator (role-based: admin/edit/view), not by external-initiator HMAC credentials. External initiator credentials (`AccessKey`/`Secret`) are used to authenticate webhook trigger requests to job-run endpoints, not to call the general admin API. An external-initiator credential holder therefore has no path to reach this handler at all; only an already-authenticated node API user (minimally view-role) can call it.

### Impact Explanation
Within the node's own set of authenticated API users, a low-privileged (view-role) session/API-token holder can enumerate `OutgoingToken` values for external initiators they did not create, via `GET /v2/external_initiators`. This is a real but narrow cross-tenant information disclosure limited to a single field (`OutgoingToken`), not the full secret set (`OutgoingSecret`/`HashedSecret`/`Salt`) as hypothesized in the question. It does not by itself allow forging incoming EI requests (which require `AccessKey` + `Secret`/`HashedSecret`, not disclosed here), so its exploitability for request impersonation is limited unless `OutgoingToken` is independently used elsewhere as a bearer credential for outbound calls the node makes to the EI's webhook — which would need further tracing to confirm actual impersonation impact.

### Likelihood Explanation
Requires an authenticated node API session/token with at least the default view role — this is within the audit's allowed unprivileged-attacker class ("view/run-role user"), but it is not reachable by an unauthenticated external-initiator credential holder as the question assumes, since EI credentials don't authenticate to this route.

### Recommendation
Scope `Index` results to initiators owned/associated with the requesting principal (if such ownership model exists), or remove `OutgoingToken` from `ExternalInitiatorResource` entirely, exposing it only once at creation time via `ExternalInitiatorAuthentication`, consistent with how `OutgoingSecret`/`HashedSecret`/`Salt` are already handled.

### Proof of Concept
1. Create two external initiators A and B via `POST /v2/external_initiators` as an admin/edit-role session, capturing B's `outgoingToken` from the creation response.
2. Authenticate as a separate view-role session/API token (no relation to B).
3. Call `GET /v2/external_initiators` and assert the response includes an entry for initiator B whose `outgoingToken` field matches the value captured in step 1, while confirming `outgoingSecret`, `hashedSecret`, and `salt` are absent from the response for all entries (per `presenters.ExternalInitiatorResource`).
