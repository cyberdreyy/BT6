### Title
Stale per-epoch instant-withdraw basis is never cleared on claim, inflating default recovery and letting early claimants drain the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` records per-epoch receipt basis in `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`, but the funded claim path `claimInstantWithdrawRequest` only clears the aggregate `instantWithdrawsRequests[_user]` and never decrements either per-epoch mapping. This is the on-chain analog of prototype pollution: keyed state ("properties") is written under an epoch key and survives after the receipt it describes has already been paid and burned. If a default is later finalized while `pendingInstantWithdraws != 0`, the stale basis is double-counted into `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, pricing recovery against underlying that was already paid out.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestInstantWithdraw` writes `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` [1](#0-0) .
- `claimInstantWithdrawRequest` burns the receipt and zeroes only `instantWithdrawsRequests[_user]`; `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are left untouched [2](#0-1) .
- On default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` into the claim basis, and `_defaultPrefundedInstantReserve()` treats `instantBasis - pendingInstant` as underlying already held by the strategy, even though the already-claimed portion was transferred out [3](#0-2) [4](#0-3) .
- `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` on a denominator inflated by dead claims and a numerator inflated by phantom "prefunded" funds that no longer sit in the strategy [5](#0-4) .

The phantom entries have basis in `totalBasis` (denominator) but only partially real backing in `reserveAmount` (numerator). Every legitimately defaulted receipt — normal `withdrawsRequestsByEpoch`, unfunded instant receipts, and active AA/BB NAV via `defaultBBNav` — therefore gets a `recoveryPrice` computed as if the already-claimed funds were still claimable. Claims via `_claimDefaultedInstantWithdrawRequest` / `_transferDefaultRecovery` draw on the real underlying balance, so aggregate payouts exceed the true reserve; the stale-keyed user himself reverts on `instantWithdrawsRequests[_user] -= claimBasis` (underflow on zero) when trying to claim, but honest claimants who claim late get underpaid or blocked [6](#0-5) .

### Impact Explanation
Direct loss to defaulted receipt holders and tranche LPs: recovery reserve is mispriced against nonexistent backing. Early claimants (which can be the attacker, holding a genuine defaulted receipt created before default) receive more than their pro-rata share; the residual deficit falls on later claimants and on active LPs whose `lastNAVAA/lastNAVBB` were crystallized using the polluted basis. For a vault where the attacker claimed X of instant withdrawals pre-default and the epoch then defaults with Y still unfunded, the inflated `instantBasis` shifts up to X of phantom basis into the recovery computation, diluting every honest claim by roughly `X / totalBasis` — e.g., with X = 50% of the instant queue and instant claims = 30% of total basis, honest recovery is diluted ~15%. Alternatively `_transferDefaultRecovery` reverts once the real balance is exhausted, permanently freezing remaining claims.

### Likelihood Explanation
Requires: (a) an epoch where instant withdraws are only partially funded by the borrower so `pendingInstantWithdraws != 0` at stop time, (b) a funded user successfully claiming via `claimInstantWithdrawRequest` before the default, and (c) borrower default followed by `finalizeDefault`. Partial instant funding is a designed-for scenario (the prefunded-reserve logic exists precisely for it), and an attacker simply needs to request and claim an instant withdrawal in the same epoch — an unprivileged, KYC'd lender action. No privileged misbehavior needed; borrower honesty assumptions still allow non-malicious default.

### Recommendation
In `claimInstantWithdrawRequest` (and any funded instant claim path), clear the per-epoch keys alongside the aggregate: decrement `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` and `instantWithdrawClaimsByEpoch[requestEpoch]`, tracking the request epoch (e.g., via `lastWithdrawRequest`-style storage or a dedicated `lastInstantRequestEpoch` mapping) so the correct key is cleared. Verify `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only ever see live, unclaimed basis.

### Proof of Concept
Foundry fork sketch against a live `IdleCreditVault`/`IdleCDOEpochVariant` deployment:

```solidity
function testStaleInstantBasisInflatesRecovery() public {
    // 1. Alice (attacker) and Bob deposit AA in buffer phase.
    idleCDO.depositAA(100_000e6);      // alice
    depositAs(bob, 100_000e6);

    // 2. Alice requests instant withdraw of X before epoch start.
    vm.prank(alice);
    cdoEpoch.requestWithdraw(amountAA, AATranche); // routed to instant path
    // instantWithdrawsRequestsByEpoch[alice][E] and
    // instantWithdrawClaimsByEpoch[E] now hold X.

    // 3. Manager starts epoch; borrower sends only part of the instant
    //    liability, so pendingInstantWithdraws = Y > 0.
    vm.prank(manager); cdoEpoch.startEpoch();

    // 4. Alice claims the funded instant receipt.
    vm.prank(alice); cdoEpoch.claimInstantWithdrawRequest();
    // instantWithdrawsRequests[alice] == 0, receipt tokens burned,
    // but instantWithdrawClaimsByEpoch[E] still contains X  <-- bug

    // 5. Epoch ends; borrower fails to repay -> defaulted.
    vm.prank(manager); cdoEpoch.stopEpoch();  // triggers _handleBorrowerDefault

    // 6. Owner finalizes with a real recovered amount R.
    vm.prank(owner);
    cdoEpoch.finalizeDefault(R, recoverySource);

    // totalBasis included X (dead claim); prefundedReserve counted
    // X - related pending as held cash already paid to Alice.
    // 7. Alice's still-open defaulted normal receipt (or Bob's) claims
    //    at the inflated/diluted price; the last claimant reverts or is
    //    underpaid by ~X * recoveryPrice.
    assertGt(aliceProfit, honestShare); // Alice extracts > pro-rata
}
```

Key assertions: after step 4, `strategy.instantWithdrawClaimsByEpoch(epochNumber)` remains `X` while `instantWithdrawsRequests[alice] == 0`; after step 6, `defaultRecoveryPrice` differs from the value computed when the stale basis is excluded, and the sum of successful `claimWithdrawRequest`/`claimInstantWithdrawRequest` payouts exceeds `defaultRecoveryReserve` backing until the last claim reverts.

    _onlyIdleCDO();

    // burn strategy tokens from cdo

    // mint equal amount of strategy tokens to the user as receipt, useful in case of default

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;

    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests

  }

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
