### Title
Front-runnable `InitializeBuffer` instruction lets attacker hijack a newly created upgrade buffer's authority - (File: programs/bpf_loader/src/lib.rs)

### Summary
The `bpf_loader_upgradeable` builtin program's `InitializeBuffer` instruction handler sets the buffer account's authority to whatever pubkey is passed as instruction account index 1, without requiring that account (or the buffer account itself) to be a transaction signer. Any user can submit an `InitializeBuffer` instruction against any uninitialized buffer account owned by the loader, seizing control of the buffer's authority before the legitimate owner's initialization transaction lands — the same "unauthorized/unchecked initializer" root cause described in the referenced report.

### Finding Description
`process_loader_upgradeable_instruction` handles `UpgradeableLoaderInstruction::InitializeBuffer` as follows: [1](#0-0) 

It only checks that the buffer account state is `Uninitialized` and then unconditionally sets `authority_address` to the pubkey supplied at instruction-account index 1 — no `is_instruction_account_signer` check is performed on either the buffer account or the proposed authority. Contrast this with every other authority-mutating instruction in the same file (`Write`, `DeployWithMaxDataLen`, `SetAuthority`, `SetAuthorityChecked`), all of which explicitly require the current authority to sign: [2](#0-1) [3](#0-2) 

A buffer account is created by a separate `system_instruction::create_account` call that allocates space owned by `bpf_loader_upgradeable` (still in the `Uninitialized` state); `InitializeBuffer` is a distinct instruction that can be submitted in a separate transaction. The CLI's `create_buffer` helper happens to bundle both instructions into one transaction/message, but this is a client-side convention, not a protocol-enforced atomicity guarantee — nothing in the runtime prevents the two steps from being split, retried, or resubmitted independently, or prevents a third party from observing the pending/confirmed `CreateAccount` and racing the account owner's `InitializeBuffer` transaction with their own.

### Impact Explanation
An attacker who front-runs `InitializeBuffer` against a target's freshly created (but not yet initialized) buffer account becomes the buffer's authority:
- The legitimate deployer's subsequent `Write` and `DeployWithMaxDataLen` calls will fail with `IncorrectAuthority`/`InvalidArgument` since they check the (now attacker-controlled) `authority_address`, breaking the deployment flow (`programs/bpf_loader/src/lib.rs` lines 177-190, 242-250).
- Because the attacker is now the recorded authority, they can call `UpgradeableLoaderInstruction::Close` on the buffer and redirect its rent-exempt lamports to an account of their choosing via `common_close_account`, i.e. direct unauthorized fund extraction from the victim's paid-for buffer account: [4](#0-3) 

This is reachable by any ordinary user submitting a standard transaction against the `bpf_loader_upgradeable` builtin program — no special privileges, leaked keys, or node-level access required.

### Likelihood Explanation
Exploitation requires only observing a pending `CreateAccount` transaction that allocates a buffer owned by `bpf_loader_upgradeable` (via mempool/RPC monitoring or blockspace scanning) and racing an `InitializeBuffer` transaction against the newly visible account before the legitimate owner's own `InitializeBuffer` transaction confirms. This mirrors exactly the front-running mechanism described in the source report. Because the common CLI path bundles create+initialize atomically in one transaction, day-to-day `solana program deploy` usage reduces (but does not eliminate) the window; any integrator, SDK, or custom tooling that issues these as separate transactions (e.g., to support offline signing of the initialize step, as seen in `create_buffer_with_offline_authority` test helpers) is directly exposed.

### Recommendation
Require the intended authority (or the buffer account) to sign `InitializeBuffer`, mirroring the signer checks already present in `Write`, `DeployWithMaxDataLen`, and `SetAuthority`. At minimum, require `instruction_context.is_instruction_account_signer(1)?` (the proposed authority) before setting `authority_address`, closing the front-runnable initialization window.

### Proof of Concept
1. User submits `system_instruction::create_account` creating account `B`, owned by `bpf_loader_upgradeable`, sized for `UpgradeableLoaderState::Buffer`, in transaction T1.
2. Attacker observes T1 (mempool/RPC) and, once `B` exists on-chain in the `Uninitialized` state, immediately submits `UpgradeableLoaderInstruction::InitializeBuffer` naming `B` as account 0 and the attacker's own pubkey as account 1 — no signature from `B` or the attacker's pubkey is required by the handler (`programs/bpf_loader/src/lib.rs` lines 158-172).
3. This transaction lands before the user's own `InitializeBuffer` transaction; `B`'s state becomes `Buffer { authority_address: Some(attacker) }`.
4. The user's subsequent `Write`/`DeployWithMaxDataLen` calls fail with `IncorrectAuthority` (lines 177-190, 242-250), and the attacker calls `Close` on `B`, draining its rent-exempt lamports to themselves (lines 710-716).
