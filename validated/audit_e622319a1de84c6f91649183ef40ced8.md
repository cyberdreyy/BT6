## No Vulnerability found for this question.

The described scenario is not a protocol vulnerability. `action_add_key` (in `runtime/runtime/src/access_keys.rs`) simply writes a new access key onto whatever account is the receipt's receiver — it performs no separate "permission" check because the receipt itself only reaches this action after passing through the standard receipt-execution pipeline, where the actor executing the action is always the receiver account itself (a receipt's actions run with the receiver as actor; NEAR has no notion of one account executing an `AddKey` action against another account's storage without that account being the receiver) [1](#0-0) .

`Receipts::append_action_add_key_with_function_call` in `receipt_manager.rs` is a host-function-backed helper invoked when a **deployed contract itself** calls `promise_batch_action_add_key_with_function_call` from within its own wasm code [2](#0-1) . The resulting `AddKeyAction` is placed into a promise/receipt whose receiver is chosen when the promise batch was created — for the AddKey action to succeed at all, that receiver must be an account where the runtime allows the contract to add a key, and in every realistic deployment pattern (e.g., linkdrop-style contracts) the contract is deliberately targeting its **own** account. This is the intended, documented mechanism by which a contract manages its own access keys (e.g., distributing function-call-scoped keys to users) — it is not an authorization bypass of any invariant enforced by the protocol. The original caller's access-key permissions (e.g., a narrow `FunctionCall` key restricted to one method) govern only whether the caller was allowed to **submit the transaction that invokes that method**; they say nothing about what the contract's own logic is permitted to do once invoked, because contract logic executes with the contract as the acting party, by design (this is exactly how any contract method that transfers tokens, calls other contracts, or creates sub-accounts works).

The claimed "invariant" — that "a promise created by the receiver must not grant privileges the original caller's key lacked, on an account the caller doesn't own" — is not a real NEAR protocol invariant. Contracts are explicitly permitted, and expected, to grant new access keys, transfer balance, or create promises on their own account regardless of what access-key scope the invoking transaction used, because the account being modified is the contract's own account, not the caller's. If a contract author writes code that blindly forwards attacker-controlled `deposit`/`method_names`/`receiver_id` into `add_key_with_function_call` without validation, that is an application-level bug in that specific contract's business logic — not a bug in `nearcore`'s runtime, receipt manager, or access-key enforcement code. There is no reachable path here where the runtime itself fails to enforce a check that it is supposed to enforce; the "attacker" already fully controls what happens inside the method they are permitted to call, which is inherent to the smart-contract execution model, not a protocol-level authorization escalation across accounts. pub(crate) fn action_add_key(
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;
    } else {
        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}

    /// Attach the [`AddKeyAction`] action an existing receipt.
    ///
    /// The access key associated with the action will have the
    /// [`AccessKeyPermission::FunctionCall`] permission scope.
    ///
    /// # Arguments
    ///
    /// * `receipt_index` - an index of Receipt to append an action
    /// * `public_key` - a public key for an access key
    /// * `nonce` - a nonce
    /// * `allowance` - amount of tokens allowed to spend by this access key
    /// * `receiver_id` - a contract witch will be allowed to call with this access key
    /// * `method_names` - a list of method names is allowed to call with this access key (empty = any method)
    ///
    /// # Panics
    ///
    /// Panics if the `receipt_index` does not refer to a known receipt.
    pub(super) fn append_action_add_key_with_function_call(
        &mut self,
        receipt_index: ReceiptIndex,
        public_key: PublicKey,
        nonce: Nonce,
        allowance: Option<Balance>,
        receiver_id: AccountId,
        method_names: Vec<Vec<u8>>,
    ) -> Result<(), VMLogicError> {
        self.append_action(
            receipt_index,
            Action::AddKey(Box::new(AddKeyAction {
                public_key,
                access_key: AccessKey {
                    nonce,
                    permission: AccessKeyPermission::FunctionCall(FunctionCallPermission {
                        allowance,
                        receiver_id: receiver_id.into(),
                        method_names: method_names
                            .into_iter()
                            .map(|method_name| {
                                String::from_utf8(method_name)
                                    .map_err(|_| HostError::InvalidMethodName)
                            })
                            .collect::<std::result::Result<Vec<_>, _>>()?,
                    }),
                },
            })),
        );
        Ok(())
    }
