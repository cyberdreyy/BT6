### Title
Unauthenticated `/proposal_response` alternate channel lets a proposing miner forge `BlockValidateOk`/`BlockValidateReject` and drive an unvalidated block to signature — ([File: libsigner/src/events.rs])

### Summary
The stacks-signer's local HTTP event listener (`SignerEventReceiver`) accepts `BlockValidateOk`/`BlockValidateReject` payloads on `/proposal_response` — the messages that are supposed to represent the stacks-node's actual chainstate validation verdict for a block proposal — with **no authentication, no source verification, and no binding to a request the signer actually issued**. This is an unprotected alternate channel analogous to CWE-420: the "real" validation path (`stackslib/src/net/api/postblock_proposal.rs`, gated behind the node's `auth_token`) can be bypassed entirely by posting a forged verdict straight to the signer's own listener.

### Finding Description
`EventReceiver::next_event` in `libsigner/src/events.rs` dispatches purely on URL path with no auth/signature check: [1](#0-0) 

`process_event` then simply JSON-deserializes the HTTP body into `BlockValidateResponse` and converts it to a `SignerEvent`, again with zero provenance checks: [2](#0-1) 

The signer's own documentation acknowledges the endpoint is trust-based and dangerous if exposed: [3](#0-2) 

and the sample config binds this listener to `0.0.0.0:30000` by default: [4](#0-3) 

Compare this to the *primary* channel: the node's `/v3/block_proposal` endpoint that actually performs chainstate/tx validation is intended to be protected by `auth_token`/`connection_options`: [5](#0-4) 

`handle_block_validate_ok` in the signer does **not** require that the incoming `BlockValidateOk` correspond to a validation request the signer actually submitted. The `submitted_block_proposal` check only clears bookkeeping state if it happens to match — it is not a gate: [6](#0-5) 

The only requirement to accept the forged verdict is that the signer is already "tracking" the block (i.e., it has stored a `BlockInfo` in `Unprocessed`/pending state) via `block_lookup_by_reward_cycle`. That tracking state is trivially created by a miner: a miner needs only to broadcast *any* `BlockProposal` over the `.miners` StackerDB contract (an action any current sortition-winning miner — a "one-slot miner" — can already perform), which the signer stores via `handle_block_proposal → insert_block` per the documented flow: [7](#0-6) 

Once tracked, an attacker who can reach the signer's listening socket (bound to `0.0.0.0` per the sample config, or reachable through NAT/firewall misconfiguration that the project's own docs warn about) can POST a forged `BlockValidateOk` for that exact `signer_signature_hash` to `/proposal_response`, without the node ever validating it. The signer will then:
- accept it as if the node validated the block (`handle_block_validate_ok`),
- run `check_block_against_signer_db_state` (a much weaker, signer-local check that does not re-run miner-signature/tx-execution/chain-fit validation performed by `NakamotoBlockProposal::validate` in `postblock_proposal.rs`),
- `mark_pre_committed`, broadcast a pre-commit, and proceed toward `mark_locally_accepted`/signature if enough signers are similarly deceived or naturally miscount the fake OK, [8](#0-7) 

This breaks the fundamental equality the whole signer protocol depends on: *signed implies validated by the node* (section 4 of `docs/signer-flows.md`: "the signer re-checks its own DB state and only then advertises willingness to sign"). Here, "validated by the node" is forgeable by anyone who can reach the signer's socket, not just the node.

The same unauthenticated channel also accepts forged `BlockValidateReject` (`handle_block_validate_reject`), letting an attacker force `mark_locally_rejected` and a broadcast rejection for a block that the node never actually rejected — a liveness/censorship wedge against a valid, canonical block.

### Impact Explanation
This is Critical: it lets a single sortition-winning miner (who can already emit a proposal over `.miners`), combined with reachability to the signer's own event port, cause a signer to sign a block that was never actually validated by the stacks-node's chainstate/tx-execution logic — i.e., cause the signer to produce a signature over a potentially invalid/non-canonical block. It directly breaks the "signed vs validated" equality that `postblock_proposal.rs`'s node-side validation exists to enforce. The alternate `BlockValidateReject` injection also provides a High-severity liveness wedge, forcing rejection of legitimately valid blocks.

### Likelihood Explanation
Likelihood depends entirely on network exposure of the signer's event-receiver port. The project's own sample configuration binds it to `0.0.0.0:30000`, and `stacks-signer/src/lib.rs` explicitly warns operators about "communicating with an external node" exposing "sensitive data or functionalities to security risks if additional proper security checks are not integrated" — i.e., the maintainers are aware the channel is unauthenticated and rely entirely on network-level mitigation (firewalling/binding to localhost), exactly the same posture that made the ComfyUI-Manager alternate-channel bug exploitable in non-default deployments. Any signer operator running behind a reverse proxy, in a container/K8s network, or with a misconfigured firewall is exposed. No majority collusion or possession of another signer's key is required — only (1) the ability to have a block proposal tracked by the target signer (ordinary miner capability or StackerDB gossip) and (2) TCP reachability to the signer's listening port.

### Recommendation
- Require that inbound `/proposal_response`, `/new_burn_block`, `/new_block`, and `/stackerdb_chunks` requests be authenticated (shared-secret header, mirroring the node's `auth_token`/`connection_options` model) before `next_event`/`process_event` accept them in `libsigner/src/events.rs`.
- In `handle_block_validate_ok`/`handle_block_validate_reject` (`stacks-signer/src/v0/signer.rs`), hard-gate processing on `submitted_block_proposal` actually matching the incoming `signer_signature_hash` (and reject/ignore verdicts for hashes the signer never submitted for validation), instead of only using it for optional bookkeeping.
- Default the sample/reference configs to bind the signer's event endpoint to `127.0.0.1` rather than `0.0.0.0`, and make the warning in `stacks-signer/src/lib.rs` a hard failure/refusal to start when bound to a non-loopback address without an explicit auth token configured.

### Proof of Concept
1. Attacker controls a sortition-winning miner slot and broadcasts a `BlockProposal` for an invalid/non-canonical block `B` (with a bad tx or wrong parent) over the `.miners` StackerDB contract, causing target signers to store `BlockInfo` for `B` in `Unprocessed` state (per `handle_block_proposal`/`insert_block`, `docs/signer-flows.md:185-193`) while the real node validation is in flight/queued.
2. Attacker (same or colluding actor) obtains TCP reachability to a target signer's event-receiver port (default `0.0.0.0:30000` per `sample/conf/signer/mainnet-signer-conf.toml`).
3. Attacker sends:
   ```
   POST /proposal_response HTTP/1.1
   Host: <signer-ip>:30000
   Content-Type: application/json
   Content-Length: <n>

   {"result":"Ok","signer_signature_hash":"<hash of B>","cost":{...zero...},"size":0,"validation_time_ms":0,"replay_tx_hash":null,"replay_tx_exhausted":false}
   ```
   No `Authorization` header or token is required — confirmed by `libsigner/src/events.rs:398-459` performing no auth check on any of the dispatched paths.
4. `next_event`/`process_event` deserialize this into `SignerEvent::BlockValidationResponse` with no origin check (`libsigner/src/events.rs:519-542`) and forward it into the signer runloop.
5. `handle_block_validate_ok` (`stacks-signer/src/v0/signer.rs:1882-1975`) processes it as a genuine node verdict, runs the weaker `check_block_against_signer_db_state`, and if that passes, calls `mark_pre_committed` and broadcasts a pre-commit for block `B` — even though the node's real `NakamotoBlockProposal::validate` (`stackslib/src/net/api/postblock_proposal.rs`) never ran or would have rejected it.

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
