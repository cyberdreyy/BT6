### Title
Dust instant withdrawal request blocks all users' instant claims for the epoch - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
Analogous to the PearVault griefing where inflating `totalPendingShares` disables direct withdrawals for everyone, an unprivileged tranche holder can submit a dust `requestWithdraw` during the buffer period. At `startEpoch`, if `_pendingInstant()` exceeds the contract's idle underlying balance (`pendingInstant > totUnderlyings`), the function returns early without setting `allowInstantWithdraw = true`. Because `claimInstantWithdrawRequest()` reverts while `allowInstantWithdraw` is false and while any pending instant request remains unfunded, **all** users' instant claims — including requests that were already fully funded in prior epochs — revert with `NotAllowed` until `instantWithdrawDeadline` passes and the manager calls `getInstantWithdrawFunds()`. A single dust-sized request can therefore freeze every user's instant exit path for the duration of the delay window.

### Finding Description
- During the buffer period, any tranche holder can call `requestWithdraw(_amount, tranche)` in `IdleCDOEpochVariant`, which records an instant/normal withdrawal request in `IdleCreditVault` (`instantWithdrawsRequests`/`pendingInstantWithdraws`).
- In `startEpoch` (contracts/IdleCDOEpochVariant.sol ~L279-292):

```solidity
uint256 pendingInstant = _pendingInstant();
uint256 totUnderlyings = _contractTokenBalance(token);
_strategy.collectInstantWithdrawFunds(pendingInstant > totUnderlyings ? totUnderlyings : pendingInstant);
if (pendingInstant > totUnderlyings) {
  _startEpochProgrammableBorrower(_pendingWithdraws);
  return;                       // allowInstantWithdraw stays false
}
allowInstantWithdraw = true;
```

- The early-return branch is taken whenever `pendingInstant > totUnderlyings`. When the CDO has forwarded all idle liquidity to the borrower in the previous epoch, `totUnderlyings` is ~0, so a request as small as 1 wei of strategy-token value forces this branch.
- The regression test confirms the global-freeze behavior: with a funded claim from a prior epoch plus one new unfunded request, `claimInstantWithdrawRequest()` reverts for everyone until the delay elapses and `getInstantWithdrawFunds()` is invoked (test/foundry/IdleCreditVault.t.sol L4881-4888, L4516-4528).
- Like the PearVault fix, there is no check at request time that the vault can actually satisfy the request, and there is no per-user isolation: one unfunded request poisons the shared `allowInstantWithdraw`/`pendingClaims` gate used by every claimant.

### Impact Explanation
Temporary freezing of withdrawals for all users holding funded instant-withdraw receipts. The freeze lasts at least `instantWithdrawDelay` (e.g., 3 days) plus the latency of a privileged `getInstantWithdrawFunds`/`processWithdrawalClaims` call. Users expecting to exit at epoch start are forced to wait or bear the risk that the epoch's borrower repayment path fails in the interim. Quantified loss: delayed access to 100% of funded instant claims for at least one delay window; grief cost to the attacker is only the tranche tokens backing the dust request, which remain claimable.

### Likelihood Explanation
Moderate. The attack requires the attacker to hold (or briefly acquire) a tranche position and time the request within the buffer period before `startEpoch`. It is most effective when buffer liquidity is fully lent out (the normal operating state), making even minimal requests sufficient to trigger `pendingInstant > totUnderlyings`. KYC/whitelist gating does not mitigate it since any allowed lender qualifies as an attacker under the threat model. Honest privileged roles eventually unfreeze claims, matching the "temporary freezing" acceptance criterion.

### Recommendation
- Do not gate already-funded claims behind global pending-request state: track per-request funding status so `claimInstantWithdrawRequest()` pays out receipts whose underlyings were already collected, regardless of newer unfunded requests.
- Alternatively, at `startEpoch`, still set `allowInstantWithdraw = true` for the funded portion (compare each claimant's basis against `totUnderlyings` collected), or reject `requestWithdraw` amounts that cannot be satisfied only from blocking the shared flag — mirroring the PearVault fix of adding a balance-sufficiency check at request time.
- At minimum, keep `allowInstantWithdraw` true when `totUnderlyings > 0` and serve claims pro-rata/first-come rather than reverting all claims.

### Proof of Concept
Foundry-style scenario (modeled on `testClaimInstantWithdrawRequestAfterAnEpochWithInstantWithdraw` in test/foundry/IdleCreditVault.t.sol):

```solidity
// Setup: deposits made, epoch 0 runs and stops; instant withdrawals enabled
// (apr dropped below instantWithdrawMinAprDiff) so requests are instant.
cdoEpoch.setInstantWithdrawParams(instantDelay, 1e18, false);

// user1 requests instant withdraw during buffer period of epoch N
vm.prank(user1);
uint256 req1 = cdoEpoch.requestWithdraw(user1Bal, address(AAtranche));

// start epoch N+1: all idle underlyings go to borrower after funding req1
vm.prank(manager);
cdoEpoch.startEpoch();
vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds();   // req1 is now funded

// epoch N+1 stops; buffer period of epoch N+2 begins
_stopEpochAndCheckPrices(...);

// ATTACK: griefing user deposits dust earlier and requests withdraw now.
// Contract holds ~0 idle underlyings (all lent to borrower).
vm.prank(attacker);
cdoEpoch.requestWithdraw(1, address(AAtranche));  // dust

// start epoch N+2 -> pendingInstant (1 wei) > totUnderlyings (0)
// -> early return, allowInstantWithdraw stays false
vm.prank(manager);
cdoEpoch.startEpoch();

// user1's *already funded* claim now reverts for everyone
vm.expectRevert(NotAllowed.selector);
vm.prank(user1);
cdoEpoch.claimInstantWithdrawRequest();   // frozen

// Only recovers after the full instant delay + privileged manager action
vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds();
vm.prank(user1);
cdoEpoch.claimInstantWithdrawRequest();   // finally succeeds
```

A confirming PoC should verify the revert path there directly.
