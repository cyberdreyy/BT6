### Title
Post-finalization instant-withdraw receipts pollute the defaulted-epoch claim key and drain `defaultRecoveryReserve` - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The prototype-pollution bug class — writing attacker-chosen data into an existing key of a shared structure — maps here onto the epoch-keyed receipt mappings. `requestInstantWithdraw` indexes `instantWithdrawsRequestsByEpoch[_user][epochNumber]` but, unlike `requestWithdraw`, never checks `defaultRecoveryFinalized`. After a default is finalized, `epochNumber` remains equal to `defaultRecoveryEpoch`, so a new instant-withdraw receipt is written into the *already-consumed* epoch key. `claimInstantWithdrawRequest` then treats that fresh receipt as a defaulted-epoch claim and pays it from `defaultRecoveryReserve` at `defaultRecoveryPrice`, stealing recovery funds reserved for genuine defaulted claimants. [1](#0-0) [2](#0-1) 

### Finding Description
`requestWithdraw` explicitly guards the post-default path: after `defaultRecoveryFinalized` it rejects users with any open request and routes new requests into `postDefaultRequests` at an already-haircut price. [3](#0-2)  `requestInstantWithdraw` has no equivalent branch — it unconditionally mints the receipt and writes `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`. [1](#0-0) 

`epochNumber` is only bumped inside `deposit` during `stopEpoch`. [4](#0-3)  A defaulted vault does not run further epochs, so `epochNumber == defaultRecoveryEpoch` forever after finalization (`finalizeDefaultRecovery` stores `defaultRecoveryEpoch = epochNumber`). [5](#0-4) 

On the claim side, `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. That helper reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — the key the attacker just polluted — burns the receipt tokens, and calls `_transferDefaultRecovery`, which decrements and pays out of `defaultRecoveryReserve` with no per-user solvency check. [6](#0-5) [2](#0-1) [7](#0-6) 

The only mitigation nearby is the `claimBasis >= pending ? 0 : pending - claimBasis` clamp on `pendingInstantWithdraws`, which protects the counter, not the reserve — the payout itself is `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` regardless of whether the receipt existed at finalization time.

### Impact Explanation
Any tranche-token holder can, after `finalizeDefaultRecovery`, request an instant withdrawal (burning `x` strategy tokens, which post-default are priced at or near `defaultRecoveryPrice`) and immediately claim `x * defaultRecoveryPrice / 1e18` underlying from `defaultRecoveryReserve`. Since their receipt was minted *after* the reserve was sized to `totalBasis` at finalization, every wei they withdraw is wei that belonged to holders of genuine defaulted-epoch receipts. Repeating or sizing the request to the reserve lets an attacker drain the entire recovery reserve, leaving legitimate defaulted claimants with reverts on `defaultRecoveryReserve -= _amount` underflow — direct theft plus permanent freezing of the remaining recovery claims. Broken invariant: "one receipt one payout" and reserve isolation for finalized default accounting. Quantified loss: up to `defaultRecoveryReserve` minus the attacker's own legitimate share, i.e., effectively all recovered funds, for the cost of tranche tokens purchased at post-default (haircutted) prices — a near-risk-free arbitrage whenever `defaultRecoveryPrice > 0`. [8](#0-7) 

### Likelihood Explanation
Likelihood is gated by two conditions, both plausible:

1. `defaultInstantWithdrawsFinalized` must be true, i.e., `pendingInstantWithdraws != 0` at finalization — this happens whenever instant withdrawals were requested in the default epoch and only partially funded, a common state when a borrower defaults mid-queue. [9](#0-8) 
2. The IdleCDO must still route `requestInstantWithdraw` to the strategy after default. The strategy side imposes no `defaulted()`/`defaultRecoveryFinalized` check of its own, so the vulnerability exists at the vault layer; whether the CDO's instant-withdraw entry point reverts on defaulted vaults should be confirmed in the PoC (the vault's asymmetry between `requestWithdraw` and `requestInstantWithdraw` strongly suggests the guard was simply forgotten).

No privileged role is required — the attacker is any tranche-token holder (unprivileged per the threat model), and `requestInstantWithdraw`/`claimInstantWithdrawRequest` are reachable through the CDO's public withdraw flow in the defaulted phase. The reserve guard in `_transferFundedClaim` does not apply because the payout path is `_transferDefaultRecovery`. [10](#0-9) 

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert, or route the request into a separate post-default bucket that is claimed via `_transferFundedClaim` only after being funded — never into `instantWithdrawsRequestsByEpoch[_user][epochNumber]` while `epochNumber == defaultRecoveryEpoch`. [1](#0-0)  Additionally, harden `_claimDefaultedInstantWithdrawRequest`/`_claimDefaultedWithdrawRequest` by snapshotting the claimable basis at finalization time (e.g., a `defaultedReceiptsFinalized` marker or comparing `block.timestamp`/a frozen request set) so receipts created after `finalizeDefaultRecovery` can never be paid from `defaultRecoveryReserve`. [2](#0-1) 

### Proof of Concept
Foundry fork test (against a mainnet fork block where a credit vault has defaulted, or a local harness reproducing `finalizeDefaultRecovery`):

```solidity
// test/foundry/PostDefaultInstantPollution.t.sol
function test_postDefaultInstantRequestDrainsRecoveryReserve() public {
    // --- fixture ---
    // epoch N running with pendingInstantWithdraws > 0 partially funded.
    // borrower defaults; owner calls finalizeDefault / finalizeDefaultRecovery:
    //   defaultRecoveryFinalized = true
    //   defaultInstantWithdrawsFinalized = true   (pendingInstantWithdraws != 0)
    //   defaultRecoveryReserve = R, defaultRecoveryPrice = P (< 1e18)
    //   epochNumber == defaultRecoveryEpoch == N

    address attacker = makeAddr("attacker");

    // attacker buys/holds tranche tokens post-default and requests instant
    // withdraw of `amt` via the CDO (requestInstantWithdraw path).
    uint256 amt = 1_000e6; // sized to available tranche tokens
    vm.prank(address(cdo));
    vault.requestInstantWithdraw(amt, attacker);
    // writes instantWithdrawsRequestsByEpoch[attacker][N] += amt
    // because epochNumber is still N == defaultRecoveryEpoch

    uint256 reserveBefore = vault.defaultRecoveryReserve();

    // claim: _claimDefaultedInstantWithdrawRequest reads the polluted key and
    // pays amt * P / 1e18 straight out of defaultRecoveryReserve
    vm.prank(address(cdo));
    vault.claimInstantWithdrawRequest(attacker);

    uint256 stolen = amt * vault.defaultRecoveryPrice() / 1e18;
    assertEq(vault.defaultRecoveryReserve(), reserveBefore - stolen);
    assertEq(underlying.balanceOf(attacker), stolen);

    // legitimate defaulted-epoch claimant now underflows / is left short:
    vm.expectRevert(); // defaultRecoveryReserve -= amount underflows
    vm.prank(address(cdo));
    vault.claimInstantWithdrawRequest(honestDefaultedUser);
}
```

Key assertions: `instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch]` is nonzero for a receipt created *after* finalization; `defaultRecoveryReserve` decreases by the attacker's payout; honest defaulted claimants' subsequent claims revert or are underpaid. The one assumption to verify in the harness is that the IdleCDO exposes `requestInstantWithdraw` to users while `defaulted()` — if the CDO already hard-blocks it, severity drops, but the missing strategy-level guard remains a latent defect given `requestWithdraw`'s explicit post-default branch.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
