### Title
Unvalidated fee parameters in `createDstEscrow` cause permanent underflow-revert of `EscrowDst.withdraw`/`publicWithdraw` - (File: contracts/BaseEscrowFactory.sol, contracts/EscrowDst.sol)

### Summary
The external report's root cause is a subtraction in a hot-path function (`circulating_supply() = totalSupply - veTotalSupply`) that can underflow and revert when the subtrahend can exceed the minuend, permanently DOSing a periodic protocol action. This repository has an analogous unchecked subtraction in `EscrowDst._withdraw`, where `immutables.amount - integratorFeeAmount - protocolFeeAmount` can underflow if the fee amounts exceed `amount`. Unlike the `_postInteraction` path (which validates fees via `InvalidFeeAmounts`), the `createDstEscrow` entry point accepts `dstImmutables.parameters` directly from an unprivileged caller with no such validation.

### Finding Description
`BaseEscrowFactory._postInteraction` (contracts/BaseEscrowFactory.sol) computes `integratorFeeAmount`/`protocolFeeAmount` via `FeeTaker._getFeeAmounts` and explicitly guards: [1](#0-0) 
This ensures the emitted `immutablesComplement.parameters` (fee amounts) are always strictly less than `takingAmount` for the "correct" flow.

However, `createDstEscrow` is a separate, independently callable entry point that takes `dstImmutables` — including the ABI-encoded `parameters` field containing `protocolFeeAmount`/`integratorFeeAmount` — directly from `msg.sender` with **no equivalent fee-vs-amount check**: [2](#0-1) 

Later, `EscrowDst._withdraw` blindly subtracts the fee amounts from `immutables.amount`: [3](#0-2) 

If a caller supplies `parameters` such that `integratorFeeAmount + protocolFeeAmount > immutables.amount`, line 92 (`uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;`) underflows and reverts unconditionally (Solidity 0.8 checked arithmetic), for both `withdraw` and `publicWithdraw`, since both route through `_withdraw`.

This is the same bug class as the Minter finding: an unchecked/unvalidated subtraction between two independently-controllable values, reachable without any bounds check, causing an unconditional revert of the withdrawal function for the life of the escrow.

### Impact Explanation
Any unprivileged caller can invoke `createDstEscrow` directly (bypassing the validated `_postInteraction`/`FeeTaker` computation entirely) with a crafted `parameters` payload. Once such a destination escrow is deployed and funded, `withdraw`/`publicWithdraw` will always revert due to the underflow, and the only remaining recovery path is `cancel()` (which returns funds to `taker`, not `maker`) after the cancellation timelock elapses. This is a temporary freezing of the escrowed funds during the live swap lifecycle — the intended recipient cannot claim funds by revealing the correct secret during the withdrawal window, matching the "Medium: smart contract unable to operate because required token/native balances can be broken by an unprivileged actor" bounty bucket.

### Likelihood Explanation
Because `parameters` (including the fee fields) is part of the immutables hash used as the CREATE2 salt, a maliciously-parameterized escrow deploys to a different address than the one an honest counterparty would compute from the correctly-emitted `SrcEscrowCreated` event. A maker who verifies the escrow address before revealing the secret (as recommended in this repo's documented security considerations) would detect the mismatch and not interact with the tampered escrow, largely limiting the practical blast radius to self-griefing by the caller who funded it. This significantly reduces real-world likelihood/severity versus the original Minter bug, which affected a shared, unavoidable protocol-wide function.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`, validating that `protocolFeeAmount + integratorFeeAmount < dstImmutables.amount` (decoded from `dstImmutables.parameters`) before deploying/funding the escrow, and/or make `EscrowDst._withdraw`'s subtraction defensive (e.g., clamp or revert with a clear, guarded check rather than relying on implicit underflow revert).

### Proof of Concept
1. Attacker (any address) calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.amount = 100`, `dstImmutables.parameters = abi.encode(protocolFeeAmount = 60, integratorFeeAmount = 60, protocolFeeRecipient, integratorFeeRecipient)`, funding it with the required `msg.value`/token transfer per [2](#0-1) .
2. After the withdrawal timelock, anyone with the secret calls `withdraw`/`publicWithdraw`, which reaches `_withdraw`: [4](#0-3) 
3. `amount = 100 - 60 - 60` underflows and reverts, so `withdraw`/`publicWithdraw` can never succeed for this escrow instance; only `cancel()` (returning funds to `taker`) works after the cancellation timelock.

Note: I could not fully verify the exact byte-layout parsing of `dstImmutables.parameters` in `ImmutablesLib` beyond the offsets shown (protocolFeeAmount at 0x20, integratorFeeAmount at 0x40) since the full file contents were only partially retrieved via search; a Devin session with full repo access would be needed to confirm the exact ABI encoding expected by `createDstEscrow` callers versus `ImmutablesLib`.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
