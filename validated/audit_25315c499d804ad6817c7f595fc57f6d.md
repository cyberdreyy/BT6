### Title
Lockup factory lets an unprivileged caller override the canonical staking-pool whitelist, letting the lockup owner fake staked balances and release un-vested/locked NEAR early - ([File: lockup-factory/src/lib.rs])

### Summary
The pyUmbral report describes a class of bug where a critical trust parameter (the curve) is not pinned to a single canonical source, but can be silently overridden by an optional argument, so the system ends up trusting the wrong configuration. The same pattern exists in `LockupFactory::create`, where the staking-pool whitelist account — a security-critical trust anchor that the lockup contract relies on to decide which staking-pool contract's data it will trust — is not fixed to the factory's canonical value but can be freely overridden by the (unprivileged) caller of `create`.

### Finding Description
`LockupFactory::create` is a public, `#[payable]` method with no caller restriction: any account can call it as long as it attaches `MIN_ATTACHED_BALANCE`. [1](#0-0) 

Instead of always using the factory's canonical `whitelist_account_id` set at `#[init]` time, `create` lets the caller pass an arbitrary `whitelist_account_id` argument that fully replaces the canonical one for the deployed lockup: [2](#0-1) 

This attacker-supplied account ID is embedded as `staking_pool_whitelist_account_id` in the `LockupArgs` sent to the newly deployed lockup contract, becoming the sole source of truth the lockup contract will trust for whitelist checks going forward: [3](#0-2) 

Inside the lockup contract, `select_staking_pool` (an owner method) checks the chosen staking pool exclusively against this `staking_pool_whitelist_account_id`: [4](#0-3) 

and `on_whitelist_is_whitelisted` blindly trusts whatever boolean the whitelist contract returns: [5](#0-4) 

Because the "whitelist" is just an `AccountId` supplied unrestricted by the lockup creator (who is also free to set themselves as `owner_account_id`), an attacker can:
1. Deploy a malicious contract implementing `is_whitelisted(staking_pool_account_id) -> bool` that always returns `true`.
2. Call `LockupFactory::create(..., whitelist_account_id: Some(my_malicious_whitelist))`, becoming owner of a freshly deployed lockup with a `vesting_schedule` (locked/unvested tokens).
3. As owner, call `select_staking_pool` pointing at a second malicious contract they control that implements the staking-pool ABI (`get_account_total_balance`, `deposit_and_stake`, etc.) but returns arbitrary, inflated balances.
4. Call `refresh_staking_pool_balance` / rely on `on_get_account_total_balance`, which updates `known_deposited_balance` from the value reported by the (attacker-controlled) "staking pool," inflating the lockup's tracked staked balance beyond what was ever actually transferred to a real staking pool.

This breaks the intended custody binding that the lockup's owner-balance computation is supposed to preserve: `get_owners_balance` / `get_liquid_owners_balance` are meant to equal *(vested amount actually recoverable from real, whitelisted staking activity)*. By forging the reported staked balance through a whitelist that was never actually the foundation-controlled `staking-pool-whitelist` account, the owner can make the contract's internal accounting diverge from the NEAR genuinely available/vested, and use `transfer`/`withdraw`-type owner methods (bounded by this inflated tracked balance) to move out tokens that should still be locked/unvested — an early release of locked/unvested tokens, i.e. exactly the "locked or unvested tokens released early" Critical impact category.

### Impact Explanation
The staking-pool whitelist is meant to be a single canonical trust anchor (analogous to the "one canonical curve configuration" recommendation in the report) that guarantees a lockup contract only interacts with staking pools vetted by the foundation. Allowing the `whitelist_account_id` to be supplied per-lockup by an arbitrary, unprivileged caller means the entitlement ("this staking pool is trusted") is granted by the same party who benefits from lying about it, breaking the authorization boundary the whitelist exists to enforce. This can let a lockup owner report/realize balances that were never staked with a genuine, whitelisted validator, letting them extract funds inconsistent with the actual vesting/locking schedule — a Critical loss category (early release of locked/unvested tokens and/or divergence between recorded staked balance and NEAR actually held/staked).

### Likelihood Explanation
Any account can trigger this: `create` has no `assert_called_by_foundation`/owner check, only a minimum deposit requirement, and the `whitelist_account_id` override is a normal optional argument exposed in the public API and already exercised by the test `test_create_lockup_with_custom_whitelist_success`. The only requirement is deploying two small helper contracts (fake whitelist + fake staking pool), which is a well within reach of any unprivileged NEAR account.

### Recommendation
- Do not allow the lockup creator to override the whitelist account; always use the factory's canonical `whitelist_account_id` set at `#[init]`, deleting the `whitelist_account_id: Option<ValidAccountId>` parameter from `create` (mirrors the report's recommendation to "define which curve/whitelist the system is using in a single, canonical location").
- If per-lockup customization is genuinely required, restrict it to a caller authorized by the foundation (e.g. `assert_called_by_foundation`), not to any depositor.
- Ensure the lockup contract's owner-balance/liquid-balance computation cannot be inflated purely by a self-reported "staking pool" balance without independent verification, and make illegal states (a lockup whose whitelist differs from the foundation's canonical whitelist) unrepresentable.

### Proof of Concept
1. Attacker deploys `FakeWhitelist` contract implementing `is_whitelisted(_: AccountId) -> bool { true }`.
2. Attacker deploys `FakeStakingPool` contract implementing the staking-pool ABI (`deposit_and_stake`, `get_account_total_balance`, etc.), returning an arbitrarily large balance for any account.
3. Attacker calls:
   ```
   near call lockup-factory create '{
     "owner_account_id": "attacker",
     "lockup_duration": "0",
     "vesting_schedule": {...long vesting...},
     "whitelist_account_id": "fake-whitelist.attacker.near"
   }' --accountId=attacker --deposit=35 --amount=<MIN_ATTACHED_BALANCE>
   ```
   (per `lockup-factory/src/lib.rs:107-133`).
4. New lockup contract is deployed with `staking_pool_whitelist_account_id = "fake-whitelist.attacker.near"` (`lockup-factory/src/lib.rs:141-157`).
5. Attacker (as owner) calls `select_staking_pool("fake-staking-pool.attacker.near")`; the check against `fake-whitelist` returns `true` (`lockup/src/owner.rs:12-41`, `lockup/src/owner_callbacks.rs:6-25`), so the fake pool is accepted with no foundation vetting.
6. Attacker calls `deposit_and_stake`/`refresh_staking_pool_balance`; the fake pool reports an inflated `get_account_total_balance`, inflating `known_deposited_balance` and thus `get_owners_balance`/`get_liquid_owners_balance` beyond what vesting should allow.
7. Attacker calls `transfer`/withdraw methods to move out NEAR inconsistent with the real vesting schedule.

Note: I was not able to fully trace the exact numeric bound checks in `get_owners_balance`/`get_liquid_owners_balance`/`withdraw` inside `lockup/src/lib.rs` and `lockup/src/getters.rs` within the remaining tool budget (the grep hits were not opened), so the precise degree to which the withdrawal amount is capped by the contract's real NEAR balance vs. the reported/inflated staking balance should be verified against `lockup/src/getters.rs` and `lockup/src/owner.rs` before treating the PoC as fully proven end-to-end.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

    pub fn select_staking_pool(&mut self, staking_pool_account_id: AccountId) -> Promise {
        self.assert_owner();
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The staking pool account ID is invalid"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();

        env::log(
            format!(
                "Selecting staking pool @{}. Going to check whitelist first.",
                staking_pool_account_id
            )
            .as_bytes(),
        );

        ext_whitelist::is_whitelisted(
            staking_pool_account_id.clone(),
            &self.staking_pool_whitelist_account_id,
            NO_DEPOSIT,
            gas::whitelist::IS_WHITELISTED,
        )
        .then(ext_self_owner::on_whitelist_is_whitelisted(
            staking_pool_account_id,
            &env::current_account_id(),
            NO_DEPOSIT,
            gas::owner_callbacks::ON_WHITELIST_IS_WHITELISTED,
        ))
    }

    /// Called after a given `staking_pool_account_id` was checked in the whitelist.
    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,
        staking_pool_account_id: AccountId,
    ) -> bool {
        assert_self();
        assert!(
            is_whitelisted,
            "The given staking pool account ID is not whitelisted"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();
        self.staking_information = Some(StakingInformation {
            staking_pool_account_id,
            status: TransactionStatus::Idle,
            deposit_amount: 0.into(),
        });
        true
    }
