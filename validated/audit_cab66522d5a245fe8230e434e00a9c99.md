### Title
Withdrawal requests revert on underflow when upfront management fee exceeds principal plus interest - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` charges an upfront management fee for the entire waiting period of the receipt (one full epoch plus any remaining buffer time). The fee is computed independently of the requested principal, so if the admin-configured `managementFee` rate and `epochDuration + bufferPeriod` are large enough, `totalFees` can exceed `principal + interest`, causing an underflow at `principal + interest - totalFees` and permanently reverting every withdrawal request for affected users. This is the same bug class as the Buffer finding: an unbounded/sub-linear fee parameter combined with a subtraction, where a sub-component fee can exceed the amount it is deducted from, bricking a user-facing entry point.

### Finding Description
In `requestWithdraw`, the receipt amount is computed as:

```solidity
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;   // line ~776
``` [1](#0-0) 

`_totalWithdrawFees` returns at least the full upfront management fee on `principal` for a duration of `epochDuration` plus any remaining buffer time:

```solidity
uint256 _mgmtFee = _calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration());
return _mgmtFee >= _interest ? _mgmtFee : _interest - _netGainAfterFees(_interest, _mgmtFee);
``` [2](#0-1) 

The management fee is linear in duration: `_nav * managementFee * _duration / (FULL_ALLOC * 365 days)` [3](#0-2) , and `_withdrawRequestManagementFeeDuration` returns `epochDuration + (epochEndDate + bufferPeriod - block.timestamp)`, i.e., up to `epochDuration + bufferPeriod` [4](#0-3) .

Therefore, whenever `managementFee * (epochDuration + bufferPeriod) > FULL_ALLOC * 365 days` — e.g., a 50% management fee with a 2-year epoch, or a 10% fee with a >10-year epoch — `_mgmtFee > principal`, and since `totalFees >= _mgmtFee`, the subtraction `principal + interest - totalFees` underflows (Solidity 0.8 checked arithmetic) and the whole `requestWithdraw` reverts. Because `_amount = 0` defaults to the full user balance, there is no smaller-amount escape: any withdrawal attempt hits the same arithmetic.

The mirror path in `maxWithdrawable` has the identical issue: `currentUnderlyings -= _calculateManagementFee(currentUnderlyings, block.timestamp - latestHarvestBlock)` underflows once accrued management fee exceeds the position NAV [5](#0-4) .

Like the Buffer `referrerTierStep`, `managementFee` is a privileged-set parameter; the code relies on the setter bounds rather than checking that the deducted fee stays below the base it is taken from at the point of subtraction — so even parameter combinations the setter legitimately accepts (long epochs) can satisfy the revert condition.

### Impact Explanation
All withdrawal requests revert for every holder whose `principal + interest < totalFees`, i.e., effectively all users once `managementFee * duration > FULL_ALLOC * 365 days` holds. Tranche tokens cannot be converted to receipts, `claimWithdrawRequest`/`claimInstantWithdrawRequest` are unreachable for new requests, and user funds are frozen in the vault for the entire period the configuration persists. Direct DoS of the exit path with fund impact (temporary/permanent freezing depending on whether the owner can lower parameters before epoch transitions lock them in).

### Likelihood Explanation
Requires `managementFee`, `epochDuration`, and `bufferPeriod` to be set to values whose product exceeds one year's worth of fees. These are owner/manager-set values analogous to `ReferralStorage.configure` in the original finding: the arithmetic itself has no guard that the fee stays below the base at subtraction time. No existing guard (skim, flags, epoch gating) prevents the underflow — `_skimDonatedAssets` and `_updateAccounting` run before the subtraction but don't bound `totalFees`. Honest admin configuration of long-duration epochs is a realistic deployment scenario for credit vaults.

### Recommendation
Bound `totalFees` at the point of subtraction rather than only in the setter — e.g., `totalFees = Math.min(totalFees, principal + interest)` or cap the management fee as `min(_mgmtFee, principal + interest)` inside `_totalWithdrawFees` — and/or enforce `managementFee * (epochDuration + bufferPeriod) < FULL_ALLOC * 365 days` in `setFeeParams`/`setEpochParams`. Apply the same cap to the `currentUnderlyings -= _calculateManagementFee(...)` subtraction in `maxWithdrawable`.

### Proof of Concept
Conceptual Foundry flow (against `test/foundry/IdleCreditVault.t.sol` scaffolding):

```solidity
// owner configures a high management fee and manager a long epoch
_setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 50_000);      // managementFee = 50% of FULL_ALLOC/yr
vm.prank(manager);
cdoEpoch.setEpochParams(3 * 365 days, 30 days);          // duration*fee > 365d

uint256 trancheAmount = idleCDO.depositAA(10_000 * ONE_SCALE);

// _mgmtFee = principal * 0.5 * (1095+30)/365 >> principal
// totalFees >= _mgmtFee > principal + interest
// -> principal + interest - totalFees underflows
vm.expectRevert();
cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));
```

The revert leaves the user's tranche balance locked; repeating with `_amount = 0` (full balance) also reverts. Note: I could not fully verify the exact upper bounds enforced by `setFeeParams`/`setEpochParams` in this pass; the PoC assumes the setter accepts the parameters above — if it caps `managementFee` strictly below the break-even product for allowed epoch durations, the residual risk reduces to the `maxWithdrawable` accrued-fee path and setter-acceptance should be verified against `IdleCDOCreditVault.setFeeParams` directly.
