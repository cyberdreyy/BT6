### Title
Unrestricted strategy-token donations are counted as NAV and permanently strand withdrawal funding - (File: `contracts/IdleCDOCreditVault.sol`)

### Summary
`IdleCDOCreditVault.getContractValue()` treats the complete `strategyToken` balance held by the CDO as NAV, while `IdleCDOEpochVariant._skimDonatedAssets()` removes only unsolicited underlying-token transfers. A withdrawal receipt is itself a freely transferable strategy token: `IdleCreditVault` burns the CDO's principal tokens and mints receipt tokens to the requester. If the requester transfers that receipt back to the CDO, the next accounting update records the transfer as a new gain even though the withdrawal request remains outstanding. A later withdrawal can burn the donated receipt as active NAV, leaving the original `withdrawsRequests` entry with no receipt tokens available to burn. The resulting funded claim can never be paid.

### Finding Description
`getContractValue()` returns `strategyToken.balanceOf(CDO) + token.balanceOf(CDO) - unclaimedFees`. [1](#0-0) 

`_skimDonatedAssets()` transfers only the underlying `token` balance to `feeReceiver`; it does not identify or remove donated `strategyToken` balances. [2](#0-1) 

Withdrawal requests call `_skimDonatedAssets()` and `_updateAccounting()`, so a donated receipt is crystallized as NAV during any subsequent request. [3](#0-2) 

When a withdrawal is requested, `IdleCreditVault.requestWithdraw()` burns `principal` strategy tokens from the CDO and mints receipt tokens to the user. [4](#0-3) 

Because `IdleCreditVault` inherits `ERC20Upgradeable` and the former `canTransfer` control is deprecated, a receipt holder can directly transfer those minted tokens back to the CDO. [5](#0-4) [6](#0-5) 

During accounting, the increased raw strategy-token balance is treated as a gain, potentially accrued as fees and distributed into tranche NAV. [7](#0-6) 

Later claims burn the user's full recorded withdrawal amount before paying it. Once the original receipt has been donated and burned as part of another withdrawal, the recorded claim remains but the user lacks the required receipt tokens, making the claim permanently unexecutable. [8](#0-7) 

### Impact Explanation
The broken invariant is **one receipt, one payout** and the corresponding solvency invariant that each pending withdrawal basis remains represented by transferable receipt tokens.

A donor can create a pending withdrawal receipt, send it to the CDO, and let the protocol count it again as active NAV. A subsequent withdrawal burns that same token balance without clearing the donor's original `withdrawsRequests` entry. After the epoch is funded, `pendingWithdraws` has already been decreased by `collectWithdrawFunds()`, but the donor's claim cannot complete because `_claimFundedWithdrawRequest()` first attempts to burn receipt tokens that no longer exist.

At minimum, the amount of the donated receipt `R` becomes permanently frozen: the strategy can collect `R` underlying for the pending basis, while the claim's burn precondition can never succeed. Repeated or larger donations can strand a correspondingly larger amount of borrower-funded underlying. This is a protocol insolvency/permanent-freeze issue rather than an accounting display issue.

### Likelihood Explanation
The attack requires no privileged role. A KYC-passing tranche holder can request a withdrawal during the buffer period, receive the strategy-token receipt, and send it directly to the CDO. Any later withdrawal interaction crystallizes the donated balance through `_updateAccounting()`; the sequence does not depend on malicious owner, manager, borrower, oracle, or ERC4626 behavior.

The relevant phase is the normal buffer phase in fixed-APR mode. No flash-loan dependency exists: the ERC20 receipt itself is sufficient to perform the donation.

### Recommendation
Do not derive active NAV from the CDO's raw `strategyToken` balance.

Track active strategy-token principal in dedicated CDO accounting, or mark withdrawal receipts as a separate non-transferable receipt token. At minimum:

1. Keep a `trackedStrategyTokenBalance` updated by strategy deposits, mints, burns, default finalization, and loss burns.
2. Use that tracked balance for NAV and active-loss basis rather than `balanceOf(address(this))`.
3. Add a strategy-token skim/rescue path for unsolicited receipts so they cannot enter NAV.
4. Revert or isolate direct transfers of withdrawal receipts to the CDO.
5. Add regression tests asserting that donating a withdrawal receipt does not change `virtualPrice`, `lastNAVAA`, `lastNAVBB`, or pending-claim backing.

### Proof of Concept
This test is intended to be added to `test/foundry/IdleCreditVault.t.sol` and uses that file's existing fixture and helper variables.

```solidity
function testStrategyTokenReceiptDonationBreaksClaimBacking() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 half = amount / 2;

    // Buffer phase: create two active tranche positions.
    idleCDO.depositAA(amount);

    address donor = address(this);
    address nextWithdrawer = makeAddr("nextWithdrawer");

    // First withdrawal: CDO principal is burned and donor receives receipt tokens.
    uint256 donatedReceipt = cdoEpoch.requestWithdraw(half, address(AAtranche));
    IdleCreditVault creditVault = IdleCreditVault(cdoEpoch.strategy());

    assertEq(creditVault.balanceOf(donor), donatedReceipt);
    assertEq(creditVault.withdrawsRequests(donor), donatedReceipt);

    // The ERC20 receipt can be sent directly to the CDO.
    creditVault.transfer(address(cdoEpoch), donatedReceipt);
    assertEq(creditVault.balanceOf(donor), 0);

    // Move the remaining active tranche position to another wallet so the
    // second request does not aggregate with the donor's original request.
    AAtranche.transfer(nextWithdrawer, half);

    // This call crystallizes the donated receipt as NAV, then burns active
    // CDO strategy tokens to mint the next withdrawal receipt.
    vm.prank(nextWithdrawer);
    uint256 secondReceipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // The phantom donation inflated the next request above its original NAV.
    assertGt(secondReceipt, half);

    // The original request basis remains recorded, but its receipt was burned.
    assertEq(creditVault.withdrawsRequests(donor), donatedReceipt);
    assertEq(creditVault.balanceOf(donor), 0);

    // Once funded, `_claimFundedWithdrawRequest` will try to burn
    // `withdrawsRequests[donor]` from `donor` and always revert.
    vm.expectRevert();
    creditVault.claimWithdrawRequest(donor);
}
```

The decisive state is `withdrawsRequests[donor] == donatedReceipt` while `strategyToken.balanceOf(donor) == 0`. Under normal accounting, the pending request and its receipt balance remain paired; after the donation and subsequent withdrawal, the receipt has been burned as active NAV while the request basis survives.
