### Title
Path traversal in kv-v2 Vault engine `dataPath` allows escaping the configured mount/project secret prefix - ([File: helpers/vault/secret_engines/kv_v2/engine.go])

### Summary
`engine.dataPath` (and `metadataPath`) builds the Vault request path with `path.Join(e.path, "data", p)`, where `p` is the job-controlled `secrets.vault.path` value (which can itself embed job/CI variables). Because `path.Join`/`filepath.Clean` resolves `..` segments purely lexically with no bounds check against `e.path`, a value like `../../team-b/secret` can walk the resolved path outside `e.path`'s intended namespace.

### Finding Description
`engine.Get(path)` calls `e.dataPath(path)` at helpers/vault/secret_engines/kv_v2/engine.go:29-56, which returns `path.Join(e.path, "data", p)`. `path.Join` internally calls `Clean`, which collapses `..` without ever validating that the result stays under the `e.path` prefix. For example, with `e.path = "kv/team-a"` and `p = "../../team-b/secret"`:

`path.Join("kv/team-a", "data", "../../team-b/secret")` → Clean(`"kv/team-a/data/../../team-b/secret"`) → `"kv/team-b/secret"`.

The resulting path no longer contains `team-a` at all — it lands under an entirely different, sibling secret path. This value comes from `resolver.Resolve` (helpers/secrets/resolvers/vault/resolver.go:38-63), which passes the job's `spec.Secret.Vault` configuration (populated from `.gitlab-ci.yml` `secrets:vault:path`, with CI variables interpolated into it) down through `service.defaultVault.GetField` to `engine.Get`. No sanitization/allow-listing of `p` occurs anywhere in this call chain before it reaches `path.Join`.

### Impact Explanation
If the Vault auth role/policy bound to the runner's JWT auth method is scoped more broadly than the single intended mount subpath (e.g., grants read on the whole `kv/` mount or a prefix shared by multiple projects/teams), an unprivileged pipeline author can set `secrets.vault.path` (directly, or via a job variable interpolated into it) to a `../`-laden value and have the runner issue a Vault read against a sibling project's secret path instead of its own, resulting in cross-project secret exfiltration.

### Likelihood Explanation
Exploitability depends entirely on the external precondition that Vault's ACL/policy for the runner's auth role is broader than the intended per-project mount subpath — this is explicitly listed as a precondition in the question and is a plausible/common misconfiguration (e.g., a single shared JWT role scoped at `kv/*` rather than per-project). Given that precondition, the traversal itself is trivially reachable and repeatable by any pipeline author who can edit `.gitlab-ci.yml` or influence a CI variable used in the vault path — no special runner or GitLab privileges are required. If, however, the Vault policy is correctly scoped to `kv/team-a/data/*` (least privilege), Vault itself will reject the traversed read with 403, independent of this bug.

### Recommendation
Sanitize and validate `p` in `engine.dataPath`/`metadataPath` (and generally in the generic engine) before joining: reject any path containing `..` segments, or resolve the joined path and assert it still has `e.path` (with a trailing separator) as a strict prefix, failing the request otherwise. This provides defense-in-depth so Runner does not construct out-of-scope Vault requests even under permissive Vault policies.

### Proof of Concept
```go
func TestDataPath_NoTraversalEscape(t *testing.T) {
    e := &engine{path: "kv/team-a"}
    got := e.dataPath("../../team-b/secret")
    assert.True(t, strings.HasPrefix(got, "kv/team-a/data/"),
        "resolved path %q escaped engine mount prefix kv/team-a/data/", got)
}
```
Expected (current) result: the assertion fails, because `dataPath` returns `kv/team-b/secret`, proving the traversal escapes `e.path`. A companion integration test can point `e.client` at a mocked Vault server with a policy allowing `kv/*` and confirm the read actually returns `team-b`'s secret data when `secrets.vault.path: "../../team-b/secret"` is set in a job's `.gitlab-ci.yml`. func (e *engine) Get(path string) (map[string]interface{}, error) {
	secret, err := e.client.Read(e.dataPath(path))
	if err != nil {
		return nil, fmt.Errorf("reading from Vault: %w", err)
	}

	if secret == nil {
		return nil, nil
	}

	data := secret.Data()
	if data == nil {
		return nil, nil
	}

	if raw, ok := data["data"]; !ok || raw == nil {
		return nil, nil
	}

	result, ok := data["data"].(map[string]interface{})
	if !ok {
		return nil, fmt.Errorf("data for key %s cannot be coerced to 'map[string]any'", path)
	}
	return result, nil
}

func (e *engine) dataPath(p string) string {
	return path.Join(e.path, "data", p)
}

func (v *resolver) Resolve() (string, error) {
	if !v.IsSupported() {
		return "", secrets.NewResolvingUnsupportedSecretError(resolverName)
	}

	secret := v.secret.Vault

	url := secret.Server.URL
	namespace := secret.Server.Namespace

	s, err := newVaultService(url, namespace, secret)
	if err != nil {
		return "", classifyError(err)
	}

	data, err := s.GetField(secret, secret)
	if err != nil {
		return "", classifyError(err)
	}

	if data == nil {
		return "", common.ErrSecretNotFound
	}

	return fmt.Sprintf("%v", data), nil
}
