### Title
KYC-excluded lender can fully exit the vault by transferring tranche tokens to an allowed address - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` enforces Keyring KYC gating only at the entry points that initiate an action (`_deposit`, `requestWithdraw`, `depositDuringEpoch`, queue requests) via `isWalletAllowed(msg.sender)`. It never enforces the credential on the movement of the tranche tokens themselves. `IdleCDOTranche` is a plain transferable ERC20, and the `WriteOffEscrow` flow proves this: a wallet with `checkCredential == false` can receive tranche tokens (`testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw`). Consequently, a lender whose credential is revoked keeps full economic control of its position: it transfers its AA/BB tranche tokens to any credential-passing address it controls, which then calls `requestWithdraw` and later `claimWithdrawRequest` on its behalf. This mirrors the external report exactly — an exclusion bit enforced on the account but not on token transfer/delegation is trivially bypassed by moving the tokens. The same gap exists at the receipt layer: `IdleCreditVault` receipts are address-bound (`_transfer` reverts unless `msg.sender == idleCDO`), but `claimWithdrawRequest`/`claimInstantWithdrawRequest` pay the receipt holder with no `isWalletAllowed` re-check, so a wallet that was credential-passing at `requestWithdraw` time and revoked before `stopEpoch` still claims.

### Finding Description
In `requestWithdraw` the only wallet gate is:

```solidity
// contracts/IdleCDOEpochVariant.sol:739-744
_checkNotAllowed(
  (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
  !isWalletAllowed(msg.sender)
);
```

`_deposit` applies the same check only to `msg.sender` (line 645). Neither `IdleCDOTranche` nor any `_beforeTokenTransfer` hook consults the Keyring checker on `transfer`/`transferFrom`, and `fullfillWriteOffRequest` in `WriteOffEscrow` transfers tranche tokens to arbitrary buyers — the test at `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:247-294` confirms a non-allowed buyer holds the tranches and is only blocked when it later calls `requestWithdraw`. So the exclusion is bound to the *caller identity at request time*, not to the *claim or the token*. Two bypass paths exist, matching the report's delegation/transfer split:

1. **Transfer path**: revoked lender sends tranche tokens to a second KYC'd wallet under its control (or sells them through `WriteOffEscrow` to a KYC'd buyer). The new holder calls `requestWithdraw`/`deposit`-adjacent flows normally and the value exits.
2. **Stale-claim path**: lender requests a withdrawal while allowed, gets revoked mid-flight, and still calls `claimWithdrawRequest` — `IdleCreditVault._transferWithdraw` pays `withdrawsRequests[_user]` to `msg.sender` with no credential check, and receipts cannot be transferred (`_transfer` only allows the CDO), so revocation can never claw back a pending receipt.

The broken invariant is access control: `excluded`/`not-allowed` is a property of the *position*, not of a single transaction's caller, but the code treats it as the latter.

### Impact Explanation
A lender that Keyring has revoked (sanctions, failed re-screening, comped credential) retains the ability to withdraw 100% of principal plus accrued interest from the pool by routing through a second allowed wallet — i.e., the exclusion provides no containment whatsoever. If revocation is used to freeze assets pending compliance action, those funds are unrecoverable: they can be out the door in the same transaction in which the credential is observed revoked. Quantified loss: the revoked lender's entire tranche balance (`_userTrancheBal`) converted at `_tranchePrice`, e.g., a revoked AA holder with 1,000,000 tranche tokens exits ~1,000,000e6 underlying through the KYC'd proxy.

### Likelihood Explanation
High. Requirements: (a) the attacker controls or contracts with one credential-passing wallet — KYC is per-wallet, and nothing prevents an entity from maintaining several; (b) tranche tokens are freely transferable, which is already the case and is exercised by `WriteOffEscrow`. The stale-claim variant requires only that revocation happen between `requestWithdraw` and `claimWithdrawRequest`, a window of at least one full epoch, making it a likely occurrence in practice rather than an edge case. No privileged cooperation is needed.

### Recommendation
Treat exclusion as a property of the position, not the caller:

- Add a `_beforeTokenTransfer` (or `_transfer` override) on `IdleCDOTranche` that reverts when `from` or `to` fails `isWalletAllowed`, so revoked holders cannot move tokens to a clean wallet. If free transferability for secondary sales is a hard requirement, enforce the check in `WriteOffEscrow.fullfillWriteOffRequest` and on `requestWithdraw` for the *tranche owner* rather than only `msg.sender`.
- Re-check `isWalletAllowed(msg.sender)` inside `claimWithdrawRequest`/`claimInstantWithdrawRequest` before paying out, so a credential revoked while a receipt is pending blocks the claim; optionally add a privileged `sweepRevokedClaim` that redirects the payout to `feeReceiver`/owner.
- Apply the same re-check to `IdleCDOEpochQueue.requestWithdraw` claim/cancel paths for consistency.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
function testRevokedLenderExitsViaSecondWallet() external {
  address keyring = address(1);
  vm.prank(owner);
  cdoEpoch.setKeyringParams(keyring, 1);

  // Both wallets pass KYC initially; attacker controls both.
  address walletA = makeAddr("walletA");
  address walletB = makeAddr("walletB");
  vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector), abi.encode(true));

  // walletA deposits and receives AA tranches.
  _depositWithUser(walletA, 100_000 * ONE_SCALE, true);
  uint256 trancheBal = IERC20(AAtranche).balanceOf(walletA);

  // Keyring revokes walletA's credential (mock per-address via expectCall filtering,
  // or use a minimal mock contract returning false for walletA, true otherwise).
  KeyringMock km = new KeyringMock();
  km.setAllowed(walletA, false);
  km.setAllowed(walletB, true);
  vm.prank(owner);
  cdoEpoch.setKeyringParams(address(km), 1);

  // walletA can no longer request a withdraw...
  vm.prank(walletA);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));

  // ...but simply transfers the tranche tokens to its second, still-KYC'd wallet.
  vm.prank(walletA);
  IERC20(AAtranche).transfer(walletB, trancheBal);

  // walletB requests and later claims the full withdrawal: exclusion bypassed.
  vm.prank(walletB);
  cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
  _startEpochAndCheckPrices(1);

  uint256 balPre = underlying.balanceOf(walletB);
  vm.prank(walletB);
  cdoEpoch.claimWithdrawRequest();
  assertGt(underlying.balanceOf(walletB) - balPre, 0, "revoked lender exited via proxy wallet");
}
```

For the stale-claim variant: `requestWithdraw` while allowed, mock `checkCredential(walletA) == false`, then `claimWithdrawRequest` from `walletA` — it succeeds because the strategy pays `withdrawsRequests[msg.sender]` with no KYC re-check.

Caveat: I was unable to read `claimWithdrawRequest`/`claimInstantWithdrawRequest` bodies in `IdleCreditVault` within the available iterations; the stale-claim claim is inferred from `withdrawsRequests(_user)` bookkeeping and `_transferWithdraw` (`contracts/strategies/idle/IdleCreditVault.sol:901-907`), which contain no credential check. The transfer-path bypass is fully confirmed by the WriteOffEscrow test showing tranche tokens landing in a non-allowed wallet.
