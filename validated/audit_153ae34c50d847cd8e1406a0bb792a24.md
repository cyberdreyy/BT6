### Title
EI-authenticated requests are treated as authenticated Users, allowing External Initiators to trigger arbitrary jobs by int32 ID despite the "EIs not allowed" comment - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}` for every successfully authenticated EI request, so `auth.GetAuthenticatedUser(c)` returns `ok=true` for EI callers exactly as it does for real session/token users. `PipelineRunsController.Create`'s `isUser` gate — intended per its own comment to block External Initiators from triggering jobs via numeric int32 IDs — is therefore dead code, and any EI credential holder can invoke `RunJobV2` on an arbitrary job ID.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in `core/web/router.go:450-456` under the `userOrEI` group, authenticated via `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, or `auth.AuthenticateBySession`, and wrapped only with `auth.RequiresRunRole`. [1](#0-0) 

Inside `AuthenticateExternalInitiator`, after validating the EI's access key/secret, the code sets both the EI context key and a synthetic run-role `User`: [2](#0-1) 

`GetAuthenticatedUser` simply reads `SessionUserKey` from context with no distinction as to how it was populated: [3](#0-2) 

In `PipelineRunsController.Create`, the code explicitly comments that only real Users (not EIs) should be allowed to trigger jobs via int32 IDs, gating on `isUser`: [4](#0-3) 

Because `AuthenticateExternalInitiator` unconditionally injects a synthetic `User` object into the same context key checked by `isUser`, this check can never distinguish an EI-authenticated request from a genuine user/token session. The only surviving check that could have differentiated the two paths — matching against the job's UUID for webhook-type jobs — has been removed along with the `Webhook` job type (line 104-107: any UUID-shaped ID is now rejected outright with `job.ErrJobTypeRemoved`). Consequently, for EI-authenticated requests with a numeric `ID`, the `isUser` branch is entered and `prc.App.RunJobV2(ctx, jobID, nil)` is invoked directly with attacker-supplied `jobID`, with no verification that the job is associated with the calling External Initiator at all.

### Impact Explanation
An attacker holding only an External Initiator credential (access key/secret pair, which is a lower-trust credential intended to be scoped to triggering that EI's own webhook job) can trigger **any** job on the node by numeric ID, not just the job(s) associated with their EI registration. This is an authorization-bypass / privilege-escalation issue: a low-privilege credential (EI, meant only to invoke pre-registered webhook flows) gains equivalent capability to a run-role user account, enabling unauthorized job runs (e.g., triggering OCR/VRF/direct-request jobs, causing unwanted on-chain transactions, fund movement via triggered pipeline tasks, or unwanted external HTTP calls performed by the job's tasks) that were not intended to be reachable by that credential.

### Likelihood Explanation
Exploitability requires only a valid External Initiator access key/secret — a credential class explicitly designed to be more restricted than a user session/API token. No admin/session/API-token access is needed. The request is a straightforward, repeatable POST to `/v2/jobs/:ID/runs` with the EI headers and a numeric job ID; no race conditions, no privileged intermediate state. This makes it fully and reliably reproducible by anyone possessing a single EI credential (e.g., a compromised/leaked external-initiator secret, or a legitimately-provisioned but restricted EI integration turned malicious).

### Recommendation
Distinguish EI-authenticated requests from real user sessions/tokens explicitly, e.g. check `auth.GetAuthenticatedExternalInitiator(c)` (or a dedicated flag) before allowing `isUser`-gated execution, and reject/limit EI-triggered runs to only the job(s) legitimately tied to that External Initiator (as was presumably intended pre-webhook-removal), rather than relying on the shared `SessionUserKey`/`isUser` check which EI authentication itself populates.

### Proof of Concept
Go handler-level integration test plan (using existing test harness patterns from `core/web/pipeline_runs_controller_test.go`):
1. Set up a test app with a registered `ExternalInitiator` and a separate job (int32 ID `X`) unrelated to that EI, mocking/stubbing `App.RunJobV2` to record calls.
2. Build a gin test context authenticated purely via `auth.AuthenticateExternalInitiator` (send `X-External-Initiator-AccessKey`/`X-External-Initiator-Secret` headers matching the EI, no session cookie, no API token).
3. POST to `/v2/jobs/{X}/runs` (or call `PipelineRunsController.Create` directly with that context).
4. Assert `auth.GetAuthenticatedUser(c)` returns `(user, true)` with `user.Role == UserRoleRun`.
5. Assert `App.RunJobV2` was invoked with `jobID == X`, and the response is `200`/job-run resource — proving the "EIs not allowed" comment is inaccurate and EI credentials can trigger arbitrary int32-ID jobs.
