### Title
Exact-asset ERC4626 withdrawal with zero slippage tolerance permanently reverts `onStopEpoch` when the configured vault charges any withdrawal fee - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` frees epoch-end liquidity with `vault.withdraw(shortfall, address(this), address(this))`, which demands an *exact* asset amount out — the ERC4626 equivalent of `xcall(..., 0)` zero-slippage. Any ERC4626 vault that deducts a withdrawal fee (or any share/asset rounding gap) needs to burn more shares than the share-value of `shortfall`; when `shortfall` equals the whole position the withdrawal reverts, is caught, and rethrown as `StopEpochVaultLiquidityUnavailable`, so `stopEpoch` can never complete while funds sit in the vault.

### Finding Description
The bug class from the report — a hardcoded zero tolerance on an external settlement call — maps to `onStopEpoch`'s liquidity pull in `ProgrammableBorrower.sol:239-254`:

```solidity
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

- `withdraw(assets)` in ERC4626 means "send me exactly `assets`, burn whatever shares it costs." That is a zero-tolerance exchange-rate parameter, just like `xcall` slippage `0`: the call succeeds only if share-value covers `assets` with nothing to spare.
- The guard `shortfall > _currentVaultAssets() return true` only checks the *asset-denominated* share value (`convertToAssets(balanceOf)`). With a nonzero withdrawal fee, `maxWithdraw` is strictly less than `convertToAssets(balanceOf)`; withdrawing the full covered `shortfall` exceeds `maxWithdraw` and reverts. Even a 1-wei rounding gap between `convertToAssets` and `previewWithdraw` suffices at the boundary.
- The revert is rethrown as `StopEpochVaultLiquidityUnavailable`, so the whole `stopEpoch` on the CDO reverts every time it is attempted while the vault sleeve is the liquidity source. The same zero-tolerance pattern exists in `_borrow` at `ProgrammableBorrower.sol:452` (`vault.withdraw(shortfall, ...)`, uncaught), making borrower draws revert whenever the vault's effective rate moved against the position since `_currentVaultAssets()` was consistent.

### Impact Explanation
While the configured ERC4626 vault charges a withdrawal fee or its share price produces boundary rounding, the running epoch cannot be stopped: `stopEpoch` always reverts inside the `onStopEpoch` hook, so pending withdraw requests (`epochPendingWithdraws`) cannot be funded and tranche holders' epoch-end redemptions are frozen. Freezing persists until the owner/manager manually calls `emergencyExitVault` to redeem the whole position (temporary freezing of user funds, bounded by operator intervention). Quantified impact: the entire vault-held sleeve plus all pending withdraw-request amounts are unreachable by the epoch flow.

### Likelihood Explanation
- Requires no attacker action: it triggers deterministically the first time `stopEpoch` must pull a shortfall equal to (or fee-adjusted beyond) the vault share value — i.e., whenever most of the liquidity is parked in the vault, which is the normal design of `onStartEpoch` (`_depositToVault(underlyingToken.balanceOf(...), 0)` at line 216 parks all idle cash).
- ERC4626 vaults with withdrawal fees (e.g., the Instadapp Lite ETHV2 vault already integrated in this codebase, whose `withdrawalFeePercentage` causes redeem reverts per `test/foundry/InstadappLiteETHV2Strategy.t.sol:293-317`) are a realistic configuration target; the protocol itself acknowledges fee-bearing vaults elsewhere via `liquidationToleranceBps`.
- The `_borrow` path additionally lets any authorized executor hit the revert simply by calling `executeBorrow` at a moment when the vault's effective rate dipped (e.g., right after a fee event), denying draws — but the freezing impact stands via `stopEpoch`.

### Recommendation
Use share-denominated redemption instead of exact-asset withdrawal, mirroring "set a nonzero slippage":
- In `onStopEpoch`, compute shares via `vault.previewWithdraw(shortfall)` (rounds up), or simply `vault.redeem(sharesNeeded, ...)`/`redeem(vault.balanceOf(this))` for full unwinds, then transfer what was actually received; treat the residual gap through the existing accounting (`epochWithdrawnFromVault += assets actually received`).
- Alternatively wrap the call so that on revert it falls back to `redeem`ing the full share balance, letting the CDO's downstream `transferFrom` decide solvency instead of reverting unconditionally.
- Apply the same change to `_borrow` (`vault.withdraw(shortfall, ...)`) so draws use `previewWithdraw`/`redeem` with a tolerance.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ProgrammableBorrower} from "contracts/strategies/idle/ProgrammableBorrower.sol";
import {IERC4626} from "contracts/interfaces/IERC4626.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";

/// Minimal ERC4626 vault with a withdrawal fee (like Instadapp Lite ETHV2).
contract FeeVault is ERC20 {
    ERC20 public immutable assetTok;
    uint256 public constant FEE_BPS = 50; // 0.5% withdrawal fee
    constructor(ERC20 _a) ERC20("fV", "fV") { assetTok = _a; }
    function deposit(uint256 assets, address to) external returns (uint256 sh) {
        sh = assets; // 1:1 for simplicity
        assetTok.transferFrom(msg.sender, address(this), assets);
        _mint(to, sh);
    }
    function convertToAssets(uint256 sh) public pure returns (uint256) { return sh; }
    function withdraw(uint256 assets, address to, address owner) external returns (uint256 sh) {
        // gross assets needed incl. fee -> shares burned exceed 'assets'
        sh = assets * 10_000 / (10_000 - FEE_BPS);
        require(sh <= balanceOf(owner), "withdraw > max");
        _burn(owner, sh);
        assetTok.transfer(to, assets);
    }
    function redeem(uint256 sh, address to, address owner) external returns (uint256 assets) {
        _burn(owner, sh);
        assets = sh * (10_000 - FEE_BPS) / 10_000;
        assetTok.transfer(to, assets);
    }
}

contract ZeroToleranceStopEpoch is Test {
    function test_stopEpochRevertsWithFeeVault() external {
        // setup: CDO = this contract impersonated via harness; borrower deposited N assets,
        // onStartEpoch parked everything into FeeVault, so onHand == 0 and
        // shortfall == _amountRequired == full share value.
        //
        // _currentVaultAssets() = convertToAssets(shares) = N  -> guard passes
        // vault.withdraw(N) requires N * 10000/9950 shares > N held -> revert
        // catch -> revert StopEpochVaultLiquidityUnavailable()
        //
        // Therefore IdleCDOEpochVariant.stopEpoch() reverts on every call while
        // liquidity lives in the fee vault; pending withdraw requests stay unfunded.
        vm.expectRevert(); // StopEpochVaultLiquidityUnavailable
        // programmableBorrower.onStopEpoch(N, false);  // called by IdleCDO
    }
}
```

Concrete trace: (1) epoch running, all idle cash deposited to a fee-charging ERC4626 vault via `onStartEpoch`/`_depositToVault`; (2) `stopEpoch` invoked → `onStopEpoch(_amountRequired ≈ full position)` → `shortfall == _currentVaultAssets()` passes the coverage guard → `vault.withdraw(shortfall)` needs `shortfall / (1 - fee)` shares > shares held → reverts → `StopEpochVaultLiquidityUnavailable` → `stopEpoch` never completes; withdraw requests freeze until `emergencyExitVault` rescue.
