### Title
Stale per-epoch instant-withdraw receipts are never cleared on normal claim, enabling a second defaulted-epoch claim that drains the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a funded instant-withdraw receipt and clears only the aggregate `instantWithdrawsRequests[_user]`, but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]` — the same bug class as CVE-2021-47237 (unregister without free). If the pool later defaults in that same epoch while another instant request remains unfunded, the stale entry is counted again in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` and is payable a second time via `_claimDefaultedInstantWithdrawRequest`, letting an attacker double-claim and steal from the honest users' recovery reserve.

### Finding Description
On request, `requestInstantWithdraw` records the receipt three ways: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

On a normal (funded) claim, only the aggregate is cleared; the per-epoch entries are leaked:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

When a default is finalized, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` — which includes the attacker's already-paid claim — as reserve backing [3](#0-2) [4](#0-3) .

After finalization, `claimInstantWithdrawRequest` routes to `_claimDefaultedInstantWithdrawRequest`, which reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from `defaultRecoveryReserve` [5](#0-4) .

### Impact Explanation
An unprivileged tranche holder (KYC'd lender) who made and claimed an instant withdrawal in the defaulted epoch can claim it a second time. Because the phantom entry inflates `totalBasis` and `prefundedReserve`, the computed `defaultRecoveryPrice` is wrong, and the second payout is drawn directly from `defaultRecoveryReserve` — funds reserved for honest defaulted-epoch claimants. This is direct theft of recovery funds plus reserve insolvency: later honest claimants' `_transferDefaultRecovery` calls either revert or receive less, permanently freezing part of their unclaimed recovery.

### Likelihood Explanation
Requires: instant withdrawals enabled, an epoch where at least one instant receipt is funded and claimed while another remains unfunded (`pendingInstantWithdraws > 0`), and a borrower default finalized via `finalizeDefaultRecovery` in the same `epochNumber`. Borrower default is an honest-role event (not attacker-controlled), consistent with the threat model. No privileged collusion needed; timing is feasible because instant claims and epoch stop both happen within one epoch. The missing cleanup is unconditional — every funded instant claim leaves the stale per-epoch entry — so the double-claim path is always reachable once the default conditions align.

### Recommendation
In `claimInstantWithdrawRequest` (or `_transferFundedClaim` path for instant receipts), clear the per-epoch accounting: iterate/record the request epoch so `instantWithdrawsRequestsByEpoch[_user][epoch]` is zeroed and `instantWithdrawClaimsByEpoch[epoch]` is decremented by the claimed amount, mirroring what `_claimDefaultedInstantWithdrawRequest` does at lines 847–853. Alternatively, store the request epoch per user (like `lastWithdrawRequest`) so the funded claim can clear the matching epoch entry.

```solidity
// test/foundry/InstantWithdrawDoubleClaim.t.sol
function testInstantWithdrawDoubleClaimAfterDefault() external {
    // 1. Enable instant withdrawals: setInstantWithdrawParams(delay, minAprDiff, false)
    // 2. Attacker (KYC'd user A) deposits, starts epoch, requests instant withdraw X.
    //    Victim (user B) also requests instant withdraw Y in the SAME epoch.
    // 3. CDO funds only attacker's request: collectInstantWithdrawFunds(X)
    //    -> pendingInstantWithdraws == Y > 0
    // 4. After instantDelay, attacker calls claimInstantWithdrawRequest via CDO.
    //    ASSERT BUG: instantWithdrawsRequestsByEpoch[A][epoch] == X (stale),
    //    instantWithdrawClaimsByEpoch[epoch] == X + Y (not decremented).
    // 5. Warp past epochEndDate; borrower repays nothing -> stopEpoch defaults.
    // 6. manager finalizeDefault(recovered, source) ->
    //    finalizeDefaultRecovery counts basis = pendingWithdraws + (X+Y)
    //    and prefundedReserve = (X+Y) - Y = X (phantom, already paid out).
    // 7. Attacker calls claimInstantWithdrawRequest again:
    //    _claimDefaultedInstantWithdrawRequest pays X * recoveryPrice from
    //    defaultRecoveryReserve -> second payout on the same receipt.
    // 8. Assert attacker received ~2x entitlement and victim's recovery
    //    claim reverts/underpays (reserve drained).
}
```

Key assertions that prove the leak: step 4 showing `instantWithdrawsRequestsByEpoch[A][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are never reduced by the funded claim, and step 7 showing the second transfer out of `defaultRecoveryReserve`.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
