### Title
Pending APR0 withdraw receipt permanently bricks `stopEpoch` after any APR increase — full vault freeze - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. Any KYC-passing lender can create a non-zero `apr0TotalPrincipal` bucket by calling `requestWithdraw` during an APR0 epoch, and there is no way for that bucket to be cleared except inside `stopEpoch` itself. If the manager (honest, per model) subsequently sets a non-zero APR through `setApr`/`setAprsWithBuffer`, every `stopEpoch`/`stopEpochWithDuration` call reverts, the epoch can never end, borrower repayments can never be pulled, and all user funds — including the attacker's own receipt and every other depositor's principal — are frozen.

### Finding Description
The MySQL CVE is an availability bug: an easily triggered code path hangs the whole server. The closest analog here is an easily triggered state combination that hangs the epoch state machine.

1. During an epoch running with `unscaledApr == 0` (the APR0/programmable-borrower mode), the attacker deposits AA or BB tranches and calls `IdleCDOEpochVariant.requestWithdraw`. Because `unscaledApr == 0`, `IdleCreditVault.requestWithdraw` routes into `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` (`IdleCreditVault.sol:567-577`).
2. `apr0TotalPrincipal` is only ever reset to zero inside `prepareStopEpochWithApr0` (`IdleCreditVault.sol:540`) or partially decreased during default-finalization claims (`_clearWithdrawClaimForEpoch`). A user cannot unwind it: claiming requires `epochNumber > lastWithdrawRequest[user]` in `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:326`), and `epochNumber` only advances at a successful `stopEpoch` (via `deposit` at `IdleCreditVault.sol:610`).
3. `prepareStopEpochWithApr0` is invoked unconditionally at the top of `_stopEpoch` in `IdleCDOEpochVariant._stopEpoch`. With `apr0TotalPrincipal != 0` it checks `if (unscaledApr != 0) revert NotAllowed()` (`IdleCreditVault.sol:506-508`).
4. `unscaledApr` is settable by the manager at any time via `setAprsWithBuffer`/`setApr` (`IdleCreditVault.sol:217-235`). A routine APR change while an APR0 receipt is pending therefore permanently poisons `stopEpoch`: the revert happens before any borrower pull, accounting update, or `epochNumber` increment.
5. Resulting deadlock: the APR0 requester cannot claim (epoch never rolls), and no other user can deposit normally (buffer-period flow requires a completed stop), withdraw (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` only re-enable inside a successful stop, `IdleCDOEpochVariant.sol:481-482`), or claim funded receipts (`epochNumber <= lastWithdrawRequest` guard). If the epoch had already started and borrower holds the funds, repayment cannot be processed; `epochEndDate` expiry just makes every `stopEpoch` call revert rather than triggering a clean default path.

The existing guards do not stop it: `_onlyIdleCDO`, KYC (`isWalletAllowed`), and the loss-receipt re-request guard are all satisfied by a normal lender request; the `NotAllowed` revert at line 506 is itself the bug — it converts a user-created, user-unresolvable state into a revert on the privileged liveness path.

### Impact Explanation
Denial of service with direct fund impact: the entire vault TVL plus borrower-held principal is frozen as long as `unscaledApr != 0` and the APR0 bucket is non-zero. Because `apr0TotalPrincipal` cannot be decremented outside `stopEpoch`/default finalization, the only recovery is the manager manually resetting `unscaledApr` back to 0 — i.e., temporary freezing of all user funds and unclaimed yield for the duration, and permanent freezing if the pool has moved operationally to a non-zero-APR regime. Attack cost is one deposit + one `requestWithdraw`; loss is bounded only by total pool TVL.

### Likelihood Explanation
The trigger requires an APR0-configured deployment (programmable borrower / zero-APR epoch), an unprivileged withdraw request while APR is 0, and a subsequent APR raise — all normal operations. The manager raising APR is an ordinary administrative action, not attacker collusion, and the bug exists precisely because the code anticipates this state yet resolves it by reverting the only function that can clear it. No privileged misbehavior, oracle manipulation, or economic assumption is needed.

### Recommendation
Do not revert in `prepareStopEpochWithApr0` when `unscaledApr != 0`. Instead, on an APR transition with a pending APR0 bucket, settle the bucket at the realized rate (or at zero interest) before applying the new APR, e.g. compute `_apr0NetInterest` against the old APR-0 terms and clear `apr0TotalPrincipal`. Alternatively, add an explicit sweep path that lets `stopEpoch` finalize outstanding APR0 requests regardless of current `unscaledApr`, or forbid APR changes while `apr0TotalPrincipal != 0` at `setApr` time (reverting the harmless config call instead of the liveness-critical `stopEpoch`).

### Proof of Concept
Foundry fork test sketch against `IdleCreditVault.t.sol` harness:

```solidity
// Setup: pool configured with unscaledApr == 0 (APR0/programmable mode), epoch running.
idleCDO.depositAA(10_000e6);                 // attacker + others deposit
uint256 tr = AAtranche.balanceOf(address(this));

cdoEpoch.requestWithdraw(tr, address(AAtranche)); // unscaledApr==0 -> _requestWithdrawApr0
assertGt(strategy.apr0TotalPrincipal(), 0);       // attacker poisoned bucket

// Honest manager later raises APR (normal ops)
vm.prank(manager);
strategy.setAprsWithBuffer(5e18, 30 days, 5 days); // unscaledApr = 5e18

// Epoch end passes; manager tries to stop -> permanent revert
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(0, 0);

// Attacker cannot self-clean: claim reverts (epochNumber <= lastWithdrawRequest)
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimWithdrawRequest();

// No second request allowed either; stopEpoch keeps reverting while apr0TotalPrincipal != 0
// => all funds frozen until manager restores unscaledApr == 0
```
