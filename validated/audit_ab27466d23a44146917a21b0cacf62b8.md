### Title
Claimed instant-withdraw receipts keep stale per-epoch basis and are counted again in default recovery, diluting and permanently locking reserve funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a use-after-free caused by an object being completed twice: the error path inside `btrfs_submit_chunk()` frees the bio while the async endio path still references it. The analog in `IdleCreditVault` is an instant-withdraw receipt that is consumed (claimed) through the normal path but whose per-epoch claim basis is never cleared, so the default-recovery path later counts the same receipt a second time as outstanding claim basis.

### Finding Description
`requestInstantWithdraw` records the receipt in three places: the aggregate `instantWithdrawsRequests[_user]`, the per-user-per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch aggregate `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

`claimInstantWithdrawRequest` only clears the aggregate field and burns the receipt tokens. It never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` and never decrements `instantWithdrawClaimsByEpoch[epoch]` [2](#0-1) .

Both stale counters are later treated as live claim basis on the default path:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery denominator whenever `pendingInstantWithdraws != 0` [3](#0-2) .
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` and adds it to `defaultRecoveryReserve` as already-held backing [4](#0-3) .
- `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` as claimBasis and then executes `instantWithdrawsRequests[_user] -= claimBasis`, which underflows (the aggregate was zeroed at claim) and permanently reverts that user's claim path [5](#0-4) .

### Impact Explanation
An unprivileged lender who legitimately claims a partially-prefunded instant withdrawal during a running epoch leaves phantom basis behind. If the borrower then defaults and `finalizeDefault` runs while `pendingInstantWithdraws != 0`:

1. `defaultPendingClaimBasis` is inflated by the already-paid amount, so `recoveryPrice = reserveAmount / totalBasis` is diluted — every genuine defaulted receipt (normal, APR0, and other instant claimants) is underpaid.
2. The reserve share earmarked for the phantom basis can never be paid out: the stale claimant's `_claimDefaultedInstantWithdrawRequest` reverts on the underflow at `instantWithdrawsRequests[_user] -= claimBasis`, and no other path consumes `defaultRecoveryReserve` for it. That portion of the recovery reserve is permanently locked in the contract.
3. Loss magnitude: up to the full prefunded-and-claimed instant amount for that epoch, i.e. `instantWithdrawClaimsByEpoch[epoch] - pendingInstantWithdraws` worth of reserve stranded plus proportional dilution of all other claimants' payouts.

The broken invariant is "one receipt one payout" plus solvency of the recovery reserve: a consumed receipt is double-counted on the error (default) path. None of the existing guards stop it — `_ensureDefaultRecoveryInitialized` explicitly refuses to clear pending instant withdrawals [6](#0-5) , and `_transferFundedClaim`'s reserve guard only protects the reserve from being spent, not from being inflated [7](#0-6) .

### Likelihood Explanation
Requires only ordinary, unprivileged actions: request an instant withdraw during the buffer, have the manager collect partial instant funds, claim the funded portion during the running epoch, then a borrower default with `pendingInstantWithdraws != 0` — exactly the "partially prefunded instant" state the codebase already models and tests (`testFinalizeDefaultHaircutsPendingInstantRedeems` asserts `pendingInstant < instantClaimBasis`) [8](#0-7) . The only missing step in existing tests is a user *claiming* the prefunded portion before the default, which is the natural usage of `claimInstantWithdrawRequest`.

### Recommendation
In `claimInstantWithdrawRequest`, clear the consumed basis before paying out: locate the request epoch(s) backing `instantWithdrawsRequests[_user]` (e.g. iterate/track the outstanding request epoch, or clear `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount). Alternatively, snapshot/clear per-epoch entries at claim time the same way `_clearWithdrawClaimForEpoch` clears `withdrawsRequestsByEpoch` for normal receipts [9](#0-8) .

### Proof of Concept
Foundry fork PoC (reusing the harness style of `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testClaimedInstantReceiptCountedTwiceInDefaultRecovery() external {
    uint256 instantDelay = cdoEpoch.instantWithdrawDelay();
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 0, false);

    address userA = makeAddr('claimed-instant-user');
    address userB = makeAddr('pending-instant-user');
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(userA, amount, true);
    _depositWithUser(userB, amount, true);

    // buffer: both request instant withdraw (simplified via requestWithdraw in instant mode)
    vm.prank(userA);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(userB);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);

    // borrower partially funds instant queue: only enough for A
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    uint256 basisA = creditVault.instantWithdrawsRequests(userA);
    deal(defaultUnderlying, borrower, basisA);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).transfer(address(cdoEpoch), basisA);
    vm.warp(block.timestamp + instantDelay + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();

    // userA claims the funded portion — per-epoch basis stays stale
    vm.prank(userA);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(creditVault.instantWithdrawsRequests(userA), 0);
    // BUG: stale basis still present
    assertGt(creditVault.instantWithdrawClaimsByEpoch(creditVault.epochNumber()), basisA);

    // borrower defaults on the rest at stopEpoch
    _checkDefault();

    uint256 phantomBasis = basisA; // already paid to A
    uint256 totalBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest()
        - cdoEpoch.pendingWithdrawFees() + creditVault.defaultPendingClaimBasis();
    // defaultPendingClaimBasis includes phantomBasis again
    uint256 recovered = totalBasis * 7e17 / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // userA's defaulted claim path now underflows and reverts forever
    vm.prank(userA);
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();

    // ~phantomBasis * recoveryPrice of the reserve is stranded; all claimants diluted
}
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
