### Title
Global cross-tenant Request ID collision enables trigger-request DOS in HTTP Trigger Gateway Handler - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
`httpTriggerHandler.setupCallback()` keys the in-flight-request map solely by the client-supplied `requestID`, with no scoping to workflow, workflow owner, or authenticated key. Any authorized DON client can pre-claim an arbitrary `requestID` value, and the resulting single "pending slot" blocks every other caller — even from a completely different workflow/owner — from using that same ID until the slot times out and is reaped.

### Finding Description
`HandleUserTriggerRequest` validates the request, resolves and authorizes the target workflow, checks rate limits, and finally calls `setupCallback`: [1](#0-0) 

The `callbacks` map is declared and used purely as `map[string]savedCallback` keyed by `requestID`: [2](#0-1) 

Because the key is `requestID` alone (never combined with `workflowID`, workflow owner, or the authorized key), the "pending" namespace is shared globally across the entire gateway, across all workflows and all owners. This mirrors the report's bug class exactly: a single, unscoped "pending slot" keyed by an attacker-influenceable value, reachable via a public/unprivileged entry point (`HandleUserTriggerRequest` is reachable by any client holding a valid JWT for *any* workflow served by the gateway — attacker only needs authorization for their *own* workflow, not the victim's).

An attacker who can predict or observe a legitimate client's `requestID` (e.g., sequential IDs, UUIDs derived from deterministic client logic, or IDs the attacker learns from a shared integration) can submit a trigger request for their own (unrelated) workflow using that exact `requestID` first. Since the check-and-insert is done under `callbacksMu` with no ownership scoping, the second (legitimate) caller using the same ID hits the `found` branch and is rejected with `jsonrpc.ErrConflict`: [3](#0-2) 

This existing behavior is even demonstrated (from a single-tenant perspective) in the test suite: [4](#0-3) 

The blocked slot persists until `reapExpiredCallbacks` clears it after `CleanUpPeriodMs` (default 10 minutes): [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a real cross-tenant availability impact within the internet-facing gateway: a client that only has authorization for one workflow can deny legitimate `workflows.execute` trigger invocations for a *different* workflow/owner simply by colliding on `requestID`. Impact is Medium — it does not compromise secrets or funds directly, but it can delay/deny legitimate workflow executions for up to the cleanup period, and can be repeated indefinitely by re-claiming the ID as soon as it's reaped, similar to the referenced `submitStrategy()` DOS which permanently front-runs the single pending slot.

### Likelihood Explanation
Likelihood is Medium: exploitation requires (a) the attacker to hold valid authorization for at least one workflow on the same gateway (a low bar, since it's their own legitimate workflow), and (b) knowledge or prediction of the victim's `requestID`. Many client implementations use deterministic or easily-guessable IDs (timestamps, counters, hashes of predictable inputs), making collision feasible in practice, and the attack can be repeated cheaply to sustain the DOS.

### Recommendation
Scope the `callbacks` map key by `(workflowID, requestID)` (or `(authorizedOwner, workflowID, requestID)`) instead of `requestID` alone, so that request-ID uniqueness is enforced only within a single workflow/tenant's namespace rather than globally across the gateway. This eliminates the possibility of unrelated tenants colliding on and blocking each other's trigger requests.

### Proof of Concept
1. Attacker registers/owns Workflow A and obtains a valid JWT authorizing trigger requests for Workflow A.
2. Attacker predicts or learns that a victim client will shortly submit a `workflows.execute` request with `id = "X"` against Workflow B.
3. Attacker sends their own `workflows.execute` request for Workflow A with `id = "X"` first; `setupCallback` inserts `callbacks["X"]`.
4. Victim's legitimate request for Workflow B with `id = "X"` arrives; `setupCallback` finds `callbacks["X"]` already present (from an unrelated workflow) and rejects it with `jsonrpc.ErrConflict` / "requestID: X has already been used" — as shown in the existing duplicate-ID test path at `http_trigger_handler_test.go:317-355`.
5. The victim's request is denied until the attacker's stale entry is reaped after `CleanUpPeriodMs` (default 10 minutes), and the attacker can repeat the collision indefinitely.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

// reapExpiredCallbacks removes callbacks that are older than the maximum age
func (h *httpTriggerHandler) reapExpiredCallbacks(ctx context.Context) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()
	now := time.Now()
	var expiredCount int
	for reqID, callback := range h.callbacks {
		if now.Sub(callback.createdAt) > time.Duration(h.config.CleanUpPeriodMs)*time.Millisecond {
			h.metrics.IncrementRequestErrors(ctx, jsonrpc.ErrInternal, h.lggr)
			h.cleanupCallback(reqID)
			expiredCount++
		}
	}
	if expiredCount > 0 {
		h.metrics.IncrementPendingRequestsCleanUpCount(ctx, int64(expiredCount), h.lggr)
		h.lggr.Infow("Removed expired callbacks", "count", expiredCount, "remaining", len(h.callbacks))
	}
	h.metrics.RecordPendingRequestsCount(ctx, int64(len(h.callbacks)), h.lggr)
}
