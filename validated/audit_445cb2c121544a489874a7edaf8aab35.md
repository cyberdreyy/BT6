### Title
Unfunded instant-withdraw receipts can be claimed early, draining underlying reserved for other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

CVE-2021-34548 (TROVE-2021-003) is about a forged `RELAY_END`/`RELAY_RESOLVED` cell: a party that should not be able to terminate a stream convinces the endpoint to tear it down, bypassing the intended ordering/access control on stream closure. The analog in `IdleCreditVault` is `claimInstantWithdrawRequest`: it pays out an instant-withdraw receipt with no check that the borrower's funding for that request ever arrived. The intended lifecycle is "request in buffer → borrower funds at next `startEpoch` via `collectInstantWithdrawFunds` → user claims during the running epoch" (`contracts/IdleCDOEpochVariant.sol:975`). The claim function burns the user's receipt and calls `_transferFundedClaim`, but nothing verifies that the request's funding was actually collected, so a receipt whose funding is still owed by the borrower is "ended" prematurely and paid out of whatever underlying the strategy happens to hold — including funds reserved for other users' already-funded claims.

### Finding Description

`requestInstantWithdraw` mints strategy-token receipts to the user and records them in `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`contracts/strategies/idle/IdleCreditVault.sol:356-374`). Funding arrives later through `collectInstantWithdrawFunds`, which only decrements `pendingInstantWithdraws` and pulls tokens from the CDO (`contracts/strategies/idle/IdleCreditVault.sol:398-403`). There is no per-request funded flag.

`claimInstantWithdrawRequest` then pays out the full `instantWithdrawsRequests[_user]` balance by burning the receipt and calling `_transferFundedClaim` (`contracts/strategies/idle/IdleCreditVault.sol:380-393`). Its only access gate is `_onlyIdleCDO`, and the CDO-side wrapper only checks the `allowInstantWithdraw` flag (`contracts/IdleCDOEpochVariant.sol:975-978`). The docstring "Can be done when epoch is running as funds will get transferred from borrower when epoch starts" is an assumption, not an enforced invariant: `requestWithdraw` can create instant receipts mid-epoch (whenever `lastEpochApr > currentApr + instantWithdrawAprDelta`, `contracts/IdleCDOEpochVariant.sol:761-768`), and those receipts will not be funded until the *next* epoch start.

Meanwhile the strategy legitimately holds underlying at that moment: `collectWithdrawFunds` pulls funded normal withdraws into the vault at `stopEpoch` (`contracts/strategies/idle/IdleCreditVault.sol:411-430`), and partially funded instant requests also sit in the vault (see `_defaultPrefundedInstantReserve`, lines 716-723). `_transferFundedClaim` pays the claimer from the vault's token balance without distinguishing whose funding it is.

Attack sequence (attacker = KYC-passed AA/BB lender):

1. Epoch N runs; some users have pending withdraw requests. Manager calls `stopEpoch`, which funds those receipts via `collectWithdrawFunds` — the vault now holds underlying reserved for those claimants.
2. During the new epoch, the (honest) borrower lowers `unscaledApr` such that `lastEpochApr > unscaledApr + instantWithdrawAprDelta` (a normal rate renegotiation the rules allow sequencing around).
3. Attacker calls `requestWithdraw(trancheAmount, tranche)` on the CDO. The instant path fires: `requestInstantWithdraw` mints the attacker a receipt and increments `pendingInstantWithdraws`, but no funding is collected — the borrower only funds instant requests at the next `startEpoch`.
4. Attacker immediately calls `claimInstantWithdrawRequest`. The vault burns the receipt and transfers the full amount from underlying that belongs to step-1 funded claimants.
5. When those claimants call `claimWithdrawRequest`, `_transferFundedClaim` reverts on insufficient balance — their funded claims are permanently unpaid even though `pendingWithdraws` was funded.

### Impact Explanation

Direct theft plus permanent freezing: the attacker converts an unfunded receipt into real underlying by expropriating funds earmarked for other users' funded claims. The victims' claims were already paid for by the borrower (`pendingWithdraws` cleared, tokens in the vault) yet become unclaimable — a permanent loss equal to the attacker's receipt amount, bounded by the vault's claim reserve. One receipt/one payout is broken because the payout draws on a funding source the receipt never had a claim to. All privileged parties (manager, borrower, guardian) remain honest; only timing around their routine calls is required.

### Likelihood Explanation

Requires instant-withdraw mode enabled (`!disableInstantWithdraw`, not programmable borrower, `allowInstantWithdraw` true), a real APR decrease while the vault holds unclaimed funded underlying, and an attacker who has deposited tranche tokens (KYC only). The precondition of the vault holding a funded-but-unclaimed balance is normal — users are explicitly told they "can withdraw at any time even if a new epoch started" (`contracts/strategies/idle/IdleCreditVault.sol:320-321`), so unclaimed funded balances are expected to linger across epochs. No loss-epoch, default, or privileged misbehavior is needed.

### Recommendation

Track funded vs. unfunded instant receipts separately — e.g., maintain a `fundedInstantWithdraws` counter incremented in `collectInstantWithdrawFunds` and pay claims only against it (per-epoch funded accounting mirroring `withdrawsRequestsByEpoch`), or have `claimInstantWithdrawRequest` pay only receipts whose request epoch is strictly older than the epoch in which funding was collected. Alternatively, gate the CDO-side instant request path so receipts can only be created during the buffer period when funding is guaranteed at the imminent `startEpoch`.

### Proof of Concept

Foundry fork sketch (pattern after `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testUnfundedInstantClaimDrainsFundedReceipts() external {
    // 1. Victim deposits and requests a normal withdraw during buffer
    uint256 amt = 10_000 * ONE_SCALE;
    vm.prank(victim);
    uint256 tr = idleCDO.depositAA(amt);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(tr, address(AAtranche));

    // 2. Epoch runs; borrower funds victim's receipt at stopEpoch
    vm.prank(manager); cdoEpoch.startEpoch();
    deal(underlying, borrower, owed);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager); cdoEpoch.stopEpoch(0, 0); // collectWithdrawFunds pulls victim's funds into vault
    uint256 vaultBal = underlying.balanceOf(address(strategy));
    assertGt(vaultBal, 0); // funded underlying waiting for victim claim

    // 3. Honest borrower lowers APR so instant path triggers
    vm.prank(borrower); strategy.setApr(lowerApr); // lastEpochApr > apr + delta

    // 4. Attacker deposits and requests -> instant receipt, unfunded
    vm.prank(attacker); uint256 tr2 = idleCDO.depositAA(amt);
    vm.prank(attacker); cdoEpoch.requestWithdraw(tr2, address(AAtranche));
    assertGt(strategy.pendingInstantWithdraws(), 0); // funding still owed

    // 5. Attacker claims immediately, paid from victim's funded reserve
    vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker), 0);

    // 6. Victim's funded claim now reverts / is unpaid
    vm.prank(victim);
    vm.expectRevert(); // insufficient vault balance
    cdoEpoch.claimWithdrawRequest();
}
```

Uncertainty: I was unable to read the body of `_transferFundedClaim` within available iterations, so the exact payout source is inferred from `collectWithdrawFunds`/`collectInstantWithdrawFunds` transferring underlying into the vault and the claim functions delegating to it; a PoC run should confirm whether it pays from the strategy's token balance as described.
