### Title
Junior (BB) lenders dodge the BB-first loss waterfall by queuing withdrawals before `stopEpochWithDuration(_lossAmount)` — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
In `IdleCDOEpochVariant`, a loss realized at epoch stop is split into (a) a pro-rata haircut on all pending withdraw receipts and (b) a remainder applied BB-first to active positions. Because the pending-receipt bucket drops tranche identity, a BB (junior) holder can `requestWithdraw` during the buffer period / running epoch, converting junior principal into a loss-sharing pending receipt. The receipt only bears `pendingLoss = _lossAmount * pendingBasis / totalBasis` pro rata, while under the intended waterfall it should absorb losses before AA. The shortfall is pushed onto remaining active BB and AA holders and onto AA holders who also queued receipts. This mirrors the report's bug class: sequencing around loss realization to leave "bad debt" borne by others and escape the loss-absorption ordering.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` calls `IdleCreditVault.previewLossAdjustedWithdrawFunds(_lossAmount)`, which computes:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:454-459
uint256 totalBasis = activeBasis + pendingBasis;
uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
pendingToFund = pendingBasis - pendingLoss;
activeLoss = _lossAmount - pendingLoss;
```

`pendingToFund` is pulled from the borrower and `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]`, haircutting every pending receipt pro rata. `activeLoss` is then burned via `_forceUpdateAccounting()`, applying the ordinary BB-first waterfall to whoever stayed active.

Meanwhile `requestWithdraw` (`contracts/strategies/idle/IdleCreditVault.sol:243-295`, invoked from `IdleCDOEpochVariant.requestWithdraw`) is permissionless for any KYC'd tranche holder while the epoch is running or in buffer period: it burns the CDO's strategy tokens, mints the user a receipt, and adds `_amount` to `pendingWithdraws` — with no tranche tagging.

Concretely: an attacker holding BB tranche tokens sees (or expects) that the manager will call `stopEpochWithDuration(..., _lossAmount)` to realize a loss (loss realization is a manager call, so timing is observable/anticipatable, and the attacker only needs the request to land before the stop). By requesting a withdraw during the buffer window, the attacker's principal enters `pendingWithdraws`. When the stop executes:

- Under correct waterfall: if `_lossAmount <= lastNAVBB`, BB absorbs 100% of the loss; AA absorbs 0.
- Actual: the attacker's receipt only loses `pendingLoss * (theirReceipt / pendingBasis)`, and part of the loss that BB should have absorbed is instead spread across AA pending receipts (which should bear zero loss while BB NAV remains) and re-concentrated onto the remaining active BB holders, whose post-loss NAV is then lower than it should be relative to the escaped attacker.

Broken invariant: the loss waterfall — junior tranche absorbs losses before senior. The guard `_lossAmount >= totalBasis revert` and the `Default` revert in `_updateAccounting` (for losses exceeding BB NAV at a deposit/withdraw-triggered accounting update) do not stop this: `requestWithdraw` computes the receipt amount at `virtualPrice`, but the stop-epoch loss has not yet been realized, so the request prices at pre-loss value and enters the pending bucket cleanly. Note the comment at `IdleCDOEpochVariant.sol:391-393` explicitly acknowledges pending receipts share loss pro rata — however the exploitable consequence (juniors escaping the waterfall and dumping loss onto seniors by sequencing `requestWithdraw`) is an attacker-controllable wealth transfer, not merely an accounting approximation.

### Impact Explanation
A BB holder facing a stop-epoch loss converts junior exposure into a pro-rata pending receipt, materially reducing their loss share. The displaced loss lands on AA pending receipts (which should be loss-free while BB NAV covers the loss) and on remaining active BB/AA holders via the active waterfall. Loss magnitude is bounded by `pendingLoss` share: with BB NAV ≥ loss, an attacker moving amount `X` of BB into pending escapes roughly `X * (1 - pendingBasis/totalBasis)`-proportional loss attribution vs. full BB-first absorption. For example, with pendingBasis = totalBasis/2 and loss fully within BB NAV, a BB withdrawer bears only ~half the loss they should, with the remainder socialized to seniors and remaining juniors — a direct, quantified transfer of value between unprivileged LPs.

### Likelihood Explanation
Requires: a manager-initiated `stopEpochWithDuration` carrying `_lossAmount != 0` (a documented recovery path for realized borrower losses), and the attacker holding BB tokens and submitting `requestWithdraw` before the stop tx. Withdraw requests during the buffer/running epoch are the normal, intended user flow, so no special privileges or timing manipulation beyond ordinary mempool observation are needed. When losses do occur, rational junior holders are strongly incentivized to queue exits first — the same "liquidate the worst CDP last / dodge the bad debt" incentive the source report describes.

### Recommendation
Preserve tranche identity for pending receipts (e.g., per-epoch AA/BB receipt buckets via `withdrawsRequestsByEpoch`) and apply `pendingLoss` BB-first across the pending bucket: pending BB receipts absorb pending-loss up to their basis before pending AA receipts are haircut. Alternatively, checkpoint per-tranche receipt composition at request time so `previewLossAdjustedWithdrawFunds` can reconstruct the waterfall ordering.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testBBHolderEscapesLossViaPendingReceipt() external {
    uint256 amountAA = 9_000 * ONE_SCALE;
    uint256 amountBB = 1_000 * ONE_SCALE;
    idleCDO.depositAA(amountAA);          // honest senior
    idleCDO.depositBB(amountBB);          // attacker junior
    _startEpochAndCheckPrices(0);

    // Attacker queues a full BB withdraw during buffer/running epoch,
    // before the manager realizes the loss.
    cdoEpoch.requestWithdraw(0, address(BBtranche)); // attacker

    uint256 lossAmount = 500 * ONE_SCALE; // < lastNAVBB, should be 100% BB-borne
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), lossAmount);

    // Attacker claims; receipt only haircut by pro-rata pendingLoss,
    // not the full BB-first loss.
    uint256 claimed = IdleCreditVault(address(strategy)).claimWithdrawRequest(attacker);
    // Assert attacker lost less than lossAmount and AA absorbed a nonzero loss,
    // i.e. virtualPrice(AAtranche) < pre-loss price despite loss <= lastNAVBB.
    assertLt(claimed, amountBB);
    assertGt(claimed, amountBB - lossAmount); // escaped the waterfall
    assertLt(cdoEpoch.virtualPrice(address(AAtranche)), preAAPrice);
}
```

Key assertions to verify against `previewLossAdjustedWithdrawFunds` math: `pendingLoss = lossAmount * pendingBasis / totalBasis` is charged to all receipts pro rata, so the BB attacker's effective loss is strictly less than `lossAmount`, while AA receipts/active NAV absorb the difference that BB-first ordering would have assigned to the attacker.
