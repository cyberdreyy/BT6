### Title
`PipelineRunsController.Create`'s `isUser` check is satisfied by External-Initiator-issued sessions, allowing EI credential holders to run jobs by numeric ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` intends to restrict numeric-ID job runs to authenticated `User` sessions only, explicitly excluding External Initiator (EI) credentials, per the code comment "only users are allowed to run jobs using int IDs - EIs not allowed". However, `auth.AuthenticateExternalInitiator` sets the exact same context key (`SessionUserKey`) that `auth.GetAuthenticatedUser` checks, using a synthetic `clsessions.User{Role: clsessions.UserRoleRun}`. This makes `isUser` evaluate to `true` for EI-authenticated requests, defeating the intended restriction.

### Finding Description
In `core/web/pipeline_runs_controller.go`, the `Create` handler gates numeric job-ID runs behind: [1](#0-0) 

`isUser` is derived from `auth.GetAuthenticatedUser(c)`: [2](#0-1) 

This function only checks whether `SessionUserKey` is present in the gin context and can be type-asserted to `*clsessions.User` — it has no way to distinguish a genuine dashboard/API-token `User` session from an EI session.

Critically, `AuthenticateExternalInitiator` — the auth method invoked for EI-credentialed requests — explicitly sets `SessionUserKey` to a synthetic `User` object with `Role: clsessions.UserRoleRun`, in addition to setting `SessionExternalInitiatorKey`: [3](#0-2) 

Because both `AuthenticateBySession`/`AuthenticateByToken` (real user auth) and `AuthenticateExternalInitiator` (EI auth) populate the same `SessionUserKey`, `GetAuthenticatedUser` — and therefore `isUser` in `PipelineRunsController.Create` — cannot tell the two apart. If the route serving `POST /v2/jobs/:ID/runs` is wired with `Authenticate(authr, AuthenticateBySession, AuthenticateByToken, AuthenticateExternalInitiator)` (the standard multi-method authentication pattern used elsewhere in this codebase), a request authenticated purely via EI access-key/secret headers will cause `isUser` to be `true`, allowing the numeric-ID branch of `Create` to execute `prc.App.RunJobV2(ctx, jobID, nil)` — exactly the behavior the inline comment says should be blocked for EIs.

I was not able to fully confirm the exact middleware chain applied to the `/v2/jobs/:ID/runs` route in `core/web/router.go` within this session (tool budget exhausted before reading that file), so I cannot state with certainty whether `AuthenticateExternalInitiator` is actually included in that specific route's middleware list. This is the one remaining gap in tracing the "reachable path" end-to-end; the auth.go/pipeline_runs_controller.go code itself unambiguously shows that the `isUser` check as written cannot distinguish EI sessions from User sessions.

### Impact Explanation
If the run-creation route does include `AuthenticateExternalInitiator` in its auth chain (consistent with the comment in `Create` acknowledging EIs can reach this handler), an EI credential holder — a lower-trust, restricted caller intended only to trigger webhook/UUID-keyed job runs — could invoke arbitrary jobs by numeric ID via `RunJobV2`, which can trigger fund-moving or state-changing pipeline tasks. This matches the "unauthorized job run" bounty impact class.

### Likelihood Explanation
The only precondition is possession of a valid EI access key/secret pair (the intended low-trust credential for external initiators) and knowledge/guessing of a numeric job ID. No admin or operator access is required. The flaw is deterministic and repeatable given the code path described.

### Recommendation
Do not overload `SessionUserKey` for EI-authenticated requests. Distinguish EI-origin sessions explicitly — e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and reject if present, or introduce a distinct session marker/role that `isUser`-style checks can safely exclude, rather than relying solely on `SessionUserKey` presence which `AuthenticateExternalInitiator` also sets.

### Proof of Concept
1. Handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
   - Create an application, insert a job with a numeric ID (non-webhook type).
   - Mint an External Initiator credential (`bridges.ExternalInitiator`) via the standard test helper used in `core/bridges/external_initiator_test.go`.
   - Build an HTTP client that sends only `OCR-EI-ACCESSKEY`/`OCR-EI-SECRET` (or equivalent `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`) — no session cookie, no `X-API-KEY`.
   - POST to `/v2/jobs/<numeric job ID>/runs`.
   - Expected assertion under fix: response is `422 Unprocessable Entity` with body containing `"bad job ID"`, and `RunJobV2` is never invoked.
   - Current (vulnerable) behavior to verify: if the route includes `AuthenticateExternalInitiator`, the request instead succeeds (200) and creates a pipeline run, because `isUser` evaluates `true`.
2. Unit test on `auth.GetAuthenticatedUser`: call `AuthenticateExternalInitiator` against a gin context with a valid EI token, then call `GetAuthenticatedUser(c)` and assert it returns `ok == true` — demonstrating the root cause that `isUser` cannot differentiate EI sessions from User sessions.

// GetAuthenticatedUser extracts the authentication user from the context.
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
