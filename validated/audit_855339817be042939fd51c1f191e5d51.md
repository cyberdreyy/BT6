This confirms the persistence precondition: with `GIT_STRATEGY: fetch` or `none`, the build directory is explicitly **not wiped** between job runs (`case gitStrategyNone: e.Noticef("Skipping build directory cleanup step")`), and cache extraction runs into that same reused directory. This is exactly the shared-`e.dir`-across-runs precondition needed.

### Title
Unvalidated symlink target (`Linkname`) in tar+zstd extractor allows arbitrary-path write-through across cache restores sharing a build directory - (File: `commands/helpers/archive/tarzstd/tarzstd_extractor.go`)

### Summary
`tarzstd_extractor.go` validates only an entry's own destination path (`hdr.Name`) against the chroot (`e.dir`), but never validates `hdr.Linkname` for symlink entries, and `tarzstd_archiver.go` faithfully captures whatever `os.Readlink` returns without restricting it either. A pipeline author can create a symlink pointing anywhere on the filesystem inside their own cache paths, have it archived and stored as project cache, and — because `GIT_STRATEGY: none`/`fetch` and cache restoration deliberately leave the build directory (`e.dir`) un-cleaned between job runs — a later cache/artifact extraction that writes a same-named regular file will follow that pre-planted symlink via `os.Create`, writing content outside the intended build root.

### Finding Description
In `tarzstd_extractor.go` line 57-64 the chroot check is `path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name)); ... strings.HasPrefix(path, e.dir+...)`. This only bounds where the symlink *file itself* is created, not where it *points*. `hdr.Linkname` is used unchecked at line 114: `os.Symlink(hdr.Linkname, path)`. The same gap exists in the archiver, `tarzstd_archiver.go` lines 85-91, where `os.Readlink(path)` captures whatever real filesystem symlink target a job created (fully attacker-controlled since job scripts run as the container user with their own filesystem), with no bound check on the returned `link` before it's written to `hdr.Linkname` via `tar.FileInfoHeader`. [1](#0-0) [2](#0-1) [3](#0-2) 

Within a single `Extract()` call, the `deferred` map design (symlinks and dirs deferred, materialized only after all regular files, lines 42, 75-77, 107-122) actually prevents the *same-archive* ordering race as literally described in the question: any path collision between a regular-file entry and a symlink/dir entry at the identical name causes `os.Create`/`os.Symlink`/`os.Mkdir` to fail with `EEXIST`/`EISDIR`, aborting extraction rather than silently substituting content. So the precise "symlink processed before target directory exists ... repopulated by a same-named regular file entry" race, confined to one archive, does not hold.

The real exploitable variant is cross-extraction, matching the "across job runs sharing `e.dir`" part of the question: (1) a job plants, via ordinary `ln -s /arbitrary/target foo` in its script plus `cache: paths: [foo]`, a cache archive containing a symlink `foo -> /arbitrary/target` with an unchecked `Linkname`; (2) cache restoration in a later job run on the same runner extracts this into the build directory, succeeding because only `foo`'s own path (inside `e.dir`) is checked; (3) since `GIT_STRATEGY: none`/`fetch` explicitly skips build-directory cleanup (`functions/concrete/run/stages/cleanup.go` lines 33-42/59-60, `shells/abstract.go` lines 1858-1891) and cache restoration also writes on top of the existing tree, the dangling symlink at `foo` persists; (4) a subsequent cache/artifact extraction (or even a later cache upload of the same key with different content by the attacker) whose archive has a regular-file entry named `foo` triggers `os.Create(path)` in the extractor, which follows the pre-existing on-disk symlink and writes content to the attacker-chosen target outside `e.dir`. ### Impact Explanation
An unprivileged pipeline author controlling only their own job's cache content can cause the runner process to write attacker-chosen bytes to an attacker-chosen filesystem path outside the job's build/cache root on a runner host where the build directory persists across job runs (self-hosted runners with `GIT_STRATEGY: fetch`/`none`, persistent shell/docker/Kubernetes PVC executors — all documented, non-ephemeral, common configurations, not admin misconfigurations). This violates the "File operations must stay within intended build/cache/artifact roots" invariant and can lead to writing into another project's shared build directory, host files reachable by the runner process, or planted files subsequently executed by other jobs.

### Likelihood Explanation
Feasibility is moderate to high: it only requires an attacker to run two of their own jobs (or one job whose retry reuses cache) against a runner with a persistent build directory — no special runner misconfiguration beyond commonly-used `GIT_STRATEGY: fetch`/`none` or persistent PVC/shell setups. It requires the write-through target directory to already exist and be writable by the job/runner process, and the symlink to survive between the two extractions (true by design for `fetch`/`none` strategies). Reproducible deterministically since both steps are fully attacker-scripted.

### Recommendation
In `tarzstd_extractor.go`, validate `hdr.Linkname` before calling `os.Symlink`: resolve the intended target (`filepath.Join(filepath.Dir(path), hdr.Linkname)` for relative links, or reject absolute links outright) and reject any target that escapes `e.dir`. Additionally, before `os.Create`/`os.Mkdir` in the main loop, `os.Lstat` the destination path and, if it's an existing symlink, `os.Remove` it first (as `helpers/archives/zip_extract.go`'s `extractZipFileEntry`/`extractZipSymlinkEntry` already do) so that a residual symlink from a prior extraction can never be silently followed by a subsequent write.

### Proof of Concept
Go test in `commands/helpers/archive/tarzstd`:
1. Build a temp dir `e.dir`.
2. Extraction #1: hand-craft (not via `Archive`) a tar+zstd stream with one entry: symlink `foo -> /tmp/outside-target` (outside `e.dir`). Call `NewExtractor(...).Extract(ctx)`; assert success and assert `os.Lstat(filepath.Join(e.dir,"foo"))` reports a symlink pointing outside `e.dir`.
3. Create `/tmp/outside-target` as an existing writable regular file (simulating a real-world writable location, e.g. another project's build dir).
4. Extraction #2: craft a second tar+zstd stream with one entry: regular file `foo` with content `"PWNED"`.
5. Call `Extract(ctx)` again with the same `e.dir`.
6. Assert: `os.ReadFile("/tmp/outside-target")` equals `"PWNED"`, proving write-through outside `e.dir`, and assert this happens without any error being returned by `Extract`.
