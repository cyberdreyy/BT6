### Title
Stale confirmations from deleted members are counted toward `num_confirmations`, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` only purges confirmations for requests that the removed member *originated* (`r.member == member`), but never scans the `confirmations` map for entries where the removed member is merely a *confirmer* on someone else's request. `confirm` then counts `confirmations.len() + 1 >= num_confirmations` without checking that each recorded confirmer is still a current member, so a request can execute with fewer than `num_confirmations` live confirmations.

### Finding Description
The invariant claimed by the contract is: `num_confirmations == |{ m in confirmations[request_id] : m ∈ members_at_execution_time }| ` when a request executes. The code breaks this equality.

- `confirm` (`multisig2/src/lib.rs:294-315`) reads the existing `confirmations` set for a `request_id`, and if `confirmations.len() as u32 + 1 >= self.num_confirmations` it executes the request immediately: [1](#0-0) 
This length check makes no attempt to filter out confirmers who are no longer in `self.members`.

- `delete_member` (`multisig2/src/lib.rs:356-379`) only cleans confirmations for requests *created by* the removed member: [2](#0-1) 
It never iterates `self.confirmations` to strip the removed member's string identity from confirmation sets of *other* requests where that member merely confirmed (via `confirm`, not `add_request`).

- `assert_valid_request` (`multisig2/src/lib.rs:407-423`) only checks that the *caller* of the current call is a member; it performs no re-validation of the *already-recorded* confirmers in the set being counted.

Exploit flow (using only ordinary multisig operation, no privileged access needed beyond being one of the existing members with the standard function-call key installed by `add_member` for `MULTISIG_METHOD_NAMES = "add_request,delete_request,confirm,add_and_confirm_request"`):
1. Member X creates request A (e.g. a `Transfer` draining funds) via `add_request`.
2. Member Y confirms request A via `confirm` → `confirmations[A] = {Y}`.
3. Separately, a `DeleteMember { member: Y }` request is created and confirmed to reach `num_confirmations`, executing and removing Y from `self.members` and deleting Y's *own* access key/entries — but `confirmations[A]` still contains `Y`, since A was not created by Y.
4. Member Z (any remaining live member) calls `confirm(A)`. `confirmations[A].len()` is `1` (stale `Y`), so `1 + 1 >= num_confirmations` (e.g., `num_confirmations = 2`) is satisfied and the transfer executes — even though only Z is a genuinely live confirming member at execution time (Y’s confirmation is stale).

None of the existing guards prevent this: `assert_valid_request` validates the *caller*, not the historical confirmer set; `current_member` is only invoked for the new confirmer, not retroactively for already-stored confirmations; `delete_member`'s request-purge logic keys off request ownership (`r.member == member`), not participation as a confirmer.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below `num_confirmations` live members." A stale confirmation from a removed member can be combined with fewer live confirmations than the configured threshold to authorize `Transfer`, `FunctionCall`, `AddKey`, `AddMember`/`DeleteMember`, etc., moving NEAR (or invoking arbitrary calls, e.g. draining wNEAR via `FunctionCall`) out of the multisig account. This is repeatable for every request left with outstanding confirmations at the moment any of its confirmers is removed, and scales with the number of pending requests versus member turnover.

### Likelihood Explanation
This requires no privileged access beyond ordinary multisig membership actions: any member can create/confirm requests using the standard `MULTISIG_METHOD_NAMES` function-call key, and member removal (`DeleteMember`) is a normal, expected multisig operation. The scenario naturally arises whenever a member is removed while they have outstanding confirmations on other pending requests, which is a realistic and low-cost sequence of ordinary transactions (no special balances or accounts needed).

### Recommendation
When executing `delete_member`, iterate `self.confirmations` for **all** requests (not just those authored by the removed member) and strip the removed member's identity from every confirmation set; alternatively, in `confirm`, re-validate at count time that every string in `confirmations[request_id]` still corresponds to a member in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
```rust
// multisig2/src/lib.rs test module addition
#[test]
fn test_stale_confirmation_after_delete_member() {
    let amount = 1_000;
    // members(): alice, bob, key1 (Eg2j...), key2 (TEST_KEY)
    testing_env!(context_with_key(
        PublicKey::from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()),
        amount
    ));
    let mut c = MultiSigContract::new(members(), 2); // num_confirmations = 2

    // Request A: transfer funds, created by key1
    let transfer_request = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let request_a = c.add_request(transfer_request);

    // key2 (TEST_KEY) confirms request A -> confirmations[A] = {key2}
    testing_env!(context_with_key(PublicKey::try_from(TEST_KEY.to_vec()).unwrap(), amount));
    c.confirm(request_a);
    assert_eq!(c.confirmations.get(&request_a).unwrap().len(), 1);

    // Remove key2 via DeleteMember request, created & confirmed by alice + bob (2 confirmations)
    let key2_member = MultisigMember::AccessKey { public_key: PublicKey::try_from(TEST_KEY.to_vec()).unwrap() };
    testing_env!(context_with_account(alice(), amount));
    let delete_request = MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteMember { member: key2_member.clone() }],
    };
    let request_b = c.add_request(delete_request);
    c.confirm(request_b); // 1st confirmation

    testing_env!(context_with_account(bob(), amount));
    c.confirm(request_b); // 2nd confirmation -> executes DeleteMember, removes key2

    // BINDING CHECK: key2 is no longer a member...
    assert!(!c.get_members().contains(&key2_member));
    // ...but its stale confirmation on request A is still present
    assert!(c.confirmations.get(&request_a).unwrap().contains(&key2_member.to_string()));

    // Now a single additional live confirmer (bob) triggers execution of request A,
    // using the stale key2 confirmation to reach num_confirmations=2
    testing_env!(context_with_account(bob(), amount));
    c.confirm(request_a); // should NOT execute (only 1 live confirmer: bob), but does

    // Binding broken: request A executed (removed from requests) with only 1 live confirmer
    assert_eq!(c.requests.len(), 0); // proves execution happened with < num_confirmations live members
}
```
Running this with `cargo test -p multisig2 test_stale_confirmation_after_delete_member` demonstrates `request_a` executes (removed from `self.requests`) even though only one genuinely live member (`bob`) confirmed it, violating `num_confirmations == 2` live confirmers.
