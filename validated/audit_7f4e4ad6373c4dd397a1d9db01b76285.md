### Title
Unbounded per-request insertion into shared `savedCallbacks` map with no per-sender cap allows single restricted-token holder to exhaust `MaxSavedCallbacks` budget and cause resource-exhaustion DoS for all other gateway users - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` unconditionally inserts an entry into `h.savedCallbacks[msg.Body.MessageId]` for every accepted trigger message, with no per-sender quota and no check against `HandlerConfig.MaxSavedCallbacks` at insertion time. The only enforcement of the size limit happens asynchronously in `pruneCallbacks`, which runs on a fixed `CallbackPruneIntervalSec` (default 30s) ticker, so between prune cycles the map can grow without bound and there is no explicit "cache full" rejection path comparable to `requestCache`'s size check.

### Finding Description
The attacker-reachable path is: gateway HTTP endpoint → `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) → for a legacy DON-keyed message, after `msg.Validate()` succeeds, it calls `h.HandleLegacyUserMessage(ctx, msg, callback)` (`gateway.go:269`) → `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`).

This assignment is unconditional — there is no check of `len(h.savedCallbacks)` against `h.config.MaxSavedCallbacks` before insertion, and no per-sender/per-key counter is maintained anywhere in the `handler` struct: [2](#0-1) 

The only place size is enforced is the periodic `pruneCallbacks` goroutine started in `Start`, which fires every `CallbackPruneIntervalSec` seconds (default 30, from `defaultCallbackPruneIntervalSec`) and, after removing expired entries, trims down to `maxSize/2` only if the current count exceeds `maxSize`: [3](#0-2) [4](#0-3) 

Both `HandlerConfig.MaxSavedCallbacks` and `CallbackPruneIntervalSec` are populated only from `NewHandler`'s JSON config parsing and are not attacker-influenceable — they come from operator-configured `HandlerConfig` and default to 20000 / 30 respectively: [5](#0-4) 

However, `MessageId` values are attacker-supplied/unique per submitted message, and `msg.Validate()` in `gateway.go` only checks message structure/signature (and `jsonRequest.ID` length ≤ 200), not sender-specific quotas. Because insertion is unconditional and the pruning cadence is fixed and asynchronous, an attacker who can submit `HandleLegacyUserMessage`-routed requests with unique `MessageId`s faster than the 30-second prune interval (or simply in volume between prune ticks) can push `len(savedCallbacks)` arbitrarily above `MaxSavedCallbacks` (the comment at line 44, `defaultMaxSavedCallbacks = 20000 // could briefly exceed under heavy load`, acknowledges this). Unlike `requestCache.NewRequest` (referenced in the question) which performs an explicit "cache is full" rejection before insertion, `HandleLegacyUserMessage` never rejects on cache-full; it always accepts the trigger, dispatches to DON members, and stores the callback, regardless of current map size.

### Impact Explanation
This is a shared, unpartitioned resource: `savedCallbacks` is a single map guarded by one mutex on the handler instance servicing an entire DON/service. A single restricted-token/gateway-credential holder able to send many uniquely-keyed legacy trigger messages can grow this map far beyond the configured 20000-entry budget between prune cycles, consuming unbounded memory on the gateway process and increasing goroutine/CPU pressure from concurrent `SendToNode` fan-out to all DON members per submitted trigger. This does not directly cause other users' requests to be explicitly rejected (no "full" error path exists), but it does cause uncontrolled memory growth and increased mutex contention that can degrade or crash the shared gateway handler, denying availability to all other tenants of that handler/DON. This matches a resource-exhaustion / availability-impact class rather than fund loss or key disclosure.

### Likelihood Explanation
Precondition is minimal: any actor with a valid signature/credential accepted by `msg.Validate()` for the target DON (e.g., a restricted API token or external-initiator-equivalent gateway credential) can submit an arbitrary number of uniquely-`MessageId` legacy trigger messages within a short window (less than the 30s default prune interval, or sustained faster than pruning can catch up), with no server-side check preventing this. This is fully repeatable and requires no operator/admin access, no race condition beyond normal concurrent HTTP submission, and no exploitation of a parsing bug — it is a straightforward volumetric flood against an unbounded insertion path.

### Recommendation
Enforce the size cap synchronously at insertion time in `HandleLegacyUserMessage`: under `h.mu`, check `len(h.savedCallbacks) >= h.config.MaxSavedCallbacks` before adding a new entry and return an explicit "cache is full" / rate-limited error response (mirroring `requestCache.NewRequest`'s explicit check) instead of relying solely on the asynchronous `pruneCallbacks` ticker. Additionally, consider adding a per-sender/per-node quota (e.g., tracked by node address or requester identity) so that no single sender can consume the entire shared budget, and consider making the prune interval tighter or triggering an eager prune when the map size crosses a high-water mark.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Use `setupHandler(t)` to construct a `*handler` with `config.MaxSavedCallbacks` set to a small value (e.g., 5) and `config.CallbackPruneIntervalSec` set large enough that the prune ticker does not fire during the test (or simply don't call `Start`/`pruneCallbacks`).
2. Loop and call `handler.HandleLegacyUserMessage(ctx, msg, callback)` directly (bypassing HTTP) with valid `webapicap.TriggerRequestPayload` bodies and unique `msg.Body.MessageId` values (e.g., `id-0` .. `id-20`), for a count > `MaxSavedCallbacks` (e.g., 20 messages against cap of 5).
3. After each call, assert `err == nil` and that `callback.Wait` does not immediately return a "cache full" style `api.HandlerError`/rejection.
4. Lock `handler.mu` and assert `len(handler.savedCallbacks) > handler.config.MaxSavedCallbacks` (e.g., `== 20`, not capped at 5), proving unconditional/unbounded insertion.
5. Contrast by pointing to `requestCache_test.go`'s existing "request cache is full" test case demonstrating explicit-cap-check behavior in that component, to highlight the asymmetry with `HandleLegacyUserMessage`'s lack of an equivalent guard.

func (h *handler) Start(context.Context) error {
	return h.StartOnce(handlerName, func() error {
		h.wg.Go(func() {
			ticker := time.NewTicker(time.Duration(h.config.CallbackPruneIntervalSec) * time.Second)
			defer ticker.Stop()
			for {
				select {
				case <-ticker.C:
					h.pruneCallbacks()
				case <-h.stopCh:
					return
				}
			}
		})
		return nil
	})

			entries = append(entries, entry{id, cb.createdAt})
