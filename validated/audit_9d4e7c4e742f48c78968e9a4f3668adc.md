### Title
Unprivileged front-running of `initialize_fee_state` allows attacker to seize global fee admin authority - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
`InitFeeState` only requires `payer: Signer<'info>` and relies on the Anchor `init` constraint on the `fee_state` PDA (seeded solely by `FEE_STATE_SEED`) to prevent re-initialization. There is no check binding the caller to a privileged deployer/upgrade authority, so any signer can call `initialize_fee_state` first and set `admin_key`/`fee_wallet` to arbitrary values, permanently becoming `FeeState.global_fee_admin`/`global_fee_wallet` for the entire program.

### Finding Description
The account struct `InitFeeState` is defined with: [1](#0-0) 

The `payer` field is only constrained as `Signer<'info>` with `#[account(mut)]`, and the sole protection against duplicate/unauthorized invocation is the `init` constraint (which just guarantees the PDA doesn't already exist), not any check that `payer` matches a known program-upgrade authority or hardcoded admin pubkey. Inside `initialize_fee_state`, the `admin_key` and `fee_wallet` parameters supplied by the caller are written directly into the global `FeeState` account with no validation: [2](#0-1) 

Since the PDA `[FEE_STATE_SEED]` is deterministic and global (not per-caller), whichever transaction lands first claims the account. Any unprivileged party that observes the pending/expected deployment (e.g., watches for the program's first `InitFeeState`-eligible slot, or simply races to call it before the legitimate deployer) can submit their own `initialize_fee_state(admin_key=attacker, fee_wallet=attacker_wallet, ...)` and it will succeed identically to the legitimate call, since Anchor's `init` only fails if the account already exists — it performs no authority check on who is allowed to create it first.

### Impact Explanation
`FeeState.global_fee_admin` is the authority checked by `edit_global_fee_state` (and related global-fee-admin-gated instructions) for adjusting protocol-wide program fees, flat SOL fees, liquidation/order fee caps, and the fee wallet destination. If an attacker wins the race, they gain durable control over all future global fee parameters and the destination wallet for protocol fee sweeps across every bank/group in the deployment — a protocol-wide authorization bypass with direct value-redirection impact (fees can be redirected to attacker's own wallet, and legitimate admins lose all ability to correct it without a program upgrade/migration).

### Likelihood Explanation
This requires the very narrow precondition that the `FeeState` PDA has not yet been created — i.e., it is only exploitable in the brief window during initial mainnet deployment of a fresh program (or a redeploy that resets the PDA namespace), before the legitimate deployer's `initialize_fee_state` transaction confirms. Once deployed and initialized correctly, the `init` constraint permanently blocks any further calls, so this is not exploitable against an already-running, correctly-initialized deployment. Feasibility hinges on mempool visibility/timing at the exact moment of first deployment, which is a real but narrow and one-time attack window per deployment, not a repeatable ongoing risk against live infrastructure.

### Recommendation
Add an explicit authorization check to `InitFeeState`, e.g., require `payer` to equal the program's upgrade authority read via `bpf_loader_upgradeable` `ProgramData` account, or hardcode/verify against a known deployer pubkey constant, before allowing `init` to proceed. Alternatively, bundle `initialize_fee_state` in the same atomic transaction as the program's initial deployment/upgrade instruction so no external transaction can be interleaved.

### Proof of Concept
Rust integration test plan (using existing test harness, e.g. `test-utils/src/marginfi_group.rs` init helpers):
1. Deploy the program fresh in a local validator/bankrun environment without pre-initializing `FeeState`.
2. From an unprivileged keypair (not the intended deployer/upgrade authority), construct and send `initialize_fee_state(admin_key = attacker_pubkey, fee_wallet = attacker_wallet, ...)` referencing the `[FEE_STATE_SEED]` PDA.
3. Assert the transaction succeeds and `FeeState.global_fee_admin == attacker_pubkey`.
4. Subsequently have the legitimate deployer attempt the same `initialize_fee_state` call; assert it fails with an account-already-in-use/`init` constraint error, confirming the attacker's values are permanently locked in.
5. As a control, assert that `edit_global_fee_state` called by the legitimate deployer now fails/`ConstraintHasOne`-type authorization error because `global_fee_admin` no longer matches them, while the attacker's signature succeeds — demonstrating full authority takeover.
