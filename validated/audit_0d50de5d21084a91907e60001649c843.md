### Title
Fee-on-transfer underlyings underfund epoch repayments and withdrawal reserves - (File: `contracts/IdleCDOEpochVariant.sol`)

### Summary
Credit-vault accounting assumes every ERC20 transfer credits the recipient with the nominal `amount`. If a configured underlying starts charging a transfer fee after funds are deposited—such as a future USDT fee—the borrower repayment transfers less than the amount `stopEpoch` accounts for, while withdrawal funding and strategy backing continue to use the nominal amount. This can revert `stopEpoch`, strand borrower repayments in the CDO, and leave withdrawal receipts underfunded.

### Finding Description
`IdleCreditVault` accepts the underlying as an unconstrained initialization parameter and does not reject fee-on-transfer tokens. [1](#0-0) 

At epoch end, `IdleCDOEpochVariant._stopEpoch` calculates the nominal interest and pending withdrawal amount, then pulls that sum from the borrower through `getFundsFromBorrower`. [2](#0-1) [3](#0-2) 

The CDO subsequently calls `IdleCreditVault.collectWithdrawFunds(_pendingWithdraws)`, which clears the nominal pending withdrawal basis before pulling the same nominal amount from the CDO. [4](#0-3) [5](#0-4) 

With a 1% transfer tax, a requested 100-unit borrower repayment credits the CDO with only 99 units. A subsequent 99-unit withdrawal-reserve collection again transfers only 98.01 units to the strategy, but `collectWithdrawFunds` clears the full 99-unit obligation. Claims later attempt to transfer the full receipt amount from the underfunded reserve. [6](#0-5) 

The same nominal-accounting issue exists in the programmable-borrower repayment path: `_repay` debits the full `assets` debt after `safeTransferFrom`, even though the facility receives only `assets - tax`. [7](#0-6) 

The initial deposit path partially measures the amount received by the CDO, but it then calls the strategy with the original nominal `_amount`, making already-taxed assets unusable at entry. [8](#0-7)  The more impactful case is therefore an initially untaxed asset whose transfer fee is enabled after deposits, which is the same future-fee risk described for USDT-style tokens.

### Impact Explanation
A single taxed epoch repayment can permanently disrupt settlement:

1. Existing lenders hold positions funded before the tax was enabled.
2. The borrower approves and pays the full epoch liability.
3. The CDO receives less than the nominal liability because the token deducts a fee.
4. `collectWithdrawFunds` may clear the nominal receipt basis while delivering fewer assets to the strategy.
5. A later nominal transfer—strategy funding, fee payment, or interest deposit—can revert because the CDO balance is short by the transfer tax.
6. Since the successful external borrower pull has already happened, failed settlement leaves repaid assets stranded in the CDO and withdrawal claims can be underfunded.
7. A subsequent `finalizeDefault` call skims raw CDO underlyings as donations before recovery accounting, potentially diverting the stranded repayment to `feeReceiver`. [9](#0-8) [10](#0-9) 

For a vault with 1,000,000 units of liabilities and a 1% transfer tax, each borrower repayment leg creates a 10,000-unit first-order deficit. Further outbound CDO-to-strategy transfers create additional deficits. This breaks the solvency invariant that one funded withdrawal receipt corresponds to one unit of reserved underlying.

### Likelihood Explanation
The vulnerability requires the configured underlying to charge a transfer fee. A token that already charges fees generally cannot complete the initial deposit path because the strategy pull uses the pre-tax nominal amount, but a currently untaxed token can enable fees later while positions remain outstanding. [8](#0-7) 

USDT has an owner-configurable transfer-fee mechanism, so this is not limited to exotic tokens. No malicious privileged role in the vault is required: normal lender deposits, normal epoch operations, and an honest borrower approval are sufficient once the token fee is enabled.

### Recommendation
Do not treat requested transfer amounts as received amounts. At minimum:

- Measure `balanceAfter - balanceBefore` around every inbound borrower, CDO, strategy, deposit, recovery, and programmable-borrower repayment transfer.
- Fund withdrawal reserves using the actual received amount and only clear the amount actually funded.
- Require the actual amount received to cover each accounting leg before clearing debt or receipt basis.
- Avoid leaving successful external borrower pulls outside the revert-protected scope of a settlement operation; make repayment collection and reserve funding atomic or explicitly reconcile partial receipts without double-pulling the borrower on retries.
- Either explicitly reject fee-on-transfer underlyings during initialization or make every accounting path use actual received amounts.
- Add tests where a configured token starts at 0% tax and enables a nonzero tax before `stopEpoch`, `collectWithdrawFunds`, `collectInstantWithdrawFunds`, recovery finalization, and `ProgrammableBorrower.repay`.

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "./IdleCreditVault.t.sol";

interface IMutableTether {
    function setParams(uint256 basisPoints, uint256 maxFee) external;
}

contract CreditVaultFeeOnTransferPoC is TestIdleCreditVault {
    // USDT owner at the suite's fork block; replace if the fork block changes.
    address internal constant TETHER_OWNER =
        0xC6CDE7C39eB2f0F0095F41570af89eFC2C1Ea828;

    function testFeeOnTransferBreaksEpochSettlement() public {
        uint256 depositAmount = 1_000_000e6;
        uint256 pendingAmount = 990_000e6;
        address lender = makeAddr("lender");

        // Deposit while the underlying has no fee.
        deal(defaultUnderlying, lender, depositAmount);
        vm.startPrank(lender);
        IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), depositAmount);
        cdoEpoch.depositAA(depositAmount);
        vm.stopPrank();

        // Open a large pending withdrawal before the epoch starts.
        vm.prank(lender);
        cdoEpoch.requestWithdraw(pendingAmount, cdoEpoch.AATranche());

        // Start the epoch normally while transfers are still untaxed.
        vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
        vm.prank(manager);
        cdoEpoch.startEpoch();

        // Enable a 0.1% token transfer fee after positions already exist.
        // The exact parameter values satisfy USDT's bounded setParams checks.
        vm.prank(TETHER_OWNER);
        IMutableTether(defaultUnderlying).setParams(10, 49);

        // Borrower honestly supplies and approves the full nominal liability.
        deal(defaultUnderlying, borrower, 1_100_000e6);
        vm.prank(borrower);
        IERC20Detailed(defaultUnderlying).approve(
            address(cdoEpoch),
            type(uint256).max
        );

        vm.warp(cdoEpoch.epochEndDate() + 1);

        // Settlement pulls the borrower successfully, but the recipient gets
        // less than nominal accounting assumes. Later nominal funding fails
        // or leaves the withdrawal reserve short.
        vm.prank(manager);
        vm.expectRevert();
        cdoEpoch.stopEpoch(0, 1);

        // The borrower repayment is stranded in the CDO even though
        // epoch settlement did not complete.
        assertGt(IERC20Detailed(defaultUnderlying).balanceOf(address(cdoEpoch)), 0);
        assertFalse(cdoEpoch.defaulted());
        assertTrue(cdoEpoch.isEpochRunning());
    }
}
```
