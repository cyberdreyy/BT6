### Title
Missing access control on `replace`/`clean` allows any account to overwrite contract storage during a migration - (File: `state-manipulation/src/lib.rs`)

### Summary
The `replace` and `clean` exports in `state-manipulation/src/lib.rs` write/remove raw storage keys supplied entirely by the caller with **no** `predecessor_id`, owner, or key check whatsoever. While this contract is temporarily deployed on an account to perform a state migration, any unprivileged account can call `replace` (or `clean`) in the same block as the operator and have its own arbitrary key/value pairs become the final on-chain state, since both calls share the identical unrestricted write path.

### Finding Description
The invariant the question describes is: `final_storage_state == operator_intended_state`, i.e. only the migration operator's writes should determine the resulting contract storage after a migration. Tracing the code:

- `replace()` reads `input()`, deserializes a JSON body containing arbitrary base64 `entries: Vec<(key, value)>`, and calls `storage_write` for every pair with **no caller identity check at all**: [1](#0-0) 

- `clean()` similarly deserializes arbitrary base64 `keys` and calls `storage_remove` for each, again with no check: [2](#0-1) 

- Neither function references `env::predecessor_id()`, an owner field, or any authorization primitive — the only guard present in the file is the `#[cfg]` feature-gate that decides which export exists at compile time, not who may call it: [3](#0-2) 

Because `storage_write`/`storage_remove` operate directly on raw NEAR storage keys with no namespacing or predecessor binding, whichever transaction executes last within the block (or simply after the operator's) wins on any key that is written by both. An ordinary account — not the contract account, not its deployer — can submit its own `replace` call with attacker-chosen `entries` (e.g., overwriting a serialized `owner_id`, staking pool accounting fields, or an FT `total_supply`/balance record at the exact storage key used by whatever production contract is redeployed after the migration window). Since the contract enforces no principal restriction, the "only one principal can drive a migration" invariant does not hold: any caller is an equally valid principal from the contract's point of view.

None of the standard guards referenced in the validation checklist (`assert_owner`, `assert_called_by_foundation`, `assert_self()`, `is_promise_success()`, `assert_one_yocto()`, etc.) appear anywhere in this file — there is nothing to check.

### Impact Explanation
Whoever's `replace`/`clean` transaction lands last for a given storage key controls that key's final value before the operator redeploys the real contract. If the attacker races the operator and wins on keys such as `owner_id`, staked/unstaked balances, vesting/lockup fields, or FT ledger rows, the attacker can set arbitrary values that a subsequently-redeployed production contract will trust as legitimate state — e.g., granting themselves ownership, inflating a balance, or unlocking funds early. This directly matches the Critical category: "an account whitelisted or a lockup deployed with parameters its rightful creator never chose" / accounting values diverging from reality that another party (the redeployed contract) will settle on. The attack is repeatable on any account where this migration helper is temporarily deployed, and costs only a normal transaction fee.

### Likelihood Explanation
Preconditions: the account under migration must have this `state-manipulation` WASM temporarily deployed (which is the documented intended use per `state-manipulation/README.md`), and the attacker must know/guess the account ID and submit a `replace`/`clean` call in the same block window before the operator redeploys the real contract. No special privilege, balance, or key is required — any account able to send a NEAR transaction can call the exported method, since it is a plain public function with zero predecessor checks. This is fully feasible and cheap; the only timing constraint is racing within the (short) migration window, which is realistic given NEAR's public mempool/block visibility.

### Recommendation
Add an explicit authorization check at the top of both `replace` and `clean`, e.g. assert that `env::predecessor_id() == env::current_account_id()` (self-call only, invoked via a `Promise` from a trusted account/key) or bind the calls to a hard-coded owner account id compiled into the contract, so that only the account owner/deployer performing the migration can invoke these exports.

### Proof of Concept
```rust
// near-workspaces sandbox test, added to state-manipulation/src/lib.rs tests module (illustrative)
#[tokio::test]
async fn attacker_overwrites_operator_migration_same_block() -> anyhow::Result<()> {
    let worker = workspaces::sandbox().await?;
    let wasm = tokio::fs::read("res/state_manipulation.wasm").await?;
    let contract = worker.dev_deploy(&wasm).await?; // simulates account mid-migration

    let operator = worker.dev_create_account().await?;
    let attacker = worker.dev_create_account().await?; // ordinary account, not contract/deployer

    let key = base64::encode(b"owner_id");
    let operator_value = base64::encode(b"operator.near");
    let attacker_value = base64::encode(b"attacker.near");

    // Operator's legitimate migration write
    operator
        .call(&worker, contract.id(), "replace")
        .args_json(serde_json::json!({ "entries": [[key.clone(), operator_value]] }))?
        .transact().await?;

    // Attacker races in the same block / immediately after, no auth required
    attacker
        .call(&worker, contract.id(), "replace")
        .args_json(serde_json::json!({ "entries": [[key.clone(), attacker_value.clone()]] }))?
        .transact().await?;

    let state = contract.view_state(&worker, None).await?;
    let final_value = state.get(&base64::decode(&key)?).unwrap();

    // Binding broken: final state == attacker's write, not operator's intended state
    assert_eq!(final_value, &base64::decode(&attacker_value)?);
    Ok(())
}
```
This demonstrates that `final_storage_state != operator_intended_state`, confirming the invariant "only one principal can drive a migration" is violated by any unprivileged account.

#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    #[derive(serde::Deserialize)]
    struct ReplaceInput<'a> {
        #[serde(borrow)]
        entries: Vec<(&'a str, &'a str)>,
    }

    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}
