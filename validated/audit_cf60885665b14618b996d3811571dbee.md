### Title
Loss-adjusted withdrawal haircut is keyed to the loss epoch, not the user's request epoch — earlier-epoch withdraw receipts escape the haircut and are paid at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
When `stopEpochWithDuration` realizes a loss that must be shared with pending withdraw receipts, `collectWithdrawFunds` stores the recovery price under the *current* `epochNumber` (`lossRecoveryPriceByEpoch[epochNumber]`, line 421). But when a user later claims, `_claimLossAdjustedWithdrawRequest` looks up the haircut under `lastWithdrawRequest[_user]` — the epoch in which *that user* requested the withdrawal (lines 790–791). Any pending receipt whose request epoch differs from the epoch in which the loss is recorded finds `lossRecoveryPriceByEpoch[theirEpoch] == 0`, skips the loss-adjusted path entirely, and is paid at par through `_claimFundedWithdrawRequest`. This is the direct analog of a use-after-free: a stale/dangling epoch pointer dereferences the wrong state, so the haircut that was applied to the pending bucket is silently lost for those users.

### Finding Description
- `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the *aggregate* `pendingWithdraws`, zeroes `pendingWithdraws`, and records the price under `epochNumber` — the epoch at the time of the loss (line 421).
- `requestWithdraw` records each user's receipt under `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch]` (lines 282, 293).
- `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` only applies the haircut when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` (lines 790–792). If the user's last request was made in an earlier epoch than the one in which the loss crystallized (e.g., the request sat pending across more than one buffer/stop cycle, or `epochNumber` was incremented by `deposit()` inside `stopEpoch` before `collectWithdrawFunds` ran, lines 607–611), the lookup misses.
- The claim then falls into `_claimFundedWithdrawRequest`, whose only gate is `epochNumber <= lastWithdrawRequest[_user]` (line 326). Once the epoch has advanced past the request epoch, the full `withdrawsRequests[_user]` is burned and paid 1:1 via `_transferFundedClaim` (lines 338–349).
- The guard in `requestWithdraw` (lines 263–270) only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, so it does not prevent this mismatch either — it re-derives the same wrong key.

### Impact Explanation
Broken invariant: loss socialization / fair payout of pending receipts. The borrower only funds `pendingToFund = pendingBasis - pendingLoss` (line 458), so the strategy holds strictly less than the aggregate receipt basis. A user whose receipt escapes the haircut withdraws 100% of their basis, consuming more than their pro-rata share of the funded amount. Receipts that *do* resolve to the correct loss epoch are then underpaid or blocked by the `NotAllowed` revert in `_transferFundedClaim` (line 904) once the balance is drained — direct theft of other users' funded withdrawals, or permanent freezing of the remainder of the loss-adjusted bucket. Quantified: an unprivileged user who requested `R` underlying in an epoch `E` prior to the loss epoch `L` receives `R` instead of `R * lossRecoveryPrice / RECOVERY_FULL`, stealing `R * (1 - price)` from honest claimants.

### Likelihood Explanation
Attacker is an ordinary KYC-passing lender who calls `requestWithdraw` and `claimWithdrawRequest` — no privileged role. The exploit requires only that a `stopEpochWithDuration(_lossAmount > 0)` occur while the attacker's pending receipt's `lastWithdrawRequest` differs from the `epochNumber` at which `collectWithdrawFunds` records the price. Since `epochNumber` is bumped inside `deposit()` during stopEpoch processing (lines 607–611), whether the mismatch hits *all* pending receipts or only earlier-epoch ones depends on the exact call ordering in `IdleCDOEpochVariant.stopEpochWithDuration`, which I could not fully confirm within this analysis; however, the per-user-epoch lookup design (`withdrawsRequestsByEpoch`) makes the aggregate-keyed write at line 421 incorrect under any ordering in which request epoch ≠ loss-record epoch, and there is no compensating normalization between the two keys anywhere in the claim path.

### Recommendation
Record and look up loss-recovery prices consistently per request epoch: either iterate/tag each pending receipt's epoch when the loss is realized (e.g., track `pendingWithdrawsByEpoch`), or have `_claimLossAdjustedWithdrawRequest` check whether a receipt was still unfunded at the loss epoch rather than keying on `lastWithdrawRequest`. At minimum, apply the haircut whenever the user's request epoch is `<=` the epoch for which a `lossRecoveryPriceByEpoch` was stored while the receipt was pending.

### Proof of Concept
Foundry fork outline (mirroring `test/foundry/IdleCDOEpochQueue.t.sol` around lines 811–858):

```solidity
// Setup: standard IdleCDOEpochVariant + IdleCreditVault, AA tranche depositors.
// 1. Attacker deposits AA, then during buffer of epoch E calls
//    cdoEpoch.requestWithdraw(attackerTranches, AAtranche) -> lastWithdrawRequest[attacker] = E.
// 2. Honest user requests withdraw in a later buffer epoch E' so that
//    lastWithdrawRequest[honest] = E' and epochNumber at loss time == E' (or vice versa,
//    depending on whether deposit() increments epochNumber before collectWithdrawFunds).
// 3. Manager calls stopEpochWithDuration(apr, 0, duration, lossAmount) with lossAmount > 0;
//    borrower funds only pendingToFund < pendingBasis.
//    -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[E''] where E'' != E.
// 4. Attacker calls cdoEpoch.claimWithdrawRequest():
//    - _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[E] == 0 -> skipped.
//    - _claimFundedWithdrawRequest: epochNumber > E -> pays withdrawsRequests[attacker] at par.
// 5. assert attacker received full basis R (not R * price / RECOVERY_FULL);
//    assert honest user's subsequent claim receives less than R_h * price / RECOVERY_FULL
//    or reverts NotAllowed in _transferFundedClaim.
```

One aspect remains unverified: the exact ordering of `deposit()`'s `epochNumber` increment relative to `collectWithdrawFunds` inside `stopEpochWithDuration`. If the increment happens first, the haircut is recorded under the *new* epoch while *all* pending receipts point at the *old* epoch, making the escape universal rather than limited to earlier-epoch requesters — an even more severe variant of the same defect. A full PoC should pin down that ordering, but the keying mismatch itself is demonstrable either way.
