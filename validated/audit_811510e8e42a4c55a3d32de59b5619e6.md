## Title
Unbounded recursive descent in `TrieNode::decode` allows stack-overflow denial of service in the fault-proof program via a crafted MPT node preimage - (File: `crates/proof/mpt/src/node.rs`)

## Summary
`TrieNode`'s RLP `Decodable` implementation recursively parses nested Extension nodes with no depth limit, and the preimage oracle client that supplies the raw bytes being decoded imposes no maximum length on a single preimage. A dispute-game participant (or any party supplying preimages consumed by the fault-proof program) can submit one crafted, hash-valid preimage blob that encodes a deep chain of nested Extension nodes, driving `TrieNode::decode` into unbounded native recursion and overflowing the program's stack. This mirrors CVE-2019-12798's root cause: a parser with no bound on the size/depth of the structure it builds, leading to overflow.

## Finding Description
`TrieNode::decode` dispatches on the RLP header of a node [1](#0-0) . For a 2-element list it calls `try_decode_leaf_or_extension_payload`, and for an Extension node this function recursively invokes `Self::decode(buf)` on the *same* buffer to parse the pointed-to child node [2](#0-1) . There is no depth counter or recursion-depth argument anywhere in this call chain (unlike, e.g., the CBOR parser elsewhere in the codebase, which explicitly tracks `depth` and enforces `MAX_CBOR_NESTING_DEPTH`) [3](#0-2) .

Normally the Ethereum trie invariant "nodes ≥32 bytes are blinded" (see the `Encodable` impl's `blinded_length`/blinding logic [4](#0-3) ) would keep any single unblinded subtree small when honestly produced. But `Decodable::decode` never checks or enforces this invariant on the bytes it is given — it just recursively parses whatever RLP list structure exists in the buffer. An attacker who controls the raw preimage bytes (which only need to keccak256-hash to the commitment they registered) can therefore construct one buffer that nests thousands of minimal Extension-node headers (a couple of bytes of RLP + a 1-byte path each), each one legally "under 32 bytes" from the decoder's point of view even though the whole encloses far more.

The buffer size that reaches `TrieNode::decode` is itself unbounded: `OracleReader::get` reads a host-supplied 8-byte big-endian length prefix and blindly allocates and reads that many bytes with no maximum-size check [5](#0-4) . Every caller in the fault-proof program path (`OracleL1ChainProvider::trie_node_by_hash`, `get_trie_account`, disk/other providers) feeds that unbounded byte slice straight into `TrieNode::decode` [6](#0-5) [7](#0-6) .

## Impact Explanation
Decoding attacker-chosen state/storage-trie or account-trie nodes is a mandatory step of the derivation performed by the fault-proof program while it computes a claimed output root during dispute resolution. A single oversized/deeply-nested preimage causes unbounded native call-stack growth in `TrieNode::decode`, which will exhaust the process/emulated stack and crash or corrupt execution of the fault-proof program. This can prevent an honest party from producing the correct output root during a dispute-game step (denial of service on the proving path) or otherwise halt the node process handling that step — matching the "node halt" / "wrong provable output root" impact classes in scope.

## Likelihood Explanation
Reachability requires only that the attacker be able to make the fault-proof program open/decode a trie node whose preimage they control the raw bytes of (i.e., they pick bytes `B`, use `keccak256(B)` as the pointer value somewhere reachable in the derivation, and serve `B` when the preimage is requested). This is achievable by any dispute-game participant supplying preimages for the derivation, since preimage integrity is enforced only by hash equality, not by structural/size limits. No signature or privileged role is required — likelihood is high once such a preimage is queried.

## Recommendation
- Add an explicit recursion-depth parameter to `TrieNode::decode` (and `try_decode_leaf_or_extension_payload`), threaded through every recursive call, and reject decoding once a maximum depth (e.g., matching the maximum possible hexary trie depth, ~64) is exceeded — the same pattern already used by `CborItem::read_at`'s `MAX_CBOR_NESTING_DEPTH` guard.
- Enforce a maximum preimage length in `OracleReader::get`/`get_exact` before allocating/reading the host-declared length, rejecting preimages above a sane bound before they are handed to the RLP decoder.

## Proof of Concept
1. Construct a byte buffer `B` that RLP-encodes a chain of `N` nested `Extension` nodes, each of the minimal form `rlp([single_nibble_path, child])`, terminating in a small `Leaf`. Each level costs only a few bytes of RLP overhead, so `N` can be made very large (tens of thousands to millions) within a single preimage of a few MB.
2. Register `keccak256(B)` as a `TrieNode::Blinded` commitment reachable from the account/storage trie root used by the fault-proof program's derivation (e.g., as the value pointed to during a state read for a chosen dispute step).
3. When the fault-proof program's `TrieProvider` implementation (e.g. `OracleL1ChainProvider::trie_node_by_hash`) is asked to open that commitment, it calls `TrieNode::decode(&mut B.as_ref())`, which recurses `N` times through `Self::decode` → `try_decode_leaf_or_extension_payload` → `Self::decode`, with no depth check, exhausting the stack and crashing/aborting the program before it can produce a valid output root.

    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.

                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }

impl<C> PreimageOracleClient for OracleReader<C>
where
    C: Channel + Send + Sync,
{
    /// Get the data corresponding to the currently set key from the host. Return the data in a new
    /// heap allocated `Vec<u8>`
    async fn get(&self, key: PreimageKey) -> PreimageOracleResult<Vec<u8>> {
        trace!(target: "oracle_client", key = %key, "Requesting data from preimage oracle");

        let length = self.write_key(key).await?;

        if length == 0 {
            return Ok(Default::default());
        }

        let mut data_buffer = alloc::vec![0; length];

        trace!(target: "oracle_client", key = %key, "Reading data from preimage oracle");

        // Grab a read lock on the preimage channel to read the data.
        self.channel.read_exact(&mut data_buffer).await?;

        trace!(target: "oracle_client", key = %key, "Successfully read data from preimage oracle");

        Ok(data_buffer)
    }
