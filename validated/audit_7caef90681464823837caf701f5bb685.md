### Title
`StakingPool.rewards_pool` Balance Can Be Insufficient to Cover Exchange-Rate-Implied Rewards, Permanently Locking Staker Rewards — (File: `crates/sui-framework/packages/sui-system/sources/staking_pool.move`)

### Summary

In `sui_system::staking_pool`, the `withdraw_rewards` function silently caps the reward payout to `pool.rewards_pool.value()` when the actual `rewards_pool` balance is less than what the stored exchange rate implies. The code itself acknowledges this with a `// TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN.` comment. The result is that stakers permanently lose the difference between their exchange-rate-entitled rewards and what the pool can actually pay — an exact analog of the external "contract records prize amounts but does not enforce actual balance" bug class.

### Finding Description

`StakingPool` maintains two separate accounting values for rewards:

1. `sui_balance` — a `u64` counter updated at epoch boundaries that tracks total SUI in the pool (principal + rewards). It is used to compute and store `PoolTokenExchangeRate` entries.
2. `rewards_pool` — an actual `Balance<SUI>` object that holds only the rewards portion. [1](#0-0) 

These two values are expected to stay in sync, but they can diverge through two mechanisms:

**Mechanism 1 — Integer division truncation across multiple stakers.** `get_sui_amount` uses integer division. When N stakers each withdraw their proportional share, the sum of individually truncated amounts can exceed the actual `rewards_pool` balance.

**Mechanism 2 — `sui_balance` underflow.** In `process_pending_stake_withdraw`, if `pending_total_sui_withdraw > sui_balance`, `sui_balance` is clamped to `0` and the deficit is stored in `UnderflowSuiBalance`. The exchange rate recorded at the next epoch boundary is therefore computed from a `sui_balance` that has been artificially zeroed, while `rewards_pool` still holds real SUI. Subsequent stakers who staked before the underflow epoch will compute a reward entitlement based on the pre-underflow exchange rate, but the pool cannot pay it. [2](#0-1) 

When a staker calls `request_withdraw_stake`, it calls `withdraw_rewards`:

```move
fun withdraw_rewards(...): Balance<SUI> {
    let exchange_rate = pool.pool_token_exchange_rate_at_epoch(epoch);
    let total_sui_withdraw_amount = exchange_rate.get_sui_amount(pool_token_withdraw_amount);
    let mut reward_withdraw_amount = if (total_sui_withdraw_amount >= principal_withdraw_amount) {
        total_sui_withdraw_amount - principal_withdraw_amount
    } else 0;

    // This may happen when we are withdrawing everything from the pool and
    // the rewards pool balance may be less than reward_withdraw_amount.
    // TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN.
    reward_withdraw_amount = reward_withdraw_amount.min(pool.rewards_pool.value());
    pool.rewards_pool.split(reward_withdraw_amount)
}
``` [3](#0-2) 

The `.min(pool.rewards_pool.value())` silently reduces the payout. No error is raised, no event is emitted, and the shortfall is never recorded or compensated. The staker's `StakedSui` object is consumed and destroyed, so the claim is permanently lost.

The same silent cap appears in `calculate_rewards` (the view function), meaning the UI/RPC layer also reports the reduced amount, hiding the discrepancy from users: [4](#0-3) 

### Impact Explanation

**Impact: Medium — permanent fund lock / harmful smart-contract behavior.**

Any ordinary SUI holder who stakes and later unstakes can receive fewer SUI rewards than the exchange rate they staked under entitles them to. The shortfall is permanently unclaimable: the `StakedSui` receipt is destroyed on withdrawal, so there is no second attempt. The lost SUI remains stranded in the pool's `rewards_pool` balance, inaccessible to the staker who earned it. This matches the HackenProof "permanent fund lock" and "harmful smart-contract behavior" impact classes.

### Likelihood Explanation

**Likelihood: Medium.**

The condition is reachable by any staker without any privileged action. It is triggered by the normal combination of:
- Multiple stakers withdrawing from the same pool in the same epoch (integer truncation path), or
- A pool epoch where `pending_total_sui_withdraw` exceeds `sui_balance` (underflow path, which the code explicitly handles with `UnderflowSuiBalance`).

The developers' own `TODO` comment confirms the condition is observed in practice.

### Recommendation

1. **Enforce the invariant at deposit time.** After `deposit_rewards`, assert that `pool.rewards_pool.value() >= (pool.sui_balance - sum_of_all_principals)`. Move's linear type system makes this straightforward.
2. **Remove the silent cap.** Replace `reward_withdraw_amount.min(pool.rewards_pool.value())` with an `assert!(pool.rewards_pool.value() >= reward_withdraw_amount, EInsufficientRewardsPoolBalance)` so that the invariant violation is surfaced rather than silently absorbed.
3. **Resolve the `UnderflowSuiBalance` root cause.** The underflow in `process_pending_stake_withdraw` is the deeper source of the divergence; it should be investigated and fixed rather than papered over.

### Proof of Concept

1. Validator V has a `StakingPool` with `sui_balance = 200 SUI`, `rewards_pool = 100 SUI` (100 SUI principal held in `StakedSui` objects, 100 SUI rewards).
2. Staker A and Staker B each hold `StakedSui` receipts entitling them to 50 SUI of rewards each (per the stored exchange rate).
3. Due to integer truncation, `get_sui_amount` returns 51 SUI of rewards for Staker A when they withdraw first. `rewards_pool` is now 49 SUI.
4. Staker B calls `request_withdraw_stake`. `withdraw_rewards` computes `reward_withdraw_amount = 50`, but `pool.rewards_pool.value() = 49`. The `.min()` cap silently reduces the payout to 49 SUI.
5. Staker B's `StakedSui` is destroyed. The 1 SUI shortfall is permanently unclaimable.

The same scenario is reachable via the `UnderflowSuiBalance` path at larger scale: if `pending_total_sui_withdraw` exceeds `sui_balance` in one epoch, the exchange rate recorded for the next epoch is computed from `sui_balance = 0`, causing all stakers who staked before that epoch to have their reward entitlement silently zeroed by the `.min()` cap. [5](#0-4)

fun process_pending_stake_withdraw(pool: &mut StakingPool) {
    pool.sui_balance = if (pool.sui_balance >= pool.pending_total_sui_withdraw) {
        pool.sui_balance - pool.pending_total_sui_withdraw
    } else {
        let diff = pool.pending_total_sui_withdraw - pool.sui_balance;
        // While this key is expected to be removed in the next call to `process_pending_stake`,
        // we do not call `process_pending_stake` for inactive pools — skip the bookkeeping.
        if (!pool.is_inactive()) {
            pool.extra_fields.add(UnderflowSuiBalance {}, diff);
        };
        0
    };

    pool.pool_token_balance = if (pool.pool_token_balance >= pool.pending_pool_token_withdraw) {
        pool.pool_token_balance - pool.pending_pool_token_withdraw
    } else {
        0
    };

    pool.pending_total_sui_withdraw = 0;
    pool.pending_pool_token_withdraw = 0;
}
