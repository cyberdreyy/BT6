### Title
Reorg-timing check in `check_parent_tenure_choice` can be forced to wrongly permit a tenure reorg via a `saturating_sub` underflow - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg away one or more already-mined/signed tenures. The decision hinges on `proposal_to_sortition = sortition_state_received_time.saturating_sub(approved_at)`, compared against the configured `first_proposal_burn_block_timing`. This mirrors the oracle bug class: an arithmetic expression that is supposed to represent "how much time elapsed since we approved this block" can silently collapse to `0` whenever `approved_at` happens to be `>= sortition_state_received_time`, exactly like the oracle's modulo expression silently producing a future timestamp instead of the intended "start of today" value. A collapsed `0` always satisfies `Duration::from_secs(0) < first_proposal_burn_block_timing`, so the code takes the "poorly timed, allow the reorg" branch even when the real elapsed time was large (or meaningless), permitting a reorg that should have been refused. [1](#0-0) 

### Finding Description
The function's purpose is to reject reorgs of tenures that already produced a globally-known first block, *unless* that first block's proposal-to-next-sortition interval was suspiciously short (i.e., the tenure "raced" the burn block transition, so allowing a competing miner to replace it is considered fair). This interval is computed as an unsigned subtraction:

```rust
let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
    sortition_state_received_time.saturating_sub(approved_at)
} else { ... 0 };
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    // treat as poorly-timed -> permit reorg
}
``` [2](#0-1) 

`saturating_sub` is a defensive idiom against underflow, but it also silently maps *any* case where `approved_at >= sortition_state_received_time` to exactly `0`, which is indistinguishable from "the block was approved right at the sortition boundary." The check treats a computed `0` identically to a genuinely tiny/legitimate interval, always satisfying the "poorly timed" branch and pushing the tenure into `superseded_tenures`, i.e., permitting the reorg. Both timestamps come from the signer's own monotonic-in-theory system clock (`approved_time` recorded when the signer locally accepted the block; `sortition_state_received_time` recorded when the burn block event was received), so under normal conditions `approved_at` should predate `sortition_state_received_time` by a meaningful margin for any tenure that has been running for a while. However, this ordering assumption is not otherwise enforced or validated anywhere else in the check — there is no floor/ceiling sanity check on the computed interval, no assertion that `sortition_state_received_time > approved_at`, and no distinction between "true small interval" and "underflowed to zero." Any event that causes the local clock used for `SystemTime::now()`-based burn-block bookkeping to read behind (or equal to) the time recorded at block approval — e.g., host clock adjustment/NTP correction, VM pause/resume, leap-second handling, or event-processing races between `insert_burn_block` and `mark_locally_accepted` — silently collapses the safety margin to zero and forces the "reorg permitted" path.

Once permitted, `record_superseded_tenure`/`mark_tenure_superseded` marks the reorged tenure's blocks as no longer blocking, which then affects `conflict_still_blocks`/`reorg_permit_stands` used by `handle_block_pre_commit` before a signature is emitted [3](#0-2) . This is exactly the class of "approved-parent vs canonical" equality the guard exists to protect: the miner should only be allowed to replace an already-built, well-timed tenure when the elapsed interval genuinely proves it raced the sortition, not because a local clock artifact zeroed out the calculation.

### Impact Explanation
If the reorg is wrongly deemed permitted, the signer will drop its own guard against double-signing/conflicting blocks for that tenure and go on to sign a competing (non-canonical, reorging) block that should have been rejected, matching the "signer signing a non-canonical/conflicting block" Critical impact category. Because the permit is recorded per-tenure and propagates through `reorg_permit_stands`, a single miscalculation removes the guard for the whole superseded tenure, not just one block.

### Likelihood Explanation
This does not require compromising a majority of signers or any key material — it can be triggered by ordinary clock skew/adjustment on a single signer's host, or exploited by an attacker who can influence relative timing of burn-block delivery vs. local block approval (e.g., delaying the burn-block event observer callback or NewBurnBlock processing while forcing the signer to approve a block right before that event lands). Because `approved_at` and `sortition_state_received_time` are recorded independently at different points in the async signer event pipeline (`insert_burn_block` on `NewBurnBlock`, `mark_locally_accepted`/`approved_time` on validation), tight timing coincidences are plausible even without malicious host clock manipulation, especially under load or during resumption from a paused/sleeping process. That said, I could not fully verify from the available code whether these two timestamps are guaranteed to be sourced from a single monotonically-increasing clock instance in all code paths (`get_epoch_time_secs()` vs `SystemTime::now()`), which affects how easily the underflow condition can be hit in practice — this remains uncertain given the index's coverage of the surrounding time-source implementation.

### Recommendation
Do not let the interval calculation silently saturate to zero and treat that identically to "definitely a short interval." Distinguish the "clock went backwards / data is untrustworthy" case from "genuinely small interval, permit reorg":
```rust
let proposal_to_sortition = match sortition_state_received_time.checked_sub(approved_at) {
    Some(v) => v,
    None => {
        warn!("approved_at is after sortition_state_received_time; treating as untrustworthy, refusing to permit reorg");
        return Ok(false); // or otherwise fail closed instead of always permitting
    }
};
```
Fail closed (refuse the reorg) rather than fail permissive whenever the subtraction would underflow, mirroring the oracle fix's approach of adding an explicit guard (`require(block.timestamp >= expiry, ...)`) rather than relying on an arithmetic identity that happens to work only under assumed orderings.

### Proof of Concept
I could not construct a fully deterministic PoC purely from static code reading, since triggering the underflow requires either (a) a host clock adjustment between the `insert_burn_block` and `mark_locally_accepted` calls, or (b) a race in event delivery ordering that I was unable to confirm is reachable purely over gossip/StackerDB within the scope allowed. Conceptually:
1. A tenure `T1` mines and gets its first block approved locally by the signer at time `t0` (`approved_time = t0`), recorded via `mark_locally_accepted` [4](#0-3) .
2. A new sortition's burn block arrives and is recorded via `insert_burn_block` with a receive timestamp `t1`, where due to clock skew/adjustment `t1 <= t0` (host clock stepped backward, or the receive-time write happens to read an earlier wall-clock value than the approval write did).
3. A new miner proposes a block building on a different parent, triggering `check_parent_tenure_choice` for `T1`. `sortition_state_received_time.saturating_sub(approved_at)` evaluates to `0`.
4. `Duration::from_secs(0) < first_proposal_burn_block_timing` is true for any nonzero configured timing threshold, so `T1` is added to `superseded_tenures` and the reorg is permitted [5](#0-4) , even though `T1`'s actual mining-to-sortition gap may have been arbitrarily large and should have blocked the reorg.

This PoC requires further validation in a running environment (or with Devin's terminal access) to confirm the exact reachability of the underflow condition and whether it is exploitable purely through gossip/StackerDB timing rather than host clock manipulation; I flag this uncertainty explicitly rather than asserting exploitability with full confidence.

    /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
    }
