### Title
Missing sender/DON-membership authorization allows cross-DON request injection into WebAPI capabilities handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`Message.Validate()` in `core/services/gateway/api/message.go` only checks length/null-suffix constraints on `DonId` and derives `Body.Sender` from the ECDSA signature, but never verifies that the derived signer belongs to the DON named in `DonId`. `gateway.ProcessRequest` then routes purely on the `DonId` string to `g.handlers[handlerKey]`, and the `capabilities.handler.HandleLegacyUserMessage` accepts and forwards any correctly-signed message to all of that DON's nodes with no sender authorization/allowlist check at all.

### Finding Description
The routing path is: `gateway.ProcessRequest` (`core/services/gateway/gateway.go:250-262`) takes the attacker-controlled `msg.Body.DonId`, calls `msg.Validate()`, then looks up `h, ok = g.handlers[handlerKey]` where `handlerKey = msg.Body.DonId`. `Validate()` (`core/services/gateway/api/message.go:54-88`) performs only structural checks (signature length, ID/method/DonId length and null-suffix, receiver length) and computes `m.Body.Sender` from `ExtractSigner()` — it never checks whether that signer is a member of the DON identified by `DonId`.

The request is then dispatched to `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go:341-421`. This function validates payload structure (timestamp, method), but performs no check that `msg.Body.Sender` is authorized for this DON — the code explicitly contains `// TODO: apply allowlist and rate-limiting here` at line 384, confirming no such check exists. It then unconditionally forwards the message to every node in `h.donConfig.Members` [1](#0-0) .

Because the allowlist check is entirely absent (not merely misconfigured), any holder of a valid ECDSA key — regardless of whether that key is enrolled anywhere — can address any configured DON by putting its `DonId` in the message body, sign it, and have the message forwarded to that DON's node set (which may bear job-spec/bridge-credential-handling capabilities).

### Impact Explanation
This allows cross-DON request injection: an unauthorized/unenrolled signer can submit a `web_api_trigger`/target/compute-action message that gets forwarded to all nodes of a chosen DON, without any check that the sender is a legitimate user of that DON's capability. Depending on downstream node-side handling of the trigger, this can result in unauthorized job/workflow triggering on a DON the attacker was never enrolled in. This maps to the "unauthorized job run" / "authorization bypass" bounty class. [2](#0-1) 

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to generate/hold any ECDSA private key (no prior enrollment in any DON is even required for the capabilities handler, since it has no allowlist check at all) and know a valid `DonId` string that maps to a configured handler (`g.handlers` keys are effectively discoverable/enumerable). The exploit is a single signed JSON-RPC request to the gateway's user endpoint — trivially repeatable, no rate limiting or authorization gate blocks it before dispatch (`nodeRateLimiter` in the handler is applied only to outbound node responses, not inbound user messages, per `handleWebAPIOutgoingMessage`).

### Recommendation
Add explicit sender-authorization/allowlist enforcement in `capabilities.handler.HandleLegacyUserMessage` (replacing the `// TODO: apply allowlist and rate-limiting here` comment) that checks `msg.Body.Sender` against a per-DON authorized-sender/workflow-owner allowlist before forwarding to `donConfig.Members`, mirroring the `vaultcap.Authorizer`/`AuthorizeRequest` pattern already used in `core/services/gateway/handlers/vault/handler.go`. Additionally, consider adding a DON-membership/authorization check inside `Message.Validate()` or immediately after handler lookup in `gateway.ProcessRequest`, so that cross-DON routing cannot succeed for unauthorized senders regardless of which handler processes the request.

### Proof of Concept
1. Configure a gateway with two DONs, "donA" and "donB", each with distinct `HandlerConfig`/`DONConfig.Members`, using `capabilities.NewHandler` for both (mirroring `core/services/gateway/handlers/capabilities/handler_test.go:setupHandler`).
2. Generate a fresh ECDSA key not present in either DON's node/member list (or not on any allowlist).
3. Build and sign an `api.Message` with `Body.DonId = "donB"`, `Body.Method = MethodWebAPITrigger`, and a valid `TriggerRequestPayload` (per `triggerRequest` helper in `handler_test.go`).
4. Call `gw.ProcessRequest` (via `gateway.NewGatewayFromConfig`) with this signed request.
5. Assert: the request is NOT rejected (`msg.Validate()` succeeds, handler forwards via `don.SendToNode` to all of donB's members) — demonstrating there is no rejection based on sender identity/DON membership, contrary to the expectation that an unenrolled signer be blocked. Compare against `vault/handler.go`, which does call an `Authorizer.AuthorizeRequest` and would reject the equivalent unauthorized sender, showing the capabilities handler lacks the analogous protection.
