### Title
Unbounded `bincode::deserialize` of `SystemInstruction` in `parse_system` can panic the RPC-serving thread on attacker-crafted seed-length data - ([File: transaction-status/src/parse_system.rs])

### Summary
`parse_system` decodes attacker-controlled `CompiledInstruction.data` with plain `bincode::deserialize::<SystemInstruction>`, which has no length/size limit configured, unlike the consensus-critical `system_processor` path which explicitly uses a bounded `limited_deserialize`. Because several `SystemInstruction` variants (`CreateAccountWithSeed`, `AllocateWithSeed`, `AssignWithSeed`, `TransferWithSeed`) contain a `String` (`seed`/`from_seed`) whose length is read from an attacker-controlled 8-byte length prefix, a crafted instruction can cause the decoder to attempt to read/slice more bytes than are present, panicking the calling thread when a client fetches the transaction via `getTransaction`/`getConfirmedBlock` with `UiTransactionEncoding::JsonParsed`.

### Finding Description
`parse_system` is reached from `parse_instruction::parse` when the RPC layer JSON-parses a transaction's instructions for `UiTransactionEncoding::JsonParsed`: [1](#0-0) 

The call `deserialize(&instruction.data)` uses `bincode`'s default, unbounded configuration to decode `SystemInstruction`. Several variants carry a `String` field whose wire format is a length prefix followed by that many raw bytes (`seed` in `CreateAccountWithSeed`/`AllocateWithSeed`/`AssignWithSeed`, `from_seed` in `TransferWithSeed`): [2](#0-1) [3](#0-2) 

An attacker submits a `CompiledInstruction` targeting the System program with `data` = [enum discriminant for `CreateAccountWithSeed`][32-byte `base` Pubkey][8-byte `seed` length = a huge value, e.g. `u64::MAX`][...no further bytes]. This is only ~44 bytes and easily fits within `PACKET_DATA_SIZE` (1232 bytes), so it passes normal transaction-size sanitization and can be landed on-chain (the System program itself will reject the instruction at execution time since it uses a *bounded* `limited_deserialize`, but the instruction still lands as a *failed* transaction in a rooted slot — RPC still parses and returns data for failed transactions). When a client later requests this transaction with `getTransaction(..., encoding: JsonParsed)`, `parse_system` invokes bare `bincode::deserialize`, which reads the bogus length prefix and attempts to consume/slice that many bytes from the remaining (much smaller) buffer, panicking the calling thread instead of returning an `Err` that would be caught by the `map_err` on line 16.

This directly contrasts with the consensus-execution path, which deliberately uses a size-bounded deserializer: [4](#0-3) 

The bound in `limited_deserialize(instruction_data, PACKET_DATA_SIZE)` prevents the runtime from ever attempting to trust an oversized length prefix beyond the packet size, but no equivalent guard exists in `transaction-status/src/parse_system.rs`, which is exercised purely by RPC read paths on attacker-authored, already-landed transaction data.

### Impact Explanation
A single unprivileged client can submit one transaction (or reuse an existing failed one) containing a malformed System-program instruction, then issue a single `getTransaction`/`getConfirmedBlock` RPC call with `JsonParsed` encoding to trigger a panic in the RPC request-handling code path of any full node that later serves that request. This matches the "decoder panic on read" / single client crash-on-read bounty category — the scope is a client-triggerable RPC-thread panic from data that legitimately landed on chain, not a consensus-affecting bug.

### Likelihood Explanation
- Preconditions are trivial: attacker needs only to submit one transaction with crafted System-program instruction bytes (it may even fail on-chain execution and still be stored/queryable).
- Exploitation requires exactly one subsequent `getTransaction`(JsonParsed) call, well within the single-call-per-slot constraint.
- No special privileges, staking, or validator control needed — purely client-supplied instruction bytes plus a standard RPC call.
- The bug is fully reachable and reproducible because `parse_system` has no size or bounds guard prior to calling `bincode::deserialize`.

### Recommendation
Replace the unbounded `bincode::deserialize` call in `parse_system` (and ideally other `parse_*` decoders that use raw `bincode::deserialize` on attacker-supplied instruction bytes) with a bounded/limited deserializer analogous to `limited_deserialize`, configured with a byte limit equal to `instruction.data.len()` (or `PACKET_DATA_SIZE`), so any length prefix that exceeds the actual available bytes is rejected via a normal `Result::Err` instead of causing a panic. Additionally wrap `parse_instruction::parse` call sites with `catch_unwind` as defense-in-depth so a decoder bug cannot take down the RPC-serving thread/process.

### Proof of Concept
```rust
// transaction-status/src/parse_system.rs (added test)
#[test]
fn test_parse_system_malformed_seed_length_does_not_panic() {
    use solana_message::{AccountKeys, Message, compiled_instruction::CompiledInstruction};
    use solana_pubkey::Pubkey;
    use solana_sdk_ids::system_program;

    // Build raw bytes: 4-byte discriminant for CreateAccountWithSeed (index 3)
    // + 32-byte base pubkey + 8-byte bogus seed length (u64::MAX), no further data.
    let mut data = vec![];
    data.extend_from_slice(&3u32.to_le_bytes()); // CreateAccountWithSeed discriminant
    data.extend_from_slice(&[0u8; 32]);           // base pubkey
    data.extend_from_slice(&u64::MAX.to_le_bytes()); // malicious seed length

    let instruction = CompiledInstruction {
        program_id_index: 1,
        accounts: vec![0, 0],
        data,
    };
    let account_keys = AccountKeys::new(&[Pubkey::new_unique(), system_program::id()], None);

    // Expected: parse_system should return Err(InstructionNotParsable), never panic.
    let result = std::panic::catch_unwind(|| parse_system(&instruction, &account_keys));
    assert!(result.is_ok(), "parse_system panicked on malformed seed length");
}
```
Fuzz plan: use `cargo-fuzz`/`proptest` to generate arbitrary `Vec<u8>` as `CompiledInstruction.data` for the System program id, call `parse_system`, and assert (a) no panic occurs and (b) peak memory allocation stays bounded (e.g., under `instruction.data.len() * small_constant`), across many iterations including length prefixes near `u64::MAX`.
