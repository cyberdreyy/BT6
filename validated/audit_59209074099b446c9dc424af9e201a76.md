### Title
View-role (and run-role) users can read a bridge's `OutgoingToken` secret via unrestricted `GET /v2/bridge_types/:BridgeName` and `GET /v2/bridge_types` - ([File: core/web/router.go])

### Summary
`bt.Show` (and also `bt.Index`) are registered under `authv2` with only session/token authentication and no role gate, while `Create`/`Update`/`Destroy` are wrapped in `auth.RequiresEditRole`. Since `presenters.NewBridgeResource` unconditionally serializes `OutgoingToken` (no redaction, no `omitempty`), any authenticated user — including the lowest-privileged `view` role — can retrieve a bridge's outgoing token, a secret used by the node to authenticate itself to the external bridge adapter.

### Finding Description
In `core/web/router.go`, the bridge routes are: [1](#0-0) 
`bt.Index` is wrapped only in `paginatedRequest` (no role check) and `bt.Show` has no wrapper at all, while `Create`, `Update`, and `Destroy` are explicitly gated with `auth.RequiresEditRole`. Both routes sit behind the `authv2` group, which only requires `auth.Authenticate` (session or API token) — no role check is performed there: [2](#0-1) 

`bt.Show` looks up the bridge and serializes it directly with `presenters.NewBridgeResource`: [3](#0-2) 

`presenters.NewBridgeResource` copies `OutgoingToken` into the JSON response unconditionally (`json:"outgoingToken"`, no `omitempty`, no redaction): [4](#0-3) 

`RequiresRunRole` and `RequiresEditRole` explicitly deny `UserRoleView` (and `UserRoleRun` for edit-only actions): [5](#0-4) 

Because `Show`/`Index` bypass any role check, a `view`-role user (or a run-role user, or an external-initiator-derived run-role token) that is merely authenticated to the node can call `GET /v2/bridge_types/:BridgeName` and receive the bridge's `OutgoingToken` in plaintext. Note `IncomingToken` is not at risk here because the ORM's `BridgeType` struct only stores `IncomingTokenHash`/`Salt`, not the raw incoming token, so `Show`/`Index` cannot leak it — the exposure is specific to `OutgoingToken`.

### Impact Explanation
`OutgoingToken` is the credential the Chainlink node uses to authenticate itself when calling out to an external bridge/adapter. Disclosure to a low-privileged `view`-role account lets that user impersonate the node to the external bridge, potentially manipulating bridge responses or accessing the bridge's API on the node's behalf. This maps to a secret/credential disclosure and privilege-boundary-bypass impact (a `view`-role principal obtaining a credential that should require at least `edit` privileges, since only `Create`/`Update`/`Destroy` are edit-gated).

### Likelihood Explanation
Minimal precondition: any valid authenticated session or API token with `view` role (the lowest privilege tier in the node's RBAC) is sufficient — no edit/admin/run role, no additional exploitation steps. The request is a single unauthenticated-role `GET /v2/bridge_types/:BridgeName` (or `GET /v2/bridge_types` for all bridges), fully repeatable and deterministic since the role check is simply absent on this route, unlike its sibling mutating routes.

### Recommendation
Wrap `bt.Show` and `bt.Index` with an appropriate role gate (at minimum consistent with the sensitivity of the returned data), or redact `OutgoingToken` in `presenters.NewBridgeResource` for view/run-role callers, mirroring the pattern already used for `IncomingToken`'s `omitempty`/create-only exposure.

### Proof of Concept
1. In `core/web/bridge_types_controller_test.go`, create a bridge via an admin/edit-role client with a known `OutgoingToken`.
2. Create an HTTP client authenticated as a `view`-role user (`cltest.NewApplication` + a user session with `sessions.UserRoleView`).
3. Call `client.Get("/v2/bridge_types/" + bridgeName)` and `client.Get("/v2/bridge_types")`.
4. Assert `http.StatusOK` is returned (not `401`/`403`) and that `respJSON.Get("data.attributes.outgoingToken")` equals the known token — demonstrating that unlike `Create`/`Update`/`Destroy` (which return `401 Unauthorized` for the same view-role client per `auth.RequiresEditRole`), `Show`/`Index` leak the secret to the unprivileged role.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
