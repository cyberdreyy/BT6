### Title
Unbounded stake-delegation count enables single-slot epoch-boundary reward computation DoS - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
CoreDAO's `CandidateHub.register()` has no cap on the number of candidates, so `candidateSet` can be inflated arbitrarily, and `turnRound()`'s single-transaction loop over `candidateSet` can then exceed the block gas limit. Agave has the analogous structural risk in the epoch-boundary reward calculation: unlike vote accounts (which are explicitly capped via VAT filtering), the number of stake delegations that must be iterated in `calculate_reward_points_partitioned` / `calculate_stake_rewards_and_commissions` is unbounded and computed synchronously, in full, in a single bank/slot at each epoch boundary — separate from and prior to the deliberately *partitioned* reward-distribution phase.

### Finding Description
Solana explicitly partitions the *distribution* of stake rewards across multiple blocks to avoid doing unbounded per-slot work — capped by `MAX_PARTITIONED_REWARDS_PER_BLOCK` and `get_reward_distribution_num_blocks`, which clamps the number of blocks to at most 10% of the epoch's slots. [1](#0-0) [2](#0-1) 

Likewise, vote accounts used for leader-schedule/epoch-stakes purposes are explicitly bounded via `clone_and_filter_for_vat`, which truncates the vote-account set to `max_vote_accounts` (e.g. `MAX_ALPENGLOW_VOTE_ACCOUNTS`), sorted by stake, exactly to prevent unbounded per-epoch work from growing without limit. [3](#0-2) 

However, the *calculation* phase that precedes distribution — `calculate_reward_points_partitioned` and `calculate_stake_rewards_and_commissions` — iterates over the full `stake_delegations` vector for the network in one shot, inside a single bank at the epoch boundary, with no equivalent cap. The code even acknowledges this can reach into the millions: [4](#0-3) [5](#0-4) 

`stake_delegations` itself is an unbounded `ImblHashMap<Pubkey, T>` with no maximum size check anywhere in `runtime/src/stakes.rs`; any user can create an arbitrarily large number of stake accounts and delegate stake to them at the low, fixed cost of the stake-account rent-exempt reserve plus minimum delegation, exactly analogous to how CoreDAO's `register()` only required a fixed margin deposit per candidate with no upper bound. [6](#0-5) [7](#0-6) 

Whereas the vote-account path was deliberately hardened (SIMD-357 VAT filtering) and the distribution path was deliberately partitioned, the calculation path over all `stake_delegations` was not given a symmetrical cap, leaving it as the remaining unbounded, single-slot O(N) computation directly reachable by ordinary users staking cheaply created accounts.

### Impact Explanation
If the number of stake delegations network-wide grows very large (attacker-inflatable at low per-account cost), the once-per-epoch, single-bank calculation of reward points and stake rewards becomes proportionally expensive and must complete within that bank's processing before rewards distribution and epoch-boundary bank freeze can proceed. Because this work is not partitioned across multiple blocks the way distribution is, sufficiently large delegation counts risk delaying bank freezing/hashing at epoch boundaries across the whole cluster, potentially causing skipped slots, degraded liveness, or fork instability at every epoch boundary — a cluster-wide consensus-liveness impact, not merely a local one.

### Likelihood Explanation
Creating a stake account and delegating a minimal amount is a permissionless, cheap, ordinary user transaction (`stake_instruction::create_account_and_delegate_stake` costs only the rent-exempt reserve plus the minimum delegation). There is no protocol-level maximum on the total number of stake delegations analogous to the vote-account VAT cap, so an attacker with modest capital could create very large numbers of low-value stake accounts over time. Likelihood is moderate: it requires sustained capital outlay and is bounded by the ordinary cost of account creation, but no on-chain limit currently prevents it.

### Recommendation
Introduce an explicit bound (or graceful degradation/parallelization safeguard already partially present via rayon, but formalized as a hard cap or partitioned pre-computation) on the number of stake delegations processed in a single epoch-boundary reward calculation pass, symmetric to the `clone_and_filter_for_vat` cap already applied to vote accounts and the block-partitioning already applied to reward distribution — e.g., limiting/filtering stake delegations per epoch similarly to how vote accounts are filtered, or restructuring `calculate_reward_points_partitioned`/`calculate_stake_rewards_and_commissions` to run across multiple blocks rather than a single bank.

### Proof of Concept
1. Use ordinary `system_instruction::create_account` + `stake_instruction::create_account_and_delegate_stake` calls (as in `cli/src/stake.rs::process_delegate_stake`) to create a very large number of stake accounts, each funded at only the rent-exempt reserve + minimum delegation. [8](#0-7) 
2. At the next epoch boundary, `calculate_rewards_for_partitioning` → `calculate_reward_points_partitioned` and `calculate_stake_rewards_and_commissions` iterate over the entire, now-inflated `stake_delegations` list in a single bank, with no partitioning or cap. [9](#0-8) 
3. Observe that, unlike vote-account processing (bounded) and reward distribution (explicitly partitioned across blocks), this calculation work scales unboundedly with attacker-created stake-delegation count within a single slot's processing.

    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));
        }

        let valid_len = entries_to_sort.len();
        if entries_to_sort.len() > max_vote_accounts {
            // Find the cutoff stake using partial sort (more efficient than full sort).
            let (_, cutoff_entry, _) =
                entries_to_sort.select_nth_unstable_by(max_vote_accounts, |a, b| b.2.cmp(&a.2));
            let floor_stake = cutoff_entry.2;

            // Per SIMD 357, we remove all vote accounts with stake smaller or equal to
            // the first truncated one.
            entries_to_sort.retain(|(_, _, stake)| *stake > floor_stake);
