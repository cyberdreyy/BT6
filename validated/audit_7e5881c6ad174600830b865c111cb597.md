### Title
Permissionless bank creation bypasses the protocol panic-pause, allowing new lending markets to spin up mid-incident - ([File: programs/marginfi/src/instructions/marginfi_group/add_pool_permissionless.rs])

### Summary
The external report's bug class — an asynchronous/permissionless code path that creates new protocol state without checking the pause flag — maps to `lending_pool_add_bank_permissionless` in marginfi. This instruction is fully permissionless and creates a brand-new, immediately `Operational` staked-collateral bank, but its account-validation struct contains no `is_protocol_paused()` constraint, unlike nearly every other permissionless/user instruction in the program.

### Finding Description
Marginfi implements a group-wide panic-pause mechanism (`panic_pause`/`panic_unpause`/`panic_unpause_permissionless`) intended to halt "all normal user flows" during an incident, including deposit, borrow, withdraw, repay, permissionless fee collection, and permissionless bad-debt settlement, as documented in [1](#0-0) . Nearly every permissionless or user-facing instruction enforces this via a `group.load()?.is_protocol_paused()` account constraint, for example on `LendingPoolWithdrawFeesPermissionless` [2](#0-1)  and `TransferToNewAccount` [3](#0-2) .

However, `lending_pool_add_bank_permissionless` — a fully permissionless instruction that creates a new `Bank` account, initializes its liquidity/insurance/fee vaults, and sets `operational_state = BankOperationalState::Operational` immediately — has no such check anywhere in its handler or its `Accounts` struct [4](#0-3) [5](#0-4) [6](#0-5) . A grep across the entire `marginfi_group` instruction module confirms `is_protocol_paused`/`ProtocolPaused` only appear in `collect_bank_fees.rs`, `accrue_bank_interest.rs`, `configure_bank.rs`, and `handle_bankruptcy.rs` — `add_pool_permissionless.rs` is absent from that list.

This is directly analogous to the reported `entropyCallback` bug: a permissionless/asynchronous entry point that creates brand-new protocol state (a new auction / a new bank) while completely bypassing the pause gate that every other comparable flow respects.

### Impact Explanation
During a `panic_pause` incident (e.g., an oracle malfunction, exploit in progress, or other emergency the admin is trying to contain), anyone can still permissionlessly call `lending_pool_add_bank_permissionless` to spin up a brand-new, immediately `Operational` staked-collateral bank tied to an arbitrary validator/stake pool. Because the new bank starts `Operational` (not `Paused`, unlike normal admin-added banks), users could begin depositing/borrowing against it immediately, undermining the very purpose of the panic-pause (freezing all new financial activity while the incident is investigated). This is an unauthorized state change with financial effect: new markets/exposure are created against the operator's explicit intent, and it also increases the attack surface and integration exposure right when the protocol wants everything frozen.

### Likelihood Explanation
The precondition is a group-wide pause being active, which is an admin-initiated, low-frequency event (rate-limited to 4 consecutive pauses / 3 per day per the docs), but the instruction is otherwise fully permissionless and requires no privileged role or unusual conditions to trigger — any account holding a valid stake-pool/vote-account combination can call it at any time, including during a pause. This matches the "unprivileged-user analog" requirement.

### Recommendation
Add the same `!group.load()?.is_protocol_paused() @ MarginfiError::ProtocolPaused` constraint used elsewhere (e.g., in `LendingPoolWithdrawFeesPermissionless` and `TransferToNewAccount`) to the `LendingPoolAddBankPermissionless` accounts struct in `programs/marginfi/src/instructions/marginfi_group/add_pool_permissionless.rs`, so that new bank creation is blocked while the protocol is in a panic-paused state.

### Proof of Concept
1. `global_fee_admin` or `pause_delegate_admin` calls `panic_pause` and propagates the pause to the target `marginfi_group` (per `PERMISSIONS_AND_ROLES.md`), intending to halt all protocol activity.
2. An unprivileged user, in a separate transaction, calls `lending_pool_add_bank_permissionless` with a valid stake pool / validator vote account combination.
3. Because `LendingPoolAddBankPermissionless`'s account constraints never check `group.load()?.is_protocol_paused()` (confirmed absent from `add_pool_permissionless.rs` in the repo-wide grep for `is_protocol_paused`/`ProtocolPaused`), the instruction succeeds: a new `Bank` account is created, its vaults initialized, and `operational_state` set to `Operational` [5](#0-4) .
4. Users can now interact with this new bank even though the group is supposed to be fully paused, contradicting the documented pause guarantees in `PERMISSIONS_AND_ROLES.md`.
