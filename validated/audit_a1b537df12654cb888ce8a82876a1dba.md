### Title
Multi-epoch withdraw requests bypass the `stopEpochWithDuration` loss haircut and claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The external bug is a TOCTOU: `tpacket_snd()` validates a header once, then re-reads mutable fields later, so the validated state and the used state diverge. The analog in `IdleCreditVault` is identical in shape: `collectWithdrawFunds()` computes a single loss-recovery price against the *aggregate* `pendingWithdraws` (the "check"), while claims re-derive what is haircutted from *per-epoch* state keyed only by `lastWithdrawRequest[_user]` (the "use"). Receipt basis recorded in an older epoch is not covered by the stored recovery price and is later paid at par by `_claimFundedWithdrawRequest`, even though only haircutted funds were collected. This is a direct theft/insolvency in the loss-waterfall invariant.

### Finding Description

`requestWithdraw` accrues basis into both an aggregate and a per-epoch bucket:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
pendingWithdraws += _amount;                                   // L279
lastWithdrawRequest[_user] = currentEpoch;                     // L282
withdrawsRequests[_user] += _amount;                           // L292
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;      // L293
```

A user may hold unclaimed request basis spanning multiple request epochs — the NatSpec at L323-324 explicitly supports requesting again without claiming ("he will have to wait for another epoch to claim both requests").

When the borrower underfunds at epoch end, `collectWithdrawFunds` computes one price over the *entire* global pending basis:

```solidity
uint256 pendingBasis = pendingWithdraws;                       // L413
if (_amount < pendingBasis) {
  uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;  // L417
  pendingWithdraws = 0;                                        // L420
  // stored under a single epoch key in lossRecoveryPriceByEpoch
```

But the claim side only looks up the haircut for the epoch stored in `lastWithdrawRequest[_user]`:

```solidity
function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
  uint256 lossEpoch = lastWithdrawRequest[_user];              // L790
  uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
  ...
  amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;   // L799
```

`_clearWithdrawClaimForEpoch` clears only that epoch's slice (`withdrawsRequestsByEpoch[_user][_claimEpoch]`, L815-819). Any basis the same user recorded in an *earlier* epoch remains in `withdrawsRequests[_user]`, and `_claimFundedWithdrawRequest` (L338-349) then pays `amount = normalAmount + apr0Principal + apr0Interest` at par via `_transferFundedClaim`.

The result: the user's older-epoch basis was included in `pendingBasis` when computing the haircut, so the funded amount assumes it is paid at `lossRecoveryPrice`, yet it is paid at 100%. This is exactly the TOCTOU pattern — `pendingWithdraws` was "validated" (priced) under one assumption, while the payout path re-reads a different state view that silently widens the claim.

### Impact Explanation

- Insolvency/theft among withdraw claimants: the strategy only received `_amount = pendingBasis * lossRecoveryPrice` underlyings. A user with stale-epoch basis draining it at par takes funds that belong to other receipt holders; later claimants' `safeTransfer` reverts (temporary freezing of unclaimed claims) or claims underpay the last withdrawers.
- Quantification: a user splitting a request of size `X` across two epochs where `lossRecoveryPrice = p` extracts `X_old * (1 - p)` extra underlyings versus intended — e.g., at a 50% haircut, half of the older-epoch basis is stolen from the funded pool.
- The mirror-image guard gap also exists: `requestWithdraw` only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (L262-271), so once `lastWithdrawRequest` has been overwritten to a price-less epoch, an old haircutted receipt's existence is not detected.

### Likelihood Explanation

Requires: an attacker (any KYC-passing lender / tranche holder) making two `requestWithdraw` calls in different epochs without claiming between them, then the honest manager calling `stopEpochWithDuration(_lossAmount)` / underfunded `collectWithdrawFunds` while both bases sit in `pendingWithdraws`. Underfunded epoch stops are a designed-for bad-debt path, not an edge case. No privileged misbehavior is needed. Uncertainty: whether the deployed code writes `lossRecoveryPriceByEpoch` under `epochNumber` at stop time or under each contributing epoch — the visible snippet (L411-420) shows a single aggregate price and `pendingWithdraws = 0`, consistent with the single-epoch key that creates the gap; the exact write line was not inspected in this pass.

### Recommendation

In `collectWithdrawFunds`, apply the loss price per contributing request epoch (e.g., track `pendingWithdrawsByEpoch` and write `lossRecoveryPriceByEpoch` for every epoch with nonzero basis, analogous to `instantWithdrawClaimsByEpoch`), or revert/adjust if basis exists in more than one epoch. On the claim side, iterate all epochs with nonzero `withdrawsRequestsByEpoch[_user][*]` that have a nonzero `lossRecoveryPriceByEpoch`, not only `lastWithdrawRequest[_user]`. Also extend the `requestWithdraw` guard to scan for any unclaimed loss-adjusted basis, not only the latest epoch's.

### Proof of Concept

Foundry fork sketch (fork at a live `IdleCDOEpochVariant`+`IdleCreditVault` deployment; mirrors `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`):

```solidity
function testStaleEpochBasisClaimsAtPar() public {
    // Attacker deposits and requests withdraw during buffer of epoch N (basis E1)
    _depositWithUser(attacker, 100_000e6, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, AAtranche);          // basis in epoch e1

    // Epoch N+1 runs and stops normally; attacker does NOT claim.
    _startEpochAndCheckPrices(0);
    deal(underlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr, 0);                       // funds E1 fully

    // New buffer: attacker requests again -> basis now spans e1 and e2,
    // lastWithdrawRequest = e2
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, AAtranche);          // basis in epoch e2

    // Next epoch ends with a loss: borrower underfunds pendingWithdraws
    _startEpochAndCheckPrices(0);
    uint256 pending = creditVault.pendingWithdraws();
    deal(underlying, borrower, _expectedFundsEndEpoch() - pending + pending / 2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, lossAmount); // lossRecoveryPrice ~ 0.5

    // Victim also had pending basis in e2
    // Attacker claims: e2 slice paid at haircut, e1 slice paid AT PAR via
    // _claimFundedWithdrawRequest even though only haircutted funds exist.
    vm.prank(attacker);
    uint256 got = cdoEpoch.claimWithdrawRequest();

    // Invariant broken: attacker received e2*p + e1*1.0 while pool holds
    // only (e1+e2)*p for all claimants -> victim claim reverts or underpays.
    vm.prank(victim);
    vm.expectRevert(); // or assertUnderpaid
    cdoEpoch.claimWithdrawRequest();
}
```

Expected: attacker's total payout exceeds `claimBasis * lossRecoveryPrice`; the funded pool is drained below what remaining claimants are owed, demonstrating theft/insolvency consistent with the haircut-accounting invariant.
