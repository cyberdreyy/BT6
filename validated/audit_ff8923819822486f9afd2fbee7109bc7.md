### Title
Currently-winning miner can indefinitely reset its own inactivity clock with throwaway invalid block proposals, blocking signer failover — ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` treats *any* block proposal from the currently active/winning miner that fails to confirm as many blocks as expected as valid "miner activity," and unconditionally bumps `last_activity_time` for that tenure via `signer_db.update_last_activity_time`. That same `last_activity_time` is the sole input `SortitionState::is_timed_out` uses to decide whether the signer set should fail over from the current miner to the prior tenure's miner. Because the activity bump happens *before*/independent of whether the proposal is otherwise sane (it only needs to pass the pubkey check, which the legitimate current-tenure miner trivially satisfies with its own key), the current miner can keep resubmitting cheap, invalid, non-advancing proposals purely to refresh the clock and prevent `is_timed_out` from ever firing — mirroring the AlgebraPool bug class where an earlier, attacker-controlled action mutates shared state that a later, security-relevant check depends on.

### Finding Description
The activity/timeout mechanism lives in two places:

- `SortitionData::check_latest_block_in_tenure` (stacks-signer/src/chainstate/mod.rs:376-478) fetches the tenure's last signed/known block via `get_tenure_last_block_info`. If the newly proposed block does **not** confirm more blocks than that (`block.header.chain_length <= info.block.header.chain_length`), it is rejected as `InvalidParentBlock`/not-latest — but first, as long as `info.signed_group` is absent or recent (within `reorg_attempts_activity_timeout`), the code calls:
```
stacks-signer/src/chainstate/mod.rs:411-416
if let Err(e) = signer_db.update_last_activity_time(
    &block.header.consensus_hash,
    get_epoch_time_secs(),
) { ... }
```
The comment even states the intent explicitly: *"The miner may just be slow, so count this invalid block proposal towards valid miner activity."* The same pattern repeats for pre-committed-block conflicts a few lines later (mod.rs:442-446).

- `SortitionState::is_timed_out` (stacks-signer/src/chainstate/v1.rs:55-94) is the only gate that ever fails the current miner over to the prior sortition's miner. It reads exactly this value:
```
stacks-signer/src/chainstate/v1.rs:76-93
let last_activity = db
    .get_last_activity_time(sortition)?
    .map(|time| UNIX_EPOCH + Duration::from_secs(time))
    .unwrap_or(received_time);
...
Ok(elapsed > block_proposal_timeout)
```
`check_proposal` in v1 (stacks-signer/src/chainstate/v1.rs:144-163) and `check_miner_inactivity` in v0/signer_state.rs (stacks-signer/src/v0/signer_state.rs:284-354, v2 path) both rely on `is_timed_out` to trigger the failover to the last valid sortition's miner.

Crucially, in v1's `check_proposal`, the pubkey-hash check happens *before* `confirms_latest_block_in_same_tenure`/`check_latest_block_in_tenure` is reached (v1.rs:238-286, then the `confirms_latest_block_in_same_tenure` call at v1.rs:328-338). This means the party that can trigger the activity reset must already be the legitimate sortition-winning miner for that tenure (or the prior sortition's miner if the current one was already invalidated before its first block) — i.e., exactly the "one-slot miner" actor class permitted by scope. That miner does not need any signer collusion, majority, or extra key access: it simply signs a cheap, deliberately-stale/non-advancing `NakamotoBlock` header with its own already-legitimate mining key and gossips it as a proposal.

This is the direct analog of the AlgebraPool bug: in AlgebraPool, an in-block state variable (the dynamic swap fee) that should be independent of unrelated actions (flashloan fee) is instead mutated by an earlier, attacker-triggerable transaction (a swap) that the later operation blindly reads. Here, `last_activity_time` — a piece of state that should reflect genuine miner liveness/progress — is mutated by attacker-controlled input (a non-advancing block proposal) that a later, security-critical decision (`is_timed_out`, and hence the signer failover state machine) blindly trusts.

### Impact Explanation
This is a liveness wedge: a misbehaving, stalled, or malicious current-tenure miner can indefinitely retain "current miner" status in the eyes of every signer without ever producing a block that advances the chain, by feeding a steady trickle of low/duplicate/non-advancing block proposals (well within `reorg_attempts_activity_timeout`/`block_proposal_timeout` cadence). Because `is_timed_out` never fires, `check_miner_inactivity`/`check_proposal` never fails over to the previous tenure's miner, so signers keep waiting on a miner that will never deliver a valid block — the network is wedged into non-production of new Stacks blocks by that tenure's holder, matching the "signer wedged into never signing valid blocks" impact class.

### Likelihood Explanation
Likelihood is high for any miner that wins a sortition slot and decides to grief or has degraded infrastructure: it requires no coordination with other signers, no cryptographic breaks, and no elevated access — only the ability to sign and gossip a `NakamotoBlock` header with a `chain_length` that doesn't exceed the tenure's already-known highest block, repeated at an interval shorter than `reorg_attempts_activity_timeout`. This is explicitly anticipated as legitimate ("miner may just be slow") but nothing distinguishes a genuinely slow miner from one deliberately spamming non-advancing proposals to suppress failover.

### Recommendation
Do not let a proposal that fails the "confirms more blocks" check indefinitely refresh the inactivity clock. Options: cap the number of times/aggregate duration a given tenure can extend its own timeout window purely via non-advancing proposals; require some proof of forward progress (e.g., increasing but still-invalid chain length, or bound the total extension time independent of proposal frequency); or decouple `is_timed_out`'s failover decision from `last_activity_time` refreshes that originate from proposals that were ultimately rejected.

### Proof of Concept
1. Miner M wins the sortition for tenure T and is set as `cur_sortition`/`ActiveMiner` for all signers.
2. M proposes and signs a single legitimate low block, or none at all, then repeatedly gossips additional `NakamotoBlock` proposals for tenure T whose `chain_length` does not exceed the tenure's currently known highest block (trivially producible, no execution needed beyond a valid header/signature from M's own mining key), spaced at an interval `< reorg_attempts_activity_timeout` (and `< block_proposal_timeout`).
3. Each such proposal reaches `SortitionData::check_latest_block_in_tenure` (stacks-signer/src/chainstate/mod.rs:390-419), is rejected as not-latest, but triggers `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` (mod.rs:411-416) on every signer that receives it.
4. `SortitionState::is_timed_out` (chainstate/v1.rs:55-94) computes `elapsed` against this continuously-refreshed `last_activity_time`, so `elapsed > block_proposal_timeout` never becomes true.
5. `check_proposal`/`check_miner_inactivity` therefore never invalidate M or fail over to the prior sortition's miner, even though M produces no chain progress — the tenure is wedged as long as M keeps up the trickle of throwaway proposals. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }

    pub fn check_miner_inactivity(
        &mut self,
        db: &mut SignerDb,
        client: &StacksClient,
        proposal_config: &ProposalEvalConfig,
        eval: &GlobalStateEvaluator,
    ) -> Result<(), SignerChainstateError> {
        let Self::Initialized(ref mut state_machine) = self else {
            // no inactivity if the state machine isn't initialized
            return Ok(());
        };

        let MinerState::ActiveMiner { ref tenure_id, .. } = state_machine.current_miner else {
            // no inactivity if there's no active miner
            return Ok(());
        };

        let version = SortitionStateVersion::from_protocol_version(
            state_machine.active_signer_protocol_version,
        );
        let is_timed_out = SortitionState::is_timed_out(
            &version,
            tenure_id,
            db,
            client.get_signer_address(),
            proposal_config,
            eval,
        )?;

        if !is_timed_out {
            return Ok(());
        }

        // the tenure timed out, try to see if we can use the prior tenure instead
        let CurrentAndLastSortition { last_sortition, .. } =
            client.get_current_and_last_sortition()?;
        let Some(last_sortition) = last_sortition
            .and_then(|val| SortitionData::try_from(val).ok())
            .map(|data| SortitionState::new(version, data))
        else {
            warn!("Signer State: Current miner timed out due to inactivity, but could not find a valid prior miner. Allowing current miner to continue");
            return Ok(());
        };

        let sortition_data = last_sortition.data();
        // If we already reverted to the last sortition miner, don't time it out as it means we have already timed out the current sorititon miner
        // as there is no other miner available.
        if &sortition_data.consensus_hash == tenure_id {
            warn!("Signer State: Last sortition miner has timed out, but no prior valid miner. Allowing last sortition miner to continue");
            return Ok(());
        }

        // Only revert to the prior miner if its tenure is the canonical Stacks tip's
        // tenure. A miner only continues (extends) a tenure it won, so if the canonical
        // tip is in some other tenure due to a Bitcoin reorg orphaning the prior
        // sortition's tenure, the prior miner's node has already stopped mining and
        // will never propose again.
        let stacks_tip_ch = client.get_peer_info()?.stacks_tip_consensus_hash;
        if sortition_data.consensus_hash != stacks_tip_ch {
            warn!(
                "Signer State: Current miner timed out due to inactivity, but the canonical stacks tip is not in the prior miner's tenure, so the prior miner cannot continue it. Allowing current miner to continue";
                "stacks_tip_consensus_hash" => %stacks_tip_ch,
                "prior_sortition_consensus_hash" => %sortition_data.consensus_hash,
            );
            return Ok(());
        }

        if !last_sortition.is_tenure_valid(db, client, proposal_config, eval)? {
            warn!("Signer State: Current miner timed out due to inactivity, but prior miner is not valid. Allowing current miner to continue");
            return Ok(());
        }
