### Title
Bridge `OutgoingToken` and URL disclosed to any authenticated role (including view-role) via unrestricted `GET /v2/bridge_types/:BridgeName` - ([File: core/web/router.go])

### Summary
`authv2.GET("/bridge_types/:BridgeName", bt.Show)` in `core/web/router.go` has no role wrapper, unlike its sibling mutation routes (`Create`, `Update`, `Destroy`) which all use `auth.RequiresEditRole`. `BridgeTypesController.Show` in `core/web/bridge_types_controller.go` returns `presenters.NewBridgeResource(bt)`, which includes the plaintext `OutgoingToken` field, so any authenticated user — including a view-role session/token — can retrieve it.

### Finding Description
The bridge routes are registered as: [1](#0-0) 

`authv2` only requires `auth.Authenticate` (session or token) with no role check, and `Show`/`Index` are not wrapped by any `RequiresXRole` function, while `Create`, `Update`, and `Destroy` explicitly require `auth.RequiresEditRole`. This means any authenticated role — including the lowest "view" role — can call `GET /v2/bridge_types/:BridgeName` or `GET /v2/bridge_types`.

`BridgeTypesController.Show` looks up the bridge and serializes it via `presenters.NewBridgeResource`: [2](#0-1) 

`NewBridgeResource` copies `OutgoingToken` (stored in plaintext in `bridges.BridgeType.OutgoingToken`) directly into the JSON response, along with the bridge `URL`: [3](#0-2) 

Note that the question's premise about `IncomingToken` is only partially correct: `BridgeType` only stores `IncomingTokenHash` (a salted hash), never the plaintext incoming token, and `NewBridgeResource` never populates the `IncomingToken` field (it stays as the zero value and is `omitempty`), so incoming tokens are not exposed via `Show`. `IncomingToken` plaintext is only ever returned once, at `Create` time. [4](#0-3) [5](#0-4) 

However, `OutgoingToken` (used by the node/adapter to authenticate outbound bridge requests) and the bridge `URL` are genuinely exposed on every `Show`/`Index` call with no role gate.

### Impact Explanation
A view-role authenticated user can retrieve the plaintext `OutgoingToken` and confidential `URL` for any bridge in the node, which is a credential/URL disclosure beyond what the view role is intended to access (compare with `Create/Update/Destroy` which require edit role). This maps to Chainlink's secret/credential disclosure impact class, though the severity is bounded because it requires already-authenticated access (no role check bypass of authentication itself, only of role authorization for reading a secret field) and the `OutgoingToken` is used to call out to the external adapter rather than a chain key.

### Likelihood Explanation
Requires only a valid view-role session or API token (the lowest privilege authenticated credential) and knowledge of a bridge name, which is discoverable via the equally-unrestricted `GET /v2/bridge_types` index endpoint. This is trivially and repeatably exploitable by any authenticated low-privilege user.

### Recommendation
Wrap `bt.Show` and `bt.Index` with an appropriate role check (e.g., `auth.RequiresEditRole` or a new `auth.RequiresViewRole` that still excludes secret fields), and/or redact `OutgoingToken` from `BridgeResource` in `presenters.NewBridgeResource` unless the requester holds edit/admin role, consistent with how `IncomingToken` is already excluded from `Show`/`Index` responses.

### Proof of Concept
Add a handler-level integration test in `core/web/bridge_types_controller_test.go`:
1. Create an `app := cltest.NewApplication(t)`, start it, create a bridge with `app.BridgeORM().CreateBridgeType(ctx, bt)` where `bt.OutgoingToken` is a known secret value.
2. Build an HTTP client authenticated with a view-role session/API token (`app.NewHTTPClient(&cltest.User{Role: sessions.UserRoleView})` or equivalent view-role fixture used elsewhere in the test suite).
3. Call `client.Get("/v2/bridge_types/" + bt.Name.String())`.
4. Assert the response is `200 OK` (not `403 Forbidden`) and parse into `presenters.BridgeResource`, asserting `resource.OutgoingToken == bt.OutgoingToken` and `resource.URL == bt.URL.String()`, demonstrating the view-role user obtained the plaintext outgoing token and URL.
5. As a control, repeat against `PATCH /v2/bridge_types/:BridgeName` with the same view-role client and assert `403 Forbidden` is returned (since `Update` is `RequiresEditRole`-gated), highlighting the asymmetric/missing gate on `Show`.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
