Reorg-permit record for a superseded tenure can be silently overwritten by an unrelated later reorg, voiding a signature's conflict protection - ([File: stacks-signer/src/signerdb.rs])

### Summary
`SignerDb::mark_tenure_superseded` persists the "reorg permit" that `SortitionData::check_parent_tenure_choice` grants when a miner legitimately reorgs a tenure that produced at most one poorly-timed block. The permit record is keyed only by the superseded tenure's `consensus_hash`, and is written with `INSERT OR REPLACE`, so any later, unrelated tenure that also happens to supersede the same `consensus_hash` will overwrite the earlier permit's `superseded_by_*` sortition — even though the two grants may refer to different reorg events with different validity windows. This mirrors the report's `init_if_needed` pattern: a security-relevant record meant to be set exactly once per sanctioned decision can instead be re-written by a later, independent caller.

### Finding Description
`check_parent_tenure_choice` sanctions a reorg only after checking that every reorged tenure has at most one globally accepted block and a poorly timed first block [2](#0-1) . Once sanctioned, it records the superseded tenures via `record_superseded_tenure` → `SignerDb::mark_tenure_superseded`, so that the signer's own prior signature over the superseded tenure's block no longer blocks the sanctioned replacement [3](#0-2) .

The persistence layer explicitly documents the overwrite behavior and treats it as intentional:

```
/// The permit is only honored while the permitting tenure's sortition is still canonical
/// (checked against the node when the record is applied): if a burnchain fork orphans it,
/// the reorg we sanctioned can no longer happen, so the record must not keep suppressing
/// this tenure's conflicts. A re-permit by a different tenure replaces the record, so the
/// latest permitting sortition is the one checked. Records age out via
/// [`SignerDb::prune_superseded_tenures`].
pub fn mark_tenure_superseded(...) {
    self.db.execute(
        "INSERT OR REPLACE INTO superseded_tenures (consensus_hash, burn_block_height, superseded_by_consensus_hash, superseded_by_burn_block_hash, superseded_at) VALUES (?1, ?2, ?3, ?4, ?5)",
        ...
    )?;
    Ok(())
}

`get_signed_conflicts` joins `blocks` against `superseded_tenures` by `consensus_hash` alone, and `reorg_permit_stands` derives whether the recorded permit is still valid purely from whether `superseded_by.burn_block_hash`'s sortition is canonical [5](#0-4) [6](#0-5) .

The overwrite ("re-permit") is confirmed by an in-repo test, which shows a permit recorded by tenure B for superseded tenure 1 later replaced by a permit recorded by a different tenure D — the earlier grant's `superseded_by_consensus_hash`/`burn_block_hash` are gone from the record entirely [7](#0-6) .

Because the primary key is `consensus_hash` (the superseded tenure) rather than a composite of (superseded tenure, permitting tenure), any later miner tenure that legitimately reorgs the *same* old tenure will replace the permit unconditionally. This makes the guard's freshness/validity check ("is `superseded_by` still canonical?") answer a question about the *latest* permit only. If a burnchain fork orphans only the newer permitting sortition while the original permitting sortition (which the earlier reorg was actually validated against) is still canonical, `reorg_permit_stands` will incorrectly report the permit voided, because the original `superseded_by_burn_block_hash` was discarded and replaced. Conversely, and more dangerously: if the *original* permit was correctly granted for a valid, still-canonical reorg, and a second, unrelated tenure independently and correctly re-supersedes the same old tenure with a *different* permitting sortition, the record now reflects only the later grant. If that later permitting sortition is later orphaned (a fork), `reorg_permit_stands` returns `false` and the conflict is treated as still live — even though the *first* permit (for the same superseded tenure, still canonical) legitimately excludes it. The net effect: the signer can be made to treat an already-sanctioned, still-valid reorg exclusion as void, causing it to refuse to sign a valid replacement block, or (in the inverse timing) to keep excluding a conflict based on a now-dead sortition, since only one `superseded_by_*` value can be tracked per `consensus_hash` at a time.

### Impact Explanation
This is a High-severity liveness/correctness issue: it can wedge a signer into refusing to sign an otherwise valid, already-sanctioned replacement block (because the stale/overwritten permit lookup reports the permit as void), or conversely leave a stale permit in effect based on the wrong sortition, letting an exclusion persist that should have expired. Either direction breaks the intended invariant that "the reorg-permit for a given superseded tenure remains valid exactly as long as the sortition that granted it does" — the record cannot represent more than one live grant, so a second, unrelated grant for the same tenure clobbers the first one's canonicality anchor.

### Likelihood Explanation
This requires no majority collusion and only a single miner producing two legitimate (rule-conforming) tenure-change sequences that both reorg the same prior tenure at different points — a scenario the reorg-timing rules in `check_parent_tenure_choice` are explicitly designed to permit under specific narrow conditions (an empty tenure, or one whose sole block was proposed too close to the next sortition) [8](#0-7) . Because burnchain forks and back-to-back short tenures are within a single miner's control (one-slot miner + normal gossip), and the code path is reachable purely by proposing tenure-change blocks that legitimately satisfy the reorg rules twice against the same target tenure, the precondition is realistic, though it depends on the specific timing/fork sequence needed to make the two permits diverge in canonicality.

### Recommendation
Key `superseded_tenures` (and the corresponding lookup/join in `get_signed_conflicts`) by `(consensus_hash, superseded_by_consensus_hash)` (or otherwise retain all live grants, not just the most recent), so that a later re-permit for the same tenure does not discard an earlier, still-canonical grant. Alternatively, before overwriting, check whether the existing permit's sortition is still canonical and only replace it if it has become invalid, preserving whichever grant is actually live.

### Proof of Concept
The existing regression test already demonstrates the overwrite mechanics end-to-end (it is the exact `INSERT OR REPLACE` semantics being exploited, just not yet driven through two independently valid `check_parent_tenure_choice` calls with divergent later fork outcomes): [9](#0-8) 

1. Miner tenure B legitimately reorgs tenure 1 under the reorg-timing rules → `mark_tenure_superseded(tenure_1, ..., superseded_by=B)` is recorded; tenure B's sortition is (and remains) canonical.
2. Later, miner tenure D independently and legitimately also ends up superseding tenure 1 (e.g., after further forking) → `mark_tenure_superseded(tenure_1, ..., superseded_by=D)` overwrites the record; now `superseded_by = D` only.
3. A burnchain fork later orphans tenure D's sortition (but not B's). `reorg_permit_stands` calls `get_sortition_by_burn_hash(D)`, gets 404, and returns `false` — even though B's grant, which would have returned `true`, is exactly as valid as it was in step 1, but is no longer recoverable because the record only tracks the latest permit.
4. The signer subsequently treats tenure 1's signed block as a live conflict again, and can refuse to sign a valid, already-sanctioned block built on the tenure-B chain, or otherwise diverge from what the (originally correct) permit intended — a liveness wedge distinct from the `INSERT OR REPLACE` behavior explicitly tested but never checked against this two-independent-grant scenario in `stacks-signer/src/signerdb.rs:3647-3710`.

    pub fn check_parent_tenure_choice(
        &self,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        first_proposal_burn_block_timing: &Duration,
    ) -> Result<bool, SignerChainstateError> {
        // if the parent tenure is the last sortition, it is a valid choice.
        // if the parent tenure is a reorg, then all of the reorged sortitions
        //  must either have produced zero blocks _or_ produced their first (and only) block
        //  very close to the burn block transition.
        if self.prior_sortition == self.parent_tenure_id {
            return Ok(true);
        }
        info!(
            "Most recent miner's tenure does not build off the prior sortition, checking if this is valid behavior";
            "sortition_state.consensus_hash" => %self.consensus_hash,
            "sortition_state.prior_sortition" => %self.prior_sortition,
            "sortition_state.parent_tenure_id" => %self.parent_tenure_id,
        );

        let tenures_reorged =
            client.get_tenure_forking_info(&self.parent_tenure_id, &self.prior_sortition)?;
        if tenures_reorged.is_empty() {
            warn!("Miner is not building off of most recent tenure, but stacks node was unable to return information about the relevant sortitions. Marking miner invalid.");
            return Ok(false);
        }

        // this value *should* always be some, but try to do the best we can if it isn't
        let sortition_state_received_time =
            signer_db.get_burn_block_receive_time(&self.burn_block_hash)?;

        // Track which tenures are superseded by the reorg, then mark them in
        // the DB after the reorg is permitted.
        let mut superseded_tenures = Vec::new();
        for tenure in tenures_reorged.iter() {
            if tenure.consensus_hash == self.parent_tenure_id {
                // this was a built-upon tenure, no need to check this tenure as part of the reorg.
                continue;
            }

            // disallow reorg if more than one block has already been signed
            let globally_accepted_blocks =
                signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
            if globally_accepted_blocks > 1 {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already more than one globally accepted block.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => ?tenure.first_block_mined,
                    "globally_accepted_blocks" => globally_accepted_blocks,
                );
                return Ok(false);
            }

            let Some(first_block_mined) = &tenure.first_block_mined else {
                // The node saw no blocks in this tenure, so the reorg takes nothing away from
                // the canonical chain. We may still hold a signature over a block in it that
                // the node has never seen (a block we accept locally is not handed to the node
                // until the whole signer set has signed it), so the reorg must still be
                // recorded if it is permitted.
                superseded_tenures.push(tenure);
                continue;
            };
            let Some(local_block_info) =
                signer_db.get_first_approved_block_in_tenure(&tenure.consensus_hash)?
            else {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already mined blocks, and there is no local knowledge for that tenure's block timing.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => %first_block_mined,
                );
                return Ok(false);
            };

            let checked_proposal_timing = if let Some(sortition_state_received_time) =
                sortition_state_received_time
            {
                // how long was there between when the proposal was received and the next sortition started?
                let proposal_to_sortition = if let Some(approved_at) =
                    local_block_info.approved_time
                {
                    sortition_state_received_time.saturating_sub(approved_at)
                } else {
                    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
                    0
                };
                if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
                    info!(
                        "Miner is not building off of most recent tenure. A tenure they reorg has already mined blocks, but the block was poorly timed, allowing the reorg.";
                        "parent_tenure" => %self.parent_tenure_id,
                        "last_sortition" => %self.prior_sortition,
                        "violating_tenure_id" => %tenure.consensus_hash,
                        "violating_tenure_first_block_id" => %first_block_mined,
                        "violating_tenure_proposed_time" => local_block_info.proposed_time,
                        "new_tenure_received_time" => sortition_state_received_time,
                        "new_tenure_burn_timestamp" => self.burn_header_timestamp,
                        "first_proposal_burn_block_timing_secs" => first_proposal_burn_block_timing.as_secs(),
                        "proposal_to_sortition" => proposal_to_sortition,
                    );
                    superseded_tenures.push(tenure);
                    continue;
                }
                true
            } else {
                false
            };

            warn!(
                "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already mined blocks.";
                "parent_tenure" => %self.parent_tenure_id,
                "last_sortition" => %self.prior_sortition,
                "violating_tenure_id" => %tenure.consensus_hash,
                "violating_tenure_first_block_id" => %first_block_mined,
                "checked_proposal_timing" => checked_proposal_timing,
            );
            return Ok(false);
        }
        // Every reorged tenure cleared the rules, so the reorg is permitted.
        for tenure in superseded_tenures {
            self.record_superseded_tenure(signer_db, tenure);
        }
        Ok(true)
    }

    /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
    }
