### Title
CORS wildcard-origin suffix matching allows domain-spoofing bypass without dot-boundary check - ([File: core/services/gateway/network/httpserver.go])

### Summary
`(*httpServer).isAllowedOrigin` implements wildcard-origin matching (`*.example.com`) using `strings.HasSuffix(originHost, allowedHost)` without verifying that the character preceding the matched suffix is a literal `.`. This allows an attacker-controlled host such as `evilexample.com` to satisfy an allow-rule intended only for subdomains of `example.com` (e.g. `sub.example.com`), causing the gateway to reflect the attacker's `Origin` in `Access-Control-Allow-Origin`.

### Finding Description
In `isAllowedOrigin` [1](#0-0) , wildcard entries strip the leading `*.` and then perform a raw suffix comparison: `strings.HasSuffix(originHost, allowedHost)`. Because there is no check that `originHost` has a `.` immediately before the matched `allowedHost` substring, a host like `evilexample.com` incorrectly satisfies a `*.example.com` allow-rule (since `"evilexample.com"` ends with the literal string `"example.com"`), even though it is not actually a subdomain of `example.com`. This is a genuine implementation defect in the intentionally-supported wildcard-subdomain matching feature (not merely a misconfiguration), since the wildcard capability is explicitly coded and documented via the `*.` prefix convention, and the bug lies in the missing boundary check within that code path.

Once `isAllowedOrigin` returns `true` for the attacker's crafted `Origin`, `handleRequest` reflects it verbatim: `w.Header().Set("Access-Control-Allow-Origin", origin)` [2](#0-1) . The exact (non-wildcard) match path (`originHost == allowedHost`) is unaffected and safe; the flaw is confined to the wildcard branch.

### Impact Explanation
If an operator configures a wildcard `CORSAllowedOrigins` entry (e.g. `*.example.com`) intending to permit only legitimate subdomains, an attacker who registers or controls a domain that merely ends with that string (e.g. `evilexample.com`, `notexample.com`) can have their origin treated as allowed. A victim's browser visiting the attacker's page could then have cross-origin gateway requests answered with `Access-Control-Allow-Origin` set to the attacker's origin, letting the attacker-controlled page read the response via `fetch`/`XHR` with credentials, if the browser attaches credentials (cookies/authorization headers) automatically to such gateway requests. This maps to a cross-user response confusion / CORS allowlist bypass impact class.

I was unable to fully confirm within available context whether the gateway's HTTP endpoint relies on browser-stored credentials (cookies) that are automatically attached cross-origin, versus payload-embedded signatures/JWTs that a malicious page cannot forge; the `ProcessRequest` handler takes an explicit `jwtToken` string extracted from the `Authorization: Bearer` header [3](#0-2) , and if that token is not stored in a way the browser auto-attaches (e.g. only in JS memory / localStorage, not a cookie), classic CSRF-with-CORS credential theft would require the attacker's page to already possess the token, reducing exploitability to scenarios where the victim's own session token is otherwise exposed to the page.

### Likelihood Explanation
Exploitability requires: (1) the gateway operator has configured at least one wildcard entry in `CORSAllowedOrigins` (a supported, common configuration pattern for multi-tenant subdomains), and (2) the attacker registers/controls a domain string that happens to end with the configured suffix without an intervening dot (e.g. `evilexample.com` vs. intended `*.example.com`). This is a plausible, low-cost attack for an external, unauthenticated actor — domain registration is trivial and no privileged access is needed. It does not require exact-match allowlists to be misconfigured; it is triggered by the existing wildcard-matching code itself.

### Recommendation
Fix the wildcard suffix comparison to require a literal dot boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // keep leading dot: ".example.com"
    if strings.HasSuffix(originHost, suffix) || originHost == suffix[1:] {
        return true
    }
}
```
This ensures `originHost` must equal `example.com` or end with `.example.com`, rejecting `evilexample.com`.

### Proof of Concept
Go unit test in `core/services/gateway/network/httpserver_test.go`:
```go
func TestIsAllowedOrigin_WildcardSuffixBypass(t *testing.T) {
    s := &httpServer{
        config: &HTTPServerConfig{CORSAllowedOrigins: []string{"https://*.example.com"}},
        lggr:   logger.Test(t),
    }
    // Should be allowed: legitimate subdomain
    assert.True(t, s.isAllowedOrigin("https://sub.example.com"))
    // Should be rejected: not an actual subdomain, only shares suffix
    assert.False(t, s.isAllowedOrigin("https://evilexample.com"))
}
```
Expected current (buggy) behavior: the second assertion fails (returns `true`), demonstrating the bypass; after applying the recommended dot-boundary fix, it correctly returns `false`.
