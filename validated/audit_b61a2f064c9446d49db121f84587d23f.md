### Title
JWT replay-protection TOCTOU race allows double-use of single-use trigger token - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` and only calls `h.jwtCache.recordUsage(claims.ID)` after all subsequent authorization checks succeed, with no locking spanning the check-and-record sequence. Two concurrent requests bearing the identical JWT can both observe "not yet replayed" and both pass authorization before either records usage, defeating the single-use guarantee.

### Finding Description
`Authorize` (core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:80-108) calls:
- `h.jwtCache.isReplay(claims.ID)` at line 87, which takes `cache.mu.RLock()`, checks map membership, and releases the lock (lines 399-405).
- Only after passing the workflow-lookup and signer-authorization checks does it call `h.jwtCache.recordUsage(claims.ID)` at line 105, which takes a separate `cache.mu.Lock()` (lines 407-412).

There is no single critical section covering "check-then-set" — `isReplay` and `recordUsage` are two independent lock acquisitions separated by other logic (map lookups, signer authorization). This is a classic TOCTOU (time-of-check/time-of-use) race: if two goroutines call `Authorize` concurrently with the same JWT (same `jti`), both can execute `isReplay` before either executes `recordUsage`, so both see `exists == false` and both proceed to be treated as validly authorized.

This is reachable from an unprivileged, unauthenticated-except-for-the-JWT attacker: `HTTPTriggerHandler.HandleUserTriggerRequest` → `authorizeRequest` → `WorkflowMetadataHandler.Authorize` (core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:99, 361-369), which is invoked directly from the gateway's user-facing JSON-RPC request path (`req.Auth` is attacker-supplied). No other check in the call path (rate limiting, request-ID uniqueness) protects against JWT reuse in the same instant — `checkRateLimit` runs after `Authorize` and rate limiting is per-workflow, not per-JWT, so it does not prevent this specific double-authorization. `setupCallback`'s requestID dedup check (line 402) only prevents duplicate `requestID`s, and the JWT/jti is independent from `req.ID`, so an attacker can pair the same JWT with two different unique `req.ID`s to reach two independent, distinct `savedCallback`s, each triggering a separate downstream workflow execution.

### Impact Explanation
Successful exploitation causes double execution of a workflow trigger from a single-use authorization JWT. This is a replay-protection / request-binding bypass: an attacker with a single, valid, authorized JWT can cause it to authorize two (or more, with enough parallel requests) separate `workflows.execute` invocations sent to the DON, effectively impersonating two independent authorized requests from one token. Depending on the workflow's semantics, this can result in double-spending of a one-time authorization (e.g., double execution of an action gated to run only once per token), consistent with Chainlink's "unauthorized job run" / "request impersonation" bounty impact class.

### Likelihood Explanation
Preconditions: attacker needs only a single valid JWT for the target workflow (the same credential a legitimate authorized user would normally use once) and the ability to fire two requests to the gateway near-simultaneously — no elevated privileges, no signing capability beyond what a normal authorized caller already has. The race window is small (µs to ms, bounded by workflow lookup + map iteration + signer comparison between the two lock acquisitions) but is a genuine, reproducible concurrency bug, not merely theoretical; exploitability under real network latency depends on how tightly synchronized the two requests can be made, which introduces some non-determinism but does not eliminate the vulnerability.

### Recommendation
Make the replay-check-and-record operation atomic under a single critical section, e.g. add a combined method:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	if _, exists := cache.cache[jti]; exists {
		return false // replay
	}
	cache.cache[jti] = time.Now()
	return true
}
```
Call this once, immediately upon extracting `claims.ID` (before or in place of the current `isReplay` call), and reject the request if it returns `false`. If authorization subsequently fails for other reasons (workflow not found, signer not authorized), keep the jti marked as used (rejecting all subsequent reuse) or handle rollback deliberately — but do not perform separate check/record calls with unrelated logic executing in between.

### Proof of Concept
Go unit test plan (in `workflow_metadata_handler_test.go`):
1. Instantiate a `WorkflowMetadataHandler` with a registered `workflowID`, an authorized key pool containing a test signer, and `jwtCache` initialized via `newJWTReplayCache`.
2. Generate one valid JWT (`token`) signed by the authorized test key with a fixed `jti`.
3. Add an artificial delay/synchronization point inside a wrapped/test-only copy of `Authorize` (or use a race-timing harness) so both goroutines pass `isReplay` before either reaches `recordUsage` — e.g. use two goroutines with a `sync.WaitGroup`/barrier so both call `h.jwtCache.isReplay(claims.ID)` concurrently before proceeding.
4. Fire two goroutines calling `h.Authorize(workflowID, token, req)` concurrently with the same `token`/`jti`, synchronized via a barrier (channel) to maximize race window overlap.
5. Assert: both goroutines return `nil` error (success) — demonstrating replay protection is defeated. A fixed implementation using `checkAndRecord` should instead show exactly one goroutine succeeding and the other receiving the "JWT token has already been used" error.
6. Optionally, run with `go test -race -count=100` to confirm reproducibility of the double-success outcome under load, and confirm `len(h.jwtCache.cache)` still shows only one entry despite two successful authorizations (proving both bypassed the cache check). func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
