### Title
Unprotected `initializeConfig` Setter Allows Anyone to Inject a Malicious `IBridgeConfig` into `BridgeCommittee`, Enabling Bridge Vault Drain — (`File: bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig` is an `external` function with no access-control modifier. Its only guard is a one-time check (`config == address(0)`). Any Ethereum address can front-run the legitimate deployer and set a malicious `IBridgeConfig` contract. Because every token-unlock path in `SuiBridge` resolves the ERC-20 address and decimal precision through `committee.config()`, a poisoned config redirects vault withdrawals to an attacker-chosen token and inflates the transferred amount, draining the bridge vault.

---

### Finding Description

`BridgeCommittee.sol` exposes a two-step initialization pattern. The first step, `initialize`, is protected by OpenZeppelin's `initializer` modifier and sets committee members and stakes. The second step, `initializeConfig`, is a plain `external` function:

```solidity
// bridge/evm/contracts/BridgeCommittee.sol  lines 63-66
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [1](#0-0) 

There is no `onlyOwner`, no committee-signature gate, and no deployer check. The sole guard prevents a *second* call, but does nothing to prevent a *first* call by an arbitrary address before the legitimate deployer reaches it.

The `config` storage variable is the single source of truth for every token-related decision in `SuiBridge`:

- **`_transferTokensFromVault`** (line 250) resolves the ERC-20 address to pull from the vault:
  ```solidity
  address tokenAddress = committee.config().tokenAddressOf(tokenID);
  vault.transferERC20(tokenAddress, recipientAddress, amount);
  ``` [2](#0-1) 

- **`transferBridgedTokensWithSignatures`** (lines 78-82) uses `config` to compute the ERC-20-adjusted amount:
  ```solidity
  uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
      IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(),
      config.tokenSuiDecimalOf(tokenTransferPayload.tokenID),
      tokenTransferPayload.amount
  );
  ``` [3](#0-2) 

- **`onlySupportedChain`** modifier (line 285) and **`bridgeERC20`** (line 148) also call `committee.config()`. [4](#0-3) 

A malicious `IBridgeConfig` can return:
- `tokenAddressOf(any_id)` → `address(WETH)` (or any high-value token held by the vault)
- `tokenSuiDecimalOf(any_id)` → `0` (maximises `convertSuiToERC20Decimal` output)
- `chainID()` → the real chain ID (so the chain check passes)
- `isChainSupported(any_id)` → `true`
- `tokenPriceOf(any_id)` → `1` (minimises the limiter's USD calculation, bypassing the 24-hour cap)

---

### Impact Explanation

**Critical — direct fund theft from the bridge vault.**

With a poisoned config in place:

1. The attacker initiates a legitimate bridge transfer on Sui for 1 unit of any token (negligible cost).
2. The committee signs the resulting message (they have no visibility into the EVM config state).
3. The attacker calls `SuiBridge.transferBridgedTokensWithSignatures` with the valid committee signatures.
4. `_transferTokensFromVault` resolves `tokenAddress = WETH` from the malicious config and calls `vault.transferERC20(WETH, attacker, inflated_amount)`.
5. The `BridgeVault` (owned by `SuiBridge`) executes the transfer unconditionally.
6. The bridge limiter is bypassed because the malicious config returns a near-zero USD price.

The entire WETH (and any other ERC-20) balance of the vault can be drained in a single transaction. The `BridgeVault` holds all bridged assets; its `transferERC20` and `transferETH` functions are `onlyOwner` (owner = `SuiBridge`), so the vault itself provides no additional protection once `SuiBridge` is directed by a poisoned config. [5](#0-4) 

---

### Likelihood Explanation

**High.** The vulnerability is exploitable by any Ethereum address with no special privileges. The attack window opens the moment `BridgeCommittee.initialize` completes and closes only when the legitimate `initializeConfig` call is mined. On Ethereum mainnet, a mempool-watching bot can trivially front-run the deployer's `initializeConfig` transaction. The deployer's own comment acknowledges the sequencing dependency ("This function should be called directly after config deployment"), confirming the window is known but unguarded. [6](#0-5) 

---

### Recommendation

Set `config` atomically inside `initialize`, eliminating the separate `initializeConfig` function entirely:

```solidity
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // add config here
) external initializer {
    // ... existing committee setup ...
    require(_config != address(0), "BridgeCommittee: Zero config address");
    config = IBridgeConfig(_config);
}
```

If a two-step flow is required for deployment ordering, restrict `initializeConfig` to the deployer or a multisig:

```solidity
address private immutable _deployer;
constructor() { _deployer = msg.sender; _disableInitializers(); }

function initializeConfig(address _config) external {
    require(msg.sender == _deployer, "BridgeCommittee: Not deployer");
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

### Proof of Concept

```
Deployment sequence (attacker observes mempool):

1. Deployer broadcasts: BridgeCommittee.initialize([v1,v2,...], [stake1,...], 10000)
   → mined; committee members set, config == address(0)

2. Deployer broadcasts: BridgeCommittee.initializeConfig(legitimateConfig)
   → PENDING in mempool

3. Attacker broadcasts (higher gas): BridgeCommittee.initializeConfig(maliciousConfig)
   → MINED FIRST; config = maliciousConfig

4. Deployer's tx reverts: "BridgeCommittee: Config already initialized"

5. Vault is funded with WETH.

6. Attacker bridges 1 unit of token-id 1 from Sui → Ethereum.
   Committee signs: {tokenID:1, amount:1, recipient:attacker, targetChain:1}

7. Attacker calls SuiBridge.transferBridgedTokensWithSignatures(sigs, message)
   - verifySignatures passes (committee stake unaffected)
   - config.tokenAddressOf(1) → WETH
   - config.tokenSuiDecimalOf(1) → 0
   - convertSuiToERC20Decimal(18, 0, 1) → 1e18 (= 1 WETH)
   - config.tokenPriceOf(1) → 1 → limiter passes
   - vault.transferERC20(WETH, attacker, 1e18) → 1 WETH stolen

8. Repeat for each token in the vault until drained.
```
