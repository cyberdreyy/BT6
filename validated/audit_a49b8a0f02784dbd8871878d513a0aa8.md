### Title
Stale confirmations from deleted multisig members are counted toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` removes a member and its own outstanding requests, but does not remove that member's confirmations from requests submitted by *other* members. `confirm` (and the identical logic in the older `multisig/src/lib.rs`) executes a request once `confirmations.len() + 1 >= num_confirmations`, without checking that every entry in `confirmations` still corresponds to a live member. This lets a request execute with fewer *live* confirmations than the configured threshold, breaking the binding: confirmations counted == confirmations from currently live members.

### Finding Description
- A pending request `R` (filed by member `A`) is confirmed by member `B` (`confirm` inserts `B`'s identity into `self.confirmations[R]`), per `confirm`: [2](#0-1) .
- Later, the multisig votes to `DeleteMember { member: B }`. `delete_member` only purges requests where `r.member == member` (i.e., requests B *itself* filed), and drops `num_requests_pk` for B and B's access key — it never scans `self.confirmations` for entries where B appears as a confirmer on someone else's request: [3](#0-2) .
- Request `R`'s confirmation set therefore still contains B even though B is no longer in `self.members`.
- When enough of the *remaining* live members confirm `R`, `confirm` computes `confirmations.len() as u32 + 1 >= self.num_confirmations` using the stale set size, which still includes B's now-invalid confirmation, and executes the request: [4](#0-3) .
- `current_member()`/`assert_valid_request` only validate the *caller* of the current transaction is a live member; they never re-validate the *previously stored* confirmers in the set: [5](#0-4)  and [6](#0-5) .

Equality broken: `live confirmations required == num_confirmations` becomes `live confirmations + stale confirmations >= num_confirmations`, i.e. a request can execute with fewer than `num_confirmations` currently authorized signers.

### Impact Explanation
This is a Critical-class issue per the rubric ("a multisig request executed below threshold"). A `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` action can be pushed through with one fewer live signer than the multisig's configured K-of-N policy, effectively lowering the security threshold without an explicit `SetNumConfirmations` action. This can enable unauthorized fund transfers or authority changes (e.g. adding a new full-access key) that should have required more currently-trusted approvals.

### Likelihood Explanation
Requires: (1) a member confirms a pending request, (2) that member is later removed via a legitimate `DeleteMember` vote (a routine operational action, e.g. offboarding a team member or rotating a compromised key) before request `R` is deleted/expired, and (3) `R` is still pending. Given requests can remain active up to the `active_requests_limit`/until deleted, and member turnover is a normal multisig operation, this is readily triggerable in normal operational flow — it does not require any single member to be a malicious "attacker" beyond ordinary participation, and the surviving members executing `R` may not even realize a stale confirmation is being counted.

### Recommendation
When deleting a member, iterate `self.confirmations` and remove the deleted member's identity from every confirmation set (not just requests they authored), or alternatively re-validate at `confirm`/execution time that every entry in the confirmation set is still contained in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize multisig with members `[A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` for `Transfer{amount}` to `evil` → request `R0`, confirmations = `{A}`.
3. `B` calls `confirm(R0)` → confirmations = `{A, B}` (2 < 3, not yet executed).
4. Members vote (via their own separate request) to `DeleteMember { member: B }`; `delete_member` runs — since `B` did not author `R0`, `R0`'s confirmations are untouched, `B` remains in `confirmations[R0] = {A, B}`, and `self.members` no longer contains `B`.
5. `C` calls `confirm(R0)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request` fires the `Transfer`, even though only `A` and `C` are currently live members who ever confirmed it (2 live confirmations, threshold 3). [7](#0-6)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
