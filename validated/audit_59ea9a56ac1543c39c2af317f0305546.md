### Title
Multisig confirmations from removed members are not purged, letting a request execute below the true K-of-N threshold - (File: `multisig2/src/lib.rs`)

### Summary
The multisig contract's `DeleteMember` action removes a member from the active member set and cancels only the requests *created* by that member, but it never scrubs confirmations that member had already cast on *other* still-pending requests. Those stale confirmations continue to count toward `num_confirmations` in `confirm()`, so a request can be executed with fewer live, currently-authorized members than the configured threshold — the same class of bug as the reported issue, where a previously-trusted party's granted role/permission is not relinquished when their standing changes, letting them retain effective custodial power they should have lost.

### Finding Description
`add_request` records a `MultiSigRequestWithSigner{ member, ... }` and initializes an empty confirmation `HashSet<String>` keyed by `member.to_string()`: [1](#0-0) 

`confirm()` only checks whether the *current caller* is a valid member (`current_member()`), then simply counts the size of the stored confirmation set against `num_confirmations` — it never re-validates that the *previously stored* confirmations still belong to current members: [2](#0-1) 

When a member is removed via `DeleteMember`, `delete_member()` only clears requests **created by** that member and removes their `num_requests_pk` entry — it does not touch `self.confirmations` entries the member may have left on requests created by *other* members: [3](#0-2) 

Because `self.members` and `self.confirmations` are independent data structures, a member's identity string persists inside any confirmation set it was added to, even after that member is deleted from `self.members`. `confirm()`'s threshold check (`confirmations.len() + 1 >= self.num_confirmations`) treats that stale entry as a live vote forever, since nothing re-derives "is this confirming identity still a current member" at execution time.

**Binding broken**: `confirmations counted == live members who approved`. After a member is removed, the equality becomes `confirmations counted > live members who approved`, letting an under-threshold set of *current* members execute an action that should require `num_confirmations` currently-authorized approvals.

The exact same pattern exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` removes only the requests signed by that key and the `num_requests_pk` entry, without scrubbing that key's confirmations on other requests: [4](#0-3) [5](#0-4) 

### Impact Explanation
This is Critical per the rules: "a multisig request executed below threshold." An action (e.g. `Transfer`, `FunctionCall`, `AddKey`/`AddMember`) can be scheduled and executed with confirmations from fewer currently-valid members than `num_confirmations` requires, because one or more of the counted confirmations belong to an account/key that has since been removed from the member set. This directly weakens the custody guarantee that the multisig's K-of-N threshold is supposed to enforce over funds and privileged actions controlled by the contract.

### Likelihood Explanation
This requires no attacker-controlled deployment or foundation privilege — it only requires the normal, expected operational sequence of a multisig: a member confirms a pending request, that member is later removed (e.g., due to key rotation, offboarding, or compromise response), and the remaining members later confirm the same still-pending request. This is a realistic and likely operational sequence for any long-lived multisig with membership churn, not a contrived edge case.

### Recommendation
When a member is deleted (`DeleteMember`/`DeleteKey`), iterate over `self.requests`/`self.confirmations` and strip that member's identifier from every confirmation set, not just requests it authored. Alternatively, on `confirm()`, filter the stored confirmation set against `self.members` before comparing its size to `num_confirmations`, so stale confirmations from removed members never count toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with 5 members `{A,B,C,D,E}` and `num_confirmations = 3`.
2. Member `A` calls `add_request` creating request `X` (e.g., `Transfer`).
3. Member `B` calls `confirm(X)` → `confirmations = {B}` (1/3).
4. Members later submit and confirm a separate request removing `B` via `DeleteMember{member: B}` (reaching 3/5 valid confirmations on that unrelated request) — `delete_member()` only clears requests `B` authored; it does not touch request `X`'s confirmation set, which still contains `B`: [6](#0-5) 
5. Members `C` and `D` (both still valid) each call `confirm(X)`. On `D`'s call, `confirmations.len() + 1 = 3 >= num_confirmations (3)` is satisfied using stale entry `B` plus live `C`,`D` — request `X` executes via `execute_request`: [7](#0-6) 
6. Request `X` (e.g. a `Transfer` or `AddKey`) is executed with only 2 currently-authorized members (`C`, `D`) actually approving it, below the intended 3-of-N threshold.

    pub fn add_request(&mut self, request: MultiSigRequest) -> RequestId {
        let current_member = self.current_member().unwrap_or_else(|| {
            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )
        });
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
