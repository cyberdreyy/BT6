### Title
External Initiator credentials bypass the "EIs not allowed" restriction on int-ID job runs, permitting unauthorized execution of arbitrary jobs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` intends to restrict execution-by-numeric-job-ID to genuine users only (per its own comment "only users are allowed to run jobs using int IDs - EIs not allowed"), but it implements this check via `auth.GetAuthenticatedUser(c)`'s boolean return value rather than checking the actual authenticated principal type. Because `AuthenticateExternalInitiator` also populates `SessionUserKey` with a synthetic `UserRoleRun` user, `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests, defeating the intended restriction and letting any EI credential holder trigger `RunJobV2` on any integer job ID, without that job ever being bound to the EI.

### Finding Description
- `AuthenticateExternalInitiator` (core/web/auth/auth.go:119-151) validates only the EI access key/secret against `bridges.ExternalInitiator`, then sets both `SessionExternalInitiatorKey` and, critically, `SessionUserKey` to a placeholder `&clsessions.User{Role: clsessions.UserRoleRun}` (line 148). This makes the EI indistinguishable from a real user when queried via `GetAuthenticatedUser`.
- `GetAuthenticatedUser` (core/web/auth/auth.go:178-187) simply reads `SessionUserKey` from context and returns `(*User, true)` if present — it cannot tell whether the caller authenticated as a session/token user or as an EI.
- `PipelineRunsController.Create` (core/web/pipeline_runs_controller.go:109-125) uses exactly this boolean (`_, isUser := auth.GetAuthenticatedUser(c)`) to gate the numeric-job-ID execution path, with an explicit comment stating EIs should be excluded from this path. Since `isUser` is `true` for EI requests too, an EI can reach `strconv.ParseInt(idStr, ...)` and call `prc.App.RunJobV2(ctx, jobID, nil)` directly.
- `RunJobV2` is invoked with only the numeric job ID — there is no lookup or check that verifies the job is one the EI is registered for (that binding only exists for webhook/UUID-addressed jobs, and the UUID branch is explicitly disabled at lines 103-107 with `job.ErrJobTypeRemoved`). Thus for the int-ID path, **no job ownership/binding check exists at all** for EI callers.
- The route is registered under the v2 API group authenticated via the combined `auth.Authenticate(..., AuthenticateBySession, AuthenticateByToken, AuthenticateExternalInitiator)` chain and wrapped by `auth.RequiresRunRole`, which only checks `user.Role != UserRoleView` — the synthetic `UserRoleRun` assigned to EIs satisfies this trivially.

### Impact Explanation
An EI credential holder (a low-privilege, non-admin, non-operator credential type intended only to trigger jobs it is registered against) can invoke arbitrary job runs on the node by integer job ID, including jobs it was never associated with. This is an authorization bypass leading to unauthorized job execution — matching the "unauthorized job run" impact class. Depending on job configuration, this could trigger unintended on-chain transactions, oracle report submissions, or resource exhaustion, all without the job owner's consent.

### Likelihood Explanation
The only precondition is possession of a valid EI access key/secret — a credential class explicitly intended to be far less privileged than a full user session/API token. The exploit path is deterministic and fully server-side reachable via a single crafted HTTP request (`POST /v2/jobs/<int_job_id>/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers), requiring no race conditions or timing dependencies. It is trivially repeatable against any int32 job ID on the node.

### Recommendation
Do not conflate EI authentication with user authentication in `SessionUserKey`. Either:
1. Keep a distinct context key/type for EI-derived pseudo-users so `GetAuthenticatedUser` returns `false` (or a distinguishable value) for EI-only requests, and have `Create` explicitly check `auth.GetAuthenticatedExternalInitiator(c)` to reject the int-ID path for EIs, matching its own comment's intent; or
2. In `PipelineRunsController.Create`, explicitly check `_, isEI := auth.GetAuthenticatedExternalInitiator(c); if isEI { reject }` before allowing the numeric-ID `RunJobV2` path, regardless of `isUser`.

### Proof of Concept
Go handler-level integration test plan (in `core/web/pipeline_runs_controller_test.go` style):
1. Set up a test app with an authenticated non-EI job (e.g., a DirectRequest/keeper job) created normally, obtaining its int32 `job.ID`.
2. Register an `ExternalInitiator` (via `bridges.NewExternalInitiator`) that is **not** associated with that job (EIs have no job-binding table entry for int-ID jobs at all).
3. Issue `POST /v2/jobs/<job.ID>/runs` using the EI's `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers (no session cookie, no API token).
4. Assert response is `200 OK` with a valid `pipelineRun` resource returned (i.e., `RunJobV2` executed), and that the pipeline run appears in `PipelineORM().FindRun`, despite the EI never having been linked to that job.
5. Contrast with expected-secure behavior: assert the request should instead return `422 Unprocessable Entity` ("bad job ID") per the code comment's intent, proving the check `isUser` at core/web/pipeline_runs_controller.go:109 fails to exclude EIs as documented. func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
