### Title
Unbounded commission basis-points accepted and stored by `update_commission_bps` - (File: programs/vote/src/vote_state/mod.rs)

### Summary
The vote program's `update_commission_bps` instruction handler (SIMD-0291/SIMD-0123) accepts any `u16` value (0–65535) for `commission_bps` and stores it directly into the vote account state without any upper-bound validation, unlike the analogous legacy `update_commission` percentage setter that is at least range-limited by the `u8` type (0–255, informally 0-100).

### Finding Description
`update_commission_bps` in `programs/vote/src/vote_state/mod.rs` (lines 827-859) takes a caller-supplied `commission_bps: u16` and, after verifying the authorized withdrawer's signature, calls `vote_state.set_inflation_rewards_commission_bps(commission_bps)` or `vote_state.set_block_revenue_commission_bps(commission_bps)` with no bounds check. `VoteStateHandler::set_inflation_rewards_commission_bps` (in `programs/vote/src/vote_state/handler.rs`) writes the raw value into `VoteStateV4.inflation_rewards_commission_bps` unconditionally — the corresponding unit test `test_set_inflation_rewards_commission_bps` explicitly documents that "values > 10,000 are allowed at program level. Capping happens during reward calculation, not storage" (lines 1768-1774).

This is exactly the bug class from the external report: a fee/commission setter with no enforced upper (or lower) limit at the point of mutation, relying entirely on a downstream consumer to clamp the value. Here that downstream consumer is `commission_split`/`commission_split_preserve_lamports` in `runtime/src/inflation_rewards/mod.rs`, which does correctly clamp with `commission_bps.min(MAX_BPS)` where `MAX_BPS = 10_000`. So the actual inflation/block-revenue reward math is protected.

However, the stored, unclamped value (e.g. `commission_bps` up to `u16::MAX` = 65,535, representing 655.35%) is exposed to any other consumer that reads `inflation_rewards_commission_bps`/`block_revenue_commission_bps` directly without re-clamping — including RPC/CLI displays (`account-decoder/src/parse_vote.rs`, `cli-output/src/cli_output.rs`) and any future or third-party code path that treats the field as a genuine percentage. Any such consumer would either panic on unexpected values, silently misreport delegator-facing commission info, or (if a code path exists that uses the raw value in fixed-point math without an explicit `.min(10_000)` clamp) could compute a share exceeding 100%, over-crediting the validator/collector at stakers' expense.

### Impact Explanation
This is a state-mutation correctness issue: the vote program itself accepts and permanently stores fee-like values (commission basis points) with no plausibility check, contrary to Solana's own domain semantics of "at most 100%." While the primary reward-calculation call sites currently defend themselves by clamping, this places the entire correctness burden on every present and future caller. A missed or inconsistent clamp on any less-audited consumer (RPC display, off-chain analytics, custom-collector logic in `custom_commission_collector`, or a future SIMD extension) can silently produce economically incorrect commission splits or misleading on-chain data, without any panic or explicit failure signal to indicate the misconfiguration.

### Likelihood Explanation
This requires only the vote account's authorized withdrawer signature — a normal, unprivileged operation available to any vote account owner via the `VoteInstruction::UpdateCommissionBps` instruction, dispatched from `programs/vote/src/vote_processor.rs`. No admin/consensus/validator privilege is needed; it's directly reachable from any ordinary signed transaction, so likelihood of triggering the invalid-state condition is high, even though the currently-known consumer clamps it.

### Recommendation
Add an explicit upper-bound check (`commission_bps <= 10_000`) inside `update_commission_bps` before calling `set_inflation_rewards_commission_bps`/`set_block_revenue_commission_bps`, returning `InstructionError::InvalidInstructionData` for out-of-range values, so invalid commission values can never be persisted to vote account state regardless of how downstream consumers handle them.

### Proof of Concept
1. Create/own a vote account (`VoteStateV4`) with an authorized withdrawer keypair.
2. Submit a `VoteInstruction::UpdateCommissionBps { commission_bps: 65535, kind: InflationRewards }` instruction signed by the withdrawer (with `block_revenue_sharing` feature active if targeting `BlockRevenue`).
3. Observe: the instruction succeeds and `VoteStateV4.inflation_rewards_commission_bps` is now `65535` (655.35%), as verified directly in the existing repository test `test_set_inflation_rewards_commission_bps` at `programs/vote/src/vote_state/handler.rs:1768-1774`, and exercised end-to-end in `test_update_commission_bps` at `programs/vote/src/vote_state/mod.rs:1927-1934` (`commission_bps_roundtrip(50_000); // 500%`).
4. Any RPC/CLI/analytics consumer reading this field directly (without re-implementing the `min(10_000)` clamp used only in `runtime/src/inflation_rewards/mod.rs`) will treat the vote account as having a commission > 100%, producing an economically invalid or crash-inducing state.

pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
