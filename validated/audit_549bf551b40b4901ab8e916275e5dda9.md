### Title
Loss-adjusted withdraw haircut only applies to the latest request epoch — older unclaimed receipts claim at par and drain the funded pool, freezing other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` records each receipt's basis under the *current* `epochNumber` (`withdrawsRequestsByEpoch[user][epoch]`) but only tracks the *latest* request epoch in `lastWithdrawRequest[user]`. When `stopEpochWithDuration` applies a pending-receipt loss, `collectWithdrawFunds` haircuts the **aggregate** `pendingWithdraws` (which includes receipts from all earlier epochs) but stores the recovery price only under the epoch at which the stop occurred. `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`, so it haircuts only the basis recorded under that one epoch. Any receipt basis the user accumulated in earlier epochs falls through to `_claimFundedWithdrawRequest`, which pays it at 100% from a pool that was only funded at the haircut rate. The early claimant over-draws, and later claimants' transfers revert — permanently freezing their recovery funds.

### Finding Description
Relevant code:

- `requestWithdraw` adds `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and sets `lastWithdrawRequest[_user] = currentEpoch` (lines 282–293). A user can request in multiple epochs; only the last epoch is remembered.
- `collectWithdrawFunds` (lines 411–430): when `_amount < pendingBasis`, it sets `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and pulls only the haircut amount of underlying into the strategy. `pendingBasis` is the aggregate over *all* pending receipts, including ones requested in earlier epochs. In `_stopEpoch` (IdleCDOEpochVariant.sol:408–410) `collectWithdrawFunds` runs *before* `strategy.deposit` increments `epochNumber`, so the price is stored under the epoch that was just stopped — the same epoch in which the newest requests were made.
- `_claimLossAdjustedWithdrawRequest` (lines 789–801): `lossEpoch = lastWithdrawRequest[_user]`; it clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` and the APR0 entry for that epoch via `_clearWithdrawClaimForEpoch`, which also resets `lastWithdrawRequest` to 0 (lines 832–835).
- `_claimFundedWithdrawRequest` (lines 319–350) then pays the remaining `withdrawsRequests[_user]` (the older-epoch basis, since the latest epoch's piece was subtracted) **at par** via `_transferFundedClaim`.

The only guard against this is in `requestWithdraw` (lines 261–271): it rejects a new request if `lossRecoveryPriceByEpoch[lastWithdrawRequest]` is non-zero. That check cannot help here because at the time the attacker makes the second request, no loss has been recorded yet — the loss is applied by the honest manager's `stopEpochWithDuration` *afterwards*.

Attack sequence (attacker = ordinary KYC'd lender):

1. Epoch E running → stops normally → buffer period.
2. Attacker `requestWithdraw(part1)` → basis under epoch E, `lastWithdrawRequest = E`. Attacker does **not** claim even though eligible.
3. Buffer still open → attacker `requestWithdraw(part2)` → basis under epoch E+1, `lastWithdrawRequest = E+1`. (Allowed: receipt is merged, user "waits another epoch", per the comment at line 323.)
4. Epoch E+1 runs and ends with a realized loss; manager calls `stopEpochWithDuration(_, _, _, _lossAmount)`. `pendingWithdraws` (which includes the attacker's epoch-E basis *and* every other user's receipts) is haircut to `price < 1`, and the strategy is funded with only `pendingBasis * price`.
5. Attacker calls `claimWithdrawRequest`: `_claimLossAdjustedWithdrawRequest` haircuts only the epoch-E+1 piece; `_claimFundedWithdrawRequest` then pays the epoch-E piece at par. The attacker receives strictly more than `basis * price`.
6. Other users claiming afterwards find the strategy's funded balance exhausted; `safeTransfer` in `_transferFundedClaim` reverts — their haircut-entitled recovery is permanently unclaimable (no reflow path exists; `pendingWithdraws` was zeroed).

Broken invariant: "one receipt one (loss-adjusted) payout" / fair loss socialization — the haircut funded pool assumes every pending receipt claims at `price`, but older-epoch receipts escape the multiplier, so the last claimants are left insolvent.

### Impact Explanation
Direct theft plus permanent freezing of unclaimed yield. If the attacker holds fraction `f` of `pendingBasis` in the older-epoch receipt and the haircut price is `p`, they extract an extra `(1 - p) * f * pendingBasis` underlying over their entitlement, and an equal value of other claimants' recovery is frozen forever (the reserve is never topped up). With a 50% haircut and 20% attacker share routed through the stale-epoch receipt, the attacker steals ~10% of the entire pending-receipt pool beyond their fair share.

### Likelihood Explanation
Requires only that (a) an unprivileged lender makes withdraw requests in two consecutive epochs without claiming the first — a normal, permitted usage pattern — and (b) the honest manager later stops an epoch with `_lossAmount > 0` (an explicit feature of `stopEpochWithDuration`). No privileged misbehavior, no oracle input, no timing race; deterministic once a loss-adjusted stop occurs while a multi-epoch receipt exists.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate/apply the recovery price to **all** basis funded under the same haircut — e.g., track a per-user "haircut basis" that accumulates across epochs, or have `collectWithdrawFunds` record which epochs' receipts were haircut and check/clear every epoch ≤ `epochNumber` for the user, not just `lastWithdrawRequest`. Simpler alternative: at `requestWithdraw`, revert if the user has *any* unfunded pending basis from an earlier epoch (not only when `lossRecoveryPriceByEpoch[lastWithdrawRequest] != 0`), forcing consolidation into a single receipt epoch so the haircut always covers the user's full basis.

### Proof of Concept
```solidity
// Fork test on IdleCreditVault.t.sol harness (cdoEpoch, strategy, idleCDO helpers).
function testOldEpochReceiptBypassesLossHaircut() external {
    uint256 amt = 10_000 * ONE_SCALE;
    address alice = makeAddr("alice");   // honest LP
    address eve   = makeAddr("eve");     // attacker LP

    // both deposit
    _depositAs(idleCDO, alice, amt, true);   // AA
    _depositAs(idleCDO, eve,   amt, true);

    // epoch 1 runs and stops normally
    _startEpochAndCheckPrices(0);
    _stopEpochNormal();                       // epochNumber -> 1, buffer opens

    // buffer of epoch 2: both request withdraw; eve does NOT claim
    vm.prank(alice); cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(eve);   cdoEpoch.requestWithdraw(evePart1, address(AAtranche));

    // eve requests AGAIN in same buffer -> lastWithdrawRequest moves to epoch 1
    // while withdrawsRequestsByEpoch[eve][0] keeps the first basis
    vm.prank(eve);   cdoEpoch.requestWithdraw(evePart2, address(AAtranche));

    // epoch 2 runs; borrower underfunds; manager stops with a loss
    _startEpochAndCheckPrices(0);
    _fundBorrowerPartial();
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, 0, 3 days, lossAmount); // price p < 1 stored

    uint256 pool = underlying.balanceOf(address(strategy));
    // pool == pendingBasis * p / 1e18

    // eve claims: epoch-1 basis haircut, epoch-0 basis paid AT PAR
    uint256 balPre = underlying.balanceOf(eve);
    vm.prank(eve);
    cdoEpoch.claimWithdrawRequest();
    uint256 eveGot = underlying.balanceOf(eve) - balPre;

    // eve's fair payout should be (basis0 + basis1) * p / 1e18
    assertGt(eveGot, (eveBasis0 + eveBasis1) * lossRecoveryPrice() / 1e18);

    // alice's claim now reverts: funded pool drained below her entitlement
    vm.prank(alice);
    vm.expectRevert();                        // safeTransfer fails on strategy
    cdoEpoch.claimWithdrawRequest();
}
```
