### Title
Unsanitized database error returned to unauthenticated attacker via `AuthenticateByToken` / `jsonAPIError` - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateByToken` only converts `FindUserByAPIToken` errors to `auth.ErrorAuthFailed` when the error is `sql.ErrNoRows` or `clsessions.ErrUserSessionExpired`; any other error (e.g. a wrapped driver/DB error) is returned verbatim. Because `Authenticate`'s method-chain loop only continues to the next auth method when the error `Is` `auth.ErrorAuthFailed`, any other error immediately aborts the chain and is serialized into the HTTP response body by `jsonAPIError` via `err.Error()`, exposing raw internal error text to an unauthenticated caller.

### Finding Description
`core/web/auth/auth.go` `AuthenticateByToken` (lines 92-99):
```go
user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
if err != nil {
    if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
        return auth.ErrorAuthFailed
    }
    return err
}
``` [1](#0-0) 

`FindUserByAPIToken` in `core/sessions/localauth/orm.go` performs a raw `GetContext` query and returns the driver error unmodified:
```go
func (o *orm) FindUserByAPIToken(ctx context.Context, apiToken string) (user sessions.User, err error) {
	sql := "SELECT * FROM users WHERE token_key = $1"
	err = o.ds.GetContext(ctx, &user, sql, apiToken)
	return
}
``` [2](#0-1) 

`Authenticate` in the same file loops through the auth methods, but only continues to the next method (e.g., falls through from token auth to session auth) if the error `Is(auth.ErrorAuthFailed)`; any other error breaks the loop and is passed straight to `jsonAPIError`:
```go
for _, method := range methods {
    err = method(c, store)
    if !errors.Is(err, auth.ErrorAuthFailed) {
        break
    }
}
if err != nil {
    c.Abort()
    jsonAPIError(c, http.StatusUnauthorized, err)
    return
}
``` [3](#0-2) 

`jsonAPIError` (`core/web/auth/helpers.go`) serializes `err.Error()` directly into the JSON response body sent to the client:
```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
``` [4](#0-3) 

All `/v2/*` routes are wrapped with `auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)` (and similarly for the `userOrEI` group), so any unauthenticated request carrying `X-API-KEY`/`X-API-SECRET` headers reaches this code path. [5](#0-4) 

Root cause: the error-classification allowlist in `AuthenticateByToken` is too narrow — it only recognizes two specific "not found"/"expired" sentinel errors and treats everything else (DB connectivity errors, driver errors, context errors, etc.) as a raw pass-through instead of sanitizing to a generic auth failure.

### Impact Explanation
If the underlying datastore query in `FindUserByAPIToken` fails with something other than "no rows" (e.g., a connection error, timeout, or malformed-query error), the exact `Error()` string of that error — which can include driver-specific details (e.g., libpq/pgx error text, occasionally connection parameters or query fragments depending on driver/version) — is returned in the JSON body of a 401 response to the *unauthenticated* caller. This is an information-disclosure issue (Chainlink bounty class: sensitive information disclosure / internal error leakage), not an authentication bypass — the attacker does not gain access, but may learn internal infrastructure details useful for further attacks.

### Likelihood Explanation
Exploitability requires the backend datastore call in `FindUserByAPIToken` to actually fail with a non-`sql.ErrNoRows` error while processing an attacker's request (e.g., transient DB outage, connection pool exhaustion, network partition between node and DB, or a malformed context/query error). This is not attacker-controllable in the general case — an attacker with only unprivileged network access cannot force a DB-level error on demand under normal operation, so likelihood is low but non-zero (any DB hiccup during token-auth turns into a leak to the requester, which could be an unauthenticated party since token/session are optional headers). Reproducible deterministically via a mock `Authenticator.FindUserByAPIToken` that returns a wrapped error, as suggested in the proof-of-concept.

### Recommendation
Sanitize all non-nil errors returned from `FindUserByAPIToken` (and similarly other credential lookup calls) before returning them from `AuthenticateByToken`: log the original error server-side and return `auth.ErrorAuthFailed` (or a new generic internal error, mapped to 500 without echoing `err.Error()`) for any error path, rather than special-casing only two sentinel values. Ensure `jsonAPIError`/`Authenticate` never emit raw upstream error strings for internal/infrastructure failures in unauthenticated code paths.

### Proof of Concept
Go unit test plan (extending `core/web/auth/auth_test.go`):
1. Define a mock `Authenticator` whose `FindUserByAPIToken` returns a wrapped error simulating a DB failure, e.g. `errors.Wrap(&pq.Error{Message: "connection to server at \"10.0.0.5\", port 5432 failed"}, "querying users")`.
2. Build a `gin.Engine` with a route protected by `auth.Authenticate(mockAuthr, auth.AuthenticateByToken)`.
3. Send an HTTP request with `X-API-KEY`/`X-API-SECRET` headers set (attacker does not need valid credentials, any non-empty value triggers the lookup).
4. Assert:
   - HTTP status is 401.
   - Response JSON body does NOT contain the string `"10.0.0.5"` or `"connection to server"` or any part of the wrapped error message (asserting equality only with a generic "Unauthorized"/invalid-token message).
   - Currently (pre-fix) this assertion fails because the mocked error text appears verbatim in the response body produced by `jsonAPIError`.
