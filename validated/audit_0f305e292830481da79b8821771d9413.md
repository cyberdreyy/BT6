### Title
Signer weight double-counted across acceptance and rejection buckets when a signer changes its vote — breaks the reject/accept threshold arithmetic - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` tallies each signer's weight into two independent buckets, `total_weight_approved` and `total_weight_rejected`, guarding duplicate additions with two *separate* keys (`gathered_signatures` for accept, `responded_signers` for both). Because a slot's weight is only ever added, never removed from the bucket it first landed in, a signer that rejects and later accepts (or vice versa) has its weight counted in **both** buckets simultaneously, breaking the invariant that `total_weight_approved + total_weight_rejected <= total_weight`.

### Finding Description
In `handle_block_response` (`stackerdb_listener.rs`):

- On `Accepted`, weight is added to `total_weight_approved` only if the slot is not already in `block.gathered_signatures`: [1](#0-0) 
- On `Rejected`, weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first response ever from that slot, whether accept or reject): [2](#0-1) 

The two guards are asymmetric:
- A signer that **rejects first, then accepts**: the reject handler adds weight to `total_weight_rejected` and marks `responded_signers`. The later accept handler only checks `gathered_signatures` (not yet present for this slot), so it *also* adds the same signer's weight to `total_weight_approved`, without ever decrementing `total_weight_rejected`.
- The reverse case (accept first, reject second) is correctly guarded: the reject path's `responded_signers.insert` will return `false` since `insert` already ran on accept, so no double count occurs.

This means the sum `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and stale rejection weight from a signer who has since switched to accept remains permanently and incorrectly counted toward the reject side. The consuming loop in `SignerCoordinator::get_block_status` decides outcomes purely from these two counters: [3](#0-2) 
So a stale, superseded rejection can combine with *new, distinct* rejecting signers to push `total_weight_rejected` past the blocking-minority threshold (`total_weight - weight_threshold`) even though the signer who originally contributed that stale rejection weight has since voted to accept — i.e., the true, current opinion of the signer set never actually reached the 30% blocking minority, yet the miner is told `SignersRejected`.

### Impact Explanation
This is a liveness wedge on the miner/coordinator side: the node can conclude a block is globally rejected (and abandon it, excluding txids, etc.) based on stale weight that no longer reflects a live rejection, even though a legitimate supermajority might still be converging toward acceptance. This matches the "High" impact category of a signer-adjacent component being wedged into not processing a valid block due to a stale/miscounted tally, analogous to the reported bug's core defect: a participant's "stake" (collateral/weight) gets stuck counted against them in the wrong bucket after their position has changed, and the arithmetic never reconciles it away.

### Likelihood Explanation
This requires no majority collusion — any single signer that changes its vote from reject to accept (a realistic scenario: e.g. transient validation failure resolved after a retried validation, or a signer initially rejecting due to a stale local view and then re-evaluating and accepting) triggers the double count. Combined with unrelated, distinct signers independently rejecting, the miner's rejection threshold can be tripped earlier/incorrectly. This is reachable purely through normal gossip traffic that a single miner-observing node will process; it needs no majority weight and no key compromise.

### Recommendation
Track a single "current vote" state per slot (e.g., an enum Accept/Reject with the associated weight) instead of two independently-guarded weight accumulators, so that switching a vote removes the stale weight from the old bucket before adding it to the new one; recompute `total_weight_approved`/`total_weight_rejected` by summing over current votes rather than incrementally with disjoint guards.

### Proof of Concept
1. Reward set with total_weight = 100, weight_threshold = 70 (blocking minority = 30).
2. Signer A (weight 15) sends `BlockResponse::Rejected` for hash H. `total_weight_rejected` = 15, `responded_signers` = {A}.
3. Signers B, C (combined weight 16) send `BlockResponse::Rejected` for H (unrelated, distinct rejecters). `total_weight_rejected` = 31 > blocking minority 30 — before A's later reversal, the coordinator already would flag rejection; to see the pure double-count effect, instead sequence:
   - A rejects (weight 15) → `total_weight_rejected` = 15.
   - A reconsiders and sends `BlockResponse::Accepted` for H → since slot A not in `gathered_signatures`, `total_weight_approved` becomes 15, but `total_weight_rejected` stays at 15 (never decremented).
   - Signers D, E (combined weight 16, distinct from A) send `Rejected` → `total_weight_rejected` = 15 (stale, from A) + 16 = 31 > blocking minority (30).
   - The coordinator's check `total_weight_rejected.saturating_add(weight_threshold) > total_weight` → `31 + 70 = 101 > 100` fires `NakamotoNodeError::SignersRejected`, even though the *live* rejecting weight (D+E = 16) is well under the 30-weight blocking minority and A has actually voted to accept.
