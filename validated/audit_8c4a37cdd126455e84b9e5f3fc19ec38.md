### Title
Loss-adjusted withdraw receipts keyed only to `lastWithdrawRequest` are re-paid at par once a newer request overwrites the marker - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The analog of the Junrar prefix-confusion bug is an epoch-key confusion in `IdleCreditVault.claimWithdrawRequest`. Like `LocalFolderExtractor` validating a sibling directory because it shares a path prefix, the vault validates which "class" a pending receipt belongs to using only the user's *latest* request epoch (`lastWithdrawRequest[_user]`) instead of checking each stored epoch. A receipt that belongs to a loss-adjusted "sibling" epoch shares the same `withdrawsRequests` aggregate and slips through to the funded, at-par claim path, so a haircutted receipt is paid in full.

### Finding Description
`claimWithdrawRequest` tries `_claimPostDefaultWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `_claimLossAdjustedWithdrawRequest`, then `_claimFundedWithdrawRequest`. The loss-adjusted path derives the claim epoch solely from `lastWithdrawRequest[_user]` and looks up `lossRecoveryPriceByEpoch[lossEpoch]` [1](#0-0) . The funded path then pays the entire aggregate `withdrawsRequests[_user]` at par, clearing everything [2](#0-1) .

`collectWithdrawFunds` stores the haircut price under the *current* `epochNumber` when the borrower under-funds pending receipts in `stopEpochWithDuration`, and zeroes `pendingWithdraws` [3](#0-2) . `requestWithdraw` then records each new request per-epoch and unconditionally overwrites `lastWithdrawRequest[_user]` [4](#0-3) .

Sequence:
1. User calls `requestWithdraw` in epoch N (records `withdrawsRequestsByEpoch[user][N]`, `lastWithdrawRequest[user] = N`).
2. Epoch N ends via `stopEpochWithDuration(_lossAmount)`; `collectWithdrawFunds` sets `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL` and `pendingWithdraws = 0`.
3. In epoch N+1 the user calls `requestWithdraw` again (any amount). `lastWithdrawRequest[user] = N+1`; `withdrawsRequestsByEpoch[user][N]` remains populated.
4. After epoch N+1 ends, `claimWithdrawRequest` runs. `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = N+1`; `lossRecoveryPriceByEpoch[N+1] == 0` (that epoch was fully funded), so it returns 0 without clearing `withdrawsRequestsByEpoch[user][N]` [5](#0-4) . The guard in `_claimFundedWithdrawRequest` (`epochNumber <= lastWithdrawRequest`) now passes, so `_claimFundedWithdrawRequest` pays `withdrawsRequests[user]`, which still includes the entire epoch-N receipt, at par.

The per-epoch clearing helper `_clearWithdrawClaimForEpoch` is only invoked for the single `lossEpoch`/`defaultEpoch` looked up, so it never gets a chance to haircut the older epoch-N bucket [6](#0-5) . The same confusion applies to `defaultRecoveryEpoch` claims: a defaulted-epoch receipt left under `withdrawsRequestsByEpoch[user][defaultEpoch]` survives if `lastWithdrawRequest` points elsewhere... actually the default path uses `defaultRecoveryEpoch` correctly, so the concrete exploit is specifically the loss-adjusted epoch keyed off `lastWithdrawRequest`.

### Impact Explanation
The invariant "one receipt, one haircut-adjusted payout" is broken. The borrower only funded `pendingBasis * lossRecoveryPrice / RECOVERY_FULL` for the epoch-N receipt; paying it at par transfers more underlying than was collected. The excess is pulled from the strategy's underlying balance, which is backed by other users' funded claims and the default-recovery/active reserve — i.e., direct theft from other claimants and solvency damage proportional to the loss haircut times the attacker's epoch-N receipt size. An attacker controlling any KYC'd lender wallet can do this with two `requestWithdraw` calls around a `stopEpochWithDuration`; no privileged role is needed.

### Likelihood Explanation
`stopEpochWithDuration` with a nonzero `_lossAmount` is a supported manager flow (partial borrower repayment). The attacker controls both transactions: request in the loss epoch (or already have a pending request there), then make a dust-sized new request in the next epoch to overwrite the marker, wait one epoch boundary, and claim. Because `requestWithdraw` is permissionless for allowed wallets and `lastWithdrawRequest` is overwritten unconditionally, the only precondition is that a loss epoch occurs while the attacker has a pending receipt — or the attacker can even create the pending receipt during the buffer before the lossy stop.

### Recommendation
Track loss-adjusted claims per request epoch rather than via `lastWithdrawRequest`. Options: in `_claimLossAdjustedWithdrawRequest`, iterate or store the user's request epochs and check `lossRecoveryPriceByEpoch` for each `withdrawsRequestsByEpoch[user][e]` entry; or maintain a per-user mapping of epochs with pending loss-adjusted receipts (set at `collectWithdrawFunds` time via a recorded epoch list, or a per-user `lossEpochs` list appended in `requestWithdraw` when the epoch later gets a recovery price). At minimum, when `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]`, ensure any receipt whose `lastWithdrawRequest` is later overwritten still resolves to the loss epoch — e.g., store per-user `lossClaimEpoch` at the time the price is set, or refuse new `requestWithdraw`s while a user has an unclaimed loss-adjusted receipt.

### Proof of Concept
Foundry fork PoC sketch (based on `test/foundry/IdleCreditVault.t.sol` / `IdleCDOEpochQueue.t.sol` helpers):

```solidity
function testLossEpochReceiptPaidAtParAfterNewRequest() external {
    uint256 trancheAmount = 100e18; // strategy tokens 1:1 with underlying
    _depositWithUser(attacker, 1000e6);

    // Epoch N: attacker requests withdraw
    _requestWithdrawWithUser(attacker, trancheAmount);
    // Borrower under-funds: stopEpochWithDuration with a loss
    uint256 lossAmount = _fundLossyStop(); // e.g. 50% loss on pending basis
    // lossRecoveryPriceByEpoch[N] now < RECOVERY_FULL

    // Epoch N+1 buffer: attacker requests a dust withdraw, overwriting marker
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(attacker, 1);

    // Epoch N+1 stops normally, fully funded
    _stopCurrentEpochWithApr(10e18);

    // Attacker claims: loss-adjusted path keyed on lastWithdrawRequest = N+1 misses epoch N
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(address(cdoEpoch));
    strategy.claimWithdrawRequest(attacker);
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    // Paid = (epoch N receipt + epoch N+1 dust) at par
    // Expected under correct haircut: epochN * lossRecoveryPrice / RECOVERY_FULL + dust
    assertGt(paid, trancheAmount * strategy.lossRecoveryPriceByEpoch(lossEpoch) / RECOVERY_FULL);
}
```

The assertion that `paid` equals `withdrawsRequests[attacker]` at par (rather than the haircutted epoch-N amount plus funded dust) demonstrates the overpayment; the excess underlying leaves the strategy under-collateralized for remaining claimants.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
