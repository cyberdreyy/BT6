### Title
Concurrent `Bucket::grow` calls under `RwLock::read()` can double-increment `Reallocated::active_reallocations`, panicking the validator - ([File: bucket_map/src/bucket.rs])

### Summary
`BucketApi::grow` intentionally acquires only a **read** lock on the bucket (`bucket_map/src/bucket_api.rs:118-124`), while all mutating write-lock entry points (`try_write`, `insert`, `update`, `batch_insert_non_duplicates`) call `handle_delayed_grows()` first thing under the **write** lock (`bucket_map/src/bucket_api.rs:103-111`). Because `RwLock::read()` permits multiple simultaneous readers, two threads that each independently hit a `BucketMapError` (one `IndexNoSpace`, one `DataNoSpace`) on the *same* underlying `Bucket` can both call `Bucket::grow` → `grow_index`/`grow_data` → `Reallocated::add_reallocation` concurrently, without an intervening write-lock cycle to apply/clear the pending reallocation.

### Finding Description
`Reallocated::add_reallocation` asserts that `active_reallocations` transitions from `0` to `1`: [1](#0-0) 

Both `grow_index` and `grow_data` call `self.reallocated.add_reallocation()` while only holding `&self` (an immutable reference obtained from a `RwLockReadGuard`), and the only place that clears/consumes the flag (`get_reallocated`, via `handle_delayed_grows`) is reached exclusively through the **write**-lock path: [2](#0-1) [3](#0-2) [4](#0-3) 

`BucketApi::grow` deliberately takes a read lock so that concurrent readers/writers on other keys aren't blocked while a resize is prepared: [5](#0-4) 

`RwLock::read()` in Rust's std allows multiple concurrent readers. If two different threads (e.g. two accounts-index flush/write-through operations for two different pubkeys that hash into the same `Bucket`) each get a `BucketMapError` from `try_write` (one thread encountering `IndexNoSpace`, the other `DataNoSpace`) and then call `BucketApi::grow(err)` concurrently, both acquire read guards on the same `RwLock<Option<Bucket<T>>>` at the same time. Both then call `Bucket::grow` → either `grow_index` or `grow_data` → `Reallocated::add_reallocation`. If thread A's `fetch_add` runs first (0→1) and thread B's `fetch_add` runs before any write-lock holder calls `handle_delayed_grows` (which requires acquiring the exclusive write lock, blocked as long as any reader holds it, but not blocked as against another reader), thread B observes `1` and the `assert_eq!(0, 1, ...)` panics, killing the validator process.

The retry loop in `write_to_disk` (`accounts-db/src/accounts_index/in_mem_accounts_index.rs:435-452`) demonstrates the intended real-world call pattern: `try_write` (write lock, applies any pending grow first) then `disk.grow(err)` (read lock, only sets pending state) in a loop. This pattern is safe for a single thread in isolation, but nothing prevents two different threads executing this same loop concurrently for two different pubkeys that land in the same `Bucket`, from calling `grow()` at effectively the same moment.

This is reachable purely from normal write-heavy account activity: an attacker who submits many transactions creating/writing new accounts can drive both index-capacity exhaustion (many distinct new pubkeys hashing into the same bucket) and data-bucket capacity exhaustion (an existing pubkey's slot list growing past the current data-bucket size) concurrently across the runtime's parallel transaction-processing/flush threads, without needing any special privileges — this is achievable solely via on-chain writes.

### Impact Explanation
A successful race results in an `assert_eq!` panic (`Reallocated::add_reallocation`), which crashes the validator process (`panic = "abort"` in most Agave build profiles, or otherwise unwinds through unrelated locking state leaving `Bucket` unusable). This matches the "validator process crash from writing on-chain data" bounty category — availability impact via a client-triggerable, non-consensus-privileged panic path.

### Likelihood Explanation
This requires: (1) many distinct pubkeys hashing into the same accounts-index bucket to exhaust index capacity, (2) an existing pubkey's slot list simultaneously growing enough to exhaust data-bucket capacity, and (3) the two threads' independent `try_write`→error→`grow()` sequences interleaving at the exact moment both call `add_reallocation` before any write-lock cycle intervenes. This is a genuine race condition — feasible under load (many parallel transactions touching the same bucket) but timing-dependent and not deterministically reproducible from a single serialized instruction stream; it depends on the validator's internal thread scheduling for the accounts-index write-through/flush paths. I could not fully confirm from the available code snippets whether the normal transaction execution/flush pipeline dispatches concurrent `try_write`/`grow` calls for different pubkeys in the same bucket in a way that reliably produces the tight race window (this would require examining `accounts_index.rs`'s parallel upsert/flush call sites, `bucket_map_holder.rs`, and the scheduler's parallelism model, which I was not able to fully trace given the remaining tool budget).

### Recommendation
Make `active_reallocations` tolerate/queue multiple pending reallocations instead of asserting exactly one, or use a `compare_exchange`-based check inside `add_reallocation` that treats a "1" observed value as "already pending — queue this reallocation instead of overwriting/panicking" (e.g., store both an `index` and a `data` reallocation in `ReallocatedItems` — which the struct already supports — and change `add_reallocation` to increment without asserting, relying on `get_reallocated`'s compare_exchange only to decide whether *any* reallocation is pending, or move to a proper counting/queueing scheme so both a pending index-grow and a pending data-grow can coexist safely). At minimum, guard `grow_index`/`grow_data` with the bucket's own mutex around the "check-then-set" of `active_reallocations` so concurrent read-lock holders can't race there.

```rust
fn test_concurrent_grow_index_and_grow_data_panics() {
    use std::{sync::Arc, thread};

    // Construct a Bucket<u64> via BucketApi so we can hold concurrent read locks.
    let bucket_map = /* construct BucketMap<u64> with small max_search / small capacities */;
    let api = bucket_map.get_bucket(&Pubkey::new_unique()).clone(); // Arc<BucketApi<u64>>

    // Drive the bucket into a state where both errors are producible:
    // - populate enough distinct keys to be one insert away from IndexNoSpace
    // - grow one key's slot list to be one push away from DataNoSpace
    // (setup omitted for brevity — use existing test helpers in this file)

    let api_a = Arc::clone(&api);
    let api_b = Arc::clone(&api);

    let barrier = Arc::new(std::sync::Barrier::new(2));
    let (b1, b2) = (Arc::clone(&barrier), Arc::clone(&barrier));

    let t1 = thread::spawn(move || {
        b1.wait();
        // triggers IndexNoSpace then calls api_a.grow(err) under a read lock
        let err = BucketMapError::IndexNoSpace(/* current index capacity */);
        api_a.grow(err);
    });
    let t2 = thread::spawn(move || {
        b2.wait();
        // triggers DataNoSpace then calls api_b.grow(err) under a read lock
        let err = BucketMapError::DataNoSpace((0, /* current data cap pow2 */));
        api_b.grow(err);
    });

    // Expected (buggy) behavior: one of these threads panics with
    // "Only 1 reallocation can occur at a time" instead of both succeeding
    // or one being safely queued.
    let r1 = t1.join();
    let r2 = t2.join();
    assert!(r1.is_ok() && r2.is_ok(), "concurrent grow() calls panicked: {:?} {:?}", r1, r2);
}
```
Expected outcome on the vulnerable code: with sufficient repetitions/timing (or by directly calling `bucket.reallocated.add_reallocation()` twice from two threads without an intervening `get_reallocated()`), the `assert_eq!(0, ..., "Only 1 reallocation can occur at a time")` in `Reallocated::add_reallocation` fires, panicking the thread and (in the real validator, given panic=abort in release profiles for account/index paths) crashing the process. A fixed implementation should allow both grows to be recorded and safely applied without panicking.

```rust
    pub fn grow_index(&self, mut current_capacity: u64) {
        if self.index.contents.capacity() == current_capacity {
            // make sure to grow to at least % more than the anticipated size
            // The indexing algorithm expects to require some over-allocation.
            let anticipated_size = self.anticipated_size * 140 / 100;
            let mut m = Measure::start("grow_index");
            //debug!("GROW_INDEX: {}", current_capacity_pow2);
            let mut count = 0;
            loop {
                count += 1;
                // grow relative to the current capacity
                let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);
                let (mut index, file_name) = BucketStorage::new_with_capacity(
                    Arc::clone(&self.drives),
                    1,
                    std::mem::size_of::<IndexEntry<T>>() as u64,
                    Capacity::Actual(new_capacity),
                    self.index.max_search,
                    Arc::clone(&self.stats.index),
                    Arc::clone(&self.index.count),
                );
                // index may have allocated something larger than we asked for,
                // so, in case we fail to reindex into this larger size, grow from this size next iteration.
                current_capacity = index.capacity();
                let mut valid = true;
                for ix in 0..self.index.capacity() {
                    if !self.index.is_free(ix) {
                        let elem: &IndexEntry<T> = self.index.get(ix);
                        let new_ix =
                            Self::bucket_create_key(&mut index, &elem.key, self.random, true);
                        if new_ix.is_err() {
                            valid = false;
                            break;
                        }
                        let new_ix = new_ix.unwrap();
                        let new_elem: &mut IndexEntry<T> = index.get_mut(new_ix);
                        *new_elem = *elem;
                        index.copying_entry(new_ix, &self.index, ix);
                    }
                }
                if valid {
                    self.stats.index.update_max_size(index.capacity());
                    let mut items = self.reallocated.items.lock().unwrap();
                    items.index = Some(index);
                    self.reallocated.add_reallocation();
                    self.restartable_bucket.set_file(file_name, self.random);
                    break;
                }
            }
            m.stop();
            if count > 1 {
                self.stats
                    .index
                    .failed_resizes
                    .fetch_add(count - 1, Ordering::Relaxed);
            }
            self.stats.index.resizes.fetch_add(1, Ordering::Relaxed);
            self.stats
                .index
                .resize_us
                .fetch_add(m.as_us(), Ordering::Relaxed);
        }
    }
```

```rust
    /// grow a data bucket
    /// The application of the new bucket is deferred until the next write lock.
    pub fn grow_data(&self, data_index: u64, current_capacity_pow2: u8) {
        let (new_bucket, _file_name) = BucketStorage::new_resized(
            &self.drives,
            self.index.max_search,
            self.data.get(data_index as usize),
            Capacity::Pow2(std::cmp::max(
                current_capacity_pow2 + 1,
                DEFAULT_CAPACITY_POW2,
            )),
            1 << data_index,
            Self::elem_size(),
            &self.stats.data,
        );
        self.reallocated.add_reallocation();
        let mut items = self.reallocated.items.lock().unwrap();
        items.data = Some((data_index, new_bucket));
    }

    fn bucket_index_ix(key: &Pubkey, random: u64) -> u64 {
        // the locally generated random will make it hard for an attacker
        // to deterministically cause all the pubkeys to land in the same
        // location in any bucket on all validators
        let hasher_builder = ahash::RandomState::with_seeds(random, random, random, random);
        hasher_builder.hash_one(key)
    }

    /// grow the appropriate piece. Note this takes an immutable ref.
    /// The actual grow is set into self.reallocated and applied later on a write lock
    pub(crate) fn grow(&self, err: BucketMapError) {
        match err {
            BucketMapError::DataNoSpace((data_index, current_capacity_pow2)) => {
                //debug!("GROWING SPACE {:?}", (data_index, current_capacity_pow2));
                self.grow_data(data_index, current_capacity_pow2);
            }
            BucketMapError::IndexNoSpace(current_capacity) => {
                //debug!("GROWING INDEX {}", sz);
                self.grow_index(current_capacity);
            }
        }
    }
```

```rust
    /// if a bucket was resized previously with a read lock, then apply that resize now
    pub fn handle_delayed_grows(&mut self) {
        if self.reallocated.get_reallocated() {
            // swap out the bucket that was resized previously with a read lock
            let mut items = std::mem::take(&mut *self.reallocated.items.lock().unwrap());

            if let Some(bucket) = items.index.take() {
                self.apply_grow_index(bucket);
            } else {
                // data bucket
                let (i, new_bucket) = items.data.take().unwrap();
                self.apply_grow_data(i as usize, new_bucket);
            }
        }
    }
```
