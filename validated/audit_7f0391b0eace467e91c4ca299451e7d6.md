### Title
`check_parent_tenure_choice` treats an un-timestamped local approval as an automatically "poorly-timed" tenure, letting a miner reorg an already-signed block without the intended timing guarantee - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
The reorg-permission logic in `SortitionData::check_parent_tenure_choice` is supposed to allow a one-block tenure to be reorged only if that tenure's *first* block was proposed "poorly timed" — i.e., close enough to the next sortition (`first_proposal_burn_block_timing`) that the incoming miner had no fair chance to build on it. This mirrors the report's underlying bug class: a decision meant to depend on *real elapsed time* is instead gameable through a local, per-signer timestamp gap, letting an adversarial miner get treated as if the timing condition were met when it was not.

### Finding Description
In `check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs`, function starting line 170), for each reorged tenure the code computes: [1](#0-0) 

```
let checked_proposal_timing = if let Some(sortition_state_received_time) = sortition_state_received_time {
    let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
        sortition_state_received_time.saturating_sub(approved_at)
    } else {
        info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
        0
    };
    if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
        // ... permit reorg (push to superseded_tenures); continue;
    }
    true
} else {
    false
};
```

`local_block_info` here comes from `signer_db.get_first_approved_block_in_tenure(&tenure.consensus_hash)` [2](#0-1) , which is only reached once we already know this signer holds *some* local record for the reorged tenure's first block (otherwise the function has already returned `Ok(false)` on the preceding "no local knowledge" branch). But holding a `BlockInfo` record does not guarantee `approved_time` is populated — per `docs/signer-flows.md`, `approved_time` is stamped only "at pre-commit or local acceptance," and the code path unconditionally substitutes `0` whenever it's `None`, rather than treating a missing timestamp as "unknown, deny the reorg" (the safe default used one branch above for a fully missing record).

Substituting `0` means `proposal_to_sortition` is always the minimum possible value, so `Duration::from_secs(0) < first_proposal_burn_block_timing` is true unless the operator has configured `first_proposal_burn_block_timing_secs = 0`. In other words: **any signer whose local `BlockInfo` for the reorged tenure's first block never had `approved_time` set will unconditionally treat the reorg as "poorly timed" and permit it**, regardless of how much real wall-clock time has actually elapsed since that block was first proposed and regardless of the actual delay before the next sortition.

This breaks the equality the check is meant to enforce: "reorg allowed ⟺ tenure's first block was proposed close to the sortition boundary." A miner can exploit this on any signer subset whose local DB lacks a timestamp for that block (e.g., a signer that recovered/rebuilt its DB, replayed events, or otherwise obtained the `BlockInfo` row through a path that didn't go through `mark_pre_committed`/`mark_locally_accepted`), causing that signer to sign a tenure-change block that reorgs out a tenure which had already produced a globally-accepted block long before the new sortition — a non-canonical/conflicting-block signature from that signer's perspective of consensus history.

### Impact Explanation
This falls into the Critical bucket: a signer can be induced to sign a conflicting/non-canonical tenure-change block, replacing an already globally-accepted tenure's block, purely because of a missing local timestamp rather than the real timing condition the protocol relies on for safety (`check_parent_tenure_choice` is the sole gate preventing arbitrary reorgs of established tenures — see `docs/signer-flows.md` section on burn blocks/miner-view state machine). If enough signers hit this un-timestamped code path (e.g., because their signer restarted and reloaded state without direct pre-commit/acceptance bookkeeping), the aggregate signature can cross threshold for an improperly-timed reorg, which is exactly the equivocation/liveness property `first_proposal_burn_block_timing` exists to prevent, as documented in the sample config's explicit warning: "Setting this too LOW allows dangerous reorgs of established tenures" (`sample/conf/signer/mainnet-signer-conf.toml`). [3](#0-2) 

### Likelihood Explanation
Reachable by a single sortition-winning miner (one slot) plus normal gossip/relay timing — no majority signer collusion or key compromise is required. The trigger condition (a signer's local `BlockInfo` record existing but `approved_time` being `None`) depends on internal signer-db state that I could not fully verify from the available index (I was not able to trace every code path that inserts/loads `BlockInfo` rows to confirm whether `approved_time: None` combined with a "first approved block" query result is actually reachable in practice, e.g. via crash-recovery, DB migration, or synthesized records outside the normal `mark_pre_committed`/`mark_locally_accepted` flow). This is the primary uncertainty in this finding — the exploit's likelihood hinges on how `get_first_approved_block_in_tenure` and `approved_time` are populated in cases outside the "happy path," which I could not fully confirm from the index. Because I could not read the complete `signerdb.rs` implementation of these functions in this session, I am treating this as plausible-but-unverified rather than a confirmed proof of concept.

### Recommendation
Change the missing-`approved_time` branch to treat the timing as unknown/unsafe (deny the reorg, mirroring the fully-missing-record branch), rather than substituting `0`, e.g.:
```
let Some(approved_at) = local_block_info.approved_time else {
    warn!("No approval timestamp recorded for the reorged tenure's first block; denying reorg to be safe.");
    return Ok(false); // or: do not add to superseded_tenures, fall through to the deny path
};
```
Additionally, audit all code paths that produce a `BlockInfo` returned by `get_first_approved_block_in_tenure` to guarantee `approved_time` is always set whenever the corresponding state (`PreCommitted`/`LocallyAccepted`/global states) is set, closing off any path that can yield the record without the timestamp.

### Proof of Concept
Not verified end-to-end due to index limits on `stacks-signer/src/signerdb.rs`'s full write paths for `approved_time`. The code-level proof is the branch shown above in `check_parent_tenure_choice` (lines 247–278 of `stacks-signer/src/chainstate/mod.rs`): supplying any `BlockInfo` with `approved_time == None` to this function causes `proposal_to_sortition` to be computed as `0`, which is always less than any positive `first_proposal_burn_block_timing`, unconditionally permitting the reorg. Confirming a concrete trigger for `approved_time == None` on an otherwise-returned `get_first_approved_block_in_tenure` result requires reading the full `signerdb.rs` insertion/query logic, which a Devin session with full repository access could verify and, if reachable, demonstrate with a unit test analogous to `stacks-signer/src/chainstate/tests/v1.rs::check_proposal_reorg_timing_bad`/`_ok`.

```text
# Reorg protection window. Measures the time between when the first block
# of a tenure was signed and when the next burn block (sortition) arrived.
#
# If a new miner tries to reorg a tenure that already produced blocks:
#   - If (burn_block_received - first_block_signed) < this value:
#     Reorg is ALLOWED (the tenure was "poorly timed" and the incoming
#     miner did not have sufficient time to RBF an outdated commit)
#   - If (burn_block_received - first_block_signed) >= this value:
#     Reorg is DENIED (the tenure was established long enough for the
#     incoming miner to RBF any outdated commit)
#
# WARNING: Setting this too LOW allows dangerous reorgs of established
# tenures. Setting it too HIGH blocks legitimate miner handoffs when
# the previous tenure's first block arrived shortly before the sortition.
#
# Default: 60
# Units: seconds
# first_proposal_burn_block_timing_secs = 60
```
