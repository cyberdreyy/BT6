### Title
Premature division in `_calcInterestWithApr` truncates sub-percent APR and systematically misprices withdraw receipts and epoch interest - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`_calcInterestWithApr` divides `_apr` by 100 *before* multiplying by `_amount` and `epochDuration`. Because the epoch APR is a scaled integer that carries fractional-percent precision (the code comments themselves use an 11.67% APR example), truncating `_apr / 100` first destroys the fractional part of the rate. Every downstream consumer — `_calcInterest`, `_calcInterestWithdrawRequest`, `requestWithdraw` receipt sizing, `expectedEpochInterest` and the `interestForOverUnderPerformance` AA/BB rebalancing term — therefore uses a rate that is floored to whole-percent units, permanently misallocating yield between tranches and shortchanging withdrawers. This mirrors the external report's bug class: an order-of-operations error where a normalization/adjustment is applied before the scaling operation it must follow, producing a systematically wrong result with direct fund impact.

### Finding Description
In `IdleCDOEpochVariant.sol`, interest is computed as:

```solidity
function _calcInterestWithApr(uint256 _amount, uint256 _apr) internal view returns (uint256) {
    return _amount * (_apr / 100) * epochDuration / (365 days * ONE_TRANCHE_TOKEN);
}
``` [1](#0-0) 

The comments for `_calcInterestWithdrawRequest` show the intended APR granularity: a 10% target over 30 days with a 5-day buffer is set as `10% * 35/30 = 11.67%`, i.e. APR is a scaled integer with two decimals of percent precision (1167 = 11.67%). Evaluating `_apr / 100` before multiplication collapses 1167 to 11, silently discarding 0.67% of APR — roughly 5.7% of the intended interest — on every call. [2](#0-1) 

The wrong value propagates through three paths:

1. **Withdraw receipts.** `requestWithdraw` computes `(interest, diff) = _calcInterestWithdrawRequest(_underlyings, _tranche)`, then `_underlyings = principal + interest - totalFees` and registers that amount with `creditVault.requestWithdraw(_underlyings, msg.sender, principal)`. The receipt is fixed at request time, so the truncated interest is permanently locked in — the user can never recover the shortfall. [3](#0-2) [4](#0-3) 

2. **Tranche split.** `_diff = interestWithoutSplitRatio - _interest` is added to `interestForOverUnderPerformance`, which adjusts `expectedEpochInterest` at `startEpoch`. Both terms of the subtraction are truncated the same way, so the AA-over/BB-underperformance rebalancing transferred between tranche NAVs is computed from a floored rate, shifting value between AA and BB holders even when the withdrawal itself is legitimate.

3. **Epoch accounting.** `expectedEpochInterest`/`totInterest` for the whole pool (`_calcInterest(_managedContractValue())`) is under-computed, so the projected yield the epoch promises is inconsistent with the APR the manager actually configured.

No guard catches this: it is not a donation (skim only forwards stray balance), not gated by epoch phase, KYC, `onlyIdleCDO`, or reserve checks — it is plain arithmetic executed on every withdrawal request and epoch interest computation.

### Impact Explanation
Direct, permanent loss of yield. For the documented 11.67% configuration, every withdraw request forfeits ~0.67/11.67 ≈ 5.7% of its owed interest, and the AA/BB rebalancing term is miscalculated on the same magnitude. Worse, any configured APR below 1% (`_apr < 100`) floors `_apr / 100` to 0, so withdrawers receive *zero* interest and `_diff` attribution between tranches is entirely wrong while the vault's own epoch bookkeeping still assumes yield exists. Because receipts are fixed at request time and tranche prices are updated through `lastNAVAA/lastNAVBB` from these values, the mispricing is baked into NAV — this is theft/permanent freezing of unclaimed yield, not a recoverable rounding artifact.

### Likelihood Explanation
High. The bug triggers on the ordinary, unprivileged path: any tranche holder calling `requestWithdraw` during the buffer/withdrawal window while the epoch APR has a fractional-percent component (which the protocol's own buffer-scaling mechanism *guarantees* whenever `bufferPeriod` does not evenly divide `epochDuration`). No privileged cooperation, oracle manipulation, or donation setup is required; the loss occurs on every such request in every epoch.

### Recommendation
Multiply before dividing so the scaled APR keeps its precision:

```solidity
function _calcInterestWithApr(uint256 _amount, uint256 _apr) internal view returns (uint256) {
    return _amount * _apr * epochDuration / (100 * 365 days * ONE_TRANCHE_TOKEN);
}
```

The same reordering discipline applies to the `* _duration / (_duration + _buffer)` rescaling in `_calcInterestWithdrawRequest` (already ordered correctly there — multiply-then-divide — but worth covering with a regression test asserting interest matches `apr * duration` exactly for fractional APRs such as 1167).

### Proof of Concept
Foundry fork test against the epoch-variant CDO (e.g., `IdleCDOEpochVariant` harness in `test/foundry/`): configure `epochDuration = 30 days`, `bufferPeriod = 5 days`, and have the manager stop the epoch with an effective APR of 11.67% (`_apr = 1167`). Then:

```solidity
// Attacker/victim: ordinary AA tranche holder, unprivileged
uint256 expected = principal * 1167 * epochDuration / (100 * 365 days * ONE_TRANCHE_TOKEN);
uint256 actual   = principal * (1167 / 100) * epochDuration / (365 days * ONE_TRANCHE_TOKEN);
assertLt(actual, expected);            // ~5.7% of interest lost
cdo.requestWithdraw(amount, AATranche); // receipt minted at truncated interest
// claim after next epoch settles pays exactly the truncated amount — shortfall is permanent
```

Additionally, setting `_apr < 100` (sub-1% epoch APR) yields `actual == 0`, demonstrating a complete loss of withdraw-request interest and a fully wrong `interestForOverUnderPerformance` transfer between AA and BB NAV.

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }
