Confirmed: `rescueFunds` and `cancel` never touch `immutables.parameters` — they don't call any `ImmutablesLib` fee-decoding function — so both remain callable by the taker even when `withdraw`/`publicWithdraw` are bricked.

### Title
Malformed dst `parameters` blob permanently bricks both private and public withdraw, freezing maker's payout - (File: `contracts/EscrowDst.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
`createDstEscrow` takes the entire `IBaseEscrow.Immutables` struct — including the `parameters` bytes field — directly from `msg.sender` with zero validation of its length or content. If that field is shorter than the 128 bytes needed to hold `(protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)`, `EscrowDst._withdraw` unconditionally reverts on fee decoding, for both the private `withdraw` and the public `publicWithdraw` path, since they share the same internal implementation.

### Finding Description
`createDstEscrow` deploys the destination escrow using caller-supplied immutables verbatim, with the `parameters` bytes fully attacker-controlled and unchecked: [1](#0-0) 

`EscrowDst._withdraw` unconditionally calls `integratorFeeAmountCd()` and `protocolFeeAmountCd()` before any transfer logic, and both `withdraw` (taker-only) and `publicWithdraw` (access-token holder) funnel into this same function: [2](#0-1) 

`ImmutablesLib.integratorFeeAmountCd` reverts with `IndexOutOfRange()` if `parameters.length < 0x40` (64 bytes), and `protocolFeeAmountCd` reverts if `< 0x20` (32 bytes): [3](#0-2) 

Since `parameters` is included in the immutables hash used both as the CREATE2 salt and for `onlyValidImmutables` validation, any caller (public or private) attempting to withdraw must submit the exact same malformed `parameters` to pass validation — which then reverts on fee decoding. This bricks `withdraw` and `publicWithdraw` identically; there is no code path in either function that bypasses the fee decode.

By contrast, `cancel()` and `rescueFunds()` never touch `parameters` at all: [4](#0-3) [5](#0-4) 

so the taker who deployed the corrupted escrow can still reclaim the deposited destination amount plus safety deposit via `cancel()` once the `DstCancellation` timelock elapses (or via `rescueFunds` after the rescue delay), while the maker's expected payout via `withdraw`/`publicWithdraw` is permanently unreachable.

### Impact Explanation
Anyone who calls `createDstEscrow` (there is no whitelist/role check inside this function itself — msg.sender simply funds the deposit and becomes `taker`) can deliberately set a truncated `parameters` blob (e.g., 31 bytes). This makes fee decoding revert unconditionally in `_withdraw`, so neither the taker's private withdrawal nor the public withdrawal (available to any access-token holder after `DstPublicWithdrawal`) can ever succeed for that specific escrow instance — even with a correct, known secret. The maker's payout is frozen for the entire withdrawal window and is only released back to the taker via `cancel()`/`rescueFunds()`, never to the maker. This matches "temporary freezing of funds during the live swap lifecycle" (High) under the bounty's Required Impacts, since the maker's expected destination-chain proceeds cannot be claimed through the intended withdraw paths and only the depositor (taker) can eventually recover the escrowed value.

### Likelihood Explanation
High. This requires no privileged role, no owner/governance action, and no third-party trust assumption — only calling the public, permissionless `createDstEscrow` with a crafted `parameters` byte length. It is fully reproducible and deterministic once the escrow is funded.

### Recommendation
Validate `dstImmutables.parameters` length (and ideally structure) inside `createDstEscrow` before deployment — e.g., require `parameters.length == 0` or `parameters.length == 128` (4 × 32 bytes) matching the expected fee-metadata encoding — so malformed escrows can never be created. Alternatively, make `_withdraw` tolerant of missing/short parameters by treating undersized `parameters` as "no fees" rather than reverting.

### Proof of Concept
1. Attacker (as taker) calls `escrowFactory.createDstEscrow{value: safetyDeposit (+amount if native)}(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.parameters` set to a 31-byte blob (e.g., `bytes(hex"00...00")` of length 31) and destination token set to native (`address(0)`).
2. Escrow deploys successfully — creation performs no length check on `parameters` [1](#0-0) .
3. Warp past `DstWithdrawal`; call `dstClone.withdraw(secret, dstImmutables)` with the correct secret — reverts with `IndexOutOfRange()` from `integratorFeeAmountCd()` [6](#0-5) .
4. Warp past `DstPublicWithdrawal`; call `dstClone.publicWithdraw(secret, dstImmutables)` from any access-token holder — reverts identically [7](#0-6) .
5. Warp past `DstCancellation`; only the original taker can call `cancel(dstImmutables)` to reclaim the deposited amount and safety deposit, since `cancel` never decodes `parameters` [4](#0-3) , confirming the maker's payout was frozen throughout and never delivered.

    function protocolFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;
        if (parameters.length < 0x20) revert IndexOutOfRange();
        assembly ("memory-safe") {
            ret := calldataload(parameters.offset)
        }
    }

    /**
     * @notice Returns the integrator fee amount from the immutables (calldata version).
     * @param immutables The immutables to extract the fee from.
     * @return ret The integrator fee amount.

    function integratorFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;
