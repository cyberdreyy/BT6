### Title
`Bank::capitalization` is an incrementally-tracked cache that can silently diverge from the true sum of account lamports, with reconciliation only possible via an expensive full index scan - (File: `runtime/src/bank.rs`, `runtime/src/bank/fee_distribution.rs`)

### Summary
The external report describes `OmoVault.sol`'s `totalAssets()` as an accounting value that is supposed to mirror the real location/sum of managed funds, but which can be pushed out of sync with reality by paths that move funds without updating the tracked total, with no cheap way to reconcile except a full, expensive recomputation. Agave's `Bank::capitalization` field is the analogous construct: it is not derived by summing account lamports on every operation, but is instead incrementally bumped up or down at a small, scattered set of call sites whenever lamports are minted or burned [1](#0-0) . The only authoritative, ground-truth recomputation is `calculate_capitalization_at_startup_from_index()`, which walks the entire accounts index account-by-account and is explicitly documented as "*very* expensive" and "only intended to be called at startup by ledger-tool or tests" [2](#0-1) .

### Finding Description
`Bank::capitalization` is maintained as an `AtomicU64` that is adjusted piecemeal by several independent code paths whenever a mutation is believed to mint or burn lamports:
- `store_account_and_update_capitalization()` diffs the old and new account lamports and adjusts capitalization accordingly [3](#0-2) .
- `distribute_transaction_fee_details()` subtracts the burned portion of transaction fees from capitalization after depositing/burning fees [4](#0-3) .
- `run_incinerator()` reads whatever lamports were sent to the incinerator account and subtracts them from capitalization, then zeroes the account, at the end of a slot [5](#0-4) .
- Core-BPF migration paths (`migrate_builtin_to_core_bpf`, `upgrade_core_bpf_program`, `upgrade_loader_v2_program_with_loader_v3_program`) each independently compute lamports-to-burn/lamports-to-fund and call `update_captalization()` before storing the new accounts [6](#0-5) .
- `maybe_burn_vat_from_staked_accounts()` (Alpenglow VAT burn) directly mutates vote-account and incinerator-account lamports via `store_accounts()`, relying on the *later* `run_incinerator()` pass to actually deduct the moved amount from capitalization [7](#0-6) .
- Epoch-rewards sysvar helpers add/subtract lamports into the sysvar account "without updating capitalization" in some branches (relying on other bookkeeping) [8](#0-7) [9](#0-8) .

Because these updates are scattered across many independent functions rather than being derived from the ledger of accounts itself, any single path that mutates lamports (mints or burns) without going through one of these specific bookkeeping helpers — or that computes the correct delta incorrectly, races against a concurrent update to the same account, or is invoked in an unexpected order relative to `run_incinerator()` — leaves `self.capitalization` permanently wrong from that slot forward. This exactly mirrors the OmoVault bug class: an internal "total assets" style counter that is supposed to reflect where funds actually are, but which can be pushed out of sync by any code path that moves/mints/burns funds outside the tracked mechanism, and for which the only real fix (a full recomputation) is documented as too expensive to run during normal operation.

The divergence is not caught in real time. It is only caught:
1. At snapshot load, via `bank.capitalization() != info.calculated_capitalization` checks in `bank_from_snapshot_archives` / `bank_from_snapshot_dir`, which return `SnapshotError::MismatchedCapitalization` and cause the node to fail to start — but this check is explicitly skipped whenever `limit_load_slot_count_from_snapshot` is set [10](#0-9) [11](#0-10) .
2. Manually, via `ledger-tool`'s `--recalculate_capitalization` or `assert_capitalization()` helper, which is not part of normal validator operation [12](#0-11) .

During ordinary, continuous validator operation (no snapshot reload), an incorrect `capitalization` value is never independently re-derived from the accounts themselves; it just persists, silently wrong, across all subsequent slots.

### Impact Explanation
`capitalization` is not merely cosmetic. It feeds:
- Inflation and reward calculation logic that assumes the tracked supply reflects reality.
- Snapshot integrity checks that gate node startup (`MismatchedCapitalization`), meaning a latent divergence can later cause a validator to refuse to boot from an otherwise-valid snapshot, or (if `limit_load_slot_count_from_snapshot` masks the check) to silently boot with wrong state.
- Diagnostic/monitoring assumptions (e.g. `hash_internal_state()` logs capitalization alongside the bank hash for debugging bank-hash mismatches) [13](#0-12) .

I was not able to fully confirm, within the remaining investigation budget, the precise call ordering between `maybe_burn_vat_from_staked_accounts()` (which moves lamports into the incinerator without itself touching capitalization) and `run_incinerator()` (which is the only place that later debits capitalization for whatever sits in the incinerator) inside `Bank::freeze()`. If these two ever execute out of the expected order in a given slot — e.g. VAT burn lamports land in the incinerator account after `run_incinerator()` has already run for that slot — those lamports would be burned from the account's balance but never subtracted from `capitalization`, producing a real, silent overstatement of capitalization that would only surface as a `MismatchedCapitalization` failure at the next snapshot reload. This part of the analysis is a hypothesis based on the code structure, not a confirmed reachable divergence; I could not verify the exact invocation order of `freeze()` given the tool budget.

### Likelihood Explanation
Likelihood is low-to-moderate and comparable to the original report's "Low" rating: each individual capitalization-adjusting call site appears internally consistent by inspection, and the design intentionally keeps ordinary lamport transfers (which don't mint/burn) outside of capitalization tracking. The risk is concentrated in the growing number of independent mint/burn call sites (fee burns, incinerator, core-BPF migrations, Alpenglow VAT burns, epoch-rewards sysvar) that each have to get their bookkeeping exactly right, with no continuous, cheap runtime invariant check to catch a mistake before it propagates for potentially very many slots until the next snapshot load.

### Recommendation
- Add a cheap, continuous (or periodic, e.g. per-epoch) sanity check that reconciles `Bank::capitalization` against an incremental digest of lamport deltas rather than relying solely on the expensive full-index recomputation done only at startup.
- Audit and centralize all lamport-minting/burning code paths (fee burns, incinerator, core-BPF migrations, VAT burns, epoch-rewards sysvar) to go through a single, tested capitalization-adjustment primitive instead of each independently computing and applying deltas.
- Explicitly verify and document (with an assertion or test) the required ordering between `maybe_burn_vat_from_staked_accounts()` and `run_incinerator()` within `Bank::freeze()`, to guarantee VAT-burned lamports landing in the incinerator are always captured by the same slot's incinerator capitalization debit.
- Do not silently skip the `MismatchedCapitalization` check when `limit_load_slot_count_from_snapshot` is set without at minimum logging a prominent warning, since this currently hides genuine divergences.

### Proof of Concept
Not independently reproduced. The evidence supporting this finding is the code-level pattern: `Bank::capitalization` is updated by discrete, scattered call sites (`runtime/src/bank.rs` lines 4819-4851, 4528-4535, 2644-2694; `runtime/src/bank/fee_distribution.rs` lines 69-77; `runtime/src/bank/builtins/core_bpf_migration/mod.rs` lines 276-294, 361-373, 449-464) rather than derived from a single source of truth, and the only full reconciliation (`calculate_capitalization_at_startup_from_index`) is documented as too expensive for anything but startup/tests, matching the reported "funds not always tracked correctly, and the only fix is an expensive full recompute" bug class. A concrete exploit PoC would require constructing a sequence of Alpenglow epoch-boundary VAT burns and slot-freeze events to test the ordering hypothesis raised above, which I was unable to complete given the tool-call budget.

                    self.capitalization.fetch_add(diff, Relaxed);
                }

                    let diff = old_account.lamports() - new_account.lamports();
                    trace!("store_account_and_update_capitalization: decreased: {pubkey} {diff}");

                "store_account_and_update_capitalization: created: {pubkey} {}",
                new_account.lamports()
            );
            self.capitalization
                .fetch_add(new_account.lamports(), Relaxed);
            0
        };
