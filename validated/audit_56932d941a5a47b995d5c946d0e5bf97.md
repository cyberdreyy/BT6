### Title
Reorg-permit check counts only `GloballyAccepted` blocks, letting a lagging signer sanction reorging a tenure with multiple quorum-signed blocks - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` is the sole gate that decides whether a signer may sanction a miner's tenure reorging a prior tenure. It refuses the reorg only if the reorged tenure has "more than one globally accepted block," using `SignerDb::get_globally_accepted_block_count_in_tenure`, which by construction only counts blocks whose local `BlockState` is `GloballyAccepted` — a state this signer only reaches once its own node reports a `NewBlock` event for that tip. A tenure can, from the network's point of view, already have two (or more) blocks that reached the full 70% signing quorum (`signed_group` set, `LocallyAccepted`) while this particular signer's own node has not yet advanced its tip to reflect them. In that window the signer's local view of "globally accepted blocks in this tenure" is 0 or 1, so it wrongly permits a reorg that the rule was designed to forbid, and records the reorged tenure as `superseded` — which subsequently makes `Signer::reorg_permit_stands`/`conflict_still_blocks` stop treating its own past signatures over that tenure's blocks as conflicts, clearing the way for this signer to sign a new, competing chain.

### Finding Description
The rule's own comment states the intent plainly: [1](#0-0) 

But the implementation checks a strictly narrower predicate than "signed": it only counts rows whose `state == GloballyAccepted`: [2](#0-1) 

The repo's own unit test confirms a `LocallyAccepted` block — i.e. one that already carries a full signer-quorum signature (`signed_group` set) — is excluded from the count: [3](#0-2) 

`GloballyAccepted` is only reached once this signer's own node reports the block as its canonical tip (a `NewBlock` event), which is strictly later than — and can lag arbitrarily behind — the moment the 70% signature quorum is actually reached and gossiped as `BlockAccepted` messages: [4](#0-3) 

The consequence of wrongly permitting the reorg is not cosmetic: `check_parent_tenure_choice` immediately records the reorged tenure as superseded, [5](#0-4) 

and that record is exactly what later causes the signer's own past signatures over that tenure's quorum-signed blocks to stop being treated as a blocking conflict when it evaluates whether to sign a new, competing block: [6](#0-5) 

So a signer whose own node is momentarily behind (a normal, frequent condition — node restart, slow `NewBlock` event delivery, or simply a race between quorum formation and the node observing it) evaluates "has this tenure already produced ≥2 signed blocks?" using a predicate that structurally cannot see quorum-signed-but-not-yet-locally-confirmed blocks, and answers "no" when the true, network-visible answer is "yes."

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" / "approved-parent vs canonical" equality the reorg-timing rule exists to protect: the rule is supposed to require that a reorged tenure has at most one *signed* block before a replacement can be sanctioned, but the check instead measures a strictly-narrower, node-tip-lagged notion of "signed." A signer that wrongly grants the permit will subsequently sign a new tenure's blocks that reorg a tenure the rest of the honest signer set (whose nodes are caught up) still correctly treats as having ≥2 quorum-signed blocks and refuses to reorg. Different signers can therefore reach different verdicts on the same reorg attempt from the same underlying facts, purely as a function of local node lag — a wedge that can produce conflicting, quorum-eligible signature sets over two incompatible chains, i.e. exactly the "signer signing a conflicting/non-canonical block" and equivocation-guard-loss class the review scope calls Critical/High.

### Likelihood Explanation
No collusion or majority-signer compromise is required. Two blocks reaching group signature threshold in a tenure is normal chain operation. A single signer merely needs its own node to be behind the `NewBlock` event for one of the two already-quorum-signed blocks at the moment a miner (the one-slot attacker in scope) proposes the very next tenure as a reorg of that tenure. This is a routine timing window (node restart, event-processing delay, or a miner racing the reorg proposal immediately after the second block's quorum forms but before this signer's own node has ingested it), not a rare or adversarial-only condition, making the mis-permit realistically reachable by ordinary network jitter combined with a miner's tenure-start proposal timing.

### Recommendation
Change the disallow check in `check_parent_tenure_choice` to count blocks by *signed* status (i.e. `signed_self IS NOT NULL OR signed_group IS NOT NULL`, matching `has_signed_block_in_tenure`/`get_last_signed_block` semantics) rather than by the node-tip-dependent `GloballyAccepted` state, so the permit decision reflects what the network has actually endorsed rather than what this signer's own (possibly lagging) node has observed.

### Proof of Concept
1. Tenure A produces block A1, which reaches full 70% signature quorum (`signed_group` set on all honest signers) → state `LocallyAccepted` everywhere and pushed toward the node.
2. Tenure A produces a second block A2, which also reaches full quorum and is likewise `LocallyAccepted` on Signer S, but Signer S's own `stacks-node` has not yet processed the `NewBlock` events for A1/A2 (e.g. S's node just restarted, or event delivery is delayed) — so on S, `get_globally_accepted_block_count_in_tenure(A) == 0`.
3. A miner starts tenure B that does not build on tenure A (a reorg attempt), triggering `check_parent_tenure_choice` on Signer S.
4. Because `globally_accepted_blocks (0) > 1` is false, S proceeds to the timing branch and, depending on proposal timing, may permit the reorg and call `mark_tenure_superseded(A, ..., B, ...)` — even though tenure A genuinely has two quorum-signed blocks, which should have unconditionally forbidden the reorg per the stated rule and per the behavior of every other signer whose node was caught up.
5. `reorg_permit_stands` on S will now treat A1/A2 as no-longer-blocking, and S can go on to sign a competing block in tenure B, while the rest of the honest set (with caught-up nodes) refuses B's reorg outright — producing a persistent split between the signer sets' local reorg-permit records over the same objective set of facts.
