### Title
APR0 withdraw requester can brick `stopEpoch` once APR is raised, freezing the epoch - ([File: contracts/strategies/idle/IdleCreditVault.sol](https://github.com/EzraCole/idle-tranches--017/blob/master/contracts/strategies/idle/IdleCreditVault.sol))

### Summary
CVE-2024-54479 is a WebKit "unexpected process crash" bug; the credit-vault analog is an unexpected hard revert in the epoch-state machine. `IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` while `unscaledApr` has been raised above zero. Any unprivileged (KYC-passing) lender can create the `apr0TotalPrincipal` bucket via `requestWithdraw` during a 0-APR epoch; when the honest manager later raises the APR for the next epoch through `setAprs`/`setAprsWithBuffer`, every subsequent `stopEpoch` call reverts, crashing the epoch lifecycle.

### Finding Description
In `requestWithdraw`, when `unscaledApr == 0`, the request is routed to `_requestWithdrawApr0`, which increases the global `apr0TotalPrincipal` bucket (`IdleCreditVault.sol:567-577`). The only place that bucket is ever reset to zero is inside `prepareStopEpochWithApr0` at `apr0TotalPrincipal = 0` (`IdleCreditVault.sol:540`) — but that line is only reached after the guard:

```solidity
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

(`IdleCreditVault.sol:506-508`). So once the APR is non-zero, the bucket can never be cleared: `_settleApr0` only moves the user's `principal` into `settledPrincipal` and never decrements `apr0TotalPrincipal` (`IdleCreditVault.sol:545-565`), and `claimWithdrawRequest`/`_claimFundedWithdrawRequest` likewise never touch it. There is no path for an attacker or manager to shrink `apr0TotalPrincipal` while `unscaledApr != 0`.

Attack sequence:
1. Pool runs/buffers an epoch with `unscaledApr == 0` (APR0 mode is a first-class supported mode).
2. Attacker (any allowed lender) deposits and calls `IdleCDOEpochVariant.requestWithdraw`. `IdleCreditVault.requestWithdraw` mints the receipt and sets `apr0TotalPrincipal > 0` (`IdleCreditVault.sol:285-286`).
3. Honest manager calls `setAprsWithBuffer`/`setAprs` to schedule a positive APR for the following epoch — a routine, privileged-but-honest action.
4. At `epochEndDate`, manager calls `stopEpoch`, which invokes `prepareStopEpochWithApr0` on the strategy. It hits `unscaledApr != 0` with `apr0TotalPrincipal > 0` and reverts. Every retry reverts identically.

### Impact Explanation
`stopEpoch` is the only function that ends the running epoch, repays lenders, increments `epochNumber`, unlocks buffer deposits/withdraw claims (`epochNumber <= lastWithdrawRequest` gate in `_claimFundedWithdrawRequest`, `IdleCreditVault.sol:326`), and unpauses the CDO. Brick­ing it freezes the entire pool: all LP principal and the running epoch's accrued interest stay locked, borrower repayment cannot be booked, and all queued withdraw receipts become unclaimable. This is temporary-to-permanent freezing of the whole TVL. The only rescue is the manager setting `unscaledApr` back to 0 via `setAprs(0, x)` mid-epoch — which itself corrupts accounting, because `prepareStopEpochWithApr0` will then distribute a pro-rata APR0 net-interest share computed against a pool whose real APR for the epoch was positive, paying withdrawers interest priced as if the epoch had run at 0 APR semantics while `lastApr` was concurrently changed for everyone else. Loss is quantified as: (a) the full pool TVL frozen for the freeze duration, and (b) the forced APR rollback, which zeroes the honest LPs' expected yield for the bricked epoch (loss of `expectedEpochInterest` for the epoch).

### Likelihood Explanation
Triggering requires only that a pool supports APR0 epochs and that the manager later raises APR while an APR0 withdraw request is outstanding — both are normal operations, and the attacker controls only the cheap `requestWithdraw` step. The revert lives on the mandatory `stopEpoch` path (`prepareStopEpochWithApr0` is called unconditionally by the CDO when `apr0TotalPrincipal != 0`), so no edge-case parameters are needed. Whether the freeze is permanent depends on whether the manager notices and accepts the APR rollback; there is no clean escape that preserves accounting correctness.

### Recommendation
- In `prepareStopEpochWithApr0`, do not revert when `unscaledApr != 0`. Instead, settle the outstanding APR0 bucket with zero (or last-recorded `apr0RateByEpoch`) interest and clear `apr0TotalPrincipal`, so the epoch can always stop.
- Alternatively, decrement `apr0TotalPrincipal` in `_settleApr0`/`_clearWithdrawClaimForEpoch` so stale buckets cannot persist across APR changes, and/or prevent `requestWithdraw` under APR0 once the manager has staged a non-zero next-epoch APR.
