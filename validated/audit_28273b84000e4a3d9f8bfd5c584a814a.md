### Title
JobsController.Update destroys job spec on partial failure when AddJobV2 fails after DeleteJob succeeds - ([File: core/web/jobs_controller.go])

### Summary
`JobsController.Update` deletes the existing job via `App.DeleteJob` before validating that the new TOML can actually be re-added via `App.AddJobV2`. If `AddJobV2` fails (e.g. `job.ErrNoSuchKeyBundle`, `keystore.KeyNotFoundError`, `job.ErrNoSuchTransmitterKey`, `job.ErrNoSuchSendingKey`), the handler returns a 400/500 error but the original job has already been irreversibly deleted, with no rollback/restore logic.

### Finding Description
In `core/web/jobs_controller.go`, `JobsController.Update` performs the update as two sequential, non-transactional steps: [1](#0-0) 

First `jc.App.DeleteJob(ctx, jb.ID)` is called and, if it succeeds, the code proceeds to `jc.App.AddJobV2(ctx, &jb)`. If `AddJobV2` fails with any of the recognized "bad input" errors (missing key bundle, missing transmitter key, missing sending key, keystore key not found) or any other error, the handler returns an HTTP error response to the caller — but the deleted job is never restored. There is no compensating transaction, no re-insertion of the old spec, and no rollback wrapper spanning both `DeleteJob` and `AddJobV2`. Consequently a subsequent `GET /v2/jobs/:ID` (or `Show`) will return 404 because the job no longer exists in the ORM/active jobs map.

This is a genuine partial-failure / state-consistency defect: the operation is not atomic despite looking like a single "update" endpoint to the caller.

### Impact Explanation
Any caller with edit-level access to the Jobs API can permanently delete a job spec they are only supposed to be editing, by supplying TOML that parses/validates successfully (passes `validateJobSpec`) but references a nonexistent key bundle/transmitter/sending key at the `AddJobV2` stage. This matches a "state consistency under partial failure" / unintended destructive-action impact class — the job configuration (potentially another job/owner's configuration, if job IDs aren't strictly scoped per-caller within the same edit-role tier) is lost with no recovery path, and the API response (400) does not warn the caller that a destructive deletion has already occurred.

### Likelihood Explanation
Preconditions are minimal: an authenticated caller with the "edit" role (the role required for `PUT /v2/jobs/:ID` — exact router-level role wrapper could not be fully confirmed in this session due to the router.go grep not returning the JobsController route registrations, but the code comment "Update validates a new TOML for an existing job, stops and deletes existing job, saves and starts a new job" and the endpoint's job-mutation nature indicate it requires an editor-level API token, consistent with other mutating job endpoints). The attacker only needs to know a valid job ID (obtainable via `GET /v2/jobs` if their role allows listing) and craft TOML with a plausible key bundle ID field that doesn't exist. This is trivially reproducible and repeatable — every failed `AddJobV2` call after a successful `DeleteJob` reproduces the bug deterministically.

### Recommendation
Make the update operation atomic / safe against partial failure:
1. Validate the new spec more thoroughly before deleting the old job — e.g., attempt to construct/validate all referenced key bundles, transmitter keys, and sending keys against the keystore *before* calling `DeleteJob`, so `AddJobV2` cannot fail for these reasons after deletion.
2. Alternatively, restructure `AddJobV2`/`DeleteJob` to run inside a single DB transaction (or wrap both calls in a saga/rollback) so that if `AddJobV2` fails, the deleted job spec is automatically restored (re-inserted) before returning the error to the caller.
3. At minimum, if `AddJobV2` fails after `DeleteJob` succeeded, attempt to restore the original job (re-add the pre-update spec) and surface a distinct error indicating the job was restored, rather than silently leaving it deleted.

### Proof of Concept
Handler-level integration test (extending `core/web/jobs_controller_test.go`):
1. Create a job via `POST /v2/jobs` with valid OCR2 TOML.
2. Send `PUT /v2/jobs/:ID` with TOML that is syntactically/schema valid (passes `validateJobSpec`) but references a non-existent `keyBundleID` (triggers `job.ErrNoSuchKeyBundle` in `AddJobV2`).
3. Assert response status is `400 Bad Request`.
4. Send `GET /v2/jobs/:ID` for the same job ID and assert it now returns `404 Not Found`, proving the original job was destroyed despite the update failing.
5. Repeat with `job.ErrNoSuchTransmitterKey`/`job.ErrNoSuchSendingKey` to confirm the same behavior across all error branches at [2](#0-1) .

	err = jc.App.DeleteJob(ctx, jb.ID)
	// Error can be either come from ORM or from the activeJobs map.
	if err != nil {

			jsonAPIError(c, http.StatusNotFound, errors.Wrap(err, "failed to update job"))
			return
		}

		return
	}

	err = jc.App.AddJobV2(ctx, &jb)
