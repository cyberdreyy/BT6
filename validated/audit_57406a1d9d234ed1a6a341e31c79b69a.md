### Title
Reorg-permit decision keyed to each signer's own local receive/approval clock, not a canonical/consensus value - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_parent_tenure_choice` decides whether a miner is allowed to reorg a prior tenure by comparing two *locally observed, per-signer* wall-clock timestamps against a fixed configuration threshold (`first_proposal_burn_block_timing`). This mirrors the report's root cause pattern: a decision that should rest on a validated/canonical, hard-to-manipulate source instead rests on a value that is directly a function of when-things-happened-to-arrive-at-this-particular-node — a quantity a single miner (through ordinary network/gossip timing, not a majority of signers) can push across the threshold differently for different signers, exactly as a single trader can push a DEX spot price across a decision boundary.

### Finding Description
`check_parent_tenure_choice` in `stacks-signer/src/chainstate/mod.rs` computes: [1](#0-0) 

- `sortition_state_received_time` = this signer's own `signer_db.get_burn_block_receive_time(...)`, i.e. the local wall-clock time *this node* recorded when it processed the `NewBurnBlock` event for the new sortition.
- `local_block_info.approved_time` = this signer's own local wall-clock time when *this node* finished validating/approving the reorged tenure's first block.

`proposal_to_sortition = sortition_state_received_time - approved_time` is then compared to the config constant `first_proposal_burn_block_timing` (default 60s, see `sample/conf/signer/mainnet-signer-conf.toml` lines 149-166) to decide "was the prior tenure poorly timed enough that a reorg is allowed." Neither timestamp is a signed, consensus-visible, or canonical value — both are purely local observations that can differ signer-to-signer by ordinary network/propagation jitter, and can be pushed across the 60s boundary by a miner's own message timing (e.g., how late it proposes/broadcasts the first block of a tenure, or how the outgoing tenure's block happens to propagate to different signers).

This is structurally the same defect class as the report: instead of deriving "is this reorg legitimate" from a canonical, single, agreed-upon fact (e.g., a consensus-visible timestamp such as the burn block's own on-chain timestamp, or a value all signers necessarily compute identically), the check derives it from a value that is (a) locally measured per node and (b) sensitive to the very actor whose behavior is being judged. Two signers evaluating the exact same proposal can reach opposite `is_valid_parent_tenure` verdicts.

Where the report's pool price directly determines domain cost (and a manipulated price is directly acted upon as truth), here `is_valid_parent_tenure` directly gates `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:497-504`) and `check_proposal` (`stacks-signer/src/chainstate/v1.rs:180-201`), i.e. it gates whether a signer will sign the tenure-change block outright as valid, and whether `mark_tenure_superseded` is recorded, voiding this signer's own prior conflicting signature (`docs/signer-flows.md:496-511`). [2](#0-1) 

### Impact Explanation
Because the input is a local, unauthenticated timing observation rather than a canonical fact, different signers can be driven to opposite conclusions about whether the same reorg is legitimate:
- Signers whose `approved_time` for the old tenure's first block was late relative to their own `sortition_state_received_time` (small `proposal_to_sortition`) will treat the reorg as "poorly timed" → permitted → they sign the new (potentially illegitimate/non-canonical, per other signers' view) tenure-change block, and mark the old tenure superseded so their own prior signature no longer blocks it.
- Signers who approved the old tenure's block promptly (large `proposal_to_sortition`, ≥ threshold) will refuse the reorg and keep blocking the new tenure's block as a conflict.

This is exactly the Critical-class outcome called for by the rules: a subset of signers ends up signing a block that other signers correctly judge non-canonical/invalid (a reorg that shouldn't be permitted), because the "canonical" determination was substituted with a spot, locally-observed value susceptible to ordinary timing skew that a single proposing miner (plus normal gossip propagation, no majority collusion needed) can influence relative to the fixed threshold.

### Likelihood Explanation
The mechanism triggers on completely ordinary conditions — a tenure change/reorg proposal arriving near the `first_proposal_burn_block_timing` boundary (default 60s) is a routine occurrence in tenure handoffs, and network propagation delay of a few seconds around this boundary is common, not adversarial-only. A miner does not need to compromise any other party; it only needs to control when it proposes/broadcasts, and rely on the naturally-varying propagation/validation latency across signers. This makes the disagreement realistically reachable without a majority of signers, an auth token, or another signer's key — consistent with the rules' one-slot-miner-plus-gossip framing. However, actually causing a *material* chain-safety event (both a valid signature set forming for the losing tenure and the winning tenure) still depends on how the population of "early" vs "late" approvers falls relative to the 70% threshold; this repo's own tests (`stacks-signer/src/chainstate/tests/v1.rs:326-355`, `stacks-signer/src/chainstate/tests/v2.rs:362-380`) show the check is knife-edge sensitive to exactly this timing (1-second difference flips the verdict), corroborating that the boundary is easy to straddle, but I could not verify from the index alone whether downstream safeguards (e.g. `conflict_still_blocks`, `reorg_permit_stands`) fully neutralize a split population in all cases — that would require deeper live/integration analysis than the indexed code provides.

### Recommendation
Do not gate the reorg-permit decision on purely local, per-signer wall-clock observations of message arrival/approval. Instead, derive `first_proposal_burn_block_timing` comparisons from a canonical, consensus-visible timestamp that all signers necessarily agree on (e.g., the burn block's own on-chain timestamp compared against a block header field that is itself covered by the miner's signature, or a node-RPC-resolved fact rather than a signer-local receive/approval clock). At minimum, treat this as a fact requiring corroboration from the node's own view (similar to how `conflict_still_blocks` re-derives fork status from `stacks_client` calls) rather than trusting `signer_db`'s locally-recorded times as the sole input to a chain-safety-relevant boolean.

### Proof of Concept
Not directly exploitable as a standalone repro from static analysis; the repo's own unit tests demonstrate the sensitivity of the mechanism: [3](#0-2) 
- `check_proposal_reorg_timing_bad`/`check_proposal_reorg_timing_ok` show a 1-second shift in the timing inputs (`sortition_timing_secs` 31 vs 29 against a 30s threshold) flips `is_valid_parent_tenure` from `false` to `true`. Since these inputs (`approved_time`, `sortition_state_received_time`) are locally observed per signer rather than a shared canonical value, two signers who received/approved the same proposal a few seconds apart (ordinary propagation jitter, or a miner deliberately timing its broadcast) can land on opposite sides of this same boundary, one signing the reorg's tenure-change block as valid, the other rejecting it as an unauthorized reorg — reproducing, in this codebase, the report's core pattern of trusting a manipulable spot observation for a decision that should be canonical.
