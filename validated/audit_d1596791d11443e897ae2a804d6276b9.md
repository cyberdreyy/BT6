### Title
Loss-adjusted withdraw receipts keyed to the wrong epoch index skip the haircut and pay claims at par, draining the funded reserve and freezing later claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores a realized stop-epoch loss under `lossRecoveryPriceByEpoch[epochNumber]` (line 421), while `_claimLossAdjustedWithdrawRequest` looks the haircut up under `lastWithdrawRequest[_user]`, i.e. the epoch in which the user *requested* (lines 789-800). `epochNumber` is only incremented inside `deposit()` when the epoch is still running (lines 607-610). If `stopEpoch` calls `collectWithdrawFunds` after the strategy-token deposit that bumps `epochNumber`, the haircut is written under epoch N+1 while every affected receipt points at epoch N — the per-epoch haircut mapping is read at an out-of-bounds (stale) index, exactly analogous to CVE-2016-9297's out-of-bounds read driven by an index the parser did not validate.

### Finding Description
- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 282-293).
- On a loss-making `stopEpoch`, `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (line 421) and clears `pendingWithdraws` while pulling only the haircut `_amount` of underlying.
- `epochNumber` is bumped in `deposit()` (line 610) whenever `isEpochRunning()` is still true — i.e. inside the same `stopEpoch` transaction before the flag is cleared.
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 790-791). If the stored key is N+1 and the receipt key is N, the lookup returns 0, the loss-adjusted path silently returns 0, and the claim falls through to `_claimFundedWithdrawRequest` (line 313), which pays the full unhaircutted `withdrawsRequests[_user]` once `epochNumber > lastWithdrawRequest[_user]` (line 326) — a condition already satisfied.
- The same stale index also defeats the guard in `requestWithdraw` (lines 261-271), which only reverts when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`; with the haircut stored under N+1 the guard sees 0 and lets users stack new requests on top of unclaimed loss receipts.

### Impact Explanation
The strategy receives only `pendingBasis * lossRecoveryPrice` underlying but owes `pendingBasis` at par through `_transferFundedClaim`. Early claimants are overpaid relative to the intended socialized loss; once the funded reserve is exhausted, `_transferFundedClaim` reverts for all remaining claimants, permanently freezing their receipts (or paying them from unrelated strategy funds, causing insolvency). Loss is quantified as `pendingBasis - fundedAmount` (the portion of `_lossAmount` assigned to pending receipts), stolen by whoever claims first.

### Likelihood Explanation
Triggered on any `stopEpoch` where the borrower under-funds pending withdrawals (`_amount < pendingBasis`) and `collectWithdrawFunds` executes after the epoch-incrementing deposit — the normal stop flow in `IdleCDOEpochVariant`. Any unprivileged lender whose withdraw request was pending in that epoch can then claim at par or observe frozen funds; no privileged role misbehavior is required (the manager invoking `stopEpoch` with a loss is an honest, in-scope action).

### Recommendation
Key `lossRecoveryPriceByEpoch` by the epoch the pending receipts were recorded in (e.g. `epochNumber - 1` after the bump, or the value captured before `deposit()` increments), or better, pass the request epoch explicitly from the CDO. Add an invariant check in `requestWithdraw`/`claimWithdrawRequest` that a non-zero haircut for *any* epoch the user has receipts in must be claimed first. The same epoch-keying audit should be applied to `apr0RateByEpoch[epochNumber]` (line 537) and `defaultPendingClaimBasis`'s use of `instantWithdrawClaimsByEpoch[epochNumber]` (line 647), which share the same stale-index pattern.

function testLossEpochIndexMismatch() external {
    // 1. KYC'd lender deposits AA during epoch N buffer.
    uint256 amt = 10_000 * ONE_SCALE;
    uint256 tr = _depositWithUser(victim, amt);
    // 2. victim requests withdraw in epoch N
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    // 3. Honest manager stops epoch with a partial loss (borrower under-funds pending).
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(lossAmount, apr, 0); // triggers collectWithdrawFunds(shortfall)
    // 4. If haircut was stored under epochNumber (N+1) while lastWithdrawRequest == N:
    assertEq(strategy.lossRecoveryPriceByEpoch(strategy.lastWithdrawRequest(victim)), 0);
    // 5. victim claims FULL basis instead of haircut amount
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest(); // pays > funded amount -> drains reserve
    // 6. second claimant's funded claim reverts / freezes
    vm.prank(victim2);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}

Caveat: the finding depends on `collectWithdrawFunds` being invoked after the `epochNumber` increment inside the same `stopEpoch` transaction in `IdleCDOEpochVariant`; I could not fully read that call ordering within this session. If `collectWithdrawFunds` runs before the increment, the same mismatch reappears mirrored — receipts keyed at N are haircut by a price stored at N — so the index-consistency assumption should be verified first when executing the PoC.
