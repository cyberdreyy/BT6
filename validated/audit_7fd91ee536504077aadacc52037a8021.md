### Title
v1-protocol `DuplicateBlockFound` proposal gate only checks global acceptance, not local — a stale conflict guard is the only backstop against signing a competing tenure-start block - ([File: stacks-signer/src/chainstate/v1.rs], [File: stacks-signer/src/v0/signer.rs])

### Summary
Under the v1 signer protocol, the proposal-time duplicate-block check (`validate_tenure_change_payload`) rejects a second tenure-start proposal for the same tenure only when a **globally accepted** block already exists there (`get_last_globally_accepted_block`), per `docs/signer-flows.md` section 7. A block that this signer has already **locally accepted / signed** (`signed_self` set) but that has not yet reached global acceptance is invisible to that check. A one-slot miner can therefore get a second, competing tenure-start proposal (block B) past the proposal-time gate for a tenure where the signer already signed block A. The only remaining defense is the pre-commit-time conflict guard in `handle_block_pre_commit` (`get_signed_conflicts` / `conflict_still_blocks`), which is a silent "refuse to sign" backstop, not a rejection, and is explicitly documented as depending on freshness/node-liveness derivation rather than a hard invariant.

### Finding Description
- `handle_block_proposal` in `stacks-signer/src/v0/signer.rs` (lines ~1574-1727) treats a proposal with a **different** `signer_signature_hash` as brand new, running it through `check_block_against_state` → `SortitionsView::check_proposal` (v1) with no memory of any block already signed in that tenure except via the global-acceptance-based `DuplicateBlockFound` check. [1](#0-0) 
- The doc explicitly states the asymmetry: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)" and that this duplicate check "never runs again" after proposal time. [2](#0-1) 
- `BlockInfo::mark_locally_accepted` sets `signed_self`/`valid=true` and moves state to `LocallyAccepted` — this is a real signature already produced by this signer — well before `mark_globally_accepted` (which only fires once the node reports the block processed). [3](#0-2) 
- The v2 code path was hardened for exactly this gap, as shown by the regression test asserting `DuplicateBlockFound` fires against a merely-`LocallyAccepted` block ("Before the fix, this would have incorrectly passed because `get_last_globally_accepted_block` would not find the locally-accepted block"). [4](#0-3) 
- No equivalent v1 test or fix is present in the explored v1 chainstate code; the v1 `SortitionState`/`SortitionData` proposal path relies on the same `get_last_globally_accepted_block`-based check described in the docs.
- The only remaining protection is `handle_block_pre_commit`'s conflict check, which queries `get_signed_conflicts` (any block with `signed_self` or `signed_group` set at or above the proposed height) and gates on freshness/liveness derived from the node (`conflict_still_blocks`, `reorg_permit_stands`). [5](#0-4) 
This means that for v1-protocol signers, whether a second proposal for a tenure where a block has already been *signed but not yet globally accepted* gets far enough to even attempt a signature depends entirely on the conflict guard rather than a hard reject at proposal time — the layered defense the v2 path enjoys is missing for v1.

### Impact Explanation
If the conflict guard's node-derived liveness questions (`conflict_still_blocks`) are ever momentarily wrong or race against a slow node (e.g., the node hasn't yet reflected the locally-accepted-but-not-yet-globally-accepted block, or a signer restarted and never observed A but received B's proposal + B's own pre-commit round independently), a subset of v1 signers could sign block B while a fresh conflicting signature over A exists elsewhere in the signer set. This is exactly the equivocation class in scope: a signer signing a conflicting/non-canonical block that breaks the "one-per-height" equality the guard exists to protect, achievable by a single miner proposing two competing tenure-start blocks and gossip alone (no majority-signer collusion required to *create* the ambiguous state — only normal signer set behavior on both sides of the race).

### Likelihood Explanation
Requires v1 protocol to still be active/supported (mixed-version fleets are explicitly a first-class concern per the "outdated peer fallback" design elsewhere in this codebase) and a timing window between local signing and global acceptance, or a restart that lost in-memory state, coinciding with a miner re-proposing a competing tenure-start block. This is a narrower window than a straightforward equality bug, and it is only reachable while v1 is in use, which I could not fully confirm is still exercised end-to-end (I was not able to load the complete `v1.rs` `check_proposal`/`validate_tenure_change_payload` body before running out of iterations, so the exact call site and whether any additional guard exists there is unverified).

### Recommendation
Align v1's `validate_tenure_change_payload` duplicate check with v2's: use a helper equivalent to `get_last_signed_block` (locally OR globally accepted) instead of `get_last_globally_accepted_block`, so a locally-signed-but-not-yet-globally-accepted block also blocks a second tenure-start proposal for the same tenure at proposal time, rather than relying solely on the pre-commit conflict guard.

### Proof of Concept
Unverified end-to-end due to not having read the full v1 `check_proposal`/`validate_tenure_change_payload` implementation before the tool budget ended. The reasoning is based on:
1. `docs/signer-flows.md` explicitly documenting the v1/v2 asymmetry in the `DuplicateBlockFound` check.
2. The v2 regression test `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs`, which proves the bug class existed and was fixed for v2 but gives no evidence of an equivalent fix for v1.
A concrete PoC would require: (a) confirming v1's `validate_tenure_change_payload` source, and (b) a test analogous to the v2 one but exercising `stacks-signer/src/chainstate/v1.rs`'s `check_proposal`, asserting it does *not* reject a second tenure-start block when the first is only `LocallyAccepted`. I recommend a Devin session load and diff `stacks-signer/src/chainstate/v1.rs` against `v2.rs`'s duplicate-block logic to confirm and fix this before treating it as fully proven.

    /// Mark this block as valid and the appropriate timestamps if they aren't already set, and attempt to mark it as locally accepted.
    pub fn mark_locally_accepted(&mut self, group_signed: bool) -> Result<(), String> {
        if group_signed {
            self.signed_group.get_or_insert(get_epoch_time_secs());
        } else {
            self.valid = Some(true);
            self.approved_time.get_or_insert(get_epoch_time_secs());
            self.signed_self.get_or_insert(get_epoch_time_secs());
        }
        self.move_to(BlockState::LocallyAccepted)
    }

    /// Mark this block's signed group time if not already set and attempt to mark it as globally accepted.
    pub fn mark_globally_accepted(&mut self) -> Result<(), String> {
        self.signed_group.get_or_insert(get_epoch_time_secs());
        self.move_to(BlockState::GloballyAccepted)
    }

        // A pre-commit may be superseded by a competing proposal at the same height (e.g. a
        // re-proposed tenure-start block after the first failed to reach consensus), but a
        // signature must not be superseded while it's still "fresh". A signed block at the
        // same or higher height in ANY tenure is a conflict: two blocks at the same height are
        // siblings no matter which tenure they belong to (e.g. the next tenure's tenure-start
        // block conflicts with the current tenure's block at the same height). Blocks in
        // tenures whose reorg we sanctioned under the reorg-timing rules are excluded, but
        // only while the sortition the permit was granted to is still canonical
        // (`check_parent_tenure_choice` records the permit, `reorg_permit_stands` re-derives
        // its validity from the node); every other question about whether a conflict is
        // still live is derived from the node in `conflict_still_blocks`.
        //
        // Unlike the chainstate check above, a refusal here is "for now" rather than a
        // broadcast rejection: a later pre-commit re-evaluation may still sign the block once
        // the conflicting signature has gone stale.
        let conflicts = match self
            .signer_db
            .get_signed_conflicts(block_info.block.header.chain_length, &block_hash)
        {
            Ok(conflicts) => conflicts,
            Err(e) => {
                warn!("{self}: Failed to query the signed blocks. Refusing to sign block {block_hash}: {e:?}");
                return;
            }
        };
        let freshness_cutoff = get_epoch_time_secs().saturating_sub(
            self.proposal_config
                .tenure_last_block_proposal_timeout
                .as_secs(),
        );
        // A fresh signature only blocks while the block it covers could still be part of the
        // chain: see `conflict_still_blocks`, which asks the node whether it is. Check
        // freshness first: it is a local timestamp comparison, while `reorg_permit_stands`
        // and `conflict_still_blocks` each query the node, so stale conflicts cost no
        // round-trips.
        if let Some(conflict) = conflicts.iter().find(|conflict| {
            conflict.last_endorsed > freshness_cutoff
                && !self.reorg_permit_stands(stacks_client, conflict)
                && self.conflict_still_blocks(
                    stacks_client,
                    conflict,
                    block_info.block.header.chain_length,
                )
        }) {
            warn!(
                "{self}: Reached the pre-commit threshold for a block, but we have recently signed or accepted a different block at the same or higher height. Refusing to sign.";
                "signer_signature_hash" => %block_hash,
                "block_height" => block_info.block.header.chain_length,
                "conflicting_signer_signature_hash" => %conflict.signer_signature_hash,
                "conflicting_block_height" => conflict.stacks_height,
                "conflicting_consensus_hash" => %conflict.consensus_hash,
            );
            return;
        }
