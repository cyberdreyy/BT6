### Title
Instant-withdraw path in `requestWithdraw` forfeits accrued epoch interest - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCDOEpochVariant.requestWithdraw` has two payout paths. The normal path computes `principal` plus pro‑rata epoch interest via `_calcInterestWithdrawRequest` and deducts fees, so the user's receipt includes accrued yield [1](#0-0) . The instant-withdraw path — taken whenever `_isInstantWithdrawEnabled()` is true and the current vault APR has dropped more than `instantWithdrawAprDelta` below `lastEpochApr` — skips interest calculation entirely and mints a receipt for `_underlyings = _trancheToUnderlyings(_amount)` (principal at current price) only [2](#0-1) . Because the normal path explicitly adds `interest` on top of `principal`, the tranche price does not include accrued-but-uncredited epoch interest; instant-withdraw users therefore silently forfeit all yield accrued in the current epoch. This mirrors the Spartan `SynthVault.withdraw` bug class: a withdrawal variant that fails to credit accumulated rewards.

### Finding Description
In `requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739-791):

```solidity
_underlyings = _trancheToUnderlyings(_amount, _tranche);
if (_isInstantWithdrawEnabled()) {
  uint256 currentApr = creditVault.unscaledApr();
  if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
    creditVault.requestInstantWithdraw(_underlyings, msg.sender);
    _withdrawOps(_amount, _underlyings, _tranche);
    return _underlyings;
  }
}
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
...
_underlyings = principal + interest - totalFees;
```

Broken invariant — fair burn: identical tranche tokens burned at the same instant yield either `principal + interest − fees` (normal path) or just `principal` (instant path), depending solely on the APR delta — a condition the user does not control and that is not priced into the receipt. The forfeited `interest` remains in NAV and accrues to remaining tranche holders. Additionally, the instant path skips the `interestForOverUnderPerformance += diff` adjustment [3](#0-2) , so an AA instant withdrawal also fails to record the overperformance it would have generated for BB, distorting `expectedEpochInterest` at the next `startEpoch`.

`IdleCreditVault.requestInstantWithdraw` then mints the user a receipt equal to the principal-only amount and burns the CDO's strategy tokens [4](#0-3) ; `claimInstantWithdrawRequest` pays exactly that receipt, so the loss is permanent [5](#0-4) .

### Impact Explanation
Any tranche holder withdrawing during a buffer period after an APR cut exceeding `instantWithdrawAprDelta` permanently loses all interest accrued on their position during the current epoch — the same "withdraw forfeits rewards" class as the reference report. The loss is the full `interest` term from `_calcInterestWithdrawRequest`, proportional to the elapsed epoch fraction and the APR; for a holder requesting late in an epoch this approaches a full epoch's yield. No guard prevents it: KYC and allow-flag checks pass, `_updateAccounting` runs, and the receipt is honored in full at the underpaid amount.

### Likelihood Explanation
The trigger is a manager-set APR decrease larger than `instantWithdrawAprDelta`, which is a normal protocol operation (APR0 / rate-cut epochs are exercised in the test suite). Any user calling `requestWithdraw` in that window is routed to the instant path automatically — they cannot opt into the interest-paying path. Once routed, the forfeiture is certain. One caveat: whether the team considers principal-only instant exit an intentional trade-off (as Spartan argued) cannot be fully confirmed from the code, and I could not read `_trancheToUnderlyings`/`virtualPrice` internals to verify that no accrued interest is embedded in price — though the normal path adding `interest` on top of `principal` strongly indicates it is not.

### Recommendation
In the instant-withdraw branch, compute `(interest, diff)` via `_calcInterestWithdrawRequest` and charge `_totalWithdrawFees` exactly like the normal path, passing `principal + interest − totalFees` to `requestInstantWithdraw`, and update `pendingWithdrawFees` and `interestForOverUnderPerformance` consistently. If principal-only instant exit is intended, revert the request instead of silently underpaying, or document and gate it behind an explicit user flag.

### Proof of Concept
Foundry fork test (sketch, modeled on `test/foundry/IdleCreditVault.t.sol` APR0 scenarios):

```solidity
function testInstantWithdrawForfeitsAccruedInterest() external {
    // deposit AA, run epoch 0 normally
    idleCDO.depositAA(10000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _fundBorrowerAndStopEpoch(); // borrower repays principal+interest

    // epoch 1 runs; warp to 90% of epoch so interest has accrued
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() - epochDuration / 10);

    // manager cuts APR below lastEpochApr - instantWithdrawAprDelta
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // currentApr << lastEpochApr

    uint256 trancheBal = IERC20(AAtranche).balanceOf(address(this));
    uint256 expectedInterest = cdoEpoch.getWithdrawRequestInterest(trancheBal, AAtranche); // preview helper
    uint256 requested = cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));

    // BUG: requested equals principal only; expectedInterest (~90% of epoch yield) is forfeited
    assertLt(requested, expectedInterest + principalPreview, "instant path paid no interest");
}
```

The assertion compares the `requestWithdraw` return value against `principal + _calcInterestWithdrawRequest`-equivalent interest; on the fork it shows the instant branch returns strictly the price-denominated principal while the accrued interest stays in NAV for remaining holders.
