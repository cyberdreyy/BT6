### Title
Defaulted APR0 receipt is paid twice — haircut via default claim then again at par via funded claim (double-free analog) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimWithdrawRequest` chains `_claimDefaultedWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` → `_claimFundedWithdrawRequest` in a single call. The defaulted-epoch clear path (`_clearWithdrawClaimForEpoch`) zeroes `apr0User.principal` and `apr0User.principalEpoch`, but leaves `apr0User.settledPrincipal` and `apr0User.settledInterest` intact. Like the U-Boot double-free of a cached block, the same settled APR0 balance is then "freed" a second time when `_claimFundedWithdrawRequest` computes `apr0PrincipalAmount = settledPrincipal + principal` and `apr0InterestAmount = settledInterest` and pays them at par.

### Finding Description
In `IdleCreditVault.claimWithdrawRequest` (`contracts/strategies/idle/IdleCreditVault.sol:301-314`), when `defaultRecoveryFinalized` is true, `_claimDefaultedWithdrawRequest` (`:772-784`) computes the claim basis for the defaulted epoch via `_withdrawClaimAmountsForEpoch` (`:862+`), which sums the normal receipt plus the APR0 principal and settled APR0 interest for that epoch, then pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from the recovery reserve. `_clearWithdrawClaimForEpoch` (`:811-837`) clears `withdrawsRequestsByEpoch`, `apr0User.principal`, and `apr0User.principalEpoch`, but does not touch `settledPrincipal` or `settledInterest` and does not `delete apr0Users[_user]` (that delete only happens in `_claimFundedWithdrawRequest` at `:346-348`).

Execution then continues into `_claimFundedWithdrawRequest` (`:319-350`). After `_settleApr0(_user)`, it reads `apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal` (with `principal` now 0, this is the full `settledPrincipal`) and `apr0InterestAmount = _apr0User.settledInterest`, burns `normalAmount + apr0PrincipalAmount` receipt tokens, and transfers `normalAmount + apr0PrincipalAmount + apr0InterestAmount` at par via `_transferFundedClaim`. If `settledPrincipal`/`settledInterest` were already included in `claimBasis` for the defaulted epoch (they are part of `pendingWithdraws` claim basis per the comment at `:777-780`), the same underlying is paid a second time — once haircut from `defaultRecoveryReserve`, once in full from the funded-receipt balance.

The "one receipt one payout" invariant is broken: the cleared receipt's cached APR0 fields are reused, exactly mirroring CVE-2019-13105's double-free of a cached block.

### Impact Explanation
An unprivileged lender (any KYC-passing wallet) who holds an APR0 withdraw receipt from the defaulted epoch that had already accrued `settledPrincipal`/`settledInterest` receives both the haircutted recovery payout and a full par payout of the settled amounts. The second payout drains underlyings reserved for other users' funded claims, directly stealing `settledPrincipal + settledInterest` worth of underlying beyond the intended recovery ratio. Loss is bounded by the attacker's settled APR0 position size, which is user-controlled (deposit size × epoch count).

### Likelihood Explanation
Requires: APR0 mode (`unscaledApr == 0`), a user requesting withdraw before the epoch in which the borrower defaults, settlement of APR0 interest at an intervening `stopEpoch` (which populates `settledPrincipal`/`settledInterest`), borrower default, and honest manager `finalizeDefault`. After that a single `cdoEpoch.claimWithdrawRequest()` call executes both payouts. No privileged cooperation is needed; all attacker steps are ordinary user calls.

### Recommendation
In `_clearWithdrawClaimForEpoch`, when clearing a defaulted APR0 claim, also zero `apr0User.settledPrincipal` and `apr0User.settledInterest` (or `delete apr0Users[_user]` once all fields for the claim epoch are consumed), and reduce `pendingWithdraws`/burn amounts consistently so `_claimFundedWithdrawRequest` cannot re-pay the settled bucket. Add a test asserting a defaulted-epoch APR0 receipt pays exactly `claimBasis * defaultRecoveryPrice` and leaves `apr0Users[user]` fully cleared.

### Proof of Concept
Foundry fork PoC sketch (mirroring `testFinalizeDefaultClaimsOldFundedAndDefaultedRedeemsInOneCall` in `test/foundry/IdleCreditVault.t.sol:4388`):

```solidity
// 1. Configure vault with unscaledApr == 0 (APR0 mode).
// 2. user deposits; user calls cdoEpoch.requestWithdraw(...) -> requestWithdrawApr0 path.
// 3. startEpoch; stopEpoch -> _settleApr0 accrues settledPrincipal/settledInterest
//    (or a second request epoch so principal settles).
// 4. Borrower defaults; manager calls finalizeDefault(recovered, manager)
//    -> defaultRecoveryFinalized = true, defaultRecoveryEpoch = epoch N.
// 5. user calls cdoEpoch.claimWithdrawRequest() once:
//    - _claimDefaultedWithdrawRequest pays claimBasis * recoveryPrice
//      (claimBasis includes settledPrincipal + settledInterest),
//      clears principal/principalEpoch but NOT settled fields.
//    - _claimFundedWithdrawRequest then pays settledPrincipal + settledInterest
//      AGAIN at par via _transferFundedClaim.
// 6. assert user received haircut + full settled amount, and vault balance
//    decreased by more than defaultRecoveryReserve consumed.
```

Note: I could not fully read `_withdrawClaimAmountsForEpoch` (lines ~870-900) and `_settleApr0` to confirm the settled fields are included in `claimBasis` for the defaulted epoch. If `claimBasis` deliberately excludes settled APR0 amounts (i.e. they are intentionally left for the funded path at par), this finding collapses to intended behavior; that exact accounting boundary should be verified before reporting.
