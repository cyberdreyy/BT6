### Title
Haircutted withdraw receipts from a loss epoch are repaid at par via the funded-claim path once the user re-requests in a later epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimWithdrawRequest` resolves a user's receipt through a chain of "namespaces": post-default reserve, defaulted epoch, `lossRecoveryPriceByEpoch` (keyed by `lastWithdrawRequest[_user]`), and finally the funded path which pays the whole `withdrawsRequests[_user]` aggregate at par. Because only `lastWithdrawRequest[_user]` selects which epoch gets the loss haircut, a lender whose epoch-N receipt was haircutted can request again in a later, fully-funded epoch M. `lastWithdrawRequest` moves to M, `lossRecoveryPriceByEpoch[M]` is 0 so the loss-adjusted path is skipped, and `_claimFundedWithdrawRequest` then pays the aggregate — including the never-cleared epoch-N receipt — at 100%, even though the borrower only funded `price × basis` for it.

### Finding Description
In `collectWithdrawFunds`, when the borrower underfunds pending withdrawals, `pendingWithdraws` is zeroed and a haircut is recorded only under `lossRecoveryPriceByEpoch[epochNumber]` (IdleCreditVault.sol:411-430). Individual receipts remain in `withdrawsRequestsByEpoch[user][epoch]` and in the `withdrawsRequests[user]` aggregate.

On claim, `_claimLossAdjustedWithdrawRequest` only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (IdleCreditVault.sol:789-801). `_clearWithdrawClaimForEpoch` removes the epoch's piece from the aggregate only for that single epoch (IdleCreditVault.sol:811-837). If the user subsequently makes a new `requestWithdraw` in a later epoch — which the code explicitly allows ("if a user does not claim... he will have to wait for another epoch", IdleCreditVault.sol:323-324) — `lastWithdrawRequest` is overwritten to the new epoch. Once that epoch ends fully funded:

1. `_claimLossAdjustedWithdrawRequest` sees `lossRecoveryPriceByEpoch[M] == 0` → returns 0, never clearing the epoch-N receipt.
2. `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` (basis_N + basis_M) at par and burns the receipt tokens (IdleCreditVault.sol:338-349).

The strategy balance only received `p × basis_N` for the epoch-N portion, so the payout exceeds funded assets by `(1 − p) × basis_N`. Analogous to path traversal: the attacker steers which "directory" (price namespace) resolves their claim, escaping the intended haircut scope.

### Impact Explanation
Direct theft/insolvency: the overpayment `(1 − p) × basis_N` is drained from underlyings belonging to other funded claimants and LPs. With a 50% haircut epoch and a 1M underlyings receipt, re-requesting a dust amount in the next epoch upgrades the loss receipt to par — a 500k underlyings theft, deterministic once a loss epoch exists.

### Likelihood Explanation
Requires a `stopEpochWithDuration`/`collectWithdrawFunds` loss event (borrower underfunding — an honest borrower action, not attacker-controlled) plus the attacker being a KYC'd lender holding a pending receipt in that epoch and making a second request in a later epoch. No privileged collusion needed; the guard in `_claimFundedWithdrawRequest` (epoch gating, reserve check at IdleCreditVault.sol:899-905) does not catch it because the reserve guard only protects `defaultRecoveryReserve`, not the haircut shortfall.

### Recommendation
Do not key loss-adjusted resolution solely on `lastWithdrawRequest`. Either iterate the user's per-epoch receipts (e.g., check `lossRecoveryPriceByEpoch` for every epoch present in `withdrawsRequestsByEpoch[_user]`), or in `_claimFundedWithdrawRequest` exclude any epoch where `lossRecoveryPriceByEpoch[epoch] != 0`, forcing those receipts through the haircutted path regardless of which epoch is "last". Alternatively, block new `requestWithdraw` while an unclaimed haircutted receipt exists.

### Proof of Concept
Foundry fork PoC (setup omitted; uses deployed `IdleCDOEpochVariant` + `IdleCreditVault` strategy):

```solidity
function test_LossReceiptPaidAtPar() public {
    // attacker = KYC'd AA lender on the vault's CDO
    uint256 basis = 1_000_000e6; // underlying decimals

    // Epoch N: deposit, epoch runs, attacker requests withdraw of `basis`
    vm.prank(attacker);
    cdo.requestWithdraw(basis, true); // AA
    vm.prank(manager);
    cdo.stopEpochWithDuration(duration, lossAmount); // borrower underfunds
    // collectWithdrawFunds stores lossRecoveryPriceByEpoch[N] = p < 1e18
    uint256 p = vault.lossRecoveryPriceByEpoch(vault.epochNumber());

    // Attacker does NOT claim. Epoch M: new epoch starts, attacker requests dust.
    vm.prank(manager);
    cdo.startEpoch(...); // honest manager action
    vm.prank(attacker);
    cdo.requestWithdraw(1, true); // moves lastWithdrawRequest to epoch M
    // epoch M ends fully funded
    vm.prank(manager);
    cdo.stopEpoch(...);

    // Claim: loss-adjusted path skipped (price[M]==0), funded path pays
    // basis + 1 at par even though only p*basis + 1 was funded.
    uint256 balBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdo.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balBefore;

    assertEq(paid, basis + 1);                 // paid at par
    assertLt(vault fundedBalance, paid);       // overdraws by (1-p)*basis
}
```

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
