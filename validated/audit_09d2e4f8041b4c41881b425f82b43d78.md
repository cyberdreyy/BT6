## Finding

### Title
Block-proposal re-evaluation wipes an already-signed `BlockInfo` via an unfiltered `BlockInfo::from(block_proposal)` overwrite - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_proposal` decides whether to re-evaluate an already-tracked block via `should_reevaluate_block`, but once re-evaluation is allowed it discards the entire previously-stored `BlockInfo` and replaces it with a brand-new one built solely from the incoming (attacker/miner-controlled) `BlockProposal`, wiping fields that record that the signer already validated/signed the block. This mirrors the reported bug class: the whole incoming object is used to reconstruct persisted state without an allowlist of which fields may be overwritten, defeating checks meant to gate a sensitive transition (here, "have we already signed this block").

### Finding Description
When a `BlockProposal` for an already-known block arrives, `should_reevaluate_block` is the only gate: [1](#0-0) 

This only special-cases the fully terminal `globally_approved_and_responded()` state. For everything else it defers to `should_reevaluate_reject_reason(block_info)`: [2](#0-1) 

Only the `PreCommitted` state gets a safe branch (re-run the pre-commit/threshold evaluation instead of resigning). Any other non-terminal state — notably `LocallyAccepted`, which is reached only *after* the signer has produced and broadcast a signature (`signed_self` set) — falls through to `determine_response`/re-send unless `should_reevaluate_reject_reason` says the stored `reject_reason` is "reconsiderable," in which case the function logs "our rejection reason allows us to reconsider" and returns `true`: [3](#0-2) 

Back in `handle_block_proposal`, a `true` result leads directly to: [4](#0-3) 

The comment on that line is a direct admission of the bug class: *"Creating a new proposal will overwrite any prior proposal info on the block if it exists, e.g. validity, signed_timestamps, etc."* The resulting fresh `BlockInfo` (state `Unprocessed`, `valid = None`, `signed_self = None`, `reject_reason = None`) is then persisted via `insert_block`, which is a primary-key upsert on `(reward_cycle, signer_signature_hash)`: [5](#0-4) 

The gating condition (`reject_reason` reconsiderable) is evaluated purely from a leftover field on the stored record; nothing in this path checks whether the block previously reached `LocallyAccepted`/`signed_self` before allowing the wipe. If a block's `reject_reason` was set from an earlier reconsiderable rejection and the block was subsequently accepted and signed on re-evaluation without that field being cleared, a further identical re-proposal from the same miner (trivial to trigger — this is normal miner re-broadcast behavior, exercised in `stacks-signer/src/v0/tests.rs:711-750` for the `PreCommitted` case) drives the code back into the "reconsider" branch and erases the `signed_self`/`state` record for that exact block hash, even though this signer already produced a signature over it.

This breaks the equality the state machine relies on: the per-block `signed_self`/`state=LocallyAccepted` fields are the local record of "did I already sign at this height for this block," used by the pre-commit/height-conflict logic described in `docs/signer-flows.md` (`get_signed_conflicts`, section 5) and by `store_and_process_block_signature`'s "have I already decided" checks. Silently resetting that record via an unfiltered full-object overwrite is the direct analog of the Flowise `merge(User, oldUserData, newUserData)` mass assignment: the entire incoming payload is trusted to reconstruct protected state instead of only updating the fields the workflow intends to change.

### Impact Explanation
If the wipe occurs after the signer already signed a block (`signed_self` set, state `LocallyAccepted`) but before it is globally accepted and responded to, the signer's own bookkeeping loses the fact that it already committed to that specific block hash. A subsequent full re-evaluation of the same (or now-conflicting) height under different chain conditions can cause the signer to reprocess the pre-commit/signature path from `Unprocessed`, undermining the "one signature per height" invariant that `handle_block_pre_commit`'s conflict checks are built to enforce. This falls into the High/Critical impact category (signer state corrupted in a way that can permit reconsidering an already-signed decision) — I cannot fully confirm from the available code whether `get_signed_conflicts`/height-conflict scans key off *only* this per-row field (which would make the break immediately actionable) or also track equivalent state elsewhere, so the ceiling of the impact carries that caveat.

### Likelihood Explanation
Triggering a re-proposal of an identical block requires nothing beyond normal miner behavior (a one-slot miner resending its own proposal, which the codebase already treats as a routine event — see the re-propose test). The only uncertain precondition is whether `reject_reason` is left populated with a "reconsiderable" value after a block transitions from a reconsidered rejection to acceptance; I could not verify `mark_locally_accepted`'s handling of `reject_reason` clearing within my available search budget, so likelihood is assessed as Medium pending that confirmation.

### Recommendation
- In `should_reevaluate_block`, explicitly treat any block that has `signed_self.is_some()` (i.e., `LocallyAccepted` or later) as non-reevaluable regardless of `reject_reason`, mirroring the existing special-case for `PreCommitted`.
- When constructing the fresh `BlockInfo` in `handle_block_proposal` (line 1654), preserve/carry forward fields that represent an irreversible local decision (`signed_self`, `state` once ≥ `LocallyAccepted`) instead of unconditionally rebuilding from `BlockProposal::from`.
- Ensure `reject_reason` is cleared whenever a block transitions out of a rejected state into `PreCommitted`/`LocallyAccepted`, so stale reconsiderable reasons cannot re-arm the reevaluation path after acceptance.

### Proof of Concept
1. Miner proposes block `B` at height `h`; signer rejects it for a reconsiderable reason (`reject_reason` = X, reevaluable) — [3](#0-2) .
2. Conditions change; miner re-proposes the identical `B`. `should_reevaluate_block` returns `true` (reason X still reevaluable), fresh evaluation runs, block validates, signer marks it `LocallyAccepted` and signs it — assuming `reject_reason` is not cleared on this transition, it remains X.
3. Miner re-proposes the identical `B` a third time. `should_reevaluate_block` again sees the stale reconsiderable `reject_reason` and returns `true` even though `state == LocallyAccepted` and `signed_self` is set.
4. `handle_block_proposal` executes `BlockInfo::from(block_proposal.clone())` [4](#0-3) , producing a fresh `Unprocessed`/`signed_self=None` record, which is persisted via `insert_block` [5](#0-4) , erasing the local record that this signer already signed block `B` at height `h`.
