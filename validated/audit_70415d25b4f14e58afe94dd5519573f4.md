### Title
Multisig2 `delete_member` fails to purge a removed member's existing confirmations on other requests, allowing execution below the configured `K`-of-`N` threshold - (`File: multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` decides whether to execute a pending request purely by counting entries in the `self.confirmations` map for that `request_id` and comparing against `self.num_confirmations` [1](#0-0) . `delete_member`, which is used to remove a member from `self.members` (revoking their access key/authorization), only deletes *requests originally created by* that member — it never scans other pending requests' `confirmations` sets to strip out confirmations that member previously gave [2](#0-1) . As a result, a removed member's stale confirmation continues to count toward the threshold on any request they confirmed but did not create, letting the multisig execute a `Transfer` (or other) action with fewer *live* authorized confirmations than `num_confirmations` requires.

### Finding Description
The contract enforces its K-of-N custody guarantee via the binding:
`confirmations.get(request_id).len() == count of confirmations from members currently present in self.members`.

- `self.members` is the authoritative "currently trusted signer" set [3](#0-2) .
- `self.confirmations` is a separate `LookupMap<RequestId, HashSet<String>>` that records which member strings confirmed a given request, independent from `self.members` [4](#0-3) .
- `confirm()` trusts `confirmations.len()` directly against `num_confirmations` without ever re-validating that each recorded confirmer is still in `self.members` [5](#0-4) .
- `delete_member()` only removes `self.requests` entries whose `r.member == member` (i.e., requests *created* by the removed member), and only removes `num_requests_pk` for that member. It performs no cleanup of `self.confirmations` entries where that member appears as a confirmer of a request created by someone else [2](#0-1) .

Once a member is removed (e.g., because they are believed compromised, left the organization, or their key was rotated), any confirmation they previously placed on a still-pending, not-yet-executed request remains valid data in `self.confirmations` and is still counted by `confirm()`. This breaks the equality between "confirmations recorded" and "confirmations from members currently entitled to grant them," which is exactly the custody binding the K-of-N scheme is supposed to preserve — analogous to the OrbitChain bug where output was authorized against records that were no longer bound to genuine, currently-valid state.

### Impact Explanation
This crosses an authorization/threshold boundary: a `Transfer` (or `AddKey`/`FunctionCall`/etc.) request can be executed with only `K-1` (or fewer) confirmations from members who are actually still part of the multisig, because a stale confirmation from a removed member is silently counted as if it were live. This falls under the Critical impact category "a multisig request executed below threshold," since NEAR held by the multisig account can be moved (or a full-access key added) without truly meeting the configured signer quorum.

### Likelihood Explanation
The precondition — a member confirms a request, then is later removed via `DeleteMember` while that request is still pending/unconfirmed to completion — is a normal, foreseeable multisig lifecycle event (rotating out a departing signer or one whose key is suspected compromised). No redeploy, no owner-only bypass, and no assumption that the deployment ignored documented initialization is required; it is a direct consequence of the `confirm`/`delete_member` code as shipped. A malicious former member who anticipates their own removal can also deliberately pre-confirm high-value pending requests to guarantee their "vote" persists after they are kicked out.

### Recommendation
In `delete_member`, iterate over all pending `self.requests`/`self.confirmations` entries (not just ones created by the removed member) and remove the removed member's string from every confirmation set. Alternatively, have `confirm()` re-validate, at count time, that every entry in `confirmations.get(&request_id)` still corresponds to a member present in `self.members`, only counting live members toward the threshold.

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C, D], 3)` (3-of-4 multisig) [6](#0-5) .
2. `A` calls `add_request` to create a `Transfer{amount}` request `R1`; `B` and `C` call `confirm(R1)` — `self.confirmations[R1] = {B, C}`, not yet executed (2 < 3) [1](#0-0) .
3. Separately, `A`, `B`, `D` execute a `DeleteMember{C}` request that reaches 3 confirmations and removes `C` from `self.members` — but `R1`'s confirmations set still contains `"C"` because `delete_member` only scanned requests created by `C` [2](#0-1) .
4. `D` calls `confirm(R1)`. `confirmations.len() + 1 == 3 == num_confirmations`, so `execute_request` fires the `Transfer` [7](#0-6) , even though only `B` and `D` are currently live members who actually authorized it — one confirmation short of the real, current 3-of-4 threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
