Confirmed: `Prod` is the default build mode [1](#0-0) , so official/production Chainlink node binaries have `build.IsProd()==true`, and `RunJobV2` immediately rejects with an error before ever looking at `jobID` [2](#0-1) .

### Title
EI-authenticated request can trigger job runs for arbitrary job IDs (not just the bound job) on non-production builds - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` authenticates a request using only the EI access-key/secret pair but then sets the generic `SessionUserKey` to a `User{Role: UserRoleRun}` object [3](#0-2) , which is indistinguishable from a real user session to `GetAuthenticatedUser`. `PipelineRunsController.Create` uses only this `isUser` boolean — not the EI's job binding — to decide whether to call `RunJobV2` with the attacker-supplied numeric `jobID` from the URL [4](#0-3) . There is no check anywhere that the authenticated EI's `ExternalInitiator` record is associated with the requested job.

### Finding Description
Route wiring: `POST /v2/jobs/:ID/runs` is registered in the `userOrEI` group, authenticated via `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`, then wrapped with `auth.RequiresRunRole` [5](#0-4) .

`AuthenticateExternalInitiator` looks up the `ExternalInitiator` by access key, verifies the secret, and — regardless of which job(s) that EI is configured to trigger — sets the session user role to `Run` [6](#0-5) . `RequiresRunRole` only checks that role is not `View`, so it passes [7](#0-6) .

Inside `PipelineRunsController.Create`, the code comments state "only users are allowed to run jobs using int IDs - EIs not allowed," but the check `_, isUser := auth.GetAuthenticatedUser(c)` returns `true` for EI-authenticated requests too, because `AuthenticateExternalInitiator` populates the same `SessionUserKey` with a `*clsessions.User` value [8](#0-7) . The handler then parses the URL `:ID` as an `int32` and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly, with **no lookup or comparison against the authenticated `ExternalInitiator`'s bound job/spec** [9](#0-8) . Thus an EI credential legitimately issued for job A can be used to trigger a run of any other job B by supplying B's numeric ID, since the authorization check is role-based (`Run`) rather than resource-scoped.

However, `RunJobV2`'s implementation begins with a hard gate: `if build.IsProd() { return 0, errors.New("manual job runs not supported on secure builds") }`, with an explicit comment "Only used for local testing, not supported by the UI" [2](#0-1) . `Prod` is the default build mode unless overridden with a `dev`/`test` build tag [1](#0-0) . Since standard, officially-distributed Chainlink node binaries are built in `Prod` mode, this code path is unreachable and the endpoint always fails before any job-run logic executes, for any caller (real user, EI, or otherwise).

### Impact Explanation
On a real (production-built) Chainlink node, this is **not exploitable**: `RunJobV2` unconditionally errors out on `build.IsProd()`, so the authorization gap in `PipelineRunsController.Create` (missing EI-to-job binding check) can never be reached to actually trigger an unauthorized run. The bug only manifests on nodes built with the `dev` build tag or in `go test` binaries, which are not production node deployments and fall outside the "real node compromise" scope of this audit (this is closer to a defense-in-depth/logic flaw in a dev-only diagnostic feature, not a live exploitable authorization bypass on a running node).

### Likelihood Explanation
Zero on standard production nodes, since the gating check in `RunJobV2` unconditionally blocks the vulnerable code path regardless of role or EI/job binding. The flaw would only be reachable if an operator intentionally builds and deploys a `dev`-tagged binary in production, which is a misconfiguration/build-choice scenario explicitly out of scope per the audit rules.

### Recommendation
Not required for production security, since the code path is already disabled via `build.IsProd()`. If desired for defense-in-depth, `PipelineRunsController.Create` should distinguish EI-authenticated sessions from real user sessions (e.g., check `GetAuthenticatedExternalInitiator` and reject, or validate that the EI's associated job/spec matches the requested `:ID`) rather than relying solely on the coarse `Run` role, and the misleading comment ("only users are allowed... EIs not allowed") should be corrected to match actual enforced behavior.

### Proof of Concept
Not applicable as an exploitable production vulnerability — a handler-level Go test confirming the block would look like: build the test binary normally (`build.IsProd()==true` by default for `go test` unless a `dev` tag is used — note `IsTest()` is a separate mode from `IsProd()`, so actual test binaries may not hit the `IsProd()` branch; a full verification would require confirming under which build tag `go test` runs and would need explicit code reading of `mode` assignment, which was not found in the indexed files). Given the residual uncertainty (see below), no concrete production-exploitable PoC applies.

### Uncertainty note
I could not locate the code that sets the `mode` variable in `core/build/build.go` (e.g., via `-ldflags` or `_test.go` init) within the indexed files, so I cannot fully confirm whether `go test`-run integration tests hit `IsProd()==true` or a different mode. This does not change the conclusion for real deployed nodes (default `Prod` mode), but affects only how a PoC test would be constructed in this repo's test environment.

	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
