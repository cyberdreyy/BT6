**Analysis confirming the security property holds:**

`RuntimeExt` is defined with a fixed, non-aliasing set of fields — `trie_update`, `receipt_manager`, `account_id: AccountId`, `account: Account`, `action_hash`, `data_count`, `epoch_id`, `block_height`, `epoch_info_provider`, `current_protocol_version`, `storage_access_mode`, `trie_access_tracker`, `storage_proof_size_before_receipt` [1](#0-0) . Both `account_id` and `account` are owned values (not references, indices, or maps keyed by other accounts), so a single `RuntimeExt` instance can only ever represent exactly one account for the lifetime of the call.

`RuntimeExt::new` receives `account: Account` by value from `action_function_call`, where it is constructed via `account.clone()` from the `account: &mut Account` parameter tied to `account_id` [2](#0-1) . The `VMContext.storage_usage`/`account_balance`/`account_locked_balance` fields are populated from `runtime_ext.account()`, which simply returns `&self.account` [3](#0-2) [4](#0-3) .

After the VM runs, only the write-back path `account.set_amount(outcome.balance); account.set_storage_usage(outcome.storage_usage);` applies the outcome — and it applies it to the exact same `account: &mut Account` reference (same `account_id`) that was cloned in, not to any other account [5](#0-4) .

There is no field on `RuntimeExt` that holds a reference, handle, or key referring to a different account's `Account`/storage record — `account_id` and `account` are singular, owned, non-aliasing values scoped to the receiver of the current `FunctionCall` action. Therefore no direct-write vector exists in this file for a contract to observe or mutate a third-party account's `storage_usage` through `VMContext`. This is a confirmation of correct design, not a vulnerability.
