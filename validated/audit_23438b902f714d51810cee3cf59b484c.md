### Title
Unchecked ERC-4626 `maxDeposit` lets a direct token sender block epoch startup - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower._depositToVault` forwards the entire on-hand balance to the configured ERC-4626 vault in one `deposit` call without checking `vault.maxDeposit(address(this))` or splitting the amount into permitted chunks. [1](#0-0) 

During `IdleCDOEpochVariant.startEpoch`, surplus pool funds are transferred to the programmable borrower and `_startEpochProgrammableBorrower` invokes its `onStartEpoch` hook. [2](#0-1)  `onStartEpoch` then attempts to deposit the borrower adapter’s complete underlying balance into the external vault. [3](#0-2) 

An unprivileged user can directly transfer underlying tokens to `ProgrammableBorrower` so that its balance exceeds the vault’s per-call or remaining deposit limit; alternatively, a depositor can consume the external vault’s remaining capacity. The next `startEpoch` call then reverts and rolls back the entire epoch transition.

### Finding Description
ERC-4626 exposes `maxDeposit` specifically because a vault may impose deposit restrictions and revert when the supplied amount is too large. [4](#0-3)  The EIP also permits `deposit` to revert when the full amount cannot be accepted because of a deposit limit. [5](#0-4) 

`ProgrammableBorrower` treats the external vault as an unconditionally accepting sink:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol
uint256 shares = vault.deposit(_assetAmount, address(this));
``` [1](#0-0) 

There is no `maxDeposit` query, minimum calculation, partial-deposit loop, or fallback that leaves only the excess amount on hand.

The vulnerable sequence is:

1. A vault is configured with `depositLimit` or `maxDeposit` equal to `D`.
2. An attacker directly sends `D + 1` underlying to `ProgrammableBorrower`, or normal user deposits make its balance greater than `D`.
3. A lender deposits into the CDO while it is in the buffer phase.
4. An honest owner or manager calls `startEpoch`.
5. `startEpoch` sends the surplus to the programmable borrower and calls its start hook. [2](#0-1) 
6. `onStartEpoch` calls `_depositToVault` with the borrower adapter’s entire on-hand balance. [6](#0-5) 
7. The external vault rejects `balance > maxDeposit`, reverting the hook and therefore all of `startEpoch`.

Because the attacker’s direct transfer remains in `ProgrammableBorrower`, every retry that uses the same vault and the same limit also reverts. The existing approval logic does not constrain the amount, and there is no donation-skimming path in `ProgrammableBorrower`; `_depositToVault` deliberately uses the complete ERC-20 balance. [7](#0-6) 

### Impact Explanation
Epoch startup can be temporarily frozen. All user principal intended for the epoch remains locked in the pre-start state while `ProgrammableBorrower` holds more underlying than the configured vault accepts.

For example, if a MetaMorpho-style vault or another ERC-4626 wrapper has a remaining deposit capacity of `100_000 USDC`, and pool funds plus a donation make the adapter balance `100_001 USDC`, then `startEpoch` repeatedly reverts. The attacker only needs to donate the incremental `1 USDC` when pool funds already equal the limit, or deposit into the external vault to reduce its remaining capacity below the amount swept by `onStartEpoch`.

This is a direct availability failure of the credit vault: lenders cannot have the epoch started, borrower capital cannot be deployed through the normal programmable-borrower path, and pending epoch operations cannot progress until governance changes the vault, the external vault raises capacity, or sufficient capacity is otherwise restored. `setVault` can be used only while accounting is inactive and no old vault shares remain, so a donated-cash condition can persist across retries even though the honest manager may eventually switch to another vault. [8](#0-7) 

### Likelihood Explanation
The condition is realistic because ERC-4626 explicitly supports receiver-specific and global deposit caps, and `ProgrammableBorrower` is designed to park all undrawn revolving-credit capital in an external ERC-4626 vault. [9](#0-8) 

The attacker does not need a privileged role: an ordinary direct token transfer to `ProgrammableBorrower` is enough when the current pool balance is already near the vault’s deposit ceiling. Where the limit is a remaining-capacity cap rather than a fixed per-call cap, an ordinary deposit into the external vault can also consume capacity immediately before the manager’s `startEpoch` transaction.

The failure does not depend on borrower misbehavior, malformed oracle data, or a malicious vault. A correctly implemented, honest ERC-4626 vault is allowed to revert when the requested deposit exceeds its current limit.

### Recommendation
Cap each vault deposit by the live ERC-4626 limit and leave the remainder on hand rather than reverting:

```solidity
uint256 maxAssets = vault.maxDeposit(address(this));
uint256 depositAmount = _assetAmount > maxAssets ? maxAssets : _assetAmount;
if (depositAmount != 0) {
    uint256 shares = vault.deposit(depositAmount, address(this));
    emit DepositedIntoVault(depositAmount, shares);
}
```

Accounting should continue to use the pre-deposit asset baseline, so `epochStartVaultAssets` should remain based on on-hand cash plus current vault assets rather than assuming every on-hand token entered the vault. [10](#0-9) 

If `maxDeposit` is unavailable or returns zero, `onStartEpoch` should still succeed and begin accounting with the funds held as cash; `availableToBorrow` already includes both the underlying balance and current vault assets. [11](#0-10) 

For defense in depth, consider a privileged recovery function that can sweep unsolicited underlying donations out of `ProgrammableBorrower`, or explicitly account for donated cash before calling `vault.deposit`.

### Proof of Concept
Add this mock and test to `test/foundry/ProgrammableBorrowerCreditVault.t.sol`. The mock models an ERC-4626 vault enforcing a deposit cap:

```solidity
contract MockCappedDepositVault is MockStopEpochLiquidityVault {
  uint256 public depositLimit = type(uint256).max;

  constructor(address _asset) MockStopEpochLiquidityVault(_asset) {}

  function setDepositLimit(uint256 assets) external {
    depositLimit = assets;
  }

  function maxDeposit(address) external view returns (uint256) {
    return depositLimit;
  }

  function deposit(uint256 assets, address receiver)
    external
    returns (uint256 shares)
  {
    require(assets <= depositLimit, "max-deposit");
    uint256 assetsBefore = assetToken.balanceOf(address(this));
    uint256 supply = totalSupply();
    shares = supply == 0 || assetsBefore == 0
      ? assets
      : assets * supply / assetsBefore;
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }
}
```

The test places the pool in buffer phase, donates enough underlying to exceed the vault cap, and shows that `startEpoch` cannot complete:

```solidity
function testStartEpochRevertsWhenVaultMaxDepositExceeded() external {
  MockCappedDepositVault cappedVault =
    new MockCappedDepositVault(USDC);
  uint256 poolDeposit = 10_000 * oneScale;
  uint256 depositCap = poolDeposit + 1;

  cappedVault.setDepositLimit(depositCap);

  vm.prank(owner);
  cdoEpoch.setIsInterestMinted(true);

  vm.prank(manager);
  programmableBorrower.setVault(address(cappedVault));

  // Attacker is an arbitrary direct token sender.
  address attacker = makeAddr("attacker");
  deal(USDC, attacker, 2, true);
  vm.prank(attacker);
  underlying.transfer(address(programmableBorrower), 2);

  // Normal lender supplies pool principal while the CDO is in buffer phase.
  idleCDO.depositAA(poolDeposit);

  uint256 borrowerBalance =
    underlying.balanceOf(address(programmableBorrower));
  assertEq(borrowerBalance, 2, "attacker donation is held on hand");

  // startEpoch transfers poolDeposit to ProgrammableBorrower, then
  // onStartEpoch tries to deposit poolDeposit + 2 in one call.
  vm.expectRevert("max-deposit");
  vm.prank(manager);
  cdoEpoch.startEpoch();

  assertFalse(
    cdoEpoch.isEpochRunning(),
    "epoch startup is blocked"
  );
  assertFalse(
    programmableBorrower.epochAccountingActive(),
    "borrower accounting did not start"
  );

  // The donation remains on hand, so every retry through the same vault fails.
  vm.expectRevert("max-deposit");
  vm.prank(manager);
  cdoEpoch.startEpoch();
}
```
