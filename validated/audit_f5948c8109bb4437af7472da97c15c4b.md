### Title
Rotating/deleting an API token via NewAPIToken/DeleteAPIToken does not invalidate the user's existing browser session cookie - ([File: core/web/user_controller.go])

### Summary
`UserController.NewAPIToken` and `UserController.DeleteAPIToken` only mutate the user's API token (via `SetAuthToken`/`DeleteAuthToken`) and never call `ClearNonCurrentSessions`. A previously stolen session cookie remains valid via `AuthenticateBySession` after the legitimate user rotates or deletes their API token, contrary to the reasonable expectation that "revoking access" invalidates all outstanding credentials.

### Finding Description
`AuthenticateBySession` (`core/web/auth/auth.go:55-71`) authenticates purely by looking up the session ID stored in the cookie against `AuthorizedUserWithSession`; it has no dependency on the user's API token/access key. `NewAPIToken` (`core/web/user_controller.go:244-286`) and `DeleteAPIToken` (`core/web/user_controller.go:289-330`) only call `SetAuthToken`/`DeleteAuthToken` on the `AuthenticationProvider` — there is no call to `DeleteUserSession` or `ClearNonCurrentSessions`. By contrast, `UpdatePassword` (`core/web/user_controller.go:202-241`) calls `u.updateUserPassword`, which is the only code path that invokes `ClearNonCurrentSessions` (confirmed via `grep` — the sole non-test/non-interface caller is in `user_controller.go`). Consequently, if an attacker has obtained a valid session cookie (e.g., via XSS, malware, or a leaked cookie) and the legitimate user believes they've revoked the attacker's access by rotating their API token, the stolen session cookie continues to authenticate indefinitely, and the attacker can continue performing all actions available to that session (which is not the API token) via `/v2/*` session-authenticated routes.

### Impact Explanation
This matches a "credential revocation is not honored" issue: a user-initiated remediation action (rotating/deleting an API token) fails to revoke an active, stolen browser session, allowing continued impersonation of the victim's account and role (up to admin, depending on the victim's role) through session-cookie-authenticated endpoints. This is a real authorization/session-management gap, though it is scoped to the case where the attacker already possesses a valid session cookie (a precondition, not something granted by this bug itself).

### Likelihood Explanation
Precondition: attacker must already possess a valid, unexpired session cookie for the victim (e.g., stolen via XSS or malware) — this is the same precondition needed to exploit any session-cookie based attack, and is explicitly the threat model named in the question. Once that precondition holds, the bug is deterministic and 100% reproducible: no additional guessing, timing, or race condition is needed — the stale session simply continues to work after `NewAPIToken`/`DeleteAPIToken` is called.

### Recommendation
Call `ClearNonCurrentSessions` (or `DeleteUserSession` for all sessions of that user) from `NewAPIToken` and `DeleteAPIToken` in `core/web/user_controller.go`, consistent with the behavior already implemented for `UpdatePassword`, so that rotating or deleting the API credential also invalidates other active sessions for that user (excluding, if desired, the current session for `NewAPIToken`/`DeleteAPIToken` since those are typically called from an authenticated session rather than API token).

### Proof of Concept
Go handler-level integration test (extending `core/web/user_controller_test.go`):
1. Start app, log in via HTTP client to obtain session cookie `session1` (as `cltest.NewApplicationEVMDisabled` + `app.NewHTTPClient` does).
2. Call `client.Get("/v2/config")` (or any authenticated `/v2/*` GET route) using `session1` cookie and assert `200 OK`, proving `session1` is valid via `AuthenticateBySession`.
3. Call `POST /v2/user/token` with the correct password using `session1`, and assert `201 Created` (mirrors `TestUserController_NewAPIToken`).
4. Replay the exact same `session1` cookie against `/v2/config` (or `auth.AuthenticateBySession` directly, calling `AuthorizedUserWithSession(ctx, sessionID)` with the sessionID extracted from `session1`) and assert whether it still returns `200 OK`.
5. Expected (buggy) result: request in step 4 still succeeds with `200 OK`, proving the old session was not invalidated by API token rotation.
6. Repeat steps 1–5 substituting `POST /v2/user/token/delete` for `DeleteAPIToken`, with the same expected outcome.
7. As a contrast/control, repeat with `PATCH /v2/user/password` (`UpdatePassword`) instead of `NewAPIToken`, and assert that the old session cookie now fails (`401 Unauthorized`) — demonstrating the parity gap between the two revocation paths.
