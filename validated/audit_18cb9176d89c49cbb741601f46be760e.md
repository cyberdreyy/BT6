## Analysis

**The binding to check:** For every successful `withdraw`/`withdraw_all` call, `account.unstaked_after = account.unstaked_before - amount` AND `last_total_balance_after = last_total_balance_before - amount` should equal `contract_actual_near_balance_after = contract_actual_near_balance_before - amount` (i.e., the accounted decrease must match an actual NEAR outflow to the entitled `account_id`).

**Code path:** [1](#0-0) 

`internal_withdraw` reads `account_id = env::predecessor_account_id()`, asserts `account.unstaked >= amount` and the epoch delay, then **synchronously** decrements `account.unstaked`, saves the account, decrements `self.last_total_balance`, and only afterward schedules `Promise::new(account_id).transfer(amount)`. There is no callback (`.then(...)`) checking `is_promise_success()` to roll back state if the transfer receipt fails — unlike `withdraw_from_staking_pool`/`on_staking_pool_withdraw` flows in the lockup contract which do use callbacks.

**Does the Transfer receipt actually fail?**
- Per NEAR protocol semantics (as the question states), a `Transfer` action targeting a 64-hex implicit account always succeeds because the runtime auto-creates the account. So for implicit accounts, this path cannot fail — the premise in the question is correct for that case.
- For **named accounts**, a `Transfer` action to an account that no longer exists does fail (`AccountDoesNotExist`), and the deposit is refunded back to the *sender* of that receipt — i.e., back to the staking-pool contract's own balance, not lost to the network. So the divergence that would occur is: `account.unstaked` and `last_total_balance` are permanently reduced while the actual NEAR silently returns to the pool contract's balance (as unaccounted surplus).

**Who can trigger the named-account failure, and does anyone gain?**
`account_id` in `internal_withdraw` is always `env::predecessor_account_id()` — the caller itself. There is no way to withdraw on behalf of another account. So the only way to make the target account "not exist" at receipt time is for that same caller to delete their own account (via a `DeleteAccount` action, which requires a full-access key they legitimately hold on their own account) in the narrow window between the `withdraw` function call and the async `Transfer` receipt landing.

This means:
- The "victim" of the lost claim and the party who caused the failure (by self-deleting) are the same account — there is no unprivileged attacker extracting value from another party.
- The pool's real balance is left with an unaccounted surplus (in the pool's favor), not a loss out of the pool to an unentitled party.
- This is self-inflicted griefing with no attacker gain, and does not match any of the listed Critical/High impact categories (no NEAR leaves the pool to an unentitled party, no early release of locked funds, no owner-fee misattribution, no multisig bypass).

Per the audit rules, "griefing with no attacker gain" is explicitly out of scope, and this scenario provides no gain to any party at another's expense — it can, at most, cause the self-deleting caller to lose their own claimed withdrawal, with the pool contract accidentally retaining a small refunded surplus.     pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }
