### Title
Unchecked u64 subtraction in `operator_fee_refund` can underflow/panic on gas accounting inputs - (File: `crates/common/evm/src/l1block.rs`)

### Summary
`L1BlockInfo::operator_fee_refund` computes the gas actually used via a raw (non-`checked_`/non-`saturating_`) subtraction `gas.limit() - (gas.remaining() + gas.refunded() as u64)`, unlike virtually every other arithmetic operation in this codebase's fee/gas-accounting paths, which consistently uses `checked_*`, `saturating_*`, or explicit error returns (see the EIP-8130 `settle_fees`/`prepay` functions and `charge_upfront` guards elsewhere in the same crate family).

### Finding Description [1](#0-0) 

The function is:
```rust
pub fn operator_fee_refund(&self, gas: &Gas, spec_id: BaseSpecId) -> U256 {
    ...
    let operator_cost_gas_used = self.operator_fee_charge_inner(
        U256::from(gas.limit() - (gas.remaining() + gas.refunded() as u64)),
        spec_id,
    );
    operator_cost_gas_limit.saturating_sub(operator_cost_gas_used)
}
```
This is called from `reimburse_caller` in `crates/common/evm/src/handler.rs` (line 240) after every non-deposit transaction's execution, on every block, for every transaction — a directly reachable, unprivileged path from a single signed transaction. `gas.remaining()` and `gas.refunded()` are derived from EVM execution and are influenced by the calling transaction's bytecode/refund behavior (e.g. SSTORE clear refunds under EIP-3529). If `gas.remaining() + (gas.refunded() as u64)` can ever exceed `gas.limit()` — whether via a latent bug elsewhere in refund accounting, an edge case in the EIP-8037 reservoir/spill mechanics that this fork has added on top of upstream revm (see the reservoir/spill logic exercised in `handler.rs` tests around lines 536-584), or a future regression during a refactor — this subtraction underflows. In a release build without `overflow-checks`, this silently wraps to a value near `u64::MAX`; in a debug/checked build it panics.

This mirrors the reported flatmoney bug class exactly: an unguarded integer subtraction on state derived from cumulative accounting (funding fees / gas refunds) that assumes a safety invariant ("subtraction never underflows") without enforcing it via checked arithmetic, unlike the disciplined `checked_add`/`checked_sub` pattern used throughout the rest of the fee-settlement code in this same repository (e.g. `crates/common/evm/src/eip8130.rs:1566-1585`).

### Impact Explanation
If the underflow occurs, the wrapped huge `u64` is converted via `U256::from(...)` and fed into `operator_fee_charge_inner`, producing an enormous fee amount that is fed into `operator_cost_gas_limit.saturating_sub(operator_cost_gas_used)`. Because it's `saturating_sub`, the *direct* outcome is clamped to zero (the caller loses their legitimate operator-fee refund) rather than an unbounded mint — this bounds the blast radius compared to the original Solidity bug, where an unguarded cast produced an astronomically large balance. However, if built with debug/overflow-checked assertions (common in CI, test networks, or a misconfigured release profile), the raw `-` panics, which would halt block execution for any node processing that specific transaction — a consensus-node-halt / potential chain-split scenario if only some nodes in the network are built with overflow checks enabled and others are not.

### Likelihood Explanation
Likelihood is moderate-to-low: under normal EIP-3529 refund accounting invariants (refund ≤ used_gas/5, and used_gas = limit − remaining), the subtraction should not underflow in practice, so this is defense-in-depth rather than a demonstrated exploitable path today. I was not able to fully verify all invariants of the upstream `Gas`/`GasTracker` type (from `revm`) governing `remaining()` and `refunded()` under this fork's added EIP-8037 reservoir/spill mechanics, so I cannot rule out an edge case where the invariant is violated.

### Recommendation
Replace the raw subtraction with checked arithmetic that fails safe (matching the pattern used in `crates/common/evm/src/eip8130.rs`), e.g.:
```rust
let gas_used = gas
    .remaining()
    .saturating_add(gas.refunded().max(0) as u64)
    .min(gas.limit());
let operator_cost_gas_used = self.operator_fee_charge_inner(
    U256::from(gas.limit().saturating_sub(gas_used)),
    spec_id,
);
```
or return an explicit error/log if the invariant is violated, rather than allowing silent wraparound or an unguarded panic.
