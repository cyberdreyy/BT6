### Title
Unbounded/Stuck `blockSubscribe` Notification Loop When `get_complete_block` Permanently Fails for a Slot - (File: rpc/src/rpc_subscriptions.rs)

### Summary
The `notify_watchers` function that services `blockSubscribe` pubsub clients tracks per-subscription progress with a single pointer, `last_notified_slot`, that is advanced **only** on the success path of `blockstore.get_complete_block()`. If that call ever returns an `Err` for a given slot (e.g., the slot was cleaned up / pruned from the blockstore, or any other error condition), there is no alternate path to advance the pointer, so the subscription becomes permanently stuck at that slot and re-attempts the same failing range of slots on every subsequent commitment notification, indefinitely. This mirrors the TON Gateway bug class: a monotonic progress counter with exactly one increment path, whose failure blocks all future progress that depends on it.

### Finding Description
In `rpc/src/rpc_subscriptions.rs`, the `Block` branch of `notify_watchers` computes the range of slots to notify from `w_last_unnotified_slot` to the current `slot`, then iterates and fetches each block: [1](#0-0) 

```
let mut w_last_unnotified_slot = subscription.last_notified_slot.write().unwrap();
if *w_last_unnotified_slot == 0 { *w_last_unnotified_slot = slot; }
let mut slots_to_notify: Vec<_> = (*w_last_unnotified_slot..slot).collect();
...
for s in slots_to_notify {
    if s > max_complete_transaction_status_slot.load(Ordering::SeqCst) { break; }
    let block_update_result = blockstore.get_complete_block(s, false)...;
    match block_update_result {
        Ok(block_update) => {
            ...
            *w_last_unnotified_slot = s + 1;   // <-- the ONLY place last_notified_slot advances
        }
        Err(err) => {
            // we don't advance `w_last_unnotified_slot` so that it'll retry on the next notification trigger
            notifier.notify(..., RpcBlockUpdate { slot: s, block: None, err: Some(err) }, ..., false);
        }
    }
}
```

The comment on the error path explicitly documents the intended retry behavior: [2](#0-1) . There is exactly one code path (`Ok(block_update)`) that increments `w_last_unnotified_slot`; every other outcome leaves it unchanged. If `get_complete_block(s, false)` returns a persistent error for slot `s` — for example because that slot has already been purged from the blockstore by the ledger cleanup service (yielding `BlockstoreError::SlotCleanedUp` or similar) — the pointer can never advance past `s`. On every subsequent bank/commitment notification, `slots_to_notify` is recomputed as `(w_last_unnotified_slot..slot)`, which grows without bound as `slot` keeps advancing, and the block-fetch attempt (plus `bank.proper_ancestors_set()` computation) is redone for the same permanently-failing slot and the ever-growing tail of subsequent slots on every tick.

This is directly analogous to the TON Gateway's `handle_withdrawal()` nonce increment: a single function is the only place that advances a monotonically-tracked position, and any failure prior to that increment blocks all future progress dependent on it, indefinitely.

### Impact Explanation
`notify_watchers` runs for every commitment-slot notification (multiple times per second) and iterates all matching subscriptions in parallel via `subscriptions.into_par_iter()` on the shared RPC PubSub notification thread pool: [3](#0-2) . A single `blockSubscribe` client that ends up stuck on a purged/failing slot causes recurring, ever-growing recomputation of the `slots_to_notify` range and repeated calls into the blockstore on every subsequent notification tick, consuming CPU/blockstore I/O on the shared notification thread pool for as long as the subscription remains open. Because the pool and worker threads are shared across all block/account/program/log/signature subscribers, this degrades or starves notification delivery to other RPC pubsub clients — an availability impact triggered by a single low-rate client action (one `blockSubscribe` call plus naturally occurring ledger cleanup), consistent with the "unbounded cost for a single low-rate call" acceptance criterion.

### Likelihood Explanation
`blockSubscribe` is gated behind `--rpc-pubsub-enable-block-subscription` and `--enable-rpc-transaction-history`, so it is not on by default, but once enabled by an operator, it is reachable by any unprivileged RPC pubsub client: [4](#0-3) . The failure condition (a subscription's `last_notified_slot` falling behind the blockstore's retained/first-available block due to ledger cleanup, a slow consumer, or a transient blockstore error) is a normal operational condition, not something requiring privileged access — it can occur simply from a client subscribing early and then being slow to keep up while the ledger-cleanup service purges older slots.

### Recommendation
Add an explicit recovery path so that a permanent per-slot failure cannot indefinitely stall the subscription's progress pointer, analogous to the Solana Gateway's `increment_nonce`/TON Gateway fix referenced in the report. For example: after a bounded number of retries or when the failing slot falls below `get_first_available_block()`, advance `w_last_unnotified_slot` past the unrecoverable slot (optionally still emitting the error notification) so subsequent, fetchable slots are not permanently blocked, and cap the recomputation cost of `slots_to_notify` regardless of how far the subscription has fallen behind.

### Proof of Concept
1. Enable `--enable-rpc-transaction-history` and `--rpc-pubsub-enable-block-subscription` on a validator.
2. Open a `blockSubscribe` websocket subscription with `commitment: confirmed` (or `finalized`).
3. Ensure the client is not immediately advanced by keeping `last_notified_slot` at an old slot (e.g., subscribe just before a burst of slot advancement), then let the ledger cleanup service purge that slot from the blockstore, causing `get_complete_block` to return an `Err` for it (mirrors `err` handling shown in the test harness at [2](#0-1) ).
4. Observe that on every subsequent commitment notification, `notify_watchers` recomputes and retries the same failing slot plus a growing tail of subsequent slots for that subscription — `w_last_unnotified_slot` never advances past the failing slot, per the single-increment-path logic at [5](#0-4) .
