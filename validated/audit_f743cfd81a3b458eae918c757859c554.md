### Title
Anyone can overwrite the vault APR while `idleCDO` is unset, letting an unprivileged attacker force a borrower default or zero out LP yield - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setApr()` explicitly skips its only access-control check while `idleCDO == address(0)`. Because the comment in the code acknowledges this window "can happen only during the setup", the intent was to let the deployer configure APR — but the check skips authorization for *everyone*, not just the owner/manager. This is the exact analog of the kernel bug: `mtk_dp_aux_transfer()` dereferenced the `drm` device before the bridge was attached; here, `setApr`/`setAprs`/`setAprsWithBuffer` mutate APR-critical state before the CDO (the "attachment") is wired via `setWhitelistedCDO`. An unprivileged EOA can front-run the wiring transaction and poison `lastApr`/`unscaledApr`, which then drives `expectedEpochInterest` and the borrower's repayment obligation for the entire first epoch.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol` (lines 225-235):

```solidity
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
  }
```

When `idleCDO == address(0)` (i.e. between `initialize()` and `setWhitelistedCDO()`, the standard factory flow in `IdleCreditVaultFactory.sol`), any caller can invoke:

- `setApr(_apr)` — sets `lastApr` up to `maxApr` (default `DEFAULT_MAX_APR = 20e18`, line 89-90)
- `setAprs(_unscaledApr, _apr)` — also sets `unscaledApr` (line 206-210)
- `setAprsWithBuffer(...)` — same, with buffer scaling (line 217-220)

This poisoned `lastApr` is then consumed as the source of truth:

1. `IdleCDOEpochVariant._additionalInit()` calls `_setScaledApr(_getStrategyApr())`, which reads `lastApr` and rescales it by `(epochDuration + bufferPeriod) / epochDuration` (`IdleCDOEpochVariant.sol:89`, `544-546`). An attacker must pick `_apr` so the rescaled value stays under `maxApr` (e.g. `17e18` → `19.83e18` at 30d/5d defaults) so initialization does not revert.
2. `startEpoch()` computes `expectedEpochInterest = pendingWithdrawFees + _calcInterest(getContractValue())` using the poisoned scaled APR (`IdleCDOEpochVariant.sol:260-262`).
3. `stopEpoch()` pulls `expectedEpochInterest + pendingWithdraws` from the borrower via `getFundsFromBorrower` (`IdleCDOEpochVariant.sol:408`). If the borrower approved only the honest APR interest, the transfer fails and `_handleBorrowerDefault` fires (`IdleCDOEpochVariant.sol:501-505`), marking `defaulted = true`, pausing the contract, and disabling withdraw requests (`IdleCDOEpochVariant.sol:577-599`).

Two concrete attack outcomes:

- **Yield theft (APR → 0):** attacker sets `unscaledApr = lastApr = 0`. `_calcInterest` returns 0, `expectedEpochInterest ≈ pendingWithdrawFees` only, borrower repays principal only, and all LPs lose the full epoch interest (≈ agreed APR × TVL × 35/365). Loss is directly quantified.
- **Forced default / fund freeze (APR → near-max):** attacker sets `lastApr` just below the post-scaling `maxApr` bound. Borrower's honest approval is insufficient at `stopEpoch`; `getFundsFromBorrower` reverts → `defaulted = true`, deposits/withdrawals/requests disabled, and funds are frozen until a manual `finalizeDefault` recovery flow. All lender principal sits locked (temporary freezing; potential losses if recovery < par).

None of the guards stop this: `maxApr` only bounds the value, `onlyOwner`/`_onlyIdleCDO` are bypassed by the `idleCDO == 0` branch, KYC (`isWalletAllowed`) is not checked, and honest roles never need to call `setApr` again for the attack to persist (the CDO reads `lastApr` itself at init).

### Impact Explanation
Direct quantified loss in the zero-APR variant: all epoch interest owed to AA and BB lenders (e.g. ~17% annualized × TVL × 35/365 ≈ 1.6% of TVL for a single epoch) is never accrued — borrowers legally repay principal only, an unrecoverable yield loss since `lastEpochInterest`/`expectedEpochInterest` are computed on-chain. In the max-APR variant: forced `defaulted` state permanently closes the epoch (`epochDuration = 0` path is not even needed — `setEpochParams`, `startEpoch`, `requestWithdraw` all gate on `defaulted`), freezing 100% of lender principal until governance executes `finalizeDefault`, with haircut risk if the recovery source funds less than the full basis.

### Likelihood Explanation
The vulnerable window is a single deployment gap, but it is the *standard* deployment path: `IdleCreditVaultFactory` initializes the strategy with `idleCDO = 0` and only later calls `setWhitelistedCDO`. The attacker needs only a mempool/front-running or any-lateral call in that window — no capital, no KYC, no role. Whether the poisoned APR survives depends on the operator not explicitly calling `setAprs` after CDO wiring; the code's own comment shows the APR passed to `initialize()` is expected to be authoritative ("on the first setup we set the lastApr equal to the unscaledApr", line 144-146), so silent overwrite is realistic. Attack cost is gas only; payoff is an entire epoch of borrower interest or the ability to force a default event on demand.

### Recommendation
When `idleCDO == address(0)`, require `msg.sender == owner() || msg.sender == manager` instead of skipping the check entirely:

```solidity
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    if (_cdo == address(0)) {
      if (msg.sender != owner() && msg.sender != manager) revert NotAllowed();
    } else {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    ...
}
```

Alternatively, have `initialize()`/`setWhitelistedCDO` set `idleCDO` atomically in the same factory transaction, and consider emitting an event on APR changes so operators can detect pre-attach manipulation.
