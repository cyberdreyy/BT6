Found a solid analog in the multisig2 contract: stale confirmations from removed members remain counted toward the confirmation threshold.

## Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing request execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in [1](#0-0)  only purges pending requests that were *created* by the member being removed; it never scans the `confirmations` map to strip that member's confirmation entry from *other* pending requests they had previously confirmed. `confirm()` in [2](#0-1)  then executes a request purely by comparing `confirmations.len()` against `num_confirmations`, without verifying that every recorded confirmer is still a current member. This is the same class of bug as the reported `BondBaseSDA.setIntervals` issue: a mutating admin action (`setIntervals` changing tuning params / here `DeleteMember` changing the member set) fails to update a dependent cached value (`meta.tuneBelowCapacity` / here the `confirmations` set), so stale state is later used as if it were still valid.

### Finding Description
- `members: UnorderedSet<MultisigMember>` is the source of truth for who is currently allowed to confirm, as seen in `current_member()` [3](#0-2) .
- Confirmations are stored per-request as a `HashSet<String>` keyed by the member's serialized identity, populated in `confirm()`.
- `delete_member` removes the member from `members`, deletes their `num_requests_pk` entry, and deletes any request that member *authored*, but leaves any *confirmation they cast on someone else's still-pending request* untouched: [4](#0-3) .
- `confirm()` computes `confirmations.len() as u32 + 1 >= self.num_confirmations` to decide whether to execute the request immediately, with no re-validation that the existing entries in `confirmations` still correspond to members present in `self.members`: [5](#0-4) .

As a result, once a member is removed, any confirmation they previously cast on a pending, not-yet-executed request continues to count toward the threshold forever, even though that identity is no longer trusted.

### Impact Explanation
This breaks the intended equality: `confirmations counted == confirmations from currently live members`. A pending `Transfer`, `AddKey`, `FunctionCall`, etc. request can be pushed over the `num_confirmations` threshold using one or more confirmations from accounts/keys that have since been removed from the multisig (e.g., because they were compromised or the org removed that signer). This is exactly the "multisig request executed below threshold" Critical impact category, since the request executes with fewer genuine current-member approvals than the configured `num_confirmations` requires, potentially moving NEAR or granting access keys without the actual quorum of live members' consent.

### Likelihood Explanation
No privileged attacker action or foundation/owner assistance is required beyond normal multisig operation: a request being confirmed by some members, followed later by a routine `DeleteMember` action (a normal governance action any multisig can legitimately perform, e.g. rotating out a departing or compromised signer) while that earlier request is still pending. This is a realistic sequence in any long-lived multisig with churn in its member set and multiple in-flight requests, which the contract explicitly supports (`active_requests_limit`, `REQUEST_COOLDOWN`).

### Recommendation
When removing a member in `delete_member`, iterate over all pending requests' `confirmations` sets (not just those authored by the removed member) and strip the removed member's entry, or alternatively, in `confirm()`, recompute the effective confirmation count by intersecting `confirmations` with the current `members` set before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize multisig2 with `num_confirmations = 3`, `members = {A, B, C, D}`.
2. `A` calls `add_request_and_confirm(R)` where `R` transfers funds to an arbitrary receiver → `confirmations[R] = {A}`.
3. `B` calls `confirm(R)` → `confirmations[R] = {A, B}` (not yet at threshold: `1 + 1 < 3`).
4. Members execute a separate, already-fully-confirmed request with action `DeleteMember { member: B }` (e.g., because `B`'s key is suspected compromised). `delete_member` removes `B` from `self.members`, but `R`'s confirmations set still contains `B`.
5. `C` calls `confirm(R)`. Check: `confirmations[R].len() (2, still includes stale B) + 1 >= 3` → true → `R` executes with only `A` and `C` as genuine live-member approvals, i.e., below the real 3-of-N live threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Returns current member: either predecessor as account or if it's the same as current account - signer.
    fn current_member(&self) -> Option<MultisigMember> {
        let member = if env::current_account_id() == env::predecessor_account_id() {
            MultisigMember::AccessKey {
                public_key: env::signer_account_pk()
                    .try_into()
                    .unwrap_or_else(|_| env::panic_str("Failed to deserialize public key")),
            }
        } else {
            MultisigMember::Account {
                account_id: env::predecessor_account_id(),
            }
        };
        if self.members.contains(&member) {
            Some(member)
        } else {
            None
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
