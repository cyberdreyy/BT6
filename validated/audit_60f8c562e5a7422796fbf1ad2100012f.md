### Title
`check_latest_block_in_tenure` fails open (returns `Ok(true)`) on `get_tenure_tip` RPC error, allowing a tenure-change block to be treated as confirming its parent tenure without any positive canonicity evidence - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` (used to determine whether a tenure-change block confirms its expected parent tenure) queries `client.get_tenure_tip(tenure_id)` for tenures the local `signer_db` has no record of. When that RPC call errors for any reason, the code logs a warning and unconditionally returns `Ok(true)`, treating the proposal as "higher than the parent tenure" purely because the query failed, not because canonicity was verified.

### Finding Description
In `stacks-signer/src/chainstate/mod.rs`, after failing to find a locally known block for `tenure_id` in `signer_db`, the function falls through to: [1](#0-0) 

If `client.get_tenure_tip(tenure_id)` returns `Err(e)` — which can occur for a tenure the node itself doesn't have data for, or due to a transient node error — the function logs "Assuming proposal is higher than the parent tenure for now" and returns `Ok(true)` unconditionally. This return value flows into the parent-confirmation logic that determines `confirms_expected_parent`. The equality the audit examines — `confirms_expected_parent == true` must be backed by positive evidence that tenure `P`'s tip is canonical — is broken here: the `true` value is produced purely from the *absence* of an answer (an RPC error), not from any successful validation of `P`'s canonical tip.

An attacker who wins tenure `T` can set `prev_tenure_consensus_hash = P` for a tenure `P` that the local signer's `signer_db` has never recorded (e.g., a tenure the signer was offline for, or one that exists on a minority/non-canonical fork). This forces the DB-miss path down to the RPC call. If that call to the local node transiently errors (node busy, timeout, or if the node genuinely has no record of `P` because it's not canonical), the fallback fires and the check reports the parent tenure as confirmed with no canonicity check ever having occurred.

### Impact Explanation
This breaks the canonicity/validity guard that `check_tenure_change_confirms_parent` is meant to enforce before a signer signs a tenure-change block. If exploited, a signer could sign a tenure-change block whose parent tenure was never verified as canonical — a Critical chain-safety violation matching the "signing an invalid or non-canonical block" category. Because any single miner slot holder can trigger this by naming an unknown/uncertain parent tenure, and RPC calls transiently error under normal operational conditions (especially under node load, which an attacker might induce via other means), this is potentially repeatable across tenure changes.

### Likelihood Explanation
The precondition is a transient failure of `client.get_tenure_tip` for the specific parent tenure hash chosen by the attacker. This requires:
1. The attacker's own miner slot win at tenure `T` (single unprivileged slot, no majority-signer role needed).
2. Naming an unknown-to-local-DB parent tenure `P` in the tenure-change payload.
3. The RPC call to the local node for `P` failing at that moment (busy node, timeout, or node not yet caught up).

Item 3 is not fully attacker-controlled — it depends on the node's local state — so it is a probabilistic/opportunistic rather than fully deterministic exploit, but it does not require any privileged access, majority stake, or compromise of other signers; it only needs one slot and normal gossip of a block proposal, satisfying the threat model.

### Recommendation
Change the error-handling branch of `check_latest_block_in_tenure` (and any equivalent fallback in `check_tenure_change_confirms_parent`) to fail closed: on `client.get_tenure_tip` error, return `Ok(false)` (or propagate the error so the caller rejects/defers the proposal) rather than assuming the proposal confirms the parent tenure. Positive confirmation of `confirms_expected_parent` must require a successful, verified tenure tip lookup showing canonicity — never an RPC failure.
