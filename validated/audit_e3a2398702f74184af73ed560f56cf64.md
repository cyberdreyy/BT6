### Title
V1 chainstate's `validate_tenure_change_payload` fails to reject a competing tenure-change block when the prior block was only locally accepted - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
In `stacks-signer/src/chainstate/v1.rs`, `validate_tenure_change_payload` checks for a duplicate tenure-start block using `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` (line 505-509), which only returns a value once a block has reached global (majority) consensus. The v2 equivalent in `stacks-signer/src/chainstate/v2.rs::validate_tenure_change_payload` (line 344-348) instead calls `signer_db.get_last_signed_block`, which additionally accounts for blocks the signer has only locally accepted. This asymmetry lets a v1 signer sign a second, competing tenure-change block for the same tenure while the first block it already signed is still only locally accepted.

### Finding Description
The intended invariant is: at most one block should be signed per (tenure, height) by a given signer, enforced via the `RejectReason::DuplicateBlockFound` check in `validate_tenure_change_payload`.

In v1 (`stacks-signer/src/chainstate/v1.rs:505-518`):
```rust
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)
    ...
if let Some(last_in_current_tenure) = last_in_current_tenure {
    ...
    return Err(RejectReason::DuplicateBlockFound);
}
```
`get_last_globally_accepted_block` only returns `Some` for blocks whose `BlockState` has reached `GloballyAccepted` — i.e., a supermajority of signer weight signed it. A block that is only `LocallyAccepted` (this signer signed it, `signed_self` set, `signed_group` still `None`) is invisible to this query.

In v2 (`stacks-signer/src/chainstate/v2.rs:344-348`), the analogous check uses `get_last_signed_block`, whose comment explicitly states: "Only blocks we have signed (locally or globally accepted) count here." This is the correct check to prevent re-signing a conflicting block at the same tenure/height once this signer has already committed a signature to one.

Exploit flow:
1. Attacker wins a sortition/miner slot honestly with their own BTC.
2. Attacker proposes tenure-change Block A for tenure T. Under a live near-50/50 signer split, enough signers (including the victim signer) sign Block A, but it never reaches the global-acceptance threshold — it stays `LocallyAccepted` in the victim's `SignerDb`.
3. Attacker (or a colluding miner in the same slot window) proposes a second, distinct tenure-change Block B, also for tenure T (e.g., a different parent-tenure micro-fork or reorg attempt still satisfying `check_tenure_change_confirms_parent`/`check_parent_tenure_choice`).
4. The victim signer runs `validate_tenure_change_payload` for Block B. Because Block A is only `LocallyAccepted`, `get_last_globally_accepted_block(T)` returns `None`, so the `DuplicateBlockFound` rejection never fires.
5. All other checks (parent tenure match, `check_tenure_change_confirms_parent`, `check_parent_tenure_choice`) can independently pass since Block B is a legitimate competing tenure-start with a different signer-signature-hash but the same declared parent tenure.
6. The victim signer signs Block B, producing two distinct signed tenure-start blocks in the same tenure at the same height — an equivocation.

This is achievable by an unprivileged single-slot attacker with gossip access alone; no majority of signers, no compromised keys, and no node access are required. The precondition of a near-50/50 live split is a normal network condition, not a privileged capability.

### Impact Explanation
This breaks the uniqueness/equivocation-guard safety property that the duplicate check exists to enforce: at most one block signed per (tenure, height) by any given signer. A signer producing two valid signatures over conflicting tenure-start blocks at the same tenure/height is a Critical chain-safety violation — it can be combined with signatures from other signers (who saw only Block A or only Block B) to potentially assemble two competing globally-accepted chains for the same tenure, and it also constitutes signer equivocation that undermines any downstream slashing/accountability assumption for equivocating signers. This is repeatable across tenures whenever the split condition recurs.

### Likelihood Explanation
Requires: (1) a live near-50/50 signer split so that a legitimately-signed block by the victim stalls at `LocallyAccepted` rather than reaching global acceptance, and (2) an attacker capable of proposing a second competing tenure-change block for the same tenure. Both conditions are within reach of a single unprivileged miner-slot holder with gossip access — network splits happen naturally under normal signer-set disagreement/latency, and crafting a second `BlockProposal` requires no special privilege. No majority of signers, no keys, no auth_token, no node/local access needed. The attack is repeatable any time this split condition recurs.

### Recommendation
Change v1's `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, matching the v2 semantics, so that a locally-accepted (signed but not yet globally accepted) block for the tenure also triggers `RejectReason::DuplicateBlockFound` for any subsequent competing tenure-change proposal.

### Proof of Concept

fn v1_duplicate_block_check_misses_locally_accepted() {
    // Setup: signer_db, SortitionsView with cur_sortition for tenure T
    // 1. Insert Block A for tenure T into signer_db with BlockState::LocallyAccepted
    //    (i.e., signed_self = Some(ts), signed_group = None)
    // 2. Construct Block B: a distinct tenure-change block for the same tenure T,
    //    same prev_tenure_consensus_hash, satisfying check_tenure_change_confirms_parent
    //    and check_parent_tenure_choice.
    // 3. Call sortitions_view.validate_tenure_change_payload(&proposed_by, &tenure_change_b, &block_b, &mut signer_db, &client)

    // ASSERTION (bug in v1): result is Ok(()) -- NOT Err(RejectReason::DuplicateBlockFound)
    assert!(result.is_ok());

    // Contrast: run the equivalent v2 GlobalStateView::validate_tenure_change_payload
    // with the same LocallyAccepted Block A in signer_db.
    // ASSERTION (v2 correct behavior): result is Err(RejectReason::DuplicateBlockFound)
    let v2_result = GlobalStateView::validate_tenure_change_payload(
