### Title
Reorg-permission timing check uses each signer's own local clock, letting a miner split the signer set into conflicting accept/reject decisions on a tenure reorg - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a new tenure is allowed to reorg (supersede) a prior tenure that already produced a signed block, based on comparing two **locally observed, per-signer wall-clock timestamps**: the time this signer's SignerDb recorded receiving the new sortition's burn block, and the time this signer approved the earlier tenure's first block. That comparison is not derived from any canonical/consensus-anchored value, so different signers, observing the same sequence of network events at different times (ordinary latency, or timing deliberately induced by the miner), can reach opposite conclusions about whether the reorg is "poorly timed" (and thus permitted) or not.

### Finding Description
`check_parent_tenure_choice` is reached from both `v1::validate_tenure_change_payload` and `v2::validate_tenure_change_payload` via `check_tenure_change_confirms_parent`, i.e. it runs during proposal validation on every signer that receives a tenure-change block: [1](#0-0) [2](#0-1) 

Inside the function, for each reorged tenure with an already-mined first block, the signer computes:

```
proposal_to_sortition = sortition_state_received_time - approved_at
if proposal_to_sortition < first_proposal_burn_block_timing:
    // treat as "poorly timed", ALLOW the reorg (mark tenure superseded)
else:
    // reject the reorg
``` [3](#0-2) 

Both `sortition_state_received_time` (from `signer_db.get_burn_block_receive_time`, populated when *this* signer's node relays a new burn block to *this* signer) and `approved_at` (`local_block_info.approved_time`, stamped when *this* signer pre-committed to the earlier block) are purely local observations — each signer records them independently, at the moment they individually receive the relevant events. Neither is a value that other signers, the miner, or the node agree on; there is no canonical, consensus-visible timestamp being compared.

Because the whole point of `first_proposal_burn_block_timing` is to distinguish "the prior tenure had a fair chance to build more blocks before this sortition" from "the prior tenure's first block barely beat the next sortition", the correctness of the check depends on all signers agreeing on this classification. But since each signer's `proposal_to_sortition` value is a function of that signer's own network/propagation timing (how fast the earlier block propagated to it vs. how fast the new sortition announcement reached it), a miner who controls the broadcast/propagation timing of their own blocks (a capability any single sortition-winning miner naturally has) can arrange for:
- a subset of signers to see a `proposal_to_sortition` below the threshold (reorg looks "poorly timed" → permitted, tenure gets marked superseded and their earlier signature ceases to block the new tenure via `record_superseded_tenure` / `mark_tenure_superseded`), while
- another subset of signers (who received the earlier block sooner, or the new sortition later) compute a value at or above the threshold and correctly refuse the reorg, keeping their signature over the earlier tenure "live."

The result is a split within the signer set on which tenure is legitimate: some signers will go on to sign the new tenure-change block (superseding the old tenure), while others will reject it and continue to defend the previously signed block. If the miner can concentrate enough weight on the "permit" side (still short of a bare majority, since normal signer-set weight thresholds still apply per rule constraints, but sufficient combined with normal signer non-participation/latency variance to reach the 70% signing threshold on the *new* chain while the old chain also retains signatures), the protocol can end up with two chains each carrying valid-looking signer endorsements for a period, i.e. a `signer signing a conflicting block` scenario driven entirely by an attacker manipulating message timing rather than by controlling a majority of keys.

### Impact Explanation
This breaks the safety equality that all honest signers must agree on which tenure is canonical/permitted to reorg a previously-signed one. A miner (with only their own single winning slot, i.e. no signer key compromise and no signer majority) can, purely through selective/delayed gossip of their own blocks, cause some signers to treat an equally-valid prior tenure as "poorly timed" and thus permit a supersede, while other signers refuse it — producing divergent, conflicting signing decisions across the honest signer set on the same tenure fork. This matches the specified Critical impact class: "a signer signing an invalid/non-canonical/conflicting block."

### Likelihood Explanation
Likelihood is Medium: the attack requires no signer collusion, no majority of keys, and no auth token — only ordinary control over one's own block-propagation timing (broadcasting the same block, or delaying/staggering announcement of the next sortition-following tenure's block, to different peers), which is well within what a single miner naturally can do. The attack window is bounded by `first_proposal_burn_block_timing` (a config-tunable value, default in the seconds-to-tens-of-seconds range based on tenure timing config), so a miner must engineer natural or induced propagation-delay variance across signers that straddles this threshold — feasible but requires some care and does not reliably succeed against every signer set topology.

### Recommendation
Do not gate reorg-permission decisions on a per-signer local wall-clock timestamp comparison. Either:
- Derive `sortition_state_received_time` and the "proposal was late" determination from data that is canonical / agreed upon by the node (e.g., the burn block's own timestamp, or the previous tenure's first-block timestamp as recorded by the Stacks node rather than the signer's local receipt time), so every signer computing `check_parent_tenure_choice` derives the same verdict from the same inputs; or
- Require corroboration from the Stacks node (which has canonical burn/tenure timing data) rather than trusting the signer's own local receive/approve timestamps for a decision that must be consistent across the whole signer set.

### Proof of Concept
1. Miner M wins sortition for tenure T1 and mines its first (and, per the `globally_accepted_blocks > 1` guard, only) block B1.
2. M deliberately staggers propagation of B1: it reaches signers S1..Sk quickly (they pre-commit/approve at time `t_early`) and signers Sk+1..Sn slowly (they approve at `t_late`, close to when the next sortition happens).
3. M (or a colluding/independent next-slot winner) then wins the next sortition and proposes a tenure-change block T2 whose `prev_tenure_consensus_hash` points to a tenure prior to T1 (attempting to reorg T1 away), timed such that:
   - For S1..Sk: `sortition_state_received_time - t_early >= first_proposal_burn_block_timing` → `check_parent_tenure_choice` returns `false` at [4](#0-3) , and these signers reject T2 as `ReorgNotAllowed`.
   - For Sk+1..Sn: `sortition_state_received_time - t_late < first_proposal_burn_block_timing` → the code path at [5](#0-4)  classifies the reorg as permitted, marks T1 superseded via `record_superseded_tenure`, and these signers go on to sign T2.
4. If the "permit" subset happens to carry ≥70% weight, T2 (a conflicting tenure to the one B1's signers already endorsed) gets a valid signer certificate and is broadcast/accepted by the node, while a disjoint set of signers still holds a valid signature over B1's tenure — a concrete instance of the signer set producing signatures over two conflicting tenures for the same height range, driven purely by exploiting each signer's independent, non-canonical local timing measurement. [6](#0-5)

impl SortitionData {
    /// Check if the tenure defined by `sortition_state` is building off of an
    ///  appropriate tenure.
    ///
    /// A permitted reorg is recorded once the whole reorg is permitted: each tenure whose
    /// blocks this one is allowed to replace is marked superseded (see
    /// [`SignerDb::mark_tenure_superseded`]), so a signature we already placed on one of those
    /// blocks does not later block the replacement. The record carries this tenure's sortition
    /// as the permitting one, so the permit stops applying if a burnchain fork later orphans
    /// it. Nothing is recorded for a refused reorg, even for the tenures in it that
    /// individually qualified.
    pub fn check_parent_tenure_choice(
        &self,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        first_proposal_burn_block_timing: &Duration,
    ) -> Result<bool, SignerChainstateError> {
        // if the parent tenure is the last sortition, it is a valid choice.
        // if the parent tenure is a reorg, then all of the reorged sortitions
        //  must either have produced zero blocks _or_ produced their first (and only) block
        //  very close to the burn block transition.
        if self.prior_sortition == self.parent_tenure_id {
            return Ok(true);
        }
        info!(
            "Most recent miner's tenure does not build off the prior sortition, checking if this is valid behavior";
            "sortition_state.consensus_hash" => %self.consensus_hash,
            "sortition_state.prior_sortition" => %self.prior_sortition,
            "sortition_state.parent_tenure_id" => %self.parent_tenure_id,
        );

        let tenures_reorged =
            client.get_tenure_forking_info(&self.parent_tenure_id, &self.prior_sortition)?;
        if tenures_reorged.is_empty() {
            warn!("Miner is not building off of most recent tenure, but stacks node was unable to return information about the relevant sortitions. Marking miner invalid.");
            return Ok(false);
        }

        // this value *should* always be some, but try to do the best we can if it isn't
        let sortition_state_received_time =
            signer_db.get_burn_block_receive_time(&self.burn_block_hash)?;

        // Track which tenures are superseded by the reorg, then mark them in
        // the DB after the reorg is permitted.
        let mut superseded_tenures = Vec::new();
        for tenure in tenures_reorged.iter() {
            if tenure.consensus_hash == self.parent_tenure_id {
                // this was a built-upon tenure, no need to check this tenure as part of the reorg.
                continue;
            }

            // disallow reorg if more than one block has already been signed
            let globally_accepted_blocks =
                signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
            if globally_accepted_blocks > 1 {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already more than one globally accepted block.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => ?tenure.first_block_mined,
                    "globally_accepted_blocks" => globally_accepted_blocks,
                );
                return Ok(false);
            }

            let Some(first_block_mined) = &tenure.first_block_mined else {
                // The node saw no blocks in this tenure, so the reorg takes nothing away from
                // the canonical chain. We may still hold a signature over a block in it that
                // the node has never seen (a block we accept locally is not handed to the node
                // until the whole signer set has signed it), so the reorg must still be
                // recorded if it is permitted.
                superseded_tenures.push(tenure);
                continue;
            };
            let Some(local_block_info) =
                signer_db.get_first_approved_block_in_tenure(&tenure.consensus_hash)?
            else {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already mined blocks, and there is no local knowledge for that tenure's block timing.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => %first_block_mined,
                );
                return Ok(false);
            };

            let checked_proposal_timing = if let Some(sortition_state_received_time) =
                sortition_state_received_time
            {
                // how long was there between when the proposal was received and the next sortition started?
                let proposal_to_sortition = if let Some(approved_at) =
                    local_block_info.approved_time
                {
                    sortition_state_received_time.saturating_sub(approved_at)
                } else {
                    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
                    0
                };
                if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
                    info!(
                        "Miner is not building off of most recent tenure. A tenure they reorg has already mined blocks, but the block was poorly timed, allowing the reorg.";
                        "parent_tenure" => %self.parent_tenure_id,
                        "last_sortition" => %self.prior_sortition,
                        "violating_tenure_id" => %tenure.consensus_hash,
                        "violating_tenure_first_block_id" => %first_block_mined,
                        "violating_tenure_proposed_time" => local_block_info.proposed_time,
                        "new_tenure_received_time" => sortition_state_received_time,
                        "new_tenure_burn_timestamp" => self.burn_header_timestamp,
                        "first_proposal_burn_block_timing_secs" => first_proposal_burn_block_timing.as_secs(),
                        "proposal_to_sortition" => proposal_to_sortition,
                    );
                    superseded_tenures.push(tenure);
                    continue;
                }
                true
            } else {
                false
            };

            warn!(
                "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already mined blocks.";
                "parent_tenure" => %self.parent_tenure_id,
                "last_sortition" => %self.prior_sortition,
                "violating_tenure_id" => %tenure.consensus_hash,
                "violating_tenure_first_block_id" => %first_block_mined,
                "checked_proposal_timing" => checked_proposal_timing,
            );
            return Ok(false);
        }
        // Every reorged tenure cleared the rules, so the reorg is permitted.
        for tenure in superseded_tenures {
            self.record_superseded_tenure(signer_db, tenure);
        }
        Ok(true)
    }
