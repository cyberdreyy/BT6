### Title
Unrandomized top-bit pubkey bucket selection in disk-backed accounts index `BucketMap` enables attacker-grindable bucket collisions - ([File: bucket_map/src/bucket_map.rs])

### Summary
`BucketMap::bucket_ix`, which selects which top-level on-disk index bucket a `Pubkey` is routed to, uses the raw, un-hashed high bits of the pubkey directly, with no per-instance randomization. This is inconsistent with the sibling hashing function `Bucket::bucket_index_ix` in the same crate, which explicitly mixes in a locally-generated random seed "to make it hard for an attacker to deterministically cause all the pubkeys to land in the same location," and with `PubkeyBinCalculatorBuilder::with_bins`, which selects a random bit offset into the pubkey specifically to prevent attacker-predictable bin selection. The top-level bucket selector skips this mitigation entirely.

### Finding Description
`BucketMap::bucket_ix` computes the bucket for a pubkey as: [1](#0-0) 
```
pub fn bucket_ix(&self, key: &Pubkey) -> usize {
    if self.max_buckets_pow2 > 0 {
        let location = read_be_u64(key.as_ref());
        (location >> (u64::BITS - self.max_buckets_pow2 as u32)) as usize
    } else {
        0
    }
}
```
`read_be_u64` simply reinterprets the first 8 raw bytes of the pubkey as a big-endian integer, and the bucket index is derived from its top `max_buckets_pow2` bits — no hashing, no per-process secret, no salt.

This differs from two other pubkey→bucket/bin mechanisms in the same subsystem that were explicitly designed against attacker-chosen pubkeys:
- `Bucket::bucket_index_ix` (per-bucket index slot selection) uses `ahash::RandomState::with_seeds(random, random, random, random)` where `random` is generated per bucket at startup, precisely to defeat deterministic pubkey placement by an attacker: [2](#0-1) 
- `PubkeyBinCalculatorBuilder::with_bins` (the in-memory `AccountsIndex` bin selector) picks a random byte/bit offset via `rng().random_range(...)` for the same stated reason (to avoid deterministic grinding of pubkey bins): [3](#0-2) 

`BucketMap::bucket_ix` is the analogous "top of the tree" routing decision for the on-disk index (per the crate's `BucketMap` docstring, "mostly contention free concurrent map backed by MmapMut") but omits the randomization present in its sibling functions, using the raw pubkey bytes directly — the same class of bug as the reported `Yeetback.sol` issue, where a value that was supposed to be hashed/salted for uniform, unpredictable distribution is instead used raw, collapsing entropy and making the distribution attacker-predictable.

Because Solana account/program pubkeys (system-created accounts, PDAs via `find_program_address`, or freshly generated keypairs for new accounts) are attacker-controllable/grindable at negligible cost, an attacker can cheaply search for pubkeys whose leading bits collide within the same `max_buckets_pow2`-bit prefix, and then create/fund many accounts under such pubkeys.

### Impact Explanation
This affects `accounts-db`'s disk-index commit/indexing path, which the scope explicitly allows ("accounts-db commit and indexing"). If many attacker-created accounts are routed to the same physical on-disk bucket (rather than being spread across `max_buckets_pow2` buckets as intended), that bucket's `BucketStorage`/`Bucket` structures grow disproportionately, causing:
- Increased mmap growth/resize churn and lock/contention concentrated on a single bucket, degrading indexing throughput for the whole validator.
- Skewed search cost (`max_search()` linear probing within the affected bucket) for legitimate accounts that happen to hash near the same region, since collisions raise the "no space" resize frequency (`BucketMapError::IndexNoSpace`) and increase per-op probing.

This is a load-imbalance / performance-degradation vector on a component every validator relies on for account state tracking — a plausible ingest/processing-starvation vector rather than a direct fund-theft bug, consistent with the referenced report's own "Medium Risk" classification of the entropy-reduction bug class.

### Likelihood Explanation
Likelihood is moderate: the number of buckets (`max_buckets_pow2`, tied to `bins`/`BINS_DEFAULT` in `AccountsIndex::allocate_accounts_index`) is a small power of two (order of a few bits), so grinding a keypair or PDA whose leading `max_buckets_pow2` bits fall in a target bucket costs only ~`2^max_buckets_pow2` pubkey generations/hashes — trivially cheap with commodity hardware, and PDAs make this even easier since the attacker fully controls the seed/bump search space. No special privileges or leaked keys are required; only ordinary account creation is needed to populate a targeted bucket.

### Recommendation
Change `BucketMap::bucket_ix` to derive the bucket index from a randomized/keyed hash of the pubkey rather than raw bytes, consistent with `Bucket::bucket_index_ix`'s use of a per-process random seed (e.g., hash the pubkey with an `ahash`/keyed hasher seeded from a random value generated at `BucketMap::new`, then take the top bits of that hash for bucket selection), instead of `read_be_u64(key.as_ref())` on the raw pubkey.

### Proof of Concept
Conceptual PoC (cannot be executed without the running validator's live `max_buckets_pow2`/`bins` config, but the mechanism is directly demonstrated in-repo):
1. Observe that `bucket_ix` is deterministic and public in its formula: `top max_buckets_pow2 bits of pubkey (big-endian) → bucket index` (see `read_be_u64` combined with the shift in `bucket_ix`), with no secret/random component, unlike `bucket_index_ix`/`PubkeyBinCalculatorBuilder` which explicitly guard against this: [4](#0-3) 
2. An attacker locally iterates `solana_pubkey::new_rand()` (or PDA seeds) offline, computing `bucket_ix` for a chosen `max_buckets_pow2` (e.g., 5, giving 32 buckets) until finding pubkeys whose top 5 bits match a specific target value — costing on average `2^5 = 32` tries per matching pubkey, entirely offline and free of any network interaction.
3. The attacker submits ordinary `CreateAccount`/`AllocateWithSeed`/PDA-owning-program transactions to instantiate large numbers of accounts using only these pre-ground pubkeys.
4. All such accounts route to the same `BucketMap` bucket via `get_bucket`/`bucket_ix` (`bucket_map/src/bucket_map.rs` lines 184-190), concentrating index growth/resizes and probe-search contention onto that single bucket while the other buckets remain comparatively empty, degrading indexing performance disproportionately for a given number of created accounts compared to an ideal uniform distribution.

Note: I was unable to directly confirm the exact default `bins`/`max_buckets_pow2` value used in production configuration within the available index (searches only surfaced `BINS_DEFAULT` references without resolving its numeric value), so the precise grinding cost (bits to match) could not be fully pinned down from the indexed context alone.

/// Look at the first 8 bytes of the input and reinterpret them as a u64
fn read_be_u64(input: &[u8]) -> u64 {
    assert!(input.len() >= std::mem::size_of::<u64>());
    u64::from_be_bytes(input[0..std::mem::size_of::<u64>()].try_into().unwrap())
}
