### Title
Loss-adjusted funding haircut in `collectWithdrawFunds` only applies to the current request epoch — older unclaimed withdraw receipts still pay at par and drain the haircut pool - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The erofs bug is a *logical length > physical length* validation failure: a structure claims more data than was physically recorded. The analog in `IdleCreditVault` is `collectWithdrawFunds`: when `stopEpochWithDuration` realizes a loss, the funded `_amount` is haircut against the **aggregate** `pendingWithdraws` basis (all epochs' receipts), but the haircut ratio is stored under a **single** key, `lossRecoveryPriceByEpoch[epochNumber]`. Receipts whose `lastWithdrawRequest` points at an earlier epoch never see that ratio and are paid 1:1 through `_claimFundedWithdrawRequest`, so their logical claim length exceeds the physical funded extent.

### Finding Description
- `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * 1e18 / pendingBasis` where `pendingBasis = pendingWithdraws` is the sum of *all* outstanding receipts, regardless of request epoch, then zeroes `pendingWithdraws` and stores the price only under `lossRecoveryPriceByEpoch[epochNumber]` (`IdleCreditVault.sol:411-421`).
- On claim, `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol:789-800`). A user whose last request was made in an earlier epoch gets `lossRecoveryPrice == 0`, falls through to `_claimFundedWithdrawRequest`, and is paid the full `withdrawsRequests[_user]` amount at par via `_transferFundedClaim` (`IdleCreditVault.sol:319-349`, `897-907`).
- `requestWithdraw` explicitly permits a user to hold/refresh receipts across epochs ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests", `IdleCreditVault.sol:323-325`), so multi-epoch `pendingWithdraws` aggregation is a normal state, not an edge case. The block at `IdleCreditVault.sol:263-270` only stops *new* requests once the user's *own latest* epoch already carries a loss price; it does not reprice pre-existing older receipts.

### Impact Explanation
Broken invariant: one receipt one payout / fair loss socialization. The borrower funds `pendingToFund = pendingBasis - pendingLoss` (`previewLossAdjustedWithdrawFunds`, `IdleCreditVault.sol:440-459`), i.e., the physical extent is short by `pendingLoss`. Older-epoch claimants withdraw their full par receipt anyway, so current-epoch haircut claimants (and any other funded claims sharing the strategy balance) recover less than `lossRecoveryPrice` or nothing — the shortfall is paid out of other users' funded claims. Quantified loss: `oldEpochReceipts * (1 - lossRecoveryPrice)` is paid in excess of funding; equivalently current-epoch claimants lose up to that amount. An unprivileged lender can also *choose* to be on the winning side by leaving an early request unclaimed, then claiming first after the loss-adjusted stop.

### Likelihood Explanation
Requires (a) a stop epoch with `_lossAmount > 0` (honest manager/borrower default-adjacent loss path `stopEpochWithDuration`), and (b) at least one unclaimed receipt from an earlier epoch in `pendingWithdraws` — both routine states. No privileged misbehavior is needed; the claim order determines who is made whole.

### Recommendation
Apply `lossRecoveryPrice` to *every* outstanding receipt included in `pendingBasis`, not only the current epoch: e.g., store a global "funding ratio" consumed by `_claimFundedWithdrawRequest`, or track funded-vs-basis so `_transferFundedClaim` pays `receipt * fundedAmount / pendingBasis` pro rata for all epochs touched by the underfunded stop. Alternatively, reject partial funding whenever `pendingWithdraws` contains receipts older than `epochNumber` (impractical) — the correct fix is epoch-agnostic pricing of the haircut bucket.

// SPDX-License-Identifier: UNLICENSED
// Fork-style PoC sketch against the repo's existing Foundry harness.
function testLossHaircutSkippedForOlderEpochReceipt() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // Alice (epoch N-1): deposit + requestWithdraw, then does NOT claim.
    address alice = makeAddr("alice");
    _depositWithUser(alice, amount, true);
    vm.prank(alice);
    cdoEpoch.requestWithdraw(0, address(AAtranche));   // lastWithdrawRequest[alice] = N-1

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch()); // epoch N-1 funded at par

    // Bob (epoch N): deposit + requestWithdraw in the next buffer.
    address bob = makeAddr("bob");
    _depositWithUser(bob, amount, true);
    vm.prank(bob);
    cdoEpoch.requestWithdraw(0, address(AAtranche));   // lastWithdrawRequest[bob] = N
    _startEpochAndCheckPrices(1);

    // Manager stops epoch N with a realized loss -> collectWithdrawFunds(_amount < pendingBasis).
    // pendingBasis aggregates BOTH alice's (N-1) and bob's (N) receipts, but the haircut
    // price is stored only under lossRecoveryPriceByEpoch[N].
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(_lossAmount, 0);

    uint256 stratBal = underlying.balanceOf(address(strategy));

    // Alice claims FIRST: her lastWithdrawRequest epoch has no lossRecoveryPrice,
    // so _claimFundedWithdrawRequest pays her full par receipt.
    vm.prank(alice);
    cdoEpoch.claimWithdrawRequest();

    // Bob's claim should be basis * lossRecoveryPrice, but the strategy balance was
    // already drained above the funded amount by Alice's par payout.
    vm.prank(bob);
    cdoEpoch.claimWithdrawRequest(); // receives less than lossRecoveryPrice * basis, or reverts
    assertLt(underlying.balanceOf(address(strategy)), 0 + remainingExpected);
}
