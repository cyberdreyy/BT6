### Title
Unauthenticated flood of `web_api_trigger` requests causes oldest-first eviction in `pruneCallbacks` to silently drop a victim's pending callback, causing permanent loss of their response - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores every incoming trigger request's callback in `h.savedCallbacks` keyed by `MessageId` with no allowlist or rate-limiting (explicitly noted as a `TODO` in the code), and the periodic `pruneCallbacks` eviction sorts entries strictly by `createdAt` and deletes the oldest half whenever the map exceeds `MaxSavedCallbacks`. An attacker able to reach the gateway's user HTTP endpoint can submit a large volume of cheaply-signed, distinct-`MessageId` requests to inflate `savedCallbacks` past `MaxSavedCallbacks`, causing a victim's older, still-pending legitimate callback to be evicted before the DON node responds, permanently losing the victim's `SendResponse` invocation.

### Finding Description
`gateway.ProcessRequest` routes any incoming legacy request (keyed by `DonId`) to `handler.HandleLegacyUserMessage` after only syntactic validation (`msg.Validate()`), with no per-user allowlist or quota check at this stage [1](#0-0) . Inside `HandleLegacyUserMessage`, the handler validates payload shape/timestamp/method but explicitly punts on authorization: `// TODO: apply allowlist and rate-limiting here` [2](#0-1) . It then unconditionally inserts the request's callback into the shared map: [3](#0-2) 

`pruneCallbacks`, run on a timer, first removes expired entries, then — if the map still exceeds `MaxSavedCallbacks` — sorts **all** remaining entries (attacker's and victims' alike) ascending by `createdAt` and deletes the oldest `len(entries)-maxSize/2` entries regardless of ownership: [4](#0-3) 

Because eviction is purely time-ordered with no notion of "requester" or fairness, an attacker who submits a burst of `MaxSavedCallbacks`+N distinct-`MessageId` `web_api_trigger` requests immediately after a victim's legitimate (older) request is registered will cause the victim's entry to be deleted from `savedCallbacks` during the next prune cycle, before the corresponding node response (`handleWebAPITriggerMessage`) arrives and looks it up: [5](#0-4) 

When the DON node's response eventually arrives, `msg.Body.MessageId` no longer exists in `savedCallbacks` (`found == false`), so `savedCb.SendResponse(...)` is never called for the victim — the victim's original HTTP request stalls until `callback.Wait(ctx)` times out in `gateway.ProcessRequest`, effectively denying/losing their response. No signature check, rate limiter, or role check in this code path distinguishes callers or protects one user's pending entry from another user's flood; `h.nodeRateLimiter` only rate-limits node→gateway outgoing messages, not user→gateway trigger submissions.

### Impact Explanation
This is a cross-user denial-of-service / response-loss: an unprivileged flood from one user (attacker) can cause a completely unrelated legitimate user's (victim's) in-flight web API trigger request to silently fail with no error surfaced to the victim beyond an eventual timeout. This matches the "isolation" invariant class — one user's flood should not be able to destroy another user's pending request/callback — and corresponds to Chainlink's cross-user denial-of-service / response-confusion impact bucket. It does not grant fund movement, key disclosure, or privilege escalation, so its severity is bounded to availability/loss-of-service for the victim's specific request.

### Likelihood Explanation
Feasibility is high: the attacker needs no elevated role, no allowlist membership beyond being able to reach the gateway's user-facing port, and no expensive resource (each request only needs a cheap signature and distinct `MessageId`, and `MessageId` uniqueness is trivially attacker-controlled). The `TODO: apply allowlist and rate-limiting here` comment confirms the intended mitigation is not yet implemented. Given `defaultMaxSavedCallbacks = 20000`, flooding this many trigger requests in a short window (before a target node responds) is well within reach of a scripted attacker, making this reliably repeatable.

### Recommendation
- Implement the allowlist/rate-limiting explicitly marked as a `TODO` in `HandleLegacyUserMessage` before accepting/storing callbacks, so a single sender cannot flood `savedCallbacks`.
- Change `pruneCallbacks` eviction policy so it does not evict purely by global age irrespective of requester; e.g., cap `savedCallbacks` entries per-sender/per-key and evict per-sender oldest-first, or reject new insertions (return an error to the new caller) once the map is at capacity instead of evicting older, still-pending entries belonging to other users.
- Alternatively, prioritize eviction of expired-but-not-yet-answered entries from suspected abusive senders (e.g., via per-IP/per-key counters) rather than a single global time-sorted cut.

### Proof of Concept
Go unit test plan added to `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `MaxSavedCallbacks = N` (e.g., 10) via `NewHandler`.
2. Seed `h.savedCallbacks` with one "victim" entry with `createdAt = now - 1*time.Minute` and a callback whose `SendResponse` sets a flag/records invocation.
3. Seed `h.savedCallbacks` with `N` "attacker" entries all with `createdAt = now` (newer than the victim), each with distinct `MessageId`s and no-op callbacks.
4. Call `h.pruneCallbacks()` directly.
5. Assert: the victim's `MessageId` key is no longer present in `h.savedCallbacks` (evicted) even though it was the oldest and still pending, i.e. `len(h.savedCallbacks) == N/2` and does not include the victim id — confirming victim entry does not survive despite it being the legitimate, currently-pending request the attacker should not be able to affect.
6. (End-to-end variant) Call `HandleLegacyUserMessage` for the victim first, then call it repeatedly with attacker payloads until count exceeds `MaxSavedCallbacks`, invoke `pruneCallbacks`, then simulate `HandleNodeMessage` for the victim's `MessageId` and assert `victimCallback.SendResponse` is never invoked (i.e., `found == false` in `handleWebAPITriggerMessage`).

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
