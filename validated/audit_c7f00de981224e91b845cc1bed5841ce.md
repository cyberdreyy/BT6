### Title
Orchestrated batch epoch transitions are not fail-safe: one vault's external-call failure reverts the entire cluster - (File: contracts/IdleCreditVaultManagerOrchestrator.sol)

### Summary
`IdleCreditVaultManagerOrchestrator.startEpoch` and `stopEpochWithDuration` loop over multiple credit vaults and call `cdo.startEpoch()` / `cdo.stopEpochWithDuration(...)` directly, with no try/catch or per-vault isolation. This is the exact analog of `RootManager.propagate`: a batch of calls into external/dependent contracts where a single failure reverts the whole transaction. In this codebase the "untrusted third-party" is the ERC4626 vault backing each `ProgrammableBorrower`: `onStopEpoch` reverts `StopEpochVaultLiquidityUnavailable` when `vault.withdraw` fails, and that revert bubbles up through `IdleCDOEpochVariant._stopEpoch` and the orchestrator loop, rolling back every other vault's epoch transition in the same batch.

### Finding Description
- `stopEpochWithDuration` iterates `_actions` and calls `cdo.stopEpochWithDuration(op.newApr, op.interest, op.duration, op.loss)` unconditionally; any revert aborts the loop and rolls back all previously stopped vaults [1](#0-0) .
- `startEpoch` has the same structure: `cdo.startEpoch()` per vault, no isolation [2](#0-1) .
- Inside `IdleCDOEpochVariant._stopEpoch`, the programmable-borrower hook is invoked as `IProgrammableBorrower(_borrower()).onStopEpoch(...)`, and "hook reverts bubble" by design [3](#0-2) .
- `ProgrammableBorrower.onStopEpoch` calls the external ERC4626 vault and reverts `StopEpochVaultLiquidityUnavailable` whenever `vault.withdraw` throws, even though the vault economically covers the shortfall [4](#0-3) .
- Similarly, `onStartEpoch` unconditionally calls `_depositToVault`, which performs `vault.deposit` on the external ERC4626; a paused or deposit-limited vault bricks `startEpoch` [5](#0-4) .

An unprivileged user of the shared ERC4626 vault can time a liquidity-draining withdrawal (or rely on the vault's own withdrawal cap / paused state) so that `vault.withdraw(shortfall, ...)` reverts at exactly the block where the operator submits the cluster batch. One vault's transient ERC4626 failure then reverts the entire `stopEpochWithDuration` / `startEpoch` transaction.

### Impact Explanation
Temporary freezing of funds across every healthy vault in the cluster. `stopEpoch` is what fulfills pending withdraw requests (`collectWithdrawFunds`) and accrues epoch interest; while the batch keeps reverting, all vaults remain past `epochEndDate`, `requestWithdraw` receipts cannot be claimed, and lenders' assets stay locked. As in the Connext report, the system only recovers after manual intervention — the operator must discover the failing vault, and the owner must remove it via `setCreditVaultAllowed` or resubmit a batch excluding it. The blast radius grows with the number of orchestrated vaults, matching the original report's scaling concern. Loss magnitude: all pending withdraws plus accrued-but-unsettled interest across the cluster, for the duration of the freeze.

### Likelihood Explanation
Medium. Triggering requires no privilege: any holder of the shared ERC4626 vault can withdraw liquidity, and many real ERC4626 vaults (Morpho/GAUNTLET-style, used in the repo's own fork tests) impose `maxWithdraw` limits or can pause. A single brittle vault in the registry is enough to DoS the whole batch, and the revert is indistinguishable from a transient failure, so it can be repeated each time the operator resubmits. The operator can work around it by excluding the vault, but that mirrors the report's "manually removes the problematic connector" remediation — the fail-safety gap remains.

### Recommendation
Make the batch loops fail-safe per vault: wrap `cdo.startEpoch()` / `cdo.stopEpochWithDuration(...)` in try/catch, emit a failure event carrying the vault and revert reason, and continue with the remaining actions (or provide a `skipOnFailure` flag so the operator can opt into atomicity). Per-vault external dependencies should not be allowed to veto the cluster's epoch lifecycle.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultManagerOrchestrator} from "../contracts/IdleCreditVaultManagerOrchestrator.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {ProgrammableBorrower} from "../contracts/strategies/idle/ProgrammableBorrower.sol";
import {IERC4626} from "../contracts/interfaces/IERC4626.sol";

/// Two vaults in one cluster. Vault B's programmable borrower parks funds in an
/// ERC4626 vault. A vault user drains withdrawable liquidity so B's
/// onStopEpoch -> vault.withdraw(shortfall) reverts
/// StopEpochVaultLiquidityUnavailable (see testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable
/// in test/foundry/ProgrammableBorrowerCreditVault.t.sol for the single-vault revert primitive).
contract OrchestratorNotFailSafeTest is Test {
    IdleCreditVaultManagerOrchestrator orchestrator;
    IdleCDOEpochVariant cdoA; // healthy vault
    IdleCDOEpochVariant cdoB; // vault whose ProgrammableBorrower uses the shared ERC4626
    IERC4626 externalVault;   // ERC4626 backing cdoB's borrower
    address operator = address(0x0P);
    address vaultUser = address(0xA77); // unprivileged user of the ERC4626 vault

    function testOneBadVaultRevertsEntireBatch() external {
        // setup: both epochs running, epochEndDate passed, both have pendingWithdraws
        vm.warp(cdoA.epochEndDate() + 1);

        // Attacker (any ERC4626 vault user): withdraw vault liquidity so that
        // shortfall <= borrower vault assets but vault.withdraw reverts/caps out
        vm.prank(vaultUser);
        externalVault.withdraw(externalVault.maxWithdraw(address(externalVault)), vaultUser, vaultUser);
        // or: vault owner pauses / hits an integration withdrawal cap

        IdleCreditVaultManagerOrchestrator.StopEpochWithDurationAction[] memory actions =
            new IdleCreditVaultManagerOrchestrator.StopEpochWithDurationAction[](2);
        actions[0] = IdleCreditVaultManagerOrchestrator.StopEpochWithDurationAction({
            cdo: address(cdoA), newApr: 0, interest: 0, duration: 30 days, loss: 0, allowDefault: false
        });
        actions[1] = IdleCreditVaultManagerOrchestrator.StopEpochWithDurationAction({
            cdo: address(cdoB), newApr: 0, interest: 0, duration: 30 days, loss: 0, allowDefault: false
        });

        // The whole batch reverts on vault B's transient ERC4626 failure;
        // vault A's stopEpoch is rolled back too -> pending withdraws frozen cluster-wide
        vm.prank(operator);
        vm.expectRevert(); // StopEpochVaultLiquidityUnavailable bubbles from ProgrammableBorrower.onStopEpoch
        orchestrator.stopEpochWithDuration(actions);

        assertTrue(cdoA.isEpochRunning(), "healthy vault's epoch stop rolled back");
        assertTrue(cdoB.isEpochRunning(), "failing vault still running");
        // pending withdraw receipts on BOTH vaults remain unclaimable until the
        // owner manually removes B via setCreditVaultAllowed or liquidity returns
    }
}
```
