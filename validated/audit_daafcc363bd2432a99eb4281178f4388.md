### Title
Gateway `Message.Validate()`/`ExtractSigner` binds `Sender` to any self-generated ECDSA key with no allowlist check, and the WebAPI-trigger legacy handler forwards it to DON nodes unchecked - ([File: core/services/gateway/api/message.go], [File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`Message.Validate()` only checks that the `Signature` recovers to *some* valid ECDSA public key via `ExtractSigner`/`ecrecover`, and unconditionally sets `Body.Sender` to whatever address that recovers to — there is no check that the recovered address belongs to any registered/allowlisted subscriber. The legacy WebAPI-trigger handler (`handler.HandleLegacyUserMessage`) that consumes this `Sender` value forwards the message to every DON node with an explicit `// TODO: apply allowlist and rate-limiting here` comment, meaning the sender identity is never verified against an authorization list before being sent to the DON.

### Finding Description
In `core/services/gateway/api/message.go`, `Message.Validate()` performs field-length and null-byte checks, then calls `m.ExtractSigner()`, which recovers the signer purely from `ecrecover` over the raw message bytes and the supplied `Signature`: [1](#0-0) 
`ExtractSigner` performs no lookup against any known/authorized address set — any freshly generated ECDSA keypair that signs the correct raw bytes will successfully "validate": [2](#0-1) 

This is by design at this layer — `Validate()`'s job is purely to check the signature is well-formed and self-consistent, deferring authorization to the handler layer. The reachable path is `gateway.ProcessRequest` → for legacy DON-ID requests, `msg.Validate()` is called, then the message is routed to the handler keyed by `Body.DonId`: [3](#0-2) 

For the WebAPI capabilities handler, `HandleLegacyUserMessage` processes the `web_api_trigger` method. After basic payload/staleness/method checks, it explicitly skips authorization with a TODO comment and forwards the message — with attacker-controlled `Body.Sender` — to **every** DON member node: [4](#0-3) 

This gap is also acknowledged in the existing test suite, which documents that sender validation is unresolved for this handler: [5](#0-4) 

An unprivileged attacker with only network access to the gateway's user-facing HTTP endpoint can: generate a throwaway ECDSA key, craft a `MessageBody{MessageId, Method: "web_api_trigger", DonId, Receiver}`, sign `GetRawMessageBody(&body)` with the throwaway key, and submit it. `Validate()` succeeds and sets `Body.Sender` to the attacker's own address, and the message (bearing the forged `Sender`) is forwarded to all DON nodes participating in that DON ID, impersonating a legitimate WebAPI-trigger sender that the DON never subscribed to.

### Impact Explanation
This allows request/identity impersonation: an attacker can present themselves as an arbitrary "sender" of a WebAPI trigger event to a DON's off-chain oracle nodes without ever being registered or allowlisted. Downstream capability/workflow logic that trusts `Body.Sender` as an authenticated principal (e.g., for workflow triggering, rate limiting scoping, or auditing) can be spoofed, potentially causing unauthorized triggering of workflows attributed to a forged identity. This maps to the "authentication/authorization bypass leading to unauthorized action" bounty impact class, scoped specifically to the legacy WebAPI trigger path where the TODO admits the allowlist check is missing.

### Likelihood Explanation
No credentials are required beyond network reachability to the gateway's user HTTP port (`ProcessRequest`/`UserServerConfig.Path`). Crafting a valid signature only requires generating an ECDSA keypair and signing the deterministic raw bytes produced by `GetRawMessageBody`, which is fully documented in `message.go`. The exploit is trivially repeatable and does not depend on any race condition, timing, or privileged state.

### Recommendation
In `core/services/gateway/handlers/capabilities/handler.go::HandleLegacyUserMessage`, implement the pending allowlist/authorization check before forwarding to DON nodes — verify `msg.Body.Sender` against a per-DON/per-workflow authorized senders list (similar to the pattern already used in `core/capabilities/vault/allow_list_based_auth.go`) and reject/callback-error unauthorized senders instead of relying solely on `Validate()`'s signature well-formedness check.

### Proof of Concept
Go test plan (handler-level, in `core/services/gateway/handlers/capabilities/handler_test.go` style):
1. Generate a fresh ECDSA key not present in any DON/subscriber config (`crypto.GenerateKey()`).
2. Build `api.MessageBody{MessageId: "poc1", Method: MethodWebAPITrigger, DonId: <handler's donID>, Receiver: "", Payload: validTriggerPayloadJSON}`.
3. Call `msg.Sign(attackerKey)` (per `message.go` lines 96-108), producing `Signature` and `Body.Sender = attackerAddress`.
4. Call `msg.Validate()` and assert `err == nil` and `msg.Body.Sender == strings.ToLower(attackerAddress.Hex())`, proving no allowlist check occurred.
5. Call `handler.HandleLegacyUserMessage(ctx, msg, callback)` with a mocked `don.SendToNode` and assert it is invoked for all DON members (i.e., the forged sender's message is forwarded), confirming the missing authorization enforcement noted by the `// TODO: apply allowlist and rate-limiting here` comment.
