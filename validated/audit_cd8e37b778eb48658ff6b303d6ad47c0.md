### Title
Custom inflation-rewards commission collector is redirected using the current (distribution-time) vote-account state instead of a rewarded-epoch snapshot, letting a validator retarget already-earned commission - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`redeem_delegation_rewards` protects the *commission rate* (`commission_bps`) from last-minute manipulation by reading it from a delayed, epoch-boundary snapshot (`snapshot_epoch_vote_accounts` / `rewarded_epoch_vote_accounts`), but it does **not** apply the same protection to the *commission destination* (`commission_pubkey`, driven by `inflation_rewards_collector()`). The collector pubkey is read from `distribution_epoch_vote_accounts`, i.e. the live vote-account state at distribution time, not the state that was in effect during the rewarded epoch. This is the same class of bug as the reported curator-rewards issue: reward ownership for a past period is resolved using "current" state rather than "historical" state.

### Finding Description
`calculate_rewards_for_partitioning` builds a `CachedVoteAccounts` struct with three views of vote-account state: [1](#0-0) 
- `snapshot_epoch_vote_accounts` / `rewarded_epoch_vote_accounts`: delayed snapshots taken up to a full epoch earlier, explicitly to prevent "last-minute commission rugs".
- `distribution_epoch_vote_accounts`: the live, current vote-account state used at the moment rewards are actually paid out.

Inside `redeem_delegation_rewards`, the commission **rate** is deliberately pulled from the delayed snapshot when `delay_commission_updates` is enabled: [2](#0-1) 

But the commission **destination pubkey** is computed later using `vote_state`, which was derived from `distribution_epoch_vote_accounts` (the live/current vote account), not from the delayed snapshot: [3](#0-2) [4](#0-3) [5](#0-4) 

The vote account's custom commission collector can be changed at any time by the vote account's authority via the vote program's authorize/collector-update path (`NewCommissionCollector`, gated behind `custom_commission_collector` feature) in `programs/vote/src/vote_state/mod.rs` and dispatched from `programs/vote/src/vote_processor.rs`. Reward calculation happens at epoch boundary (`process_new_epoch` → `compute_new_epoch_caches_and_rewards` → `calculate_rewards_for_partitioning`), but actual payout of commission for that epoch is deferred and spread across the following epoch via partitioned distribution (`begin_partitioned_rewards` / `distribute_epoch_rewards_in_partition`). Because `commission_pubkey` is re-derived from the live vote account state at the time each partition is processed (which occurs after epoch N ends, and can complete throughout epoch N+1), any change to the collector pubkey made after epoch N ends but before that partition's distribution is processed will redirect commission that was earned during epoch N to the new address.

### Impact Explanation
This allows a vote-account authority (or anyone who gains that authority, e.g. through a sale/transfer of validator identity or a compromised authority key) to retroactively redirect already-earned inflation commission for a just-finished epoch to a new address of their choosing, after the reward-earning period has already ended. This is a fund-misdirection/reward-corruption bug: the party entitled to the commission for epoch N (the collector configured during epoch N) can lose it to whoever controls the collector setting at the time distribution actually executes, mirroring exactly the reported curator-reward bug ("owner at distribution time" vs "owner during the period"). The protocol already recognizes this exact risk for the commission *rate* (hence the delayed-snapshot mitigation with the explicit "last minute commission rugs" comment) but left the commission *pubkey* unprotected.

### Likelihood Explanation
Changing the custom commission collector is a normal, unprivileged vote-program instruction available to any vote account's designated collector-authority; no special protocol privilege is required. Given partitioned reward distribution can span the length of an entire epoch after the rewarded epoch ends, there is a wide window (up to ~1 epoch) during which the collector can be swapped before all reward partitions for the prior epoch have been distributed, making exploitation straightforward and reliably reproducible.

### Recommendation
Apply the same delay/snapshot protection used for `commission_bps` to the commission collector pubkey: resolve `inflation_rewards_collector()` from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` (the epoch-boundary snapshot) rather than from `distribution_epoch_vote_accounts`, whenever `delay_commission_updates` (or an equivalent guard for `custom_commission_collector`) is active.

### Proof of Concept
1. Enable `custom_commission_collector` and set vote account `V`'s inflation rewards collector to address `A`.
2. During epoch `N`, `V` accrues stake/vote inflation rewards normally; `calculate_rewards_for_partitioning` computes `commission_pubkey = A` at epoch-boundary calculation time based on cached state, but the actual credit happens later during partitioned distribution.
3. Immediately after epoch `N` ends (epoch `N+1` begins) but before all reward partitions for epoch `N` have been distributed (`store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition` runs across many blocks of epoch `N+1`), submit a vote-program transaction changing the collector to address `B` (attacker-controlled), using the same authority that was valid the whole time.
4. When `redeem_delegation_rewards` runs for the still-outstanding epoch-`N` partitions, it reads `distribution_epoch_vote_accounts` (current state) and computes `commission_pubkey = B`, crediting `B` with commission that was earned while the collector was `A`.
5. `A` receives none of the epoch-`N` commission it was entitled to; `B` receives commission for a period during which it was not configured as the collector.

    /// Get cached vote account state from the past few epochs so that some vote
    /// state configuration changes are delayed before being used in reward
    /// calculation.
    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }
