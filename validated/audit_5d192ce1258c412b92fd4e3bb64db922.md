### Title
Stale/permanent block rejections are never reconciled against later acceptances, letting a signer become wedged in `GloballyRejected` for a block that legitimately reaches signing consensus - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_rejection` and `store_and_process_block_signature` maintain two independent, monotonically-growing tallies for the same block hash — `total_reject_weight` (from `get_block_rejection_signer_addrs`) and `total_signature_weight` (from `get_block_signatures`) — with no mechanism that reconciles a signer's earlier rejection against that same signer's later acceptance of the same block. This mirrors the `UR = borrows / (cash + borrows - reserves)` defect described in the report: two quantities (`cash`, `reserves`) that are tracked independently and combined into a threshold decision, with no invariant enforced between them, letting the derived ratio exceed its valid bound (`UR > 1`). Here, `total_reject_weight` and `total_signature_weight` are tracked independently per signer address and can both include the same signer's weight, letting the 30%-blocking-minority threshold be crossed using weight that has already (or will later) count toward the 70%-approval threshold.

### Finding Description
`store_and_process_block_rejection` records a peer's rejection permanently: [1](#0-0) 

and then computes `total_reject_weight` purely from the accumulated set of rejecting addresses returned by `get_block_rejection_signer_addrs`: [2](#0-1) 

If that threshold is crossed, the block is moved to `BlockState::GloballyRejected` via `mark_globally_rejected`: [3](#0-2) 

Separately, `store_and_process_block_signature` records acceptances in a completely different table (`add_block_signature`) and computes `total_signature_weight` from `get_block_signatures`, again with no cross-check against the rejection table: [4](#0-3) 

Nothing in either path removes or invalidates a stale rejection when the same signer address later signs (accepts) the identical block, and nothing prevents a signer's weight from being counted in `total_reject_weight` at one point in time and in `total_signature_weight` at another. This is analogous to the audited contract's failure to guarantee `reserves <= cash`: two quantities that should be mutually constrained (an address's current stance is either "reject" or "accept", not both, and shouldn't retroactively count against the opposite tally) are accumulated with no invariant tying them together.

Critically, `check_state` makes `GloballyRejected` a sink with respect to `GloballyAccepted`: [5](#0-4) 

so once a signer's local view of a block crosses the (stale-inflated) 30% rejection threshold and calls `mark_globally_rejected`, that signer can never subsequently mark the same block `GloballyAccepted`/sign it — even if the same peers whose earlier rejections were counted have since re-evaluated and signed the block (the documented `LocallyRejected --> LocallyAccepted : re-evaluated` transition confirms peer opinions on a proposal are expected to flip, e.g. due to `check_block_against_signer_db_state` transient failures being cleared by a later chainstate view).

### Impact Explanation
This breaks the "rejection recounted as an accept" / "aggregated-weight vs verified-accepts" equality the rules call out: the reject tally is not the current set of live objectors, it is the historical union of everyone who ever objected, even after they've withdrawn that objection by signing. A signer that locks itself at `GloballyRejected` for a block using such stale weight is a High-impact liveness wedge (per the rules' definition: "a signer wedged into never signing valid blocks") for that specific proposal, and if enough signers independently accumulate the same stale rejection set, the block can be permanently blocked at the signer layer even though a legitimate, up-to-date supermajority would otherwise sign it — forcing the miner to abandon and re-propose, and denying credit to signers who already committed real signatures.

### Likelihood Explanation
No majority collusion or forged key is required. The pattern only needs ordinary, honest signer behavior that the codebase itself models as normal: a signer rejects a proposal for a reason that is later invalidated by new information (chain tip advancing, a competing block going stale, a reorg permit expiring), then legitimately re-evaluates and signs. This flip is explicitly anticipated by the state machine (`LocallyRejected --> LocallyAccepted`), but the peer-side vote tallying in `store_and_process_block_rejection`/`store_and_process_block_signature` never revisits or invalidates the earlier rejection record for that peer. A miner or gossip timing that induces even a handful of signers to reject-then-accept in this way is sufficient to trigger the stale-weight accumulation.

### Recommendation
Tie the two tallies together the same way the report recommends for `UR`: enforce and check the invariant that a signer address cannot simultaneously (or via stale history) count toward both `total_reject_weight` and `total_signature_weight` for the same block hash. Concretely: (1) when storing a new acceptance for a block hash, retract/void that signer's earlier rejection record for that same hash (and vice versa) before recomputing thresholds; (2) before calling `mark_globally_rejected`, require that no address counted in `total_reject_weight` has a more-recent recorded acceptance for the same block; (3) consider deriving both weights from a single canonical "current stance per address" table instead of two independently-appended tables.

### Proof of Concept

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
