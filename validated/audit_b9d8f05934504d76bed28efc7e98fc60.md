### Title
EI-authenticated requests bypass `isUser`-only guard and can run arbitrary int32-ID jobs - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
`PipelineRunsController.Create` intends to restrict job runs triggered by numeric (int32) job IDs to authenticated *users* only, explicitly excluding External Initiators (EIs), per the comment `// only users are allowed to run jobs using int IDs - EIs not allowed` [1](#0-0) . The gate for this is `_, isUser := auth.GetAuthenticatedUser(c)`.

However, `auth.GetAuthenticatedUser` merely checks whether the `SessionUserKey` context value is set: [2](#0-1) . Critically, `AuthenticateExternalInitiator` — the middleware used for EI-authenticated requests — explicitly sets that same key to a synthetic user object:

```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [3](#0-2) 

As a result, `GetAuthenticatedUser(c)` returns `true` for EI-authenticated requests exactly the same as for real users, meaning the `isUser` check in `Create` cannot distinguish EI-only credentials from a genuine user session/API-token. The uuid.Parse check only blocks legacy webhook UUID-style IDs [4](#0-3) , and does nothing to stop numeric IDs. Consequently, an attacker holding only valid EI credentials can POST `/v2/jobs/123/runs` with a numeric job ID and reach `prc.App.RunJobV2(ctx, jobID, nil)` [5](#0-4) , for **any** job ID, not just jobs the EI is associated with — the code performs no check that the EI in context is bound to the target job.

### Impact Explanation
An EI-credential holder (a restricted, non-admin, non-user credential type) can trigger execution of arbitrary jobs on the node by numeric job ID, including jobs unrelated to that EI. This is unauthorized job-run triggering by an unrelated principal — matching Chainlink's bounty class for unauthorized job run / authorization bypass, since the code's own design intent (comment) explicitly disallows this for EIs.

### Likelihood Explanation
Requires only valid EI access-key/secret headers (`static.ExternalInitiatorAccessKeyHeader`/`ExternalInitiatorSecretHeader`), no session, no API token, no admin/operator access. Any numeric job ID hosted on the node can be targeted. This is trivially reproducible and repeatable — a single authenticated EI can enumerate/probe integer job IDs.

### Recommendation
Distinguish EI-authenticated context from genuine user context, e.g. by checking `auth.GetAuthenticatedExternalInitiator(c)` is absent before treating the request as `isUser`, or by not overwriting `SessionUserKey` in `AuthenticateExternalInitiator`, and instead relying solely on `SessionExternalInitiatorKey` plus role checks. In `Create`, explicitly reject requests where an EI principal is present.

### Proof of Concept
1. Build a `gin.Engine` wiring the real `userOrEI` middleware chain (`auth.Authenticate` with `AuthenticateBySession`, `AuthenticateByToken`, `AuthenticateExternalInitiator`) in front of `PipelineRunsController.Create`, as done in `core/web/router.go`.
2. Seed a valid `ExternalInitiator` in the ORM/mock, bound to job A, but send `POST /v2/jobs/<jobB-id>/runs` (numeric ID of an unrelated job B) using only EI headers (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`), no session cookie, no API key/secret.
3. Assert that inside the handler `auth.GetAuthenticatedUser(c)` returns `(user, true)` even though only EI credentials were supplied (this is the root cause).
4. Assert the HTTP response status is `200`/run-created rather than the expected `422`/`401`, confirming `RunJobV2` was invoked for job B despite the EI never being associated with it.
