### Title
`JsonRpcRequestProcessor::bank()` silently falls back to `root_bank()` on stale/pruned commitment slot, returning wrong-fork data - ([File: rpc/src/rpc.rs])

### Summary
When a commitment-resolved slot from `BlockCommitmentCache` is no longer present in `BankForks` (e.g., pruned between commitment-cache update and RPC read), `JsonRpcRequestProcessor::bank()` logs a warning and silently substitutes `root_bank()` instead of returning an error. Any RPC method built on `bank()`/`get_bank_with_config()` (e.g., `getBalance`, `getAccountInfo`) then returns data and `context.slot` for the unrelated root bank while claiming to answer the originally requested commitment.

### Finding Description
`JsonRpcRequestProcessor::bank()` resolves a commitment level to a slot via `self.block_commitment_cache.read().unwrap().slot_with_commitment(commitment.commitment)`, then looks that slot up in `BankForks`: [1](#0-0) 

If `r_bank_forks.get(slot)` returns `None` — which happens if the bank at that slot has already been pruned from `BankForks` by normal cleanup before the `BlockCommitmentCache` is updated to reflect the new state — the code does **not** propagate an error. Instead it logs `warn!("Bank with {:?} not found at slot: {:?}", ...)` and returns `r_bank_forks.root_bank()`. The comment in the source explicitly documents this as a known, unresolved race ("it may occur after an old bank has been purged from BankForks and a new BlockCommitmentCache has not yet arrived"), referencing solana-labs/solana#11078.

Every RPC path that calls `self.bank(commitment)` (directly or via `get_bank_with_config`) inherits this behavior — e.g. `get_balance`, `get_account_info`, and other commitment-aware handlers construct their `RpcResponse` using `new_response(&bank, ...)`, which reports `bank.slot()` as `context.slot`. Since `bank` here is silently the root bank, the response's `context.slot` and the returned account/balance state belong to a different, unrelated slot/fork than the one the client requested via `commitment=finalized` (or `processed`), violating the invariant that returned data must belong to the requested commitment/slot.

This differs from the `min_context_slot` check in `get_bank_with_config`, which only compares the resolved bank's slot against the client-supplied `min_context_slot` — it cannot catch this problem because the substituted root bank's slot could still be numerically below/above expectations without violating that specific check, and no explicit error is surfaced for the "was pruned" case itself.

### Impact Explanation
This causes wrong-slot/wrong-fork data to be returned in response to a single, unprivileged RPC call, matching the "wrong-slot/fork/account data returned" bounty category. Impact is scoped to consensus-state read pollution for a single query — the client can be misled into believing stale/root-bank account state (balances, account data) reflects the freshly finalized/processed slot it asked for, with no crash or unbounded cost.

### Likelihood Explanation
The precondition is a benign, naturally-occurring race: `BankForks` bank pruning happens continuously as part of normal validator operation (rooting/squashing old banks), while `BlockCommitmentCache` updates asynchronously on a separate path. A single `getBalance`/`getAccountInfo` request with `commitment=finalized` issued right as the referenced slot is pruned reproduces it — no elevated privileges, special timing control beyond ordinary request cadence, or multiple clients are required. The code's own comment acknowledges this can occur "as a result of a known bug" and cites an open, unresolved GitHub issue, which supports that this is a real, reachable, previously-known gap rather than a theoretical one.

### Recommendation
Change `bank()` to propagate an explicit RPC error (e.g., reuse/extend `RpcCustomError`, such as a "Bank not found for commitment/slot" variant) instead of falling back to `root_bank()` when `r_bank_forks.get(slot)` is `None`. Alternatively, per the existing code comment, have `BlockCommitmentCache` hold an `Arc<Bank>` directly rather than a bare `Slot`, eliminating the possibility of the referenced bank being pruned out from under a commitment lookup.

### Proof of Concept
Integration test outline (in `rpc/src/rpc.rs` test module, using existing `RpcHandler`/`new_bank_forks` test scaffolding):
1. Build `BankForks` with banks at slots 0..N; set `BlockCommitmentCache` (via `CommitmentSlots`) so `slot_with_commitment(Finalized)` returns slot `K` where `K` has a live bank.
2. Prune slot `K` from `BankForks` (e.g., call `bank_forks.write().unwrap().set_root(...)` with a root beyond `K`, or otherwise remove it) without updating `BlockCommitmentCache`, simulating the race window.
3. Call `meta.get_balance(&pubkey, RpcContextConfig { commitment: Some(CommitmentConfig::finalized()), min_context_slot: None })` (or issue the `getBalance` JSON-RPC request through `RpcHandler::handle_request_sync`).
4. Current behavior: assertion that `response.context.slot == root_bank_slot` (not `K`) proves silent substitution — i.e., `bank(commitment).slot() != K`.
5. Expected/fixed behavior: assert the call returns `Err(...)` (e.g., a distinct `RpcCustomError` variant) instead of any successful response referencing an unrelated slot.

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })
    }
