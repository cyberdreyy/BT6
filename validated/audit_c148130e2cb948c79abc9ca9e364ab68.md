### Title
Post-default instant-withdraw receipts escape the recovery bucket and drain other users' funded-but-unclaimed underlying — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.requestInstantWithdraw` has no `defaultRecoveryFinalized` handling, unlike `requestWithdraw`, which routes post-default requests through the haircutted `postDefaultRequests` path. A post-default instant request therefore lands in the same aggregate `instantWithdrawsRequests` bucket as pre-default receipts and is paid at par by `claimInstantWithdrawRequest` via `_transferFundedClaim`, which only ring-fences `defaultRecoveryReserve` — not the unclaimed funded claims of other users. This is the vault analog of a directory traversal: a request "escapes" its designated recovery directory and reads funds belonging to a different claim class.

### Finding Description
After `finalizeDefaultRecovery` sets `defaultRecoveryFinalized = true`:

- `requestWithdraw` correctly detects the finalized state and isolates new requests into `postDefaultRequests[_user]` (IdleCreditVault.sol:247-257), which is later paid from `defaultRecoveryReserve` via `_claimPostDefaultWithdrawRequest` / `_transferDefaultRecovery` (lines 760-767, 912-917).
- `requestInstantWithdraw` (lines 356-375) performs **no equivalent check**. It burns the CDO's strategy tokens, mints an equal receipt to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws`.
- `claimInstantWithdrawRequest` (lines 380-393) only applies the recovery haircut to receipts stored under `defaultRecoveryEpoch` and only when `defaultInstantWithdrawsFinalized` is true. The remainder — including the attacker's brand-new post-default receipt — is paid in full by `_transferFundedClaim`.
- `_transferFundedClaim` (lines 897-907) protects only `defaultRecoveryReserve`. Any other underlying sitting in the strategy — funded-but-unclaimed normal withdraw receipts (`collectWithdrawFunds`) or funded instant receipts belonging to other users — is spendable.

The attacker needs tranche tokens to route through the CDO's `requestInstantWithdraw` path (a KYC'd tranche holder). `pendingInstantWithdraws` is incremented but post-default there is no epoch machinery that ever calls `collectInstantWithdrawFunds` to fund it — the receipt is unfunded by construction, yet redeemable at par against unrelated users' money. Additionally, `defaultPendingClaimBasis` (lines 644-649) includes `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, so a request opened between `stopEpoch` and `finalizeDefaultRecovery` also inflates the recovery basis, diluting `defaultRecoveryPrice` for legitimate claimants (denominator grows while reserve does not).

### Impact Explanation
Direct theft: an attacker who deposits (or already holds tranche tokens) right after default finalization can open an instant withdraw request and immediately claim it, receiving underlying at 1:1 from the strategy's funded-but-unclaimed balance that belongs to other withdraw claimants — up to `balance - defaultRecoveryReserve`. If executed between default and `finalizeDefaultRecovery`, the same request also dilutes the recovery price for all defaulted claimants (BB-first loss waterfall bypass). Loss is bounded by the funded unclaimed balance; even a small balance yields a proportional theft of other users' claims.

### Likelihood Explanation
Requires the vault to be in the `defaulted`/`finalized` phase and the CDO to still expose `requestInstantWithdraw` (it is gated by allow-flags and `_onlyIdleCDO`, not by `defaultRecoveryFinalized`, in the strategy; whether the CDO-side entry point reverts when `defaulted()` could not be fully confirmed within available iterations — if it does not gate on default, the attack is a two-transaction sequence available to any KYC'd holder). The funded-claim pool it drains exists whenever any user requested a withdraw that was funded by a prior `stopEpoch`/`collectWithdrawFunds` but not yet claimed — a common state.

### Recommendation
Mirror the `requestWithdraw` treatment: in `requestInstantWithdraw`, either revert when `defaultRecoveryFinalized` is true, or route through a `postDefaultRequests`-equivalent bucket that is only payable from `defaultRecoveryReserve`. Also gate `requestInstantWithdraw` between `defaulted()` and finalization so `instantWithdrawClaimsByEpoch[epochNumber]` cannot inflate `defaultPendingClaimBasis` without a matching reserve contribution.

### Proof of Concept
Foundry fork sketch (extends `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
// Assume: victim has a withdraw request funded at stopEpoch (collectWithdrawFunds
// moved victimUnderlying into the strategy), and victim has not yet claimed.

// 1. Borrower defaults; manager calls _handleBorrowerDefault -> CDO defaulted.
// 2. finalizeDefaultRecovery(0, address(0)) runs; defaultRecoveryFinalized = true.

// 3. Attacker (KYC'd, holds AA tranche tokens post-default haircut pricing):
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(ATTACK_TRANCHE_AMOUNT, address(AAtranche));
// -> strategy.requestInstantWithdraw burns CDO strategy tokens, mints receipt,
//    instantWithdrawsRequests[attacker] += amount; pendingInstantWithdraws += amount;
//    no funds are ever collected (no collectInstantWithdrawFunds post-default).

// 4. Same tx / next block:
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// -> claimInstantWithdrawRequest: defaulted-epoch branch clears nothing for attacker
//    (receipt epoch > defaultRecoveryEpoch), then pays instantWithdrawsRequests[attacker]
//    at par via _transferFundedClaim, spending victim's funded-but-unclaimed underlying.

assertGt(underlying.balanceOf(attacker), attackerCostBasis);
// victim's subsequent claimWithdrawRequest now reverts or underpays.
```

Note: step 3 depends on `IdleCDOEpochVariant.requestInstantWithdraw` remaining callable while `defaulted()`; I was unable to confirm that gating in the CDO entry point within the tool-call budget — if it reverts on `defaulted()`, this specific path is blocked, but the basis-dilution variant (request in the window between default and `finalizeDefaultRecovery`) does not require post-default reachability and stands independently, since `defaultPendingClaimBasis` counts the new instant claim without any matching funded reserve.
