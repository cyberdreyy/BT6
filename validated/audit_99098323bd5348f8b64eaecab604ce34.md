### Title
Loss-adjusted withdraw receipts are paid at par once the user files a second withdraw request — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
When `collectWithdrawFunds` is called with `_amount < pendingWithdraws` (the borrower under-funds pending receipts at `stopEpochWithDuration`), the strategy records a `lossRecoveryPriceByEpoch[epoch]` haircut but leaves each user's receipt in `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][epoch]`. The loss-adjusted claim path (`_claimLossAdjustedWithdrawRequest`) looks up the haircut **only** via `lastWithdrawRequest[_user]`. If the same user files any new `requestWithdraw` in a later epoch, `lastWithdrawRequest[_user]` is overwritten, the loss-epoch price is never consulted, and the entire aggregate — including the haircutted receipt — is paid at par by `_claimFundedWithdrawRequest`. The user extracts the written-off loss portion, leaving the strategy underfunded for all other claimants.

### Finding Description
The external bug class is a missing validation that lets attacker input reach a resource it shouldn't (unvalidated `file_path` → `open()`). The analog is a missing epoch-scope validation: the claim path keys the haircut lookup on a single mutable marker instead of the receipt's own epoch.

Relevant code (`contracts/strategies/idle/IdleCreditVault.sol`):

- `collectWithdrawFunds(_amount)` stores `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` under `lossRecoveryPriceByEpoch[epochNumber]` and sets `pendingWithdraws = 0`, but cannot clear per-user `withdrawsRequests` / `withdrawsRequestsByEpoch` entries (lines 411-420).
- `requestWithdraw` accumulates: `withdrawsRequests[_user] += _amount; withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;` and overwrites `lastWithdrawRequest[_user] = currentEpoch` (lines 282-294). The comment at lines 323-324 explicitly allows requesting again before claiming.
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` only (lines 789-795). After a second request, `lastWithdrawRequest` points to the new epoch, whose price is 0, so this path returns 0 forever — the old loss-epoch receipt can never be claimed at its haircut.
- `_claimFundedWithdrawRequest` then pays `amount = withdrawsRequests[_user] + apr0…` — the *full* pre-haircut basis — and zeroes the accounting (lines 338-349).

Sequence (fixed-APR mode, epoch N stopped with partial funding, epoch N+1 running):

1. LP `U` has a pending receipt `R` created in epoch N (in `withdrawsRequests[U]` and `withdrawsRequestsByEpoch[U][N]`).
2. Owner calls `stopEpochWithDuration`; borrower funds only `R * p` (`p < 1`). `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[N] = p`, sets `pendingWithdraws = 0`, and pulls only `R*p` underlying into the strategy. `epochNumber` is now N+1.
3. During epoch N+1 (running), `U` calls `cdoEpoch.requestWithdraw(dust, tranche)` → `lastWithdrawRequest[U] = N+1`, `withdrawsRequests[U] = R + dust`.
4. After epoch N+1 stops, `U` calls `claimWithdrawRequest()`:
   - `_claimLossAdjustedWithdrawRequest`: `lossRecoveryPriceByEpoch[N+1] == 0` → returns 0 (epoch-N receipt skipped).
   - `_claimFundedWithdrawRequest`: `epochNumber (N+2) > lastWithdrawRequest (N+1)` → pays `R + dust` at par.
5. `U` receives `R*(1 - p)` more underlying than the strategy ever collected for that receipt. That excess comes out of the strategy's underlying balance, which funds other funded receipts (and is only guarded against the recovery reserve when `defaultRecoveryReserve != 0`, line 900-905 — irrelevant here since no default occurred).

### Impact Explanation
Broken invariant: fair burn — one receipt, one payout **at its epoch's price**. The attacker redeems a haircutted receipt at par, directly extracting the unrealized loss `R * (1 - lossRecoveryPrice)` from the strategy's funded-withdrawal liquidity. Loss is quantified exactly: e.g., a 100,000 USDC receipt funded at 70% yields an extra 30,000 USDC paid to the attacker. This either insolvencies the receipt pool (later claimants' `safeTransfer` reverts → temporary/permanent freezing of their claims) or, if the strategy holds other liquidity, directly steals it. Reproducible as a Foundry fork test following `test/foundry/IdleCreditVault.t.sol` loss-adjusted scenarios.

### Likelihood Explanation
Requires: (a) a `stopEpochWithDuration`/`collectWithdrawFunds` partial funding event (borrower repays less than pending receipts — a real, supported loss path, not a default), and (b) the attacker being a lender whose receipt was pending in the loss epoch and who files a trivial second request in the next epoch. Both steps are unprivileged, normal user actions; the attacker only needs tranche tokens and a dust second deposit. No privileged role is involved in the exploit — owner/manager calls are sequenced around, not abused. The only mitigating factor is that partial-funding epochs are event-driven rather than attacker-triggerable, but once one occurs every affected receipt holder can execute the extraction.

### Recommendation
In `IdleCreditVault.sol`, decouple the loss-adjusted claim from `lastWithdrawRequest`: iterate or check all epochs with nonzero `withdrawsRequestsByEpoch[_user][epoch]` where `lossRecoveryPriceByEpoch[epoch] != 0` before the funded path, or store a per-user bitmap/list of loss epochs. Minimal alternative: in `_claimFundedWithdrawRequest`, revert (or exclude the epoch's amount) while any `withdrawsRequestsByEpoch[_user][e]` exists with a nonzero `lossRecoveryPriceByEpoch[e]`, forcing the haircut path first — this is the direct analog of adding `validate_safe_path(file_path)` before `open()`.

### Proof of Concept
Foundry fork test (mainnet block ~23032567, harness per `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossReceiptPaidAtParAfterSecondRequest() external {
    // 1. user deposits AA, requests withdraw in epoch N (receipt R)
    uint256 R = _depositWithUserAndRequestWithdraw(user, 100_000 * ONE_SCALE); // epoch N pending

    // 2. stop epoch N with partial funding: borrower funds only 70% of pendingWithdraws
    _startEpochAndCheckPrices(N);
    uint256 pending = strategy.pendingWithdraws();
    uint256 funded = pending * 7e17 / 1e18;
    deal(underlying, borrower, funded + interestDue);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), type(uint256).max);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(newApr, interest, duration, 0); // collectWithdrawFunds(funded) inside
    assertEq(strategy.lossRecoveryPriceByEpoch(N), 7e17);

    // 3. new epoch N+1 running: attacker files a dust second request
    _startEpochAndCheckPrices(N+1); // new epoch running
    vm.prank(user);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // overwrites lastWithdrawRequest[user]

    // 4. after epoch N+1 stops, claim pays R at par instead of 0.7*R
    _stopEpochAndCheckPrices(N+1, apr, expectedFunds);
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(user) - balPre;

    // BUG: paid ~= R + dust, but strategy only ever collected 0.7*R for epoch N
    assertGt(paid, R * 7e17 / 1e18 + dust, "loss-adjusted receipt overpaid at par");
    // subsequent claimants' claims now revert on insufficient strategy balance
}
```

Key assertion: `paid` exceeds `R * lossRecoveryPrice / 1e18` by the written-off loss, while `strategy` never received more than `funded` for that receipt — the delta is taken from other claimants' liquidity.
