### Title
Epoch-0 withdraw receipts bypass the loss haircut and are paid at par (or permanently frozen) because `lastWithdrawRequest == 0` is indistinguishable from "no request" - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` records a receipt's epoch in `lastWithdrawRequest[_user]`, where `0` is both the first valid epoch number and the "unset" sentinel. When `collectWithdrawFunds` stores a haircut under `lossRecoveryPriceByEpoch[epochNumber]`, `epochNumber` has already been incremented by `deposit` during `stopEpoch`, so a request made in epoch 0 points at index 0 while the haircut lives at index 1. This mirrors CVE-2026-26829's NULL-deref class: a zero-value state entry is dereferenced as if initialized, and the loss-adjusted claim path is silently skipped.

### Finding Description
In `requestWithdraw`, `lastWithdrawRequest[_user] = currentEpoch` stores `0` for the first epoch [1](#0-0) . In `collectWithdrawFunds`, a partial funding writes `lossRecoveryPriceByEpoch[epochNumber]` where `epochNumber` was already bumped by `deposit()` when the epoch ran (`epochNumber += 1` on deposits while `isEpochRunning()`) [2](#0-1) [3](#0-2) . Both `_claimLossAdjustedWithdrawRequest` and the re-request guard in `requestWithdraw` look up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. index `0`, and find `0` ("no loss epoch") [4](#0-3) [5](#0-4) . The claim then falls through to `_claimFundedWithdrawRequest`, which burns the receipt and pays the full un-haircut basis [6](#0-5) .

### Impact Explanation
`pendingWithdraws` was zeroed and only the haircut amount (`pendingBasis * lossRecoveryPrice / 1e18`) was pulled into the strategy by `collectWithdrawFunds`, yet the receipt still pays `claimBasis` at par. Two outcomes depending on strategy balance: (a) if the strategy holds enough underlying (e.g., prefunded instant-withdraw cash or other receipts' funding), the claimant withdraws more than funded, directly stealing the unfunded loss portion reserved for other claimants; (b) if it does not, `safeTransfer` reverts, and because `lastWithdrawRequest[_user]` can never match the epoch where the haircut is stored, the user is permanently unable to claim at the loss-adjusted price while the guard also blocks them from re-requesting only by luck — worse, the missed lookup means other users' epoch-0 receipts also evade `revert NotAllowed()` re-request protection, letting them stack new requests on top of unclaimed haircut receipts. Either way it is theft or permanent freezing of funds, quantified as `claimBasis * (1 - lossRecoveryPrice)` per affected epoch-0 receipt.

### Likelihood Explanation
Any unprivileged tranche holder can trigger this by calling `cdoEpoch.requestWithdraw` during the very first epoch (buffer phase before the first `stopEpoch`). It then requires only the honest manager calling `stopEpochWithDuration` with a nonzero `_lossAmount` that leaves a nonzero `lossRecoveryPrice` — an ordinary protocol operation, not attacker manipulation of privileged roles. The bug is deterministic whenever a first-epoch request meets a lossy stop.

### Recommendation
Initialize `lastWithdrawRequest` with a non-zero sentinel (e.g., store `currentEpoch + 1` or a separate `hasRequest` flag) so epoch 0 is never conflated with "unset". Apply the same adjustment consistently in `requestWithdraw`, `_claimLossAdjustedWithdrawRequest`, `_claimFundedWithdrawRequest`, `_clearWithdrawClaimForEpoch`, and the epoch-0 comparisons in `_settleApr0`. Alternatively, store the haircut keyed by the request epoch captured before the `epochNumber` bump in `deposit`.

// test/foundry/IdleCreditVaultEpoch0Loss.t.sol
function testEpoch0ReceiptSkipsLossHaircut() external {
    // 1. Lender deposits and requests withdraw during buffer of epoch 0.
    uint256 amt = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amt);
    vm.prank(AAUser);
    cdoEpoch.requestWithdraw(AAtranche.balanceOf(AAUser), address(AAtranche));
    // lastWithdrawRequest[AAUser] == 0 (epochNumber is still 0)

    // 2. Manager runs epoch and stops it with a realized loss.
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 loss = amt / 10; // 10% loss
    deal(address(underlying), strategy.borrower(), amt + loss, true);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), loss);
    // deposit() bumped epochNumber to 1 => lossRecoveryPriceByEpoch[1] != 0,
    // but the user's marker is 0 => lookup misses.

    // 3. Claim pays full basis instead of haircut (or reverts if underfunded).
    uint256 balPre = underlying.balanceOf(AAUser);
    vm.prank(AAUser);
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(AAUser) - balPre,
             amt * 9 / 10, "receipt paid above funded haircut");
}

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
