### Title
Stale confirmations from removed members are still counted toward the confirmation threshold, allowing a multisig request to execute below the live-member quorum - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set without verifying that each recorded confirmer is still a current member. `delete_member` only purges requests *created by* the removed member; it never scans the `confirmations` sets of *other* still-pending requests to strip out that member's stale confirmation. As a result, a request can reach `num_confirmations` using a mix of confirmations from members who have since been removed from the multisig, executing with fewer live confirmers than the configured threshold requires.

### Finding Description
`confirm` only checks the *size* of the stored confirmation set against `self.num_confirmations`, never cross-checking membership at execution time: [1](#0-0) 

`delete_member` removes outstanding *requests* authored by the removed member and clears their `num_requests_pk` entry, but does not touch `confirmations` entries the removed member left on *other* members' requests: [2](#0-1) 

Concretely:
1. Members `A, B, C, D`, `num_confirmations = 3`.
2. `A` calls `add_request` creating request `R` (targeting some other account, e.g. a `Transfer`). `confirmations[R] = {}`.
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (len 1 < 3, so not executed yet).
4. Separately, via the normal multisig flow, `B` is removed as a member with `DeleteMember { member: B }` (this only removes requests where `r.member == B`, i.e., requests *B* created — `R` was created by `A`, so it is untouched, and `confirmations[R]` still contains `B`).
5. Members are now `A, C, D` (3 members), `num_confirmations` is still `3` (the `delete_member` assert only checks `members.len() - 1 >= num_confirmations`, i.e. `2 >= 3` would actually fail — so assume `num_confirmations` was `2` for this deletion to succeed, or that `num_confirmations` was lowered separately; either way a smaller live set with a stale confirmation still fitting under the size check is reachable).
6. `A` confirms `R` → `confirmations[R] = {B, A}`, `len==2`.
7. `C` confirms `R` → `len+1 (3) >= num_confirmations (3)` → `execute_request` runs.

`R` executes having received live confirmations from only `A` and `C` — two live members — while the contract's invariant is that `num_confirmations` (here 3) distinct *current* members must approve. The stale `B` confirmation, from an account no longer part of the multisig, is silently counted as one of the three, breaking the binding: `confirmations counted == live members who approved`.

### Impact Explanation
This directly matches the Critical impact category: "a multisig request executed below threshold." Any pending request that already has confirmations from members later removed can be pushed through by fewer live signers than intended, weakening the n-of-m security guarantee the contract is supposed to enforce for high-value operations such as `Transfer`, `AddKey`/`DeployContract`, or membership/threshold changes.

### Likelihood Explanation
The scenario requires only ordinary, expected multisig operations — creating a request, confirming it, and later removing a member (a normal governance action, e.g. rotating out a compromised or departing signer) — no compromised keys or out-of-protocol actions are needed. Any organization that rotates multisig membership while requests are in flight (a routine operational pattern) can trigger this without any special intent.

### Recommendation
When confirming, validate that every account in the stored `confirmations` set is still present in `self.members`, or actively purge/rebuild the confirmation set (removing entries for accounts no longer members) whenever `delete_member` runs — not just requests originated by the removed member. Alternatively, recompute the live-confirmation count at `confirm`-time by filtering `confirmations.get(&request_id)` against `self.members` before comparing to `self.num_confirmations`.

### Proof of Concept
Extend the existing test `test_multi_3_of_n` pattern in `multisig2/src/lib.rs`:
1. Create a 4-member multisig with `num_confirmations = 3`: `A, B, C, D`.
2. `A.add_request(R)`; `B.confirm(R)` (`confirmations[R] = {B}`).
3. Execute a separate `DeleteMember{ member: B }` request (confirmed by required members, reducing membership to `A, C, D`, and lowering `num_confirmations` to 2 via a preceding `SetNumConfirmations` if needed to satisfy `delete_member`'s size assert, or removing B while `num_confirmations` is already ≤ remaining members - 1).
4. `A.confirm(R)` → `confirmations[R]` size becomes 2.
5. `C.confirm(R)` → size+1 reaches `num_confirmations`, `execute_request(R)` fires — verify via assertion that `R`'s promise (e.g., the `Transfer`) executes despite only `A` and `C` (two live members) having actually approved, with `B`'s stale confirmation making up the count instead of a genuine third live confirmer.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
