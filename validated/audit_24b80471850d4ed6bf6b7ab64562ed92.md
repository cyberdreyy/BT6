### Title
Replay-guard digest poisoning via owner-mismatched request allows DoS against a legitimate owner's request - ([File: core/capabilities/vault/authorizer.go])

### Summary
`authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(authResult.Digest(), ...)` **before** `validateSecretOwnersMatchAuthorized`. Because `Digest()` is computed purely from request content (method/ID/params) and is independent of the caller's identity or the `AuthorizedOwner()` derived from the JWT/allowlist auth, an attacker holding their own valid credentials can submit a request whose params impersonate a victim owner's `Id.Owner`, get its digest recorded by the replay guard, and then fail the subsequent owner check — permanently burning the digest slot the real owner would need for that exact request.

### Finding Description
- `authorizer.AuthorizeRequest` (`core/capabilities/vault/authorizer.go:99-119`) runs, in order:
  1. `a.authorizeRequest` → returns `AuthResult{orgID, workflowOwner, digest, expiresAt}`. For JWT auth (`jwt_based_auth.go:252-276`), `digest := req.Digest()` — computed over the wire content of the request (ID/Method/Params), and `workflowOwner` is derived independently from JWT claims (`DeriveJWTAuthorizedVaultWorkflowOwner(claims.OrgID, claims.TenantID, claims.WorkflowOwner)`), not from the request params.
  2. `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` (line 109) — records the digest as "seen" immediately.
  3. Only afterwards, `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())` (line 113) checks that `Id.Owner` fields inside `req.Params` match the authorized owner.
- Multiple tests confirm `Digest()` is content-derived and independent of the `Auth` field/signer identity (e.g. `outboundRequestWithoutAuth` used in `system-tests/tests/smoke/cre/vault_don_test_helpers.go:1119-1147`, and `TestMustMintVaultJWTForRequest_UsesRawRequestDigest`), meaning any party — including an attacker — can compute/bind a JWT to an arbitrary chosen request body's digest, regardless of who legitimately owns that content.
- An attacker with their own valid JWT (own org/tenant, correct OAuth scope) can construct a request whose `Params` (e.g. `EncryptedSecrets[].Id.Owner` or `ListSecretIdentifiersRequest.Owner`) contains the **victim's** owner address, identical to what the victim would legitimately submit. Because the digest calculation does not include the caller's authorized owner, the attacker's self-signed JWT digest binding still validates against `req.Digest()` for this victim-owner-impersonating payload.
- `AuthorizeRequest` then: passes JWT validation → passes `CheckAndRecord` (digest recorded for the first time, succeeds) → fails `validateSecretOwnersMatchAuthorized` because `authResult.AuthorizedOwner()` (attacker's derived owner) doesn't match `Id.Owner` (victim's owner) in the params, and the request is rejected with an owner error.
- However, the digest has already been recorded as seen in step 2. When the legitimate victim later submits the exact identical request (same digest-affecting fields) with their own correctly-scoped JWT, they pass token validation, scope, tenant, and owner derivation correctly — but `CheckAndRecord` on the same digest returns `ErrRequestAlreadySeen`, and the legitimate request is rejected as a replay.

### Impact Explanation
This is a denial-of-service against a legitimate vault owner's specific request: an unprivileged but authenticated attacker (holding only their own valid JWT) can pre-poison the replay-guard digest slot for any request content they can predict or observe (e.g., a `vault.secrets.create`/`update`/`delete`/`list` call with a known/guessable `request_id`, namespace, and secret key for the victim), causing that victim's genuine, first-time request to be wrongly rejected as a replay. This matches the "availability of legitimate requests should not be blockable by an unprivileged attacker" impact class — a targeted, repeatable griefing/DoS against a specific counterparty's vault operation.

### Likelihood Explanation
Feasible with low privilege: the attacker needs only their own valid vault JWT (own org/tenant/scope) — no admin, operator, or victim credentials. The attacker must know or guess the exact digest-affecting fields of the victim's intended request (method, request ID, secret key/namespace/owner) to make the digests collide exactly, which is a real but non-trivial precondition (predictable/guessable request IDs, e.g. sequential or workflow-derived IDs, would make this practical). The exploit is deterministic and repeatable once the fields are known — no race condition or timing requirement, since `CheckAndRecord` unconditionally records before the owner check runs.

### Recommendation
Reorder the checks in `authorizer.AuthorizeRequest` so that `validateSecretOwnersMatchAuthorized` runs and succeeds **before** `replayGuard.CheckAndRecord` records the digest, i.e. validate ownership first, and only record the digest in the replay guard once the request is fully authorized (owner match confirmed). This ensures a request that fails the owner-binding check never consumes/poisons a replay-guard slot.

### Proof of Concept
Go unit test plan in `core/capabilities/vault/authorizer_test.go`:
1. Build a JSON-RPC request `req` for `vault.secrets.list` (or `secrets.create`) whose params encode victim owner `victimOwner` in `Owner`/`Id.Owner`, with a fixed `request_id`.
2. Compute `digest, _ := req.Digest()`.
3. Mint a valid JWT for an *attacker* org/tenant (`attackerOwner != victimOwner`) whose `authorization_details` binds to `digest` (mirroring `TestJWTBasedAuth_AuthorizeCreateRequestFromRawJSON`), and set `req.Auth` to it.
4. Call `authorizer.AuthorizeRequest(ctx, req)` — assert it returns an owner-mismatch error (current behavior, expected to still fail).
5. Construct an identical `req2` (same digest-affecting content) but now minted/signed under the real victim's valid JWT (`workflowOwner == victimOwner`).
6. Call `authorizer.AuthorizeRequest(ctx, req2)` — **current buggy behavior**: returns `ErrRequestAlreadySeen` because step 4 already recorded `digest`. Expected/fixed behavior: `AuthorizeRequest` succeeds and returns a valid `AuthResult` for the victim.
7. Assert failure of the fix: `require.NoError(t, err)` and `require.Equal(t, victimOwner, authResult.AuthorizedOwner())` after the fix reorders owner validation before replay-guard recording.
