### Title
IdleCDOCreditVault grants unlimited underlying and strategyToken allowance to the strategy with no way to revoke it - (contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault.initialize` grants `type(uint256).max` allowance of both the underlying `token` and the `strategyToken` to the `strategy` contract. There is no owner/guardian-accessible function to reduce or reset that allowance to 0. If the strategy contract is ever exploited or misbehaves, it can pull the CDO's entire underlying balance — including instant-withdraw liquidity, fee balances, and unskimmed donations — even while the vault is paused or in emergency shutdown.

### Finding Description
During initialization the CDO calls `_allowUnlimitedSpend` twice: [1](#0-0) 

`_allowUnlimitedSpend` uses `safeIncreaseAllowance(spender, type(uint256).max)`, granting a standing unlimited approval: [2](#0-1) 

Deposits rely on this allowance when the strategy pulls funds via `IIdleCDOStrategy(strategy).deposit(_amount)` inside `_deposit`: [3](#0-2) 

The problem: no function in `IdleCDOCreditVault` calls `approve`/`safeApprove`/`safeDecreaseAllowance` to reduce this allowance. Owner and guardian only have `pause`, `unpause`, `emergencyShutdown`, and fee/split setters — none of which touch ERC20 allowances: [4](#0-3) 

The CDO's underlying balance is non-trivial at rest: `getContractValue` counts raw `token` balance alongside strategy tokens, meaning funds the strategy could pull via `transferFrom` are real pool value (instant-redeem liquidity, donations awaiting `_skimDonatedAssets`, accrued `unclaimedFees` pending collection): [5](#0-4) 

An identical pattern exists in `ProgrammableBorrower`, which grants unlimited allowance to `idleCDO` at init. `setVault` revokes the old vault's allowance (`safeApprove(address(vault), 0)`), but there is no corresponding setter or revoke for `idleCDO`, so a compromised/upgraded CDO retains a permanent pull right over the borrower's held underlying: [6](#0-5) [7](#0-6) 

### Impact Explanation
Lack of emergency protection with direct theft exposure. The strategy is a separate contract holding a standing unlimited approval over all underlyings ever held by the CDO. If any strategy-side bug or exploit allows arbitrary `transferFrom` (reentrancy into a strategy deposit path, a strategy admin-key compromise, a strategy upgrade in integrated deployments), the attacker drains every underlying token on the CDO — not just funds mid-deposit — bypassing `pause`/`emergencyShutdown` entirely, since ERC20 allowance is unaffected by CDO pausing. Loss is bounded only by `balanceOf(IdleCDOCreditVault)` in `token` plus its `strategyToken` balance, i.e., the full instant-liquidity buffer and pending fees.

### Likelihood Explanation
Medium. Exploitation requires a separate strategy-side weakness, so it is conditional rather than directly attacker-reachable; however, the missing mitigation is unconditional — there is no sunset/revoke path at all, so the CDO cannot de-risk an already-deployed strategy even when a vulnerability is discovered. The honest-owner emergency tooling (`emergencyShutdown`, `pause`) demonstrably does not stop allowance-based drainage.

### Recommendation
Add an owner (or owner-or-guardian) callable sunset function that sets the strategy allowances to 0, and optionally re-approves:

```solidity
function revokeStrategyAllowance() external {
    _checkOnlyOwnerOrGuardian();
    IERC20Detailed(token).safeApprove(strategy, 0);
    IERC20Detailed(strategyToken).safeApprove(strategy, 0);
}
```

Apply the same pattern in `ProgrammableBorrower` for the `idleCDO` allowance (an `setIdleCDO`/revoke path mirroring `setVault`'s `safeApprove(vault, 0)` logic).

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

contract MaliciousStrategy {
    // Simulates a strategy bug/exploit that allows arbitrary transferFrom
    function drain(address token, address from) external {
        IERC20(token).transferFrom(from, msg.sender, IERC20(token).balanceOf(from));
    }
}

contract AllowanceSunsetTest is Test {
    IdleCDOCreditVault cdo;
    IERC20Detailed token;
    address strategy;

    function setUp() public {
        // deploy + initialize cdo via factory/proxy with a real strategy
        strategy = cdo.strategy();
        token = IERC20Detailed(cdo.token());
        // lender deposits; some underlyings remain on the CDO (instant liquidity, donations, fees)
    }

    function testNoWayToRevokeStrategyAllowance() public {
        uint256 allowance = token.allowance(address(cdo), strategy);
        assertEq(allowance, type(uint256).max);

        // Guardian/owner emergency actions do not touch the allowance
        vm.prank(cdo.guardian());
        cdo.emergencyShutdown();
        assertEq(token.allowance(address(cdo), strategy), type(uint256).max);

        // There is no function to set it to 0 — static check:
        // no selector matching approve/decreaseAllowance/revoke is callable on the CDO.
        // Strategy (or a strategy exploit) can pull the CDO's entire token balance:
        uint256 bal = token.balanceOf(address(cdo));
        MaliciousStrategy evil = MaliciousStrategy(strategy); // hypothetical strategy-side bug
        evil.drain(address(token), address(cdo));
        assertEq(token.balanceOf(address(cdo)), 0);
        assertGt(bal, 0);
    }
}
```
