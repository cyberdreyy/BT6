## Analog vulnerability found

### Title
Stale confirmations from deleted/revoked keys are not invalidated, allowing a multisig request to execute below the real live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
`LendingLedger`'s bug was a **recorded-state-vs-real-state divergence**: the ledger kept crediting a reward for a full epoch even though the real deposit only existed for an instant. The `multisig` contract has the same class of bug for the **"confirmations counted versus live members"** binding: a confirmation given by a key is permanently recorded in `self.confirmations[request_id]`, but when that key is later revoked via `DeleteKey`, only the confirmations on requests *originated* by that key are purged. Confirmations that key gave on *other* pending requests survive forever, so a request can reach `num_confirmations` while actually having fewer live, currently-authorized keys behind it than the contract requires.

### Finding Description
`confirm()` checks the recorded confirmation count against the threshold and never re-validates that every recorded signer key is still an active key on the account: [1](#0-0) 

`DeleteKey` execution only cleans confirmations for requests that were *added* by the removed key — it does not scan `self.confirmations` for entries where the removed key appears as a *confirmer* of some other request: [2](#0-1) 

So the binding that should hold is:
```
recorded_confirmations(request) ⊆ { currently active keys on the account }
```
but after a `DeleteKey` execution this becomes false for any request not authored by the deleted key: a "ghost" confirmation from a now-unauthorized key remains counted.

The identical pattern exists in `multisig2` for `DeleteMember`, which only purges requests where `r.member == member`, leaving stale confirmations by that member on other requests: [3](#0-2) [4](#0-3) 

### Impact Explanation
This crosses the "multisig request executed below threshold" boundary explicitly called out as Critical impact: a `Transfer`, `FunctionCall`, `AddKey`, or any other sensitive action can be executed with fewer currently-live approving keys than `num_confirmations` mandates, because a stale/ghost confirmation from a revoked key still counts toward the total. This defeats the entire purpose of the K-of-N scheme — the security guarantee is that K *currently trusted* keys must approve, not K keys that were ever trusted.

### Likelihood Explanation
This requires no privileged access beyond being (or having been) one of the legitimate keys on the multisig — exactly the kind of "unprivileged attacker breaking a custody binding" scenario in scope. A realistic path: a key holder who is about to be off-boarded/revoked (e.g. suspected compromise, employee departure) confirms a request before their key is deleted; after the team executes the `DeleteKey` request to revoke that key (believing it neutralizes that key's influence), the earlier confirmation remains valid and can be combined with just one more (now the only "second" *live* approver) to push a malicious or unauthorized request over the threshold — effectively 1-of-K live approval executing a 2-of-K (or higher) protected action.

### Recommendation
When executing `DeleteKey` / `DeleteMember`, iterate over **all** entries in `self.confirmations` (not just requests authored by that key) and remove the deleted key/member from every confirmation set, re-checking whether any request no longer meets `num_confirmations` count. Alternatively, validate at `confirm()`-execution time that every public key/member recorded in `confirmations` is still present in the current key/member set before counting it toward the threshold.

### Proof of Concept
```rust
// multisig/src/lib.rs test-style PoC
// Keys: A, B, C ; num_confirmations = 2

// 1. Key A adds a sensitive request (e.g. large Transfer) - not confirmed by A itself
let request_id = contract.add_request(transfer_request); // signer_pk = A

// 2. Key C (soon to be revoked, e.g. suspected compromised) confirms it.
// confirmations[request_id] = {C}; 1 < 2, so it's just recorded, not executed.
set_signer(C);
contract.confirm(request_id);

// 3. Team detects C may be compromised, revokes it via a properly-confirmed DeleteKey request.
let delete_key_req = MultiSigRequest {
    receiver_id: current_account(),
    actions: vec![MultiSigRequestAction::DeleteKey { public_key: C }],
};
let del_id = contract.add_request(delete_key_req); // e.g. added by A
set_signer(B);
contract.confirm(del_id); // executes: deletes key C on-chain

// DeleteKey execution only purges confirmations for requests where signer_pk == C.
// request_id was added by A, so confirmations[request_id] still equals {C}.

// 4. Only ONE live key (A) confirms the original transfer request.
set_signer(A);
contract.confirm(request_id);
// confirmations.len() (1, stale C) + 1 (A) == 2 >= num_confirmations (2)
// => request executes with only 1 currently-live key's real approval.
```

        self.assert_valid_request(request_id);

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
