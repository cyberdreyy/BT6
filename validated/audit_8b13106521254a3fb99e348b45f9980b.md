### Title
Signer weight double-counted in both accept and reject tallies when a signer reconsiders a rejected block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The report's bug class is: a total used as a denominator/threshold accumulator (`vault.total_shares`) is decremented in one code path while the corresponding numerator/asset state is only updated in a different, later path, so the two sides of an accounting equality go out of sync and an actor extracts more value than is owed. The analogous break in this codebase is in the node-side StackerDB block-response tally (`StackerDBListener`), where a single signer's weight can be added to *both* `total_weight_approved` and `total_weight_rejected` for the same block, because the "already counted" guard differs between the two branches instead of being one mutually-exclusive per-signer state.

### Finding Description
`StackerDBListener` maintains, per proposed block, `total_weight_approved`, `total_weight_rejected`, `gathered_signatures` (map keyed by `slot_id`), and `responded_signers` (a set keyed by `slot_id`) [1](#0-0) .

- On `Accepted`, the "already counted" guard is `!block.gathered_signatures.contains_key(&slot_id)`, and afterwards the code unconditionally does `block.responded_signers.insert(slot_id)` [1](#0-0) .
- On `Rejected`, the guard is `block.responded_signers.insert(slot_id)` itself: `if block.responded_signers.insert(slot_id) { block.total_weight_rejected = ...add weight... }` [2](#0-1) .

These two guards are not the same state, so the outcome depends on message order for a given signer:
- Reject-then-Accept: Reject arrives first → `responded_signers.insert(slot_id)` returns `true` → `total_weight_rejected` gains this signer's weight. Later the *same* signer sends an Accept for the *same* block (legitimate: the signer protocol explicitly allows switching a vote away from a prior rejection "unless we receive a new block proposal for it and the reject reason allows us to reconsider" — i.e., reconsideration is a designed, reachable path, not byzantine behavior) [3](#0-2) . On the Accept, `gathered_signatures` does not yet contain this `slot_id` (only rejections had been recorded), so the guard passes and `total_weight_approved` is *also* incremented by the same signer's weight [4](#0-3) .
- Accept-then-Reject does not double-count, because the Accepted branch always inserts into `responded_signers` too, so a later Reject's `responded_signers.insert(slot_id)` returns `false` and is skipped.

The net effect: a signer's weight can be permanently counted in `total_weight_rejected` even after that signer switches to accepting the block, while simultaneously counting again in `total_weight_approved`. This breaks the intended invariant that each signer's weight is attributed to exactly one side of the tally — the aggregated-weight vs. verified-accepts/rejects equality that the coordinator's threshold logic depends on.

### Impact Explanation
This tally feeds `SignerCoordinator::get_block_status`'s decision logic on the node/miner side, which independently checks the reject-threshold (`total_weight_rejected.saturating_add(weight_threshold) > total_weight` → `SignersRejected`) and the accept-threshold (`total_weight_approved >= weight_threshold` → block accepted) [5](#0-4) . Because `total_weight_rejected` is never decremented when a signer reconsiders and switches to acceptance, stale rejection weight from signers who no longer oppose the block can remain permanently "baked in." This can cause the miner to conclude a block is globally rejected (crossing the >30% blocking-minority condition) using weight that no longer reflects the signer's current vote, i.e., a liveness wedge where a block that in fact has (or would have) sufficient current support is discarded as rejected. This matches the "High" impact category: the coordinator/miner path can be driven to treat a valid, sufficiently-supported block as rejected due to a stale/duplicated weight accounting bug, stalling block production.

### Likelihood Explanation
The trigger requires only ordinary, protocol-sanctioned signer behavior: one honest signer initially rejects a proposal, then legitimately reconsiders and accepts the same `signer_signature_hash` once the reject reason no longer applies (a documented, reachable code path in `signer.rs`) [6](#0-5) . No majority collusion, no other signer's key, and no auth-token access is needed — a single reconsidering signer combined with normal gossip propagation order (reject message observed before the later accept message) is sufficient to desynchronize the tally.

### Recommendation
Use a single per-signer record (e.g., an enum `SignerVote::Accepted | Rejected` stored per `slot_id`) as the sole gate for both branches, and when a signer's vote changes, subtract their weight from the previous bucket before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` always remain mutually exclusive per signer weight, mirroring how the report recommends keeping `total_shares` and the underlying assets in sync rather than updating one side of an accounting equality without the other.

### Proof of Concept
1. Miner proposes block B; signer S (weight W) initially rejects B for a reason that is later re-evaluable (e.g., a reorg/proposal timing reason).
2. `StackerDBListener` processes the `Rejected` message: `responded_signers.insert(S)` → true, `total_weight_rejected += W`.
3. The condition that caused S's rejection resolves (e.g., a new proposal arrives, or the chain state check now passes), and S's local signer state legitimately reconsiders and emits an `Accepted` response for the same `signer_signature_hash` per the documented reconsider path in `signer.rs`.
4. `StackerDBListener` processes the `Accepted` message: `gathered_signatures` does not contain S's `slot_id` yet → `total_weight_approved += W` is also applied.
5. Now W is counted in both `total_weight_rejected` and `total_weight_approved`. If enough other signers had also rejected (pushing `total_weight_rejected` toward the blocking minority) before reconsidering, the stale, never-decremented `total_weight_rejected` can still trip the `SignersRejected` branch in `signer_coordinator.rs`, discarding a block that no longer has sufficient real opposition — a liveness wedge triggered purely by legitimate vote reconsideration and message ordering.
