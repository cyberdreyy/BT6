### Title
Signer weight double-counted in both `total_weight_approved` and `total_weight_rejected` when a signer flips from Reject to Accept - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::handle_stackerdb_chunk` (the block-status tracker consumed by `SignerCoordinator::get_block_status`) tallies signer weight into two independent counters, `total_weight_approved` and `total_weight_rejected`, using two different de-duplication sets. Because the de-duplication for acceptance only checks `gathered_signatures` while rejection de-duplication uses `responded_signers` (which acceptance also populates but rejection-checking does not clear), a single signer that first rejects a block and later legitimately signs/accepts the same block has its weight counted in *both* totals permanently. This is the same bug class as the Yeti report: a per-signer "extra amount" is added to a running tally without first subtracting what was already counted against it, so the two tallies can jointly exceed the real total signer weight.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, when an `Accepted` message is processed: [1](#0-0) 

weight is added to `block.total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, then the slot id is inserted into both `gathered_signatures` and `responded_signers` unconditionally.

When a `Rejected` message is processed: [2](#0-1) 

weight is added to `block.total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot appears in `responded_signers`).

The two gating sets are asymmetric:
- Reject → Accept: the signer's slot is already in `responded_signers` (added during the earlier reject), but *not* in `gathered_signatures`. When the later `Accepted` arrives, `gathered_signatures.contains_key` is `false`, so the acceptance weight is added — on top of the reject weight that was already added and is never removed.
- Accept → Reject: the signer's slot is already in `responded_signers` (added during the earlier accept), so a later `Rejected`'s `responded_signers.insert(slot_id)` returns `false` and the rejection weight is correctly *not* added.

So only the Reject→Accept direction leaks: the signer's weight is simultaneously present in `total_weight_rejected` (stale) and `total_weight_approved` (current), breaking the invariant that `total_weight_approved + total_weight_rejected` should never exceed `self.total_weight` for the actively-responding signer set.

This is directly analogous to the Yeti finding: an "additional amount" (`additionalYetiTokenBalance` there, signer weight here) is credited to a running aggregate without being bounded by what has already been consumed/attributed elsewhere (`effectiveYetiTokenBalance` there, the other tally bucket here), so the aggregate can exceed the true total.

### Impact Explanation
`total_weight_rejected` and `total_weight_approved` are read directly by `SignCoordinator::get_block_status` in `stacks-node/src/nakamoto_node/signer_coordinator.rs` to decide, in order, whether the block is globally rejected (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`, checked first) or globally accepted (`total_weight_approved >= weight_threshold`): [3](#0-2) 

Because the reject tally is never decremented for a signer who later accepts, a legitimate flip (which the signer-side flow explicitly supports — a signer can reconsider and later sign after an earlier reject once "the reject reason allows us to reconsider") leaves a stale weight permanently counted against acceptance. Once enough such flips (or a flip combined with genuine rejections from other signers) accumulate, `total_weight_rejected` can cross the blocking-minority threshold even though the true current rejecting weight is below it, causing the miner's coordinator to declare the block `SignersRejected` and abort/retry a block that in reality has (or would have) reached the 70% acceptance threshold. This is a liveness wedge on the node/coordinator side rather than a chain-consensus-breaking defect (the tallies are ephemeral, in-memory, per-proposal), but it directly breaks the "aggregated-weight vs verified-accepts" equality the coordinator relies on to make its accept/reject decision.

### Likelihood Explanation
This requires only a single signer (one StackerDB slot, i.e., a one-slot participant) to send a `Rejected` message for a block and later send an `Accepted` message for the same `signer_signature_hash` — a scenario the signer's own logic explicitly allows and documents (rejecting for a transient reason, then reconsidering and signing once conditions change, or reaching the pre-commit threshold after an earlier rejection). No majority of signers, no other signer's key, and no auth token are needed — only gossip messages over StackerDB that any registered signer can legitimately emit.

### Recommendation
Use a single de-duplication mechanism (or explicitly move weight between buckets) so that a signer's weight can only ever be attributed to one of `total_weight_approved` / `total_weight_rejected` at a time. E.g., when an `Accepted` arrives for a slot previously present in `responded_signers` due to a prior rejection, subtract the signer's weight from `total_weight_rejected` before adding it to `total_weight_approved` (and symmetrically for the reverse transition), rather than gating the two counters with two different sets.

### Proof of Concept
1. Coordinator waits on `block_status` for a proposed block with `weight_threshold` set to 70% of `total_weight`.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for the block's `signer_signature_hash`; `stackerdb_listener.rs` records `responded_signers.insert(S)` → `true`, so `total_weight_rejected += w`.
3. Signer `S` later re-evaluates and sends `BlockResponse::Accepted` for the same hash (permitted by the signer's own reconsideration logic). `gathered_signatures.contains_key(S)` is `false` (never set by the reject path), so `total_weight_approved += w` as well — `S`'s weight `w` now sits in both totals.
4. With enough additional genuine rejections from other signers, `total_weight_rejected.saturating_add(weight_threshold) > total_weight` becomes true in `signer_coordinator.rs`, triggering `NakamotoNodeError::SignersRejected` even though the true, current rejecting weight (excluding `S`, who accepted) may be below the blocking minority.
