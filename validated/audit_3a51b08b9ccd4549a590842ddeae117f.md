### Title
Unauthenticated pipeline-run resume endpoint lets any client choose the result data used to complete a privileged pipeline task - (File: core/web/router.go)

### Summary
The MapleLoan bug class described in the report is: an actor with limited/no elevated privilege can supply arbitrary arguments to a sensitive state-transition function (an "upgrade"/migration call) that the contract executes without hardcoding or validating them, letting that actor bias the outcome in their favor or skip the intended logic. The Chainlink node has a structurally analogous pattern: the `PATCH /v2/resume/:runID` HTTP endpoint is registered with **no authentication middleware at all** and accepts an attacker-supplied JSON body that becomes the `pipeline.Result` used to resume/finish a suspended pipeline task run.

### Finding Description
In `v2Routes`, the resume route is mounted on the unauthenticated group before any auth middleware is applied: [1](#0-0) 

Compare this to every other pipeline-run route, which requires session/token authentication and role checks (`authv2.GET("/pipeline/runs", ...)`, `authv2.POST("/jobs/:ID/runs", auth.RequiresRunRole(...))`, etc.) at [2](#0-1)  and [3](#0-2) .

The handler for the unauthenticated resume route decodes a fully attacker-controlled JSON body into a `pipeline.ResumeRequest`, converts it into a `pipeline.Result`, and calls into the application layer without any authorization check tied to caller identity — the only "secret" gating this call is knowledge of the `runID` (a UUID `taskID`): [4](#0-3) 

The audit event name itself documents that this is an intentionally unauthenticated action: [5](#0-4) 

This mirrors the MapleLoan pattern precisely: a caller who should have no (or only very limited) trust is allowed to freely choose the arguments/result data fed into a sensitive completion routine (`ResumeJobV2` → `pipelineRunner.ResumeRun`), rather than the node hardcoding/validating expected outcome data itself. Just as the borrower could pick migration arguments favorable to themselves or "noop" the migration by choosing arguments that skip the real logic, here any party who obtains or guesses a pending task's `runID` can inject an arbitrary `Result.Value`/`Result.Error` to force a suspended pipeline task (e.g., an external/bridge adapter callback task awaiting an async result) to complete with attacker-chosen data, bypassing whatever the legitimate external system was supposed to return.

### Impact Explanation
If an attacker can obtain or predict a `runID`/`taskID` for a suspended pipeline task (for example via response bodies, logs, or a bridge that echoes it to an external party as part of a legitimate async callback flow), they can call this fully unauthenticated endpoint to inject arbitrary result data into that task, directly influencing downstream pipeline computation results (which can feed into on-chain writes, VRF fulfillment values, price data, etc., depending on the job/task in question) — an outcome-manipulation impact analogous to the borrower forging favorable migration/upgrade arguments.

### Likelihood Explanation
Exploitation is fully gated by knowledge of the `runID`, which is a UUID generated per-task and only intended to be known by the specific external system participating in that task's designed callback (e.g., the bridge/external adapter it was sent to). The report explicitly asks me to reject "no impact" analogs and require it be reachable from an "unprivileged client request" — this endpoint is reachable with zero authentication, satisfying that bar structurally, but full weaponization additionally requires the attacker to learn a valid pending `runID`, which is not guaranteed to be disclosed to arbitrary unprivileged parties in the general case. I was not able to fully trace, within the available iterations, every task type/bridge flow that surfaces `runID` values to third parties, so I cannot conclusively confirm real-world disclosure paths for this identifier; that would need further investigation of the bridge/external-adapter response format and any job specs that echo `runID` back to external callers.

### Recommendation
- Require the resume request to be authenticated and bound to the specific external system/bridge that owns the corresponding pending task (e.g., via a per-task shared secret or scoped bridge API token), rather than trusting solely knowledge of the `runID`.
- Alternatively, restrict `/v2/resume/:runID` to authenticated bridge/external-initiator credentials the same way `/v2/jobs/:ID/runs` uses `auth.AuthenticateExternalInitiator`/`auth.AuthenticateByToken` at [6](#0-5) .
- Validate/sanitize the `pipeline.Result` payload against the expected task type/schema before resuming, rather than trusting attacker-supplied `Value`/`Error` fields verbatim, matching the "hardcode expected arguments, don't let the caller choose them" recommendation from the report.

### Proof of Concept
1. Identify a job with a task that suspends pending an external callback (produces a `runID`/`taskID`).
2. Without any authentication, send:
   `PATCH /v2/resume/<runID>` with body `{"value": "<attacker-chosen result>"}` (per `pipeline.ResumeRequest`/`ToResult()` at [7](#0-6) ).
3. The node resumes the pipeline run using the attacker-supplied value with no authentication check performed at [8](#0-7) , completing the task as if the legitimate external system had returned that result.

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```
