## Analog Found

### Title
Stale confirmations from removed multisig members are not purged from in-flight requests, allowing a request to execute below the live-member confirmation threshold - (`multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
This mirrors the HydraDX Oracle bug class: state belonging to a removed entity (an oracle price entry / here, a multisig member's confirmation) is left behind in a shared aggregate, and later combines with fresh state to produce an incorrect result. In the multisig contracts, a member's confirmation on a request they did **not** create survives that member's removal, and is still counted toward the `num_confirmations` threshold, letting a request execute with fewer *live* confirming members than required.

### Finding Description
Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` clean up confirmations for a removed key/member only for requests that member itself *created* (the `signer_pk`/`member` field on `MultiSigRequestWithSigner`), not for requests where that member merely *confirmed*: [1](#0-0) [2](#0-1) 

The confirmation set itself is populated by `confirm()` regardless of who created the request: [3](#0-2) [4](#0-3) 

The removal path (`DeleteKey` in `multisig`, `DeleteMember` in `multisig2`) only scans and purges requests whose *original signer* matches the removed key/member:

```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter(|(_k, r)| r.signer_pk == pk)   // only matches requests THEY created
    .map(|(k, _r)| k)
    .collect();
```

If member `A` confirms a request `R` created by member `B` (not `A`), and `A` is later removed via a separate `DeleteKey`/`DeleteMember` request, `A`'s stale confirmation on `R` is never purged — `R`'s signer is `B`, so the filter `r.signer_pk == pk` (or `r.member == member`) never matches `R`. `R`'s `confirmations` set continues to contain `A`, a no-longer-valid member.

When enough remaining live members confirm `R`, the threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations` counts `A`'s stale confirmation as valid, executing the request with fewer live-member confirmations than `num_confirmations` actually requires. This breaks the binding: *confirmations counted versus live members*.

### Impact Explanation
This allows a `MultiSigRequest` (e.g. `Transfer`, `AddKey`/`AddMember`, `FunctionCall`) to be executed while backed by fewer than `K` currently-authorized signers — effectively a multisig request executed below threshold. This is a Critical-severity custody-binding violation: funds can be moved, or a malicious key/member can be added, using one fewer live confirmation than intended, provided one confirmer was later removed from the multisig without ever having created the pending request.

### Likelihood Explanation
This requires no special privilege beyond being a (former) legitimate multisig member. It requires:
1. Member `B` creates request `R`.
2. Member `A` (different member) confirms `R` (not enough to execute yet).
3. Member `A` is later removed from the multisig via a normal `DeleteKey`/`DeleteMember` request (a routine operational action, e.g. offboarding a signer).
4. Remaining members confirm `R` until `A`'s stale confirmation plus new confirmations reach `num_confirmations`.

Because member turnover and confirming requests created by others are both ordinary, expected multisig usage patterns (not privileged attacker actions), this is readily reachable in normal contract operation.

### Recommendation
When removing a key/member (`DeleteKey` in `multisig`, `DeleteMember` in `multisig2`), scan **all** pending requests' `confirmations` sets (not just requests the removed party created) and strip the removed key/member's entry from each. Alternatively, when `confirm()` reaches threshold, validate that every entry in the request's `confirmations` set still corresponds to a current key/member before allowing execution.

### Proof of Concept
Using the `multisig2` contract with members `{A, B, C}` and `num_confirmations = 2`:
1. `B` calls `add_request_and_confirm(R)` where `R` = `Transfer{amount}` — `R.member = B`, `confirmations = {B}`.
2. `A` calls `confirm(R)` — `confirmations = {B, A}`... wait, but if this already reaches 2 it'd execute. Instead assume `num_confirmations = 3`, members `{A,B,C,D}`:
   - `B` creates and confirms `R` — `confirmations = {B}`.
   - `A` confirms `R` — `confirmations = {B, A}` (below threshold 3, request stays pending).
3. Separately, members create and confirm a `DeleteMember{member: A}` request — this only purges requests whose `r.member == A` (i.e., requests **A created**), so `R` (created by `B`) is untouched; `A` is removed from `self.members`, but `R.confirmations` still contains `A`.
4. `C` calls `confirm(R)` — `confirmations.len() + 1 = 3 >= num_confirmations(3)` → `R` executes, backed by confirmations from `B`, `A` (no longer a member), and `C` — i.e., only 2 live members truly authorized it despite the threshold being 3. [5](#0-4) 
The existing test only exercises the case where the removed member is the request's own signer/creator (cleanly purged); it does not cover the case where the removed member is merely a confirmer of someone else's request, which is exactly the gap described above.

            "Already confirmed this request with this key"
        );

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
