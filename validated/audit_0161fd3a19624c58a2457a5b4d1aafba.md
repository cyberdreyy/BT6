### Title
Storage-slot collision safety net for precompile layouts is compiled out in production builds - (File: `crates/common/precompile-macros/src/layout.rs`)

### Summary
The `#[contract]` macro used to define every native precompile's storage layout (B-20 asset/stablecoin/factory, policy registry, activation, nonce, token-accounting) generates a `__check_all_collisions()` routine that verifies no two fields (including namespaced/`Mapping` fields mixed with sequentially-packed fields) resolve to the same storage slot. This is the exact mitigation class the external report recommends (recommendation 2: "check the storage layout ... to verify"). However, the generated check — and the call site that invokes it — are both gated behind `#[cfg(debug_assertions)]`, so the check is entirely absent from release binaries, which is what production Base nodes run.

### Finding Description
`gen_collision_checks` in `crates/common/precompile-macros/src/layout.rs:273-293` emits `__check_all_collisions()` wrapped in `#[cfg(debug_assertions)]` [1](#0-0) , and the constructor generated by `gen_constructor` only calls it inside the same `#[cfg(debug_assertions)]` block [2](#0-1) .

`debug_assertions` is off in `--release` builds, which is the build profile used for production node binaries (`base`, `base-builder`, etc.). Consequently, in the binaries that actually execute on mainnet/testnet, this per-precompile struct layout validation never runs. Every native precompile that composes storage via `#[contract]`/`#[namespace]` (`B20Asset`, `B20Stablecoin`, `B20Factory`, `PolicyRegistryStorage`, `TokenAccounting`, activation and nonce registries — see `crates/common/precompiles/src/{b20_asset,b20_factory,b20_stablecoin,common/token_accounting,policy,activation,nonce}/storage.rs`) relies on this macro-generated check as its only automated guard against a field-slot collision such as an owner/admin-controlling field landing on the same slot as a per-user `Mapping` field, exactly the class of bug in the ProxyStorage report where `_implementation`/`_owner` collide with verifier fields.

This mirrors the report's risk precisely: the storage layout tooling exists (matching recommendation 2 — "recommended to check the storage layout... we recommend building a small tool for doing this"), but it is neutralized in the artifact that is actually deployed, so any latent or future-introduced collision (e.g., during an upgrade that appends fields, or a mistake mixing `#[namespace]` and manual `#[slot]`/`#[base_slot]` on the same layout) would go completely undetected in production, silently corrupting critical native-precompile state such as ownership/admin/balance slots.

### Impact Explanation
If a colliding layout is ever introduced (now or in a future precompile/upgrade), a single ordinary transaction that triggers a normal precompile write path (e.g., a B-20 transfer, mint, or policy update reachable by any unprivileged token holder/caller) could overwrite an unrelated critical field such as a token's admin/owner-controlling slot or total-supply accounting slot, because the write would land on the aliased slot with no runtime check to catch it. That can translate into unauthorized privilege escalation over a B-20 asset/stablecoin, incorrect supply accounting (unbacked supply), or funds becoming inaccessible — the same fund-theft/freezing impact called out in the original report. This is High risk because the affected code paths (B-20 precompiles) are protocol-native and directly control token supply/ownership.

### Likelihood Explanation
Likelihood is contingent on a layout collision actually existing or being introduced; I was not able to confirm, within the available search budget, that a concrete overlapping-slot instance currently exists in the shipped `B20Asset`/`B20Stablecoin`/`B20Factory`/`PolicyRegistryStorage` definitions — the crate's namespacing (`#[namespace("b20")]`, `#[namespace("b20.asset")]`, etc.) and its `README.md` "append-only rule" appear designed to avoid this in the currently-committed layouts. What is concretely proven is that the only automated defense against such a collision is stripped from release builds, so any collision that is introduced by a future change (a very plausible mistake given the macro's flexibility — mixing `#[slot]`, `#[base_slot]`, and `#[namespace]` on the same struct) would ship to production undetected. This is a latent-defect / missing-safety-net finding rather than a demonstrated exploit against a specific currently-deployed field pair.

### Recommendation
Make `__check_all_collisions()` unconditional (or run it once at process start / via a `const`-evaluated compile-time assertion) instead of gating it behind `#[cfg(debug_assertions)]`, so release builds retain the same protection debug builds have. Since slot indices and field offsets are compile-time constants, the check should ideally be turned into a `const _: () = { assert!(...) };` block evaluated at compile time (true recommendation-1/2 style enforcement), removing any runtime/profile dependence entirely.

### Proof of Concept
Not applicable as a runnable exploit against a specific existing collision — the concrete, provable artifact is the gating itself: [2](#0-1) [1](#0-0) 

Building any node binary with `cargo build --release` (the profile used for shipped/production binaries) compiles out the `__check_all_collisions` call for every precompile defined via `#[contract]` in `crates/common/precompiles/src/{b20_asset,b20_factory,b20_stablecoin,common/token_accounting,policy,activation,nonce}/storage.rs`, so a colliding layout introduced in any future PR to these files would pass CI/tests built in debug but silently corrupt state once deployed in the release binary actually run by validators/sequencers/RPC nodes.
