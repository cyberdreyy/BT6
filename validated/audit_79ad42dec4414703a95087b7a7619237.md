This is a genuine vulnerability in `multisig2/src/lib.rs`: `delete_member` at line 356-379 only cleans up `confirmations` for requests that the deleted member *originated* (`r.member == member` filter at line 365), but does not scan `confirmations` sets across all pending requests for the deleted member's stale confirmation entries left as a *confirmer* on other members' requests. `confirm()` at line 294-315 counts `confirmations.len() as u32 + 1 >= self.num_confirmations` purely against the stored `HashSet<String>` without re-validating that every entry in that set is still a current member (`self.members.contains(...)`), unlike `assert_valid_request`/`current_member()` which only checks the *caller's* live membership, not the *stored* confirmers.

### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing request execution below the live-member quorum - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in [1](#0-0)  counts confirmations solely from the `confirmations: LookupMap<RequestId, HashSet<String>>` map, incrementing and comparing against `self.num_confirmations` without checking whether each recorded confirming member is still present in `self.members`. `delete_member` in [2](#0-1)  only removes confirmations for requests whose *original requester* (`r.member`) equals the member being deleted (`r.member == member` filter at line 365); it never inspects the `confirmations` sets of other pending requests to strip out entries where the removed member had merely *confirmed* (not originated) the request.

### Finding Description
When a member confirms a request they didn't originate, their identity string is added to that request's `confirmations` `HashSet<String>` via [3](#0-2) . If that member is later removed via a `DeleteMember` action, `delete_member` at [4](#0-3)  only purges requests they *originated* — the guard `self.members.len() - 1 >= self.num_confirmations` at line 358 permits the removal as long as remaining membership count still meets the confirmation count, oblivious to which specific pending requests already carry that member's now-stale confirmation. The removed member's string remains inside `confirmations` for the untouched request. A subsequent live member calling `confirm` on that pending request in [5](#0-4)  only checks size (`confirmations.len() as u32 + 1 >= self.num_confirmations`), so the stale, no-longer-a-member confirmation is silently counted toward the threshold, causing `execute_request` to run with a live-quorum of members strictly fewer than `num_confirmations`.

The equality that should hold is: `confirmations counted == confirmations from currently live members`. This bug breaks it to: `confirmations counted == confirmations from members live at time of confirming, regardless of subsequent removal`.

### Impact Explanation
This crosses the authorization/threshold boundary explicitly named in scope ("confirmations counted versus live members"). It allows a multisig request — including `Transfer`, `FunctionCall`, `AddKey` (full access key grant), or `DeployContract` — to execute with fewer genuinely live confirming members than `num_confirmations` requires, i.e., "a multisig request executed below threshold" (Critical per the given impact classification), since one confirming party has effectively been evicted from the multisig yet their vote still counts.

### Likelihood Explanation
This requires normal multisig operation flow without any external actor, malicious validator, or redeploy: (1) member A originates a request, (2) member B (not the originator) confirms it, (3) the members later legitimately vote to remove member B via `DeleteMember` (e.g., an offboarding), while A's earlier request remains pending and unconfirmed by enough members, (4) a remaining live member confirms, at which point B's stale confirmation is silently counted. This is a realistic operational sequence for any multisig wallet with active pending requests during membership changes, not a contrived edge case.

### Recommendation
When deleting a member in `delete_member`, iterate all pending `confirmations` entries (not just requests originated by that member) and remove the deleted member's identity string from every set; alternatively, when counting confirmations in `confirm`, filter `confirmations` against `self.members.contains(...)` before comparing to `self.num_confirmations`, so only currently live members' confirmations count toward the threshold.

### Proof of Concept
1. Deploy `MultiSigContract::new` with 4 members `[A, B, C, D]` and `num_confirmations = 3` (as in [6](#0-5) ).
2. Member A calls `add_request` to create a `Transfer` request `R` (1 confirmation implicitly none yet; A is the recorded requester at [7](#0-6) ).
3. Member B calls `confirm(R)` — since `confirmations.len() (0) + 1 (2) < 3`, B's identity is stored in `confirmations[R]` (line 311-312). Now `confirmations[R] = {A? no — actually A must confirm too; assume A also confirmed via add_request_and_confirm, so confirmations[R] = {A, B}}`.
4. The group votes to remove member B via `add_request_and_confirm` with `DeleteMember { member: B }`, executed by 3 live members (A, C, D). `delete_member` checks `members.len()-1 (3) >= num_confirmations (3)` — passes — and removes B from `members`, but request `R` is untouched because `R`'s originator is A, not B (filter at line 365 doesn't match), so `confirmations[R]` still contains B's stale entry.
5. Member C now calls `confirm(R)`. `confirmations.len() (2) + 1 (3) >= num_confirmations (3)` — passes — and `execute_request` runs the `Transfer`, even though B is no longer a member: only A and C are truly live confirmers, one short of the required 3 live confirmations.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);

            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));

        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
