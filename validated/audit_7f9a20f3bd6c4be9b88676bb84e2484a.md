Based on the code I reviewed, the technical claim in the question about `stackerdb_listener.rs` is accurate, but I could not fully verify (within the tool budget) whether an honest signer can legitimately emit an Accept followed by a Reject for the *same* hash under the described "pre-commit RECHECK" flow — which is required to determine real exploitability by the scoped, unprivileged attacker.

### Title
Later Reject from a slot that already Accepted a block never retracts the earlier signature/weight - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
In the `BlockResponse::Accepted` handler, `block.gathered_signatures.insert(slot_id, signature)` and `block.responded_signers.insert(slot_id)` run unconditionally on every verified Accept for a slot [1](#0-0) . If that same slot subsequently sends a `Rejected` for the identical hash, the `Rejected` branch's effect on `total_weight_rejected`/`failed_txids` is gated by `block.responded_signers.insert(slot_id)` returning `true`, but since the slot was already inserted into `responded_signers` by the earlier Accept, this insert returns `false` and the whole rejection-accounting block is skipped entirely [2](#0-1) . There is no code path anywhere that removes a slot's entry from `gathered_signatures` or decrements `total_weight_approved`.

### Finding Description
The equality the code should maintain is: weight aggregated toward finalization == weight of Accepts whose signer has not subsequently, authoritatively rejected the same hash. Instead, the actual invariant maintained is: weight aggregated == weight of the *first* Accept ever seen per slot per hash, permanently, with any later Reject from that slot for that hash being silently dropped (it doesn't even update `responded_signers` state or rejection weight) because `HashSet::insert` returns `false` for an already-present slot_id [3](#0-2) . This is confirmed and is a real gap in the aggregation logic in `signer_coordinator.rs`'s `get_block_status`, which finalizes on `block_status.gathered_signatures.values().cloned().collect()` once `total_weight_approved >= weight_threshold` [4](#0-3) .

However, I was **not able to confirm** the key precondition the question depends on: that an honest, correctly-functioning signer can legitimately emit an Accept and then a Reject for the *exact same* `signer_signature_hash` as part of normal protocol operation (e.g., a "pre-commit RECHECK" race). This aggregation code lives on the **miner/node side** (`stacks-node`), which only reflects whatever `BlockResponse` messages a signer chooses to gossip — it cannot itself cause a signer to double-respond. Whether the stacks-signer state machine (`stacks-signer/src/v0/signer.rs`, `signerdb.rs`) has a code path that allows sending Accept then later Reject for the same hash after a "recheck" is unresolved from what I reviewed; I found matches for `PreCommit`/`recheck` in `signerdb.rs` and `v0/signer.rs` but ran out of iterations to read those functions and confirm.

### Impact Explanation
If the precondition holds (an honest signer, or the attacker's own single-weight slot, can send Accept-then-Reject for the same hash), the miner would count and finalize on a signature the signer has since disavowed, which is a Critical-category issue (rejection recounted as acceptance) per the rubric. If it does not hold — i.e., the signer state machine never re-emits a Reject for a hash it already Accepted — this path is unreachable and the bug is at most a latent/defensive-coding gap with no attacker-triggerable impact, since the attacker (limited to one miner slot + gossip, no other signer's key) cannot forge another signer's Accept/Reject messages, and their own slot's weight already legitimately counts toward `total_weight_approved` regardless of this bug.

### Likelihood Explanation
Cannot be conclusively assessed without confirming the stacks-signer-side state machine can legitimately produce this Accept-then-Reject-same-hash sequence for an honest signer. The attacker as scoped (single miner/signer slot, no other signer's key, no auth_token, no local access) cannot themselves inject a forged Accept under another signer's identity — `signer_pubkey.verify` requires a valid signature from that signer's own key [5](#0-4) , and rejections require `recover_public_key()` to match the claimed signer [6](#0-5) . So the attacker alone cannot manufacture the "stuck accept" scenario against a victim signer; it would require an honest signer's own logic bug/race to occur naturally, which is outside what I could confirm from the reviewed files.

### Recommendation
Given the uncertainty, I recommend deferring judgment until the stacks-signer state machine's Accept/Reject transition logic is reviewed. If a legitimate Accept→Reject-same-hash sequence is possible on the signer side, `stackerdb_listener.rs` should be changed so a `Rejected` message from a slot that previously `Accepted` the same hash removes that slot's entry from `gathered_signatures`, decrements `total_weight_approved` by that signer's weight, and only then proceeds to update rejection accounting.

### Proof of Concept
Not constructed, pending confirmation of the signer-side precondition. If confirmed, the test would: insert a block into `StackerDBListener::blocks`, feed an `Accepted` message for `slot_id=0` (asserting `gathered_signatures.contains_key(&0)` and `total_weight_approved == weight_0`), then feed a `Rejected` message from the same `slot_id=0`/same hash, and assert `gathered_signatures.contains_key(&0) == false` and `total_weight_approved == 0` — which currently fails since no retraction path exists.
