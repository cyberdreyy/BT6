### Title
Per-account write-lock cost limit can be front-run to censor a targeted user's transaction within a block - (File: cost-model/src/cost_tracker.rs)

### Summary
The Agave cost tracker enforces a fixed per-writable-account compute-unit budget (`MAX_WRITABLE_ACCOUNT_UNITS = 24_000_000`) inside `CostTracker::would_fit` [1](#0-0) . Any ordinary transaction that writes to that account is checked against this account-scoped ceiling before being admitted into the block being built [2](#0-1) . This is structurally the same pattern as the reported `maxContractBalance` bug: a shared, fixed-capacity resource keyed by a single identifier (there, the contract's total balance; here, a specific writable account's per-block cost budget) that any unprivileged party can top-off first, causing a subsequent legitimate user's transaction targeting the same resource to be rejected.

### Finding Description
`CostTracker::would_fit` performs three checks for every transaction attempting to enter a block: block-wide CU limit, per-transaction CU limit, and — critically — a per-writable-account CU limit (`account_cost`, default `MAX_WRITABLE_ACCOUNT_UNITS`) that is checked against `self.cost_by_writable_accounts` for every account the transaction writes to [3](#0-2) . Because this cost is tracked per pubkey and cumulatively summed across all transactions in the same block that write-lock that pubkey, any user can submit low-value, cheap-but-CU-heavy transactions that write to a specific target account (e.g., a shared PDA, an AMM pool, an auction/market account, a program's state account) to saturate that account's `MAX_WRITABLE_ACCOUNT_UNITS` budget before a victim's transaction touching the same account is processed in that slot. The existing unit tests already demonstrate this exact "fills up, blocks the next writer" behavior: `test_cost_tracker_chain_reach_limit` shows that once an account's cost budget is consumed, a second transaction touching the same account is rejected even though the block as a whole has capacity [4](#0-3) . The rejection surfaces as `TransactionError::WouldExceedMaxAccountCostLimit`, tracked via `accumulate_cost_limit_error` in banking stage [5](#0-4) , and the transaction is dropped/retried, exactly mirroring the "Limit hit" revert in the original report.

Unlike the original Solidity bug (a permanent global state variable persisting across transactions until manually withdrawn), this Solana analog resets every block/slot, so the "attacker deposit / victim fails / attacker withdraw" cycle here is naturally per-slot rather than persistent — the attacker must repeat the same-account saturation transaction in every slot they want to censor the victim, and only for that one slot's leader.

### Impact Explanation
An attacker (any fee-paying wallet, no special privilege) can selectively deny an ordinary user's transaction from landing in a given block whenever that transaction writes to an account the attacker also targets, by submitting their own transactions against that same account first (or in a bundled/co-located submission to the current leader). This enables market manipulation analogous to the original report: e.g., preventing rival bidders/traders from writing to a shared auction or pool account during a specific slot, forcing their transaction to fail and retry (potentially missing a deadline, a bid window, or arbitrage opportunity), while the attacker's own transaction to the same account succeeds. This is a real censorship/DoS primitive reachable purely from ordinary user transactions via the standard TPU ingest → banking stage → cost tracker admission path.

### Likelihood Explanation
Likely to be low/medium in practice: this per-account limit (`MAX_WRITABLE_ACCOUNT_UNITS = 24,000,000` CU, i.e. 40% of the 60M CU block budget) is large, so saturating it purely to deny one specific victim transaction requires substantial CU spend by the attacker within a single slot, and the effect only lasts for that one slot (next slot resets the tracker). It is most exploitable against accounts with naturally low activity/low CU ceilings relative to attacker budget, or in combination with other mechanisms (e.g., repeated slot-by-slot griefing, or coordination with the current leader). This is a known design property of Solana's per-account cost accounting rather than a memory-safety or fund-theft bug, but it is a legitimate reachable griefing/censorship vector directly analogous to the reported bug class.

### Recommendation
Consider whether `MAX_WRITABLE_ACCOUNT_UNITS` should be dynamically scaled (e.g., relative to account activity/contention) rather than a single static per-account ceiling shared indiscriminately by all writers, and/or expose better local-fee-market signals so that legitimate transactions can outbid griefing transactions for the same account's write-lock budget within a slot (similar in spirit to the Reality Cards team's fallback of treating the limit as a toggle rather than a hard exploitable partition). At minimum, document this per-account limit explicitly as a griefing surface so RPC/wallet tooling can detect and retry across leaders/slots rather than treating `WouldExceedMaxAccountCostLimit` as a terminal failure.

### Proof of Concept
1. Identify a target account `T` that a victim's upcoming transaction will write-lock (e.g., a shared pool/auction account).
2. In the same slot (or repeatedly across the leader's slot window), submit attacker transactions that write-lock `T` with combined compute-unit cost approaching `MAX_WRITABLE_ACCOUNT_UNITS` (24,000,000 CU) — this is straightforward since `would_fit` sums `chained_cost.saturating_add(cost)` per writable account with no per-sender fairness [6](#0-5) .
3. Once the victim's transaction touching `T` is processed by `try_add`/`would_fit`, it is rejected with `CostTrackerError::WouldExceedAccountMaxLimit` → `TransactionError::WouldExceedMaxAccountCostLimit`, exactly as reproduced by `test_cost_tracker_chain_reach_limit` [7](#0-6) , even though the overall block still has spare CU capacity.
4. The attacker's own transactions against `T` succeed and are committed, giving them exclusive access to `T` for that slot.

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }
