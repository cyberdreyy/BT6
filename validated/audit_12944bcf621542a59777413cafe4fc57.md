`insert_block` in `stacks-signer/src/signerdb.rs` serializes the entire `BlockInfo` (including the full `NakamotoBlock` with its header) as JSON, and `block_id()` is a *derived* value computed from the header fields (`consensus_hash` and block header hash), not a separately stored/round-tripped column that could drift independently. [1](#0-0)  The `block_id` used at line 1813 is only used for a debug log line, not stored as an authoritative separate value, so there is no place where persistence could produce a *different* id than what's recomputed from the stored block bytes on lookup. [2](#0-1) 

The existing test suite in `signerdb.rs` explicitly exercises this round-trip: `test_update_block` inserts a block and then asserts `BlockInfo::from(block_proposal.clone()) == block_info` after `block_lookup`, and `test_basic_signer_db`/migration tests (e.g. lines 5170-5176) re-insert and re-fetch blocks, asserting equality of the full `BlockInfo`, which subsumes the block id (derived from the header) not changing across a persist/load cycle. [3](#0-2) [4](#0-3) 

Because `block_id` is computed deterministically from the header fields that are themselves part of the serialized/deserialized `NakamotoBlock` (not a separately-stored, potentially-inconsistent field), a standard JSON serde round trip through sqlite (`serde_json::to_string` / deserialize back) cannot change the derived id unless serde itself loses fidelity on the header fields — which is out of scope per the rules (serde defects with no path through signer logic are explicitly excluded). I found no code path in `signerdb.rs` or `stacks_client.rs::submit_block_for_validation` where the persisted block id is computed or compared separately from the block's own header such that an attacker-controlled proposal could cause the two to diverge.

I was unable to fully inspect `stacks_client.rs::submit_block_for_validation`'s exact body (the tool did not return its content in this session), so I cannot cite its precise internals, but the reachable path into it (via `signer.rs` lines 1670-1727) always passes the same `block_proposal.block` object that was used to compute `signer_signature_hash` and is inserted via `insert_block` — there is no separate "id" field derived independently before/after persistence in the code I was able to examine.
