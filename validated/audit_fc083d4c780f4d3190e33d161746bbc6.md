## Title
Missing minimum-length check on hex-encoded `workflowID`/`workflowOwner` allows a negative-count `strings.Repeat` panic in the HTTP Trigger Gateway handler - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
The Gateway's HTTP trigger handler validates user-supplied `workflowID`/`workflowOwner` hex strings with `validateHexInput()`, which only enforces a **maximum** length and hex validity, but never checks the string against the **exact/expected** length. The subsequent `normalizeHex()` helper assumes the input can only be shorter than or equal to the expected hex length (after removing an optional `0x` prefix) and left-pads it using `strings.Repeat("0", expectedHexLength-len(hexStr))`. An attacker who omits the `0x` prefix can submit a hex string whose length equals the constant `workflowIDLength`/`workflowOwnerLength` (which was defined assuming the `0x` prefix is present), causing `expectedHexLength-len(hexStr)` to go negative and `strings.Repeat` to panic.

### Finding Description
`validateHexInput()` only rejects inputs that are *too long*, not inputs whose length doesn't match after accounting for the (optional) `0x` prefix: [1](#0-0) 

The constants for expected length embed the 2-character `0x` prefix in the count: [2](#0-1) 

After validation, `resolveWorkflowID` normalizes the (validated) `workflowID`/`workflowOwner` via `normalizeHex`, which strips any `0x` prefix and left-pads assuming `len(hexStr) <= expectedHexLength`: [3](#0-2) 

If a client submits `workflowID` **without** the `0x` prefix but with exactly `workflowIDLength` (66) hex characters — i.e., 33 bytes' worth of hex digits instead of the intended 32 bytes (64 hex chars) — `validateHexInput` accepts it because:
- `len(input) == 66 == workflowIDLength` → the "too long" check (`len(input) > expectedLength`) does not trigger.
- `hex.DecodeString` on 66 hex characters succeeds (even length, valid hex chars).

Then in `normalizeHex(workflowID, 66)`:
- `hexStr := strings.TrimPrefix(input, "0x")` leaves the string unchanged (no prefix present), so `len(hexStr) == 66`.
- `expectedHexLength := length - 2` → `64`.
- `paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr))` → `strings.Repeat("0", -2)`.

`strings.Repeat` panics with a negative count. This is exactly the class of bug described in the reference report: the length-validation logic assumes a fixed relationship between input length and encoded byte length without accounting for all valid input shapes (odd length / too short / too long relative to what downstream code assumes), causing either silent data corruption (upstream report) or, here, an outright crash.

This code path is reached directly from an unprivileged/external client request: `HandleJSONRPCUserMessage` on the gateway handler invokes `HandleUserTriggerRequest` synchronously with attacker-controlled JSON-RPC parameters: [4](#0-3) 

which flows to `validatedTriggerRequest` → `validateWorkflowFields` → `validateWorkflowID`/`validateWorkflowOwner` (passes) → `resolveWorkflowID` → `normalizeHex` (panics): [5](#0-4) [6](#0-5) 

### Impact Explanation
Whether this results in a crash of the whole Gateway node process (denial of service to all workflows served by that Gateway) depends on whether the code that ultimately invokes `HandleJSONRPCUserMessage` (the websocket/JSON-RPC message dispatch loop in `core/services/gateway/network`) wraps per-request handling in a `recover()`. I was not able to confirm the presence or absence of such a recover wrapper around this specific call within the available search budget — `recover()` usage was found only in test files under `core/services/gateway`, not in the production dispatch code I inspected (`wsserver.go`, `httpserver.go`, `handler.go`). If no recovery exists at that layer, an unauthenticated/unprivileged HTTP-trigger request can crash the Gateway process, disrupting all workflow trigger delivery for the DON shard(s) served by that Gateway (denial of service). If a recover does exist, the impact is limited to a failed/erroring single request, which is still a data-validation defect but not directly exploitable for DoS.

### Likelihood Explanation
The request path is reachable by any client capable of sending an HTTP trigger JSON-RPC request to the Gateway (`workflows.execute`), with no special privileges required beyond producing a syntactically valid JSON-RPC request — authorization (`authorizeRequest`) happens *after* `resolveWorkflowID`, so the panic can be triggered before any authentication/authorization check succeeds. Crafting the malicious `workflowID` value requires no special knowledge beyond omitting the `0x` prefix and choosing the exact boundary length, which is trivial to construct.

### Recommendation
In `validateHexInput`, require the input length (after removing an optional `0x` prefix) to match the expected hex-digit count exactly (or, at minimum, bound it on both ends), rather than only checking `len(input) > expectedLength`. Concretely:
- Normalize (strip `0x`) before comparing lengths.
- Validate `len(hexStr)` equals `expectedLength-2` (or otherwise define/document the accepted length range, e.g. if left-padding to a canonical length is intended, enforce `len(hexStr) <= expectedLength-2` explicitly) before calling `normalizeHex`.
- In `normalizeHex`, guard against `expectedHexLength-len(hexStr) < 0` and return an error instead of calling `strings.Repeat` with a negative count.

### Proof of Concept
1. Send a JSON-RPC `workflows.execute` request to the Gateway’s HTTP trigger endpoint with:
```json
{
  "jsonrpc": "2.0",
  "id": "poc-1",
  "method": "workflows.execute",
  "params": {
    "workflow": { "workflowID": "1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef" },
    "input": {}
  }
}
```
   Note: the `workflowID` value has exactly 66 lowercase hex characters and **no** `0x` prefix.
2. `validateHexInput` accepts it (`len(input) == 66 == workflowIDLength`, valid hex, lowercase).
3. `resolveWorkflowID` calls `normalizeHex(workflowID, 66)`, computing `strings.Repeat("0", 64-66)`, which panics with `"strings: negative Repeat count"`.

Verification that this panic escapes unrecovered up to the Gateway's message-processing goroutine (rather than being caught by a `recover()` in the websocket/HTTP dispatch layer) requires further investigation of `core/services/gateway/network/wsserver.go` and `httpserver.go`, which I could not fully complete due to tool-call limits in this session.

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)
	workflowID := triggerReq.Params.Workflow.WorkflowID
	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
	}
	workflowOwner := normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)
	workflowName := "0x" + hex.EncodeToString([]byte(workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName)))
	workflowID, found := h.workflowMetadataHandler.GetWorkflowID(
		workflowOwner,
		workflowName,
		triggerReq.Params.Workflow.WorkflowTag,
	)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "Workflow not found. Provide either a valid 'workflowID' or a valid combination of 'workflowOwner', 'workflowName', and 'workflowTag'", callback)
		return "", errors.New("workflow not found")
	}
	return workflowID, nil
}
