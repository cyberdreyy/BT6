### Title
Second withdraw request overwrites `lastWithdrawRequest`, bypassing `lossRecoveryPriceByEpoch` haircut and paying a loss-adjusted receipt at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When a borrower partial default occurs mid-epoch, `stopEpochWithDuration` funds pending withdraw receipts at a reduced `lossRecoveryPriceByEpoch[epochNumber]`. The loss-adjusted claim path is keyed solely by `lastWithdrawRequest[user]`, which is overwritten on every new `requestWithdraw`. A user who holds a haircutted receipt from epoch E1 can inject a second request in a later epoch E2, resetting the delimiter (`lastWithdrawRequest = E2`). Because `lossRecoveryPriceByEpoch[E2] == 0`, `_claimLossAdjustedWithdrawRequest` returns 0 and `_claimFundedWithdrawRequest` pays the full aggregate `withdrawsRequests[user]` — including the haircutted E1 receipt — at par, spending funds that were never deposited into the strategy.

### Finding Description
The analog to delimiter-injection is epoch-index injection: the epoch number is the delimiter that decides whether a receipt was haircut at funding time, and a later attacker request injects a new epoch delimiter that makes the haircutted receipt indistinguishable from a fully funded one.

- `collectWithdrawFunds(_amount)` at `IdleCreditVault.sol:411-430`: when funded `_amount < pendingBasis`, it stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and sets `pendingWithdraws = 0`. The strategy therefore holds only `_amount` underlying for receipts whose aggregate claim basis is `pendingBasis`.
- `requestWithdraw` at `IdleCreditVault.sol:282-293` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` for every new request.
- `_claimLossAdjustedWithdrawRequest` at `IdleCreditVault.sol:789-801` reads `lossEpoch = lastWithdrawRequest[_user]` and returns 0 if `lossRecoveryPriceByEpoch[lossEpoch] == 0`.
- `_claimFundedWithdrawRequest` at `IdleCreditVault.sol:319-350` then pays `withdrawsRequests[_user]` (the aggregate across all epochs) at par once `epochNumber > lastWithdrawRequest[_user]`, burning all receipt tokens.

Attack trace (unprivileged tranche holder, normal fixed-APR mode):
1. Buffer of epoch E1: user calls `IdleCDOEpochVariant.requestWithdraw`, minted a strategy-token receipt of `R1`; `lastWithdrawRequest[user] = E1`, `withdrawsRequests[user] = R1`, `withdrawsRequestsByEpoch[user][E1] = R1`.
2. Manager calls `stopEpochWithDuration` with a partial loss; `collectWithdrawFunds` funds only `p * R_total` with `lossRecoveryPriceByEpoch[E1] = p < RECOVERY_FULL`. Legitimate payout for the user is `R1 * p`.
3. Buffer of epoch E2: user calls `requestWithdraw` again (any dust amount). `lastWithdrawRequest[user] = E2`; `withdrawsRequests[user] = R1 + R2`.
4. After `stopEpoch` ends E2 (`epochNumber > E2`), user calls `claimWithdrawRequest`. `lossRecoveryPriceByEpoch[E2] == 0` → loss-adjusted path skipped; funded path pays `R1 + R2` at par from `underlyingToken.balanceOf(strategy)`.

Existing guards do not stop it: `_transferFundedClaim` only protects `defaultRecoveryReserve`, not other users' funded claims; the per-epoch bookkeeping `withdrawsRequestsByEpoch` exists but is never consulted on the funded path; `lastWithdrawRequest` being a single-slot "latest epoch" marker is exactly the delimiter being overwritten.

### Impact Explanation
Direct theft / insolvency of funded withdrawal receipts. The user receives `R1` instead of `R1 * p` — extracting `(1 - p) * R1` underlying that the borrower never repaid. Since the strategy only holds `p * Σreceipts` for epoch E1 plus E2-era funding, the overpayment drains underlying belonging to other pending claimants; the last claimants of epoch E1 revert on insufficient balance (permanent freezing of their remaining claims). Loss scales linearly with the attacker's haircutted receipt size and `1 - p`; with a 50% recovery price, the attacker roughly doubles their withdrawal.

### Likelihood Explanation
Requires: an epoch stopped via `stopEpochWithDuration` with a partial loss (a real borrower shortfall, not a full default — `defaulted` stays false so requests remain enabled), and the attacker holding a receipt in that epoch plus being able to place any later request. Both are unprivileged, non-defaulted-pool flows; `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are re-enabled after each `startEpoch`, and the second request can be dust-sized. No privileged cooperation needed beyond the honest manager stopping an epoch with a loss, which is a designed code path.

### Recommendation
Do not key the loss-adjusted lookup on the mutable `lastWithdrawRequest`. Iterate/record all request epochs per user, or store per-epoch haircut flags and clear `withdrawsRequestsByEpoch[user][e]` for every `e` with `lossRecoveryPriceByEpoch[e] != 0` before paying the funded remainder. At minimum, in `_claimFundedWithdrawRequest` subtract `withdrawsRequestsByEpoch[user][e]` amounts for any epoch carrying a `lossRecoveryPriceByEpoch` and pay them through the haircut path, and prevent `requestWithdraw`/`_settleApr0` from collapsing multi-epoch history into `lastWithdrawRequest` when earlier receipts are still outstanding.

### Proof of Concept
Foundry fork sketch (pattern follows `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testLossHaircutBypassViaSecondRequest() external {
    // Setup: fixed-APR mode, non-programmable borrower, isAYSActive == false.
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");

    // Buffer of epoch 0: attacker and victim deposit and request withdraws.
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    _depositWithUser(victim,   10_000 * ONE_SCALE, true);
    vm.prank(attacker);
    uint256 r1 = cdoEpoch.requestWithdraw(0, address(AAtranche)); // receipt R1
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);

    // stopEpochWithDuration with a 50% loss on pending receipts.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = strategy.pendingWithdraws();
    uint256 funded  = pending / 2; // borrower repays only half
    deal(defaultUnderlying, borrower, funded + cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, /* lossAmount so that pendingToFund == funded */ 0);
    // (use cdoEpoch.stopEpochWithDuration(duration, lossAmount) overload that
    //  leaves lossRecoveryPriceByEpoch[0] == 0.5e18)
    assertEq(strategy.lossRecoveryPriceByEpoch(0), 5e17);

    // Epoch 1 buffer: attacker injects a second (dust) request, overwriting
    // lastWithdrawRequest[attacker] = 1.
    _startEpochAndCheckPrices(1);
    uint256 dust = 1; // 1 wei of tranche token
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(dust, address(AAtranche));
    assertEq(strategy.lastWithdrawRequest(attacker), 1);

    // Epoch 1 ends normally.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Attacker claims: lossRecoveryPriceByEpoch[1] == 0 so the E1 haircut is
    // skipped; _claimFundedWithdrawRequest pays R1 + dust-request at par.
    uint256 balBefore = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balBefore;

    assertGt(got, r1 * strategy.lossRecoveryPriceByEpoch(0) / 1e18,
        "attacker paid above haircut price");
    assertGe(got, r1, "attacker paid haircutted receipt at par");

    // Victim's claim now fails / is short: strategy holds only 0.5 * pending.
    vm.prank(victim);
    vm.expectRevert(); // underflow / insufficient underlying
    cdoEpoch.claimWithdrawRequest();
}
```

Caveat I could not fully verify within the available context: whether `requestWithdraw` is reachable for a user holding only an unsettled earlier receipt depends on `allowAAWithdrawRequest`/`isWalletAllowed` state after a loss-adjusted stop, and on whether `stopEpochWithDuration` leaves `defaulted == false` (the full-default path routes through `defaultRecoveryPrice`/`defaultRecoveryEpoch` instead, which uses per-epoch keys and is not affected). If `requestWithdraw` is gated off in that state, the same overwrite can be achieved with a normal request placed in epoch E2 before the loss is realized, provided `lastWithdrawRequest` still lands on an epoch without a `lossRecoveryPriceByEpoch` entry.
