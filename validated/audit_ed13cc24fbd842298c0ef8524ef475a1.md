### Title
Parsed SPL Token instruction JSON can misrepresent transfer topology when duplicate account indexes are used - ([File: transaction-status/src/parse_token.rs])

### Summary
`parse_token` only validates that `instruction.accounts.len()` meets a minimum via `check_num_token_accounts`, but never checks that the referenced account indexes resolve to distinct `Pubkey`s. An attacker can submit a `Transfer`/`Approve`/etc. instruction where `source`, `destination` (and/or `mint`, `owner`) indexes all point at the same key in `account_keys`, and the parser will silently emit a normal-looking three-role JSON structure via `getTransaction`.

### Finding Description
In `parse_token`, after the bounds check on `instruction.accounts.iter().max()` [1](#0-0) , each `TokenInstruction` variant calls `check_num_token_accounts(&instruction.accounts, N)` and then directly indexes `account_keys[instruction.accounts[i] as usize]` to build `source`, `destination`, `mint`, `owner`, etc. fields, e.g. for `Transfer`: [2](#0-1) . Neither `check_num_token_accounts` nor the surrounding code cross-checks that the indexes resolve to distinct `Pubkey` values — it only enforces a minimum count. Because `CompiledInstruction.accounts` is attacker-controlled (it is part of an on-chain transaction the attacker submits), an attacker can construct a transaction whose `Transfer` instruction has `accounts = [k, k, k]` (or similar) where `k` is the same index/Pubkey for source, destination, and authority. When this transaction is later fetched via `getTransaction`, the transaction-status parsing path produces JSON with `"source"`, `"destination"` fields both equal to the same address, with nothing indicating this is a degenerate/self-referential instruction rather than a genuine three-party transfer.

### Impact Explanation
This is a decoder misreporting issue (JSON-RPC `getTransaction` response), not a crash or consensus issue. Downstream consumers (explorers, indexers, analytics tooling) that rely on the parsed `source`/`destination`/`mint` fields to reconstruct transfer topology can be misled into believing a normal transfer occurred between three distinct parties when in fact all roles collapse to a single account — enabling a "wash-transfer" or topology-obfuscation pattern to appear more legitimate in tooling built on top of the RPC output.

### Likelihood Explanation
Fully attacker-reachable with a single, unprivileged action: build and submit a transaction where a token instruction's account list contains duplicate indexes referencing the same key, and observe the result of a single `getTransaction` call. No special permissions, validator control, or elevated call rate are required — the SPL Token program itself does not reject `source == destination` transfers in most implementations, and even if the runtime rejected certain nonsensical combinations, `parse_token` performs no on-chain verification and would still parse an instruction from a submitted transaction as long as `TokenInstruction::unpack` succeeds and `check_num_token_accounts` passes.

### Recommendation
Extend `check_num_token_accounts` (or add an additional check within `parse_token`) to detect when indexes required to be logically distinct roles (e.g., source/destination, or source/destination/mint depending on instruction) resolve to the same `Pubkey`, and either include an explicit flag (e.g., `"selfTransfer": true`) or leave the raw parsing intact but document/mark that role distinctness is not guaranteed, since the parser's job is descriptive rather than semantic validation. At minimum, since this only affects presentation/analytics rather than consensus, downstream consumers should be documented as needing to independently verify address uniqueness rather than assuming the parser enforces it.

### Proof of Concept
```rust
// transaction-status/src/parse_token.rs (new test)
#[test]
fn test_parse_transfer_with_duplicate_accounts() {
    use solana_message::{AccountKeys, compiled_instruction::CompiledInstruction};
    use spl_token_2022_interface::instruction::TokenInstruction;

    let key = Pubkey::new_unique();
    let account_keys = AccountKeys::new(&[key], None); // single distinct key used 3x
    let data = TokenInstruction::Transfer { amount: 42 }.pack();
    let instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![0, 0, 0], // source == destination == authority, all index 0
        data,
    };

    let parsed = parse_token(&instruction, &account_keys).unwrap();
    let info = parsed.info;

    // Current (vulnerable) behavior: source == destination silently, no flag
    assert_eq!(info["source"], info["destination"]);
    // Expected fix: parser should surface this ambiguity, e.g.
    // assert_eq!(info["selfTransfer"], true);
}
```
Running this test against the current implementation shows `source` and `destination` (and `authority`) collapse to the same address with no indication in the emitted JSON, confirming the misreporting behavior.
