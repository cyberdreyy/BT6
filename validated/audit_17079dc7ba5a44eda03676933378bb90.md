### Title
Transient BB deposits manipulate AYS to fix an inflated withdrawal yield - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
A whitelisted attacker can deposit a dominant amount into the junior `BB` tranche during the buffer phase, immediately call `requestWithdraw`, and lock a withdrawal receipt whose projected epoch interest was calculated using the temporarily manipulated `trancheAPRSplitRatio`. `_withdrawOps` then removes the deposit from live NAV and recomputes a normal split, but the attacker’s fixed payout remains inflated. The exploit applies to credit vaults with BB deposits and AYS enabled.

### Finding Description
`IdleCDOCreditVault._deposit` mints tranche shares and immediately recalculates `trancheAPRSplitRatio` from the post-deposit AA TVL ratio. [1](#0-0)  The AYS formula uses the current AA ratio and gives the BB tranche `FULL_ALLOC - trancheAPRSplitRatio` of subsequent gains. [2](#0-1) 

`requestWithdraw` first accrues accounting, computes the withdrawal’s projected tranche interest with the current split, and creates a fixed claim in `IdleCreditVault`. [3](#0-2)  Only after that does `_withdrawOps` burn the tranche tokens, remove the principal from NAV, and recompute the split. [4](#0-3) 

The projected interest is explicitly derived from `trancheAPRSplitRatio` through `_calcInterestWithdrawRequest` and `_calcTrancheInterestShare`. [5](#0-4)  There is no same-transaction or minimum-holding-period guard between depositing and requesting withdrawal.

For example, with 100 units of honest AA NAV, an attacker deposits 9,900 units of BB. The AA ratio becomes approximately 1%, the lower AYS bound is applied, and `trancheAPRSplitRatio` becomes approximately 0.5%. The attacker immediately requests withdrawal of all BB. The receipt receives approximately 99.5% of the next epoch’s vault interest even though `_withdrawOps` removes the attacker’s principal from live NAV and restores the AA split afterward. `interestForOverUnderPerformance` records the delta but does not reduce the already-created fixed receipt. [6](#0-5) 

### Impact Explanation
Honest AA depositors lose part of the next epoch’s yield because the attacker’s queued claim receives the BB-biased share that was calculated while the attacker artificially dominated BB NAV. The attacker’s capital remains supplied for the epoch, but after `requestWithdraw` it is represented by a fixed claim rather than a junior-risk tranche position.

With 10% epoch APR and the example TVL above, roughly 99.5% of the approximately 1,000-unit epoch yield is allocated to the attacker’s receipt rather than the share that would result after the withdrawal. The stolen amount is approximately the overperformance recorded by `_diff`, scaling with total NAV, epoch APR, and the attacker’s temporary BB dominance.

### Likelihood Explanation
The attack requires an AYS-enabled epoch vault with BB deposits enabled and a whitelisted attacker. Those conditions are ordinary supported configurations rather than privileged behavior. The attacker needs enough capital to dominate AA TVL, but no owner, manager, borrower, or other privileged cooperation is required. The deposit and withdrawal request can be made in one transaction during the buffer phase.

### Recommendation
Calculate withdrawal interest using the post-withdrawal tranche composition, or snapshot the epoch’s APR split before allowing withdrawal requests to affect NAV. At minimum, prevent a deposit and withdrawal request from being evaluated under a transient split in the same transaction, and delay AYS changes caused by deposits until the next epoch boundary. Add regression coverage showing that a large BB deposit followed by `requestWithdraw` cannot retain the pre-withdrawal inflated BB share.

### Proof of Concept
Add this regression test to the existing `IdleCreditVault` Foundry suite. It uses the suite’s existing whitelisting/deposit helper and honest manager-controlled epoch lifecycle:

```solidity
// test/foundry/IdleCreditVault.t.sol
function testAysSplitManipulatedBeforeWithdrawRequest() external {
  _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());

  vm.prank(owner);
  cdoEpoch.setBBDepositEnabled(true);

  uint256 aaAmount = 100_000 * ONE_SCALE;
  uint256 bbAmount = 9_900_000 * ONE_SCALE;

  // Honest senior liquidity.
  idleCDO.depositAA(aaAmount);

  // Whitelisted attacker temporarily dominates BB NAV.
  address attacker = makeAddr("ays-attacker");
  _depositWithUser(attacker, bbAmount, false); // false selects BB in this suite

  uint256 manipulatedSplit = cdoEpoch.trancheAPRSplitRatio();
  assertLt(manipulatedSplit, 1_000); // near the 0.5% lower-bound result

  uint256 attackerTrancheBalance =
    IERC20Detailed(address(BBtranche)).balanceOf(attacker);

  vm.prank(attacker);
  uint256 receipt = cdoEpoch.requestWithdraw(
    attackerTrancheBalance,
    address(BBtranche)
  );

  // The transient deposit is gone from live NAV and AYS is restored,
  // while `receipt` was already fixed using `manipulatedSplit`.
  uint256 restoredSplit = cdoEpoch.trancheAPRSplitRatio();
  assertGt(restoredSplit, 90_000);
  assertGt(receipt, bbAmount);

  // Honest manager runs the epoch; the fixed receipt can then be claimed.
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(
    0,
    initialProvidedApr,
    _expectedFundsEndEpoch()
  );

  uint256 balanceBefore =
    IERC20Detailed(defaultUnderlying).balanceOf(attacker);

  vm.prank(attacker);
  cdoEpoch.claimWithdrawRequest();

  assertEq(
    IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balanceBefore,
    receipt
  );
}
```

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }
