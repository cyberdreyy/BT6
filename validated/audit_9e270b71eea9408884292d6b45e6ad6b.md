### Title
Claimed instant-withdraw receipts are never cleared from per-epoch accounting, inflating the default-recovery reserve and making later recovery claims unpayable - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch counters `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. Like the upstream bug (a node reference acquired but never released), a claimed receipt keeps a stale per-epoch reference. At `finalizeDefaultRecovery`, that stale entry is counted a second time via `_defaultPrefundedInstantReserve`, so `defaultRecoveryReserve` is credited with underlyings that were already paid out. Later recovery claimants then find the reserve promised more than the contract holds: their `_transferDefaultRecovery` either drains funds owed to others or reverts once the balance is exhausted.

### Finding Description
- `requestInstantWithdraw` increments three counters: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]` (lines 366-372).
- `claimInstantWithdrawRequest` only zeroes `instantWithdrawsRequests[_user]` and burns the receipt (lines 387-392). The two per-epoch counters are only cleared inside `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which runs only when `defaultInstantWithdrawsFinalized` is true — i.e. never for a normally-claimed receipt.
- `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` as the CDO funds claims (lines 398-403), but `instantWithdrawClaimsByEpoch` is left untouched.
- At finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` when `pendingInstantWithdraws != 0` (lines 644-649), and `_defaultPrefundedInstantReserve` returns `instantBasis - pendingInstant` (lines 716-723). Both include already-claimed-and-paid receipts.
- `finalizeDefaultRecovery` then sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` (line 686) — a reserve larger than the real balance by exactly the already-claimed amount.

The attacker needs no privilege: any KYC-allowed tranche holder can call `requestInstantWithdraw`, let the CDO fund it, claim it, and then have a partially-unfunded co-requester trigger the inflation when the borrower defaults in the same epoch.

### Impact Explanation
Insolvency of the recovery reserve, quantified by the claimed amount `A`:

- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is inflated because both `totalBasis` (via `defaultPendingClaimBasis`) and `reserveAmount` (via `prefundedReserve`) contain `A`. The reserve over-promises because `A` underlyings already left the contract.
- Every `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest`/`_claimPostDefaultWithdrawRequest` pays out of `defaultRecoveryReserve` with no balance check (lines 912-917). Claimants are paid `claimBasis * price` until the real balance is exhausted; the final claimants' `safeTransfer` reverts — permanent freezing of unclaimed recovery, with early claimants extracting more than their fair share. Net effect equals theft/redistribution of `A` from the last claimants.

Broken invariant: one receipt, one payout — a paid receipt is counted a second time as prefunded reserve.

### Likelihood Explanation
Requires a specific but ordinary sequence: two instant-withdraw requests in the same epoch, partial funding (common, since instant requests draw on available CDO liquidity), one claim, then a borrower default finalized in that epoch. No attacker control over privileged roles is needed; the bug triggers whenever default finalization runs while a stale `instantWithdrawClaimsByEpoch` entry coexists with nonzero `pendingInstantWithdraws`. The `reserve` guard in `_transferFundedClaim` (lines 899-905) does not help because the inflated reserve itself authorizes the overspend.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch entries when consuming a funded receipt: locate the user's receipt epochs and zero `instantWithdrawsRequestsByEpoch[_user][e]` and decrement `instantWithdrawClaimsByEpoch[e]` and `pendingInstantWithdraws` accounting consistently with `collectInstantWithdrawFunds`. Alternatively, have `collectInstantWithdrawFunds`/claim paths reconcile `instantWithdrawClaimsByEpoch` so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only see receipts that are still unpaid.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleInstantReceiptInflatesRecovery() public {
    // buffer phase: users deposit AA so vault has liquidity
    idleCDO.depositAA(100 * ONE_SCALE);           // this contract = userA
    // userB deposits similarly

    // both request instant withdraw in the same epoch N
    cdoEpoch.requestInstantWithdraw(10 * ONE_SCALE, address(AAtranche)); // userA
    // userB requestInstantWithdraw(B) similarly

    // CDO funds only userA's claim (partial funding leaves pendingInstantWithdraws = B)
    vm.prank(manager);
    cdoEpoch.collectInstantWithdrawFunds(10 * ONE_SCALE); // pulls A into strategy
    cdoEpoch.claimInstantWithdrawRequest();               // userA paid; per-epoch counters stale

    // borrower defaults in epoch N; finalizeDefaultRecovery with recovered amount R
    _defaultAndFinalize(R);

    // reserve was credited (instantBasis - pendingInstant) including A's already-paid 10
    assertGt(creditVault.defaultRecoveryReserve(), realBalanceAvailable);

    // userB's defaulted claim pays, but the LAST defaulted claimant's
    // _transferDefaultRecovery reverts on insufficient underlying balance.
    vm.expectRevert(); // or measure shortfall == 10 * ONE_SCALE
    cdoEpoch.claimWithdrawRequest(); // last claimant
}
```

Key assertion: after `claimInstantWithdrawRequest`, `instantWithdrawsRequestsByEpoch[userA][epoch] != 0` and `instantWithdrawClaimsByEpoch[epoch]` still includes the paid amount, which `finalizeDefaultRecovery` then double-counts into `defaultRecoveryReserve`.
