### Title
Builder withdrawal amount committed to `payload_expected_withdrawals` is not capped to `builder.balance`, allowing Gwei to be created on the execution layer while only a smaller amount is deducted from CL state - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals()` copies the full requested `withdrawal.amount` from `state.builder_pending_withdrawals` into the `Withdrawal` object that is committed via `state.payload_expected_withdrawals` (and must equal `block.body.execution_payload.withdrawals`), without capping it to the builder's actual balance. `apply_withdrawals()` then only deducts `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance`. If a builder's balance is smaller than the requested amount, the CL commits to (and the EL will credit) the full requested amount to `fee_recipient`, but only the smaller `builder_balance` is subtracted from CL-tracked total balance — creating Gwei with no corresponding balance decrease anywhere in the system, exactly analogous to the M-30 pattern of marking an operation "processed" without confirming the full amount was actually moved.

### Finding Description
`get_builder_withdrawals` (used by `get_expected_withdrawals`) builds the withdrawal list: [1](#0-0) 

Note `amount=withdrawal.amount` is the raw requested amount from `BuilderPendingWithdrawal`, with no `min()` against `state.builders[builder_index].balance`.

This list becomes `state.payload_expected_withdrawals`, which the block’s `execution_payload.withdrawals` must exactly match: [2](#0-1) 

`apply_withdrawals` then only decreases the builder's CL-tracked balance by the capped amount: [3](#0-2) 

The entry is unconditionally removed from the queue regardless of whether the full amount was honored: [4](#0-3) 

The repo's own generated report documents this asymmetry explicitly as intended-looking behavior ("Actual = `min(amount, builder.balance)`" vs. the committed/output amount being the full requested amount), and the test suite confirms the exact scenario: [5](#0-4) 

In `test_builder_withdrawal_insufficient_balance`, the builder has only 1 ETH but the pending withdrawal requests 5 ETH. The test asserts `withdrawal_amounts_builders={builder_index: withdrawal_amount}` (5 ETH, the requested/committed amount appearing in `payload_expected_withdrawals`), while `builder_balances={builder_index: 0}` (only 1 ETH actually deducted). The 4 ETH difference is committed to the execution payload's withdrawal to `fee_recipient` (an EL credit of ETH) with no matching CL balance decrease anywhere in the system — the beacon chain simply trusts that the payload will honor exactly the list it output, and the EL mechanically credits accounts for whatever amount appears in the withdrawals list, regardless of whether the CL "backed" that amount with a real balance reduction.

Equality broken: total Gwei conserved across CL beacon-state minus EL credits must be zero-sum for withdrawals (every Gwei credited to an execution address must be matched by an equal Gwei debit from `state.balances`/`state.builders[*].balance`). Here, `min(withdrawal.amount, builder_balance) < withdrawal.amount` breaks that equality — Gwei is created out of thin air and paid to an address chosen by the builder (`fee_recipient` in `BuilderPendingWithdrawal`), a non-owner relative to the missing amount.

### Impact Explanation
This is Critical: it is a direct Gwei-creation bug. Whenever a builder is withdrawn down to (or below) an amount less than a queued pending withdrawal request(s) — e.g. via a sequence of `settle_builder_payment` withdrawals, exits, or slashing-equivalent mechanisms reducing `builder.balance` below the sum of queued `builder_pending_withdrawals` amounts — the execution layer will mint/credit more ETH than the beacon chain actually removes from any account. This directly increases total ETH supply beyond what consensus rules should allow, which is one of the explicitly listed Critical impacts ("Gwei created, destroyed, or paid to a non-owner").

### Likelihood Explanation
The scenario requires a builder's balance to fall below the sum of its outstanding `builder_pending_withdrawals` entries before those entries are processed. This is plausible under normal operation: a builder can have multiple payments/withdrawals queued (from `settle_builder_payment`, exits, etc.) and there is no invariant enforced elsewhere in the spec preventing `builder.balance` from dropping below `get_pending_balance_to_withdraw_for_builder(state, builder_index)` in all code paths that decrease builder balance (e.g., via slashing-like penalties or concurrent withdrawal ordering within the same block, since multiple withdrawals for the same builder can be queued and only capped independently per withdrawal against the balance at the time each is applied). The repository's own test suite (`test_builder_withdrawal_insufficient_balance`, `test_builder_withdrawal_insufficient_balance_realistic_bounds`) demonstrates and normalizes exactly this insufficient-balance condition as expected/tested behavior, indicating the condition is reachable and already anticipated by spec authors — but the fix (capping the *committed* withdrawal amount, not just the balance decrement) has not been applied.

### Recommendation
In `get_builder_withdrawals`, cap the committed `Withdrawal.amount` to the builder's balance at withdrawal-construction time (accounting for prior withdrawals against the same builder within the same block, similar to `get_balance_after_withdrawals` used for validators), i.e. `amount=min(withdrawal.amount, balance_after_prior_withdrawals_for_this_builder)`, so that the amount placed into `payload_expected_withdrawals` (and thus the EL credit) never exceeds what `apply_withdrawals` actually deducts from `state.builders[builder_index].balance`. This restores the invariant that every Gwei credited on the EL side has an equal, already-applied debit on the CL side.

### Proof of Concept
Using the existing test harness pattern from `test_builder_withdrawal_insufficient_balance`: [6](#0-5) 

1. Set `state.builders[0].balance = 1 ETH`.
2. Queue `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5 ETH, fee_recipient=X)]`.
3. Call `process_withdrawals(state)` (with parent block full so the sweep executes).
4. Observe: `state.payload_expected_withdrawals[0].amount == 5 ETH` (committed to EL, execution payload must include a 5 ETH withdrawal to `X`), while `state.builders[0].balance` decreases only from 1 ETH to 0.
5. Net effect: the execution layer credits `X` with 5 ETH while the consensus layer only removed 1 ETH from any account — 4 ETH of unbacked Gwei is created and paid to `X`, and `builder_pending_withdrawals` is popped as if fully "processed" (mirroring the M-30 pattern of marking work done without validating the full amount was withdrawn).
