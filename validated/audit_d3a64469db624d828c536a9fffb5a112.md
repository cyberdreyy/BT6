### Title
`stopEpoch()` liveness DoS via external ERC4626 liquidity drain: any vault borrower can permanently block epoch settlement, withdrawal fulfillment and pool closure - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch()` is a mandatory hook inside `IdleCDOEpochVariant._stopEpoch()` — the shared entrypoint for epoch settlement, pending-withdrawal funding, interest distribution and pool closure. When `IdleCDO` needs to pull cash (`_amountToPullFromBorrower + _pendingWithdraws`) that exceeds the borrower's on-hand balance, the hook calls `vault.withdraw(shortfall, ...)` on the external ERC4626 vault and **reverts with `StopEpochVaultLiquidityUnavailable()` if that withdrawal fails**, even though the borrower's vault shares fully cover the shortfall. Because the revert propagates out of `_stopEpoch()` before any default handling runs, an unprivileged user of the configured ERC4626 vault (e.g. a borrower on the underlying Morpho/Gauntlet market) can keep the vault's liquid assets fully borrowed and make every `stopEpoch` / `stopEpochWithDuration` call revert indefinitely.

### Finding Description
In `ProgrammableBorrower.sol` `onStopEpoch` (lines 231-268):

```solidity
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true; // covered-by-shares check
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The intent (comment lines 242-245) is that only a *transient* withdrawal failure should be retryable while genuine under-collateralization falls through to the `transferFrom`-failure default path. But a `vault.withdraw` revert caused purely by **insufficient idle liquidity inside the ERC4626 vault** — while `convertToAssets(shares) >= shortfall` — hits the `catch` and reverts, bubbling up through `IdleCDOEpochVariant.sol` line 398:

```solidity
if (!IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)) {
  _handleBorrowerDefault(...);
  return;
}
```

The revert preempts both the `return false → _handleBorrowerDefault` path and the subsequent `getFundsFromBorrower` try/catch (line 408), so the transaction reverts atomically: `isEpochRunning` stays `true`, `epochEndDate` stays set, `pendingWithdraws` stay unfunded, and tranche holders cannot claim. This is confirmed by `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable` (`test/foundry/ProgrammableBorrowerCreditVault.t.sol` L372-399), which shows the epoch remaining running with withdraw requests stuck.

Unlike the Panoptic `StaleOracle` gate, the manipulated quantity here is not a price but **vault redeemable liquidity**: for vaults like MetaMorpho, any unprivileged market participant can borrow the underlying liquidity (or the vault can be naturally fully utilized), causing `withdraw`/`redeem` to revert for everyone holding shares, including `ProgrammableBorrower`.

### Impact Explanation
- **Frozen epoch settlement**: `stopEpoch`/`stopEpochWithDuration` revert 100% of the time while vault liquidity < `shortfall`, so interest is never distributed and the epoch never closes.
- **Frozen lender funds**: all pending `requestWithdraw` receipts (`pendingWithdraws`) can never be funded via `collectWithdrawFunds` (line 410); claimants' funds are stuck for the duration of the manipulation. Tranche holders' capital remains locked in the still-running epoch.
- **Blocked close-pool / default escape**: `stopEpoch(0, 1)` (request-all-funds close) hits the same revert before `_handleBorrowerDefault` can mark the facility defaulted, so even the emergency unwind path is blocked. `emergencyExitVault` uses `vault.redeem`, which requires the same underlying liquidity and fails identically; `setVault` is barred because `vault.balanceOf(address(this)) != 0` (line 165). The only recovery is waiting for third-party liquidity to return — which the attacker can perpetually re-drain.
- **Quantified impact**: for the duration of the freeze, the entire pool NAV (test scale: 10,000 USDC + accrued interest + pending withdraws) is illiquid; the attacker bears only borrow-interest cost on the Morpho market, analogous to the swap cost in the original report.

### Likelihood Explanation
- The attacker set explicitly includes "a user of the programmable borrower's ERC4626 vault" — exactly the capability needed. Borrowing ~all available liquidity on a Morpho market is a routine, capital-efficient action (cost = borrow APR on the borrowed amount, optionally for one block per grief, repeatable).
- No privileged action is required; manager/owner calls `stopEpoch` honestly and it reverts.
- The guard that *should* catch this — `shortfall > _currentVaultAssets() → return true` — only detects share-value insufficiency, not liquidity insufficiency, and `emergencyExitVault`/`setVault`/`onDefault` all either need the same vault liquidity or are unreachable while the hook reverts.
- Natural (non-adversarial) full utilization of the vault produces the same freeze during stress periods — the same "liveness failure exactly when settlement is most needed" pattern as the original `StaleOracle` finding.

### Recommendation
Mirror the report's "degraded mode / two-step" mitigations:
1. On `vault.withdraw` failure, fall back to `vault.redeem(maxShares)` or partial `withdraw(vault.maxWithdraw(...))` rather than reverting, and let the subsequent `transferFrom` shortfall trigger the existing default path if cash is genuinely unavailable.
2. Alternatively return `false` (or a dedicated status) on covered-but-illiquid failures so `IdleCDO` can mark a default, letting `onDefault()` (lines 289-301, which deliberately avoids `convertToAssets`) cleanly stop accounting instead of leaving `epochAccountingActive == true` forever.
3. Provide a guardian/manager bypass that settles the epoch using only on-hand assets and vault-share valuation, treating the un-withdrawable sleeve as a recorded vault loss rather than a hard revert.

### Proof of Concept
Reproducible Foundry fork PoC (mainnet fork at a Gauntlet/MetaMorpho USDC vault block, as used by `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function test_PoC_StopEpochDoS_VaultLiquidityDrain() external {
    _setUpProgrammableBorrowerCreditVault(GAUNTLET_FORK_BLOCK, GAUNTLET_USDC_PRIME);
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    // lender creates a pending withdraw that must be funded at stopEpoch
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
    _startEpochAndCheckPrices(0); // ProgrammableBorrower deposits idle cash into the Morpho vault

    // --- attack: unprivileged vault user borrows (almost) all vault liquidity ---
    // On the underlying Morpho market, attacker supplies collateral and borrows
    // USDC so that gauntletVault.maxWithdraw(programmableBorrower) < pendingWithdraws.
    _drainMorphoVaultLiquidity(GAUNTLET_USDC_PRIME); // any EOA, see market.borrow(...)

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // shares still cover the shortfall -> early-return path NOT taken
    uint256 pending = strategy.pendingWithdraws();
    assertLe(pending, programmableBorrower.totalUnderlying());

    // every settlement attempt reverts atomically
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(StopEpochVaultLiquidityUnavailable.selector));
    cdoEpoch.stopEpoch(0, 0);

    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(StopEpochVaultLiquidityUnavailable.selector));
    cdoEpoch.stopEpoch(0, 1); // close-pool also blocked; default path unreachable

    // fund impact: epoch stays running, withdraw receipts unfunded, lender NAV frozen
    assertTrue(cdoEpoch.isEpochRunning());
    assertEq(strategy.pendingWithdraws(), pending);
    // attacker can re-borrow any repaid liquidity to extend the freeze indefinitely
}
```

State to assert per the original report's table: (a) `stopEpoch` succeeds pre-drain, (b) identical call reverts with `StopEpochVaultLiquidityUnavailable` post-drain, (c) `stopEpoch(0,1)` close-pool reverts the same way, (d) `pendingWithdraws` and tranche balances unchanged across the reverted calls.
