Investigation confirms this is a real, exploitable griefing/theft vector rooted in a missing length validation.

## Finding

**`createDstEscrow` accepts an arbitrary-length `parameters` blob with no validation**, and `EscrowDst.withdraw()`/`publicWithdraw()` unconditionally decode fee fields out of it via `ImmutablesLib`, which reverts if the blob is even one byte short of the expected 128 bytes.

`BaseEscrowFactory.createDstEscrow` takes `dstImmutables` entirely from the caller (an unprivileged taker/resolver) and performs no check on `dstImmutables.parameters` length or content before hashing it into the CREATE2 salt and deploying/funding the clone: [1](#0-0) 

The canonical encoding used elsewhere is `abi.encode(protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)` — 4 words, i.e. 128 (`0x80`) bytes: [2](#0-1) 

`ImmutablesLib` only enforces *minimum* lengths per field, not the full expected size: [3](#0-2) 

`EscrowDst._withdraw` calls `integratorFeeAmountCd()` (needs ≥ `0x40`/64 bytes) before `protocolFeeAmountCd()` (needs ≥ `0x20`/32 bytes): [4](#0-3) 

So a `parameters` blob of exactly 63 bytes passes the `protocolFeeAmountCd` check (≥32) but fails `integratorFeeAmountCd` (needs ≥64) with `IndexOutOfRange()`, regardless of what the encoded fee values are — including the "both fees zero" case described in the question. Since `onlyValidImmutables` (via `_validateImmutables`/CREATE2 address recomputation) requires the exact same `parameters` bytes used at deployment to be replayed on every call, `withdraw()` and `publicWithdraw()` will **revert every single time** for this escrow — there is no way to submit different, correctly-sized parameters later because that would produce a different immutables hash / wrong escrow address.

Critically, `cancel()` does **not** touch `ImmutablesLib` fee getters and pays the taker directly with `immutables.amount`: [5](#0-4) 

So after the cancellation timelock, the same taker who crafted the malformed `parameters` can call `cancel()` and reclaim the entire destination deposit back to themselves — while having already used the (now-public) secret to withdraw the maker's assets from the corresponding source escrow. This produces a scenario where the maker's source-chain funds go to the taker, and the maker is permanently unable to claim the destination-chain payout, which the taker instead reclaims via `cancel()`.

### Title
Unvalidated `parameters` length in `createDstEscrow` permanently bricks `EscrowDst.withdraw`/`publicWithdraw`, enabling taker to steal maker's counter-value funds - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
`BaseEscrowFactory.createDstEscrow` never validates the length/shape of `dstImmutables.parameters`. `ImmutablesLib`'s fee getters only check minimum-length thresholds per field, not the full 128-byte structure. A taker can deploy and fund a destination escrow with a 63-byte `parameters` blob (one byte short of the `integratorFeeAmountCd` 64-byte minimum). Because `onlyValidImmutables` requires bit-for-bit identical immutables (including `parameters`) to be replayed on every call, `withdraw()`/`publicWithdraw()` will always revert with `ImmutablesLib.IndexOutOfRange()` for that escrow, while `cancel()` (which bypasses `ImmutablesLib` fee decoding) remains callable by the taker after the cancellation timelock.

### Impact Explanation
This allows a malicious taker to fund the maker's counter-value escrow in a way that guarantees the maker can never withdraw it, then reclaim the funds via `cancel()` — after already having claimed the maker's source-chain assets using the publicly revealed secret. This is direct theft of user funds / permanent freezing of the maker's expected payout, which maps to the Critical/High tiers of the bounty (theft of funds in motion, permanent freezing of funds).

### Likelihood Explanation
No privileged role is required — any resolver/taker calling the public `createDstEscrow` entrypoint controls the full `Immutables` struct including `parameters`, and nothing in `BaseEscrowFactory` or `ImmutablesLib` prevents a truncated encoding. The condition (`parameters.length` between 32 and 63 inclusive) is trivial to construct.

### Recommendation
Enforce an exact expected length (`parameters.length == 0x80`) for destination immutables in `createDstEscrow` (or in `ImmutablesLib`/`EscrowDst`), rejecting malformed/short blobs at creation time rather than allowing them to be deployed and only failing at withdrawal time.

### Proof of Concept
1. Taker calls `createDstEscrow` with `dstImmutables.parameters` set to a hand-crafted 63-byte blob (e.g., truncated `abi.encode(0,0,protocolFeeRecipient,integratorFeeRecipient)`), funding it with the correct native/ERC20 amounts.
2. Escrow clone deploys successfully; `_deployEscrow`/`Clones.cloneDeterministic` and balance checks pass since they don't inspect `parameters` content.
3. Once the withdrawal window opens and the secret is known (e.g., because taker already withdrew from the corresponding source escrow), the maker or taker calls `EscrowDst.withdraw`/`publicWithdraw`; `_withdraw` calls `immutables.integratorFeeAmountCd()` [6](#0-5)  which reverts with `IndexOutOfRange()` because `parameters.length (63) < 0x40`.
4. This reverts on every subsequent attempt (immutables must match exactly for `onlyValidImmutables` to pass), so the maker can never withdraw.
5. After `DstCancellation` timelock, taker calls `cancel()` [5](#0-4)  and reclaims the destination funds and safety deposit for themselves.

            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);

        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();

        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
