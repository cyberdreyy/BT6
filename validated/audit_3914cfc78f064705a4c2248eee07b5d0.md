### Title
Bridge outgoing token (secret) disclosed to any view-role user via GET /v2/bridge_types - ([File: core/web/presenters/bridges.go])

### Summary
`BridgeTypesController.Index` (core/web/bridge_types_controller.go) serializes every configured bridge via `presenters.NewBridgeResource`, which always includes the `OutgoingToken` field with no `omitempty` and no redaction. Any caller authorized to hit `GET /v2/bridge_types` (minimum view-role session) receives every bridge's name, URL, and outgoing token in plaintext.

### Finding Description
`Index` fetches all bridges from `btc.App.BridgeORM().BridgeTypes(ctx, offset, size)` and maps each to a `presenters.BridgeResource` [1](#0-0) . `NewBridgeResource` copies `b.OutgoingToken` into the response struct unconditionally [2](#0-1) . The struct definition marks only `IncomingToken` as `omitempty` ("only provided when creating a Bridge"), while `OutgoingToken` is a plain, always-serialized JSON field [3](#0-2) .

The `OutgoingToken` is a bridge-specific secret used by the Chainlink node's HTTP client to authenticate outbound requests to the external adapter (and/or verify inbound webhook callbacks from that adapter). Unlike the claimed premise in the question ("tokens are redacted"), the code does not redact this token at all in the `Index`/`Show`/`Update`/`Destroy` responses — only the separate `IncomingToken` (issued at creation time) is treated as sensitive via `omitempty`. This means the audit's assumed mitigation does not exist for `OutgoingToken`.

Since `GET /v2/bridge_types` is reachable by any session with at least view-role privileges (the minimum authenticated role for read-only routes in this router), a low-privileged, non-admin user can list all bridges and directly harvest each bridge's `OutgoingToken` secret alongside its name/URL — not merely perform attack-surface mapping, but obtain live credentials usable against the corresponding adapter/webhook endpoints.

### Impact Explanation
This is a credential/secret disclosure vulnerability (Chainlink bounty class: sensitive data/secret exposure), not just enumeration. A view-role attacker obtains the `OutgoingToken` for every bridge configured on the node, which can be replayed against external adapters or used to forge authenticated bridge traffic, extending impact beyond simple reconnaissance into direct credential theft.

### Likelihood Explanation
Preconditions: attacker only needs a valid authenticated session with view role (the documented minimum for GET routes) — no admin/run privileges required. The request is a single unauthenticated-relative-to-role `GET /v2/bridge_types` call, trivially repeatable and requiring no special conditions, chain state, or timing.

### Recommendation
Add `json:"-"` or `omitempty` plus explicit clearing of `OutgoingToken` in `presenters.NewBridgeResource` for list/show responses (mirroring the `IncomingToken` handling), or introduce a separate redacted presenter for `Index`/`Show`/`Update`/`Destroy` that never serializes `OutgoingToken` back to API clients after creation.

### Proof of Concept
1. Go handler-level integration test (extending `core/web/bridge_types_controller_test.go`):
   - Seed a bridge via `orm.CreateBridgeType` with a known `OutgoingToken`.
   - Authenticate as a view-role session (minimum role for `GET /v2/bridge_types`).
   - Call `GET /v2/bridge_types`.
   - Assert response status 200 and that `resources[0].OutgoingToken` equals the seeded secret — this assertion currently passes, proving the leak (whereas the expected/secure behavior would have this field empty or absent).
2. Table-driven unit test on `presenters.NewBridgeResource`: construct a `bridges.BridgeType` with `OutgoingToken = "secret"`, call `NewBridgeResource`, and assert `resource.OutgoingToken == ""` — this currently fails, confirming the presenter does not redact the field.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}
