### Title
Wrapper only signals the direct child PID, never the process group, letting grandchildren outlive `terminateWrappedProcess` cleanup - (helpers/runner_wrapper/wrapper.go, helpers/runner_wrapper/commander_unix.go)

### Summary
`setProcessGroup` puts the wrapped command in its own process group via `Setpgid: true`, but `terminateWrappedProcess` / `forcefulShutdown` never actually deliver a signal to that group (e.g. via `syscall.Kill(-pid, ...)`) — they call `p.Signal(syscall.SIGTERM)` on the `os.Process` handle, which only targets the single leader PID [1](#0-0) [2](#0-1) . The process-group creation in `commander_unix.go` is therefore dead protection: it establishes a group but nothing in the shutdown path ever uses it to reach descendants [3](#0-2) .

### Finding Description
`newDefaultCommander` configures `Setpgid: true` so the spawned process becomes the leader of a new process group, and any children it forks (which inherit the pgid unless they explicitly call `setpgid`) remain members of that same group [4](#0-3) . This is the correct mechanism to later kill the whole tree with a single group-wide signal (`kill(-pgid, SIGTERM)`).

However, `Wrapper.terminateWrappedProcess` retrieves the `process` interface (backed by `*os.Process`) and calls `p.Signal(syscall.SIGTERM)` [1](#0-0) . `os.Process.Signal` on Unix issues `kill(pid, sig)` against the specific PID only — it does not target `-pid` (the group). The same pattern repeats in `forcefulShutdown` [2](#0-1) .

So the actual defect is not that children "escape" the process group during a fork/exec race — Setpgid is applied before `exec` via `SysProcAttr`, so descendants that don't explicitly call `setpgid`/`setsid` themselves stay in the group. The real bug is that the termination code never signals the group at all: if the wrapped command forks a background/detached grandchild (e.g. `sh -c 'child_writer &' ` or a script that daemonizes, closes stdio, and keeps running), that grandchild is a separate process not reaped by `cmd.Wait()` and is never sent SIGTERM. `terminateWrapper` only waits on `w.errCh` for the *direct* child's `cmd.Wait()` to return and then treats the job/process as terminated [5](#0-4) . Once the parent exits, the orphaned grandchild can continue running and writing files indefinitely, unconstrained by `terminationTimeout`.

### Impact Explanation
An unprivileged job that forks a detached child (common with `nohup`, `disown`, double-fork daemonization, or simply background job control in a shell script) can leave that process alive after the wrapper believes shutdown is complete. If the wrapped process is the job execution wrapper and the workspace/build/cache/artifact directories remain mounted and writable after cleanup begins, this leftover process can keep writing to those paths, violating the invariant that no job process may outlive cleanup.

### Likelihood Explanation
The precondition is simply that the job script backgrounds/detaches a child before or during the wrapped command's execution — a trivial and common shell idiom, requiring no exploitation of memory-safety or race conditions. It is fully attacker-controlled (the job author supplies the script executed via the commander) and 100% reproducible, since the group-kill logic simply doesn't exist in the code, rather than being racy.

### Recommendation
In `terminateWrappedProcess`/`forcefulShutdown`, signal the whole process group instead of the leader PID alone, e.g. `syscall.Kill(-pid, syscall.SIGTERM)` (falling back to per-PID signal if `getpgid` fails or PID equals PGID edge cases), and apply the same group-wide signal for the timeout-triggered forceful kill path. Ensure this is guarded for platforms where `Setpgid` isn't set (Windows uses a job object already, per `wrapper_windows.go`/`job_windows.go`).

### Proof of Concept
Go integration test outline (mirrors the suggested proof idea):
1. Build a tiny helper binary/script that on start forks a detached grandchild (e.g. `sh -c 'while true; do echo x >> tracked_file; sleep 0.1; done & disown'`) and then exits quickly itself.
2. Use `runner_wrapper.New(...)` with `commanderFactory` pointed at this script, call `Run(ctx)`, then cancel `ctx` to trigger `terminateWrapper()` -> `terminateWrappedProcess()`.
3. After `terminationTimeout` elapses, assert that `tracked_file`'s mtime/size has stopped changing (expected to fail today, since the grandchild is never signaled and keeps appending).
4. Additionally assert via `pgrep`/`/proc` that a process in the original process group is still alive after the wrapper reports the wrapped process as stopped.

```go
func (w *Wrapper) terminateWrapper() error {
	w.log.Info("Shutting down wrapper process...")

	err := w.terminateWrappedProcess()
	if err != nil {
		if errors.Is(err, api.ErrProcessNotInitialized) {
			return nil
		}
		return err
	}

	select {
	case err := <-w.errCh:
		w.log.WithError(err).Info("Wrapped application exited")

		return nil

	case <-time.After(w.terminationTimeout):
		return errProcessExitTimeout
	}
}
```

```go
func (w *Wrapper) terminateWrappedProcess() error {
	w.lock.RLock()
	p := w.process
	w.lock.RUnlock()

	if p == nil {
		w.log.Info("No process to shutdown; exiting")

		return api.ErrProcessNotInitialized
	}

	err := p.Signal(syscall.SIGTERM)
	if err != nil {
		return fmt.Errorf("%w: %w", errFailedToTerminateProcess, err)
	}

	return nil
}
```
