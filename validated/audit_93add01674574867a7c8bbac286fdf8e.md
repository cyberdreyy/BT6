### Title
Miner-inactivity timeout can be reset indefinitely by repeated conflicting proposals, wedging the signer into never falling back to a prior tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_latest_block_in_tenure` bumps a tenure's `last_activity_time` whenever *any* conflicting/non-advancing block proposal for that tenure is seen, and `SortitionState::is_timed_out` computes miner inactivity purely from the *elapsed time since the last such bump*. A one-slot miner that stalls (never proposes a valid, height-advancing block) can nonetheless keep re-submitting proposals at the same or lower `chain_length` more frequently than `block_proposal_timeout`, continuously resetting the inactivity clock. This mirrors the reported analog: just as claiming before a full `periodLength` elapses zeroes the "elapsed" quantity used for reward accrual, submitting a new (even invalid/duplicate) proposal before the timeout elapses zeroes the "elapsed" quantity used for the inactivity check, permanently deferring the fallback and wedging liveness.

### Finding Description
`SortitionState::is_timed_out` (v1: `stacks-signer/src/chainstate/v1.rs:55-94`; v2: `stacks-signer/src/chainstate/v2.rs:48-89`) measures `elapsed = now - last_activity_time` and only calls the tenure timed out if `elapsed > block_proposal_timeout`. `last_activity_time` for a consensus hash is stored in `signer_db` via `update_last_activity_time` [1](#0-0) .

That timestamp is bumped from `check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:376-448`) whenever a proposal for the tenure arrives that does **not** advance past the last known block (`chain_length <= info.block.header.chain_length`), as long as there is no fresh `signed_group` acceptance blocking it or a pre-commit is still fresh: [2](#0-1) [3](#0-2) 

This function is explicitly documented as counting *any* attempt to reorg a locally-accepted or pre-committed block "towards valid miner activity," on the theory that "the miner may just be slow." But nothing in this path requires the resubmitted proposal to be valid, unique, or to make forward progress — it only needs a `chain_length` that does not exceed what's already known, and the same tenure's `consensus_hash`. A stalled miner (or any actor that can get proposals routed through this check for the tenure) can therefore emit a stream of essentially no-op/duplicate proposals spaced less than `block_proposal_timeout` apart, and each one refreshes `last_activity_time`, so `elapsed` never crosses the threshold in `is_timed_out`.

`check_miner_inactivity` (`stacks-signer/src/v0/signer_state.rs:284-374`) is the only path that falls back to the prior tenure's miner, and it is gated entirely on `is_timed_out` returning `true`: [4](#0-3) 

If `is_timed_out` never fires because the activity timer keeps getting refreshed, the signer can never revert `state_machine.current_miner` to the prior valid tenure, and `docs/signer-flows.md` confirms that this timeout is the *only* escape hatch from a stalled current miner (a block we signed suppresses it permanently; otherwise this is the fallback path) [5](#0-4) .

This is structurally the same bug class as the external report: the reward calculation's "elapsed since last claim" is reset by any claim, even one that captures only a fraction of a period, causing the fractional progress to be lost/reset instead of accumulated; here, the "elapsed since last activity" is reset by any conflicting proposal, even one that makes no real progress, causing the inactivity duration to be lost/reset instead of accumulated toward the timeout.

### Impact Explanation
This falls under the High-impact category: "a signer wedged into never signing valid blocks... or acting on a stale reward set/threshold" — more precisely here, a signer wedged into never falling back to the correct/prior miner because the timeout guard that exists specifically to detect and recover from an inactive miner can be kept perpetually unsatisfied. If the current miner is unable or unwilling to produce a valid, height-advancing block (e.g. it is down, byzantine, or partitioned) but can still get conflicting/duplicate proposals accepted into this check, signers following this logic will never revert to the prior tenure, stalling block production for that tenure's signer cohort until some other unrelated mechanism (e.g., a new sortition) intervenes.

### Likelihood Explanation
The triggering actor is exactly the tenure's own one-slot miner (the miner who won the current sortition), which is within scope as "a one-slot miner (plus gossip)". No majority of signers or other signers' keys are needed — the miner simply needs to keep the proposal-submission cadence under `block_proposal_timeout` (default in tests: 5s, configurable) with proposals that don't advance `chain_length`. `update_last_activity_time` is invoked unconditionally on this path save for the narrow guard on `signed_group`/`reorg_attempts_activity_timeout`, so the reset is easy to trigger repeatedly.

### Recommendation
Do not treat every non-advancing/conflicting proposal as activity that resets the clock indefinitely. Consider bounding how much cumulative benefit repeated "activity" resets can grant (e.g., prorate/cap the total window rather than fully resetting `last_activity_time` on every touch), or require the "activity" to correspond to actual forward progress (e.g., a block that gets locally/globally accepted, or at minimum a proposal with a strictly higher `chain_length` than any previously seen for the tenure) before refreshing the inactivity timer. This mirrors the external fix's approach of prorating between windows instead of resetting the floor on every interaction.

### Proof of Concept
1. Signer S is following tenure T with `block_proposal_timeout = 5s`.
2. Miner M (winner of T's sortition) never produces a block advancing past chain_length N.
3. Every ~4s, M crafts and gossips a new "proposal" for tenure T with `chain_length <= N` (e.g., a duplicate/slightly-modified block at the same height).
4. Each such proposal reaches `check_latest_block_in_tenure`, satisfies `block.header.chain_length <= info.block.header.chain_length`, and (absent a fresh `signed_group` on the existing block) calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())`.
5. `SortitionState::is_timed_out` computes `elapsed = now - last_activity_time`, which never exceeds 5s, so it always returns `false`.
6. `check_miner_inactivity` therefore never triggers the fallback to the prior tenure, and the signer remains wedged waiting on M indefinitely.

    pub fn update_last_activity_time(
        &mut self,
        tenure: &ConsensusHash,
        last_activity_time: u64,
    ) -> Result<(), DBError> {
        debug!("Updating last activity for tenure"; "consensus_hash" => %tenure, "last_activity_time" => last_activity_time);
        self.db.execute("INSERT OR REPLACE INTO tenure_activity (consensus_hash, last_activity_time) VALUES (?1, ?2)", params![tenure, u64_to_sql(last_activity_time)?])?;
        Ok(())
    }
