### Title
Builder withdrawal payload amount is not capped to the builder's actual balance, allowing uncollateralized ETH to be created and paid out - (File: specs/gloas/beacon-chain.md)

### Summary
`process_withdrawals` commits to a `Withdrawal` list (`state.payload_expected_withdrawals`) that the execution layer must honor exactly. For builder-originated withdrawals, `get_builder_withdrawals` puts the *requested* `BuilderPendingWithdrawal.amount` into the committed `Withdrawal.amount` field without checking it against the builder's actual balance [1](#0-0) . The actual state deduction in `apply_withdrawals` is capped with `min(withdrawal.amount, builder_balance)` [2](#0-1) . This means the beacon state can commit the execution layer to pay out more ETH to a `fee_recipient` than was ever debited from any account in the beacon state.

### Finding Description
`BuilderPendingWithdrawal` entries are created from execution-payload-bid processing, recording a builder's committed payment amount without necessarily validating it stays valid until settlement (e.g. across missed slots/epochs, `settle_builder_payment` and `process_builder_pending_payments` move `payment.withdrawal` into `builder_pending_withdrawals` verbatim) [3](#0-2) [4](#0-3) .

When `process_withdrawals` eventually converts a `BuilderPendingWithdrawal` into an execution-layer `Withdrawal`, `get_builder_withdrawals` copies `amount=withdrawal.amount` unmodified into the committed list [5](#0-4) . Only later, in `apply_withdrawals`, does the beacon state deduct `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance` — i.e. the state-side debit is capped at whatever balance the builder happens to have at that moment [6](#0-5) .

The equality broken: the sum of ETH the execution layer is committed to credit to withdrawal addresses (`Withdrawal.amount` in the block-committed `payload_expected_withdrawals`) must equal the sum of ETH debited from beacon-state-tracked balances (builder or validator balances). Here, if a builder's balance is smaller than the pending withdrawal amount (which can happen legitimately, e.g. the builder's balance was reduced by an earlier withdrawal or slashing-like penalty processed in between bid submission and settlement, or by multiple pending withdrawals draining the same builder), the committed `Withdrawal.amount` used by the execution layer exceeds the actual debit applied to `state.builders[...].balance`. This creates ETH: the recipient address on the execution layer receives more Gwei than was ever removed from any account in the consensus state, since builder balances are validator-state-external.

This is directly demonstrated (as an intended/tested-for behavior, not defended against) by the repo's own test: `test_builder_withdrawal_insufficient_balance` sets a builder balance of 1 ETH but a pending withdrawal amount of 5 ETH, and asserts the committed withdrawal still carries `amount = 5 ETH` while the balance is merely floored at 0 [7](#0-6) .

### Impact Explanation
This falls under Critical: "Gwei created ... or paid to a non-owner" / "a payload executed or paid that the block did not commit to" (inverted: the block commits to paying more than is actually backed). If a builder's balance can legitimately fall below its outstanding pending withdrawal total (e.g., via `get_builders_sweep_withdrawals` draining balance first, via `initiate_builder_exit`/withdrawability interactions, or by multiple queued `BuilderPendingWithdrawal`s summing above the balance without any check at enqueue or dequeue time), the execution layer will be instructed by a spec-following consensus client to mint ETH to the `fee_recipient` beyond what was actually removed from beacon-chain-tracked funds, breaking the total-supply invariant.

### Likelihood Explanation
Likelihood depends on whether any invariant elsewhere in the spec guarantees `sum(pending builder withdrawal amounts for a builder) <= builder.balance` at all times between enqueue and settlement. The docstring/spec comment for `get_builder_withdrawals`/`apply_withdrawals` treats "insufficient balance" as an explicitly anticipated and tested case (not an assertion failure), and the queue can accumulate duplicate entries for the same builder without balance re-validation at dequeue time [8](#0-7) , so it appears reachable through normal spec-following state transitions rather than requiring a byzantine participant.

### Recommendation
Cap the committed `Withdrawal.amount` in `get_builder_withdrawals` (and in `get_builders_sweep_withdrawals` if similarly affected) to `min(withdrawal.amount, builder.balance)` — the same cap already applied in `apply_withdrawals` — so the execution-layer-committed amount always matches the actual state-side debit, preserving the total-supply invariant.

### Proof of Concept
1. Builder `B` has `balance = 1e9` Gwei (1 ETH) and two `BuilderPendingWithdrawal` entries queued for it, each requesting `amount = 5e9` Gwei (as in `test_builder_withdrawal_insufficient_balance` and `test_duplicate_builder_index_in_pending_withdrawals`) [7](#0-6) .
2. `get_expected_withdrawals` → `get_builder_withdrawals` emits `Withdrawal(amount=5e9)` for each entry into `state.payload_expected_withdrawals`, which the execution layer is required to honor exactly.
3. `apply_withdrawals` deducts only `min(5e9, 1e9) = 1e9` from `B.balance` for the first withdrawal (balance now 0), and `min(5e9, 0) = 0` for the second.
4. Total committed withdrawal payout = `1e10` Gwei (10 ETH); total actual debit from `B.balance` = `1e9` Gwei (1 ETH). The execution layer pays out `9e9` Gwei (9 ETH) that was never debited from any consensus-layer-tracked account.
