### Title
Unprivileged `DepositDelegatorRewards` can permanently lock lamports in a vote account with zero delegated stake - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
`deposit_delegator_rewards()` lets any signer transfer lamports into a vote account's `pending_delegator_rewards` field with no check that the vote account has any active delegated stake. When that vote account's `total_active_stake` is zero, the reward-distribution path (`calculate_block_reward`) never distributes (and therefore never reduces) `pending_delegator_rewards` for it, leaving the deposited lamports permanently stuck — the exact same "increase the pool total without any corresponding share/consumption accounting" pattern described in the Notional `reinvestReward()` report, where `totalPoolClaim` grows while `totalVaultSharesGlobal` stays at zero, leaving funds unredeemable.

### Finding Description
`deposit_delegator_rewards()` is reachable by any transaction where the source account signs; it performs a CPI system transfer and then unconditionally increments `pending_delegator_rewards` via `add_pending_delegator_rewards()`: [1](#0-0) 

There is no check on whether the target vote account has any active delegated stake before accepting the deposit. The only "consumption" path for `pending_delegator_rewards` is `calculate_block_reward()`, which looks up `total_active_stake` for the vote account, and if it is zero, returns `0` — i.e., no reward is redeemed and `pending_delegator_rewards` is not reduced for that vote account in that epoch: [2](#0-1) 

Meanwhile, `withdraw()` explicitly reserves `pending_delegator_rewards` lamports and refuses withdrawals (or closing the account) that would dip into that reserve, as verified by `test_withdraw_pending_delegator_rewards`/`test_withdraw_with_pending_delegator_rewards`: [3](#0-2) [4](#0-3) 

Combining these: if a vote account has zero delegated stake (either because it never received any delegation, or all delegations deactivate/undelegate), any unprivileged party can call `DepositDelegatorRewards` to push lamports into `pending_delegator_rewards`. Since `total_active_stake == 0` causes `calculate_block_reward` to always return `0` for that account, `pending_delegator_rewards` is never decremented, and the authorized withdrawer can never withdraw those lamports (blocked by the reserve check) nor close the account (`InsufficientFunds` while `pending_delegator_rewards > 0`). This mirrors the Notional root cause: a public/permissionless "reinvest"-like operation that increases an aggregate accounting field (`totalPoolClaim` / `pending_delegator_rewards`) without any corresponding mechanism to bring the "shares" (`totalVaultSharesGlobal` / active stake) in line, permanently corrupting the account's redeemable state.

### Impact Explanation
This results in unauthorized, irreversible fund lock-up: lamports deposited by any signer (or even self-griefed by the withdrawer) become permanently unspendable/unwithdrawable from the vote account once `total_active_stake` is zero, since the code path that would reduce `pending_delegator_rewards` never fires. This is a concrete state-mutation bug reachable by an ordinary transaction with unprivileged actors, causing loss of access to funds for the vote account's authorized withdrawer — a direct analog of the "vault enters an abnormal state" impact in the source report.

### Likelihood Explanation
Requires only a v4 vote account (post SIMD-0185) with the relevant features enabled (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`) and zero currently-active delegated stake — a state easily reached for freshly created vote accounts before any delegation lands, or for vote accounts whose stake has fully deactivated. No special privileges are needed to trigger the deposit call.

### Recommendation
Before or after incrementing `pending_delegator_rewards` in `deposit_delegator_rewards()`, verify the vote account currently has non-zero active delegated stake (or provide an alternate path to reclaim/refund `pending_delegator_rewards` when `total_active_stake` is zero), analogous to the recommended `totalVaultSharesGlobal > 0` guard in the Notional fix.

### Proof of Concept
1. Create/observe a V4 vote account with all SIMD features enabled but with zero stake delegated to it (`total_active_stake == 0` for that epoch, as modeled in `get_block_reward_for_test(0, 0, ...)` in the test suite).
2. Any signer calls `VoteInstruction::DepositDelegatorRewards { deposit: N }` with itself as the source account — this succeeds and increases `pending_delegator_rewards` by `N` [5](#0-4) .
3. At epoch boundaries, `calculate_block_reward()` returns `0` for this account because `total_active_stake == 0` [6](#0-5) , so `pending_delegator_rewards` is never reduced.
4. The authorized withdrawer attempts `Withdraw` for any amount that would encroach on the `pending_delegator_rewards` reserve, or tries to close the account — both fail with `InstructionError::InsufficientFunds`, as demonstrated by the existing test `test_withdraw_pending_delegator_rewards` [3](#0-2) , permanently locking the deposited lamports.

Note: I was unable to fully trace within the available search budget whether any other code path elsewhere in the reward/distribution pipeline decrements `pending_delegator_rewards` outside of `calculate_block_reward`'s stake-proportional payout; no such decrement site was found via targeted search (`pending_delegator_rewards.*sub`), but a full audit of the reward-distribution module (e.g. `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`) would be needed to rule out an alternate reclaim mechanism with certainty.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
