### Title
FoT/rebase underlying mints tranche shares on received delta but pushes the nominal `_amount` to the strategy, draining withdrawal buffer - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault._deposit` (and `IdleCDO._deposit` when `directDeposit` is enabled) correctly mints tranche shares using the post-transfer balance delta, so fee-on-transfer/rebase tokens are partially handled at the share-minting layer — the Blueberry-style mis-mint is avoided. However, the same function then forwards the *requested* `_amount`, not the received delta, to `IIdleCDOStrategy(strategy).deposit(_amount)`. The strategy (`contracts/strategies/idle/IdleCreditVault.sol` / `BaseStrategy.sol`-style strategies) pulls `safeTransferFrom(msg.sender, address(this), _amount)` from the CDO. With an FoT underlying, the CDO received less than `_amount`, so the extra tokens are pulled out of the CDO's residual balance — i.e., the liquidity buffer reserved for instant withdrawals and epoch payouts.

### Finding Description
In `contracts/IdleCDOCreditVault.sol` `_deposit` (lines ~201-211):

```solidity
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
// minted on the *actual* received amount
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
_updateSplitRatio(_getAARatio(true));
IIdleCDOStrategy(strategy).deposit(_amount); // <-- nominal amount, not delta
```

The strategy then performs `underlyingToken.safeTransferFrom(idleCDO, strategy, _amount)`. For a token that takes a fee on transfer, `balanceDelta < _amount`, yet the strategy debits the full `_amount` from the CDO. The shortfall (`_amount - delta`) is sourced from tokens the CDO already holds for other purposes — pending instant-withdraw reserves and unstopped-epoch liquidity — while the depositor is only charged their own tokens and only minted shares for the delta. `IdleCDO._deposit` (lines ~248-258) has the identical pattern gated on `directDeposit`.

### Impact Explanation
Each deposit by any KYC'd lender silently moves `fee% * _amount` of withdrawal-reserved liquidity into the borrower/strategy sleeve. The broken invariant is solvency of the withdrawal buffer: `collectWithdrawFunds` / instant-withdraw reserves become under-collateralized even though the strategy still owes the full principal. Withdrawing lenders later find the CDO short of tokens (insolvency / permanent freezing of unclaimed payouts), while the borrower-side accounting shows the full `_amount` deployed. Loss per deposit equals the token's transfer fee; repeated deposits or a large deposit can drain the entire buffer.

### Likelihood Explanation
Conditional: it requires the CDO's `token` to be fee-on-transfer or rebasing (e.g., USDT if its fee switch is ever enabled, or a rebasing stable). Token choice is owner-controlled and honest, so this is not exploitable on current USDC-denominated vaults; it is a latent accounting bug identical in class to the referenced Blueberry finding — the share-mint side was hardened with a delta, but the downstream strategy push was not. If the buffer is smaller than the shortfall the call reverts, limiting impact to a deposit DoS; the harmful case is when a buffer exists.

### Recommendation
Use the measured delta for the strategy deposit:

```solidity
uint256 _received = _contractTokenBalance(_token) - _preBal;
_minted = _mintSharesAtCurrPrice(_received, msg.sender, _tranche);
...
IIdleCDOStrategy(strategy).deposit(_received);
```

Apply the same fix in `IdleCDO._deposit` for the `directDeposit` branch, or explicitly document/revert that FoT underlyings are unsupported.

### Proof of Concept
A Foundry PoC would deploy `IdleCDOCreditVault` with a mock FoT ERC20 (e.g., 1% burn on transfer) as `token`, seed the CDO with withdrawal-reserve liquidity via a first deposit, then have a second KYC'd lender call `depositAA(x)`. Assert: strategy balance increased by `x` while CDO balance decreased by `x` (not `0.99x`), i.e., CDO's residual balance fell below the reserved withdraw amount; a subsequent `requestWithdraw`/instant-withdraw claim reverts on insufficient balance. Note: this PoC could not be executed here (read-only tooling, no mock FoT token verified in repo), so the claimed reversion path and exact reserve accounting lines in the strategy's `deposit` were not fully line-verified — the core discrepancy at `IdleCDOCreditVault.sol:204-211` is confirmed.
