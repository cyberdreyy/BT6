### Title
Withdraw instruction parser mislabels arbitrary attacker-supplied accounts as `instructionsSysvar`/proof-context accounts when `account_indexes` length is inconsistent with the encoded proof offset flags - (File: `transaction-status/src/parse_token/extension/confidential_transfer.rs`)

### Finding Description
`parse_confidential_transfer_instruction`'s `Withdraw` branch only guarantees `account_indexes.len() >= 4` via `check_num_token_accounts(account_indexes, 4)` [1](#0-0) . It then walks a fixed sequential slot budget (`offset`, starting at 2) guarded only by `offset < account_indexes.len().saturating_sub(1)`, filling optional fields (`instructionsSysvar`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`) purely based on the *data-supplied* `equality_proof_instruction_offset`/`range_proof_instruction_offset` flags, in a fixed priority order (sysvar first, then equality, then range) [2](#0-1) .

The instruction data (`WithdrawInstructionData`, including both proof offsets) and `account_indexes` are both fully attacker-controlled fields of a compiled instruction inside a transaction message; nothing enforces that the *number* of trailing accounts actually matches what the flags claim to need. When a legitimately-constructed instruction is built via `inner_withdraw`, the account list length always matches the flags (as shown by the existing `test_withdraw` combinations) [3](#0-2) , but an attacker who hand-crafts the `Message`/`CompiledInstruction` is not bound by that helper and can supply exactly 4 accounts (the checked minimum) together with flags (e.g. `equality_proof_instruction_offset == 0`, `range_proof_instruction_offset != 0`) that, under the real spl-token-2022 program semantics, would require 5 accounts (token, mint, sysvar, equality-context, owner) to be self-consistent.

With only 4 accounts and that flag combination:
- `has_sysvar` is true (range offset != 0) so slot `account_indexes[2]` is labeled `"instructionsSysvar"`.
- The following `equality_proof_instruction_offset == 0` branch is then skipped because `offset` (now 3) is no longer `< len - 1 (3)`, so no `"equalityProofContextStateAccount"` is emitted at all even though the flag says the equality proof is context-state-based.
- `parse_signers` then labels `account_indexes[3]` as `"owner"`.

The net effect: the account at index 2 — which, per the encoded flags, semantically should be an equality-proof context-state account — is instead labeled `"instructionsSysvar"` in the parsed JSON, and no `equalityProofContextStateAccount` field is produced at all. The attacker fully controls which arbitrary pubkey occupies that slot, so the parsed output falsely claims an attacker-chosen account is the `instructionsSysvar` (normally a fixed, well-known address), or conversely omits/mislabels the equality-proof context account.

This works because `check_num_token_accounts` only checks a lower bound on account count and never cross-validates it against the offset flags, and the sequential `offset`-slot-filling logic assumes (without enforcing) that account count and flags were produced together by the canonical instruction builder.

### Impact Explanation
This is a decoder/parser misreporting bug (`parse_token` → `parse_confidential_transfer_instruction`) reachable via any RPC method that returns "parsed" instruction JSON (e.g. `getTransaction`, `getConfirmedTransaction`, `getBlock` with `encoding: "jsonParsed"`, or transaction/logs pubsub with parsed encoding) for a transaction whose message the attacker fully controls. The instruction need not even succeed on-chain — a transaction can land in a block (and thus be queryable) as long as it pays fees and is otherwise well-formed, even if the confidential-transfer program itself later rejects it for missing accounts. This falls under the accepted "wrong … account data returned" / decoder misreporting category, since downstream tooling/wallets/explorers relying on the parsed `instructionsSysvar` / `equalityProofContextStateAccount` / `owner` fields would attribute an attacker-chosen account to the wrong semantic role.

### Likelihood Explanation
Fully attacker-reachable with a single crafted transaction/message (no special privileges, no leader/validator control): the attacker only needs to hand-construct a `CompiledInstruction` with `account_indexes.len() == 4` and proof offset flags whose true semantics require 5 accounts, then submit it via a single `sendTransaction` (or simply have the RPC parse an already-submitted such message) and read back the parsed JSON via one `getTransaction` call. This is deterministic and repeatable for every combination where the true minimum account count (per flags) exceeds 4 but the crafted account_indexes length is only 4.

### Recommendation
Cross-validate the required account count against the encoded proof-offset flags before filling optional fields — compute the exact expected number of trailing accounts from `has_sysvar`, `equality_proof_instruction_offset == 0`, and `range_proof_instruction_offset == 0`, call `check_num_token_accounts` with that computed minimum (instead of the flat `4`), and only then perform the unconditional (non-`saturating_sub`-guarded) slot assignment. Apply the same fix to the structurally identical logic in `Transfer`, `TransferWithFee`, and `confidential_mint_burn.rs`'s `Mint`/`Burn` branches, which share this pattern.

```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (test module)
#[test]
fn test_withdraw_offset_flag_mismatch_mislabels_account() {
    use solana_instruction::{AccountMeta, Instruction};

    let program_id = spl_token_2022_interface::id();
    let token_account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let mystery_account = Pubkey::new_unique(); // attacker-chosen, arbitrary account
    let owner = Pubkey::new_unique();

    // Hand-craft WithdrawInstructionData bytes with:
    //   equality_proof_instruction_offset == 0  (claims equality proof is a context account)
    //   range_proof_instruction_offset != 0     (claims range proof is inline -> needs sysvar)
    // but supply only 4 accounts total (the checked minimum), which is only
    // self-consistent when BOTH offsets are non-zero.
    let mut data = vec![/* ConfidentialTransferInstruction::Withdraw discriminator + Withdraw sub-discriminator */];
    // ... append amount, decimals, new_decryptable_available_balance,
    //     equality_proof_instruction_offset = 0i8,
    //     range_proof_instruction_offset = 1i8   (non-zero)

    let instruction = Instruction {
        program_id,
        accounts: vec![
            AccountMeta::new(token_account, false),
            AccountMeta::new_readonly(mint, false),
            AccountMeta::new_readonly(mystery_account, false), // should be "equalityProofContextStateAccount"
            AccountMeta::new_readonly(owner, true),
        ],
        data,
    };

    let message = Message::new(&[instruction], None);
    let parsed = parse_token(
        &message.instructions[0],
        &AccountKeys::new(&message.account_keys, None),
    )
    .unwrap();

    // BUG: mystery_account gets mislabeled as instructionsSysvar even though
    // equality_proof_instruction_offset == 0 claims it should be an
    // equalityProofContextStateAccount, and that field is silently dropped.
    assert_ne!(
        parsed.info.get("instructionsSysvar"),
        Some(&json!(mystery_account.to_string())),
        "mystery_account should not be mislabeled as instructionsSysvar"
    );
    assert_eq!(
        parsed.info.get("equalityProofContextStateAccount"),
        Some(&json!(mystery_account.to_string())),
        "equalityProofContextStateAccount should be reported when offset == 0"
    );
}
```
Expected (buggy) result: the first assertion fails — `mystery_account` is reported under `instructionsSysvar` — and the second assertion also fails because `equalityProofContextStateAccount` is missing entirely, confirming the parse-fidelity violation.
