## Analysis: Weight double-counting in `StackerDBListener` — analog of the EIP-2981 "single bucket" bug

The Sherlock report's essence: a quantity that must be tracked *distinctly per source* (per-token royalty) is instead accumulated into a single undifferentiated bucket, so the aggregate no longer reflects the truth it's supposed to represent. The reachable analog in this codebase is in the miner's signer-response tally: a single signer's weight can be attributed to **both** the accept bucket and the reject bucket for the same block, breaking the invariant that `total_weight_approved + total_weight_rejected` should never double-count one signer's weight.

### Root cause

`StackerDBListener` maintains, per proposed block, independent counters `total_weight_approved` and `total_weight_rejected`, gated by two *different* dedup sets:

- The `Accepted` handler gates on `block.gathered_signatures.contains_key(&slot_id)` before adding to `total_weight_approved`: [1](#0-0) 

- The `Rejected` handler gates on a *separate* structure, `block.responded_signers.insert(slot_id)`, before adding to `total_weight_rejected`: [2](#0-1) 

Neither handler checks the *other* bucket's membership before crediting weight. A slot_id that has already had its weight counted in `total_weight_approved` (via `gathered_signatures`) is not excluded from also being counted in `total_weight_rejected` (via `responded_signers`), and vice versa — a signer that rejects first and later accepts will have its weight added to `total_weight_rejected` by the reject-handler's own gate, then *also* added to `total_weight_approved` by the accept-handler's gate, since `gathered_signatures` never held that slot before.

### Where the miscounted weight is consumed

The coordinator checks the inflated `total_weight_rejected` **before** checking `total_weight_approved`, and treats crossing the blocking-minority threshold as fatal (`SignersRejected`), including banning transaction ids based on the (inflated) per-txid weight: [3](#0-2) 

So a single signer (one slot, no majority, no other signer's key needed) can:
1. Send `BlockResponse::Rejected` for a proposal, crediting its weight `w` into `total_weight_rejected`.
2. Later send `BlockResponse::Accepted` (a legitimate signature) for the same proposal, crediting the same weight `w` into `total_weight_approved`.

`w` is now counted in both totals simultaneously. Combined with the honest opposing minority's weight `R` (still `< 30%` on its own), the *displayed* `total_weight_rejected = R + w` can cross the blocking-minority threshold `total_weight - weight_threshold` purely from this double count, even though the truly distinct rejecting weight is still `R < 30%`. Because the coordinator checks `total_weight_rejected` first, this manufactures a spurious `SignersRejected` outcome — a liveness wedge in which the miner abandons a block proposal (and potentially bans transactions per `failed_txids` weight, also inflated by the same mechanism) that legitimately had enough distinct approving weight, purely because one signer's weight was double-attributed across the two mutually exclusive buckets.

This is a direct structural analog of the report: royalty (weight) that should be attributed to exactly one recipient/bucket is instead split/duplicated across buckets because the tracking system uses independent, non-mutually-exclusive dedup keys (`gathered_signatures` vs `responded_signers`) instead of a single per-signer ledger that enforces "one signer, one vote, one bucket."

### Title
Signer weight double-counted across `total_weight_approved` and `total_weight_rejected` in `StackerDBListener`, letting one signer manufacture a spurious block rejection — (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::handle_signer_message` (the message dispatch containing the `Accepted`/`Rejected` arms shown above) tracks accept-weight and reject-weight with two independent dedup sets (`gathered_signatures` and `responded_signers`) instead of one shared per-slot ledger. A single signer that sends a rejection and later an acceptance (or the reverse) for the same block has its weight credited into *both* `total_weight_approved` and `total_weight_rejected`, violating the conservation invariant that a signer's weight should be attributed to at most one outcome.

### Finding Description
The `Accepted` arm gates crediting `total_weight_approved` on whether `slot_id` is already a key in `gathered_signatures`. The `Rejected` arm gates crediting `total_weight_rejected` on whether `slot_id` is newly inserted into `responded_signers`. These are two disjoint data structures with no cross-check, so nothing prevents the same `slot_id`'s weight from being added to both totals when that signer emits one message of each kind for the same `signer_signature_hash`. `signer_coordinator.rs` then evaluates `total_weight_rejected` (using the inflated value) against the blocking-minority threshold before ever checking `total_weight_approved`, so the inflated rejection count can independently trigger `NakamotoNodeError::SignersRejected`, along with txid exclusion logic that also uses the same per-signer weight accounting for `failed_txids`.

### Impact Explanation
This lets a single, minority-weight signer (no collusion, no other signer's key, no majority required) manufacture an appearance of higher rejection weight than truly exists, causing the miner to prematurely conclude a block proposal is globally rejected even though genuinely distinct opposing weight never reached 30%. This is a liveness wedge on block production for that proposal (forcing resubmission/miner stalls) and can incorrectly flag/ban transactions via the `failed_txids` weight path, which uses the same signer-weight bookkeeping.

### Likelihood Explanation
Trivially triggerable by any single participating signer (or a compromised/buggy signer client) simply by emitting a `BlockRejected` and then a `BlockAccepted` (or vice versa) for the same block over StackerDB — both are messages a legitimate signer is expected to be able to send during the normal proposal lifecycle (e.g., re-evaluating a decision), so no special privileges beyond controlling one signer slot are required.

### Recommendation
Track weight-crediting with a single per-signer ledger shared between the accept and reject code paths (e.g., a `HashMap<slot_id, FinalVote>` or reuse `responded_signers` for both branches with a tri-state result), so that once a slot_id's weight has been counted toward one outcome it is excluded from being counted toward the other, and updates to a signer's vote should replace rather than add to the previous bucket's tally.

### Proof of Concept
1. Reward set has signers A (weight 25), B (weight 25), C (weight 40), D (weight 10); `weight_threshold` = 70 (of 100), blocking minority = 30.
2. Miner proposes block `H`.
3. A and B genuinely reject `H` (`total_weight_rejected` = 50 already... to keep numbers below the threshold, assume just C initially rejects: `total_weight_rejected = 40`, still under 30? adjust weights for clarity):
   - Assume weights: A=15, B=15, C=40, D=30, threshold=70, blocking minority=30.
   - A and B genuinely reject: `total_weight_rejected = 30` (already at the threshold in this toy example — pick smaller weights to stay under 30, e.g., A=10,B=10 rejecting gives 20, under 30).
4. D initially sends `Rejected` for `H`: `responded_signers` gains D's slot, `total_weight_rejected += 30` → now `20 + 30 = 50` (nowhere near enough alone to flip, but shows the credit happens).
5. D later reconsiders and sends `Accepted` for `H` (a legitimate signature): since D's slot is not yet in `gathered_signatures`, `total_weight_approved += 30`.
6. Result: `total_weight_rejected = 50` and `total_weight_approved = 30` are simultaneously non-zero for D's weight, i.e., D's 30 weight is present in both totals. Tune the honest-minority weight so that `total_weight_rejected` (inflated by D's double-counted weight) crosses `total_weight - weight_threshold` before `total_weight_approved` (which correctly reflects real signatures, including D's) can reach `weight_threshold`, causing `signer_coordinator.rs` to return `SignersRejected` at [4](#0-3)  even though the truly distinct rejecting weight (excluding D, who ultimately accepted) never reached the 30% blocking minority.
