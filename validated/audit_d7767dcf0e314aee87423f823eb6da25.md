### Title
Pending APR0 withdraw requests permanently brick `stopEpoch` once a non-zero APR is set, freezing all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The CVE analog is a state machine that can never make progress: in Miniz, `sym2`/`counter` stay zero so `tinfl_decompress` loops forever; here, `apr0TotalPrincipal` can never be cleared once `unscaledApr != 0`, because `prepareStopEpochWithApr0` unconditionally reverts in that state. Since `prepareStopEpochWithApr0` is invoked on the `stopEpoch` path, any non-zero `apr0TotalPrincipal` combined with a non-zero APR makes every `stopEpoch` call revert, permanently freezing the epoch and all funds owed to lenders and withdraw requesters.

### Finding Description
`requestWithdraw` routes requests into the APR0 bucket whenever `unscaledApr == 0` at request time:

- `IdleCreditVault.sol:285-287` — `if (unscaledApr == 0 && !isClosed) { _requestWithdrawApr0(_amount, _user); }`
- `IdleCreditVault.sol:567-577` — `_requestWithdrawApr0` increments `apr0Users[_user].principal` and the global `apr0TotalPrincipal`.

At epoch end, the CDO calls `prepareStopEpochWithApr0`, which contains the fatal ordering:

- `IdleCreditVault.sol:502-508`:
```solidity
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```
The fast-path return happens only when `apr0TotalPrincipal == 0`. If it is non-zero and `unscaledApr != 0`, the function reverts before reaching the bucket-closing `apr0TotalPrincipal = 0` at line 540.

There is no other non-default path that clears `apr0TotalPrincipal`:
- `_settleApr0` (lines 545-565) only moves per-user `principal` into `settledPrincipal`; it never decrements the global `apr0TotalPrincipal`.
- `_clearWithdrawClaimForEpoch` (lines 822-828) reduces `apr0TotalPrincipal` only while clearing a *default* claim.
- `_ensureDefaultRecoveryInitialized` (line 931) zeroes it only during lazy migration when `pendingWithdraws != 0` and the pool is closed.

`unscaledApr` can be set non-zero by the honest manager or CDO via `setAprs`/`setAprsWithBuffer`/`setApr` (lines 206-235) — a routine, legitimate action when a new loan is priced for the next epoch. Nothing in `setAprsWithBuffer` warns that a pending APR0 bucket makes the change fatal.

Sequence:
1. Vault runs an epoch with `unscaledApr == 0` (APR0 mode).
2. Attacker (any KYC-passing lender / tranche holder) deposits a minimal amount and calls `requestWithdraw` via the CDO with dust `_amount`. `apr0TotalPrincipal` becomes non-zero.
3. Manager (honest) calls `setAprsWithBuffer` to price the next loan with `unscaledApr > 0`, or `setAprs` directly.
4. Borrower repays; manager/queue calls `stopEpoch` → `prepareStopEpochWithApr0` → `apr0TotalPrincipal != 0 && unscaledApr != 0` → `revert NotAllowed()`.
5. Every subsequent `stopEpoch` reverts identically. `epochNumber` never increments, so `claimWithdrawRequest` also reverts for all requesters via the `epochNumber <= lastWithdrawRequest` gate at line 326. The epoch state machine is permanently stuck — the direct analog of the decompressor's counter that can never advance.

### Impact Explanation
Permanent freezing of all funds in the credit vault: borrower repayments held by the strategy cannot be distributed, all pending withdraw receipts (not just the attacker's dust receipt) can never be claimed, and active tranche holders cannot redeem because redemptions route through epoch processing. The attacker's cost is a single dust deposit + withdraw request during any APR0 epoch; the damage scales to the entire vault TVL. This is a stuck-state/no-progress bug with direct fund impact, not a gas/DoS-only issue.

### Likelihood Explanation
Likelihood depends on a real operational transition: an APR0 epoch followed by a non-zero APR epoch. That transition is a normal business event (a zero-rate promotional/parked period, then a priced loan). The attacker only needs to seed `apr0TotalPrincipal` with dust during the APR0 window — it persists across epochs because the bucket is global and only cleared inside the reverting function. No malicious privileged role is required; the honest manager's routine repricing triggers the freeze.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert on `unscaledApr != 0`. Either:
- settle the APR0 bucket at zero interest (`apr0RateByEpoch[epochNumber] = 0`, `apr0TotalPrincipal = 0`) and proceed, or
- move the check earlier: reject `requestWithdraw` into the APR0 path once a non-zero APR has been scheduled, and/or clear the APR0 bucket inside `setAprsWithBuffer` when transitioning APR from 0.

Additionally, gate `setApr`/`setAprs` to refuse a 0→non-zero transition while `apr0TotalPrincipal != 0`, so the invariant "APR0 bucket only exists while APR is 0" is enforced at write time rather than at the irreversible `stopEpoch` boundary.

### Proof of Concept
A Foundry fork test would:

1. Deploy/attach `IdleCDOEpochVariant` + `IdleCreditVault` with `unscaledApr == 0`, a funded borrower epoch in progress.
2. As an unprivileged lender, deposit 1 wei-equivalent of underlying into a tranche and call the CDO's withdraw-request entry so `IdleCreditVault.requestWithdraw(dust, attacker, dust)` executes → assert `apr0TotalPrincipal() == dust`.
3. As manager, call `setAprsWithBuffer(newApr, duration, buffer)` with `newApr > 0` (the honest repricing for the next loan).
4. Warp past `epochEndDate`, have the borrower repay principal+interest, then call `stopEpoch` on the CDO.
5. Assert `stopEpoch` reverts with `NotAllowed()`; repeat to show it always reverts; assert `epochNumber` is unchanged and a second lender's `claimWithdrawRequest` also reverts → permanent freeze of the repaid funds.
