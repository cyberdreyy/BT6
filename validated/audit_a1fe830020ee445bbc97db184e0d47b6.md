### Title
Unbounded WebSocket Handshake in RPC PubSub `listen()`/`handle_connection` Enables Stream/Connection Exhaustion DoS - (File: rpc/src/rpc_pubsub_service.rs)

### Summary
The RPC PubSub server's `listen()` function accepts every incoming TCP connection unconditionally and spawns a task per connection that calls `server.receive_request().await?` with no timeout and no cap on concurrent connections, mirroring the reported gRPC `stream.Recv()`-without-timeout DoS pattern in the external report.

### Finding Description
In `rpc/src/rpc_pubsub_service.rs`, `listen()` accepts TCP connections in a loop and immediately spawns `handle_connection` for each one via `tokio::spawn`, using only a `TokenCounter` for metrics tracking, not enforcement: [1](#0-0) 

`TokenCounter::create_token()` only emits a `datapoint_info!` metric based on `Arc::strong_count` — it has no ability to reject or limit connections: [2](#0-1) 

Inside `handle_connection`, the very first operation is `server.receive_request().await?`, which waits for the client's WebSocket handshake bytes with no timeout applied: [3](#0-2) 

A malicious client can open a TCP connection to the pubsub port and simply never send (or send partial) WebSocket handshake bytes. The spawned tokio task, and the underlying TCP socket/file descriptor, will remain alive indefinitely waiting on `receive_request()`. Because there is no cap on the number of concurrently-accepted connections and no handshake timeout, repeating this many times exhausts file descriptors and tokio task/socket resources on the validator, exactly as described in the original report's gRPC stream analog (`stream.Recv()` without a deadline).

This is structurally identical to the reported issue: both cases involve a network-facing bidirectional handshake/authentication step that blocks indefinitely on a peer-controlled `recv`, with no per-connection timeout and no enforced concurrency cap, allowing resource (fd/socket/task) exhaustion.

### Impact Explanation
An unauthenticated remote attacker can open a large number of TCP connections to the RPC PubSub port (default 8900) and withhold the WebSocket handshake, or send it byte-by-byte extremely slowly, holding open file descriptors and spawned tokio tasks indefinitely. This can exhaust the process's file descriptor limit (default 1024 on many Linux systems, and validators often just raise this but it's still finite) or otherwise degrade the RPC pubsub service, preventing legitimate WebSocket clients (used for account/program/log/slot subscriptions) from connecting, and potentially impacting other services sharing the same process's fd budget. This is a service-availability/DoS issue against the RPC-facing component, not a consensus or fund-safety issue.

### Likelihood Explanation
High likelihood of triggerability: the RPC PubSub endpoint is unauthenticated and reachable by any network client that can reach the configured pubsub port; no special privileges, staking, or on-chain state are required, and the resource cost to the attacker (opening a TCP socket and withholding data) is far lower than the resource cost imposed on the validator (a held fd + tokio task indefinitely).

### Recommendation
Wrap `server.receive_request().await` (and, more generally, all per-connection async work in `handle_connection`) in a `tokio::time::timeout` with a bounded duration, closing/dropping the connection if the handshake or any subsequent read does not complete in time — mirroring the way `streamer/src/nonblocking/quic.rs` applies `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` and `wait_for_chunk_timeout` to bound QUIC connection/stream lifetimes. Additionally, enforce an actual cap on concurrently accepted (but not-yet-handshaked) pubsub TCP connections rather than relying solely on the non-enforcing `TokenCounter` metric.

### Proof of Concept
1. Start a validator/test-validator with RPC PubSub enabled.
2. From an attacker host, open N TCP connections to the pubsub port (e.g., using raw sockets) and, for each, send nothing after connecting (do not perform the WebSocket handshake).
3. Observe that each connection spawns a task in `handle_connection` blocked on `server.receive_request().await` indefinitely; repeat until the validator's open file descriptor count approaches its limit, at which point new legitimate PubSub (and potentially other) connections begin to fail.

impl TokenCounter {
    /// Creates a new counter with the specified metrics `name`.
    pub fn new(name: &'static str) -> Self {
        Self(Arc::new(name))
    }

    /// Creates a new token for this counter. The metric's value will be equal
    /// to the number of `CounterToken`s.
    pub fn create_token(&self) -> CounterToken {
        // new_count = strong_count
        //    - 1 (in TokenCounter)
        //    + 1 (token that's being created)
        datapoint_info!(*self.0, ("count", Arc::strong_count(&self.0), i64));
        CounterToken(self.0.clone())
    }
}
