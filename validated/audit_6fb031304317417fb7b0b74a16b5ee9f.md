### Title
`parse_address_lookup_table` mislabels arbitrary trailing accounts as `payerAccount`/`systemProgram` in `ExtendLookupTable` by account-count heuristic instead of verifying identity - (File: transaction-status/src/parse_address_lookup_table.rs)

### Summary
The `ExtendLookupTable` branch of `parse_address_lookup_table` only requires `check_num_address_lookup_table_accounts(&instruction.accounts, 2)`, then separately checks `if instruction.accounts.len() >= 4` to decide whether to emit `payerAccount`/`systemProgram` fields, mapping `account_keys[accounts[2]]` and `account_keys[accounts[3]]` to those roles purely by position. No check is performed that `account_keys[accounts[3]]` actually equals `system_program::id()`, so any 4-account `ExtendLookupTable` instruction — even one where accounts 2/3 are attacker-chosen unrelated keys — is unconditionally reported with those roles.

### Finding Description
In `transaction-status/src/parse_address_lookup_table.rs`, the `ExtendLookupTable` match arm: [1](#0-0) 
only calls `check_num_address_lookup_table_accounts(&instruction.accounts, 2)`, meaning the instruction is accepted with as few as 2 accounts. It then independently checks `instruction.accounts.len() >= 4` and, if true, blindly inserts `account_keys[instruction.accounts[2]]` as `"payerAccount"` and `account_keys[instruction.accounts[3]]` as `"systemProgram"` with no verification that the latter is actually the System Program ID (unlike, e.g., verifying against `solana_sdk_ids::system_program::id()`). This is purely a count-based heuristic ("if there happen to be 4 accounts, assume positions 2 and 3 are payer/system-program"), not a semantic check.

Since a client can construct and sign any `CompiledInstruction` with the `AddressLookupTable` program ID, arbitrary account indices, and an `ExtendLookupTable` payload (bincode-encoded `ProgramInstruction::ExtendLookupTable{ new_addresses }`), it can supply 4 accounts where indices 2 and 3 are unrelated dummy keys (not a fee payer, not the system program). The transaction may fail at runtime execution (e.g., the on-chain address-lookup-table program CPI into "system program" would fail with `IncorrectProgramId` if index 3 isn't actually `11111111111111111111111111111111`), but Solana still includes failed transactions in the block and they remain queryable via `getTransaction`/`getConfirmedTransaction` with `encoding: jsonParsed`. The RPC-side instruction parser (`parse_address_lookup_table`) runs independently of runtime execution result and is not aware of whether the transaction succeeded or which accounts were truly used, so it will emit the misleading `payerAccount`/`systemProgram` fields based only on position.

### Impact Explanation
This causes `getTransaction`/`getConfirmedTransaction` (jsonParsed encoding) to return incorrect `payerAccount` and `systemProgram` fields for downstream integrators (explorers, indexers, wallets) that trust these parsed fields, misattributing an arbitrary attacker-chosen key as the fee payer or as the System Program. This matches the "decoder misreporting authority/payer" category described in the audit scope (Scope: High, decoding logic produces incorrect but plausible parsed output).

### Likelihood Explanation
Fully reachable by an unprivileged single client: craft and submit one transaction containing an `ExtendLookupTable` instruction against the `AddressLookupTable` program with 4 accounts, where accounts[2]/accounts[3] are arbitrary unrelated pubkeys, then call `getTransaction` with `jsonParsed` encoding once. No special privileges, staking, or repeated high-rate calls are required — a single submitted transaction (even if it fails at runtime) and a single RPC call reproduce the mislabeling.

### Recommendation
In the `ExtendLookupTable` branch, only populate `payerAccount`/`systemProgram` when there is actual evidence those roles are present — e.g., require exactly 4 accounts (not merely `>= 4`) AND verify `account_keys[instruction.accounts[3]] == solana_sdk_ids::system_program::id()` before inserting the fields; otherwise omit them or return a parse error/fallback to raw (unparsed) instruction display, consistent with how other parsers in this crate validate role identities rather than relying solely on position/count.

### Proof of Concept
```rust
// transaction-status/src/parse_address_lookup_table.rs (add to `mod test`)
#[test]
fn test_extend_lookup_table_mislabels_arbitrary_accounts() {
    use solana_message::compiled_instruction::CompiledInstruction;

    let lookup_table_pubkey = Pubkey::new_unique();
    let authority = Pubkey::new_unique();
    let attacker_key2 = Pubkey::new_unique(); // unrelated to payer role
    let attacker_key3 = Pubkey::new_unique(); // NOT the system program id

    let account_keys_vec = vec![lookup_table_pubkey, authority, attacker_key2, attacker_key3];
    let account_keys = AccountKeys::new(&account_keys_vec, None);

    let data = bincode::serialize(&ProgramInstruction::ExtendLookupTable {
        new_addresses: vec![],
    })
    .unwrap();

    let instruction = CompiledInstruction {
        program_id_index: 4, // arbitrary, not checked in this unit
        accounts: vec![0, 1, 2, 3],
        data,
    };

    let parsed = parse_address_lookup_table(&instruction, &account_keys).unwrap();

    // BUG: systemProgram is reported even though attacker_key3 != system_program::id()
    assert_ne!(attacker_key3, system_program::id());
    assert_eq!(
        parsed.info["systemProgram"],
        json!(attacker_key3.to_string())
    ); // demonstrates misreporting: parser labels a non-system-program key as "systemProgram"
    assert_eq!(
        parsed.info["payerAccount"],
        json!(attacker_key2.to_string())
    );
}
```
This test demonstrates that `parse_address_lookup_table` reports `systemProgram`/`payerAccount` for the 4th/3rd accounts without verifying `attacker_key3 == system_program::id()`, confirming the count-based mislabeling described in the finding.
