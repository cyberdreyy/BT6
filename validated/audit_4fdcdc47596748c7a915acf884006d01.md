### Title
Programmable-borrower vault losses are truncated to zero instead of being applied to tranche NAV - (File: `contracts/IdleCDOEpochVariant.sol`)

### Summary
`IdleCDOEpochVariant._resolveStopEpochInterest` consumes only `ProgrammableBorrower.totalInterestDueNow()`. That function nets vault losses against borrower and buffer yield, but saturates at zero and does not expose the uncovered negative remainder to the CDO. Consequently, a successful programmable-borrower `stopEpoch` can crystallize zero yield while leaving tranche NAV and strategy-token balances at par even though the ERC4626 sleeve has already suffered a larger realized loss.

### Finding Description
The external bug class is a reported failure condition being ignored at the point where the result is consumed. The analogous behavior is in the programmable-borrower stop flow:

- `ProgrammableBorrower._vaultNetInterest` calculates a signed vault delta and returns either `interest` or `loss`.
- `totalInterestDueNow` subtracts the loss from borrower interest and buffer interest, but returns zero whenever the loss is larger.
- `IdleCDOEpochVariant._resolveStopEpochInterest` returns that saturated value as the epoch result.
- `_stopEpoch` has no compensating call to `vaultLoss()` and only burns active basis when the manager supplies `_lossAmount` through `stopEpochWithDuration`; ordinary `stopEpoch` always passes zero.
- On the success path, `_updateAccounting`, minted-interest accounting, reopening of deposits, and reopening of withdrawal requests proceed using the unimpaired saved NAV.

Relevant code: `ProgrammableBorrower.totalInterestDueNow` clamps negative net performance at zero [1](#0-0) , while `_vaultNetInterest` correctly computes the signed loss [2](#0-1) . The CDO consumes only the nonnegative interest result [3](#0-2)  and the normal stop path supplies no separate active-loss amount [4](#0-3) .

### Impact Explanation
This breaks the loss-waterfall and fair-withdrawal invariants.

Assume:

- active pool principal: `1,000`
- borrower contractual interest plus positive buffer yield: `20`
- ERC4626 vault loss: `50`

`totalInterestDueNow()` returns `0`, not an explicit loss of `30`. The CDO records no epoch interest and completes the stop successfully. Because no `_lossAmount` is supplied and no other path burns strategy tokens, active tranche NAV remains based on the original `1,000` principal rather than the economically correct `970`.

Withdrawal requests made after the reopened buffer are therefore priced against unimpaired tranche prices. Earlier or faster claimants can receive par value while the shortfall remains with later LPs. If the vault loss is permanent, the final claimants bear an outsized loss or the pool becomes unable to honor all receipts. This is not a third-party price-report issue: the programmable borrower itself computes the loss in `_vaultNetInterest`, but the CDO interface collapses that signal into a zero-interest result.

### Likelihood Explanation
The bug requires programmable-borrower mode and a negative ERC4626 delta larger than the sum of borrower interest and buffer interest during an epoch or carried buffer period. That state can arise from a realized vault loss, withdrawal penalty, bad-debt accounting, or another ERC4626-native decrease in `convertToAssets`.

An unprivileged user of the programmable borrower’s ERC4626 vault can initiate the sequence where the vault exposes that loss. The CDO owner or manager then executes the normal `stopEpoch` call. No privileged malicious behavior, borrower default, or forged external oracle data is required; the vulnerable part is that the protocol treats a net-negative vault result as equivalent to zero yield.

The issue is easier to trigger when borrower APR or epoch duration is low, because even a modest vault loss can exceed total borrower interest.

### Recommendation
Do not collapse vault principal impairment into the nonnegative interest return value.

- Extend the programmable-borrower interface so `stopEpoch` receives both `totalInterestDueNow()` and an explicit uncovered `vaultLoss()` amount.
- In `IdleCDOEpochVariant._stopEpoch`, route the uncovered loss through `previewLossAdjustedWithdrawFunds`, reduce funded pending receipts where applicable, and burn the active-side strategy-token loss through the existing `burnStrategyTokens` and `_forceUpdateAccounting` path.
- Ensure the loss path preserves the intended invariant: pending receipts share only the pending portion pro rata, while the remaining loss follows the ordinary BB-first waterfall.
- Add regression coverage for `vaultLoss > borrowerInterest + bufferInterest`, including both a normal stop and a stop with pending withdrawal receipts.

### Proof of Concept
A Foundry PoC should reuse the existing programmable-borrower vault setup and force a real ERC4626 asset loss before manager stop:

```solidity
function testStopEpochIgnoresUncoveredVaultLoss() public {
    uint256 principal = 1_000e18;
    uint256 borrowerInterest = 20e18;
    uint256 vaultLoss = 50e18;

    // Existing test helpers/configuration:
    // - enable programmable borrower mode
    // - enable minted interest
    // - deposit AA/BB principal
    // - start epoch so ProgrammableBorrower deposits into the ERC4626 vault
    depositAA(principal / 2);
    depositBB(principal / 2);
    startEpoch();

    // Create a real ERC4626 loss of 50 while borrower interest due is only 20.
    // The exact call is vault-specific; on a fork it should use the vault's
    // unprivileged loss-realization path, not storage manipulation.
    realizeErc4626Loss(vault, vaultLoss);

    assertEq(programmableBorrower.vaultLoss(), vaultLoss);
    assertEq(programmableBorrower.totalInterestDueNow(), 0);

    uint256 navBefore = cdo.getContractValue();

    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(manager);
    cdo.stopEpoch(0, 0);

    // Vulnerable behavior: stop succeeds, but no strategy-token loss was burned.
    assertEq(cdo.getContractValue(), navBefore);
    assertEq(cdo.lastEpochInterest(), 0);
    assertFalse(cdo.defaulted());

    // Economically expected NAV is principal + borrowerInterest - vaultLoss.
    // The reported NAV remains above the real recoverable vault value.
    assertGt(cdo.getContractValue(), principal + borrowerInterest - vaultLoss);
}
```

The decisive assertions are that `vaultLoss()` reports the full `50e18`, `totalInterestDueNow()` reports only `0`, and the successful CDO stop leaves NAV unchanged instead of crystallizing the uncovered `30e18` loss.
