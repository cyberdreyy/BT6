### Title
Identity conflation between real users and External Initiators via shared SessionUserKey allows EI credentials to bypass the "EIs not allowed" restriction on int-ID job runs and defeats audit attribution - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates integer-ID job-run execution on `isUser` from `auth.GetAuthenticatedUser`, which only checks for the presence of `SessionUserKey` in the gin context. Because `AuthenticateExternalInitiator` sets that exact same key with a synthetic `clsessions.User{Role: clsessions.UserRoleRun}`, an External Initiator credential is treated identically to a real authenticated user, defeating the code's own comment/intent that "EIs not allowed" to trigger int-ID job runs, and leaving no way to distinguish the two principal types for audit/incident-response purposes.

### Finding Description
`auth.AuthenticateBySession` and `auth.AuthenticateByToken` populate `c.Set(SessionUserKey, &user)` with the real DB-backed user record (real email, real role) [1](#0-0) [2](#0-1) . `auth.AuthenticateExternalInitiator`, used to authenticate External Initiator (EI) credentials, sets the very same key with a synthetic placeholder user that has no email and a fixed `UserRoleRun`: `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` [3](#0-2) .

`auth.GetAuthenticatedUser` only checks for the presence of that key and a successful type assertion — it cannot and does not distinguish a synthetic EI-derived user from a genuine session/token-authenticated user [4](#0-3) .

In `PipelineRunsController.Create`, the code explicitly relies on this boolean to restrict int-ID job-run triggering to real users only: `_, isUser := auth.GetAuthenticatedUser(c) // only users are allowed to run jobs using int IDs - EIs not allowed` [5](#0-4) . Since an EI-authenticated request also produces `isUser == true` (with the synthetic role-`Run` user), an EI can execute the `isUser` branch and call `prc.App.RunJobV2(ctx, jobID, nil)` for any integer job ID, contradicting the code's own stated intent that EIs are restricted from this path.

Additionally, `Create` never calls `prc.App.GetAuditLogger().Audit(...)` at all (unlike `Resume`, which logs `audit.UnauthedRunResumed`) [6](#0-5) , so there is no audit trail recording which principal type (real user vs. EI) triggered a given run in the first place — the identity conflation compounds an existing absence of attribution logging for this endpoint.

I confirmed via `grep_search` that `core/web/pipeline_runs_controller_test.go` contains no test that exercises this endpoint under EI credentials or asserts anything about audit-log attribution for `Create`; existing tests only cover session/token-authenticated flows [7](#0-6) , confirming the premise that no test enforces distinguishability of these identity classes downstream.

### Impact Explanation
This maps to Chainlink's "unauthorized job run" / authorization-bypass impact class: a restricted, lower-privilege EI credential — intended only to trigger webhook-type job runs (a job type that has since been removed) — can, due to identity conflation, trigger arbitrary jobs by integer ID through the same code path as a genuine authenticated user. Combined with the complete absence of `audit.Audit` calls in `Create`, there is no way to determine after the fact whether a run was triggered by a real user or an EI credential, which masks caller attribution and enables repudiation during incident response.

### Likelihood Explanation
The only precondition is possession of valid EI credentials (`ExternalInitiatorAccessKeyHeader`/`ExternalInitiatorSecretHeader`), which is one of the explicitly in-scope unprivileged attacker classes. If the router wires `PipelineRunsController.Create` behind an EI-authenticated route group (as it does for legacy webhook-triggered runs), the bypass is trivially and repeatably reachable by sending `POST /v2/jobs/:ID/runs` with an integer job ID and valid EI headers.

### Recommendation
Make identity class explicit and unambiguous rather than inferring it from key presence alone:
- Do not store the synthetic EI user under `SessionUserKey`; introduce a distinct context key/type (e.g., `SessionExternalInitiatorUserKey`) or wrap the value in a type that carries provenance (`Real` vs `ExternalInitiator`).
- In `PipelineRunsController.Create`, explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (or route differently) if present, instead of relying solely on `isUser`.
- Add `audit.Audit(...)` calls in `Create` recording the resolved principal type and identifier (user email or EI name) for every triggered run, matching the pattern used in `Resume`.

### Proof of Concept
Handler-level integration test plan (Go, in `core/web/pipeline_runs_controller_test.go`):
1. `TestPipelineRunsController_Create_ExternalInitiatorCanTriggerIntIDRun`: register an EI via `AuthenticationProvider().CreateExternalInitiator` (or test helper), create a non-webhook job with an int ID, send `POST /v2/jobs/{intID}/runs` using an HTTP client configured with EI headers instead of session/token, and assert the response is `200 OK` with a created pipeline run — demonstrating the "EIs not allowed" comment is not enforced.
2. `TestPipelineRunsController_Create_AuditAttribution`: trigger the same endpoint once with a real user session and once with EI credentials, then assert on `prc.App.GetAuditLogger()` (using a mock/spy audit logger) that two distinct, attributable audit entries were recorded with different principal identifiers — this assertion should currently fail since `Create` performs no `audit.Audit` call at all.

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
