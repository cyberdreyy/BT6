### Title
Rejecting then accepting a block lets a single signer's weight be double-counted toward both the reject and accept thresholds - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side signature/rejection tally in `StackerDBListener` (the node-side "coordinator" component explicitly in scope) uses two different, inconsistent guards to decide whether a signer's weight has already been counted: the `Accepted` branch checks `block.gathered_signatures.contains_key(&slot_id)`, while the `Rejected` branch checks `block.responded_signers.insert(slot_id)`. Because these are two different sets, a signer that first rejects a block (adding its weight to `total_weight_rejected` and inserting into `responded_signers`) and later accepts the *same* block (`signer_signature_hash`) will also have its weight added to `total_weight_approved`, since `gathered_signatures` was never touched by the reject path. The signer's weight is now counted on both sides of the 70%/30% threshold equality simultaneously.

### Finding Description
`BlockStatus` tracks two independent weight accumulators and two membership sets: [1](#0-0) 

On `Accepted`, the weight-add guard is `!block.gathered_signatures.contains_key(&slot_id)`: [2](#0-1) 

On `Rejected`, the weight-add guard is `block.responded_signers.insert(slot_id)` (true only the first time this slot is seen at all): [3](#0-2) 

Sequence that breaks the accounting:
1. Signer `S` (slot `k`) sends `BlockResponse::Rejected` for signer_signature_hash `H`. `responded_signers.insert(k)` succeeds → `total_weight_rejected += w_k`. `gathered_signatures` is untouched.
2. The protocol legitimately allows a signer to revisit a verdict for the same block later (re-proposal, `should_reevaluate_block`/`should_reevaluate_reject_reason`, or a corrected validation outcome causing the signer to flip from `LocallyRejected` to `LocallyAccepted`), per `docs/signer-flows.md` section 3/6.
3. Signer `S` later sends `BlockResponse::Accepted` for the same `H`. The check `!block.gathered_signatures.contains_key(&k)` is `true` (nothing was ever inserted there), so `total_weight_approved += w_k` as well.

Result: `w_k` is now counted in *both* `total_weight_approved` and `total_weight_rejected` for the same block. This breaks the intended equality that "aggregated weight" tracked by the coordinator must equal the weight of genuinely-held, mutually exclusive current verdicts from *verified, distinct* signers. It does not require a majority of signers or another signer's key — a single honest-but-flip-flopping signer (a legitimate protocol path) or gossip replay of stale then fresh messages from one signer over StackerDB is enough to trigger it.

### Impact Explanation
This directly targets the "aggregated-weight vs verified-accepts" equality called out as an in-scope Critical class. Concretely:
- `total_weight_rejected` can cross the blocking-minority threshold (`> total_weight - weight_threshold`) using weight that is simultaneously also being applied toward `total_weight_approved`, and vice versa — the two mutually exclusive verdict tallies are no longer partitions of the same signer set.
- In the "both signal near-simultaneously" case, the coordinator (`signer_coordinator.rs`) can observe `total_weight_approved >= self.weight_threshold` and hand back `gathered_signatures` as sufficient for a valid block even though the *distinct* accepting weight is actually lower than required once the double-counted portion is discounted — i.e., the miner can be led to believe a block reached 70% approval when the real amount of accepting weight (excluding a signer who has also filed a rejection) is lower.
- Conversely, it can also cause a legitimately-approved block to be treated as globally rejected via inflated `total_weight_rejected`, which is a liveness/safety-adjacent break in the accept/reject equality the whole pre-commit/threshold design depends on (see `docs/signer-flows.md` section 6, "Rejections tally toward the blocking minority... Acceptances tally toward the 70% threshold").

### Likelihood Explanation
Reachable by a single signer or by benign message reordering/gossip replay over StackerDB — no majority of signers, no other signer's key, and no auth_token/local access is required. The re-evaluate-after-reject path is a first-class, documented flow (`should_reevaluate_reject_reason`, pre-commit re-send after re-proposal), so the Reject→Accept sequence for the same `signer_signature_hash` is an ordinary occurrence, not an exotic edge case.

### Recommendation
Use a single, shared "already counted" gate for a given `(block, slot_id)` pair across both branches — e.g., gate both the `Accepted` and `Rejected` weight additions on `block.responded_signers.insert(slot_id)`, and when a signer flips its vote for the same block, first back out (or refuse to re-add) the previous side's weight before applying the new one, rather than allowing both `total_weight_approved` and `total_weight_rejected` to include the same signer's weight concurrently.

### Proof of Concept
1. Configure `N` signers with `signer_entries` weights such that no single signer's weight alone crosses `weight_threshold`, but the sum of one signer's weight plus other genuine votes does.
2. Have the miner submit a block proposal; signer `S` (slot `k`, weight `w_k`) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `signer_signature_hash = H`. Confirm via logs that `total_weight_rejected` increases by `w_k` and `responded_signers` contains `k`.
3. Trigger the block's re-proposal path (or have signer `S`'s local re-evaluation flip to accept, e.g., after the pending validation completes favorably) so that `S` now emits `SignerMessage::BlockResponse(BlockResponse::Accepted(...))` for the same `H`.
4. Observe in `stackerdb_listener.rs`'s handling that `block.gathered_signatures.contains_key(&k)` is `false` (never set by the reject branch), so `total_weight_approved` is incremented by `w_k` as well — confirm via the same debug logs that both `total_weight_approved` and `total_weight_rejected` now include `w_k` for block `H` simultaneously, violating the intended mutually-exclusive tally invariant.
