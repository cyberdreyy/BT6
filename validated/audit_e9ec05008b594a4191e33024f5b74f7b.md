### Title
`getRecentPrioritizationFees` performs an unbounded nested scan over the prioritization-fee cache for every requested account - (File: `runtime/src/prioritization_fee_cache.rs`)

### Summary
The `BatchRequests.sendWithdrawalRequests` finding is about an externally-triggerable unbounded loop whose cost scales with an attacker-influenced/administrator-controlled list, risking a gas/compute DoS. The closest reachable analog in agave is `PrioritizationFeeCache::get_prioritization_fees`, invoked by the unprivileged JSON-RPC method `getRecentPrioritizationFees`, which nests a loop over up to `MAX_TX_ACCOUNT_LOCKS` (64) attacker-supplied pubkeys inside a loop over every cached block (up to 150), performing a linear/hash lookup for each combination on every call.

### Finding Description
The RPC handler `FullImpl::get_recent_prioritization_fees` in `rpc/src/rpc.rs` only bounds the number of input pubkeys to `MAX_TX_ACCOUNT_LOCKS` [1](#0-0) , then calls `JsonRpcRequestProcessor::get_recent_prioritization_fees`, which forwards straight to `prioritization_fee_cache.get_prioritization_fees(&pubkeys)` [2](#0-1) .

`PrioritizationFeeCache::get_prioritization_fees` iterates over every entry in the in-memory cache (`BTreeMap<Slot, PrioritizationFee>`, holding up to ~150 finalized blocks worth of fee data), and for each cached slot it iterates over every pubkey in the caller-supplied list, doing a lookup via `get_writable_account_fee` for each: [3](#0-2) . This is an O(cached_blocks × requested_pubkeys) operation performed synchronously in the RPC request path, unlike other similarly-shaped RPC endpoints (`getMultipleAccounts`, `getInflationReward`, `getBlocks`) which explicitly cap either the total work or delegate to bounded/indexed lookups.

### Impact Explanation
A single unprivileged JSON-RPC caller can repeatedly request `getRecentPrioritizationFees` with the maximum 64 pubkeys, forcing the node to perform up to 150 × 64 = 9,600 map lookups per call, and can issue this call at arbitrary rate (unlike the excluded getProgramAccounts DoS pattern which requires unfiltered scans). While each individual call's cost is small in absolute terms, this matches the reported bug class: a per-request unbounded nested nested loop scaling with a caller-controlled list size that is not amortized or rate-limited beyond the flat count check, and it runs on the same thread handling other RPC/administrative work. This is a low-severity finding, comparable to the original "Medium/acknowledged" severity of the referenced report, since the actual per-call cost is bounded and small relative to block-processing budgets, and the maintainer's own precedent (M-13 in the referenced report) was ultimately "acknowledged" with no change (i.e., accepted risk), suggesting minimal marginal impact here as well.

### Likelihood Explanation
High likelihood of reachability: `getRecentPrioritizationFees` is a standard unprivileged RPC method with no additional authentication, and the account list length check is the only guard. Any RPC-exposed validator node accepts this call.

### Recommendation
Bound the total work of `get_prioritization_fees` independent of input list size (e.g., cap combined iterations, or restructure the cache to allow O(1) per-account lookups per slot instead of a linear scan through `get_writable_account_fee`), and consider tightening `MAX_TX_ACCOUNT_LOCKS` specifically for this endpoint if it is larger than necessary for typical use.

### Proof of Concept
1. Connect to a public/unauthenticated JSON-RPC endpoint of an agave validator that serves the Full RPC API.
2. Issue repeated `getRecentPrioritizationFees` requests with 64 (the `MAX_TX_ACCOUNT_LOCKS` limit) distinct pubkeys in the parameter array.
3. Each call causes `PrioritizationFeeCache::get_prioritization_fees` [3](#0-2)  to perform up to `cache_max_size` (default up to 150) × 64 lookups.
4. Repeat the call at high frequency to accumulate CPU load on the RPC-serving thread pool.

Note: this is a low-impact, low-severity finding relative to the report's Medium classification — I flag it as the closest reachable analog found, but confidence in materially significant impact is limited given the small absolute bound (150×64 lookups) and the precedent that the original report itself was only "acknowledged" without a code fix.

    pub fn get_prioritization_fees(&self, account_keys: &[Pubkey]) -> Vec<(Slot, u64)> {
        self.cache
            .read()
            .unwrap()
            .iter()
            .map(|(slot, slot_prioritization_fee)| {
                let mut fee = slot_prioritization_fee
                    .get_min_compute_unit_price()
                    .unwrap_or_default();
                for account_key in account_keys {
                    if let Some(account_fee) =
                        slot_prioritization_fee.get_writable_account_fee(account_key)
                    {
                        fee = std::cmp::max(fee, account_fee);
                    }
                }
                (*slot, fee)
            })
            .collect()
    }
