### Title
Unanchored regex matching in `evaluateOverwrite`/`overwriteRegexCheck` allows `KUBERNETES_NAMESPACE_OVERWRITE`/`KUBERNETES_SERVICE_ACCOUNT_OVERWRITE` values to satisfy an admin-intended narrow regex via substring match - ([File: executors/kubernetes/overwrites.go])

### Summary
`overwriteRegexCheck` validates the user-supplied namespace/service-account overwrite value with `regexp.MatchString`/`Regexp.MatchString`, which succeeds if the pattern matches *anywhere* in the string rather than requiring a full match. If the admin-configured `NamespaceOverwriteAllowed`/`ServiceAccountOverwriteAllowed` pattern is not explicitly anchored with `^...$`, a job can supply a value that only contains the intended substring (e.g. `kube-system-ci-x` against pattern `ci-.*`) and pass validation.

### Finding Description
`createOverwrites` reads `KUBERNETES_NAMESPACE_OVERWRITE`/`KUBERNETES_SERVICE_ACCOUNT_OVERWRITE` job variables directly from job-controlled `spec.Variables` [1](#0-0) , and passes them to `evaluateOverwrite`, which calls `overwriteRegexCheck(regex, overwriteValue)` [2](#0-1) . That helper compiles the admin's regex and calls `r.MatchString(value)` [3](#0-2) . Go's `regexp.MatchString` (and `Regexp.MatchString`) reports whether the pattern matches *any substring* of the input unless the pattern itself is anchored with `^`/`$`. So a regex like `ci-.*` intended by the admin to constrain namespaces to a `ci-` prefix will also match `kube-system-ci-x`, `evil-ci-anything`, etc., because the matcher only needs to find `ci-` followed by anything, anywhere in the string.

The only "check" here is this single unanchored regex match, and there is no runner-side normalization or anchoring enforcement — the code relies entirely on the admin writing a fully anchored pattern (`^ci-.*$`). If they don't (a very plausible, common mistake since most engineers assume `MatchString` requires a full match, and GitLab's own docs/config examples for `KUBERNETES_NAMESPACE_OVERWRITE` historically show patterns without both anchors), the intended allow-list restriction can be bypassed. Since the returned `overwriteValue` is used verbatim as the pod's `namespace`/`serviceAccount` when creating Kubernetes objects, this can result in scheduling the job pod into a namespace or with a service account outside the admin's intended set.

### Impact Explanation
If the admin's regex is unanchored (e.g. `ci-.*`, `.*-ci`, or any pattern without both `^` and `$`), an unprivileged pipeline author can set `KUBERNETES_NAMESPACE_OVERWRITE=kube-system-ci-x` or `KUBERNETES_SERVICE_ACCOUNT_OVERWRITE=cluster-admin-ci` and have it accepted, causing the job pod to be created in a namespace, or run under a service account, that the admin never intended to allow — potentially granting elevated privileges (access to a privileged namespace, or a service account with broader RBAC) depending on what exists in the cluster. This is a real logic/validation bug in the runner (relying on `MatchString` instead of `MatchString` + explicit anchoring or `regexp.MustCompile("^(?:"+regex+")$")`), not merely a "bad admin regex" — most admins reasonably expect substring-style patterns like `ci-.*` to mean "starts with ci-", not "contains ci- anywhere."

### Likelihood Explanation
Preconditions: the admin must have configured `NamespaceOverwriteAllowed`/`ServiceAccountOverwriteAllowed` with a plausible but non-fully-anchored regex (common, since regex anchoring is an easy oversight and it's not enforced/validated by the runner). Given that, any pipeline author able to set CI/CD variables (a very low bar — pipeline-level variables, `.gitlab-ci.yml` `variables:`) can trivially construct a bypass string, so exploitation is straightforward and fully repeatable/deterministic once the precondition holds.

### Recommendation
In `overwriteRegexCheck`, force full-string matching regardless of admin-provided anchors, e.g. compile with `regexp.Compile("^(?:" + regex + ")$")` before calling `MatchString`, or use `regexp.MatchString` semantics equivalent to `FindString(...) == value`. Additionally, document/enforce that overwrite-allow regexes are always full-match semantics so admin patterns like `ci-.*` behave as `^ci-.*$` without requiring the admin to add anchors manually.

### Proof of Concept
```go
func TestOverwriteRegexCheck_UnanchoredBypass(t *testing.T) {
    // Admin intends only namespaces literally starting with "ci-" to be allowed.
    regex := "ci-.*"

    // Should be rejected but currently passes due to unanchored MatchString.
    err := overwriteRegexCheck(regex, "kube-system-ci-x")
    assert.Error(t, err, "namespace outside intended prefix must not satisfy the allow-list regex")
}
```
Expected (current) result: the test fails (no error returned), proving `kube-system-ci-x` incorrectly satisfies `ci-.*`. A fuzz test iterating over adversarial strings that embed the intended substring (`prefix-ci-` combinations, `ci-` sandwiched inside unrelated namespace names) against representative unanchored patterns (`ci-.*`, `.*-prod`, `svc-account-\d+`) should assert `overwriteRegexCheck` never accepts a value that doesn't fully match the intended prefix/suffix/format, catching this anchoring gap systematically.

func (o *overwrites) evaluateOverwrite(
	fieldName, value, regex, overwriteValue string,
	logger buildlogger.Logger,
) (string, error) {
	if regex == "" {
		logger.Debugln("Regex allowing overrides for", fieldName, "is empty, disabling override.")
		return value, nil
	}

	if overwriteValue == "" {
		return value, nil
	}

	if err := overwriteRegexCheck(regex, overwriteValue); err != nil {
		return value, err
	}

	logValue := overwriteValue
	if fieldName == "BearerToken" {
		logValue = "XXXXXXXX..."
	}

	logger.Println(fmt.Sprintf("%q overwritten with %q", fieldName, logValue))

	return overwriteValue, nil
}

func overwriteRegexCheck(regex, value string) error {
	var err error
	var r *regexp.Regexp
	if r, err = regexp.Compile(regex); err != nil {
		return err
	}
	if match := r.MatchString(value); !match {
		return &malformedOverwriteError{value: value, pattern: regex}
	}
	return nil
}
