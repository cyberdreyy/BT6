### Title
Post-default instant withdraw requests merge into the finalized default-epoch claim basis and are paid from the recovery reserve at `defaultRecoveryPrice`, enabling reserve drain and >1 recovery theft - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2015-8550 is a double-fetch: a value is read once for accounting and read again later after it has been silently mutated. `IdleCreditVault` has an exact analog: `finalizeDefaultRecovery` snapshots the default-epoch instant-claim basis (`instantWithdrawClaimsByEpoch[epochNumber]`) and sizes `defaultRecoveryReserve` on it, but `requestInstantWithdraw` keeps writing new receipts into that *same* epoch slot (`instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` / `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]`) because `epochNumber` never advances after default. Claims then re-read the mutated slot and pay out of the fixed reserve — basis fetched twice, mutated between fetch and payout.

### Finding Description
`requestWithdraw` explicitly handles the post-default regime: after `defaultRecoveryFinalized`, it burns/mints receipt tokens and records a segregated `postDefaultRequests` entry that is paid 1:1 and explicitly separated from the defaulted-epoch haircut path (`IdleCreditVault.sol:247-257`, `_claimPostDefaultWithdrawRequest` at `:760-767`).

`requestInstantWithdraw` has no such guard (`:356-375`). It unconditionally:

```solidity
uint256 currentEpoch = epochNumber;              // still == defaultRecoveryEpoch after default
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

After default finalization, `epochNumber` equals `defaultRecoveryEpoch` forever (it only increments in `deposit()` when `isEpochRunning()`, `:607-614`, which no longer runs). So a post-finalization instant request is written into the exact storage slot that `finalizeDefaultRecovery` already accounted for:

- basis snapshot: `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` when `pendingInstantWithdraws != 0` (`:644-649`), and `defaultRecoveryPrice = reserveAmount * 1e18 / totalBasis` is frozen on that basis (`:679-693`).
- payout re-fetch: `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — which now includes the post-finalization request — burns it and pays `claimBasis * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve` (`:842-856`).

The reserve was sized for the pre-finalization basis only; each new request adds claimable basis without adding a single wei of reserve. Two consequences:

1. If `recoveryPrice > 1e18` (explicitly allowed: "Recovery can be above par", `:687`), an attacker who opens an instant request after finalization is paid *more* than they deposited — e.g. price 1.5e18 turns a 100 USDC request into a 150 USDC payout, stealing excess reserve belonging to pre-default claimants.
2. Regardless of price, every post-default instant claim consumes reserve that honest defaulted-epoch claimants were promised; once the reserve is exhausted, `_transferDefaultRecovery` underflows on `defaultRecoveryReserve -= _amount` (`:912-917`) and all remaining recovery claims permanently revert.

The asymmetry is unambiguous: the normal-withdraw path was deliberately rerouted into `postDefaultRequests` "so they must not fall through to the defaulted-epoch receipt logic" (`:304-305`), while the instant path was left writing into the finalized epoch bucket.

### Impact Explanation
Direct theft and permanent freezing of unclaimed recovery. With `defaultRecoveryPrice > 1e18` (possible whenever recovered funds exceed the computed basis, e.g. a write-off escrow payout plus prefunded instant reserve), an unprivileged user — anyone who can route a withdraw through the CDO's instant-withdraw flow — receives `amount * price` for a deposit of `amount`, extracting surplus recovery assets that belong to defaulted-epoch claimants. With `price <= 1e18`, the same flow lets an attacker burn a small amount to inflate the epoch basis and cause all subsequent legitimate recovery claims to revert on reserve underflow, permanently freezing unclaimed recovery funds (which satisfies "permanent freezing of unclaimed yield"). Loss is quantified: total extractable value = `defaultRecoveryReserve` minus the sum of legitimate remaining claims, or full freeze of the remaining reserve.

### Likelihood Explanation
Requires a borrower default followed by `finalizeDefaultRecovery` — a state the codebase explicitly supports and tests — and that the CDO's instant-withdraw path (`requestInstantWithdraw`, called only by `idleCDO` via `_onlyIdleCDO`) remains reachable post-default. No privileged role needs to be malicious; the sequencing is entirely driven by an unprivileged user's withdraw transaction after finalization. The missing `defaultRecoveryFinalized` branch in `requestInstantWithdraw` (present in its sibling `requestWithdraw`) makes the exploit path deterministic whenever it is reachable. Note: the trigger requires that `IdleCDOEpochVariant`'s post-default withdraw flow still dispatches instant requests to the strategy; if the CDO blocks instant withdrawals entirely after `defaulted()`, the bug is unreachable — this is the one element I could not fully confirm within the strategy file alone.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert or route the request into a segregated `postDefaultRequests`-style bucket paid 1:1, and never write to `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` or `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` after finalization. Additionally, `claimInstantWithdrawRequest` should reject receipts whose per-epoch basis was recorded after `defaultRecoveryEpoch`.

### Proof of Concept
Foundry fork PoC sketch (test/foundry style, against an existing `IdleCreditVault` instance):

```solidity
function test_postDefaultInstantWithdrawDrainsRecovery() public {
    // 1. Epoch running; LP deposits via CDO -> strategy tokens minted.
    // 2. Borrower defaults; owner/guardian triggers default and calls
    //    IdleCDOEpochVariant.finalizeDefaultRecovery, which invokes
    //    vault.finalizeDefaultRecovery(recovered, source).
    //    Assert: vault.defaultRecoveryFinalized() == true,
    //    vault.defaultRecoveryEpoch() == vault.epochNumber(),
    //    recoveryPrice = vault.defaultRecoveryPrice() (> 1e18 for the theft case).
    uint256 reserveBefore = vault.defaultRecoveryReserve();

    // 3. Attacker (unprivileged user) performs an instant withdraw through the CDO.
    //    CDO calls vault.requestInstantWithdraw(amount, attacker).
    uint256 epochSlot = vault.defaultRecoveryEpoch();
    //    BUG: requestInstantWithdraw writes into the finalized epoch slot:
    assertEq(vault.instantWithdrawsRequestsByEpoch(attacker, epochSlot), amount);
    //    instantWithdrawClaimsByEpoch[epochSlot] grew AFTER finalization.

    // 4. Attacker claims: claimInstantWithdrawRequest -> _claimDefaultedInstantWithdrawRequest
    //    pays amount * defaultRecoveryPrice / 1e18 from defaultRecoveryReserve.
    uint256 balBefore = token.balanceOf(attacker);
    cdo.claimInstantWithdraw(attacker); // routes to vault.claimInstantWithdrawRequest
    uint256 gained = token.balanceOf(attacker) - balBefore;

    // Theft case (price > 1): gained > amount — attacker extracted surplus recovery.
    assertGt(gained, amount);
    assertEq(vault.defaultRecoveryReserve(), reserveBefore - gained);

    // Freeze case (price <= 1): repeat attacker requests until reserve is consumed
    // by inflated basis; an honest defaulted-epoch claimant then reverts:
    vm.expectRevert();
    vault.claimInstantWithdrawRequest(honestUser); // _transferDefaultRecovery underflows
}
```

The invariant broken is "one receipt one payout against a fixed recovery reserve": the epoch-keyed basis is snapshotted at finalization and re-read at claim, while `requestInstantWithdraw` continues mutating that same basis — a classic double-fetch over shared accounting state.

One caveat: full exploitability depends on `IdleCDOEpochVariant` still routing instant withdrawals to `requestInstantWithdraw` after `defaulted()`; that CDO-side dispatch was not fully verified here and should be confirmed during PoC development (if it reverts, the issue downgrades to a latent accounting hazard still worth fixing given the documented `requestWithdraw` asymmetry).
