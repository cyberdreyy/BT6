### Title
Negative `interestForOverUnderPerformance` is clamped to zero at `startEpoch`, inflating `expectedEpochInterest` and pulling excess funds from the borrower into tranche NAV - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
Analogous to the Elfi bug where a `> 0` guard on `amount`/`unsettledAmount` caused the pool value to skip a negative component (`lossAmount`/short uPnL), `startEpoch()` computes `adjustedActiveInterest = _calcInterest(getContractValue()) + interestForOverUnderPerformance` and clamps it with `if (adjustedActiveInterest < 0) adjustedActiveInterest = 0` (`contracts/IdleCDOEpochVariant.sol:260-262`). When withdraw requests push `interestForOverUnderPerformance` negative, the negative adjustment is silently dropped instead of reducing what the borrower owes, so `expectedEpochInterest` is overstated.

### Finding Description
`requestWithdraw` records each request's effect on epoch yield in the signed accumulator `interestForOverUnderPerformance` (`contracts/IdleCDOEpochVariant.sol:773-784`). Per the code comments in `writeOffDeposit` (`contracts/IdleCDOEpochVariant.sol:952-954`), `diff` is positive for AA withdrawals (overperformance owed to BB) and negative for BB withdrawals (the pool no longer owes interest on the withdrawn principal).

At `startEpoch` (`contracts/IdleCDOEpochVariant.sol:255-263`):
```solidity
int256 adjustedActiveInterest = int256(_calcInterest(getContractValue())) + interestForOverUnderPerformance;
if (adjustedActiveInterest < 0) adjustedActiveInterest = 0;
expectedEpochInterest = pendingWithdrawFees + uint256(adjustedActiveInterest);
```
If cumulative negative `diff` (from BB withdrawals during the buffer) exceeds `_calcInterest(getContractValue())`, the true net interest owed by the borrower is `pendingWithdrawFees + adjustedActiveInterest < pendingWithdrawFees`, but the clamp stores `pendingWithdrawFees + 0`. At `stopEpoch`, `_amountToPullFromBorrower = _expectedInterest` is pulled from the (honest) borrower via `getFundsFromBorrower` → `safeTransferFrom` (`contracts/IdleCDOEpochVariant.sol:376,408,550-553`), and `_strategy.deposit(netInterest)` mints strategy tokens to the CDO (`contracts/IdleCDOEpochVariant.sol:463-466`), inflating `getContractValue()` and therefore `virtualPrice`/`priceAA`/`priceBB` beyond the fair value.

### Impact Explanation
Unfair share value / direct extraction from the borrower: the borrower is debited up to `|negative adjustedActiveInterest|` more underlying than owed. That excess is credited to live NAV and split between AA/BB holders per `trancheAPRSplitRatio`. An attacker who is a KYC-passed lender can (1) hold most of the TVL, (2) place a BB withdraw request sized to make `interestForOverUnderPerformance` negative during the buffer, (3) let the epoch run and stop normally, then (4) redeem remaining tranche tokens (or the funded withdraw receipt) at the inflated price. The stolen amount is bounded by `_calcInterest(getContractValue())` of one epoch and is proportional to the attacker's share of post-stop NAV. No guard prevents it: `_skimDonatedAssets` only removes raw token balance, the honest borrower is expected to approve repayment, and the `Default` path does not trigger since NAV only increases.

### Likelihood Explanation
Requires a fixed-APR (non-programmable) vault in buffer phase with BB withdraw requests large enough that `interestForOverUnderPerformance < -_calcInterest(TVL)` — i.e., heavy BB withdrawal activity relative to remaining TVL and epoch APR. The attacker controls the timing and size of their own `requestWithdraw`, so this is reachable whenever BB holders exit before `startEpoch`. One caveat I could not fully verify in this pass: whether other flows (e.g., `depositDuringEpoch`, prior-epoch resets) reliably reset `interestForOverUnderPerformance`; it is zeroed at `startEpoch` line 263, so accumulation is per-buffer-period only.

### Recommendation
Do not clamp the signed aggregate to zero inside the expected-interest computation. Instead compute `expectedEpochInterest` as `pendingWithdrawFees` plus the true signed `adjustedActiveInterest` (flooring the *total* at 0, or tracking a negative carry so underperformance reduces `pendingWithdrawFees`/future interest), so that negative over/underperformance is accounted regardless of sign — the same fix pattern as Elfi's "add uPnL and loss regardless of amount/unsettledAmount".

### Proof of Concept
Foundry fork sketch against `IdleCDOEpochVariant` + `IdleCreditVault` (mirroring the harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Buffer phase, fixed-APR vault, APR > 0, attacker = KYC'd lender holding most TVL.
uint256 tvl = 1_000_000e6;
depositAA(attacker, tvl);           // attacker dominates AA too
// Attacker requests BB withdraw of principal P such that
// diff(BB, P) < -_calcInterest(getContractValue()): e.g. P close to whole BB NAV.
cdo.requestWithdraw(bbBalance, BBtranche);   // sets interestForOverUnderPerformance negative
// Owner starts epoch
cdo.startEpoch();
// expectedEpochInterest == pendingWithdrawFees (clamped), but fair value would be lower
uint256 expected = cdo.expectedEpochInterest();
// Borrower (honest) approves and repays
deal(underlying, borrower, expected + pendingWithdraws);
borrowerApprove(expected + pendingWithdraws);
vm.warp(cdo.epochEndDate() + 1);
cdo.stopEpoch(newApr, 0);
// Inflation check: getContractValue() grew by the clamped-out |negative diff|
// attacker claims receipt at par and redeems remaining tranche tokens at inflated price.
assertGt(cdo.getContractValue(), fairNav);
```

The assertion to encode: `stopEpoch` pulls `expected` from the borrower while the economically owed interest was `expected - X` (the discarded negative), and `virtualPrice` of the attacker's retained tranche reflects the excess `X` as NAV gain.
