### Title
Vault pause via `BaseVault.pause()` blocks all user exit paths through `MultiDepositorVault.exit()` - ([File: v3/src/core/MultiDepositorVault.sol])

### Summary
`MultiDepositorVault.exit()` is gated by `whenNotPaused`, the same OZ `Pausable` state controlled by `BaseVault.pause()`/`unpause()`. Since every user-reachable withdrawal/cancellation/refund/solve path in `ProvisionerV2` (`redeem`, `withdraw`, `refundDeposit`, `cancelRequest`, `refundRequest` for redeems, `solveRequestsVault`, and the vault-liquidity branch of async solving) ultimately calls `IMultiDepositorVault.exit()`, a pause freezes not just new deposits but also all existing withdrawal/exit flows, trapping already-deposited principal and pending redeem requests until the vault is explicitly unpaused.

### Finding Description
`BaseVault.pause()` is callable by `onlyAuthOrGuardian` and simply calls OZ's `_pause()`: [1](#0-0) 

`MultiDepositorVault.enter()` and `exit()` both carry the `whenNotPaused` modifier tied to that same pause state: [2](#0-1) 

`ProvisionerV2` funnels essentially every exit-side operation through `IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).exit(...)`:
- `refundDeposit` (allows a user/receiver to reclaim a sync deposit within the refund window) calls `exit` directly: [3](#0-2) 
- `redeem` and `withdraw` (synchronous exit paths) funnel through `_syncRedeem`, which also calls `exit`, gated only by `solvingNotPaused(token)` — a *different* pause flag from `BaseVault`'s `Pausable` state: [4](#0-3) 
- `cancelRequest` for redeem requests burns escrowed units via `exit`: [5](#0-4) 
- Async solving (`solveRequestsVault` → `_solveRequestsVault` → `_solveRedeemVaultAutoPrice`/fixed-price variants) calls `exit` to release tokens to redeemers: [6](#0-5) 

None of these ProvisionerV2-level checks (`solvingNotPaused`, `PRICE_FEE_CALCULATOR.isVaultPaused`) reference `BaseVault`'s own `Pausable` state — that check is exclusively enforced inside `MultiDepositorVault.exit()` itself. So once `BaseVault.pause()` is invoked (an ordinary, documented emergency-stop action, not a malicious/collusive act), every one of these calls unconditionally reverts with `"Pausable: paused"`, regardless of the Provisioner's independent pause/gate state. This is the same root-cause pattern as the source report: a single `whenNotPaused` guard is shared between actions that legitimately need to be frozen (new deposits/loans) and the exit/withdrawal action that documentation and design intent (as reflected even in this repo's own Balancer dependency, which explicitly states "Internal Balance can still be withdrawn, and Pools exited" while paused) expect to remain available.

### Impact Explanation
While the vault is paused, users cannot:
- Refund a sync deposit within its refund window (`refundDeposit`)
- Synchronously redeem/withdraw already-held vault units (`redeem`/`withdraw`)
- Self-cancel a pending redeem request (`cancelRequest`)
- Have their pending redeem requests solved (`solveRequestsVault` path)

This causes a temporary freeze of user-owned funds and pending redemptions (principal held as vault units or escrowed as pending requests) for the entire duration of the pause, which is undone only when an authorized address calls `unpause()`. This matches an Immunefi Medium-severity "temporary freezing of user funds" impact on funds already committed to the vault.

### Likelihood Explanation
The only precondition is a call to `BaseVault.pause()`, callable by any address holding the `guardian` role or `requiresAuth` — a normal, expected operational action (e.g., in response to a market or oracle anomaly), not an abuse of privilege or malicious collusion. Given the vault has active depositors/pending requests at the time of pause (the ordinary operating state), the freeze is triggered deterministically and unconditionally for every affected user; no attacker interaction is required.

### Recommendation
Decouple withdrawal/exit capability from the general emergency-pause state. Either:
- Remove `whenNotPaused` from `MultiDepositorVault.exit()` (keep it only on `enter()`), or
- Add a `whenPaused`-safe exit code path (mirroring the Balancer analog referenced in-repo) so that redemptions, refunds, and cancellations remain callable while new deposits/loans are frozen.

### Proof of Concept
Local Foundry fork steps:
1. Deploy `BaseVault`/`MultiDepositorVault` + `ProvisionerV2` with a whitelisted token, deposit cap set, sync deposits enabled.
2. User A calls `ProvisionerV2.deposit(token, amount, minUnitsOut, userA)` — succeeds, mints vault units to A via `MultiDepositorVault.enter`.
3. An authorized/guardian address calls `BaseVault.pause()` — succeeds (`_pause()` sets `Pausable._paused = true`).
4. User A calls `ProvisionerV2.redeem(token, unitsIn, minTokensOut, userA)`.
   - Assert: call reverts with `"Pausable: paused"` bubbled up from `MultiDepositorVault.exit()`, even though `solvingNotPaused(token)` (Provisioner-level gate) is unrelated and open.
5. Repeat with `ProvisionerV2.withdraw(...)`, `refundDeposit(...)` (within refund window), and `cancelRequest(...)` on a pending redeem request — all revert identically.
6. Assert User A's tokens/units remain locked in the vault/Provisioner until `unpause()` is called by an authorized address, demonstrating the freeze window is fully controlled by the pauser and unbounded from the ordinary user's perspective.

    function enter(address sender, IERC20 token, uint256 tokenAmount, uint256 unitsAmount, address recipient)
        external
        whenNotPaused
        onlyProvisioner
    {
        // Interactions: pull tokens from the sender
        if (tokenAmount > 0) token.safeTransferFrom(sender, address(this), tokenAmount);

        // Effects: mint units to the recipient
        _mint(recipient, unitsAmount);

        // Log the enter event
        emit Enter(sender, recipient, token, tokenAmount, unitsAmount);
    }

    /// @inheritdoc IMultiDepositorVault
    function exit(address sender, IERC20 token, uint256 tokenAmount, uint256 unitsAmount, address recipient)
        external
        whenNotPaused
        onlyProvisioner
    {
        // Effects: burn units from the sender
        _burn(sender, unitsAmount);

        // Interactions: transfer tokens to the recipient
        if (tokenAmount > 0) token.safeTransfer(recipient, tokenAmount);

        // Log the exit event
        emit Exit(sender, recipient, token, tokenAmount, unitsAmount);
    }
