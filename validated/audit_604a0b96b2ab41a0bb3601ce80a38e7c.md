### Title
Stale confirmations from removed multisig members allow request execution below the configured confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
The reported bug in `FixedPrice.sol` shows a pattern where a state value that should be re-validated at settlement time (fee eligibility) is instead trusted from an earlier, now-stale record. The same class of bug exists in the `MultiSigContract` in `multisig2/src/lib.rs`: confirmations recorded by a member are never purged from *other* pending requests when that member is removed via `delete_member`, so a stale confirmation from a no-longer-existing member is still counted toward the `num_confirmations` quorum. This breaks the binding "confirmations counted == confirmations from live members" and lets a request execute with fewer live-member approvals than the contract's configured threshold requires.

### Finding Description
`confirm()` counts confirmations purely from the `confirmations: LookupMap<RequestId, HashSet<String>>` set and compares its length against `self.num_confirmations`: [1](#0-0) 

`delete_member()` only cleans up requests and confirmations for requests that were *created by* the removed member; it does not scan other still-active requests for confirmations *cast by* that member: [2](#0-1) 

Specifically, the cleanup loop is:
```
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
```
This filters by `r.member` (the request's *creator*), not by whether `member` appears inside the `confirmations` `HashSet` of some *other* request. Consequently, if member `B` confirms a request created by member `A`, and `B` is later removed from the multisig, `B`'s confirmation entry remains in the `confirmations` set for `A`'s request. `assert_valid_request` / `confirm` never re-validate that every entry inside the confirmation set still corresponds to a `self.members.contains(...)` entry — they only validate the *current* caller (`current_member()`), not the historical confirmers already recorded.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." A request can reach the required `num_confirmations` count using a mix of live and stale (removed) member confirmations, meaning the multisig can execute a `Transfer`, `AddKey`, `DeployContract`, `AddMember`, or `DeleteMember` action with strictly fewer *live* approvals than the k-of-n policy demands. This defeats the entire security guarantee of the multisig (k independent live signers must agree) and could be used to push through unauthorized transfers or key/member changes with collusion of fewer current members than intended.

### Likelihood Explanation
Moderate: it requires that (a) a member confirms a request but the request is not yet executed, (b) that confirming member is subsequently removed via a separate `DeleteMember` action, and (c) the original request is later confirmed by enough additional live members to reach the (unchanged) `num_confirmations` count. This is a normal operational sequence (member confirms, then org rotates out a signer, then remaining members finish confirming an older pending request) rather than a contrived edge case, and multisig operators have no way to detect the stale confirmation via any exposed view method before it silently counts toward quorum.

### Recommendation
In `delete_member`, iterate over `self.requests` and, for every active request, remove the removed member's entry from its `confirmations` set (not only requests created by that member). Alternatively, when counting confirmations in `confirm()`, filter the stored `HashSet<String>` against `self.members` before comparing its length to `num_confirmations`, so removed members' historical confirmations never count.

### Proof of Concept
1. Initialize multisig with members `{A, B, C, D}` and `num_confirmations = 3`.
2. Member `A` creates request `X` (e.g., `Transfer`) via `add_request_and_confirm` → confirmations for `X` = `{A}`.
3. Member `B` calls `confirm(X)` → confirmations for `X` = `{A, B}` (2 < 3, not yet executed).
4. Members create and confirm a `DeleteMember { member: B }` request (`Y`) with 3 live confirmations → `delete_member` executes: `self.members.len() - 1 (=3) >= num_confirmations (=3)` passes; members become `{A, C, D}`. Because request `X` was created by `A`, not `B`, the cleanup loop in `delete_member` does not touch `X`'s confirmations, which remain `{A, B}`.
5. Member `C` calls `confirm(X)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → request `X` executes, even though only `A` and `C` are live members who actually approved it (2 of 3 required live approvals), with `B`'s stale, no-longer-valid confirmation making up the quorum.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
