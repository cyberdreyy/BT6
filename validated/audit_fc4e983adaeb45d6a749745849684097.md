### Title
Pending APR0 withdraw requests permanently brick `stopEpoch` once APR becomes nonzero - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The undici bug is a null-check on a value the client never requested, crashing the whole process instead of failing gracefully. The analog in the credit vault is `prepareStopEpochWithApr0`: it dereferences the invariant "APR0 principal only exists while `unscaledApr == 0`" and, when that condition doesn't hold, hard-reverts `NotAllowed()` with no fallback path — aborting the entire epoch-close instead of settling the APR0 bucket. Any KYC-passing lender can create a persistent `apr0TotalPrincipal` during an APR0 epoch; once `unscaledApr` becomes nonzero (a routine honest-manager `setAprs`/`setAprsWithBuffer` at the next epoch start), every subsequent `stopEpoch` reverts, freezing all vault funds until APR is forced back to zero, which forfeits borrower interest for that period.

### Finding Description
In `requestWithdraw`, whenever `unscaledApr == 0` and the pool is not closed, the request is routed into `_requestWithdrawApr0`, which increments `apr0TotalPrincipal` [1](#0-0) [2](#0-1) .

At epoch close, the CDO calls `prepareStopEpochWithApr0`. If `apr0TotalPrincipal != 0` it enforces:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:505-508
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

There is no alternative settlement path: `apr0TotalPrincipal` is only cleared inside `prepareStopEpochWithApr0` itself (`apr0TotalPrincipal = 0`, line 540) or via defaulted-epoch claims in `_clearWithdrawClaimForEpoch`. `unscaledApr` is set by `setAprs`/`setAprsWithBuffer`, callable any time by the honest manager or the CDO [3](#0-2) . Neither `requestWithdraw` nor `claimWithdrawRequest` prevents an APR0 request from outliving the zero-APR window — `_settleApr0` only settles after the *next* `stopEpoch`, which is exactly the call that now reverts [4](#0-3) .

Broken invariant: liveness of the epoch state machine. The "one receipt, one payout" path also degrades because funded claims remain claimable only after `stopEpoch` bumps `epochNumber` (`epochNumber <= lastWithdrawRequest[_user]` gate in `_claimFundedWithdrawRequest` [5](#0-4) ).

### Impact Explanation
Temporary freezing of all vault funds. With `stopEpoch` reverting, no withdraw request (normal, instant-funded, or APR0) matures, `epochNumber` never advances, and interest is never accounted. Recovery requires the manager to set `unscaledApr` back to 0 — i.e., run an epoch at zero borrower APR — so the freeze persists for at least one full epoch duration and destroys the yield lenders were owed for that period. On a vault with e.g. 10M USDC TVL at 10% APR, one forced APR0 epoch forfeits roughly `10M * 10% * epochDuration/365` of yield.

### Likelihood Explanation
The trigger is a sequence of fully ordinary, permissionless-or-honest actions:

1. Epoch runs with `unscaledApr == 0` (a supported configuration — the APR0 flow exists precisely for this).
2. Attacker (any KYC-passing lender) calls `requestWithdraw` — a legitimate, unprivileged action that permanently seeds `apr0TotalPrincipal`.
3. The honest manager or CDO sets a nonzero APR at the next `startEpoch`/`setAprsWithBuffer`, as happens in normal operations.
4. Every `stopEpoch` now reverts until APR is manually forced back to zero.

No existing guard blocks it: `maxApr` only caps the APR value, nothing ties `unscaledApr` changes to `apr0TotalPrincipal`, and `_ensureDefaultRecoveryInitialized` does not apply. The only mitigating factor is that recovery is possible via manager intervention, keeping this at temporary-freeze severity rather than permanent loss.

### Recommendation
Decouple APR0 settlement from the current-APR invariant in `prepareStopEpochWithApr0`: instead of reverting when `unscaledApr != 0`, settle the APR0 bucket with zero accrued interest (set `apr0RateByEpoch[epochNumber] = 0` and clear `apr0TotalPrincipal`), treating the requests as matured principal-only receipts. Alternatively, snapshot the APR per APR0 request epoch (`apr0Users.principalEpoch` already exists) so mid-lifecycle APR changes cannot invalidate the bucket.

### Proof of Concept
Foundry fork test outline (uses the repo's existing fork-test conventions):

```solidity
// test/foundry/Apr0StopEpochDoS.t.sol
function test_Apr0BlocksStopEpochAfterAprChange() public {
    // 1. Deposit into AA tranche (KYC'd lender)
    idleCDO.depositAA(1_000_000e6);
    // 2. Epoch running with unscaledApr == 0
    //    (configure vault APR to 0 before startEpoch)
    // 3. Attacker lender requests a withdraw during the APR0 epoch
    idleCDO.requestWithdraw(shares); // routes to _requestWithdrawApr0, apr0TotalPrincipal > 0
    // 4. Honest manager sets a nonzero APR for the next epoch
    vm.prank(manager);
    strategy.setAprs(10e18, 10e18); // unscaledApr != 0
    // 5. Next stopEpoch reverts -> funds frozen
    vm.expectRevert(NotAllowed.selector);
    idleCDO.stopEpoch();
}
```

The revert persists for every `stopEpoch` attempt while `unscaledApr != 0`; only forcing APR back to 0 (forfeiting a full epoch of borrower interest) restores liveness.

  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
  }
