### Title
ERC4626 liquidity draining blocks epoch settlement and freezes withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol#L231-L253))

### Summary
`ProgrammableBorrower.onStopEpoch` treats ERC4626 share value as equivalent to immediately withdrawable liquidity. An unprivileged lender can create a pending withdrawal, while an unprivileged user of the configured ERC4626 vault drains its cash liquidity before `stopEpoch`; the subsequent failed `vault.withdraw` call makes the entire epoch settlement revert and keeps pool funds temporarily frozen.

### Finding Description
At epoch start, `epochPendingWithdraws` is only recorded as an accounting reservation, while the contract deposits its entire underlying balance into the external ERC4626 vault via `_depositToVault(underlyingToken.balanceOf(address(this)), 0)`. [1](#0-0) 

During `stopEpoch`, `IdleCDOEpochVariant._stopEpoch` calls `onStopEpoch` before transferring funds for pending withdrawals. A revert in the hook bubbles out of `stopEpoch` instead of completing epoch accounting. [2](#0-1) 

`onStopEpoch` only verifies that the requested `shortfall` is less than or equal to `_currentVaultAssets()`, which is the share-conversion value rather than available ERC4626 cash. It then attempts `vault.withdraw`; if the vault is economically solvent but temporarily illiquid, the failed withdrawal is caught and deliberately converted into `StopEpochVaultLiquidityUnavailable`. [3](#0-2) 

The ERC4626 attacker therefore does not need to own or corrupt the protocol’s shares: draining the vault’s liquid asset balance is sufficient when the programmatic borrower’s share NAV still covers the withdrawal amount.

### Impact Explanation
A dust-sized pending withdrawal can make `_amountRequired` nonzero. After all idle cash has been deposited into the vault, `onHand` can be zero, forcing the stop path through `vault.withdraw`. If the external vault has share value but no withdrawable cash, the withdrawal reverts, `onStopEpoch` reverts, and `stopEpoch` cannot finish. [4](#0-3) [3](#0-2) 

The frozen amount is at least the aggregate `pendingWithdraws`, but practically the whole active pool is temporarily frozen because `isEpochRunning` remains true, deposit/withdraw-request gates stay closed, and the epoch number is not advanced to permit normal claims. In minted-interest mode, even a one-wei pending withdrawal is sufficient to force this external withdrawal dependency; the quantified frozen pool exposure is `underlyingToken.balanceOf(programmableBorrower) + programmableBorrower.vault.convertToAssets(vaultSharesBalance)`. [5](#0-4) [6](#0-5) 

### Likelihood Explanation
The attack requires three unprivileged actions:

1. A KYC-passing lender submits a normal withdrawal request before `startEpoch`.
2. The honest manager starts the epoch, causing the borrower contract to park its on-hand balance in the ERC4626 vault.
3. Before `stopEpoch`, an ordinary ERC4626-vault participant withdraws its own shares or borrows/removes the underlying liquidity through the vault’s normal external mechanism.

No privileged actor needs to misbehave. The `epochPendingWithdraws` guard limits borrowing against the reserve but does not keep the reserve as cash, and the `shortfall <= _currentVaultAssets()` check does not verify `vault.maxWithdraw` or actual token liquidity. [3](#0-2) [7](#0-6) 

The practical likelihood depends on how much of the configured ERC4626 vault’s liquidity one attacker can remove. For lending-style ERC4626 vaults, a sufficiently collateralized borrower or large shareholder can make the vault temporarily illiquid while its share valuation remains positive.

### Recommendation
Keep the pending withdrawal reserve in underlying instead of depositing it into the external vault. In `onStartEpoch`, deposit at most `underlyingToken.balanceOf(address(this)) - epochPendingWithdraws`, so the normal stop path can satisfy pending claims without depending on ERC4626 liquidity. [8](#0-7) 

Alternatively, separate the required amount into a cash component and a vault-withdrawal component, checking `vault.maxWithdraw(address(this))` and `vault.maxRedeem(address(this))` before epoch start. For large pending withdrawals, retain the full reserve in cash or a segregated liquid sleeve. This preserves `epochPendingWithdraws` as a real liquidity reserve rather than merely a borrow cap. [7](#0-6) 

### Proof of Concept
The following Foundry test is intended to run inside the repository’s existing `ProgrammableBorrowerCreditVault.t.sol` mainnet-fork harness. The only environment-specific step is `drainLiveVaultLiquidity`, which must call the live ERC4626 vault’s public withdraw/borrow liquidity path rather than modify storage.

```solidity
function testExternalVaultLiquidityDrainBlocksStopEpoch() external {
    uint256 depositAmount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(depositAmount);

    // An unprivileged KYC-passing lender creates the smallest pending claim.
    // In minted mode this makes stopEpoch request one unit of cash.
    uint256 requested = cdoEpoch.requestWithdraw(1, address(aaTranche));
    assertEq(requested, 1);
    assertEq(strategy.pendingWithdraws(), 1);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // onStartEpoch parked the borrower's entire on-hand balance in the vault.
    assertEq(underlying.balanceOf(address(programmableBorrower)), 0);
    assertGt(morphoVault.balanceOf(address(programmableBorrower)), 0);

    // An ordinary ERC4626-vault participant drains the live vault's cash via
    // its public withdraw/borrow mechanism. Vault NAV remains solvent, but the
    // underlying token balance available for immediate withdrawal is zero.
    drainLiveVaultLiquidity();

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Share value still covers the one-unit shortfall, so onStopEpoch reaches
    // vault.withdraw instead of taking the early `return true` branch.
    assertLe(1, programmableBorrower.vault().convertToAssets(
        morphoVault.balanceOf(address(programmableBorrower))
    ));
    assertEq(underlying.balanceOf(address(morphoVault)), 0);

    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertEq(strategy.pendingWithdraws(), 1);
}
```

For a fully self-contained fork run, `drainLiveVaultLiquidity()` should select the live vault’s dominant Morpho market and execute the normal public `supplyCollateral`/`borrow` flow with attacker-funded collateral, leaving the borrowed USDC outstanding until after the failed `stopEpoch`. The important reproduction condition is `underlying.balanceOf(vault) < requiredShortfall` while `vault.convertToAssets(programmableBorrower.vaultSharesBalance()) >= requiredShortfall`; this matches the production check and subsequent revert path. [3](#0-2)
