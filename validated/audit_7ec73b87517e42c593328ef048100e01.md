### Title
Unprivileged ERC4626 vault users can drain vault liquidity and make `stopEpoch` permanently revert while liquidity is exhausted - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
CVE-2020-11934 is a "trusted component, attacker-controlled environment" bug: `snapctl` invoked the system `xdg-open` while letting the caller shape its environment (`$XDG_DATA_DIRS`), so a sandboxed attacker redirected a trusted external process. The idle-tranches analog is the programmable-borrower stop-epoch path: `IdleCDOEpochVariant._stopEpoch` delegates liquidity sourcing to `ProgrammableBorrower.onStopEpoch`, which in turn calls `vault.withdraw(shortfall, ...)` on a shared third-party ERC4626 vault. Any unprivileged user of that vault can shape its state (borrow/redeem all available liquidity) so that the withdrawal reverts, and that revert aborts the entire `stopEpoch` call — freezing every lender's funds for as long as the vault lacks liquidity.

### Finding Description
In programmable mode, `stopEpoch`/`stopEpochWithDuration` must complete to end the epoch, settle interest, fund pending withdraw receipts, and unpause deposits/withdrawals. The flow is:

1. `IdleCDOEpochVariant._stopEpoch` resolves interest via `totalInterestDueNow()` and computes `_amountToPullFromBorrower + _pendingWithdraws` (lines 357-376). [1](#0-0) 
2. It then calls `IProgrammableBorrower(_borrower()).onStopEpoch(amountRequired, isRequestingAllFunds)` **outside** any try/catch — only the subsequent `getFundsFromBorrower` call is wrapped (lines 395-408 vs 408/501). [2](#0-1) 
3. Inside `onStopEpoch`, if `shortfall <= _currentVaultAssets()` (the shares economically cover the pull), the contract calls `vault.withdraw(shortfall, ...)` and `catch { revert StopEpochVaultLiquidityUnavailable(); }` (lines 240-253). The comment explicitly frames this as "retryable" — meaning the epoch intentionally stays un-stopped while the vault cannot pay out. [3](#0-2) 

The intended default path (`return true` → `transferFrom` fails → catch → `_handleBorrowerDefault`) is only reachable when the vault position is *economically* insufficient. A pure *liquidity* shortage — vault shares are fully backed but the vault's underlying is lent out or redeemed by other users — reverts instead of defaulting.

The attacker's lever is identical to the CVE: an external party who legitimately uses the shared resource (here, any depositor/borrower of the underlying ERC4626 vault, e.g. a Morpho-style market) drains available liquidity right before the scheduled `epochEndDate`, so `vault.withdraw` reverts. Every subsequent manager/owner `stopEpoch` call reverts until liquidity returns. While the epoch cannot stop:

- `isEpochRunning` stays true, so `restoreOperations` early-returns and ordinary deposits/withdraw requests stay disabled (lines 624-631). [4](#0-3) 
- Normal withdraw claims remain locked: `_claimFundedWithdrawRequest` reverts while `epochNumber <= lastWithdrawRequest[_user]` during a running epoch (lines 326-328). [5](#0-4) 
- The borrower-side facility is also stuck: `borrow()`/`repay()` park epoch accounting, and `epochAccountingActive` stays true until `onStopEpoch` succeeds.

No existing guard prevents this: `nonReentrant` and `_checkOnlyIdleCDO` only restrict who calls the hook; `emergencyExitVault` (lines 361-372) is owner-only and equally hits `redeem`, which fails under the same liquidity shortage; there is no cap on how much vault liquidity external users may consume, and the revert is deliberately bubbled up rather than converted into the default path.

### Impact Explanation
Temporary freezing of all lender principal and pending withdrawal claims for the duration of the vault liquidity shortage — explicitly an accepted impact class. Quantified: 100% of `getContractValue()` plus all `pendingWithdraws`/`pendingInstantWithdraws` remain unclaimable while the external vault reports zero withdrawable liquidity. On a real ERC4626 (e.g. MetaMorpho market vaults used in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`), an attacker only needs to be a vault counterparty — borrow the last unit of liquidity or sandwich `stopEpoch` with a large redeem — which requires capital only for the duration of the freeze, plus gas. A griefing variant repeats the drain each time liquidity returns, extending the freeze indefinitely at the cost of interest rate slippage, while borrower interest keeps accruing against the pool's benefit but cannot be settled.

### Likelihood Explanation
Requires a programmable-borrower deployment whose ERC4626 vault can temporarily exhaust liquidity — precisely the design (idle capital parked in an external lending vault). No privileged role needed; the attacker is an ordinary user of the shared vault, matching the sanctioned attacker profile "a user of the programmable borrower's ERC4626 vault." The freeze is timing-sensitive (must overlap a `stopEpoch` attempt), but because the epoch runs to a public `epochEndDate`, the attacker's window is predictable and cheap to maintain. Mitigated only by vaults with guaranteed idle liquidity; the code itself adds no reserve floor or forced-default fallback.

### Recommendation
Convert a covered-but-illiquid vault into a recoverable path instead of a revert. Options: (a) in `onStopEpoch`, on `vault.withdraw` failure return `false` so `_handleBorrowerDefault` runs rather than blocking; (b) bound the withdraw by `vault.maxWithdraw(address(this))` and pull `min(shortfall, maxWithdraw)`, letting the CDO's `transferFrom` shortfall flow into the existing default/catch path; (c) revert only when `vault.maxWithdraw` is provably manipulated mid-call, not for ordinary liquidity shortages. This keeps the "shares insolvent → default" and "shares illiquid → default/freeze once" semantics consistent instead of giving third-party vault users a veto over the epoch clock.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, which deploys the real MetaMorpho vault at `morphoVault`):

```solidity
function testStopEpochFrozenByExternalVaultLiquidityDrain() external {
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);          // funds parked in morphoVault

    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(amount / 2);

    // Attacker: ordinary Morpho borrower drains the market's idle liquidity
    // so morphoVault.maxWithdraw(programmableBorrower) < required shortfall.
    address whale = makeAddr("whale");
    deal(address(collateralToken), whale, 1_000_000 * 1e18);
    vm.startPrank(whale);
    morphoMarket.borrow(/* borrow all available liquidity */);
    vm.stopPrank();

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // stopEpoch reverts; epoch cannot end, withdraw claims stay locked
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Retries keep reverting while the vault has no withdrawable liquidity
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());              // still running
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();                    // pending receipts frozen
}
```

The key assertions: the manager's `stopEpoch` reverts (not default), `isEpochRunning` remains true, and user claims keep reverting until the whale repays the external market — demonstrating unprivileged, capital-bounded temporary freezing of all pool funds via manipulation of the trusted external vault's environment.
