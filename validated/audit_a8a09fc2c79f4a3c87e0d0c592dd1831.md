### Title
Rejection-address ledger keyed only on `signer_addr` silently drops a signer's rejection of a second block, permanently under-counting the reject-weight tally - ([File: stacks-signer/src/signerdb.rs])

### Summary
`block_rejection_signer_addrs`, the table used to persist which signer addresses have rejected which block, is created with a `PRIMARY KEY` on `signer_addr` alone rather than the composite `(signer_signature_hash, signer_addr)` that every query and every call site assumes. Once a signer address has one row in this table (for whatever block it first rejected), any later `INSERT` recording that same address's rejection of a *different* block hash cannot be added — it collides on the primary key — and the write silently fails. This is the same bug class as APWine H-14: the code assumes a per-item quantity (here, "this signer's rejection of block Y") will always be additively recorded, but a single global column ends up capping it at one entry system-wide, so a legitimate later signal from that signer is lost, permanently skewing the aggregate the consensus decision depends on.

### Finding Description
The table is defined as:
```
CREATE TABLE IF NOT EXISTS block_rejection_signer_addrs (
    signer_signature_hash TEXT NOT NULL,
    signer_addr TEXT NOT NULL,
    PRIMARY KEY (signer_addr)
) STRICT;
``` [1](#0-0) 

Every read/write against this table, however, is written as if `(signer_signature_hash, signer_addr)` were the key: the existence check, the "already recorded, same reason" dedup check, and the update-vs-insert branch in `add_block_rejection_signer_addr` all filter `WHERE signer_signature_hash = ?1 AND signer_addr = ?2`, and the final `INSERT` path assumes a fresh row can always be created for a new `(hash, addr)` pair: [2](#0-1) 

Because the actual `PRIMARY KEY` is `signer_addr` alone, the very first time a given signer address's rejection is recorded (for block hash A), that address now "owns" the sole row it is allowed to have in the whole table. When that same signer later rejects a *different* block (hash B, e.g. a re-proposed block at the same height, or an unrelated future block), `existing_code` will find no row for `(B, addr)` (the lookup is scoped to `signer_signature_hash = B`), so the code falls into the `None =>` branch and issues a plain `INSERT`, which then fails with a SQLite primary-key/uniqueness violation because the address already exists in the table (against block A's row).

This propagates back through `add_block_rejection_signer_addr`'s `?` into the caller, `store_and_process_block_rejection`, which just logs a warning and returns without doing anything else: [3](#0-2) 

The consequence is that `get_block_rejection_signer_addrs(block_hash)`, used to compute `total_reject_weight` for the >30%-rejection consensus decision, will never see this address's rejection of block B, understating the true rejection weight for every subsequent block that address rejects, for the lifetime of that signer's database: [4](#0-3) 

This breaks the equality the state machine relies on — "aggregated rejection weight == verified set of signers who actually rejected this block" — in the direction of under-counting, which can prevent `mark_globally_rejected` from ever firing for a block that in reality has enough rejecting weight, so a signer never locally settles that a stuck/invalid block has been rejected by the network. Because the schema bug affects every signer's own local `SignerDb`, it degrades in exactly the same way across the whole fleet whenever any given signer rejects a second, different block over its lifetime — a very ordinary occurrence (a signer can legitimately reject one block for `ProposalTooOld` and later reject a different, unrelated block for `InvalidParentBlock`, etc.), so this is not a contrived edge case.

### Impact Explanation
This degrades the >30%-rejection consensus computation used in `store_and_process_block_rejection` (and the corresponding pre-global-state "mark miner invalid" logic that depends on `RejectReasonPrefix::ReorgNotAllowed` weight) so that the recorded rejection weight can be permanently lower than the true rejection weight. This can leave a signer's local state machine unable to ever reach the rejection threshold for a block that a supermajority has actually rejected, wedging that signer into waiting indefinitely for a decision on a block that will never be resolved through this path (it can still resolve via acceptance-threshold or via seeing the block appear/not-appear on chain, but the local rejection accounting itself is broken and cannot be trusted for any decision — including the "mark miner invalid" invalidation branch tied to `ReorgNotAllowed` weight). This matches the "signer wedged / losing an equivocation-style safety accounting" impact category: a persistent miscount of a security-relevant aggregate weight, not a majority-controlled or externally-forced condition — it is triggered purely by ordinary honest signer operation (rejecting two different blocks over time) and by the schema itself, independent of attacker action.

### Likelihood Explanation
High likelihood of occurrence in normal operation: any signer that rejects more than one distinct block over the life of its database (a routine event — stale proposals, invalid parents, reorg-not-allowed, etc., all recorded through this same table) will trigger the primary-key collision on its second rejection. No majority of signers, no privileged key, and no coordination is required — it happens from a single signer's own local bookkeeping the moment it needs to record its second-ever rejection of a different block hash.

### Recommendation
Change the table's primary key to the composite `(signer_signature_hash, signer_addr)` (matching every query/`WHERE` clause already written against it), with a migration to move existing single-column-keyed rows into the corrected schema. Add a regression test that has the same signer address reject two different block hashes and asserts both rejections are independently retrievable via `get_block_rejection_signer_addrs` for their respective hashes.

### Proof of Concept
1. Signer `S` receives proposal for block `A` and rejects it (e.g., `InvalidParentBlock`); `add_block_rejection_signer_addr(A, S, InvalidParentBlock)` inserts `(A, S)` — succeeds because the table is empty for `S`.
2. Later, signer `S` receives proposal for an unrelated block `B` at a different height/tenure and rejects it too (e.g., `DuplicateBlockFound`); `add_block_rejection_signer_addr(B, S, DuplicateBlockFound)` looks up `existing_code` scoped to `(B, S)` — finds nothing — falls into the `None =>` branch and executes `INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (B, S, ...)`.
3. This `INSERT` fails at the SQLite layer because `S` already has a row (for `A`) and `signer_addr` alone is the `PRIMARY KEY`; the error surfaces as `Err(DBError)` from `self.db.execute(...)`.
4. `store_and_process_block_rejection` logs `warn!("Failed to save block rejection signature: {e:?}")` and returns; `S`'s rejection of `B` is never persisted, so any subsequent `get_block_rejection_signer_addrs(B)` call by this or any peer signer processing the message locally never counts `S`'s weight toward block `B`'s rejection tally, even though `S` genuinely rejected `B`. [2](#0-1) [5](#0-4) 

**Uncertainty note:** I was not able to locate (within the remaining tool budget) any later migration in `signerdb.rs` that alters `block_rejection_signer_addrs`'s primary key to the composite form after its initial creation; the analysis above is based on the `CREATE_BLOCK_REJECTION_SIGNER_ADDRS_TABLE` definition found at the cited lines. If a subsequent schema migration corrects the key, this finding would not apply — this should be verified against the full migration history in `stacks-signer/src/signerdb.rs`.
