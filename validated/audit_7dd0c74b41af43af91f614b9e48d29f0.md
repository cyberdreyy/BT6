### Title
Revoked LDAP privileges remain valid until background sync tick due to per-request cache-only authorization - ([File: core/sessions/ldapauth/sync.go])

### Summary
`NewLDAPServerStateSyncer` (`core/sessions/ldapauth/sync.go`) only reconciles local `ldap_sessions`/`ldap_user_api_tokens` roles with the upstream LDAP directory on a background timer (`Work`/`run`), gated additionally by `UpstreamSyncRateLimit`. All authenticated `/v2` requests are authorized via `AuthorizedUserWithSession`/`FindUserByAPIToken` in `core/sessions/ldapauth/ldap.go`, which read only the locally cached role from the database and never trigger a sync, so a revoked user's cached role/session stays valid until the next scheduled sync.

### Finding Description
The request path for every authenticated `/v2` route goes through `core/web/auth/auth.go`'s `AuthenticateBySession`/`AuthenticateByToken`, which call `Authenticator.AuthorizedUserWithSession` / `FindUserByAPIToken`. Both are implemented in `core/sessions/ldapauth/ldap.go` (lines 205-236 and 345-373) purely as local SQL `SELECT`s against `ldap_sessions`/`ldap_user_api_tokens`, returning the cached `user_role` without any upstream LDAP check. The only code path that reconciles roles/removes revoked users against the upstream directory is `LDAPServerStateSyncer.Work` in `core/sessions/ldapauth/sync.go` (lines 93-284), invoked either once at `Start()` when `UpstreamSyncInterval` is instant, or periodically via `run()`'s `ticker` at the configured `UpstreamSyncInterval`, additionally throttled by `UpstreamSyncRateLimit` (lines 106-114). There is no hook from the authentication middleware or handlers that calls `Work` synchronously per request — despite the package-level doc comment in `core/sessions/ldapauth/ldap.go` (lines 12-17) and the config doc string for `UpstreamSyncInterval` (`core/config/docs/core.toml:268`) both claiming "This sync happens for every auth endpoint hit," this is not reflected in the actual code (`ldap.go`'s `AuthorizedUserWithSession`/`FindUserByAPIToken` contain no call into the syncer). Consequently, once an admin revokes a user's LDAP group membership, an attacker holding a previously-issued session cookie or API token for that user continues to be authorized with their old cached role (e.g. escalated from 'view' to 'admin' if that was the pre-revocation role, or simply retains any elevated role/session validity) until the next background `Work()` execution, which may be disabled entirely (`UpstreamSyncInterval = '0s'` default disables periodic runs after startup) or rate-limited by `UpstreamSyncRateLimit` (default `2m0s`).

### Impact Explanation
This does not by itself grant privilege escalation beyond what the user already had before revocation — the "attacker" in this question already holds a legitimate 'view'-role session/token issued prior to revocation, and post-revocation they retain exactly that same cached role, not an elevated one, since `Work` only updates roles/purges when it actually runs. The real impact is a stale-access window: revoked credentials keep exactly the privileges they had at time of revocation (not the "admin control of the node" impact class claimed in the question) until the next sync. If `UpstreamSyncInterval` is left at its default `'0s'` (disabled), that stale-session window can persist indefinitely, since `Work()` never re-runs.

### Likelihood Explanation
Precondition is straightforward: LDAP auth (`WebServer.AuthenticationMethod = 'ldap'`) must be configured, a session/API token must have been issued prior to revocation, and the admin must revoke the user's LDAP group membership without also explicitly logging the session out via `DeleteUserSession`. No special exploit steps are needed beyond continuing to send the pre-revocation session ID/API token — this is entirely feasible and repeatable, and worse with `UpstreamSyncInterval` at its default disabled value.

### Recommendation
Perform (or at minimum offer/document as required) an upstream LDAP validation on every `AuthorizedUserWithSession`/`FindUserByAPIToken` call, or reduce reliance on a background-only sync: e.g., call `LDAPServerStateSyncer.Work` (respecting `UpstreamSyncRateLimit` as a cache TTL, not a full bypass) synchronously from the auth path so a revoked user is rejected on the very next request once the rate limit window elapses. Also correct or implement the misleading doc claims in `core/sessions/ldapauth/ldap.go` and `core/config/docs/core.toml` that already assert per-request sync occurs but do not match `AuthorizedUserWithSession`/`FindUserByAPIToken` implementations.

### Proof of Concept
1. Unit/integration test in `core/sessions/ldapauth`: create an `ldap_sessions` row for `user@example.com` with role `view` (mirroring `ldap_test.go` helpers).
2. Mock the LDAP client (as done in `ldap_test.go`) so that a subsequent call to `LDAPServerStateSyncer.Work` would remove/downgrade `user@example.com` (simulating group revocation) — but do NOT invoke `Work`.
3. Call `AuthorizedUserWithSession(ctx, sessionID)` directly (or via `AuthenticateBySession` handler test) and assert it still returns the pre-revocation cached role, proving no per-request revalidation occurs.
4. Then call `LDAPServerStateSyncer.Work(ctx)` explicitly, then repeat step 3 and assert the session is now purged/`ErrUserSessionExpired`, showing revocation only takes effect after an explicit sync call, not immediately on the next request.

func (l *ldapAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (sessions.User, error) {
	if len(sessionID) == 0 {
		return sessions.User{}, errors.New("session ID cannot be empty")
	}
	// Query the ldap_sessions table for given session ID, user role and email are cached so
	// no further upstream LDAP query is performed
	var foundSession struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	if err := l.ds.GetContext(ctx, &foundSession,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1",
		sessionID, l.config.SessionTimeout().Duration(),
	); err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	if !foundSession.Valid {
		// Sessions expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_sessions WHERE id = $1", sessionID); execErr != nil {
			l.lggr.Errorf("error purging stale ldap session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	return sessions.User{
		Email: foundSession.UserEmail,
		Role:  foundSession.UserRole,
	}, nil
}
