### Title
Missing upper-bound validation on `AssetV1::update_multiplier` allows an operator-set multiplier to permanently overflow scaled-balance reads - (File: `crates/common/precompiles/src/b20_asset/logic/v1.rs`)

### Summary
`AssetV1::update_multiplier` only rejects a zero multiplier; it has no upper-bound check analogous to the one added in `AssetV2`. `AssetV2::update_multiplier` and `AssetV2::update_ui_multiplier` both explicitly enforce `new_multiplier > Self::MAX_UI_MULTIPLIER` (`type(uint128).max`) as an "overflow guard," but the V1 setter frozen at Beryl never gained this bound.

### Finding Description
`AssetV1::update_multiplier` accepts any nonzero `U256` value: [1](#0-0) 

Compare this with `AssetV2::update_multiplier`, which added the exact bound the V1 setter is missing: [2](#0-1) 

The `MAX_UI_MULTIPLIER` constant is documented as existing precisely to prevent `balance * multiplier` from overflowing `U256` on scaled-balance reads: [3](#0-2) 

The repo's own test suite proves the overflow condition this bound is meant to prevent, for both the V1 and V2 logic implementations, when a multiplier above the safe range is set: [4](#0-3) [5](#0-4) 

Because V1's setter lacks the `MAX_UI_MULTIPLIER` guard, an `OPERATOR_ROLE` holder can set a multiplier large enough (e.g. above `U256::MAX/2`) that any subsequent `to_scaled_balance`/scaled-read operation on the token overflows and reverts unconditionally, since `set_multiplier` itself has no bound check either — only `update_multiplier` is supposed to enforce it, and it doesn't in V1.

### Impact Explanation
Once an out-of-range multiplier is committed to storage, every downstream scaled-balance computation that multiplies a balance by the multiplier permanently reverts with an overflow error. This bricks the token's scaled-view/scaled-balance functionality for all holders — a permanent freezing condition — with no path to self-heal, since the only other setter (`update_multiplier` itself) is exactly what let the bad value in and provides no way to "unset" it below the overflow threshold once other user balances have grown, and the same operator-only role gate governs any future correction. This mirrors the reported bug class: an admin/operator-controlled parameter setter accepts a value beyond the safe operating bound and the resulting on-chain effect deviates catastrophically from the protocol's documented invariant (the `MAX_UI_MULTIPLIER` "overflow guard" that V2 documents as load-bearing).

### Likelihood Explanation
Triggering this requires only a single call to `updateMultiplier(uint256)` by an address holding `AssetV1::OPERATOR_ROLE` (or through the factory-privileged path) with a sufficiently large value — no coordination, no rare timing condition, and no external dependency. Any legitimate operator misconfiguration (a fat-fingered value, unit confusion between WAD-scaled and raw values) or a compromised/malicious operator key can trigger it in one transaction.

### Recommendation
Add the same `new_multiplier.is_zero() || new_multiplier > MAX_UI_MULTIPLIER` guard used in `AssetV2::update_multiplier`/`update_ui_multiplier` to `AssetV1::update_multiplier`, using the same `type(uint128).max` bound (or the appropriate bound consistent with V1's supply cap and `WAD` precision) so the setter cannot commit a multiplier that overflows scaled-balance arithmetic.

### Proof of Concept
1. Grant `ALICE` the `OPERATOR_ROLE` on a fresh V1 token (as in `golden_update_multiplier` at `crates/common/precompiles/tests/b20_asset_v1_golden.rs:2069-2087`).
2. Call `updateMultiplier(U256::MAX / 2 + 1)` (or any value above the safe `type(uint128).max`-scale range) as `ALICE`. `AssetV1::update_multiplier` only checks for zero, so this call succeeds and is persisted via `set_multiplier`.
3. Any subsequent call that computes a scaled balance (`to_scaled_balance`, mirroring the existing test `to_scaled_balance_overflows_when_product_exceeds_u256_max` at `crates/common/precompiles/src/b20_asset/logic/v1.rs:1456-1464`) with any nonzero balance now reverts with `BasePrecompileError::under_overflow()`, permanently, for every account, with no recovery path other than another operator call that is subject to the same unbounded setter.

    fn update_multiplier(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        new_multiplier: U256,
        privileged: bool,
    ) -> Result<()> {
        self.ensure_operator_role(token, caller, privileged)?;
        if new_multiplier.is_zero() {
            return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
        }
        token.accounting_mut().set_multiplier(new_multiplier)?;
        token.accounting_mut().emit_event(
            IB20Asset::MultiplierUpdated { multiplier: new_multiplier }.encode_log_data(),
        )
    }
