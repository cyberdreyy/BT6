### Title
Stale rejection weight in the miner's StackerDB tally is never retracted when a signer later accepts the same block, letting a transient rejection permanently poison the vote tally for that block - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side `StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` per block independently, keyed only by whether a given `slot_id` has already been recorded in `gathered_signatures` (for accepts) or is inserted into the *shared* `responded_signers` set (used as the rejection dedup guard). Because a signer can legitimately reject a block once (for a transient reason such as a not-yet-stale conflict) and later accept the very same block hash after re-evaluating it, the reject weight recorded for that signer is never removed, while the accept weight is added on top. This can make `total_weight_rejected` cross the `>30%` blocking-minority threshold and the miner give up on a block (`NakamotoNodeError::SignersRejected`) even though a supermajority — including the very signers who once rejected — has since accepted it.

### Finding Description
`StackerDBListener::run` processes `BlockResponse::Accepted` and `BlockResponse::Rejected` messages independently, per block hash:

- On `Accepted`, the weight is added to `total_weight_approved` gated only on `!block.gathered_signatures.contains_key(&slot_id)` [1](#0-0) , and `responded_signers.insert(slot_id)` is called unconditionally afterward [2](#0-1) .
- On `Rejected`, the weight is added to `total_weight_rejected` gated on `block.responded_signers.insert(slot_id)` succeeding (i.e., the slot has not been seen before) [3](#0-2) .

Both counters are monotonically increasing (`saturating_add`) and are never decremented anywhere in this file. There is no code path that subtracts a signer's earlier rejection weight when that same signer later accepts the block, nor vice versa.

On the signer side, this ordering is not merely theoretical: the signer protocol explicitly supports issuing a rejection for a block and later reconsidering and signing the *same* block once conditions change — the reevaluation logic explicitly re-runs the pre-commit/accept path for previously-rejected blocks whose reject reason is judged reevaluable, and the "conflict" freshness/staleness mechanism in `handle_block_pre_commit` is designed precisely so a signer that once withheld/rejected due to a conflicting sibling can later sign once the conflict goes stale [4](#0-3) . The signer_state diagram documents `LocallyRejected --> LocallyAccepted : re-evaluated` as a legitimate transition [5](#0-4) .

When a signer flips from Reject to Accept for the same `signer_signature_hash`, the coordinator's `get_block_status` loop evaluates the rejection-threshold check first, using the stale, never-retracted `total_weight_rejected` value:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight { ... return Err(SignersRejected...) }
else if block_status.total_weight_approved >= self.weight_threshold { ... return Ok(...) }
``` [6](#0-5) 

Because rejection weight from signers who have since changed their mind is never cleared, cumulative historical rejections (which individually can be well under the 30% blocking minority at any single point in time, but sum across multiple signers' independent, non-colluding, transient rejections over the life of a proposal) can push `total_weight_rejected` past the blocking-minority threshold, even while `total_weight_approved` simultaneously also grows toward (or past) the 70% acceptance threshold from the very same signers having since switched their votes. Since the reject branch is checked first in the loop, the coordinator declares the block dead (`SignersRejected`) and the miner discards good transactions/txids and tries a new block, even though a valid signer supermajority currently supports the original proposal.

This is a liveness wedge that does not require a majority of colluding signers or another signer's key — it results from each signer's own legitimate, individually-triggered reject→accept transition (driven by conflict staleness/timing that a miner's own tenure/proposal timing can influence) being tallied by a coordinator that has no mechanism to retract stale votes.

### Impact Explanation
This falls under the "High" impact bucket: a signer's honestly-issued vote sequence can wedge the miner-side tally into treating a block as globally rejected (or into needlessly re-proposing / discarding good transactions as "problematic") even though the current, up-to-date signer set supports the block. It is a tally/threshold equality break (`aggregated-weight vs verified-accepts` — specifically, aggregated rejected-weight is stale and not re-derived from the signers' *current* view), causing the miner to wedge state (give up on a valid block, discard/quarantine transactions under `permanently_excluded_txids`/`temporarily_excluded_txids`) purely due to the non-retraction of past rejections.

### Likelihood Explanation
Likelihood is moderate: it requires several distinct signers (not necessarily a majority, and not colluding) to each pass through a reject→accept flip for the *same* proposed block, driven by ordinary protocol timing (conflict staleness, transient validation issues, node desync) that is a normal and expected occurrence in the documented pre-commit/conflict-freshness design (see the “Pre-commit threshold → signature” staleness logic) rather than by malicious crafting of packets. A one-slot miner cannot directly force this, but by controlling proposal/re-proposal timing and tenure/parent choices it can materially increase the odds of triggering multiple signers' reject→accept transitions on the same block hash, particularly around tenure-start/sibling-conflict scenarios that the "Pre-commit threshold → signature" logic is built to handle.

### Recommendation
Have `StackerDBListener` retract a signer's earlier rejection weight (and any associated `failed_txids` entries) when that same signer later submits an `Accepted` for the identical block, and vice versa retract approved weight if an accept is later followed by a reject for the same block — i.e., track the signer's single current vote per block/slot rather than accumulating both categories independently and irreversibly. Re-derive `total_weight_rejected`/`total_weight_approved` from the latest vote per signer rather than a monotonic running sum.

### Proof of Concept
1. Miner proposes block `B` (hash `H`).
2. Signers `S1..Sk` (cumulative weight < blocking minority individually, but summing to > 30% over time) each independently reject `B` at different points for transient reasons (e.g., a conflicting sibling that is still "fresh" per `conflict_still_blocks`/`freshness_cutoff`). Each rejection increments `total_weight_rejected` in `StackerDBListener` via the `Rejected` branch [3](#0-2) .
3. Time passes; the conflicting sibling blocks go stale/get orphaned. Per the documented staleness logic, each of `S1..Sk` legitimately re-evaluates and now signs (`Accepted`) the same block `H`, each adding their weight to `total_weight_approved` via the `Accepted` branch [1](#0-0) . Their earlier rejection weight is never subtracted from `total_weight_rejected`.
4. `get_block_status` on the miner now sees both `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (from stale rejects) AND `total_weight_approved >= weight_threshold` (from current accepts) — but the rejected-branch check runs first [6](#0-5) , so the miner treats the block as `SignersRejected` and discards it, despite currently having a valid signer supermajority in favor.

Note: I was not able to fully trace `should_reevaluate_reject_reason`'s exact set of reevaluable reject codes within the remaining tool budget (the function body itself was not retrieved), so the precise conditions under which a signer transitions Reject→Accept for the identical block hash are inferred from the surrounding documentation/comments and the `handle_block_pre_commit` conflict-staleness code rather than directly confirmed line-by-line in `should_reevaluate_reject_reason`. A Devin session with full file access could confirm the exact reject-reason set and construct a concrete end-to-end reproduction.
