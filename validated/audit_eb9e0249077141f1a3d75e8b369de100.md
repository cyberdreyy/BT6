Confirmed: in both `multisig/src/lib.rs` (`DeleteKey` action) and `multisig2/src/lib.rs` (`delete_member`), key/member removal only purges **requests originated by** that key/member — it never scans other pending requests' `confirmations` sets to strip a removed key's stale confirmation. A confirmation recorded by a key/member that is later removed remains counted toward `num_confirmations` on any other still-open request.

### Title
Multisig executes requests using confirmations from removed keys/members, allowing execution below the live-member threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`confirm()` in both the k-of-n `multisig` and `multisig2` contracts authorizes execution purely by counting entries in the `confirmations` `HashSet` for a request: `if confirmations.len() as u32 + 1 >= self.num_confirmations`. When a key (`DeleteKey`) or member (`DeleteMember`) is removed, the cleanup logic only removes **requests that key/member itself created** and their own confirmation sets — it never removes that key/member's confirmation entries from *other* still-pending requests they had previously confirmed. Those stale confirmations continue to count toward the threshold forever.

### Finding Description
In `multisig/src/lib.rs`, the `DeleteKey` branch of `execute_request` (lines 198-216) does: [1](#0-0) 
It filters `self.requests` for entries whose `signer_pk == pk` (i.e. requests the removed key itself authored) and purges those requests plus their confirmations. It does not iterate `self.confirmations` for requests authored by *other* keys to strip `pk` out of their confirmation sets.

`confirm()` then blindly trusts the stored set size: [2](#0-1) 

The identical pattern exists in `multisig2/src/lib.rs`'s `delete_member`: [3](#0-2) 
which filters `self.requests` by `r.member == member` (requests the removed member created) and again never touches `confirmations` entries the removed member left on requests created by someone else. `confirm()` in `multisig2` has the same threshold check pattern: [4](#0-3) 

The custody binding broken: `num_confirmations` is meant to represent confirmations from currently-authorized signers/members, i.e. `confirmations_counted == confirmations_from_live_members`. Once a signer is removed, this equality is violated — a request can reach `confirmations.len() + 1 >= num_confirmations` using a confirmation cast by an account/key that is no longer a valid multisig member.

### Impact Explanation
This lets a multisig request execute (transferring NEAR, deploying/upgrading contract code, adding/deleting keys, etc.) with fewer than `num_confirmations` *live* signers, because one of the counted confirmations belongs to a removed key/member. Per the accepted impact set, this is "a multisig request executed below threshold," a Critical-severity outcome — remaining/new signers effectively lose part of their protection, and the deployer/attacker who removed a key can potentially replay the stale-confirmation channel to push a request through with only `num_confirmations - 1` currently-live approvals.

### Likelihood Explanation
Requires a normal, expected multisig lifecycle: (1) a member confirms a pending request but confirmations don't yet reach the threshold, (2) the same or another authorized flow later removes that member/key (e.g. as part of routine key rotation or offboarding, an entirely permitted multisig action), (3) the original request is still open (it isn't auto-expired) and later gets enough additional confirmations to cross the (now effectively lower, in terms of *live* signers) threshold. No attacker-controlled deployment or malicious validator is needed — only ordinary sequential use of documented multisig actions (`DeleteKey`/`DeleteMember` followed by `confirm`), which members can trigger unintentionally or an adversarial minority member could engineer deliberately.

### Recommendation
When executing `DeleteKey`/`DeleteMember`, iterate all entries in `self.confirmations` (not only requests authored by the removed key/member) and remove the removed key/member from every confirmation set. Alternatively, validate in `confirm()` that every public key/member currently present in a request's confirmation set is still an active signer before counting it toward `num_confirmations` (recomputing the effective count from only live members at confirmation time).

### Proof of Concept
1. Initialize `multisig` with `num_confirmations = 3` and keys `A, B, C, D`.
2. `A` calls `add_request` to create request `R` (e.g. a `Transfer`).
3. `B` calls `confirm(R)` → `confirmations = {B}`, `len()=1 < 3`, request stays open.
4. Using another already-satisfied request (e.g. any prior `add_request_and_confirm` reaching 3-of-4), execute a `DeleteKey { public_key: B }` action to remove `B` from the multisig (this only purges requests where `signer_pk == B`, i.e. none created by `B` here — `R`'s confirmation set is untouched): [1](#0-0) 
5. `C` calls `confirm(R)` → `confirmations = {B, C}`, `len()+1 = 3 >= 3` → `execute_request(R)` runs and transfers funds, even though only `A` (creator, unconfirmed by itself unless it also confirmed) and `C` are still live signers — `B`'s stale confirmation was decisive in reaching the threshold.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
