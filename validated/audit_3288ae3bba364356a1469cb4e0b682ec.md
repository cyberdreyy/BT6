### Title
Unfunded instant-withdraw receipts from prior epochs escape default-recovery accounting and freeze in `claimInstantWithdrawRequest` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug is a check-then-act on shared state: `rt6_uncached_list_del()` skipped locking because `list_empty()` observed a half-deleted node on another CPU, so teardown freed and rewrote a live entry. The vault analog is the same shape: default finalization decides whether instant-withdraw receipts join the recovery haircut by inspecting only the *current* epoch's per-epoch counter, `instantWithdrawClaimsByEpoch[epochNumber]` in `defaultPendingClaimBasis()` (`IdleCreditVault.sol:644-649`) and `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` in `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`), while the *global* unfunded counter `pendingInstantWithdraws` may still cover receipts booked under an older epoch key. Those older receipts are never haircutted and never cleared, and post-finalization claims revert inside `_transferFundedClaim` because every held wei is accounted as `defaultRecoveryReserve` (`IdleCreditVault.sol:897-905`). Result: permanently frozen user claims plus an overstated `defaultRecoveryPrice` that overpays default-epoch claimants at the expense of the frozen ones.

### Finding Description
Three pieces of state are maintained on different granularity:

- `pendingInstantWithdraws` — global unfunded instant basis, decremented only by `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`) and by defaulted-claim clearing (`IdleCreditVault.sol:849-852`).
- `instantWithdrawClaimsByEpoch[currentEpoch]` — per-request-epoch aggregate, incremented in `requestInstantWithdraw` (`IdleCreditVault.sol:371-372`) but **never decremented or rolled forward** when an epoch ends partially funded.
- `instantWithdrawsRequestsByEpoch[user][epoch]` — per-user, per-epoch basis.

At finalization, `defaultPendingClaimBasis()` adds instant basis only if `pendingInstantWithdraws != 0`, and then only `instantWithdrawClaimsByEpoch[epochNumber]` — the current epoch's bucket (`IdleCreditVault.sol:644-648`). If a previous epoch stopped with only partial instant funding (borrower returned less than the instant queue), the unfunded remainder keeps `pendingInstantWithdraws > 0` and keeps its basis under the *old* epoch key. `instantWithdrawClaimsByEpoch` for that old epoch is never migrated into the new epoch, so that basis is silently dropped from `totalBasis` at line 680, inflating `recoveryPrice` for everyone else.

Symmetrically, `defaultInstantWithdrawsFinalized` is set to true, but `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (`IdleCreditVault.sol:844-847`). A user whose unfunded receipt was booked in an earlier epoch retains it in `instantWithdrawsRequests[user]`; `claimInstantWithdrawRequest` then falls through to `_burn(_user, amount)` and `_transferFundedClaim(_user, amount)` (`IdleCreditVault.sol:387-392`), where `balance - reserve < amount` reverts `NotAllowed` because all held underlying is reserve.

### Impact Explanation
- **Permanent freezing of unclaimed yield/principal:** users with unfunded instant receipts created in a pre-default epoch can never claim — every call reverts after default finalization. Their funds are absorbed into the recovery pool and redistributed to others.
- **Incorrect recovery ratio:** because old-epoch instant basis is missing from `totalBasis` at `IdleCreditVault.sol:680`, `defaultRecoveryPrice` is overstated, so default-epoch claimants withdraw more than pro-rata, leaving the reserve insufficient — the last claimants under `_transferDefaultRecovery` also revert on `defaultRecoveryReserve -= _amount` underflow/insufficient balance.
- Broken invariant: "one receipt one payout" and reserve isolation (`_transferFundedClaim` exists precisely to protect the reserve, but the accounting upstream misclassifies these receipts as funded when they were not).

### Likelihood Explanation
Requires: an epoch that ends with partially funded instant withdrawals (borrower repays less than the instant queue — a normal partial-repayment scenario, no privilege needed to request the instant withdrawal), followed by a borrower default finalized via `finalizeDefault` in a later epoch while `pendingInstantWithdraws != 0`. The attacker is any unprivileged tranche holder making a legitimate `requestInstantWithdraw` in the earlier epoch; honest manager/borrower sequence the epochs. The stale-epoch-key read mirrors the CVE's stale `list_empty` observation: the code checks the wrong granularity of the shared list and acts on it.

### Recommendation
Track unfunded instant basis per epoch and carry it forward, or make `defaultPendingClaimBasis()` sum all epochs with outstanding instant claims (e.g., persist a cumulative `instantWithdrawClaims` unfunded total instead of keying only `epochNumber`). Correspondingly, `_claimDefaultedInstantWithdrawRequest` should clear/haircut every epoch's unfunded instant basis for the user, not only `defaultRecoveryEpoch`. Alternatively, decrement `instantWithdrawClaimsByEpoch` in `collectInstantWithdrawFunds` and roll the unfunded remainder into the new epoch key at `stopEpoch`.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `_checkDefault`):

```solidity
function testOldEpochInstantReceiptEscapesRecoveryBasis() external {
    // 1. Deposit with instantUser (epoch 0 buffer), enable instant withdrawals.
    _depositWithUser(instantUser, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // 2. User requests instant withdraw in epoch 0.
    vm.prank(instantUser);
    cdoEpoch.requestInstantWithdraw(trancheAmount, address(AAtranche));
    uint256 instantBasis = strategy.instantWithdrawsRequests(instantUser);

    // 3. stopEpoch with partial funding: borrower repays only part of the
    //    instant queue -> pendingInstantWithdraws stays > 0 and
    //    instantWithdrawClaimsByEpoch[0] keeps instantBasis.
    deal(defaultUnderlying, borrower, partialFunds);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, /* borrower sends partial */);

    // 4. New epoch 1 runs; borrower defaults. Manager finalizes.
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, 0);
    _checkDefault();
    uint256 basis = strategy.defaultPendingClaimBasis();
    // BUG: instantBasis (booked under epoch 0) is excluded even though
    // pendingInstantWithdraws != 0.
    assertEq(basis, strategy.pendingWithdraws()); // instant basis missing
    cdoEpoch.finalizeDefault(recovered, manager);

    // 5. instantUser's claim permanently reverts: the old-epoch receipt was
    //    never haircut/cleared, and _transferFundedClaim reverts because the
    //    full strategy balance is defaultRecoveryReserve.
    vm.prank(instantUser);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Expected result: `defaultPendingClaimBasis()` omits the epoch-0 instant basis, `defaultRecoveryPrice` is overstated, and `claimInstantWithdrawRequest` for the epoch-0 receipt reverts `NotAllowed` forever — permanent freezing and reserve shortfall.

*Caveat: the exact partial-funding path for instant withdrawals at `stopEpoch`/`collectInstantWithdrawFunds` in `IdleCDOEpochVariant.sol` was not fully traced (tool budget exhausted); the PoC assumes partial borrower repayment can leave `pendingInstantWithdraws > 0` across an epoch boundary, which the code comments at `IdleCreditVault.sol:636-640` and `850-852` explicitly acknowledge ("still-unfunded remainder", "prefunded reserve").*
