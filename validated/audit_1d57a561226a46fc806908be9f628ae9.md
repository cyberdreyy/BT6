### Title
Underflow in `pendingWithdraws -= claimBasis` permanently bricks default-epoch withdrawal claims for closed-pool receipts - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.requestWithdraw` records closed-pool receipts in `withdrawsRequestsByEpoch` but deliberately skips the `pendingWithdraws` increment. After a borrower default is finalized, `_claimDefaultedWithdrawRequest` subtracts every claimant's epoch-keyed `claimBasis` from the aggregate `pendingWithdraws`. Closed-pool receipts recorded in `defaultRecoveryEpoch` therefore subtract basis that was never added, so the subtraction underflows and reverts — permanently freezing recovery funds for those receipt holders, analogous to the U-Boot negative `payload_len` reaching `memcpy` without validation.

### Finding Description
In `requestWithdraw`, when the pool is closed (`epochEndDate == 0`), `pendingWithdraws += _amount` is skipped, but the receipt is still recorded in `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) .

After default finalization, `claimWithdrawRequest` routes to `_claimDefaultedWithdrawRequest`, which computes `claimBasis` from `withdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (+ APR0 buckets) and executes `pendingWithdraws -= claimBasis` [2](#0-1) [3](#0-2) .

`defaultRecoveryEpoch` is set to the current `epochNumber` at finalization [4](#0-3) . If the default occurs in pool-close mode (`stopEpoch` with the `_interest == 1` "return all funds" sentinel, which sets `epochEndDate = 0`), any withdraw requests made in that epoch were recorded under `defaultRecoveryEpoch` but never counted in `pendingWithdraws`. The claim then computes `claimBasis > pendingWithdraws`, the subtraction underflows (Solidity 0.8 checked arithmetic), and the transaction reverts — mirroring the missing `tcp_seg_in_wnd()` validation that let a negative length reach `memcpy`.

`collectWithdrawFunds` confirms the intended invariant: `pendingWithdraws` is supposed to equal the sum of outstanding claim basis [5](#0-4)  — closed-mode receipts break it. Note also the neighboring guarded pattern (`pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis`) shows the codebase already knows such aggregates can diverge [6](#0-5) .

### Impact Explanation
Once `defaultRecoveryFinalized` is set, every closed-mode receipt holder whose `claimBasis` exceeds the remaining `pendingWithdraws` reverts in `claimWithdrawRequest` permanently — there is no alternative claim path (`_claimFundedWithdrawRequest` reverts on the same epoch gate and cannot pay a defaulted-epoch receipt). Their share of `defaultRecoveryReserve` is locked in the strategy forever. More generally, closed-mode claimBasis dilutes `pendingWithdraws` accounting for normal requesters too: cumulative claims can exceed the counter mid-way, so later claimants revert even when reserve funds remain. Impact: permanent freezing of unclaimed recovery funds; magnitude equals the sum of closed-mode receipts in the defaulted epoch plus any stranded remainder of the reserve.

### Likelihood Explanation
Triggering requires (a) the borrower defaulting while the pool is in closed mode — the exact scenario close mode exists for (borrower fails to return principal+interest), and (b) at least one lender calling `requestWithdraw` after close, which is a normal, unprivileged action explicitly supported by the code comments. No malicious privileged role is needed: the lender is an ordinary KYC'd LP, and the borrower "defaulting" is an honest failure to repay, not attacker behavior. The revert is deterministic once both conditions hold.

### Recommendation
In `_claimDefaultedWithdrawRequest`, track defaulted-epoch basis independently of `pendingWithdraws` (e.g., a `defaultEpochClaimBasis` aggregate populated at finalization), or include closed-pool receipts in `pendingWithdraws`/default-epoch basis accounting at request time. At minimum, clamp the subtraction (`pendingWithdraws = claimBasis >= pendingWithdraws ? 0 : pendingWithdraws - claimBasis`) and reconcile `defaultPendingClaimBasis()` so closed-mode receipts are either fully inside or fully outside the recovery basis consistently.

function testClosedPoolReceiptUnderflowsDefaultClaim() external {
    // LP deposits AA, epoch starts and stops normally so epochNumber = N+1
    _depositWithUser(LP, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Pool-close mode: stopEpoch with _interest == 1 sentinel sets epochEndDate = 0
    // (borrower returns only part of the funds -> pool will be marked defaulted)
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1); // close-mode stop; epochEndDate == 0 afterwards

    // Unprivileged LP requests withdraw in closed pool:
    // requestWithdraw skips pendingWithdraws += _amount but records
    // withdrawsRequestsByEpoch[LP][N+1] = _amount
    vm.prank(LP);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(IdleCreditVault(address(strategy)).pendingWithdraws(), 0);

    // Borrower fails to return funds -> defaulted; manager finalizes recovery
    _checkDefault();
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager); // sets defaultRecoveryEpoch = N+1
    vm.stopPrank();

    // LP claims: claimBasis (epoch N+1) > pendingWithdraws (0) -> underflow revert
    vm.prank(LP);
    vm.expectRevert(); // panic: arithmetic underflow
    cdoEpoch.claimWithdrawRequest();

    // LP's share of defaultRecoveryReserve is permanently locked

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }

  function _withdrawClaimAmountsForEpoch(address _user, uint256 _claimEpoch) internal view returns (uint256 claimBasis, uint256 burnAmount) {
    // We calculate what the user is owed in underlyings (claimBasis) and how many strategy tokens to burn (burnAmount).
    // the amount owned is the sum of the normal withdraw request and the APR0 principal and interest if any.
    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 apr0PrincipalAmount;
    uint256 apr0InterestAmount;
    uint256 principal = _apr0User.principal;
    uint256 principalEpoch = _apr0User.principalEpoch;
    if (principal != 0 && principalEpoch == _claimEpoch) {
      apr0PrincipalAmount = principal;
      uint256 rate = apr0RateByEpoch[principalEpoch];
      if (rate != 0) {
        // APR0 interest increases the user's default claim basis, but not the receipt burn amount.
        apr0InterestAmount += (principal * rate) / RECOVERY_FULL;
      }
    }
    claimBasis = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    burnAmount = normalAmount + apr0PrincipalAmount;
  }
