### Title
ETH sent with `withdrawAA`/`withdrawBB` is permanently locked in the per-request `EthenaCooldownRequest` clone and never refunded - ([File: contracts/IdleCDOEthenaVariant.sol](contracts/IdleCDOEthenaVariant.sol))

### Summary
Analogous to the `OperatorProposal` leftover-ETH bug (operator returns unused ETH to the proposal contract, which never forwards it to the executor), `IdleCDOEthenaVariant._withdraw` forwards the caller's entire `msg.value` into a freshly cloned `EthenaCooldownRequest` contract, which has no code path to ever move native ETH. The ETH is not refunded and is permanently frozen.

### Finding Description
In `IdleCDOEthenaVariant._withdraw`, the user's `msg.value` is passed as the `value` argument of `clone`, which deploys the minimal proxy and transfers that ETH to it: [1](#0-0) 

```solidity
EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
  abi.encodePacked(address(this), msg.sender),
  msg.value
));
```

The clone's only functions are `startCooldown` (gated to the CDO), `unstake` (calls `SUSDE.unstake(user)`), and `rescue`, which only sweeps ERC-20 balances — it calls `IERC20Detailed(_token).transfer(...)` and cannot move native ETH: [2](#0-1) 

There is no `receive`/ETH-sweep and no refund in `_withdraw` — after `clone.startCooldown()` the function simply emits an event and returns, exactly mirroring the reported "just returns without sending back the unused funds" pattern. [3](#0-2) 

### Impact Explanation
Any ETH attached by an unprivileged user to a `withdrawAA`/`withdrawBB` call on the sUSDe variant is permanently locked in an ephemeral clone address that has no mechanism to spend or recover ETH (`rescue` handles tokens only). This is a direct, quantified loss of `msg.value` per call — permanent freezing of user funds, matching the accepted impact class. This is realistic because the withdraw entrypoints are payable (the code deliberately forwards `msg.value`), so routers, multicalls, or UIs that attach ETH will silently lose it.

### Likelihood Explanation
Likelihood depends on a caller sending ETH with the withdrawal. Since `msg.value` is explicitly forwarded to the clone, the interface signals ETH is accepted/needed, making accidental or bundled ETH attachment plausible (e.g., a multicall aggregating payable calls, or a user expecting a refund of excess). No privileged action, oracle manipulation, or timing is required — a single ordinary withdrawal transaction triggers it.

### Recommendation
Either make the withdrawal path non-payable/reject `msg.value > 0`, or refund the caller:

```solidity
EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
  abi.encodePacked(address(this), msg.sender)
));
// ...
if (msg.value > 0) {
  (bool ok,) = msg.sender.call{value: msg.value}("");
  require(ok, "ETH refund failed");
}
```

Alternatively add a native-ETH sweep to `EthenaCooldownRequest.rescue`/`unstake`.

### Proof of Concept
Foundry fork (mainnet), sketch:

```solidity
function test_WithdrawEthLocked() public {
  // fork mainnet, use real sUSDe CDO (IdleCDOEthenaVariant) with an existing BB holder
  vm.createSelectFork("mainnet");
  IdleCDOEthenaVariant cdo = IdleCDOEthenaVariant(payable(ETHEREUM_SUSDE_CDO));
  address user = <tranche holder>;
  uint256 bal = IERC20(cdo.BBTranche()).balanceOf(user);

  uint256 ethBefore = user.balance;
  vm.prank(user);
  cdo.withdrawBB{value: 1 ether}(bal); // payable entrypoint

  // clone received msg.value and has no way to release it
  // user is not refunded
  assertEq(user.balance, ethBefore - 1 ether);
  // clone.balance == 1 ether, rescue() cannot recover ETH (ERC20 only)
}
```

Note: I could not inspect `ClonesWithImmutableArgs.clone`'s internals (node_modules not indexed) to confirm the value-forwarding semantics line-by-line, but the call site explicitly passes `msg.value` as the clone's endowed balance, and the clone contract contains no ETH-handling code, so the lock-up follows directly from the indexed source.
