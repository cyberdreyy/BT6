## Analysis

The `AgentFactoryV4` bug class is: **a permissionless external call can pre-claim a resource key (the Uniswap pair) that a two-step registration flow assumes is exclusively reserved for the legitimate caller, causing the legitimate call to revert.** The strongest analog in this in-scope codebase is in `multisig-factory/src/lib.rs`, and here the consequence is worse than a simple revert — it results in **permanent loss of the user's attached deposit**, not merely a DoS.

### Root cause

`MultisigFactory::create()` derives a deterministic sub-account name from a user-supplied `name` parameter and unconditionally schedules `create_account()` + `transfer()` + `function_call()` on it, with **no callback checking success or refunding the caller on failure**: [1](#0-0) 

Compare this to the two sibling factories, `staking-pool-factory` and `lockup-factory`, which face the exact same "account may already exist" race but explicitly attach an `on_..._create` callback that checks `is_promise_success()` and refunds the deposit to `predecessor_account_id` on failure: [2](#0-1) [3](#0-2) 

The existence of these manual refund callbacks in the sibling contracts confirms that NEAR's protocol-level refund for a failed batched-action receipt goes back to the **predecessor of the failed receipt** (i.e., the factory contract's own balance), not automatically to the original transaction signer. `MultisigFactory::create()` has no such callback, so any deposit lost to a failed `create_account()` becomes permanently stuck in the factory contract with no withdrawal method to recover it.

### Attack path (front-running analog)

1. Victim submits `create(name="alice", members=[...], num_confirmations=N)` with an attached deposit, intending to deploy their multisig at `alice.multisig-factory`.
2. Attacker observes the pending transaction and back-runs/front-runs it with their own call `create(name="alice", members=[garbage], num_confirmations=1)` with zero or minimal deposit — this call is fully permissionless, costs only gas, and succeeds first, creating `alice.multisig-factory`.
3. Victim's transaction now fails at the `create_account()` action inside the batched receipt (`AccountAlreadyExists`), which per NEAR's batched-action-receipt atomicity aborts the whole receipt (deploy, transfer, function_call included).
4. Because `create()` lacks the success/failure callback present in `staking-pool-factory`/`lockup-factory`, the victim's attached deposit is not returned to them — it is retained by the `multisig-factory` contract's own balance, unreachable through any exposed method.

This breaks the custody binding "value debited from the user equals value delivered (multisig deployed or refunded)": the value is debited but neither delivered nor refunded — it is permanently frozen.

### Title
Unrefunded deposit loss via front-run account-name squatting in `MultisigFactory::create()` - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create()` derives the target multisig sub-account name directly from an attacker-controllable, permissionless-to-race `name` parameter and batches `create_account`, `transfer`, and `function_call` into a single promise with no completion callback. An unprivileged attacker can front-run a legitimate deployment by calling `create()` with the same `name` first (at negligible cost), causing the victim's `create_account()` action to fail. Because there is no `on_create` style callback (unlike the analogous `staking-pool-factory` and `lockup-factory` contracts), the victim's attached NEAR deposit is never refunded and becomes permanently stuck in the factory contract's balance.

### Finding Description
`create()` computes `account_id = format!("{}.{}", name, env::current_account_id())` and issues `Promise::new(account_id).create_account().deploy_contract(CODE.to_vec()).transfer(env::attached_deposit()).function_call(...)` with no `.then()` callback: [4](#0-3) 
If an attacker races ahead and calls `create()` with the identical `name` (any dummy `members`/`num_confirmations`, zero deposit is sufficient), `alice.multisig-factory` is created by the attacker first. When the victim's transaction executes, `create_account()` fails because the account already exists, which aborts the whole batched receipt including the `transfer()` of the victim's deposit. Since NEAR routes the refund of a failed receipt's actions back to the receipt's predecessor (the `multisig-factory` contract account itself — as evidenced by the fact that the sibling contracts must explicitly re-transfer to `predecessor_account_id` in their callbacks), and `MultisigFactory` implements no such callback or withdrawal mechanism, the deposit is absorbed into the factory's balance with no code path to return or claim it.

### Impact Explanation
This matches the Critical impact category "funds permanently frozen": the victim's attached NEAR deposit is debited from their account and never delivered to a deployed multisig contract, nor refunded — it is irrecoverably locked inside `multisig-factory`'s balance, which exposes no `create()`-failure recovery or withdrawal function.

### Likelihood Explanation
The attack requires only observing a pending `create()` transaction (public in the mempool/mempool-equivalent for NEAR) and submitting a competing `create()` call with the same `name` and negligible deposit before the victim's transaction is included — an unprivileged, cheap, and repeatable griefing action with no special access needed, directly analogous to the reported Uniswap `createPair` front-run.

### Recommendation
Add a completion callback to `MultisigFactory::create()` analogous to `on_lockup_create`/`on_staking_pool_create`: check `is_promise_success()` after the account-creation promise resolves, and if it failed, refund `env::attached_deposit()` back to `env::predecessor_account_id()`. Additionally, consider deriving the sub-account name deterministically from the caller's account id (or otherwise binding it to `predecessor_account_id`) so that only the intended owner can ever claim that specific sub-account name.

### Proof of Concept
1. Victim calls `multisig-factory.create({"name": "alice", "members": [...], "num_confirmations": 2})` attaching e.g. 5 NEAR, intending to deploy `alice.multisig-factory`.
2. Attacker submits `multisig-factory.create({"name": "alice", "members": [{"account_id":"attacker"}], "num_confirmations": 1})` with 0 attached deposit, and it lands first, creating `alice.multisig-factory` under attacker's control.
3. Victim's transaction executes: the batched receipt to `alice.multisig-factory` fails at `create_account()` (`AccountAlreadyExists`); `deploy_contract`, `transfer`, and `function_call` never apply.
4. No callback exists in `multisig-factory/src/lib.rs` to detect this failure or refund the victim; the 5 NEAR deposit remains stuck in the `multisig-factory` contract's balance, permanently inaccessible to the victim.

impl MultisigFactory {
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
