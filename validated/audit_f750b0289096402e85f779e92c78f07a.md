### Title
Symlink-following arbitrary file write during cache/artifact extraction via pre-planted symlink - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
`extractor.Extract` in `tarzstd_extractor.go` validates that the *literal* target path lies inside `e.dir`, but for regular-file tar entries it calls `os.Create(path)` directly, which follows an existing symlink at that path. A build container can pre-create a symlink inside the shared build directory pointing outside `e.dir` before the helper container runs `cache-extractor`/`artifacts-downloader`, causing the subsequent archive-file write to land at the symlink's target instead of being rejected.

### Finding Description
The prefix check `strings.HasPrefix(path, e.dir+separator)` at [2](#0-1)  only validates the tar-entry-derived path string; it never calls `os.Lstat`/`os.Readlink` to detect whether that path already exists as a symlink. For regular files the code proceeds straight to `os.Create(path)` at [3](#0-2) , and `os.Create` uses `O_CREATE|O_TRUNC` without `O_NOFOLLOW`, so if `path` is a pre-existing symlink, the OS transparently follows it and opens/truncates the link's target — which can be anywhere the extracting process (helper container, often root) can write, entirely outside `e.dir`.

Exploit flow: with `SharedBuildsDir` enabled or a bind-mounted `/builds`, an attacker's job script runs `ln -s /etc/cron.d /builds/proj/.git/cache-target` (or any path whose basename matches a name the attacker knows/controls, e.g. a fixed cache key path) before the cache extraction stage executes in the helper container. When `cache-extractor` later runs `extractor.Extract` and processes a tar entry named `cache-target` from the (attacker-influenced, since caches are written by the same project's earlier jobs) cache archive, `os.Create` follows the planted symlink and writes archive-controlled bytes to the linked-to location outside the build root.

The directory-symlink deferred-write path (`os.Symlink(hdr.Linkname, path)`) is a secondary variant: it plants a *new* symlink, but doesn't itself write through it; it only matters if a subsequent tar entry in the same archive targets that symlinked directory, which is a related but distinct issue from the specific `os.Create`-follows-symlink primitive described here. The check at line 62 does not stop this because it only inspects the requested path string, not the resolved filesystem state, and there is no removal/replacement of pre-existing filesystem objects before write.

### Impact Explanation
An attacker with normal pipeline privileges can achieve an arbitrary-path file write (subject to the extracting process's OS permissions) inside the helper container's filesystem namespace, using content they control via the archive entry. Since `e.dir`-scoping is the only sandboxing mechanism for cache/artifact extraction, this defeats it and can corrupt or overwrite files outside the intended build/cache root reachable by the helper container (e.g., other mounted paths shared with the host or other containers, depending on volume configuration).

### Likelihood Explanation
Requires `SharedBuildsDir: true` or an equivalent shared/bind-mounted `/builds` between build and helper containers (a supported, non-default-but-documented configuration), and requires the job script to run before the cache-extraction stage — which is the normal Runner execution order (job body runs, then post-stage cache/artifact upload; but for `cache-extractor`/`artifacts-downloader`, extraction happens at stage start, so this requires either a `cache: policy: pull` at a subsequent job stage within the same shared workspace, or artifact/cache extraction in a later job/stage after an earlier stage planted the symlink and it persisted on the shared volume). This is fully attacker-controlled and repeatable without any special GitLab or admin privileges beyond writing `.gitlab-ci.yml` script commands.

### Recommendation
Before creating/writing each regular-file entry, `Lstat` the target path; if it exists and is a symlink (or any type other than a plain file at a path validated via `filepath.EvalSymlinks` of the parent directory chain), remove it or reject the archive. Alternatively, open files with `O_NOFOLLOW` where supported, and validate the resolved (evaluated) path — not just the literal joined path — is within `e.dir` for every entry, including verifying that no ancestor path component is itself a symlink pointing outside `e.dir`.

### Proof of Concept
Go unit test in `tarzstd_extractor_test.go`:
1. Create temp dir `dir`.
2. Create a target file/dir outside `dir` (e.g., `outside := t.TempDir()+"/secret"`, write known content).
3. `os.Symlink(outside, filepath.Join(dir, "payload"))`.
4. Build a tar+zstd stream containing a single regular-file entry named `payload` with attacker content `"PWNED"`.
5. Call `extractor.Extract(ctx)` with `dir` as the target.
6. Assert: either `Extract` returns an error (desired fix) OR — demonstrating the bug — assert `os.ReadFile(outside)` now equals `"PWNED"`, proving the write escaped `dir` through the symlink despite the `HasPrefix` check passing.
