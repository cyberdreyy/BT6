### Title
Decimal-Truncation Dust Permanently Locked in BridgeVault on Every ETH/ERC20 Deposit - (File: bridge/evm/contracts/SuiBridge.sol, bridge/evm/contracts/utils/BridgeUtils.sol)

---

### Summary

`SuiBridge.bridgeETH` and `SuiBridge.bridgeERC20` transfer the user's **full** wei/token amount into `BridgeVault`, then call `BridgeUtils.convertERC20ToSuiDecimal` which performs integer floor-division to produce the Sui-side amount. The truncated remainder — up to `factor - 1` wei per deposit — is never bridged and has no recovery path in the current contract code.

---

### Finding Description

`BridgeUtils.convertERC20ToSuiDecimal` computes the Sui-adjusted amount with a plain integer division:

```solidity
uint256 factor = 10 ** (erc20Decimal - suiDecimal);
amount = amount / factor;          // floor division; remainder silently discarded
``` [1](#0-0) 

For ETH (18 EVM decimals, 8 Sui decimals), `factor = 10^10`. Any deposit whose wei value is not an exact multiple of `10^10` leaves up to `9_999_999_999` wei (~10 Gwei) stranded per transaction.

In `bridgeETH`, the full `msg.value` is forwarded to the vault before the conversion:

```solidity
(bool success,) = payable(address(vault)).call{value: amount}("");
require(success, "SuiBridge: Failed to transfer ETH to vault");
// ...
uint64 suiAdjustedAmount = BridgeUtils.convertERC20ToSuiDecimal(..., amount);
emit TokensDeposited(..., suiAdjustedAmount, ...);
``` [2](#0-1) 

The bridge node reads `suiAdjustedAmount` from the event and mints exactly that amount on Sui. The truncated remainder stays in `BridgeVault` forever. The same pattern applies to `bridgeERC20`: [3](#0-2) 

`BridgeVault` exposes only `transferERC20` and `transferETH`, both `onlyOwner` (the `SuiBridge` proxy), and `SuiBridge` has no sweep or dust-recovery function: [4](#0-3) 

The existing test suite explicitly demonstrates the truncation and confirms the vault retains the full unrounded amount:

```
// 2_000_000_011_000_000_888 is rounded to 2.00000001 eth
bridge.bridgeERC20(BridgeUtils.ETH, 2_000_000_011_000_000_888, ...);
assertEq(IERC20(wETH).balanceOf(address(vault)), 3_000_000_011_000_000_888);
// vault holds 3_000_000_011_000_000_888 but only 3_000_000_010_000_000_000 is bridgeable
``` [5](#0-4) 

The official documentation acknowledges the rounding but does not acknowledge the permanent vault lock:

> "There is no minimum transfer, but very small fractions can be rounded down." [6](#0-5) 

---

### Impact Explanation

Every `bridgeETH` or `bridgeERC20` call with a non-round amount permanently locks up to `factor - 1` wei in `BridgeVault`. For ETH that is up to ~10 Gwei per deposit. With high bridge volume this accumulates to a material sum. The user receives fewer tokens on Sui than they deposited on Ethereum, and the difference is irrecoverable under the current contract code. This matches the **permanent fund lock** impact class (High/Medium).

---

### Likelihood Explanation

Any ordinary bridge user calling `bridgeETH` or `bridgeERC20` with a non-round amount (which is the common case for ETH) triggers this. No special privilege is required. The trigger is public and unconditional.

---

### Recommendation

1. **Reject sub-`factor` remainders at deposit time**: require `amount % factor == 0` and revert if not, forcing users to send only round amounts.
2. **Or refund the remainder**: compute `remainder = amountTransfered % factor` and return it to `msg.sender` before emitting the event.
3. **Add a governance sweep function** to `SuiBridge` that can recover accumulated dust from the vault to a designated treasury address.

---

### Proof of Concept

1. User calls `bridgeETH{value: 1_000_000_001_000_000_001}(recipientAddress, destinationChainID)`.
2. `BridgeVault` receives `1_000_000_001_000_000_001` wei (WETH after vault's `receive()`).
3. `convertERC20ToSuiDecimal(18, 8, 1_000_000_001_000_000_001)` → `factor = 10^10`, result = `100000000` (i.e., 1.00000000 ETH in Sui units).
4. `TokensDeposited` emits `suiAdjustedAmount = 100000000`.
5. Bridge node mints `100000000` Sui-ETH units = `1_000_000_000_000_000_000` wei equivalent.
6. Remainder `1_000_000_001` wei (~1 Gwei) is permanently locked in `BridgeVault` with no recovery path.
7. Repeat across thousands of deposits; the vault accumulates an ever-growing irrecoverable balance.
