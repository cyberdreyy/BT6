### Title
De-listed wallet bypasses the Keyring/Idle withdrawal gating by moving tranche tokens to a controlled whitelisted wallet — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` enforces the Keyring/whitelist gate on `msg.sender` (`isWalletAllowed(msg.sender)` in `_deposit` and `depositDuringEpoch`), while `IdleCDOTranche` is a plain unrestricted ERC20 with no transfer hook or holder-level credential check. A lender whose address is removed from the `KeyringIdleWhitelist` (credential revoked / admin de-whitelisted) retains full claim on their deposited funds: they simply `transfer` their tranche tokens to a second wallet they control that still passes `checkCredential`, and execute the withdrawal request / claim flow from that address. This is the direct analog of the suspended-PartyA/controlled-PartyB bypass: the revocation binds to the *caller address*, not to the *economic ownership* of the position.

### Finding Description
- `contracts/KeyringIdleWhitelist.sol:78-80` — `checkCredential` returns `whitelist[entity] || Keyring.checkCredential(policyId, entity)`; revocation flips an address-level bit only.
- `contracts/IdleCDOEpochVariant.sol:644-649` — `_deposit` reverts with `!isWalletAllowed(msg.sender)`, so a de-listed wallet cannot deposit.
- `contracts/IdleCDOEpochVariant.sol:656-668` — `depositDuringEpoch` enforces `!isWalletAllowed(msg.sender)` the same way; any other gated user entry point binds to `msg.sender`.
- `contracts/IdleCDOTranche.sol:7-41` — `IdleCDOTranche` inherits `ERC20` with no `_beforeTokenTransfer` override, no per-holder allowlist, and no minter check on `transfer`/`transferFrom`. Tranche tokens (the sole receipt needed for `requestWithdraw`, `claimWithdrawRequest`, `claimInstantWithdrawRequest` / post-default `postDefaultRequests`) are freely movable.

Attack path (buffer phase, fixed-APR mode): Alice is de-listed. She calls `AAtranche.transfer(Bob, bal)` where Bob is her second KYC'd (or still-whitelisted) wallet. Bob calls `requestWithdraw`/the claim path; the vault burns Bob's tranche tokens and pays Bob. Alice's funds exit despite revocation — exactly the "suspended party withdraws via controlled counterparty" pattern, and no existing guard (skim, epoch gating, only-CDO, reserve checks) intersects it because token transfers never touch `IdleCDO`.

### Impact Explanation
The compliance/access invariant — "a wallet whose credential is revoked cannot move value out of the vault" — is broken. The de-listed user exits 100% of their position through the surrogate wallet. Severity is bounded to the user's own funds (no third-party theft), consistent with a Medium.

### Likelihood Explanation
Requires only that the attacker control (or obtain) one additional credential-passing wallet; token transfer costs a single ERC20 call in any epoch phase that permits transfers at all. No privileged cooperation is needed — only the honest admin performing a revocation that silently fails to cover the position.

### Recommendation
Either gate tranche-token transfers on `isWalletAllowed(to)`/`isWalletAllowed(from)` via a `_beforeTokenTransfer` hook in `IdleCDOTranche`, or accept that revocation is deposit-side only and document/enforce at the claim layer on the *beneficiary* rather than `msg.sender`. If revocation is intended to freeze exit, snapshot positions at revocation time and route them through a permissioned redemption path.

### Proof of Concept
Foundry fork sketch (against a live `IdleCDOEpochVariant` deployment):

```solidity
// Alice: de-listed lender; Bob: second wallet controlled by Alice, still credentialed
vm.prank(admin);
keyringWhitelist.setWhitelistStatus(alice, false); // revocation

// confirm alice can no longer act on gated paths
vm.prank(alice);
vm.expectRevert(); // NotAllowed via isWalletAllowed
idleCDO.depositDuringEpoch(1, AA);

// bypass: move the receipt to the controlled whitelisted wallet
vm.prank(alice);
IIdleCDOTranche(AA).transfer(bob, aliceBal);

vm.prank(bob);
idleCDO.requestWithdraw(aliceBal, AA); // or claim path depending on epoch phase
// bob receives the underlying; alice's funds have exited post-revocation
```

Note on verification limits: I confirmed the `isWalletAllowed(msg.sender)` gating on `_deposit`/`depositDuringEpoch` and the unrestricted ERC20 in `IdleCDOTranche`; I did not enumerate every claim-path line (`claimWithdrawRequest`/`claimInstantWithdrawRequest` in `IdleCreditVault`) — if those paths lack the check entirely, the finding is stronger (revocation never gated exit at all, and the transfer step is only needed where a caller check exists).
