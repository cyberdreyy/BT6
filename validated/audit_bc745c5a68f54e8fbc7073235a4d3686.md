No sanity/bound check exists anywhere for `operator_fee_scalar`/`operator_fee_constant` in the codebase.

### Title
Missing sanity/upper-bound check on `operator_fee_scalar`/`operator_fee_constant` derived from L1 `SystemConfig` allows unbounded per-transaction fee extraction - (File: crates/common/genesis/src/updates/operator_fee.rs)

### Summary
The Base rollup derives the `operator_fee_scalar` (u32) and `operator_fee_constant` (u64) directly from an L1 `SystemConfig.ConfigUpdate(OperatorFee)` log with no range/sanity validation, and applies them unconditionally to every L2 transaction's operator-fee charge. This mirrors the reported `originationFee` issue: a fee parameter that is trusted and applied without any bound, so a misconfigured or compromised fee-setting authority can impose an arbitrarily large per-transaction fee on all L2 users.

### Finding Description
`OperatorFeeUpdate::try_from` decodes the raw `operator_fee_scalar`/`operator_fee_constant` bytes straight from the L1 log payload with no upper-bound check [1](#0-0) , and `OperatorFeeUpdate::apply` writes them into `SystemConfig` unconditionally [2](#0-1) .

This is invoked from the generic `SystemConfig` log-processing pipeline, which applies every successfully-decoded update with no further validation [3](#0-2)  and [4](#0-3) .

These scalars are then fed into the operator-fee formula used both by the txpool (for balance admission) and by the execution layer (for the actual charge), with no clamping — `saturating_mul`/`saturating_add` only prevent overflow panics, they do not cap the resulting fee: [5](#0-4) .

Unlike the `eip1559_denominator`/`elasticity` path, which has an explicit zero-denominator guard elsewhere in the codebase, there is no analogous ceiling anywhere for `operator_fee_scalar`/`operator_fee_constant` (confirmed by absence of any bound-checking logic referencing these fields in the codebase).

### Impact Explanation
The operator fee scalar/constant directly determines how much ETH is deducted from every L2 sender's balance and routed to `Predeploys::OPERATOR_FEE_VAULT` on every transaction [6](#0-5) . Because there is no upper bound, a `SystemConfig` update setting `operator_fee_scalar` to a very large value (up to `u32::MAX`, further amplified `x100` under the Jovian multiplier) or `operator_fee_constant` to `u64::MAX` causes every subsequent L2 transaction to be charged an enormous, effectively confiscatory fee, siphoning user funds to the operator fee vault. This is comparable to the reported `originationFee` issue's impact: an improperly/maliciously set fee parameter causes direct, protocol-enforced fund loss for ordinary users, with no way for the chain or the user to reject or cap it once the log has been derived.

### Likelihood Explanation
The only gating factor is that the `ConfigUpdate(OperatorFee)` log must originate from the configured `l1_system_config_address` [7](#0-6) . If that L1 authority is compromised, or if it mis-fires a value (e.g., due to a bug or unit-mismatch), the value is applied to the entire L2 chain instantly and unconditionally at the next epoch boundary, with no timelock, no sanity ceiling, and no rejection path — exactly the class of risk flagged in the original `originationFee` report ("compromised admin could ... charge fee up to the limit, stealing fund from users").

### Recommendation
Add an explicit upper-bound (and ideally a timelock/two-step change) for `operator_fee_scalar` and `operator_fee_constant` at the point they are applied in `OperatorFeeUpdate::apply` / `SystemConfig::process_config_update_log`, rejecting or clamping values above a sane maximum (e.g., a scalar corresponding to no more than a small single-digit percentage of gas cost), analogous to the existing zero-denominator guard used for EIP-1559 parameters.

### Proof of Concept
1. On L1, emit `SystemConfig.ConfigUpdate(version, OperatorFee, abi.encode(scalar=0xFFFFFFFF, constant=0xFFFFFFFFFFFFFFFF))` from the configured `l1_system_config_address` (as exercised by `enqueue_operator_fee_update` in the test harness, see `actions/harness/tests/upgrade/operator_fees.rs`).
2. Once this log is derived at the next L1 epoch, `SystemConfig::operator_fee_scalar`/`operator_fee_constant` are updated to these values with no validation (`crates/common/genesis/src/updates/operator_fee.rs:19-24`).
3. Every subsequent L2 transaction has its operator fee computed via `operator_fee_charge_inner` using these unbounded scalars [8](#0-7) , resulting in an enormous fee debited from the sender's balance to the operator fee vault on every transaction, with no code path anywhere in the repository capping or rejecting the value.

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }

#[test]
fn operator_fee_is_gated_by_isthmus_and_scaled_by_jovian() {
    let params = l1_fee_params();

    // Pre-Isthmus: no operator fee is collected even though the scalars are configured.
    let mut pre = build_evm2(BaseUpgrade::Fjord, U256::from(10u128.pow(18)));
    let _ = pre.transact(&Recovered::new_unchecked(eip1559_envelope(), SENDER)).unwrap().commit();
    assert_eq!(
        balance(&mut pre, Predeploys::OPERATOR_FEE_VAULT),
        U256::ZERO,
        "operator fee is not collected before Isthmus",
    );

    // Isthmus vs Jovian: the identical transaction uses the same gas, but Jovian applies the
    // operator-fee multiplier, so its operator fee is strictly larger and matches the Jovian
    // formula.
    let mut ist = build_evm2(BaseUpgrade::Isthmus, U256::from(10u128.pow(18)));
    let ist_gas = U256::from(
        ist.transact(&Recovered::new_unchecked(eip1559_envelope(), SENDER))
            .unwrap()
            .commit()
            .tx_gas_used(),
    );
    let mut jov = build_evm2(BaseUpgrade::Jovian, U256::from(10u128.pow(18)));
    let jov_gas = U256::from(
        jov.transact(&Recovered::new_unchecked(eip1559_envelope(), SENDER))
            .unwrap()
            .commit()
            .tx_gas_used(),
    );

    let ist_op = balance(&mut ist, Predeploys::OPERATOR_FEE_VAULT);
    let jov_op = balance(&mut jov, Predeploys::OPERATOR_FEE_VAULT);
    assert_eq!(ist_op, params.operator_fee_charge(&enveloped(), ist_gas, BaseUpgrade::Isthmus));
    assert_eq!(jov_op, params.operator_fee_charge(&enveloped(), jov_gas, BaseUpgrade::Jovian));
    assert!(jov_op > ist_op, "the Jovian multiplier increases the operator fee");
