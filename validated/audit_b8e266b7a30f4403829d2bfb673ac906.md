### Title
Unbounded `da_footprint_gas_scalar` system-config update can permanently DOS all user transactions on Base - (File: `crates/common/genesis/src/updates/da_footprint_gas_scalar.rs`)

### Summary
`DaFootprintGasScalarUpdate::try_from` decodes the DA footprint gas scalar as a raw `u16` with no upper-bound sanity check beyond its type width, and `DaFootprintGasScalarUpdate::apply` only special-cases the value `0` (mapping it to the default `400`). Any other value, including the maximum `u16::MAX = 65535`, is accepted and applied unconditionally to `SystemConfig.da_footprint_gas_scalar`, which is later used as a hard, protocol-enforced multiplier gating whether *any* transaction can be included in a block.

### Finding Description
The DA footprint gas scalar is derived from an L1 `SystemConfig` `ConfigUpdate` log (update type `DaFootprintGasScalar`) and applied without any upper bound: [1](#0-0) 

The only defensive branch guards against zero, not against unreasonably large values.

This scalar then multiplies the estimated compressed transaction size to compute the "DA footprint," which is protocol-enforced (post-Jovian) to stay below the block gas limit for every transaction included in a block, both during block building and validation: [2](#0-1) 

The same check is duplicated in the tx-pool admission path, again with no bound on the scalar read from `SystemConfig`/`L1BlockInfo`: [3](#0-2) 

Because `total_da_bytes_used` (or `estimated_da_size`) is multiplied by `da_footprint_gas_scalar` using `saturating_mul`, a scalar close to `u16::MAX` makes the DA footprint of essentially any non-trivial transaction exceed the block gas limit (`limits.block_gas_limit`, tens of millions of gas). Since this check is protocol-enforced (applies identically in the builder and in execution/validation, not just local mempool policy), once such a value is derived from L1, no sequencer/builder can construct a valid block containing any ordinary user transaction, and the tx-pool will reject essentially all incoming transactions with `DaFootprintExceedsBlockGasLimit`.

This is the same bug class as the original report: an admin/privileged-but-unbounded numeric fee/scalar parameter that downstream code assumes will always be "reasonable," and whose extreme value makes a `paidOnly`/gated code path permanently unsatisfiable — except here the analog is reachable through Base's L1-derived `SystemConfig` update pipeline (attacker/owner-controlled L1 log data processed by derivation), which is an explicitly in-scope path.

### Impact Explanation
If the DA footprint gas scalar is derived with a large value, the L2 chain can no longer include ordinary user transactions in blocks (both the sequencer's block builder and independent node validation enforce the same threshold), effectively halting user-transaction processing on the chain until a corrective `SystemConfig` update is derived from L1. This matches the "node halt" / "RPC the node can no longer serve (meaningful) transactions" impact bar, since transaction admission and inclusion become impossible chain-wide, not just for a single node's local policy.

### Likelihood Explanation
The value is decoded straight from an L1 log with only structural/ABI validation (data length, pointer, length fields) — there is no reasonableness/sanity bound on the scalar itself (`DaFootprintGasScalarUpdate::try_from`, lines 38-63). Any process capable of emitting a valid `ConfigUpdate(DaFootprintGasScalar)` log from the configured L1 `SystemConfig` address (i.e., whoever controls the L1-side system config, or a bug/misconfiguration there) can trigger this with a single L1 transaction; the derivation pipeline applies it automatically at the next epoch update with no additional gating in this repo's code.

### Recommendation
Add an explicit sanity upper bound to `DaFootprintGasScalarUpdate::try_from`/`apply` (e.g., reject or clamp values above some maximum considered safe relative to typical transaction sizes and the block gas limit, similar to how `GasLimitUpdate` already bounds its value against `u64::MAX`), and/or have the builder/tx-pool checks clamp the effective scalar used for the DA footprint computation to a safe ceiling instead of trusting the raw derived value unconditionally.

### Proof of Concept
1. Emit an L1 `ConfigUpdate` log of kind `DaFootprintGasScalar` (type 7) from the configured `l1_system_config_address`, ABI-encoding a `uint16` value such as `65535`.
2. The derivation pipeline decodes and applies it via `DaFootprintGasScalarUpdate::apply`, setting `SystemConfig.da_footprint_gas_scalar = Some(65535)` (see `crates/common/genesis/src/updates/da_footprint_gas_scalar.rs`).
3. Once this config becomes active (post-Jovian), for any typical transaction, `tx_da_footprint = total_da_bytes_used * 65535` (crates/builder/core/src/execution.rs, `is_tx_over_limits`) will exceed `limits.block_gas_limit`, causing every transaction to be rejected both from block building and from the tx-pool (`BaseTxPoolError::DaFootprintExceedsBlockGasLimit` in `crates/execution/txpool/src/validator.rs`), halting inclusion of ordinary user transactions on the chain.

impl DaFootprintGasScalarUpdate {
    /// The default DA footprint gas scalar
    /// <https://github.com/ethereum-optimism/specs/blob/664cba65ab9686b0e70ad19fdf2ad054d6295986/specs/protocol/jovian/l1-attributes.md#overview>
    pub const DEFAULT_DA_FOOTPRINT_GAS_SCALAR: u16 = 400;

    /// Applies the update to the [`SystemConfig`].
    pub const fn apply(&self, config: &mut SystemConfig) {
        let mut da_footprint_gas_scalar = self.da_footprint_gas_scalar;

        // If the da footprint gas scalar is 0, use the default value
        // <https://github.com/ethereum-optimism/specs/blob/664cba65ab9686b0e70ad19fdf2ad054d6295986/specs/protocol/jovian/l1-attributes.md#overview>
        if da_footprint_gas_scalar == 0 {
            da_footprint_gas_scalar = Self::DEFAULT_DA_FOOTPRINT_GAS_SCALAR;
        };

        config.da_footprint_gas_scalar = Some(da_footprint_gas_scalar);
    }
}
