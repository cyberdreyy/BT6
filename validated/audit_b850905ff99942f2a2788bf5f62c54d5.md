### Title
Loss-adjusted withdraw haircut is written to the wrong epoch slot because `deposit()` bumps `epochNumber` before `collectWithdrawFunds`, letting loss-adjusted receipts claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.deposit()` increments `epochNumber` whenever the IdleCDO calls it while `isEpochRunning()` is still true, which is exactly the case inside `stopEpoch` when the borrower's repayment is deposited. `collectWithdrawFunds()` is invoked afterwards in the same `stopEpoch` flow and records the realized loss haircut under the **already-bumped** `epochNumber` (`lossRecoveryPriceByEpoch[epochNumber]`, IdleCreditVault.sol:421). Users' receipts, however, are keyed to the epoch in which they called `requestWithdraw` via `lastWithdrawRequest[_user]` (IdleCreditVault.sol:282), i.e. the pre-bump epoch. The haircut is therefore stored in an epoch slot no receipt ever looks up — an "out-of-bounds" write analogous to a heap buffer overflow corrupting an adjacent structure. Loss-adjusted receipts then fall through `_claimLossAdjustedWithdrawRequest` (price lookup returns 0) into `_claimFundedWithdrawRequest`, which pays them at par from an underfunded strategy balance.

### Finding Description
In `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` the CDO moves borrower repayment into the strategy and then calls `collectWithdrawFunds(_amount)` to fund pending receipts. Inside `IdleCreditVault.deposit()`:

```solidity
if (IIdleCDOEpochVariant(idleCDO).isEpochRunning()) {
    totEpochDeposits = 0;
    epochNumber += 1;   // bumped during the stopEpoch repayment deposit
}
```

(IdleCreditVault.sol:607-611)

`collectWithdrawFunds` then executes in the same transaction with `epochNumber` already incremented:

```solidity
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice; // stores under N+1
```

(IdleCreditVault.sol:417-421)

But every user who requested during epoch N has `lastWithdrawRequest[_user] = N` and `withdrawsRequestsByEpoch[_user][N]`. On claim:

1. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[N]` → 0 → returns 0 (IdleCreditVault.sol:789-792).
2. `_claimFundedWithdrawRequest` passes its gate because `epochNumber (N+1) > lastWithdrawRequest (N)` (IdleCreditVault.sol:326-328).
3. It burns the full receipt and calls `_transferFundedClaim(_user, fullParAmount)` (IdleCreditVault.sol:338-349).

The strategy only received `_amount = pendingBasis - loss`, so claimants are paid the un-haircut basis. The invariant "one pending receipt claims `basis * lossRecoveryPrice / RECOVERY_FULL`" is broken: the recorded loss is orphaned in epoch slot N+1.

### Impact Explanation
Direct theft and insolvency. With a realized stopEpoch loss of L on pending basis P, the strategy is funded with only `P - pendingLoss`, yet every pending receipt claims P pro-rata. The first claimants to call `claimWithdrawRequest` receive more than their fair recovery share (up to 100% of basis instead of `lossRecoveryPrice`), draining the funded underlyings; all subsequent claimants revert on the ERC20 transfer, permanently freezing their share. The attacker is any unprivileged tranche holder with a pending withdraw request in the defaulted/loss epoch — no privileged role required. Loss magnitude equals `pendingLoss` distributed to early claimers plus permanently frozen funds for the rest.

### Likelihood Explanation
Requires a `stopEpoch`/`stopEpochWithDuration` where the borrower funds less than `pendingWithdraws` (a realized loss on the pending bucket — a normal, intended code path, not an edge case) and at least one pending withdraw receipt. The accounting mismatch is deterministic on that path; only the ordering of `claimWithdrawRequest` calls determines who steals and who is frozen. Guard review: `_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve`, not underfunded pending receipts; the `epochNumber <= lastWithdrawRequest` gate is satisfied by design after one epoch; nothing re-does the lookup under the correct epoch.

### Recommendation
Record the loss price under the epoch the requests were made in, not the bumped counter — e.g., persist `lastWithdrawRequest` epoch semantics by storing `lossRecoveryPriceByEpoch[epochNumber - 1]` (or better, capture `epochNumber` in `collectWithdrawFunds` before any incrementing deposit, or increment `epochNumber` only after `collectWithdrawFunds`). Alternatively, key user lookups symmetrically: set `lastWithdrawRequest[_user]` to the epoch that will own the haircut. Add a test: request withdraw in epoch N → `stopEpochWithDuration` with loss → assert `claimWithdrawRequest` pays `amount * lossRecoveryPrice / RECOVERY_FULL`, not par.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.x;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

// Demonstrates the epoch off-by-one: the loss haircut is stored under the
// post-bump epochNumber while receipts are keyed to the request epoch,
// so a loss-adjusted receipt pays at par and freezes later claimants.
contract LossEpochSlotMismatch is Test {
    IdleCDOEpochVariant cdo;
    IdleCreditVault vault;
    IERC20Detailed underlying;

    address manager = /* manager */;
    address borrower = /* borrower */;
    address alice = makeAddr("alice");
    address bob   = makeAddr("bob");

    function testLossReceiptClaimsAtPar() public {
        // --- setup: KYC'd alice and bob each deposit 1000 into AA during buffer ---
        uint256 amt = 1_000e18;
        dealCdo(address(underlying), alice, amt);
        dealCdo(address(underlying), bob, amt);
        vm.prank(alice); cdo.depositAA(amt);
        vm.prank(bob);   cdo.depositAA(amt);

        // --- both request withdraw in epoch N (buffer of next epoch) ---
        uint256 epochN = vault.epochNumber();
        vm.prank(alice); cdo.requestWithdraw(0, address(cdo.AATranche()));
        vm.prank(bob);   cdo.requestWithdraw(0, address(cdo.AATranche()));
        assertEq(vault.lastWithdrawRequest(alice), epochN);

        // --- epoch runs; at stopEpoch borrower repays with a 50% loss on pending ---
        vm.prank(manager); cdo.startEpoch();
        vm.warp(cdo.epochEndDate() + 1);

        uint256 pending = vault.pendingWithdraws();
        // borrower repays only enough to cover active LPs + half of pending
        uint256 repay = /* expected funds - pending/2 */;
        deal(address(underlying), borrower, repay);

        vm.prank(manager);
        cdo.stopEpochWithDuration(repay, /* duration */, pending / 2); // _lossAmount hits pending bucket

        // haircut was stored under epochNumber (N+1) after deposit() bumped it,
        // while alice/bob receipts live under epoch N:
        assertEq(vault.lossRecoveryPriceByEpoch(epochN), 0);          // receipt's epoch: no haircut
        assertGt(vault.lossRecoveryPriceByEpoch(epochN + 1), 0);      // orphaned haircut slot

        // --- alice claims first and is paid AT PAR despite the 50% haircut ---
        uint256 aliceBasis = vault.withdrawsRequests(alice);
        uint256 balPre = underlying.balanceOf(alice);
        vm.prank(alice); cdo.claimWithdrawRequest();
        assertEq(underlying.balanceOf(alice) - balPre, aliceBasis);   // paid 100%, expected 50%

        // --- bob's identical claim now reverts: vault is drained ---
        vm.prank(bob);
        vm.expectRevert();
        cdo.claimWithdrawRequest();                                   // permanently frozen
    }
}
```

Note: the PoC assumes `stopEpoch`'s repayment `deposit()` executes before `collectWithdrawFunds()` inside the same call — matching `deposit()`'s `isEpochRunning()` bump branch — which I could not fully re-verify line-by-line in the remaining budget; if the CDO bumps `epochNumber` strictly after funding pending receipts, the slot is consistent and this finding does not hold.
