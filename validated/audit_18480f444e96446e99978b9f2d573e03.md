### Title
Post-default withdraw receipts are paid at par from the recovery reserve, letting tranche holders bypass the default haircut and drain funds owed to defaulted-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
After `finalizeDefaultRecovery` crystallizes a `defaultRecoveryPrice < 1e18`, a holder of AA/BB tranche tokens can call `requestWithdraw`, receive a receipt priced at the already-haircut `virtualPrice`, and then claim it **at par (1:1)** through `_claimPostDefaultWithdrawRequest`, which pays out of `defaultRecoveryReserve` — the same reserve that was sized only to pay defaulted-epoch receipts at the `recoveryPrice` ratio. Each such claim consumes reserve that belongs to defaulted claimants, so the attacker extracts more than their fair recovery share and leaves earlier claimants unable to withdraw.

### Finding Description
Type-confusion analog: two different *classes* of receipts are treated as interchangeable claims on the same underlying pool.

- When the CDO reports a borrower default, `finalizeDefaultRecovery` computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` where `totalBasis` covers active LPs plus default-epoch pending receipts only (`defaultPendingClaimBasis` = `pendingWithdraws` + current-epoch instant claims). Nothing in the reserve accounts for *future* post-default requests. [1](#0-0) 

- Post-finalization, `requestWithdraw` mints the user a receipt for `_amount` (computed by the CDO at the haircut `virtualPrice`) and records `postDefaultRequests[_user] = _amount`, deliberately **not** increasing `pendingWithdraws`, so no borrower funding is ever collected for it (`collectWithdrawFunds` only funds `pendingWithdraws`). [2](#0-1) 

- `claimWithdrawRequest` then routes to `_claimPostDefaultWithdrawRequest`, which pays `amount` **1:1** via `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve`. [3](#0-2) [4](#0-3) 

So a post-default requester receives `virtualPrice_post * trancheAmount` paid at par, while a defaulted-epoch receipt holder receives `claimBasis * recoveryPrice / 1e18`. When `recoveryPrice < 1`, the post-default receipt is systematically paid more per unit of basis, and the two receipt types share one finite reserve.

Broken invariant: **one receipt, one proportional payout** — claims of different vintages draw from a reserve sized only for the defaulted basis, so post-default claims steal defaulted claimants' recovery.

### Impact Explanation
Direct theft of unclaimed recovery funds, quantified: if `recoveryPrice = 0.5e18` and `defaultRecoveryReserve = R`, an attacker holding tranche tokens worth `X` of post-haircut NAV can request a withdrawal and claim `X` underlying from the reserve, whereas the same economic position held as a defaulted receipt would entitle them only to `X * recoveryPrice`-equivalent treatment at finalization. Every unit withdrawn this way reduces `defaultRecoveryReserve`, so once enough post-default claims are processed, `_transferDefaultRecovery` underflows and remaining defaulted/post-default claimants' transactions revert — permanent loss of their unclaimed recovery up to the full reserve.

### Likelihood Explanation
- Attacker requirements: any tranche-token holder (AA or BB) after a default is finalized — an explicitly in-scope unprivileged actor. No privileged role needed.
- Preconditions: borrower default followed by `finalizeDefaultRecovery` with `defaultRecoveryPrice < 1e18` and non-zero `defaultRecoveryReserve`. Partial-recovery defaults are exactly the scenario this machinery was built for.
- No existing guard stops it: `requestWithdraw` post-finalization only reverts if the user already has an open request/instant/postDefault receipt; `_transferDefaultRecovery` does not distinguish reserve belonging to defaulted claimants from post-default ones; `_transferFundedClaim`'s reserve guard does not apply because payment goes through `_transferDefaultRecovery`.
- The attacker can scale the theft by acquiring tranche tokens cheaply post-default (tranche tokens themselves are transferable) up to the entire remaining reserve.

### Recommendation
Do not pay post-default receipts out of `defaultRecoveryReserve`. Either:
1. Track post-default requests in a separate funded bucket: add `postDefaultRequests` to a `pendingPostDefaultWithdraws` counter that `collectWithdrawFunds`/stopEpoch must source from borrower repayments, and pay them via `_transferFundedClaim` (whose reserve guard already prevents spending recovery funds); or
2. If they must draw on the reserve, fund the reserve for them at request time — e.g., require the CDO to transfer the haircut `_amount` into the strategy and add it to `defaultRecoveryReserve` when the post-default request is created — so claims remain self-funded and cannot dilute defaulted claimants.

Additionally, consider reverting `requestWithdraw` entirely while `defaultRecoveryFinalized` if the CDO never re-enters a running epoch, since there is no funding path for these receipts.

### Proof of Concept
Foundry fork-style test against `IdleCreditVault` + `IdleCDOEpochVariant` (existing harness in `test/foundry/` provides the deployment pattern):

```solidity
// test/foundry/PostDefaultReserveDrain.t.sol
function testPostDefaultClaimDrainsRecoveryReserve() public {
    // --- setup: victim deposits, epoch runs ---
    _depositWithUser(victim, 1_000e6);          // victim holds tranche tokens
    _depositWithUser(attacker, 1_000e6);        // attacker holds tranche tokens
    vm.prank(manager); cdoEpoch.startEpoch();

    // victim requests a normal withdraw during the epoch -> pending receipt
    _requestWithdrawWithUser(victim, tranche.balanceOf(victim));

    // --- borrower defaults; partial recovery is finalized ---
    // (CDO: _handleBorrowerDefault, then finalizeDefaultRecovery pulling e.g. 50% of basis)
    _finalizeDefaultWithRecovery(0.5e18);       // defaultRecoveryPrice == 0.5e18

    uint256 reserveBefore = strategy.defaultRecoveryReserve();
    assertGt(reserveBefore, 0);
    assertLt(strategy.defaultRecoveryPrice(), 1e18);

    // --- attacker requests a withdraw AFTER finalization ---
    uint256 atkTranche = tranche.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attacker /* via CDO path, amount priced at haircut virtualPrice */);
    uint256 postAmt = strategy.postDefaultRequests(attacker);
    assertGt(postAmt, 0);

    // --- attacker claims at par, from the recovery reserve ---
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();            // routes to _claimPostDefaultWithdrawRequest
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // attacker received postAmt * 1.0 instead of postAmt * recoveryPrice
    assertEq(got, postAmt);
    assertGt(got, postAmt * strategy.defaultRecoveryPrice() / 1e18);

    // --- victim's defaulted receipt is now under-collateralized ---
    // victim claim pays claimBasis * recoveryPrice; after enough attacker claims the
    // reserve is exhausted and the victim's claim reverts / pays less than entitled:
    // vm.expectRevert(); cdoEpoch.claimWithdrawRequest(victim)  (defaultRecoveryReserve underflow)
    assertLt(strategy.defaultRecoveryReserve(), reserveBefore - postAmt + 1);
}
```

Key assertions demonstrating the theft: (1) the attacker is paid at par despite `defaultRecoveryPrice < 1`, and (2) `defaultRecoveryReserve` decreases by the full par amount even though `totalBasis` — and therefore the reserve — never accounted for post-default requests, so the last defaulted claimants cannot be paid.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }

  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
