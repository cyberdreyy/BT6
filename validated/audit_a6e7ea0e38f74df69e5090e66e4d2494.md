### Title
Stale per-epoch instant-withdraw ledger permanently freezes user receipts after default (`claimInstantWithdrawRequest` never clears `instantWithdrawsRequestsByEpoch`) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to a resource that is allocated but never released on the consuming path (the kernel's missing `v4l2_ctrl_handler_free`), `claimInstantWithdrawRequest` consumes an instant-withdraw receipt but only clears the aggregate `instantWithdrawsRequests[_user]`. It never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. After a borrower default, `_claimDefaultedInstantWithdrawRequest` re-reads that stale per-epoch entry, computes a `claimBasis` larger than the user's remaining aggregate receipt, and the `instantWithdrawsRequests[_user] -= claimBasis` subtraction underflows, permanently reverting every claim for that user — including legitimately unclaimed instant receipts and post-default balances.

### Finding Description
`requestInstantWithdraw` records the receipt in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . The funded-claim path clears only the first of these [2](#0-1) . The default-recovery path, however, derives `claimBasis` solely from the per-epoch entry [3](#0-2) .

### Impact Explanation
Attack scenario (attacker is an unprivileged tranche-token holder):

1. Epoch N is running with `allowInstantWithdraw` enabled. Attacker requests instant withdraw of `X` via `IdleCDOEpochVariant` → vault records `instantWithdrawsRequestsByEpoch[attacker][N] = X`.
2. Funds are collected at epoch start; attacker calls `claimInstantWithdrawRequest()` on the CDO. Vault pays `X`, sets `instantWithdrawsRequests[attacker] = 0`, but leaves `instantWithdrawsRequestsByEpoch[attacker][N] = X` — the stale "unfreed" entry.
3. Attacker requests another instant withdraw of `Y` in the same epoch N (`requestInstantWithdraw` has no existing-request guard in the pre-default path). Now `instantWithdrawsRequestsByEpoch[attacker][N] = X + Y` while the true outstanding aggregate is `Y`.
4. Borrower repays only partially / defaults at stop; `finalizeDefault` / `finalizeDefaultRecovery` set `defaultRecoveryEpoch = N` and `defaultInstantWithdrawsFinalized = true`.
5. Any subsequent `claimInstantWithdrawRequest(attacker)` reaches `_claimDefaultedInstantWithdrawRequest`, which computes `claimBasis = X + Y` and executes `instantWithdrawsRequests[attacker] -= claimBasis` → `Y - (X + Y)` underflows and reverts [4](#0-3) .

Result: the attacker's own `Y` receipt and any older funded receipts are permanently frozen, and more importantly the same poisoned `instantWithdrawClaimsByEpoch[N]`/`pendingInstantWithdraws` accounting is corrupted for the recovery waterfall — the guard at line 385 forces this revert on *every* claim call for that user, so no recovery path remains. The attacker can also weaponize this against the recovery reserve: because `claimBasis` is inflated by already-paid `X`, had the user retained a large enough aggregate the stale basis would over-draw `defaultRecoveryReserve`, shrinking `defaultRecoveryPrice`-denominated payouts for honest defaulted claimants.

### Likelihood Explanation
Requires `allowInstantWithdraw`, a same-epoch re-request after a claim, and a borrower default in that epoch — all reachable by an unprivileged KYC'd lender with no privileged cooperation. The missing cleanup is unconditional in the code path.

### Recommendation
In `claimInstantWithdrawRequest`, mirror the default-claim cleanup: for each epoch the user claimed (track or iterate the funded epoch), zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` alongside `instantWithdrawsRequests[_user]`, so the per-epoch ledger and the aggregate never diverge.

### Proof of Concept
Foundry fork PoC (pseudocode against existing harness in `test/foundry/IdleCDOEpochQueue.t.sol` style):

```solidity
// epoch N running, allowInstantWithdraw == true
cdoEpoch.requestInstantWithdraw(X, tranche);   // attacker
// ... startEpoch funding collected ...
cdoEpoch.claimInstantWithdrawRequest();        // attacker paid X; per-epoch entry stale
cdoEpoch.requestInstantWithdraw(Y, tranche);   // attacker, same epoch N
// borrower defaults at stopEpoch -> finalizeDefault / finalizeDefaultRecovery
// defaultRecoveryEpoch == N, defaultInstantWithdrawsFinalized == true
vm.expectRevert(); // arithmetic underflow at instantWithdrawsRequests -= claimBasis
cdoEpoch.claimInstantWithdrawRequest();        // attacker's legitimate Y now unclaimable
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
```
