### Title
Permissionless revolving-vault factory accepts attacker-controlled ERC4626 valuation sources - ([File: contracts/IdleCreditVaultFactory.sol](contracts/IdleCreditVaultFactory.sol))

### Summary
`deployRevolvingCreditVault` is permissionless and accepts a caller-supplied ERC4626 vault without any allowlist or validation beyond matching `asset()`. An unprivileged attacker can therefore deploy a vault with a malicious vault contract, attract honest lender deposits, and let the honest manager operate the normal epoch flow. The malicious vault reports an inflated `convertToAssets()` value, causing `ProgrammableBorrower.totalInterestDueNow()` to mint fictitious strategy-token interest. The attacker then exits through the normal withdrawal flow and drains the real underlying held by the malicious vault.

### Finding Description
`ProgrammableBorrowerParams.vault` is supplied directly by the caller, and `deployRevolvingCreditVault` has no caller authentication or vault allowlist. [1](#0-0) [2](#0-1) 

`ProgrammableBorrower.initialize` rejects only a zero vault or a vault whose `asset()` differs from the credit-vault underlying. It does not verify that the vault is trusted or economically safe. [3](#0-2) 

During `startEpoch`, pool underlyings are sent to the programmable borrower, which deposits its entire idle balance into the configured vault. [4](#0-3) [5](#0-4) 

The configured vault is the accounting oracle: its `convertToAssets()` result determines `vaultInterestAccrued()`, `vaultLoss()`, and `totalInterestDueNow()`. [6](#0-5) [7](#0-6) 

In programmable mode, the credit vault treats `totalInterestDueNow()` as the authoritative epoch result and mints unbacked strategy tokens for that reported gain. [8](#0-7) [9](#0-8) [10](#0-9) 

The attack sequence is:

1. The attacker deploys a malicious ERC4626-like contract whose `asset()` is the pool underlying but whose `convertToAssets()` returns a manipulated value.
2. The attacker calls `deployRevolvingCreditVault` using honest implementations, an honest manager, an honest borrower, and the malicious vault.
3. The attacker and a victim each deposit through `depositAA`.
4. The honest manager calls `startEpoch`; all deposited underlying is deposited into the attacker-controlled vault.
5. The malicious vault reports, for example, twice the actual assets.
6. The honest manager calls `stopEpoch`; the fake delta is minted as strategy-token interest and raises tranche prices.
7. The attacker requests withdrawal during the buffer.
8. The honest manager starts and stops the next epoch; `onStopEpoch` withdraws the attacker's inflated claim from the malicious vault.
9. The malicious vault pays the attacker with the pool's real underlying.
10. The victim retains tranche tokens or receipts backed primarily by phantom accounting and cannot be paid in full.

This preserves honest privileged behavior: the attacker is only the permissionless factory caller, a lender, and the operator of the externally supplied vault contract.

### Impact Explanation
The attacker converts the honest pool's real deposits into an inflated withdrawal claim. With equal attacker and victim deposits, a manipulated valuation near twice the real value lets the attacker claim approximately the entire real vault balance, stealing almost all of the victim's principal rather than merely extracting profit from the attacker's own deposit.

The broken invariant is fair mint/burn and solvency: strategy tokens and tranche NAV are minted from an unbacked external valuation, while redemption later consumes real underlying. The skim guard does not prevent this because the funds are not unsolicited CDO donations; they are intentionally deposited into the configured vault. The default path also does not prevent the theft because the malicious vault can satisfy the attacker's first withdrawal before becoming insolvent.

### Likelihood Explanation
Deployment requires no protocol privilege, and the attacker can configure the pool with legitimate implementations, an honest manager, an honest borrower, and compatible Keyring parameters. The main requirement is attracting victim liquidity or routing an integration through the deployed vault, which is the same deployment-risk pattern described by the external report. Once deposits exist, the honest manager's ordinary `startEpoch` and `stopEpoch` calls execute the attack.

### Recommendation
Maintain an owner- or governance-controlled allowlist of approved ERC4626 vaults in `IdleCreditVaultFactory.deployRevolvingCreditVault`. Reject any `programmableBorrowerParams.vault` not on the list. `ProgrammableBorrower.setVault` should also be restricted to the same allowlist so the vault valuation source cannot later be replaced with an unreviewed contract.

If vault implementations must remain permissionless, the factory should at minimum enforce:

- approved vault address or implementation hash;
- compatible `asset()`;
- bounded valuation changes;
- withdrawal-liquidity validation;
- explicit integration-specific risk review before enabling deposits.

import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {TransparentUpgradeableProxy} from "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";

import {ProgrammableBorrower} from "../contracts/strategies/idle/ProgrammableBorrower.sol";

contract MaliciousValuationVault is ERC20 {
    ERC20 public immutable assetToken;
    uint256 public quoteMultiplier = 1;

    constructor(address asset_) ERC20("evil share", "EVIL") {
        assetToken = ERC20(asset_);
    }

    function asset() external view returns (address) {
        return address(assetToken);
    }

    function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
        shares = assets;
        assetToken.transferFrom(msg.sender, address(this), assets);
        _mint(receiver, shares);
    }

    function convertToAssets(uint256 shares) external view returns (uint256) {
        // Attacker-controlled valuation source.
        return shares * quoteMultiplier;
    }

    function withdraw(uint256 assets, address receiver, address owner) external returns (uint256) {
        uint256 shares = balanceOf(owner);
        _burn(owner, shares);

        // Pay the first withdrawal from the real underlying that honest depositors supplied.
        assetToken.transfer(receiver, assets);
        return shares;
    }

    function redeem(uint256 shares, address receiver, address owner) external returns (uint256) {
        uint256 assets = convertToAssets(shares);
        _burn(owner, shares);
        assetToken.transfer(receiver, assets);
        return assets;
    }

    function setQuoteMultiplier(uint256 multiplier) external {
        quoteMultiplier = multiplier;
    }
}

        ERC20 underlying = new ERC20("USDC", "USDC");

        MaliciousValuationVault evilVault =

        IdleCreditVaultFactory factoryImpl = new IdleCreditVaultFactory();

            cv.tranchePrice(aaTranche),
            1e18,
            "remaining tranche price still reflects inflated accounting"
        );
