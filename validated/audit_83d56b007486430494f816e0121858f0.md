### Title
Loss-adjusted withdraw receipts are keyed to the wrong epoch in `collectWithdrawFunds`, making funded claims unpayable or drained at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the external "wrong namespace on commit" bug, `IdleCreditVault.collectWithdrawFunds` commits the per-epoch loss-recovery price under `epochNumber`, while user receipts were recorded (and later looked up) under `lastWithdrawRequest[user]`, the epoch value at request time. Because `deposit()` increments `epochNumber` mid-`stopEpoch`, the write key and the read key are different epochs, so `lossRecoveryPriceByEpoch` is stored under a namespace the claim path never reads.

### Finding Description
Withdraw receipts are keyed at request time: `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` where `currentEpoch = epochNumber` (`IdleCreditVault.sol:260-293`). Claims later resolve the haircut via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` in `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:790-791`).

However, `epochNumber` is advanced inside `deposit()` whenever `isEpochRunning()` is true — i.e., during the `stopEpoch` funding deposit ("deposit done on stopEpoch ... epochNumber += 1", `IdleCreditVault.sol:607-610`). `collectWithdrawFunds` is the function that books the realized loss for pending receipts, and it writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` using the post-increment value (`IdleCreditVault.sol:417-421`). The loss price is therefore committed under epoch N+1 while every affected receipt is stored under epoch N — the same write-namespace ≠ read-namespace defect class as the `replaceKeyNamespace(BYTES32, key)` vs `BOOL` bug.

### Impact Explanation
When a `stopEpochWithDuration(_lossAmount)` haircut is applied, `collectWithdrawFunds` collects only `_amount < pendingBasis`, sets `pendingWithdraws = 0`, and stores `lossRecoveryPrice` under the wrong epoch key. On claim:

- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lossEpoch]` = 0 and returns early (`IdleCreditVault.sol:791-795`).
- The funded-claim path then pays `withdrawsRequests[_user]` **at par** via `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:338-349`), because the gate `epochNumber <= lastWithdrawRequest[_user]` is already satisfied (N+1 > N).

But the strategy only holds the haircutted amount. First claimants drain the funded pool at full value; later claimants' transfers revert/short-pay, socializing the entire haircut onto the tail of the queue — or, if the haircut is large, all receipts are effectively unbacked. This breaks the loss-waterfall invariant: a loss meant to be shared pro rata across pending receipts is instead concentrated on whoever claims last, with quantified loss equal to `pendingBasis - _amount` shifted onto late claimers. No guard stops this: `defaultRecoveryInitialized` passes, the `NotAllowed` reverts are all keyed off the same mismatched mappings, and `_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve`, not haircutted pools.

### Likelihood Explanation
The trigger requires only honest privileged sequencing: a manager calling `stopEpochWithDuration` with `_lossAmount > 0` while `pendingWithdraws != 0` — a normal, expected code path for realized losses (the entire `previewLossAdjustedWithdrawFunds` / `lossRecoveryPriceByEpoch` machinery exists for it). The attacker is any unprivileged lender with a pending withdraw receipt: claiming before others extracts more than the fair post-loss share, at the direct expense of other receipt holders. The defect depends on `collectWithdrawFunds` executing after the epoch-incrementing `deposit()` within `stopEpoch`; since `collectWithdrawFunds` pulls underlying via `transferFrom(idleCDO, ...)`, the CDO must already hold the borrower-funded amount, which is delivered through the same stopEpoch deposit flow that bumps `epochNumber`. If the integrator's `stopEpoch` orders collection before that deposit, the keys coincide and the path works — this ordering is the determining factor and should be verified against `IdleCDOEpochVariant.stopEpoch`.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the receipts' request epoch, not the post-increment counter. Either write `lossRecoveryPriceByEpoch[epochNumber - 1]` inside `collectWithdrawFunds` (when it runs after the epoch bump), or pass the claim epoch explicitly from the CDO, or increment `epochNumber` only after all pending-receipt accounting is finalized. Add a regression test: request withdraw in epoch N → `stopEpochWithDuration(loss)` → assert `lossRecoveryPriceByEpoch[N] != 0` and that two receipt holders each recover exactly `basis * price / 1e18`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

// Fork test sketch (extend test/foundry/IdleCreditVault.t.sol harness):
function testLossReceiptKeyedToWrongEpoch() external {
    // 1. Two KYC'd users deposit into AA during buffer, then epoch runs.
    address alice = makeAddr('alice');
    address bob   = makeAddr('bob');
    _depositWithUser(alice, 100_000 * ONE_SCALE, true);
    _depositWithUser(bob,   100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // 2. Both request withdraw during epoch N (epochNumber == N).
    uint256 epochN = creditVault.epochNumber();
    vm.prank(alice); cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(bob);   cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(creditVault.lastWithdrawRequest(alice), epochN);
    assertEq(creditVault.lastWithdrawRequest(bob),   epochN);

    // 3. Borrower partially repays; manager stops epoch with a realized loss.
    //    Internally: strategy.deposit(...) runs while isEpochRunning() =>
    //    epochNumber becomes N+1 BEFORE collectWithdrawFunds writes the price.
    deal(defaultUnderlying, borrower, partialRepayAmount);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, lossAmount); // collectWithdrawFunds(haircutAmount)

    // 4. BUG: price committed under N+1, receipts keyed under N.
    assertEq(creditVault.lossRecoveryPriceByEpoch(epochN),     0);        // read key
    assertGt(creditVault.lossRecoveryPriceByEpoch(epochN + 1), 0);        // write key

    // 5. Alice claims FIRST and is paid at PAR (no haircut applied),
    //    draining the underfunded pool.
    uint256 pre = underlying.balanceOf(alice);
    vm.prank(alice);
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(alice) - pre, fundedAmount / 2); // > fair share

    // 6. Bob's identical receipt now reverts or short-pays:
    //    the haircut was fully socialized onto him.
    vm.prank(bob);
    vm.expectRevert(); // insufficient strategy balance / NotAllowed
    cdoEpoch.claimWithdrawRequest();
}
```

Note: the PoC assumes `stopEpoch`/`stopEpochWithDuration` in `IdleCDOEpochVariant` calls `collectWithdrawFunds` after the epoch-incrementing `strategy.deposit(...)`. If ordering places collection before the increment, the keys coincide and the issue does not trigger — that ordering in `contracts/IdleCDOEpochVariant.sol` should be confirmed before relying on this finding.
