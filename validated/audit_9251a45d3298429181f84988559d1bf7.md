### Title
Gateway `ProcessRequest` routes legacy requests to a target DON's handler without validating that the message signer belongs to that DON's allowlist - ([File: core/services/gateway/gateway.go])

### Finding Description
`Gateway.ProcessRequest` in `core/services/gateway/gateway.go` (`func (g *gateway) ProcessRequest`, lines 218-292) looks up a handler purely by `msg.Body.DonId`: it calls `msg.Validate()` and then `h, ok = g.handlers[handlerKey]` where `handlerKey = msg.Body.DonId` [1](#0-0) . `Message.Validate()` (`core/services/gateway/api/message.go`, lines 54-88) only checks field-length/format constraints and calls `ExtractSigner()` to populate `m.Body.Sender` from the ECDSA signature — it never checks whether the recovered signer is a member of the DON identified by `m.Body.DonId` [2](#0-1) .

The request is then forwarded via `h.HandleLegacyUserMessage(ctx, msg, callback)`. In the capabilities handler (`core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage`), the code explicitly notes this gap with `// TODO: apply allowlist and rate-limiting here` (line 384) right before it validates only the method name, then forwards the message to **all** members of `h.donConfig.Members` regardless of who signed it [3](#0-2) . Nowhere in this path is `msg.Body.Sender` compared against the target DON's configured member/owner allowlist before dispatch.

So an attacker who signs a syntactically valid message with any private key (not necessarily belonging to any node/owner authorized for the target DON) and sets `DonId` to a real, configured DON ID will have `ProcessRequest` successfully route the request to that DON's handler and onward to all of that DON's nodes — the `TestGateway_ProcessRequest_IncorrectDonId` test only covers the case of an *unknown* DON ID (`gw.ProcessRequest` returning `Unsupported DON ID`), not the case of a *valid* DON ID with an unauthorized signer [4](#0-3) .

### Impact Explanation
This is a request-to-DON binding / authorization confusion: any external attacker able to reach the gateway's user-facing HTTP endpoint can submit signed messages that get delivered to a specific target DON's node set, even though their signing key is not part of that DON's allowlist. Depending on the handler/method (e.g. `web_api_trigger`), this can trigger unauthorized job/workflow execution on nodes belonging to a DON the attacker has no legitimate relationship to — matching the "unauthorized job run" / "allowlist bypass" bounty impact class. The impact is scoped to legacy-message handlers that route by `DonId` without per-sender allowlist checks (confirmed for the capabilities handler); other handlers using the same `HandleLegacyUserMessage` pattern would be equally exposed unless they separately enforce sender allowlisting (not found in the reviewed code).

### Likelihood Explanation
Requires only the ability to send an HTTP POST to the gateway's public request endpoint (unauthenticated capability, matching the allowed attacker profile) plus knowledge of a valid target `DonId` (DON IDs are not secret — they're part of routing config) and any ECDSA keypair to sign the message. No node, admin, or DON membership is required. This is trivially repeatable — the existing `newSignedLegacyRequest` test helper in `gateway_test.go` already demonstrates how to construct such signed requests with an arbitrary key.

### Recommendation
In `HandleLegacyUserMessage` (and any other handler implementing the same interface), verify `msg.Body.Sender` against the target DON's configured allowlist (e.g., `donConfig.Members` or an explicit permitted-senders list) before dispatching to nodes, rejecting with an authorization error if the signer is not permitted for that DON. Remove/resolve the `// TODO: apply allowlist and rate-limiting here` gap explicitly.

### Proof of Concept
Extend `core/services/gateway/gateway_test.go`:
1. Configure `newGatewayWithMockHandler`/DON config for `"testDON"` with a known allowlist of node/owner addresses (as in existing tests).
2. Generate a new, unrelated ECDSA keypair not present in `testDON`'s member/allowlist config.
3. Build a legacy request via `newSignedLegacyRequest(t, "abc", "request", "testDON", payload)` but sign it using the unrelated keypair instead of an allowlisted key.
4. Call `gw.ProcessRequest(t.Context(), req, "")`.
5. Assert the response is an authorization-failure error (e.g., `api.HandlerError`/403-equivalent) and that the mock handler's `HandleLegacyUserMessage`/`don.SendToNode` was **never** invoked — instead of the current behavior where routing proceeds successfully to the handler.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
