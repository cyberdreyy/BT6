### Title
Node-lag race in `check_parent_tenure_choice`'s empty-tenure branch bypasses the timing gate and permits superseding a tenure that actually produced a canonical, globally-accepted block - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a new tenure's chosen parent legitimately reorgs an earlier tenure. When the queried node reports `tenure.first_block_mined == None` for a reorged tenure, the function unconditionally pushes that tenure into `superseded_tenures` and later calls `record_superseded_tenure`, skipping entirely the timing check (`first_proposal_burn_block_timing`) that is otherwise mandatory for tenures that produced exactly one globally-accepted block. Because a tenure can be locally recorded as having exactly one globally-accepted block (`get_globally_accepted_block_count_in_tenure` == 1, which passes the `> 1` guard) while the specific node queried via `get_tenure_forking_info` has not yet ingested that block, the signer can supersede a tenure whose block is in fact canonical, without ever checking whether the reorg attempt was "poorly timed."

### Finding Description
The vulnerable branch: [1](#0-0) 

The guard at lines 210-223 only rejects a reorg attempt outright when the *signer's own* `signerdb` shows `globally_accepted_blocks > 1` for the reorged tenure — this is purely local state, independent of what the remote node has processed. If the local count is `0` or `1`, execution proceeds to the `first_block_mined` check, which is populated by `client.get_tenure_forking_info` — i.e., derived from whatever a specific stacks-node has processed so far: [2](#0-1) 

When `first_block_mined` is `None`, the code takes the fast path — it appends the tenure directly to `superseded_tenures` with no timing analysis at all. Contrast this with the `Some(first_block_mined)` path just below, which requires local knowledge via `get_first_approved_block_in_tenure` and computes `proposal_to_sortition` against `first_proposal_burn_block_timing` before permitting the same supersession (lines 234-288). That timing check exists precisely to stop a reorg of a tenure whose first (and only) block was *not* poorly timed — i.e., a legitimately-produced canonical block.

The code's own comment acknowledges the race ("We may still hold a signature over a block in it that the node has never seen... because a block we accept locally is not handed to the node until the whole signer set has signed it") but treats it as harmless. This reasoning assumes that `first_block_mined == None` implies the block has *not yet reached full signer-set (globally-accepted) status*. That assumption does not hold across the boundary between "signer-side globally accepted" and "node has ingested/processed the block," which are two distinct, asynchronous events. A tenure can have `get_globally_accepted_block_count_in_tenure == 1` locally (full threshold reached) while the specific node being queried for `get_tenure_forking_info` has not yet processed/indexed that block — landing exactly on the fast, unconditional supersede path and skipping the timing gate that the `Some` branch enforces for otherwise-identical single-block tenures.

`record_superseded_tenure` then calls `SignerDb::mark_tenure_superseded`, which is documented to void the conflict-blocking effect of a prior signature on that tenure's block: [3](#0-2) 

### Impact Explanation
This breaks the chain-safety guarantee that a signer will not sign a block that reorgs a tenure whose canonical, globally-accepted block was not "poorly timed." Once the tenure is marked superseded, the earlier signature on its (real, canonical) block stops counting as a conflict, and the signer becomes willing to sign a competing/reorging proposal for the new tenure. This matches the "Critical" category: a signer signing a conflicting/non-canonical block, enabling a chain split that the timing rule was specifically designed to disallow. The window is repeatable whenever the race condition (node lag vs. local global-acceptance bookkeeping) recurs.

### Likelihood Explanation
The attacker needs only to win a single sortition slot (their own BTC, as permitted) and craft a `BlockProposal`/`TenureChange` whose parent tenure reorgs an earlier tenure. The exploit's success additionally depends on a timing race outside the attacker's direct control — the specific node queried by the victim signer must not yet have processed the earlier tenure's sole block when `get_tenure_forking_info` is called, even though that signer's local `signerdb` already counts it as globally accepted (count == 1, so the `> 1` reject at line 213 doesn't trigger). This window can plausibly occur around tenure/burn-block boundaries when block dissemination to the node lags signer-to-signer consensus propagation, making it a feasible, if probabilistic, race rather than a fully deterministic one-shot exploit.

### Recommendation
Before taking the `first_block_mined == None` fast path, cross-check against local signerdb state (e.g. `get_first_approved_block_in_tenure` / `get_globally_accepted_block_count_in_tenure`) to determine if a block for that tenure has already been signed/accepted locally. If local state shows a globally-accepted or approved block for that tenure, treat it the same as the `Some(first_block_mined)` branch and require the `first_proposal_burn_block_timing` check (or reject the reorg) instead of unconditionally superseding it merely because the queried node has not yet caught up.

### Proof of Concept
Rust test plan (in `stacks-signer/src/chainstate/tests/`):
1. Set up a `SignerDb` where tenure `T1` has a block that reached `globally_accepted_blocks == 1` (via `get_first_approved_block_in_tenure`/insert with `BlockState::GloballyAccepted`, `approved_time` set well after `sortition_state_received_time - first_proposal_burn_block_timing` so it is *not* poorly timed).
2. Mock `StacksClient::get_tenure_forking_info` to return a `TenureForkingInfo` entry for `T1` with `first_block_mined: None` (simulating node lag) even though signerdb has full local knowledge.
3. Call `check_parent_tenure_choice` for a new sortition whose `parent_tenure_id` bypasses `T1`.
4. Assert: with `first_block_mined: None`, the call returns `Ok(true)` and `T1` is marked superseded via `mark_tenure_superseded` — even though replaying the same scenario with `first_block_mined: Some(block_id)` (and identical timing, not poorly timed) would return `Ok(false)`.
5. This asymmetry (`None` -> always permitted; `Some` -> gated by timing) for an otherwise identical locally-globally-accepted block demonstrates the bypass.
