### Title
User enumeration via distinct error messages/timing in `CreateSession` - ([File: core/sessions/localauth/orm.go])

### Summary
`CreateSession` in `core/sessions/localauth/orm.go` performs `FindUser` first and returns the raw lookup error (e.g. a DB "no rows" error) immediately for a non‑existent email, but returns a distinct, hardcoded `"Invalid password"` error for an existing email with a wrong password. `SessionsController.Create` forwards this error verbatim to the HTTP client via `jsonAPIError(c, http.StatusUnauthorized, err)`, giving an unauthenticated caller a direct oracle to distinguish valid from invalid emails.

### Finding Description
The flow is: unauthenticated `POST /sessions` → `SessionsController.Create` (`core/web/sessions_controller.go:56`) → `AuthenticationProvider().CreateSession(ctx, sr)` → `orm.CreateSession` (`core/sessions/localauth/orm.go:144`).

Inside `CreateSession`:
- `user, err := o.FindUser(ctx, sr.Email)` (line 145) — if the email does not exist, this returns the underlying SQL error (not a generic "Invalid email"/"Invalid password" message), and the function returns immediately with `return "", err` (lines 146–148).
- If the email exists, execution proceeds to `utils.CheckPasswordHash` (line 159); on mismatch it returns the distinct string `"Invalid password"` (line 161).
- The "Invalid email" branch (lines 154–157) via `constantTimeEmailCompare` is effectively dead code for typical mismatches, since `FindUser`'s SQL (`WHERE lower(email) = lower($1)`) already guarantees any returned `user.Email` matches `sr.Email` case-insensitively.

`SessionsController.Create` (`core/web/sessions_controller.go:56-60`) does not normalize or replace this error before sending it to the client — it calls `jsonAPIError(c, http.StatusUnauthorized, err)` directly with whatever `CreateSession` returned. This means an attacker can distinguish:
- Non-existent email → raw DB error (e.g., "sql: no rows in result set" or similar wrapped error).
- Existing email + wrong password → `"Invalid password"`.

This is a response-content oracle (not merely a timing side channel), which is strictly stronger and more reliable than the timing-only scenario described in the question. Additionally, the code paths differ in work performed (extra bcrypt hash check plus `GetUserWebAuthn` query for valid emails), which also creates a secondary timing difference, compounding the enumeration primitive.

No authentication middleware protects `/sessions` (it is the login endpoint itself, unauthenticated by design), and no generic-error normalization exists between `orm.CreateSession` and `SessionsController.Create` to suppress the distinction.

### Impact Explanation
This enables account/email enumeration against the node's local-auth login endpoint by any unauthenticated network client. This falls under the "authentication soundness" class — while it does not by itself bypass authentication, it materially assists targeted credential-stuffing, password-spraying, or MFA-bypass attempts against confirmed valid admin/API accounts on the Chainlink node's web UI, which controls funds, jobs, and keys. Impact is scoped to information disclosure (enumeration) rather than direct compromise.

### Likelihood Explanation
No preconditions or credentials are required — this is exploitable by any unauthenticated client capable of sending `POST /sessions` requests. It's a repeatable, low-cost binary oracle (differing JSON error body) rather than requiring precise timing measurement, making it trivially and reliably exploitable in any deployment exposing the node's login endpoint to a network the attacker can reach.

### Recommendation
Normalize authentication failures in `orm.CreateSession` (and ensure `SessionsController.Create` does not leak the underlying error) so that "email not found" and "wrong password" return the same generic message (e.g., `"invalid credentials"`) with the same error type before any further checks, and ensure processing time is equalized (e.g., always execute a constant-time or dummy password hash comparison even when the user does not exist) to remove both the content-based and timing-based oracle.
