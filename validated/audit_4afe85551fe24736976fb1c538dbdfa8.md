### Title

Zero-share ERC4626 deposit lets a vault user steal programmable-borrower principal - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower` deposits all idle pool principal into the configured ERC4626 vault but never validates the number of vault shares received. If an unprivileged vault user inflates the vault’s share price before the first programmable-borrower deposit, `vault.deposit()` can transfer the entire LP principal while minting zero shares. The borrower contract subsequently reports the deposit as principal loss rather than holding a redeemable vault position, while `IdleCDOEpochVariant` can still stop a minted-interest epoch successfully because it needs no cash transfer when no withdrawal receipt is pending. The attacker redeems the controlling vault shares and extracts the deposited LP principal. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`initialize()` only checks that the vault’s `asset()` matches the underlying token and grants that vault unlimited allowance. It does not require the vault to prevent share-inflation, enforce a minimum share output, or maintain protected seed liquidity. [4](#0-3) 

At epoch start, `onStartEpoch()` captures `startAssets` before depositing every on-hand underlying through `_depositToVault()`. [5](#0-4)  `_depositToVault()` reads the returned `shares` only for the event and has no `shares > 0`, `minSharesOut`, or post-deposit `convertToAssets()` check. [2](#0-1) 

A typical susceptible ERC4626 lets the attacker execute the classic first-depositor sequence:

1. Deposit `1 wei` of underlying and receive a small initial share supply.
2. Donate at least the programmable borrower’s expected deposit amount `P` directly to the vault.
3. Let `ProgrammableBorrower.onStartEpoch()` deposit `P`.
4. The vault calculates `shares = P * totalSupply / totalAssets`; with `totalAssets > P * totalSupply`, this rounds to zero.
5. The borrower loses custody of `P`, receives no shares, and the attacker redeems their share for approximately `P + donation`.

The accounting then treats the vanished position as a vault loss: `_currentVaultAssets()` converts the borrower’s zero-share balance to zero, and `_vaultNetInterest()` derives a loss relative to `epochStartVaultAssets`. [6](#0-5) [7](#0-6)  However, programmable-borrower deployments require minted-interest accounting, and `_stopEpoch()` requests only pending withdrawal cash in that mode; with no pending withdrawal, `amountRequired` is zero, so `onStopEpoch()` succeeds even though the vault position is unbacked. [8](#0-7) [3](#0-2) [9](#0-8) 

### Impact Explanation

The attacker directly steals up to the entire underlying balance swept into the vault at epoch start. The credit vault’s strategy-token accounting can remain nominally solvent because the CDO still holds strategy tokens, while the actual programmable-borrower vault position has no shares backing it. Later withdrawals or full-pool closure become insolvent once the real cash is demanded.

For example, with `P = 1,000,000 USDC`, an attacker seeds a susceptible vault with one share and donates at least `1,000,000 USDC`. The borrower deposit mints zero shares, and the attacker redeems the vault’s controlling share for approximately the deposited `1,000,000 USDC` plus their donation. The net theft is the LP principal swept by `onStartEpoch()`, less attacker gas and any residual vault-accounting share.

### Likelihood Explanation

Likelihood is conditional but realistic during initial programmable-borrower setup or migration to a new ERC4626 vault. The attacker needs only ordinary permissionless access to the selected vault and must arrange for one asset deposited by `ProgrammableBorrower` to mint less than one share. Owner and manager remain honest; selecting a standards-compliant but inflation-susceptible vault is sufficient.

The vulnerability does not apply to an already healthy high-liquidity ERC4626 whose conversion math includes adequate virtual-share protection or whose share price cannot economically be inflated above the borrower deposit. A vault migration through `setVault()` can recreate the risky initialization path when the newly selected vault is empty or near-empty. [10](#0-9) 

### Recommendation

Require economically meaningful share issuance for every vault deposit:

```solidity
uint256 shares = vault.deposit(_assetAmount, address(this));
if (shares == 0 || vault.convertToAssets(shares) < _assetAmount - toleratedDust) {
    revert InvalidAmount();
}
```

Prefer exposing a `minSharesOut` bound internally, checking the actual share-balance delta rather than trusting only the return value, and reverting when `_assetAmount != 0 && sharesReceived == 0`. Operational deployments should additionally require an audited ERC4626 with virtual-share/first-deposit protection or pre-seed the selected vault before enabling the programmable borrower.

### Proof of Concept

A Foundry PoC can fork mainnet only to reuse the production underlying token and credit-vault fixture, then substitute a deliberately standards-compliant susceptible ERC4626 without virtual shares:

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ERC4626, ERC20, IERC20} from "@openzeppelin/contracts/token/ERC20/extensions/ERC4626.sol";

contract InflatableVault is ERC4626 {
    constructor(IERC20 asset_)
        ERC20("Inflated Share", "iSHARE")
        ERC4626(asset_)
    {}
}

contract ProgrammableBorrowerShareInflationPoC is Test {
    // Reuse the repository's ProgrammableBorrowerCreditVault fixture/setup and the
    // forked USDC address. Replace the configured external vault with InflatableVault.
    function testZeroShareDepositDrainsEpochPrincipal() external {
        vm.createSelectFork(vm.envString("MAINNET_RPC_URL"));

        uint256 depositAmount = 1_000_000e6;
        address attacker = makeAddr("erc4626-user");

        // After deploying ProgrammableBorrower with `vault`:
        // 1. attacker calls vault.deposit(1, attacker);
        // 2. attacker donates depositAmount underlying directly to `vault`;
        // 3. an honest LP deposits depositAmount into the credit vault;
        // 4. the honest manager calls cdoEpoch.startEpoch();
        // 5. ProgrammableBorrower transfers depositAmount to `vault` and receives 0 shares;
        // 6. attacker calls vault.redeem(vault.balanceOf(attacker), attacker, attacker);
        // 7. attacker receives approximately donation + depositAmount;
        // 8. programmableBorrower.vaultSharesBalance() == 0;
        // 9. programmableBorrower.vaultLoss() == depositAmount;
        // 10. programmableBorrower.totalInterestDueNow() == 0;
        // 11. with no pending withdraw, manager calls cdoEpoch.stopEpoch(0, 0) successfully;
        // 12. the CDO still carries strategy tokens, while their external vault backing is gone.
    }
}
```

The decisive assertions are `vault.balanceOf(programmableBorrower) == 0` immediately after `startEpoch()` and the attacker’s ERC4626 redemption extracting the borrower’s deposited principal.
