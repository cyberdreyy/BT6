### Title
Local authentication CreateSession leaks account existence via distinct error text and timing (unknown email vs wrong password vs MFA-enabled account) - ([File: core/sessions/localauth/orm.go])

### Summary
`CreateSession` returns the raw `FindUser` database error (e.g., `sql: no rows in result set`) immediately for a nonexistent email, but returns the literal string `"Invalid password"` for an existing account with a wrong password, and this check happens only after a computationally expensive `bcrypt` comparison. This creates both a distinguishable error-text oracle and a timing oracle that lets an unauthenticated attacker enumerate valid accounts, including which accounts have MFA registered (via the separate `GetUserWebAuthn` call made unconditionally in the controller).

### Finding Description
`CreateSession` (`core/sessions/localauth/orm.go:144-162`) performs checks in this order:
1. `o.FindUser(ctx, sr.Email)` — for a non-existent email this immediately returns `"", err` with the *raw* database error [1](#0-0) .
2. `constantTimeEmailCompare` — dead code for the nonexistent-email case since step 1 already returned, but produces `"Invalid email"` for the (unreachable via HTTP because `lower(email)=lower($1)` in the SQL query, so this branch is effectively never hit) mismatch case [2](#0-1) .
3. `utils.CheckPasswordHash(sr.Password, ...)` — for an existing email with a wrong password, returns the literal `"Invalid password"` string, but only *after* running a `bcrypt` comparison, which is deliberately slow [3](#0-2) .
4. `GetUserWebAuthn` — only reached if the password is correct, so within `CreateSession` itself MFA status is not leaked for failed-password attempts, consistent with the code comment about avoiding "extra database look up for MFA tokens leaking if an account has MFA tokens or not" [4](#0-3) .

However, the HTTP handler `SessionsController.Create` (`core/web/sessions_controller.go:29-68`) unconditionally calls `GetUserWebAuthn(ctx, sr.Email)` *before* calling `CreateSession`, for every login attempt regardless of whether the account exists or the password is correct [5](#0-4) . That call and the subsequent `CreateSession` call are both then serialized into the HTTP response via `jsonAPIError(c, http.StatusUnauthorized, err)`, which forwards the underlying Go error's message into the response body [6](#0-5) .

The net effect for an unauthenticated attacker probing `POST /sessions`:
- Nonexistent email: fast response (no bcrypt call), body containing the raw SQL "no rows" style error text.
- Existing email + wrong password: slower response (bcrypt hash compare executed), body containing `"Invalid password"`.
- Existing email with MFA + wrong password: same as above — MFA status is *not* additionally leaked by `CreateSession` itself, so the MFA-specific part of the question is not confirmed as an independent oracle beyond generic email enumeration.

### Impact Explanation
This enables account enumeration: an attacker can distinguish "email doesn't exist" from "email exists, wrong password" via both error text and response timing, without any credentials or privileges. This is a precursor to targeted credential-stuffing/password-spraying and lets an attacker build a list of valid Chainlink node operator accounts to target more efficiently. It does not by itself allow authentication bypass, privilege escalation, or MFA bypass — the MFA presence itself is not distinguishably leaked by `CreateSession`'s ordered checks as the code comment intends. Impact class: information disclosure / account enumeration (low-to-moderate severity), not authentication bypass.

### Likelihood Explanation
No preconditions: the `/sessions` endpoint is unauthenticated and reachable by any attacker with network access to the node's operator UI/API. The difference is easily observable and repeatable (identical inputs produce consistent error strings and consistent relative timing due to `bcrypt`'s deterministic cost), so likelihood of exploitation for enumeration purposes is high, though the exploit yields only enumeration, not a takeover primitive.

### Recommendation
- Normalize the error returned to the HTTP layer for "unknown email" and "wrong password" to an identical generic message and status code (e.g., always `"Invalid email or password"`).
- Ensure `FindUser` failure still executes a dummy/constant-cost password hash comparison (e.g., against a fixed dummy hash) before returning, to remove the timing side-channel.
- Move the `GetUserWebAuthn` call in `SessionsController.Create` so it does not run, or runs with equalized timing, prior to establishing that the email/password pair is valid, avoiding any additional oracle.

### Proof of Concept
Table-driven Go test in `core/sessions/localauth/orm_test.go` (or handler-level test in `core/web/sessions_controller_test.go`):
1. Case A: `sr.Email` = nonexistent address, `sr.Password` = arbitrary. Call `CreateSession`, record elapsed time and `err.Error()`.
2. Case B: `sr.Email` = existing user, `sr.Password` = wrong. Call `CreateSession`, record elapsed time and `err.Error()`.
3. Case C: same as B but for a user with a registered WebAuthn credential. Call `CreateSession`, record elapsed time and `err.Error()`.
4. Assert (to prove the bug): `err.Error()` strings differ between Case A and Case B/C, and elapsed time for Case A is measurably smaller (no bcrypt compare) than B/C (bcrypt compare executed) — demonstrating the enumeration oracle.
5. At the handler level, additionally assert via `httptest` that `POST /sessions` returns different JSON error bodies for the three inputs, confirming the oracle is externally observable.
