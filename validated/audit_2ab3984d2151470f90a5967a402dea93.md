### Title
Unbounded intermediate memory allocation in `get_token_largest_accounts` before top-N reduction - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_token_largest_accounts` first awaits `get_filtered_spl_token_accounts_by_mint`, which materializes the *entire* set of matching token accounts (address + full `AccountSharedData`, including data blob) into a `Vec` before any reduction happens. Only after this full vector is built in memory does the function iterate it to maintain a bounded `BinaryHeap` of size `NUM_LARGEST_ACCOUNTS`. This means the cost of a single RPC call is proportional to the number of on-chain token accounts an attacker has created for the target mint, not bounded by the final response size.

### Finding Description

The heap-based top-N logic (`BinaryHeap::<Reverse<(u64, Pubkey)>>::with_capacity(NUM_LARGEST_ACCOUNTS)`) only bounds the *output*; it operates on the result of `.await?` on `get_filtered_spl_token_accounts_by_mint(...)`, meaning the full collection returned by that call must be constructed before the loop can begin trimming it down. That underlying call filters program accounts by mint (via secondary index scan or full program-account scan depending on whether the SPL-token-mint index is enabled) and returns a `Vec<(Pubkey, AccountSharedData)>` containing the complete token account data for every matching account.

Because SPL token accounts are cheap and permissionless to create (each is a fixed ~165-byte token account, rent-exempt, owned by the token program), an attacker can create an arbitrarily large number `N` of token accounts for a single mint they control via ordinary transactions. A single subsequent `getTokenLargestAccounts(mint)` call forces the validator's JSON-RPC processing thread to allocate and hold `N` copies of account data in memory simultaneously before the heap reduction discards all but `NUM_LARGEST_ACCOUNTS` of them. No length-based or account-count-based limit is applied prior to this materialization step in `rpc.rs`.

### Impact Explanation
This is a single-call resource-exhaustion / unbounded-cost issue: the memory (and CPU cost of unpacking token account data for filtering) of one RPC request scales linearly with attacker-controlled on-chain state (number of token accounts for one mint), rather than being bounded by an explicit, documented limit tied to the fixed output size (`NUM_LARGEST_ACCOUNTS`). This falls under "unbounded cost for a single low-rate call" in the validated impact categories, as it can be triggered with one `getTokenLargestAccounts` call per `CLUSTER_SLOT_TIME_TARGET / 2` and requires no privileged access — only ordinary token-account-creation transactions plus one RPC call.

### Likelihood Explanation
- Precondition: attacker creates N SPL token accounts for a mint they control, via standard `CreateAccount` + `InitializeAccount` transactions — fully within unprivileged capability and inexpensive at scale (only rent-exemption cost per account, ~0.002 SOL each).
- Trigger: single `getTokenLargestAccounts(mint)` JSON-RPC call.
- This is fully repeatable and does not require multiple concurrent clients or exceeding rate limits — a single call suffices to force full materialization of N accounts' worth of data.

### Recommendation
Push the top-N bound into the filtered-account-fetching layer: use a streaming/iterator-based scan (rather than collecting into a `Vec` first) and maintain a size-`NUM_LARGEST_ACCOUNTS` bounded heap during the scan itself in `get_filtered_spl_token_accounts_by_mint`/`get_filtered_indexed_accounts`, so accounts are unpacked and discarded incrementally rather than the whole set being retained in memory. Alternatively, enforce a hard cap on the number of accounts scanned/returned per mint filter query, returning an error or truncated result if it exceeds a safe threshold.
