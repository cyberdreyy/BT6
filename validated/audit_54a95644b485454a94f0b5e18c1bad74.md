Confirmed: `bank_account.withdraw_all()` runs and closes/deactivates the balance *before* `check_account_init_health` executes, so a user CAN always exit their own broken staked-collateral position via `withdraw_all` without needing that bank's oracle, since the now-inactive balance is skipped by `get_health_components`'s `.filter(|b| b.is_active())` loop. This means the primary escape hatch exists, unlike the Telcoin plugin bug where there was truly no way to bypass a rogue plugin. However, this only protects the position being fully closed in *that same instruction* — any *other* active balance the user holds still requires ALL active balances (including any permanently-broken one they haven't closed yet) to pass oracle validation during `check_account_init_health`, since `get_health_components` ( [1](#0-0) ) propagates any single balance's oracle error (via `calc_weighted_liab_value_standalone`/`calc_weighted_value_for_balance`) as a hard `Err` for the whole call, rather than catching it and zeroing that one position out.

### Title
Permanently-freezable staked-collateral bank oracle (zero LST supply) blocks withdraw/borrow across a user's other balances until the broken position is closed - (File: programs/marginfi/src/state/price.rs)

### Summary
Permissionless staked-collateral banks (`OracleSetup::StakedWithPythPush`) are validated during pricing by requiring `lst_mint.supply > 0` [2](#0-1) . If a validator's single-validator-stake-pool LST supply drops to zero (e.g., all other depositors exit that specific pool), oracle loading for that bank permanently errors with `ZeroSupplyInStakePool`, and this error is propagated (not swallowed) by `get_health_components`, which is invoked by every risk-checked instruction (`lending_account_withdraw`, `lending_account_borrow`, Kamino/Solend/JupLend withdraw/borrow flows).

### Finding Description
`get_health_components` iterates **all active balances** on the account and requires each oracle adapter to load successfully; on error it returns `Err` for the whole call rather than skipping/zeroing only the failing balance [3](#0-2) [4](#0-3) . `check_account_init_health`, used by `lending_account_withdraw`, `lending_account_borrow` and the integration (Kamino/Solend/JupLend) withdraw instructions, calls into this same function [5](#0-4) .

Staked-collateral banks are permissionlessly created via `lending_pool_add_bank_permissionless` for any validator's single-validator-stake-pool [6](#0-5) , and the README confirms this is intentionally open ("Adding Staked Collateral is permissionless!"). If that pool's LST mint supply later reaches zero (all other holders redeem, leaving the marginfi vault the sole staker whose shares aren't reflected in `supply` the same way, or via other pool-draining conditions), `validate_bank_config`/`OraclePriceFeedAdapter` permanently rejects that bank's price with `ZeroSupplyInStakePool` — this is a structural, not admin-fixable, condition since `configure_bank_oracle` cannot repair an external mint's supply.

Because this failure surfaces inside the *shared* health-check loop (not scoped to the one balance), any user who has an active (non-zero) position in that specific broken staked bank **and any other balance** cannot withdraw or borrow against those *other* balances either — `check_account_init_health` fails for the whole account until the broken balance is closed. The only mitigation is that a user can still `withdraw_all` the broken balance itself in the same instruction (since the balance is deactivated before the health check runs), so full compromise (funds frozen forever) is avoidable for a sole-affected user acting promptly, but the account is effectively DoS'd for any other outflow operation while that stale balance exists, and third-party flows like receivership liquidation or order execution which enumerate all balances/oracles could also be obstructed.

### Impact Explanation
This is not as severe as the original Telcoin report (full permanent freeze with no recovery), because a user can self-heal by calling `withdraw_all` on the broken position. But it still represents a durable, financially-relevant DoS: until that call is made, all other withdraw/borrow instructions on the account revert, and any protocol/indexer/liquidator flow that must pass all balances+oracles (e.g. risk engine checks, `pulse_health`-based tooling) will observe a permanently broken engine result for that account, blocking third-party operations that also require iterating the whole balance set.

### Likelihood Explanation
Requires a specific external condition (a single-validator-stake-pool LST mint supply hitting zero) which is plausible only for very small/inactive validator pools, and is otherwise outside the marginfi program's control. Not an attacker-forced condition against arbitrary users, but the underlying design flaw (propagating a hard error for one balance rather than isolating it) is a legitimate broader robustness issue not scoped to just staked banks — any future oracle type with a similarly permanent failure mode (Kamino/Solend/JupLend reserve corruption, though those integrations are gated by trusted program IDs) would hit the exact same class of issue.

### Recommendation
In `get_health_components` (and its cache counterparts), do not propagate a single balance's oracle-load error as a fatal error for the whole account health check. Instead, mirror the existing `internal_err`/`err_index` bookkeeping already present in `HealthCache` [7](#0-6)  to zero out just the broken balance's value (as is already done in some paths, e.g. asset-side errors) rather than returning `Err` up through `check_account_init_health`, and/or provide a permissionless "force-exit"/"repair" path so an account with a permanently broken staked-collateral balance can be salvaged without depending on withdrawing that specific position first.

### Proof of Concept
1. Create a permissionless staked bank for a small validator's single-validator-stake-pool via `lending_pool_add_bank_permissionless`.
2. User A deposits into this staked bank and also deposits into an unrelated USDC bank.
3. The validator's stake pool LST mint supply drops to zero (all other stakers redeem from the underlying single-pool program, outside marginfi's control).
4. User A calls `lending_account_withdraw` on the USDC bank — `check_account_init_health` iterates all active balances, hits the staked bank, `OraclePriceFeedAdapter::try_from_bank` returns `MarginfiError::ZeroSupplyInStakePool` [2](#0-1) , and the entire withdraw transaction reverts — even though the withdrawal only concerns the healthy USDC balance.
5. User A can recover by first calling `lending_account_withdraw` with `withdraw_all=true` on the staked bank (closing that balance before the health check runs), after which normal operations on other balances resume — but until that step is taken, all outflow instructions on the account are blocked.
