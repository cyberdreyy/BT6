### Title
Stale instant-withdraw per-epoch receipts are never cleared on claim, corrupting default-finalization claim basis - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` pays out and zeroes the aggregate `instantWithdrawsRequests[_user]`, but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched. If the borrower later defaults in that same epoch, `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch basis and treats already-paid receipts as unfunded default claims, decrementing live counters a second time. This is the vault analog of a heap buffer overflow: accounting reads past the real "buffer" (the funded-and-claimed receipt) into stale state.

### Finding Description
In `IdleCreditVault.sol`, `requestInstantWithdraw` writes three ledgers: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]`. When the CDO calls `claimInstantWithdrawRequest` (lines 380-393), only the aggregate `instantWithdrawsRequests[_user]` is reset to 0; the two per-epoch mappings retain the full basis.

Later, if the borrower defaults during that epoch and default recovery is finalized (`defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`), `_claimDefaultedInstantWithdrawRequest` (lines 842-856) reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and:

- subtracts `claimBasis` from `instantWithdrawsRequests[_user]`, which is already 0 → arithmetic underflow revert, or pays out double if the user has a newer open request;
- subtracts `claimBasis` from `instantWithdrawClaimsByEpoch[defaultEpoch]`, double-counting it in whatever reserve sizing reads that aggregate;
- resets `pendingInstantWithdraws` via `claimBasis >= pending ? 0 : pending - claimBasis`, corrupting the unfunded-remainder counter used by `collectInstantWithdrawFunds`.

The existing guards do not stop it: `_onlyIdleCDO` is satisfied, the `defaultEpoch` key legitimately matches (the receipt was created in the epoch that later defaulted), and there is no "already claimed" flag on the per-epoch entries.

### Impact Explanation
Two outcomes depending on user state at finalization:

1. **Frozen recovery claims**: for a user whose instant receipt was funded and claimed pre-default, `instantWithdrawsRequests[_user] -= claimBasis` underflows and every subsequent `claimInstantWithdrawRequest` reverts. If `defaultInstantWithdrawsFinalized` is already set, that revert path is permanent — the user (and the queue contract, which calls through `claimInstantWithdrawRequest`) can never claim, and `processWithdrawalClaims` deadlocks for that epoch.
2. **Reserve mispricing**: `instantWithdrawClaimsByEpoch[defaultEpoch]` is inflated by already-paid basis, so any reserve-sizing or `defaultRecoveryPrice` computation that consumes it under-funds other claimants or misapplies the haircut.

Loss quantification: all underlyings backing the user's legitimate (new or defaulted-epoch) receipts, plus recovery claims of other users blocked behind the same corrupted aggregate.

### Likelihood Explanation
Requires: instant withdrawals enabled (`_isInstantWithdrawEnabled`, APR drop > `instantWithdrawAprDelta`), a user whose instant receipt is funded via `collectInstantWithdrawFunds` and claimed, and a borrower default in the same `epochNumber` — i.e., the borrower fails to top up by `instantWithdrawDeadline`/`stopEpoch` while the epoch counter has not advanced. This is a normal market-stress sequence needing no privileged misbehavior; the attacker is merely an unprivileged tranche holder exercising request/claim at the right time. Likelihood is moderate: the window is one epoch, but instant withdrawals exist precisely for the APR-cut scenario that precedes borrower stress.

### Recommendation
Clear per-epoch receipt storage inside `claimInstantWithdrawRequest` (and mirror it in the CDO-side claim path): after paying `amount`, zero `instantWithdrawsRequestsByEpoch[_user][epoch]` for the request epoch(s) and decrement `instantWithdrawClaimsByEpoch[epoch]` correspondingly, so default finalization only sees genuinely unfunded basis. Alternatively, store a claimed flag/remaining-basis per epoch and have `_claimDefaultedInstantWithdrawRequest` cap `claimBasis` at `instantWithdrawsRequests[_user]`.
