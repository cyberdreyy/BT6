### Title
Stale confirmations from removed multisig members are not purged and can be counted toward `num_confirmations`, letting a request execute below the effective live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only removes pending requests and confirmations for which the deleted member was the *original requester* (`r.member == member`), but it never scans other pending requests to strip that member's confirmation entries from `self.confirmations`. Because `confirm()` counts raw entries in that `HashSet<String>` against `num_confirmations` without validating that each entry still belongs to a current member, a stale confirmation left behind by a removed member can be combined with confirmations from currently-live members to reach the threshold and execute a request, even though fewer live members actually approved it.

### Finding Description
`delete_member` at [1](#0-0)  removes `num_requests_pk`, deletes the member from `self.members`, and cleans up requests/confirmations only for `request_ids` filtered by `r.member == member` — i.e., requests *created* by the departing member. It does not iterate `self.confirmations` to remove the departing member's string entry from requests created by *other* members that this member had previously confirmed.

`confirm()` treats the confirmation set purely as a counter of strings, with no re-validation against `self.members`: [2](#0-1) 

Since `confirmations` is keyed by `member.to_string()` and stored independently of the live `members: UnorderedSet<MultisigMember>`, once a member is deleted, any confirmation they left on a still-pending request (that they didn't create) remains valid data used toward the threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations`.

The binding that should hold is:
`confirmations counted toward execution == confirmations from currently active members`

After a member removal this becomes:
`confirmations counted toward execution == confirmations from currently active members + stale confirmations from removed members on requests they didn't create`

### Impact Explanation
This breaks the multisig's core custody guarantee: a request (e.g., a `Transfer` of contract funds, an `AddKey`/`AddMember` action, or a `FunctionCall`) can be executed with fewer *live* member approvals than `num_confirmations` requires, because one or more of the counted confirmations belong to an account that is no longer a member. This falls squarely under the Critical impact bucket: "a multisig request executed below threshold."

### Likelihood Explanation
This requires no privileged action by an attacker beyond normal multisig workflow: a former member (who may have turned malicious, or whose key was compromised before removal) leaves a confirmation on a pending request, is later removed via `DeleteMember`, and the remaining members simply continue confirming other pending requests as usual — none of them can observe from on-chain state that a stale confirmation is embedded, since `get_confirmations`/`confirmations` are just strings with no liveness flag. Any workflow where a member is removed while other members' requests are still pending (which is a normal, foreseeable multisig operational scenario, not an edge case) exposes this.

### Recommendation
When deleting a member in `delete_member`, iterate all entries in `self.confirmations` (not just requests created by that member) and remove the departing member's `to_string()` entry from every confirmation set. Alternatively, validate on every `confirm()`/execution check that all entries in the confirmation set still correspond to current members in `self.members`, discarding stale ones before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new` with members `[A, B, C]` and `num_confirmations = 2`.
2. Member `B` calls `add_request` to create request `R` (transfer of contract funds to an external account), leaving it unconfirmed by `B`'s own logic (or `add_request` then a separate `confirm` from `C`), so `R`'s confirmations = `{C}`.
3. Members vote to remove `B` via `DeleteMember` (a legitimate, unrelated request/action, e.g. because `B`'s key was compromised) — [1](#0-0)  executes and removes `B` from `self.members`, but `R`'s confirmation set still only reflects requests *created* by `B`; since `B` didn't create `R`, `R.confirmations` is untouched and remains `{C}`... 

   (Adjust scenario: have `B` be the one who *confirmed* R, i.e. `R` created by `A`, confirmed by `B` → `confirmations = {B}`.)
4. `B` is later removed via `DeleteMember` (members = `{A, C}` now).
5. `C` calls `confirm(R)`. The check `confirmations.len() + 1 >= num_confirmations` evaluates `1 (stale B) + 1 (C) >= 2` → true, and `R` executes — despite only one *current* member (`C`) ever having confirmed it, one short of the intended 2-of-current-members threshold. [2](#0-1) [3](#0-2)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
