### Title
Post-default withdraw requests consume `defaultRecoveryReserve` earmarked for defaulted-epoch claimants, freezing legitimate recovery claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
After `finalizeDefaultRecovery` sizes `defaultRecoveryReserve` to exactly cover the pre-default claim basis, the post-default path in `requestWithdraw` lets a fresh depositor mint a receipt and claim it 1:1 out of that same reserve via `_transferDefaultRecovery`, while their newly deposited underlying is never credited to the reserve. This "use-after-free" analog — reserve slots freed/accounted for defaulted claimants being reused by new receipts — causes `defaultRecoveryReserve -= _amount` to underflow once the reserve accounting is exhausted, permanently reverting recovery claims even though the underlying tokens are physically present.

### Finding Description
`finalizeDefaultRecovery` computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and prices `defaultRecoveryPrice` against `activeBasis + pendingBasis` only [1](#0-0) . Afterwards, `requestWithdraw` accepts new requests, minting the user a full receipt (`_mint(_user, _amount)`) and recording `postDefaultRequests[_user] = _amount` with no contribution to `defaultRecoveryReserve` [2](#0-1) . `_claimPostDefaultWithdrawRequest` then pays that receipt 1:1 from the reserve: `defaultRecoveryReserve -= amount` in `_transferDefaultRecovery` [3](#0-2) . The attacker's accompanying `deposit()` transfers fresh underlying into the strategy and mints strategy tokens to the CDO, but does not increase `defaultRecoveryReserve` [4](#0-3) . The `_transferFundedClaim` reserve guard does not help because post-default claims bypass it entirely and draw directly from the reserve counter [5](#0-4) .

### Impact Explanation
Invariant broken: recovery-reserve isolation / one-reserved-unit-one-claimant. Each post-default request of size `X` decrements `defaultRecoveryReserve` by `X` while backing it with funds outside the reserve accounting. Once cumulative post-default claims exceed what the recovery math reserved for them (which is zero), the subtraction underflows and every subsequent defaulted/post-default claim reverts — permanent freezing of unclaimed recovery yield for defaulted-epoch receipt holders, even though tokens remain in the contract. Loss is bounded by total post-default request volume; a single attacker cycling deposits can consume the entire reserve quota, DoS-ing all remaining legitimate claimants.

### Likelihood Explanation
Requires the pool to have defaulted and `finalizeDefaultRecovery` to have run with a positive `defaultRecoveryPrice`, plus the CDO still accepting deposits/withdraw requests post-default (`requestWithdraw` explicitly supports this path, and the CDO forwards `deposit`/`requestWithdraw`). The attacker is an unprivileged KYC-passing lender performing only `depositAA` → `requestWithdraw` → `claimWithdrawRequest`; all privileged roles act honestly. One caveat not fully verified in this review: whether `IdleCDOEpochVariant` deposit entry points are gated on `defaulted()`/`defaultRecoveryFinalized` — if deposits are hard-blocked post-default, the attack vector closes and this finding reduces to a reserve-accounting inconsistency.

### Recommendation
Either fund post-default claims from their own backing rather than `defaultRecoveryReserve` — e.g. pay `_claimPostDefaultWithdrawRequest` via `_transferFundedClaim` so the reserve guard protects default claimants — or increment `defaultRecoveryReserve` by the haircut-adjusted amount when `requestWithdraw` runs post-finalization so the reserve tracks all claimants it must pay.

### Proof of Concept
Foundry fork PoC outline (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// 1. user deposits, requests withdraw; epoch runs and borrower defaults.
_depositWithUser(victim, amount, true);
vm.prank(victim); cdoEpoch.requestWithdraw(bal, address(AAtranche));
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr, 0); // triggers default
assertTrue(cdoEpoch.defaulted());

// 2. manager finalizes with partial recovery -> defaultRecoveryReserve = R
deal(defaultUnderlying, manager, recovered);
vm.startPrank(manager);
IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
cdoEpoch.finalizeDefault(recovered, manager);
vm.stopPrank();
uint256 reserveBefore = IdleCreditVault(address(strategy)).defaultRecoveryReserve();

// 3. attacker deposits post-default, requests withdraw, claims immediately
_depositWithUser(attacker, amount, true);
vm.startPrank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche));
cdoEpoch.claimWithdrawRequest(); // pays from reserve
vm.stopPrank();
assertLt(IdleCreditVault(address(strategy)).defaultRecoveryReserve(), reserveBefore);

// 4. repeat until reserve accounting is exhausted; victim claim then reverts
//    on underflow in _transferDefaultRecovery despite tokens in contract
vm.prank(victim);
vm.expectRevert(); // defaultRecoveryReserve -= amount underflows
cdoEpoch.claimWithdrawRequest();
```

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @notice Transfer default recovery reserve to a user.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }
