### Title
Unfunded instant-withdraw receipts can claim against any strategy-held underlying — (`contracts/strategies/idle/IdleCreditVault.sol:claimInstantWithdrawRequest`)

### Summary
`claimInstantWithdrawRequest` pays a user's instant-withdraw receipt from the strategy's aggregate underlying balance without verifying that the request was actually funded through `collectInstantWithdrawFunds`. The analog to CVE-2023-45841's skipped integrity check is that the receipt's funding status is never verified before payout, so an unfunded receipt can consume underlying held in the strategy for other purposes.

### Finding Description
- `requestInstantWithdraw` burns CDO strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`).
- Funding arrives only via `collectInstantWithdrawFunds`, which pulls exactly `_amount` from the CDO and decrements `pendingInstantWithdraws` (`IdleCreditVault.sol:398-403`).
- `claimInstantWithdrawRequest` then burns the receipt and calls `_transferFundedClaim(_user, amount)` for the full `instantWithdrawsRequests[_user]` (`IdleCreditVault.sol:380-392`).
- `_transferFundedClaim` only isolates `defaultRecoveryReserve`; every other underlying sitting in the strategy is spendable by any claimant (`IdleCreditVault.sol:897-907`).

There is no per-user or per-epoch record that a given instant request was funded. A receipt is treated as paid-in-full the moment the strategy happens to hold enough tokens. During the buffer phase, `deposit()` pulls underlying into this strategy before it is forwarded (`IdleCreditVault.sol:596-617`), and `_defaultPrefundedInstantReserve` shows the code itself acknowledges partially funded queues where some underlying is held on behalf of specific receipts (`IdleCreditVault.sol:716-723`). An attacker who calls `requestInstantWithdraw` while the strategy holds underlying destined for other users (buffer-period deposits, or the funded portion of another epoch's instant claims counted via `instantWithdrawClaimsByEpoch`) can immediately trigger `claimInstantWithdrawRequest` and be paid first-come-first-served, leaving the legitimately funded earlier receipt unpayable.

### Impact Explanation
Direct theft / permanent freezing of other users' withdrawals: the attacker drains underlying reserved for earlier funded instant claimants or buffer deposits, breaking the "one receipt, one payout" and funding-isolation invariants. Loss equals up to the strategy's transient underlying balance at claim time.

### Likelihood Explanation
Requires an unprivileged lender able to request an instant withdraw, sequenced when the strategy holds non-reserve underlying (buffer window after `deposit`, or a partially funded instant queue). The attacker is an ordinary user; no privileged role is needed. Likelihood is bounded by the existence of those windows, which the prefunded-reserve logic confirms occur in normal operation.

### Recommendation
Track funded instant withdrawals separately (e.g., a `fundedInstantWithdraws` counter increased in `collectInstantWithdrawFunds` and a per-epoch funded basis mirroring `instantWithdrawClaimsByEpoch`), and revert in `claimInstantWithdrawRequest` when the claimed amount exceeds the funded portion attributable to that user's epochs.

### Proof of Concept
```solidity
// Foundry fork test sketch
// 1. Epoch running; victim requests instant withdraw of V.
//    CDO partially funds: collectInstantWithdrawFunds(F) with F < V.
//    => strategy now holds F underlying owed to victim's receipt.
// 2. Attacker (ordinary lender) calls requestInstantWithdraw(A) with A <= F
//    via the CDO. instantWithdrawsRequests[attacker] = A, unfunded.
// 3. In the same epoch attacker calls claimInstantWithdrawRequest(attacker)
//    through the CDO. _burn(attacker, A); _transferFundedClaim pays A from
//    the F held for victim (no funded check; defaultRecoveryReserve == 0).
// 4. Victim calls claimInstantWithdrawRequest -> safeTransfer of V fails
//    (balance < V) or pays only V - A. Attacker stole A underlying.
assertEq(underlying.balanceOf(attacker), A);
assertEq(underlying.balanceOf(strategy), F - A);
```

Note: I verified this path only within `IdleCreditVault.sol`; whether the CDO side (`IdleCDOEpochVariant`) blocks user-initiated instant claims until funding completes could not be confirmed in the available iterations — if the CDO fully orders funding before claims, the exploit requires the partially funded window described in `_defaultPrefundedInstantReserve`.
