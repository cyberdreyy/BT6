### Title
Unrestricted Mid-Epoch Commission Changes via `UpdateCommissionBps` Break Reward-Round Fairness - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The vote program's new basis-point commission update path (`update_commission_bps`, implementing SIMD-0291/SIMD-0249) removes all timing restrictions that the legacy `update_commission` path enforces, allowing a vote account's inflation-rewards or block-revenue commission to be changed at any point within an epoch (the Solana analog of the reported "round"). This mirrors the reported bug class where `commissionPercent`/`baseStake` can be mutated mid-round, producing inconsistent payouts for stake/validators depending on when in the epoch the change occurred.

### Finding Description
The legacy commission-update function `update_commission` enforces `is_commission_update_allowed`, which only permits commission *increases* during the first half of an epoch, specifically to prevent a validator from raising commission late in the epoch after most of the epoch's rewards have already accrued to delegators under the old rate: [1](#0-0) [2](#0-1) 

The new `update_commission_bps` instruction, however, explicitly drops this rule: [3](#0-2) 

The comment in the test file confirms the intent: "Unlike test_update_commission, SIMD-0291 has no timing restrictions (per SIMD-0249). Updates are always allowed regardless of epoch position." [4](#0-3) 

This matters because commission read for reward calculation is not uniformly delayed. For inflation rewards, a `delay_commission_updates` feature gate exists to fetch the commission from a *prior* epoch's snapshot specifically to avoid mid-epoch mutation affecting the current reward round: [5](#0-4) 

But block-revenue commission (`block_revenue_commission_bps`, used for per-block/per-slot transaction fee and block-reward splitting via SIMD-0123) has no equivalent delay mechanism in the reviewed code path — `calculate_block_reward` and the leader/vote-account collector logic in `fee_distribution.rs` read the vote account's live state each time fees/rewards are distributed, with no snapshot-based delay analogous to `delay_commission_updates`. Since `update_commission_bps` for `CommissionKind::BlockRevenue` can be called by the authorized withdrawer at any slot with no epoch-half restriction, a validator can alter its take of block revenue mid-epoch (i.e., mid-"round"), so stakers/delegators earning rewards from blocks produced early in the epoch are subject to a different commission split than those from blocks produced later in the same epoch — the direct analog of "changing commission percent mid-round" from the reported issue.

### Impact Explanation
This causes protocol-level inconsistency in reward distribution within a single epoch: delegators to the same validator receive different effective commission rates depending purely on which slot within the epoch a block was produced, undermining the fairness guarantee that the epoch-half restriction was designed to preserve for the legacy commission field. It does not grant unauthorized fund access (the withdrawer authority is still required), but it produces state-mutation-driven reward inconsistency that is unpredictable and disputable, matching the "Medium" bug class from the analog report.

### Likelihood Explanation
Any vote account's authorized withdrawer can trigger this at will since `update_commission_bps` requires only the withdrawer's signature and no timing/epoch check is enforced at all (unlike the legacy path). This makes the condition trivially and repeatedly reachable by any validator operator, not requiring any special node privilege beyond normal vote-account key custody.

### Recommendation
Apply the same delay/snapshotting principle used for `delay_commission_updates` (inflation rewards) to the block-revenue commission path, or reintroduce an epoch-position restriction analogous to `is_commission_update_allowed` for `update_commission_bps`, so that mid-epoch changes to `block_revenue_commission_bps` only take effect starting the next epoch/reward round rather than immediately affecting in-flight block reward distribution.

### Proof of Concept
1. At the start of an epoch, a validator's vote account has `block_revenue_commission_bps = 500` (5%).
2. Blocks are produced during the first half of the epoch and rewards are distributed using the 5% split (via `fee_distribution.rs`/`calculate_block_reward`, which read live vote-account state) as shown at [6](#0-5) .
3. Midway through the epoch, the validator's withdrawer calls `VoteInstruction::UpdateCommissionBps { commission_bps: 5000, kind: CommissionKind::BlockRevenue }`, which succeeds unconditionally per `update_commission_bps` (no `is_commission_update_allowed` check), as validated in `test_vote_update_commission_bps`: [7](#0-6) .
4. Blocks produced in the remainder of the epoch are now rewarded/split using the new 50% commission, while blocks from the first half used 5% — all within the same epoch/reward round, producing inconsistent payouts to delegators purely based on block timing.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}

/// Computes the voting reward in Lamports.
///
/// Returns `(validator rewards, leader rewards)`.
fn calculate_reward(
    epoch_state: &EpochInflationState,
    total_stake_lamports: u64,
    validator_stake_lamports: u64,
) -> (u64, u64) {
    // Rewards are computed as following:
    // per_slot_inflation = epoch_validator_rewards_lamports / slots_per_epoch
    // fractional_stake = validator_stake / total_stake_lamports
    // rewards = fractional_stake * per_slot_inflation
    //
    // The code below is equivalent but changes the order of operations to maintain precision

    let numerator =
        epoch_state.max_possible_validator_reward as u128 * validator_stake_lamports as u128;
    let denominator = epoch_state.slots_per_epoch as u128 * total_stake_lamports as u128;

    // SAFETY: the result should fit in u64 because we do not expect the inflation in a single
    // epoch to exceed u64::MAX.
    let reward_lamports: u64 = (numerator / denominator).try_into().unwrap();
    // As per the Alpenglow SIMD, the rewards are split equally between the validators and the leader.
    let validator_reward_lamports = reward_lamports / 2;
    let leader_reward_lamports = reward_lamports - validator_reward_lamports;
    (validator_reward_lamports, leader_reward_lamports)
}
