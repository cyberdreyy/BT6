### Title
`getTransaction`/`getBlock` `preTokenBalances`/`postTokenBalances` misreport `uiAmount` for SPL-Token-2022 tokens with `ScaledUiAmountConfig`/`InterestBearingConfig` extensions - (File: `svm/src/transaction_balances.rs`, `runtime/src/transaction_balances.rs`)

### Summary
The external report describes `VoterProxy` incorrectly assuming a fixed 1-1 ratio between a gauge token balance and the underlying LP token, causing it to compute a wrong withdrawal amount because it ignores a per-pool "staking factor" that can scale the two quantities apart. The analogous bug class here is: computing a user-facing derived quantity from a raw on-chain balance while ignoring a scaling/rebasing factor that can legitimately differ from 1:1 for certain token configurations.

### Finding Description
When the SVM collects pre/post token balances for a transaction (used to populate `preTokenBalances`/`postTokenBalances` in `getTransaction`/`getBlock` RPC responses), it extracts only the raw token `amount` and the mint's `decimals`, explicitly discarding any `InterestBearingConfig` or `ScaledUiAmountConfig` extension data: [1](#0-0) 

This is then converted into the reported `UiTokenAmount` using only `decimals`, with a comment acknowledging the omission: [2](#0-1) 

By contrast, the dedicated JSON-RPC methods `getTokenAccountBalance` and `getTokenSupply` correctly fetch the mint's `InterestBearingConfig`/`ScaledUiAmountConfig` extensions via `get_mint_owner_and_additional_data`/`get_additional_mint_data` and factor them into the `ui_amount`/`ui_amount_string` computation: [3](#0-2) [4](#0-3) 

The shared conversion routine `token_amount_to_ui_amount_v3` does apply the scaling/interest math correctly when given the additional data — the bug is that the transaction-balances collection path in the SVM never supplies it (it only ever constructs `SplTokenAdditionalDataV2::with_decimals(decimals)`), so for SPL-Token-2022 mints using the `ScaledUiAmount` or `InterestBearingConfig` extensions, the derived `uiAmount`/`uiAmountString` reported for `preTokenBalances`/`postTokenBalances` do not reflect the same 1-1 relationship between raw `amount` and `uiAmount` that the mint's own extension configuration establishes — mirroring the VoterProxy bug of assuming a fixed ratio between a raw balance and a derived value where the underlying protocol allows that ratio to change.

### Impact Explanation
Any unprivileged client calling `getTransaction` or `getBlock` (with token-balance fields requested) for a transaction touching a Token-2022 mint with `ScaledUiAmountConfig` (rebasing multiplier) or `InterestBearingConfig` receives `uiAmount`/`uiAmountString` values in `preTokenBalances`/`postTokenBalances` that are computed as if the multiplier/interest were `1`/`0`, i.e. as raw `amount / 10^decimals`, rather than the actual scaled/interest-adjusted value. This is wrong-data-returned to an RPC caller (a "misreporting" outcome), even though the raw integer `amount` field itself remains correct. Downstream consumers (explorers, wallets, indexers) that rely on the `ui_amount` fields in transaction status for balance-change display could show materially incorrect deltas for such tokens, analogous to how the VoterProxy computed an incorrect withdrawal amount by ignoring the gauge's non-1:1 factor.

### Likelihood Explanation
This is reachable with a single, unprivileged JSON-RPC call (`getTransaction`/`getBlock`) against any transaction that includes a Token-2022 account whose mint has the `ScaledUiAmountConfig` or `InterestBearingConfig` extension enabled — both are shipped, real extensions supported elsewhere in the same codebase (`get_additional_mint_data`, `get_mint_owner_and_additional_data`). No special privileges, multiple calls, or unusual cluster state are required; only a mint configured with these extensions, which is entirely within an ordinary (unprivileged) token creator's control.

### Recommendation
When collecting `SvmTokenInfo` in `svm/src/transaction_balances.rs`, also capture the mint's `InterestBearingConfig`/`ScaledUiAmountConfig` extension state (as is already done in `rpc/src/parsed_token_accounts.rs::get_additional_mint_data`), and thread that through to `svm_token_info_to_token_balance` in `runtime/src/transaction_balances.rs` so it builds a full `SplTokenAdditionalDataV2` (not just decimals) before calling `token_amount_to_ui_amount_v3`, ensuring `preTokenBalances`/`postTokenBalances` are consistent with `getTokenAccountBalance`/`getTokenSupply`.

### Proof of Concept
1. Create an SPL-Token-2022 mint with the `ScaledUiAmountConfig` extension enabled and a non-1.0 `multiplier` (e.g. `2.0`), as constructed in the test fixture at [5](#0-4)  which exercises exactly this extension.
2. Submit a transaction that transfers this token between two accounts.
3. Call `getTransaction` on that transaction and inspect `meta.preTokenBalances`/`meta.postTokenBalances`.
4. Because `SvmTokenInfo::unpack_token_account` only reads `decimals` from the mint ( [6](#0-5) ) and `svm_token_info_to_token_balance` builds `SplTokenAdditionalDataV2::with_decimals(decimals)` with no multiplier ( [7](#0-6) ), the `uiAmount`/`uiAmountString` values returned will be exactly half of what `getTokenAccountBalance` reports for the same account/amount at the same slot, which correctly applies the `2.0` multiplier ( [8](#0-7) ).

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}

    pub fn get_token_account_balance(
        &self,
        pubkey: &Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<UiTokenAmount>> {
        let bank = self.bank(commitment);
        let account = bank.get_account(pubkey).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find account".to_string())
        })?;

        if !is_known_spl_token_id(account.owner()) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token account".to_string(),
            ));
        }
        let token_account = StateWithExtensions::<TokenAccount>::unpack(account.data())

        let mint = &Pubkey::from_str(&token_account.base.mint.to_string())
            .expect("Token account mint should be convertible to Pubkey");
        let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;
        let balance = token_amount_to_ui_amount_v3(token_account.base.amount, &data);
        Ok(new_response(&bank, balance))
    }
