### Title
Funded instant-withdraw claims are never removed from `instantWithdrawClaimsByEpoch`, inflating `defaultPendingClaimBasis` and permanently locking default-recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the kernel bug (an offset adjusted unconditionally without checking whether the field was in its "set" state), `IdleCreditVault.claimInstantWithdrawRequest` pays out a funded instant receipt and clears `instantWithdrawsRequests[_user]`, but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements the aggregate `instantWithdrawClaimsByEpoch[epoch]`. The aggregate is later consumed unconditionally by `defaultPendingClaimBasis()` whenever `pendingInstantWithdraws != 0`, treating already-paid claims as still-outstanding basis.

### Finding Description
In `requestInstantWithdraw` the vault increments both per-user and aggregate per-epoch ledgers (`instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount; instantWithdrawClaimsByEpoch[currentEpoch] += _amount`, lines 371-372). The normal funded claim path at lines 380-393 only does `_burn(_user, amount)`, `instantWithdrawsRequests[_user] = 0`, and `_transferFundedClaim` — the per-epoch mappings are left populated.

Only the *defaulted* claim path clears them: `_claimDefaultedInstantWithdrawRequest` zeroes `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and does `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` (lines 847-853).

`defaultPendingClaimBasis()` (lines 644-649) then computes:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

`pendingInstantWithdraws` tracks the *unfunded* remainder (decremented in `collectInstantWithdrawFunds`), while `instantWithdrawClaimsByEpoch[epochNumber]` counts *all* receipts ever minted in that epoch, including ones already fully funded and already paid out. So in an epoch where (a) at least one instant claim was funded and claimed, and (b) some later instant request remains partially unfunded when the borrower defaults, `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over a `totalBasis` inflated by the already-paid claims. The recovery price is pushed below the true ratio; every legitimate defaulted claimant is underpaid pro-rata, and the reserve slice attributed to the phantom basis is stranded forever — nothing can ever claim it (`_transferDefaultRecovery` only pays out against cleared receipts) and there is no sweep function for `defaultRecoveryReserve`.

### Impact Explanation
Permanent freezing of recovery funds and underpayment of every default-epoch claimant. The stranded amount equals roughly `staleBasis * recoveryPrice / 1e18`, which scales with the size of instant withdrawals funded earlier in the default epoch — not dust if instant withdrawals are material. The loss waterfall / "one receipt one payout" invariant is broken: a receipt already paid at par is counted a second time as an unpaid creditor.

### Likelihood Explanation
Requires an epoch in which some instant requests are funded and claimed (normal operation whenever the CDO holds enough cash or `getInstantWithdrawFunds` succeeds), a subsequent instant request in the same epoch that stays partially unfunded (`pendingInstantWithdraws > 0`), and a borrower default finalized that epoch. All actors are unprivileged users; the honest manager/borrower sequence (stopEpoch → default → finalizeDefault) triggers the mispricing automatically.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers for the epoch(s) being claimed (or track the current claim epoch) before paying out: zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, mirroring `_claimDefaultedInstantWithdrawRequest`. Alternatively, make `defaultPendingClaimBasis` derive the unfunded instant basis from `pendingInstantWithdraws` plus a per-epoch *unclaimed* ledger that is maintained on every claim path.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testStaleInstantBasisDilutesDefaultRecovery() external {
  // enable instant withdraws
  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(instantDelay, 1000, false);

  address earlyUser = makeAddr('early-instant');
  address lateUser  = makeAddr('late-instant');
  _depositWithUser(earlyUser, 10_000 * ONE_SCALE, true);
  _depositWithUser(lateUser, 10_000 * ONE_SCALE, true);

  // epoch 0 runs and repays normally
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

  // epoch 1: earlyUser requests instant withdraw, gets fully funded and claims
  vm.prank(earlyUser);
  cdoEpoch.requestWithdraw(0, address(AAtranche));
  _startEpochAndCheckPrices(1);
  vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
  vm.prank(manager);
  cdoEpoch.getInstantWithdrawFunds();
  vm.prank(earlyUser);
  cdoEpoch.claimInstantWithdrawRequest(); // paid at par, per-epoch ledger NOT cleared

  // lateUser files an instant request that stays unfunded
  vm.prank(lateUser);
  cdoEpoch.requestWithdraw(0, address(AAtranche));
  // borrower defaults without funding it
  _checkDefault();

  IdleCreditVault vault = IdleCreditVault(address(strategy));
  // BUG: basis includes earlyUser's already-paid claim
  uint256 basis = vault.defaultPendingClaimBasis();
  assertGt(basis, vault.pendingInstantWithdraws(), 'stale paid claim counted as basis');

  // finalize with enough to cover only the *real* unfunded basis at 70%
  // -> recoveryPrice is diluted; after all legitimate claims, reserve > 0 is stranded
  // assert residual: vault.defaultRecoveryReserve() > 0 after lateUser + active claims
}
```

Uncertainty note: I verified that `claimInstantWithdrawRequest` does not touch the per-epoch instant ledgers and that `defaultPendingClaimBasis` reads the aggregate unconditionally gated only on `pendingInstantWithdraws != 0`; I could not fully trace every write to `pendingInstantWithdraws` inside `IdleCDOEpochVariant.getInstantWithdrawFunds` within the tool budget, so the exact precondition (an unfunded remainder coexisting with a fully-claimed funded request in the same epoch) should be confirmed when writing the PoC.
