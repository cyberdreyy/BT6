### Title
Parser reuses Token-2022 instruction decoder for the legacy SPL Token program id, causing misreported instruction types - ([File: transaction-status/src/parse_token.rs])

### Summary
`parse_token()` unpacks every SPL-Token-family `CompiledInstruction` with `spl_token_2022_interface::instruction::TokenInstruction::unpack`, regardless of whether the instruction's `program_id` is the legacy `spl_token_interface` id or the `spl_token_2022_interface` id. Because `PARSABLE_PROGRAM_IDS` maps both ids to the single `ParsableProgram::SplToken` variant and `parse_token` never receives or checks the actual `program_id`, an attacker can craft an instruction addressed to the legacy Token program whose data byte matches a Token-2022-only extension opcode (e.g. `PausableExtension`, `CpiGuardExtension`, `TransferHookExtension`, etc.), and the RPC/`jsonParsed` decoder will report `program: "spl-token"` with a `parsed.type` (e.g. `"pause"`) that the real, on-chain legacy Token program has never implemented.

### Finding Description
`parse()` in [1](#0-0)  looks up `program_id` in `PARSABLE_PROGRAM_IDS`, which is built from `spl_token_ids()` mapping both the legacy and 2022 token program ids to the same `ParsableProgram::SplToken` value [2](#0-1) . Dispatch for that variant calls `parse_token(instruction, account_keys)` with no knowledge of which of the two ids was actually targeted [3](#0-2) .

`parse_token()` itself never inspects `program_id` — its signature only takes the `CompiledInstruction` and `AccountKeys` — and unconditionally calls `TokenInstruction::unpack` from the `spl_token_2022_interface` crate, which understands the full, extended Token-2022 opcode space, including `*Extension` variants such as `PausableExtension`, `CpiGuardExtension`, `TransferHookExtension`, `MetadataPointerExtension`, `GroupPointerExtension`, etc. [4](#0-3) [5](#0-4) . These opcodes are not part of the real, deployed legacy `Tokenkeg...` program's instruction set — that on-chain program will reject such data at execution time — but the parser has no such awareness and will happily decode and label the instruction as, e.g., `"pause"` while reporting `"program": "spl-token"` and `"programId": <legacy Token id>`.

An attacker only needs to submit (and have included on-chain, even if it fails at runtime) a transaction with a `CompiledInstruction` whose `program_id_index` points at the legacy Token program and whose `data` begins with one of the Token-2022-only opcode bytes. When any client later calls `getTransaction`/`get_transaction` with `jsonParsed` encoding, the transaction-status parsing path in this file produces a `ParsedInstruction` whose `program`/`program_id` claim legacy `spl-token` semantics while `parsed.type` reflects an operation the legacy program does not support, since the underlying decode is fully unconditional in program id.

### Impact Explanation
This is a decoder-misreporting bug in a read path reachable via a single unprivileged JSON-RPC call (`getTransaction`, jsonParsed). It does not crash the validator or corrupt consensus state, but it produces "wrong data returned" for a given, verifiable on-chain instruction: it invents a semantic label (e.g. `"pause"`, `"initializeCpiGuard"`, `"initializeTransferHook"`) for the legacy SPL Token program that the real deployed program cannot execute. Any downstream indexer, explorer, or wallet trusting the `parsed.type` field together with `program`/`programId` will misreport what actually happened (or would happen) with that instruction, matching the "decoder panic and misreporting" bounty category referenced in the rules.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: the attacker only needs to submit one transaction (that is later readable via `getTransaction`) whose instruction data byte matches a Token-2022 extension opcode while addressed at the legacy Token program id. No special privileges, staking, or validator control are required — this is a pure client-submitted-data + read-back scenario.

### Recommendation
Thread the actual `program_id` into `parse_token()` (or split `ParsableProgram::SplToken` into distinct legacy/2022 variants) and, based on which id is present, either use the legacy `spl_token_interface::instruction::TokenInstruction` decoder for the legacy program id (rejecting/returning `InstructionNotParsable` for opcodes only valid under Token-2022) or explicitly document/label output so `program`/`parsed.type` never imply Token-2022-only semantics for the legacy program id.

### Proof of Concept
Rust unit test (to add to `transaction-status/src/parse_token.rs` test module), asserting differential behavior between the two ids:
```rust
#[test]
fn test_legacy_token_rejects_extension_only_opcode() {
    // Build data for a Token-2022-only instruction, e.g. PausableExtension::Pause
    let mint = Pubkey::new_unique();
    let owner = Pubkey::new_unique();
    let pause_ix = pause(&spl_token_2022_interface::id(), &mint, &owner, &[]).unwrap();

    // Re-target the exact same instruction data/accounts at the LEGACY Token program id
    let legacy_ix = Instruction {
        program_id: spl_token_interface::id(),
        accounts: pause_ix.accounts.clone(),
        data: pause_ix.data.clone(),
    };
    let message = Message::new(&[legacy_ix], None);
    let compiled_instruction = &message.instructions[0];

    let result = parse_token(
        compiled_instruction,
        &AccountKeys::new(&message.account_keys, None),
    );

    // Expectation: should be rejected as unparsable/unsupported for the legacy program,
    // since the on-chain legacy Token program does not implement PausableExtension.
    assert!(result.is_err(), "legacy spl-token program must not report a Token-2022-only instruction type");
}
```
Currently this assertion fails: `parse_token` returns `Ok(ParsedInstructionEnum { instruction_type: "pause", .. })` even though `program_id` is the legacy Token program, demonstrating the misreporting.
