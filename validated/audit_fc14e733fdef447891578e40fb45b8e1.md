### Title
Unbounded per-notification serialization cost for accountSubscribe/programSubscribe on large on-chain accounts - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
`filter_account_result` in `rpc/src/rpc_subscriptions.rs` builds the `UiAccount` sent to `accountSubscribe`/`programSubscribe` clients by calling `encode_ui_account` directly, bypassing the size guard that `rpc/src/rpc.rs::encode_account` applies for HTTP RPC calls. When the client (attacker or victim) selects `Base64`/`Base64Zstd`/`JsonParsed` encoding, `account-decoder/src/lib.rs::encode_ui_account` base64-encodes/serializes the entire account buffer with no length cap, so the per-notification allocation and CPU cost scale linearly with the size of data the attacker wrote on-chain (up to the account max), independent of the "explicit limits, not attacker data size" cost assumption for the notification path (`RpcNotifier::notify` / `RPC_NOTIFIER_BUF`).

### Finding Description
- `rpc/src/rpc_pubsub.rs::account_subscribe`/`program_subscribe` (lines 424-476) build `AccountSubscriptionParams`/`ProgramSubscriptionParams` straight from client-supplied `encoding`/`data_slice`, defaulting encoding to `Binary` but allowing the attacker to request `Base64`, `Base64Zstd`, or `JsonParsed`.
- On each matching bank/account update, `rpc/src/rpc_subscriptions.rs::filter_account_result` (lines 370-392) computes the notification payload with:
  ```
  encode_ui_account(&params.pubkey, &account, params.encoding, None, None)
  ``` [1](#0-0) 
  Note this call hardcodes `None` for `data_slice_config`, i.e. it ignores `params.data_slice` entirely and always encodes the **full** account buffer, regardless of what the client requested.
- `account-decoder/src/lib.rs::encode_ui_account` (lines 46-101) only applies a size check for `Binary`/`Base58` encoding, via `encode_bs58`, which pre-checks length against `MAX_BASE58_BYTES` (128 bytes) before allocating a base58 string. For `Base64`/`Base64Zstd`, there is no such check — `BASE64_STANDARD.encode(slice_data(...))` (or the zstd encoder) is run unconditionally against the entire account data. `JsonParsed` falls back to the same unchecked `Base64` path when the data does not parse. [2](#0-1) 
- By contrast, the plain HTTP `getAccountInfo`/`getProgramAccounts` path in `rpc/src/rpc.rs::encode_account` explicitly rejects oversized `Binary`/`Base58` requests and forces callers to use base64, but that same guard function is not used by the subscription notification path. [3](#0-2) 
- Exploit flow: an attacker creates/owns an account and fills it with the maximum permitted on-chain data (an account can hold up to the protocol max data size). The attacker then subscribes via `accountSubscribe`/`programSubscribe` requesting `encoding: base64` and no `data_slice`. Each time the account is updated (an update the attacker themself triggers by writing to their account, respecting the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` limit), the subscription filter path re-encodes the full account buffer into a base64 string and serializes the resulting `UiAccount`/`RpcResponse` JSON payload, which is written by `RpcNotifier::notify` into the thread-local `RPC_NOTIFIER_BUF` via `serde_json::to_writer`. No length/queue-capacity check gates this per-notification payload size the way it does for the base58 path.

### Impact Explanation
This falls under the "RPC denial-of-service / resource-exhaustion from a single low-rate call" category: the cost of a single subscription notification is not bounded by a fixed protocol constant but scales with attacker-chosen on-chain account size, allowing repeated large allocations/CPU work (base64 encode + JSON serialize) in the validator's PubSub notification thread for every account update, at a rate the attacker fully controls by writing to their own account.

### Likelihood Explanation
Fully attacker-controlled and requires no privileged access: create one large account (max permitted account data), open one websocket subscription with `encoding: base64` (or default `JsonParsed` on non-parseable owner data) and no `data_slice`, then periodically write to the account (within the allowed one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` cadence) to trigger repeated full-size re-encodes. This is deterministic and repeatable.

### Recommendation
Route `filter_account_result` (and the analogous program-account notification path) through the same size-aware encoding helper used by `rpc/src/rpc.rs::encode_account`, enforcing the existing `data_slice`/size guards for subscription notifications, and honor `params.data_slice` instead of hardcoding `None`. Additionally, apply an explicit maximum serialized-notification-size check before writing into `RpcNotifier`'s buffer, dropping or truncating oversized notifications rather than performing an unconditional full-size base64/JSON encode.

### Proof of Concept
Integration test outline (in `rpc/src/rpc_subscriptions.rs` test module, using existing `rpc_pubsub_service::test_connection` helpers seen in the file's tests):
1. Create a bank/genesis, then process a transaction that allocates an account owned by a non-parseable program with the maximum permitted account data size and writes it once.
2. Call `rpc.account_subscribe(pubkey, RpcAccountInfoConfig { encoding: Some(UiAccountEncoding::Base64), data_slice: None, .. })`.
3. Update the account's data (same size) in a subsequent bank/slot and call `subscriptions.notify_subscribers(...)`.
4. Measure/assert: (a) the size of the JSON string returned by `receiver.recv()` is proportional to the account size (~4/3 of 10 MiB), and (b) there is no configured cap (`queue_capacity_bytes`) that rejects or truncates the notification — i.e., the full payload is delivered rather than a bounded/error response, in contrast to the `test_account_subscribe` case exercising `MAX_BASE58_BYTES` which does return a bounded "error: data too large" string. Assert failure of the invariant: notification payload size == O(account size), not O(fixed limit).

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
