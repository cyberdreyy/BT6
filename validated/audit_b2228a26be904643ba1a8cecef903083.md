## Title
Hardcoded Solend CPI instruction discriminators/account layouts break if the upstream Solend program changes its instruction interface, mirroring the Pendle router signature mismatch (`M-11`) - (`programs/solend-mocks/src/cpi.rs`)

### Summary
The Pendle bug (`M-11`) was caused by hardcoding the exact function signature/parameter list of an external protocol's instruction (`addLiquiditySingleSy`/`removeLiquiditySingleSy`) inside the integrating contract. When the external protocol (Pendle) shipped a new router version that added a mandatory `limit` parameter, every call from the integrating contract reverted because the account/argument layout no longer matched what the external program expected. Marginfi has the exact same structural risk in its Solend integration: instead of using the Solend SDK/IDL, marginfi re-implements the Solend CPI surface by hand with raw, hardcoded instruction discriminators and a fixed account ordering.

### Finding Description
`programs/solend-mocks/src/cpi.rs` hardcodes single-byte instruction discriminators for the real, mainnet Solend program (`declare_id!("So1endDq2YkqhipRh3WViPa8hdiSpxWy6z3Z6tMCpAo")` in `programs/solend-mocks/src/lib.rs`): [1](#0-0) [2](#0-1) 

Each CPI helper (`init_obligation`, `deposit_reserve_liquidity_and_obligation_collateral`, `withdraw_obligation_collateral_and_redeem_reserve_collateral`) manually builds the `Instruction` with a fixed account list and a single leading discriminator byte, exactly mirroring the pattern that broke in the Pendle case (fixed positional args/accounts with no forward compatibility): [3](#0-2) [4](#0-3) 

These helpers are invoked directly from marginfi's production instruction handlers for Solend integration banks — user-facing deposit/withdraw/init-obligation flows that any depositor into a Solend-integration bank will hit: [5](#0-4) [6](#0-5) 

If the real Solend program at `So1endDq2YkqhipRh3WViPa8hdiSpxWy6z3Z6tMCpAo` ever changes its instruction interface (adds a required account, changes discriminator width/values, or adds a mandatory argument — precisely the kind of change Pendle made when it added the `limit: LimitOrderData` parameter to `addLiquiditySingleSy`/`removeLiquiditySingleSy`), every one of these hand-rolled CPI calls will be built with a stale account list/argument encoding and will be rejected by the Solend program (invalid instruction data or missing/extra accounts), exactly as the Pendle router rejected marginfi's/Wise's stale calls with `RouterInvalidAction`.

### Impact Explanation
A breaking upstream change to Solend's instruction interface would cause all `init_obligation`, `deposit`, and `withdraw` CPI calls for Solend-integration banks to permanently revert. Because these are the only code paths (no fallback/legacy-vs-new-version branching exists) for moving funds into/out of Solend-integration banks, this would durably freeze all user deposit/withdraw operations against those banks — the same "protocol cannot use new/updated markets" impact class judged Medium in the original Pendle finding. Existing depositors' funds intermediated through the `liquidity_vault` could become stuck if withdraw CPIs start failing.

### Likelihood Explanation
This requires an upstream, out-of-marginfi's-control change (Solend shipping a new instruction interface/version), just like the Pendle case required Pendle to ship `PendleRouterV3`. It is not exploitable by an attacker directly, but is a durable, protocol-breaking maintenance risk with concrete precedent (Solend has previously changed reserve/obligation account layouts across program versions), and is architecturally identical to the confirmed Pendle finding: hand-encoded, unversioned CPI calls to a third-party program with no compatibility shim.

### Recommendation
Replace the hand-rolled discriminator/account-list encoding in `programs/solend-mocks/src/cpi.rs` with generated bindings from Solend's canonical IDL/SDK (as is already done for Kamino/Drift/JupLend via `declare_program!`), or add explicit version detection/negotiation so that a Solend program upgrade does not silently invalidate all integration CPI calls. At minimum, add integration tests that pin against the live mainnet Solend program's current instruction interface so a mismatch is caught before deployment rather than causing an on-chain revert for users.

### Proof of Concept
Not independently reproducible without a live/forked Solend program that has changed its instruction interface; the finding is a structural analog based on direct code inspection of `programs/solend-mocks/src/cpi.rs` showing hardcoded discriminators (`INIT_OBLIGATION_DISCRIMINATOR = 6`, `DEPOSIT_DISCRIMINATOR = 14`, `WITHDRAW_DISCRIMINATOR = 15`) and fixed account orderings called against the real Solend program ID, the same root-cause pattern documented and confirmed in the Pendle `M-11` finding.

pub fn init_obligation<'info>(
    ctx: CpiContext<'_, '_, '_, 'info, InitObligation<'info>>,
) -> Result<()> {
    let ix = Instruction {
        program_id: ID,
        accounts: vec![
            AccountMeta::new(*ctx.accounts.obligation_info.key, false),
            AccountMeta::new_readonly(*ctx.accounts.lending_market_info.key, false),
            AccountMeta::new_readonly(*ctx.accounts.obligation_owner_info.key, true),
            AccountMeta::new_readonly(*ctx.accounts.rent_info.key, false),
            AccountMeta::new_readonly(*ctx.accounts.token_program_info.key, false),
        ],
        data: vec![INIT_OBLIGATION_DISCRIMINATOR],
    };

    invoke_signed(
        &ix,
        &[
            ctx.accounts.obligation_info.to_account_info(),
            ctx.accounts.lending_market_info.to_account_info(),
            ctx.accounts.obligation_owner_info.to_account_info(),
            ctx.accounts.rent_info.to_account_info(),
            ctx.accounts.token_program_info.to_account_info(),
        ],
        ctx.signer_seeds,
    )?;

    Ok(())
}
