### Title
Instant-withdraw receipts can be created while claims are disabled, permanently freezing recovery funds and diluting default claimants - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.requestWithdraw` decides whether to route a request into the instant-withdraw path using `_isInstantWithdrawEnabled()`, which only checks `disableInstantWithdraw` and `isProgrammableBorrower` — it never checks `allowInstantWithdraw`. However `claimInstantWithdrawRequest` reverts unless `allowInstantWithdraw` is true. Disabling instant withdrawals via `allowInstantWithdraw = false` therefore leaves the request side open while permanently closing the claim side, letting a KYC'd lender mint receipt tokens and inflate `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` with claims that can never be exercised. At default finalization these unclaimable receipts consume claim basis and prefunded reserve, lowering `defaultRecoveryPrice` for honest claimants and locking the corresponding underlyings in `IdleCreditVault` forever.

### Finding Description
In `IdleCDOEpochVariant.sol:761-770`, `requestWithdraw` enters the instant path when `_isInstantWithdrawEnabled()` is true and the new epoch APR dropped by more than `instantWithdrawAprDelta`. `_isInstantWithdrawEnabled()` (lines 839-841) returns `!disableInstantWithdraw && !isProgrammableBorrower` — `allowInstantWithdraw` is absent. It calls `IdleCreditVault.requestInstantWithdraw`, which burns CDO strategy tokens, mints receipt tokens to the user, and increases `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`).

Claims go through `claimInstantWithdrawRequest` (`IdleCDOEpochVariant.sol:975-979`), which reverts when `!allowInstantWithdraw`. So when the owner disables instant withdrawals using `allowInstantWithdraw` (the natural "allow" flag) rather than `disableInstantWithdraw`, any request routed into the instant branch produces a receipt that can never be claimed.

The downstream damage lands in default accounting:

- `defaultPendingClaimBasis` (`IdleCreditVault.sol:644-649`) adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0`.
- `_defaultPrefundedInstantReserve` (`IdleCreditVault.sol:716-723`) treats the funded portion of those receipts as reserve backing them.
- `finalizeDefaultRecovery` (`IdleCreditVault.sol:661-710`) computes `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over a basis that includes the dead receipts, and sets `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`.

Since the attacker's claim path reverts (`_claimDefaultedInstantWithdrawRequest` is only reachable via `claimInstantWithdrawRequest`), the reserve slice and basis dilution attributable to those receipts is permanent: honest claimants receive a lower recovery price, and the underlying backing the dead receipts is stranded in the strategy. The same permanently-nonzero `pendingInstantWithdraws` also makes `_ensureDefaultRecoveryInitialized` revert (`IdleCreditVault.sol:924-935`) on any vault not yet initialized.

### Impact Explanation
An unprivileged KYC'd lender can permanently freeze a quantifiable portion of vault funds and dilute every other claimant's default recovery by `attackerReceiptBasis / totalBasis`. The underlyings transferred at `startEpoch` to fund instant claims (`collectInstantWithdrawFunds`, `IdleCreditVault.sol:398-403`) are locked in the strategy with no withdrawal path, and the inflated `totalBasis` reduces `defaultRecoveryPrice` paid to honest defaulted-epoch receipt holders and active LPs.

### Likelihood Explanation
Two conditions are needed, both realistic: (1) the owner disables instant withdrawals via `allowInstantWithdraw = false` — the flag's name and its use in `claimInstantWithdrawRequest` suggest this is the intended kill switch, while `disableInstantWithdraw` reads as a permanent-deprecation flag; (2) the next epoch's APR drops by more than `instantWithdrawAprDelta`, which is exactly the scenario instant withdrawals exist for. No privileged party misbehaves; the attacker only calls `requestWithdraw` during a normal buffer period.

### Recommendation
Add `allowInstantWithdraw` to the request-path gate, e.g. `_isInstantWithdrawEnabled()` should return `allowInstantWithdraw && !disableInstantWithdraw && !isProgrammableBorrower`, so a request can never enter a branch whose claim is disabled. Alternatively, remove the redundant flag and rely on a single switch checked by both request and claim.

### Proof of Concept
Foundry fork sketch (based on `TestIdleCDOBase` harness patterns):

```solidity
// Setup: epoch variant deployed, KYC'd attackerLP deposits, epoch running.
// 1. Owner disables instant withdraws via the allow flag only:
vm.prank(cdoEpoch.owner());
cdoEpoch.setAllowInstantWithdraw(false); // allowInstantWithdraw = false, disableInstantWithdraw stays false

// 2. Epoch stops with a lower APR (drop > instantWithdrawAprDelta), new buffer period opens.
_stopEpochWithLowerApr();

// 3. Attacker requests withdraw; _isInstantWithdrawEnabled() is still true so the
//    instant branch is taken: receipt minted, pendingInstantWithdraws > 0.
vm.prank(attackerLP);
cdoEpoch.requestWithdraw(0, AA); // burns tranche tokens, mints strategy-token receipt

assertGt(creditVault.pendingInstantWithdraws(), 0);
assertGt(creditVault.instantWithdrawsRequests(attackerLP), 0);

// 4. startEpoch funds the instant queue via collectInstantWithdrawFunds.
_startEpoch();

// 5. Attacker can never claim: claim path reverts on !allowInstantWithdraw.
vm.prank(attackerLP);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimInstantWithdrawRequest();

// 6. Borrower defaults; owner finalizes recovery. Dead receipts inflate
//    defaultPendingClaimBasis -> lower defaultRecoveryPrice; their funded
//    slice stays locked in the strategy permanently.
_handleBorrowerDefault();
uint256 price = creditVault.defaultRecoveryPrice();
// price is diluted by instantWithdrawClaimsByEpoch[epochNumber] that no one can claim;
// underlying backing it is stranded (defaultRecoveryReserve never fully drainable).
```

Note: exact setter names (`setAllowInstantWithdraw`) and the epoch helper calls should be matched to the deployed admin functions in `IdleCDOEpochVariant`; the core assertion — a nonzero `pendingInstantWithdraws` receipt whose only claim path reverts — follows directly from the code cited above.
