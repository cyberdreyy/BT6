### Title
`system_processor::create_account` Permanently Blocks Account Creation If a Griefer Pre-Funds the Target Address - (File: `programs/system/src/system_processor.rs`)

### Summary
The `SystemInstruction::CreateAccount` handler in `programs/system/src/system_processor.rs` rejects the instruction with `SystemError::AccountAlreadyInUse` whenever the target ("to") account already holds any lamports, exactly mirroring the reported `SeaportDeleverage` bug class: an unprivileged party can send an arbitrary token/lamport amount into an address the victim intends to control, and a strict "must equal zero"/"must not exist" balance check then permanently blocks the intended, legitimate operation for that address.

### Finding Description
`create_account` (used to process `SystemInstruction::CreateAccount`) contains a hard pre-check: [1](#0-0) 
Specifically: [2](#0-1) 
If `to.get_lamports() > 0`, the instruction unconditionally fails with `SystemError::AccountAlreadyInUse`, regardless of whether the account has been "used" in any meaningful sense (no data, no owner change) — it may simply have received a plain lamport transfer from any unprivileged sender, since anyone can transfer lamports to any pubkey with `SystemInstruction::Transfer` without the recipient's cooperation.

Because Solana addresses (especially PDAs, which have no private key and cannot sign transactions or move funds out) are frequently pre-computed off-chain (e.g., associated-token-account addresses, program-derived vault addresses) before the owning program actually calls `CreateAccount` via CPI to materialize them, an attacker who front-runs this initialization by sending even 1 lamport to that address can make every subsequent `CreateAccount` call targeting it fail permanently — the address can never be created via the standard path again, and for a PDA there is no way to reclaim/move the lamports out to "fix" the balance, since PDAs cannot sign.

This is the exact bug class from the report: a strict, unconditional balance-state assertion (there `BASE` balance == 0 after full deleverage, here `to.get_lamports() == 0` before creation) that can be permanently violated by any unprivileged party sending funds into the target account, bricking the legitimate flow for that address with no in-protocol recovery.

The codebase's own fix corroborates this: an alternate instruction path, `SystemInstruction::CreateAccountAllowPrefund` / `create_account_allow_prefund`, was added specifically to allow account creation when lamports have already been sent to the address: [3](#0-2) 
This mirrors the external report's own remediation, i.e., removing/loosening the "must be pristine" balance check. However, this remediation is feature-gated: [4](#0-3) 
`create_account_allow_prefund` is referenced in `feature-set/src/lib.rs`, `svm-feature-set/src/lib.rs`, `cost-model/src/cost_model.rs`, and `transaction-status/src/parse_system.rs`, indicating it is a new, separately-activated feature rather than a change to the base `CreateAccount` behavior — meaning any cluster/program that has not integrated `CreateAccountAllowPrefund` (or that has this feature inactive) remains fully exposed to the griefing described above.

### Impact Explanation
This does not directly move funds or corrupt consensus, but it constitutes a transaction-triggered, unprivileged denial-of-service: any single, unsigned, cheap `Transfer` instruction sent by any account can permanently prevent a specific address (frequently a PDA with no recovery path) from ever being initialized via `CreateAccount`. For protocols relying on deterministic PDAs/ATAs created lazily via CPI to the system program (a very common pattern across the Solana ecosystem), this can permanently disable a legitimate on-chain account/vault for as little as 1 lamport, until/unless `CreateAccountAllowPrefund` is both activated cluster-wide and adopted by the calling program.

### Likelihood Explanation
Trivial to trigger: the attacker only needs to know or compute the target address in advance (deterministic PDAs are, by definition, publicly computable) and send it any nonzero lamport amount via a standard, unsigned-by-victim `SystemInstruction::Transfer` before the legitimate `CreateAccount` call executes. No special privileges, signatures from the victim, or race conditions beyond simple front-running are required.

### Recommendation
Where practical, callers (particularly programs that lazily create PDAs via CPI) should use `SystemInstruction::CreateAccountAllowPrefund` instead of `CreateAccount` once/where the feature is activated, so pre-funded addresses can still be initialized. More generally, consider whether the base `create_account` check should distinguish "already funded" (recoverable) from "already has data/owner" (truly in use), rather than treating any nonzero lamport balance as an unconditional failure, to reduce reliance on a separately-gated instruction for what is a widely reachable griefing vector.

### Proof of Concept
1. Attacker computes/knows a PDA address `P` that some program will later create via CPI `system_instruction::create_account(payer, P, lamports, space, owner)`.
2. Attacker submits `SystemInstruction::Transfer` sending 1 lamport from any funded account to `P`. This succeeds unconditionally via `transfer`/`transfer_verified`: [5](#0-4) 
3. The victim program's later CPI to `create_account` targeting `P` now hits `to.get_lamports() > 0` and unconditionally returns `SystemError::AccountAlreadyInUse`: [6](#0-5) 
4. Since `P` is a PDA, it cannot sign a transaction to move the lamports elsewhere, so this failure is permanent unless the calling program is updated to use `CreateAccountAllowPrefund` (feature-gated) instead.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}
