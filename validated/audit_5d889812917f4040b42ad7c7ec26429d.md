### Title
Stale cache entry when a stake/vote account changes owner is not evicted in `StakesCache::check_and_store` - (File: `runtime/src/stakes.rs`)

### Summary
The reported bug pattern is a mapping keyed by an entity identity that is not cleared when that entity is "removed," letting the identity be re-associated with new data while the stale mapping entry from the old association is still applied. The closest reachable analog in this Agave codebase is an explicitly-acknowledged gap in `StakesCache::check_and_store`, which decides whether to update or evict an account from the stakes cache based only on its current owner, with a `TODO` noting that an owner change is not handled.

### Finding Description
`StakesCache::check_and_store` is the single entry point that keeps the in-memory `Stakes<StakeAccount>` cache (vote accounts and stake delegations, which directly drive stake-weighted rewards and leader/consensus stake calculations) synchronized with on-chain account writes. [1](#0-0) 

The function branches purely on the account's current `owner()`: if the owner is the vote program it goes through `upsert_vote_account`/`remove_vote_account`; if it's the stake program it goes through `upsert_stake_delegation`/`remove_stake_delegation`. Critically, the code carries an explicit acknowledgement that an owner transition is not handled:
```
// TODO: If the account is already cached as a vote or stake account
// but the owner changes, then this needs to evict the account from
// the cache. see:
// https://github.com/solana-labs/solana/pull/24200#discussion_r849935444
``` [2](#0-1) 

This is structurally the same defect as the `_marketWeightsByToken` bug: an association keyed by a pubkey (analogous to `rewardToken`) is written into a cache/mapping (`vote_accounts` / `stake_delegations`, analogous to `_marketWeightsByToken`), and when the underlying entity is repurposed (owner changes away from stake/vote program and back, or reassigned to a different role), the code path that would need to clear the stale cache entry for that pubkey is only reached via the `owner()` branch that matches the *new* state — there is no explicit "owner changed, evict old association first" step for the case where the pubkey transitions between being a stake account and something else and back.

I was not able to fully trace, within the remaining tool budget, every accounts-db code path guaranteeing that `check_and_store` is invoked for every intermediate account state transition (including reallocation/reassignment sequences within a single or across transactions) to conclusively prove an end-to-end exploitable sequence reachable purely from an unprivileged transaction sender. The `upsert_stake_delegation`/`remove_stake_delegation`/`upsert_vote_account`/`remove_vote_account` implementations that determine exactly how `delegated_stakes` and `vote_accounts` entries are added/removed were not fully read before the tool budget was exhausted, so the precise mechanics of whether a genuinely stale entry can persist (versus being naturally overwritten on the next `upsert`) could not be confirmed with certainty.

### Impact Explanation
If an owner-change scenario can leave a stale `stake_delegations` or `vote_accounts` entry in the cache (as the TODO suggests was a known open concern), the impact would be high: stake and reward accounting is derived directly from this cache (`Stakes<StakeAccount>` feeds `calculate_rewards`, `calculate_stake_rewards_and_commissions`, and `EpochStakeInfo`/`EpochStakes` used for leader schedule and stake-weighted voting), so incorrect stale entries could corrupt reward distribution or stake-weight calculations, which are consensus-relevant.

### Likelihood Explanation
Low. This requires a specific account owner-transition sequence that is constrained by Solana's system-level rules for changing account ownership (generally only possible when transitioning through the System Program with zero data), and the code explicitly documents this as an already-considered, long-standing edge case rather than a newly-introduced regression. I could not confirm, given the remaining investigation budget, that a concrete transaction sequence exists today that produces a genuinely-stale (as opposed to correctly-overwritten) cache entry.

### Recommendation
Complete the eviction logic referenced by the TODO in `check_and_store`: when an account's owner no longer matches the program that its previously-cached entry corresponds to, explicitly call `remove_vote_account`/`remove_stake_delegation` for the *old* classification before processing the *new* owner's branch, rather than relying on each branch to only handle its own program ID.

### Proof of Concept
Not established with certainty — the exact instruction sequence needed to force an owner transition of a previously-cached stake/vote account through `check_and_store` without going through the corresponding removal branch was not fully verified against `upsert_stake_delegation`/`remove_stake_delegation`/`upsert_vote_account`/`remove_vote_account` semantics within the available investigation.

    pub(crate) fn check_and_store(
        &self,
        pubkey: &Pubkey,
        account: &impl ReadableAccount,
        new_rate_activation_epoch: Option<Epoch>,
        use_fixed_point_stake_math: bool,
    ) {
        // TODO: If the account is already cached as a vote or stake account
        // but the owner changes, then this needs to evict the account from
        // the cache. see:
        // https://github.com/solana-labs/solana/pull/24200#discussion_r849935444
        let owner = account.owner();
        // Zero lamport accounts are not stored in accounts-db
        // and so should be removed from cache as well.
        if account.lamports() == 0 {
            if solana_vote_program::check_id(owner) {
                let _old_vote_account = {
                    let mut stakes = self.0.write().unwrap();
                    stakes.remove_vote_account(pubkey)
                };
            } else if stake_program::check_id(owner) {
                let mut stakes = self.0.write().unwrap();
                stakes.remove_stake_delegation(
                    pubkey,
                    new_rate_activation_epoch,
                    use_fixed_point_stake_math,
                );
            }
            return;
        }
