### Title
Unsanitized Vault auth `path` allows traversal outside the `auth/` mount prefix - (File: helpers/vault/auth_methods/jwt/auth.go)

### Summary
The `path` value used to build the Vault JWT auth login URL is taken directly from job-configured `secrets.vault.auth.path` (with `${VARIABLE}` expansion) and joined with `path.Join("auth", a.path, "login")` without any validation. Because `path.Join` calls `path.Clean`, a value containing `..` segments can strip the `auth/` prefix entirely and redirect the Vault `Write` call to an arbitrary path.

### Finding Description
`AuthMethod.Authenticate` builds the request path as: [1](#0-0) 
`a.path` comes straight from the job's Vault secret configuration (`VaultSecret.Server.Auth.Path` → `AuthPath()`), which supports `${CI_...}` variable expansion before being handed to `NewMethod`: [2](#0-1) 
`NewMethod` stores this string with no format/character validation: [3](#0-2) 
`path.Join` normalizes `..` components (`path.Join("auth", "../role-x", "login")` → `"role-x/login"`), so a value like `../other-mount` in the auth `path` field causes the resulting request path to escape the `auth/` prefix completely, targeting `other-mount/login` (or any arbitrary Vault path reachable via traversal) instead of the intended `auth/<mount>/login`. No allowlist, prefix check, or `path.Clean`-aware rejection of `..` exists anywhere between the job spec and `client.Write` (`helpers/vault/client.go:96-99`), nor in `helpers/vault/service/vault.go`'s `prepareAuthMethodAdapter`, which simply forwards `AuthPath()`/`AuthData()` unchanged.

### Impact Explanation
If an unprivileged actor can influence the auth-path string that ends up in `secrets.vault.auth.path` (e.g., a pipeline variable interpolated into that field by the `.gitlab-ci.yml` author, or any process where this string flows from job-controlled data), they can redirect the Runner's authentication `Write` call to a different Vault auth mount/role login endpoint than the operator intended. Because this call happens *before* the client has a Vault token (unauthenticated JWT login), a successful traversal only yields impact if the target endpoint also accepts anonymous login and returns a token with the JWT/claims the attacker controls — in which case the attacker could obtain a token bound to a different, potentially higher-privileged Vault role than the one the operator provisioned for that pipeline, enabling cross-project secret access. The `role` field is sent inside the JSON payload (not the path), so `role` traversal itself is not a path-escape vector — the concrete escape vector is limited to the `path`/`auth.path` field.

### Likelihood Explanation
This requires the operator to have configured the Vault secret's `auth.path` using a variable that is expandable/overridable by a lower-privileged pipeline trigger (the scenario is explicitly granted as a precondition in the prompt). Whether an "unprivileged pipeline author" in practice can set that specific variable depends entirely on project-level CI/CD variable protection settings, which Runner does not control. The underlying code defect (missing traversal check before `path.Join`) is real and independent of that precondition, but Runner's code has no built-in enforcement that operators must use fixed, non-interpolated auth paths — this is a genuine missing input-sanitization gap in `Authenticate`.

### Recommendation
In `jwt.method.Authenticate` (or `NewMethod`), validate that the resolved `path` does not escape the intended `auth/` mount: reject or `path.Clean`-and-compare the joined result to ensure it still has the `auth/` prefix, or reject any path segment containing `..`/absolute paths before calling `path.Join`.

### Proof of Concept
```go
func TestAuthenticate_PathTraversalRejected(t *testing.T) {
    m, err := jwt.NewMethod("../other-mount", auth_methods.Data{"jwt": "x"})
    require.NoError(t, err)

    mockClient := new(vault.MockClient)
    // Assert Write is never invoked with a path outside "auth/"
    mockClient.On("Write", mock.MatchedBy(func(p string) bool {
        return !strings.HasPrefix(p, "auth/")
    }), mock.Anything).Run(func(mock.Arguments) {
        t.Fatal("Write called outside auth/ prefix — traversal succeeded")
    })

    err = m.Authenticate(mockClient)
    require.Error(t, err) // expect rejection instead of a Write call
}
```
Expected (current) behavior: `client.Write` is invoked with path `"other-mount/login"` (outside `auth/`), demonstrating the missing check. After a fix, `Authenticate` should return an error before calling `client.Write`.
