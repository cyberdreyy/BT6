### Title
Malicious current-tenure miner can indefinitely suppress its own inactivity timeout by resetting `last_activity_time` with rejected/conflicting proposals - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` updates the tenure's `last_activity_time` whenever a proposal arrives that does *not* actually extend the tenure (i.e. it is rejected for being no higher than the current tip, or it conflicts with a fresh pre-commit), as long as it falls within `reorg_attempts_activity_timeout`. This timestamp is the sole input to `SortitionState::is_timed_out`, which gates whether signers ever fall back from the current miner to the prior tenure's miner. A miner who has legitimately won the current sortition (a "one-slot miner") can therefore keep sending proposals that get rejected by the signer set but still count as "activity," permanently defeating `block_proposal_timeout` and blocking the fallback path in `check_miner_inactivity`.

### Finding Description
`check_latest_block_in_tenure` [1](#0-0)  rejects a proposal whose `chain_length` does not exceed the tenure's last signed/accepted block, but as a side effect it calls `signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` when the conflicting proposal is still within `reorg_attempts_activity_timeout` of the last group signature, explicitly to "count [it] towards valid miner activity." A second branch does the same for a proposal that conflicts with a fresh pre-commit [2](#0-1) .

This timestamp is later read back by `SortitionState::is_timed_out` in both the v1 and v2 chainstate implementations: [3](#0-2) [4](#0-3) 

`is_timed_out` only measures elapsed time since `last_activity_time` (or the burn-block receipt time) against `block_proposal_timeout`; it has no independent way to distinguish "the miner produced a proposal that could plausibly become the canonical tip" from "the miner repeatedly resubmitted a stale/duplicate proposal that will never be signed." `check_miner_inactivity` in `stacks-signer/src/v0/signer_state.rs` relies entirely on `is_timed_out` to decide whether to fall back to the prior sortition's miner [5](#0-4) .

Because `check_latest_block_in_tenure` is only reached after the proposal has already passed the pubkey-hash check against the sortition winner (`proposed_by.state().data.miner_pkh != miner_pkh` in `v1.rs`) [6](#0-5) , this griefing path is only reachable by the actual current sortition-winning miner — i.e. exactly the "one-slot miner" capability permitted by the scope of this analysis. That miner can repeatedly submit blocks at (or below) the currently accepted `chain_length` — each rejected with `RejectReason` for not confirming the latest block — yet each rejection resets `last_activity_time` and restarts the `block_proposal_timeout` clock, as long as consecutive submissions are spaced under `reorg_attempts_activity_timeout`.

### Impact Explanation
This breaks the liveness guarantee that `block_proposal_timeout` is supposed to provide: a byzantine or unresponsive-but-adversarial current-tenure miner can hold the tenure indefinitely without ever producing a validly signable, tip-extending block, while preventing signers from ever invalidating it and reverting to the prior sortition's miner (`check_miner_inactivity`). This matches the "High" impact category: a signer wedged into never signing valid blocks because the fallback/timeout mechanism that would otherwise recover liveness is permanently defeated by the very miner it is meant to police.

### Likelihood Explanation
Likelihood is moderate-to-high in an adversarial-miner model: it requires only that the current sortition winner (already a single, trusted-until-proven-otherwise slot) be malicious or buggy, needs no majority of signers, no other signer's key, and no auth token. It only requires sending signed block proposals over the ordinary miner-to-signer StackerDB channel at a cadence faster than `reorg_attempts_activity_timeout` (default configurable, historically on the order of tens of seconds to a few minutes), which is easily automatable.

### Recommendation
Do not treat every rejected/non-extending proposal as fresh "activity" for purposes of suppressing `block_proposal_timeout`. Specifically:
- Bound the number of times, or the total additional time, that a given tenure's `last_activity_time` can be pushed forward by non-extending (rejected) proposals before `is_timed_out` is allowed to fire regardless.
- Alternatively, track "genuine" activity (e.g., a proposal that at least matches or exceeds the previously known canonical parent, rather than any conflicting/duplicate one) separately from reorg-timing credit, so a stalled miner replaying old/duplicate proposals cannot indefinitely reset the same timer that governs miner invalidation.
- Ensure the fix does not itself reintroduce the previously-fixed "pre-commit suppresses miner inactivity" bug (see `stacks-signer/changelog.d/precommit-suppresses-miner-timeout.fixed`) [7](#0-6) ; the same discipline (do not count non-canonicalizable signals as "signed activity") should be applied here.

### Proof of Concept
1. Miner M wins the current sortition and successfully has an initial block B0 signed/accepted for tenure T (so `has_signed_block_in_tenure` is true only transiently — assume no block has yet been globally accepted, or M avoids ever completing a valid tip-extending proposal after the first).
2. Every `reorg_attempts_activity_timeout - ε` seconds, M crafts and signs a new `NakamotoBlock` for tenure T with `chain_length` equal to (or below) the currently known tip, changing only the timestamp to satisfy `min_time_between_blocks_ms`, and broadcasts it as a `BlockProposal` over its miner StackerDB slot.
3. Each proposal reaches `check_proposal` → passes the `miner_pkh` check (it is M, the legitimate winner) → reaches `check_latest_block_in_tenure`, which rejects it (`chain_length <= info.block.header.chain_length`) but calls `update_last_activity_time` because `signed_group + reorg_attempts_activity_timeout > now` [8](#0-7) .
4. `SortitionState::is_timed_out` never observes `elapsed > block_proposal_timeout` because `last_activity_time` keeps being bumped, so `check_miner_inactivity` never falls back to the prior sortition's miner, and the tenure stalls indefinitely with no new blocks reaching the chain.

Note: I was not able to independently trace every intermediate call from `confirms_latest_block_in_same_tenure` to `check_latest_block_in_tenure` in this session (tool budget exhausted before that final read completed), so the exact call graph linking `check_proposal` → `confirms_latest_block_in_same_tenure` → `check_latest_block_in_tenure` should be re-verified, though the surrounding code strongly indicates this is the intended path based on `chainstate/mod.rs` documentation comments and the `v1.rs`/`v2.rs` proposal-check flow already inspected.

        tenure_id: &ConsensusHash,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,
    ) -> Result<bool, ClientError> {
        let last_block_info = SortitionData::get_tenure_last_block_info(
            tenure_id,
            signer_db,
            tenure_last_block_proposal_timeout,
        )?;

        if let Some(info) = last_block_info {
            // N.B. this block might not be the last globally accepted block across the network;
            // it's just the highest one in this tenure that we know about.  If this given block is
            // no higher than it, then it's definitely no higher than the last globally accepted
            // block across the network, so we can do an early rejection here.
            if block.header.chain_length <= info.block.header.chain_length {
                warn!(
                    "Miner's block proposal does not confirm as many blocks as we expect";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "expected_at_least" => info.block.header.chain_length + 1,
                );
                if info.signed_group.is_none_or(|signed_time| {
                    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
                }) {
                    // Note if there is no signed_group time, this is a locally accepted block (i.e. tenure_last_block_proposal_timeout has not been exceeded).
                    // Treat any attempt to reorg a locally accepted block as valid miner activity.
                    // If the call returns a globally accepted block, check its globally accepted time against a quarter of the block_proposal_timeout
                    // to give the miner some extra buffer time to wait for its chain tip to advance
                    // The miner may just be slow, so count this invalid block proposal towards valid miner activity.
                    if let Err(e) = signer_db.update_last_activity_time(
                        &block.header.consensus_hash,
                        get_epoch_time_secs(),
                    ) {
                        warn!("Failed to update last activity time: {e}");
                    }
                }
                return Ok(false);
            }

impl SortitionState {
    /// Check if the given sortition identified by its ConsensusHash has timed out based on current signed blocks
    /// and the time at which the burn block for it was first recorded in the provided signerdb
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }

    /// the blocks within the signer db and the block proposal timeout

        sortition: &ConsensusHash,
        signer_db: &SignerDb,
        eval: &GlobalStateEvaluator,
        local_address: &StacksAddress,
        timeout: Duration,

        // committed a signature to this tenure and must not help abandon it.

            return Ok(false);

        let Some(received_ts) =

            return Ok(false);

            return Ok(false);

            info!("Sortition has timed out";

                "timeout" => %timeout.as_secs(),
                "elapsed" => %elapsed.as_secs()
