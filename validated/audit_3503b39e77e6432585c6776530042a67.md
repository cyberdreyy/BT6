### Title
Stale confirmations from removed members are counted toward `num_confirmations`, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` only strips confirmations for requests that the removed member *created* (`r.member == member`), but never removes that member's entry from the `confirmations: LookupMap<RequestId, HashSet<String>>` of requests they merely *confirmed*. Consequently, a stale confirmation string from a since-removed member is still counted by `confirm()`'s `confirmations.len() as u32 + 1 >= self.num_confirmations` check, letting a request execute with fewer than `num_confirmations` confirmations from members who are actually live at execution time.

### Finding Description
The invariant the multisig is supposed to guarantee is:
`|{ c ∈ confirmations(request_id) : c ∈ current_members }| + (new confirmer) == num_confirmations` at the moment of execution.

In practice the code only checks the raw set size: [1](#0-0) 
`confirm()` reads `self.confirmations.get(&request_id)` and compares `confirmations.len() as u32 + 1 >= self.num_confirmations` without ever re-validating that every string already present in the set still corresponds to a `MultisigMember` currently in `self.members`.

`delete_member` is the only place that prunes `confirmations`, and it does so **only for requests authored by the removed member**: [2](#0-1) 
It filters `self.requests` for `r.member == member` (the request's *creator*) and removes those requests' confirmation sets and the member's `num_requests_pk` entry. It never scans other requests' `confirmations` HashSets to strip the removed member's identity string from requests they had only *confirmed* but did not create.

Exploit flow:
1. Member `D` creates request `R` via `add_request` (`R.member == D`).
2. Member `B` calls `confirm(R)`; since the confirmation count doesn't yet reach `num_confirmations`, `B`'s identity string is stored in `confirmations[R]` (branch at `multisig2/src/lib.rs:310-314`).
3. Through normal multisig governance, the members later pass a `DeleteMember { member: B }` request, executing `delete_member`, which removes `B` from `self.members` and clears `num_requests_pk[B]`, but leaves `confirmations[R]` containing `B`'s stale string because `R.member == D`, not `B`.
4. Remaining live members (e.g. `A`, `C`) confirm `R`. The threshold check counts the stale `B` entry plus the new live confirmations, so `R` executes (e.g. a `Transfer` action moving funds) even though fewer than `num_confirmations` *live* members actually approved it.

`assert_valid_request` (`multisig2/src/lib.rs:407-423`) only checks that the *caller* is currently a member; it never re-validates the members recorded in `confirmations`. `current_member()` (`multisig2/src/lib.rs:322-339`) is likewise only used to validate the new confirmer, not to prune stale entries. No other guard revisits `confirmations` contents on membership change except the narrow "requests created by this member" filter in `delete_member`.

### Impact Explanation
A request (including a `Transfer` action that moves NEAR out of the multisig account) can execute with a confirmation set that includes identities no longer in `self.members`, i.e., the request is approved by fewer live members than `num_confirmations` requires. This directly matches the listed Critical impact category "a multisig request executed below `num_confirmations` live members," and can be leveraged to move account funds out of the multisig without the intended quorum of currently-authorized signers. The flaw is repeatable any time a member who has confirmed but not created a pending request is later removed while that request remains outstanding.

### Likelihood Explanation
The precondition is common in normal multisig operation: staggered confirmations (member confirms before quorum is reached) combined with routine member rotation (e.g., revoking a compromised or departing signer) while a request is still pending. No attacker privilege escalation is required beyond ordinary multisig member behavior/timing; a malicious or compromised member simply needs to confirm a request and then be removed (or arrange removal) while the request is still open, after which any remaining members' confirmations plus the stale entry cross the threshold.

### Recommendation
When deleting a member, iterate all entries in `self.confirmations` (not just requests authored by the member) and remove the member's identity string from every confirmation set. Alternatively, when checking the threshold in `confirm()`, filter `confirmations` to only those entries still present in `self.members` before comparing against `num_confirmations`.

```rust
fn test_stale_confirmation_counted_after_member_removal() {
    // members: alice, bob, carol(access key D), key_member(access key B) ... construct 4 members, num_confirmations = 3
    // 1. As D (a member), add_request(Transfer) -> request_id R, R.member == D
    // 2. As B (a member), confirm(R) -> confirmations[R] == {B}, len==1 < 3, not executed
    // 3. Simulate governance removing B via DeleteMember request (separate request, executed with 3 live confirmations)
    //    -> asserts confirmations[R] still contains "B" (stale) because R.member != B
    // 4. As C (a member), confirm(R) -> confirmations.len()==1(stale B)+1(C)=2 < 3
    // 5. As A (a member), confirm(R) -> confirmations.len()==2+1==3 >= num_confirmations -> executes Transfer
    // Assert: only A and C are live members that actually confirmed; count of live confirmers == 2 < num_confirmations == 3
    // yet c.requests no longer contains R (it executed), proving execution occurred below live-member threshold.
}
```
The binding to assert on both sides: `live_confirmers(R) = |{c in confirmations[R] before final confirm : c in current members}|` vs `num_confirmations`. Before the fix, execution occurs when `live_confirmers(R) + 1 < num_confirmations` (here `2 < 3`) yet the request is still executed, proving the invariant "an executed request is confirmed by `num_confirmations` members who are members at execution time" is broken.

```rust
        self.assert_valid_request(request_id);

        }
```

```rust
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
```
