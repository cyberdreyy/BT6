No vulnerability found for this question.

The instruction `disable_staked_oracles` is gated by both a `has_one = admin @ MarginfiError::Unauthorized` constraint on `group` and a genuine `Signer<'info>` `admin` account [1](#0-0) . The `enable_staked_oracle_onramp` instruction has the identical admin/signer gating [2](#0-1) .

Grepping the whole program for `disable_staked_oracles`/`enable_staked_oracle` shows these functions are referenced only in `lib.rs` (the direct anchor instruction dispatch), the `on_ramp_transition.rs` module itself, and tests — there is no other instruction handler anywhere in the program that internally calls this logic via CPI with a PDA signer [3](#0-2) . Both `lib.rs` entrypoints simply forward the `Context` unchanged to `marginfi_group::disable_staked_oracles`/`marginfi_group::enable_staked_oracle_onramp`, with no alternate wrapper instruction. Tests confirm a non-admin signer attempting either instruction fails with `Unauthorized` (error 6042) [4](#0-3) [5](#0-4) .

No permissionless CPI wrapper or alternate entrypoint exists that forwards a PDA signer in place of a real `admin` `Signer`, so the described attack path is not reachable.
