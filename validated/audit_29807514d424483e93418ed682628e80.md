### Title
`parse_signers` misreports a valid single-authority Transfer/Approve/Burn as a multisig instruction when an extra throwaway account is appended - ([File: transaction-status/src/parse_token.rs])

### Summary
`parse_signers` in `transaction-status/src/parse_token.rs` decides whether an SPL-Token instruction (`Transfer`, `Approve`, `Burn`, `MintTo`, `SetAuthority`, etc.) is multisig-authorized purely by comparing `accounts.len()` to `last_nonsigner_index + 1`, with no verification that the referenced account actually holds Multisig-owned data. An attacker can append one extra, unrelated non-signing pubkey to a normal (non-multisig) instruction's `accounts` list; on-chain the SPL-Token program's `validate_owner` logic ignores the unused extra account and processes it as an ordinary single-authority instruction, but the transaction-status decoder reports it as a multisig instruction with a fabricated `signers` array.

### Finding Description
`parse_signers` is invoked from `parse_token` for `Transfer`, `Approve`, `Revoke`, `SetAuthority`, `MintTo`, `Burn`, `CloseAccount`, `FreezeAccount`, `ThawAccount`, `TransferChecked`, `ApproveChecked`, `MintToChecked`, `BurnChecked`, `WithdrawExcessLamports`, and `UnwrapLamports` [1](#0-0) . Its logic is: [2](#0-1) 

The branch is chosen solely from `accounts.len()` vs. `last_nonsigner_index + 1`; there is no check on-chain-account data (e.g. whether the account at `last_nonsigner_index` is actually a `Multisig`-owned account). This directly implements the exact boundary condition in the question: if `accounts.len() == last_nonsigner_index + 2` (exactly one extra account past what is minimally required, checked only for a *minimum* count by `check_num_token_accounts`/`check_num_accounts`), the code unconditionally treats the account at `last_nonsigner_index` as a `multisigAuthority`/`multisigOwner` and treats the single trailing extra pubkey as the sole `signers` entry, instead of the true `authority`/`owner` field.

Crucially, the real SPL-Token/Token-2022 program's `validate_owner` routine only treats the following accounts as required multisig signers when the account at the "owner" position is actually owned by the token program and deserializes as `Multisig` data; otherwise it simply checks `is_signer` on that account and ignores any additional accounts present in the instruction. Solana's runtime does not require that every account passed to a program actually be consumed by it. This means an attacker can submit (and have confirmed) a completely ordinary, successful Transfer/Approve/Burn instruction where the authority account is a normal keypair (not a Multisig account), but with one extra unrelated pubkey appended to `instruction.accounts`. On-chain, this executes and finalizes exactly like a normal single-signer transfer. When any client fetches that transaction via `getTransaction`/`getConfirmedTransaction` with `jsonParsed` encoding, `parse_token` → `parse_signers` will render it with a fake `multisigAuthority` and `signers: [<attacker-controlled throwaway pubkey>]`, completely omitting the real `authority` field.

No existing guard prevents this: `check_num_token_accounts`/`check_num_accounts` (in `parse_instruction.rs`) only enforce a *minimum* account count, not an exact one, and `parse_token`'s only accounts bound check is that the max account index is within `account_keys.len()` [3](#0-2) . Nothing cross-validates the parsed account list against actual on-chain account state (Multisig vs. plain key) at decode time — the decoder is a pure syntactic transformation of the raw `CompiledInstruction`.

### Impact Explanation
This is a decoder misreporting bug in `solana-transaction-status`, reachable purely by submitting one on-chain transaction containing an attacker-crafted instruction and later reading it back via a standard read-only RPC call (`getTransaction`/`getConfirmedTransaction`, `jsonParsed`). It falls under the explicitly accepted "decoder ... misreporting" impact category. Concretely, integrators, explorers, and wallets that trust the jsonParsed `parsed.info` field to determine the authorizing key for a Transfer/Approve/Burn will see a bogus multisig structure and a fabricated signer, and will fail to identify the actual `authority` pubkey that authorized the transfer — undermining any downstream analysis, compliance tooling, or UI display relying on that field.

### Likelihood Explanation
Fully attacker-controlled and trivially repeatable: the attacker needs to construct exactly one transaction with an SPL-Token instruction whose `accounts` array has one extra, non-multisig pubkey appended (a throwaway key the attacker generates), have it confirmed on-chain (it will actually succeed normally, since the token program ignores the unused extra account for a non-multisig owner), and then issue a single `getTransaction` RPC call with `encoding: jsonParsed`. No elevated privileges, staking, leader/validator control, or repeated high-rate calls are required.

### Recommendation
`parse_signers` should not infer "multisig" purely from account-list length. Since transaction-status has no access to account state at decode time, the safest fix is to stop guessing: either (a) always report the last non-signer-indexed account as the singular `authority`/`owner` and separately, unconditionally list any additional trailing accounts under a neutral field such as `signers` without renaming the primary field to a "multisig" variant, or (b) document/flag that the multisig interpretation is a heuristic and cannot be trusted without independently checking the referenced account's on-chain data for `Multisig` state (e.g., via `parsed_account_data` combined with an actual account fetch) before labeling it multisig in any downstream consumer.

### Proof of Concept
Rust unit test added to `transaction-status/src/parse_token.rs` `mod test`, demonstrating the boundary condition:

```rust
#[test]
fn test_transfer_extra_account_misreported_as_multisig() {
    let program_id = spl_token_2022_interface::id();
    let source = Pubkey::new_unique();
    let destination = Pubkey::new_unique();
    let authority = Pubkey::new_unique(); // NOT a multisig account on-chain
    let throwaway = Pubkey::new_unique(); // attacker-controlled extra pubkey, non-signer

    // Build the transfer instruction with the "canonical" 3 accounts...
    let mut ix = transfer(&program_id, &source, &destination, &authority, &[], 100).unwrap();
    // ...then append one extra, non-signing account (attacker-controlled).
    ix.accounts.push(solana_instruction::AccountMeta::new_readonly(throwaway, false));

    let message = Message::new(&[ix], None);
    let compiled_instruction = &message.instructions[0];
    let parsed = parse_token(compiled_instruction, &AccountKeys::new(&message.account_keys, None)).unwrap();

    let info = parsed.info.as_object().unwrap();
    // BUG: authority field is missing/misreported as multisigAuthority
    assert!(info.get("authority").is_none());
    assert_eq!(
        info.get("multisigAuthority").unwrap().as_str().unwrap(),
        authority.to_string()
    );
    assert_eq!(
        info.get("signers").unwrap().as_array().unwrap(),
        &vec![serde_json::json!(throwaway.to_string())]
    );
    // Ground truth: `authority` is not a Multisig account and the on-chain
    // program would execute this normally as a single-authority transfer,
    // ignoring the extra `throwaway` account entirely.
}
```

Expected assertion failures on the *fixed* version: `authority` must be present and equal to the real signer, and no spurious `multisigAuthority`/`signers` fields should appear unless the referenced account is verified to actually be Multisig-owned data.

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
```
