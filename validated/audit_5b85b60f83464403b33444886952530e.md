### Title
Permissionless factory-deployed programmable vault grants unlimited underlying allowance to an unverified ERC4626 vault - ([File: contracts/IdleCreditVaultFactory.sol](contracts/IdleCreditVaultFactory.sol))

### Summary
`deployRevolvingCreditVault` is externally callable and accepts the ERC4626 vault address supplied by the caller. The deployed `ProgrammableBorrower` only verifies that `vault.asset()` equals the pool underlying, then immediately grants that vault an unlimited ERC20 allowance. A malicious vault can therefore drain every underlying token held by the programmable borrower during the first deposit callback or at any later time while the allowance remains active.

### Finding Description
`deployRevolvingCreditVault` has no caller restriction and forwards `programmableBorrowerParams.vault` directly into the programmable-borrower initializer. [1](#0-0) 

`ProgrammableBorrower.initialize` rejects only a zero vault or a vault reporting a different `asset()`, and otherwise stores the caller-selected address. [2](#0-1) 

Initialization then grants both the unverified vault and the CDO unlimited underlying-token allowance. [3](#0-2) 

The same weak validation is used when rotating vaults: only `asset()` equality, an inactive epoch, and zero current shares are required before another unlimited allowance is granted. [4](#0-3) 

At epoch start, the programmable borrower deposits its complete on-hand underlying balance into the configured vault, giving the vault a reliable execution callback after lender funds have been transferred to the facility. [5](#0-4) 

### Impact Explanation
A malicious ERC4626 can implement `deposit(uint256,address)` so that it invokes `underlying.transferFrom(programmableBorrower, attacker, underlying.balanceOf(programmableBorrower))`, using the standing unlimited allowance rather than merely receiving the requested deposit amount. This steals the entire programmable-borrower cash position, including lender principal received for the epoch and later borrower repayments, while still returning shares to make the accounting integration superficially functional.

The loss is quantifiable as `underlyingToken.balanceOf(programmableBorrower)` at the moment the malicious vault first uses its allowance. In a pool where lenders deposit `N` underlying and the honest manager starts the epoch, the attacker receives all `N` before any borrower draw or repayment protection applies.

### Likelihood Explanation
The attack requires an attacker to deploy a revolving credit vault through the permissionless factory with a malicious ERC4626 that reports the correct underlying asset. [6](#0-5) 

Subsequent privileged participants can remain honest: the configured manager only needs to perform the normal epoch-start operation, while the malicious vault executes the theft during the resulting trusted `vault.deposit` call. [7](#0-6) 

The existing checks do not prevent this because there is no canonical vault registry, implementation verification, deposit callback restriction, or per-operation allowance bound; `asset()` equality is insufficient to establish that an ERC4626 is trusted. [8](#0-7) 

### Recommendation
Do not allow arbitrary factory callers to set an unverified ERC4626 endpoint. Maintain a treasury-controlled registry of approved vaults and require `programmableBorrowerParams.vault` to match a listed address exactly.

Prefer removing the standing `type(uint256).max` approval. Instead approve exactly `_assetAmount` before each deposit and clear it afterward. If a standing approval is retained, vault rotation should revoke the old vault’s allowance and be restricted to governance-approved integrations.
