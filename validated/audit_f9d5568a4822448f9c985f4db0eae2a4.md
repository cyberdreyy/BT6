## Verified

I've confirmed the root cause: `delete_member` in `multisig2/src/lib.rs` only purges requests/confirmations for requests that the removed member itself *created* (`r.member == member`), but never scans other requests' `confirmations` sets for entries keyed by that removed member's identity. A confirmation string recorded in `self.confirmations` for a request created by a *different* member remains present after the member is deleted, and `confirm()` counts `confirmations.len()` unconditionally against `self.num_confirmations` without re-checking liveness of each stored confirmer against `self.members`. ### Title
Stale confirmations from removed members are still counted toward execution threshold - (multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts entries in the `confirmations` `HashSet<String>` for a request without verifying that each confirming identity is still a current member. `delete_member` only cleans up requests *originated* by the removed member; it does not scan and strip that member's confirmation entries from *other* pending requests. This lets a request execute with fewer live, authorized confirmations than `num_confirmations` requires, breaking the equality "confirmations counted == live members who confirmed."

### Finding Description
In `add_request`/`confirm`, a `MultiSigRequestWithSigner` records the creating `member`, and `confirmations: LookupMap<RequestId, HashSet<String>>` records every member (via `member.to_string()`) that has called `confirm` on a request without yet reaching the threshold: [3](#0-2) [2](#0-1) 

`execute_request` handles `DeleteMember` by calling `self.delete_member(promise, member)`: [4](#0-3) 

`delete_member` removes the member from `self.members`, deletes its access key, and purges only the requests it *originated* (`r.member == member`): [1](#0-0) 

It never iterates `self.confirmations` to strip the deleted member's string from confirmation sets belonging to requests created by *other* members. Consequently, if member `M2` had previously confirmed a pending request `R` created by `M1` (without yet hitting the threshold), and `M2` is later removed via a `DeleteMember` request, `R`'s confirmation set still contains `M2`. Any subsequent `confirm(R)` by a live member re-evaluates `confirmations.len() as u32 + 1 >= self.num_confirmations`, counting the stale `M2` entry as if `M2` were still a legitimate, live signer — executing `R` (which can be an arbitrary `Transfer`, `AddKey`, `FunctionCall`, etc.) with effectively one fewer *live* confirmation than the configured `K` requires.

This is the direct analog of the reported class: the report's Hub allowed a debit (borrow/withdraw) to be authorized against a recorded state (deposited liquidity) that no longer reflected reality (actual spoke liquidity) because no re-validation was performed against the current, real state before acting. Here, the recorded state is "confirmations set for request R," and the real state is "which of those confirmers are still live multisig members" — the contract never re-validates the confirmation set against current membership before executing.

### Impact Explanation
This crosses the "confirmations counted versus live members" custody-authorization boundary explicitly in scope. Because `execute_request` for a `Transfer` action moves NEAR (`promise.transfer(amount.into())`) or can add a new full-access key / deploy new code, a request can be executed by `K-1` live members plus one departed member's stale confirmation — i.e. below the intended threshold `K`. This is an unauthorized move of NEAR (or unauthorized privileged action) not entitled under the current membership configuration, matching the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
No attacker capability beyond normal, expected multisig usage is required: any legitimate member confirming a request, followed by a routine `DeleteMember` action (e.g., offboarding a departing signer or rotating a compromised key) while other requests are still pending, silently degrades the effective threshold for those pending requests. This is a plausible operational sequence (member departs while a transfer is mid-flight awaiting one more confirmation), not a contrived edge case, and requires no compromise of any key beyond the normal K-of-N signers already trusted to run the contract.

### Recommendation
When executing `DeleteMember`, iterate all entries in `self.confirmations` (not just requests originated by the removed member) and remove the deleted member's string from every confirmation set; alternatively, validate at `confirm()` time that every string in the stored confirmation set still corresponds to a current member (recomputing the effective count by intersecting stored confirmations with `self.members`) before comparing against `self.num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{M1, M2, M3}` and `num_confirmations = 2`.
2. `M1` calls `add_request` to create request `R` (e.g. `Transfer` of funds to an external account) — `R` has 0 confirmations.
3. `M2` calls `confirm(R)` — `confirmations[R] = {M2}` (1 confirmation, below threshold 2, so it's just stored, not executed) per `confirm`'s branch at [5](#0-4) .
4. Separately, `M1`+`M3` (or any 2 live members) create and confirm a `DeleteMember{ member: M2 }` request, which executes and removes `M2` from `self.members` via `delete_member`. Since `R` was not created by `M2`, `delete_member`'s cleanup loop (filtering `r.member == member`) does not touch `R`'s confirmation set, so `confirmations[R]` still equals `{M2}`.
5. `M3` (a live, legitimate member) now calls `confirm(R)`. `confirmations.len() as u32 + 1 = 2 >= num_confirmations (2)` — the request executes, having been authorized by `M3` (live) plus the stale confirmation of the now-removed `M2`, i.e., effectively only 1 live confirming member reaching a 2-of-3 threshold that should require 2 currently-authorized signers.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
