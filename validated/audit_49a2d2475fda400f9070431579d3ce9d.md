## Analysis Result [1](#0-0) , [2](#0-1)  reveal a stale-confirmation accounting bug analogous to the `ensureNodeIsSafeModuleMember()` report's core defect: a trust/threshold check is evaluated against state that no longer corresponds to the live authorization set. In the HOPR case, the code iterated modules assuming they all still implement the trusted interface; in this repository, `confirm()` counts entries in the `confirmations: HashSet<PublicKey>` set assuming every entry still corresponds to a live access key, even though `DeleteKey` only purges confirmations for requests it itself originally created.

### Title
Stale confirmations from deleted multisig keys still count toward the confirmation threshold, allowing request execution below the live-signer quorum - (File: multisig/src/lib.rs)

### Summary
`MultiSigContract::confirm()` computes whether a request has reached quorum by checking `confirmations.len() as u32 + 1 >= self.num_confirmations` [3](#0-2) , where `confirmations` is a `HashSet<PublicKey>` of public keys that previously called `confirm`. When a key is removed via `MultiSigRequestAction::DeleteKey`, the cleanup logic only removes confirmations for requests that key itself *originally added* (`r.signer_pk == pk`) [4](#0-3) . It never scans other pending requests to strip confirmations contributed by the deleted key as a *confirmer* (not the creator). As a result, a confirmation cast by a key that is later deleted remains permanently counted toward the `num_confirmations` threshold for any other request it had confirmed, even though that key can no longer sign anything on the account.

### Finding Description
The binding the contract is supposed to maintain is:
`confirmations counted for request R == confirmations from keys that are still live members of the account`

`DeleteKey`'s cleanup only enforces this equality for requests where the deleted key is the `signer_pk` of `MultiSigRequestWithSigner` (i.e. the request's creator) [1](#0-0) . It does not iterate `self.confirmations` to remove the deleted key's entries from requests it merely *confirmed*. `confirm()` then treats every entry in the stored `HashSet<PublicKey>` as a currently valid confirmation without re-verifying key liveness [5](#0-4) .

Before the attacker's action: request R has confirmations `{D}` (D added a confirmation but did not create R; R's `signer_pk` is A). num_confirmations = 3, live keys = {A,B,C,D}.

DeleteKey(D) executes (separately confirmed by A,B,C reaching quorum, a completely ordinary key-rotation operation) — key D is deleted from the account, but since R's `signer_pk` is A (not D), R's confirmation set `{D}` is untouched [6](#0-5) .

After the attacker's action: live keys = {A,B,C}. B confirms R → confirmations = `{D,B}`, len=2 < 3, no execution. C confirms R → `confirmations.len()==2`, `2+1>=3` → **executes R**, with confirmations recorded as `{D,B,C}`. Only B and C are live signers who genuinely authorized R post key-rotation; D is a phantom, deleted key. The request executes with 2 genuinely live confirmations instead of the required 3, i.e. `confirmations counted (3) != live confirmations (2)`.

### Impact Explanation
This breaks the multisig's core custody guarantee: `num_confirmations` live signers must approve before any `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc. is executed. Because stale confirmations from deleted keys persist and count toward quorum, a request (including a `Transfer` of the contract's NEAR balance) can be executed with fewer live approvals than the configured threshold — matching the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
No attacker privilege beyond normal multisig usage is required — this occurs through ordinary operational sequences: (1) a member confirms a pending request without pushing it to quorum, (2) the account later rotates out that member's key via a normal, properly-quorumed `DeleteKey` request (routine key rotation/compromise response), (3) the old pending request is still sitting in `requests`/`confirmations` with the now-deleted key's stale confirmation baked in. Any subsequent confirmations from remaining live members will silently "inherit" the phantom confirmation and can push the request past quorum with fewer live approvals than intended. This requires no exploitation of a bug in NEAR runtime and no cooperation from a malicious member — it is a latent state-management defect in the contract itself, triggered by completely legitimate multisig operations occurring in an ordinary sequence.

### Recommendation
When executing `DeleteKey` (or `DeleteMember` in `multisig2/src/lib.rs`, which has the identical `r.member == member` filter limited to requests created by that member [7](#0-6) ), iterate over **all** pending requests' confirmation sets (not just those the deleted key/member created) and remove the deleted key's/member's entry from each. Alternatively, at `confirm()` time, validate that every public key in the stored `confirmations` set is still a currently authorized key/member before counting it toward the threshold, rather than trusting the historically-stored set.

### Proof of Concept
1. Initialize `MultiSigContract::new(num_confirmations = 3)` with 4 access keys: A, B, C, D on the account.
2. Using key A, call `add_request(R)` where R is `Transfer { amount }` to an attacker-controlled receiver (`R.signer_pk = A`, confirmations = `{}`).
3. Using key D, call `confirm(R_id)` → confirmations = `{D}`, len=1 < 3, not executed.
4. Using keys A, B, C, create and confirm a separate request `DeleteKey { public_key: D }` up to quorum (3 confirmations) → this executes `MultiSigRequestAction::DeleteKey`, which only inspects requests with `signer_pk == D` (none, since R was added by A) [6](#0-5) ; key D is deleted from the account; R's confirmation set `{D}` is left intact.
5. Using key B, call `confirm(R_id)` → confirmations = `{D, B}`, len=2 < 3, not executed.
6. Using key C, call `confirm(R_id)` → `confirmations.len()==2`, `2+1 >= 3` → `execute_request(R)` fires, transferring funds, even though only B and C are live signers that approved post key-rotation (D's approval is from a deleted key). [8](#0-7)
