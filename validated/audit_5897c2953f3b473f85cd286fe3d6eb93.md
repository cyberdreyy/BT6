### Title
Zip extractor creates symlinks with unvalidated targets, allowing dangling symlinks that point outside the extraction root - ([File: helpers/archives/zip_extract.go])

### Summary
`extractZipSymlinkEntry` in `helpers/archives/zip_extract.go` reads the ZIP entry's file data (the symlink target) and passes it directly to `os.Symlink(string(data), file.Name)` with no check that the resulting link target stays within the extraction directory. This is reachable from the exact call chain in the question: `ziplegacy.extractor.Extract` → `archives.ExtractZipArchive` → `extractZipFile` → `extractZipSymlinkEntry`.

### Finding Description
`extractZipSymlinkEntry` (helpers/archives/zip_extract.go, lines 22-39) reads the file's data payload as the symlink target and calls: [1](#0-0) 
There is no `filepath.Clean`, no check for a leading `/` (absolute path), and no check that a relative target (e.g. `../../outside`) resolves within the extraction directory. `extractZipFile` (lines 61-83) dispatches to this function purely based on `file.Mode() & os.ModeType == os.ModeSymlink`, which is fully attacker-controlled metadata inside a ZIP the user builds and uploads as a job artifact/cache/dependency. The extraction entrypoint (`ziplegacy.extractor.Extract`, `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go` lines 26-33) parses the ZIP and calls `archives.ExtractZipArchive(zr)` directly — confirming the full reachable path from an attacker-supplied ZIP file to `os.Symlink`. [2](#0-1) 

### Impact Explanation
An attacker who controls a ZIP artifact/cache extracted by the runner (e.g. an artifact dependency from a prior job, or a cache archive) can embed a symlink entry whose data is an absolute path or a `../`-escaping relative path. `os.Symlink` will happily create that link at `file.Name` inside the extraction directory, pointing outside the workspace. The symlink creation itself does not write data outside the workspace (unlike a classic Zip Slip where the *entry name* escapes), but it plants a dangling symlink. If a later step in the same job (e.g. writing build output, subsequent artifact upload, or a script writing to that relative path) writes through that path, the write is redirected to the symlink target outside the extraction root — an out-of-workspace file write/read primitive.

### Likelihood Explanation
This is straightforward to trigger: a normal, unprivileged pipeline author can craft a ZIP with a symlink entry (`archive/zip` supports arbitrary `Mode()`/`ModeSymlink` entries and arbitrary file contents as link target) and have it consumed as a job artifact, cache, or dependency, which the runner extracts via `ExtractZipArchive`/`extractZipFile` without any restriction on the symlink's target. No special privileges beyond normal CI job authoring are required, and the exploit is fully repeatable.

### Recommendation
Validate/sanitize the symlink target in `extractZipSymlinkEntry` before calling `os.Symlink`: reject absolute targets, and resolve relative targets against the entry's directory using `filepath.Clean`/`filepath.Rel`, rejecting any result that escapes the intended extraction root (mirroring the "zip slip" name-path validation that should also exist for `file.Name`, but explicitly extended to cover the symlink's *data* payload).

### Proof of Concept
Go unit test to add to `helpers/archives/zip_extract_test.go`:
```go
func TestExtractZipSymlinkEntry_RejectsEscapingTarget(t *testing.T) {
    dir := t.TempDir()
    chdir(t, dir) // change CWD to extraction root, as done in other tests in this file

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    hdr := &zip.FileHeader{Name: "evil-link"}
    hdr.SetMode(os.ModeSymlink | 0o777)
    w, _ := zw.CreateHeader(hdr)
    _, _ = w.Write([]byte("/etc/cron.d/malicious"))
    _ = zw.Close()

    zr, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    err := ExtractZipArchive(zr)
    require.NoError(t, err) // extraction should not error, but the link should be rejected/skipped

    target, linkErr := os.Readlink(filepath.Join(dir, "evil-link"))
    // Assert the symlink either was not created, or its target is confined to dir
    if linkErr == nil {
        resolved := target
        if !filepath.IsAbs(resolved) {
            resolved = filepath.Join(dir, resolved)
        }
        require.True(t, strings.HasPrefix(resolved, dir), "symlink target escaped extraction root: %s", resolved)
    }
}
```
Expected (current) result: the test fails today because `os.Readlink` returns `/etc/cron.d/malicious`, proving the target is unconfined. After the fix, either the symlink creation is rejected or the resolved target is forced to stay under `dir`.
