### Title
Missing Source-Chain Domain Separation in `isTransferProcessed` Nonce Key Causes Permanent Fund Lock — (`bridge/evm/contracts/SuiBridge.sol`)

---

### Summary

`SuiBridge.sol` tracks processed token-transfer messages with `mapping(uint64 nonce => bool isProcessed) public isTransferProcessed`. The replay-protection check and the mark-as-processed write both key on `nonce` alone, discarding `message.chainID` (the source chain). Because `BridgeConfig` explicitly supports an **array** of source chains, two independent source chains each maintain their own per-chain nonce counter starting at 0. When both chains are live, their nonces overlap, and the first chain to process nonce *N* permanently blocks the identical nonce from every other supported source chain.

---

### Finding Description

In `transferBridgedTokensWithSignatures`:

```solidity
// bridge/evm/contracts/SuiBridge.sol  lines 65 and 92
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
// ...
isTransferProcessed[message.nonce] = true;
``` [1](#0-0) [2](#0-1) [3](#0-2) 

The key is `uint64 nonce` only. `message.chainID`, which carries the source chain identifier, is never incorporated into this key.

`BridgeConfig` is initialised with an **array** of supported source chains and stores them in `mapping(uint8 chainId => bool isSupported) public supportedChains`. The only restriction is that a chain cannot list itself:

```solidity
// bridge/evm/contracts/BridgeConfig.sol  lines 18, 55-58
mapping(uint8 chainId => bool isSupported) public supportedChains;
for (uint8 i; i < _supportedChains.length; i++) {
    require(_supportedChains[i] != _chainID, "BridgeConfig: Cannot support self");
    supportedChains[_supportedChains[i]] = true;
}
``` [4](#0-3) [5](#0-4) 

The `onlySupportedChain(message.chainID)` modifier in `transferBridgedTokensWithSignatures` therefore passes for any chain in that list:

```solidity
// bridge/evm/contracts/SuiBridge.sol  lines 62-63
verifyMessageAndSignatures(message, signatures, BridgeUtils.TOKEN_TRANSFER)
onlySupportedChain(message.chainID)
``` [6](#0-5) 

Crucially, the `verifyMessageAndSignatures` modifier skips the chain-ID equality check for `TOKEN_TRANSFER` messages entirely:

```solidity
// bridge/evm/contracts/utils/MessageVerifier.sol  lines 43-50
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    require(
        message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID"
    );
    require(message.nonce == nonces[message.messageType], "MessageVerifier: Invalid nonce");
    nonces[message.messageType]++;
}
``` [7](#0-6) 

Each source chain's Sui bridge contract maintains its own independent per-message-type sequence counter starting at 0:

```move
// crates/sui-framework/packages/bridge/sources/bridge.move  lines 696-705
fun get_current_seq_num_and_increment(bridge: &mut BridgeInner, msg_type: u8): u64 {
    if (!bridge.sequence_nums.contains(&msg_type)) {
        bridge.sequence_nums.insert(msg_type, 1);
        return 0
    };
    let entry = &mut bridge.sequence_nums[&msg_type];
    let seq_num = *entry;
    *entry = seq_num + 1;
    seq_num
}
``` [8](#0-7) 

Because every supported source chain starts its nonce at 0 and increments monotonically, nonces from different chains are guaranteed to collide (nonce 0, 1, 2, … are shared across all chains). The first chain to have nonce *N* processed sets `isTransferProcessed[N] = true`; every subsequent legitimate transfer from any other source chain that carries the same nonce is permanently rejected with `"SuiBridge: Message already processed"`.

On the Sui side the analogous key is `BridgeMessageKey { source_chain, message_type, bridge_seq_num }`, which correctly includes `source_chain`:

```move
// crates/sui-framework/packages/bridge/sources/message.move  lines 40-44
public struct BridgeMessageKey has copy, drop, store {
    source_chain: u8,
    message_type: u8,
    bridge_seq_num: u64,
}
``` [9](#0-8) 

The EVM side omits `source_chain` from its equivalent key, creating the asymmetry.

---

### Impact Explanation

When the EVM bridge is configured with two or more supported source chains (e.g., SuiMainnet and SuiTestnet, or two independent Sui deployments), any user who deposits tokens on source chain B with nonce *N* will have their tokens permanently locked in the `BridgeVault` if source chain A has already had nonce *N* processed. The tokens are burned/escrowed on the Sui side and can never be released on the EVM side. This matches the **permanent fund lock** impact class (High/Medium).

---

### Likelihood Explanation

`BridgeConfig.initialize` accepts an array of supported chains and the contract design explicitly anticipates multiple source chains. A governance action at deployment time (or a future `addTokensWithSignatures`-style governance message) can register multiple Sui chains. Once two source chains are live, nonce collisions begin at nonce 0 and recur for every nonce value, affecting every user of the lower-priority chain.

---

### Recommendation

Change the replay-protection mapping to use a composite key of `(sourceChainID, nonce)`:

```solidity
// Before
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
require(!isTransferProcessed[message.nonce], ...);
isTransferProcessed[message.nonce] = true;

// After
mapping(uint8 chainID => mapping(uint64 nonce => bool isProcessed)) public isTransferProcessed;
require(!isTransferProcessed[message.chainID][message.nonce], ...);
isTransferProcessed[message.chainID][message.nonce] = true;
```

This mirrors the correct domain separation already present in the Sui Move bridge (`BridgeMessageKey` includes `source_chain`) and in `BridgeUtils.encodeMessage` (which includes `chainID` in the signed bytes).

---

### Proof of Concept

1. Deploy EVM bridge on Ethereum Mainnet with `_supportedChains = [SuiMainnet(1), SuiTestnet(2)]`.
2. Alice deposits 1 ETH on SuiMainnet → Sui bridge emits `TokenDepositedEvent { seq_num: 5, source_chain: 1, ... }`. Validators sign and submit to EVM bridge. `transferBridgedTokensWithSignatures` succeeds; `isTransferProcessed[5] = true`.
3. Bob deposits 1 ETH on SuiTestnet → Sui bridge emits `TokenDepositedEvent { seq_num: 5, source_chain: 2, ... }`. Validators sign and submit to EVM bridge.
4. `transferBridgedTokensWithSignatures` reaches `require(!isTransferProcessed[5], ...)` → **reverts** with `"SuiBridge: Message already processed"`.
5. Bob's 1 ETH is burned on SuiTestnet and permanently locked in the EVM `BridgeVault`. No recovery path exists. [10](#0-9) [11](#0-10)
