### Title
Unauthenticated flood of `HandleLegacyUserMessage` evicts unrelated legitimate pending callbacks via global size-based pruning - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`pruneCallbacks` evicts callbacks purely by global count once `len(savedCallbacks) > MaxSavedCallbacks`, trimming to `maxSize/2` by oldest `createdAt`, without regard to whether an entry is expired under `CallbackMaxAgeSec`. Because `HandleLegacyUserMessage` inserts a new `savedCallback` for every distinct signed message with no rate limiting or allowlist check (explicitly marked as a TODO), an unauthenticated/unprivileged sender can flood the map to force eviction of up to half of all currently pending, non-expired callbacks belonging to other users.

### Finding Description
`HandleLegacyUserMessage` accepts any structurally-valid, non-stale, signed message and unconditionally stores it in the shared map: [1](#0-0) . Immediately preceding that, the code contains an explicit acknowledgment that no authorization/quota control exists at this entry point: [2](#0-1) . The only gating checks are payload decodability, a non-zero timestamp, and a staleness window based on `MaxAllowedMessageAgeSec` — none of which limit request volume or require any privileged credential (message signing keys are self-generated, not allowlisted at this point).

`pruneCallbacks` first removes only truly expired entries (`createdAt` older than `CallbackMaxAgeSec`) [3](#0-2) , but then, if the map is still over `MaxSavedCallbacks`, sorts ALL remaining entries (expired or not) by `createdAt` and deletes everything except the newest `maxSize/2` [4](#0-3) . This size-based eviction makes no distinction between legitimate in-flight requests and attacker-injected ones — it simply keeps the newest half by timestamp. The existing test suite even documents this behavior for entries that are still "live" (not yet expired): [5](#0-4) .

Exploit flow: an attacker with no session/API token repeatedly calls the gateway's user-message path with distinct signed messages (each getting a unique `MessageId`), inserting more than `MaxSavedCallbacks` entries. When the periodic `pruneCallbacks` tick fires (`Start` schedules it every `CallbackPruneIntervalSec`) [6](#0-5) , half of all entries — including legitimate, still-within-age callbacks belonging to other unrelated users — are silently deleted from `savedCallbacks`. Because eviction happens without ever calling `callback.SendResponse`, the legitimate caller's request is dropped with no response and will only fail via its own client-side timeout, and the entry is gone so a late node response can no longer be routed back to it.

### Impact Explanation
Scoped impact is a denial-of-service against unrelated, legitimate, already-accepted in-flight requests: an unauthenticated/unprivileged flood can evict pending callbacks belonging to other users, breaking the isolation invariant that unrelated unauthenticated traffic should not affect another user's already-accepted request state. This matches a mass DoS / resource-exhaustion impact class rather than authentication bypass or fund loss — no key material, secrets, or authorization boundary is crossed, but availability of in-flight capability/gateway requests for arbitrary victims is compromised by a single unprivileged actor.

### Likelihood Explanation
Highly feasible and fully repeatable: no authentication, session, API token, or DON/node privilege is required — only the ability to produce a structurally valid signed message with a fresh timestamp and a unique `MessageId`, which is entirely attacker-controlled (self-generated key). The attacker just needs to send more than `MaxSavedCallbacks` (default 20000, configurable) distinct requests before/at a prune tick (default every `CallbackPruneIntervalSec`, default 30s). There is no rate limiter or allowlist gating `HandleLegacyUserMessage` itself (the node-directed `nodeRateLimiter` only applies to node-originated traffic, not this user entry point).

### Recommendation
- Prioritize eviction candidates by expiry status; never evict non-expired (still within `CallbackMaxAgeSec`) callbacks purely to satisfy a size cap, or at minimum log/alert and prefer capacity rejection over silent eviction of live entries.
- Enforce a per-sender/per-key rate limit or quota on `HandleLegacyUserMessage` before inserting into `savedCallbacks` (the code has a `// TODO: apply allowlist and rate-limiting here` marker indicating this was intentionally deferred).
- When the map is at capacity, reject new insertions (return a capacity/backpressure error to the new caller) instead of evicting existing legitimate entries, or use a bounded per-key concurrent-request limit so no single sender can grow the map disproportionately.

### Proof of Concept
Go unit test plan (extends `TestPruneCallbacks` in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Seed `handler.savedCallbacks` with N "legitimate" entries with `createdAt = now` (well within `CallbackMaxAgeSec`).
2. Simulate the attacker by inserting `MaxSavedCallbacks` additional entries with `createdAt` timestamps newer than the legitimate entries (mirroring what repeated `HandleLegacyUserMessage` calls would produce), so total exceeds `MaxSavedCallbacks`.
3. Call `handler.pruneCallbacks()`.
4. Assert that some/all of the legitimate entries seeded in step 1 are missing from `handler.savedCallbacks` despite `now.Sub(createdAt) < CallbackMaxAgeSec`, demonstrating that unexpired, legitimate callbacks were evicted purely due to attacker-driven volume.
5. Optionally, extend to a handler-level integration test: call `handler.HandleLegacyUserMessage` for a "victim" message, then loop-call it with `MaxSavedCallbacks` attacker messages (distinct `MessageId`s, valid signatures/timestamps), trigger prune, and assert the victim's callback channel never receives a response because its `savedCallback` entry was deleted.

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
