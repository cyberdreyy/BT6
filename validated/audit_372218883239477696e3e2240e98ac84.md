### Title
`is_valid_indexed_payload_attestation` accepts duplicate PTC attesting indices, unlike its `is_valid_indexed_attestation` counterpart - (File: `specs/gloas/beacon-chain.md`)

### Summary
In `specs/gloas/beacon-chain.md`, `is_valid_indexed_payload_attestation` only checks that the `attesting_indices` list is sorted, but — unlike the phase0 `is_valid_indexed_attestation` — it never checks for uniqueness. This is the same bug class as the ML-DSA `monotonic` regression: a check that is supposed to enforce a canonical, strictly-increasing/unique ordered set instead only enforces non-strict ordering, so an equal (duplicate) value passes.

### Finding Description
Compare the two validity predicates:

Phase0, correct (checks both sortedness and uniqueness via `sorted(set(...))`): [1](#0-0) 

Gloas, `is_valid_indexed_payload_attestation`, which drops the uniqueness requirement and only checks `list(indices) != sorted(indices)`: [2](#0-1) 

Because Python's `sorted()` is stable and non-strict, a list like `[3, 3, 5]` satisfies `list(indices) == sorted(indices)` and is accepted as "valid" even though index `3` appears twice. This mirrors exactly the reported ML-DSA flaw: a `<=`-style (non-strict) check is used where a strict/unique check (`<` or `sorted(set(...))`) is required, so the encoding/set is not canonical and duplicate entries are silently accepted.

`BLS.FastAggregateVerify(pubkeys, signing_root, signature)` does not itself reject duplicate pubkeys — if the same validator's pubkey appears twice in `pubkeys`, an aggregate signature can be validly constructed by aggregating that validator's individual signature with itself (or reusing it), and the verification succeeds. So `is_valid_indexed_payload_attestation` can be made to accept an `IndexedPayloadAttestation` where a single Payload Timeliness Committee (PTC) member's index is repeated multiple times, while the aggregate signature is signed by that one validator's key alone (with multiplicity), not requiring cooperation from any of the other distinct committee members whose indices are absent.

### Impact Explanation
The PTC/payload-attestation mechanism (EIP-7732) is used to determine payload timeliness/availability and factors into fork-choice weighting and, per the design intent, quorum-style thresholds (see `get_builder_payment_quorum_threshold`, `specs/gloas/beacon-chain.md:1413-1423`, and the various `get_ptc`/`get_indexed_payload_attestation` helpers at `specs/gloas/beacon-chain.md:1375-1411`). If code that consumes an `IndexedPayloadAttestation` (rather than a freshly-constructed one via `get_indexed_payload_attestation`, which already dedupes via committee-bit derivation) trusts `is_valid_indexed_payload_attestation` as its sole check of "this represents N distinct committee members attesting," an attacker holding a single PTC member's key could forge an attestation object whose `len(attesting_indices)` (or any downstream count/weight based on iterating that list) is inflated by duplication, without the cooperation or authority of the other listed indices. This is analogous to "a duty selection/committee-weight outcome one participant can steer" and "signature malleability that breaks a uniqueness invariant the protocol relies on."

### Likelihood Explanation
I was not able to fully trace, within the remaining tool budget, whether the count/weight consumers of `IndexedPayloadAttestation` (in `specs/gloas/fork-choice.md`) always reconstruct the object via `get_indexed_payload_attestation` (which derives indices strictly from committee membership bits and therefore cannot contain duplicates) versus accepting/validating an attacker-supplied `IndexedPayloadAttestation` container directly and then trusting `len(indices)`/iteration count from `is_valid_indexed_payload_attestation`. This distinction determines whether the bug is reachable by an unprivileged actor or is merely dead/defense-in-depth code. This should be verified against the full `specs/gloas/fork-choice.md` payload-attestation processing logic before treating this as exploitable in production; regardless, the predicate itself is objectively inconsistent with the phase0 analog and is the root-cause equality it was clearly meant to enforce (sorted AND unique) is missing.

### Recommendation
Change the check in `is_valid_indexed_payload_attestation` to also enforce uniqueness, matching `is_valid_indexed_attestation`:
```python
if len(indices) == 0 or list(indices) != sorted(set(indices)):
    return False
```

### Proof of Concept
Given a `BeaconState` with at least one active PTC member `v` at slot `s`:
1. Construct `attestation.attesting_indices = [v, v]` (or `[v, v, w]` for any `w > v`), which passes `list(indices) == sorted(indices)`.
2. Construct `pubkeys = [state.validators[v].pubkey, state.validators[v].pubkey]`.
3. Compute an aggregate signature by aggregating `v`'s individual BLS signature over the signing root with itself (standard BLS aggregation permits repeated signers/pubkeys).
4. Call `is_valid_indexed_payload_attestation(state, attestation)` — it returns `True` despite the attestation only reflecting one real signer with a duplicated index, breaking the "each attesting index represents one distinct committee member's contribution" invariant that any downstream weight/count logic would implicitly rely on. def is_valid_indexed_attestation(
    state: BeaconState, indexed_attestation: IndexedAttestation

    """

def is_valid_indexed_payload_attestation(
    state: BeaconState, attestation: IndexedPayloadAttestation
) -> bool:
    """
    Check if ``attestation`` is non-empty, has sorted indices, and has
    a valid aggregate signature.
    """
    # Verify indices are non-empty and sorted
    indices = attestation.attesting_indices
    if len(indices) == 0 or list(indices) != sorted(indices):
        return False

    # Verify aggregate signature
    pubkeys = [state.validators[i].pubkey for i in indices]
    domain = get_domain(state, DOMAIN_PTC_ATTESTER, compute_epoch_at_slot(attestation.data.slot))
    signing_root = compute_signing_root(attestation.data, domain)
    return bls.FastAggregateVerify(pubkeys, signing_root, attestation.signature)
