### Title
`ValidatedMessageFromReq` overwrites the signed `MessageId` with the caller-controlled JSON-RPC `req.ID` *before* signature validation, allowing callback-map key collision/overwrite in `HandleLegacyUserMessage` - ([File: core/services/gateway/handlers/common/message_util.go])

### Summary
`ValidatedMessageFromReq` unmarshals the signed `api.Message` from `req.Params`, then unconditionally overwrites `m.Body.MessageId` with the outer, unauthenticated `req.ID` field before calling `m.Validate()`. Because signature verification (`ExtractSigner`) is performed *after* this overwrite and recomputes the signed hash using the now-replaced `MessageId`, there is no check that the outer `req.ID` matches what was actually signed. An attacker can therefore set `req.ID` to a victim's pending message ID, and the resulting message will be stored in `handler.savedCallbacks` keyed by that victim ID, overwriting the victim's callback registration.

### Finding Description
In `core/services/gateway/handlers/common/message_util.go`: [1](#0-0) 

`m.Body.MessageId` is set from `req.ID` (line 52) *before* `m.Validate()` is invoked (line 53). `Validate()` calls `ExtractSigner()`, which recomputes the signed payload via `GetRawMessageBody(&m.Body)` — using the just-overwritten `MessageId`, not the ID that was actually signed by the legitimate sender: [2](#0-1) [3](#0-2) 

ECDSA recovery (`ecrecover`) does not fail on a hash/signature mismatch — it simply returns whatever address the signature happens to recover to for the (now-different) hash. `Validate()` has no check that this derived `Sender` corresponds to anything meaningful, nor any check that the outer `req.ID` equals the ID that was originally embedded/signed in the body. The comment in `HandleLegacyUserMessage` even acknowledges allowlisting/sender checks are a `TODO` and not yet implemented: [4](#0-3) 

The resulting message (with `Body.MessageId` forced to the attacker-chosen `req.ID`) is then registered in the shared callback map keyed purely by that ID: [5](#0-4) 

If a victim's legitimate request with ID `B` is already pending (registered in `savedCallbacks["B"]`), an attacker submitting a second, differently-signed message under the same outer `req.ID = B` will silently overwrite that map entry with the attacker's own `callback`. When the DON later replies to messageId `B`, `handleWebAPITriggerMessage` looks up and deletes `savedCallbacks["B"]` and forwards the response to whichever `Callback` is currently stored there: [6](#0-5) 

This is a genuine last-writer-wins race on a map key that is not otherwise validated for uniqueness/ownership, and the map write is not conditioned on whether an entry already exists.

### Impact Explanation
This matches the "cross-user response confusion" / request-impersonation impact class: an unauthenticated caller who can predict or observe another client's pending `req.ID` can hijack or intercept the response destined for that ID, redirecting a legitimate DON response (which may include workflow execution results) to the attacker's connection instead of the victim's. It does not itself leak secrets held by the DON (the DON's actual response content correctness is untouched), but it breaks per-request isolation guaranteed by the callback map, which is the exact invariant targeted by the question.

### Likelihood Explanation
Exploitation requires the attacker to know or guess a victim's currently-pending `req.ID` and to be able to reach the gateway's legacy user-message ingress path (`HandleLegacyUserMessage`) with a self-signed, otherwise well-formed `api.Message` before the victim's callback is fulfilled (default TTL is 120s per `defaultCallbackMaxAgeSec`). No DON, gateway-operator, or credential compromise is needed—only network access to the user-facing endpoint and the ability to construct a validly self-signed message with an arbitrary `MessageId` in its body. Likelihood is moderate to low in practice, gated entirely on whether `req.ID` values used by legitimate clients are predictable/observable (this is an application-level assumption not enforced anywhere in the reviewed code).

### Recommendation
- In `ValidatedMessageFromReq`, validate the signature (`m.Validate()`) using the `MessageId` actually embedded and signed in `req.Params` *before* mutating it, and require that this signed `MessageId` equals the outer `req.ID` — reject the request if they differ, rather than silently overwriting.
- In `HandleLegacyUserMessage`, refuse to register/overwrite a `savedCallbacks` entry if one already exists for that ID (return an error/duplicate-ID response) instead of blindly overwriting via `h.savedCallbacks[msg.Body.MessageId] = ...`.
- Implement the still-outstanding sender allowlist/authorization check referenced in the `TODO` comment so an unrecognized/garbage recovered signer cannot pass validation.

### Proof of Concept
Go handler-level integration test plan (in `core/services/gateway/handlers/capabilities/handler_test.go` style):
1. Create handler `h` with a mock `handlers.DON` and two mock `handlers.Callback` implementations, `victimCB` and `attackerCB`.
2. Build `victimMsg` signed by `victimKey` with `Body.MessageId = "B"`, call `h.HandleLegacyUserMessage(ctx, victimMsg, victimCB)`; assert `h.savedCallbacks["B"].Callback == victimCB`.
3. Build `attackerMsg` signed by `attackerKey` with `Body.MessageId = "A"` (different from `"B"`), wrap in a `jsonrpc.Request` with `ID = "B"`, run it through `common.ValidatedMessageFromReq` to obtain the reconstructed message (its `Body.MessageId` will now be `"B"`), then call `h.HandleLegacyUserMessage(ctx, reconstructedMsg, attackerCB)`.
4. Assert `h.savedCallbacks["B"].Callback == attackerCB` (i.e., the victim's registered callback was silently replaced) — this demonstrates that the second, unrelated submitter overwrote the first submitter's callback registration for the same ID, rather than being rejected as a duplicate/mismatched-ID request.
5. Simulate the DON's response for messageId `"B"` via `h.HandleNodeMessage`; assert the response is delivered to `attackerCB.SendResponse` instead of `victimCB.SendResponse`, confirming cross-user response hijack.

func (m *Message) Sign(privateKey *ecdsa.PrivateKey) error {
	if m == nil {
		return errors.New("nil message")
	}
	rawData := GetRawMessageBody(&m.Body)
	signature, err := gw_common.SignData(privateKey, rawData...)
	if err != nil {
		return err
	}
	m.Signature = utils.StringToHex(string(signature))
	m.Body.Sender = strings.ToLower(crypto.PubkeyToAddress(privateKey.PublicKey).Hex())
	return nil
}
