### Title
Fee-on-transfer underlying breaks IdleCreditVault deposit and claim accounting — minted shares and funded amounts assume gross while vault receives net - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` is the ERC20-style credit-vault strategy used by `IdleCDOCreditVault`. Every token in/out path in it and in `IdleCDO._deposit` assumes `transferFrom`/`transfer` deliver exactly `_amount`. For a fee-on-transfer underlying (e.g. USDT with fees enabled), the vault receives `_amount - fee` while all internal accounting (strategy-token supply, `pendingWithdraws`, `lossRecoveryPriceByEpoch`, `defaultRecoveryReserve`, `defaultRecoveryPrice`) is credited at the gross amount. This creates an unbacked liability: deposits over-mint strategy tokens 1:1, and borrower funding/recovery pulls are under-collateralized, so the last claimants' `safeTransfer` calls revert and funds are permanently frozen/insolvent.

### Finding Description
The analogous bug has three concrete surfaces:

1. **Deposit over-mint.** `IdleCDOCreditVault._deposit` correctly mints tranche shares from the *actual* balance delta, but then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the **gross** `_amount` (`contracts/IdleCDOCreditVault.sol:203-211`). In `IdleCreditVault.deposit` (`contracts/strategies/idle/IdleCreditVault.sol:596-617`) the strategy does `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` and unconditionally `_mint(msg.sender, _amount)` — minting 1:1 against money that was never received. `getContractValue()` (CDO strategy-token balance × `price() == oneToken`) is thereby inflated by the fee, and `_updateAccounting` distributes the phantom value as NAV to tranche holders while real backing is short.

2. **Epoch funding shortfall.** When the borrower repays at `stopEpoch`, `collectWithdrawFunds` (`IdleCreditVault.sol:411-430`) does `underlyingToken.safeTransferFrom(idleCDO, address(this), _amount)` and records the full `_amount` as funded — setting `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` only when `_amount < pendingBasis`. With a fee, `_amount` equals `pendingBasis` in the books but the vault holds less, so claimants calling `claimWithdrawRequest` → `_transferFundedClaim` → `safeTransfer(_user, _amount)` will revert once the shortfall is hit (the earlier claimants succeed; the tail is frozen permanently).

3. **Default recovery mispricing.** `finalizeDefaultRecovery` (`IdleCreditVault.sol:686-708`) computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` **before** pulling `_recoveredAmount` via `safeTransferFrom(_recoverySource, ...)`. A fee shrinks the real reserve below `defaultRecoveryReserve`, so `defaultRecoveryPrice` overstates per-unit recovery and `_transferDefaultRecovery` reverts for the last claimants — the same "promise gross, receive net" failure as the Notional `withdraw()` finding.

The deposit path is attacker-reachable: any KYC'd lender can call `depositAA`/`depositBB` on the CDO with a fee-on-transfer token and have the CDO credited with `amount` strategy tokens while the vault only holds `amount - fee`.

### Impact Explanation
- **Insolvency / dilution:** each deposit creates `fee` units of unbacked strategy tokens, inflating tranche NAV; each funding pull creates `fee` units of unbacked claim basis. Loss = token fee % of every transfer, borne by remaining LPs/claimants.
- **Permanent freezing of claims:** `_transferFundedClaim` / `_transferDefaultRecovery` use `safeTransfer(_user, _amount)`; when the vault's real balance < recorded liability, the last claimants' claims revert forever — including the post-default path where users' tranche tokens were already burned into receipts.
- Broken invariants: fair mint/burn (shares minted without backing) and one-receipt-one-payout (funded basis exceeds real balance).

### Likelihood Explanation
Conditional on the underlying being fee-on-transfer. IdleCreditVault deployments use stablecoin pool currencies (e.g. USDT on several Pareto vaults); USDT's fee is currently disabled but can be switched on by Tether, exactly the scenario the original report flags. Until then no loss occurs; if enabled, every deposit/funding skews accounting and withdrawals begin failing. Medium likelihood, high impact when triggered — consistent with the source report's own severity framing.

### Recommendation
- In `IdleCreditVault.deposit`, `collectWithdrawFunds`, `collectInstantWithdrawFunds` and `finalizeDefaultRecovery`, measure `balanceOf(address(this))` before/after the `safeTransferFrom` and credit/mint only the *received* delta, mirroring how `IdleCDO._deposit` already computes `_contractTokenBalance(_token) - _preBal` for tranche minting.
- In `IdleCDOCreditVault._deposit`, pass the net received amount (not the gross `_amount`) to `IIdleCDOStrategy(strategy).deposit(...)`.
- Alternatively, document and enforce (e.g. in `initialize` via a test `safeTransferFrom` of 1 wei to self, or an allowlist) that `token` must not be fee-on-transfer, acknowledging USDT can enable fees later.

### Proof of Concept
Foundry sketch (fork test): mock/wrap USDT with a `FeeToken` that deducts 0.5% on `transfer`/`transferFrom`, initialize `IdleCreditVault` + `IdleCDOCreditVault` with it.

```solidity
function testFoTBreaksAccounting() public {
    FeeUSDT usdt = new FeeUSDT(); // 0.5% fee on transfer
    usdt.mint(lender, 1000e6);
    usdt.mint(borrower, 1000e6);

    // 1) deposit: CDO gets 1000e6 strategy tokens, vault holds 995e6
    vm.startPrank(lender);
    usdt.approve(address(cdo), 1000e6);
    cdo.depositAA(1000e6);
    vm.stopPrank();
    assertEq(vault.balanceOf(address(cdo)), 1000e6);          // minted gross
    assertEq(usdt.balanceOf(address(vault)), 995e6);         // received net
    // getContractValue() reports ~5e6 phantom NAV -> tranche price inflated

    // 2) epoch funding: borrower "fully" funds pendingWithdraws = 500e6
    //    vault.collectWithdrawFunds(500e6) records full basis, receives 497.5e6
    // 3) two claimants each owed 250e6: first claim succeeds,
    //    second claim's safeTransfer reverts -> receipt permanently unclaimable
    vm.expectRevert(); // ERC20: transfer amount exceeds balance
    cdo.claimWithdrawRequest(); // second claimant
}
```
