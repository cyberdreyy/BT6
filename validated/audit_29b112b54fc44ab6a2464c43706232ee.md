## Title
Transaction Parser Reports Instruction-Supplied Token Decimals Instead of Verified Mint Decimals - (File: `transaction-status/src/parse_token.rs`)

### Summary
The reported CDS bug is a broader "trust user input instead of authoritative source" bug class: a caller-supplied numeric parameter (price) is used directly in a fund-moving computation with no cross-check against the true on-chain value (an oracle). The closest reachable analog in Agave is in the transaction/instruction JSON-parsing path used by `getTransaction`/`getConfirmedTransaction` (jsonParsed encoding) and other RPC consumers of `solana-transaction-status`: for SPL Token "Checked" instructions, the `decimals` value used to compute the human-readable `tokenAmount`/`feeAmount` fields is taken directly from the attacker-controlled instruction data embedded in the transaction, not from the actual, authoritative decimals recorded in the corresponding mint account.

### Finding Description
In `parse_token`, several `TokenInstruction` variants carry a `decimals` field supplied by whoever constructed the instruction (any unprivileged user, since transaction data is arbitrary and untrusted): [1](#0-0) 

The code builds `SplTokenAdditionalDataV2::with_decimals(decimals)` straight from this field and calls `token_amount_to_ui_amount_v3` to compute `ui_amount`/`ui_amount_string`: [2](#0-1) [3](#0-2) 

This is structurally the same pattern as the CDS `redeemUSDT` bug: a value that should be derived from a trusted, on-chain source (the mint account's real `decimals`, analogous to an oracle price) is instead taken verbatim from user/attacker-controlled input and used to compute a reported monetary amount. Contrast this with the RPC handlers for `getTokenAccountBalance`/`getTokenSupply`/`getParsedTokenAccounts`, which correctly fetch decimals from the actual mint account via `get_mint_owner_and_additional_data`/`get_additional_mint_data`: [4](#0-3) [5](#0-4) 

The transaction/instruction parser has no equivalent cross-check — it parses instruction bytes in isolation and never consults bank/mint state.

### Impact Explanation
This falls under the "decoder panic and misreporting" acceptance category: unprivileged RPC clients calling `getTransaction`, `getConfirmedTransaction`, or subscribing to transaction notifications with `jsonParsed` encoding can receive a `tokenAmount`/`feeAmount`/`uiAmount` field that does not correspond to the real value moved on-chain — it reflects whatever `decimals` the transaction author chose to encode in the instruction, not the mint's true decimals. Wallets, explorers, and indexers that trust this parsed field without independently checking the mint's real decimals could display materially wrong amounts.

I could not fully verify from the available code whether the SPL Token / Token-2022 program's on-chain execution of `TransferChecked`/`ApproveChecked`/etc. always rejects a mismatched `decimals` for every code path (e.g., all extensions), which would bound this to failed/no-op transactions only. If the on-chain check is airtight in all cases, the practical impact is limited to cosmetically wrong display data on failed transactions rather than a fund-relevant discrepancy on successful ones — this is a materially weaker impact than the original H-35 report (fund drain) and should be treated as a misreporting-class issue, not a crash or fund-loss vulnerability.

### Likelihood Explanation
Trivial to trigger: any user can submit (or merely construct, without even landing on-chain) a transaction containing a `TransferChecked`-family instruction with an arbitrary `decimals` byte, then query it via a public, unprivileged JSON-RPC endpoint (`getTransaction` with `encoding: jsonParsed`) that any client can call at will — no special privileges, mocked components, or multi-request amplification are needed.

### Recommendation
When parsing "Checked" SPL Token instructions for JSON display, cross-reference the mint account referenced by the instruction (already available via `account_keys`) to obtain the authoritative decimals, falling back to the instruction-supplied value only when the mint cannot be resolved (e.g., historical/pruned state), and clearly flag any mismatch in the parsed output rather than silently trusting the instruction-encoded value.

### Proof of Concept
Not established with certainty beyond the code-path trace above; a full PoC would require confirming whether Token-2022 program execution can succeed with a `decimals` value diverging from the mint's actual decimals for any instruction/extension combination, which was not verifiable from the indexed code alone. Suggest starting a Devin/dev session with direct repo access to check the SPL Token / Token-2022 program's decimals-validation logic for all "Checked" instruction variants to confirm whether a successful (non-failed) transaction can carry a mismatched decimals value, which would raise this from "cosmetic misreporting on failed txs" to a confirmed misreporting issue on real, successful transfers.

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }

    pub fn get_token_account_balance(
        &self,
        pubkey: &Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<UiTokenAmount>> {
        let bank = self.bank(commitment);
        let account = bank.get_account(pubkey).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find account".to_string())
        })?;

        if !is_known_spl_token_id(account.owner()) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token account".to_string(),
            ));
        }
        let token_account = StateWithExtensions::<TokenAccount>::unpack(account.data())
            .map_err(|_| Error::invalid_params("Invalid param: not a Token account".to_string()))?;
        let mint = &Pubkey::from_str(&token_account.base.mint.to_string())
            .expect("Token account mint should be convertible to Pubkey");
        let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;
        let balance = token_amount_to_ui_amount_v3(token_account.base.amount, &data);
        Ok(new_response(&bank, balance))
    }
