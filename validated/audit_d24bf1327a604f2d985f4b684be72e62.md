### Title
EI-authenticated requests can trigger arbitrary job runs via `POST /v2/jobs/:ID/runs` bypassing intended EI restriction - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`RequiresRunRole` only checks that `user.Role != UserRoleView`, and never validates that the authenticated external initiator (EI) matches the job's configured EI. Worse, `PipelineRunsController.Create` attempts to exclude EI-authenticated callers via an `isUser` check based on `auth.GetAuthenticatedUser(c)`, but this check is ineffective because `AuthenticateExternalInitiator` also sets `SessionUserKey`, making `GetAuthenticatedUser` return `true` for EI-authenticated requests as well.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is protected by `RequiresRunRole`, which only enforces `user.Role != clsessions.UserRoleView`: [1](#0-0) 

When a request authenticates as an external initiator via `AuthenticateExternalInitiator`, the middleware sets both `SessionExternalInitiatorKey` (the actual EI) and `SessionUserKey` to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}`: [2](#0-1) 

In `PipelineRunsController.Create`, the code attempts to gate int-ID job runs to "users only" (excluding EIs) via:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
``` [3](#0-2) 

Because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `GetAuthenticatedUser(c)` returns `ok == true` for EI-authenticated requests too — the comment's intent ("EIs not allowed") is not actually enforced by this check. The code never calls `GetAuthenticatedExternalInitiator(c)` in `Create` to verify which EI is calling, nor is there any comparison against the job's configured EI (e.g. `ExternalInitiatorWebhookSpec`). As a result, any valid EI access key/secret can reach `prc.App.RunJobV2(ctx, jobID, nil)` for any numeric job ID, regardless of which EI is associated with that job.

### Impact Explanation
An attacker holding valid credentials for any one external initiator can trigger pipeline runs for any job on the node by numeric ID — including VRF/keeper or other funds-moving jobs not associated with that EI at all. This is unauthorized triggering of job execution across job/EI boundaries, matching Chainlink's "unauthorized transaction/job execution" bounty impact class.

### Likelihood Explanation
The precondition is only a valid EI access key/secret for any registered external initiator (an unprivileged, non-admin credential type by design, meant to be scoped to specific webhook jobs). No user session, API token, or role above the implicit "run" role is required. The request is a single `POST /v2/jobs/:ID/runs` with an integer job ID — trivially repeatable and requires no additional preconditions beyond guessing/knowing target job IDs.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests where `auth.GetAuthenticatedExternalInitiator(c)` is present (i.e., true EI-authenticated calls) rather than relying on `GetAuthenticatedUser`, since the latter is always populated for EI sessions. Additionally/alternatively, if EI-triggered runs by numeric ID are intended to be supported, validate that the authenticated EI's name matches the job's `ExternalInitiatorWebhookSpec.ExternalInitiatorID` before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
1. Create job A with `ExternalInitiatorWebhookSpec` referencing EI "X".
2. Create job B with `ExternalInitiatorWebhookSpec` referencing EI "Y" (or no EI at all).
3. Authenticate as EI "X" (valid access key/secret headers).
4. `POST /v2/jobs/:jobB.ID/runs`.
5. Assert response is `401/403` and `App.RunJobV2` is never invoked for job B — currently the code returns `200` with a created pipeline run, confirming the bypass.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
