### Title
Unprivileged APR takeover during `idleCDO == address(0)` setup window in `IdleCreditVault.setApr` - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.setApr` explicitly skips its caller authorization check whenever `idleCDO` has not been linked yet. Because `initialize` never sets `idleCDO`, any unprivileged EOA that calls `setApr`, `setAprs` or `setAprsWithBuffer` before `setWhitelistedCDO` executes gains the manager/CDO-only privilege of writing `lastApr` and, critically, the uncapped `unscaledApr`. This is the direct analog of CVE-2025-49734 ("improper restriction of communication channel to intended endpoints" → local privilege escalation): a state-dependent gap lets an unauthorized caller exercise a privileged function.

### Finding Description
The authorization logic lives in `setApr` (contracts/strategies/idle/IdleCreditVault.sol:225-235):

```solidity
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;
  // if cdo is not yet set we skip the check (this can happen only during the setup)
  if (_cdo != address(0)) {
    if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  }
  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
```

Two companion functions mutate state before delegating to `setApr`, so the same bypass applies:

- `setAprs` (IdleCreditVault.sol:206-210) writes `unscaledApr = _unscaledApr` — **uncapped** — then calls `setApr`.
- `setAprsWithBuffer` (IdleCreditVault.sol:217-220) does the same.

`initialize` (IdleCreditVault.sol:124-158) sets `maxApr = DEFAULT_MAX_APR` but leaves `idleCDO` at `address(0)`. The link is only established by a separate owner transaction, `setWhitelistedCDO` (IdleCreditVault.sol:954-957). The test harness confirms this ordering: `strategy.initialize(...)` runs first and `cv.setWhitelistedCDO(_cdo)` is a distinct `vm.prank(owner)` call (test/foundry/IdleCreditVault.t.sol:62 and :95). In the factory path, `IdleCreditVaultFactory._deployBaseCreditVault` (contracts/IdleCreditVaultFactory.sol:182-208) initializes the strategy proxy without ever passing the CDO address to the strategy.

An attacker observing mempool/deployment order can therefore frontrun (or sandwich, if linking is done in a later owner tx — as the test topology shows) the `setWhitelistedCDO` call with `setAprs(type(uint256).max, 0)`:

- `unscaledApr = type(uint256).max` — no cap is applied to this field anywhere.
- `lastApr = 0` — passes the `maxApr` check since `0 <= maxApr`.

From then on, every call that accrues borrower interest via `_calcInterest(principal, elapsed)` against `unscaledApr`/`lastApr` either computes a nonsensical obligation or overflows/reverts, breaking epoch interest accounting until the honest manager or CDO resets the APR — and each reset race can be re-contested while the window is open.

### Impact Explanation
- **Temporary freezing of the vault/epoch flows**: with `unscaledApr` or `lastApr` attacker-controlled, `stopEpochWithDuration` / interest accrual on the funded principal produces arithmetic overflow or an astronomically inflated `expectedEpochInterest`. Epoch stop/start and borrower repayment calls revert or mis-account, freezing lender withdrawals (queued withdraws cannot be priced) until governance intervenes — temporary freezing of all pooled funds.
- **Integrity/insolvency vector**: if a corrupted `unscaledApr` survives into an epoch before being noticed, borrower debt is inflated and the pool can be pushed into a spurious default, forcing BB-first loss socialization on lenders.

Caveat on reachability: exploitability requires the attacker to act before `setWhitelistedCDO` is mined. If every production deployment links the CDO atomically in the same transaction as proxy initialization, the window is theoretical; however the contract gives no atomic guarantee, the test suite itself uses two separate transactions, and nothing prevents a non-atomic operational deployment. Given the contract explicitly hardcodes the exception (`"this can happen only during the setup"`), the bug is a genuine code defect regardless of operational timing.

### Likelihood Explanation
- Requires only a deployment/configuration ordering gap — a one-transaction race any MEO bot can win when the owner uses a multi-step script (the pattern the repo's own tests encode).
- No privileged role, KYC, or capital needed; attacker is a plain EOA, which matches the allowed threat model.
- Impact is bounded (manager/owner can re-set APR once aware), so the primary outcome is temporary freezing plus accounting corruption rather than permanent theft — consistent with a High-severity local-elevation analog.

### Recommendation
- Remove the `if (_cdo != address(0))` carve-out and instead allow `owner()` during setup, e.g. `if (msg.sender != _cdo && msg.sender != manager && msg.sender != owner()) revert NotAllowed();`.
- Or set `idleCDO` inside `initialize`/`_additionalInit` (the factory already knows the CDO address at deploy time in `IdleCreditVaultFactory._deployBaseCreditVault`) so no unauthenticated window exists.
- Apply the same bound (`maxApr` or a dedicated cap) to `unscaledApr` in `setAprs`/`setAprsWithBuffer`.

### Proof of Concept
Foundry (mainnet fork as in `test/foundry/IdleCreditVault.t.sol`, FORK_BLOCK 18678289):

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;
import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";

contract AprHijackPoC is Test {
  address constant USDC = 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;
  address attacker = makeAddr("attacker");
  address owner_ = makeAddr("owner");
  address manager_ = makeAddr("manager");
  address borrower_ = makeAddr("borrower");

  function testUnprivilegedAprTakeover() public {
    IdleCreditVault cv = new IdleCreditVault();
    // simulate proxy storage reset like tests do
    stdstore.target(address(cv)).sig(cv.token.selector).checked_write(address(0));
    cv.initialize(USDC, owner_, manager_, borrower_, "Borrower", 10e18);

    assertEq(cv.idleCDO(), address(0), "precondition: CDO not yet linked");

    // attacker (any EOA) frontruns owner's setWhitelistedCDO tx
    vm.prank(attacker);
    cv.setAprs(type(uint256).max, 0); // succeeds: auth check skipped

    assertEq(cv.unscaledApr(), type(uint256).max, "uncapped unscaledApr hijacked");
    assertEq(cv.lastApr(), 0, "lastApr zeroed -> borrowers accrue 0 / accrual corrupted");

    // next: owner finally links CDO — too late, corrupted values are live
    vm.prank(owner_);
    cv.setWhitelistedCDO(makeAddr("cdo"));
    // any interest accrual using unscaledApr now overflows/reverts ->
    // epoch stop and queued-withdraw pricing are frozen until manual recovery
  }
}
```

Expected: `setAprs` from `attacker` succeeds pre-link, demonstrating privilege escalation through the `idleCDO == 0` gap; interest paths become unusable (overflow) or zeroed (theft-of-yield shape) until manual remediation.
