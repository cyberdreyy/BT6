### Title
Stale confirmations from removed multisig members still count toward execution threshold - ([File: multisig2/src/lib.rs])

### Summary
When a member (or key) is removed from a NEAR multisig via `DeleteMember` (multisig2) or `DeleteKey` (multisig v1), the contract only purges confirmations for requests that the *removed member originally created*. Confirmations that the removed member previously cast on *other* pending requests are never cleared, and they continue to be counted toward `num_confirmations` when a subsequent `confirm()` call executes the request.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` counts entries in the `confirmations` `HashSet<String>` for a `request_id` and executes the request once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

`delete_member()` (invoked from `DeleteMember` inside `execute_request`) only removes requests and confirmations where the request was *authored* by the departing member (`r.member == member`); it does not scan or scrub the `confirmations` sets of the remaining pending requests for entries contributed by that member: [2](#0-1) 

Because `confirmations` is a plain `HashSet<String>` of `MultisigMember.to_string()` values (not re-validated against the current `members` set at confirm time other than for the *caller* itself via `assert_valid_request`/`current_member()`), a confirmation cast by a member before their removal remains valid and is still added to the count when the threshold is reached: [3](#0-2) 

The identical pattern exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` only removes requests keyed by the removed `signer_pk` and clears confirmations only for *those* requests, leaving the removed key's confirmation on any *other* still-pending request intact: [4](#0-3) 

This breaks the intended custody binding: **confirmations counted (`confirmations.len()`) must equal confirmations from live members**. After a member/key is removed, the equality `confirmations_counted == confirmations_from_current_members` no longer holds — the counted set can contain confirmations from accounts/keys that are no longer members, so a request can execute with fewer than `num_confirmations` *live* approvals.

### Impact Explanation
This allows a multisig request (e.g., a `Transfer` of NEAR, a `FunctionCall`, or an `AddKey`/`AddMember` granting new access) to be executed while effectively below the configured K-of-N confirmation threshold, because one or more of the counted confirmations came from a party that was removed from the multisig (e.g., an offboarded employee, a compromised/rotated key, or a member removed specifically because they were no longer trusted). This is a request executed below threshold — funds can be moved, or unauthorized keys/members can be added, by fewer genuinely-authorized parties than the multisig's security model requires.

### Likelihood Explanation
Requires a realistic multisig lifecycle event that these contracts explicitly support and document (member/key rotation via `DeleteMember`/`DeleteKey`), combined with a request that was confirmed by the outgoing member before removal but not yet reaching threshold. Any organization that removes a member for cause (compromise, offboarding) while a pending request already carries that member's confirmation is exposed; no privileged bypass or malicious deployment is needed — it is a straightforward operational sequence: confirm → remove member → remaining live members confirm → request executes counting the stale confirmation.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over **all** pending requests (not just those authored by the departing member) and remove the departing member's/key's entry from each request's `confirmations` set, decrementing the counted confirmations accordingly. Alternatively, validate at `confirm()`-time / execution-time that every entry in the `confirmations` set still corresponds to a current member of `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` for `Transfer{amount}` → confirmations = `{A}`.
3. `B` calls `confirm(request_id)` → confirmations = `{A, B}` (2 < 3, not yet executed).
4. The organization submits and executes a separate multisig request `DeleteMember{member: B}` (3-of-3 reached by A, B, C on that unrelated request) — `B` is removed from `self.members`; `delete_member` only scrubs requests where `r.member == B` (requests B *authored*), leaving the Transfer request's confirmation set `{A, B}` untouched: [5](#0-4) 
5. `C` (now the only remaining live member besides `A`) calls `confirm(request_id)` on the original Transfer request → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → the transfer executes, even though only 2 *current* members (`A`, `C`) actually approved it — `B`'s stale confirmation counted toward the threshold. [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
