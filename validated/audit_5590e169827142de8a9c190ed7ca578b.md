### Title
Block-revenue "orphaned rewards" capture via `DepositDelegatorRewards` before stake activation — first delegator gets a disproportionate share (File: `programs/vote/src/vote_state/mod.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`deposit_delegator_rewards` (SIMD-0123) lets any unprivileged signer transfer lamports into a vote account's `pending_delegator_rewards` field at any time, with no check on whether the vote account currently has any active delegated stake. When rewards are subsequently distributed via `calculate_block_reward`, the pending pool is split strictly by `stake / total_active_stake` for the *current* rewarded epoch — with no accounting for how long each delegator's stake was actually active while the pool accumulated. This mirrors the `sdeusd.move` bug class: rewards can pile up while there are zero (or very few) active stakers, and whoever is staked when distribution happens captures a share disproportionate to their actual participation, up to the entire pool if they are briefly the sole staker.

### Finding Description
`deposit_delegator_rewards` in [1](#0-0)  transfers lamports from an arbitrary signer into the vote account and unconditionally calls `add_pending_delegator_rewards`, with no assertion that `total_active_stake` for that vote account is non-zero — analogous to the missing `assert!(total_supply(management) > 0, ENoActiveStakers)` check the report calls out in `transfer_in_rewards()`.

At distribution time, `calculate_block_reward` in [2](#0-1)  computes each delegator's share purely as:

```
pending_delegator_rewards * stake / total_active_stake
```

using `total_active_stake` from `reward_epoch_delegated_stakes.delegated_stakes` for the rewarded epoch [3](#0-2) . If `total_active_stake` was zero (or negligible) while the pool accumulated and a delegator then activates stake for that vote account, that delegator's `stake / total_active_stake` ratio can be 1 (sole staker) or otherwise far larger than their true time-weighted contribution, letting them claim the entire — or a disproportionate share of the — `pending_delegator_rewards` pool that accrued before they staked. There is no vesting/time-weighting mechanism (unlike inflation stake rewards, which are gated by `credits_observed`/epoch activation), and no lower bound requiring stake to have been active for the period over which the deposit accumulated.

### Impact Explanation
Impact is limited relative to the `sdeusd.move` case: this does not mint unbacked funds or break consensus — the lamports being redistributed were legitimately deposited by a signer. The economic harm is a timing-based unfairness/griefing vector: a party can deposit rewards to a vote account with little/no delegated stake, then delegate (or coordinate with a colluding validator/delegator) immediately before distribution to capture a reward share not proportional to actual stake-time contribution, at the expense of delegators who would otherwise have shared it more fairly, or at the expense of the depositor's intended target set of long-term stakers. This is a fairness/incentive-design flaw reachable by an unprivileged transaction sender (`DepositDelegatorRewards` + a stake delegation), not a fund-conservation or double-spend bug — funds distributed never exceed `pending_delegator_rewards`, and the code even clamps with `.min(pending_delegator_rewards)` [4](#0-3) .

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires SIMD-0123 features to be active (`block_revenue_sharing`, `custom_commission_collector`, `commission_rate_in_basis_points`) [5](#0-4) , a vote account willing to accept deposits while having low/zero delegated stake, and precise timing of stake activation relative to the epoch boundary and deposit. This is more of a griefing/incentive-fairness issue than a directly and cheaply exploitable fund-extraction bug, since the attacker/first-staker is only capturing lamports that were voluntarily deposited (often by the validator/operator itself), not minting new value or stealing from other parties' principal.

### Recommendation
Consider requiring `deposit_delegator_rewards` to check that the vote account currently has non-zero delegated stake before accepting a deposit (mirroring the report's suggested `assert!(total_supply(management) > 0, ENoActiveStakers)`), or alternatively make `calculate_block_reward`'s distribution time-weighted (e.g., vest deposits over some period, or require a minimum stake-active-epoch count) rather than an instantaneous `stake / total_active_stake` snapshot at reward-epoch's end, so delegators cannot capture pool value accrued before their stake was active.

### Proof of Concept
1. Vote account `V` has `pending_delegator_rewards = 0` and zero (or negligible) delegated stake for several epochs.
2. Anyone submits `DepositDelegatorRewards { deposit: N }` for `V` — this succeeds unconditionally per [6](#0-5) , setting `pending_delegator_rewards = N`.
3. Immediately after, a delegator activates a stake account delegated to `V` such that, by the end of the rewarded epoch, `stake_history`/`reward_epoch_delegated_stakes` shows this delegator as (effectively) the only active stake for `V` (`total_active_stake ≈ stake`).
4. At epoch-reward distribution, `calculate_block_reward` computes `block_reward ≈ N * stake / total_active_stake ≈ N` [7](#0-6) , so the delegator receives (approximately) the entire deposited pool despite having no stake-time exposure during most of the period the deposit accrued.

Note: Due to index size limits, the exact mechanics of `store_stake_accounts_in_partition` (how/whether `pending_delegator_rewards` is decremented on payout) in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` could not be fully retrieved in this session; a Devin session with full file access would be needed to confirm the exact decrement/consumption logic and whether any additional safeguard exists there.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
