### Title
Precision loss in SPL-token `ui_amount` (f64) conversion causes misreported token balances in RPC / `jsonParsed` responses - (File: account-decoder/src/parse_token.rs)

### Summary
The PoolTogether finding is a classic "round-down when converting between raw integer units and a derived value" precision-loss bug that silently produces a wrong reported/derived value. The closest reachable analog in this repo is in `token_amount_to_ui_amount_v3`, which converts a raw `u64` token amount into a floating-point `ui_amount` for display in `jsonParsed` account/instruction responses. Any unprivileged user can create an SPL Token / Token-2022 mint and account with an arbitrary raw `amount` and `decimals`, then query it via public JSON-RPC (`getAccountInfo` with `encoding: "jsonParsed"`, `getTokenAccountBalance`, `getParsedTokenAccountsByOwner`, or parsed instruction data in `getTransaction`), causing the node to compute and return an imprecise `ui_amount`.

### Finding Description
`token_amount_to_ui_amount_v3` computes the informational `ui_amount` field by casting the raw `u64` amount to `f64` and dividing by `10^decimals`: [1](#0-0) 

`f64` can only exactly represent integers up to 2^53 (~9.007×10^15). For any token whose raw `amount` exceeds this threshold (easily reachable since `amount` is a `u64`, and `decimals` is attacker-controlled, e.g. `decimals = 0` or small), the cast `amount as f64` silently loses precision, so `ui_amount` no longer reflects the true value encoded in `amount`. This mirrors the PoolTogether bug class: a rounding/precision step in a derived-value computation ("round down"/"lossy cast") that is not guarded, causing the reported value to diverge from the ground truth (`amount`, the actual raw account state).

Separately, this same function also handles Token-2022 extension-derived amounts (`interest_bearing_config.amount_to_ui_amount`, `scaled_ui_amount_config.amount_to_ui_amount`) which parse a string back into `f64` via `f64::from_str` and can yield `f64::INFINITY`/`"inf"` for attacker-chosen extension parameters: [2](#0-1) 
The existing unit tests explicitly demonstrate `ui_amount == Some(f64::INFINITY)` and `ui_amount_string == "inf"` for adversarial mint configuration: [3](#0-2) [4](#0-3) 

This decoding logic is invoked from the public RPC surface for `jsonParsed` account decoding and parsed instructions: [5](#0-4) [6](#0-5) 

The `amount` string field (raw, exact) is always returned alongside the lossy `ui_amount`, and `ui_amount_string` is computed independently via exact string arithmetic in most non-extension cases: [7](#0-6) 
so the exact value is still recoverable from `amount`/`ui_amount_string`, which reduces — but for the extension paths (`interest_bearing_config`/`scaled_ui_amount_config`) does not eliminate — the practical impact, since those paths can produce `"inf"` for both fields.

### Impact Explanation
This is a misreporting bug within an unprivileged, publicly-reachable RPC/account-decoding path (`getAccountInfo` `jsonParsed`, `getTokenAccountBalance`, parsed token instructions in transaction/tx-status APIs). It does not corrupt consensus state, does not crash the validator, and does not affect actual token balances or fund custody — the raw `amount` field remains correct. The impact is limited to downstream consumers (wallets, explorers, bots) that trust the floating-point `ui_amount`/`ui_amount_string` fields for financial decisions, which could display incorrect (including infinite) balances for maliciously configured mints or extremely large raw amounts. This is a low-severity "misreporting" class rather than a fund-loss or availability issue, unlike the original PoolTogether under-collateralization bug (which directly gated deposits/withdrawals).

### Likelihood Explanation
High likelihood of the *decoding* condition being triggered (any user can mint tokens with `decimals = 0` and `amount` close to `u64::MAX`, or configure a Token-2022 mint with an extreme `ScaledUiAmountConfig`/`InterestBearingConfig`), since token creation and RPC queries are fully permissionless. However, likelihood of meaningful *harm* is low because most serious consumers rely on the raw `amount` string, not the derived float, for anything security-relevant.

### Recommendation
- For the non-extension path in `token_amount_to_ui_amount_v3`, treat `ui_amount` purely as a best-effort display value and document/clamp precision limits (e.g., return `None` when `amount` exceeds `2^53` for the given `decimals`, similar to how the `checked_pow` overflow path already returns `None`).
- For the `interest_bearing_config`/`scaled_ui_amount_config` extension paths, validate/clamp extension-provided multipliers and rates so that `amount_to_ui_amount` cannot produce `inf`/`NaN`, or explicitly represent such cases as `None` rather than serializing `"inf"` to RPC consumers.

pub fn real_number_string(amount: u64, decimals: u8) -> String {
    let decimals = decimals as usize;
    if decimals > 0 {
        // Left-pad zeros to decimals + 1, so we at least have an integer zero
        let mut s = format!("{:01$}", amount, decimals + 1);
        // Add the decimal point (Sorry, "," locales!)
        s.insert(s.len() - decimals, '.');
        s
    } else {
        amount.to_string()
    }
}

pub fn real_number_string_trimmed(amount: u64, decimals: u8) -> String {
    let mut s = real_number_string(amount, decimals);
    if decimals > 0 {
        let zeros_trimmed = s.trim_end_matches('0');
        s = zeros_trimmed.trim_end_matches('.').to_string();
    }
    s
}
