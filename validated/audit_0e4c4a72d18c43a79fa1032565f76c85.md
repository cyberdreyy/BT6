### Title
Unbounded zstd compression cost in `encode_ui_account`'s Base64Zstd branch scales with attacker-controlled account size - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account`'s `UiAccountEncoding::Base64Zstd` branch feeds the entire (post-slice) account data buffer directly into a `zstd::stream::write::Encoder` with no separate size/CPU budget check beyond the account's own on-chain size. An attacker who writes a large, high-entropy (poorly compressible) account and then requests it via `getAccountInfo`/`getProgramAccounts`/`accountSubscribe` with `encoding=base64+zstd` forces the RPC node to perform a full zstd compression pass over that data on every single call, with cost scaling linearly with account size and no independent ceiling.

### Finding Description
In `encode_ui_account`, the `Base64Zstd` arm constructs a fresh `zstd::stream::write::Encoder` and calls `write_all`/`finish` on `slice_data(account.data(), data_slice_config)` without any pre-check on the size of the data being compressed or the compression effort involved: [1](#0-0) 

Unlike `encode_bs58`, which explicitly rejects slices larger than `MAX_BASE58_BYTES` before doing any encoding work, there is no analogous guard in the `Base64Zstd` branch limiting the amount of data handed to the zstd encoder: [2](#0-1) 

`slice_data` only bounds the data by the caller-provided `data_slice_config` (offset/length), which defaults to the full account data if unset, so a client that omits `dataSlice` (as is typical for `getAccountInfo`) causes the entire account body to be handed to the encoder: [3](#0-2) 

The compression cost is a function purely of the number of input bytes and their entropy; zstd on random, non-repetitive data cannot exploit dictionary matches and thus does the maximum amount of match-finding work per byte for the given compression level, making high-entropy data close to worst-case CPU cost for a given size. The only limit on the input size is the network-wide account data size cap, not any RPC-encoding-specific throttle, meaning the cost of a single JSON-RPC/pubsub request handling this encoding is bounded exclusively by how large an account the attacker chooses to create on-chain, not by an independent resource budget in the encoder path itself.

### Impact Explanation
This falls under the "unbounded cost for a single low-rate call" category: a single `getAccountInfo`/`getProgramAccounts`/`accountSubscribe` call with `encoding=base64+zstd` against an attacker-authored, maximally-sized, incompressible account forces the validator's RPC service to perform CPU/memory work proportional to the full account size on every request, repeated indefinitely at the permitted rate (one call per `CLUSTER_SLOT_TIME_TARGET / 2`). This can be used to sustain elevated CPU/memory load on the RPC-serving node's JSON-RPC thread pool with a cheap, repeatable, unprivileged action, since there is no distinct cost ceiling for the encode step separate from the account's on-chain size.

### Likelihood Explanation
The attacker only needs unprivileged ability to write/own an account (e.g. via a system/data program) up to the maximum permitted account size with high-entropy content, and then issue a single, legal JSON-RPC/pubsub request specifying `base64+zstd` encoding for that account — both of which are within the stated attacker capability (one on-chain write, one client call at the allowed rate). This is straightforward and fully reproducible without any validator/leader/peer control.

### Recommendation
Add an explicit size/cost guard for the `Base64Zstd` (and ideally `Base64`) encoding path analogous to `MAX_BASE58_BYTES` for `encode_bs58` — e.g., reject or fall back to a cheaper encoding (or require `dataSlice`) when the sliced data exceeds a fixed threshold, or apply a per-request CPU/memory budget (e.g., using a bounded zstd compression level and a hard byte-count cap) so that encode cost for a single RPC call is capped independent of the account's actual on-chain size.

### Proof of Concept
Add a benchmark/unit test in `account-decoder/src/lib.rs` (or a new bench file) exercising `encode_ui_account` with `UiAccountEncoding::Base64Zstd` over increasing account sizes filled with random/incompressible bytes up to the maximum permitted account data length, asserting wall-clock/CPU time (and peak allocation) grows linearly with input size and exceeds a fixed budget (e.g., >5ms/MB) at max size — demonstrating the absence of an explicit ceiling distinct from account size:

```rust
#[test]
fn bench_base64_zstd_incompressible_scales_with_size() {
    use std::time::Instant;
    let sizes = [1_024, 1_048_576, 10_485_760]; // up to MAX account size
    for size in sizes {
        let data: Vec<u8> = (0..size).map(|_| rand::random::<u8>()).collect();
        let account = AccountSharedData::from(Account { data, ..Account::default() });
        let start = Instant::now();
        let _ = encode_ui_account(&Pubkey::default(), &account, UiAccountEncoding::Base64Zstd, None, None);
        let elapsed = start.elapsed();
        println!("size={size} elapsed={elapsed:?}");
        // Expect: no explicit per-call budget rejects/caps large incompressible inputs;
        // elapsed time scales roughly linearly with `size`, with no independent ceiling.
    }
}
```
Expected result: time/memory usage for the largest (max-permitted-size) incompressible account is substantially higher than for small accounts, confirming per-call cost is bounded only by account size, not an explicit encoder-side budget.

fn slice_data(data: &[u8], data_slice_config: Option<UiDataSliceConfig>) -> &[u8] {
    if let Some(UiDataSliceConfig { offset, length }) = data_slice_config {
        if offset >= data.len() {
            &[]
        } else if length > data.len() - offset {
            &data[offset..]
        } else {
            &data[offset..offset + length]
        }
    } else {
        data
    }
}
