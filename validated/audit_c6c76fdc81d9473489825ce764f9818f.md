### Title
Stale APR0 withdraw request permanently reverts `stopEpoch` after an APR change, freezing all vault funds - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged lender can plant a dust-sized APR0 withdraw request, and once the APR is later set non-zero (a routine manager operation, or the `setAprs` path that has no epoch-phase guard), every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts before its try/catch, so no epoch can ever close and no queued withdrawal can be funded until governance remediates. This mirrors ALPINE-CVE-2021-25214: a malformed/poison record accepted at request time crashes the next state "refresh" (epoch rollover).

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request is routed to `_requestWithdrawApr0`, which increments `apr0TotalPrincipal` and stores `apr0Users[_user].principalEpoch = epochNumber` (`IdleCreditVault.sol:285-294`, `567-577`).

`setAprs`/`setApr` has no check on `apr0TotalPrincipal` and no epoch-phase gating (`IdleCreditVault.sol:206-235`), so `unscaledApr` can become non-zero while an APR0 bucket is still open — e.g. the manager updates the vault APR mid-buffer while a user's request is pending, or an APR0 request is made during a window where APR was 0 and the APR is raised before `stopEpoch`.

At stop time, `_stopEpoch` calls `prepareStopEpochWithApr0` **before** entering the `try`/`catch` block (`IdleCDOEpochVariant.sol:362`). Inside it:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
if (unscaledApr != 0) {
  revert NotAllowed();
}
```
(`IdleCreditVault.sol:499-508`)

Because this revert happens outside the `try this.getFundsFromBorrower(...)` block, it does not trigger `_handleBorrowerDefault`; the whole `stopEpoch`/`stopEpochWithDuration` transaction reverts.

The deadlock:
- `apr0TotalPrincipal` is only cleared inside `prepareStopEpochWithApr0` (line 540), which is unreachable while `unscaledApr != 0`.
- `epochNumber` only increments in `deposit()` during a successful `stopEpoch` (`IdleCreditVault.sol:607-610`), so the user's `_settleApr0` can never pass the `reqEpoch >= epochNumber` gate (`IdleCreditVault.sol:553`) to clear the bucket via `claimWithdrawRequest`.
- The user's receipt tokens are burned/minted ledger entries claimable only through the CDO; there is no user-side cancel.

Result: the epoch can never be stopped while `unscaledApr != 0`. The only recovery is a privileged `setAprs(0, 0)` followed by a `stopEpoch` — meaning the APR is forced back to 0 for an entire epoch boundary, and until the manager performs this non-obvious sequence the vault is stuck.

### Impact Explanation
- All pending normal withdrawals (`pendingWithdraws`) cannot be funded: `collectWithdrawFunds` is only reached inside a successful `stopEpoch`.
- Active lenders cannot exit: withdrawal claims require `epochNumber > lastWithdrawRequest` (`_claimFundedWithdrawRequest`, `IdleCreditVault.sol:326`), which requires a completed `stopEpoch`.
- Deposits and new requests continue to be accepted during the buffer while the vault is unclosable, enlarging the stuck principal.
- Recovery forces the pool to run an extra epoch boundary at `unscaledApr == 0`, i.e. interest-free lending of the entire TVL to the borrower for that period — a direct, quantified yield loss equal to `TVL * intendedApr * epochDuration / YEAR`, plus the freeze duration. Trigger cost for the attacker is one dust-sized tranche deposit + `requestWithdraw`.

### Likelihood Explanation
Requires (a) vault operating at `unscaledApr == 0` (supported mode — the APR0 flow exists specifically for it), and (b) APR being raised while an APR0 request is open. (b) is a routine, honest manager action; `setApr` is explicitly callable by the manager at any time with no phase check. An attacker only needs to keep a dust request open during the APR0 window to arm the trap, at negligible cost.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert on `unscaledApr != 0`; instead settle the APR0 bucket at a zero rate (skip the pro-rata interest split, just close `apr0TotalPrincipal` and record `apr0RateByEpoch[epochNumber] = 0`), or alternatively, settle the open bucket at the *new* rate. Add a guard in `setAprs`/`requestWithdraw` so an APR cannot move away from 0 while `apr0TotalPrincipal > 0`, or fold APR0 settlement into `stopEpoch` unconditionally.

### Proof of Concept
Foundry fork sketch (mode: fixed-APR, `unscaledApr = 0`, non-programmable borrower, buffer phase):

```solidity
// 1. Vault running at APR = 0, epoch ended -> buffer phase
// 2. Attacker (KYC'd AA holder) deposits dust and requests withdraw
vm.prank(attacker);
cdo.depositAA(dust);
vm.prank(attacker);
cdo.requestWithdraw(dustShares, AATranche); // -> _requestWithdrawApr0, apr0TotalPrincipal = dust

// 3. Manager legitimately raises APR before stopping the epoch
vm.prank(manager);
strategy.setAprs(10e18, 10e18); // unscaledApr = 10e18, apr0TotalPrincipal still > 0

// 4. Any stopEpoch now reverts permanently
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpoch(10e18, 0);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdo.stopEpochWithDuration(10e18, 0, epochDuration, 0);

// 5. Claim also cannot clear the bucket: epochNumber <= principalEpoch
vm.prank(attacker);
vm.expectRevert(NotAllowed.selector);
cdo.claimWithdrawRequest(); // epochNumber <= lastWithdrawRequest -> revert

// 6. Vault frozen: pendingWithdraws never funded until setAprs(0,0) + stopEpoch at APR 0
```
