## Title
Stale confirmations from removed multisig members are still counted toward the approval threshold, allowing a request to execute below the configured `num_confirmations` - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
When a multisig member is removed via `DeleteMember` (or `DeleteKey` in the legacy contract), the contract only purges the *requests that member itself created*, but it never removes that member's existing **confirmations** on requests created by *other* members. `confirm()` later counts `confirmations.len()` toward `num_confirmations` without re-validating that every recorded confirmer is still a current member, so a stale confirmation from a departed member can combine with a single live confirmation to trigger execution, even though fewer than `num_confirmations` *currently authorized* members actually approved the request.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member()` only cleans up requests whose creator (`r.member`) equals the removed member: [1](#0-0) 

It does not scan `self.confirmations` for entries referencing the removed member on requests created by *other* members. Those stale confirmation strings remain in the `confirmations` `HashSet<String>` for those requests.

`confirm()` then decides whether to execute purely based on the size of that set plus one, without re-checking that the members inside it are still part of `self.members`: [2](#0-1) 

The only membership check performed is on the *current* caller via `current_member()`/`assert_valid_request()`: [3](#0-2) 

Because the threshold check is `confirmations.len() as u32 + 1 >= self.num_confirmations`, a confirmation recorded by a member who has since been deleted is still counted as valid weight.

The legacy `multisig/src/lib.rs` contract has the identical structural flaw, keyed by `signer_pk` instead of `MultisigMember`: `DeleteKey` only removes requests created by that key and only removes `num_requests_pk` bookkeeping, leaving that key's confirmations on other members' pending requests untouched: [4](#0-3) [5](#0-4) 

The binding that should hold is:
`num_valid_confirmations(request) == |{c ∈ confirmations(request) : c ∈ current_members}|`, and execution should require `num_valid_confirmations(request) >= num_confirmations`.

The actual code instead checks `|confirmations(request)| >= num_confirmations` without filtering by current membership, so the invariant `confirmations counted == confirmations from live members` is broken.

### Impact Explanation
This directly matches the "multisig request executed below threshold" Critical impact category. A request (e.g., a `Transfer` moving NEAR out of the multisig account, or an `AddKey`/`AddMember` granting a new full-access key) can be executed with fewer live, currently-authorized confirmations than `num_confirmations` requires, because a confirmation from a removed member is still tallied. This undermines the core "K out of N" security guarantee the contract is supposed to provide and can lead to unauthorized transfer of funds or unauthorized key/member additions with less real consensus than configured.

### Likelihood Explanation
This requires no attacker to break cryptography or bypass any authorization check directly — it is triggered purely by the normal, expected lifecycle of the contract: members are added and removed over time (turnover, key rotation, compromised key removal), and any request that received a confirmation from a member prior to that member's removal remains "live" with its stale confirmation intact. Any request left pending across a membership change is susceptible; no special timing tricks or privilege escalation beyond ordinary usage is needed to hit the code path.

### Recommendation
When confirming a request, filter `confirmations` to only members currently present in `self.members` before comparing against `num_confirmations`, e.g. `confirmations.iter().filter(|c| self.members.contains(...)).count()`. Additionally, when a member is deleted, prune that member's confirmation entries from every pending request's `confirmations` set (not just requests they created), and consider re-validating/pruning stale confirmations on `add_request`/`confirm`/`delete_member` uniformly for both `multisig/src/lib.rs` and `multisig2/src/lib.rs`.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 2` and `members = [A, B, C]`.
2. `B` calls `add_request(request)` creating `request_id = R1` (e.g., a `Transfer` of the account's balance) — `confirmations(R1) = {}`.
3. `A` calls `confirm(R1)` → `confirmations(R1) = {A}`, `1 < 2`, not executed.
4. Through normal governance, members create and confirm a `DeleteMember{A}` request (a legitimate, unrelated action, e.g. because A's key rotated) — `A` is removed from `self.members`. Since `R1.member == B` (not `A`), `delete_member()` does **not** touch `R1` or its confirmations: [6](#0-5) 
5. `C` calls `confirm(R1)`. In `confirm()`, `confirmations(R1) = {A, C}`, so `confirmations.len() as u32 + 1 = 3 >= num_confirmations (2)` — actually `2 >= 2` even before adding C is reached at the `+1` check — the request executes via `self.execute_request(request)`: [7](#0-6) 
6. The `Transfer` executes, even though `A` is no longer a member and only `C`'s confirmation is a live, current-member approval alongside `B`'s unconfirmed creation — effectively 1 live confirming member instead of the required 2.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
