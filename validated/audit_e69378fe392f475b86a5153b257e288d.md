### Title
Zip-slip / missing path confinement in legacy zip extractor allows path traversal, unlike `tarzstd` extractor - ([File: helpers/archives/zip_extract.go])

### Summary
`ExtractZipArchive` in `helpers/archives/zip_extract.go` writes each zip entry using the raw `file.Name` from the archive with no directory-confinement check, only checking for a literal `.git` prefix via `errorIfGitDirectory` (which just warns, it does not block extraction). In contrast, the `tarzstd` extractor's `Extract` method explicitly rejects any entry whose resolved absolute path does not start with `e.dir+separator`. This is a real, reachable divergence in path-traversal protection between formats.

### Finding Description
`ExtractZipArchive` iterates `archive.File` entries and, for every entry, calls `errorIfGitDirectory(file.Name)` (only detects `.git` as the first path component) and then `extractZipFile(file)`. [1](#0-0) 
`extractZipFile` builds the destination purely from `file.Name` — `filepath.Dir(file.Name)` for `MkdirAll`, and `file.Name` directly for `os.OpenFile`/`os.Symlink`/`os.Mkdir` — with no `filepath.Join` against a confinement root and no rejection of `..` segments. [2](#0-1) 
`errorIfGitDirectory` only checks whether the first path component (after `filepath.Clean`) equals `.git`; it has no bearing on `../` traversal and, per the observed code, any actionable error is merely logged as a warning via `printGitArchiveWarning`, not treated as fatal for extraction. [3](#0-2) 

This legacy zip extractor is reachable in production: it is wired up by `ziplegacy.NewExtractor`, whose `Extract` method calls `archives.ExtractZipArchive(zr)` directly — critically, the `dir` field on the `ziplegacy` extractor struct is never passed to or used by `ExtractZipArchive`, so there is no directory root enforced at all for this code path. [4](#0-3) 

By contrast, `tarzstd`'s `Extract` computes `path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name))` and then enforces `strings.HasPrefix(path, e.dir+string(filepath.Separator)) || path == e.dir`, returning an error ("cannot be extracted outside of chroot") for any entry that would traverse outside `e.dir`. [5](#0-4) 

The dispatch layer treats formats uniformly through a common `archive.Extractor` interface (`Extract(ctx) error`), selected via `NewExtractor(format, r, size, dir)`, so a caller cannot tell from the interface that one implementation enforces confinement and another does not. [6](#0-5) [7](#0-6) 

Note: the modern/default zip path uses `fastzip.NewExtractorFromReader(...).Extract(ctx)`, delegating path handling to the third-party `fastzip` library rather than `archives.ExtractZipArchive`. [8](#0-7) 
I was unable to fully verify, within the remaining tool budget, under exactly which conditions/build configuration the `ziplegacy` extractor (rather than `fastzip`) is registered/selected as the handler for `Format Zip` at runtime (e.g., env var override, legacy fallback, specific OS). This is the one open question that determines real-world exploitability versus dead/legacy code — a background agent with full repo access should confirm the `Register(archive.Zip, ...)` call site(s).

### Impact Explanation
If the `ziplegacy` extractor is reachable for any supported code path (cache/artifact extraction), an attacker who controls the contents of an uploaded zip artifact or cache archive can include an entry like `../../../etc/cron.d/evil` or `../victim-project/.git/hooks/pre-commit`. Because `extractZipFile` uses the raw entry name with no confinement check, extraction would write outside the intended build/cache/artifact directory, potentially overwriting files elsewhere on the runner host's filesystem (e.g., other projects' checked-out repositories co-located on a shared runner host, or arbitrary writable paths reachable from the extraction process's working directory) — this directly violates the invariant that "file operations must stay within intended build/cache/artifact roots" and that a job "must not access another project's workload."

### Likelihood Explanation
Reachability depends on confirming that `ziplegacy.NewExtractor` (rather than `fastzip`) is actually registered/used for `Format Zip` extraction in some configuration. `errorIfGitDirectory`/`printGitArchiveWarning` show this is exercised code (there's `zip_extract_test.go`), and the interface-uniform dispatch (`archive.NewExtractor`) means format selection is data-driven, consistent with the question's precondition that zip/tar.zst are interchangeable per job config. Given the `dir` field is unused entirely in the legacy extractor, this looks like an unintentional regression/gap rather than an intentionally accepted risk — it is not a documented admin trust boundary.

### Recommendation
Add the same absolute-path confinement check used in `tarzstd`'s `Extract` to `ExtractZipArchive`/`extractZipFile`: resolve `filepath.Join(dir, file.Name)` to an absolute path and reject any entry whose resolved path is not equal to or does not have `dir+separator` as prefix, before performing `MkdirAll`/`OpenFile`/`Symlink`. Thread the extraction root (`dir`) through `ExtractZipArchive`/`ExtractZipFile` (currently dropped by `ziplegacy.extractor.Extract`) so the check has a root to enforce against. Ensure `errorIfGitDirectory` failures are also treated consistently across formats if they are meant to be blocking rather than warning-only.

### Proof of Concept
Go unit test (to be run against `helpers/archives` package, extending `zip_extract_test.go`):
1. Create an in-memory zip (`archive/zip`) with a single entry named `../evil.txt`.
2. Call `archives.ExtractZipArchive(zr)` from within a fresh temp "extraction" directory `tmpdir/extract`.
3. Assert: `os.Stat(filepath.Join(tmpdir, "evil.txt"))` (i.e., outside `extract/`) succeeds — proving traversal outside the intended root.
4. As a differential comparison, build the equivalent tar.zst archive with the same `../evil.txt` entry, call `tarzstd.NewExtractor(r, size, tmpdir+"/extract").Extract(ctx)`, and assert it returns the `"cannot be extracted outside of chroot"` error and that `filepath.Join(tmpdir, "evil.txt")` does NOT exist.
5. The differing accept/reject outcomes for identical relative-path payloads confirm the format-selection bypass described in the question, contingent on confirming `ziplegacy`'s registration as an active `Format Zip` handler.

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}

func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))
	if len(parts) > 0 && parts[0] == ".git" {
		return true
	}
	return false
}

func errorIfGitDirectory(path string) *os.PathError {
	if !isPathAGitDirectory(path) {
		return nil
	}

	return &os.PathError{
		Op:   ".git inside of archive",
		Path: path,
		Err:  errors.New("trying to archive or extract .git path"),
	}
}
