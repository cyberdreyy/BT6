### Title
`grantRole` allows granting `DEFAULT_ADMIN_ROLE` (or any role) to `address(0)`, permanently bricking the role - ([File: crates/common/precompiles/src/b20_asset/logic/v1.rs])

### Summary
The B-20 asset/stablecoin precompile's `grant_role`/`grant_role_unchecked` implementations never reject `account == Address::ZERO`, unlike every value-moving path in the same file (`transfer`, `transfer_from`, `mint`, `approve`), which all explicitly check for and reject `Address::ZERO`. This is the same bug class as the reported `BvbProtocol.transferPosition` issue: a privileged state-transition function accepts the zero address as a legitimate recipient/holder of a role, when it can never be exercised by a real signer.

### Finding Description
`grant_role_unchecked` in `crates/common/precompiles/src/b20_asset/logic/v1.rs` (and the equivalent `v2.rs`, and the `b20_stablecoin` counterparts) unconditionally sets the role for `account` without validating it is non-zero: [1](#0-0) 

This is reachable through the authorized path `grant_role`, which only checks the caller's authorization (role-admin membership), never the target `account`: [2](#0-1) 

Contrast this with every balance-affecting mutation in the exact same file, which treats `Address::ZERO` as an explicit `InvalidReceiver`/`InvalidSender`/`InvalidApprover` condition: [3](#0-2) [4](#0-3) 

The `DEFAULT_ADMIN_ROLE` case is the concerning one, because `role_member_count` is tracked specifically to prevent the *last* admin from renouncing: [5](#0-4) [6](#0-5) 

Since `account == Address::ZERO` is never checked, a legitimate admin can call `grantRole(DEFAULT_ADMIN_ROLE, address(0))`. This increments `role_member_count` to 2, so `revoke_role`'s "last admin" guard no longer blocks the real admin from subsequently renouncing/being revoked (`role_member_count != 1`). Once the real admin exits, `address(0)` remains recorded as the sole `DEFAULT_ADMIN_ROLE` holder — but since no transaction can ever originate with `msg.sender == address(0)` (no one holds its private key, and normal transactions require valid ECDSA recovery to a nonzero address), all admin-gated functions in the token (role management, policy updates, supply-cap changes, pause controls, etc., gated via `B20Guards::ensure_role`/`ensure_token_role`) become permanently unreachable — a griefing/self-bricking path, or a foot-gun that removes the "last admin" safety net the code otherwise takes pains to implement.

### Impact Explanation
This permanently and irrecoverably locks all `DEFAULT_ADMIN_ROLE`-gated administrative functionality of a deployed B-20 asset/stablecoin token (grant/revoke role, `set_role_admin`, policy updates such as pause/unpause, supply cap changes, mint role management). Because there is no privileged escape hatch or admin-recovery mechanism modeled here beyond the `role_member_count == 1` last-admin guard, this results in a permanent denial-of-service of that token's admin surface — matching the "permanent freezing of funds/functionality" impact bar, since operations such as unpausing a paused token, or granting a new mint role, would become impossible once the sole functioning admin exits.

### Likelihood Explanation
This requires the current `DEFAULT_ADMIN_ROLE` holder to intentionally or mistakenly call `grantRole(DEFAULT_ADMIN_ROLE, address(0))` and then relinquish their own admin role (revoke or renounce). This could happen via a scripting/tooling bug (e.g., an uninitialized `newAdmin` variable defaulting to `address(0)` in an off-chain admin-rotation script), mirroring exactly the scenario the original Sherlock report describes — an unintended zero-address transfer with no on-chain guard to catch it. It requires an unprivileged/inadvertent action by an authorized (not attacker) party, so likelihood is that of an operational/foot-gun bug rather than a directly attacker-triggerable exploit, but the missing check is unambiguous and trivial to demonstrate.

### Recommendation
Add an explicit zero-address check in `grant_role`/`grant_role_unchecked` (and the `b20_stablecoin` equivalents) mirroring the pattern already used in `transfer`, `mint`, and `approve`:
```rust
if account == Address::ZERO {
    return Err(BasePrecompileError::revert(IB20::InvalidReceiver { receiver: account }));
}
```
placed before `token.accounting_mut().set_role(role, account, true)?;` in `grant_role_unchecked`, for both the `b20_asset` and `b20_stablecoin` V1/V2 logic implementations.

### Proof of Concept
1. Deploy a B-20 asset token; `ADMIN` holds `DEFAULT_ADMIN_ROLE` (member count = 1).
2. `ADMIN` calls `grantRole(DEFAULT_ADMIN_ROLE, address(0))`. This succeeds silently, per `grant_role_unchecked` at [1](#0-0) , bumping `role_member_count` to 2.
3. `ADMIN` then calls `revokeRole(DEFAULT_ADMIN_ROLE, ADMIN)` (or `renounceRole`). The last-admin guard at [7](#0-6)  only fires when `role_member_count == 1`; here it is 2, so the guard is bypassed and the real admin is removed.
4. `address(0)` is now the sole `DEFAULT_ADMIN_ROLE` holder. No transaction can ever be signed with `from == address(0)`, so no future call can pass `B20Guards::ensure_role`/`ensure_token_role(DefaultAdmin)` checks — all admin-only functions on this token are permanently disabled.

Note: I was not able to fully trace whether the factory's initial-admin bootstrap path (`grant_role_unchecked` called from the factory, `crates/common/precompiles/src/b20_factory/logic/v1.rs`) independently constrains the initial admin to be non-zero; this is a secondary path outside the primary bug demonstrated above, and I could not verify its full guard chain within the available search results, so it is not asserted in the finding.

    fn grant_role_unchecked(
        &self,
        token: &mut B20AssetToken<S, A>,
        role: B256,
        account: Address,
        sender: Address,
    ) -> Result<()> {
        if token.accounting().has_role(role, account)? {
            return Ok(());
        }
        token.accounting_mut().set_role(role, account, true)?;
        if role == B20TokenRole::DefaultAdmin.id() {
            let current = token.accounting().role_member_count(role)?;
            let next =
                current.checked_add(U256::ONE).ok_or_else(BasePrecompileError::under_overflow)?;
            token.accounting_mut().set_role_member_count(role, next)?;
        }
        token
            .accounting_mut()
            .emit_event(IB20::RoleGranted { role, account, sender }.encode_log_data())
    }
