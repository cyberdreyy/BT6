### Title
Lockup contract trusts staking pool's `withdraw()` promise success without verifying actual NEAR received, allowing funds to be permanently stranded at a malicious/faulty whitelisted pool - (File: lockup/src/owner.rs, lockup/src/owner_callbacks.rs, lockup/src/foundation_callbacks.rs)

### Summary
The lockup contract's staking-pool integration mirrors the reported router pattern exactly: it whitelists an external contract (a staking pool, analogous to the router) and then, after invoking that contract's privileged method (`withdraw`), only checks `is_promise_success()` before updating its internal accounting — it never verifies that the NEAR balance it actually holds increased by the requested amount.

### Finding Description
`withdraw_from_staking_pool` sends a cross-contract `withdraw(amount)` call to the currently selected staking pool and attaches a callback: [1](#0-0) 

The callback `on_staking_pool_withdraw` treats `is_promise_success()` as proof that `amount` NEAR was actually transferred back to the lockup account, and unconditionally decrements the internal `deposit_amount` ledger by that amount: [2](#0-1) 

`is_promise_success()` only confirms the callee's function did not panic — it does **not** confirm that a `Promise::transfer` of the requested amount actually executed or landed. There is no before/after check of `env::account_balance()` around this call, which is precisely the missing invariant flagged in the original report ("similar before-after balance checks are missing" for the router's transfer). The same unchecked pattern is repeated in the foundation's termination-withdrawal path: [3](#0-2) 

This is a legitimate trust-boundary analog: the whitelist contract is documented as the mechanism that lets a lockup delegate to a staking pool because "the staking pool should faithfully implement the spec... such as the lockup contract should be able to recover delegated tokens back to the lockup from a staking pool": [4](#0-3) 

Any account can be whitelisted either directly by the Foundation or, permissionlessly, via a whitelisted factory that "allows any user to create a new whitelisted staking pool": [5](#0-4) 

A pool created and whitelisted this way — or a legitimate pool later compromised/misbehaving — can implement `withdraw()` to return successfully (no panic) without issuing the corresponding `Promise::transfer`. The lockup contract has no defense against this: it decrements its internal `deposit_amount` as if the funds were returned, while the actual NEAR balance of the lockup account (`env::account_balance()`) never increases.

### Impact Explanation
The binding that should hold is:
```
deposit_amount_decrease == actual_increase_in(env::account_balance())
```
After a malicious/faulty pool's `withdraw` promise succeeds without transferring funds, this equality breaks: `deposit_amount` (the ledger of NEAR believed to still be at the pool) is reduced to reflect a withdrawal that never happened, while `env::account_balance()` stays flat. Because `get_owners_balance()` and `get_liquid_owners_balance()` derive directly from `env::account_balance() + get_known_deposited_balance()`: [6](#0-5) 

the contract's own record of funds "still owed back from the pool" silently drops to zero (or an understated value) even though the real NEAR remains stuck at the pool. Nothing in the contract re-queries or reconciles this — subsequent calls (e.g. unselecting the staking pool once `get_known_deposited_balance()` reaches 0, as exercised in the test flow) proceed on the false assumption that all funds were recovered: [7](#0-6) 

This can permanently strand real NEAR at the malicious/misbehaving pool with no on-chain accounting trail indicating unresolved funds are owed, which is a funds-frozen (Critical/High tier) outcome consistent with the rules' scope ("an account trusted as a pool... versus the code and arguments that trust was granted for").

### Likelihood Explanation
Requires a staking pool that has been whitelisted (either directly by the Foundation or, more easily, permissionlessly through a whitelisted factory) to behave maliciously or buggy on its `withdraw` entrypoint. The report itself acknowledges this exact category of risk is accepted as a trade-off for the router case ("the factory owner has no incentive to not add routers which don't pay the fee... if they do, they can always disable/add a new one"), and the same reasoning/acceptance likely applies here for the staking-pool owner trust model, but the underlying code pattern (no before/after balance check on a promise from a whitelisted, not fully protocol-controlled, contract) is identical and reachable via normal `withdraw_from_staking_pool` / `withdraw_all_from_staking_pool` / termination flows.

### Recommendation
Add an explicit before/after check of `env::account_balance()` (or equivalent) around the `withdraw` cross-contract call in `on_staking_pool_withdraw`, `on_staking_pool_withdraw_for_termination`, and any other callback that currently relies solely on `is_promise_success()` to infer that NEAR was actually received, mirroring the recommendation given for the router-transfer case.

### Proof of Concept
Conceptual (no test harness access to execute):
1. Foundation (or a whitelisted factory) whitelists staking pool `evil.pool` that implements `withdraw(amount)` to simply return without transferring any NEAR.
2. Owner selects `evil.pool` and deposits/stakes `N` NEAR, so `deposit_amount == N`.
3. Owner calls `withdraw_from_staking_pool(N)`; `evil.pool::withdraw` executes and returns success (no panic, no transfer).
4. `on_staking_pool_withdraw(N)` observes `is_promise_success() == true` and sets `deposit_amount -= N` (becomes 0), per [8](#0-7) , while `env::account_balance()` of the lockup account is unchanged.
5. `get_known_deposited_balance()` and `get_owners_balance()` now report the funds as fully recovered even though `N` NEAR is permanently stuck in `evil.pool`, and `unselect_staking_pool()` becomes callable, severing the lockup's remaining link to the pool holding the funds.

```markdown
# Staking Pool Factory Contract

This contract deploys and automatically whitelists new staking pool contracts.
It allows any user to create a new whitelisted staking pool.

The staking pool factory contract packages the binary of the staking pool contract within its own binary.
To create a new staking pool a user should issue a function call transaction and attach the required minimum deposit.
The entire deposit will be transferred to the newly created staking pool contract in order to cover the required storage.

When a user issues a function call towards the factory to create a new staking pool the factory internally checks that
the staking pool account ID does not exists, validates arguments for the staking pool initialization and then issues a
receipt that creates the staking pool. Once the receipt executes, the factory checks the status of the execution in the
callback. If the staking pool was created successfully, the factory then whitelists the newly created staking pool.
Otherwise, the factory returns the attached deposit back the users and returns `false`.
```
