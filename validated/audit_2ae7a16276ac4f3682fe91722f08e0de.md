### Title
External Initiator job-run trigger path ignores `ExternalInitiatorsEnabled=false`, letting pre-existing initiators keep triggering runs after the feature is disabled - (File: `core/web/auth/auth.go`, `core/web/router.go`)

### Summary
The `ExternalInitiatorsEnabled` config flag is checked only in `ExternalInitiatorsController.Create` [1](#0-0)  when a *new* external initiator credential is minted. However, the authentication middleware that actually uses an external initiator's access key/secret to authorize job-run triggering, `AuthenticateExternalInitiator`, performs no equivalent check [2](#0-1) , and it is wired into the `/v2/jobs/:ID/runs` route alongside token/session auth in the router [3](#0-2) .

### Finding Description
This is structurally identical to the MagicSea bug class: a global "shut this feature off" control (`emergencyUnlock` there, `ExternalInitiatorsEnabled=false` here) is expected to block an entire category of state-mutating actions, but one already-existing credential/position (`addToPosition` there, an already-provisioned `ExternalInitiator` row here) retains an unrestricted path to keep acting.

- Creation is gated: `eic.App.GetConfig().JobPipeline().ExternalInitiatorsEnabled()` is checked and a `405` is returned if disabled [1](#0-0) .
- But any `ExternalInitiator` row created *before* the flag was disabled continues to authenticate successfully: `AuthenticateExternalInitiator` looks up the initiator by access key, verifies the HMAC secret, and on success sets the request's role to `UserRoleRun` unconditionally — with no call to the config at all [4](#0-3) .
- The `/v2/jobs/:ID/runs` route accepts this authentication method directly: `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` guards `userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))` [3](#0-2) .
- The same unchecked pattern is repeated in every `AuthenticationProvider` implementation's `FindExternalInitiator`, none of which consult the enabled flag: local [5](#0-4) , LDAP [6](#0-5) , and OIDC [7](#0-6) .

An operator who disables `ExternalInitiatorsEnabled` (e.g., in response to an incident, to lock down the external-trigger attack surface, or as part of a security hardening step) reasonably expects that *no* external initiator can trigger job runs anymore. Instead, only the *creation* of new external initiators is blocked — every initiator provisioned beforehand retains full, unrestricted ability to authenticate and invoke `POST /v2/jobs/:ID/runs` with `run` role privileges, exactly analogous to how `addToPosition()` kept working for pre-existing staking positions while `createPosition`/`renewLock`/`extendLock` were disabled during `emergencyUnlock`.

### Impact Explanation
Disabling `ExternalInitiatorsEnabled` is a security/operational control meant to close off the external-initiator attack surface. If an operator flips this flag intending to immediately revoke all external-initiator-triggered job execution capability (for example, after suspecting a leaked EI credential, or as a blanket lockdown), the control silently fails for any credential issued prior to the change: those credentials can still authenticate as `UserRoleRun` and trigger arbitrary job runs via `/v2/jobs/:ID/runs`. This is a false sense of security / access-control bypass: the operator believes the external-trigger surface is closed, but it remains open for all previously-issued initiators, which could result in unauthorized/unexpected job execution (including fund-moving jobs, depending on job configuration).

### Likelihood Explanation
Requires that (a) at least one `ExternalInitiator` credential already exists in the `external_initiators` table (a normal, expected operational state for nodes using this integration), and (b) an operator disables `ExternalInitiatorsEnabled` expecting it to fully revoke external-initiator capability. This is a plausible and realistic incident-response scenario, and the gap is only visible by reading both the controller and the auth-middleware code paths together — an operator has no direct way to observe from the config alone that pre-existing initiators remain active. No source-code changes or malicious insider access are needed; it is triggered purely by normal admin action (toggling the config) plus a benign or malicious holder of a previously-issued EI credential.

### Recommendation
Enforce the `ExternalInitiatorsEnabled` check inside `AuthenticateExternalInitiator` (or in the `/v2/jobs/:ID/runs` route handler) so that when the feature is disabled, authentication via external initiator credentials is rejected regardless of when the credential was created — mirroring the Sherlock recommendation to apply the same restrictive check uniformly to every code path that can perform the restricted action, not just the "create new" path.

### Proof of Concept
1. Ensure `JobPipeline.ExternalInitiatorsEnabled = true` and create an external initiator via `POST /v2/external_initiators` (as an `edit`+ role user), storing the returned `AccessKey`/`Secret`.
2. Operator disables the feature: set `JobPipeline.ExternalInitiatorsEnabled = false` and restart/reconfigure the node. Attempts to `POST /v2/external_initiators` now correctly fail with `405 Method Not Allowed` [8](#0-7) .
3. Using the credential obtained in step 1, send `POST /v2/jobs/:ID/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the previously issued values (as exercised in `TestTokenAuthRequired_TokenCredentials`-style requests [9](#0-8) ).
4. `AuthenticateExternalInitiator` succeeds (no config check present) [4](#0-3) , sets `UserRoleRun`, and the job run is created — despite the operator having disabled external initiators entirely.

// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
