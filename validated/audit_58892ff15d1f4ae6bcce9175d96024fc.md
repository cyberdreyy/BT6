### Title
Stale `lastWithdrawRequest` cursor lets old loss-adjusted withdraw receipts claim at par, draining funded claims of other users - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug (CVE-2023-53354) is a stale-snapshot bug: `skb_segment` cached `nrfrags`/`frag`, then called `skb_orphan_frags()`, which could change the frag list, and the loop kept iterating over the stale cursor — a NULL deref panic. The credit-vault analog is in `IdleCreditVault.claimWithdrawRequest`: `_claimLossAdjustedWithdrawRequest` locates the loss-adjusted epoch through a single-slot cursor, `lastWithdrawRequest[_user]` (line 790), while receipt data is actually stored per-epoch in `withdrawsRequestsByEpoch[_user][epoch]` and `lossRecoveryPriceByEpoch[epoch]`. If a user holds a loss-adjusted receipt from an earlier epoch and then makes any later withdraw request, the cursor points at the latest epoch, the earlier loss-adjusted receipt is never haircutted, and it falls through to `_claimFundedWithdrawRequest`, which pays the full basis at par — even though `collectWithdrawFunds` only funded that epoch at `lossRecoveryPrice < RECOVERY_FULL`.

### Finding Description
Ordering of the claim path in `claimWithdrawRequest` (lines 301–314): defaulted claims are cleared first, then `_claimLossAdjustedWithdrawRequest`, then `_claimFundedWithdrawRequest`. The loss-adjusted step reads the haircut epoch from the mutable marker `lastWithdrawRequest[_user]`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

But `collectWithdrawFunds` (lines 411–430) can set `lossRecoveryPriceByEpoch[epochNumber]` for *any* epoch in which `stopEpochWithDuration(_lossAmount)` underfunded `pendingWithdraws`, and `requestWithdraw` (line 282) overwrites `lastWithdrawRequest[_user] = currentEpoch` on every new request. The per-epoch claim basis (`withdrawsRequestsByEpoch`) survives in the aggregate `withdrawsRequests[_user]` — `_claimLossAdjustedWithdrawRequest` only calls `_clearWithdrawClaimForEpoch` for the cursor epoch, so an earlier loss-epoch receipt is left in `withdrawsRequests`. `_claimFundedWithdrawRequest` then computes `normalAmount = withdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)` at full value, burning the full receipt balance. The "pointer" to the loss epoch is stale relative to the per-epoch data — exactly the stale-`nrfrags` pattern.

Reproducible sequence (all attacker-allowed, honest manager):

1. Epoch N (running/stopped): user calls `cdoEpoch.requestWithdraw(amount, tranche)` → receipt minted 1:1, `lastWithdrawRequest[user] = N`, `withdrawsRequestsByEpoch[user][N] = amount`.
2. Manager calls `stopEpochWithDuration`/`stopEpoch` with a partial loss so `collectWithdrawFunds(amount < pendingBasis)` sets `pendingWithdraws = 0` and `lossRecoveryPriceByEpoch[N] < 1e18`. The strategy receives only `funded < basis` underlying.
3. In a later epoch M > N, user calls `requestWithdraw` again (even a small amount) → `lastWithdrawRequest[user] = M`. Epoch M is fully funded (`lossRecoveryPriceByEpoch[M] == 0`).
4. After epoch M ends, user calls `claimWithdrawRequest` via the CDO: `_claimLossAdjustedWithdrawRequest` sees `lossRecoveryPriceByEpoch[M] == 0` and returns 0; `_claimFundedWithdrawRequest` pays `withdrawsRequests[user]` = epoch-N basis (full) + epoch-M amount at par, even though epoch N was funded at a haircut.

### Impact Explanation
Direct insolvency/theft of funded claims. The strategy's underlying balance after the loss-adjusted `collectWithdrawFunds` contains only `basis * lossRecoveryPrice / RECOVERY_FULL` for epoch N, plus fully-funded later receipts. Paying the epoch-N receipt at par transfers `(basis − funded)` extra underlying to the attacker, which is subtracted from the common funded bucket backing all other pending and instant withdraw claims (`_transferFundedClaim` draws on the strategy's plain underlying balance). The last claimant(s) are left undercollateralized — temporary freezing up to permanent loss of their unclaimed yield/principal, quantified at `basis * (RECOVERY_FULL − lossRecoveryPrice) / RECOVERY_FULL` per inflated receipt. An attacker can fully exploit this alone: be the epoch-N requester, re-request in epoch M, claim at par, while other users' funded receipts absorb the shortfall.

### Likelihood Explanation
Requires `stopEpochWithDuration`/loss-adjusted funding (`_amount < pendingBasis`) to occur while `defaultRecoveryInitialized` is set (i.e., any post-upgrade deployment), and a user holding a receipt in that epoch who later re-requests. Both actions are unprivileged: `requestWithdraw` is callable by any tranche holder; the loss path is exercised by the honest manager at epoch end. No existing guard stops it — the revert check `epochNumber <= lastWithdrawRequest` only gates timing, `_settleApr0` doesn't touch normal receipts, and nothing cross-checks `withdrawsRequestsByEpoch` against `lossRecoveryPriceByEpoch` on the funded path. Uncertainty: whether an attacker benefits when they are the *only* claimant is limited (strategy would just pay what's there — actually `safeTransfer` of more than balance reverts); the theft materializes when other funded claims exist in the same strategy balance, which is the normal case.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate or track all epochs with pending claims rather than relying on `lastWithdrawRequest` as the sole cursor — e.g., check `lossRecoveryPriceByEpoch` for every epoch present in `withdrawsRequestsByEpoch[_user]`, or store a per-user set/first-loss-epoch pointer. Alternatively, in `_claimFundedWithdrawRequest`, subtract any `withdrawsRequestsByEpoch[_user][e]` where `lossRecoveryPriceByEpoch[e] != 0` from the par claim before paying. Also consider storing per-epoch request epochs in an enumerable structure so claims cannot strand haircutted receipts in the aggregate `withdrawsRequests` bucket.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// 1. deposit, start epoch 0, stop epoch 0 (normal)
idleCDO.depositAA(AMOUNT);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, apr, expected);

// 2. user requests withdraw in buffer of epoch 1 request window
uint256 req1 = cdoEpoch.requestWithdraw(bal/2, address(AAtranche)); // lastWithdrawRequest = epochN

// 3. start epoch; at stop, manager calls stopEpochWithDuration/_lossAmount>0
//    so collectWithdrawFunds funds < pendingWithdraws:
//    lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL; pendingWithdraws = 0
//    strategy received only req1 * p / RECOVERY_FULL for epoch N

// 4. next epoch window: user requests again (small amount)
uint256 req2 = cdoEpoch.requestWithdraw(bal/10, address(AAtranche)); // lastWithdrawRequest = M
//    epoch M funded in full

// 5. after epoch M stop:
cdoEpoch.claimWithdrawRequest();
// expected (correct): received == req1 * p / RECOVERY_FULL + req2
// actual (buggy):     received == req1 + req2  -> overpaid by req1 * (1 - p)
// assert strategy underlying balance < sum of remaining funded claims -> insolvency
```

The assertion to check: `underlying.balanceOf(strategy)` after the claim is less than the sum of remaining funded receipts (`instantWithdrawsRequests` + other users' `withdrawsRequests` + `defaultRecoveryReserve` guard), proving the haircut was bypassed at the expense of other claimants.
