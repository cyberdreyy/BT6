## Title
`MultiSigContract::delete_member` fails to purge stale confirmations left on unrelated pending requests, letting a re-added member's pre-removal confirmation count toward `num_confirmations` — ([File: multisig2/src/lib.rs])

## Summary
`delete_member` only deletes requests and confirmations for requests that `member` itself originally created (`r.member == member`), never scanning `confirmations` for entries where the *string* `member.to_string()` was recorded as a confirmer on some other request `R` created by someone else. If `M` confirms `R`, is deleted, and is later re-added with the identical `public_key`/`account_id` (producing an identical `to_string()`), the stale confirmation for `R` survives untouched and still counts toward `num_confirmations` in `confirm`, even though `M` never called `confirm(R)` after rejoining.

## Finding Description
The invariant that should hold is:
`confirmations.get(&R).len() == |{ m ∈ current_members : m called confirm(R) while being a current member }|`

`delete_member` at `multisig2/src/lib.rs:356-379` only cleans up requests that `member` itself created: [1](#0-0) 
It iterates `self.requests` filtering on `r.member == member` (the request's *creator*), deletes those requests and their confirmation sets, and removes `num_requests_pk` for `member`. It does **not** iterate `self.confirmations` to strip `member.to_string()` out of confirmation sets belonging to requests `M` merely *confirmed* but did not create.

`confirm` at `multisig2/src/lib.rs:294-315` re-derives `current_member()` from the caller's key/account at call time and checks the caller hasn't already confirmed, then increments the length of the raw `HashSet<String>`: [2](#0-1) 
The threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations` counts *all* strings in the set, including stale ones inserted by a member who was later deleted, with no re-validation that every string in the set corresponds to a member who was continuously a member (or even currently a member) at insertion vs. execution time.

Exploit flow:
1. Members `A, B, M` govern the multisig with `num_confirmations = 2` (or higher).
2. `A` creates request `R` (e.g., `Transfer`). `M` calls `confirm(R)` — `confirmations[R] = {"M"}`.
3. Via a *separate* fully-confirmed request, the multisig executes `DeleteMember{member: M}` — `delete_member` removes `M` from `self.members`, deletes `num_requests_pk[M]`, and deletes only requests where `M` was the *creator*. `R` (created by `A`) is untouched; `confirmations[R]` still equals `{"M"}`.
4. Via another fully-confirmed request, `AddMember{member: M}` re-adds `M` with the identical public key/account id, so `member.to_string()` is identical to before.
5. `B` (a genuinely live, continuously-current member) calls `confirm(R)`. `confirmations[R].len()` is `1` (the stale "M") `+ 1` (`B`'s new confirmation) `= 2 >= num_confirmations`, so `execute_request(R)` runs.
6. `R` executes (e.g., a `Transfer`) even though only one member (`B`) actually confirmed it while being a current member — `M`'s confirmation predates its re-admission and was never re-cast.

Existing guards do not prevent this: `assert_valid_request` only checks the request exists, `assert_self_request`/`assert_one_action_only` are unrelated to confirmation-set integrity, and `current_member()`/the `!confirmations.contains(...)` check in `confirm` only prevent a *currently* mapped member from confirming twice — they never invalidate stale strings left by a member who was removed and later re-added.

## Impact Explanation
This lets a multisig request execute (e.g., `Transfer`, `AddKey`) with fewer genuinely live, continuously-current confirmations than `num_confirmations` requires, effectively lowering the K-of-N threshold to K-1 whenever any member is ever removed and re-added with the same key/account while an unrelated request they once confirmed is still pending. This directly moves NEAR out of the multisig account (or grants a full-access key) below the configured `num_confirmations` — matching the Critical impact category "a multisig request executed below `num_confirmations` live members." The blast radius covers every multisig deployed from `multisig2`/`multisig-factory` where membership churn (key rotation, member replacement) intersects with any pending request, and is repeatable per pending request each time the churn pattern recurs.

## Likelihood Explanation
This requires the multisig's own members to perform the `DeleteMember`/`AddMember` sequence (a normal governance action, e.g., rotating a compromised or lost key back to the same identity, or simple membership churn) while a request is pending unconfirmed by all needed parties — a plausible, non-adversarial operational sequence, not requiring any privilege beyond what members already hold via multisig governance itself. However, per the audit's threat model, the attacker is explicitly defined as *not* a multisig member and holds no member key; the exploit as described requires that a currently-existing pending request `R` was confirmed by `M` prior to `M`'s removal, and that legitimate multisig members (not the external attacker) execute the `DeleteMember`/`AddMember` sequence. There is no externally triggerable path for an unprivileged, non-member attacker to force this sequence — membership changes and confirmations are gated by `current_member()` and the multisig's own K-of-N governance.

## Recommendation
In `delete_member`, in addition to removing requests created by `member`, iterate all pending `confirmations` entries and remove `member.to_string()` from every confirmation set (not just those where `member` was the request creator). Alternatively, disallow `AddMember` from re-adding a `MultisigMember` whose `to_string()` matches any string still present in any active `confirmations` set, or store confirmations keyed by an incrementing "membership epoch"/generation counter combined with the member identity so a stale confirmation from a prior membership epoch cannot count after re-admission.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
