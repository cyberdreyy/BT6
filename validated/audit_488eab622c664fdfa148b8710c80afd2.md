### Title
KYC/credential revocation permanently blocks withdrawal requests for existing tranche holders - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The bug class is "removing support/authorization for an asset or user after deposits prevents them from withdrawing". In this codebase the analog is the `isWalletAllowed` Keyring check applied on the withdrawal *request* paths (`requestWithdraw`, `requestInstantWithdraw`, `depositDuringEpoch`) and on `IdleCDOEpochQueue.requestWithdraw` via `_checkAllowed`. If a lender's Keyring credential lapses or is revoked (e.g. credential expiry, policy change by the honest Keyring admin, or `keyring`/`keyringPolicyId` repointed by the owner), that lender can no longer call `requestWithdraw` — their tranche tokens cannot be converted into a withdrawal receipt even though they already hold a legitimate deposit.

### Finding Description
`IdleCDOEpochVariant.requestWithdraw` reverts for wallets that fail `isWalletAllowed` (confirmed by `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:288-291`, which asserts `NotAllowed` for a non-allowed buyer). `isWalletAllowed` returns `IKeyring(keyring).checkCredential(keyringPolicyId, _user)` (`IdleCDOEpochVariant.sol:984-987`), so the gate depends on mutable external state: the Keyring credential itself and the owner-set `keyring`/`keyringPolicyId` pair. `IdleCDOEpochQueue.requestWithdraw` repeats the same gate in `_checkAllowed` (`IdleCDOEpochQueue.sol:415-421`).

Unlike the Biconomy report, the *claim* paths (`claimWithdrawRequest`, `claimInstantWithdrawRequest`, and the queue's `claimWithdrawRequest`) do not re-check `isWalletAllowed`, so already-issued receipts remain payable. The impact is confined to users whose credential becomes invalid *before* they manage to submit a request.

Because the epoch variant has no direct tranche redeem path — the only exit is `requestWithdraw` → wait one epoch → `claimWithdrawRequest` — a revoked holder has no in-protocol exit. The residual workaround is that `IdleCDOTranche` tokens are transferable, so a revoked user can transfer tranches to a still-allowed address that requests the withdrawal on their behalf; but this requires a trusted counterparty and is not a protocol-guaranteed exit.

### Impact Explanation
Temporary-to-permanent freezing of user funds. A lender whose Keyring credential expires during a running epoch (requests are also blocked during the epoch by `allowAAWithdrawRequest`/`allowBBWithdrawRequest`, set false in `startEpoch` at lines 249-250) may find they cannot queue a withdrawal once the buffer period reopens. If the credential cannot be renewed (compliance rejection, policy sunset) and no trusted allowed address exists, the freeze is effectively permanent for the full tranche balance. Quantified loss: the user's entire tranche position's underlying value at `tranchePrice`.

### Likelihood Explanation
Medium-low. It requires an honest-but-unlucky credential state change (credential expiry, policy migration, or a legitimate revocation) coinciding with an open position. Keyring credentials do expire and policies are rotated in practice; the `keyring`/`keyringPolicyId` owner setters also make the gate changeable at will. No malicious privileged role is needed — the state change is honest, matching the external report's shape (a support flag is legitimately turned off, stranding users).

### Recommendation
Mirror the mitigation from the external report: allow withdrawal *requests* from wallets that already hold tranche tokens even when `isWalletAllowed` returns false, e.g. skip the KYC check in `requestWithdraw`/`requestInstantWithdraw`/`IdleCDOEpochQueue.requestWithdraw` (or check `tranche.balanceOf(msg.sender) >= amount` as the authorization). Claims are already ungated, so this preserves the exit path without expanding deposit access — KYC should gate money *in*, not money *out*.

### Proof of Concept
```solidity
// Foundry fork-style PoC sketch (setup mirrors TestIdleCDOBase / IdleCreditVaultWriteOffEscrow.t.sol)
function testRevokedKycCannotRequestWithdraw() external {
    // 1. LP passes KYC and deposits during buffer period
    _depositAA(LP, 10_000e6);              // mints AA tranche tokens to LP

    // 2. Manager starts the epoch; borrower pulls funds
    _startEpoch();

    // 3. Epoch ends, manager stops it; buffer reopens requests
    _stopCurrentEpoch();

    // 4. LP's Keyring credential is now revoked/expired:
    //    mock IKeyring.checkCredential(policyId, LP) => false
    vm.mockCall(
        keyring,
        abi.encodeWithSelector(IKeyring.checkCredential.selector, policyId, LP),
        abi.encode(false)
    );

    // 5. LP cannot exit: requestWithdraw reverts with NotAllowed
    vm.prank(LP);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.requestWithdraw(trancheAA.balanceOf(LP), address(trancheAA));

    // same for the queue path
    vm.prank(LP);
    vm.expectRevert(NotAllowed.selector);
    epochQueue.requestWithdraw(amount);
}
```

Caveat: I did not fully verify the exact `requestWithdraw` body in `IdleCDOEpochVariant` (file section between lines ~700-930 was not read), but the `NotAllowed` revert on `isWalletAllowed` is confirmed by the existing test. The severity also depends on whether `IdleCDOTranche` transfers are unrestricted; if transfers are ever restricted by the same credential check, the issue upgrades to strict permanent freezing.
