### Title
Instant-withdraw claims are paid from a shared, unmarked underlying balance, letting an unprivileged user drain other users' funded normal-withdraw reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The NamelessMC bug counted a view on every request because the "already counted" marker lived client-side (a cookie) rather than server-side. `IdleCreditVault.claimInstantWithdrawRequest` has the same structural flaw in the funding dimension: it burns the caller's instant-withdraw receipt tokens and pays out from the strategy's raw `underlyingToken` balance without checking that the borrower actually prefunded those receipts via `collectInstantWithdrawFunds`. Funded normal withdraws collected by `collectWithdrawFunds` sit in the same unsegregated balance, so an instant receipt is "counted" against money earmarked for other claimants.

### Finding Description
`requestInstantWithdraw` mints receipt tokens and increments `instantWithdrawsRequests`/`pendingInstantWithdraws` ([IdleCreditVault.sol:356-375](contracts/strategies/idle/IdleCreditVault.sol)). `claimInstantWithdrawRequest` then simply burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim` ([IdleCreditVault.sol:380-393](contracts/strategies/idle/IdleCreditVault.sol)). `pendingInstantWithdraws` is only decremented in `collectInstantWithdrawFunds` ([IdleCreditVault.sol:398-403](contracts/strategies/idle/IdleCreditVault.sol)) — the claim path never reads it. `_transferFundedClaim` only excludes `defaultRecoveryReserve` ([IdleCreditVault.sol:897-907](contracts/strategies/idle/IdleCreditVault.sol)); there is no marker distinguishing "underlying reserved for funded pending withdraws" from "underlying available for instant claims".

Attack sequence in a running epoch with `allowInstantWithdraw` enabled:

1. Epoch N stops; the borrower funds pending withdraws. `collectWithdrawFunds` transfers the underlying into the strategy and clears `pendingWithdraws` ([IdleCreditVault.sol:411-430](contracts/strategies/idle/IdleCreditVault.sol)). Victim users hold funded receipts but have not yet called `claimWithdrawRequest` — late claims are explicitly supported ([IdleCreditVault.sol:319-328](contracts/strategies/idle/IdleCreditVault.sol)).
2. Epoch N+1 runs with instant withdrawals enabled (`allowInstantWithdraw` / delay per `IdleCDOEpochVariant.claimInstantWithdrawRequest`, which checks only the flag, not funding — [IdleCDOEpochVariant.sol:975-979](contracts/IdleCDOEpochVariant.sol)).
3. Attacker calls `requestInstantWithdraw` mid-epoch, after the start-epoch prefund for that epoch's instant queue was already collected — so no new borrower funding is owed for this receipt.
4. Attacker immediately calls `claimInstantWithdrawRequest`. `_burn` succeeds on the just-minted receipts, and `_transferFundedClaim` pays the full `amount` out of the strategy balance — which is the victims' funded normal-withdraw reserve.

The broken invariant is one-receipt-one-payout / reserve isolation: a receipt whose funding was never collected is paid at par from another bucket's reserves.

### Impact Explanation
The attacker receives underlying equal to the instant-withdraw amount with zero funded backing. When victims later call `claimWithdrawRequest`, `_claimFundedWithdrawRequest` → `_transferFundedClaim` either reverts on insufficient balance or pays out only partially — direct theft of already-funded, unclaimed withdrawals, quantified as `min(strategyBalance - defaultRecoveryReserve, instantWithdrawAmount)`.

### Likelihood Explanation
Requires: instant withdrawals enabled (`allowInstantWithdraw`), a running epoch past the instant-withdraw delay, and residual strategy balance from funded-but-unclaimed pending withdraws — a routine state since claims are permissionlessly delayed. The attacker is any KYC-passing tranche holder. The existing guards do not stop it: `_onlyIdleCDO` is satisfied through the CDO's public `claimInstantWithdrawRequest`, and `_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve`.

Caveat I could not fully verify within the available context: whether `IdleCDOEpochVariant` internally sequences instant-claim payouts against a per-epoch funded amount tracked on the CDO side. The strategy itself enforces no such check, and the CDO claim path only gates on `allowInstantWithdraw`, so the strategy-level hole stands unless an uninspected CDO guard blocks the call ordering.

### Recommendation
Track funded instant withdrawals separately (e.g., an `availableInstantWithdraws` counter incremented only in `collectInstantWithdrawFunds` and decremented in `claimInstantWithdrawRequest`), and revert in `claimInstantWithdrawRequest` when `instantWithdrawsRequests[_user]` exceeds the funded remainder — mirroring how `pendingWithdraws`/`collectWithdrawFunds` gate normal claims.

```solidity
    // 1. victim requests normal withdraw; epoch stops; borrower funds
    //    -> collectWithdrawFunds moves underlying into strategy, pendingWithdraws = 0
    // 2. next epoch starts; attacker deposits, gets tranche tokens
    // 3. attacker: cdoEpoch.requestInstantWithdraw(attackerTranches)
    // 4. attacker: cdoEpoch.claimInstantWithdrawRequest()   // no prefund for this receipt

    // assert strategy.underlyingBalance < victim funded claim basis
    // 5. victim: cdoEpoch.claimWithdrawRequest() -> revert/shortfall
}
```

The key assertions are that step 4 succeeds despite `pendingInstantWithdraws` never having been funded for that receipt, and that the strategy's post-claim underlying balance is below the victims' `withdrawsRequests` claim basis.
