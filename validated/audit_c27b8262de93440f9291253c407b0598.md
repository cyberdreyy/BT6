This confirms the vulnerability pattern. Note that sibling handlers `confidentialrelay/handler.go` (`newActiveRequest`, lines 368-383) and `vault/handler.go` explicitly reject a request when `req.ID` already exists in their active-request maps — but `capabilities/handler.go`'s `HandleLegacyUserMessage` performs no such check before unconditionally overwriting `h.savedCallbacks[msg.Body.MessageId]`, confirming this is an inconsistency/gap relative to the rest of the codebase rather than intentional design.

### Title
Unconditional overwrite of `savedCallbacks[MessageId]` allows cross-user callback hijacking/DoS - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` stores the caller's callback keyed only by the client-supplied `msg.Body.MessageId`, with no check for a pre-existing in-flight entry, unlike sibling handlers (`confidentialrelay`, `vault`) that explicitly reject duplicate IDs. Because `MessageId` is attacker-chosen and not scoped per-sender, any unauthenticated gateway client that submits a `MethodWebAPITrigger` request with a `MessageId` colliding with another user's in-flight request silently overwrites that user's saved callback, causing the original request's node response to be delivered to the attacker instead of the legitimate caller, and dropping the legitimate caller's response entirely.

### Finding Description
`HandleLegacyUserMessage` at [1](#0-0)  does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
```
This unconditionally overwrites any existing map entry for the same `MessageId` without checking `found` first. `MessageId` originates from the JSON-RPC request `ID` field, which is fully attacker-controlled (set from `jsonRequest.ID` and copied onto `msg.Body.MessageId` in `ValidatedMessageFromReq`/gateway `ProcessRequest`), and `Message.Validate()` at [2](#0-1)  only checks length/format, never uniqueness against other senders. The gateway entrypoint at [3](#0-2)  calls `h.HandleLegacyUserMessage(ctx, msg, callback)` for any valid signed request, without any per-node/per-user request ID namespace.

When a second (attacker) request arrives with the same `MessageId` as a still-pending legitimate request, the entry in `h.savedCallbacks` is replaced with the attacker's `callback`. Later, when a DON node responds via `HandleNodeMessage` → `handleWebAPITriggerMessage` ( [4](#0-3) ), the lookup is done purely by `msg.Body.MessageId`:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
```
There is no check that the node's response corresponds to the same sender/request that originally created the entry, so the legitimate victim's node response gets delivered to the attacker's `callback`, and the victim's original callback is dropped (never invoked, eventually the victim's HTTP request times out at the gateway layer, `RequestTimeoutError`).

This contrasts with the `confidentialrelay` handler's `newActiveRequest` ( [5](#0-4) ), which explicitly checks `if h.activeRequests[req.ID] != nil { return nil, errors.New("request ID already exists...") }` before storing — the capabilities handler lacks this guard entirely.

### Impact Explanation
This is a cross-user response confusion / unauthorized data disclosure and denial-of-service vector: an attacker can (a) cause another legitimate user's web-API-trigger response to be delivered to the attacker's own connection instead of the rightful caller, and (b) cause the legitimate caller's request to silently hang/time out. Depending on payload content this may expose data intended only for the original requester through the gateway response channel.

### Likelihood Explanation
Exploitability requires only unauthenticated/unprivileged access to the gateway HTTP endpoint (any signed message from any address is accepted; there's no allowlist enforced at this stage — see the `TODO: apply allowlist and rate-limiting here` comment at [6](#0-5) ) plus knowledge of a live/in-flight `MessageId` belonging to another user. Since `MessageId` is a client-chosen string (often predictable, sequential, or externally observable, e.g. embedded in workflow trigger identifiers or logs) rather than a server-issued secret nonce, guessing/observing collisions is plausible, and the race window is the full request round-trip to DON nodes (up to `MaxAllowedMessageAgeSec`/callback TTL). It is trivially repeatable — no rate limit or uniqueness check blocks it.

### Recommendation
In `HandleLegacyUserMessage`, before storing, check if `msg.Body.MessageId` already exists in `h.savedCallbacks` (mirroring `confidentialrelay.newActiveRequest`'s pattern) and reject the request with an error response (e.g., a new error code like "request ID already exists") instead of silently overwriting. Additionally consider keying `savedCallbacks` by a tuple of `(Sender, MessageId)` or validating that the DON node response's `MessageId` is bound to the same sender that originally issued it, to close any residual cross-user confusion even under legitimate re-submissions.

### Proof of Concept
Add a test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two signed `triggerRequest` messages, `msgA` (signer keyA) and `msgB` (signer keyB), both using the same `msg.Body.MessageId` (e.g., `"12345"`), each with distinct payload/topics to make responses distinguishable.
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` — assert it succeeds and `handler.savedCallbacks["12345"]` is `cbA`'s wrapper.
3. Before resolving A, call `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` — assert `handler.savedCallbacks["12345"]` is now `cbB`'s wrapper (overwritten), i.e., `cbA`'s entry is gone.
4. Simulate the DON node responding to the original request A (e.g., call `handler.HandleNodeMessage(ctx, respForMsgA, nodeAddr)`).
5. Assert that `cbB.Wait(ctx)` returns the response intended for A's request (cross-user leak), and that `cbA.Wait(ctx)` times out / never resolves (dropped callback) — proving both the confusion and the DoS.
