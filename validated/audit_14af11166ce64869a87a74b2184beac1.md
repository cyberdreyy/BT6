### Title
Post-reap PID/PGID reuse race in `killer_unix.go` `Terminate`/`ForceKill` can signal an unrelated process group - ([File: helpers/process/job_unix.go], [File: helpers/process/killer_unix.go], [File: helpers/process/killer.go])

### Summary
`unixKiller.Terminate`/`ForceKill` sign raw `syscall.Kill(-pid, sig)` using a PID captured from `Commander.Process()`, with no check that the process is still alive or still owned by the same job before signaling. Combined with a `select` race in the callers (`executors/shell/shell.go`, `executors/custom/command/command.go`) that can invoke `KillAndWait` even after the job's own `Wait()` has already reaped the process, this creates a TOCTOU window where the negated-PID (process-group) signal can hit a different, unrelated process group if the kernel has already reused that PID.

### Finding Description
`osCmd.Start()` sets `Setpgid: true` [1](#0-0)  so the job's process becomes its own process-group leader (`pgid == pid`). `unixKiller.getPID()` returns `-pid`, i.e. the process-group id, used for both `SIGTERM` and `SIGKILL` [2](#0-1) . This is a raw `syscall.Kill` call, not `os.Process.Signal()`, so it does not benefit from any pidfd-based protections Go's standard library may use elsewhere — it purely trusts the numeric PID snapshot.

Callers such as `executors/shell/shell.go` run:
```go
select {
case err = <-waitCh:
    return err
case <-cmd.Context.Done():
    ... KillAndWait(c, waitCh)
}
``` [3](#0-2) 
and `executors/custom/command/command.go` has the identical pattern [4](#0-3) . `waitCh` is written to by a goroutine as soon as `c.Wait()` returns [5](#0-4) . Go's `select` picks pseudo-randomly among cases that are ready simultaneously; if the job's own context is already cancelled (e.g. the job was cancelled/timed out right as the script naturally finished), it is possible for `ctx.Done()` to be chosen even though `waitCh` already has a value, meaning the process has already been reaped by `cmd.Wait()` (Go's `exec.Cmd.Wait()` calls `wait4`, freeing the PID for kernel reuse). `KillAndWait` then calls `Terminate()`/`ForceKill()` on `command.Process().Pid`, a stale, already-reaped PID [6](#0-5) . Neither `killer_unix.go` nor `killer.go` re-validates that the PID/PGID still belongs to the originating job (no `/proc/[pid]` identity check, no pidfd, no liveness probe) before issuing the group-wide signal.

### Impact Explanation
If, under high PID churn, the kernel reassigns the freed PID (and, since the new process also self-elects as its own group leader via the same `setpgid` pattern, the same PGID) to an unrelated process — e.g., another concurrent job's shell/build process on the same shared-runner host — then the stale `SIGTERM`/`SIGKILL` from the first job's late-arriving cancellation will terminate that unrelated job's process group instead. This is a cross-job/cross-project denial-of-service on shared hosts (shell executor, or any executor where host-level processes are spawned via `NewOSCmd`), violating the invariant that a job must not affect another project's workload.

### Likelihood Explanation
The bug is real but requires two independent low-probability conditions to align: (1) the caller's `select` must choose the `ctx.Done()` branch despite `waitCh` already being ready — a narrow race window that occurs only when cancellation and natural process exit happen essentially simultaneously; and (2) the OS must reuse the exact freed PID (and matching PGID) for an unrelated process within the brief interval between reaping and the `syscall.Kill` call. On typical hosts with a large `pid_max` this is rare, but it becomes materially more likely under sustained high job concurrency/short-lived jobs and constrained PID ranges (e.g., containerized runner hosts with small PID namespaces), which an attacker with the ability to submit many rapid, short pipelines to a shared runner could partially induce.

### Recommendation
- Avoid signaling by bare PID after `Wait()` may have already reaped the process: have the `Wait()` goroutine set an atomic "exited" flag (or close a dedicated channel) *before* pushing to `waitCh`, and have `KillAndWait`/`Terminate`/`ForceKill` check this flag first and no-op if already set.
- Where available (Linux), use `pidfd_open`/`pidfd_send_signal` (or Go's newer os/exec pidfd-aware `Process` primitives) to bind the kill target to the specific process instance rather than a raw numeric PID, eliminating PID-reuse TOCTOU entirely.
- As a cheaper mitigation, before sending the group signal, verify process identity (e.g., compare `/proc/<pid>/stat` start-time or command line captured at `Start()` time) and skip the signal if it no longer matches.

### Proof of Concept
Go integration test in `helpers/process`:
1. Start a `Commander` running a very-short-lived binary (`sleep 0` equivalent) via `NewOSCmd`.
2. Immediately after `Start()`, spawn a goroutine that calls `Wait()` and signals a channel the moment it returns (simulating the process being reaped).
3. Concurrently, in a tight loop, fork many short-lived "victim" processes with `Setpgid: true` to induce PID churn around the freed PID (may require lowering `/proc/sys/kernel/pid_max` in a container to make reuse likely, or mocking the reuse deterministically by injecting a fake `Process()` result after `Wait()` completes).
4. Call `KillAndWait` on the original `Commander` deliberately after step 2's wait channel fires (simulating the `select` race picking the cancellation branch late), and assert via `/proc/<victim_pid>/stat` (or exit codes) that no victim process outside the original job's tracked group was killed.
5. Fuzz/stress variant: run many concurrent (job, cancel) pairs with randomized timing offsets around zero to maximize the chance of the `select` race, and assert (over many iterations) that `syscall.Kill` targets always correspond to PIDs owned by their originating `Commander` instance (e.g., by comparing process start-time recorded at `Start()` vs. at kill-time).

func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}

// getPID will return the negative PID (-PID) which is the process group. The
// negative symbol comes from kill(2) https://linux.die.net/man/2/kill `If pid
// is less than -1, then sig is sent to every process in the process group whose
// ID is -pid.`
func (pk *unixKiller) getPID() int {
	return pk.cmd.Process().Pid * -1
}

func (kw *osKillWait) KillAndWait(command Commander, waitCh chan error) error {
	process := command.Process()
	if process == nil {
		return ErrProcessNotStarted
	}

	log := kw.logger.WithFields(logrus.Fields{
		"PID": process.Pid,
	})

	processKiller := newProcessKiller(log, command)
	processKiller.Terminate()

	select {
	case err := <-waitCh:
		return err
	case <-time.After(kw.gracefulKillTimeout):
		processKiller.ForceKill()

		select {
		case err := <-waitCh:
			return err
		case <-time.After(kw.forceKillTimeout):
			return &KillProcessError{pid: process.Pid}
		}
	}
```
