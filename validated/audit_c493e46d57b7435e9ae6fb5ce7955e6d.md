### Title
Removed LDAP/OIDC users retain valid access via cached sessions and API tokens until the next background sync — analogous to a de-authorized validator retaining voting power ([File: core/sessions/ldapauth/sync.go])

### Summary
The external report describes a bug class where a trusted party (a validator) that is removed from its role of trust can still exercise the privileges of that role because the system relies on a stale/cached snapshot of authorization instead of re-validating trust at the time of use. The Chainlink LDAP/OIDC authentication backends exhibit the same bug class: a user's session and API-token role are cached locally in `ldap_sessions`/`ldap_user_api_tokens` (and OIDC equivalents), and these caches are only reconciled with the upstream identity provider (where the actual removal/demotion happens) on a configurable interval or rate limit — not on every authenticated request.

### Finding Description
`ldapauth` (and `oidcauth`) caches the authenticated user's email and role locally after a successful login/API-token creation. Requests are authorized against this local cache via `AuthorizedUserWithSession`/`FindUserByAPIToken`, which only checks local expiry, not current upstream state: [1](#0-0) 

The only mechanism that reconciles local sessions/API tokens with the upstream source of truth (removing purged users or updating roles) is `LDAPServerStateSyncer.Work`, which runs on a background timer gated by `UpstreamSyncInterval` and further throttled by `UpstreamSyncRateLimit`: [2](#0-1) 

If `UpstreamSyncInterval` is non-zero, sync only happens periodically in the background rather than per-request: [3](#0-2) 

This means that once an admin de-provisions or demotes a user in the upstream LDAP/OIDC directory (the equivalent of the DAO reducing a validator's balance to zero), that user's already-issued session cookie or API token continues to be treated as valid locally — with the stale (higher) role — until the next sync cycle fires and purges/updates the local `ldap_sessions`/`ldap_user_api_tokens` rows: [4](#0-3) [5](#0-4) 

This directly mirrors the report's root cause: authorization decisions are made against a back-dated/cached snapshot of trust rather than the current state, allowing a party whose trust has been revoked to continue acting with the old privileges for an arbitrary window of time (bounded only by `UpstreamSyncInterval`, which defaults to `'0s'`/disabled per documentation, meaning sync could effectively rely solely on process restarts or manual triggers via login/logout events) [6](#0-5) .

By contrast, the local (non-LDAP) auth backend `localauth` immediately purges sessions synchronously as part of `UpdateRole`/`DeleteUser`, since those are the only sources of truth there: [7](#0-6) . The LDAP/OIDC backends lack this immediacy because the actual privilege-revoking action (removing/demoting the user) happens in an external system that Chainlink does not synchronously observe.

### Impact Explanation
A misbehaving, compromised, or terminated administrative/edit-level user removed from the upstream LDAP group or OIDC role can retain admin/edit/run access to the Chainlink node's HTTP API (job creation, key management, bridge configuration, etc.) using their still-cached session cookie or API token, for as long as the configured `UpstreamSyncInterval`/`UpstreamSyncRateLimit` window permits. This is a genuine authorization-bypass window that maps to "Accept only concrete authentication or role bypass" in the rules of this scan, arising from an unprivileged-actor-reachable path (an already-issued but now-revoked session/token making authenticated node API requests).

### Likelihood Explanation
Likelihood is dependent on operator configuration: if `UpstreamSyncInterval` is left at its `0s` default (sync disabled from timer, only run once at startup per `Start`), or set to a long interval, or `UpstreamSyncRateLimit` (default `2m0s`) is set high, the staleness window can be large. This requires LDAP or OIDC auth to be enabled (not the default `local` auth), narrowing applicability, but it is a realistic configuration for enterprise deployments that this module is specifically designed for.

### Recommendation
Re-validate the user's active/role status against the upstream identity provider (or at least check a "generation"/"revoked" flag maintained by the sync process) synchronously on every authenticated request, not only against the local cache expiry — mirroring the way `localauth.UpdateRole`/`DeleteUser` synchronously purges sessions. Alternatively, ensure `Work`/sync is invoked (and its result awaited) on every session/API-token validation call rather than only on a background timer, and document/default to a short mandatory revalidation window when LDAP/OIDC auth is enabled.

### Proof of Concept
1. Enable `LDAPAuth` (or `OIDCAuth`) with `UpstreamSyncInterval` unset (default `0s`, timer disabled) or set to a large value.
2. User Alice logs in via LDAP, receiving a session cookie; `ldap_sessions` caches her `Admin` role: [8](#0-7) 
3. Administrator removes Alice from the LDAP Admin group upstream (equivalent to zeroing a validator's balance).
4. Because the background syncer (`LDAPServerStateSyncer.run`) only fires on the configured ticker interval, and no per-request upstream check is performed by `AuthorizedUserWithSession`, Alice's existing session cookie continues to authenticate her as `Admin` against the local Chainlink node API until the next sync cycle purges/updates the row.
5. Alice (or an attacker who has compromised her session/token) can continue to issue privileged API requests during this window.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}

func (l *LDAPServerStateSyncer) Work(ctx context.Context) {
	// Purge expired ldap_sessions and ldap_user_api_tokens
	recordCreationStaleThreshold := l.config.SessionTimeout().Before(time.Now())
	err := l.deleteStaleSessions(ctx, recordCreationStaleThreshold)
	if err != nil {
		l.lggr.Error("unable to expire local LDAP sessions: ", err)
	}
	recordCreationStaleThreshold = l.config.UserAPITokenDuration().Before(time.Now())
	err = l.deleteStaleAPITokens(ctx, recordCreationStaleThreshold)
	if err != nil {
		l.lggr.Error("unable to expire user API tokens: ", err)
	}

	// Optional rate limiting check to limit the amount of upstream LDAP server queries performed
	if !l.config.UpstreamSyncRateLimit().IsInstant() {
		if !time.Now().After(l.nextSyncTime) {
			return
		}

		// Enough time has elapsed to sync again, store the time for when next sync is allowed and begin sync
		l.nextSyncTime = time.Now().Add(l.config.UpstreamSyncRateLimit().Duration())
	}

	l.lggr.Info("Begin Upstream LDAP provider state sync after checking time against config UpstreamSyncInterval and UpstreamSyncRateLimit")

// UpdateRole overwrites role field of the user specified by email.
func (o *orm) UpdateRole(ctx context.Context, email, newRole string) (sessions.User, error) {
	var userToEdit sessions.User

	if newRole == "" {
		return userToEdit, pkgerrors.New("user role must be specified")
	}

	err := sqlutil.TransactDataSource(ctx, o.ds, nil, func(tx sqlutil.DataSource) error {
		// First, attempt to load specified user by email
		if err := tx.GetContext(ctx, &userToEdit, "SELECT * FROM users WHERE lower(email) = lower($1)", email); err != nil {
			return pkgerrors.New("no matching user for provided email")
		}

		// Patch validated role
		userRole, err := sessions.GetUserRole(newRole)
		if err != nil {
			return err
		}
		userToEdit.Role = userRole

		_, err = tx.ExecContext(ctx, "DELETE FROM sessions WHERE email = lower($1)", email)
		if err != nil {
			o.lggr.Errorw("Failed to purge user sessions for UpdateRole", "err", err)
			return pkgerrors.New("error updating API user")
		}

		sql := "UPDATE users SET role = $1, updated_at = now() WHERE lower(email) = lower($2) RETURNING *"
		if err := tx.GetContext(ctx, &userToEdit, sql, userToEdit.Role, email); err != nil {
			o.lggr.Errorw("Error updating API user", "err", err)
			return pkgerrors.New("error updating API user")
		}

		return nil
	})

	return userToEdit, err
}
