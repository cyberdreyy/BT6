### Title
Stale cross-epoch instant-withdraw receipts corrupt default recovery accounting and are permanently frozen after `finalizeDefaultRecovery` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` tracks pending instant withdrawals with a **global aggregate** (`pendingInstantWithdraws`) but tracks per-epoch claim basis with `instantWithdrawClaimsByEpoch[epochNumber]`. When a borrower defaults and `finalizeDefaultRecovery` runs, only the **current** epoch's instant claims join the recovery basis, while the aggregate `pendingInstantWithdraws` may still contain receipts requested in *older* epochs. Those stale receipts are (a) excluded from `defaultPendingClaimBasis`, (b) never cleared by `_claimDefaultedInstantWithdrawRequest` (which only looks at `defaultRecoveryEpoch`), and (c) then attempted to be paid at par via `_transferFundedClaim` — which reverts because paying them would consume the isolated `defaultRecoveryReserve`. The result is a permanent freeze of the stale instant receipts and a mispriced `defaultRecoveryPrice` for everyone else. This mirrors the CVE-2017-9612 use-after-free pattern: a stale/leftover allocation (`pendingInstantWithdraws` from a prior epoch) is dereferenced under the assumption it belongs to the current epoch.

### Finding Description
Relevant code paths in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestInstantWithdraw` increments both the aggregate `pendingInstantWithdraws` and the per-epoch `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366–374). `collectInstantWithdrawFunds` decrements only the aggregate (lines 398–403) when the CDO pulls funded liquidity; whatever is not funded stays in `pendingInstantWithdraws` across later epochs.
- At default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` **only for the current epoch**, gated on `pendingInstantWithdraws != 0` (lines 644–649). Receipts from epoch N that were still unfunded when `epochNumber` advanced to M are silently dropped from `totalBasis`, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688) is computed on a basis that ignores them — yet their tokens were never returned to the reserve.
- After finalization, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest` which only clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (lines 842–856). The stale epoch-N component remains in `instantWithdrawsRequests[user]` and falls through to `_transferFundedClaim` (lines 387–392).
- `_transferFundedClaim` reverts whenever `balance - defaultRecoveryReserve < amount` (lines 897–905). Since the stale receipt has no backing outside the reserve, the claim **always reverts** → the user's receipt tokens remain minted but unspendable: permanent freezing of funds.
- Symmetrically, `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` using current-epoch `instantBasis` against the *aggregate* `pendingInstant` (lines 716–723): a large stale aggregate makes `prefundedReserve = 0` even when the current-epoch instant queue was fully funded, undercounting `reserveAmount` and lowering `defaultRecoveryPrice` for all recovery claimants (freeing reserve dust that is then permanently locked in the strategy since `defaultRecoveryReserve` only moves via claims).

### Impact Explanation
- Permanent freezing of unclaimed instant-withdraw receipts carried across an epoch boundary before a default: the claim path reverts 100% of the time once `defaultRecoveryReserve != 0`, and there is no admin sweep for user receipts.
- Dilution/mispricing of the default recovery for all other claimants: `defaultRecoveryPrice` is computed against a `totalBasis` that omits still-live liabilities while `reserveAmount` omits already-held prefunded cash.
- Loss quantification: every wei left unfunded in `pendingInstantWithdraws` from a pre-default epoch is permanently locked; recovery claimants lose `stalePending / totalBasis` of the price they should have received (or receive a price inflated by missing basis while the contract becomes under-reserved).

### Likelihood Explanation
Requirements: (1) an unprivileged lender requests an instant withdraw in epoch N; (2) the CDO collects less than `pendingInstantWithdraws` at `stopEpoch`/instant processing (happens whenever available CDO liquidity < queued instant amount — the contract explicitly tolerates a remainder, per comments at lines 636–640); (3) `epochNumber` advances; (4) borrower defaults and `finalizeDefaultRecovery` is called by the honest manager. No privileged misbehavior is needed; the attacker only needs a wallet allowed to request withdrawals. The window is any epoch in which instant withdrawals are partially unfunded, which is a normal operating condition.

### Recommendation
- Track pending instant withdrawals per epoch (e.g. `pendingInstantWithdrawsByEpoch`) or fold any non-zero stale `pendingInstantWithdraws` remainder into `defaultPendingClaimBasis` and into the claim-clearing loop, not only `instantWithdrawClaimsByEpoch[epochNumber]`.
- In `_claimDefaultedInstantWithdrawRequest`, iterate/clear all epochs with nonzero `instantWithdrawsRequestsByEpoch[_user]` up to and including `defaultRecoveryEpoch` rather than only `defaultEpoch`.
- In `_defaultPrefundedInstantReserve`, bound `pendingInstant` by the current-epoch basis it is compared against (or subtract stale pending first) so prefunded cash isn't hidden by an old-epoch remainder.

### Proof of Concept
Foundry fork PoC outline (standard `IdleCDOEpochVariant` + `IdleCreditVault` with instant withdrawals enabled via `setInstantWithdrawParams`):

```solidity
// Epoch N (running):
// 1. user A deposits, epoch starts, instant withdraw enabled.
// 2. A calls requestInstantWithdraw(x, A) -> pendingInstantWithdraws = x,
//    instantWithdrawClaimsByEpoch[N] = x.
// 3. stopEpoch with low APR -> instant path triggers, but CDO liquidity covers
//    only y < x: collectInstantWithdrawFunds(y) runs, pendingInstantWithdraws = x - y > 0.
// 4. New epoch M starts (epochNumber = M). No new instant requests needed.
// 5. Borrower defaults: cdoEpoch.stopEpoch(0,0) -> defaulted() = true.
// 6. manager calls cdoEpoch.finalizeDefault(...) ->
//    finalizeDefaultRecovery sees pendingInstantWithdraws != 0, adds only
//    instantWithdrawClaimsByEpoch[M] (= 0) to basis; A's epoch-N receipt is
//    excluded from totalBasis and defaultInstantWithdrawsFinalized = true.
// 7. A calls cdoEpoch.claimInstantWithdrawRequest(A):
//    _claimDefaultedInstantWithdrawRequest clears epoch M only (0),
//    then instantWithdrawsRequests[A] = x is sent through _transferFundedClaim,
//    which reverts NotAllowed because balance - defaultRecoveryReserve < x.
// assert: claim reverts; A's receipt tokens remain minted; underlying locked.
```

Note: I verified the strategy-side logic directly; the exact sequencing of `collectInstantWithdrawFunds` inside `IdleCDOEpochVariant.getInstantWithdrawFunds`/`stopEpoch` (whether a partial collection leaves the remainder pending across the epoch boundary) is inferred from the strategy comments and the `pendingInstantWithdraws != 0` gates — a full PoC should confirm that path on a fork before submission.
