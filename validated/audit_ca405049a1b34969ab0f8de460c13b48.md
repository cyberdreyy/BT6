### Title
Unvalidated mint-account owner lets a crafted token account cause RPC to misreport `uiTokenAmount` decimals/decimals-based scaling for arbitrary token accounts - (File: `rpc/src/parsed_token_accounts.rs`, `rpc/src/rpc.rs`)

### Summary
The bug class from the external report (trusting a component-reported asset address instead of verifying it against the canonical node asset) maps directly onto how the JSON-RPC layer resolves a token account's "mint" for `jsonParsed` display formatting: the mint pubkey is taken verbatim from the token account's own data, and the account found at that pubkey is used to compute display decimals/scaling **without ever checking that the referenced account is actually owned by the same SPL-Token(-2022) program** that owns the token account being displayed.

### Finding Description
`get_token_account_mint()` simply reads the first 32 bytes of a token account's data as the "mint" pubkey, after only checking the data length/type marker: [1](#0-0) 

This pubkey is then used, unmodified, to look up whatever account currently exists there and to derive `SplTokenAdditionalDataV2` (decimals + optional interest-bearing/scaled-UI-amount extension configs) that get applied to the token amount: [2](#0-1) [3](#0-2) 

`get_mint_owner_and_additional_data()` (used both here and by `get_token_account_balance`) fetches the account at `mint` from the bank and unpacks it as a `Mint` with no check that `mint_account.owner()` equals the token account's own program id: [4](#0-3) 

By contrast, the SVM transaction-balance code performs exactly the owner check that is missing here, confirming this check is considered necessary elsewhere in the codebase: [5](#0-4) 

Because the mint field inside an SPL-Token account is fully attacker/user-controlled data (any 32 bytes), a token account can point its "mint" field at a pubkey belonging to an unrelated, differently-configured `Mint` (different `decimals`, or one carrying `InterestBearingConfig`/`ScaledUiAmountConfig` extensions), or even at an account owned by a different token program entirely, without any consistency check between the token account's own program id and the "mint" account's owner. This same trust-without-verification pattern is what the external report flagged for `component.asset()` vs `node.asset()`.

### Impact Explanation
This affects the `jsonParsed`-encoded output of `getAccountInfo`, `getProgramAccounts`, `getTokenAccountsByOwner`, `getTokenAccountsByDelegate` (all routed through `get_parsed_token_account(s)`), and the raw numeric output of `getTokenAccountBalance`. All of these are unprivileged, single-call JSON-RPC endpoints. An attacker who controls the on-chain data of a token account (which any user can construct via a malicious/compromised token-issuing program) can cause the RPC node to compute and return a materially wrong `uiAmount`/`uiAmountString` (and even wrong decimals) for that account to any third-party caller — this is a decoder misreporting bug rather than a raw-amount corruption, since the underlying `amount` (u64) field itself is unaffected, but wallets/explorers that rely on the RPC-provided `uiAmount` would display an incorrect balance for accounts that are not their own.

### Likelihood Explanation
Likelihood is high in the sense that it requires no special privilege — a single crafted account (any user can deploy or use an arbitrary token-like program to create such an account) is sufficient, and it is triggered by a single unprivileged `getAccountInfo`/`getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountBalance` call, consistent with the low-risk classification given to the analogous DeFi finding.

### Recommendation
In `get_mint_owner_and_additional_data()` (`rpc/src/rpc.rs`) and in `get_additional_mint_data()` (`rpc/src/parsed_token_accounts.rs`), verify that the fetched mint account's owner matches the expected SPL-Token program id (the same check `SvmTokenInfo::unpack_token_account` already performs in `svm/src/transaction_balances.rs`) before using its data to compute display decimals/scaling; if the owner does not match, treat the additional data as unavailable rather than trusting it.

### Proof of Concept
1. Deploy or use any program that can write account data byte-for-byte matching the SPL-Token `Account` layout (owned by `spl_token::id()`), setting the `mint` field (bytes 0..32) to the pubkey of an unrelated, real `Mint` account that has different `decimals` or carries `InterestBearingConfig`/`ScaledUiAmountConfig` extensions (e.g., a Token-2022 mint).
2. Call `getAccountInfo` (or `getTokenAccountBalance`/`getProgramAccounts`/`getTokenAccountsByOwner`) with `encoding: "jsonParsed"` against the crafted token account.
3. Observe that the RPC-reported `uiAmount`/`uiAmountString` (and potentially interest-bearing scaling) reflect the unrelated mint's configuration rather than being rejected, because `get_mint_owner_and_additional_data`/`get_additional_mint_data` never check `mint_account.owner()` against the token account's own program id, unlike the equivalent check performed in `SvmTokenInfo::unpack_token_account`.

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}

            .expect("Token account mint should be convertible to Pubkey");
        let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;
        let balance = token_amount_to_ui_amount_v3(token_account.base.amount, &data);
        Ok(new_response(&bank, balance))
    }

impl SvmTokenInfo {
    fn unpack_token_account<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,
        account: &AccountSharedData,
        index: usize,
    ) -> Option<Self> {
        let program_id = *account.owner();
        let generic_token::Account {
            mint,
            owner,
            amount,
        } = generic_token::Account::unpack(account.data(), &program_id)?;

        let mint_account = account_loader.load_account(&mint)?;
        if *mint_account.owner() != program_id {
            return None;
        }

        let generic_token::Mint { decimals, .. } =
            generic_token::Mint::unpack(mint_account.data(), &program_id)?;

        Some(Self {
            account_index: index.try_into().ok()?,
            mint,
            amount,
            owner,
            program_id,
            decimals,
        })
    }
