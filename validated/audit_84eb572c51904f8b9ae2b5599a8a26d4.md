### Title
APR0 withdraw request bricks `stopEpoch` once APR is raised, permanently freezing the requester's principal and unclaimed yield — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the `StakedCSX.stake()` reward-loss bug (a routine user action silently destroys pending accrued yield), in `IdleCreditVault` an unprivileged KYC-passed lender's ordinary `requestWithdraw` during an APR-0 phase opens an `apr0Users` bucket that cannot be closed once the honest manager restores a nonzero APR. `prepareStopEpochWithApr0` reverts `NotAllowed` whenever `apr0TotalPrincipal != 0 && unscaledApr != 0`, so `stopEpoch` can no longer execute, `epochNumber` never advances, `_settleApr0` can never run, and the requester's principal plus its pending APR0 interest are frozen — mirroring "unclaimed rewards lost on each call to stake()".

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:739`), any allowed wallet can request a withdrawal during the buffer phase. When `unscaledApr == 0`, `IdleCreditVault.requestWithdraw` routes to `_requestWithdrawApr0` (`contracts/strategies/idle/IdleCreditVault.sol:285-286, 567-577`), which sets `apr0Users[user].principal`/`principalEpoch` and increments the global `apr0TotalPrincipal`.

At epoch end the CDO calls `prepareStopEpochWithApr0` (`contracts/strategies/idle/IdleCreditVault.sol:490-508`):

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) { return ...; }
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

The revert propagates into `stopEpoch`, so the epoch cannot be closed with a nonzero APR while any open APR0 bucket exists. Crucially, there is no escape hatch on the user side:

- The requester cannot cancel or convert the APR0 request; a second `requestWithdraw` with `unscaledApr != 0` takes the `else` branch (`IdleCreditVault.sol:287-293`) and leaves `apr0Users[user].principal` untouched — `_settleApr0` is only invoked inside `_requestWithdrawApr0` and `_claimFundedWithdrawRequest`.
- `_claimFundedWithdrawRequest` calls `_settleApr0`, which refuses to settle until `epochNumber > principalEpoch` (`IdleCreditVault.sol:551-555`). `epochNumber` only increments inside `deposit` during `stopEpoch` (`IdleCreditVault.sol:607-611`) — which is exactly the call that reverts.
- The only other clearing path is `_clearWithdrawClaimForEpoch` with `_isClearingApr0 = true`, reachable only through a defaulted/finalized epoch (`IdleCreditVault.sol:822-831`) — i.e., escape requires forcing the pool into default.

The guard is asymmetric in the wrong direction: it protects accounting consistency but places the cost on the user and the pool rather than settling the APR0 bucket at the transition, the same class of defect as `_updateRewardRate` resetting accrued rewards instead of crediting them.

### Impact Explanation
- **Permanent freezing of user funds and unclaimed yield**: the APR0 requester's principal and its not-yet-settled `apr0RateByEpoch` interest are unreachable until a default finalization forcibly clears the bucket at `defaultRecoveryPrice` (a haircut), so the user's expected full payout is permanently impaired.
- **Pool-level DoS with fund impact**: while `apr0TotalPrincipal > 0` and APR is nonzero, `stopEpoch` always reverts — the running epoch can never close, `epochEndDate` passes, borrower repayment cannot be booked, and all lender principal/interest is frozen. Resolution requires pushing the pool into borrower default (`_handleBorrowerDefault`), socializing the "loss" onto all tranche holders even though the borrower may be fully solvent.
- Quantified loss: the full `apr0Users[user].principal` plus its pro-rata APR0 interest, and potentially the entire `pendingWithdraws`/TVL if the pool is forced through the default path to unbrick.

### Likelihood Explanation
Requires only: (1) a phase where the manager sets `unscaledApr == 0` (a normal operating mode, e.g., programmable-borrower or paused-interest epochs), (2) an unprivileged KYC-passed lender calling `requestWithdraw` during the buffer — a normal user action, not an attack; the "attacker" is just an ordinary user, and (3) the honest manager later restoring a positive APR and calling `stopEpoch`, also normal behavior. No privileged-role collusion, no oracle manipulation, no reentrancy. The failure is deterministic once the state combination is reached.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert when APR changed. Instead, settle outstanding APR0 principal for the current epoch (e.g., compute the final `apr0RateByEpoch` against the interest realized up to the APR change, or settle at zero rate if no interest accrued), then close the bucket (`apr0TotalPrincipal = 0`) so `stopEpoch` proceeds. Equivalently, allow `requestWithdraw`/claims to force-settle a user's open APR0 bucket when `unscaledApr` has become nonzero, so a stale bucket can never block epoch finalization.

### Proof of Concept
Foundry fork PoC sketch (modeled on `test/foundry/IdleCreditVault.t.sol:testApr0WithdrawGetsInterestAtStopEpoch`):

```solidity
// 1. Setup: deposit AA, start epoch 0, stop epoch 0 with apr 0
idleCDO.depositAA(amount);
_startEpochAndCheckPrices(0);
vm.warp(cdoEpoch.epochEndDate() + 1);
deal(underlying, borrower, expectedInterest);
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);            // sets unscaledApr = 0 via setAprs

// 2. Unprivileged lender requests withdraw during buffer -> APR0 bucket opens
uint256 principal = cdoEpoch.requestWithdraw(bal / 2, address(AAtranche));
assertGt(IdleCreditVault(strategy).apr0TotalPrincipal(), 0);

// 3. Honest manager restores positive APR and tries to stop the next epoch
_startEpochAndCheckPrices(1);
vm.prank(manager);
IdleCreditVault(strategy).setAprs(aprX, 0);   // unscaledApr != 0
vm.warp(cdoEpoch.epochEndDate() + 1);
deal(underlying, borrower, type(uint256).max);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);          // prepareStopEpochWithApr0 reverts
cdoEpoch.stopEpoch(0, interest);

// 4. User cannot self-rescue: claim reverts (epochNumber not bumped),
//    new requestWithdraw goes to normal branch and leaves apr0 principal set
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimWithdrawRequest();
```

Caveat: I could not fully verify within the iteration budget the exact `stopEpoch`/`setAprs` code path in `IdleCDOEpochVariant.sol`/`IdleCreditVault.sol` that invokes `prepareStopEpochWithApr0`, nor whether a privileged-but-honest recovery path (e.g., borrower default finalization clearing `apr0TotalPrincipal` per-user via `_clearWithdrawClaimForEpoch`) is considered an accepted mitigation. If the default path is reachable while `stopEpoch` reverts, the impact downgrades from permanent freeze to forced-haircut loss of the requester's full claim — still a loss of unclaimed yield consistent with the bug class.
