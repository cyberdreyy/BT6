## Analysis

`lending_pool_emissions_deposit` is a **permissionless** instruction that lets *anyone* push additional same-mint tokens into a bank's `liquidity_vault` and immediately re-price `asset_share_value` for every existing depositor pro‑rata to their current share of `total_asset_shares` at that instant: [1](#0-0) 

The share-repricing formula is:
```
asset_share_value = (total_assets + amount) / total_asset_shares
```
computed using whatever `total_asset_shares` happens to be **at the moment the instruction executes** [2](#0-1) . There is no snapshot of "who deposited before the reward accrued", no vesting, and no minimum holding period for bank deposits — a user can call `lending_account_deposit` and `lending_account_withdraw` back-to-back in the same or adjacent transaction, exactly as demonstrated by the flash-loan test harness that freely composes borrow/repay (and by extension deposit/withdraw) inside a single atomic transaction bracketed by `lending_account_start_flashloan`/`lending_account_end_flashloan` [3](#0-2) [4](#0-3) .

This is structurally the same bug class as the H-04 finding: a reward-distribution event that mints/injects value proportional to *current* stake, with no lock-up, so a large momentary depositor can capture a disproportionate share of a reward event intended for long-term depositors, then exit immediately.

I checked the other candidate reward-harvest paths (`drift_harvest_reward`, Kamino farm harvest) and those route rewards to the **global fee wallet**, not the bank's `liquidity_vault`/`asset_share_value`, so they are not diluted by depositor shares and are not viable analogs [5](#0-4) . `lending_pool_emissions_deposit` is the only instruction that ties an externally-funded, permissionless value injection directly to `asset_share_value` for arbitrary current depositors.

Important caveat I could not fully verify within tool limits: whether `bank.config.deposit_limit` meaningfully bounds the size of a flash deposit relative to existing depositors (which would cap — but not eliminate — the attacker's achievable share of an emissions event), and I did not confirm the presence/absence of any other cooldown gate on `lending_account_deposit`/`lending_account_withdraw`. I also note that a **self-funded** version of this attack (attacker both flash-deposits and personally funds the `emissions_deposit`) is mathematically unprofitable (proven below), so real-world exploitation requires the attacker to sandwich a *third party's* (e.g., protocol admin/treasury) emissions-funding transaction — feasible on Solana via Jito bundles/leader-level ordering, but this reduces likelihood relative to a fully permissionless one-transaction exploit.

### Title
Flash-Deposit Dilution of `lending_pool_emissions_deposit` Rewards - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
`lending_pool_emissions_deposit` reprices `asset_share_value` for a bank based on `total_asset_shares` at the instant it executes, with no lock-up or minimum holding period on bank deposits. An attacker can flash-deposit a large sum into the bank immediately before a genuine emissions-funding transaction lands, then withdraw immediately after, capturing a share of the injected reward proportional to their momentary (not economically real) stake — diluting the reward intended for real, long-term depositors.

### Finding Description
`lending_pool_emissions_deposit` transfers `amount` of the bank's mint into `liquidity_vault` and recomputes:
```rust
let total_assets = bank.get_asset_amount(total_asset_shares)?;
let updated_total_assets = total_assets.checked_add(I80F48::from_num(amount))...;
bank.asset_share_value = updated_total_assets.checked_div(total_asset_shares)...;
``` [2](#0-1) 

Because `total_asset_shares` is read live and any signer can be the `depositor` funding this instruction [6](#0-5) , and because standard `lending_account_deposit`/`lending_account_withdraw` carry no time-lock (bank deposits can be entered and exited within the same transaction, as marginfi's own flash-loan mechanism permits arbitrary borrow/repay/deposit/withdraw sequences inside one atomic transaction) [7](#0-6) , any account holding shares at the moment `lending_pool_emissions_deposit` executes benefits pro-rata from the injected amount — regardless of how briefly those shares were held.

### Impact Explanation
If an attacker can insert a large deposit immediately before, and a withdrawal immediately after, a legitimate emissions-funding call (e.g. via Jito bundle construction, or simply by being the entity scheduled/known to trigger the reward distribution), they capture `amount * attacker_shares / total_shares` of the reward without bearing any real economic exposure to the bank, at the direct expense of the bank's genuine depositors who were meant to receive the full distribution. This is a value-redirection issue affecting real depositor rewards.

### Likelihood Explanation
Moderate-to-low. A fully self-contained (single attacker, single transaction) exploit is **not profitable**: if the attacker both supplies the flash-deposit `D` and funds the emissions `R` themselves, their net PnL is `R * (D/(V+D) - 1) < 0` (they always get back less than they put into `R`, since their share of the pool is strictly less than 100%). Profitable exploitation requires sandwiching a *separate* legitimate emissions funder's transaction — feasible on Solana through block-builder/searcher (Jito) transaction ordering, or when reward-funding schedules are predictable/public, but not a guaranteed-success attack in the way a public-mempool front-run would be. This significantly reduces likelihood relative to the original NFTX H-04 finding, which required no such sandwiching.

### Recommendation
- Require deposits to be held for a minimum duration (or a per-block/epoch snapshot) before they are eligible to receive newly injected `lending_pool_emissions_deposit` value, or
- Track a "shares as of last emissions checkpoint" snapshot and only distribute pro-rata to shares held since the prior checkpoint, or
- Restrict `lending_pool_emissions_deposit` to only the group admin / a designated emissions authority (removing full permissionlessness) so funding timing is not predictable/front-runnable by third parties, or
- Rate-limit / cap the fraction of `total_asset_shares` that can be added in a single transaction immediately preceding an emissions deposit (e.g., disallow same-transaction deposit+emissions_deposit+withdraw sequences by enforcing the flashloan-account state flag on regular deposit/withdraw as well).

### Proof of Concept
1. Bank state: `total_asset_shares = 100`, `total_assets = 100` (`asset_share_value = 1.0`), held by legitimate long-term depositors.
2. Attacker observes (or is aware of a scheduled) call to `lending_pool_emissions_deposit(100)` by the protocol treasury.
3. Attacker flash-borrows 900 tokens, calls `lending_account_deposit` into the bank, minting ~900 new shares (`total_asset_shares = 1000`, `total_assets = 1000`).
4. The treasury's `lending_pool_emissions_deposit(100)` executes (attacker ensures it lands immediately after step 3, e.g. via bundle ordering): `updated_total_assets = 1100`, new `asset_share_value = 1100/1000 = 1.10`.
5. Attacker immediately calls `lending_account_withdraw` for their ~900 shares, redeeming `900 * 1.10 = 990` tokens — netting a 90-token profit purely from momentary stake, while the pre-existing depositors' 100 shares only gained `100*1.10 - 100 = 10` tokens instead of the full 100 they would have received alone.
6. Attacker repays the flash loan (890 tokens borrowed of value, plus fee), pocketing the 90-token skim, minus flash-loan fee.

/// Permissionlessly deposit same-mint emissions directly into the bank liquidity vault,
/// increasing depositor value through asset share value.
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```

/// Checklist
/// 1. `end_flashloan` ix index is after `start_flashloan` ix index
/// 2. Ixs has an `end_flashloan` ix present
/// 3. `end_flashloan` ix is for the marginfi program
/// 4. `end_flashloan` ix is for the same marginfi account
/// 5. Start flashloan ix is not in CPI
/// 6. End flashloan ix is not in CPI
pub fn check_flashloan_can_start(
    marginfi_account: &AccountLoader<MarginfiAccount>,
    sysvar_ixs: &AccountInfo,
    end_fl_idx: usize,
) -> MarginfiResult<()> {
    let current_ix_idx: usize = validate_not_cpi_with_sysvar(sysvar_ixs)?;
    check!(current_ix_idx < end_fl_idx, MarginfiError::IllegalFlashloan);
    validate_not_cpi_by_stack_height()?;

    // Will error if ix doesn't exist
    let unchecked_end_fl_ix = load_instruction_at_checked(end_fl_idx, sysvar_ixs)?;

    let discrim = &unchecked_end_fl_ix.data[..8];
    if discrim != END_FLASHLOAN {
        msg!("discrim: {:?}, expected: {:?}", discrim, END_FLASHLOAN);
        return err!(MarginfiError::IllegalFlashloan);
    }

    check!(
        unchecked_end_fl_ix.program_id.eq(&crate::ID),
        MarginfiError::IllegalFlashloan
    );

    let end_fl_ix = unchecked_end_fl_ix;

    let end_fl_marginfi_account = end_fl_ix
        .accounts
        .get(END_FL_IX_MARGINFI_ACCOUNT_AI_IDX)
        .ok_or(MarginfiError::IllegalFlashloan)?;

    check!(
        end_fl_marginfi_account.pubkey.eq(&marginfi_account.key()),
        MarginfiError::IllegalFlashloan
    );

    Ok(())
}

async fn flashloan_success_1op() -> anyhow::Result<()> {
