### Title
Unbounded zstd compression cost for `getAccountInfo`/`base64+zstd` scales with attacker-controlled account size - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account`'s `UiAccountEncoding::Base64Zstd` branch feeds the full (or data-sliced) account payload directly into a `zstd::stream::write::Encoder` with no size cap, unlike the sibling `Base58`/`Binary` paths which are explicitly gated by `MAX_BASE58_BYTES`. Since accounts can be funded on-chain up to `MAX_PERMITTED_DATA_LENGTH`, a single `getAccountInfo` call with `encoding=base64+zstd` forces CPU/allocation work proportional to attacker-controlled data size rather than to any RPC-side constant.

### Finding Description
`rpc::get_account_info` resolves `encoding` and calls `get_encoded_account` → `encode_account` → `encode_ui_account` on a `spawn_blocking` task [1](#0-0) . `encode_account` only enforces a size check (`MAX_BASE58_BYTES`) for `Binary`/`Base58` encodings; all other encodings, including `Base64Zstd`, pass straight through to `encode_ui_account` with no length gate [2](#0-1) . Inside `encode_ui_account`, the `Base64Zstd` arm builds a `zstd::stream::write::Encoder` and writes the entire sliced account data into it before base64-encoding the result [3](#0-2) . There is no explicit bound analogous to `MAX_BASE58_BYTES` before entering this compression path, so cost (CPU cycles, transient allocations for the encoder buffer and output vector) scales with `account.data().len()`, which is attacker-controlled up to `MAX_PERMITTED_DATA_LENGTH` (10 MiB) via a normal `SystemProgram::Allocate`/write funding sequence.

### Impact Explanation
This falls under "RPC DoS" bounded by a single low-rate call: one `getAccountInfo` request with `base64+zstd` encoding against a self-funded max-size account consumes a blocking-thread-pool worker for CPU time proportional to the full account size, with no RPC-side cap analogous to the base58 128-byte limit. Repeating this (still within the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` constraint) against large accounts degrades a fraction of the RPC blocking thread pool without needing multiple clients or any privileged access.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs (1) enough funds/rent to grow an account's data up to (near) `MAX_PERMITTED_DATA_LENGTH` via ordinary system-program allocate/write instructions, and (2) a single `getAccountInfo` call specifying `encoding: "base64+zstd"`. No special privileges, gossip access, or multiple concurrent connections are required, and the RPC method offers no encoding-specific size check to reject it, unlike the base58 path.

### Recommendation
Add an explicit size gate before entering the zstd encoder in `encode_ui_account` (or in `encode_account`), e.g. reject/short-circuit `Base64Zstd` requests where the sliced data length exceeds a fixed cap, or move the compression work off the request-critical resource pool with a stricter bound, mirroring the existing `MAX_BASE58_BYTES`-style guard used for `Base58`/`Binary`.

### Proof of Concept
```rust
// account-decoder/src/lib.rs (or a new bench)
#[test]
fn bench_base64_zstd_cost_scales_with_account_size() {
    use std::time::Instant;
    let sizes = [4 * 1024, 1024 * 1024, 10 * 1024 * 1024]; // up to MAX_PERMITTED_DATA_LENGTH
    let mut timings = vec![];
    for size in sizes {
        let account = AccountSharedData::from(Account {
            data: vec![0u8; size],
            ..Account::default()
        });
        let start = Instant::now();
        let _ = encode_ui_account(
            &Pubkey::default(),
            &account,
            UiAccountEncoding::Base64Zstd,
            None,
            None,
        );
        timings.push(start.elapsed());
    }
    // Assert timings grow roughly linearly with size (no bound independent of size),
    // demonstrating there is no explicit cap analogous to MAX_BASE58_BYTES.
    assert!(timings[2] > timings[1] * 2);
    assert!(timings[1] > timings[0] * 2);
}
```
Combine this with an integration test issuing repeated `getAccountInfo` RPC calls (`encoding: "base64+zstd"`) against an account grown to `MAX_PERMITTED_DATA_LENGTH` via `SystemProgram::allocate`, confirming request latency and CPU usage scale with account size and that no `InvalidRequest` error is returned prior to compression (unlike the base58 128-byte case in `test_encode_account_throws_when_data_too_large_to_base58_encode`) [4](#0-3) .

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
