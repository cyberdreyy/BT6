### Title
Deterministic Address Overwrite in Escrow Deployment - ([File: contracts/BaseEscrowFactory.sol])

### Summary
The `BaseEscrowFactory` contract is vulnerable to a "deterministic address overwrite" issue where an unprivileged actor can prevent the deployment of a legitimate escrow or potentially interfere with its state. This occurs because the factory uses `Clones.cloneDeterministic` (based on `CREATE2`) to deploy escrow proxies at addresses derived solely from the `immutables` hash, without verifying if a contract already exists at that address or if the deployment was successful.

### Finding Description
In `BaseEscrowFactory.sol`, both `_postInteraction` (for source escrows) and `createDstEscrow` (for destination escrows) calculate a `salt` using `immutables.hashMem()` and then call `_deployEscrow`. [1](#0-0) [2](#0-1) 

The `_deployEscrow` function uses OpenZeppelin's `cloneDeterministic`: [3](#0-2) 

The vulnerability arises because:
1.  **Lack of Existence Check**: The factory does not check if an escrow has already been deployed at the computed address.
2.  **Unprivileged Trigger**: An attacker can pre-compute the escrow address for a pending order (as all parameters are public or predictable) and deploy a contract there first (e.g., via a different factory or directly if the implementation allows).
3.  **Deployment Failure**: If a contract already exists at the `CREATE2` address, `cloneDeterministic` will revert.
4.  **State Overwrite Invariant**: While `CREATE2` prevents overwriting *code* if the address is occupied, the protocol logic assumes that if `_deployEscrow` is called, it is a fresh deployment. In `createDstEscrow`, the factory proceeds to transfer tokens into the address: [4](#0-3) 

If an attacker successfully "squats" on the address or if a previous failed/cancelled swap used the exact same `immutables` (e.g., same `orderHash`, `hashlock`, and `timelocks`), the new deployment will fail, or funds will be sent to an already existing contract whose state might not be what the new user expects.

### Impact Explanation
- **Permanent Freezing of Funds**: If a user sends a "safety deposit" to a pre-computed address (as instructed by the docs) and an attacker has already deployed a contract there, the `postInteraction` will revert, and the user's native tokens are stuck in the malicious/existing contract.
- **Protocol Denial of Service**: An attacker can monitor the mempool for `createDstEscrow` calls and front-run them by deploying a dummy contract at the same address, causing the legitimate transaction to revert.
- **Theft of Fees/Funds**: If the attacker can control the state of the pre-deployed contract (e.g., by exploiting a different implementation that shares the same address space), they could potentially withdraw the tokens sent by the factory in `createDstEscrow`.

### Likelihood Explanation
The likelihood is medium-high because all parameters used for the `salt` (order details, hashlocks, timelocks) are visible in the mempool or off-chain order books. An unprivileged actor can easily compute the target address and front-run the deployment.

### Recommendation
1.  **Check for Existence**: Before calling `_deployEscrow`, check if `address(escrow).code.length > 0`.
2.  **Include Nonce/Sender**: Include `msg.sender` or a unique nonce in the `immutables` hash to ensure that different users or attempts result in different addresses.
3.  **Validate Success**: Ensure the deployment actually succeeded and the contract is in the expected initial state.

### Proof of Concept
1.  User $A$ signs a cross-chain order.
2.  Attacker $B$ sees the order and computes the `SrcEscrow` address using `addressOfEscrowSrc`.
3.  $B$ deploys a minimal contract at that address using a separate `CREATE2` factory.
4.  $A$ sends the `safetyDeposit` to the address.
5.  The Resolver tries to fill the order. The `postInteraction` call in `BaseEscrowFactory` reaches `_deployEscrow`, which calls `cloneDeterministic`.
6.  `cloneDeterministic` reverts because the address is already occupied.
7.  The order cannot be filled, and $A$'s `safetyDeposit` is trapped in the contract deployed by $B$. [5](#0-4)
