### Title
Clearpool reward claiming permanently disabled on Polygon zkEVM strands all accrued CPOOL/MATIC yield in the strategy - (File: contracts/polygon-zk/strategies/clearpool/IdleClearpoolStrategyPolygonZK.sol)

### Summary
`IdleClearpoolStrategyPolygonZK` is a chain-specific copy of the Ethereum `IdleClearpoolStrategy` (`contracts/strategies/clearpool/IdleClearpoolStrategy.sol`). On mainnet, `redeemRewards` harvests Clearpool rewards via `IPoolMaster(pool).factory().withdrawReward(pools)` and forwards them to the `IdleCDO`. That Clearpool reward API is a mainnet deployment detail (the analog of `Minter.mint(gauge)` being mainnet-only for Curve): Clearpool's zkEVM pools do not expose the same `PoolFactory.withdrawReward` reward pipeline, so on `IdleClearpoolStrategyPolygonZK` the entire reward-claim body has been commented out rather than ported to a chain-correct API. The function still advertises MATIC as a reward token via `getRewardTokens()`, but `redeemRewards` returns an uninitialized (empty) `rewards` array and never transfers any token to the CDO.

Meanwhile `getRewardTokens()` still reports `MATIC` to the CDO (line 140-148), and `CPOOL`/`MATIC` constants are hardcoded (lines 58-63), so reward tokens that accrue to or are sent to the strategy contract have no exit path: `redeemRewards` is the only function that moves reward tokens, and it is a no-op. Reward tokens accumulating in the strategy are permanently frozen — the direct equivalent of "CurveProxy calls the wrong chain API so CRV can never be minted on the sidechain," except here the sidechain port was abandoned mid-way, leaving the function callable but functionless.

### Impact Explanation
All CPOOL/MATIC (and any other reward token) sent to or accrued by the strategy is permanently locked in `IdleClearpoolStrategyPolygonZK`. There is no sweep/rescue function and no code path transferring reward balances to the `IdleCDO`. Loss equals the full accumulated reward balance of the strategy contract — theft-free but permanent freezing of unclaimed yield, which is in the accepted impact classes.

### Likelihood Explanation
High for the freezing component: reward distributions (MATIC incentives noted in the commented code) are expected to flow through `redeemRewards`. Since `getRewardTokens()` still returns MATIC, any harvest flow relying on it cannot recover the tokens. However, there is no unprivileged-attacker lever: the stuck funds are lost by omission, not stealable by an EOA. Severity is bounded by reward accrual, not principal — deposit/redeem paths (`_depositToVault`, `_redeem` via `provide`/`redeem`) use APIs that do exist and function.

### Recommendation
Either implement the zkEVM-correct reward-claim path for Clearpool on that chain (mirroring the recommendation in the external report to use `IGauge(gauge).factory().mint(gauge)` rather than the mainnet `Minter.mint`), or, if rewards are not supported on zkEVM, remove the misleading `getRewardTokens()`/`redeemRewards` surface and add an `onlyOwner` rescue function to sweep stranded reward tokens to the CDO or fee receiver.

### Proof of Concept
A Foundry zkEVM fork test deploys `IdleClearpoolStrategyPolygonZK`, initializes it against a live Clearpool pool, sends MATIC/CPOOL to the strategy (simulating accrued rewards), calls `redeemRewards` from the `idleCDO` address, and asserts: (a) the call succeeds returning an empty array, (b) the strategy's reward-token balance is unchanged and no transfer to the CDO occurred, demonstrating permanent freeze. Confirm additionally that `IPoolMaster(cpToken).factory().withdrawReward` is absent/reverts on the zkEVM Clearpool deployment — I was unable to verify the live zkEVM Clearpool ABI within this review, so the "API does not exist on-chain" leg should be confirmed against the actual deployment before finalizing severity.
