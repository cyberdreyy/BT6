### Title
EI-authenticated requests satisfy `isUser` check and can trigger arbitrary jobs by integer ID despite comment "EIs not allowed" - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}` in addition to `SessionExternalInitiatorKey`, so any code that calls `auth.GetAuthenticatedUser(c)` cannot distinguish a real run-role user from an EI-authenticated caller. `PipelineRunsController.Create` relies exactly on this ambiguous check (`isUser`) to gate the integer-job-ID run path, even though its own comment states "only users are allowed to run jobs using int IDs - EIs not allowed." As a result an EI can trigger a run for any job by numeric ID with no EI-to-job binding validation.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) authenticates the EI token, then unconditionally does: [1](#0-0) 
This puts a `*clsessions.User{Role: UserRoleRun}` into the same context key (`SessionUserKey`) used for real session/token users.

The `/v2/jobs/:ID/runs` route is wrapped with `auth.RequiresRunRole` after trying EI, token, and session auth in that order: [2](#0-1) 
`RequiresRunRole` only checks `user.Role != UserRoleView` via `GetAuthenticatedUser` — it has no notion of EI scoping: [3](#0-2) 

Inside the handler, the intended design (per its own comment) is that int32 job IDs should be run only by real users, not EIs: [4](#0-3) 
But `isUser` is derived from `auth.GetAuthenticatedUser(c)`, which returns `true` for the synthetic EI user set in `AuthenticateExternalInitiator`. There is no call to `auth.GetAuthenticatedExternalInitiator(c)` anywhere in this controller to validate that the target job is actually bound to the authenticated EI. Consequently, an EI credential holder satisfies `isUser`, and can call `prc.App.RunJobV2(ctx, jobID, nil)` for any int32 job ID it can enumerate/guess, regardless of job type or EI ownership.

Note: the originally hypothesized scenario (EI #1 bound to webhook Job X using the job's external UUID to hit Job Y bound to EI #2) is not reachable as stated, because webhook-by-UUID job running has been entirely removed from the codebase — the handler now rejects any UUID-shaped `:ID` outright with `job.ErrJobTypeRemoved` before any user/EI check occurs, and webhook job creation itself is rejected: [5](#0-4) [6](#0-5) [7](#0-6) 
So the specific EI-to-EI webhook UUID cross-trigger described cannot occur today. The real, still-live manifestation of the same root cause (shared Role==UserRoleRun check without EI-job binding) is the int32-ID path described above.

### Impact Explanation
An external-initiator credential (a low-privilege, job-scoped credential intended only to trigger runs of the webhook job it is bound to) can instead trigger `RunJobV2` for any job in the node by supplying its integer database ID — not limited to jobs it "owns." This is an authorization bypass allowing unauthorized triggering of another job's pipeline run (matching the bounty class "unauthorized job run"), potentially causing unintended on-chain transactions, wasted LINK/gas, unintended oracle responses, or interference with unrelated jobs' state, depending on what job types/pipelines exist on that node.

### Likelihood Explanation
Requires only valid credentials for any single EI already registered on the node — no admin/edit privileges. The attacker additionally needs to know or guess a target job's int32 ID, which is sequential/enumerable (job IDs are typically small integers assigned at creation) and can often be discovered via other exposed endpoints or by brute-forcing a small ID range. No special timing or race condition needed; fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, distinguish real authenticated users from EI-authenticated pseudo-users (e.g., by checking `auth.GetAuthenticatedExternalInitiator(c)` first and rejecting if present, rather than relying on `GetAuthenticatedUser` alone), so the int32-ID path is only reachable by genuine session/token users, consistent with the existing code comment's intent. More broadly, avoid overloading `SessionUserKey` for EI authentication; use a distinct check (e.g. `isEI := ei != nil`) to gate any user-role logic.

### Proof of Concept
Handler/integration test plan:
1. Start an application, create an `ExternalInitiator` EI1 and a job Job A (any type creatable, e.g. non-webhook job) unrelated to EI1.
2. Authenticate as EI1 via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers.
3. POST `/v2/jobs/{JobA.ID}/runs` (integer ID) using EI1's credentials.
4. Assert response is `200 OK` with a created pipeline run (i.e., `prc.App.RunJobV2` was invoked), demonstrating EI1 triggered a run for a job it has no binding to.
5. Compare against expected behavior: assert `403`/`422` should occur because "EIs not allowed" per the code comment, proving the check `isUser` does not enforce that restriction.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
