### Title
AWS Secrets Manager resolver ignores job cancellation, allowing prolonged runner-slot occupation via retry-multiplied fixed timeouts - ([File: helpers/secrets/resolvers/aws/aws_secrets_manager_resolver.go])

### Summary
`resolver.Resolve()` creates its AWS call context with `context.WithTimeout(context.Background(), contextTimeout)` instead of deriving it from the build's cancellable context, so a canceled/aborted job cannot interrupt in-flight `GetSecretString` calls. Combined with the job-controlled `SECRETS_RETRIEVAL_ATTEMPTS` retry loop, a pipeline author can force the runner to hold a build-execution goroutine/slot for up to `contextTimeout` (30s) × attempts even after the job is cancelled, delaying other tenants' queued jobs on a `concurrent`-limited runner.

### Finding Description
In `helpers/secrets/resolvers/aws/aws_secrets_manager_resolver.go`, `Resolve()` builds its own context independent of any caller-supplied context: [1](#0-0) 

Because `context.Background()` is the parent, there is no linkage to the build's cancellation signal. When GitLab cancels a job, whatever mechanism the runner uses to propagate cancellation (via a build context) cannot reach this `ctx`; only the fixed 30-second timeout, or actual completion/error of the AWS SDK call, will unblock `s.GetSecretString`. The resolver's timeout constant is fixed and not attacker-tunable, but the retry count around it is job-controlled through `SECRETS_RETRIEVAL_ATTEMPTS`, referenced in `common/build.go`. An unprivileged pipeline author can define a secret pointing at a `SecretId`/region/role combination that is slow or unreachable (e.g., non-existent VPC endpoint, throttled/backoff-inducing role, or a region with no route) so each attempt stalls close to the 30s ceiling, and set a large `SECRETS_RETRIEVAL_ATTEMPTS`. The retry wrapper (`retry.New().WithMaxTries(attempts)`) will call `Resolve()` repeatedly; since each call spawns an independent `context.Background()`-rooted context, cancelling the outer job does not shortcut any already-started attempt, and — critically — nothing prevents the retry loop itself from continuing to invoke `Resolve()` beyond the point the job was cancelled if the retry/backoff logic isn't itself tied to the same cancellable context. This isolates the AWS Secrets Manager resolver's blocking calls from the job's cancellation lifecycle, violating the invariant that cancellation must promptly release runner resources.

### Impact Explanation
On a runner configured with a limited `concurrent` value, a build's execution goroutine remains occupied by the blocked/retrying secret resolution for up to `30s * attempts`, even after the job is cancelled from GitLab. Since concurrency slots are shared across projects on that runner, this ties up a slot that would otherwise pick up queued jobs from other tenants, causing scheduling delays for unrelated projects — a persistent, low-privilege-triggerable resource-starvation/DoS effect scoped to the shared runner, consistent with "Medium persistent multi-tenant disruption."

### Likelihood Explanation
Exploitation only requires an unprivileged pipeline author with rights to define a `.gitlab-ci.yml` `secrets:` block referencing `AWSSecretsManager` (using attacker-controlled/misconfigured region, role, or unreachable SecretId) and setting the `SECRETS_RETRIEVAL_ATTEMPTS` job variable to a large value — both are standard job-author capabilities, no admin access needed. The slow/hanging AWS response condition (bad `RoleARN`, unreachable network path, or throttling) is realistic and reproducible by any user with an AWS account or by pointing at a black-holed endpoint.

### Recommendation
Thread the build's cancellable `context.Context` (e.g., from `Build.Cancel`/`Build.ctx` or the stage's context) into `SecretResolver.Resolve()` (change its signature to accept a `context.Context`), and use `context.WithTimeout(callerCtx, contextTimeout)` instead of `context.WithTimeout(context.Background(), contextTimeout)` in `helpers/secrets/resolvers/aws/aws_secrets_manager_resolver.go` (and the analogous Azure/GCP/Vault/GitLab resolvers). Ensure the retry wrapper around `executeResolveSecretsStage` also checks/propagates cancellation between attempts so it stops retrying once the job/build context is done.

### Proof of Concept
Go unit test plan:
1. Stub `newAWSSecretsManagerService`/`AWSSecretsManager.GetSecretString` to block until its passed `ctx.Done()` fires or 30s elapses (whichever first), simulating a slow AWS backend.
2. Call `resolver.Resolve()` from a goroutine, then cancel an outer/build context (once `Resolve` is changed to accept one, or observe current behavior with the existing signature) after e.g. 2 seconds.
3. Assert that `Resolve()` returns within a short bound (e.g. < 3s) once cancellation occurs — this fails today because `Resolve()`'s internal `ctx` is rooted in `context.Background()` and only stops at the full 30s timeout or completion, proving the goroutine is not released on cancellation.
4. Extend to an integration-style test around `Build.attemptResolveSecrets` with `SECRETS_RETRIEVAL_ATTEMPTS=5` and a mocked slow resolver, cancelling the build mid-retry, and asserting the retry loop and goroutine terminate promptly rather than continuing for `5 * 30s`.
