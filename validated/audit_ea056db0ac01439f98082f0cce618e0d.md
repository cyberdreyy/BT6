### Title
Malicious ERC4626 vault user can DoS `stopEpoch` by draining vault liquidity, freezing all tranche withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
Analogous to the Cooler "malicious callback blocks repayment" bug, `IdleCDOEpochVariant.stopEpochWithDuration` calls the borrower hook `IProgrammableBorrower.onStopEpoch`, which performs an external call into a permissionless ERC4626 vault (`vault.withdraw`). If that withdrawal reverts, the hook reverts with `StopEpochVaultLiquidityUnavailable` and the whole `stopEpoch` reverts. Any unprivileged user of the vault (e.g. a borrower in the underlying Morpho-style market) can drain available liquidity just before the manager stops the epoch, repeatedly blocking epoch settlement and freezing lender funds.

### Finding Description
In `contracts/IdleCDOEpochVariant.sol`, the programmable-borrower stop path deliberately lets hook reverts bubble up instead of falling through to the default handler: [1](#0-0) 

In `contracts/strategies/idle/ProgrammableBorrower.sol`, `onStopEpoch` returns `true` (leading to a real default via the failed `transferFrom`) only when the vault position *economically* can't cover the shortfall (`shortfall > _currentVaultAssets()`). But when shares do cover the shortfall on paper, it calls `vault.withdraw(shortfall, ...)` in a `try/catch` and reverts `StopEpochVaultLiquidityUnavailable` on failure: [2](#0-1) 

The gap: ERC4626 `convertToAssets` values shares against *total* assets, while `withdraw` requires *liquid* assets. For a vault over a lend/borrow market, an attacker can:

1. Supply collateral and borrow out (nearly) all idle liquidity in the vault's underlying market, leaving `convertToAssets` unchanged (share price is unaffected — the assets are still accounted for, just lent out).
2. Wait for / front-run the manager's `stopEpoch` call when `shortfall` exceeds remaining liquidity.
3. `vault.withdraw(shortfall)` reverts (insufficient liquidity), so `onStopEpoch` reverts `StopEpochVaultLiquidityUnavailable`, so `stopEpoch` reverts. The epoch stays running, `epochAccountingActive` stays true, and no withdraw requests can be claimed.
4. Repeat each time liquidity returns, or simply hold the borrow position (paying borrow interest) to extend the freeze.

No guard stops this: `setVault` can't migrate while `vault.balanceOf != 0` ( [3](#0-2) ), the `try this.getFundsFromBorrower` catch in `stopEpoch` is never reached because the revert happens earlier in the hook, and the pause/default path only triggers on `return false` or a failed `transferFrom` — not on a hook revert.

### Impact Explanation
Temporary freezing of all lender principal and yield in the vault. Every pending and future withdraw request (`claimWithdrawRequest`, normal redemptions gated on epoch stop) is blocked for as long as the attacker keeps vault liquidity drained. The cost to the attacker is only the borrow interest on the drained liquidity (zero if the underlying market subsidizes borrows, or briefly via a leveraged looped position), versus freezing the entire pool TVL. Quantified loss: 100% of pool NAV is illiquid for the attack duration; lenders' opportunity cost = pool NAV × pool APR × freeze duration.

### Likelihood Explanation
Medium. Requires (a) the programmable-borrower vault variant in production, (b) a vault whose liquidity an unprivileged user can borrow/withdraw, and (c) the attacker paying borrow interest to sustain the freeze. All three are realistic: the design explicitly routes withdrawals through a shared ERC4626 liquidity venue, and the attacker needs no privileged role and causes no state corruption — matching the "unprivileged vault user" attacker model.

### Recommendation
Make the vault-withdraw failure non-fatal for epoch settlement, e.g.:

- In `onStopEpoch`, on `vault.withdraw` failure withdraw whatever `vault.maxWithdraw(address(this))` allows (partial withdrawal) and return `true`, letting IdleCDO's `transferFrom` pull what's available; the residual shortfall then fails `transferFrom` and flows into the existing `_handleBorrowerDefault` path instead of reverting. Note this converts freeze into a default, which may be the desired escalation.
- Alternatively, allow the manager to pass a flag to `stopEpochWithDuration` that skips/limits the vault recall, or add a `maxIterations`-style retry with a capped withdrawal amount so a partially-liquid vault still makes progress.

### Proof of Concept
Foundry fork test outline (mainnet fork over a Morpho Blue / ERC4626 vault with an underlying borrow market):

```solidity
function testGriefStopEpochByDrainingVaultLiquidity() external {
    // Setup: deposit into AA tranche, start epoch (borrower vault funded)
    idleCDO.depositAA(amount);
    vm.prank(manager);
    cdoEpoch.startEpoch(); // PB.onStartEpoch deposits into vault

    // Attacker: unprivileged user of the vault's underlying market.
    // Supply collateral + borrow all available liquidity (or withdraw via own shares).
    vm.startPrank(attacker);
    morpho.supplyCollateral(collateralToken, collateralAmt, attacker, "");
    morpho.borrow(marketParams, vaultIdleLiquidity, 0, attacker, attacker);
    vm.stopPrank();
    // Now vault.maxWithdraw(PB) < shortfall, but convertToAssets(shares) still covers it.

    // Epoch matures; manager tries to settle.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(newApr, 0);

    // Epoch still running; all withdraw requests remain frozen.
    assertTrue(cdoEpoch.isEpochRunning());
    // Attacker can repeat indefinitely by re-draining liquidity whenever it returns.
}
```

The revert propagates from `ProgrammableBorrower.onStopEpoch` (`try vault.withdraw ... catch { revert StopEpochVaultLiquidityUnavailable(); }`) through the unchecked hook call in `IdleCDOEpochVariant` line 398, before the `try this.getFundsFromBorrower` catch that would otherwise route to `_handleBorrowerDefault`.
