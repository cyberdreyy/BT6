### Title
Zip extraction lacks path traversal / Zip-Slip protection allowing writes outside build root - (File: helpers/archives/zip_extract.go)

### Summary
`extractZipFile` (and the helpers it dispatches to, `extractZipFileEntry` and `extractZipSymlinkEntry`) write extracted content to `file.Name` via `os.OpenFile`/`os.Symlink` with no validation that the resolved path stays within the extraction root. Unlike `tarzstd_extractor.go`, which resolves `filepath.Join(e.dir, hdr.Name)` and rejects any path that doesn't have `e.dir` as a prefix, the zip extraction path (`ExtractZipArchive` → `extractZipFile`) performs no such check, and the `dir` parameter is not even threaded through to `helpers/archives.ExtractZipArchive` by `ziplegacy.extractor.Extract`.

### Finding Description
`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`'s `extractor.Extract` opens a `zip.Reader` and calls `archives.ExtractZipArchive(zr)` — note that `e.dir` (the intended confinement root) is never passed into `ExtractZipArchive` or used anywhere in that call. In `helpers/archives/zip_extract.go`, `ExtractZipArchive` iterates `archive.File` and calls `extractZipFile(file)` for each entry, which:
- Creates parent directories with `os.MkdirAll(filepath.Dir(file.Name), 0o777)` using the raw `file.Name`.
- For regular files, calls `extractZipFileEntry`, which does `os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, ...)` directly on `file.Name`.
- For symlinks, calls `extractZipSymlinkEntry`, which does `os.Symlink(string(data), file.Name)`, writing an attacker-controlled symlink target to an attacker-controlled path.

None of these functions join `file.Name` against a base directory nor validate it — contrast with `commands/helpers/archive/tarzstd/tarzstd_extractor.go`'s `Extract`, which computes `path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name))` and enforces `strings.HasPrefix(path, e.dir+string(filepath.Separator))`. The only guard present in the zip path is `errorIfGitDirectory`, which only blocks entries whose name is a `.git` directory — it does nothing to prevent `../` traversal or absolute paths.

If the process has `chdir`'d into the artifact/build working directory before extraction (as implied by the call sequence `openArchive → archive.NewExtractor(archive.Zip, f, size, wd) → ExtractZipArchive`), a zip entry name such as `../../etc/cron.d/evil` will resolve relative to that cwd and can write outside the intended root; an absolute entry name (e.g. `/etc/cron.d/evil`) is honored by `os.OpenFile`/`os.Symlink` unconditionally, regardless of cwd. The `fastzip` extractor (`commands/helpers/archive/fastzip/zip_fastzim_extractor.go`) delegates to the third-party `saracen/fastzip` library, which does perform its own path-confinement checks internally — but the legacy zip path (`ziplegacy`, backed by `helpers/archives/zip_extract.go`) does not, and it is registered/selectable as one of the supported zip extractor implementations.

### Impact Explanation
An attacker who controls the contents of an artifact zip (e.g., a pipeline author whose job produces artifacts consumed by a downstream job/stage that runs `artifacts-downloader`) can craft entry names with `../` sequences or absolute paths. When that archive is extracted via the legacy zip path, files or symlinks can be written outside the job's artifact/build root, on the host or container filesystem the runner process can write to — a classic Zip-Slip arbitrary file write, potentially leading to file overwrite outside the sandboxed build directory.

### Likelihood Explanation
This is straightforwardly reproducible with no special privileges beyond controlling job artifact content — a normal CI job can shape its own artifact zip's raw entries (or the archive can be forged/replayed since nothing validates entry names on download). Whether it is actually reachable at runtime depends on which zip extractor implementation is selected/registered by default (`ziplegacy` vs `fastzip`); if `ziplegacy`/`archives.ExtractZipArchive` is used, the exploit is fully open with no mitigating check in `zip_extract.go`.

### Recommendation
Add the same confinement check used in `tarzstd_extractor.go` to the zip path: thread the target `dir` through `ziplegacy.extractor.Extract` into `archives.ExtractZipArchive`/`extractZipFile`, resolve each entry as `filepath.Join(dir, file.Name)`, reject entries whose resolved absolute path does not have `dir` as a prefix (and reject empty/absolute `file.Name` outright), and apply this validation before any `os.MkdirAll`, `os.OpenFile`, or `os.Symlink` call, mirroring the `strings.HasPrefix(path, e.dir+separator)` guard.

### Proof of Concept
Go unit test in `helpers/archives`:
```go
func TestExtractZipArchive_PathTraversalRejected(t *testing.T) {
    dir := t.TempDir()
    outside := filepath.Join(dir, "..", "evil.txt")

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    w, _ := zw.Create("../evil.txt")
    _, _ = w.Write([]byte("pwned"))
    _ = zw.Close()

    zr, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))

    // Simulate extraction rooted at dir (once dir confinement is added)
    _ = os.Chdir(dir)
    err := ExtractZipArchive(zr)

    _, statErr := os.Stat(outside)
    require.True(t, os.IsNotExist(statErr), "file must not be created outside extraction root")
    _ = err
}
```
Expected (current) result: `os.Stat(outside)` succeeds — the file is created outside `dir`, proving the missing confinement check; after the fix, extraction should fail/skip the entry and `outside` must not exist.
