This confirms the full picture: `rescueFunds` is also `onlyCaller(taker)`-gated and does not depend on fee decoding at all — it simply moves whatever `token`/`amount` the taker specifies to itself. So the only ways out of a bricked escrow are `cancel()` (taker-only, timelocked) and `rescueFunds()` (taker-only, rescue-delay-gated) — neither of which requires decoding `parameters`, but neither can send funds to the maker either.

### Title
Unvalidated `parameters` length in `createDstEscrow` lets a short blob permanently revert both `withdraw` and `publicWithdraw` on `EscrowDst` - (File: `contracts/EscrowDst.sol`, `contracts/BaseEscrowFactory.sol`, `contracts/libraries/ImmutablesLib.sol`)

### Summary
`createDstEscrow` accepts caller-supplied `Immutables.parameters` with no minimum-length check, and that same `parameters` blob is baked into the CREATE2 salt/immutables hash used by every later call (`withdraw`, `publicWithdraw`, `cancel`, `rescueFunds`). `EscrowDst._withdraw` unconditionally calls `integratorFeeAmountCd()`/`protocolFeeAmountCd()`, which revert with `IndexOutOfRange` if `parameters.length < 0x40`/`0x20`. A destination-escrow creator who funds the escrow with a `parameters` blob shorter than 0x40 bytes (e.g., 1 byte) makes both the private `withdraw()` and the public `publicWithdraw()` path permanently revert, for the life of the withdrawal windows, since `Immutables` (including `parameters`) can never be changed without changing the hash checked by `onlyValidImmutables`.

### Finding Description
- `createDstEscrow` in [1](#0-0)  takes `dstImmutables` directly from `msg.sender` with no validation of `parameters` content or length, computes `salt = immutables.hashMem()`, and deploys/funds the clone.
- `EscrowDst._withdraw` in [2](#0-1)  unconditionally calls `immutables.integratorFeeAmountCd()` and `immutables.protocolFeeAmountCd()` before computing the maker payout, regardless of whether fees are actually zero.
- `ImmutablesLib.integratorFeeAmountCd`/`protocolFeeAmountCd` in [3](#0-2)  revert `IndexOutOfRange` if `parameters.length` is below `0x20`/`0x40`.
- Both `withdraw()` and `publicWithdraw()` route through the same `_withdraw()` internal function ( [4](#0-3) ), so there is no alternate path to reach the maker payout once `parameters` is malformed.
- `Immutables` (including `parameters`) is committed via `onlyValidImmutables(immutables.hash())` on every action (see `ImmutablesLib.hash` at [5](#0-4) ), so the caller cannot resubmit a corrected `parameters` value later — the deployed escrow is permanently stuck with whatever `parameters` was used at `createDstEscrow` time.
- The only exits are `cancel()` ( [6](#0-5) ), which sends the full `amount` back to the *taker* (not the maker) after `DstCancellation`, and `rescueFunds()` ( [7](#0-6) ), also taker-only and after the rescue delay. Neither one performs fee decoding, so they remain callable, but neither one can ever deliver funds to the maker.

### Impact Explanation
This breaks the required invariant that a funded destination escrow with a known secret must be withdrawable via the public path. A destination-escrow creator (the taker calling `createDstEscrow`, which has no access-control/whitelist gate in this contract) can fund an escrow whose `parameters` field is 1 byte, guaranteeing that neither the maker (via `withdraw`) nor any access-token holder (via `publicWithdraw`) can ever release the maker's payout. The maker's expected destination funds are frozen for the entire withdrawal/public-withdrawal window and can only be recovered by the taker reclaiming them via `cancel()`/`rescueFunds()` — the maker never receives the destination-side funds despite having correctly revealed the secret. This matches the "temporary freezing of funds during the live swap lifecycle" High-severity criterion in the bounty scope.

### Likelihood Explanation
`createDstEscrow` is a plain external function with no whitelist or fee-schema validation on `parameters`; any caller funding the correct native/token amount can set an arbitrary `parameters` byte string. No special privilege beyond being the destination-escrow creator/taker in the normal swap flow is required, and the bug is deterministic (not probabilistic), so likelihood is high whenever a taker supplies a malformed `parameters`.

### Recommendation
Validate `dstImmutables.parameters.length` in `createDstEscrow` (require it to be exactly the expected fixed size, e.g. `0x80` bytes for the four fee fields, or `0` if fees are unused) before deploying/funding the clone, and/or make `EscrowDst._withdraw` tolerant of a missing/empty `parameters` blob (treat fee amounts as zero) instead of reverting, so a malformed length cannot brick both withdrawal entrypoints.

### Proof of Concept
1. Attacker (any address) calls `createDstEscrow{value: safetyDeposit (+amount if native)}` with `dstImmutables.parameters = hex"00"` (1 byte) for a real order's `hashlock`/`maker`/`amount`, matching test helpers such as [8](#0-7)  but truncating `parameters`.
2. Escrow deploys and is funded normally (native/token checks in `createDstEscrow` don't inspect `parameters`).
3. After `DstWithdrawal` starts, the maker calls `withdraw(secret, immutables)` with the correct secret — reverts with `IndexOutOfRange` inside `integratorFeeAmountCd()`.
4. After `DstPublicWithdrawal` starts, any access-token holder calls `publicWithdraw(secret, immutables)` — reverts identically, since it calls the same `_withdraw()`.
5. Funds remain in the escrow until `DstCancellation`, at which point only the taker can reclaim them via `cancel()`, leaving the maker without the destination-side payout despite a valid secret. [9](#0-8)

    function hash(IBaseEscrow.Immutables calldata immutables) internal pure returns(bytes32 ret) {
        // Compute the EIP-712 hash for the immutables struct
        bytes calldata parameters = immutables.parameters;
        assembly ("memory-safe") {
            let ptr := mload(0x40)

            // Copy immutables.parameters to memory and compute its hash
            calldatacopy(ptr, parameters.offset, parameters.length)
            let parametersHash := keccak256(ptr, parameters.length)

            calldatacopy(ptr, immutables, IMMUTABLES_SIZE)
            mstore(add(ptr, IMMUTABLES_LAST_WORD), parametersHash)
            ret := keccak256(ptr, IMMUTABLES_SIZE)
        }
    }
