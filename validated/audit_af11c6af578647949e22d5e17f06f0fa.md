### Title
External Initiator credentials bypass per-job binding and can trigger `RunJobV2` for any job ID via `POST /v2/jobs/:ID/runs` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` authenticates any valid EI access-key/secret pair and unconditionally injects a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` into the Gin context, with no reference to which job the EI is associated with. `PipelineRunsController.Create` then only checks `auth.GetAuthenticatedUser(c)` ("isUser") to decide whether to allow triggering a run by integer job ID — a check that is satisfied by both real session/token users and by EI-authenticated requests, since both populate the same `SessionUserKey`. As a result, holding any single EI credential lets an attacker call `RunJobV2` for arbitrary job IDs, regardless of which job the EI was created for.

### Finding Description
- `AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) looks up the initiator solely by `access_key` via `FindExternalInitiator` [1](#0-0)  and, on a successful secret hash comparison, sets:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [2](#0-1) 
This makes `GetAuthenticatedUser(c)` return `(user, true)` for EI-authenticated requests exactly as it would for a real logged-in "Run" role user [3](#0-2) .

- The route is registered in the `userOrEI` group, which accepts `AuthenticateExternalInitiator` OR token OR session auth, gated only by `RequiresRunRole`:
```go
userOrEI := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(),
    auth.AuthenticateExternalInitiator,
    auth.AuthenticateByToken,
    auth.AuthenticateBySession,
))
userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))
``` [4](#0-3) 
`RequiresRunRole` only checks `user.Role != UserRoleView` [5](#0-4) , so the fabricated EI "Run" user passes.

- Inside `PipelineRunsController.Create`, the only gate before calling `RunJobV2` with an attacker-supplied integer job ID is:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
``` [6](#0-5) 
Despite the comment "EIs not allowed," the code checks the *presence* of a `SessionUserKey`, not whether the caller authenticated via session/token vs. EI. Since EI auth sets the exact same key/type, `isUser` is `true` for EI callers too, and there is no call to `auth.GetAuthenticatedExternalInitiator(c)` to enforce any job/EI relationship at this layer.
- `RunJobV2` itself performs no initiator-to-job binding check either — it just looks the job up by ID and executes its pipeline spec [7](#0-6) .
- Historically, EI-to-job binding was expressed through Webhook job specs and external-initiator join tables (`external_initiator_webhook_specs`), but the `Webhook` job type has since been removed from job creation, and the UUID-based path in `Create` is explicitly rejected with `job.ErrJobTypeRemoved` [8](#0-7) . This leaves the integer-ID path as the only remaining way to trigger runs, and it has no equivalent binding check.

### Impact Explanation
An attacker who compromises or is issued a single EI access-key/secret pair (for any external initiator, tied to any or no job) can trigger `RunJobV2` for an arbitrary job ID on the node, not just jobs associated with their EI. This is an authorization-scoping bypass allowing unauthorized triggering of job execution ("unauthorized job run") — matching the "unauthorized job run" bounty class referenced in the question. However, `RunJobV2` immediately returns an error on secure/production builds (`build.IsProd()`):
```go
if build.IsProd() {
    return 0, errors.New("manual job runs not supported on secure builds")
}
``` [9](#0-8) 
This significantly limits real-world impact: on production Chainlink node builds this specific endpoint is a no-op regardless of caller identity. The exploitable window is limited to non-production/dev builds, where the lack of binding is real but the practical blast radius is reduced (dev nodes typically aren't running mainnet-critical jobs with real funds).

### Likelihood Explanation
Preconditions are minimal: possession of any one valid EI `AccessKey`/`Secret` pair is sufficient (no job/EI relationship required), and the target node must be running a non-production build (since `build.IsProd()` blocks the action otherwise). Given that in this codebase there is no per-user/per-EI multi-tenant ownership model over jobs — any authenticated Run/Edit/Admin-role user can already invoke this same endpoint for any job ID via session/token auth — the EI bypass does not grant a fundamentally new privilege beyond what any legitimately provisioned Run-role credential already has; it only extends that "any job" capability to EI credential holders as well, which is inconsistent with the comment's stated intent ("EIs not allowed") but not a novel privilege escalation relative to other credential types on the same route.

### Recommendation
- In `PipelineRunsController.Create`, distinguish EI-authenticated requests from real session/token users explicitly (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and reject if present, honoring the existing comment's intent), rather than relying on the shared `SessionUserKey` presence check.
- If EI-triggered runs by job ID are intended to be supported at all, reintroduce an explicit job-to-EI binding check (e.g., verify the EI is associated with the requested job) before calling `RunJobV2`.
- Consider removing the `AuthenticateExternalInitiator` method from the `userOrEI` group for the `/jobs/:ID/runs` route entirely, since the UUID/webhook-based binding mechanism this route depended on has already been removed (`job.ErrJobTypeRemoved`).

### Proof of Concept
Handler-level integration test plan (Go, using existing `cltest` helpers similar to `core/web/pipeline_runs_controller_test.go`):
1. Build the app with a non-prod build tag (as tests already run in this mode).
2. Create Job A with EI1 credentials never referenced in Job A's spec, and Job B (or reuse) with different/no EI.
3. Create two `bridges.ExternalInitiator` records (EI1, EI2) via `bridges.NewExternalInitiator`, persisted through `orm.CreateExternalInitiator`.
4. Using an HTTP client with only EI1's `AccessKey`/`Secret` headers (`static.ExternalInitiatorAccessKeyHeader`/`...SecretHeader`), `POST /v2/jobs/<JobA.ID>/runs` where Job A has no association to EI1.
5. Assert response is `200 OK` (or whatever success status `PipelineRunsController.Create` returns) with a valid `pipelineRun` resource, proving the EI1 credential triggered Job A despite no binding — expected/desired behavior would be `401`/`403`.
6. Repeat with EI2 credentials against the same Job A ID to show any EI can hit any job.
7. As a control, assert that supplying an invalid EI secret returns `401 Unauthorized` (confirms the auth layer itself works, isolating the bug to the missing binding check in `Create`).

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
