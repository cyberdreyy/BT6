### Title
Pending APR0 withdraw bucket permanently reverts `stopEpoch` after an APR-policy change - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the OpenClaw bug — where multiple accounts collapsed onto a shared webhook path and one configuration replaced/blocked another — `IdleCreditVault` collapses all APR=0 withdraw requests into a single global bucket (`apr0TotalPrincipal`) plus one per-user slot (`apr0Users[user].principalEpoch`). That shared bucket is only valid while `unscaledApr == 0`, but nothing prevents the honest manager/CDO from changing the APR while the bucket is non-empty. Once `unscaledApr != 0`, `prepareStopEpochWithApr0` reverts unconditionally, and since that function is the *only* code path that can clear `apr0TotalPrincipal`, `stopEpoch` becomes uncallable until the APR is manually flipped back to zero — freezing the epoch, all deposits, and all pending withdraw claims.

### Finding Description
When a user calls `IdleCDOEpochVariant.requestWithdraw` while `unscaledApr == 0` and the pool is not closed, `IdleCreditVault.requestWithdraw` routes the request into `_requestWithdrawApr0`, which increments the shared `apr0TotalPrincipal` aggregate and records a single `principalEpoch` slot per user [1](#0-0) [2](#0-1) .

At the next `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which contains a fail-closed check:

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
``` [3](#0-2) 

The single shared bucket conflates two different policy regimes: requests created under an APR=0 epoch remain in `apr0TotalPrincipal` even after `setAprsWithBuffer` (callable any time by the CDO or manager) moves the vault to a non-zero APR. There is no migration, per-epoch bucket, or escape hatch — `apr0TotalPrincipal = 0` is only reachable *past* the revert [4](#0-3) . Meanwhile `unscaledApr` is free-running storage set independently by `setAprsWithBuffer` [5](#0-4) .

Attack sequence (buffer phase, APR0 mode):

1. Vault runs an epoch with `unscaledApr == 0`. Epoch ends; buffer begins.
2. Attacker (any KYC'd lender with tranche tokens) calls `cdoEpoch.requestWithdraw(...)`. Funds route to `_requestWithdrawApr0`; `apr0TotalPrincipal` becomes `> 0`.
3. Epoch lifecycle proceeds: manager (honest) sets a non-zero APR for the next epoch via `setAprsWithBuffer` / `startEpoch` — a routine configuration change.
4. At epoch end, `stopEpoch` → `prepareStopEpochWithApr0` → `apr0TotalPrincipal != 0 && unscaledApr != 0` → `revert NotAllowed()`. Every subsequent `stopEpoch` reverts identically.

The invariant broken is liveness of the epoch state machine: a single unprivileged withdraw request makes `stopEpoch` unconditionally revert under a legitimate APR change. The cost is one normal `requestWithdraw` (tranche tokens are burned into a receipt; no capital is at risk for the attacker beyond the receipt itself).

### Impact Explanation
While `stopEpoch` reverts, `epochEndDate` never advances, `epochNumber` never increments, and the borrower is never forced to return funds. All active tranche holders cannot redeem (tranche value is locked in the lent-out position), and all pending withdraw receipts (normal + APR0 + instant) cannot mature because claims require `epochNumber > lastWithdrawRequest` [6](#0-5) . Recovery requires the honest owner/manager to notice and set `unscaledApr` back to 0 so `stopEpoch` can proceed — a temporary freezing of the entire pool TVL plus all pending receipts, proportional to however long the freeze persists, and repeatable: the attacker can re-arm it every time the vault is in APR0 mode before an APR change.

### Likelihood Explanation
- Attacker cost: one ordinary `requestWithdraw` during a buffer period in APR0 mode. No privileged role, no capital loss.
- Trigger condition: any APR transition from 0 to non-zero while an APR0 request is pending — a normal operator action, not adversarial.
- No existing guard stops it: the `unscaledApr != 0` revert is precisely the guard that fails closed instead of migrating the bucket; `defaultRecoveryFinalized`, KYC, and `_onlyIdleCDO` are all satisfied on this path.
- Mitigating factor: the freeze is temporary (reversible by restoring APR 0), so impact is DoS-with-recovery rather than permanent loss.

### Recommendation
In `prepareStopEpochWithApr0`, don't revert when `unscaledApr != 0`. Instead, settle the stale APR0 bucket at zero interest (they accrued under a 0-APR regime) and clear `apr0TotalPrincipal`, moving each user's principal to `settledPrincipal`, or settle lazily in `_settleApr0` with `apr0RateByEpoch` defaulting to 0 for epochs finalized under non-zero APR. Alternatively, gate `setAprsWithBuffer`/`setApr` to reject a 0→non-zero transition while `apr0TotalPrincipal != 0`, making the policy collision explicit at configuration time rather than at `stopEpoch`.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testApr0RequestBlocksStopEpochAfterAprChange() external {
  // assume vault configured with unscaledApr == 0, epoch 0 running
  _stopCurrentEpoch(); // enter buffer of epoch 1
  // attacker: KYC'd LP requests withdraw during buffer while unscaledApr == 0
  address attacker = makeAddr('attacker');
  _depositWithUser(attacker, 100e6, true);
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(0, address(AAtranche));
  assertGt(strategy.apr0TotalPrincipal(), 0);

  // honest manager starts next epoch with non-zero APR
  vm.prank(manager);
  strategy.setAprsWithBuffer(5e18, epochDuration, bufferPeriod); // unscaledApr = 5%
  vm.prank(manager);
  cdoEpoch.startEpoch();

  // epoch ends; borrower repays fully; stopEpoch still reverts forever
  vm.warp(block.timestamp + epochDuration + 1);
  vm.prank(manager);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.stopEpoch(0, 0);

  // repeat: still bricked
  vm.prank(manager);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.stopEpoch(0, 0);

  // pending receipt cannot mature: epochNumber never bumped
  vm.prank(attacker);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.claimWithdrawRequest();
}
```

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
