### Title
Node coordinator double-counts a flip-flopping signer's weight in both approval and rejection tallies - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` tracks per-block `responded_signers`, `total_weight_approved`, and `total_weight_rejected` in a shared `BlockStatus`. The guard that prevents a signer's weight from being counted twice is asymmetric between the `Accepted` and `Rejected` branches: the `Rejected` branch gates on `responded_signers.insert(slot_id)` (so a signer who already counted — in either direction — cannot add rejection weight again), but the `Accepted` branch only gates on `gathered_signatures.contains_key(&slot_id)`, never checking `responded_signers`. This lets a single signer slot contribute its weight to `total_weight_rejected` first, and later contribute the same weight to `total_weight_approved` as well, inflating the aggregated tallies beyond what the true, distinct set of accepting/rejecting signers actually represents.

### Finding Description
`BlockStatus` holds the per-block bookkeeping used by the miner to decide whether a block has crossed the 70% approval threshold or the >30% blocking-rejection threshold: [1](#0-0) 

On an `Accepted` message, weight is only guarded against `gathered_signatures`, and the slot is then unconditionally recorded into `responded_signers`: [2](#0-1) 

On a `Rejected` message, weight is only added if `responded_signers.insert(slot_id)` returns `true` — i.e. if the slot has never been recorded as "responded" before, in *either* direction: [3](#0-2) 

This creates an asymmetric ordering dependency, exactly analogous to the whitelist bug where an unchecked/ungated `add` silently let one path corrupt state that a different path was correctly protecting:

- Accept → Reject: the second message (`Rejected`) is blocked from adding weight because `responded_signers` already contains the slot from the earlier `Accepted` call. Correctly single-counted.
- Reject → Accept: the second message (`Accepted`) is *not* blocked, because the `Accepted` branch never consults `responded_signers`, only `gathered_signatures` (which is empty for this slot since the signer never accepted before). The signer's weight is added a second time, now into `total_weight_approved`, while the earlier addition to `total_weight_rejected` is never reversed.

A single StackerDB slot can legitimately be overwritten by its owning signer across polling iterations of the listener's loop (`for (slot_id, _pk, message) in messages.into_iter()` inside the polling loop), so one signer sending first a `Rejected` chunk and later an `Accepted` chunk for the same `signer_signature_hash` is a normal, single-signer, no-majority-required sequence of StackerDB writes — no other signer's key or cooperation is required.

### Impact Explanation
The result is that `total_weight_approved + total_weight_rejected` can exceed `total_weight` for a single block, meaning the coordinator's threshold arithmetic (`total_weight_approved >= self.weight_threshold` and `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight`) in `SignerCoordinator`'s wait loop is being fed a value that no longer reflects the true, distinct-signer approval/rejection weight: [4](#0-3) 

This is the "aggregated-weight vs verified-accepts" equality break named in the analog rules: the coordinator's aggregated `total_weight_approved` can be pushed toward (or past) the signing threshold using weight from a signer whose only genuine, still-current opinion may be a rejection, letting a block accumulate an approval tally that does not correspond to that many genuinely-approving, distinct signers at that moment. Depending on how close the vote is, this can let the miner treat a block as having reached the 70% weight threshold when the real, current distinct-signer approval weight is lower — a concrete case of "an aggregated weight not equal to verified accepts."

### Likelihood Explanation
Reachable by any single registered signer (regardless of its own weight) simply by writing two chunks to its own StackerDB slot in sequence — first a `Rejected` `BlockResponse` and then an `Accepted` `BlockResponse` for the same block — which requires no majority, no other signer's key, and no auth token. It only requires that the coordinator's polling loop observe both writes across two polling iterations, which is a normal occurrence, not an unusual timing race.

### Recommendation
Make the `Accepted` branch check the same `responded_signers` set the `Rejected` branch uses (or track a single authoritative "current vote" per slot, e.g. an enum `Accepted`/`Rejected` in a `BTreeMap<u32, Vote>`) so that a state transition from reject to accept (or vice versa) correctly moves the signer's weight from one tally to the other, rather than allowing an `insert`/`contains_key` mismatch to add it to both. Concretely: when a slot that is present in `responded_signers` (from a previous rejection) sends an `Accepted` message, subtract its weight from `total_weight_rejected` before adding it to `total_weight_approved` (and symmetrically for accept→reject), keeping the two tallies mutually exclusive per slot at all times.

### Proof of Concept
1. Reward set includes signer `S` at slot `k` with weight `w`.
2. `S` writes an `Accepted` chunk is not sent yet; `S` writes a `Rejected` `BlockResponse` chunk for block `B` to its slot. Coordinator observes it: `responded_signers.insert(k) == true` → `total_weight_rejected += w`. [3](#0-2) 
3. Before the block is finalized as globally rejected, `S` overwrites its slot with an `Accepted` `BlockResponse` for the same block `B`. Coordinator observes it: `gathered_signatures.contains_key(k) == false` (no prior accept) → `total_weight_approved += w`, and `responded_signers.insert(k)` is now a no-op (already present) but this does not stop the approved-weight addition, which was gated only on `gathered_signatures`. [2](#0-1) 
4. `S`'s weight `w` is now present in both `total_weight_rejected` and `total_weight_approved` simultaneously — the two tallies together exceed `total_weight` by `w`, corrupting the threshold arithmetic consumed in `SignerCoordinator::wait_for_signatures`. [4](#0-3)
