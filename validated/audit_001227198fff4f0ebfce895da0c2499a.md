### Title
Loss-adjusted withdraw receipts can be re-claimed at par after a second withdraw request orphans the haircut epoch - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
When a stop epoch realizes a loss (`stopEpochWithDuration` → `collectWithdrawFunds` with `_amount < pendingBasis`), the unfunded part of pending withdraw receipts is converted into a per-epoch haircut via `lossRecoveryPriceByEpoch[epochNumber]` [1](#0-0) . The claim path for such receipts, `_claimLossAdjustedWithdrawRequest`, looks up the haircut epoch exclusively via `lastWithdrawRequest[_user]` [2](#0-1) . If the same user makes a second withdraw request in a later epoch before claiming, `lastWithdrawRequest` is overwritten and the haircut receipt at the loss epoch is never cleared — yet its amount remains in the aggregate `withdrawsRequests[_user]`, which `_claimFundedWithdrawRequest` later pays out at full par value [3](#0-2) . The user thus receives both the funded loss-adjusted portion accounting-wise ignored and the full unhaircutted principal, draining underlying that belongs to other claimants.

### Finding Description
The withdrawal lifecycle stores receipts in two places: the per-epoch map `withdrawsRequestsByEpoch[_user][epoch]` and the aggregate `withdrawsRequests[_user]` [4](#0-3) . On a loss stop, `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores only `lossRecoveryPriceByEpoch[epochNumber]` — the shortfall exists only as a price, not as an adjustment to the stored receipt amounts [5](#0-4) . Correct settlement therefore depends on `_claimLossAdjustedWithdrawRequest` clearing the loss-epoch receipt before `_claimFundedWithdrawRequest` pays the aggregate.

The clearing function chooses the epoch to clear as `lastWithdrawRequest[_user]` [6](#0-5) . `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` on every new request [7](#0-6) . So the sequence:

1. Epoch N (buffer): user requests withdraw of amount `W`. `withdrawsRequestsByEpoch[u][N] = W`, `withdrawsRequests[u] = W`, `lastWithdrawRequest[u] = N`.
2. `stopEpochWithDuration` ends epoch N with a loss: borrower funds only `W * r`; `lossRecoveryPriceByEpoch[N] = r`, `pendingWithdraws = 0`. Only `W * r` underlying was pulled into the vault [8](#0-7) .
3. Epoch N+1 (buffer): user requests another withdraw `W2`. `lastWithdrawRequest[u] = N+1`, `withdrawsRequests[u] = W + W2`.
4. User calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = N+1`, `lossRecoveryPriceByEpoch[N+1] = 0`, returns 0 without clearing epoch N [9](#0-8) .
5. `_claimFundedWithdrawRequest` reverts while `epochNumber <= N+1` [10](#0-9) , but after the next `stopEpoch` (`epochNumber = N+2`) it pays `normalAmount = W + W2` in full via `_transferFundedClaim` [3](#0-2) .

The epoch-N haircut is permanently unreachable: no later code path ever consults `lossRecoveryPriceByEpoch[N]` for this user, and `_clearWithdrawClaimForEpoch` is only invoked with `claimEpoch = lastWithdrawRequest` or the default epoch [11](#0-10) .

### Impact Explanation
Direct theft / insolvency. The vault only received `W * r` underlying for the epoch-N receipt, but pays `W`. The excess `W * (1 - r)` is taken from underlying held in the strategy reserved for other users' funded claims, instant-withdraw claims, or the default recovery reserve, breaking the one-receipt-one-payout and solvency invariants. Loss scales with the haircut size; a large realized loss on a large receipt can drain a multiple of the funded amount. Any tranche-token holder (KYC-passed lender) can execute this with two `requestWithdraw` calls and one `claimWithdrawRequest` — no privileged role needed.

### Likelihood Explanation
Requires a realized loss via `stopEpochWithDuration` (manager-called but economically driven by borrower shortfall — the attacker merely sequences around it) and the same user requesting again in a subsequent buffer epoch before claiming. Re-requesting before claiming is an explicitly supported flow per the code comments [12](#0-11) . All guards (`_onlyIdleCDO`, epoch gating, recovery price storage) operate correctly — the flaw is that the loss-epoch receipt is never keyed by anything other than `lastWithdrawRequest`, which is mutable.

### Recommendation
Track the haircut epoch per receipt rather than deriving it from `lastWithdrawRequest`. Concretely: when `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]`, the claim path should iterate/check the user's actual receipt epochs (e.g., check `lossRecoveryPriceByEpoch` for each epoch with a nonzero `withdrawsRequestsByEpoch[_user][e]`, or store a per-user `lossEpochByUser` set at request time), and `_claimFundedWithdrawRequest` must subtract any receipt basis belonging to an epoch with a nonzero `lossRecoveryPriceByEpoch` from the par payout.

### Proof of Concept
Foundry fork PoC sketch (mirror `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `stopEpochWithDuration`):

```solidity
function testLossAdjustedReceiptOrphanedBySecondRequest() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    address user = makeAddr('attacker');
    uint256 amount = 100_000 * ONE_SCALE;
    _depositWithUser(user, amount, true);

    // Epoch 0 buffer: request full withdraw
    vm.prank(user);
    uint256 w1 = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // stopEpochWithDuration with a 50% loss -> lossRecoveryPriceByEpoch[0] = 0.5e18
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, w1 / 2);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, epochDuration, w1 / 2); // funds only half

    // deposit again to have tranche balance for second request
    _depositWithUser(user, amount, true);

    // Epoch 1 buffer: second request overwrites lastWithdrawRequest
    vm.prank(user);
    uint256 w2 = cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch()); // epochNumber = 2

    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    // BUG: pays w1 + w2 at par; expected was w1 * 0.5 + w2
    assertEq(underlying.balanceOf(user) - balPre, w1 + w2);
    // excess stolen: w1 / 2 drained from vault reserves of other claimants
}
```

Note: I could not fully trace `_transferFundedClaim`'s reserve checks within the available iterations; if it draws only from the strategy's own underlying balance (which it must, being a plain transfer), the over-claim directly reduces funds backing other pending claims, confirming insolvency rather than a revert.

    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    if (claimBasis == 0) return amount;

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
