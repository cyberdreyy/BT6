### Title
`debug/vars` endpoint requires only a valid session, no role check, exposing runtime `expvar` data to view-only users - ([File: core/web/router.go])

### Summary
`debugRoutes` in `core/web/router.go` mounts `GET /debug/vars` behind only `auth.Authenticate(..., auth.AuthenticateBySession)`, with no `auth.RequiresAdminRole`/`RequiresEditRole` wrapper unlike almost every other sensitive route in `v2Routes`. Any authenticated user, including one with the lowest "view" role, can reach the standard Go `expvar` handler and receive runtime state (memstats, cmdline, GC stats, and any custom-published vars).

### Finding Description [1](#0-0) 

`debugRoutes` registers the route group with a single middleware, `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)`, and directly attaches the third-party `expvar.Handler()` with no additional role gate. Contrast this with `v2Routes` (e.g. lines 251-254, 276-281, 318-320, 340-342), where nearly every state-exposing or key-management endpoint is additionally wrapped in `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole`. `debugRoutes` has no such wrapper, so a session established via `POST /sessions` with any role (including `view`) satisfies the middleware and reaches the handler.

I searched the codebase for `expvar.Publish`/`expvar.NewString`/`expvar.NewMap` calls and found none registered in this repo, meaning the exposed data set is limited to the Go runtime's built-in `expvar` variables (`cmdline`, `memstats`) rather than any Chainlink-specific custom secret variable explicitly published via `expvar`. I could not confirm any code path that publishes decrypted key material or environment secrets directly into `expvar`; this would need further verification (e.g., a Devin session with full-repo access) since the index may not include all files.

### Impact Explanation
The exact vulnerability documented is: **missing role/authorization exactness on the `/debug/vars` route** — an unprivileged "view" role session can access an endpoint that should logically be restricted to an elevated role, consistent with the pattern used everywhere else in the router. However, based on what is discoverable in this codebase, the concrete data exposed via Go's built-in `expvar.Handler()` is limited to runtime metadata (`cmdline`, `memstats`) rather than confirmed decrypted key material or secrets — no `expvar.Publish` calls surfacing secret data were found. This still constitutes an authorization-exactness gap (information disclosure of internal process/runtime state to a lower-privileged principal than intended) but the "key material/secrets disclosure" severity claimed in the question is not substantiated by concrete code evidence.

### Likelihood Explanation
Any user who can authenticate via `POST /sessions` (even a view-only account) can immediately reach `GET /debug/vars` with no further checks. This is fully reproducible and requires no elevated privilege — just a valid session cookie.

### Recommendation
Wrap the `/debug/vars` route in `debugRoutes` with `auth.RequiresAdminRole` (matching the pattern used for other sensitive/internal endpoints like `/keys/*/export`, `/log` PATCH, and `pprof` routes accessed via `metricRoutes`, which sit under `authv2` and thus already require an authenticated v2 role context). At minimum, restrict to admin/edit roles rather than any authenticated session.

### Proof of Concept
Go handler-level integration test (in `core/web` test package, following patterns in existing router tests):
1. Start the app/test server via the existing `web.NewRouter` / `cltest` test harness.
2. Create two users: one with `admin` role, one with `view` role (using existing test helpers for user/session creation).
3. `POST /sessions` with the `view`-role user's credentials to obtain a session cookie.
4. `GET /debug/vars` with that session cookie attached.
5. Assert the response status is `200 OK` and the body is valid JSON containing `cmdline` and `memstats` keys — demonstrating that a view-role session can access the debug endpoint.
6. Add a table-driven assertion documenting the expected fix: after adding `auth.RequiresAdminRole`, the same request from a `view`-role session should return `403 Forbidden`, while an `admin`-role session should still return `200 OK`.
