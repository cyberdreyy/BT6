### Title
Replay of previously-seen signed legacy user messages within the allowed age window re-triggers capability execution - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`(h *handler).HandleLegacyUserMessage` only rejects messages whose `payload.Timestamp` is older than `MaxAllowedMessageAgeSec`; it never tracks or rejects previously-seen `MessageId` values. Any valid signed `api.Message` captured by an attacker (e.g. the requesting user or a network observer) can be resubmitted verbatim to the gateway any number of times while its timestamp remains inside the allowed window, causing the same capability request to be dispatched to the DON again.

### Finding Description
`HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) performs the following checks on an incoming `api.Message`:
1. Decodes `webapicap.TriggerRequestPayload` from `body.Payload`.
2. Rejects if `payload.Timestamp == 0`.
3. Rejects only if `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` (staleness check) — `core/services/gateway/handlers/capabilities/handler.go:372-383`.
4. Rejects unsupported methods.
5. Converts the message to a JSON-RPC request and stores a callback keyed by `msg.Body.MessageId` in `h.savedCallbacks` — `core/services/gateway/handlers/capabilities/handler.go:411-414` — simply overwriting any existing entry for that key, with no check for prior existence.
6. Forwards the request to every DON member via `don.SendToNode` — `core/services/gateway/handlers/capabilities/handler.go:416-419`.

There is no code path anywhere in this function, or in `api.Message.Validate()` (`core/services/gateway/api/message.go:54-88`) or in `common.ValidatedRequestFromMessage` (`core/services/gateway/handlers/common/message_util.go:82-105`), that maintains a persistent set of already-processed `MessageId`s (or of `(Sender, MessageId)` / `(Sender, Timestamp)` pairs) to reject duplicates. The signature covers `MessageId`, `Method`, `DonId`, `Receiver`, and `Payload` (`GetRawMessageBody`, `core/services/gateway/api/message.go:136-146`), so a byte-for-byte replay of a previously captured message is a perfectly valid signature — it is not a forgery, it is a legitimate resubmission of prior wire data. The only gate against resubmission is the timestamp/age check, which by design permits replays for the entire configured window (`MaxAllowedMessageAgeSec`, default not shown here but configurable, `core/services/gateway/handlers/capabilities/handler.go:63-65`).

Because `h.savedCallbacks` is keyed by `MessageId` and entries are only removed when a trigger response is later received (`handleWebAPITriggerMessage`, `core/services/gateway/handlers/capabilities/handler.go:148-162`) or pruned after `CallbackMaxAgeSec`, a second submission of the same message before the first callback is consumed will simply overwrite the map entry and be dispatched to the DON again — no rejection occurs.

### Impact Explanation
This allows an attacker who has observed one valid signed capability-trigger message (e.g., their own prior legitimate request, or one captured via a non-TLS hop, logs, or client-side leakage) to resubmit it to the gateway multiple times within the configured age window, causing the DON to re-execute the underlying web-API trigger/target/compute capability multiple times for a single authorized request. Depending on what the capability does (e.g., HTTP callouts, workflow triggers, or capabilities that consume paid/rate-limited resources), this can result in duplicate side effects, resource exhaustion, or unintended repeated invocation of downstream jobs/workflows — mapping to an "unauthorized job run" / duplicate-execution impact class rather than fund theft or credential disclosure.

### Likelihood Explanation
No special privilege is required beyond obtaining one previously valid signed message (which the attacker may already legitimately possess as the original sender, since nothing prevents the sender itself from replaying its own message). The exploit is trivially repeatable: simply resend the identical JSON payload to the gateway endpoint any number of times before `MaxAllowedMessageAgeSec` elapses. This is a deterministic, low-effort attack requiring no cryptographic bypass.

### Recommendation
Maintain a bounded, time-windowed set (or persistent cache) of already-processed `(Sender, MessageId)` pairs — or a `MessageId`+`Timestamp` combination — in `HandleLegacyUserMessage`, and reject/return an error for messages whose `MessageId` (or the tuple) has already been seen, independent of whether the timestamp is still within the allowed window. Reuse the existing `savedCallbacks` map (or a dedicated dedup store) to check-and-reject before creating/overwriting the callback entry, and prune it purely by time rather than allowing silent overwrite.

### Proof of Concept
Go handler-level test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a valid signed `api.Message` with `Method = MethodWebAPITrigger`, a `TriggerRequestPayload` with `Timestamp = time.Now().Unix()`, and a fixed `MessageId`.
2. Set up a `handler` with a mock `handlers.DON` whose `SendToNode` records call counts, and `HandlerConfig.MaxAllowedMessageAgeSec` large enough that both submissions remain "fresh".
3. Call `h.HandleLegacyUserMessage(ctx, msg, callback1)` — assert `don.SendToNode` was called once per DON member and the callback was registered under `msg.Body.MessageId`.
4. Call `h.HandleLegacyUserMessage(ctx, msg, callback2)` again with the exact same `msg` (same signature, same `MessageId`, same `Timestamp`) before any trigger response is received.
5. Assert (current behavior, demonstrating the bug): `don.SendToNode` is called a second time for the same `MessageId`/payload and no error/rejection is returned — i.e., the handler does not detect message-id reuse and dispatches the capability again.
6. Desired assertion after the fix: the second call should return an error (e.g., "message id already processed") and `don.SendToNode` should not be invoked a second time for that `MessageId`.
