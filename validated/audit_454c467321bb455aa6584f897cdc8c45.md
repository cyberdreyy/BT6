### Title
`createDstEscrow` accepts unvalidated fee parameters that cause `EscrowDst.withdraw()` to permanently revert via checked-arithmetic underflow - (File: contracts/BaseEscrowFactory.sol)

### Summary
`BaseEscrowFactory.createDstEscrow()` deploys a destination escrow using an arbitrary `IBaseEscrow.Immutables` struct supplied directly by the caller (any unprivileged taker), including the `parameters` field that encodes `protocolFeeAmount` and `integratorFeeAmount`. Unlike the source-side `_postInteraction()` path, which explicitly guards `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();`, `createDstEscrow()` performs no equivalent check. `EscrowDst._withdraw()` then computes `immutables.amount - integratorFeeAmount - protocolFeeAmount` using Solidity 0.8 checked arithmetic, which reverts if the fee sum exceeds `amount`. Because `immutables` (and therefore the deployed escrow's committed parameters) are fixed by the deterministic CREATE2 salt at deployment time, this underflow condition is permanent and cannot be repaired — `withdraw()` and `publicWithdraw()` will always revert.

### Finding Description [1](#0-0) 
`createDstEscrow` takes `dstImmutables` fully from calldata, only checking `msg.value` against `safetyDeposit`/`amount` and the cancellation-timestamp ordering. It never validates that `protocolFeeAmount() + integratorFeeAmount() < amount`.

Contrast with the source path validation: [2](#0-1) 

The unchecked fee parameters are consumed later in `EscrowDst._withdraw()` with plain Solidity 0.8 subtraction: [3](#0-2) 

`immutables.amount - integratorFeeAmount - protocolFeeAmount` reverts (checked-arithmetic underflow) whenever `integratorFeeAmount + protocolFeeAmount > immutables.amount`. This mirrors the Malt/Uniswap bug class exactly: a value computed elsewhere without bounds checking is later consumed by Solidity ≥0.8 checked arithmetic, causing an unconditional revert of the core operation (`stabilize()` there, `withdraw()`/`publicWithdraw()` here).

Because the escrow's address and stored immutables (including `parameters`) are fixed via `Create2`/`Clones.cloneDeterministic` at deploy time and validated on every call via `onlyValidImmutables` (`immutables.hash()` must match), there is no way to "fix" a bad `parameters` value post-deployment — `withdraw` is permanently broken for that specific escrow instance.

`cancel()` on `EscrowDst`, by contrast, does not subtract fees and instead returns the *entire* `immutables.amount` to `immutables.taker` (the resolver who funded it), not to the maker: [4](#0-3) 

### Impact Explanation
Any unprivileged caller of `createDstEscrow` (the function has no whitelist/access-control modifier and is reachable by any account willing to fund the safety deposit/amount, per `contracts/interfaces/IEscrowFactory.sol` `createDstEscrow`) can construct `dstImmutables.parameters` with `protocolFeeAmount + integratorFeeAmount >= amount`. This permanently disables `withdraw()`/`publicWithdraw()` on that escrow (checked-arithmetic revert), so the maker can never receive their destination-chain funds through the intended withdrawal path. Only `cancel()`/`publicCancel()` remain available after the cancellation timelock, and those return funds to the *taker*, not the maker — meaning the maker is prevented from ever receiving payment on the destination chain for that swap instance, i.e. a freezing of the maker's expected destination funds during the live swap lifecycle. This fits the "temporary freezing of funds during the live swap lifecycle" (or permanent freezing, since the specific escrow can never validly complete a `withdraw`) impact tier.

### Likelihood Explanation
`createDstEscrow` is a normal, unprivileged, publicly reachable entry point in the intended live-swap flow (any resolver calls it to fund the destination escrow), and the caller fully controls the `Immutables.parameters` bytes that are ABI-decoded later for fee amounts, with zero validation against `amount`. No special privileges, governance, or malicious infrastructure assumptions are required — a single malicious or buggy resolver/taker performing this call in the normal flow triggers the condition deterministically (this is a straightforward parameter-crafting attack, not a probabilistic/race condition).

### Recommendation
Add the same fee-sum validation used in `_postInteraction` to `createDstEscrow`:
```solidity
(uint256 integratorFeeAmount, uint256 protocolFeeAmount) = (
    dstImmutables.integratorFeeAmount(),
    dstImmutables.protocolFeeAmount()
);
if (integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
placed before deployment in `createDstEscrow`, mirroring the guard already present in `_postInteraction` at [5](#0-4) .

### Proof of Concept
1. Attacker (any account) calls `escrowFactory.createDstEscrow{value: safetyDeposit + amount}(dstImmutables, srcCancellationTimestamp)` where `dstImmutables.parameters = abi.encode(protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)` is crafted such that `protocolFeeAmount + integratorFeeAmount >= amount` (e.g., `protocolFeeAmount = amount`, `integratorFeeAmount = 0`).
2. `createDstEscrow` performs no fee-sum check (see [1](#0-0) ) and deploys the escrow, transferring `amount` tokens/native currency into it.
3. Once the withdrawal window opens, the maker (or anyone with the secret) calls `withdraw`/`publicWithdraw`. Inside `_withdraw`, `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` underflows and reverts under Solidity 0.8 checked arithmetic (see [6](#0-5) ).
4. Every subsequent call to `withdraw`/`publicWithdraw` for this escrow instance reverts identically, since `immutables` (and thus fee parameters) are fixed by the deployment salt and cannot be altered. Only `cancel`, which pays the *taker* (not the maker), remains functional after the cancellation timelock.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);

        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
