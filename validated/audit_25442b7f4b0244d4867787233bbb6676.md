### Title
Height-only equality check in `check_block_builds_on_highest_block_in_tenure` lets a miner point a new block's parent at a non-canonical sibling at the same height - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
`check_block_builds_on_highest_block_in_tenure` (the node-side gate the signer relies on when it calls `Self::check_block_has_valid_parent` inside `BlockProposal::validate`) is supposed to prove that a proposed block's parent is *the* highest block of a tenure. Instead of comparing block identity (`StacksBlockId`), it compares only `chain_length` (block height): [1](#0-0) 

This is the same bug class as the Lambo `directionMask` finding: a full-identity check (which pool / which parent) is replaced by a partial/proxy check (MSB bit / height only), letting an attacker substitute a different-but-matching-partial-value target for the legitimate one.

### Finding Description
`find_highest_known_block_header_in_tenure` explicitly documents that ties can occur: [2](#0-1) 

and its underlying query groups by `burn_view` and can return multiple `StacksHeaderInfo` rows at the same `block_height` for one tenure ("If there are ties at a given burn view, they will both be returned"), later filtered down by canonical-burn-view membership in `get_highest_canonical_block_header_from_candidates`: [3](#0-2) 

That means the chainstate DB can legitimately hold two different, distinctly-hashed Nakamoto blocks in the same tenure at the same `chain_length` (e.g. a burn-view fork/sibling that produced a competing block that a node stored but that is not the block the rest of the network converged on for that height). `check_block_builds_on_highest_block_in_tenure` then determines "is this proposal's parent the tenure's tip?" purely by comparing `parent_header.anchored_header.height() != highest_header.anchored_header.height()`. If a miner supplies a `parent_block_id` that resolves (via `get_block_header`) to the *other*, non-canonical sibling block at the same height rather than the true highest/canonical one, this equality check still passes, because it never compares `parent_block_id` against `highest_header`'s `StacksBlockId`/`index_block_hash()`.

This is exactly the "MSB-only" pattern from the reference finding: the correct invariant is "the parent must equal the actual highest known block" (an identity equality), but the code enforces only a necessary-but-not-sufficient proxy ("same height"), letting an attacker substitute an unintended, differently-hashed block that happens to satisfy the weaker condition.

Downstream, this validation result (`BlockValidateOk`/`Reject`) is exactly what the signer's `handle_block_validate_response` trusts to decide whether to sign the proposal — the signer does not itself re-derive "highest block in tenure" via full block-ID identity in this specific path; it relies on the node's `postblock_proposal` verdict for this check. A pre-committed/older sibling artifact in `nakamoto_block_headers` (which can persist from forks, stalled proposals, or burn-view races) is enough raw material for the substitution.

### Impact Explanation
If exploitable, this breaks the "approved-parent vs canonical" equality: a signer could be induced to validate-and-sign a block whose declared parent is not actually the tenure's canonical/highest block, but a different, non-canonical sibling block with a matching height. That is a Critical-class outcome per the rubric — a signer being led to accept (and thus sign) a block built on a non-canonical parent, i.e. a non-canonical/conflicting block getting a valid signature.

### Likelihood Explanation
A single miner (who controls what tenure/parent they declare, and who may have caused or observed a same-height sibling in a tenure from a prior fork/race) can supply the crafted `parent_block_id` in a `BlockProposal` without needing cooperation from any other signer, majority control, or private keys beyond their own mining key. The precondition — the chainstate holding two Nakamoto headers at the same height/tenure but different burn views — is explicitly acknowledged as a possible, non-degenerate state by the code's own comments ("If there are ties ... they will both be returned"), so it is not a contrived edge case but a documented possibility of the schema/query. That said, I was not able to fully trace, within the given iterations, whether `get_block_header` used in `check_block_builds_on_highest_block_in_tenure` combined with `get_highest_canonical_block_header_from_candidates`'s canonical-burn-view filtering fully forecloses the "wrong sibling accepted as parent" path in all cases (e.g., whether a non-canonical sibling parent would independently be rejected elsewhere, such as by `check_block_has_valid_tenure`'s canonical-fork check on the *tenure* consensus hash, which only validates the tenure ID, not the specific parent block within it). This residual uncertainty should be resolved by a background agent with test/execution access.

### Recommendation
Change `check_block_builds_on_highest_block_in_tenure` to compare full block identity, not just height:
```
if parent_header.index_block_hash() != highest_header.index_block_hash() {
    // reject
}
```
(or equivalently compare `StacksBlockId::new(&parent_header.consensus_hash, &parent_header.anchored_header.block_hash())` against the same for `highest_header`), so that a parent which merely shares a height with the tenure's true tip but is a different block is rejected as `InvalidParentBlock`.

### Proof of Concept
Not independently verified end-to-end in this pass (requires constructing a chainstate with two `nakamoto_block_headers` rows sharing `consensus_hash`/tenure and `block_height` but different `burn_view`/hash, then submitting a `BlockProposal` whose `parent_block_id` resolves to the non-canonical one, and observing that `check_block_builds_on_highest_block_in_tenure` returns `Ok(())` instead of `InvalidParentBlock`). Given the explicit "ties" comment in `get_highest_known_block_header_in_tenure_at_each_burnview`, and the height-only comparison, a background agent with test-execution access should:
1. Reproduce a same-height tenure fork (two `nakamoto_block_headers` rows, same `consensus_hash`, same `block_height`, differing `burn_view`).
2. Submit a `NakamotoBlock` proposal whose `parent_block_id` points at the non-canonical sibling.
3. Confirm whether `postblock_proposal::validate` (`check_block_has_valid_parent` → `check_block_builds_on_highest_block_in_tenure`) incorrectly returns `Ok`, and whether this verdict flows through to the signer's decision to sign.

    /// Get the first canonical block header in a vector of height-ordered candidates
    fn get_highest_canonical_block_header_from_candidates(
        sort_db: &SortitionDB,
        candidates: Vec<StacksHeaderInfo>,
    ) -> Result<Option<StacksHeaderInfo>, ChainstateError> {
        let canonical_sortition_handle = sort_db.index_handle_at_tip();
        for candidate in candidates.into_iter() {
            // if burn_view is None, then this is an epoch 2.x header, and since epoch 2.x tenure's correspond
            // to a single stacks block, we can use the miner's tenure sortition as a proxy for canonicity.
            let candidate_ch = candidate
                .burn_view
                .as_ref()
                .unwrap_or(&candidate.consensus_hash);
            let in_canonical_fork = canonical_sortition_handle.processed_block(candidate_ch)?;
            if in_canonical_fork {
                return Ok(Some(candidate));
            }
        }

        // did not find any blocks in candidates
        Ok(None)
    }
