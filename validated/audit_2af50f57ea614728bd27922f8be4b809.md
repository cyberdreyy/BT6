### Title
`IdleCreditVault.requestInstantWithdraw` accepts new instant-withdraw receipts after default finalization, minting a permanently unpayable receipt — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a verifier (`use_hint`) that accepts an input which should be rejected at an edge case. The analog is `requestInstantWithdraw` in `IdleCreditVault.sol`: it is the only receipt-creating entry point that does **not** gate on `defaultRecoveryFinalized`. After `finalizeDefaultRecovery` runs, `defaultRecoveryReserve` is set to the strategy's entire underlying balance, and `_transferFundedClaim` enforces `balance - reserve >= amount`. A post-default instant-withdraw request therefore mints the user a receipt that can never be paid, while the user's principal-bearing strategy tokens were already burned.

### Finding Description
- `requestWithdraw` explicitly handles the post-default state: it reverts if the user has pending requests and routes new requests into `postDefaultRequests`, which are paid from `defaultRecoveryReserve` at the already-haircut `defaultRecoveryPrice` (lines 247–257).
- `requestInstantWithdraw` (lines 356–375) has no `defaultRecoveryFinalized` branch at all. It burns the CDO's strategy tokens (`_burn(msg.sender, _amount)`), mints an equal receipt to the user, and increases `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws`.
- On claim, `claimInstantWithdrawRequest` (lines 380–393): since `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` is only true when `pendingInstantWithdraws != 0` *at finalization time* (`defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`, line 696), a request created **after** finalization skips `_claimDefaultedInstantWithdrawRequest` (its per-epoch entry `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` is 0, so it returns early at line 845). It then falls into `_burn(_user, amount)` and `_transferFundedClaim(_user, amount)`.
- `_transferFundedClaim` (lines 897–907) requires `balanceOf(this) - defaultRecoveryReserve >= _amount`. After finalization, `defaultRecoveryReserve` equals the recovery-priced basis that consumed essentially the full strategy balance (line 686–691), so `balance - reserve` is ~0 and every such claim reverts `NotAllowed()` forever.

The edge case — "receipt requested after default finalization" — is accepted (receipt minted, principal burned) when it should be rejected, exactly mirroring the advisory's "signature that should be rejected is accepted" shape.

### Impact Explanation
Any tranche-token holder who calls the CDO's instant-withdraw path after the vault's default has been finalized loses their entire requested amount: their strategy tokens are burned at the strategy, the CDO-side shares are burned, and the minted receipt is permanently unclaimable because the recovery-reserve guard in `_transferFundedClaim` blocks any funded payout. This is a permanent freezing/destruction of user principal with no recovery path (claims also cannot be rerouted into `postDefaultRequests`, since that path is only created inside `requestWithdraw`).

### Likelihood Explanation
Reachable whenever (a) the vault has defaulted and `finalizeDefaultRecovery` has executed, and (b) the CDO's `requestInstantWithdraw`/instant path remains callable post-default (the CDO does not pass `defaulted` state into the strategy call — the strategy is expected to enforce its own state machine, as `requestWithdraw` does). The attacker/victim is an ordinary tranche holder (unprivileged). Likelihood is bounded by how long the post-default window is open and whether users interact during it; there is no front-running or oracle requirement — it is a deterministic acceptance of an invalid-state request.

### Recommendation
Add the same post-default guard to `requestInstantWithdraw`:

```solidity
function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    if (defaultRecoveryFinalized) revert NotAllowed();
    ...
}
```

Alternatively, route post-default instant requests through `postDefaultRequests` with the haircut applied at request time, matching `requestWithdraw`. A revert is strictly safer because there is no funding source for new post-default instant receipts.

### Proof of Concept
Foundry fork-style sketch against the existing harness in `test/foundry/IdleCreditVault.t.sol`:

```solidity
function testInstantWithdrawAfterDefaultFinalizationFreezesFunds() external {
    // 1. Deposit and run an epoch
    idleCDO.depositAA(amountAA);
    _startEpochAndCheckPrices(0);

    // 2. Trigger borrower default and finalize recovery at a haircut
    _handleBorrowerDefaultAndFinalize(recoveredAmount); // sets defaultRecoveryFinalized, defaultRecoveryPrice, reserve = balance

    // 3. A different holder (or same) still holds tranche tokens; they request instant withdraw
    vm.roll(block.number + 1); // avoid same-block guard
    uint256 reqAmount = 1_000 * ONE_SCALE;
    idleCDO.requestInstantWithdraw(reqAmount); // burns holder tranche tokens, mints receipt

    // 4. Claim is permanently impossible: funded-claim guard reverts since balance == reserve
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    idleCDO.claimInstantWithdrawRequest();

    // Holder's principal is destroyed: strategy tokens burned, receipt unpayable.
}
```

Caveat I could not fully verify within the available index: whether `IdleCDOCreditVault`/`IdleCDOEpochVariant` independently reverts instant-withdraw requests once `defaulted()`/`defaultRecoveryFinalized` is set. If the CDO blocks the call upstream, the strategy-side omission is defense-in-depth rather than exploitable; the missing guard is still a real inconsistency with `requestWithdraw` and should be fixed regardless. If the CDO path is reachable post-default (the strategy's own state checks imply it is expected to be), the PoC demonstrates permanent loss of the requested principal.
