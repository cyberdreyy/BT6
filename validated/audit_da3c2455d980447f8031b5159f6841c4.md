### Title
Unchecked `program_id_index` indexing in `parse_ui_instruction`/`make_ui_partially_decoded_instruction` causes RPC-thread panic on malformed historical instruction data - ([File: transaction-status/src/lib.rs])

### Summary
`parse_ui_instruction` and its fallback helper `make_ui_partially_decoded_instruction` index `account_keys[instruction.program_id_index as usize]` (and `account_keys[i as usize]` for each account index) with no bounds check before ever calling `parse()`. `parse()` itself only validates bounds for `HashMap`/known-program lookups but relies on the caller having already resolved a valid `program_id`, so the panic-causing index happens strictly earlier, at line `transaction-status/src/lib.rs:118`, and again in the fallback path at line 102/106.

`AccountKeys` implements slice-style indexing via `solana_message`, which panics on out-of-range indices just like `Vec`/`[T]` indexing. Individual parsers such as `parse_bpf_loader`/`parse_token` explicitly guard against this ("Runtime should prevent this from ever happening" comment) by checking `instruction.accounts[..] as usize >= account_keys.len()` before indexing: [2](#0-1) [3](#0-2) 

but the top-level dispatcher `parse_ui_instruction` (and its `PartiallyDecoded` fallback) has no equivalent guard for `program_id_index`, and `account_keys` for the instruction accounts.

While the runtime sanitizes `CompiledInstruction`/`AccountKeys` relationships for *live* transactions, the historical `getTransaction` path reconstructs `CompiledInstruction` from data stored via lossy conversions such as `storage-proto/src/convert.rs`'s `From<generated::CompiledInstruction> for CompiledInstruction`, which copies `program_id_index`/`accounts` fields verbatim with zero validation: [4](#0-3) 

For versioned transactions using address-table lookups, the `AccountKeys` used at parse time is built from static keys plus `loaded_addresses` taken from the stored transaction meta. If the bigtable/blockstore-stored meta for a given historical entry lacks (or has truncated) `loaded_addresses` — e.g., older/legacy stored records, protobuf deserialization producing a default/empty `loaded_addresses`, or any code path constructing `AccountKeys` from only `message.static_account_keys()` — then `account_keys.len()` at reconstruction time can be smaller than it was when the instruction was originally sanitized by the runtime. In that mismatch case `instruction.program_id_index` (which validly pointed into the *loaded* address range at execution time) is out of range for the reconstructed `account_keys`, and `parse_ui_instruction` panics instead of falling back gracefully.

### Impact Explanation
A single unprivileged `getTransaction` (or `getConfirmedTransaction`/websocket historical equivalent) RPC call with `encoding: jsonParsed` against such a stored entry causes an unhandled Rust panic (`index out of bounds`) inside the JSON-RPC request-handling thread. Depending on whether that thread is wrapped in `catch_unwind`, this can crash the RPC-serving validator process or thread pool for a single client request — matching the "decoder panic" / real validator-process-crash-from-one-request bounty category. No consensus state is affected; the impact is scoped to RPC availability/crash.

### Likelihood Explanation
Requires a pre-existing malformed/legacy stored transaction entry (bigtable or blockstore) whose `program_id_index`/account index exceeds the `account_keys` length reconstructed for JSON parsing at query time — e.g. via missing/legacy `loaded_addresses` metadata for a versioned transaction. This is plausible for very old or externally-imported historical data but not reproducible from a freshly-sanitized live transaction, so likelihood depends on whether such malformed historical records can exist in a deployed bigtable/blockstore, which is unverified from the code alone.

### Recommendation
Add bounds checks in `parse_ui_instruction` and `make_ui_partially_decoded_instruction` before indexing into `account_keys`, returning a safe fallback (e.g., `UiInstruction::Parsed(UiParsedInstruction::PartiallyDecoded(...))` with a placeholder/empty program id, or a new "malformed instruction" variant) instead of panicking, mirroring the guard pattern already used in `parse_bpf_loader`/`parse_token`.

### Proof of Concept
```rust
// transaction-status/src/lib.rs (new test)
#[test]
fn test_parse_ui_instruction_oob_program_id_index_does_not_panic() {
    use solana_message::{AccountKeys, compiled_instruction::CompiledInstruction};

    let account_keys_vec = vec![Pubkey::new_unique(), Pubkey::new_unique()];
    let account_keys = AccountKeys::new(&account_keys_vec, None);

    // Manually constructed instruction with an out-of-range program_id_index,
    // simulating a reconstructed historical CompiledInstruction whose
    // account_keys length no longer matches what the runtime originally sanitized.
    let bad_instruction = CompiledInstruction {
        program_id_index: 5, // out of bounds: account_keys.len() == 2
        accounts: vec![0, 1],
        data: vec![],
    };

    // Expected: graceful PartiallyDecoded fallback, not a panic.
    let result = std::panic::catch_unwind(|| {
        parse_ui_instruction(&bad_instruction, &account_keys, None)
    });
    assert!(result.is_ok(), "parse_ui_instruction panicked on OOB program_id_index");
}
```
A fuzz harness would generate `(program_id_index, accounts: Vec<u8>, account_keys.len())` tuples where indices may exceed `account_keys.len()`, call `parse_ui_instruction`, and assert `std::panic::catch_unwind` always returns `Ok`.
