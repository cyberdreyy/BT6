### Title
Dust APR0 withdraw request permanently reverts `stopEpoch` whenever APR is non-zero, freezing all vault funds — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` [1](#0-0) . Any unprivileged tranche holder can create a non-zero `apr0TotalPrincipal` with a dust `requestWithdraw` while APR is 0 [2](#0-1) . Because `apr0TotalPrincipal` is only cleared inside the same function after the revert check [3](#0-2) , every subsequent `stopEpoch` call reverts while APR stays non-zero — a self-inflicted livelock of the epoch state machine analogous to CVE-2023-21976's repeatable-crash DoS, but here it freezes real user funds.

### Finding Description
- When `unscaledApr == 0` and the pool is not closed, `requestWithdraw` routes into `_requestWithdrawApr0`, which credits `apr0Users[_user]` and increases the global `apr0TotalPrincipal` [4](#0-3) .
- There is no minimum amount check, so a 1-wei receipt is enough.
- At `stopEpoch`, `IdleCDOEpochVariant` calls `prepareStopEpochWithApr0`, which reverts if `apr0TotalPrincipal != 0 && unscaledApr != 0` [5](#0-4) .
- The clear (`apr0TotalPrincipal = 0`) sits *after* the revert, so no code path removes the poisoned bucket while APR is non-zero.
- The poisoned bucket also cannot be unwound by the attacker: `_settleApr0` only moves principal after `epochNumber` has advanced past the request epoch [6](#0-5) , which requires a successful `stopEpoch` — a circular dependency. `claimWithdrawRequest`/`claimInstantWithdrawRequest` cannot clear it either.
- Result: while APR remains non-zero, `stopEpoch` always reverts. Funds can only be recovered if the manager sets APR back to 0 and completes a stop — and if the pool must run at non-zero APR (normal operating mode), the freeze is effectively indefinite.

### Impact Explanation
Temporary (potentially indefinite) freezing of the entire vault: all lender principal, accrued interest, and all pending withdraw receipts (`pendingWithdraws`, `withdrawsRequests`, `instantWithdrawsRequests`) are locked because no epoch can be stopped and no claim gates open (`epochNumber <= lastWithdrawRequest` stays true forever) [7](#0-6) . Quantified loss = full TVL + pending receipts frozen for at least one extra `epochDuration`, and indefinitely while non-zero APR is required.

### Likelihood Explanation
The attacker needs only to be a wallet allowed to hold tranche tokens (KYC-passing lender) and to wait for or induce an APR0 configuration. The cost is a dust deposit plus one `requestWithdraw` call. The trigger condition (manager raising APR while an APR0 receipt is pending) is a routine configuration change, not an attacker-contrived edge. No privileged cooperation or oracle manipulation is required. Uncertainty: I could not fully verify whether `setAprs` applies `unscaledApr` immediately or only at the next `stopEpoch` boundary; if it is applied at stop-time through `prepareStopEpochWithApr0` itself, the window narrows but the same livelock still applies across any APR change while an APR0 bucket is open.

### Recommendation
Do not revert `stopEpoch` on a stale APR0 bucket. Options: (a) settle APR0 principal at a zero rate when `unscaledApr != 0` (forfeit or carry principal without interest) and still clear `apr0TotalPrincipal`; (b) move the `apr0TotalPrincipal = 0` reset before the APR check and treat nonzero-APR epochs as settling at rate 0; (c) enforce a minimum request size and allow the manager to force-close the APR0 bucket. Ensure the bucket can always be finalized independently of current APR.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol — fork PoC sketch
function testApr0DustRequestLivelocksStopEpoch() external {
    // Setup: pool running, manager sets APR to 0 for the epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // Attacker deposits dust and requests withdraw while APR == 0
    address attacker = makeAddr('attacker');
    uint256 dust = 1;
    _depositWithUser(attacker, dust);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // Manager raises APR (normal ops) before stopEpoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(10e18, 0);

    // stopEpoch now reverts forever while APR != 0
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _repayBorrowerFully(); // borrower is honest and provides funds
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // Attacker cannot self-clear: claim reverts (epoch not advanced)
    vm.prank(attacker);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();

    // All user funds remain frozen; only setting APR back to 0 unblocks the pool.
}
```
