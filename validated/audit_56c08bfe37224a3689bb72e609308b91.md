### Title
Fee-on-transfer deposits over-mint credit vault strategy tokens and can wedge epoch startup - ([File: contracts/IdleCDOCreditVault.sol])

### Summary
`IdleCDOCreditVault._deposit` correctly mints tranche shares from the amount received by the CDO, but then calls `IdleCreditVault.deposit` with the original gross amount rather than the received amount. `IdleCreditVault.deposit` mints the same gross amount of strategy tokens even though a fee-on-transfer token delivers less.

### Finding Description
The deposit flow measures the user's first transfer accurately:

- The CDO records `preBal`.
- It pulls `_amount` from the depositor.
- It mints tranche shares based on `balanceAfter - preBal`, not `_amount` [1](#0-0) .

However, it subsequently deposits the original `_amount` into the strategy. `IdleCreditVault.deposit` pulls `_amount` from the CDO and unconditionally mints `_amount` strategy tokens to the CDO [2](#0-1) .

For a token charging a fee on each transfer, this produces two deductions:

1. User → CDO: `_amount` is debited, but only `_amount - fee1` is received.
2. CDO → strategy: `_amount` is debited, but only `_amount - fee2` is received.

If the CDO already holds enough raw underlying to satisfy the gross second transfer, the strategy mints `_amount` strategy tokens while receiving only `_amount - fee2` underlying. Those excess strategy tokens are counted one-to-one as vault value by `getContractValue` [3](#0-2) .

An unprivileged attacker can create the required residual CDO balance with a direct underlying transfer. The strategy also records `totEpochDeposits += _amount` even though it received less [4](#0-3) . At the next `startEpoch`, the CDO reads `totEpochDeposits` and asks the strategy to send that amount [5](#0-4) . Since the strategy's actual token balance is lower, `sendInterestAndDeposits` reverts, preventing the epoch from starting until the strategy is recapitalized [6](#0-5) .

### Impact Explanation
The protocol's strategy-token accounting claims more backing than the strategy actually holds. In addition to overstating NAV, the mismatch causes `startEpoch` to request more underlying than the strategy owns, so the borrower's epoch cannot begin and deposited funds remain stuck in buffer state. A 10% fee token depositing `100` units after a `10`-unit residual balance is staged produces `100` strategy tokens backed by only `90` underlying and records `100` epoch deposits.

### Likelihood Explanation
The issue requires the configured underlying to charge fees on every transfer, including both user-to-CDO and CDO-to-strategy transfers. It also requires enough residual CDO balance to cover the first transfer fee. That residual can be supplied by the attacker as a direct token transfer, so no privileged action or protocol malfunction is needed. If no residual exists, the second `transferFrom` fails and the deposit transaction reverts.

### Recommendation
Do not forward the gross `_amount` into the strategy and do not mint strategy tokens from the requested amount. Measure the actual balance received at each hop and use the final amount received by the strategy as the backing for both strategy-token and tranche-share issuance. Alternatively, explicitly reject fee-on-transfer underlying tokens during vault deployment/configuration.

// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

// Deploy alongside the normal IdleCreditVault Foundry fixture:
// - `cdo` is IdleCDOEpochVariant
// - `strategy` is IdleCreditVault
// - `underlying` is a fee-on-transfer ERC20
contract FeeOnTransferDepositPoC is Test {
    FeeToken underlying;
    IdleCDOEpochVariant cdo;
    IdleCreditVault strategy;
    address attacker = address(0xA11CE);

    uint256 constant DEPOSIT = 100e18;

    function setUp() public {
        // Deploy FeeToken with a 10% fee on both transfer and transferFrom.
        // Initialize IdleCreditVault and IdleCDOEpochVariant with it as `token`.
        // Keep the pool in buffer phase.
    }

    function testFeeOnTransferDepositCreatesUnbackedStrategyTokens() public {
        underlying.mint(attacker, DEPOSIT + 10e18);

        vm.startPrank(attacker);

        // Stage enough residual balance for the CDO to satisfy the gross
        // strategy pull after the first transfer fee.
        underlying.transfer(address(cdo), 10e18); // CDO receives 9e18 with a 10% fee

        underlying.approve(address(cdo), DEPOSIT);
        cdo.depositAA(DEPOSIT);

        vm.stopPrank();

        // With a 10% fee:
        // attacker -> CDO transfers 100 but CDO receives 90.
        // CDO -> strategy transfers 100 but strategy receives 90.
        // The strategy nevertheless minted 100 strategy tokens to the CDO.
        assertEq(strategy.balanceOf(address(cdo)), 100e18);
        assertEq(underlying.balanceOf(address(strategy)), 81e18); // if direct transfer also charged
        // If the staged direct transfer is mocked as fee-free, this is 90e18;
        // either way it is less than the 100e18 strategy-token claim.

        assertEq(strategy.totEpochDeposits(), 100e18);

        // startEpoch asks the strategy for the recorded 100e18, but the
        // strategy has less underlying, so the transfer reverts.
        vm.prank(cdo.owner());
        vm.expectRevert();
        cdo.startEpoch();
    }
}

contract FeeToken is ERC20 {
    uint256 public constant FEE_BPS = 1_000;

    constructor() ERC20("FeeToken", "FEE") {}

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal override {
        uint256 fee = amount * FEE_BPS / 10_000;
        super._transfer(from, address(0xdead), fee);
        super._transfer(from, to, amount - fee);
    }
}
