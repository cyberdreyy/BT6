### Title
Division-by-zero panic in B20 asset precompile `to_raw_balance` on zero multiplier - (File: `crates/common/precompiles/src/b20_asset/logic/v1.rs` / `v2.rs`)

### Summary
The Sherlock report flags Surge's `Pool.borrow` for dividing by an unchecked `collateralBalanceOf[msg.sender]` that can be zero, causing an unhandled revert with no error message. The analogous pattern in this Base repo is the B20 asset precompile logic's `to_raw_balance`, which divides by `multiplier` without validating it is non-zero at the point of use.

### Finding Description
`to_raw_balance` in both the V1 and V2 asset logic implementations computes:
```
let multiplier = token.accounting().multiplier()?; // or effective_multiplier()?
let product = balance.checked_mul(B20AssetStorage::WAD)...;
Ok(product / multiplier)
``` [1](#0-0) [2](#0-1) 

Only the multiplication is checked (`checked_mul` → `BasePrecompileError::under_overflow`), but the divisor `multiplier` is used directly with the plain `/` operator, with no `checked_div` / zero guard at the call site. This differs from the fee-math code elsewhere in the repo, which explicitly guards divisors: `crates/common/l1-fees/src/params.rs` uses `wrapping_div` throughout to avoid panics on zero denominators [3](#0-2) , and the EIP-1559 header decoder explicitly rejects a zero denominator before use with a dedicated error variant [4](#0-3) .

The V2 code's own comment reveals the safety of this division is based purely on an invariant enforced elsewhere ("Both setters reject zero, so a stored pending is never zero") rather than a check at the division site: [5](#0-4) 

This is architecturally the same defect class as the reported issue: relying on an off-site invariant (setter validation) instead of defending the division itself. If any code path (e.g., an uninitialized token, a storage migration bug, or a future setter that doesn't validate) ever allows `multiplier` to become `0`, the `/` operation on the `U256`-like type used here will panic rather than return a controlled error, since this codebase clearly treats unchecked division as panic-prone (as evidenced by the deliberate `wrapping_div` usage elsewhere and the explicit zero-denominator error path for EIP-1559 params).

### Impact Explanation
Whereas the original Solidity bug merely causes an unexpected `revert` (poor UX), a division-by-zero panic inside the B20 asset precompile's Rust logic is potentially more severe: a panic inside precompile dispatch, if not caught by an unwind boundary, can abort the executing thread instead of failing the single transaction cleanly. This is an unprivileged-reachable path (`toRawBalance`/`fromUIAmount`-style calls or any internal accounting path invoking `to_raw_balance`) that could turn into a node-halting or transaction-processing-halting condition rather than a benign revert, which is a materially worse outcome than the original finding.

### Likelihood Explanation
I could not fully verify within the available search whether any reachable code path can leave `multiplier` at `0` post-initialization — the V1 fake/test default is `B20AssetStorage::WAD`, and V2 relies on setter-side validation that I was not able to fully inspect before running out of search budget. This materially limits confidence: the finding is a structural pattern match (missing defensive division check, same root cause class as the reported issue) rather than a confirmed exploitable state transition to `multiplier == 0`. This should be treated as a code-quality/defense-in-depth concern pending confirmation that no path (e.g., partial initialization, upgrade/migration) can leave the multiplier unset or zero.

### Recommendation
At minimum, harden `to_raw_balance` (and `to_scaled_balance`'s inverse-facing callers) to explicitly reject or short-circuit a zero multiplier before dividing, e.g. using `checked_div` and mapping `None` to a proper `BasePrecompileError` variant, mirroring the explicit `ZeroDenominator` error pattern already used in `crates/proof/executor/src/util.rs`, rather than relying solely on setter-side invariants.

### Proof of Concept
Not constructible with confidence from static review alone: I was unable to confirm within the available search whether `multiplier`/`effective_multiplier` can return `0` through any reachable path (e.g., before/without full initialization). A concrete PoC would require exercising the token accounting initialization/upgrade paths in `crates/common/precompiles/src/b20_asset/accounting.rs` to determine whether `multiplier` can ever be persisted or read as `0` prior to a call into `to_raw_balance`.

    fn effective_multiplier(&self, token: &B20AssetToken<S, A>) -> Result<U256> {
        let now = token.accounting().timestamp()?;
        let effective_at = token.accounting().pending_effective_at()?;
        if effective_at != 0 && now >= U256::from(effective_at) {
            let pending = token.accounting().pending_multiplier()?;
            // Both setters reject zero, so a stored pending is never zero. Do not fall back to WAD:
            // the Solidity reference also returns the raw pending value.
            debug_assert!(pending != 0, "matured pending multiplier must be non-zero");
            return Ok(U256::from(pending));
        }
        token.accounting().multiplier()
    }
