### Title
Already-claimed instant-withdraw receipts remain in `instantWithdrawClaimsByEpoch`, inflating the default-recovery basis and prefunded reserve with ghost funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` pays a funded instant receipt but never clears `instantWithdrawsRequestsByEpoch[user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If a later unfunded instant request lands in the **same epoch** and the borrower then defaults, `finalizeDefaultRecovery` treats the already-paid-out amount as still-held "prefunded" reserve, minting unbacked recovery claims. This is the vault analog of a use-after-free: stale, logically-freed receipt state is reused by the recovery accounting.

### Finding Description
The instant-withdraw lifecycle tracks three pieces of state per request epoch:

- `instantWithdrawsRequests[user]` — cleared on claim (`claimInstantWithdrawRequest`, lines 387-392)
- `instantWithdrawsRequestsByEpoch[user][epoch]` — **never cleared** on a funded claim; only cleared in `_claimDefaultedInstantWithdrawRequest` (line 847)
- `instantWithdrawClaimsByEpoch[epoch]` — **never decremented** on a funded claim; only decremented in `_claimDefaultedInstantWithdrawRequest` (line 853) [1](#0-0) 

When default is finalized, `defaultPendingClaimBasis` adds the **entire** `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`: [2](#0-1) 

and `_defaultPrefundedInstantReserve` assumes `instantBasis - pendingInstant` underlyings are still held by the strategy: [3](#0-2) 

That assumption is false for receipts already paid out: `collectInstantWithdrawFunds` pulled the tokens in and `claimInstantWithdrawRequest` already transferred them to the user, yet they still count toward both the claim basis and the prefunded reserve.

### Impact Explanation
Attack sequence (running epoch, non-defaulted):

1. User A (attacker address 1) calls `requestInstantWithdraw(100)`. The CDO honestly funds it via `collectInstantWithdrawFunds(100)` (`pendingInstantWithdraws` → 0, strategy holds 100).
2. A calls `claimInstantWithdrawRequest` and receives 100 underlying. `instantWithdrawClaimsByEpoch[epoch]` still equals 100; `instantWithdrawsRequestsByEpoch[A][epoch]` still equals 100.
3. User B (attacker address 2, or any honest user) calls `requestInstantWithdraw(50)` in the same epoch; the CDO does not fund it before epoch end (`pendingInstantWithdraws` = 50, `instantWithdrawClaimsByEpoch[epoch]` = 150).
4. The honest borrower fails to repay; the CDO calls `finalizeDefaultRecovery`:
   - `defaultPendingClaimBasis` includes 150 instant basis instead of 50 (ghost +100).
   - `_defaultPrefundedInstantReserve` returns `150 - 50 = 100`, although the strategy holds **0** of that (it was paid to A in step 2).
   - `recoveryPrice = (recovered + 100_ghost) / totalBasis` is inflated, and `defaultRecoveryReserve` is credited with 100 tokens that do not exist.
   - Since `activeFinalNAV` is computed from the inflated price, `_mint(idleCDO, activeFinalNAV - activeBalance)` creates unbacked strategy tokens, diluting the tranche waterfall.

Consequences:

- Early recovery claimants (`_transferDefaultRecovery`) are overpaid relative to the true recovery ratio — direct theft of recovery value belonging to other claimants / active tranche holders.
- `defaultRecoveryReserve` accounting exceeds the real token balance by the ghost amount G; once reserve bookkeeping is exhausted, `underlyingToken.safeTransfer` in `_transferDefaultRecovery` reverts — **permanent freezing** of the last claimants' recovery funds (lines 912-917).
- Quantified loss: up to the sum of all same-epoch instant withdrawals that were funded and claimed before finalization, i.e. a full ghost-reserve overstatement; with realistic sizing this can be a large fraction of the epoch's recovery pool.

Broken invariant: reserve isolation / one-receipt-one-payout — the recovery reserve is credited for underlying that was already disbursed.

### Likelihood Explanation
No privileged misbehavior is required: the owner/manager/borrower/CDO all act honestly. The trigger is a specific but ordinary ordering — a funded-and-claimed instant withdrawal followed by a still-unfunded instant withdrawal in the same epoch, then a borrower default before `epochNumber` increments. `claimInstantWithdrawRequest` is the normal user flow, and partial instant-queue funding is an expected condition (that is exactly why `pendingInstantWithdraws` and `_defaultPrefundedInstantReserve` exist). The only uncertainty is whether epoch durations make same-epoch request→fund→claim→new-request common; nothing in the code prevents it. Note the guard `pendingInstantWithdraws != 0` in `defaultPendingClaimBasis` means the bug requires at least one unfunded instant receipt at finalization — satisfied by step 3.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch receipt accounting when paying a funded claim in a non-finalized state, e.g.:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
// clear stale per-epoch basis so it cannot be double-counted at default finalization
uint256 epochBasis = instantWithdrawsRequestsByEpoch[_user][epochNumber];
if (epochBasis != 0) {
    instantWithdrawsRequestsByEpoch[_user][epochNumber] = 0;
    instantWithdrawClaimsByEpoch[epochNumber] -= epochBasis;
}
_transferFundedClaim(_user, amount);
```

Care is needed for multi-epoch receipts (receipts requested in an earlier epoch but claimed later); the per-epoch entries for all epochs contributing to `instantWithdrawsRequests[_user]` must be cleared, not only the current one — or alternatively track a per-epoch "claimed" counter that `_defaultPrefundedInstantReserve` and `defaultPendingClaimBasis` subtract.

### Proof of Concept
Foundry fork PoC outline (against `test/foundry/IdleCreditVault.t.sol` setup with a live `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
function test_GhostInstantReserveInflatesRecovery() public {
    // epoch running; A deposits, requests instant withdraw of 100e6 USDC
    _depositAs(A, 100e6);
    vm.prank(address(cdo)); // via cdo.requestInstantWithdraw path
    vault.requestInstantWithdraw(100e6, A);
    // honest CDO funds the instant queue and A claims at par
    cdo.collectInstantWithdrawFunds(100e6);
    cdo.claimInstantWithdrawRequest(A);           // A paid 100e6
    assertEq(vault.instantWithdrawClaimsByEpoch(vault.epochNumber()), 100e6); // stale!

    // B requests instant withdraw 50e6 same epoch; left unfunded
    _depositAs(B, 50e6);
    vault.requestInstantWithdraw(50e6, B);        // pendingInstantWithdraws = 50

    // honest borrower defaults; CDO finalizes recovery with `recovered`
    _defaultBorrower();
    uint256 recovered = ...;
    vault.finalizeDefaultRecovery(recovered, recoverySource);

    // prefundedReserve counted 100e6 ghost tokens not held by the vault
    // => defaultRecoveryPrice inflated, defaultRecoveryReserve > token balance
    uint256 realBalance = underlying.balanceOf(address(vault));
    assertGt(vault.defaultRecoveryReserve(), realBalance - fundedClaims);

    // first claimants overpaid; last claimant's transfer reverts (frozen funds)
    cdo.claimWithdrawRequest(B); // or tranche recovery claim
    vm.expectRevert();
    cdo.claimWithdrawRequest(victim); // insolvency: reserve bookkeeping exhausted
}
```

Caveat: exact CDO entry points (`requestInstantWithdraw`/`claimInstantWithdrawRequest` wrappers in `IdleCDOEpochVariant`) and the borrower-default helper should be matched to the existing `IdleCreditVault.t.sol` harness; the core assertion — `instantWithdrawClaimsByEpoch` retaining a claimed receipt and `defaultRecoveryReserve` exceeding the real underlying balance — follows directly from lines 380-392, 644-649 and 716-723.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
