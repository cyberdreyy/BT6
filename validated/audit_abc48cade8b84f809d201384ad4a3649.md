### Title
Division before multiplication in `_calcInterestWithApr` truncates the APR to whole percents, systematically underpaying epoch interest - ([File: contracts/IdleCDOEpochVariant.sol:807-809](contracts/IdleCDOEpochVariant.sol))

### Summary
`_calcInterestWithApr` computes `_apr / 100` before multiplying by the amount and epoch duration. Since `_apr` is expressed on a `1e18` scale where `1e18 = 100%`, the division truncates the APR down to a whole percent (e.g., `1.99% → 1%`, `0.99% → 0%`). Every downstream consumer — `expectedEpochInterest`, mid-epoch deposit share pricing, and withdraw-request interest — is computed on this understated interest, causing users to receive materially less yield than the configured APR implies.

### Finding Description
In `IdleCDOEpochVariant`:

```solidity
// contracts/IdleCDOEpochVariant.sol:807-809
function _calcInterestWithApr(uint256 _amount, uint256 _apr) internal view returns (uint256) {
  return _amount * (_apr / 100) * epochDuration / (365 days * ONE_TRANCHE_TOKEN);
}
```

`_apr` is a scaled rate where `1e18` corresponds to 100% APR (confirmed by the denominator `365 days * ONE_TRANCHE_TOKEN` and mirrored test helper `_calcInterestAtApr` in `test/foundry/IdleCreditVault.t.sol:3556`). `_apr / 100` therefore yields the number of whole percentage points; any fractional part below `1e16` (1%) is discarded:

- APR = 1.99% (`_apr = 1.99e16`) → `_apr / 100 = 1e16` → interest computed at 1% (~50% relative error)
- APR = 0.99% (`_apr = 9.9e15`) → `_apr / 100 = 0` → interest computed as 0 (100% error)
- APR = 10.5% → computed at 10% (~4.8% error)

This value feeds three fund-critical paths:

1. `startEpoch`/expected yield: `expectedEpochInterest` accrues `_calcInterest(nav)` (IdleCDOEpochVariant.sol:~693 area and epoch accounting), so the pool's tracked yield is understated.
2. `requestWithdraw` → `_calcInterestWithdrawRequest` (IdleCDOEpochVariant.sol:865-875): both `totInterest` and `interestWithoutSplitRatio` are computed via `_calcInterest`, so a withdrawer's `principal + interest - fees` receipt is short by the truncated fraction.
3. `depositDuringEpoch` (IdleCDOEpochVariant.sol:693-724): `interest` and `trancheInterest` are understated, so `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` mints fewer tranche tokens than the depositor is entitled to — they permanently subsidize existing holders.

### Impact Explanation
Direct loss of user yield with a quantified bound: for any APR that is not a whole percentage multiple, withdrawers and mid-epoch depositors lose up to nearly 1 percentage point of APR each epoch; below 1% APR they lose their entire interest. The lost yield is redistributed to remaining tranche holders / fee accounting rather than the entitled users — a persistent value leak on every epoch, not a rounding dust issue. Example: pool with `epochDuration = 30 days`, `NAV = 1,000,000 USDC`, `apr = 5.5%`: computed interest uses 5%, losing `1e6 * 0.5% * 30/365 ≈ 411 USDC` per epoch of expected interest attribution.

### Likelihood Explanation
High. Borrower/pool APRs are almost never exact whole percentages — typical values like 4.35%, 7.25%, 0.5% all trigger truncation, and sub-1% APRs (common for senior/stable pools) zero out interest entirely. No privileged misbehavior is required; the error is deterministic once an epoch runs at a fractional-percent APR. An unprivileged tranche holder invoking `requestWithdraw` or `depositDuringEpoch` suffers the loss on the very next transaction; no guard (skim, epoch gating, KYC, `only-CDO`) compensates for it.

### Recommendation
Reorder operations so all multiplications precede division, and drop the premature `/ 100`:

```solidity
return _amount * _apr * epochDuration / (365 days * ONE_TRANCHE_TOKEN * 100);
```

Apply the same fix in `IdleCreditVault`/`ProgrammableBorrower` interest helpers that replicate the `_apr / 100` pattern, and add a fork test asserting `_calcInterest` at a fractional APR (e.g., 5.5%) matches the exact expected value.

### Proof of Concept
Foundry fork PoC sketch (against the repo's existing `IdleCreditVault.t.sol` harness):

```solidity
function testAprTruncationLoss() external {
    // pool: 1e6 USDC, epochDuration = 30 days, buffer = 0
    // manager sets apr = 5.5e16 (5.5%) via setAprs
    // deposit AA, startEpoch, warp mid-epoch
    uint256 expected = 1_000_000e6 * 55e15 * 30 days / (365 days * 1e18); // exact 5.5%
    uint256 actual   = 1_000_000e6 * (55e15 / 100) * 30 days / (365 days * 1e18);
    // actual uses 5% not 5.5%
    assertLt(actual, expected);
    // requestWithdraw returns principal + actual interest, not expected
    // => withdrawer loses ~411 USDC per epoch
}
```

Deploy `IdleCDOEpochVariant` + `IdleCreditVault` on a mainnet fork, set `apr = 5.5%` (550 in the vault's scaled units / `5.5e16`), deposit into a tranche, `startEpoch`, then `requestWithdraw` and compare the returned `_underlyings` against `principal + amount*0.055*duration/365`. The shortfall equals the truncated `0.5%` component and is reproducible for any non-integer-percent APR.
