### Title
Cross-user response confusion via colliding `MessageId` in `h.savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending trigger request in `h.savedCallbacks` keyed solely by the caller-supplied `msg.Body.MessageId`, with no binding to the caller's identity (`Sender`), `DonId`, or payload. Any signer able to submit a valid, signed `api.Message` can choose an arbitrary `MessageId` (up to 128 bytes), so a second request with the same `MessageId` overwrites the first callback before a node responds, causing `handleWebAPITriggerMessage` to deliver the DON's trigger response to the wrong caller.

### Finding Description
`msg.Body.MessageId` is fully attacker/user-controlled and only constrained by length (`MessageIdMaxLen`) and a null-byte-suffix check in `Message.Validate()` (`core/services/gateway/api/message.go:61-66`) — there is no uniqueness or ownership check performed anywhere before it is used as a map key.

In `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:411-414`):
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
```
This unconditionally overwrites any existing entry for the same key. There is no check for `found` before overwrite, no comparison of `Sender`, and no per-caller namespacing of the key.

Later, `handleWebAPITriggerMessage` (`core/services/gateway/handlers/capabilities/handler.go:148-162`) looks the callback up purely by `msg.Body.MessageId` (the node echoes back whatever `MessageId` was in the original request) and delivers the response to whichever `savedCallback` currently occupies that slot:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
```

Exploit flow: Attacker A (holder of a valid signing key for workflow/caller A) sends `msg1` with `MessageId = "X"`. Before any DON node responds, Attacker/careless caller B sends `msg2` with the same `MessageId = "X"` (different `DonId`/payload, but the check for `DonId` correspondence in `HandleLegacyUserMessage` only affects payload contents, not the map key). Since each `handler` instance is scoped per DON (`donConfig`), the collision applies to messages destined to the same `handler` (same `DonId`) — the two requests must be routed to the same `handler` (same `DonId`), which any signer of a valid message for that DON can do. `h.savedCallbacks["X"]` is overwritten with B's callback. When a node responds with `MessageId = "X"` for A's original outgoing trigger request, `handleWebAPITriggerMessage` fetches and fires B's callback, delivering A's (potentially sensitive) trigger response to B's connection instead of A's.

No existing check stops this: `Message.Validate()` only checks length/format, `ExtractSigner`/signature verification confirms authenticity of the sender but does not tie `MessageId` to that sender, and `HandleLegacyUserMessage` never checks `found` before clobbering the map entry.

### Impact Explanation
This breaks the request/response binding invariant of the gateway: a legitimate caller's trigger response (which can contain application data returned via the web API trigger, e.g., HTTP webhook payloads relayed to the workflow) can be silently redirected to a different, unrelated caller's open connection/callback. This is a cross-user response confusion issue — data belonging to one identity is attributed/delivered to another — matching Chainlink's "unauthorized access to another user's data/response" bounty impact class. It does not grant fund movement or direct privilege escalation, but does leak/misdirect response data intended for another party.

### Likelihood Explanation
Exploitability requires only the ability to sign a well-formed `api.Message` and send it to the same gateway/DON that a victim is using — no elevated role, allowlist bypass, or node compromise is needed since MessageId is entirely user-chosen. The attacker must know or guess the victim's `MessageId` (or coordinate timing if MessageIds are otherwise predictable, e.g., sequential/timestamp-based, which is common client behavior), and the race window is bounded by the time between the victim's request submission and the DON's first response. This is realistically exploitable when MessageIds are not cryptographically random (e.g., simple counters) or when the attacker controls both ends of a race (e.g., simultaneous requests to a shared DON endpoint).

### Recommendation
- Reject/overwrite-guard: in `HandleLegacyUserMessage`, if `h.savedCallbacks[msg.Body.MessageId]` already exists (`found`), reject the new request with an error instead of silently overwriting.
- Bind the map key to more than just `MessageId` — include `Sender` (from `msg.Body.Sender`, populated during signature verification) or generate a gateway-side unique key composed of `(Sender, MessageId)`, so a colliding `MessageId` from a different sender cannot collide with the map key.
- Verify sender/receiver consistency between the initial request and the DON's response before dispatching to the saved callback.

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct `handler` with mocked `handlers.Callback` implementations `callbackA` and `callbackB` (mock `SendResponse`).
2. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` where `msgA.Body.MessageId = "X"`, signed by key A, with a valid `webapicap.TriggerRequestPayload`.
3. Immediately call `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` where `msgB.Body.MessageId = "X"` too (same ID, different signer/payload), before any node response arrives.
4. Assert `h.savedCallbacks["X"].Callback == callbackB` (overwrite occurred), i.e., `callbackA` reference is gone.
5. Simulate a node response for the original trigger tied to `msgA` (a `jsonrpc.Response` with `ID = "X"` for `MethodWebAPITrigger`), call `h.HandleNodeMessage(ctx, resp, nodeAddr)`.
6. Assert `callbackB.SendResponse` was invoked (wrong recipient) and `callbackA.SendResponse` was never called — proving cross-user response delivery. [1](#0-0) [2](#0-1) [3](#0-2)

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
