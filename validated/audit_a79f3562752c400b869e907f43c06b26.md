### Title
`lockup-factory::create` lets the lockup's own owner supply an arbitrary `whitelist_account_id`, letting the owner self-whitelist a fake "staking pool" and drain the locked/unvested tokens early - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` in `lockup-factory/src/lib.rs` accepts an optional `whitelist_account_id` parameter from the caller and, if supplied, uses it instead of the factory's configured `staking_pool_whitelist_account_id` when initializing the new lockup contract. Since the caller of `create` is typically the same party who will become (or controls) the lockup's `owner_account_id`, this lets that owner deploy the lockup trusting a whitelist contract *they themselves control*, breaking the custody binding the lockup/whitelist/staking‑pool design depends on: "a staking pool is trusted only because a foundation‑controlled whitelist vetted it."

### Finding Description
`create()` builds the lockup's init args and, for `staking_pool_whitelist_account_id`, prefers the caller-supplied value over the factory default: [1](#0-0) 

```
pub fn create(
    &mut self,
    owner_account_id: ValidAccountId,
    ...
    whitelist_account_id: Option<ValidAccountId>,
) -> Promise {
    ...
    // Defaults to the whitelist account ID given on init call.
    let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
        account_id.into()
    } else {
        self.whitelist_account_id.clone()
    };
    ...
``` [2](#0-1) 

This value is passed straight into the lockup's `#[init]` `new` and is stored permanently and immutably as `staking_pool_whitelist_account_id` — the lockup's only source of truth for whether a chosen "staking pool" is safe to delegate funds to: [3](#0-2) 

The lockup's guarantee that "the staking pool contract and the account have to be approved by the whitelisting contract to prevent tokens from being lost, locked, or stolen" is stated explicitly in the lockup README and depends entirely on `staking_pool_whitelist_account_id` pointing to the NEAR‑Foundation‑controlled whitelist contract: [4](#0-3) 

The lockup's `select_staking_pool` method only trusts this configured account for the whitelist check: [5](#0-4) 

and the callback that actually records the staking pool selection trusts whatever boolean the "whitelist" cross-contract call returns: [6](#0-5) 

Because `create()` lets the caller substitute this whitelist account, the person paying for and effectively controlling the lockup (who typically becomes its `owner_account_id`) can:
1. Deploy their own trivial contract that always returns `true` from `is_whitelisted`.
2. Call `lockup-factory::create` with `whitelist_account_id` pointing at that contract, and `owner_account_id` set to themselves.
3. As owner, call `select_staking_pool` naming any plain account they control (not a real staking pool contract implementing the delayed-unstake/withdraw guarantees) — the fake whitelist approves it.
4. Call `deposit_and_stake`/`deposit_to_staking_pool`, which unconditionally transfers the requested NEAR out of the lockup account to the "staking pool" account via `ext_staking_pool::deposit_and_stake`/`deposit`: [7](#0-6) 

Because the target is just a plain account (or a contract they wrote), there is no real unstake/withdraw waiting period — the owner immediately has liquid NEAR outside the lockup contract, while `get_locked_amount()`/`get_owners_balance()` inside the lockup still (incorrectly) assume the tokens remain under lockup/vesting rules since `deposit_amount` on `staking_information` is simply incremented, not verified against a real staking pool's slashing/unbonding guarantees: [8](#0-7) 

This breaks the binding: `locked/unvested amount reported by the lockup == NEAR actually inaccessible to the owner`. After the attack, the reported locked/unvested balance in the lockup no longer reflects reality — the NEAR has left the custody chain the lockup/whitelist design is supposed to enforce.

### Impact Explanation
This matches the Critical impact category: "locked or unvested tokens released early." An employee/owner of a lockup (an otherwise unprivileged party with respect to the vesting/lockup schedule — they are not supposed to be able to bypass it) can use the `lockup-factory::create` custom-whitelist parameter to fully evade both the lockup duration and the vesting schedule, extracting funds that the foundation-controlled `foundation_account_id` and vesting/termination logic assume are inaccessible until the schedule completes (or until the foundation processes a termination).

### Likelihood Explanation
This requires only the actions available to any user creating their own lockup through the permissionless factory (paying the minimum attached deposit) plus deploying one small helper contract — no foundation, no multisig member, no validator, and no deployment that deviates from documented initialization on the *lockup* side (the lockup contract's own `#[init]` correctly validates that whatever whitelist account ID it's given is a syntactically valid account ID; it has no way to know the account isn't the "real" whitelist). The vulnerability is squarely in the factory's decision to let the caller override this security-critical parameter. Given `lockup-factory` is explicitly designed to let "any user create and fund the lockup contract" (per its README), this path is directly reachable by the intended owner of the vesting position — the party the vesting logic is meant to restrain.

### Recommendation
Remove the `whitelist_account_id: Option<ValidAccountId>` parameter from `LockupFactory::create` (or restrict overriding it to a foundation-only method), and always use the factory's own `self.whitelist_account_id` when constructing the lockup's init args, mirroring how `foundation_account_id` is derived internally rather than taken from caller input.

### Proof of Concept
1. Deploy a trivial helper contract `fake_whitelist` exposing `pub fn is_whitelisted(&self, staking_pool_account_id: AccountId) -> bool { true }`.
2. Call `lockup-factory::create` with `owner_account_id = attacker`, attaching the minimum deposit, and `whitelist_account_id = Some(fake_whitelist)` — per [1](#0-0) , this is accepted and used verbatim to init the new lockup, and per `lockup/src/lib.rs` `new` ( [3](#0-2) ), it's stored as the trusted whitelist for the lifetime of the contract with no further validation.
3. As `attacker` (the lockup owner), call `select_staking_pool` with `staking_pool_account_id = attacker_pool` (a plain account controlled by attacker) — [5](#0-4)  queries `fake_whitelist`, which returns `true`, and `on_whitelist_is_whitelisted` ( [6](#0-5) ) records it as the selected pool.
4. Call `deposit_and_stake` for the full locked/unvested balance — [7](#0-6)  transfers the NEAR to `attacker_pool` via a cross-contract call; since `attacker_pool` is just a normal account (or a contract the attacker wrote that immediately forwards funds), the tokens are now liquid and outside the vesting/lockup enforcement, despite the lockup contract's view methods still reporting them as locked.

Note: I was unable to execute this against a live NEAR sandbox/testnet to confirm the exact promise-chain behavior end-to-end (e.g., precise gas accounting on the deposit/stake callback); the analysis is based on static reading of `lockup-factory/src/lib.rs`, `lockup/src/lib.rs`, `lockup/src/owner.rs`, and `lockup/src/owner_callbacks.rs`.

    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,
        staking_pool_account_id: AccountId,
    ) -> bool {
        assert_self();
        assert!(
            is_whitelisted,
            "The given staking pool account ID is not whitelisted"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();
        self.staking_information = Some(StakingInformation {
            staking_pool_account_id,
            status: TransactionStatus::Idle,
            deposit_amount: 0.into(),

        true
    }

    pub fn on_staking_pool_deposit_and_stake(&mut self, amount: WrappedBalance) -> bool {
        assert_self();

        let deposit_and_stake_succeeded = is_promise_success();
        self.set_staking_pool_status(TransactionStatus::Idle);

        if deposit_and_stake_succeeded {
            self.staking_information.as_mut().unwrap().deposit_amount.0 += amount.0;
            env::log(
                format!(
                    "The deposit and stake of {} to @{} succeeded",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        } else {
            env::log(
                format!(
                    "The deposit and stake of {} to @{} has failed",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        }
        deposit_and_stake_succeeded
    }
