### Title
`ValidatedMessageFromReq` only verifies signature/structure, not sender authorization — DON-facing handlers (`dummyHandler`, `capabilities.handler`) forward attacker-signed messages to DON nodes without any allowlist/authorization check - ([File: core/services/gateway/handlers/common/message_util.go])

### Summary
`ValidatedMessageFromReq` performs only structural field-length validation and ECDSA signature-recovery via `m.Validate()` → `m.ExtractSigner()`, populating `Body.Sender` with whatever address recovers from the signature — it never checks that sender against a DON membership list, workflow-owner allowlist, or subscription record. Two concrete handler implementations that consume this validated message, `dummyHandler.HandleLegacyUserMessage` and `capabilities.handler.HandleLegacyUserMessage`, forward the message straight to every DON node with no additional authorization check, so a caller who signs with a throwaway, never-before-seen key can reach DON node dispatch.

### Finding Description
`ValidatedMessageFromReq` decodes JSON-RPC params into an `api.Message` and calls `m.Validate()`: [1](#0-0)  `Message.Validate()` checks field lengths/null-termination and calls `ExtractSigner()`, assigning the recovered address to `Body.Sender` — there is no comparison of that address against any allowlist, DON member set, or capability registry: [2](#0-1) 

Two production handler paths consume this result without adding their own authorization:
- `dummyHandler.HandleLegacyUserMessage` stores the callback and forwards the request to **all** DON members regardless of sender, with the type's own doc comment stating it "forwards each request/response without doing any checks": [3](#0-2) [4](#0-3) 
- `capabilities.handler.HandleLegacyUserMessage` (the WebAPI/CRE handler) contains an explicit acknowledgment of the missing check — `// TODO: apply allowlist and rate-limiting here` — immediately before forwarding the request to every DON member: [5](#0-4) 

By contrast, the Vault capability's gateway handler (`core/capabilities/vault/gw_handler.go`) demonstrates the intended pattern: it explicitly wires an `Authorizer` (allowlist-based or JWT-based) on top of message validation before dispatching to the secrets service. [6](#0-5)  This confirms that `ValidatedMessageFromReq`/`Message.Validate()` intentionally defers authorization to each handler, and that at least the dummy and WebAPI/capabilities handlers do not implement it.

### Impact Explanation
Any unauthenticated client that can reach gateway ingress and produce a syntactically valid signed `Message` (from a disposable key) can have that message forwarded to every configured DON node via the `dummy` or WebAPI (`capabilities`) handler routes, since neither checks the recovered `Body.Sender` against a DON/workflow allowlist before dispatch. This matches the "allowlist/quota bypass" and "unauthorized job/workflow run" bounty impact classes: an unauthorized sender can trigger DON node processing (e.g., `web_api_trigger`) and consume node resources/callback slots that are meant to be gated by sender identity.

### Likelihood Explanation
Precondition is only unauthenticated network access to the gateway HTTP ingress and the ability to generate an ECDSA keypair to sign a message — trivial and fully attacker-controlled, no operator/admin access required. The `capabilities.handler` TODO comment shows the maintainers are aware allowlisting is not yet implemented at this layer, indicating the gap is real rather than a false positive from an untraced downstream check. Actual severity ultimately depends on whether DON nodes independently re-validate the sender for these methods (not verifiable from the gateway-side code alone), so the confirmed, in-code gap is the missing gateway-side authorization for `dummy` and WebAPI-trigger routes.

### Recommendation
Add explicit sender authorization (DON-member/workflow-owner allowlist check) inside `capabilities.handler.HandleLegacyUserMessage` before forwarding to DON nodes, replacing the `// TODO: apply allowlist and rate-limiting here` comment with real enforcement, mirroring the pattern already used in `core/capabilities/vault/gw_handler.go`. If `dummyHandler` is intended only for testing, ensure it cannot be selected via production DON handler configuration; otherwise apply the same allowlist check there.

### Proof of Concept
1. Handler-level Go test in `core/services/gateway/handlers/capabilities` (or `handler.dummy_test.go`): construct an `api.Message` with `Body.DonId` set to a configured DON, sign it with a freshly generated key never present in `donConfig.Members` or any workflow-owner allowlist.
2. Call `ValidatedMessageFromReq` and assert it returns no error (confirming structural/signature-only validation passes).
3. Call `handler.HandleLegacyUserMessage` (or `dummyHandler.HandleLegacyUserMessage`) with the resulting message and a mock `DON`/`don.SendToNode`.
4. Assert `SendToNode` is invoked for DON members despite the sender key being unregistered/unallowlisted — demonstrating the request reaches DON dispatch without any authorization rejection.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (d *dummyHandler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback Callback) error {
	d.mu.Lock()
	d.savedCallbacks[msg.Body.MessageId] = &savedCallback{msg.Body.MessageId, callback}
	don := d.don
	d.mu.Unlock()
	params, err := json.Marshal(msg)
	if err != nil {
		return err
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageId,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	for _, member := range d.donConfig.Members {
		err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
	}
	return err
}
