### Title
Permanent epoch-stop DoS via dust APR0 withdraw request once APR becomes non-zero - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` hard-reverts whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. The bucket is only cleared at the end of the same function, after the revert, so once a user holds an open APR0 withdrawal request and the APR is raised to a non-zero value, every subsequent `stopEpoch`/`stopEpochWithDuration` reverts forever. An unprivileged tranche holder can permanently freeze the vault's epoch lifecycle (or force borrower-default handling) with a dust-sized withdrawal request.

### Finding Description
The external bug class is "a crafted stored event causes persistent denial of service for everyone." The analog lives in the APR0 withdrawal flow of `IdleCreditVault`:

1. While the vault runs with `unscaledApr == 0`, a user calls `requestWithdraw` through the CDO. The strategy mints the user a receipt and routes into `_requestWithdrawApr0`, which increments `apr0TotalPrincipal` and sets `apr0Users[user].principal` (lines 285–286, 567–577). Only a principal-sized request is needed; dust suffices.
2. The manager later configures a non-zero APR for a new epoch via `setAprs`/`setAprsWithBuffer` — a normal, honest operation. `unscaledApr` is now non-zero while `apr0TotalPrincipal` remains non-zero.
3. At the next `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which executes `if (unscaledApr != 0) revert NotAllowed();` (lines 505–508) **before** reaching `apr0TotalPrincipal = 0;` (line 540). Nothing else in the contract clears `apr0TotalPrincipal`: `_settleApr0` only touches per-user `apr0Users` entries, and `_claimDefaultedWithdrawRequest`'s `apr0TotalPrincipal` adjustment is unreachable because finalization requires the epoch state machine to progress. Even the affected user claiming their receipt does not decrement `apr0TotalPrincipal` — it is only zeroed inside the function that reverts.
4. The revert propagates into the CDO's epoch-stop path. As seen in `IdleCDOEpochVariant` (line ~571), a failing stop falls into `_handleBorrowerDefault`, so the attacker either permanently bricks epoch processing or forces the pool into `defaulted = true`, pausing deposits and disabling all withdrawal requests (`allowAAWithdrawRequest = false`, `allowBBWithdrawRequest = false`, lines 594–596) even though the borrower is honest and solvent.

Broken invariant: liveness of the epoch state machine and fair access to withdrawals — one unprivileged user's receipt permanently blocks `stopEpoch` for all LPs.

Existing guards do not help: `maxApr` caps the APR value but not the 0→non-zero transition; `_ensureDefaultRecoveryInitialized` does not clear `apr0TotalPrincipal`; there is no settle-then-continue path when APR changed mid-lifecycle.

### Impact Explanation
Permanent freezing of funds or forced default. All LP principal and yield stay locked because the epoch can never be stopped while the condition holds; alternatively the pool is pushed into the default path where withdrawals are disabled and recovery must go through `finalizeDefaultRecovery` with a haircut — a fund-impacting outcome triggered by a dust request. Loss is bounded only by the entire pool TVL.

### Likelihood Explanation
High in any pool that ever operates at `unscaledApr == 0` and later raises the APR. The attacker only needs to be a KYC-passing lender/tranche holder who submits one tiny `requestWithdraw` during a zero-APR epoch; keeping a small open APR0 request each epoch guarantees the brick whenever the APR is raised. The manager's APR change is a routine honest action, so no attacker control over privileged roles is required.

### Recommendation
In `prepareStopEpochWithApr0`, when `unscaledApr != 0`, settle the outstanding APR0 bucket at zero interest instead of reverting — e.g., iterate-free accounting by recording `apr0RateByEpoch[epochNumber] = 0` and clearing `apr0TotalPrincipal`, or move the `apr0TotalPrincipal = 0` reset before the `unscaledApr` check with a per-epoch zero rate. Alternatively, prevent APR transitions away from 0 while `apr0TotalPrincipal != 0` in `setAprs`, and let `claimWithdrawRequest` decrement `apr0TotalPrincipal` when a user settles early.

### Proof of Concept
Foundry fork PoC sketch (extending `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testPocApr0PermanentStopDos() external {
  // Arrange: pool configured with unscaledApr == 0
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(0, 0);

  address attacker = makeAddr('dust-attacker');
  _depositWithUser(attacker, 1000 * ONE_SCALE, true); // small AA deposit
  _startEpochAndCheckPrices(0);

  // Attacker files a dust withdraw request while APR is 0
  uint256 dust = 1; // one wei of tranche
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(dust, address(AAtranche));
  assertGt(strategy.apr0TotalPrincipal(), 0, 'apr0 bucket seeded');

  _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch()); // epoch 0 stops fine (apr still 0)

  // Manager honestly raises APR for the next epoch
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(initialProvidedApr, initialProvidedApr);
  _startEpochAndCheckPrices(1);

  vm.warp(cdoEpoch.epochEndDate() + 1);
  // Borrower fully repays; stopEpoch still reverts forever
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  // Attacker claiming their receipt does not clear apr0TotalPrincipal
  vm.prank(attacker);
  cdoEpoch.claimWithdrawRequest();
  assertGt(strategy.apr0TotalPrincipal(), 0, 'bucket still open after claim');

  // Every subsequent stopEpoch reverts -> epoch frozen / forced default path
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);
}
```

Uncertainty note: I could not read `IdleCDOEpochVariant.stopEpoch` in full within the iteration budget, so whether the revert is caught into `_handleBorrowerDefault` (forced default) or propagates as a raw revert (frozen epoch) is inferred from the `catch`-into-default pattern at `IdleCDOEpochVariant.sol:571`. Either outcome satisfies the "persistent DoS with fund impact" bar.
