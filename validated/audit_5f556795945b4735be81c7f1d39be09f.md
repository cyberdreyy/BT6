The bug report concerns application-layer ECIES/secp256k1 key exchange in a JavaScript wallet protocol (`eciesjs`, `base64ToBytes`, session resumption from MMKV), where raw byte buffers are accepted as public keys without calling `secp256k1.publicKeyVerify()`. This bug class does not have a reachable analog in the in-scope NEAR contracts.

In `multisig/src/lib.rs` and `multisig2/src/lib.rs`, public keys are represented by near_sdk's `PublicKey` type, which is validated at the deserialization boundary (curve-type byte + correct length check) before it ever reaches contract logic such as `AddKey`, `AddMember`, or `confirm`. [1](#0-0) [2](#0-1)  Unlike the JS report's raw `base64ToBytes()` buffers passed straight into `eciesjs.encrypt()`, there is no code path in this repo where an unvalidated byte string is deserialized directly into a cryptographic key used for encryption or shared-secret derivation — public keys here are used only for NEAR access-key authorization, and malformed keys are rejected by the SDK's own `PublicKey` parsing rather than by application logic. [3](#0-2)
