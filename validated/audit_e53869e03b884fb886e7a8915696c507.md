### Title
Unbounded per-notification CPU cost in `accountSubscribe` with `jsonParsed` encoding scales with attacker-controlled account size/extension count - (File: `rpc/src/rpc_subscriptions.rs`)

### Summary
A websocket `accountSubscribe` with `encoding: jsonParsed` causes every commitment-driven notification for that account to synchronously re-run `parse_account_data_v3`, which for SPL/token-2022 accounts walks every extension present in the account. Because the account owner fully controls the account's size (up to `MAX_PERMITTED_DATA_LENGTH`) and extension count/types, a single subscription's per-notification cost scales with attacker-chosen data rather than being bounded by a fixed limit.

### Finding Description
`RpcSolPubSubImpl::account_subscribe` (`rpc/src/rpc_pubsub.rs:425-443`) accepts an arbitrary `UiAccountEncoding`, including `JsonParsed`, with no size, complexity, or cost bound on the encoding choice. [1](#0-0) 

When a bank/gossip commitment update fires, `RpcSubscriptions::notify_watchers` iterates all commitment watchers in parallel and, for `SubscriptionParams::Account`, calls `check_commitment_and_notify` whenever the account was modified since the last notified slot: [2](#0-1) 

`check_commitment_and_notify` invokes `filter_account_result`, which for non-token owners calls `encode_ui_account` with the subscriber's configured encoding, and for known SPL/token-2022 mints/accounts calls `get_parsed_token_account` unconditionally when `encoding == JsonParsed`: [3](#0-2) 

Both paths end in `parse_account_data_v3` (`account-decoder/src/lib.rs:80-90`, `account-decoder/src/parse_account_data.rs:126-157`), which for token/token-2022 accounts calls `parse_token_v3` (`account-decoder/src/parse_token.rs:24-38`). `parse_token_v3` unpacks the full account buffer and then calls `account.get_extension_types()` followed by `parse_extension` for every extension type present: [4](#0-3) 

None of these code paths impose a size or extension-count cap independent of the account's actual on-chain size — the only limit is the protocol-level `MAX_PERMITTED_DATA_LENGTH` (10 MiB), which is far larger than what a lightweight per-notification decode should tolerate. The attacker fully controls this input: they own the subscribed account, can grow/realloc its data up to the maximum permitted size, and can populate it with many token-2022 extensions (each of which adds proportional parsing work in `parse_extension`). Each subsequent low-rate update to that account (at most once per slot, satisfying the "single call" precondition since the notification is triggered internally by bank/gossip commitment processing, not by additional client calls) causes the RPC notification thread pool to re-run this full decode.

There is no length/complexity check gating the `JsonParsed` branch in `filter_account_result` or `encode_ui_account`, no truncation, and no fallback to a cheaper encoding based on account size — only base58 encoding has a size guard (`MAX_BASE58_BYTES`, `account-decoder/src/lib.rs:32-44`), which does not apply to `JsonParsed`.

### Impact Explanation
Per-notification CPU/allocation cost for a single, legitimately-established subscription scales with attacker-controlled on-chain data size and extension count instead of being bounded by an explicit, size-independent limit. This falls under "unbounded cost for a single low-rate call" — an RPC/pubsub CPU-amplification issue reachable via one subscription and one on-chain write per slot, without requiring multiple clients or additional RPC calls beyond the rate ceiling.

### Likelihood Explanation
Fully feasible with the granted attacker capability: create/own an SPL Token-2022 mint or account, subscribe to it with `jsonParsed` encoding, then perform a single realloc/update per slot growing it toward `MAX_PERMITTED_DATA_LENGTH` while adding many extensions. Each such update (at most one per slot, i.e., not exceeding `CLUSTER_SLOT_TIME_TARGET / 2`) triggers a full re-parse on the shared notification thread pool. This is deterministic and repeatable every time the account changes.

### Recommendation
Bound the cost of `JsonParsed` decoding independent of account size: cap the account data length or extension count eligible for `JsonParsed` parsing in `parse_account_data_v3`/`parse_token_v3` and fall back to `Base64`/`Base64Zstd` encoding above the cap (mirroring the existing `MAX_BASE58_BYTES` fallback pattern), or move expensive per-notification parsing off the shared notification pool into a bounded, time-limited task with a cheap fallback on timeout.

### Proof of Concept
Rust benchmark/unit test plan in `rpc/src/rpc_subscriptions.rs` tests module:
1. Build a token-2022 mint/account with a minimal extension set (baseline size) and measure wall time of `filter_account_result` (or `encode_ui_account` directly) with `UiAccountEncoding::JsonParsed`.
2. Build a token-2022 account sized near `MAX_PERMITTED_DATA_LENGTH` with the maximum number of decodable extensions supported by `parse_extension`.
3. Call `check_commitment_and_notify`/`filter_account_result` for both cases with identical subscription setup (single `AccountSubscriptionParams`, single simulated slot notification) and assert that decode time for case 2 stays within a small constant multiple (e.g., 2x) of case 1.
4. Expect the assertion to fail, demonstrating that per-notification time grows roughly linearly with data size/extension count rather than being capped by a fixed bound, confirming the unbounded-cost finding.

fn filter_account_result(
    result: Option<(AccountSharedData, Slot)>,
    params: &AccountSubscriptionParams,
    last_notified_slot: Slot,
    bank: Arc<Bank>,
) -> (Option<UiAccount>, Slot) {
    // If the account is not found, `last_modified_slot` will default to zero and
    // we will notify clients that the account no longer exists if we haven't already
    let (account, last_modified_slot) = result.unwrap_or_default();

    // If last_modified_slot < last_notified_slot this means that we last notified for a fork
    // and should notify that the account state has been reverted.
    let account = (last_modified_slot != last_notified_slot).then(|| {
        if is_known_spl_token_id(account.owner())
            && params.encoding == UiAccountEncoding::JsonParsed
        {
            get_parsed_token_account(&bank, &params.pubkey, account, None)
        } else {
            encode_ui_account(&params.pubkey, &account, params.encoding, None, None)
        }
    });
    (account, last_modified_slot)
}
