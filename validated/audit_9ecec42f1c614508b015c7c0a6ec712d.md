### Title
Owner `emergencyWithdraw` can drain escrowed tranches while write-off requests are pending, permanently stranding lender requests and escrowed tokens - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow` escrows lender tranche tokens inside `createWriteOffRequest` and records them in `userRequests` / `pendingUnderlyings` until either the fulfiller pays via `fullfillWriteOffRequest` or the lender cancels via `deleteWriteOffRequest`. The owner escape hatch `emergencyWithdraw` can pull arbitrary amounts of any token (including the escrowed `tranche`) out of the contract at any time, with no check against live `userRequests` or `pendingUnderlyings`. This is the same bug class as `remove_offer`: an admin recovery function that violates the non-mutability of an in-flight exchange, after which the pending request can never be resolved or unwound.

### Finding Description
- `createWriteOffRequest` transfers tranche tokens into the escrow and increments `userRequests[msg.sender]` and `pendingUnderlyings` (lines 86-102).
- `fullfillWriteOffRequest` assumes the escrow still holds `currentRequest.tranches`: it pulls `_underlyings` from the fulfiller, pays the user minus `exitFee`, then `safeTransfer`s the escrowed tranches to the fulfiller (lines 123-155).
- `deleteWriteOffRequest` assumes the same and returns `currentRequest.tranches` to the lender (lines 105-116).
- `emergencyWithdraw(_token, _to, _amount)` performs an unbounded `safeTransfer` of any token to any address with only `_checkOnlyOwner()` and a non-zero `_to` check — no reservation for escrowed tranches (lines 174-180). Analogously, nothing stops it from being called between `createWriteOffRequest` and fulfillment, exactly as `remove_offer` was called between `buy` and `resolve_nft_payout`.

Sequence (epoch running, pool not defaulted):
1. Lender calls `createWriteOffRequest(amount = T, underlyingsRequested = U)`. `T` tranches are now escrowed; `pendingUnderlyings += U`.
2. Admin (honestly, e.g., to recover "stuck" tokens or reacting to an unrelated incident) calls `emergencyWithdraw(tranche, owner, T)`. The escrow balance no longer covers the live request.
3. Fulfiller calls `fullfillWriteOffRequest(lender, T, U)`. The contract pulls `U` underlyings, pays the lender, then the final `tranche.safeTransfer(msg.sender, T)` reverts on insufficient balance — the whole tx reverts, so the request is never cleared.
4. Lender tries `deleteWriteOffRequest()` — also reverts on insufficient tranche balance.
5. Result: `userRequests[lender]` and `pendingUnderlyings` remain permanently set, the lender's tranche tokens are gone (withdrawn by the owner), and no unprivileged path can ever delete or fulfill the request. The escrow is bricked for that user exactly as the listing was bricked for `accountA`.

Broken invariant: escrowed tranche tokens must be immutable while a write-off request is live ("one receipt, one payout" — every pending request must be either fulfillable or deletable). `emergencyWithdraw` violates this without any guard, and no existing check (`_checkOnlyOwner`, `Is0`, `WrongRequest`) prevents it.

### Impact Explanation
Permanent freezing plus loss of lender escrowed tranche tokens: once `emergencyWithdraw` removes tranche tokens backing a live request, both resolution paths revert forever. The lender's loss equals `currentRequest.tranches` (up to 100% of their escrowed position), and `pendingUnderlyings` is permanently inflated, distorting the contract's outstanding-request accounting. This matches the external report's impact: the honest counterparty (`accountA` / the lender) never gets paid and cannot recover, while the admin escape hatch — retained for legitimate recovery — is the mechanism.

### Likelihood Explanation
Likelihood is moderate and operationally driven rather than attacker-driven, mirroring the external report: the bug triggers only if the owner calls `emergencyWithdraw` on the tranche (or sweeps "excess" tokens mis-accounting escrowed balances, since the contract holds no per-request balance accounting) while requests are pending. During a vault default or write-off campaign is precisely when both escrow activity and emergency operations are most plausible. No malicious privileged behavior is required — a routine sweep suffices.

### Recommendation
Mirror the external remediation ("only call removal on resolution failure") with an enforced guard rather than an operational guideline:
- In `emergencyWithdraw`, refuse to withdraw `tranche` below the aggregate escrowed obligation: track total escrowed tranches (e.g., `pendingTranches`, incremented in `createWriteOffRequest` and decremented in `deleteWriteOffRequest`/`fullfillWriteOffRequest`) and require `IERC20Detailed(tranche).balanceOf(address(this)) - _amount >= pendingTranches` when `_token == tranche`.
- Alternatively, restrict `emergencyWithdraw` to tokens other than `tranche` and `underlying`, or add a dedicated path that also clears affected `userRequests` and `pendingUnderlyings` consistently.

### Proof of Concept
Foundry-style fork PoC (against the deployed escrow or a freshly initialized instance):

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol
function testEmergencyWithdrawStrandsWriteOffRequest() external {
    // lender escrows T tranches for U underlyings during a running epoch
    uint256 T = 100e18;
    uint256 U = 50e6; // USDC
    deal(address(trancheToken), lender, T);
    vm.startPrank(lender);
    trancheToken.approve(address(escrow), T);
    escrow.createWriteOffRequest(T, U);
    vm.stopPrank();

    // honest-owner recovery action while the request is in flight
    vm.prank(owner);
    escrow.emergencyWithdraw(address(trancheToken), owner, T);

    // fulfiller attempts to honor the request: reverts on tranche transfer
    deal(address(underlyingToken), fulfiller, U);
    vm.startPrank(fulfiller);
    underlyingToken.approve(address(escrow), U);
    vm.expectRevert(); // ERC20: transfer amount exceeds balance
    escrow.fullfillWriteOffRequest(lender, T, U);
    vm.stopPrank();

    // lender cannot cancel either: request is permanently stuck
    vm.prank(lender);
    vm.expectRevert();
    escrow.deleteWriteOffRequest();

    assertEq(escrow.pendingUnderlyings(), U);     // accounting permanently inflated
    assertEq(trancheToken.balanceOf(owner), T);   // escrowed tranches left the contract
}
```

Caveat: I verified the escrow contract directly but did not exhaustively check every other admin escape hatch (e.g., `IdleCDOEpochVariant`/`IdleCDOCreditVault` emergency functions) for an even stronger analog; if a privileged sweep exists that touches in-flight `pendingWithdraws`/`epochPendingClaims` funds, it would warrant the same analysis.
