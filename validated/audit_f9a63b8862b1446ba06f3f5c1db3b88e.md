## Finding

### Title
`getMultipleAccounts` aborts the entire batch on a single account's encoding failure instead of returning partial results - (File: rpc/src/rpc.rs)

### Summary
`JsonRpcRequestProcessor::get_multiple_accounts` iterates over the caller-supplied list of pubkeys and calls `get_encoded_account` for each one, propagating any per-account error with `?`. Because the loop uses early-return on first error rather than continuing to encode the remaining independent accounts, one "bad" account in a batch causes the whole multi-account RPC response to fail — the same bug class as the ZetaChain finding, where an error on one independent unit of work (one chain) aborted processing of the rest instead of the loop continuing.

### Finding Description
`get_multiple_accounts` builds its response one pubkey at a time: [1](#0-0) 

Each iteration calls `get_encoded_account`, which for `Binary`/`Base58` encodings enforces `MAX_BASE58_BYTES` via `encode_account`, returning an `Err(error::Error{ code: InvalidRequest, .. })` when the (possibly data-sliced) account data exceeds 128 bytes: [2](#0-1) 

The `?` on `.await.expect(...)?` inside the `for pubkey in pubkeys` loop means the very first pubkey whose encoding fails aborts the entire request — none of the other, perfectly valid accounts in the batch get resolved, and the client receives a bare JSON-RPC error instead of the expected array with per-item results. This is analogous to `crosschain/keeper/abci.go`'s `IterateAndUpdateCctxGasPrice`, where an error processing one chain's pending `cctx` (`return err`) prevented the remaining chains from having their gas price updated at all, instead of skipping only the failing item and continuing the loop.

The same early-return pattern also exists in the related `simulateTransaction`'s post-simulation account-fetch path, which `.collect::<Result<Vec<_>>>()?`s over `config_accounts.addresses`: [3](#0-2) 

### Impact Explanation
Any RPC client (unauthenticated, since `getMultipleAccounts` is a public read RPC method) can construct a batch request containing one arbitrarily chosen account whose on-chain data is larger than 128 bytes together with `encoding: "base58"` (or `"binary"`), and requesting that combination will cause the *entire* multi-account query to fail with an `InvalidRequest` error, even though the RPC method's contract (as exercised by tests such as `test_rpc_get_multiple_accounts`) is to return `null`/valid entries per address. This degrades RPC availability/usability for legitimate wallets and indexers that batch several addresses together — a single unrelated large account (which is public and not owned by the caller) silently breaks the whole batch response for every other address in the same call, an ingest-starvation-style RPC annoyance/DoS analogous to the aborted-loop bug class in the reference finding.

### Likelihood Explanation
High: any address on the network can already have >128 bytes of data (extremely common), any client can freely choose which pubkeys to bundle into `getMultipleAccounts`, and the base58/binary encoding limit is public, well-known behavior. No privileged access or special conditions are required — this is trivially reproducible from any RPC endpoint that serves `getMultipleAccounts`.

### Recommendation
In `get_multiple_accounts` (and the analogous simulate-transaction post-simulation accounts path), do not propagate a single account's encoding error with `?`. Instead, catch the per-account error and push `None`/an error marker for just that entry (consistent with how `get_encoded_account` already returns `Ok(None)` for missing accounts), so the loop continues processing the remaining pubkeys and the response contains valid results for every account that could be encoded successfully.

### Proof of Concept
1. Store (or find) an existing on-chain account `A` whose data length exceeds `MAX_BASE58_BYTES` (128 bytes) — trivially common on mainnet.
2. Call `getMultipleAccounts([A, validPubkey1, validPubkey2, ...], {"encoding": "base58"})`.
3. Observe that the JSON-RPC response is a single top-level error (`InvalidRequest`, "Encoded binary (base 58) data should be less than 128 bytes...") instead of an array containing `null`/valid encodings for `validPubkey1`/`validPubkey2`, because the `for pubkey in pubkeys { ... get_encoded_account(...)? }` loop in `rpc/src/rpc.rs` aborts on the first failing account.

    pub async fn get_multiple_accounts(
        &self,
        pubkeys: Vec<Pubkey>,
        config: Option<RpcAccountInfoConfig>,
    ) -> Result<RpcResponse<Vec<Option<UiAccount>>>> {
        let RpcAccountInfoConfig {
            encoding,
            data_slice,
            commitment,
            min_context_slot,
        } = config.unwrap_or_default();
        let bank = self.get_bank_with_config(RpcContextConfig {
            commitment,
            min_context_slot,
        })?;
        let encoding = encoding.unwrap_or(UiAccountEncoding::Base64);

        let mut accounts = Vec::with_capacity(pubkeys.len());
        for pubkey in pubkeys {
            let bank = Arc::clone(&bank);
            accounts.push(
                self.runtime
                    .spawn_blocking(move || {
                        get_encoded_account(&bank, &pubkey, encoding, data_slice, None)
                    })
                    .await
                    .expect("rpc: get_encoded_account panicked")?,
            );
        }
        Ok(new_response(&bank, accounts))
    }

fn get_encoded_account(
    bank: &Bank,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
    // only used for simulation results
    overwrite_accounts: Option<&HashMap<Pubkey, AccountSharedData>>,
) -> Result<Option<UiAccount>> {
    match account_resolver::get_account_from_overwrites_or_bank(pubkey, bank, overwrite_accounts) {
        Some(account) => {
            let response = if is_known_spl_token_id(account.owner())
                && encoding == UiAccountEncoding::JsonParsed
            {
                get_parsed_token_account(bank, pubkey, account, overwrite_accounts)
            } else {
                encode_account(&account, pubkey, encoding, data_slice)?
            };
            Ok(Some(response))
        }
        None => Ok(None),
    }
}

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
