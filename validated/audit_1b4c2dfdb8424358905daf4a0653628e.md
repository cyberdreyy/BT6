### Title
Wiped BB tranche can never recover after `restoreOperations()`: `priceBB` stays 0 with non-zero supply, permanently bricking `depositBB()` and corrupting mid-epoch BB deposits - (File: contracts/IdleCDOCreditVault.sol)

### Summary
When a reported loss fully exhausts the junior (BB) tranche, `_updateAccounting()` sets `lastNAVBB = 0` and `priceBB = 0` but never burns or adjusts `IdleCDOTranche(BBTranche).totalSupply()`. After the owner calls `restoreOperations()` — which only blocks restoration when `defaulted` or `priceAA == 0` — the vault reopens with a zombie BB class: `depositBB()` reverts on a division-by-zero in `_mintSharesAtCurrPrice()`, and `_virtualPriceAux()` hard-codes `_totalTrancheGain = 0` for any tranche with `_lastTrancheNAV == 0`, so the wipe is irreversible even if new NAV accrues. This mirrors the Carapace `totalSTokenUnderlying`-zeroed / supply-not-burned bug: the "exchange rate" (tranche price) is permanently pinned to zero while the receipt-token supply survives.

### Finding Description
In `IdleCDOCreditVault._virtualPriceAux()` (contracts/IdleCDOCreditVault.sol:287-337):

- A loss larger than `lastNAVBB` produces `_totalBBGain = -lastNAVBB` (line 330-332), so `_virtualPrice` computes to `0` (line 336).
- `_updateAccounting()` (lines 240-246) detects the BB wipe, calls `_emergencyShutdown(true)` which in `IdleCDOEpochVariant` pauses the vault and sets `skipDefaultCheck = true` (contracts/IdleCDOEpochVariant.sol:602-615), and stores `priceBB = 0`.

Recovery path:

- `restoreOperations()` (contracts/IdleCDOEpochVariant.sol:619-632) only reverts when `defaulted || priceAA == 0`. A loss applied via `stopEpochWithDuration(…, _lossAmount)` → `_strategy.burnStrategyTokens(_lossAmount)` → `_forceUpdateAccounting()` (lines 496-500) is *not* a borrower default (`defaulted` stays false), and AA retains NAV, so the owner can fully restore operations: `skipDefaultCheck = false`, `_unpause()`, withdraw requests re-enabled.
- Once unpaused, any user calling `depositBB(_amount)` reaches `_mintSharesAtCurrPrice()` (contracts/IdleCDOCreditVault.sol:344-348): `_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(BBTranche)`. `_tranchePrice()` (lines 422-427) returns `priceBB` because supply is non-zero — i.e. `0` — so the division panics and every BB deposit reverts.
- The wipe can never heal: on any subsequent accounting, `_virtualPriceAux()` line 319 (`if (_lastTrancheNAV == 0) _totalTrancheGain = 0`) forces the BB gain to zero and recomputes `_virtualPrice = 0 * ONE / supply = 0`, even after genuine NAV growth. Combined with `trancheSupply == 0` being the only path that returns `oneToken` (line 297), the non-zero zombie supply guarantees `priceBB` can never be re-initialized.
- Additionally, `depositDuringEpoch()` (contracts/IdleCDOEpochVariant.sol:656-733) does not divide by price; it uses `expectedFinal = _lastSavedNAV(BB) + trancheExpected`. After a wipe, `_lastSavedNAV(BB) == 0` but `trancheExpected` (the BB share of `expectedEpochInterest`) is positive, so a mid-epoch BB deposit mints shares and `_mintShares()` revives `lastNAVBB` — spreading the new depositor's principal across the surviving zombie supply on the next `_updateAccounting()`, resurrecting claims of wiped holders at the new depositor's expense.

Broken invariant: fair mint/burn — a wiped share class retains supply, so both the price-division mint path (permanent revert) and the supply-ratio mint path (value transfer to dead shares) are inconsistent.

### Impact Explanation
After any manager-reported loss that exhausts BB NAV (`stopEpochWithDuration` `_lossAmount` ≥ `lastNAVBB`, or forced accounting crystallizing a borrower shortfall without setting `defaulted`), the vault can be legitimately reopened by `restoreOperations()` and new epochs can run, but `depositBB()` is permanently DoS'd by an arithmetic panic — no new junior capital can ever enter, exactly like the Carapace pool that can never receive deposits after leaving the locked state. If `depositDuringEpoch` is enabled (`isDepositDuringEpochDisabled = false`, `isAYSActive = false`, non-programmable), a mid-epoch BB depositor mints shares whose backing is immediately socialized to the zombie supply: direct, quantified loss of the depositor's principal equal to the fraction of post-deposit BB NAV attributed to pre-wipe tokens.

### Likelihood Explanation
The trigger is a junior-exhausting loss — a normal, anticipated protocol event (the code explicitly supports `_lossAmount` burns and forced accounting past `skipDefaultCheck`), not an edge case. `restoreOperations()` deliberately permits reopening when only BB is wiped (it checks `priceAA == 0`, not `priceBB == 0`), indicating the resumed-operation state is intended to be supported. No attacker privilege is needed: any KYC-passed wallet calling `depositBB` hits the revert; any such wallet calling `depositDuringEpoch(BBTranche)` suffers the dilution loss. Likelihood is moderate-to-high since it depends only on a realized loss ≥ BB NAV followed by the documented recovery call.

### Recommendation
When a tranche class is fully wiped, either (a) burn the surviving tranche supply (or mark the class as permanently closed and revert early in `depositBB`/`depositDuringEpoch` with a clear error), or (b) treat a non-zero-supply/zero-NAV class like a fresh class in `_virtualPriceAux` and `_tranchePrice` (return `oneToken` and allow the next deposit to re-seed NAV) so the class can be re-initialized. `restoreOperations()` should also explicitly gate on `priceBB == 0` if reopening BB deposits is not supported.

### Proof of Concept
Foundry fork PoC (against the repo's `IdleCreditVault.t.sol` harness, where `cdoEpoch` is an `IdleCDOEpochVariant`, `manager`/`owner` are honest privileged roles, `alice`/`bob` are KYC-passed lenders):

```solidity
function testDepositsBBBrokenAfterWipeAndRestore() external {
    // 1. Alice seeds AA and Bob seeds BB during buffer
    vm.startPrank(alice);
    IERC20Detailed(defaultUnderlying).approve(address(idleCDO), type(uint256).max);
    idleCDO.depositAA(10_000 * ONE_SCALE);
    idleCDO.depositBB(1_000 * ONE_SCALE);
    vm.stopPrank();

    // 2. Run an epoch at apr 0 to isolate the loss
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    _startEpochAndCheckPrices(0);

    // 3. Honest manager reports a loss that fully exhausts BB NAV
    uint256 lossAmount = idleCDO.lastNAVBB(); // wipes junior class
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), lossAmount);
    // _forceUpdateAccounting crystallizes: priceBB == 0, lastNAVBB == 0,
    // but BBtranche.totalSupply() is still > 0
    assertEq(idleCDO.priceBB(), 0);
    assertGt(BBtranche.totalSupply(), 0);

    // 4. Owner restores operations (allowed: defaulted == false, priceAA != 0)
    vm.prank(owner);
    idleCDO.restoreOperations();
    assertFalse(idleCDO.paused());
    assertEq(idleCDO.virtualPrice(address(BBtranche)), 0); // permanently pinned

    // 5. Any lender's depositBB is permanently bricked: _amount * ONE / priceBB -> div-by-zero panic
    vm.startPrank(bob);
    IERC20Detailed(defaultUnderlying).approve(address(idleCDO), type(uint256).max);
    vm.expectRevert(); // arithmetic panic in _mintSharesAtCurrPrice
    idleCDO.depositBB(500 * ONE_SCALE);
    vm.stopPrank();
}
```

Note: the exact helper names (`_startEpochAndCheckPrices`, `idleCDO` vs `cdoEpoch` handles, tranche token variables) follow the conventions in `test/foundry/IdleCreditVault.t.sol` (e.g. the `stopEpochWithDuration` flow at lines 5918-5940); minor wiring adjustments may be needed to match the fixture.
