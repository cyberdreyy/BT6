This mirrors the DEPU-1 bug-class exactly: a shared, globally-keyed accounting/tracking structure (there: WETH balance in a deposit store keyed loosely; here: an in-flight-callback map keyed only by an attacker-controllable string) that any unprivileged caller can pollute to deny service to another legitimate, unrelated caller — simply by guessing or reusing the same `requestID` value before the victim's request completes.

### Title
Global, Caller-Unscoped `requestID` Namespace Enables Cross-Tenant Denial of Service in HTTP Trigger Handler - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The gateway's HTTP trigger handler (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`) tracks in-flight user requests in a single map, `callbacks map[string]savedCallback`, keyed solely by the client-supplied JSON-RPC `id`. Any unprivileged, unauthenticated-to-other-workflows caller can submit a request using the same `id` string as another workflow owner's concurrent in-flight request, causing the second request to be rejected outright, denying that unrelated caller service.

### Finding Description
`HandleUserTriggerRequest` validates and authorizes the trigger request per-workflow, but the final concurrency-control step, `setupCallback`, keys its uniqueness/dedup check on `requestID` alone, with no owner or workflow binding: [2](#0-1) 

`validateRequestID` is the only gate on the `id` shape, and it does nothing to prevent collisions across different callers/workflows — it merely forbids empty strings and `/`: [3](#0-2) 

Because `h.callbacks` is a single node-wide map (`map[string]savedCallback`), an unprivileged party who knows or predicts another workflow's `id` (e.g. sequential/timestamp-based/short IDs, or simply racing many guesses) can pre-register that `id` first. This is structurally analogous to the GMX `createDeposit` bug: a shared piece of state (there, the WETH balance backing `executionFee`; here, the `callbacks` map keyed by `requestID`) is not isolated per legitimate actor, so an unrelated, unprivileged party can manipulate it to block someone else's otherwise-valid operation.

### Impact Explanation
A successful collision causes the legitimate caller's `HandleUserTriggerRequest` call to return an `ErrConflict` (`-32001`) instead of executing the workflow trigger, denying that specific request. Because the map is shared across all workflows/owners served by this DON shard's gateway handler, a single unprivileged client can grief any other tenant sharing the same gateway.

### Likelihood Explanation
Likelihood depends on how predictable/guessable request IDs are in practice; if clients use random UUIDs the collision is unlikely to occur incidentally, but a deliberate attacker can enumerate or brute-force common ID patterns, or simply flood with many guesses concurrently with a victim's request window, to selectively deny specific requests. The bug class is confirmed structurally (unscoped shared key), matching the reachable pattern rules (internet-facing gateway, request handler, cache/dedup keyed insufficiently), but I could not fully verify from static reading alone what format/entropy client `id`s typically use in production, since that is caller-controlled and not enforced by this code.

### Recommendation
Scope the `callbacks` map key by both the `workflowID` (or workflow owner) and `requestID`, e.g. `workflowID + "/" + requestID`, instead of `requestID` alone, so that one caller cannot collide with another's in-flight request tracking entry.

### Proof of Concept
1. Attacker crafts JSON-RPC HTTP trigger requests with `id = "X"` targeting the gateway's HTTP trigger endpoint for their own (attacker-owned) workflow, and sends them continuously/concurrently.
2. Victim independently sends a legitimate HTTP trigger request also using `id = "X"` (possible whenever ID generation is short, sequential, timestamp-based, or otherwise guessable/collidable) for a different workflow.
3. Whichever request's `setupCallback` call executes second observes `h.callbacks["X"]` already populated and is rejected via `jsonrpc.ErrConflict`, denying that caller's workflow execution, even though the two requests belong to entirely unrelated workflows/owners.

**Caveat:** I could not execute the code or trace how `id` values are actually generated by real gateway clients in this repo's ecosystem (e.g., whether SDKs enforce high-entropy UUIDs), so exploitability in practice depends on external client behavior not enforced server-side.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
