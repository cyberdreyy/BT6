### Title
Missing signer/authority check in `initialize_nonce_account` allows front-running to seize nonce authority and drain funds - (File: programs/system/src/system_instruction.rs)

### Summary
`initialize_nonce_account` in the System program sets the nonce account's `authority` field to whatever `nonce_authority` pubkey is supplied by the caller, without requiring that pubkey, the nonce account itself, or any other privileged party to be a transaction signer. The only preconditions checked are that the account is writable and currently in `State::Uninitialized`, mirroring the reported `initOwner`-style pattern where an initialization function that sets ownership/authority lacks access control and can be front-run.

### Finding Description
`initialize_nonce_account` only validates writability, `Uninitialized` state, and rent-exemption before writing `State::Initialized(Data::new(*nonce_authority, ...))`: [1](#0-0) 

Crucially, there is no requirement that `nonce_authority` (or the nonce account key) appear in the transaction's signer set — compare this to `authorize_nonce_account`, which explicitly checks the current authority is a signer via `versions.authorize(signers, ...)`: [2](#0-1) 

The dispatch path in `system_processor.rs` confirms `InitializeNonceAccount` only checks account count and sysvar validity, not signers of the target account: [3](#0-2) 

Because a freshly created nonce account (via a preceding `CreateAccount`/`create_nonce_account` transaction) is publicly visible on-chain (and its future address may even be visible in the mempool before confirmation), any unrelated transaction sender can race to submit `InitializeNonceAccount` naming themselves as `nonce_authority` for that account as soon as it exists and is still `Uninitialized`. Whoever's `InitializeNonceAccount` instruction lands first wins control of the account's authority — exactly the "front-running due to lack of access control on an initializer" bug class described in the external report.

### Impact Explanation
If an attacker's `InitializeNonceAccount` instruction is included before the legitimate owner's, the attacker becomes the nonce `authority`. They can subsequently call `WithdrawNonceAccount` (or `AuthorizeNonceAccount`) as that authority to withdraw the account's lamports (including the funds the legitimate owner deposited for rent-exemption/durable nonce usage) to an address of their choosing. This is a concrete unsigned fund movement: the original funder never signed anything permitting the attacker to control or drain the account.

### Likelihood Explanation
Exploitability depends on the initialization sequence not being atomic with account creation. Standard tooling (e.g., `system_instruction::create_nonce_account`, wallet/CLI helpers) bundles `CreateAccount` and `InitializeNonceAccount` into a single atomic transaction signed by the new account keypair, which prevents this race because the whole transaction fails atomically if front-run appropriately. However, any integrator, custom script, or program that creates the account and initializes it as a nonce account in two separate transactions (which the instruction API explicitly allows and does not itself prevent) is exposed to this race. Given this requires non-atomic usage, likelihood is moderate rather than certain, but the underlying code path itself provides no protection at all.

### Recommendation
Require that the account being initialized (or a designated authority passed in as a signer) sign the `InitializeNonceAccount` instruction, or otherwise bind the resulting `authority` value to a signer present in the transaction, mirroring the signer check already implemented in `authorize_nonce_account`. Alternatively, document/enforce that `InitializeNonceAccount` must always be submitted atomically with the preceding `CreateAccount` in the same transaction, and consider adding an explicit check that the calling transaction includes the `nonce_authority` (or account owner) as a signer before allowing initialization.

### Proof of Concept
1. Victim submits transaction A: `CreateAccount(nonce_pubkey, ..., owner=system_program)` funding `nonce_pubkey` with lamports for rent-exemption, intending to follow up with a separate `InitializeNonceAccount(nonce_authority=victim)` transaction.
2. After transaction A confirms (and before the victim's initialize transaction lands), attacker observes the now-existing, `Uninitialized`, system-owned account at `nonce_pubkey`.
3. Attacker submits `InitializeNonceAccount(nonce_authority=attacker)` referencing `nonce_pubkey` as account 0 — this succeeds because `initialize_nonce_account` only checks writability/state/rent, per [4](#0-3) , not that the attacker is authorized in any way.
4. Attacker is now the nonce `authority`. Attacker submits `WithdrawNonceAccount` signed by themselves to drain the account's lamports to their own address.
5. Victim's original `InitializeNonceAccount(nonce_authority=victim)` transaction now fails (`State::Initialized` branch returns `InstructionError::InvalidAccountData`), confirming the attacker's front-run succeeded and the victim's funds were misappropriated.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}

pub(crate) fn authorize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Authorize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }
    match account
        .get_state::<Versions>()?
        .authorize(signers, *nonce_authority)
    {
        Ok(versions) => account.set_state(&versions),
        Err(AuthorizeNonceError::Uninitialized) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
        Err(AuthorizeNonceError::MissingRequiredSignature(account_authority)) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} must sign",
                account_authority
            );
            Err(InstructionError::MissingRequiredSignature)
        }
    }
}
