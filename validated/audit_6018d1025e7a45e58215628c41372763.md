### Title
Post-default instant-withdraw requests alias the defaulted epoch key and drain the recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` records receipts under the *current* `epochNumber` even after `finalizeDefaultRecovery` has frozen `epochNumber` at `defaultRecoveryEpoch`. A post-default instant request therefore lands in `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`, is treated by `_claimDefaultedInstantWithdrawRequest` as a defaulted-epoch receipt, and is paid out of `defaultRecoveryReserve` — reserve sized only for pre-default claim basis. Each such claim steals recovery funds from legitimate defaulted-epoch claimants and can underflow the reserve accounting.

### Finding Description
The CVE-2020-15306 pattern is an attacker-influenced index (`chunkCount`) selecting an offset-table entry that was never sized for it. The analog here is the epoch index: `epochNumber` stops advancing once the pool defaults, yet `requestInstantWithdraw` keeps writing into `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` (`contracts/strategies/idle/IdleCreditVault.sol:367-374`). After finalization, `epochNumber == defaultRecoveryEpoch` (set at `:693`), so a *new* receipt is indistinguishable from a defaulted-epoch receipt.

`requestWithdraw` was explicitly hardened for this case — post-default requests are routed to `postDefaultRequests` and blocked if old receipts exist (`:247-257`). `requestInstantWithdraw` has no equivalent branch: it happily mints a receipt keyed to `defaultEpoch` and increases `instantWithdrawClaimsByEpoch[defaultEpoch]` (`:371-372`).

On claim, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` (`:382-385`). That function reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — now including the post-default amount — and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` (`:842-856`, `:912-917`). The reserve was sized at finalization as `reserveAmount ≈ totalBasis * recoveryPrice` where `totalBasis` only included basis existing at that moment (`:679-692`).

### Impact Explanation
An attacker holding/acquiring strategy-token receipts post-default can route an instant withdraw through the IdleCDO, then claim it at `defaultRecoveryPrice` from the isolated reserve. Every unit paid out this way is a unit of recovery reserve that pre-default claimants (tranche holders with defaulted-epoch receipts) will never receive: once the reserve is consumed, later `_transferDefaultRecovery` calls underflow on `defaultRecoveryReserve -= _amount` (`:915`) and revert, permanently freezing the remaining recovery claims. Loss is bounded by the reserve size but directly transfers recovery value from legitimate claimants to the post-default requester — theft of unclaimed recovery yield plus freezing of the remainder.

### Likelihood Explanation
Requires (a) a default finalized with `pendingInstantWithdraws != 0` so `defaultInstantWithdrawsFinalized` is true, and (b) the IdleCDO still permitting `requestInstantWithdraw` after default. The strategy imposes no post-default gate on this path — the asymmetry with `requestWithdraw`'s explicit `defaultRecoveryFinalized` branch indicates the gap is unguarded at the strategy layer. An attacker needs only a strategy-token balance and KYC/whitelist standing already required of any lender.

### Recommendation
In `requestInstantWithdraw`, when `defaultRecoveryFinalized` is true, either revert or route through a post-default bucket (mirroring `postDefaultRequests`) that is paid 1:1 from prefunded liquidity rather than from `defaultRecoveryReserve`, and never write to `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. Additionally, in `_claimDefaultedInstantWithdrawRequest`, cap the cleared basis at the per-epoch basis recorded at finalization rather than trusting a key that can be grown afterward.

### Proof of Concept
```solidity
// Foundry fork test sketch against deployed IdleCreditVault + IdleCDOEpochVariant
function testPostDefaultInstantDrainsReserve() public {
    // 1. Epoch N running: users deposit; victim requests normal + instant withdraw.
    // 2. Borrower defaults; owner calls finalizeDefault(...);
    //    finalizeDefaultRecovery(recovered, source) sets
    //    defaultRecoveryEpoch = epochNumber, defaultRecoveryPrice, reserve.
    assertEq(vault.epochNumber(), vault.defaultRecoveryEpoch());
    uint256 reserveBefore = vault.defaultRecoveryReserve();

    // 3. Attacker holds strategy tokens (or acquires tranche and redeems via CDO).
    //    CDO routes to vault.requestInstantWithdraw(X, attacker):
    vm.prank(cdo);
    vault.requestInstantWithdraw(X, attacker);
    // lands in instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch]
    assertEq(
        vault.instantWithdrawsRequestsByEpoch(attacker, vault.defaultRecoveryEpoch()),
        X
    );

    // 4. Attacker claims; paid X * defaultRecoveryPrice from reserve.
    vm.prank(cdo);
    vault.claimInstantWithdrawRequest(attacker);
    uint256 drained = X * vault.defaultRecoveryPrice() / 1e18;
    assertEq(reserveBefore - vault.defaultRecoveryReserve(), drained);

    // 5. Repeat until reserve exhausted: victim's defaulted-epoch claim now
    //    reverts on defaultRecoveryReserve underflow -> permanent freeze.
    vm.prank(cdo);
    vm.expectRevert();
    vault.claimInstantWithdrawRequest(victim);
}
```

Caveat: I could not fully inspect `IdleCDOEpochVariant`'s redeem path within the available iterations to confirm instant-withdraw requests are still forwarded to the strategy after `defaulted()` is set. If the CDO hard-reverts instant requests post-default, the strategy-side gap is unreachable and this reduces to defense-in-depth.
