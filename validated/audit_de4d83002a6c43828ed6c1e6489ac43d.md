### Title
Loss-adjusted withdraw receipts recorded under pre-increment epoch can never match `lossRecoveryPriceByEpoch`, so claimants are paid at par from an underfunded reserve — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
When `stopEpoch` realizes a loss, `IdleCreditVault.collectWithdrawFunds()` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]`. However, `epochNumber` is incremented inside `deposit()` during the same `stopEpoch` flow (`isEpochRunning()` is still true), while user receipts were recorded and `lastWithdrawRequest[user]` was set under the pre-increment epoch. `_claimLossAdjustedWithdrawRequest()` looks up the haircut via `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` — the old epoch key — finds `0`, and skips the haircut entirely. The claim then falls through to `_claimFundedWithdrawRequest()` and pays every pending receipt at par, even though the borrower only funded the loss-adjusted amount.

### Finding Description
In `IdleCreditVault.sol`:

- `requestWithdraw` records `withdrawsRequestsByEpoch[user][epochNumber]` and sets `lastWithdrawRequest[user] = epochNumber` (pre-stop value, e.g. `N`).
- During `stopEpoch`, `deposit()` runs while `isEpochRunning()` is still true and executes `epochNumber += 1` (lines 607–611), so the epoch becomes `N+1` before/with the funding step.
- `collectWithdrawFunds` then writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` — i.e. keyed under `N+1` — and sets `pendingWithdraws = 0` after collecting only `_amount < pendingBasis` (lines 411–429).
- `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` = `lossRecoveryPriceByEpoch[N]` = `0` and returns early (lines 789–795). `_claimFundedWithdrawRequest` then pays `withdrawsRequests[user]` at par via `_transferFundedClaim` (lines 319–350).

This is the direct analog of the kernel bug: a lookup performed with a stale/no-longer-valid key misses the node that was actually written, so the "grace-period" haircut metadata is never applied and the freed (underfunded) basis is dereferenced at full value.

### Impact Explanation
The strategy only holds `pendingToFund < pendingBasis` underlying for that epoch's receipts (the haircut funding), but pays each claimant `claimBasis` at par. Early claimants drain the reserve; the excess paid equals `pendingBasis - pendingToFund` (the realized loss share assigned to pending receipts). Later claimants' `_transferFundedClaim` calls revert on insufficient balance — permanent freezing of their entitled funds — and the haircut is effectively socialized onto whoever claims last instead of pro-rata, breaking the loss-waterfall invariant and causing insolvency equal to the unapplied loss amount.

### Likelihood Explanation
Requires a `stopEpochWithDuration`/`stopEpoch` that realizes a loss while `pendingWithdraws > 0` and the borrower funds less than the full basis — a normal, honest-manager/borrower sequence, not an edge case. Any unprivileged tranche holder with a pending receipt in that epoch triggers the mispricing simply by calling `claimWithdrawRequest`; the first claimers extract the difference at the expense of the rest.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the same epoch identifier stored in `lastWithdrawRequest`/`withdrawsRequestsByEpoch` (i.e. the request epoch), or snapshot `epochNumber` before the in-`stopEpoch` increment and pass it explicitly to `collectWithdrawFunds`. Alternatively, store the loss epoch alongside the receipt so the claim path does not depend on matching a mutable global counter.

### Proof of Concept
Foundry fork PoC sketch (contracts + test harness already in `test/foundry/IdleCDOEpochQueue.t.sol` style):

```solidity
// 1. userA and userB deposit into AA during buffer; manager startEpoch().
// 2. Both call cdoEpoch.requestWithdraw(fullBalance, AA) -> receipts keyed epochNumber N,
//    lastWithdrawRequest[*] = N, pendingWithdraws = A + B.
// 3. Borrower repays less / manager calls stopEpochWithDuration with _lossAmount > 0
//    so previewLossAdjustedWithdrawFunds -> pendingToFund < pendingBasis.
//    deposit() bumps epochNumber to N+1; collectWithdrawFunds writes
//    lossRecoveryPriceByEpoch[N+1] = price < 1e18 and pendingWithdraws = 0.
// 4. userA: cdoEpoch.claimWithdrawRequest()
//    - _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[N] == 0 -> skip
//    - _claimFundedWithdrawRequest pays A at par.
//    assert userA received full A  (should have been A * price / 1e18)
// 5. userB: cdoEpoch.claimWithdrawRequest() -> reverts / pays less than
//    B * price / 1e18 because the reserve was drained.
```

Note: I was unable to read `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` to confirm the exact ordering of `deposit()` (epoch increment) relative to `collectWithdrawFunds` within this iteration budget. If funding is collected strictly *before* the incrementing `deposit()`, the keys match and this finding reduces to the narrower issue that `lossRecoveryPriceByEpoch` is keyed on a mutable counter rather than on the request epoch recorded in receipts — the PoC should be run first to confirm which side of the increment `collectWithdrawFunds` lands on.
