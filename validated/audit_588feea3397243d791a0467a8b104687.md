### Title
DeployGlobalContract storage fee is burnt from the caller's balance and is not refunded when a later action in the same receipt fails, even though the fee-triggered distribution receipt itself is discarded by `set_error` - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`action_deploy_global_contract` unconditionally debits `storage_cost` from the signer's account and mutates the in-memory `Account` object *before* any later action in the same receipt runs. [1](#0-0)  If a subsequent action in the same action receipt fails, `ActionResult::set_error` is invoked, which clears `tokens_burnt` and, critically, clears `new_receipts` back to empty. [2](#0-1)  Because the global-contract distribution receipt created by `initiate_distribution` was only queued into `result.new_receipts`—not yet emitted—it is discarded along with everything else, so the contract is never distributed anywhere. [3](#0-2)  The account balance mutation performed inside `action_deploy_global_contract` (`account.set_amount(updated_balance)`), however, is not part of `ActionResult` and is not rolled back by `set_error`—only the receipt-scoped bookkeeping fields are cleared.

### Finding Description
`action_deploy_global_contract` computes `storage_cost` from `deploy_contract.code.len()`, subtracts it from `account.amount()`, adds it to `result.tokens_burnt`, and calls `account.set_amount(updated_balance)` directly on the mutable `Account` reference that is shared across all actions in the receipt. [4](#0-3)  It then calls `initiate_distribution`, which pushes a `GlobalContractDistribution` receipt into `result.new_receipts`—this receipt is what eventually triggers `apply_distribution_current_shard`, the code that actually writes the global contract bytes into state. [3](#0-2) [5](#0-4) 

When multiple actions exist in one action receipt, each action's result is merged into the aggregate `ActionResult` via a merge routine. On success, `tokens_burnt` and `new_receipts` accumulate; on failure of a merged action, `self.set_error(err)` is invoked, which sets `self.new_receipts.clear()`, `self.validator_proposals.clear()`, and `self.tokens_burnt = Balance::ZERO`. [6](#0-5)  This means: if action index 0 is `DeployGlobalContract` and action index 1 (or any later action in the same receipt) fails, the queued distribution receipt from action 0 is wiped out—no `GlobalContractDistribution` receipt is ever emitted, so `apply_distribution_current_shard` never runs and the contract code is never written to state.

However, the account debit from action 0 (`account.set_amount(updated_balance)`) already happened as a direct mutation of the shared `Account` struct, not via `ActionResult`. Per NEAR's documented action-execution semantics, when one action in a receipt fails, actions already executed keep their state effects (this is why `set_error` explicitly says it discards only "receipt-scoped state" like queued receipts and burnt/subsidized balances, while noting "Profile, gas counters, logs and `current_contracts` are kept — they reflect work already done"). The account balance decrease is exactly this kind of already-applied effect that is not reverted. So the signer pays `storage_cost` (an irrecoverable debit), yet the contract deployment is entirely aborted—no code lands on any shard, and no compensating refund receipt is generated for the storage cost.

### Impact Explanation
Any account submitting a transaction with `DeployGlobalContract` followed by any other action that deterministically fails (e.g., a `FunctionCall` invoking a non-existent method, an oversized/invalid action, or any action producing an `ActionError`) will have `storage_cost` permanently burnt from its balance while receiving zero service—the global contract is never distributed to any shard. This is a permanent, unrecoverable loss of user funds with no compensating refund path, violating the value-conservation invariant the question asks about ("fee charged must equal work performed"). This maps to the NEAR bounty category "token inflation or loss" (specifically fund loss without refund).

### Likelihood Explanation
This is fully attacker/user-controlled and trivially reproducible: an ordinary account only needs to construct a single transaction/receipt containing `DeployGlobalContract` as one action and any guaranteed-failing action afterward (no special privileges, keys, or timing needed). It is deterministic and repeatable on demand. The "attacker" in this scenario burns their own funds, so it does not enable theft from other users, but it does constitute unconditional, protocol-level fund destruction disproportionate to any service rendered, and can also occur accidentally (e.g., a wallet/dApp batching a `DeployGlobalContract` with other actions that unexpectedly fail due to gas/balance issues), silently costing users the global-contract storage fee for nothing.

### Recommendation
Either (a) defer the balance debit for `DeployGlobalContract` until after the distribution receipt has been confirmed queued and the overall receipt result is known to be `Ok`, or (b) make the debit conditional/reversible by not applying `account.set_amount` directly but instead tracking it in a way that participates in the same rollback as `tokens_burnt`/`new_receipts` in `set_error`, so a later action's failure in the same receipt fully reverts the storage-cost charge along with the distribution receipt it was meant to pay for.

### Proof of Concept
Runtime/test-loop integration test outline:
1. Create account `S` with sufficient balance to pay gas and the global-contract storage fee.
2. Build a transaction/receipt with actions: `[DeployGlobalContract{code}, FunctionCall{method_name: "nonexistent_method", ...}]` targeting `S` itself (or another action guaranteed to raise an `ActionError`, e.g., calling a method that doesn't exist in `code`, causing a `MethodResolveError`).
3. Apply the receipt and assert:
   - The overall `ExecutionOutcome` for the receipt is `Failure`.
   - `S`'s post-apply account balance decreased by exactly `storage_cost` (from `global_contract_storage_amount_per_byte * code.len()`).
   - No `GlobalContractCode` trie key exists in state for the identifier that would have been produced (confirm via `state_update.get(&TrieKey::GlobalContractCode{...})` returning `None`).
   - No `GlobalContractDistribution` receipt appears in the produced outgoing receipts.
4. Compare against a control case where `DeployGlobalContract` is the sole action and succeeds: verify the contract *is* written to state and the fee is burnt—demonstrating the discrepancy: same fee charged, but no work performed when bundled with a failing action.
