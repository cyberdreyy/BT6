Based on tracing the code, the claimed equality break does not hold up under the stated threat model.

**Key findings:**

1. `SignerEntries::parse` assigns `signer_id` by enumerating the `reward_set` slice it's given, in order [1](#0-0) . The node's `verify_signer_signatures` builds `signers_by_pk` the same way, by enumerating `reward_set.signers()` in slice order [2](#0-1) . Both sides derive index purely as a function of the specific `reward_set` value they're handed — there is no independent degree of freedom between them when they operate on the same `RewardSet`.

2. `pox_5_make_signer_set` always finishes by sorting the final `signer_set` strictly ascending by `signing_key` [3](#0-2) , and even the largest-remainder tie-break uses the same ascending `signing_key` ordering [4](#0-3) , and this is proven permutation-invariant by test [5](#0-4) . Order is a deterministic function of the aggregated stake entries, not an independent axis of divergence.

3. Reward-set lookup for both mining/verification and RPC-serving is bound to a specific tenure's electing sortition/consensus_hash, not to "whatever tip is currently canonical": `load_nakamoto_reward_set_for_tenure` takes the `tenure_snapshot` (the sortition whose consensus_hash the tenure's blocks carry) [6](#0-5) , and block-signature verification in the relay path loads the reward set keyed off `sn.block_height`'s reward cycle from that block's own sortition [7](#0-6) . The signer's RPC-fetched reward set (`get_reward_set_signers` → `/v3/stacker_set/{cycle}`) is served by the same `OnChainRewardSetProvider`/`read_reward_set_nakamoto_of_cycle` logic [8](#0-7) , reading whatever the honest node's own canonical view currently holds.

4. The scenario requires the reward set *itself* (i.e., which stackers/weights were computed for the cycle) to differ between two forks due to a "Hare-round boundary" difference — that is only possible if the prepare-phase anchor block computing that cycle's `.signers` differs between forks, which is a reward-cycle-anchor-level reorg, not something a single unprivileged miner-slot winner ("attacker-won competing sortition") can force within a normal tenure-competition scenario. Winning one sortition slot does not let an attacker rewrite which anchor block the PoX-5 reward-cycle computation used.

Because the mapping the question hinges on (signer_id assignment vs. node's `signers_by_pk`) is a pure function of the shared `reward_set` value, and reward-set retrieval on both node and signer sides is bound to the tenure/consensus_hash-derived sortition rather than "whichever tip happens to be current," there is no reachable path by which a single unprivileged attacker (one miner slot, no majority-signer/no node-compromise capability) can force a signer to sign against a reward set that diverges from what canonical block validation will use for that same block. Even in a hypothetical race, the block simply fails verification network-wide under the correct fork's reward set — it does not get miscounted into acceptance.
