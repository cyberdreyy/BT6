### Title
Funded instant-withdraw receipts persist per-epoch after claim and are double-counted / DoS users when the same epoch later defaults - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The analog of CVE-2024-38312 ("private/ephemeral data persisted incorrectly after termination") is stale per-epoch receipt data that survives its own settlement. `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never deletes `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) . If the same epoch subsequently defaults and is finalized, `_claimDefaultedInstantWithdrawRequest` resurrects the already-paid receipt as a defaulted-epoch claim basis [2](#0-1) .

### Finding Description
`requestInstantWithdraw` records receipt basis in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [3](#0-2) . On a normal funded claim, `claimInstantWithdrawRequest` burns the receipt and zeroes only `instantWithdrawsRequests[_user]`; both per-epoch mappings persist indefinitely [4](#0-3) . `collectInstantWithdrawFunds` likewise only decrements `pendingInstantWithdraws` [5](#0-4) .

Attack/breakage sequence, all unprivileged:

1. Epoch E is running; instant withdrawals enabled. Attacker (KYC-passing lender) deposits AA/BB, then calls `requestInstantWithdraw` via the CDO — `instantWithdrawsRequestsByEpoch[attacker][E] += amt` and `instantWithdrawClaimsByEpoch[E] += amt`.
2. Honest owner/manager collects funds (`collectInstantWithdrawFunds`); attacker calls `claimInstantWithdrawRequest` and is paid. Aggregate is 0, but per-epoch entries persist.
3. At `stopEpoch` of the same epoch E the borrower defaults; `finalizeDefault`/`finalizeDefaultRecovery` sets `defaultRecoveryEpoch = E`, `defaultRecoveryPrice`, `defaultRecoveryReserve`, and `defaultInstantWithdrawsFinalized = true`. The defaulted-epoch instant claims bucket `instantWithdrawClaimsByEpoch[E]` still includes the attacker's already-paid receipt, so the prefunded/unfunded split and the recovery price are computed against an inflated basis.
4. Attacker makes a new instant withdraw request in a later epoch (restoring `instantWithdrawsRequests[attacker] != 0` so the subtraction at line 848 passes) and calls `claimInstantWithdrawRequest`. `_claimDefaultedInstantWithdrawRequest` now clears the stale `instantWithdrawsRequestsByEpoch[attacker][E]` basis, burns `claimBasis` receipt tokens, and pays `claimBasis * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve` — a second payout for a receipt that was already settled at par [6](#0-5) .

If instead the attacker has no new receipt, step 4 reverts at `instantWithdrawsRequests[_user] -= claimBasis` (underflow) and `claimInstantWithdrawRequest` permanently reverts for every user who claimed an instant withdrawal in the defaulted epoch, freezing their subsequent claims [7](#0-6) .

### Impact Explanation
Two concrete outcomes depending on ordering:

- Direct theft from `defaultRecoveryReserve`: a user reclaims a haircut-paid amount for a receipt already paid at par, draining reserve owed to genuine default-epoch creditors (insolvency of the recovery pool by the full stale basis × `defaultRecoveryPrice`).
- Permanent freezing: users who claimed instant withdrawals in the defaulted epoch and later make any new instant request have `claimInstantWithdrawRequest` revert on underflow, permanently blocking that claim path.

Loss is bounded by total instant-withdraw volume claimed within the defaulted epoch, which can be a large fraction of the pool (instant withdraws draw on contract liquidity).

### Likelihood Explanation
Requires no privileged misbehavior: instant withdrawals enabled, at least one funded-and-claimed instant request during an epoch, and a borrower default in that same epoch — a normal adverse scenario the default-recovery machinery was explicitly built for. The stale-state write is deterministic (no per-epoch cleanup exists anywhere in the claim path). Caveat: I could not fully verify `finalizeDefaultRecovery`'s use of `instantWithdrawClaimsByEpoch` within the search budget; if it independently snapshots unfunded basis via `pendingInstantWithdraws` rather than the per-epoch map, the reserve mispricing portion reduces to the double-claim/DoS described above, which stands regardless.

### Recommendation
- In `claimInstantWithdrawRequest`, when clearing a funded claim, also clear the request's per-epoch entries: subtract `amount` from `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` and `instantWithdrawClaimsByEpoch[requestEpoch]`. This requires tracking each request's epoch (e.g., a `lastInstantWithdrawRequestEpoch` marker mirroring `lastWithdrawRequest`, or clearing the mapping keyed by the epoch recorded at request time).
- Alternatively, in `_claimDefaultedInstantWithdrawRequest`, cap `claimBasis` to the portion of `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` still backed by an unfunded `instantWithdrawsRequests` balance, and treat funded-claimed basis as already settled.
- Add a regression test: funded instant claim inside epoch E → borrower default at E's stopEpoch → finalize → assert the claimant cannot reclaim and that `instantWithdrawClaimsByEpoch[E]` only reflects unfunded receipts.

```solidity
function testStaleInstantReceiptDoubleClaim() external {
    // 1. Epoch E running; enable instant withdrawals
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 1e18, false);

    // 2. Attacker deposits and requests instant withdraw in epoch E
    uint256 tranches = _depositWithUser(attacker, 100e6);
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(tranches, tranche); // via CDO -> vault.requestInstantWithdraw

    uint256 epochE = strategy.epochNumber();
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epochE), expectedBasis);

    // 3. Fund + claim inside epoch E (borrower still healthy)
    _fundInstantWithdraws();              // collectInstantWithdrawFunds via CDO
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(strategy.instantWithdrawsRequests(attacker), 0);
    // BUG: per-epoch entries survive
    assertGt(strategy.instantWithdrawsRequestsByEpoch(attacker, epochE), 0);
    assertGt(strategy.instantWithdrawClaimsByEpoch(epochE), 0);

    // 4. Same epoch E defaults at stopEpoch; finalize recovery
    _borrowerDefaultsAtStopEpoch();       // stopEpochWithDuration loss / handleBorrowerDefault

    // 5a. DoS path: a new instant request then claim -> revert on stale-basis subtraction
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(1, tranche);
    vm.prank(attacker);
    vm.expectRevert(); // underflow / burn of non-existent receipt
    cdoEpoch.claimInstantWithdrawRequest();

    // 5b. Theft path (with sufficient new receipt balance): attacker is paid
    // claimBasis * defaultRecoveryPrice from defaultRecoveryReserve a second time.
    // uint256 reservePre = strategy.defaultRecoveryReserve();
    // ... claim succeeds, reserve decreases by stale basis * price ...
}
```

The assertion at step 3 (`instantWithdrawsRequestsByEpoch` still nonzero after full claim) is the minimal reproduction of the persisted-state bug; steps 4–5 demonstrate fund impact and DoS.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
