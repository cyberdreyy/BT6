Looking at the Sui bridge code, I need to trace the exact analog of the Axelar bug: tokens committed on the source chain that cannot be recovered when the destination-side claim permanently fails.

The key code path is in `claim_token_internal` in `bridge.move`:

- V2 messages get `bypass_limiter = true` after 48 hours (escape hatch)
- V1 messages always have `bypass_limiter = false` (no escape hatch, ever)
- `bridgeERC20` (V1) is still callable on `SuiBridgeV2` (inherited, not disabled)
- If a V1 transfer amount exceeds the 24h bridge limit, the claim permanently fails — the 24h window reset does not help because the single transfer amount itself exceeds the total limit

The EVM-side lock is committed; the Sui-side `BridgeRecord` stays `claimed: false` forever with no recovery path.

### Title
V1 Bridge Messages Permanently Locked When Transfer Amount Exceeds Bridge Limit — (File: `crates/sui-framework/packages/bridge/sources/bridge.move`)

### Summary
`claim_token_internal` only sets `bypass_limiter = true` for message version 2. V1 messages (`bridgeERC20` on EVM, `send_token` on Sui) always go through the limiter with no time-based escape hatch. If a V1 transfer's notional USD value exceeds the per-route 24-hour limit, the Sui-side claim permanently fails: the 24-hour rolling window reset does not help because the single transfer amount itself exceeds the total window capacity. The EVM-side tokens remain locked in the vault with no on-chain recovery path.

### Finding Description
In `claim_token_internal`, the bypass flag is initialized to `false` and only flipped for version-2 messages:

```move
let mut bypass_limiter = false;
if (record.message.message_version() == 2) {
    let token_payload_v2 = record.message.extract_token_bridge_payload_v2();
    let timestamp = token_payload_v2.timestamp_ms();
    bypass_limiter = clock.timestamp_ms() > timestamp + 48 * 3600000;
    token_payload = token_payload_v2.to_token_payload_v1();
} else {
    token_payload = record.message.extract_token_bridge_payload();
    // bypass_limiter stays false — no escape hatch
};
``` [1](#0-0) 

When the limiter check fails, the function returns `(option::none(), owner)` without setting `record.claimed = true`:

```move
if (!bypass_limiter && !inner.limiter.check_and_record_sending_transfer<T>(...)) {
    event::emit(TokenTransferLimitExceed { message_key: key });
    return (option::none(), owner)
};
``` [2](#0-1) 

The `BridgeRecord` is left with `claimed: false` permanently. Because the limiter is a 24-hour rolling window with a fixed total cap, a single transfer whose notional value exceeds the cap can never pass the check regardless of how many times it is retried.

On the EVM side, `bridgeERC20` (V1) is still callable on `SuiBridgeV2` because `SuiBridgeV2 is SuiBridge` and the function is not overridden or disabled: [3](#0-2) 

The EVM deposit path locks tokens in the vault and emits `TokensDeposited` (V1 event). The bridge node creates a V1 `BridgeMessage` for this event. The Sui-side `approve_token_transfer` stores a V1 `BridgeRecord`. The claim then permanently fails.

The mainnet limit for ETH→Sui is 5 000 000 USD per 24 hours: [4](#0-3) 

Any single V1 transfer whose notional value exceeds this cap is permanently unclaimable without a governance limit increase.

The V2 update was specifically introduced to add the 48-hour bypass for mature messages, but V1 messages were not deprecated or disabled, leaving a permanent-lock path open.

### Impact Explanation
A user who calls `bridgeERC20` (V1) on `SuiBridgeV2` with a transfer amount whose notional USD value exceeds the bridge limit will have their EVM tokens permanently locked in the vault. The Sui-side `BridgeRecord` stays `claimed: false` indefinitely. There is no on-chain refund or recovery mechanism. This is a permanent fund lock matching the "High or Medium" impact class in the HackenProof scope.

### Likelihood Explanation
`bridgeERC20` is a public function callable by any ordinary user. Institutional or automated integrations that have not updated to `bridgeERC20V2` can trigger this path. On mainnet the threshold is $5 M USD per 24 hours; a single large transfer using the old API crosses it. Likelihood is low-to-medium but the impact is permanent and irreversible without governance intervention.

### Recommendation
1. Override `bridgeERC20` in `SuiBridgeV2` to revert, forcing callers to use `bridgeERC20V2`.
2. Alternatively, add a time-based bypass for V1 messages in `claim_token_internal` analogous to the V2 bypass (e.g., treat any V1 message older than 48 hours as bypass-eligible using block timestamp at approval time).
3. Emit a clear on-chain warning or revert path so users are not silently stuck.

### Proof of Concept
1. User calls `bridgeERC20(ETH_TOKEN_ID, 2_000_00000000, suiRecipient, SUI_CHAIN_ID)` on `SuiBridgeV2` — this locks ~2 000 ETH (~$5.2 M at $2 600/ETH) in the vault and emits `TokensDeposited` (V1 event). [5](#0-4) 

2. Bridge node picks up `TokensDeposited`, creates a V1 `BridgeMessage` (no timestamp field), and calls `approve_token_transfer` on Sui. A `BridgeRecord` with `message_version = 1` and `claimed = false` is stored. [6](#0-5) 

3. User (or relayer) calls `claim_and_transfer_token<ETH>(bridge, clock, ETH_CHAIN, seq_num, ctx)`. Inside `claim_token_internal`, `bypass_limiter` stays `false` because `record.message.message_version() != 2`. [1](#0-0) 

4. `check_and_record_sending_transfer` computes notional value ≈ $5.2 M > $5 M limit → returns `false`. [7](#0-6) 

5. `TokenTransferLimitExceed` is emitted; `record.claimed` remains `false`; function returns `(option::none(), owner)`. [8](#0-7) 

6. User retries after 24 hours. The rolling window resets, but the single transfer amount ($5.2 M) still exceeds the $5 M cap. Step 4–5 repeat indefinitely.

7. The 2 000 ETH remain locked in the EVM vault. The Sui recipient receives nothing. There is no on-chain path to refund or re-route the funds.
