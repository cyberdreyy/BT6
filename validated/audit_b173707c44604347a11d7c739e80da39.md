### Title
External-Initiator credential escalates to `run`-role User and can trigger runs of arbitrary jobs with no EI-to-job binding check - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` authenticates only that *some* external-initiator (EI) credential is valid, then unconditionally injects a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` into the Gin context under the same `SessionUserKey` used for real authenticated users. Because `PipelineRunsController.Create` distinguishes "user vs EI" solely by checking for the presence of that same key (`auth.GetAuthenticatedUser`), any valid EI credential is treated as a full run-role user and can call `RunJobV2` for **any** integer job ID, without checking that the EI is bound to that job at all.

### Finding Description
`AuthenticateExternalInitiator` verifies the caller's EI credential (`bridges.AuthenticateExternalInitiator`) against the corresponding `ExternalInitiator` row, but performs no check tying that EI to any specific job/webhook spec. It then does: [1](#0-0) 
This sets `SessionUserKey` to a fresh `User{Role: UserRoleRun}` — the exact same key used by `AuthenticateBySession`/`AuthenticateByToken` for real user sessions: [2](#0-1) [3](#0-2) 

The route `POST /v2/jobs/:ID/runs` is gated by both EI and user auth methods, then `RequiresRunRole`: [4](#0-3) 
`RequiresRunRole` only rejects `UserRoleView`; the synthetic EI user has `UserRoleRun`, so it passes trivially: [5](#0-4) 

Inside `PipelineRunsController.Create`, the code attempts to restrict integer-ID job runs to real users only, explicitly commenting "EIs not allowed": [6](#0-5) 
However, the `isUser` check is `auth.GetAuthenticatedUser(c)`, which only checks for the presence of `SessionUserKey` — it cannot distinguish a real authenticated user from the synthetic EI-injected user, since both are stored under the identical key with identical type (`*clsessions.User`). Because of this, an EI credential satisfies `isUser == true` and reaches `prc.App.RunJobV2(ctx, jobID, nil)` for an arbitrary attacker-chosen `jobID`, with no lookup of `external_initiator_webhook_specs` or any other binding between the authenticated EI and the target job.

Historically, EI-triggered runs were scoped to a job's `externalJobID` (UUID) matched against the job's registered EI in `external_initiator_webhook_specs`, but that entire webhook-by-UUID code path has been removed and now unconditionally errors out: [7](#0-6) 
This leaves the integer-ID path as the only viable path for any caller possessing a `SessionUserKey`-bearing session — including EIs — with **no replacement authorization check** for EI-to-job binding.

### Impact Explanation
An attacker who holds any single valid EI credential (even one issued for an unrelated bridge/job) can invoke `RunJobV2` on any job ID in the node, not just jobs associated with their EI. This is an authorization/role-boundary bypass enabling unauthorized triggering of job runs across the entire node — which can result in unintended on-chain transactions, resource exhaustion (DoS via pipeline run flooding), or manipulation of pipeline execution for jobs the attacker has no legitimate relationship to. This matches the "unauthorized job run" bounty impact class.

### Likelihood Explanation
The only precondition is possession of a single valid, even unrelated, external-initiator access key/secret pair — a low-privilege credential by design (meant to trigger only its own bound webhook). No admin/session/token credentials are required, and the path is a standard, unauthenticated-by-default HTTP route (`/v2/jobs/:ID/runs`) reachable by anyone holding EI creds. The vulnerability is deterministic and repeatable for any job ID.

### Recommendation
Do not reuse `SessionUserKey` to represent EI callers. Instead, use `GetAuthenticatedExternalInitiator` to detect EI-origin requests distinctly from real users in `PipelineRunsController.Create`, and reject/scope EI-triggered runs to only the jobs that are actually bound to that EI (e.g., via a lookup analogous to the removed `external_initiator_webhook_specs` binding, or reintroducing an explicit EI-to-job authorization check before calling `RunJobV2`).

### Proof of Concept
Handler-level integration test plan:
1. Create two jobs, Job A and Job B (both webhook or any job runnable via `RunJobV2` by int ID).
2. Register EI `A` with no association to Job B.
3. Authenticate as EI `A` using `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`.
4. POST to `/v2/jobs/<Job B's int ID>/runs` using EI `A`'s credentials.
5. Assert response is `200 OK` with a `pipelineRun` resource (i.e., `RunJobV2` was invoked for Job B), proving `RequiresRunRole(prc.Create)` succeeded and no EI-to-job binding check exists — despite EI `A` never being registered for Job B's webhook.
6. As a control, verify `GetAuthenticatedExternalInitiator(c)` returns EI `A`'s identity in this same request context, confirming the request was authenticated as an EI (not a real user), yet still passed the "only users allowed" check in `prc.Create`.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
