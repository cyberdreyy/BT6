### Title
Deterministic account deployment onto a pre-existing (front-run) account preserves attacker access keys - (File: runtime/runtime/src/deterministic_account_id.rs)

### Summary
`action_deterministic_state_init` gates the "deploy contract" step solely on `account.contract().is_none()`, without checking whether the account already existed before this receipt. An attacker can pre-create the exact `0s<hex>` deterministic account id with an ordinary `CreateAccount` + `AddKey` transaction (unrestricted because such ids are >32 chars), leaving `AccountContract::None`. When the legitimate depositor's `DeterministicStateInitAction` later lands on that same account, the runtime deploys the contract on top of the attacker-controlled account and never removes the attacker's key.

### Finding Description
`action_deterministic_state_init` at [1](#0-0)  only creates a fresh account via `create_deterministic_account` when `maybe_account` is `None`; if the account already exists (`maybe_account` is `Some`), it reuses that existing `Account` object directly. The subsequent decision to deploy the contract (`deploy_deterministic_account`) is gated only by `account.contract().is_none()` — this condition is true both for a brand-new "nonexist → uninit" account and for a pre-existing account that simply happens to have no contract deployed, e.g. one created and left contract-less by an attacker's own `CreateAccount` action.

The account id target, `0s<hex>`, is derived by `derive_near_deterministic_account_id` at [2](#0-1) , and its exactness is enforced only at the action-validation layer by `validate_deterministic_state_init` at [3](#0-2) , which merely checks `derived_id == receiver_id`. Nothing in this check, nor in `action_deterministic_state_init`, verifies that the receiver account is in the NEP-616 "nonexist" state before allowing deployment.

Because the id is 42 characters (`0s` + 40 hex chars), which exceeds the top-level account name length restriction (only names ≤32 chars require the `near` registrar as predecessor), an attacker can submit an ordinary transaction with `CreateAccount` followed by `AddKey` (full access) directly targeting that id. `CreateAccount`'s actor-id update means the following `AddKey` in the same receipt is authorized against the newly created account. This leaves an account with `AccountContract::None` and an attacker-owned full-access key sitting at the exact address the victim's factory will later target.

When the victim's `DeterministicStateInitAction` receipt is later applied to that same `account_id`, `maybe_account` is `Some(existing attacker-created account)`, `account.contract().is_none()` is still true, so `deploy_deterministic_account` proceeds and deploys the code/data, and the victim's deposit is applied via `check_storage_stake`. The attacker's previously added full-access key is never revoked, list of access keys is untouched by this code path — see the comment at [4](#0-3)  which only speaks to `actor_id`, not to any pre-existing access keys on the account. The end state is an account holding the victim's funds/code plus the attacker's full-access key.

### Impact Explanation
This breaks the authorization-exactness invariant NEP-616 relies on: only the deriver of a `DeterministicAccountStateInit` should ever control keys usable against the deployed contract. Here, an unprivileged attacker predicting or learning a victim's `state_init` (e.g., a public factory template) can obtain a full-access key on the account that ends up holding the victim's deposited funds and deployed contract, enabling theft of those funds. This matches the "Contracts execution flows / Unauthorized transaction" bounty category, with concrete impact of theft of user funds via authorization escalation on a promise/receipt boundary.

### Likelihood Explanation
Preconditions are modest: the attacker only needs to predict the `state_init` (via a known factory contract or template) before it is submitted, and race to create the account first with a cheap `CreateAccount`+`AddKey` transaction — no privileged role required. This is fully repeatable against any deterministic-account deployment flow where `state_init` content is derivable off-chain ahead of the funding transaction (a realistic pattern for factory-style deployments described in the NEP).

### Recommendation
`action_deterministic_state_init` must track whether the account existed prior to this receipt (i.e., whether `maybe_account` started as `None`) and only permit the `uninit → active` deployment transition when the account is verified to be in the genuine NEP-616 "nonexist"/"uninit" state — specifically, verify the account has zero existing access keys (and no contract) before deploying, or otherwise refuse to deploy onto an account with any pre-existing access key. Alternatively/additionally, reject the `DeterministicStateInitAction` outright (returning an `ActionError`) if the target account already has any `AccessKey` in the trie.

### Proof of Concept
Runtime apply-path integration test (test-loop or `runtime/runtime/src/tests`):
1. Compute `state_init` for a template contract/data and derive `account_id = derive_near_deterministic_account_id(&state_init)`.
2. Build and apply receipt A from an attacker account: actions `[CreateAccount, AddKey(full_access, attacker_pubkey)]` targeting `account_id`. Assert it succeeds and the account now exists with `AccountContract::None` and one `AccessKey` for `attacker_pubkey`.
3. Build and apply receipt B: `DeterministicStateInitAction { state_init, deposit }` from the victim, targeting the same `account_id`.
4. Assert receipt B succeeds (no `ActionError`), and read the resulting `Account` record: assert `account.contract()` is `Some(...)` (deployed) AND the access key for `attacker_pubkey` is still present in the trie (`TrieKey::AccessKey`).
5. This demonstrates the attacker retains a full-access key on the account now holding the victim's deposited funds and deployed contract.

```rust
/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}
```

```rust
fn validate_deterministic_state_init(
    limit_config: &LimitConfig,
    action: &DeterministicStateInitAction,
    receiver_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    validate_global_contract_identifier(action.state_init.code())?;

    let derived_id = derive_near_deterministic_account_id(&action.state_init);

    if derived_id != *receiver_id {
        return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver {
            derived_id,
            receiver_id: receiver_id.clone(),
        });
    }
```
