### Title
`getMultipleAccounts` response size is bounded only by pubkey count (100), not by total account bytes, allowing ~1GB of base64-encoded data to be synchronously cloned/serialized in a single RPC call - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_multiple_accounts` enforces only `MAX_MULTIPLE_ACCOUNTS` (100) on the number of pubkeys per request, with no accompanying limit on the aggregate size of the account data being fetched and encoded. Because individual on-chain accounts can be up to the 10MiB `MAX_PERMITTED_DATA_LENGTH`, and `UiAccountEncoding::Base64` has no data-size cap comparable to the `MAX_BASE58_BYTES` guard applied to base58 output, a single call with 100 such pre-provisioned accounts forces the node to clone and base64-encode roughly 1GB of account data within one request/response cycle.

### Finding Description
The RPC handler pulls in `MAX_MULTIPLE_ACCOUNTS` from `solana_rpc_client_api::request` [1](#0-0) , which is used to reject requests with too many pubkeys, but this cap is purely a *count* limit — it says nothing about the size of the accounts referenced. Each pubkey is resolved via `get_encoded_account`, which loads the account (via `Bank::get_account_modified_slot` or similar), clones its data, and encodes it with `encode_ui_account` from `solana_account_decoder` [2](#0-1) . The `encode_ui_account` path applies a hard byte cutoff (`MAX_BASE58_BYTES`) only when the client requests base58 encoding; base64/base64+zstd encodings carry no equivalent cap, so the full account payload (up to 10MiB per account) is copied and serialized regardless of size. Since accounts of the maximum permitted size can legitimately be written on-chain ahead of time (a precondition explicitly allowed by the rules, "writing on-chain data that is later returned through those APIs"), an attacker only needs to reference 100 such pre-existing large accounts in one `getMultipleAccounts(encoding=base64)` call to force ~1GB of clone+encode work and response payload in a single request, with cost scaling linearly with on-chain data size rather than with any explicit per-request budget.

### Impact Explanation
This falls into the "RPC node resource exhaustion from a single low-rate call" category: a single JSON-RPC request causes O(accounts × max_account_size) memory allocation, CPU-bound base64 encoding, and network egress, none of which are capped by an explicit per-request byte or CPU budget — only by the incidental 100-pubkey count limit. Repeated at the permitted rate (one call per `CLUSTER_SLOT_TIME_TARGET/2`), this can meaningfully degrade RPC node memory and CPU availability, and is not excluded by SECURITY.md (which only explicitly excludes unfiltered `getProgramAccounts` without secondary indexes, not `getMultipleAccounts`).

### Likelihood Explanation
Feasibility depends on the attacker (or someone else) having previously funded/created 100 accounts at or near the 10MiB size limit, which is expensive (rent-exempt reserve for 10MiB accounts) but not prohibited by protocol rules, and is a one-time cost reusable for repeated attacks thereafter. Once such accounts exist, triggering the expensive read/encode/response path requires nothing more than a single unauthenticated `getMultipleAccounts` call, making it fully repeatable at the maximum allowed unprivileged call rate.

### Recommendation
Enforce an aggregate response-size or per-request byte/CPU budget for `getMultipleAccounts` (and similarly for `getAccountInfo`/`getProgramAccounts`) independent of the on-chain account size, e.g., summing account `data.len()` across the requested pubkeys before encoding and rejecting/erroring once a configurable threshold is exceeded, and extend the `MAX_BASE58_BYTES`-style cap to base64/base64+zstd encodings as well.

### Proof of Concept
Integration test plan (Rust, using `solana_rpc::rpc::JsonRpcRequestProcessor` test harness):
1. Create a `Bank` with `bank.store_account` used to store 100 distinct accounts, each with `data: vec![0u8; MAX_PERMITTED_DATA_LENGTH as usize]` (10MiB), owned by a test program.
2. Issue a single `getMultipleAccounts` RPC request (or call `JsonRpcRequestProcessor::get_multiple_accounts` directly) with all 100 pubkeys and `encoding: UiAccountEncoding::Base64`.
3. Measure process RSS delta and wall-clock latency of the single call.
4. Assert that response payload size and peak RSS delta stay under an explicit fixed budget (e.g., a few MB), and fail the test when total bytes returned scale linearly with `100 × 10MiB` (demonstrating today's actual behavior violates the intended invariant).
