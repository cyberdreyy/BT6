### Title
Post-default instant-withdraw requests collide with the defaulted-epoch receipt bucket and drain `defaultRecoveryReserve` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.requestInstantWithdraw` has no post-default handling. After `finalizeDefaultRecovery`, `epochNumber` still equals `defaultRecoveryEpoch`, so a fresh instant-withdraw receipt is recorded into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — the same slot that tracks receipts owed a haircut from the isolated recovery reserve. `claimInstantWithdrawRequest` then frees that slot as if it were defaulted-epoch basis and pays it out of `defaultRecoveryReserve`. This mirrors the GnuTLS double-free: an object (the epoch bucket) is released under an ownership assumption (defaulted-epoch claim) that does not hold for the new allocation written into it.

### Finding Description
`requestWithdraw` explicitly branches on `defaultRecoveryFinalized` and routes post-default requests into a separate `postDefaultRequests` map so they never mix with defaulted-epoch accounting (IdleCreditVault.sol:247-257). `requestInstantWithdraw` does not: it only calls `_ensureDefaultRecoveryInitialized`, then unconditionally writes `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount` and `instantWithdrawsRequests[_user] += _amount` (IdleCreditVault.sol:356-375). Post-default, `epochNumber` is frozen at `defaultRecoveryEpoch` because it is only incremented inside `deposit` during a running-epoch stop, which no longer occurs.

`claimInstantWithdrawRequest` then runs `_claimDefaultedInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` (IdleCreditVault.sol:382-385). That function treats the entire `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` as defaulted basis: it zeroes the slot, decrements `instantWithdrawsRequests`, `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch[defaultEpoch]`, burns `claimBasis` receipt tokens, and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` (IdleCreditVault.sol:842-856).

Because the reserve was sized in `finalizeDefaultRecovery` as `reserveAmount * RECOVERY_FULL / totalBasis` against the pre-finalization claim set (IdleCreditVault.sol:679-699), any post-default basis added under the same epoch key spends reserve earmarked for legitimate defaulted claimants. The comments at lines 635-649 confirm `instantWithdrawClaimsByEpoch[epochNumber]` is meant to capture only the default-epoch instant queue; post-default writes corrupt that invariant.

### Impact Explanation
- Theft under over-recovery: `recoveryPrice` is explicitly allowed above `RECOVERY_FULL` ("Recovery can be above par", line 687). A post-default requester deposits tranche tokens worth `R`, receives `R * recoveryPrice / RECOVERY_FULL > R` from the reserve — direct profit extracted from recovered funds belonging to defaulted-epoch claimants and active LPs.
- Insolvency at any price: even at `recoveryPrice < 1`, every post-default instant claim pays from `defaultRecoveryReserve` for basis never included in `totalBasis`, so the last defaulted-epoch claimants find the reserve depleted — permanent freezing/loss of their entitled recovery.
- An attacker needs only tranche tokens (a KYC-passing lender) and an instant-withdraw-enabled pool that defaults with `pendingInstantWithdraws != 0` (the prefunded-instant scenario already exercised in `testFinalizeDefaultHaircutsPendingInstantRedeems`).

### Likelihood Explanation
Requires a borrower default with a partially unfunded instant-withdraw queue at `finalizeDefaultRecovery` (so `defaultInstantWithdrawsFinalized` is set), and profit requires `reserveAmount > totalBasis` (over-recovery). The reserve-drain harm occurs even without over-recovery. No privileged cooperation is needed: the attacker transacts entirely through the public CDO instant-withdraw path after finalization. The asymmetric guarding between `requestWithdraw` and `requestInstantWithdraw` indicates the collision was not intended.

### Recommendation
Mirror the `requestWithdraw` post-default branch in `requestInstantWithdraw`: after `defaultRecoveryFinalized`, either revert instant withdrawals or record them in a dedicated post-default bucket (analogous to `postDefaultRequests`) that is paid at par or at a separately priced rate — never into `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]`. Additionally, key the defaulted instant claim on a snapshot flag per user rather than re-reading the live epoch bucket.

### Proof of Concept
Foundry fork PoC outline (mirroring `testFinalizeDefaultHaircutsPendingInstantRedeems` in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. Deposit with attacker + victim, enable instant withdraws.
// 2. Victim requests instant withdraw mid-epoch; pool stop leaves
//    pendingInstantWithdraws > 0 (partially prefunded).
// 3. Epoch stops with 0 repayment -> defaulted() == true.
// 4. finalizeDefault(recovered, manager) with recovered > totalBasis
//    so defaultRecoveryPrice > RECOVERY_FULL.
// 5. Attacker calls cdoEpoch.requestInstantWithdraw(amount) post-default.
//    Assert: strategy.instantWithdrawsRequestsByEpoch(attacker, defaultEpoch) == amount
//    i.e. the new receipt landed in the defaulted-epoch bucket.
// 6. Attacker calls cdoEpoch.claimInstantWithdrawRequest().
//    Assert: underlying received == amount * defaultRecoveryPrice / RECOVERY_FULL > amount
//    and defaultRecoveryReserve decreased by that amount, leaving victim's
//    defaulted claim unfunded (subsequent victim claim reverts or underpays).
```

Uncertainty: whether `IdleCDOEpochVariant.requestInstantWithdraw` itself blocks calls once `defaulted()`/`defaultRecoveryFinalized` is set could not be fully verified within the search budget; the strategy-level code path shown unconditionally accepts the request, and the fix belongs in `IdleCreditVault.requestInstantWithdraw` regardless.
