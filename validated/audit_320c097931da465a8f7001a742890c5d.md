### Title
Missing job/instance ownership check in `VaultController.VerifyDKGResult`/`ExportDKGResult` allows any authenticated caller to verify/export DKG results for arbitrary `instanceId` values - ([File: core/web/vault_controller.go])

### Summary
`VerifyDKGResult` and `ExportDKGResult` accept an attacker-supplied `instanceId` from the JSON body and pass it directly to `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage(...)` with no check that the caller (session user, API-token holder, or an external-initiator credential forced to `UserRoleRun`) is actually authorized for that specific vault/OCR2 job instance. [1](#0-0) [2](#0-1)  Because there is no per-instance authorization binding, any caller who can reach this route (whatever role is minimally required by the router middleware) can retrieve or verify DKG result data belonging to a completely unrelated vault plugin job simply by guessing/enumerating another `instanceId`.

### Finding Description
Both handlers follow the same pattern: decode `InstanceID` from the untrusted request body, then call `orm.ReadResultPackage(ctx, dkgocrtypes.InstanceID(req.InstanceID))`, which performs a global lookup by instance ID with no join/filter against the authenticated identity, job ownership, or external-initiator's assigned job. [3](#0-2) [4](#0-3)  The only gating in the codebase for external-initiator-authenticated requests is the generic role check performed by `auth.RequiresRunRole`, which merely verifies `user.Role != UserRoleView` — it never inspects which specific job/instance the caller is entitled to act on. [5](#0-4)  `AuthenticateExternalInitiator` unconditionally sets the session user to `UserRoleRun` regardless of which external initiator/job the credential was issued for. [6](#0-5)  Consequently, once any run-role-or-higher caller can reach this route, the handler itself provides no "one authorized job" binding — it will happily verify/export the DKG result for any `instanceId` present in the vault ORM, not just the instance tied to the caller's own job/EI credential.

Note: I was unable to fully confirm from `core/web/router.go` which exact middleware chain (session, API token, and/or `AuthenticateExternalInitiator`) is applied to the `/vault/dkg_results/verify` and `/vault/dkg_results/export` routes before the audit iteration budget was exhausted; the index search only confirmed matches exist there without retrieving line content. However, the vulnerability (missing per-instance authorization inside the handler) is confirmed and holds for whatever the minimum role required by the router is, including a restricted API-token holder at run role, satisfying the rule's allowed unprivileged-attacker categories independent of the exact EI-authentication path.

### Impact Explanation
This breaks tenant/job isolation for the Vault DKG capability: a caller authorized only for one workflow/job can read cryptographic verification material and export the raw `ReportWithResultPackage` (containing the DKG result package/shares) for a different, unrelated vault plugin job instance. This matches the bounty class of "cross-user response confusion" / unauthorized access to another job's secrets/keys material, since DKG result packages are sensitive vault-secret-management artifacts.

### Likelihood Explanation
Exploitability only requires: (1) network access to the node's authenticated API surface, and (2) any low-privilege run-role credential (session, API token, or external-initiator credential) valid for some job. No admin/operator access is needed. The attacker only needs to know or guess another job's `instanceId` string, which may be observable (e.g., from job specs, logs, or GraphQL/job listing endpoints) even without permission to act on that job.

### Recommendation
Add explicit authorization scoping in `VerifyDKGResult`/`ExportDKGResult`: resolve the caller's authorized job(s) (for session/API-token users, via job ownership; for external-initiator credentials, via the EI's bound `ExternalJobID`) and verify that the resolved job's DKG instance matches `req.InstanceID` before calling `ReadResultPackage`. Reject with 403/404 on mismatch, and ensure `AuthenticateExternalInitiator`-derived requests are limited to the EI's own bound job/instance rather than any instance ID supplied in the body.

### Proof of Concept
Handler-level integration test in `core/web/vault_controller_test.go`:
1. Seed two DKG result packages in the vault ORM tied to two distinct `instanceId`s (`jobA-instance`, `jobB-instance`), each conceptually owned by a different job.
2. Create an external-initiator (or run-role API token) credential associated only with the job producing `jobA-instance`.
3. Authenticate as that credential and POST to `/vault/dkg_results/verify` (and `/vault/dkg_results/export`) with `instanceId = jobB-instance` and a valid `masterPublicKey`.
4. Assert the current behavior returns `200 OK` with `jobB`'s result data (or successful verification), demonstrating the missing scoping.
5. Expected/fixed behavior: assert `403 Forbidden` or `404 Not Found` because the caller's credential is not bound to `jobB-instance`.

func (vc *VaultController) VerifyDKGResult(c *gin.Context) {
	var req VerifyDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" || req.MasterPublicKey == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId and masterPublicKey are required"))
		return
	}

	keys, err := vc.App.GetKeyStore().DKGRecipient().GetAll()
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
	if len(keys) == 0 {
		jsonAPIError(c, http.StatusBadRequest, errors.New("no DKG recipient key found"))
		return
	}
	if len(keys) > 1 {
		jsonAPIError(c, http.StatusBadRequest, errors.New("multiple DKG recipient keys found"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
