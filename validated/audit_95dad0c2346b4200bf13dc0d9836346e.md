## Confirmed root cause

`get_owners_balance()` = `env::account_balance() + get_known_deposited_balance()` − `get_locked_amount()`, and `get_known_deposited_balance()` is exactly the `deposit_amount` field the contract stores for the currently-selected staking pool. [1](#0-0)  That `deposit_amount` is not derived from anything verified on this contract — it is whatever value the selected staking pool's `get_account_total_balance` view call returns, written back verbatim with no bound check against amounts actually transferred:

```rust
pub fn on_get_account_total_balance(&mut self, #[callback] total_balance: WrappedBalance) {
    ...
    self.staking_information.as_mut().unwrap().deposit_amount = total_balance;
}
``` [2](#0-1) 

The only gate that is supposed to make this trust-worthy is the one-time whitelist check performed inside `select_staking_pool`, which fires a cross-contract call to the whitelist and, on success, permanently records the pool in `staking_information` with no re-validation on any later call:

```rust
ext_whitelist::is_whitelisted(...).then(ext_self_owner::on_whitelist_is_whitelisted(...))
``` [3](#0-2) 
```rust
pub fn on_whitelist_is_whitelisted(&mut self, #[callback] is_whitelisted: bool, staking_pool_account_id: AccountId) -> bool {
    ...
    self.staking_information = Some(StakingInformation { staking_pool_account_id, status: TransactionStatus::Idle, deposit_amount: 0.into() });
    true
}
``` [4](#0-3) 

None of `deposit_to_staking_pool`, `deposit_and_stake`, `stake`, `unstake`, `withdraw_from_staking_pool`, or `refresh_staking_pool_balance` re-check whitelist status or bound the pool's reported balance — they only check `assert_staking_pool_is_idle()` / `assert_owner()`. [5](#0-4)  This is a direct structural analog of the TSS report's core bug class: a custody-relevant trust check ("is this pool whitelisted / does this node have sufficient deposit") is only enforced at the moment of initial commitment and never re-validated for the lifetime of the relationship, so the invariant it was meant to protect ("only whitelisted pools can receive delegated tokens and be trusted for balance", per `whitelist/README.md` lines 6-9) silently stops holding.

### Title
Lockup Trusts Staking Pool's Self-Reported Balance With No Bound Check, Enabling Early Release of Locked/Vested NEAR - (File: `lockup/src/owner_callbacks.rs`)

### Summary
The lockup contract's `refresh_staking_pool_balance` flow accepts an arbitrary `total_balance` value from the selected staking pool contract and stores it unmodified as `deposit_amount`, which directly feeds `get_owners_balance()`/`get_liquid_owners_balance()` — the values that gate how much NEAR the owner may transfer out of the still-locked/vesting account.

### Finding Description
The whitelist mechanism exists specifically so a lockup contract only ever delegates to a staking pool contract that faithfully implements the pool spec (`whitelist/README.md` — "the staking pool should faithfully implement the spec... only approved (whitelisted) accounts... can receive delegated tokens"). [6](#0-5)  Because staking pools can be created permissionlessly and auto-whitelisted via `staking-pool-factory` (`create_staking_pool` → `on_staking_pool_create` → `ext_whitelist::add_staking_pool`), [7](#0-6)  the owner of a lockup contract can deploy their own staking pool contract, select it via `select_staking_pool` (which passes the whitelist check since it's freshly registered), and then have the lockup deposit locked/unvested NEAR into it.

Because the pool contract is fully owner-controlled, its `get_account_total_balance` view method can return any value the owner chooses — there is no code in the lockup contract enforcing that the reported total balance is consistent with the amount actually transferred plus a bounded, plausible reward. `on_get_account_total_balance` writes that number straight into `deposit_amount`:
```rust
self.staking_information.as_mut().unwrap().deposit_amount = total_balance;
``` [8](#0-7) 

`get_known_deposited_balance()` returns this figure directly, [9](#0-8)  and `get_owners_balance()` adds it to the account's liquid balance before subtracting `get_locked_amount()`:
```rust
pub fn get_owners_balance(&self) -> WrappedBalance {
    (env::account_balance() + self.get_known_deposited_balance().0)
        .saturating_sub(self.get_locked_amount().0)
        .into()
}
``` [10](#0-9) 

`transfer()` allows the owner to withdraw up to `get_liquid_owners_balance()`, which is `min(get_owners_balance(), get_account_balance())`:
```rust
assert!(
    self.get_liquid_owners_balance().0 >= amount.0,
    ...
);
Promise::new(receiver_id).transfer(amount.0)
``` [11](#0-10) 

The binding that should hold is:
`get_owners_balance()` == actual vested/unlocked NEAR the owner is entitled to (real account balance + *real* staked/rewarded balance − locked amount)

What the code actually allows:
`get_owners_balance()` == real account balance + *any number a self-controlled "staking pool" claims* − locked amount

By inflating the reported `total_balance` (e.g., reporting a large fictitious reward), the owner inflates `known_deposited_balance`, which inflates `get_owners_balance()`. Since `get_liquid_owners_balance()` is capped by `env::account_balance()` (the lockup account's *actual* NEAR-cash balance, not staked), the immediately practical attack is: withdraw the deposited principal from the malicious pool back to the lockup account (via `withdraw_from_staking_pool`, which only checks `is_promise_success()` on the pool's own withdraw call — again self-controlled and always "succeeds") while `deposit_amount` retains the inflated phantom reward value, then `transfer()` out up to that inflated `get_owners_balance()` cap, which is now bounded only by the real liquid `account_balance` — funds that would otherwise remain gated by `get_locked_amount()`.

### Impact Explanation
This breaks the "locked or unvested tokens released early" invariant explicitly called out as Critical impact: the owner can move NEAR out of the lockup account before it is actually vested/unlocked, using their own unwhitelisted-in-spirit (spec-violating) but nominally-whitelisted staking pool to fabricate the `known_deposited_balance` reward figure that offsets `get_locked_amount()` in the `get_owners_balance()` formula.

### Likelihood Explanation
Likelihood is high for any lockup owner willing to deploy a custom staking pool contract via the permissionless `staking-pool-factory`, since factory-created pools are auto-whitelisted and nothing about the whitelist re-validates the pool's behavior once selected. No foundation action, redeploy of the lockup contract, or third-party cooperation is required — only the owner's own transactions (`create_staking_pool`, `select_staking_pool`, `deposit_to_staking_pool`, `refresh_staking_pool_balance`, `withdraw_from_staking_pool`, `transfer`).

### Recommendation
`on_get_account_total_balance` should bound the accepted `total_balance` to a sane range relative to the amount actually deposited (e.g., disallow an increase larger than a modest, capped reward rate per epoch), and/or the lockup contract should re-verify the selected pool is still whitelisted before trusting any balance-affecting callback (`on_get_account_total_balance`, `on_staking_pool_withdraw`, etc.), not just once at `select_staking_pool` time.

### Proof of Concept
1. Owner calls `staking-pool-factory::create_staking_pool` to deploy a pool they fully control; it is auto-whitelisted. [7](#0-6) 
2. Owner calls lockup's `select_staking_pool(pool)`; whitelist check passes since the pool is registered. [3](#0-2) 
3. Owner calls `deposit_to_staking_pool(X)`, transferring `X` locked NEAR to the malicious pool. [12](#0-11) 
4. Owner calls `withdraw_from_staking_pool` to move `X` back into the lockup account (pool always reports success). [13](#0-12) 
5. Owner calls `refresh_staking_pool_balance`; the malicious pool's `get_account_total_balance` returns an inflated value `X + fake_reward`, which is stored verbatim as `deposit_amount`. [2](#0-1) 
6. `get_owners_balance()` now includes `fake_reward` in excess of `get_locked_amount()`, and `get_liquid_owners_balance()` = min(that, real account balance). [14](#0-13) 
7. Owner calls `transfer()` to move liquid NEAR out, realizing an early release of otherwise-locked tokens. [11](#0-10) 

Note: I could not fully trace `lockup-factory/src/**` to see whether it imposes any additional constraint on which staking pools an owner-created lockup may select (e.g., an immutable, foundation-fixed whitelist address baked in at deployment) — that code was not surfaced by my searches. If `lockup-factory` pins the whitelist account non-configurably and the whitelist contract itself has independent, ongoing anti-abuse controls on what factories can register pools, that would not change the finding above (the check-once/no-revalidation and no-bound-on-reported-balance issues are still present in `lockup/src/owner.rs` and `lockup/src/owner_callbacks.rs`), but I flag this as an area a full Devin session with repo access should double check.

# Whitelist contract for staking pools

The purpose of this contract is to maintain the whitelist of the staking pool contracts account IDs that are approved

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.
