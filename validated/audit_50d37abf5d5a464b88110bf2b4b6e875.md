### Title
Stale `pendingInstantWithdraws` excludes prior-epoch unfunded instant receipts from `defaultPendingClaimBasis`, permanently freezing them after `finalizeDefaultRecovery` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The analog of CVE-2019-19952's use-after-free is a stale-pointer/stale-accounting bug in `IdleCreditVault`: instant-withdraw debt is tracked globally in `pendingInstantWithdraws` but the default-recovery claim basis is taken only from the current-epoch bucket `instantWithdrawClaimsByEpoch[epochNumber]`. An unfunded instant receipt created in an earlier epoch keeps `pendingInstantWithdraws != 0` — which flips `defaultInstantWithdrawsFinalized` on — while contributing nothing to `totalBasis` in `finalizeDefaultRecovery`. After finalization the holder's claim can never be paid: `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]`, and the fallback `_transferFundedClaim` reverts because the underlyings were never collected and the recovery reserve cannot be spent.

### Finding Description
`defaultPendingClaimBasis()` adds instant claims only for the current epoch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:644
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

`pendingInstantWithdraws` is incremented in `requestInstantWithdraw` (line 374) and decremented only by `collectInstantWithdrawFunds` (line 401) or pro-rata claim clearing (line 852). It is a global aggregate — it does not distinguish which epoch the unfunded receipt belongs to. `instantWithdrawClaimsByEpoch`, however, is per-epoch.

If a user's instant request in epoch N remains unfunded (borrower/manager never calls `getInstantWithdrawFunds`, or funds only partially arrive), `pendingInstantWithdraws` stays non-zero into epochs N+1, N+2…. When the pool later defaults in epoch M and `finalizeDefaultRecovery` runs:

- `defaultPendingClaimBasis()` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[M]` — the stale epoch-N receipt is missing from `totalBasis`, so `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed on an understated basis (over-paying all default-epoch claimants relative to fair pro-rata).
- `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` becomes `true` (line 696) purely because of the stale receipt.
- Post-finalization, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which only reads `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` (line 844) — zero for the epoch-N receipt — then falls through to `_burn` + `_transferFundedClaim` for the full `instantWithdrawsRequests[user]`. `_transferFundedClaim` reverts `NotAllowed` when `balance - defaultRecoveryReserve < amount` (lines 899–905), and the tokens were never pulled in via `collectInstantWithdrawFunds`, so the call reverts permanently.

The receipt is "freed" from the accounting basis but still referenced by the claim path — the same stale-reference shape as the MNG use-after-free: an object cleared in one structure (`instantWithdrawClaimsByEpoch` keyed by the wrong epoch) while still reachable through another (`instantWithdrawsRequests` / `pendingInstantWithdraws`).

### Impact Explanation
- The epoch-N instant receipt holder's claim is permanently frozen: every `claimInstantWithdrawRequest` reverts, and `requestWithdraw` post-default also reverts for them via `_hasWithdrawRequest`/instant checks, so there is no alternative exit.
- Fair-loss-distribution invariant is broken for everyone else: `totalBasis` omits a real claim, inflating `defaultRecoveryPrice` and over-distributing the recovery reserve to default-epoch claimants and active LPs (`activeFinalNAV` minted/burned on the same inflated price, lines 699–705).
- Quantified loss: the frozen user loses their entire instant receipt amount; other claimants receive `reserve * (basis + staleReceipt) / basis` times more than the fair share.

### Likelihood Explanation
Requires: (1) an instant-withdraw request left unfunded across an epoch boundary (possible whenever `getInstantWithdrawFunds` is not called or the borrower underfunds — the code explicitly supports partial prefunding, lines 716–723), then (2) a later borrower default finalized via `finalizeDefault`. Both are normal unprivileged-sequenceable protocol states; no privileged misbehavior needed. The trigger window is narrow but the failure is deterministic once reached.

### Recommendation
Track unfunded instant debt per-epoch or fold stale `pendingInstantWithdraws` into the default basis. Concretely: include `pendingInstantWithdraws` itself (not just `instantWithdrawClaimsByEpoch[epochNumber]`) in `defaultPendingClaimBasis()`, and make `_claimDefaultedInstantWithdrawRequest` clear all unfunded instant receipts (e.g., iterate or store each user's unfunded epoch set) at `defaultRecoveryPrice` rather than only `defaultRecoveryEpoch`. Alternatively, settle or haircut stale instant receipts at `stopEpoch` so `pendingInstantWithdraws` cannot outlive its epoch.

### Proof of Concept
```solidity
// Foundry fork PoC sketch against IdleCDOEpochVariant + IdleCreditVault
function testStaleInstantReceiptFrozenAfterDefault() external {
    // 1. user deposits AA, starts epoch 0
    _depositWithUser(user, 10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // 2. user requests instant withdraw; manager never calls getInstantWithdrawFunds
    vm.prank(user);
    cdoEpoch.requestInstantWithdraw(half, address(AAtranche)); // or requestWithdraw instant path
    // pendingInstantWithdraws > 0, instantWithdrawClaimsByEpoch[0] > 0

    // 3. epoch ends WITHOUT funding the instant request; epoch 1 starts
    _stopEpochAndCheckPrices(0, apr, funded); // instant still pending
    _startEpochAndCheckPrices(1);             // epochNumber now 1

    // 4. borrower defaults in epoch 1
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(owner);
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());

    // 5. finalizeDefault: basis = pendingWithdraws + instantWithdrawClaimsByEpoch[1] (=0)
    //    but pendingInstantWithdraws != 0 -> defaultInstantWithdrawsFinalized = true
    deal(underlying, manager, recovered);
    vm.prank(manager);
    cdoEpoch.finalizeDefault(recovered, manager);

    // 6. user's epoch-0 instant receipt is unclaimable forever
    vm.prank(user);
    vm.expectRevert(NotAllowed.selector); // _transferFundedClaim reserve guard
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Uncertainty: I could not fully trace `IdleCDOEpochVariant.stopEpoch`/`requestInstantWithdraw` gating in the remaining iterations (e.g., whether a non-defaulted stopEpoch forces instant funding, or whether instant requests are blocked once pending exists). If the CDO hard-reverts `stopEpoch` while `pendingInstantWithdraws > 0` in non-default mode, the stale-receipt window closes and this degrades to a no-issue. A confirmation pass on `IdleCDOEpochVariant.getInstantWithdrawFunds`/`stopEpoch` ordering is warranted before reporting.
