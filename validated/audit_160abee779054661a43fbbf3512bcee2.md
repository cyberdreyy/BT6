### Title
Unprivileged client can hijack another user's WebAPI trigger response via client-controlled MessageId collision in the Gateway `WebAPIHandler` savedCallbacks map - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Gateway's legacy WebAPI-trigger handler stores each incoming user request's response callback in a shared map keyed by a client-supplied `MessageId` (the JSON-RPC request `ID`), with no check for an existing/duplicate ID before overwriting the entry. This mirrors the root cause of the external report: an unprivileged caller can supply an identifier that collides with another in-flight caller's identifier, silently overwriting shared per-request state, so that a subsequent asynchronous callback (the node's response) is delivered to the wrong (attacker-controlled) caller instead of the original owner.

### Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` decodes an incoming, unauthenticated/unprivileged HTTP client request and passes the client-supplied JSON-RPC `ID` straight through as the message's `MessageId`: [1](#0-0) 

This `MessageId` is fully attacker-controlled — it is the JSON-RPC `id` field submitted by the external, unprivileged client of the gateway HTTP endpoint.

In `handler.HandleLegacyUserMessage` (the `WebAPIHandler` used for `MethodWebAPITrigger`), the callback for a request is inserted into a shared, unauthenticated `savedCallbacks` map keyed solely by this attacker-supplied `MessageId`, with **no check that the ID is unique / not already in use**: [2](#0-1) 

Later, when a DON node responds with that same `MessageId`, `handleWebAPITriggerMessage` looks up and deletes the map entry and forwards the response to whichever callback is currently registered under that key: [3](#0-2) 

Because the map key is client-controlled and there is no ownership/uniqueness enforcement, if two different (unprivileged) HTTP clients happen to submit overlapping requests using the same `MessageId` while one is still in flight, the second caller's `HandleLegacyUserMessage` call silently overwrites the first caller's saved callback entry (line 412). When the DON node later responds with that `MessageId`, the response is delivered to whichever callback is currently registered — potentially the second (attacker's) caller — not the original requester. This is architecturally identical to the reported bug class: a user-controlled identifier is used to clobber shared state belonging to a different in-flight operation, because there is no check that the state slot is "owned" or unused before overwrite.

Notably, this exact class of bug is explicitly guarded against elsewhere in the codebase: the Vault gateway handler enforces detection of duplicate request IDs and returns an explicit error ("request was already authorized previously") rather than silently overwriting shared per-request state, as shown by its test: [4](#0-3) 

The WebAPI capabilities `HandleLegacyUserMessage` path has no equivalent protection.

### Impact Explanation
If exploited, this leads to cross-user response confusion: an unprivileged attacker who is able to submit a request with the same `MessageId`/JSON-RPC `id` as a concurrent, legitimate in-flight WebAPI-trigger request can receive the DON's response intended for the victim (potential disclosure of the victim's workflow-trigger response data), while the legitimate caller either never receives a response (timeout/DoS for that specific request) or receives the attacker's response instead. This is a genuine cross-user response confusion / request impersonation vulnerability originating from an unprivileged, internet-facing gateway endpoint, matching the accepted impact categories (cross-user response confusion).

The practical exploitability depends on the ability of an attacker to predict or race a victim's chosen `MessageId` value; if IDs are low-entropy, sequential, or otherwise guessable/observable (e.g., reused constants, sequence counters, or publicly visible IDs from a prior interaction), the attack is straightforward. If callers always use high-entropy random UUIDs, the collision requires luck/race, but nothing in the code enforces or requires this — the protocol does not validate uniqueness, and other analogous handlers (Vault) do enforce it, indicating this was recognized as necessary but was not applied uniformly.

### Likelihood Explanation
The gateway HTTP endpoint accepting WebAPI-trigger requests is internet-facing and unauthenticated at this layer (any external client can submit a `MethodWebAPITrigger` legacy message with an arbitrary `MessageId`). No special privilege is required. The window for collision is real (`savedCallbacks` entries live until a node responds or are pruned after `CallbackMaxAgeSec`, default 120s), giving an attacker a meaningful window to guess/race an ID. Likelihood is moderate: it requires either a predictable/observed victim ID or a race, but is fully unprivileged-attacker driven and requires no cooperation from the victim.

### Recommendation
In `HandleLegacyUserMessage`, before inserting into `h.savedCallbacks`, check whether an entry already exists for `msg.Body.MessageId` and reject the request (mirroring the Vault handler's duplicate-request-id behavior) instead of silently overwriting it. Consider additionally namespacing the map key by sender/connection identity where available, so that even distinct legitimate senders cannot collide on the same `MessageId`.

### Proof of Concept
Conceptual PoC (not fully verified against a running gateway, based on code-path analysis):
1. Victim submits a legitimate JSON-RPC request to the gateway HTTP endpoint with `id = "X"` and `method = "web_api_trigger"`; this reaches `HandleLegacyUserMessage`, which stores `h.savedCallbacks["X"] = victimCallback` and forwards the message to DON nodes. [5](#0-4) 
2. Before the DON node responds, attacker submits their own request to the same gateway endpoint using the same `id = "X"`. This overwrites `h.savedCallbacks["X"] = attackerCallback` (no uniqueness check).
3. When a DON node responds with `MessageId = "X"`, `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds `attackerCallback`, deletes the entry, and sends the DON's response (originally destined for the victim's trigger request) to the attacker. [3](#0-2) 
4. The victim's original HTTP request either times out or never receives a response, while the attacker receives the response intended for the victim's request.

I was unable to fully verify end-to-end exploitability (e.g., whether upstream layers enforce ID uniqueness or randomization before reaching this handler) within the available tool calls; a background Devin session with full repository/test access would be needed to write and run an executable Go test reproducing the race/collision against `handler.HandleLegacyUserMessage` and `handleWebAPITriggerMessage` to conclusively confirm exploitability.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
