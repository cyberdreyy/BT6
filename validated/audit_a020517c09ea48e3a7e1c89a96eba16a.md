### Title
B20 token owners cannot invalidate an unused, signed `permit`, allowing a stale signature to re-establish an allowance the owner believed revoked - (File: crates/common/precompiles/src/common/ops/permit.rs)

### Summary
The B20 asset/stablecoin `permit` implementation follows EIP-2612 exactly: the owner's nonce advances only as a *side effect* of a successful `permit()` call. There is no owner-callable operation that burns/invalidates an outstanding, unconsumed permit signature before its `deadline`. This mirrors the reported Kairos issue, where a signer of an off-chain authorization has no way to void it once it is signed but before it is consumed on-chain.

### Finding Description
`PermitArgs` binds a signature to `(owner, spender, value, deadline, nonce)`, and the nonce is only incremented inside the `permit` logic path after a successful signature check [1](#0-0) . Each version's `permit()` (`b20_asset`/`b20_stablecoin`, v1/v2) reads the current `nonce`, verifies the signature over that nonce, then calls `increment_nonce` before applying the approval [2](#0-1) [3](#0-2) .

Critically, the ordinary `approve()` mutation does **not** touch the permit nonce — it only overwrites the allowance mapping [4](#0-3) . There is no other dispatched call (in `b20_asset/dispatch.rs`) that lets an owner burn/advance their own nonce independent of a successful `permit`. Consequently, once an owner signs a `permit`, that signature stays valid and replay-capable (up to `deadline`) regardless of any subsequent `approve()` calls the owner makes, because `approve()` does not consume the nonce the permit is bound to.

This is the same "signer cannot void an unused, already-signed authorization" bug class as the reported Kairos `Offer` issue: Kairos's offers are pure signed structs with no revocation path; Base's `permit` is pure EIP-2612 with no revocation path either. Notably, Base's own EIP-8130 account-authorization design explicitly recognizes and closes this exact bug class for account-change batches via `CHANGE_TYPE_INCREMENT_LOCAL_EPOCH`, which "invalidates every unlanded local signature at a prior epoch" [5](#0-4) , but no analogous invalidation primitive exists for B20 `permit` nonces.

### Impact Explanation
An owner who signs a `permit(spender, value, deadline)` and later decides they no longer want `spender` to hold that allowance (e.g., because the price/conditions changed, similar to the NFT-price-change scenario in the original report) has no way to invalidate the outstanding signature. If the owner instead calls `approve(spender, 0)` believing this "revokes" the grant, an attacker/spender who is still holding the valid permit signature can submit it after the owner's revoking `approve()` call, re-establishing the originally signed allowance and then draining funds via `transferFrom`. This is an unauthorized-operation / fund-theft vector stemming from the missing signer-side revocation mechanism.

### Likelihood Explanation
Likelihood is moderate: it requires an owner to sign a permit, later change their mind and issue a conflicting `approve()`, and a holder of the original signature to notice and land it after the owner's revoke — a realistic race condition in any permit-based integration (common in DEX/lending front-ends that request permits ahead of use), and it requires no privileged access, only ordinary transaction submission by the spender who was given the (stale) signature.

### Recommendation
Add an explicit nonce-invalidation entrypoint (e.g., an owner-callable "invalidate permit"/`incrementNonce` mutation dispatched through `b20_asset`/`b20_stablecoin` `dispatch.rs`) that lets the signer bump their own permit nonce without requiring a successful `permit()` call, so a previously signed-but-unused permit can be deliberately voided — mirroring the pattern Base already uses for EIP-8130 account-change batches (`CHANGE_TYPE_INCREMENT_LOCAL_EPOCH`).

### Proof of Concept
1. Alice (owner) signs `PermitArgs { owner: alice, spender: bob, value: 1000, deadline: T, nonce: 0 }` for a B20 token but does not submit it yet.
2. Alice changes her mind and calls `approve(bob, 0)` directly, believing Bob's allowance is now zero — this only calls the `approve` logic in `logic/v1.rs`/`v2.rs`, which does not touch the nonce [4](#0-3) .
3. Bob (still holding the original valid signature, nonce 0) submits `permit(alice, bob, 1000, T, v, r, s)`. Since Alice's nonce is still `0` (unchanged by `approve`), `permit()` in `logic/v1.rs` recovers Alice's signature successfully, sets `allowance(alice, bob) = 1000`, and increments the nonce [2](#0-1) .
4. Bob then calls `transferFrom(alice, bob, 1000)`, moving funds Alice believed she had revoked access to.

    pub fn struct_hash(&self, nonce: U256) -> B256 {
        keccak256(
            (Self::TYPEHASH, self.owner, self.spender, self.value, nonce, self.deadline)
                .abi_encode(),
        )
    }

    /// Builds the EIP-712 signing digest: `keccak256("\x19\x01" ‖ domainSeparator ‖ structHash)`.
    pub fn signing_hash(&self, domain_separator: B256, nonce: U256) -> B256 {
        let struct_hash = self.struct_hash(nonce);
        let mut buf = [0u8; 66];
        buf[..2].copy_from_slice(&Self::EIP712_SIGNING_PREFIX);
        buf[2..34].copy_from_slice(domain_separator.as_slice());
        buf[34..66].copy_from_slice(struct_hash.as_slice());
        keccak256(buf)
    }

    fn approve(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        spender: Address,
        amount: U256,
    ) -> Result<()> {
        if caller == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidApprover { approver: caller }));
        }
        if spender == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidSpender { spender }));
        }
        token.accounting_mut().set_allowance(caller, spender, amount)?;
        token
            .accounting_mut()
            .emit_event(IB20::Approval { owner: caller, spender, amount }.encode_log_data())
    }

```rust
    fn permit(
        &self,
        token: &mut B20AssetToken<S, A>,
        chain_id: u64,
        now: U256,
        args: PermitArgs,
    ) -> Result<()> {
        if now > args.deadline {
            return Err(BasePrecompileError::revert(IB20::ExpiredSignature {
                deadline: args.deadline,
            }));
        }
        let domain_sep = self.domain_separator(token, chain_id)?;
        let nonce = token.accounting().nonce(args.owner)?;
        let signing_hash = args.signing_hash(domain_sep, nonce);
        let recovered = args.recover_signer(signing_hash)?;
        PermitArgs::validate_recovered_address(recovered, args.owner)?;
        token.accounting_mut().increment_nonce(args.owner)?;
        self.approve(token, args.owner, args.spender, args.value)
    }
```
