One more check on epoch numbering for pending requests vs. default finalization.### Title
False `onStopEpoch` return permanently shortcuts the pool into an unrecoverable `defaulted` state — ([contracts/IdleCDOEpochVariant.sol:395-404](contracts/IdleCDOEpochVariant.sol))

### Summary
In programmable-borrower mode, `_stopEpoch` treats a `false` return from `IProgrammableBorrower.onStopEpoch` as a hard borrower default and calls `_handleBorrowerDefault`, which irreversibly sets `defaulted = true`, stops the epoch, and disables all withdrawal requests. There is no transition out of `defaulted` — `startEpoch` reverts on it (line 239), `restoreOperations` reverts on it (line 622), and `_beforeUnpause` blocks unpausing (line 636). The only exit is `finalizeDefault`, which crystallizes a recovery haircut on all active LPs and pending receipts.

This mirrors the RDS bug class: a "shortcut" transition around the error/shutdown path that leaves a terminal flag stuck forever. Here the asymmetry is explicit in the code comment itself — "Hook reverts bubble so transient ERC4626 liquidity failures can be retried" (line 397) — yet a `false` return, which signals exactly the same transient liquidity shortfall, is *not* retryable; it permanently locks the pool in the default state.

### Finding Description
At `contracts/IdleCDOEpochVariant.sol:395-404`:

```solidity
if (isProgrammableBorrower) {
  // Ask the programmable borrower to recall ERC4626 liquidity before IdleCDO pulls funds.
  // Hook reverts bubble so transient ERC4626 liquidity failures can be retried.
  if (!IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)) {
    _handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws);
    return;
  }
}
```

`onStopEpoch` returns `false` when the programmable borrower cannot recall enough liquidity from its underlying ERC4626 vault *at that moment*. The ERC4626 vault's available liquidity is controlled by third parties — any user of that vault can withdraw or borrow and drain transient liquidity. When `false` is returned:

1. `_handleBorrowerDefault` sets `defaulted = true`, `isEpochRunning = false`, `allowAAWithdrawRequest = false`, `allowBBWithdrawRequest = false`, and pauses the contract (lines 577-599). Nothing in this path is revertible by anyone, including the owner.
2. The honest borrower has not actually failed — it may hold full funds and repay seconds later. But the pool is already permanently defaulted; the borrower repaying cannot undo the flag.
3. The epoch bookkeeping is left half-updated: `expectedEpochInterest` and `pendingWithdrawFees` were already persisted (lines 388-389), `prepareStopEpochWithApr0` already mutated APR0 bucket state (line 362), but `collectWithdrawFunds` never ran so `pendingWithdraws` stays high while no funds arrived.
4. Every LP and pending receipt holder is frozen until owner/manager calls `finalizeDefault`, which applies `defaultRecoveryPrice` — computed from whatever recovery amount is supplied — as a haircut on all claims (`IdleCreditVault.finalizeDefaultRecovery`, lines 661-710). A false default therefore crystallizes a real loss on users even though the borrower is solvent.

The `try/catch` on `getFundsFromBorrower` (lines 408-505) has the same one-way property — any revert inside a ~90-line block (fee transfers, `mintStrategyTokens`, `deposit`, `_updateAccounting`) is treated as borrower default — but the `onStopEpoch` path is the cleaner attack because the attacker controls the prerequisite (ERC4626 vault liquidity) as a permitted unprivileged actor.

### Impact Explanation
- **Permanent freezing / forced loss**: A transient liquidity gap in the programmable borrower's ERC4626 vault — inducible by any vault depositor withdrawing a large amount in the same block as `stopEpoch` — permanently flips `defaulted`. All deposits, withdrawal requests, and claims freeze; the pool cannot resume operations even after the borrower becomes liquid again.
- **Unnecessary haircut**: `finalizeDefault` prices recovery as `reserveAmount / totalBasis`. Because the borrower never actually defaulted, the manager must source "recovered" funds externally to make users whole, or users absorb a haircut and `pendingWithdraws`/`instantWithdrawClaimsByEpoch` claims are settled at a discount.
- Loss magnitude: up to the entire pool TVL being frozen pending recovery, plus any shortfall between the supplied recovery amount and `totalBasis`.

### Likelihood Explanation
Requires programmable-borrower mode (`isProgrammableBorrower`) where `onStopEpoch` can return `false` when ERC4626 liquidity is insufficient. An attacker who is a user of that ERC4626 vault (explicitly in scope) can drain or borrow its liquidity right before the epoch end, then let the honest manager's routine `stopEpoch` call trigger the permanent default. No privileged-role misbehavior is needed — the manager's normal stop call is the trigger. Rate-limiting is nil: one `false` return suffices, and there is no retry path.

### Recommendation
Distinguish transient failure from insolvency: treat a `false` return from `onStopEpoch` the same as a revert — bubble it up (revert) so the manager can retry, rather than calling `_handleBorrowerDefault`. Alternatively, add a pre-finalization rescue path (e.g., owner-controlled `cancelDefault` callable only before `defaultRecoveryFinalized`) so a borrower that repays after a premature default can restore the pool without forcing a recovery haircut.

```solidity
function testTransientVaultIlliquidityCausesPermanentDefault() external {
  uint256 amount = 10_000 * ONE_SCALE;
  idleCDO.depositAA(amount);
  _startEpochAndCheckPrices(0); // programmable borrower mode

  // Attacker (unprivileged ERC4626 vault user) drains vault liquidity
  // so borrower.onStopEpoch returns false.
  vm.prank(attacker);
  erc4626Vault.withdraw(erc4626Vault.maxWithdraw(attacker), attacker, attacker);

  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0); // borrower honest; onStopEpoch returns false

  assertTrue(cdoEpoch.defaulted(), 'pool permanently defaulted on transient illiquidity');

  // Borrower repays in full the very next block — too late, no way back.
  deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
  vm.prank(owner);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.restoreOperations(); // defaulted => cannot exit error state

  vm.prank(manager);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.startEpoch(); // defaulted => epoch machine dead

  // All LP funds frozen until owner supplies external recovery via finalizeDefault.
}
```
