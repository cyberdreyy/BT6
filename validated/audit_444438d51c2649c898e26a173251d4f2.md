### Title
TOKEN_TRANSFER Nonce Namespace Shared Across Source Chains Enables Permanent Fund Lock — (`bridge/evm/contracts/utils/MessageVerifier.sol`, `bridge/evm/contracts/SuiBridge.sol`)

---

### Summary

`MessageVerifier.sol` deliberately skips chain-ID verification for `TOKEN_TRANSFER` messages, and `SuiBridge.sol` tracks processed transfers in a mapping keyed only by `message.nonce` — not by `(message.chainID, message.nonce)`. This collapses the nonce namespace across all supported source chains. In any deployment where more than one Sui-side chain ID is accepted (including a hard-fork scenario), a transfer from source chain A with nonce N permanently blocks the corresponding transfer from source chain B with the same nonce N, locking the second user's funds with no recovery path.

---

### Finding Description

**`MessageVerifier.sol` — chain-ID check is gated out for TOKEN_TRANSFER**

```solidity
// bridge/evm/contracts/utils/MessageVerifier.sol  lines 43-50
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    // verify chain ID
    require(
        message.chainID == committee.config().chainID(),
        "MessageVerifier: Invalid chain ID"
    );
    require(message.nonce == nonces[message.messageType], "MessageVerifier: Invalid nonce");
    nonces[message.messageType]++;
}
```

Every governance message type (EMERGENCY_OP, UPGRADE, BLOCKLIST, …) has its `message.chainID` verified against the contract's own chain ID and uses a strictly sequential nonce. TOKEN_TRANSFER is explicitly excluded from both checks. [1](#0-0) 

**`SuiBridge.sol` — processed-nonce map keyed by nonce alone**

```solidity
// bridge/evm/contracts/SuiBridge.sol  line 24
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;

// line 92
isTransferProcessed[message.nonce] = true;
```

The key is a bare `uint64 nonce`. There is no `chainID` component. [2](#0-1) [3](#0-2) 

**`BridgeConfig.sol` — multiple source chains can be registered**

```solidity
mapping(uint8 chainId => bool isSupported) public supportedChains;
```

`BridgeConfig.initialize` accepts an array of supported chain IDs, and `addTokensWithSignatures` can extend the set later. Nothing prevents SUI_MAINNET (0) and SUI_CUSTOM (2) from both being marked supported on the same ETH_MAINNET bridge. [4](#0-3) [5](#0-4) 

**`onlySupportedChain` only checks membership, not identity**

```solidity
// bridge/evm/contracts/SuiBridge.sol  lines 283-289
modifier onlySupportedChain(uint8 targetChainID) {
    require(
        committee.config().isChainSupported(targetChainID),
        "SuiBridge: Target chain not supported"
    );
    _;
}
```

Any chain ID in the supported set passes. There is no assertion that `message.chainID` equals a single expected source chain. [6](#0-5) 

**`BridgeUtils.Message.chainID` is the SOURCE chain for TOKEN_TRANSFER**

The struct comment confirms: *"The chain ID of the source chain (for token transfer messages this is the source chain)"*. The destination chain lives inside the payload as `targetChain`. [7](#0-6) 

---

### Impact Explanation

When two source chains are both registered (or after a hard fork where the forked chain is later added as SUI_CUSTOM), their nonce sequences are independent on-chain but share a single `isTransferProcessed` slot on Ethereum. Whichever chain's transfer with nonce N is relayed first marks `isTransferProcessed[N] = true`. The second chain's transfer with the same nonce is then permanently rejected with `"SuiBridge: Message already processed"`. The user's tokens are locked in the Sui-side bridge with no on-chain mechanism to recover them, because the Ethereum side will never accept the claim.

This matches the **permanent fund lock** impact class in the allowed gate.

---

### Likelihood Explanation

The scenario requires either:

1. **Multi-source-chain deployment** — governance adds a second Sui chain ID (e.g., SUI_CUSTOM = 2) as a supported source on ETH_MAINNET. Both chains independently assign nonces starting from 0, so collisions are guaranteed as volume grows.
2. **Hard fork** — Sui forks; the forked chain inherits the same nonce counter; governance eventually registers the fork as a supported source chain. This is the exact external-factor scenario rated Medium in the reference report.

Neither path requires a malicious actor: the collision is a natural arithmetic consequence of the shared key space.

---

### Recommendation

Key `isTransferProcessed` by the composite `(chainID, nonce)` pair:

```solidity
// Replace:
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;

// With:
mapping(uint8 chainID => mapping(uint64 nonce => bool isProcessed)) public isTransferProcessed;
```

Update every read/write site accordingly:

```solidity
require(!isTransferProcessed[message.chainID][message.nonce], "SuiBridge: Message already processed");
// ...
isTransferProcessed[message.chainID][message.nonce] = true;
```

Apply the same fix to `SuiBridgeV2.sol`, which inherits the same mapping. [8](#0-7) 

---

### Proof of Concept

**Setup**: ETH_MAINNET bridge with `supportedChains[SUI_MAINNET=0] = true` and `supportedChains[SUI_CUSTOM=2] = true`.

**Step 1** — User A bridges 10 ETH from SUI_MAINNET → ETH_MAINNET. The Sui bridge node collects committee signatures over the message `{messageType:TOKEN_TRANSFER, chainID:0, nonce:5, payload:{targetChain:ETH_MAINNET, recipient:A, …}}` and calls `transferBridgedTokensWithSignatures`.

- `verifyMessageAndSignatures`: type ✓, signatures ✓, chain-ID check **skipped** (TOKEN_TRANSFER branch).
- `onlySupportedChain(0)`: SUI_MAINNET is supported ✓.
- `isTransferProcessed[5]` is false ✓ → tokens released, `isTransferProcessed[5] = true`.

**Step 2** — User B bridges 5 ETH from SUI_CUSTOM → ETH_MAINNET. The message is `{messageType:TOKEN_TRANSFER, chainID:2, nonce:5, payload:{targetChain:ETH_MAINNET, recipient:B, …}}`. Relay calls `transferBridgedTokensWithSignatures`.

- `verifyMessageAndSignatures`: type ✓, signatures ✓, chain-ID check **skipped**.
- `onlySupportedChain(2)`: SUI_CUSTOM is supported ✓.
- `isTransferProcessed[5]` is **true** → **revert "SuiBridge: Message already processed"**.

User B's 5 ETH is permanently locked. No on-chain path exists to claim it because the nonce slot is consumed by a different source chain's transfer. [9](#0-8) [10](#0-9)

        bytes[] memory signatures,
        BridgeUtils.Message memory message

        external
        nonReentrant
        verifyMessageAndSignatures(message, signatures, BridgeUtils.TOKEN_TRANSFER)
        onlySupportedChain(message.chainID)

        // verify that message has not been processed
        require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");

        );

        // convert amount to ERC20 token decimals

            config.tokenSuiDecimalOf(tokenTransferPayload.tokenID),
            tokenTransferPayload.amount
        );

        _transferTokensFromVault(
            message.chainID,
            tokenTransferPayload.tokenID,
            tokenTransferPayload.recipientAddress,
            erc20AdjustedAmount
        );

        // mark message as processed
        isTransferProcessed[message.nonce] = true;

            message.chainID,
            message.nonce,
            config.chainID(),
            tokenTransferPayload.tokenID,
            erc20AdjustedAmount,
            tokenTransferPayload.senderAddress,

        );
