### Title
Bridge OutgoingToken secrets are disclosed to any view-role user via GET /v2/bridge_types pagination - ([File: core/web/presenters/bridges.go])

### Finding Description
`BridgeTypesController.Index` fetches all bridges via `btc.App.BridgeORM().BridgeTypes(ctx, offset, size)` and builds a `BridgeResource` for every bridge with `presenters.NewBridgeResource(bridge)`, then returns them in a paginated JSON:API response with no field-level filtering: [1](#0-0) 

`BridgeResource` unconditionally serializes `OutgoingToken` with the JSON tag `json:"outgoingToken"` (no `omitempty`, no redaction), while `IncomingToken` is explicitly commented as "only provided when creating a Bridge" and tagged `omitempty`: [2](#0-1) 

`NewBridgeResource` copies `b.OutgoingToken` straight from the DB-backed `bridges.BridgeType` into the resource for every list/show call: [3](#0-2) 

The `OutgoingToken` is the secret bearer credential the Chainlink node uses to authenticate itself when an external adapter/bridge calls back into `/v2/runs/:id/bridge`, so its confidentiality is the entire security boundary between bridges. There is no per-caller ownership scoping in `Index`/`Show`/`Update`/`Destroy` — any authenticated caller who can hit these endpoints gets every bridge's outgoing token, not just bridges they created (bridges have no owner/user association at all in this ORM model). This is a genuine violation of secret confinement: a low-privileged/read-only authenticated user who is only supposed to view bridge configuration also receives the live outgoing auth token for all bridges configured on the node, enabling them to forge authenticated callback requests to `/v2/runs/:id/bridge` for any bridge, impersonating the bridge's expected caller.

I was not able to fully confirm from the available index whether `GET /v2/bridge_types` is registered in `core/web/router.go` under a view-only role guard (e.g., `RequiresViewRole`) as opposed to edit/admin-only — the grep matched but I could not retrieve the specific route registration line before the tool budget ran out. If the route is restricted to edit/admin roles only, this downgrades from a cross-privilege-tier leak to same-tier exposure to already-privileged operators; if it is reachable by a "view" role (consistent with GET bridge listing being a natural read-only operation, and consistent with the question's stated precondition), the finding stands as a role-boundary secret disclosure. Given Chainlink's convention of GET endpoints generally being reachable by view-role sessions and the explicit contrast in the code between `IncomingToken` (intentionally hidden by default) and `OutgoingToken` (always exposed), the presenter-level flaw is confirmed regardless: there is no code path anywhere that redacts `OutgoingToken` from list/show responses.

### Impact Explanation
Exposure of `OutgoingToken` for every bridge to any authenticated caller of `GET /v2/bridge_types` (and `GET /v2/bridge_types/:BridgeName`) allows that caller to construct and send forged, authenticated bridge callback requests to `/v2/runs/:id/bridge`, impersonating the legitimate external adapter for bridges they do not own/manage. This matches the "key/secret disclosure enabling request impersonation" bounty impact class — a lower-privileged (view-role) session obtains credential material that should be confined to bridge creation time / bridge operators, enabling cross-bridge run manipulation.

### Likelihood Explanation
Precondition is simply an authenticated session with any role capable of calling the bridge-types listing/show endpoints (view-role per the question's stated scenario). No special timing, race condition, or additional exploit primitive is required — a single `GET /v2/bridge_types?size=1000&page=1` request (or repeated pagination) trivially and reliably enumerates all `outgoingToken` values in the JSON response body. This is fully deterministic and repeatable.

### Recommendation
Do not include `OutgoingToken` in `BridgeResource` responses for list/show/update/destroy operations. Apply the same treatment already used for `IncomingToken` (tag with `omitempty` and populate only on the `Create` path in `core/web/bridge_types_controller.go`), or better, remove `OutgoingToken` from the JSON-serialized `BridgeResource` entirely and expose it only through a dedicated, audited, one-time-reveal endpoint restricted to admin/edit roles with explicit re-authentication, mirroring how API-key/CSA-key secrets are typically only shown once at creation.

### Proof of Concept
Go handler-level integration test plan (in `core/web/bridge_types_controller_test.go` style):
1. Seed two bridges via `orm.CreateBridgeType` with distinct `OutgoingToken` values (e.g., "secretA", "secretB").
2. Create an authenticated test client using a view-role user session (per existing test helpers for role-scoped clients in the `web` test suite).
3. Issue `GET /v2/bridge_types?size=100&page=1` with the view-role client.
4. Parse the JSON:API response `resources[].attributes.outgoingToken`.
5. Assert failure of the fix (current behavior): both "secretA" and "secretB" are present in the response body, proving cross-bridge secret disclosure to a view-role caller.
6. After applying the recommended fix (omit/redact `OutgoingToken` in list responses), assert `outgoingToken` is absent or empty in the JSON payload for both bridges while other non-secret fields (`name`, `url`, `confirmations`) remain present.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}
