### Title
Tenure-change duplicate check in v1 uses `get_last_globally_accepted_block` instead of signed-block check, allowing equivocation on `LocallyAccepted`-only blocks - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
In `SortitionsView::validate_tenure_change_payload` (v1 chainstate rules), the final duplicate-tenure-change-block guard queries `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0) . This only detects a prior tenure-change block for tenure `T` if it already reached global consensus, not merely if this signer already signed one. The v2 equivalent fixes this by using `get_last_signed_block` instead [2](#0-1) .

### Finding Description
The broken equality: v1 treats `get_last_globally_accepted_block(T) == None` as "no signed tenure-change block yet exists for tenure T," but that is false when this signer has already produced a `LocallyAccepted` (signed but not globally-accepted) block A for T — `get_last_globally_accepted_block` will return `None` for A even though the signer already signed it, whereas `get_last_signed_block`/`has_signed_block_in_tenure` would correctly return `Some(A)`. The v2 comment explicitly documents the intended semantics — "Only blocks we have signed (locally or globally accepted) count here" — and implements it with `get_last_signed_block` [3](#0-2) , while v1's comment claims the same intent ("if we've already signed a block in this tenure") but the code checks global acceptance [1](#0-0) .

Exploit flow: an attacker who wins a single miner slot for tenure T proposes tenure-change block A. `check_proposal` → `validate_tenure_change_payload` runs, `get_last_globally_accepted_block(T)` returns `None` (A doesn't exist in signerdb yet), so the check passes and the signer signs A, later persisted as `LocallyAccepted`. If the attacker prevents A from reaching the global-acceptance threshold (e.g., by not gossiping/aggregating enough `BlockAccepted` responses from other signers, which is entirely outside this victim signer's control and requires no privilege beyond controlling their own miner slot and message gossip), A remains `LocallyAccepted` forever in this signer's DB. The attacker then proposes a second, different tenure-change block B, also claiming tenure T with `prev_tenure_consensus_hash` equal to the same parent. `check_tenure_change_confirms_parent` only validates the parent tenure linkage, not whether T itself already has a signed block, so it does not catch this. The final duplicate check calls `get_last_globally_accepted_block(T)`, which still returns `None` (A never reached global acceptance), so the check incorrectly passes, and this signer signs B too — a clear equivocation for tenure T (two different tenure-change blocks both signed by the same signer).

Existing guards fail here specifically because: `check_parent_tenure_choice` validates the *parent* tenure choice, not duplication within the same tenure T; and the duplicate-detection query itself uses the wrong signerdb accessor (global-acceptance instead of signed-status).

### Impact Explanation
This breaks the equivocation-guard / uniqueness safety property: a single signer can be induced to sign two conflicting tenure-change blocks for the same tenure, which is exactly the kind of double-signing scenario the equivocation guard exists to prevent. If enough signers hit this same race (each independently produces its own `LocallyAccepted`-only A, then signs a conflicting B), it can contribute to two competing block sets for the same tenure both amassing partial signature sets, undermining canonicity guarantees at the chain level. This matches the **Critical** category: "a signer signing an invalid, non-canonical, or conflicting block (chain safety)." It is repeatable per-tenure per-signer as long as v1 rules are active and the attacker can prevent global acceptance of A before proposing B.

### Likelihood Explanation
Preconditions: the signer must be running v1 chainstate rules (this is a real path since `v1.rs` is present alongside `v2.rs`, implying v1 is still active for signers that haven't upgraded or during a transition period). The attacker needs only to win a single Bitcoin miner slot for tenure T (their own BTC, no privilege) and craft two different tenure-change block proposals for the same tenure, plus control gossip/response timing so that A doesn't cross the global-acceptance threshold before B is proposed — well within an unprivileged single-slot attacker's capability. No majority-signer collusion, no auth_token, and no local host access are required. This is feasible and repeatable across tenures.

### Recommendation
Change the duplicate-detection call in `SortitionData::validate_tenure_change_payload` (v1.rs) from `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` to `signer_db.get_last_signed_block(&block.header.consensus_hash)` (or equivalently gate on `has_signed_block_in_tenure`), mirroring the v2 fix, so that any locally-accepted-only signed block for tenure T is also treated as a duplicate that blocks signing a second, conflicting tenure-change block.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests/v1.rs`:
1. Construct a `SignerDb` and insert tenure-change block A for tenure T, mark it `LocallyAccepted` (signed_self = true, but not globally accepted) — e.g., via the same helper functions used in `stacks-signer/src/chainstate/tests/v2.rs` for constructing signed blocks.
2. Build a `SortitionsView`/`SortitionData` context for tenure T (matching parent tenure, valid pubkey, etc.).
3. Construct a second tenure-change block B for the same tenure T with a different `signer_signature_hash` but same `prev_tenure_consensus_hash`.
4. Call `SortitionsView::validate_tenure_change_payload` (or `check_proposal`) for B.
5. Assert current (buggy) behavior returns `Ok(())` (wrongly accepting B), and after applying the fix (`get_last_signed_block` instead of `get_last_globally_accepted_block`), assert it returns `Err(RejectReason::DuplicateBlockFound)`.
