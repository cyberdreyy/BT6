## Title
Builder pending withdrawal with insufficient balance mints Gwei on the execution layer — capped CL deduction vs. uncapped EL credit (`specs/gloas/beacon-chain.md`, `get_builder_withdrawals` / `apply_withdrawals`)

## Summary
`get_builder_withdrawals` emits a `Withdrawal` whose `amount` is the raw, uncapped `builder_pending_withdrawals[i].amount`, which is committed into `state.payload_expected_withdrawals` and must be honored verbatim by the execution layer (the note in the spec explicitly states this: "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer"). However, `apply_withdrawals` only decreases the builder's *beacon-state* balance by `min(withdrawal.amount, builder_balance)`. When a builder's balance is smaller than the queued withdrawal amount, the CL debits less than what the EL is contractually obligated to credit to `fee_recipient` — the difference is Gwei created out of nothing, paid to a non-owner (the fee recipient), and permanently lost from total supply accounting.

## Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md:1802-1834) builds the `Withdrawal` list directly from the requested amount, without capping to the builder's actual balance: [1](#0-0) 

`apply_withdrawals` (specs/gloas/beacon-chain.md:1920-1932), which mutates CL state, caps the *balance decrement* to what the builder actually has: [2](#0-1) 

The committed `Withdrawal.amount` (uncapped) is what the execution payload must honor — this is the exact same value flow used for all standard Capella/Electra withdrawals, where the EL unconditionally credits the specified `address` with `amount` Gwei. Since Capella-era `apply_withdrawals` (decrease_balance) and `get_validators_sweep_withdrawals` always compute `amount` from validator balance so it can never exceed what's decremented, this equality (amount emitted == amount deducted) has always held for validator withdrawals. Gloas breaks it specifically for the new builder pending-withdrawal path, where `amount` is taken from a caller-populated request (`BuilderPendingWithdrawal.amount`, ultimately sourced from `settle_builder_payment`/bid processing) rather than being derived from the builder's live balance at emission time.

This is directly analogous to the BlueBerry `withdrawLend` bug class: a "debit" side (shares burned / builder balance capped) and a "credit" side (amount paid to the user / amount committed to the EL) diverge, and one side is silently truncated while the other is not — except here the mismatch runs in the direction of *minting* rather than trapping funds.

The scenario is also explicitly exercised and asserted as expected/passing behavior by the test suite, confirming the divergence is intentional/unaddressed rather than an oversight caught by existing tests: [3](#0-2) 

## Impact Explanation
If a builder's balance is insufficient to cover a pending withdrawal amount (e.g., because multiple `builder_pending_withdrawals` entries were queued for the same builder and drained its balance via processing order, or a large payment was queued shortly before the builder's balance was reduced by other means), the emitted `Withdrawal.amount` — which the execution payload must match exactly — exceeds the actual Gwei ever removed from the builder's `state.builders[i].balance`. Since `fee_recipient` is credited the full requested amount on the EL side, this is Gwei created and paid to a non-owner, i.e. an unconditional protocol-level ETH-supply invariant break. Per the impact taxonomy, this is Critical (Gwei created and paid to a non-owner).

## Likelihood Explanation
The trigger condition — a builder's `builder_pending_withdrawals` amount exceeding its current `balance` — is a normal, permitted state per the spec's own `assert_process_withdrawals` test helper comment ("Builder withdrawals cap at available balance (spec uses min())"), and multiple dedicated tests construct exactly this scenario (`test_builder_withdrawal_insufficient_balance`, `test_builder_withdrawal_insufficient_balance_realistic_bounds`). No malicious peer, coalition, or client bug is required — any sequence of otherwise valid builder payments/settlements that leaves `builder_pending_withdrawals` amount(s) exceeding current balance triggers it whenever `process_withdrawals` runs.

## Recommendation
Cap the amount recorded in the emitted `Withdrawal` (in `get_builder_withdrawals`) to `min(withdrawal.amount, state.builders[builder_index].balance)` at emission time — mirroring what `apply_withdrawals` actually deducts — so the committed EL payload amount and the CL balance decrement are always equal, consistent with how validator sweep/partial withdrawal amounts are already bounded by live balance before being placed into the `Withdrawal` list.

## Proof of Concept
Using the state from `test_builder_withdrawal_insufficient_balance`: [4](#0-3) 

1. Builder 0 balance = 1 ETH; `builder_pending_withdrawals[0] = {builder_index: 0, amount: 5 ETH, fee_recipient: X}`.
2. `get_builder_withdrawals` emits `Withdrawal(validator_index=builder_0, address=X, amount=5 ETH)` into `state.payload_expected_withdrawals`.
3. Any spec-following execution client MUST include this withdrawal in the execution payload and credit address `X` with 5 ETH (standard EIP-4895-style unconditional credit).
4. `apply_withdrawals` executes `state.builders[0].balance -= min(5 ETH, 1 ETH)` → builder balance becomes 0 (only 1 ETH removed from CL accounting).
5. Net effect: address `X` receives 5 ETH on the EL, but only 1 ETH was ever removed from any tracked balance — 4 ETH created from nothing, credited to a non-owner (`X`), and both spec-following CL/EL sides accept this as a valid, honored transition.
