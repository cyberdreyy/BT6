### Title
GET /v2/config and /v2/config/v2 lack any role check, allowing run/view-role users to read the full effective server TOML - ([File: core/web/config_controller.go])

### Summary
`ConfigController.Show` is mounted in `core/web/router.go` with only session/token authentication (`auth.Authenticate`) and no role wrapper, unlike nearly every other mutating/sensitive route in the same `v2Routes` function which is explicitly wrapped with `auth.RequiresEditRole`, `auth.RequiresAdminRole`, or `auth.RequiresRunRole`. Any authenticated user regardless of role — including `UserRoleView` and `UserRoleRun` — can call `GET /v2/config` and receive the full effective TOML, including `WebServer()`, `Database()`, `RateLimit`, `TLS`, and other topology sections.

### Finding Description
The route is registered as: [1](#0-0) 
with no `auth.RequiresEditRole`/`auth.RequiresRunRole`/`auth.RequiresAdminRole` wrapper, contrasting with sibling routes in the same block (`/external_initiators`, `/bridge_types`, `/transfers`, `/replay_from_block`, `/find_lca`, `/lp_skip_to_block`) which all use explicit role gates: [2](#0-1) [3](#0-2) 

The handler itself performs no role check and simply returns the effective (or user) TOML: [4](#0-3) 

`ConfigTOML()` returns `inputTOML`/`effectiveTOML`, which are derived from the non-secret `Config` struct (WebServer, Database, TLS, RateLimit, etc.); credentials such as the DB URL and keystore password live in a separate `secretsTOML` that this endpoint never returns: [5](#0-4) [6](#0-5) 

So the concrete data exposed to a run/view-role session includes non-secret but sensitive topology data: `WebServer.TLS` (cert paths, listen IP, HTTPS port), `WebServer.RateLimit` (authenticated/unauthenticated rate thresholds), `WebServer.LDAP`/`OIDC` group-claim mapping names, and `Database` tuning parameters, as shown in the effective-config testdata: [7](#0-6) 

There is no role gate anywhere in the handler or route registration that restricts this to edit/admin roles; every authenticated session (view, run, edit, admin) receives an identical response.

### Impact Explanation
This is an authorization-gap / information-disclosure finding, not a secrets leak: actual credentials (DB password, keystore password) are excluded from the response by design, since they live only in `secretsTOML`, which `ConfigTOML()` never returns. The exposed data is limited to internal topology/config metadata (TLS listen settings, rate-limit thresholds, LDAP/OIDC group-claim names, DB connection pool tuning). A run-role principal (e.g., a job-runner integration credential) can use this to fingerprint the node's internal network topology and security controls (e.g., rate-limit thresholds to plan abuse, TLS ports/paths, LDAP/OIDC claim group names to aid social-engineering or targeted enumeration), which exceeds what a run-role principal needs for job execution. This corresponds to a low/informational-severity "unauthorized information disclosure" rather than a credential-disclosure or fund-movement class bug.

### Likelihood Explanation
Trivial and fully repeatable: any valid session or API token with `UserRoleRun` (or even `UserRoleView`) can call `GET /v2/config` with no additional preconditions, since the route only requires `auth.Authenticate` and applies no role check at all.

### Recommendation
Wrap the `/config` and `/config/v2` routes with an explicit role check consistent with the rest of the role matrix (e.g., `auth.RequiresEditRole` or a dedicated `RequiresAtLeastViewWithConfigScope`), or split the response so that only non-sensitive fields are visible to `view`/`run` roles while `WebServer`, `Database`, `TLS`, and `RateLimit` sections require `edit`/`admin`.

### Proof of Concept
Go handler-level integration test plan:
1. Start a test `chainlink.Application` with a full config containing `WebServer.TLS`, `WebServer.RateLimit`, `WebServer.LDAP`/`OIDC` sections populated (mirroring `core/services/chainlink/testdata/config-full.toml`).
2. Create four users with roles `admin`, `edit`, `run`, `view` and obtain authenticated sessions for each (following the pattern in `core/cmd/renderer_test.go` `TestRendererTable_RenderConfigurationV2`).
3. For each session, call `GET /v2/config/v2` and assert HTTP 200 for all four roles, and that the returned `Config` string is byte-identical across roles and contains the `[WebServer.TLS]`, `[WebServer.RateLimit]` sections.
4. Assert that no `403`/`401` is ever returned for `run`/`view` roles, proving the absence of any role gate — contrasted with a call to `/v2/replay_from_block/:number` or `/v2/external_initiators` (POST) with a `view` session, which correctly returns `401 Unauthorized` per `auth.RequiresRunRole`/`auth.RequiresEditRole`.

```go
func (cc *ConfigController) Show(c *gin.Context) {
	cfg := cc.App.GetConfig()
	var userOnly bool
	if s, has := c.GetQuery("userOnly"); has {
		var err error
		userOnly, err = strconv.ParseBool(s)
		if err != nil {
			jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("invalid bool for userOnly: %w", err))
			return
		}
	}
	var toml string
	user, effective := cfg.ConfigTOML()
	if userOnly {
		toml = user
	} else {
		toml = effective
	}
	jsonAPIResponse(c, ConfigV2Resource{toml}, "config")
}
```
