### Title
Late APR0 `requestWithdraw` captures a full epoch of pro-rata interest, stealing yield from active LPs - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug-class analog: a low-privilege input (`requestWithdraw`) is fed unsanitized into a privileged accounting path (`prepareStopEpochWithApr0`), letting an attacker "inject" their principal into the epoch interest split. When `unscaledApr == 0`, `requestWithdraw` routes to `_requestWithdrawApr0`, which adds the user's principal to `apr0TotalPrincipal` with only an epoch number recorded — no timestamp or duration weighting [1](#0-0) . At `stopEpoch`, `prepareStopEpochWithApr0` pays every APR0 requester a pro-rata share of the *entire* epoch's realized interest, computed as `_interestNetOfFees * _principal / _totalPrincipalForSplit`, and stores a flat `apr0RateByEpoch` per epoch [2](#0-1) . `apr0RateByEpoch` is a single per-epoch rate applied to all principal in the bucket identically [3](#0-2) .

### Finding Description
In an APR0-mode epoch (`unscaledApr == 0`), a KYC-passing lender can:

1. Deposit into AA tranches during the buffer phase (or via `depositDuringEpoch` during the running epoch if not disabled).
2. Wait until the epoch is nearly over, then call `IdleCDOEpochVariant.requestWithdraw`, which calls `IdleCreditVault.requestWithdraw` and — because `unscaledApr == 0` — routes to `_requestWithdrawApr0`, adding the full requested principal to `apr0TotalPrincipal` [4](#0-3) .
3. The manager calls `stopEpoch`, which calls `prepareStopEpochWithApr0`. The attacker receives the same per-epoch rate as lenders who queued their principal for the entire epoch: `apr0RateByEpoch[epochNumber] = _apr0NetInterest * 1e18 / _principal` [3](#0-2) .
4. The deducted `_apr0NetInterest` is subtracted from `_expInterest`, so it is directly carved out of the interest that would otherwise accrue to active AA/BB tranche holders [5](#0-4) .
5. After `epochNumber` increments, the attacker calls `claimWithdrawRequest` → `_settleApr0`, which pays `_principal * apr0RateByEpoch[reqEpoch] / 1e18` as `settledInterest` plus the full principal back [6](#0-5) .

The broken invariant is fair yield distribution: epoch interest should be proportional to time-weighted capital at risk, but APR0 receipts earn a flat share regardless of entry time within the epoch. There is no guard in `requestWithdraw`/`_requestWithdrawApr0` against requesting immediately before `stopEpoch`, and the loss-epoch gating (`lastWithdrawRequest`/`lossRecoveryPriceByEpoch` checks) only blocks *repeated* requests, not first-time late entries [7](#0-6) . This can be repeated each epoch, and scaled by depositing a large amount via `depositDuringEpoch` near epoch end (the deposited funds are even sent to the borrower only for the residual epoch time, yet earn the full epoch rate).

### Impact Explanation
Direct theft of yield. The attacker extracts a pro-rata share of realized epoch interest proportional to `attackerPrincipal / (CDO TVL + apr0TotalPrincipal)` with near-zero capital-at-risk duration, diluting all active tranche holders' `virtualPrice` gains. With a deposit equal to pool TVL, the attacker captures roughly half of the epoch's net interest despite participating for a negligible fraction of the epoch. Repeating across epochs compounds the theft. Quantified loss per epoch: `epochInterest * attackerPrincipal / (TVL + attackerPrincipal)`.

### Likelihood Explanation
High where the mode is reachable: it only requires `unscaledApr == 0` (a supported configuration used for minted-interest/programmable deployments), an attacker able to pass the Keyring/KYC check (`isWalletAllowed`), and `isDepositDuringEpochDisabled == false` or timing the deposit in the buffer phase and the request late in the epoch. No privileged cooperation is needed; `stopEpoch` is called by the honest manager on schedule. The main uncertainty I could not fully verify within the iteration budget: whether `requestWithdraw` is itself blocked during the running epoch in `IdleCDOEpochVariant` (buffer vs running gating) — if requests are only permitted during the buffer, the attack shifts to depositing in the buffer and the impact profile changes but the missing time-weighting flaw stands.

### Recommendation
Time-weight the APR0 interest: record a per-request timestamp (or deposit-weighted duration) in `Apr0UserData` and compute `apr0RateByEpoch` from a duration-weighted `apr0TotalPrincipal`, or accrue APR0 interest per-user at claim time using elapsed time within the epoch. Alternatively, exclude principal requested after a cutoff (e.g., within the last portion of the epoch) from `apr0RateByEpoch` accrual, or disable `depositDuringEpoch`-funded principal from entering the APR0 interest bucket in its first epoch.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testApr0LateRequestStealsEpochInterest() external {
    // Setup: APR0-mode credit vault, attacker and victim are KYC'd lenders
    uint256 victimAmt = 10_000 * ONE_SCALE;
    uint256 attackerAmt = 10_000 * ONE_SCALE;

    _depositWithUser(victim, victimAmt, true);          // honest LP
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);    // APR0 mode
    _startEpochAndCheckPrices(0);

    // Attacker deposits mid-epoch (depositDuringEpoch) and immediately requests withdraw
    _depositWithUser(attacker, attackerAmt, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));     // routed to _requestWithdrawApr0

    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                            // prepareStopEpochWithApr0 splits interest

    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    // Attacker received ~50% of the epoch's net interest despite requesting at epoch end,
    // while victim's virtualPrice gain is correspondingly diluted.
    uint256 stolen = apr0RateByEpoch_share * attackerAmt / 1e18;
    assertGt(stolen, 0, "late APR0 requester earned full-epoch interest");
}
```

Caveat: exact helper names and whether `requestWithdraw` is callable during a running epoch in this variant need confirmation against `IdleCDOEpochVariant.requestWithdraw`'s epoch-phase gating; if gated to the buffer, substitute an early deposit with the request still placed late relative to capital contribution via `depositDuringEpoch`.

  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;

  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
    apr0TotalPrincipal += _amount;
  }
