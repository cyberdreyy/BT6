### Title
Missing slippage protection on `requestWithdraw` allows realized losses to devalue a user's withdrawal mid-flight - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.requestWithdraw()` converts the caller's tranche tokens to underlyings at the current tranche price and immediately burns them, with no `minAmountOut` parameter. If a loss is realized between the user's transaction submission and its execution — via `stopEpochWithDuration(_lossAmount)` or a forced accounting update — the same tranche tokens redeem for materially fewer underlyings than quoted. This is the direct analog of the reported Pool/SuperPool withdraw slippage issue.

### Finding Description
In `requestWithdraw` (`contracts/IdleCDOEpochVariant.sol:739-791`) the flow is:

```solidity
_updateAccounting();
_underlyings = _trancheToUnderlyings(_amount, _tranche);   // priced at current virtualPrice
...
creditVault.requestWithdraw(_underlyings, msg.sender, principal);
_withdrawOps(_amount, principal, _tranche);                // tranche tokens burned now
```

The receipt amount `_underlyings` is fixed at request time and the tranche tokens are burned atomically. There is no user-supplied minimum. Meanwhile losses hit the price through two paths:

- `stopEpochWithDuration(..., _lossAmount)` calls `previewLossAdjustedWithdrawFunds`, burns `_lossAmount` strategy tokens, then `_forceUpdateAccounting()` applies the loss BB-first through `_virtualPriceAux`, lowering `virtualPrice`/`priceAA`/`priceBB` (`IdleCDOEpochVariant.sol:393,496-500`; `IdleCDOCreditVault.sol:222-249`).
- Any ordinary `_updateAccounting()` triggered inside `requestWithdraw` itself picks up a contract-value drop.

Sequence: a BB (or AA, once the loss exceeds `lossToleranceBps * lastNAV` or BB TVL) holder calls `requestWithdraw(trancheAmount)` expecting `trancheAmount * price / 1e18`. The honest manager's `stopEpochWithDuration` carrying a `_lossAmount` executes first; the user's tx then reprices at the post-loss price and burns the identical share amount for fewer underlyings. Unlike a default, partial losses do not revert — `testStopEpochWithDurationLossKeepsExpectedInterestFlow` and `testStopEpochWithDurationLargeLossUsesBBFirstWaterfall` (`test/foundry/IdleCreditVault.t.sol:5948-5998`) show the pool stays live and `allowAAWithdrawRequest`/`allowBBWithdrawRequest` remain enabled after a loss stop, so the user's request executes rather than reverting.

The donation-skim (`_skimDonatedAssets`) and `Default` revert guards do not help: they handle unaccounted donations and full junior wipeouts, not partial-loss repricing, which proceeds normally by design.

### Impact Explanation
A withdrawing user burns a fixed quantity of tranche tokens but receives `trancheAmount * postLossPrice` underlyings instead of `trancheAmount * preLossPrice`. For BB holders the loss is concentrated entirely on them (BB-first waterfall), so a loss equal to e.g. 20% of TVL against a BB TVL of 50% produces a ~40% reduction in received underlyings with no way for the user to bound it. Losses are capped only by insolvency; any realized `_lossAmount` translates 1:1 into withdrawer slippage.

### Likelihood Explanation
Losses are an expected feature of this credit vault (`_lossAmount` parameter, BB-first waterfall, loss socialization within `lossToleranceBps`). Stop-epoch transactions are public and predictable in the mempool (manager-called at `epochEndDate`), so user withdraw requests submitted near an epoch boundary routinely race a potential loss-bearing `stopEpochWithDuration`. No privileged misbehavior is required — only normal sequencing around an honest manager call.

### Recommendation
Add a `_minAmountOut` parameter to `requestWithdraw` (and a deadline if desired) and revert if the computed `_underlyings` is below it, before burning tranche tokens. Symmetrically, consider a `minOut` on `claimWithdrawRequest`/`claimInstantWithdrawRequest` for loss-adjusted receipts priced via `lossRecoveryPriceByEpoch`/`postDefaultRequests`.

### Proof of Concept
Foundry fork PoC sketch (existing harness in `test/foundry/IdleCreditVault.t.sol` provides `_startEpochAndCheckPrices`, `deal`, borrower):

```solidity
function testRequestWithdrawSlippageOnLoss() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mintedBB = idleCDO.depositBB(amount);   // victim holds BB
    idleCDO.depositAA(amount);                     // senior cushion

    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    _startEpochAndCheckPrices(0);

    uint256 pricePre = cdoEpoch.virtualPrice(address(BBtranche));
    uint256 expectedOut = mintedBB * pricePre / ONE_TRANCHE_TOKEN;

    // Manager's loss-bearing stop lands while user's requestWithdraw is pending
    uint256 loss = 4_000 * ONE_SCALE;             // < BB TVL, all hits BB
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), loss);

    // Victim's tx now executes at the post-loss price; burns full mintedBB
    uint256 received = cdoEpoch.requestWithdraw(mintedBB, address(BBtranche));

    assertLt(received, expectedOut);               // received ~expectedOut - loss share
    assertEq(IERC20(address(BBtranche)).balanceOf(address(this)), 0);
}
```

The burned share count is identical regardless of ordering; only the underlyings out change, confirming the missing `minAmountOut` is the sole deficiency.
