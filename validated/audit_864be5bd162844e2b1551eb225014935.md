### Title
Fee-on-transfer underlying inflates `IdleCreditVault` strategy-token supply — minted shares exceed actual backing - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.deposit` mints strategy tokens 1:1 with the requested `_amount` after `safeTransferFrom`, without measuring the actual balance received. If the vault's `token` is a fee-on-transfer (or burn-on-transfer) asset, the strategy mints full shares while holding less underlying. The parent CDO already accounts for the transfer fee when minting tranche shares (it uses a balance delta), but then calls `strategy.deposit(_amount)` with the *pre-fee* amount, so the mismatch is booked into the strategy's share supply. The same pattern exists in `collectWithdrawFunds`, `collectInstantWithdrawFunds`, and `finalizeDefaultRecovery`, which debit pending-claim accounting by the requested amount rather than the received amount.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`, `deposit` does:

```solidity
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
_mint(msg.sender, _amount);          // mints full _amount of strategy tokens
totEpochDeposits += _amount;         // epoch-deposit counter also uses full _amount
``` [1](#0-0) 

The CDO-side `_deposit` in `IdleCDOCreditVault` mints the user's tranche shares on the actual balance delta, so the user is correctly credited less — but it then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the original amount, and the strategy mints `_amount` strategy tokens while receiving only `_amount - fee` underlying: [2](#0-1) 

The identical assumption exists at funding time:

- `collectWithdrawFunds`: `pendingWithdraws` is reduced and a `lossRecoveryPriceByEpoch` entry may be written assuming `_amount` arrived; the strategy actually holds less. [3](#0-2) 
- `collectInstantWithdrawFunds`: `pendingInstantWithdraws -= _amount` while fewer tokens were received. [4](#0-3) 
- `finalizeDefaultRecovery`: `defaultRecoveryReserve` is set to `_recoveredAmount + prefundedReserve + defaultRecoveryReserve` but the pull of `_recoveredAmount` yields less underlying, leaving claims unbacked. [5](#0-4) 

### Impact Explanation
Two broken invariants:

1. **Solvency of the strategy token.** Every deposit inflates the strategy-token supply by the transfer fee percentage of `_amount`. `getContractValue`/tranche pricing treats each strategy token as backed by 1 underlying (`price()` returns `oneToken`), so withdrawers redeem against phantom backing. As deposits accumulate, late claimants (`claimWithdrawRequest` / `claimInstantWithdrawRequest` / `_transferFundedClaim`) find the vault underfunded — withdrawals revert on insufficient balance, permanently freezing the tail of the queue. The deficit equals the cumulative fee taken on all deposits plus all `collectWithdrawFunds`/`collectInstantWithdrawFunds` pulls.
2. **Recovery-reserve shortfall.** After a default, `finalizeDefaultRecovery` books a reserve larger than what it pulled, so `defaultRecoveryPrice` overstates recovery and the last defaulted/post-default claimants are unpaid.

The loss is unbounded in aggregate (proportional to total throughput × fee rate) and hits unprivileged, honest lenders — no privileged action is required beyond a normal deposit by any KYC-passing lender into a vault whose underlying charges transfer fees (e.g., a fee-taking stablecoin variant used as pool currency).

### Likelihood Explanation
Conditional: the vulnerability triggers whenever a credit vault is deployed on a fee-on-transfer underlying. All in-scope flows (`deposit`, `collectWithdrawFunds`, `collectInstantWithdrawFunds`, `finalizeDefaultRecovery`) share the same "requested == received" assumption, and no guard (`_onlyIdleCDO`, reserve checks in `_transferFundedClaim`, `lossRecoveryPrice` zero check) compares actual balance deltas. The skim/negative-balance checks in `_transferFundedClaim` only protect the recovery reserve partition, not the overall backing, so they do not stop the insolvency — they merely make the deficit surface earlier as reverts. Any lender depositing normally is the unwitting trigger; no attacker sophistication is needed.

### Recommendation
Measure actual received amounts at every pull boundary:

- In `deposit`: `uint256 before = underlyingToken.balanceOf(address(this)); underlyingToken.safeTransferFrom(...); _amount = underlyingToken.balanceOf(address(this)) - before;` then mint and increment `totEpochDeposits` by the delta.
- In `collectWithdrawFunds`/`collectInstantWithdrawFunds`: compute the balance delta and apply the loss-shortfall logic to the *received* amount.
- In `finalizeDefaultRecovery`: add the received delta to the reserve instead of `_recoveredAmount`.
- Alternatively, document/enforce at initialization that `token` must not charge transfer fees.

### Proof of Concept
Foundry test sketch (run against the repo's test setup with a fee-on-transfer mock underlying):

```solidity
// Mock FOT ERC20: burns 1% on every transfer/transferFrom
contract FOTToken is ERC20 {
    function _transfer(address f, address t, uint256 a) internal override {
        uint256 feeAmt = a / 100;
        super._transfer(f, t, a - feeAmt);
        super._burn(f, feeAmt);
    }
}

function testFOTDepositInflation() public {
    // Deploy IdleCDOCreditVault + IdleCreditVault with token = FOTToken
    // Alice (KYC lender) deposits 1000e6 via depositAA
    fot.approve(cdo, 1000e6);
    cdo.depositAA(1000e6);   // CDO credits ~990e6 of tranche shares (preBal delta)

    // Strategy minted 1000e6 strategy tokens to CDO but holds only ~980e6 underlying
    uint256 stratTokens = strategy.balanceOf(cdo);
    uint256 stratBal    = fot.balanceOf(strategy);
    assertGt(stratTokens, stratBal);          // supply > backing
    // Repeating deposits widens the gap; eventual claimWithdrawRequest reverts
    // on insufficient balance -> last claimants permanently frozen.
}
```

The same shortfall can be asserted for `collectWithdrawFunds` by having the borrower fund fewer-than-requested receipts after the transfer fee, leaving `pendingWithdraws` accounting cleared while `lossRecoveryPriceByEpoch` claimants cannot all be paid.
