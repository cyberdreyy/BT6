## Analysis

I found a valid analog. The bug class in the OP report — an entity (a dispute game) is implicitly trusted for a security-critical decision, but the system fails to re-validate that trust when the entity's underlying authorization has been invalidated — maps directly onto `multisig/src/lib.rs`'s handling of `DeleteKey` versus the `confirmations` set stored per-request.

### Title
Confirmations from deleted multisig keys remain valid, allowing requests to execute below the live-member threshold - (File: multisig/src/lib.rs)

### Summary
`confirm()` counts a request's `confirmations: HashSet<PublicKey>` against `num_confirmations` to decide whether to execute. When a `DeleteKey` action is executed, the contract only purges requests and confirmations tied to requests *originated* by the deleted key (`r.signer_pk == pk`), but never scans other pending requests' `confirmations` sets to strip out the deleted key. A confirmation cast by a key that is later removed keeps counting toward the threshold for any other still-pending request.

### Finding Description
`execute_request`'s `DeleteKey` branch:
```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [1](#0-0) 

This cleanup keys only on `r.signer_pk` — the key that *added* a request — not on membership inside any request's `confirmations` HashSet. `confirm()` never re-checks that a stored public key in `confirmations` still corresponds to a live multisig key:
```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert!(!confirmations.contains(&env::signer_account_pk()), "Already confirmed this request with this key");
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(env::signer_account_pk());
        self.confirmations.insert(&request_id, &confirmations);
        PromiseOrValue::Value(true)
    }
}
``` [2](#0-1) 

Equality that should hold: `count(confirmations for request X) == count(currently-live authorized keys who confirmed X)`. This breaks whenever a key confirms request X (added by a *different* key), and is later removed via a `DeleteKey` request that does not target X. The stale confirmation from the removed key still counts in `confirmations.len()`, so a request can reach `num_confirmations` using a mix of live and already-revoked keys — i.e., a request executes with fewer live-key confirmations than the configured threshold requires.

### Impact Explanation
This directly breaks the confirmations-counted-vs-live-members custody binding called out as in-scope. Any multisig action (including `Transfer` of NEAR, `FunctionCall`, `AddKey`, `DeployContract`) can be pushed through with a confirmation count that nominally satisfies `num_confirmations`, but where one or more of the "confirming" keys had already been revoked before the last confirmation was cast. This is a "multisig request executed below threshold" scenario, explicitly listed as Critical impact.

### Likelihood Explanation
This requires no privileged or out-of-scope actor: it only needs the ordinary sequence of events the contract is designed to support — a request added by key A, confirmed by key B (below threshold), followed by an ordinary `DeleteKey` request (for key B, executed by other legitimate members) that does not touch A's pending request, and then a final confirmation by key C. This is a normal operational sequence of a K-of-N multisig (key rotation while requests are in flight), not a hypothetical or externally-gated event, so likelihood is high in any multisig doing routine key rotation with concurrent pending requests.

### Recommendation
When executing `DeleteKey`, iterate over all `self.confirmations` entries and remove the deleted public key from every confirmation set (or equivalently, re-validate at `confirm()`-execution time that every key in a request's `confirmations` set is still a member/valid key before counting it toward `num_confirmations`).

### Proof of Concept
1. Initialize `MultiSigContract::new(2)` (2-of-N) with keys `A`, `B`, `C` as function-call access keys.
2. Key `A` calls `add_request` to create `request2` = `{ receiver_id: self, actions: [Transfer { amount }] }`. `confirmations[request2] = {}`.
3. Key `B` calls `confirm(request2)` → `confirmations[request2] = {B}` (1 < 2, not yet executed).
4. Key `A` (or `C`) creates and confirms (2-of-2, using `add_request_and_confirm` + one more confirm) a separate `request3 = DeleteKey{ public_key: B }`, which executes and removes key `B` from the account's access keys. Per the code shown above, only requests where `r.signer_pk == B` are purged — `request2` (signed/added by `A`, merely confirmed by `B`) is untouched, so `confirmations[request2]` still contains `B`.
5. Key `C` calls `confirm(request2)`. `confirmations.len() + 1 == 2 >= num_confirmations(2)` → `execute_request` runs the `Transfer`, even though `B`'s key has been deleted and only one genuinely live key (`C`, plus the requester `A`) truly authorized this action through confirmation — `B`'s revoked confirmation was counted as if still valid.

Result: the transfer executes using a stale confirmation from a deleted key, i.e., below the intended live-member threshold.
