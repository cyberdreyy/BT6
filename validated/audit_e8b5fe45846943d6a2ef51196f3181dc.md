### Title
External ERC4626 withdraw failure permanently bricks `stopEpoch` despite reported solvency — `StopEpochVaultLiquidityUnavailable` DoS - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The external report describes unsigned→signed truncation feeding a negative value into logic that throws an unhandled exception, producing a busy-loop DoS. The direct analog in this codebase is `ProgrammableBorrower.onStopEpoch`: the vault sleeve declares itself covered via `convertToAssets` (a *reported* value), but the actual state-changing `vault.withdraw` reverts, and the error is re-thrown as `StopEpochVaultLiquidityUnavailable`, which propagates out of `IdleCDOEpochVariant.stopEpoch` and makes epoch settlement uncallable. An unprivileged user of the configured ERC4626 vault can keep the vault illiquid (e.g., by borrowing/redeeming all of the vault's own liquidity, or via a share-price manipulation that desynchronizes `convertToAssets` from withdrawable cash), causing every `stopEpoch` call to revert while tranche holder funds sit locked.

### Finding Description
In `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:239-253), the contract decides whether the vault can cover a shortfall using the *view* `convertToAssets`:

```solidity
uint256 shortfall = _amountRequired - onHand;
if (shortfall > _currentVaultAssets()) return true;
try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
  ...
} catch {
  revert StopEpochVaultLiquidityUnavailable();
}
```

`_currentVaultAssets()` returns `vault.convertToAssets(shares)` (line 546-549), which reflects the vault's *total* assets, not its *withdrawable* balance. For any ERC4626 whose assets are partially deployed/borrowed (the standard case — the vault is used precisely to earn yield), `convertToAssets` reports full coverage while `withdraw` reverts on insufficient liquidity. The revert propagates through `IdleCDOEpochVariant.stopEpoch`/`_beforeStopEpoch`, so:

- The epoch can never be stopped while the vault is illiquid.
- Unlike the `shortfall > _currentVaultAssets()` branch, which returns `true` and falls through to IdleCDO's `transferFrom` failure → proper default path, this branch hard-reverts, so the default/finalizeDefault machinery is never reached.
- Withdraw requests, claims, and new epochs are all gated behind a successful `stopEpoch`, so all tranche principal and interest are frozen for as long as the vault remains illiquid.

This is the same structural flaw as the advisory: a computed value (`convertToAssets` / the truncated integer) claims the operation is safe, the real operation throws, and the throw is surfaced as an unrecoverable loop-blocking error rather than being routed into the existing failure path (return `false`/default handling).

### Impact Explanation
Temporary-to-permanent freezing of all lender funds in the pool. Cost to the attacker is whatever it costs to keep the vault illiquid (e.g., holding a borrow position open in the vault, or repeatedly frontrunning `stopEpoch` with liquidity-draining transactions). If the vault can be kept illiquid indefinitely (attacker is a borrower of the vault with open-ended terms, or the vault itself becomes insolvent), the freeze is permanent and losses equal the entire pool NAV, since the honest default path (`transferFrom` failing → `defaulted` → `finalizeDefault`/`DefaultDistributor`) is never reached. Quantified bound: full `getContractValue()` of the CDO for the duration the vault stays illiquid.

### Likelihood Explanation
Requires a `ProgrammableBorrower` deployment whose vault has genuinely fractional liquidity, and an attacker able to exhaust or withhold that liquidity at epoch end — this is a normal capability of "a user of the programmable borrower's ERC4626 vault" per the threat model (any vault depositor can redeem; any vault borrower can draw). The trigger needs no privileged role: owner/manager calling `stopEpoch` on schedule is honest behavior that simply reverts. The fragility is structural — the solvency check and the withdrawal use two different notions of "available" — so it reproduces deterministically whenever `convertToAssets ≥ shortfall` but `maxWithdraw < shortfall`.

### Recommendation
- In `onStopEpoch`, check liquidity against `vault.maxWithdraw(address(this))` (or `convertToAssets` of the redeemable portion) instead of `convertToAssets(balanceOf)`, so the coverage test reflects what `withdraw` can actually do.
- On catch, do not revert — return `true` (or `false`) and let IdleCDO's `transferFrom` fail so the standard default path engages, matching the behavior already used for the `shortfall > _currentVaultAssets()` case. Optionally attempt `redeem` of the exact share amount instead of `withdraw`, since share-bounded redemptions fail less often than asset-bounded withdrawals.
- Alternatively, wrap the whole withdraw-and-transfer sequence so a vault liquidity failure maps to the same "insufficient funds" default outcome rather than a retryable revert.

### Proof of Concept
Foundry fork sketch (in-scope mode: programmable borrower, running epoch):

```solidity
// Setup: IdleCDOEpochVariant + IdleCreditVault + ProgrammableBorrower
// wired to a real ERC4626 vault V that lends/locks most of its assets
// (e.g., an ERC4626 whose cash buffer < convertToAssets).

// 1. Lenders deposit into AA/BB, manager calls startEpoch().
//    ProgrammableBorrower.onStartEpoch deposits idle cash into V.

// 2. Attacker (unprivileged user of V) drains V's withdrawable liquidity:
//    - if V supports borrowing: attacker borrows nearly all of V's cash;
//    - else attacker redeems a large position so cash < needed shortfall,
//      while convertToAssets(borrower.shares) still >= shortfall.

// 3. Warp past epochEndDate. Owner calls cdoEpoch.stopEpoch(apr, _):
//    - IdleCDO calls programmableBorrower.totalInterestDueNow() (fine),
//    - then onStopEpoch(amountRequired, false):
//        onHand < amountRequired
//        shortfall <= _currentVaultAssets()      // passes — inflated view
//        vault.withdraw(shortfall,...) REVERTS    // real liquidity missing
//        => revert StopEpochVaultLiquidityUnavailable
//    - stopEpoch reverts. Repeated calls keep reverting while V is illiquid.

// 4. Assert: cdoEpoch.isEpochRunning() still true, no default triggered,
//    claimWithdrawRequest/claimInstantWithdrawRequest unavailable,
//    all tranche funds frozen. Attacker sustains freeze at borrow-interest cost.
```

The assertion that makes it a vulnerability rather than intended behavior: the `shortfall > _currentVaultAssets()` early-return shows the authors intended "economically uncovered → let transferFrom fail → default," but the withdraw-revert path bypasses that and produces a hard revert with no path to `finalizeDefault`, i.e., the exception is "not handled suitably," exactly mirroring the Oxenstored busy-loop.
