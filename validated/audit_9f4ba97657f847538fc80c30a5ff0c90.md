### Title
View-role session can self-enroll a WebAuthn credential via /v2/enroll_webauthn with no edit/admin role gate - ([File: core/web/webauthn_controller.go])

### Summary
`WebAuthnController.BeginRegistration` and `FinishRegistration` only check that a session is authenticated (`auth.GetAuthenticatedUser`) and never verify the user's role. The routes for `/v2/enroll_webauthn` in `core/web/router.go` are wired with plain session authentication and no `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper, unlike other credential-sensitive endpoints (e.g. `/sessions` deletion, admin-only routes) that do use these wrappers.

### Finding Description
`BeginRegistration` [1](#0-0)  and `FinishRegistration` [2](#0-1)  both call `auth.GetAuthenticatedUser(c)` to fetch the current user but perform no role check whatsoever before proceeding to generate WebAuthn registration options or persist a new credential via `sessions.AddCredentialToUser`. `GetAuthenticatedUser` simply reads whatever user was set into the gin context by the `Authenticate` middleware, regardless of role [3](#0-2) .

The role-gating wrappers `RequiresRunRole`, `RequiresEditRole`, and `RequiresAdminRole` exist in the codebase specifically to reject `UserRoleView` (and in the edit case, also `UserRoleRun`) sessions from sensitive handlers [4](#0-3) . The `enroll_webauthn` route registrations found in `core/web/router.go` are only wrapped with basic session `Authenticate`, with no such role wrapper applied to `BeginRegistration`/`FinishRegistration` — this is corroborated by the fact that a combined search for `enroll_webauthn` together with `RequiresEditRole`/`RequiresAdminRole` in `router.go` did not show these role-gate wrappers attached to the enroll_webauthn handlers, whereas other admin-sensitive routes elsewhere in the router explicitly attach them.

As a result, a compromised or stolen `view`-role session cookie is sufficient to complete the full WebAuthn registration ceremony and have an attacker-controlled public-key credential persisted against that user's account via `sessions.AddCredentialToUser` [5](#0-4) . Since MFA/WebAuthn credential enrollment is a security-boundary-changing action, it should require step-up authentication or at minimum a higher role than `view`.

### Impact Explanation
This falls under Chainlink's "authentication/authorization bypass" bounty class: a low-privilege (view-role) compromised session can entrench itself by adding a persistent second-factor credential it controls. If the account is later investigated or its password/role is downgraded, the attacker's enrolled WebAuthn key remains valid for any future authentication flow gated by that user's MFA, providing a durable backdoor tied to the victim account rather than a one-time session compromise.

### Likelihood Explanation
The precondition is simply possession of a valid `view`-role session cookie (e.g. via XSS, stolen cookie, or a leaked session). No edit/admin privilege or reauthentication step is required by the handler code. The attack is fully client-driven (POST/GET to `/v2/enroll_webauthn`) and repeatable — no rate limiting or extra confirmation beyond the WebAuthn ceremony itself, which the attacker fully controls (attacker supplies their own authenticator/public key).

### Recommendation
Wrap `BeginRegistration` and `FinishRegistration` with `auth.RequiresEditRole` (or introduce a step-up/reauthentication requirement, e.g. re-prompting for password) before allowing WebAuthn credential enrollment, so that only edit/admin-role sessions — or freshly re-authenticated sessions — can add new MFA credentials to an account.

### Proof of Concept
1. Add a handler-level integration test in `core/web/webauthn_controller_test.go` (or equivalent) that creates a user session with `Role: sessions.UserRoleView`.
2. Call `GET /v2/enroll_webauthn` with that session and assert the response is `200 OK` with registration options returned (demonstrating no role gate blocks it), where the expected secure behavior would be `401/403`.
3. Complete `POST /v2/enroll_webauthn` with a test WebAuthn credential response and assert `200 OK` plus that `sessions.AddCredentialToUser` persisted the credential for the view-role user, confirming the credential-enrollment succeeded without any edit/admin check or reauthentication step.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
