### Title
No vulnerability — post-action storage-stake check in `apply_action_receipt` covers `AddKey` for both self and third-party accounts - ([File: runtime/runtime/src/lib.rs])

### Summary
`add_regular_key` (and `add_gas_key`) in `access_keys.rs` only performs a `checked_add` for arithmetic-overflow safety on `storage_usage`; it does not itself verify the account can afford the resulting storage stake. However, this is by design: the actual solvency check is deferred to `apply_action_receipt` in `lib.rs`, which runs unconditionally after *every* action in a receipt (not just deposit-bearing ones), for the receiver account regardless of who authored the receipt.

### Finding Description
`add_regular_key` (`runtime/runtime/src/access_keys.rs:230-255`) writes the new access key and does `account.storage_usage().checked_add(access_key_storage_usage(...))`, failing only on `u64` overflow (`StorageInconsistentState`), not on insufficient balance. This is consistent with the design described in `protocol-model/spec/accounts-keys.md:41` and `:112`: storage-usage overflow is the only thing checked inline; balance sufficiency is checked elsewhere.

The actual balance-sufficiency enforcement point is in `apply_action_receipt` (`runtime/runtime/src/lib.rs:954-977`):
```
if result.result.is_ok() {
    if let Some(ref account) = account {
        match check_storage_stake(account, account.amount(), &apply_state.config) {
            Ok(()) => { set_account(...); }
            Err(StorageStakingError::LackBalanceForStorageStaking(amount)) => {
                result.set_error(ActionError { index: None, kind: ActionErrorKind::LackBalanceForState { account_id: account_id.clone(), amount } });
            }
            ...
        }
    }
}
```
This runs once **after the entire loop over all actions in the receipt** (`lib.rs:892-951`), for the receipt's receiver account (`account_id = receipt.receiver_id()`, `lib.rs:791`) — the account whose `AddKey` action(s) modified `storage_usage`. It is unconditional: it does not check whether any action carried a deposit; it fires for any receipt whose actions leave the receiver's account under-collateralized, `AddKey` included. `check_storage_stake` (`verifier.rs:48`) requires `amount + locked >= storage_amount_per_byte * storage_usage`, with a zero-balance-account exemption below 770 bytes (`ZERO_BALANCE_ACCOUNT_STORAGE_LIMIT`, `verifier.rs:24`).

If the check fails, `result.set_error(...)` marks the whole receipt as failed with `LackBalanceForState`, and the caller rolls back all trie changes for the receipt (`lib.rs:961-970` per the spec, "failure calls `state_update.rollback()`, discarding all state changes from the receipt"). So an attacker cannot leave any account — their own or another — in a state where `amount() + locked() < storage_amount_per_byte * storage_usage` as a persisted result of an `AddKey` receipt; the whole receipt reverts atomically.

Because the check keys off `receipt.receiver_id()`, not the signer/predecessor, it applies equally whether the attacker sends the `AddKey` actions to their own account or crafts/relays (e.g., via a meta-transaction `DelegateAction`) a receipt targeting a victim account — the victim's account balance is verified before commit either way; the attacker cannot induce this state on an account they don't control.

### Impact Explanation
No impact: this is not a vulnerability. The value-conservation invariant holds — insufficient-balance-for-storage receipts are reverted, not committed, regardless of whether the underlying action was `AddKey`, `AddKey` for a gas key, `DeployContract`, or any other storage-usage-increasing action.

### Likelihood Explanation
N/A — the described "gap" does not exist; the storage-stake check is generic and unconditional per receipt, not deposit-action-specific.

### Recommendation
None required. If desired for defense-in-depth/clarity, `access_keys.rs`'s doc comments could explicitly note that `add_regular_key`/`add_gas_key` do not themselves check solvency and rely on the receipt-level `check_storage_stake` in `lib.rs:957`, to avoid future maintainers assuming it's checked locally.
