### Title
`blockSubscribe` pubsub notification path re-invokes the same `get_complete_block`/`Shredder::deshred` panic surface on every new slot, turning a single subscription into a persistent crash trigger - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
`RpcSubscriptions::notify_watchers` services every active `blockSubscribe` subscription by calling `Blockstore::get_complete_block` for each newly notified slot, which internally calls `Blockstore::get_slot_data_in_block` → `Shredder::deshred`, the exact code path that contains the `maybe_panic` abort when a shred is missing for a slot above `lowest_cleanup_slot`. Because this is driven by the validator's own per-slot notification loop rather than by direct client requests, a single `blockSubscribe` session causes the vulnerable path to be re-executed once per produced slot for the lifetime of the subscription.

### Finding Description
`RpcSubscriptions::notify_watchers` iterates active subscriptions and, for `SubscriptionParams::Block`, calls `blockstore.get_complete_block(s, false)` for every slot between the subscription's last-notified slot and the newly notified commitment slot: [1](#0-0) . `get_complete_block` ultimately reaches `Blockstore::get_slot_data_in_block`, which defines the `maybe_panic` closure that calls `panic!("Missing shred...")` whenever a shred lookup misses and `slot > self.lowest_cleanup_slot()`: [2](#0-1) , and this closure is invoked inline when a shred key is absent right before feeding the shred stream into `Shredder::deshred`: [3](#0-2) . `Shredder::deshred` itself also returns (not panics) `Error::InvalidDeshredSet`/`TooFewDataShards` on malformed shred sets: [4](#0-3) , but the `maybe_panic` call happens in the enclosing blockstore code, not inside `deshred`.

This is the same underlying code path used by the `getBlock` JSON-RPC method. The distinguishing factor raised by this question is that `blockSubscribe` causes this path to be invoked automatically and repeatedly - once per new slot for as long as the subscription is open - rather than requiring the client to issue a new call each time: [5](#0-4) . `blockSubscribe` is a supported (if "unstable"/opt-in) public API that must be explicitly enabled via `--rpc-pubsub-enable-block-subscription` and requires `check_is_at_least_confirmed`, but no additional guard exists against the missing-shred/racy-purge condition: [6](#0-5) [7](#0-6) .

The exploit ultimately reduces to whether the underlying "missing-shred/racy-purge" condition (referenced as "question 2" in the prompt, and not independently re-derivable from this investigation alone) is genuinely attacker-reachable through purely unprivileged, single-call-rate actions, or whether it depends on an internal validator race (ledger cleanup/purge racing a concurrent read) that is not driven by attacker input. I could not locate, within the available index, code demonstrating that an unprivileged client can force `lowest_cleanup_slot` to advance past a "complete" slot concurrently with a `get_complete_block` read without validator/operator-side state (e.g. cleanup service timing) being the actual trigger. The cleanup service (`ledger/src/blockstore/cleanup_service.rs`) purges old shreds on a background schedule based on disk usage, not on attacker-controlled parameters: [8](#0-7) .

### Impact Explanation
If the missing-shred panic condition from "question 2" is real and reachable without validator-side control, then routing it through `blockSubscribe` does increase the practical severity: instead of needing repeated `getBlock` calls (each independently rate-limited to at most one per `CLUSTER_SLOT_TIME_TARGET / 2`), a single subscription session causes the same panic-prone code to run on every new slot indefinitely, matching the "persistent crash trigger" framing. This would qualify as a validator-process crash from a single low-rate call/subscription under the stated bounty categories.

### Likelihood Explanation
I cannot confirm the likelihood independently in this investigation because it is entirely contingent on the "missing-shred/racy-purge condition from question 2" being a genuine, attacker-reachable race and not an internal validator timing artifact requiring cleanup-service/operator conditions (which is explicitly out of scope per the rules: "direct store mutation," "operator config," races requiring validator-internal timing not driven by a single unprivileged call). Based on what is visible here, the purge/cleanup trigger is governed by the background `BlockstoreCleanupService` on disk-usage thresholds, not by client-supplied parameters, which weighs against attacker-controllability of the race window.

### Recommendation
Independent of the race's origin, the `maybe_panic` panic in `Blockstore::get_slot_data_in_block` should be removed/replaced with a returned `BlockstoreError` (as is already done for the non-panic branch that returns `BlockstoreError::MissingShred`), so that both `getBlock` and `blockSubscribe`'s `notify_watchers` path handle a missing-shred/purge race by emitting an error notification (as the existing `Err(err)` arm in `notify_watchers` already does) instead of ever calling `panic!`.

### Proof of Concept
This cannot be confirmed as a standalone PoC without the "question 2" precondition (a reproducible way to make `get_slot_data_in_block`'s `maybe_panic` fire under purely unprivileged, single-rate-limited conditions). Conceptually, the integration test would extend the existing `test_pubsub_block_subscribe` test as follows:
1. Reuse the setup from `rpc/src/rpc_subscriptions.rs::test_pubsub_block_subscribe` (`PubSubConfig { enable_block_subscription: true, .. }`, `PubsubClient::block_subscribe`).
2. Insert a slot's shreds into the blockstore, then, concurrently with a `notify_subscribers` call for that slot, delete/purge one data shred for that slot from the `data_shred_cf` column (simulating the racy-purge condition established in question 2) so that `slot_meta` is `Some` and `slot > lowest_cleanup_slot()`.
3. Trigger repeated `notify_subscribers` calls for successive slots to simulate normal slot production churn.
4. Assert that the `solRpcNotify` worker thread does not abort/panic across multiple slot notifications, and that the subscriber instead receives `RpcBlockUpdate { block: None, err: Some(_) }` notifications for the affected slots.

Because I could not verify the precise mechanism by which an unprivileged client can trigger the shred-purge race referenced from "question 2" using only the tools/context available in this session, I cannot assert with confidence that this is a fully valid, independently exploitable finding as scoped. It is only a valid amplification of that prior finding *if* that finding itself is confirmed valid.

    pub fn deshred<I, T: AsRef<[u8]>>(shreds: I) -> Result<Vec<u8>, Error>
    where
        I: IntoIterator<Item = T>,
    {
        let (data, _, data_complete) = shreds.into_iter().try_fold(
            <(Vec<u8>, Option<u32>, bool)>::default(),
            |(mut data, prev, data_complete), shred| {
                // No trailing shreds if we have already observed
                // DATA_COMPLETE_SHRED.
                if data_complete {
                    return Err(Error::InvalidDeshredSet);
                }
                let shred = shred.as_ref();
                // Shreds' indices should be consecutive.
                let index = Some(
                    shred::layout::get_index(shred)
                        .ok_or_else(|| Error::InvalidPayloadSize(shred.len()))?,
                );
                if let Some(prev) = prev
                    && prev.checked_add(1) != index
                {
                    return Err(Error::from(TooFewDataShards));
                }
                data.extend_from_slice(shred::layout::get_data(shred)?);
                let flags = shred::layout::get_flags(shred)?;
                let data_complete = flags.contains(ShredFlags::DATA_COMPLETE_SHRED);
                Ok((data, index, data_complete))
            },
        )?;
        // The last shred should be DATA_COMPLETE_SHRED.
        if !data_complete {
            return Err(Error::from(TooFewDataShards));
        }

// Shreds occupy the majority of disk space in the Blockstore. Transaction
// metadata can occupy quite a bit of space as well for (RPC) nodes that are
// recording this data; however, this impact is very dependent and variable on
// cluster load and node configuration. Additionally, transaction and block
// metadata columns are keyed differently than other columns, and are not
// subject to the regular FIFO cleanup logic in this file. So at this time,
// block and transaction metadata columns are excluded from consideration in the
// comments below that describe targetting a fixed disk footprint.
//
// Shreds are approximated at 1250 bytes per shred:
// - Shreds have an upper bound of the IPv6 minimum MTU (1280 bytes); actual
//   paylod is less when networking headers are subtracted out.
// - Shred metadata columns introduce several kB overhead per slot. But, this
//   data is fixed per slot and relatively small when amortized per shred.
// - Data and coding shreds are assumed to be stored at a 1:1 ratio to match
//   consensus parameters. However, the budget is shared between the two so
//   the logic accounts for deviations from this assumption. Under normal
//   conditions, more data shreds will be present than coding shreds because
//   only missing data shreds are recovered and inserted (not coding shreds).
//
// Target a default 500 GB footprint for the Blockstore by default. Blocks may
// have infrequent access after replay, but keeping a decent amount of block
// history is useful for replaying from a snapshot as well as being a good
// network participant to be able to serve repair requests for older blocks.
pub const DEFAULT_MAX_BLOCKSTORE_SHREDS: u64 = 400_000_000;
// Allow down to 100m total shreds
pub const DEFAULT_MIN_MAX_BLOCKSTORE_SHREDS: u64 = 100_000_000;
