### Title
Post-default instant-withdraw requests bypass recovery gating and drain the fixed default-recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` explicitly branches on `defaultRecoveryFinalized` and funnels new requests into the isolated `postDefaultRequests` bucket, but `requestInstantWithdraw` performs no equivalent check. An attacker who requests an instant withdraw after default finalization gets a receipt recorded under `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (since `epochNumber` no longer advances after default), and `claimInstantWithdrawRequest` then routes it through `_claimDefaultedInstantWithdrawRequest`, paying out of the finite `defaultRecoveryReserve` that was sized exactly to cover pre-default claims. Like the CVE-2023-3390 pattern, the finalized-default state transition leaves a stale "current epoch" pointer (`epochNumber`/`defaultRecoveryEpoch`) that later requests in the same lifecycle reuse as if it were live, so already-spent recovery basis is claimed a second time.

### Finding Description
In `IdleCreditVault.sol`, `requestInstantWithdraw` (lines 356–375) burns the caller's strategy tokens, mints an equal receipt, and unconditionally indexes the new receipt into `instantWithdrawsRequestsByEpoch[_user][epochNumber]` while incrementing `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws`. After `finalizeDefaultRecovery` (lines 661–710) runs, `defaultRecoveryEpoch = epochNumber` and `epochNumber` is never advanced again, so any later instant request lands in the same epoch bucket that finalization already accounted for.

`claimInstantWithdrawRequest` (lines 380–393) first calls `_claimDefaultedInstantWithdrawRequest` when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. That function (lines 842–856) reads the full `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — which now includes the post-default request — burns the receipt, and transfers `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` out of `defaultRecoveryReserve` via `_transferDefaultRecovery`.

The reserve was computed in `finalizeDefaultRecovery` as `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and divided across `totalBasis` that only included claims existing at finalization (`defaultPendingClaimBasis`, line 644). A post-default requester therefore withdraws haircut recovery funds that were sized for, and economically belong to, the defaulted-epoch claimants. The remaining `claimInstantWithdrawRequest` code then burns the leftover `instantWithdrawsRequests[_user]` and pays it at par via `_transferFundedClaim`, compounding the drain. By contrast `requestWithdraw` (lines 247–257) reverts if prior receipts exist and stores new requests in `postDefaultRequests`, which are paid 1:1 only because the CDO pre-haircuts the amount — instant requests have no such isolation.

### Impact Explanation
Each post-default instant request converts CDO-held strategy tokens (whose NAV was already written down by the `_burn(idleCDO, activeBalance - activeFinalNAV)` in finalization) into a claim against the recovery reserve, effectively letting the attacker recover the same defaulted NAV twice: once in the crystallized tranche price and once as a reserve payout. Since `defaultRecoveryReserve` is finite, legitimate defaulted-epoch claimants and other instant receipt holders are left underfunded or unable to claim — direct theft and insolvency of the recovery pool, proportional to the attacker's post-default tranche balance.

### Likelihood Explanation
Requirements are modest: the pool must have suffered a borrower default with `finalizeDefaultRecovery` executed (a supported flow: `stopEpochWithDuration` loss → `defaulted()` → finalization), and the attacker needs only tranche tokens and an enabled instant-withdraw path — both unprivileged attacker capabilities under the threat model. No honest-actor cooperation is needed between the request and claim; sequencing is trivial once the vault sits in the finalized-default state. The main constraint is that `defaultInstantWithdrawsFinalized` must be true (i.e., `pendingInstantWithdraws != 0` at finalization) for the defaulted-claim path to pay the receipt; if false, the post-default request still falls through to the par `_transferFundedClaim` path, which pays funded claims but from a reserve that no longer corresponds to it.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is set, either revert or route the request into `postDefaultRequests`-style accounting (with the CDO passing a pre-haircut amount) so new receipts cannot join `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]`. Additionally, in `claimInstantWithdrawRequest`, compute the defaulted claim from a snapshot taken at finalization rather than the mutable `instantWithdrawsRequestsByEpoch` entry, so post-finalization increments cannot inflate the default-epoch basis.

### Proof of Concept
Conceptual Foundry fork sequence (solidity pseudo-test against `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
function testPostDefaultInstantDrain() external {
    // 1. Running epoch; user deposits AA, borrower draws funds.
    _depositWithUser(Alice, 1_000e6);
    vm.prank(manager); cdoEpoch.startEpoch();

    // 2. Honest user requests instant withdraw mid-epoch (receipt minted).
    _requestInstantWithdrawWithUser(Bob, bobTranches);

    // 3. Borrower defaults at stopEpoch: repay less than owed.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager); cdoEpoch.stopEpochWithDuration(apr, interest, duration, loss);

    // 4. Owner finalizes recovery with recoveredAmount R.
    vm.prank(manager); cdoEpoch.finalizeDefault(recovered, source);
    uint256 reserveBefore = strategy.defaultRecoveryReserve();

    // 5. Attacker (tranche holder) requests instant withdraw AFTER finalization.
    //    No defaultRecoveryFinalized check in requestInstantWithdraw.
    _requestInstantWithdrawWithUser(Attacker, attackerTranches);
    //    Receipt lands in instantWithdrawsRequestsByEpoch[Attacker][defaultRecoveryEpoch].

    // 6. Attacker claims: _claimDefaultedInstantWithdrawRequest pays
    //    claimBasis * defaultRecoveryPrice / RECOVERY_FULL from the reserve.
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    // Reserve is drained by a claim that never entered the finalization basis;
    // honest defaulted claimants are underfunded.
    assertLt(strategy.defaultRecoveryReserve(), reserveBefore);
}
```

Caveat: I could not fully verify the CDO-side guard on `requestInstantWithdraw` (whether `IdleCDOEpochVariant` blocks instant requests once `defaulted()` is true) or the body of `_transferDefaultRecovery`/`_transferFundedClaim`, so the exact entry-point gating should be confirmed during PoC development; the strategy-level accounting asymmetry described above is confirmed in the code.
