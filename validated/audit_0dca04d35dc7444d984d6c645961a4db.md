### Title
Stale per-epoch withdraw receipt is never cleared on the funded-claim path, allowing a replayed double payout after default finalization in a closed pool - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to the unvalidated/reused `orderId`, `IdleCreditVault` keys withdraw receipts by `(user, epochNumber)` in `withdrawsRequestsByEpoch`, but the normal funded-claim path clears only the aggregate `withdrawsRequests[_user]` and `lastWithdrawRequest[_user]`, leaving the per-epoch entry stale. When `epochNumber` is reused for a later claim-basis computation — which happens in a closed pool (`epochEndDate == 0`), where all subsequent requests are recorded under the same frozen `epochNumber` — the stale "identifier" is treated as a live receipt again by `_claimDefaultedWithdrawRequest`, producing a second payout for an already-claimed request.

### Finding Description
`requestWithdraw` in `IdleCreditVault` records each request under the current epoch: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 287–294), and in a closed pool skips `pendingWithdraws` (lines 276–280). The funded claim path `_claimFundedWithdrawRequest` burns the receipt tokens and zeroes `withdrawsRequests[_user]` and `lastWithdrawRequest[_user]`, but never touches `withdrawsRequestsByEpoch[_user][*]` (lines 338–348). Per-epoch entries are only deleted inside `_clearWithdrawClaimForEpoch`, which is reachable only via the loss-adjusted (`_claimLossAdjustedWithdrawRequest`) or defaulted (`_claimDefaultedWithdrawRequest`) claim paths.

After `finalizeDefault`, `defaultRecoveryEpoch` is set to the then-current `epochNumber`, and `_claimDefaultedWithdrawRequest` calls `_withdrawClaimAmountsForEpoch(_user, defaultRecoveryEpoch)`, which reads `withdrawsRequestsByEpoch[_user][_claimEpoch]` as the claim basis and pays `claimBasis * defaultRecoveryPrice / 1e18` out of `defaultRecoveryReserve`.

In a closed pool, `epochNumber` no longer advances (no further `stopEpoch`), so a user can:

1. `requestWithdraw` in closed-pool mode → entry recorded at `withdrawsRequestsByEpoch[user][E]`; tranche tokens burned, receipt minted.
2. `claimWithdrawRequest` → the `epochEndDate != 0` guard at line 326 is skipped, `_claimFundedWithdrawRequest` pays the full amount at par and clears the aggregate, but `withdrawsRequestsByEpoch[user][E]` stays non-zero.
3. Borrower defaults and `finalizeDefault` runs while `epochNumber` is still `E`, so `defaultRecoveryEpoch == E`.
4. `claimWithdrawRequest` again → `_claimDefaultedWithdrawRequest` re-reads the stale `withdrawsRequestsByEpoch[user][E]` basis and pays `claimBasis * defaultRecoveryPrice` once more from `defaultRecoveryReserve`, burning receipt tokens that correspond to the second mint (or, where accounting permits, paying basis that no longer has backing).

The "one receipt one payout" invariant is broken: the same epoch-keyed identifier is settled twice — once at par via the funded path, once haircutted via the defaulted path.

### Impact Explanation
Direct theft of recovery funds: the attacker withdraws `staleBasis * defaultRecoveryPrice` from `defaultRecoveryReserve` for a receipt that was already fully paid. Since the reserve is sized by `finalizeDefault` to cover legitimate defaulted-epoch receipts, a phantom claim dilutes or fully drains the recovery owed to other pending-withdrawal users (bounded by the attacker's prior deposit size, repeatable per stale entry accumulated across repeated request/claim cycles in the closed pool).

### Likelihood Explanation
Requires: (a) pool operating in closed mode (`epochEndDate == 0`), which is a supported pool lifecycle state where `requestWithdraw`/`claimWithdrawRequest` remain usable; and (b) a borrower default followed by `finalizeDefault` while `epochNumber` is unchanged. No privileged misbehavior is needed — the attacker is an ordinary KYC'd lender using only `requestWithdraw` and `claimWithdrawRequest`. Caveat: I could not fully verify within the iteration budget whether `finalizeDefault`/`_handleBorrowerDefault` is reachable while `epochEndDate == 0`, and whether `_hasWithdrawRequest` or default-finalization accounting independently consumes stale per-epoch entries; if default finalization is blocked in closed pools, the collision window narrows to any other flow that re-reads `withdrawsRequestsByEpoch` at a reused `epochNumber` (e.g., a second `lossRecoveryPriceByEpoch` write at the same epoch). The stale-entry defect itself is confirmed from code: the funded path never clears the per-epoch record.

### Recommendation
In `_claimFundedWithdrawRequest` (and `_settleApr0`/funded-claim path generally), clear `withdrawsRequestsByEpoch[_user][lastWithdrawRequest[_user]]` — and iterate/clear any other non-zero per-epoch entries for the user — before zeroing `lastWithdrawRequest`, mirroring the cleanup already done in `_clearWithdrawClaimForEpoch`. Alternatively, make `_claimDefaultedWithdrawRequest`/`_withdrawClaimAmountsForEpoch` ignore entries whose receipts were already settled (e.g., a per-epoch `claimed` flag), so an epoch key can never be paid twice.

### Proof of Concept
Foundry fork PoC sketch (against the mainnet fork setup used in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Pool put into closed mode (epochEndDate == 0) via the close-mode stopEpoch path.
// Attacker is a regular allowed lender `user`.

// 1) Closed-pool request -> recorded at withdrawsRequestsByEpoch[user][E]
uint256 req = cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));
assertEq(strategy.withdrawsRequestsByEpoch(user, E), req);

// 2) Immediate funded claim (epochEndDate==0 skips the epoch wait)
cdoEpoch.claimWithdrawRequest();
assertEq(strategy.withdrawsRequests(user), 0);
// BUG: stale per-epoch basis remains
assertEq(strategy.withdrawsRequestsByEpoch(user, E), req); // non-zero!

// 3) Borrower defaults; manager finalizes while epochNumber == E
//    (stopEpoch with default + finalizeDefault(recovered, payer))
//    -> defaultRecoveryEpoch == E, reserve funded.

// 4) Replay the same epoch key
uint256 balPre = underlying.balanceOf(user);
cdoEpoch.claimWithdrawRequest();
// Pays req * defaultRecoveryPrice / 1e18 a SECOND time from defaultRecoveryReserve
assertGt(underlying.balanceOf(user) - balPre, 0);
```

Key lines: request keyed by epoch (`IdleCreditVault.sol:282-294`), funded claim not clearing per-epoch entry (`IdleCreditVault.sol:338-348`), defaulted claim re-reading the same key (`IdleCreditVault.sol:772-784`, `_withdrawClaimAmountsForEpoch` at `IdleCreditVault.sol:862-870`).
