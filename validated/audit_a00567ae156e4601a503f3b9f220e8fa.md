### Title
Removing a multisig member does not purge their existing confirmations on other members' requests, allowing a request to execute with fewer live-member confirmations than `num_confirmations` requires - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` counts entries in the `confirmations` map for a `request_id` against `num_confirmations` to decide whether to execute a request [1](#0-0) . When a member is removed via `DeleteMember`, `delete_member` only deletes requests that the removed member *originated* (`r.member == member`), and clears confirmations only for those requests [2](#0-1) . It never scans the `confirmations` map to strip the removed member's confirmation entries from *other* members' still-open requests. This leaves a "ghost" confirmation from a no-longer-live member counted toward the threshold, letting a request execute even though fewer than `num_confirmations` currently-live members actually approved it.

### Finding Description
The multisig's core security invariant is "K of N live members must approve a request." The binding that must hold is:
`count(confirmations[request_id]) == count(confirmations by accounts/keys that are still in self.members)`.

- `confirm()` only checks `confirmations.len() as u32 + 1 >= self.num_confirmations`, using the raw size of the stored `HashSet<String>` for that request, with no cross-check against the live `self.members` set [3](#0-2) .
- `delete_member()` removes only outstanding requests whose *signer/originator* (`r.member`) equals the member being deleted; it does not iterate `self.confirmations` to remove that member's confirmation string from requests originated by someone else [4](#0-3) .
- Consequently, if a member confirms a request created by a different member, and is later removed from the multisig, their confirmation persists in the map and continues to count toward the execution threshold.

This breaks the equality above: after removal, `count(confirmations[request_id])` still includes the removed (non-live) member, so the recorded "confirmations" no longer equal confirmations "issued by accounts currently entitled to confirm."

### Impact Explanation
This is Critical: it allows a multisig request (e.g., `Transfer`, `AddKey`, `FunctionCall`, `AddMember`) to be executed below the intended threshold of live members. In a K-of-N scheme, an attacker who is one of the remaining members can combine their own live confirmation with a stale confirmation left behind by a departed/removed member to reach `num_confirmations`, effectively executing a transfer or privileged action with fewer genuinely-authorizing members than the multisig's configured security threshold — a direct "multisig request executed below threshold" scenario.

### Likelihood Explanation
Requires: (1) a member other than the request's originator confirms a request but the request doesn't reach the threshold yet, and (2) that confirming member is later removed via `DeleteMember` while their confirmation is still outstanding on that unexecuted request. Member turnover (e.g., an employee/partner leaving, a compromised key being rotated out) combined with slow-to-finalize multisig requests is a realistic, non-exotic operational sequence, and no special privilege beyond being a current member is needed to exploit the residual ghost confirmation.

### Recommendation
When deleting a member, iterate all outstanding `requests`/`confirmations` and:
- Remove the deleted member's confirmation string from every request's confirmation set (not only requests they originated), and/or
- On `confirm()`, validate that every existing entry in `confirmations.get(&request_id)` still corresponds to a member present in `self.members` before counting them toward `num_confirmations` (i.e., recompute a "live" confirmation count rather than trusting the stored set size).

### Proof of Concept
1. Initialize multisig with members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request` to create a `Transfer` request sending funds to `A`.
3. `C` calls `confirm(request_id)` — `confirmations[request_id] = {C}` (1 of 2, not yet executed).
4. Members `B` and `A` (or any 2-of-3 including A) submit and confirm a `DeleteMember { member: C }` request — `delete_member` runs but only removes requests where `r.member == C`; A's Transfer request keeps `confirmations[request_id] = {C}` untouched [5](#0-4) . Now live members are `{A, B}`.
5. `A` calls `confirm(request_id)` on the original Transfer request. `confirmations.len() (1, from removed C) + 1 (A) = 2 >= num_confirmations (2)` → request executes via `execute_request` [6](#0-5) , transferring funds to `A` with only one genuinely live confirming member (`A`) instead of the required two.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
