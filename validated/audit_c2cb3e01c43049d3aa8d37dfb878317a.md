### Title
Tenure-change duplicate-block guard checks only globally-accepted state, allowing a signer to sign two conflicting tenure-change blocks for the same tenure - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`SortitionsView::validate_tenure_change_payload` rejects a second tenure-change `BlockProposal` for a tenure only if `signer_db.get_last_globally_accepted_block` already returns a block for that `consensus_hash`. Because this query only reflects blocks that have crossed the network-wide global-acceptance threshold, a first tenure-change block that this signer has only *locally* signed (not yet globally accepted) does not populate that lookup, so a second, conflicting tenure-change proposal for the same tenure passes this guard and can be signed too.

### Finding Description
The intended uniqueness property, stated in the guard's own warning message ("we've already signed a block in this tenure"), is that this signer signs at most one tenure-change block per tenure. The implementation instead checks: [1](#0-0) 

`get_last_globally_accepted_block(&block.header.consensus_hash)` only returns a block once it has accumulated enough signer signatures to be globally accepted on the network — not merely once this signer has locally signed it. There is no complementary check against "has this signer already signed *any* block for this consensus_hash" for the tenure-change branch.

Contrast this with the non-tenure-change branch of `check_proposal`, which instead validates against the local canonical tip via `SortitionData::confirms_latest_block_in_same_tenure`: [2](#0-1) 
That branch is not exercised for tenure-change proposals — tenure-change payloads are routed exclusively through `validate_tenure_change_payload`, which relies solely on the global-acceptance lookup for its duplicate check.

Exploit flow:
1. Attacker wins the current miner slot (single BTC-funded slot, no privileged role needed).
2. Attacker crafts a first tenure-change `BlockProposal` (`consensus_hash = CH`) and gossips it via StackerDB; the target signer validates and locally signs it (state recorded in signerdb as locally accepted, but global acceptance threshold not yet reached).
3. Before global acceptance propagates, the attacker crafts a second, conflicting tenure-change `BlockProposal` also with `consensus_hash = CH` (different block content/parent choice) and gossips it.
4. The target signer calls `check_proposal` → `validate_tenure_change_payload` for the second proposal. `get_last_globally_accepted_block(CH)` returns `None` (first block not yet globally accepted), so the `DuplicateBlockFound` branch never fires.
5. All other checks in `validate_tenure_change_payload` (parent-tenure match, `check_tenure_change_confirms_parent`, `check_parent_tenure_choice`) can independently pass for the second proposal since it targets the same sortition/tenure and can reuse a valid parent choice.
6. The signer proceeds to sign the second, conflicting tenure-change block, producing two differently-signed tenure-change blocks for the same tenure from the same signer.

### Impact Explanation
This breaks the uniqueness/safety property that a signer must sign at most one (canonical) block per tenure slot for a tenure-change. If enough signers hit this same race (all racing on the same attacker-controlled two proposals), two conflicting tenure-change blocks could each collect enough signatures to become independently valid/broadcastable, resulting in a signer-level equivocation on a tenure boundary — matching the Critical category ("a signer signing an invalid, non-canonical, or conflicting block; a signature valid across ... tenure boundaries").

### Likelihood Explanation
The attacker needs only: (a) to win a single sortition/miner slot with their own BTC, and (b) to gossip two competing tenure-change `BlockProposal`s in quick succession over StackerDB, both of which are explicitly within the unprivileged attacker capability defined in scope. No majority of signers, no compromised keys, and no local access are required. The only precondition is a timing window between local signing and network-wide global acceptance of the first block, which routinely exists in the gossip-based signing protocol and is repeatable every tenure.

### Recommendation
In `validate_tenure_change_payload`, replace (or supplement) the `get_last_globally_accepted_block` lookup with a check against any block this signer has already locally signed/accepted for the same `consensus_hash` (e.g., using the same underlying data source as `has_signed_block_in_tenure`, or a dedicated "have I already signed a block for this tenure" query), so the `DuplicateBlockFound` rejection fires as soon as this signer has locally signed one candidate, not only after global acceptance.
