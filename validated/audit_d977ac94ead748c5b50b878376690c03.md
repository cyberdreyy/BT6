### Title
Dust deposits mint zero tranche tokens and dust withdraw requests burn shares for a zero-value receipt - (File: contracts/IdleCDO.sol, contracts/IdleCDOCreditVault.sol, contracts/IdleCDOEpochVariant.sol)

### Summary
The vault has no minimum-mint or minimum-redemption check. `_mintSharesAtCurrPrice` computes `minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` with round-down division, so any deposit where `_amount < _tranchePrice / ONE_TRANCHE_TOKEN` transfers the full underlying into NAV while minting 0 tranche tokens. The reverse path has the symmetric flaw: `_withdraw` / `requestWithdraw` compute `toRedeem = _amount * _tranchePrice / ONE_TRANCHE_TOKEN`, so a small tranche-token amount burns the user's shares while paying out 0 underlying (or creating a 0-value withdrawal receipt).

### Finding Description
In `IdleCDO._deposit`, the underlying is pulled from the user first, then `_mintSharesAtCurrPrice` mints shares at the current tranche price [1](#0-0) . The mint calculation is pure integer division [2](#0-1) :

```solidity
_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche);
_mintShares(_tranche, _to, _minted, _amount);
```

`_mintShares` credits the *full* `_amount` of underlyings to `lastNAVAA`/`lastNAVBB` even when `_minted == 0` [3](#0-2) . Whenever the tranche price is above `1 * ONE_TRANCHE_TOKEN` (the normal state for any tranche that has accrued yield), any `_amount` below `price / 1e18` units of underlying mints zero shares while permanently inflating the tranche NAV — a forced donation to all other holders. The identical unchecked division exists in `IdleCDOCreditVault._mintSharesAtCurrPrice` [4](#0-3) .

The reverse operation is also affected. `IdleCDO._withdraw` computes `toRedeem = _amount * _tranchePrice(_tranche) / ONE_TRANCHE_TOKEN` and burns `_amount` shares regardless of the rounded result [5](#0-4) . In `IdleCDOEpochVariant.requestWithdraw`, `_underlyings = _trancheToUnderlyings(_amount, _tranche)` rounds to 0 for a dust `_amount`; `creditVault.requestWithdraw(0, msg.sender, 0)` then records a zero-value receipt while `_withdrawOps(_amount, 0, _tranche)` burns the tranche tokens and reduces NAV by 0 [6](#0-5)  — the user's principal is destroyed with no claim at all. The same zero-mint hole exists in `depositDuringEpoch`, where `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` can round to 0 while `_transferUnderlyings(_borrower(), _amount)` still forwards the funds to the borrower [7](#0-6) .

### Impact Explanation
Any user (KYC-passing lender or tranche holder) who deposits or requests withdrawal of a dust amount permanently loses the entire transaction value: depositors get 0 shares while their underlying is absorbed into `lastNAV`/`getContractValue` (a wealth transfer to remaining holders), and withdrawers burn tranche tokens for a receipt that pays 0. The loss per transaction is bounded below one unit of underlying at the current price, so individual impact is dust-sized, but the invariant broken — fair mint/burn: every unit of underlying taken must mint a claim, every share burned must yield a redemption — is unconditional and there is no revert or guard (`_checkIs0` only guards the `_amount == 0` input path in `_withdraw`, not the rounded-down output) [8](#0-7) . For `depositDuringEpoch` the loss additionally accrues to the borrower, who receives dust underlyings the depositor can never reclaim.

### Likelihood Explanation
Low. It requires a user to deliberately or mistakenly transact below ~1 wei-equivalent of underlying per unit of tranche price (e.g. a few wei of a 6-decimal USDC vault after price appreciation). There is no minimum-deposit check, no minted>0 check, and no redeemed>0 check anywhere in the deposit/withdraw/request path, so nothing prevents it; it simply yields no profit to an attacker and only burns the transactor's own dust.

### Recommendation
- In `_mintSharesAtCurrPrice` (both `IdleCDO` and `IdleCDOCreditVault`), revert or return early when `_minted == 0` before transferring underlyings — or better, revert in `depositAA`/`depositBB`/`depositDuringEpoch` if the computed mint is 0 so no funds are taken.
- In `_withdraw` and `IdleCDOEpochVariant.requestWithdraw`, revert when the computed `toRedeem`/`_underlyings` is 0 (after the redeem-all `_amount == 0` resolution) so dust shares cannot be burned for nothing.
- Alternatively enforce a documented minimum deposit/withdraw amount at the entry points.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

// Assume a standard IdleCDOEpochVariant / IdleCDO deployment with USDC (6 decimals)
// and tranchePrice > 1e18 after accrued yield (e.g. 1.1e18).

contract DustZeroMintPoC is Test {
    // --- Deposit side: minted == 0 while NAV absorbs the funds ---
    function testDustDepositMintsZero() public {
        // tranchePrice = 1.1e18  => any _amount < 1.1 units of underlying rounds to 0
        uint256 dust = 1; // 1 wei USDC

        uint256 navPre = idleCDO.lastNAVAA();
        deal(address(underlying), user, dust);
        vm.startPrank(user);
        underlying.approve(address(idleCDO), dust);
        uint256 minted = idleCDO.depositAA(dust);
        vm.stopPrank();

        assertEq(minted, 0, "dust deposit minted shares");
        assertEq(AAtranche.balanceOf(user), 0);
        assertEq(idleCDO.lastNAVAA(), navPre + dust, "NAV grew without minting");
        assertEq(underlying.balanceOf(user), 0, "user funds taken for nothing");
    }

    // --- Withdraw side: shares burned for a 0-value receipt ---
    function testDustWithdrawRequestBurnsForZero() public {
        // user holds some AA tranche tokens; request withdrawal of a dust share amount
        // such that _amount * tranchePrice / 1e18 == 0
        uint256 dustShares = 1; // 1 wei of tranche token, price ~1e18 => underlyings = 0

        vm.prank(user);
        uint256 requested = cdoEpoch.requestWithdraw(dustShares, address(AAtranche));

        assertEq(requested, 0, "receipt value should be 0");
        // tranche tokens were burned anyway
        assertLt(AAtranche.balanceOf(user), balBefore, "shares burned for zero");
        // lastNAVAA was reduced by `principal` == 0, so NAV is unchanged:
        // the burned shares' value is redistributed to remaining holders
    }
}
```
Steps: fork a live credit vault (or bootstrap the standard test fixture), let the tranche price drift above `1e18` via `startEpoch`/`stopEpoch`, then (1) call `depositAA(1)` from a funded EOA — observe `minted == 0` and `lastNAVAA` increasing by 1; (2) call `requestWithdraw(1, AATranche)` — observe a zero-value strategy-token receipt while 1 tranche token is burned, permanently forfeiting that principal.
