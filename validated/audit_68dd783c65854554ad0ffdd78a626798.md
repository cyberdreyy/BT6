### Title
Stale rejected-weight after a signer reconsiders lets a stuck rejection override a valid acceptance - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies per-block signer weight into two separate counters, `total_weight_approved` and `total_weight_rejected`, guarded by two *different* membership checks (`gathered_signatures` for accept, `responded_signers` for reject). When a signer legitimately reconsiders a rejection and later accepts the same block — an explicitly supported transition in the signer's own state machine — the listener adds the signer's weight to `total_weight_approved` but never removes it from `total_weight_rejected`. The miner-side coordinator checks the rejection threshold before the approval threshold, so the stale rejected weight can make it treat an actually-approved block as globally rejected.

### Finding Description
Node-side, `StackerDBListener::run` processes `BlockResponse` messages from signers and mutates a shared `Arc<(Mutex<HashMap<Sha512Trunc256Sum, BlockStatus>>, Condvar)>` (`self.blocks`):

- On `Accepted`: weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, then `block.responded_signers.insert(slot_id)` is unconditionally executed. [1](#0-0) 

- On `Rejected`: weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot has "responded" at all). [2](#0-1) 

These two branches use inconsistent bookkeeping keys for the *same* logical fact ("has this signer already voted, and how"):

- If a signer **rejects first, then accepts** the same `signer_signature_hash`: the reject path inserts the slot into `responded_signers` and adds its weight to `total_weight_rejected`. Later, the accept path checks `gathered_signatures` (which is still empty for this slot), so it also adds the same signer's weight to `total_weight_approved`. The weight is never subtracted from `total_weight_rejected`. The two accumulators for the same slot/block are now simultaneously non-zero for the same signer, and `total_weight_rejected` is permanently stale/stuck at a value that no longer reflects the signer's current opinion.
- The reverse order (accept then reject) is at least partially guarded — `responded_signers` already contains the slot, so the later reject is silently dropped and `total_weight_rejected` is correctly not incremented — but this "protection" only exists because of the asymmetric checks, not because the code deliberately models vote revision.

This reject→accept sequence is not a corner case; it's the codebase's own documented, intended behavior. The signer's local model explicitly treats "signed" state as reachable from "locally/globally rejected" and rejection as "a revocable opinion" whose weight can later be re-aggregated toward acceptance: [3](#0-2) [4](#0-3) 

and `should_reevaluate_block` / `should_reevaluate_reject_reason` on the signer side are built precisely to let a signer revisit a prior rejection on a re-proposal and issue an acceptance for the same block: [5](#0-4) 

On the miner side, `SignerCoordinator` evaluates the rejection condition *before* the approval condition on every poll of the shared `BlockStatus`: [6](#0-5) 

So a stuck/stale `total_weight_rejected` (inflated by signers who have since reconsidered and accepted) can cross `total_weight - weight_threshold` and force `Err(NakamotoNodeError::SignersRejected)` even though those same signers' current opinion, reflected in `total_weight_approved`, has independently reached the signing threshold. This breaks the "aggregated-weight vs verified-accepts" equality the shared `BlockStatus` map is supposed to maintain: the weight bookkeeping no longer corresponds 1:1 to each signer's *current* vote, and a stale rejection is effectively "recounted" against a block that the signer set has actually approved.

### Impact Explanation
This is a liveness wedge for block production: a block that genuinely reaches the 70% approval threshold (verified accepts) can still be reported as globally rejected by the coordinator because of leftover, never-cleared rejection weight from signers who changed their mind — a state the signer protocol explicitly allows and expects the aggregator to tolerate. Repeated occurrences (e.g., a slow signer that rejects on first pass due to `ConnectivityIssues`/timing and then accepts on reconsideration) can stall tenures or force unnecessary tenure-extends/re-proposals, matching the "signer set wedged" liveness class called out in scope. It does not require a signer majority or key compromise — a single signer following the normal reconsideration path is sufficient to corrupt the shared weight state for that block.

### Likelihood Explanation
High under ordinary operating conditions: reject→accept for the same block is a documented, tested transition (`reject_then_accept`, `has_signed_block`, `signers_respond_to_unprocessed_globally_rejected_block_proposals`), not an adversarial edge case. Any signer that initially rejects (e.g., due to a transient chainstate mismatch, connectivity timeout, or a reconsiderable reject reason) and later legitimately accepts the same block will trigger the double-booked weight. No special timing, majority, or malicious signer is required — only two ordinary StackerDB messages from one signer for one block.

### Recommendation
Make the two accumulators derive from a single per-slot "current vote" record instead of two independently-guarded weight tallies:
- Track a `HashMap<slot_id, Vote>` (Accepted/Rejected) per block, and recompute `total_weight_approved`/`total_weight_rejected` from that map (or explicitly move the weight: on a new Accepted for a slot previously in `Rejected`, subtract the weight from `total_weight_rejected` before adding it to `total_weight_approved`, and symmetrically for Rejected after Accepted).
- Use the same membership key (e.g., a single `votes: HashMap<u32, BlockResponseKind>`) for both branches in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` instead of the disjoint `gathered_signatures`/`responded_signers` sets.

### Proof of Concept
1. Node proposes block `B` with `signer_signature_hash = H`; `StackerDBListener` creates `BlockStatus` for `H` with `total_weight_approved = total_weight_rejected = 0`.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `H` (e.g., due to a transient `check_block_against_signer_db_state` failure). Handler at [7](#0-6) 
inserts `S`'s slot into `responded_signers` and sets `total_weight_rejected = w`.
3. `S` later reconsiders (per `should_reevaluate_block`/`should_reevaluate_reject_reason` on the signer side) and sends `BlockResponse::Accepted` for the *same* `H`.
4. Handler at [1](#0-0) 
finds `gathered_signatures` empty for `S`'s slot (only `responded_signers` was touched in step 2), so it adds `w` to `total_weight_approved` as well. Result: `total_weight_approved = w` **and** `total_weight_rejected = w` simultaneously for the same signer/block, with no code path ever decrementing `total_weight_rejected`.
5. If enough other signers' weight pushes `total_weight_rejected + weight_threshold > total_weight` (using this stale `w`), `SignerCoordinator::wait_for_signatures` (or equivalent) returns `Err(SignersRejected)` at [8](#0-7) 
even though the *current* signer opinions (reflected by `total_weight_approved`) would otherwise cross the acceptance threshold — the miner abandons a block the signer set has actually endorsed.
