## Title
Reorg-Timing Guard Defaults Missing Local Approval-Time to Zero, Letting a Signer Permit an Illegitimate Reorg of an Established Tenure - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner may legitimately reorg a prior tenure by measuring the time between when *this signer itself* approved the reorged tenure's first block and when *this signer* received the new tenure's burn block. When the local `BlockInfo` record for the reorged tenure exists but this signer never recorded an `approved_time` for it, the code substitutes `0` for the elapsed time instead of rejecting or treating the timing as unknown, which makes the "poorly timed, so a reorg is allowed" branch fire unconditionally.

### Finding Description
`check_parent_tenure_choice` in [1](#0-0)  is the only place that decides, and durably records via `mark_tenure_superseded`, whether a miner's reorg of a prior tenure is legitimate. For every reorged tenure, it first checks whether more than one block was *globally accepted* in that tenure — from the local signer DB — and rejects the reorg if so [2](#0-1) . If the node reports the tenure produced a first block, the code looks up this signer's own local record of that block via `get_first_approved_block_in_tenure`, and refuses the reorg outright if no local record exists at all [3](#0-2) .

However, when a local record *does* exist but this signer's own `approved_time` for it is `None`, the code does not refuse the reorg or treat the situation conservatively. Instead it substitutes `0` for the elapsed "proposal to sortition" duration:

```
let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
    sortition_state_received_time.saturating_sub(approved_at)
} else {
    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
    0
};
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    // ... "the block was poorly timed, allowing the reorg" — recorded via superseded_tenures
``` [4](#0-3) 

Because `0` is always less than any positive `first_proposal_burn_block_timing` configured on the signer, this branch always concludes the reorg is "poorly timed" and therefore permitted, regardless of how much wall-clock time actually separated the reorged tenure's block from the new sortition. The reorg is then recorded as a sanctioned "supersession" via `mark_tenure_superseded`, which subsequently causes this signer's own already-placed signature over the reorged tenure's block to stop counting as a conflict in `get_signed_conflicts`/`reorg_permit_stands` [5](#0-4) [6](#0-5) , and it will go on to sign the replacement block.

This defaulting-to-zero path is reachable precisely in the scenario the code's own comment describes: this particular signer has a local `BlockInfo` for the reorged tenure's first block (so the "no local knowledge" refusal at lines 234-245 does not trigger) but never itself signed/pre-committed it (so `approved_time` was never set). A one-slot miner, by controlling tenure-start timing and relying on ordinary propagation asymmetries across the signer set (a signer that received/queued the proposal but rejected, timed out, or was still pending validation when the tenure switched), can arrange for some signers to be in exactly this state while the tenure is, in fact, well-established (already multiply confirmed/globally accepted from the perspective of other signers and the canonical chain). Those affected signers will then unconditionally treat any subsequent reorg attempt as "poorly timed" and permit it — defeating the entire purpose of `first_proposal_burn_block_timing`, which exists specifically to prevent reorgs of tenures that have had enough time to be properly confirmed.

### Impact Explanation
This breaks the "approved-parent vs canonical" equality that `check_parent_tenure_choice` is meant to enforce. A subset of signers can be induced, without any majority collusion or key compromise, to sign a block that illegitimately reorgs an established tenure (one that other signers correctly refuse to let be reorged), and to retroactively treat their own already-placed signature over the original tenure's block as void. This is a signer signing a conflicting/non-canonical block — a Critical-class impact per the stated criteria.

### Likelihood Explanation
The triggering condition (a local record exists but `approved_time` is `None`) is not a hypothetical edge case — it is explicitly anticipated and logged by the existing code comment ("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal"), confirming the path is reachable in normal operation (e.g., the block was received and stored but rejected/pending/never pre-committed by this particular signer before the tenure was superseded). A miner fully controls tenure sequencing and burn-block timing and only needs ordinary propagation-timing variance across the signer set (no majority or key compromise) to land some signers in this state.

### Recommendation
Do not substitute `0` when `local_block_info.approved_time` is `None`. Since the safe, conservative direction here is to refuse the reorg (as is already done when there is no local record at all), the missing-`approved_time` case should likewise cause `check_parent_tenure_choice` to return `Ok(false)` (or otherwise avoid comparing against `first_proposal_burn_block_timing` using a fabricated zero duration), rather than defaulting to a value that always satisfies the "poorly timed" condition.

### Proof of Concept
1. A miner starts tenure A and gets its first block confirmed/globally accepted by the signer set at large; assume signer S receives and stores the block proposal but does not pre-commit/sign it before A is treated as replaced (e.g., S was still awaiting validation, or previously rejected it for a reason unrelated to timing, leaving a `BlockInfo` record in S's DB with `approved_time == None`).
2. The miner (or a colluding/next miner) quickly wins the next sortition and proposes a tenure B that reorgs A.
3. On signer S, `check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170-290`) finds `local_block_info` for A's first block (non-`None`), but `local_block_info.approved_time == None`.
4. `proposal_to_sortition` is set to `0` (line ~257), which is always `< first_proposal_burn_block_timing`, so the code logs "the block was poorly timed, allowing the reorg" and marks A's tenure as superseded.
5. S proceeds to sign B's block, and its earlier signature over A's block is excluded from `get_signed_conflicts` via `reorg_permit_stands`, even though A may already be globally accepted from the perspective of other signers/the canonical chain — producing a signer that has now signed a conflicting/non-canonical block relative to the rest of the network's view.

    /// Record that we permitted the tenure identified by `superseded_by_*` to reorg this one
    /// under the reorg-timing rules (`first_proposal_burn_block_timing`).
    ///
    /// Having sanctioned the replacement, our own signature over what this tenure built must not
    /// then block it: its blocks stop counting as conflicts (see
    /// [`SignerDb::get_signed_conflicts`]). Recorded when the reorg is permitted rather than
    /// derived at signing time, because by the time a replacement reaches the pre-commit
    /// threshold the sortition view that sanctioned the reorg may be long gone.
    ///
    /// The permit is only honored while the permitting tenure's sortition is still canonical
    /// (checked against the node when the record is applied): if a burnchain fork orphans it,
    /// the reorg we sanctioned can no longer happen, so the record must not keep suppressing
    /// this tenure's conflicts. A re-permit by a different tenure replaces the record, so the
    /// latest permitting sortition is the one checked. Records age out via
    /// [`SignerDb::prune_superseded_tenures`].
    pub fn mark_tenure_superseded(
        &mut self,
        consensus_hash: &ConsensusHash,
        burn_block_height: u64,
        superseded_by_consensus_hash: &ConsensusHash,
        superseded_by_burn_block_hash: &BurnchainHeaderHash,
    ) -> Result<(), DBError> {
        self.db.execute(
            "INSERT OR REPLACE INTO superseded_tenures (consensus_hash, burn_block_height, superseded_by_consensus_hash, superseded_by_burn_block_hash, superseded_at) VALUES (?1, ?2, ?3, ?4, ?5)",
            params![
                consensus_hash,
                u64_to_sql(burn_block_height)?,
                superseded_by_consensus_hash,
                superseded_by_burn_block_hash,
                u64_to_sql(get_epoch_time_secs())?
            ],
        )?;
        Ok(())
    }

    /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
