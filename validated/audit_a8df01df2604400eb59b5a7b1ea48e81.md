### Title
Second `requestWithdraw` overwrites `lastWithdrawRequest`, letting a loss-adjusted receipt drain the reserve at par - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The ath10k bug is a premature unmap: a DMA buffer is freed on a "copy complete" interrupt while the hardware is still reading it. The credit-vault analog is the premature clearing of the *claim epoch marker*. `IdleCreditVault.requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user]` (contracts/strategies/idle/IdleCreditVault.sol:282). `_claimLossAdjustedWithdrawRequest` looks up the haircut only via `lastWithdrawRequest[_user]` → `lossRecoveryPriceByEpoch` (lines 789–801), while the actual claim basis still lives in the aggregate `withdrawsRequests[_user]` and per-epoch `withdrawsRequestsByEpoch[_user][epoch]`. A user who re-requests a withdraw before claiming a loss-adjusted receipt destroys the epoch link the same way the driver unmaps a buffer still in use: the pending claim can no longer be routed to its haircut price and is instead paid at par through `_claimFundedWithdrawRequest`.

### Finding Description
1. Epoch N ends via `stopEpochWithDuration` with a loss, so `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL` is set and the borrower's funded amount already reduces `pendingWithdraws`, but each user's receipt basis remains in `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][N]` until claimed (comment at line 797: "pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount").
2. In epoch N+1 (buffer phase) the same user calls `requestWithdraw` again. Lines 279–294 bump `pendingWithdraws`, `withdrawsRequests[_user]`, and `withdrawsRequestsByEpoch[_user][N+1]`, and overwrite `lastWithdrawRequest[_user] = N+1`.
3. Now `_claimLossAdjustedWithdrawRequest` computes `lossEpoch = lastWithdrawRequest[_user] = N+1`; `lossRecoveryPriceByEpoch[N+1]` is 0, so it returns without calling `_clearWithdrawClaimForEpoch`. The epoch-N basis is stranded inside the aggregate.
4. After epoch N+1 ends (`epochNumber > lastWithdrawRequest[_user]`), `_claimFundedWithdrawRequest` passes its gate, pays `withdrawsRequests[_user]` — which still includes the epoch-N amount — at par via `_transferFundedClaim`, and only then clears the aggregates (lines 319–350).
5. The user receives `epochN_basis` instead of `epochN_basis * lossRecoveryPrice / RECOVERY_FULL`. The haircut difference `(1 − lossRecoveryPrice) × basis` is paid out of the strategy's funded-underlying balance / `defaultRecoveryReserve`, stealing from other claimants.

Existing guards do not stop it: `_claimFundedWithdrawRequest` only checks `epochNumber <= lastWithdrawRequest[_user]`, `_clearWithdrawClaimForEpoch` is keyed off the overwritten marker, and `_transferFundedClaim` only protects `defaultRecoveryReserve` (which does not exist in a healthy `stopEpochWithDuration` loss scenario — the haircut funds sit as ordinary strategy balance). The comment at lines 323–324 even acknowledges "if a user does not claim … he will have to wait for another epoch," but the protocol never intended the old receipt to be upgraded from haircutted to par.

### Impact Explanation
Direct theft: any lender with a withdraw request pending through a loss epoch can recover the full un-haircutted amount by placing a second small `requestWithdraw` in the next epoch. The excess `(1 − lossRecoveryPrice) × basis` is paid from underlyings owed to other pending redeemers and depositors, breaking the loss-waterfall invariant that `stopEpochWithDuration` losses are borne by the withdraw requesters of that epoch. With a 50% loss price and a 1M-claim request, the attacker extracts ~500k extra units.

### Likelihood Explanation
Requires only an unprivileged tranche-token holder. The sequence is two `requestWithdraw` calls bracketing a `stopEpochWithDuration` loss epoch — no privileged action, no default needed. The re-request can be a dust amount; only requirement is that `epochNumber` advances past the new `lastWithdrawRequest`, which happens every epoch boundary. Likelihood is moderate: it needs a loss epoch to occur, which is a normal (honest manager) protocol event.

### Recommendation
Track the loss-claim epoch independently of `lastWithdrawRequest`, or iterate a per-user set of pending epochs. Minimal fix: store the request epoch per receipt (e.g., make `withdrawsRequestsByEpoch` the source of truth and let `_claimLossAdjustedWithdrawRequest` scan `withdrawsRequestsByEpoch[_user][e]` for any epoch `e` with `lossRecoveryPriceByEpoch[e] != 0`), or block `requestWithdraw` while a user still has a receipt in an epoch with a non-zero `lossRecoveryPriceByEpoch`/`defaultRecoveryEpoch` claim, or store `lastWithdrawRequest` as a list so overwriting cannot orphan the older receipt.

### Proof of Concept
```solidity
// Foundry fork PoC (skeleton) — strategy = IdleCreditVault, cdo = IdleCDOEpochVariant
function testLossReceiptUpgradedToPar() external {
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, 1_000_000 * ONE_SCALE, true);   // epoch N-1 buffer deposit

    // epoch N running, then stopEpochWithDuration with a loss (e.g., borrower returns 60%)
    _startEpochAndCheckPrices(0);
    vm.prank(attacker);
    uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche)); // receipt epoch N
    uint256 lossPrice = 6e17; // 60% recovery
    // borrower funds the loss-adjusted amount; manager stops epoch with loss
    _stopEpochWithLoss(basis * lossPrice / 1e18);

    // lastWithdrawRequest[attacker] == N; lossRecoveryPriceByEpoch[N] = 0.6e18
    // ATTACK: instead of claiming at 60%, request a dust withdraw in epoch N+1
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche));           // overwrites marker to N+1

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, apr, expectedFunds);           // epochNumber > N+1

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();                           // goes to _claimFundedWithdrawRequest

    // Paid ~basis at par instead of basis * 0.6 — extra 40% * basis taken from other claimants
    assertGt(underlying.balanceOf(attacker) - balPre, basis * lossPrice / 1e18);
}
```
The exploit works because `requestWithdraw` at line 282 sets `lastWithdrawRequest[_user] = currentEpoch` without checking that the previous epoch's receipt was already claimed, and `_claimLossAdjustedWithdrawRequest` (lines 789–795) trusts that single marker to locate the pending loss claim — the orphaned epoch-N basis remains in `withdrawsRequests[_user]` and is paid at par once the funded-claim epoch gate clears.

One caveat worth noting: I was unable to fully read `stopEpochWithDuration`'s internals to confirm `withdrawsRequestsByEpoch` is left populated (not decremented) after borrower funding; the comment at line 797 and the existence of `_clearWithdrawClaimForEpoch` strongly indicate the per-epoch basis persists until claim, but if the epoch-N basis were fully removed from `withdrawsRequests` at funding time the overpay path would not exist.
