### Title
Unauthenticated `/v2/resume/:runID` endpoint allows any unprivileged client to complete or corrupt arbitrary pending pipeline runs - (File: core/web/router.go, core/web/pipeline_runs_controller.go)

### Summary
The GoGoPool finding describes an FSM defect where a privileged actor (Rialto) can transition a Minipool through states without the system verifying that the resource backing the transition (the node operator's AVAX deposit) is actually still associated with that state. The analogous weakness in `chainlink--015` is the `PATCH /v2/resume/:runID` route, which is registered with **no authentication middleware at all** and drives a pipeline-run state transition (`suspended` → `running`/`completed`/`errored`) using only a bare UUID as the sole "credential", with no verification that the caller is the actual bridge/external adapter that owns that specific task.

### Finding Description
In `core/web/router.go`, the resume route is deliberately placed in the unauthenticated group: [1](#0-0) 

```go
func v2Routes(app chainlink.Application, r *gin.RouterGroup) {
	unauthedv2 := r.Group("/v2")
	prc := PipelineRunsController{app}
	...
	unauthedv2.PATCH("/resume/:runID", prc.Resume)
```

The handler itself performs no authorization check beyond parsing the UUID and decoding the body: [2](#0-1) 

It calls `App.ResumeJobV2(ctx, taskID, result)` → `runner.ResumeRun` → `orm.UpdateTaskRunResult`, which selects and updates the task purely by `taskID`, checking only that the parent run is in `running`/`suspended` state — with no binding to the identity of whichever bridge/external adapter the task was dispatched to: [3](#0-2) [4](#0-3) 

Just as `recreateMinipool` transitioned Minipool state without verifying the AVAX-deposit invariant tied to that specific state, this endpoint performs a job-run state transition (`Suspended → Running/Completed/Errored`) keyed solely by an opaque UUID, without verifying that the request actually originates from — or is authorized on behalf of — the specific external adapter/bridge that was given that task ID. The UUID is the *only* factor standing in for "ownership" of the task; any actor able to observe or reconstruct that UUID (e.g. via bridge server logs, HTTP proxies, browser history, monitoring tools, or a compromised/malicious third-party adapter that the operator integrated) can inject arbitrary `value`/`error` results into ANY node's ANY pending pipeline run at any time, not just the one it was meant to resume.

### Impact Explanation
An attacker who obtains a valid pending `runID` (task UUID) can:
- Force completion of a suspended job run with attacker-chosen output, potentially causing incorrect on-chain data to be written by a job whose result feeds a transaction task (unauthorized/forged job-run completion — cross-user response confusion, since the completing party is not the entity the pipeline was waiting on).
- Repeatedly resume/error out runs to disrupt jobs (denial of correct operation) belonging to other bridges/EI configurations on the same node.

This mirrors the GoGoPool root cause: a state-machine transition exposed without re-validating that the invariant tied to that state (correct deposit / correct originating caller) still holds.

### Likelihood Explanation
Exploitability depends on the attacker discovering a live, still-pending `runID`. This is plausible in practice because: the URL containing the UUID is sent as plaintext over HTTP(S) to third-party bridge/adapter servers (outside the node operator's control), may be logged by those servers, proxies, or observability tooling, and the endpoint accepts the callback from any source IP with no additional secret, token, or signature. This is lower likelihood than a fully unauthenticated exploit against arbitrary users (since a valid pending UUID is required), matching the Medium-severity characterization the judges gave the original GoGoPool finding (mistake/leak-dependent, not directly exploitable without extra information).

### Recommendation
Bind the resume callback to proof of ownership of the specific task, e.g., include a per-task HMAC/secret (similar to the External Initiator's `OutgoingToken`/`OutgoingSecret` pattern already used in `core/bridges/external_initiator.go`) that must be presented alongside the `runID`, and validate that the resuming request corresponds to the specific bridge task that was dispatched, not merely that some run exists in `running`/`suspended` state.

### Proof of Concept
1. Create a job containing a bridge task; the pipeline suspends the run and dispatches a request to the external bridge containing a callback URL `PATCH /v2/resume/<taskUUID>`.
2. An attacker who obtains `<taskUUID>` (e.g., from bridge-side logs) sends their own unauthenticated `PATCH /v2/resume/<taskUUID>` with a forged JSON body before the legitimate bridge responds:
```
curl -X PATCH https://node/v2/resume/<taskUUID> -d '{"error":null,"value":"attacker-controlled"}'
```
3. `PipelineRunsController.Resume` (`core/web/pipeline_runs_controller.go:133-159`) processes this with no auth check, and `orm.UpdateTaskRunResult` (`core/services/pipeline/orm.go:271-302`) updates the task/run purely by UUID match, completing the pipeline run with attacker-supplied data.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)

func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
