### Title
Unsafe `int64`→`uint` cast in gateway `web_api_trigger` staleness check allows freshness-validation bypass - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` validates the freshness of an incoming `web_api_trigger` message by comparing `time.Now().Unix()` against the client-supplied `Timestamp` field, but performs the comparison using an unsafe cast from the signed `int64` payload field to `uint`. A caller can supply a negative timestamp, which wraps to a huge unsigned value and defeats the staleness check entirely — the same class of bug as the reported `uint120` truncation in `IndexPool.mint`, where a value chosen by the caller is cast to a narrower/different-signedness type and used unchecked in a security-relevant comparison.

### Finding Description
`HandleLegacyUserMessage` is the entry point that processes user-submitted messages on the internet-facing gateway for the `web_api_trigger` method, before any sender allowlist/rate-limiting is applied (see the `// TODO: apply allowlist and rate-limiting here` comment immediately following the staleness check): [1](#0-0) 

The payload is unmarshaled into `webapicap.TriggerRequestPayload`, whose `Timestamp` field is declared as a signed `int64` fully controlled by the caller: [2](#0-1) 

The freshness check is:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    // reject as stale
}
``` [3](#0-2) 

`payload.Timestamp` is cast directly from `int64` to `uint` with no bounds validation. If an attacker sets `Timestamp` to a negative number (e.g., `-1`), `uint(payload.Timestamp)` wraps around to a value near `math.MaxUint64` (or `MaxUint32` on 32-bit builds). The left-hand side (`uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`) can never exceed this wrapped value, so the "stale message" branch is never taken — the freshness check is unconditionally bypassed for any negative timestamp.

### Impact Explanation
The staleness check exists specifically to prevent old/replayed `web_api_trigger` payloads from being forwarded to DON member nodes: `h.don.SendToNode(ctx, member.Address, req)` for every DON member. By defeating this check with a crafted negative timestamp, an unauthenticated caller of the gateway's public message-handling path can force forwarding of stale/forged trigger payloads to all DON nodes, which the code's own comment acknowledges is not yet allowlist- or rate-limit-protected at this stage. This can be used to force execution/re-execution of a workflow trigger with an event the freshness gate was designed to reject, undermining the anti-replay guarantee for the web API trigger capability.

### Likelihood Explanation
High from a reachability standpoint: the vulnerable field (`Timestamp`) is fully attacker-controlled JSON input on a path reached before allowlist/rate-limiting enforcement, and crafting a negative integer in JSON requires no special privilege.

### Recommendation
Avoid the signed-to-unsigned reinterpretation entirely. Perform the comparison in a signed/monotonic type consistently (e.g., compare `time.Now().Unix()` and `payload.Timestamp` as `int64`), and explicitly reject non-positive or otherwise out-of-range timestamps before use:
```go
now := time.Now().Unix()
if payload.Timestamp <= 0 || now-int64(h.config.MaxAllowedMessageAgeSec) > payload.Timestamp {
    // reject as stale/invalid
}
```
More generally, use `math/bits`-safe or `SafeCast`-style helpers (bounds-checked conversions) anywhere a caller-controlled numeric field crosses a type/signedness boundary before being used in a validation comparison.

### Proof of Concept
1. Submit a `web_api_trigger` message to the gateway's legacy user-message path with a JSON body whose `payload.timestamp` is set to `-1`.
2. `uint(payload.Timestamp)` evaluates to `18446744073709551615` (on 64-bit) — far larger than `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`.
3. The `stale message` branch at [4](#0-3)  is never entered, so the message is accepted and forwarded to every DON member via `don.SendToNode`, even though a negative/garbage timestamp should be rejected outright.
