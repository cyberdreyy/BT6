### Title
Unfunded instant-withdraw receipts can be claimed in full, draining strategy-held deposits reserved for the borrower and other claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The directory-traversal analog is a claim path that lets a user reach funds outside their entitled scope. In `IdleCreditVault.claimInstantWithdrawRequest`, the full aggregate receipt `instantWithdrawsRequests[_user]` is burned and paid out, while `pendingInstantWithdraws` — the unfunded remainder that was never collected via `collectInstantWithdrawFunds` — is never checked. A user whose instant receipt was only partially funded (or not funded at all) at `startEpoch` can still claim the entire amount, paid out of unrelated underlyings sitting in the strategy (epoch deposits awaiting `sendInterestAndDeposits`, or other users' funded claims).

### Finding Description
`requestInstantWithdraw` mints a 1:1 strategy-token receipt to the user and accrues `instantWithdrawsRequests[_user]` plus the global `pendingInstantWithdraws` (lines 356–375). Funding is delivered lazily: `collectInstantWithdrawFunds(_amount)` reduces `pendingInstantWithdraws` by whatever amount the CDO actually transfers (lines 398–403). The contract's own comments confirm partial funding is a real state: "`pendingInstantWithdraws` is only the unfunded remainder. If it is lower than the current-epoch claim basis, the difference is already-held underlying reserved for those claims" (`_defaultPrefundedInstantReserve`, lines 716–722, and `defaultPendingClaimBasis`, lines 644–649).

The claim path, however, ignores funding entirely:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);   // lines 387-392
```

`_transferFundedClaim` only guards the `defaultRecoveryReserve` isolation (lines 897–907); it does not verify that `amount <= instantWithdrawsRequests[_user] - (unfunded share attributable to _user)`. There is no per-epoch funding check on the instant claim — the user "traverses" past their funded balance into the strategy's general token balance.

### Impact Explanation
If `collectInstantWithdrawFunds` transfers less than `instantWithdrawClaimsByEpoch[currentEpoch]` (borrower under-funds an epoch start, or the CDO's available liquidity only covers part of the instant queue), the first user(s) to call `claimWithdrawRequest`/`claimInstantWithdrawRequest` via `IdleCDOEpochVariant` receive full payouts sourced from strategy-held underlyings that belong to other claimants or were deposited for onward lending. Concretely:

- Underlying held by the strategy includes buffer-period deposits (accumulated via `deposit`, lines 596–617) that are earmarked for `sendInterestAndDeposits` to the borrower/CDO.
- An instant claimant whose receipt was never funded can claim it anyway, converting an unfunded IOU into real tokens — direct theft from remaining instant claimants and active LPs, and insolvency for the last claimers (their `_burn` succeeds but the `safeTransfer` reverts, permanently freezing the residual claims).

Quantified loss: up to `pendingInstantWithdraws` (the unfunded remainder) paid out to earlier claimants, bounded by the strategy's underlying balance.

### Likelihood Explanation
Requires an epoch to start while the instant queue is only partially funded. This is not an exotic state — the code explicitly accounts for it (`_defaultPrefundedInstantReserve`, `defaultInstantWithdrawsFinalized`). An unprivileged attacker only needs to hold an instant-withdraw receipt in that epoch and call `claimInstantWithdrawRequest()` through the CDO before the queue is topped up. No privileged-role misbehavior is needed; honest sequencing of `startEpoch` with limited CDO liquidity suffices.

### Recommendation
In `claimInstantWithdrawRequest`, cap the claimable amount by the user's funded share: track per-user (or per-epoch) funded basis when `collectInstantWithdrawFunds` runs, or revert claims while `instantWithdrawsRequests[_user]` exceeds the funded portion for that user's receipt epochs. Alternatively, only burn/pay receipts for epochs that were fully collected, mirroring the per-epoch accounting already used for normal requests (`withdrawsRequestsByEpoch`).

```solidity
// Foundry fork PoC sketch (IdleCreditVault.t.sol harness)
// 1. Lender deposits during buffer, epoch starts.
// 2. User calls cdoEpoch.requestInstantWithdraw(amount) -> receipt minted,

// 3. startEpoch runs; CDO calls collectInstantWithdrawFunds(amount / 2)
//    (only partial liquidity available). pendingInstantWithdraws = amount / 2.
// 4. Strategy holds D underlying from buffer deposits.
// 5. User calls cdoEpoch.claimInstantWithdrawRequest():
//    _burn(user, amount); _transferFundedClaim(user, amount)
//    -> user receives full `amount`, half of it taken from deposits D.
// 6. Later instant claimants revert on safeTransfer: funds permanently frozen;
//    CDO is short `amount/2` of deposit principal -> insolvency.

assertLt(underlying.balanceOf(address(creditVault)), D);
```

Note: I was unable to fully verify the exact partial-funding path inside `IdleCDOEpochVariant.startEpoch`/`collectInstantWithdrawFunds` call site (the grep output was truncated before I could read the funding logic). If the CDO is hard-coded to always collect exactly `pendingInstantWithdraws` or revert when it cannot, the unfunded-claim window would be limited to borrower-default-adjacent sequencing and the severity would drop. The claim path's missing funded-basis check is confirmed in the strategy code itself.
