This confirms the wiki's own documentation: `AccountType` typing (`get_account_type`, `account_id_ref.rs:203`) is exhaustive and mutually exclusive — **EthImplicit** (`0x` + 40 hex), **NearImplicit** (64 hex), **NearDeterministic** (`0s` + 40 hex), and **Named** (everything else) are determined purely by the string shape, and a `Named` account can never also satisfy the `0x`+40-hex EthImplicit shape since these are checked in priority order over disjoint character-pattern classes. [1](#0-0) 

Critically, `AccountType` is derived solely from the account-id string, independent of creation history. Any account whose name is literally `0x` + 40 lowercase hex characters is unconditionally typed `EthImplicitAccount` by `get_account_type`, regardless of whether it was created via implicit-transfer or via `action_create_account` (named-account creation path). But `action_create_account` only allows creating sub-accounts of the predecessor or top-level accounts via the registrar, and crucially the account-id validity rules for a "named" account still permit `0x...` hex-looking strings syntactically — however `get_account_type` will classify *any* string matching the `0x`+40-hex pattern as `EthImplicitAccount`, not `NamedAccount`, no matter how it was created. [2](#0-1) 

So the real question is: can `action_create_account` (the named-account creation path) actually create an account whose id is `0x` + 40 hex chars, and if so, would `AccountContract::Local` end up on it, then have `RuntimeContractIdentifier::resolve` treat it as `EthImplicitAccount` for the `LegacyEthWallet::resolve` check?

pub(crate) fn action_transfer(account: &mut Account, deposit: Balance) -> Result<(), StorageError> {
    account.set_amount(account.amount().checked_add(deposit).ok_or_else(|| {
        StorageError::StorageInconsistentState("Account balance integer overflow".to_string())
    })?);
    Ok(())
}
