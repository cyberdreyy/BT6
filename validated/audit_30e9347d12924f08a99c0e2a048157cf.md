### Title
Unbounded-allocation DoS via crafted `Vec<u8>` length prefix in `parse_bpf_upgradeable_loader` bincode deserialization - ([File: transaction-status/src/parse_bpf_loader.rs])

### Summary
`parse_bpf_upgradeable_loader` deserializes `instruction.data` with plain `bincode::deserialize`, which has no size limit and will pre-allocate a `Vec<u8>` sized by an attacker-controlled length prefix before checking it against the actual remaining bytes in the buffer. A single `getTransaction(encoding=jsonParsed)` call for a previously-landed transaction containing a crafted `Write`/`DeployWithMaxDataLen`-shaped instruction can trigger an allocation-failure abort or capacity-overflow panic in the validator's RPC-serving process.

Every other place in this codebase that deserializes untrusted instruction bytes uses `solana_bincode::limited_deserialize(data, PACKET_DATA_SIZE)`, e.g. the actual bpf_loader_upgradeable processor: [3](#0-2) 
as well as `cost_model.rs`, `system_processor.rs`, `vote_parser.rs`, and `cli-output/src/display.rs`. `limited_deserialize` bounds allocation via a configured `Limit`, causing bincode to fail fast with a size-limit error instead of allocating based on an untrusted length field. `transaction-status/src/parse_bpf_loader.rs` is the outlier that uses raw, unbounded `bincode::deserialize` for both `parse_bpf_loader` (legacy `LoaderInstruction`) and `parse_bpf_upgradeable_loader` (`UpgradeableLoaderInstruction`).

`UpgradeableLoaderInstruction::Write { offset: u32, bytes: Vec<u8> }` is serialized by bincode as: 4-byte enum discriminant + 4-byte `offset` + 8-byte `Vec<u8>` length prefix + payload bytes. With bincode's unbounded default options, the deserializer reads the 8-byte length field verbatim and attempts `Vec::with_capacity(len)` for that many `u8` elements before validating that the buffer actually contains that many remaining bytes. An attacker can set that 8-byte field to a value close to `usize::MAX` (or any very large value) while providing only a few real trailing bytes — the whole payload still fits comfortably within the ~1232-byte transaction/packet size limit (`PACKET_DATA_SIZE`), since only ~16-20 bytes are needed to encode the malicious header.

Exploit flow:
1. Attacker submits (as an ordinary client) a transaction whose instruction targets the BPF Upgradeable Loader program with a `Write`-shaped `instruction.data` containing an inflated `Vec<u8>` length prefix and truncated payload. The transaction can even fail at runtime (the program's own `limited_deserialize` call will reject it), but the raw `CompiledInstruction` bytes are still recorded in the block/blockstore because fees are charged and the transaction is included regardless of instruction-level failure.
2. Any single unprivileged client later calls `getTransaction` (or `getBlock`) with `encoding=jsonParsed` for that transaction.
3. RPC encoding path calls `parse_bpf_upgradeable_loader`, which calls unbounded `bincode::deserialize(&instruction.data)`.
4. bincode reads the inflated length field and calls `Vec::with_capacity(len)` for the `bytes` field before verifying `len` against remaining buffer size. Depending on the magnitude chosen, this either (a) exceeds the allocator's `isize::MAX` capacity check and panics with "capacity overflow", or (b) triggers a real allocation request that, on failure, calls Rust's `handle_alloc_error`, which unconditionally aborts the process (this abort path is not catchable via `catch_unwind`).
5. Because the RPC service runs in-process with the validator (not a separate sandboxed process), this can crash the entire validator from one low-rate, single-client RPC call.

This bypasses the fact that `instruction.data` itself is already bounded to `PACKET_DATA_SIZE` by transaction sanitization — the bound applies to the outer byte buffer, not to any length value encoded *within* that buffer, and unbounded `bincode::deserialize` does not check the two against each other before allocating.

### Impact Explanation
A single `getTransaction(encoding=jsonParsed)` RPC call from one unprivileged client can cause a validator-process crash (allocator abort) or unbounded memory-allocation attempt, matching the "real validator-process crash from one request" / "unbounded cost for a single low-rate call" bounty categories. The prerequisite malicious transaction can itself be submitted by an unprivileged client (it doesn't need to succeed at runtime, only to land in a confirmed block), so no privileged access is required anywhere in the chain.

### Likelihood Explanation
Feasible and repeatable with modest effort: crafting the malicious instruction bytes is deterministic and requires no special resources beyond submitting one ordinary transaction and issuing one subsequent `getTransaction` call at normal RPC rate limits (well under one call per `CLUSTER_SLOT_TIME_TARGET / 2`). It relies purely on an inconsistency between this parsing module and every other instruction-deserialization call site in the codebase, which is a stable, code-level condition rather than a timing race.

### Recommendation
Replace the unbounded `bincode::deserialize(&instruction.data)` calls in `parse_bpf_loader` and `parse_bpf_upgradeable_loader` (`transaction-status/src/parse_bpf_loader.rs`) with `solana_bincode::limited_deserialize(&instruction.data, solana_packet::PACKET_DATA_SIZE as u64)`, consistent with every other instruction-data deserialization site in the codebase (`programs/bpf_loader/src/lib.rs`, `cost-model/src/cost_model.rs`, `vote/src/vote_parser.rs`, `cli-output/src/display.rs`). This causes bincode to enforce a size limit against declared length prefixes before allocating, returning a fast `Err` instead of attempting an oversized allocation.

### Proof of Concept
```rust
// transaction-status/src/parse_bpf_loader.rs (test module)
#[test]
fn test_parse_bpf_upgradeable_loader_write_inflated_length_prefix_is_bounded() {
    use solana_message::compiled_instruction::CompiledInstruction;

    // UpgradeableLoaderInstruction discriminant for Write is variant index 1 (u32 LE).
    let mut data = vec![];
    data.extend_from_slice(&1u32.to_le_bytes());       // Write discriminant
    data.extend_from_slice(&0u32.to_le_bytes());        // offset
    data.extend_from_slice(&u64::MAX.to_le_bytes());    // inflated Vec<u8> length prefix
    data.extend_from_slice(&[0xAA, 0xBB]);              // truncated payload (only 2 real bytes)

    let instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![0, 1],
        data,
    };
    let account_keys = solana_message::AccountKeys::new(
        &[solana_pubkey::Pubkey::new_unique(), solana_pubkey::Pubkey::new_unique()],
        None,
    );

    // Expected (fixed) behavior: returns Err quickly, no huge allocation attempted.
    // Current (vulnerable) behavior: bincode attempts Vec::with_capacity(u64::MAX),
    // causing a capacity-overflow panic or allocator abort before returning.
    let result = parse_bpf_upgradeable_loader(&instruction, &account_keys);
    assert!(result.is_err(), "must fail gracefully instead of aborting/panicking");
}
```
Run under a memory-limited harness (e.g. `ulimit -v` or a custom allocator that panics on requests above a threshold) to assert peak allocation stays bounded by `instruction.data.len()` (a few dozen bytes) rather than by the attacker-supplied `u64::MAX` value, and that the call returns `Err` rather than aborting the process.
