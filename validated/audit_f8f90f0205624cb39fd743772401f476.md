### Title
External Initiator can bypass job-binding restriction to trigger runs on arbitrary integer job IDs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` determines whether to allow the "integer job ID" run path by calling `auth.GetAuthenticatedUser(c)`, but `AuthenticateExternalInitiator` also populates `SessionUserKey` with a synthetic `UserRoleRun` user for every successfully authenticated EI. As a result, an EI credential holder is treated as `isUser == true` and can trigger `RunJobV2` on any integer job ID, without any check that the job is the one bound to that EI.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is reachable by three authentication methods (EI, token, session) via `auth.Authenticate` [5](#0-4) . When authenticated via `AuthenticateExternalInitiator`, the middleware sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` in addition to `SessionExternalInitiatorKey` [2](#0-1) . `RequiresRunRole` merely requires role != view, which the injected run-role user satisfies [3](#0-2) . Inside `Create`, the comment states "only users are allowed to run jobs using int IDs - EIs not allowed", but the actual check `_, isUser := auth.GetAuthenticatedUser(c)` cannot distinguish an EI-originated synthetic user from a real session/token user, because both populate the same `SessionUserKey` [4](#0-3) . Consequently an EI-authenticated request with an integer `:ID` reaches `prc.App.RunJobV2(ctx, jobID, nil)` with no verification that the job ID belongs to/was configured for that external initiator (there's no call to `GetAuthenticatedExternalInitiator` combined with a job-EI binding lookup in this path).

### Impact Explanation
An external initiator credential (a lower-privilege, narrowly-scoped credential meant only to trigger its own bound webhook job) can be used to trigger pipeline runs on any job identified by an arbitrary integer ID, not just the job it was provisioned for. This is an authorization/job-binding bypass — unauthorized triggering of job runs — matching the "unauthorized job run" bounty impact class, potentially causing unwanted on-chain transactions, fund movement, or resource exhaustion depending on the target job's tasks.

### Likelihood Explanation
Only a valid EI access key/secret is required (no admin/session/user credential needed). The request is a straightforward single POST with EI headers and an attacker-guessable-or-enumerable integer job ID. This is easily repeatable and requires no race conditions or special timing.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests authenticated as an external initiator from using the integer-job-ID path — check `auth.GetAuthenticatedExternalInitiator(c)` first and reject if present, rather than relying solely on `GetAuthenticatedUser`. Alternatively, differentiate the synthetic EI-injected user (e.g., a distinct marker/type) from real authenticated users so `isUser` truly reflects "authenticated as a human user," and additionally verify job-to-EI binding before calling `RunJobV2` for any EI-initiated request.

### Proof of Concept
1. Handler/integration test using `gin.Context` with `AuthenticateExternalInitiator` invoked with valid EI credentials for `ExternalInitiator A`, setting `SessionUserKey` and `SessionExternalInitiatorKey`.
2. Call `PipelineRunsController.Create` with `c.Param("ID")` set to an integer job ID that belongs to a different job not associated with `ExternalInitiator A`.
3. Assert current behavior: `RunJobV2` is invoked and a run is created (200 response) — demonstrating the bypass.
4. Expected fixed behavior: request should be rejected with `http.StatusUnprocessableEntity` (or 403) because EI is not authorized for that job ID, verified via a job-EI binding check.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
