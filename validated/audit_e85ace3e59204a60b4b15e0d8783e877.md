### Title
Missing future-timestamp validation in gateway staleness check allows stale-message protection bypass - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The internet-facing gateway's legacy user-message handler validates message freshness with a single unsigned-integer comparison that only rejects messages that are *too old*. It never validates that the client-supplied `payload.Timestamp` is not in the future relative to the gateway's clock, so an unprivileged HTTP caller can bypass the staleness protection by supplying an arbitrarily large (future) timestamp.

### Finding Description
`HandleLegacyUserMessage` decodes an untrusted JSON payload (`webapicap.TriggerRequestPayload`) coming directly from an external HTTP client through the gateway's public user-facing endpoint, then performs the staleness check: [1](#0-0) 

The check is:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
``` [2](#0-1) 

This is the same underlying bug class as the referenced Synthetix commit: an unsigned time-delta comparison that assumes the externally supplied timestamp is always ≤ the local/chain clock. The Synthetix fix addressed underflow when `block.timestamp - priceTimestamp` was computed with `priceTimestamp` in the future; here the analogous flaw is that the gateway computes a lower bound (`now - MaxAllowedMessageAgeSec`) and only checks that the *supplied* timestamp is not below it — there is no upper-bound check (`payload.Timestamp <= now`). A caller who sets `payload.Timestamp` far in the future trivially satisfies `threshold > payload.Timestamp == false` and the message is treated as fresh regardless of its true age or validity, then forwarded to every DON member: [3](#0-2) 

The handler config (`MaxAllowedMessageAgeSec`, `HandlerConfig`) is node/gateway operator configuration, not attacker-controlled, but `payload.Timestamp` originates entirely from the external, unprivileged request body: [4](#0-3) 

I could not fully confirm the exact Go type (`int64` vs `uint64`) of the `Timestamp` field in `webapicap.TriggerRequestPayload` from the indexed code, since the generated file `core/capabilities/webapi/webapicap/event_trigger_generated.go` was not fully retrievable in this session — this affects whether a negative timestamp value could also trigger an actual unsigned-integer wraparound (true underflow) in `uint(payload.Timestamp)`, in addition to the confirmed future-timestamp bypass. This should be verified directly in a full checkout.

### Impact Explanation
This staleness check is the gateway's only defense against replay/anti-freshness abuse of `web_api_trigger` messages before they are broadcast to all DON members and a callback is registered for the response (`savedCallbacks`). Bypassing it lets an unprivileged internet client submit messages that are always considered "fresh" irrespective of actual submission time, undermining the intended anti-replay/staleness guarantee for this internet-facing gateway path and allowing bulk/rapid message injection to DON nodes.

### Likelihood Explanation
High reachability: the vulnerable code path is directly invoked by `HandleLegacyUserMessage`, which processes untrusted, unauthenticated (beyond the gateway's own coarse validation) requests arriving over the public gateway HTTP interface (`core/services/gateway/gateway.go` `ProcessRequest` → handler dispatch). Setting an arbitrary future value for `payload.Timestamp` in the JSON body requires no special privilege.

### Recommendation
Add a symmetric upper-bound check, e.g. reject when `payload.Timestamp > uint(time.Now().Unix())` (optionally with a small clock-skew allowance), in addition to the existing lower-bound staleness check, and confirm/normalize the type of `Timestamp` to avoid any unsigned wraparound when negative or out-of-range values are supplied.

### Proof of Concept
1. Send a `web_api_trigger` request to the gateway's public HTTP endpoint with `payload.Timestamp` set to, e.g., `9999999999` (far future).
2. The check `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` evaluates false since the RHS is much larger than the threshold, so the "stale message" branch is skipped.
3. The message passes staleness validation and is forwarded to all DON members via `don.SendToNode`, despite carrying an invalid/future timestamp that should have failed a proper freshness check.
