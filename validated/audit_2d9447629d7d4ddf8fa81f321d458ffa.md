### Title
Unchecked `new_authority` in account migration permanently locks funds if set to the zero pubkey - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The Connext report flags `xcall()` for missing zero-address checks on `recovery`/`agent`, warning that a zero `agent` can leave funds "locked forever." The direct analog in marginfi-v2 is the `new_authority` account in the account-migration instructions `transfer_to_new_account` and `transfer_to_new_account_pda`, which is explicitly annotated `/// CHECK: WARN: New authority is completely unchecked` and is never validated against `Pubkey::default()`.

### Finding Description
`TransferToNewAccount` and `TransferToNewAccountPda` accept an arbitrary `new_authority: UncheckedAccount<'info>` with no on-chain validation: [1](#0-0) 

The value is written directly into the newly created `MarginfiAccount.authority` field via `initialize_migrated_account`, with no check that it is non-zero: [2](#0-1) [3](#0-2) 

The same unchecked pattern exists in the PDA variant: [4](#0-3) [5](#0-4) 

Once migration completes, `finalize_migrated_old_account` disables the old account and marks it migrated, making the migration effectively irreversible and permanently redirecting the position to the new account: [6](#0-5) 

If `new_authority` is `Pubkey::default()` (all-zero), the resulting `MarginfiAccount.authority` field is the zero pubkey. `is_signer_authorized` gates control of the account on the `authority` field matching the transaction signer: [7](#0-6) 

Since no valid Solana keypair corresponds to the all-zero public key, no signer can ever satisfy `has_one = authority` / `is_signer_authorized` for the migrated account, permanently freezing every balance (deposits and open positions) it holds — this is the "agent == 0 -> funds locked forever" analog called out in the Connext report for `xcall()`.

### Impact Explanation
This is a durable, financial-impact freeze of user funds: any deposits, collateral, or liabilities transferred into the newly created account become permanently inaccessible, with no recovery path in the contract (the old account is disabled and cannot be un-migrated). This matches the report's "funds locked forever" class of issue.

### Likelihood Explanation
The action is entirely self-triggered by the unprivileged account authority calling `transfer_to_new_account`/`transfer_to_new_account_pda` and passing `new_authority = Pubkey::default()` (or any account with an untrusted keypair), either by mistake (client-side bug, copy-paste error) or by an attacker socially engineering / phishing a user's front-end into submitting a zero/garbage authority. There is no signer requirement on `new_authority` itself, so it is trivial to pass any pubkey, including the zero address, without additional privileges.

### Recommendation
Add an explicit check in `transfer_to_new_account` and `transfer_to_new_account_pda` that `ctx.accounts.new_authority.key() != Pubkey::default()` (and consider requiring it differ from the system program / disallowing known-unspendable addresses), returning a descriptive error (e.g., `MarginfiError::InvalidAuthority`) before `initialize_migrated_account` is called and before the old account is disabled.

### Proof of Concept
1. User (or attacker-controlled front-end) calls `transfer_to_new_account` (or `transfer_to_new_account_pda`) supplying `new_authority = Pubkey::default()`.
2. `initialize_migrated_account` sets `new_account.authority = Pubkey::default()`.
3. `finalize_migrated_old_account` disables the old account (`ACCOUNT_DISABLED` flag) and sets `migrated_to = new_account_key`, making the old account permanently unusable per `can_be_closed`/existing account-state checks.
4. Any subsequent instruction on the new account that requires `is_signer_authorized`/`has_one = authority` (deposits, withdrawals, repay, close balance, etc.) can never be satisfied because no signer can produce the zero pubkey — the account's balances and collateral are permanently locked.

*Note*: I could not find an existing test in `tests/specs/basic/12_transfer_account.spec.ts` that exercises a zero-address `new_authority`, and `SECURITY.md` does not list this scenario as an explicitly out-of-scope class (it only excludes generic "best practice" and privileged-access issues, which do not apply here since the caller is an unprivileged, ordinary account authority).

fn initialize_migrated_account(

    current_timestamp: u64,
    old_account_key: Pubkey,

    new_account.indexer_flags = old_account.indexer_flags;
    new_account.sync_indexer_flags();
}

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
