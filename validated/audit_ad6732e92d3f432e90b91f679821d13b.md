### Title
Unauthenticated `base_setMeteringEnabled`/`base_setMeteringInformation`/`base_clearMeteringInformation` RPC lets any client disable or falsify block-builder resource metering - (File: `crates/builder/metering/src/extension.rs`)

### Summary
The rclone advisory's root cause is a mutating administrative RPC method that is exposed **without** the same authorization gate applied to sibling privileged methods, letting an unauthenticated caller flip a security-relevant runtime flag and defeat protections meant for other operations. The Base builder exhibits the same pattern: `MeteringStoreExtension` registers the `base_setMeteringEnabled`, `base_setMeteringInformation`, and `base_clearMeteringInformation` methods via `ctx.modules.add_or_replace_configured(...)`, with **no `RethRpcModule` gate at all**, while the sibling privileged mutation API in the same RPC-extension family (`AdminTxPoolApiImpl`) is explicitly gated behind `RethRpcModule::Admin` in the same crate group. [1](#0-0) [2](#0-1) 

### Finding Description
`BaseApiExt` is declared under the public `base` RPC namespace (not `admin`): [3](#0-2) 

Its handler mutates shared, process-wide state with no caller authentication or namespace check: [4](#0-3) 

The extension wiring adds this module with `add_or_replace_configured`, which — unlike `merge_if_module_configured(RethRpcModule::Admin, ...)` used for the builder's own `AdminTxPoolApi` — performs no privileged-namespace gating before installing the handler into the RPC server: [1](#0-0) 

Contrast this with the pattern the codebase otherwise follows for privileged mutating RPC in the same execution/builder RPC surface, where admin-only operations are conditioned on the `admin` namespace being explicitly enabled: [5](#0-4) [6](#0-5) 

This is structurally the same defect class as the rclone `options/set` bug: a state-mutating endpoint that controls a security/resource-limiting mechanism is reachable through the normal, non-privileged namespace, bypassing the authorization boundary that protects equivalent-risk operations elsewhere in the same RPC server.

### Impact Explanation
`base_setMeteringEnabled(false)` lets any client with network access to the builder's RPC endpoint globally disable resource metering used by the block builder's DA/gas/resource-limiting pipeline (`SharedMeteringProvider` / `MeteringStore`), and `base_setMeteringInformation`/`base_clearMeteringInformation` let a caller inject falsified metering data for arbitrary transaction hashes or wipe the store entirely. Because this metering data feeds the builder's transaction/bundle resource accounting (`base_meterBundle`, block metering) used for block-building and resource-limiting decisions, an anonymous caller can defeat the metering-based resource protection, enabling inclusion of unexpectedly resource-heavy transactions/bundles that the metering system was designed to catch, risking block-building slowdowns, builder resource exhaustion, or degraded block production. This maps to the allowed "block building and resource metering" category.

### Likelihood Explanation
Reachability depends on whether the builder's HTTP/WS RPC listener (where `MeteringStoreExtension` is installed via `runner.install_ext::<MeteringStoreExtension>` in `bin/builder/src/main.rs`) is exposed beyond a private network in a given deployment. Whether this endpoint is intended to be public-facing or restricted like the `admin`/`opp2p` RPCs elsewhere in the codebase (which carry explicit "Security Model: internal control-plane, never expose it publicly" documentation) could not be confirmed from available files/index — no equivalent security-model note was found for the builder's `base` namespace or `MeteringStoreExt`. This uncertainty affects the practical likelihood but not the underlying authorization-boundary inconsistency, which is confirmed at the code level.

### Recommendation
Gate `MeteringStoreExt`'s mutating methods (`setMeteringEnabled`, `setMeteringInformation`, `clearMeteringInformation`) behind the same privileged-namespace check (e.g., `RethRpcModule::Admin`) used for `AdminTxPoolApiImpl`, or move them into the `admin` namespace so they require the `--rpc.enable-admin`-equivalent private-network control, and split any read-only metering RPC from the mutating operations.

### Proof of Concept
Against a builder node with the `MeteringStoreExtension` installed and its RPC HTTP endpoint reachable:
```bash
curl -sS -X POST http://<builder-rpc>:PORT \
  -H 'Content-Type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"base_setMeteringEnabled","params":[false]}'
```
No credentials are required; per [7](#0-6)  this immediately disables resource metering globally, and `base_clearMeteringInformation`/`base_setMeteringInformation` can likewise be called unauthenticated to erase or falsify the metering store.

#[async_trait]
impl BaseApiExtServer for MeteringStoreExt {
    async fn set_metering_information(
        &self,
        tx_hash: TxHash,
        metering: MeterBundleResponse,
    ) -> RpcResult<()> {
        self.store.insert(tx_hash, metering);
        Ok(())
    }

    async fn set_metering_enabled(&self, enabled: bool) -> RpcResult<()> {
        self.store.set_enabled(enabled);
        Ok(())
    }

    async fn clear_metering_information(&self) -> RpcResult<()> {
        info!(
            rpc_method = "base_clearMeteringInformation",
            "Clearing builder metering information"
        );
        self.store.clear();
        Ok(())
    }
