### Title
Unauthenticated request forwarding for service-routed JSON-RPC requests — no gateway-layer signature check and confidentialrelay handler performs none either - ([File: core/services/gateway/gateway.go])

### Summary
`gateway.ProcessRequest` only calls `msg.Validate()` (which enforces the signature check) on the legacy DON-ID branch; for service-based routing (`isLegacyRequest == false`), the raw `jsonrpc2.Request` is dispatched straight to `handlers.Handler.HandleJSONRPCUserMessage` with no gateway-level authentication. This is a documented design choice pushing auth into individual handlers, but at least one registered handler, `confidentialrelay`, implements no authentication check at all in that path.

### Finding Description
In `core/services/gateway/gateway.go`, `ProcessRequest` branches on `msg == nil || msg.Body.DonId == ""` to decide legacy vs. service-based routing: [1](#0-0) 
Only the legacy `else` branch invokes `msg.Validate()` (line 253), which performs the message-level signature verification. The service-routing branch resolves a handler from `g.serviceToMultiHandler[serviceName]` and later calls `h.HandleJSONRPCUserMessage(ctx, jsonRequest, callback)` directly with no gateway-side auth/signature check.

For the `confidentialrelay` handler, `HandleJSONRPCUserMessage` only validates `req.ID` length/non-emptiness and then immediately fans the raw request out to all DON member nodes with no signature/authorization check whatsoever: [2](#0-1) 

This contrasts with the `vault` handler, which performs its own authorization via `h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)` (backed by `vaultcap.Authorizer`/`AllowListBasedAuth`/JWT) before forwarding any privileged (non-`MethodPublicKeyGet`) request: [3](#0-2) 

An attacker can POST a JSON-RPC body (no `Body`/`DonId` fields, so `msg == nil`/`msg.Body.DonId == ""`) targeting the `confidentialrelay` service name configured in `cfg.Services`, with an arbitrary/empty `Auth`/no embedded signature, and the request is forwarded to DON nodes unauthenticated — relying entirely on downstream node/enclave-side signature verification of the *response*, not the incoming user request's authenticity/authorization.

### Impact Explanation
Requests reaching `confidentialrelay`'s `fanOutToNodes` are sent as-is to all DON members via `h.don.SendToNode`. Because there is no caller identity/authorization check at the gateway or handler layer for this service, any unauthenticated network client that can reach the gateway's user-facing HTTP port can trigger `MethodSecretsGet`/`MethodCapabilityExec` relay requests toward the DON, impersonating a legitimate caller and consuming DON node resources/rate-limit budget, and potentially obtaining responses intended to be gated behind authorization (depending on what the enclave itself checks). This matches Chainlink's "authentication bypass / request impersonation" bounty impact class since a fundamental caller-authentication step is missing at both gateway and handler layers for this specific service.

### Likelihood Explanation
No credentials are required; the only precondition is that the node operator has configured a `confidentialrelay` service under `cfg.Services` (the new-style default config format required by `NewGatewayFromConfig`, since it errors out if `cfg.Services`/`cfg.ShardedDONs` are empty). Exploitation only requires knowing/guessing the `serviceName` value and issuing a single unsigned JSON-RPC POST, making it trivially repeatable and requiring no privileged access.

### Recommendation
Add an explicit authentication/authorization check inside `confidentialrelay.handler.HandleJSONRPCUserMessage` (mirroring `vault`'s `requestProcessor.ProcessRequest`/`Authorizer` pattern) before any request is fanned out to DON nodes. Additionally, consider enforcing a baseline signature/format check for all service-routed JSON-RPC requests at the `gateway.ProcessRequest` layer (e.g., verifying `jsonRequest.Auth` structurally) so that authentication is not solely dependent on each handler remembering to implement it.

### Proof of Concept
1. Unit test in `core/services/gateway/handlers/confidentialrelay/handler_test.go`: construct a `jsonrpc.Request[json.RawMessage]` with `Method: MethodSecretsGet`, a valid `ID`, but empty/absent `Auth` field and no signature.
2. Call `handler.HandleJSONRPCUserMessage(ctx, req, callback)` directly (or via `gateway.ProcessRequest` with a service-routed request body lacking `Body`/`DonId`).
3. Assert: no error is returned, `h.don.SendToNode` (mocked) is invoked for every DON member, and the callback is not synchronously rejected with an authorization error — demonstrating the request reaches the DON without any signature/authorization check having been performed at the gateway or handler layer.
4. Contrast test: run the same unsigned request against `vault.handler.HandleJSONRPCUserMessage` for a non-`MethodPublicKeyGet` method and confirm it returns an authorization error (`"request not authorized: ..."`), proving the security gap is specific to handlers (like `confidentialrelay`) that omit their own auth check.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}
