### Title
Batch redeem solving (`_solveRequestsVault`) can be griefed by a single malicious/blacklisted receiver, DoSing all other users' pending deposit/redeem requests - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`_solveRequestsVault` iterates over an array of `RequestV2` items and, for un-expired redeem requests, calls `token.safeTransfer(request.receiver, ...)` directly instead of going through the fallback-protected `_transferWithFallback` helper used elsewhere in the same file. Any ordinary user can call the public `requestRedeem` function and set `receiver` to an address that reverts on token receipt (e.g., a token-blacklisted address for USDC/USDT, or a contract without proper handling), causing the whole batch call to revert whenever the solver includes that request, freezing settlement for every other request batched alongside it.

### Finding Description
`requestRedeem` is a fully public, `anyoneButVault`-gated function that lets any user create a redeem request with an arbitrary `receiver` address and no restriction preventing the receiver from being a griefing target (only `_requireValidReceiver`-style checks apply to deposit receiver approvals, not to redeem receiver's ability to accept tokens): [1](#0-0) 

When a solver later batches multiple pending requests together via `solveRequestsVault` → `_solveRequestsVault`, each redeem request is processed with a direct, unprotected transfer to `request.receiver`: [2](#0-1) [3](#0-2) 

Notably, the expired-request branches of these same functions use `_transferWithFallback`, which falls back to the original requester on transfer failure: [4](#0-3) 

But the "happy path" (un-expired, solved) redeem branches skip this protection and call `token.safeTransfer` directly, so a single reverting receiver among the batch causes the entire `_solveRequestsVault` call — and therefore all other users' requests batched in the same transaction — to revert: [5](#0-4) 

This is the same root cause as the referenced Gitcoin `DonationVotingMerkleDistributionBaseStrategy._distribute` finding: a loop over user-controlled/attacker-influenced recipients performs an unguarded push-transfer, so one bad recipient blocks processing for everyone else in the batch.

### Impact Explanation
Because the solver (an authorized but non-privileged-in-request-creation role) has no way to know in advance which receivers will revert, an attacker who is blacklisted by a stablecoin issuer (or deploys a reverting receiver contract) can repeatedly submit `requestRedeem` calls naming themselves (or their contract) as `receiver`. Every batch that includes this request will revert, delaying settlement of legitimate users' deposit/redeem requests indefinitely (until the solver identifies and excludes the poisoned request, which requires off-chain detection and manual exclusion). This is a temporary freeze of user funds/yield across the batch, matching Immunefi Medium severity for temporary fund/yield freezing.

### Likelihood Explanation
The attack requires no privileged role and no special preconditions beyond calling the already-public `requestRedeem` (or `requestDeposit`, though deposit routes through `enter`/mint which is less likely to revert) with a receiver address that reverts on `safeTransfer`. This is trivially reproducible with a self-controlled contract that reverts in its fallback/receive-equivalent ERC20 hook path (e.g., a contract with no token approval path or that reverts unconditionally when receiving tokens if the token has hooks, or more directly for tokens like USDC/USDT, an already-blacklisted address). The solver batches multiple pending requests together as a normal operational pattern to save gas, making inclusion of a poisoned request likely without additional safeguards.

### Recommendation
Route the "solved" branch transfers in `_solveDepositVaultAutoPrice`, `_solveDepositVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, and `_solveRedeemVaultFixedPrice` through the same `_transferWithFallback` mechanism (or a try/catch with per-request failure event and hash-restore/skip) that is already used in the expired branches, so that a single failing receiver cannot revert the entire batch and other requests in the same call continue to be processed.

### Proof of Concept
1. Deploy `ProvisionerV2` with a mock ERC20 `token` and `MultiDepositorVault`; enable async redeem for `token`.
2. User A (attacker) calls `requestRedeem(token, unitsIn, minTokensOut, 0, deadline, maxPriceAge, true, attackerReceiverContract)`, where `attackerReceiverContract` is a contract whose fallback (or token hook, depending on token type) unconditionally reverts on receiving `token`.
3. User B (honest) calls `requestRedeem(token, unitsIn2, minTokensOut2, 0, deadline2, maxPriceAge2, true, userB)`.
4. Authorized solver calls `solveRequestsVault(token, [requestA, requestB], "", "")`.
5. Assert the whole transaction reverts because `_solveRedeemVaultFixedPrice`'s `token.safeTransfer(attackerReceiverContract, ...)` reverts, and confirm that removing requestA from the batch allows requestB to settle successfully — demonstrating that a single poisoned receiver blocks unrelated users' requests from being solved in the same batch.

    function _solveRequestsVault(IERC20 token, RequestV2[] calldata requests) internal {
        // Requirements: vault is not paused in the priceAndFeeCalculator
        require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());

        // Interactions: get price age
        uint256 priceAge = block.timestamp - PRICE_FEE_CALCULATOR.getVaultPriceTimestamp(MULTI_DEPOSITOR_VAULT);

        uint256 solverTip;
        RequestV2 calldata request;

        uint256 length = requests.length;
        TokenDetailsV2 memory tokenDetails = tokensDetails[token];
        bool depositsExist;
        for (uint256 i = 0; i < length; i++) {
            request = requests[i];
            if (_isRequestTypeDeposit(request.requestType)) {
                // Requirements: async deposit is enabled
                if (!tokenDetails.asyncDepositEnabled) {
                    // Log async deposit disabled event
                    emit AsyncDepositDisabled(i);
                    continue;
                }

                if (!depositsExist) {
                    depositsExist = true;
                    token.forceApprove(MULTI_DEPOSITOR_VAULT, type(uint256).max);
                }

                if (_isRequestTypeAutoPrice(request.requestType)) {
                    // Requirements + Effects + Interactions: solve auto price deposit
                    solverTip += _solveDepositVaultAutoPrice(
                        token, tokenDetails.asyncDepositMultiplier, request, priceAge, i
                    );
                } else {
                    // Requirements + Effects + Interactions: solve fixed price deposit
                    solverTip += _solveDepositVaultFixedPrice(
                        token, tokenDetails.asyncDepositMultiplier, request, priceAge, i
                    );
                }
            } else {
                // Requirements: async redeem is enabled
                if (!tokenDetails.asyncRedeemEnabled) {
                    // Log async redeem disabled event
                    emit AsyncRedeemDisabled(i);
                    continue;
                }

                if (_isRequestTypeAutoPrice(request.requestType)) {
                    // Requirements + Effects + Interactions: solve auto price redeem
                    solverTip += _solveRedeemVaultAutoPrice(
                        token, tokenDetails.asyncRedeemMultiplier, request, priceAge, i
                    );
                } else {
                    // Requirements + Effects + Interactions: solve fixed price redeem
                    solverTip += _solveRedeemVaultFixedPrice(
                        token, tokenDetails.asyncRedeemMultiplier, request, priceAge, i
                    );
                }
            }
        }

    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
