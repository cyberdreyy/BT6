### Title
Unauthenticated MessageId flood causes eviction of victim's pending callback via oldest-first pruning - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` inserts every incoming request into the shared `savedCallbacks` map keyed by attacker-controlled `MessageId`, with no allowlist or per-caller quota gating admission (explicitly marked `// TODO: apply allowlist and rate-limiting here`). `pruneCallbacks` evicts entries strictly oldest-first once the map exceeds `MaxSavedCallbacks`, without checking whether an "old" entry is still within `CallbackMaxAgeSec`, so a high-volume unauthenticated flood can evict a legitimate victim's still-pending callback before the DON responds.

### Finding Description
In `HandleLegacyUserMessage` [1](#0-0) , every syntactically valid signed message (only signature/schema/timestamp checks apply, at lines 345-409) is admitted and stored in `h.savedCallbacks[msg.Body.MessageId]` with no allowlist or per-sender quota — the code explicitly notes this gap: [2](#0-1) . `MessageId` is attacker-controlled/attacker-generated, so an attacker can create unlimited distinct entries.

`pruneCallbacks`, run every `CallbackPruneIntervalSec` (default 30s), first removes expired entries by `createdAt` vs `CallbackMaxAgeSec`, then — if the map is still over `MaxSavedCallbacks` (default 20000) — sorts all *remaining, unexpired* entries by `createdAt` and deletes the oldest half regardless of whether they are still within `CallbackMaxAgeSec`: [3](#0-2) . There is no distinction in the eviction step between "old and about to expire naturally" and "old but still validly pending a DON response." If an attacker inserts more than `MaxSavedCallbacks` distinct fresh entries within one prune interval, a victim's earlier (but still unexpired) callback — created slightly before the flood — sorts into the oldest half and gets deleted by `delete(h.savedCallbacks, e.id)` at line 331, silently discarding the victim's callback state. When the DON later replies for that `MessageId` via `handleWebAPITriggerMessage`, the lookup at line 150 will miss (`found == false`), and the response is silently dropped at line 161 — no error is surfaced to the victim.

No middleware upstream of this handler (`multiHandler.HandleLegacyUserMessage` in `core/services/gateway/multihandler.go`, lines 53-60) applies rate limiting or an allowlist before dispatch; the `nodeRateLimiter` field in `handler.go` only gates node-originated outgoing messages (`handleWebAPIOutgoingMessage`, line 166), not user-originated messages that populate `savedCallbacks`.

### Impact Explanation
This is a cross-user denial-of-service / resource-starvation vulnerability: an unauthenticated flood from one attacker can cause another legitimate user's in-flight gateway request to be silently dropped, violating the tenant-isolation invariant that one user's traffic should not affect another's pending state. This maps to Chainlink's "Denial of Service" impact class for gateway request-handling isolation, scoped to lost/dropped responses rather than fund loss.

### Likelihood Explanation
The only precondition is the ability to send signed messages to the gateway — the prompt states message signing is already reachable by an unprivileged/unauthenticated party (no allowlist currently gates this path, matching the noted prior finding at line 384). An attacker who can send >`MaxSavedCallbacks` (20000) distinct `MessageId` requests within a single `CallbackPruneIntervalSec` window (30s default) reliably triggers oldest-first eviction and can repeat this at will, making it a fully repeatable, low-cost attack requiring no special privileges.

### Recommendation
In `pruneCallbacks`, only evict entries that have exceeded (or are close to) `CallbackMaxAgeSec` when trimming for size — e.g., evict oldest-first only among candidates near expiry, or reject new insertions once the map is at capacity instead of evicting unexpired entries (respond with a capacity/backpressure error from `HandleLegacyUserMessage`). Additionally, implement the still-pending allowlist/per-sender rate limiting noted in the TODO at line 384 to prevent a single attacker from generating enough distinct `MessageId`s to affect global map size at all.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `MaxSavedCallbacks = N` (e.g. 100) and `CallbackMaxAgeSec` large enough that nothing naturally expires during the test.
2. Insert one "victim" callback via `h.savedCallbacks["victim"] = &savedCallback{id: "victim", createdAt: time.Now()}` (a fake `handlers.Callback` mock that records whether `SendResponse` was invoked).
3. Immediately after, insert `N` more distinct fake callbacks (`"attacker-0"` ... `"attacker-N-1"`) with slightly later `createdAt` timestamps, simulating a flood — either directly manipulating the map (unit-level) or via repeated calls to `HandleLegacyUserMessage` with distinct `MessageId`s and valid signatures (handler-level integration).
4. Call `h.pruneCallbacks()`.
5. Assert: `_, found := h.savedCallbacks["victim"]` is `false`, i.e., the victim's still-unexpired entry (created within `CallbackMaxAgeSec`) was evicted purely due to attacker volume — demonstrating the isolation violation.
6. Optionally simulate the DON's late response for `"victim"` via `handleWebAPITriggerMessage` and assert the victim's mock `SendResponse` is never called, confirming silent response loss.
