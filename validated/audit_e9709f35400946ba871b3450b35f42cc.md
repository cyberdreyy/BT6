### Title
Global signer state machine agreement threshold uses floor rounding while block-signing threshold uses ceiling rounding, allowing "current miner"/burn-view/replay-set consensus to be declared with sub-threshold weight - ([File: libsigner/src/v0/signer_state.rs])

### Summary
`GlobalStateEvaluator::reached_agreement` (used to determine the global view of the current miner, burn block, protocol version, and tx replay set that a signer capitulates to) computes the approval threshold using floor (truncating) integer division, while the actual block-approval threshold used for signing/rejecting blocks, `NakamotoBlockHeader::compute_voting_weight_threshold`, computes the same nominal 70% threshold using ceiling division. [1](#0-0) [2](#0-1) 

### Finding Description
`compute_voting_weight_threshold` computes `ceil(total_weight * 7 / 10)` explicitly adding a ceiling term when the division isn't exact, and this is the threshold `verify_signer_signatures` and the signer's own `store_and_process_block_signature`/`store_and_process_block_rejection` paths use to decide when a block is signed/rejected with consensus. [3](#0-2) [4](#0-3) 

By contrast, `GlobalStateEvaluator::reached_agreement` computes `total_weight * 7 / 10` with plain integer (floor) division and no ceiling adjustment, then compares `vote_weight >= threshold`. [5](#0-4) 

For any `total_weight` where `total_weight * 7` is not evenly divisible by 10, the floor-based threshold is strictly less than the ceiling-based threshold used for block signatures. For example, with `total_weight = 13`: `13*7=91`, `91/10=9` (floor, `reached_agreement` threshold), whereas `compute_voting_weight_threshold` gives `ceil(9.1)=10`. A vote weight of exactly `9` therefore satisfies `reached_agreement` (`9 >= 9`) but would not satisfy the actual signing/rejection threshold (`9 < 10`).

This function is used to decide the "current miner" (`MinerState::ActiveMiner`), the global burn view, the active protocol version, and the transaction replay set in `determine_global_state`, `determine_global_burn_view`, and `determine_latest_supported_signer_protocol_version`, which are exactly the fields a signer's local state machine capitulates to via `LocalStateMachine::capitulate_viewpoint`/`capitulate_miner_view`. [6](#0-5) [7](#0-6) [8](#0-7) 

This mirrors the LinearCurve report's bug class: a boundary/threshold calculation used for one purpose (deciding "how much is settled/decided") diverges from the calculation used for the actual authoritative accounting (transferred NFTs / accepted signature weight), producing an outcome that is inconsistent with what the stricter, canonical computation would allow.

### Impact Explanation
Because a minority-weight subset of signers (below the true 70% ceiling threshold, but at/above the floor threshold) can cause `reached_agreement` to return `true`, a signer can capitulate its local view of the "current miner" to a value that fewer than 70% (ceiling) of signers actually support. Since `capitulate_miner_view` can mark the previous sortition's miner status as `InvalidatedBeforeFirstBlock` on a miner-view change, and since `check_miner_inactivity`/`is_tenure_valid` gate whether a signer is willing to sign blocks from a given miner, this rounding discrepancy can push a signer's local state machine (and therefore its willingness to sign or its treatment of the current miner as invalid) out of sync with the group that actually reaches the canonical 70% weight required for block approval. In a worst case this can help wedge a signer into rejecting/refusing to sign a legitimately building miner's blocks based on a global-state "agreement" that was never actually reached at the block-approval threshold, which is a liveness concern (never signing valid blocks from the true canonical miner) rather than a majority-controlled attack — a single minority weight difference (the gap between floor and ceiling thresholds) is sufficient to trigger the discrepancy, not "a majority of signers."

### Likelihood Explanation
The divergence is fully deterministic and depends only on `total_weight` not being a multiple of 10 relative to 7 (i.e., `total_weight * 7 % 10 != 0`), which is the common case for real-world signer weight distributions. No malicious majority is required — the discrepancy arises purely from disagreeing rounding rules baked into two different threshold functions used for related but distinct decisions.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement` (and `reached_disagreement`) use the same ceiling-based rounding as `NakamotoBlockHeader::compute_voting_weight_threshold`, ideally by sharing a single canonical threshold-computation function between `stackslib` and `libsigner`, so that "global agreement" as computed by the state-machine evaluator can never be satisfied with less weight than what is actually required to sign/reject a block.

### Proof of Concept
Given a reward set with signer weights summing to `total_weight = 13` (e.g., weights `[9, 2, 1, 1]`):
1. `compute_voting_weight_threshold(13)` computes `13*7=91`, `91 % 10 = 1 != 0` so `ceil = 1`, threshold `= 91/10 + 1 = 10`. A block needs signature weight `>= 10` to be globally accepted.
2. `GlobalStateEvaluator::reached_agreement(9)` computes `13*7/10 = 9` (floor, no ceiling term), so `9 >= 9` returns `true`.
3. If signers with combined weight `9` (e.g., the weight-9 signer alone) report a `StateMachineUpdate` naming miner `M` as `current_miner`, `determine_global_state` will report `M` as the agreed global miner view (`found_state_view = Some(...)`) even though weight `9` is below the `10` needed to actually approve any block from `M`.
4. Any signer capitulating via `capitulate_miner_view`/`capitulate_viewpoint` to this "global" view can flip its local `current_miner` and potentially mark the actual majority-supported miner's sortition as `InvalidatedBeforeFirstBlock`, even though the true block-signing quorum was never reached for that view — creating disagreement between the local state machine's view and the canonical, ceiling-threshold-gated chain state.

Note: I was unable to execute this scenario end-to-end (e.g., via a unit/integration test) within this session; the analysis is based on static reading of `compute_voting_weight_threshold` and `reached_agreement`/`reached_disagreement` and their call sites in `libsigner/src/v0/signer_state.rs` and `stacks-signer/src/v0/signer_state.rs`. Confirming the full exploitability (i.e., whether other guards elsewhere in `stacks-signer/src/v0/signer.rs` or `chainstate/v1/v2` compensate for this specific discrepancy) would require deeper tracing of `capitulate_miner_view`'s full body and `is_tenure_valid`, which extends beyond what was reviewed here.

    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
