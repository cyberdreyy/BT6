### Title
Bridge TOKEN_TRANSFER Signature Replay on EVM Hard Fork via Static Custom `chainID` in `BridgeUtils.encodeMessage` — (File: `bridge/evm/contracts/utils/BridgeUtils.sol`)

---

### Summary

`BridgeUtils.encodeMessage` constructs the message hash that committee members sign using a custom 8-bit `message.chainID` field (sourced from `BridgeConfig.chainID`, a stored state variable). It never binds the hash to the EVM-native `block.chainid`. On an EVM hard fork both chains inherit identical contract storage, so `BridgeConfig.chainID` is the same on both chains, the signed hash is identical on both chains, and a TOKEN_TRANSFER message already processed on one chain can be replayed on the other to unlock tokens a second time.

---

### Finding Description

`BridgeUtils.encodeMessage` serialises a bridge message as:

```
MESSAGE_PREFIX | messageType | version | nonce | chainID | payload
``` [1](#0-0) 

The `chainID` field here is `message.chainID`, a custom 8-bit bridge-internal identifier (e.g. `0` = Sui mainnet, `2` = Ethereum mainnet). It is **not** the EVM `block.chainid`. Its value comes from `BridgeConfig.chainID`, which is set once at initialisation and never updated: [2](#0-1) [3](#0-2) 

`BridgeCommittee.verifySignatures` recovers signers from `BridgeUtils.computeHash(message)`, which is `keccak256(encodeMessage(message))` — no `block.chainid` anywhere in the signed digest: [4](#0-3) 

For TOKEN_TRANSFER messages, `MessageVerifier.verifyMessageAndSignatures` **skips** both the chain-ID check and the sequential-nonce check that protect every other message type: [5](#0-4) 

The only chain-ID guard for TOKEN_TRANSFER is in `SuiBridge.transferBridgedTokensWithSignatures`:

```solidity
require(
    tokenTransferPayload.targetChain == config.chainID(),
    "SuiBridge: Invalid target chain"
);
``` [6](#0-5) 

`config.chainID()` returns the same stored value on both sides of a fork. Replay protection for TOKEN_TRANSFER relies solely on:

```solidity
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
``` [7](#0-6) 

After a fork this mapping diverges: a nonce marked `true` on the canonical chain is still `false` on the fork, so the same signed message passes every check on the fork.

`SuiBridgeV2.transferBridgedTokensWithSignaturesV2` inherits the same `verifyMessageAndSignatures` modifier and the same `isTransferProcessed` mapping, so it is equally affected: [8](#0-7) 

---

### Impact Explanation

On an EVM hard fork (historical precedent: ETH/ETC 2016, ETH/ETHPoW 2022):

1. Both chains inherit identical `BridgeConfig.chainID` and identical `isTransferProcessed` state at the fork block.
2. A committee-signed TOKEN_TRANSFER message (e.g. Sui → Ethereum, nonce = N, targetChain = 2) is submitted and processed on the canonical chain → `isTransferProcessed[N] = true` there.
3. The **identical** signed bytes are submitted to the forked chain. Every check passes:
   - `verifySignatures` recovers the same signers (hash is identical).
   - `onlySupportedChain(message.chainID)` passes (same supported-chain list).
   - `targetChain == config.chainID()` passes (same stored `chainID`).
   - `isTransferProcessed[N]` is still `false` on the fork.
4. Tokens are unlocked on the fork for free — **illegitimate token unlock / double-spend**.

This matches the HackenProof Critical impact class: *bridge message forgery … that enables illegitimate … unlock*.

---

### Likelihood Explanation

EVM hard forks are rare but have occurred on Ethereum itself. The Sui bridge is deployed on Ethereum mainnet, making this a realistic threat. No privileged actor is required; any ordinary user who received a legitimate transfer on the canonical chain can replay the same committee-signed message on the fork without any additional capability.

---

### Recommendation

Bind the signed message to the EVM-native chain ID so the hash differs on each side of a fork:

```diff
 function encodeMessage(Message memory message) internal pure returns (bytes memory) {
     bytes memory prefixTypeAndVersion =
         abi.encodePacked(MESSAGE_PREFIX, message.messageType, message.version);
     bytes memory nonce = abi.encodePacked(message.nonce);
     bytes memory chainID = abi.encodePacked(message.chainID);
-    return bytes.concat(prefixTypeAndVersion, nonce, chainID, message.payload);
+    return bytes.concat(prefixTypeAndVersion, nonce, chainID,
+                        abi.encodePacked(block.chainid), message.payload);
 }
```

Alternatively, adopt EIP-712 domain separation (which already mandates `chainId`) for all bridge message hashing. Cache `block.chainid` at initialisation and recompute the domain separator whenever it changes, following the pattern recommended in the analogous Beanstalk finding.

### Proof of Concept

**Setup**: Sui bridge deployed on Ethereum mainnet (`BridgeConfig.chainID = 2`). Ethereum undergoes a hard fork producing chain ETHFork.

**Step 1** — Legitimate transfer on mainnet:
```
message = {
  messageType: TOKEN_TRANSFER (0),
  version: 1,
  nonce: 42,
  chainID: 0,          // Sui mainnet (source)
  payload: [..., targetChain=2, recipient=Alice, amount=10 ETH, ...]
}
hash = keccak256(encodeMessage(message))   // no block.chainid bound
```
Committee signs `hash`. Alice submits to mainnet bridge → `isTransferProcessed[42] = true` on mainnet. Alice receives 10 ETH on mainnet.

**Step 2** — Replay on ETHFork (no new signatures needed):
- `BridgeConfig.chainID` on ETHFork = `2` (same storage).
- `isTransferProcessed[42]` on ETHFork = `false` (diverged state).
- `encodeMessage(message)` produces the **identical** bytes → same `hash`.
- `verifySignatures` recovers the same committee members → passes.
- `targetChain (2) == config.chainID() (2)` → passes.
- `isTransferProcessed[42]` → `false` → passes.
- Alice receives another 10 ETH on ETHFork from the vault — **illegitimate unlock**.
