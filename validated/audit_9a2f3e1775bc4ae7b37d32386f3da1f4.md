### Title
Claimed instant-withdraw payouts are never removed from `instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws`, so default finalization counts already-paid cash as prefunded reserve and inflates `defaultRecoveryPrice` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Linux CVE is a hang caused by stale "wanted" state: `mds_wanted` says the request was already sent, so the waiter never re-sends and sleeps forever. The analog in `IdleCreditVault` is stale "still-held/funded" state in the instant-withdraw ledgers: `claimInstantWithdrawRequest` pays out underlying but never decrements `instantWithdrawClaimsByEpoch[epoch]` or `pendingInstantWithdraws`. When a borrower default is later finalized in the same epoch, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` trust those stale counters, treating already-paid-out cash as still-held prefunded reserve. The result is a phantom reserve, an inflated `defaultRecoveryPrice`, aggregate claims that exceed the real strategy balance, and a permanently reverting transfer for the last recovery claimants.

### Finding Description
`requestInstantWithdraw` records three pieces of state per request (`contracts/strategies/idle/IdleCreditVault.sol:356-375`):
- `instantWithdrawsRequests[_user] += _amount` (per-user receipt)
- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (epoch basis)
- `pendingInstantWithdraws += _amount` (unfunded remainder)

`collectInstantWithdrawFunds` reduces only `pendingInstantWithdraws` as the CDO pulls liquidity in (`IdleCreditVault.sol:398-403`). `claimInstantWithdrawRequest` then burns `instantWithdrawsRequests[_user]` and transfers the full amount via `_transferFundedClaim` (`IdleCreditVault.sol:380-393`), but touches neither `instantWithdrawClaimsByEpoch` nor `pendingInstantWithdraws`.

At default finalization, those stale counters are read as if nothing was ever paid:
- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-649`).
- `_defaultPrefundedInstantReserve` returns `instantBasis - pendingInstant` as "underlying already held by this strategy" (`IdleCreditVault.sol:716-723`), which is added verbatim into `defaultRecoveryReserve`/`reserveAmount` in `finalizeDefaultRecovery` (`IdleCreditVault.sol:685-691`).

The invariant `prefundedReserve == instantBasis - pendingInstant` only holds if no funded instant receipt has been claimed yet. Once a claim pays out, that cash has left the contract but is still counted. Every other ledger in the file is carefully cleared on claim (`_clearWithdrawClaimForEpoch`, `_claimDefaultedInstantWithdrawRequest` decrement `instantWithdrawClaimsByEpoch` and `instantWithdrawsRequests` at lines 847-853) — the pre-default funded claim path is the one place the epoch aggregate is not updated, exactly mirroring the kernel bug where `cap->mds_wanted` is raised before the message is actually sent and is then trusted as "already delivered".

### Impact Explanation
Concrete sequence (running epoch, instant withdrawals enabled, unprivileged users only):

1. Attacker A and victim B each call `cdoEpoch.requestInstantWithdraw` for 50 underlyings. State: `instantWithdrawClaimsByEpoch[N]=100`, `pendingInstantWithdraws=100`.
2. Honest manager/borrower flow only supplies partial liquidity; `collectInstantWithdrawFunds(50)` runs, `pendingInstantWithdraws=50`, strategy holds 50.
3. A calls `cdoEpoch.claimInstantWithdrawRequest()`; `_transferFundedClaim` sees `defaultRecoveryReserve == 0` and pays A 50. Strategy balance is now 0, but `instantWithdrawClaimsByEpoch[N]` is still 100 and `pendingInstantWithdraws` still 50.
4. Borrower defaults; owner/manager calls the default finalization path. `defaultPendingClaimBasis` includes 100 of instant basis; `_defaultPrefundedInstantReserve` credits 50 as held cash that no longer exists. `defaultRecoveryPrice` is computed on a `reserveAmount` inflated by 50.
5. B's defaulted instant claim (`_claimDefaultedInstantWithdrawRequest`) and all other recovery claimants draw on a reserve that is 50 short. Whoever claims last hits an `underflow`/`safeTransfer` revert — permanent freezing of their recovery — while A was paid at par and still counted in the basis.

Broken invariants: one receipt one payout (A's basis is paid twice — once in cash, once inside the recovery pool) and solvency of the recovery reserve (total claims = `totalBasis * recoveryPrice` > actual balance). Existing guards do not stop it: `_transferFundedClaim`'s reserve check only applies once `defaultRecoveryReserve != 0`, i.e., after finalization; `_ensureDefaultRecoveryInitialized` only blocks when `pendingInstantWithdraws != 0` at *request* time; the loss-adjusted path (`collectWithdrawFunds`) is unrelated. Quantified loss: up to the full amount of funded instant claims paid out before finalization while other instant receipts remain pending — direct overpayment to early claimants and permanent freeze of the equivalent tail-end recovery claims.

### Likelihood Explanation
Requires (a) instant withdrawals enabled, (b) two instant requests in the same epoch, (c) only partial `collectInstantWithdrawFunds` before epoch end (happens whenever CDO liquidity < pending instant queue — the documented partial-funding case in the `defaultPendingClaimBasis` comments), (d) one funded claimant actually claims, and (e) a borrower default in that epoch. (e) is the same honest-sequence default the recovery machinery is built for; (c)-(d) are normal user behavior requiring no privileged cooperation. The attacker is just an unprivileged instant-withdraw requester who claims early — explicitly in scope.

### Recommendation
In `claimInstantWithdrawRequest`, decrement `instantWithdrawClaimsByEpoch[epochOfReceipt]` (or track claimed amounts per epoch) when a claim is paid from pre-default funded liquidity, so `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` only count still-outstanding receipts. Since `instantWithdrawsRequestsByEpoch` is already per-epoch, clearing it for the current epoch on claim and reducing `instantWithdrawClaimsByEpoch[currentEpoch]` by the claimed amount restores the `prefundedReserve == held cash` invariant. Add a regression test: two instant requests, partial collect, one claim, then `finalizeDefaultRecovery` — assert the reserve equals the real balance and all claimants are paid.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVaultStaleInstantReserve.t.sol — fork/harness per existing tests
function testClaimedInstantReceiptInflatesRecoveryReserve() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);                 // enter epoch #1 buffer
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    uint256 amt = 50 * ONE_SCALE;
    address A = makeAddr('attacker'); address B = makeAddr('victim');
    _depositWithUser(A, amt); _depositWithUser(B, amt);

    // epoch starts; both request instant withdraws
    vm.prank(manager); cdoEpoch.startEpoch();
    vm.warp(block.timestamp + 100);
    vm.prank(A); cdoEpoch.requestInstantWithdraw(aaAmount_A, address(AAtranche));
    vm.prank(B); cdoEpoch.requestInstantWithdraw(aaAmount_B, address(AAtranche));
    assertEq(strategy.instantWithdrawClaimsByEpoch(1), 2*amt);
    assertEq(strategy.pendingInstantWithdraws(), 2*amt);

    // CDO only collects half (partial liquidity)
    deal(address(underlying), address(cdoEpoch), amt, true);
    vm.prank(address(cdoEpoch));                     // via getInstantWithdrawFunds path
    strategy.collectInstantWithdrawFunds(amt);
    assertEq(strategy.pendingInstantWithdraws(), amt);

    // Attacker claims the only funded cash
    vm.prank(A); cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(address(strategy)), 0);
    // STALE: epoch aggregate still says 2*amt outstanding
    assertEq(strategy.instantWithdrawClaimsByEpoch(1), 2*amt);

    // Borrower defaults; manager finalizes recovery
    _triggerBorrowerDefaultAndFinalize(recovered);   // honest owner calls

    // prefunded reserve credited with cash that was already paid to A
    // defaultRecoveryPrice is inflated by `amt`; last claimant reverts
    vm.prank(B); cdoEpoch.claimInstantWithdrawRequest(); // pays from reserve
    vm.expectRevert();                                    // tail claimant / BB recovery claim
    vm.prank(otherClaimant); distributor.claim();
}
```
Note: exact default-finalize entry points (`_handleBorrowerDefault`/`finalizeDefault` on `IdleCDOEpochVariant` calling `finalizeDefaultRecovery`) should be wired following the existing `IdleCreditVault.t.sol` default tests; the core assertion is that `defaultRecoveryReserve` exceeds `underlying.balanceOf(strategy)` by the previously claimed amount.
