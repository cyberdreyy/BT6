### Title
Stale rejection weight survives a signer's later acceptance, letting a phantom blocking-minority veto a genuinely-approved block - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node-side StackerDB tally used to decide whether a proposed block has been globally accepted or globally rejected accumulates per-signer weight into two independent counters, `total_weight_approved` and `total_weight_rejected`, guarded by two different, non-overlapping dedup sets (`gathered_signatures` and `responded_signers`). The implicit (and unsound) assumption baked into this bookkeeping is that a signer's vote is monotonic — that once a signer's weight lands in one bucket it can never also land in the other. That assumption is never enforced, so a single signer (its own key, no majority required) that first rejects and later accepts the same block hash has its weight double-booked: once permanently in `total_weight_rejected` and again in `total_weight_approved`.

### Finding Description
In the `Rejected` branch, weight is added to `total_weight_rejected` guarded only by `responded_signers.insert(slot_id)`: [1](#0-0) 

In the `Accepted` branch, weight is added to `total_weight_approved` guarded by a *different* set, `gathered_signatures.contains_key(&slot_id)`, and `responded_signers.insert(slot_id)` is called unconditionally afterward with no effect on the already-added rejection weight: [2](#0-1) 

Because the two code paths key off two different maps/sets, the ordering Reject → Accept for the same `slot_id`/block hash is not detected as a state transition: the earlier `total_weight_rejected` increment is never reversed, and the later `Accepted` message is treated as a fresh vote because `gathered_signatures` does not yet contain that slot. The result is that one signer's weight can simultaneously and permanently count toward both `total_weight_rejected` and `total_weight_approved` for the same block. (Note the opposite ordering, Accept → Reject, is safe: `responded_signers.insert` on the second `Reject` message returns `false` because `Accepted` already inserted the slot into `responded_signers`, so the reject increment is correctly suppressed — confirming the bug is one-directional and purely a consequence of using two different dedup keys for the two branches.)

### Impact Explanation
`signer_coordinator.rs` reads these two counters to decide the outcome for the block it proposed: it checks the rejection condition (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`, i.e. a >30% blocking minority) before the acceptance condition (`total_weight_approved >= weight_threshold`): [3](#0-2) 

Because a signer's stale rejection weight is never cleared after it later accepts, `total_weight_rejected` can retain phantom weight from signers who have since switched to accept. In a scenario where the "live" approving weight is right at/above the 70% threshold but includes one or more signers who initially rejected before accepting, the stale rejected total can independently cross the >30% blocking-minority condition, which is checked first. The miner then treats a block that a real current supermajority has accepted as globally rejected, excludes it, and reports "failed" transaction ids for banning — a liveness wedge in the block-proposal/coordinator state machine driven purely by a single participant's message ordering, no collusion or majority required. This falls under the "wedge in the state machine" / stale-aggregated-weight class called out in the report analogy (the Certora `require_uint256`→`assert_uint256` fix was about silently assuming an invariant instead of proving it; here the code silently assumes a signer's weight is exclusive-or between the accept/reject buckets, without ever enforcing or revoking it).

### Likelihood Explanation
Triggering this requires only one signer (controlling its own StackerDB slot/key) to publish a `Rejected` `BlockResponse` for a given `signer_signature_hash` and later publish an `Accepted` response for the same hash — both are ordinary, already-defined `SignerMessageV0` variants that the node accepts from any registered signer slot without further gating on message ordering. No majority, no other signer's key, and no protocol violation on the wire format is needed; it is purely a timing/ordering choice by the participant whose own key is being used (or, without malice, could occur naturally if a signer briefly rejects a stale view and then rescinds/accepts once caught up with block validation, since the code has no reconciliation logic for that case).

### Recommendation
Track each signer's current vote in a single map (e.g., `HashMap<slot_id, BlockResponseKind>`), and derive `total_weight_approved`/`total_weight_rejected` by recomputing from that map (or by explicitly subtracting the previous bucket's weight before adding to the new bucket) whenever a signer's vote changes, rather than using two independently-guarded, monotonically-increasing counters keyed off different dedup structures (`gathered_signatures` vs `responded_signers`).

### Proof of Concept
1. Node proposes a block with `signer_signature_hash = H` and `weight_threshold` set to 70% of `total_weight`.
2. Signer `S` (slot `k`, weight `w`) publishes `BlockResponse::Rejected` for `H`. `stackerdb_listener.rs` sets `responded_signers.insert(k)` and `total_weight_rejected += w` (lines 515-518).
3. Enough other signers approve so that "live" approving weight (excluding `S`) is just under 70%, and `total_weight_rejected` (including `S`'s `w`) is engineered/close to exceeding `total_weight - weight_threshold` (the >30% blocking minority), e.g., by combining `S`'s stale rejection with a few honest signers who reject for legitimate reasons.
4. Signer `S` then publishes `BlockResponse::Accepted` for the same `H`. The `Accepted` branch checks `gathered_signatures.contains_key(&k)`, which is `false` (S never accepted before), so `total_weight_approved += w` (lines 443-446); `total_weight_rejected` is left untouched at its already-incremented value.
5. `total_weight_approved` may now reach `weight_threshold` (a genuine 70% including `S`), while `total_weight_rejected` (still containing `S`'s stale weight plus the other rejecters) also exceeds the >30% blocking-minority bound.
6. `get_block_status` in `signer_coordinator.rs` evaluates the rejection branch first (lines 509-513) and returns `NakamotoNodeError::SignersRejected`, discarding a block that a live 70% supermajority (including `S`'s corrected vote) actually approved — demonstrating the liveness wedge caused by the unreconciled double-count.
