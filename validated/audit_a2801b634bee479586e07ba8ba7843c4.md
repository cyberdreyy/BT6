### Title
V1 Signer's Duplicate-Tenure-Change Check Uses `get_last_globally_accepted_block` Instead of `get_last_signed_block`, Letting a Single Miner Slip a Competing Tenure-Change Proposal Past the Early-Reject Guard - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
The v1 signer chainstate's proposal-time duplicate-tenure-change check (`validate_tenure_change_payload`) only consults `get_last_globally_accepted_block` to decide whether a tenure-change block duplicates one already accepted for the same tenure. It does not see blocks the signer has already `LocallyAccepted` (self-signed and pushed to the node but not yet confirmed by a `NewBlock` event) or merely `PreCommitted`. The v2 chainstate was fixed to use `get_last_signed_block` for exactly this reason, as documented by a regression test explaining the old behavior was buggy.

### Finding Description
`validate_tenure_change_payload` in v1 rejects a tenure-change proposal with `RejectReason::DuplicateBlockFound` only when `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` returns `Some`: [1](#0-0) 

Global acceptance requires the stacks-node to actually process the block (`NewBlock` event), which can lag well behind the signer set already reaching the 70% signing threshold and marking a block `LocallyAccepted`: [2](#0-1) 

By contrast, the v2 chainstate closed this exact gap by switching to `get_last_signed_block`, which also covers `LocallyAccepted`/`PreCommitted-then-signed` blocks: [3](#0-2) 

The project's own regression test documents that this was a real, previously-fixed bug class: [4](#0-3) 

The documentation for the shared chainstate checks also states this duplicate check runs **only** at proposal time and is never re-run at validate-ok or at signing; the only backstop is the pre-commit-time "own-tenure conflict" guard, which relies on freshness and the node's tenure tip and is designed to eventually let a stale, unconfirmed signature be superseded (to avoid permanently wedging a tenure on a lost race): [5](#0-4) [6](#0-5) 

Putting these together: for a v1 signer, a single miner can propose a second, different tenure-change block for a tenure that the signer has already `LocallyAccepted` a tenure-change block for. Because `get_last_globally_accepted_block` sees nothing (the first block hasn't been confirmed by the node yet), the proposal-time `DuplicateBlockFound` rejection never fires — the only protocol-defined layer designed to reject this class of proposal outright. The proposal is then queued for validation and pre-commit exactly like a legitimate first proposal. The remaining backstop (the "own-tenure conflict" guard at pre-commit time) is fresh only for a bounded window; once the first signature goes stale before the node confirms it (which is exactly the situation `get_last_globally_accepted_block` cannot distinguish from "never signed"), the guard's own logic explicitly permits signing the replacement rather than blocking, since it cannot tell "abandoned" from "not yet confirmed."

### Impact Explanation
This breaks the "one signed block per tenure" equality that the duplicate check exists to enforce, at the proposal layer where it was intended to fire immediately and unconditionally. It reduces the layered defense to a single, staleness-dependent path — increasing the odds that a v1 signer eventually signs two different tenure-change blocks for the same tenure (a conflicting-block-signing outcome), which is a Critical-class equivocation risk for the signer.

### Likelihood Explanation
The trigger requires only a single miner in its block-production slot (no other signer's key, no majority collusion): propose a second tenure-change block for a tenure whose first tenure-change block has already been locally/group-signed but not yet confirmed by the node — a state that is not unusual under any latency between `broadcast_signed_block` and the node's `NewBlock` event. Since `validate_tenure_change_payload` is proposal-time-only and never re-checked, the miner's manufactured "duplicate" proposal proceeds through the normal validation and pre-commit pipeline exactly as if it were the tenure's only proposal.

### Recommendation
Update the v1 `validate_tenure_change_payload` duplicate-tenure check to use `signer_db.get_last_signed_block` (as v2 already does) instead of `get_last_globally_accepted_block`, so that a locally-accepted-but-not-yet-globally-confirmed tenure-change block is recognized at proposal time, restoring the intended immediate rejection rather than relying solely on the staleness-sensitive pre-commit guard.

### Proof of Concept
1. Bring a v1 signer set to a fresh tenure T with tenure-change block B1.
2. Have enough signers pre-commit and sign B1 so that it reaches `LocallyAccepted` (`store_and_process_block_signature` → `mark_locally_accepted(true)`), per `stacks-signer/src/v0/signer.rs:2525-2537`, but delay/suppress the node's `NewBlock` event so `get_last_globally_accepted_block` for T still returns `None`.
3. As the block-producing miner, immediately craft and broadcast a second, distinct tenure-change block B2 for the same tenure T (same `tenure_consensus_hash`, different content/timestamp).
4. Observe that `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:505-518`) does not return `DuplicateBlockFound`, since `get_last_globally_accepted_block` sees nothing; B2 proceeds to validation and pre-commit as if it were the tenure's first proposal.
5. Let B1's signature age past `reorg_attempts_activity_timeout`/freshness cutoff while the node still has not confirmed it (still plausible given no `NewBlock` event); at the pre-commit threshold for B2, `conflict_still_blocks`'s own-tenure branch (`stacks-signer/src/v0/signer.rs:1192-1205`) resolves to "never confirmed" and signs B2, producing two signed conflicting blocks for tenure T from the same signer set.
