### Title
Unauthenticated `/v2/resume/:runID` Endpoint Allows Any Actor to Inject Results Into Another User's Suspended Pipeline Run - (File: `core/web/pipeline_runs_controller.go`)

### Summary
`PipelineRunsController.Resume` accepts a bare `taskID` (a UUID) and a JSON body containing an arbitrary result, and immediately calls `App.ResumeJobV2` to complete the task and un-suspend the associated pipeline run — with no ownership or session check tied to the specific run/job. The audit event name itself, `audit.UnauthedRunResumed`, confirms this endpoint is explicitly exempted from normal authenticated-user checks that other pipeline-run routes (`Show`, `Create`, `Index`) enforce via `auth.GetAuthenticatedUser`.

### Finding Description
`Resume` parses `runID` as a `uuid.Parse` task ID [1](#0-0) , decodes an attacker-controlled JSON body into a `pipeline.ResumeRequest`, and forwards it straight to `prc.App.ResumeJobV2(ctx, taskID, result)` [2](#0-1) . Unlike `Create`, which checks `auth.GetAuthenticatedUser(c)` before allowing a user to trigger a run [3](#0-2) , `Resume` performs no such check and is even audited under the distinct event `UnauthedRunResumed` [4](#0-3) [5](#0-4) .

`ResumeJobV2` forwards directly into the pipeline `Runner.ResumeRun`, which loads the run/task purely by `taskID` via `UpdateTaskRunResult`, sets the supplied value/error onto that task, and if the run was suspended, restarts it: [6](#0-5)  and [7](#0-6) . There is no check that the caller is the same session/user/external-initiator that originally created the corresponding run — resumption is entirely keyed off possession of a `taskID` UUID.

This mirrors the reported bug class: an action intended for one legitimate "owner" of a stateful resource (a stake / a pending job run) can be performed by an unrelated, unprivileged actor because the endpoint has no per-resource authorization/ownership gate, only relying on the difficulty of guessing an identifier (UUID here, `unstakeDelay` timing there). In both cases the state-mutating action is exposed to a party who should not be able to invoke it on someone else's resource.

### Impact Explanation
An attacker who obtains or guesses a valid task UUID (e.g., leaked via logs, presenters, or brute force since UUIDs are the only barrier) can:
- Inject arbitrary fabricated results/errors into another job's suspended pipeline run, corrupting downstream task outputs (`Value`/`Error`) for tasks the attacker does not own.
- Prematurely or repeatedly force-resume a run, causing state confusion, incorrect final job results, or unintended execution of downstream tasks (potentially triggering fund-moving `ETHTx` tasks with attacker-controlled inputs from earlier stages, depending on job wiring).
- Cause a denial of service against legitimate suspended runs by resuming them with error results before the true async response (e.g., an external adapter callback) arrives, since `UpdateTaskRunResult` will overwrite whatever data is passed for `taskID` unconditionally as long as the run is `running`/`suspended` [8](#0-7) .

This is a legitimate concern for nodes exposing this API without additional network-level protections, since the analog to the `unstakeDelay` bug — an unprivileged actor manipulating another party's stateful, time-sensitive resource — is directly present here, but at the level of job-run integrity rather than fund custody.

### Likelihood Explanation
Exploitation requires knowledge of a valid pending `taskID` UUID. Since UUIDs are high-entropy, blind guessing is impractical, but the identifier is not scoped to any authentication context and may be observable through response bodies (bridge callback URLs of the form `/v2/resume/<uuid>` are sent out to third-party bridge adapters, as seen in test fixtures such as `core/services/pipeline/runner_test.go:787`), logs, or a compromised bridge endpoint. Any party that can observe or intercept that callback URL — which is by design shared with external, less-trusted bridge/adapter services — can then submit arbitrary resume payloads without further authentication.

### Recommendation
Require a shared secret/token (already present in bridge configurations, e.g., outgoing tokens used for external initiators) to be validated on `/v2/resume/:runID`, or otherwise verify that the resume request is authorized (e.g., by embedding and checking a per-run secret in the resume URL rather than only the low-context task UUID) before allowing `Runner.ResumeRun` to mutate the run.

### Proof of Concept
1. Create a job with an async/bridge task, which suspends the pipeline run and generates a resume URL of the form `http://<node>/v2/resume/<taskUUID>` (sent to the bridge adapter as `ResponseURL`, as seen in `core/services/pipeline/runner_test.go:787`).
2. An attacker who observes or intercepts this URL (e.g., via a network path to the bridge service, logs, or a compromised/curious downstream adapter) sends: `PATCH /v2/resume/<taskUUID>` with an arbitrary JSON body matching `pipeline.ResumeRequest` (e.g., `{"data":{"result": "attacker-controlled"}}`).
3. `PipelineRunsController.Resume` performs no ownership check and calls `App.ResumeJobV2`, which resumes the run with the attacker-supplied data [9](#0-8) , causing the pipeline to complete with forged data instead of the legitimate bridge/adapter response.

func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)

func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}

func (o *orm) UpdateTaskRunResult(ctx context.Context, taskID uuid.UUID, result Result) (run Run, start bool, err error) {
	if result.OutputDB().Valid && result.ErrorDB().Valid {
		panic("run result must specify either output or error, not both")
	}
	err = o.transact(ctx, func(tx *orm) error {
		sql := `
		SELECT pipeline_runs.*, pipeline_specs.dot_dag_source "pipeline_spec.dot_dag_source", job_pipeline_specs.job_id "job_id"
		FROM pipeline_runs
		JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
		JOIN pipeline_specs ON (pipeline_specs.id = pipeline_runs.pipeline_spec_id)
		JOIN job_pipeline_specs ON (job_pipeline_specs.pipeline_spec_id = pipeline_specs.id)
		WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
		FOR UPDATE`
		if err = tx.ds.GetContext(ctx, &run, sql, taskID); err != nil {
			return fmt.Errorf("failed to find pipeline run for task ID %s: %w", taskID.String(), err)
		}

		sql = `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1`

			return fmt.Errorf("failed to update pipeline task run: %w", err)
