### Title
Loss-adjusted epoch haircut only applies to the user's latest request epoch, letting older pending receipts escape the realized loss and draining funding from loss-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` applies a realized `stopEpochWithDuration` loss to the **entire** `pendingWithdraws` aggregate and stores a single `lossRecoveryPriceByEpoch[epochNumber]`, but `_claimLossAdjustedWithdrawRequest` only haircuts receipts whose `lastWithdrawRequest` equals that one epoch. Pending receipts opened in earlier epochs — which were counted in `pendingBasis` when the haircut price was computed — claim at par through `_claimFundedWithdrawRequest`. The result is the same shape as the OpenEXR overflow: a bounded input (funded amount) is consumed by more claims than it was sized for, so aggregate payouts exceed the collected buffer and later claimants are left insolvent.

### Finding Description
When `stopEpochWithDuration` realizes a loss, `IdleCreditVault.collectWithdrawFunds` computes:

```solidity
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

`pendingBasis` is the aggregate of **all** pending receipts across **all** request epochs (`withdrawsRequestsByEpoch[user][epoch]` accumulated over time, plus APR0 principal/interest). `previewLossAdjustedWithdrawFunds` confirms the intent: "all pending receipts share their aggregate portion of the loss pro rata."

However, on the claim side `_claimLossAdjustedWithdrawRequest` looks up only `lastWithdrawRequest[_user]`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
```

A user who requested a withdraw in an earlier epoch and never claimed has `lastWithdrawRequest` pointing to that older epoch, where `lossRecoveryPriceByEpoch` is 0. They therefore fall through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` (including the receipt that was haircut at funding time) **at par**. The epoch gate `epochNumber <= lastWithdrawRequest[_user]` passes because at least one epoch has elapsed.

Concrete sequence (epoch-running mode):
1. Epoch 1: Alice calls `requestWithdraw(100e18)` via the CDO. `pendingWithdraws = 100e18`, `withdrawsRequestsByEpoch[alice][1] = 100e18`, `lastWithdrawRequest[alice] = 1`.
2. Epoch 1 ends without funding (borrower repays only interest; `collectWithdrawFunds` receives the full `pendingBasis`... note: see caveat below) — more precisely, Alice simply does not claim.
3. Epoch 2: Bob calls `requestWithdraw(100e18)`. `pendingWithdraws = 200e18`, `withdrawsRequestsByEpoch[bob][2] = 100e18`, `lastWithdrawRequest[bob] = 2`.
4. `stopEpochWithDuration(_lossAmount)` realizes a loss; `previewLossAdjustedWithdrawFunds` allocates `pendingLoss` across the whole `200e18` pending basis, so say `collectWithdrawFunds` receives `150e18` → `lossRecoveryPriceByEpoch[2] = 0.75e18`, `pendingWithdraws = 0`. The strategy now holds `150e18` for receipt claims.
5. Alice claims: `lastWithdrawRequest[alice] = 1`, `lossRecoveryPriceByEpoch[1] == 0` → funded path pays `100e18` at par. Remaining balance: `50e18`.
6. Bob claims: `lastWithdrawRequest[bob] = 2` → haircutted `100e18 * 0.75e18 / 1e18 = 75e18`, but only `50e18` remains → `safeTransfer` reverts. Bob's claim is permanently underpaid by `25e18` (or frozen until the contract is topped up), while Alice received `25e18` that the loss accounting had assigned as Bob's/Alice's shared haircut.

Note on step ordering: `collectWithdrawFunds` records the price under the **current** `epochNumber` at the moment of the call, matching the request epoch only because `epochNumber` is bumped later in `deposit` during the same `stopEpoch`. The mis-haircut affects any receipt whose `lastWithdrawRequest` differs from that epoch.

### Impact Explanation
Direct insolvency / theft of funded withdraw proceeds. Whenever a loss-adjusted stop occurs while pre-existing (older-epoch) pending receipts coexist with current-epoch receipts, the funded pool is under-reserved by `olderReceipts * (1 - lossRecoveryPrice)`. First-come claimants drain the pool at par; current-epoch claimants cannot claim their full haircutted amount. Loss magnitude equals the haircut that should have been applied to older receipts — unbounded as a fraction of the funded amount (up to nearly all of it if `lossRecoveryPrice` is small and older receipts dominate).

### Likelihood Explanation
Requires: (a) at least one user with an unclaimed receipt from a prior epoch — routine, since receipts never expire and the docs explicitly allow claiming "at any time even if a new epoch started"; (b) a `stopEpochWithDuration` with `_lossAmount > 0` while `pendingWithdraws > 0` — an honest manager/borrower sequence, not attacker-dependent. Any KYC'd lender can hold the stale receipt. No privileged misbehavior needed. The only mitigation is the `_transferFundedClaim` reserve guard, which applies only when `defaultRecoveryReserve != 0` (post-default), not in the loss-adjusted path.

### Recommendation
Track the haircut per receipt epoch rather than per `lastWithdrawRequest`. Options:
- In `_claimFundedWithdrawRequest`/`_claimLossAdjustedWithdrawRequest`, iterate or bucket `withdrawsRequestsByEpoch` so each epoch's receipt is paid at its own `lossRecoveryPriceByEpoch` (or par if none). Since per-epoch data already exists, a minimal fix is to store, at claim time, the sum over the user's epochs of `amount_e * (price_e != 0 ? price_e : RECOVERY_FULL) / RECOVERY_FULL`.
- Alternatively, split `pendingWithdraws` so `collectWithdrawFunds` only haircuts receipts belonging to the current epoch and treats older receipts as already-funded obligations — but that changes the intended "all pending receipts share the loss" semantics of `previewLossAdjustedWithdrawFunds`.
- Ensure the same treatment for APR0 principal/interest buckets (`apr0Users.principalEpoch` vs loss epoch), which currently follow the same `lastWithdrawRequest` gate.

### Proof of Concept
Foundry fork-style test sketch (adapt addresses/setup to the existing `test/foundry` harness, e.g. `IdleCreditVaultFactory.t.sol` deployment helpers):

```solidity
// contracts: IdleCDOEpochVariant cdo, IdleCreditVault vault, underlying ERC20 (e.g. USDC)
// roles: lpAlice, lpBob are KYC'd lenders; manager/borrower honest.

function test_OlderReceiptEscapesLossHaircut() public {
    uint256 amt = 100e6; // USDC

    // --- Epoch 1 ---
    vm.prank(lpAlice);
    cdo.depositAA(amt);
    vm.prank(manager);
    cdo.startEpoch();                      // borrower takes funds
    vm.prank(lpAlice);
    cdo.requestWithdraw(amt /* via CDO withdraw request flow */);
    // epoch 1 ends normally: borrower repays only interest, receipts funded or left pending
    vm.prank(manager);
    cdo.stopEpoch();
    // Alice does NOT claim.

    // --- Epoch 2 ---
    vm.prank(lpBob);
    cdo.depositAA(amt);
    vm.prank(manager);
    cdo.startEpoch();
    vm.prank(lpBob);
    cdo.requestWithdraw(amt);

    // stopEpochWithDuration realizes a loss covering 25% of aggregate basis
    uint256 loss = computeLossForPendingHaircut(); // such that pendingToFund = 150e6
    vm.prank(manager);
    cdo.stopEpochWithDuration(loss);

    // vault now holds 150e6 for receipt claims; lossRecoveryPriceByEpoch[2] = 0.75e18

    // Alice claims first: pays FULL 100e6 at par despite being in the haircut basis
    vm.prank(lpAlice);
    cdo.claimWithdrawRequest();
    assertEq(underlying.balanceOf(lpAlice), /* includes */ 100e6);

    // Bob claims: entitled to 75e6 (0.75 haircut), only 50e6 remains -> revert
    vm.prank(lpBob);
    vm.expectRevert(); // safeTransfer underflow / ERC20 insufficient balance
    cdo.claimWithdrawRequest();
}
```

Expected result: Bob's claim reverts or pays less than his haircut-adjusted `75e6`, demonstrating that Alice's stale receipt consumed `25e6` of funding the loss accounting had already deducted.

Caveat: exact CDO call names (`requestWithdraw`, epoch timings, how `stopEpochWithDuration` forwards to `collectWithdrawFunds`) should be aligned with `IdleCDOEpochVariant.sol`; the strategy-side accounting bug is at `IdleCreditVault.sol:411-430` (aggregate haircut) vs `IdleCreditVault.sol:789-801` (per-`lastWithdrawRequest` claim). I did not verify whether `IdleCDOEpochVariant` forbids requesting a new withdraw while an old one is pending in a way that prevents the two-epoch-receipt state — the strategy's own comments ("if a user does not claim... he will have to wait for another epoch to claim both requests") indicate coexisting pending receipts are expected.
