### Title
Permissionless revolving-vault deployment lets an attacker bind lender funds to a malicious ERC4626 vault - (File: contracts/IdleCreditVaultFactory.sol)

### Summary
`IdleCreditVaultFactory.deployRevolvingCreditVault` is callable by any EOA and accepts caller-controlled implementation and ERC4626 vault addresses. [1](#0-0) [2](#0-1)  The factory deploys transparent proxies around those caller-provided implementations without checking an allowlist or bytecode hash. [3](#0-2) 

The programmable-borrower initializer checks only that the supplied vault reports the expected `asset()`, then stores it and grants it unlimited underlying allowance. [4](#0-3)  During the first epoch start, lender assets are sent to the programmable borrower and deposited into that vault. [5](#0-4) [6](#0-5)  A malicious ERC4626 can therefore execute arbitrary code in `deposit` and immediately forward the entire pool balance to the attacker. [7](#0-6) 

### Finding Description
The vulnerable composition is:

1. An unprivileged attacker calls `deployRevolvingCreditVault` with:
   - the canonical `IdleCDOEpochVariant`, `IdleCreditVault`, and `ProgrammableBorrower` implementations;
   - a real underlying token;
   - an honest manager/borrower/feeReceiver;
   - an attacker-controlled ERC4626 vault.
2. `ProgrammableBorrower.initialize` calls only `IERC4626(_vault).asset()` and compares it to the CDO underlying. [8](#0-7) 
3. The initializer grants unlimited underlying allowance to that arbitrary code address. [9](#0-8) 
4. A victim deposits through `depositAA`, causing the canonical strategy to custody the underlying and mint strategy tokens to the CDO. [10](#0-9) [11](#0-10) 
5. The honest manager later calls `startEpoch`; the CDO transfers buffer deposits to the configured borrower and invokes `onStartEpoch`. [5](#0-4) 
6. `ProgrammableBorrower.onStartEpoch` deposits its full on-hand underlying balance by calling `vault.deposit`. [12](#0-11) 
7. `_depositToVault` does not verify that shares were minted, that the vault retained assets, or that the vault belongs to an approved registry. [7](#0-6) 
8. The malicious vault uses its unlimited allowance inside `deposit`, moves all underlying to the attacker, and returns arbitrary share data.

The same trust-boundary flaw exists for every caller-controlled implementation address accepted by the factory, but the malicious ERC4626 path is sufficient to steal all deposits while using the production CDO, strategy, and programmable-borrower implementations. [13](#0-12) 

### Impact Explanation
All lender deposits present when the first epoch starts can be stolen. The broken invariant is solvency/fair minting: the victim receives tranche and strategy-token accounting backed by assets that are immediately transferred to attacker-controlled code rather than retained by a valid ERC4626 vault. [14](#0-13) 

For a deposit of `A`, the quantified loss is `A`: `vault.deposit(A, ProgrammableBorrower)` may send all `A` underlying tokens to the attacker while returning any value. Existing guards do not prevent this: `asset()` matching is only interface confirmation, `nonReentrant` does not stop an external vault from transferring funds it was explicitly authorized to take, and the manager calling `startEpoch` is honest. [4](#0-3) [15](#0-14) 

### Likelihood Explanation
The deployment path requires only an unprivileged factory call because `deployRevolvingCreditVault` has no caller authorization. [2](#0-1)  The deployed contracts can use canonical implementation bytecode, legitimate tokens, an honest manager, normal fee parameters, and a normal `CreditVaultDeployed` event, making the malicious external vault the only hostile component. [16](#0-15) 

The attacker must induce a KYC-passing or otherwise eligible lender to deposit into the malicious deployment and wait for the configured honest manager to start an epoch. That sequence is externally plausible because the factory emits the deployed addresses itself and does not give depositors an authenticated registry or implementation/vault identity to verify. [17](#0-16) [15](#0-14) 

### Recommendation
Restrict deployment to an authorized factory operator or treasury-controlled role. Additionally:

- maintain treasury-approved allowlists for CDO, strategy, queue, write-off escrow, and programmable-borrower implementations;
- maintain an approved ERC4626 vault registry rather than accepting an arbitrary `vault` parameter;
- validate implementation addresses before constructing `TransparentUpgradeableProxy`;
- store deployment provenance so off-chain users can distinguish canonical deployments;
- optionally verify ERC4626 behavior with a bounded probe before granting unlimited allowance;
- revoke the old vault allowance before switching vaults, which `setVault` currently does only through `safeApprove(address(vault), 0)` after the vault variable is read. [18](#0-17) 

### Proof of Concept
A Foundry PoC can deploy the real factory and canonical implementations, supply a malicious ERC4626, let an honest manager start the epoch, and show that the full victim deposit reaches the attacker.
