### Title
Cross-user callback hijack via MessageId-keyed `savedCallbacks` map without Sender binding - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Finding Description
`HandleLegacyUserMessage` stores the caller's `handlers.Callback` keyed solely by `msg.Body.MessageId` in `h.savedCallbacks`, with no binding to `msg.Body.Sender`: [1](#0-0) 

`MessageId` is attacker-controlled (part of the signed payload, arbitrary string up to 128 bytes) and is not required to be globally unique — `Message.Validate()` only checks length/format, not uniqueness: [2](#0-1) 

If two different signers (Sender A and Sender B) submit `WebAPITrigger` requests with the same `MessageId` but different signatures/payloads, the second call to `HandleLegacyUserMessage` simply overwrites `h.savedCallbacks[msg.Body.MessageId]` with Sender B's callback, silently discarding Sender A's callback reference (Sender A's original request was already forwarded to DON nodes, so no error is returned to A at write time).

When a DON node later responds with that `MessageId` (e.g. answering A's original forwarded request), `handleWebAPITriggerMessage` looks up `savedCallbacks[msg.Body.MessageId]`, finds B's callback (since it overwrote A's), deletes the entry, and invokes `SendResponse` on B's callback with the node's response data — which corresponds to A's original request: [3](#0-2) 

`HandleNodeMessage` only validates that `msg.Body.Sender == nodeAddr` (i.e., that the responding DON node is who it claims to be) — it does nothing to correlate the response back to the correct *user* request beyond the `MessageId` key: [4](#0-3) 

Thus Sender A never receives a response (times out), while Sender B's callback receives data/response content tied to Sender A's request — a cross-user isolation break. There is no allowlist/rate-limit/uniqueness check preventing two distinct senders from using the same `MessageId` (the handler code even has a `// TODO: apply allowlist and rate-limiting here` comment, and a separate `// TODO: Validate Senders` note in the test file confirming sender-scoped validation is not yet implemented): [5](#0-4) [6](#0-5) 

### Impact Explanation
An unauthenticated (from the node's perspective — any address holding a valid ECDSA key, no special role) attacker can cause a legitimate user's WebAPITrigger response to be silently swallowed (denial of service for that request) and, more seriously, can have the DON's response payload intended for another user's request delivered into the attacker's own callback — a cross-user response confusion/data leak matching the "cross-user callback hijack/DoS" bounty class. This affects response data confidentiality/integrity between callers sharing a gateway/DON, though it does not by itself compromise node keys or funds.

### Likelihood Explanation
Exploitability requires only: (1) network/HTTP access to the gateway endpoint for a known DON ID, (2) two valid signing keys (attacker can generate their own ECDSA keys freely — no allowlist enforcement is implemented per the code comments), and (3) sending two `WebAPITrigger` messages with the same `MessageId` in quick succession before the first is resolved by a node response. Because `MessageId` is entirely attacker-chosen and no uniqueness/sender-scoping check exists, this is trivially reproducible and repeatable, limited only by the race window between the victim's request being forwarded and the DON's response arriving.

### Recommendation
Key `savedCallbacks` by a composite of `(Sender, MessageId)` (or a server-generated globally unique correlation ID) instead of `MessageId` alone, and reject/queue duplicate `(Sender, MessageId)` pairs. When storing/looking up the callback in `handleWebAPITriggerMessage`, use the same composite key derived from the response's validated `Sender`/original request association, ensuring a node's response can only be routed to the callback of the specific sender who originally submitted that request.

### Proof of Concept
Go handler-level integration test (extends `handler_test.go`):
1. Build `msgA := triggerRequest(t, nodes[0].PrivateKey, ...)` and `msgB := triggerRequest(t, someOtherKey, ...)` both with the same `MessageId` (e.g., patch `triggerRequest` to accept an explicit ID, or hand-construct `api.Message` with `Body.MessageId = "dup-id"`, sign each with a different key).
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` then immediately `handler.HandleLegacyUserMessage(ctx, msgB, cbB)`.
3. Assert `handler.savedCallbacks["dup-id"]` now refers to `cbB`, not `cbA`.
4. Simulate a DON node response for `msgA`'s original request via `handler.HandleNodeMessage(ctx, respForMsgA, nodes[0].Address)`.
5. Assert `cbB.Wait(ctx)` receives the response payload corresponding to `msgA` (proving cross-user leak), and assert `cbA.Wait(ctx)` times out / never receives a response (proving DoS for the original sender).

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
