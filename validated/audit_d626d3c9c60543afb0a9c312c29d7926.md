### Title
APR0 withdraw bucket permanently bricks `stopEpoch` once APR is raised, freezing all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed()` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` (lines 502-508). An unprivileged KYC-passed lender can open the APR0 bucket by calling `requestWithdraw` while the vault runs at APR 0. If the (honest) manager later raises the APR via `setAprs`/`setAprsWithBuffer` before the bucket is settled, every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts, so the epoch can never end and all deposits, interest, and pending withdraw receipts stay frozen.

### Finding Description
The bug class of CVE-2020-2804 — an unauthenticated party causing a hang/crash (DoS) of a service — maps to an unprivileged lender forcing a state in which the epoch state machine can no longer advance.

Relevant code:

- `IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw` routes requests to `_requestWithdrawApr0` whenever `unscaledApr == 0` and the pool isn't closed (IdleCreditVault.sol:285-286).
- `_requestWithdrawApr0` increments the global `apr0TotalPrincipal` (IdleCreditVault.sol:567-577). Once set, this counter is only cleared by `prepareStopEpochWithApr0` (line 540) or by default-claim clearing — there is no user- or manager-facing way to decrement it.
- `setApr`/`setAprsWithBuffer` are callable by the manager at any time and set `unscaledApr`/`lastApr` without checking `apr0TotalPrincipal` (IdleCreditVault.sol:206-235).
- `_stopEpoch` calls `prepareStopEpochWithApr0` before `_setScaledApr(_newApr)` (IdleCDOEpochVariant.sol:362, 471), so the check at line 506 sees the *out-of-band* APR change, not the new-epoch APR.

Sequence:

1. Vault runs an epoch at `unscaledApr == 0` (a supported mode — APR0 requests accrue pro-rata realized interest at stop).
2. Epoch ends (buffer phase). Attacker (any allowed wallet) calls `requestWithdraw` on the CDO → `apr0TotalPrincipal = X > 0`.
3. Manager updates APR for the next epoch early via `setAprs`/`setAprsWithBuffer` with `_apr > 0` (a routine operation; `setApr` is explicitly manager-callable).
4. Next epoch starts, runs, ends. `stopEpoch` is called → `prepareStopEpochWithApr0` reverts at `if (unscaledApr != 0) revert NotAllowed()` because `apr0TotalPrincipal != 0`.
5. Every retry reverts identically. `isEpochRunning` stays true, `_beforeUnpause` blocks unpausing, deposits remain paused, and `claimWithdrawRequest` can never satisfy `epochNumber > lastWithdrawRequest` because `epochNumber` only increments inside a successful `deposit()` during `stopEpoch`.

Existing guards don't help: the revert sits before `apr0TotalPrincipal` is reset, `_ensureDefaultRecoveryInitialized` only zeroes `apr0TotalPrincipal` when the pool is already closed (`epochEndDate == 0`, IdleCreditVault.sol:927-932) which can't happen because stopping requires this same function, and `claimWithdrawRequest` for the APR0 user reverts on the epoch gate (line 326) since `epochNumber` never advances — so users cannot self-clear the bucket.

### Impact Explanation
All LP principal and accrued interest (AA + BB) plus all pending withdraw/instant receipts are frozen indefinitely. The freeze is technically recoverable only if the manager diagnoses the issue and restores `unscaledApr = 0` via `setAprs(0, 0)` so `stopEpoch` can run — nothing in the code or comments documents this dependency, so in practice the freeze persists until manual remediation, and any APR>0 stop path is permanently unreachable while the bucket is open. Frozen amount = entire `getContractValue()` plus `pendingWithdraws`/`pendingInstantWithdraws`.

### Likelihood Explanation
Requires two conditions: the vault operates an epoch at APR 0 (an explicitly supported mode with dedicated accounting), and the manager changes APR while APR0 receipts are outstanding — a natural operational action with no warning in the code. The attacker's cost is one minimal deposit + withdraw request (dust-sized principal suffices, plus a Keyring credential). The attacker cannot raise the APR themselves, so exploitation is a forced-state/griefing bug rather than a single-transaction attack; this lowers likelihood but the result is deterministic once the state combination occurs.

### Recommendation
In `prepareStopEpochWithApr0`, either (a) settle the APR0 bucket at rate 0 instead of reverting when `unscaledApr != 0`, or (b) block out-of-band APR changes while `apr0TotalPrincipal != 0` inside `setApr`/`setAprs`/`setAprsWithBuffer`. Option (b) is the minimal fix: add `if (apr0TotalPrincipal != 0 && _apr != 0) revert NotAllowed();` to `setApr`, so the incompatible state can never be entered.

### Proof of Concept
```solidity
// Foundry fork test sketch against a live IdleCreditVault deployment at APR 0
function test_Apr0BucketBricksStopEpoch() public {
    // epoch N running with unscaledApr == 0, then buffer phase
    vm.warp(cdo.epochEndDate());
    // attacker: KYC'd EOA deposits and requests withdraw during buffer
    deal(underlying, attacker, 1e6);
    vm.startPrank(attacker);
    IERC20(underlying).approve(address(cdo), 1e6);
    cdo.depositAA(1e6);
    cdo.requestWithdraw(0, AA);            // routes to _requestWithdrawApr0
    vm.stopPrank();
    assertGt(vault.apr0TotalPrincipal(), 0);

    // honest manager raises APR before next stopEpoch
    vm.prank(manager);
    vault.setAprs(5e18, 5e18 * 35 days / 30 days);

    vm.prank(manager);
    cdo.startEpoch();
    vm.warp(cdo.epochEndDate() + 1);

    // every stopEpoch now reverts; epoch can never close
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdo.stopEpoch(0, 0);
}
```

Note: I was unable to fully verify there is no manager-side recovery path other than resetting `unscaledApr` to 0, and I did not confirm the exact signatures used in the repo's test helpers (`depositAA`/`requestWithdraw` argument order should be checked against `IdleCDOCreditVault.sol`). The core revert chain in `prepareStopEpochWithApr0` (lines 502-508) and the absence of any `apr0TotalPrincipal` guard in `setApr` (lines 225-235) are confirmed in the source.
