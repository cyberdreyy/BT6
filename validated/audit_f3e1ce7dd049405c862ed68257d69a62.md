### Title
Unbounded `bincode::deserialize` on attacker-controlled seed length prefix causes decoder panic/huge allocation for every `getTransaction(jsonParsed)` reader - ([File: transaction-status/src/parse_system.rs])

### Summary
`parse_system` in `transaction-status/src/parse_system.rs` calls raw `bincode::deserialize(&instruction.data)` with no size limit, unlike the runtime and CLI paths which use `solana_bincode::limited_deserialize` bounded by `PACKET_DATA_SIZE`. An attacker can submit a finalized System-program transaction whose `CreateAccountWithSeed`/`AllocateWithSeed`/`AssignWithSeed`/`TransferWithSeed` instruction data encodes a `String` (`seed`) with a bogus, oversized internal length prefix that does not match the actual remaining bytes in the ≤1232-byte instruction data, then have every subsequent `getTransaction`/`getConfirmedTransaction` call with `jsonParsed` encoding attempt to allocate/parse based on that untrusted length prefix.

### Finding Description
`parse_system` deserializes directly: [1](#0-0) 
without any length limit, in contrast to every other consumer of `SystemInstruction` in this codebase (`system_processor.rs`, `cost_model.rs`, `display.rs`) which all use `limited_deserialize(data, solana_packet::PACKET_DATA_SIZE as u64)`: [2](#0-1) [3](#0-2) [4](#0-3) 

The bounded variant is important because `SystemInstruction::CreateAccountWithSeed`, `AllocateWithSeed`, `AssignWithSeed`, and `TransferWithSeed` all embed a `String seed` field, which bincode decodes by first reading an 8-byte little-endian length prefix and then attempting to read/allocate that many bytes: [5](#0-4) [6](#0-5) 

Because the whole instruction data byte slice is limited only by the overall transaction wire-size limit (`PACKET_DATA_SIZE`, 1232 bytes, enforced at RPC ingestion in `decode_and_deserialize`): [7](#0-6) 
that 1232-byte budget bounds only the number of *bytes on the wire*, not the *value* encoded in the 8-byte length-prefix field itself. An attacker can therefore place an arbitrary 8-byte integer (e.g. a very large value) as the seed's length prefix while the instruction data is otherwise tiny. At execution time the runtime's `limited_deserialize` (bounded) will reject such a payload cheaply — returning an `InstructionError` — but the transaction is still included on-chain as a *failed* transaction (Agave records failed transactions with their raw instruction bytes intact), and is retrievable via `getTransaction` once finalized.

Later, any unprivileged client calling `getTransaction` (or `getConfirmedTransaction`) with `encoding=jsonParsed` triggers `parse_system`, which runs the *unbounded* `bincode::deserialize` on that same raw, attacker-controlled bytes. Since there is no bound check on the seed's untrusted length prefix before bincode attempts to size/allocate the destination buffer for the `String`, a crafted transaction can drive the decoder to attempt an outsized allocation (or hit bincode's internal capacity-overflow panic path) purely as a side effect of one RPC read, with no privileged access, no config change, and no more than one call needed per client.

This differs from the runtime and CLI decoders precisely because those already apply a `PACKET_DATA_SIZE`-bounded config (`limited_deserialize`) that fails fast when the encoded length exceeds the bound, before any large buffer is requested. `parse_system`, used by the JSON-RPC "jsonParsed" transaction encoder, has no equivalent guard.

### Impact Explanation
Every client, present and future, that requests `jsonParsed` encoding for this one maliciously-crafted (but validly signed and finalized) transaction repeats the unbounded deserialize and hits the same oversized-allocation/panic path — a decoder correctness/DoS bug matching the "unbounded cost/panic from a single low-rate query" bounty category. Because `getTransaction` is a permissionless, unauthenticated RPC method with no special quota beyond normal call-rate limits, this is reachable by any unprivileged client, and the failure recurs identically for anyone who later reads the same transaction (e.g. block explorers, indexers, other RPC nodes replaying jsonParsed decoding of the same ledger entry).

### Likelihood Explanation
Preconditions are minimal and fully within attacker capability: craft a `System` program instruction whose raw bytes decode structurally close enough to `CreateAccountWithSeed` (or another with-seed variant) to pass signature/format checks but embed a corrupted seed length prefix; submit it via `sendTransaction`; wait for it to be included and finalized (it can fail execution and still land on-chain); then trigger (or wait for another client to trigger) a single `getTransaction(..., {"encoding":"jsonParsed"})` call. No leader/validator control, no elevated privileges, and no more than one RPC call is required to repeat the impact indefinitely for that transaction's signature.

### Recommendation
Replace the unbounded `bincode::deserialize(&instruction.data)` in `parse_system` (and analogous unbounded deserializes elsewhere in `transaction-status` parsers, if any) with `solana_bincode::limited_deserialize(&instruction.data, solana_packet::PACKET_DATA_SIZE as u64)`, matching the pattern already used in `system_processor.rs`, `cost_model.rs`, and `cli-output/src/display.rs`, so any oversized/inconsistent length prefix is rejected with an `Err` before any allocation is attempted.

### Proof of Concept
```rust
// transaction-status/src/parse_system.rs (added test)
#[test]
fn test_parse_system_malformed_seed_length_prefix_does_not_panic_or_overallocate() {
    use solana_message::compiled_instruction::CompiledInstruction;

    // Manually build bytes that bincode will interpret as
    // SystemInstruction::CreateAccountWithSeed { base: Pubkey, seed: String, .. }
    // but with a seed length prefix (u64) far larger than the remaining bytes.
    let mut data = Vec::new();
    data.extend_from_slice(&3u32.to_le_bytes()); // enum discriminant for CreateAccountWithSeed
    data.extend_from_slice(&[0u8; 32]);          // base Pubkey
    data.extend_from_slice(&u64::MAX.to_le_bytes()); // bogus seed length prefix
    // no further bytes follow -- fewer bytes than the declared seed length

    let instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![0, 1],
        data,
    };
    let account_keys = AccountKeys::new(&[Pubkey::default(); 2], None);

    // Expectation: parse_system must return Err (InstructionNotParsable),
    // not panic ("capacity overflow"/OOM) and not attempt to allocate u64::MAX bytes.
    let result = std::panic::catch_unwind(|| parse_system(&instruction, &account_keys));
    assert!(result.is_ok(), "parse_system must not panic on malformed seed length prefix");
    assert!(result.unwrap().is_err(), "parse_system should reject malformed instruction data");
}
```
Additionally, a `cargo-fuzz` target should be added that feeds arbitrary/truncated/oversized-length-prefixed byte sequences into `bincode::deserialize::<SystemInstruction>` (the exact call used by `parse_system`) and asserts the process never panics and peak memory stays bounded, contrasting it with the same fuzz corpus run through `limited_deserialize::<SystemInstruction>(_, PACKET_DATA_SIZE as u64)` to confirm the bounded variant already rejects such inputs cheaply.
