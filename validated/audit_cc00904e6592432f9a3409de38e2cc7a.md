Based on my investigation, I found a plausible root-cause analog to the reported bug class (arithmetic operations on unsigned values that can be forced into an invalid/reverting state, blocking a required code path) in the destination-escrow withdrawal logic.

### Title
Unchecked fee-amount subtraction in `EscrowDst._withdraw` can underflow and permanently freeze maker funds - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw` computes the maker's payout as `immutables.amount - integratorFeeAmount - protocolFeeAmount` using unsigned arithmetic with no explicit check that the sum of fees does not exceed `immutables.amount` at the point of computation, mirroring the root cause in the referenced report: a value that must be allowed to be "negative" (fees exceeding the base amount) is instead computed with unsigned subtraction, causing a revert instead of a defined, safe outcome.

### Finding Description [1](#0-0) 

The relevant code:
```solidity
uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
...
uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
``` [2](#0-1) 

If `integratorFeeAmount + protocolFeeAmount > immutables.amount` for the immutables used to deploy a given `EscrowDst` clone, this line underflows and reverts, so `withdraw`, `publicWithdraw`, and the `_withdraw` internal call can never succeed for that escrow deployment (the `immutables` values are fixed/hashed at clone deployment and validated by `onlyValidImmutables`, so they cannot be corrected later).

On the source-chain path, `BaseEscrowFactory._postInteraction` does guard the analogous computation:
```solidity
if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();
``` [3](#0-2) 

This check happens during order fill on the *source* chain, when the resolver-supplied `extraData` (integrator/protocol fee recipients and encoded fee data) is processed to build the `ExtraDataArgs`/immutables. However, `createDstEscrow` is a separate call made directly by the resolver on the *destination* chain, and I was not able to fully confirm from the available indexed contents of `contracts/BaseEscrowFactory.sol` whether an equivalent `integratorFeeAmount + protocolFeeAmount < amount` check is independently enforced for the destination-side immutables before `EscrowDst` is deployed and funded.

### Impact Explanation
If the destination-chain fee-amount validation is missing or can be bypassed/mismatched relative to the source-chain check (e.g., a resolver supplies inconsistent `integratorFeeAmountCd`/`protocolFeeAmountCd` values when calling `createDstEscrow`, or the two checks are not perfectly symmetric), the resulting `EscrowDst` clone becomes permanently unwithdrawable: `withdraw`/`publicWithdraw` will always revert due to underflow, while `cancel` (which does not subtract fees) may still allow the taker to recover the deposited amount, but the maker can never receive their destination-chain tokens through the intended withdrawal path. This falls under the Medium/High impact categories in scope ("smart contract unable to operate... broken by an unprivileged actor," or "temporary/permanent freezing of funds during the live swap lifecycle").

### Likelihood Explanation
Uncertain/Low-to-Medium. This requires either (a) a bug or gap in destination-chain fee validation inside `createDstEscrow` that I could not fully verify with the remaining investigation budget, or (b) the resolver being able to independently choose destination-side fee-amount encodings that are not cross-checked against `immutables.amount`. If `createDstEscrow` mirrors the exact same `>=` guard seen in `_postInteraction` and enforces it against the correct `amount` field on the destination side, this finding does not apply and the invariant is preserved.

### Recommendation
Verify (or add, if missing) an explicit check in the destination-chain `createDstEscrow` path (in `contracts/BaseEscrowFactory.sol`) enforcing `integratorFeeAmount + protocolFeeAmount < immutables.amount` before deployment, matching the guard already present in `_postInteraction`. As a defense-in-depth measure, `EscrowDst._withdraw` could also independently validate this invariant (or cap the fee amounts) rather than relying solely on upstream validation, so that a future change to fee-encoding logic elsewhere cannot silently reintroduce this underflow-revert path.

### Proof of Concept
Not independently reproduced — this requires confirming, via `contracts/BaseEscrowFactory.sol`'s `createDstEscrow` implementation (not fully available in the indexed context retrieved), whether a resolver can supply/trigger destination immutables where `integratorFeeAmountCd() + protocolFeeAmountCd() > amount`. I recommend a Devin session with full repository/terminal access to read `createDstEscrow` in full and write a Foundry test that deploys an `EscrowDst` clone with such immutables and calls `withdraw` to confirm the revert-on-underflow and the resulting permanent freeze.
