## Analysis

The reported bug class is: a status change (liquidation) invalidates an actor's standing, but the code that grants privileges checks stale state instead of re-verifying the actor's current standing, letting accounting diverge from reality. The strongest reachable analog in this repository is in the **Multisig contract's key-revocation logic**, where a `confirm()` reaching the threshold can include a confirmation from a key that has already been revoked via `DeleteKey`, letting a request execute below the real, live-key threshold.### Title
Multisig request executes below the configured confirmation threshold because a revoked key's stale confirmation is not purged - (File: `multisig/src/lib.rs`)

### Summary
`MultiSigContract::execute_request`'s `DeleteKey` action only removes pending requests and confirmation sets for requests that the *deleted key itself originally added* (`r.signer_pk == pk`). It does not scan and strip confirmations that the deleted key placed on *other* pending requests it did not originate. `confirm()` then counts confirmations purely by set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) with no re-validation that every confirming public key is still a live access key on the account. A key that confirmed a pending request and is subsequently revoked still counts toward the threshold, letting the request execute with fewer genuinely live/authorized signatures than `num_confirmations` requires.

### Finding Description
The intended invariant of the K-of-N multisig is:
`confirmations counted == confirmations from currently-valid (live) keys`

`execute_request`'s `DeleteKey` branch breaks this invariant: [1](#0-0) 

It filters `self.requests` by `r.signer_pk == pk` — i.e. only requests where the deleted key was the *original request adder* — and clears `self.confirmations` solely for those matched requests. Any other pending request that the deleted key merely *confirmed* (but did not create) keeps that key's entry inside its `HashSet<PublicKey>` of confirmations forever, even though `promise.delete_key(pk)` has just revoked that key's access on-chain.

`confirm()` has no compensating check: [2](#0-1) 

It only asserts the confirming key hasn't already confirmed (`assert!(!confirmations.contains(&env::signer_account_pk())...)`) and then compares `confirmations.len() as u32 + 1` to `self.num_confirmations`. There is no lookup against the account's actual current access-key set (the README itself documents that near-sdk provides no way to query the account's live key set: "there is not having a way to query blockchain for current number of access keys on the account").

Consequently a request's approval count can include one or more keys that have since been deleted, so the request can be pushed over threshold and executed by live keyholders numbering strictly fewer than `num_confirmations`.

`multisig2/src/lib.rs`'s `delete_member` has the identical pattern — it filters `self.requests` by `r.member == member` (the request's original signer) before wiping confirmations, but never purges confirmations the deleted member placed on requests it did not originate: [3](#0-2) [4](#0-3) 

### Impact Explanation
This breaks an authorization/custody boundary: a `Transfer`, `FunctionCall`, `AddKey`, or `DeployContract` request can be executed with fewer live confirmations than the deployer configured via `num_confirmations`. This directly matches the Critical impact category "a multisig request executed below threshold" — NEAR held by the multisig account can be moved by a party set (live keys + one stale/revoked confirmation) that was never entitled to authorize the move under the current key set.

### Likelihood Explanation
Exploitation requires no privileged access beyond being one of the account's own keyholders (the multisig's normal actor set) — no owner, foundation, or external party is needed. It requires a realistic and expected lifecycle event: revoking a key (e.g., an employee leaving, or a suspected-compromised key being rotated out) while that key has an outstanding, unexecuted confirmation on some other pending request. Any such revocation silently leaves a "ghost vote" in place; any subsequent legitimate-looking `confirm()` from a remaining live key can then complete execution below the intended threshold. Because there is no window in which this state is detected or repaired (no view method flags a "stale confirmation"), the condition persists indefinitely until the affected request is either executed or explicitly deleted.

### Recommendation
When executing `DeleteKey` (multisig v1) / `DeleteMember` (multisig2), iterate all pending requests (not just those the deleted key originated) and remove the deleted key/member from every `confirmations` set it appears in. Alternatively, at `confirm()`/`execute_request` time, re-validate that every public key in a request's confirmation set still corresponds to a currently valid access key/member before counting it toward `num_confirmations`.

### Proof of Concept
Assume a 2-of-3 multisig with keys `K1`, `K2`, `K3`, `num_confirmations = 2`.

1. `K1` calls `add_request(request_R)` where `request_R = Transfer{amount}` targeting some receiver. This creates `MultiSigRequestWithSigner{ signer_pk: K1, ... }` with empty confirmations (`multisig/src/lib.rs:116-146`).
2. `K2` calls `confirm(request_R)`. `confirmations.len() (0) + 1 = 1 < 2`, so `confirmations = {K2}` is stored (`multisig/src/lib.rs:246-266`). `request_R` is still pending, not yet executed.
3. Separately, the account's keyholders decide to revoke `K2` (e.g. compromised/departing key) by getting 2-of-3 confirmations on a new request `request_D = DeleteKey{public_key: K2}` (added and confirmed by `K1` and `K3`). This executes `execute_request`, hitting the `DeleteKey` branch (`multisig/src/lib.rs:198-216`): it filters `self.requests` for entries where `signer_pk == K2` — `request_R` was added by `K1`, so it is *not* matched — and only calls `promise.delete_key(K2)`. `request_R`'s confirmation set `{K2}` is left untouched in storage.
4. `K2`'s access key is now deleted on-chain (per the executed `delete_key` promise action), and `K2` can no longer sign transactions for this account.
5. `K1` (or `K3`) calls `confirm(request_R)`. `confirmations.len() (1, still containing stale K2) + 1 = 2 >= num_confirmations(2)`, so `request_R` executes the `Transfer` — approved by only one genuinely live key (`K1`) plus a phantom confirmation from the now-deleted `K2`, i.e. below the real 2-of-3 threshold.

This lets a single remaining live keyholder (in collusion with, or simply after, a revoked co-signer's earlier confirmation) push through a transfer that the current, live key set never actually authorized to the required threshold.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
