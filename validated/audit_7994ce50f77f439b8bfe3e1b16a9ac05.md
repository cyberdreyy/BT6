### Title
Unhandled Missing Slot-Entry Lookup Permanently Kills the StackerDB Listener Thread, Wedging the Signer Coordinator - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run()` terminates the entire listener thread (returning a fatal `Err`) the moment it receives a signer message whose `slot_id` is not present in the coordinator's `signer_entries` map, rather than skipping that single malformed/stale message. This is functionally the same bug class as the reported Shardeum crash: unvalidated network-controlled input (`slot_id`) reaches a lookup with no defensive handling, and the failure path aborts the entire message-processing loop instead of gracefully discarding the offending item.

### Finding Description
`self.signer_entries` is a `HashMap<u32, NakamotoSignerEntry>` captured once, at coordinator start-up, from the `RewardSet` snapshot passed into `StackerDBListener::new()`: [1](#0-0) 

In the main receive loop, every incoming signer message's `slot_id` (taken directly from the StackerDB chunk, i.e., attacker/network-influenced metadata, not validated against the current membership) is looked up in that fixed map. If the lookup fails, the function returns an `Err`, unwinding out of the `loop` and out of `run()` entirely: [2](#0-1) 

Every other malformed/unexpected condition in this same loop (bad signature, unknown block hash, wrong signer_set, deserialization failure) is handled with `continue`/`warn!`/`debug!` — only this one lookup treats a mismatch as fatal to the whole loop.

The caller spawns `listener.run()` in a dedicated thread and, on `Err`, only logs it — it does **not** respawn or otherwise recover the listener: [3](#0-2) 

Because `signer_set` is only compared by parity (`reward_cycle_id % 2`), not by exact reward-cycle number, a chunk belonging to a different (but same-parity) reward cycle's signer membership can pass the `signer_set != self.signer_set` guard while carrying a `slot_id` that no longer exists (or never existed) in the coordinator's cached `signer_entries`: [4](#0-3) 

Once the thread dies, `SignerCoordinator::propose_block` / `get_block_status` keep polling `stackerdb_comms.wait_for_block_status(...)`, but no further updates will ever arrive since the producer thread is gone — the coordinator is permanently wedged for the remainder of its lifetime (until the whole miner/coordinator is torn down and rebuilt for a new tenure): [5](#0-4) 

### Impact Explanation
This breaks the liveness property the rules define as in-scope High impact: the node-side coordinator that gathers signer accept/reject votes stops processing all further signer messages after a single anomalous/stale chunk. The miner will never again observe accepted or rejected signatures for that tenure, causing every subsequent `propose_block` call to run out its rejection/timeout logic blind, effectively stalling block confirmation on that node until a full restart of the coordinator. This directly mirrors the reported vulnerability's effect (one crafted/unexpected input silently kills the message-processing loop, producing a standing denial of block-confirmation capability).

### Likelihood Explanation
No signature or authentication forgery is needed — the trigger is purely a `slot_id` value that falls outside a `HashMap` populated from a point-in-time reward-set snapshot. This can occur from perfectly legitimate reward-cycle-boundary conditions (parity reuse of `signer_set` every other cycle combined with reward-set/signer-count changes), or from any StackerDB chunk delivered with a slot metadata mismatch relative to the coordinator's cached view. Unlike the other rejection/error branches in the same loop, this single path was written to be fatal rather than defensive, so once such a mismatch happens it is deterministic and 100% reproducible for that coordinator instance.

### Recommendation
Replace the `return Err(...)` on missing `signer_entries.get(&slot_id)` with a `continue` (mirroring the handling of every other malformed-input case in this loop), and log a `warn!` including the reward cycle/slot id for diagnostics. Additionally, validate the exact reward-cycle id (not just parity) when filtering `signer_set`, so stale same-parity cycle messages are dropped before reaching the slot-entry lookup.

### Proof of Concept
1. Start a `StackerDBListener` for reward cycle `N` (signer_set = `N % 2`), which caches `signer_entries` for the signer count/membership active at cycle `N`.
2. Have any registered signer (or a lingering pre-rotation writer) deliver a chunk on the `.signers-*` StackerDB contract for a same-parity cycle whose corresponding `slot_id` is not present in the cycle-`N` `signer_entries` map (e.g., a slot index beyond the current signer count, reachable if the signer set shrank between cycle `N-2` and `N`).
3. `StackerDBListener::run()` hits the `let Some(signer_entry) = &self.signer_entries.get(&slot_id) else { return Err(...) }` branch and exits.
4. `SignerCoordinator::new`'s spawned thread logs `"StackerDBListener: exited with error"` and terminates; no thread is respawned.
5. All subsequent `SignerCoordinator::propose_block` calls on that node now poll a `stackerdb_comms` that will never receive new updates, permanently stalling that node's ability to gather signer signatures until it is restarted.
