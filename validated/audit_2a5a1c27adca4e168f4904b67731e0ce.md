## Title
Missing zero-address validation in `set_beneficiary_for_operator` permanently strands operator commission at `0x0` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`, `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
Both `staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` let an operator redirect their future commission payouts to an arbitrary `new_beneficiary: address` with **no validation whatsoever** — not even a check that the address is non-zero. This is the exact bug class from the external report (missing zero checks on a "destination"-style parameter), applied to Aptos' staking commission/beneficiary flow.

### Finding Description
`staking_contract::set_beneficiary_for_operator` unconditionally stores whatever address is passed: [1](#0-0) 

Every subsequent commission distribution looks up this beneficiary and routes the operator's share there via `aptos_account::deposit_coins`: [2](#0-1) 

The identical unguarded pattern exists in the delegation-pool beneficiary flow, which similarly stores `new_beneficiary` with no validation before it is used to route commission: [3](#0-2) 

By contrast, the vesting module's own `set_beneficiary` (a sibling beneficiary-setting function operating on shareholder distributions) explicitly guards against exactly this failure mode by requiring the target account to already be registered for APT before accepting it as a beneficiary: [4](#0-3) 

`staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` have no equivalent guard. `aptos_account::deposit_coins` will transparently create and register an account at any unregistered address, including `0x0`, so the call does not abort — it silently succeeds and locks funds at an address for which no one holds signing authority.

### Impact Explanation
If an operator (or a front end acting on the operator's behalf, per the exact "buggy front end" scenario described in the external report) calls `set_beneficiary_for_operator` with `@0x0` — whether due to an uninitialized variable, a copy/paste error, or a compromised client — every future commission distribution for that operator's staking contract or delegation pool is deposited to `0x0`. Since no private key controls `0x0`, this permanently and irrecoverably strands the operator's commission rewards. This satisfies the "permanent lock or non-recoverable loss of claim rights in ... commission [or] beneficiary ... flows" impact category, and can recur indefinitely on every subsequent `distribute`/`synchronize_delegation_pool` call for the affected operator until a new beneficiary is set — but any already-distributed commission is unrecoverable.

### Likelihood Explanation
The function is `public entry`, callable by any operator on their own account with a single argument, requiring no elevated privilege — matching the report's "unprivileged user" threat model. The likelihood mirrors the external report's exploit scenario almost exactly (a front-end bug supplying a default/zero address for a destination-like parameter), and Aptos' own vesting module already demonstrates that this is a recognized risk class the team validates against in a sibling function, but the fix was not applied consistently to `staking_contract` / `delegation_pool`.

### Recommendation
Add a validation check to `staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` that rejects `new_beneficiary == @0x0` (and ideally mirrors `vesting::set_beneficiary`'s `assert_account_is_registered_for_apt`/reserved-address checks) before storing the new beneficiary.

### Proof of Concept
1. Operator `O` owns a staking contract with a staker and accrues commission.
2. `O` calls `staking_contract::set_beneficiary_for_operator(O, @0x0)` (e.g., via a front end that fails to populate the beneficiary field and defaults to zero). This succeeds with no abort. [1](#0-0) 
3. On the next `distribute` call, the operator's commission share is computed and, because `recipient == operator`, redirected to `beneficiary_for_operator(operator)` = `@0x0`, then deposited via `aptos_account::deposit_coins`. [5](#0-4) 
4. The coins are now held at `0x0`, an address with no controlling signer — permanently unrecoverable by `O` or the staker.

**Note on verification limits:** I was unable to fully confirm within the indexed content whether `account::create_account`/`aptos_account::deposit_coins` contains any special-case rejection of `0x0` specifically (as opposed to the named framework reserved addresses 0x1–0xA checked elsewhere via `system_addresses::is_reserved_address`). If such a special-case check exists deeper in `account.move` and is not indexed here, the described PoC step 3 could abort instead of succeeding, which would reduce the severity of this finding to only untested address ranges. I recommend confirming this specific behavior in a full checkout of `account.move`'s `create_account` implementation before treating this as fully confirmed.

    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
