### Title
Sortition inactivity timeout can be indefinitely suppressed by a miner cycling never-signed pre-commits, permanently blocking the timeout fallback - ([File: stacks-signer/src/chainstate/mod.rs], [File: stacks-signer/src/chainstate/v2.rs], [File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionState::is_timed_out` (chainstate/v1.rs, chainstate/v2.rs) correctly no longer treats a merely `PreCommitted` (unsigned) block as proof of signing progress via `has_signed_block_in_tenure`, but it falls back to `get_last_activity_time`, which is refreshed by `SortitionData::check_latest_block_in_tenure` (chainstate/mod.rs) any time a new proposal conflicts with a still-"fresh" pre-commit. Because a miner can keep replacing its own never-signed pre-committed proposal with a new one before the previous pre-commit's freshness window expires, `last_activity` can be kept perpetually current without a single signature ever being produced, defeating the exact fallback mechanism this guard was fixed to preserve.

### Finding Description
The intended equality is: *"sortition is timed out" ⇔ "no forward signing progress has occurred in this tenure for `block_proposal_timeout`."* `is_timed_out` implements this as `!has_signed_block_in_tenure(tenure) && (now - last_activity) > timeout` [1](#0-0) [2](#0-1) 

`has_signed_block_in_tenure` was already hardened to exclude `PreCommitted` blocks (only `signed_self`/`signed_group` count), so a lone pre-commit cannot suppress the timeout by itself [3](#0-2) . The remaining leak is `last_activity`, updated inside `check_latest_block_in_tenure`: whenever a *new* competing proposal at the same or lower height conflicts with the tenure's currently pre-committed block, and that pre-commit is still "fresh" (`approved_time + tenure_last_block_proposal_timeout > now`), the code calls `update_last_activity_time(tenure, now)` before evaluating the new proposal against the node [4](#0-3) .

Because the node has never confirmed any block for this tenure (nothing reached the 70% signature threshold), `client.get_tenure_tip(tenure_id)` typically errors, and the function falls back to `Ok(true)` ("assume higher") [5](#0-4) , so the new competing proposal is accepted into validation, and — if it also passes the node's stateless validation and `check_block_against_signer_db_state` — it is itself marked `PreCommitted` with a fresh `approved_time` [6](#0-5) . This new pre-commit becomes the next "fresh reference" that the *next* competing proposal's activity-refresh check will fire against.

Attacker flow (single miner slot, crafted `BlockProposal`s only, no majority of signers required):
1. Win a sortition. Propose block P1 at height h. Signers validate it and reach `PreCommitted` (never 70% pre-commit weight, since the attacker never lets consensus converge).
2. Before `tenure_last_block_proposal_timeout` elapses since P1's `approved_time`, propose a distinct conflicting block P2 at the same height h (e.g., different timestamp/txs). Each signer's `check_latest_block_in_tenure` sees P1 as a fresh pre-commit, calls `update_last_activity_time(tenure, now)`, and — since the tenure tip is unconfirmed — accepts P2 into validation, which itself gets `mark_pre_committed` with a new `approved_time`.
3. Repeat with P3, P4, ... at a cadence faster than `min(tenure_last_block_proposal_timeout, block_proposal_timeout)`.
4. `has_signed_block_in_tenure` stays `false` throughout (no `signed_self`/`signed_group` ever set), yet `elapsed = now - last_activity` never exceeds `block_proposal_timeout`, so `is_timed_out` never returns true.

`check_miner_inactivity` (v0/signer_state.rs) calls `is_timed_out` and only falls back to the prior miner's tenure when it returns true [7](#0-6) ; with the guard permanently defeated, this fallback never fires for the duration of the attack.

The existing guards (`is_fresh_pre_commit`'s bound by `tenure_last_block_proposal_timeout`, the reorg conflict checks in section 5/7 of the pre-commit path) bound each *individual* pre-commit's freshness window but do not bound the *cumulative* number of times a miner can re-arm that window with a brand-new (still unsigned) pre-commit — the code explicitly treats any conflicting-but-plausible proposal as valid miner activity ("the miner may just be slow") [8](#0-7) , without distinguishing genuine slow progress from repeated non-converging churn.

### Impact Explanation
This breaks a liveness guarantee, matching the High category "a signer wedged into never signing valid blocks (liveness)." While the miner sustains the churn, `check_miner_inactivity`'s fallback to the prior tenure never triggers, so signers keep waiting on the current (uncooperative) miner instead of reverting to a miner that can actually produce a confirmable block. This stalls all transaction processing for that tenure's duration. It is repeatable: any account that wins a miner slot with its own BTC can execute it, on every tenure it wins, using only the crafted-proposal capability explicitly permitted to the attacker.

### Likelihood Explanation
Preconditions are modest and within the stated attacker capability: control of the current miner slot (own BTC, no signer collusion needed) and the ability to gossip distinct `BlockProposal`s. No node operator or signer privileges, no auth token, and no majority of signer weight are required — the attack specifically depends on consensus *not* being reached. Feasibility hinges on proposing new conflicting blocks faster than `min(tenure_last_block_proposal_timeout, block_proposal_timeout)`, both node-configurable but by default well within a normal miner's proposal cadence, making the attack practically low-cost and repeatable every tenure the attacker wins.

### Recommendation
Do not treat pre-commit-driven "miner activity" refreshes as unlimited: cap the total time (or number of successive un-converged pre-commits) that `last_activity` can be refreshed purely by conflicting/never-signed pre-commits within a single tenure, independent of individual pre-commit freshness windows — e.g., track the tenure's *first* pre-commit time and require `is_timed_out` to fire once `now - first_pre_commit_time` exceeds a bound even if `last_activity` keeps being nudged, unless genuine forward progress (an actual signature, i.e., `has_signed_block_in_tenure`) is observed.

```rust
fn is_timed_out_never_fires_under_pre_commit_churn() {
    let signer_db_path = tmp_db_path();
    let mut signer_db = SignerDb::new(signer_db_path).unwrap();

    let consensus_hash = ConsensusHash([1; 20]);
    let burn_hash = BurnchainHeaderHash([1; 32]);
    signer_db
        .insert_burn_block(&burn_hash, &consensus_hash, 1, &SystemTime::now(), &BurnchainHeaderHash([0; 32]))
        .unwrap();

    let address = StacksAddress::p2pkh(false, &StacksPublicKey::new());
    let mut address_weights = HashMap::new();
    address_weights.insert(address.clone(), 10);
    let eval = GlobalStateEvaluator::new(HashMap::new(), address_weights);

    let timeout = Duration::from_secs(5);
    let tenure_last_block_proposal_timeout = Duration::from_secs(3);

    // Simulate the attacker cycling conflicting, never-signed pre-commits faster
    // than tenure_last_block_proposal_timeout, each with a fresh approved_time,
    // mirroring update_last_activity_time being called by check_latest_block_in_tenure.
    for i in 0..5u8 {
        let mut block_info = /* build BlockInfo at same chain_length, distinct hash, i as differentiator */;
        block_info.mark_pre_committed().unwrap(); // fresh approved_time = now
        signer_db.insert_block(&block_info).unwrap();

        // Assert: still no signature over the tenure.
        assert!(!signer_db.has_signed_block_in_tenure(&consensus_hash).unwrap());

        // Simulate the activity refresh check_latest_block_in_tenure performs
        // against this fresh pre-commit for the NEXT conflicting proposal.
        signer_db.update_last_activity_time(&consensus_hash, get_epoch_time_secs()).unwrap();

        std::thread::sleep(tenure_last_block_proposal_timeout - Duration::from_secs(1));

        // WEDGE: despite `timeout` having elapsed cumulatively across iterations
        // and no signature ever placed, is_timed_out must never return true.
        assert!(!SortitionState::is_timed_out(
            &consensus_hash, &signer_db, &eval, &address, timeout
        ).unwrap());
    }

    // Total elapsed time now exceeds `timeout` several times over, yet:
    assert!(!signer_db.has_signed_block_in_tenure(&consensus_hash).unwrap());
    assert!(!SortitionState::is_timed_out(
        &consensus_hash, &signer_db, &eval, &address, timeout
    ).unwrap(), "inactivity fallback permanently suppressed with zero signing progress");
}
```

```rust
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
```

```rust
    /// Return whether this signer has signed a block, or observed the signer set sign a block,
    /// in a tenure (identified by its consensus hash). Used by `is_timed_out` to keep a tenure
    /// we are committed to from being timed out.
    ///
    /// Unlike [`SignerDb::has_approved_block_in_tenure`] this excludes blocks that were only
    /// pre-committed. A pre-commit does not put a signature over the block, so it does not
    /// represent a commitment that would be violated by abandoning the tenure.
    ///
    /// Rejection, even global rejection, does NOT clear the commitment. A rejection is a
    /// revocable opinion; a signature is a bearer instrument. Once ours is public, anyone can
    /// aggregate it toward the 70% threshold should enough rejecting signers change their
    /// minds, so a block we signed binds us to its tenure no matter what state it later fell
    /// to. This is deliberately a different predicate from
    /// [`SignerDb::get_last_signed_block`], which answers a tip question rather than a
    /// commitment question (see there).
    pub fn has_signed_block_in_tenure(&self, tenure: &ConsensusHash) -> Result<bool, DBError> {
        let query = "SELECT 1 FROM blocks WHERE consensus_hash = ? AND (signed_self IS NOT NULL OR signed_group IS NOT NULL) LIMIT 1;";
        let result: Option<u64> = query_row(&self.db, query, [tenure])?;

        Ok(result.is_some())
    }
```
