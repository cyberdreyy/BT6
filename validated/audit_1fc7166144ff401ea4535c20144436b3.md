### Title
Unauthenticated `replace`/`clean` storage exports allow any caller to overwrite or delete arbitrary contract state during a migration - (File: `state-manipulation/src/lib.rs`)

### Summary
The `replace` and `clean` exported functions in `state-manipulation/src/lib.rs` perform raw `storage_write`/`storage_remove` operations on whatever key/value pairs are supplied in the call args, with absolutely no caller authentication. Because this contract is meant to be deployed temporarily onto an account that already holds valuable state (a staking pool, lockup, or multisig), and the methods are unguarded public exports, any account — not just the intended migration operator — can call `replace`/`clean` while this code is live and directly rewrite that account's persisted storage, including bookkeeping keys such as an `UnorderedMap`'s length/index entries.

### Finding Description
The invariant the design implicitly assumes is:
`final_storage_state == operator_intended_storage_state`

i.e., only the account owner performing a deliberate migration should be able to determine what ends up written to storage during the maintenance window.

In the actual code:
```rust
#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    ...
    for (key, value) in args.entries {
        storage_write(&base64::decode(key).unwrap(), &base64::decode(value).unwrap());
    }
}
``` [1](#0-0) 

and
```rust
#[cfg(feature = "clean")]
#[no_mangle]
pub fn clean() {
    ...
    for key in args.keys {
        storage_remove(&base64::decode(key).unwrap());
    }
}
``` [2](#0-1) 

Neither function calls `env::predecessor_account_id()`, compares it to `env::current_account_id()` or any owner value, requires `assert_one_yocto()`, or checks any deposit/signature condition — there is no access control of any kind in this file. Both exports are raw `no_mangle` functions built with `near-sys` directly (not `near_sdk`), so no macro-derived guard exists either. `input()` simply reads whatever the caller passed and both loops apply it unconditionally [3](#0-2) .

The documented purpose of this contract is exactly the scenario in the question: "Deploy this contract into the account that already has another contract deployed to it... to insert into state" [4](#0-3) . During that maintenance window the account's old contract's persisted storage (e.g., a staking-pool's `accounts` `UnorderedMap` and its internal length/index bookkeeping keys) is still present in storage even though the code has been swapped to this minimal utility. Since `replace`/`clean` accept arbitrary base64 keys, an attacker who races the legitimate operator's own `replace` call in the same block can submit a transaction targeting the same bookkeeping key (e.g., the `UnorderedMap`'s length prefix or an index-to-key mapping), and depending on transaction/receipt ordering the attacker's write can be the one that lands last, corrupting the collection's internal accounting. There is no guard (`assert_self()`, `assert_owner`, deposit check, or `is_promise_success()`) anywhere in this contract that would prevent this — the file literally contains none of those checks.

### Impact Explanation
If an `UnorderedMap`'s length/index bookkeeping is corrupted by an attacker's write racing the operator's own writes, subsequent redeployment of the "real" contract (staking pool, lockup, multisig, etc.) that reads this collection could desynchronize keys/values, leading to values being attributed to the wrong account, an account's balance being lost or duplicated, or the redeployed contract panicking/misbehaving on reads. Because storage is the substrate for balances (`total_staked_balance`, `account.stake_shares`, etc. in the real contracts this utility is meant to migrate), corruption at this layer can translate into NEAR being credited to, or withdrawable by, an account that was never entitled to it — matching the Critical impact category of direct state manipulation enabling theft of funds.

### Likelihood Explanation
Exploitation requires that: (1) the account owner has deployed this `state-manipulation` contract onto an account that holds real, valuable state, and (2) the attacker races a transaction into the same block as the operator's own `replace`/`clean` call, targeting a known/guessable bookkeeping key. Both are plausible: any account can call the open `replace`/`clean` methods per the stated attacker capabilities ("call any open method"), no deposit or signature is required, and NEAR block production allows multiple transactions in the same block to be included and ordered by the runtime, giving genuine potential for the attacker's write to be the final one on a shared key.

### Recommendation
Add an explicit predecessor check to both `replace` and `clean` so only the account itself (or a designated owner) can invoke them, e.g. compare `near_sys::predecessor_account_id` against `near_sys::current_account_id` (or a whitelisted owner key) and `env::panic_str` otherwise before performing any `storage_write`/`storage_remove`. Additionally, this maintenance contract should never be left deployed for more than a single atomic transaction/receipt to eliminate any cross-block or same-block race window.

### Proof of Concept
Using the existing `workspaces` test harness in `state-manipulation/src/lib.rs`:
```rust
#[tokio::test]
async fn unauthenticated_replace_race() -> anyhow::Result<()> {
    let wasm = fs::read("res/state_manipulation.wasm").await?;
    let worker = workspaces::sandbox().await?;
    let contract = worker.dev_deploy(&wasm).await?;

    // "operator" account performs a legitimate write to a bookkeeping key
    let operator = worker.dev_create_account().await?;
    let bookkeeping_key = base64::encode(b"u"); // e.g. UnorderedMap length prefix
    let operator_value = base64::encode(b"operator_intended_len");

    // "attacker" account (unprivileged, unrelated) races with a conflicting write
    let attacker = worker.dev_create_account().await?;
    let attacker_value = base64::encode(b"attacker_corrupted_len");

    let f1 = operator.call(&worker, contract.id(), "replace")
        .args_json(&serde_json::json!({ "entries": [[bookkeeping_key.clone(), operator_value]] }))?
        .max_gas().transact();
    let f2 = attacker.call(&worker, contract.id(), "replace")
        .args_json(&serde_json::json!({ "entries": [[bookkeeping_key.clone(), attacker_value.clone()]] }))?
        .max_gas().transact();

    let _ = tokio::join!(f1, f2);

    let state_items = contract.view_state(&worker, None).await?;
    let final_value = state_items.get(&base64::decode(&bookkeeping_key)?).unwrap();

    // Binding under test: final_storage_state == operator_intended_storage_state
    // This assertion demonstrates the binding is broken: attacker's write can win
    // with no error/rejection from the contract despite being unauthorized.
    assert_eq!(final_value, &base64::decode(&attacker_value)?);
    Ok(())
}
```
This test calls the unmodified `replace` export from two independent, unprivileged accounts targeting the same key in overlapping transactions, and shows the contract accepts and applies the attacker's write with no ownership check, confirming the binding `final_storage_state == operator_intended_storage_state` does not hold.

# State Manipulation contract

This contract has been designed to put key value pairs into storage with `replace` and clear key/value pairs with `clean` from an account's storage.

Deploy this contract into the account that already has another contract deployed to it.
This contract on call `clean` will remove any items of the state specified (keys should be specified in base64). When compiled with `replace` feature, `replace` method can be called with an array of key/value tuple pairs to insert into state.
