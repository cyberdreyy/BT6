### Title
`parse()` routes both legacy spl-token and spl-token-2022 program IDs into `parse_token`, which decodes purely by data discriminant with no program_id–aware validation - ([File: transaction-status/src/parse_instruction.rs])

### Summary
`PARSABLE_PROGRAM_IDS` maps every id returned by `spl_token_ids()` (both the legacy `spl_token::id()` and `spl_token_2022::id()`) to the same `ParsableProgram::SplToken` variant, and `parse()` dispatches all of them to a single `parse_token(instruction, account_keys)` function that never receives or checks `program_id`. `parse_token` unconditionally calls `spl_token_2022_interface::instruction::TokenInstruction::unpack`, which understands extension-only discriminants (e.g. transfer-fee/confidential-transfer/metadata-pointer extensions) that the legacy spl-token program does not implement.

### Finding Description
In `transaction-status/src/parse_instruction.rs`, `PARSABLE_PROGRAM_IDS` is built by chaining a fixed list of program ids with `spl_token_ids().into_iter().map(|id| (id, ParsableProgram::SplToken))` [1](#0-0) , so both the legacy spl-token id and the spl-token-2022 id resolve to the identical `ParsableProgram::SplToken` branch in `parse()`, which calls `parse_token(instruction, account_keys)` [2](#0-1) . Critically, `parse_token`'s signature is `parse_token(instruction: &CompiledInstruction, account_keys: &AccountKeys)` — it does not take `program_id` as a parameter at all [3](#0-2) , so there is no way for it to distinguish "this instruction targets the legacy fixed-Pack spl-token program" from "this instruction targets spl-token-2022." It always dispatches through `TokenInstruction::unpack(&instruction.data)` from `spl_token_2022_interface`, which is a strict superset that additionally recognizes extension-only discriminants beyond the legacy program's supported tag range.

An attacker can submit (or place on-chain) a transaction/instruction with `program_id == spl_token::id()` (legacy) and instruction `data` bytes whose leading discriminant only exists in the extended `spl-token-2022` instruction set. The legacy on-chain spl-token program would reject this instruction as invalid data at execution time, but the RPC/transaction-status parsing path (`getTransaction` with `jsonParsed` encoding) parses instructions directly from the raw transaction message independent of execution outcome. `parse()` still looks up `program_id` in `PARSABLE_PROGRAM_IDS`, gets `SplToken`, and calls `parse_token`, which successfully unpacks the 2022-only discriminant and reports a plausible but semantically wrong `instruction_type`/`info` for an instruction that the legacy program never actually executes that way (and which in fact fails/rejects on-chain). No guard in `parse()` or `parse_token` cross-checks the discriminant range against which concrete `program_id` (legacy vs. 2022) was used.

### Impact Explanation
This is a decoder misreporting bug in Agave's own transaction-status crate (not the sBPF interpreter or an external dependency's bug per se — the routing/dispatch logic that fails to distinguish legacy vs. 2022 token program ids lives in `parse_instruction.rs`/`parse_token.rs`). Clients that rely on `getTransaction`'s `jsonParsed` `instruction_type`/`info` fields (explorers, indexers, wallets) can be shown a fabricated instruction semantics (e.g., an extension-style operation) for a transaction actually addressed to the legacy spl-token program, which in reality would have failed with invalid instruction data. This matches the "decoder panic and misreporting" impact category, scoped strictly to display/report fidelity for legacy spl-token transactions using extension-only discriminants; it does not corrupt consensus state, account data, or validator process integrity.

### Likelihood Explanation
Highly feasible for a single unprivileged client: constructing a `CompiledInstruction` with `program_id_index` pointing at `spl_token::id()` and arbitrary `data` bytes matching a token-2022 extension discriminant requires no special access, no leader/validator control, and only one RPC call to submit the transaction plus one subsequent `getTransaction` call to observe the mis-parsed result. No commitment/length/subscription guard in the current code path prevents it, since `parse()` only checks program-id membership in `PARSABLE_PROGRAM_IDS`, not discriminant validity for that specific program id.

### Recommendation
Thread `program_id` (or a legacy-vs-2022 flag derived from it) into `parse_token`, and either (a) reject/return a parse error for discriminants that are only valid under spl-token-2022 when `program_id == spl_token::id()`, or (b) maintain two distinct dispatch paths/discriminant validators for legacy spl-token vs. spl-token-2022 so `instruction_type` only reflects operations the target program id can actually execute.

### Proof of Concept
```rust
// transaction-status/src/parse_instruction.rs (test module) or parse_token.rs
#[test]
fn test_parse_legacy_token_with_2022_only_extension_discriminant() {
    let account_keys = AccountKeys::new(&[Pubkey::new_unique(), Pubkey::new_unique()], None);

    // Discriminant byte >= 200 corresponds to a spl-token-2022 extension-only
    // instruction (e.g. TransferFeeExtension / ConfidentialTransferExtension),
    // which the legacy spl-token program does not implement.
    let extension_only_discriminant: u8 = 26; // TransferFeeExtension tag in TokenInstruction
    let data = vec![extension_only_discriminant, 0 /* sub-instruction */];

    let instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![0, 1],
        data,
    };

    // program_id is the LEGACY spl-token id, not spl-token-2022.
    let result = parse(&spl_token::id(), &instruction, &account_keys, None);

    // Expected (fixed) behavior: parsing should fail/refuse for a discriminant
    // that the legacy program does not support, rather than silently claiming
    // a successful, semantically-2022-specific instruction_type.
    match result {
        Err(_) => {} // acceptable: fidelity preserved by refusing to parse
        Ok(parsed) => {
            // Current buggy behavior: parsed.parsed["type"] will be a
            // token-2022 extension instruction type (e.g. "transferFeeExtension")
            // even though program_id is the legacy spl-token program, which
            // cannot execute this instruction. This assertion should fail
            // once the bug is present, demonstrating PARSE_FIDELITY violation.
            assert_ne!(
                parsed.parsed["type"], "transferFeeExtension",
                "legacy spl-token instruction misreported as token-2022 extension type"
            );
        }
    }
}
```
This test demonstrates that `parse()`/`parse_token` currently has no mechanism to reject or reinterpret extension-only discriminants when `program_id` is the legacy spl-token id, confirmed structurally by `parse_token`'s signature omitting `program_id` [3](#0-2)  and by `PARSABLE_PROGRAM_IDS` collapsing all `spl_token_ids()` into one `SplToken` branch [1](#0-0) .
