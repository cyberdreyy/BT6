## Analysis

Tracing `vesting::update_operator` → `staking_contract::switch_operator`, the bug is real but is a **wrong-recipient / mis-attributed-commission bug**, not a "loss due to distribute/request_commission race" as framed in the question. It stems from how `distribute_internal`'s beneficiary substitution is keyed.

### Root cause

`switch_operator` does the following, in order, on the *same* `StakingContract` (and its `distribution_pool`) that gets re-keyed from `old_operator` to `new_operator`: [1](#0-0) 

1. `distribute_internal(staker, old_operator, &mut staking_contract)` — pays out any *already inactive* pending distributions. Here the redirect check works correctly because `operator == old_operator` matches the stored shareholder key: [2](#0-1) 

2. `request_commission_internal(old_operator, &mut staking_contract)` — computes the commission accrued up to the switch and calls `add_distribution(operator, staking_contract, recipient=operator, commission_amount)`, i.e. it buys `old_operator`'s address into the `distribution_pool` as a shareholder, and calls `stake::unlock_with_cap` (moves stake to `pending_inactive`, not yet withdrawable): [3](#0-2) 

3. `stake::set_operator_with_cap(new_operator)` then the *same* `StakingContract` object (still holding the pending share keyed to `old_operator`'s address) is inserted into the map under `new_operator`.

Because that commission just requested in step 2 is still locked, it cannot be paid out inside `switch_operator` itself. It is only paid later when someone calls `distribute(staker, new_operator)`. At that point, `distribute_internal` is invoked with `operator = new_operator`, but the pending shareholder key in the pool is still `old_operator`'s address:

```
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
```

`recipient` (`old_operator`) no longer equals `operator` (`new_operator`), so the beneficiary substitution **never triggers**, and the coins are paid directly to `old_operator`'s own address instead of `beneficiary_for_operator(old_operator)`. [4](#0-3) 

### Is this "unprivileged"?

`vesting::update_operator` requires the vesting contract's `admin` signer (`verify_admin`), and `staking_contract::switch_operator` requires the `staker`/owner of the stake pool. Both callers already possess legitimate control over *their own* resources (the vesting contract / the stake pool) — they are not exploiting a missing permission check on those resources. However, they have **no privilege whatsoever over `old_operator`'s `BeneficiaryForOperator` configuration** — that is a resource fully controlled by `old_operator`. The bug lets a party with no authority over the beneficiary setting cause commission that should route to that beneficiary to instead land in `old_operator`'s raw account. This satisfies the "credits the wrong account" impact category, and the party harmed (`old_operator`'s beneficiary) never granted any authority to the admin/staker performing the switch.

### Scope caveat

This does **not** cause permanent loss of value — `old_operator` still legitimately earned the commission and receives it, just at the wrong address (their own, instead of the beneficiary they designated for custody/compliance/security separation purposes). It is a misroute, not a burn. [5](#0-4) [6](#0-5)

### Title
Commission requested during `switch_operator` bypasses old operator's beneficiary redirect on later distribution - (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::switch_operator` (reachable via `vesting::update_operator`) requests commission for `old_operator` right before re-keying the `StakingContract`'s shared `distribution_pool` under `new_operator`. Because the beneficiary substitution in `distribute_internal` compares the pool's stored shareholder address to the *current call's* `operator` parameter rather than checking whether the shareholder itself has a beneficiary configured, that final pre-switch commission tranche is later paid directly to `old_operator`'s address instead of `old_operator`'s configured beneficiary.

### Finding Description
- `switch_operator` calls `distribute_internal` then `request_commission_internal` for `old_operator`, adding a new distribution share keyed to `old_operator`'s address into the pool (`add_distribution`), then re-keys the same `StakingContract`/`distribution_pool` under `new_operator`.
- The freshly requested commission is still `pending_inactive` (locked) and cannot be distributed inside `switch_operator`.
- When it is eventually distributed via `distribute(staker, new_operator)`, `distribute_internal` runs with `operator = new_operator`, so the check `if (recipient == operator)` fails for the `old_operator`-keyed share, and the beneficiary substitution `beneficiary_for_operator(operator)` never executes for that share.
- Coins go straight to `old_operator`'s address, silently bypassing the beneficiary redirect that `set_beneficiary_for_operator` promises ("Any existing unpaid commission rewards will be paid to the new beneficiary"). [7](#0-6) 

### Impact Explanation
Corrupts operator-commission-to-beneficiary attribution across an operator switch: value is credited to the wrong account (`old_operator` directly) rather than the account `old_operator` designated to receive commission. This can defeat custodial/compliance separation an operator relies on (e.g., cold-wallet beneficiary), though the value itself is not permanently lost — it's redirected to the operator's own address.

### Likelihood Explanation
Requires only: (1) the vesting admin/staker performing an ordinary `update_operator`/`switch_operator` call while commission has accrued but not yet been distributed, and (2) `old_operator` having previously set a beneficiary via `set_beneficiary_for_operator`. Both are normal, unprivileged-with-respect-to-the-beneficiary operations that occur in typical operator rotation flows.

### Recommendation
In `distribute_internal`, redirect based on whether the shareholder (`recipient`) itself has a `BeneficiaryForOperator` entry, not on whether `recipient == operator` (the function's caller-supplied operator argument):
```move
if (exists<BeneficiaryForOperator>(recipient)) {
    recipient = beneficiary_for_operator(recipient);
};
```
This makes the substitution independent of which "current operator" happens to be passed into `distribute_internal`, correctly following whoever the shareholder actually is.

### Proof of Concept
Extend `test_set_beneficiary_for_operator` (`vesting.move`, around line 1639) as follows, using the referenced construct at: [8](#0-7) 

1. Set up vesting contract with `operator1`, 10% commission; call `set_beneficiary_for_operator(operator1, beneficiary_address)`.
2. Let the pool earn rewards (`stake::end_epoch()`).
3. Call `update_operator(admin, contract_address, operator_address2, new_commission)` — this triggers `switch_operator`, which internally calls `request_commission_internal` and adds the pending commission share keyed to `operator1` into the pool now stored under `operator2`.
4. Fast forward past lockup (`stake::fast_forward_to_unlock`), then call `staking_contract::distribute(contract_address, operator_address2)`.
5. Assert: `coin::balance<AptosCoin>(beneficiary_address)` stays at 0 (or unchanged), while `coin::balance<AptosCoin>(operator_address1)` receives the pre-switch commission directly — demonstrating the beneficiary redirect was bypassed, contrary to the documented guarantee in `set_beneficiary_for_operator`'s doc comment.

        let distribution_pool = &mut staking_contract.distribution_pool;
