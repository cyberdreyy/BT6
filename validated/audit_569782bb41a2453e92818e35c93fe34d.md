### Title
Re-requesting a withdrawal after a loss-adjusted epoch resets `lastWithdrawRequest` and lets the old haircutted receipt be claimed at par, stealing from the funded-claims reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user]` with the current epoch. The loss-adjusted claim path (`_claimLossAdjustedWithdrawRequest`) derives the haircut epoch solely from `lastWithdrawRequest[_user]`, while the funded claim path (`_claimFundedWithdrawRequest`) pays the aggregate `withdrawsRequests[_user]` at par. An unprivileged user can therefore sandwich a fresh small withdrawal after an epoch that suffered a `stopEpochWithDuration` loss, hide the old loss epoch from the loss-adjusted path, and claim both epochs' receipts fully funded — draining underlying that was only collected at the haircut rate or that belongs to other claimants.

### Finding Description
In `requestWithdraw`, the strategy records the request epoch and aggregates `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) . When `stopEpochWithDuration` results in a partial funding, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epoch]`, clears `pendingWithdraws`, but leaves the per-epoch basis in `withdrawsRequestsByEpoch` [2](#0-1) .

The problem is in the claim ordering inside `claimWithdrawRequest`: `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` only [3](#0-2) . If the user requested a new withdrawal in a later epoch, `lastWithdrawRequest[_user]` equals that later epoch, whose `lossRecoveryPriceByEpoch` is 0 (fully funded), so the loss path returns 0 without touching the old epoch's basis. `_clearWithdrawClaimForEpoch` is never called for the loss epoch, so `withdrawsRequests[_user]` still contains the haircutted basis [4](#0-3) .

`_claimFundedWithdrawRequest` then only requires `epochNumber > lastWithdrawRequest[_user]` — satisfied once the new epoch ends — and pays `normalAmount = withdrawsRequests[_user]` (old basis + new basis) in full via `_transferFundedClaim` [5](#0-4) . The strategy only ever collected `basis * lossRecoveryPrice / RECOVERY_FULL` for the old epoch, so the difference is paid out of the reserve meant for other funded receipts.

### Impact Explanation
Direct theft / insolvency. The attacker escapes the loss haircut entirely and extracts `basis * (1 - lossRecoveryPrice)` in excess of what was funded for their receipt. The shortfall is borne by other users whose funded or loss-adjusted claims are backed by the same strategy-held underlying — the last claimants revert on insufficient balance (permanent loss of unclaimed payouts up to the haircut amount). Concretely, with a 50% recovery price, a 1000-underlying receipt plus a dust re-request yields ~500 underlying stolen.

### Likelihood Explanation
- Attacker is an ordinary KYC'd tranche holder; only requires not claiming once, then calling `requestWithdraw` again (dust amount) in the next buffer epoch.
- Preconditions: an epoch ended via `stopEpochWithDuration` with `_amount < pendingWithdraws` (loss recovery flow), and at least one subsequent epoch is fully funded and ends — normal operation, honest manager/borrower sequencing.
- No guard stops it: the epoch-gating in `_claimFundedWithdrawRequest` is based on `lastWithdrawRequest`, which the attacker controls; the loss path has no fallback scan of older `withdrawsRequestsByEpoch` entries.

### Recommendation
Track the loss-adjusted claim independently of `lastWithdrawRequest` — e.g., store the epoch of each loss-adjusted basis (or iterate `withdrawsRequestsByEpoch` epochs that have a nonzero `lossRecoveryPriceByEpoch`), or at minimum, when computing the funded claim, subtract any per-epoch basis whose epoch has a recorded `lossRecoveryPriceByEpoch` and route it through `_claimLossAdjustedWithdrawRequest`. Alternatively, prevent `requestWithdraw` from updating `lastWithdrawRequest` while an unclaimed loss-adjusted epoch exists (or force settlement of the oldest loss epoch at request time).

```solidity
    _startEpoch();
    _stopEpochFullyFunded(); // lossRecoveryPriceByEpoch[N+1] == 0, epochNumber = N+2

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(address(idleCDO));

    // old loss epoch (N) was skipped because lookup used epoch N+1;
    // attacker receives basis + dust at par instead of basis*0.5 + dust
    assertEq(claimed, basis + dust);
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```

```text
  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
```
