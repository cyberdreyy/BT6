## Analog Vulnerability Analysis

Root cause of the reported issue: the Bitcoin adapter's `appendUtxos` mixes `int64` fee/amount arithmetic without overflow checks, allowing an attacker-influenced value (`fee`, `costSatoshis`) to wrap and corrupt a security-relevant calculation.

Searching chainlink's unprivileged-client-facing surfaces (gateway message handlers, node API auth, session/token handling) for the same bug class — unchecked fixed-width integer arithmetic on attacker-controlled input feeding a security check — the closest analog is the message-staleness check in the public WebAPI gateway handler.

### Title
Integer Underflow/Overflow in Gateway Message Staleness Check Allows Replay of Stale Messages - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage`, the entry point that processes untrusted, client-submitted WebAPI trigger messages arriving at the gateway, validates message freshness using unsigned integer subtraction on an attacker-controlled, signed `Timestamp` field. Because the subtraction and comparison are performed as `uint`, an attacker can supply a `Timestamp` value that causes the cast to wrap, defeating the staleness check.

### Finding Description
The staleness check is: [1](#0-0) 

specifically: [2](#0-1) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    ... "stale message" ...
}
```

`payload` is `webapicap.TriggerRequestPayload`, decoded directly from the unauthenticated/legacy user message body: [3](#0-2) . `Timestamp` is attacker-controlled JSON input reaching this code before any allowlist/rate-limit check is applied — the code even contains a `TODO: apply allowlist and rate-limiting here` comment immediately after the staleness check: [4](#0-3) .

Casting a signed `Timestamp` to `uint` reproduces the same class of bug as the reported `appendUtxos` issue: fixed-width arithmetic performed on externally-supplied values without bounds validation. If `payload.Timestamp` is negative (or otherwise crafted so `uint(payload.Timestamp)` becomes a very large value), the right-hand side of the comparison becomes enormous, so `diff > uint(payload.Timestamp)` evaluates false regardless of the message's real age — the staleness gate is bypassed. This mirrors the report's overflow mechanism (unchecked native-width arithmetic on attacker-influenced values corrupting a security-relevant comparison), applied here to an authorization/freshness gate that runs on every unprivileged client request instead of a fee computation.

Note: I could not fully confirm the exact Go type of `TriggerRequestPayload.Timestamp` from the indexed code (only usage sites were retrievable, not the generated field definition), so the precise overflow trigger value depends on that type; this should be verified directly in `core/capabilities/webapi/webapicap` generated types before treating this as confirmed-exploitable.

### Impact Explanation
If the staleness check can be bypassed, an attacker can resubmit or forge messages that should be rejected as stale, i.e., a replay-style bypass of a request-freshness/anti-replay control on the internet-facing gateway ingestion path. Depending on downstream handling, this could permit re-triggering workflow/webapi actions with old data outside their intended validity window.

### Likelihood Explanation
The path is reachable directly from an unprivileged external client — this handler processes "legacy user messages" prior to any allowlist/rate-limit enforcement (per the adjacent `TODO`). Exploitability hinges on whether the `Timestamp` field's underlying type and JSON decoding permit a negative or out-of-range value to be supplied; this needs verification against the exact generated struct definition, which was not retrievable from the index.

### Recommendation
Avoid casting attacker-controlled signed timestamps to `uint` for security comparisons. Validate `payload.Timestamp` bounds (reject negative or unreasonable future/past values) before use, and perform the staleness comparison using signed arithmetic (e.g., `time.Now().Unix() - int64(h.config.MaxAllowedMessageAgeSec) > payload.Timestamp`), consistent with the report's recommendation to use overflow-safe arithmetic (e.g., `big.Int` or explicit bounds checks) instead of raw fixed-width casts on external input.

### Proof of Concept
Conceptual (pending confirmation of `Timestamp`'s type):
1. Attacker sends a WebAPI trigger message to the gateway's legacy user-message endpoint with `payload.Timestamp` set to a negative value (if the field is signed) or a value near `math.MaxInt64`.
2. `uint(payload.Timestamp)` wraps to a very large unsigned value.
3. `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec` (a comparatively small number) is not greater than this wrapped value, so the "stale message" branch is skipped.
4. The message proceeds to `common.ValidatedRequestFromMessage` and is forwarded to DON members despite failing the intended freshness check: [5](#0-4) .

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	body := msg.Body
	var payload webapicap.TriggerRequestPayload
	codec := api.JsonRPCCodec{}
	err := json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}
