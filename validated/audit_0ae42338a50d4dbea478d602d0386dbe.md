### Title
Signer accepts a fallback block from `last_sortition` even after `last_sortition` itself is marked timed out - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::check_proposal` computes `last_sortition`'s own `is_timed_out` status and sets `last_sortition.miner_status = InvalidatedBeforeFirstBlock` when it fires, but the `ProposedBy::LastSortition` match arm that decides whether to accept a proposal attributed to `last_sortition` never reads that field — it only checks `self.cur_sortition.miner_status`. This lets a stale miner's replayed proposal for the prior sortition pass this gate even though the signer has just independently determined that same miner has also timed out.

### Finding Description
In `check_proposal` [1](#0-0) , if `cur_sortition` times out it is marked `InvalidatedBeforeFirstBlock`. Separately, `last_sortition`'s own liveness is checked and, if timed out, `last_sortition.miner_status` is set to `InvalidatedBeforeFirstBlock` as well [2](#0-1) . Both computations use the identical `self.config.block_proposal_timeout`.

Later, `proposed_by` is resolved to `ProposedBy::LastSortition` purely by consensus-hash equality to `last_sortition.data.consensus_hash` [3](#0-2) , and pubkey-hash is checked against `proposed_by.state().data.miner_pkh` [4](#0-3) . The final authorization gate is:

```
ProposedBy::LastSortition(last_sortition) => {
    if self.cur_sortition.miner_status != SortitionMinerStatus::InvalidatedBeforeFirstBlock {
        ... return Err(RejectReason::NotLatestSortitionWinner);
    }
}
``` [5](#0-4) 

This condition checks only `self.cur_sortition.miner_status`; it never inspects the bound variable `last_sortition.miner_status`, even though that exact field was populated moments earlier in this same call by the independent `is_timed_out` check at lines 205-220. So a proposal from a miner attributed to `last_sortition` is authorized as soon as `cur_sortition` is invalidated — regardless of whether `last_sortition` has itself also timed out under the identical rule.

None of the subsequent checks (tenure-change validation, `confirms_latest_in_tenure`, tenure-extend handling) reference `last_sortition.miner_status` either — they operate on `proposed_by.state().data`, not on miner-status/liveness. This means the computed invalidation of `last_sortition` is dead for gating purposes within this call: it is set but not consulted before returning `Ok(())`.

The existing regression test `check_block_proposal_timeout` [6](#0-5)  does not cover this scenario: it only inserts a burn-block record for `cur_sortition` (via `insert_burn_block`), so `last_sortition`'s own `is_timed_out` call at line 207 returns `Ok(false)` early because `get_burn_block_receive_time_ch` finds no record for it [7](#0-6) . The test therefore never exercises the branch where `last_sortition.miner_status` actually flips to `InvalidatedBeforeFirstBlock`, masking the gap.

### Impact Explanation
This breaks the liveness/staleness safety invariant: the same `block_proposal_timeout` rule that is meant to invalidate an inactive miner is applied inconsistently between `cur_sortition` and `last_sortition`. A signer can be induced to sign (or locally-accept) a block from a miner two sortitions stale, whose own tenure has independently timed out by the identical rule applied to the current sortition. If enough signers hit this same window, an invalid/non-canonical block from a stale miner could gain enough signatures to be treated as validly signed — a chain-safety (Critical) concern per the stated categories, since it is a signer approving a block attributable to a miner the signer itself has just determined is inactive.

### Likelihood Explanation
Preconditions: both `cur_sortition` and `last_sortition` must be near/at `block_proposal_timeout` in the signer's local view, and a burn-block receive-time record must exist for `last_sortition` in `signerdb` (otherwise its own timeout check short-circuits to `false`, as in the existing test). The attacker needs only the miner key that won the `last_sortition` slot historically (already public/spent) and the ability to gossip a `BlockProposal` with `last_sortition`'s `consensus_hash` — a single miner-slot-level capability with no other signer's key. This is repeatable each time a signer's tenure timing lands both sortitions near the timeout boundary, which is a plausible/recurring condition rather than a rare accident, given block_proposal_timeout is a fixed, publicly-known config value.

### Recommendation
In the `ProposedBy::LastSortition` arm, additionally require `last_sortition.miner_status == SortitionMinerStatus::Valid` (i.e., check both `self.cur_sortition.miner_status == InvalidatedBeforeFirstBlock` AND `last_sortition.miner_status == SortitionMinerStatus::Valid`) before accepting the proposal, so a `last_sortition` that has itself independently timed out is rejected rather than treated as a legitimate fallback.

### Proof of Concept
Extend `stacks-signer/src/chainstate/tests/v1.rs::check_block_proposal_timeout` (or add a new test) as follows:
1. Set up `view.cur_sortition` and `view.last_sortition` as in `check_block_proposal_timeout` (see setup at lines 570-600).
2. Additionally call `signer_db.insert_burn_block(...)` for `last_sortition`'s `burn_block_hash`/`consensus_hash`, so its own `is_timed_out` check is actually evaluated (not short-circuited to `false`).
3. Sleep long enough that both `cur_sortition` and `last_sortition` exceed `block_proposal_timeout`.
4. Call `view.check_proposal(...)` with a block whose `consensus_hash` equals `last_sortition`'s consensus hash, signed by `last_sortition`'s miner key.
5. Assert (current buggy behavior) that `check_proposal` returns `Ok(())` — i.e., it wrongly succeeds.
6. After applying the fix (checking `last_sortition.miner_status == Valid` in the `ProposedBy::LastSortition` arm), assert instead `.expect_err(...)` with `RejectReason::NotLatestSortitionWinner` (or a new dedicated reject reason), confirming the equality is enforced on both sides: `last_sortition` timed out ⇒ proposal rejected, not merely logged.

#[test]
fn check_block_proposal_timeout() {
    let (stacks_client, mut signer_db, block_sk, mut view, mut curr_sortition_block) =
        setup_test_environment(function_name!());
    curr_sortition_block.header.consensus_hash = view.cur_sortition.data.consensus_hash.clone();
    curr_sortition_block.header.sign_miner(&block_sk).unwrap();

    let mut last_sortition_block = curr_sortition_block.clone();
    last_sortition_block.header.consensus_hash = view
        .last_sortition
        .as_ref()
        .unwrap()
        .data
        .consensus_hash
        .clone();
    last_sortition_block.header.sign_miner(&block_sk).unwrap();

    // Ensure we have a burn height to compare against
    let burn_hash = view.cur_sortition.data.burn_block_hash.clone();
    let consensus_hash = view.cur_sortition.data.consensus_hash.clone();
    let burn_height = 1;
    let received_time = SystemTime::now();
    signer_db
        .insert_burn_block(
            &burn_hash,
            &consensus_hash,
            burn_height,
            &received_time,
            &view.last_sortition.as_ref().unwrap().data.burn_block_hash,
        )
        .unwrap();

    view.check_proposal(
        &stacks_client,
        &mut signer_db,
        &curr_sortition_block,
        false,
        ReplayTransactionSet::none(),
    )
    .expect("Proposal should validate");

    view.check_proposal(
        &stacks_client,
        &mut signer_db,
        &last_sortition_block,
        false,
        ReplayTransactionSet::none(),
    )
    .expect_err("Proposal should not validate");

    // Sleep a bit to time out the block proposal
    std::thread::sleep(Duration::from_secs(5));
    view.check_proposal(
        &stacks_client,
        &mut signer_db,
        &curr_sortition_block,
        false,
        ReplayTransactionSet::none(),
    )
    .expect_err("Proposal should not validate");

    view.check_proposal(
        &stacks_client,
        &mut signer_db,
        &last_sortition_block,
        false,
        ReplayTransactionSet::none(),
    )
    .expect("Proposal should validate");
}
