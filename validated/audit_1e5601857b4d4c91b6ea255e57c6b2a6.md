Confirmed: `multisig-factory/src/lib.rs::create` lacks the callback/refund pattern that its sibling factories implement.

### Title
Failed multisig creation strands attached NEAR in the factory contract with no refund path - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` builds a single-receipt promise batch (`create_account().deploy_contract().transfer().function_call()`) with no `.then()` callback to `self`. If the derived `account_id` (`{name}.{factory}`) already exists — e.g. because the attacker pre-funded it with a bare NEAR transfer, or it collides with an implicit account form — `create_account()` fails, the whole batch fails atomically, and the attached deposit is refunded by the runtime to the *predecessor of the failed receipt*, which is the factory contract account itself, not the original caller. There is no method on `MultisigFactory` to recover or forward that balance, so the deposit is permanently stranded in the factory's account balance.

### Finding Description
The broken binding: for every call to `create`, `factory.balance_after == factory.balance_before` should hold once the outcome (success or failure) settles — the factory should never durably retain the caller's deposit. In `multisig-factory/src/lib.rs` lines 34-49: [1](#0-0) 

the promise chain has no `.then(ext_self::on_create(...))` callback, unlike the equivalent logic in `staking-pool-factory/src/lib.rs`'s `create_staking_pool`/`on_staking_pool_create` and `lockup-factory/src/lib.rs`'s `create`/`on_lockup_create`, both of which explicitly refund `predecessor_account_id` via `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` inside a callback guarded by `assert_self()` and `is_promise_success()`: [2](#0-1) [3](#0-2) 

The multisig factory has neither an `on_create` callback nor any such refund logic. Attack flow: the attacker (1) picks a `name` and computes `account_id = "{name}.{factory}"`; (2) transfers NEAR directly to that derived account id beforehand (any unprivileged account can send a bare transfer to any account id, funding/creating it as an implicit-style pre-existing account) or otherwise ensures the account already exists; (3) calls `create(name, members, num_confirmations)` with an attached deposit. Because the target account already exists, the `create_account()` action inside the single batched receipt fails, causing the whole receipt (including the `transfer` of the attached deposit) to fail. Per NEAR runtime semantics, the deposit that was already deducted from the caller and forwarded as part of the outgoing receipt is refunded to the **receipt's predecessor**, i.e., the `multisig-factory` contract account, not back to the calling account. Since `MultisigFactory` has no owner, no withdrawal method, and no accounting of who is entitled to that stranded balance, the NEAR is permanently locked in the factory with no code path to return it to the rightful depositor. This breaks the audit's target invariant ("a failed creation strands no NEAR") explicitly, since none of `assert_owner`, `assert_self()`, `is_promise_success()`, or any equivalent guard exists in this file to detect the failure and issue a refund.

### Impact Explanation
Every failed `create` call permanently transfers the attacker's/victim's attached deposit into the `multisig-factory` account's balance, where it sits unaccounted for and unrecoverable by anyone (not even the factory owner, since the contract has no state or methods referencing it). This is repeatable indefinitely across accounts and callers — anyone (attacker griefing themselves is irrelevant, but a victim caller unknowingly targeting a colliding name loses funds) can trigger this on any name they choose, and each occurrence permanently strands more NEAR in the factory. This matches the "accounting value diverges from reality" / "funds frozen permanently" category: the caller's expected multisig balance never materializes, the factory's balance silently grows with unaccounted deposits, and there is no method to reconcile or reclaim it — effectively a permanent freeze of funds belonging to whoever's deposit was consumed by the failed batch.

### Likelihood Explanation
Low cost, fully attacker-controlled: the attacker only needs to (a) pre-create/fund the target `{name}.{factory}` account with any transfer, and (b) call `create` with that `name` and a deposit. No privileged role, timing, or coordination required. This is trivially repeatable for any `name` value and requires no interaction with existing multisig members, the factory owner, or the NEAR Foundation. The `create` entrypoint is `#[payable]` and open to any caller.

### Recommendation
Add a `.then()` callback (`ext_self::on_create`) after the account-creation batch, guarded by `assert_self()`, checking `is_promise_success()`. On failure, refund `env::attached_deposit()` back to `env::predecessor_account_id()` (captured before the promise, similar to `lockup-factory`'s and `staking-pool-factory`'s patterns), and only treat the multisig as created on success.

### Proof of Concept
Using `near-sdk-sim` or a `testing_env!`-based unit test mirroring `lockup-factory`'s `test_create_lockup_rollback`:
1. Set up `MultisigFactory` and call `create(name, members, num_confirmations)` with `attached_deposit = X`.
2. Simulate the derived account `{name}.{factory}` already existing (in `near-workspaces`, pre-create/fund that account before calling `create`); run the resulting batch and confirm `create_account` fails.
3. Assert: `factory_balance_after_failed_create == factory_balance_before + X` (deposit retained by factory) and `caller_balance_after != caller_balance_before` (caller never gets `X` back), demonstrating the equality `factory.balance_after == factory.balance_before` is violated with no compensating refund transaction issued — unlike `lockup-factory::on_lockup_create` / `staking-pool-factory::on_staking_pool_create`, `multisig-factory::create` has no callback to assert against, confirming the missing refund path.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
