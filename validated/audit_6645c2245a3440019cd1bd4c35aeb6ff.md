## Title
Stale confirmations from deleted members are still counted toward the multisig threshold, allowing execution below the intended `num_confirmations` - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges outstanding *requests* created by the member being removed; it never scans the `confirmations` map to strip confirmations that removed member previously cast on *other* still-pending requests. `confirm()` then authorizes execution purely by comparing the stored confirmation-set size to `num_confirmations`, without checking that every confirming entry is still a live member. This lets a request execute with fewer *currently authorized* confirmations than the configured threshold — the same class of bug as the reported issue, where a "current" trust check (`amAmm.getTopBid`) is used without validating that the underlying authorization state (am-AMM enabled) is still current.

### Finding Description
`delete_member` at [1](#0-0)  removes:
- outstanding requests where `r.member == member` (i.e., requests the deleted member *created*),
- the `num_requests_pk` counter for that member,
- the member from `self.members`, and the associated access key.

It does **not** iterate `self.confirmations` to remove entries where the deleted member appears as a **confirmer** of a request created by someone else. That map is only cleaned in `remove_request` (called from `delete_request` or after a request executes) — never in `delete_member`.

`confirm()` counts raw confirmation-set size against `num_confirmations` with no re-validation that each already-recorded confirming identity is still in `self.members`: [2](#0-1) 

So the binding that should hold is:
```
confirmations_counted(request) == live_members_who_actually_authorized(request)
```
But after a member is deleted while having already confirmed a pending, unrelated request, the equality breaks: `confirmations_counted(request) > live_members_who_authorized(request)`, because a stale confirmation from a now-removed member is still present in the `HashSet<String>` for that request and is counted by the `>= self.num_confirmations` check.

### Impact Explanation
This is a threshold-integrity failure: a multisig configured for `K`-of-`N` can end up executing a request (including `Transfer`, `AddKey`, `FunctionCall`, etc.) with fewer than `K` *currently valid* confirmations, because one or more of the counted confirmations belong to an account/key that has since been removed from the multisig. This matches the Critical impact category "a multisig request executed below threshold" — funds can move, or new keys/members can be added, with insufficient live authorization.

### Likelihood Explanation
Likelihood is Medium: it requires an ordinary, expected sequence of multisig operations — a member confirms a pending request, and before that request accumulates enough further confirmations, the multisig (through a separate, otherwise legitimate `DeleteMember` request) removes that member (e.g., rotating out a departing or compromised signer). No malicious behavior or external attacker capability is needed beyond normal contract usage patterns that the multisig is explicitly designed to support (member rotation via `DeleteMember`).

### Recommendation
When executing `DeleteMember`, iterate all pending requests' confirmation sets and remove the deleted member's identity from each, or alternatively validate at `confirm()`-time (before comparing against `num_confirmations`) that every already-stored confirming identity is still present in `self.members`, discarding stale ones from the count.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request_and_confirm` with a `Transfer` request `R` to an attacker-controlled or colluding account — `confirmations[R] = {A}` (1 of 2, not yet executed): see `add_request_and_confirm`/`confirm` at [3](#0-2)  and [2](#0-1) .
3. Separately, `B` and `C` submit and confirm a `DeleteMember { member: A }` request, which succeeds because `members.len()-1 (2) >= num_confirmations (2)`: [4](#0-3) . This removes `A` from `self.members` and deletes `A`'s access key, but leaves `confirmations[R] = {A}` untouched since `R` was created by `A`... 

   Note: for a cleaner PoC where the confirming member and the request creator differ, use: `B` creates request `R` (not `A`), `A` confirms it (`confirmations[R] = {A}`), then `B`/`C` delete member `A`. Because `delete_member`'s cleanup filter only targets requests where `r.member == member` (i.e., requests *created by* `A`), request `R` (created by `B`) is untouched, so `confirmations[R]` still contains `A` even though `A` is no longer a member.
4. `C` now calls `confirm(R)`. `confirmations.len() (1) + 1 >= num_confirmations (2)` is true, so `R` executes — despite only `B` and `C` being live members who authorized it and `A`'s confirmation being stale/unauthorized at execution time. Effectively the request executed with the multisig's threshold satisfied by a confirmation from an account that is no longer entitled to confirm. [2](#0-1) [1](#0-0)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
