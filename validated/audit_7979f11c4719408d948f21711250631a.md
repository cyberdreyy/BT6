### Title
Loss-haircut price cached under the post-increment epoch, so pending withdraw receipts claim at par — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` keeps one haircut cache, `lossRecoveryPriceByEpoch`, shared between two different epoch contexts: the request-side context (`requestWithdraw` records `lastWithdrawRequest[user] = currentEpoch` before `stopEpoch`) and the funding-side context (`collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]` during `stopEpoch`). `deposit()` increments `epochNumber` when called while `isEpochRunning()` — i.e. inside `stopEpoch`, when the CDO pushes borrower repayment into the strategy. Because the write happens after the increment while the read key was captured before it, a `stopEpochWithDuration`-style partial funding stores the haircut under the *new* epoch number, and victims' receipts point at the *old* epoch number where the mapping is `0`. This mirrors the upstream seg6 bug class: one shared cache populated by whichever path runs first (or under the wrong key) and blindly reused by a path with a different context.

### Finding Description
- Request path: `requestWithdraw` snapshots `uint256 currentEpoch = epochNumber` and stores `lastWithdrawRequest[_user] = currentEpoch` plus `withdrawsRequestsByEpoch[_user][currentEpoch]`. (`IdleCreditVault.sol:260-293`)
- Funding path: during `stopEpoch`, the CDO deposits recalled funds; `deposit()` sees `isEpochRunning() == true` and executes `epochNumber += 1`. (`IdleCreditVault.sol:607-617`)
- Loss path: `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws` then stores `lossRecoveryPriceByEpoch[epochNumber]` — the already-incremented epoch. (`IdleCreditVault.sol:411-430`)
- Claim path: `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the pre-increment epoch — gets `0`, and returns early without applying the haircut. (`IdleCreditVault.sol:789-801`)
- The receipt then falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` **at par** from strategy-held underlyings, even though `pendingWithdraws` was zeroed and only `_amount < pendingBasis` was ever funded. (`IdleCreditVault.sol:319-350`)

### Impact Explanation
After a loss-adjusted `stopEpoch` (borrower repays less than `pendingWithdraws`), every pending receipt claims 100% instead of `lossRecoveryPrice`. The excess comes directly out of underlyings held by the strategy: it drains the funded remainder owed to other claimants and, once `defaultRecoveryReserve`/funded balances are consumed, later claimants revert — i.e., early claimants over-claim and late claimants' funds are permanently frozen. Broken invariant: loss waterfall — the `stopEpochWithDuration` loss intended to be socialized across pending receipts is instead fully absorbed by the last withdrawers. The `lossRecoveryPrice == 0` guard in `collectWithdrawFunds` does not help: it prevents storing a zero price, not storing under the wrong key.

### Likelihood Explanation
Requires an honest manager calling `stopEpoch` with a shortfall (`_amount < pendingWithdraws`), which is a normal, supported flow for realized losses — no privileged misbehavior needed. Whether the mismatch triggers depends on `IdleCDOEpochVariant.stopEpoch` ordering (deposit/recall into the strategy before `collectWithdrawFunds`); I was unable to read `IdleCDOEpochVariant.sol` within this session to confirm the exact call order, so this finding assumes the deposit-side `epochNumber += 1` precedes the collect — which the code comments ("deposit done on stopEpoch") indicate is the designed sequence. If collect precedes the increment, the symmetric mismatch still exists for receipts whose `lastWithdrawRequest` differs from the write epoch.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the epoch in which the receipts were requested, not the epoch in which funding is collected. Either pass the request epoch explicitly from the CDO (e.g. `collectWithdrawFunds(_amount, _requestEpoch)`), or snapshot `epochNumber` for pending receipts at `stopEpoch` entry before any deposit-triggered increment. Also make `_claimLossAdjustedWithdrawRequest` verify that a haircut exists for the receipt's epoch before allowing the funded par claim.

// Foundry fork PoC (scaffold)
function testLossEpochMismatch() external {
    // 1. user requests withdraw in epoch N: lastWithdrawRequest[user] = N
    cdo.requestWithdraw... // via IdleCDOEpochVariant
    // 2. manager stops epoch with a loss: borrower funds < pendingWithdraws.
    //    Inside stopEpoch, strategy.deposit() runs while isEpochRunning() => epochNumber becomes N+1
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, lossAmount);
    // 3. collectWithdrawFunds stores lossRecoveryPriceByEpoch[N+1] = price < 1e18
    assertEq(vault.lossRecoveryPriceByEpoch(N), 0);       // user's key: empty
    assertGt(vault.lossRecoveryPriceByEpoch(N + 1), 0);   // write key: populated
    // 4. user claims: reads price 0 at epoch N -> funded par claim
    uint256 balBefore = underlying.balanceOf(user);
    cdo.claimWithdrawRequest(user);
    // BUG: received full request amount instead of amount * lossRecoveryPrice
    assertEq(underlying.balanceOf(user) - balBefore, requestedAmount);
    // 5. subsequent claimants revert on insufficient funded balance -> funds frozen
}
