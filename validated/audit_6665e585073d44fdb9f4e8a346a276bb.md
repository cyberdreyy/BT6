### Title
Signer reward-cycle attribution trusts the miner-supplied `BlockProposal.reward_cycle` field instead of the block's actual burn-height-derived reward cycle - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`stacks-signer` gates almost all block-tracking logic — whether a proposal belongs to "our" reward cycle, and whether a later validation response, acceptance signature, or rejection applies to a block we are tracking — on a single field: `BlockInfo.reward_cycle`. That field is copied verbatim from the `reward_cycle` field of the `BlockProposal` message, which is set by the miner and never independently verified against the block's real sortition/burn-height context. This is the same root-cause shape as the Admidio IDOR: an authorization/routing decision is bound to a caller-supplied label (`folder_uuid` / `reward_cycle`) instead of the resource's true parent context (the file's actual folder / the block's actual sortition-derived reward cycle).

### Finding Description
`BlockProposal` (the message a miner broadcasts to signers) carries a self-reported `reward_cycle: u64` field with no cryptographic or structural binding to the block's `consensus_hash`/burn height: [1](#0-0) 

On the node side, when the coordinator constructs this message it derives `reward_cycle` correctly from the election sortition's burn height: [2](#0-1) 

But this is only the *honest* path. Nothing on the signer side re-derives or verifies that value; a miner (a single, non-colluding actor) fully controls the bytes of the `BlockProposal` it broadcasts on `.miners` StackerDB, including `reward_cycle`.

On the signer side, `handle_block_proposal` uses this field as the sole gate deciding whether the signer processes the proposal at all: [3](#0-2) 

The resulting `BlockInfo` (created via `BlockInfo::from(block_proposal.clone())`) persists this miner-supplied `reward_cycle` into the signer's own database, and every subsequent lookup by hash is filtered by this stored, attacker-influenced value rather than anything derived from the block's `consensus_hash`/burn height: [4](#0-3) 

This same helper (`block_lookup_by_reward_cycle`) is the gate used when processing block-validation responses, observed acceptance signatures, and observed rejections: [5](#0-4) [6](#0-5) [7](#0-6) 

Critically, this "trust the label" gate is the *documented fix* for a previously-known bug class: [8](#0-7) 

i.e. "Prevent old reward cycle signers from processing block validation response messages that do not apply to blocks from their cycle" was implemented by trusting `reward_cycle` on the stored `BlockInfo`/message rather than by deriving the block's true reward cycle from its `consensus_hash`/burn height (no `block_height_to_reward_cycle` call exists anywhere under `stacks-signer/`, confirmed by search). Neither `SortitionsView::check_proposal` in v1 nor v2 chainstate cross-checks `reward_cycle` against the block's actual sortition: [9](#0-8) 

Meanwhile, the signer's own conflict-detection queries key purely by the block's real `consensus_hash`, independent of the (mislabeled) `reward_cycle` tag: [10](#0-9) 

So a single miner can construct a `BlockProposal` whose `block.header.consensus_hash` genuinely belongs to reward cycle N's sortition/tenure, but stamp the message's `reward_cycle` field with N+1 (or vice versa) and broadcast it during the well-documented overlap window where both the outgoing and incoming reward-cycle signer sets are simultaneously live and reading the same `.miners` StackerDB feed (per `docs/signer-flows.md` "own reward cycle has started ... everything else is dropped until then"). The N+1 signer set's `self.reward_cycle == block_proposal.reward_cycle` check passes trivially (attacker sets the field to match), so the N+1 process locally evaluates, potentially pre-commits/locally-accepts, and persists a `BlockInfo` for a block that structurally belongs to a *different* reward cycle's tenure/parent-chain context, under its own `reward_cycle` label. Because signerdb's tenure/conflict-tracking queries (`get_last_signed_block`, `has_signed_block_in_tenure`, etc.) are keyed only on `consensus_hash` — not reward cycle — this pollutes the same signer process's equivocation/conflict bookkeeping for that tenure with state that was validated under the wrong signer-set context (wrong reward set assumptions, wrong "own tenure" viewpoint, wrong pre-commit threshold weight).

### Impact Explanation
This maps to the "High" bucket: **a signer acting on a stale/foreign reward-cycle context, weakening its own conflict/equivocation bookkeeping**. While the final aggregated signature is still checked by the node/network against the block's *real* epoch reward set (`verify_signer_signatures` in `stackslib/src/chainstate/nakamoto/mod.rs`, which correctly derives the reward set from actual burn height), the mislabeling lets a single miner cause a signer process to locally accept/pre-commit/sign a block outside the tenure/reward-cycle context its local state machine and signerdb bookkeeping assume, corrupting the very `consensus_hash`-keyed tables (`get_last_signed_block`, `has_signed_block_in_tenure`) that the "own-tenure conflict guard" and equivocation protections rely on. This can wedge or confuse a signer's local safety checks around reward-cycle boundaries without needing collusion from any other signer.

### Likelihood Explanation
Triggerable by a single miner with no majority-signer collusion, and squarely within the documented overlap window where two reward-cycle signer sets are simultaneously live reading the same broadcast feed — a condition the codebase itself acknowledges and partially defends against (the CHANGELOG entry), just via a label the miner controls rather than a value derived from the block's own sortition data.

### Recommendation
Do not trust `BlockProposal.reward_cycle` as an authorization boundary. Derive the block's true reward cycle from `block.header.consensus_hash`/its sortition (or `burn_height`) via the burnchain's PoX constants, exactly as the node does when constructing the message (`Burnchain::block_height_to_reward_cycle`), and reject/ignore any proposal whose self-reported `reward_cycle` does not match the independently-derived value before it is ever persisted into `BlockInfo`/`signer_db`.

### Proof of Concept
1. Node A produces a genuine block B during reward cycle N's tenure (`B.header.consensus_hash` belongs to a real cycle-N sortition).
2. A malicious/compromised miner broadcasts a `BlockProposal { block: B, burn_height: <N's burn height>, reward_cycle: N+1, .. }` on `.miners` StackerDB during the boundary window when both cycle-N and cycle-N+1 signer processes are live (`docs/signer-flows.md` overlap description).
3. Cycle-N+1 signer's `handle_block_proposal` sees `block_proposal.reward_cycle (N+1) == self.reward_cycle (N+1)` and proceeds (`stacks-signer/src/v0/signer.rs:1582-1589`), storing `BlockInfo{ reward_cycle: N+1, ... consensus_hash: <cycle-N tenure> }`.
4. This signer's subsequent `get_last_signed_block`/`has_signed_block_in_tenure` calls for that tenure's `consensus_hash` (`stacks-signer/src/signerdb.rs:1564-1585`) now reflect state gathered under the wrong reward-cycle context, corrupting its own-tenure conflict/equivocation bookkeeping for a tenure it was never meant to track.

    /// Helper for getting the block info from the db while accommodating for reward cycle
    pub fn block_lookup_by_reward_cycle(
        &self,
        block_hash: &Sha512Trunc256Sum,
    ) -> Option<BlockInfo> {
        let block_info = self
            .signer_db
            .block_lookup(block_hash)
            .inspect_err(|e| {
                error!("{self}: Failed to lookup block hash {block_hash} in signer db: {e:?}");
            })
            .ok()
            .flatten()?;
        if block_info.reward_cycle == self.reward_cycle {
            Some(block_info)
        } else {
            None
        }
    }

    /// Return the last signed block in a tenure (identified by its consensus hash).
    /// A block is considered signed if it is locally or globally accepted. Blocks that
    /// have only been pre-committed are excluded, because a pre-commit does not put a
    /// signature over the block and may be safely superseded by a competing proposal.
    ///
    /// This answers "what is the tenure's signed tip?", a different question from
    /// [`SignerDb::has_signed_block_in_tenure`]'s "does a signature bind us to this tenure?",
    /// which is why the predicates deliberately differ on rejected blocks (see there).
    pub fn get_last_signed_block(
        &self,
        tenure: &ConsensusHash,
    ) -> Result<Option<BlockInfo>, DBError> {
        let query = "SELECT block_info FROM blocks WHERE consensus_hash = ?1 AND state IN (?2, ?3) ORDER BY stacks_height DESC LIMIT 1";
        let args = params![
            tenure,
            &BlockState::GloballyAccepted.to_string(),
            &BlockState::LocallyAccepted.to_string(),
        ];
        let result: Option<String> = query_row(&self.db, query, args)?;

        try_deserialize(result)
    }
