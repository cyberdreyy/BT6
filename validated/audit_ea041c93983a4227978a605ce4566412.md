### Title
Multisig executes requests using stale confirmations from removed members, letting requests pass below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member()` in `multisig2/src/lib.rs` only purges pending *requests that the removed member originally authored*; it never scans `self.confirmations` to strip that member's confirmation from *other* members' pending requests. `confirm()` then counts confirmation-set size against `num_confirmations` without re-validating that every account/key already present in the confirmation set is still a current member. As a result, a confirmation cast by a member who is later removed keeps counting toward the threshold, letting a request execute (moving funds, adding a full-access key, deploying a contract, etc.) with fewer live-member confirmations than `num_confirmations` requires.

### Finding Description
The binding that should hold is:

`confirmations counted toward execution == confirmations from currently live members`

`delete_member` breaks this equality: [1](#0-0) 
It filters `self.requests` for entries where `r.member == member` (i.e., requests *created* by the removed member) and deletes those plus their confirmation sets. It does **not** iterate `self.confirmations` to remove the departing member's entry from confirmation sets of requests created by *other* members that the departing member had already confirmed.

`confirm()` never re-checks the members recorded in an existing confirmation set: [2](#0-1) 
It only validates that the *current caller* is a member (via `assert_valid_request` / `current_member()`), then simply does `confirmations.len() as u32 + 1 >= self.num_confirmations`. The pre-existing entries in `confirmations` (from a now-removed member) are counted at face value. [3](#0-2) 

Concretely:
1. Multisig has members `{A, B, C}` with `num_confirmations = 2`.
2. `B` creates a request (`add_request`), `A` confirms it (`confirm`) — confirmation set is `{A}`, one short of the threshold of 2.
3. Members vote via `DeleteMember { member: A }` to remove `A` (e.g., A's key is compromised or A leaves). `delete_member` only removes requests *authored by* `A`; the request authored by `B` (with `A`'s confirmation already in it) is untouched — its confirmation set still contains `A`.
4. `C`, the only other live member besides `B`, calls `confirm()` on that same request. `confirmations.len() + 1 = 2 >= num_confirmations (2)`, so the request executes — using one confirmation from a member (`A`) that has been removed and one from `C`. Effectively the request executed with only 1 live confirming member instead of the required 2.

This is the direct analog of the Remora forwarder bug: an entity is stripped of its "active" status (holder / member) but stale accounting data attributable to it (`calculatedPayout` / a recorded confirmation) is left dangling and later mis-trusted — in Remora the stale data caused loss of funds, here it causes a multisig request to be authorized below the intended k-of-n threshold, i.e., "a multisig request executed below threshold," which is explicitly listed as a Critical impact in the scope rules.

The identical pattern exists in `multisig/src/lib.rs`'s `DeleteKey` handling, which likewise only purges requests authored by the deleted key and leaves that key's confirmations on other members' requests intact: [4](#0-3) 

### Impact Explanation
This breaks the core multisig custody guarantee: any transfer, key addition, contract deployment, or function call gated behind `num_confirmations` can be executed with strictly fewer live confirming members than configured, once at least one confirming member is later removed from the multisig while their confirmation is still pending on an outstanding request. Since `MultiSigRequestAction::Transfer`, `AddKey`, `DeployContract`, and `FunctionCall` are all executable this way, this can lead directly to unauthorized fund transfers or account takeover — squarely within "a multisig request executed below threshold" (Critical).

### Likelihood Explanation
This requires only ordinary multisig operation, not any privileged bypass: a member creates a request, gets partial confirmation, and later (for entirely legitimate reasons — key rotation, offboarding, compromise response) the multisig votes to remove one of the confirming members via the normal `DeleteMember`/`DeleteKey` action. The stale confirmation remains exploitable until the request is separately deleted or fully re-confirmed. Given `REQUEST_COOLDOWN` is only 15 minutes and requests otherwise remain pending indefinitely, the window in which a stale confirmation can be leveraged is realistic in normal operational timelines (e.g., a slow k-of-n approval combined with membership rotation).

### Recommendation
When removing a member (`delete_member` in `multisig2/src/lib.rs`, and the `DeleteKey` handler in `multisig/src/lib.rs`), also scan `self.confirmations` for all request IDs and remove the departing member's/key's entry from every confirmation set — not just requests they authored. Alternatively, have `confirm()` re-validate (or `execute_request`/threshold-check) that every entry counted in the confirmation set corresponds to a currently live member/key before treating it as satisfying `num_confirmations`.

### Proof of Concept
Conceptual sequence (Rust, using existing `multisig2` test harness patterns as in `multisig2/src/lib.rs` tests around line 655):
1. `MultiSigContract::new(vec![A, B, C], 2)`.
2. As `B`: `add_request(transfer_request)` → `request_id`.
3. As `A`: `confirm(request_id)` → confirmations = `{A}` (below threshold of 2, request stays pending).
4. As multisig (2-of-3 confirmed): execute `DeleteMember { member: A }` (via its own request/confirm flow) — `A` is removed from `self.members`; `delete_member` does not touch `request_id`'s confirmation set because that request's `member` field is `B`, not `A`.
5. As `C`: `confirm(request_id)` → `confirmations.len() (1) + 1 = 2 >= num_confirmations (2)` → request executes, transferring funds, despite only `C` (a currently live member) having confirmed it directly and `A` no longer being part of the multisig. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
