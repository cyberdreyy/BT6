### Title
`parse_confidential_transfer_instruction` Withdraw branch misreports a `rangeProofContextStateAccount` as `owner`/`multisigOwner` when both proofs use context-state accounts but only the minimum account count is supplied - ([File: transaction-status/src/parse_token/extension/confidential_transfer.rs])

### Summary
In the `Withdraw` arm of `parse_confidential_transfer_instruction`, the account-index advancement heuristic assumes there is always at least one account left over for `owner` after inserting proof-context accounts, using the guard `offset < account_indexes.len().saturating_sub(1)`. When an attacker crafts a `Withdraw` instruction with `equality_proof_instruction_offset == 0` and `range_proof_instruction_offset == 0` (both proofs are context-state accounts, which legitimately requires 5 accounts) but supplies only the minimum 4 accounts accepted by `check_num_token_accounts`, the range-proof-context insertion is silently skipped and the account that should be `rangeProofContextStateAccount` is instead attributed to `owner`.

### Finding Description
The Withdraw branch only enforces a minimum of 4 accounts: [1](#0-0) 

but the real minimum required when both proofs are `ContextStateAccount` (i.e. `equality_proof_instruction_offset == 0 && range_proof_instruction_offset == 0`, exercised by the "All Contexts" test case) is 5 accounts: `account`, `mint`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`, `owner`.

The advancement logic is: [2](#0-1) 

With `account_indexes.len() == 4` and both offsets `== 0`:
- `has_sysvar` is `false`, so the sysvar branch is skipped.
- `offset = 2`, bound `= len - 1 = 3`. `2 < 3` is true → `equalityProofContextStateAccount = accounts[2]`, `offset` becomes 3.
- Next check: `3 < 3` is false → the `rangeProofContextStateAccount` insertion is skipped entirely, even though `range_proof_instruction_offset == 0` signals a context account is expected.
- `parse_signers` is then called with `offset = 3`, so `accounts[3]` is reported as `owner` (or `multisigOwner`).

In a correctly-formed 5-account instruction, `accounts[3]` would be the `rangeProofContextStateAccount`, and `accounts[4]` would be the real owner. By truncating the account list to 4 and setting both offsets to 0, the attacker causes the parser to (a) silently drop the `rangeProofContextStateAccount` field from the parsed JSON and (b) mislabel that same account as `owner`/authority. This is purely a client-supplied instruction encoding issue — `check_num_token_accounts` performs only a length check and never validates the length against the semantic combination of proof offsets, so nothing in the parsing path rejects this malformed-but-decodable input.

### Impact Explanation
This is a decoder misreporting bug in `transaction-status`, reachable by any client submitting a transaction (even one that may fail on-chain execution, since instruction display/parsing for `getTransaction`/`getBlock` with `jsonParsed` encoding is independent of execution success). Any integrator or wallet relying on the parsed `owner` field for a `withdrawConfidentialTransfer` instruction can be shown an attacker-chosen account as the "owner"/authority, while the actual proof-context account for the range proof is silently hidden from the output. This matches the "decoder panic and misreporting" bounty category — no crash, but a wrong/misleading semantic value is returned for a query.

### Likelihood Explanation
Fully attacker-controlled and requires only one crafted, submitted transaction: the attacker chooses the `ConfidentialTransferInstruction::Withdraw` data bytes with `equality_proof_instruction_offset = 0` and `range_proof_instruction_offset = 0`, and supplies exactly 4 account indices in the instruction. No special privileges, keys, or validator control are needed; the transaction only needs to make it into a confirmed block (it does not need to succeed) for `getTransaction`/`getBlock` with jsonParsed encoding to run this parser over it. This is deterministically reproducible.

### Recommendation
Make `check_num_token_accounts` for `Withdraw` (and the analogous `Transfer`/`TransferWithFee` arms which use the same pattern) depend on the actual number of context-state accounts implied by the proof offsets, rather than a fixed minimum of 4. Concretely, compute the expected account count as `2 (account, mint) + (1 if has_sysvar else 0) + (number of offsets == 0) + 1 (owner)` and validate `account_indexes.len()` against that value before applying the offset-advancement heuristic, or track remaining accounts more explicitly instead of relying on `saturating_sub(1)` reserving exactly one trailing slot.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (test module)
#[test]
fn test_withdraw_underfunded_accounts_misattributes_owner() {
    use solana_instruction::{AccountMeta, Instruction};
    use solana_message::Message;

    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let range_ctx_that_should_not_be_owner = Pubkey::new_unique();
    let fourth_account = Pubkey::new_unique();

    // Manually construct a Withdraw instruction with:
    // - equality_proof_instruction_offset == 0
    // - range_proof_instruction_offset == 0
    // - only 4 accounts total (minimum accepted by check_num_token_accounts)
    let data = build_withdraw_instruction_data(/* amount */ 1, /* decimals */ 0,
        /* eq_offset */ 0, /* range_offset */ 0);

    let instruction = Instruction {
        program_id: spl_token_2022_interface::id(),
        accounts: vec![
            AccountMeta::new(account, false),
            AccountMeta::new_readonly(mint, false),
            AccountMeta::new_readonly(range_ctx_that_should_not_be_owner, false),
            AccountMeta::new_readonly(fourth_account, false),
        ],
        data,
    };

    let message = Message::new(&[instruction], None);
    let parsed = parse_token(
        &message.instructions[0],
        &AccountKeys::new(&message.account_keys, None),
    )
    .unwrap();

    // Expected (bug): rangeProofContextStateAccount is silently missing
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());

    // Expected (bug): the account meant to be rangeProofContextStateAccount
    // is instead reported as "owner"
    assert_eq!(
        parsed.info["owner"],
        json!(fourth_account.to_string())
    );
    // This assertion demonstrates the misattribution: `range_ctx_that_should_not_be_owner`
    // is silently dropped from the output entirely, and `fourth_account` (which should be
    // the range-proof context account) is reported as the authority/owner instead.
}
```
Expected result confirming the bug: `parsed.info["equalityProofContextStateAccount"] == account_indexes[2]`, no `rangeProofContextStateAccount` key present, and `parsed.info["owner"] == account_indexes[3]` — demonstrating that with a 4-account, dual-context-offset Withdraw instruction, the parser drops a real proof-context account and reports it (or a different account than the true, 5th, owner account) as `owner`.
