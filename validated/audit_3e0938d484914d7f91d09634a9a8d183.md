### Title
Reorg-timing check treats an unseen/never-approved competing tenure block as instantly late, letting a miner bypass the anti-reorg timing guard - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs`, around lines 204-290) decides whether a new tenure is allowed to reorg away a prior tenure that already mined a block. The decision is supposed to hinge on how much time elapsed between when the signer *approved* the reorged tenure's first block and when the new sortition arrived (`proposal_to_sortition`), compared against `first_proposal_burn_block_timing`. When `local_block_info.approved_time` is `None`, the code substitutes `proposal_to_sortition = 0` and logs "considering it as a late-arriving proposal," which trivially satisfies `Duration::from_secs(0) < first_proposal_burn_block_timing` and unconditionally permits the reorg via `superseded_tenures.push(tenure)`.

### Finding Description
The guard is meant to enforce: "only allow a reorg of a tenure with an already-mined block if that block's proposal arrived suspiciously close to the next sortition" (i.e., a legitimate tie-break race), and to refuse reorgs of tenures that had a healthy amount of time to be signed. This is exactly analogous to the external report's flaw: a proxy value (`CONFIRMATION_BLOCKS` / here, "did we locally approve it") is used as a stand-in for real chain state / real timing, and an adversarial actor can manufacture the edge case where the proxy signals "safe" when the underlying state is not.

Here, `approved_time` is `None` whenever this signer has no local record of having approved/pre-committed the reorged tenure's first block — which happens whenever the proposal simply never reached (or was never processed in time by) this particular signer, for reasons entirely under an attacking/competing miner's control (e.g., selectively delaying or omitting the StackerDB broadcast of the tenure-start proposal to a subset of signers while the block is nonetheless mined and can be independently observed via `first_block_mined`/`tenures_reorged`). In that case the code does not treat "no local timing information" conservatively (as it does one branch above, where `local_block_info` being entirely absent causes an explicit `Ok(false)` refusal); instead it defaults to the most permissive branch, treating the missing data as proof of lateness and greenlighting the reorg. [1](#0-0) 

Contrast this with the sibling branch just above it, which explicitly refuses the reorg when there is no local knowledge at all: [2](#0-1) 

The asymmetry is the bug: "we have a DB record for the block but never approved it" is treated identically to "the proposal just arrived" (safe to reorg), when in fact it can equally mean "we never got a fair chance to sign it because gossip was manipulated against us," which is the case the whole timing guard exists to prevent.

### Impact Explanation
This directly weakens the reorg-timing safety guard that gates `check_parent_tenure_choice`, which feeds `check_proposal` in both v1 and v2 chainstate paths and ultimately marks a miner's sortition as valid/invalid and records a superseded tenure (`mark_tenure_superseded`) that later suppresses the older tenure's block as a signed conflict (see `reorg_permit_stands`/`conflict_still_blocks` in `stacks-signer/src/v0/signer.rs`). If the guard is bypassed, signers can be led to sanction a reorg of a tenure whose block should still be protected, i.e., signing/accepting a competing (non-canonical, from the deceived signer's perspective) tenure-start block and superseding a signature that should still stand — this falls under "a signer signing an invalid/non-canonical/conflicting block" per the impact categories, since it undermines the equality the guard exists to protect (approved-parent vs. canonical choice). [3](#0-2) 

### Likelihood Explanation
Exploiting this requires only a single miner (the one proposing the reorging tenure, or a colluding party controlling gossip timing to a specific signer) to ensure a target signer never records `approved_time` for the reorged tenure's first block before the next sortition — no majority of signers or other signers' keys are needed, matching the in-scope "one-slot miner (plus gossip)" threat model. However, exploitability depends on the specific conditions of `get_first_approved_block_in_tenure` returning `Some(local_block_info)` with `approved_time == None` (i.e., some DB record exists but no approval timestamp was ever set), which I could not fully confirm from the available index — the query implementation for `get_first_approved_block_in_tenure` in `stacks-signer/src/signerdb.rs` was not retrieved before the session ended, so I cannot state with certainty which block states leave `approved_time` unset while still being returned by that query.

### Recommendation
Treat a missing `approved_time` the same way missing `local_block_info` is treated — as insufficient information to sanction a reorg — rather than defaulting to `proposal_to_sortition = 0` (the most permissive outcome). At minimum, require a positive determination that the block's proposal genuinely arrived late (e.g., by consulting the node directly for the block's actual observed/mined timestamp) rather than inferring "late" from local absence of an approval record, since that absence is attacker-influenceable via selective proposal delivery.

### Proof of Concept
Not independently reproduced in a test harness; the reasoning is based on static code review of `stacks-signer/src/chainstate/mod.rs` lines 204-290. I was unable to verify, within the remaining investigation budget, the exact DB query behind `get_first_approved_block_in_tenure` (whether it can return a record with `approved_time == None`) — a Devin session with full repo access should confirm this by reading `stacks-signer/src/signerdb.rs`'s `get_first_approved_block_in_tenure` implementation and writing a unit test mirroring `stacks-signer/src/chainstate/tests/v2.rs`'s `reorg_timing_testing` helper, but with a `local_block_info` that has `approved_time = None`, to confirm the reorg is unconditionally permitted regardless of the actual elapsed time to sortition.
