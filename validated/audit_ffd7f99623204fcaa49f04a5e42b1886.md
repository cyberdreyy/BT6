### Title
Per-signer local wall-clock burn-block receipt time makes `check_parent_tenure_choice`'s reorg-timing verdict diverge across signers - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg a prior tenure by comparing, in real time, the gap between when *this signer* recorded a reorged tenure's first block as approved and when *this signer* recorded receiving the burn block that starts the new sortition. Because that receipt timestamp is captured locally per signer (via `SignerDb::get_burn_block_receive_time`, populated at `insert_burn_block` time) rather than derived from a value all signers agree on, ordinary network/propagation delay near the `first_proposal_burn_block_timing` boundary can make signers reach opposite verdicts on the identical reorg — exactly the class of bug described in the report, where a decision boundary is evaluated against wall-clock time at the moment of local processing instead of a value fixed at proposal time.

### Finding Description
`check_parent_tenure_choice` is used by `check_proposal` and `validate_tenure_change_payload` (chainstate/v1.rs, v2.rs) to decide whether a tenure-change block that does not build on the prior sortition is a permitted reorg or must be rejected (`RejectReason::ReorgNotAllowed`): [1](#0-0) 

The core timing computation is: [2](#0-1) 

`sortition_state_received_time` comes from `signer_db.get_burn_block_receive_time(&self.burn_block_hash)`, which is populated when *this signer's* event loop processes the `NewBurnBlock` event and calls `insert_burn_block` with a locally-generated `SystemTime::now()` — not a value that is broadcast or otherwise synchronized across signers. `approved_at` (`local_block_info.approved_time`) is likewise a purely local timestamp, stamped the first time this signer pre-committed or locally accepted the reorged tenure's first block: [3](#0-2) 

The decision `Duration::from_secs(proposal_to_sortition) < first_proposal_burn_block_timing` therefore hinges on two independently-observed local clocks that can differ across signers by however much StackerDB/event delivery jitter exists between them — the report's exact pattern of "a boundary computed from wall-clock time at execution rather than a value fixed at submission/proposal time," which lets ordinary transaction/message delay flip the outcome across participants.

This is directly acknowledged and unit-tested as a hard cutoff (30s allowed vs 31s not allowed in the same test harness): [4](#0-3) 

The consequence: for a tenure-change block proposed near this boundary, some signers (those whose local burn-block receipt or block-approval timestamps landed them just inside the window) will treat the reorg as **permitted** — marking the reorged tenure `superseded` via `mark_tenure_superseded` and signing the new tenure's block — while other signers (whose local clocks landed them just outside the window) will treat the identical reorg as **not permitted**, reject the block with `ReorgNotAllowed`, and continue to regard the old tenure's block as canonical. This breaks the "approved-parent vs canonical" equality: the same proposed block is simultaneously a canonical continuation for one group of signers and an invalid/non-canonical reorg for another, without any signer acting incorrectly relative to its own local information — no majority collusion, no key compromise, and no consensus/gossip requirement beyond a miner naturally proposing a tenure-change block near the boundary.

### Impact Explanation
Depending on how the signer population splits at this local-clock boundary:
- If enough signers land in the "permitted" bucket to reach the ~70% signing threshold, a subset of signers ends up **signing a block that other signers correctly consider a disallowed, non-canonical reorg** of the network's canonical tenure — a Critical-class outcome per the stated criteria (a signer signing a non-canonical/conflicting block).
- If the population splits without either side reaching threshold, no side can converge and the tenure stalls, requiring the existing `capitulate_viewpoint`/`capitulate_miner_view_timeout` mechanism to eventually paper over the disagreement (a High-class liveness wedge until that timeout fires) — but that recovery path itself only converges signers to a *shared node-observed tip*, not necessarily to a definitively-correct verdict about whether the reorg should have been permitted at all.

### Likelihood Explanation
Likelihood is driven purely by ordinary network/propagation timing, not adversarial control: any tenure-change proposal whose reorg-permission window (`first_proposal_burn_block_timing`, default 60s per `sample/conf/signer/mainnet-signer-conf.toml`) is close to the actual gap between the prior tenure's approval and the new sortition's arrival is exposed. Because `sortition_state_received_time` and `approved_time` are both stamped independently per-signer at local wall-clock time, even sub-second StackerDB/event-loop delivery jitter across ten-plus geographically distributed signers is sufficient to place different signers on opposite sides of the cutoff whenever the true gap is near the threshold — this does not require the miner or any signer to act maliciously, mirroring the report's "constant probabilistic leak" argument for delayed-transaction bugs. A one-slot miner could also intentionally time its tenure-change proposal to land close to this boundary to increase the odds of a split verdict.

### Recommendation
Do not gate this permission decision on each signer's independently observed wall-clock receipt/approval timestamps. Instead, derive the timing comparison from data that all signers can agree on, e.g., the sortition/burn-block's own on-chain timestamps (`burn_header_timestamp`) for both endpoints, or require some quorum-confirmed timestamp before evaluating the cutoff, so that every signer computes the same verdict for the same reorg regardless of its own event-processing latency.

### Proof of Concept
1. A tenure T1 signs and locally-approves its first (and only) block at signer-local time `t0` (recorded independently by each signer as `approved_time`).
2. A new sortition's burn block is delivered to different signers with natural network jitter; signer A processes it (and stamps `insert_burn_block`) at `t0 + 59s`, signer B at `t0 + 61s`, both real timings that occur naturally without any single party controlling delivery order.
3. The incoming miner (miner-controlled, single actor, no consensus needed) proposes a tenure-change block for T2 that reorgs T1 instead of building on it.
4. `check_parent_tenure_choice` computes, for signer A, `proposal_to_sortition = 59s < first_proposal_burn_block_timing (60s)` → reorg **permitted**, T1 marked superseded, signer A pre-commits/signs T2's block.
5. For signer B, `proposal_to_sortition = 61s ≥ 60s` → reorg **refused**, signer B rejects T2's block with `RejectReason::ReorgNotAllowed`, per the same logic exercised in [4](#0-3) .
6. Signers A and B now hold mutually exclusive views of which block is canonical for the same height, with signer A having already produced a valid signature over a block signer B considers an invalid reorg — reproducing the equality break called for in the rules, triggered purely by the natural delivery-timing gap described in the referenced report.

Note: I was not able to fully trace every call site of `insert_burn_block` (e.g., exact event-loop invocation timing in `stacks-signer/src/v0/signer.rs`) within the available iterations to confirm whether any additional synchronization step exists before `get_burn_block_receive_time` is read; based on the code and tests inspected, no such synchronization is present, but a full audit of `stacks-signer/src/v0/signer.rs`'s `insert_burn_block` call sites would be needed to rule out a mitigating step I did not locate.

        &self,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        first_proposal_burn_block_timing: &Duration,
    ) -> Result<bool, SignerChainstateError> {
        // if the parent tenure is the last sortition, it is a valid choice.
        // if the parent tenure is a reorg, then all of the reorged sortitions
        //  must either have produced zero blocks _or_ produced their first (and only) block
        //  very close to the burn block transition.
        if self.prior_sortition == self.parent_tenure_id {
            return Ok(true);
        }
        info!(
            "Most recent miner's tenure does not build off the prior sortition, checking if this is valid behavior";
            "sortition_state.consensus_hash" => %self.consensus_hash,

            "sortition_state.parent_tenure_id" => %self.parent_tenure_id,
        );

            client.get_tenure_forking_info(&self.parent_tenure_id, &self.prior_sortition)?;
