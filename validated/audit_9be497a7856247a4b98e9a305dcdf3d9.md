Based on my investigation, I found a genuine analog to the reported bug class: **code that assumes an ID/context represents one category of caller without actually validating that assumption**, leading to a privilege/authorization confusion — mirroring how `_ownerOf` assumed a token ID was always a 1x1 quad without checking.

### Title
Missing caller-type validation lets External Initiators impersonate authenticated users when triggering job runs by ID - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController.Create` decides whether a caller is allowed to trigger a job run by integer ID based on `auth.GetAuthenticatedUser(c)`, under the stated assumption that "only users are allowed to run jobs using int IDs - EIs not allowed" [1](#0-0) . However, `GetAuthenticatedUser` merely type-asserts whatever object was stored under `SessionUserKey` in the gin context [2](#0-1) , and `AuthenticateExternalInitiator` (the middleware used to authenticate External Initiator (EI) requests) explicitly stores a `*clsessions.User{Role: clsessions.UserRoleRun}` under that same key [3](#0-2) .

### Finding Description
The root cause is structurally identical to the reported analog: a function receives an identifier/context value (here, the authenticated identity in `gin.Context`) and acts on an unstated assumption about which "kind" of value it holds — a genuine logged-in Chainlink user versus a lower-trust External Initiator — without validating that assumption. Just as `_ownerOf` never checked that an `id` was actually a 1x1 quad before letting `burn`/`approve` act on it, `PipelineRunsController.Create` never checks that the object behind `SessionUserKey` originated from `AuthenticateBySession`/`AuthenticateByToken` rather than `AuthenticateExternalInitiator`. Since `AuthenticateExternalInitiator` deliberately sets the same context key to satisfy other role checks (`RequiresRunRole`, etc.), `isUser` in `Create` will be `true` for EI-authenticated requests too, defeating the intended restriction that "EIs [are] not allowed" to run jobs by integer job ID.

### Impact Explanation
Historically, External Initiators were restricted to trigger only the specific webhook job(s) that explicitly listed them in `externalInitiators = [...]` in the job's TOML spec — this is the entire point of the `external_initiator_webhook_specs` join table [4](#0-3) . If this integer-ID `Create` path is reachable by EI-authenticated requests (the code's comment implies it is meant to be blocked, which suggests it was previously reachable), an EI with valid access-key/secret for one job could trigger execution of **any** job in the node by numeric ID, bypassing the intended job-to-initiator authorization binding. This would let an unprivileged/lower-trust actor (an external initiator credential, which is far less privileged than a node operator's session/API token) force pipeline runs for unrelated jobs, potentially causing unauthorized on-chain transactions, resource exhaustion, or unintended fund-moving job executions depending on job types configured on the node.

### Likelihood Explanation
This requires an attacker to already hold valid credentials for at least one External Initiator (a legitimately lower-trust, remotely-facing credential type explicitly designed to be exposed to third parties for triggering webhook runs) and to know or guess a target job's integer ID (`c.Param("ID")`, sequential integers). No source/on-chain privilege is needed beyond one EI credential.

### Recommendation
Do not rely on `auth.GetAuthenticatedUser` alone to distinguish EI-originated identities from real user sessions/API tokens. Introduce an explicit, distinct context key/type (e.g. checking `SessionExternalInitiatorKey` is unset, or a dedicated `IsExternalInitiator(c)` helper) and use it in `PipelineRunsController.Create` (and any other handler making the same "isUser" assumption) to positively reject requests authenticated via `AuthenticateExternalInitiator`. Additionally, audit all other call sites of `auth.GetAuthenticatedUser` for the same conflation risk now that EI requests populate `SessionUserKey`.

### Proof of Concept
1. Register two independent jobs (e.g., an OCR job with ID 5, owned/managed by the node operator) and a webhook job with an associated External Initiator `ei-A` (ID doesn't matter, EI only needs valid AccessKey/Secret).
2. As the holder of `ei-A`'s credentials only (no session cookie, no API token), send:
   `POST /v2/jobs/5/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to `ei-A`'s credentials.
3. `AuthenticateExternalInitiator` succeeds and sets `SessionUserKey` to a `User{Role: UserRoleRun}` [3](#0-2) .
4. In `Create`, `auth.GetAuthenticatedUser(c)` returns `ok=true`, so `isUser` is `true`, and `prc.App.RunJobV2(ctx, 5, nil)` is invoked [5](#0-4)  — triggering job 5 even though `ei-A` was never associated with that job.

**Verification limitation:** I was unable to confirm within tool-call budget which specific `authMethod`s (`AuthenticateBySession`, `AuthenticateByToken`, `AuthenticateExternalInitiator`) are actually chained onto the `/v2/jobs/:ID/runs` POST route registration in `core/web/router.go` (the grep matched 16 lines there but I ran out of iterations before reading them). If that route is registered only with `AuthenticateBySession`/`AuthenticateByToken` (excluding `AuthenticateExternalInitiator`), then this specific endpoint would not be reachable by EI credentials and the impact would be limited to defense-in-depth / code-assumption fragility rather than an exploitable bypass today. I recommend a Devin session read `core/web/router.go` in full to confirm the exact middleware chain for this route before treating this as confirmed-exploitable.
