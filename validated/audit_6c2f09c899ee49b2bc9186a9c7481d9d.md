## Finding: Confirmed

### Title
Stale confirmations from deleted members count toward `num_confirmations` threshold, allowing request execution below live-member quorum - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` compares `confirmations.len() as u32 + 1` against `self.num_confirmations`, where `confirmations` is a `HashSet<String>` of member identities stored per `request_id`. `delete_member` only purges confirmations/requests for requests whose *creator* (`r.member`) equals the removed member, but never scrubs that member's confirmation entries from requests they merely *confirmed* but did not create. A request can therefore execute (moving funds) once the stored confirmation count reaches the threshold even though one or more of those stored confirmations belong to accounts/keys no longer present in `self.members`.

### Finding Description
The invariant this code is supposed to maintain is:
`count(entries in confirmations[request_id] that are ∈ self.members) + 1 >= self.num_confirmations`

but the code actually checks:
`confirmations.len() as u32 + 1 >= self.num_confirmations` [1](#0-0) 

`confirmations` is populated purely by string identity in `confirm`, with no re-validation against current membership for previously-stored entries [2](#0-1) .

`delete_member`'s cleanup only removes requests/confirmations where the removed member is the *original creator* of the request (`r.member == member`); it does not scan `confirmations` values for stale entries belonging to the removed member on requests created by someone else: [3](#0-2) 

Exploit flow:
1. Multisig has 4 members (threshold `num_confirmations = 3`): `alice`, `bob` (accounts) and two `AccessKey` members, `key1`, `key2` (installed via `add_member`, which grants only the restricted `MULTISIG_METHOD_NAMES` function-call access — `add_request,delete_request,confirm,add_and_confirm_request`) [4](#0-3) .
2. `alice` creates a `Transfer` request (creator = `alice`), `bob` confirms, then `key2` confirms — `confirmations = {bob, key2}` (2 of 3, request pending).
3. Separately, a legitimate `DeleteMember{key2}` request (created by `alice`) is confirmed by `alice` and `bob` and executes, removing `key2` from `self.members`. `delete_member`'s filter only targets requests created *by* `key2`, so the pending transfer request (created by `alice`) is untouched, and its stored confirmations `{bob, key2}` are never purged [5](#0-4) .
4. `key1` (the only remaining member who hasn't confirmed) calls `confirm` on the pending transfer request. `confirmations.len()` is `2` (`{bob, key2}`), `+1 = 3 >= num_confirmations(3)` — the check passes and `execute_request` runs the `Transfer`, moving funds, even though only `bob` and `key1` are actual live members among the approvers; `key2`'s confirmation is stale.

`assert_valid_request` and `current_member()` only gate the *caller* of `confirm`/`add_request` against current membership [6](#0-5) ; they do nothing to revalidate the previously-accumulated `confirmations` set, so none of the existing guards catch this.

### Impact Explanation
Funds (`Transfer`, or any other `MultiSigRequestAction` including `AddKey`/`FunctionCall`) held by the multisig account can be moved with fewer distinct live-member approvals than `num_confirmations` mandates — a direct violation of the K-of-N guarantee the contract exists to provide. This matches the explicitly listed Critical impact: "a multisig request executed below `num_confirmations` live members." It is repeatable on any multisig instance across any request as long as membership churn happens between a partial confirmation and the request's final confirmation.

### Likelihood Explanation
This requires normal, expected multisig operation: a partially-confirmed request outstanding at the time one of its confirmers is removed from the member set (a routine event — key rotation, offboarding, compromise response). No special privilege beyond ordinary use of the function-call-restricted access key (`add_request`, `confirm`) is needed to trigger the stale-confirmation accumulation; the only "attacker-controlled" element is timing the removal relative to the still-pending confirmation, which is entirely feasible in real-world member rotation and does not require a full-access key. Cost is negligible (a few `confirm`/`delete_request` gas fees); the bug is fully deterministic once the ordering condition is met, and is reproducible on every multisig instance deployed from this contract.

### Recommendation
When executing `DeleteMember`, scan all requests' `confirmations` sets (not just requests created by the removed member) and remove the deleted member's entry from every one of them; alternatively, revalidate each stored confirmation's membership at the time the threshold check runs in `confirm`, counting only entries that are still `self.members.contains(...)`.

### Proof of Concept
```rust
#[test]
fn test_stale_confirmation_after_member_removal_meets_threshold() {
    let amount = 1_000;
    // members(): alice (Account), bob (Account), key1 = Eg2j... (AccessKey), key2 = TEST_KEY (AccessKey)
    testing_env!(context_with_account(alice(), amount));
    let mut c = MultiSigContract::new(members(), 3); // 4 members, threshold 3

    // 1. alice creates the transfer request (creator = alice)
    let transfer_req = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let transfer_id = c.add_request(transfer_req);

    // 2. bob confirms
    testing_env!(context_with_account(bob(), amount));
    c.confirm(transfer_id);
    // 3. key2 (TEST_KEY) confirms -> confirmations = {bob, key2}, still pending (2 < 3)
    testing_env!(context_with_key(
        PublicKey::try_from(TEST_KEY.to_vec()).unwrap(), amount
    ));
    c.confirm(transfer_id);
    assert_eq!(c.confirmations.get(&transfer_id).unwrap().len(), 2);

    // 4. Remove key2 via a fully legitimate DeleteMember request created by alice
    let key2_member = MultisigMember::AccessKey {
        public_key: PublicKey::try_from(TEST_KEY.to_vec()).unwrap(),
    };
    testing_env!(context_with_account(alice(), amount));
    let del_id = c.add_request(MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteMember { member: key2_member.clone() }],
    });
    c.confirm(del_id); // alice confirms (creator implicitly not auto-confirmed by add_request)
    testing_env!(context_with_account(bob(), amount));
    c.confirm(del_id); // bob confirms -> 2+1>=3, executes DeleteMember{key2}

    // key2 is no longer a member
    assert!(!c.get_members().contains(&key2_member));

    // BINDING CHECK: pending transfer request's stale confirmations were NOT purged
    assert_eq!(c.confirmations.get(&transfer_id).unwrap().len(), 2); // still {bob, key2}

    // 5. key1 (Eg2j...) confirms the transfer -> threshold check uses stale count
    testing_env!(context_with_key(
        PublicKey::from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()),
        amount
    ));
    c.confirm(transfer_id); // executes: 2 (stale) + 1 >= 3, request removed/executed

    // Live confirmers were only {bob, key1} = 2, strictly less than num_confirmations = 3
    assert_eq!(c.requests.len(), 0); // request executed despite only 2 live-member approvals
}
```
This test demonstrates the equality `confirmations.len() + 1 >= num_confirmations` (code's check, satisfied) diverging from `count(live members in confirmations) + 1 >= num_confirmations` (the true invariant, which is `2 + 1 - 1(stale) = 2 < 3`, violated), while the funds transfer executes.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
