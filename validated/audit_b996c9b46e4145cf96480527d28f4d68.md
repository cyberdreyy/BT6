### Title
Proposer self-slashing erases the builder's pending payment obligation, letting a builder's already-canonical block go unpaid — ([File: specs/gloas/beacon-chain.md])

### Summary
The Gloas fork's `process_proposer_slashing` was modified to delete the `BuilderPendingPayment` entry associated with a slashed proposer's proposal, whenever that proposal is still inside the 2-epoch settlement window [1](#0-0) . Because a validator can trigger its own slashing at will (equivocation is fully within a single proposer's control), a proposer can unilaterally erase the payment obligation that a builder owes for a block that has already been made canonical and whose execution payload has already been (or will be) applied — an escaped builder payment, analogous to the auction "refund can be blocked so the bidder keeps the win without paying" pattern in the referenced report.

### Finding Description
In Gloas, when a proposer accepts a builder's bid via `process_execution_payload_bid`, a `BuilderPendingPayment` is recorded, tracking `withdrawal.amount`/`fee_recipient` and the `proposer_index` who is meant to receive the payment [2](#0-1) . This payment accumulates attester "weight" via `process_attestation` [3](#0-2)  and, once quorum is reached, is flushed into a real `BuilderPendingWithdrawal` (and eventually an actual balance-decreasing `Withdrawal`) by `process_builder_pending_payments` [4](#0-3) .

`process_proposer_slashing` was modified so that, if the slashed validator is the `proposer_index` recorded on a still-pending payment within the 2-epoch window, that payment is wiped out entirely:

```python
if payment.proposer_index == header_1.proposer_index:
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()
``` [5](#0-4) 

The equality this breaks: a builder that had its bid accepted and its block made canonical (payload delivered, gas paid by the builder, users benefiting from the execution) is supposed to unconditionally owe the committed `bid.value` to the block's `fee_recipient` once the block is part of the canonical chain. A single proposer, by intentionally double-signing a header for its own past slot (a fully self-contained, no-coalition action — comparable to "Bidder 1" putting themselves on a blacklist in the original report), can retroactively cancel that payment obligation before quorum/settlement completes, with no compensating mechanism to redirect the value elsewhere. The builder keeps the Gwei that the protocol had already committed it to pay for a block that is not reverted.

### Impact Explanation
This falls under the High severity bucket "a builder payment or withdrawal misdirected, doubled or escaped." The block/payload itself is not rolled back — only the payment obligation is deleted — so a builder can, in effect via proposer collusion (which requires no protocol-level coalition beyond the pre-existing bid/fee_recipient relationship the protocol already assumes), obtain a canonical, paid-for-by-nobody payload. This is a value-transfer bug, not merely a loss of the slashed proposer's own stake: the beneficiary of the erased payment is the builder (a distinct party), and the intended fee_recipient permanently loses the Gwei it was owed.

### Likelihood Explanation
The action requires only a single validator (the proposer of the slot in question) to sign two conflicting headers for a slot where it already accepted a non-zero-value bid, and to submit that `ProposerSlashing` before the payment reaches quorum/settlement (within the 2-epoch window). No other node's cooperation, client bug, or network partition is required to trigger the code path; only an off-protocol incentive (e.g., a kickback from the builder) motivates why a validator would sacrifice its stake to do this, but the mechanism itself is fully self-inflicted and deterministic.

### Recommendation
When the slashed proposer is the recorded `proposer_index` of a pending builder payment, do not simply erase (`.empty()`) the payment — instead ensure the committed amount is still enqueued as a `BuilderPendingWithdrawal` (payable to the original `fee_recipient`, or to a protocol-defined sink) rather than discarded, so that slashing a proposer changes *who* benefits from stake slashing but never allows a builder to skip paying for an already-canonical block.

### Proof of Concept
1. Builder `B` submits `SignedExecutionPayloadBid` with `value = V > 0`, accepted by proposer `P` at slot `S`; `process_execution_payload_bid` records a `BuilderPendingPayment` with `proposer_index = P` [6](#0-5) .
2. Block at slot `S` becomes canonical; PTC/attesters begin accumulating `weight` toward quorum, but quorum has not yet been reached (payment still pending, e.g. still within the first sub-epoch window) — see `test_process_builder_pending_payments_below_quorum` for the below-quorum, not-yet-flushed state [7](#0-6) .
3. `P` (who signed the block at slot `S`) also signs a second, conflicting `BeaconBlockHeader` for slot `S`, and submits a `ProposerSlashing` referencing both headers, while still within the 2-epoch settlement window.
4. `process_proposer_slashing` finds `payment.proposer_index == P` and sets `state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()` [5](#0-4) , matching the exact behavior asserted by `test_builder_payment_deletion_current_epoch` / `test_builder_payment_deletion_previous_epoch` [8](#0-7) .
5. Result: `P`'s stake is slashed (self-inflicted loss), but `B`'s canonical block at slot `S` — already executed/finalized on the EL — is never charged the committed `V` Gwei; no `BuilderPendingWithdrawal`/`Withdrawal` for that bid is ever created.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def test_process_builder_pending_payments_below_quorum(spec, state):
    """Test payment below quorum threshold - should not be processed."""
    # Advance past genesis epochs

    next_epoch(spec, state)

    builder_index = 0
    amount = spec.MIN_ACTIVATION_BALANCE
    quorum = spec.get_builder_payment_quorum_threshold(state)

    # Add pending payment with weight below quorum
    payment = create_builder_pending_payment(spec, builder_index, amount, weight)
