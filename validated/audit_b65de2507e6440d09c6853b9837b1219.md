### Title
Node-side signer weight double-counting when a signer flips a prior rejection to an acceptance - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
In the node's StackerDB response listener, `total_weight_approved` and `total_weight_rejected` are tracked in two separate, imperfectly-synchronized dedup guards. A signer that first rejects a block and later legitimately reconsiders and accepts it (a documented, supported behavior) gets its weight counted into *both* totals, because the acceptance path's dedup check only looks at `gathered_signatures`, never at `responded_signers` (which was already populated by the earlier rejection).

### Finding Description
`BlockStatus` tracks `responded_signers: HashSet<u32>`, `gathered_signatures: BTreeMap<u32, MessageSignature>`, `total_weight_approved`, and `total_weight_rejected`. [1](#0-0) 

On a `Rejected` message, the dedup guard is `if block.responded_signers.insert(slot_id)`, so the first rejection from a slot adds weight into `total_weight_rejected` and marks that slot as "responded": [2](#0-1) 

On an `Accepted` message, the dedup guard is instead `if !block.gathered_signatures.contains_key(&slot_id)` — it never checks `responded_signers`: [3](#0-2) 

Because a prior `Rejected` message never touches `gathered_signatures`, a signer that later sends an `Accepted` for the same block passes the `!gathered_signatures.contains_key(&slot_id)` check and has its weight added to `total_weight_approved` — while its earlier weight contribution to `total_weight_rejected` is never removed (there is no subtraction path; `reset_rejections` only fires on an explicit proposal-retry timeout, not on a per-signer vote flip): [4](#0-3) 

The result: the same signer's weight is simultaneously present in both `total_weight_rejected` and `total_weight_approved`. This breaks the equality that `total_weight_rejected` should reflect only signers currently opposed to the block, and `total_weight_approved` only signers currently in favor — the two sets are supposed to be disjoint per-signer, and the code enforces this via `responded_signers` for the reject path but not for the accept path.

This is a genuine one-slot-miner-observable path: the miner's `SigningCoordinator` consumes exactly these two counters when deciding a block's fate. [5](#0-4) 

Note that the rejection-crossing check is evaluated *before* the approval-crossing check in that loop, so a stale/duplicated rejection weight (from a signer who has since switched to accept) can trip the "blocking minority" branch even though the real, current opposing weight is lower than what is recorded.

The signer-side codebase (`stacks-signer/src/signerdb.rs`) is aware of exactly this accept/reject overlap hazard and defends against the accept→reject direction (a test `accept_then_reject` proves a rejection after an acceptance is rejected/not counted), consistent with the CHANGELOG entry "Do not count both a block acceptance and a block rejection for the same signer/block." [6](#0-5) [7](#0-6) 

However, that guard/test lives in the signer's own local bookkeeping DB, not in the node's `stackerdb_listener.rs`, and the node-side implementation has no analogous protection for the reject→accept direction that this codebase explicitly supports elsewhere (a signer legitimately "reconsiders a block proposal that it previously rejected" for some reject reasons): [8](#0-7) 

### Impact Explanation
This is a liveness-class issue, not a signature-forgery issue: no invalid signature is produced and no cryptographic equality is broken. But it corrupts the vote tally the miner uses to make a Critical decision (whether to abandon the block as globally rejected or push it as globally accepted). Because the rejection branch is checked first in `signer_coordinator.rs`, an inflated/stale `total_weight_rejected` (carrying weight from a signer who has since switched to accept) can cause the miner to erroneously conclude a block was rejected by a blocking minority and abandon a block that a real-time majority would actually approve — a wedge on progress/liveness for that block, forcing a re-mine. It does not by itself let a signer sign an invalid/conflicting block or let a rejection be recounted as an approval of a *different* block; the corruption is confined to the node-local, in-memory tally used to decide when to stop waiting for signatures.

### Likelihood Explanation
Reachable by a single ordinary signer's own legitimate behavior (no majority, no key compromise, no auth_token needed): the signer stack already supports reconsidering certain rejections and later accepting the same proposal. Any one signer taking that documented reject→accept path against a block the current miner is tracking triggers the double count. This requires no malicious signer, just normal timing (e.g., a signer initially rejects due to a stale-view reason, then re-evaluates and accepts once conditions change) — a routine, expected event during proposal retries/timeouts.

### Recommendation
In the `Accepted` branch of `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, gate the `total_weight_approved` increment (and treat the transition) using the same `responded_signers` set the `Rejected` branch uses, and when a signer that is already recorded in `responded_signers` via a prior rejection now accepts, subtract its weight from `total_weight_rejected` (and remove any per-txid `failed_txids` contribution it made) before adding it to `total_weight_approved`, mirroring the one-vote-per-signer invariant already enforced signer-side in `signerdb.rs`'s `add_block_signature`/`add_block_rejection_signer_addr` pair.

### Proof of Concept
1. Miner proposes block B; `StackerDBListenerComms::insert_block` creates a fresh `BlockStatus` with all counters zero.
2. Signer S (weight w_S) sends `BlockResponse::Rejected` for B. `responded_signers.insert(S)` succeeds → `total_weight_rejected += w_S`.
3. Signer S later reconsiders (a supported reject-reason path) and sends `BlockResponse::Accepted` for B, with a valid signature.
4. In the `Accepted` handler, `block.gathered_signatures.contains_key(&S)` is `false` (only `Rejected` was ever processed for S), so `total_weight_approved += w_S` executes.
5. Now both `total_weight_rejected` and `total_weight_approved` include `w_S`. If enough other signers are near the rejection or approval thresholds, `signer_coordinator.rs`'s check `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can fire using S's stale rejected weight even though S currently approves, causing the miner to abandon a block it should have accepted (or vice versa, depending on which branch is hit first with the corrupted numbers).

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
