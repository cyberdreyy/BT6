### Title
External-initiator credentials for one bridge can trigger job runs for **any** job via `POST /v2/jobs/:ID/runs`, violating request-to-job binding - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` unconditionally injects a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` into the gin context for *any* valid external-initiator (EI) key/secret pair, with no association to the specific job/bridge the EI was created for. `PipelineRunsController.Create` (the only run-role-gated endpoint reachable via this auth method) then uses `auth.GetAuthenticatedUser(c)` merely to detect "is this a user vs. an EI", but since the EI middleware fakes a `User`, that check silently passes for EI callers too, letting any EI credential invoke `RunJobV2` on an arbitrary job ID.

### Finding Description
The route is registered in [1](#0-0) , wrapping `PipelineRunsController.Create` with `auth.RequiresRunRole` behind `auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)`.

In `AuthenticateExternalInitiator`, once a request's EI access-key/secret pair is validated against *any* row in the `external_initiators` table (`store.FindExternalInitiator` + `bridges.AuthenticateExternalInitiator`), the middleware sets both the EI context key and a synthetic run-role user: [2](#0-1) 

`RequiresRunRole` only checks `user.Role != clsessions.UserRoleView`, so this synthetic run-role user passes: [3](#0-2) .

Inside `PipelineRunsController.Create`, the code attempts to gate integer-ID job runs to "real" users only, with a comment stating EIs are not allowed to use this path: [4](#0-3) 

However `isUser` comes from `auth.GetAuthenticatedUser(c)`, which merely checks for presence of the `SessionUserKey` in the gin context — it cannot distinguish a genuine session/token user from the fake `User{Role: UserRoleRun}` object injected by `AuthenticateExternalInitiator`. Since that key is always set for EI-authenticated requests too, `isUser` evaluates `true` for EI callers, defeating the intended guard, and `prc.App.RunJobV2(ctx, jobID, nil)` is invoked with an attacker-supplied `jobID` that has no relationship to the authenticating EI's bridge/job at all.

Historically, webhook jobs were triggered via job-specific UUIDs tied to a given EI/job pairing, providing implicit request binding. That mechanism has been removed ("Webhook runs used external job UUIDs; that job type has been removed" — line 103-107 above) but the replacement integer-ID path never re-implemented any binding between the authenticated EI and the target job. There is no lookup anywhere in this handler (or in `RunJobV2`) that verifies the EI recorded on the job's `ExternalInitiatorSpec`/bridge matches the EI that authenticated the request.

### Impact Explanation
Any holder of a valid, low-privilege external-initiator key/secret (issued solely to trigger runs for one specific bridge/job) can trigger pipeline runs for **any** job on the node by integer ID, including jobs belonging to unrelated bridges/integrations they were never authorized to touch. Depending on job type this can move funds, submit transactions, or otherwise perform actions reserved for a different, more trusted integration — a authorization/role-bypass and unauthorized job-run class impact.

### Likelihood Explanation
- Minimal precondition: possession of any one valid EI access key/secret (these are routinely distributed to external services, i.e. lower trust than admin/edit users).
- No knowledge of the target job's owning EI credentials is required — only the numeric job ID, which is discoverable via `GET /v2/jobs` (also reachable by EI-injected run-role user since that route has no role wrapper) or simply guessed/enumerated (small integers).
- Fully reproducible with a single crafted HTTP request; no race conditions or timing needed.

### Recommendation
In `PipelineRunsController.Create` (and generally wherever `AuthenticateExternalInitiator` is composed with `AuthenticateByToken`/`AuthenticateBySession`), distinguish real authenticated users from EI-injected pseudo-users, e.g. by checking `auth.GetAuthenticatedExternalInitiator(c)` first and rejecting/branching accordingly, rather than relying on `GetAuthenticatedUser` presence alone. Additionally, when a request is authenticated via `AuthenticateExternalInitiator`, verify that the target job's associated external initiator ID matches `ei.ID` before invoking `RunJobV2`, restoring REQUEST_BINDING between the credential and the job it is authorized to trigger.

### Proof of Concept
1. In a Go test (e.g. extending `core/web/pipeline_runs_controller_test.go`), seed two jobs, Job A bound to `ExternalInitiator A` and Job B bound to `ExternalInitiator B`, both non-webhook job types accepting integer IDs.
2. Build a gin engine mirroring `v2Routes`'s `userOrEI` group: `auth.Authenticate(store, auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` wrapping `auth.RequiresRunRole(prc.Create)` on `POST /v2/jobs/:ID/runs`.
3. Send `POST /v2/jobs/<Job B's integer ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` (per `static.ExternalInitiatorAccessKeyHeader/SecretHeader`) set to External Initiator A's credentials.
4. Assert the response is `200 OK` with a created pipeline run resource for Job B (i.e. `prc.App.RunJobV2` was invoked with Job B's ID), proving EI-A triggered a run for a job it has no association with.
5. Contrast with expected behavior: assert should be `401/403` since EI-A's credentials should only be valid for Job A's associated job/bridge.

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
