### Title
`IdleCreditVault.deposit` and `depositDuringEpoch` credit the full requested `_amount` without measuring actual tokens received — fee-on-transfer underlying breaks vault solvency - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug is "accounting records the transfer *parameter*, not the actual balance delta." The idle-tranches credit vault has the identical pattern in its core deposit path: `IdleCreditVault.deposit` pulls `_amount` via `safeTransferFrom` and mints `_amount` strategy tokens 1:1 without measuring what actually arrived, and `IdleCDOEpochVariant.depositDuringEpoch` mints tranche tokens priced off `_amount` plus `mintStrategyTokens(_amount)` after `_transferUnderlyingsFrom(msg.sender, address(this), _amount)`. If the vault's underlying is any fee-on-transfer or deflationary token, every deposit mints more claim value than the cash received, and the shortfall is socialized across later withdrawers.

### Finding Description
In `IdleCreditVault.deposit` (contracts/strategies/idle/IdleCreditVault.sol:596-617):

```solidity
function deposit(uint256 _amount) external virtual override returns (uint256) {
    _onlyIdleCDO();
    if (_amount > 0) {
        underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
        _mint(msg.sender, _amount);   // mints parameter, not received amount
    }
    ...
    totEpochDeposits += _amount;      // counter also uses parameter
    return _amount;
}
```

There is no `balanceBefore`/`balanceAfter` measurement anywhere in the CDO → strategy deposit path. The same parameter-trusting pattern repeats at every cash ingress:

- `collectInstantWithdrawFunds(_amount)` decrements `pendingInstantWithdraws` by `_amount` before/along the transfer (lines 398-403).
- `collectWithdrawFunds(_amount)` computes `lossRecoveryPriceByEpoch` and rewrites `pendingWithdraws` from the parameter `_amount` (lines 411-430). With a FOT token, the funded basis is marked fully covered while less cash actually arrived, so `lossRecoveryPriceByEpoch[epoch]` is recorded as `RECOVERY_FULL` (or a higher price) than what the contract can pay.
- `depositDuringEpoch` (contracts/IdleCDOEpochVariant.sol:656-690) mints tranche tokens priced on `_amount` and calls `mintStrategyTokens(_amount)` — again the parameter.
- `finalizeDefaultRecovery(_recoveredAmount, ...)` sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` (line 686) where `_recoveredAmount` is the parameter, not the received delta — recovery claims would be under-collateralized and the last claimant's `_transferDefaultRecovery` reverts or drains others' share.

Notably, `TrancheWrapper._deposit` *does* measure `beforeBal - afterBal` (contracts/TrancheWrapper.sol:226-238) — but only to report `deposited`; the shares minted come from `depositAA/depositBB` which still credit `_amount`, so the wrapper does not mitigate the root issue.

Broken invariant: fair mint/burn and solvency — 1 strategy token ≠ 1 underlying after a FOT deposit, so NAV is overstated and withdraw receipts outnumber backing.

### Impact Explanation
Direct theft + insolvency. A KYC-passed lender deposits `_amount` of a FOT underlying, receives tranche tokens (and the strategy mints receipt backing) worth `_amount`, while the vault only received `_amount * (1 - f)`. On `requestWithdraw`/`claimWithdrawRequest` the attacker extracts full basis; the deficit is borne by other LPs, whose claims either pay out at an implicitly reduced rate or revert on insufficient balance in `claimWithdrawRequest`/`_transferFundedClaim`. If it hits `collectWithdrawFunds`, every pending receipt of that epoch is marked funded at a recovery price the contract cannot honor — permanent freezing of unclaimed yield for the last claimants.

### Likelihood Explanation
Requires the vault's `token` to charge transfer fees. Most current Pareto/Clearpool vaults use USDC (no fee), so exploitation needs either a new vault deployed on a FOT token or an underlying that introduces fees. This lowers likelihood to Medium, but no guard anywhere in the protocol rejects such tokens and the accounting breaks silently rather than reverting.

### Recommendation
Measure balance deltas at every ingress: in `IdleCreditVault.deposit`, `collectInstantWithdrawFunds`, `collectWithdrawFunds`, and `finalizeDefaultRecovery`, snapshot `underlyingToken.balanceOf(address(this))` before `safeTransferFrom` and use the delta for minting, `totEpochDeposits`, `pendingWithdraws`/`pendingInstantWithdraws` decrements, `lossRecoveryPriceByEpoch`, and `defaultRecoveryReserve`. Do the same around `_transferUnderlyingsFrom` in `depositDuringEpoch` before pricing the minted tranche tokens.
