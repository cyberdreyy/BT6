### Title
Cross-user response hijacking via unauthenticated MessageId collision in gateway WebAPI handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's `handler.savedCallbacks` map, which routes DON node responses back to the originating HTTP client, is keyed solely by the client-supplied `MessageId` (the `body.message_id` field, which the gateway derives directly from the JSON-RPC request `ID` supplied by the calling client). There is no binding between the stored callback and the identity/session of the request that created it, and the map entry is unconditionally overwritten on collision.

### Finding Description
`HandleLegacyUserMessage` stores the caller's response `Callback` in a shared map keyed only by the message ID taken from the incoming (unauthenticated, user-controlled) request: [1](#0-0) 

The message ID itself originates from `req.ID` on the inbound JSON-RPC request and is copied verbatim into `MessageBody.MessageId`, with no server-side uniqueness enforcement or scoping to a session/sender: [2](#0-1) 

When a DON node later responds, the handler looks up and removes the callback purely by that same string key and delivers the response to whatever `Callback` is currently stored there: [3](#0-2) 

This is structurally analogous to the reported ERC777 bug class: a critical piece of state (`balanceBefore`/leaf amount in the original report; here, the `savedCallbacks[messageId]` entry) is written using a value that is trusted/assumed unique across the lifetime of an in-flight operation, but an unprivileged actor can race/collide that key before the legitimate operation completes, causing the shared state to be silently overwritten in favor of the attacker. In the original bug, the attacker's re-entrant call overwrote the accounted deposit amount; here, an attacker who submits a request with the same `MessageId` as a pending legitimate request from a different user overwrites `savedCallbacks[id]` with their own `Callback`. When the DON later replies for the original (legitimate) request, `handleWebAPITriggerMessage`/`handleWebAPIOutgoingMessage` will deliver that response to the attacker's callback instead of the original caller's — a cross-user response confusion.

### Impact Explanation
If exploited, an unprivileged client could receive another user's workflow-trigger/HTTP-target response body, which may contain sensitive computed data intended for a different caller (cross-user response confusion — one of the explicitly accepted analog classes). The original legitimate caller would either receive no response (timeout) or the attacker's spoofed data, depending on timing of the second overwrite.

### Likelihood Explanation
Exploitability requires the attacker to:
1. Know or predict the exact `MessageId`/request `ID` used by a legitimate concurrent request (this is the key open question — I could not confirm from the indexed code whether callers are expected/required to use cryptographically random, unpredictable IDs, or whether the gateway enforces uniqueness anywhere upstream of `HandleLegacyUserMessage`).
2. Win the race by submitting their colliding request while the legitimate one is still pending in `savedCallbacks` (window bounded by `CallbackMaxAgeSec`, default 120s, per `defaultCallbackMaxAgeSec`).

I was not able to fully verify, within the available index, what component assigns `MessageId` on the actual inbound HTTP path from an external client (i.e., whether it is always attacker-chosen, or sometimes server-generated) — this is necessary to establish full exploitability with certainty; it should be confirmed by reading the full HTTP ingress path (outside `core/services/gateway/handlers/*`) in a Devin session with complete file access, since the index may not include every file in the ingress chain.

### Recommendation
- Scope `savedCallbacks` keys to a value not solely controlled by the client (e.g., a server-generated internal request key derived from `(sender, MessageId)` or a server-side UUID), rather than trusting the raw `MessageId`.
- Reject or de-duplicate collisions instead of silently overwriting an existing `savedCallbacks` entry in `HandleLegacyUserMessage`.
- Bind the stored callback to the authenticated identity/session of the caller, and verify that identity matches before delivering the DON's response back through `handleWebAPITriggerMessage`.

### Proof of Concept
Conceptual PoC (cannot be fully validated without confirming client-facing ID assignment, per Likelihood section above):
1. Legitimate User A sends a WebAPI trigger request with `message_id = "X"`; the gateway calls `HandleLegacyUserMessage`, storing `savedCallbacks["X"] = CallbackA`, then forwards the request to DON nodes.
2. Before the DON responds, Attacker sends a second request also using `message_id = "X"` (if permitted to choose/predict it), causing `savedCallbacks["X"] = CallbackAttacker` to overwrite the prior entry.
3. When a DON node responds for User A's original request (echoing `message_id = "X"`), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `CallbackAttacker`, deletes the entry, and sends User A's response payload to the Attacker's HTTP connection instead of User A's.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
