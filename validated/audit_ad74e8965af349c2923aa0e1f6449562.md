### Title
Out-of-bounds panic in `jsonParsed` instruction decoding for v0 transactions when account-key count excludes lookup-table addresses - (File: `transaction-status/src/lib.rs`)

### Summary
`parse_ui_instruction` (`transaction-status/src/lib.rs:113-126`) unconditionally indexes `account_keys[instruction.program_id_index as usize]` (line 118) with no bounds check, unlike sibling parsers (`parse_token`, `parse_bpf_loader`, `parse_address_lookup_table`) which explicitly validate `instruction.accounts.iter().max() < account_keys.len()` before indexing. The `v0::Message::encode()` (without meta) at lines 794-818 builds the `AccountKeys` used for this call from `AccountKeys::new(&self.account_keys, None)` — i.e., **static keys only**, silently dropping the "loaded/dynamic" addresses that a v0 message's `address_table_lookups` may reference. This is the same bug class as H-6: a downstream consumer (`parse_ui_instruction`) assumes an invariant ("program_id_index and account indices are always within `account_keys.len()`") that is only guaranteed when the *full* set of addresses (static + ALT-loaded) is present, but one code path (`encode()`, as opposed to `encode_with_meta()`) reconstructs `AccountKeys` while omitting the loaded-address component that the runtime actually appended when compiling/executing the instruction.

### Finding Description
For a `v0` transaction whose `program_id_index` (or any `accounts[i]`) refers to an address loaded via an address-lookup-table (i.e., index `>= static_account_keys.len()`), calling `.encode(UiTransactionEncoding::JsonParsed)` on the bare `v0::Message` (not `encode_with_meta`) produces an `AccountKeys` view sized to only the static keys count. `parse_ui_instruction` then does:
```rust
let program_id = &account_keys[instruction.program_id_index as usize];
``` [1](#0-0) 
which indexes past the end of the vector, panicking (`index out of bounds`) inside the RPC/CLI worker thread processing the request.

Compare to the "correct" invariant-checking siblings that treat this exact condition as reachable/untrusted input and return an error instead of panicking: [2](#0-1) [3](#0-2) 

The two divergent `v0::Message` encoders: [4](#0-3) [5](#0-4) 

The `encode()` path omits `meta.loaded_addresses` (uses `LoadedAddresses::default()`), while the `encode_with_meta()` path correctly includes them via `AccountKeys::new(&self.account_keys, Some(&meta.loaded_addresses))`. This mirrors the HSG bug pattern: one path ("enableModule/encode_with_meta") maintains the required invariant on a derived count/collection, while a second path ("bypassing module add/encode without meta") skips it, and a downstream consumer trusts the invariant unconditionally and indexes without a bounds check, causing a hard failure instead of a bounded fallback.

### Impact Explanation
This is a decoder panic reachable from processing already-persisted, otherwise valid v0 transactions that use address-lookup-table accounts for their program id or instruction accounts, whenever code calls the meta-less `Message::encode` path for `jsonParsed` on a `v0::Message`. Per the validation criteria, a decoder panic/misreporting on unprivileged read paths (JSON-RPC transaction/instruction decoding) is in-scope impact. A panic in the RPC handling thread manifests as a crash/error surfaced to the operator process depending on how panics are caught in that async context; at minimum it is a hard failure and wrong/incomplete data returned for that request, matching the "decoder panic and misreporting" acceptance criterion.

### Likelihood Explanation
Reaching this from live RPC surfaces (`getTransaction`, `getBlock`) requires those call sites to go through `Message::encode` rather than `encode_with_meta`; the primary `VersionedTransactionWithStatusMeta::encode` path (`transaction-status/src/lib.rs:522-548`) does call `encode_with_meta`, which is the safe path for `EncodedTransaction`. I was not able to fully confirm within this session whether any production JSON-RPC or CLI code path calls the bare, meta-less `v0::Message::encode(JsonParsed)` directly on a v0 message with ALT-referencing instructions (as opposed to always going through `encode_with_meta`); the two encoders otherwise appear designed for different call sites (with vs. without associated `TransactionStatusMeta`). This uncertainty means likelihood is not fully proven; it may be low-severity/no-impact if no unprivileged-reachable caller exists that supplies a v0 message with ALT-loaded program/account indices to the meta-less `encode()`.

### Recommendation
1. Make `parse_ui_instruction` defensively bounds-check `instruction.program_id_index` and each entry of `instruction.accounts` against `account_keys.len()` before indexing, mirroring the pattern already used in `parse_token`, `parse_bpf_loader`, and `parse_address_lookup_table`, returning a `PartiallyDecoded`/error variant instead of panicking.
2. Audit all call sites of `v0::Message::encode(UiTransactionEncoding::JsonParsed)` (the meta-less variant) to confirm whether any of them can receive a message whose instructions reference lookup-table-loaded accounts; if so, require `encode_with_meta` there instead, or fail closed with an `EncodeError` rather than silently using `LoadedAddresses::default()`.

    fn encode_with_meta(
        &self,
        encoding: UiTransactionEncoding,
        meta: &TransactionStatusMeta,
    ) -> Self::Encoded {
        if encoding == UiTransactionEncoding::JsonParsed {
            let reserved_account_keys = ReservedAccountKeys::new_all_activated();
            let account_keys = AccountKeys::new(&self.account_keys, Some(&meta.loaded_addresses));
            let loaded_message = LoadedMessage::new_borrowed(
                self,
                &meta.loaded_addresses,
                &reserved_account_keys.active,
            );
            UiMessage::Parsed(UiParsedMessage {
                account_keys: parse_v0_message_accounts(&loaded_message),
                recent_blockhash: self.recent_blockhash.to_string(),
