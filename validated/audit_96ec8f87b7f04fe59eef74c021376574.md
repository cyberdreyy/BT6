## Title
Removing a multisig member does not purge their stale confirmations from other pending requests, allowing a request to execute below the live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`delete_member` (in `multisig2`) and the `DeleteKey` action (in `multisig`) only clean up requests that were *created* by the removed member/key. They never scan the `confirmations` map to strip that member's prior confirmations from requests created by *someone else*. Because `confirm()` counts `confirmations.len()` without verifying that every entry is still a current member, a stale confirmation from an already-removed member can still count towards `num_confirmations`, letting a request execute with fewer live, currently-authorized confirmations than the configured threshold.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` decides execution purely on set size: [1](#0-0) 

`delete_member()` only removes requests whose *creator* (`r.member`) equals the removed member; it does not touch the `confirmations` set of any other still-pending request that the removed member had already confirmed: [2](#0-1) 

The same gap exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` filters outstanding requests `by public_key` (i.e. requests *signed/created* by that key) and removes their confirmations, but does not purge that key's confirmation entry from confirmation sets of requests created by other keys: [3](#0-2) [4](#0-3) 

This breaks the intended equality `confirmations counted == confirmations from live members`. After a member is removed, `confirmations.len()` can still include their earlier vote, so the number of *live* confirmers required to push a request past `num_confirmations` is silently reduced by one for every stale confirmation left in the set.

### Impact Explanation
This falls squarely under the Critical impact category "a multisig request executed below threshold." A pending `Transfer`, `FunctionCall`, `AddKey`, or `AddMember` request can be executed with fewer than `num_confirmations` currently-valid members having approved it in the post-removal membership set, effectively lowering the K in the K-of-N scheme without any explicit `SetNumConfirmations` action. This directly undermines the security guarantee the multisig is supposed to provide (moving funds/keys only with K live approvals).

### Likelihood Explanation
This requires no unusual privilege beyond normal multisig operation: any request can be left partially confirmed while membership changes occur (a routine event — rotating keys, offboarding members, revoking a compromised key). No attacker-controlled deployment, oracle, or governance bypass is needed; it is a straightforward sequencing of standard, permitted multisig actions (`add_request`, `confirm`, `DeleteMember`/`DeleteKey`), making it readily reachable in normal contract lifecycle.

### Recommendation
When removing a member/key (`delete_member` / `DeleteKey`), iterate over the `confirmations` map for *all* outstanding requests (not just ones the removed member created) and remove that member's entry from every confirmation set. Alternatively, have `confirm()` re-validate that every address/key present in a request's confirmation set is still a current member before counting it toward the threshold.

### Proof of Concept
1. Initialize a multisig with members `A, B, C, D` and `num_confirmations = 3`.
2. `C` calls `add_request` to create request `R1` (e.g., a large `Transfer`).
3. `A` calls `confirm(R1)` → `confirmations(R1) = {A}`.
4. `D` calls `confirm(R1)` → `confirmations(R1) = {A, D}` (2 of 3 needed).
5. Separately, members execute a `DeleteMember { member: D }` request (via the normal 3-confirmation flow) to remove `D` from the multisig — this succeeds via `execute_request` → `delete_member`, per [5](#0-4) . `delete_member` only removes requests created by `D`; since `D` did not create `R1`, `R1` and its confirmation set `{A, D}` are left untouched, per [6](#0-5) .
6. `B` (a live member) calls `confirm(R1)`. `confirmations(R1).len() + 1 == 3 >= num_confirmations`, so `R1` executes, per [7](#0-6) .
7. `R1` (the `Transfer`) is executed even though only `A` and `B` are still live members who approved it — `D`'s confirmation is stale and should not count. The request executed with 2 live approvals against a nominal 3-of-N threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
