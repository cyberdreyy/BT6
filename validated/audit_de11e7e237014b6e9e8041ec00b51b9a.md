### Title
Stale-epoch instant-withdraw receipts escape default haircut and drain the recovery reserve at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` records a user's claim basis under the epoch active at request time (`instantWithdrawsRequestsByEpoch[user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`), but `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` only ever look at `instantWithdrawClaimsByEpoch[epochNumber]` / `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — i.e. the *current* epoch at finalization. An unfunded instant receipt created in an earlier epoch is therefore excluded from the default-claim basis (inflating `defaultRecoveryPrice`), yet remains in `instantWithdrawsRequests[user]` and is paid out **at par** by `claimInstantWithdrawRequest` through `_transferFundedClaim`, which only checks `balance - defaultRecoveryReserve >= amount`. The result is recovery-reserve insolvency: earlier claimants (including the attacker) over-claim, and later defaulted-epoch claimants' `_transferDefaultRecovery` either underflow-reverts or pays nothing.

### Finding Description
The QR-decoder heap overflow class maps to credit-vault terms as *a claim recorded under one index (epoch bucket) being dereferenced under a different index*, letting a receipt slip past the haircut bounds.

Relevant code (all in `contracts/strategies/idle/IdleCreditVault.sol`):

- Request-time indexing (lines 367–374): `currentEpoch = epochNumber; instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount; instantWithdrawClaimsByEpoch[currentEpoch] += _amount;`
- Finalization basis (lines 644–649): `basis = pendingWithdraws; if (pendingInstantWithdraws != 0) basis += instantWithdrawClaimsByEpoch[epochNumber];` — only the finalization-time epoch bucket is counted.
- Per-user defaulted claim (lines 842–848): `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — same single-epoch lookup, so the older receipt is untouched and stays in `instantWithdrawsRequests[_user]`.
- Par payout (lines 387–392): `claimInstantWithdrawRequest` burns the full `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim`, whose only guard (lines 899–905) is `balance - reserve >= amount`; the stale receipt's basis was never added to the reserve requirement.

`epochNumber` increments in `deposit` while an epoch is running (lines 607–611), and `collectInstantWithdrawFunds` can leave `pendingInstantWithdraws` partially unfunded (lines 398–403), so an instant receipt can legitimately survive a `stopEpoch` boundary while still unpaid.

### Impact Explanation
Broken invariant: one receipt one payout at the correct recovery ratio. A stale-epoch receipt is paid 1:1 even though it was part of the defaulted queue, while the reserve and `defaultRecoveryPrice` were computed without its basis. Attacker extracts the inflated recovery share; honest defaulted-epoch claimants' claims revert on `defaultRecoveryReserve -= _amount` underflow or are paid from an emptied balance — direct theft plus permanent freezing of remaining claims, quantified as `staleReceipt * (1 - fairPrice)` stolen and up to the full `defaultRecoveryReserve` shortfall for last claimants.

### Likelihood Explanation
Requires: an instant withdraw requested in epoch N, `stopEpoch` (honest manager) that only partially funds the instant queue (`collectInstantWithdrawFunds` < pending), then borrower default in epoch N+1 finalized via `finalizeDefaultRecovery`. The attacker only needs to be a KYC-passing lender holding tranche tokens to place the instant request and later claim. Partial instant funding at stop is a normal failure mode (borrower shortfall), and defaults are a designed-for state, so reachability is realistic. Existing guards don't stop it: `_transferFundedClaim`'s reserve check uses a reserve that already excludes the stale basis, and `_claimDefaultedInstantWithdrawRequest` silently misses the earlier epoch bucket.

### Recommendation
In `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest`, aggregate `instantWithdrawClaimsByEpoch` / `instantWithdrawsRequestsByEpoch` across *all* epochs with unfunded instant basis (e.g. track a global `pendingInstantBasis` incremented at request and decremented on claim/collect), or block `startEpoch`/`stopEpoch` from advancing `epochNumber` while `pendingInstantWithdraws != 0`. Add a regression test: instant request in epoch N → partial fund at stop → default finalize in epoch N+1 → assert the stale claim is haircut, not paid at par.

### Proof of Concept
Foundry fork outline (fixture: deployed `IdleCreditVault` + `IdleCDOEpochVariant`, impersonated borrower/manager only for honest protocol calls; attacker is a normal lender):

```solidity
// Epoch N running
cdo.depositAA(attacker, 100e6);            // attacker deposits, KYC'd
vault.requestInstantWithdraw(60e6, attacker); // via cdo, epochNumber = N
// honest manager stops epoch; borrower only returns part of instant queue
vm.prank(manager); cdo.stopEpoch();         // epochNumber -> N+1 via deposit()
// collectInstantWithdrawFunds pulls only 30e6 -> pendingInstantWithdraws = 30e6
// borrower defaults in epoch N+1
vm.prank(manager); cdo.stopEpochWithDuration(0, loss); // defaulted
vm.prank(manager); cdo.finalizeDefaultRecovery(recovered, source);
// BUG: defaultPendingClaimBasis() used instantWithdrawClaimsByEpoch[N+1],
// so the 60e6 epoch-N receipt was excluded from totalBasis ->
// defaultRecoveryPrice inflated.
// Attacker claim: _claimDefaultedInstantWithdrawRequest finds 0 at epoch N+1,
// falls through, burns instantWithdrawsRequests[attacker]=60e6 and pays 60e6 at par.
vault.claimInstantWithdrawRequest(attacker); // via cdo -> 60e6, not 60e6*price
// Honest claimant in the true default epoch now reverts/underpays on
// _transferDefaultRecovery because reserve was sized for a smaller basis.
assertEq(underlying.balanceOf(attacker), attackerPrincipal + 60e6); // over-paid
```
