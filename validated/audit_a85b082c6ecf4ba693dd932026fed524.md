### Title
Missing validation on `underlyingsRequested` lets any EOA seize a lender's escrowed tranche tokens for zero payment - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The analog of the Starklane `depositTokens` missing `msg.value` validation is `IdleCreditVaultWriteOffEscrow.createWriteOffRequest` / `fullfillWriteOffRequest`. `createWriteOffRequest` validates `amount != 0` for the escrowed tranche tokens but performs no sanity check on `underlyingsRequested` — the price the lender expects to be paid. Because `fullfillWriteOffRequest` only enforces `_underlyings >= currentRequest.underlyings` and can be called by any wallet (no KYC, no borrower check), a request created with `underlyingsRequested == 0` (or dust) can be fulfilled by anyone paying nothing, and the fulfiller receives all of the lender's escrowed tranche tokens, which carry a real claim on vault funds.

### Finding Description
In `createWriteOffRequest` the only input check is on the tranche amount:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:86-101
if (amount == 0) revert NotAllowed();
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
```

There is no `underlyingsRequested != 0` check and no minimum-price enforcement. Fulfillment then checks only a lower bound on the payment, and is permissionless ("this function can be called by any wallet"):

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:123-151
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
...
underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
underlyingToken.safeTransfer(_user, _underlyings - _totFee);
IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```

With `underlyings == 0`, `_underlyings = 0` satisfies the check, the exit fee computes to 0, the lender receives 0 underlyings, and the fulfiller receives the full `tranches` balance escrowed. The tranche tokens the attacker obtains are redeemable claims: they can be sold into another write-off request, or claimed via `requestWithdraw`/`claimWithdrawRequest`/`claimInstantWithdrawRequest` on `IdleCDOEpochVariant` for underlying (subject to KYC, which an attacker can pass or bypass by reselling the receipt to a KYC'd buyer).

### Impact Explanation
Permanent loss of the lender's escrowed tranche tokens (whose value equals the tranche's underlying claim, e.g. `tranchePrice` × balance) with zero compensation. This mirrors the external report's impact: a user-submitted economic parameter is not validated, the protocol executes anyway, and the user's assets are irreversibly consumed. Unlike the Starklane case where funds are merely stuck pending cancellation, here the escrowed tranches are directly transferred to a third-party fulfiller — direct theft of the tranche position.

### Likelihood Explanation
Requires a lender to create (or top up) a write-off request with a zero/dust `underlyingsRequested`, i.e. user misconfiguration rather than a purely opportunistic exploit — same likelihood class as the external report (user sends wrong payment parameter). However, the consequence is strictly worse (immediate, permissionless seizure vs. temporary lockup), and nothing in the UI-facing contract warns or blocks the zero-price request. Any EOA can monitor `WriteOffRequest` creations and fulfill a zero-priced request atomically in the same block it appears.

### Recommendation
- Revert in `createWriteOffRequest` when `underlyingsRequested == 0` while `amount > 0`, or require the total `underlyings` for the merged request to be non-zero.
- Optionally enforce a minimum recovery ratio (e.g. `underlyings >= tranches * minPrice / ONE_TRANCHE`) to prevent dust-priced requests.
- Consider a confirmation/two-step for request creation, or emit the implied price in an event so integrators can warn users.

### Proof of Concept
Foundry test against the existing harness in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`:

```solidity
function testFulfillZeroPricedWriteOffRequest() external {
    // LP accidentally creates a write-off request asking 0 underlyings
    vm.prank(LP);
    escrow.createWriteOffRequest(10000e18, 0); // 10k tranches, 0 USDC requested

    (uint256 tranches, uint256 underlyings) = escrow.userRequests(LP);
    assertEq(tranches, 10000e18);
    assertEq(underlyings, 0);

    // any unprivileged EOA fulfills it paying nothing
    address attacker = makeAddr("attacker");
    uint256 attackerTranchePre = tranche.balanceOf(attacker);
    uint256 lpUnderlyingPre = underlying.balanceOf(LP);

    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, 10000e18, 0); // succeeds: _underlyings(0) >= requested(0)

    // attacker seized all escrowed tranche tokens for free
    assertEq(tranche.balanceOf(attacker) - attackerTranchePre, 10000e18);
    // lender received nothing (0 payment, 0 fee)
    assertEq(underlying.balanceOf(LP) - lpUnderlyingPre, 0);
    (tranches, underlyings) = escrow.userRequests(LP);
    assertEq(tranches, 0);
    assertEq(underlyings, 0);
}
```

The existing `testFullfillWriteOffRequest` confirms the fulfil path reverts only on `WrongRequest` when `_underlyings < requested`; with `requested == 0` no revert occurs and the full tranche amount moves to the caller.
