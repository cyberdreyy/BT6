### Title
Unbounded `connAttempts` map growth via repeated `StartHandshake` calls enables gateway memory-exhaustion DoS - ([File: core/services/gateway/connectionmanager.go])

### Summary
`connectionManager.newAttempt` inserts a new entry into `m.connAttempts` on every call to `StartHandshake`, keyed by a monotonically increasing counter, with no cap on the number of outstanding attempts per node or globally. Any client that can produce (or replay) a validly-signed, timestamp-tolerant auth header can repeatedly call `StartHandshake` to grow this map without bound until the entries are cleaned up via `FinalizeHandshake`/`AbortHandshake` or connection timeouts.

### Finding Description
`StartHandshake` (`core/services/gateway/connectionmanager.go:196-224`) validates the auth header's signature, DON ID, gateway ID, and timestamp tolerance (`AuthTimestampToleranceSec`), then unconditionally calls `m.newAttempt` [1](#0-0) . `newAttempt` increments `connAttemptCounter` and stores a new `connAttempt` struct in `m.connAttempts[newId]` for every call, with no check for how many attempts already exist for that `nodeAddress` and no maximum map size [2](#0-1) .

The HTTP entrypoint `handleRequest` in `core/services/gateway/network/wsserver.go` calls `s.acceptor.StartHandshake(authBytes)` for every incoming request that presents a base64 auth header under the size limit, before any websocket upgrade occurs [3](#0-2) . Cleanup of an entry only happens on `FinalizeHandshake` success, or on `AbortHandshake` triggered by websocket-upgrade failure or a failed/slow `ReadMessage` (bounded by `ReadTimeoutMillis`/`HandshakeTimeoutMillis`, default 10s) [4](#0-3) . There is no per-node cap, no global cap, and no de-duplication of attempts for the same auth header/nodeAddress — each call, even with an identical header content, produces a fresh map entry via the incrementing counter.

Because attempts persist for up to the configured read/handshake timeout before being aborted, an attacker who can supply a validly-signed auth header for a known node address (either because they hold that node's private key, or because they replay a captured valid header within `AuthTimestampToleranceSec`) can issue requests faster than the timeout window elapses, causing `connAttempts` to grow unbounded and consuming gateway memory/CPU.

### Impact Explanation
This is a resource-exhaustion / availability issue against the gateway's `ConnectionManager`: sustained abuse can grow `connAttempts` without bound, consuming memory and CPU (map operations under a single mutex, `connAttemptsMu`), potentially starving or slowing down legitimate node reconnection handshakes for the entire gateway process. This maps to a Chainlink bounty "Denial of Service" class impact rather than authentication bypass or fund movement — no signature/authorization check is bypassed, only the lack of a quota on in-flight attempts.

### Likelihood Explanation
Exploitability depends heavily on the precondition already noted in the question: the attacker needs a validly-signed auth header for a legitimate node address. If the attacker does not hold a node's private key, this is limited to replaying a previously captured valid header within `AuthTimestampToleranceSec` seconds — a narrow, network-observation-dependent window, not something achievable purely as an "unauthenticated client of the node API." If the attacker does hold a node's signing key, this is a malicious-node scenario, which is explicitly out of scope per the audit rules. Absent either precondition, an attacker cannot produce inputs that pass signature verification in `UnpackSignedAuthHeader`/`common.ExtractSigner`, so `StartHandshake` will reject requests with `ErrChallengeInvalidSignature`/`ErrAuthInvalidNode` before reaching `newAttempt`. Thus feasibility for a strictly unprivileged, credential-less attacker is low; it only becomes practical under the replay precondition, which itself requires a capture capability outside the pure "unprivileged API client" threat model this audit is scoped to.

### Recommendation
Add a per-node (and optionally global) cap on outstanding `connAttempts` entries in `newAttempt`, rejecting or evicting oldest attempts once the cap is reached; alternatively, apply a rate limiter (the codebase already uses `limits.Factory` elsewhere, e.g. `MaxRequestBytesLimiter` in `wsserver.go`) keyed by `nodeAddress` before calling `newAttempt`, and actively expire stale attempts on a timer rather than relying solely on `FinalizeHandshake`/`AbortHandshake` being called by the HTTP layer.

### Proof of Concept
Go unit test in `core/services/gateway/connectionmanager_test.go`:
1. Construct a `connectionManager` with a valid DON/node config and a fixed `clockwork.FakeClock`.
2. Build one valid signed auth header for a configured node address (using the same node private key available in the test, as existing tests do for `StartHandshake`).
3. Call `StartHandshake` with that same header value N times (e.g., 10,000) in a loop, within `AuthTimestampToleranceSec` (do not call `FinalizeHandshake`/`AbortHandshake`).
4. Assert `len(m.connAttempts) == N` (or read via a test-only accessor / reflection), demonstrating unbounded growth with no rejection, cap, or rate limit enforced by `StartHandshake`.
5. Optionally assert memory/time scaling grows linearly with N with no error returned by `StartHandshake` on any call, confirming the absence of any quota mechanism.

func (m *connectionManager) newAttempt(nodeSt *nodeState, nodeAddress string, timestamp uint32) (string, []byte, error) {
	challengeBytes := make([]byte, m.config.AuthChallengeLen)
	_, err := rand.Read(challengeBytes)
	if err != nil {
		return "", nil, err
	}
	challenge := network.ChallengeElems{Timestamp: timestamp, GatewayId: m.config.AuthGatewayId, ChallengeBytes: challengeBytes}
	m.connAttemptsMu.Lock()
	defer m.connAttemptsMu.Unlock()
	m.connAttemptCounter++
	newId := fmt.Sprintf("%s_%d", nodeAddress, m.connAttemptCounter)
	m.connAttempts[newId] = &connAttempt{nodeState: nodeSt, nodeAddress: nodeAddress, challenge: challenge, timestamp: timestamp}
	return newId, network.PackChallenge(&challenge), nil
}

		return

	if err != nil {
		s.lggr.Debugw("received invalid auth header", "err", err)
		w.WriteHeader(http.StatusUnauthorized)
		return
	}
