Found it — `RequestCache.NewRequest` in `core/services/gateway/handlers/common/requestcache.go` implements the exact same class of bug as the CNote finding: a pre-condition check on a shared, attacker-influenceable key (`request already exists`) that any unprivileged client hitting the internet-facing gateway can poison to permanently block a legitimate request.

### Title
Gateway `RequestCache` keyed only by attacker-supplied `(sender, MessageId)` lets an unprivileged client permanently block a legitimate user's in-flight request - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` rejects a new request whenever the cache already contains an entry with the same `globalId{sender, MessageId}` key, returning `"request already exists"` [1](#0-0) . Both `sender` and `MessageId` originate from the inbound message body supplied by the calling client over the gateway's public/internet-facing HTTP path, and nothing in `NewRequest` verifies that the caller who "owns" a given sender/message-id pair is actually authorized to use it before the slot is created. This mirrors the CNote bug: a precondition ("no active/duplicate entry" ~ "cash balance == 0") that is supposed to reflect internal state can instead be forced into a blocking state by an untrusted, unprivileged party, bricking functionality for everyone else who shares that key space until the timeout entry expires.

### Finding Description
`RequestCache` is a generic per-handler dedupe/aggregation cache used across gateway handlers (vault, confidential relay, etc.) to track in-flight multi-node requests keyed by `globalId{sender, id}` [2](#0-1) . `NewRequest` computes the key directly from `request.Body.Sender` and `request.Body.MessageId`, both of which are values found in the incoming request envelope rather than values independently derived or authenticated by the gateway itself:

```go
key := globalId{request.Body.Sender, request.Body.MessageId}
c.mu.Lock()
defer c.mu.Unlock()
_, ok := c.cache[key]
if ok {
    return errors.New("request already exists")
}
``` [1](#0-0) 

If any two logically distinct callers happen to submit a request with the same `(sender, MessageId)` pair — which is entirely plausible for `MessageId` values that are client-chosen, low-entropy, or predictable/reused — the second caller's `NewRequest` call fails outright with `"request already exists"` until the first entry's timeout fires and `deleteAndSendOnce` removes it [3](#0-2) [4](#0-3) . Because no authentication ties `Sender`/`MessageId` uniqueness to a specific caller's identity at this layer, an unprivileged client can deliberately occupy a target key (or flood many keys) to keep the slot "busy," causing every subsequent legitimate request that maps to the same key to be rejected for the lifetime of the configured `timeout`. This is architecturally the same failure as CNote's `getCashPrior() == 0` check: a functional gate that assumes a benign, self-consistent state can be forced into the "blocked" branch by an outside party supplying attacker-chosen input, with no way for the legitimate caller to clear it early.

I could not fully verify, within the indexed context, whether `Sender` is cryptographically bound to a per-connection authenticated node identity by the callers of `NewRequest` in every handler (e.g., vault, confidentialrelay) such that an unrelated unprivileged HTTP client could actually forge another user's `Sender` value — the call sites that populate `request.Body.Sender` for user-originated (non-DON-node) messages were not fully traced in this pass. This is the key open question that determines whether this is exploitable purely by an unprivileged HTTP client of the gateway, or requires impersonating a specific sender identity that is otherwise access-controlled elsewhere in the stack.

### Impact Explanation
If `Sender`/`MessageId` can be influenced or replayed by an unprivileged party (e.g., a public gateway client choosing its own `MessageId`, or a not-fully-isolated sender namespace), the impact is denial of service: legitimate requests using the colliding key are rejected with `"request already exists"` and never processed, for up to `timeout` duration, effectively bricking that request path the same way CNote's contract was bricked by the forced-balance transfer. Given this is a generic component shared by multiple internet-facing gateway handlers, the blast radius could extend to any handler built on `RequestCache`.

### Likelihood Explanation
Likelihood depends entirely on whether `MessageId`/`Sender` values reaching `NewRequest` are attacker-controllable and not scoped per authenticated identity — this was not conclusively confirmed in the available index, so likelihood is uncertain and should be validated against the concrete callers of `NewRequest` (e.g., `core/services/gateway/handlers/vault/handler.go`, `core/services/gateway/handlers/confidentialrelay/handler.go`) before treating this as confirmed-exploitable.

### Recommendation
Ensure `globalId` incorporates a value that is authenticated/derived by the gateway itself (not purely attacker-supplied), or scope the cache key by an authenticated caller identity in addition to `MessageId`, so an unprivileged party cannot pre-occupy another caller's slot. Alternatively, reject `NewRequest` collisions only when the existing entry actually belongs to the same authenticated sender, and/or apply per-sender rate limiting before requests reach `NewRequest`.

### Proof of Concept
1. Determine or predict a `(sender, MessageId)` pair that a legitimate user's client is about to submit to a gateway handler built on `RequestCache` (e.g., low-entropy or client-generated `MessageId`s, or ability to send with an arbitrary `Sender` value if not otherwise authenticated at this layer).
2. Submit a request to the gateway carrying that same `(sender, MessageId)` first, causing `NewRequest` to insert the entry into `c.cache`.
3. When the legitimate user's actual request with the same key arrives, `NewRequest` returns `"request already exists"` [5](#0-4) , and the legitimate request is dropped/rejected until the attacker's bogus entry's timeout expires and is cleaned up by `deleteAndSendOnce` [6](#0-5) .

func (c *requestCache[T]) deleteAndSendOnce(key globalId, callbackResponse handlers.UserCallbackPayload) error {
	c.mu.Lock()
	entry, deleted := c.cache[key]
	delete(c.cache, key)
	c.mu.Unlock()
	if deleted {
		entry.timeoutTimer.Stop()
		return entry.SendResponse(callbackResponse)
	}

	return nil
}
