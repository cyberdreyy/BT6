### Title
`parse_signers` misreports a single-signer authority as a multisig authority based solely on trailing account count - ([File: transaction-status/src/parse_token.rs])

### Summary
`parse_signers` in `transaction-status/src/parse_token.rs` decides whether to emit an `owner`/`authority` field vs. a `multisigOwner`/`multisigAuthority` + `signers` field purely by comparing `accounts.len()` to `last_nonsigner_index + 1`, without ever inspecting the referenced account's actual on-chain data to confirm it is a real SPL Token `Multisig` account. Since the SPL Token program's own `validate_owner` logic ignores extra trailing accounts when the authority is *not* a multisig, an attacker can append one arbitrary extra account to a legitimate single-signer `Transfer`/`Burn`/`SetAuthority`/etc. instruction, causing the RPC's `jsonParsed` output to falsely report a multisig authorization model with a spoofed `signers` list.

### Finding Description
`parse_signers` is called from every token-authority-consuming instruction handler (`Transfer`, `Approve`, `Revoke`, `SetAuthority`, `MintTo`, `Burn`, `CloseAccount`, `FreezeAccount`, `ThawAccount`, `TransferChecked`, etc.) at [1](#0-0) . The function's entire decision of "is this a multisig authority" is:

```rust
if accounts.len() > last_nonsigner_index + 1 {
    // treat accounts[last_nonsigner_index] as multisig owner
    // treat accounts[last_nonsigner_index+1..] as "signers"
} else {
    // treat accounts[last_nonsigner_index] as plain owner/authority
}
``` [2](#0-1) 

This mirrors the account-slicing convention used by SPL Token's `Processor::validate_owner`, which reads any accounts remaining in `account_info_iter` after the authority as would-be multisig signers — but that on-chain function *only* treats those trailing accounts as meaningful when `owner_account_info.owner == program_id && owner_account_info.data_len() == Multisig::LEN`. If the authority account is not an actual `Multisig` account, `validate_owner` falls into the plain single-signer branch and simply ignores any extra trailing accounts in the instruction — it does not require them to be signers, does not fail because of their presence, and does not validate their content.

Consequently, an attacker (transaction author) can construct a `Transfer` (or `Burn`, `Approve`, etc.) instruction with a normal single-signer `authority` (which they actually sign for), and append one arbitrary extra, non-signer, unrelated pubkey to `instruction.accounts` (`accounts.len() == last_nonsigner_index + 2`). On-chain this transaction executes exactly like a normal single-authority transfer — the extra account is inert. But the pre-check `check_num_token_accounts` (via `check_num_accounts` in `transaction-status/src/parse_instruction.rs`) only enforces a *minimum* account count, not an exact/maximum count, so this crafted instruction passes validation in `parse_token`'s dispatch at [3](#0-2)  before reaching `parse_signers`. When this transaction is later fetched via `getTransaction`/`getConfirmedBlock` with `jsonParsed` encoding, `parse_signers` will emit `multisigAuthority`/`multisigOwner` (with the real authority's pubkey) and a fabricated `signers` array containing the attacker's arbitrary extra pubkey — even though the true authorization is a single ordinary signature from the authority account, and the extra pubkey played no role in authorizing anything.

### Impact Explanation
This is a decoder misreporting bug: the `jsonParsed` RPC output for a legitimately-executed, single-signer-authorized token instruction can be made to falsely present a multisig authorization model with a spoofed `signers` list. This directly matches the "decoder ... misreporting" category and "wrong ... data returned" from a single unprivileged RPC call (`getTransaction`), which is in-scope per the rules. Impact is limited to misleading downstream consumers (block explorers, indexers, compliance/monitoring tools) about the true authorization structure of a transfer/burn/setAuthority/etc.; it does not affect consensus, validator state, or funds movement, since the actual on-chain execution and authorization semantics are unaffected — only the RPC's parsed representation is wrong.

### Likelihood Explanation
Fully feasible and repeatable with only unprivileged attacker capability: any client can construct and submit (or have already-confirmed) a standard SPL Token instruction with one extra, non-signer trailing account, since neither the on-chain SPL Token program nor `check_num_token_accounts`'s minimum-length check rejects it. Every subsequent `getTransaction`/`getConfirmedBlock` call with `jsonParsed` encoding against that transaction will reproduce the misreport deterministically.

### Recommendation
`parse_signers` should not infer multisig status purely from account-array length. Where feasible, cross-check against actual account state (e.g., via the account's owning program and `Multisig::LEN`/deserialization) when such data is available to the parser, or, if account state is unavailable at parse time, clearly document/flag output as a heuristic (e.g., include the raw account list alongside the heuristic label) rather than asserting an authoritative `multisigOwner`/`signers` field that downstream consumers may treat as ground truth.

### Proof of Concept
```rust
// transaction-status/src/parse_token.rs (test module)
#[test]
fn test_parse_signers_misreport_on_single_signer_with_extra_account() {
    let account_keys_vec = vec![
        Pubkey::new_unique(), // source
        Pubkey::new_unique(), // destination
        Pubkey::new_unique(), // real single-signer authority (actually signs the tx)
        Pubkey::new_unique(), // attacker-supplied arbitrary extra, non-signer account
    ];
    let account_keys = AccountKeys::new(&account_keys_vec, None);

    // accounts.len() == last_nonsigner_index(2) + 2 == 4
    let accounts: Vec<u8> = vec![0, 1, 2, 3];

    let mut map = Map::new();
    parse_signers(
        &mut map,
        2,
        &account_keys,
        &accounts,
        "authority",
        "multisigAuthority",
    );

    // BUG: heuristic reports a multisig authority + spoofed signers list,
    // even though account_keys[2] is an ordinary single signer and
    // account_keys[3] never authorized anything on-chain.
    assert!(map.contains_key("multisigAuthority"));
    assert!(map.contains_key("signers"));
    assert!(!map.contains_key("authority"));

    // Expected (correct) behavior would require verifying that
    // account_keys[2] is actually a Multisig account before reporting
    // "multisigAuthority"/"signers"; absent that check, the assertions
    // above demonstrate the misreport.
}
```
This test demonstrates that `parse_signers` emits `multisigAuthority` + `signers` for a genuinely single-signer-authorized instruction whenever one extra trailing account is present, regardless of whether that account is a real multisig or its signers, confirming the misreporting described above.

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
