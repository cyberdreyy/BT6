## Analysis

The bug-class hint here is "a state transition proceeds without checking a prior, still-relevant piece of state" — the Compound contract lets a transfer proceed without checking whether the sender actually still has the balance it claims. The analogous pattern in this codebase is in the node-side signer response tally in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, which tracks per-block, per-signer weight for the mining coordinator.

### Title
Signer weight double-counted across accept/reject buckets when a signer changes its vote from Rejected to Accepted - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener`'s tally of `BlockStatus.total_weight_approved` / `total_weight_rejected` is keyed on two different sets (`gathered_signatures` and `responded_signers`) that are not mutually consistent, so a signer who first rejects a block and later legitimately signs it (an explicitly supported flow on the signer side) gets counted in *both* the rejected and the approved weight totals, with the rejected weight never cleared.

### Finding Description
`BlockStatus` tracks two independent bookkeeping structures: [1](#0-0) 

On `BlockResponse::Accepted`, the code only guards weight addition with `gathered_signatures.contains_key(&slot_id)`, not with `responded_signers`: [2](#0-1) 

On `BlockResponse::Rejected`, the guard is the opposite — it uses `responded_signers.insert(slot_id)`, which correctly prevents a second rejection from double-counting, and correctly prevents a reject *after* an accept from counting (since `responded_signers` was already populated by the accept branch): [3](#0-2) 

The asymmetry: if signer S sends `Rejected` first (its slot is added to `responded_signers`, its weight added to `total_weight_rejected`), and later sends `Accepted` for the same block — which is a documented, legitimate flow on the signer side, since a prior rejection can be re-evaluated and turned into a signature once the reject reason no longer holds (`should_reevaluate_reject_reason`, `should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`, described in `docs/signer-flows.md` section 3) — the `Accepted` branch sees `gathered_signatures` does *not* yet contain S's slot, so it adds S's weight to `total_weight_approved` as well. S's weight is now counted in both `total_weight_rejected` and `total_weight_approved`, and the stale rejected weight is never removed.

This breaks the "aggregated weight vs verified accepts" equality: the sum of weight recorded for a block can now exceed the true, current, per-signer vote weight, because one signer's superseded vote and current vote are both counted.

### Impact Explanation
`SigningCoordinator`'s wait loop in `stacks-node/src/nakamoto_node/signer_coordinator.rs` evaluates the rejection threshold *before* the acceptance threshold: [4](#0-3) 

Because stale rejection weight from a signer who has since flipped to accept is never cleared, `total_weight_rejected` can remain permanently inflated by that signer's weight. If enough weight is stuck in this stale state, the coordinator can incorrectly declare `NakamotoNodeError::SignersRejected` for a block that has, in current reality, reached (or is approaching) the real 70% acceptance threshold — discarding a validly-signed block and forcing the miner into a new proposal/tenure path, a liveness wedge on block production driven purely by a miscounted response rather than a real rejection majority.

### Likelihood Explanation
This requires no signer collusion or majority — a single honest signer flipping its vote from Reject to Accept (an explicitly supported re-evaluation path per the signer's own state machine) is enough to trigger the double-count. Any transient condition that causes a rejection to later resolve (e.g. a stale/timed-out conflicting sibling, a temporarily-unreachable node treated as "assume higher", etc., all documented in `docs/signer-flows.md` sections 3 and 7) will produce exactly this sequence of StackerDB messages from a signer's normal, correct operation.

### Recommendation
Make the accept-path weight bookkeeping symmetric with the reject-path: before adding weight to `total_weight_approved`, check (and if necessary reverse) any weight already attributed to this signer in `total_weight_rejected` (and vice versa), keyed off a single "current vote" map per slot instead of two independently-guarded structures. Concretely, gate the `Accepted` branch on `!block.responded_signers.contains(&slot_id)` (or explicitly subtract the signer's weight from `total_weight_rejected` when transitioning) so a signer's weight is attributed to exactly one bucket at a time.

### Proof of Concept
1. Miner proposes block `B`; signer `S` (weight `w`) sends `BlockResponse::Rejected` for `B` (e.g., due to a stale-sibling conflict) — `responded_signers` gains `S`'s slot, `total_weight_rejected += w`. [3](#0-2) 
2. The condition that caused `S`'s rejection resolves (per `should_reevaluate_reject_reason` on the signer side), and `S` legitimately re-evaluates and signs `B`, broadcasting `BlockResponse::Accepted`.
3. `StackerDBListener` receives the `Accepted` message; since `gathered_signatures` has no entry for `S`'s slot, it adds `w` to `total_weight_approved` as well, without touching `total_weight_rejected`. [2](#0-1) 
4. `BlockStatus` for `B` now reports `w` counted in both `total_weight_rejected` and `total_weight_approved`, inflating the sum of recorded weight beyond the true per-signer total and — because the rejected-threshold check runs first in `SigningCoordinator`'s loop — can cause a validly-signed block to be discarded as `SignersRejected`. [4](#0-3)
