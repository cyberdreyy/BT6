Based on investigation, the strongest analog in marginfi-v2 to the PoolTogether `cancelPromotion` bug class (deleting state and stranding unclaimed rewards) is the missing enforcement of `MarginfiError::CannotCloseOutstandingEmissions` in the `lending_account_close_balance` instruction path.

### Title
Closing a lending balance destroys accrued but unclaimed `emissions_outstanding` with no enforcement of the dedicated safety check - (File: programs/marginfi/src/state/marginfi_account.rs)

### Summary
The `Balance` struct tracks `emissions_outstanding`, the user's accrued but not-yet-distributed incentive rewards for a position [1](#0-0) . The codebase defines a dedicated error, `CannotCloseOutstandingEmissions` ("Cannot close balance because of outstanding emissions"), clearly signaling the intended invariant that a balance must not be closeable while it still holds unclaimed emissions [2](#0-1) . However, the actual `close_balance` logic that runs when a user calls `lending_account_close_balance` only validates that liability and asset amounts are zero — it never checks `emissions_outstanding` before zeroing/deactivating the balance slot via `balance.close()`.

### Finding Description
`BankAccountWrapper::close_balance` performs exactly two guard checks (debt is zero, assets are zero) and then unconditionally calls `balance.close()`, which resets the balance slot (including `emissions_outstanding`) via `Balance::empty_deactivated()`-style logic: [3](#0-2) 

The instruction wrapper `lending_account_close_balance` (invoked by any account authority) calls this function directly with no additional emissions check: [4](#0-3) 

This is directly analogous to the PoolTogether `cancelPromotion` bug: a lifecycle-ending state transition (`close_balance`/`delete _promotions[_promotionId]`) is permitted despite the presence of unclaimed reward accounting (`emissions_outstanding`/unclaimed epoch rewards), silently erasing the record that entitles the holder to a payout, with no code path to recover it afterward. The presence of `CannotCloseOutstandingEmissions` (error code 6033) in `errors.rs` — unused anywhere in the current instruction logic — demonstrates the check was intended but is not wired in, mirroring the "too rigorous"/"insufficiently guarded" mismatch between design intent and enforcement in the original report.

Per project documentation, emissions are delivered by periodic off-chain "airdrop" to the account authority based on state read from the chain , so `emissions_outstanding` is the durable on-chain record an off-chain distributor relies on before a drop occurs. If a balance is closed (e.g. by the account authority, or as part of automated flows that call `close_balance`) between an emissions-accrual point and the off-chain distribution sweep, the pending amount is permanently wiped with no recovery mechanism, functionally identical to PoolTogether's "unclaimed tokens... stay locked" outcome.

### Impact Explanation
This causes a durable, irreversible loss of a user's earned-but-undistributed incentive rewards with no state-based path to recovery — the exact "freeze/loss of previously accrued value" pattern flagged in the original report. Unlike a pure griefing self-harm case, this also matters wherever `close_balance` executes automatically as part of protocol flows (e.g., liquidation cleanup or dust-balance closures) rather than purely voluntary user action, since a position can be terminated by protocol logic without the holder's explicit intent to forfeit rewards.

### Likelihood Explanation
Likelihood is moderate: any account authority (or automated flow that calls `close_balance`) can trigger it under completely normal, permissionless conditions — no privileged role or unusual state is required, only that `emissions_outstanding` be non-zero at the moment the balance's debt/assets happen to be at zero (a common terminal state after a full withdraw/repay). No signature from an emissions-related admin nor bad-debt condition is needed to hit this path.

### Recommendation
Add a guard in `close_balance` (`programs/marginfi/src/state/marginfi_account.rs`) that checks `balance.emissions_outstanding` is zero (with the same tolerance pattern used for asset/liability shares) before allowing `balance.close()`, returning `MarginfiError::CannotCloseOutstandingEmissions` otherwise — wiring in the already-defined but currently-unused error. Alternatively, settle/flush `emissions_outstanding` (e.g., transfer to a claimable/global bucket, or require a companion claim instruction) as part of `close_balance` so the value is not silently discarded.

### Proof of Concept
1. User deposits into a bank with active emissions (per docs, emissions accrue continuously and settle at a later "airdrop" pass) .
2. Emissions accrue into `balance.emissions_outstanding` over time (field defined in `Balance`) [5](#0-4) .
3. User fully withdraws/repays so asset and liability shares are at (or below) the zero threshold, then calls `lending_account_close_balance` [6](#0-5) .
4. `close_balance` only checks debt/assets are zero and proceeds to `balance.close()`, discarding `emissions_outstanding` with no check and no error, despite `MarginfiError::CannotCloseOutstandingEmissions` existing specifically for this scenario [7](#0-6) [2](#0-1) .
5. Any pending off-chain distribution tied to this position's `emissions_outstanding` value can no longer be sourced from on-chain state, as the balance slot has been deactivated/reset.

Note: I could not verify from the indexed code whether any current on-chain instruction still reads/settles `emissions_outstanding` directly for distribution (the legacy `lending_pool_reclaim_emissions_vault`/`lending_account_clear_emissions` instructions were removed per patch notes), so the precise operational significance of this dangling field to the current off-chain airdrop pipeline is not fully confirmed from the available index — a Devin session with full repository access could confirm how `emissions_outstanding` is currently consumed downstream.

pub fn lending_account_close_balance(ctx: Context<LendingAccountCloseBalance>) -> MarginfiResult {
    let LendingAccountCloseBalance {
        marginfi_account,
        bank: bank_loader,
        group: marginfi_group_loader,
        ..
    } = ctx.accounts;

    let mut marginfi_account = marginfi_account.load_mut()?;
    let mut bank = bank_loader.load_mut()?;

    check!(
        !marginfi_account.get_flag(ACCOUNT_DISABLED),
        MarginfiError::AccountDisabled
    );

    let group = &*marginfi_group_loader.load()?;
    bank.accrue_interest(
        Clock::get()?.unix_timestamp,
        group,
        #[cfg(not(feature = "client"))]
        bank_loader.key(),
    )?;

    bank.update_bank_cache(group)?;

    let in_receivership = marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP);
    let lending_account: &mut marginfi_type_crate::types::LendingAccount =
        &mut marginfi_account.lending_account;
    let mut bank_account =
        BankAccountWrapper::find(&bank_loader.key(), &mut bank, lending_account)?;

    bank_account.close_balance(in_receivership)?;
    lending_account.sort_balances();
    marginfi_account.sync_indexer_flags();
    marginfi_account.last_update = Clock::get()?.unix_timestamp as u64;

    Ok(())
}
