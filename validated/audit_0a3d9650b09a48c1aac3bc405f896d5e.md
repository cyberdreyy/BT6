This confirms the mechanics. The `lockup_account_id` is derived purely from `sha256(owner_account_id)[..20].<factory>` with no check that the caller of `create()` is the intended owner or grant issuer — `create()` is a public, unauthenticated, `#[payable]` method callable by anyone who supplies `owner_account_id` and `MIN_ATTACHED_BALANCE` [1](#0-0) . Since `create_account()` on an already-existing account fails, only the first successful call for a given `owner_account_id` wins; later calls fail at `create_account()` and get refunded via `on_lockup_create` [2](#0-1) . The `foundation_account_id` passed to `LockupContract::new` is `Some(self.foundation_account_id)` only if the caller's `vesting_schedule` argument is `Some(..)`, otherwise `None` [3](#0-2) .

### Title
Front-running `LockupFactory::create` to squat a victim's deterministic lockup address with `vesting_schedule=None`, permanently stripping `foundation_account_id` - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the deployed lockup's account ID deterministically from `sha256(owner_account_id)[..20]` with no restriction on who may call `create()` for a given `owner_account_id`, and it only sets `foundation_account_id = Some(self.foundation_account_id)` when the caller's own `vesting_schedule` argument is `Some(..)`. An unprivileged attacker can therefore observe or predict a pending grant to `owner_account_id = victim`, call `create()` first with `vesting_schedule = None` and the minimum deposit, and permanently occupy the address before the legitimate issuer's transaction with the real vesting schedule lands.

### Finding Description
The broken binding: **the `foundation_account_id` stored in the lockup deployed at `sha256(victim)[..20].<factory>` == the `foundation_account_id` that the legitimate issuer's intended `vesting_schedule = Some(VestingScheduleOrHash::VestingHash(...))` call would have produced.** This is violated: `None != Some(self.foundation_account_id)`.

Code path:
- `create()` computes `lockup_account_id` solely from `owner_account_id`, independent of `predecessor_account_id` [4](#0-3) .
- `foundation_account` is set based on the *caller-supplied* `vesting_schedule`, not on any authorization tied to `owner_account_id` [3](#0-2) .
- The `Promise::new(lockup_account_id).create_account()...` chain deploys and initializes `LockupContract::new` with these attacker-chosen args [5](#0-4) .
- `LockupContract::new` only asserts internal consistency between its own `vesting_schedule` and `foundation_account_id` arguments (`None` vesting requires `None` foundation, and vice versa) — it has no way to know or check what the "intended" grant was [6](#0-5) .
- Once the attacker's transaction succeeds first, the legitimate issuer's later `create()` call attempts `create_account()` on an already-existing account, which fails; `on_lockup_create` detects `is_promise_success() == false` and simply refunds the deposit to the legitimate `predecessor_account_id`, silently doing nothing else [7](#0-6) .

No guard (`assert_owner`, `assert_called_by_foundation`, signature/allowlist check tying `owner_account_id` to a specific permitted caller, or a nonce/salt in the address derivation) exists to prevent an arbitrary account from claiming an owner's deterministic lockup address first with attacker-chosen parameters.

### Impact Explanation
The victim's employment/grant lockup ends up permanently deployed with `vesting_information = VestingInformation::None` and `foundation_account_id = None`, so the NEAR Foundation has no way to invoke termination/clawback logic (`lockup/src/foundation.rs` methods are gated on `foundation_account_id` being set) — unvested tokens that were meant to be forfeitable become unconditionally the owner's, once funded. This matches the "locked or unvested tokens released early" / "a lockup deployed with parameters its rightful creator never chose" Critical category. The blast radius is any lockup address that hasn't been created yet for any `owner_account_id`; the attack is repeatable per victim address, limited only by the attacker's willingness to front-run and to fund `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squatted account, which they can later abandon (the deposit stays locked in the deployed contract, not necessarily recoverable by the attacker) — the primary "gain" is denial of the foundation's clawback right and forcing the victim/foundation to use a fresh account name, or, if the victim's own key still controls `owner_account_id` and it's funded/used, the tokens become the owner's without vesting constraints.

### Likelihood Explanation
Preconditions are minimal and match the "unprivileged attacker" profile exactly: no account must yet exist at the deterministic address, and the attacker only needs to attach `MIN_ATTACHED_BALANCE` and race a public mempool transaction. Grant/lockup creations for known `owner_account_id`s (e.g., new employee account names) are often predictable or observable before the foundation's official `create()` transaction is included, making front-running practically feasible on a public blockchain. The cost per attempt is `MIN_ATTACHED_BALANCE`, and the attack is repeatable across any number of victim accounts.

### Recommendation
Restrict `create()` for grants requiring vesting so that only the `foundation_account_id` (or an explicitly authorized caller) may create a lockup with `vesting_schedule = None` for a given `owner_account_id`, or require `predecessor_account_id == foundation_account_id` when initializing vesting-bearing lockups regardless of the caller-supplied `vesting_schedule`. Alternatively, incorporate a foundation-issued signed authorization or reservation step prior to allowing address-deterministic `create()` calls, so the deployed lockup's parameters cannot diverge from what the foundation intended for a given `owner_account_id`.
