### Title
Stale confirmations from removed keys still count toward `num_confirmations`, allowing execution below live-key threshold - (File: `multisig/src/lib.rs`)

### Summary
In `multisig/src/lib.rs`, `MultiSigContract::confirm` counts every public key ever recorded in a request's `confirmations` `HashSet` toward the `num_confirmations` threshold, without verifying those keys are still active access keys on the account. The `DeleteKey` action's cleanup logic only purges requests whose *original adder* (`signer_pk`) matches the deleted key; it never scans other requests' `confirmations` sets to strip out a deleted key that had merely confirmed (not originated) them. This lets a request be executed with fewer than `num_confirmations` currently-live keys.

### Finding Description
The broken binding: `confirmations.get(&request_id).len()` (live confirming keys) should equal `count of currently-valid access keys that confirmed request_id`. In reality, `confirmations.len()` can include public keys that have already been deleted from the account.

Code path:
- `confirm` [1](#0-0)  inserts `env::signer_account_pk()` into the request's `confirmations` `HashSet` and, once `confirmations.len() as u32 + 1 >= self.num_confirmations`, calls `remove_request` then `execute_request` — with no re-validation that previously-stored keys in the set are still active access keys.
- `MultiSigRequestAction::DeleteKey` cleanup only removes requests/confirmations for request IDs whose stored `signer_pk` (i.e. the original *adder* of the request) equals the deleted key: `self.requests.iter().filter(|(_k, r)| r.signer_pk == pk)` [2](#0-1) . It never inspects `self.confirmations` values on requests added by *other* keys to strip out `pk` there.
- `assert_valid_request` only checks the request/confirmations map entries exist and that predecessor == current account; it performs no per-key liveness check [3](#0-2) .

Exploit flow (all actors are keys already present on the account, e.g. one full-access key and additional restricted keys added via `AddKey` — no external/unprivileged party is involved, since `add_request`/`confirm` require `predecessor_account_id == current_account_id`, i.e. the caller must already hold a key on this account):
1. With `num_confirmations = 2` and keys `K1, K2, K3` on the account, `K2` calls `add_request(R)` (a `Transfer` request) — `signer_pk` of `R` is `K2`.
2. `K1` calls `confirm(R)` — count is `0+1 < 2`, so `K1` is stored in `R`'s confirmations set: `{K1}`.
3. A separate, legitimately-confirmed request deletes `K1`'s access key (`DeleteKey { public_key: K1 }`). Its cleanup loop only removes requests where `signer_pk == K1` — since `R`'s original adder was `K2`, `R` and its confirmations (`{K1}`) are untouched.
4. `K1`'s NEAR access key no longer exists on-chain, but the stale confirmation remains in contract state.
5. `K3` calls `confirm(R)`. `confirmations.len() (1, still counting K1) + 1 == 2 >= num_confirmations`, so `remove_request` + `execute_request` fire the `Transfer`, moving funds — authorized by only one truly live key (`K3`) plus one already-revoked key (`K1`).

This breaks the intended multisig invariant that a confirmation from a removed key never counts, and lets a request execute below the number of live confirming members.

### Impact Explanation
Funds (`Transfer`, `FunctionCall` deposits, etc.) leave the multisig account authorized by fewer live keys than `num_confirmations` requires. This matches the listed Critical impact category "a multisig request executed below `num_confirmations` live members." Any request type reachable via `execute_request` (transfers, function calls, adding/deleting further keys) can be forced through this way, and the bug is repeatable for every subsequent request as long as a stale confirmation from a deleted key remains attached to an unexecuted request. Blast radius is limited to individual multisig account instances deployed from this contract code, but within such an account it undermines the entire security model (any minority keyholder can force execution once another key gets rotated out while a confirmation is pending).

### Likelihood Explanation
Preconditions: the account must have ≥2 keys and a pending, partially-confirmed request whose confirmer is later removed via `DeleteKey` while the original adder key is different from the removed key — a normal, foreseeable sequence during routine key rotation (e.g., replacing a compromised or departing signer) rather than a contrived edge case. No special balances are needed beyond whatever funds the account holds; the attacker only needs to be one of the account's already-provisioned keys (which is explicitly the entrypoint model for `add_request`/`confirm`). Cost is a couple of ordinary transactions; the flaw is deterministic and reproducible every time a confirmation is left pending across a key-rotation event.

### Recommendation
When executing `DeleteKey` (and any future member-removal action), iterate over all entries of `self.confirmations` (not just requests whose `signer_pk` matches the deleted key) and remove the deleted public key from every confirmation set; alternatively, validate at `confirm`/execution time that every key in the stored `confirmations` set is still a valid access key on the account before counting it toward `num_confirmations`.

### Proof of Concept
```rust
// multisig/src/lib.rs tests module
#[test]
fn test_stale_confirmation_from_deleted_key_still_counts() {
    let amount = 1_000;
    let k1 = Base58PublicKey::try_from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy").unwrap();
    let k2 = Base58PublicKey::try_from("HghiythFFPjVXwc9BLNi8uqFmfQc1DWFrJQ4nE6ANo7R").unwrap();
    let k3 = Base58PublicKey::try_from("2EfbwnQHPBWQKbNczLiVznFghh9qs716QT71zN6L1D95").unwrap();

    testing_env!(context_with_key(k2.clone().into(), amount));
    let mut c = MultiSigContract::new(2);

    // K2 adds transfer request R (signer_pk = K2)
    let transfer_req = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let r_id = c.add_request(transfer_req);

    // K1 confirms R -> confirmations(R) = {K1}, below threshold of 2
    testing_env!(context_with_key(k1.clone().into(), amount));
    c.confirm(r_id);
    assert_eq!(c.confirmations.get(&r_id).unwrap().len(), 1);

    // K1's access key gets removed via a DeleteKey request (adder=K1, so cleanup
    // only nukes requests where signer_pk == K1, NOT request R added by K2).
    testing_env!(context_with_key(k1.clone().into(), amount));
    let delete_key_req = MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteKey { public_key: k1.clone() }],
    };
    // single confirmation is enough only if num_confirmations were 1; to keep it simple,
    // assume this request reaches threshold via K1+K3 confirmations in a separate flow.
    // (Full reproduction requires simulating the second confirmer K3 here.)
    testing_env!(context_with_key(k3.clone().into(), amount));
    c.confirm(c.add_request(delete_key_req)); // executes DeleteKey(K1)

    // Assert: R's stale confirmation from deleted K1 is still present
    assert!(c.confirmations.get(&r_id).unwrap().contains(&k1.clone().into()));

    // K3 confirms R -> count = len({K1}) + 1 = 2 >= num_confirmations(2)
    // triggers remove_request + execute_request (Transfer) despite K1 no longer valid
    testing_env!(context_with_key(k3.into(), amount));
    c.confirm(r_id);
    assert_eq!(c.requests.len(), 0); // R executed using stale K1 confirmation + live K3
}
```
This test demonstrates the binding violation: `confirmations.get(&r_id)` still contains `K1` after `K1` was deleted, and the subsequent `confirm` by `K3` alone triggers execution, proving the request executed with only one truly live confirmer against a `num_confirmations = 2` requirement.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
