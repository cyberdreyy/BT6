### Title
Upfront withdrawal management fee can exceed the receipt amount and revert `requestWithdraw()` - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCDOEpochVariant.requestWithdraw()` subtracts the total upfront management and performance fees from `principal + interest` without first bounding those fees to the resulting claim amount. [1](#0-0) 

Because `_totalWithdrawFees()` returns the full management fee whenever it exceeds projected interest, a sufficiently long epoch can make the fee exceed `principal + interest`, causing an arithmetic underflow and preventing withdrawal requests. [2](#0-1) 

### Finding Description
Withdrawal requests charge an upfront management fee over one full epoch plus any remaining buffer period. [3](#0-2) 

The annualized management fee is computed as `nav * managementFee * duration / (FULL_ALLOC * 365 days)`. [4](#0-3) 

`setEpochParams()` does not bound `epochDuration`, while `setFeeParams()` permits `managementFee` up to `MAX_FEE / 10`, or 2% annually. [5](#0-4) [6](#0-5) 

With a 2% management fee and an epoch longer than 50 years, the upfront fee alone exceeds 100% of principal; at 51 years it is approximately 102% of principal. [4](#0-3) 

For a zero-APR vault, projected withdrawal interest is zero, so `principal + interest - totalFees` underflows whenever the upfront fee is greater than principal. [7](#0-6) 

### Impact Explanation
Affected tranche holders cannot create withdrawal receipts while the configuration remains in place, temporarily freezing their tranche principal in the vault. [8](#0-7) 

The freeze is proportional rather than dust-specific: under a 2% fee and 51-year zero-APR epoch, every nontrivial request calculates fees of approximately `1.02 * principal`, so reducing the requested amount does not avoid the revert. [4](#0-3) 

A user’s entire tranche balance can therefore remain inaccessible until an honest owner lowers the management fee or the epoch configuration is otherwise corrected. [1](#0-0) 

### Likelihood Explanation
This requires a valid but extreme owner/manager configuration rather than malicious privileged behavior: the fee cap permits 2%, and the epoch-duration setter accepts arbitrarily large durations. [6](#0-5) [5](#0-4) 

The issue can be triggered by any KYC-passing tranche holder through an ordinary `requestWithdraw()` call, with no privileged call embedded in the exploit transaction itself. [9](#0-8) 

### Recommendation
Cap `totalFees` at `principal + interest` before subtracting it, or explicitly bound the management-fee charge to the available interest/principal according to the intended fee policy. [1](#0-0) 

For example, calculate `claimAmount = principal + interest`, set `totalFees = min(totalFees, claimAmount)`, and store the resulting fee in `pendingWithdrawFees`; alternatively, enforce a protocol-level maximum on `epochDuration` that makes an upfront fee above 100% impossible. [2](#0-1) 

### Proof of Concept
The following Foundry test can be added to `test/foundry/IdleCreditVault.t.sol`, using the file’s existing vault fixture and helper naming conventions:

```solidity
function testRequestWithdrawRevertsWhenUpfrontManagementFeeExceedsReceipt() external {
    uint256 depositAmount = 10_000 * ONE_SCALE;

    // Valid configuration: managementFee == MAX_FEE / 10 == 2%.
    _setFeeParams(TL_MULTISIG, 0, 0, 2_000);

    vm.startPrank(manager);
    // 51 years makes the upfront 2% annual fee approximately 102% of principal.
    cdoEpoch.setEpochParams(51 * 365 days, 0);
    IdleCreditVault(address(strategy)).setApr(0);
    vm.stopPrank();

    idleCDO.depositAA(depositAmount);

    // _amount == 0 requests the caller's full AA balance.
    vm.expectRevert(stdError.arithmeticError);
    cdoEpoch.requestWithdraw(0, cdoEpoch.AATranche());
}
```

The computed fee is `depositAmount * 2_000 * (51 * 365 days) / 3153600000000 = 1.02 * depositAmount`, while projected interest is zero, so the subtraction in `requestWithdraw()` underflows. [4](#0-3) [7](#0-6)
