### Title
CreateSession leaks raw WebAuthn CredentialAssertion challenge JSON in 401 error body to unauthenticated callers with valid credentials - ([File: core/sessions/localauth/orm.go])

### Summary
When a valid email/password is supplied for an MFA-enabled account but `sr.WebAuthnData` is empty, `orm.CreateSession` marshals the full WebAuthn `CredentialAssertion` (including the RPID, allowed credential ID list, and challenge) into the error returned to `SessionsController.Create`, which forwards it verbatim as the 401 `jsonAPIError` body. Any caller who can brute-force or knows correct credentials receives this internal challenge state instead of a generic "MFA required" indicator.

### Finding Description
`SessionsController.Create` at [1](#0-0)  calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and on any error simply does `jsonAPIError(c, http.StatusUnauthorized, err)`, passing the raw `err.Error()` string through to the HTTP response body.

In `orm.CreateSession`, once email/password checks pass and the user has registered WebAuthn tokens, if `sr.WebAuthnData == ""` the code begins a WebAuthn login challenge, marshals the resulting `protocol.CredentialAssertion` options to JSON, and returns it as the error message itself: [2](#0-1) . That JSON (containing `publicKey.challenge`, `rpId`, `allowCredentials` list with credential IDs, timeout, userVerification policy, etc., produced by `sessions.BeginWebAuthnLogin`) becomes the literal string of the returned `error`, which is embedded into the JSON:API error `detail` field returned to the client with HTTP 401.

This is only reachable by a caller who already knows valid email+password (i.e., who can pass the constant-time email compare and `CheckPasswordHash` checks earlier in `CreateSession`, at [3](#0-2) ). There is no additional gating, redaction, or generic-message substitution before the error reaches `jsonAPIError`; the comment at line 182-183 states the intent is only "return a 401 error for the frontend to prompt the user," but the implementation returns the full internal challenge payload rather than a generic flag.

### Impact Explanation
This exposes internal WebAuthn challenge/session state (registered credential IDs, RPID, per-request server-generated challenge nonce) to any caller who can produce correct credentials, rather than confirming MFA is required via a minimal, generic signal. It functions as an information-disclosure/oracle bug: it confirms MFA status and discloses credential IDs bound to the account, which is unnecessary internal state exposure beyond a boolean "MFA required" response. This matches a credential/secret-disclosure impact class (partial exposure of WebAuthn internal state), though it does not by itself allow session creation, privilege escalation, or bypassing MFA — full login still requires a valid signed assertion from the physical authenticator via `sessions.FinishWebAuthnLogin`.

### Likelihood Explanation
Exploitation requires only a valid email and password for an MFA-enabled account — no operator/admin access, no session, and no prior authentication. Given valid credentials (e.g., obtained via credential stuffing, phishing, or an already-compromised password), an attacker can trivially POST to `/sessions` with `WebAuthnData` omitted and receive the challenge JSON in the 401 response body. It is fully repeatable per request since a fresh challenge is generated (and stored) on each attempt.

### Recommendation
In `orm.CreateSession` (core/sessions/localauth/orm.go, ~line 184-199), do not return the marshaled WebAuthn challenge as the `error` text surfaced to the HTTP layer. Instead, have `CreateSession` return a distinct, generic sentinel error (e.g., `ErrMFARequired`) and separately transport the actual challenge payload out-of-band (e.g., via a dedicated success-path response body/field constructed in `SessionsController.Create`, not via the generic `jsonAPIError` message string) so unauthenticated/generic error paths never echo back internal WebAuthn session data beyond what the legitimate follow-up login step needs.

### Proof of Concept
Go handler-level integration test plan:
1. Seed a test user with a hashed password and one registered `web_authns` row (valid `PublicKeyData` credential) via the local auth ORM test fixtures used in `core/sessions/localauth/orm_test.go`.
2. Instantiate `SessionsController` with this ORM-backed `AuthenticationProvider` (as done in `core/web/sessions_controller_test.go` patterns).
3. POST a JSON body `{"email": "<valid>", "password": "<valid>"}` (omit `webauthndata`) to the `/sessions` create route.
4. Assert HTTP status is 401.
5. Assert the response body's `errors[0].detail` (jsonapi error detail) is NOT parseable as JSON containing keys like `publicKey.challenge`, `publicKey.rpId`, or `publicKey.allowCredentials` — i.e. assert it equals a fixed generic string (e.g., `"MFA required"`) rather than the marshaled `protocol.CredentialAssertion`.
6. As a negative control, show that with the current code the test fails because `errors[0].detail` unmarshal succeeds and contains `allowCredentials` entries matching the seeded credential ID, proving the leak.
