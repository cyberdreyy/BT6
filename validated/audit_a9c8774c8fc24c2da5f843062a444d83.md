## Summary

I evaluated four lockup/stake-accounting candidates:
1. `pool_u64::amount_to_shares` / `shares_to_amount` rounding (generic, protected by `MIN_COINS_ON_SHARES_POOL` in `delegation_pool.move`) — weak.
2. `vesting::distribute` dust handling — dust explicitly routed to `withdrawal_address`, not exploitable.
3. `delegation_pool` commission accounting — uses `pool_u64_unbound` with minimum-balance guards.
4. `staking_contract::update_distribution_pool` double-rounding on commission transfer — this one holds up under trace and is the strongest candidate.

The RaptorCast bug's core defect is repeated integer-division truncation that silently drops value owed to a party, with no mechanism to recover the dropped remainder. `staking_contract.move`'s `update_distribution_pool` has the same structural flaw, and unlike `delegation_pool`'s equivalent pool, it lacks any minimum-balance floor to bound the loss, and the function is reachable by the staker (an unprivileged party relative to the operator's commission) via permissionless entry functions.

### Title
Double-rounding in `update_distribution_pool` lets the staker permanently siphon operator commission via frequent small distributions - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Finding Description
`update_distribution_pool` recalculates the operator's owed commission every time the underlying stake pool value changes, and immediately snapshots the new baseline via `distribution_pool.update_total_coins(updated_total_coins)`: [1](#0-0) 

For every non-operator shareholder it computes:
```
unpaid_commission = (current_worth - previous_worth) * commission_percentage / 100
shares_to_transfer = amount_to_shares_with_total_coins(unpaid_commission, updated_total_coins)
```
Both operations use integer (floor) division: `math64::mul_div` in `pool_u64::amount_to_shares_with_total_coins` and `shares_to_amount_with_total_coins`. [2](#0-1) 

Because `distribution_pool.update_total_coins(updated_total_coins)` is called unconditionally at the end of `update_distribution_pool`, the baseline (`previous_worth`) for the *next* invocation becomes the post-truncation value — any fractional commission lost to floor-division in this call is never revisited or reconciled in a future call. This is structurally identical to the RaptorCast defect: repeated truncating division that "undercounts" the amount owed to a party, with the shortfall never redistributed and no bound on how often the truncating operation can be triggered.

`update_distribution_pool` is invoked from `distribute_internal`, `add_distribution`, and thus reachable from the permissionless entry functions `distribute` (callable by anyone), `unlock_stake` (staker-only, but staker-controlled), `request_commission`, and `switch_operator`: [3](#0-2) [4](#0-3) 

Notably, the module comment in the unrelated example contract `aptos-move/move-examples/staking/sources/commission.move` explicitly documents this exact attack pattern and states it is mitigated there only by a minimum-balance check before distributing: [5](#0-4) 

`staking_contract.move`'s `distribution_pool` (a `pool_u64::Pool`, not `pool_u64_unbound`) has no equivalent minimum-balance floor comparable to `delegation_pool`'s `MIN_COINS_ON_SHARES_POOL` guard: [6](#0-5) 

so nothing bounds how small or how frequent the reward deltas triggering `update_distribution_pool` can be.

### Impact Explanation
A staker (the counterparty to the operator, with no privileged role over the operator's commission) can repeatedly trigger `unlock_stake` with minimal amounts (or wait for `distribute`/`request_commission` calls to be made against small reward accruals each epoch) so that `current_worth - previous_worth` times `commission_percentage / 100` truncates to 0 (or systematically less than the true fractional amount) on every call. Each truncation permanently strands the fractional commission with the staker's shares instead of crediting the operator, because the baseline resets after each call. Over many small calls this compounds into a non-trivial, non-recoverable diversion of operator commission to the staker — a role-boundary violation ("Operator commission ... share-accounting corruption that credits the wrong account or traps value") without the staker ever holding the operator's role or rights.

### Likelihood Explanation
The staker fully controls the timing and size of `unlock_stake` calls against their own staking contract, and `distribute`/`request_commission` are explicitly permissionless. The probability of triggering truncation-to-zero rises as commission percentage is low or reward deltas are small relative to `100 / commission_percentage`, similar to the RaptorCast case where `num_packets` divided by stake ratios rounds down to zero for a wide range of realistic inputs. No stake-amount floor exists in this pool to prevent frequent tiny-delta triggering, unlike `delegation_pool`'s guarded design.

### Recommendation
Track and carry forward the truncated remainder (a "commission dust" accumulator) across calls to `update_distribution_pool`, adding it back into the next `unpaid_commission` calculation before re-truncating, analogous to how the RaptorCast fix recommends allocating the previously lost blocks rather than discarding them. Alternatively, enforce a minimum stake-pool-value delta (or minimum elapsed time) before recomputing/transferring commission, mirroring the `MIN_COINS_ON_SHARES_POOL` protection already used in `delegation_pool.move`.

### Proof of Concept
Conceptual trace (not executed against a live node):
1. Staker creates a staking contract with `commission_percentage = 1` (or any low value) via `create_staking_contract`.
2. Operator joins the validator set; stake pool begins accruing rewards each epoch.
3. Instead of waiting, the staker calls `unlock_stake` (or any path invoking `distribute_internal`/`add_distribution`) after every small reward accrual, ensuring `(current_worth - previous_worth) * commission_percentage < 100` each time so `unpaid_commission` floors to `0`.
4. Because `distribution_pool.update_total_coins(updated_total_coins)` advances the baseline unconditionally regardless of whether commission was actually transferred, the fractional commission owed for that increment is permanently lost to the operator.
5. Repeating this over many epochs/calls accumulates a material amount of commission that never reaches the operator (or the operator's beneficiary), effectively redirected to the staker's balance in the distribution pool.

I was not able to execute this against a running Move VM/test harness in this session to obtain exact numeric loss figures — the trace above is derived from static analysis of `update_distribution_pool`, `pool_u64::amount_to_shares_with_total_coins`, and the call graph from `unlock_stake`/`distribute`/`request_commission`. A Devin session with Move test execution (`cargo test` / `aptos move test`) would be needed to produce concrete before/after balances confirming the magnitude of loss for a chosen commission percentage and reward cadence.

```text
    fun update_distribution_pool(
        distribution_pool: &mut Pool,
        updated_total_coins: u64,
        operator: address,
        commission_percentage: u64
    ) {
        // Short-circuit and do nothing if the pool's total value has not changed.
        if (distribution_pool.total_coins() == updated_total_coins) { return };

        // Charge all stakeholders (except for the operator themselves) commission on any rewards earnt relatively to the
        // previous value of the distribution pool.
        let shareholders = &distribution_pool.shareholders();
        shareholders.for_each_ref(
            |shareholder| {
                let shareholder: address = *shareholder;
                if (shareholder != operator) {
                    let shares = pool_u64::shares(distribution_pool, shareholder);
                    let previous_worth = pool_u64::balance(distribution_pool, shareholder);
                    let current_worth =
                        pool_u64::shares_to_amount_with_total_coins(
                            distribution_pool, shares, updated_total_coins
                        );
                    let unpaid_commission =
                        (current_worth - previous_worth) * commission_percentage / 100;
                    // Transfer shares from current shareholder to the operator as payment.
                    // The value of the shares should use the updated pool's total value.
                    let shares_to_transfer =
                        pool_u64::amount_to_shares_with_total_coins(
                            distribution_pool, unpaid_commission, updated_total_coins
                        );
                    pool_u64::transfer_shares(
                        distribution_pool, shareholder, operator, shares_to_transfer
                    );
                };
            }
        );

        distribution_pool.update_total_coins(updated_total_coins);
    }
```

```text
    /// Return the number of new shares `coins_amount` can buy in `self` with a custom total coins number.
    /// `amount` needs to big enough to avoid rounding number.
    public fun amount_to_shares_with_total_coins(self: &Pool, coins_amount: u64, total_coins: u64): u64 {
        // No shares yet so amount is worth the same number of shares.
        if (self.total_coins == 0 || self.total_shares == 0) {
            // Multiply by scaling factor to minimize rounding errors during internal calculations for buy ins/redeems.
            // This can overflow but scaling factor is expected to be chosen carefully so this would not overflow.
            coins_amount * self.scaling_factor
        } else {
            // Shares price = total_coins / total existing shares.
            // New number of shares = new_amount / shares_price = new_amount * existing_shares / total_amount.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(coins_amount, self.total_shares, total_coins)
        }
    }

    /// Return the number of coins `shares` are worth in `self`.
    /// `shares` needs to big enough to avoid rounding number.
    public fun shares_to_amount(self: &Pool, shares: u64): u64 {
        self.shares_to_amount_with_total_coins(shares, self.total_coins)
    }

    /// Return the number of coins `shares` are worth in `self` with a custom total coins number.
    /// `shares` needs to big enough to avoid rounding number.
    public fun shares_to_amount_with_total_coins(self: &Pool, shares: u64, total_coins: u64): u64 {
        // No shares or coins yet so shares are worthless.
        if (self.total_coins == 0 || self.total_shares == 0) {
            0
        } else {
            // Shares price = total_coins / total existing shares.
            // Shares worth = shares * shares price = shares * total_coins / total existing shares.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(shares, total_coins, self.total_shares)
        }
    }

    public fun multiply_then_divide(self: &Pool, x: u64, y: u64, z: u64): u64 {
        math64::mul_div(x, y, z)
    }
```
