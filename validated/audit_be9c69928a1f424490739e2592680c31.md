### Title
Permissionless `propagate_staked_settings` bypasses `FREEZE_SETTINGS` bank freeze, allowing unauthorized mutation of frozen staked-bank risk parameters - ([File: programs/marginfi/src/instructions/marginfi_group/propagate_staked_settings.rs])

### Summary
`propagate_staked_settings` is a fully permissionless instruction (no `Signer` in its `Accounts` struct) that unconditionally overwrites a staked bank's oracle, asset weights, deposit limit, `total_asset_value_init_limit`, `oracle_max_age`, risk tier, and staked-oracle flags from the group's `StakedSettings` PDA. Unlike every other bank-mutating instruction (`lending_pool_configure_bank`, `lending_pool_configure_bank_oracle`, `lending_pool_set_fixed_oracle_price`, `lending_pool_configure_bank_interest_only`, `lending_pool_configure_bank_limits_only`), it never checks `bank.get_flag(FREEZE_SETTINGS)` before mutating.

### Finding Description
The instruction handler loads the bank and settings and directly writes config fields without any freeze check: [1](#0-0) 

Contrast this with every sibling admin-mutation path, which explicitly gates on the flag before touching risk-affecting fields: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The documented intent of the flag is explicit — once set, "the bank's risk parameters, oracle configuration, interest rate curves, and other settings will not change," and only `configure_bank`'s frozen path (which restricts to deposit/borrow limits) is supposed to be reachable: [6](#0-5) 

`PropagateStakedSettings`'s account struct requires no signer at all, only a group binding and asset-tag constraint, confirming any unprivileged party can build and submit this instruction against any staked bank in any group: [7](#0-6) 

Because `bank.config.oracle_keys[0]`, `asset_weight_init`, `asset_weight_maint`, `total_asset_value_init_limit`, `oracle_max_age`, `risk_tier`, and staked-oracle flag bits are all overwritten unconditionally, an attacker can force a frozen staked bank back to whatever the group's mutable `StakedSettings` PDA currently holds — even if the admin froze the bank specifically to lock in a different (e.g., safer, or contractually-committed) configuration than the current group default. This directly violates the invariant that `FREEZE_SETTINGS` blocks all config mutation.

### Impact Explanation
This breaks the freeze commitment for every staked-collateral bank: an admin that sets `FREEZE_SETTINGS` on a staked bank to lock in specific weights/oracle/limits cannot actually prevent those parameters from changing, since any unprivileged caller can permissionlessly re-sync the bank to the group's current `StakedSettings`, which the admin (or the group's `edit_staked_settings` flow) may have since diverged from. This is an unauthorized state transition on a bank the admin explicitly locked — changing oracle keys, asset weights, risk tier, and value-init limits without going through any authorization check, which can alter collateral valuation and risk parameters for a bank users and integrators rely on being frozen.

### Likelihood Explanation
Fully feasible and repeatable: requires only (1) a group with a `StakedSettings` PDA, and (2) a staked bank (`ASSET_TAG_STAKED`) with `FREEZE_SETTINGS` set — both are normal, expected admin operations documented in the codebase. The attacker needs no signer authority; they just submit `PropagateStakedSettings` with the standard three accounts (`marginfi_group`, `staked_settings`, `bank`), exactly as the permissionless CLI/test helpers already do. [8](#0-7) 

### Recommendation
Add a `FREEZE_SETTINGS` check in `propagate_staked_settings` mirroring the pattern used elsewhere: if the flag is set, either reject the propagation entirely (e.g., `err!(MarginfiError::...)`) or restrict the update to only the fields still mutable under freeze (deposit limit), leaving oracle keys, weights, `total_asset_value_init_limit`, `oracle_max_age`, risk tier, and flags untouched.

### Proof of Concept
Rust unit/integration test plan (bankrun or program-test):
1. Create a group with `StakedSettings`, create a staked bank, set default settings (oracle A, weights W1).
2. Admin calls `lending_pool_configure_bank` (or equivalent) with `freeze_settings = true` on the staked bank; assert `bank.flags & FREEZE_SETTINGS != 0`.
3. Snapshot `bank.config` (oracle_keys[0], asset_weight_init, asset_weight_maint, deposit_limit, total_asset_value_init_limit, oracle_max_age, risk_tier, flags).
4. Admin edits `StakedSettings` (via `edit_staked_settings`) to a divergent oracle B / weights W2.
5. As an unprivileged, unrelated keypair (only paying tx fee, no signer requirement on `PropagateStakedSettings`), submit `propagate_staked_settings` against the frozen bank.
6. Assert expected behavior: with the fix, the instruction should fail (or leave `bank.config` unchanged except deposit/borrow limit); currently, without the fix, `bank.config.oracle_keys[0] == B`, weights == W2, etc., proving the freeze was bypassed — i.e. assert `bank.config != pre_freeze_snapshot`, demonstrating `AUTHZ_HOLDS` is violated.

pub fn propagate_staked_settings(ctx: Context<PropagateStakedSettings>) -> Result<()> {
    let settings = ctx.accounts.staked_settings.load()?;
    let mut bank = ctx.accounts.bank.load_mut()?;

    let (oracle_before, oracle_after) = (bank.config.oracle_keys[0], settings.oracle);

    bank.config.oracle_keys[0] = settings.oracle;
    bank.config.asset_weight_init = settings.asset_weight_init;
    bank.config.asset_weight_maint = settings.asset_weight_maint;
    bank.config.deposit_limit = settings.deposit_limit;
    bank.config.total_asset_value_init_limit = settings.total_asset_value_init_limit;
    bank.config.oracle_max_age = settings.oracle_max_age;
    bank.config.risk_tier = settings.risk_tier;
    bank.flags &= !STAKED_ORACLE_FLAGS;
    bank.flags |= settings.flags & STAKED_ORACLE_FLAGS;

    // Only validate the oracle info if it has changed
    if oracle_before != oracle_after {
        bank.config
            .validate_oracle_setup(ctx.remaining_accounts, None, None, None)?;
    }

    bank.config.validate()?;

    Ok(())
}

### Freeze Settings (Bit 3)

- **Bit 3** (`FREEZE_SETTINGS`, value 8): When set, most bank configuration parameters are frozen.
  Only `deposit_limit` and `borrow_limit` can still be changed. Note: `total_asset_value_init_limit`
  is also frozen (it can only be updated when the bank is NOT frozen).

This flag provides a credible commitment that the bank's risk parameters, oracle configuration,
interest rate curves, and other settings will not change. It can only be set through the
`configure_bank` instruction by the group admin. Once frozen, the admin can still adjust capacity
limits, but cannot change anything that affects the risk profile of the bank (such as weights,
oracle setup, interest rate curves, init limit, etc).

export const propagateStakedSettings = (
  program: Program<Marginfi>,
  args: PropagateStakedSettingsArgs,
) => {
  const remainingAccounts = args.oracle
    ? [
        {
          pubkey: args.oracle,
          isSigner: false,
          isWritable: false,
        } as AccountMeta,
      ]
    : [];

  const ix = program.methods
    .propagateStakedSettings()
    .accounts({
      // marginfiGroup: args.group, // implied from stakedSettings
      stakedSettings: args.settings,
      bank: args.bank,
    })
    .remainingAccounts(remainingAccounts)
    .instruction();

  return ix;
};
