### Title
Signer block-response signature does not bind `response_data`/`reason_code`, allowing tampered rejection/acceptance metadata to pass authentication - (File: `libsigner/src/v0/messages.rs`)

### Summary
`BlockRejection` (and analogously `BlockAccepted`) is authenticated by a signature that commits only to the block's `signer_signature_hash`, not to the rest of the message that downstream signer logic treats as authenticated, trusted data (`reason_code`, `response_data.reject_reason`, `response_data.failed_txid`, `tenure_extend_timestamp`, `read_count_extend_timestamp`). This is the same class of defect as the external report: sensitive/consequential data is not bound by the security mechanism that is supposed to protect it (there, a header disclosed keys outside the encryption's protection scope; here, a signature's domain excludes fields that are nonetheless treated as attested and used for consensus-relevant decisions).

### Finding Description
`BlockRejection::hash()` computes the signed digest as: [1](#0-0) 

which only feeds `self.signer_signature_hash` (plus the domain/chain-id) into `structured_data_message_hash`. Everything else on the struct — `reason`, `reason_code: RejectCode`, and the whole `response_data: BlockResponseData` (which carries `reject_reason`, `failed_txid`, `tenure_extend_timestamp`, `read_count_extend_timestamp`) — is excluded from what the signature commits to. `verify()`/`recover_public_key()` operate over this same narrow hash: [2](#0-1) 

The receiving signer's authentication logic recovers the public key from this narrow hash and, once `is_valid_signer` passes, unconditionally trusts the *other*, unsigned fields of the message for consensus-relevant logic: [3](#0-2) 

Those unsigned fields are then used to decide `RejectReason`, drive `mark_globally_rejected`, and — for pre-global-state protocol versions — flag the miner as having attempted an invalid reorg via `RejectReasonPrefix::ReorgNotAllowed` weight tallying: [4](#0-3) [5](#0-4) 

On the node/coordinator side, `reason_code` and `response_data.failed_txid` (both unsigned in the above sense) are separately used to tally per-txid rejection weight and decide which transactions get temporarily/permanently excluded from future proposals: [6](#0-5) 

The `Accepted` path has the analogous property: `handle_block_signature` recovers the signer's public key straight from the raw `block_hash.bits()` and `signature`, again a domain that does not cover `response_data` (`tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`): [7](#0-6) 

Normally, when a signer publishes a `BlockResponse` to its own `.signers` StackerDB slot, the *outer* StackerDB chunk signature covers the full serialized payload, so nobody without that signer's private key can alter any byte, including the "unsigned" fields — this closes the gap in the common path. However, the `.miners` StackerDB contract (`MinerMessages`) is deserialized without any chunk-level public-key binding to the inner message's claimed identity at all: [8](#0-7) 

versus the `.signers` contract path, which explicitly recovers and carries the chunk-writer's public key alongside each message: [9](#0-8) 

This means the only cryptographic binding that actually protects `reason_code`/`response_data`/`tenure_extend_timestamp` from tampering by anyone who is not the miner is the *inner* `BlockRejection`/`BlockAccepted` signature — and that signature, by construction, does not cover those fields.

### Impact Explanation
If a message carrying a legitimate signer's previously-observed `BlockRejection`/`BlockAccepted` (which is public, replicated data any participant, including the block's own miner, can read off `.signers`) is re-delivered with its `reason_code`/`response_data` fields altered but its `signer_signature_hash` and `signature` left untouched, the signature check in `handle_block_rejection`/`handle_block_signature` still succeeds and attributes the tampered content to the legitimate signer. Depending on which field is altered this can:
- Cause a `Rejected` message with a forged `RejectReason::ReorgNotAllowed`-class reason to be recounted toward `total_reorg_reject_weight`, flipping `SortitionMinerStatus` to `InvalidatedBeforeFirstBlock` — i.e., a rejection recounted with a different, attacker-chosen reason than what the signer actually attested to.
- Cause the coordinator's `failed_txid`/`problematic_weight` tallies in `stackerdb_listener.rs` to attribute a forged transaction id to a real signer's weight, influencing which transactions get temporarily or permanently excluded from block templates.
- Alter `tenure_extend_timestamp`/`read_count_extend_timestamp`, which feed into idle/read-count timeout tracking, potentially manipulating tenure-extension timing decisions attributed to a signer who never sent that value.

This falls in the "rejection recounted as something else" / equality-break class defined by the rules: the equality "what the signer signed" vs. "what is credited to the signer" is broken because the signature's domain is narrower than the data trusted downstream.

### Likelihood Explanation
The concrete exploitation path requires a channel where the outer transport signature does not already bind the full byte content to a known identity — the `.miners` StackerDB contract is such a channel, since it deserializes message chunks without recovering/validating a public key for the content (`libsigner/src/events.rs:547-567`), unlike `.signers` chunk handling. A block miner already has write access to `.miners` and can read the public `.signers` StackerDB to obtain a legitimate signer's previously-published `BlockRejection`/`BlockAccepted`. I was not able to fully confirm, within the scope of this review, whether `stacks-signer/src/v0/signer.rs`'s `handle_event_match` actually forwards `BlockResponse`-type payloads arriving via the `SignerEvent::MinerMessages` variant into the same `handle_block_rejection`/`handle_block_signature` processing used for `SignerMessages`, or whether it filters `MinerMessages` to only `BlockProposal`/`MockProposal` types before further dispatch. That dispatch-filtering check is the remaining piece needed to fully establish end-to-end reachability by a miner-only attacker; the root-cause signature-scope defect itself, however, is directly confirmed in the code cited above.

### Recommendation
Extend the structured-data hash committed to by `BlockRejection::hash()` and the equivalent for `BlockAccepted`/its `response_data` to include `reason_code` and every field of `response_data` (`reject_reason`, `failed_txid`, `tenure_extend_timestamp`, `read_count_extend_timestamp`), so the signature authenticates the entire semantically-meaningful payload, not just the block hash. Additionally, confirm (and if missing, add) explicit filtering in the `MinerMessages` dispatch path so that message types which are supposed to originate only from signers (`BlockResponse`, `BlockPreCommit`, `StateMachineUpdate`) are rejected/ignored when they arrive via the `.miners` contract instead of `.signers`.

### Proof of Concept
Conceptual PoC (network-level, not executable without live cluster access):
1. Observe a legitimate signer's `BlockRejection` for block `H` on the `.signers` StackerDB slot; note `signer_signature_hash`, `signature`, and original `reason_code`/`response_data`.
2. Construct a new `BlockRejection` with the same `signer_signature_hash` and `signature`, but with `reason_code`/`response_data.reject_reason` changed (e.g., to `RejectReasonPrefix::ReorgNotAllowed`) and/or `response_data.failed_txid` set to an arbitrary txid.
3. Serialize as `SignerMessage::BlockResponse(BlockResponse::Rejected(..))` and publish it to the `.miners` contract slot (writable by the block miner's key) — or, if `MinerMessages` dispatch is confirmed to reach `handle_block_rejection`, deliver it through that path.
4. On a receiving signer, `rejection.recover_public_key()` still recovers the original signer's address (since it only re-hashes `signer_signature_hash`), `is_valid_signer` passes, and the forged `reason_code`/`response_data` are stored/tallied as if genuinely attested by that signer.

    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";

            return;

        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_rejection_response(
                block_hash,
                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";
            "signer_pubkey" => public_key.to_hex(),
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,

            "reject_reason" => ?rejection.response_data.reject_reason,
