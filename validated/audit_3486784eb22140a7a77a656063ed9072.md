### Title
Unvalidated mint reference lets an attacker misreport `jsonParsed` token balances / decimals via RPC - (File: `rpc/src/parsed_token_accounts.rs`)

### Summary
When the JSON-RPC server renders an SPL token account with `jsonParsed` encoding, it reads the `mint` field embedded in the account's raw data and fetches whatever account exists at that pubkey to obtain `decimals`/extension config, without ever checking that the referenced "mint" account is actually owned by (i.e., legitimately created by) the SPL Token or Token-2022 program. This is the same bug class as the referenced Escher finding: a reference (`sale.edition` / here, `mint`) supplied inside attacker-controlled data is trusted and dereferenced without validating it was produced by the "legitimate factory" (the token program).

### Finding Description
`get_parsed_token_account` and `get_parsed_token_accounts` in `rpc/src/parsed_token_accounts.rs` extract the mint pubkey directly from the token account's byte layout via `get_token_account_mint`, and then load whatever account lives at that pubkey and unpack it as a `Mint`: [1](#0-0) [2](#0-1) [3](#0-2) 

Both paths ultimately call `get_mint_owner_and_additional_data` / `get_additional_mint_data`, which unpack whatever bytes are at the "mint" address as a `Mint` struct and return its `decimals`/extension configs — with no check that `mint_account.owner()` is one of the known SPL Token program ids: [4](#0-3) 

By contrast, other RPC paths that resolve a mint (`get_token_largest_accounts`, `get_token_program_id_and_mint`) explicitly call `is_known_spl_token_id(&mint_owner)` and reject the request if the "mint" isn't actually owned by a real token program: [5](#0-4) [6](#0-5) 

That ownership check is missing in the `jsonParsed` display path (`parsed_token_accounts.rs`). Any unprivileged user can create (or already control, e.g. via `AddressLookupTable`/any program with writable data) an account at an arbitrary pubkey whose data happens to satisfy the `Mint`/`StateWithExtensions<Mint>` byte layout (this only requires correct size/`is_initialized` flag — the owner program can be anything, e.g. the System program is not sufficient since it can't hold arbitrary data with lamports for rent, but any user-owned program — including a custom BPF program the attacker deploys — can hold accounts with arbitrary bytes). The attacker then creates a normal SPL token account (owned by the real token program, so it passes all normal validity checks) whose embedded `mint` field points at that attacker-controlled "fake mint" pubkey instead of a real mint.

### Impact Explanation
When any RPC client queries this attacker-crafted token account via `getAccountInfo`, `getProgramAccounts`, `getTokenAccountsByOwner`, etc. with `encoding: "jsonParsed"`, the validator will:
- decode the (fake) mint's `decimals` and extension configs from an account never validated to be a real mint of the SPL Token/Token-2022 program, and
- use that fabricated `decimals` value to compute `tokenAmount.uiAmount`/`uiAmountString` for the token account.

This lets an attacker make a token account's displayed balance appear arbitrarily larger or smaller than its raw `amount`, i.e., the validator returns wrong (misreported) account data to RPC consumers (wallets, explorers, bots) that trust the JSON-parsed response instead of independently validating the mint. This matches the allowed "wrong-slot/fork/account data returned" / "decoder panic and misreporting" impact category — a validator-served RPC response misrepresents on-chain state for a value an unprivileged actor fully controls (their own token account's displayed amount), which can be leveraged to deceive third parties relying on the RPC's parsed output (the same "fake edition, fool the buyer" pattern as the source report).

### Likelihood Explanation
High likelihood of exploitation: this requires only standard, unprivileged actions — creating a token account and a data-bearing account under an attacker-owned program, and issuing a single `jsonParsed` RPC call. No special permissions, no more than one RPC call per abuse (well under `CLUSTER_SLOT_TIME_TARGET / 2`), and no reliance on `getProgramAccounts` without indexes for the exploit path itself (the attacker chooses the target account directly via `getAccountInfo`).

### Recommendation
In `get_mint_owner_and_additional_data` / `get_additional_mint_data` (and any other place that dereferences a token account's embedded `mint` field to compute display data), verify `mint_account.owner()` is a member of `is_known_spl_token_id(...)` before trusting the unpacked `Mint` data, mirroring the check already present in `get_token_largest_accounts` and `get_token_program_id_and_mint`. If the owner check fails, fall back to omitting `tokenAmount` UI conversion (or reporting raw `amount` only) rather than trusting attacker-controlled decimals/extension data.

### Proof of Concept
1. Deploy a small BPF program (or use any owned account) and initialize an account `FakeMint` under it whose bytes match the `Mint`/`StateWithExtensions<Mint>` packed layout, with `decimals = 0` (or any attacker-chosen value) and `is_initialized = true`.
2. Create a normal SPL Token account `FakeTokenAccount` (owned by the real `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` program) with `amount = 1` but with its `mint` field set to `FakeMint`'s pubkey instead of a real mint.
3. Call `getAccountInfo` with `{"encoding":"jsonParsed"}` on `FakeTokenAccount`.
4. Observe the RPC response's `parsed.info.tokenAmount.uiAmount`/`decimals` is derived from `FakeMint`'s attacker-controlled data (unpacked via `get_additional_mint_data` in `rpc/src/parsed_token_accounts.rs`) even though `FakeMint` is not owned by any real SPL Token program — no `is_known_spl_token_id` check rejects it, unlike the equivalent check performed in `rpc/src/rpc.rs`'s `get_token_program_id_and_mint`/`get_token_largest_accounts`.

pub fn get_parsed_token_accounts<I>(
    bank: Arc<Bank>,
    keyed_accounts: I,
) -> impl Iterator<Item = RpcKeyedAccount>
where
    I: Iterator<Item = (Pubkey, AccountSharedData)>,
{
    let mut mint_data: HashMap<Pubkey, AccountAdditionalDataV3> = HashMap::new();
    keyed_accounts.filter_map(move |(pubkey, account)| {
        let additional_data = get_token_account_mint(account.data()).and_then(|mint_pubkey| {
            mint_data.get(&mint_pubkey).cloned().or_else(|| {
                let (_, data) = get_mint_owner_and_additional_data(&bank, &mint_pubkey).ok()?;
                let data = AccountAdditionalDataV3 {
                    spl_token_additional_data: Some(data),
                };
                mint_data.insert(mint_pubkey, data);
                Some(data)
            })
        });

        let maybe_encoded_account = encode_ui_account(
            &pubkey,
            &account,
            UiAccountEncoding::JsonParsed,
            additional_data,
            None,
        );
        if let UiAccountData::Json(_) = &maybe_encoded_account.data {
            Some(RpcKeyedAccount {
                pubkey: pubkey.to_string(),
                account: maybe_encoded_account,
            })
        } else {
            None
        }
    })
}

/// Analyze a mint Pubkey that may be the native_mint and get the mint-account owner (token
/// program_id) and decimals
pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}

/// Analyze a passed Pubkey that may be a Token program id or Mint address to determine the program
/// id and optional Mint
fn get_token_program_id_and_mint(
    bank: &Bank,
    token_account_filter: TokenAccountsFilter,
) -> Result<(Pubkey, Option<Pubkey>)> {
    match token_account_filter {
        TokenAccountsFilter::Mint(mint) => {
            let (mint_owner, _) = get_mint_owner_and_additional_data(bank, &mint)?;
            if !is_known_spl_token_id(&mint_owner) {
                return Err(Error::invalid_params(
                    "Invalid param: not a Token mint".to_string(),
                ));
            }
            Ok((mint_owner, Some(mint)))
        }
        TokenAccountsFilter::ProgramId(program_id) => {
            if is_known_spl_token_id(&program_id) {
                Ok((program_id, None))
            } else {
                Err(Error::invalid_params(
                    "Invalid param: unrecognized Token program id".to_string(),
                ))
            }
        }
    }
}
