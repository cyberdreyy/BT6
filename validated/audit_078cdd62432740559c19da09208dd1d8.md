### Title
Unbounded storage-wipe iteration on contract self-destruct enables gas-underpriced node stall - (File: crates/execution/trie/src/in_memory.rs, crates/execution/trie/src/db/store.rs, crates/execution/trie/src/db/rocksdb.rs)

### Summary
Destroying a contract account that has accumulated a large number of storage slots over its lifetime forces every backend of the proofs/trie storage layer (`InMemoryProofsStorage`, `MdbxProofsStorage`, `RocksdbProofsStorage`) to enumerate and tombstone *all* of that account's historical storage entries during block-state commit, at cost proportional to the account's total slot count — while the EVM only charges the flat/cheap `SELFDESTRUCT` gas cost (or equivalent `DestroyedChanged` wipe cost) to the transaction that triggers it.

### Finding Description
`HashedStorage::from_plain_storage` sets `wiped = was_destroyed()` when a contract account transitions to `AccountStatus::Destroyed`/`DestroyedChanged` (i.e., via `SELFDESTRUCT`, or destroy+recreate in the same block) [4](#0-3) . When `store_trie_updates` later persists this diff with `storage.is_wiped() == true`, each storage backend must walk the account's *entire prior storage history* to emit deletion tombstones for every slot ever written, not just the slots touched by the wiping transaction:

- The in-memory backend explicitly documents this as "an expensive operation" scanning its whole `hashed_storages` map for matching `(block, address, slot)` triples: [1](#0-0) 
- The MDBX backend runs a cursor over the account's full storage-history range from block 0 forward via `wipe_and_overlay`, collecting every key into a `BTreeMap` before writing tombstones: [5](#0-4) 
- The RocksDB backend does the same via `storage_hashed_cursor`/`storage_trie_cursor`, iterating the account's full key range: [3](#0-2) 

The cost of these traversals scales with however many storage slots the account has ever held across its history — a quantity an attacker fully controls (any number of cheap, individually-metered `SSTORE`s spread across many prior transactions/blocks) but which is *not* re-charged at destruction time. A single `SELFDESTRUCT` (or `DestroyedChanged` recreation) opcode has a fixed, small gas cost regardless of how many slots must be wiped, exactly mirroring the CVE-2020-36311 pattern where destroying a large KVM SEV VM required unregistering an unbounded number of encrypted memory regions at a cost disproportionate to the operation that triggered it, causing a soft lockup.

### Impact Explanation
An attacker can grow a single contract's storage to an extremely large number of slots over time (each write individually gas-metered and affordable), then trigger destruction in one transaction. The resulting state-commit work (trie/history wipe) executes synchronously as part of block processing/finalization on every full node, is not gas-metered, and scales with attacker-controlled prior storage size. If sized large enough, this can stall block processing for the node applying/committing the block, a Medium-severity node-halt/liveness impact analogous to the referenced kernel soft lockup.

### Likelihood Explanation
Growing large per-account storage footprints via many cheap `SSTORE`s and then self-destructing is straightforward and fully reachable by any unprivileged contract deployer/transaction sender; no special permissions, precompile access, or protocol violation is required — only patience/cost to first inflate the account's storage before the single destroying transaction.

### Recommendation
Bound or amortize the wipe cost: either (a) charge gas for the wipe proportional to the number of slots actually enumerated (tracking a per-account slot count so `SELFDESTRUCT`/`DestroyedChanged` gas reflects the true wipe cost), (b) perform the historical tombstoning lazily/incrementally (e.g., via background compaction or copy-on-read tombstoning) rather than synchronously during block commit, or (c) cap the number of slots wiped synchronously per block and defer the remainder, ensuring an attacker cannot force unbounded synchronous work with a single cheap transaction.

### Proof of Concept
1. Deploy a contract and, across many separate (cheap, gas-paid) transactions, write to a very large number of distinct storage slots (e.g., millions), building up persistent state under one address.
2. In a single transaction, invoke `SELFDESTRUCT` on that contract (or destroy+recreate it in the same block to trigger `DestroyedChanged`), paying only the flat self-destruct/recreate gas cost.
3. Observe that block-state commit on the receiving node(s) must enumerate all previously-written slots for that address via the wipe path (`InMemoryStorageInner::store_trie_updates`, `MdbxProofsStorage`'s `wipe_and_overlay`, or the RocksDB equivalent), with wall-clock cost proportional to the account's total historical slot count and disproportionate to the gas charged, stalling block processing.

    /// resolve in favor of `new_entries`, and `append_dup` the merged set in sorted-key order at
    /// `block_number`. Used by the wipe branches of `store_trie_updates_for_block` to keep new
    /// slots / nodes that arrive in the same block as a `wiped`/`is_deleted` entry —
    /// `HashedStorage::from_plain_storage` sets `wiped = was_destroyed()` (true for
    /// `DestroyedChanged`), so a SELFDESTRUCT + same-block recreate produces both at once.
    fn wipe_and_overlay<T, Next, I, K, VV, V>(
        &self,
        tx: &(impl DbTxMut + DbTx),
        block_number: u64,
        hashed_address: B256,
        mut next: Next,
        new_entries: I,
    ) -> BaseProofsStorageResult<Vec<T::Key>>
    where
        T: Table<Value = VersionedValue<V>> + DupSort,
        Next: FnMut() -> BaseProofsStorageResult<Option<(K, VV)>>,
        I: IntoIterator<Item = (K, Option<V>)>,
        (B256, K, Option<V>): IntoKV<T>,
        T::Key: Clone,
        K: Ord,
    {
        let mut merged: BTreeMap<K, Option<V>> = BTreeMap::new();
        while let Some((k, _vv)) = next()? {
            merged.insert(k, None);
        }
        for (k, v) in new_entries {
            merged.insert(k, v);
        }

        let mut cur = tx.cursor_dup_write::<T>()?;
        let mut keys: Vec<T::Key> = Vec::with_capacity(merged.len());
        for (k, value) in merged {
            let key: T::Key = (hashed_address, k, Option::<V>::None).into_key();
            let vv: T::Value = VersionedValue { block_number, value: MaybeDeleted(value) };
            cur.append_dup(key.clone(), vv)?;
            keys.push(key);
        }
        Ok(keys)
    }
