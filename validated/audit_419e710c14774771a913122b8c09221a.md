### Title
Stale KYC authorization persists across epoch transitions — de-whitelisted users can still claim deposits/withdrawals processed after revocation - ([File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
`IdleCDOEpochQueue` checks Keyring/whitelist authorization only at request time in `requestDeposit` and `requestWithdraw` via `_checkAllowed`, which verifies `cdoEpoch.isWalletAllowed(wallet)` and `isEpochRunning()`. The corresponding settlement/claim functions — `claimDepositRequest` and `claimWithdrawRequest` — perform no authorization check at all. This is the direct analog of CVE-2023-4379 ("code owner approval was not removed when the target branch was updated"): an approval captured against one state survives after that state (the user's credential / whitelist status) is revoked. ### Finding Description
In `contracts/IdleCDOEpochQueue.sol`:

- `requestDeposit` (line 103) and `requestWithdraw` (line 131) gate entry with `_checkAllowed(msg.sender)`, which calls `IdleCDOEpochVariant.isWalletAllowed` (Keyring credential or `KeyringIdleWhitelist.whitelist`, see `contracts/KeyringIdleWhitelist.sol:78-80`). Whitelist status is mutable: `setWhitelistStatus` (line 102) can revoke an entity at any time, and Keyring credentials are evaluated live.
- `claimDepositRequest` (line 373) and `claimWithdrawRequest` (line 393) only check that the epoch was priced/processed (`epochPrice`, `epochWithdrawPrice`, `epochPendingClaims`). They never call `_checkAllowed` or `isWalletAllowed`.
- `deleteRequest`/`deleteWithdrawRequest` similarly have no KYC check (acceptable — returning funds), but the *claim* paths are the security-relevant ones: `claimDepositRequest` mints tranche tokens to the caller, granting full ongoing participation (yield accrual, future withdraw rights), and `claimWithdrawRequest` pays out underlying.

Because requests span epoch boundaries by design (`userDepositsEpochs[user][nextEpoch]`), the honest admin/manager necessarily processes them (`processDeposits`, `processWithdrawRequests`, `processWithdrawalClaims`) at a later time. There is no point in the pipeline where revocation is re-evaluated before the payout/tranche mint.

The same gap exists at the CDO level: `claimWithdrawRequest`/`claimInstantWithdrawRequest` in `IdleCreditVault` (lines 301-349, `contracts/strategies/idle/IdleCreditVault.sol`) only require `_onlyIdleCDO()` and epoch gating (`epochNumber <= lastWithdrawRequest[_user]` revert), not `isWalletAllowed` — but the queue path is the cleanest analog since entry and claim are separated by a full epoch.

### Impact Explanation
Broken invariant: **access** — the protocol's stated policy is that only Keyring-cleared/whitelisted wallets may interact with the vault, yet a wallet whose credential or whitelist status is revoked mid-flight retains a fully executable claim. Concretely, after revocation the attacker can:

1. Call `claimWithdrawRequest(_epoch)` and receive `amount * epochWithdrawPrice[_epoch] / 1e18` underlying tokens — a withdrawal the protocol explicitly intended to deny to non-cleared wallets.
2. Call `claimDepositRequest(_epoch)` and receive freshly minted tranche tokens, re-entering the lender set and accruing future yield despite revocation.

Quantified loss example: user queues `requestWithdraw(1_000_000e6)` worth of AA tranches while KYC'd; admin revokes whitelist during the running epoch; manager stops epoch and processes claims; user claims ~1,000,000 USDC plus interest. The withdrawal itself is funded (so no insolvency), but it is an unauthorized payout under the protocol's access-control policy — equivalent severity to the GitLab bug where stale CODEOWNER approval enabled a merge that policy forbade.

### Likelihood Explanation
Requires only ordinary sequencing around honest privileged calls: user passes KYC → queues a request during a running epoch → Keyring/admin revokes the credential (a normal operational action, e.g., sanctions/compliance) → owner/manager processes the epoch as usual → revoked user claims. No privileged collusion needed. Caveat: the "loss" is policy-violating fund release rather than theft of other users' funds; if the program only accepts theft-of-others'-funds, this is a borderline-medium access-control issue rather than a high.

### Recommendation
Re-check authorization on the claim/mint side, or at processing time:

- In `claimDepositRequest`/`claimWithdrawRequest` (and/or `processDeposits`/`processWithdrawRequests`/`processWithdrawalClaims`), call `cdoEpoch.isWalletAllowed(msg.sender)` — or, to avoid griefing users who were legitimately cleared at request time, snapshot authorization intent explicitly and revoke claim rights when `isWalletAllowed` flips false before settlement.
- Mirror the check in `IdleCreditVault.claimWithdrawRequest`/`claimInstantWithdrawRequest` if the policy is meant to cover direct CDO interactions too.

### Proof of Concept
```solidity
// test/foundry/IdleCDOEpochQueue.t.sol context
function testClaimAfterWhitelistRevoked() external {
    _stopCurrentEpoch();                       // buffer for epoch #1

    address user = makeAddr('user');
    uint256 amount = 100e6;
    uint256 tranches = _depositWithUser(user, amount); // deposit + KYC ok

    vm.prank(manager);
    cdoEpoch.startEpoch();                     // epoch running

    // user requests withdraw while whitelisted
    _requestWithdrawWithUser(user, tranches);
    uint256 reqEpoch = strategy.epochNumber() + 1;

    // ---- admin revokes user's whitelist mid-epoch (honest actor) ----
    vm.prank(keyringAdmin);
    keyringWhitelist.setWhitelistStatus(user, false);
    assertFalse(cdoEpoch.isWalletAllowed(user));      // authorization revoked

    _stopCurrentEpoch();                       // buffer for epoch #2
    vm.prank(manager);
    queue.processWithdrawRequests();
    vm.prank(manager);
    queue.processWithdrawalClaims(reqEpoch);

    // BUG: revoked user still claims underlying - no isWalletAllowed check
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    queue.claimWithdrawRequest(reqEpoch);
    assertGt(underlying.balanceOf(user) - balPre, 0, 'revoked user paid out');
}
```

Note: the exact cheatcode setup (Keyring whitelist mock, `_depositWithUser`/`_requestWithdrawWithUser` helpers) follows the existing patterns in `test/foundry/IdleCDOEpochQueue.t.sol`; the assertion that fails the invariant is `claimWithdrawRequest` succeeding for a wallet where `isWalletAllowed` returns false.

Uncertainty: I could not fully verify whether `IdleCDOEpochVariant.claimWithdrawRequest`/`claimInstantWithdrawRequest` independently re-check `isWalletAllowed` before calling the strategy (the grep output was truncated); if they do, the queue-side gap still stands since the queue contract is the msg.sender to the CDO, not the end user.

  function claimDepositRequest(uint256 _epoch) external {
    // Deposits can be claimed only after the epoch has been finalized and priced.
    _checkNotAllowed(
      epochPrice[_epoch] == 0 ||
      epochPendingDeposits[_epoch] != 0 ||
      epochPrefundedDeposits[_epoch] != 0
    );

    uint256 amount = userDepositsEpochs[msg.sender][_epoch];
    if (amount == 0) {
      return;
    }
    // reset user deposit for the epoch
    userDepositsEpochs[msg.sender][_epoch] = 0;
    // transfer tranche tokens to user based on the price of that epoch
    IERC20Detailed(tranche).safeTransfer(msg.sender, amount * ONE_TRANCHE / epochPrice[_epoch]);
  }

  /// @notice claim withdraw request
  /// @param _epoch epoch when withdraw request were processed
  function claimWithdrawRequest(uint256 _epoch) external {
    // check if withdraw requests were processed and claimed for the epoch
    uint256 _withdrawPrice = epochWithdrawPrice[_epoch];
    _checkNotAllowed(
      (_withdrawPrice == 0 && !isEpochWithdrawZero[_epoch]) ||
      epochPendingClaims[_epoch] != 0
    );
    // amount is in tranche tokens
    uint256 amount = userWithdrawalsEpochs[msg.sender][_epoch];
    if (amount == 0) {
      return;
    }
    // reset user withdraw request counter for the epoch
    userWithdrawalsEpochs[msg.sender][_epoch] = 0;
    // transfer underlyings to user based on the withdraw price of that epoch
    if (_withdrawPrice != 0) {
      IERC20Detailed(underlying).safeTransfer(msg.sender, amount * _withdrawPrice / ONE_TRANCHE);
    }
  }
