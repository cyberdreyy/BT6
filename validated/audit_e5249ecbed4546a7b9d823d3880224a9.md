### Title
`BlockProposal::validate` anchors block acceptance to a non-canonical burn view via an attacker-supplied `TenureChange` Extend `burn_view_consensus_hash` - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
`NakamotoBlockProposal::validate` derives `burn_view_consensus_hash` from `NakamotoChainState::get_block_burn_view`, which for a `TenureChange` with an Extend-family cause simply takes the miner-supplied `tenure_change.burn_view_consensus_hash` after checking only that it *descends from the parent's burn view* — not that it is the sortition DB's current canonical tip. `validate()` then resolves `sort_tip` via `SortitionDB::get_block_snapshot_consensus`, which returns any indexed snapshot regardless of canonical status, and builds every subsequent "canonical" check (`check_block_has_valid_tenure`, `get_expected_burns`, `validate_nakamoto_tenure_snapshot`) from a `SortitionHandleConn` scoped to that potentially stale `sort_tip`, making the checks self-referential rather than anchored to the sortdb's true canonical tip.

### Finding Description
The equality that must hold is: `burn_view_consensus_hash` resolved in `validate()` == the sortition DB's actual canonical burn chain tip at validation time. The code only enforces ancestral connectivity to the parent block's burn view, not equality to the canonical tip: [1](#0-0) 

In `get_block_burn_view`, for a block carrying a `TenureChange` payload, the returned burn view is `tenure_change.burn_view_consensus_hash.clone()` after only checking that the sortition it names is a descendant of the parent's burn-view sortition (`get_ancestor_sort_id` / `connected_sort_id == parent_burn_view_sn.sortition_id`). There is no query against `SortitionDB::get_canonical_burn_chain_tip(sortdb.conn())` to confirm the named consensus hash is still the chain's heaviest fork.

`validate()` then does: [2](#0-1) 

`SortitionDB::get_block_snapshot_consensus` returns *any* stored snapshot matching the consensus hash — canonical or not — as `sort_tip`. The rest of validation (`check_block_has_valid_tenure`, `get_expected_burns`, `validate_normal_nakamoto_block_burnchain` → `validate_nakamoto_tenure_snapshot`) is performed through `db_handle = sortdb.index_handle(&sort_tip.sortition_id)`: [3](#0-2) 

`validate_nakamoto_tenure_snapshot` computes its own "`sort_tip`" via `SortitionDB::get_canonical_burn_chain_tip(db_handle)`, but because `db_handle` is already scoped to the attacker-influenced `sort_tip.sortition_id`, this "canonical tip" is just that same handle's anchor point — not the sortdb's global canonical fork. All ancestor checks are therefore performed relative to the attacker-chosen fork, not the real chain tip.

An attacker who wins a single miner slot fully controls both `tenure_consensus_hash` (their own tenure's sortition) and the Extend's `burn_view_consensus_hash`. They can name a burn-view sortition that: (a) is a genuine descendant of their tenure's sortition (satisfying the connectivity check), and (b) belongs to a burnchain fork that has since been abandoned by Bitcoin consensus, but whose snapshot the node's sortition DB still retains (sortition history for orphaned forks is not purged). `validate()` will resolve this stale fork as `sort_tip` and proceed through the rest of validation self-consistently, returning `BlockValidateOk` to the signer.

Signer-side, this gap is not caught: the stacks-signer chainstate logic (`v1.rs`/`v2.rs`) only special-cases burn-view changes for read-count-extend causes and otherwise treats a changed `burn_view_consensus_hash` on a normal Extend as acceptable, fully deferring to the node's `validate()` result: [4](#0-3) [5](#0-4) 

This means the signer's acceptance of the node's `POST /v3/block_proposal` response is the final line of defense for burn-view canonicity, and that defense is exactly what the node-side circular check fails to provide.

### Impact Explanation
If exploitable, this breaks the canonicity safety property: a signer would sign a Nakamoto block whose `TenureChange` Extend anchors the tenure to a non-canonical (abandoned) burn view, while the node's `validate()` reports acceptance. This is a Critical chain-safety issue — a signer signing a block that is not actually consistent with the canonical burnchain state, potentially enabling later reorg/equivocation conflicts once the true canonical fork's state diverges. The attack requires only the attacker's own single miner slot (to craft the `TenureChange` payload) plus normal proposal gossip, and it is repeatable across tenures as long as suitable orphaned-but-indexed sortitions exist.

### Likelihood Explanation
Preconditions: (1) the sortition DB must still retain a snapshot for an abandoned fork descending from the same sortition height as the parent's burn view (plausible since orphaned sortitions are not typically purged), (2) the attacker must hold the current miner slot to submit the tenure-extend proposal. No majority-signer collusion, no auth token, and no local node access are needed — this matches the specified unprivileged attacker model. However, I was unable to fully inspect the implementation of `check_block_has_valid_tenure` (referenced in `validate()` at line 602 but its body was not retrieved), which is explicitly commented as "(For the signer) Verify that the block's tenure is on the canonical sortition history." It is possible that function independently queries the true global canonical tip (via `sortdb.conn()` rather than the scoped `db_handle`) and closes this gap; this could not be confirmed or refuted with the available tooling.

### Recommendation
In `NakamotoChainState::get_block_burn_view` (or immediately after in `validate()`), explicitly compare the resolved `burn_view_consensus_hash`'s snapshot against `SortitionDB::get_canonical_burn_chain_tip(sortdb.conn())` (the raw, unscoped connection) rather than only checking ancestral connectivity from the parent. Reject the proposal unless the named burn view is on the sortdb's actual canonical fork. Additionally, audit `check_block_has_valid_tenure` to confirm it performs this canonical-fork check against the global tip rather than the `sort_tip`-scoped handle, and add an explicit regression test.
