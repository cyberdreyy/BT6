### Title
Single un-registered/opted-out recipient in `StakingContract.distribution_pool` blocks distribution to all other queued parties - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`distribute_internal` in `staking_contract.move` processes **all** pending payouts (staker withdrawals, operator commission, and any unpaid commission left over from a previous operator after `switch_operator`) in a single non-skippable `while` loop. Each iteration calls `aptos_account::deposit_coins`, which aborts if the recipient has never registered a `CoinStore` for `AptosCoin` **and** has opted out of direct coin transfers. Because the loop redeems shares and transfers funds for every queued recipient in one atomic transaction, one recipient in that state causes the whole call — and therefore every other party's payout in the same batch — to fail, exactly mirroring the "one bad order blocks the whole batch" class of bug from the external report.

### Finding Description
`distribute_internal` iterates over all shareholders of `staking_contract.distribution_pool` and pays each one out before returning: [1](#0-0) 

Each payout goes through `aptos_account::deposit_coins`: [2](#0-1) 

`deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when the target address has **not** registered a `CoinStore<AptosCoin>` and has explicitly disabled `allow_arbitrary_coin_transfers` via `aptos_account::set_allow_direct_coin_transfers(false)` — an action any account owner can perform unprivileged on their own address at any time.

`distribution_pool` can legitimately contain more than one address simultaneously: the staker (pending withdrawal from `unlock_stake`), the current operator/beneficiary (pending commission from `request_commission`), and even a **previous** operator who is still owed unpaid commission after `switch_operator` reassigns the contract to a new operator (confirmed by the `test_staker_can_switch_operator` test, which shows a pending distribution for `operator_1` persisting after the switch): [3](#0-2) 

Since `distribute_internal` is invoked as a precondition inside `request_commission`, `unlock_stake`, and other staking-contract entry points before they can complete their own logic, if *any single* queued recipient (staker, operator, beneficiary, or a stale former operator) has previously called `set_allow_direct_coin_transfers(false)` on an address that has never held `AptosCoin`, every subsequent call that needs to run `distribute_internal` for that `StakingContract` will abort — for everyone, not just the griefer. [4](#0-3) [5](#0-4) 

### Impact Explanation
This can strand an innocent staker's already-unlocked principal and rewards (and an operator's commission) indefinitely, because the batched loop is all-or-nothing: there is no mechanism in `distribute_internal` to skip a failing recipient and continue with the others, unlike what the external report recommends fixing (skip a bad order rather than reverting the whole batch). A staker who unlocked stake and is waiting on `unlock_stake`/`distribute` cannot get their funds out as long as any co-recipient in the pool is in the "opted-out, unregistered" state, which meets the "withdrawal of stake ... not owned by the attacker" / "permanent lock ... of claim rights" impact criteria.

### Likelihood Explanation
The precondition (an address that has never registered `AptosCoin` and calls `set_allow_direct_coin_transfers(false)`) is a normal, unprivileged, one-time action any account can take before ever interacting with a staking contract, so the DoS condition is easy to set up. However, I was **not able to fully verify** within the available tool budget whether operators can freely redirect their beneficiary to an arbitrary fresh address they control (there is an `EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED` error constant in the module, suggesting some beneficiary-change paths may be restricted), which would determine whether a malicious operator can weaponize this against an unrelated staker versus only being able to self-grief. The core loop-abort mechanism itself, however, is confirmed directly in the code.

### Recommendation
In `distribute_internal`, follow the same remediation pattern recommended in the source report: if `aptos_account::deposit_coins` would fail for a given recipient (i.e., `!coin::is_account_registered<AptosCoin>(recipient) && !aptos_account::can_receive_direct_coin_transfers(recipient)`), skip that recipient (leave their redeemed value in a queryable/re-claimable state) and continue distributing to the remaining shareholders instead of aborting the entire call.

### Proof of Concept
Not independently reproduced end-to-end due to tool limitations (no execution environment available), but the mechanism is directly supported by code:
1. Address `A` (to be staker or operator's beneficiary) calls `aptos_account::set_allow_direct_coin_transfers(A, false)` before ever receiving `AptosCoin`.
2. `A` becomes staker/operator/beneficiary in a `StakingContract`, or remains as a stale previous operator after `switch_operator`.
3. Any subsequent call requiring `distribute_internal` (e.g. `unlock_stake`, `request_commission`, `distribute`) attempts `aptos_account::deposit_coins(A, ...)` inside the `while` loop and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, reverting the whole transaction and blocking payout to every other queued recipient in the same `distribution_pool`.
