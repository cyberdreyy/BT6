Found a concrete analog: `is_simple_vote_transaction` (a coarse "any single vote-program instruction" check) is used as an exemption/classification flag across fee prioritization, cost accounting, and forwarding paths, without verifying that the instruction is actually a vote-state-update — mirroring the `GovernorAlpha` bug class where a coarse "is this a call to X" check is used as a proxy for "is this the specific privileged operation," bypassable by choosing a benign instruction variant of the same program.

### Title
Coarse `is_simple_vote_transaction` classification allows non-vote vote-program instructions to receive vote-transaction exemptions - (File: `runtime-transaction/src/runtime_transaction/transaction_view.rs`, `perf/src/sigverify.rs`)

### Summary
`is_simple_vote_transaction_impl`/`is_simple_vote_transaction_view` classify a transaction as a "simple vote transaction" solely by checking that it is a legacy message with ≤2 signatures and exactly one instruction whose program id equals the vote program [1](#0-0) . Unlike `vote::vote_parser::is_valid_vote_only_transaction`, which additionally requires `VoteInstruction::is_single_vote_state_update()` [2](#0-1) , the "simple vote" classifier never inspects the instruction discriminant/data at all.

### Finding Description
This is the same bug class as the `GovernorAlpha` veto issue: a security/economic exemption is granted based on a coarse condition ("targets program X") rather than the specific action that justifies the exemption ("is a vote-state-update"). Here, `is_simple_vote_transaction` is computed from `program_instructions_iter` matching the vote program id only, with no decode of the `VoteInstruction` enum [3](#0-2) . The `perf/src/sigverify.rs::is_simple_vote_transaction_view` implementation is identical in spirit [1](#0-0) .

This `is_simple_vote_transaction` flag is then relied upon in multiple unprivileged, ordinary-transaction-facing paths to grant exemptions intended only for actual votes:
- Cost tracker: vote transactions are exempted from the normal non-vote cost-tracking bucket/limits [4](#0-3) .
- Prioritization fee cache: vote transactions are explicitly skipped from prioritization-fee accounting ("Vote transactions are not prioritized, therefore they are excluded from updating fee_cache") [5](#0-4) .
- Banking-stage counters/accounting distinguish "non-vote" vs vote transactions using this same flag [6](#0-5) .
- Forwarding stage routes/forwards "simple vote" packets over the dedicated vote path/vote client rather than the general non-vote forwarding path and client [7](#0-6) .

Because any `VoteInstruction` variant targeting the vote program (e.g. `Authorize`, `AuthorizeWithSeed`, `UpdateCommission`, etc. — not just `Vote`/`TowerSync`) satisfies the coarse check, an attacker can submit a single-instruction, ≤2-signature legacy transaction invoking a cheap/benign vote-program instruction (not an actual vote-state update) and have it treated system-wide as a "vote" for cost/fee/forwarding purposes, exactly analogous to appending an innocuous self-call to `GovernorAlpha.votingDelay()` to trigger a broad "targets self" check without performing the intended privileged action.

### Impact Explanation
Non-vote vote-program transactions can piggyback on vote-transaction exemptions:
- Bypass/weaken prioritization-fee based spam mitigation by avoiding entry into the prioritization fee cache used for fee-market signal (`update()` early-`continue`s on `is_simple_vote_transaction()`), letting attacker transactions dodge fee tracking that non-vote transactions are subject to.
- Skew cost-tracker accounting, since vote transactions use a separate/relaxed accounting path relative to ordinary transactions.
- Cause vote-designated forwarding/QUIC paths (dedicated vote client, separate from stake-weighted non-vote client) to carry attacker-controlled non-vote-purpose traffic, potentially degrading vote propagation given votes and these look-alikes now share vote ingest/forward capacity.

This is a resource-accounting/ingest-classification integrity issue rather than a direct fund-loss bug, but it is a genuine unprivileged-transaction-reachable divergence between the intended "is this an actual vote" semantics and the coarse check actually used to grant exemptions in several subsystems.

### Likelihood Explanation
High reachability: any user can construct and submit such a transaction from the normal transaction ingestion path (RPC submission or TPU/QUIC) without any special privilege — it only requires one instruction to the vote program (any `VoteInstruction` variant), a legacy message, and ≤2 signatures, all trivially satisfiable.

### Recommendation
Restrict the "simple vote transaction" fast-path/exemption classification the same way `is_valid_vote_only_transaction` already does: decode the instruction data and require `VoteInstruction::is_single_vote_state_update()` (or an equivalent allow-list of the specific vote-state-update variants) rather than only checking the program id, in both `runtime-transaction/src/runtime_transaction/transaction_view.rs::is_simple_vote_transaction` and `perf/src/sigverify.rs::is_simple_vote_transaction_view`, before granting cost/fee/forwarding exemptions.

### Proof of Concept
1. Construct a legacy `Transaction` with a single instruction: `solana_vote_interface::instruction::authorize(&vote_pubkey, &authorized_pubkey, &new_authorized_pubkey, VoteAuthorize::Voter)` (or any non-vote-state-update `VoteInstruction` variant), signed by 1–2 keys.
2. Submit via normal TPU/RPC ingestion.
3. Observe: `is_simple_vote_transaction_view`/`is_simple_vote_transaction` returns `true` (per the existing test coverage confirming any single vote-program-id instruction satisfies the check) [8](#0-7) , causing the transaction to be (a) excluded from `PrioritizationFeeCache::update` [9](#0-8) , (b) accounted under vote-transaction cost tracking, and (c) routed via the dedicated `VoteClient` forwarding path [10](#0-9)  — despite performing no actual vote.

Note on confidence: I was not able to fully trace every downstream consumer of `is_simple_vote_transaction` (14 call sites found) within the available exploration budget, so there may be additional or different-severity effects (e.g. in `entry/src/entry.rs`, `runtime/src/bank.rs`, `rpc/src/transaction_status_service.rs`) not analyzed here.

fn is_simple_vote_transaction_view<D: TransactionData>(view: &SanitizedTransactionView<D>) -> bool {
    // vote could have 1 or 2 sigs; zero sig has already been excluded by sanitization.
    if view.num_signatures() > 2 {
        return false;
    }

    // simple vote should only be legacy message
    if !matches!(view.version(), TransactionVersion::Legacy) {
        return false;
    }

    // skip if has more than 1 instruction
    if view.num_instructions() != 1 {
        return false;
    }

    let mut instructions = view.instructions_iter();
    let Some(instruction) = instructions.next() else {
        return false;
    };
    if instructions.next().is_some() {
        return false;
    }

    let program_id_index = usize::from(instruction.program_id_index);
    let Some(program_id) = view.static_account_keys().get(program_id_index) else {
        return false;
    };

    *program_id == solana_sdk_ids::vote::id()
}

/// Check if a transaction is a valid vote-only transaction.
/// A valid vote-only transaction must:
/// 1. Have exactly one instruction
/// 2. That instruction must be to the vote program
/// 3. That instruction must be a single vote state update (UpdateVoteState, TowerSync, etc.)
pub fn is_valid_vote_only_transaction(tx: &impl SVMTransaction) -> bool {
    let mut instructions = tx.program_instructions_iter();

    let Some((program_id, instruction)) = instructions.next() else {
        return false;
    };

    if instructions.next().is_some() {
        return false;
    }

    if !solana_sdk_ids::vote::check_id(program_id) {
        return false;
    }

    limited_deserialize::<VoteInstruction>(instruction.data, solana_packet::PACKET_DATA_SIZE as u64)
        .map(|ix| ix.is_single_vote_state_update())
        .unwrap_or(false)
}
