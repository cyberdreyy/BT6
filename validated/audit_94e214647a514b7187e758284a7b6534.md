### Title
Silent Pending-Inactive-to-Inactive Settlement in `join_validator_set_internal` Bypasses Delegation Pool Synchronization, Breaking OLC Isolation Invariant - (File: aptos-move/framework/aptos-framework/sources/stake.move)

### Summary
`join_validator_set_internal` in `stake.move` contains a state-mutating branch that silently merges `pending_inactive` coins into `inactive` on the underlying `StakePool` whenever the lockup has expired, executed directly by any node operator calling the public entry function `join_validator_set`. Like the `AddApprover` call in the external report, this mutation happens with no error handling, no assertion, and — critically — no invocation of the dependent module's own synchronization routine. For a delegation pool built on top of that `StakePool`, this call path can move stake between accounting states without going through `delegation_pool::synchronize_delegation_pool`, which is the sole entry point the module's own documented invariants require before any inactive/pending_inactive transition is reflected in `total_coins_inactive` and `observed_lockup_cycle`.

### Finding Description
`join_validator_set_internal` is reachable by any unprivileged account that holds the `operator` role on a `StakePool` (an operator is not necessarily privileged — it can be set by anyone via `staking_contract::create_staking_contract` or `vesting`, and for a `delegation_pool`, the operator is a normal external account, not the delegation-pool resource account itself): [1](#0-0) 

The vulnerable branch: [2](#0-1) 

This code merges the entire `pending_inactive` coin balance into `inactive` directly on the `StakePool` resource, bypassing the standard epoch-driven `update_stake_pool`/`on_new_epoch` path that the framework normally uses for such transitions. Critically, it does this without calling `delegation_pool::synchronize_delegation_pool`, which the delegation pool module's own specification states is mandatory before *any* stake-management operation: [3](#0-2) 

The delegation pool module explicitly documents the invariant that "unlocking and/or unlocked stake originating from different real lockups are never mixed together into the same pool_u64" and that "no delegator can have unlocking and/or unlocked stake (pending withdrawals) in different OLCs." The module tracks its own `total_coins_inactive` field and `observed_lockup_cycle` (OLC) counter, which are only ever advanced inside `synchronize_delegation_pool`, by comparing the stake pool's `inactive` balance against the delegation pool's last-known value.

Because `join_validator_set_internal` moves coins from `pending_inactive` to `inactive` on the raw `StakePool` resource outside of this synchronization protocol, the delegation pool's internal ledger (`total_coins_inactive`, `observed_lockup_cycle`, and the `pool_u64` shares per OLC) is left silently stale relative to the actual `stake::StakePool` state, analogous to the unchecked `AddApprover` failure in the external report: a state-changing call with no error signal and no downstream consistency check.

I was not able to fully trace `synchronize_delegation_pool`'s internal drift-detection function to completion before this session's tool budget ran out, so I cannot state with certainty the exact numeric outcome (e.g., whether this desync causes reward misattribution, a failed/incorrect OLC advance, or stranded withdrawal rights) — this remains to be confirmed by stepping through `calculate_stake_pool_drift` (or equivalent) inside `delegation_pool.move` and cross-referencing it against the coin merge in `join_validator_set_internal`.

### Impact Explanation
If the desynchronization described above causes the delegation pool's OLC bookkeeping to diverge from the actual stake pool's inactive/pending_inactive split, delegators' pending withdrawals could be attributed to the wrong observed lockup cycle, mixing unlocking stake from different real lockups into the same `pool_u64` — a scenario the module's own documentation calls out as one that "invalidates the accounting of which rewards belong to whom." This could redirect rewards or strand a delegator's ability to withdraw already-inactive stake, matching the "Stake And Lockup Gate" criteria for wrong-role/wrong-balance impact.

### Likelihood Explanation
The trigger requires only that: (1) an operator's `StakePool` is `INACTIVE` with a nonzero `pending_inactive` balance whose `locked_until_secs` has already elapsed (e.g., a delegation pool validator was previously kicked/left the set), and (2) the operator (an unprivileged, non-governance role) calls `join_validator_set`/`join_validator_set_internal` to rejoin. Both are ordinary operator actions with no special privileges required, so the precondition is realistically reachable, but I could not fully verify with certainty (within the remaining tool budget) that `synchronize_delegation_pool`'s drift detection is actually fooled by this out-of-band mutation, so likelihood should be treated as provisional pending that trace.

### Recommendation
Before performing the silent `pending_inactive -> inactive` settlement in `join_validator_set_internal`, either (a) require callers that operate on delegation-pool-owned stake pools to invoke `delegation_pool::synchronize_delegation_pool` first so `total_coins_inactive`/`observed_lockup_cycle` stay consistent, or (b) remove this bespoke settlement logic entirely and rely solely on the standard `update_stake_pool` epoch-transition path (which `delegation_pool.move`'s invariants already assume is the only mutator of `inactive`/`pending_inactive`).

### Proof of Concept
Conceptual trigger (needs to be validated end-to-end against `delegation_pool.move`'s synchronization function, which I was unable to fully trace in this session):
1. Operator sets up a `delegation_pool` and joins the validator set; delegators unlock stake, creating `pending_inactive` shares in OLC N.
2. The stake pool leaves the validator set (e.g., insufficient stake) while `pending_inactive` is still unlocking; `locked_until_secs` eventually elapses while the pool is `INACTIVE`.
3. Operator calls `join_validator_set(operator, pool_address)`, which invokes `join_validator_set_internal`, hitting the branch at `stake.move:1103-1108` that merges `pending_inactive` into `inactive` directly on the `StakePool`, without any call into `delegation_pool::synchronize_delegation_pool`.
4. A delegator subsequently calls `unlock`/`withdraw`/`add_stake` on the delegation pool, triggering `synchronize_delegation_pool`; whether this correctly detects and reconciles the out-of-band inactive-stake jump, or instead misattributes/mismatches the OLC accounting, is the open question that needs direct tracing of `calculate_stake_pool_drift` (or equivalent) inside `delegation_pool.move` to confirm exploitability.
