## Finding

### Title
Stale confirmations from removed multisig members still count toward execution threshold, allowing requests to execute below the live-member quorum - ([File: multisig2/src/lib.rs])

### Summary
This is a structural analog of the reported bug class: a value used to authorize an action (`confirmations` count) is not refreshed against the current, live state (`members`) at the moment it is relied upon, so a stale record accepted before a state change is treated as still valid after the change — exactly like using a stale spot price after expiry instead of the value that should apply at settlement time. In `multisig2`, `confirm()` counts confirmations recorded in a `HashSet<String>` toward `num_confirmations` [1](#0-0) , but `delete_member()` only purges pending requests originally *submitted* by the removed member — it never scans other requests' confirmation sets to strip out confirmations that member had already cast [2](#0-1) .

### Finding Description
`MultiSigContract` stores confirmations per request as `LookupMap<RequestId, HashSet<String>>`, where each entry is `member.to_string()` [3](#0-2) . When a member calls `confirm`, the contract checks only that the request exists and the caller is currently a member (`assert_valid_request` → `current_member().is_some()`), and then increments the count [4](#0-3) [5](#0-4) . It never re-validates that the *other* entries already present in `confirmations` still belong to current members.

`delete_member()` is the only place that cleans up requests/confirmations tied to a removed member, but the cleanup is scoped only to requests where `r.member == member`, i.e., requests the removed member *originally created*:
```rust
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [6](#0-5) 

If the removed member had instead only *confirmed* someone else's pending request (not created it), that confirmation entry is left untouched in `self.confirmations`. The binding this breaks is:

`confirmations counted toward num_confirmations == confirmations from currently live members`

After a member is deleted, this equality no longer holds — a stale confirmation from a non-member is still summed into the threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations` [7](#0-6) .

### Impact Explanation
This allows a pending request (e.g., a `Transfer` of NEAR funds, `AddKey`, `AddMember`/`DeleteMember`, or arbitrary `FunctionCall`) to execute after collecting confirmations from fewer than `num_confirmations` *currently authorized* members, because one "confirmer" is a former member whose approval should no longer count. This is a multisig request executed below the intended live threshold, which the task rules classify as Critical impact (funds moved without the required number of currently-entitled approvers, or a governance/config action performed with insufficient live authorization).

### Likelihood Explanation
This requires no privileged or out-of-scope action beyond normal multisig operation: a request is created and partially confirmed, then, independently, a `DeleteMember` request removes one of the confirmers (a legitimate, unprivileged flow that member-removal is designed to support, e.g. rotating a compromised or departing signer). The stale confirmation is never invalidated, and any remaining member can complete the threshold and trigger execution. No malicious deployment argument, redeploy, or key compromise is needed — it's an inherent gap in state cleanup on `delete_member`.

### Recommendation
On `delete_member`, iterate over **all** active requests' confirmation sets (not just those created by the removed member) and remove the deleted member's entry from each; if removing that entry causes any request's confirmation count to now be `0`, that's fine, but the counts must reflect only current members. Alternatively, validate membership of every entry in the confirmation set at `confirm()`-time before counting (i.e., filter `confirmations` against `self.members` before comparing to `self.num_confirmations`).

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C], 2)` (K=2 of N=3).
2. Member `B` calls `add_request(R)` for a `Transfer` action; `confirmations[R] = {}`.
3. Member `A` calls `confirm(R)`; since `0 + 1 < 2`, it stores `confirmations[R] = {A}` (not yet executed) — see `confirm()` logic [8](#0-7) .
4. Members `B` and `C` submit and confirm a separate `DeleteMember{A}` request, which executes `delete_member(A)`. This only clears requests where `r.member == A`; since `R` was created by `B`, `confirmations[R] = {A}` remains untouched [6](#0-5) . Members are now `{B, C}`, and `num_confirmations` (2) still satisfies `members.len() - 1 >= num_confirmations` check at deletion time.
5. Member `C` calls `confirm(R)`. `confirmations.len()` (1, from stale `A`) `+ 1 = 2 >= num_confirmations (2)` → `execute_request(R)` runs the `Transfer`, even though only one currently-live member (`C`) actually approved it.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
