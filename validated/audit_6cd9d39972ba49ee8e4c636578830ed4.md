### Title
`drift_claim_bad_debt` sweeps the entire claimant ATA balance to the fee wallet instead of only the claimed amount - (File: `programs/marginfi/src/instructions/drift/claim_bad_debt.rs`)

### Summary
`drift_claim_bad_debt` correctly computes the actual claimed amount via a before/after balance diff, but then ignores that computed value and instead transfers out the **entire current balance** of the claimant token account. Any token balance that happens to be sitting in that account at call time — not just the newly-claimed bad-debt allocation — is swept to the global fee wallet, mirroring exactly the `ClaimFees`-style bug class from the external report (measuring "total balance" instead of the delta actually produced by the action being settled).

### Finding Description
The handler computes the real claimed delta but discards it for the actual transfer: [1](#0-0) 

`cpi_transfer_to_destination` re-reads the raw token balance from `claimant_token_account` (not the `received_amount` diff) and transfers all of it: [2](#0-1) 

`claimant_token_account` is the canonical ATA for `claim_mint`, owned by the bank's `liquidity_vault_authority` PDA — the same authority signer used across all of the bank's other CPI flows (Drift deposits/withdrawals, Kamino operations, etc.): [3](#0-2) 

The instruction has no admin/authority gate tied to the bank (`bank` is only checked via `has_one` on integration accounts and an asset-tag constraint, and `payer` is an unconstrained `Signer`), so it is reachable by any unprivileged caller who can supply a valid merkle proof for the distributor — the exact "permissionless sweep" precondition described in the report. This is structurally the same root cause as the Hybra `GaugeCL._claimFees` bug: the code has the information needed to isolate the newly-produced funds (`received_amount`), but the actual fund-moving step instead reads and moves the account's *total* balance, so any unrelated tokens co-located in that PDA-owned account (dust from a prior partial/failed claim, or funds transiently routed through the same claim-mint ATA owned by `liquidity_vault_authority` by other Drift/Kamino instructions using that authority) are permanently redirected to the global fee wallet instead of being credited back to the bank/depositors.

### Impact Explanation
Any value that ends up in the claim-mint ATA of `liquidity_vault_authority` for reasons unrelated to the specific `new_claim` call being processed (e.g., residual dust from a previous claim, or any other flow that transiently stages funds through that same ATA/authority) is swept irrecoverably to the global fee wallet rather than to the bank's liquidity vault. This is a direct, permanent loss of bank/depositor funds with no on-chain path to recovery, since the destination is the protocol's `global_fee_wallet`, not depositors.

### Likelihood Explanation
`drift_claim_bad_debt` is callable without bank-admin authorization (no `has_one = admin` gate on the `bank` account, `payer` is any signer), so exploitation only requires possessing (or waiting for) a valid merkle-distributor proof and observing/triggering a state where the claimant ATA holds more than the amount granted by that specific claim. Because the code already computes and emits the correct `received_amount` alongside the incorrect `swept_amount`, the discrepancy is directly observable on-chain via `DriftClaimBadDebtEvent`, making detection and exploitation straightforward for anyone monitoring bank activity.

### Recommendation
Transfer only `received_amount` (the pre/post-claim balance delta already computed) instead of the full current balance of `claimant_token_account`. If leftover/dust balances are expected to accumulate in that ATA, sweep them explicitly and separately (e.g., back into the bank's `liquidity_vault`, crediting depositors) rather than folding them into the fee-wallet transfer of an unrelated claim instruction. Consider gating `drift_claim_bad_debt` behind an admin/keeper role if permissionless dust accumulation cannot be fully ruled out.

### Proof of Concept
Conceptual sequence (mirrors the Hybra PoC pattern):
1. `claimant_token_account` (ATA of `liquidity_vault_authority` for `claim_mint`) ends up holding `D` tokens unrelated to the pending distributor claim (e.g., dust left from a previous `drift_claim_bad_debt` call whose `new_claim` under-delivered relative to expectations, or any other transient transfer into that same PDA-owned ATA).
2. Anyone calls `drift_claim_bad_debt` with a valid merkle proof for amount `A`.
3. `pre_claim_balance = D`; after `cpi_new_claim`, `post_claim_balance = D + A`; `received_amount` is correctly computed as `A` ( [4](#0-3) ).
4. `cpi_transfer_to_destination` re-reads the account balance as `D + A` and transfers the full `D + A` to `destination_token_account` ( [5](#0-4) ), sending the unrelated `D` tokens to the global fee wallet instead of leaving them recoverable for the bank.
5. `emit_claim_event` reports `received_amount = A` but `swept_amount = D + A`, confirming on-chain that more was moved than was actually claimed ( [6](#0-5) ).

Note: I was not able to fully trace every other Drift/Kamino code path that might transiently deposit into this same claim-mint ATA owned by `liquidity_vault_authority` (index coverage is limited for some integration files), so the exact mechanism by which unrelated funds `D` would first arrive in that account is not fully confirmed — this should be verified in a full repository checkout. The core defect (discarding the correctly-computed `received_amount` in favor of sweeping the raw account balance) is confirmed directly from the cited source.

    fn cpi_transfer_to_destination(&self) -> MarginfiResult<u64> {
        let amount = accessor::amount(&self.claimant_token_account.to_account_info())?;
        if amount == 0 {
            return Ok(0);
        }

        let accounts = Transfer {
            from: self.claimant_token_account.to_account_info(),
            to: self.destination_token_account.to_account_info(),
            authority: self.liquidity_vault_authority.to_account_info(),
        };
        let bump = self.bank.load()?.liquidity_vault_authority_bump;
        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), bump);
        let cpi_ctx = CpiContext::new_with_signer(self.token_program.key(), accounts, signer_seeds);

        token::transfer(cpi_ctx, amount)?;
        Ok(amount)
    }

            requested_amount,
            received_amount,
            swept_amount,
        });

    }
