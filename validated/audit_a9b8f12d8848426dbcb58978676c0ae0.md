### Title
Global `requestID`-only keying of `h.callbacks` allows cross-workflow request-ID squatting and response misrouting - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`setupCallback` stores callbacks in `h.callbacks` keyed only by the client-supplied `requestID`, with no workflowID or sender binding. Because `HandleNodeTriggerResponse` later looks up the callback purely by `resp.ID` and dispatches to whichever `responseAggregators[shard.donID]` was captured at registration time, two different workflows/users racing with the same `requestID` string can (a) trivially DoS each other via `jsonrpc.ErrConflict`, and (b) if their workflows share a DON/shard, have their node responses misrouted into the wrong caller's aggregator/callback.

### Finding Description
`HandleUserTriggerRequest` (core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:88-140) validates, resolves, authorizes, and rate-limits a request, then calls `setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)` at line 134. `setupCallback` (lines 398-435) does: [1](#0-0) 

The map key is `requestID` alone — `req.ID` — supplied by the caller with essentially no server-side uniqueness guarantee beyond "not empty" and "no `/`" (`validateRequestID`, lines 183-195). There is no per-workflow or per-sender namespace prefix baked into the map key.

Response routing is symmetric: `HandleNodeTriggerResponse` (lines 448-496) looks up `h.callbacks[resp.ID]` by the same bare string, then resolves the shard via `nodeAddrToShard[nodeAddr]` and indexes into `saved.responseAggregators[shard.donID]` — the aggregator map captured at whichever registration won the race: [2](#0-1) 

Because the top-level JSON-RPC `id` field sent to nodes is preserved unchanged from the caller's `req.ID` (see `reqWithAuthorizedKey`, lines 744-759, and `sendWithRetries`/`sendToShard`), a node's echoed response `id` is indistinguishable between two different logical requests that happen to share the same string. Shards/DONs (`shardEndpoint`, core/services/gateway/handlers/capabilities/v2/shard_endpoints.go:11-22) are shared infrastructure that can serve multiple workflows simultaneously; nothing in `buildShardEndpoints` or `WorkflowShards` guarantees disjoint shard assignment per workflow.

Exploit flow:
1. Attacker controls/knows a `requestID` value `R` (attacker picks it themselves — they need not "guess" a victim's ID if they control timing, e.g., by re-using recently observed or brute-forced sequential/timestamp-based IDs from another endpoint).
2. Attacker sends `HandleUserTriggerRequest` for their own workflow `W2` with `id=R`.
3. Concurrently, the victim sends a legitimate request for `W1` also using `id=R` (e.g., due to a client-side ID generation collision, retried idempotency key, or attacker deliberately front-running a predictable ID scheme).
4. Whichever caller's `setupCallback` executes first under `callbacksMu` wins; the loser receives `jsonrpc.ErrConflict` with the message `"requestID: %s has already been used"` (line 403) — directly confirming to the attacker that a request with that exact `requestID` is in flight, an information leak about the victim's request identifier/timing that the attacker should not be able to observe.
5. If the attacker wins the race and `W1`/`W2` share any DON shard (`donID`), subsequent node responses to the victim's real request for `W1` — which the gateway cannot distinguish from the attacker's own responses because both carry `id=R` — get routed into `h.callbacks[R]`, which now belongs to the attacker. If the attacker's `responseAggregators` map contains that shared `donID` (from `W2`'s own shard assignment) and enough matching responses arrive, `saved.SendResponse` at line 481 delivers the aggregated payload — potentially derived from `W1` node activity — to the attacker's callback instead of the victim's, and the victim's own `setupCallback` call already failed with `ErrConflict` before ever reaching `sendWithRetries`, so the victim's legitimate request is silently dropped without being sent to nodes at all.

No existing check (auth, rate limiter, presenter) verifies that the entity finalizing/reading a `requestID`'s callback is the same workflow/sender that registered it; `authorizeRequest` (line 361-369) only validates the caller's signature against the target workflow being requested, not against exclusive ownership of the `requestID` key.

### Impact Explanation
This maps to Chainlink's "cross-user response confusion" bounty class: an unprivileged caller of the HTTP trigger workflow endpoint can (1) cause denial-of-service against a specific in-flight request from another workflow/user by ID-squatting (their real request is silently rejected with `ErrConflict` and never sent to nodes), and (2) leak the fact that a specific `requestID` is currently in use by someone else, which is metadata that should not cross workflow/tenant boundaries. Under favorable conditions (shared DON/shard between the two workflows), it further creates a path for response misdelivery across workflow boundaries.

### Likelihood Explanation
Exploitability requires the attacker to know or predict the exact `requestID` string a victim is about to use and to win a `sync.Mutex`-guarded race with fine timing — feasible if requestIDs are client-generated in a low-entropy or predictable manner (e.g., sequence numbers, timestamps) but not if the caller uses high-entropy UUIDs. The response-misdelivery escalation additionally requires the two workflows to share a DON shard. This is a real but conditional/timing-dependent design gap rather than a trivially always-exploitable bug; it is best characterized as a missing request-binding invariant rather than a guaranteed cross-tenant compromise in default configuration.

### Recommendation
Namespace `h.callbacks` keys by both `workflowID` (or workflow owner) and `requestID` (e.g., `workflowID + "/" + requestID`), and include the same composite key in the response envelope routed back from nodes (or otherwise verify that `HandleNodeTriggerResponse` only accepts a response into a `savedCallback` whose stored `workflowID` matches the shard/DON that produced the response). This removes the shared global keyspace and eliminates both the `ErrConflict` cross-tenant info leak and any theoretical cross-workflow aggregation path.

### Proof of Concept
Go unit test in `http_trigger_handler_test.go`:
1. Construct an `httpTriggerHandler` with two workflows `W1`, `W2` assigned to an overlapping shard/donID via `workflowMetadataHandler`.
2. Call `setupCallback(ctx, "R", callbackW1, t0, W1)` and `setupCallback(ctx, "R", callbackW2, t0, W2)` concurrently (e.g., via two goroutines with a `sync.WaitGroup` and a barrier to maximize race likelihood).
3. Assert exactly one call succeeds and returns a non-nil `doneCh`; assert the other returns an error and that `callbackW2` (or `callbackW1`, whichever lost) received a `jsonrpc.ErrConflict` response via a mock `Callback.SendResponse`.
4. Assert `h.callbacks["R"]` contains `responseAggregators` sourced only from the winning workflow's shard assignment (`workflowMetadataHandler.WorkflowShards(winningWorkflowID)`), not the loser's.
5. Simulate `HandleNodeTriggerResponse` with a `resp.ID = "R"` from a node belonging to the shared shard and assert the payload is only ever delivered to the winning callback, never split/leaked to the losing party — and separately assert that the losing party's own legitimate `sendWithRetries` path is never invoked (proving their request was dropped, not merely delayed).

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
