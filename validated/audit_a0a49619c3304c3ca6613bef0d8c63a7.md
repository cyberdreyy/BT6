### Title
Post-default instant withdraw requests bypass the post-default receipt path and either steal the recovery reserve or freeze user funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` mixes post-default requests into the same aggregate `instantWithdrawsRequests[_user]` / `instantWithdrawsRequestsByEpoch[_user][epochNumber]` buckets used for pre-default (defaulted-epoch) receipts. Unlike `requestWithdraw`, which routes post-default requests to `postDefaultRequests`, instant requests share one counter for two different claim classes. This is the same bug class as the reported Liquorice issue: a single accounting value is consumed by two different settlement paths (`_claimDefaultedInstantWithdrawRequest` and the funded path in `claimInstantWithdrawRequest`), and the result breaks when the two classes disagree.

### Finding Description
`requestWithdraw` explicitly branches on `defaultRecoveryFinalized` and stores post-default receipts in `postDefaultRequests`, paid 1:1 from `defaultRecoveryReserve` via `_claimPostDefaultWithdrawRequest` [1](#0-0) [2](#0-1) . `requestInstantWithdraw` has no such branch: after `_ensureDefaultRecoveryInitialized` it unconditionally mints a receipt and adds the amount to `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws` [3](#0-2) .

On claim, `claimInstantWithdrawRequest` only routes through `_claimDefaultedInstantWithdrawRequest` when `defaultInstantWithdrawsFinalized` is set, then pays the whole remaining `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim` [4](#0-3) . Two breakages follow:

1. **Same-epoch pollution of the defaulted bucket.** `epochNumber` is unchanged by default finalization (it only increments in `deposit` during a running epoch and at `stopEpoch` paths) [5](#0-4) . If operations are restored in the same epoch, a new instant request lands in `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, so `_claimDefaultedInstantWithdrawRequest` treats it as defaulted-epoch basis: it pays `claimBasis * defaultRecoveryPrice` from the reserve and clamps `pendingInstantWithdraws` to zero [6](#0-5) . A post-default, already-haircut request is haircut a second time and corrupts the unfunded-instant counter.

2. **New-epoch requests paid at par from non-existent funded balance.** If `epochNumber` has advanced, the post-default instant receipt is claimed through `_transferFundedClaim`, which reverts whenever `balance - defaultRecoveryReserve < amount` [7](#0-6) . Post-default the strategy balance is essentially the recovery reserve, so the claim permanently reverts — the user's tranche tokens were burned at request time and the receipt can never be paid. Where the CDO's epoch machinery does fund it via `collectInstantWithdrawFunds`, the receipt is paid at par of a haircut amount while `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` were already consumed by default accounting, draining funds earmarked for other claimants.

### Impact Explanation
An unprivileged KYC-passed lender can trigger instant withdrawals post-default whenever `allowInstantWithdraw` and the APR-drop condition hold (honest manager lowers APR after default). The impact is permanent freezing of the user's principal (tranche tokens burned, claim always reverts) or misallocation of the default recovery reserve — i.e., direct theft of unclaimed recovery owed to defaulted-epoch claimants, quantified as the post-default instant request amount.

### Likelihood Explanation
Requires a default-then-restore sequence and instant withdrawals enabled, both supported modes. The missing `defaultRecoveryFinalized` branch is a clear asymmetry versus `requestWithdraw`, indicating the post-default path was simply not handled for instant receipts.

### Recommendation
In `requestInstantWithdraw`, mirror `requestWithdraw`: when `defaultRecoveryFinalized`, require no outstanding requests, burn CDO tokens and mint the haircut receipt into a dedicated post-default instant bucket (or reuse `postDefaultRequests`), never touching `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`. In `claimInstantWithdrawRequest`, route post-default receipts to `_transferDefaultRecovery` at par rather than the aggregate funded path.

### Proof of Concept
Foundry fork outline (modeled on `test/foundry/IdleCreditVault.t.sol`):

1. Deploy `IdleCDOEpochVariant` + `IdleCreditVault` with instant withdraws enabled; deposit AA/BB.
2. Run an epoch, let the borrower default; call `finalizeDefault`/`finalizeDefaultRecovery` so `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized` are set and `defaultRecoveryReserve > 0`.
3. Restore operations / let a new request occur while `epochNumber == defaultRecoveryEpoch` (or after increment), with APR dropped so `_isInstantWithdrawEnabled()` passes.
4. Attacker calls `cdoEpoch.requestWithdraw(amount, tranche)`, which enters `creditVault.requestInstantWithdraw` — the receipt lands in `instantWithdrawsRequestsByEpoch[attacker][epochNumber]`.
5. Call `cdoEpoch.claimInstantWithdrawRequest()`:
   - Same-epoch case: `_claimDefaultedInstantWithdrawRequest` pays `amount * defaultRecoveryPrice` (double haircut) and zeroes `pendingInstantWithdraws`, corrupting unfunded-instant accounting.
   - Later-epoch case: `_transferFundedClaim` reverts because `balance - reserve < amount`; assert `vm.expectRevert(NotAllowed.selector)` while the attacker's tranche tokens are already burned — funds permanently frozen.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
