### Title
Exited/swept Gloas builders can be silently reactivated by anyone via a builder deposit request - (File: specs/gloas/beacon-chain.md)

### Summary
`process_builder_deposit_request` in `specs/gloas/beacon-chain.md` explicitly documents that "Exited builders cannot be reactivated," yet the function's own logic reactivates an exited-and-swept builder whenever *any* deposit request references its existing pubkey, with no signature check and no involvement of the builder's own authority.

### Finding Description
When a builder deposit request's pubkey already exists in `state.builders`, the function skips signature verification entirely (`is_valid_builder_deposit_signature` is only checked in the *new*-pubkey branch) and unconditionally executes: [1](#0-0) 

If the builder had exited and been swept (`builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0`), the code resets `builder.withdrawable_epoch` to a future epoch and adds the deposited amount to `builder.balance`, i.e. it undoes the "exited" state and restores a live, funded builder entry. This is a permissionless EL-originated deposit request; nothing ties it to proof of ownership of the builder key beyond the withdrawal-credential prefix check, so any party who knows the exited builder's pubkey can trigger this. This directly contradicts the surrounding spec prose: "Exited builders cannot be reactivated, although a newly registered builder's public key may have previously appeared in the builder set." [2](#0-1) 

The `add_builder_to_registry`/`get_index_for_new_builder` path reuses a builder-slot index only once `withdrawable_epoch <= current_epoch and balance == 0`, i.e. it is designed around the assumption that an exited-and-swept builder slot is permanently dead until reused for a *different* pubkey: [3](#0-2) 

That invariant is broken because a same-pubkey deposit in the `else` branch bypasses `get_index_for_new_builder` and mutates the existing (supposedly dead) `Builder` record in place, restoring both balance and a live withdrawable epoch.

### Impact Explanation
This breaks the equality that a builder's exited/removed status should only change through actions authorized by that builder (analogous to the reported "Disabled Adapters Should Stay Disabled" issue, where anyone could re-enable a disabled entity). Here, an exited builder—whose registration and payment eligibility was supposed to be permanently terminated—can be re-credentialed/reactivated into an active, funded builder state by an unauthorized third party simply submitting an execution-layer deposit request against the old pubkey. This matches the High-impact category "a validator or builder exited, consolidated or re-credentialed without its authority."

### Likelihood Explanation
The pubkey of an exited builder is public (it was previously registered on-chain), and builder deposit requests are permissionless execution-layer requests processed by `process_operations`/`process_builder_deposit_request` with no additional authorization for top-ups to existing pubkeys. Any party can construct such a request, making this trivially reachable whenever a builder has exited and been swept.

### Recommendation
In `process_builder_deposit_request`, do not allow deposits to top up a builder whose `withdrawable_epoch != FAR_FUTURE_EPOCH` (i.e., one that has exited/been swept). Such deposits should be routed to a full-withdrawal/refund path (as the surrounding comment intends: "Any deposit sent to an exited builder will be withdrawn to the builder's execution address") rather than reinstating the builder's balance and withdrawable epoch in place.

### Proof of Concept
1. Builder `B` with pubkey `pk` is active with nonzero balance.
2. `B` exits via `process_builder_exit_request` → `initiate_builder_exit` sets a finite `withdrawable_epoch`. [4](#0-3) 
3. After the withdrawal sweep, `state.builders[idx].balance == 0` and `withdrawable_epoch != FAR_FUTURE_EPOCH`.
4. Any actor submits a `BuilderDepositRequest` with `pubkey == pk` (no signature required since `pk` is already in `builder_pubkeys`).
5. `process_builder_deposit_request` takes the `else` branch, sets `builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY` and `builder.balance += amount`, fully reviving the exited builder without any action or consent from `B`'s original owner.

def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))

###### New `process_builder_exit_request`

```python
def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
