### Title
Mid-epoch `setTrancheAPRSplitRatio` update retroactively re-prices already-accrued epoch yield between AA and BB tranches - (File: contracts/IdleCDO.sol)

### Summary
The vesting bug class is "a privileged config update applies retroactively, re-locking or re-pricing entitlements users already accrued." The direct analog is `setTrancheAPRSplitRatio` in `IdleCDO.sol` (lines 899–903): it is guarded only by `_checkOnlyOwner()` and a bounds check, with no epoch-phase gating, and `trancheAPRSplitRatio` is read at accounting/withdraw time via `_calcTrancheInterestShare` (IdleCDOEpochVariant.sol line 884), so the ratio in effect when `stopEpoch`/`_updateAccounting` runs is applied to the gain accrued over the *entire* elapsed epoch — including the period that accrued under the old ratio.

Notably, the codebase already recognized this exact retroactivity hazard for `managementFee`: `setManagementFee` checkpoints accrued fees at the old rate before applying the new one (covered by `testSetManagementFeeCheckpointsBeforeRateChange`, test/foundry/IdleCreditVault.t.sol:1043). No equivalent checkpointing exists for `trancheAPRSplitRatio`.

### Finding Description
1. An epoch is running (`isEpochRunning == true`, `paused() == true`, `allowAAWithdrawRequest == false`). AA and BB holders are locked in; they cannot deposit, request withdrawals, or exit.
2. Yield accrues on the live NAV over time and is split between `lastNAVAA`/`lastNAVBB` only when `_updateAccounting()` runs, using the *current* `trancheAPRSplitRatio` (via `_calcTrancheInterestShare`).
3. The owner calls `setTrancheAPRSplitRatio(X)` mid-epoch. There is no `isEpochRunning`/`paused()` guard — unlike `setEpochParams` (line 122: blocked while `isEpochRunning`) and `setInstantWithdrawParams` (line 133: blocked while `paused()`), this setter is usable in exactly the phase where users are locked.
4. At `stopEpoch`, `_updateAccounting` splits the whole epoch's accrued gain using `X`, retroactively re-assigning interest that economically accrued under the old ratio.

The mirror image of the vesting report: vested yield becomes "unvested" (reassigned to the other tranche class) because the new config is applied retroactively to elapsed time. Setting `trancheAPRSplitRatio = FULL_ALLOC` (or toggling `isAYSActive`, which has the same effect) mid-epoch moves the BB share of the elapsed-period gain to AA.

### Impact Explanation
Quantified loss for the disadvantaged tranche class equals `(newRatio − oldRatio applied to their share) × accrued epoch gain`. Example: with a 10% epoch gain and the AA split moved from 50% to 100% at day 25 of a 30-day epoch, BB holders lose the entire epoch gain that accrued over 25 days under the 50% expectation — not just the remaining 5 days. Victims cannot react because withdrawals are disabled during the epoch, combining yield theft with the locked-in window. This matches the accepted impact categories (theft of unclaimed yield during a mandatory lock).

### Likelihood Explanation
Like the source report, this is not a malicious-owner scenario — it triggers whenever the owner/manager legitimately retunes the split ratio (a documented governance knob, also exercised in tests mid-epoch) while an epoch is live. Since epochs routinely run for weeks, any ratio rebalancing during a live epoch silently reprices elapsed yield. Asymmetry with the checkpointed `managementFee` setter suggests this was an oversight rather than an intended retroactive power.

### Recommendation
Gate `setTrancheAPRSplitRatio` (and `setIsAYSActive`) behind `!isEpochRunning`, mirroring `setEpochParams`, or checkpoint accrued interest at the old ratio (call `_updateAccounting()` at the current ratio before storing the new one) exactly as `setManagementFee` does for fees.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol harness
function testMidEpochSplitRatioRepricesAccruedYield() external {
    // AA and BB holders deposit during buffer
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _depositBBWithUser(bbUser, amount);

    // AA split starts at 50%
    vm.prank(owner);
    idleCDO.setTrancheAPRSplitRatio(50_000);

    _startEpochAndCheckPrices(0);
    uint256 navBBStart = idleCDO.lastNAVBB();

    // 25 of 30 days elapse; gain accrues under 50% terms
    vm.warp(block.timestamp + 25 days);

    // Honest owner retunes the ratio mid-epoch: all yield to AA
    vm.prank(owner);
    idleCDO.setTrancheAPRSplitRatio(FULL_ALLOC);

    // stop epoch with realized interest
    uint256 expectedInterest = cdoEpoch.expectedEpochInterest();
    deal(defaultUnderlying, borrower, expectedInterest);
    vm.warp(cdoEpoch.epochEndDate());
    vm.prank(manager);
    cdoEpoch.stopEpoch(10e18, 0);

    // BB receives ~0% of the ENTIRE epoch gain, not just the last 5 days
    uint256 bbGain = idleCDO.lastNAVBB() - navBBStart;
    // Under correct accrual BB should get ~ (50% * 25/30 + 0% * 5/30) of gain
    assertLt(bbGain, expectedInterestAfterFees * 25 days / 30 days / 2);
}
```
Run on a mainnet fork with the existing `IdleCreditVault.t.sol` fixture (AA+BB deposits, `startEpoch`, warp, `stopEpoch` with funded borrower interest).
