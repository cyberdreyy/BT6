### Title
Merkle secret-index truncation mismatch lets an unprivileged taker permanently poison `lastValidated` and block all future partial fills of an order - (File: `contracts/MerkleStorageInvalidator.sol`)

### Summary
`MerkleStorageInvalidator.takerInteraction` verifies the Merkle proof using only the low 64 bits of the attacker-supplied `idx` (`uint64(takerData.idx)`), but persists the **full, untruncated** `idx` value into `lastValidated[key].index`. An unprivileged taker filling a multiple-fills order can supply `idx = realIdx + k·2^64` for any real, valid `realIdx`/secret pair — the proof still verifies because only the low 64 bits are hashed — while storing an astronomically large `index` in storage. This is the on-chain analog of the Zetaclient bug: an unprivileged party can push in a crafted-but-locally-"valid" value that corrupts a monotonically-tracked progression counter, and no future action can move that counter back into a valid range, permanently blocking subsequent processing.

`takerData.idx` is declared as a full `uint256` in `IMerkleStorageInvalidator.TakerData`: [2](#0-1) 

The proof-verification hash truncates `idx` to `uint64` (matching the off-chain Merkle-tree construction convention, e.g. `keccak256(abi.encodePacked(i, hashedSecrets[i]))` with `i` as `uint64` in the test suite), but the value written to `lastValidated` uses the **original, untruncated** `takerData.idx`. Any address that is currently allowed to take the order (any address can act as taker once the order enters the public/permissionless fill phase of the Fusion flow) can:

1. Take a genuinely valid `(realIdx, secretHash)` pair with a valid Merkle proof for `realIdx < partsAmount`.
2. Submit `idx = realIdx + 2^64` (or any multiple of `2^64` plus `realIdx`) instead of `realIdx` in the `takerInteraction` calldata (`abi.encode(proof, idx, secretHash)`), while keeping the same `proof` and `secretHash`.
3. Because `uint64(takerData.idx) == realIdx`, `rootCalculated` still matches `rootShortened`, so `InvalidProof` is not triggered.
4. `lastValidated[key]` is now set to `ValidationData(realIdx + 2^64 + 1, secretHash)` — an index value that can never legitimately occur again for that order.

This corrupted `index` is consumed directly by `BaseEscrowFactory._postInteraction` -> `_isValidPartialFill`: [3](#0-2) [4](#0-3) 

`_isValidPartialFill` requires `calculatedIndex + 1 == validatedIndex` (or `+2` for the final fill), where `calculatedIndex` is bounded by `partsAmount` (a small number, e.g. up to a few hundred). Once `validated.index` has been poisoned to `~2^64`, this equality can never hold for any realistic `partsAmount`, so **every subsequent `_postInteraction` call for that order permanently reverts with `InvalidPartialFill`**, regardless of which resolver/taker attempts to fill the remainder.

### Impact Explanation
This permanently blocks all further partial fills of the affected multi-fill order: the maker's remaining `makingAmount` can never be escrowed/filled again through this mechanism, and any resolver's attempt to complete the cross-chain swap for the unfilled remainder will revert indefinitely (the `lastValidated.index` value only ever gets overwritten by another successful `takerInteraction`, but a subsequent legitimate proof for the real next `realIdx` will fail the same `_isValidPartialFill` check because it can never equal the poisoned huge index, and it can't be "de-poisoned" back down). This matches the Medium-severity bounty class ("smart contract unable to operate because required state can be broken by an unprivileged actor") and, for orders where a resolver has already begun expecting subsequent fills (partial fills already escrowed and safety deposits pre-funded to their pre-computed CREATE2 address), also causes temporary freezing of the resolver's committed safety deposit/allowance for the blocked deterministic escrow address that can never be triggered via the intended path.

### Likelihood Explanation
The action requires only calling `fillOrderArgs` on the Limit Order Protocol as taker with crafted `extraData` for a multi-fill order (`allowMultipleFills` set) — this is a normal, permissionless interaction path once the order is open to public fillers, requiring no privileged role, no admin/owner rights, and no cryptographic break (the attacker reuses a legitimate proof/secret pair and only manipulates the redundant high bits of `idx`). It is a one-shot, deterministic, low-cost transaction.

### Recommendation
Truncate `idx` consistently before both proof verification and storage, or reject any `idx` whose value exceeds `type(uint64).max` (or the valid `partsAmount` bound) before storing it:

```solidity
if (takerData.idx > type(uint64).max) revert InvalidProof();
...
lastValidated[key] = ValidationData(uint64(takerData.idx) + 1, takerData.secretHash);
```

Alternatively, use the same truncated/typed value for both the proof hash and the stored `ValidationData.index` so they can never diverge.

### Proof of Concept
1. Deploy an order with `allowMultipleFills` and `partsAmount = N`, with `hashedPairs[i] = keccak256(abi.encodePacked(uint64(i), hashedSecrets[i]))` for `i` in `[0, N]`, as built by `test/unit/MerkleStorageInvalidator.t.sol`.
2. Take a genuinely valid `realIdx` (e.g. `0`) with its correct Merkle `proof` and `hashedSecrets[0]`.
3. Call `fillOrderArgs` with `interaction = abi.encode(proof, realIdx + 2**64, hashedSecrets[0])` instead of `abi.encode(proof, realIdx, hashedSecrets[0])`.
4. Observe that `takerInteraction` succeeds (no `InvalidProof` revert) because `uint64(realIdx + 2**64) == realIdx`, but `lastValidated[key].index` is now `realIdx + 2**64 + 1`.
5. Attempt any subsequent legitimate fill of the same order (any `idx`), and observe `_isValidPartialFill` in `BaseEscrowFactory._postInteraction` always reverts with `InvalidPartialFill`, since `calculatedIndex + 1`/`+2` can never equal `realIdx + 2**64 + 1` for any realistic `partsAmount`.

    function _isValidPartialFill(
        uint256 makingAmount,
        uint256 remainingMakingAmount,
        uint256 orderMakingAmount,
        uint256 partsAmount,
        uint256 validatedIndex
    ) internal pure returns (bool) {
        uint256 calculatedIndex = (orderMakingAmount - remainingMakingAmount + makingAmount - 1) * partsAmount / orderMakingAmount;

        if (remainingMakingAmount == makingAmount) {
            // If the order is filled to completion, a secret with index i + 1 must be used
            // where i is the index of the secret for the last part.
            return (calculatedIndex + 2 == validatedIndex);
        } else if (orderMakingAmount != remainingMakingAmount) {
            // Calculate the previous fill index only if this is not the first fill.
            uint256 prevCalculatedIndex = (orderMakingAmount - remainingMakingAmount - 1) * partsAmount / orderMakingAmount;
            if (calculatedIndex == prevCalculatedIndex) return false;
        }

        return calculatedIndex + 1 == validatedIndex;
    }
