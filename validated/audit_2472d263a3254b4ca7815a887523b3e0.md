## Title
Multisig confirmations from removed members/keys remain counted toward the approval threshold, allowing requests to execute below the true live-member quorum - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` only checks that the *current caller* is a live member before tallying confirmations toward `num_confirmations`; it never re-validates that the confirmations already stored in a request's `HashSet` still belong to current members. When a member (or access key) is removed via `DeleteMember`/`DeleteKey`, the cleanup logic only purges requests that member *originated*, not confirmations they cast on requests submitted by someone else. A stale confirmation from an already-removed member therefore still counts toward reaching the quorum, letting a request execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` does the threshold check purely against the size of the stored `confirmations: LookupMap<RequestId, HashSet<String>>` set: [1](#0-0) 

The set is populated by `member.to_string()` at confirmation time and is never re-validated against the current `members: UnorderedSet<MultisigMember>` — the only membership check performed is on the *new* confirmer via `current_member()` inside `assert_valid_request`: [2](#0-1) 

When a member is removed, `delete_member` purges only requests that member *submitted* (`r.member == member`), and clears confirmations solely for those requests: [3](#0-2) 

It never scans other requests' `confirmations` sets to strip out the removed member's entry. So if that member had previously *confirmed* (but not submitted) some other pending request, their stale approval string remains in that request's `HashSet` and still counts toward `confirmations.len() as u32 + 1 >= self.num_confirmations` on a later `confirm()` call.

The same structural gap exists in the v1 contract: `DeleteKey` only removes requests where `r.signer_pk == pk` (the key's own submissions), leaving that key's confirmations on other requests intact: [4](#0-3) [5](#0-4) 

This is the same bug class as the external report's `SessionData` example: a stored value (`sd.sessionKey` / `confirmations`) is trusted without re-checking it is still bound to an authorized identity (the correct `sessionKeySigner`/wallet or, here, a still-current member) at consumption time.

**Binding broken:** `confirmations counted == live members who approved`. After a member's removal, this repository allows `confirmations counted (including departed member) >= num_confirmations` while `live members who approved < num_confirmations`.

### Impact Explanation
This is Critical per the scope rubric: "a multisig request executed below threshold." The multisig contract typically holds and controls the account's own NEAR balance and full-access keys (`Transfer`, `AddKey`, `FunctionCall`, `DeployContract` actions execute directly against `env::current_account_id()`'s funds and permissions). Executing a `Transfer`/`AddKey`/`DeployContract` request with fewer live approvals than `num_confirmations` mandates means funds can be moved, or control can be seized, without the intended quorum of currently-authorized members — a governance/custody bypass with direct NEAR loss potential.

### Likelihood Explanation
The exploit path requires only ordinary multisig operations that are already expected in production: a request pending confirmation, a member confirming it (not submitting it), and a later `DeleteMember`/`DeleteKey` governance action removing that member — a routine occurrence in any multisig lifecycle (e.g., key rotation, offboarding). No privileged bug or malicious deployment is needed; the flaw is triggered by the contract's own designed member-removal flow interacting with any request left pending across that removal.

### Recommendation
When tallying/using confirmations in `confirm()`, filter the stored confirmation set to only those entries whose corresponding `MultisigMember` (or public key, in v1) is still present in `self.members` (or still an access key on chain) before comparing against `num_confirmations`. Alternatively, on `DeleteMember`/`DeleteKey`, iterate over *all* pending requests' confirmation sets (not just requests the member submitted) and strip the removed member's entry, e.g.:
```rust
for (request_id, mut confirmations) in self.confirmations.iter() {
    if confirmations.remove(&member.to_string()) {
        self.confirmations.insert(&request_id, &confirmations);
    }
}
```

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request(R1)` (e.g., `Transfer { amount }`) — not auto-confirmed.
3. `B` calls `confirm(R1)` → `confirmations[R1] = {B}` (`1 < 3`, stored, not executed).
4. `C` calls `confirm(R1)` → `confirmations[R1] = {B, C}` (`2 < 3`, stored, not executed).
5. Separately, members legitimately pass a `DeleteMember { member: C }` request (reaching quorum with `A, B, D`), removing `C` from `self.members`. `delete_member` only removes requests `C` *submitted*; `R1` (submitted by `A`) is untouched, so `confirmations[R1]` still contains `C`.
6. `D` calls `confirm(R1)`: `current_member()` succeeds (`D` is live). `confirmations[R1].len() == 2`, `+1 == 3 >= num_confirmations`, so `execute_request(R1)` fires — even though only `B` and `D` are the live members who actually approved; `C`'s stale confirmation from before removal filled the third slot.
7. Result: the transfer executes with only 2 of 3 required *live* member approvals, breaking the intended custody threshold. [6](#0-5) [7](#0-6)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

        }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
