### Title
Stale confirmations from removed multisig members are not purged and still count toward the execution threshold, allowing requests to execute below the live-member quorum - (File: `multisig2/src/lib.rs`)

### Summary
The bug-class hint from the report ("recorded state not fully synchronized after a state-changing operation") maps directly onto the multisig contracts' member-removal flow. When a member is deleted via `DeleteMember` (or `DeleteKey` in the v1 `multisig` contract), the contract only purges requests *owned* by that member — it does not purge that member's confirmations recorded on *other* still-pending requests. Those stale confirmations remain in the `confirmations` map and are still counted by `confirm()` toward `num_confirmations`, so a request can later execute with fewer live-member approvals than the configured threshold.

### Finding Description
`delete_member` in `multisig2/src/lib.rs` only cleans up requests created by the removed member: [1](#0-0) 

```
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
``` [1](#0-0) 

The filter is `r.member == member` — i.e. it only removes requests where the *removed member is the original requester*. If the removed member had already confirmed a *different* request (created by someone else), that confirmation entry is never scrubbed from `self.confirmations`.

`confirm()` then counts confirmations purely by size, without checking whether each entry is still a current member: [2](#0-1) 

```
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let member = self.current_member()...;
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert(!confirmations.contains(&member.to_string()), ...);
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else { ... }
}
``` [2](#0-1) 

This breaks the equality that should hold: `confirmations counted == confirmations from currently active members`. Instead, `confirmations counted ⊇ {live confirmations} ∪ {stale confirmations from removed members}`.

The same root cause exists in the legacy `multisig` (v1) contract, where `DeleteKey` only removes requests whose `signer_pk == pk` and leaves that key's confirmations on other requests intact: [3](#0-2) 

### Impact Explanation
This is a Critical-impact finding under "a multisig request executed below threshold." A pending high-value request (e.g. a `Transfer` moving the multisig account's NEAR, or an `AddKey`/`AddMember` granting new full control) can be executed with fewer approvals from *currently authorized* members than `num_confirmations` requires, because a stale confirmation from an already-removed member is still counted. This effectively lowers the live quorum required to move funds or add malicious keys/members, defeating the entire purpose of the M-of-N scheme.

### Likelihood Explanation
This does not require any redeploy, victim key compromise, or social engineering. It arises from the contract's normal, documented lifecycle: members regularly rotate (delete old members, add new ones) while other requests remain pending, which is an expected and even encouraged operational pattern (per the contract's own request/confirmation state machine). Any current member can time an `AddMember`/`DeleteMember` execution to leave a stale confirmation on a pending request, then get the remaining live members to push it over threshold.

### Recommendation
When removing a member (or key), scrub the removed member's confirmation entry from every request's `confirmations` set, not just requests they authored. Alternatively (and more robustly), have `confirm()` re-validate that all currently recorded confirmers in a request's confirmation set are still members of `self.members` before counting them toward the threshold (e.g., filter `confirmations` against `self.members` on every read/count), so removed members' approvals never count. Apply the same fix to `DeleteKey` handling in the legacy `multisig` contract.

### Proof of Concept
Setup: multisig2 contract with members `{A, B, C, D}`, `num_confirmations = 3`.

1. `B` calls `add_request_and_confirm(R1 = Transfer{...})` → `confirmations[R1] = {B}`.
2. `A` calls `confirm(R1)` → `confirmations[R1] = {B, A}` (2/3, not yet executed).
3. `C` creates `R2 = DeleteMember{A}` and confirms; `B`, `D` also confirm R2 to reach 3/3 → `R2` executes: `A` is removed from `self.members`. `delete_member` scans requests with `r.member == A` — `R1` was created by `B`, so it is untouched; `confirmations[R1]` still contains stale `A`.
4. Remaining members are `{B, C, D}` (3 members, satisfying `members.len()-1 >= num_confirmations`).
5. `C` calls `confirm(R1)` → `confirmations[R1].len() (2: B,A) + 1 = 3 >= num_confirmations (3)` → `R1` (the `Transfer`) executes.

Result: the transfer executed with only **2 genuinely live approvals (`B`, `C`)** out of 3 required, because the stale confirmation from removed member `A` was still counted — the multisig request executed below the live-member threshold.

        );

            let request = self.remove_request(request_id);

            confirmations.insert(member.to_string());
