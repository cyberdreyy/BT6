### Title
Unbounded iteration over the full `vote_accounts` collection in `getVoteAccounts` allows single-call DoS via unprivileged vote-account creation - ([File: rpc/src/rpc.rs])

### Summary
The `getVoteAccounts` RPC handler iterates over the entire in-memory `vote_accounts` collection on every call, decoding vote state for each entry, with no cap on the number of entries processed or returned. Because creating a vote account is an unprivileged operation requiring only the rent-exempt minimum balance (no validator/operator role needed), an attacker can cheaply grow this collection to an arbitrarily large size, after which every subsequent `getVoteAccounts` call becomes proportionally expensive — mirroring the reported `addPool` bug class where a bounded-looking admin action produces an unboundedly growing array that is fully scanned by unrelated, frequently-called functionality.

### Finding Description
`JsonRpcRequestProcessor::get_vote_accounts` retrieves `bank.vote_accounts()` and then iterates and `filter_map`s over *every* entry to build the `current`/`delinquent` response lists, decoding the `vote_state_view` (including epoch credits) for each one: [1](#0-0) 

There is no pagination, no byte/entry limit, and no early-exit — every vote account in the bank's `vote_accounts` map is visited and decoded on each call, unlike `getProgramAccounts`/token-account scans which enforce `byte_limit_for_scan` (`scan_results_limit_bytes`) via `accumulate_and_check_scan_result_size`/`maybe_abort_scan`: [2](#0-1) 

Crucially, `getVoteAccounts` is part of `rpc_minimal`, i.e., it is always available (does not require the accounts-scan feature) and is even relied upon by `agave-validator wait-for-restart-window`: [3](#0-2) 

Creating a vote account only requires signing with the vote account keypair and the "node" keypair, and funding it with the rent-exempt minimum for `VoteStateV4` (a few hundredths of a SOL) — this is not an admin/validator-privileged action; any unprivileged wallet holder can create as many vote accounts as they can afford: [4](#0-3) [5](#0-4) 

This is directly analogous to the `addPool` bug class: a low-privilege, repeatable, individually-cheap action (`InitializeAccount` on the vote program) appends unboundedly to a global collection (`vote_accounts`) that is later iterated in full by an unrelated, frequently invoked, single-call operation (`getVoteAccounts`), with no limit analogous to the recommended pool cap.

### Impact Explanation
Once enough vote accounts are created, every `getVoteAccounts` call (used by wallets, CLI tooling, staking dashboards, and validator restart tooling) must decode and filter the entire, attacker-inflated vote-accounts set on the calling thread, degrading RPC responsiveness for this and potentially other RPC calls sharing the same runtime pool. Because the endpoint is part of `rpc_minimal` and has no opt-out/limit configuration, this cannot be mitigated by node operators via existing scan-limit config (`scan_results_limit_bytes`), which only applies to accounts-scan/secondary-index paths.

### Likelihood Explanation
Low-to-medium: the cost to the attacker is the rent-exempt minimum balance per vote account (bounded, non-recoverable while the account exists), and any wallet can perform the `InitializeAccount` vote instruction without needing validator identity, stake, or any special role — making the "many cheap calls by an unprivileged actor" precondition realistic, similar in spirit but requiring capital investment scaling with the number of dummy vote accounts created.

### Recommendation
Bound the cost of `get_vote_accounts` similar to other accounts-scan RPC paths: e.g., enforce a maximum number of vote accounts iterated/returned per call, add pagination, or apply a byte/entry limit analogous to `scan_results_limit_bytes`/`accumulate_and_check_scan_result_size` used in the account-scan code paths.

### Proof of Concept
1. Using any funded unprivileged keypair, repeatedly submit `VoteInstruction::InitializeAccount` transactions (via `vote_instruction::create_account_with_config`) to create a large number (e.g., tens of thousands) of vote accounts, each funded only with the rent-exempt minimum for `VoteStateV4`.
2. Call the `getVoteAccounts` JSON-RPC method.
3. Observe that `JsonRpcRequestProcessor::get_vote_accounts` (`rpc/src/rpc.rs:1155-1246`) must iterate and decode the vote state view of every created vote account on this single call, with processing time growing linearly with the number of vote accounts created, and no limit preventing this cost.
