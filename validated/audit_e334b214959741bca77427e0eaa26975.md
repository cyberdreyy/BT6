### Title
Multi-epoch withdraw receipts escape `stopEpochWithDuration` loss haircut — later claims paid at par drain the loss-adjusted funding pool - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Rizin bug class — an attacker-influenced write landing outside the bounds that later readers check — maps onto `IdleCreditVault`'s per-epoch withdraw accounting. `requestWithdraw` writes the receipt into `withdrawsRequestsByEpoch[user][epochNumber]` and stores only a *single* marker `lastWithdrawRequest[user]`. When a user has receipts in two different epochs and the second epoch ends with a loss (`collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]`), the loss-claim path only clears the epoch pointed to by `lastWithdrawRequest`. The earlier-epoch receipt — whose basis was nevertheless included in `pendingBasis` when the haircut was computed — survives in the aggregate `withdrawsRequests[user]` and is later paid **at par** through `_claimFundedWithdrawRequest`.

### Finding Description
- `requestWithdraw` accumulates `pendingWithdraws` and `withdrawsRequestsByEpoch[user][currentEpoch]`, and overwrites `lastWithdrawRequest[user] = currentEpoch` (lines 277–294).
- `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * 1e18 / pendingBasis` where `pendingBasis` is the **aggregate** of *all* pending receipts, including older-epoch ones, and records it under the current `epochNumber` (lines 411–430).
- `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` and `_clearWithdrawClaimForEpoch` only zeroes `withdrawsRequestsByEpoch[user][lossEpoch]`, decrementing `withdrawsRequests[user]` by that epoch's piece (lines 789–837). It then resets `lastWithdrawRequest[user] = 0`.
- Afterwards `claimWithdrawRequest` falls into `_claimFundedWithdrawRequest`, whose gate `epochNumber <= lastWithdrawRequest[user]` now passes trivially (`lastWithdrawRequest == 0`), paying the remaining `withdrawsRequests[user]` (the older-epoch receipt) **at full value** (lines 319–350).

The anti-overwrite guard in `requestWithdraw` (lines 261–271) does not stop this: at the time the second request is made, `lossRecoveryPriceByEpoch` for the first epoch is still 0, because the loss is only recorded later at `stopEpoch`/`collectWithdrawFunds`. The broken invariant is "one receipt, one (haircut-adjusted) payout": a subset of the pooled haircut basis is paid without the haircut.

### Impact Explanation
Direct theft / insolvency. Suppose the attacker has pending receipts of 100 in epoch N and 100 in epoch N+1, and other users have 800 pending; `pendingBasis` = 1000. The borrower funds only 500 (50% loss), so `lossRecoveryPriceByEpoch[N+1] = 0.5e18`. The attacker claims: 100 × 0.5 = 50 for epoch N+1 plus 100 at par for epoch N = 150 total from a 500 pool, while an honest user with the same 200 aggregate receives only 100. Every extra wei the attacker extracts above their pro-rata haircut share is directly subtracted from what other pending withdrawers and the default-recovery reserve can pay; with a sufficiently large attacker share of `pendingBasis` this makes the strategy unable to fund remaining funded claims — permanent loss for honest lenders.

### Likelihood Explanation
Requirements are all unprivileged and reachable in normal operation:
- Attacker only needs to be a KYC'd tranche holder calling `requestWithdraw` in two distinct epochs before claiming (the code explicitly supports deferring claims across epochs; `withdrawsRequestsByEpoch` exists precisely for that).
- A lossy `stopEpochWithDuration`/`collectWithdrawFunds(_amount < pendingBasis)` is an honest manager/borrower action, not attacker-controlled privilege.
- No existing guard covers it: the re-request guard only fires when the *prior* epoch already has a stored loss price; `_claimLossAdjustedWithdrawRequest` by design only reads `lastWithdrawRequest`; `_transferFundedClaim` deliberately excludes the reserve and pays par.

Likelihood is moderate-to-high: it requires a realized stop-epoch loss while the attacker happens to straddle two request epochs, which an attacker can cheaply arrange by splitting withdrawals across every epoch boundary.

### Recommendation
In `requestWithdraw`, block (or auto-claim) when the user has *any* outstanding receipt, not only when `lastWithdrawRequest`'s epoch carries a loss price — e.g. `if (withdrawsRequests[_user] != 0 || apr0 principal/settled != 0) revert` or force `claimWithdrawRequest` semantics first. Alternatively, store a per-user list of request epochs and have `_claimLossAdjustedWithdrawRequest` apply the haircut to **all** receipts whose basis was inside `pendingBasis` at loss time, not just `lastWithdrawRequest`. A cheaper mitigation: when recording `lossRecoveryPriceByEpoch`, also iterate is impossible on-chain, so prefer tracking `pendingEpochRange`/bitmap or requiring claims to be fully settled before a new `requestWithdraw` is accepted.

### Proof of Concept
Foundry sketch against the existing `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
function testLossHaircutEscapeAcrossEpochs() external {
    // APR != 0 mode, default fee params
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    _depositWithUser(victim,   800_000 * ONE_SCALE, true);

    _startEpochAndCheckPrices(0); // epoch running

    // epoch N request
    vm.prank(attacker);
    uint256 reqA = cdoEpoch.requestWithdraw(100 * ONE_SCALE, address(AAtranche));

    _startEpochAndCheckPrices(1); // roll to next epoch without claiming

    // epoch N+1 request — guard passes, lossRecoveryPriceByEpoch[N] == 0
    vm.prank(attacker);
    uint256 reqB = cdoEpoch.requestWithdraw(100 * ONE_SCALE, address(AAtranche));
    vm.prank(victim);
    cdoEpoch.requestWithdraw(800 * ONE_SCALE, address(AAtranche));

    // Lossy stop: pendingBasis = reqA + reqB + 800; borrower funds only 50%
    IdleCreditVault cv = IdleCreditVault(address(strategy));
    uint256 pending = cv.pendingWithdraws();
    deal(defaultUnderlying, borrower, pending / 2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, /* _lossAmount = */ pending / 2, /*duration*/ 0);

    // Attacker claims: gets reqB * 0.5 + reqA * 1.0
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - pre;
    assertGt(got, (reqA + reqB) / 2, "attacker escaped haircut");

    // Victim (or the pool) is short: remaining funded balance < victim's fair share
    uint256 poolLeft = underlying.balanceOf(address(cv));
    assertLt(poolLeft, pending / 2 - (reqA + reqB) / 2, "pool insolvent vs fair share");
}
```

Expected result: attacker receives `reqA` at par plus `reqB × lossRecoveryPrice`, i.e. strictly more than `pendingAttacker × lossRecoveryPrice`, and the residual strategy balance is insufficient to pay all remaining claimants at the same ratio — demonstrating the haircut-escape theft.
