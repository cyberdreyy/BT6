Based on my investigation, the accounting flows in `staking_contract.move`, `delegation_pool.move`, `vesting.move`, and `pool_u64`/`pool_u64_unbound` all use consistent floor-division (round-down) for share/coin conversions. The specific analog worth flagging is in `update_distribution_pool()`.

### Title
Systematic double round-down in `update_distribution_pool()` lets a staker erode operator commission via repeated small stake-pool value updates - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`update_distribution_pool()` computes unpaid commission and converts it back into shares using two consecutive floor divisions, both of which round in favor of the shareholder (staker) and against the operator, mirroring the M-3 pattern of always rounding a debt-like obligation down instead of up.

### Finding Description
`update_distribution_pool()` is invoked whenever a shareholder's (staker's) portion of a `StakingContract`'s distribution pool changes in value (e.g. on `unlock_stake`, `switch_operator`, `request_commission`, `add_stake` paths that touch `distribution_pool`). For each non-operator shareholder it computes:
```
let unpaid_commission = (current_worth - previous_worth) * commission_percentage / 100;
let shares_to_transfer = pool_u64::amount_to_shares_with_total_coins(distribution_pool, unpaid_commission, updated_total_coins);
``` [1](#0-0) 

Both `unpaid_commission * commission_percentage / 100` and `amount_to_shares_with_total_coins` (which itself calls `math64::mul_div`, a floor division) round down. This double rounding means the operator receives strictly less than their entitled commission on every incremental update, and the residual "dust" is left with the staker's shares in the pool rather than transferred to the operator. The `pool_u64` and `pool_u64_unbound` primitives never round up: `amount_to_shares_with_total_coins` and `shares_to_amount_with_total_coins` both floor via `multiply_then_divide`/`math64::mul_div` [2](#0-1) .

The developer-authored example contract `move-examples/staking/commission.move` explicitly documents this exact class of issue for a similar commission-distribution design: *"In theory this function can be called very often (e.g. once every few seconds) to use rounding errors to 'rob' the operator... mitigated by asserting a min balance before distributing."* [3](#0-2)  Critically, `update_distribution_pool()` in the core framework's `staking_contract.move` has **no equivalent mitigation** (no minimum-delta or minimum-balance gate before triggering the rounding-down commission calc), and it is triggered by staker-controlled actions (`unlock_stake`, `switch_operator`, `add_stake`) rather than only periodic epoch distributions.

### Impact Explanation
Per Sherlock's stake/lockup impact gate, this maps to "operator commission... share-accounting corruption that credits the wrong account or traps value." The staker (unprivileged relative to the operator's commission rights) can, in principle, trigger many small `unlock_stake`/`add_stake` calls that each invoke `update_distribution_pool()`, causing repeated 1-unit-scale under-crediting of the operator's commission shares. Over many iterations this could accumulate into a non-trivial amount of value being retained by the staker instead of transferred to the operator — corrupting the commission-share accounting invariant in the staker's favor.

### Likelihood Explanation
This is rated as low/informational rather than high/critical for two independent reasons I could not rule out with the available code:
1. Every rounding-down step here only ever costs 1 unit (of `u64` coin precision, i.e., 1 octa) per invocation of `update_distribution_pool()`. Extracting meaningful value requires an extremely large number of transactions, each paying real gas, making the attack economically unattractive on mainnet — the existing test suite already documents dust of exactly `1` in comparable `distribute()` scenarios [4](#0-3) .
2. I could not confirm within the available index whether `unlock_stake`/`add_stake` can be called with zero economic cost or unlimited frequency by the staker without altering the stake pool's lockup/epoch state in a way that would throttle this (e.g., minimum stake thresholds, per-epoch limits). This would need verification with a live Devin session and the full `stake.move`/`staking_contract.move` source to build a concrete PoC transaction sequence and quantify actual extractable value.

Given the extremely small per-call magnitude (bounded by 1 octa) and the gas cost required to repeat the action at scale, this does not clearly reach a "high or critical" bar as required by the task's strict criteria, and no exact corrupted-balance root cause beyond bounded floor-rounding could be demonstrated from the indexed code alone.

### Recommendation
If mainnet-relevant, apply ceiling rounding when computing `unpaid_commission` (or when converting it to shares) in `update_distribution_pool()`, analogous to the Notional fix, and/or add a minimum-delta gate (as `commission.move` recommends) before running the commission calculation, to prevent staker-triggered dust-draining via many small triggering transactions.

### Proof of Concept
I was not able to construct a concrete, gas-viable PoC transaction sequence proving material (non-dust) value extraction from the indexed code alone; the mechanism is real (double floor-division favoring the staker) but bounded to ~1 octa per call as shown in the project's own test assertions [5](#0-4) . A background Devin session with full repo/tooling access would be needed to trace `unlock_stake`/`add_stake` call costs and lockup-cycle throttling to determine whether this rises above dust-level impact.

    /// Return the number of new shares `coins_amount` can buy in `self` with a custom total coins number.
    /// `amount` needs to big enough to avoid rounding number.
    public fun amount_to_shares_with_total_coins(self: &Pool, coins_amount: u64, total_coins: u64): u64 {
        // No shares yet so amount is worth the same number of shares.
        if (self.total_coins == 0 || self.total_shares == 0) {
            // Multiply by scaling factor to minimize rounding errors during internal calculations for buy ins/redeems.
            // This can overflow but scaling factor is expected to be chosen carefully so this would not overflow.
            coins_amount * self.scaling_factor
        } else {
            // Shares price = total_coins / total existing shares.
            // New number of shares = new_amount / shares_price = new_amount * existing_shares / total_amount.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(coins_amount, self.total_shares, total_coins)
        }
    }

    /// Return the number of coins `shares` are worth in `self`.
    /// `shares` needs to big enough to avoid rounding number.
    public fun shares_to_amount(self: &Pool, shares: u64): u64 {
        self.shares_to_amount_with_total_coins(shares, self.total_coins)
    }

    /// Return the number of coins `shares` are worth in `self` with a custom total coins number.
    /// `shares` needs to big enough to avoid rounding number.
    public fun shares_to_amount_with_total_coins(self: &Pool, shares: u64, total_coins: u64): u64 {
        // No shares or coins yet so shares are worthless.
        if (self.total_coins == 0 || self.total_shares == 0) {
            0
        } else {
            // Shares price = total_coins / total existing shares.
            // Shares worth = shares * shares price = shares * total_coins / total existing shares.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(shares, total_coins, self.total_shares)
        }
    }

    public fun multiply_then_divide(self: &Pool, x: u64, y: u64, z: u64): u64 {
        math64::mul_div(x, y, z)
    }
