Based on my investigation, I was unable to fully read `lockup/src/lib.rs`'s `new()` function (specifically the `MIN_BALANCE_FOR_STORAGE` check and whether `new()` guards with `assert!(!env::state_exists())`), so some details of the exact panic condition inside the lockup contract remain unverified against the index. However, the core defect is fully demonstrable from `lockup-factory/src/lib.rs` alone, combined with documented NEAR receipt-action execution semantics (actions within a single batched receipt are applied sequentially to state and are **not** rolled back as a group when a later action in the same receipt fails — only the failing action itself aborts, while prior successful actions' state mutations persist).

### Title
Failed `new` call after account creation leaves a funded, uninitializable lockup with unrefundable deposit - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` batches `CreateAccount`, `DeployContract`, `Transfer`, and `FunctionCall("new", ...)` into a single promise, then relies on `on_lockup_create`'s single `is_promise_success()` boolean to decide whether to refund the caller. Because prior actions in a NEAR receipt are not rolled back when a later action in the same receipt fails, a `new` call failure (e.g., triggered by attaching exactly `MIN_ATTACHED_BALANCE`) leaves a real, funded, code-deployed account with no initialized state, while the factory simultaneously believes the whole operation failed and attempts to refund the deposit from its own balance — balance it no longer holds because it was already transferred to the new account in the same original receipt.

### Finding Description
The binding claimed to hold is: `attached_deposit == refunded_to_predecessor OR attached_deposit == usable_lockup_balance`. In other words, every NEAR yoctoNEAR attached via `create()` must end up either (a) inside a working, initialized lockup contract that can cover its own storage, or (b) back in the caller's hands.

The code path:
- `create()` asserts only `attached_deposit >= MIN_ATTACHED_BALANCE` [1](#0-0) , with no check that the resulting `lockup_amount` (computed inside the lockup contract from `env::account_balance()`) leaves enough for the lockup's own storage requirement.
- All four actions — `create_account()`, `deploy_contract()`, `transfer()`, `function_call("new", ...)` — are chained onto a single `Promise` targeting the new lockup account id [2](#0-1) .
- The `.then(ext_self::on_lockup_create(...))` callback checks only `is_promise_success()`, a single aggregate boolean for the whole batch [3](#0-2) .

If an attacker calls `create()` with exactly `MIN_ATTACHED_BALANCE` and crafts arguments (e.g., a `vesting_schedule`/timestamp combination) that cause the lockup's `new()` to panic — because the leftover balance after the storage/`lockup_amount` accounting is insufficient — the `CreateAccount`, `DeployContract`, and `Transfer` actions have already committed to state before the `FunctionCall` action fails. NEAR's per-action execution does not retroactively revert already-applied actions in the same receipt when a subsequent action in that receipt fails. The result is a real on-chain account that: holds the attached NEAR, has the lockup WASM deployed, but has no initialized contract state (since `new()` never completed).

Meanwhile `on_lockup_create` sees `is_promise_success() == false` and unconditionally issues `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` [4](#0-3) , drawing from the **factory's own account balance**. But the factory already forwarded that exact amount to the newly created (now broken) account in the original receipt's `Transfer` action — it has no separate reserve to cover this refund. If the factory holds no surplus balance, this refund transfer itself fails (a decoupled promise failure that is not observed or retried by the contract), so the predecessor is never made whole. The deposit is now stranded inside an account that has deployed code but no valid state, which nobody — not the factory, not the intended owner, not the attacker — can access, since further calls to that account's methods will panic on missing state and there is no code path to reinitialize or drain it.

No existing guard prevents this: `assert_self()` only ensures the callback is invoked by the contract itself; `is_promise_success()` collapses a multi-action batch into one boolean and cannot distinguish "nothing happened" from "partially happened, funds already moved."

### Impact Explanation
NEAR that left the factory account (and, transitively, was attached by the caller) becomes permanently unrecoverable — stuck in an account with deployed bytecode but no usable state and no owner key. This matches the Critical category "funds permanently frozen." The blast radius is any account (attacker's own funds in the minimal PoC, but the same defect fires for any legitimate user whose `create()` call happens to hit the boundary condition) attempting `create()` at or near the deposit floor combined with any parameter set that makes `new()` fail post-account-creation. It is repeatable per lockup account name (deterministic from `owner_account_id`'s hash), so a given `owner_account_id` slot can be permanently poisoned this way, blocking that owner from ever successfully creating their real lockup at that deterministic address.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: any unprivileged account can call `create()` with `attached_deposit == MIN_ATTACHED_BALANCE` and any argument combination that causes the lockup's `new()` to panic post-account-creation (e.g., insufficient leftover balance for `lockup_amount`/storage after the transferred deposit is accounted for). No special privileges, foundation role, or victim key are needed. The only cost to the attacker is the `MIN_ATTACHED_BALANCE` deposit itself (self-inflicted in the minimal PoC) and gas; the mechanism is deterministic and repeatable across distinct `owner_account_id` values.

### Recommendation
Do not batch `CreateAccount + DeployContract + Transfer + FunctionCall("new")` into a single all-or-nothing receipt when the callback's failure-handling assumes atomicity that NEAR does not provide. Either: (1) verify inside `create()`, before attaching the deposit, that `attached_deposit` strictly exceeds the lockup contract's minimum storage/schedule requirements with sufficient margin so `new()` cannot fail for balance reasons; (2) have `on_lockup_create` explicitly check the created account's actual balance/state (e.g., via a follow-up view-style promise) rather than trusting a single aggregate `is_promise_success()`, so it can detect the "account exists but uninitialized" state and issue a `DeleteAccount` (recovering the balance) instead of a doomed refund from the factory's own funds; or (3) keep a dedicated reserve/escrow in the factory sized to always cover refunds independent of funds already forwarded in the same batch.

```rust
// lockup-factory/src/lib.rs tests module (near-sdk testing_env!)
#[test]
fn test_create_lockup_new_call_fails_leaves_stuck_deposit() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker attaches exactly MIN_ATTACHED_BALANCE.
    context.is_view = false;
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = MIN_ATTACHED_BALANCE;
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), LOCKUP_DURATION.into(), None, None, None, None);

    // Simulate the batched receipt: CreateAccount+DeployContract+Transfer already
    // committed (factory balance already decreased by MIN_ATTACHED_BALANCE),
    // but FunctionCall("new") panicked -> promise result is Failed.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    // Do NOT credit context.account_balance with the refund amount here,
    // modeling that the factory never actually retained the deposit.
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);

    let result = contract.on_lockup_create(
        lockup_account(),
        MIN_ATTACHED_BALANCE.into(),
        String::from(account_tokens_owner()),
    );

    // Binding under test: attached_deposit == refunded_to_predecessor OR
    // attached_deposit == usable_lockup_balance.
    // Assert (a) refund promise is scheduled without checking factory has the balance,
    // and (b) the lockup_account (already created per receipt semantics) has no
    // retrievable, initialized state — i.e., neither side of the equality is
    // actually satisfiable from the factory's own accounting.
    assert_eq!(result, false);
    // A near-workspaces / RuntimeStandalone integration test would additionally show:
    //   - the lockup account exists on-chain with deployed code and balance == MIN_ATTACHED_BALANCE
    //   - calling any view/state method on it panics (state not initialized)
    //   - the refund Promise::new(predecessor).transfer(...) fails when factory has no reserve
}
```
Full end-to-end confirmation of the receipt-level partial-commit behavior (that `CreateAccount/DeployContract/Transfer` persist despite the trailing `FunctionCall` failing) requires a `near-workspaces` sandbox test rather than `testing_env!` mocks, since the unit-test harness cannot model multi-action receipt semantics precisely — this is the part of the analysis based on documented NEAR protocol behavior rather than something directly observable in this repository's mocked test utilities.

```rust
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
