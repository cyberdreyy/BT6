### Title
Missing re-initialization guard in `LockupContract::new` allows owner hijack and fund drain - (File: `lockup/src/lib.rs`)

### Summary
The `lockup` contract's `#[init]` constructor `LockupContract::new` (`lockup/src/lib.rs:181-243`) never checks `env::state_exists()` before writing state, unlike every sibling contract in this repo (`staking-pool/src/lib.rs:179`, `multisig/src/lib.rs:104`, `voting/src/lib.rs:36`, `whitelist/src/lib.rs:34`, `lockup-factory/src/lib.rs:80`), which all guard with `assert!(!env::state_exists(), "Already initialized")`. This is the same bug class as the external report: an `initialize`/`new` entry point that lacks parameter/state validation and caller restriction, letting it be invoked (again) by an unprivileged party. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`new` is public, marked `#[init]`, and takes `owner_account_id` directly from the caller's arguments without any restriction on `msg.sender`/`predecessor_account_id` and without checking that the contract hasn't already been initialized: [4](#0-3) 

Because there is no `assert!(!env::state_exists(), ...)` check, calling `new` a second time on an already-deployed and already-initialized lockup account fully overwrites the `LockupContract` struct — including `owner_account_id`, `staking_information`, `vesting_information`, and `foundation_account_id` — with attacker-supplied values: [5](#0-4) 

`lockup_information.lockup_amount` is set to `env::account_balance()` at call time (i.e., whatever NEAR the account currently holds, including any already-vested/deposited funds), and `staking_information` is reset to `None`, clearing any live staking-pool binding recorded for the original owner: [6](#0-5) 

The binding that should hold is: `owner_account_id == the account originally designated by the lockup-factory at creation time`, for the lifetime of the contract. Re-invoking `new` breaks this equality — an attacker can set `owner_account_id` to their own account.

Every owner-privileged action in `lockup/src/owner.rs` is gated solely by `self.assert_owner()`, which simply checks `predecessor_account_id == self.owner_account_id`. Once an attacker becomes `owner_account_id` via re-init, they gain full owner privileges, including `transfer`, which moves the account's liquid NEAR to any receiver: [7](#0-6) 

### Impact Explanation
This is Critical: NEAR held by the lockup contract can be moved by a party (the attacker) not entitled to it. By re-calling `new`, the attacker overwrites `owner_account_id` to themselves, and (subject to the contract's transfer-enabled/vesting/lock conditions being satisfiable, e.g. an already fully-vested or transfers-enabled lockup, or one whose `unstake`/`withdraw_from_staking_pool` flow brings balance back to liquid) can drain the account via `transfer` or `add_full_access_key`, permanently taking control of the funds and the account itself.

### Likelihood Explanation
Likelihood is limited by two factors that keep this from being trivially always-exploitable:
1. `lockup-factory`'s `create` function batches `create_account`, `deploy_contract`, `transfer`, and the `new` function call into a single promise chain (`lockup-factory/src/lib.rs:136-157`), so under normal operation there's no window between deployment and initialization for another actor to front-run the very first `new` call. [8](#0-7) 
2. The real exposure is *re*-initialization after the contract is already live: because there is no `state_exists` guard, `new` remains publicly callable indefinitely after legitimate initialization, unlike every other contract in this codebase. Any account can call `new` on the live lockup account at any time.

### Recommendation
Add the same guard used elsewhere in this codebase to `LockupContract::new`:
```rust
assert!(!env::state_exists(), "The contract is already initialized");
```
in `lockup/src/lib.rs`, mirroring `staking-pool/src/lib.rs:179`, `multisig/src/lib.rs:104`, `voting/src/lib.rs:36`, `whitelist/src/lib.rs:34`, and `lockup-factory/src/lib.rs:80`. [9](#0-8) 

### Proof of Concept
1. `lockup-factory` deploys and initializes a lockup contract `lockup1.factory.near` with `owner_account_id = "victim"` via the batched `create`/`new` call. [8](#0-7) 
2. Attacker, from any account, directly calls:
```bash
near call lockup1.factory.near new '{"owner_account_id":"attacker","lockup_duration":"0","transfers_information":{"TransfersEnabled":{"transfers_timestamp":"0"}},"vesting_schedule":null,"release_duration":null,"staking_pool_whitelist_account_id":"whitelist","foundation_account_id":null}' --accountId attacker
```
Since `LockupContract::new` (`lockup/src/lib.rs:181`) has no `state_exists` check and no caller restriction, this succeeds and overwrites `owner_account_id` to `attacker`. [4](#0-3) 
3. Attacker now calls `transfer` as the new owner:
```bash
near call lockup1.factory.near transfer '{"amount":"<liquid_balance>","receiver_id":"attacker"}' --accountId attacker
```
`assert_owner()` passes because `predecessor_account_id == "attacker" == self.owner_account_id`, and the liquid NEAR balance is transferred out. [7](#0-6) 

I was unable to independently confirm whether the near-sdk `#[init]` macro version pinned in this repo's `Cargo.lock`/toolchain injects an implicit re-initialization guard at the macro level (this repo excludes `Cargo.lock`/tooling from scope and I could not inspect the exact `near-sdk` version behavior); based on the explicit, duplicated `assert!(!env::state_exists(), ...)` pattern present in every other contract's `new` and its conspicuous absence only in `lockup`, the guard is implemented manually per-contract, not by the macro, in this codebase.
