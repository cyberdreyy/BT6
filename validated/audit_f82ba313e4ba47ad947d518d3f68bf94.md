## Analysis: Analog Found

### Title
Permissionless `propagate_staked_settings` skips emode leverage validation when overwriting bank weights, allowing state inconsistency with liquidation-risk impact - (File: `programs/marginfi/src/instructions/marginfi_group/propagate_staked_settings.rs`)

### Summary
The Sherlock M-11 bug class is "a setter overwrites config fields without validating them against interdependent invariants, leaving the system in a broken/inconsistent state." In marginfi-v2, the permissionless instruction `propagate_staked_settings` overwrites a bank's `asset_weight_init`/`asset_weight_maint` (and other config fields) from the group's `StakedSettings` account, but — unlike the equivalent *admin* path `lending_pool_configure_bank` — it never re-validates the bank's existing `EmodeSettings` entries against the new weights.

### Finding Description
`propagate_staked_settings` is explicitly documented and implemented as permissionless (any signer can pay the fee and call it; there is no admin/signer check on the caller, only PDA/`has_one` relationship checks): [1](#0-0) 

It directly overwrites `bank.config.asset_weight_init`, `bank.config.asset_weight_maint`, `deposit_limit`, `total_asset_value_init_limit`, `oracle_max_age`, and `risk_tier` from the group's `StakedSettings`, then only calls `bank.config.validate()` (and oracle validation, conditionally) — it never calls emode validation: [2](#0-1) 

Compare this to the privileged-admin path `lending_pool_configure_bank`, which performs the analogous weight update and additionally re-validates every emode entry on the bank against the *new* weights via `bank.emode.validate_entries_with_liability_weights(...)`: [3](#0-2) 

`BankConfig::validate()` (called by `propagate_staked_settings`) only checks the weight fields internal to `BankConfig` itself (ranges, isolated-tier zero weights, oracle age) — it has no knowledge of `bank.emode` entries: [4](#0-3) 

`EmodeSettingsImpl::validate_entries_with_liability_weights` is the only function that checks emode entries do not exceed `emode_max_init_leverage`/`emode_max_maint_leverage` given a bank's current weights: [5](#0-4) 

Because `propagate_staked_settings` is callable by anyone and is the designated path to push group-wide `StakedSettings` weight changes onto individual banks, if the group admin edits `StakedSettings` to less-conservative weights (a legitimate, validated operation via `edit_staked_settings`, whose `StakedSettings::validate()` has no emode awareness either: [6](#0-5) ), any unprivileged user can then permissionlessly call `propagate_staked_settings` to push those weights onto a specific bank that already has emode entries configured — entries whose leverage limits were validated against the *old* weights only, at the time they were set via `config_bank_emode` (which is admin-gated and thus not re-checked here).

### Impact Explanation
This mirrors the Sherlock M-11 root cause precisely: a setter (permissionless here, rather than admin-only as in the original bond report) mutates interdependent risk parameters (`asset_weight_init`/`asset_weight_maint`) without validating them against a dependent invariant (`emode` leverage caps), which other code paths in the same codebase (`lending_pool_configure_bank`) treat as mandatory. The result is a bank whose on-chain `EmodeSettings` entries can imply leverage above `emode_max_init_leverage`/`emode_max_maint_leverage`, silently breaking the leverage-cap invariant the protocol relies on for accounts opted into emode. This is a state inconsistency with a direct financial-safety effect: emode-eligible positions could be opened/maintained at leverage beyond the intended risk ceiling, understating required collateral relative to the protocol's own risk model.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a staked-collateral group that has configured emode entries on a staked bank, and (2) the admin subsequently loosening `StakedSettings` weights via the normal, validated `edit_staked_settings` flow. Given that, the trigger step — calling permissionless `propagate_staked_settings` — requires no special privileges and no attacker-controlled malicious input; it is a standard, expected maintenance operation that any party (including the admin's own automation, a bot, or any third party) can and is expected to call. No `has_one`/authority check gates the caller of `propagate_staked_settings` itself.

### Recommendation
In `propagate_staked_settings`, after overwriting `bank.config.asset_weight_init`/`asset_weight_maint`, call `bank.emode.validate_entries_with_liability_weights(&bank.config, group.emode_max_init_leverage, group.emode_max_maint_leverage)` (loading the `MarginfiGroup`) just as `lending_pool_configure_bank` does, and fail the propagation (or clear/limit the offending emode entries) if the invariant is violated.

### Proof of Concept
1. Group admin creates a staked bank and configures an `EmodeEntry` on it via `config_bank_emode`, valid under the bank's current `asset_weight_init`/`asset_weight_maint` and the group's `emode_max_init_leverage`/`emode_max_maint_leverage`.
2. Group admin calls `edit_staked_settings` to raise `asset_weight_init`/`asset_weight_maint` in the group's `StakedSettings` account — this succeeds because `StakedSettings::validate()` has no emode awareness.
3. Any user calls permissionless `propagate_staked_settings` for that bank; `bank.config.validate()` passes (weight ranges are fine in isolation), and the bank's weights are updated with no emode re-check.
4. The bank's existing `EmodeEntry` now implies leverage exceeding `emode_max_init_leverage`/`emode_max_maint_leverage`, a state that `lending_pool_configure_bank` would have rejected with `MaxInitLeverageExceeded`/`MaxMaintLeverageExceeded` (as demonstrated by the existing test `configure_bank_rejects_invalid_emode_leverage_on_weight_update`): [7](#0-6)

impl EmodeSettingsImpl for EmodeSettings {
    fn validate_entries_with_liability_weights(
        &self,
        bank_config: &BankConfig,
        emode_max_init_leverage: u32,
        emode_max_maint_leverage: u32,
    ) -> MarginfiResult {
        let liab_init_w: I80F48 = bank_config.get_weight(
            RequirementType::Initial,
            marginfi_type_crate::types::BalanceSide::Liabilities,
        );
        let liab_maint_w: I80F48 = bank_config.get_weight(
            RequirementType::Maintenance,
            marginfi_type_crate::types::BalanceSide::Liabilities,
        );

        let max_allowed_init_leverage: I80F48 = u32_to_basis(emode_max_init_leverage);
        let max_allowed_maint_leverage: I80F48 = u32_to_basis(emode_max_maint_leverage);

        for entry in self.emode_config.entries {
            if entry.is_empty() {
                continue;
            }
            let asset_init_w: I80F48 = I80F48::from(entry.asset_weight_init);
            let asset_maint_w: I80F48 = I80F48::from(entry.asset_weight_maint);

            // Basic sanity checks
            check!(
                asset_init_w >= I80F48::ZERO,
                MarginfiError::BadEmodeConfig,
                "emode entry tag {}: asset_init_w ({}) must be >= 0",
                entry.collateral_bank_emode_tag,
                asset_init_w
            );
            check!(
                asset_maint_w >= asset_init_w,
                MarginfiError::BadEmodeConfig,
                "emode entry tag {}: asset_maint_w ({}) must be >= asset_init_w ({})",
                entry.collateral_bank_emode_tag,
                asset_maint_w,
                asset_init_w
            );

            let max_leverage_init = calculate_max_leverage(asset_init_w, liab_init_w)?;
            check!(
                max_leverage_init <= max_allowed_init_leverage,
                MarginfiError::MaxInitLeverageExceeded,
                "emode entry tag {}: init leverage ({}) exceeds max allowed ({})",
                entry.collateral_bank_emode_tag,
                max_leverage_init,
                max_allowed_init_leverage
            );

            let max_leverage_maint = calculate_max_leverage(asset_maint_w, liab_maint_w)?;
            check!(
                max_leverage_maint <= max_allowed_maint_leverage,
                MarginfiError::MaxMaintLeverageExceeded,
                "emode entry tag {}: maint leverage ({}) exceeds max allowed ({})",
                entry.collateral_bank_emode_tag,
                max_leverage_maint,
                max_allowed_maint_leverage
            );

async fn configure_bank_rejects_invalid_emode_leverage_on_weight_update(
    bank_mint: BankMint,
) -> anyhow::Result<()> {
    let test_f = TestFixture::new(Some(TestSettings::all_banks_payer_not_admin())).await;
    let bank = test_f.get_bank(&bank_mint);

    let liab_init_w = I80F48::from_num(1.5);
    let liab_maint_w = I80F48::from_num(1.5);
    bank.update_config(
        BankConfigOpt {
            liability_weight_init: Some(liab_init_w.into()),
            liability_weight_maint: Some(liab_maint_w.into()),
            ..BankConfigOpt::default()
        },
        None,
    )
    .await?;

    let asset_init_w = liab_init_w * I80F48::from_num(0.9);
    let asset_maint_w = liab_maint_w * I80F48::from_num(0.9);

    let emode_tag = 1u16;
    let emode_entries = vec![EmodeEntry {
        collateral_bank_emode_tag: emode_tag,
        flags: 0,
        pad0: [0, 0, 0, 0, 0],
        asset_weight_init: asset_init_w.into(),
        asset_weight_maint: asset_maint_w.into(),
    }];

    test_f
        .marginfi_group
        .try_lending_pool_configure_bank_emode(&bank, emode_tag, &emode_entries)
        .await?;

    // Tighten base weights to push emode leverage above max while remaining a valid bank config.
    let new_liab_init_w = asset_init_w / I80F48::from_num(0.96);
    let new_liab_maint_w = asset_maint_w / I80F48::from_num(0.96);

    let res = test_f
        .marginfi_group
        .try_lending_pool_configure_bank(
            &bank,
            BankConfigOpt {
                liability_weight_init: Some(new_liab_init_w.into()),
                liability_weight_maint: Some(new_liab_maint_w.into()),
                ..BankConfigOpt::default()
            },
        )
        .await;

    assert!(
        res.is_err(),
        "Updating base weights that push emode leverage above limits should fail"
    );
    assert_custom_error!(res.unwrap_err(), MarginfiError::MaxInitLeverageExceeded);

    Ok(())
}
