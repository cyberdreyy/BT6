### Title
EI credential holder can trigger `RunJobV2` for arbitrary non-webhook job IDs via `PipelineRunsController.Create` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the integer-ID run path on `isUser` returned by `auth.GetAuthenticatedUser`, intending to restrict it to session/token users and exclude external initiators (EIs). However, `auth.AuthenticateExternalInitiator` also sets the `SessionUserKey` context value to a synthetic `clsessions.User{Role: clsessions.UserRoleRun}`, so `GetAuthenticatedUser` returns `ok=true` (i.e. `isUser=true`) for EI-authenticated requests as well, defeating the intended restriction.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Create` first rejects UUID-formatted IDs (webhook jobs, now removed) and then checks: [1](#0-0) 
The comment explicitly states "only users are allowed to run jobs using int IDs - EIs not allowed," implying the check is meant to distinguish a real user session/token from an EI credential. But in `core/web/auth/auth.go`, `AuthenticateExternalInitiator` stores the EI object under `SessionExternalInitiatorKey` and *also* stores a synthetic `User` under `SessionUserKey`: [2](#0-1) 
`GetAuthenticatedUser` only reads `SessionUserKey` and returns `true` whenever that key is set, with no way to distinguish whether it was populated by `AuthenticateBySession`/`AuthenticateByToken` (real user) or by `AuthenticateExternalInitiator` (synthetic run-role user for EI): [3](#0-2) 
Consequently, if the `/v2/jobs/:ID/runs` route (or any route reachable by EI auth) is protected by an `Authenticate` middleware chain that includes `AuthenticateExternalInitiator`, an EI credential holder gets `isUser=true` in `Create`, parses the integer job ID, and calls `prc.App.RunJobV2(ctx, jobID, nil)` for any job type (e.g., an OCR job), with no check that the job is bound to that EI or is of a type EIs are permitted to trigger.

### Impact Explanation
This is an authorization-bypass / unauthorized job-run trigger: an external-initiator credential — which should be scoped to running the specific webhook job(s) it is bound to — can instead trigger `RunJobV2` for arbitrary numeric job IDs belonging to any job type (OCR, keeper, flux monitor, etc.) it has no binding to. Triggering unauthorized pipeline runs of non-webhook job types can cause unintended on-chain transactions/reports or resource exhaustion depending on job type, matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Requires only valid EI credentials for any registered external initiator (a low-privilege, narrowly-scoped credential type) and knowledge/guessing of a target job's small integer ID — feasible and repeatable via a single POST request. Actual exploitability depends on router configuration confirming this endpoint's middleware chain includes `AuthenticateExternalInitiator`; I could not fully confirm the exact middleware chain for the `/v2/jobs/:ID/runs` POST route from `core/web/router.go` within the available exploration, so this should be verified before treating it as fully confirmed. Based on the code comment ("EIs not allowed") and the existing UUID-based webhook check, the code's intent strongly implies EI auth is expected on this route, making the mismatch between intent and enforcement the root cause.

### Recommendation
Distinguish EI-derived pseudo-users from genuine session/token users, e.g., by checking `auth.GetAuthenticatedExternalInitiator(c)` and rejecting when present, or by adding an explicit synthetic flag (not just `Role: UserRoleRun`) that `Create` can check, rather than relying solely on `isUser`/`SessionUserKey` presence. Additionally, RunJobV2 triggered via EI paths should validate the EI-to-job binding before executing.

### Proof of Concept
Go handler-level integration test (in `core/web/pipeline_runs_controller_test.go` or similar):
1. Set up an app with a registered external initiator and a non-webhook (e.g., OCR) job with a known integer ID, with no relation between the EI and that job.
2. Send `POST /v2/jobs/<ocrJobID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's valid credentials (per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`).
3. Assert the middleware chain authenticates via `AuthenticateExternalInitiator`, setting `SessionUserKey` to the synthetic run-role user.
4. Assert `Create` proceeds into the `isUser` branch, calls `RunJobV2`, and returns `200 OK` with a pipeline run resource — demonstrating the EI triggered a run of a job it has no binding to.
5. Compare against expected correct behavior: the request should be rejected with `401`/`422` for EI-authenticated requests targeting a job the EI is not bound to.
