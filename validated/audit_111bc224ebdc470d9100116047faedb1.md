### Title
A second `requestWithdraw` overwrites `lastWithdrawRequest`, letting a loss-adjusted receipt escape the haircut and be claimed at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` stores the user's request epoch in a single slot `lastWithdrawRequest[_user]`. When a borrower loss is applied via `stopEpochWithDuration(_lossAmount)`, the affected epoch's receipts must be redeemed at `lossRecoveryPriceByEpoch[epoch]` through `_claimLossAdjustedWithdrawRequest`, which is keyed **only** by `lastWithdrawRequest[_user]`. If the user makes a second withdraw request in a later epoch before claiming, `lastWithdrawRequest[_user]` is overwritten, the loss-adjusted claim path silently misses the old epoch (`lossRecoveryPriceByEpoch[newEpoch] == 0` → early return), and the old haircut amount survives in `withdrawsRequests[_user]`/`withdrawsRequestsByEpoch[_user][lossEpoch]`, where it is later paid at par through `_claimFundedWithdrawRequest`. This mirrors CVE-2022-38076's bug class: insufficient validation of user-supplied sequencing lets an unprivileged user escalate an ordinary request into an inflated claim. [1](#0-0) [2](#0-1) 

### Finding Description
In `requestWithdraw`, the strategy burns the caller's principal, mints an equal receipt of strategy tokens, increments `pendingWithdraws`, and writes `lastWithdrawRequest[_user] = currentEpoch` unconditionally — there is no check that a previous, not-yet-settled loss-adjusted receipt exists. [3](#0-2) 

On claim, `claimWithdrawRequest` first tries `_claimLossAdjustedWithdrawRequest`, which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If the marker now points at a non-loss epoch, it returns 0 without clearing `withdrawsRequestsByEpoch[_user][lossEpoch]`, and the same amount is still included in `withdrawsRequests[_user]`, so `_claimFundedWithdrawRequest` burns and pays `normalAmount` at 100%. [4](#0-3) [5](#0-4) 

The code comments themselves assume "any remaining normal/APR0 receipt is older and already funded" — that assumption is false for a loss-adjusted receipt, because `stopEpochWithDuration` only sources the haircut amount (`claimBasis * lossRecoveryPrice`) from the borrower, not par. [6](#0-5) 

### Impact Explanation
Direct theft / insolvency: a lender whose epoch-E request is subject to, say, a 90% haircut (`lossRecoveryPrice = 10_000`) escapes the haircut entirely by re-requesting a dust amount in epoch E+1, then claiming the full E receipt at par. The vault only funded `10%` of that receipt; the remaining `90%` is paid from reserves belonging to other withdrawers and depositors, breaking the "one receipt, one haircut-adjusted payout" invariant and socializing the attacker's recovered loss onto honest users. Cost to the attacker is a dust-sized second request and one extra epoch of waiting.

### Likelihood Explanation
Requires a loss epoch (`stopEpochWithDuration` with `_lossAmount > 0` while the attacker has a pending request) and an honest manager/borrower continuing epochs — all within the intended threat model (attacker is merely a KYC'd lender / tranche holder). No privileged collusion, no oracle manipulation, no reentrancy: just two ordinary `requestWithdraw` calls and one `claimWithdrawRequest`. The `epochNumber <= lastWithdrawRequest` gate delays but does not prevent the claim. [7](#0-6) 

### Recommendation
In `requestWithdraw`, revert (or first settle) when the caller has an unsettled loss-adjusted receipt — i.e., check `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` and force `_claimLossAdjustedWithdrawRequest`-style settlement before overwriting the marker. Alternatively, track per-epoch receipts exclusively via `withdrawsRequestsByEpoch` and iterate/scan all epochs with nonzero receipts at claim time instead of relying on a single `lastWithdrawRequest` slot.

### Proof of Concept
Foundry fork PoC outline (against `IdleCreditVault`/`IdleCDOEpochVariant` on the credit-vault deployment):

```solidity
// setup: attacker deposits AA, epoch starts (epoch N running)
// 1. attacker calls cdoEpoch.requestWithdraw(attackAmount, AATranche) during epoch N
//    -> lastWithdrawRequest[attacker] = N, withdrawsRequestsByEpoch[attacker][N] = X
// 2. epoch ends with loss: manager calls stopEpochWithDuration(apr, 0, duration, lossAmount)
//    -> lossRecoveryPriceByEpoch[N] = haircut < RECOVERY_FULL; pendingWithdraws cleared
// 3. manager starts epoch N+1; attacker calls requestWithdraw(1 wei worth of tranches)
//    -> lastWithdrawRequest[attacker] overwritten to N+1
// 4. epoch N+1 ends (stopEpoch, borrower repays); attacker calls claimWithdrawRequest()
//    -> _claimLossAdjustedWithdrawRequest uses epoch N+1: lossRecoveryPriceByEpoch[N+1]==0, returns 0
//    -> _claimFundedWithdrawRequest pays withdrawsRequests[attacker] (still includes X) at par
// assert: attacker received X + interest instead of X * lossRecoveryPrice / RECOVERY_FULL
```

Key assertion: `underlyingReceived > X * lossRecoveryPriceByEpoch[N] / RECOVERY_FULL`, i.e., the haircut was never applied and the difference is drained from the reserve funding other users' claims.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
