## Title
Operator can permanently block *all* stakers' commission and stake withdrawals by setting an unregistered/opt-out beneficiary - (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::set_beneficiary_for_operator` lets an operator set an arbitrary `new_beneficiary` address with no check that the address can actually receive `AptosCoin`. Every `distribute()` call for *any* staker that has a staking contract with that operator routes the operator's commission through `aptos_account::deposit_coins` to this beneficiary inside the same atomic loop that also pays out the staker's own unlocked stake. If the beneficiary address has opted out of direct coin transfers (`aptos_account::set_allow_direct_coin_transfers(false)`) and is not registered for `AptosCoin`, `deposit_coins` aborts, reverting the whole `distribute()` transaction and blocking every shareholder in that pool — including stakers who never authorized the operator to control this.

### Finding Description
`set_beneficiary_for_operator` stores the beneficiary keyed only by `operator_addr`, with **no validation** on `new_beneficiary`: [1](#0-0) 

Because `BeneficiaryForOperator` is stored under the operator's own address, this beneficiary is shared across **every staking contract the operator has with every staker** — `beneficiary_for_operator(operator)` is looked up the same way for all of them.

`distribute_internal` is invoked by the permissionless `distribute()` entry function, and it redeems shares for both the staker and the operator/beneficiary in one loop, using the same withdrawn `coins` pot: [2](#0-1) 

The payout to any recipient goes through `aptos_account::deposit_coins`, which **aborts** if the recipient is unregistered for the coin type and has disabled arbitrary transfers: [3](#0-2) [4](#0-3) 

Notably, the framework's own `vesting.move` module recognizes this exact hazard and guards against it in its analogous `set_beneficiary` function, explicitly stating the reason in a comment: [5](#0-4) 

`staking_contract::set_beneficiary_for_operator` has no equivalent guard, so the same DoS the vesting module deliberately prevents is fully reachable in `staking_contract`.

### Impact Explanation
An operator (who legitimately controls only their own beneficiary setting) can weaponize this to indefinitely trap the stake of every staker who delegates to them:
1. Operator sets `new_beneficiary` to an address they control.
2. From that address, call `aptos_account::set_allow_direct_coin_transfers(false)` and never register for `AptosCoin` (or simply never call `coin::register`).
3. Any subsequent `staking_contract::distribute(staker, operator)` call — for *any* staker with a contract to this operator — will abort inside the shareholder loop when it tries to pay the operator's commission to this beneficiary, because `coin::is_account_registered<AptosCoin>` is false and `can_receive_direct_coin_transfers` is false.
4. Since `distribute()` reverts atomically, the staker's already-unlocked/withdrawable principal (sitting in `inactive`/`pending_inactive` stake) can never be paid out as long as the beneficiary remains in this state — a permanent, non-recoverable block on withdrawal rights for stakers who never granted the operator any such control.

This satisfies "Permanent lock or non-recoverable loss of claim rights in stake ... beneficiary ... flows" and "Wrong-role control ... without already holding that role" (operator gains unilateral power over staker withdrawal availability).

### Likelihood Explanation
High. No special privileges beyond being an operator (a role obtainable by anyone a staker chooses, or self-assigned via `create_staking_contract`) are required, and the malicious beneficiary configuration (`set_allow_direct_coin_transfers(false)` + non-registration) is trivial and cheap to set up. The bug is a straightforward omission — contrasted directly against the fix already applied in the sibling `vesting.move` module for the same class of issue.

### Recommendation
Add the same guard used in `vesting::set_beneficiary` to `staking_contract::set_beneficiary_for_operator`: require `aptos_account::assert_account_is_registered_for_apt(new_beneficiary)` before accepting the update, so a beneficiary can never be set to an address that would revert `distribute()`. Additionally, consider isolating operator-commission payout failures from staker payout in `distribute_internal` (e.g., by paying stakers first / independently, or by falling back to crediting an escrow/pending-withdrawal record instead of aborting the whole transaction) to remove the shared-failure-domain design entirely.

### Proof of Concept
1. Staker `S` calls `staking_contract::create_staking_contract(S, operator=O, ...)`, staking 100 APT with 10% commission.
2. `O` calls `staking_contract::set_beneficiary_for_operator(O, B)` where `B` is an address `O` controls.
3. From `B`, call `aptos_account::set_allow_direct_coin_transfers(B_signer, false)`, and ensure `B` never registers for `AptosCoin` (a fresh, never-`coin::register`-ed account satisfies this by default until this call; the explicit opt-out call additionally guarantees `can_receive_direct_coin_transfers(B) == false`).
4. Stake pool accrues rewards; `O` calls `staking_contract::request_commission(O, S, O)` to unlock commission, and `S`'s stake also becomes unlockable after lockup expiry (`stake::fast_forward_to_unlock`).
5. Anyone calls `staking_contract::distribute(S, O)`. Execution reaches the shareholder loop in `distribute_internal`, hits the recipient == `O` case, resolves `beneficiary_for_operator(O) == B`, and calls `aptos_account::deposit_coins(B, ...)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The entire `distribute` transaction reverts — `S`'s unlocked principal (and any future rewards) remains permanently stuck as long as `B`'s configuration is unchanged, which `O` fully controls and can maintain indefinitely.

```text
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };
```
