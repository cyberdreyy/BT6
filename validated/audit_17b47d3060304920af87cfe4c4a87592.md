### Title
GET /v2/external_initiators lacks role wrapper, allowing view-role users to enumerate all external initiators including their AccessKey - ([File: core/web/router.go])

### Summary
The `GET /v2/external_initiators` route is registered without any `RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` wrapper, unlike its sibling `Create`/`Destroy` routes, so any authenticated user (including the lowest `view` role) can list all configured External Initiators. The response, built from `presenters.ExternalInitiatorResource`, includes the initiator's `AccessKey` field, which is a credential component used together with a secret in `bridges.AuthenticateExternalInitiator`.

### Finding Description
In `core/web/router.go`, the `authv2` group requires only session/token authentication (any of the three roles: view, run, edit/admin), and within it: [1](#0-0) 
`Create` and `Destroy` are wrapped with `auth.RequiresEditRole`, but `Index` is only wrapped with `paginatedRequest`, which does not perform any role check — it purely parses pagination parameters (confirmed by `RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` implementations in `core/web/auth/auth.go`, none of which are applied to `eia.Index`).

`ExternalInitiatorsController.Index` fetches all external initiators from the ORM and maps them through `presenters.NewExternalInitiatorResource`: [2](#0-1) 

The presenter includes the `AccessKey` field but omits `Salt` and `HashedSecret`: [3](#0-2) 

The underlying `bridges.ExternalInitiator` model stores `AccessKey`, `Salt`, and `HashedSecret`, where `AccessKey` paired with a caller-supplied `Secret` (verified against `HashedSecret`/`Salt`) is used by `bridges.AuthenticateExternalInitiator` to authenticate EI requests: [4](#0-3) [5](#0-4) 

An existing test confirms the actual behavior of `Index`: a view-role-accessible (any authenticated) GET returns `Name`, `URL`, `AccessKey`, and `OutgoingToken` for every EI, with no secret/hash exposed: [6](#0-5) 

So the disclosed fields are `Name`, `URL`, `AccessKey`, `OutgoingToken`, `CreatedAt`, `UpdatedAt` — the `Secret`/`HashedSecret`/`Salt` are correctly excluded from the presenter, so full credential extraction (which would allow EI impersonation without further effort) is not possible via this endpoint. However, the `AccessKey` (the identifier half of the EI credential pair) is disclosed to any authenticated user regardless of role, which is an authorization-exactness violation: `Create`/`Destroy` require edit role, but `Index` requires none.

### Impact Explanation
This is an authorization/role-check gap (missing role wrapper) causing unauthorized enumeration of External Initiator metadata and access-key identifiers to any authenticated low-privilege (`view`-role) user. It does not directly yield full credential compromise since the secret/hash is excluded from the response, but it does violate least-privilege/authorization exactness (`Create`/`Destroy` are edit-gated, `Index` is not) and discloses `AccessKey` values, `Name`s, and `URL`s that were intended to be edit-role-only information, which could facilitate targeted follow-on attacks (e.g., combined with any secret-leak vector elsewhere) or simply be treated as unauthorized information disclosure.

### Likelihood Explanation
Trivial to exploit: any authenticated `view`-role session or API token can send a single unauthenticated-w.r.t.-role `GET /v2/external_initiators` request and enumerate all initiators. No special preconditions beyond having any valid low-privilege session/token.

### Recommendation
Wrap the `Index` route with an explicit role check consistent with the other EI endpoints, e.g. `authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))` (or at minimum `RequiresRunRole` if run-role users are intended to view EIs), in `core/web/router.go`.

### Proof of Concept
1. In `core/web/external_initiators_controller_test.go`, extend `TestExternalInitiatorsController_Index` to create a session/token with `clsessions.UserRoleView` (mirroring how other controller tests build role-specific clients, e.g., `cltest.NewHTTPClient` variants with view role) and issue `GET /v2/external_initiators`.
2. Assert the response status is `200 OK` (not `401`/`403`) for a view-role client, proving no role wrapper is enforced (contrast with a similarly-constructed test against `POST /v2/external_initiators` using a view-role client, which should assert `401 Unauthorized` per `auth.RequiresEditRole`).
3. Parse the response body into `[]presenters.ExternalInitiatorResource` and assert it contains `Name`, `URL`, `AccessKey`, `OutgoingToken` for all inserted EIs, and separately assert (via reflection or JSON field check) that `presenters.ExternalInitiatorResource` has no `Secret`/`HashedSecret`/`Salt` json tags, confirming the exact scope of the disclosure.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

// AuthenticateExternalInitiator compares an auth against an initiator and
// returns true if the password hashes match
func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}
