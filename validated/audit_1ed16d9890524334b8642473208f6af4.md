### Title
Dust withdrawal request blocks processing of an entire queued withdrawal epoch - ([File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
`IdleCDOEpochQueue.processWithdrawRequests` batches all queued withdrawals for an epoch into one call to `IdleCDOEpochVariant.requestWithdraw` and requires the resulting per-tranche price to be nonzero. A KYC-passing tranche holder can enqueue a one-wei tranche withdrawal that converts to zero underlying units, causing `_cdo.requestWithdraw` to return `0` and the queue to revert with `Is0`. Because requests are stored only in aggregate and per-user mappings, the manager cannot exclude the dust request, so one dust request can repeatedly prevent all other queued withdrawals in that epoch from being processed. [1](#0-0) 

### Finding Description
During a running epoch, `requestWithdraw` accepts any nonzero transferable tranche amount, records it in `userWithdrawalsEpochs`, and adds it to the aggregate `epochPendingWithdrawals`. [2](#0-1) 

Later, `processWithdrawRequests` uses the whole `epochPendingWithdrawals[_epoch]` balance as `_pending` and passes it to the CDO. [3](#0-2) 

The CDO converts tranche tokens to underlying with integer division:

```solidity
_amount * _tranchePrice(_tranche) / ONE_TRANCHE_TOKEN
```

so a one-wei tranche request converts to `0` for any underlying-denominated price below `1e18`. [4](#0-3) 

For a normal withdrawal, `_underlyings` remains `0` after interest and fee accounting, `IdleCreditVault.requestWithdraw` returns immediately for a zero amount, and `_withdrawOps` only burns the dust tranche amount. [5](#0-4) [6](#0-5) 

The queue then computes:

```solidity
_epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending;
```

For `_underlyingsRequested == 0`, `_epochPrice == 0`, and the transaction reverts with `Is0`. [7](#0-6) 

The revert rolls back `epochPendingWithdrawals[_epoch] = 0`, `epochPendingClaims[_epoch]`, and `pendingClaims`, so the contaminated batch remains pending. [8](#0-7) 

Only the attacker can remove the dust request through `deleteWithdrawRequest`; owner and manager cannot selectively remove it. [9](#0-8) 

### Impact Explanation
One KYC-passing tranche holder can temporarily freeze withdrawal processing for every other user in the same queue epoch. The cost is one wei of tranche tokens plus gas. The attacker can repeat this each epoch, keeping the queue unavailable for as long as they continue submitting dust requests. Honest queued users cannot receive underlying through `claimWithdrawRequest` while the batch remains unprocessed because `epochWithdrawPrice` is still unset. [10](#0-9) 

Users retain an escape path by deleting their own requests and receiving their tranche tokens back, so this is a temporary withdrawal freeze rather than permanent loss of principal. However, the freeze can be maintained indefinitely at negligible cost and disrupts all withdrawals routed through the affected queue. [9](#0-8) 

### Likelihood Explanation
Likelihood is moderate. The attack requires only a wallet that passes `isWalletAllowed` and holds at least one wei of the relevant tranche token. [2](#0-1) [11](#0-10) 

The existing checks do not stop it because:

- the queue has no minimum withdrawal amount;
- the CDO allows a tranche amount that converts to zero underlying;
- `IdleCreditVault.requestWithdraw` explicitly returns early for `_amount == 0`;
- the queue treats a zero aggregate withdrawal price as fatal;
- `pendingClaims` only prevents processing a second batch and does not help remove the zero-price batch. [6](#0-5) [12](#0-11) 

### Recommendation
Enforce a minimum queue withdrawal denominated in tranche tokens that guarantees a nonzero underlying conversion, or reject `_underlyingsRequested == 0` inside `IdleCDOEpochVariant.requestWithdraw` before burning tranche tokens. A more precise fix is to let the queue identify and ignore zero-value requests, but because requests are aggregated, the simpler invariant is to require each `requestWithdraw(amount)` to satisfy:

```solidity
amount * cdo.virtualPrice(tranche) / ONE_TRANCHE >= 1
```

For the prefunded-style rounding case, the code already recognizes that zero-share minting should not block epoch finalization; the withdrawal queue should similarly avoid making a zero-valued batch an unrecoverable processing state. [13](#0-12) 

### Proof of Concept
The following Foundry test follows the existing `IdleCDOEpochQueue.t.sol` setup and demonstrates that a one-wei queued withdrawal poisons the whole batch:

```solidity
function testDustWithdrawRequestBlocksEpochProcessing() external {
    // Move from the initial running epoch into epoch 1 buffer.
    _stopCurrentEpoch();

    // Give a victim a meaningful queued withdrawal.
    address victim = makeAddr('victim');
    uint256 victimTranches = _depositWithUser(victim, 100e6);

    // Give the attacker enough tranche balance for a one-wei request.
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1e6);

    // Start epoch 1; queue withdrawals are accepted while it is running.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    uint256 nextEpoch = strategy.epochNumber() + 1;

    // Victim queues a normal withdrawal.
    _requestWithdrawWithUser(victim, victimTranches);

    // Attacker adds a one-wei withdrawal to the same aggregate epoch batch.
    vm.prank(attacker);
    queue.requestWithdraw(1);

    assertEq(
        queue.epochPendingWithdrawals(nextEpoch),
        victimTranches + 1
    );

    // Stop epoch 1. The pending batch is now keyed to current epochNumber.
    _stopCurrentEpoch();
    assertEq(strategy.epochNumber(), nextEpoch);

    // The dust amount converts to zero underlying in the CDO, so
    // _underlyingsRequested * ONE_TRANCHE / _pending == 0 and this reverts.
    vm.expectRevert(Is0.selector);
    vm.prank(manager);
    queue.processWithdrawRequests();

    // The revert preserves the contaminated aggregate request.
    assertEq(
        queue.epochPendingWithdrawals(nextEpoch),
        victimTranches + 1
    );
    assertEq(queue.epochWithdrawPrice(nextEpoch), 0);
    assertFalse(queue.pendingClaims());

    // Consequently, the victim cannot claim underlying for that epoch.
    vm.expectRevert(NotAllowed.selector);
    vm.prank(victim);
    queue.claimWithdrawRequest(nextEpoch);
}
```

The same test remains valid if the victim requests first and the attacker appends the dust request afterward, because `processWithdrawRequests` aggregates all requests into a single `_pending` amount. [14](#0-13)
