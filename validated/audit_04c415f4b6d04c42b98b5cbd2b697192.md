### Title
Reorg-permit exclusion in `reorg_permit_stands` is validated against the wrong scope, letting a stale permit for one tenure silently excuse a conflict when a *different*, unrelated tenure reaches the pre-commit threshold - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The Anyswap bug granted a standing, unbounded privilege ("infinite approval") to whatever address the caller supplied, without checking that the address was the one actually entitled to it. The stacks-signer has a structurally similar pattern: a "reorg permit" recorded for one tenure (`superseded_tenures`, keyed only by the *superseded* tenure's consensus hash) is consulted purely by asking "is the permitting sortition still canonical?" — never by checking that the block *currently being signed* is the one the permit was actually granted for. Because the exclusion check in the fresh-conflict scan (`handle_block_pre_commit`, `stacks-signer/src/v0/signer.rs:1403-1411`) is keyed only on the conflicting (superseded) tenure, not on the candidate block's own tenure, a standing permit can be reused to wave away a conflict on behalf of a tenure it was never granted to.

### Finding Description
`SortitionData::check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170-295`) records a permit when a new tenure `self` is allowed to reorg an older tenure that produced at most one poorly-timed block:

```
fn record_superseded_tenure(&self, signer_db: &mut SignerDb, tenure: &TenureForkingInfo) {
    signer_db.mark_tenure_superseded(
        &tenure.consensus_hash,        // the superseded tenure (e.g. "A")
        tenure.burn_block_height,
        &self.consensus_hash,          // the permitted-replacement tenure (e.g. "C")
        &self.burn_block_hash,
    )
}
``` [1](#0-0) 

The record is stored keyed *only* by the superseded tenure's `consensus_hash` (PRIMARY KEY) together with the identity of the sortition that was granted the right to replace it:

```
consensus_hash TEXT PRIMARY KEY,
superseded_by_consensus_hash TEXT NOT NULL,
superseded_by_burn_block_hash TEXT NOT NULL,
``` [2](#0-1) 

When a *different* block later crosses the pre-commit threshold, `handle_block_pre_commit` asks the DB for every signed conflict at or above its height (`get_signed_conflicts`) and, for each, checks only whether that conflict's permit sortition is still canonical:

```
if let Some(conflict) = conflicts.iter().find(|conflict| {
    conflict.last_endorsed > freshness_cutoff
        && !self.reorg_permit_stands(stacks_client, conflict)
        && self.conflict_still_blocks(...)
}) { ... refuse ... }
``` [3](#0-2) 

`reorg_permit_stands` itself only checks the *sortition's* canonicality — never that the block currently being evaluated for signature belongs to (or descends from) the tenure the permit was actually granted to:

```
fn reorg_permit_stands(&self, stacks_client: &StacksClient, conflict: &SignedConflictInfo) -> bool {
    let Some(superseded_by) = &conflict.superseded_by else { return false; };
    match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
        Ok(_) => true,
        ...
    }
}
``` [4](#0-3) 

The only place `conflict.consensus_hash` is compared against the candidate block's own tenure is later, in the *separate* own-tenure duplicate-check branch:

```
if conflicts.iter().any(|conflict| {
    conflict.consensus_hash == block_info.block.header.consensus_hash
        && !self.reorg_permit_stands(stacks_client, conflict)
}) { ... }
``` [5](#0-4) 

That comparison is not present in the earlier, cross-tenure fresh-conflict scan at lines 1403-1411 that actually decides whether to refuse signing. The permit is therefore treated as a blanket, tenure-agnostic "the conflict is excused" flag rather than being scoped to the specific tenure it was granted to. This mirrors the Anyswap flaw precisely: a privileged exemption ("approval"/"permit") that should only ever benefit the one entity it was issued to (the router that requested it / the tenure that was sanctioned to reorg) is instead honored for anyone who happens to hit the same code path, as long as an easily-satisfied side condition (the router contract exists / the permitting sortition is still canonical) holds.

### Impact Explanation
If exploitable end-to-end (see Likelihood), the consequence is a signer excusing a conflict it should not excuse and proceeding to sign a block that has *not* actually been sanctioned to replace the previously-signed conflicting block. That is exactly the Critical-tier "signing a conflicting block" outcome called out in the rules: the signer's equivocation/double-sign guard (the whole point of `get_signed_conflicts` + `reorg_permit_stands` + `conflict_still_blocks`) is bypassed for a tenure that was never checked or sanctioned to displace the tenure it conflicts with.

### Likelihood Explanation
The permit's scope defect is unambiguous by direct code inspection: `reorg_permit_stands` is only ever invoked with the *conflict's* record, and the fresh-conflict exclusion path (lines 1403-1411) never checks `conflict.superseded_by.consensus_hash` (the tenure that was actually sanctioned) against the tenure of the block presently being signed. I was not able to fully construct, purely from static review, an end-to-end scenario that reliably produces two live, non-superseding tenures both at a height that survives the `stacks_height >= ?1` filter in `get_signed_conflicts` while also passing every other proposal-time check (`check_proposal`, pubkey/tenure-change validation) independently for the second tenure. Such a scenario plausibly requires a burn-chain fork producing sibling successor tenures around the same superseded parent, which is within the "one-slot miner plus gossip/natural forks" threat model, but confirming it needs tracing the exact height/ancestry arithmetic across a live fork, which this static pass could not fully close out. This should be verified with a targeted unit/integration test (mirroring `run_cross_tenure_scenario`/`standing_reorg_permit_clears_conflict` in `stacks-signer/src/v0/tests.rs:1193-1209`) using two *different*, non-descendant tenures both conflicting with a superseded tenure, to determine whether the second (unauthorized) tenure gets its conflict silently excused.

### Recommendation
In the fresh-conflict exclusion check (`stacks-signer/src/v0/signer.rs:1403-1411`), require that `reorg_permit_stands` only excuse a conflict when the permit's `superseded_by_consensus_hash` matches (or is an ancestor tenure of) the tenure of the block currently being evaluated for signature — not merely when the permitting sortition happens to still be canonical for some unrelated reason. Equivalently, thread the candidate block's `consensus_hash` into `reorg_permit_stands` and reject the exclusion if it does not match `conflict.superseded_by.consensus_hash`.

### Proof of Concept
Not fully reproducible from static analysis alone. The concrete steps to validate/reproduce would be:
1. Sign block A in tenure T1.
2. Trigger a legitimate reorg permit for T1 via a tenure T2 that satisfies `check_parent_tenure_choice`'s timing rules (as in `standing_reorg_permit_clears_conflict`, `stacks-signer/src/v0/tests.rs:1193-1209`), recording `superseded_tenures(T1 -> T2)`.
3. Construct a third, unrelated tenure T3 (distinct sortition, not descending from T2) whose proposed block also conflicts with A at height ≥ A's height, and that independently satisfies proposal-time checks (`check_proposal`) without itself needing/obtaining a permit for T1.
4. Drive T3's block to the pre-commit threshold and observe whether `handle_block_pre_commit`'s fresh-conflict scan excuses the conflict with A solely because T2's sortition (unrelated to T3) is still canonical, causing the signer to sign T3's block despite never having sanctioned T3 as A's replacement.

This would need to be exercised via the existing mock-node test harness in `stacks-signer/src/v0/tests.rs` (following the pattern of `run_cross_tenure_scenario`) to conclusively determine reachability.
