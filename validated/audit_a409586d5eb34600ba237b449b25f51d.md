### Title
External-initiator credentials bypass the "EIs not allowed" guard and trigger arbitrary job runs by integer job ID via cross-user session pollution - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` sets both `SessionExternalInitiatorKey` and `SessionUserKey` (with a synthetic `UserRoleRun` user) on every successful EI authentication. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser(c)` to gate the integer-job-ID run path with the explicit comment "only users are allowed to run jobs using int IDs - EIs not allowed," but because the EI auth method fakes a `SessionUserKey`, this check is satisfied by EI credentials too, defeating the intended restriction and the job-to-initiator binding.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go` lines 119-151) validates only the EI `AccessKey`/`Secret` pair against the `ExternalInitiator` row via `bridges.AuthenticateExternalInitiator`, then does:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
```
This means any successfully-authenticated EI request now also has a `SessionUserKey` present in the gin context, indistinguishable at that layer from a real logged-in user.

`PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go` lines 89-128) is reached via the `userOrEI` route group for `POST /v2/jobs/:ID/runs`, wrapped with `auth.RequiresRunRole`, which only rejects `UserRoleView` — the fake EI user has `UserRoleRun` so it passes trivially. Inside `Create`, the code explicitly tries to prevent EIs from using this integer-ID path:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
```
Because `GetAuthenticatedUser` just checks for the presence of `SessionUserKey` (set by `AuthenticateExternalInitiator` for every EI), `isUser` is `true` for EI-authenticated calls as well. This defeats the intended EI exclusion, and there is no subsequent check anywhere in this path binding the job ID to the calling EI's own `ExternalInitiator` record (unlike the removed webhook/UUID path, which is explicitly disabled). Consequently, an EI credential holder for initiator A can supply any integer job ID — including a job created for/owned by a completely different initiator or tenant B — and `RunJobV2` will be invoked unconditionally for that job.

### Impact Explanation
This allows unauthorized triggering of another job's pipeline run using only a restricted external-initiator credential, breaking the "one sender bound to one authorized job" invariant. Depending on job configuration (e.g., pipelines involving on-chain transactions, VRF fulfillment stubs, direct request fulfillment), this can cause unauthorized execution of another tenant's job logic and potential fund-moving side effects, aligning with Chainlink's "unauthorized job run" bounty impact class.

### Likelihood Explanation
The attacker needs only their own valid EI `AccessKey`/`Secret` — no admin or elevated privileges. The exploit is a single unauthenticated-role HTTP call (`POST /v2/jobs/:ID/runs` with a target job's integer ID), fully reproducible and repeatable, requiring no timing or race conditions.

### Recommendation
Do not set `SessionUserKey` when authenticating an external initiator; instead rely solely on `SessionExternalInitiatorKey` and a distinct role-check helper for EI requests (e.g., `RequiresRunRoleOrEI` that explicitly recognizes EI-only role) so that `auth.GetAuthenticatedUser` and the `isUser` check in `PipelineRunsController.Create` correctly identify true user sessions versus EI sessions. Additionally, if EIs are ever permitted to trigger runs by job ID, add an explicit ownership check that the job's configured external initiator matches the authenticated EI record before calling `RunJobV2`.

### Proof of Concept
Go handler-level integration test plan (in `core/web` test package, using `web.Router` similar to existing `external_initiator_test.go` patterns):
1. Seed two `ExternalInitiator` records A and B, each with distinct `AccessKey`/`Secret`, and two `Job` records `jobA` (intended for initiator A) and `jobB` (intended for initiator B).
2. Authenticate as initiator A by setting `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers for A.
3. Send `POST /v2/jobs/<jobB.ID>/runs` (jobB belongs to B).
4. Assert current (buggy) behavior returns `200 OK` with a created pipeline run (via mocked `RunJobV2`), demonstrating cross-initiator run triggering — expected correct behavior should be `401/403`.
5. Repeat with `isUser` check exercising `auth.GetAuthenticatedUser` directly in a unit test on `core/web/auth/auth.go`, confirming `AuthenticateExternalInitiator` populates `SessionUserKey` and that `GetAuthenticatedUser` returns `ok=true` for an EI-only request, proving the guard in `PipelineRunsController.Create` is bypassed.
