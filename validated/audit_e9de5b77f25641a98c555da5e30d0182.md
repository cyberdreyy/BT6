## Finding

### Title
Rejection weight is not excluded when tallying acceptance weight in `StackerDBListener`, letting a single signer's weight be double-counted across `total_weight_rejected` and `total_weight_approved` - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The node-side `StackerDBListener` tallies signer votes for a block into two separate running counters, `total_weight_approved` and `total_weight_rejected`, which the `SignerCoordinator` compares against `self.weight_threshold` / `self.total_weight` to decide whether a block is accepted, rejected, or still pending [1](#0-0) . As with the `_decrementWeightUntilFree` bug (M-07), where deprecated gauges were unnecessarily excluded from one running total but not the other, here the two branches that update these counters apply **asymmetric membership checks**, letting a signer's weight land in both buckets.

### Finding Description
In the `Accepted` branch, weight is only added to `total_weight_approved` if the signer's slot is not already present in `gathered_signatures`: [2](#0-1) 

It does not check `responded_signers`. In the `Rejected` branch, weight is only added to `total_weight_rejected` if `block.responded_signers.insert(slot_id)` succeeds (i.e., the slot has not yet responded at all): [3](#0-2) 

Both branches unconditionally add the slot to `responded_signers` after processing [4](#0-3) . So if a signer first broadcasts a `Rejected` message for a given `block_sighash` (its weight is added to `total_weight_rejected`, and its slot is recorded in `responded_signers`), and later broadcasts a validly-signed `Accepted` message for the **same** `block_sighash`, the `Accepted` branch's guard (`!gathered_signatures.contains_key(&slot_id)`) is still true — it was never added to `gathered_signatures` — so its weight is *also* added to `total_weight_approved`. The signer's weight is now counted in both buckets simultaneously.

This is exactly the M-07 pattern: one running total (`total_weight_approved`) is computed using a criterion (`gathered_signatures` membership) that is independent of, and inconsistent with, the criterion used to gate the other running total (`responded_signers` membership), so the sum of the two totals is not properly partitioned across signers, and the actual "distinct signers who currently endorse `Accept`" weight can be inflated by weight that logically belongs to a signer who has (at least previously) rejected the block.

A signer fully controls its own StackerDB slot content and only needs its own private key to produce two validly-signed `BlockResponse` messages (a `Rejected` then later an `Accepted`, or the reverse order relative timing) for the same `signer_signature_hash`; the legitimate `stacks-signer` client itself supports switching from a prior rejection to acceptance for the same block hash when `should_reevaluate_reject_reason` permits reconsideration (a re-proposal path) [5](#0-4) , or a signer can simply write both messages independently of that gating logic since it's writing to its own slot.

### Impact Explanation
`SignerCoordinator::get_block_status` uses `total_weight_approved >= self.weight_threshold` to decide the block has "received enough signatures" and returns the signature set to be pushed to the chain [6](#0-5) , and separately uses `total_weight_rejected` to decide the block should be treated as rejected [7](#0-6) . Because a single signer's weight can be simultaneously present in both totals, the miner's accounting of "how much distinct weight currently backs acceptance" is inflated relative to the true, mutually-exclusive weight backing the block. This breaks the aggregated-weight-vs-verified-accepts equality this scan is meant to protect: a signer whose true (or most recent) position is "reject" can still contribute weight toward the threshold that triggers the miner to push the block, i.e. a rejection recounted as an accept.

### Likelihood Explanation
Reachable by a single signer (or gossip of a signer's own two messages) without needing a majority, another signer's key, or the `auth_token`/local node access — matching the "reject rejected/accepted recounted" Critical-impact class in scope for this scan.

### Recommendation
Make the two counters mutually exclusive over `responded_signers` (or equivalently over a single per-slot "final vote" map), e.g. gate the `Accepted` branch's weight addition on `!block.responded_signers.contains(&slot_id)` (the same criterion the `Rejected` branch already uses), or track a single authoritative vote per slot and recompute both totals from that single source of truth rather than from two independently-guarded running sums.

### Proof of Concept
1. Miner proposes block `B` with `signer_signature_hash = H`.
2. Signer `S` (weight `w`) broadcasts `BlockResponse::Rejected` for `H`. `StackerDBListener` adds `w` to `total_weight_rejected` and inserts `S`'s slot into `responded_signers` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-519`).
3. Signer `S` later broadcasts a validly-signed `BlockResponse::Accepted` for the same `H` (either because `should_reevaluate_reject_reason` allowed it to reconsider, or because `S` simply writes a new chunk to its own StackerDB slot). `gathered_signatures` for `S`'s slot is still empty, so the guard at line 443 passes and `w` is also added to `total_weight_approved` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:443-446`).
4. `total_weight_approved + total_weight_rejected` now exceeds `total_weight` by `w`, and if `total_weight_approved` crosses `self.weight_threshold` only because of this double-counted `w`, `SignerCoordinator::get_block_status` returns `Ok(...)` and the miner pushes the block believing it has genuine 70% distinct-signer approval, even though `S`'s weight is also recorded as a rejection.
