### Title
Response cache scoped by `WorkflowOwner` only, not `WorkflowID`, causing cross-workflow cache confusion for HTTP action responses - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The PoolTogether finding is a class of bug where an aggregate/isolation invariant that the system design assumes ("individual balances sum to the total", i.e., "the sponsorship address must not affect the vault total") is silently violated in the accounting code because a scoping field is dropped in one code path but not another, letting one principal's state be conflated with another's. The Chainlink analog is the gateway's `v2` HTTP-action `responseCache`, whose documented design invariant is "workflow-scoped caching" / "cache entries are scoped by workflow ID to prevent cross-workflow data leakage" (`core/services/gateway/handlers/capabilities/v2/README.md:46-49,69-72`), but the actual `OutboundHTTPRequest.Hash()` implementation used as the cache key omits `WorkflowID` entirely while including `WorkflowOwner`.

### Finding Description
`responseCache.Fetch` and `responseCache.Set` key the shared, process-wide cache map (`cache map[string]*cachedResponse`) purely by `req.Hash()`: [1](#0-0) [2](#0-1) 

The package's own test suite documents that `Hash()` is invariant to `WorkflowID` while it does vary with `WorkflowOwner`: [3](#0-2) [4](#0-3) 

But the design documentation explicitly states the opposite invariant ("Cache Key: Generated from workflow ID and request hash"; "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage"): [5](#0-4) 

This is structurally the same root cause as the PoolTogether bug: the invariant that the accounting/isolation model depends on (per-key scoping) is asserted in the design but broken in the actual key-derivation code for a subset of fields, causing state from one context (a workflow ID) to be attributed to/shared with another (a different workflow ID, same owner). Any two workflows belonging to the same `WorkflowOwner` that make an HTTP action request to the same URL/method/headers/body will collide on the same cache entry regardless of `WorkflowID`, `CacheSettings`, timing, or intent — one workflow's stored response is silently served to a completely different workflow (`isExpiredOrNotCached`/`Fetch` read path at lines 48-54 and 66-108).

### Impact Explanation
Because cache scoping is by owner rather than by the documented workflow ID, a workflow can receive an HTTP response that was actually fetched/cached on behalf of a different workflow owned by the same address. This is a concrete cross-workflow response confusion: outputs (potentially containing owner-specific, workflow-context-specific, or stale/replayed data) leak or get reused across workflow boundaries that the system is designed to keep isolated (`Workflow Isolation` invariant in the README). Under `CacheSettings.Store=true` with a non-zero `MaxAgeMs`, a workflow's own logic (or a malicious/compromised co-owned workflow deployed by the same owner) can pre-seed a cache entry for a well-known URL that a different, security-sensitive workflow subsequently consumes as if it were a fresh, workflow-specific fetch, effectively poisoning the response that a workflow node acts on. This does not cross owner boundaries (the `WorkflowOwner` field is honored), so it is not a full cross-tenant leak, but it does break the documented per-workflow isolation guarantee that downstream workflow logic and any capability relying on `CacheSettings` correctness assumes.

### Likelihood Explanation
This is reachable purely from the unprivileged workflow-owner path: any owner who deploys more than one workflow (a normal, permitted action) can trigger this by having two workflows issue HTTP actions with the same method/URL/headers/body and `CacheSettings.Store=true`. No gateway/node compromise, no special privilege, and no on-chain access is required — only the ability to author and run two workflows under one owner, which is the standard, expected capability of any CRE user. The bug is deterministic and always reproducible (not probabilistic), and is directly confirmed by the project's own unit tests, which assert the (unintended) `WorkflowID`-invariance of `Hash()` as current behavior rather than flagging it as a defect.

### Recommendation
Include `WorkflowID` (in addition to `WorkflowOwner`, method, URL, headers, and body) in `OutboundHTTPRequest.Hash()` so the cache key matches the documented workflow-scoped isolation invariant. Add an explicit test asserting that two requests differing only in `WorkflowID` produce different hashes (inverting the currently-passing `having different workflowID results in same Hash` test), and audit other cache/rate-limiter/allowlist key-derivation functions in the gateway (`v2/http_handler.go`, `v2/http_trigger_handler.go`) for the same owner-vs-id scoping mismatch.

### Proof of Concept
1. Owner `O` deploys `WorkflowA` and `WorkflowB`.
2. `WorkflowA` issues an `OutboundHTTPRequest{Method: "GET", URL: "https://victim-api.example.com/data", WorkflowOwner: O, WorkflowID: "A", CacheSettings: {Store: true, MaxAgeMs: 600000}}`. The gateway fetches the response and stores it under `req.Hash()` via `responseCache.Fetch`/`Set` (`response_cache.go:66-108`).
3. `WorkflowB` (same owner `O`, different `WorkflowID: "B"`) issues the identical `Method`/`URL`/`Headers`/`Body` request with `CacheSettings.Store: true, MaxAgeMs: 600000`.
4. Because `Hash()` does not incorporate `WorkflowID` (confirmed by `response_cache_test.go:139-149`), `WorkflowB`'s request hits the same cache key as `WorkflowA`'s and receives `WorkflowA`'s previously cached response without any fresh HTTP fetch — violating the "Workflow Isolation" guarantee stated in `README.md:72`.

	defer rc.cacheMu.Unlock()

### 3.2 Caching Behavior

- **Cacheable Responses**: 2xx (success) and 4xx (client error) status codes.
- **Cache TTL**: Configurable, default 10 minutes
- **Cache Key**: Generated from workflow ID and request hash
- **Cache Invalidation**: Time-based expiration with periodic cleanup
- **Cache Strategy**: All cacheable responses are cached; Non-zero `CacheSettings.MaxAgeMs` determines whether to return a cached value or make a fresh request
- **Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage
