The core `_deposit` already mints on actual received amount, but `strategy.deposit(_amount)` uses the nominal amount — worth checking. Let me look at the credit vault deposit paths and `_skimDonatedAssets`.### Title
Credit vault mints/records full nominal amount on token pulls, so fee-on-transfer underlyings leave strategy tokens and withdraw receipts under-backed — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.deposit`, `collectWithdrawFunds`, `collectInstantWithdrawFunds` and `finalizeDefaultRecovery` all pull underlying with `safeTransferFrom(..., _amount)` and then credit/mint/reserve the full `_amount`, assuming the amount sent equals the amount received. For an underlying that charges a transfer fee (USDT/USDC can enable one), the vault receives `_amount - fee` while its accounting grows by `_amount`, silently under-backing strategy tokens and funded withdraw receipts by the cumulative fee.

### Finding Description
`IdleCDOCreditVault._deposit` correctly mints tranche shares on the *received* amount (`_contractTokenBalance(_token) - _preBal`), but then forwards the nominal `_amount` to the strategy: `IIdleCDOStrategy(strategy).deposit(_amount)` (contracts/IdleCDOCreditVault.sol:211). Inside `IdleCreditVault.deposit` (contracts/strategies/idle/IdleCreditVault.sol:596-617):

```solidity
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
_mint(msg.sender, _amount);
```

There is no `balanceOf` delta measurement. With a fee-on-transfer token:

1. The user's `transferFrom` into the CDO delivers `_amount - fee`; the CDO mints the lender shares only for the received amount — consistent so far.
2. The CDO then sends `_amount` to the strategy. If `preBal == 0` this reverts (deposit DoS); if the CDO holds any residual underlying (unclaimed-fee accruals not yet converted, donation dust, funds parked between epochs), the `fee` shortfall is paid out of that residual.
3. The strategy mints `_amount` strategy tokens (1:1 claim on underlyings via `price() == oneToken`) while it only ever took custody of `_amount - fee` of fresh value. `totEpochDeposits` also grows by `_amount`.

The same assumption appears in the claim-funding paths: `collectWithdrawFunds` (line 428) clears `pendingWithdraws` by `_amount` while receiving `_amount - fee`; `collectInstantWithdrawFunds` (line 402) decrements `pendingInstantWithdraws` by the full `_amount`; `finalizeDefaultRecovery` (line 708) pulls `_recoveredAmount` yet stores `defaultRecoveryReserve = reserveAmount` at full face value, so the recovery reserve backing defaulted/post-default claims is overstated by the fee.

### Impact Explanation
Strategy token supply (receipts for pending and instant withdraw claims, plus CDO active NAV) exceeds real underlying backing by the fee on every pull. Since `getContractValue` values the CDO's strategy-token balance at `price() == 1`, the deficit is hidden until payout time. The borrower repays principal+interest only up to the recorded amounts; claims are paid via `_transferFundedClaim`/`_transferDefaultRecovery` from the actual balance, so the last claimant(s) in each epoch — or defaulted-epoch recovery claimants — find the vault `fee` short per funding transaction and their `safeTransfer` reverts. Funds are permanently locked for the shortfall; with repeated deposits the gap compounds. Additionally the fee drained from the CDO residual in step 2 is effectively a transfer of other users' funds to cover the depositor's nominal credit.

### Likelihood Explanation
The vault is designed around ERC-20 pool currencies such as USDC/USDT, which implement optional fee-on-transfer logic that can be enabled by the issuer; no allowlist constrains `token` to fee-free assets. Any KYC-passing lender calling `depositAA`/`depositBB`/`depositDuringEpoch`, and the honest owner/manager flows that call `collectWithdrawFunds`/`collectInstantWithdrawFunds`/`finalizeDefaultRecovery`, trigger the mismatch. No existing guard stops it: `_deposit`'s pre/post balance check covers only share minting, `_skimDonatedAssets`/reserve guards assume accounting equals balance, and `onlyIdleCDO` gating is irrelevant since the CDO itself supplies the bad `_amount`. Uncertainty: this requires the underlying token to actually charge a fee (or begin charging one, per the USDT/USDC caveat in the original report), which is a deployment/asset assumption rather than a certainty on current mainnet configs.

### Recommendation
Measure received amounts everywhere tokens are pulled: in `IdleCreditVault.deposit`, `collectWithdrawFunds`, `collectInstantWithdrawFunds` and `finalizeDefaultRecovery`, snapshot `underlyingToken.balanceOf(address(this))` before and after `safeTransferFrom` and use the delta for `_mint`, `totEpochDeposits`, `pendingWithdraws`/`pendingInstantWithdraws` bookkeeping and `defaultRecoveryReserve`. Alternatively pass the CDO-measured received amount from `IdleCDOCreditVault._deposit` into `strategy.deposit`, and/or revert or document that fee-on-transfer underlyings are unsupported.

### Proof of Concept
Foundry fork-style sketch using a fee-on-transfer mock `FoTToken` (1% fee):

```solidity
function test_FoT_DepositUnderbacked() public {
    // vm fork: credit vault + CDO deployed with FoTToken as `token`
    uint256 amount = 1_000_000e6;
    fot.mint(lender, amount);
    vm.prank(lender);
    fot.approve(address(cdo), amount);

    // Ensure CDO has residual underlying > fee so strategy pull succeeds
    fot.mint(address(cdo), amount / 50);

    vm.prank(lender);
    cdo.depositAA(amount);

    // Strategy minted `amount` strategy tokens but only received `amount - fee`
    uint256 fee = amount / 100;
    assertEq(strategy.balanceOf(address(cdo)), amount);
    // real fresh backing is amount - fee; borrower later repays at most `amount`
    // -> last withdraw claimant is short `fee` and safeTransfer reverts
    assertLt(strategy.realBacking(), amount); // balanceOf(strategy) minus pre-existing
}
```

Same shape applies to `collectWithdrawFunds`: borrower funds `pendingWithdraws == X`, vault receives `0.99X`, `pendingWithdraws` is cleared to 0, and the last `claimWithdrawRequest` reverts on `_transferFundedClaim`.
