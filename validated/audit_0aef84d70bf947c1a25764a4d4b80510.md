### Title
Unfunded and stale-epoch instant-withdraw receipts are paid at par from the default-recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` is a use-after-free analog: an instant-withdraw receipt whose epoch-level backing was never collected (or that belongs to an epoch other than the defaulted one) is still redeemable at par. After `finalizeDefaultRecovery`, only receipts recorded under `defaultRecoveryEpoch` are haircutted via `_claimDefaultedInstantWithdrawRequest`; every other receipt accumulated in the aggregate `instantWithdrawsRequests[_user]` is burned and paid in full from the strategy's underlying balance, which post-finalization consists of `defaultRecoveryReserve`. Unfunded instant claims thereby steal recovery funds earmarked for haircutted claimants and active LPs.

### Finding Description
The bookkeeping is per-epoch on the claim side but aggregate on the funding side:

- `requestInstantWithdraw` credits `instantWithdrawsRequests[_user]` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and bumps the global unfunded bucket `pendingInstantWithdraws` (IdleCreditVault.sol:356-375).
- `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws`; no per-user/per-epoch funded flag is ever written (IdleCreditVault.sol:398-403).
- `finalizeDefaultRecovery` computes `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` and only adds `instantWithdrawClaimsByEpoch[epochNumber]` (current epoch) to the recovery basis via `defaultPendingClaimBasis` (IdleCreditVault.sol:644-649, 696).
- `claimInstantWithdrawRequest` then haircut-claims only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and pays the entire remaining `instantWithdrawsRequests[_user]` at par through `_transferFundedClaim` (IdleCreditVault.sol:380-393).

So an instant receipt from an epoch before the default that was never funded (its share of `pendingInstantWithdraws` was never collected by the CDO) survives finalization unhaircutted and outside `defaultPendingClaimBasis`, yet is paid at par out of the reserve. This is the stale-state/UAF shape: the receipt outlives the accounting that was supposed to settle it. The same hole exists pre-default for the normal path — `claimInstantWithdrawRequest` never verifies that the CDO actually collected funds for the receipt before paying it from the strategy's underlying balance, which can be holding borrower-funded amounts backing normal `withdrawsRequests` claims or recovery reserves.

### Impact Explanation
Direct theft of reserve/funded liquidity. An attacker (any KYC'd lender) requests an instant withdraw in epoch E; if the CDO collects only part of the instant queue at `startEpoch`, the attacker's receipt remains in `pendingInstantWithdraws`. When the pool later defaults and `finalizeDefaultRecovery` runs in epoch D, the attacker's old receipt is excluded from the haircut basis but still pays 1:1 from `defaultRecoveryReserve`. Every defaulted-epoch claimant and active LP is paid `defaultRecoveryPrice < 1` while the attacker is paid par, proportionally draining the reserve. Loss is bounded by the unfunded instant remainder, i.e. up to the full `pendingInstantWithdraws` amount, which can be the majority of the recovery reserve.

### Likelihood Explanation
Requires a partially-funded instant queue followed by a borrower default and `finalizeDefaultRecovery` — both are normal protocol paths (`getInstantWithdrawFunds`/`collectInstantWithdrawFunds` at `startEpoch`, default flow via `_handleBorrowerDefault`/`finalizeDefault`). No privileged collusion is needed; the attacker only needs to hold an instant receipt in a non-defaulted epoch, which is automatic if the queue was underfunded. Guard analysis: `defaultInstantWithdrawsFinalized` only covers `instantWithdrawClaimsByEpoch[epochNumber]`, `_claimDefaultedInstantWithdrawRequest` clears only the default-epoch slice, and nothing in `claimInstantWithdrawRequest` checks per-receipt funding, so existing guards do not stop it.

### Recommendation
Track funded instant receipts per epoch (mirror `instantWithdrawClaimsByEpoch` with a funded-by-epoch map written in `collectInstantWithdrawFunds`), include *all* unfunded instant claims in `defaultPendingClaimBasis` (not only `instantWithdrawClaimsByEpoch[epochNumber]`), and in `claimInstantWithdrawRequest` settle each epoch slice through `_claimDefaultedInstantWithdrawRequest`/recovery pricing rather than paying the aggregate remainder at par. At minimum, cap the at-par payout to per-user funded amounts so unfunded receipts cannot draw on `defaultRecoveryReserve` or funds backing normal withdraw claims.

### Proof of Concept
Foundry fork PoC sketch (mainnet fork, `IdleCreditVault` + `IdleCDOEpochVariant` deployed via `IdleCreditVaultFactory`):

```solidity
// 1. Users A (attacker) and B deposit AA; manager starts epoch E with instant
//    withdrawals enabled (setInstantWithdrawParams(delay, minAprDelta, true)).
// 2. A calls cdoEpoch.requestInstantWithdraw(x) -> vault mints A's receipt,
//    instantWithdrawsRequests[A] = x, instantWithdrawsRequestsByEpoch[A][E] = x,
//    pendingInstantWithdraws = x.
// 3. At startEpoch, arrange CDO liquidity so getInstantWithdrawFunds collects
//    only part of x (collectInstantWithdrawFunds(y), y < x). Epoch rolls to E+1.
// 4. Epoch E+1 runs; borrower fails to repay -> manager stopEpoch triggers
//    _handleBorrowerDefault; owner/keeper calls finalizeDefault ->
//    vault.finalizeDefaultRecovery(recovered, source) with
//    pendingInstantWithdraws = x - y != 0, so defaultInstantWithdrawsFinalized
//    = true but instantWithdrawClaimsByEpoch[E+1] == 0 -> A's basis excluded.
// 5. A calls cdoEpoch.claimInstantWithdrawRequest():
//    _claimDefaultedInstantWithdrawRequest(A) pays 0 (nothing at epoch E+1),
//    then instantWithdrawsRequests[A] = x is burned and paid at par via
//    _transferFundedClaim -> underlying leaves defaultRecoveryReserve.
// 6. Assert: B's defaulted claims and active-LP recovery price are reduced
//    pro-rata by A's par payout; reserve decreased by x - y beyond its basis.
```

Note: I was unable to fully read `IdleCDOEpochVariant.getInstantWithdrawFunds`/`claimInstantWithdrawRequest` and `_transferFundedClaim`/`_transferDefaultRecovery` bodies within the iteration budget, so the exact CDO-side gating of when instant claims may be called (e.g., whether the CDO blocks claiming while `pendingInstantWithdraws > 0`) is unverified; if such a guard exists at the CDO layer it would reduce severity to the post-default stale-epoch component described above.
