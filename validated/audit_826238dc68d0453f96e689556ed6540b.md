## Analysis

I found a valid analog to the reported bug class in Agave's transaction-v1 (SIMD-based) compute budget configuration path, where the framework — not the user — defaults a critical execution parameter to `0`, guaranteeing execution failure while the transaction fee is still charged to the sender.

### Title
Transaction V1 messages default `compute_unit_limit` to 0 when unset, causing guaranteed execution failure with fee loss - (File: `runtime-transaction/src/transaction_meta.rs`)

### Summary
For legacy/v0 transactions, an unset compute-unit-limit is given a sensible non-zero default computed per-instruction via `calculate_default_compute_unit_limit`. For the newer transaction-v1 format, the equivalent default is hardcoded to `0` whenever the `compute_unit_limit` field of `TransactionConfig` is `None`, mirroring the external report's pattern of a hardcoded `0` limit parameter that guarantees downstream failure.

### Finding Description
`VersionedTransactionConfiguration::from_v1_config` converts a V1 message's optional `TransactionConfig.compute_unit_limit` into the runtime's `TransactionConfiguration.compute_unit_limit` using `unwrap_or(0)`: [1](#0-0) 

This same defaulting-to-zero behavior is repeated in the transaction-view fast path used by the banking stage: [2](#0-1) 

and in the conformance harness path: [3](#0-2) 

By contrast, the Legacy/V0 path computes a non-zero default via `calculate_default_compute_unit_limit` (a per-instruction allocation), only settling at `0` for a fully empty instruction list: [4](#0-3) 

Critically, `TransactionConfig::empty()` (all fields `None`, including `compute_unit_limit`) is a *validated, acceptable* V1 message body — confirmed by test code that calls `message.validate().unwrap()` on a message built with `v1::TransactionConfig::empty()`: [5](#0-4) 

The resulting `compute_unit_limit: 0` is then propagated directly into the execution budget used to run the transaction: [6](#0-5) 

Since virtually every builtin/BPF instruction consumes at least some compute units, a V1 transaction that omits `SetComputeUnitLimit`-equivalent configuration is executed with `compute_unit_limit = 0` and is guaranteed to fail immediately with `InstructionError::ComputationalBudgetExceeded` on its very first instruction — an outcome the sender cannot avoid other than by knowing to explicitly set a limit, unlike Legacy/V0 transactions where the system silently supplies a workable default.

### Impact Explanation
Any transaction that reaches execution (passes signature/lock/fee-payer checks) but is doomed to fail still results in the fee payer being charged the base transaction fee (`ExecutedFailed` status, not discarded). An unprivileged sender constructing a syntactically valid, signed V1 transaction without setting a compute unit limit will unconditionally lose the transaction fee with zero possibility of success, purely due to the runtime's own `unwrap_or(0)` default — the same "hardcoded zero limit causes forced revert / fund loss" root cause pattern as the reported cross-domain-message bug.

### Likelihood Explanation
This is trivially reachable by any unprivileged transaction sender constructing a V1 message and simply not populating the `compute_unit_limit` optional field (the default/empty value for the struct), with no special privileges or leader/validator collusion required. Wallets or naive tooling adopting the V1 format without being aware of this asymmetric default (compared to Legacy/V0 auto-defaulting) would systematically produce guaranteed-fail, fee-losing transactions.

### Recommendation
Make the V1 `compute_unit_limit` default consistent with the Legacy/V0 path — i.e., compute a sensible non-zero default (e.g., via the same `calculate_default_compute_unit_limit`/`DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` logic) when `TransactionConfig.compute_unit_limit` is `None`, rather than defaulting to `0`, in `VersionedTransactionConfiguration::from_v1_config` and the analogous conversions in `transaction_view.rs` and `conformance/transaction_meta.rs`.

### Proof of Concept
1. Construct a `solana_message::v1::Message` with `TransactionConfig::empty()` (i.e., `compute_unit_limit: None`) and at least one instruction that consumes any compute units (e.g., a `system_instruction::transfer`).
2. Sign and submit the transaction with a funded fee payer.
3. The message passes `validate()` (per `svm/src/account_loader.rs` test at lines 2312-2330) and is accepted by the bank.
4. `VersionedTransactionConfiguration::from_v1_config` sets `compute_unit_limit = 0` (`runtime-transaction/src/transaction_meta.rs:125`).
5. `check_age_and_compute_budget_limits` builds the execution budget using this `0` limit (`runtime/src/bank/check_transactions.rs:190-198`).
6. Execution fails immediately with `InstructionError::ComputationalBudgetExceeded`, yet the base signature fee is deducted from the sender's account (`ExecutedFailed`).
