### Title
Loss-adjusted withdraw receipts are indexed by the wrong epoch, letting requesters claim the full un-haircutted basis and drain funds belonging to other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.collectWithdrawFunds` records the haircut under `lossRecoveryPriceByEpoch[epochNumber]` — the epoch counter at collection time — while `_claimLossAdjustedWithdrawRequest` looks the price up under `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the epoch in which the user *requested* the withdrawal. Because `epochNumber` is incremented inside `deposit()` during `stopEpoch` before/while the CDO collects the funded amount, these two indices diverge. The lookup then returns 0, the loss-adjusted path is skipped entirely, and the user falls through to `_claimFundedWithdrawRequest`, which pays the full un-haircutted `withdrawsRequests[_user]` basis at par. This is the on-chain analog of CVE-2022-43592's stale/uninitialized-state disclosure: a stale index reads the wrong slot and silently returns "no haircut", producing an overpayout.

### Finding Description
- A user calls `IdleCDOEpochVariant.requestWithdraw` during the buffer/running phase of epoch N. `IdleCreditVault.requestWithdraw` stores `lastWithdrawRequest[user] = N` and `withdrawsRequestsByEpoch[user][N] += amount` (lines 281–293).
- `stopEpoch` runs; the CDO deposits borrower funds back into the strategy. `deposit()` detects `isEpochRunning()` and executes `epochNumber += 1` (lines 607–610), so the counter is now N+1.
- If the borrower underfunds the pending basis (loss scenario, `_amount < pendingBasis`), `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]`, i.e. index N+1, and zeroes `pendingWithdraws` (lines 414–421). Only `_amount` underlyings are pulled into the strategy.
- When the user later calls `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` = `lossRecoveryPriceByEpoch[N]` = 0 and returns early (lines 789–792).
- Execution proceeds to `_claimFundedWithdrawRequest`. The epoch-wait check passes (`epochNumber` N+1 > `lastWithdrawRequest` N), and the user is paid the entire `withdrawsRequests[user]` at par via `_transferFundedClaim` (lines 326–349).
- The same index mismatch makes the guard in `requestWithdraw` (lines 261–271) useless: a new request in a later epoch sets `lossEpoch = lastWithdrawRequest[user]` to the new epoch, again missing the haircut stored at the collect-time index.

### Impact Explanation
Direct theft / insolvency. Every user whose receipt was haircutted under `stopEpochWithDuration`-style partial funding can claim 100% of basis instead of `claimBasis * lossRecoveryPrice / 1e18`. Since the strategy only received `_amount < pendingBasis` from the borrower, paying receipts at par drains underlyings that belong to other funded claimants (or to the default-recovery reserve boundary guarded by `_transferFundedClaim`, lines 897–907 — the guard only protects the reserve, not other claimants). The first claimants to call `claimWithdrawRequest` are overpaid; later claimants' transactions revert on insufficient balance — a permanent loss up to `pendingBasis - _amount` (the full haircut amount), and permanent freezing of the remaining honest claims.

### Likelihood Explanation
Requires only: (a) a `stopEpoch` where the borrower funds less than `pendingWithdraws` (a realized loss path explicitly supported by `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds`), and (b) any unprivileged lender with a pending withdraw request calling the permissionless `claimWithdrawRequest`. No privileged misbehavior is needed — the honest manager/borrower sequence triggers it. The misindexing is deterministic: `epochNumber` advances in `deposit()` during stop, while requests are stamped with the pre-stop counter, so every loss-adjusted epoch is affected whenever collection happens after the increment (note: the exact ordering depends on whether `collectWithdrawFunds` is invoked by the CDO before or after the deposit that bumps `epochNumber`; if it runs before the increment for a given variant, the haircut lands on N and the bug does not manifest — this ordering should be confirmed against `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration`, which the available index snippets did not fully show).

### Recommendation
Key `lossRecoveryPriceByEpoch` by the same epoch value used to stamp the receipts. Either snapshot `pendingWithdrawsEpoch = epochNumber` at the last `requestWithdraw`, or have `collectWithdrawFunds` accept the epoch index from the CDO. Alternatively, store a single `pendingLossRecoveryPrice` scalar since `pendingWithdraws` is a single aggregate bucket, and have `_claimLossAdjustedWithdrawRequest` use it directly instead of indexing by `lastWithdrawRequest`. Add a regression test where a stop-epoch loss partially funds pending receipts and assert claimants receive exactly `basis * price / 1e18`.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossAdjustedReceiptClaimedAtPar() external {
    // 1. LP deposits and epoch N starts
    idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);

    // 2. User requests withdraw during epoch N (buffer)
    uint256 reqBasis = cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));
    uint256 reqEpoch = IdleCreditVault(address(strategy)).epochNumber(); // N

    // 3. Borrower repays only a fraction of pendingWithdraws at stopEpoch (loss path)
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 funded = pending / 2; // 50% loss on receipts
    deal(defaultUnderlying, borrower, funded + expectedInterestRest);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(interest, _lossAmount); // triggers collectWithdrawFunds(funded)

    // lossRecoveryPriceByEpoch stored at epochNumber (N+1), not reqEpoch N
    assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0);

    // 4. User claims: loss-adjusted path skipped, paid full basis at par
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(user) - balPre;

    // BUG: receives reqBasis instead of reqBasis * 50%
    assertEq(got, reqBasis); // overpaid by reqBasis/2

    // 5. Second claimant's funded claim now reverts / vault is insolvent
    vm.expectRevert();
    vm.prank(user2);
    cdoEpoch.claimWithdrawRequest();
}
```

Uncertain as noted: the PoC holds if `collectWithdrawFunds` executes after the `deposit()`-driven `epochNumber` increment inside `stopEpoch`; if the CDO collects before incrementing, the haircut is stored under N and the claim path behaves correctly, in which case no vulnerability exists.
