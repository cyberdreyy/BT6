### Title
`claimInstantWithdrawRequest` leaves stale per-epoch receipt basis, inflating `instantWithdrawClaimsByEpoch` and corrupting default-recovery pricing — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class is "a withdrawal is completed without decrementing the queued/pending-share accounting, so the system overreports assets/claims." The direct analog exists in `IdleCreditVault.claimInstantWithdrawRequest`: when a user successfully claims an instant-withdrawal receipt, the function zeroes the aggregate `instantWithdrawsRequests[_user]` and burns the receipt tokens, but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. Those per-epoch counters are exactly what `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and `_claimDefaultedInstantWithdrawRequest` use if the same epoch later defaults. Already-paid claims are therefore counted a second time in default-recovery accounting.

### Finding Description
`claimInstantWithdrawRequest` (contracts/strategies/idle/IdleCreditVault.sol:380-393) does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It never touches `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`, which were incremented in `requestInstantWithdraw` (lines 371-374). The only place these are decremented is `_claimDefaultedInstantWithdrawRequest` (lines 844-853), which only runs once `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`.

Now consider epoch N where instant withdrawals are only *partially* funded:

1. Epoch N runs with instant withdrawals enabled. User A requests an instant withdraw of `X`. `instantWithdrawsRequestsByEpoch[A][N] += X`, `instantWithdrawClaimsByEpoch[N] += X`, `pendingInstantWithdraws += X`, and other users add `Y` more.
2. `startEpoch`/funding moves some but not all instant cash to the strategy via `collectInstantWithdrawFunds`, leaving `pendingInstantWithdraws > 0` while A's `X` was funded.
3. User A calls `claimInstantWithdrawRequest` and receives `X` underlying. The per-epoch basis entries remain stale.
4. The borrower defaults in epoch N; `finalizeDefaultRecovery` runs. Because `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still includes A's already-paid `X` (line 644-649).
5. `_defaultPrefundedInstantReserve` returns `instantBasis - pendingInstant` (lines 716-722), treating A's already-paid-out `X` as underlying "already held" by the strategy. That phantom amount is added to `defaultRecoveryReserve`/the reserve amount at line 685-691.

Result: `totalBasis` is overstated by `X` and `reserveAmount` is overstated by funds that already left the contract, so `defaultRecoveryPrice` is computed against non-existent backing.

### Impact Explanation
The invariant broken is "one receipt, one payout" and solvency of the recovery reserve. Two concrete harms:

- `defaultRecoveryReserve` is set to a value larger than the strategy's actual underlying balance (the phantom prefunded reserve was never pulled and was already paid to A). Every defaulted and post-default claim decrements this reserve via `_transferDefaultRecovery` (line 915), but the final claimants' `safeTransfer` calls revert on insufficient balance — their recovery is permanently frozen.
- The stale `instantWithdrawsRequestsByEpoch[A][N]` also means a later `claimInstantWithdrawRequest` by A enters `_claimDefaultedInstantWithdrawRequest`, computes `claimBasis = X`, and `instantWithdrawsRequests[A] -= X` reverts (it's 0), permanently DoS-ing A's claim path and leaving `instantWithdrawClaimsByEpoch[N]` inconsistent forever.

Loss is quantified by the amount of already-claimed instant withdrawals `X` in the defaulting epoch: `X` of reserve is promised to claims with no backing, so up to `X` of legitimate recovery claims (aggregated across users) cannot be paid.

### Likelihood Explanation
Requires a partially-funded instant-withdraw queue in the epoch that defaults: some users claim funded instant receipts while `pendingInstantWithdraws` remains non-zero. This is an ordinary mid-epoch state (the code explicitly handles "partially prefunded instant requests" in `_defaultPrefundedInstantReserve`), and an unprivileged tranche holder only needs to claim their instant withdrawal normally — no malicious sequencing beyond timing. Any subsequent borrower default in that epoch crystallizes the overreported basis. Honest privileged callers (borrower default path, CDO finalization) trigger the bug automatically.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers alongside the aggregate: iterate/delete `instantWithdrawsRequestsByEpoch[_user]` for the outstanding epoch(s) and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, mirroring what `_claimDefaultedInstantWithdrawRequest` does at lines 847-853. Alternatively track a per-user current instant-request epoch (like `lastWithdrawRequest`) so the per-epoch entry can be cleared in O(1).

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry` harness conventions in `test/foundry/IdleCreditVault.t.sol` / `IdleCDOEpochQueue.t.sol`):

```solidity
// setup: epoch running with instant withdraws enabled (setInstantWithdrawParams)
// userA and userB deposit, request instant withdrawals during epoch N
cdoEpoch.requestInstantWithdraw(amountA); // via requestWithdraw path when APR drops
cdoEpoch.requestInstantWithdraw(amountB);

// borrower funds only amountA worth of instant claims
// -> strategy.collectInstantWithdrawFunds(amountA) via CDO startEpoch
// pendingInstantWithdraws == amountB > 0

// userA claims successfully
cdoEpoch.claimInstantWithdrawRequest(); // pays amountA; byEpoch entries stale

// borrower defaults in epoch N; owner finalizes
cdoEpoch.stopEpochWithDuration(...); // or _handleBorrowerDefault path
cdoEpoch.finalizeDefaultRecovery(recovered, source);

// assert bug: basis inflated by already-paid amountA
assertGt(strategy.instantWithdrawClaimsByEpoch(N), amountB);
// defaultRecoveryReserve > actual strategy balance by ~amountA
// last claimant's _transferDefaultRecovery reverts -> recovery frozen
```

Key assertions: after A's claim, `strategy.instantWithdrawsRequestsByEpoch(A, N)` still equals `amountA` and `instantWithdrawClaimsByEpoch(N)` still includes `amountA`; after finalization, `defaultRecoveryReserve` exceeds `underlying.balanceOf(strategy)` and the final defaulted claim reverts.
