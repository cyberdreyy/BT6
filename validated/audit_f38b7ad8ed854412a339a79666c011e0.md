### Title
Division-before-multiplication in `_calcInterest` truncates the APR to whole percent, causing loss of interest for withdraw-request and instant-withdraw payouts - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external report describes a "multiply-after-divide" pattern: an intermediate value is divided (with integer truncation) and only afterwards multiplied, amplifying rounding error. The same pattern exists in `IdleCDOEpochVariant._calcInterest`, which first computes `_apr / 100` (integer division) and only then multiplies by `_amount` and the epoch duration. Every downstream consumer — `_calcInterestWithdrawRequest`, instant-withdraw accounting, and `expectedEpochInterest` — inherits the truncated APR.

### Finding Description
`_calcInterest` computes interest as:

```solidity
_amount * (_apr / 100) * _duration / (365 days * ONE_TRANCHE_TOKEN)
```

The test harness mirrors this exactly in `_calcInterestAtApr` (`test/foundry/IdleCreditVault.t.sol:3556-3558`).

Because `_apr / 100` is evaluated before any multiplication, any fractional component of the APR below 100 units (i.e. below a full percentage point) is truncated to zero. Concretely:

- `apr = 150` (intended 1.5%) → `150/100 = 1` → effective 1.0%; **33% of all interest is silently dropped**.
- `apr = 99` (intended 0.99%) → `99/100 = 0` → **100% of interest is dropped**.

This truncated interest then flows into `_calcInterestWithdrawRequest` (lines 856-878), where `totInterest` and `interestWithoutSplitRatio` are both computed from the floored APR, and into the epoch's `expectedEpochInterest` accounting. Withdrawers' interest, AA/BB split via `_calcTrancheInterestShare`, and the `_diff` reconciliation between the two tranches are all computed on the wrong (lower) interest base.

The ordering should be multiplication-then-division, e.g. `_amount * _apr * _duration / (100 * 365 days * ONE_TRANCHE_TOKEN)`, which preserves the fractional part of `_apr`.

### Impact Explanation
All users who `requestWithdraw` or take instant withdrawals during an epoch where the honest borrower/manager sets an APR that is not a multiple of 100 receive less underlying than they are entitled to — the lost yield remains in the vault and is captured by non-withdrawing holders, so this is a redistribution of unclaimed yield away from withdrawers. The loss is bounded by just under 1 percentage point of APR on the principal, but reaches 100% of owed interest whenever `apr < 100`, and ~9% of owed interest at e.g. `apr = 1099`. There is no guard that normalizes `_apr` to a multiple of 100, so the truncation is silent and systematic.

### Likelihood Explanation
Likelihood is moderate: the bug triggers deterministically whenever the configured APR has a non-zero remainder modulo 100, which is the common case for APRs like 4.25% or 11.67% (the comments in `_calcInterestWithdrawRequest` at lines 843-851 explicitly describe scaling APRs such as `10% * 35/30 = 11.67%`, i.e. values like 1167 that are not multiples of 100). No attacker action is required to enable the loss — any unprivileged user who files a withdraw request in such an epoch is underpaid. The magnitude per epoch is small (sub-1% of principal), which caps severity.

### Recommendation
Reorder operations so division happens last:

```solidity
// IdleCDOEpochVariant._calcInterest
return _amount * _apr * _duration / (100 * 365 days * ONE_TRANCHE_TOKEN);
```

Alternatively, keep `_apr` already scaled and document that APR must be expressed in units where no pre-division is needed. Add a Foundry test that sets `apr = 150` and asserts `requestWithdraw` pays interest consistent with 1.5%, not 1.0%.

### Proof of Concept
Conceptual Foundry test (to be placed in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function test_AprTruncationLosesInterest() external {
    // epoch running, borrower set apr = 150 (1.5%) in stopEpoch/startEpoch params
    uint256 amount = 1_000_000e6; // USDC
    uint256 duration = cdoEpoch.epochDuration();

    uint256 expected = amount * 150 * duration / (100 * 365 days * ONE_TRANCHE_TOKEN); // mul-first
    uint256 actual   = strategy.calcInterestView(amount); // wraps _calcInterest

    // actual uses (_apr / 100) first -> equals interest at apr = 100 (1.0%)
    assertEq(actual, amount * 100 * duration / (100 * 365 days * ONE_TRANCHE_TOKEN));
    assertLt(actual, expected); // ~33% of interest lost before any fees
}
```
