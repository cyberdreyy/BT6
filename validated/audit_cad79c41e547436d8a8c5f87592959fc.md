### Title
Withdraw requests opened while the pool is closed (`epochEndDate == 0`) bypass `pendingWithdraws` funding accounting and steal other users' funded receipts if the pool resumes - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.requestWithdraw` mirrors the kernel bug class — a boundary condition that wrongly accepts an out-of-domain input (`cs == ntargets` there; `epochEndDate == 0` "closed pool" requests here). When a request is submitted while the CDO is in the closed state, the code still burns CDO principal, mints a full receipt to the user, and records `withdrawsRequests` / `withdrawsRequestsByEpoch` / `lastWithdrawRequest`, but deliberately skips incrementing `pendingWithdraws` (lines 277–280) under the assumption that "a successfully closed pool already recalled all funds and has no later stopEpoch". If the pool is ever restarted (`restoreOperations` / a new `startEpoch` on the prefunded/epoch variants), that receipt is a valid claim for which `stopEpoch` will never source funds, so the claimant is paid out of underlying reserved for other users' funded withdraw/instant requests.

### Finding Description
In `requestWithdraw` (lines 259–294):

```solidity
bool isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0;
...
_burn(msg.sender, _principal);
_mint(_user, _amount);
if (!isClosed) {
  pendingWithdraws += _amount;   // skipped entirely when closed
}
lastWithdrawRequest[_user] = currentEpoch;
withdrawsRequests[_user] += _amount;
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
```

The receipt is fully recorded for the user but is invisible to `pendingWithdraws`, which is the aggregate that `stopEpoch`/funding flows use to pull underlying from the borrower/strategy for all pending receipts.

The claim gate in `_claimFundedWithdrawRequest` (line 326) is:

```solidity
if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
  revert NotAllowed();
}
```

Once a new epoch runs and `stopEpoch` increments `epochNumber` past `lastWithdrawRequest`, the claim succeeds and `_transferFundedClaim` pays `amount` at par — even though no funds were ever sourced for that receipt.

### Impact Explanation
Direct theft / insolvency. `stopEpoch` funds exactly `pendingWithdraws` worth of receipts. The attacker's unrecorded receipt claims at par, first-come-first-served, consuming underlying that belongs to honest users' funded `withdrawsRequests` / `instantWithdrawsRequests`. The last honest claimants are permanently shortfall-frozen (transfer reverts on insufficient balance), i.e., theft and permanent freezing of up to the attacker's `_amount`. Broken invariant: one receipt ↔ one funded payout (solvency of the request pool).

### Likelihood Explanation
Requires the pool to enter and then leave the closed/zero-`epochEndDate` state — e.g., `restoreOperations` after `_emergencyShutdown`, or the close/reopen path on the epoch variants — plus the attacker holding enough tranche/strategy tokens to pass a `_principal` burn via the CDO (`_onlyIdleCDO` requires going through the CDO's withdraw path, which any tranche holder can trigger). Honest privileged roles only need to run normal epoch operations around the attacker's request, which fits the threat model. Caveat: I verified the strategy-side accounting but did not fully trace the CDO-side closed→restart transitions (`restoreOperations`/`startEpoch` in `IdleCDOEpochVariant`/`Prefunded`) to confirm a reachable reopen path, so reachability should be confirmed in the PoC; if `epochEndDate == 0` is truly terminal for a given deployment, severity drops to defense-in-depth.

### Recommendation
Reject or segregate requests made while `epochEndDate == 0` that cannot be funded: either revert in `requestWithdraw` when `isClosed` (unless the post-default path applies), or increment `pendingWithdraws` regardless and let the restart funding logic account for it. Add an invariant test asserting `sum(withdrawsRequestsByEpoch)` is always backed by funded underlying or `pendingWithdraws` across closed→restart transitions.

### Proof of Concept
```solidity
// forge test --match-test testClosedPoolRequestStealsFundedReceipts
function testClosedPoolRequestStealsFundedReceipts() public {
  // Setup: credit vault + IdleCDOEpochVariant, honest user U1 deposits and
  // requests withdraw in epoch N; epoch runs and stopEpoch funds pendingWithdraws.
  vm.prank(address(cdo));
  vault.requestWithdraw(amount1, U1, principal1); // epoch N
  _runEpochAndStop();                              // U1's request is now funded, epochNumber = N+1

  // Pool is closed/emergency: epochEndDate == 0 (e.g. after _emergencyShutdown
  // or close-pool mode). Attacker (any tranche holder) submits a request now.
  vm.prank(address(cdo));
  vault.requestWithdraw(amount2, attacker, principal2);
  assertEq(vault.pendingWithdraws(), 0);           // NOT counted
  assertEq(vault.withdrawsRequests(attacker), amount2); // but receipt exists

  // Honest manager/guardian restores operations and runs epochs.
  _restoreOperations();
  _runEpochAndStop();                              // epochNumber = N+2 > N+1

  // Attacker claims first: paid at par from U1's funded underlying.
  vm.prank(address(cdo));
  uint256 got = vault.claimWithdrawRequest(attacker);
  assertEq(got, amount2);

  // U1's fully funded receipt now reverts on insufficient balance.
  vm.prank(address(cdo));
  vm.expectRevert();
  vault.claimWithdrawRequest(U1);
}
```
