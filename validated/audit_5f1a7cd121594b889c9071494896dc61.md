### Title
EI-authenticated principal is misidentified as a real user, bypassing the "EIs not allowed" numeric-ID guard and enabling cross-job run triggering - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController.Create` intends to block External-Initiator (EI) credentials from triggering jobs by numeric ID, using `_, isUser := auth.GetAuthenticatedUser(c)` as the gate. However, `AuthenticateExternalInitiator` stores a synthetic `*clsessions.User{Role: clsessions.UserRoleRun}` under the same `SessionUserKey` used for real users, so `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests too. This defeats the intended `isUser` check and lets any EI credential trigger `RunJobV2` for an arbitrary numeric job ID, not just the job(s) it is registered for.

### Finding Description
The comment in `Create` states the intent clearly: "only users are allowed to run jobs using int IDs - EIs not allowed" [1](#0-0) . That gate relies entirely on `auth.GetAuthenticatedUser(c)` returning `ok=false` for EI principals.

But `AuthenticateExternalInitiator` explicitly sets the same session key used for users: [2](#0-1) 
```
c.Set(SessionExternalInitiatorKey, ei)

// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
// of 'run' (required to trigger job runs)
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
```
`GetAuthenticatedUser` simply reads `SessionUserKey` and type-asserts it to `*clsessions.User`: [3](#0-2) 

Because the EI auth path populates `SessionUserKey` with a real (synthetic) `*clsessions.User`, `isUser` evaluates to `true` for EI-authenticated requests, exactly the case the code comment says should be rejected. The request then flows into the branch that parses the numeric job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` unconditionally for whatever `jobID` was supplied in the URL [4](#0-3) , with no check that the authenticated EI is registered/scoped to that specific job.

Historically, EI-triggered runs were scoped through the Webhook job type's `ExternalInitiatorWebhookSpecs` relation (matching EI to a specific job via UUID). That job type has been removed per the comment in `Create` ("Webhook runs used external job UUIDs; that job type has been removed") [5](#0-4) , and the only remaining guard against EI-triggered numeric-ID runs is the flawed `isUser` check — which the shared `SessionUserKey` mechanism silently defeats.

The route is reachable through the authenticated v2 API group that layers `auth.Authenticate` with `AuthenticateExternalInitiator` among its methods and `RequiresRunRole` as the role gate; since the EI's synthetic user has `Role: UserRoleRun`, it also passes `RequiresRunRole`'s check (`role != View`) [6](#0-5) .

### Impact Explanation
An attacker holding only a valid External Initiator credential (scoped, by design, to a specific job/webhook) can trigger pipeline runs for **any** job on the node by guessing/enumerating numeric job IDs, because `RunJobV2` is called with no per-EI job-scope check. This is an authorization/scope-bypass leading to unauthorized job execution — matching Chainlink's "unauthorized job run" bounty impact class. Depending on what the target job does (e.g., write to external systems, submit transactions), this can cause unintended fund movement or unauthorized on-chain actions triggered outside the EI's intended scope.

### Likelihood Explanation
- Precondition: possession of any valid EI access key/secret pair (the lowest-privilege credential class explicitly in scope as attacker capability).
- No additional role or admin access needed — the synthetic user role `UserRoleRun` is sufficient to pass `RequiresRunRole`.
- Job IDs are sequential integers, so cross-job guessing is trivial and repeatable.
- The exploit requires only a single authenticated HTTP POST; deterministic and fully repeatable.

### Recommendation
Do not attach a `SessionUserKey` for EI-authenticated requests, or use a distinct sentinel/type that is not confusable with `*clsessions.User` for real users. In `PipelineRunsController.Create`, explicitly reject the request if `auth.GetAuthenticatedExternalInitiator(c)` returns `ok=true`, regardless of what `SessionUserKey` contains, e.g.:
```go
if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI {
    jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("bad job ID"))
    return
}
```
Additionally, consider removing the `c.Set(SessionUserKey, ...)` call from `AuthenticateExternalInitiator` and instead have role checks (`RequiresRunRole`) consult a dedicated EI-role accessor rather than piggybacking on the user session key.

### Proof of Concept
Go handler-level integration test plan (in `core/web/pipeline_runs_controller_test.go` style):
1. Set up a test app with two jobs, Job A and Job B (any non-webhook type supporting `RunJobV2`, e.g., a keeper/cron/direct-request spec).
2. Create an External Initiator credential (`bridges.ExternalInitiator`) not associated with Job B (EI scoping only ever existed for now-removed Webhook specs, so any EI qualifies as "not scoped to Job B").
3. Authenticate as the EI using `static.ExternalInitiatorAccessKeyHeader` / `SecretHeader`.
4. POST `/v2/jobs/<jobB_id>/runs` with the EI credentials.
5. Assert:
   - Expected (per comment "EIs not allowed"): response is `422 Unprocessable Entity` and `RunJobV2` mock is never invoked.
   - Actual (bug): response is `200 OK` with a created pipeline run resource, and `RunJobV2` is called with Job B's ID — proving cross-job triggering via an EI credential not scoped to Job B.
6. Repeat with a numeric ID for Job A (the EI's "intended" job, if any association existed) to show no differentiation is made between jobs — confirming the missing scope check.
