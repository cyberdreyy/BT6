### Title
Interactive terminal shell does not inherit job BuildDir, escaping job workspace confinement - (File: executors/shell/shell_terminal.go)

### Summary
`executor.TerminalConnect` in `executors/shell/shell_terminal.go` builds the interactive terminal's shell process with `exec.Command(s.BuildShell.Command, s.BuildShell.Arguments...)` and never sets `cmd.Dir`. Unlike the main build script—which is generated with explicit `cd`/working-directory instructions embedded in the shell script itself—the terminal shell has no such instruction, so it starts in whatever directory the `gitlab-runner` daemon process currently has as its working directory, not the job's `BuildDir`.

### Finding Description
`TerminalConnect` (executors/shell/shell_terminal.go:38-56) constructs the pty-backed shell: [1](#0-0) 
There is no `cmd.Dir = s.Build.RootDir` (or similar) assignment anywhere in this function, and a repo-wide search of `executors/shell/*.go` shows no other file sets `cmd.Dir` for the terminal path either—the only matches for `cmd.Dir` in the shell executor package are in the test file, not production code.

By contrast, the actual job script that runs the user's CI commands is generated as a shell script containing its own `cd` into the build directory (the shell writer embeds working-directory changes textually into the script content), so the *build script's* effective cwd is correct even though `exec.Command` for it also may not set `cmd.Dir` explicitly—the confinement there comes from script content, not from `cmd.Dir`. The interactive terminal path, however, invokes the raw shell binary (`s.BuildShell.Command`) directly via pty with no script wrapper and no `cmd.Dir`, so it has no equivalent mechanism to `cd` into `BuildDir`.

The call path is exactly as described: `session.Session.execHandler` (session/session.go:146-191) → `s.newTerminalConn` (session/session.go:200-216) → `s.interactiveTerminal.TerminalConnect()` → `executor.TerminalConnect` (executors/shell/shell_terminal.go:38) → `exec.Command(...)` → `pty.Start(cmd)`. None of the intermediate layers (`execHandler`'s auth check via `s.Token`, `newTerminalConn`'s `connectionInUseError` guard) validate or set a working directory—they only gate access and connection reuse, not filesystem confinement.

### Impact Explanation
An attacker with a valid terminal session token (obtained via the job's terminal URL, which GitLab exposes to any user permitted to view/debug that job) can open an interactive shell that starts in the runner daemon's process cwd instead of the job's isolated `BuildDir`. Depending on how the runner service/daemon was launched (e.g., `/`, `/etc/gitlab-runner`, home directory, or another directory containing unrelated files/other jobs' leftover state), this can expose files outside the intended build root to browsing, reading, or writing—an escape from the expected build/workspace confinement invariant for the shell executor.

### Likelihood Explanation
This is trivially reachable by any user who can trigger a job with an interactive web terminal enabled (a standard, user-facing GitLab feature, not an admin-only capability) and has permission to open that job's terminal. No special privilege escalation, malicious peer, or admin compromise is required—only the documented WebSocket session token precondition already stated in the prompt. It is deterministically reproducible: the shell's initial cwd is always the runner process's cwd unless the host administrator happens to run the runner service from within the build root (uncommon).

### Recommendation
Set `cmd.Dir` explicitly in `TerminalConnect` to the job's build directory, e.g. `cmd.Dir = s.Build.FullProjectDir()` (or the equivalent `BuildDir`/`RootDir` field used elsewhere in the shell executor), mirroring the confinement applied to the main build script. Add a regression test asserting that a `pwd` command issued over the terminal session returns the same path as the build's `BuildDir`.

### Proof of Concept
Go integration test in `executors/shell/shell_integration_test.go`:
1. Configure a build with `BuildDir` set to a known temp directory (e.g., `t.TempDir()`).
2. Start the shell executor and call `TerminalConnect()` directly (or drive it through `session.Session.execHandler` over a mocked WebSocket).
3. Write `pwd\n` (or `cd` on Windows equivalents) to the resulting `shellFd` and read back the output.
4. Assert the returned path equals `build.BuildDir` — currently it will equal the test process's working directory instead, demonstrating the escape.

	if s.Shell().Shell == "pwsh" {
