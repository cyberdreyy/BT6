### Title

Loss-adjusted withdrawal receipts are permanently frozen by a later default - ([contracts/strategies/idle/IdleCreditVault.sol](https://github.com/ThankGod76/idle-tranches--016/blob/main/contracts/strategies/idle/IdleCreditVault.sol))

### Summary

`claimWithdrawRequest` misclassifies an already-funded, loss-adjusted receipt as an unfunded defaulted receipt when the next epoch defaults in the same strategy epoch number. The defaulted-claim path subtracts the receipt basis from `pendingWithdraws`, which was already cleared when the earlier loss-adjusted claim was funded, causing an underflow and permanently blocking the funded claim path.

### Finding Description

`claimWithdrawRequest` first calls `_claimDefaultedWithdrawRequest` whenever `defaultRecoveryFinalized` is true, before it reaches `_claimLossAdjustedWithdrawRequest`. [1](#0-0)  A request made during the buffer is tagged with the current `epochNumber`; the subsequent epoch uses that same number because `deposit` increments `epochNumber` only on a successful stop. [2](#0-1)  A stop with `_lossAmount` can clear aggregate `pendingWithdraws` and store a haircut under that same epoch, while the user receipt remains claimable through `lossRecoveryPriceByEpoch`. [3](#0-2) 

If the next epoch later defaults before the user claims, `defaultRecoveryEpoch` is that same epoch number and `_claimDefaultedWithdrawRequest` clears the funded receipt as if it were unfunded default basis. [4](#0-3)  It then executes `pendingWithdraws -= claimBasis`, but the funded basis was already set to zero by `collectWithdrawFunds`, so the call reverts before the later loss-adjusted claim can execute. [5](#0-4)  This is analogous to the kernel bug class: the code does not distinguish two operation types sharing the same identifier—an already-funded loss receipt and an unfunded defaulted receipt.

### Impact Explanation

An unprivileged tranche holder can leave a funded loss-adjusted receipt unclaimed, after which an honest borrower default permanently freezes that receipt. `claimWithdrawRequest` always executes the misclassified defaulted branch first and reverts on the `pendingWithdraws` underflow, so the user cannot reach `_claimLossAdjustedWithdrawRequest`, even though its payout is already backed by strategy-held underlyings. [6](#0-5)  The loss is the full funded payout, `claimBasis * lossRecoveryPrice / 1e18`, and it remains unavailable indefinitely.

### Likelihood Explanation

The setup only requires the user to request withdrawal during a buffer, the manager to settle that epoch with a partial loss, and the borrower to default on the following epoch before the user claims. None of these actions require the user to control a privileged role. The attacker can directly create the exposure by holding tranche tokens and simply delaying the ordinary claim.

### Recommendation

Track whether an epoch's pending-receipt basis was already funded. For example, persist a separate `fundedWithdrawsByEpoch` amount when `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch`, or record a flag that causes `_claimDefaultedWithdrawRequest` to skip epochs whose `lossRecoveryPriceByEpoch` is nonzero. `claimWithdrawRequest` should process loss-adjusted funded receipts independently of `defaultRecoveryEpoch`, and `pendingWithdraws` must only be reduced by genuinely unfunded default basis.

// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "./IdleCreditVault.t.sol";

contract LossAdjustedReceiptFrozenByDefault is IdleCreditVaultTest {
  function testFundedLossReceiptFrozenByLaterDefault() external {
    uint256 depositAmount = 100_000 * ONE_SCALE;
    uint256 minted = idleCDO.depositAA(depositAmount);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Attacker requests withdrawal during the buffer, in strategy epoch N.
    uint256 receipt = cdoEpoch.requestWithdraw(minted / 2, address(AAtranche));

    // Next epoch starts and ends with a partial loss. The receipt remains in
    // strategy epoch N and collectWithdrawFunds clears aggregate pendingWithdraws.
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, epochDuration, receipt / 10);

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 lossEpoch = vault.lastWithdrawRequest(address(this));
    assertEq(vault.pendingWithdraws(), 0);
    assertGt(vault.lossRecoveryPriceByEpoch(lossEpoch), 0);

    // Honest borrower fails to fund the following epoch. epochNumber is not
    // incremented because stopEpoch reverted before strategy.deposit().
    _startEpochAndCheckPrices(2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);
    assertTrue(cdoEpoch.defaulted());

    // Manager/owner finalizes the default. The prior funded receipt was not
    // included in pending default basis because pendingWithdraws is zero.
    deal(defaultUnderlying, recoverySource, 1_000 * ONE_SCALE);
    vm.prank(recoverySource);
    IERC20Detailed(defaultUnderlying).approve(address(vault), 1_000 * ONE_SCALE);
    vm.prank(manager);
    cdoEpoch.finalizeDefault(1_000 * ONE_SCALE, recoverySource);

    // The claim is misclassified as defaulted-epoch basis. pendingWithdraws
    // underflows, so the already-funded loss-adjusted claim is unreachable.
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
  }
}

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);

  /// @notice Claim a stopEpochWithDuration loss-adjusted withdraw receipt.
  /// @param _user address of the user
  /// @return amount amount paid from funded strategy underlyings
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
