### Title
`check_parent_tenure_choice` mistreats a missing local `approved_time` as "elapsed = 0", letting a stale reorg attempt be treated as poorly-timed and approved - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg a tenure that already produced a block. It bases that decision on `proposal_to_sortition = sortition_state_received_time - approved_at`. When the local `BlockInfo.approved_time` for the reorged tenure's first block is `None`, the code substitutes a hard-coded `0` for the elapsed time instead of leaving the timing unknown, which unconditionally satisfies `elapsed < first_proposal_burn_block_timing` and approves the reorg.

### Finding Description
In `check_parent_tenure_choice`: [1](#0-0) 

```rust

    let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {

    } else {
```

By this point `local_block_info` is `Some` — `signer_db.get_first_approved_block_in_tenure` found a record for the reorged tenure's first block (via `approved_time IS NOT NULL OR signed_self ... OR signed_group ...`, per the doc note at [2](#0-1) ). It is still possible for that record to carry `approved_time == None` while `signed_group` is set — i.e. this signer never pre-committed/approved that block itself (e.g., it restarted, was offline, joined mid-cycle, or missed the pre-commit but later observed the group signature/global acceptance). In that case the code does not compute the real elapsed time (which the recommendation in the referenced bug class calls for): it silently defaults to `0`, which is always `< first_proposal_burn_block_timing`, so the branch always concludes "the block was poorly timed, allowing the reorg" — regardless of how long the reorged tenure had actually been established.

This is the exact bug-class described in the report: a timing/elapsed computation with an unhandled edge case that silently substitutes a value guaranteeing the "happy path" branch instead of reflecting reality, producing a materially different (and wrong) decision precisely when the input is missing rather than truly recent.

The impact is on `check_parent_tenure_choice`'s consumers: `SortitionsView::check_proposal` (v1) at [3](#0-2)  and `validate_tenure_change_payload` at [4](#0-3) , which gate `RejectReason::ReorgNotAllowed`. A signer whose local record for the reorged block lacks `approved_time` will incorrectly pass this gate and go on to sign a tenure-change block that illegitimately reorgs an established tenure, when other signers (who do have `approved_time` populated, e.g. because they personally pre-committed) would correctly reject the same proposal via the real elapsed-time computation. This directly breaks the "approved-parent vs canonical" equality across signers: some signers sign a reorging block that the `first_proposal_burn_block_timing` policy is meant to forbid, while others reject it, producing a signature over a non-canonical/disallowed reorg.

### Impact Explanation
This meets the Critical bar: a signer can be induced to place its signature over a block that performs a disallowed reorg of an already-established tenure (more than the intended "poorly-timed" grace window), i.e., signing a non-canonical/conflicting block relative to the network's reorg policy. Because the decision also triggers `record_superseded_tenure` (`mark_tenure_superseded`) at [5](#0-4) , this signer additionally starts treating its own prior signature over the superseded tenure's block as no longer a conflict, compounding the erroneous state.

### Likelihood Explanation
The `approved_time == None` condition is not exotic: any signer that restarted after pre-commit but before local signing, was offline for the original block's pre-commit round, or simply never crossed 70% pre-commit weight locally while still holding a `get_first_approved_block_in_tenure` record via `signed_group`/`signed_self`, would hit this path. In periods where signer restarts, upgrades, or network partitions occur — realistic on a live network with dozens of independently operated signers — the fallback triggers routinely, not merely in a contrived corner case, making divergence in reorg decisions plausible during ordinary operations.

### Recommendation
Do not default the elapsed time to `0` when `approved_time` is missing. Either:
- Treat "no local approval timestamp" as "insufficient local information to compute timing" and fail closed (reject the reorg, consistent with the sibling branch at lines 234–245 which already rejects when `get_first_approved_block_in_tenure` returns `None` entirely), or
- Fall back to a timestamp that reflects when the block was actually first known locally (e.g., `proposed_time`, which is always set) rather than an unconditional `0`, and clearly document that this is an approximation, not a substitute for the real elapsed time.

### Proof of Concept
1. Signer S restarts (or otherwise misses the pre-commit round) after tenure T's first block B is proposed, but later learns of B's existence with `signed_group` set and `approved_time == None` (e.g., via a `NewBlock`/global-acceptance event that populates the record without going through `mark_pre_committed`/`mark_locally_accepted`).
2. A significant amount of time passes — well beyond `first_proposal_burn_block_timing` — during which tenure T remains canonical and established.
3. A malicious/faulty miner proposes a tenure-change block reorging T, well after the RBF grace window has expired.
4. In `check_parent_tenure_choice`, signer S looks up `local_block_info` for T's first block, finds `approved_time == None`, and computes `proposal_to_sortition = 0`, which is `< first_proposal_burn_block_timing`; S concludes the reorg is permitted and marks T as superseded.
5. Other signers, who do have `approved_time` set (having pre-committed to B themselves), correctly compute the real (large) elapsed time and reject the reorg via `RejectReason::ReorgNotAllowed`.
6. Signer S diverges from the rest of the set: it signs (or is prepared to sign) a tenure-change block that the majority correctly rejects as an out-of-policy reorg — an equivocation-style split over whether the reorg is canonical.
