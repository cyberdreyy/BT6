### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing execution below live threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts a request as approved once `confirmations.len() + 1 >= num_confirmations`, where `confirmations` is a `HashSet<String>` of member identifiers that previously called `confirm`. `delete_member` only purges confirmations/requests that the removed member *originally submitted* via `add_request` — it never scrubs that member's identifier from the `confirmations` set of other pending requests they had merely *confirmed*. As a result, a confirmation cast by a member who is later removed from the multisig still counts toward the threshold, letting a request execute with fewer genuinely-live approvals than `num_confirmations` requires.

### Finding Description
`confirm()` is entirely on-chain and live-signature based (no detached/offline signatures, unlike the referenced report), but it has an analogous "stale approval" defect: the confirmation-counting binding (`confirmations counted == live members who approved`) is broken once membership changes mid-flight.

- `add_request` records a pending request tied to a `member` (the submitter) and creates an empty confirmation set for it: [1](#0-0) 
- `confirm` looks up the confirmation set and simply checks length against `num_confirmations`, without re-validating that every already-recorded confirmer is still in `self.members`: [2](#0-1) 
- `delete_member` removes only the requests submitted by the removed member (matched via `r.member == member`), and clears `num_requests_pk` for that member, but does **not** iterate over `confirmations` of requests submitted by *other* members to strip the removed member's prior approvals: [3](#0-2) 

So the equality that should hold — "confirmations counted == confirmations by currently-live members" — is violated: a confirmation recorded while a member was live remains valid and counted even after that member is deleted from `self.members`.

### Impact Explanation
This is Critical impact per the custody-binding categories: it allows a multisig request (e.g. a `Transfer` of NEAR held by the multisig account, or an `AddKey`/`FunctionCall`) to be executed with fewer live, current approvals than the configured `num_confirmations` threshold. Funds controlled by the multisig account can be moved by a set of members that does not actually meet the intended K-of-N live-member threshold at execution time.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires normal governance operations to interleave in a specific order — a member confirms a pending request, then that same member is later removed from the multisig (a legitimate `DeleteMember` action), and the pending request is still around and gets pushed to threshold by remaining members. This is a plausible operational sequence for any multisig with membership changes and no requirement to re-confirm the whole set from scratch, especially since there is no expiry on requests other than the 15-minute deletion cooldown floor.

### Recommendation
When executing/counting confirmations in `confirm()`, filter the stored `confirmations` set down to members that are currently present in `self.members` before comparing against `num_confirmations` (or, simpler, have `delete_member` iterate all `requests`/`confirmations` entries and remove the deleted member's identifier from every confirmation set, not just from requests they submitted). Equivalently, revalidate live membership of every recorded confirmer at the moment the threshold check is performed in `confirm`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled account).
3. `B` calls `confirm(R)` → `confirmations = {B}`.
4. Members separately submit and approve a `DeleteMember { member: B }` request (a normal governance action) via `add_request_and_confirm` reaching 3 confirmations — `delete_member` runs: it only scrubs requests where `r.member == B` (i.e., requests *B submitted*), not `R`, which `A` submitted. `R`'s `confirmations = {B}` remains untouched even though `B` is no longer in `self.members`.
5. `A` calls `confirm(R)` → `confirmations = {B, A}` (len 2).
6. `C` calls `confirm(R)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → `execute_request` runs the `Transfer`.
7. Result: `R` executed although only `A` and `C` are actually live members who approved it — `B`'s stale confirmation, cast before removal, was counted — i.e., only 2 of the required 3 *live* approvals actually back the transfer, breaking the K-of-N live-member threshold guarantee.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
