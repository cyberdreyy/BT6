### Title
Unprivileged ERC4626 vault user can indefinitely block `stopEpoch` by draining vault liquidity, freezing all tranche funds in a running epoch - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
Analog to CVE-2020-14619 (a remotely-triggerable, low-privilege hang/DoS): in the programmable-borrower deployment, `ProgrammableBorrower.onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable` whenever the configured ERC4626 vault cannot deliver the withdrawal `shortfall`, even though the shares remain economically backed. Any unprivileged user of that vault (e.g., a borrower draining available liquidity on a Morpho-style market) can therefore make `IdleCDOEpochVariant.stopEpoch` revert every time it is called, keeping `isEpochRunning = true` past `epochEndDate` and freezing all pending withdraw requests and tranche redemptions for as long as the liquidity drain is maintained.

### Finding Description
`stopEpoch` → `_stopEpoch` → `_beforeStopEpoch` calls `IProgrammableBorrower.onStopEpoch(_amountRequired, ...)`. In `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:239-253):

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The bail-out to the default path (`return true` → later `transferFrom` fails → default) only fires when the vault shares are *economically* insufficient (`shortfall > _currentVaultAssets()`, which is `convertToAssets` of share balance). But `vault.withdraw` can also revert when shares are fully backed yet *liquid* underlying is temporarily unavailable — exactly what happens on Morpho/ERC4626 lending vaults when utilization is high. In that case the revert propagates up through `_beforeStopEpoch` and `stopEpoch`, so the whole stop transaction reverts while the epoch keeps running (the repo's own invariant test encodes this: "retryable stop revert should keep epoch running", test/foundry/ProgrammableBorrowerEpochInvariant.t.sol:318-323).

An unprivileged attacker who is a user of the programmable borrower's ERC4626 vault (an explicitly allowed attacker class) can:
1. Wait for the epoch to run and for IdleCDO to deposit pool funds into the vault via `onStartEpoch` → `_depositToVault` (ProgrammableBorrower.sol:214-216, 378-385).
2. Borrow (or withdraw, if a large LP) essentially all *liquid* underlying from the vault, so `vault.withdraw(shortfall)` reverts while `convertToAssets` still values the shares above the shortfall.
3. Keep utilization high (maintain the borrow / immediately re-borrow after repayments) so every `stopEpoch`/`stopEpochWithDuration` call after `epochEndDate` reverts.

None of the existing guards stop this:
- `_checkNotAllowed(!isEpochRunning || block.timestamp < epochEndDate || _pendingInstant() != 0 || ...)` in `_stopEpoch` (IdleCDOEpochVariant.sol:338-351) does not gate on vault liquidity.
- `emergencyExitVault` (ProgrammableBorrower.sol:361-372) also calls `vault.redeem`, which hits the same liquidity wall, so the manager cannot unstick it.
- The default path is unreachable: `shortfall > _currentVaultAssets()` is false because share value is intact, so it reverts instead of defaulting.
- `onDefault` explicitly avoids `convertToAssets` during stress (lines 289-301), acknowledging the vault valuation/liveness coupling, but the stop path has no equivalent escape.

### Impact Explanation
Broken invariant: epoch state-machine liveness — a running epoch must be stoppable after `epochEndDate`. While the drain persists:
- `stopEpoch`/`stopEpochWithDuration` revert unconditionally; `isEpochRunning` stays true, `epochNumber` never advances.
- All normal withdraw requests in `IdleCreditVault` (`requestWithdraw`/`claimWithdrawRequest`, which require `epochNumber > lastWithdrawRequest`, IdleCreditVault.sol:326-328) are unclaimable; queued withdrawals via `IdleCDOEpochQueue.processWithdrawRequests` cannot be processed.
- Instant-withdraw funding (`getInstantWithdrawFunds`) and new-epoch start are blocked; no depositor can exit.
- Quantified loss: 100% of pool TVL (tranche principal + accrued interest + pending receipts) is locked for the duration of the attack; duration is attacker-controlled and indefinite as long as they service a vault borrow. Cost to the attacker is only the vault's borrow interest on the drained liquidity — and on a lending vault that interest is paid *to* suppliers (including the pool's own position), making the griefing asymmetric.

This is a temporary freezing of user funds with a quantified (full-TVL) impact, meeting the acceptance bar; it is not a gas/unbounded-loop DoS — it is a liveness failure of the core epoch transition driven by an unprivileged external actor.

### Likelihood Explanation
Medium. Requirements: a live programmable-borrower deployment where pool funds are parked in a borrowable ERC4626 vault (the codebase is built for exactly this — MetaMorpho/Steakhouse USDC vaults appear in the fork tests). Any borrower on that shared market can push utilization to ~100% at any time; this requires capital but no privileged role, no KYC, and no coordination with the honest borrower/manager. The attack is repeatable at every epoch boundary and front-runnable each time liquidity returns.

Uncertainties I could not fully verify within the iteration budget: the exact `_beforeStopEpoch` body in `IdleCDOEpochVariant.sol`/`IdleCDOEpochVariantPrefunded.sol` (whether `onStopEpoch` is invoked directly or wrapped in try/catch — the revert would only propagate if it is a plain call, which the `returns (bool)` signature and the invariant test's "retryable stop revert" behavior strongly suggest); and whether a manager-side fallback exists (e.g., `setVault` to a liquid vault — ProgrammableBorrower.sol allows `setVault` by owner/manager, which would eventually unstick the pool but only after a full stuck period and doesn't negate the bug).

### Recommendation
Make the stop path robust to vault illiquidity rather than reverting:
- In `onStopEpoch`, treat a failed `vault.withdraw` the same as economic insufficiency for liveness purposes: attempt `vault.withdraw(vault.maxWithdraw(address(this))` (pull what's liquid), emit an event, and return whether the *covered* amount is met so IdleCDO can either proceed with partial funds or take the explicit default/loss path (`stopEpochWithDuration(..., _lossAmount)`) instead of reverting.
- Alternatively, let the manager pass a `maxWait/force` flag into `stopEpoch` that downgrades `StopEpochVaultLiquidityUnavailable` into the existing loss-socialization flow so the epoch can always terminate after `epochEndDate`.
- Document that share solvency (`convertToAssets`) and withdrawable liquidity (`maxWithdraw`) are distinct conditions and must be checked separately.

### Proof of Concept
Foundry fork test (against the real Morpho vault used in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, e.g. `STEAKHOUSE_USDC`):

```solidity
function testStopEpochDosByVaultLiquidityDrain() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);              // user deposits; funds parked in vault at startEpoch
    _startEpochAndCheckPrices(0);
    assertGt(morphoVault.balanceOf(address(programmableBorrower)), 0);

    // Attacker: unprivileged Morpho borrower drains liquid underlying from the shared market(s)
    address attacker = makeAddr("vaultUser");
    deal(morphoCollateral, attacker, type(uint256).max);
    vm.startPrank(attacker);
    morpho.supplyCollateral(mktParams, morpho.market(mktId).totalSupplyAssets /* enough */, attacker, "");
    morpho.borrow(mktParams, morpho.market(mktId).totalBorrowAssets /* all liquid */, 0, attacker, attacker);
    vm.stopPrank();
    assertLt(morphoVault.maxWithdraw(address(programmableBorrower)),
             morphoVault.convertToAssets(morphoVault.balanceOf(address(programmableBorrower))));

    // Epoch ends; manager tries to stop
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Still running: withdrawals blocked indefinitely while attacker maintains utilization
    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
}
```

Both the revert and the non-default, still-running state are asserted; repeating the borrow after any liquidity returns keeps the freeze alive, demonstrating the indefinite hang.
