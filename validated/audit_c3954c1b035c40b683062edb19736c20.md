The "family" analog likely maps to per-epoch receipt accounting that only inspects `lastWithdrawRequest` / a single epoch rather than all pending receipt epochs. I need to check the ordering of `epochNumber` increment vs `collectWithdrawFunds` in `stopEpoch`.### Title
Loss haircut on pending withdraw receipts is keyed to the post-increment epoch, so receipts escape `lossRecoveryPriceByEpoch` and are paid at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.collectWithdrawFunds` records a stop-epoch loss haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is incremented earlier in the same `stopEpoch` call by `deposit()`, while user receipts were stamped with the pre-increment request epoch (`lastWithdrawRequest`, `withdrawsRequestsByEpoch`). The guard and the claim path only ever look up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` — like the Tor guard-selection bug that considered only the relay and not its family, the haircut accounting considers only the *current* epoch counter and not the *request* epoch where the receipts actually live. Result: every pending receipt in a loss epoch is paid at par from under-funded reserves.

### Finding Description
- Receipts are stamped at request time: `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` in `requestWithdraw` (`IdleCreditVault.sol:260-294`).
- `epochNumber` is incremented inside `deposit()` when `isEpochRunning()` is still true, i.e. during `stopEpoch` (`IdleCreditVault.sol:607-610`).
- In `IdleCDOEpochVariant._stopEpoch`, `getFundsFromBorrower(...)` (which routes repaid principal through `strategy.deposit`, bumping `epochNumber`) executes at line 408, and `_strategy.collectWithdrawFunds(_pendingWithdraws)` runs after it at line 410.
- `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` — the **bumped** epoch (`IdleCreditVault.sol:421`).
- The new-request guard checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the **request** epoch (`IdleCreditVault.sol:261-271`), so it never sees the stored price and never blocks.
- `_claimLossAdjustedWithdrawRequest` also reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol:790-791`), gets 0, and returns 0; the claim falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` **at par** via `_transferFundedClaim` (`IdleCreditVault.sol:338-349`).
- Meanwhile `collectWithdrawFunds` already zeroed `pendingWithdraws` after pulling only the haircutted `_amount` from the CDO, so the strategy is under-funded by exactly the intended loss.

### Impact Explanation
When `stopEpochWithDuration` (or a borrower under-repayment) produces a loss on pending receipts, every receipt holder claims 100% instead of `lossRecoveryPrice`. The deficit is absorbed by whoever claims last (other pending-receipt users whose funded claims revert on insufficient balance) and/or by `defaultRecoveryReserve`, which `_transferFundedClaim` prefers not to touch only up to the reserve check — a funded claim can drain reserves earmarked for default-recovery claimants. Direct theft of other users' funded claims, quantified as `pendingBasis - fundedAmount` per loss epoch.

### Likelihood Explanation
Requires a manager-called `stopEpochWithDuration` with `_lossAmount > 0` (an honest-privileged action that is part of normal operations during borrower distress) while pending receipts exist. No attacker precondition beyond holding a pending withdraw receipt — any KYC'd tranche holder requesting withdraw in the loss epoch qualifies. Every affected claim pays out over par deterministically; even honest early claimers extract value before the under-funding is discovered.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the request epoch, not the post-increment counter: in `collectWithdrawFunds`, write `lossRecoveryPriceByEpoch[epochNumber - 1]` (or snapshot `epochNumber` before `deposit()` bumps it), matching the `lastWithdrawRequest` / `withdrawsRequestsByEpoch` keying used by `requestWithdraw` and `_claimLossAdjustedWithdrawRequest`. Add a regression test that requests a withdraw, runs a loss `stopEpochWithDuration`, and asserts the claim pays `basis * lossRecoveryPrice / 1e18`.

### Proof of Concept
```solidity
function testLossHaircutEpochMismatch() external {
    // setup: depositAA(amount), start epoch 0, requestWithdraw(trancheBal)
    uint256 trancheBal = IERC20(AAtranche).balanceOf(address(this));
    uint256 principal = cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));
    uint256 reqEpoch = IdleCreditVault(address(strategy)).lastWithdrawRequest(address(this));

    _startEpochAndCheckPrices(1);

    // manager stops epoch with a loss on pending receipts
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 loss = pending / 2;
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(newApr, 0, epochDuration, loss);

    // haircut was stored under the bumped epoch, not the request epoch
    assertEq(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(reqEpoch), 0);
    assertGt(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(reqEpoch + 1), 0);

    // claim pays full principal instead of half
    uint256 balBefore = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(address(this)) - balBefore, principal);
    // expected: principal * lossRecoveryPrice / 1e18 ~= principal / 2
}
```
