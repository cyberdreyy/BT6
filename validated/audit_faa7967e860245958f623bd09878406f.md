### Title
Any unprivileged lender can permanently wedge `stopEpoch` by leaving an APR-0 withdraw request pending when the APR is later raised — `prepareStopEpochWithApr0` reverts on every subsequent epoch stop (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog to ALPINE-CVE-2026-28388 ("processing a delta CRL without checking that a required field is present causes a crash"): `prepareStopEpochWithApr0` requires `unscaledApr == 0` whenever `apr0TotalPrincipal != 0`, and reverts otherwise instead of settling or clearing the bucket. Since `apr0TotalPrincipal` is only zeroed inside `prepareStopEpochWithApr0` (or via default-claim clearing in `_clearWithdrawClaimForEpoch`), a single unprivileged `requestWithdraw` made during a zero-APR buffer permanently arms a stopEpoch revert that fires as soon as the manager performs a routine APR change.

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `unscaledApr == 0` the request is routed to `_requestWithdrawApr0`, which increases the global `apr0TotalPrincipal` (`IdleCreditVault.sol:285-286`, `567-577`). At epoch stop, `IdleCDOEpochVariant._stopEpoch`/`stopEpochWithDuration` calls `prepareStopEpochWithApr0`, which unconditionally reverts if the bucket is non-empty and `unscaledApr != 0` (`IdleCreditVault.sol:499-508`). Two properties make this a trap rather than a benign guard:

1. `apr0TotalPrincipal` is never reduced by user claims — `_settleApr0` (`IdleCreditVault.sol:545-565`) and `_claimFundedWithdrawRequest` do not touch it; only `prepareStopEpochWithApr0` (`IdleCreditVault.sol:540`) or defaulted-claim clearing (`IdleCreditVault.sol:823-828`) modify it.
2. `unscaledApr` can be legitimately changed by the honest manager mid-epoch via `setAprsWithBuffer`/`setApr` (`IdleCreditVault.sol:217-235`), and is also updated every `stopEpoch` via `_setScaledApr` (`IdleCDOEpochVariant.sol:469-471`, `544-546`). No guard prevents raising the APR while an APR-0 request bucket is open.

Sequence:

1. A `stopEpoch(_newApr = 0)` leaves `unscaledApr == 0` for the upcoming epoch (valid configuration — the pool can run at 0% APR).
2. During the buffer, an attacker (any KYC-passing lender) calls `IdleCDOEpochVariant.requestWithdraw` with a dust amount. `requestWithdraw` routes to `_requestWithdrawApr0`; `apr0TotalPrincipal > 0`, `apr0Users[attacker].principalEpoch == epochNumber`.
3. `startEpoch` runs the epoch normally.
4. During (or at the end of) the epoch the manager changes the APR — e.g. calls `setAprsWithBuffer(5e18, …)` to adjust the yield, or a subsequent `stopEpoch` is invoked with `_newApr != 0` and `_setScaledApr` ordering makes `unscaledApr` non-zero. Either way `unscaledApr != 0` while `apr0TotalPrincipal != 0`.
5. Every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts inside `prepareStopEpochWithApr0` at `IdleCreditVault.sol:506-508`. The epoch can never end: lender funds, pending withdraw receipts, fees, and borrower repayment processing are all frozen. Recovery requires the manager to discover that `unscaledApr` must be forced back to `0` (sacrificing the epoch's yield) before any stop can succeed — and a front-running attacker can re-arm the bucket with another dust APR-0 request in the next buffer.

The guard at `IdleCreditVault.sol:506` does not protect solvency; it converts a missing/stale pre-condition (`apr0TotalPrincipal` left over from a previous APR regime) into an unconditional denial of the core epoch transition, mirroring the NULL-check omission in the advisory.

### Impact Explanation
Temporary freezing of all user funds and pending withdrawal receipts: while `stopEpoch` reverts, deposits cannot earn new epochs, `claimWithdrawRequest`/`claimInstantWithdrawRequest` cannot mature (epoch gating at `IdleCreditVault.sol:326`), and borrower repayments cannot be processed. The freeze persists until governance/manager resets `unscaledApr` to 0, and can be re-triggered by the attacker each cycle with a dust request, so in practice the pool can be kept frozen indefinitely or forced to run at 0% APR, destroying lender yield (loss of the full epoch interest on all TVL).

### Likelihood Explanation
Low-to-medium. It requires the pool to run an epoch at 0% APR (a supported mode — `requestWithdraw` explicitly branches on `unscaledApr == 0`) and an honest APR change while any APR-0 receipt is pending. The attacker cost is one dust `requestWithdraw`; no privileged collusion or default is needed. However, impact is temporary freezing only — a competent operator can unstick the pool by forcing APR back to 0 — so this is a liveness/griefing issue rather than direct theft.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert when `unscaledApr != 0`. Instead, settle the open bucket gracefully: either (a) treat APR-0 receipts as normal receipts for the stop (write them into `withdrawsRequests`/`withdrawsRequestsByEpoch` at the current epoch and zero `apr0TotalPrincipal`), or (b) zero `apr0TotalPrincipal` and record `apr0RateByEpoch[epochNumber] = 0` so receipts settle principal-only via `_settleApr0`. Additionally, consider decrementing `apr0TotalPrincipal` in `_settleApr0`/claim paths so the bucket cannot outlive the receipts it tracks.

### Proof of Concept
```solidity
// Foundry fork PoC sketch
// 1. Pool configured normally; manager stops epoch N with _newApr = 0.
vm.prank(manager);
cdoEpoch.stopEpoch(0, /* _newApr */ 0);

// 2. Attacker (KYC'd lender holding AA tranche) requests a dust withdrawal
//    during the buffer while unscaledApr == 0.
vm.prank(attacker);
cdoEpoch.requestWithdraw(1, address(AAtranche));
assertGt(strategy.apr0TotalPrincipal(), 0);

// 3. Epoch starts.
vm.prank(manager);
cdoEpoch.startEpoch();

// 4. Honest manager raises APR mid-epoch (routine ops via setAprsWithBuffer).
vm.prank(manager);
strategy.setAprsWithBuffer(5e18, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());

// 5. Epoch end arrives; every stopEpoch reverts -> pool frozen.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(5e18, 0);
```

Note: I verified the revert path at `contracts/strategies/idle/IdleCreditVault.sol:499-508` and the `apr0TotalPrincipal` lifecycle (`567-577`, `540`, `545-565`), and the manager-callable APR setter (`217-235`) and per-stop APR update (`IdleCDOEpochVariant.sol:469-471`, `544-546`). I could not fully trace the call site of `prepareStopEpochWithApr0` inside `_stopEpoch` (before line 400) to confirm it executes outside the `try { getFundsFromBorrower }` block at `IdleCDOEpochVariant.sol:408`; if it were inside that `try/catch`, the revert would be swallowed into `_handleBorrowerDefault` and the impact would shift from freezing to a spurious default — either outcome is harmful, but the PoC should confirm which branch is hit.
