Based on tracing the full construction path, the invariant claimed to be missing is actually enforced.

**Analysis of the guard mechanism:**

`VoteStateFrame::try_new` first reads a `u32` version tag via a checked cursor read, failing with `AccountDataTooSmall` if too few bytes exist [1](#0-0) . For each version, the corresponding `VoteStateFrameV{1_14_11,3,4}::try_new` sequentially reads each variable-length field (votes, root slot, authorized voters, epoch credits, etc.) using `solana_serialize_utils::cursor::read_u64/read_u8`, which return errors when insufficient bytes remain, and each list length is additionally clamped through `u8::try_from` [2](#0-1) .

Although `Cursor::consume()` itself does not bounds-check (it just advances `pos`), Rust's standard `Cursor::fill_buf` implementation uses `cmp::min(pos, len)`, so any subsequent `read_u8`/`read_u64` call after an over-consumption sees an empty slice and fails cleanly rather than panicking. This means every field boundary is implicitly validated by the *next* field's read call. The very last consumption (the trailing `BlockTimestamp`) has no subsequent read to validate it, which is why each frame's `try_new` explicitly checks `cursor.position() as usize <= bytes.len()` before returning `Ok` [3](#0-2) [4](#0-3) .

Because `node_pubkey_offset`, `commission_offset`, `votes_offset`, etc. are monotonically increasing constants/derived values that all precede `last_timestamp_offset` (the final validated cursor position), a successful `try_new` guarantees every field offset used later by `VoteStateView::node_pubkey()`, `commission()`, `votes_iter()`, etc. is `<= data.len()` [5](#0-4) [6](#0-5) .

This is directly exercised by existing tests that fuzz truncated buffers for every byte-length prefix and assert `AccountDataTooSmall`/`InvalidXxxLength` errors are returned instead of a successful `VoteStateView`, for all three versions [7](#0-6) [8](#0-7) [9](#0-8) .
