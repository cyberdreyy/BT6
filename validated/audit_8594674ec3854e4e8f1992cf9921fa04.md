### Title
External ERC4626 liquidity withdrawal can repeatedly force `stopEpoch` to revert and freeze pending withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower.onStopEpoch` treats an ERC4626 withdrawal failure as a hard revert whenever the vault shares nominally cover the requested shortfall. A third-party vault participant can remove or borrow the vault’s available liquidity before `IdleCDOEpochVariant.stopEpoch`, making the covered `vault.withdraw` call revert. Because the error bubbles through `stopEpoch`, the epoch remains running, pending withdrawal receipts are not funded, and the same failure can be repeated whenever liquidity becomes available again.

### Finding Description

During a running epoch in programmable-borrower mode, `IdleCDOEpochVariant._stopEpoch` reads `pendingWithdraws` and calls `IProgrammableBorrower.onStopEpoch` for `_amountToPullFromBorrower + _pendingWithdraws`. [1](#0-0) 

`ProgrammableBorrower.onStopEpoch` compares the requested shortfall with `convertToAssets(balanceOf(this))`. If the shares are economically sufficient, it calls `vault.withdraw`; if that withdrawal reverts for a liquidity reason, the hook rethrows `StopEpochVaultLiquidityUnavailable`. [2](#0-1) 

The revert is not caught by `_stopEpoch`, so none of the borrower-pull, receipt-funding, accounting, or epoch-close logic executes. [3](#0-2) 

`convertToAssets` values the vault claim but does not prove that the ERC4626 vault currently has withdrawable underlying liquidity. [4](#0-3) 

A vault participant can therefore create a state where `shortfall <= _currentVaultAssets()` but `vault.withdraw(shortfall)` reverts because idle liquidity has been redeemed or borrowed. Repeating that action before each manager `stopEpoch` call keeps the epoch running indefinitely.

The pending receipts remain frozen because `requestWithdraw` increments `pendingWithdraws`, while `claimWithdrawRequest` requires the request epoch to be finalized before the normal funded-claim path can pay. [5](#0-4) [6](#0-5) 

### Impact Explanation

This is a repeatable temporary freeze of all pending withdrawal funds, not merely gas loss. For example, a lender with a funded basis of 5,000 USDC in `pendingWithdraws` cannot receive the 5,000 USDC while an attacker keeps the external vault illiquid enough for `vault.withdraw` to fail but leaves the shares’ `convertToAssets` value at or above the shortfall.

The same condition also delays every active LP’s epoch settlement because `isEpochRunning` remains true and the next buffer phase cannot begin. Unlike the intended default path, the protocol cannot haircut or reserve the affected amount because `onStopEpoch` reverts instead of returning `false`. [7](#0-6) 

### Likelihood Explanation

The attack requires the programmable-borrower configuration and a third-party ERC4626 vault whose available cash can be consumed independently of the share valuation. That is an ordinary property of lending-market-backed ERC4626 vaults: shares can remain valuable while immediate withdrawable liquidity is insufficient.

The attacker does not need to be the credit borrower or a privileged role. A vault shareholder able to redeem enough idle liquidity, or a lending-market borrower able to borrow it, can create the failed-withdraw condition. Maintaining the freeze requires keeping the liquidity unavailable or repeating the action before each stop attempt.

### Recommendation

Do not let an economically covered ERC4626 liquidity failure indefinitely prevent epoch settlement.

Possible mitigations include:

- Record a liquidity-failure timestamp or retry count in `ProgrammableBorrower.onStopEpoch` and allow a manager/owner to escalate the condition to the normal borrower-default flow after a bounded retry period.
- Change `onStopEpoch` to return a richer status such as `success`, `realDefault`, or `temporaryLiquidityFailure`, and let `IdleCDOEpochVariant` apply a bounded waiting period before processing a default.
- Add a dedicated manager function that explicitly finalizes the vault liquidity failure after the timeout, including the current vault share claim in recovery accounting.
- Permit partial liquidity recall by funding `min(shortfall, actualWithdrawable)` and applying the shortage through the existing loss/default machinery rather than reverting forever.
