### Title
View-role users can read all External Initiator AccessKey/OutgoingToken secrets via unrestricted GET /v2/external_initiators - ([File: core/web/router.go])

### Summary
The `GET /v2/external_initiators` route is registered without any role gate (unlike its `POST`/`DELETE` siblings, which require edit role), so any authenticated session—including a view-role user—can call `ExternalInitiatorsController.Index`. The handler returns `presenters.ExternalInitiatorResource` objects that include the plaintext `AccessKey` and `OutgoingToken` for every configured external initiator, disclosing bridge/EI credentials meant to be edit/admin-only secrets.

### Finding Description
In `v2Routes` (`core/web/router.go`), the `authv2` group requires only authentication (session or API token), not any specific role, by default. Individual routes opt into stricter role checks via `auth.RequiresEditRole` / `auth.RequiresAdminRole` wrappers. For External Initiators:
- `authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))`
- `authv2.DELETE("/external_initiators/:Name", auth.RequiresEditRole(eia.Destroy))`
- `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` — **no role wrapper**

`ExternalInitiatorsController.Index` (`core/web/external_initiators_controller.go`) calls `eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)` to list all records, then builds `presenters.ExternalInitiatorResource` via `presenters.NewExternalInitiatorResource(initiator)`. That presenter (`core/web/presenters/external_initiators.go`) copies `ei.AccessKey` and `ei.OutgoingToken` verbatim into the JSON response with no redaction, unlike some other credential-holding resources in the codebase that mask secret values. Because the route has no role check, any authenticated user — including one created with only the `view` role — reaches this handler and receives the full list of EI credentials.

### Impact Explanation
This matches Chainlink's credential/secret disclosure impact class: a low-privilege (view-role) authenticated user can enumerate `AccessKey` and `OutgoingToken` for every external initiator configured on the node. These credentials are used by external initiators to authenticate inbound webhook/job-trigger calls to the node and by the node to authenticate outbound calls to the EI service; leaking them allows an attacker with only view access to impersonate an external initiator or forge/trigger job runs bound to that EI, and to authenticate as the EI toward downstream systems using the outgoing token — a privilege escalation from view-only to effectively edit/admin capability over EI-triggered job flows.

### Likelihood Explanation
Fully feasible with minimal privilege: only a valid view-role session or API token is required (`POST /sessions` as a view-role user, or a view-role API token), then a single `GET /v2/external_initiators` call returns the full plaintext credential set. No additional preconditions, timing, or race conditions needed; fully repeatable.

### Recommendation
Wrap the `GET /v2/external_initiators` route with `auth.RequiresEditRole` (or at minimum `auth.RequiresRunRole`, whichever matches the intended read-access policy for EI secrets) in `core/web/router.go`, mirroring the `POST`/`DELETE` routes. Additionally, consider redacting `AccessKey`/`OutgoingToken` in `presenters.ExternalInitiatorResource` for list/read responses (defense in depth), similar to how one-time secrets are handled elsewhere, so that even edit-role listing does not re-expose long-lived outgoing tokens.

### Proof of Concept
Add a table-driven test in `core/web/external_initiators_controller_test.go`:
1. Set up a test app via `cltest.NewApplicationWithKey`/similar harness, create an `ExternalInitiator` via `BridgeORM().CreateExternalInitiator` with known `AccessKey`/`OutgoingToken` values.
2. Create three users/sessions with roles `admin`, `edit`, and `view` respectively (or API tokens with those roles), matching patterns already used in `core/web/auth/auth_test.go` for role-based route tests.
3. For each role, issue `client.Get("/v2/external_initiators")`.
4. Assert current (vulnerable) behavior: all three roles get `200 OK` and the JSON body's `data[].attributes.accessKey` / `outgoingToken` match the stored values — demonstrating the view role obtains the secrets.
5. Expected (fixed) behavior: `view` role should receive `403 Forbidden` (matching the pattern of `POST`/`DELETE` external_initiators tests using `client.Post`/`client.Delete` and asserting `http.StatusForbidden` for insufficient role), while `edit`/`admin` continue to succeed.

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
type ExternalInitiatorResource struct {
	JAID
	Name          string         `json:"name"`
	URL           *models.WebURL `json:"url"`
	AccessKey     string         `json:"accessKey"`
	OutgoingToken string         `json:"outgoingToken"`
	CreatedAt     time.Time      `json:"createdAt"`
	UpdatedAt     time.Time      `json:"updatedAt"`
}

func NewExternalInitiatorResource(ei bridges.ExternalInitiator) ExternalInitiatorResource {
	return ExternalInitiatorResource{
		JAID:          NewJAID(strconv.FormatInt(ei.ID, 10)),
		Name:          ei.Name,
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,
		OutgoingToken: ei.OutgoingToken,
		CreatedAt:     ei.CreatedAt,
		UpdatedAt:     ei.UpdatedAt,
	}
}
```
