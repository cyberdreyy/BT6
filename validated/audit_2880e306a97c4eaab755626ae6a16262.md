### Title
Unredacted internal error messages from vault handler authorization/authentication failures relayed verbatim to unauthenticated gateway caller - ([File: core/services/gateway/gateway.go])

### Summary
`gateway.ProcessRequest` wraps any error returned from `h.HandleJSONRPCUserMessage` directly into the JSON-RPC response's `Error.Message` field via `newError(jsonRequest.ID, api.HandlerError, err.Error())`, with no sanitization. The vault handler's authorization failure path returns raw wrapped errors (`"request not authorized: " + err.Error()`) that bypass the handler's own dedicated redaction logic (`errorResponse`), so caller-supplied trigger conditions can cause internal authorizer/validator error text to be echoed back to the requester.

### Finding Description
In `core/services/gateway/gateway.go`, `ProcessRequest` calls `h.HandleJSONRPCUserMessage(ctx, jsonRequest, callback)` (line 272) and on error does: [1](#0-0) 
returning `err.Error()` verbatim as the JSON-RPC `Message` field with no redaction.

The vault handler (`core/services/gateway/handlers/vault/handler.go`) has two distinct error-return mechanisms: (1) `h.errorResponse(...)` which contains explicit per-errorCode redaction logic (e.g., it hides `NodeReponseEncodingError` detail entirely: `err = errors.New(errorCode.String())`), sent via `callback.SendResponse`; and (2) direct Go `error` returns from `HandleJSONRPCUserMessage` back up to `gateway.ProcessRequest`, which have **no** such redaction. The authorization failure path uses the second, unprotected mechanism: [2](#0-1) 

This wraps `h.requestProcessor.ProcessRequest`'s error, which itself further wraps the authorizer's error: [3](#0-2) 

Any error text produced deep inside `Authorizer.AuthorizeRequest` (allow-list based auth, JWT-based auth/Auth0 validation, or workflow-owner derivation) propagates through this chain (`authorizer error` → `authErr` → `"request not authorized: " + err.Error()` → `gateway.ProcessRequest`'s `newError(...)`) and reaches the unauthenticated/low-privileged caller's raw HTTP/JSON-RPC response with no sanitization, unlike every other vault-handler error path that funnels through `errorResponse`.

The attacker only needs the ability to submit a request that passes the gateway's coarse structural checks (JSON-RPC decode, DON/service lookup) and reach `HandleJSONRPCUserMessage`, then trigger any downstream error inside `AuthorizeRequest` (e.g., malformed signature, unexpected owner claim, JWT validation error containing token/claim details, or internal derivation errors) — none of which require valid authorization.

### Impact Explanation
This is an information-disclosure path (Chainlink bounty class: sensitive information disclosure) rather than key/secret leakage per se — the code as read does not obviously place raw signed-request bytes, node private keys, or decrypted secret material into these specific error strings. However, it does leak **internal implementation/authorization details** (error text from JWT validation, owner-derivation, or allow-list matching internals) to an unauthenticated caller, which can aid further attacks (e.g., probing which auth mechanism is in use, valid vs invalid owner formats, or partial claim values embedded in library error messages) and violates the intended invariant that non-generic/internal error text should not be relayed to callers — an invariant the codebase itself enforces elsewhere via `errorResponse`'s explicit case-by-case redaction, but which is skipped for this authorization-failure return path.

### Likelihood Explanation
No privilege is required — this is reachable by any caller of the gateway's public HTTP endpoint with a syntactically valid JSON-RPC vault request (`api.UserMessageParseError`/DON-lookup/method checks passed), i.e., an entirely unauthenticated actor. Triggering an authorization error (e.g., malformed `Auth` field, mismatched owner in `req.ID` prefix vs. signature, or an Auth0/JWT token that causes an internal library error) is trivial and repeatable on demand.

### Recommendation
In `core/services/gateway/handlers/vault/handler.go` at line 442, replace `return errors.New("request not authorized: " + err.Error())` with a generic, non-detail-leaking error (e.g., `return errors.New("request not authorized")`), logging the detailed `err` only via `h.lggr.Errorw` (already done at line 441). More broadly, in `core/services/gateway/gateway.go`, `ProcessRequest`'s generic `newError(jsonRequest.ID, api.HandlerError, err.Error())` fallback (line 275) should not echo arbitrary handler-returned `error.Error()` strings to the caller; handlers should return sentinel/structured errors and the gateway should map them to fixed, generic messages, consistent with the redaction pattern already implemented in `errorResponse`.

### Proof of Concept
Go handler-level test plan (extending `core/services/gateway/handlers/vault/handler_test.go` patterns):
1. Construct a `handler` via `newHandlerWithAuthorizer` with a mock `vaultcap.Authorizer` (from `core/capabilities/vault/mocks/authorizer.go`) whose `AuthorizeRequest` returns `errors.New("internal-secret-token-XYZ123 owner-derivation failed")`.
2. Send a `MethodSecretsList` (or `MethodSecretsCreate`) JSON-RPC request with valid structure/params through `handler.HandleJSONRPCUserMessage`.
3. Assert the returned `error.Error()` string contains `"internal-secret-token-XYZ123"` — demonstrating the raw authorizer error text is propagated unredacted.
4. Extend to `gateway.ProcessRequest` (using a `handlers.Handler` mock from `core/services/gateway/handlers/mocks/handler.go` returning this same error) and assert the JSON-RPC response's `Error.Message` field (via `newError`) contains the fake secret token verbatim, proving end-to-end leakage to the caller.
5. Expected fix assertion: after remediation, `Error.Message`/returned error should equal a generic constant (e.g., `"request not authorized"`) and never contain the injected sentinel string.
