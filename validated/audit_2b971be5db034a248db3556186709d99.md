### Title
Node-side signer response tally never removes a signer's stale rejection weight when that signer later switches to acceptance, letting `total_weight_rejected` and `total_weight_approved` double-count the same signer and spuriously trip the block-rejection branch - (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` (which the block-broadcast coordinator in `signer_coordinator.rs` polls to decide whether a proposed block has enough signer weight to push or must be treated as rejected) keeps two independent accumulators per block, `total_weight_approved` and `total_weight_rejected`, gated by two different keys (`gathered_signatures` vs `responded_signers`). A signer that first rejects and later reconsiders and accepts the same block (a flow the signer-side logic explicitly supports via `should_reevaluate_reject_reason`/`should_reevaluate_block`) has its weight added to `total_weight_rejected` on the first message and then *also* added to `total_weight_approved` on the later message, without the earlier rejection weight ever being subtracted. This is the opposite of the guarantee the signer's own local database (`stacks-signer/src/signerdb.rs`) enforces (a signature explicitly clears a stored rejection, per the `reject_then_accept`/`accept_then_reject` unit tests), but the node-side tally in `stackerdb_listener.rs` has no equivalent cleanup.

### Finding Description
`BlockStatus` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82` tracks, per proposed block:
- `responded_signers: HashSet<u32>` – used only to gate the **rejection** counter.
- `gathered_signatures: BTreeMap<u32, MessageSignature>` – used to gate the **acceptance** counter.

In the `BlockResponse::Accepted` handler (`stackerdb_listener.rs:386-465`), the code adds a signer's weight to `total_weight_approved` only `if !block.gathered_signatures.contains_key(&slot_id)` (line 443), then unconditionally inserts into both `gathered_signatures` and `responded_signers` (lines 464-465).

In the `BlockResponse::Rejected` handler (`stackerdb_listener.rs:486-518`), the weight is added to `total_weight_rejected` only `if block.responded_signers.insert(slot_id)` (line 515) — i.e. only the first time this `slot_id` appears in `responded_signers` at all, regardless of source.

Because these two counters are keyed off different maps, the two possible orderings behave asymmetrically:
- Accept → Reject: `responded_signers` already contains `slot_id` from the accept, so the later reject is silently dropped (correctly prevents double counting in this direction).
- **Reject → Accept: `gathered_signatures` does *not* yet contain `slot_id` when the accept arrives (only `responded_signers` does, from the earlier reject), so the accept branch's guard passes and the signer's weight is added to `total_weight_approved`. The signer's weight remains permanently counted in `total_weight_rejected` from the earlier rejection — nothing in this code path ever decrements it.**

This breaks the invariant that a single signer's weight should only ever count toward one side of the "aggregated-weight vs verified-accepts" equality that `signer_coordinator.rs` relies on (`stacks-node/src/nakamoto_node/signer_coordinator.rs:512-545`), which checks `total_weight_rejected` against the blocking-minority threshold *before* checking `total_weight_approved` against the approval threshold, in an if/else‑if chain. As a result, stale rejection weight from a signer who has since reconsidered and accepted can push `total_weight_rejected` past `>30%` and cause the coordinator to return `NakamotoNodeError::SignersRejected` even though the block currently has (or could reach) a legitimate `≥70%` acceptance weight, because the rejected branch is checked first and its condition can remain permanently satisfied by phantom weight.

This is reachable by ordinary protocol activity that a one-slot miner can help trigger: the miner controls proposal/reproposal timing, and signer reconsideration of a prior rejection (`should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`) is an explicitly supported path in this codebase (see `docs/signer-flows.md` section 3 and section 6, and the CHANGELOG entry "Do not count both a block acceptance and a block rejection for the same signer/block" which documents the intended fix for exactly this class of bug — but that fix lives only in `stacks-signer/src/signerdb.rs`, the signer's own local ledger, not in the node-side `stackerdb_listener.rs` tally used by the miner/coordinator).

### Impact Explanation
This is a liveness wedge on the node/coordinator side: a legitimately-approved block can be treated by the miner's coordinator as globally rejected due to permanently-retained stale rejection weight from a signer that has since switched its vote to acceptance. Because the reject-threshold check runs before the accept-threshold check in `signer_coordinator.rs`, the coordinator can give up on pushing a valid, sufficiently-signed block, causing the tenure to stall until the miner re-mines/reproposes — a liveness impact consistent with the report's "High" bucket (a signer-set/threshold decision acting on stale/phantom weight rather than the verified current vote state). It does not by itself cause a signature over an invalid/non-canonical block (the acceptance side remains correctly single-counted per signer), so it is not a Critical safety break, but it is a concrete break of the aggregated-weight vs. verified-accepts equality that the tally is supposed to maintain.

### Likelihood Explanation
The trigger condition (a signer rejecting a proposal and later accepting the same `signer_signature_hash`) is a normal, protocol-sanctioned occurrence — not a majority-signer or key-compromise scenario. It can arise from ordinary timing/reconsideration behavior (e.g., a transient validation hiccup followed by a successful re-evaluation), and a miner can influence the odds of hitting it via reproposal timing. No majority-of-signers assumption, no key compromise, and no StackerDB-transport-only flaw is required — the root cause is purely in the counting logic of `stackerdb_listener.rs`.

### Recommendation
In the `BlockResponse::Accepted` handler, when the signer being credited already appears in `responded_signers` due to a prior *rejection* (not just a prior acceptance), subtract that signer's weight from `total_weight_rejected` (and drop it from any per-txid `failed_txids` weight it previously contributed to) before adding it to `total_weight_approved`, mirroring the guarantee already implemented in `stacks-signer/src/signerdb.rs::add_block_signature`/`add_block_rejection_signer_addr`. Equivalently, track a single "current vote" per `slot_id` (accept/reject) instead of two independently-gated sets, and recompute `total_weight_approved`/`total_weight_rejected` as sums over that single source of truth so a signer's weight can never count in both totals simultaneously.

### Proof of Concept
1. Miner proposes block `B`; signer `S` (weight `w`) initially rejects `B` (e.g. a validation race or a stale-conflict rejection) → `stackerdb_listener.rs` `Rejected` branch: `responded_signers.insert(slot_id)` succeeds, `total_weight_rejected += w` (line ~515-518).
2. `S` re-evaluates (per `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`) and now sends `Accepted` for the same `signer_signature_hash`.
3. In the `Accepted` branch, `gathered_signatures.contains_key(slot_id)` is `false` (first acceptance), so `total_weight_approved += w` (line ~443-446), while `total_weight_rejected` still includes `w` from step 1 — never decremented.
4. Enough other signers approve so `total_weight_approved >= weight_threshold`, but before/at the same time `total_weight_rejected.saturating_add(min_weight) > total_weight` also holds due to `S`'s stale rejected weight plus other real rejecters.
5. `signer_coordinator.rs`'s wait loop (`stacks-node/src/nakamoto_node/signer_coordinator.rs:505-545`) evaluates the reject condition first and returns `Err(NakamotoNodeError::SignersRejected{..})`, discarding a block that in reality has sufficient current signer approval.
