### Title
Fail-open fallback in `check_latest_block_in_tenure` lets a miner bypass the "confirms latest tenure tip" guard via an unknown/unreachable tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` is the function that answers "does this proposed block actually confirm the tip we expect in a given tenure?" — it is re-run at proposal time, at validate-ok, and again right before a signature is issued (the "last look"). When its call to the node, `client.get_tenure_tip(tenure_id)`, returns *any* `Err`, the function does not fail closed; it treats the error identically to "the tenure genuinely has no known blocks yet" and returns `Ok(true)` (i.e., "the proposal is higher, check passes"), rather than only doing this for a true connectivity failure.

### Finding Description
`check_latest_block_in_tenure` in `stacks-signer/src/chainstate/mod.rs` (around lines 450-461) does:

```rust
let tip = match client.get_tenure_tip(tenure_id) {
    Ok(tip) => tip.anchored_header,
    Err(e) => {
        warn!("Failed to fetch the tenure tip ... Assuming proposal is higher ...");
        return Ok(true);
    }
};
``` [1](#0-0) 

`client.get_tenure_tip` hits the node's `/v3/tenures/tip/:consensus_hash` endpoint, implemented in `RPCNakamotoTenureTipRequestHandler::try_handle_request` (`stackslib/src/net/api/gettenuretip.rs`). That handler calls `NakamotoChainState::find_highest_known_block_header_in_tenure`, and if it returns `Ok(None)` (i.e., the node has *never heard of any block in this tenure*), it responds with a hard `404 Not Found`:

```rust
Ok(None) => {
    let msg = format!("No blocks in tenure {}", &consensus_hash);
    return Err(StacksHttpResponse::new_error(&preamble, &HttpNotFound::new(msg)));
}
``` [2](#0-1) 

On the signer side, this 404 surfaces as an `Err` from `client.get_tenure_tip`, which is exactly the branch that `check_latest_block_in_tenure` treats as "assume higher" (i.e., pass the check) — the same code path used for a genuine local RPC/connectivity failure. The function does not distinguish "my node is unreachable" from "the tenure the block claims to build on doesn't exist / was never observed."

This check feeds `check_tenure_change_confirms_parent` and `confirms_latest_block_in_same_tenure`, which are called from `check_block_against_signer_db_state` in `stacks-signer/src/v0/signer.rs` at both the validate-ok step and — critically — right before a signature is emitted once the pre-commit threshold is reached (`handle_block_pre_commit`, per `docs/signer-flows.md` section 5/7). A miner (or a colluding/compromised prior tenure) can craft a `TenureChange` transaction whose `prev_tenure_consensus_hash` references a tenure the signer's connected node has no record of at all (e.g., a consensus hash that never had a block posted to this node, whether due to a genuine gap, selective withholding, or timing). The node legitimately answers 404 for that consensus hash, and the signer's guard silently treats that as "the parent tenure's tip is confirmed" instead of refusing.

### Impact Explanation
This breaks the "approved-parent vs canonical" equality that `check_latest_block_in_tenure` exists to enforce: the whole point of the re-check (done three times, explicitly to catch conditions that changed between proposal and signature) is to prevent a signer from confirming/signing a tenure-change block that does not build on the real prior tenure tip. Turning an unknown-tenure 404 into an automatic pass means the last-look re-check before signing can be defeated by any tenure reference the node hasn't independently observed, undermining the guard at exactly the moment (right before the irreversible signature) that the design intends it to be strongest. This matches the "signer signing an invalid/non-canonical/conflicting block" impact class.

### Likelihood Explanation
The comment in the code frames this fallback as intentionally "safe" because "this proposal ultimately must be passed to the `stacks-node` for proposal processing," i.e. the `/v3/block_proposal` full validation (`postblock_proposal.rs::validate`) is assumed to be the real backstop. That is true for the *first* proposal-time check, but this same fallback governs a second, independent call site: the re-check performed at pre-commit-threshold time right before signing (`check_block_against_signer_db_state` invoked from `handle_block_pre_commit`), which is explicitly documented as needed because the world can change between validation and threshold. At that later point, the "stacks-node proposal endpoint is the backstop" reasoning is materially weaker, since the full `/v3/block_proposal` validation ran once, earlier, against a possibly-different state — not at the moment the signature is actually produced.

### Recommendation
Distinguish "true connectivity failure querying `get_tenure_tip`" from "confirmed 404 — no blocks exist in this tenure" in `check_latest_block_in_tenure`. Only the former should fall back to "assume higher" as a backstop-dependent behavior; a confirmed 404 for an unrecognized/unobserved tenure referenced by a `TenureChange` should not be silently treated as passing, especially in the last-look call site immediately preceding signature issuance.

### Proof of Concept
Cannot be fully constructed from the available context without live execution — the concrete conditions under which a legitimately-participating node would independently 404 on a `prev_tenure_consensus_hash` referenced by a proposed `TenureChange` (versus already knowing about it from a prior proposal/validation round) would need to be verified with a running signer+node setup to confirm exploitability end-to-end, which is outside the scope of static code review here.
