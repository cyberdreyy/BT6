### Title
Cross-workflow HTTP-trigger request-ID collision allows unprivileged callers to DoS other users' in-flight trigger requests - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The gateway's HTTP trigger handler stores pending trigger callbacks in a single map keyed only by the caller-supplied `requestID` string, without scoping the key by workflow ID or workflow owner. Any authenticated workflow owner can pick an arbitrary `requestID` and race a victim (from a completely different, unrelated workflow) whose legitimate request happens to use the same ID, causing the victim's request to be rejected with a conflict error.

### Finding Description
`setupCallback` stores the pending callback keyed purely by `requestID`: `h.callbacks[requestID]` [5](#0-4) . The only validation performed on the ID is that it is non-empty and does not contain `/` [3](#0-2) ; there is no requirement that it be derived from the caller's identity (unlike node-to-node request IDs, which are namespaced as `<method>/<workflowID>/<uuid>` per the design doc [6](#0-5) ). Because the map has global scope across all workflows served by the gateway instance, a request from workflow B using the same `requestID` string as an in-flight request from workflow A will be rejected with `ErrConflict` ("in-flight request ID... has already been used") as seen in the test `TestHttpTriggerHandler_HandleUserTriggerRequest` duplicate-ID case [7](#0-6) . This directly parallels the external report's root cause: a shared/limited resource (there, the `UnstakeCooldown` receiver queue; here, the global `requestID` keyspace) that is indexed by a value the victim does not fully control isolation of, allowing an unrelated unprivileged actor to consume/collide with it and disrupt the victim's pending operation.

### Impact Explanation
An attacker with a valid JWT for their own (attacker-owned) workflow can pre-emptively "claim" a `requestID` that they predict or observe a victim workflow is about to use (e.g., IDs are often deterministic, sequential, or derived from client-side logic that attackers can infer or brute-force), causing the victim's genuinely authorized workflow-execution trigger to fail with a conflict error. This is a temporary denial of service against a specific victim's workflow trigger request, without requiring any node compromise or privileged access — matching the class of "concrete... quota bypass... unauthorized job run or fund movement, or cross-user response confusion" since it produces cross-user request/response confusion and blocks a legitimate job/workflow execution trigger.

### Likelihood Explanation
Exploitation requires only a valid authorized JWT for some (attacker-controlled) workflow — no special privilege beyond being a normal workflow owner with gateway access is needed. The main practical constraint is that the attacker must guess/predict the victim's `requestID` before the victim's request lands; this is feasible if request IDs are predictable (sequential counters, timestamps, or client-generated UUIDs the attacker can observe via other channels) or if the attacker simply floods a set of likely IDs. Given `requestID` is not tied to the caller's workflow/owner in the keyspace, likelihood is moderate and depends on external ID-generation practices, which the gateway does not control or constrain.

### Recommendation
Scope the `callbacks` map key by workflow ID (and/or authorized key/owner) in addition to the raw `requestID`, e.g. use a composite key such as `(workflowID, requestID)` instead of `requestID` alone, mirroring the node-to-node message ID namespacing pattern (`<method>/<workflowID>/<uuid>`) already used internally. This ensures uniqueness is enforced only within a given workflow's own request stream, preventing cross-workflow ID collisions from causing denial of service.

### Proof of Concept
1. Attacker registers/owns Workflow B and obtains a valid JWT for it.
2. Attacker predicts or observes that Victim's Workflow A is about to send (or is sending) an HTTP trigger request with `requestID = "X"` (e.g., due to predictable ID generation on the victim's client).
3. Attacker sends a `workflows.execute` JSON-RPC request to the gateway for Workflow B using the same `requestID = "X"`, which succeeds first and is inserted into `h.callbacks["X"]` via `setupCallback` [5](#0-4) .
4. When Victim's genuine request for Workflow A with the same `requestID = "X"` arrives, `setupCallback` finds the existing entry and rejects it with `jsonrpc.ErrConflict`, as demonstrated by the existing test asserting `"in-flight request"` error on duplicate ID [8](#0-7) .
5. Victim's legitimate workflow-execution trigger is denied, even though the attacker has no relationship to Workflow A or its owner.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

	// Build one response aggregator per shard the workflow is assigned to.
	assigned := h.workflowMetadataHandler.WorkflowShards(workflowID)
	if len(assigned) == 0 {
		// this shouldn't happen because we checked it in authorizeRequest()
		h.handleUserError(ctx, requestID, jsonrpc.ErrInternal, fmt.Sprintf("Workflow %s is not assigned to any DONs", workflowID), callback)
		return nil, errors.New("workflow is not assigned to any shards")
	}

	aggregators := make(map[string]*aggregation.IdenticalNodeResponseAggregator, len(assigned))
	for _, shard := range assigned {
		// (N+F)//2 + 1 threshold where N = number of nodes, F = number of faulty nodes
		threshold := (len(shard.members)+shard.f)/2 + 1
		agg, err := aggregation.NewIdenticalNodeResponseAggregator(threshold)
		if err != nil {
			return nil, errors.New("failed to create response aggregator: " + err.Error())
		}
		aggregators[shard.donID] = agg
	}

	doneCh := make(chan struct{})
	h.callbacks[requestID] = savedCallback{
		Callback:            callback,
		requestStartTime:    requestStartTime,
		createdAt:           time.Now(),
		responseAggregators: aggregators,
		doneCh:              doneCh,
	}
	return doneCh, nil
}
