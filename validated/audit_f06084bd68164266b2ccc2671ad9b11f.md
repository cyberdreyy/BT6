## Finding

**Root-cause match confirmed.** The Sherlock report's core defect — a *per-user* (not per-request/per-collateral) timestamp that gets unconditionally overwritten on every new user action, extending the lock for unrelated already-eligible funds — has a direct analog in `ProvisionerV2`'s sync-deposit lock mechanism.

### Title
Each new sync deposit resets the global per-user unlock timestamp, re-freezing previously vested vault units - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2._syncDeposit` unconditionally overwrites `userUnitsRefundableUntil[receiver]` with a new `block.timestamp + depositRefundTimeout` on every call to `deposit`/`mint`, regardless of any earlier, still-active or already-expired lock for that user. Since `MultiDepositorVault._update` and the sync `redeem`/`withdraw` functions gate on this single global-per-user value, a routine second deposit (in the same or a different sync-enabled token) re-locks *all* of the user's previously minted units, including units whose original lock window had already elapsed.

### Finding Description
`_syncDeposit` sets: `userUnitsRefundableUntil[receiver] = refundableUntil;` at [1](#0-0) , where `refundableUntil = block.timestamp + depositRefundTimeout`. This mapping is keyed only by `user`, not by deposit/token/request, so it can only ever hold one active deadline at a time — exactly the flaw described in the report (single `lastRedeemedBlock[user]` instead of per-collateral tracking).

This value gates three separately reachable, ordinary-user-callable paths:
- Unit transfers, via `MultiDepositorVault._update`, which reverts if `!areUserUnitsLocked(from)` is false for a non-mint/non-burn transfer: [2](#0-1) 
- `ProvisionerV2.redeem` (sync redeem): `require(userUnitsRefundableUntil[msg.sender] < block.timestamp, Aera__UnitsLocked());` [3](#0-2) 
- `ProvisionerV2.withdraw` (sync withdraw): same check [4](#0-3) 

`deposit()` (and `mint()`) are public/anyone-callable (`anyoneButVault`) for any token with `syncDepositEnabled`, with no cooldown, no cap on call frequency, and no check that the caller/receiver already has an outstanding lock: [5](#0-4) .

Ordinary sequence:
1. User calls `deposit(tokenA, ...)` at `t0`. `userUnitsRefundableUntil[user] = t0 + depositRefundTimeout`.
2. Before that window elapses (or even right after), the user calls `deposit(tokenB, ...)` (a second sync-enabled collateral, or even the same token again) at `t1`. `_syncDeposit` overwrites the mapping: `userUnitsRefundableUntil[user] = t1 + depositRefundTimeout`, which is strictly later than the original deadline.
3. The user's units from step 1, which were already unlocked or about to unlock at `t0 + depositRefundTimeout`, are now locked again until `t1 + depositRefundTimeout`. They cannot transfer, sync-redeem, or sync-withdraw any of their units (old or new) until the later deadline, and this can be repeated indefinitely by any third party depositing on the user's behalf (`receiver` is attacker-controlled in `deposit`/`mint`), perpetually re-locking the victim's units with dust deposits.

This directly mirrors the reported pattern: a single, global-per-user delay/lock timestamp reset by an unrelated, permissionless action, rather than being tracked per underlying position.

### Impact Explanation
This is a temporary freeze of user funds: previously-deposited, already-vested vault units become non-transferable and non-redeemable via `redeem`/`withdraw` for an additional `depositRefundTimeout` period every time a new sync deposit is made for that receiver — including by an unrelated third party who calls `deposit`/`mint` with the victim as `receiver`. This matches an Immunefi Medium-severity temporary-freezing-of-funds impact, and can be griefed indefinitely with trivial dust deposits since `receiver` is attacker-supplied and there is no per-caller restriction.

### Likelihood Explanation
High feasibility: `deposit`/`mint` are unauthenticated public functions, `depositRefundTimeout` is a protocol-configured but generally non-zero window (bounded by `MAX_DEPOSIT_REFUND_TIMEOUT`), and any address can specify an arbitrary `receiver`. No special privileges, oracle manipulation, or governance action needed — just a second (griefing) deposit call with minimal token amount.

### Recommendation
Track the refundable/lock deadline per deposit (e.g., keyed by depositHash or in a per-user array/queue of `(amount, refundableUntil)`), or only extend `userUnitsRefundableUntil[receiver]` if the new deadline exceeds the current one is not sufficient — instead ensure that a subsequent deposit's lock does not restrict already-unlockable balances (e.g., cap the impacted locked amount to the newly minted units rather than blocking the entire balance, or use per-tranche locking similar to vesting schedules).

### Proof of Concept
Foundry steps (local fork):
1. Deploy/hook into an existing `ProvisionerV2`/`MultiDepositorVault` with two sync-deposit-enabled tokens (A, B) and non-zero `depositRefundTimeout`.
2. `vm.prank(attacker); provisioner.deposit(tokenA, amt, minOut, victim);` — sets `userUnitsRefundableUntil[victim] = t0 + timeout`.
3. `vm.warp(t0 + timeout - 1);` assert `provisioner.areUserUnitsLocked(victim) == true` (expected, still within original window).
4. `vm.prank(attacker); provisioner.deposit(tokenB, dustAmt, 1, victim);` at this same timestamp — resets `userUnitsRefundableUntil[victim] = (t0+timeout-1) + timeout`.
5. `vm.warp(t0 + timeout + 1);` (past the *original* deadline) — attempt `vm.prank(victim); vault.transfer(other, unitsFromStep2);` and `provisioner.redeem(tokenA, unitsFromStep2, ..., victim)`; both revert with `Aera__UnitsLocked()` despite the original lock having elapsed, demonstrating the freeze extension caused solely by an unrelated deposit.
