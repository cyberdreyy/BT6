### Title
External Initiator credentials can trigger job runs for **any** job ID via `POST /v2/jobs/:ID/runs`, not just their bound job - ([File: core/web/auth/auth.go, core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` attaches a generic `clsessions.User{Role: UserRoleRun}` to the gin context that is indistinguishable from a real user session/token. `PipelineRunsController.Create`, the only run-role endpoint reachable by EI credentials, gates its int-ID job-trigger branch solely on `auth.GetAuthenticatedUser(c)` succeeding (`isUser`), and never inspects `auth.GetAuthenticatedExternalInitiator(c)` to verify the EI is authorized for the specific `:ID` in the URL. As a result, a valid EI access key/secret for job/bridge A can trigger a run of an unrelated job B.

### Finding Description
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` (lines 119-151) authenticates the EI's access key/secret, stores the `*bridges.ExternalInitiator` under `SessionExternalInitiatorKey`, and separately sets `SessionUserKey` to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` with no reference back to the specific EI or its bound job/bridge: [1](#0-0) 

This fake user is set in the `userOrEI` route group in `core/web/router.go`, which wires `AuthenticateExternalInitiator` ahead of token/session auth and exposes exactly two endpoints, `GET /ping` and `POST /jobs/:ID/runs` (guarded by `RequiresRunRole`): [2](#0-1) 

`RequiresRunRole` only checks `user.Role != UserRoleView`, so the synthetic EI-derived user passes it identically to a real run-role human: [3](#0-2) 

In `PipelineRunsController.Create`, the handler retrieves the authenticated user via `auth.GetAuthenticatedUser(c)` and, if present (`isUser == true`), directly parses `:ID` as an int32 job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` — with **no lookup or comparison against `auth.GetAuthenticatedExternalInitiator(c)`** to confirm the EI is bound to that job: [4](#0-3) 

Because `GetAuthenticatedUser` merely checks for the presence of a `*clsessions.User` in context (regardless of whether it was set by `AuthenticateBySession`, `AuthenticateByToken`, or `AuthenticateExternalInitiator`): [5](#0-4) 

`isUser` is `true` for EI-authenticated requests as well, even though the code comment explicitly states "only users are allowed to run jobs using int IDs - EIs not allowed." The comment's intended restriction is not enforced in code, since the EI middleware plants an indistinguishable generic user object. The `ExternalInitiator` object fetched via `GetAuthenticatedExternalInitiator` is never consulted in `Create` to scope the request to the EI's own job.

### Impact Explanation
Any holder of a valid external-initiator access key/secret for one job/bridge (job A) can trigger job runs on any other job in the node by ID (job B), by simply calling `POST /v2/jobs/<jobB_ID>/runs` with EI-A's credentials. This is an authorization/request-binding bypass: the EI credential's intended scope (trigger job A only) is not enforced, allowing cross-job unauthorized job execution. Depending on job B's pipeline (e.g., an ETH tx task, VRF fulfillment, or other on-chain write), this can lead to unauthorized job runs and potentially unauthorized on-chain actions/fund movement, matching Chainlink's "unauthorized job run" / "role or authorization bypass" bounty impact class.

### Likelihood Explanation
This requires only a single valid EI access key/secret (any external initiator registered on the node) — no admin, edit, or run-role human credential is needed, and no additional preconditions beyond knowing/guessing another job's int ID (job IDs are sequential integers and can often be enumerated via `GET /v2/jobs`, though that endpoint requires a different auth). The attack is fully repeatable via a single unauthenticated-to-the-target-job HTTP POST once EI credentials are obtained.

### Recommendation
In `PipelineRunsController.Create`, when the request was authenticated via `AuthenticateExternalInitiator` (i.e., `auth.GetAuthenticatedExternalInitiator(c)` returns ok), verify that the EI is actually authorized to trigger the specific job ID in `:ID` (e.g., via the job's `ExternalInitiatorWebhookSpec`/allowed EI list) before calling `RunJobV2`, instead of relying on the generic `isUser` check which cannot distinguish EI-origin requests from real user sessions/tokens.

### Proof of Concept
1. Register two webhook jobs, Job A and Job B, each with distinct `ExternalInitiatorWebhookSpec` bindings; create External Initiator `EI-A` bound only to Job A.
2. Handler-level integration test (using `web.NewRouter`/`httptest`):
   - Send `POST /v2/jobs/<JobA.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` for `EI-A` → expect `200 OK`, job A run created.
   - Send `POST /v2/jobs/<JobB.ID>/runs` with the same `EI-A` credentials → current behavior: `200 OK`, job B run is created (vulnerable); expected/fixed behavior: `401`/`403` since `EI-A` is not authorized for Job B.
3. Assert via `prc.App.PipelineORM().FindRun` that a pipeline run for Job B was created using EI-A's credentials, demonstrating cross-job triggering.

```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
```

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
