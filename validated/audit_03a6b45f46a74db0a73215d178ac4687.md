### Title
Allowed-image check validates unexpanded image string, while variable-expanded value is used for VM creation - ([File: executors/instance/instance.go], [File: executors/internal/autoscaler/acquisition.go])

### Summary
`executor.Prepare` in `executors/instance/instance.go` calls `common.VerifyAllowedImage` against the raw `options.Build.Image.Name` string before nesting VM creation happens. Later, in `executors/internal/autoscaler/acquisition.go`'s `createVMTunnel`, the image string is expanded with `options.Build.GetAllVariables().ExpandValue(image)` and the *expanded* value — not the validated raw value — is what gets passed to `nc.Create` to build the nested VM.

### Finding Description
`executor.Prepare` performs the allow-list check as follows: [1](#0-0) 

This check runs `doublestar.Match` on the literal `options.Build.Image.Name` value with `AllowedImages` glob patterns: [2](#0-1) 

Only after `Prepare` succeeds does `environment.Prepare` get called, which (when VM isolation is enabled) eventually reaches `createVMTunnel`: [3](#0-2) 

The critical line is `image = options.Build.GetAllVariables().ExpandValue(image)` — this expands `$VAR`-style references using the full set of job variables *after* the allow-list check has already passed on the raw string, and the resulting expanded string (not the originally-checked string) is what is handed to `nc.Create` to provision the nested VM.

If an attacker (pipeline author) sets the job's `image:` field to a string containing an embedded variable reference (e.g. `ubuntu:$MY_VAR`) and also controls the value of `MY_VAR` via job/pipeline variables, then:
1. `VerifyAllowedImage` is evaluated on the literal string `"ubuntu:$MY_VAR"`, which can satisfy an admin-configured glob pattern such as `ubuntu:*` (single `*` in doublestar does not cross `/`, so as long as the literal text has no `/`, it passes).
2. After the check passes, `ExpandValue` substitutes `$MY_VAR` with the attacker-controlled variable value, which can contain arbitrary text (including additional path segments), yielding a final image string that was never itself checked against `AllowedImages`.

I was not able to confirm from the available code whether GitLab Rails pre-expands the `image:` field's variable references before sending the job payload to the Runner (which would neutralize this specific path by removing `$VAR` syntax before it reaches the Runner). This is a material precondition that could not be verified with the tools available — if Rails already expands the image field server-side, `options.Build.Image.Name` arriving at the Runner would already be a fully resolved value and `ExpandValue` in `acquisition.go` would be a no-op for this field, closing the gap described here. This uncertainty should be resolved by inspecting GitLab Rails' job-payload construction / variable-expansion logic, which is outside this repository.

### Impact Explanation
If the precondition holds (Runner receives an unexpanded image string containing variable references), an attacker who can set job-level variables could bypass an admin's `allowed_images`/`AllowedImages` restriction on the instance executor and cause a nested VM to be created from an arbitrary, non-allow-listed image/template — undermining the intended image allow-list control for VM-isolated instance executor jobs.

### Likelihood Explanation
Exploitability strictly depends on the unresolved precondition above (whether unexpanded `$VAR` syntax in the `image:` field reaches the Runner at all). Given that GitLab CI variable expansion for job attributes is typically performed by GitLab Rails before the job is dispatched to a runner, this path may not be reachable in practice. Without being able to confirm that server-side behavior, this finding is a potential bug in the local validation order (check-then-use on different values) but not verifiably a fully triggerable end-to-end exploit for an unprivileged attacker in this codebase alone.

### Recommendation
Regardless of whether the upstream precondition holds, defense-in-depth in the Runner would close this gap: perform `common.VerifyAllowedImage` on the *fully expanded* image string (i.e., call `options.Build.GetAllVariables().ExpandValue(...)` before the allow-list check in `executors/instance/instance.go`), or re-validate the expanded image inside `createVMTunnel` in `executors/internal/autoscaler/acquisition.go` immediately before `nc.Create` is invoked.

### Proof of Concept
Go unit test outline for `executors/instance/instance_test.go` combined with `acquisition_test.go`:
1. Configure `AllowedImages: []string{"ubuntu:*"}`.
2. Set `options.Build.Image.Name = "ubuntu:$INJECT"` and job variable `INJECT=evil/backdoor:latest`.
3. Assert `executor.Prepare` returns `nil` (check passes on raw string).
4. Call `acquisitionRef.createVMTunnel` (or a mocked nesting client capturing the `image` argument to `nc.Create`) and assert the image string passed to VM creation equals `"ubuntu:evil/backdoor:latest"`, demonstrating that the value used for creation was never itself checked against `AllowedImages`.
5. This test would need to be paired with confirmation (outside this repo) of whether GitLab Rails ever forwards unexpanded `$VAR` syntax in the `image:` field to Runner API job payloads; if it does not, the PoC demonstrates a latent/defense-in-depth gap rather than a currently reachable exploit.
