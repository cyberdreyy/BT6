### Title
B20Asset `updateMultiplier` Lets OPERATOR_ROLE Instantly Change the Rebase Multiplier With No Timelock, Enabling Front-Running of Pending Transfers/Redemptions - (File: `crates/common/precompiles/src/b20_asset/logic/v2.rs`)

### Summary
The B20Asset precompile exposes two multiplier-mutation paths: a timelocked `update_ui_multiplier` (ERC-8056, introduced at Cobalt) that enforces `effective_at > now` before a new multiplier can take effect, and a legacy instant `update_multiplier` setter that applies the new multiplier immediately in the same transaction, with no delay. An `OPERATOR_ROLE` holder using the instant setter can change a value-determining parameter (the multiplier that scales every account's UI balance and total supply) atomically, in the same block as — or ahead of — a user's pending transfer/burn/mint transaction, exactly the "admin front-runs users by changing a critical economic parameter with no timelock" pattern described in the source report (Knox `PerformanceFee`/`withdrawalFee`).

### Finding Description
`update_ui_multiplier` explicitly guards against instant changes: [1](#0-0) 
requiring `effective_at > now`, rejecting a schedule that fires in the past, and rejecting a second update while one is still pending — this is a proper timelock.

By contrast, the multiplier is read lazily via `effective_multiplier`, which flips to the pending value once matured: [2](#0-1) 
and `to_scaled_balance`/`to_raw_balance` compute a user's UI-facing balance/value directly from this multiplier: [3](#0-2) 

Confirmed by the test suite, the legacy `update_multiplier` call is described explicitly as an "instant setter" that takes effect in the same call, alongside the timelocked `update_ui_multiplier`: [4](#0-3) 
Both setters are gated only by `OPERATOR_ROLE`, with no waiting period on the instant path: [5](#0-4) 

Because `update_multiplier` mutates `token.accounting_mut()`'s multiplier synchronously and takes effect for every subsequent read in the same and later blocks, an `OPERATOR_ROLE` holder observing a pending user transaction in the transaction pool (e.g., a large `transfer`, `burnWithMemo`, or a redemption flow built on top of the scaled balance) can submit a fee/multiplier-changing transaction ahead of it in the same block, altering the effective value the user's transaction settles at. This mirrors the Knox `VaultAdmin` issue: an admin-level role can unilaterally and instantly change a value-critical parameter with no on-chain delay, denying users the opportunity to react, and enabling extraction of value from users mid-flight.

### Impact Explanation
An `OPERATOR_ROLE` holder on any B20Asset token can, within a single transaction, instantly change the multiplier that scales every holder's UI balance and total supply, then immediately have that new multiplier apply to any subsequent transaction in the block (including one the operator itself constructs to front-run a specific user's pending transfer/burn). This allows a privileged-but-not-omnipotent role to unilaterally shift economic value away from users at a time of the role holder's choosing, without the delay/notice that the codebase's own `update_ui_multiplier` path was specifically designed to provide (per its Cobalt-era comment "ERC-8056 scheduled multiplier"). This satisfies the "unauthorized operation" / value-extraction bar because a user's expected settlement value can be unilaterally altered by a role holder with no forewarning, undermining the fairness guarantee the timelocked variant was built to provide.

### Likelihood Explanation
Likelihood is Medium: the actor must hold `OPERATOR_ROLE` on the specific B20Asset token, which is a legitimate but non-owner-level trust tier (not the top `DefaultAdmin`), meaning it is plausible for an ecosystem partner or automated relayer key to hold this role in practice, and no additional privilege escalation is required — a single call to `update_multiplier` (unlike `update_ui_multiplier`) achieves an instant, unannounced change.

### Recommendation
Deprecate or remove the instant `update_multiplier` code path for any token configuration that also exposes `update_ui_multiplier`, or gate the instant setter behind the same "must schedule for the future" invariant enforced by `update_ui_multiplier` (`effective_at > now`), so that all multiplier changes are subject to a mandatory minimum delay and are broadcast via `UIMultiplierUpdated` (or equivalent) before taking effect, closing the front-running window that currently exists via the instant setter.

### Proof of Concept
1. Grant address `OP` the `OPERATOR_ROLE` on a `B20AssetToken` (v2) instance. [5](#0-4) 
2. A user submits a `transfer`/`burnWithMemo` transaction to the txpool that will settle based on the current multiplier (via `to_scaled_balance`/`effective_multiplier`). [6](#0-5) 
3. `OP` observes the pending transaction and, in the same block, calls the legacy instant `update_multiplier` entry point, changing the multiplier with no `effective_at` delay (as opposed to `update_ui_multiplier`'s enforced future-timestamp check). [4](#0-3) 
4. The user's transaction now settles against the new, operator-chosen multiplier rather than the multiplier that was live when the user signed and broadcast their transaction — value is extracted/shifted with no advance notice, exactly the front-running-via-missing-timelock class described in the source report.

    fn update_ui_multiplier(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        new_multiplier: U256,
        effective_at: U256,
        privileged: bool,
    ) -> Result<()> {
        let now = token.accounting().timestamp()?;
        self.ensure_operator_role(token, caller, privileged)?;
        if new_multiplier.is_zero() || new_multiplier > Self::MAX_UI_MULTIPLIER {
            return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
        }
        if effective_at <= now {
            return Err(BasePrecompileError::revert(IB20Asset::EffectiveAtInPast {
                effectiveAt: effective_at,
            }));
        }
        if effective_at > U256::from(u64::MAX) {
            return Err(BasePrecompileError::revert(IB20Asset::EffectiveAtTooFar {
                effectiveAt: effective_at,
            }));

        if U256::from(pending_effective_at) > now {
            return Err(BasePrecompileError::revert(IB20Asset::UIMultiplierUpdateExists {
                effectiveAt: U256::from(pending_effective_at),
