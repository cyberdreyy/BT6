### Title
Unbounded `pending_repair_requests` growth from a single crafted `ParentFecSetCount` response - (File: core/src/repair/block_id_repair_service.rs)

### Summary
`BlockIdRepairService::process_block_id_repair_response` extends `state.pending_repair_requests` with `fec_set_count` entries taken directly from an unprivileged peer's `BlockIdRepairResponse::ParentFecSetCount` reply, with no upper bound check on `fec_set_count` before the `BinaryHeap::extend` call. A single reply to one outstanding request can therefore drive unbounded heap allocation and CPU work in the repair thread.

### Finding Description
When a `ParentAndFecSetCount` request is outstanding, `state.outstanding_requests.register_response` validates the nonce and calls `request.verify_response(&response)` [1](#0-0) . Assuming this succeeds (nonce matches, response not expired), control reaches the `ParentFecSetCount` match arm in `process_block_id_repair_response`:

```
state
    .pending_repair_requests
    .extend((0..fec_set_count).map(|i| {
        let fec_set_index = i * DATA_SHREDS_PER_FEC_BLOCK as u32;
        OutgoingMessage::Metadata(BlockIdRepairType::FecSetRoot {
            slot,
            block_id,
            fec_set_index,
        })
    }));
``` [2](#0-1) 

`fec_set_count` is a `u32` field taken directly from the deserialized, attacker-controlled `BlockIdRepairResponse::ParentFecSetCount` variant [3](#0-2) . There is no `min()`/cap applied against a `MAX_FEC_SET_COUNT`-style constant at this call site before the `extend`, unlike other bounded structures in this same file (e.g. `MAX_REPAIR_REQUESTS_PER_ITERATION`, `MAX_ALTERNATE_BLOCKS_PER_SLOT`, `MAX_PENDING_REPAIR_EVENTS` are all enforced elsewhere in `RepairState`) [4](#0-3) . If an attacker who is a legitimate repair peer replies to the real outstanding nonce with `fec_set_count` near `u32::MAX`, this single `.extend()` call attempts to construct billions of `OutgoingMessage::Metadata(BlockIdRepairType::FecSetRoot {..})` entries into the `BinaryHeap`, in one synchronous call on the repair processing thread (`process_responses` → `process_block_id_repair_response`), which runs inline in `run_repair_iteration` [5](#0-4) .

I was not able to fully verify, within available tool budget, whether `BlockIdRepairType::verify_response` (implemented in `core/src/repair/serve_repair.rs`, not fully inspected) independently bounds `fec_set_count` before this code path is reached; the grep results show many matches in that file but I could not confirm the exact verification logic for `ParentFecSetCount` in the time available. Based on the code actually read, no bound is enforced at or before the `extend` call in `block_id_repair_service.rs`.

### Impact Explanation
If `verify_response` does not independently reject overly large `fec_set_count` values, this is unbounded memory allocation and thread-stall (single-request DoS) matching the "unbounded cost for a single low-rate call" category — the repair thread would attempt to allocate and heap-insert an attacker-chosen number of entries (up to `u32::MAX`) from processing exactly one response packet to one legitimate outstanding request, without needing multiple calls or additional privilege.

### Likelihood Explanation
Preconditions: the attacker must be a peer selected to receive a `ParentAndFecSetCount` repair request (i.e., it must be a real outstanding nonce, requiring the attacker to be reachable as a repair peer and respond within the request's expiration window). Given that repair peers are chosen from cluster peer lists and any responsive peer/address can plausibly serve a repair reply, and that only the payload content (`fec_set_count`) is attacker-controlled with no visible bound check at the vulnerable call site, this is feasible with a single crafted packet if `verify_response` does not filter it — but this final gate is unverified.

### Recommendation
Clamp `fec_set_count` to a defined maximum (e.g., a `MAX_FEC_SET_COUNT_PER_BLOCK` constant reflecting realistic maximum FEC sets per block) either in `BlockIdRepairType::verify_response` or immediately before the `.extend()` call in `process_block_id_repair_response`, rejecting/truncating responses whose `fec_set_count` exceeds the bound, consistent with the other explicit caps already present in this module (`MAX_REPAIR_REQUESTS_PER_ITERATION`, `MAX_ALTERNATE_BLOCKS_PER_SLOT`).

    pub fn register_response<R>(
        &mut self,
        nonce: u32,
        response: &S,
        now: u64,
        success_fn: impl Fn(&T) -> R,
    ) -> Option<R> {
        let mut should_delete = false;
        let response = self.requests.get_mut(&nonce).and_then(|status| {
            if status.num_expected_responses == 0 {
                // No more expected responses
                return None;
            }

            if now >= status.expire_timestamp || !status.request.verify_response(response) {
                // Invalid/expired response should invalidate this nonce.
                should_delete = true;
                return None;
            }

            status.num_expected_responses -= 1;
            if status.num_expected_responses == 0 && status.metadata.is_none() {
                // No metadata, and no more expected responses safe to delete eagerly.
                should_delete = true;
            }
            Some(success_fn(&status.request))
        });
