### Title
Attacker can frontrun `setVault` with a dust ERC4626 deposit-on-behalf to permanently block vault migration - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary

The DYAD bug is a griefing vector: a permissionless "deposit into someone else's position" defeats a "position must be empty" check, letting anyone block a removal/migration. `ProgrammableBorrower.setVault` has the identical structure — it reverts unless the contract holds zero shares of the current ERC4626 vault — and ERC4626 `deposit(assets, receiver)` lets anyone mint dust vault shares directly to `ProgrammableBorrower`, so every `setVault` attempt can be frontrun and reverted at near-zero cost.

### Finding Description

In `contracts/strategies/idle/ProgrammableBorrower.sol`, `setVault` is the owner/manager function used to migrate the facility's idle-funds sleeve to a new ERC4626 vault. It enforces a hard precondition that the old position is fully unwound:

```solidity
function setVault(address _vault) external {
    _checkOnlyOwnerOrManager();
    if (_vault == address(0) || IERC4626(_vault).asset() != address(underlyingToken)) {
      revert InvalidAddress();
    }
    // Switching the accounting source is only safe once the current epoch is fully settled and the
    // old vault position has been unwound.
    if (epochAccountingActive || vault.balanceOf(address(this)) != 0) revert NotAllowed();
    underlyingToken.safeApprove(address(vault), 0);
    vault = IERC4626(_vault);
    ...
}
``` [1](#0-0) 

The guard `vault.balanceOf(address(this)) != 0` is exactly the same shape as DYAD's `Vault(vault).id2asset(id) > 0 → revert VaultHasAssets()`. In DYAD, anyone could call `vaultManager.deposit(id, vault, 1)` to force the check to fail; here, the ERC4626 standard itself provides the permissionless deposit-on-behalf: `vault.deposit(1, address(programmableBorrower))` mints 1 wei worth of shares to the facility, pulling the underlying from the attacker.

The operator's only recovery path is `emergencyExitVault(0)`, which redeems all shares back to underlying [2](#0-1) . But `emergencyExitVault` and `setVault` are two separate transactions with no atomic multicall/batching path, so the attacker can simply re-donate dust between them — or watch the mempool and frontrun every `setVault` retry. The window also requires `epochAccountingActive == false` [3](#0-2) , i.e., migration is only possible during the buffer period between epochs, giving the attacker a narrow, predictable, repeatable target window. Each `startEpoch` calls `_depositToVault` which re-fills the position anyway, so the attack only needs to be sustained during buffer periods.

The `NotAllowed` revert, `epochAccountingActive` gate, and `nonReentrant` guards do not stop this — the deposit happens on the external vault contract, not through `ProgrammableBorrower` at all.

### Impact Explanation

Temporary freezing of an administrative action with an ongoing cost asymmetry: the owner/manager cannot migrate the facility to a new ERC4626 vault (e.g., to escape a degraded or misconfigured vault, or rotate yield venues) for as long as the attacker keeps donating dust. The donated shares are credited to the facility, so the attacker's cost per block is bounded by the vault's minimum deposit rounding (often ~1 wei of underlying). The owner cannot bundle `emergencyExitVault` + `setVault` atomically since the contract exposes no multicall, so no privileged sequence permanently fixes the precondition. This mirrors the DYAD impact — the victim cannot complete a removal/migration and is forced to retry indefinitely or abandon the operation.

### Likelihood Explanation

The attack is cheap and permissionless: any EOA holding a dust amount of the underlying token can call `deposit` on the public ERC4626 vault. Motivation is griefing/competitive or preventing a risk-mitigating migration during a vault incident — precisely the moment `setVault` would be needed. The precondition (`vault.balanceOf == 0` during a buffer window) is observable on-chain and the mempool makes the target transaction visible, so the attack is reliably repeatable. The only mitigation factors are that the impact is a blocked admin action rather than direct fund loss, and the attacker must pay gas plus an unrecoverable dust donation per attempt.

### Recommendation

Same class of fix as DYAD's recommendation — do not make migration conditional on an attacker-controllable zero balance:

- Let `setVault` tolerate residual shares: redeem `vault.balanceOf(address(this))` via the existing `emergencyExitVault` logic inside `setVault` itself (atomic unwind-and-switch), or sweep leftover shares to the new vault / a recovery address.
- Alternatively, check `vault.convertToAssets(balanceOf)` against a dust threshold rather than strict zero, or track internally-deposited shares (`epochDepositedToVault`-style internal accounting) instead of the raw ERC4626 balance, so unsolicited share donations don't gate the migration.

### Proof of Concept

Foundry fork test against the deployed `ProgrammableBorrower` and its configured ERC4626 `vault`:

```solidity
function testGriefSetVaultWithDustDeposit() public {
    // setup: epoch is not active, facility has unwound its vault position
    // owner wants to migrate to newVault (same underlying asset)
    address newVault = address(newMockVault); // IERC4626(newVault).asset() == underlying

    // precondition holds: facility holds 0 shares of the old vault
    assertEq(programmableBorrower.vaultSharesBalance(), 0);

    // attacker observes setVault in the mempool and frontruns with a dust
    // deposit on behalf of the facility on the *old* vault
    IERC4626 oldVault = IERC4626(programmableBorrower.vault());
    underlying.approve(address(oldVault), 1);
    oldVault.deposit(1, address(programmableBorrower)); // mints dust shares to PB

    // owner's setVault now reverts
    vm.prank(owner);
    vm.expectRevert(NotAllowed.selector);
    programmableBorrower.setVault(newVault);

    // recovery attempt: redeem dust then retry — attacker re-frontruns
    vm.prank(owner);
    programmableBorrower.emergencyExitVault(0);

    underlying.approve(address(oldVault), 1);
    oldVault.deposit(1, address(programmableBorrower));

    vm.prank(owner);
    vm.expectRevert(NotAllowed.selector);
    programmableBorrower.setVault(newVault); // blocked again
}
```

The `emergencyExitVault`/`setVault` pair can be re-griefed indefinitely because there is no atomic path to clear the share balance and switch the vault in one transaction.

  function emergencyExitVault(uint256 _shares) external nonReentrant returns (uint256 assets) {
    _checkOnlyOwnerOrManager();
    if (_shares == 0) {
      _shares = vault.balanceOf(address(this));
    }
    if (_shares == 0) revert InvalidAmount();
    assets = vault.redeem(_shares, address(this), address(this));
    if (epochAccountingActive) {
      epochWithdrawnFromVault += assets;
    }
    emit RedeemedFromVault(_shares, assets, address(this));
```
