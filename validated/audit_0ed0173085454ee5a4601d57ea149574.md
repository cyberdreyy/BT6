### Title
Loss-adjusted withdraw receipt escapes its haircut when the user re-requests before claiming — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The kernel bug is an ordering flaw: a queue is cleared while callbacks that still reference its entries remain pending. The direct analog lives in `IdleCreditVault.claimWithdrawRequest`: `lastWithdrawRequest[_user]` stores only the *latest* request epoch, and `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch` only for that single epoch. If a user holds an unclaimed loss-adjusted receipt from an earlier epoch and makes a new withdraw request, the haircut bookkeeping for the old epoch is orphaned, and `_claimFundedWithdrawRequest` then pays the full un-haircutted `withdrawsRequests[_user]` aggregate at par — even though the strategy only ever received the haircut amount.

### Finding Description
- `requestWithdraw` records `withdrawsRequestsByEpoch[_user][currentEpoch]`, increments `withdrawsRequests[_user]`, and overwrites `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282-294`).
- When `stopEpochWithDuration` is called with `_lossAmount > 0`, `collectWithdrawFunds` funds only `pendingBasis - pendingLoss` and stores the haircut in `lossRecoveryPriceByEpoch[epochNumber]` (`IdleCreditVault.sol:411-430`).
- `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` (line 790). It can only ever process *one* epoch — the most recent request epoch.
- In `claimWithdrawRequest` (lines 301-314) the flow is: loss-adjusted claim for `lastWithdrawRequest` → funded claim for the whole `withdrawsRequests[_user]` remainder at par (`_claimFundedWithdrawRequest`, lines 319-350).
- Scenario: user requests in epoch E1; manager stops with a loss, so `lossRecoveryPriceByEpoch[E1] < RECOVERY_FULL` and the strategy is funded only `E1_basis * price`. The user does not claim and instead submits a new request in E2 — allowed by the documented "wait another epoch" semantics (lines 323-324). `lastWithdrawRequest` is now E2.
- After the next successful stop, the claim runs: `_claimLossAdjustedWithdrawRequest` checks `lossRecoveryPriceByEpoch[E2]`, which is 0, and returns 0 — the E1 haircut is silently skipped. `_clearWithdrawClaimForEpoch` is never invoked for E1, so `withdrawsRequests[_user]` still contains the full E1 basis. `_claimFundedWithdrawRequest` then pays `E1_basis + E2_amount` at par via `_transferFundedClaim`.
- The same orphaning occurs in the default path: `_claimDefaultedWithdrawRequest` clears the default epoch and resets `lastWithdrawRequest` to 0 (lines 832-835), so an older loss-adjusted receipt falls through to `_claimFundedWithdrawRequest` and is also paid at par.

### Impact Explanation
The user receives `E1_basis * (1 - lossRecoveryPrice)` more underlying than was ever funded for their receipt. Since `pendingWithdraws` was decremented by the funded (haircut) amount only, the overpayment is drawn from strategy underlyings backing other pending/funded receipts and active LPs — a direct violation of the loss waterfall (receipts must bear their pro-rata loss) and of solvency. The excess is a quantified, permanent theft: `excess = E1_basis - funded_E1`. No guard stops it: `requestWithdraw` does not check for outstanding loss-adjusted receipts, and the claim path's gating (`epochNumber <= lastWithdrawRequest`) passes because `lastWithdrawRequest` points at the newer, unhaircutted epoch.

### Likelihood Explanation
Fully attacker-controlled sequencing. The user only needs to (1) request a withdraw, (2) have the honest manager apply a loss via `stopEpochWithDuration(_lossAmount > 0)`, (3) refrain from claiming and submit any second withdraw request in a later buffer period, then (4) call `claimWithdrawRequest`. Any normal withdrawal-sized amount works, and in the default variant the same escape applies to receipts pending when the borrower defaults.

### Recommendation
Track loss-adjusted receipts per epoch rather than via the single `lastWithdrawRequest` marker. Either iterate all epochs with non-zero `withdrawsRequestsByEpoch[_user]` and apply each epoch's `lossRecoveryPriceByEpoch` before paying the funded remainder, or block `requestWithdraw` while the user has an unclaimed receipt in an epoch with a non-zero `lossRecoveryPriceByEpoch` (forcing claim first, so the haircut is applied before a new receipt is created).

### Proof of Concept
```solidity
// Foundry fork PoC (IdleCreditVault.t.sol harness style)
// 1) user deposits AA, owner starts epoch 1
idleCDO.depositAA(10_000 * oneScale);
_startEpochAndCheckPrices(0);

// 2) user requests withdraw during buffer of epoch 1 (epoch E1 = epochNumber)
cdoEpoch.requestWithdraw(0, address(AAtranche));
uint256 e1Basis = strategy.withdrawsRequests(user);

// 3) honest manager stops epoch WITH a loss: only e1Basis*(1-pendingLoss) is funded
//    and lossRecoveryPriceByEpoch[E1] < RECOVERY_FULL is stored
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(0, interest, newDuration, lossAmount); // lossAmount > 0
uint256 recoveryPrice = strategy.lossRecoveryPriceByEpoch(E1);
assertLt(recoveryPrice, RECOVERY_FULL);

// 4) user does NOT claim; in the next buffer they request again -> lastWithdrawRequest = E2
cdoEpoch.requestWithdraw(0, address(AAtranche));

// 5) epoch 2 runs and stops normally (no loss), funding E2 at par
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, interest2);

// 6) claim: _claimLossAdjustedWithdrawRequest looks up lossRecoveryPriceByEpoch[E2] == 0
//    and skips; _claimFundedWithdrawRequest pays (e1Basis + e2Amount) at par
uint256 balPre = underlying.balanceOf(user);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(user) - balPre;

// funded cash for E1 was only e1Basis * recoveryPrice / RECOVERY_FULL,
// but the user received full e1Basis -> excess drained from other claimants
assertGt(paid, e1Basis * recoveryPrice / RECOVERY_FULL + e2Amount);
```
