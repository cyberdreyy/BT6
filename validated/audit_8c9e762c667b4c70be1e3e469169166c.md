## Analog Confirmed

### Title
Stale confirmations from removed multisig members are still counted toward the execution threshold, allowing requests to execute below the live `num_confirmations` quorum - (`multisig2/src/lib.rs`)

### Summary
This is the same bug class as the Basin `GeoEmaAndCumSmaPump` report: a downstream accounting/state-counting mechanism (there: reserve-derived TWA oracle; here: the confirmation counter) is only correct if an invariant is externally maintained (there: "caller must never pass reserve=0"; here: "every counted confirmation must come from a currently-live member"), but the code that could break that invariant (`Well.swapFrom`/`_update` there; `delete_member` here) does not enforce it, so stale/invalid state silently counts toward a security-critical decision.

### Finding Description
`MultiSigContract::confirm` in `multisig2/src/lib.rs` decides whether a request executes purely by comparing the size of the `confirmations` set for a `request_id` against `self.num_confirmations`: [1](#0-0) 

Membership in `confirmations` is a `HashSet<String>` of member identifiers (`MultisigMember::to_string()`), populated whenever a member calls `confirm` without yet reaching quorum.

When a member is removed via `MultiSigRequestAction::DeleteMember` → `delete_member`, the contract only purges requests **created by** that member, and only removes that member's `num_requests_pk` entry and their entry from `self.members`: [2](#0-1) 

It does **not** scan the `confirmations` map to strip the removed member's identifier from confirmation sets of *other* still-open requests that member previously confirmed (but did not create). Since `current_member()` (used by `confirm`) is the only place membership is checked, and it is only checked for the *new* confirming caller — not retroactively for already-recorded confirmations — a confirmation recorded by an account/key that has since been deleted from `self.members` remains in the `confirmations` set and continues to count toward `confirmations.len() as u32 + 1 >= self.num_confirmations`.

Binding broken: `confirmations counted == live members who confirmed`. After a `DeleteMember` action, this becomes `confirmations counted > live members who confirmed`, because a stale entry from a no-longer-member persists.

### Impact Explanation
This falls squarely into the Critical impact category "a multisig request executed below threshold." Concretely:
1. Members A, B, C, D exist with `num_confirmations = 3`.
2. A creates request R (e.g., a `Transfer` of contract funds) via `add_request`.
3. B and C confirm R via `confirm`, but confirmations = {B, C} = 2 < 3, so it stays pending.
4. Separately, the remaining members execute a `DeleteMember` request removing C (e.g., because C's key was compromised or C is being offboarded). `delete_member` only removes requests *created* by C; R was created by A, so R and its confirmation set `{B, C}` are untouched.
5. Now only A, B, D are live members (3 total, `num_confirmations` still 3 — the `delete_member` assert `members.len() - 1 >= num_confirmations` guarantees at least 3 remain, but does not guarantee C's stale confirmation was purged).
6. A (or D) confirms R: `confirmations.len() as u32 + 1` = `2 + 1 = 3 >= 3` → executes, even though the confirming, still-live members are only A, B, D minus the fact that C's confirmation (a removed member) is one of the three counted votes. The request executes with only 2 genuinely current-member confirmations plus 1 stale one, i.e., below the intended live-member threshold.

This lets an operator execute a transfer, key addition, or arbitrary function call with fewer live approvals than the configured `K` in the `K`-of-`N` scheme, directly moving NEAR or granting access keys without proper authorization — matching "NEAR moved by a party not entitled to it" / "a multisig request executed below threshold."

### Likelihood Explanation
Reachable via ordinary, permitted multisig operations (no owner/foundation compromise required beyond the multisig's own members acting within their normal authority): create a request, get partial confirmation, then remove one of the confirming members through a routine `DeleteMember` request. No exploit of nearcore or off-chain infra is needed; it's a pure state-management gap in `delete_member`/`confirm`. Likelihood is Medium-to-High in any multisig that performs membership rotation (a very common lifecycle event) while requests are pending.

### Recommendation
When executing `DeleteMember`, iterate all entries in `self.confirmations` and remove the deleted member's identifier from every confirmation set (not just requests created by that member). Alternatively, in `confirm`, revalidate that every account/key in the stored confirmation set is still `self.members.contains(...)` before counting it toward quorum, discarding stale entries.

### Proof of Concept
Trace through `multisig2/src/lib.rs`:
1. `new(members=[A,B,C,D], num_confirmations=3)`.
2. `A.add_request(Transfer{...})` → `request_id=0`, `confirmations[0] = {}`. [3](#0-2) 
3. `B.confirm(0)` → `confirmations.len()+1 = 1 < 3` → `confirmations[0] = {B}`.
4. `C.confirm(0)` → `confirmations.len()+1 = 2 < 3` → `confirmations[0] = {B, C}`. [1](#0-0) 
5. Members execute a separate, already-quorum-approved request: `DeleteMember{C}` → `delete_member` runs; it only deletes requests where `r.member == C` (i.e., requests C *created*), not request 0 (created by A). `confirmations[0]` remains `{B, C}`, `self.members = {A,B,D}`. [2](#0-1) 
6. `D.confirm(0)` → `current_member()` returns `D` (valid, live member) → `confirmations.len()+1 = 2+1 = 3 >= 3` → `execute_request` runs the `Transfer`, even though C — one of the three counted approvers — is no longer a multisig member.

Note: I could not execute this against a live/compiled build in this environment; the trace above is derived directly from the reachable code paths in `multisig2/src/lib.rs` shown above, which do not contain any additional membership-revalidation logic for stored confirmations.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
