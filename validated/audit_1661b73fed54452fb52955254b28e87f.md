### Title
Post-default withdraw requests are paid 1:1 from `defaultRecoveryReserve`, over-draining the haircut-priced recovery pool and stealing funds owed to defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` has a dedicated post-default branch (lines 247–257) that mints a full `_amount` receipt and records it in `postDefaultRequests`. The corresponding claim path `_claimPostDefaultWithdrawRequest` pays that receipt **at par** out of `defaultRecoveryReserve` via `_transferDefaultRecovery`. The reserve, however, was sized at finalization to pay every unit of claim basis only `defaultRecoveryPrice` (`< RECOVERY_FULL` whenever the recovery is partial). Paying a new claimant at par while burning only `_amount` of already-haircutted CDO strategy tokens removes more underlying than the basis it frees, so each post-default request dilutes the recovery price for everyone whose defaulted-epoch receipts have not yet been claimed — a classic "state already consumed but still spendable" (UAF-style) accounting flaw.

### Finding Description
At `finalizeDefaultRecovery` the strategy computes:

- `totalBasis = activeBasis + pendingBasis`
- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`
- `defaultRecoveryReserve = reserveAmount` — exactly `totalBasis * recoveryPrice` worth of backing for all outstanding claims (pending withdraws, defaulted instant receipts, and active LP basis).

After finalization, an attacker who is a KYC'd tranche holder calls `IdleCDOEpochVariant.requestWithdraw`. The strategy branch executes:

```solidity
// IdleCreditVault.sol, requestWithdraw post-default path
_burn(msg.sender, _amount);          // burns CDO strategy tokens
_mint(_user, _amount);               // mints user receipt
postDefaultRequests[_user] = _amount;
```

Then `claimWithdrawRequest → _claimPostDefaultWithdrawRequest` does:

```solidity
postDefaultRequests[_user] = 0;
_burn(_user, amount);
_transferDefaultRecovery(_user, amount);   // pays `amount` at 1:1 from the reserve
```

Invariant check. Let `R = defaultRecoveryReserve`, `B` = remaining claim basis, `p = R/B < 1`. A post-default request of size `X` burns `X` basis units but pays `X` underlyings (not `pX`). After the call: `R' = R - X`, `B' = B - X`, so `R'/B' = (R - X)/(B - X) < p`. Each such request strictly lowers the effective recovery ratio; the attacker is overpaid by `X(1 - p)` per request relative to what the reserve can sustain. Repeating the flow (deposit is not required — any tranche holder with an existing position, or anyone who acquires tranche tokens, can iterate) drains the reserve until defaulted-epoch claims revert or are underpaid — directly breaking the "one receipt, recovery-priced payout" invariant.

Existing guards do not stop this: `requestWithdraw` only requires that the user have no prior unclaimed request; `_claimPostDefaultWithdrawRequest` has no cap against a fair share of the reserve; `defaultRecoveryReserve` is decremented in `_transferDefaultRecovery` without checking that paying at par is solvent.

### Impact Explanation
Direct theft / insolvency with quantified loss: with recovery price `p`, each post-default request of `X` extracts `X` but is only backed by `pX` of reserve capacity, stealing `X(1 - p)` from defaulted claimants. An attacker cycling requests can consume the entire `defaultRecoveryReserve`, leaving legitimate defaulted-epoch receipt holders (who waited one epoch before claiming) permanently underpaid or unable to claim — loss bounded only by reserve size, i.e. up to the full recovered amount.

### Likelihood Explanation
Requires only: a borrower default that was finalized with `recoveryPrice < 1` (any partial recovery), and an unprivileged user holding or acquiring tranche tokens to submit post-default `requestWithdraw`/`claimWithdrawRequest` calls. No privileged action is needed after finalization. The window is open until the reserve is exhausted, and every earlier claimer profits at the expense of later ones.

### Recommendation
Pay post-default receipts at `defaultRecoveryPrice` like every other claim (`amount = postDefaultRequests * defaultRecoveryPrice / RECOVERY_FULL`), or — since the CDO already haircuts `_amount` via the post-default `virtualPrice` — fund post-default claims from a distinct bucket rather than `defaultRecoveryReserve`, so they cannot cannibalize the fixed recovery pool.

### Proof of Concept
```solidity
// Foundry fork-style PoC (conceptual)
// Setup: deposit AA/BB, run epoch, borrower repays less than owed -> default.
cdoEpoch.startEpoch();
// borrower underpays at stopEpoch -> pool defaults
// manager finalizes with partial recovery, e.g. recoveryPrice = 0.5e18
strategy.finalizeDefaultRecovery(recovered / 2, recoverySource);
// victim V holds a defaulted-epoch withdraw receipt (claimBasis = 100e18, owed 50e18)

// Attacker A holds tranche tokens, has no prior request.
// Post-default: requestWithdraw burns CDO tokens and mints a receipt of
// haircutted size X = trancheValue * virtualPrice (still > 0).
cdoEpoch.requestWithdraw(trancheAmount, AATranche);   // postDefaultRequests[A] = X
cdoEpoch.claimWithdrawRequest();                      // pays X at par from reserve

// Attacker received X underlying while only pX of reserve was attributable.
// Repeating (or using a second account with no prior request) drains
// defaultRecoveryReserve; victim's _claimDefaultedWithdrawRequest then pays
// less than claimBasis * defaultRecoveryPrice or reverts on empty reserve.
assertLt(strategy.defaultRecoveryReserve(), expectedReserveAfterFairPayouts);
assertLt(victimPayout, victimBasis * defaultRecoveryPrice / RECOVERY_FULL);
```

Note: I verified the strategy-side accounting in `IdleCreditVault.sol` (requestWithdraw post-default branch, `_claimPostDefaultWithdrawRequest`, `finalizeDefaultRecovery` reserve sizing). I did not get to read the CDO-side `requestWithdraw` body in `IdleCDOEpochVariant.sol` to confirm the haircutted `_amount` hand-off and that post-default requests are not blocked upstream; the strategy's explicit post-default path and its comments ("CDO passes an already-haircut amount because finalization lowered virtualPrice") indicate the flow is intended and reachable.
