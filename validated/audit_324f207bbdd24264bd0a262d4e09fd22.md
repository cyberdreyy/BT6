The strongest reachable analog to the Treasury `deposit()` issue in this codebase is in the gateway's legacy web-API capability handler, where an explicit `// TODO: apply allowlist and rate-limiting here` marks a code path that forwards **any** signed user message to all DON nodes without enforcing an allowlist or rate limit — directly mirroring the "anyone can push unvalidated data into a shared resource that other legitimate operations depend on" bug class from the report.

### Title
Missing Allowlist/Rate-Limit Enforcement in Gateway `HandleLegacyUserMessage` Allows Unrestricted Forwarding of Trigger Requests to All DON Nodes - (`core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The gateway's `capabilities` handler forwards any incoming `web_api_trigger` user message to every node in the DON, but the allowlist and rate-limiting checks that are supposed to gate this forwarding are not implemented — the code contains a literal `// TODO: apply allowlist and rate-limiting here` comment at the exact point where such a check should occur.

### Finding Description
In `HandleLegacyUserMessage`, after basic payload decoding and a staleness check, the handler reaches the method-dispatch check with an explicit unfinished-security marker: `// TODO: apply allowlist and rate-limiting here` immediately preceding the `if msg.Body.Method != MethodWebAPITrigger` check. [1](#0-0) 

Once the method matches, the handler saves a callback, then unconditionally iterates over every DON member and sends the request to each node: [2](#0-1) 

There is no check tying the request to an authorized/allowlisted workflow owner, no per-sender quota, and no origin validation beyond the generic message signature/timestamp validation performed earlier in `ValidatedRequestFromMessage`. This is analogous to the Treasury `deposit()` bug: a caller-supplied payload (here, a trigger request) is accepted with insufficient validation and is then propagated into a shared resource (here, every DON node's inbound queue / `savedCallbacks` map) that other legitimate protocol operations (webhook/trigger processing across the whole DON) depend on.

The `savedCallbacks` map itself is bounded by `pruneCallbacks()` (`maxSavedCallbacks`, age-based eviction), which mitigates unbounded memory growth from this specific path, but the fan-out to all DON nodes with no allowlist check is still unmitigated. [3](#0-2) 

### Impact Explanation
Since any user message that passes the generic message envelope/signature/timestamp validation is forwarded to every node in the DON without an allowlist check, an unprivileged/unauthorized client can flood all DON nodes with trigger requests, consuming node-side processing capacity and potentially crowding out legitimate workflow triggers — a denial-of-service on protocol operations that depend on trigger delivery, similar in effect to the Treasury `_totalValue` DoS.

### Likelihood Explanation
The vulnerable code path is reached on the normal legacy user-message flow for the `web_api_trigger` method, which is a supported, documented method (`Methods()` returns `MethodWebAPITrigger`), so any client capable of producing a validly-formed and signed message reaches this code. The missing check is explicitly marked as not-yet-implemented (`TODO`), confirming it is a genuine gap rather than an intentional design choice. [4](#0-3) 

### Recommendation
Implement the allowlist and rate-limiting check referenced by the TODO comment before dispatching to `don.SendToNode`, restricting which senders/workflow owners may trigger a given DON, and apply per-sender quotas analogous to the existing `nodeRateLimiter` used for outgoing messages. [5](#0-4) 

### Proof of Concept
Not executable from available context — the gap is demonstrated directly by the source: the allowlist/rate-limit TODO comment sits directly above the unconditional per-member `SendToNode` fan-out loop, with no authorization check inserted between message validation and dispatch. [6](#0-5)

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
