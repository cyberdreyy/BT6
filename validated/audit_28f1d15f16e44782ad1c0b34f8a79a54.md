### Title
Unbounded TCP connection acceptance in the flashblocks WebSocket publisher `Listener` - (File: `crates/builder/publish/src/listener.rs`)

### Summary
The block builder's flashblocks `WebSocketPublisher` accepts TCP connections in an unbounded loop and spawns a task per connection with no cap on the number of concurrently accepted connections, no per-IP limiting, and no backpressure. This is the same bug class as the http4s-blaze-server advisory: connections are accepted and a socket/task is allocated for every incoming connection regardless of current load, unlike the sibling `websocket-proxy` service, which explicitly enforces `instance_connection_limit`/`per_ip_connection_limit` via a semaphore-based `RateLimit` before accepting.

### Finding Description
`Listener::run` binds a `tokio::net::TcpListener` and loops on `listener.accept()`, unconditionally spawning a new `tokio::spawn` task for every accepted connection to perform the WebSocket handshake and run a `BroadcastLoop`: [1](#0-0) 

There is no semaphore, counter, or `max_connections`-style gate anywhere in this accept loop — every accepted TCP connection results in a spawned task, an allocated socket handle, and (until the 10s handshake timeout fires or the WebSocket closes) an entry in the broadcast subscriber set: [2](#0-1) [3](#0-2) 

Contrast this with `crates/infra/websocket-proxy`, a similar flashblocks-broadcast component, which enforces a global connection semaphore and per-IP connection limits *before* upgrading to WebSocket: [4](#0-3) [5](#0-4) 

The `WebSocketPublisher` (the builder-side flashblocks publisher) has no equivalent limiting mechanism — `WebSocketPublisher::with_capacity` only configures broadcast-channel and ring-buffer capacities, not connection limits: [6](#0-5) 

The project's own README documents this component as accepting connections from "clients" without describing any connection cap, unlike the `websocket-proxy` README, which documents `--instance-connection-limit`/`--per-ip-connection-limit`: [7](#0-6) 

### Impact Explanation
An attacker (or misbehaving/compromised client population) reachable to the flashblocks publisher's TCP port can open connections without bound. Each accepted connection allocates a kernel socket handle and a spawned Tokio task holding a broadcast-channel `Receiver` (via `receiver.resubscribe()`), consuming file descriptors and memory. Because there is no cap, connection acceptance is not backpressured to the process's or host's actual resource limits — sustained connection opening degrades or exhausts file-descriptor/memory limits, which can stall or crash the flashblocks publisher within the builder process. Given flashblocks pending-state distribution is on the block-building critical path (feeding downstream RPC/consumer nodes with pending-state updates), degradation here can delay or drop flashblocks delivery, impacting the freshness of pending-state data served to `eth_*`/WS clients downstream — a resource-exhaustion/availability issue matching CWE-400/CWE-770, analogous to the referenced blaze-core advisory.

### Likelihood Explanation
Exploitability depends on network reachability of the publisher's bind address; the severity of the underlying report (High, CVSS AV:N) stems from that same class of bug being reachable to any network client that can complete TCP handshakes to the listening port, with no authentication or per-IP/global cap required before a socket/task is consumed. Within this repository the port is deliberately created to serve flashblocks WebSocket subscribers, so any party permitted to reach that port (which may include downstream RPC nodes or, depending on deployment/network topology, a wider set of peers) can trigger unbounded resource consumption purely by opening TCP connections and never completing/using the WebSocket handshake meaningfully.

### Recommendation
Add a `max_connections` (and ideally per-IP) admission gate to `Listener::run`, mirroring the `InMemoryRateLimit`/semaphore pattern already used in `crates/infra/websocket-proxy`, so that `listener.accept()` is followed by a bounded-capacity check before a task is spawned and a socket is retained; reject/close connections beyond the configured limit instead of unconditionally spawning a handler.

### Proof of Concept
1. Start a `WebSocketPublisher` bound to a reachable address (as created via `WebSocketPublisher::new`/`with_capacity`).
2. From an attacking client, open TCP connections to the publisher's address in a tight loop without completing the WebSocket handshake (or completing it and then idling), e.g., thousands of concurrent `TcpStream::connect` calls.
3. Observe `Listener::run`'s `listener.accept()` branch fires for every connection and unconditionally `tokio::spawn`s a handler task, with no rejection path — file descriptors/memory grow unbounded, exhausting the builder process's resource limits, potentially crashing or stalling flashblocks publishing for legitimate downstream subscribers.

```rust
#[derive(Debug)]
struct Inner {
    active_connections: HashMap<IpAddr, usize>,
    semaphore: Arc<Semaphore>,
}

/// In-memory rate limiter that tracks connections per IP and globally.
#[derive(Debug)]
pub struct InMemoryRateLimit {
    per_ip_limit: usize,
    inner: Mutex<Inner>,
}

impl InMemoryRateLimit {
    /// Create a new in-memory rate limiter with the given limits.
    pub fn new(instance_limit: usize, per_ip_limit: usize) -> Self {
        Self {
            per_ip_limit,
            inner: Mutex::new(Inner {
                active_connections: HashMap::new(),
                semaphore: Arc::new(Semaphore::new(instance_limit)),
            }),
        }
    }
}

impl RateLimit for InMemoryRateLimit {
    fn try_acquire(self: Arc<Self>, addr: IpAddr) -> Result<Ticket, RateLimitError> {
        let mut inner = self.inner.lock().unwrap_or_else(|e| e.into_inner());

        let permit = Arc::clone(&inner.semaphore).try_acquire_owned().map_err(|_| {
            RateLimitError::Limit {
                reason: "Global limit".to_owned(),
                limit_type: RateLimitType::Global,
            }
        })?;

        let current_count = inner.active_connections.get(&addr).copied().unwrap_or(0);

        if current_count + 1 > self.per_ip_limit {
            debug!(message = "Rate limit exceeded, trying to acquire", client = addr.to_string());
            return Err(RateLimitError::Limit {
                reason: String::from("IP limit exceeded"),
                limit_type: RateLimitType::PerIp,
            });
        }

        let new_count = current_count + 1;

        inner.active_connections.insert(addr, new_count);

        let rate_limiter: Arc<dyn RateLimit> = Arc::clone(&self) as Arc<dyn RateLimit>;
        Ok(Ticket { addr, _permit: permit, rate_limiter })
    }
```

```rust
fn websocket_handler(
    state: ServerState,
    ws: WebSocketUpgrade,
    addr: SocketAddr,
    headers: HeaderMap,
    filter: FilterType,
) -> Response {
    let connect_addr = addr.ip();
    let client_addr = state.trusted_proxy_config.client_ip(connect_addr, &headers);

    let ticket = match state.rate_limiter.try_acquire(client_addr) {
        Ok(ticket) => ticket,
        Err(RateLimitError::Limit { reason, limit_type }) => {
            match limit_type {
                RateLimitType::PerIp => {
                    info!(
                        message = "per-IP rate limit exceeded",
                        client_ip = client_addr.to_string(),
                        reason = reason
                    );
                    Metrics::per_ip_rate_limited_requests().increment(1);
                }
                RateLimitType::Global => {
                    Metrics::global_rate_limited_requests().increment(1);
                }
            }

            return Response::builder()
                .status(StatusCode::TOO_MANY_REQUESTS)
                .body(Body::from(json!({"message": reason}).to_string()))
                .unwrap();
        }
    };
```

```rust
        Self::with_capacity(addr, DEFAULT_CHANNEL_CAPACITY, DEFAULT_RING_BUFFER_CAPACITY)

    /// Creates a new `WebSocketPublisher` with custom broadcast channel and
    /// ring buffer capacities.
    ///
    /// The channel capacity determines how many messages can be buffered before
    /// slow subscribers begin lagging. The ring buffer capacity controls how
    /// many recent messages are retained for reconnection replay.
    pub fn with_capacity(
        addr: SocketAddr,
        channel_capacity: usize,
        ring_buffer_capacity: NonZeroUsize,
    ) -> std::io::Result<Self> {
        let (pipe, _) = broadcast::channel(channel_capacity);
        let cancel = CancellationToken::new();
        let metrics: Arc<dyn PublisherMetrics> = Arc::new(PublishingMetrics);
        let ring_buffer = Arc::new(RwLock::new(RingBuffer::new(ring_buffer_capacity)));

        let std_listener = std::net::TcpListener::bind(addr)?;
        std_listener.set_nonblocking(true)?;
        let listener = tokio::net::TcpListener::from_std(std_listener)?;

        tokio::spawn(
            Listener::new(
                listener,
                Arc::clone(&metrics),
                pipe.subscribe(),
                Arc::clone(&ring_buffer),
                cancel.child_token(),
            )
            .run(),
        );

        Ok(Self { cancel, pipe, metrics, ring_buffer })
    }
```

```markdown
WebSocket broadcast publisher for the Base block builder. Accepts WebSocket connections from clients and broadcasts serialized payloads to all connected subscribers.

## Overview

- **`WebSocketPublisher`**: Top-level API that binds a TCP listener, accepts WebSocket connections, and broadcasts serialized messages to all subscribers. Metrics are registered automatically.
- **`Listener`**: Accepts incoming TCP connections, upgrades them to WebSocket, and spawns a `BroadcastLoop` for each client.
- **`BroadcastLoop`**: Per-client send loop that forwards broadcast messages to a single WebSocket stream.
- **`PublishingMetrics`**: Concrete metrics implementation backed by the `metrics` crate, registered under the `base_builder` scope.
- **`PublisherMetrics`**: Trait abstracting metrics collection for message sends, connection lifecycle, and lag detection.
```
