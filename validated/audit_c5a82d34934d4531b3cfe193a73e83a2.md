### Title
Missing `state_exists` guard in `LockupContract::new` allows re-initialization of an existing lockup, releasing locked/unvested `VestingHash` tokens - (File: lockup/src/lib.rs)

### Summary
`LockupContract::new` (lines 180-243) is the `#[init]` constructor, but unlike every sibling contract in this repository it never calls `assert!(!env::state_exists(), ...)`. [1](#0-0)  Because the method is a normal public `near_bindgen` function with no self/owner check, and near-sdk's `#[init]` macro at this version does not itself enforce single-initialization (every other contract — factory, multisig, staking-pool, staking-pool-factory, voting, whitelist — explicitly re-implements this check), any account can invoke `new` a second time against an already-deployed, already-funded lockup account and completely overwrite its state.

### Finding Description
The invariant the question asks to validate is: `lockup_information/vesting_information/owner_account_id written at deploy time == lockup_information/vesting_information/owner_account_id at any later read`. `new` should execute exactly once per account.

Compare `LockupContract::new` to its siblings:
- `lockup-factory/src/lib.rs` `new`: `assert!(!env::state_exists(), "The contract is already initialized");` [2](#0-1) 
- `staking-pool/src/lib.rs` `new`: `assert!(!env::state_exists(), "Already initialized");` [3](#0-2) 
- `staking-pool-factory/src/lib.rs`, `multisig/src/lib.rs`, `voting/src/lib.rs`, `whitelist/src/lib.rs` all do the same. [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

`lockup/src/lib.rs`'s `new` begins straight with account-ID validity asserts and never checks `env::state_exists()` before constructing and returning `Self { .. }`: [8](#0-7) . The `#[near_bindgen]`/`#[init]` expansion writes whatever `Self` is returned to contract storage; it does not itself refuse to run if storage already holds a previous `LockupContract`. Since every other in-repo contract had to add the check manually, its absence here is a real gap, not framework-guaranteed safety.

Exploit flow:
1. A victim (owner) has a real lockup deployed via `lockup-factory::create`, initialized with `Some(VestingScheduleOrHash::VestingHash(hash))` and a real unvested balance held in the account. [9](#0-8) 
2. An unprivileged attacker (any account, no keys on the victim account, no owner rights) sends a plain `FunctionCall` transaction to the victim lockup account, calling `new` again with attacker-chosen arguments: `owner_account_id = attacker`, `vesting_schedule = Some(VestingScheduleOrHash::VestingHash(attacker_hash))` (or `None`), and any `lockup_timestamp`/`release_duration` they like.
3. `new` recomputes `lockup_amount = env::account_balance()` (the full current balance, including the funds that were still locked/unvested under the old vesting schedule) and overwrites `owner_account_id`, `lockup_information`, `vesting_information`, resets `staking_information: None`. [10](#0-9) 
4. Because vesting is now `VestingInformation::VestingHash` with a hash the attacker controls (or `None`), and `get_locked_amount`/`get_owners_balance` treat `VestingHash` vesting as contributing `U128(0)` unvested for un-revealed-schedule view purposes (only revealed at termination via `assert_vesting`) [11](#0-10) , the attacker (now `owner_account_id`) can immediately call owner methods to transfer out the full balance that used to be locked/unvested to the original owner and reserved for the NEAR Foundation on termination.

No existing guard stops this: there is no `assert_self`, no `assert_owner`, no `assert_called_by_foundation`, and — critically — no `state_exists` check inside `new`.

### Impact Explanation
This is Critical: NEAR that was locked/unvested and belonged to the original owner (and, in case of termination, to the NEAR Foundation) is released to an attacker who redefines themselves as the contract's `owner_account_id`. The attack is repeatable against any lockup account whose account ID and balance the attacker can target (all lockup account IDs are derivable deterministically from `sha256(owner_account_id)` per `lockup-factory::create` [12](#0-11) , so no secrecy protects them), so the blast radius covers every deployed lockup contract using this codebase.

### Likelihood Explanation
The attacker needs only their own funded NEAR account and gas to send a `FunctionCall("new", …)` transaction to the target lockup account ID — no attached deposit is required to call `new` again (it is not `#[payable]`-gated against re-entry), no key on the victim account, no multisig or foundation role. This is directly exploitable via a plain `near-sdk-sim`/`near-workspaces` transaction and is fully repeatable across every lockup contract account.

### Recommendation
Add `assert!(!env::state_exists(), "The contract is already initialized");` as the first line of `LockupContract::new` in `lockup/src/lib.rs`, matching every other contract in the repository.

### Proof of Concept
```rust
// lockup/tests/spec.rs - new test
#[test]
fn test_double_init_takeover() {
    // 1. Deploy lockup with VestingHash and a real balance, owner = "owner1".
    // 2. Assert get_owners_balance()/get_liquid_owners_balance() reflect locked state under owner1.
    // 3. From an unrelated attacker account, call `new` again on the same lockup_account_id with
    //    owner_account_id = "attacker", vesting_schedule = None (or an attacker-chosen VestingHash),
    //    and the same/other args.
    // 4. EXPECT (bug present): call succeeds (no panic), contract.get_owner_account_id() == "attacker",
    //    contract.get_locked_amount() == 0 or attacker-controlled value, and attacker can withdraw
    //    the account's full balance via owner methods.
    // 5. FIX ASSERTION: after adding `assert!(!env::state_exists(), ...)`, the second `new` call
    //    must panic with "The contract is already initialized", leaving owner_account_id == "owner1"
    //    and vesting/lockup fields unchanged.
}
```
The two sides of the equality to assert on both before/after: `owner_account_id_before == owner_account_id_after` and `vesting_information_before == vesting_information_after`; the PoC demonstrates they diverge without the fix and match with it.
