## Analysis

`switch_operator` reuses the **same** `StakingContract` struct (and therefore the same `distribution_pool: Pool`) when moving a contract from `old_operator` to `new_operator` — it only re-keys the outer `SimpleMap` from `old_operator` to `new_operator` [1](#0-0) . The inner `pool_u64::Pool` still contains a share entry for `old_operator` for any commission that was requested but not yet distributed (via `request_commission_internal`, which is forced to run right before the switch) [2](#0-1) .

The problem is in `update_distribution_pool`, which is invoked on every subsequent `add_distribution`/`distribute_internal` call with the *current* operator (now `new_operator`) and the *current* `commission_percentage` (the new rate chosen by whoever calls `switch_operator`, up to 100%): [3](#0-2) 

It taxes **every shareholder except the current `operator` parameter** on growth of their balance in the pool and transfers those shares to the current operator as "commission." Since the pool's `total_coins` (backed by `inactive + pending_inactive` stake, which keeps earning rewards until fully unlocked) grows over time, `old_operator`'s already-earned-but-undistributed balance is treated as if it were fresh staker principal subject to commission — and that commission is paid to `new_operator`, not `old_operator`. With `new_commission_percentage` settable up to 100 at switch time, an attacker controlling the (previously-unused) `new_operator` address can capture reward growth that rightfully belongs to `old_operator`'s pending distribution.

Separately, `distribute_internal`'s beneficiary-redirect logic only fires when `recipient == operator` (the function's `operator` parameter, which after a switch is `new_operator`) [4](#0-3) . Any leftover distribution belonging to `old_operator` is paid directly to the `old_operator` address instead of `old_operator`'s registered `BeneficiaryForOperator`, silently bypassing the beneficiary configuration set up before the switch.

The existing regression test `test_staker_can_switch_operator` only checks that the *principal amount* of old_operator's commission is preserved right after the switch and before any further reward accrual on the pending distribution [5](#0-4) ; it does not let further epochs pass with `old_operator`'s undistributed commission sitting in the pool before checking the final amount old_operator receives, so this skimming path is not covered.

### Title
Cross-operator commission skimming via shared distribution pool in `switch_operator` - (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` reassigns a staking contract (including its shared `distribution_pool`) from `old_operator` to `new_operator` without segregating each operator's pending, already-earned distribution shares. `update_distribution_pool` subsequently charges the *new* operator's commission rate on growth of *all* shareholders' balances except the current operator, and pays that "commission" to the current operator. This lets the new operator (an address not previously known to the staker's `Store`, satisfying the "attacker-controlled unused address" precondition) capture value out of `old_operator`'s already-vested, undistributed commission as it continues to earn rewards while pending withdrawal. Additionally, the beneficiary-redirect check `recipient == operator` in `distribute_internal` never matches `old_operator`, so `old_operator`'s registered beneficiary is bypassed for the leftover balance.

### Impact Explanation
Value (staking rewards accrued on `old_operator`'s not-yet-distributed commission) is redirected to `new_operator`, an address the staker never previously trusted with any commission share, and away from `old_operator`/`old_operator`'s beneficiary. This is a commission/share-accounting corruption that credits the wrong account, falling squarely within the "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account" impact family.

### Likelihood Explanation
This triggers on the ordinary, permissionless `switch_operator` entry function whenever (a) `old_operator` has an outstanding, requested-but-undistributed commission in the pool at switch time, and (b) any epochs pass with that pending amount still earning rewards before it's finally redeemed. Both conditions are common in normal validator operation (commission requests followed by lockup delay before withdrawal), so no special attacker capability beyond registering an unused address as `new_operator` is required.

### Recommendation
`update_distribution_pool` should not charge commission on shareholders that are not the staker's current stake principal — i.e., pending distributions belonging to a former operator (or already-settled shares) should be excluded from commission recalculation, or `switch_operator` should force a full `distribute_internal` (paying out, not merely computing) for `old_operator`'s existing shares before reassigning the `distribution_pool`'s underlying commission rate/operator context. The beneficiary redirect in `distribute_internal` should also check `beneficiary_for_operator` per-recipient rather than only for the single `operator` parameter, so a former operator's beneficiary continues to receive payouts correctly.

### Proof of Concept
1. Staker creates a staking contract with `operator_1`, `commission_percentage = 10`.
2. Validator earns rewards; `operator_1` calls `request_commission`, moving commission into `distribution_pool` as pending shares for `operator_1` (not yet unlocked/withdrawn) — see `request_commission_internal` [6](#0-5) .
3. Before the lockup unlocks (so the commission is still `pending_inactive` and still earning rewards), staker calls `switch_operator(staker, operator_1, attacker_operator, 100)`.
4. Several more epochs pass; the `pending_inactive` amount backing `operator_1`'s pool shares grows due to rewards.
5. `attacker_operator` calls `request_commission`/`distribute`, which invokes `update_distribution_pool` with `operator = attacker_operator`, `commission_percentage = 100`. Since `operator_1 != attacker_operator`, the growth of `operator_1`'s share value is fully taxed at 100% and transferred to `attacker_operator`.
6. When `distribute` is finally called, `operator_1` receives less than the value it was owed at switch time (only the pre-growth principal, not the accrued rewards on the pending commission), while `attacker_operator` receives the difference — despite never having earned it. [7](#0-6)
