### Title
Withdraw receipts are permanently locked when the recorded claimant can no longer receive the underlying, with no way to redirect the payout - (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
In the external report, `withdrawToken()` always sends the escrowed NFT to a stored `bull` address; if that address cannot receive NFTs, the asset is locked forever because there is no `to` parameter and no alternative path.

The same structure exists in `IdleCreditVault`: every withdrawal claim path (`_claimFundedWithdrawRequest`, `_claimLossAdjustedWithdrawRequest`, `_claimPostDefaultWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `claimInstantWithdrawRequest`) hardcodes the payout recipient to the address-bound `_user` via `_transferFundedClaim(_user, amount)` / `_transferDefaultRecovery(_user, amount)` (`IdleCreditVault.sol:906`, `IdleCreditVault.sol:916`). At the same time, receipt strategy tokens are non-transferable: `_transfer` reverts unless `msg.sender == idleCDO`, and `setCanTransfer(true)` is permanently disabled (`IdleCreditVault.sol:939-951`). So if the recorded claimant address becomes unable to receive the underlying (e.g., a USDC-blacklisted contract wallet, a sanctioned EOA, an exchange deposit account that rejects the credit), every claim reverts and there is no mechanism — neither a `to` parameter nor token transfer — to redirect the payout. The underlyings remain locked in `IdleCreditVault` (or in `defaultRecoveryReserve`) forever.

### Finding Description
- `requestWithdraw` records the claim under `_user` and mints receipt strategy tokens to `_user` (`IdleCreditVault.sol:275`, `:282`, `:292-293`).
- `claimWithdrawRequest(_user)` is only callable by `idleCDO`, which always passes `msg.sender` as `_user`; the internal claims settle via `underlyingToken.safeTransfer(_user, _amount)` in `_transferFundedClaim` (`IdleCreditVault.sol:897-907`) and `_transferDefaultRecovery` (`IdleCreditVault.sol:912-917`). There is no recipient parameter.
- The receipt token cannot be moved to a healthy wallet: `_transfer` reverts `NotAllowed` for anyone but `idleCDO` (`IdleCreditVault.sol:939-942`), and `setCanTransfer` only allows clearing the flag (`IdleCreditVault.sol:948-951`). The test `testReceiptTransfersRemainDisabledAfterDefault` codifies this binding (`test/foundry/IdleCreditVault.t.sol:4678-4687`).
- Contrast with `DefaultDistributor.claim(address _to)` (`contracts/DefaultDistributor.sol:35-40`), which does allow choosing a payout address — so the codebase has a "safe" claim pattern in one place and the vulnerable one elsewhere.
- Unlike the NFT case, a plain ERC20 transfer does not invoke a receiver hook, so the realistic trigger is a token-level restriction on the recipient (USDC/USDT blacklist, frozen account) or the claimant address being a contract/account that the token refuses to pay. In that scenario `safeTransfer` reverts on every attempt, forever.

Scenario (running epoch, non-prefunded variant):
1. Alice is a KYC-passed lender using a smart-contract wallet; she calls `requestWithdraw` in the buffer period and receives an address-bound receipt (`IdleCreditVault.sol:275`).
2. The epoch stops; `collectWithdrawFunds` pulls the borrower's repayment into the strategy (`IdleCreditVault.sol:411-430`). Her claim is now funded.
3. Alice's wallet address lands on the underlying token's blacklist (or her custody account is frozen). She calls `claimWithdrawRequest` → `_transferFundedClaim` → `safeTransfer(Alice, amount)` reverts.
4. She cannot sell/transfer the receipt (`_transfer` reverts), cannot name an alternate recipient (no `to` parameter), and cannot selfdestruct-and-redeploy the claim because receipts are keyed to her address. The funded underlyings sit in `IdleCreditVault` permanently; `defaultRecoveryReserve` bookkeeping can also trap funds in the defaulted/finalized paths for the same reason.

### Impact Explanation
Permanent freezing of a funded withdraw claim. Once the borrower funds `pendingWithdraws`, the underlyings are reserved for the receipt holders, but an unreceivable claimant can never withdraw them, and the non-transferable receipt prevents any secondary-market exit. Loss = the full `claimBasis` of the stuck receipt (and its recovery-priced equivalent in `_claimDefaultedWithdrawRequest` / `_claimPostDefaultWithdrawRequest`). The solvency/fair-redemption invariant "one receipt → one payout" is violated: the payout leg exists but is unreachable.

### Likelihood Explanation
Medium-low. It requires the claimant address to be token-blocked (stablecoin blacklist/sanction) — an external event, not attacker-engineered — matching the original report's "honest user whose address can't receive" framing rather than a malicious lock. It is not exploitable for theft and cannot be triggered by an unprivileged attacker against a healthy EOA, since ERC20 sends to EOAs/ordinary contracts do not revert. The finding is primarily a missing-escape-hatch/permanent-freeze issue, so it sits at the weaker end of the accept criteria ("permanent freezing" is listed, but quantified loss depends on an out-of-scope token-level cause).

### Recommendation
Add an explicit recipient parameter to the claim flow, mirroring `DefaultDistributor.claim(_to)`:
- `claimWithdrawRequest(address _to)` / `claimInstantWithdrawRequest(address _to)` in `IdleCDOEpochVariant`, forwarding `_to` down to `IdleCreditVault.claimWithdrawRequest(_user, _to)`, with `_transferFundedClaim(_to, amount)` / `_transferDefaultRecovery(_to, amount)`.
- Keep receipts address-bound (authorization stays keyed to `msg.sender`), only the payout destination becomes configurable. Alternatively, allow the receipt-holder to redirect via a signed approval or permit an `onlyIdleCDO` rescue path after governance review.

### Proof of Concept
Sketch of a Foundry PoC on the existing harness (`test/foundry/IdleCreditVault.t.sol`); requires an underlying mock that can block a recipient (e.g., a `MockERC20` with a `blocked` mapping that reverts in `transfer`):

```solidity
function testClaimLockedForBlockedRecipient() external {
    address aliceContract = address(blockingWallet); // e.g. a contract whose address gets token-blocked
    uint256 amount = 10_000 * ONE_SCALE;

    _depositWithUser(aliceContract, amount, true);
    vm.prank(aliceContract);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch()); // claim now funded in strategy

    // token-level block on recipient (USDC blacklist analogue)
    underlying.setBlocked(aliceContract, true);

    // claim always reverts: recipient is hardcoded to _user
    vm.startPrank(aliceContract);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
    vm.stopPrank();

    // receipt cannot be moved to another wallet either
    vm.prank(aliceContract);
    vm.expectRevert(NotAllowed.selector);
    IERC20Detailed(address(strategy)).transfer(makeAddr("backup"), 1);

    // funds permanently stranded in IdleCreditVault
    assertGt(underlying.balanceOf(address(strategy)), 0);
}
```

Caveat: the PoC hinges on a token-mock `blocked` flag to emulate a blacklist/frozen recipient; without that external condition the revert path is unreachable for normal ERC20 tokens, which is the main weakness of this analog relative to the original NFT receiving-hook scenario.
