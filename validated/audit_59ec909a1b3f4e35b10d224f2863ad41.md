### Title
Unescaped `\r` in `EscapeForPosix` allows forged `section_start:`/`section_end:` trace markers when `posix_escape` is enabled - (File: functions/script_legacy/internal/trace_section.go)

### Summary
`writeSectionStart` embeds the escaped command preview into the same `printf` line that carries the real `section_start:` marker, relying on `escape()` to neutralize control characters. When `posix_escape` is true, `escape()` routes through `EscapeForPosix` [1](#0-0) , which — unlike `EscapeForAnsiC` — never escapes `\r`, `\n`, or any other control character [2](#0-1) . A job whose command text contains a raw carriage return followed by literal ASCII `section_end:...` or `section_start:...` text will have that byte sequence pass through unmodified into the trace stream that GitLab's frontend parses for section boundaries.

### Finding Description
`WriteSection` calls `writeSectionStart(buf, sectionName, command)`, which does:

```go
command = w.escape(ansiBoldGreen + commandPrefix + command + ansiResetTrace)
fmt.Fprintf(buf, "printf '%%s\\n' section_start:%s:section_%s[%s]\r%s%s\n", ...)
``` [3](#0-2) 

The attacker-controlled `command` (a job `script` entry, fully author-controlled) is concatenated as a single shell word right after the runner's own `\r<ansiClear>` sequence in the same `printf` argument. The only thing preventing the command text from containing byte-for-byte `\r` + `section_start:`/`section_end:` is the `escape()` routing:

```go
func (w *TraceSectionWriter) escape(input string) string {
	if w.posixMode {
		return EscapeForPosix(input)
	}
	return "$'" + EscapeForAnsiC(input) + "'"
}
``` [4](#0-3) 

`EscapeForAnsiC` (the non-POSIX / default path) explicitly hex/backslash-escapes every control character including `\r` (`case '\r': buf.WriteString("\\r")`, plus a catch-all hex-escape for bytes `<0x20`) [5](#0-4) . This is confirmed by its own test suite explicitly asserting CR and ESC sequences are turned into literal `\r`/`\xNN` text, not raw bytes [6](#0-5) .

`EscapeForPosix`, used when `posix_escape` (mapped from `FF_POSIXLY_CORRECT_ESCAPES`) is enabled, only handles a small set of shell metacharacters (`` ` ``, `"`, `\`, `$`, and a short list of characters requiring double-quoting) and otherwise writes runes through untouched via `default: buf.WriteRune(r)` [2](#0-1) . `\r` and `\n` are not in the switch at all, so a raw carriage return in the command text is emitted verbatim inside the double-quoted (or unquoted) shell literal. That literal is passed to `printf '%s\n' ...`, so the shell prints the raw `\r` byte followed by whatever literal text follows it directly to the job's stdout/trace stream — the exact stream GitLab's frontend regex-parses for `section_start:`/`section_end:` markers (which match markers positioned right after a `\r` reset, since the runner's own real markers use that same convention).

Because `sectionName`/`timestampCommand` are runner-generated and not reachable by job input, the *legitimate* marker is safe; but the *invariant that only runner text can contain a literal `section_start:`/`section_end:` immediately following a `\r`* is broken specifically for the POSIX-escaping code path, since job-controlled bytes can supply their own `\r` + fake marker text within the same printf argument, at a byte position the frontend's line-boundary detection will treat as a legitimate new line/marker.

### Impact Explanation
An unprivileged job author (anyone who can define `script:` entries or CI variables consumed as script content, when `posix_escape`/`FF_POSIXLY_CORRECT_ESCAPES` is in effect) can inject a raw CR followed by a forged `section_end:<fake-timestamp>:section_x\r` sequence inside the command-preview text. Once the trace log frontend re-renders/line-splits on `\r`, this forged text is indistinguishable from a genuine section boundary, letting an attacker close a legitimate section prematurely (hiding subsequent output visually in the collapsed/ended section) or reopen a spoofed section with attacker-chosen name/label. This is a trace-log/UI integrity issue (log spoofing to mislead reviewers), not a sandbox escape or secret leak.

### Likelihood Explanation
Requires: (1) the `posix_escape` input / `FF_POSIXLY_CORRECT_ESCAPES` feature flag enabled, and (2) `trace_sections` enabled so `WriteSection` is invoked, both of which are configuration choices, not attacker-controlled toggles directly, so exploitability is conditional on the runner/pipeline configuration. Given those preconditions, any job author can trivially embed a literal CR byte in a script line (e.g., via `$'...\r...'`, a CI/CD variable containing a CR, or heredoc/base64-decoded content), making the injection itself fully reproducible and repeatable once the mode is active.

### Recommendation
Make `EscapeForPosix` escape all C0 control characters (0x00–0x1F, 0x7F) — at minimum `\r` and `\n` — the same way `EscapeForAnsiC` does, either by hex-escaping them or by switching quoting strategy so control bytes cannot survive into the shell literal, restoring symmetry between the two escaping paths and preserving the invariant that only runner-generated bytes can produce a `\r`-adjacent `section_start:`/`section_end:` token.

### Proof of Concept
Go unit test in `functions/script_legacy/internal/trace_section_test.go`:
```go
func TestTraceSectionWriter_PosixMode_CRInjection(t *testing.T) {
    writer := NewTraceSectionWriter(false, true) // posixMode = true
    var buf strings.Builder

    malicious := "echo hi\rsection_end:0:section_script_step_0\r\x1b[0Ksection_start:0:section_fake[collapsed=true]\r\x1b[0K"
    writer.WriteSection(&buf, 0, malicious)
    result := buf.String()

    // Assert the raw CR + literal marker text survived unescaped into the
    // generated shell script (i.e., will be echoed byte-for-byte to trace stdout).
    assert.Contains(t, result, "\rsection_end:0:section_script_step_0\r")
    assert.Contains(t, result, "\rsection_start:0:section_fake[")
}
```
Expected: assertions pass, proving that job-controlled `\r`+marker text is not neutralized by `EscapeForPosix`, whereas an equivalent test with `posixMode=false` (ANSI-C path) shows the same input is hex/backslash-escaped and never appears as raw `\r`-prefixed marker text.

func EscapeForAnsiC(s string) string {
	var buf strings.Builder

	for i := 0; i < len(s); i++ {
		c := s[i]
		switch c {
		case '\\':
			buf.WriteString("\\\\")
		case '\'':
			buf.WriteString("\\'")
		case '\n':
			buf.WriteString("\\n")
		case '\r':
			buf.WriteString("\\r")
		case '\t':
			buf.WriteString("\\t")
		case '\a':
			buf.WriteString("\\a")
		case '\b':
			buf.WriteString("\\b")
		case '\f':
			buf.WriteString("\\f")
		case '\v':
			buf.WriteString("\\v")
		default:
			// Hex-escape control characters (0x00-0x1F, 0x7F) and non-ASCII (>0x7F)
			// This prevents ANSI escape sequences (ESC = 0x1B) from manipulating terminal
			if c < 0x20 || c == 0x7F || c > 0x7F {
				fmt.Fprintf(&buf, "\\x%c%c", hextable[c>>4], hextable[c&0x0f])
			} else {
				buf.WriteByte(c)
			}
		}
	}

	return buf.String()
}
```

```go
func EscapeForPosix(s string) string {
	if s == "" {
		return "''"
	}

	var buf strings.Builder
	needsQuoting := false

	for _, r := range s {
		switch r {
		case '`', '"', '\\', '$':
			buf.WriteRune('\\')
			buf.WriteRune(r)
			needsQuoting = true
		case ' ', '!', '#', '%', '&', '(', ')', '*', '<', '=', '>', '?', '[', '|':
			buf.WriteRune(r)
			needsQuoting = true
		default:
			buf.WriteRune(r)
		}
	}

	if needsQuoting {
		return `"` + buf.String() + `"`
	}

	return buf.String()
```
