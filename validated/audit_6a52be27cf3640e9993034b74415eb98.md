### Title
`SortitionsView::validate_tenure_change_payload` (v1) checks only globally-accepted blocks for a tenure duplicate, letting a locally-signed-but-not-yet-global block be silently superseded by a second tenure-start proposal - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The v1 (`uses_global_state() == false`) tenure-change duplicate check queries `SignerDb::get_last_globally_accepted_block` instead of a "locally or globally signed" predicate, unlike the v2 implementation which uses `get_last_signed_block` (i.e., signed locally OR globally). This asymmetry is explicitly called out in the repo's own documentation as a known gap, and it means the proposal-time `DuplicateBlockFound` guard can miss a competing tenure-change block that would conflict with a block this signer has already locally signed (but the network has not yet globally accepted) in the same tenure.

### Finding Description
`validate_tenure_change_payload` in `v1.rs` performs the duplicate-tenure-start check with: [1](#0-0) 

using `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`. Compare this with the v2 equivalent, which uses `get_last_signed_block` (locally OR globally accepted): [2](#0-1) 

The project's own documentation confirms this is a deliberate/known asymmetry between the two protocol versions: [3](#0-2) 

The documentation also states plainly that this `DuplicateBlockFound` check "belong[s] to the proposal path only and [is] **not** re-run at validate-ok or at signing" for the *own-tenure* duplicate case — only the cross-tenure signed-conflicts check at the pre-commit/signing stage (section 5, `get_signed_conflicts`) is described as covering the same ground "long after" proposal: [4](#0-3) 

Putting this together for a v1 signer: a miner can propose a first tenure-start block B1 for tenure T. The signer locally signs B1 (`signed_self` set via `mark_locally_accepted`), but B1 has not yet reached the 70% weight needed to be marked `GloballyAccepted`. Because `validate_tenure_change_payload`'s duplicate check on the v1 path only looks at `get_last_globally_accepted_block`, a second, competing tenure-change block B2 (also targeting the start of tenure T, e.g. an equivocating/forked tenure-start proposal) is *not* rejected as `DuplicateBlockFound` at proposal time — it passes this specific check and is queued for node validation.

### Impact Explanation
If the node's own validation and the later pre-commit/sign-time conflict guard (`get_signed_conflicts`, described in section 5 of the docs) do not independently and reliably catch this exact scenario for the v1 code path, the signer risks producing a second valid signature over a conflicting tenure-start block (B2) at the same tenure/height as one it already signed (B1) before B1 reached global acceptance. That is a direct instance of a signer signing two conflicting blocks — a break of the "one signed block per tenure/height" safety invariant that the whole pre-commit/duplicate-check machinery exists to enforce. Given the report's required Critical impact bucket ("a signer signing an invalid, non-canonical, or conflicting block"), this maps directly if the downstream guard does not also apply to the v1 local-accept case.

### Likelihood Explanation
This requires a single miner (one slot) proposing two competing tenure-start blocks for the same tenure in quick succession — well within a miner's ability and consistent with the report's constraint that only a miner/gossip actor is needed, not a majority of signers. It is a narrow timing window (between local signing and global acceptance of B1), but that window is exactly the one the general `has_signed_block_in_tenure`/`get_last_signed_block` predicates elsewhere in the codebase were designed to close, making its absence here a real gap by omission rather than by intended design (the docs frame it as an asymmetry, not as a proven safe redundancy).

### Recommendation
Change the v1 `validate_tenure_change_payload` duplicate check to use `SignerDb::get_last_signed_block` (or equivalently `has_signed_block_in_tenure`) instead of `get_last_globally_accepted_block`, matching the v2 semantics, so that a locally-signed-but-not-yet-globally-accepted block in the target tenure also triggers `RejectReason::DuplicateBlockFound` at proposal time for v1 signers.

### Proof of Concept
I was not able to fully trace whether the later pre-commit-stage `get_signed_conflicts` check (section 5 of `docs/signer-flows.md`, implemented in `signerdb.rs`, referenced from `stacks-signer/src/v0/signer.rs`) independently catches this same scenario for a v1 signer before signature production, because tool access ended before I could read the `get_signed_conflicts` implementation in `signerdb.rs` in full. This is the key uncertainty: if `get_signed_conflicts` reliably vetoes signing over B2 whenever `signed_self` is set on a conflicting block B1 regardless of protocol version, then this finding degrades to a proposal-time inefficiency rather than a true signature-safety break, and should be treated with lower confidence. I flag this explicitly rather than asserting the exploit chain completes.
