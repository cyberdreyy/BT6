## Title
Gateway `WebAPIHandler.savedCallbacks` Map Keyed Only by Client-Controlled `MessageId` Allows Cross-User Response Overwrite/Hijack - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The Chainlink Gateway's WebAPI capabilities handler stores pending user callbacks in a map keyed solely by the client-supplied `MessageId`, with no sender/session component and no collision check before insertion. An unprivileged client can submit a `web_api_trigger` request using a `MessageId` that collides with another in-flight request (from itself or another user), silently overwriting the stored callback. When the DON node eventually responds for that `MessageId`, the response is delivered to whichever callback last occupied that map slot — not necessarily the party that made the original request. This is directly analogous to the reported `IonPool.initializeIlk` bug, where writing new data into a fixed/keyed structure without validating for an existing/colliding entry silently overwrites prior state (there, the `rate` for a prior `ilk`; here, the callback owner for a `MessageId`).

### Finding Description
`NewHandler` initializes `savedCallbacks map[string]*savedCallback` keyed by string message ID [1](#0-0) .

In `HandleLegacyUserMessage`, when an unprivileged user submits a `web_api_trigger` request through the gateway's public HTTP endpoint, the handler unconditionally overwrites any existing entry at that key: [2](#0-1) 

There is no check analogous to the one used in the sibling `RequestCache` type (`core/services/gateway/handlers/common/requestcache.go`), which explicitly rejects a `NewRequest` call if an entry already exists for the key: [3](#0-2) 

Critically, `RequestCache`'s key is a composite `globalId{sender, id}` [4](#0-3) , so collisions require the *same* sender to pick a duplicate ID. In contrast, `savedCallbacks` is keyed purely by `MessageId` with **no sender scoping at all**.

`MessageId` is attacker-controlled: it is any string of 1–128 bytes not ending in a null byte, validated only for length/format, not uniqueness across senders: [5](#0-4) 

The message signature covers `MessageId`, `Method`, `DonId`, `Receiver`, and `Payload` [6](#0-5) , but nothing prevents two independently-signed messages from *different* senders from choosing the identical `MessageId` string, since the value is chosen by the client itself before signing.

When a node later responds with `MethodWebAPITrigger`, the handler looks up and deletes the callback purely by `msg.Body.MessageId`: [7](#0-6) 

If an attacker sends their own `web_api_trigger` request reusing the `MessageId` of a victim's still-pending request (submitted moments earlier and forwarded to DON nodes), the attacker's callback overwrites the victim's entry in the map. When the DON node's genuine response to the *victim's* original request arrives at the gateway keyed by that same `MessageId`, `handleWebAPITriggerMessage` will deliver it to the attacker's callback instead of the victim's — the victim's HTTP client is left with no response (until its own request queue mechanics or timeout), while the attacker receives the victim's trigger response.

### Impact Explanation
This is a cross-user response confusion vulnerability reachable from an unprivileged client via the gateway's public user-facing HTTP endpoint. An attacker can hijack another client's DON response payload by racing a colliding `MessageId`, or cause denial-of-service to a legitimate client's request by silently dropping their callback. Depending on what data the `web_api_trigger` response payload contains, this could leak information intended for another workflow/user session.

### Likelihood Explanation
Exploitation requires only sending a standard signed `web_api_trigger` request to the gateway's user-facing endpoint with an attacker-chosen `MessageId` that collides with a currently pending request from another sender, and winning a modest timing race (the pending window is bounded by `CallbackMaxAgeSec`, default 120s) [8](#0-7) . No special privileges, node cooperation, or protocol-layer tricks are needed — this is a pure application-logic bug reachable by any client capable of calling the gateway.

### Recommendation
Scope the `savedCallbacks` map key by both sender and `MessageId` (mirroring `RequestCache`'s `globalId{sender, id}` pattern), and reject/ignore new registrations that would collide with an existing, unexpired entry rather than silently overwriting it, in `HandleLegacyUserMessage`.

### Proof of Concept
1. Victim signs and submits a `web_api_trigger` request to the gateway HTTP endpoint with `MessageId = "X"`; the gateway stores `savedCallbacks["X"] = victimCallback` and forwards the request to DON members [9](#0-8) .
2. Before the DON responds, attacker signs and submits their own `web_api_trigger` request with the same `MessageId = "X"` (a distinct, validly-signed message under the attacker's own key, since `MessageId` uniqueness across senders is never checked). This overwrites `savedCallbacks["X"]` with `attackerCallback`.
3. When a DON node returns a `web_api_trigger` response for `MessageId = "X"` (intended for the victim's request), `handleWebAPITriggerMessage` looks it up by `MessageId` only, finds `attackerCallback`, deletes the entry, and sends the victim's response payload to the attacker [7](#0-6) .

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
