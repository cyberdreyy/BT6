### Title
Missing path-containment check in legacy zip extraction lets a crafted `zip.FileHeader.Name` drive `os.Lchown`/file writes outside the intended cache/artifact extraction root - (File: `helpers/archives/zip_extra_unix.go`)

### Summary
`ExtractZipArchive` (helpers/archives/zip_extract.go) and `processZipUIDGidField` (helpers/archives/zip_extra_unix.go) operate directly on `file.Name`/`file.FileHeader.Name` taken verbatim from the zip entry, with no `filepath.Clean`, no join against a fixed extraction root, and no containment check. This contrasts with the sibling `tarzstd` extractor, which explicitly enforces `strings.HasPrefix(path, e.dir+string(filepath.Separator))` before touching the filesystem. As a result, a crafted zip entry name (e.g. containing `../` or an absolute path) can cause file writes, `lchmod`, `os.Chtimes`, and `os.Lchown` to target a path outside the extraction root.

### Finding Description
`extractZipFile`/`extractZipFileEntry`/`extractZipDirectoryEntry`/`extractZipSymlinkEntry` in `helpers/archives/zip_extract.go` (lines 12-83) use `file.Name` directly for `os.Mkdir`, `os.OpenFile`, and `os.Symlink` with no path sanitization. `ExtractZipArchive` (lines 85-110) then calls `lchmod(file.Name, ...)` and `processZipExtra(&file.FileHeader)` for every archive entry, and `processZipExtra`/`processZipUIDGidField` (helpers/archives/zip_extra.go:96-122, helpers/archives/zip_extra_unix.go:37-48) call `os.Lchown(file.Name, int(ugField.UID), int(ugField.Gid))` on the same unsanitized name.

Compare this to `commands/helpers/archive/tarzstd/tarzstd_extractor.go:57-64`, which builds the target path as `filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects entries that escape `e.dir`. The zip legacy path (`helpers/archives/zip_extract.go`, reached via `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`) has no equivalent check — it never joins entry names against a target directory at all, relying entirely on the archive's `zip.File.Name` being well-formed.

Reachability: `commands/helpers/cache_extractor.go:Execute` downloads a cache blob and calls `archive.NewExtractor(format, f, size, wd)` → `extractor.Extract(ctx)`, and this is registered per-`Format` via `archive.Register` (commands/helpers/archive/archive.go). The `ziplegacy` extractor (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go:26-32`) is a registered `archive.Extractor` implementation that discards the passed-in `dir` entirely and calls `archives.ExtractZipArchive(zr)` directly — it never restricts extraction to `wd`. Cache/artifact content is attacker-influenced: a job can archive/upload arbitrary bytes as a "cache" via the normal cache-archiver flow, and a later job (or the same job) triggers `cache-extractor`, hitting this code path if the `ziplegacy` extractor is the one selected for the received format.

I was not able to fully confirm within the available tool budget whether `ziplegacy` or `fastzip` (`commands/helpers/archive/fastzip/zip_fastzip_extractor.go`, which delegates to the `saracen/fastzip` library and its own path handling) is the extractor actually bound to the `Zip`/`ZipZstd` `Format` constants at registration time in the current build. This is a genuine gap in my analysis — if `fastzip` is the exclusive handler for all zip-based cache/artifact formats and `ziplegacy`/`archives.ExtractZipArchive` is unreachable from the cache/artifact restore flow, the exploit path described would not be reachable in practice, since `archives.ExtractZipFile`/`ExtractZipArchive` also has direct unit-test coverage (`helpers/archives/zip_extract_test.go`) suggesting it is still an actively used, registered code path in some capacity (e.g. `commands/helpers/cache_extractor_test.go` also exercises related zip-based extraction).

Regarding the specific "docker socket / CI_JOB_TOKEN mounted path" framing in the question: even granting the missing containment check, `os.Lchown` changing ownership of an existing sensitive file requires the process to already have permission to chown that file (typically root, or `CAP_CHOWN`, or being the file's current owner on some systems) — this is a privilege-dependent, not purely path-dependent, primitive. In gVisor/rootless/non-root helper containers this call would simply fail with `EPERM`. The impact is therefore real for **arbitrary-path ownership/permission tampering when the extracting process has sufficient privilege (e.g. runs as root inside the helper container)** — a precondition that must be documented rather than assumed, and one that overlaps with "privileged container" execution which the audit rules ask to deprioritize unless it creates a *new* user-triggered exploit path. Here it does create a new path: the *targeting* of the chown (which file gets touched) is fully attacker-controlled via the crafted zip entry name, which is the actual missing check, independent of whether the process is root.

### Impact Explanation
If the affected extractor is reachable from cache/artifact restore and the extracting process holds sufficient privilege, a crafted cache/artifact zip lets a job cause `os.Lchown`/`lchmod`/`os.Chtimes`/file writes on a path chosen by the attacker rather than confined to the intended cache/build root — e.g. an entry named `../../../some/mounted/path`. This is an ownership/permission-tampering primitive on whatever `file.Name` resolves to on the host/container filesystem, scoped by the extracting process's actual privileges. It is not confirmed to reach a docker.sock or CI_JOB_TOKEN file specifically — that depends entirely on undocumented, deployment-specific mount layout, which is outside Runner's control and not something Runner can be expected to guard against by path convention alone.

### Likelihood Explanation
- Preconditions: (1) the vulnerable `ziplegacy`/`archives.ExtractZipArchive` code path must actually be the one invoked for cache/artifact restoration in the deployed configuration/build (unverified here); (2) the extracting process/container must have privilege to `chown`/write outside the workspace (commonly true only for root-running helper images); (3) attacker must control raw zip bytes stored as a "cache," which is achievable by any job author since cache content is opaque to GitLab.
- Feasibility: Crafting a zip with a traversal-style `Name` and a `0x7875` extra field is straightforward and fully reproducible offline.
- Repeatability: High, given the preconditions hold.

### Recommendation
Add the same containment check used in `tarzstd_extractor.go` to the zip extraction path: resolve each entry's target path as `filepath.Abs(filepath.Join(rootDir, file.Name))`, reject any entry whose resolved path is not equal to or nested under `rootDir`, and pass that validated path (rather than the raw `file.Name`) into `extractZipFile`, `lchmod`, `processZipTimestampField`, and `processZipUIDGidField`/`os.Lchown`. This closes the gap at the source rather than relying on downstream file permissions to limit blast radius.

### Proof of Concept
```go
func TestExtractZipArchive_RejectsPathTraversalInUIDGidField(t *testing.T) {
    tmpDir := t.TempDir()
    root := filepath.Join(tmpDir, "workspace")
    require.NoError(t, os.MkdirAll(root, 0o755))

    sensitive := filepath.Join(tmpDir, "sensitive_token")
    require.NoError(t, os.WriteFile(sensitive, []byte("secret"), 0o600))
    fi, _ := os.Stat(sensitive)
    origMode := fi.Mode()

    var buf bytes.Buffer
    zw := zip.NewWriter(&buf)
    fh := &zip.FileHeader{Name: "../sensitive_token"}
    fh.SetMode(0o777) // attempt to change perms via lchmod path
    w, _ := zw.CreateHeader(fh)
    _, _ = w.Write([]byte("owned"))
    zw.Close()

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    // Run extraction with cwd set to `root` (as cache-extractor does).
    origWd, _ := os.Getwd()
    defer os.Chdir(origWd)
    require.NoError(t, os.Chdir(root))

    _ = archives.ExtractZipArchive(zr)

    // Assert the file outside root was NOT modified.
    data, _ := os.ReadFile(sensitive)
    assert.Equal(t, "secret", string(data), "extraction must not overwrite files outside the workspace root")
    fiAfter, _ := os.Stat(sensitive)
    assert.Equal(t, origMode, fiAfter.Mode(), "extraction must not change mode of files outside the workspace root")
}
```
Expected current (buggy) behavior: the assertions fail because `../sensitive_token` resolves outside `root` and is overwritten/chmodded. Expected fixed behavior: `ExtractZipArchive` returns/logs an error for the out-of-root entry and leaves `sensitive_token` untouched.
