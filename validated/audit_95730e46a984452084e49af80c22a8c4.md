### Title
APR0 withdraw receipt permanently bricks `stopEpoch` once APR is raised, freezing all pool funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the OpenLeverage anti-flashloan check that reverts and blocks liquidation during a drawdown, `IdleCreditVault.prepareStopEpochWithApr0` contains a consistency guard (`unscaledApr != 0 → revert NotAllowed`) that permanently blocks the epoch-settlement path — the credit vault's equivalent of closing out the loan. Once any lender holds an open APR0 withdraw receipt and the (honest) manager raises the APR for a subsequent epoch, `stopEpoch`/`stopEpochWithDuration` can never succeed, the borrower can never repay through the normal path, and all lender funds are frozen until a default is forced.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` (lines 285–286) routes to `_requestWithdrawApr0` whenever `unscaledApr == 0`, incrementing `apr0TotalPrincipal` (line 576) and recording `apr0Users[_user].principal`.
- `prepareStopEpochWithApr0` (lines 505–508) reverts with `NotAllowed` if `apr0TotalPrincipal != 0` while `unscaledApr != 0`.
- The only place `apr0TotalPrincipal` is cleared is line 540 — *after* the reverting check. There is no cancel-request path, and `claimWithdrawRequest` requires `epochNumber > lastWithdrawRequest[_user]` (line 326), which can only advance inside `deposit()` called from a successful `stopEpoch`.

In `contracts/IdleCDOEpochVariant.sol`:

- `_stopEpoch` calls `_strategy.prepareStopEpochWithApr0(_interest)` at line 362, *outside* the `try/catch` around `getFundsFromBorrower` (line 408). So the revert propagates and aborts `stopEpoch` entirely — the `_handleBorrowerDefault` fallback is never reached.
- The strategy's `setAprs`/`setApr` (IdleCreditVault lines 206–235) can be called directly by the manager at any time, including while an epoch is running, and sets `unscaledApr`.

Attack sequence (attacker = ordinary KYC-passed lender):

1. Epoch N runs with `unscaledApr == 0`. Attacker deposits AA and calls `requestWithdraw` with a dust amount → `apr0TotalPrincipal = dust > 0`.
2. Epoch N stops normally at APR 0 (check passes since `unscaledApr == 0`), then — crucially — the attacker's receipt stays open because claims require a full additional epoch wait, and the attacker simply never claims.
3. Manager honestly sets a non-zero APR for the next epoch via `setAprs`/`setAprsWithBuffer` (routine operation; `unscaledApr` becomes nonzero while `apr0TotalPrincipal` still holds the attacker's dust principal, since `apr0TotalPrincipal` is only reset at stopEpoch when APR stays 0 — actually it is reset to 0 at line 540 on the APR0 stop).

Uncertainty to flag: whether `apr0TotalPrincipal` survives depends on whether the APR0 bucket is closed at the stop where the APR is still 0. If `apr0TotalPrincipal` is zeroed at the first stop, the attacker must instead request the APR0 withdrawal during an epoch that is already running — `requestWithdraw` is only callable between epochs (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` gating in the CDO), and APR is set for the *next* epoch at stop time via `_setScaledApr`. So the durable variant is: attacker requests withdrawal during the buffer while `unscaledApr` was set to 0 for epoch N+1; then during epoch N+1 the manager calls `setAprs` directly (allowed at any time) to raise APR mid-epoch → at epoch end, `prepareStopEpochWithApr0` reverts permanently. The manager setting APR mid-epoch is an honest, permitted action, and the attacker's dust APR0 receipt is what arms the trap.

### Impact Explanation
Permanent freezing of all pool funds / forced insolvency. `stopEpoch` and `stopEpochWithDuration` both funnel through `_stopEpoch` → `prepareStopEpochWithApr0`, which will revert on every call once `unscaledApr != 0 && apr0TotalPrincipal > 0`. `apr0TotalPrincipal` cannot be decremented by any user action (no cancel, and claim is epoch-gated behind a stop that can never occur). The borrower — honest and willing to repay — has no path to return principal; `getFundsFromBorrower` is only invoked inside `_stopEpoch`. The only remaining resolution is `finalizeDefault`, which crystallizes a total-loss recovery price, haircutting every active LP and pending receipt for a loss the borrower never actually caused. The attacker's cost is a dust deposit; the damage is the entire pool NAV.

### Likelihood Explanation
Requires: (a) the vault operating an APR0 epoch at some point, and (b) the manager later setting a non-zero APR while an APR0 receipt is still outstanding — both routine, honest operations. The attacker contributes only a normal deposit + dust withdraw request, fully within unprivileged lender capabilities. No privileged misbehavior, oracle manipulation, or market condition is needed.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert when `unscaledApr != 0` and an open APR0 bucket exists. Either settle the open APR0 principal at zero interest for the transition epoch (the receipt's economic terms were fixed at request time), or sweep `apr0TotalPrincipal` into a closed state before applying the APR change. Alternatively, block APR changes while `apr0TotalPrincipal != 0` in `setAprs` (with a clear error) so the trap state is unreachable, or provide a way to settle/expire APR0 principal that does not depend on a successful `stopEpoch`.

### Proof of Concept
A Foundry PoC against the epoch credit vault (modeled on `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testApr0ReceiptBricksStopEpoch() external {
    // setup: deposits, epoch running at APR 0
    idleCDO.depositAA(100_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);            // APR 0 epoch
    _stopEpochAndCheckPrices(0, 0, expected); // stop at APR 0, next epoch APR still 0

    // attacker (KYC'd lender) opens dust APR0 withdraw receipt in buffer
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // apr0TotalPrincipal = 1

    _startEpochAndCheckPrices(0);            // epoch runs at APR 0
    // honest manager raises APR mid-epoch (allowed by setAprs access control)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(5e18, 5e18 * scale);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    // every subsequent stopEpoch reverts forever; apr0TotalPrincipal can never clear
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    // borrower repayment path unreachable -> forced default/total loss via finalizeDefault
}
```

Note: the exact line where `apr0TotalPrincipal` resets (line 540) relative to mid-epoch APR changes should be verified when writing the PoC; the invariant is that once `unscaledApr != 0` coincides with a nonzero `apr0TotalPrincipal`, no code path can clear the bucket.
