### Title
Non-retryable `ValidationFailed` rejection reasons let a transient node-side chainstate error permanently wedge a signer against a re-proposed valid block - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The Chainlink report shows a class of bug where an external dependency's call failure (a revert) gets folded into a decision that the caller cannot revisit, causing permanent denial of service. The stacks-signer codebase has a structurally similar chokepoint: `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs` hard-codes most `RejectReason::ValidationFailed(_)` variants (everything except `UnknownParent`/`NotFoundError`) as non-reevaluatable, so once a signer stores such a rejection it will resend the same verdict forever instead of re-validating a re-proposed block, even if the original rejection was caused by a transient node-side error rather than a deterministic invalidity.

### Finding Description
When a signer submits a block for validation, the stacks node runs `NakamotoBlockProposal::validate` in `stackslib/src/net/api/postblock_proposal.rs`. That function performs several DB/chainstate lookups (parent header lookup, burn view lookup, sortition lookup, expected-burn lookup, etc.), and multiple failure paths are mapped to `ValidateRejectCode::ChainstateError` and other `ValidateRejectCode` variants (see e.g. lines 398-402, 416-422, 611-623 of `postblock_proposal.rs`) whenever an internal DB call errors out (`?` on `chainstate.db()`/`sortdb` queries) — this is functionally analogous to an external dependency call reverting: a transient hiccup in the node's local chainstate/sortition access (e.g., a concurrent DB write, a lock timeout, a brief inconsistency during a reorg window) produces the exact same rejection response as a truly invalid block.

Back on the signer side, `handle_block_validate_reject` (`stacks-signer/src/v0/signer.rs:1987-2051`) unconditionally calls `block_info.mark_locally_rejected()` and persists `block_info.reject_reason` via `self.signer_db.insert_block(&block_info)` for any `BlockValidateReject`, without distinguishing a deterministic invalidity from a chainstate/DB error.

Later, when the same block hash is re-proposed (e.g., the miner retries because the transient condition has since cleared and the block is now perfectly valid), `handle_block_proposal` looks up `prior_block_info` and calls `should_reevaluate_block`, which in turn consults `should_reevaluate_reject_reason` (lines 2705-2739):

```
RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
| RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
| RejectReason::NoSortitionView
| RejectReason::ConnectivityIssues(_)
| ... => true,
RejectReason::ValidationFailed(_)
| RejectReason::RejectedInPriorRound
| RejectReason::SortitionViewMismatch
| ... => false,
```

Only two `ValidationFailed` sub-reasons (`UnknownParent`, `NotFoundError`) and `ConnectivityIssues`/`NoSortitionView` are treated as "might have been transient, worth re-checking." Every other `ValidateRejectCode` (including `ChainstateError` and similar codes produced by internal DB-lookup failures unrelated to the block's actual validity) is bucketed under the catch-all `RejectReason::ValidationFailed(_) => false`, meaning the signer will never re-validate; it just resends its stale rejection (per the `PREV` branch documented in `docs/signer-flows.md:181-188`, "re-send previous response").

This is the direct analog of the external report's root cause: a transient failure of an external/DB call is folded into a decision (`reject_reason`) that the caller (the signer state machine) is structurally prevented from revisiting, unlike `ConnectivityIssues`/`NotFoundError`/`UnknownParent`, which the codebase's authors evidently recognized *could* be transient and explicitly whitelisted for re-evaluation.

### Impact Explanation
This is a liveness wedge: a signer that hit a transient chainstate/DB error while validating one instance of a block will permanently refuse to sign that exact block (by signer_signature_hash) even after it becomes fully valid and is re-proposed unchanged, because it never resubmits it for revalidation — it only replays its stale decision. If enough signers experience the same transient condition around the same block (plausible during a burn-chain reorg or node restart, which is exactly the kind of window where DB/chainstate contention occurs), the block could fail to reach the 70% signing weight even though it is legitimately valid, matching the "signer wedged into never signing valid blocks" category of impact. Because the rejection is per `signer_signature_hash`, once wedged for a given block, only a competing block that changes the header will let the signer participate again.

### Likelihood Explanation
Reachability is high in the sense that no majority collusion or privileged access is required: any legitimate transient chainstate/DB read failure inside `validate()` at the node (which a miner cannot fully control, but which occurs naturally during reorgs, load, or race windows) triggers the non-reevaluatable path. However, deliberately and reliably forcing this specific window from a single miner/gossip actor is harder to demonstrate than a clean single-message exploit, since it depends on hitting one of the DB-lookup failure branches in `postblock_proposal.rs` rather than the more common deterministic-invalidity branches. I could not fully verify (due to running out of tool iterations) whether any external input from a proposing miner can deterministically force one of the DB-lookup `?` failures in `validate()` (e.g. via block timing, replay-tx state, or a crafted burn view) versus only occurring from genuine node-local transient conditions; this materially affects whether the bug is miner-triggerable on demand or only opportunistically triggered by network conditions.

### Recommendation
Expand `should_reevaluate_reject_reason` to treat `RejectReason::ValidationFailed(ValidateRejectCode::ChainstateError)` (and any other `ValidateRejectCode` variant that stems from internal DB/state lookups rather than deterministic block content invalidity) as re-evaluatable, mirroring the existing treatment of `UnknownParent`/`NotFoundError`/`ConnectivityIssues`. Alternatively, have the node distinguish "transient infrastructure error" from "content is invalid" at the `ValidateRejectCode` level so the signer can safely default to re-validating on any reason it cannot prove is a durable, content-based rejection.

### Proof of Concept
Conceptual reproduction (not independently executed, given the ask-only/no-terminal constraints of this task):
1. A miner proposes block `B`. The signer submits `B` to its node via `submit_block_for_validation`.
2. The node's `validate()` hits a transient chainstate/DB error unrelated to `B`'s actual correctness (e.g., a lock/read race during `NakamotoChainState::get_expected_burns` or a similar internal lookup) and returns `BlockValidateReject` with `reason_code: ValidateRejectCode::ChainstateError`.
3. The signer's `handle_block_validate_reject` marks and persists `B` as `RejectReason::ValidationFailed(ValidateRejectCode::ChainstateError)`.
4. The transient condition clears. The miner (or gossip) re-proposes the identical `B` (same `signer_signature_hash`).
5. `handle_block_proposal` → `should_reevaluate_block` → `should_reevaluate_reject_reason` returns `false` for this reason code, so the signer resends its stale rejection without contacting the node again — permanently refusing to sign an otherwise valid `B`.     /// Handle the block validate reject response
    fn handle_block_validate_reject(
        &mut self,
        block_validate_reject: &BlockValidateReject,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        crate::monitoring::actions::increment_block_validation_responses(false);
        let signer_signature_hash = &block_validate_reject.signer_signature_hash;
        if self
            .submitted_block_proposal
            .as_ref()
            .map(|(proposal_hash, _)| proposal_hash == signer_signature_hash)
            .unwrap_or(false)
        {
            self.submitted_block_proposal = None;
        }
        let Some(mut block_info) = self.block_lookup_by_reward_cycle(signer_signature_hash) else {
            // We have not seen this block before. Why are we getting a response for it?
            debug!("{self}: Received a block validate response for a block we are not tracking. Ignoring...");
            return;
        };
        if block_info.valid.is_some() {
            // We should only have valid set if we have already processed a validation response for this block OR we locally marked it as rejected.
            // and responded to it. If we received a new proposal for it, we would have reset valid to None.
            warn!(
                "{self}: Already processed a block validate response for block {}. Ignoring validation response.", block_info.block.header.signer_signature_hash(); "valid" => ?block_info.valid,
            );
            return;
        }
        if !block_info.check_static_valid_block() {
            debug!("{self}: Block is syntatically invalid; will not store");
            return;
        }
        if let Err(e) = block_info.mark_locally_rejected() {
            if !block_info.has_reached_consensus() {
                warn!("{self}: Failed to mark block as locally rejected: {e:?}");
            }
        }
        let block_rejection = BlockRejection::from_validate_rejection(
            block_validate_reject.clone(),
            &self.private_key,
            self.mainnet,
            self.signer_db.calculate_full_extend_timestamp(
                self.proposal_config
                    .tenure_idle_timeout
                    .saturating_add(self.proposal_config.tenure_idle_timeout_buffer),
                &block_info.block,
                false,
            ),
            self.signer_db.calculate_read_count_extend_timestamp(
                self.proposal_config
                    .read_count_idle_timeout
                    .saturating_add(self.proposal_config.tenure_idle_timeout_buffer),
                &block_info.block,
                false,
            ),
        );

        block_info.reject_reason = Some(block_rejection.response_data.reject_reason.clone());
        self.signer_db
            .insert_block(&block_info)
            .unwrap_or_else(|e| self.handle_insert_block_error(e));
        self.handle_block_rejection(&block_rejection, sortition_state);
        self.send_block_response(&block_info.block, block_rejection.into());
    }

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
