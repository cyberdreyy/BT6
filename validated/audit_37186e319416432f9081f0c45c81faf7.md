## Finding

The Aptos analog to the ERC314Factory fee-distribution DoS lives in `aptos_framework::vesting::distribute` (and its callers `terminate_vesting_contract`/`vest`/`unlock_rewards`), where a single shareholder can permanently block payouts to *every* shareholder of a shared vesting contract.

### Title
Unprivileged shareholder can permanently freeze distributions to all co-shareholders in a vesting contract - (File: aptos-move/framework/aptos-framework/sources/vesting.move)

### Summary
`vesting::distribute` withdraws all currently-unlocked stake/rewards for a vesting contract and then loops over **every** shareholder in `grant_pool`, paying each one via `aptos_account::deposit_coins` with no error handling. `aptos_account::deposit_coins` aborts if the target address is unregistered for `AptosCoin` and has opted out of direct coin transfers via `set_allow_direct_coin_transfers(false)` — a fully permissionless action any account holder can take on their own address. Because Move has no try/catch, a single poisoned recipient in the loop reverts the entire transaction, which blocks payout for *every other* shareholder in that same vesting contract, indefinitely.

### Finding Description
`distribute` computes `total_distribution_amount` and then iterates all shareholders unconditionally: [1](#0-0) 

Each iteration calls `aptos_account::deposit_coins(recipient_address, share_of_coins)` for the shareholder (or its beneficiary via `get_beneficiary`), with the whole loop needing to fully complete for the transaction to succeed.

`aptos_account::deposit_coins` will abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when the recipient is not yet registered for the coin type and has disabled arbitrary transfers: [2](#0-1) 

Opting out is a completely permissionless, self-serve action available to any account: [3](#0-2) 

Because this check only triggers when `!coin::is_account_registered<CoinType>(to)`, any shareholder (or a beneficiary address they control, settable via `set_beneficiary`) that has never registered a `CoinStore<AptosCoin>` can call `set_allow_direct_coin_transfers(false)` on that address. From that point on, every call to `distribute(contract_address)` will hit this address in the `for_each_ref` loop and abort, reverting the *entire* transaction — undoing the stake withdrawal for that call and leaving all shareholders unpaid.

There is no mechanism in `vesting.move` to remove a shareholder from `grant_pool`, skip a failing recipient, or otherwise route around a blocked account — `grant_pool.shareholders()` is fixed at contract creation and iterated unconditionally on every distribution.

This DoS is not confined to `distribute()`. `terminate_vesting_contract` unconditionally calls `distribute` as its very first step, *before* even checking the admin signer: [4](#0-3) 

So once one shareholder poisons their receiving address, the admin can no longer terminate the vesting contract either, which also blocks the eventual `admin_withdraw` recovery path since it requires `VESTING_POOL_TERMINATED` state: [5](#0-4) 

This is the direct structural analog of the reported bug: in the external report, one of two fee-recipient "teams" can revert on receipt and block the other team's share from a `require`-gated transfer loop. Here, one shareholder among the vesting contract's shareholder set can revert on receipt (via `set_allow_direct_coin_transfers(false)` while unregistered) and block *all* other shareholders' vested stake and rewards from a similarly unguarded, all-or-nothing distribution loop.

### Impact Explanation
This causes a **permanent, non-recoverable freeze of vesting/stake claim rights** for every shareholder of an affected vesting contract, not just the actor who set up the block:
- Rewards and vested APT already unlocked from the stake pool become permanently stuck rotating between the vesting contract's stake pool and reverted transactions — they can never be withdrawn to any shareholder's or the withdrawal address's account.
- `terminate_vesting_contract`/`admin_withdraw` recovery is also blocked, since termination itself calls `distribute` first.
- Any shareholder (an unprivileged party by design, since anyone can be added to a vesting schedule and shareholders permissionlessly control their own account's `DirectTransferConfig`) can trigger this against all co-shareholders, matching the "permanent lock/non-recoverable loss of claim rights in ... vesting flows" impact category.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires a shareholder (or someone controlling a beneficiary address for a shareholder) to have never registered `CoinStore<AptosCoin>` on that address and to deliberately call `set_allow_direct_coin_transfers(false)`. This is entirely within that single account's own unprivileged control and requires no cooperation or compromise of any other party, similar to the low-likelihood-but-high-impact classification in the source report.

### Recommendation
In `distribute_internal`-style loops (both `vesting::distribute` and `staking_contract::distribute_internal`, which has the identical pattern), do not let a single recipient's failed/rejected deposit revert the whole distribution. Options:
- Wrap each recipient's deposit so a failure only forfeits/queues that recipient's share (e.g., keep it in the pool as still-owed) rather than aborting the entire loop.
- Check `coin::is_account_registered` / `can_receive_direct_coin_transfers` per recipient beforehand and skip (retain shares) for recipients that would reject the deposit, instead of calling `aptos_account::deposit_coins` unconditionally.
- Ensure `terminate_vesting_contract`/`admin_withdraw` do not depend on prior successful `distribute` when a shareholder is uncooperative.

### Proof of Concept
1. Admin creates a vesting contract with shareholders `[A, B]` via `create_vesting_contract` [6](#0-5) .
2. Shareholder `B` creates a fresh account that is never registered for `AptosCoin` (no `coin::register<AptosCoin>` call), then calls `aptos_account::set_allow_direct_coin_transfers(B_signer, false)`.
3. Stake pool earns rewards; someone calls `vest(contract_address)` to unlock rewards, then waits for lockup, then calls `distribute(contract_address)`.
4. Inside `distribute`, the loop reaches `B` and calls `aptos_account::deposit_coins(B, share_of_coins)`; since `B` is unregistered and has disabled arbitrary transfers, this aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The entire `distribute` transaction reverts — shareholder `A` (and any other shareholder) receives nothing, and this will repeat on every future call to `distribute`, `vest`, or `terminate_vesting_contract` for this contract, since `B` remains a shareholder forever.

    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
