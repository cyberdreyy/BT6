### Title
A single APR0 withdrawal request can block epoch settlement after a routine APR change - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.requestWithdraw` places withdrawal receipts into a global APR0 bucket whenever `unscaledApr == 0`. [1](#0-0)  Every subsequent `IdleCDOEpochVariant.stopEpoch` calls `prepareStopEpochWithApr0` before borrower funds are pulled or accounting is finalized. [2](#0-1)  If any APR0 principal remains outstanding while the pool APR has become nonzero, `prepareStopEpochWithApr0` reverts, causing the entire epoch settlement to revert. [3](#0-2) 

### Finding Description
An unprivileged KYC-passed lender can create the blocking condition by calling `requestWithdraw` while the strategy APR is zero. [4](#0-3)  The request is added to the shared `apr0TotalPrincipal` bucket rather than ordinary epoch withdrawal accounting. [5](#0-4)  The bucket is not isolated per user during settlement: `stopEpoch` first calls the shared APR0 preparation routine, and that routine reverts globally when `apr0TotalPrincipal != 0` and `unscaledApr != 0`. [6](#0-5) 

The relevant sequence is:

1. Start an epoch with APR set to zero.
2. Attacker deposits or uses an existing tranche balance and calls `requestWithdraw`.
3. `requestWithdraw` increases `apr0TotalPrincipal`.
4. The manager later changes the active APR to a nonzero value before the request epoch is settled.
5. At `epochEndDate`, the manager calls `stopEpoch` or `stopEpochWithDuration`.
6. `_stopEpoch` calls `prepareStopEpochWithApr0`, which reverts on the attacker’s outstanding APR0 bucket.
7. No tranche holder’s withdrawal can be settled through that attempted stop call.

The failure is analogous to one market reverting inside a shared settlement callback: one user’s unprocessed request changes a shared precondition and causes the common settlement path to revert for the entire pool. [3](#0-2) 

### Impact Explanation
The invariant broken is epoch progress and timely withdrawal settlement. [7](#0-6)  While `apr0TotalPrincipal` remains nonzero and `unscaledApr` remains nonzero, every `stopEpoch` attempt reverts before `pendingWithdraws`, interest accounting, tranche prices, or fees are finalized. [2](#0-1)  This temporarily freezes all epoch withdrawals and prevents the honest manager from completing settlement under the newly configured APR. [8](#0-7) 

The freeze is recoverable only by changing the current APR back to zero and stopping the epoch again, after which `prepareStopEpochWithApr0` clears `apr0TotalPrincipal`. [9](#0-8)  The practical impact is delayed settlement and delayed access to the full pending withdrawal amount for all requesters, proportional to `pendingWithdraws`. [10](#0-9) 

### Likelihood Explanation
The attacker only needs a tranche balance and permission to submit a withdrawal request during a zero-APR period. [11](#0-10)  The additional condition is an ordinary APR transition before the outstanding request is settled, since the code explicitly supports manager-configured APRs but does not prevent changing APR while APR0 principal is outstanding. [12](#0-11)  Because `stopEpoch` applies `_newApr` only after APR0 preparation succeeds, an APR passed as the next-epoch parameter does not itself trigger the revert; the problematic transition is changing the strategy’s current `unscaledApr` before settlement. [13](#0-12) 

### Recommendation
Do not make global epoch settlement depend on an APR compatibility check for stale user requests. [12](#0-11)  At minimum, prevent APR changes while `apr0TotalPrincipal != 0`, or migrate outstanding APR0 requests into the normal withdrawal accounting path when the APR changes. [5](#0-4)  Alternatively, have `prepareStopEpochWithApr0` settle or quarantine the outstanding bucket instead of reverting, so one requester cannot make the shared `stopEpoch` path unusable. [14](#0-13) 

### Proof of Concept
A Foundry regression test can reproduce the sequence with the existing credit-vault fixture:

```solidity
function testApr0RequestBlocksStopAfterAprChange() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // Start an APR0 configuration.
    vm.prank(manager);
    strategy.setAprs(0, 0);

    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    // Unprivileged lender creates an APR0 pending request.
    uint256 trancheAmount = IERC20(address(AAtranche)).balanceOf(address(this)) / 2;
    uint256 requested = idleCDO.requestWithdraw(trancheAmount, address(AAtranche));
    assertGt(requested, 0);
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // Honest operational APR update before the request settles.
    vm.prank(manager);
    strategy.setAprs(10e18, 0);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Shared epoch settlement is blocked by the single outstanding APR0 request.
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(manager);
    cdoEpoch.stopEpoch(10e18, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertGt(strategy.pendingWithdraws(), 0);
}
```

The revert occurs inside `prepareStopEpochWithApr0`, before `IdleCDOEpochVariant` reaches borrower funding, withdrawal funding, tranche accounting, or the final `isEpochRunning = false` transition. [15](#0-14)

  function prepareStopEpochWithApr0(uint256 _interest) external returns (uint256 _expInterest, uint256 _adjPendingWithdrawFees) {
    _onlyIdleCDO();
    IIdleCDOEpochVariant _cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 _pendingFees = _cdo.pendingWithdrawFees();
    uint256 _tvl = _cdo.getContractValue();
    _expInterest = _interest > 1 ? _interest : _cdo.expectedEpochInterest();
    _adjPendingWithdrawFees = _pendingFees;
    // Principal currently waiting for withdraw that was requested while APR was 0,
    // net of the upfront management fee charged at request time.
    uint256 _principal = apr0TotalPrincipal;

    // Fast path: no APR0 accounting needed.
    if (_principal == 0) {
      return (_expInterest, _adjPendingWithdrawFees);
    }
    // APR0 principal is only valid while APR is 0 for that request lifecycle.
    if (unscaledApr != 0) {
      revert NotAllowed();
    }

    uint256 _apr0NetInterest;
    // APR0 allocation is computed only when stopEpoch receives a real override interest.
    // _expectedInterest == 1 is the "request all funds back" sentinel and is handled in IdleCDO.
    if (_expInterest > 1 && _expInterest > _pendingFees) {
      // Remove already booked withdraw fees from the interest base before splitting.
      uint256 _interestNetOfFees = _expInterest - _pendingFees;
      // Total principal used for the pro-rata split:
      // IdleCDO TVL (which excludes APR0 requested principal) + APR0 principal bucket.
      uint256 _totalPrincipalForSplit = _tvl + _principal;
      if (_totalPrincipalForSplit != 0) {
        // APR0 users get a pro-rata share of realized interest.
        uint256 _apr0InterestGross = _interestNetOfFees * _principal / _totalPrincipalForSplit;
        if (_apr0InterestGross != 0) {
          // Same fee model as normal withdraw interest.
          uint256 _apr0Fee = _apr0InterestGross * _cdo.fee() / FULL_ALLOC;
          _apr0NetInterest = _apr0InterestGross - _apr0Fee;
          _adjPendingWithdrawFees += _apr0Fee;
          _expInterest -= _apr0NetInterest;
        }
      }
    }

    // Finalize one-epoch APR0 interest for current epoch only.
    if (_apr0NetInterest != 0) {
      // Funds owed to withdraw requesters increase by APR0 net interest.
      pendingWithdraws += _apr0NetInterest;
      // Save per-epoch net rate; each APR0 request accrues exactly once on its request epoch.
      apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal;
    }
    // Close current APR0 bucket so it cannot accrue again on later stopEpoch calls.
    apr0TotalPrincipal = 0;
  }
