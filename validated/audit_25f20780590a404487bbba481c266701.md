### Title
Stale `total_weight_rejected` Never Decremented When a Signer Flips from Reject to Accept — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`BlockStatus` tracks per-slot voting outcomes using two independent gating structures — `gathered_signatures` (a map keyed by slot) for acceptances and `responded_signers` (a shared `HashSet<u32>`) for the "already counted" guard on rejections. Because a slot is only added to `gathered_signatures` on acceptance, a signer who first rejects and later accepts the same block causes `total_weight_approved` to be incremented for that slot without ever decrementing `total_weight_rejected`, leaving that signer's weight counted in *both* aggregate totals simultaneously. This mirrors the reported class of bug (a value updated on one path but never reversed on the complementary path), breaking the aggregated-weight-vs-verified-accepts equality the coordinator relies on.

### Finding Description
`BlockStatus` holds separate counters/guards for accept and reject paths: [1](#0-0) 

On `BlockResponse::Accepted`, the guard that decides whether to add weight to `total_weight_approved` is `!block.gathered_signatures.contains_key(&slot_id)`: [2](#0-1) 

On `BlockResponse::Rejected`, the guard that decides whether to add weight to `total_weight_rejected` is `block.responded_signers.insert(slot_id)`: [3](#0-2) 

Because the accept path checks `gathered_signatures` (not `responded_signers`) before crediting `total_weight_approved`, a signer that rejects a block first (crediting `total_weight_rejected` and inserting into `responded_signers`) and then later sends an `Accepted` message for the same block sighash will pass the `gathered_signatures.contains_key` check (since that slot was never inserted into `gathered_signatures`), causing `total_weight_approved` to be incremented as well — with no corresponding decrement of `total_weight_rejected`. There is no code path anywhere in this handler that removes or corrects a stale rejection weight once a signer's vote changes to acceptance, exactly analogous to `withdrawUser` never reversing the `deposit`-side ledger update in the source report.

### Impact Explanation
The node-side coordinator (`SignerCoordinator::get_block_status`) treats `total_weight_rejected` and `total_weight_approved` as if they partition signer weight, using `total_weight_rejected.saturating_add(weight_threshold) > total_weight` to decide the block was rejected by a blocking minority, and `total_weight_approved >= weight_threshold` to decide it was accepted: [4](#0-3) 

With the stale-weight bug, a single signer's weight can be counted in both totals. This can cause the miner to prematurely declare `NakamotoNodeError::SignersRejected` (abandoning/retrying a valid block proposal) or, at minimum, corrupt the failed-txid exclusion accounting (`temporarily_excluded_txids`/`permanently_excluded_txids`), which is driven off `total_weight_rejected`/`blocking_minority` comparisons in the same function. This is a liveness wedge on the mining/coordination path: a valid, ultimately-approved block can be treated as rejected because of one signer's earlier, superseded rejection vote whose weight was never reclaimed.

### Likelihood Explanation
Triggerable by a single signer (one signer's own valid, correctly-signed messages) with no majority or key compromise required — the signer only needs to send a `Rejected` response followed later by an `Accepted` response for the same `signer_signature_hash`/slot, which is within normal signer behavior (e.g., a signer that rejects for a timing/tx reason and then reconsiders and signs after the miner resubmits or after a local retry). No StackerDB tampering or replay across other signers is needed.

### Recommendation
When processing `BlockResponse::Accepted`, check whether `slot_id` is present in `responded_signers` due to a prior rejection, and if so, subtract `signer_entry.weight` from `total_weight_rejected` (and drop any associated `failed_txids` weight contributed by that signer) before adding it to `total_weight_approved`, so a signer's weight is only ever counted toward one of the two totals at a time. Alternatively, track outcome per slot explicitly (e.g., `HashMap<u32, Accepted|Rejected>`) instead of two independently-gated structures, and derive `total_weight_approved`/`total_weight_rejected` by recomputation rather than incremental += mutation.

### Proof of Concept
1. Miner proposes block `B`; `BlockStatus` for `B` starts with `total_weight_approved = 0`, `total_weight_rejected = 0`, empty `responded_signers`/`gathered_signatures`.
2. Signer `S` (slot `k`, weight `w`) sends `BlockResponse::Rejected` for `B`. Handler: `responded_signers.insert(k)` succeeds → `total_weight_rejected += w` (per `stackerdb_listener.rs:515-518`).
3. Signer `S` later sends `BlockResponse::Accepted` for the same `B` (e.g. after local re-evaluation, or a retried proposal round with the identical `signer_signature_hash`). Handler: `gathered_signatures.contains_key(&k)` is `false` (never populated by the reject path) → `total_weight_approved += w` (per `stackerdb_listener.rs:443-446`), and `k` is inserted into `gathered_signatures`.
4. Now `total_weight_rejected` still includes `w` from step 2, while `total_weight_approved` also includes `w` from step 3 — `S`'s weight is double-counted across the two totals, so `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, and the coordinator's rejection-threshold check in `signer_coordinator.rs:509-513` can fire using stale rejection weight that no longer reflects `S`'s actual (accepted) vote.
