### Title
Share-price inflation via direct `token` donation enables theft of subsequent depositors' funds - (File: contracts/IdleCDO.sol)

### Summary
The WiseLending exploit inflated the lending-pool share price by donating underlying tokens so that rounding "in favor of the protocol" minted ~0 shares for later deposits, letting the attacker withdraw the entire pool with 1 wei of shares. The same pattern exists in `IdleCDO`: `getContractValue()` counts the raw `token` balance of the contract, and `_deposit`/`_withdraw` never skim unsolicited transfers. The epoch-based credit-vault variant (`IdleCDOEpochVariant`) explicitly mitigated this by adding `_skimDonatedAssets()` before every accounting touchpoint, but the base `IdleCDO` contract used by the standard tranche products has no such protection.

### Finding Description
`getContractValue()` sums the strategy-token value plus the raw underlying balance held by the contract, with no distinction between lent funds and unsolicited donations (`IdleCDO.sol:178-187`). `_deposit` calls `_updateAccounting()` before transferring the user's funds, so any previously donated balance is crystallized into `priceAA`/`priceBB` via `_virtualPriceAux` (`IdleCDO.sol:283-284`, `429`), and shares are minted as `_amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` (`IdleCDO.sol:437-439`). There is no minimum-mint check, so a deposit smaller than the inflated per-share price mints 0 shares while still crediting the full `_amount` to `lastNAV` through `_mintShares` (`IdleCDO.sol:448-456`).

Attack sequence (unprivileged, no privileged role needed):
1. Before any other deposit (or while attacker holds ~all supply), `depositAA(1 wei)` → mints 1 wei of tranche tokens at `priceAA = oneToken` (`_tranchePrice` returns `oneToken` when supply is 0, `IdleCDO.sol:422-427`).
2. Transfer `D` underlying directly to the `IdleCDO` contract (donation). No skim exists in the base contract.
3. Victim calls `depositAA(V)` with `V < D`. `_updateAccounting()` first re-prices: `priceAA ≈ (1 + D·(1-fee)) / 1 wei`. Then `_minted = V·ONE / priceAA` truncates to `0`. The victim's `V` is added to `lastNAVAA` but the victim holds no shares.
4. In a later block (to pass `_checkSameBlock`, `IdleCDO.sol:479`), attacker calls `withdrawAA(1 wei)` and redeems the entire NAV ≈ `1 + D + V`, profiting `V` minus the performance fee on the donation.

Guards that do not stop this: `whenNotPaused` is not set during normal operation; `_guarded(_amount)` only enforces a TVL cap (`limit`), which the attacker's 1-wei deposit doesn't approach; `_checkDefault` only checks strategy price; `_checkSameBlock` only blocks deposit+withdraw in the same block, not a donation across blocks. In contrast, `IdleCDOEpochVariant._deposit` calls `_skimDonatedAssets()` first (`IdleCDOEpochVariant.sol:647`, `794-796`), confirming the developers recognize this exact class but the fix was not applied to `IdleCDO.sol`.

### Impact Explanation
Direct theft of user funds: every victim deposit smaller than the inflated share price is captured by the attacker, who withdraws the full NAV. On a live tranche the attacker does not need to be the sole holder; any holder can front-run a large pending deposit with a donation and minted-0-share theft proportional to their share fraction. Cost is the donation leakage to other holders plus the performance fee; profit is bounded only by victim deposit size and TVL cap.

### Likelihood Explanation
Requires a tranche with low/atomically-controllable supply or mempool visibility of a victim deposit. `depositAA`/`depositBB` are permissionless (no KYC check exists in base `IdleCDO._deposit` — the `isWalletAllowed` gate is only in `IdleCDOEpochVariant`). A 1-wei supply state occurs for any newly deployed/initialized CDO before its first deposit, and the victim's deposit is front-runnable on-chain. Caveat I could not fully verify within this pass: `GuardedLaunchUpgradable._guarded` may additionally restrict deposits during a guarded-launch phase on some deployments; if a deployment enforces an allowlist permanently, likelihood drops accordingly, but the code path itself remains unprotected.

### Recommendation
Apply the same mitigation the credit vault already uses: skim unsolicited underlying before accounting. In `IdleCDO._deposit`, `_withdraw`, and `harvest`, transfer `_contractTokenBalance(token)` in excess of accounted pending funds to `feeReceiver` before `_updateAccounting()`, or track NAV with an internal accounting balance rather than the raw `balanceOf`. Additionally, revert in `_mintSharesAtCurrPrice` when `_minted == 0` for a nonzero `_amount` so victims cannot silently receive zero shares.

### Proof of Concept
Foundry fork/test sketch against an `IdleCDO` instance (or a locally deployed `IdleCDO` with a mock strategy where `directDeposit = false` so donations remain as raw balance):

```solidity
// contracts/IdleCDO.sol target
function testDonationInflation() public {
    // 1. Attacker is first depositor
    underlying.mint(attacker, 1 + DONATION);
    vm.startPrank(attacker);
    underlying.approve(address(cdo), type(uint).max);
    cdo.depositAA(1);                       // mints 1 wei AA tranche

    // 2. Donate to inflate priceAA (raw balance counted in getContractValue)
    underlying.transfer(address(cdo), DONATION); // e.g. 1000e18
    vm.stopPrank();

    // 3. Victim deposits less than inflated price per share
    underlying.mint(victim, VICTIM_DEPOSIT);     // < DONATION
    vm.startPrank(victim);
    underlying.approve(address(cdo), VICTIM_DEPOSIT);
    uint256 minted = cdo.depositAA(VICTIM_DEPOSIT);
    assertEq(minted, 0);                        // victim gets 0 shares, NAV increases
    vm.stopPrank();

    // 4. Attacker redeems 1 wei share for ~entire NAV next block
    vm.roll(block.number + 1);
    vm.prank(attacker);
    uint256 redeemed = cdo.withdrawAA(1);
    assertGt(redeemed, DONATION);               // donation recovered + victim funds stolen
}
```

Key lines exercised: `getContractValue` counting raw balance (`IdleCDO.sol:183-186`), accounting crystallizing the donation (`IdleCDO.sol:280-284`, `429`), and zero-share mint (`IdleCDO.sol:439`). Compare with the donation tests in `test/foundry/IdleCreditVault.t.sol:5536-5574` which pass only because `IdleCDOEpochVariant` skims donations first.
