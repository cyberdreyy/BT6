### Title
Mid-epoch APR change in `IdleCreditVault.setApr` is applied without checkpointing accrued interest or gating on pending APR0 receipts — (`File: contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.setApr` / `setAprs` / `setAprsWithBuffer` overwrite `lastApr` and `unscaledApr` immediately, with no checkpoint of interest accrued at the old rate and no check on outstanding epoch state (`apr0TotalPrincipal`). This is the same bug class as the external `setRewardPerSecond` report: a rate parameter is mutated while pending accrual exists, so accrual state is corrupted. Concretely, if APR is moved off zero while `apr0TotalPrincipal != 0`, `prepareStopEpochWithApr0` reverts `NotAllowed`, so `stopEpoch` can no longer be executed and all vault funds are frozen until the parameter is reverted.

### Finding Description
`setApr` is callable by the `idleCDO` and the `manager` at any time, in any epoch phase, and only validates `maxApr`: [1](#0-0) [2](#0-1) 

Neither setter checkpoints accrued interest, nor does it check `epochNumber`, `epochEndDate`, or pending APR0 principal. Meanwhile, `requestWithdraw` enters the APR0 accounting path based on the *current* `unscaledApr`: [3](#0-2) 

and `prepareStopEpochWithApr0` — called by the CDO during `stopEpoch` — hard-reverts if any APR0 principal exists while `unscaledApr != 0`: [4](#0-3) 

So an APR0 withdraw requested during an APR-0 epoch (a perfectly legitimate, unprivileged lender action) creates a latent poison: any subsequent APR change — including the routine `setAprsWithBuffer` the CDO/manager performs to price the next epoch — makes `stopEpoch` revert. Additionally, because the epoch interest is computed lazily at `stopEpoch`/`expectedEpochInterest` from the current `lastApr`, a mid-epoch rate change retroactively reprices interest already accrued at the old rate, so lenders lose or gain unclaimed yield with no settlement at the change point — exactly the "change reward rate without updating accrued rewards" flaw.

### Impact Explanation
- **Temporary freezing of all vault funds:** one APR0 withdraw request in an APR-0 epoch plus a subsequent honest APR change makes every `stopEpoch` revert `NotAllowed` through `prepareStopEpochWithApr0` → `pendingWithdraws`/deposits stay locked; LPs cannot exit via the epoch mechanism until the parameter is restored to 0 (which then overwrites the intended new pricing).
- **Theft/loss of unclaimed yield:** interest accrued at the pre-change `lastApr` is never checkpointed; changing the rate mid-epoch reprices the entire elapsed epoch period, so LPs can lose already-earned yield (quantified as `TVL * (oldApr - newApr) * elapsed / YEAR`).

### Likelihood Explanation
The APR0 freeze requires only an unprivileged lender (or any KYC-passing withdraw requester) to call `requestWithdraw` while `unscaledApr == 0`, followed by the manager/CDO setting a nonzero APR — a routine configuration action with no guard tying it to pending APR0 state. The yield-repricing impact requires only a mid-epoch APR change. No malicious privileged role is needed; the vulnerability is the missing mandatory checkpoint/gating, as in the source report.

### Recommendation
- In `setApr`/`setAprs`/`setAprsWithBuffer`, revert (or require an explicit epoch-boundary state) when `apr0TotalPrincipal != 0`, or settle the open APR0 bucket before changing `unscaledApr`.
- Apply APR changes only at epoch boundaries (e.g., stage `nextApr` and have `stopEpoch`/`startEpoch` promote it after accounting is finalized), so accrued interest is always computed at the rate in effect for the elapsed period.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
// Foundry fork test: APR0 request + APR change bricks stopEpoch
function testAprChangeFreezesEpochWithApr0Receipts() external {
    // 1. Vault configured with unscaledApr == 0 (APR0 mode), epoch running.
    // 2. Unprivileged lender requests withdraw -> enters _requestWithdrawApr0,
    //    apr0TotalPrincipal > 0 (IdleCreditVault.sol:285-286, 567-577).
    vm.prank(address(cdo));
    vault.requestWithdraw(amount, lender, principal);
    assertGt(vault.apr0TotalPrincipal(), 0);

    // 3. Manager (honest) sets a nonzero APR for the next epoch. No checkpoint,
    //    no guard on pending APR0 principal (IdleCreditVault.sol:225-235).
    vm.prank(manager);
    vault.setAprs(5e18, 5e18);

    // 4. stopEpoch -> prepareStopEpochWithApr0 sees apr0TotalPrincipal != 0
    //    and unscaledApr != 0 -> revert NotAllowed (IdleCreditVault.sol:505-508).
    vm.expectRevert(NotAllowed.selector);
    vm.prank(address(cdo));
    vault.prepareStopEpochWithApr0(0);

    // Result: epoch cannot stop; all deposits and pending withdraws frozen
    // until APR is restored to 0.
}
```
