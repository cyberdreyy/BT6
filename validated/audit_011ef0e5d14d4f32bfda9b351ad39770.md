### Title
Stale-epoch withdraw receipts escape default haircut and are paid at par — out-of-epoch index read in `defaultRecoveryEpoch`/`instantWithdrawsRequestsByEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2025-58050 is an out-of-bounds read where data outside the intended buffer influences the match result. The direct analog in `IdleCreditVault` is an out-of-epoch read: receipts are stored under the epoch in which they were requested (`instantWithdrawsRequestsByEpoch[user][epochNumber]`, `withdrawsRequestsByEpoch[user][currentEpoch]`), but after a default they are looked up only under `defaultRecoveryEpoch = epochNumber` at finalization time. Any receipt created in an earlier epoch reads back as zero — the "out-of-bounds" slot — and the claim falls through to the unfunded/par path instead of being haircutted by `defaultRecoveryPrice`.

### Finding Description
`requestWithdraw` and `requestInstantWithdraw` key receipt basis by `epochNumber` at request time (lines 282–293, 367–372). `finalizeDefaultRecovery` later sets `defaultRecoveryEpoch = epochNumber` (line 693), which can be strictly greater than the request epoch because `deposit()` increments `epochNumber` at each `stopEpoch` (line 610). Both `defaultPendingClaimBasis` (line 647) and `_defaultPrefundedInstantReserve` (line 719) read `instantWithdrawClaimsByEpoch[epochNumber]` — the finalization epoch — so older-epoch instant basis is excluded from `totalBasis` and from the reserved prefunded amount.

Attack trace (instant path):
1. Epoch N running. Attacker (KYC'd lender via honest CDO calls) calls `requestInstantWithdraw`; receipt recorded in `instantWithdrawsRequestsByEpoch[attacker][N]`, `instantWithdrawClaimsByEpoch[N]` and `pendingInstantWithdraws` increased. Attacker simply does not claim.
2. Honest stop/start cycle bumps `epochNumber` to N+1.
3. Borrower defaults; CDO calls `finalizeDefaultRecovery`. `defaultRecoveryEpoch = N+1`. Basis and prefunded reserve both miss the epoch-N instant claim.
4. Attacker calls `claimInstantWithdrawRequest`. `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[attacker][N+1] == 0` (line 844) and returns without clearing. Execution continues to lines 387–392: full `instantWithdrawsRequests[attacker]` is burned and `_transferFundedClaim` pays the *par* amount from strategy balance. The guard at line 904 only ensures `balance - reserve >= amount`; the prefunded underlying backing the instant receipt was never added to `reserve`, so it is spendable.

The same index mismatch exists for normal withdraw receipts: `_claimDefaultedWithdrawRequest` only clears `withdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (lines 773–774). A pending normal request from epoch < `defaultRecoveryEpoch` yields `claimBasis == 0`, then reaches `_claimFundedWithdrawRequest`, where the epoch-wait check passes once `epochNumber > lastWithdrawRequest[user]` and the aggregate `withdrawsRequests[user]` is claimed at par despite being part of `pendingWithdraws` that was counted in `totalBasis` and priced with the recovery haircut.

### Impact Explanation
An unprivileged lender holding a pre-default receipt receives 100% of claim basis instead of `claimBasis * defaultRecoveryPrice / 1e18`. On the instant path the payout comes from underlying that was deliberately left out of `defaultRecoveryReserve` — direct theft of funds that belonged to the recovery pool or other claimants. On the normal path the receipt was already counted in `totalBasis` (diluting `defaultRecoveryPrice` for everyone) yet is paid at par — a double-counted, over-par payout draining strategy balance/reserve before other claimants. Broken invariant: loss socialization — one recovery price for all defaulted claims.

### Likelihood Explanation
Requires only that a withdraw/instant receipt remain unclaimed across at least one `epochNumber` increment before default finalization — a routine sequence (request during epoch, epoch stops, borrower defaults next epoch). No privileged collusion is needed; the attacker merely delays `claimInstantWithdrawRequest`/`claimWithdrawRequest`, which is permitted by design (receipts are claimable at any later time).

### Recommendation
Track the actual request epoch per receipt rather than assuming `defaultRecoveryEpoch`. For example, store the request epoch alongside `instantWithdrawsRequests[user]`/`withdrawsRequests[user]` (or iterate per-user epochs), and have `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` aggregate over all outstanding epochs rather than only `instantWithdrawClaimsByEpoch[epochNumber]`. Alternatively, record receipts under a monotonically consistent key (e.g., the epoch that will be finalized) so the default-epoch lookup cannot miss older entries.

### Proof of Concept
A Foundry fork PoC: deploy `IdleCDOEpochVariant` + `IdleCreditVault`; attacker deposits, calls `requestInstantWithdraw` (or `requestWithdraw`) in epoch N; run `stopEpoch`/`startEpoch` (epochNumber → N+1); trigger borrower default and `finalizeDefaultRecovery` with `recoveryPrice < 1e18`; call `claimInstantWithdrawRequest`/`claimWithdrawRequest` for the attacker and assert it receives the full par amount while other claimants receive the haircutted amount, and that `defaultRecoveryReserve`/strategy balance is drained accordingly.   function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
