### Title
Anyone can set `unscaledApr`/`lastApr` while `idleCDO` is unset due to skipped access check - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.setApr`, `setAprs`, and `setAprsWithBuffer` gate the caller check on `idleCDO != address(0)`. Between `initialize` (which does not set `idleCDO`) and the owner's `setWhitelistedCDO` call, the check is entirely skipped, so any EOA can write `unscaledApr` and `lastApr` — the variables that drive borrower interest debt and the APR0 withdraw path. This is the same bug class as the Canto `Note.sol` finding: a role-gated setter silently disables its guard when the privileged address is still `address(0)`, letting a first-caller front-run seize privileged functionality.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

```solidity
function setAprs(uint256 _unscaledApr, uint256 _apr) external {
    unscaledApr = _unscaledApr;
    // here we also check that msg.sender is allowed
    setApr(_apr);
}

function setAprsWithBuffer(uint256 _unscaledApr, uint256 _duration, uint256 _buffer) external {
    unscaledApr = _unscaledApr;
    setApr(_duration == 0 ? _unscaledApr : _unscaledApr * (_duration + _buffer) / _duration);
}

function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
        if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
}
```

- `initialize` sets `manager`, `borrower`, `maxApr = DEFAULT_MAX_APR`, and `lastApr = unscaledApr = _apr`, but never sets `idleCDO`. The CDO wiring happens only later via `setWhitelistedCDO` (owner-only, line ~954).
- While `idleCDO == address(0)`, `setApr`'s only auth check is bypassed for every caller. `lastApr` remains capped by `maxApr`, but `setAprs`/`setAprsWithBuffer` assign `unscaledApr` with **no cap at all** — it can be set to `0` or an arbitrary huge value by anyone.
- An attacker only needs to front-run (or simply race) the honest `setWhitelistedCDO` transaction on the deployment block, or call between proxy deployment and wiring in a multi-transaction setup. This mirrors the Note.sol front-run where the first caller became `accountant`.

### Impact Explanation
`unscaledApr` controls two fund-relevant paths:

1. **APR0 withdrawal path**: `requestWithdraw` routes requests into the APR0 bucket when `unscaledApr == 0` (`if (unscaledApr == 0 && !isClosed) _requestWithdrawApr0(...)`), and `prepareStopEpochWithApr0` reverts with `NotAllowed` if `unscaledApr != 0` while an APR0 bucket is open. An attacker who zeroes `unscaledApr` before wiring changes which accounting bucket honest depositors' withdraw requests land in, and a non-zero value later set by the CDO/manager makes `prepareStopEpochWithApr0` revert on every stop while `apr0TotalPrincipal != 0` — permanently freezing stopEpoch settlement until defaulted, i.e., freezing all LP funds in the vault.

2. **Borrower interest debt**: `unscaledApr`/`lastApr` feed `totalInterestDueNow`/`expectedEpochInterest` style accounting used by `stopEpoch`/`stopEpochWithDuration`. A huge attacker-chosen `unscaledApr` set pre-wiring inflates the expected interest figure used to split yield between AA/BB and to compute what the borrower must repay; when the honest borrower repays the real (lower) amount, the accounting mismatch propagates into tranche pricing and can force `stopEpoch` reverts or mis-price LP claims — direct insolvency/freeze of pooled lender funds.

Broken invariant: role-gated configuration (`only CDO or manager may set APR`) is silently disabled during a state window every deployment passes through, corrupting interest accounting that determines fund distribution and epoch settlement. Impact is permanent freezing of vault funds and/or solvency corruption, not a privileged-role compromise — the attacker is an arbitrary EOA.

### Likelihood Explanation
- The vulnerable window is deterministic: it exists on every deployment between `initialize` and `setWhitelistedCDO`, and on any proxy upgrade/redeployment where the CDO is re-wired in a separate transaction.
- Deployment scripts that do not atomically call `initialize` + `setWhitelistedCDO` in one transaction (or a factory multicall) expose a front-runnable gap; even atomic deployment of the strategy before the CDO exists (a common ordering, since the CDO constructor/initializer needs the strategy address) means the window persists for the entire period until the CDO exists and calls `setWhitelistedCDO`.
- Check whether `IdleCreditVaultFactory` wires the CDO in the same transaction as strategy deployment — if any path leaves `idleCDO` unset across blocks, exploitation requires only monitoring the mempool/chain, no privileged access.

### Recommendation
- Do not skip the caller check when `idleCDO == address(0)`; instead require `msg.sender == owner()` (or `manager`) in that branch, e.g.:
  ```solidity
  if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  ```
  with `_cdo` allowed to be `address(0)` only for owner/manager callers, or revert when `idleCDO` is unset except from the owner during setup.
- Bound `unscaledApr` with `maxApr` inside `setAprs`/`setAprsWithBuffer`, since it currently bypasses the cap even for legitimate callers.
- Ensure the factory wires `setWhitelistedCDO` atomically at deployment so the unset window never spans public blocks.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {ERC20PresetMinterPauser} from "@openzeppelin/contracts/token/ERC20/presets/ERC20PresetMinterPauser.sol";

contract SetAprAccessControlPOC is Test {
    IdleCreditVault strategy;
    ERC20PresetMinterPauser underlying;
    address owner = address(0x1);
    address manager = address(0x2);
    address borrower = address(0x3);
    address attacker = address(0xA77AC);

    function setUp() public {
        underlying = new ERC20PresetMinterPauser("USDC", "USDC");
        strategy = new IdleCreditVault();
        // CDO not yet deployed/wired: idleCDO == address(0)
        strategy.initialize(address(underlying), owner, manager, borrower, "Borrower", 500);
    }

    function testAnyoneCanSetAprsBeforeCdoWired() public {
        // Attacker front-runs setWhitelistedCDO: no caller check while idleCDO == 0
        vm.prank(attacker);
        strategy.setAprs(0, 0);
        assertEq(strategy.unscaledApr(), 0);

        // Or set unscaledApr to an uncapped arbitrary value
        vm.prank(attacker);
        strategy.setAprs(type(uint256).max, 1);
        assertEq(strategy.unscaledApr(), type(uint256).max);
    }

    function testAccessCheckReturnsAfterCdoWired() public {
        vm.prank(owner);
        strategy.setWhitelistedCDO(address(0xCD0));
        vm.prank(attacker);
        vm.expectRevert(); // NotAllowed
        strategy.setAprs(0, 0);
    }
}
```

The PoC deploys the strategy, leaves `idleCDO` unset (the documented setup window), and shows an unprivileged EOA writing `unscaledApr`/`lastApr` — including an uncapped `unscaledApr` — which then feeds the APR0 withdraw routing in `requestWithdraw` and the `prepareStopEpochWithApr0` revert path, freezing epoch settlement for the vault.
