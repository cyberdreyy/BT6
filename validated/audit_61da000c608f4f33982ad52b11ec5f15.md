### Title
Claimed instant-withdraw receipts are never removed from `instantWithdrawClaimsByEpoch`, inflating default recovery basis with phantom funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears the per-user receipt (`instantWithdrawsRequests`) and pays out the underlying, but it never decrements `instantWithdrawsRequestsByEpoch[_user][epoch]` or the epoch aggregate `instantWithdrawClaimsByEpoch[epoch]`. If a borrower default is finalized in the same epoch while some other instant request is still unfunded (`pendingInstantWithdraws != 0`), `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` both treat already-claimed-and-paid receipts as live claims backed by strategy-held cash. The phantom amounts inflate `defaultRecoveryPrice`, so early claimants drain the real recovery reserve at an overstated price and later claimants are left with nothing.

### Finding Description
The request/claim accounting for instant withdrawals lives in `requestInstantWithdraw` / `claimInstantWithdrawRequest`. On request, three counters are increased: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]` [1](#0-0) . On a normal (non-default) claim, only `instantWithdrawsRequests[_user]` is cleared — the per-epoch and aggregate claim counters are left untouched [2](#0-1) . By contrast, the default-claim path `_claimDefaultedInstantWithdrawRequest` does decrement all of them, confirming the aggregate is meant to track *unclaimed* claims [3](#0-2) .

At default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `_defaultPrefundedInstantReserve` credits `instantBasis - pendingInstant` as underlying already held by the strategy [5](#0-4) . That "prefunded" assumption is broken for a user who already claimed: `collectInstantWithdrawFunds` moved the cash in [6](#0-5)  and `_transferFundedClaim` paid it out, so the strategy no longer holds it, yet `finalizeDefaultRecovery` still adds it to `reserveAmount` and `totalBasis` [7](#0-6) . This is the analog of the CVE's "queue submission silently skipped" class: a completed claim is never dequeued from the epoch-level ledger, so stale entries corrupt a later settlement.

### Impact Explanation
The stale aggregate inflates both sides of `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, but asymmetrically: the phantom basis is fully counted while the phantom reserve is only counted up to `instantBasis - pendingInstant`. In a mixed epoch (one claimant already paid at par, another still unfunded) the unfunded claimant's basis and every other pending/active basis share a reserve padded with non-existent funds. Concretely, with a claimed amount `C` and unfunded amount `U` in the default epoch, the real cash shortfall is `C` but the stored price is computed as if `C` were still in the contract — the first claimants to call `claimInstantWithdrawRequest`/`claimWithdrawRequest` are overpaid relative to true recovery, and the reserve is exhausted so the last claimants receive 0. This is direct theft/permanent freezing of unclaimed recovery funds, unbounded in `C` (scales with claimed instant volume in the default epoch).

### Likelihood Explanation
Requires a specific but unremarkable sequence: instant withdrawals enabled, at least one instant request funded and claimed, a second instant request pending unfunded, and borrower default finalization in the same epoch. All attacker steps (deposit, request instant withdraw, claim) are unprivileged user actions; the honest borrower defaulting and manager finalizing are allowed by the threat model. No existing guard stops it: the stale counters are never validated against `instantWithdrawsRequests`, and `_ensureDefaultRecoveryInitialized` / `defaulted()` checks do not inspect per-epoch aggregates.

### Recommendation
In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epoch]` (and track/store the request epoch per user if needed, mirroring `_claimDefaultedInstantWithdrawRequest`'s cleanup), so epoch-level claim aggregates only ever reflect outstanding, not yet paid, receipts.

### Proof of Concept
```solidity
// Fork test in test/foundry/IdleCreditVault.t.sol harness.
// Mode: instant withdrawals enabled, mid-epoch default finalization.

// 1. userA deposits and requests instant withdraw of 100e6.
uint256 tranchesA = _depositWithUser(userA, 100e6);
_requestInstantWithdraw(userA, tranchesA);            // instantWithdrawClaimsByEpoch[N] += 100e6

// 2. Epoch starts; CDO funds the request -> pendingInstantWithdraws = 0, strategy holds 100e6.
//    userA claims at par: cash leaves the strategy,
//    BUT instantWithdrawClaimsByEpoch[N] still == 100e6 (stale).
vm.prank(userA);
cdoEpoch.claimInstantWithdrawRequest();
assertEq(strategy.instantWithdrawsRequests(userA), 0);
assertGt(strategy.instantWithdrawClaimsByEpoch(epochN), 0); // BUG: stale basis

// 3. userB requests instant withdraw of 50e6, unfunded -> pendingInstantWithdraws = 50e6,
//    instantWithdrawClaimsByEpoch[N] = 150e6 while true live claims = 50e6.
_requestInstantWithdraw(userB, tranchesB);

// 4. Borrower defaults; finalizeDefaultRecovery computes:
//    prefundedReserve = 150e6 - 50e6 = 100e6  (phantom: userA's cash already paid out)
//    recoveryPrice uses reserveAmount including 100e6 that does not exist.
_handleAndFinalizeDefault();

// 5. userB and earlier claimants are paid at an inflated defaultRecoveryPrice;
//    the reserve is drained by phantom-covered claims and the LAST claimant reverts
//    on safeTransfer or receives 0.
vm.prank(userB);
cdoEpoch.claimInstantWithdrawRequest(); // overpaid relative to real recovery
// assert: strategy.underlying balance < remaining claimBasis * defaultRecoveryPrice
```

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
