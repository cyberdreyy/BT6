Unbounded per-request zstd compression cost for `base64+zstd` encoded account data lets a single request force compression of up to 10MB attacker-controlled bytes - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account` in `account-decoder/src/lib.rs` compresses the full (unsliced-unless-configured) account data with `zstd::stream::write::Encoder` whenever `UiAccountEncoding::Base64Zstd` is requested, with no size cap on the input, unlike the Base58/Binary path which enforces `MAX_BASE58_BYTES`. An attacker can grow an account they own to `MAX_ACCOUNT_DATA_LEN` (10 MiB, defined in `transaction-context/src/lib.rs`) via System Program `Allocate`/CPI realloc, fill it with incompressible (random) bytes, and then issue a single `getAccountInfo` (or `getProgramAccounts`) RPC call with `encoding: "base64+zstd"` to force the validator's JSON-RPC thread to zstd-compress the full 10 MiB on every such call.

### Finding Description
The RPC entrypoint `encode_account` in `rpc/src/rpc.rs` only enforces `MAX_BASE58_BYTES` for `Binary`/`Base58` encodings; for any other encoding (including `Base64Zstd`) it calls `encode_ui_account` unconditionally with the full account data (or data-slice) as input: [1](#0-0) 

Inside `encode_ui_account`, the `Base64Zstd` arm feeds `slice_data(account.data(), data_slice_config)` directly into a fresh `zstd::stream::write::Encoder`, with no length check or cap prior to compressing: [2](#0-1) 

Contrast this with the `Base58`/`Binary` path, which is explicitly capped at `MAX_BASE58_BYTES = 128` bytes: [3](#0-2) 

An unprivileged attacker can grow an account they control to the maximum permitted size using the System Program `Allocate` instruction (capped at `MAX_PERMITTED_DATA_LENGTH`): [4](#0-3) 

or via CPI realloc within their own program, similarly capped at `MAX_ACCOUNT_DATA_LEN` (10 MiB): [5](#0-4) [6](#0-5) 

Once the account holds up to 10 MiB of attacker-chosen (e.g., high-entropy/random) data, every single `getAccountInfo`/`getProgramAccounts` call specifying `encoding: base64+zstd` against that account causes the RPC handler to run `zstd::stream::write::Encoder::write_all` + `finish()` over the full buffer, with CPU cost scaling with input size and entropy (incompressible data is markedly more expensive to compress than all-zero data because the encoder cannot exploit run-length/dictionary matches as effectively). No per-request cost cap independent of `account.data().len()` exists in this path.

### Impact Explanation
This is a single-call, unprivileged RPC-triggered CPU cost amplification: one JSON-RPC request causes the validator's RPC/JSON-RPC-serving thread to perform CPU work proportional to attacker-chosen account size (up to 10 MiB) and content entropy, rather than a fixed, request-level bound. This falls into the "RPC single low-rate call causing unbounded cost" bounty category, since it requires only one call at ≤1 call per `CLUSTER_SLOT_TIME_TARGET / 2` against attacker-owned/authored on-chain data — no leader/gossip/staked-node control, no multiple clients, and no unfiltered `getProgramAccounts` without indexes is needed (a single `getAccountInfo` against one known pubkey suffices).

### Likelihood Explanation
Highly feasible: growing an account to 10 MiB via `Allocate`/realloc and filling it with random data is a normal, permissionless on-chain operation available to any funded account owner (subject to rent for 10 MiB, which is a one-time cost, not a per-request cost). Once set up, the attacker (or anyone with knowledge of the pubkey) can repeatedly issue `getAccountInfo`/`getProgramAccounts` calls with `encoding=base64+zstd` at the allowed low rate, each triggering full-size zstd compression, indefinitely.

### Recommendation
Add an explicit size limit for `Base64Zstd` encoding analogous to `MAX_BASE58_BYTES`, e.g., reject or fall back to plain `Base64` when `slice_data(...).len()` exceeds a fixed threshold (independent of the account's actual size), before invoking the zstd encoder in `encode_ui_account` (`account-decoder/src/lib.rs`). This should be enforced in `encode_account`/`get_encoded_account` in `rpc/src/rpc.rs` the same way it is for `Base58`/`Binary`, so the compression cost per request is bounded by a fixed limit rather than by attacker-controlled account size.

```rust
use std::time::Instant;

fn make_account(len: usize, random: bool) -> AccountSharedData {
    let data = if random {
        (0..len).map(|_| rand::random::<u8>()).collect::<Vec<u8>>()
    } else {
        vec![0u8; len]
    };
    AccountSharedData::from(Account { data, ..Account::default() })

#[test]
fn test_base64_zstd_cost_scales_with_attacker_controlled_size() {
    const MAX_ACCOUNT_DATA_LEN: usize = 10 * 1024 * 1024;

    let zero_account = make_account(MAX_ACCOUNT_DATA_LEN, false);
    let random_account = make_account(MAX_ACCOUNT_DATA_LEN, true);

    let t0 = Instant::now();
    let _ = encode_ui_account(&Pubkey::default(), &zero_account, UiAccountEncoding::Base64Zstd, None, None);
    let zero_elapsed = t0.elapsed();

    let t1 = Instant::now();
    let _ = encode_ui_account(&Pubkey::default(), &random_account, UiAccountEncoding::Base64Zstd, None, None);
    let random_elapsed = t1.elapsed();

    // EXPECTED (fails on current code): a fixed cap should bound total
    // encoder work regardless of account.data().len(); e.g. compressing
    // a small fixed-size slice should be independent of `space`.
    // Assert there's a per-request cap, e.g. encode_ui_account should error
    // or truncate for inputs larger than some MAX_ZSTD_INPUT_BYTES constant.
    assert!(
        random_account.data().len() <= /* MAX_ZSTD_INPUT_BYTES (does not exist today) */ 128 * 1024,
        "no per-request cap on Base64Zstd input size; encoder compressed {} bytes of \

        random_account.data().len(), random_elapsed, zero_elapsed
    );
}
```
This test demonstrates that `encode_ui_account`'s `Base64Zstd` branch has no upper bound on input size and that compression time is driven entirely by `account.data().len()`, which an unprivileged attacker fully controls via on-chain realloc, with no guard comparable to `MAX_BASE58_BYTES` preventing this in `rpc/src/rpc.rs::encode_account`.

```rust
fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())

        );

            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
```
