## Finding Confirmed

I traced the fee-split logic and confirmed the described mechanism is real, though its practical severity is constrained by several factors.

### Title
Timing-Manipulable Transaction-Fee Split Between Active and Pending-Inactive Stake Buckets - (`aptos-move/framework/aptos-framework/sources/stake.move`)

### Summary
`update_stake_pool` splits a validator's accumulated per-epoch transaction fee (`fee_octa`) between the `active` and `pending_inactive` coin buckets of a `StakePool` using the *current* balances of those buckets at the exact moment the function executes during `on_new_epoch`: [1](#0-0) 

Because `stake_active`/`stake_pending_inactive` are read live (not from a fixed snapshot taken at `reconfig_start`), any stake movement between the two buckets that happens up until the reconfiguration transaction executes changes the split ratio.

### Finding Description
`unlock()` (exposed to owners directly and to delegators via `delegation_pool.move`/`staking_contract.move`) moves coins from `stake_pool.active` into `stake_pool.pending_inactive` immediately, not at epoch boundary. If a delegator/owner submits `unlock()` in the last block before a reconfiguration, the `stake_pending_inactive` value used in the division at [2](#0-1)  is inflated, so a larger fraction of the epoch's minted `fee_octa` is minted directly into `pending_inactive` at [3](#0-2)  instead of `active`.

For a `delegation_pool`, this pending_inactive bucket corresponds to a specific OLC's `pending_inactive_shares_pool`, whose drift is later picked up by `synchronize_delegation_pool`/`calculate_stake_pool_drift`, crediting the minted amount to whichever shares pool grew: [4](#0-3) . This means a delegator who times an `unlock()` just before reconfiguration can pull a disproportionate share of the freshly-minted transaction fee into the soon-withdrawable pending_inactive pool, at the expense of the `active_shares` pool that other (non-manipulating) delegators/the operator are entitled to.

### Impact Explanation
This is a real share-accounting skew: it does not touch delegators' pre-existing principal, but it does misallocate a portion of newly minted transaction-fee rewards between the `active` and `pending_inactive` share pools based on last-moment timing rather than actual proportional staking contribution during the epoch. Value is redirected among co-stakers of the same pool (from other active delegators/operator toward whoever moved stake into `pending_inactive` last), which fits "share-accounting corruption that credits the wrong account."

### Likelihood Explanation
Exploitability is real but bounded:
- The redirected amount is capped by `max_fee_octa_allowed_per_epoch_per_pool` (`fee_limit`) at [5](#0-4) , so damage per epoch per validator is limited by that config.
- For a plain, single-owner `stake.move` pool this has no attacker-vs-victim effect since active and pending_inactive both belong to the same owner.
- The attack is meaningful only in multi-delegator `delegation_pool` pools, and requires the attacker to already hold active stake in that specific pool and time an `unlock()` at the right block, which is achievable by any delegator without special privilege — hence it does qualify as an unprivileged-input issue, but the gain scales only with the size of that epoch's fee pool for that one validator, not with total stake.

### Recommendation
Snapshot `stake_active`/`stake_pending_inactive` at `reconfig_start` (or otherwise fix the ratio used for the fee split before any in-epoch `unlock()`/`reactivate_stake()` calls can affect it) instead of reading live balances inside `update_stake_pool`, so the split reflects a stable point-in-time state rather than one manipulable by a last-block transaction.

### Proof of Concept
1. Delegator/owner holds stake split across `active` in a validator's pool that has accumulated `fee_octa` in `PendingTransactionFee` for the epoch.
2. In the last block before reconfiguration, call `unlock()` (directly, or via `delegation_pool::unlock`) to shift a large amount from `active` to `pending_inactive`.
3. `on_new_epoch` → `update_stake_pool` executes, computing `fee_pending_inactive` using the just-inflated `stake_pending_inactive` value at [1](#0-0) , minting a disproportionate share of `fee_octa` into `pending_inactive` at [3](#0-2) .
4. A unit test can compare `DistributeTransactionFee`/resulting bucket values when `unlock()` is called (a) mid-epoch versus (b) in the block immediately preceding `on_new_epoch`, showing the split changes purely due to timing rather than actual epoch-long stake composition.

**Note:** I was unable to view the `PendingTransactionFee`/`register_transaction_fee`-equivalent accumulation logic in the final iteration (tool budget exhausted) to fully confirm whether `fee_octa` accrual itself has any additional mitigations (e.g., partial accrual per block rather than a single lump sum) that could further limit or negate this timing window; this should be verified before treating the recommendation as complete.
