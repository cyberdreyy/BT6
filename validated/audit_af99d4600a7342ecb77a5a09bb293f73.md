### Title
Missing fee-amount validation in `createDstEscrow` lets an unprivileged caller deploy a destination escrow whose withdraw always reverts via arithmetic underflow - (File: contracts/BaseEscrowFactory.sol, contracts/EscrowDst.sol)

### Summary
`BaseEscrowFactory.createDstEscrow` accepts a fully caller-supplied `Immutables.parameters` field (encoding `protocolFeeAmount` and `integratorFeeAmount`) with **no validation** that the sum of these fees does not exceed `immutables.amount`. This is inconsistent with the source-side flow in `_postInteraction`, which explicitly enforces `integratorFeeAmount + protocolFeeAmount < takingAmount` before proceeding. Because `EscrowDst._withdraw` later computes `immutables.amount - integratorFeeAmount - protocolFeeAmount` without any bound check, an escrow created with fee amounts summing above `amount` will permanently revert on `withdraw`/`publicWithdraw` with an arithmetic underflow (Panic 0x11), exactly matching the reported root cause pattern (unchecked subtraction from an unbounded/attacker-controlled deduction value).

### Finding Description
`createDstEscrow` is a public, unprivileged entry point: [1](#0-0) 

It only validates the native value sent (`msg.value == safetyDeposit [+ amount]`) and the cancellation timing, but never inspects or bounds the caller-supplied `dstImmutables.parameters` payload that encodes the fee amounts. Compare this to the guarded source-side path, which explicitly checks the analogous invariant: [2](#0-1) 

The unguarded fee values are later decoded and subtracted unconditionally in `EscrowDst._withdraw`, which is reached from both `withdraw` and `publicWithdraw`: [3](#0-2) 

If `integratorFeeAmount + protocolFeeAmount > immutables.amount`, the line `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` underflows and reverts unconditionally — for every future call to `withdraw` or `publicWithdraw`, by any caller (taker or public), because the immutables (and thus this computed value) are fixed at escrow-creation time and re-validated by hash on every call. This is the same class of bug as the Taurus finding: a subtraction of an unbounded, unvalidated deduction amount from a capped/base amount, causing certain-revert instead of graceful degradation.

### Impact Explanation
Once such an escrow is created, its funds can never be released through `withdraw`/`publicWithdraw` — the only recovery path is `cancel()`, which is restricted to `onlyCaller(taker)` and only becomes available after the `DstCancellation` timelock elapses: [4](#0-3) 
This matches the "Medium: smart contract unable to operate because required token/native balances can be broken by an unprivileged actor" bounty tier — the escrow contract instance becomes permanently unable to execute its core withdraw function due to a state (fee parameters) set entirely by an unprivileged, public function call, with no factory-side or escrow-side validation ever performed. It also produces a "temporary freezing of funds during the live swap lifecycle" (funds are locked from creation until the cancellation timelock expires), aligning with the High-tier impact category as well, depending on duration.

### Likelihood Explanation
Likelihood is High for reachability: `createDstEscrow` is a completely public, unprivileged function and nothing prevents `parameters` from encoding `protocolFeeAmount + integratorFeeAmount > amount` — no unit test or on-chain check enforces this invariant on this path (only the `_postInteraction`/source path enforces it). This could be triggered by a resolver's fee-calculation bug, a malformed/malicious `parameters` payload, or simply by any address directly invoking the public `createDstEscrow` function with crafted immutables.

### Recommendation
Add the same invariant check already used in `_postInteraction` to `createDstEscrow` (or generically inside `EscrowDst`/`BaseEscrowFactory` before deployment):
```solidity
(uint256 integratorFeeAmount, uint256 protocolFeeAmount) = (dstImmutables.integratorFeeAmount(), dstImmutables.protocolFeeAmount());
if (integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
Alternatively, clamp the subtraction in `EscrowDst._withdraw` using `Math.min` or a saturating subtraction so withdrawal cannot underflow-revert regardless of how the escrow was funded.

### Proof of Concept
1. Attacker (or a buggy resolver) calls `escrowFactory.createDstEscrow{value: safetyDeposit + amount}(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.amount = 100` and `dstImmutables.parameters = abi.encode(protocolFeeAmount = 60, integratorFeeAmount = 60, protocolFeeRecipient, integratorFeeRecipient)` (sum 120 > 100), funding it with their own tokens/ETH as required.
2. The factory deploys the clone without validating the fee sum, per [1](#0-0) .
3. After the withdrawal timelock, anyone calls `withdraw(secret, immutables)` or `publicWithdraw`; execution reaches `_withdraw` and reverts with Panic 0x11 at `immutables.amount - integratorFeeAmount - protocolFeeAmount`, per [5](#0-4) .
4. The maker can never receive the escrowed funds; only the `taker` recorded in immutables can eventually reclaim them via `cancel()` after `DstCancellation`, freezing the swap's destination-side funds for the entire withdrawal window.
