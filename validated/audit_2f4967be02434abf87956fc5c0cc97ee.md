### Title
Unsanitized `file.Name` in `processZipUIDGidField` allows zip-slip-based arbitrary path `Lchown` - ([File: helpers/archives/zip_extra.go])

### Summary
`processZipUIDGidField` calls `os.Lchown(file.Name, UID, GID)` using the raw, attacker-controlled `zip.FileHeader.Name` with no path validation. Unlike the sibling `tarzstd` extractor, which explicitly chroots extraction to a directory with `filepath.Abs`/`strings.HasPrefix` checks, the zip extraction path (`helpers/archives/zip_extract.go` and `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`) performs no such containment check, so a crafted zip entry name containing `../` sequences can cause file writes and ownership changes outside the intended extraction directory.

### Finding Description
`ExtractZipArchive` iterates `archive.File` and, for each entry, calls `extractZipFile(file)` which does `os.MkdirAll(filepath.Dir(file.Name), ...)` and then creates/writes the file directly at `file.Name` [1](#0-0) . It performs no `filepath.Abs`/prefix check against a root directory, unlike the tar+zstd extractor which explicitly enforces `strings.HasPrefix(path, e.dir+string(filepath.Separator))` before writing any entry [2](#0-1) . The zip extractor used by `ziplegacy.extractor.Extract` simply forwards to `archives.ExtractZipArchive(zr)` and ignores its own `dir` field entirely for path containment [3](#0-2) .

After extraction, `ExtractZipArchive` processes zip "extra" metadata via `processZipExtra(&file.FileHeader)` for every entry [4](#0-3) . For a `ZipUIDGidFieldType` extra field, `processZipExtra` dispatches to `processZipUIDGidField(data, file)` [5](#0-4) , which reads the UID/GID from the attacker-supplied extra field bytes and calls `os.Lchown(file.Name, int(ugField.UID), int(ugField.Gid))` — again using the raw `file.Name` with no path validation [6](#0-5) .

Since `file.Name` is fully attacker-controlled zip entry metadata and is never sanitized against zip-slip anywhere in this call chain (`readZipExtraField` → `processZipExtra` → `processZipUIDGidField` → `os.Lchown`), a job that supplies a zip archive containing an entry named e.g. `../../other-project/checkout/some-file` with an embedded `0x7875` extra field will cause the extraction code to first write/create a file at that traversal-resolved path (via `extractZipFile`) and then call `os.Lchown` on that same path, changing its ownership. There is no allowed-path, chroot, or `errorIfGitDirectory`-style traversal check that would block this — `errorIfGitDirectory` only detects `.git` directory names for a different concern, not path traversal [7](#0-6) .

### Impact Explanation
On a shared runner filesystem, if a job-supplied archive (e.g. a cache archive processed through `ExtractZipFile`/`ExtractZipArchive`, or via the `ziplegacy` extractor) is extracted with entry names crafted to traverse out of the job's own build/cache directory, the process can create a file and then `Lchown` it to attacker-chosen UID/GID at a path in another project's checkout or shared cache tree, corrupting ownership state of files not owned by the extracting job. This is a real path-containment defect, not merely a theoretical concern, because the write step (`extractZipFile`) and the chown step (`processZipUIDGidField`) both operate on the same unsanitized `file.Name`.

### Likelihood Explanation
Precondition is that the runner extracts a zip archive whose contents/names are attacker-controlled (e.g., a cache archive built and uploaded by the job itself, later restored by the runner) and that the runner process has sufficient privilege/access to write and `Lchown` outside the intended job directory (e.g., shared cache directories or another checkout sharing a filesystem, as is common with shared-cache shell/non-namespaced executors). Since `zip.FileHeader.Name` is fully attacker-settable, and `ZipUIDGidField` (extra field type `0x7875`) is a standard, well-documented zip extra field that any user can embed with a standard zip library, constructing the malicious archive is straightforward and repeatable.

### Recommendation
Add path containment validation in the zip extraction path analogous to the tar+zstd extractor: before using `file.Name` anywhere (`extractZipFile`, `lchmod`, and `processZipExtra`/`processZipUIDGidField`/`processZipTimestampField`), resolve it against the intended extraction root with `filepath.Abs`/`filepath.Join` and reject entries whose resolved path escapes that root (mirroring `commands/helpers/archive/tarzstd/tarzstd_extractor.go` lines 58-64). This check should be centralized (e.g., in `ExtractZipArchive` before both extraction loops) so it applies uniformly to file writes, `lchmod`, and all `processZipExtra` sub-handlers including `processZipUIDGidField`.

### Proof of Concept
Go unit test in `helpers/archives`:
```go
func TestExtractZipArchive_RejectsZipSlipWithUIDGidExtra(t *testing.T) {
    tmpRoot := t.TempDir()
    outsideFile := filepath.Join(filepath.Dir(tmpRoot), "victim-owned-file")
    require.NoError(t, os.WriteFile(outsideFile, []byte("victim"), 0644))
    defer os.Remove(outsideFile)

    var buf bytes.Buffer
    zw := zip.NewWriter(&buf)
    // craft an entry name that traverses out of tmpRoot
    traversal := filepath.Join("..", filepath.Base(outsideFile))
    fh := &zip.FileHeader{Name: traversal}
    fh.SetMode(0644)
    // embed ZipUIDGidFieldType extra field
    var extra bytes.Buffer
    _ = binary.Write(&extra, binary.LittleEndian, ZipExtraField{Type: ZipUIDGidFieldType, Size: uint16(binary.Size(ZipUIDGidField{}))})
    _ = binary.Write(&extra, binary.LittleEndian, ZipUIDGidField{Version: 1, UIDSize: 4, UID: 1234, GIDSize: 4, Gid: 1234})
    fh.Extra = extra.Bytes()
    w, _ := zw.CreateHeader(fh)
    _, _ = w.Write([]byte("payload"))
    zw.Close()

    zr, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, os.Chdir(tmpRoot))
    _ = ExtractZipArchive(zr)

    // Expected assertion (currently FAILS, proving the bug):
    // ownership/content of outsideFile must be unchanged
    st, _ := os.Stat(outsideFile)
    sysStat := st.Sys().(*syscall.Stat_t)
    assert.NotEqual(t, uint32(1234), sysStat.Uid, "victim file outside extraction root must not have its ownership changed")
}
```
Expected result on the current code: the assertion fails, demonstrating that `os.Lchown` is invoked on the traversal-resolved path outside `tmpRoot`.

```go
func processZipUIDGidField(data []byte, file *zip.FileHeader) error {
	var ugField ZipUIDGidField
	err := binary.Read(bytes.NewReader(data), binary.LittleEndian, &ugField)
	if err != nil {
		return err
	}

	if !(ugField.Version == 1 && ugField.UIDSize == 4 && ugField.GIDSize == 4) {
		return errors.New("uid/gid data not supported")
	}

	return os.Lchown(file.Name, int(ugField.UID), int(ugField.Gid))
```
