### Title
KYC-blocked lender can fully exit the vault by transferring tranche tokens to an allowed wallet, since restriction is checked on `msg.sender` but never on tranche-token transfers or claim payouts - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` enforces the Keyring credential gate only on the caller of the entry points (`_deposit`, `depositDuringEpoch`, `requestWithdraw`, and the queue's `requestDeposit`/`requestWithdraw`), while `IdleCDOTranche` is a plain ERC20 with no transfer hook and the claim paths (`claimWithdrawRequest`, `claimInstantWithdrawRequest`, `claimDepositRequest`) perform no `isWalletAllowed` check at all. A lender whose Keyring credential is revoked after depositing — the intended meaning of the gate, per `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw` — can transfer their tranche tokens to any credentialed wallet, which then requests and claims the full withdrawal on their behalf. This is the direct analog of the Ethena `FULL_RESTRICTED` approval bypass: the withdrawal path authenticates the operator, not the economic owner of the position.

### Finding Description
The Keyring gate is applied exclusively to `msg.sender`:

- `IdleCDOEpochVariant.requestWithdraw` reverts only if `!isWalletAllowed(msg.sender)`; the burned balance (`_userTrancheBal(msg.sender, _tranche)`) and the receipt in `IdleCreditVault.requestWithdraw(_underlyings, msg.sender, principal)` are both keyed to the same caller.
- `IdleCDOEpochVariant._deposit` and `depositDuringEpoch` check `isWalletAllowed(msg.sender)` only.
- `IdleCDOEpochQueue.requestDeposit`/`requestWithdraw` call `_checkAllowed(msg.sender)` and key `userDepositsEpochs`/`userWithdrawalsEpochs` by `msg.sender`.
- `claimWithdrawRequest`, `claimInstantWithdrawRequest`, and the queue's `claimDepositRequest`/`claimWithdrawRequest` pay `msg.sender` with no Keyring check whatsoever.

Meanwhile `IdleCDOTranche` has no `_beforeTokenTransfer`/`_transfer` override (verified: no matches in `contracts/IdleCDOTranche.sol`), so tranche tokens move freely between wallets regardless of credential status. The Keyring check is a live `checkCredential` call evaluated at each interaction, so revocation after deposit is supported by design — but revocation is ineffective because value can be laundered through a transfer plus an allowed caller.

Attack path (named phase/mode): during the buffer period of a running deployment (fixed-APR or APR0, any tranche):

1. Blocked lender `L` calls `AAtranche.transfer(helper, balance)` — succeeds, no hook.
2. `helper` (any Keyring-credentialed EOA/contract) calls `cdoEpoch.requestWithdraw(0, AATranche)` — `isWalletAllowed(helper)` passes; `L`'s position is burned and a withdrawal receipt is minted in `helper`'s name via `IdleCreditVault.requestWithdraw`.
3. After `startEpoch`/`stopEpoch` settles the epoch, `helper` calls `cdoEpoch.claimWithdrawRequest()` (or `claimInstantWithdrawRequest` in instant mode) — no Keyring check — and receives `L`'s principal plus interest, then forwards it to `L` off-chain or atomically via a helper contract that also relays the transfer in step 1.

The same bypass applies to queued withdrawals (`IdleCDOEpochQueue.requestWithdraw` → `claimWithdrawRequest`) and to the instant-withdraw receipt path.

Existing guards do not stop this: `_updateAccounting`/`_skimDonatedAssets` are orthogonal, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` gate the epoch phase not the wallet, and `keyringAllowWithdraw` (visible in the ABI) is an explicit owner-set relaxation — this bypass works even while it is `false`, i.e., while the protocol intends withdrawals to be restricted. The dedicated test `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw` asserts the intended invariant ("non-keyring holder cannot withdraw"), which is violated transitively.

### Impact Explanation
The access invariant — that a wallet failing `IKeyring.checkCredential` cannot deposit into or withdraw from the vault — is broken for withdrawal. A credential-revoked lender recovers the entirety of their position (principal plus accrued interest, quantized to their full tranche balance) through an unprivileged intermediary. While no third-party funds are stolen (mirroring the Ethena judge's downgrade rationale), the compliance control that the protocol deliberately enforces — evidenced by the revert in `requestWithdraw` and the explicit `keyringAllowWithdraw` flag — is fully circumvented with a single ERC20 transfer.

### Likelihood Explanation
High whenever Keyring revocation is a live capability. Any blocked holder needs only one credentialed counterparty (or a self-deployed contract that passes, or an OTC desk) to exit. The WriteOffEscrow secondary-market path (`fullfillWriteOffRequest`) already demonstrates the protocol expects tranche tokens to change hands to non-credentialed buyers, making credential revocation of existing holders a realistic operational event.

### Recommendation
Choose one and enforce it consistently:

1. If blocked holders must be unable to exit: add an `isWalletAllowed` check in `IdleCDOTranche` via `_beforeTokenTransfer` (or in a `_update` hook) reverting when `from`/`to` fails the credential check, and add the check to `claimWithdrawRequest`/`claimInstantWithdrawRequest` so stale receipts can't be claimed by a since-revoked requester.
2. If transferability is intended (secondary market), then the `requestWithdraw` gate is security theater — remove it or document that restriction is best-effort, since it can never bind the economic owner.

### Proof of Concept
Foundry test for `test/foundry/IdleCreditVault.t.sol` (modeled on `testOnlyKeyringUsersCanInteract`):

```solidity
function testNonKeyringHolderExitsViaTransfer() external {
  address keyring = address(1);
  address helper  = makeAddr("helper"); // credentialed

  vm.prank(owner);
  cdoEpoch.setKeyringParams(keyring, 1);
  vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector), abi.encode(true));

  uint256 amount = 100 * ONE_SCALE;
  uint256 minted = idleCDO.depositAA(amount); // this contract deposits while allowed

  // Lender's credential is now revoked; helper remains allowed
  vm.mockCall(
    keyring,
    abi.encodeWithSelector(IKeyring.checkCredential.selector, address(this)),
    abi.encode(false)
  );

  // Direct withdraw is correctly blocked for the revoked holder
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.requestWithdraw(minted, address(AAtranche));

  // Bypass: move tranche tokens to an allowed wallet
  IERC20(address(AAtranche)).transfer(helper, minted);
  assertEq(AAtranche.balanceOf(address(this)), 0);

  vm.startPrank(helper);
  uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche)); // passes: helper is allowed
  vm.stopPrank();

  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

  uint256 balPre = underlying.balanceOf(helper);
  vm.prank(helper);
  cdoEpoch.claimWithdrawRequest(); // no keyring check on claim
  assertGt(underlying.balanceOf(helper) - balPre, 0, "revoked holder exited via helper");
  assertEq(AAtranche.balanceOf(helper), 0);
}
```

Expected result: the revoked holder's full position is redeemed to `helper`, proving the `isWalletAllowed` gate on `requestWithdraw` is circumventable via a plain tranche-token transfer.

If the flag is consulted inside `IdleCreditVault.requestWithdraw`/`claimWithdrawRequest` rather than only in the CDO, the bypass conclusion is unchanged — it applies when the flag is `false`, which is precisely the configuration in which the protocol intends blocked wallets to be unable to withdraw.
