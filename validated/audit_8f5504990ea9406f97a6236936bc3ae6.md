### Title
Any lender can permanently freeze the vault by leaving APR0 withdraw principal when the APR turns non-zero - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` contains an assertion-style guard that reverts with `NotAllowed()` whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0` (`IdleCreditVault.sol:502-508`). This mirrors the FoK crash: a state the code assumes impossible (APR0 withdrawal principal outstanding at the same time as a non-zero APR) makes `stopEpoch` permanently revert once reached. Any KYC-passing lender can create that state by calling `requestWithdraw` during an APR=0 epoch, and a subsequent legitimate APR change by the manager bricks every future `stopEpoch`, permanently freezing all vault funds.

### Finding Description
When `unscaledApr == 0`, `requestWithdraw` routes the request through `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` bucket (`IdleCreditVault.sol:285-286`, `567-577`). The only place that bucket is decremented is `prepareStopEpochWithApr0`, which is called by the IdleCDO during `stopEpoch`. But before decrementing, it asserts:

```solidity
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
``` [1](#0-0) 

`unscaledApr` is set by `setAprs`/`setAprsWithBuffer`, callable by the CDO or the manager at any time (`IdleCreditVault.sol:206-220`). Nothing in `requestWithdraw` or `_requestWithdrawApr0` prevents an APR0 request from surviving into an epoch whose APR is non-zero, and nothing lets the bucket be cleared once `unscaledApr != 0`. Unlike the Nord FoK `assert`, which panicked once, this revert is deterministic and repeats on every `stopEpoch` call because `apr0TotalPrincipal` is never reset (`IdleCreditVault.sol:540` is unreachable). The epoch can never be stopped, so queued withdraws can never be funded or claimed via `_claimFundedWithdrawRequest`, which requires `epochNumber` to advance past `lastWithdrawRequest` (`IdleCreditVault.sol:326-328`).

### Impact Explanation
Permanent freezing of all lender funds: once `apr0TotalPrincipal > 0` and `unscaledApr != 0`, every `stopEpoch` reverts, `epochNumber` never increases, and no pending withdraw receipt can ever be claimed. The loss equals the full TVL of the vault plus all pending withdrawal basis. The attacker only needs a dust-sized APR0 withdraw request to trigger it.

### Likelihood Explanation
High once the mode sequence occurs: an unprivileged lender deposits, waits for an epoch running at APR=0, and calls `requestWithdraw`. If the borrower/manager later configures a non-zero APR for a subsequent epoch — a normal operational action — the freeze condition is met with no further attacker involvement. The vault requires the APR0 mode to be used at least once, so likelihood is bounded by whether such pools run zero-APR epochs, which the dedicated `apr0Users`/`apr0RateByEpoch` machinery shows is a supported mode.

### Recommendation
Handle the edge case instead of asserting against it, exactly as in the FoK fix: when `unscaledApr != 0`, `prepareStopEpochWithApr0` should settle the outstanding `apr0TotalPrincipal` at zero interest (set `apr0RateByEpoch[epochNumber] = 0` implicitly by not writing a rate, clear `apr0TotalPrincipal`, and still add principal to `pendingWithdraws`) rather than reverting. Alternatively, forbid APR transitions while `apr0TotalPrincipal != 0`, or auto-settle APR0 requests when `setAprs`/`setAprsWithBuffer` moves APR away from zero.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Setup: deploy/upgraded IdleCreditVault + IdleCDOEpochVariant, KYC'd lender, borrower, manager.
// 1. Manager configures epoch with unscaledApr == 0; lender depositAA(X) via CDO.
// 2. Lender calls CDO.requestWithdraw -> strategy.requestWithdraw(amount, lender, principal)
//    while unscaledApr == 0 -> _requestWithdrawApr0 sets apr0TotalPrincipal = amount.
// 3. Epoch ends; borrower repays; manager calls setAprsWithBuffer(newApr, ...) with newApr != 0
//    (or CDO does at next startEpoch) -> unscaledApr != 0, apr0TotalPrincipal still > 0.
// 4. manager/keeper calls cdo.stopEpoch():
//    -> strategy.prepareStopEpochWithApr0(interest)
//    -> apr0TotalPrincipal != 0 && unscaledApr != 0 -> revert NotAllowed()
// 5. Repeat stopEpoch from any caller: always reverts. epochNumber never advances.
// 6. lender.claimWithdrawRequest() reverts NotAllowed() because
//    epochNumber <= lastWithdrawRequest[lender].
// Assert: vm.expectRevert(NotAllowed.selector) on step 4 and 6; funds permanently locked.
```

Uncertainty note: I did not trace `IdleCDOEpochVariant.stopEpoch` itself to confirm `prepareStopEpochWithApr0` is invoked unconditionally on every stop path (e.g., loss path via `stopEpochWithDuration`). If it is only called on the normal-interest path, an alternative stop path might partially recover the epoch, though normal withdraws would still be stuck. A full PoC should verify which stop paths call it.
