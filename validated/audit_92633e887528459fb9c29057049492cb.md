### Title
Stale rejection weight is never withdrawn when a signer flips from Reject to Accept, letting a single signer's retracted vote permanently pollute the block-status tally - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`BlockStatus` (the miner-side per-block vote tally used by `SignerCoordinator`/`StackerDBListener`) tracks two independent, monotonically-increasing counters — `total_weight_approved` and `total_weight_rejected` — gated by two different, inconsistent membership checks. When a signer first rejects a block and later re-evaluates and accepts the *same* block (a legitimate, explicitly supported flow in this codebase — see `should_reevaluate_reject_reason`/`should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`), its earlier rejection weight is never removed from `total_weight_rejected`. This is the exact shape of the Bribe `totalVoting` bug: a "deposit" (weight added on one side of the tally) is correctly counted, but the corresponding "withdrawal" (removing the stale vote when the signer's position changes) never happens, so a portion of the weight becomes permanently and incorrectly attributed.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, `BlockStatus` holds: [1](#0-0) 

For an **Accepted** response, the gate for crediting `total_weight_approved` is whether the slot already has a stored signature (`gathered_signatures`), *not* whether it's in `responded_signers`: [2](#0-1) 

For a **Rejected** response, the gate for crediting `total_weight_rejected` is membership in the shared `responded_signers` set: [3](#0-2) 

Trace the sequence for one signer `S` with weight `w` on block `B`:
1. `S` broadcasts `Rejected(B)`. `responded_signers.insert(slot_id)` succeeds ⇒ `total_weight_rejected += w`.
2. Later `S` legitimately reconsiders (the signer-side logic explicitly allows re-evaluating a rejected block and switching to acceptance — `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`) and broadcasts `Accepted(B)`.
3. On the Accepted path, the check is `!block.gathered_signatures.contains_key(&slot_id)` — this is `true` (nothing was ever inserted into `gathered_signatures` for `S`), so `total_weight_approved += w` is applied.
4. `block.responded_signers.insert(slot_id)` at line 465 is a no-op (already present from step 1), but **`total_weight_rejected` is never decremented.**

The result: `S`'s weight `w` is now counted in **both** `total_weight_approved` and `total_weight_rejected` simultaneously, even though `S` currently only supports acceptance. This breaks the intended equality that the sum of tallied weights should reflect each signer's *current* verified vote (aggregated-weight vs. verified-accepts divergence), exactly analogous to the Bribe contract's `totalVoting` never being decremented on `withdraw()` while `balanceOf`/`totalSupply` are updated.

### Impact Explanation
This is consumed directly by `SignerCoordinator::get_block_status` in `stacks-node/src/nakamoto_node/signer_coordinator.rs`: [4](#0-3) 

Because `total_weight_rejected` is stuck holding a phantom weight that the signer set no longer actually endorses, this stale weight:
- Counts toward `block_status.total_weight_rejected.saturating_add(weight_threshold) > total_weight` at line 511-513, which can make the miner conclude the block is `SignersRejected` and discard it even though the true, live rejecting weight (accounting for the flip) does not clear the >30% blocking-minority bar.
- Simultaneously the phantom weight also inflates `total_weight_approved` toward the 70% acceptance threshold via the double-count, so the tally no longer satisfies `approved + rejected ≤ total_weight` for a single signer's true, current vote.
- A single signer flip-flopping (which is a normal, protocol-permitted event given re-proposals/timeouts) is sufficient to trigger this — no majority or malicious collusion is required, consistent with a one-slot/one-signer trigger.

This falls squarely in the "aggregated-weight vs. verified-accepts" equality-break category and manifests as a liveness wedge: blocks can be spuriously treated as rejected (forcing pointless re-mining/re-proposal cycles) or the acceptance threshold can be reached with double-counted rather than genuinely-verified weight.

### Likelihood Explanation
The Reject→Accept flip is not a contrived edge case; it is a first-class, explicitly documented signer behavior in this codebase (`should_reevaluate_reject_reason`, `should_reevaluate_block`, and the whole "reject reason allows us to reconsider" path in `stacks-signer/src/v0/signer.rs`). Any timeout-driven re-proposal, sortition catch-up, or reorg-related re-evaluation that flips a signer's stance from reject to accept for the same block hash will trigger this on the miner's `StackerDBListener` tally. This requires only one non-malicious signer changing its mind — a routine occurrence — making the likelihood high relative to bugs needing coordinated majorities.

### Recommendation
When processing an `Accepted` message for a slot that is already present in `responded_signers` (i.e., previously rejected), subtract that signer's weight from `total_weight_rejected` (and, symmetrically, when processing a `Rejected` message for a slot previously counted in `gathered_signatures`/`total_weight_approved`, subtract from `total_weight_approved`) before adding it to the new bucket. Alternatively, track a single `HashMap<slot_id, Vote>` (Accept/Reject) as the source of truth and recompute `total_weight_approved`/`total_weight_rejected` from that map on every update, rather than maintaining two independently-incremented counters gated by inconsistent membership checks.

### Proof of Concept
Not executable from indexed context alone (no local Rust test harness output available here), but the trace above is fully supported by the cited code:
1. Send `BlockResponse::Rejected` from signer `S` (weight `w`) for block `B` → `total_weight_rejected == w`, `responded_signers = {slot_S}` (stackerdb_listener.rs:515-518).
2. Send `BlockResponse::Accepted` from the same signer `S` for the same block `B` → guard `!gathered_signatures.contains_key(&slot_S)` is `true` → `total_weight_approved == w` (stackerdb_listener.rs:443-446); `responded_signers.insert` at line 465 is a no-op.
3. Final state: `total_weight_approved == w` **and** `total_weight_rejected == w` simultaneously for the same signer's weight `w`, violating the intended one-vote-per-signer accounting used by `get_block_status`'s threshold checks (signer_coordinator.rs:509-519).

A background Devin agent with repo/test access should add a unit test in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` (or its test module) that feeds a Rejected message followed by an Accepted message from the same slot_id for the same block and asserts `total_weight_rejected` returns to 0 (or is decremented) once the signer accepts, to confirm and then fix the regression.
