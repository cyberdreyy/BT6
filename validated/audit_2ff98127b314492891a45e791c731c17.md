### Title
Invalid Keyring dependency can permanently lock a lender out of the withdrawal window - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCDOEpochVariant.setKeyringParams` accepts any nonzero address without checking that it is a contract implementing `checkCredential`. If the owner or manager configures an EOA or incompatible contract, every unprivileged lender action gated by `isWalletAllowed` reverts. If this occurs during the buffer phase and remains uncorrected until `startEpoch`, lenders miss the withdrawal-request window and their funds remain locked for the next epoch.

### Finding Description
`setKeyringParams` directly stores `_keyring` and `_keyringPolicyId` without validating a nonzero `_keyring` [1](#0-0) . All nonzero Keyring addresses are invoked through an external interface call in `isWalletAllowed` [2](#0-1) .

Deposits call `isWalletAllowed` before processing user funds [3](#0-2) , and withdrawal requests apply the same check [4](#0-3) . Therefore, setting Keyring to an EOA or a contract that does not return a boolean makes those user calls revert.

The issue has time-sensitive impact because `startEpoch` disables both AA and BB withdrawal requests [5](#0-4) . Correcting the Keyring address after the epoch starts does not reopen withdrawal requests; the affected lender must wait through the full epoch.

### Impact Explanation
A lender who deposited before the misconfiguration can be prevented from submitting `requestWithdraw` during the entire buffer period. Once the owner or manager starts the epoch, withdrawal requests are disabled, so the lender's principal is locked for the configured `epochDuration`.

For example, with a 100,000 USDC deposit and a 36.5-day epoch, the user loses access to the full 100,000 USDC position for that epoch. This is temporary freezing of user funds, with the quantified loss equal to the unavailable principal and any opportunity cost during the epoch.

### Likelihood Explanation
The exploit requires an honest owner or manager to configure an invalid nonzero Keyring dependency, rather than malicious privileged behavior. The setter explicitly permits `address(0)` as a way to disable Keyring, so zero itself is valid; the defect is accepting nonzero values that cannot service the required `checkCredential` call.

No attacker-controlled call is needed. An unprivileged lender merely calling `depositAA`, `depositBB`, `depositDuringEpoch`, or `requestWithdraw` encounters the broken external dependency.

### Recommendation
Validate nonzero Keyring addresses before storing them:

```solidity
if (_keyring != address(0)) {
    if (_keyring.code.length == 0) revert NotAllowed();
}
```

For stronger validation, perform a guarded interface sanity call during configuration and reject implementations that cannot return a boolean. The zero address should remain allowed because `isWalletAllowed` treats it as disabling Keyring checks [2](#0-1) .

### Proof of Concept
The following test can be added to `test/foundry/IdleCreditVault.t.sol`, inside `TestIdleCreditVault`, whose mainnet-fork setup deposits USDC and configures a 36.5-day epoch:

```solidity
function testInvalidKeyringLocksWithdrawalForEpoch() external {
    uint256 amount = 100_000 * ONE_SCALE;

    // Keyring is disabled in setup, so the lender can deposit.
    idleCDO.depositAA(amount);
    uint256 trancheBalance = AAtranche.balanceOf(address(this));
    assertGt(trancheBalance, 0);

    // Honest owner/manager configures an invalid nonzero dependency: an EOA.
    vm.prank(owner);
    cdoEpoch.setKeyringParams(makeAddr("notAContract"), 1);

    // The lender cannot request withdrawal during the buffer period.
    vm.expectRevert();
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Epoch start does not depend on Keyring, so it proceeds with the lender still invested.
    vm.prank(manager);
    cdoEpoch.startEpoch();
    assertTrue(cdoEpoch.isEpochRunning());

    // Even after the owner fixes Keyring, the withdrawal-request window is already closed.
    vm.prank(owner);
    cdoEpoch.setKeyringParams(address(0), 0);

    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // The lender's tranche position remains locked for the 36.5-day epoch.
    assertEq(AAtranche.balanceOf(address(this)), trancheBalance);
}
```

The first revert occurs because `isWalletAllowed` attempts `IKeyring(EOA).checkCredential`, which returns no decodable boolean. The second revert occurs because `startEpoch` has already set `allowAAWithdrawRequest` and `allowBBWithdrawRequest` to false.
