### Title
Replay guard records (burns) a request digest before owner-ownership validation, allowing a griefing attacker to permanently poison a legitimate owner's future vault write - ([File: core/capabilities/vault/authorizer.go])

### Summary
`authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(authResult.Digest(), ...)` before `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())`. Because `RequestReplayGuard.CheckAndRecord` unconditionally marks a digest as "seen" with no rollback path, a request that is later rejected for owner mismatch still permanently consumes that digest, so a subsequent, correctly-owned request using the identical digest is rejected as `ErrRequestAlreadySeen`.

### Finding Description
`authorizer.AuthorizeRequest` (core/capabilities/vault/authorizer.go:99-119) executes the following sequence:
1. `authResult, err := a.authorizeRequest(ctx, req)` — resolves auth via AllowList or JWT path.
2. `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` — records the digest as consumed.
3. `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())` — checks that the `owner` field embedded in the request payload (`EncryptedSecret.Id.Owner` / `SecretIdentifier.Owner`) matches the authorized owner.

`RequestReplayGuard.CheckAndRecord` (core/capabilities/vault/request_replay_guard.go:35-47) inserts the digest into `g.seen` immediately, with no way to remove it if a later step (step 3) fails.

The request digest itself is a deterministic hash of the request's method/id/params (`req.Digest()`, confirmed by comments/tests in `system-tests/tests/smoke/cre/vault_don_test.go` and `system-tests/lib/cre/vault/jwt_auth.go` — "binds the digest of the exact JSON-RPC params wire body"). Critically, for the AllowList path (`allow_list_based_auth.go:34-77`), the *owner* returned in `AuthResult.workflowOwner` comes from the on-chain `WorkflowRegistryOwnerAllowlistedRequest.Owner` — i.e., whichever address called `AllowlistRequest(digest, expiry)` on the workflow registry contract — and is entirely independent from the `owner` field embedded inside the request's `params` (e.g. `DeleteSecretsRequest.Ids[].Owner`). Nothing prevents an attacker who controls their own registered workflow-owner identity from pre-computing the digest of a request whose embedded secret-identifier `owner` field references a victim, and allowlisting that digest under their own address. When such a request is submitted:
- `authorizeAllowListBasedAuth` succeeds (digest is allowlisted, not expired) and returns `AuthResult{workflowOwner: attacker}`.
- `replayGuard.CheckAndRecord(digest)` succeeds and marks the digest used.
- `validateSecretOwnersMatchAuthorized` fails because `ids[].Owner == victim != attacker`.

Because the digest was already recorded in step 2, if the legitimate victim owner later submits the exact matching request (same method/id/params, hence the same digest, with `owner == victim`), `CheckAndRecord` now returns `ErrRequestAlreadySeen`, and the legitimately-owned request is rejected before it ever reaches owner validation or execution.

### Impact Explanation
This is a griefing / denial-of-service vulnerability: an attacker who never had valid credentials for the victim owner can permanently block a specific legitimate vault write (secrets create/update/delete/list) tied to a predictable request id/digest, purely by pre-registering an allowlisted entry (or minting a JWT with a matching `request_digest` claim if applicable) for their own identity referencing the victim's identifiers in the payload. This matches the "denial of service / griefing against legitimate user actions" bounty impact class rather than credential theft or fund movement, since the attacker cannot read/write the victim's actual secret, only block one specific request instance.

### Likelihood Explanation
Exploitability requires: (1) the attacker holds a legitimate but low-privilege registered workflow-owner identity able to call the permissionless `AllowlistRequest` on-chain function (or otherwise obtain a digest-matching credential), and (2) the attacker can predict/guess the exact future request content (`request_id`, secret `key`/`namespace`, and the victim's owner address) that the victim will submit, since the digest is a pure hash of that content. This is feasible when request ids or secret keys follow predictable/enumerable naming conventions, but requires some knowledge of the victim's upcoming request shape, limiting blast radius to a single predictable request rather than arbitrary DoS of all victim traffic (a victim can retry with a different, unguessed `request_id` to get a fresh digest).

### Recommendation
Reorder validation in `authorizer.AuthorizeRequest` so `validateSecretOwnersMatchAuthorized` runs before `replayGuard.CheckAndRecord`, ensuring the digest is only marked "seen" once the request has fully passed all authorization/ownership checks. Alternatively, make `CheckAndRecord` transactional/reversible so a subsequent failure can un-record the digest.

### Proof of Concept
Go unit test plan in `core/capabilities/vault/authorizer_test.go`:
1. Build the existing `TestAuthorizer_AllowListPath_RejectsDeleteOwnerMismatch` setup: allowlist a digest under attacker address `A` for a `DeleteSecretsRequest` whose `ids[0].Owner == victimOwner`.
2. Call `authorizer.AuthorizeRequest(ctx, req)` and assert it fails with the owner-mismatch error (existing behavior).
3. Re-submit the identical `req` (same method/id/params, digest unchanged) but this time backed by an authorization mechanism that legitimately resolves `AuthorizedOwner() == victimOwner` (e.g., allowlist the same digest a second time under `victimOwner`, or use a JWT authorizer returning `victimOwner`).
4. Call `authorizer.AuthorizeRequest(ctx, req)` again and assert the outcome:
   - Expected (buggy) result: returns `nil, ErrRequestAlreadySeen`, even though the owner now matches correctly — proving the digest was burned by the first, rejected request.
   - After fix: the second call should succeed (or at least not fail with `ErrRequestAlreadySeen`) because the replay guard should not have recorded the digest from the failed first attempt.
