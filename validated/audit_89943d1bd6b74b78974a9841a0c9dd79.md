I need to verify how instant requests persist across epochs and how default finalization is triggered.### Title
Cross-epoch instant-withdraw receipts are excluded from default recovery basis via stale `epochNumber` dereference — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug pattern is an iterator whose init silently failed, leaving later `next()`/`exit()` calls to dereference uninitialized pointers. The analog here is `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`: they dereference `instantWithdrawClaimsByEpoch[epochNumber]` — a single "current epoch" pointer — while the gate `pendingInstantWithdraws != 0` is an aggregate that can contain instant-withdraw basis from *earlier* epochs. If an unfunded instant receipt survives a `stopEpoch` (which bumps `epochNumber`), default finalization computes the recovery basis and prefunded reserve from the wrong epoch bucket, inflating `defaultRecoveryPrice` and leaving the stale receipt permanently unclaimable.

### Finding Description
`requestInstantWithdraw` records per-epoch basis under the *request-time* epoch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:367-374
uint256 currentEpoch = epochNumber;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

`epochNumber` is incremented inside `deposit()` when an epoch is running (i.e. during `stopEpoch` processing, line 610). `pendingInstantWithdraws` is only decremented in `collectInstantWithdrawFunds` (line 401), so an instant request that is not fully funded before `stopEpoch` leaves `pendingInstantWithdraws > 0` while its basis stays keyed to the *old* epoch index.

At default finalization:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:644-649
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber]; // current epoch only
}
```

and

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:716-723
uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
if (instantBasis > pendingInstant) {
  prefundedReserve = instantBasis - pendingInstant;
}
```

Both read `instantWithdrawClaimsByEpoch[epochNumber]` — the "wild pointer" — while `pendingInstantWithdraws` aggregates all epochs. Consequences:

1. `totalBasis` in `finalizeDefaultRecovery` (line 680) is understated by the stale-epoch instant amount, so `recoveryPrice` (line 688) is inflated. Defaulted-epoch claimants via `_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` draw `claimBasis * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve`, consuming more than their fair pro-rata share.
2. `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844), so the stale-epoch instant receipt is never haircutted; it falls through to the par claim path in `claimInstantWithdrawRequest` (lines 387-392), which calls `_transferFundedClaim`. That guard requires `balance - defaultRecoveryReserve >= amount` (lines 900-904), so once the (under-reserved) recovery reserve is consumed, the stale claim either reverts permanently or drains underlying belonging to other funded claims.

The analogous guard does not exist: `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` per-epoch, so with `instantBasis(current epoch) < pendingInstant(aggregate)` it returns 0 and no reserve is set aside for the stale receipt.

### Impact Explanation
- Inflated `defaultRecoveryPrice` lets earlier/default-epoch claimants (an attacker holding a normal `requestWithdraw` receipt in the defaulted epoch) extract more underlying per unit of claim basis than the true pro-rata share — direct theft of recovery funds that should back the stale instant receipt and other claimants.
- Because `defaultRecoveryReserve` is decremented per claim (`_transferDefaultRecovery`, line 915) and funded claims hitting `balance - reserve < amount` revert, late claimants and holders of stale-epoch instant receipts face permanent freezing of their claims. Loss magnitude is bounded by the stale instant amount, which the attacker controls up to available instant liquidity.

### Likelihood Explanation
Requires: (a) instant withdraws enabled on the vault, (b) an instant request that remains unfunded across a `stopEpoch` (i.e. `pendingInstantWithdraws > 0` entering the next epoch — possible whenever CDO liquidity is insufficient to fund the full instant queue), and (c) a subsequent borrower default before the receipt is claimed. An unprivileged attacker can deliberately create condition (b) by sizing an instant request beyond available liquid funds; (c) is an environmental trigger, not attacker-controlled. The sequence uses only normal user flows (`requestInstantWithdraw`, `requestWithdraw`, `claimWithdrawRequest`), no privileged role.

**Unverified caveat:** I could not read `IdleCDOEpochVariant.sol` internals (only match counts were returned), so I could not confirm whether `stopEpoch` or epoch-start logic force-settles `pendingInstantWithdraws` to zero. If the CDO guarantees `pendingInstantWithdraws == 0` after every `stopEpoch`, the stale-epoch precondition cannot arise and this reduces to a non-issue. The presence of `defaultInstantWithdrawsFinalized`/`_defaultPrefundedInstantReserve` shows the code explicitly anticipates partially funded instant buckets at finalization, but whether they can span epoch boundaries is unconfirmed.

### Recommendation
Make the recovery basis epoch-agnostic: either track an aggregate `instantWithdrawClaimsTotal` incremented in `requestInstantWithdraw` and decremented in `claimInstantWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest`, or store each user's pending instant claim's epoch (a `lastInstantRequestEpoch` pointer like `lastWithdrawRequest`) and sum that bucket in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`. Apply the same fix to `_claimDefaultedInstantWithdrawRequest`, which should clear the user's actual request epoch rather than `defaultRecoveryEpoch`.
