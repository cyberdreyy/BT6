### Title
Mid-epoch depositors can sandwich an oversized `stopEpoch` interest override and drain excess yield - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
When `depositDuringEpoch` is enabled, a KYC-passed lender can deposit near `epochEndDate`, receive shares priced only against the currently expected epoch interest, and then receive part of any larger interest override supplied by the honest manager in `stopEpoch`. The depositor can request withdrawal immediately after the epoch stops, converting the excess yield into a larger withdrawal receipt and diluting existing tranche holders. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`startEpoch` pauses ordinary deposits and records `expectedEpochInterest` from the configured fixed APR. If mid-epoch deposits are enabled, `depositDuringEpoch` remains callable while the epoch is running and before `epochEndDate`. [4](#0-3) [1](#0-0) 

The mid-epoch mint price is derived from the pre-deposit expected final tranche NAV: the depositor's principal plus only its prorated share of the already modeled epoch interest is divided by the existing holders' expected final NAV. The function then increases `expectedEpochInterest` by that modeled interest, mints strategy tokens, and forwards the deposit to the borrower. [5](#0-4) 

`stopEpoch` accepts an explicit `_interest` override greater than `1`, provided it covers pending withdrawal fees and `_newApr == 0`. The override replaces the expected amount, is pulled from the borrower together with pending withdrawals, and is then included in `_updateAccounting`, which raises tranche prices for all outstanding shares. [6](#0-5) [7](#0-6) 

Therefore, the attacker is not required to hold shares for the epoch over which the surprise yield is produced. A deposit made immediately before `epochEndDate` can capture a pro-rata share of an interest override that was not included in its discounted mint calculation. After `stopEpoch` succeeds, withdrawal requests are re-enabled and `requestWithdraw` prices the attacker's tranche tokens using the updated tranche price. [8](#0-7) [9](#0-8) 

### Impact Explanation
The broken invariant is fair mint/burn: shares minted at a price derived from expected epoch yield receive a portion of a later, larger realized yield. This directly transfers value from existing AA/BB holders to the new depositor. [10](#0-9) [11](#0-10) 

For example, with existing NAV `1,000,000`, expected net epoch interest `10,000`, and an attacker deposit of `1,000,000` immediately before the deadline, the attacker obtains approximately `49.75%` of the post-deposit supply. If the manager's successful `stopEpoch` override realizes `110,000` instead of `10,000`, approximately `49,750` of the unexpected `100,000` excess is credited to the attacker rather than solely to holders who bore the epoch risk. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
The attack requires `isDepositDuringEpochDisabled == false`, an active epoch, and a pending `stopEpoch` call whose `_interest` exceeds the yield modeled by `expectedEpochInterest`. The attacker can be any wallet allowed by `isWalletAllowed`; no owner, manager, guardian, borrower, or privileged behavior is required. [1](#0-0) [14](#0-13) 

The donation skim does not prevent this because the excess is not an unsolicited token balance: it is borrower-supplied epoch interest explicitly pulled through `getFundsFromBorrower` and incorporated into NAV. The epoch pause also does not prevent it because `depositDuringEpoch` is the dedicated live-epoch deposit path. [15](#0-14) [16](#0-15) 

### Recommendation
Price mid-epoch deposits using a conservative upper bound for realizable epoch yield, or settle them into a separate bucket that cannot receive interest above the modeled amount. Alternatively, disable `depositDuringEpoch` whenever stop-epoch interest can be overridden, delay withdrawal eligibility for shares minted during the final portion of an epoch, or require `stopEpoch` to use only `expectedEpochInterest` when mid-epoch deposits are enabled. [17](#0-16) 

### Proof of Concept
A Foundry fork test can reproduce the dilution with these concrete transactions:

```solidity
// Setup: epoch deposits enabled, attacker is wallet-allowed,
// epoch is running, and block.timestamp < epochEndDate.

uint256 existingNav = cdo.lastNAVAA() + cdo.lastNAVBB();
uint256 supply = tranche.totalSupply();

// 1. Attacker front-runs the manager's profitable stopEpoch.
uint256 depositAmount = existingNav;
underlying.approve(address(cdo), depositAmount);
uint256 minted = cdo.depositDuringEpoch(depositAmount, address(tranche));

// Shares are priced from expectedEpochInterest, not the pending override.
assertGt(minted, 0);

// 2. Warp past epochEndDate; honest manager supplies excess realized interest.
vm.warp(cdo.epochEndDate());
uint256 expected = cdo.expectedEpochInterest();
uint256 surpriseInterest = expected * 10;

deal(address(underlying), borrower, surpriseInterest + pendingWithdraws);
vm.prank(borrower);
underlying.approve(address(cdo), surpriseInterest + pendingWithdraws);

vm.prank(manager);
cdo.stopEpoch(0, surpriseInterest);

// 3. Attacker requests withdrawal at the post-surprise tranche price.
uint256 receipt = cdo.requestWithdraw(minted, address(tranche));

// Receipt exceeds principal plus the prorated interest modeled by
// depositDuringEpoch, capturing part of the surprise override.
assertGt(receipt, depositAmount + modeledProratedInterest);
```

The key assertion is that `depositDuringEpoch` computes `minted` from `expectedFinal` and `trancheInterest`, while the later override updates global NAV for the enlarged supply. [18](#0-17) [7](#0-6)

  function depositDuringEpoch(uint256 _amount, address _tranche) external virtual returns (uint256 _minted) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == BBTranche && !isBBDepositEnabled) ||
      isDepositDuringEpochDisabled ||
      skipDefaultCheck ||
      // programmable borrowers use APR=0 so mid-epoch deposits would dilute existing depositors
      isProgrammableBorrower ||
      // check if AYS is active as we don't support deposits during epoch in that case
      isAYSActive ||
      // check if epoch is still running even if not manually stopped yet
      !isEpochRunning || block.timestamp >= epochEndDate ||
      !isWalletAllowed(msg.sender)
    );

    if (_amount == 0) {
      return _minted;
    }

    uint256 _trancheTotSupply = _trancheSupply(_tranche);
    // Avoid pricing discontinuities for the first mid-epoch deposit in a tranche
    _checkNotAllowed(_trancheTotSupply == 0);

    _skimDonatedAssets();
    // Check that limit is not exceeded after removing skimmable raw donations.
    _guarded(_amount);
    _updateAccounting();

    // Get underlyings from user
    _transferUnderlyingsFrom(msg.sender, address(this), _amount);

    // interest for the remaining epoch plus the full buffer period
    // NOTE: _calcInterest already gives full‑epoch + full‑buffer interest for the whole epoch
    //   So when a user joins mid‑epoch, we take the fraction of that full‑period interest 
    //   that matches the time they actually remain plus the entire buffer
    uint256 buffer = bufferPeriod;
    uint256 remaining = epochEndDate - block.timestamp;
    uint256 interest = _calcInterest(_amount) *
      // the time the depositor actually participates (remaining epoch + full buffer)
      (remaining + buffer) /
      // the total time baked into the scaled APR (epoch + buffer).
      (epochDuration + buffer);

    uint256 expectedInt = expectedEpochInterest;
    uint256 pendingFees = pendingWithdrawFees;
    uint256 trancheExpected;
    // existing holders' share of net expected interest for the epoch (pre-deposit)
    // (exclude pendingWithdrawFees since they go to fee receivers, not tranche holders)
    if (expectedInt > pendingFees) {
      trancheExpected = _calcTrancheInterestShare(
        _netGainAfterFees(expectedInt - pendingFees, _calculateManagementFee(lastNAVAA + lastNAVBB, remaining)),
        _tranche
      );
    }
    // interest this deposit will earn for the tranche over the remaining time (net of fees)
    uint256 trancheInterest = _calcTrancheInterestShare(
      _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)),
      _tranche
    );
    // pre-deposit expected final NAV for existing holders.
    // This won't ever be zero as we checked _trancheTotSupply and we seed initial NAV at tranche creation
    uint256 expectedFinal = _lastSavedNAV(_tranche) + trancheExpected;

    // mint at a discounted price so depositor gets principal + its prorated interest at epoch end
    // A mid‑epoch depositor should get _amount + trancheInterest at epoch end.
    // So they need minted = (amount + trancheInterest) / priceEnd.
    // priceEnd = expectedFinal / _trancheTotSupply
    // so minted = (amount + trancheInterest) * _trancheTotSupply / expectedFinal
    _minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
    _mintShares(_tranche, msg.sender, _minted, _amount);

    // update expected epoch interest
    expectedEpochInterest += interest;
    // mint strategy tokens to this contract
    IdleCreditVault(strategy).mintStrategyTokens(_amount);

    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.

    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;

    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest

    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
