### Title
Unauthenticated disclosure of internal LOOP plugin topology and unauthenticated proxy access to plugin metrics/pprof endpoints via `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` - ([File: core/web/router.go])

### Summary
The `loopRoutes` function registers `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol` directly on the `api` router group with no authentication middleware, unlike every other sensitive route group (`debugRoutes`, `sessionRoutes` DELETE, `v2Routes`) which wraps handlers with `auth.Authenticate(...)`. Any unauthenticated client can call these endpoints to enumerate LOOP plugin names/topology and proxy to internal plugin metrics/pprof endpoints.

### Finding Description
In `core/web/router.go`, `NewRouter` builds the `api` group and calls `loopRoutes(app, api)` at line 91 without wrapping it in an authenticated sub-group, in contrast to `debugRoutes` (line 181, wrapped with `auth.Authenticate(..., auth.AuthenticateBySession)`) and all `v2Routes` handlers wrapped with `auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)`.

```go
func loopRoutes(app chainlink.Application, r *gin.RouterGroup) {
	loopRegistry := NewLoopRegistryServer(app)
	r.GET("/discovery", ginHandlerFromHTTP(loopRegistry.discoveryHandler))
	r.GET("/plugins/:name/metrics", loopRegistry.pluginMetricHandler)
	r.GET("/plugins/:name/debug/pprof/*profile", loopRegistry.pluginPPROFHandler)
	r.POST("/plugins/:name/debug/pprof/symbol", loopRegistry.pluginPPROFPOSTSymbolHandler)
}

Similarly `pluginMetricHandler` and `pluginPPROFHandler`/`pluginPPROFPOSTSymbolHandler` proxy arbitrary GET/POST requests to `http://<loopHostName>:<PrometheusPort>/metrics` or `/debug/pprof/...` for any plugin name resolved via `l.registry.Get(pluginName)`, with the only gate being that the plugin name must exist in the registry — no session/token/EI header check:

	...

Because the entire `api` group inherits only the global middlewares registered in `NewRouter` (rate limiter, session cookie store — which does not itself enforce authentication, otelgin, size limits, CORS, helmet), and `loopRoutes` adds no per-route `auth.Authenticate` wrapper, these four routes are reachable by any anonymous HTTP client that can reach the node's web server port.

### Impact Explanation
This is an information-disclosure and internal-surface-exposure issue: an unauthenticated attacker can enumerate all registered LOOP plugin names (`/discovery`), and can further pull Prometheus metrics (`/plugins/:name/metrics`) and pprof profiles/traces (`/plugins/:name/debug/pprof/*`, including `/profile` and `/trace` which can run for attacker-controlled durations) from internal plugin processes that were never intended to be internet-facing. This matches Chainlink's "internal topology / sensitive data disclosure" bounty class rather than key/fund compromise — it does not by itself grant authentication bypass, key disclosure, or fund movement, but it does leak internal plugin architecture, metric labels, and could be leveraged as reconnaissance for further attacks, and the pprof `/profile`/`/trace` endpoints can also cause resource exhaustion (CPU-bound profiling) against internal plugin processes, an availability concern.

### Likelihood Explanation
Very high likelihood/feasibility: no credentials, session, token, or EI header of any kind are required. Any network-reachable unauthenticated client hitting the node's configured web server port can send `GET /discovery`, `GET /plugins/<name>/metrics`, or `GET/POST /plugins/<name>/debug/pprof/...` and receive a response, fully repeatable, and does not depend on any race condition or timing.

### Recommendation
Wrap `loopRoutes` registrations in an authenticated sub-group consistent with the rest of the router, e.g. mirror `debugRoutes`/`v2Routes` by using `r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession))` (or session-only, matching `debugRoutes`) before registering `/discovery`, `/plugins/:name/metrics`, and the pprof proxy routes. Since `/discovery` is meant to be scraped by an external Prometheus, consider a dedicated bearer-token check (similar to `prometheusHandler`'s token comparison) if session/API-token auth is impractical for a scraper.

### Proof of Concept
Go handler-level integration test in `core/web`:
1. Build a `chainlink.Application` test fixture (as used in `core/web/loop_registry_test.go`) with `LoopRegistry` populated with at least one registered plugin (name `"foo"`, `PrometheusPort` set).
2. Call `web.NewRouter(app, nil)` to get the `*gin.Engine`.
3. Issue `httptest.NewRequest(http.MethodGet, "/discovery", nil)` with **no** `Authorization` header, no session cookie, no EI headers, and serve it through the router.
4. Assert the response status is `200 OK` (not `401`/`403`) and the JSON body contains `"__meta_plugin_name":"foo"` and the plugin's metrics path label.
5. Repeat for `GET /plugins/foo/metrics` and `GET /plugins/foo/debug/pprof/heap` unauthenticated, asserting non-401/403 responses (200 or 500 from the proxied backend, but never an auth rejection), confirming the missing auth middleware on these routes versus a control test on `/v2/jobs` which should return `401`.

// discoveryHandler implements service discovery of prom endpoints for LOOPs in the registry
func (l *LoopRegistryServer) discoveryHandler(w http.ResponseWriter, req *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	groups := make([]*targetgroup.Group, 0, 1+len(l.registry.List()))

	// add node metrics to service discovery
	groups = append(groups, pluginGroup(l.discoveryHostName, l.exposedPromPort, "/metrics"))

	// add all the plugins
	for _, registeredPlugin := range l.registry.List() {
		group := pluginGroup(l.discoveryHostName, l.exposedPromPort, pluginMetricPath(registeredPlugin.Name))
		group.Labels[LabelMetaPluginName] = model.LabelValue(registeredPlugin.Name)
		groups = append(groups, group)
	}
