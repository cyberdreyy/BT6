### Title
Stale per-epoch instant-withdraw receipt causes underflow revert in `claimInstantWithdrawRequest` after default, permanently freezing claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2016-7052 is a NULL-deref crash: an operation on a record that was already cleared dereferences missing state and aborts. The credit-vault analog is in `IdleCreditVault.claimInstantWithdrawRequest`: funded instant-withdraw claims clear the aggregate `instantWithdrawsRequests[_user]` but never clear the per-epoch ledger `instantWithdrawsRequestsByEpoch[_user][epoch]`. If the epoch in which an already-claimed instant receipt was created later becomes the default epoch, `_claimDefaultedInstantWithdrawRequest` reloads the stale per-epoch basis and executes `instantWithdrawsRequests[_user] -= claimBasis` on a zeroed aggregate, reverting on underflow forever and blocking that user's entire claim path.

### Finding Description
`requestInstantWithdraw` records both the aggregate and the per-epoch receipt: `instantWithdrawsRequests[_user] += _amount` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` [1](#0-0) . The funded claim path only zeroes the aggregate: `instantWithdrawsRequests[_user] = 0`, leaving `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` untouched [2](#0-1) .

After a borrower default, `finalizeDefaultRecovery` sets `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`, which is true whenever the current-epoch instant queue was only partially prefunded [3](#0-2) . From then on every `claimInstantWithdrawRequest` first runs `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and subtracts it from the aggregate: `instantWithdrawsRequests[_user] -= claimBasis` [4](#0-3) [5](#0-4) .

Sequence:
1. Epoch N running; instant-withdraw window is partially funded — the borrower/CDO collects only part of `pendingInstantWithdraws` via `collectInstantWithdrawFunds`, so `pendingInstantWithdraws > 0` while some users' receipts are already paid out through `_transferFundedClaim`.
2. Victim claims their funded instant receipt via `claimInstantWithdrawRequest`. Aggregate is zeroed; `instantWithdrawsRequestsByEpoch[victim][N]` still holds the basis.
3. The epoch fails and `finalizeDefaultRecovery` runs with `defaultRecoveryEpoch = N` and `defaultInstantWithdrawsFinalized = true` (the unfunded remainder keeps `pendingInstantWithdraws != 0`).
4. Victim calls `claimInstantWithdrawRequest` again (e.g. to collect an older funded receipt or their recovery share). `_claimDefaultedInstantWithdrawRequest` finds `claimBasis = instantWithdrawsRequestsByEpoch[victim][N] > 0`, then executes `instantWithdrawsRequests[victim] -= claimBasis` where the aggregate is `0` → arithmetic underflow → permanent revert.

The per-epoch double-ledger was added precisely to distinguish default-epoch receipts from funded ones, but the funded-claim path was never updated to clear it — exactly the "dangling pointer to freed record" shape of the CVE.

### Impact Explanation
Permanent freezing of funds. The victim's `claimInstantWithdrawRequest` reverts unconditionally: they cannot claim the defaulted-epoch recovery, and because the defaulted-epoch clearing runs first in the same function, any other funded instant receipts are unreachable as well. Their basis was included in `defaultPendingClaimBasis` → `totalBasis`, so their pro-rata share of `defaultRecoveryReserve` is locked in the strategy contract forever (unclaimable dust that also diluted every other claimant's `defaultRecoveryPrice`). Loss = victim's entire instant claim basis plus reserve share, per affected user.

### Likelihood Explanation
Requires a specific but legitimate sequence: an epoch where instant withdraws are partially funded (borrower/CDO collected less than the full queue, leaving `pendingInstantWithdraws > 0`), a user claiming the funded portion pre-default, then the borrower defaulting in that same epoch. All attacker/victim actions are unprivileged; the default itself is a normal credit event the protocol explicitly handles. No privileged misbehavior needed — only the missed ledger cleanup.

### Recommendation
In `claimInstantWithdrawRequest`'s funded path (and in `_claimFundedWithdrawRequest` for symmetry), clear the per-epoch entries alongside the aggregate: iterate or track the request epoch so `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are decremented when a receipt is paid at par. Alternatively, in `_claimDefaultedInstantWithdrawRequest`, cap `claimBasis` at `instantWithdrawsRequests[_user]` and skip already-claimed stale entries.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// setup: deposits, epoch N running
_startEpochAndCheckPrices(0);

// user1 requests instant withdraw during epoch N
vm.prank(user1);
cdoEpoch.requestInstantWithdraw(amount, AAtranche); // or requestWithdraw instant path

// manager collects only PART of pending instant funds (partial prefund)
vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds(); // funds < pendingInstantWithdraws

// user1 claims the funded portion; aggregate zeroed, per-epoch entry stale
vm.prank(user1);
cdoEpoch.claimInstantWithdrawRequest();
assertEq(strategy.instantWithdrawsRequests(user1), 0);
assertGt(strategy.instantWithdrawsRequestsByEpoch(user1, epochN), 0); // stale

// borrower defaults on epoch N; recovery finalized while pendingInstantWithdraws > 0
_handleBorrowerDefault(...);            // cdo defaulted
finalizeDefaultRecovery(recovered, source);
assertTrue(strategy.defaultInstantWithdrawsFinalized());

// user1 tries to claim again -> underflow at
// instantWithdrawsRequests[_user] -= claimBasis  (0 - stale > 0)
vm.prank(user1);
vm.expectRevert(); // arithmetic underflow
cdoEpoch.claimInstantWithdrawRequest(); // permanently bricked; reserve share locked
```

Note: this PoC outline depends on the exact partial-prefund path in `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`; the PoC should drive a partial collection so `pendingInstantWithdraws` stays non-zero at finalization while one user's receipt was already paid.
