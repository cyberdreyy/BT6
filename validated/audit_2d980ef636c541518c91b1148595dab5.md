### Title
Stale `BlockInfo` reused across `process_pending_responses_for_block`'s reject/signature loops overwrites a just-signed block with `GloballyRejected` - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`process_pending_responses_for_block` fetches one `BlockInfo` snapshot and then iterates three replayed-vote lists (pre-commits, rejections, signatures) using that same, never-refreshed, in-memory `block_info` for the rejection and signature loops, while the pre-commit loop internally re-fetches and re-persists its own fresh copy via `handle_block_pre_commit`. This is the same "value captured once outside a loop, then reused across iterations that mutate underlying state independently" pattern as H-02's reused `msg.value`: a shared value is consumed/relied upon multiple times in a loop, but the thing backing it (available balance / actual DB block state) has already moved on by the time later iterations run.

### Finding Description
`handle_block_proposal` drains previously-parked votes (`drain_pending_block_responses`) and passes them into `process_pending_responses_for_block`: [1](#0-0) 

The pre-commit loop calls `handle_block_pre_commit` per address. That function does its own `block_lookup_by_reward_cycle`, mutates and `insert_block`s a *fresh* copy, and — if the replayed pre-commits push the weight over threshold — can call `mark_pre_committed`/proceed all the way to `mark_locally_accepted` and `send_block_pre_commit`, persisting `LocallyAccepted`/`signed_self` to the DB: [2](#0-1) [3](#0-2) 

Crucially, the *outer* `block_info` object held by `process_pending_responses_for_block` (the one fetched before the pre-commit loop ran) is never refreshed from the DB after that loop. It is then passed by `&mut` reference into the rejection loop: [4](#0-3) 

`store_and_process_block_rejection` uses this stale object's `has_reached_consensus()` as its short-circuit guard, and on reaching the reject threshold calls `block_info.mark_globally_rejected()` and `self.signer_db.insert_block(block_info)`, which overwrites the DB row unconditionally: [5](#0-4) 

Because the stale `block_info.state` is still `Unprocessed`/`PreCommitted` (not the `LocallyAccepted` that was actually just persisted by the pre-commit loop), `has_reached_consensus()` returns `false`, so the rejection-threshold logic runs to completion. `check_state` explicitly permits `LocallyAccepted -> GloballyRejected` (only `GloballyAccepted` is excluded as a source of `GloballyRejected`): [6](#0-5) 

So `mark_globally_rejected()` succeeds on the stale in-memory object and `insert_block` writes `GloballyRejected` (with `signed_self` still carried over from the stale struct, since `BlockInfo::from` isn't re-run) back to the DB — silently clobbering the row that a moment earlier recorded this signer's own signature (`signed_self`) via the pre-commit loop's independent `handle_block_pre_commit` → `mark_locally_accepted` path. The same staleness affects the subsequent signature loop, which reads `block_info.signed_group.is_some()` off the same stale object rather than the DB.

This breaks the equivocation guard invariant maintained by `signerdb.rs`'s persisted `BlockInfo` record. The system elsewhere relies on that persisted row (`signed_self`, `state`) to prevent double-signing a conflicting sibling (see `has_signed_block_in_tenure`, `get_signed_conflicts`, and the pre-commit "already_signed" check at signer.rs:1316). If the persisted record for a block this signer already signed gets overwritten to `GloballyRejected` by this stale-write, the signer's own bookkeeping of "I already signed this" is lost for that row. A subsequent re-proposal or re-evaluation path (`should_reevaluate_block`, `handle_block_pre_commit`'s `already_signed` check) reads `block_info.signed_self` from this now-corrupted DB row and can conclude it never signed, potentially allowing it to sign a conflicting sibling block later — a double-sign / equivocation-guard loss.

### Impact Explanation
This is a **liveness/safety wedge**: it corrupts the signer's own persisted record of having signed a block, which is the exact bookkeeping used elsewhere (`get_signed_conflicts`, `has_signed_block_in_tenure`, the pre-commit `signed_self` check) to prevent the signer from re-signing a conflicting block at the same height/tenure. Losing that guard is explicitly called out in the impact rubric as High ("losing the equivocation guard on restart" — here, losing it via a race in normal operation rather than restart, but with the same practical effect: the signer's local ledger of prior signatures becomes wrong).

### Likelihood Explanation
This requires only ordinary gossip timing that a single miner or the network naturally produces: for a signer to have *pending* pre-commits, rejections, and signatures all parked for the *same as-yet-unseen block* before the proposal itself arrives (i.e., votes racing ahead of the proposal broadcast), which `drain_pending_block_responses`/`PendingBlockResponses` is explicitly designed to accumulate. No majority-signer collusion, no key compromise, and no auth token access are needed — just message reordering across signers/gossip, which the code already anticipates (hence the "pending" tables existing at all).

### Recommendation
In `process_pending_responses_for_block`, re-fetch `block_info` from `signer_db` (or otherwise synchronize the mutable state) before each loop — particularly before the rejection and signature loops — so decisions are made against the current persisted state rather than a snapshot taken before earlier loop iterations mutated it out-of-band. Alternatively, have `handle_block_pre_commit`/`store_and_process_block_rejection`/`store_and_process_block_signature` always operate on a freshly loaded `BlockInfo` rather than accepting a caller-supplied reference that may already be stale by the time it's used.

### Proof of Concept
1. Signer S receives, before it has the block proposal itself, several `BlockPreCommit`s (from other signers) and a `BlockRejection` for the same not-yet-known `signer_signature_hash` — these get parked via `add_pending_block_pre_commit_response`/`add_pending_block_rejection_response`.
2. The proposal finally arrives; `handle_block_proposal` drains these into `pending_responses` and calls `process_pending_responses_for_block` with a freshly-inserted `block_info` (`Unprocessed`).
3. In the pre-commit loop, replaying the parked pre-commits pushes weight over the 70% threshold; `handle_block_pre_commit` (operating on its own fresh DB lookup) calls the chainstate recheck, then signs: `mark_locally_accepted`, persists `LocallyAccepted` with `signed_self = Some(t)` to the DB, and broadcasts S's own signature.
4. Control returns to `process_pending_responses_for_block`'s rejection loop, still holding the *original* stale `block_info` (`state = Unprocessed`, `signed_self = None`).
5. If the parked rejection(s) (plus any concurrently-arriving ones) cross the 30%-blocking-minority threshold, `store_and_process_block_rejection` sees `has_reached_consensus() == false` (because the stale object is `Unprocessed`, not `LocallyAccepted`), proceeds, calls `mark_globally_rejected()` (permitted transition per `check_state`), and `insert_block` overwrites the DB row to `GloballyRejected` — discarding the `signed_self` timestamp that had just been durably recorded a moment before by step 3, from the DB's own point of view.
6. S's persisted view of this block/tenure no longer reflects that it signed it. On a later re-proposal or conflicting sibling at the same height, checks such as the pre-commit `already_signed` guard (`signer.rs:1316`) or `get_signed_conflicts`/`has_signed_block_in_tenure` consult this corrupted row and can fail to recognize the prior commitment, opening the door to signing a conflicting block — the equivocation guard is effectively lost for this block.

    // Store the block rejection signature and check if we have reached a consensus decision on the block because of it. If we have, update the block state accordingly.
    fn store_and_process_block_rejection(
        &mut self,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        signer_address: &StacksAddress,
        reject_reason: RejectReasonPrefix,
    ) {
        let block_hash = &block_info.signer_signature_hash();
        // We should still store signatures even on consensus reached blocks for auditing purposes.
        // signature is valid! store it
        match self.signer_db.add_block_rejection_signer_addr(
            block_hash,
            signer_address,
            reject_reason,
        ) {
            Err(e) => {
                warn!("{self}: Failed to save block rejection signature: {e:?}",);
            }
            Ok(false) => return, // We already have this signature, do not process it again.
            Ok(true) => (),
        }

        if block_info.has_reached_consensus() {
            // Checking the rejection signatures is pointless. We have already reached consensus on this block.
            return;
        }

        // do we have enough signatures to mark a block a globally rejected?
        // i.e. is (set-size) - (threshold) + 1 reached.
        let rejection_addrs = match self.signer_db.get_block_rejection_signer_addrs(block_hash) {
            Ok(addrs) => addrs,
            Err(e) => {
                warn!("{self}: Failed to load block rejection addresses: {e:?}.",);
                return;
            }
        };
        let signature_weight = self.signer_weights.get(signer_address).unwrap_or(&0);
        let total_reject_weight =
            self.compute_signature_signing_weight(rejection_addrs.iter().map(|(addr, _)| addr));
        let total_weight = self.compute_signature_total_weight();

        let min_weight = NakamotoBlockHeader::compute_voting_weight_threshold(total_weight)
            .unwrap_or_else(|_| {
                panic!("{self}: Failed to compute threshold weight for {total_weight}")
            });
        if total_reject_weight.saturating_add(min_weight) <= total_weight {
            // Not enough rejection signatures to make a decision
            info!("{self}: Have not yet received enough block rejections to reach a consensus decision on this block";
                "signer_signature_hash" => %block_hash,
                "signature_weight" => signature_weight,
                "consensus_hash" => %block_info.block.header.consensus_hash,
                "block_height" => block_info.block.header.chain_length,
                "total_weight_rejected" => total_reject_weight,

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
