### Title
Fee-on-transfer repayments block instant-withdrawal funding - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`getInstantWithdrawFunds` performs two consecutive nominal-amount transfers: borrower → `IdleCDOEpochVariant`, then `IdleCDOEpochVariant` → `IdleCreditVault`. With a fee-on-transfer underlying token, the CDO receives less than `_instantWithdraws`, so the second transfer has insufficient balance and the funding transaction reverts. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
During the running-epoch phase, an owner or manager calls `getInstantWithdrawFunds` after `instantWithdrawDeadline`. [4](#0-3)  The function first pulls `pendingInstantWithdraws` from the borrower into the CDO through `getFundsFromBorrower`. [1](#0-0)  It then calls `collectInstantWithdrawFunds` for the same gross amount. [2](#0-1)  `collectInstantWithdrawFunds` reduces `pendingInstantWithdraws` and pulls the same amount from the CDO into the credit vault. [3](#0-2) 

If the token charges a transfer fee `F`, the CDO receives only `_instantWithdraws - F` from the borrower. Unless it already holds at least `F` unrelated underlying tokens, the CDO cannot transfer the full `_instantWithdraws` to the credit vault, so the operation reverts before `allowInstantWithdraw` is enabled. [2](#0-1) [3](#0-2) 

### Impact Explanation
Pending instant-withdrawal receipts cannot be funded even though the borrower supplied the requested nominal amount. The denial lasts until someone manually supplies at least the missing transfer fee to the CDO or governance changes the asset/flow. The quantifiable shortfall is `F = _instantWithdraws - actualReceived`, and every funding attempt remains blocked while the CDO balance is below `_instantWithdraws`. [3](#0-2) [2](#0-1) 

### Likelihood Explanation
The issue requires a fee-on-transfer token to be configured as the vault underlying. The initializer accepts an arbitrary ERC20-compatible token and does not reject or normalize fee-on-transfer behavior. [5](#0-4)  Core deposits avoid this class of accounting error by minting from the received-balance delta, but the instant-withdrawal repayment path does not apply the same principle to its second transfer. [6](#0-5) [3](#0-2) 

### Recommendation
Measure the amount actually received from the borrower and collect only that amount, or have `getFundsFromBorrower` return `balanceAfter - balanceBefore` and pass that value to `collectInstantWithdrawFunds`. [1](#0-0) [2](#0-1)  Alternatively, make the borrower transfer directly to `IdleCreditVault`, eliminating the intermediate CDO transfer and its second fee. [3](#0-2) 

### Proof of Concept
A reproducible Foundry test should initialize an `IdleCDOEpochVariant`/`IdleCreditVault` pair with an ERC20 implementation whose `transferFrom` burns a fee `F`, create one instant-withdrawal request for `X`, advance past `instantWithdrawDeadline`, fund and approve the borrower for `X`, then call `getInstantWithdrawFunds`. The borrower→CDO transfer delivers `X-F`; the subsequent CDO→vault pull requests `X` and reverts because the CDO holds only `X-F`. [2](#0-1) [3](#0-2)
