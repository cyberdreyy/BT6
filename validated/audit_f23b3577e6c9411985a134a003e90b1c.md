### Title
Rejection-triggered global consensus (`GloballyRejected`) does not stop a stale accept-tally from broadcasting a locally-conflicting signature bundle — ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_rejection` explicitly checks `block_info.has_reached_consensus()` before continuing to tally rejection weight, refusing to act once the block already reached a terminal state. `store_and_process_block_signature`, the accept-side counterpart, contains no equivalent guard: it only short-circuits on `block_info.signed_group.is_some()`, and if `mark_locally_accepted` fails because the block is already `GloballyRejected`, the function swallows the error and falls through to `broadcast_signed_block` unconditionally.

### Finding Description
Compare the two "reached-consensus" handlers in `stacks-signer/src/v0/signer.rs`:

`store_and_process_block_rejection` (lines 2267–2369):
```rust
if block_info.has_reached_consensus() {
    // Checking the rejection signatures is pointless. We have already reached consensus on this block.
    return;
}
``` [1](#0-0) 

`store_and_process_block_signature` (lines 2442–2538) has no such check. It only bails if `signed_group.is_some()`:
```rust
if block_info.signed_group.is_some() {
    // We have already processed this block to the accepted state.
    return;
}
``` [2](#0-1) 

and after tallying weight and reaching the threshold, it does:
```rust
if let Err(e) = block_info.mark_locally_accepted(true) {
    if !block_info.has_reached_consensus() {
        warn!("{self}: Failed to mark block as locally accepted: {e:?}");
    }
}
let _ = self.signer_db.insert_block(block_info).map_err(|e| { ... });
self.broadcast_signed_block(stacks_client, block_info.block.clone(), &addrs_to_sigs);
``` [3](#0-2) 

`mark_locally_accepted` calls `move_to`, whose transition table (`BlockInfo::check_state`, `signerdb.rs`) forbids `GloballyRejected -> LocallyAccepted`:
```rust
BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
    prev_state,
    BlockState::GloballyRejected | BlockState::GloballyAccepted
),
``` [4](#0-3) 

So if this signer already saw enough rejection weight and called `mark_globally_rejected` on `block_info` (via `store_and_process_block_rejection`), a subsequent `BlockAccepted` message that arrives late over gossip (stragglers, retransmits, delayed peer state) still passes through `store_and_process_block_signature`, tallies toward `total_signature_weight`, hits `min_weight`, fails the `move_to` state transition (swallowed, since `has_reached_consensus()` is now true so the warning is even suppressed), and — regardless — the code proceeds past that failed call straight into `broadcast_signed_block`, pushing the block (and the signature bundle) to this signer's own node via `handle_post_block`.

This breaks the intended equality documented in `docs/signer-flows.md`: "Rejections tally toward the blocking minority (>30% weight), which makes the 70% unreachable and finalizes the block as globally rejected" [5](#0-4)  — the design assumes a block cannot be both globally rejected and later pushed as accepted by the same signer instance, but the accept path lacks the terminal-state check its sibling rejection path has.

### Impact Explanation
This is a "rejection recounted as an accept" class defect: a block this signer already treated as dead (`GloballyRejected`, having tallied >30% rejecting weight) can still be broadcast to the node as if accepted, because the accept-tally path does not gate on `has_reached_consensus()` before calling `broadcast_signed_block`. If the node accepts the pushed block (its own independent validation may or may not catch this), a conflicting/rejected block could still land on-chain from a state the signer software itself considered dead — undermining the safety property that a globally-rejected block cannot resurface via straggling accept messages. At minimum it is a correctness/safety violation of the local state machine's terminal-state guarantee that mirrors the write/read asymmetry pattern in the source advisory (one code path enforces a guard, the sibling path does not).

### Likelihood Explanation
No majority collusion or forged keys are required beyond the normal signer-set message flow already assumed safe by design (only gossip/timing is needed): a straggling, legitimately-signed `BlockAccepted` message arriving after this signer has already locally reached `GloballyRejected` for the same `signer_signature_hash` is a routine occurrence under normal network jitter or message replay (`add_pending_block_signature_response`/StackerDB replay paths already anticipate delayed messages), making the race practically reachable rather than purely theoretical.

### Recommendation
Add the same `block_info.has_reached_consensus()` (or equivalent terminal-state) guard at the top of `store_and_process_block_signature` that already exists in `store_and_process_block_rejection`, returning early before tallying weight or calling `broadcast_signed_block` once the block has reached `GloballyRejected` (or `GloballyAccepted`).

### Proof of Concept
1. Signer S receives `BlockRejection` messages from peers totaling >30% weight for block B (via `handle_block_response` → `handle_block_rejection` → `store_and_process_block_rejection`), which calls `mark_globally_rejected()` on `block_info` for B, per `stacks-signer/src/v0/signer.rs:2335`.
2. Due to normal network delay/replay, S subsequently receives a late `BlockAccepted` message from a peer for the same B (a message that was in flight before the rejection threshold was reached, or replayed via `add_pending_block_signature_response`).
3. `handle_block_signature` → `store_and_process_block_signature` runs: `block_info.signed_group` is still `None` (short-circuit check at line 2468 doesn't trigger), so weight is tallied; if the previously-collected accept weight (plus this one) crosses `min_weight`, execution proceeds to `mark_locally_accepted(true)`, which fails the state-machine transition silently (`GloballyRejected -> LocallyAccepted` disallowed by `check_state`), but the function does not return on that error.
4. Execution falls through to `self.broadcast_signed_block(...)`, pushing block B — a block this same signer instance had already globally rejected — to the stacks-node as if it were accepted.
