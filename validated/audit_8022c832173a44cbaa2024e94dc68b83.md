### Title
Stale per-epoch withdraw receipt is paid at par after a later loss-adjusted funding, draining the funded-claim pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The use-after-free analog is a dangling receipt ledger entry: `withdrawsRequestsByEpoch[user][epoch]` entries persist across epochs, but `_claimLossAdjustedWithdrawRequest` / `_clearWithdrawClaimForEpoch` only clear the entry for `lastWithdrawRequest[_user]` (a single-epoch pointer). When a user holds pending receipts in two different epochs and the later epoch is funded at a loss via `collectWithdrawFunds`, the loss haircut is computed over the aggregate `pendingWithdraws` (both epochs), yet only the newest epoch's per-user entry is cleared and haircut. The older entry remains in `withdrawsRequests[user]`, `lastWithdrawRequest` is reset to 0, and `_claimFundedWithdrawRequest` then pays the older receipt at par — even though the funding it draws on was only sized at `recoveryPrice` of the total basis.

### Finding Description
Relevant code in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` records `withdrawsRequestsByEpoch[user][epochNumber]`, the aggregate `withdrawsRequests[user]`, and overwrites `lastWithdrawRequest[user] = currentEpoch` (lines 282–293). The guard at lines 261–271 only blocks a new request when the *previous* `lastWithdrawRequest` epoch carries a non-zero `lossRecoveryPriceByEpoch` — a normally-funded pending epoch does not block a second request.
- `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingWithdraws` over the *aggregate* `pendingWithdraws`, stores it only under `lossRecoveryPriceByEpoch[epochNumber]`, and zeroes `pendingWithdraws` (lines 411–426). The haircut therefore economically covers all pending receipts, but only the current epoch is tagged.
- On claim, `claimWithdrawRequest` runs `_claimLossAdjustedWithdrawRequest` first, which looks up `lossEpoch = lastWithdrawRequest[user]` and calls `_clearWithdrawClaimForEpoch(user, lossEpoch, false)` — clearing only `withdrawsRequestsByEpoch[user][lossEpoch]` and subtracting only that epoch's `normalAmount` from `withdrawsRequests[user]`, then resetting `lastWithdrawRequest[user] = 0` (lines 789–801, 811–837).
- `_claimFundedWithdrawRequest` then checks `epochNumber <= lastWithdrawRequest[user]` — now 0, so it passes — and pays the remaining `withdrawsRequests[user]` (the older epoch's receipt) at full par via `_transferFundedClaim` (lines 319–350).

Broken invariant: one receipt one payout at the funded rate. The strategy funded `(E_old + E_new) * lossRecoveryPrice` but the user claims `E_new * lossRecoveryPrice + E_old * 1.0`, extracting `E_old * (1 - lossRecoveryPrice)` more than their pro-rata share, directly from underlying that belongs to other funded claimants.

### Impact Explanation
Direct theft of funded withdrawal proceeds: any unprivileged KYC-passing lender can sandwich two withdraw requests across an epoch boundary and, if the borrower short-funds a subsequent `stopEpochWithDuration(_lossAmount)`, redeem their older receipt at par from a pool funded only at `recoveryPrice`. The shortfall is socialized onto every other claimant who withdraws later, up to `E_old * (1 - lossRecoveryPrice)` per attacking user — bounded only by the attacker's deposited principal and repeatable across multiple attacking accounts.

### Likelihood Explanation
Requires a loss event on `stopEpochWithDuration` while the attacker holds receipts in two epochs — an honest-manager/borrower sequence, so the attacker only needs to pre-position two requests, which is always possible during consecutive buffer phases. No privileged collusion, oracle manipulation, or default is needed; a routine partial short-fund triggers it. The guards (`lossRecoveryPrice == 0` revert, the two-request guard, `_transferFundedClaim` reserve check) do not cover cross-epoch staleness.

### Recommendation
Track loss-adjusted basis per epoch rather than per "latest" marker: e.g., iterate `withdrawsRequestsByEpoch[user]` entries that fall in epochs with a non-zero `lossRecoveryPriceByEpoch` and clear each at its own price, or store a per-user list/bitmap of request epochs and refuse `_claimFundedWithdrawRequest` until all loss-tagged entries are cleared. Alternatively, mark *every* pending epoch covered by an aggregate `collectWithdrawFunds` haircut (e.g., a `lossRecoveryPrice` floor applied to all receipts created before that `epochNumber`) so no receipt funded at a discount can later claim at par.

### Proof of Concept
Fork test in `test/foundry/IdleCreditVault.t.sol` harness (uses existing helpers `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `_depositWithUser`):

```solidity
function testStaleEpochReceiptPaidAtParAfterLossFunding() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    uint256 amountWei = 10_000 * ONE_SCALE;
    IdleCreditVault vault = IdleCreditVault(address(strategy));

    uint256 mintedAA = idleCDO.depositAA(amountWei);       // attacker = this contract
    _depositWithUser(makeAddr('victim'), amountWei, false); // honest claimant

    // Epoch 0 runs and stops; attacker requests withdraw in buffer (epoch 0)
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    uint256 reqE0 = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));

    // Epoch 1 runs and stops normally (reqE0 funded at par but NOT claimed)
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Attacker requests again during epoch-2 buffer -> marker moves to epoch 2
    uint256 reqE2 = cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));
    // victim also requests so pendingWithdraws aggregates both
    vm.prank(makeAddr('victim'));
    // (victim requests via cdoEpoch.requestWithdraw as in existing tests)

    // Epoch 2 stops with a loss: manager calls stopEpochWithDuration(_lossAmount)
    // so collectWithdrawFunds funds only pendingWithdraws * recoveryPrice
    _startEpochAndCheckPrices(2);
    // borrower short-funds: loss of, say, 20% of pending basis
    // _stopEpochWithLoss(...) helper that drives stopEpochWithDuration(_lossAmount)

    // Attacker claims:
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 claimed = IERC20Detailed(defaultUnderlying).balanceOf(address(this)) - balPre;

    uint256 recoveryPrice = vault.lossRecoveryPriceByEpoch(vault.epochNumber());
    // Correct payout: (reqE0 + reqE2) * recoveryPrice / RECOVERY_FULL
    // Actual payout:  reqE2 * recoveryPrice / RECOVERY_FULL + reqE0 (par)
    assertApproxEqAbs(claimed,
        reqE2 * recoveryPrice / 1e18 + reqE0,  // par on stale E0 receipt
        2,
        'stale epoch receipt claimed at par after loss funding');
    // Sum of all claims exceeds funded underlyings -> last claimant reverts/underpays
}
```

Key assertions: `vault.withdrawsRequestsByEpoch(attacker, epoch0)` was non-zero after the loss claim path ran, `lastWithdrawRequest[attacker]` was reset to 0 by `_clearWithdrawClaimForEpoch`, and `claimWithdrawRequest` paid `reqE0` at full price while the strategy only received `recoveryPrice`-discounted funding for it. Note: exact helper names for the loss-funding path (`stopEpochWithDuration` invocation and `previewLossAdjustedWithdrawFunds`) should be wired to the existing `testClosePoolWithDuration…` / loss-management helpers in the same test file; the exploit requires the partial-funding branch of `collectWithdrawFunds`, not a full fund or full default.
