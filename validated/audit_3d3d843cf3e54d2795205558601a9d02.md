## Analog Found

### Title
Signer treats an unreachable node as "tenure unconfirmed" and signs through an unresolved same-tenure conflict, defeating the equivocation guard - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_pre_commit` guards against a signer double-signing two blocks at the same height in the same tenure by querying the node's canonical tip before signing. When that query fails (RPC error, timeout, node restart), the code does not fail closed like every sibling check in the same function — it optimistically treats the tenure as "unconfirmed" and falls through to sign the conflicting block anyway, exactly the "assume success, no revert on failure" pattern from the external report.

### Finding Description
In `handle_block_pre_commit`, once the signer has crossed the pre-commit weight threshold for a block, it checks whether any signed/accepted conflict in the *same tenure* at the same or higher height still stands: [1](#0-0) 

If `get_tenure_tip` returns `Err` (node unreachable, timeout, etc.), the `match` arm only logs a warning ("Treating the tenure as unconfirmed") and does **not** return — execution falls through past the check, past the `if !conflicts.is_empty() { info!(...) }` bookkeeping, straight into `mark_locally_accepted` and signature creation: [2](#0-1) 

This is the opposite fail-safe direction taken by every other conflict check in the same code path. The cross-tenure conflict resolver `conflict_still_blocks` explicitly treats node errors as "keep blocking" (fail-closed): [3](#0-2) 

and the sortition-canonicality check inside the same function does the same on error ("Leaving the conflict in place"): [4](#0-3) 

The design rationale documented for the rest of the guard is explicit: "Whenever the node cannot be asked, the conflict keeps blocking: that only delays the replacement until the signature goes stale, whereas wrongly signing cannot be taken back" — yet the own-tenure branch is carved out as the one place where an unreachable node instead releases the signature: [5](#0-4) 

This mirrors the reported bug class precisely: the operation whose success cannot be confirmed (querying the node for the tenure's real tip) is optimistically assumed to have "not happened yet" rather than being treated as an unknown/failure state that should block the sensitive action (signing), so the guarded resource (the equivocation-guard invariant — signer never double-signs same-tenure siblings) is not protected when the dependency call fails.

### Impact Explanation
This breaks the one-signature-per-tenure-height equivocation guard that the whole `handle_block_pre_commit` conflict-resolution machinery in section 5 of `docs/signer-flows.md` exists to enforce. A single signer whose stacks-node RPC briefly errors (restart, timeout, transient network blip — not a Byzantine event, not requiring a majority or another signer's key) will sign a second, conflicting block at the same height in the same tenure whose first sibling it already pre-committed/signed. If multiple signers hit this transient condition around the same reorg-timing window, both siblings' signature sets can reach the 70% threshold, producing two validly-signed blocks at the same height/tenure — a signer set equivocation. This matches the "Critical: rejection/valid path producing a conflicting block signature" / "High: losing the equivocation guard" categories in scope.

### Likelihood Explanation
The trigger is purely an RPC failure to the signer's own paired stacks-node (`get_tenure_tip`) at the exact moment the pre-commit weight threshold is crossed while a same-tenure conflict exists — a condition reachable by any single miner proposing two tenure-start/sibling blocks in quick succession (which the codebase's own tests show is a realistic, already-anticipated race, see `async_sibling_validation` tests) combined with ordinary node flakiness. No majority of signers or possession of another signer's key is required; only a one-slot miner producing competing proposals plus a transient RPC error on this signer's node.

### Recommendation
Make the own-tenure conflict check fail closed like its siblings in the same function: on `Err` from `get_tenure_tip`, refuse to sign for now (return early, as `conflict_still_blocks` and the sortition-canonicality branch do) rather than treating the tenure as "unconfirmed" and proceeding to sign. This only delays a legitimate replacement until the conflicting signature goes stale, which is the same tradeoff already accepted everywhere else in this guard.

### Proof of Concept
1. Signer S has pre-committed/signed block A in tenure T at height H (`conflicts` will contain A for any later same-height proposal in T).
2. A second block B (sibling of A) at height H in tenure T is proposed and reaches the pre-commit weight threshold on signer S.
3. `handle_block_pre_commit` enters the branch at `stacks-signer/src/v0/signer.rs:1432-1435` since `conflict.consensus_hash == block_info.block.header.consensus_hash` and no reorg permit exists.
4. S's paired stacks-node RPC call `get_tenure_tip` fails (e.g., node briefly restarting) — hits the `Err(e)` arm at line 1449.
5. Execution falls through the `if` block, skips the `return`, and continues to `mark_locally_accepted` / `create_block_acceptance` / `handle_block_signature` at lines 1467-1478, producing a valid signature over sibling block B despite S having already signed sibling A at the same height in the same tenure.
