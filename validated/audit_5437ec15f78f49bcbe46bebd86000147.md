## Title
Sentinel value `0` for "not yet notified" collides with genuine slot 0 in `blockSubscribe` catch-up logic, silently skipping missed block notifications - (File: `rpc/src/rpc_subscriptions.rs`)

### Summary
`ConcentratedLiquidityPoolManager.addIncentive` failed to verify that `incentive.secondsClaimed` was still at its "not started" value (zero) before letting the incentive begin accruing, allowing pre-existing accumulated state to corrupt subsequent reward math. The Agave RPC pubsub block-notification path has the same class of defect: it uses the bare value `0` in `SubscriptionInfo.last_notified_slot` as a sentinel meaning "this subscription has not been notified yet," but `0` is also a legitimate, reachable slot number. The "has it started yet" check is therefore ambiguous, and when it evaluates true for a subscription that has genuinely already progressed to slot 0, the code incorrectly treats it as brand-new and skips the intended catch-up loop.

### Finding Description
In `RpcSubscriptions::notify_watchers`, the `SubscriptionParams::Block` handling reads and mutates the per-subscription cursor `last_notified_slot`: [1](#0-0) 

```rust
let mut w_last_unnotified_slot =
    subscription.last_notified_slot.write().unwrap();
// would mean it's the first notification for this subscription connection
if *w_last_unnotified_slot == 0 {
    *w_last_unnotified_slot = slot;
}
let mut slots_to_notify: Vec<_> =
    (*w_last_unnotified_slot..slot).collect();
```

The comment states the intent plainly: `*w_last_unnotified_slot == 0` is being used as a proxy for "no notification has happened yet for this subscription," at which point the code jumps the cursor directly to the current `slot` (skipping the catch-up range `slots_to_notify`) instead of walking forward from the subscription's actual starting point.

This is exactly analogous to the reported bug class: rather than verifying an explicit "not started" flag/invariant, the code overloads a legitimate data value (slot `0`, or `secondsClaimed == 0` in the original report) as the "unstarted" indicator. `last_notified_slot` is seeded at subscribe time by `initial_last_notified_slot(...).unwrap_or(0)`, and `.unwrap_or(0)` is reached whenever the initial computation legitimately returns `None`/`0` — e.g., early in a cluster's life (slot 0 itself), or for subscriptions whose commitment-slot lookup momentarily yields no value. In all of these cases, the resulting `last_notified_slot == 0` is indistinguishable from the "never notified" sentinel, so the very next `notify_watchers` pass for that subscription incorrectly assumes it is pristine and skips forward to `slot` rather than notifying the client for the actual missed range.

### Impact Explanation
For an unprivileged client using the JSON-RPC pubsub `blockSubscribe` notification path, this causes the server to silently drop legitimate block notifications the client should have received (wrong/omitted data returned for a live subscription), because the cursor jumps straight to the newest slot instead of walking the true unnotified range. This falls in the "wrong-slot/fork/account data returned" category of impact: the RPC pubsub client is misinformed about which blocks it has and hasn't seen, which can cause downstream consumers (indexers, exchanges, bots) to believe they have complete block coverage when gaps exist.

### Likelihood Explanation
The condition is reachable purely through the public pubsub `blockSubscribe` request, requires no special privilege, and depends only on when a subscription's `last_notified_slot` cursor legitimately becomes `0` (at genesis, or when the commitment-derived initial slot resolves to `0`/`None`). No fork choice, consensus mutation, or crash is involved; this is a data-correctness defect in a read/notification path, not a safety-critical validator process failure, so likelihood of the triggering condition is credible but the severity is bounded to notification correctness rather than crash/DoS/consensus impact.

### Recommendation
Replace the overloaded `0` sentinel with an explicit `Option<Slot>` (e.g., `last_notified_slot: RwLock<Option<Slot>>`, initialized to `None` at subscribe time) so "not yet notified" is represented unambiguously and does not collide with the valid slot value `0`. Update all call sites (`check_commitment_and_notify`, the `Block` handling arm, and `SubscriptionInfo`/`SubscriptionsTracker` construction) accordingly.

### Proof of Concept
Conceptual reproduction (not executed):
1. Start a node at genesis (or otherwise arrange for a subscription's `initial_last_notified_slot(...)` to resolve to `0`).
2. Issue `blockSubscribe` for that subscription; `SubscriptionInfo.last_notified_slot` is seeded to `0` via `.unwrap_or(0)`.
3. Advance several slots without any intervening notification round for this subscription (e.g., transient absence in a commitment bucket for a round), then trigger `notify_watchers` for slot `N`.
4. Because `*w_last_unnotified_slot == 0`, the code executes `*w_last_unnotified_slot = slot` (i.e., `N`), producing `slots_to_notify = (N..N)` — empty — instead of the intended `(0..N)` (or subscription-start..N) catch-up range.
5. The client silently never receives block notifications for the skipped slots, even though its subscription was live and its cursor was genuinely at slot 0, not "unstarted." [1](#0-0)
