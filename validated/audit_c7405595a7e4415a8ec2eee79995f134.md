Based on the investigation, I found a genuine analog in Agave's cost-accounting model for precompile signature verification, which mirrors the Tomcat CVE's core bug class (expensive per-request work performed disproportionately to its accounted resource cost, driven entirely by unprivileged/untrusted input).

### Title
Uncontrolled CPU Resource Consumption via Batched Precompile Signature Verification (secp256k1/ed25519) - (File: precompiles/src/secp256k1.rs, precompiles/src/ed25519.rs, program-runtime/src/invoke_context.rs)

### Summary
A single unprivileged transaction can request a large number of `secp256k1`/`ed25519` precompile signature verifications (up to 255 per instruction, up to `MAX_INSTRUCTION_TRACE_LENGTH` = 64 instructions per transaction), and this verification work is executed unconditionally by `InvokeContext::process_message` outside of the compute-unit metering loop that gates normal program execution, `program-runtime/src/invoke_context.rs:511-524`. The only limiter is the pre-computed, count-based cost estimate used for block/account cost-limit bookkeeping in `cost-model/src/block_cost_limits.rs:9-18`, not an enforced real-time compute budget on the precompile itself.

### Finding Description
`process_message` dispatches precompile instructions to `process_precompile`, `program-runtime/src/invoke_context.rs:616-631`, which invokes the actual cryptographic verification (`libsecp256k1::recover`, `ed25519_dalek` `verify_strict`) via `precompiles::verify_if_precompile`, `precompiles/src/lib.rs:98-119`. Unlike `process_instruction` (used for BPF/native programs), `process_precompile` never decrements a compute meter — the `compute_units_consumed` accumulator seen in `process_message` (`program-runtime/src/invoke_context.rs:514,527`) is never touched for precompile branches.

The `secp256k1` and `ed25519` verifiers accept up to 255 signatures per instruction (`count = data[0] as usize`), each requiring one ECDSA public-key recovery or Ed25519 strict verification, `precompiles/src/secp256k1.rs:31,44-100`, `precompiles/src/ed25519.rs:19,30-77`. (Notably, `secp256r1` was hardened with an explicit `num_signatures > 8` cap, `precompiles/src/secp256r1.rs:27-32`, but `secp256k1`/`ed25519` retain no equivalent per-instruction cap beyond the `u8` count byte and the 10 KiB `MAX_INSTRUCTION_DATA_LEN`.)

The cost model only *estimates* the CPU cost of these operations for scheduling/block-packing purposes using fixed per-signature constants (`SECP256K1_VERIFY_COST = 6690`, `ED25519_VERIFY_STRICT_COST = 2400`), `cost-model/src/block_cost_limits.rs:9-16`, and `CostModel::get_signature_cost`, `cost-model/src/cost_model.rs:129-151`. This estimate is checked against `MAX_WRITABLE_ACCOUNT_UNITS` (24,000,000) and `MAX_BLOCK_UNITS` (60,000,000) in `cost_tracker.rs` before scheduling in the banking stage, but this is a *leader-side admission heuristic*, not an enforced execution-time budget — the actual verification loop runs to completion once the instruction is dispatched, regardless of whether real work matches the nominal accounting.

### Impact Explanation
A single transaction can be constructed with dozens of `secp256k1`/`ed25519` precompile instructions each declaring up to 255 signatures, consuming a large fraction (up to the full `MAX_WRITABLE_ACCOUNT_UNITS`/`MAX_BLOCK_UNITS` budget) of a block purely in expensive elliptic-curve recovery/verification work, while performing no other useful state transition. Because this work executes unconditionally in every validator that replays the block (and potentially before rejection in leader admission paths), an attacker can force substantial, real wall-clock CPU consumption (hundreds of milliseconds per transaction) for a cost bounded only by ordinary priority fees on compute units — the same "cheap request, expensive processing" asymmetry underlying the Tomcat HTTP/2 CVE. At scale (multiple such transactions packed into consecutive slots), this could degrade leader block-production timing and validator replay throughput, a leader-side cost/liveness degradation.

### Likelihood Explanation
Constructing such a transaction requires no special privilege — any signer can submit valid-looking `secp256k1`/`ed25519` precompile instructions with a large declared signature count and syntactically well-formed (but not necessarily cryptographically valid, since verification failure still costs the CPU cycles before erroring) offsets. The instruction/signature-count limits (255/instr, 64 instr/tx, 10 KiB/instr data) are generous enough to construct thousands of verification operations in one transaction.

### Recommendation
Meter precompile verification against the transaction's actual compute-unit budget (matching the cost-model's per-signature CU constants) rather than exempting it from the compute meter in `process_precompile`, and/or impose an explicit per-instruction signature cap for `secp256k1`/`ed25519` similar to the existing `secp256r1` cap (`num_signatures > 8`) to bound worst-case CPU cost per instruction regardless of nominal cost-model accounting.

### Proof of Concept
Construct one transaction containing the maximum number of top-level instructions permitted (`MAX_INSTRUCTION_TRACE_LENGTH` = 64, `transaction-context/src/lib.rs:26`), each invoking the `secp256k1_program` (or `ed25519_program`) with `data[0] = 255` and syntactically valid (but arbitrary/garbage) signature offsets sized to stay within `MAX_INSTRUCTION_DATA_LEN` (10 KiB). Submit via normal RPC; `Bank::verify_transaction` only checks instruction count and size (`runtime/src/bank.rs:5551-5556`), not aggregate precompile signature count, before signature/message sanitization succeeds and the transaction is scheduled for execution and CPU-bound precompile verification.     /// Returns signature details and the total signature cost
    fn get_signature_cost(transaction: &impl TransactionMeta) -> u64 {
        let signatures_count_detail = transaction.signature_details();

        signatures_count_detail
            .num_transaction_signatures()
            .saturating_mul(SIGNATURE_COST)
            .saturating_add(
                signatures_count_detail
                    .num_secp256k1_instruction_signatures()
                    .saturating_mul(SECP256K1_VERIFY_COST),
            )
            .saturating_add(
                signatures_count_detail
                    .num_ed25519_instruction_signatures()
                    .saturating_mul(ED25519_VERIFY_STRICT_COST),
            )
            .saturating_add(
                signatures_count_detail
                    .num_secp256r1_instruction_signatures()
                    .saturating_mul(SECP256R1_VERIFY_COST),
            )
    }
