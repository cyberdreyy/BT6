### Title
Withdraw requests made after `startEpoch` are not added to the ProgrammableBorrower liquidity reserve, so reserved lender funds can be drawn and the stop-epoch pull defaults the pool - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary

CVE-2018-19278 is a "buffer sized for the compressed length, filled with the expanded length" bug: a capacity check uses a pre-expansion size while the write uses the real size. The direct analog here is the borrow-liquidity reserve in `ProgrammableBorrower`. The reserve (`epochPendingWithdraws`) is snapshotted once in `onStartEpoch` (`_pendingWithdraws` at that moment), but the actual epoch-end obligation (`IdleCreditVault.pendingWithdraws`) grows every time a lender calls `requestWithdraw` during the epoch. `availableToBorrow()` only protects the stale snapshot, so liquidity owed to new withdraw receipts is counted as free capital and can be drawn by the borrower. At `stopEpoch`, `onStopEpoch` cannot source the expanded obligation, `transferFrom` fails, and the CDO takes the default path, haircutting all lenders.

### Finding Description

In `onStartEpoch` the borrower contract reserves exactly the pending-withdraw amount passed by the CDO:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:201-205
function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    epochPendingWithdraws = _pendingWithdraws;
```

`availableToBorrow()` then treats `totalAssets - epochPendingWithdraws` as drawable:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:350-355
uint256 totalAssets = underlyingToken.balanceOf(address(this)) + _currentVaultAssets();
uint256 reserved = epochPendingWithdraws;
return totalAssets <= reserved ? 0 : totalAssets - reserved;
```

Meanwhile, `IdleCreditVault.requestWithdraw` increases the real obligation with no mechanism to update the borrower's reserve — there is no notify hook from `requestWithdraw` to `ProgrammableBorrower`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:277-294
if (!isClosed) {
  pendingWithdraws += _amount;
}
...
withdrawsRequests[_user] += _amount;
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
```

`requestWithdraw` in `IdleCDOEpochVariant` only checks `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and KYC; nothing blocks it in programmable mode (`isProgrammableBorrower` only gates `depositDuringEpoch`). At `stopEpoch`, the CDO reads `totalInterestDueNow()` and calls `onStopEpoch(_amountRequired, ...)` which must free `_amountRequired` (pending withdraws + funded amounts). If the borrower legitimately drew funds that include post-snapshot withdraw receipts — which `availableToBorrow()` explicitly permits — the vault cannot cover the shortfall, `onStopEpoch` returns `true` early (`shortfall > _currentVaultAssets()`), and the subsequent `transferFrom` into the CDO fails, forcing the default/emergency path.

### Impact Explanation

Direct insolvency/loss socialization: withdraw receipts requested mid-epoch become unpayable, and the default path (`finalizeDefault`/`defaultRecoveryPrice`) haircuts every lender's claim by the shortfall. The loss equals the mid-epoch requested amount that was drained beyond the stale reserve, i.e. up to `pendingWithdraws - epochPendingWithdraws` of principal, plus any funded-claim liquidity gap. This breaks the "one receipt one payout" invariant: receipts minted during the epoch are backed by a reserve sized for receipts that existed at epoch start only.

### Likelihood Explanation

Requires only: a programmable-borrower pool, an epoch in `running` phase, a KYC-passing lender (in attacker set) calling `requestWithdraw` after `startEpoch`, and the honest borrower having drawn the falsely-free liquidity via `borrow()` — a routine, sanctioned action for the borrower, not adversarial behavior. No privileged misbehavior, oracle manipulation, or external vault failure is needed. The trigger is a pure sequencing/sequence-around-honest-calls scenario explicitly allowed by the rules.

### Recommendation

Keep the borrow reserve synchronized with the live obligation: either have `IdleCDOEpochVariant.requestWithdraw` call a `ProgrammableBorrower` hook that does `epochPendingWithdraws += _amount` (and decrease it when receipts are funded/claimed), or have `availableToBorrow()` pull `IdleCreditVault(idleCDO.strategy()).pendingWithdraws()` live instead of using a stale snapshot.

### Proof of Concept

Foundry fork PoC sketch (built on `test/foundry/IdleCreditVault.t.sol` harness with a programmable-borrower strategy):

```solidity
function testMidEpochWithdrawBypassesBorrowerReserve() external {
    // Setup: programmable borrower pool, vault V, borrower B (honest)
    // user (KYC'd) deposits 100_000 underlying into AA
    uint256 amount = 100_000 * ONE_SCALE;
    uint256 trancheAmt = idleCDO.depositAA(amount);

    // Epoch 1 starts. onStartEpoch snapshots epochPendingWithdraws = 0.
    vm.prank(manager);
    cdoEpoch.startEpoch();
    assertEq(borrowerContract.epochPendingWithdraws(), 0);

    // Honest borrower draws the full "available" amount — includes
    // liquidity that will soon be owed to withdraw receipts.
    vm.prank(borrower);
    borrowerContract.borrow(0); // draws everything; reserve is 0

    // Attacker (ordinary KYC'd lender) requests withdrawal mid-epoch.
    // IdleCreditVault.pendingWithdraws grows; epochPendingWithdraws stays 0.
    cdoEpoch.requestWithdraw(trancheAmt, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).pendingWithdraws(), 0);

    // Borrower has NOT yet repaid (loan still within terms — honest behavior).
    // Warp past epoch end and stop the epoch.
    deal(defaultUnderlying, borrower, /* only interest, not principal */);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // borrower pulls shortfall; transferFrom fails -> default path

    // The pool is defaulted; the withdraw receipt is haircut via
    // defaultRecoveryPrice instead of paid at par.
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 claimed = underlying.balanceOf(address(this)) - balPre;
    assertLt(claimed, amount, "receipt haircut: reserve was sized at stale snapshot");
}
```

Expected result: `stopEpoch` cannot source the expanded `pendingWithdraws`, the default path engages, and the mid-epoch withdraw receipt (plus other lenders) is paid below par despite the borrower never having been authorized to draw those funds — because the authorization check used a compressed (epoch-start) size against an expanded (current) obligation.

Uncertainty note: I could not fully trace `stopEpoch`'s exact `_amountRequired` composition (funded vs. `pendingWithdraws` legs) and the revert path in `IdleCDOEpochVariant.stopEpoch` within the available iterations; if `stopEpoch` pulls only interest and lets receipts claim lazily, the impact degrades to delayed claims rather than haircut — but the stale-reserve mismatch itself is confirmed by the code above.
