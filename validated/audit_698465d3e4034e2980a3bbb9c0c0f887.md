# Reward Sniping via Epoch-Boundary Deposits in `StakingContract` - (File: staking-pool/src/internal.rs)

## Summary
The `staking-pool` contract distributes an entire epoch's accumulated staking reward to whichever accounts hold "stake" shares at the moment the epoch boundary is first observed, rather than accruing rewards continuously over the period the funds were actually staked. Since epoch height transitions are deterministic and publicly predictable, an unprivileged actor can deposit and stake immediately before an epoch switch, be present for only a few blocks, and still receive a full pro-rata share of the entire epoch's reward — diluting the return of delegators who were staked for the whole epoch.

## Finding Description
`ping`, `deposit`, `deposit_and_stake`, `stake`, `stake_all`, `unstake`, and `unstake_all` all call `internal_ping` first [1](#0-0) . `internal_ping` only does work when `env::epoch_height()` differs from the stored `last_epoch_height`; when it fires, it computes `total_reward` as the delta between the current total account balance (locked + unlocked) and `last_total_balance`, and then mutates `total_staked_balance`/`total_stake_shares`/owner shares based on that lump sum [2](#0-1) .

Crucially, reward attribution is based purely on **which shares exist at the moment the epoch switch is detected**, not on how long those shares have been outstanding during the epoch that just elapsed:

- An attacker calls `deposit_and_stake` in the last block(s) of epoch N. At this point `internal_ping` is a no-op (epoch hasn't changed yet), so the attacker's deposit is converted into "stake" shares at the pre-reward price with no waiting period.
- As soon as epoch N+1 begins, the next state-changing call (from anyone, including the attacker) triggers `internal_ping`, which now sees the full validator reward accrued over the whole of epoch N and mints/attributes it pro-rata to all outstanding shares — including the shares the attacker acquired only blocks earlier.
- The attacker thus captures a full epoch's worth of reward while only bearing exposure for a few blocks, diluting the effective yield of delegators who were staked the entire epoch.

This mirrors the referenced NFTX bug class: value distributed in a discrete, front-runnable/predictable chunk to whoever holds the accounting unit (shares) at that instant, rather than streamed proportionally to time-at-risk.

## Impact Explanation
This causes rewards to be mis-attributed away from long-term delegators toward opportunistic short-term depositors, which matches the High-impact category of "rewards ... mis-attributed ... where another party settles on it" — the share price (and thus every other delegator's later withdrawal amount) is computed off the diluted `total_staked_balance`/`total_stake_shares` state. No funds are outright stolen from the contract's solvency, but real economic value is transferred from patient stakers to opportunistic ones without any corresponding contribution to the pool.

## Likelihood Explanation
Epoch height and epoch boundaries in NEAR are deterministic and can be tracked precisely off-chain, so an attacker does not need to "front-run a mempool transaction" as in the NFTX case — they can simply schedule a `deposit_and_stake` call for the final block(s) of any epoch. The only friction is `unstake`'s 4-epoch withdrawal delay [3](#0-2) , but this only delays withdrawal of principal + captured reward; it does not prevent the reward capture itself, and repeated participation across epochs compounds the effect. This can be executed by any unprivileged account with no special access.

## Recommendation
Adopt a streaming/vesting model for reward recognition instead of crediting the whole epoch's reward instantaneously to the share price at the first post-epoch interaction — e.g., linearly release newly observed rewards over the following epoch(s), or require a minimum bonding/holding duration before newly staked shares become eligible for a given epoch's reward, consistent with the mitigation suggested in the referenced report.

## Proof of Concept
1. Epoch N is about to end (attacker monitors `env::epoch_height()` off-chain, which is deterministic based on block height).
2. In the last block of epoch N, attacker calls `deposit_and_stake` [4](#0-3) . `internal_ping` is a no-op here since the epoch hasn't switched, so attacker's shares are minted at the current (pre-reward) price.
3. Epoch N+1 begins; the validator's staking reward for epoch N is credited to the account's locked balance by the protocol.
4. Any account (attacker or third party) calls any state-changing method (e.g. `ping`), triggering `internal_ping`, which computes `total_reward = total_balance - last_total_balance` and adds `remaining_reward` to `total_staked_balance`, increasing the price of every outstanding "stake" share, including the attacker's just-minted ones [5](#0-4) .
5. Attacker calls `unstake_all` to lock in the appreciated share value, then withdraws after the standard 4-epoch delay, having captured a full epoch's pro-rata reward for a few blocks of exposure.

```rust
    /// Distributes rewards after the new epoch. It's automatically called before every action.
    /// Returns true if the current epoch height is different from the last epoch height.
    pub(crate) fn internal_ping(&mut self) -> bool {
        let epoch_height = env::epoch_height();
        if self.last_epoch_height == epoch_height {
            return false;
        }
        self.last_epoch_height = epoch_height;

        // New total amount (both locked and unlocked balances).
        // NOTE: We need to subtract `attached_deposit` in case `ping` called from `deposit` call
        // since the attached deposit gets included in the `account_balance`, and we have not
        // accounted it yet.
        let total_balance =
            env::account_locked_balance() + env::account_balance() - env::attached_deposit();

        assert!(
            total_balance >= self.last_total_balance,
            "The new total balance should not be less than the old total balance"
        );
        let total_reward = total_balance - self.last_total_balance;
        if total_reward > 0 {
            // The validation fee that the contract owner takes.
            let owners_fee = self.reward_fee_fraction.multiply(total_reward);

            // Distributing the remaining reward to the delegators first.
            let remaining_reward = total_reward - owners_fee;
            self.total_staked_balance += remaining_reward;

            // Now buying "stake" shares for the contract owner at the new share price.
            let num_shares = self.num_shares_from_staked_amount_rounded_down(owners_fee);
            if num_shares > 0 {
                // Updating owner's inner account
                let owner_id = self.owner_id.clone();
                let mut account = self.internal_get_account(&owner_id);
                account.stake_shares += num_shares;
                self.internal_save_account(&owner_id, &account);
                // Increasing the total amount of "stake" shares.
                self.total_stake_shares += num_shares;
            }
            // Increasing the total staked balance by the owners fee, no matter whether the owner
            // received any shares or not.
            self.total_staked_balance += owners_fee;

            env::log(
                format!(
                    "Epoch {}: Contract received total rewards of {} tokens. New total staked balance is {}. Total number of shares {}",
                    epoch_height, total_reward, self.total_staked_balance, self.total_stake_shares,
                )
                    .as_bytes(),
            );
            if num_shares > 0 {
                env::log(format!("Total rewards fee is {} stake shares.", num_shares).as_bytes());
            }
        }

        self.last_total_balance = total_balance;
        true
```

```markdown
#### Unstake

When an account wants to unstake a given amount, the contract calculates the number of "stake" shares needed (`num_shares`) and
the actual required rounded unstake amount (`amount`). It's calculated based on the current total price of "stake" shares.
The unstaked balance of the account is increased by `amount`, the number of "stake" shares of the account is decreased by `num_shares`.
The minimum epoch height when the account can withdraw is set to the current epoch height increased by `4`.
The contract decreases the total number of staked tokens and the total number of "stake" shares. Then the contract restakes.
```
