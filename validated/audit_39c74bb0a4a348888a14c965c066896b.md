### Title
Claimed instant-withdraw receipts are never cleared from `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, letting already-paid receipts re-enter default-recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` and burns the receipt tokens, but leaves the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched. The defaulted-instant claim path (`_claimDefaultedInstantWithdrawRequest`) and the recovery-basis computation (`defaultPendingClaimBasis`) both read those stale per-epoch counters. This mirrors the Zebra `pop_root`/`pop_tip` asymmetry: one removal path cleans the per-bucket bookkeeping, the other doesn't, so stale contributions are later folded into a finalized "batch" (here, `finalizeDefaultRecovery`) and paid out again from `defaultRecoveryReserve`.

### Finding Description
- `requestInstantWithdraw` records both `instantWithdrawsRequests[_user]` and the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` / `instantWithdrawClaimsByEpoch[currentEpoch]` (IdleCreditVault.sol:356-375).
- `claimInstantWithdrawRequest` pays a funded instant receipt but zeroes only the aggregate: `instantWithdrawsRequests[_user] = 0`; the per-epoch mappings remain (IdleCreditVault.sol:380-393).
- If the borrower defaults in that same epoch, `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (IdleCreditVault.sol:693-696), and `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still counts the already-paid amount `A` (IdleCreditVault.sol:644-649). `recoveryPrice = reserve / totalBasis` is therefore diluted.
- On `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (= stale `A` plus any unclaimed same-epoch `C`) as claim basis and pays `(claimBasis * defaultRecoveryPrice)` from the reserve (IdleCreditVault.sol:842-856). The underflow guard `instantWithdrawsRequests[_user] -= claimBasis` is bypassed whenever the user also holds an older unfunded instant receipt `X` from a previous epoch (`pendingInstantWithdraws` persists across epochs), i.e. aggregate `X + C >= A + C`.

Net effect: `A` is paid twice — once at par, once from the recovery reserve — and the inflated `totalBasis` lowers `defaultRecoveryPrice` for every other claimant, permanently locking the corresponding undistributed reserve in the strategy (there is no sweep of `defaultRecoveryReserve`).

### Impact Explanation
Attacker (a KYC-passing lender/tranche holder who can request instant withdraws via the CDO) steals `A * defaultRecoveryPrice` from the recovery reserve — funds owed to other defaulted-epoch receipt holders and active LPs. Additionally, all other claimants are underpaid pro-rata due to the inflated `defaultPendingClaimBasis`, and the excess reserve is permanently frozen in the contract.

### Likelihood Explanation
Requires: (a) an instant-withdraw-capable CDO variant, (b) the attacker to hold an older unfunded instant receipt (possible whenever `pendingInstantWithdraws` carries over epochs, which the code explicitly supports via `_defaultPrefundedInstantReserve`), (c) the borrower to default in the same epoch the attacker claimed a funded instant receipt — defaults are initiated by the honest manager/borrower flow, so this is an opportunistic sequence an unprivileged user can always pre-position for. No privileged attacker action needed.

### Recommendation
In `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrease `instantWithdrawClaimsByEpoch[epoch]` for the request epoch when paying a funded instant receipt (matching the cleanup `_clearWithdrawClaimForEpoch` performs for normal receipts). Track the per-user request epoch for instant receipts (e.g., a `lastInstantWithdrawRequest` marker) so the correct epoch bucket is decremented, and reduce `instantWithdrawClaimsByEpoch` at funding time via `collectInstantWithdrawFunds` if claims are meant to be funded collectively rather than individually.

### Proof of Concept
Foundry fork PoC sketch (setup mirroring `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleInstantReceiptDoubleClaim() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    address attacker = makeAddr('attacker');

    // --- Epoch F: attacker leaves an unfunded instant receipt X ---
    _depositWithUser(attacker, 200e6, true);          // AA deposit -> tranches
    vm.prank(manager); cdoEpoch.startEpoch();
    // request instant withdraw X = 50e6 worth; CDO has no liquid funds -> stays in pendingInstantWithdraws
    _requestInstantWithdrawWithUser(attacker, 50e6);   // instantWithdrawsRequests[attacker]=50, perEpoch[F]=50

    // --- Epoch E (>F): same-epoch funded instant claim A, then unclaimed C ---
    _stopCurrentEpoch();                               // epochNumber advances to E
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestInstantWithdrawWithUser(attacker, 60e6);   // A: perEpoch[E]+=60, claimsByEpoch[E]+=60
    // borrower/CDO funds instant withdrawals (getInstantWithdrawFunds + collectInstantWithdrawFunds)
    _fundInstantWithdraws(60e6);
    skip(instantDelay + 1);
    vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest(); // pays A at par
    // BUG: instantWithdrawsRequestsByEpoch[attacker][E]==60 and instantWithdrawClaimsByEpoch[E]==60 remain
    assertEq(vault.instantWithdrawsRequestsByEpoch(attacker, vault.epochNumber()), 60e6);
    _requestInstantWithdrawWithUser(attacker, 40e6);   // C unclaimed: aggregate=50+40=90 >= stale 100? use sizes s.t. X>=A
    // choose A=40e6, C=60e6 so aggregate X+C=110 >= claimBasis A+C=100

    // --- Borrower defaults in epoch E ---
    _startDefault();                                    // manager triggers _handleBorrowerDefault / finalizeDefault
    // finalizeDefaultRecovery: basis includes instantWithdrawClaimsByEpoch[E] = stale A + C = 100
    _finalizeDefaultRecovery(recovered);

    // Attacker claims: claimBasis = A+C = 100; aggregate 110-100 no underflow
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;
    // paid includes (A+C)*recoveryPrice -> A was already paid at par: double payment of A*price
    assertGt(paid, /* C*price + remainder */ 0);
    // every other claimant's recoveryPrice was diluted by stale A in totalBasis
}
```

Key assertions: `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` are non-zero after a fully paid `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393), the stale basis is added into `defaultPendingClaimBasis` (IdleCreditVault.sol:644-649), and `_claimDefaultedInstantWithdrawRequest` pays it again from `defaultRecoveryReserve` (IdleCreditVault.sol:842-856).
