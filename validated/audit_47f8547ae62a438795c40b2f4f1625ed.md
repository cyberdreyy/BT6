### Title
Decimal-Truncation Remainder Permanently Locked in `BridgeVault` on Every ETH Deposit — (`bridge/evm/contracts/SuiBridge.sol`, `bridge/evm/contracts/SuiBridgeV2.sol`)

---

### Summary

`bridgeETH` and `bridgeETHV2` transfer the caller's full `msg.value` into `BridgeVault`, but emit a `TokensDeposited` event for only the decimal-truncated Sui-adjusted amount. The sub-unit remainder (`msg.value % 10^10` wei, up to ≈ 9.99 Gwei per call) is wrapped as WETH inside the vault and has no on-chain recovery path. Bridge validators mint only the emitted amount on Sui, so the truncated ETH is permanently stranded.

---

### Finding Description

ETH has 18 decimals on EVM; the bridge represents it with 8 decimals on Sui. The conversion factor is `10^(18-8) = 10^10`.

**`bridgeETH` (SuiBridge.sol lines 207–221):**

```solidity
uint256 amount = msg.value;
// ALL of msg.value goes to the vault
(bool success,) = payable(address(vault)).call{value: amount}("");

// Only the truncated amount is emitted
uint64 suiAdjustedAmount = BridgeUtils.convertERC20ToSuiDecimal(
    IERC20Metadata(config.tokenAddressOf(BridgeUtils.ETH)).decimals(), // 18
    config.tokenSuiDecimalOf(BridgeUtils.ETH),                         // 8
    amount
);
emit TokensDeposited(..., suiAdjustedAmount, ...);
```

Inside `convertERC20ToSuiDecimal` (BridgeUtils.sol lines 141–142):

```solidity
uint256 factor = 10 ** (erc20Decimal - suiDecimal); // 10^10
amount = amount / factor;                            // integer division, remainder lost
```

The vault's `receive()` wraps every incoming ETH as WETH:

```solidity
receive() external payable {
    if (msg.sender != address(wETH)) {
        wETH.deposit{value: msg.value}();
    }
}
```

So the full `msg.value` is stored as WETH, but only `suiAdjustedAmount * 10^10` wei is ever claimable via bridge messages. The remainder (`msg.value % 10^10`) accumulates as WETH in the vault with no withdrawal path.

`BridgeVault` exposes only two transfer functions, both `onlyOwner` and only invoked by `SuiBridge` when processing a signed bridge message for an exact amount:

```solidity
function transferETH(address payable recipientAddress, uint256 amount) external onlyOwner ...
function transferERC20(address tokenAddress, address recipientAddress, uint256 amount) external onlyOwner ...
```

There is no sweep, rescue, or admin-recovery function. The same truncation applies to `bridgeERC20` when the token is wETH (18 decimals → 8 Sui decimals).

The existing test at `SuiBridgeTest.t.sol` lines 439–459 explicitly documents the rounding: depositing `2_000_000_011_000_000_888` wei stores the full amount in the vault but emits only `2.00000001 ether` (`2_000_000_010_000_000_000` wei). The difference — `1_000_000_888` wei — is permanently locked.

---

### Impact Explanation

Every call to `bridgeETH` or `bridgeERC20` (with wETH) where `msg.value % 10^10 != 0` permanently locks up to `10^10 - 1` wei (≈ 9.99 Gwei) in `BridgeVault`. The locked WETH accumulates across all ETH bridge deposits and cannot be recovered under the current contract set. This is a permanent fund lock reachable by any unprivileged user.

---

### Likelihood Explanation

Any ETH amount that is not an exact multiple of `10^10` wei triggers the lock. In practice, virtually every real-world ETH transfer (wallet-chosen amounts, gas-adjusted amounts, DeFi outputs) has a non-zero sub-10-Gwei remainder. The condition is met on nearly every `bridgeETH` call. The same applies to `bridgeETHV2` in `SuiBridgeV2.sol`.

---

### Recommendation

Before transferring `msg.value` to the vault, compute the truncated amount and refund the remainder to the caller:

```solidity
uint256 factor = 10 ** (erc20Decimal - suiDecimal); // 10^10 for ETH
uint256 truncated = (msg.value / factor) * factor;
uint256 refund = msg.value - truncated;

(bool success,) = payable(address(vault)).call{value: truncated}("");
require(success, "SuiBridge: Failed to transfer ETH to vault");

if (refund > 0) {
    (bool refundSuccess,) = payable(msg.sender).call{value: refund}("");
    require(refundSuccess, "SuiBridge: Failed to refund excess ETH");
}
```

Alternatively, revert if `msg.value % factor != 0`, forcing callers to supply exact amounts.

---

### Proof of Concept

1. Call `bridgeETH{value: 1_000_000_001}(recipientAddress, destinationChainID)` (1 Gwei + 1 wei).
2. `BridgeVault` receives `1_000_000_001` wei, wraps it as WETH.
3. `convertERC20ToSuiDecimal(18, 8, 1_000_000_001)` → `1_000_000_001 / 10^10 = 0` → reverts with "Insufficient amount provided".

Use a larger value: `bridgeETH{value: 10_000_000_001}` (10 Gwei + 1 wei):
- `convertERC20ToSuiDecimal` → `10_000_000_001 / 10^10 = 1` (1 unit on Sui, i.e. 0.00000001 ETH)
- Emitted: `suiAdjustedAmount = 1`
- Vault holds: `10_000_000_001` wei as WETH
- Claimable via bridge: `1 * 10^10 = 10_000_000_000` wei
- Permanently locked: `1` wei

Repeat across N transactions with remainder R each: total locked = `sum(R_i)`, growing without bound, with no on-chain recovery.
