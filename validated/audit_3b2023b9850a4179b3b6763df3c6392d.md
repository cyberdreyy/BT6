## Finding

### Title
Missing fee-sum validation in `createDstEscrow` permits underflow-blocked, permanently unwithdrawable destination escrows - (File: `contracts/BaseEscrowFactory.sol`)

### Summary
`BaseEscrowFactory._postInteraction` (source-chain escrow creation) enforces `integratorFeeAmount + protocolFeeAmount < takingAmount` before encoding fee data into escrow immutables, but `createDstEscrow` (destination-chain escrow creation) accepts fully taker-supplied `Immutables.parameters` with **no equivalent check**. This is the same root-cause pattern as the GMX report: a value (`remainingCollateralUsd` there, `amount - fees` here) that should be checked for validity/zero before being consumed, is left unguarded on one specific code path, letting an unprivileged actor push it into an underflow/zero state that blocks the intended state transition (liquidation there, withdrawal here).

### Finding Description
In source-chain flow, `BaseEscrowFactory._postInteraction` computes fees and validates them: [1](#0-0) 

That check guarantees `integratorFeeAmount + protocolFeeAmount < takingAmount` — but it is only applied to the data embedded in the `SrcEscrowCreated` event (`DstImmutablesComplement.parameters`), which is informational/off-chain guidance for building the destination escrow. It is **not** re-validated when the destination escrow is actually created: [2](#0-1) 

`createDstEscrow` copies `dstImmutables` (including the arbitrary `parameters` bytes containing `protocolFeeAmount`/`integratorFeeAmount`) verbatim, with checks only on `msg.value` (safety deposit + native amount) and on the cancellation timing — never on the relationship between `amount` and the encoded fee amounts.

Those fee values are later subtracted unconditionally in `EscrowDst._withdraw`: [3](#0-2) 

If `integratorFeeAmount + protocolFeeAmount >= immutables.amount`, line 92 (`immutables.amount - integratorFeeAmount - protocolFeeAmount`) underflows and reverts under Solidity 0.8 checked arithmetic. Since `_withdraw` is the internal function called by **both** `withdraw` (taker-only) and `publicWithdraw` (any access-token holder) on `EscrowDst`, this single corrupted value blocks **every** withdrawal path, private and public alike — exactly analogous to how the GMX liquidation function's unguarded division blocked liquidation for every caller.

`EscrowDst` has no `publicCancel` (unlike `EscrowSrc`), and `cancel`/`rescueFunds` are both `onlyCaller(taker)`: [4](#0-3) [5](#0-4) 

So once a taker deploys a destination escrow with `protocolFeeAmount + integratorFeeAmount >= amount`, only that same taker can ever reclaim the locked funds (via `cancel` after the cancellation timelock, or `rescueFunds` after `RESCUE_DELAY`) — the maker can never receive their destination-side proceeds, since every `withdraw`/`publicWithdraw` call reverts.

### Impact Explanation
This lets a taker (an unprivileged, permissionless participant who calls `createDstEscrow` — an explicitly in-scope entry point per the attacker model) construct a destination escrow that is fundable and deployable, but permanently unwithdrawable by the maker, while the taker alone can eventually reclaim the locked principal via `cancel`/`rescueFunds`. Combined with the taker's ability to withdraw the maker's source-chain tokens using the same revealed secret, this can result in the maker's source-side funds being taken while the corresponding destination-side payout is unrecoverable by them — a theft/permanent-freezing pattern for the maker's funds, matching the "Critical: direct theft of user funds... or permanent freezing of funds" bounty tier for the destination-side principal, or at minimum "High: temporary freezing of funds during the live swap lifecycle" since only the taker (not the maker) can ever release the locked balance.

### Likelihood Explanation
`createDstEscrow` is a fully permissionless, unprivileged entry point — the taker who calls it entirely controls the `parameters` bytes (which encode `protocolFeeAmount`/`integratorFeeAmount`) with the factory performing no arithmetic sanity check between these values and `amount`, unlike the equivalent, already-implemented guard on the source-chain path (`InvalidFeeAmounts`). Triggering it requires only a single malformed `createDstEscrow` call, no special privileges, and no race condition — it is a deterministic, always-reachable underflow whenever `protocolFeeAmount + integratorFeeAmount >= amount`.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`, e.g.:
```solidity
(uint256 integratorFeeAmount, uint256 protocolFeeAmount) = (dstImmutables.integratorFeeAmountCd(), dstImmutables.protocolFeeAmountCd());
if (integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
placed before the escrow is deployed and funded in `createDstEscrow`, mirroring the check at [6](#0-5) .

### Proof of Concept
1. Taker fills a source-chain order normally, or fabricates any valid src flow.
2. Taker calls `createDstEscrow` with `dstImmutables.amount = A` and `parameters` encoding `protocolFeeAmount + integratorFeeAmount >= A` (factory performs no check on this relationship, only on `msg.value` matching `amount + safetyDeposit`).
3. Once the maker reveals the secret (used by taker to withdraw src funds), any attempt to call `EscrowDst.withdraw`/`publicWithdraw` on the destination escrow reverts with a Solidity underflow panic at `contracts/EscrowDst.sol:92`, because `integratorFeeAmount + protocolFeeAmount > immutables.amount`.
4. Maker can never claim destination funds; only the taker can later call `cancel` (after `DstCancellation`) or `rescueFunds` (after `RESCUE_DELAY`) to reclaim the escrowed principal for themselves.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);

            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
