### Title
Unauthenticated pipeline run resume endpoint allows unprivileged state mutation of job runs - (File: core/web/router.go)

### Summary
The reported bug is a missing access-control gate on a state-changing "start/unpause" function that anyone can invoke. The closest reachable analog in this codebase is the `/v2/resume/:runID` route, which is explicitly registered in an unauthenticated route group and lets any network caller push a `Result` payload that finishes a pipeline task and resumes/mutates the run, with zero authentication or authorization check.

### Finding Description
In `core/web/router.go`, the v2 route group is split into an authenticated group (`authv2`) and an explicitly unauthenticated group (`unauthedv2`): [1](#0-0) 

The resume endpoint is registered on the unauthenticated group with no `auth.Authenticate(...)` middleware at all: [2](#0-1) 

The handler, `PipelineRunsController.Resume`, decodes an attacker-supplied JSON body into a `pipeline.ResumeRequest`, converts it into a `pipeline.Result`, and calls `app.ResumeJobV2` directly — there is no authentication, no session/token check, and no verification that the caller is the bridge/adapter that originally started the task: [3](#0-2) 

The only "gate" is that the caller must know the `runID` (a UUID `taskID`), which functions as a capability token rather than an authenticated credential — structurally identical to the "paused by default, unlockable by anyone" pattern in the report: a security-relevant, state-mutating action reachable without any privileged role or authentication.

### Impact Explanation
Anyone who can enumerate, guess, leak, or intercept a pending task's UUID (e.g., via logs, monitoring dashboards, error messages, or a compromised/careless bridge adapter) can inject arbitrary results into a paused pipeline run and force it to resume with attacker-controlled data. Depending on the job's task graph, this can result in unauthorized job-run completion, manipulation of on-chain reporting values, or premature/duplicate resumption of a run — matching the "unauthorized job run" impact category. The audit log call explicitly labels this as `audit.UnauthedRunResumed`, confirming the code's own awareness that this is an unauthenticated write path: [4](#0-3) 

### Likelihood Explanation
Exploitation is gated entirely by knowledge of the target `taskID` UUID — this is a deliberate design choice (bridges/external adapters call back asynchronously without a durable API-token session), functioning as a bearer-token/capability-based security model rather than a broken access control bug. Absent a taskID leak or a bridge adapter vulnerability, this is not remotely exploitable by an arbitrary anonymous party. This significantly lowers likelihood versus the referenced report, where *no* secret material is required to unpause the contract.

### Recommendation
- Restrict `PATCH /v2/resume/:runID` to require verification that the caller is the specific bridge/adapter associated with the pending task (e.g., HMAC-signed callback, per-task shared secret, or scoping to the bridge's registered outbound IP/token), rather than relying solely on UUID unguessability.
- Ensure the audit trail (`audit.UnauthedRunResumed`) is monitored/alerted on, and consider rate-limiting or short expiry windows for pending task IDs to reduce the exposure window.

### Proof of Concept
1. Obtain or infer a pending task UUID for an in-flight pipeline run (e.g., from logs, a leaked bridge callback URL, or a bridge response echoing the task ID).
2. Send an unauthenticated request:
```
PATCH /v2/resume/<taskID>
Content-Type: application/json

{"data": {"result": "attacker-controlled-value"}}
```
3. The node accepts the request without any authentication, converts it to a `pipeline.Result`, and calls `ResumeJobV2`, resuming the pipeline run with attacker-supplied data — no privileged role, session, or API token is required.

Note: This finding centers on a genuinely unauthenticated production route with no access control, satisfying the "unprivileged actor" and "session/token handling" scope constraints. However, because the taskID acts as an unguessable capability token by design, actual exploitability depends on leakage of that identifier, which I could not fully verify is systematically prevented elsewhere in the codebase (e.g., in bridge adapter logging or task-ID exposure surfaces) within the scope of this investigation.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
