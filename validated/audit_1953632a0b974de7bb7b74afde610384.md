### Title
Zip-Slip path traversal in `ExtractZipArchive`/`extractZipFile` allows writing outside extraction root - ([File: helpers/archives/zip_extract.go])

### Summary
`extractZipFile` and its helpers (`extractZipDirectoryEntry`, `extractZipSymlinkEntry`, `extractZipFileEntry`) use `zip.File.Name` verbatim—via `os.MkdirAll(filepath.Dir(file.Name), ...)`, `os.Mkdir`, `os.Symlink`, and `os.OpenFile`—with no validation that the resulting path stays inside the extraction root. The only pre-write check in `ExtractZipArchive` (`errorIfGitDirectory`) only rejects `.git` paths, not `..`-traversal or absolute/drive-qualified paths, so a crafted cache/artifact zip entry can escape the workspace and write to arbitrary filesystem locations, including a user's PowerShell profile.

### Finding Description
`ExtractZipArchive` in [1](#0-0)  iterates `archive.File` and for each entry only calls `errorIfGitDirectory(file.Name)` before calling `extractZipFile(file)`. `errorIfGitDirectory`/`isPathAGitDirectory` in [2](#0-1)  only checks whether the first path component is literally `.git`; it does not clean the path, reject `..` segments, or reject absolute/drive-letter paths.

`extractZipFile` then does: [3](#0-2) 
`os.MkdirAll(filepath.Dir(file.Name), 0o777)` creates all parent directories for the raw, attacker-supplied name, and the subsequent `extractZipDirectoryEntry`/`extractZipSymlinkEntry`/`extractZipFileEntry` calls (lines 12-59) use `file.Name` directly in `os.Mkdir`, `os.Symlink`, and `os.OpenFile`. None of these normalize or bound the path to a root directory. `filepath.Dir`/`os.MkdirAll`/`os.OpenFile` on Windows correctly interpret both `..\` sequences and drive-qualified/UNC-style paths, so an entry name such as `..\..\..\Users\<user>\Documents\WindowsPowerShell\profile.ps1` (or an absolute path) will be created/written outside of the intended extraction directory.

`lchmod` in [4](#0-3)  is called afterward for every extracted entry with the same unvalidated `file.Name` and simply calls `os.Chmod` (a no-op for symlinks); it performs no path validation either, but it is not the root cause—it is only reached after the traversal write has already succeeded, so it does not add new risk beyond what `extractZipFileEntry` already exposed, though it also doesn't provide any compensating check.

This is reachable from a normal, unprivileged job: caches and artifacts are user-controlled zip archives that a job can supply (e.g., via a pipeline that fabricates a cache/artifact zip, or a build that produces a crafted artifact later restored in another job) and are extracted with `archives.ExtractZipFile` → `ExtractZipArchive` → `extractZipFile`, as wired through `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`'s `Extract` method: [5](#0-4) .

### Impact Explanation
On a Windows runner host, a job-controlled cache/artifact zip archive with a crafted `Name` field can cause the Runner's extraction helper to write attacker-controlled file content to arbitrary filesystem paths reachable by the runner process's permissions, including auto-loaded PowerShell profile scripts or other locations. This lets a job escape its intended workspace/extraction root and influence code executed by later PowerShell invocations on the same host, matching the scoped impact (runner-side execution outside the authored job payload).

### Likelihood Explanation
The only precondition is that a job (or job output flowing into a cache/artifact) can supply/control a zip archive that Runner subsequently extracts via `ExtractZipArchive`/`ExtractZipFile`—both cache restore and artifact extraction are standard, unprivileged job-triggerable operations. No authentication bypass or admin action is needed; a normal pipeline author can build such a zip and reference it as a cache key or artifact. The bug is deterministic and fully repeatable with a static PoC.

### Recommendation
Before extracting each entry in `extractZipFile`/`ExtractZipArchive`, resolve `filepath.Join(extractionRoot, file.Name)`, `filepath.Clean` it, and verify (e.g., via `filepath.Rel` or prefix check) that the resulting absolute path is still contained within the extraction root; reject (or skip with a logged warning, consistent with existing `.git` handling) any entry whose name is absolute, contains `..` traversal after cleaning, or resolves outside the root. Apply the same containment check to symlink targets to prevent symlink-based escapes.

### Proof of Concept
Add a Go test in `helpers/archives/zip_extract_test.go`:
1. Create a `zip.Writer` with a single entry named `..\..\..\evilfile.txt` (or `../../evilfile.txt` on the unix build tag) containing marker content.
2. Change the test's working directory into a temp "workspace root" subdirectory.
3. Call `ExtractZipArchive` on the resulting `zip.Reader`.
4. Assert that `evilfile.txt` was NOT created in the temp directory's parent (outside the workspace root)—i.e., `os.Stat` on the resolved escape path returns `os.IsNotExist`—and that either an error was returned or the entry was skipped/logged as rejected.
Currently this test would fail (the file gets created outside the root), demonstrating the Zip-Slip vulnerability.

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}

func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))
	if len(parts) > 0 && parts[0] == ".git" {
		return true
	}
	return false
}
