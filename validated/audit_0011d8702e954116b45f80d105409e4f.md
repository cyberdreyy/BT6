### Title
Cross-Chain Nonce Collision in `isTransferProcessed` Allows Permanent Fund Lock - (File: `bridge/evm/contracts/SuiBridge.sol`)

### Summary

`SuiBridge.transferBridgedTokensWithSignatures` and `SuiBridgeV2.transferBridgedTokensWithSignaturesV2` track processed token-transfer messages using `mapping(uint64 nonce => bool isProcessed) public isTransferProcessed`, keyed **only by `message.nonce`**. Because the bridge supports multiple source chains simultaneously and each source chain maintains its own independent nonce counter, two legitimately committee-signed transfers from different source chains that happen to share the same nonce value collide in this mapping. An unprivileged user who observes both signed messages can submit one first, permanently blocking the other and locking the victim's funds.

### Finding Description

`SuiBridge.sol` declares the replay-protection store as:

```solidity
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
``` [1](#0-0) 

Both `transferBridgedTokensWithSignatures` (V1) and `transferBridgedTokensWithSignaturesV2` (V2) guard against replay with:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
```

and mark completion with:

```solidity
isTransferProcessed[message.nonce] = true;
``` [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The `message.chainID` field identifies the **source chain** (the chain from which tokens are being bridged). The `onlySupportedChain(message.chainID)` modifier confirms the bridge accepts transfers from multiple source chains: [6](#0-5) [7](#0-6) 

The `BridgeConfig` is explicitly initialized with multiple supported source chains (e.g., `supportedChains[0] = 11; supportedChains[1] = 12`): [8](#0-7) 

Each source chain maintains its own independent nonce counter starting from 0. Because `isTransferProcessed` is keyed only by `nonce` and not by `(chainID, nonce)`, the nonce namespace is shared across all source chains. Processing source-chain-A's transfer with `nonce=N` sets `isTransferProcessed[N] = true`, which permanently blocks source-chain-B's transfer with `nonce=N`.

The `MessageVerifier` correctly uses `(messageType, nonce)` for governance messages but explicitly **excludes** `TOKEN_TRANSFER` from that path, leaving token transfers with the weaker single-key guard: [9](#0-8) 

### Impact Explanation

A user who deposited tokens on source chain B with sequence number N has their funds permanently locked on the EVM side: the corresponding `isTransferProcessed[N]` slot is already `true` from chain A's transfer, so the claim transaction always reverts with `"SuiBridge: Message already processed"`. The tokens on chain B cannot be recovered. This satisfies the **permanent fund lock** impact class (High/Medium).

### Likelihood Explanation

The attack requires:
1. The bridge to be configured with at least two supported source chains (the config explicitly supports this).
2. Both chains to have reached the same nonce value (inevitable as both start at 0 and increment monotonically).
3. An attacker to observe both committee-signed messages (they are broadcast publicly by bridge nodes) and submit one before the other.

No privileged access, key compromise, or governance quorum is needed. Any ordinary Ethereum account can call `transferBridgedTokensWithSignatures`.

### Recommendation

Key the processed-transfer mapping by both source chain ID and nonce:

```solidity
// Before
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
require(!isTransferProcessed[message.nonce], ...);
isTransferProcessed[message.nonce] = true;

// After
mapping(uint8 chainID => mapping(uint64 nonce => bool isProcessed)) public isTransferProcessed;
require(!isTransferProcessed[message.chainID][message.nonce], ...);
isTransferProcessed[message.chainID][message.nonce] = true;
```

This mirrors how the Sui-side Move bridge correctly keys transfer records by `(source_chain, message_type, seq_num)`: [10](#0-9) 

### Proof of Concept

1. Bridge is configured with two supported source chains: chain A (`chainID=11`) and chain B (`chainID=12`).
2. A user on chain A deposits tokens; the committee signs a `TOKEN_TRANSFER` message with `chainID=11, nonce=5`.
3. A user on chain B deposits tokens; the committee signs a `TOKEN_TRANSFER` message with `chainID=12, nonce=5`.
4. Attacker calls `transferBridgedTokensWithSignatures(sigA, messageA)` → succeeds, sets `isTransferProcessed[5] = true`, chain-A user receives tokens.
5. Attacker (or anyone) calls `transferBridgedTokensWithSignatures(sigB, messageB)` → reverts with `"SuiBridge: Message already processed"`.
6. Chain-B user's tokens are permanently locked; no recovery path exists.
