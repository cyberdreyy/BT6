### Title
Cross-user response hijacking via unauthenticated MessageId collision in savedCallbacks map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each request's callback in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageId`, with no uniqueness enforcement, and `handleWebAPITriggerMessage` looks up and deletes the callback by that same key with no verification that the response actually corresponds to the request that registered it. A second signed request reusing the same `MessageId` silently overwrites the first entry, so the DON response for `MessageId` X is delivered to whoever's callback is currently stored, not necessarily the original caller.

### Finding Description
`MessageId` originates entirely from the caller: it is the JSON-RPC `id` field or `api.Message.Body.MessageId` supplied in the signed HTTP request to the gateway's user-facing endpoint, and is only validated for length/format in `api.Message.Validate()` [1](#0-0) . It is never checked for uniqueness against `h.savedCallbacks`.

In `HandleLegacyUserMessage`, the callback is stored unconditionally: [2](#0-1) 
If two signed requests (from any two distinct signers/sessions, since signature verification only binds `Sender` to the message body and is unrelated to `MessageId` uniqueness) arrive with the same `MessageId` before the first DON response comes back, the second `SendToNode`/callback registration silently overwrites the first in the map — last-writer-wins, no error, no collision detection.

When the DON eventually responds, `handleWebAPITriggerMessage` looks the callback up purely by `MessageId` and delivers to whatever is currently registered: [3](#0-2) 
There is no binding of the callback to the requester's session, IP, signer address, or any nonce beyond the caller-chosen string, so response routing is fully determined by whichever request most recently claimed that key.

### Impact Explanation
This is cross-user capability response leakage/confusion: an attacker submitting a signed request with a colliding `MessageId` (whether by predicting/observing another user's ID scheme, replaying an ID, or accidental application-level ID reuse) can have another user's DON trigger response (which may contain sensitive payload data returned via the web API trigger) delivered to the attacker's own HTTP connection instead of the legitimate requester, and/or cause the legitimate requester to receive a response for a request they didn't make. This matches Chainlink's "cross-user data exposure / request response confusion" impact class rather than fund loss or node compromise, since no signature/auth bypass occurs — only response delivery isolation is violated.

### Likelihood Explanation
Precondition: attacker only needs unauthenticated/unprivileged ability to sign and submit a gateway HTTP request (a message key alone, no operator role) and must cause `MessageId` collision with a target's in-flight request. Because `MessageId` is entirely attacker/client-chosen with no server-side randomization or uniqueness guard, and the max length is only checked (≤200 chars) with no entropy requirement, the collision precondition can be trivially satisfied if the attacker already knows or can predict the target's message ID scheme (e.g., sequential counters, workflow-execution-derived IDs, or IDs observable via other UI/telemetry channels), or if the same client integration reuses IDs across sessions. The race window is realistic given the async multi-node DON round trip in `handleWebAPIOutgoingMessage`/DON fan-out.

### Recommendation
Reject registration of a new callback if `msg.Body.MessageId` already exists and is unexpired in `savedCallbacks` (return an error to the second caller instead of overwriting). Additionally, bind stored callbacks to the requester's signer address (`msg.Body.Sender`) and verify that the responding node's forwarded response corresponds to a request that was actually sent to that specific `nodeAddr` for that `MessageId`, rather than relying on the map key alone.

### Proof of Concept
Go test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build handler via `setupHandler(t)` as in existing tests.
2. Create two distinct signed `triggerRequest` messages, `msgA` (signer keyA) and `msgB` (signer keyB), both using the *same* `MessageId` (modify `triggerRequest` helper to accept an explicit ID rather than hardcoded `"12345"`).
3. Create two separate callbacks `cbA := hc.NewCallback()` and `cbB := hc.NewCallback()`.
4. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` then `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` sequentially (or concurrently via goroutines + a small sync point) — mock `don.SendToNode` to no-op for both.
5. Deliver a single DON response for that `MessageId` via `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)`.
6. Assert: `cbB.Wait(ctx)` receives the response (since B's registration overwrote A's), while `cbA.Wait(ctx)` times out/never resolves — proving the response intended to correlate with A's request delivered to B (or vice versa depending on ordering), i.e., response routing is not tied to the originating requester, only to last-registered `MessageId` owner.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
