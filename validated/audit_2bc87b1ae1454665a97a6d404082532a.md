### Title
Stale pre-default instant-withdraw receipts steal funded recovery cash and dilute `defaultRecoveryPrice` for current-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` tracks pending instant withdrawals with a *global* counter (`pendingInstantWithdraws`) but computes the default-recovery claim basis and the "already funded" reserve using only the *current epoch's* instant claims (`instantWithdrawClaimsByEpoch[epochNumber]`). If a user holds an unfunded instant receipt from an earlier epoch, finalization (a) excludes their basis from `totalBasis`, and (b) miscomputes `_defaultPrefundedInstantReserve`, so cash that was actually collected for current-epoch instant claims is never moved into `defaultRecoveryReserve`. The stale claimant can then withdraw that cash at par via `claimInstantWithdrawRequest`, while current-epoch claimants only receive `claimBasis * defaultRecoveryPrice`.

### Finding Description
The external bug is "a retried operation double-counts because previously submitted work was not tracked." The analog: instant-withdraw accounting mixes a global unfunded remainder with per-epoch basis, so receipts minted in an earlier epoch are invisible to default finalization.

- `requestInstantWithdraw` grows the global `pendingInstantWithdraws` and per-epoch `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch` — an unfunded receipt survives across epochs. [1](#0-0) 
- `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — stale receipts from older epochs are excluded from `totalBasis`, inflating the recovery price denominator mismatch. [2](#0-1) 
- `_defaultPrefundedInstantReserve` returns `instantBasis - pendingInstant` only when `instantBasis > pendingInstant`; with a stale unfunded receipt, `pendingInstant > instantBasis` yields `0`, so the funded cash backing current-epoch claims is left outside `defaultRecoveryReserve`. [3](#0-2) 
- `claimInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, then pays the entire remaining `instantWithdrawsRequests[user]` at par through `_transferFundedClaim`, which is allowed to spend any balance above `defaultRecoveryReserve`. [4](#0-3) [5](#0-4) 

### Impact Explanation
Broken invariants: one-receipt-one-payout at the recovery haircut, and reserve isolation. Concretely: current-epoch instant claimants had `collectInstantWithdrawFunds` move e.g. 100 underlying into the strategy; because a stale unfunded receipt of 50 makes `pendingInstantWithdraws (150) > instantBasis (100)`, `_defaultPrefundedInstantReserve` returns 0, the 100 funded cash is excluded from `reserveAmount`, `defaultRecoveryPrice` is computed too low for everyone, and the stale claimant later pulls up to 50 (or more) of that 100 at par. Loss = funded instant cash up to `pendingInstantWithdraws - instantBasis` misallocated to stale claimants, plus a deflated `defaultRecoveryPrice` for all recovery claimants.

### Likelihood Explanation
Requires: (1) an instant-withdraw request left unfunded at epoch end (`pendingInstantWithdraws != 0` for an old epoch — achievable whenever borrower liquidity is short), and (2) a subsequent borrower default finalized via `finalizeDefaultRecovery` while current-epoch instant claims were prefunded. Both are plausible market conditions; the attacker is just a lender whose instant request was unfunded — an unprivileged, honest-acting user benefits by simply calling `claimInstantWithdrawRequest` after finalization. No privileged misbehavior needed; the honest manager/borrower sequence (stopEpoch → default → finalizeDefaultRecovery) triggers it.

### Recommendation
Track unfunded instant basis per epoch (or globally) and include *all* outstanding instant receipt basis in `defaultPendingClaimBasis`, not only `instantWithdrawClaimsByEpoch[epochNumber]`. Compute `_defaultPrefundedInstantReserve` as `totalInstantClaims - pendingInstantWithdraws` over all epochs, and route stale-epoch instant receipts through `_claimDefaultedInstantWithdrawRequest`-style haircutted payment instead of the at-par `_transferFundedClaim` path.

### Proof of Concept
Foundry fork sketch:

```solidity
// Epoch E0: attacker calls requestInstantWithdraw(50) via CDO; borrower never funds it
// -> pendingInstantWithdraws == 50, instantWithdrawsRequestsByEpoch[attacker][E0] == 50

// Epoch E1: victim calls requestInstantWithdraw(100); borrower funds it
// -> collectInstantWithdrawFunds(100); pendingInstantWithdraws == 150 (attacker's still unfunded)
// -> instantWithdrawClaimsByEpoch[E1] == 100

// Borrower defaults; CDO calls finalizeDefaultRecovery(recovered, source)
// defaultPendingClaimBasis() = pendingWithdraws + 100  (attacker's 50 excluded)
// _defaultPrefundedInstantReserve() = 0 because instantBasis(100) < pendingInstant(150)
// => the 100 funded underlying is NOT added to defaultRecoveryReserve
// => defaultRecoveryPrice is diluted for all claimants

// Post-finalization:
vm.prank(cdo);
vault.claimInstantWithdrawRequest(attacker);
// _claimDefaultedInstantWithdrawRequest clears only epoch E1 receipts (attacker has none)
// then pays instantWithdrawsRequests[attacker] == 50 via _transferFundedClaim,
// spending the victim's funded cash, which was left outside the reserve.

assertEq(underlying.balanceOf(attacker), 50); // paid at par, stolen from funded claims
```

The misallocation is bounded by `pendingInstantWithdraws - instantWithdrawClaimsByEpoch[epochNumber]` at finalization, directly draining underlyings that were earmarked for recovery-priced claims.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
