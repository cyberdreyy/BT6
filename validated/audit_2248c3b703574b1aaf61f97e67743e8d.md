### Title
`check_parent_tenure_choice` permits a reorg (and marks tenures superseded) based only on node-confirmed ("globally accepted") block counts, ignoring blocks that already carry a full signer-set signature — allowing a signer to sign a block that conflicts with an already-consensus-reached tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg one or more prior tenures, and if so records those tenures as **superseded** so that the signer's own prior signatures over their blocks stop counting as conflicts (`mark_tenure_superseded`, consumed later by `reorg_permit_stands`/`get_signed_conflicts`). The rule that is supposed to prevent reorging a tenure that has "already made progress" only inspects `get_globally_accepted_block_count_in_tenure`, i.e. blocks this signer's *own node* has already processed and announced via `NewBlock`. It does not consider blocks that have already reached the 70% signing threshold across the signer set (`LocallyAccepted`/`signed_group`) but simply have not yet been pushed to, or processed by, this signer's node. This is structurally identical to the reported Perennial bug: a guard that is supposed to reflect the *true* aggregated state (all committed/pending activity) instead reflects only a lagging, partial snapshot of it (`closable` vs. the actual pending position; here, "globally accepted count" vs. actual signed weight), letting an action through that the guard was designed to block.

### Finding Description
In `stacks-signer/src/chainstate/mod.rs`, `check_parent_tenure_choice` walks each tenure being reorged and enforces: [1](#0-0) 
```
// disallow reorg if more than one block has already been signed
let globally_accepted_blocks =
    signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
if globally_accepted_blocks > 1 {
    ...
    return Ok(false);
}
```
The comment says the check is about blocks that have "already been signed", but the code only counts blocks in `BlockState::GloballyAccepted` — i.e. blocks this signer's node has actually processed (`mark_globally_accepted`, driven by a `NewBlock` event or by `check_latest_block_in_tenure` observing the node's tip) [2](#0-1) . It ignores blocks in `BlockState::LocallyAccepted` that have already crossed the 70% signature threshold across the whole signer set (`signed_group` is set) but have not yet been handed to, or processed by, this signer's own node. The docs explicitly describe this gap elsewhere: a block is "not handed to the node until the whole signer set has signed it," and a signature is "a bearer instrument that can still be aggregated toward the 70% threshold ... whatever its state now" [3](#0-2) .

Only after passing the `globally_accepted_blocks > 1` gate does the function look at further blocks in the tenure, and even then it inspects only the tenure's **first** approved block's timing via `get_first_approved_block_in_tenure`, not any subsequent (already fully signed) blocks: [4](#0-3) 

So a tenure that produced, say, block N (already globally accepted by this signer's node) and block N+1 (already signed by ≥70% weight across the whole signer set, `signed_group` set, but not yet pushed to / seen by this signer's node — e.g. a network delay, or this signer being on a different, slower stacks-node) is seen by this function as having exactly `globally_accepted_blocks == 1`. The function proceeds to evaluate only block N's proposal timing and, if it looks "poorly timed", permits the reorg and calls `record_superseded_tenure` on that tenure: [5](#0-4) 

Marking the tenure superseded means this signer's own conflict-guard at signing time (`get_signed_conflicts` / `reorg_permit_stands`) will subsequently *exclude* any block in that tenure from blocking a new signature, even though block N+1 in that tenure already has enough weight to become canonical on its own: [6](#0-5) [7](#0-6) 

The result: this signer signs a brand-new tenure (or block) that reorgs a tenure which already has a block carrying an aggregated 70% signature — a signature that is a "bearer instrument" and can still be pushed and become globally accepted by any other node/signer at any time. Two conflicting chains can then each end up backed by 70%+ signer weight: exactly the "signer signing a conflicting block" class of critical impact.

### Impact Explanation
This breaks the safety property that the signer set never simultaneously endorses two conflicting chains. Because `check_parent_tenure_choice`'s progress-check is keyed off a signer-local, node-derived signal (`GloballyAccepted` state) rather than the network-visible, already-final signal (aggregated 70% signature weight, `signed_group`/`LocallyAccepted`), a signer can be tricked (by network delay, a slow/partitioned local node, or an adversarial miner racing the push) into treating an already-consensus tenure as "abandoned enough" to reorg. It then both signs the new competing tenure and disables its own future conflict protection over the old one (`mark_tenure_superseded`), removing the very safeguard (`get_signed_conflicts`) designed to prevent this class of double-endorsement. If the old tenure's already-signed block is later pushed and processed by the node network-wide, the chain now has two forks each with legitimate 70% signer backing — a consensus safety violation, not merely a delayed liveness issue.

### Likelihood Explanation
This requires no majority collusion and no key compromise — only ordinary asynchrony between "a block reached 70% signatures across the signer set" and "this signer's node has processed/announced that block." That asynchrony is already acknowledged and relied upon elsewhere in this same codebase (the "outdated peer"/bearer-signature handling, and the explicit design note that a block is "not handed to the node until the whole signer set has signed it"), so the race window is a normal, expected part of the protocol's operation rather than a contrived edge case. A single miner deciding to reorg a tenure whose second block is mid-flight (signed but not yet globally accepted by a given signer) is sufficient to trigger the flawed branch on that signer.

### Recommendation
In `check_parent_tenure_choice`, the "already made progress" check should not rely solely on `get_globally_accepted_block_count_in_tenure`. It should also account for blocks in the tenure that have reached `LocallyAccepted` with `signed_group` set (i.e., already crossed the 70% aggregate-weight threshold), treating them the same as globally accepted blocks for the purposes of refusing/limiting the reorg permit, and likewise consider all approved blocks' timing in the tenure (not only the first) when deciding whether to permit and record `mark_tenure_superseded`.

### Proof of Concept
1. Signer S maintains `SignerDb`; tenure T produces block `T#1`, which is quickly pushed to and processed by S's node (`GloballyAccepted`) — `globally_accepted_blocks == 1`.
2. Tenure T then produces block `T#2`, which reaches the 70% signature threshold across the signer set (`signed_group` recorded, `BlockState::LocallyAccepted`) via `handle_block_response` / `store_and_process_block_signature`, but S's own stacks-node has not yet received/processed the `BlockPushed`/`NewBlock` for `T#2` (e.g., S's node is briefly behind or on a slower peer).
3. A miner proposes a new tenure T' that does not build on T (i.e., it reorgs T), and S's signer evaluates `check_parent_tenure_choice` for T'. `get_globally_accepted_block_count_in_tenure(T) == 1`, so the `> 1` guard does not fire.
4. The function inspects only `T#1`'s proposal timing via `get_first_approved_block_in_tenure`; if that timing looks "poorly timed" relative to the burn-block transition, the function permits the reorg of T and calls `record_superseded_tenure(T)`.
5. S signs T' and, per `mark_tenure_superseded`, will no longer treat conflicts in T (including `T#2`) as blocking future signatures.
6. Independently, `T#2`'s already-collected 70% signature set gets pushed to (any) node and becomes globally accepted network-wide.
7. The network now has two canonical-eligible chains — one extending T via `T#2` (backed by 70% signer weight) and one extending T' (also signed by S and others) — a safety violation that the signer set's conflict-guard machinery was specifically designed to prevent, but which this particular check's use of a stale/local-only proxy for "already made progress" fails to catch.

    /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
