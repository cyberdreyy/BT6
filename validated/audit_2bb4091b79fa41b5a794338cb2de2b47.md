### Title
Repeated/replayed WebAPI trigger messages within the freshness window cause duplicate unauthorized workflow executions - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
The external report describes an attacker collecting two validly-signed oracle prices and repeatedly firing them within the `oracle_validity_period` to trigger multiple long/short positions before the price data is considered stale. The Chainlink analog is the `web_api_trigger` gateway → node pathway: a signed `TriggerRequestPayload` is accepted as long as its `timestamp` is within `MaxAllowedMessageAgeSec`, but nothing prevents the *same* validly-signed payload (or any payload from an authorized sender) from being submitted and processed multiple times inside that freshness window, causing the workflow to be triggered repeatedly.

### Finding Description
On the gateway side, `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-420`) only rejects a message if `payload.Timestamp == 0` or if it is older than `MaxAllowedMessageAgeSec` [1](#0-0) . There is no dedup on `msg.Body.MessageId`, `TriggerEventId`, or digest — a `TODO` even notes "apply allowlist and rate-limiting here" is unimplemented [2](#0-1) .

On the node side, `triggerConnectorHandler.processTrigger` (`core/capabilities/webapi/trigger/trigger.go:80-149`) validates only that the topic is allowed, the sender is in `allowedSenders`, and a per-sender rate limit is respected [3](#0-2) . It computes `TriggerEventID := body.Sender + payload.TriggerEventId` and immediately forwards a `TriggerResponse` to the workflow engine channel [4](#0-3) , with no check that this `TriggerEventId` (or message) has already been processed. As long as the rate limiter allows it and the timestamp inside the freshness window, the exact same signed trigger payload can be resubmitted an arbitrary number of times, firing the workflow execution again each time.

This mirrors the oracle bug class exactly: a validity window (`oracle_validity_period` ≈ `MaxAllowedMessageAgeSec`) is used as the sole gate, but the underlying signed artifact is not bound to single use (no monotonic ordering / nonce / replay-guard), so any authorized but otherwise unprivileged sender (or someone who captures the signed message off the wire) can multiply its effect during that window.

Note: the DON-side remote-trigger path (`core/capabilities/remote/trigger_subscriber.go`) does maintain an `ackReplayCache`/`messageCache` keyed by `(triggerEventID, workflowID, triggerID)` to dedupe duplicate broadcasts [5](#0-4) , but that mechanism protects against duplicate delivery of the *same underlying capability-DON trigger event*, not against a legitimate sender resubmitting a fresh, validly-signed `web_api_trigger` request multiple times through the legacy gateway/webapi trigger path described above.

### Impact Explanation
Each accepted trigger message causes `EmitTriggerExecutionStarted` and a full workflow execution to be started via the trigger channel [6](#0-5) . If the triggered workflow performs any state-changing or fund-moving action (as CRE workflows commonly do), an authorized-but-unprivileged sender can cause that action to execute multiple times for a single legitimate signed request, simply by resending it within the freshness window — an "unauthorized/duplicated job run" analogous to the reported repeated long/short exploitation.

### Likelihood Explanation
Any client that already qualifies as an `allowedSender` for a registered `web_api_trigger` workflow can trigger this without any additional privilege — they just need to resend the same (or their own newly minted) trigger message multiple times before `MaxAllowedMessageAgeSec` (default 120s) elapses and before hitting `rateLimiter.Allow` limits per topic/sender. Since the rate limiter is the only throttle and is configurable per workflow (and may be generously configured for legitimate burst traffic), duplicate submissions are easy to produce.

### Recommendation
Add a per-`(sender, TriggerEventId)` or per-`MessageId` replay guard (similar to `RequestReplayGuard` used in `core/capabilities/vault`) at both the gateway (`handler.go`) and node-side trigger handler (`trigger.go`) layers, rejecting reuse of the same trigger event ID/message ID within (at least) the `MaxAllowedMessageAgeSec` window, independent of the rate limiter.

### Proof of Concept
1. Register a `web_api_trigger` workflow with `allowedSenders` including the attacker's address and a lenient `RateLimiterConfig` (e.g., default burst configuration).
2. Attacker crafts and signs one `TriggerRequestPayload` with a valid `timestamp` and `trigger_event_id`.
3. Attacker sends this identical signed message to the gateway N times within `MaxAllowedMessageAgeSec`. Each call passes `HandleLegacyUserMessage`'s staleness check [7](#0-6)  and node-side `processTrigger` checks (topic allowed, sender allowed, rate limit not yet exceeded) [3](#0-2) , and each call independently emits a `TriggerResponse` to the workflow engine, running the workflow N times from one signed intent.
