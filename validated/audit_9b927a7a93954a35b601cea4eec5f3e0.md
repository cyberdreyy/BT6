### Title
Stale confirmations from removed multisig members are not purged, allowing a request to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges requests that were *created* by the member being removed; it never scans the `confirmations` map for entries where the removed member merely *confirmed* someone else's request. Those stale confirmation entries keep counting toward `num_confirmations` in `confirm`, so a request can later be executed with fewer live, authorized confirmers than the configured `K` threshold.

### Finding Description
`confirmations: LookupMap<RequestId, HashSet<String>>` stores confirmer identities (`member.to_string()`) per request [1](#0-0) . When a member is removed, `delete_member` cleans up only the requests where `r.member == member`, i.e. requests that member *created*, and their associated confirmations. It does not remove that member's confirmation entries from other requests' `confirmations` sets: [2](#0-1) 

Meanwhile, `confirm` simply checks `confirmations.len() as u32 + 1 >= self.num_confirmations` to decide whether to execute the request [3](#0-2) . It never re-validates that every string in the existing `confirmations` set still corresponds to a *current* member of `self.members`. Once a confirming member is deleted, their stale entry remains in every other pending request's confirmation set and is still counted toward the threshold.

This breaks the intended custody/authorization binding of the multisig: **confirmations counted must equal confirmations from live members**. After a removal, `count(confirmations recorded) == count(live-member confirmations) + count(stale confirmations from removed members)`, but the code treats the left side as if it were the right-hand live-member count.

### Impact Explanation
This lets a request execute with fewer live authorized confirmations than `num_confirmations`, i.e. a multisig request executed below threshold — a Critical-severity outcome per the accepted impact list (funds transfer, key/contract changes, or membership changes authorized without the required live quorum). Since `MultiSigRequestAction::Transfer`, `AddKey`, `DeployContract`, etc. are all gated the same way through `confirm`, an attacker who is a legitimate member (or colludes with one who will later be removed) can get a stale confirmation baked into a pending request, wait for that confirming member to be removed via a separate, unrelated `DeleteMember` action, and then finish confirming with fewer surviving members than the policy requires.

### Likelihood Explanation
Requires: (1) a request created by member D, (2) confirmed by member A before A is removed, (3) A subsequently removed via a `DeleteMember` request (a normal multisig operation, not an edge case), and (4) the original request R still pending (not deleted, no cooldown issue) when remaining members finish confirming it. All of these are ordinary operational flows for a long-lived multisig with membership churn (a very plausible scenario for this contract's intended use, e.g. rotating validators/employees) — no privileged bypass or malicious deployment is needed beyond normal member actions already permitted by the contract.

### Recommendation
When removing a member in `delete_member`, iterate over all pending requests' `confirmations` sets (not just requests created by that member) and strip the removed member's string identity from each. Alternatively, when counting confirmations in `confirm`, filter the confirmation set to only those confirmer strings that still exist in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy with `num_confirmations = 3`, `members = {A, B, C, D}`.
2. `D.add_request(R)` — creates request `R` (e.g. `Transfer` to an attacker-controlled receiver), `confirmations[R] = {}`.
3. `A.confirm(R)` → `confirmations[R] = {A}` (1/3).
4. `B.confirm(R)` → `confirmations[R] = {A, B}` (2/3).
5. Separately, an already-confirmed `DeleteMember{member: A}` request executes (a legitimate, unrelated multisig action) — `delete_member` only purges requests created by `A`; `R` was created by `D`, so `confirmations[R]` still contains `A`. `members` is now `{B, C, D}`.
6. `C.confirm(R)` → `confirmations[R].len() + 1 == 3 >= num_confirmations(3)` → `R` executes via `execute_request`, transferring funds, even though only `B` and `C` are live members who actually confirmed (2 live confirmations, not 3). [3](#0-2) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
