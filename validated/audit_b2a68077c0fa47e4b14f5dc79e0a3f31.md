Confirmed: `create()` has no caller restriction beyond the `MIN_ATTACHED_BALANCE` check, and the derived lockup address is a deterministic function of `owner_account_id` alone.### Title
Front-running/squatting of deterministic lockup address lets an attacker fix an owner's lockup terms before the real grantor - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` is a `#[payable]` method callable by any account, and it derives the lockup contract's `AccountId` deterministically from only `owner_account_id` (`hex::encode(&env::sha256(owner_account_id)[..20])`). Since NEAR account creation fails if the account already exists, any unprivileged attacker can pre-create this address for a target owner with attacker-chosen `vesting_schedule`, `release_duration`, `lockup_duration`/`lockup_timestamp`, and `whitelist_account_id`, permanently squatting the address the real grantor (foundation) would later try to use for that owner.

### Finding Description
The invariant that should hold is: `lockup_account_id(owner) → vesting/lockup terms chosen by owner's actual grantor`. In code, the address binding is: [1](#0-0) 

and the method has no caller restriction at all beyond a deposit floor: [2](#0-1) 

`create` is `#[payable]` and public; the only guard is `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)`, which any account — not just the NEAR Foundation — can satisfy by attaching exactly `MIN_ATTACHED_BALANCE` (3.5 NEAR). There is no `assert_called_by_foundation`, no owner-signature check, and no reservation/allow-list mechanism binding a specific `owner_account_id` to a specific caller. `owner_account_id`, `vesting_schedule`, `release_duration`, `lockup_duration`, `lockup_timestamp`, and `whitelist_account_id` are all fully attacker-controlled parameters passed straight into `LockupArgs` and forwarded to the deployed lockup contract's `new` call: [3](#0-2) 

`Promise::new(lockup_account_id.clone()).create_account()` will fail if `lockup_account_id` already exists on-chain. The callback `on_lockup_create` only checks `is_promise_success()` and, on failure, refunds the *predecessor's* deposit — it performs no comparison against any "correct" terms and cannot detect that the address was pre-squatted: [4](#0-3) 

Exploit flow: attacker learns (or predicts) that `owner_account_id` is scheduled to receive a real grant. Before the foundation calls `create(owner_account_id, ...)`, the attacker calls `create(owner_account_id, attacker_lockup_duration, attacker_lockup_timestamp, attacker_vesting_schedule, attacker_release_duration, attacker_whitelist_account_id)` attaching exactly `MIN_ATTACHED_BALANCE`. This creates and deploys the lockup contract at the exact deterministic address the real grant would have used, with terms fully chosen by the attacker (e.g., a `staking_pool_whitelist_account_id` pointing at an attacker-controlled "staking pool" contract, and a vesting/lockup schedule that unlocks funds immediately or diverts control). When the foundation later attempts the real `create` call for the same owner, `create_account()` fails because the account already exists, `on_lockup_create` returns `false`, and the foundation's deposit is refunded to it — but any subsequent transfer of the real grant's tokens to that owner's expected lockup address now lands in the attacker-controlled contract, which the ecosystem/tooling treats as "the owner's lockup."

None of the existing guards prevent this: `assert_self()` only protects the callback (already `assert_self`-guarded correctly), `is_promise_success()` only detects promise failure/success and provides no authorization check, and there is no `assert_called_by_foundation`-style check on `create` itself (unlike, e.g., staking-pool-factory's whitelist controls). The address derivation using only `owner_account_id` (with no dependency on caller identity or a commit/reveal secret from the real grantor) is the root cause.

### Impact Explanation
This is a Critical impact per the rules: "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attacker can deploy a lockup contract, at the exact address the legitimate grantor would use for a given owner, with attacker-chosen vesting schedule, release duration, and — critically — an attacker-controlled `staking_pool_whitelist_account_id`, meaning the "trusted" whitelist used by that lockup for staking operations is attacker-controlled. Any real NEAR the foundation subsequently intends for that owner (e.g., manual transfers referencing "the owner's lockup account") is routed to a contract the attacker fully parameterized and controls the trust boundaries of. This is repeatable against every distinct `owner_account_id` that has not yet had its lockup created, is low-cost (one `MIN_ATTACHED_BALANCE` = 3.5 NEAR deposit per victim), and the blast radius is any not-yet-granted employee/investor account in the ecosystem using this factory.

### Likelihood Explanation
Preconditions: attacker needs an unprivileged NEAR account with 3.5 NEAR (the `MIN_ATTACHED_BALANCE`) and knowledge (or reasonable guess) of an `owner_account_id` that is due to receive a lockup grant but hasn't yet. Given that lockup factory owner IDs (e.g., employee/investor account names) are frequently predictable or publicly known in advance (e.g. announced grants, standard naming conventions), this is highly feasible and cheaply repeatable across many target accounts, requiring no special privileges, keys, or multisig access — matching the "unprivileged attacker" threat model exactly.

### Recommendation
Restrict `create` to be callable only by `self.foundation_account_id` (i.e., add an `assert_called_by_foundation`-style check as is done in comparable factories), or otherwise bind account creation eligibility for a given `owner_account_id` to an explicit authorization/reservation issued by the real grantor before allowing an untrusted caller to deploy at that deterministic address.

### Proof of Concept
```rust
// lockup-factory/src/tests/ (new test)
#[test]
fn test_attacker_squats_owner_lockup_before_foundation() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker calls create() for the victim's owner_account_id first,
    // attaching exactly MIN_ATTACHED_BALANCE, with attacker-chosen whitelist.
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = MIN_ATTACHED_BALANCE;
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // victim owner id
        lockup_duration,
        None,
        None, // attacker could set malicious vesting_schedule here
        None,
        Some(attacker_whitelist_account_id()), // attacker-controlled whitelist
    );

    // Simulate successful account creation for attacker's squatted address.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let created = contract.on_lockup_create(
        lockup_account(), // deterministic address derived only from owner_account_id
        MIN_ATTACHED_BALANCE.into(),
        String::from("attacker.near"),
    );
    assert!(created); // attacker's contract now occupies the address

    // Foundation later attempts the legitimate creation for the same owner.
    context.predecessor_account_id = String::from(foundation_account_id());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // Simulate NEAR runtime rejecting create_account() because the account exists.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let legit_created = contract.on_lockup_create(
        lockup_account(), // SAME address as attacker's
        ntoy(35).into(),
        String::from(foundation_account_id()),
    );
    assert!(!legit_created); // foundation's deposit is refunded, address permanently
                             // occupied by attacker-parameterised contract
}
```
This demonstrates: (1) the address binding `lockup_account_id = f(owner_account_id)` is independent of caller identity, (2) an unprivileged attacker can win the race and permanently occupy the address with self-chosen terms, and (3) the legitimate grantor's subsequent `create` call fails and cannot dislodge the attacker's deployment, confirming the broken invariant.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
