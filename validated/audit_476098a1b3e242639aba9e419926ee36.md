### Title
Default recovery basis only supports a single epoch of instant-withdraw receipts — receipts left unfunded from an earlier epoch are paid at par and drain the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to a verifier hard-coded for exactly one BSB22 commitment, `defaultPendingClaimBasis` is hard-coded for exactly one epoch of unfunded instant-withdraw receipts. It adds `instantWithdrawClaimsByEpoch[epochNumber]` — a single epoch — whenever `pendingInstantWithdraws != 0`. Unfunded instant receipts can legitimately span multiple epochs (the code itself documents that startEpoch cash "covered only part of the instant queue"), so receipts recorded in an earlier epoch are silently excluded from the haircut basis yet remain fully claimable at par through `claimInstantWithdrawRequest`. They are paid out of the default recovery reserve at 100%, directly stealing recovery value owed to default-epoch claimants.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `defaultPendingClaimBasis` (lines 644–649) computes the defaulted claim basis as `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]`. Only the *current* epoch's instant claims join the haircut basis, gated on the aggregate `pendingInstantWithdraws != 0`.
- `requestInstantWithdraw` (lines 356–375) records receipts per-epoch (`instantWithdrawsRequestsByEpoch[user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`), proving the design anticipates multiple epochs — but the recovery path consumes only one.
- `claimInstantWithdrawRequest` (lines 380–393) first runs `_claimDefaultedInstantWithdrawRequest`, which clears *only* `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (lines 842–856). Any remaining balance in `instantWithdrawsRequests[user]` — i.e., receipts from older unfunded epochs — is then burned and paid **in full** via `_transferFundedClaim`.
- Those "funded" claims are paid from underlying held by the strategy, which after `finalizeDefaultRecovery` is exactly `defaultRecoveryReserve`. An old-epoch receipt therefore converts a haircut-priced recovery into a par payout.

The invariant broken is fair loss distribution: default-epoch receipts get `defaultRecoveryPrice` (e.g., 40%), while stale-epoch instant receipts get 100% from the same reserve, leaving the reserve insolvent for later claimants.

### Impact Explanation
A holder of an unfunded instant receipt from a pre-default epoch claims 100% of their basis while every default-epoch claimant receives only `defaultRecoveryPrice`. The overpayment comes directly out of `defaultRecoveryReserve`, so subsequent `_transferDefaultRecovery` calls either revert (permanent freezing of remaining recovery claims) or are underpaid. Quantified loss: up to the full unfunded earlier-epoch instant balance, i.e., `(1 - defaultRecoveryPrice) * staleInstantBasis` is stolen, and the reserve can be drained below the sum of legitimate claims.

### Likelihood Explanation
Requires `allowInstantWithdraw`, an instant queue that is only partially funded at `startEpoch` (a path the code comments explicitly acknowledge at lines 637–640), survival of that receipt into a later epoch, additional instant requests in the later epoch, and then a borrower default finalized via `finalizeDefaultRecovery`. All steps are reachable by unprivileged users through normal epoch sequencing; the funding shortfall is driven by honest borrower/manager behavior (partial liquidity at startEpoch), not attacker control of privileged roles.

### Recommendation
Track unfunded instant claim basis across *all* epochs, not just `epochNumber`. Either maintain a global `instantWithdrawClaimsTotal` that is decremented on funding/claims and included in `defaultPendingClaimBasis`, or iterate/mark all epochs carrying unfunded instant receipts during `reserveDefaultRecovery`/`finalizeDefaultRecovery`. Correspondingly, `_claimDefaultedInstantWithdrawRequest` should clear and haircut every epoch's receipt held by the user, not only `defaultRecoveryEpoch`.

### Proof of Concept
Foundry fork sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleEpochInstantReceiptDrainsRecovery() external {
    // epoch E running with allowInstantWithdraw = true
    _depositWithUser(userA, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // userA requests instant withdraw; startEpoch prefund covers only part of the queue
    vm.prank(userA);
    cdoEpoch.requestInstantWithdraw(50_000 * ONE_SCALE, address(AAtranche));
    // partial funding: collectInstantWithdrawFunds moves less than pendingInstantWithdraws
    // -> userA's claimInstantWithdrawRequest reverts (insufficient strategy balance); receipt stays

    // epoch E+1: userB files a new instant request in a different epoch
    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.prank(userB);
    cdoEpoch.requestInstantWithdraw(10_000 * ONE_SCALE, address(AAtranche));

    // borrower defaults; manager finalizes recovery at e.g. 40%
    _handleBorrowerDefaultAndFinalize(/* recovered covers 40% of basis */);

    // BUG: basis excluded userA's epoch-E receipt (instantWithdrawClaimsByEpoch[E])
    //      but userA's instantWithdrawsRequests still contains it.
    vm.prank(userA);
    cdoEpoch.claimInstantWithdrawRequest(); // pays 100% of 50_000 from recovery reserve

    // userB and normal default-epoch claimants now get less than defaultRecoveryPrice,
    // or their _transferDefaultRecovery reverts for insolvency.
}
```

Key assertion: `strategy.defaultRecoveryReserve()` decreases by the full par amount of the stale receipt while `defaultRecoveryPrice < 1e18`, proving the unhaircutted payout.
