Key finding: shell's `NewProvider` sets `features.NativeStepsViaConcreteOnly = true` (`executors/shell/shell.go` line 201), and `Build.nativeStepsBlockedWithoutConcrete()` in `common/steps.go` (lines 27-32) enforces that any executor with `NativeStepsViaConcreteOnly` must reject native-steps jobs unless `FF_CONCRETE` is on. This gate runs in `Build.executeScript` before the executor's `Run`/`Connect` is ever invoked, so a shell job cannot reach `executor.Connect` in `executors/shell/steps.go` with native steps enabled unless `FF_CONCRETE` is already on — matching what the code comment states explicitly: "Shell runs native steps only via the concrete whole-job path; run: without FF_CONCRETE is rejected in Build.executeScript" (`executors/shell/shell.go` lines 198-199).

Additionally, comparing the docker executor's `Connect` (`executors/docker/steps.go` lines 47-170), it also contains **no explicit `FF_CONCRETE`/`UseConcrete` check** — only kubernetes's `Connect` has the inline `if !s.Build.IsFeatureFlagOn(featureflags.UseConcrete)` check (`executors/kubernetes/steps.go` lines 81-84), which the code comments describe as "defense-in-depth" because "the build-level gate in Build.executeScript rejects such jobs first." So the premise that "only kubernetes and docker gate... but shell does not" is factually wrong: docker doesn't have an inline gate either, and all three executors rely on the same upstream `Build.executeScript`/`UseNativeSteps`/`nativeStepsBlockedWithoutConcrete` gate in `common/steps.go`.

Regarding the "stronger capability on shell hosts" claim: the shell executor's `Connect` simply dials a local Unix socket to an in-process step-runner (`executors/shell/steps.go` lines 44-62) that runs with the same OS-level privileges the shell executor's `Run` method already has (`executors/shell/shell.go` `Run`, lines 72-133) — i.e., the shell executor already executes arbitrary job scripts with full host privileges regardless of native steps. Native-steps dispatch via `Connect` does not grant any privilege beyond what a normal `script:` job on that shell executor already has. Kubernetes/docker's pod/container-level restrictions (image, pull policy, namespace) exist because those executors otherwise sandbox jobs inside containers — restrictions that don't apply to the shell executor's threat model in the first place (shell executor trust on a shared host is a documented, out-of-scope admin choice per the rules).

Because (1) the premise that shell skips a check the others perform is false — none of the three inline-gate on `UseConcrete` except kubernetes, and all three rely on the same `common/steps.go` build-level gate, and (2) the "stronger capability" is not real since shell already grants host-level script execution regardless of `Connect`, and (3) shell-executor-on-shared-host privilege equivalence is explicitly excluded by the rules ("Reject findings that only restate documented insecure admin choices such as ... shell executor trust on a shared host"), this does not constitute a valid finding. func (s *executor) Connect(_ context.Context) (func() (io.ReadWriteCloser, error), error) {
	if s.stepRunner == nil {
		// Only an executor built outside NewProvider reaches this.
		return nil, fmt.Errorf("shell executor was not constructed with a step-runner")
	}

	sockPath, err := s.stepRunner.ensureStarted()
	if err != nil {
		return nil, fmt.Errorf("starting step-runner: %w", err)
	}

	return func() (io.ReadWriteCloser, error) {
		conn, err := net.Dial("unix", sockPath)
		if err != nil {
			return nil, fmt.Errorf("dialing step-runner socket %q: %w", sockPath, err)
		}
		return conn, nil
	}, nil
}
