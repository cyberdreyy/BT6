### Title
Master public key fetched and request validated with expensive shared resource before authorization for MethodSecretsCreate/MethodSecretsUpdate - ([File: core/capabilities/vault/gw_handler.go])

### Summary
In `GatewayHandler.HandleGatewayMessage`, for `MethodSecretsCreate`/`MethodSecretsUpdate`, `h.getMasterPublicKey(ctx)` is called and `h.requestProcessor.ProcessRequest` performs structural validation before `AuthorizeRequest` is invoked deep inside `authorizeAndStamp`. This means an unauthenticated/unauthorized gateway client can force the node to touch the shared `cachedMasterPublicKey`/`secretsService.GetPublicKey` path and run request validation before any authorization check rejects the request.

### Finding Description
`HandleGatewayMessage` (`core/capabilities/vault/gw_handler.go:188-199`) calls `h.getMasterPublicKey(ctx)` first, then `h.requestProcessor.ProcessRequest(ctx, req, publicKey)`. Inside `ProcessRequest` (`core/capabilities/vault/gateway_vault_request_processor.go:74-86`), `processCreateSecretsRequest`/`processUpdateSecretsRequest` unmarshal params, call `p.validator.ValidateCreateSecretsRequest`/`ValidateUpdateSecretsRequest` (lines 111, 145) using the fetched `publicKey`, and only afterward call `p.authorizeAndStamp`, which is where `p.authorizer.AuthorizeRequest` (line 233) — the actual authorization check — runs.

`getMasterPublicKey` (`gw_handler.go:238-261`) does return a cheap cached copy under `h.mu.RLock()` once `h.cachedMasterPublicKey` is successfully populated, so in steady state repeated calls are inexpensive. However:
1. The ordering itself violates the stated invariant "authorization is exact and precedes resource use" — validation using the shared master public key and JSON unmarshalling/crypto-adjacent work in `ValidateCreateSecretsRequest` execute before `AuthorizeRequest` for every request, authenticated or not.
2. If `MasterPublicKeyFromSecretsService` (`gateway_vault_request_processor.go:293-311`, invoked via `secretsService.GetPublicKey`) fails or the cache has not yet been populated (e.g., during startup, key rotation, or any transient failure of the secrets service), every unauthenticated `MethodSecretsCreate`/`MethodSecretsUpdate` request re-triggers the real, uncached `secretsService.GetPublicKey` call before rejecting on authorization, because the cache is never written on error (see the early-return `nil, err` at line 249 that skips populating `h.cachedMasterPublicKey`). This is a genuine unauthenticated flood-until-authorized-check path that exercises a shared, potentially expensive resource for every attacker request.

### Impact Explanation
This corresponds to a resource-exhaustion / DoS-adjacent finding rather than a direct authentication/secret-disclosure bypass: an attacker cannot read secrets or bypass authorization for reads/writes (authorization is still eventually enforced, and no secret material or key is returned to the attacker on failure). The impact is bounded to CPU/IO amplification: forcing the node to retry `secretsService.GetPublicKey` and perform validation work on every flood request when the cache is not warm, which affects a per-node shared cache (`cachedMasterPublicKey`) and could degrade service for legitimate/other subscribers' requests during that window. This does not rise to key/secret disclosure or job/fund manipulation.

### Likelihood Explanation
Requires only an unauthenticated/unauthorized gateway client able to send `MethodSecretsCreate`/`MethodSecretsUpdate` JSON-RPC messages, which is within the "unprivileged attacker" threat model. However, the amplification only materializes when the master-key cache is not already warm (startup, key rotation, or backend failure) — in normal steady-state operation, repeated calls are cheap cache hits, significantly limiting real-world exploitability and repeatability.

### Recommendation
Move the authorization check (`AuthorizeRequest`) to occur before fetching/using the master public key and before invoking validators that use it, or perform a lightweight structural/auth pre-check first. If public-key-dependent validation must occur before authorization for architectural reasons, ensure `getMasterPublicKey` failures do not force repeated expensive calls (e.g., use a short-lived negative cache/backoff for failed lookups) so unauthenticated floods cannot repeatedly trigger the uncached `secretsService.GetPublicKey` path.

### Proof of Concept
Go unit test plan in `core/capabilities/vault/gw_handler_test.go`:
1. Construct a `GatewayHandler` with a mock `secretsService` whose `GetPublicKey` always errors (simulating unwarmed/failing cache) and a mock `Authorizer` that always rejects (`AuthorizeRequest` returns an error) with a call counter.
2. Send N `MethodSecretsCreate` requests via `HandleGatewayMessage` with garbage/unauthorized params through `gatewayConnector`.
3. Assert `secretsService.GetPublicKey` (or `MasterPublicKeyFromSecretsService`) is called N times (proportional to flood volume) rather than short-circuited by an early authorization rejection, demonstrating that unauthorized requests still trigger the shared public-key fetch path before rejection.
4. Assert the mock `Authorizer.AuthorizeRequest` is never reached in this failing-key scenario (since `getMasterPublicKey` errors out first and the response is a `gatewayErrorResponse`), confirming resource use (the public key fetch) happens independent of and prior to authorization outcome.
