### Title
Mis-indexed loss-recovery epoch lets stale `lossRecoveryPriceByEpoch` haircut later withdraw receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the haircut under the strategy's *current* `epochNumber` (line 421), but `epochNumber` is incremented inside `deposit()` during the same `stopEpoch` flow (lines 607–611). If the CDO pulls funded withdraw receipts after that increment — the ordering used in `IdleCDOEpochVariant.stopEpoch`, where the strategy `deposit` of repaid funds runs before claim-funding hooks — the loss price is written under epoch index `N+1` while all pending receipts were recorded under `lastWithdrawRequest == N` (lines 282, 293). The epoch-keyed recovery data is therefore indexed one slot off, analogous to the out-of-bounds index in CVE-2017-15047: every lookup lands on the wrong epoch bucket.

### Finding Description
Two symmetric corruptions follow from `lossRecoveryPriceByEpoch[N+1]` being set while receipts live under epoch `N`:

1. **Epoch-N receipts bypass the haircut entirely.** `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` = `lossRecoveryPriceByEpoch[N]` = 0 and returns 0 (lines 789–792). `_claimFundedWithdrawRequest` then pays the full `withdrawsRequests[_user]` at par (lines 338–349), even though the vault only received the post-loss `_amount < pendingBasis` via `collectWithdrawFunds`. Early claimants drain the funded reserve at par; the rest of the epoch-N claimants' `_transferFundedClaim` calls revert on insufficient balance — permanent freezing of their funded claims.

2. **Epoch-N+1 requests inherit a phantom haircut.** During the new buffer of epoch `N+1`, any user calling `requestWithdraw` gets `lastWithdrawRequest = N+1` and `withdrawsRequestsByEpoch[user][N+1] != 0` (lines 282–293). Their next `claimWithdrawRequest` routes into `_claimLossAdjustedWithdrawRequest`, which applies the stale `lossRecoveryPriceByEpoch[N+1]` to a receipt that was *fully funded* by the next `collectWithdrawFunds` call — the user is paid `claimBasis * stalePrice / RECOVERY_FULL` and the difference is stranded in the vault (lines 794–800). The guard at lines 263–270 also bricks any further `requestWithdraw` from that user until they accept the spurious haircut.

The existing guard at line 416 (`defaultRecoveryInitialized`) and the zero-price revert at line 419 do not prevent the mis-indexing; they only check the value, not the key.

### Impact Explanation
Broken invariant: one receipt one payout, and loss waterfall isolation. Either (a) epoch-N pending receipts are over-paid at par from a haircutted reserve, causing vault insolvency and revert-DoS for the last claimants of that epoch, or (b) innocent epoch-N+1 withdrawers are force-haircut on fully funded claims, with the confiscated amount permanently locked in the strategy contract. Quantified loss is `pendingBasis - _amount` (the realized stop-epoch loss) misapplied across the wrong epoch's claimants — in case (b) up to `(1 - lossRecoveryPrice) *` each victim's claim basis.

### Likelihood Explanation
Requires only a standard `stopEpochWithDuration(_lossAmount)` with `0 < _lossAmount < totalBasis` — an honest manager/borrower action, not an attacker precondition. Once it fires, every subsequent withdrawal request in the new epoch is affected. Attacker involvement is limited to being an ordinary KYC'd tranche holder whose receipt is either over- or under-paid. The sole uncertainty I could not fully resolve within available context is the exact call order in `IdleCDOEpochVariant.stopEpochWithDuration`/`_beforeStopEpoch` between the strategy `deposit()` that bumps `epochNumber` and `collectWithdrawFunds`; the comment at line 608 ("deposit done on stopEpoch (before setting the var to false)") confirms the bump happens mid-stopEpoch, and funding of withdraw receipts is naturally settled afterward, which is the vulnerable ordering.

### Recommendation
Index the loss price by the request epoch, not the post-increment epoch: in `collectWithdrawFunds`, persist `lossRecoveryPriceByEpoch` under the epoch in which the receipts were created (e.g., snapshot `pendingWithdrawEpoch` when requests accrue, or use `epochNumber - 1` when called after the bump inside stopEpoch). Alternatively, have the CDO call `collectWithdrawFunds` strictly before the `deposit()` that increments `epochNumber`, and assert `epochNumber == lastWithdrawRequest` alignment in `_claimLossAdjustedWithdrawRequest`.

### Proof of Concept
```solidity
// Fork test against IdleCDOEpochVariant + IdleCreditVault (non-APR0 mode).
function testLossRecoveryMisindexedEpoch() external {
    // --- Epoch N: users deposit, request withdraw ---
    uint256 amt = 100e6;
    uint256 trA = _depositWithUser(userA, amt);   // AA tranche tokens
    _requestWithdrawWithUser(userA, trA);          // lastWithdrawRequest[A] = N
    // strategy.epochNumber() == N
    // strategy.withdrawsRequestsByEpoch(userA, N) == amt

    // --- stopEpoch with partial loss: borrower funds < pendingWithdraws ---
    // Inside stopEpoch: strategy.deposit(...) executes while isEpochRunning(),
    // so epochNumber N -> N+1 BEFORE collectWithdrawFunds is reached.
    _stopCurrentEpochWithLoss(pendingBasis / 2); // collectWithdrawFunds(pending/2)
    // BUG: lossRecoveryPriceByEpoch[N+1] = 0.5e18  (should be [N])
    assertEq(strategy.lossRecoveryPriceByEpoch(N), 0);
    assertGt(strategy.lossRecoveryPriceByEpoch(N + 1), 0);

    // --- Claim 1: userA paid AT PAR from a 50%-funded reserve ---
    vm.prank(userA);
    cdoEpoch.claimWithdrawRequest(); // _claimFundedWithdrawRequest path, no haircut
    // vault balance now under-collateralized for remaining epoch-N claimants

    // --- Claim 2: userB (same epoch N) reverts — insolvency DoS ---
    vm.expectRevert();
    vm.prank(userB);
    cdoEpoch.claimWithdrawRequest();

    // --- Claim 3: userC requests in buffer of epoch N+1, gets phantom haircut ---
    uint256 trC = _depositWithUser(userC, amt);
    _requestWithdrawWithUser(userC, trC); // lastWithdrawRequest[C] = N+1
    _stopCurrentEpochNoLoss();            // fully funds C's receipt
    vm.prank(userC);
    cdoEpoch.claimWithdrawRequest();
    // received == amt * 0.5, remainder stranded in strategy
    assertLt(underlying.balanceOf(userC), amt);
}
```
