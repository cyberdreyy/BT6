### Title
Builder withdrawal amount computed from stale, unadjusted balance can overcredit the execution layer beyond the builder's actual balance - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builders_sweep_withdrawals` and `get_builder_withdrawals` compute a builder's withdrawal `amount` from the raw, un-adjusted `builder.balance` / a previously queued withdrawal amount, without subtracting withdrawals for the *same builder* already queued earlier in the same `get_expected_withdrawals` batch. This is the exact bug class from the report: an asset amount is committed to a withdrawal payload while the same backing balance is (or is about to be) simultaneously committed to another withdrawal, producing a total declared withdrawal amount that exceeds the builder's real balance.

### Finding Description
For validators, `get_pending_partial_withdrawals` and `get_validators_sweep_withdrawals` both call `get_balance_after_withdrawals(state, validator_index, all_withdrawals)` before computing an amount — this explicitly subtracts withdrawals already queued earlier in the same batch for that validator: [1](#0-0) [2](#0-1) 

For builders, no such adjustment exists. `get_builder_withdrawals` iterates `state.builder_pending_withdrawals` and emits `withdrawal.amount` verbatim for each entry, even if multiple entries exist for the same `builder_index`: [3](#0-2) 

`get_builders_sweep_withdrawals` then, independently, emits **the full raw `builder.balance`** as the withdrawal amount whenever `builder.withdrawable_epoch <= epoch and builder.balance > 0` — it never checks `prior_withdrawals` (the `all_withdrawals` list is computed but unused for balance adjustment) to see if that same builder already has withdrawal(s) queued earlier in `builder_pending_withdrawals` for this exact batch: [4](#0-3) 

Both lists are combined in `get_expected_withdrawals`, which calls `get_builder_withdrawals` first and `get_builders_sweep_withdrawals` third, using the *same* pre-block `state` for both (no intermediate deduction): [5](#0-4) 

`apply_withdrawals` only protects the **CL-side state** (`state.builders[*].balance`) from underflow, by capping the *deduction* to the currently remaining balance at the moment each withdrawal is applied: [6](#0-5) 

However, `process_withdrawals` requires the **payload's declared withdrawal amounts** (`payload_expected_withdrawals`/`expected.withdrawals`, i.e. the un-capped, stale-computed amounts) to be exactly honored on the execution layer: [7](#0-6) 

The EL credits `withdrawal.amount` for each entry unconditionally to `withdrawal.address` — it has no visibility into CL-side capping; it only sees the list of `(address, amount)` pairs it must apply. Thus, if the CL emits two `Withdrawal` entries for the same builder whose combined `amount` exceeds the builder's actual balance (because the sweep's amount was computed from stale, unadjusted `builder.balance`), the EL will credit more total Gwei to the builder's/fee-recipient's addresses than the builder ever had — Gwei created from nothing on the EL side, even though the CL-side `builder.balance` field itself never goes negative.

This mirrors the reported bug precisely: the CL's internal ledger (`builder.balance` reduction, analogous to burning `elyAssets`) is self-consistent, but the *externally paid-out amount* (analogous to `getTotalAssetTVL()`) is computed from a stale snapshot that double-counts the same backing balance across two withdrawal entries in the same batch.

### Impact Explanation
This breaks the equality "Gwei paid out to an address == Gwei actually backing it." If reachable, it results in the execution layer crediting more total value than the builder ever deposited — a direct Critical-severity issue (Gwei created / paid to unintended extent), since it is `state.balances`-equivalent value manufactured out of nothing on the EL side while the CL's bookkeeping appears locally consistent (balance capped at zero, no assert failure).

### Likelihood Explanation
Reaching the specific overlap (a builder simultaneously having an entry in `state.builder_pending_withdrawals` *and* satisfying the sweep condition `withdrawable_epoch <= epoch and balance > 0` in the same block) requires a specific sequencing of builder-exit and builder-payment-settlement events. `process_builder_exit_request` blocks voluntary exit while `get_pending_balance_to_withdraw_for_builder != 0` (i.e., while payments are outstanding) at the moment of the exit request: [8](#0-7) 

This means an *exit request submitted while a payment is pending* is rejected. However, I was unable to fully confirm/deny with certainty whether a builder that has already had its exit initiated (i.e., `withdrawable_epoch` already set to a future epoch) can *still* be treated as "active" and permitted to submit further bids (via `can_builder_cover_bid`/`is_active_builder`) before that `withdrawable_epoch` arrives — I located `is_active_builder` usages but could not retrieve its exact definition within the available tool budget. If `is_active_builder` returns `True` for the whole window up to `withdrawable_epoch`, the sequencing (exit → new bid → payment settles into `builder_pending_withdrawals` while `withdrawable_epoch` also becomes reachable) is directly constructible by a single builder acting alone, making this a real, self-triggerable defect rather than requiring a coalition. This uncertainty should be resolved by examining `is_active_builder`'s exact definition, which the index did not surface in this pass.

### Recommendation
Compute the builder-sweep withdrawal amount using a balance adjusted for all `prior_withdrawals` targeting the same `builder_index` within the current `get_expected_withdrawals` call, analogous to `get_balance_after_withdrawals` for validators — i.e., subtract from `builder.balance` any amounts already queued for this builder via `get_builder_withdrawals` (and any other prior list) before deciding the sweep amount, and skip/zero the sweep withdrawal if the adjusted balance is not positive.

### Proof of Concept
Not fully constructible without confirming `is_active_builder`'s exact semantics (see Likelihood Explanation). Conceptually:
1. Builder `B` has `balance = 10e9` Gwei and a settled entry in `state.builder_pending_withdrawals` for `10e9` Gwei (from a previously quorum-approved bid payment awaiting payout).
2. `B.withdrawable_epoch <= current_epoch` (exit already initiated and matured) while the pending withdrawal above still sits unprocessed in the same block's `get_expected_withdrawals` call.
3. `get_builder_withdrawals` emits `Withdrawal(amount=10e9, address=F1)`.
4. `get_builders_sweep_withdrawals` independently emits `Withdrawal(amount=10e9, address=B.execution_address)` because it reads raw `builder.balance` (still `10e9`, unadjusted for step 3's queued withdrawal): [9](#0-8) 
5. Total declared withdrawals for `B` = `20e9` Gwei, while `B` only ever held `10e9` Gwei. `apply_withdrawals` caps the CL-side `state.builders[B].balance` reduction so it never goes negative, but `payload_expected_withdrawals` (and thus the execution payload's `withdrawals` field, which the EL unconditionally applies) still declares `20e9` Gwei paid out — double the builder's actual backing.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
