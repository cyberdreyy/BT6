### Title
ERC4626 liquidity shortfall injected into `onStopEpoch` lets any external vault user revert and stall `stopEpoch` — temporary freezing of all LP funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The external bug is argv injection: an attacker-controlled field (`--gtk-module=PATH` inside a PDF link destination) is passed unsanitized through a trusted launcher and turns into code loaded into the victim process. The analog in idle-tranches is the programmable-borrower stop path: `IdleCDOEpochVariant.stopEpoch` unconditionally calls `ProgrammableBorrower.onStopEpoch`, which in turn calls `vault.withdraw(shortfall, …)` on the external ERC4626 vault and `revert StopEpochVaultLiquidityUnavailable()` whenever the withdrawal fails while shares still "cover" the shortfall on paper. An unprivileged user of that ERC4626 vault (a role explicitly allowed by the threat model) can inject the failing condition — withdrawing the vault's free liquidity — so the privileged epoch-stop flow reverts every time it is invoked, even though the share price still reports full coverage.

### Finding Description
In `ProgrammableBorrower.onStopEpoch`, when the amount the CDO must pull exceeds on-hand cash, the contract does:

- `if (shortfall > _currentVaultAssets()) return true;` — pass-through to the default path only when shares *economically* under-cover the shortfall
- `try vault.withdraw(shortfall, address(this), address(this)) … catch { revert StopEpochVaultLiquidityUnavailable(); }` [1](#0-0) 

This splits two different conditions that ERC4626 does not guarantee are equal:

- `convertToAssets(shares)` values the position at share price — unaffected by free liquidity if the vault lends assets out (Morpho/Aave-style vaults, or any vault with a borrow sleeve).
- `vault.withdraw` succeeds only if `totalAssets() - borrowed >= shortfall`.

So an attacker who is merely a *depositor/user of the same ERC4626 vault* (or who induces the state via a large withdrawal in the same block via flash-funded liquidity) can drive free liquidity below `shortfall` while `_currentVaultAssets()` still reports ≥ `shortfall`. Every `stopEpoch` call then reverts inside the hook. The honest borrower cannot fix this by repaying the credit facility — repayments land on `ProgrammableBorrower`, not in the vault; only vault-side borrowers repaying (out of this protocol's control) or fresh deposits restore liquidity. `emergencyExitVault` (line 361) has the same problem — `vault.redeem` reverts identically when liquidity is short, so it offers no escape.

The parallel to the CVE is structural: a trusted intermediary (`g_app_info_create_from_commandline` / `stopEpoch`) consumes attacker-shaped input (PDF link fields / ERC4626 liquidity state) without distinguishing "data" from "capability", letting a low-privilege party convert a passive input into control over a privileged code path (dlopen / forced revert of epoch settlement).

### Impact Explanation
Temporary freezing of all LP funds for the duration of the liquidity shortage. While `stopEpoch` reverts:

- Tranche holders cannot `claimWithdrawRequest` — pending receipts stay unfunded because `collectWithdrawFunds` is only invoked by the CDO during a successful stop [2](#0-1) 
- New epochs cannot start; `pendingWithdraws`, `pendingInstantWithdraws`, and tranche accounting are stuck mid-epoch. Loss is quantifiable as the full NAV of the affected CDO (all AA + BB deposits plus accrued interest) being frozen, plus the attacker's option to repeat the drain every time liquidity returns, extending the freeze indefinitely for the cost of vault-share capital.

Caveat: this requires a vault where share valuation and free liquidity diverge (a lending-sleeve ERC4626); for a vault that is just a passive asset holder, draining liquidity also drops `convertToAssets`, and the `shortfall > _currentVaultAssets()` pass-through correctly routes to default handling instead. I could not confirm within the iteration budget whether `IdleCDOEpochVariant.stopEpoch` wraps the hook call in try/catch or exposes an alternative stop/default entry that bypasses `onStopEpoch` — if such a bypass exists and is callable by owner/guardian, the freeze window shrinks to the time until they invoke it.

### Likelihood Explanation
- Attacker requirement is minimal: any EOA able to hold/redeem shares of the configured ERC4626 vault — no KYC, no privileged role, matching the allowed "user of the programmable borrower's ERC4626 vault" attacker class.
- The revert is deterministic once free liquidity < `shortfall` ≤ `convertToAssets(shares)`, a state an attacker can create in a single `vault.withdraw`/`redeem` transaction timed against the scheduled epoch end.
- Mitigating factors: the state is externally repairable (any vault depositor can refill liquidity, including the protocol itself via `emergencyExitVault` attempts on other venues or direct deposit into the vault), and large vaults make draining expensive but not impossible — the attacker only needs to remove liquidity for the block(s) in which `stopEpoch` is attempted, repeatable per attempt.
- Existing guards do not stop it: `_onlyIdleCDO`, `nonReentrant`, `epochPendingWithdraws` reservation (line 353, which only gates `borrow`), and the `shortfall > _currentVaultAssets` check all pass while the vault still reverts on withdrawal.

### Recommendation
- Treat "covered by shares" and "withdrawable now" separately: on `vault.withdraw`/`redeem` failure, `return true` (or a distinct soft-failure code) and let the subsequent `transferFrom` to IdleCDO fail naturally into the default path, rather than reverting inside the hook. Concretely, remove or soften the `catch { revert StopEpochVaultLiquidityUnavailable(); }` at lines 251–253, or escalate to a redeemable-shares hand-off so the CDO can mark the position and default.
- Alternatively cap `shortfall` at `vault.maxWithdraw(address(this))` (ERC4626 exposes it precisely for this) and treat the remainder as a covered-but-illiquid default, so the honest-manager default flow decides the outcome instead of the external vault's transient liquidity.

### Proof of Concept
Foundry fork sketch (no mocks — needs a real lending-sleeve ERC4626, e.g. a Morpho vault, as `vault`):

```solidity
// assume: cdoEpoch, programmableBorrower, vault, underlying wired per factory
// epoch running, borrower drew nothing, all pool assets sit in `vault`

// 1. attacker (random EOA) deposits 1 wei equivalent into vault to get shares,
//    then — more realistically — atomically borrows/redeems vault free liquidity
//    so vault.totalAssets() - borrowed < stopEpoch shortfall
uint256 shares = IERC4626(vault).balanceOf(address(programmableBorrower));
uint256 need   = cdoEpoch.expectedPullAmount(); // _amountRequired
vm.prank(attacker);
IERC4626(vault).withdraw(IERC4626(vault).maxWithdraw(vaultLiquidityHolder) , attacker, attacker);
// precondition: convertToAssets(shares) >= need still true (share price intact)

// 2. honest manager calls stopEpoch -> onStopEpoch -> vault.withdraw reverts
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch();

// 3. LP who requested withdraw last epoch cannot claim; funds frozen
vm.prank(lp);
vm.expectRevert(); // receipt never funded
cdoEpoch.claimWithdrawRequest();

// 4. emergencyExitVault reverts too — no privileged escape via the same vault
vm.prank(owner);
vm.expectRevert();
programmableBorrower.emergencyExitVault(0);
```

Note on confidence: steps 1–3 follow directly from the code read; whether step 2's revert propagates fatally through `IdleCDOEpochVariant.stopEpoch` (vs being caught or having an alternate default entry point) was not verifiable in the available iterations — `IdleCDOEpochVariant.sol` contains `onStopEpoch` call sites but the surrounding handling could not be inspected.
