### Title
Cross-workflow HTTP response cache confusion due to missing WorkflowID in cache key - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's `responseCache` used by the HTTP Actions handler is documented and intended to provide per-workflow cache isolation, but the cache key is derived from `gateway.OutboundHTTPRequest.Hash()`, which is proven by the test suite to be identical for requests differing only in `WorkflowID`. This is analogous to the AdapterVault bug class: a resource that must be uniquely scoped/attributed (per-strategy asset vs. per-workflow cache entry) is instead aggregated/shared across distinct logical owners because the code does not check/incorporate the unique identifier, causing incorrect (here, cross-workflow) results to be returned.

### Finding Description
The `responseCache.Fetch`/`Set`/`isExpiredOrNotCached` methods key the cache map solely by `req.Hash()`: [1](#0-0) [2](#0-1) 

The package README explicitly states the intended design invariant: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage." [3](#0-2) 

However, the unit test `TestRequestHash` explicitly demonstrates that `Hash()` ignores `WorkflowID` (two requests differing only by `WorkflowID` produce the *same* hash), while it does incorporate `WorkflowOwner`: [4](#0-3) 

This means any two different workflows belonging to the same owner (`WorkflowOwner`), issuing HTTP Action requests with the same method/URL/headers/body (a very plausible scenario — e.g. re-used templated request definitions, common API calls), will collide on the same cache key. The request enters the cache via `makeOutgoingRequest`, which calls `h.responseCache.Fetch(...)`/`Set(...)` keyed only by this hash, with no workflow-ID discriminator: [5](#0-4) 

This is the same bug class as the AdapterVault finding: the design assumes a value (asset / cache slot) is uniquely attributable to one logical entity (strategy / workflow), but the code that reads/writes it does not check or enforce that uniqueness, so data belonging to one entity is silently reused for another.

### Impact Explanation
An unprivileged workflow (belonging to the same `WorkflowOwner`, e.g. a second workflow deployed by the same DON member/owner) can receive an HTTP response that was actually fetched/cached on behalf of a *different* workflow. This breaks the documented workflow isolation guarantee and constitutes cross-user/cross-workflow response confusion: sensitive data (e.g., secrets, tokens, or account-specific payloads returned by an external HTTP API for one workflow) intended only for one workflow could be served to another workflow that happens to issue a request with the same method/URL/headers/body. Depending on how workflows use HTTP Action outputs (e.g., driving downstream on-chain actions or decisions), this could also lead to a workflow acting on stale/foreign data, or one workflow's requests populating the cache that another, less-trusted workflow of the same owner subsequently reads.

### Likelihood Explanation
Likelihood is elevated because:
- `WorkflowOwner` is a common denominator across many workflows deployed by the same operator/owner, so collisions do not require any adversarial action, just two co-owned workflows hitting the same endpoint with matching request shape.
- Caching (`CacheSettings.Store`/`MaxAgeMs`) is a normal, documented feature of the HTTP Action capability, not an edge case, so the vulnerable code path is reached under regular usage.
- No authentication bypass is needed; it's purely a cache-key collision reachable by any workflow author whose workflows share an owner.

### Recommendation
Include `WorkflowID` (in addition to method, URL, headers, body, and any other request-defining fields) in the cache key computation so cache entries are strictly scoped per workflow, matching the documented "Workflow Isolation" invariant. Add/extend `Hash()` (or wrap it in `responseCache` with a compound key of `workflowID + req.Hash()`) and update `TestRequestHash` to assert the corrected behavior (different `WorkflowID` → different cache key).

### Proof of Concept
1. Workflow A and Workflow B are both owned by the same `WorkflowOwner` on the CRE gateway.
2. Workflow A issues an `OutboundHTTPRequest` to `GET https://api.example.com/user-data` with `CacheSettings.Store = true`. The gateway's `makeOutgoingRequest` fetches the response and stores it via `h.responseCache.Set(req, outboundResp)`, keyed by `req.Hash()` (workflow-agnostic).
3. Workflow B later issues an `OutboundHTTPRequest` with the identical `Method`/`URL`/`Headers`/`Body` (but a different `WorkflowID`, same `WorkflowOwner`) and `CacheSettings.MaxAgeMs > 0`.
4. `responseCache.Fetch` computes the same `cacheKey := req.Hash()` (per `TestRequestHash`'s "different workflowID results in same Hash" assertion) and returns Workflow A's cached response to Workflow B — without ever calling the HTTP client.
5. This is directly reproducible by adapting the existing test `TestRequestHash` (`response_cache_test.go` lines 139-149) plus `TestFetch` to show that a `Fetch` call with a different `WorkflowID` but otherwise identical request returns the previous workflow's cached data.

// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	if err != nil {

	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{

		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)

			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
