### Title
Cross-user response hijack via unvalidated attacker-controlled `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each user's callback in a global map keyed solely by the attacker/user-supplied `msg.Body.MessageId`, with no per-user namespace and no collision check, silently overwriting any existing entry with the same ID. Because `handleWebAPITriggerMessage` looks up and deletes by that same shared key and delivers the *first* matching node response to whatever callback is currently registered under it, an attacker who submits a request with a `MessageId` equal to another concurrently in-flight user's `MessageId` can capture or clobber that other user's response delivery.

### Finding Description
`ValidatedMessageFromReq` (`core/services/gateway/handlers/common/message_util.go:36-58`) sets `m.Body.MessageId = req.ID`, i.e. the JSON-RPC request ID supplied by the caller becomes `msg.Body.MessageId` directly, with no server-side uniqueness enforcement or per-user prefixing. [1](#0-0) 

In `handler.HandleLegacyUserMessage`, the handler registers the caller's `Callback` under this attacker-controlled key without checking whether an entry already exists:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [2](#0-1) 

Later, `handleWebAPITriggerMessage` pulls (and deletes) whatever callback is currently stored for that `MessageId` and routes the first node response to it, with no verification that the response actually corresponds to the request that originally registered that callback:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()

if found {
    codec := api.JsonRPCCodec{}
    return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
}
``` [3](#0-2) 

Exploit flow: Victim A submits a `web_api_trigger` request with `MessageId = "X"`; the handler stores A's `callback` at `savedCallbacks["X"]` and forwards the request to all DON members. Before a node responds, Attacker submits their own `web_api_trigger` request also with `MessageId = "X"` (fully within their control, since it's just the JSON-RPC request ID); this overwrites `savedCallbacks["X"]` with the attacker's own `callback`, silently discarding A's registration — no error, no rejection. When any node later responds with `MessageId = "X"` (which could be the response to A's original request, since DON nodes process and echo back whatever `MessageId` was in the message they received), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds the attacker's callback (last writer wins), deletes the entry, and delivers that response to the attacker instead of to victim A. The comment "Send first response from a node back to the user, ignore any other ones" at handler.go:155 highlights that the code already accepts a race/first-writer-wins model for responses, but does not defend the *registration* step against last-writer-wins collisions.

There is no allowlist/auth check in `HandleLegacyUserMessage` that would prevent this — the `// TODO: apply allowlist and rate-limiting here` comment at handler.go:384 confirms rate limiting/authorization on user-side requests is not yet implemented for this path. [4](#0-3) 

### Impact Explanation
This is a cross-user response confusion / hijack: an unauthenticated or low-privileged gateway user can cause another concurrent user's webAPI trigger response (which may include HTTP response bodies, headers or other data returned to that node's callback) to be delivered to the attacker's HTTP client, or cause the victim's request to receive no response (denial of delivery) because the map entry was deleted by an unrelated response. This maps to the "cross-user response confusion" isolation violation described in the audit scope, potentially leaking data intended for another user's session.

### Likelihood Explanation
The precondition is trivial: any gateway user (unauthenticated per current TODO, or otherwise unprivileged) can submit their own `web_api_trigger` request choosing an arbitrary `MessageId` string. The only requirement is timing the attacker's request to land after the victim's initial registration but before the corresponding node response arrives back at the gateway — a realistic window given `MaxAllowedMessageAgeSec` allowances and DON round-trip latency. No cryptographic or unpredictable component protects `MessageId` uniqueness across users, so repeatable exploitation is feasible by simply guessing or observing a victim's chosen ID (e.g. via a public dApp/tooling using sequential/fixed IDs like `"12345"`, as seen in test/dev fixtures) and racing a duplicate submission.

### Recommendation
Reject registration if `msg.Body.MessageId` already has a live entry in `savedCallbacks` (return an error response to the caller, e.g. `api.HandlerError` "duplicate message id in flight"), instead of silently overwriting the existing callback in `HandleLegacyUserMessage`. Additionally consider namespacing the `savedCallbacks` key by the requesting user identity/connection (e.g. hash of sender + MessageId) so collisions across different callers are structurally impossible, and validate that a node's response actually matches the outbound request context (e.g. echoing a gateway-generated correlation ID/nonce or the sender identity) rather than trusting the raw client-supplied `MessageId` as the sole correlation key.

### Proof of Concept
Add a test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Create handler with mocked `handlers.DON` and `nodeAddr`.
2. Register two distinct `handlers.Callback` mocks (`cbA` for victim, `cbB` for attacker), each expecting `SendResponse` at most once.
3. Call `h.HandleLegacyUserMessage(ctx, msgA_with_MessageId_X, cbA)` — assert `h.savedCallbacks["X"].Callback == cbA`.
4. Call `h.HandleLegacyUserMessage(ctx, msgB_with_same_MessageId_X, cbB)` — assert the second call is rejected (e.g., returns an error response via `cbB.SendResponse` indicating duplicate ID) and `h.savedCallbacks["X"].Callback` still equals `cbA` (not silently overwritten).
5. Simulate a node response for `MessageId = "X"` via `h.handleWebAPITriggerMessage` and assert it is delivered to `cbA` (victim), never to `cbB` (attacker) — currently this assertion fails because step 4 overwrites the entry, proving the vulnerability.
