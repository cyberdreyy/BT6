### Title
`parse_signers` uses an instruction-account-count heuristic instead of on-chain multisig detection, allowing a crafted instruction to be reported with a fabricated `multisigOwner`/`owner` and `signers` list that does not match the account that actually authorized the instruction - (File: `transaction-status/src/parse_token.rs`)

### Summary
`parse_signers` decides whether an SPL-Token/Token-2022 instruction used a single owner/authority or a multisig purely by comparing `accounts.len()` to `last_nonsigner_index + 1`, i.e. by counting how many account indices the attacker chose to put in the instruction. The real on-chain program (`validate_owner` in spl-token/spl-token-2022) instead decides multisig-vs-single by inspecting the *runtime account data* of the owner account (whether it is a `Multisig`-sized account owned by the token program), which the parser never has access to. This divergence lets an attacker construct an instruction whose parsed JSON (`owner`/`authority` vs `multisigOwner`+`signers`) does not correspond to the actual authorization semantics used on-chain.

### Finding Description
`parse_signers` is called from every token-instruction parser (`Approve`, `Transfer`, `Revoke`, `MintTo`, `Burn`, `CloseAccount`, `SetAuthority`, etc.) with a fixed `last_nonsigner_index`: [1](#0-0) 

```rust
fn parse_signers(map, last_nonsigner_index, account_keys, accounts, owner_field_name, multisig_field_name) {
    if accounts.len() > last_nonsigner_index + 1 {
        // treat accounts[last_nonsigner_index] as a multisig, remaining accounts as signers
    } else {
        // treat accounts[last_nonsigner_index] as the direct owner/authority
    }
}
```

This decision is made solely from the length of the `instruction.accounts` array that the attacker supplies when building the transaction message, e.g. for `Approve`: [2](#0-1) 

The attacker fully controls `instruction.accounts` (a `&[u8]` of index into `account_keys`) when constructing the message, so they can:

1. Submit `Approve` with `accounts = [source, delegate, X, Y]` (4 accounts, so `4 > 2+1`). `parse_signers` will emit `multisigOwner = X` and `signers = [Y]`, even though `X` is not actually a `Multisig`-typed account on-chain. On-chain, `validate_owner` checks `owner_account_info.data_len() == Multisig::LEN` and `owner_account_info.owner == token_program_id` to decide multisig mode; if `X` is not really a multisig account, the real program instead falls into the single-signer branch and requires `X` itself to be a signer, ignoring `Y` entirely. If `X` did sign, the transaction succeeds on-chain as a single-owner approval, but the parsed output falsely reports `Y` as a contributing "signer" and mislabels the authorizing key's role as `multisigOwner` rather than `owner`.
2. Conversely, submit exactly 3 accounts (`accounts.len() == last_nonsigner_index + 1`) where `accounts[2]` *is* a genuine on-chain `Multisig` account. The parser takes the `else` branch and reports it as a plain `owner`, hiding the fact that it is a multisig and omitting the `signers` field entirely, even though on-chain (if additional signer accounts had been supplied) it would need M-of-N signer approval.

The check that gates entry into `parse_signers` only verifies a minimum account count (`check_num_token_accounts`), not the identity/type of the account at `last_nonsigner_index`, so no existing guard prevents this mismatch: [3](#0-2) 

Because `solana-transaction-status`'s parsing operates purely on the compiled instruction/message (no access to the referenced account's actual on-chain data at parse time), it cannot replicate the runtime `validate_owner` check, and instead relies on an account-count convention that honest client libraries follow but that an adversarial transaction author is free to violate.

### Impact Explanation
This falls in the "Decoder misreporting" category called out in the audited scope: `getTransaction`/`getBlock` with `jsonParsed` encoding will return an `approve`/`transfer`/`burn`/etc. instruction whose `owner`/`authority`/`multisigOwner`/`signers` fields do not accurately reflect which account(s) actually authorized the instruction on-chain. Downstream integrators (explorers, indexers, compliance tools) that trust the parsed `signers`/`multisigOwner`/`owner` fields as an accurate record of authorization can be misled about which key(s) approved a token movement.

### Likelihood Explanation
Fully attacker-controlled: the attacker only needs to choose the ordering/length of `instruction.accounts` when building their own transaction and submit it via the normal transaction-submission path; no validator, leader, or staked-node privileges are required. Retrieval is via a single `getTransaction`/`getBlock` RPC call with `jsonParsed` encoding, well within the one-call-per-slot budget. The technique is deterministic and trivially repeatable for every affected instruction variant that calls `parse_signers` (Approve, Transfer, Revoke, MintTo, Burn, CloseAccount, FreezeAccount, ThawAccount, SetAuthority, checked variants, and the confidential-transfer extension instructions).

### Recommendation
Either (a) document explicitly that `owner`/`multisigOwner`/`signers` in parsed token instructions are a best-effort heuristic based on instruction shape and are not authoritative proof of on-chain authorization (least invasive), or (b) have the parser fetch/pass in the actual account data for the owner account (data length + owner program) when available, so the multisig-vs-single decision mirrors `validate_owner`'s actual on-chain rule rather than inferring it from account-list length alone.

### Proof of Concept
Add a unit test in `transaction-status/src/parse_token.rs` alongside the existing `test_parse_token` tests:

```rust
#[test]
fn test_approve_misreports_owner_as_multisig() {
    let program_id = spl_token_2022_interface::id();
    let source = Pubkey::new_unique();
    let delegate = Pubkey::new_unique();
    let plain_signer_owner = Pubkey::new_unique(); // NOT a real multisig account on-chain
    let bogus_extra_account = Pubkey::new_unique(); // arbitrary account, unrelated to authorization

    // Build Approve with 4 accounts: source, delegate, owner, extra
    // (mirrors accounts=[source, delegate, ownerOrMultisigPlaceholder, extra])
    let ix = spl_token_2022_interface::instruction::approve(
        &program_id,
        &source,
        &delegate,
        &plain_signer_owner,
        &[], // no additional real multisig signer keys supplied to the builder
        100,
    )
    .unwrap();
    // Manually append an extra account index to simulate the attacker padding accounts
    let mut ix = ix;
    ix.accounts.push(solana_instruction::AccountMeta::new_readonly(bogus_extra_account, false));

    let message = Message::new(&[ix], None);
    let compiled_instruction = &message.instructions[0];
    let parsed = parse_token(
        compiled_instruction,
        &AccountKeys::new(&message.account_keys, None),
    )
    .unwrap();

    // Parser reports a multisig owner + signers, even though `plain_signer_owner`
    // is not an on-chain Multisig account and the real validate_owner() would
    // require `plain_signer_owner` itself to sign (single-owner path), ignoring
    // `bogus_extra_account` entirely.
    assert!(parsed.info.get("multisigOwner").is_some());
    assert!(parsed.info.get("owner").is_none());
    assert_eq!(
        parsed.info["signers"],
        json!([bogus_extra_account.to_string()])
    );
}
```

Expected assertion failure/finding: the parsed JSON claims a multisig authorization scheme (`multisigOwner` + `signers`) purely because 4 accounts were supplied, with no verification that `plain_signer_owner` is actually a `Multisig`-typed account or that `bogus_extra_account` played any role in authorizing the instruction — demonstrating the parse/on-chain-semantics divergence described above. A companion fuzz/invariant test can enumerate all `(accounts.len(), last_nonsigner_index)` combinations and compare `parse_signers`'s branch choice against a reference model of `validate_owner` (based on simulated account data), showing systematic mismatches whenever the attacker's account count and the referenced account's actual on-chain type disagree.

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
```
