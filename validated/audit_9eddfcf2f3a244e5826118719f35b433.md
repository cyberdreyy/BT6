### Title
Predictable `DefaultDistributor` address lets an attacker pre-fund it, inflating `rate` and leaving late claimers' recovery unpayable - ([File: contracts/DefaultDistributor.sol](contracts/DefaultDistributor.sol))

### Summary
`IdleCDOEpochVariant` deploys a fresh `DefaultDistributor` contract per tranche class during the default/recovery flow. The distributor's address is a plain `CREATE` address (`keccak256(rlp([cdoAddress, nonce]))`), fully predictable in advance because the CDO's nonce is observable on-chain. `DefaultDistributor.setIsActive` fixes the redemption `rate` as `underlying.balanceOf(this) / tranche.totalSupply()`, i.e. it trusts the raw token balance rather than an internal accounting variable. An attacker can therefore send underlying tokens to the future distributor address before it exists (and/or after deployment but before activation), inflating `rate` beyond `recoveredFunds / supply`. Early claimers (including the attacker if they hold tranche tokens) are paid at the inflated rate, and the distributor runs dry, so the last claimers' `claim` calls revert — permanent freezing/loss of their recovery share. This is the exact analog of the Velodrome bug: a predictable, freshly-deployed receiving contract whose correctness depends on its token balance being "clean" at setup.

### Finding Description
- `DefaultDistributor` is constructed with `new` (CREATE), so its address is derivable from the IdleCDO contract address plus its current nonce long before `finalizeDefault`/the claim setup executes.
- On activation, `rate` is computed from `IERC20(token).balanceOf(address(this))` (`DefaultDistributor.sol:48-50`), not from the amount the CDO actually transferred.
- `claim` pays `trancheBal * rate / ONE_TRANCHE` out of that same balance (`DefaultDistributor.sol:35-41`), so an inflated rate makes the distributor insolvent for later claims — payout ordering becomes first-come-first-served rather than pro-rata.
- There is no skim/donation-isolation guard (unlike `_skimDonatedAssets` used elsewhere for vault accounting); the only mitigations are owner-controlled `transferToken` and re-running `setIsActive(false)→(true)` after sweeping, which require the honest owner to notice the donation before activation.

### Impact Explanation
Permanent loss for late claimers in a defaulted epoch: the recovery pool is redistributed at an inflated rate, so a tail of honest tranche holders' `claim` transactions revert on insufficient balance. This breaks the "one receipt, pro-rata payout" invariant of the default distribution flow. Quantification: if the attacker donates `D`, total payouts exceed real recovered funds `R` by `D`, so claimers representing `D / rate` worth of tranches receive nothing.

### Likelihood Explanation
The attacker is unprivileged — any address can transfer underlying ERC-20 to a non-existent address. Requirements: a default occurs (not attacker-controlled, but the attack only needs execution once a default is announced) and the donation must land before the owner activates claims. The attacker gains nothing net (their donated `D` is diluted across all holders proportionally to their own share `f·D < D`), so this is a griefing/ordering attack; profitability only appears if combined with the attacker racing to claim early while donating the minimum needed to strand a specific large victim's claim. Likelihood is moderate: griefing cost scales with the victim set the attacker wants to strand.

### Recommendation
- Deploy the distributor via `cloneDeterministic`/`CREATE2` with an unpredictable salt (e.g., mixing `block.prevrandao`/`blockhash` and a caller-supplied salt), as Velodrome did in `7b35b2`.
- Better: decouple accounting from raw balance — have the CDO pass the recovered amount explicitly and compute `rate = recoveredAmount * ONE_TRANCHE / trancheToken.totalSupply()` inside `setIsActive`, or record a `deposit()`-time balance snapshot that ignores pre-existing funds.
