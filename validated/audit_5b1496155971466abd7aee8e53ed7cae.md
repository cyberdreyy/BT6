## Title
Reward Sniping via Late-Epoch `deposit_and_stake` Dilutes Pre-Existing Delegators' Rewards — (`staking-pool/src/internal.rs`)

## Summary
The staking pool distributes each epoch's `total_reward` across whatever `total_stake_shares` exist at the moment `internal_ping` runs, with no accounting for how long each share was held during the epoch that generated the reward. An unprivileged actor can call `deposit_and_stake` in the final block of an epoch — after the validator-set/stake amount for that epoch has already been fixed by the protocol — and still receive a proportional cut of the reward that is credited when the epoch flips, diluting the return of delegators who actually earned it.

## Finding Description
The binding that should hold is: `total_staked_balance_after_ping == total_staked_balance_before_ping + reward_earned_by_shares_outstanding_during_the_epoch`, where the reward is attributed only to the shares that were actually staked while the epoch's validation was performed. Instead, the contract enforces only `total_staked_balance_after_ping == total_staked_balance_before_ping + total_reward`, and `total_reward` is spread over **all** `total_stake_shares` present at the time of the `ping`, regardless of when those shares were minted [1](#0-0) .

Call sequence:
1. `deposit_and_stake` first calls `internal_ping`, which is a no-op because `env::epoch_height()` hasn't changed yet [2](#0-1) [3](#0-2) .
2. `internal_deposit` credits the attacker's `unstaked` balance and correctly bumps `last_total_balance += amount`, so the deposit itself is excluded from the next reward calculation [4](#0-3) .
3. `internal_stake` mints `num_shares` for the attacker at the *current* `total_staked_balance` / `total_stake_shares` price — i.e., before any reward has been credited — and increases `total_staked_balance` and `total_stake_shares` accordingly [5](#0-4) .
4. `internal_restake` immediately issues a `Promise::new(current_account_id()).stake(total_staked_balance, ...)`, which updates the account's locked balance right away (it does not wait for a future epoch) [6](#0-5) .
5. On the next epoch boundary, the protocol credits the validator's *already-determined* epoch reward (based on stake that was fixed epochs earlier, unaffected by the attacker's last-second stake) to `env::account_locked_balance()`.
6. Anyone calls `ping()`, which invokes `internal_ping`. It computes `total_reward = total_balance - last_total_balance` and adds `remaining_reward` to `total_staked_balance`, raising the price of *every* outstanding share, including the attacker's shares purchased moments earlier [7](#0-6) .

None of the existing guards address this: `internal_ping`'s only assertion is that `total_balance >= last_total_balance` [8](#0-7) , which is unrelated to *who* the reward is attributed to. There is no minimum holding period, vesting, or time-weighted share accounting anywhere in the contract.

## Impact Explanation
The attacker's newly-minted shares receive a pro-rata slice of a reward that was economically generated entirely by the pre-existing delegators' stake (since NEAR epoch rewards are fixed based on stake declared epochs in advance). This is a direct case of "rewards ... attributed to the wrong party," matching the **High** impact category. The loss is borne by all pre-existing delegators (and the pool owner's fee share is similarly diluted), and the attack is repeatable every epoch against any pool with a predictable/observable reward and modest `total_staked_balance` relative to the attacker's available capital.

## Likelihood Explanation
- Preconditions: an existing pool with non-trivial expected reward relative to its `total_staked_balance`; an attacker with capital `D` to stake temporarily.
- No special role is needed — `deposit_and_stake` and `ping` are both open, unprivileged methods.
- Cost to the attacker: the capital `D` must be locked while staked (and later suffers the 4-epoch unbonding delay to reclaim it via `unstake`/`withdraw`), which is bounded and non-destructive, but the profit `D·R/(S+D)` scales with how much larger `D` is relative to `S`, making the attack most profitable for well-capitalized actors against smaller/mid-size pools with predictable payout timing (rewards are visible on-chain/queryable each epoch).
- Feasibility is high because epoch boundaries and validator rewards are publicly observable, requiring no privileged information.

## Recommendation
Introduce a mechanism so that newly staked shares only start accruing rewards from the epoch *after* they are staked — e.g., track a "pending" pool of shares/stake that is only merged into the reward-eligible `total_stake_shares` after `internal_ping` has run at least once following the deposit, or snapshot `total_stake_shares` at the start of `internal_ping` before including the current transaction's new stake. Alternatively, require `internal_stake` calls to always run `internal_ping` first when it would return true and structure `deposit_and_stake` so any deposit made in the same block as (or shortly before) an epoch flip is queued for staking only in the following epoch.

## Proof of Concept
```rust
// staking-pool/src/lib.rs test module (cargo test)
#[test]
fn test_reward_sniping_via_late_stake() {
    let mut emulator = Emulator::new(
        owner(),
        "KuTCtARNzxZQ3YvXDeLjx83FDqxv2SdQTSbiq876zR7".to_string(),
        zero_fee(),
    );

    // Existing delegator stakes S
    let existing_stake = ntoy(1_000_000);
    emulator.update_context(bob(), existing_stake);
    emulator.contract.deposit_and_stake();
    emulator.amount += existing_stake;
    emulator.simulate_stake_call();

    let locked_before = emulator.locked_amount;

    // Attacker deposits and stakes D in the SAME epoch, right before it flips
    let attacker_stake = ntoy(9_000_000); // D >> S
    emulator.update_context(charlie(), attacker_stake);
    emulator.contract.deposit_and_stake();
    emulator.amount += attacker_stake;
    emulator.simulate_stake_call();

    // Epoch flips; protocol credits a reward R that was economically
    // earned only by `existing_stake` (locked_before), unrelated to `attacker_stake`.
    let reward = ntoy(100_000);
    emulator.skip_epochs(1);
    emulator.locked_amount = locked_before + reward; // reward fixed independent of attacker's D
    emulator.update_context(bob(), 0);
    emulator.contract.ping();

    let bob_balance = emulator.contract.get_account_staked_balance(bob()).0;
    let charlie_balance = emulator.contract.get_account_staked_balance(charlie()).0;

    // Binding under test: charlie (attacker) should receive 0 reward since his
    // stake was not present during the epoch that generated `reward`.
    // Actual behavior: charlie receives a share of `reward` proportional to
    // his stake_shares, diluting bob's rightful reward.
    assert!(charlie_balance > attacker_stake, "attacker captured reward it did not earn");
    assert!(bob_balance < existing_stake + reward, "existing delegator's reward was diluted");
}
```
This demonstrates that `charlie_balance` exceeds `attacker_stake` (i.e., the attacker profits from a reward generated before their stake existed) while `bob_balance` falls short of `existing_stake + reward` (the full reward it should have received alone).

    pub(crate) fn internal_stake(&mut self, amount: Balance) {
        assert!(amount > 0, "Staking amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

        // Calculate the number of "stake" shares that the account will receive for staking the
        // given amount.
        let num_shares = self.num_shares_from_staked_amount_rounded_down(amount);
        assert!(
            num_shares > 0,
            "The calculated number of \"stake\" shares received for staking should be positive"
        );
        // The amount of tokens the account will be charged from the unstaked balance.
        // Rounded down to avoid overcharging the account to guarantee that the account can always
        // unstake at least the same amount as staked.
        let charge_amount = self.staked_amount_from_num_shares_rounded_down(num_shares);
        assert!(
            charge_amount > 0,
            "Invariant violation. Calculated staked amount must be positive, because \"stake\" share price should be at least 1"
        );

        assert!(
            account.unstaked >= charge_amount,
            "Not enough unstaked balance to stake"
        );
        account.unstaked -= charge_amount;
        account.stake_shares += num_shares;
        self.internal_save_account(&account_id, &account);

        // The staked amount that will be added to the total to guarantee the "stake" share price
        // never decreases. The difference between `stake_amount` and `charge_amount` is paid
        // from the allocated STAKE_SHARE_PRICE_GUARANTEE_FUND.
        let stake_amount = self.staked_amount_from_num_shares_rounded_up(num_shares);

        self.total_staked_balance += stake_amount;
        self.total_stake_shares += num_shares;

        env::log(
            format!(
                "@{} staking {}. Received {} new staking shares. Total {} unstaked balance and {} staking shares",
                account_id, charge_amount, num_shares, account.unstaked, account.stake_shares
            )
                .as_bytes(),
        );
        env::log(
            format!(
                "Contract total staked balance is {}. Total number of shares {}",
                self.total_staked_balance, self.total_stake_shares
            )
            .as_bytes(),
        );
    }
