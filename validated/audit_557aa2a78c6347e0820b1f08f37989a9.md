### Title
Unchecked fire-and-forget `Promise::new(account_id).transfer(amount)` in `internal_withdraw` allows the staking-pool ledger to diverge from actual NEAR held - (File: staking-pool/src/internal.rs)

### Summary
`staking-pool/src/internal.rs`'s `internal_withdraw` decrements the caller's recorded `unstaked` balance and the contract's `last_total_balance` and then fires a bare `Promise::new(account_id).transfer(amount)` with no `.then()` callback to verify the transfer succeeded, mirroring the `Receiver.sol` `.call()`-without-checking-return-value bug class.

### Finding Description
`internal_withdraw` first asserts sufficient unstaked balance and unstaking-delay maturity, then unconditionally mutates state (`account.unstaked -= amount; self.internal_save_account(...); self.last_total_balance -= amount;`) before issuing the transfer, and the transfer itself is not followed by any callback that checks `is_promise_success()` and reverts/restores state on failure: [1](#0-0) 

This is unlike the equivalent flow in the `lockup` contract, where every native-token transfer that matters to accounting is chained with a callback that inspects the promise result via `is_promise_success()` before finalizing the balance change, e.g. `on_staking_pool_withdraw` in `lockup/src/owner_callbacks.rs`: [2](#0-1) 

and `on_withdraw_unvested_amount` in `lockup/src/foundation_callbacks.rs`, which explicitly restores the pre-transfer status if the promise fails: [3](#0-2) 

In `staking-pool/src/internal.rs`, no such safety net exists: `Account.unstaked` and `last_total_balance` are decremented synchronously and irreversibly regardless of whether the subsequent `Promise::new(account_id).transfer(amount)` actually succeeds.

### Impact Explanation
If the transfer promise fails asynchronously (e.g., the receiving account cannot accept the deposit for some execution-environment reason), the contract's internal ledger (`account.unstaked`, `last_total_balance`) has already been permanently decreased as if the withdrawal succeeded, while the account never actually received the NEAR. This breaks the custody binding "value debited versus value delivered": the ledger states less NEAR is owed/held than the contract still actually possesses, meaning the withdrawing account's real claim is understated and the discrepancy is not recoverable through any retry path in this contract (there is no follow-up callback to re-credit the account). This fits the High-severity impact category of "an accounting value diverging from reality where another party settles on it."

### Likelihood Explanation
Likelihood is constrained by the fact that a plain `Promise::new(account_id).transfer(amount)` on NEAR rarely fails for a valid, already-registered `account_id` (transfers to existing accounts virtually always succeed, unlike EVM `.call()` to a reverting receiver contract). This is a genuine deviation from the safer, checked pattern used elsewhere in the same repository (`lockup`), and the absence of a checking callback is a structural code smell, though the practical trigger surface for an actual failed transfer under normal operation is narrow.

### Recommendation
Chain the transfer in `internal_withdraw` with a `.then()` callback (as already done for staking-pool interactions in `lockup/src/owner_callbacks.rs`) that calls `is_promise_success()`, and re-credit `account.unstaked` and `self.last_total_balance` if the transfer failed, mirroring the revert-on-failure pattern used by `on_withdraw_unvested_amount` and `on_staking_pool_withdraw`.

### Proof of Concept
1. Account has `unstaked >= amount` and `unstaked_available_epoch_height <= env::epoch_height()`.
2. Account calls the public withdraw entrypoint, invoking `internal_withdraw(amount)` at `staking-pool/src/internal.rs:42-68`.
3. `account.unstaked -= amount` and `self.last_total_balance -= amount` are persisted immediately.
4. `Promise::new(account_id).transfer(amount)` is scheduled with no attached callback.
5. If this promise fails at execution time, there is no code path in this contract to detect the failure or restore `account.unstaked`/`last_total_balance` — the ledger permanently reflects a withdrawal that did not deliver funds, while the contract's real yoctoNEAR balance was never reduced by `amount`, leaving the account's recorded claim below what it should be.
