### Title
Loss-adjusted withdraw receipts are indexed one epoch late, so stopEpochWithDuration haircuts are applied to the wrong receipts (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the partial-funding recovery price under `lossRecoveryPriceByEpoch[epochNumber]` at a point in `stopEpoch` where `deposit()` has already incremented `epochNumber`. Withdraw receipts, however, are tagged with `lastWithdrawRequest` and `withdrawsRequestsByEpoch` using the pre-increment epoch value (the epochNumber current when `requestWithdraw` ran during the buffer). Both the re-request guard in `requestWithdraw` and `_claimLossAdjustedWithdrawRequest` look up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`, which is always zero for the receipts that were actually haircut. The result mirrors the referenced kernel bug class: shared accounting state (the pending-receipt bucket) is mutated under an epoch key that no claimant's pointer ever resolves to, so the "loss-adjusted" receipts behave like unfunded full-value claims against an underfunded pool.

### Finding Description
Relevant code:

- `requestWithdraw` tags receipts with the current epoch and guards re-requests via `lossRecoveryPriceByEpoch[lastWithdrawRequest]` (IdleCreditVault.sol:259-294).
- `collectWithdrawFunds` writes the haircut as `lossRecoveryPriceByEpoch[epochNumber]` (IdleCreditVault.sol:411-421).
- `deposit()` increments `epochNumber` when called while `isEpochRunning` is still true, which per its own comment happens inside `stopEpoch` (IdleCreditVault.sol:607-611).
- In `_stopEpoch`, the borrower pull (`getFundsFromBorrower`, which performs the strategy `deposit` and therefore the `epochNumber += 1`) is executed at IdleCDOEpochVariant.sol:408, and `_strategy.collectWithdrawFunds(_pendingWithdraws)` runs immediately after at line 410. So the haircut is stored under `epochNumber = requestEpoch + 1`, never under `requestEpoch`.
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (IdleCreditVault.sol:789-801), i.e. the pre-increment epoch key — always zero — and falls through to `_claimFundedWithdrawRequest`, which pays the full `withdrawsRequests[_user]` basis at par (IdleCreditVault.sol:319-349).

Two distinct corruptions follow:

1. Receipts that were supposed to be haircut by `_lossAmount` are paid in full from a strategy that only received `pendingBasis * recoveryPrice`. `pendingWithdraws` was zeroed at line 420, so the shortfall is silently socialized across claimants: earlier claimants are made whole and later claimants' claims revert on insufficient balance — a permanent freeze of unclaimed funded receipts.
2. Any *new* request made in the following buffer is tagged with the post-increment epoch, which is exactly the key under which the stale `lossRecoveryPriceByEpoch` entry was stored. Its owner is forced into `_claimLossAdjustedWithdrawRequest` and eats a haircut that belongs to a different epoch's receipts (and the guard at requestWithdraw blocks them from re-requesting until they claim the wrongly-haircut receipt).

### Impact Explanation
Broken invariant: "one receipt, one correctly-priced payout" and loss waterfall integrity. When `stopEpochWithDuration` realizes a loss with pending receipts (the feature `previewLossAdjustedWithdrawFunds`/`lossRecoveryPriceByEpoch` exists for), the intended haircut is never applied to the intended receipts. Quantified loss: up to the entire pending-receipt loss share (`pendingBasis - pendingToFund`) is paid out to early claimants instead of being haircut, and an equivalent amount is permanently stuck for the last claimant(s) whose funded claims revert (`safeTransfer` on insufficient balance, or the `NotAllowed` guard in `_transferFundedClaim` when a recovery reserve exists). Additionally, an unrelated later requester can receive `basis * lossRecoveryPrice` instead of `basis`, a direct theft of `(1 - lossRecoveryPrice) * basis`.

### Likelihood Explanation
Requires only the honest manager calling `stopEpochWithDuration` with `_lossAmount > 0` while pending withdraw receipts exist — a designed-for code path, not an edge case. The attacker is any unprivileged tranche holder: by requesting a withdraw in the buffer before the loss epoch and racing to claim first (or by simply being a later requester in the next buffer), they either claim at par from an underfunded pool or absorb someone else's haircut. No privileged misbehavior is needed; the misalignment is deterministic on every loss-adjusted stop.

### Recommendation
In `collectWithdrawFunds`, store the haircut under the epoch the pending receipts were requested in — i.e. snapshot `epochNumber` before the borrower pull/`deposit` bump, or pass the request epoch from `IdleCDOEpochVariant._stopEpoch` and write `lossRecoveryPriceByEpoch[requestEpoch]`. Equivalently, key claims by the funding epoch consistently in `requestWithdraw`, `_claimLossAdjustedWithdrawRequest`, and `_clearWithdrawClaimForEpoch`. Add a test that a `stopEpochWithDuration` loss with pending receipts produces `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` and that a claim pays `basis * price`.

### Proof of Concept
Foundry fork sketch (against the existing `IdleCreditVault.t.sol` harness):

```solidity
function testLossHaircutEpochMismatch() external {
    // deposit + start epoch 0
    idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);

    // stop epoch 0 (epochNumber becomes 1), user requests withdraw during buffer
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    vm.prank(user);
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(strategy.lastWithdrawRequest(user), 1);   // tagged epoch 1

    // epoch 1 runs; manager stops it with a realized loss
    _startEpochAndCheckPrices(1);
    uint256 loss = receipt / 2;
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, duration, loss);

    // haircut stored under post-increment epoch (2), receipt tagged epoch 1
    assertEq(strategy.lossRecoveryPriceByEpoch(2) != 0, true);
    assertEq(strategy.lossRecoveryPriceByEpoch(1), 0); // lookup key used by claim

    // claim pays FULL basis instead of haircut -> pool underfunded,
    // or reverts once earlier claimants drained it
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest(); // pays 'receipt', not receipt * price / 1e18
}
```

The assertion `lossRecoveryPriceByEpoch(1) == 0` while `lossRecoveryPriceByEpoch(2) != 0` demonstrates the dangling pointer analog: the claim path never resolves the haircut for the receipt that incurred it.
