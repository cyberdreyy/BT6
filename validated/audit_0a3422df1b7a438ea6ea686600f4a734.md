## Analysis Result

I found a concrete node-side accounting bug where a single signer's weight can be double-counted into both the "approved" and "rejected" tallies for the same block, corrupting the aggregated-weight-vs-verified-accepts invariant the signer coordinator relies on.

### Title
Signer weight double-counted into both approval and rejection tallies on vote reconsideration - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tracks two independent running totals per block, `total_weight_approved` and `total_weight_rejected`, guarded by two *different* de-duplication sets (`gathered_signatures` and `responded_signers`). A signer that legitimately reconsiders its vote for the same block — a transition the signer-side state machine explicitly allows (`LocallyRejected --> LocallyAccepted`) — has its weight added to `total_weight_rejected` on the first message and, independently, to `total_weight_approved` on the second, with no removal of the earlier tally. The two accumulators are never reconciled, so a single signer's weight can be counted twice, corrupting the aggregated weight the miner coordinator uses to decide accept/reject.

### Finding Description
The signer-side state machine deliberately allows a signer to reject a block and later accept the very same block (`BlockInfo::check_state`, `LocallyRejected -> LocallyAccepted` transition), for example after `handle_block_validate_reject` followed by a later successful re-validation, or via `should_reevaluate_reject_reason` reconsideration. [1](#0-0) 

On the node side, `StackerDBListener` processes `BlockResponse::Rejected` and `BlockResponse::Accepted` messages for the same `signer_signature_hash` using two separate guards:
- Accept path: weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`.
- Reject path: weight is added to `total_weight_rejected` only if `block.responded_signers.insert(slot_id)` returns `true` (first time this slot is seen in `responded_signers`). [2](#0-1) [3](#0-2) 

Neither branch checks the other branch's set nor removes the signer's previously counted weight. Concretely: signer S rejects first → `responded_signers.insert(slot)` is `true` → `total_weight_rejected += wS`. S later reconsiders and accepts the same block → `slot` is not yet in `gathered_signatures` → `total_weight_approved += wS` as well. `wS` is now counted in *both* totals, so `total_weight_approved + total_weight_rejected` can exceed the true `total_weight` of the reward set — the aggregated weight no longer reflects verified, current, one-vote-per-signer accepts/rejects.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality the coordinator's threshold logic depends on in `wait_for_signer_signature`/`gather_signatures`-style loop: [4](#0-3) 

Because the rejection branch of that loop is evaluated before the acceptance branch, the immediate practical effect is a liveness weakening rather than an outright forged acceptance: stale rejection weight from a signer who has since reconsidered and accepted is never purged, permanently shrinking the blocking-minority budget available for that specific block. This makes it strictly easier for the `>30%`-weight rejection/abort path (`SignersRejected`) to fire using less than the intended amount of *currently* rejecting weight, since part of the counted rejection weight belongs to a signer whose live vote is actually "accept." This falls under the permitted High-impact category of a signer's aggregated weight/threshold accounting being corrupted (liveness wedge via miscounted response), triggerable by a single signer's benign vote flip plus ordinary gossip — no majority collusion required.

### Likelihood Explanation
Vote reconsideration is a normal, explicitly supported path in the signer state machine (`LocallyRejected -> LocallyAccepted`), not an exotic edge case — it is exercised whenever a signer's earlier rejection reason becomes stale and `should_reevaluate_reject_reason`/re-validation succeeds. Any single signer taking this ordinary path (reject-then-accept on the same block) triggers the double count; no cooperation from other signers or privileged access is needed.

### Recommendation
Use a single per-slot "final vote" record (or explicitly subtract the previously-tallied weight when a signer's vote flips) so that `total_weight_approved` and `total_weight_rejected` always sum to at most `total_weight`, and a signer's weight only ever counts once, in its currently-effective bucket.

### Proof of Concept
1. Node tracks a `BlockStatus` for `signer_signature_hash = H` with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight `wS`) sends `BlockResponse::Rejected` for `H` (e.g., due to a transient validation failure). `responded_signers.insert(slot_S)` → `true`; `total_weight_rejected += wS`.
3. S later re-evaluates (per `should_reevaluate_reject_reason`) and sends `BlockResponse::Accepted` for the same `H`. `gathered_signatures.contains_key(slot_S)` is `false` (first acceptance) → `total_weight_approved += wS`.
4. Now `total_weight_approved + total_weight_rejected` includes `wS` twice, exceeding the honest sum of distinct signer weights, so the rejection-abort threshold in `signer_coordinator.rs` can be reached with less genuinely-rejecting weight than the 30% the protocol intends.
