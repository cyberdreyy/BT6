### Title
External initiators can trigger runs of ANY job (not just the job they are scoped to) via `POST /v2/jobs/:ID/runs` because `PipelineRunsController.Create` distinguishes "user vs EI" using the same session key that `AuthenticateExternalInitiator` also populates - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets both `SessionExternalInitiatorKey` and `SessionUserKey` (to a synthetic `User{Role: UserRoleRun}`) for any authenticated EI request. `PipelineRunsController.Create` gates its "integer job ID" run path with `_, isUser := auth.GetAuthenticatedUser(c)`, whose comment claims "EIs not allowed," but because EI auth also populates `SessionUserKey`, `isUser` is true for EIs too, so an EI can call `RunJobV2(ctx, jobID, nil)` for an arbitrary integer job ID with no check that the job is the one the EI is registered against.

### Finding Description
`core/web/auth/auth.go`'s `AuthenticateExternalInitiator` (lines 119-151) authenticates an EI purely by validating its access key/secret against the `external_initiators` table (`store.FindExternalInitiator` / `bridges.AuthenticateExternalInitiator`), and then unconditionally elevates the request to run-role by writing: [1](#0-0) 
This is the only place that sets `SessionUserKey` for EI-authenticated requests, and it is the same key used by ordinary `AuthenticateByToken`/`AuthenticateBySession` for real users. `RequiresRunRole` (used to gate `POST /v2/jobs/:ID/runs`) only checks the role field, not the auth method: [2](#0-1) 
The route is registered in `core/web/router.go` with `AuthenticateExternalInitiator` chained ahead of the token/session methods, feeding into `RequiresRunRole(prc.Create)`: [3](#0-2) 
Inside `PipelineRunsController.Create`, the code attempts to distinguish real users from EIs via `auth.GetAuthenticatedUser(c)`, with an explicit comment that "only users are allowed to run jobs using int IDs - EIs not allowed": [4](#0-3) 
However, `GetAuthenticatedUser` simply reads `SessionUserKey`: [5](#0-4) 
Because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` evaluates to `true` for EI-authenticated requests exactly as it does for real users — the intended EI-exclusion check is a no-op. The code never inspects `GetAuthenticatedExternalInitiator(c)` to confirm the caller is actually a user (as opposed to an EI), nor does it verify that the resolved job (from `idStr`) is bound to the authenticated EI via `external_initiator_webhook_specs`. Consequently, any valid EI credential (registered for job A, or for no job at all) can trigger `RunJobV2` for any arbitrary integer job ID, including jobs of any type (not just webhook jobs), regardless of whether that EI was ever associated with that job.

### Impact Explanation
This is an authorization-exactness violation: a low-privilege credential (an external-initiator secret, typically distributed to third-party integrations) can force job runs on jobs it was never scoped to, including non-webhook job types (e.g., direct request, cron, flux monitor, etc., to the extent `RunJobV2` permits). This can cause unauthorized job executions, potential unintended fund-moving transactions (if the job's pipeline includes ETH tx tasks), and repeated/abusive triggering of pipelines belonging to other job definitions on the same node — matching a "unauthorized job run" / authorization bypass impact class.

### Likelihood Explanation
The precondition is minimal: possession of a single valid EI access key + secret pair (registered for any job, or even none, since the EI just needs to exist and authenticate; no job-EI relationship is checked in this specific path). The attack is trivially repeatable: `POST /v2/jobs/<any-int-ID>/runs` with the EI headers set (`static.ExternalInitiatorAccessKeyHeader` / `static.ExternalInitiatorSecretHeader`), no other secret needed. Given EI credentials are commonly distributed to less-trusted external services for webhook-triggered jobs, this represents a realistic and easily exploitable privilege-escalation path within the "unprivileged EI holder" threat model specified.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests where `auth.GetAuthenticatedExternalInitiator(c)` returns an EI (i.e., check for the EI key/presence, not just `GetAuthenticatedUser`), or better, stop `AuthenticateExternalInitiator` from writing to the shared `SessionUserKey` and instead use a distinct context key/type for the EI-run role so the two authentication types cannot be conflated. Additionally, when a run is triggered by an EI, validate that the target job's `external_initiator_webhook_specs` row matches the authenticated EI's ID before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go` (or equivalent):
1. Create two jobs, Job A (webhook, external-initiator "EI-A") and Job B (any other job type, e.g. cron or direct-request, unrelated to EI-A).
2. Register external initiator `EI-A` via `/v2/external_initiators`, capturing its `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/<Job-B-ID>/runs` with headers `X-Chainlink-EA-AccessKey: EI-A.AccessKey`, `X-Chainlink-EA-Secret: EI-A.Secret` (no session/token headers).
4. Assert the response is `200 OK` with a created pipeline run for Job B (demonstrating the bug), where the expected/fixed behavior should be `401/403 Unauthorized` since EI-A has no relationship with Job B.
5. Additionally assert via `auth.GetAuthenticatedExternalInitiator(c)` inside a modified handler (or via `httptest`) that the context carries an EI, not a genuine `User`, proving `isUser` incorrectly evaluates `true` for EI-only auth.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
