### Title
External ERC4626 liquidity exhaustion can indefinitely delay `stopEpoch` and freeze vault funds - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
In programmable-borrower mode, `stopEpoch` synchronously calls `ProgrammableBorrower.onStopEpoch`, and a failed ERC4626 withdrawal is deliberately reverted so the stop can be retried later. [1](#0-0) [2](#0-1)  There is no timeout, failure counter, or fallback path: as long as an unprivileged user of the external vault keeps available liquidity below the pending withdrawal obligation, the epoch remains running and LP funds stay locked. [3](#0-2) 

### Finding Description
`IdleCDOEpochVariant._stopEpoch` first calculates the cash that must be pulled from the programmable borrower and then calls `onStopEpoch` outside the protected `try this.getFundsFromBorrower` block. [4](#0-3)  `ProgrammableBorrower.onStopEpoch` verifies that the borrower’s vault shares economically cover the shortfall, but still calls `vault.withdraw`; if that withdrawal reverts, it throws `StopEpochVaultLiquidityUnavailable` rather than returning `false`. [2](#0-1)  Because the hook revert bubbles out of `_stopEpoch`, the transaction never reaches the default-handling `catch`, so `isEpochRunning`, borrower accounting, and pending withdrawals remain unchanged. [1](#0-0) [5](#0-4) 

This is analogous to an unbounded wait for a peer response: the epoch cannot complete until the external vault supplies liquidity, and the protocol does not define a deadline after which the solvent-but-illiquid position is treated as a realized loss or default. [6](#0-5)  The escape functions do not reliably mitigate the condition because `setVault` is blocked while shares remain and `emergencyExitVault` calls `vault.redeem`, which can fail for the same unavailable-liquidity reason. [7](#0-6) [8](#0-7) 

### Impact Explanation
A competing ERC4626 vault user can repeatedly consume newly available underlying so that `vault.withdraw(pendingWithdraws)` continues reverting after `epochEndDate`. [2](#0-1)  While the epoch is running, deposits are paused and withdrawal requests are disabled, so active tranche holders cannot begin an exit and existing withdraw receipts cannot be funded. [9](#0-8) [10](#0-9)  In the demonstrated 10,000-USDC configuration, a 5,000-USDC liquidity shortage prevents epoch closure and temporarily freezes the full 10,000-USDC vault position for as long as the attacker maintains the state. [11](#0-10) 

### Likelihood Explanation
The attacker only needs the ability to make the selected ERC4626 vault’s immediate liquidity lower than the pending withdrawal amount; no privileged Idle role, KYC status, borrower cooperation, or malformed vault return value is required. [2](#0-1)  Liquidity must be exhausted at each attempted stop, so sustained freezing requires repeated action or a persistently illiquid vault, but even one successful exhaustion delays all withdrawals beyond the scheduled epoch end. [10](#0-9) 

### Recommendation
Introduce a bounded liquidity-recovery window for `onStopEpoch`. For example, record the first failed stop timestamp, permit retries until a manager-configured deadline, and after that deadline route the position through `stopEpochWithDuration` loss accounting or borrower-default finalization instead of reverting indefinitely. [1](#0-0) [12](#0-11)  Alternatively, make `onStopEpoch` return a retryable status and let the CDO decide when repeated failures should invoke `_handleBorrowerDefault`, while ensuring prefunded-queue settlement still runs if that route is selected. [13](#0-12) [14](#0-13)

// test/foundry/ProgrammableBorrowerCreditVault.t.sol
function testVaultUserCanRepeatedlyDelayStopEpoch() external {
    MockStopEpochLiquidityVault sharedVault =
        new MockStopEpochLiquidityVault(USDC);

    uint256 amount = 10_000 * oneScale;
    address vaultUser = makeAddr("vaultUser");

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    vm.prank(manager);
    programmableBorrower.setVault(address(sharedVault));

    idleCDO.depositAA(amount);

    // Half of the position must be funded in cash at epoch end.
    cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 2,
        address(aaTranche)
    );
    _startEpochAndCheckPrices(0);

    uint256 pendingWithdraws = strategy.pendingWithdraws();
    assertEq(pendingWithdraws, amount / 2);

    // The vault user drains immediate liquidity but the borrower's shares
    // still economically cover the required withdrawal.
    vm.prank(vaultUser);
    sharedVault.setWithdrawLimit(pendingWithdraws - 1);
    assertGe(
        sharedVault.convertToAssets(
            sharedVault.balanceOf(address(programmableBorrower))
        ),
        pendingWithdraws
    );

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // First blocked settlement.
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertEq(strategy.pendingWithdraws(), pendingWithdraws);

    // The same state can be maintained across subsequent retries.
    vm.warp(block.timestamp + 30 days);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertEq(strategy.pendingWithdraws(), pendingWithdraws);

    // Only after external liquidity returns can the epoch finally settle.
    sharedVault.setWithdrawLimit(type(uint256).max);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertFalse(cdoEpoch.isEpochRunning());
    assertEq(strategy.pendingWithdraws(), 0);
}

  /// @notice Hook called by IdleCDOEpochVariant before stopping an epoch.
  /// Withdraws enough liquidity from the vault so IdleCDO can pull funds.
  /// @param _amountRequired total amount IdleCDO will pull via transferFrom.
  /// @param _isRequestingAllFunds whether IdleCDO is closing the pool and recalling all funds.
  /// @return success false when the borrower ledger makes close-pool settlement a real default.
  function onStopEpoch(uint256 _amountRequired, bool _isRequestingAllFunds) external nonReentrant returns (bool success) {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // if we want to close the pool and the borrower still owes any amount, consider it a failure and let IdleCDO handle it as a default instead of a close. 
    if (_isRequestingAllFunds && (borrowerPrincipal != 0 || borrowerInterestDebt != 0 || borrowerInterestAccrued != 0)) {
      return false;
    }

    uint256 onHand = underlyingToken.balanceOf(address(this));
    if (_amountRequired > onHand) {
      uint256 shortfall = _amountRequired - onHand;
      // If the vault shares do not economically cover the shortfall, let IdleCDO's later
      // transferFrom fail and use the existing default path. Only an otherwise-covered ERC4626
      // withdrawal failure should make stopEpoch retryable.
      if (shortfall > _currentVaultAssets()) return true;
      try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        if (epochAccountingActive) {
          epochWithdrawnFromVault += shortfall;
        }
        emit WithdrawnFromVault(shortfall, shares, address(this));
      } catch {
        revert StopEpochVaultLiquidityUnavailable();
      }

contract MockStopEpochLiquidityVault is ERC20 {
  IERC20Detailed public immutable assetToken;
  uint256 public withdrawLimit = type(uint256).max;

  constructor(address _asset) ERC20("Stop Epoch Liquidity Vault", "SELV") {
    assetToken = IERC20Detailed(_asset);
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    if (supply == 0) return shares;
    return shares * assetToken.balanceOf(address(this)) / supply;
  }

  function maxWithdraw(address owner) external view returns (uint256) {
    uint256 assets = convertToAssets(balanceOf(owner));
    return assets < withdrawLimit ? assets : withdrawLimit;
  }

  function setWithdrawLimit(uint256 assets) external {
    withdrawLimit = assets;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 assetsBefore = assetToken.balanceOf(address(this));
    uint256 supply = totalSupply();
    shares = supply == 0 || assetsBefore == 0 ? assets : assets * supply / assetsBefore;
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }

  function withdraw(uint256 assets, address receiver, address owner) external returns (uint256 shares) {
    require(assets <= withdrawLimit, "insufficient-liquidity");
    shares = _toSharesRoundUp(assets);
    if (msg.sender != owner) _spendAllowance(owner, msg.sender, shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function redeem(uint256 shares, address receiver, address owner) external returns (uint256 assets) {
    assets = convertToAssets(shares);
    require(assets <= withdrawLimit, "insufficient-liquidity");
    if (msg.sender != owner) _spendAllowance(owner, msg.sender, shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function _toSharesRoundUp(uint256 assets) internal view returns (uint256 shares) {
    uint256 supply = totalSupply();
    uint256 managedAssets = assetToken.balanceOf(address(this));
    if (supply == 0 || managedAssets == 0) return assets;
    shares = assets * supply / managedAssets;
    if (shares * managedAssets < assets * supply) shares += 1;
  }
