### Title
Gateway routes legacy requests to any DON handler based solely on attacker-supplied DonId, with no caller authorization check before forwarding to DON nodes - ([File: core/services/gateway/gateway.go])

### Summary
`gateway.ProcessRequest` routes legacy messages to a DON handler purely by looking up `g.handlers[msg.Body.DonId]`, with no check that the signer is an authorized/allowlisted subscriber of that DON. `msg.Validate()` only checks field lengths and signature well-formedness, not membership. The downstream `capabilities` handler's `HandleLegacyUserMessage` explicitly documents this gap with a `// TODO: apply allowlist and rate-limiting here` comment and unconditionally forwards the request to every member of the target DON.

### Finding Description
In `gateway.ProcessRequest` [2](#0-1) , when `msg.Body.DonId` is non-empty, the code sets `isLegacyRequest = true`, calls `msg.Validate()`, then does `h, ok = g.handlers[handlerKey]` where `handlerKey = msg.Body.DonId`. This lookup only checks that a handler exists for that DON ID string — it does not verify the message signer is a member/subscriber authorized for that DON.

`msg.Validate()` [1](#0-0)  validates signature format/length, message ID/method/DonId length constraints, and recovers the signer address into `m.Body.Sender` via `ExtractSigner()`. It never checks whether the recovered signer is permitted to use the target DON.

The request is then forwarded via `h.HandleLegacyUserMessage(ctx, msg, callback)` [3](#0-2) . In the `capabilities` package's implementation, the comment explicitly flags the missing control: `// TODO: apply allowlist and rate-limiting here` [4](#0-3) . After this comment, the handler proceeds to validate payload structure/timestamp and then unconditionally forwards the message to every configured DON node: `for _, member := range h.donConfig.Members { err = errors.Join(err, don.SendToNode(ctx, member.Address, req)) }` [5](#0-4) .

Thus an attacker who knows a target DON's `DonId` (these are often not secret — DON names/IDs are typically published in configuration or discoverable) can sign an arbitrary `web_api_trigger` message with their own unrelated keypair, set `DonId` to the target DON, and have the gateway forward the request into that DON's nodes, consuming that DON's node compute (outbound HTTP requests via `handleWebAPIOutgoingMessage`/`sendHTTPMessageToClient`) even though the attacker was never allowlisted for it.

### Impact Explanation
This matches Chainlink's "allowlist/quota bypass" and "unauthorized job run" impact classes: an unauthorized identity can force DON nodes to execute HTTP triggers/actions on their behalf, consuming node compute, network egress quota, and rate-limit budget belonging to another DON/service context. Depending on downstream processing (e.g., `MethodWebAPITarget`/`MethodComputeAction`), this could cause DON nodes to make arbitrary outbound HTTP calls initiated by an unauthorized party, a form of request impersonation/DoS against DON capacity.

### Likelihood Explanation
Preconditions are minimal: the attacker needs (1) knowledge of a valid `DonId` string, and (2) any ECDSA keypair to sign the message — no DON membership or gateway credential is required beyond the transport-level `auth` the HTTP server independently checks. The `nodeRateLimiter` in `handleWebAPIOutgoingMessage` operates per `nodeAddr` (the DON node) [6](#0-5) , not per external caller/sender, so it does not mitigate cross-tenant abuse. This is fully repeatable and requires only network access to the gateway's user-facing HTTP endpoint.

### Recommendation
Implement the allowlist check explicitly flagged by the `TODO` in `HandleLegacyUserMessage` before forwarding to DON members — verify `msg.Body.Sender` (populated by `Validate()`/`ExtractSigner()`) against a per-DON allowlist/subscription registry prior to invoking `don.SendToNode`. This check should occur either in `gateway.ProcessRequest` (centrally, before dispatch) or at the very start of `HandleLegacyUserMessage`, and reject unauthorized senders with an appropriate error code (e.g., a new `api.UnauthorizedError`).
