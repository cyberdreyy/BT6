## Analog Found

### Title
Group admin's `lending_pool_close_bank` can be permanently blocked by an attacker's dust deposit - (File: `programs/marginfi/src/instructions/marginfi_group/close_bank.rs`)

### Summary
`lending_pool_close_bank` requires `bank.lending_position_count == 0 && bank.borrowing_position_count == 0` (plus zero total shares) before the admin can close a bank [1](#0-0) . Because depositing into any operational bank is a permissionless, unprivileged action available to anyone, an attacker can open a trivial deposit position in the target bank and simply never withdraw it, keeping `lending_position_count` non-zero forever and permanently blocking the group admin's ability to close that bank — mirroring the `arbitraryCall()`/`incentives[who]` griefing pattern in the source report, where an unprivileged actor sets state that only they control the reset of, blocking a privileged action indefinitely.

### Finding Description
The bank lifecycle documentation confirms there is no admin override to force-close a bank with open positions: closure is gated strictly on `lending_position_count`/`borrowing_position_count`/`total_asset_shares`/`total_liability_shares` all being zero [2](#0-1) . `CLOSE_ENABLED_FLAG` is set automatically at bank creation and cannot be toggled, and the only path to eligibility is "once all positions are closed and the bank is empty" [3](#0-2) .

Any user can call the ordinary deposit instruction to open a lending position in a bank (this is a normal, unprivileged, permissionless-style user action gated only by bank operational state, not by admin approval). Once a user's balance crosses `ZERO_AMOUNT_THRESHOLD`, `lending_position_count` is incremented and stays incremented until that specific balance is closed [4](#0-3) . The position can only be reset by the position holder themselves (via withdraw), exactly analogous to the `incentives[who]` state in the original report that could only be reset by the stream creator calling `claimIncentive()`. Here, the "reset" (withdrawal) is entirely under the attacker's control and they have no incentive to ever perform it if their goal is to grief the admin.

There is no admin-forced liquidation/closure path for a healthy position with no debt (liquidation only triggers when an account is unhealthy), so the admin has no mechanism to clear the attacker's dust position and unblock `lending_pool_close_bank`.

### Impact Explanation
This durably freezes an admin operation (`lending_pool_close_bank`) that the group admin cannot recover from without out-of-band cooperation from the griefing depositor. While it does not directly redirect funds, it is a concrete unauthorized/uncontrollable state lock created entirely by an unprivileged actor against a privileged administrative function — directly matching the reported bug class ("arbitraryCall() can get blocked by an attacker"), where the acknowledged root cause is: state set by an unprivileged party that only that party (or a party with unrelated/blocked privileges) can clear, permanently obstructing a privileged instruction.

### Likelihood Explanation
The attack is essentially free: the attacker deposits the minimum unit of the bank's token (no health check is required for a pure deposit) and simply never withdraws it. There is no cost beyond negligible token amount plus rent for a `MarginfiAccount`, and the action requires no special permissions — any wallet can execute it. Any bank the admin later wants to retire becomes an easy griefing target.

### Recommendation
Given the marginfi maintainers already treat this exact bug class the same way the original Locke.sol authors did (per the source report's accepted resolution: "accept the risk but clearly communicate"), the same trade-off likely applies here — bank closure is a low-frequency admin housekeeping action, not a funds-critical path. If mitigation is desired, consider adding an admin-gated force-close/force-withdraw path (e.g., only usable when all remaining positions are known-empty-of-debt or dust) or a policy to disregard trivially small "dust" positions when evaluating close-eligibility, without touching the underlying token accounting.

### Proof of Concept
1. Admin creates and operationalizes `BankMint::Usdc`.
2. Attacker opens a `MarginfiAccount` and deposits `1` unit (minimum token amount) into the bank via the standard deposit instruction — this increments `bank.lending_position_count` to `1` and raises `total_asset_shares` above zero, as validated in the closure test which shows deposits blocking bank closure until fully withdrawn [5](#0-4) .
3. Attacker never withdraws.
4. Admin calls `lending_pool_close_bank`; it fails permanently with `BankCannotClose` because `lending_position_count != 0` [6](#0-5) , with no admin-side remedy available.

    /// so that banks whose balances are closed mid-liquidation don't stay permanently locked.
    pub fn close_balance(&mut self, in_receivership: bool) -> MarginfiResult<()> {
        let balance = &mut self.balance;
        let bank = &mut self.bank;

        let current_liability_amount =
            bank.get_liability_amount(balance.liability_shares.into())?;
        let current_asset_amount = bank.get_asset_amount(balance.asset_shares.into())?;

        check!(
            current_liability_amount.is_zero_with_tolerance(ZERO_AMOUNT_THRESHOLD),
            MarginfiError::IllegalBalanceState,
            "Balance has existing debt"
        );

        check!(
            current_asset_amount.is_zero_with_tolerance(ZERO_AMOUNT_THRESHOLD),
            MarginfiError::IllegalBalanceState,
            "Balance has existing assets"
        );

        let asset_shares: I80F48 = balance.asset_shares.into();
        let liability_shares: I80F48 = balance.liability_shares.into();
        // Counters are incremented in `*_balance_internal` when shares cross
        // `ZERO_AMOUNT_THRESHOLD` upward; match that condition so we don't
        // double-decrement positions that already crossed downward earlier.
        let had_assets = asset_shares.is_positive_with_tolerance(ZERO_AMOUNT_THRESHOLD);
        let had_liabs = liability_shares.is_positive_with_tolerance(ZERO_AMOUNT_THRESHOLD);

        balance.close()?;

        if in_receivership {
            bank.cache.clear_liquidation_price_cache_locked();
        }

        // Asset-side dust = real tokens still in the liquidity vault that the
        // user never withdrew. Route to `collected_insurance_fees_outstanding`
        // so vault content stays fully accounted for, mirroring the fractional-
        // remainder handling in `withdraw_all`.
        if current_asset_amount > I80F48::ZERO {
            bank.collected_insurance_fees_outstanding =
                I80F48::from(bank.collected_insurance_fees_outstanding)
                    .checked_add(current_asset_amount)
                    .ok_or_else(math_error!())?
                    .into();
        }

        bank.change_asset_shares(-asset_shares, false)?;
        // Liability-side dust = bad debt the borrower never repaid. Decrementing
        // here makes the loss explicit instead of leaving phantom shares in
        // `total_liability_shares` that would compound interest indefinitely.
        bank.change_liability_shares(-liability_shares, true)?;

        if had_assets {
            bank.decrement_lending_position_count();
        }
        if had_liabs {
