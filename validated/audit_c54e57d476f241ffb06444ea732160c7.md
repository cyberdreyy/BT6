### Title
Frontrunning `stopEpoch`/`getInstantWithdrawFunds` with `requestWithdraw` inflates `pendingWithdraws`, fails the borrower pull and forces a spurious borrower default - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
Analogous to the vesting-transfer DoS (a user's `claim()` frontrunning the privileged `transferVesting()` so its balance check reverts), an unprivileged KYC'd tranche holder can frontrun the manager's epoch-settlement call with `requestWithdraw()`. The request increases `IdleCreditVault.pendingWithdraws`, which `stopEpoch`/`stopEpochWithDuration` must source from the borrower in the same pull as `_amountToPullFromBorrower`. If the borrower funded/approved only the pre-frontrun amount, `getFundsFromBorrower` reverts — and instead of a simple revert, the `catch` block in `_stopEpoch` calls `_handleBorrowerDefault`, wrongfully declaring the pool defaulted. The same vector exists against `getInstantWithdrawFunds` via `requestInstantWithdraw`.

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw` any allowed wallet can burn tranche tokens and create a withdraw receipt; the vault then executes `pendingWithdraws += _amount` (`contracts/strategies/idle/IdleCreditVault.sol:279`). When the manager later calls `stopEpoch`/`stopEpochWithDuration`, `_stopEpoch` pulls `_amountToPullFromBorrower + _pendingWithdraws` from the borrower inside a `try`, and **any** failure of that pull is treated as a borrower default (`contracts/IdleCDOEpochVariant.sol:501-505`). `requestWithdraw` has no `isEpochRunning` gate — only `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and `isWalletAllowed` (`contracts/IdleCDOEpochVariant.sol:739-744`) — so it can be executed in the same block, immediately before the manager's `stopEpoch` transaction. Because the honest borrower's `approve`/balance only covers `expectedEpochInterest + pendingWithdraws` as observed when the `stopEpoch` tx was broadcast, the frontrun request makes the pull revert and the `catch` path fires `_handleBorrowerDefault`, which sets `defaulted = true`, pauses the contract, stops the epoch and disables both withdraw-request flags (`contracts/IdleCDOEpochVariant.sol:577-599`). The identical pattern exists in `getInstantWithdrawFunds`: `_pendingInstant` is pulled from the borrower, and an attacker can frontrun with `requestInstantWithdraw` (reachable via `requestWithdraw` when `lastEpochApr > currentApr + instantWithdrawAprDelta`, `contracts/IdleCDOEpochVariant.sol:761-769`) to push the pull over the funded amount and trigger `_handleBorrowerDefault(_instantWithdraws)` (`contracts/IdleCDOEpochVariant.sol:566-573`).

### Impact Explanation
A single frontrun converts a benign settlement call into a protocol-wide `BorrowerDefault`: the pool is paused, `isEpochRunning = false`, withdraw requests are disabled, and all lenders' claims are pushed onto the haircut-based default recovery path (`_claimDefaultedWithdrawRequest`, `defaultRecoveryPrice`) instead of par redemption. Until the owner runs `finalizeDefault`/`finalizeDefaultRecovery` with a recovery amount, all user funds are frozen; afterward every claim is haircut by the recovery ratio even though the borrower was willing and able to pay. The attacker's cost is only the time-value of their own receipt, which remains claimable post-default. This mirrors the external report (privileged action reverted by a user claim) but with strictly worse impact: not just a revert of one transaction, but a forced default state affecting every lender.

### Likelihood Explanation
The attack requires only a KYC-passing lender holding tranche tokens — no privileged role. Its success depends on the honest borrower granting a bounded allowance/balance equal to the expected repayment rather than an unlimited approval, which is the natural operational pattern when funding an exact `expectedEpochInterest + pendingWithdraws` figure. `requestWithdraw` is permissionless during both buffer and running epoch, and the frontrun is a single transaction in the public mempool. If the borrower pre-approves unlimited underlying, the pull succeeds and the attack degrades to a normal extra pending receipt (borrower still owes it), so likelihood is moderate rather than high — comparable to the judge's "valid Medium" assessment of the source finding.

### Recommendation
Decouple "borrower failed to pay what was known at settlement time" from "pendingWithdraws grew in the same block". Concretely: snapshot `_pendingWithdraws` at `startEpoch` (or compute the pull amount from a value captured before the current block, e.g. requiring `requestWithdraw`s created after `epochEndDate`/`instantWithdrawDeadline` to settle in the next epoch), or only enter `_handleBorrowerDefault` when the pull fails for the pre-snapshot amount. Alternatively, gate `requestWithdraw`/`requestInstantWithdraw` so requests made after `epochEndDate`/`instantWithdrawDeadline` cannot alter the amount the in-flight `stopEpoch`/`getInstantWithdrawFunds` must pull.

### Proof of Concept
```solidity
// Foundry PoC sketch against test/foundry/IdleCreditVault.t.sol harness
function testFrontrunStopEpochForcesDefault() external {
    uint256 amount = 10_000 * ONE_SCALE;
    address attacker = makeAddr("attacker");

    // Attacker deposits (KYC'd wallet) and pool runs a normal epoch
    _depositWithUser(attacker, amount, true); // AA tranche
    _startEpochAndCheckPrices(0);

    // Honest borrower funds/approves ONLY expectedEpochInterest + current pendingWithdraws
    uint256 expected = cdoEpoch.expectedEpochInterest()
        + IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(defaultUnderlying, borrower, expected);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), expected); // exact allowance

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Attacker frontruns manager's stopEpoch with a withdraw request.
    // This inflates pendingWithdraws inside the same stopEpoch pull.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(attacker), address(AAtranche));

    // Manager's stopEpoch now pulls more than borrower approved -> pull reverts
    // -> catch block calls _handleBorrowerDefault instead of a clean revert.
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // Pool is wrongfully defaulted: paused, epoch stopped, withdraw requests disabled
    assertTrue(cdoEpoch.defaulted(), "spurious borrower default");
    assertTrue(cdoEpoch.paused(), "pool paused");
    assertFalse(cdoEpoch.allowAAWithdrawRequest(), "AA requests disabled");
    assertFalse(cdoEpoch.allowBBWithdrawRequest(), "BB requests disabled");
}
```
The same pattern applies to `getInstantWithdrawFunds` when instant withdrawals are enabled: the attacker frontruns with `requestWithdraw` under a dropped APR (minting an instant receipt), inflating `_pendingInstant` past the borrower's funded amount and triggering `_handleBorrowerDefault(_instantWithdraws)`.
