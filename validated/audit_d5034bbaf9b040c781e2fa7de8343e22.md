### Title
Multisig requests can execute with confirmations from removed members counted toward the threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` counts entries in a request's `confirmations` `HashSet` against `num_confirmations` without verifying that each entry belongs to a still-current member. `delete_member` only purges requests *authored* by the removed member and their `num_requests_pk` counter; it never scans `confirmations` to strip that member's votes from *other* pending requests. A removed member's stale confirmation therefore keeps counting toward quorum, letting a request execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` implements the quorum check purely as a set-size comparison: [1](#0-0) 

The intended invariant is: `confirmations.len() == number of distinct *current* members who approved`. This equality is only maintained as long as membership never changes after a confirmation is cast. But `delete_member` breaks it: [2](#0-1) 

`delete_member` removes requests where `r.member == member` (i.e., requests *added* by the departing member) and clears that member's `num_requests_pk` entry, but it never iterates `self.confirmations` to remove the departing member's `String` key from the confirmation sets of requests added by *other* members. As a result, any request that the removed member had already confirmed keeps that confirmation "live" in storage, and it is counted the next time `confirm()` checks `confirmations.len() as u32 + 1 >= self.num_confirmations`.

This is the same root-cause pattern as the RBS report: a value that is trusted to represent a currently-valid state (a synced price / a live member's endorsement) is used without re-validating that it is still current, letting a stale, no-longer-authorized data point drive execution of a privileged action (draining a wall / executing a multisig request).

The identical pattern exists in the legacy `multisig/src/lib.rs` contract via `DeleteKey`, which removes requests signed by the deleted key but likewise never strips that key's confirmations from other pending requests: [3](#0-2) [4](#0-3) 

### Impact Explanation
This breaks the core custody/authorization binding of the multisig: `MultiSigRequestAction::Transfer`, `AddKey`, `AddMember`, `DeleteMember`, `FunctionCall`, etc. are all gated by `num_confirmations` distinct approvals from members who are members *at execution time*. With this bug, a request can execute after receiving approvals from fewer live members than `num_confirmations`, because a departed member's earlier confirmation is silently counted. This directly matches the Critical impact class "a multisig request executed below threshold" — funds can be transferred, keys added, or membership/threshold changed by a coalition smaller than the configured quorum of current members.

### Likelihood Explanation
No malicious member action is required — this occurs through ordinary multisig operation: (1) a member confirms a pending request without pushing it over threshold, (2) that member is later removed via a legitimate `DeleteMember` execution (an entirely routine and expected multisig operation), (3) the remaining members confirm the original request believing it still needs `num_confirmations` *current* approvals, but the stale confirmation makes the threshold reachable with one fewer live approval than intended. Any multisig that ever rotates members while it has outstanding, partially-confirmed requests is exposed.

### Recommendation
When removing a member in `delete_member` (and `DeleteKey` in the legacy contract), iterate all entries in `confirmations` (not just requests authored by that member) and remove the departing member's identifier from every confirmation set. Alternatively, validate at `confirm()` time that every entry in `confirmations` still corresponds to `self.members.contains(...)`, lazily pruning stale entries before comparing the count to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request` for `Transfer{amount}` to an attacker-controlled `receiver_id` → `request_id = 0`.
3. `B` calls `confirm(0)` → `confirmations = {B}` (1/3, not yet executed).
4. Members `A, C, D` create and confirm a `DeleteMember{member: B}` request, which executes via `delete_member` (lines 355-379) — this removes `B` from `members` but does **not** touch `confirmations[0]`, which still contains `B`.
5. `C` calls `confirm(0)` → `confirmations = {B, C}`, `len()+1 = 3 >= num_confirmations(3)` is not yet true (`len()==2`, `+1==3` → actually triggers here). Even with only `C`'s single additional live-member confirmation on top of the stale `B` entry, `execute_request` fires and the `Transfer` is sent — despite only `B` (removed) and `C` having "confirmed", i.e., only one *current* member's confirmation plus one stale, non-member confirmation, not three live-member approvals as `num_confirmations = 3` requires.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
