### Title
`AuthenticateBySession` fails to normalize `ErrUserSessionExpired`/DB errors into `ErrorAuthFailed`, causing valid-token requests to be rejected with 401 - ([File: core/web/auth/auth.go])

### Summary
`Authenticate`'s method loop only advances to the next auth method when the previous one returns `auth.ErrorAuthFailed`. `AuthenticateBySession` (unlike `AuthenticateByToken` and `AuthenticateExternalInitiator`) passes through the raw error from `AuthorizedUserWithSession` — including `sessions.ErrUserSessionExpired` and other DB errors — without converting it to `auth.ErrorAuthFailed`. As a result, a request that carries both a valid API token and a stale/forged/invalid session cookie will short-circuit on the session error and never reach `AuthenticateByToken`, producing a 401 despite valid token credentials.

### Finding Description
`Authenticate` iterates over the configured `authMethod`s and only continues to the next method if the current error `errors.Is(err, auth.ErrorAuthFailed)` [1](#0-0) . `AuthenticateBySession` retrieves the session ID from the cookie and, if present, calls `authr.AuthorizedUserWithSession`; any error from that call is returned verbatim, with no normalization to `auth.ErrorAuthFailed` [2](#0-1) .

The local ORM implementation of `AuthorizedUserWithSession` returns `sessions.ErrUserSessionExpired` for *any* failure to find a matching, unexpired session row or associated user (e.g., a forged/nonexistent session ID, or a transient DB error), and also returns a raw DB error if `updateSessionLastUsed` fails [3](#0-2) .

By contrast, `AuthenticateByToken` explicitly maps `sql.ErrNoRows` and `clsessions.ErrUserSessionExpired` to `auth.ErrorAuthFailed` before returning [4](#0-3) , showing this normalization was intended for cross-method fallthrough but was omitted in `AuthenticateBySession`.

Consequence: when `methods` is configured as `[AuthenticateBySession, AuthenticateByToken]` (the order used in `core/web/router.go`), a request with an attacker-supplied invalid/forged `clsession` cookie (any nonexistent or expired session ID) causes `AuthenticateBySession` to return `sessions.ErrUserSessionExpired`. Since that is not `auth.ErrorAuthFailed`, the loop in `Authenticate` breaks immediately (line 163) — `AuthenticateByToken` is never invoked, even though the same request carries valid `X-API-KEY`/`X-API-SECRET` headers. `c.Abort()` + 401 is returned to the caller.

### Impact Explanation
This is a *denial-of-service on legitimate authenticated requests* rather than a privilege escalation: a client holding a valid, legitimate token can be locked out of the API for any endpoint reachable with a stray/expired/forged session cookie (e.g., a browser tab with a stale session cookie also configured to send API token headers, or an attacker who can plant a cookie in a victim's browser via other means and cause their token-based automation to fail). There is no context pollution or method confusion — `c.Set(SessionUserKey, ...)` is never reached because the loop aborts before any method succeeds, so no identity is set at all; `GetAuthenticatedUser` correctly reports "not ok" and downstream role checks reject the request. This does not amount to authentication bypass, privilege escalation, or cross-user data exposure — it is only a robustness/availability defect in the token fallback chain.

### Likelihood Explanation
Trivial to trigger: requires only sending both a `clsession` cookie with a bogus/expired session ID and valid `X-API-KEY`/`X-API-SECRET` headers in the same request, no special privilege needed beyond already possessing a valid token. However, this only affects the *token holder's own* request; it does not let the attacker impersonate or access another user's data, so it stays within a low-severity availability bug rather than the authentication-soundness violation class requested (no cross-identity or privilege-escalation impact is achievable — the loop never sets an identity for a "wrong" method to leak).

### Recommendation
Normalize errors in `AuthenticateBySession` the same way `AuthenticateByToken` does: map `clsessions.ErrUserSessionExpired`, `clsessions.ErrEmptySessionID`, and `sql.ErrNoRows` to `auth.ErrorAuthFailed` before returning, so that a failed/forged session cookie always falls through to subsequent auth methods rather than aborting the chain.

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

func (o *orm) AuthorizedUserWithSession(ctx context.Context, sessionID string) (user sessions.User, err error) {
	if len(sessionID) == 0 {
		return sessions.User{}, sessions.ErrEmptySessionID
	}

	email, err := o.findValidSession(ctx, sessionID)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	user, err = o.findUser(ctx, email)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	if err := o.updateSessionLastUsed(ctx, sessionID); err != nil {
		return sessions.User{}, err
	}

	return user, nil
}
