## Finding

### Title
Stale confirmations from removed multisig members/keys still count toward the execution threshold - ([File: multisig2/src/lib.rs])

### Summary
The multisig contracts (`multisig` and `multisig2`) let a member/key confirm any pending request. When a member (or access key) is later removed via `DeleteMember`/`DeleteKey`, the contract only purges requests and confirmations that the *removed member itself created* — it never scrubs that member's confirmation entries from *other* requests it had previously confirmed. Because `confirm()` only checks the raw size of the confirmations set against a fixed `num_confirmations`, a vote cast by a member who is no longer part of the multisig still counts toward the quorum, letting a request execute with fewer live-member approvals than the configured threshold. This is the exact analog of the reported oDAO issue: kicked members' votes are still tallied while the effective member set shrinks.

### Finding Description
`confirm()` compares the size of the stored confirmation set to `self.num_confirmations` with no regard for whether every confirming identity is still a current member: [1](#0-0) 

`delete_member()` only cleans up requests that the removed member itself originated (`r.member == member`), and only clears `num_requests_pk` for that member — it does not scan `self.confirmations` for entries referencing the removed member on requests created by *other* members: [2](#0-1) 

The same pattern exists in the legacy `multisig` contract's `DeleteKey` handling, which only removes requests where `r.signer_pk == pk`, leaving that key's confirmations on other requests intact: [3](#0-2) 

The binding that should hold is:
```
confirmations.len() (restricted to current members) >= num_confirmations
```
but the code enforces:
```
confirmations.len() (including stale entries from removed members) >= num_confirmations
```
i.e. the on-chain vote tally diverges from the live member set, exactly the class of bug described in the oDAO report ("confirmations counted versus live members").

### Impact Explanation
This crosses the "a multisig request executed below threshold" Critical impact bucket: a `Transfer`, `FunctionCall`, `AddKey`, or any other multisig action can be executed with fewer than `num_confirmations` *current* members having approved it, because a stale vote from an already-removed member/key fills one of the required confirmation slots. This can move funds or grant access below the configured authorization threshold.

### Likelihood Explanation
Member/key removal (`DeleteMember`/`DeleteKey`) is a normal, expected multisig operation (e.g. rotating out a compromised or departing signer). Any request that received a confirmation from a member prior to that member's removal will retain the stale vote automatically — no special conditions or race are needed beyond the ordinary sequence: confirm → remove that confirmer → confirm again with fewer live approvals than intended.

### Recommendation
When removing a member/key (`delete_member` in `multisig2`, `DeleteKey` in `multisig`), iterate over **all** `confirmations` entries (not just requests originated by that member) and strip the removed member's/key's entry from each set. Alternatively, validate at `confirm()`/execution time that every identity present in a request's confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
Using `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`:
1. `B` calls `add_request()` creating request `#1` (e.g. `Transfer{amount}` to some receiver). Confirmations for `#1` = `{}`.
2. `A` calls `confirm(1)`. Confirmations for `#1` = `{A}` (1/3).
3. The group legitimately decides to remove `A` (e.g. compromised key) and executes a `DeleteMember{member: A}` request confirmed by `B, C, D`. `delete_member()` runs: it only removes requests where `r.member == A`; request `#1` was created by `B`, so it is untouched, and `A` is removed from `self.members` — but `A`'s stale confirmation entry stays in request `#1`'s confirmation set.
4. `C` calls `confirm(1)` → confirmations = `{A, C}` (2/3).
5. `D` calls `confirm(1)` → confirmations = `{A, C, D}` (3/3) → `execute_request` fires, transferring funds — even though `B`, the actual request creator and a still-current member, never confirmed, and the "third" approval came from `A`, who was already removed from the multisig at step 3.

This shows the 3-of-4 threshold was satisfied with only 2 approvals from currently-active members plus 1 stale vote from a removed member, exactly mirroring the oDAO "kicked member votes still counted" pattern. [4](#0-3) [5](#0-4)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
