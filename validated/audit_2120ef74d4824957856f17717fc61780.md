### Title
Front-running `SystemInstruction::CreateAccount` by pre-funding a target address causes permanent `AccountAlreadyInUse` denial-of-service — ([File: programs/system/src/system_processor.rs])

### Summary
The reported OneWorld bug is a classic "claim-before-you" race: anyone watching for a pending `MembershipFactory::createNewDAOMembership` call can front-run it and register the same name first, since the contract only checks "does this key already exist?" before writing. The direct analog in Agave is the system program's `CreateAccount` instruction, whose `create_account` handler in `programs/system/src/system_processor.rs` treats any account with `lamports > 0` as "already in use" and unconditionally fails. An attacker who observes a pending transaction that will call `CreateAccount` for a specific address (e.g., a deterministic PDA/seeded address) can front-run it with a plain `SystemInstruction::Transfer` of a single lamport to that address, permanently blocking the legitimate `CreateAccount` from ever succeeding at that address.

### Finding Description
`create_account` in `programs/system/src/system_processor.rs` implements the "doesn't exist yet, so create it" check purely on the target account's lamport balance: [1](#0-0) 

If `to.get_lamports() > 0`, the instruction returns `SystemError::AccountAlreadyInUse` regardless of who put the lamports there. Because `Transfer` (and gossip/streamer-observable transactions in general) can target an arbitrary destination address without requiring that address to sign, an attacker who sees a user's pending `CreateAccount`/`CreateAccountWithSeed` transaction (e.g., in the mempool/gossip, or by simply guessing a deterministic seeded/derived address used by a well-known program) can send a cheap transfer of 1 lamport to that address first. When the victim's transaction subsequently executes, `create_account` sees `lamports > 0` and fails with `AccountAlreadyInUse`, exactly mirroring the ENS-name-squatting pattern in the report where the "already exists" check can be satisfied by an attacker instead of the legitimate creator.

This is confirmed as a known, real limitation by the existence of `SystemInstruction::CreateAccountAllowPrefund`, a new instruction gated behind the `create_account_allow_prefund` feature (SIMD-0312) that was added specifically to tolerate pre-funded destination accounts: [2](#0-1) [3](#0-2) 

Crucially, `CreateAccountAllowPrefund` is opt-in: it must be explicitly invoked by a program/client instead of `CreateAccount`, and is only active once the feature is enabled. Any existing on-chain program or client that still issues the ordinary `SystemInstruction::CreateAccount` (the overwhelming majority of the ecosystem, since this is the default/legacy instruction) remains fully exposed to the pre-funding front-run, since `create_account`'s "already in use" gate is unconditional on lamports: [4](#0-3) 

### Impact Explanation
This is a denial-of-service / griefing primitive reachable from any ordinary, unprivileged user transaction (a plain `SystemInstruction::Transfer`, requiring only 1 lamport and a fee). It can be used to:
- Permanently block a specific address from ever being initialized via `CreateAccount`/`CreateAccountWithSeed` (e.g., PDAs or seeded accounts many programs rely on for one-time account initialization), causing the victim's transaction to fail with `AccountAlreadyInUse`.
- Grief protocols that assume "if `CreateAccount` at this deterministic address fails, the account must already exist and be valid," potentially causing programs to enter unexpected states or fail open/closed depending on their error handling.
- Force victims to retry with alternate seeds/addresses, which for identity- or name-based derivations (directly mirroring the reported DAO-name-squatting issue) may not be feasible at all, since the destination address itself is often the resource users are trying to claim.

This does not permit unauthorized fund transfer or state corruption of the attacked account (it stays owned by the System Program), but it is a real, low-cost, unauthenticated DoS/front-running vector against unprivileged account initialization traffic.

### Likelihood Explanation
High likelihood for any observer of the mempool/gossip layer or anyone who can predict a target address (e.g., PDAs derived deterministically from known seeds, which is standard practice). The attack costs a single lamport transfer plus a normal transaction fee, requires no special privileges, and Agave's own introduction of `CreateAccountAllowPrefund` (SIMD-0312) as a dedicated mitigation is direct evidence that this attack class is recognized and was, prior to that feature, unmitigated for the default `CreateAccount` path.

### Recommendation
- Encourage/require programs and wallets that create accounts at deterministically-derivable addresses to migrate to `SystemInstruction::CreateAccountAllowPrefund` once `create_account_allow_prefund` is active, since it tolerates pre-funded destinations by skipping the `lamports > 0` failure and only transferring the additional lamports needed.
- Where possible, use `create_account_with_seed`/PDA schemes that require a base account signature so that only the legitimate creator can complete initialization, rather than schemes purely gated on lamport-balance emptiness.
- Document clearly in system-program instruction docs that `CreateAccount` (unlike `CreateAccountAllowPrefund`) is front-runnable via prefunding, so integrators understand the trust assumptions.

### Proof of Concept
1. Victim program/client intends to call `SystemInstruction::CreateAccount` to initialize a deterministic address `P` (e.g., derived via `Pubkey::create_with_seed` or a PDA-equivalent scheme) it does not yet control.
2. Attacker observes the pending transaction (mempool/gossip) or independently predicts `P` from public seed material, and submits `SystemInstruction::Transfer { lamports: 1 }` targeting `P`, landing before the victim's transaction.
3. Victim's `CreateAccount` instruction now executes against an account with `lamports = 1 > 0`; per `create_account` in `programs/system/src/system_processor.rs` (lines 160-171), it returns `SystemError::AccountAlreadyInUse`, and the victim's transaction fails — see the equivalent behavior asserted in `test_create_already_in_use` at `programs/system/src/system_processor.rs` lines 1014-1040, where an account with as little as 1 lamport causes `CreateAccount` to fail unconditionally.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
