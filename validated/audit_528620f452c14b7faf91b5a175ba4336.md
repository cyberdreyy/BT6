### Title
Unbounded native-stack recursion in `TrieNode::decode` via a single crafted preimage causes fault-proof program stack exhaustion / node halt - (File: `crates/proof/mpt/src/node.rs`)

### Summary
`TrieNode::decode` recursively decodes nested RLP list structures (`Branch`/`Extension`) with no depth limit, and is invoked directly on preimage bytes returned by the oracle client whose only validation is that `keccak256(bytes) == requested_key` [2](#0-1) . Because the decoder does not enforce that elements which should have been blinded (i.e., that are `>= 32` bytes when re-encoded) are actually 32-byte hash commitments, a single preimage blob can encode a deeply nested chain of `Branch` nodes, each triggering another recursive call to `TrieNode::decode`/`Vec::<Self>::decode` [4](#0-3) . This is directly analogous to CVE-2020-18898's stack exhaustion in Exiv2's `printIFDStructure`, where unbounded recursive parsing of an attacker-controlled nested structure exhausts the call stack.

### Finding Description
- `TrieNode::decode` peeks the RLP header, and if the payload is a list of length `BRANCH_LIST_LENGTH` (17), it calls `Vec::<Self>::decode(buf)`, which decodes each of the 17 elements by calling `TrieNode::decode` again [5](#0-4) .
- The `Encodable` implementation only blinds (replaces with a 32-byte hash) a child node if its *encoded length* is `>= 32` bytes [6](#0-5) , but `Decodable` never re-verifies this invariant — it happily decodes an inline nested `Branch` list of any size directly from the buffer, without needing a further oracle round-trip.
- `OracleL1ChainProvider`/`OracleL2ChainProvider::trie_node_by_hash` fetch a Keccak256-typed preimage and pass the raw bytes straight into `TrieNode::decode` [7](#0-6) [8](#0-7) .
- The preimage client `OracleReader::get` trusts a host-supplied length prefix with no upper bound and allocates/reads exactly that many bytes [9](#0-8) .
- Because only the *outer* blob's hash is checked (by the preimage-oracle infrastructure, standard for content-addressed Keccak256 preimages), the attacker (whoever supplies the preimage data — e.g., a dispute-game participant running their own preimage server/host for the op-program-style fault-proof execution) fully controls the internal byte layout of that one blob and can nest, e.g., thousands of `Branch{stack:[Empty x15, nested Branch]}` RLP lists to build one blob whose decode requires thousands of nested native stack frames.
- This directly mirrors the bug class in CVE-2020-18898: `printIFDStructure` in Exiv2 recursed once per nested IFD entry in a crafted image with no depth cap, exhausting the stack; here `TrieNode::decode`/`Vec<TrieNode>::decode` recurse once per nested (fake) Branch entry in a crafted trie-node preimage with no depth cap.

### Impact Explanation
Any process that executes the fault-proof/derivation pipeline against an untrusted or adversarial preimage source (e.g., a dispute-game participant's own preimage server backing their claim, or an offline/attacker-controlled `TrieProvider`) can be crashed via native stack overflow while decoding a single malicious trie-node preimage. A stack overflow in these environments typically aborts the process (panic/SIGSEGV) rather than returning a recoverable `Result`, denying that node the ability to complete verification/execution of the disputed claim — a concrete node-halt / denial-of-service impact within the fault-proof program's reachable surface explicitly in scope.

### Likelihood Explanation
The primitive is very easy to construct: an attacker only needs to choose byte content whose keccak256 hash they control (trivial, since they are the one serving/producing that preimage blob) and nest RLP `Branch` lists to any needed depth within the size bounds accepted by the preimage transport. No cryptographic breaks, no privileged access, and no interaction with legitimate state data are required — solely the ability to serve or claim a preimage during dispute-game/op-program execution, which is the assumed threat model for a "dispute-game participant."

### Recommendation
Add an explicit recursion/nesting-depth limit (or convert `TrieNode::decode` to an iterative/work-list based decoder with a bounded stack) and reject any list element inside a `Branch`/`Extension` whose raw encoded length is `>= 32` bytes but is not itself a valid 32-byte blinded commitment, restoring the encode/decode symmetry invariant documented in the type's doc comment [10](#0-9) .

### Proof of Concept
1. Construct a deeply nested `TrieNode::Branch` chain purely in memory: `let mut n = TrieNode::Leaf{...}; for _ in 0..N { n = TrieNode::Branch{ stack: vec![n, Empty, Empty, ..., Empty] } }` (17-element stack each level) and RLP-encode it to `bytes` (bypassing the normal blinding-on-encode path by constructing the enum directly rather than via `insert`, so no blinding occurs even though a child exceeds 32 bytes).
2. Compute `hash = keccak256(&bytes)`.
3. Implement/run a `TrieProvider`/preimage host that, for `PreimageKey::new(hash, PreimageKeyType::Keccak256)`, returns `bytes` verbatim (this is what any custom or dispute-side preimage server does for its own claim data).
4. Have the fault-proof program (`OracleL1ChainProvider`/`OracleL2ChainProvider::trie_node_by_hash`, or the offline `TrieNode::decode` test harness path in `crates/proof/proof/src/eip2935.rs`) call `TrieNode::decode(&mut bytes.as_ref())` for `hash`.
5. With sufficiently large `N` (bounded only by preimage transport size limits, which are unbounded on the client side per `OracleReader::get`), the recursive decode exhausts the native stack and crashes the process before returning any `Result`.

impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
        } else {
            match header.payload_length {
                0 => {
                    buf.advance(header.length());
                    Ok(Self::Empty)
                }
                32 => {
                    let commitment = B256::decode(buf)?;
                    Ok(Self::new_blinded(commitment))
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
        }
    }
}
