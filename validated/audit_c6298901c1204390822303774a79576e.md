### Title
Single-signer flip-flopping inflates both approval and rejection weight tallies, breaking the "aggregated weight ⇔ verified accepts" equality — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` accumulates two independent weight counters — `total_weight_approved` and `total_weight_rejected` — from `BlockResponse::Accepted` / `BlockResponse::Rejected` messages, each gated by its own de-duplication structure. Because these two gates (`gathered_signatures` and `responded_signers`) are not mutually exclusive against each other, a single signer who first rejects and later accepts the same block (a sequence the signer protocol itself allows via re-evaluation) has its weight counted into **both** totals simultaneously. This breaks the invariant `total_weight_approved + total_weight_rejected <= total_weight` that `NakamotoSigningCoordinator` relies on to decide whether a block has genuinely reached the 70% signing supermajority.

### Finding Description
`handle_signer_messages` (the message-processing loop in `stackerdb_listener.rs`) maintains a `BlockStatus` per proposed block with two accounting maps/sets:

- `gathered_signatures: HashMap<slot_id, signature>` — gates whether an `Accepted` message adds weight to `total_weight_approved`: [1](#0-0) 
- `responded_signers: HashSet<slot_id>` — shared across both branches, and is the sole gate for whether a `Rejected` message adds weight to `total_weight_rejected`: [2](#0-1) 

Trace both directions:
- **Accept → Reject**: An `Accepted` message unconditionally inserts the slot into `responded_signers` (line 465), so a subsequent `Rejected` from the same signer finds `responded_signers.insert(slot_id)` return `false` and is correctly *not* double-counted.
- **Reject → Accept**: A `Rejected` message inserts the slot into `responded_signers` (line 515) but never touches `gathered_signatures`. A subsequent `Accepted` from the same signer only checks `gathered_signatures.contains_key(&slot_id)` (line 443), which is still empty, so the weight is added to `total_weight_approved` **in addition to** the weight already added to `total_weight_rejected` from the earlier rejection.

The result: a single signer's weight can simultaneously back a rejection verdict and an approval verdict for the same `signer_signature_hash`. This directly parallels the UNION `cancelVouch`/`updateLocked` bug class: an accounting structure (`vouchers` array order / here, two independent weight tallies) is mutated in a way that silently violates the invariant the higher-level business logic (redemption priority / here, the 70%-threshold decision) depends on, without any explicit code path enforcing the intended one-vote-per-signer-per-outcome semantics.

The consumer of this state, `NakamotoSigningCoordinator::wait_for_signatures` in `stacks-node/src/nakamoto_node/signer_coordinator.rs`, treats `total_weight_approved` as proof that ≥70% of signer weight genuinely endorses the block and pushes it: [3](#0-2) 
and treats `total_weight_rejected` crossing the blocking-minority line as proof the block is dead: [4](#0-3) 

Because a rejecting signer's weight can leak into the approval counter, `total_weight_approved` no longer certifies that 70% of *distinct, currently-endorsing* signer weight backs the block — some of that counted weight belongs to a signer who is on record (via the same message stream) as having rejected it. This is the "aggregated-weight vs verified-accepts" equality named explicitly in scope.

### Impact Explanation
This lets the miner-side coordinator conclude a block has reached the supermajority threshold using weight that does not correspond to 70% distinct approving signers, because part of the counted weight is contributed by a signer whose most recent/only verdict on the underlying content was (or also was) a rejection. In a close vote (e.g., total approving weight just under 70% and a signer who initially rejected — perhaps a legitimately reconsidered rejection per the documented `should_reevaluate_reject_reason` re-evaluation flow — later accepts on re-proposal), the flip-flopping signer's weight is credited twice, which can:
- Push `total_weight_approved` over threshold and cause the coordinator to broadcast/push a block that a genuine 70%-of-distinct-weight supermajority did not actually endorse, or
- Simultaneously satisfy the blocking-minority (>30% reject) condition, creating a contradictory internal state (`SignersRejected` vs "signed") depending on evaluation order/timing.

This is a signer-set accounting break reachable without any majority collusion — a single signer's ordinary message sequence (reject then accept, or vice versa is safely guarded but the reverse is not) is sufficient, satisfying the "one-slot signer (plus gossip)" threat model.

### Likelihood Explanation
The trigger requires only one signer sending a `Rejected` message followed later by an `Accepted` message for the identical `signer_signature_hash` — a sequence explicitly enabled by the documented re-proposal/re-evaluation flow (`should_reevaluate_reject_reason`, `PC -- yes --> RESEND` in `docs/signer-flows.md`), where a signer that rejected can later be re-routed to accept the same block hash on re-proposal. No special privileges, majority, or malicious collusion are required — only ordinary protocol timing (or a mildly adversarial single signer intentionally flip-flopping over StackerDB gossip).

### Recommendation
Track a single per-signer "final verdict" state instead of two independently-gated counters. Before adding weight to either `total_weight_approved` or `total_weight_rejected`, check and clear the signer's slot from the *other* bookkeeping structure (or maintain one `HashMap<slot_id, Verdict>` where `Verdict ∈ {Accepted, Rejected}` and switching state debits the previous tally and credits the new one), so that at any point `total_weight_approved + total_weight_rejected` reflects exactly the sum of *current, non-overlapping* signer verdicts and never exceeds `total_weight` from a single signer's contribution to both sides.

### Proof of Concept
1. A block `B` is proposed to a reward set with signers `S1..Sn`; assume total weight is `T` and threshold is `0.7T`.
2. Signer `S_x` (weight `w`) sends `BlockResponse::Rejected` for `B`. `stackerdb_listener.rs` inserts `slot(S_x)` into `responded_signers` and adds `w` to `total_weight_rejected`.
3. Enough other signers already push `total_weight_approved` to `0.7T - w` (just short of threshold without `S_x`).
4. `S_x` later reconsiders (per the documented re-evaluation flow) and sends `BlockResponse::Accepted` for the same `signer_signature_hash`. Because `gathered_signatures` never recorded `S_x`, the accept branch's guard `!block.gathered_signatures.contains_key(&slot_id)` is true, so `w` is added to `total_weight_approved`, bringing it to `0.7T` — meeting the threshold — while `total_weight_rejected` still separately holds `w` from step 2.
5. `NakamotoSigningCoordinator::wait_for_signatures` observes `total_weight_approved >= weight_threshold` and returns `Ok(gathered_signatures)`, pushing the block, even though `S_x`'s weight is simultaneously recorded against it as a rejection in the same `BlockStatus`, and the true distinct-signer approving weight (excluding the double-counted `w`) was only `0.7T - w`.
