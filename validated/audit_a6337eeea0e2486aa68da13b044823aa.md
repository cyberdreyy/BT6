### Title
Consensus-critical checks in `check_proposal` (miner pubkey hash, consensus hash, PoX bitvec, tenure-extend, duplicate-tenure-block) are evaluated only once at proposal time and never re-verified before the signer actually signs - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The signer's decision to place its irreversible signature on a block is split into two temporally separated stages: (1) a full validity check at proposal arrival (`check_block_against_state` → `check_proposal` in `chainstate/v1.rs`/`chainstate/v2.rs`), and (2) the actual signing, which happens either immediately on a validate-ok response or later, whenever the pre-commit weight crosses 70%. Between these stages only a narrow subset of checks (`check_block_against_signer_db_state`, i.e. `check_latest_block_in_tenure`) is re-run. Several consensus-relevant checks that were only evaluated once, at proposal time, are never repeated before the signature is produced.

### Finding Description
`handle_block_proposal` runs the full check once: [1](#0-0) 

which for v2 delegates to `GlobalStateView::check_proposal`. The signer-flows documentation explicitly states which checks live only in that proposal-time wrapper and are never repeated: [2](#0-1) 

By contrast, at validate-ok time and at the pre-commit-threshold-crossing (the moment the signature is actually produced), only the much narrower `check_block_against_signer_db_state` (== `check_latest_block_in_tenure`) is re-run: [3](#0-2) [4](#0-3) 

Crucially, reaching the 70% pre-commit weight threshold that triggers the actual signature is not bounded to happen promptly after proposal — the flow explicitly acknowledges the world can change materially in between: [5](#0-4) 

So the sequence "miner pubkey hash valid → consensus hash matches active burn view → PoX bitvec valid → tenure-extend rules satisfied → no duplicate tenure-start block" is established once, at proposal time, and is treated as still true when the signature is finally emitted — even though a Bitcoin fork, reward-cycle/PoX-anchor change, or tenure-extend timing shift occurring in the intervening window (which can be arbitrarily long while pre-commits trickle in) can invalidate any of those facts. This is structurally the same class of bug as the report: a gating check (repay) is disabled/becomes stale, but the dependent irreversible action (liquidate / here, sign) proceeds anyway because it was authorized once upstream and is not re-validated at the point where it actually executes.

The documentation itself flags this same asymmetry for one of the checks (`DuplicateBlockFound`) and asserts it is covered by the "own-tenure conflict guard" in the pre-commit path: [6](#0-5) 

However, that guard (`get_signed_conflicts` / `conflict_still_blocks`, section 5) only reasons about conflicting *signed* siblings at the same/higher block height — it does not re-derive or re-check the miner's public-key hash, the block's `consensus_hash` against the *current* active burn view, the PoX bitvec, or the tenure-extend timing rules. Those specific facts, once true at proposal time, are simply assumed still true at signing time with no code path re-deriving them.

### Impact Explanation
If the burn chain forks (or a reward-cycle/PoX-anchor transition happens) after a block is proposed but before enough peers have pre-committed, the `consensus_hash`/pubkey-hash/PoX-bitvec facts that gated the original proposal acceptance can become stale/incorrect. Because those checks are never rerun at the moment the signer actually emits its signature, a signer can end up placing a valid cryptographic signature on a block that is no longer consistent with the canonical burn view (i.e., a signature over a non-canonical or otherwise-invalid block). This breaks the "signed vs validated" equality the whole two-round design (pre-commit → recheck → sign) is meant to preserve, and matches the Critical impact category: a signer signing an invalid/non-canonical block.

### Likelihood Explanation
Reachable by a single miner plus normal chain/gossip activity — no majority-signer collusion, no auth token, no other signer's key is required. The precondition is simply that the pre-commit-threshold-crossing (i.e., the actual signing event) happens materially later than the proposal-time check, which the docs concede is expected/normal (network latency, contended tenures, slow peers). A one-slot miner can also actively widen this window (e.g., by delaying its own re-broadcast/behavior, or by timing a proposal just before a burn-chain event) to increase the chance that the intervening window straddles a fork or PoX-relevant boundary.

### Recommendation
Re-run the same checks that the proposal-time `check_proposal` wrapper performs (miner pubkey hash, consensus-hash-vs-active-burn-view, PoX bitvec, tenure-extend rules, duplicate-tenure-start) as part of `check_block_against_signer_db_state`, so that they are also enforced immediately before `mark_pre_committed`/signing (`handle_block_validate_ok`) and immediately before the signature is actually emitted at pre-commit-threshold crossing (`handle_block_pre_commit`). Alternatively, bound the maximum time between proposal-time validation and signing (fail/re-propose if the pre-commit threshold isn't reached within a freshness window), so the assumptions validated at proposal time cannot silently go stale before the irreversible signature is produced.

### Proof of Concept
Not independently reproducible from the indexed context alone — the underlying mechanism (asymmetric checks between `check_proposal` at proposal time vs. `check_block_against_signer_db_state` at signing time) is explicitly documented in the codebase's own design notes: [7](#0-6) 
and confirmed by the actual call sites shown above in `stacks-signer/src/v0/signer.rs` (`handle_block_proposal` line ~1670-1672, `handle_block_validate_ok` line ~1941-1959, `handle_block_pre_commit` line ~1345-1366). A full runnable PoC (simulating a burn fork between proposal and pre-commit-threshold crossing) would require constructing a `SignerTest`/`MultipleMinerTest` scenario that stalls pre-commit accumulation across a burn-chain fork boundary, which is not fully verifiable from the indexed snippets alone; a Devin session with full repo/test-harness access would be needed to build and run that scenario end-to-end.
