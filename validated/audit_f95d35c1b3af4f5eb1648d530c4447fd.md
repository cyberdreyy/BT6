### Title
Unbounded per-slot signature index scan in `Blockstore::find_address_signatures_for_slot` allows a single `getSignaturesForAddress` call to incur cost proportional to attacker-inflated address activity in one slot - (File: ledger/src/blockstore.rs)

### Summary
`getSignaturesForAddress` is served by `JsonRpcRequestProcessor`/`Blockstore::get_confirmed_signatures_for_address2`, which begins by calling `Blockstore::find_address_signatures_for_slot` to gather every signature for the target address in a starting slot before applying the caller's `limit`. This is analogous to the reported `_removeNft` bug: an attacker can cheaply inflate a shared, address-keyed collection (transactions referencing a target address within one slot), and any later unprivileged caller who queries that address pays the full unbounded iteration cost in a single RPC call, regardless of the `limit` parameter they requested.

### Finding Description
`find_address_signatures_for_slot` iterates the `address_signatures_cf` column family starting at `(pubkey, slot, 0, Signature::default())` and pushes every matching entry into a `Vec` until it hits a different slot or address, with no cap: [1](#0-0) 

This function is invoked unconditionally, before the caller-supplied `limit` is ever applied, at the very start of `get_confirmed_signatures_for_address2`: [2](#0-1) [3](#0-2) 

The `limit` is only enforced afterwards, in the subsequent reverse-direction iterator loop (`while address_signatures.len() < limit`) and in the final `.take(limit)` on the merged list: [4](#0-3) 

Because the initial "get signatures in `slot`" step has no limit, the number of entries collected for a single address in a single slot is bounded only by how many transactions in that slot touch the target address — controlled by whoever sends transactions naming that address, not by the RPC caller. An adversary can cheaply send many transactions (e.g., simple transfers, or transactions that merely list the target address as a readonly/writable account) that all reference one victim/target `Pubkey` within the same slot. Every subsequent, unprivileged, single `getSignaturesForAddress` call for that address (even with `limit=1`) then forces the node to build and reverse a `Vec` sized to the full count of matching entries in that slot before any limiting is applied — this happens on every call as long as the highest-slot/`before` resolution lands on (or after) that inflated slot.

This mirrors the `_removeNft` pattern precisely: a low-cost, permissionless action (sending ordinary transactions vs. sending NFTs) inflates a persistent, address-keyed data structure that is fully scanned by an unrelated, unprivileged read operation, with no bound tied to the actual amount of data the caller asked for.

### Impact Explanation
A single `getSignaturesForAddress` JSON-RPC call (unprivileged, standard API surface) can consume CPU and memory proportional to the total number of transactions any user chooses to send referencing a specific address within one slot, rather than to the caller's requested `limit`. Popular/hot addresses (exchanges, DEX pools, program-derived accounts receiving many small transfers) are natural, low-cost targets. This creates elevated and attacker-influenced RPC latency/resource cost for legitimate callers querying that address, satisfying the "unbounded cost for a single low-rate call" impact category. It does not crash or corrupt the validator/consensus state, but degrades the responsiveness of a widely used JSON-RPC method under adversary-controlled load.

### Likelihood Explanation
Likelihood is moderate: an attacker only needs the ability to submit ordinary transactions naming a target address as an account key within the same slot — a normal, permissionless, and cheap action (paying only standard transaction fees), no privileged role or malicious program is required. The main limiting factor is the maximum number of transactions/accounts that can be packed into a single slot under block compute/size limits, which still permits a substantial number of low-compute transactions (e.g., simple SOL transfers) to reference the same address in one slot.

### Recommendation
Enforce the `limit` parameter (or an internal safety cap) inside `find_address_signatures_for_slot` itself, e.g., by breaking out of the loop once `signatures.len()` reaches the requested limit (or a hard maximum), rather than collecting the entire per-slot match set unconditionally. Alternatively, restructure the query so slot-local signature collection is limit-aware from the start, symmetric with how the subsequent reverse iterator already respects `limit`.

### Proof of Concept
Conceptual PoC (cannot be executed in this read-only environment):
1. Choose a target `Pubkey` `V` (e.g., a victim's or a widely-used hot account).
2. Within a single slot, submit many cheap transactions (e.g., zero/low-value SOL transfers or transactions that merely include `V` as one of the account keys) so that hundreds/thousands of entries are written to the `address_signatures_cf` column family for `(V, slot, ...)`.
3. As an unprivileged client, call `getSignaturesForAddress` for `V` with `limit: 1`.
4. Observe that the node must still execute `find_address_signatures_for_slot`, which builds and reverses a `Vec` containing all matching entries for that slot before any limiting occurs — i.e., the actual work done by the single RPC call scales with the attacker-inflated slot data rather than with the requested `limit`.

Note: I was unable to execute or profile this in the current read-only environment; the analysis is based on static code review of `ledger/src/blockstore.rs`. A background Devin session with build/test tooling would be needed to empirically measure the latency/CPU impact for a given inflation factor.
