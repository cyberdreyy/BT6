## Title
Node-unreachable fallback in the own-tenure conflict check lets a signer double-sign conflicting siblings in the same tenure - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_pre_commit` re-checks, at the moment the pre-commit threshold is crossed, whether any previously *signed* sibling at the same/higher height still blocks the new block from being signed [1](#0-0) . For same-tenure conflicts whose reorg permit does not stand, the code asks the node's `get_tenure_tip` for that tenure's canonical height; if the tip is at/above the proposed height it refuses to sign, but **if the RPC errors it logs "Treating the tenure as unconfirmed" and falls through to signing anyway** [2](#0-1) . This is the opposite default used everywhere else in the same guard: `conflict_still_blocks` treats every node-query failure as "keep blocking" precisely because "wrongly signing cannot be taken back" [3](#0-2) . The own-tenure branch inverts that fail-safe default to fail-open.

### Finding Description
The pre-commit → signature flow is designed so a "fresh" signed conflict (a block this signer already signed or saw signed at the same/higher chain height) blocks a competing signature, and every node lookup used to decide whether the conflict is still live defaults to "still blocks" on any node error, exactly as documented: *"Whenever the node cannot be asked, the conflict keeps blocking: that only delays the replacement... whereas wrongly signing cannot be taken back."* [4](#0-3) 

That rule is implemented consistently in `conflict_still_blocks` (`Err(e) => { ... return true; }` on every failure path, including a plain RPC error and a 404 whose peer-info lookup itself fails) [5](#0-4) . But the *same-tenure* special case at lines 1432-1457 does not call `conflict_still_blocks` at all — it directly calls `stacks_client.get_tenure_tip(...)` and, on `Err`, only warns and falls through, i.e. does **not** `return` and does **not** treat the conflict as still-blocking [6](#0-5) . Control then reaches `mark_locally_accepted` and the signer emits its signature over the new block [7](#0-6) , even though it already has a fresh signature over a conflicting sibling in the *same tenure* whose fate could not be confirmed.

Equality broken: "a signer must not place a second signature on a block that conflicts (same/higher height) with one it has already signed while that signature is fresh and not provably dead" — this is exactly the invariant the whole `conflict_still_blocks`/`get_signed_conflicts` machinery exists to enforce (see the doc's explicit statement of intent: *"The guard exists to stop us endorsing two blocks that could both end up in the chain"* [8](#0-7) ). The own-tenure branch silently drops that guarantee whenever the local `get_tenure_tip` call to the signer's own node fails.

### Impact Explanation
If this branch fires, the signer places its signature over a block B that conflicts with a block A it already signed in the same tenure, without any proof that A is dead. If A is (or later becomes) canonical, both A and B carry this signer's valid signature at overlapping/competing heights in the same tenure — a genuine equivocation by an otherwise-honest signer, which is precisely the Critical class this scan is scoped to ("a signer signing an invalid, non-canonical, or conflicting block"). Unlike the `check_latest_block_in_tenure` "assume higher" fallback (which is explicitly backstopped by the stacks-node's own `/v3/block_proposal` validation before anything is accepted), this failure is on the *signature-issuing* path itself — the node-side `postblock_proposal` validation cannot retroactively erase an already-broadcast, already-recorded signer signature on the sibling.

### Likelihood Explanation
Reaching this branch requires only: (1) two blocks at the same/overlapping height in one tenure (a miner can trivially re-propose or fork its own tenure to create this), (2) this signer having already signed the first one, (3) the second one crossing the 70% pre-commit threshold (a plausible one-slot-miner/gossip scenario, not requiring a signer majority to be malicious — only enough weight to *pre-commit*, which the doc says happens before validation of double-signing risk), and (4) the local RPC to the signer's own node erroring at that moment (timeout, restart, transient failure — not attacker-controlled with certainty, but a realistic operational condition given `get_tenure_tip` is called synchronously in the hot signing path). This is a likelihood-limiting factor: exploitation is opportunistic on network/node hiccups rather than fully miner-controlled, so I flag this as the main uncertainty in the analysis — I could not find a purely miner-controlled way to force the local node RPC to fail without invoking DoS/flooding, which is explicitly out of scope for this scan.

### Recommendation
Route the same-tenure conflict check through `conflict_still_blocks` (or otherwise make the `Err` arm of the `get_tenure_tip` call at line 1449 return/refuse-to-sign) so that an RPC failure defaults to "conflict still blocks," consistent with every other node-query failure path in this function.

### Proof of Concept
Not independently reproduced with a runnable test; derived from static code-path analysis of `handle_block_pre_commit` in `stacks-signer/src/v0/signer.rs`:
1. Miner tenure T proposes block A at height h; this signer signs A (`mark_locally_accepted`), recording a fresh `SignedConflictInfo` for (T, h).
2. Miner (or a gossip replay) re-proposes/produces a competing block B in the same tenure T at height h (or higher), which independently reaches the 70% pre-commit threshold at this signer.
3. `handle_block_pre_commit` runs; `get_signed_conflicts` returns A as a fresh, same-tenure conflict for which `reorg_permit_stands` is false [9](#0-8) .
4. `stacks_client.get_tenure_tip(T)` (a call to this signer's own connected stacks-node) returns an `Err` (timeout/transient failure).
5. Code logs "Treating the tenure as unconfirmed" and falls through without returning [6](#0-5) .
6. `mark_locally_accepted` is called and the signer broadcasts a signature over B, despite already having a fresh, unproven-dead signature over conflicting A in the same tenure.
