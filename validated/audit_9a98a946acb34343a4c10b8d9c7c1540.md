## Title
Stale confirmations from removed multisig members still count toward execution threshold - ([File: multisig2/src/lib.rs])

## Summary
The multisig contract lets a request execute once `confirmations.len() + 1 >= num_confirmations`. When a member is deleted via `DeleteMember`/`DeleteKey`, the contract only purges confirmations/requests that member *created* (matched by `r.member == member` / `r.signer_pk == pk`), not confirmations that member *cast* on other members' pending requests. Those stale confirmations remain in the `confirmations` map and continue to be counted by `confirm()`, letting a request execute with fewer *currently live* members' confirmations than `num_confirmations` actually requires.

## Finding Description
`confirm()` in `multisig2/src/lib.rs` (and the analogous `multisig/src/lib.rs`) determines whether to execute a request purely by counting entries in `self.confirmations.get(&request_id)`: [1](#0-0) 

When a member is removed, `delete_member()` only cleans up requests that the removed member originally *authored* (`r.member == member`), and does **not** scan `self.confirmations` for entries where the removed member appears as a *confirmer* of requests created by someone else: [2](#0-1) 

The same pattern exists in the legacy `multisig` contract's `DeleteKey` handling, which filters `requests` by `r.signer_pk == pk` (the request's creator) before clearing confirmations, again leaving other requests' confirmation sets untouched even if the deleted key had confirmed them: [3](#0-2) 

This breaks the binding: `confirmations counted == confirmations from currently-live members`. After a member is deleted, `self.confirmations` for a pending request created by *another* member can still contain the now-removed member's identifier, so `confirmations.len()` overstates the number of live, authorized confirmers.

## Impact Explanation
This is the direct analog of the flash-loan report's root cause: an operation is permitted to proceed based on a stale/optimistic record (confirmation count) rather than the actual current state (live membership set). Here it maps to the rule's explicitly called-out binding: "confirmations counted versus live members." Concretely, a request can be pushed to execution (`execute_request`, which can transfer NEAR, deploy code, add/delete keys, or call arbitrary functions on `receiver_id`) with effectively fewer live confirmations than `num_confirmations` mandates — i.e., "a multisig request executed below threshold," which the task's Critical impact bucket lists explicitly.

## Likelihood Explanation
This requires only ordinary multisig operation sequencing, no special exploit primitive:
1. A member confirms a pending request that another member created (but does not push it over threshold).
2. That confirming member is later removed via a normal `DeleteMember`/`DeleteKey` execution (e.g., because they left, were compromised, or rotated keys).
3. The original request's confirmation set still contains the removed member's stale confirmation.
4. A remaining member confirms, and the stale + new confirmations reach `num_confirmations`, executing the request even though the number of currently-live confirmers is one less than intended.

No attacker-controlled contract or external call ordering is needed — it is a straightforward consequence of `delete_member`/`DeleteKey` only filtering by request-authorship instead of by confirmer membership.

## Recommendation
When deleting a member/key, iterate over `self.confirmations` (not just `self.requests` filtered by author) and strip the removed member's identifier from every request's confirmation set, re-checking/removing requests whose remaining confirmation counts no longer reflect valid signers. Alternatively, when counting confirmations in `confirm()`, filter `confirmations` against the current `self.members` set before comparing to `num_confirmations`, so removed members' historical confirmations can never contribute to reaching the threshold.

## Proof of Concept
Given `num_confirmations = 3` and members `{A, B, C, D}`:
1. `A` calls `add_request_and_confirm(request)` → confirmations = `{A}`.
2. `B` calls `confirm(request_id)` → confirmations = `{A, B}` (2 < 3, not executed).
3. Separately, members execute a `DeleteMember { member: B }` request (a legitimate governance action, e.g. because `B`'s key was compromised) via `execute_request` → `delete_member` only removes requests where `r.member == B` (i.e., requests *authored* by `B`); the pending request from step 1/2 was authored by `A`, so its confirmations set `{A, B}` is left untouched, and `B` is removed from `self.members`.
4. `C` calls `confirm(request_id)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → request executes, even though only `A` and `C` are currently live members who confirmed it (`B`'s confirmation is stale/from a removed member), i.e., the request executed with only 2 confirmations from live members against a nominal 3-of-4 threshold.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
