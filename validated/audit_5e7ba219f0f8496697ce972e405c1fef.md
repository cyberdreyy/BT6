## Finding

### Title
JWT Replay-Protection Cache TTL Not Validated Against JWT Expiry, Allowing Trigger Request Replay - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
The HTTP Trigger Handler's JWT replay-protection cache (`jwtReplayCache`) tracks used JWT IDs (`jti`) for a duration controlled by the independently configured `JWTReplayPeriodMs` setting, while the JWT's own cryptographic validity window is bounded separately by `maxJWTExpiryDuration` / `WithMaxExpiryDuration` in `core/utils/jwt.go`. Nothing ties these two windows together, so if the replay-cache retention period is shorter than the actual lifetime of an accepted JWT, a still-valid, previously-used JWT can be replayed successfully after its `jti` entry is evicted from the cache — bypassing the single-use guarantee the mechanism is meant to enforce. This mirrors the reported Oval bug class: an independently tunable "freshness/retention" parameter (`maxAge`) that is not validated against the parameter it is meant to interact with (`lockWindow`), silently defeating the intended single-use/freshness invariant.

### Finding Description
`WorkflowMetadataHandler.Authorize` verifies an inbound HTTP trigger request's JWT and enforces single-use via a replay cache: [1](#0-0) 

The replay cache itself is a simple `jti -> timestamp` map, with entries evicted purely based on age relative to `cleanupPeriod`: [2](#0-1) [3](#0-2) 

`cleanupPeriod` is populated directly from the `JWTReplayPeriodMs` config field: [4](#0-3) [5](#0-4) 

Independently, the JWT's own validity window (its `exp`/`iat` claims) is bounded by `maxJWTExpiryDuration` (5 minutes) unless a caller overrides it with `WithMaxExpiryDuration`, and `VerifyRequestJWT` only checks that the token's own claims are internally valid and within that bound — it has no knowledge of, or dependency on, the replay-cache retention window: [6](#0-5) [7](#0-6) 

Because these two time windows (JWT cryptographic validity vs. replay-cache retention) are configured and enforced completely independently, and there is no validation ensuring `JWTReplayPeriodMs` is always ≥ the maximum possible JWT lifetime accepted by the handler, an operator (or a future caller of `VerifyRequestJWT` using a larger `WithMaxExpiryDuration`) could configure/allow a JWT lifetime longer than the replay-cache retention period. In that scenario, `cleanupOldEntries` (invoked periodically, presumably on a `CleanUpPeriodMs`/`JWTReplayPeriodMs`-based ticker analogous to the other cache reapers in this handler such as `responseCache.DeleteExpired`) removes the `jti` entry from the map before the JWT itself expires. `isReplay` then returns `false` for a token that is still cryptographically valid, permitting the exact same signed request to be resubmitted and re-authorized — a duplicate/unauthorized workflow trigger execution via replay, from an unprivileged external caller hitting the internet-facing Gateway's HTTP Trigger endpoint.

This is structurally identical to the reported Oval issue: a tunable staleness/retention parameter (`maxAge` / `JWTReplayPeriodMs`) that must be validated against a related window (`lockWindow` / JWT expiry) to preserve a security invariant (single unlock / single use), but for which the codebase provides no such cross-parameter validation.

### Impact Explanation
If `JWTReplayPeriodMs` is misconfigured below the effective maximum JWT lifetime accepted by the gateway, an unprivileged actor who observes or intercepts a valid, previously-submitted trigger JWT (e.g., via network observation, logging, or simply resending their own prior request) can replay it to trigger duplicate workflow executions after the replay cache entry expires but before the JWT itself expires. This breaks the intended "one execution per signed request" guarantee of the HTTP Trigger authentication flow, potentially causing unauthorized/duplicate job runs.

### Likelihood Explanation
Exploitability is conditional on configuration: the default `defaultJWTReplayPeriodMs` (24 hours) is far larger than the hardcoded `maxJWTExpiryDuration` (5 minutes), so the default deployment is not exploitable. However, the codebase does not enforce `JWTReplayPeriodMs >= max JWT expiry` anywhere, so a misconfigured or future deployment (e.g., an operator reducing `JWTReplayPeriodMs` for memory reasons, or a future caller using `WithMaxExpiryDuration` to allow longer-lived tokens without also raising `JWTReplayPeriodMs`) would silently reintroduce a replay window — exactly the "parameter validation" pitfall called out in the source report.

### Recommendation
Add an explicit invariant check (at handler construction/config-validation time) that `JWTReplayPeriodMs` must be strictly greater than the maximum allowed JWT lifetime (`maxJWTExpiryDuration`, or any `WithMaxExpiryDuration` value passed to `VerifyRequestJWT`), and fail fast / refuse to start if this invariant is violated, analogous to the recommended fix of validating `maxAge > lockWindow` in Oval.

### Proof of Concept
Conceptual (configuration-dependent) sequence, since no code execution/tooling is available in this mode:
1. Deploy the gateway with `JWTReplayPeriodMs` set below the max JWT lifetime that will actually be accepted (e.g., `JWTReplayPeriodMs` = 60s, while a client is allowed a 5-minute-lived JWT).
2. Client submits a valid `MethodWorkflowExecute` request with signed JWT (`jti = X`) to the HTTP Trigger endpoint; `Authorize` succeeds and records `jti X` in `jwtReplayCache` per [1](#0-0) .
3. After the configured cleanup interval elapses (> `JWTReplayPeriodMs` but still < JWT's `exp`), `cleanupOldEntries` evicts `jti X` from the cache per [8](#0-7) .
4. Attacker resubmits the identical previously-observed request+JWT. `VerifyRequestJWT` still accepts it (not yet expired), and `isReplay(X)` now returns `false`, so `Authorize` succeeds again, triggering a duplicate workflow execution.

**Note on completeness**: I was unable to view the exact periodic-cleanup call site that invokes `cleanupOldEntries` (its scheduling logic and cutoff computation) within the tool-call budget; this analysis infers its behavior from the cache's public methods and the documented purpose of `JWTReplayPeriodMs`, and from directly analogous reaper patterns elsewhere in the same handler (e.g., `responseCache.DeleteExpired`). If further certainty is required, a Devin session with full repository access should inspect the goroutine that calls `cleanupOldEntries` to confirm the cutoff formula.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func newJWTReplayCache(cleanupPeriod time.Duration) *jwtReplayCache {
	return &jwtReplayCache{
		cache:         make(map[string]time.Time),
		cleanupPeriod: cleanupPeriod,
	}
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

// cleanupOldEntries removes expired entries from the cache
func (cache *jwtReplayCache) cleanupOldEntries(cutoff time.Time) int {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	var expiredCount int
	for jti, createdAt := range cache.cache {
		if createdAt.Before(cutoff) {
			delete(cache.cache, jti)
			expiredCount++
		}
	}
	return expiredCount
}
