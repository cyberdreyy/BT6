### Title
External Initiator authorization bypass allows triggering runs on jobs not bound to the EI credential - (File: core/web/pipeline_runs_controller.go)

### Summary
`PipelineRunsController.Create` decides whether to execute a job run based solely on whether `auth.GetAuthenticatedUser(c)` returns an authenticated principal, but `AuthenticateExternalInitiator` unconditionally injects a synthetic `User{Role: UserRoleRun}` into the same context key used for real dashboard users. This means an EI-authenticated request is treated as `isUser == true`, and the handler proceeds to call `RunJobV2` using only the numeric `:ID` from the URL, with no check that the authenticated EI is actually bound to that job.

### Finding Description
`core/web/auth/auth.go` `AuthenticateExternalInitiator` (lines 119-151) authenticates the EI credential via `store.FindExternalInitiator`/`bridges.AuthenticateExternalInitiator`, then sets both `SessionExternalInitiatorKey` and `SessionUserKey` (a fabricated run-role user) on the gin context: [1](#0-0) 

`RequiresRunRole` (lines 202-217) only inspects `GetAuthenticatedUser(c)` and its `Role` field — it never inspects `GetAuthenticatedExternalInitiator(c)` nor correlates the EI identity with the requested job ID: [2](#0-1) 

`PipelineRunsController.Create` in `core/web/pipeline_runs_controller.go` (lines 89-128) then checks `isUser := auth.GetAuthenticatedUser(c)`, and because `AuthenticateExternalInitiator` sets this same key, an EI-authenticated caller satisfies `isUser == true` (despite the misleading comment "only users are allowed to run jobs using int IDs - EIs not allowed"). The handler parses `idStr` as an int32 job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` with no lookup of which EI (if any) is associated with that job: [3](#0-2) 

No code path between the `Authenticate`/`RequiresRunRole` middleware chain and `PipelineRunsController.Create` binds the specific EI credential to a specific job ID before invoking `RunJobV2`.

### Impact Explanation
An EI credential provisioned and scoped for job A can be used to invoke `POST /v2/jobs/<jobB-ID>/runs` and successfully trigger a pipeline run on job B, an entirely different job the EI was never granted. This is an authorization/access-control bypass allowing unauthorized triggering of job runs across job boundaries — matching the "unauthorized job run" impact class, potentially leading to unintended fund movement or oracle actions if job B performs on-chain transactions.

### Likelihood Explanation
The precondition is minimal: possession of any valid EI credential (access key/secret pair) registered for any single job. No admin/session access is required — this is exactly the "external-initiator credential holder" attacker profile. The attack is a single unauthenticated-relative-to-job-B HTTP POST and is fully repeatable.

### Recommendation
In `PipelineRunsController.Create` (and equivalently at the `RequiresRunRole` layer), when the authenticated principal is an external initiator (`auth.GetAuthenticatedExternalInitiator(c)` returns ok), verify that the target job's ID/webhook spec is actually associated with that EI record before calling `RunJobV2`, rejecting with 401/403 otherwise. Additionally, stop conflating EI identity with `SessionUserKey`, or introduce an explicit separate role check that distinguishes "user" from "EI" callers so the `isUser` branch in `Create` cannot be satisfied by EI auth alone.

### Proof of Concept
Go handler-level integration test plan:
1. Create job A and job B (both webhook-type jobs usable via `RunJobV2`).
2. Create an External Initiator record bound only to job A (via the EI/job association used by `FindExternalInitiator` and webhook spec).
3. Authenticate as that EI using the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers matching job A's EI.
4. Send `POST /v2/jobs/<jobA-ID>/runs` — assert `200 OK` (expected, in-scope job).
5. Send `POST /v2/jobs/<jobB-ID>/runs` using the same EI credentials — assert the response should be `401`/`403`, but current code returns `200 OK` with a created pipeline run, proving the EI can trigger runs on an unauthorized job.

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
