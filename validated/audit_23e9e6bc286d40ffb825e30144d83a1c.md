### Title
Bridge OutgoingToken credentials disclosed to view/run-role users via GET /v2/bridge_types - ([File: core/web/presenters/bridges.go])

### Summary
`NewBridgeResource` unconditionally copies `bridge.OutgoingToken` into the JSON-serialized `BridgeResource` returned by the API, with no `omitempty` or role-based redaction. `BridgeTypesController.Index` (backing `GET /v2/bridge_types`) calls this presenter for every row in the paginated bridge list, so any authenticated caller who can reach the read-only bridge listing/show endpoints receives every bridge's `OutgoingToken` in plaintext.

### Finding Description
`presenters.NewBridgeResource` builds the response resource and sets `OutgoingToken: b.OutgoingToken` directly from the DB row, and the field is tagged `json:"outgoingToken"` (no `omitempty`, no masking), unlike `IncomingToken` which is intentionally left empty except right after creation in `Create`: [1](#0-0) 

`BridgeTypesController.Index` iterates over all bridges returned from `BridgeORM().BridgeTypes` and calls `NewBridgeResource` on each, then hands the full list to `paginatedResponse` — there is no filtering of `OutgoingToken` based on the requester's role: [2](#0-1) 

`BridgeTypesController.Show` behaves the same way for a single bridge by name: [3](#0-2) 

The test suite confirms `OutgoingToken` is present and non-empty in the marshaled JSON response of `NewBridgeResource`, with no field-level access control expressed anywhere in the presenter or controller layer: [4](#0-3) 

I was not able to fully confirm, within the available index, the exact `router.go` role-middleware wiring for the `/v2/bridge_types` GET routes (whether `Index`/`Show` are wrapped only in session authentication vs. an explicit `RequiresEditRole`/`RequiresAdminRole` guard) — grep found matches in `core/web/router.go` for both `bridge_types` and the role-requiring middleware, but I could not retrieve and verify the exact route-registration lines before the session ended. This is a real gap in verification: if `Index`/`Show` are in fact wrapped with `RequiresEditRole`, the described attack path (view-role session reaching Index) would not be reachable and this finding would not hold as stated.

### Impact Explanation
If the GET routes are reachable by a view/run-role session (as the question's premise and the presenter's unconditional serialization suggest), this results in bulk disclosure of every bridge's `OutgoingToken` — a credential used by the node to authenticate itself when calling out to external adapters — to a principal that should only have read access to non-sensitive bridge metadata. This maps to Chainlink's "sensitive data / credential exposure via authorization bypass" bounty impact class, since it lets a lower-privileged, non-admin identity harvest secrets intended for edit/admin-level operators.

### Likelihood Explanation
Exploitation, if the route is unguarded for view role, requires only a valid view-role session cookie or restricted API token and a single `GET /v2/bridge_types?size=100&page=1` request — no elevated privileges needed, fully repeatable, and trivially automatable across all pages. However, since I could not conclusively verify the middleware chain for these specific routes, the actual reachability by an unprivileged/view-role principal remains unconfirmed from the available context.

### Recommendation
- Verify and, if necessary, add `RequiresEditRole`/`RequiresAdminRole` middleware to the `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` routes in `core/web/router.go`, restricting access to roles that legitimately need to reconfigure or debug bridge connectivity.
- Independently, redact `OutgoingToken` in `presenters.NewBridgeResource` for list/show responses (mirroring how `IncomingToken` is only populated in the `Create` response) so that credential exposure does not depend solely on route-level RBAC.

   - Obtain an HTTP client authenticated with a view-role (or lowest-privilege) user/session, analogous to existing `client.Get` helpers used in `TestBridgeTypesController_Create_Success`.
   - Call `GET /v2/bridge_types?size=100&page=1`.
   - Assert `http.StatusOK` and parse `data[].attributes.outgoingToken` for each bridge, asserting equality with the stored `bridge.OutgoingToken` values.

First confirm (as a prerequisite step, since this was unresolved in this session) by reading `core/web/router.go`'s `v2Routes`/bridge-types route group to determine which middleware (`sessions.Sessions` only vs. `RequiresEditRole`) wraps `BridgeTypesController.Index`/`Show`, to establish whether a view-role session can actually reach the handler before relying on the PoC above.

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
