### Title
Unfunded instant-withdraw receipts are paid at par from the funded reserve due to shared aggregate `instantWithdrawsRequests` counter - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Hoverfly bug is an unsynchronized shared map: `AddDiff()` writes into `responsesDiff` from concurrent request paths with no coordination, corrupting shared state. The credit-vault analog is `IdleCreditVault`'s instant-withdraw ledger: `requestInstantWithdraw()` and `claimInstantWithdrawRequest()` mutate a single per-user aggregate `instantWithdrawsRequests[_user]` plus a per-epoch mapping `instantWithdrawsRequestsByEpoch`, but the claim path pays the whole aggregate at par without checking which portion was actually funded by the borrower via `collectInstantWithdrawFunds()`. A new request made in the same epoch (or a later epoch) "rides along" on an already-funded receipt and gets paid immediately out of reserves belonging to other claimants.

### Finding Description
- `requestInstantWithdraw()` burns CDO strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`).
- Funding arrives later and asynchronously: `collectInstantWithdrawFunds()` pulls underlying from the CDO and decrements `pendingInstantWithdraws` (`IdleCreditVault.sol:398-403`). Until then, the request is unfunded.
- `claimInstantWithdrawRequest()` burns the entire `instantWithdrawsRequests[_user]` balance and transfers the full amount via `_transferFundedClaim()` (`IdleCreditVault.sol:380-393`). There is no check that `amount <= (funded portion)`, no per-epoch funding gate, and no deduction limited to funded receipts — the per-epoch mapping is only consulted in the post-default path (`_claimDefaultedInstantWithdrawRequest`, line 842).

Attack sequence (running epoch, instant-withdraw mode):
1. Honest users' funded instant receipts sit unclaimed; the vault holds underlying equal to the funded reserve.
2. Attacker calls `requestInstantWithdraw(X)` via the CDO. `instantWithdrawsRequests[attacker]` becomes `X`, `pendingInstantWithdraws` increases by `X`, but no underlying has been collected for it.
3. Attacker immediately calls `claimInstantWithdrawRequest()`. The function pays the full `X` from vault-held funded reserves, even though `pendingInstantWithdraws` still includes `X` as unfunded.
4. When `collectInstantWithdrawFunds()` later runs at epoch stop, `pendingInstantWithdraws` still contains the attacker's `X`, so the borrower is charged again (or, if funding is capped, other claimants' payouts are shorted).

The same corruption applies across epochs: a funded receipt from epoch N and an unfunded request in epoch N+1 are collapsed into one counter, so a single claim drains funded reserves for the unfunded piece.

### Impact Explanation
Direct theft / insolvency. The attacker withdraws underlying that was collected to satisfy *other* users' instant-withdraw receipts, before their own request is funded. Quantified loss: up to the full vault-held funded instant-withdraw reserve at the moment of the claim (all unfunded-but-claimable amounts are paid at par). If the borrower later funds `pendingInstantWithdraws` again, the loss socializes to the borrower/LPs; if not, remaining instant claimants are permanently underpaid. This breaks the "one receipt, one funded payout" invariant.

### Likelihood Explanation
- Attacker needs only to be an allowed wallet (KYC-passing tranche holder) with tranche tokens — an unprivileged role per the threat model. All calls route through `IdleCDOEpochVariant.claimInstantWithdrawRequest()` / `requestInstantWithdraw()`, which are user-facing.
- No privileged action is required in the exploit window; the manager's `collectInstantWithdrawFunds` is an honest, scheduled call the attacker simply front-runs/sequences around.
- Precondition: the vault holds funded underlying for instant claims (the normal state once any instant epoch has been funded), and the CDO permits an instant request followed by a claim in the same epoch phase. No code path blocks a claim while `pendingInstantWithdraws` includes the caller's own request.

### Recommendation
Track funded vs. unfunded instant receipts separately. Either:
- Gate `claimInstantWithdrawRequest()` on a per-epoch funded flag/price (mirroring `lossRecoveryPriceByEpoch`/`epochWithdrawPrice` in `IdleCDOEpochQueue`), paying only the portion backed by collected funds, or
- Subtract only the funded basis in the claim path (e.g., cap the payout at `instantWithdrawsRequests[_user] - unfundedByEpoch`), leaving unfunded receipts claimable after `collectInstantWithdrawFunds()` settles them.
- Alternatively revert claims while `instantWithdrawsRequestsByEpoch[_user][epochNumber]` is nonzero and that epoch's instant claims are not yet funded.

### Proof of Concept
Foundry fork test outline (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testInstantWithdrawPaysUnfundedReceipt() external {
    // Setup: userA deposits, epoch runs, userA requests instant withdraw,
    // manager collects funds (collectInstantWithdrawFunds) so vault holds funded underlying.
    _depositWithUser(userA, amount);
    _startEpochAndCheckPrices(0);
    cdoEpoch.requestInstantWithdraw(amountA, userA);        // funded request
    // manager funds it
    vm.prank(manager); cdoEpoch.stopEpoch(...);             // or explicit collectInstantWithdrawFunds path
    // vault now holds funded reserve for userA; userA does NOT claim

    // Attacker (KYC'd tranche holder) requests instant withdraw in the new epoch
    _depositWithUser(attacker, amountX);
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestInstantWithdraw(amountX, attacker);
    // pendingInstantWithdraws now includes amountX (unfunded)

    uint256 balPre = underlying.balanceOf(attacker);
    // Claim pays full aggregate, including unfunded amountX, from userA's reserve
    cdoEpoch.claimInstantWithdrawRequest(attacker);
    assertGt(underlying.balanceOf(attacker) - balPre, 0);
    // Invariant break: vault funded reserve is drained while
    // pendingInstantWithdraws still counts attacker's request.
    assertEq(strategy.pendingInstantWithdraws(), amountX + amountA_remainder);
}
```

Key assertion: attacker receives underlying equal to `instantWithdrawsRequests[attacker]` even though `pendingInstantWithdraws` still includes that amount, i.e., funds earmarked for other epochs' receipts are spent.

Uncertainty note: I could not fully trace the CDO-side gating in `IdleCDOEpochVariant.claimInstantWithdrawRequest()`/`getInstantWithdrawFunds()` (e.g., an `instantDelay` check keyed to epoch start vs. request time) within the available context. If the CDO enforces a per-request funding check before calling the vault, the exploit window narrows; the vault-level aggregate counter remains unsynchronized regardless and the per-epoch bookkeeping exists precisely because the aggregate is insufficient.
