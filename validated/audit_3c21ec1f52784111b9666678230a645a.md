### Title
`check_latest_block_in_tenure` fails open on node-unreachable, letting a signer sign a non-canonical/conflicting block during the final pre-signature recheck - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` is the shared "does this block still fit the chain" gate used both at proposal arrival and — critically — at the final recheck immediately before a signature is produced (per `docs/signer-flows.md` section 5/7, anchored at `check_block_against_signer_db_state` → `confirms_latest_block_in_same_tenure`/`check_tenure_change_confirms_parent`). When the local signer's DB has no cached tip information for the tenure, the function falls back to asking the node for the tenure tip via `client.get_tenure_tip(tenure_id)`. If that RPC call fails for any reason (timeout, connectivity issue, node restart, etc.), the code does not withhold judgment or reject — it unconditionally returns `Ok(true)`, i.e. "proposal is higher than tenure tip; check passes." [1](#0-0) 

This is structurally the same bug class as the reported OpenClaw advisory: an explicit-approval boundary (the tip-confirmation check) is bypassed by a "timeout/unreachable" fallback that defaults to the permissive outcome instead of blocking or deferring.

### Finding Description
`check_latest_block_in_tenure` is documented as running in three places: at proposal arrival (`check_proposal`), at validate-ok, and — importantly — "at the moment of signing" [2](#0-1) . The final signing-time recheck exists precisely because, between the pre-commit round and reaching the 70% signature threshold, "we may have signed a different block at the same height, possibly in another tenure, so the world must be re-checked before the signature leaves the box" [3](#0-2) .

The function's own docstring rationalizes the fallback: "If we can't look up `tenure_id`, assume `block` is higher. This assumption is safe because this proposal ultimately must be passed to the `stacks-node` for proposal processing: so, if we pass the block height check here, we are relying on the `stacks-node` proposal endpoint to do the validation" [4](#0-3) .

That reasoning holds only for the **first** two call sites (proposal arrival and validate-ok), where the node's `/v3/block_proposal` endpoint is indeed still going to be consulted downstream. It does **not** hold at the **final signing-time recheck**, which happens strictly *after* validate-ok has already succeeded and the node has already accepted the block once — the node is not consulted again before the signature is emitted. If `get_tenure_tip` transiently fails at that specific moment (e.g., a brief node hiccup, an HTTP timeout, connection reset), the check that exists specifically to catch a stale/superseded proposal silently passes, and the signer proceeds to sign a block that may no longer be the canonical tip of its own tenure — breaking the "approved-parent vs canonical" equality the check is meant to enforce.

### Impact Explanation
This can let a single signer sign a proposal that fails the very check meant to prevent it from signing over a conflicting/non-canonical block. Since block equivocation guards rely on all correctly-behaving signers enforcing chain-consistency checks *before* their signature is counted toward the 70% threshold, a signer whose network hiccups at the wrong instant contributes a signature toward a potentially non-canonical block. This maps to the "signer signing a non-canonical/conflicting block" category, which the rules classify as Critical impact, though it requires an adverse timing condition (an RPC failure) rather than a purely adversarial trigger by the miner alone.

### Likelihood Explanation
The RPC failure has to occur specifically during the narrow window of the final pre-signature recheck (as opposed to the earlier proposal-arrival check, where the fallback is safe). This requires a coincidence of network/node instability with an in-flight pre-commit reaching threshold — not something a single malicious miner can force deterministically, but it is a real, reachable path since `get_tenure_tip` is a live HTTP call to the local node that can fail transiently in production for many benign reasons (node restart, RPC timeout, load), and no majority of signers or extra privileges are needed to trigger the underlying race — only ordinary network flakiness at the wrong moment.

### Recommendation
At minimum, the signing-time call path (`confirms_latest_block_in_same_tenure` / `check_tenure_change_confirms_parent` when invoked from the final recheck, not from `check_proposal`) should not fail open on `get_tenure_tip` errors. Either: (a) treat a node-unreachable result as check-failure (reject/pre-commit-withdrawal) at the signing-time call site specifically, since the node will not be asked again before the signature is placed, or (b) plumb a flag/parameter through `check_latest_block_in_tenure` distinguishing "proposal-time" (safe to assume higher, node will validate) from "signing-time" (must not assume higher) call sites, and only fail open in the former.

### Proof of Concept
Conceptual trace:
1. A signer pre-commits to block `B` at height `h` in tenure `T` after `check_proposal`/`handle_block_validate_ok` succeed.
2. Before threshold is reached, another (rival) block `B'` at height `h` becomes the canonical tip (e.g., via a different miner or reorg-permitted sequence), advancing the tenure tip beyond `B`.
3. The 70%-pre-commit threshold is reached for `B`, triggering the final recheck via `check_block_against_signer_db_state` → `confirms_latest_block_in_same_tenure` → `check_latest_block_in_tenure`.
4. At this exact moment the signer's local DB doesn't yet have `B'` cached, so the function calls `client.get_tenure_tip(tenure_id)`; that RPC call fails (timeout/connectivity blip).
5. Per lines 450-461, the function returns `Ok(true)` unconditionally instead of retrying or rejecting, so the recheck "passes," and the signer proceeds to sign `B`, a block that in fact no longer confirms the true tenure tip.

I was unable to fully trace the exact call sites in `stacks-signer/src/v0/signer.rs` where `confirms_latest_block_in_same_tenure` is invoked at signing time versus proposal time (grep found 4 matches but I ran out of iterations to read them), so I cannot cite the exact line numbers of the signing-time call site in `signer.rs`; this should be verified in a follow-up before treating the PoC as fully confirmed end-to-end.
