### Title
Funded instant-withdraw claims leave stale per-epoch receipt data that inflates default-recovery basis and overstates the prefunded reserve - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a funded instant-withdraw receipt but only clears the aggregate `instantWithdrawsRequests[_user]`; it never clears the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. Like credentials persisting in browser storage after logout in CVE-2020-15085, these stale request records survive after the claim is settled. If the borrower defaults in the same epoch while another instant request remains unfunded, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` consume the phantom basis, diluting every claimant's recovery price, over-reserving funds that don't exist, and permanently freezing part of the recovery reserve.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

1. `requestInstantWithdraw` (lines 356-375) records three pieces of state per user/epoch: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]`, plus global `pendingInstantWithdraws`.
2. `claimInstantWithdrawRequest` (lines 380-393), on the funded path, does `_burn(_user, amount)`, sets `instantWithdrawsRequests[_user] = 0`, and transfers the funds — but does **not** zero `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrement `instantWithdrawClaimsByEpoch[epoch]`. The only cleanup of per-epoch data happens in `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which is only reachable when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`.
3. At default finalization, `defaultPendingClaimBasis()` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`. That counter still contains already-claimed receipts, so `totalBasis` in `finalizeDefaultRecovery` (lines 679-680) is inflated and `recoveryPrice` (line 688) is understated for all real claimants.
4. Worse, `_defaultPrefundedInstantReserve()` (lines 716-723) computes `instantBasis - pendingInstant`. With a phantom `instantBasis`, the "already-held" reserve is overstated, inflating `defaultRecoveryReserve` (line 691) by tokens that were already paid out. `recoveryPrice` is computed against this phantom reserve, so the last claimants' `_transferDefaultRecovery` calls (line 912-917) transfer more than the contract holds — the reserve accounting claims funds that physically do not exist, and `_transferFundedClaim`'s reserve-isolation guard (lines 900-905) cannot help recovery claimants.
5. Second-claim DoS: after finalization, `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` for the already-claimed user and executes `instantWithdrawsRequests[_user] -= claimBasis` (line 848) on a zero balance — an underflow revert that permanently bricks `claimInstantWithdrawRequest` for that user. Any new post-default `requestInstantWithdraw` from that user lands in the same `epochNumber` bucket (no new epoch can start once defaulted), making `claimBasis` strictly larger than their new receipt, so their new request is permanently frozen too.

### Impact Explanation
- **Recovery dilution**: every defaulted-epoch claimant receives `staleBasis / totalBasis` less than entitled; the loss is proportional to the attacker's already-claimed amount.
- **Reserve insolvency**: `defaultRecoveryReserve` is credited with phantom prefunded funds. Late claimants' transfers revert on insufficient balance — permanent freezing of their unclaimed recovery, and the reserved-but-unbacked accounting amount is locked forever.
- **Permanent freeze for the stale-record user**: underflow at line 848 bricks all future instant-claim calls for anyone who claimed a funded instant withdrawal in the default epoch.

### Likelihood Explanation
Requires instant-withdraw mode enabled (an explicit feature via `setInstantWithdrawParams`), one user who fully claims a funded instant withdrawal during epoch N, at least one other instant request left unfunded at epoch N, and a borrower default in that epoch. All attacker steps are unprivileged user actions (deposit, request instant withdraw, claim). The stale record is created by the protocol's own bookkeeping, so no special sequencing is needed beyond the default occurring in the same epoch.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers alongside the aggregate: locate the user's request epoch(s) (e.g., track a `lastInstantWithdrawRequest` marker or iterate recorded epochs), zero `instantWithdrawsRequestsByEpoch[_user][epoch]`, and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, mirroring the cleanup in `_claimDefaultedInstantWithdrawRequest`. Additionally, consider guarding `requestInstantWithdraw` once `defaultRecoveryFinalized` is true.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
