### Title
Stale confirmations from removed multisig members still count toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm()` in `multisig2/src/lib.rs` counts confirmations solely by set size and never re-validates that each address in the `confirmations` set is still a live member. `delete_member()` only purges requests/confirmations where the *removed member is the original requester* (`r.member == member`), not requests created by others that the removed member had already confirmed. This lets a request execute below the "live members" threshold that `num_confirmations` is supposed to enforce.

### Finding Description
`add_request` stores a `MultiSigRequestWithSigner{ member, ... }` and creates an empty confirmation `HashSet<String>` for the request id at `multisig2/src/lib.rs:189-197`. `confirm()` (`multisig2/src/lib.rs:294-315`) adds the confirming member's string representation to that set and, once `confirmations.len() + 1 >= self.num_confirmations`, executes the request via `remove_request` + `execute_request`.

`delete_member()` (`multisig2/src/lib.rs:356-379`) is the only place that cleans stale confirmation state, but its cleanup loop is scoped incorrectly:
```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
This only removes requests whose original *requester* equals `member`. It does not iterate over `self.confirmations` to strip the removed member's entry from confirmation sets of requests created by *other* members. Consequently, if member `A` confirms a request created by member `B`, and `A` is subsequently removed via `DeleteMember`, the request's confirmation set still contains `A`'s stale confirmation. `confirm()` never re-checks `self.members.contains(...)` for entries already in the set — it only checks the *new* confirmer via `current_member()`. This breaks the intended equality: `confirmations counted == confirmations from live members`.

### Impact Explanation
This crosses the "threshold" custody boundary explicitly called out in scope: a multisig request (which can be a `Transfer`, `AddKey`/`FunctionCall`, etc., moving NEAR or granting access) can be executed with fewer *currently valid* member confirmations than `num_confirmations` requires, because a stale confirmation from a removed member is still counted. This is Critical impact per the rules ("a multisig request executed below threshold").

### Likelihood Explanation
This requires only routine multisig usage: a request created by one member is confirmed by another member, and later that confirming member is removed (a normal `DeleteMember` operation, e.g. rotating out a compromised or departing key/account) before the request is confirmed to completion or deleted. No malicious deployment or foundation privilege is needed beyond the standard `DeleteMember` action any sufficient set of members can already execute. In a 2-of-3 or similar small multisig, this scenario is plausible during normal key rotation.

### Recommendation
When removing a member in `delete_member`, iterate all outstanding `confirmations` entries (not just requests originally created by that member) and remove the departing member's confirmation string from every set. Alternatively, have `confirm()` re-validate membership of every account/key already present in the confirmation set (or simply recompute the confirmation count by filtering to `self.members.contains(...)` before comparing against `num_confirmations`).

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C], 3)` (3-of-3).
2. `B` calls `add_request` to create a `Transfer` request (request_id = 0), originally-requester = `B`.
3. `A` calls `confirm(0)` → confirmations = `{A}` (1/3, not yet executed).
4. Members execute a separate `DeleteMember{member: A}` request (using confirmations from B and C, satisfying threshold) — this calls `delete_member`, which only scans requests where `r.member == A` (none, since request 0's requester is `B`), so confirmation set for request 0 is untouched and still contains `A`.
5. Now only `B` and `C` are valid members (2 total), yet `num_confirmations` is still 3.
6. `C` calls `confirm(0)` → `confirmations.len() (1, from stale A) + 1 (C) = 2`, still short of 3, but if `num_confirmations` was 2 (or was previously lowered, or in a scenario where only 2 live members remain and threshold is 2), the stale `A` confirmation plus one live confirmation from `C` reaches the threshold and executes the transfer — despite `A` no longer being a member and only one live member (`C`) having actually confirmed.
