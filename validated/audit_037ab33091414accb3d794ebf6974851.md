### Title
Front-runnable global `FeeState` PDA initialization allows an attacker to seize `global_fee_admin` and `global_fee_wallet` - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
`InitFeeState`/`initialize_fee_state` initializes the single, program-wide `FeeState` PDA (seeded only by the constant `FEE_STATE_SEED`, with no group- or admin-specific component), but the instruction has no access control tying the caller to the legitimate protocol deployer. Any signer can call it first with attacker-controlled `admin_key` and `fee_wallet` arguments, permanently seizing the singleton fee-state account before the real admin does—directly analogous to the Unlock `PublicLock.initialize()` front-running issue, where a separately-created account/contract lacks access control on its one-time initializer.

### Finding Description
`InitFeeState` derives `fee_state` from a fixed seed (`FEE_STATE_SEED`) with no per-caller or per-group differentiation, so there is exactly one valid PDA address system-wide: [1](#0-0) 

The handler blindly assigns caller-supplied `admin_key` and `fee_wallet` into the account with `load_init()`, and the account struct requires only a generic `payer: Signer<'info>` — there is no check that `payer` is the program's upgrade authority, a hardcoded deployer key, or any other privileged party: [2](#0-1) 

Because the PDA is deterministic and derivable by anyone, an attacker can front-run the legitimate deployer's initialization transaction and call `marginfi_init_fee_state` (exposed in `lib.rs`) with themselves as `admin_key` and their own wallet as `fee_wallet`. Since Anchor's `init` constraint fails if the account already exists, the legitimate admin's subsequent initialization attempt fails, permanently locking out the real fee-state configuration for that program deployment (a new program ID/redeploy would be required to recover, mirroring the "force redeploy" impact in the original Unlock report).

Once the attacker controls `global_fee_admin` in the singleton `FeeState`, they can also freely call `edit_fee_state`, which is gated only by `has_one = global_fee_admin`, allowing them to change `global_fee_wallet` and program fee parameters at will: [3](#0-2) 

This is a genuine, unprivileged-caller-reachable permissionless-maintenance/initialization gap, not a validator/peer/mocked scenario, and it is a distinct root cause from any documented out-of-scope item.

### Impact Explanation
`FeeState.global_fee_wallet` is the destination for protocol program fees collected across every marginfi group and bank in the deployment (fees charged on borrow/liquidation/order flows, per `edit_global_fee.rs` and the `fee_state_cache` propagated into every `MarginfiGroup`, as seen in `initialize_group`): [4](#0-3) 
An attacker who wins the initialization race becomes the sole `global_fee_admin`, permanently redirecting protocol-wide fee revenue to an address they control and blocking legitimate admin control over fee configuration until a program redeploy — a durable, protocol-wide value-redirection and freeze with direct financial effect.

### Likelihood Explanation
Exploitation requires only observing the deployer's `InitFeeState` transaction in the mempool (or simply racing to call it first on a freshly deployed/undeployed program, since the PDA address is fully deterministic and public from the program ID) and submitting a higher-priority transaction with the same accounts and attacker-chosen arguments. No privileged role, staked position, or special timing beyond ordinary front-running is required, making this readily reachable by any unprivileged actor at deployment time.

### Recommendation
Add explicit access control to `InitFeeState`, e.g., require `payer`/`admin_key` to match a hardcoded/immutable deployer key (such as the program's upgrade authority checked via `#[account(constraint = ...)]`), or perform initialization atomically within the same transaction/instruction that deploys or upgrades the program so it cannot be front-run. Alternatively, gate `initialize_fee_state` behind a one-time-use flag validated against the program's upgrade authority account.

### Proof of Concept
1. Program is deployed; the deterministic PDA `fee_state = PDA([FEE_STATE_SEED], marginfi::ID)` is publicly derivable before it exists on-chain.
2. Attacker submits `marginfi_init_fee_state(admin_key = attacker, fee_wallet = attacker_wallet, ...)` with a higher priority fee than the legitimate deployer's pending initialization transaction, per the account structure in [1](#0-0) .
3. Legitimate deployer's `InitFeeState` transaction subsequently fails because the PDA already exists (Anchor `init` re-init error).
4. Attacker now owns `global_fee_admin` and can call `edit_fee_state` ( [5](#0-4) ) to redirect all future protocol fees to their own wallet indefinitely.

#[allow(unused_variables)]
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
