### Title
Signer vote reconsideration is double-counted toward both approval and rejection weight in the node's `BlockStatus` tally, allowing a stale rejection to force a false `SignersRejected` outcome - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::process_event` (in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`) accumulates `BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected` from `BlockResponse::Accepted`/`BlockResponse::Rejected` messages, gating each addition on separate, non-mutually-exclusive membership tests (`gathered_signatures` for accept, `responded_signers` for reject), while both branches unconditionally insert into the same shared `responded_signers` set. Because the signer-side state machine explicitly allows a signer to move `LocallyRejected -> LocallyAccepted` ("re-evaluated"), a signer that first rejects and later accepts the same block has its weight counted on *both* sides of the tally, permanently. This breaks the invariant that a signer's weight should count toward at most one side of the vote, and can cause `SigningCoordinator::get_block_status_or_pending`/`wait_for_signer_signatures_or_timeout` in `signer_coordinator.rs` to declare the block globally rejected (`NakamotoNodeError::SignersRejected`) even though the real, current set of rejecting signers is below the blocking-minority threshold.

The accept path's weight is gated by `gathered_signatures` (a map keyed by `slot_id`), and the reject path's weight is gated by `responded_signers` (a `HashSet<slot_id>`) — but the accept path *also* inserts into `responded_signers` unconditionally at line 465, without checking it first. Consequently:

1. Signer S first sends `Rejected` for block B. `responded_signers.insert(slot_id)` returns `true` → `total_weight_rejected += weight(S)`.
2. S later re-evaluates and sends `Accepted` for B (a legitimate transition per the documented signer state machine: `LocallyRejected --> LocallyAccepted : re-evaluated`, `docs/signer-flows.md:144`). `gathered_signatures` does not yet contain `slot_id` (S never accepted before) → `total_weight_approved += weight(S)`. `responded_signers.insert(slot_id)` is a no-op (already present), so nothing detects that S's earlier rejection is now stale.

The result: `weight(S)` is counted simultaneously in both `total_weight_approved` and `total_weight_rejected`, with no mechanism to retract the earlier, superseded rejection. This directly parallels the ZeroLend root cause: an accounting field (`totalSupply.supplyShares` there, `total_weight_rejected`/`total_weight_approved` here) is updated by one code path (mint-to-treasury / reject) without a corresponding, symmetric update in the other path when the same underlying quantity should have been retracted (burn from treasury / drop the stale rejection).

Because the stale rejection weight is never removed, `total_weight_rejected` can remain inflated by signers who have since switched to accepting. If this stale-plus-current rejection weight crosses the blocking-minority threshold (`total_weight - weight_threshold`), the miner concludes the block was rejected by a blocking minority (`SignersRejected`) and bans/excludes transactions and abandons the block — even though the *actual, current* rejecting weight (excluding the signer who moved on) is below the blocking minority and the block may in fact have (or be about to have) enough approving weight. This is a liveness wedge on block production driven by a stale accounting value that the equality "current tallied reject weight == weight of signers currently rejecting" no longer holds, matching the "aggregated-weight vs verified-accepts" equality-break class named in scope. It does not require a signer majority — a single reconsidering signer plus the pre-existing legitimate voters is sufficient to trigger the discrepancy.

### Likelihood Explanation
The trigger requires only one signer to send a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash` — an explicitly supported and documented transition in the signer state machine (`LocallyRejected -> LocallyAccepted`, re-evaluation on a new/updated proposal or reconsideration of a reject reason). No malicious majority, no forged signatures, and no protocol violation are needed; it is a normal path through the existing code (`handle_block_rejection` → later `handle_block_signature` on the signer side, and the corresponding StackerDB messages reaching the node's `StackerDBListener`). This makes the double-count readily reachable during ordinary network conditions (message reordering, timeouts causing a signer to reject then accept a corrected/re-proposed block with the same hash, etc.).

### Recommendation
Track approval and rejection membership using disjoint bookkeeping, or make the "responded" tracking vote-aware (e.g., store `HashMap<slot_id, Vote>` instead of a single `responded_signers: HashSet<slot_id>` plus a separate `gathered_signatures` map) so a later vote from the same signer supersedes—rather than adds to—the earlier one. Concretely, when processing `Accepted`, first check if `slot_id` is present in a rejection-tracking set/map and, if so, subtract `signer_entry.weight` from `total_weight_rejected` (and remove any per-txid `failed_txids` weight it contributed) before adding it to `total_weight_approved`; symmetrically for `Rejected` overriding a prior `Accepted`. This preserves the invariant that a given signer's weight counts toward at most one side of the tally at any time.

### Proof of Concept
1. Node starts a mining round and creates a `BlockStatus` for block B with `total_weight_approved = 0`, `total_weight_rejected = 0`, `responded_signers = {}`, `gathered_signatures = {}` (`stackerdb_listener.rs`).
2. Signer S (weight `w`) sends `BlockResponse::Rejected(B)`. Node processes: `responded_signers.insert(S)` → true, so `total_weight_rejected += w` (line 515-518).
3. S subsequently sends `BlockResponse::Accepted(B)` (legitimate reconsideration, matching `LocallyRejected -> LocallyAccepted` in the documented state machine). Node processes: `gathered_signatures` does not contain S → `total_weight_approved += w` (lines 443-446); `gathered_signatures.insert(S, sig)`; `responded_signers.insert(S)` is a no-op since S is already present (line 465).
4. Now `total_weight_approved` and `total_weight_rejected` both include `w` for the same signer S — `total_weight_approved + total_weight_rejected` can exceed the real distinct signer weight that has voted, and stale `total_weight_rejected` persists even though S no longer opposes the block.
5. If other signers push `total_weight_rejected` (including S's stale `w`) past `total_weight - weight_threshold` in `signer_coordinator.rs:509-513`, the coordinator returns `NakamotoNodeError::SignersRejected` and the block is abandoned, even though a correct accounting (excluding S's superseded rejection) would show rejection weight below the blocking minority and/or approval weight reaching `weight_threshold`.
