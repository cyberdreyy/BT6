### Title
Claimed instant-withdraw receipts are not removed from `instantWithdrawClaimsByEpoch`, inflating default recovery basis and reserve — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` records the request in three aggregates: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, and `instantWithdrawClaimsByEpoch[epoch]` (lines 356–374). When the user later claims via `claimInstantWithdrawRequest`, only `instantWithdrawsRequests[_user]` is cleared (lines 387–392); the per-epoch aggregates `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are left stale. This mirrors the reported bug: a withdrawal completes but the accounting counter that later feeds an integrity computation is never updated.

### Finding Description
`defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery claim basis whenever `pendingInstantWithdraws != 0` (lines 644–649). `_defaultPrefundedInstantReserve` assumes that the funded portion of those epoch claims — `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` — is still held as underlying in the strategy (lines 716–723). Both assumptions break once a user claims:

- `claimInstantWithdrawRequest` burns the receipt tokens and transfers the funded underlying out (lines 387–392), but `instantWithdrawClaimsByEpoch[epochNumber]` still contains the claimed amount.
- `defaultPendingClaimBasis` then counts an already-paid-out, already-burned receipt as outstanding claim basis.
- `_defaultPrefundedInstantReserve` counts the paid-out underlying as if it were still in the strategy reserve.

If a borrower default is finalized in the same epoch while other instant receipts remain unfunded (`pendingInstantWithdraws != 0`, so `defaultInstantWithdrawsFinalized` is set at line 696), `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688) from an overstated `reserveAmount` and an overstated `totalBasis`. The stored `defaultRecoveryReserve` (line 691) exceeds the strategy's actual underlying balance by exactly the amount already claimed.

### Impact Explanation
Broken invariant: solvency of the default recovery reserve. Every `_transferDefaultRecovery` payout draws against a reserve that is overstated by the claimed amount `C`. Claims are paid at `defaultRecoveryPrice` until the underlying balance is exhausted; the last `C` worth of defaulted-epoch receipts (normal `withdrawsRequestsByEpoch`, APR0 claims, or unfunded instant receipts claimed via `_claimDefaultedInstantWithdrawRequest`) revert on transfer — permanent freezing of unclaimed recovery for honest users. Conversely, an unprivileged tranche holder who requested an instant withdraw and claimed early exits at 100% par while simultaneously worsening every other claimant's recovery. Loss is quantifiable: up to the full instant-withdraw amount claimed before finalization.

### Likelihood Explanation
Requires only: (1) a running epoch with instant-withdraw funding partially collected via `collectInstantWithdrawFunds` (`pendingInstantWithdraws > 0` but less than `instantWithdrawClaimsByEpoch`), (2) an unprivileged holder claiming their funded instant receipt, and (3) the borrower subsequently defaulting in the same epoch so the guardian/manager (honest) calls `finalizeDefaultRecovery` — exactly the "sequence around honest privileged calls" the scenario allows. No malicious privileged role is needed; the accounting gap is entirely in unprivileged claim sequencing. Partial instant funding is a normal mode (instant withdrawals draw on whatever the startEpoch liquidity move returned), so the precondition is realistic.

### Recommendation
In `claimInstantWithdrawRequest` (and `_claimDefaultedInstantWithdrawRequest`), decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, or track the still-unclaimed funded portion separately so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only count live receipts and actually-held underlying.

### Proof of Concept
Foundry fork PoC (conceptual, using the repo's existing `test/foundry/IdleCreditVault.t.sol` harness):

1. Deposit into AA tranche; manager starts epoch with instant withdrawals enabled and an APR drop (`lastEpochApr > unscaledApr + instantWithdrawAprDelta`) so `requestInstantWithdraw` is reachable via the CDO withdraw path.
2. User A requests instant withdraw of `100e18`; `instantWithdrawClaimsByEpoch[N] = 100e18`, `pendingInstantWithdraws = 100e18`.
3. `startEpoch`/`collectInstantWithdrawFunds` funds only `60e18` → `pendingInstantWithdraws = 40e18`.
4. User A calls `claimInstantWithdrawRequest`: receives `100e18`... to keep it strictly partial, have two instant requesters A (`60e18`) and B (`40e18`); A claims `60e18`. Now `instantWithdrawClaimsByEpoch[N]` still reads `100e18` while the strategy holds `0` instant-backing underlying.
5. Borrower fails to repay; guardian calls the default path → `finalizeDefaultRecovery(recovered, source)`.
6. `defaultPendingClaimBasis()` returns `pendingWithdraws + 100e18` (includes A's burned receipt); `_defaultPrefundedInstantReserve()` returns `100e18 - 40e18 = 60e18` although that `60e18` was already paid to A.
7. `defaultRecoveryReserve` is overstated by `60e18`. When B and other pending receipt holders claim via `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest`, cumulative payouts exceed the strategy's real underlying balance by `60e18` → final `safeTransfer` reverts, permanently freezing the tail of recovery claims.

Note: I verified the claim path and basis/reserve computations directly; I did not fully trace `_claimDefaultedInstantWithdrawRequest`'s per-user basis read (lines beyond 781), so whether a claimed user could also double-claim via the stale `instantWithdrawsRequestsByEpoch` entry is unconfirmed — but the reserve/basis inflation above stands on the cited lines alone.
