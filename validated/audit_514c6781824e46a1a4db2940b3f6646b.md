### Title
Post-default withdraw requests bypass the mandatory epoch wait and drain the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Nextcloud bug class is a second verification step being skipped after the first check passes. The closest analog in idle-tranches is the withdraw flow in `IdleCreditVault`: a request is supposed to be claimable only after `epochNumber` has advanced past `lastWithdrawRequest` (the "second factor" of the request → wait → claim flow). Once `defaultRecoveryFinalized` is set, `claimWithdrawRequest` routes to `_claimPostDefaultWithdrawRequest` *before* the epoch-maturity gate in `_claimFundedWithdrawRequest`, so post-default receipts created via `postDefaultRequests` can be claimed immediately, in the same epoch — or even the same transaction — as the request.

### Finding Description
In `IdleCreditVault.requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:271-295) a receipt is recorded and `lastWithdrawRequest[_user] = currentEpoch`. The funded-claim path `_claimFundedWithdrawRequest` (lines 319-350) enforces the mandatory delay:

```solidity
if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
  revert NotAllowed();
}
```

However `claimWithdrawRequest` (lines 301-314) first checks `defaultRecoveryFinalized` and calls `_claimPostDefaultWithdrawRequest(_user)`, returning early if a post-default receipt exists. That path is described as "already priced after the haircut and backed by the reserve" — it pays directly from the fixed recovery reserve without consulting `epochNumber`/`lastWithdrawRequest` at all.

After `finalizeDefaultRecovery`, `requestWithdraw` is re-enabled for users holding defaulted tranche/receipt balances (the test at test/foundry/IdleCreditVault.t.sol:4644-4652 shows `requestWithdraw` succeeds post-default and creates a `postDefaultRequests` receipt). Because the claim path for those receipts never enforces the one-epoch maturity gate, the request-then-wait invariant is bypassed: any holder can atomically `requestWithdraw` + `claimWithdrawRequest` and be paid from the reserve first-come-first-served.

### Impact Explanation
The recovery reserve (`defaultPendingClaimBasis` / recovered funds held by the vault) is sized to satisfy all claims pro rata at the haircut ratio. The epoch wait exists so that claimable volume is bounded and predictable when funds are distributed. Bypassing it lets a single fast claimant pull a payout from the fixed reserve ahead of all other defaulted-epoch and post-default claimants, leaving the reserve underfunded for later claimants — a direct, quantified loss equal to the shortfall imposed on those who claim later (up to the attacker's full receipt value).

### Likelihood Explanation
Requirements: a borrower default has been finalized via `finalizeDefaultRecovery` and post-default requests are enabled. The attacker needs only to be a tranche-token holder (which can be acquired permissionlessly — `requestWithdraw`/claim paths do not require `isWalletAllowed`; only `_deposit`/`depositDuringEpoch` do, IdleCDOEpochVariant.sol:645,668). No privileged role is involved; the sequence is two ordinary user calls. The reserved funds are transferred by `_transferFundedClaim`/the post-default payout to the first claimant, so the race favors whoever acts first after finalization.

### Recommendation
Apply the same maturity check used in `_claimFundedWithdrawRequest` to `_claimPostDefaultWithdrawRequest` (revert when `epochNumber <= lastWithdrawRequest[_user]` unless the pool is closed with `epochEndDate == 0`), or record a separate `lastPostDefaultRequest` epoch and gate post-default claims on it, so no receipt created after finalization can be claimed before the next epoch boundary.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testPostDefaultClaimBypassesEpochWait() external {
  address attacker = makeAddr("attacker");
  _depositWithUser(attacker, 10_000 * ONE_SCALE, true);

  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr, 0); // borrower default
  _checkDefault();

  uint256 recovered = /* recovery amount */;
  deal(defaultUnderlying, manager, recovered);
  vm.startPrank(manager);
  IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
  cdoEpoch.finalizeDefault(recovered, manager);
  vm.stopPrank();
  // manager finalizes recovery -> defaultRecoveryFinalized = true

  uint256 stratPre = IERC20Detailed(address(strategy)).balanceOf(attacker);
  uint256 undPre   = underlying.balanceOf(attacker);

  vm.startPrank(attacker);
  cdoEpoch.requestWithdraw(0, address(AAtranche)); // creates postDefault receipt, same epoch
  cdoEpoch.claimWithdrawRequest();                  // pays immediately: no epoch-wait revert
  vm.stopPrank();

  assertGt(underlying.balanceOf(attacker) - undPre, 0, "claim succeeded without waiting an epoch");
}
```

Expected: `claimWithdrawRequest` should revert with `NotAllowed` (epoch not matured); actual: it pays out from the recovery reserve in the same epoch, bypassing the request-maturity gate enforced for funded claims.
