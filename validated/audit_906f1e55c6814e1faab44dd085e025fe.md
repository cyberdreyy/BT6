## Finding: Confirmed Valid

The vulnerability described is real and reproducible in the current code. Tracing the flow:

**Root cause**

`add_distribution` records the pending commission for `old_operator` by literal address, not a beneficiary-resolved address: [1](#0-0) 

`switch_operator` removes the `StakingContract` under `old_operator`, calls `request_commission_internal` (which calls `add_distribution(old_operator, staking_contract, old_operator, commission_amount)` — recording a pending share for `old_operator`), then reinserts the **same** `staking_contract` struct (including its `distribution_pool` with the `old_operator` share) under the **new** key `new_operator`: [2](#0-1) 

The existing unit test `test_staker_can_switch_operator` explicitly confirms this: after switching, the pending distribution is still attributed to `operator_1_address` even though the contract is now stored/keyed under `operator_2_address`: [3](#0-2) 

**The bug**

When `distribute()` (a permissionless, public entry function) is later called, it must be invoked as `distribute(staker, new_operator)`, since `old_operator` is no longer a valid key (`assert_staking_contract_exists` would fail otherwise): [4](#0-3) 

Inside `distribute_internal`, the beneficiary redirection check compares each `recipient` against the `operator` **parameter passed in** (which is `new_operator`), not against the actual stored recipient address: [5](#0-4) 

Since the pending distribution's `recipient == old_operator` but the comparison target is `new_operator`, the condition `recipient == operator` is `false`. `beneficiary_for_operator(operator)` is therefore never invoked for `old_operator`'s pending share, and the funds get deposited directly to `old_operator` instead of `old_operator`'s registered `BeneficiaryForOperator`.

**Why existing tests don't catch it**

`test_operator_can_set_beneficiary` sets the beneficiary and calls `distribute()` to fully clear the pending commission *before* calling `switch_operator`, so it never exercises the case where `old_operator` has both (a) an outstanding pending distribution and (b) a configured beneficiary at the moment of the switch: [6](#0-5) 

### Title
Beneficiary redirection is bypassed for pending commission carried across `switch_operator` - (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` preserves a pending commission distribution keyed to the `old_operator` address inside a `StakingContract` struct that is re-inserted under `new_operator`. Because `distribute_internal`'s beneficiary check compares the *stored recipient* against the *operator argument currently in scope* (the new operator), rather than against the actual recipient's own beneficiary registration, any subsequent permissionless `distribute()` call pays `old_operator` directly, bypassing `old_operator`'s `BeneficiaryForOperator` redirection.

### Finding Description
`add_distribution` bakes in the operator's raw address as `recipient`, deferring beneficiary resolution to distribution time (`distribute_internal`) via `if (recipient == operator) { recipient = beneficiary_for_operator(operator) }`. This logic implicitly assumes `recipient == operator` implies "this distribution belongs to whichever operator is passed into this call." That assumption breaks once `switch_operator` reassigns the map key from `old_operator` to `new_operator` while leaving a stale `recipient == old_operator` entry inside the carried-over `distribution_pool`. All future calls to `distribute(staker, new_operator)` pass `operator = new_operator` into `distribute_internal`, so the equality check against the stale `old_operator` entry always fails, and `beneficiary_for_operator` is never consulted for that entry.

### Impact Explanation
An operator's registered beneficiary can permanently lose commission funds that were already accrued and legitimately owed to them, if the staker switches operators before the pending distribution is flushed. This directly violates the "beneficiary-update paths must not redirect value" invariant, since a value transfer intended for a beneficiary is silently redirected to the (possibly no-longer-controlled or untrusted) old operator's own address.

### Likelihood Explanation
This requires no privileged access beyond what any staker already has for their own contract (calling `switch_operator`) plus a fully permissionless `distribute()` call available to anyone. The only precondition is that the old operator has unpaid/pending commission and a configured beneficiary at the time of the switch — a normal, easily reachable state in production usage (e.g., an operator sets a beneficiary for tax/custody reasons and later gets replaced by the staker).

### Recommendation
In `distribute_internal`, resolve the beneficiary redirection based on the actual stored `recipient` address rather than the `operator` parameter, e.g. change the check to determine if `recipient` corresponds to *any* operator with a `BeneficiaryForOperator` record (or explicitly persist beneficiary-resolved recipients at `add_distribution` time so redirection doesn't need to be re-derived after operator/key changes).

### Proof of Concept
1. `staker` calls `create_staking_contract_with_coins(staker, operator1, ...)`.
2. `operator1` calls `set_beneficiary_for_operator(operator1, beneficiary_B)`.
3. Time passes, rewards accrue; `operator1` (or anyone authorized) calls `request_commission`, which calls `add_distribution(operator1, staking_contract, operator1, commission_amount)` — a pending share for `operator1` is recorded, but not yet distributed (i.e., skip calling `distribute()` before the switch).
4. `staker` calls `switch_operator(staker, operator1, operator2, new_commission)`. The `StakingContract` (with `operator1`'s pending share still inside its `distribution_pool`) is now stored under key `operator2`.
5. Anyone calls `distribute(staker_address, operator2_address)` (permissionless, per its doc comment: "Allow anyone to distribute...").
6. Inside `distribute_internal`, the loop processes `recipient == operator1_address`, compares `recipient == operator` (`operator == operator2_address`) → false → skips `beneficiary_for_operator` lookup → deposits directly to `operator1_address` instead of `beneficiary_B`.
7. Assert: `coin::balance<AptosCoin>(operator1_address)` increased by the commission amount, while `coin::balance<AptosCoin>(beneficiary_B)` remains unchanged — confirming beneficiary redirection was bypassed. [2](#0-1) [5](#0-4) [1](#0-0)
