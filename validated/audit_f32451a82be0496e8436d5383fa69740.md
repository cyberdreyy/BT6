I have a promising lead: `requestInstantWithdraw` in `IdleCreditVault.sol` has no `defaultRecoveryFinalized` handling, unlike `requestWithdraw`. Need to verify the CDO-side path is reachable post-default.### Title
Post-default instant withdraw requests mint unbacked receipts that drain `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` has an explicit `defaultRecoveryFinalized` branch that routes post-default requests into the haircut-priced `postDefaultRequests` bucket. `requestInstantWithdraw` — reached from `IdleCDOEpochVariant.requestWithdraw` when the instant-withdraw path is enabled and APR dropped — has **no** such branch. A tranche holder can therefore create a brand-new instant receipt *after* default finalization, have it recorded under `epochNumber == defaultRecoveryEpoch`, and immediately claim it against the finalized recovery reserve.

### Finding Description
In `IdleCreditVault.sol`:

- `requestWithdraw` (lines 243–295) correctly rejects/handles the post-finalization state: after `defaultRecoveryFinalized` it requires the user to have cleared old receipts and books the new request into `postDefaultRequests` paid 1:1 from the reserve only because the CDO already applied the haircut.
- `requestInstantWithdraw` (lines 356–375) performs only `_ensureDefaultRecoveryInitialized()`, burns CDO strategy tokens, mints a receipt to the user, and records `instantWithdrawsRequestsByEpoch[_user][epochNumber]` / `instantWithdrawClaimsByEpoch[epochNumber]` / `pendingInstantWithdraws` — with no `defaultRecoveryFinalized` check.
- `claimInstantWithdrawRequest` (lines 380–393) then does one of two things, both losing:
  - If `defaultInstantWithdrawsFinalized` is true, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. Because `epochNumber` was frozen at `defaultRecoveryEpoch` by `finalizeDefaultRecovery`, the brand-new receipt is indistinguishable from a defaulted-epoch receipt and is paid `claimBasis * defaultRecoveryPrice` out of `defaultRecoveryReserve` (lines 842–856).
  - If `defaultInstantWithdrawsFinalized` is false (`pendingInstantWithdraws == 0` at finalization), the claim falls straight through to `_transferFundedClaim(_user, amount)` at **par**, with no haircut at all.

The CDO-side entry point `IdleCDOEpochVariant.requestWithdraw` (lines 739–791) reaches `creditVault.requestInstantWithdraw` whenever `_isInstantWithdrawEnabled()` and `lastEpochApr > unscaledApr + instantWithdrawAprDelta` — a condition trivially met post-default when the strategy APR has been set to 0 while `lastEpochApr` still holds the pre-default value.

### Impact Explanation
Direct theft of recovery funds. `defaultRecoveryReserve` is sized exactly to cover active-LP basis plus defaulted-epoch pending receipts at `defaultRecoveryPrice`. An attacker-held tranche converts into an instant receipt that withdraws from this fixed reserve — at the recovery price, or at par when `defaultInstantWithdrawsFinalized == false` — before legitimate defaulted-epoch claimants and active LPs claim. Every unit extracted is a unit of reserve stolen from honest users; with a thin reserve the attacker can drain it entirely, leaving remaining claims unpayable (insolvency of the recovery pool). The strategy-token burn of CDO balance further lowers active backing after `defaultRecoveryPrice` was already crystallized.

### Likelihood Explanation
Requires only an unprivileged tranche-token holder and that the instant-withdraw APR-delta condition holds post-default — the natural state after a default since `unscaledApr` is typically lowered to 0 while `lastEpochApr` retains the last epoch's value. No privileged misbehavior needed; `finalizeDefaultRecovery` runs normally. One caveat I could not fully verify within the indexed context: whether `_updateAccounting()` or `epochEndDate`/pause flags in `IdleCDOEpochVariant.requestWithdraw` revert once `defaulted()` is set; the visible function body shows no default check before the instant-withdraw branch, and `requestWithdraw`'s own post-default path proves the function remains callable after finalization.

### Recommendation
Mirror the `requestWithdraw` post-default guard in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is set, either revert (`NotAllowed`) or route the request into `postDefaultRequests` with the same haircut pricing. Additionally, in `_claimDefaultedInstantWithdrawRequest`, require the request epoch to be strictly `<= defaultRecoveryEpoch` for basis that existed at finalization, and never let post-finalization receipts draw from `defaultRecoveryReserve`.

### Proof of Concept
Foundry fork PoC sketch (standard, non-programmable deployment):

```solidity
// Setup: depositAA/BB, run epoch 0, requestWithdraw for victim, run epoch 1.
// Borrower fails to repay -> manager triggers default flow;
// finalizeDefault/_handleBorrowerDefault -> strategy.finalizeDefaultRecovery(recovered, source).
// Post-state: defaultRecoveryFinalized = true, defaultRecoveryPrice = p < 1e18,
//             epochNumber == defaultRecoveryEpoch, unscaledApr == 0,
//             lastEpochApr > instantWithdrawAprDelta.

address attacker = attackerTrancheHolder; // holds AA tranche tokens post-default
uint256 reserveBefore = underlying.balanceOf(address(strategy));
uint256 trancheAmt = IERC20(AAtranche).balanceOf(attacker);

vm.prank(attacker);
cdoEpoch.requestWithdraw(trancheAmt, address(AAtranche));
// -> instant path -> IdleCreditVault.requestInstantWithdraw mints receipt at epochNumber
//    == defaultRecoveryEpoch. No defaultRecoveryFinalized check.

vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// -> _claimDefaultedInstantWithdrawRequest pays attacker
//    claimBasis * defaultRecoveryPrice from defaultRecoveryReserve
//    (or full par via _transferFundedClaim if defaultInstantWithdrawsFinalized == false)

assertGt(underlying.balanceOf(attacker), 0);
assertLt(underlying.balanceOf(address(strategy)), reserveBefore);
// Legitimate defaulted-epoch claimant now finds reserve depleted / claims short.
```

The asymmetry is the smoking gun: `requestWithdraw` at `IdleCreditVault.sol:247` explicitly handles `defaultRecoveryFinalized`, while `requestInstantWithdraw` at `IdleCreditVault.sol:356` does not — a crafted sequence (tranche holder requesting at the instant-withdraw trigger after finalization) escapes the loss waterfall exactly like the crafted-archive input escapes the decoder's error handling in CVE-2018-5996.
