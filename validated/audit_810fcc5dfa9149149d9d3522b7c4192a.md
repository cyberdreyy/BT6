### Title
User script command can disable the SIGTERM anti-dump trap installed by `ScriptHeader.Generate` because commands run in the same shell, not a protected subshell - (File: functions/script_legacy/internal/script_header.go)

### Summary
`ScriptHeader.Generate` installs `trap exit 1 TERM` at the top of the generated script to stop bash 4+ from dumping the remaining script text (which can include sourced `GITLAB_ENV` values) into the job trace when the runner sends SIGTERM on cancellation. Unlike the equivalent protection in `shells/bash.go` and `functions/concrete/run/stages/internal/scriptwriter/scriptwriter.go`, the `script_legacy` script builder (`functions/script_legacy/internal/script_generator.go`) writes each user command directly into the top-level script body rather than wrapping it in a trap-reinstalling subshell, so any authored command that runs `trap - TERM` or redefines the TERM handler executes in the exact same shell context and permanently removes the guard for the rest of the script.

### Finding Description
`ScriptHeader.Generate` (functions/script_legacy/internal/script_header.go:49-73) writes the trap once, at the very top of the script: [1](#0-0) 

`ScriptGenerator.GenerateScript` then appends the optional `GITLAB_ENV` sourcing preamble and every user command sequentially into the **same** buffer/shell — there is no subshell isolation: [2](#0-1) 

`CommandProcessor.writeNormalCommand` confirms each command is emitted as a plain top-level statement (echo log line + the command text), executed in the parent shell process: [3](#0-2) 

Because trap state in bash is per-shell (not per-command), any job-authored command such as `trap - TERM` or `trap 'echo pwned' TERM` overwrites the previously-installed handler for the remainder of that same shell process. This is architecturally different from the fix already applied elsewhere in the codebase: both `shells/bash.go` (`BashWriter.Finish`) and `scriptwriter.go` (`buildBashScript`) deliberately execute the user's entire command body inside an explicit subshell that **re-installs** the trap at subshell entry — `(trap 'exit 1' TERM; eval <body>) < /dev/null` — specifically so a trap change made in a nested context doesn't survive to the parent invocation, and the comments there explicitly reference issue #39005 (the bash-version-specific script-dump-on-SIGTERM bug) as the motivation: [4](#0-3) [5](#0-4) 

The `script_legacy` builder has no equivalent isolation: the trap is installed once at the top level and the commands run inline in that same shell, so `trap - TERM` issued by any command directly disarms the guard for everything that follows, including the still-unexecuted script text and any `GITLAB_ENV`-sourced KEY=VALUE lines exported earlier by `ScriptGenerator.GenerateScript`: [6](#0-5) 

Attacker input: the `script` array input to the `scriptv2`/`script_legacy` builtin function is fully job-author-controlled (`functions/script_legacy/script_legacy.go`, `Run`, reads `script` from `builtinCtx.GetInput("script", ...)`), so any pipeline author can insert `trap - TERM` as one of the commands: [7](#0-6) 

Once disarmed, a later runner-issued cancellation SIGTERM (sent by `common.Trace.Cancel`/`Abort` or script-timeout paths, as exercised by the graceful-shutdown tests) reaches the shell with no trap installed. On bash ≥4.4/<5.3 this used to be suppressed, but per the comment in `shells/bash.go:74-88`, bash 5.3+ reintroduced a code path (`print_pipeline` in `notify_of_job_status`) that prints the failed pipeline's text when a signal-killed child is reaped by a shell with no handler — i.e. exactly the scenario this trap exists to prevent. With the trap removed, that print path (or the <4.4 "current command echoed before termination" behavior) can dump the remaining unexecuted script text — including the `GITLAB_ENV` sourcing line and any subsequent commands containing masked/protected variable values — to stdout/stderr, which the executor pipes straight into the job trace.

### Impact Explanation
A pipeline author (unprivileged CI job author) can cause protected/masked CI/CD variable values embedded in the still-unexecuted portion of the generated script (or sourced from `GITLAB_ENV`) to be printed into the job trace on cancellation, violating the invariant that masked/protected values never leak through traces. This is a trace/log leak of the author's own job content, but because the script body can reference variables from later stages or GitLab-managed sourced `GITLAB_ENV` entries, this can expose values the author should not be able to observe in cleartext (e.g. protected-variable expansions that CI masking relies on suppressing at print time, not at generation time).

### Likelihood Explanation
Feasibility is high: the attacker only needs to author a job with a `script` command `trap - TERM` (or any trap redefinition) as one of the `scriptv2` commands, and have the job cancelled/aborted or hit the script timeout while a later command with sensitive content is queued to run. This is fully within normal CI authoring, requires no special GitLab or infra privilege, and is deterministically reproducible given a bash version exhibiting the dump behavior (bash ≥5.3, per the existing test's own caveat about needing a matching bash build). The `script_legacy` path is reachable via the `scriptv2` builtin dispatched from `commands/steps/steps.go` / `common/build_step_dispatch.go`.

### Recommendation
Apply the same fix already used in `shells/bash.go` and `scriptwriter.go`: wrap the entire command body generated by `ScriptGenerator.GenerateScript` in an explicit subshell that re-installs the TERM trap at subshell entry, e.g. `(trap 'exit 1' TERM; <body>) < /dev/null`, so that a `trap` change made by an authored command inside the body cannot remove the guard the outer/header trap relies on. Alternatively, since this path executes commands as plain statements rather than via `eval`, ensure the trap is unconditionally re-asserted after each command (or make the trap read-only via a wrapper function) so a later `trap - TERM`/`trap ... TERM` cannot persist across command boundaries.

### Proof of Concept
Go integration test (mirroring `common/buildtest/bash_eval.go`'s `RunBuildWithScriptBodyLeakOnCancel` pattern, adapted for `script_legacy`):
1. Build a `commands` array for `ScriptGenerator.GenerateScript`: `["trap - TERM", "sleep 30", "echo SENSITIVE_TOKEN_SHOULD_NOT_LEAK"]`.
2. Generate the script via `internal.NewScriptGenerator(...).GenerateScript(commands)` and execute it via `internal.NewExecutor(...).Execute(ctx, script)` (or through the full `builtinFunc.Run` on an executor pinned to a bash build known to exhibit the pipeline-dump behavior, e.g. bash 5.3+).
3. While the `sleep 30` step is running, send SIGTERM to the process (simulating cancellation).
4. Assert: `stdout`/`stderr` captured by the trace does NOT contain `SENSITIVE_TOKEN_SHOULD_NOT_LEAK` or any raw script source text (`assert.NotContains(t, out.String(), "SENSITIVE_TOKEN_SHOULD_NOT_LEAK")`), proving the trap-disable defeats the guard and the remaining script body leaks on cancellation — contrasted with a control case without the `trap - TERM` line, where the assertion should pass (no leak).

```go
func (g *ScriptGenerator) GenerateScript(commands []string) string {
	var buf strings.Builder

	buf.WriteString(g.header.Generate())

	if g.gitLabEnvFile != "" {
		// Export GITLAB_ENV so user commands can append KEY=VALUE pairs to it,
		// then source any variables written by previous stages. This mirrors
		// what AbstractShell.writeExports does for the legacy shell path.
		fmt.Fprintf(&buf, "export GITLAB_ENV=%q\n", g.gitLabEnvFile)
		fmt.Fprintf(
			&buf,
			"if [ -f %q ]; then while read -r line; do export \"$line\" || true; done < %q; fi\n\n",
			g.gitLabEnvFile,
			g.gitLabEnvFile,
		)
	}

	for i, cmd := range commands {
		g.processor.ProcessCommand(&buf, i, cmd)
	}

	return buf.String()
```

```go
	// Run the user script in an explicit subshell with stdin closed via
	// `< /dev/null`. The TERM trap is re-installed inside this subshell so that
	// SIGTERM causes a clean exit instead of a signal-induced death that would
	// dump the eval body — including expanded secrets — to the job log on
	// cancellation (issue 39005). FF_USE_LEGACY_BASH_EVAL restores the prior
	// `: | eval ...` pipeline form as an escape hatch.
	if b.UseLegacyBashEval {
		buf.WriteString(": | eval " + shellEscape(body.String()) + "\n")
	} else {
		buf.WriteString("(trap 'exit 1' TERM; eval " + shellEscape(body.String()) + ") < /dev/null\n")
	}
```
