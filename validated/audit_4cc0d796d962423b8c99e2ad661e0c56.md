## Title
B20 token `permit()` accepts malleable (high-s) ECDSA signatures, unlike every other signature-recovery path in the codebase - (File: `crates/common/precompiles/src/common/ops/permit.rs`)

### Summary
The B20/B20Asset/B20Stablecoin `permit()` EIP-2612 implementation recovers the signer via `PermitArgs::recover_signer`, which builds a signature from raw `(r, s, v)` and calls `recover_address_from_prehash` with no EIP-2 low-`s` canonicality check. [1](#0-0)  Every other ECDSA-recovery path in this same codebase — the EIP-8130 k1 authenticator and the EOA sender-recovery path — explicitly rejects high-`s` (malleable) signatures via `sig.normalize_s().is_some()` checks, and the codebase's own test suite documents *why*: "the malleable upper-half-s counterpart of a valid signature ... recovers the same signer but MUST be rejected so the transaction id cannot be malleated." [2](#0-1) [3](#0-2)  That protection is absent from the permit signature-verification path shared by all B20 token variants.

### Finding Description
`permit()` in every B20 logic variant (asset v1/v2, stablecoin v1/v2) calls `args.recover_signer(signing_hash)` / `args.metered_recover_signer(...)`, both of which delegate to `PermitArgs::recover_signer`: [1](#0-0) 

```rust
pub fn recover_signer(&self, signing_hash: B256) -> Result<Address> {
    let odd_y_parity = match self.v { ... };
    let sig = alloy_primitives::Signature::from_scalars_and_parity(self.r, self.s, odd_y_parity);
    sig.recover_address_from_prehash(&signing_hash)...
}
```

This performs raw secp256k1 recovery from attacker-supplied `r`, `s`, `v` with no check that `s` is in the lower half of the curve order (EIP-2). Because secp256k1 is symmetric, for any valid signature `(r, s, v)` there is a second, distinct signature `(r, N-s, !v)` that recovers to the exact same `owner` address. Both are accepted by this code.

By contrast, the codebase's own EIP-8130 transaction/authenticator recovery paths deliberately reject the high-`s` form: [4](#0-3) [5](#0-4) 

This asymmetry means the security property the team clearly considers necessary elsewhere ("the transaction id cannot be malleated") was not applied to the token `permit()` signature path invoked in `permit()`: [6](#0-5) [7](#0-6) 

The nonce is only consumed *after* successful validation, `token.accounting_mut().increment_nonce(args.owner)`, so anyone who observes a pending `permit` transaction in the mempool can derive the malleable counterpart signature and front-run with their own `permit(owner, spender, value, deadline, v', r, s')` call that consumes the owner's nonce first. [8](#0-7) 

### Impact Explanation
This is a classic SWC-117 signature-malleability gap in an EIP-2612 permit implementation. The primary reachable impact is: an unprivileged actor can extract any pending, valid `permit` signature from calldata/mempool, recompute the malleable twin `(N-s, !v)`, and submit it ahead of the original. Because the malleable signature recovers to the same `owner`, it passes `validate_recovered_address` and consumes the owner's nonce, causing the legitimate, honestly-submitted transaction to revert with `InvalidSigner` once it lands (nonce already advanced). This breaks any workflow that atomically composes `permit()` with a dependent action (e.g., router/aggregator contracts that call `permit()` then `transferFrom()` in the same transaction) — the composed transaction reverts due to the pre-consumed nonce, and does not itself steal or move funds because `spender`/`value` are fixed by the original signed data, but it is a reliable, unprivileged griefing/DoS vector against B20 permit-based flows.

### Likelihood Explanation
High likelihood of triggering: any observer of the public mempool/RPC can see a submitted `permit` call's `(r, s, v)` and compute the malleable form with a single scalar subtraction — no cryptographic secret is needed, only elementary curve arithmetic (`s' = N - s`, `v' = v XOR 1`). This requires no special privilege, matching the "unprivileged transaction sender / anonymous RPC client" reachable-actor class.

### Recommendation
Enforce EIP-2 low-`s` canonicality in `PermitArgs::recover_signer` before recovery, mirroring the check already used elsewhere in this codebase (`sig.normalize_s().is_some()` rejection in `RecoveredActorId::recover_k1` and `AuthenticatorDispatch::p256_verify`), so that only the canonical low-`s` signature for a given `(owner, spender, value, nonce, deadline)` is accepted.

### Proof of Concept
1. Owner signs a valid `permit` request producing `(v, r, s)` with `s` in the lower half of the curve order, submitted as a public mempool transaction.
2. An observer reads `(v, r, s)` from the pending transaction's calldata.
3. Observer computes `s' = SECP256K1_N - s` and `v' = v XOR 1` (flip parity), exactly as demonstrated by the existing test `recover_eoa_sender_unchecked_accepts_high_s_signature` in this repo, which shows the same curve trick recovers an identical address. [9](#0-8) 
4. Observer submits `permit(owner, spender, value, deadline, v', r, s')` with higher gas/priority to be mined first.
5. `PermitArgs::recover_signer` recovers `owner` from the malleable signature and succeeds (no low-`s` check exists), consuming `nonces[owner]`. [10](#0-9) 
6. The original transaction, when mined, reverts with `InvalidSigner` because the nonce has already advanced, confirmed by the existing replay test's own comment: "Same (v, r, s): the nonce has advanced, so recovery no longer matches `owner`." [11](#0-10)

        // (negate s, flip the recovery parity) recovers the same signer but MUST be

    fn recover_eoa_sender_unchecked_accepts_high_s_signature() {
        use alloy_primitives::U256;
        use alloy_signer::SignerSync;
        use alloy_signer_local::PrivateKeySigner;

        // secp256k1 curve order N.
        const SECP256K1_N: U256 = U256::from_be_slice(&[
            0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff, 0xff,
            0xff, 0xfe, 0xba, 0xae, 0xdc, 0xe6, 0xaf, 0x48, 0xa0, 0x3b, 0xbf, 0xd2, 0x5e, 0x8c,
            0xd0, 0x36, 0x41, 0x41,
        ]);

        let signer = PrivateKeySigner::random();
        let expected = signer.address();

        let mut tx = sample_signed(false).into_tx();
        tx.sender = None;
        let hash = tx.sender_signature_hash();

        // Sign normally (low-s, EIP-2 canonical), then flip s into the upper half
        // by replacing it with N - s and inverting parity.
        let canonical = signer.sign_hash_sync(&hash).unwrap();
        let high_s_sig = alloy_primitives::Signature::new(
            canonical.r(),
            SECP256K1_N - canonical.s(),
            !canonical.v(),
        );
        let signed =
            Eip8130Signed::new(tx, Bytes::from(high_s_sig.as_bytes().to_vec()), Bytes::new());

        // The checked recovery rejects the high-s form (EIP-2);
        // the unchecked recovery accepts it and recovers the same address.
        assert!(signed.recover_eoa_sender().is_err());
        assert_eq!(signed.recover_eoa_sender_unchecked().unwrap(), Some(expected));
    }

    fn permit(
        &self,
        token: &mut B20StablecoinToken<S, A>,
        chain_id: u64,
        now: U256,
        args: PermitArgs,
    ) -> Result<()> {
        if now > args.deadline {
            return Err(BasePrecompileError::revert(IB20::ExpiredSignature {
                deadline: args.deadline,
            }));
        }
        let domain_sep = self.domain_separator(token, chain_id)?;
        let nonce = token.accounting().nonce(args.owner)?;
        let signing_hash = args.signing_hash(domain_sep, nonce);
        let recovered = args.recover_signer(signing_hash)?;
        PermitArgs::validate_recovered_address(recovered, args.owner)?;
        token.accounting_mut().increment_nonce(args.owner)?;
        self.approve(token, args.owner, args.spender, args.value)
    }
