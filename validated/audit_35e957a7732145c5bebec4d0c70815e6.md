### Title
Loss-haircutted withdraw receipt is silently repriced to par when the user makes a later request — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.claimWithdrawRequest` routes each user through `_claimLossAdjustedWithdrawRequest`, which looks up the haircut epoch using only `lastWithdrawRequest[_user]`. If a user's pending receipt was haircut in epoch E via `stopEpochWithDuration(_lossAmount)` (stored in `lossRecoveryPriceByEpoch[E]`), and the user then files a new withdraw request in a later epoch E2 before claiming, `lastWithdrawRequest[_user]` is overwritten to E2. The E1 loss-adjusted basis is never cleared nor haircut, and `_claimFundedWithdrawRequest` then pays the full `withdrawsRequests[_user]` aggregate — including the un-haircutted E1 basis — at par.

### Finding Description
In `requestWithdraw`, the vault records per-epoch basis in `withdrawsRequestsByEpoch[_user][epochNumber]` and sets `lastWithdrawRequest[_user] = epochNumber` [1](#0-0) .

When an epoch stops with a realized loss, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]`, zeroes `pendingWithdraws`, and only pulls the post-loss amount into the strategy [2](#0-1) . The pre-loss basis, however, remains fully intact in `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][E]`.

On claim, `_claimLossAdjustedWithdrawRequest` uses `lastWithdrawRequest[_user]` as the sole epoch key. If it differs from the loss epoch (because the user re-requested in E2), `lossRecoveryPriceByEpoch[E2] == 0` and the function returns 0 without clearing the E1 basis [3](#0-2) . `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — the whole pre-loss aggregate — at par via `_transferFundedClaim` [4](#0-3) . The epoch-wait check `epochNumber <= lastWithdrawRequest[_user]` passes normally after E2 ends, and the `defaultRecoveryReserve` guard in `_transferFundedClaim` is inactive when there is no default [5](#0-4) .

The broken invariant is one-receipt-one-payout at the correct epoch price: a haircut receipt is upgraded to a par receipt purely by the attacker choosing to re-request instead of claim.

### Impact Explanation
An unprivileged KYC'd lender holding tranche tokens can steal `e1Basis * (1 - lossRecoveryPrice)` underlyings. Concretely, with a 50% loss price on E1, the attacker who requested 100k of withdraws in E1, re-requests a dust amount in E2, and after E2's stop claims ~100k + dust instead of ~50k + dust. The excess is paid from strategy underlyings funded for other pending/funded claimants, producing direct theft and vault insolvency for the remaining users. No privileged role, default, or oracle involvement is required — only two honest manager `stopEpochWithDuration`/`stopEpoch` calls in between the attacker's transactions.

### Likelihood Explanation
The attack requires only that an epoch is stopped with `_lossAmount > 0` while the attacker has a pending receipt — an expected mode of operation for a credit vault realizing losses — and that the attacker files a second withdraw request in any later epoch before claiming. Both actions are permissionless user flows (`requestWithdraw` is callable by any allowed wallet during the buffer). Re-requesting before claiming is explicitly contemplated by the code comments in `_claimFundedWithdrawRequest`, so the state combination is realistic.

### Recommendation
In `claimWithdrawRequest`, iterate/clear all epochs present in `withdrawsRequestsByEpoch[_user]` (or track the earliest unsettled loss epoch per user) rather than keying the loss-adjusted path solely on `lastWithdrawRequest[_user]`. At minimum, `_claimLossAdjustedWithdrawRequest` should check `lossRecoveryPriceByEpoch` for every epoch in which the user still has a non-zero `withdrawsRequestsByEpoch` basis, and `_claimFundedWithdrawRequest` should subtract any basis belonging to an epoch with a recorded `lossRecoveryPriceByEpoch` before paying at par.

### Proof of Concept
Foundry fork scenario (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossReceiptUpgradedToPar() external {
    uint256 amount = 10000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amount);
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, amount, true); // attacker holds tranche tokens

    // Epoch 0: attacker requests withdraw of mintedAA-equivalent, epoch runs, then
    // manager stops epoch 1 with a loss so pending receipts are haircut ~50%.
    vm.prank(attacker);
    uint256 e1Basis = cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(0);
    // borrower repays only part: fund pendingToFund for lossAmount
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 lossAmount = (activeBasis + pendingBasis) / 2; // ~50% loss
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, borrower, repay);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), repay);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), lossAmount);
    // lossRecoveryPriceByEpoch[e1Epoch] set; attacker does NOT claim.

    // Epoch 2: attacker re-requests a dust withdraw -> lastWithdrawRequest moves to e2.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Claim: lossRecoveryPriceByEpoch[lastWithdrawRequest]==0 so e1 basis is paid at par.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;
    // paid ~= e1Basis + dust, while only ~e1Basis*lossPrice + dust was funded.
    assertGt(paid, e1Basis * strategy.lossRecoveryPriceByEpoch(e1Epoch) / 1e18 + dust);
}
```

Expected result: `claimWithdrawRequest` succeeds and transfers materially more than the funded post-loss amount, draining underlyings belonging to other receipt holders.

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
