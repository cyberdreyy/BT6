### Title
Missing `approved_time` on a locally-known tenure block silently defaults reorg timing to `0`, letting an attacker force a premature-reorg approval - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` computes `proposal_to_sortition` — the elapsed time between a reorged tenure's first block being locally approved and the new sortition — to decide whether that tenure is "poorly timed" enough to be reorg-able. When the signer's own DB record for that block exists but has no `approved_time` (this signer never locally pre-committed/signed it), the code substitutes `0` instead of failing closed, which always satisfies `Duration::from_secs(0) < first_proposal_burn_block_timing` and permits the reorg unconditionally.

### Finding Description
In `stacks-signer/src/chainstate/mod.rs`, `check_parent_tenure_choice` first requires *some* local record for the reorged tenure's first block (`get_first_approved_block_in_tenure`); if there is none at all, it fails closed with `Ok(false)`: [1](#0-0) 

But if a local record *does* exist and merely lacks `approved_time` (i.e., this signer knows about the block but never locally approved/pre-committed to it — e.g. because it restarted or was partitioned from the miner during that tenure), the code takes a different path: [2](#0-1) 

The comment `"We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal"` makes the design choice explicit: absence of `approved_time` is treated as "the block arrived just before the sortition," forcing `proposal_to_sortition = 0`. Since `Duration::from_secs(0)` is always `< first_proposal_burn_block_timing`, the branch at line 259-274 always pushes the tenure into `superseded_tenures` and the loop continues, ultimately returning `Ok(true)` at line 294 — permitting the reorg regardless of how much real time actually elapsed between the tenure's globally-known first block and the new sortition.

This breaks the intended equality: the reorg-timing gate is supposed to evaluate `proposal_to_sortition >= first_proposal_burn_block_timing` against the tenure's *real* first-block timing, not against a synthetic zero produced by a gap in one particular signer's local knowledge. A signer that simply missed locally pre-committing that block (through no fault of the reorg's legitimacy) degrades to always-permit, while a fully-informed signer with a real `approved_time` correctly measures elapsed time and would reject the same reorg if it happened long before the new sortition.

An attacker who wins the current sortition can craft a `BlockProposal`/`TenureChangePayload` that reorgs a prior tenure whose first block was already globally visible well before the new sortition (satisfying `globally_accepted_blocks <= 1` so the earlier hard-stop at line 213 does not fire). Any signer in the network that has a local record for that tenure's first block but no `approved_time` for it (restart, partition, added to network mid-tenure, etc.) will unconditionally allow the reorg via this path, while other, fully-synced signers correctly refuse it — splitting the network's canonical-parent-tenure view per signer.

### Impact Explanation
This breaks canonicity/uniqueness: different signers reach different verdicts on whether a given tenure was legitimately reorged, purely as a function of gaps in their own local bookkeeping rather than the objective timing of the tenure. A signer degraded this way can be steered by the miner into approving (and eventually signing) a block that builds on a parent tenure other honest, fully-informed signers reject — a Critical chain-safety violation (signing on a non-canonical parent / accepting a reorg deeper than the rules permit). It is repeatable each time the attacker wins a sortition and can find/target a signer with the described local-knowledge gap.

### Likelihood Explanation
Preconditions: (1) attacker wins one sortition (achievable with their own BTC, per threat model), (2) the reorged tenure produced at most one globally accepted block, (3) the victim signer's `signerdb` has a record for that tenure's first block but no `approved_time` (plausible after a restart, temporary partition, or late signer onboarding). No majority-signer collusion, no compromise of the victim, and no auth_token is required — the attacker only needs to submit an ordinary tenure-change block proposal via the normal signer proposal/gossip path. This is directly reachable through `handle_block_proposal -> check_proposal -> validate_tenure_change_payload -> SortitionData::check_parent_tenure_choice`, matching the call sequence in the question.

### Recommendation
Do not substitute `0` when `approved_time` is missing. Either treat a missing `approved_time` the same as "no local knowledge" (fail closed, `Ok(false)`) as is already done when `get_first_approved_block_in_tenure` returns `None`, or fetch the true first-block timing from an authoritative source (e.g. the stacks-node's burn-block/tenure info) instead of defaulting to zero, so that the timing decision does not depend on which specific signer is evaluating it.

### Proof of Concept
In `stacks-signer/src/chainstate/tests`, add a test that:
1. Seeds `signer_db` with a `BlockInfo` for the reorged tenure's first block where `state` reflects "known/first-approved-lookup match" but `approved_time = None` (simulating a signer that has the block record from gossip but never locally pre-committed it).
2. Sets `sortition_state_received_time` (via `signer_db.insert_burn_block`/equivalent) to a time far exceeding `first_proposal_burn_block_timing` past any plausible real approval time.
3. Sets `globally_accepted_blocks <= 1` for that tenure via the relevant signerdb helper.
4. Calls `SortitionData::check_parent_tenure_choice` directly with these fixtures.
5. Asserts it returns `Ok(true)` (reorg permitted) even though, had `approved_time` been populated with a realistic early timestamp, `sortition_state_received_time - approved_time >= first_proposal_burn_block_timing` and the function would return `Ok(false)` — demonstrating the two branches diverge only because of the missing local timestamp, not real elapsed time.
