### Title
Unfunded instant-withdraw receipts are paid at par and skip the funded-claim gate, draining prefunded recovery before default finalization - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external report describes a policy middleware that exempts one request class (`OPTIONS`) from the authentication check applied to every other method, so requests that callers assume are policy-controlled pass straight through. The credit-vault analog is `IdleCreditVault.claimInstantWithdrawRequest`: normal withdraw claims are gated by epoch maturity and funding state, but instant claims burn the user's receipt and pay `_transferFundedClaim` unconditionally, with no check that the receipt was actually funded (`pendingInstantWithdraws`) and no exclusion of receipts the recovery system still counts as outstanding.

### Finding Description
Two claim paths exist in `IdleCreditVault`:

- `claimWithdrawRequest` routes through `_claimFundedWithdrawRequest`, which enforces one-epoch maturity (`epochNumber <= lastWithdrawRequest[_user]` reverts) and loss-adjusted/default recovery paths.
- `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`) only checks `_onlyIdleCDO`, burns `instantWithdrawsRequests[_user]`, and pays the full amount via `_transferFundedClaim`. It never consults `pendingInstantWithdraws` and does not clear `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`.

On the CDO side, `IdleCDOEpochVariant.claimInstantWithdrawRequest` (`IdleCDOEpochVariant.sol:975-979`) only gates on `allowInstantWithdraw`, which the default/emergency path explicitly sets to `true` (`IdleCDOEpochVariant.sol:220`). Meanwhile the default-recovery machinery assumes current-epoch instant receipts are still outstanding: `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` as already-held underlying (`IdleCreditVault.sol:716-723`), and `finalizeDefaultRecovery` adds that amount to `defaultRecoveryReserve` (`IdleCreditVault.sol:685-691`). `_transferFundedClaim` protects `defaultRecoveryReserve` (`IdleCreditVault.sol:899-905`), but the reserve is zero until finalization, so nothing stops the early claim.

Sequence:

1. Epoch N running; instant withdrawals enabled. Users A (attacker) and B each request instant withdraw of 100 via `requestWithdraw` → `requestInstantWithdraw` mints 100 receipt tokens to each, `pendingInstantWithdraws = 200`, `instantWithdrawClaimsByEpoch[N] = 200`.
2. The borrower returns only part of the instant-withdraw obligation before `instantWithdrawDeadline` (the code explicitly contemplates this: "borrower should return the difference before instantWithdrawDeadline", `IdleCDOEpochVariant.sol:231`). `collectInstantWithdrawFunds(100)` runs; the strategy holds 100 underlying, `pendingInstantWithdraws = 100`.
3. Borrower misses the deadline → `_handleBorrowerDefault` → `defaulted = true`, `allowInstantWithdraw = true`.
4. Before `finalizeDefaultRecovery` is called, A calls `IdleCDOEpochVariant.claimInstantWithdrawRequest()` → `claimInstantWithdrawRequest(A)` burns A's 100 receipt and transfers the strategy's entire 100 underlying to A at par.
5. Finalization: `prefundedReserve = instantWithdrawClaimsByEpoch[N] (200) - pendingInstantWithdraws (100) = 100` is counted into `defaultRecoveryReserve` even though the strategy now holds 0. With zero external recovery, `recoveryPrice = 100 * 1e18 / totalBasis` (where totalBasis still includes A's already-paid 100 claim).
6. B calls `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest(B)` pays `100 * recoveryPrice / 1e18`, decrementing `defaultRecoveryReserve`, then `safeTransfer` reverts because the vault holds nothing. B's claim is permanently frozen; A captured B's pro-rata share.

Note also that a second call by A post-finalization underflows at `instantWithdrawsRequests[_user] -= claimBasis` in `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:848`), confirming the accounting assumes pre-finalization par claims cannot happen.

### Impact Explanation
Direct theft plus permanent freezing of unclaimed yield: the attacker receives 100% of their unfunded receipt while honest claimants with identical receipts get ~50% diluted recovery price on a reserve that no longer exists — their claims revert permanently on the zero vault balance. The broken invariant is one-receipt-one-pro-rata-payout / loss socialization: instant receipts bypass the funded-status check that every other claim class enforces, exactly as `OPTIONS` bypassed the policy check every other method enforced.

### Likelihood Explanation
Requires (a) instant withdrawals enabled and triggered by an APR drop, (b) partial borrower funding of the instant queue before `instantWithdrawDeadline` — an explicitly designed-for state — and (c) a default with finalization not yet executed, which always has a nonzero window since `finalizeDefaultRecovery` is a separate manager/owner transaction. Any tranche holder with an instant receipt can front-run finalization; no privileged role is needed.

### Recommendation
In `IdleCreditVault.claimInstantWithdrawRequest`, treat the unfunded portion as non-claimable: only pay `min(instantWithdrawsRequests[_user], fundedPortion)` or revert while `defaulted` is set and `defaultInstantWithdrawsFinalized` is false. Equivalently, gate `IdleCDOEpochVariant.claimInstantWithdrawRequest` on `!defaulted || defaultInstantWithdrawsFinalized` so pre-finalization par payouts cannot drain the prefunded reserve. Also clear `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` when receipts are claimed so recovery basis stays consistent.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Assume epoch N running, instant withdraw enabled (lastEpochApr > unscaledApr + delta).
// A (attacker) and B each hold 100e18 tranche tokens worth 100e6 underlying.

// 1. Both request instant withdraw during buffer (APR dropped)
cdoEpoch.requestWithdraw(100e18, address(AAtranche)); // as A
cdoEpoch.requestWithdraw(100e18, address(AAtranche)); // as B
// vault: instantWithdrawsRequests[A] = instantWithdrawsRequests[B] = 100e6
// pendingInstantWithdraws = 200e6, instantWithdrawClaimsByEpoch[N] = 200e6

// 2. Epoch starts; borrower funds only half the instant queue
_startEpochAndCheckPrices(0);
// borrower sends 100e6; CDO calls collectInstantWithdrawFunds(100e6)
// strategy balance = 100e6, pendingInstantWithdraws = 100e6

// 3. Borrower misses instantWithdrawDeadline -> default
vm.warp(instantWithdrawDeadline + 1);
cdoEpoch.defaultEpoch(); // or _handleBorrowerDefault path: defaulted = true, allowInstantWithdraw = true

// 4. Attacker claims BEFORE finalizeDefaultRecovery
uint256 balPre = underlying.balanceOf(A);
vm.prank(A);
cdoEpoch.claimInstantWithdrawRequest();
assertEq(underlying.balanceOf(A) - balPre, 100e6); // paid at par from prefunded reserve

// 5. Finalize recovery with zero external recovery
finalizeDefaultRecovery(0, address(0));
// defaultRecoveryReserve = 100 (prefundedReserve) but strategy balance = 0

// 6. Victim claim permanently reverts / pays nothing
vm.prank(B);
vm.expectRevert(); // safeTransfer of 0 balance
cdoEpoch.claimInstantWithdrawRequest();
```

Caveat: I could not fully verify within this iteration whether `collectInstantWithdrawFunds` is invoked with a strictly smaller amount than `pendingInstantWithdraws` in the current start-epoch flow; the code comments and `_defaultPrefundedInstantReserve` confirm the partially-funded state is an intended configuration, but the PoC should confirm the exact funding call sequence on fork.
