### Title
`getContractValue()` counts raw donated underlyings that `virtualPrice()`/`_managedContractValue()` excludes, so `_updateAccounting` books skimmed donations as NAV and inflates tranche prices — ([File: contracts/IdleCDOCreditVault.sol](https://github.com/EzraCole/idle-tranches--025/blob/main/contracts/IdleCDOCreditVault.sol))

### Summary
The credit vault has two different "total assets" formulas, directly mirroring the external `totalAssets()` vs `_strategyController.totalValue()` bug:

- `getContractValue()` = `strategyToken.balanceOf(this) + token.balanceOf(this) - unclaimedFees` — includes raw underlying sitting in the contract.
- `_managedContractValue()` = `strategyToken.balanceOf(this) - unclaimedFees` — explicitly excludes raw underlyings because "unsolicited transfers are skimmed on interactions".

The deposit/withdraw accounting path (`_updateAccounting`) uses `getContractValue()`, while the public fair-price getter `virtualPrice()` (and the management-fee base `_accrueManagementFee`) uses `_managedContractValue()`. An unprivileged direct token sender can therefore inject a phantom "gain" into tranche NAV and prices.

### Finding Description
In `IdleCDOCreditVault`:

```solidity
function getContractValue() public override view returns (uint256) {
    return _contractTokenBalance(strategyToken) + _contractTokenBalance(token) - unclaimedFees;
}

function _managedContractValue() internal view returns (uint256) {
    uint256 strategyTokenBalance = _contractTokenBalance(strategyToken);
    uint256 fees = unclaimedFees;
    return strategyTokenBalance > fees ? strategyTokenBalance - fees : 0;
}
```

`_updateAccounting()` calls `nav = getContractValue()`, so any raw `token` balance is treated as yield:

```solidity
uint256 nav = getContractValue();
if (nav > _lastNAV) {
    unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
}
```

The donated amount `D` then flows into `_virtualPriceAux` as `totalGain`, raising `priceAA`/`priceBB` and `lastNAVAA`/`lastNAVBB` by ~`D` minus fee. However, `virtualPrice()` — the price used by `TrancheWrapper.convertToShares`/`previewDeposit`/`previewWithdraw` — is computed on `_managedContractValue()`, which excludes `D`, and the raw underlyings are designated for skimming rather than backing NAV.

The invariant broken: booked NAV (`lastNAVAA + lastNAVBB` and the tranche prices redeemers are paid at) can exceed the assets actually retained by the vault once the raw underlyings are skimmed.

### Impact Explanation
An unprivileged attacker donates `D` underlying tokens directly to the vault. On the next honest depositor/withdrawer interaction, `_updateAccounting` books `D` as profit: `unclaimedFees` grows by `D * fee / FULL_ALLOC` and `lastNAV`/tranche prices grow by the remainder. When the raw `D` is subsequently skimmed out per the donation-isolation design, the vault's liabilities (`lastNAVAA + lastNAVBB`) permanently exceed its backing (`strategyToken` balance). Result: `priceAA`/`priceBB` are inflated and the last redeemers cannot be paid in full — insolvency of up to `D` (less the fee share) borne by remaining tranche holders. This is the same class as the external report: two different totals for "assets", with the mutating path using the inflated one.

### Likelihood Explanation
Requires only an ERC-20 `transfer` to the vault address (explicitly an allowed attacker action — "direct token sender") followed by an ordinary user deposit/withdraw to trigger `_updateAccounting`, and a subsequent skim of the raw balance. No privileged cooperation is needed. The magnitude of the theft/insolvency is bounded by the donation size `D`, so economic viability depends on `D` being material relative to vault TVL; for a low-TVL vault or a flash-loaned donation this is cheap to stage. Uncertainty: the exact skim destination/ordering lives in `IdleCDOEpochVariant`/`_skimDonatedAssets`, which I could not fully verify in this session; if skimmed funds are routed into the strategy (becoming `strategyToken` balance) rather than out of the vault, the insolvency does not materialize and the issue degrades to a preview-vs-execution price mismatch (users mint fewer shares than `virtualPrice`-based `previewDeposit` indicates, an ERC-4626 violation but weaker fund impact).

### Recommendation
Make the accounting path use the same total as the valuation path — i.e., have `_updateAccounting()` compute `nav` from `_managedContractValue()` (or remove the raw `token` balance from `getContractValue()`), so donations can never be booked as tranche NAV or fees before skimming. Alternatively, perform `_skimDonatedAssets` strictly before `_updateAccounting` inside `_deposit`/withdraw so `getContractValue()` never observes unsolicited funds.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOCreditVault} from "../contracts/IdleCDOCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract DonatedNAVInflationTest is Test {
    IdleCDOCreditVault vault; // deployed credit vault instance
    IERC20Detailed token;     // vault underlying
    address attacker = makeAddr("attacker");
    address alice    = makeAddr("alice"); // honest AA holder

    function test_donationInflatesNAVAndInsolventRedeem() public {
        uint256 D = 100e18;

        // 1. Alice already holds AA tranches; vault is running normally.
        // 2. Unprivileged attacker donates raw underlying to the vault.
        deal(address(token), attacker, D);
        vm.prank(attacker);
        token.transfer(address(vault), D);

        // 3. virtualPrice() is unchanged (uses _managedContractValue),
        //    but getContractValue() jumps by D.
        uint256 navBefore = vault.lastNAVAA() + vault.lastNAVBB();

        // 4. Any honest interaction triggers _updateAccounting -> books D as gain.
        vm.prank(alice);
        vault.depositAA(1e18); // or a withdraw

        uint256 navAfter = vault.lastNAVAA() + vault.lastNAVBB();
        assertGt(navAfter, navBefore); // D - fee booked into tranche NAV

        // 5. Raw D is skimmed (donation isolation). NAV is now unbacked:
        //    lastNAVAA+lastNAVBB > strategyToken balance backing it.
        //    Final redeemers cannot be paid -> insolvency of ~D.
    }
}
```
