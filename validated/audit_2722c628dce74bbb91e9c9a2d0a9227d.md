### Title
Rate-limit token consumed before shard-assignment validation, allowing wasted-quota resource exhaustion for unassigned workflows - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
In `HandleUserTriggerRequest`, `checkRateLimit` consumes a `userRateLimiter` token immediately after `authorizeRequest` succeeds, but `authorizeRequest` only validates the signer against `authorizedKeys` — it does not confirm the workflow is assigned to any shard. The shard-assignment check happens later in `setupCallback`, so an authorized signer for a workflow with no shard assignment can burn rate-limit quota on requests that are guaranteed to fail.

### Finding Description
The request pipeline in `HandleUserTriggerRequest` runs, in order: `resolveWorkflowID` → `authorizeRequest` → `checkRateLimit` → `setupCallback` → `sendWithRetries`. [1](#0-0) 

`authorizeRequest` only calls `h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)`, which validates the caller's signature/key against the workflow's authorized keys — there is no check of shard assignment here. [2](#0-1) 

`checkRateLimit` only fails if `GetWorkflowReference` cannot find the workflow reference; if found, it immediately calls `h.userRateLimiter.AllowErr(ctx)`, consuming a token, regardless of whether the workflow has any shard assigned. [3](#0-2) 

Only later, in `setupCallback`, is `h.workflowMetadataHandler.WorkflowShards(workflowID)` checked; if empty, the request fails with "Workflow %s is not assigned to any DONs" — but by this point the rate-limit token has already been spent. [4](#0-3) 

Notably, the comment at line 410 ("this shouldn't happen because we checked it in authorizeRequest()") does not match the actual code — `authorizeRequest` (lines 361-369) does not perform any shard-assignment check, confirming this is an actual ordering/validation gap rather than defense-in-depth.

### Impact Explanation
An authorized signer for a workflow that is registered but not yet (or no longer) assigned to any shard can repeatedly call `HandleUserTriggerRequest`, each time consuming one `userRateLimiter` token per the `settings.ScopeWorkflow` scope keyed on `{Owner, Workflow}`, while every request is guaranteed to fail at `setupCallback`. This depletes the workflow's legitimate execution quota, so real trigger requests for the same workflow (once it becomes properly assigned) get throttled with "rate limit exceeded". This is a quota/allowlist-exactness violation — a low-severity resource-exhaustion/self-DoS issue, escalatable if an attacker (e.g., holder of a leaked/older but still-valid signed JWT/auth key for that workflow) intentionally floods requests against a victim workflow owner's quota before or during shard reassignment.

### Likelihood Explanation
Preconditions are narrow but realistic: the attacker must possess valid authorization for the specific workflow (an "authorized key" recognized by `Authorize`), and the workflow must currently have zero shard assignments (a normal transient state right after registration, during migration, or during shard rebalancing). Given those preconditions, the exploit is trivial and fully repeatable — simply resend `workflows.execute` JSON-RPC requests with unique `id`s; each one burns a token and fails deterministically at `setupCallback`.

### Recommendation
Reorder the validation so that shard-assignment is checked before the rate limiter is consumed, e.g., move the `WorkflowShards` emptiness check (currently in `setupCallback`) into `authorizeRequest` or immediately before `checkRateLimit`. Alternatively, restructure `checkRateLimit` to first confirm `len(h.workflowMetadataHandler.WorkflowShards(workflowID)) > 0` and return the "not assigned to any DONs" error prior to calling `h.userRateLimiter.AllowErr(ctx)`.

### Proof of Concept
Go unit test plan in `http_trigger_handler_test.go`:
1. Construct a `httpTriggerHandler` with a `workflowMetadataHandler` where the target `workflowID` has a valid `authorizedKeys` entry (so `Authorize` succeeds) and a `GetWorkflowReference` entry (so `checkRateLimit`'s lookup succeeds), but `WorkflowShards(workflowID)` returns an empty slice.
2. Use a real or spy `limits.RateLimiter` (e.g., a counting wrapper around `AllowErr`) to track token consumption calls for the workflow's `{Owner, Workflow}` scope.
3. Call `HandleUserTriggerRequest` N times with unique request IDs for this unassigned workflow.
4. Assert:
   - Each call ultimately returns an error consistent with `"workflow %s not assigned to any shard"` / the `setupCallback` failure path.
   - The rate limiter's `AllowErr` was invoked N times (i.e., N tokens consumed) despite zero successful dispatches — demonstrating that failed-to-dispatch requests do count against quota.
   - After N calls exceed the configured workflow rate limit, a subsequent call with the workflow properly assigned to a shard is now rejected with `jsonrpc.ErrLimitExceeded` ("rate limit exceeded"), proving legitimate requests are throttled by the wasted tokens.

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	// TODO orgID https://smartcontract-it.atlassian.net/browse/CRE-1707
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}
