### Title
Unbounded, ever-growing per-notification cost in `blockSubscribe` when a `mentionsAccountOrProgram` filter never matches — cursor never advances - (File: `rpc/src/rpc_subscriptions.rs`)

### Summary
The reported bug class is a cursor/pointer that is supposed to advance after each processed unit of work, but is left un-advanced when the current unit is "empty" (deleted/no-op), causing the same stale starting point to be re-scanned on every subsequent operation forever. The same pattern exists in the `Block` subscription branch of `RpcSubscriptions::notify_watchers`, where the per-subscription cursor `last_notified_slot` (aliased `w_last_unnotified_slot`) is only advanced when a block update is produced (`Some`) but is left untouched whenever the configured filter matches nothing in a slot (`Ok(None)`), unlike Account/Logs/Program/Signature subscriptions, which use `check_commitment_and_notify`/`filter_*` helpers that always update the cursor regardless of match.

### Finding Description
In `RpcSubscriptions::notify_watchers` [1](#0-0) , for `SubscriptionParams::Block(params)` the code recomputes the entire range of not-yet-notified slots on every invocation:

```rust
let mut w_last_unnotified_slot = subscription.last_notified_slot.write().unwrap();
if *w_last_unnotified_slot == 0 {
    *w_last_unnotified_slot = slot;
}
let mut slots_to_notify: Vec<_> = (*w_last_unnotified_slot..slot).collect();
let ancestors = bank.proper_ancestors_set();
slots_to_notify.retain(|slot| ancestors.contains(slot));
slots_to_notify.push(slot);
for s in slots_to_notify {
    ...
    let block_update_result = blockstore
        .get_complete_block(s, false)
        ...
        .and_then(|block| filter_block_result_txs(block, s, params));
    match block_update_result {
        Ok(block_update) => {
            if let Some(block_update) = block_update {
                notifier.notify(...);
                *w_last_unnotified_slot = s + 1;   // <-- only advances here
            }
        }
        Err(err) => { /* intentionally does not advance, for retry */ }
    }
}
``` [2](#0-1) 

`filter_block_result_txs` returns `Ok(None)` — not an error — whenever the subscription is `BlockSubscriptionKind::MentionsAccountOrProgram(pk)` and no transaction in the block touches `pk`:
```rust
if block.transactions.is_empty()
    && let BlockSubscriptionKind::MentionsAccountOrProgram(_) = params.kind
{
    return Ok(None);
}
``` [3](#0-2) 

Because the `Ok(None)` case is handled by neither branch of the `match` above, `*w_last_unnotified_slot` is never updated. This is exactly the queue-head-deletion bug class from the report: the "processed" outcome (a legitimately filtered/empty result) is conflated with "not yet processed", and the cursor that should move forward on every processed unit stays pinned at its original position indefinitely.

`notify_watchers` is invoked repeatedly for every gossip/vote/slot-confirmation event for the lifetime of the subscription [4](#0-3) . Each call recomputes `(*w_last_unnotified_slot..slot).collect()` and then does an `O(n)` `retain`, where `n = slot - w_last_unnotified_slot`. If the pubkey/program the client subscribed to simply never appears in a produced block (a completely ordinary, easily arranged condition — e.g., subscribing to a pubkey that hasn't transacted yet), `w_last_unnotified_slot` is stuck at the subscription's initial slot forever, so `n` grows by one every slot and the per-call cost grows linearly with wall-clock time since subscription — i.e. cumulative CPU/memory cost is quadratic over the life of a single, unprivileged `blockSubscribe` call, with zero additional requests from the client.

### Impact Explanation
A single unprivileged `blockSubscribe` call with `mentionsAccountOrProgram` filtering on an address that produces no matching transactions causes the RPC/pubsub notification thread to do unboundedly growing work (vector allocation + linear scan) on every subsequent slot notification for as long as the subscription is held open, with no further action required from the client. This is a self-inflicted, unbounded-cost condition triggered by one low-rate call, matching the accepted impact class "unbounded cost for a single low-rate call." It degrades the `notify_watchers` thread (shared across all pubsub subscriptions, called via `par_iter`), risking delayed or dropped notifications for other subscribers as well.

### Likelihood Explanation
Likelihood is moderate-to-high in environments where block subscriptions are enabled (`blockSubscribe` requires the operator to run with `--rpc-pubsub-enable-block-subscription`, see `validator/src/commands/run/args/pub_sub_config.rs` and gating in `rpc/src/rpc_pubsub_service.rs`/`rpc_pubsub.rs`). Once that feature flag is on — which is a normal (if less common) production configuration, not a privileged/operator-only action performed by the attacker — any ordinary JSON-RPC/pubsub client can open a `blockSubscribe` with a `mentionsAccountOrProgram` filter for an inactive address and trigger the unbounded growth purely by waiting; no further requests, no elevated privileges, and no client-side polling rate above the normal per-slot notification cadence are required.

### Recommendation
In the `Block` subscription branch of `notify_watchers`, treat `Ok(None)` the same as a successfully-processed (but filtered-out) slot: advance `*w_last_unnotified_slot = s + 1` whenever `block_update_result` is `Ok(_)` (regardless of `Some`/`None`), and only withhold the advance on the genuine `Err` path (as is already done, intentionally, for retryable errors). This mirrors the audited fix pattern from the report ("increment the counter if it's processed, and `continue` instead of `break`") — i.e. distinguish "processed, nothing to report" from "not processed, must retry," and only skip advancing the cursor in the latter case.

### Proof of Concept
Not independently executed (index-only analysis); the following reproduces the logical flaw purely by code inspection:
1. Run a validator with `--rpc-pubsub-enable-block-subscription`.
2. As an unprivileged client, call `blockSubscribe` with `{"mentionsAccountOrProgram": "<some pubkey that never appears in any block>"}`.
3. Observe (via added instrumentation/logging, or profiling) that on every subsequent `notify_watchers` invocation (roughly once per slot), the block branch computes `slots_to_notify = (*w_last_unnotified_slot..slot).collect()` with `w_last_unnotified_slot` never advancing past its initial value, per `filter_block_result_txs` returning `Ok(None)` at [3](#0-2)  and the `match` at [5](#0-4)  not advancing the cursor on the `Some(...)`-absent case. The size of `slots_to_notify` (and thus CPU work per call) grows by one every slot indefinitely, with no further client interaction, confirming the unbounded-cost condition.

Uncertainty: I could not execute a live validator/pubsub session to directly measure CPU/latency growth or to confirm end-to-end whether `bank.proper_ancestors_set()` bounds the *notified* results (it does bound eventual matches, but not the per-call `Vec` allocation/`retain` cost against the unbounded range) — this analysis relies on static code reading of `rpc/src/rpc_subscriptions.rs`. I also could not verify from the index whether any newer, unindexed code paths (outside the size limits of this index) already special-case `Ok(None)`; a live Devin session with full repository access would be needed to confirm current behavior and validate a fix.
