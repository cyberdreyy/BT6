### Title
`requestWithdraw` does not check the pause flag, so lenders can exit at pre-loss prices while the vault is paused - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The pause mechanism in `IdleCDOCreditVault`/`IdleCDOEpochVariant` is enforced inconsistently. Deposits are blocked through `whenNotPaused` on `_deposit`, and emergency paths (`_emergencyShutdown`, `_handleBorrowerDefault`) additionally clear the `allowAAWithdrawRequest`/`allowBBWithdrawRequest` flags. However, a plain guardian/owner `pause()` only sets the Pausable flag — it does not touch the withdraw-request flags — and `requestWithdraw` itself has no `whenNotPaused` modifier and never checks `paused()`. A lender can therefore submit a withdrawal request during a pause, burning tranche tokens at the stale (pre-loss) price and converting them into a fixed principal-plus-interest receipt that is paid ahead of remaining holders at the next `stopEpoch`. This is the same bug class as the Illuminate report: a redemption path bypasses the pause check, letting early redeemers escape a pending loss and socialize it onto everyone else.

### Finding Description
- `_deposit` (and thus `depositAA`/`depositBB`) is the only user entry point guarded by `whenNotPaused`: `contracts/IdleCDOEpochVariant.sol:644` and `contracts/IdleCDOCreditVault.sol:191`.
- `pause()`/`unpause()` in `IdleCDOCreditVault` only call `_pause()`/`_unpause()`; they do not modify `allowAAWithdrawRequest` or `allowBBWithdrawRequest` (`contracts/IdleCDOCreditVault.sol:518-529`). Only `_emergencyShutdown` and `_handleBorrowerDefault` clear those flags (`contracts/IdleCDOEpochVariant.sol:602-615`, `587-596`).
- `requestWithdraw` gates solely on the allow flags and KYC (`_checkNotAllowed((_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) || !isWalletAllowed(msg.sender))`) — there is no `paused()` check (`contracts/IdleCDOEpochVariant.sol:739-744`).
- Inside `requestWithdraw`, `_updateAccounting()` runs but only reverts `Default()` when a loss already visible in NAV fully wipes BB or the whole vault (`contracts/IdleCDOCreditVault.sol:240-246`). Any loss not yet reflected in `getContractValue()` — e.g., borrower distress known off-chain but not yet pushed on-chain, which is precisely the scenario a guardian `pause()` exists for — leaves prices stale, so `_trancheToUnderlyings` and `_calcInterestWithdrawRequest` value the request at the pre-loss `priceAA`/`priceBB` (`contracts/IdleCDOEpochVariant.sol:756, 773-776`).
- The request mints a fixed receipt in `IdleCreditVault` (`creditVault.requestWithdraw(_underlyings, msg.sender, principal)`, line 788) sized as `principal + interest - fees`, and burns the tranche tokens via `_withdrawOps`. When the epoch later stops, `stopEpoch` pulls `pendingWithdraws` from the borrower and `collectWithdrawFunds` reserves that cash for receipts (lines 393, 408-410) — the paused-period escapee is paid in full while any subsequently crystallized loss falls entirely on remaining tranche holders.

### Impact Explanation
Direct loss socialization: while the vault is paused to investigate a pending insolvency, a KYC-passed lender can still file a withdraw request that locks in `principal + projected epoch interest` at stale prices. If the feared loss materializes afterward (via `stopEpochWithDuration(_lossAmount)` or `finalizeDefault`), the escapee's receipt is already a fixed liability funded before active NAV, so the entire loss is borne by lenders who respected the pause. Loss magnitude is bounded by the requester's full NAV share at stale price — for a BB holder the whole `lastNAVBB` principal plus interest, and it directly reduces the recovery multiplier/NAV left for everyone else.

### Likelihood Explanation
Medium. Requires only (a) a guardian/owner `pause()` during a buffer period (not a full `emergencyShutdown`, which does clear the flags), and (b) an unprivileged but KYC-passed lender holding tranche tokens. Pausing without emergency shutdown is a plausible operational first response to suspected borrower trouble, and `setInstantWithdrawParams` explicitly treats `paused()` as a distinct state from the shutdown flags (`_checkNotAllowed(paused())`, line 133), confirming `pause()` alone is a supported intermediate state.

### Recommendation
Add `paused()` to the `_checkNotAllowed` condition in `requestWithdraw` (or apply `whenNotPaused`), so that a guardian pause freezes withdrawal requests symmetrically with deposits. For defense in depth, `pause()` in the epoch variant could also clear `allowAAWithdrawRequest`/`allowBBWithdrawRequest`, with `unpause()`/`restoreOperations` re-enabling them.

### Proof of Concept
Foundry fork PoC (schematic, against `IdleCDOEpochVariant` + `IdleCreditVault` strategy):

```solidity
function test_requestWithdraw_bypasses_pause() public {
    // Setup: buffer period, allowAAWithdrawRequest/allowBBWithdrawRequest == true.
    // lender (KYC-passed) holds AA tranche tokens.
    vm.prank(guardian);
    cdo.pause();                       // only sets paused(), flags untouched
    assertTrue(cdo.paused());

    uint256 navBefore = cdo.getContractValue();
    vm.prank(lender);
    cdo.requestWithdraw(0, AATranche); // succeeds despite pause -> receipt minted

    assertEq(IdleCDOTranche(AATranche).balanceOf(lender), 0);
    assertGt(IdleCreditVault(strategy).pendingWithdraws(), 0);
    // next stopEpoch pays lender principal+interest in full;
    // loss applied afterward hits remaining holders only.
}
```

Uncertainty note: I did not open `IdleCreditVault.sol` itself, so the claim path (`claimWithdrawRequest`) is asserted only from the CDO-side forwarding at `contracts/IdleCDOEpochVariant.sol:967-971` and the funding logic in `_stopEpoch`; the receipt is assumed to be a fixed liability as documented in the code comments. The core inconsistency (missing `paused()` check in `requestWithdraw`) is directly verifiable in the cited code.
