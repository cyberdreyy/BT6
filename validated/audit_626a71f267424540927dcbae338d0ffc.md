### Title
Confidential-transfer `Withdraw`/`Transfer` jsonParsed decoder mislabels owner/context accounts due to offset-heuristic and `saturating_sub(1)` boundary logic - (File: transaction-status/src/parse_token/extension/confidential_transfer.rs)

### Summary
`parse_confidential_transfer_instruction`'s `Withdraw`, `Transfer`, and `TransferWithFee` branches infer which optional accounts (`instructionsSysvar`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`, `ciphertextValidityProofContextStateAccount`, `feeSigmaProofContextStateAccount`, etc.) are present purely from the attacker-controlled `*_proof_instruction_offset` fields decoded from raw instruction data and from an `account_indexes.len().saturating_sub(1)` boundary check, rather than validating that the account list actually matches the declared proof-location scheme. Because `decode_instruction_data` does not cross-check the offset fields against the true account list contents, a transaction author can submit an inconsistent Withdraw/Transfer instruction that causes the parser to attribute the wrong account to `owner`/`multisigOwner`/`instructionsSysvar`/`*ContextStateAccount` fields in the `jsonParsed` RPC output.

### Finding Description
The Withdraw branch (and similarly Transfer/TransferWithFee) at [1](#0-0)  reads `equality_proof_instruction_offset` and `range_proof_instruction_offset` straight out of the raw instruction data via `decode_instruction_data`, computes `has_sysvar` from whether either offset is non-zero, and then walks a running `offset` cursor over `account_indexes`, inserting `instructionsSysvar`/`equalityProofContextStateAccount`/`rangeProofContextStateAccount` fields conditionally, guarded only by `offset < account_indexes.len().saturating_sub(1)`.

This bound is meant to always reserve the final slot(s) for the `owner`/multisig signer(s) consumed later by `parse_signers` at [2](#0-1) , but nothing enforces that the real account list produced for a given offset combination actually has the expected length. `check_num_token_accounts(account_indexes, 4)` only enforces a *minimum* of 4 accounts [3](#0-2) ; it does not validate that the count matches what the declared offsets imply.

Because the raw instruction bytes are fully attacker-controlled (the SPL-Token-2022 program id can receive any well-formed instruction bytes/account list from an unprivileged client, and this is later surfaced through `jsonParsed`), an attacker can set `equality_proof_instruction_offset`/`range_proof_instruction_offset` to values inconsistent with the account list actually supplied (e.g., declare `offset != 0` — implying "proof bundled in instruction, sysvar account present" — while omitting the sysvar account, or vice versa; or pad/truncate the account list right at the `saturating_sub(1)` boundary). This shifts the `offset` cursor so that:
- A real "owner"/authority account gets labeled as `equalityProofContextStateAccount` or `instructionsSysvar` (or the reverse: the actual sysvar/context account gets labeled `owner`/`multisigOwner`), because `parse_signers` will pick whatever account_indexes remain at the (miscalculated) `offset`.

The existing unit tests in this file (`test_withdraw`, `test_configure`, `test_empty_account`) only test proof-location/account-count combinations produced by the legitimate `inner_withdraw`/`inner_configure_account`/`inner_empty_account` builders [4](#0-3) , which always keep offsets and account lists internally consistent. They do not cover instructions built directly from raw bytes with an inconsistent offset/account-count combination, which is exactly what an unprivileged attacker can submit.

### Impact Explanation
This is a decoder misreporting bug: the `jsonParsed` transaction encoding for a `withdrawConfidentialTransfer`/`confidentialTransfer`/`confidentialTransferWithFee` instruction can report an incorrect pubkey under `owner`, `multisigOwner`, `instructionsSysvar`, or one of the `*ProofContextStateAccount` fields. This falls under the "decoder panic and misreporting" accepted impact category — no crash or consensus mutation occurs, but RPC consumers relying on `jsonParsed` (wallets, explorers, auditing tools) can be misled about which account is the true authority/signer versus which is a context/sysvar account for a confidential-transfer operation. There is no out-of-bounds indexing risk here because `account_indexes` values are bounded by the enclosing transaction's account-key list (enforced upstream during transaction deserialization/message compilation), so this is scoped strictly to field-mislabeling, not memory safety.

### Likelihood Explanation
Fully reachable by an unprivileged client: craft raw `Withdraw`/`Transfer`/`TransferWithFee` instruction bytes for the SPL-Token-2022 program id with `*_proof_instruction_offset` fields set independently of the actual account list length/order, submit it in a transaction (it can even fail on-chain execution — the transaction still lands in the ledger and is retrievable via `jsonParsed`), then request it via `getTransaction`/`getConfirmedTransaction`. No special privileges, keys, or validator control are required, and the bug is deterministic/reproducible for any chosen offset/account-count combination near the `saturating_sub(1)` boundary.

### Recommendation
Do not infer account roles solely from proof-offset flags and length heuristics. Instead, either (a) derive the account layout deterministically from the exact number of accounts and offsets using the same validated logic the token-2022 program itself uses to interpret `ProofLocation` (mirroring `spl_token_confidential_transfer_proof_extraction`), rejecting/falling back to `InstructionNotParsable`/omitting fields when the account count does not exactly match what the offsets imply, rather than silently shifting the cursor; or (b) tighten `check_num_token_accounts` per-branch to require the exact expected count for each offset combination before attempting field extraction, returning a parse error instead of guessing when the count is ambiguous.

```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (test mod)
#[test]
fn test_withdraw_inconsistent_offsets_mislabel() {
    use spl_token_2022_interface::extension::confidential_transfer::instruction::WithdrawInstructionData;

    // Build raw instruction data claiming BOTH proofs are instruction-offset based
    // (equality_proof_instruction_offset != 0, range_proof_instruction_offset != 0)
    // implying an `instructionsSysvar` account should be present and NO
    // equality/range context-state accounts, i.e. minimal account list.
    let mut data = vec![/* discriminator for Withdraw */ 5u8];
    let withdraw_data = WithdrawInstructionData {
        equality_proof_instruction_offset: 1,
        range_proof_instruction_offset: 1,
        ..Zeroable::zeroed()
    };
    data.extend_from_slice(bytemuck::bytes_of(&withdraw_data));

    // Account list: [account, mint, REAL_OWNER, decoy_account]
    // len()=4 -> saturating_sub(1)=3, offset starts at 2 -> has_sysvar guard
    // (2 < 3) is true, so index 2 (REAL_OWNER) is mislabeled as "instructionsSysvar"
    // instead of remaining available for parse_signers as "owner".
    let account_keys = vec![
        Pubkey::new_unique(), // account
        Pubkey::new_unique(), // mint
        real_owner_key,       // intended true owner/signer
        Pubkey::new_unique(), // decoy
    ];
    let account_indexes: Vec<u8> = (0..4).collect();

    let parsed = parse_confidential_transfer_instruction(
        &data,
        &account_indexes,
        &AccountKeys::new(&account_keys, None),
    )
    .unwrap();

    // Ground truth: real_owner_key should appear as "owner".
    // Bug: heuristic instead labels it "instructionsSysvar", and "owner"
    // ends up bound to the decoy account or is missing/wrong.
    assert_eq!(
        parsed.info["owner"],
        json!(real_owner_key.to_string()),
        "owner field mislabeled due to offset/account-count heuristic"
    );
}
```
Expected result on the current implementation: the assertion fails, demonstrating that `owner` is bound to the wrong pubkey (or `instructionsSysvar` incorrectly claims the real owner account) — confirming the misreporting. A fixed implementation should either produce the correct mapping deterministically or return `ParseInstructionError::InstructionNotParsable`/omit ambiguous fields rather than mislabel them.
