### Title
`jsonParsed`-encoded batch account queries silently drop accounts that fail to parse, returning incomplete results with no error indication - (File: `rpc/src/parsed_token_accounts.rs`)

### Summary
`getProgramAccounts`, `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`, and `programSubscribe` (with `jsonParsed` encoding against the token program) can silently omit legitimate accounts from their results whenever the SPL-Token/Token-2022 account or its mint fails to parse, instead of returning the account with a raw encoding fallback (as the single-account `getAccountInfo`/`getMultipleAccounts` path does) or surfacing an error.

### Finding Description
`get_parsed_token_accounts` in `rpc/src/parsed_token_accounts.rs` uses `filter_map` over the keyed accounts list. For each account it calls `encode_ui_account` with `UiAccountEncoding::JsonParsed`, and only keeps the account if the result is `UiAccountData::Json(_)`; if parsing fails (e.g. the mint account can't be found/unpacked via `get_mint_owner_and_additional_data`/`get_additional_mint_data`, or `parse_token_v3` fails on the account data), the closure returns `None` and the account is dropped entirely from the response: [1](#0-0) 

This is a different failure mode than the single-account path used by `get_account_info`/`get_multiple_accounts`, where `encode_ui_account`'s `JsonParsed` arm falls back to raw `Base64` binary data when parsing fails, so the account is still returned to the caller: [2](#0-1) 

`get_parsed_token_accounts` is the shared helper used by three unprivileged RPC methods and one pubsub subscription path: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The existing test suite documents this behavior for `getTokenAccountsByOwner` and `getProgramAccounts` explicitly ("doesn't return accounts with invalid mints"), confirming the code path is reachable and produces fewer results than the raw-encoding query for the exact same filter: [7](#0-6) 

### Impact Explanation
An unprivileged caller (any RPC/websocket client, no special role required) querying `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` with `encoding: "jsonParsed"`, or a `programSubscribe` subscriber with `jsonParsed` encoding on the token program, receives a response that is silently incomplete: existing accounts owned by the token program that match the requested filters are missing from the array with no null placeholder, no error, and no count/flag indicating truncation. Consumers such as wallets, exchanges, or indexing services that rely on this call to enumerate token holdings can under-report balances/holdings or miss newly created accounts entirely — functionally the same "leaked/unaccounted-for value" class as the referenced report, except here it manifests as account-decoding misreporting rather than an unrefunded ERC-20 transfer. This matches the accepted category of "decoder panic and misreporting" from account decoding paths.

### Likelihood Explanation
The condition triggers whenever any SPL token account's mint cannot be found or unpacked (e.g., mint account not yet in the confirmed bank state visible to this query, a corrupted/incompatible mint layout, or a token-2022 extension combination `StateWithExtensions::<Mint>::unpack` rejects), which is plausible in ordinary operation (e.g. mint creation racing with account creation, or third-party/non-standard mint-owner programs using overlapping account layouts). No adversarial crafting by the caller is required — the caller simply issues a standard `jsonParsed` request and gets a truncated list.

### Recommendation
Make `get_parsed_token_accounts` consistent with `encode_ui_account`'s single-account behavior: on parse failure, fall back to the raw (`Base64`) encoding for that account instead of dropping it, so record counts returned by `jsonParsed` queries always match the raw-encoding equivalent for the same filter set. Alternatively, if omission is intentional for API-simplicity reasons, document it clearly in the RPC spec and consider adding a warning/count field so callers can detect truncation.

### Proof of Concept
1. Store a valid SPL Token account (owner = token program, valid layout) whose `mint` field points to a pubkey that either does not exist in the bank or does not unpack as a valid `Mint` (e.g., an account with wrong data length/owner).
2. Call `getProgramAccounts` (or `getTokenAccountsByOwner`) for the token program with `{"encoding": "jsonParsed"}` — the account is absent from the result array.
3. Repeat the same call with `{"encoding": "base64"}` — the account is present.
4. The existing regression test at `rpc/src/rpc.rs` around lines 8247-8261 already reproduces and asserts this exact discrepancy (`accounts.len()` differs between `jsonParsed` and `base64`/raw `getProgramAccounts` calls for the same filter).
