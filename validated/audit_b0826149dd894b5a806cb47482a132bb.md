## Finding: Missing Reentrancy Protection in `EscrowDst._withdraw()` Allows Duplicate Payouts from Escrow Balance - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw()` performs three sequential external value transfers (`integratorFee` → `protocolFee` → `maker` amount) followed by a safety-deposit transfer to `msg.sender`, with no reentrancy guard and no state flag marking the escrow as "already withdrawn." When the destination token is native ETH, each `_uniTransfer`/`_ethTransfer` call executes attacker-controllable code (the recipient's `receive`/`fallback`), which can call back into `withdraw`/`publicWithdraw` before the original call completes.

### Finding Description
`_withdraw` is guarded only by `onlyValidImmutables` (a pure CREATE2-address check against the *constant* `immutables` hash) and `onlyValidSecret` (a pure hashlock check) — neither of which is state that changes after a withdrawal, and there is no `nonReentrant` modifier anywhere in `BaseEscrow`/`Escrow`/`EscrowDst`: [1](#0-0) 

`_uniTransfer`/`_ethTransfer` use a raw `.call{value: amount}("")` and simply check the boolean success, without any checks-effects-interactions ordering or reentrancy lock: [2](#0-1) 

The taker (and the fee recipients) are attacker-controllable inputs supplied directly to `createDstEscrow`, since `dstImmutables` (including `token`, `amount`, `taker`, and the fee data encoded in `parameters`) is caller-supplied calldata with no on-chain cap check equivalent to the `InvalidFeeAmounts` check that exists only in the *source*-side `_postInteraction` flow: [3](#0-2) [4](#0-3) 

An attacker who is both the `taker` (satisfying `onlyCaller(taker)` on every reentrant call trivially, since it calls itself) and the `integratorFeeRecipient` can:
1. Deploy the destination escrow with `token == address(0)` (native) and fee amounts crafted so a fresh reentrant call still has enough remaining native balance to redo `integratorFee` (+ `protocolFee` + `maker` amount, which can be engineered to 0 by making fees sum to `immutables.amount`) + `safetyDeposit`.
2. Call `withdraw()`. The first `_uniTransfer(integratorFeeAmount)` calls the attacker contract, whose fallback re-enters `withdraw()` (or `publicWithdraw()` once in the public window) with the same immutables/secret — both still valid, nothing having been marked as consumed.
3. Each successful reentrant frame that manages to complete all of `_withdraw`'s steps before running out of escrow balance "locks in" an additional `integratorFeeAmount` + `safetyDeposit` payout to the attacker. Frames that fail partway (due to insufficient balance) revert cleanly and are swallowed by the attacker's fallback (which does not propagate the failure), letting the enclosing frame continue as if the recipient transfer had simply succeeded.

The net effect is that the escrow's held native balance (funded exactly to cover `amount + safetyDeposit`, per `createDstEscrow`) can be paid out to the attacker more than once, at the expense of the honest maker/protocol-fee recipient and/or by depleting funds that were meant to be held atomically for a single settlement.

### Impact Explanation
This allows direct theft of user funds at rest in the destination escrow (the maker's principal and/or safety deposit), and/or causes protocol/integrator fee accounting to be duplicated or skipped, meeting the Critical bar ("direct theft of user funds at rest or in motion... protocol insolvency") and/or the High bar ("theft... of unclaimed fee-like value"). It is triggered entirely through the public `createDstEscrow` + `withdraw`/`publicWithdraw` entrypoints with no admin/governance/privileged-resolver assumption — the attacker only needs to be the resolver/taker filling their own maliciously parameterized destination escrow (and, for the `publicWithdraw` variant, hold the access token, which is unprivileged/permissionless).

### Likelihood Explanation
High. No special timing, race condition against other actors, or privileged role is needed — the attacker fully controls the destination escrow's parameters (token, amounts, fee recipients, taker) via `createDstEscrow`, and the reentrancy is a straightforward same-block, same-secret re-invocation of `withdraw`/`publicWithdraw` from within the native-token callback triggered by `_ethTransfer`.

### Recommendation
Add a reentrancy guard (e.g., OpenZeppelin `ReentrancyGuard`, or a simple `withdrawn`/status flag checked and set before any external calls) to `_withdraw` (and `cancel`) in `EscrowDst.sol`/`EscrowSrc.sol`, and follow checks-effects-interactions by finalizing/zeroing escrow state before performing any native-token or ERC20 transfer to attacker-influenced recipients (`integratorFeeRecipient`, `protocolFeeRecipient`, `maker`).

### Proof of Concept
1. Attacker deploys a `Taker` contract implementing `receive()` that, on first invocation, calls `EscrowDst(escrow).publicWithdraw(secret, immutables)` (or `withdraw` if still `taker`), ignoring the call's return value.
2. Attacker calls `createDstEscrow{value: amount + safetyDeposit}(immutables, srcCancellationTimestamp)` with `token = address(0)`, `taker = Taker`, and fee parameters (`integratorFeeRecipient = Taker`) crafted so `integratorFeeAmount + protocolFeeAmount == immutables.amount` (maker leg becomes 0) and `integratorFeeAmount` is small enough relative to `protocolFeeAmount + safetyDeposit` that at least one additional full reentrant cycle can complete.
3. Once inside the withdrawal window, attacker (as `taker`) calls `withdraw(secret, immutables)`.
4. Observe via `vm.deal`/balance assertions that `Taker` receives `integratorFeeAmount` and `safetyDeposit` more than once from the same escrow instance, exceeding the amount that a single legitimate `_withdraw()` execution should pay out, while the escrow's `onlyValidImmutables`/`onlyValidSecret` checks pass unchanged on every reentrant call because no state is updated to prevent replay.

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```
