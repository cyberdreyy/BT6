### Title
Client-controlled `MessageId` collisions in `WebAPIHandler.savedCallbacks` cause cross-user response hijacking / callback overwrite - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The C4 report's root cause is: a contract keys shared, mutable per-request state (a user's contribution) solely by an identifier the contract assumes is unique/uncontended, but the identifier space is actually shared with other unprivileged actors whose actions can overwrite or consume that state, so the wrong value gets paid out to the wrong caller. The same structural flaw exists in the gateway's legacy WebAPI trigger handler: `savedCallbacks` is a single map keyed only by the client-supplied `MessageId`, with no per-sender/per-connection scoping, and any concurrent unprivileged client can pick the same key.

### Finding Description
`WebAPIHandler.HandleLegacyUserMessage` stores the caller's response callback in a handler-wide map keyed purely by `msg.Body.MessageId`: [1](#0-0) 

`MessageId` is not a server-generated, per-request-unique value scoped to the caller — it is copied verbatim from the JSON-RPC request `ID` field supplied in the raw HTTP body sent by the (unprivileged) API client: [2](#0-1) 

`Message.Validate()` only checks length/format constraints on `MessageId` (1–128 bytes, no trailing NUL); it does not enforce uniqueness or tie the ID to the caller's signer/session in any way that prevents collision across different callers: [3](#0-2) 

When a node responds, `handleWebAPITriggerMessage` looks the callback up by that same `MessageId`, deletes the entry, and delivers the *first* matching node response to whichever callback is currently registered under that key — with no verification that the responding trigger event actually corresponds to the request that registered the callback beyond the shared ID: [4](#0-3) 

Because `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` is a plain map write (last write wins) guarded only by a mutex, not a "must not already exist" check, one unprivileged client's `HandleLegacyUserMessage` call can silently overwrite another concurrent client's callback registration if they choose the same `MessageId` (e.g., an attacker enumerating small/sequential/predictable IDs, or racing a known/observed ID). This is structurally identical to the reported bug class: code assumes a per-actor value keyed by a shared identifier remains exclusively "theirs," but concurrent unprivileged actors can mutate/consume that same slot.

### Impact Explanation
- **Cross-user response confusion**: If attacker A submits a legacy WebAPI trigger request with the same `MessageId` as victim B's in-flight request, A's callback registration can overwrite B's in the `savedCallbacks` map. The next node response bearing that `MessageId` is delivered to whichever callback remains registered — potentially delivering B's trigger response to A (response/data leak to the wrong party), or dropping/misdirecting B's expected response (denial of service for B).
- No fund movement is directly implicated here (this handler proxies external HTTP trigger/target requests, not on-chain payments), but the pattern maps directly to the requested class "cross-user response confusion" in an internet-facing gateway handler that processes unprivileged client requests.
- The blast radius is scoped to callers hitting the same DON's legacy WebAPI handler concurrently; it does not require any node or operator compromise — purely an unprivileged HTTP client interaction.

### Likelihood Explanation
Exploitability requires only that two different unprivileged callers submit legacy gateway messages with the same JSON-RPC `id`/`MessageId` while one is still pending (within the pruning window, default up to ~120s per `defaultCallbackMaxAgeSec`, see `core/services/gateway/handlers/capabilities/handler.go` lines 43-45 and 89-94 referenced in the file). Since `MessageId` is entirely attacker-chosen and not validated for uniqueness or bound to the caller's identity/session, an attacker only needs to guess or observe a value used by another concurrent request (e.g., low-entropy client IDs, or simply flooding with the same ID as a victim they are targeting) to trigger the collision. This is a realistic, moderately likely scenario for any deployment where the WebAPI legacy trigger path receives concurrent traffic from multiple untrusted clients.

### Recommendation
Do not use a purely client-supplied value as the sole key for shared, cross-request callback state. Options:
1. Derive the internal callback-map key from a server-generated, cryptographically unique token (e.g., UUID) combined with the caller's verified `Sender`/signer address, rather than trusting the raw `MessageId` alone.
2. Reject registration (`HandleLegacyUserMessage`) if an entry already exists for the same key instead of silently overwriting it, and treat that as an error back to the second caller.
3. Additionally verify that the node's trigger response corresponds to the request context (e.g., match `Sender`/`DonId`/topic in addition to `MessageId`) before dispatching to the saved callback.

### Proof of Concept
1. Client A sends a legacy gateway JSON-RPC request with `id = "X"` for `MethodWebAPITrigger` and DON `D`; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA` and forwards to DON `D` nodes.
2. Before a node responds, Client B (an unrelated unprivileged caller) sends its own legacy request also using `id = "X"` for the same DON `D`; `HandleLegacyUserMessage` overwrites `savedCallbacks["X"] = callbackB`.
3. When a node later replies with `MessageId = "X"` (which could be the response intended for A's original request), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and delivers A's node response to B — while A's `callback.Wait(ctx)` times out having never received a response.

Note: This analysis was performed via the codebase index and static code reading only (no ability to run the gateway locally); confirming the exact race timing/window and whether upstream JSON-RPC ID validation exists elsewhere in the request path would require running the gateway integration tests (`core/services/gateway/integration_tests/gateway_integration_test.go`) directly.
