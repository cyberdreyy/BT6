### Title
Unchecked `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` allows migrating a MarginfiAccount (and all its deposited collateral) to an uncontrollable address, permanently freezing funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` let an account authority migrate all of their `MarginfiAccount` positions to a brand-new account while permanently disabling the old one. The instruction accepts `new_authority` as a completely unchecked `UncheckedAccount`, mirroring the Putty bug class where a position token is minted to an address without verifying the recipient can actually use it. Once migrated, the old account is irrecoverably disabled, so if `new_authority` cannot actually produce a valid signature for the resulting account (e.g. a PDA with no corresponding keypair, or any pubkey the caller does not truly control), the entire lending position becomes permanently unreachable.

### Finding Description
In `transfer_to_new_account`, the `new_authority` field is explicitly documented as unchecked: [1](#0-0) 

The instruction unconditionally uses this value as the authority of the freshly initialized account and then disables the old account with no way back: [2](#0-1) 

`finalize_migrated_old_account` sets `ACCOUNT_DISABLED` on the old account and there is no `migrated_to` reversal path once `migrated_to` is set (`check_eq!(old_account.migrated_to, Pubkey::default(), ...)` guards against re-migration): [3](#0-2) [4](#0-3) 

The same unchecked pattern exists in `TransferToNewAccountPda`, where `new_authority` is used as a PDA seed but is likewise never validated to be a controllable signer: [5](#0-4) 

This is analogous to the Putty finding: just as Putty's `_mint` places an ERC721 position at an address without verifying the recipient can interact with it (via `_safeMint`/`onERC721Received`), marginfi's `transfer_to_new_account[_pda]` moves an entire lending position (all balances, all collateral/liability shares) to a `new_authority` pubkey without any verification that this address is a controllable wallet (e.g. not a PDA owned by an unrelated program, not an address with no known private key). The test suite explicitly documents this as an intentional, unguarded design choice: [6](#0-5) 

### Impact Explanation
If a user (or an integrator building a UI/CPI flow on top of `transfer_to_new_account`) supplies an incorrect `new_authority` — for example a PDA belonging to another program with no corresponding private key, a typo'd pubkey, or a burn-style address — the following happens atomically and irreversibly in one instruction:
1. The old account is disabled (`ACCOUNT_DISABLED`) and its `lending_account` is zeroed out (moved to the new account).
2. The new account is initialized with all the old collateral/liability shares under `new_authority`.
3. Since `migrated_to`/`ACCOUNT_DISABLED` prevent any further transfer from the old account, and there is no operation to reclaim a `MarginfiAccount` whose `authority` cannot sign, all deposited collateral and any outstanding borrow positions become permanently stranded — the user (or anyone) can never again submit a valid instruction with `authority` as a `Signer` for that account.

This is a durable, financial-impact freeze of user funds triggered by an ordinary, permissionless, unprivileged-user action, matching the "position lock/nontransferable" impact category described in the Putty report.

### Likelihood Explanation
Likelihood is moderate: the flow is reachable by any regular user with no special privileges and requires no admin cooperation, but it does require the caller (or the tooling constructing the transaction, e.g. a third-party integrator's CPI) to supply an incorrect `new_authority`. Because `transfer_to_new_account_pda` is designed explicitly for CPI callers ("If you are a CPI caller, consider using `marginfi_account_initialize_pda` instead" per the doc comment on `marginfi_account_initialize`), a buggy or malicious integrator program computing `new_authority` incorrectly (e.g., a PDA without matching signer capability) could trigger this for many users at once.

### Recommendation
Since the account cannot practically "reject" the transfer post-hoc, consider adding safeguards analogous to `_safeMint`'s receiver check where feasible: e.g., require `new_authority` to be a `Signer` (round-trip signature) for the plain `transfer_to_new_account` path, or provide a two-step/claim-based migration (create the new account in a claimable/pending state and require the `new_authority` to sign a follow-up "accept" instruction before the old account is irreversibly disabled). At minimum, document this unchecked-authority risk prominently in user-facing SDK/CLI tooling and strongly discourage constructing `new_authority` from data that hasn't been proven signable.

### Proof of Concept
1. User initializes `old_marginfi_account` with `authority = A` and deposits collateral.
2. User (or integrator) calls `transfer_to_new_account` with `new_authority` set to some PDA `P` (owned by an unrelated program, no keypair exists for `P`) and a fresh `new_marginfi_account` keypair.
3. Instruction succeeds: `old_marginfi_account.account_flags = ACCOUNT_DISABLED`, `old_marginfi_account.migrated_to = new_marginfi_account`, and `new_marginfi_account.authority = P` with all the migrated collateral/liability shares (see `transfer_to_new_account` at lines 91–105 and `finalize_migrated_old_account` at lines 39–49).
4. No instruction in the program accepts `authority = P` as a `Signer` (since no private key exists for a PDA), and `old_marginfi_account` can never be un-migrated (`AccountAlreadyMigrated` check at lines 84–89), so all collateral is permanently inaccessible.
