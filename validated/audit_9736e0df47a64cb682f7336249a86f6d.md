### Title

ERC4626 share-price inflation can strand all programmable-borrower principal and force a default - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary

`ProgrammableBorrower` deposits pool principal into an arbitrary configured ERC4626 vault through `_depositToVault()` but does not enforce a minimum number of returned shares. If the vault is empty or has a very small supply and does not implement virtual-share protection, an unprivileged vault user can perform the standard first-depositor/donation inflation attack, receive the donated and deposited assets, and leave `ProgrammableBorrower` holding zero or dust shares.

### Finding Description

The epoch start path transfers pool funds to the programmable borrower, calls `onStartEpoch()`, and `_depositToVault()` accepts whatever share amount `vault.deposit()` returns. There is no `previewDeposit()` consistency check or minimum-share bound. The only vault validation performed by `initialize()` and `setVault()` is that the vault asset matches the CDO underlying. [1](#0-0) [2](#0-1) [3](#0-2) 

In an inflation-vulnerable ERC4626, an attacker can deposit one unit to mint one share, directly donate at least the pool principal to the vault, and cause the subsequent pool deposit to mint zero shares through rounding. Because `ProgrammableBorrower` records the pre-deposit asset amount as `epochStartVaultAssets`, the stolen principal later appears as an unexplained vault loss rather than as a failed deposit. [4](#0-3) [5](#0-4) 

### Impact Explanation

The attacker can steal the deposited principal. For pool principal `P`, the attacker spends approximately `P` as vault seed liquidity plus donation, causes `ProgrammableBorrower` to receive zero vault shares for its `P` deposit, and redeems the attacker's shares for approximately `2P`, for a net profit of `P`.

The stolen position then becomes a real vault loss in `totalInterestDueNow()`. A close-pool `stopEpoch(..., 1)` requests the full strategy-token principal back, but `ProgrammableBorrower` has no vault shares and insufficient cash, so the CDO's pull fails and `_handleBorrowerDefault()` marks the pool defaulted. [6](#0-5) [7](#0-6) 

This breaks solvency and the one-receipt-one-payout guarantee: tranche holders still hold claims backed by strategy tokens, while the programmable borrower no longer owns the corresponding external vault assets.

### Likelihood Explanation

Likelihood is medium because the attack requires the configured ERC4626 vault to be newly initialized or have very low supply and to lack inflation protection. `ProgrammableBorrower` accepts a generic ERC4626 and does not require a battle-tested vault, virtual shares, an initial dead-share deposit, or minimum returned shares. An ordinary vault depositor can perform the inflation before the first `onStartEpoch()` call.

Existing skim logic does not prevent the attack because the donation is made to the external ERC4626 vault, not to the CDO. The `_checkProgrammableBorrowerMode()`, pause, and epoch checks also do not constrain ERC4626 share issuance. [8](#0-7) 

### Recommendation

Require `_depositToVault()` to enforce a minimum acceptable share amount, preferably derived from `previewDeposit()` with an explicit slippage bound, and revert on zero or unexpectedly low shares. Additionally, require configured vaults to use virtual shares or an initialized dead-share reserve, and consider atomically deploying/seeding supported vaults before any public deposit is possible.

### Proof of Concept

A reproducible Foundry test can use a deployed ERC4626 implementation without virtual-share protection:

1. Configure `ProgrammableBorrower` with an empty ERC4626 vault.
2. Attacker deposits `1` underlying and receives one vault share.
3. Attacker directly transfers `P` underlying to the vault, where `P` is the programmable-borrower deposit amount.
4. Manager starts an epoch after the CDO sends `P` to `ProgrammableBorrower`.
5. `ProgrammableBorrower` calls `vault.deposit(P, address(this))`; with `totalSupply = 1` and `totalAssets = P + 1`, it mints `P / (P + 1) == 0` shares.
6. Attacker redeems its one share for approximately `2P` underlying.
7. `vaultInterestAccrued()`/`vaultLoss()` reports a loss of `P`, and closing the pool fails to recover principal, causing `defaulted = true`.

The vulnerable sequence is the unbounded `vault.deposit()` call and the absence of a returned-share check. [9](#0-8)

  /// @notice Hook called by IdleCDOEpochVariant when a new epoch starts.
  /// It deposits all on-hand assets into the vault and starts accounting.
  /// @param _pendingWithdraws pending withdraw requests amount to reserve for epoch end.
  function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);
    // Reset the epoch accounting baseline from the exact pre-start total assets so the new epoch
    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;
    epochWithdrawnFromVault = 0;
    epochAccountingActive = true;
    emit EpochAccountingStarted(startAssets);
  }

  /// @notice Handle borrower default
  function _handleBorrowerDefault(uint256 funds) internal {
    defaulted = true;
    // Do not reopen instant claims here. They remain disabled when funding is pending;
    // successful full funding is the only path that enables them before finalization.

    if (isProgrammableBorrower) {
      IProgrammableBorrower(_borrower()).onDefault();
    }

    // deposits should be already prevented
    if (!paused()) {
      _pause();
    }

    // stop the current epoch
    isEpochRunning = false;

    // prevent withdrawals requests
    allowAAWithdrawRequest = false;
    allowBBWithdrawRequest = false;

    emit BorrowerDefault(funds);
  }
