### Title
Permissionless lamport donation to a staked-collateral bank's underlying stake/on-ramp account instantly inflates the LST oracle price used for the same-transaction health check - (File: `programs/marginfi/src/state/price.rs`)

### Summary
The external report describes `fShareRatio` being manipulable because it is derived from `fsd.getReserveBalance()`, a reserve total that a user can inflate within the same transaction (flash mint) before it feeds an important solvency/reward check. marginfi-v2 contains a structurally analogous pattern: for `OracleSetup::StakedWithPythPush` banks, the collateral price multiplier is computed live, on every instruction, directly from the lamport balance of the underlying SPL single-pool stake/on-ramp account divided by the LST mint supply. Unlike a normal Pyth/Switchboard price feed, this "reserve balance" can be pushed up permissionlessly and instantly with a plain `SystemProgram::transfer`, and the resulting inflated price is consumed immediately by the health check of a borrow/withdraw instruction placed later in the same transaction.

### Finding Description
For staked-collateral banks, `OraclePriceFeedAdapter::load_oracle_context_with_max_age` computes the effective price multiplier as: [1](#0-0) 

`sol_pool_adjusted_balance` comes from `staked_pool_net_asset_value` (or `legacy_staked_pool_delegated_value`), which reads the raw lamport balance of the native-stake-owned `sol_pool`/`pool_onramp` accounts: [2](#0-1) 

Because these accounts are owned by the native Stake program (`NATIVE_STAKE_ID`), not by marginfi, and Solana's `SystemProgram::transfer` can credit lamports to *any* account regardless of owner, any unprivileged user can top up the lamport balance of `sol_pool` (or the on-ramp account) with a plain transfer instruction placed earlier in the same transaction. The protocol's own test suite confirms this is expected/observed behavior — a raw `SystemProgram.transfer` to `splSolPool` immediately changes the computed price multiplier: [3](#0-2) 

This multiplier is applied directly to the Pyth price used for **all existing collateral of every account holding that LST**, and it is fetched fresh at call time (no caching/averaging), so it is instantly reflected in the very same transaction: [4](#0-3) 

The inflated collateral valuation is consumed by `check_account_init_health` when a borrow/withdraw instruction runs later in the same transaction, and there is no confidence/deviation/staleness check that can catch this — `oracle_max_age`/`oracle_max_confidence` only bound the underlying Pyth feed, not the stake-pool-derived multiplier: [5](#0-4) 

This is the same bug class as `fShareRatio`: a ratio computed from a live, externally-manipulable "reserve" value is used, within a single atomic transaction, to gate a financial decision (there: membership purchase/reward eligibility; here: borrowing power against staked collateral).

### Impact Explanation
An attacker who already holds a large deposit of a given LST as collateral can, within one transaction: (1) `SystemProgram::transfer` a modest amount of SOL to that validator's `sol_pool`/on-ramp account, (2) immediately call `lending_account_borrow` (or `lending_account_withdraw`) against a *different* bank using the now-inflated staked-collateral value as part of the health check. Because the price bump applies to the attacker's entire pre-existing collateral balance (not just the donated amount), the extra borrowing power unlocked can exceed the cost of the donation whenever the attacker's existing position is large relative to the target validator's total stake-pool NAV (small/low-liquidity SPL single-validator pools are common). This allows borrowing beyond what the true collateral value supports, which is a genuine under-collateralized-debt/value-redirection outcome with direct financial effect on lenders in the borrowed bank.

### Likelihood Explanation
Requires no special privileges — only a standard `SystemProgram::transfer` instruction (any account can receive lamports regardless of owner) composed in the same transaction as a normal borrow/withdraw. The transferred lamports are not easily recoverable by the attacker (they land in a stake/on-ramp account controlled by the native Stake program), so this is not a zero-cost attack, similar to the tribute-fee argument that led the original report to be rated Low — the attack is only profitable when the attacker's existing collateral in that specific validator's LST is large relative to the target pool's NAV, which limits but does not eliminate exploitability, especially against smaller/newer validator stake pools.

### Recommendation
- Do not treat a single live read of `sol_pool`/on-ramp lamport balance as an instantaneous, atomic-transaction-safe price input; consider using a time-averaged or previous-slot-committed NAV snapshot (e.g., require the value to have been refreshed by a separate, earlier-slot "pulse" instruction rather than being recomputable within the same transaction as the action that depends on it).
- Bound the maximum per-transaction/per-slot movement of the staked-NAV-derived multiplier, similar to how `oracle_max_confidence` bounds Pyth feed uncertainty.
- Consider requiring `pulse_bank_price` (or an equivalent staked-price refresh) to occur in a prior, already-committed transaction rather than being freely composable with borrow/withdraw in the same transaction.

### Proof of Concept
1. Attacker deposits a large amount of validator V's LST into marginfi as collateral (staked bank, `OracleSetup::StakedWithPythPush`).
2. In a single transaction, attacker adds instruction A: `SystemProgram::transfer` lamports directly to validator V's `sol_pool` (or `pool_onramp`) account — a plain, permissionless transfer, as demonstrated by the test harness itself: [6](#0-5) 
3. Instruction B (same tx): `lending_account_borrow` against another bank, passing V's staked bank + oracle accounts in `remaining_accounts` for the health check.
4. During instruction B's health check, `load_oracle_context_with_max_age` recomputes `sol_pool_adjusted_balance / lst_supply` live, reflecting the balance increase from instruction A, inflating the USD value assigned to attacker's entire existing LST collateral position and allowing a larger borrow than the pre-donation valuation would permit.

pub fn check_account_init_health<'info>(
    marginfi_account: &MarginfiAccount,
    remaining_ais: &'info [AccountInfo<'info>],
    health_cache: &mut Option<&mut HealthCache>,
) -> MarginfiResult {
    if marginfi_account.get_flag(ACCOUNT_IN_FLASHLOAN) {
        // Risk checks are skipped during flashloans
        return Ok(());
    }

    let (assets, liabs) = get_health_components(
        marginfi_account,
        remaining_ais,
        RequirementType::Initial,
        health_cache,
        HealthPriceMode::Live { liq_cache: None },
    )?;

    let healthy = assets >= liabs;
    if let Some(cache) = health_cache.as_mut() {
        cache.set_healthy(healthy);
    }

    if !healthy {
        return err!(MarginfiError::RiskEngineInitRejected);
    }

    check_account_risk_tiers(marginfi_account, remaining_ais)
}
