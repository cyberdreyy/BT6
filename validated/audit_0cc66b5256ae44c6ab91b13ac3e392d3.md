### Title
Duplicate-tenure-block guard is proposal-only, not re-checked at pre-commit-threshold signing time - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
The `DuplicateBlockFound` check inside `validate_tenure_change_payload` — which stops a signer from endorsing a second, competing tenure-change block for a tenure it has *already signed a block in* — is evaluated only when the block proposal first arrives (`check_proposal` → `validate_tenure_change_payload`), and is never re-run at the two later points where a signature is actually produced: `check_block_against_signer_db_state` (validate-ok path) and the pre-commit-threshold signing path in `handle_block_pre_commit`. This is the same bug class as CVE-2017-2604 (Jenkins SECURITY-371): a security-relevant check exists on one code path but is silently absent from the other paths that lead to the same privileged action, so an attacker who can control timing can reach the action through the unguarded path.

### Finding Description
`stacks-signer/src/chainstate/v1.rs` `validate_tenure_change_payload` (lines 461-520) and `stacks-signer/src/chainstate/v2.rs` (lines 306-359) both call `signer_db.get_last_globally_accepted_block` / `get_last_signed_block` for the *new* block's own consensus hash, and reject with `RejectReason::DuplicateBlockFound` if the signer has already signed a block in that tenure. This is the only place this specific "already signed a block in this exact tenure" check runs.

The signer's flow (documented in `docs/signer-flows.md` §3, §4, §5, and explicitly in §7 lines 425-437) is:
1. Proposal arrives → `check_block_against_state` → `check_proposal` (v1/v2) → `validate_tenure_change_payload` runs the `DuplicateBlockFound` check [1](#0-0) .
2. Node returns validate-ok → `check_block_against_signer_db_state` re-verifies tenure-change confirmation via `check_tenure_change_confirms_parent`, but this only calls `check_latest_block_in_tenure`, not `validate_tenure_change_payload`/duplicate check [2](#0-1) .
3. Pre-commit threshold reached (≥70% weight) → `handle_block_pre_commit` re-runs `check_block_against_signer_db_state` again before signing (per §5 of the flow doc), which is the *same* function that does not re-run the duplicate-tenure check [3](#0-2) .

The doc's own authors flag this gap explicitly: *"Because the duplicate check never runs again, a block that crosses the pre-commit threshold long after it was proposed relies on section 5's own-tenure conflict guard to cover the same ground."* [4](#0-3) 

That fallback ("section 5's own-tenure conflict guard", `get_signed_conflicts` / `conflict_still_blocks`) is a *different* mechanism keyed on height-based conflicts across "ANY tenure" and depends on freshness windows (`last_endorsed > cutoff`) and reorg-permit exclusions — it is not a re-invocation of the exact `DuplicateBlockFound` rule, and its own branches (`FRESH -- no — all stale --> OWN`, `PERM -- yes --> EXCL`) can route around signing anyway if the conflicting record has gone stale or is covered by a `reorg_permit_stands` exclusion (§5, lines 250-268 of the flow doc). Because the pre-commit round is explicitly designed to let time pass between "I am willing to sign" and the actual signature (so that "the burn chain can fork" and "another block may win the same slot" per §0 of the doc), a miner can propose a tenure-change block early (when the `DuplicateBlockFound` check at proposal time trivially passes, e.g. before any block in that tenure was actually signed elsewhere), collect pre-commits over an extended window, and only cross the 70% threshold once the "own-tenure conflict guard" fallback no longer blocks it (e.g. the conflicting block's `last_endorsed` timestamp goes stale, per the `FRESH -- no` branch in §5), letting the signer sign a genuinely duplicate/conflicting tenure-change block that the authoritative `DuplicateBlockFound` check would have rejected had it been re-evaluated at signing time.

### Impact Explanation
This breaks the "one-per-height / no duplicate tenure-start" equality that `validate_tenure_change_payload` is meant to enforce: a signer could sign a second, conflicting tenure-change block for a tenure it already has a signed (locally or globally accepted) block in, purely because the authoritative duplicate check is skipped at the moment the signature is actually produced and only a weaker, timing-sensitive fallback stands in its place. Signing a conflicting/duplicate tenure-start block is exactly the "Critical" impact category called out in scope (signer signing a conflicting block).

### Likelihood Explanation
This requires only a single miner (plus normal gossip of pre-commits from the honest signer set, which is expected protocol behavior, not collusion) manipulating proposal timing across the pre-commit window — no majority of signers, no other signer's key, and no auth token are needed. The likelihood depends on the precise freshness/staleness windows in `get_signed_conflicts`/`reorg_permit_stands`, which I was not able to fully trace before running out of tool budget (see below).

### Recommendation
Re-run the same `validate_tenure_change_payload` `DuplicateBlockFound` check (not just `check_latest_block_in_tenure`) inside `check_block_against_signer_db_state`, so it executes identically at proposal time, at validate-ok, and immediately before a signature is emitted in `handle_block_pre_commit`.

### Proof of Concept
Not fully constructible from static analysis alone. I was not able to inspect `get_signed_conflicts`, `conflict_still_blocks`, and `reorg_permit_stands` in `stacks-signer/src/signerdb.rs` / `stacks-signer/src/v0/signer.rs` in this session (ran out of tool iterations before reading those bodies), so I cannot confirm with certainty whether the "own-tenure conflict guard" fallback fully closes this gap in all timing windows, or whether there exists a concrete window (e.g. after the conflicting block's `last_endorsed` timestamp exceeds `reorg_attempts_activity_timeout`/similar cutoff, per the `FRESH -- no — all stale` branch) in which it does not. This uncertainty should be resolved by tracing those functions directly; I flag this as a documented, code-comment-acknowledged gap ("Because the duplicate check never runs again...") rather than a fully proven exploit, and recommend that be independently verified against the exact conflict-cutoff semantics in `signerdb.rs`.

    fn check_block_against_signer_db_state(
        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,
                self.proposal_config.tenure_last_block_proposal_timeout,
                self.proposal_config.reorg_attempts_activity_timeout,
            ) {
                Ok(true) => return None,
                Ok(false) => {
                    return Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                }
                Err(e) => {
                    warn!("{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %proposed_block.block_id()
                    );
                    return Some(self.create_block_rejection(
                        RejectReason::ConnectivityIssues(
                            "error checking block proposal".to_string(),
                        ),
                        proposed_block,
                    ));
                }
            }
        }
