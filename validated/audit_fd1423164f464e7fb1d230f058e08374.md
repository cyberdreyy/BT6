### Title
Stale-epoch instant-withdraw receipts are omitted from `defaultPendingClaimBasis` because recovery accounting only reads `instantWithdrawClaimsByEpoch[epochNumber]` — identical claims keyed under earlier epochs bypass the haircut list and are permanently frozen — (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The ssrfcheck bug is an incomplete denylist: the guard matches only one representation of a private IP (dot-notation) while an equivalent representation (hex-normalized IPv4-mapped IPv6) slips through. The same pattern exists in `IdleCreditVault`: default-recovery accounting enumerates unfunded instant-withdraw claims only via `instantWithdrawClaimsByEpoch[epochNumber]`, i.e. only claims keyed to the *current* epoch. Instant receipts recorded under a *previous* epoch — the same claim in a different representation/key — are invisible to `defaultPendingClaimBasis()` and to `_claimDefaultedInstantWithdrawRequest()`, so they are neither haircut-priced into the recovery reserve nor payable afterward.

### Finding Description
Instant withdraw requests record basis per request epoch at `requestInstantWithdraw` (`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`). `pendingInstantWithdraws` is a global counter that is only decremented by `collectInstantWithdrawFunds`, so if the borrower underfunds the instant queue at `startEpoch`, the remainder persists into later epochs while the per-epoch claim basis stays keyed to the original request epoch.

When default recovery is later finalized (`finalizeDefaultRecovery` → `defaultPendingClaimBasis`), the basis includes `instantWithdrawClaimsByEpoch[epochNumber]` only — current-epoch claims. `defaultInstantWithdrawsFinalized` is set from `pendingInstantWithdraws != 0`, so the stale-epoch receipts are nominally "handled", but `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. A user whose receipt lives under `defaultRecoveryEpoch - 1` gets `claimBasis == 0` there, then falls through to `_transferFundedClaim` at par — which refuses to spend `defaultRecoveryReserve`. Since their funds were never collected and never included in the reserve, the claim reverts or pays nothing: the same claim exists but is invisible to every list the contract checks (current-epoch instant basis, default-epoch instant basis, post-default requests, funded receipts).

The parallel to the advisory is exact: the contract "knows" the claim exists (`instantWithdrawsRequests[_user] != 0`, `pendingInstantWithdraws != 0`) but every enforcement structure matches only the current-epoch key, just as the regex matched only dot-notation.

### Impact Explanation
- Permanent freezing of user funds: users with unfunded instant receipts carried across an epoch boundary can never claim after default finalization — `claimInstantWithdrawRequest` clears their `instantWithdrawsRequests` entry, burns nothing for the defaulted path (wrong epoch key), and `_transferFundedClaim` reverts when only reserve-backed underlying remains.
- Recovery mispricing: `defaultPendingClaimBasis` undercounts `totalBasis`, so `defaultRecoveryPrice` is computed slightly too high for included claimants while excluded claimants get zero — a direct haircut-list bypass with quantified loss equal to the stale-epoch `instantWithdrawClaimsByEpoch[e]` amounts.

### Likelihood Explanation
Requires only honest-role sequencing: borrower partially underfunds instant withdrawals at one `startEpoch`, an epoch boundary passes (requests in the next epoch change `epochNumber`), the borrower defaults, and owner/manager call `finalizeDefaultRecovery`. The attacker/victim is an ordinary instant-withdraw requester — no privileged or malicious role needed. No existing guard stops it: `_ensureDefaultRecoveryInitialized` only gates on `pendingInstantWithdraws != 0` for the *lazy-init* path, not for finalization, and the per-epoch key mismatch is never reconciled.

I was unable to fully verify in this pass whether `collectInstantWithdrawFunds`/`startEpoch` always drain `pendingInstantWithdraws` to zero at every epoch boundary (which would make stale-epoch instant claims unreachable). If the CDO enforces exact full funding, the stale-epoch state may be unreachable and this would reduce to a defense-in-depth gap rather than an exploitable bug.

### Recommendation
Aggregate the instant claim basis across all epochs with nonzero claims (or maintain a single `pendingInstantClaimBasis` counter updated at request and claim time) instead of reading `instantWithdrawClaimsByEpoch[epochNumber]`. In `_claimDefaultedInstantWithdrawRequest`, treat any nonzero `instantWithdrawsRequests[_user]` as defaulted basis (or track per-user unfunded remainder directly), so claims cannot exist in a representation the recovery path does not enumerate — the same fix principle as replacing the dot-notation regex with `net.BlockList`.

### Proof of Concept
A Foundry fork PoC would: (1) create a user instant-withdraw request during epoch N; (2) have `startEpoch` collect less than the full instant amount so `pendingInstantWithdraws > 0` persists; (3) run `stopEpoch`/`startEpoch` so `epochNumber` becomes N+1; (4) trigger borrower default and call `finalizeDefaultRecovery`; (5) show `defaultPendingClaimBasis` excludes `instantWithdrawClaimsByEpoch[N]` and the user's `claimInstantWithdrawRequest` either reverts in `_transferFundedClaim` or pays 0 while `instantWithdrawsRequests[user]` was nonzero.
