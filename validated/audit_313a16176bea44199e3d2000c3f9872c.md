### Title
External ERC4626 liquidity manipulation can repeatedly block epoch settlement and freeze withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`IdleCDOEpochVariant.stopEpoch` synchronously recalls pending-withdrawal liquidity through `ProgrammableBorrower.onStopEpoch`. If the configured ERC4626 vault still values the borrower's shares as sufficient, but an external vault user has drained or rearranged its liquidity so `withdraw` reverts, `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`. Because this hook executes outside the `try` that catches borrower repayment failures, the entire `stopEpoch` transaction reverts, leaving the epoch running and pending withdrawals unsettled.

### Finding Description
During an epoch, deposits and withdrawal requests are disabled and prior withdrawal requests become payable only after epoch settlement. At `stopEpoch`, `IdleCDOEpochVariant` calculates the pending withdrawal amount and calls `IProgrammableBorrower.onStopEpoch` before attempting to transfer cash from the borrower. [1](#0-0) [2](#0-1) 

`ProgrammableBorrower` first checks whether the current ERC4626 position economically covers the shortfall. If it does, the contract calls `vault.withdraw`; any revert from that external call is converted into `StopEpochVaultLiquidityUnavailable` and propagated back to the CDO. [3](#0-2) 

This creates an inconsistency between accounting solvency and withdrawable liquidity. ERC4626 `convertToAssets` explicitly measures the shares' exchange value under ideal conditions and need not represent immediately withdrawable liquidity. [4](#0-3)  A public vault depositor, or a borrower in the markets underlying a vault such as MetaMorpho, can consume the liquid assets while the programmable borrower's shares still report sufficient value.

The reverted hook occurs before `isEpochRunning` is cleared, before pending withdrawals are funded, and outside the surrounding `try` that calls `_handleBorrowerDefault`. [5](#0-4) [6](#0-5)  Consequently, every manager retry fails under the same manipulated liquidity condition.

The usual administrative escapes do not remove this dependency during an active epoch:

- `restoreOperations` returns immediately while `isEpochRunning` remains true. [7](#0-6) 
- `emergencyExitVault` still depends on the same external vault liquidity through `vault.redeem`. [8](#0-7) 
- `setVault` cannot switch to another vault while epoch accounting is active or vault shares remain. [9](#0-8) 

### Impact Explanation
An unprivileged ERC4626 vault user can temporarily freeze settlement of the entire credit pool. The frozen amount is at least `pendingWithdraws`, but operationally the whole epoch remains unsettled because tranche accounting, fee settlement, APR update, and reopening of withdrawal requests all occur only after the external vault withdrawal succeeds. [10](#0-9) 

The attacker can repeat the attack whenever sufficient liquidity returns, for example by maintaining high utilization in the underlying lending markets. No borrower default is recorded, so the affected funds are not permanently written off, but pending receipt holders cannot receive `P = pendingWithdraws` and the pool cannot enter the next buffer/epoch while the manipulated illiquidity persists.

### Likelihood Explanation
The attack requires a programmable-borrower deployment whose stop amount exceeds the vault's immediately withdrawable liquidity. That is a realistic ERC4626 condition: managed assets can be lent out while `convertToAssets` still reports the borrower's full claim. The attacker needs to be a vault shareholder or a user able to borrow the underlying market liquidity; no Idle role, borrower access, KYC status, or privileged call is required.

The condition is conditional rather than constant because it depends on the selected vault's liquidity and market design. However, the attacker can choose the settlement block and can use pre-acquired vault shares to consume the common liquidity pool at the exact time `stopEpoch` becomes callable.

### Recommendation
Do not leave epoch-end withdrawal obligations inside an external ERC4626 position until the stop transaction. At `onStartEpoch`, withdraw `epochPendingWithdraws` into the programmable borrower's on-hand balance, or maintain a separately isolated reserve that cannot be lent out.

If synchronous vault liquidity must remain supported, stop should implement a bounded partial-recovery path:

1. Attempt to withdraw only the currently available amount.
2. Fund what is available without reverting the entire epoch.
3. Record any remaining liability explicitly.
4. Permit claims as additional liquidity arrives.
5. Avoid marking a covered but temporarily illiquid position as a borrower default.

### Proof of Concept
The following Foundry fork test follows the existing `GAUNTLET_USDC_PRIME` programmable-borrower setup. The attacker acquires legitimate vault shares before the CDO epoch, then redeems them after the CDO has parked its funds and before the manager calls `stopEpoch`.

```solidity
function testExternalVaultUserCanRepeatStopEpochDoS() external {
    _setUpProgrammableBorrowerCreditVault(
        GAUNTLET_FORK_BLOCK,
        GAUNTLET_USDC_PRIME
    );

    IERC4626 gauntletVault = IERC4626(GAUNTLET_USDC_PRIME);
    address attacker = makeAddr("externalVaultUser");

    uint256 lpAmount = 10_000 * oneScale;
    uint256 drainAmount = 5_000 * oneScale;

    // The attacker is an ordinary pre-existing ERC4626 vault user.
    deal(USDC, attacker, drainAmount);
    vm.startPrank(attacker);
    IERC20(USDC).approve(address(gauntletVault), drainAmount);
    uint256 attackerShares = gauntletVault.deposit(drainAmount, attacker);
    vm.stopPrank();

    // Configure minted-interest mode and create a normal withdrawal request.
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(lpAmount);
    cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 2,
        address(aaTranche)
    );

    // Start the epoch. ProgrammableBorrower parks the CDO's idle funds
    // in the same external ERC4626 vault.
    _startEpochAndCheckPrices(0);

    uint256 pending = strategy.pendingWithdraws();
    assertGt(pending, 0);
    assertTrue(cdoEpoch.isEpochRunning());
    assertTrue(programmableBorrower.epochAccountingActive());

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // The external vault user exits. On a liquidity-fragmented vault this
    // consumes common withdrawal liquidity while the CDO's shares still
    // account for at least `pending`.
    vm.prank(attacker);
    gauntletVault.redeem(attackerShares, attacker, attacker);

    // Solvency accounting still says the shares cover the shortfall, but
    // the actual withdraw cannot execute.
    assertGe(
        gauntletVault.convertToAssets(
            gauntletVault.balanceOf(address(programmableBorrower))
        ),
        pending
    );

    // The hook reverts outside IdleCDO's getFundsFromBorrower try/catch.
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Settlement did not occur.
    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertEq(strategy.pendingWithdraws(), pending);
    assertTrue(programmableBorrower.epochAccountingActive());
    assertFalse(cdoEpoch.allowAAWithdrawRequest());
    assertFalse(cdoEpoch.allowBBWithdrawRequest());
}
```

On a MetaMorpho-style deployment, the drain can equivalently be performed by borrowing idle assets from the vault's underlying markets rather than redeeming attacker-held vault shares. The relevant assertion is unchanged: `convertToAssets` remains at least `pending`, while the external `withdraw` reverts, causing every subsequent `stopEpoch` call to revert in the same state.
