### Title
Stale per-epoch instant-withdraw ledger inflates default recovery basis and freezes recovery claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2024-39481 — where the media graph walk followed every link instead of filtering to `MEDIA_LNK_FL_DATA_LINK` — `IdleCreditVault.claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. The default-recovery path (`defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, `_claimDefaultedInstantWithdrawRequest`) then "walks" those stale entries as if they were still live claims, miscounting already-paid instant withdrawals as default-epoch claim basis and as already-held prefunded reserve.

### Finding Description
In `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) the strategy burns the user's receipt tokens and pays out funded underlying, but `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (set at line 371) and `instantWithdrawClaimsByEpoch[currentEpoch]` (line 372) are never decremented. The only place they are cleared is `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which runs after `finalizeDefaultRecovery`.

At finalization:
- `defaultPendingClaimBasis` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, including receipts that were already fully claimed.
- `_defaultPrefundedInstantReserve` (lines 716-723) adds `instantBasis - pendingInstantWithdraws` to `reserveAmount` (line 686) as supposedly "already-held" underlying — but that portion was already transferred out to claimants, so `defaultRecoveryPrice` (line 688) is inflated above the true ratio.
- `defaultRecoveryEpoch = epochNumber` (line 693), and since `epochNumber` only increments inside `deposit()` during a running epoch (lines 607-610), the defaulted epoch and the stale instant-request epoch coincide.

Two concrete breakages follow:

1. **Inflated recovery price → reserve insolvency.** Claimants through `_claimDefaultedWithdrawRequest`/`_claimPostDefaultWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` are paid `claimBasis * defaultRecoveryPrice` from `defaultRecoveryReserve`. Because the price was computed against phantom prefunded funds, early claimants are overpaid and `defaultRecoveryReserve -= _amount` (line 915) or the token transfer eventually reverts, permanently freezing the remaining claimants' recovery funds in the strategy (no user-facing rescue; `transferToken` is owner-only and does not restore claim accounting).

2. **Permanent freeze of re-requested instant claims.** A user who claims a funded instant receipt in epoch N and then opens a second instant request in the same epoch ends up with `instantWithdrawsRequests[user] = Y` but `instantWithdrawsRequestsByEpoch[user][N] = X + Y`. After default finalization, `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = X + Y` and reverts at `instantWithdrawsRequests[_user] -= claimBasis` (line 848, underflow) or at `_burn` (line 854, insufficient receipt balance — the first X tokens were already burned). Every subsequent claim for that user reverts forever.

### Impact Explanation
Direct theft and permanent freezing of recovery funds. An unprivileged attacker who is an early defaulted-epoch withdraw claimant receives `claimBasis * inflatedPrice`, draining more than their pro-rata share of the real reserve; the deficit is socialized onto later claimants whose claims revert permanently. Quantified example: instant claims of 100k funded and claimed, 50k instant claims unfunded, `pendingInstantWithdraws = 50k`, `instantWithdrawClaimsByEpoch[N] = 150k`. Basis includes the full 150k and reserve is credited with a phantom `150k - 50k = 100k`, inflating `defaultRecoveryPrice` by up to `100k / totalBasis` and leaving an equivalent hole in the reserve. Separately, honest users in scenario (2) lose access to legitimately funded instant claims permanently.

### Likelihood Explanation
Requires a borrower default in the same epoch in which at least one instant withdrawal was already funded and claimed and `pendingInstantWithdraws != 0` — a plausible configuration whenever the CDO partially prefunds the instant queue at `startEpoch`. Triggering needs no privileged cooperation: any tranche holder can `requestInstantWithdraw`, claim once funded, and the stale-ledger effects materialize automatically at `finalizeDefaultRecovery`. No existing guard stops it: `_ensureDefaultRecoveryInitialized` explicitly refuses to clear instant counters, and `_transferFundedClaim`'s reserve check only protects the reserve, not the over-crediting.

### Recommendation
In `claimInstantWithdrawRequest` (and anywhere an instant receipt is paid at par), decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` alongside `instantWithdrawsRequests[_user]`, so that only still-unpaid instant receipts are counted by `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and `_claimDefaultedInstantWithdrawRequest`. Equivalent fix: have the recovery walk skip entries whose aggregate `instantWithdrawsRequests[_user]` portion was already claimed, mirroring the upstream fix of filtering the walk to only valid link types.

### Proof of Concept
Foundry fork PoC sketch (replayable against `test/foundry/IdleCreditVault.t.sol` fixtures):

```solidity
// 1. Start epoch N with borrower funds; users A (attacker) and B deposit AA.
// 2. A calls cdoEpoch.requestInstantWithdraw(amountA, AAtranche);
//    CDO pulls funds -> strategy.collectInstantWithdrawFunds(amountA);
//    pendingInstantWithdraws == 0 afterwards for A's part.
// 3. B calls requestInstantWithdraw(amountB, ...) but stays unfunded:
//    pendingInstantWithdraws == amountB, instantWithdrawClaimsByEpoch[N] == amountA + amountB.
// 4. A calls cdoEpoch.claimInstantWithdrawRequest() -> paid amountA.
//    BUG: instantWithdrawsRequestsByEpoch[A][N] and instantWithdrawClaimsByEpoch[N]
//    still contain amountA.
// 5. Borrower defaults; owner calls finalizeDefault(recovered, source).
//    -> defaultPendingClaimBasis() includes amountA (already paid)
//    -> _defaultPrefundedInstantReserve() adds phantom (amountA+amountB) - amountB = amountA
//    -> defaultRecoveryPrice inflated.
// 6. A defaulted-epoch normal-withdraw claimant C calls claimWithdrawRequest()
//    and is paid claimBasis * inflatedPrice -> overpaid, drains reserve.
// 7. B (or D with postDefaultRequests) calls claimInstant/WithdrawRequest()
//    -> _transferDefaultRecovery reverts (reserve underflow) or transfer fails:
//    permanent freeze of the remaining recovery funds.
// 8. Variant: A re-requested amountA2 instant in epoch N before the default.
//    A's claim reverts at `instantWithdrawsRequests[A] -= (amountA + amountA2)`
//    -> A's funded claim permanently frozen.
```

Assertions to encode: `defaultRecoveryPrice` strictly greater than `realReserve * 1e18 / realBasis`; second claimant's claim reverting; `defaultRecoveryReserve` underflow on the last legitimate claim.
