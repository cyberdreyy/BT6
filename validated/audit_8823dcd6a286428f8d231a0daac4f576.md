### Title
Stale confirmations from a removed-then-re-added member are counted toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` only purges confirmations for requests the removed member originally *created* (`r.member == member`), not confirmations they cast on other members' requests. If that member is re-added later with an identical `MultisigMember` string, their pre-removal confirmation on a still-pending request continues to count toward `num_confirmations` at execution time, even though they never re-confirmed after rejoining.

### Finding Description
The binding that should hold is: confirmations counted for request `R` at execution == confirmations cast by members holding **continuous live membership** through execution. The code instead computes: confirmations counted == entries present in `self.confirmations.get(&request_id)`, a `HashSet<String>` keyed by `member.to_string()`, regardless of whether that member's membership was interrupted.

Path:
1. Member `M` calls `confirm(R)` on some pending request `R` (not created by `M`), inserting `M.to_string()` into `self.confirmations` for `R` — `multisig2/src/lib.rs:311-312`.
2. Governance executes a separate `DeleteMember{member: M}` request. `delete_member` (`multisig2/src/lib.rs:356-379`) removes `M` from `self.members` and purges confirmations only for requests where `r.member == M` (i.e. requests `M` *authored*) at lines 362-371. `R`'s confirmation set still contains `M.to_string()` because `R` was not authored by `M`.
3. Governance executes `AddMember{member: M}`, re-adding the identical `MultisigMember::Account{account_id}` (or `AccessKey`) — `add_member`, `multisig2/src/lib.rs:342-353`. `M.to_string()` serializes identically to before, so it's indistinguishable from a live confirmation.
4. Other members call `confirm(R)`. `confirm` (`multisig2/src/lib.rs:294-315`) checks `confirmations.len() as u32 + 1 >= self.num_confirmations` — the stale entry from `M` is already in that set, so fewer *live, current* confirmations are needed to reach threshold, and `R` executes.
5. `assert_valid_request` (`multisig2/src/lib.rs:407-423`) only validates the *caller* of `confirm`/`delete_request` is a current member; it never re-validates the pre-existing confirmation set against `self.members`.

### Impact Explanation
This lets a request execute with fewer than `num_confirmations` members who held continuous live membership and actually endorsed the request at execution time — matching the Critical category "a multisig request executed below `num_confirmations` live members." Depending on `R`'s actions (e.g. `Transfer`, `AddKey`/`AddMember` granting new access, `FunctionCall`), NEAR or control of the account can move without the required current consent.

### Likelihood Explanation
Requires: (a) `R` pending across a `DeleteMember`/`AddMember` cycle for the same member identity, (b) `M`'s original confirmation on `R` predating removal, (c) governance actually executing the delete+re-add (this requires multisig member/threshold action, not attacker-only) — this weakens applicability, since the removed-then-readded member is itself a former/current multisig member action, not an unprivileged outside attacker forcing it. The scenario is realistic in normal member churn (e.g., temporarily removing a compromised key holder, then reinstating them) where no one thinks to re-confirm already-pending requests.

### Recommendation
When deleting a member, scan `self.confirmations` for all requests (not just ones authored by the member) and strip the member's string from each confirmation set; alternatively, revalidate every confirmation entry against `self.members` at `confirm`-time before counting, discarding stale strings.

### Proof of Concept
`cargo test` in `multisig2`: create contract with members A,B,C,M and `num_confirmations = 3`; A creates `R` (transfer); M calls `confirm(R)` (2 confirmations incl. creator A); execute `DeleteMember{M}` via required confirmations from other members; execute `AddMember{M}` re-adding same `MultisigMember::Account`; then have B call `confirm(R)` — assert `R` executes (`c.requests.len() == 0`) even though only A (creator) and B explicitly confirmed post-readd, i.e., live post-readd confirmations (2) plus stale M entry reach `num_confirmations` (3) without M ever calling `confirm` again after rejoining.     fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
