## Title
Partial-fill withdrawal accounting mismatch during sunset (`TOKENLESS_REPAYMENTS_COMPLETE`) causes user share burn to exceed tokens actually received - ([File: programs/marginfi/src/instructions/marginfi_account/withdraw.rs])

### Summary
`lending_account_withdraw` burns a user's asset shares based on the fully requested `amount_pre_fee` *before* checking whether the bank's liquidity vault actually holds that much liquidity. When the bank is flagged `TOKENLESS_REPAYMENTS_COMPLETE` (the post-bankruptcy/sunset "you get what's left" state), the code subsequently clamps the *transferred* amount down to `min(amount_pre_fee, actual_vault_balance)` — but never re-derives or refunds the share burn to match the clamped transfer. This is the same bug class as Union Finance's AssetManager `withdraw()` (M-12): the accounting layer always assumes the requested amount was fully delivered, even when the actual token transfer is smaller.

### Finding Description
In `lending_account_withdraw`: [1](#0-0) 
the non-`withdraw_all` branch computes `amount_pre_fee` from the user's requested `amount` and calls `bank_account.withdraw(I80F48::from_num(amount_pre_fee))`, which burns/decrements the user's `asset_shares` for the **full requested amount**.

Only after this share deduction has already been committed does the code check the sunset flag and clamp the transfer amount: [2](#0-1) 
```rust
// If in deleverage mode and deleverage is complete, you get what's left!
let amount_pre_fee = if bank.get_flag(TOKENLESS_REPAYMENTS_COMPLETE) {
    let actual = accessor::amount(&bank_liquidity_vault.to_account_info())?;
    ...
    u64::min(amount_pre_fee, actual)
} else {
    amount_pre_fee
};
```
The actual SPL transfer then uses this clamped `amount_pre_fee`: [3](#0-2) 

If `actual < amount_pre_fee` (requested amount) in a **partial** withdrawal (i.e. not `withdraw_all`), the user's shares were already reduced by the value of the full requested amount, but they only receive the smaller `actual` amount in tokens. The difference is permanently lost to the user — exactly mirroring the Union AssetManager pattern where `remaining` funds not actually retrieved are written off because dependent accounting (`staker.stakedAmount`, `accountBorrows`, `totalRedeemable`, etc.) always assumes full delivery.

Unlike the `withdraw_all` path — where `bank_account.withdraw_all()` deliberately zeroes out the full share balance regardless of actual liquidity, and the corresponding e2e sunset test confirms this "close the balance, take what's left" behavior is intentional for full closures — the **partial** withdraw branch has no such intentional write-off design; it simply burns shares proportional to the originally requested amount and then silently short-changes the transfer, with no adjustment to shares or any error, and no event/accounting correction recording the shortfall.

### Impact Explanation
Any user who calls `lending_account_withdraw` with a partial (non-`withdraw_all`) `amount` while the bank is in the `TOKENLESS_REPAYMENTS_COMPLETE` state (post-sunset "tokenless" liquidity-exhausted period) will have their internal share balance reduced by the full requested amount but receive fewer tokens than that if the vault's actual balance is insufficient. This causes a durable, unrecoverable loss of value for that specific depositor — the shortfall is not tracked anywhere and cannot later be reclaimed, matching the "fund freeze / write-down" impact described in the reference finding.

### Likelihood Explanation
This path is only reachable when a bank has already reached the `TOKENLESS_REPAYMENTS_COMPLETE` state, which occurs in the bankruptcy/sunset flow. This is a lower-probability, specific operational state compared to Union's routine liquidity-squeeze condition, but once that state is reached, any unprivileged user calling ordinary `lending_account_withdraw` with a specific (non-`withdraw_all`) amount can trigger the mismatch without any special privilege — it does not require an admin or validator role. The condition is also plausible in exactly the scenario this flag exists for (insufficient vault liquidity after bad-debt write-down), so the shortfall path is not a theoretical edge case but the very case the flag is designed to handle for `withdraw_all` — just not properly handled for partial withdrawals.

### Recommendation
Move the `TOKENLESS_REPAYMENTS_COMPLETE` liquidity check *before* `bank_account.withdraw()` is called in the non-`withdraw_all` branch, and use the clamped `actual` amount (not the originally requested `amount`) as the input to `bank_account.withdraw()`, so that share burn always matches the token amount that will actually be transferred. Alternatively, require that the partial-withdraw path either succeeds in full or reverts entirely when `TOKENLESS_REPAYMENTS_COMPLETE` is set and vault liquidity is insufficient, forcing users to use `withdraw_all` (which already correctly closes the position for whatever is available) instead of a partial amount.

### Proof of Concept
1. Bank `B` enters the sunset/bankruptcy flow and reaches `TOKENLESS_REPAYMENTS_COMPLETE` state (per `guides/ADMIN/BANK_STATE.md` and `zb02_e2eSunset.spec.ts` flow), with its `liquidity_vault` holding less than the sum of all depositors' claims.
2. User `U` holds shares worth `1000` tokens in bank `B`.
3. `U` calls `lending_account_withdraw(amount = 1000, withdraw_all = false)`.
4. At `withdraw.rs:128`, `bank_account.withdraw(I80F48::from_num(1000))` burns shares corresponding to `1000` tokens.
5. At `withdraw.rs:134-144`, suppose `bank_liquidity_vault` actual balance is only `400`; `amount_pre_fee` is clamped to `400`.
6. At `withdraw.rs:178-191`, only `400` tokens are transferred to `U`.
7. `U`'s on-chain shares reflect a full `1000`-token withdrawal, but they only received `400`; the remaining `600` is permanently unaccounted for and unrecoverable through this instruction — matching the write-down described in the Union M-12 report.

Note: I was unable to fully trace all downstream consumers/tests of `TOKENLESS_REPAYMENTS_COMPLETE` (e.g. `purge_delev_balance.rs`, `repay.rs`, `configure_bank_lite.rs`) within the available iterations to confirm whether any compensating mechanism exists elsewhere in the bankruptcy flow to make affected depositors whole; this should be verified against `guides/ADMIN/BANK_STATE.md` and the bankruptcy/sunset test suite before treating this as fully confirmed in production.
