### Title
Inconsistent shell quoting in BashWriter lets `$()`/backtick command substitution slip through unescaped paths - (File: shells/bash.go)

### Summary
`BashWriter` has two different quoting mechanisms: `b.escape()` (backed by `helpers.ShellEscape`/`helpers.PosixShellEscape`), which correctly neutralizes `$`, backticks and other shell metacharacters, and Go's `fmt` `%q` verb, used directly in several `BashWriter` methods that write shell double-quoted strings. Go's `%q` only escapes Go-syntax-significant characters (backslash, double quote, control chars) — it leaves `$`, `` ` ``, `(` and `)` untouched, so when the resulting string is embedded inside a bash double-quoted context it is not neutral data, it is executable shell syntax.

### Finding Description
`BashWriter.IfDirectory`, `IfFile`, `SourceEnv`, `RmFilesRecursive`, and `RmDirsRecursive` build their generated bash lines with `Linef("if [ -d %q ]; then", path)` / `Linef("touch %q", pathname)` / `Linef(`... %q ...`, path, name)` etc., passing the `path`/`name` argument straight to Go's `%q`: [1](#0-0) [2](#0-1) [3](#0-2) 

By contrast, methods that build shell commands from attacker data via `b.Command`, `b.Variable`, `b.ExportRaw`, etc., route the value through `b.escape`, which is `helpers.ShellEscape`/`helpers.PosixShellEscape` — these explicitly treat `$`, backticks, parentheses and quotes as characters that must be escaped or ANSI‑C quoted: [4](#0-3) [5](#0-4) [6](#0-5) 

Go's `%q` format verb only escapes characters that are meaningful in *Go string literal syntax* (backslash, double quote, non-printable control characters); `$`, `` ` ``, `(`, `)` are ordinary printable ASCII and are passed through unchanged. When the resulting `"..."` string is later interpreted by bash (a double-quoted string), bash performs `$var` expansion and `` `cmd` ``/`$(cmd)` command substitution inside double quotes — so any attacker-controlled value fed into `IfDirectory`, `IfFile`, `SourceEnv`, `RmFilesRecursive`, or `RmDirsRecursive` that contains `$(...)` or backticks becomes live shell syntax rather than literal data, breaking the stated invariant that "runner-generated shell commands, env files, temp paths, and cleanup paths must treat attacker text as data, not executable syntax."

These BashWriter methods are called from `shells/abstract.go` while constructing the job script (build/cache/artifact directory checks, git-config/env sourcing, temp-path cleanup), all of which is emitted through `BashShell.GenerateScript` → `generateScript` → `writeScript`: [7](#0-6) 

Paths that reach these calls are built from job/pipeline-controlled configuration such as build directory names derived from the project ref, custom clone paths, and cache/artifact path segments — none of which are restricted from containing `$(`, `` ` ``, or `)`. I was not able to fully trace, within the remaining tool budget, every concrete caller in `shells/abstract.go` that forwards raw, unsanitized user-controlled strings (e.g., `GIT_CLONE_PATH`, ref names, cache key/paths) into `IfDirectory`/`RmFilesRecursive`/`RmDirsRecursive` without prior sanitization elsewhere in the pipeline; this would need to be confirmed with a deeper trace of `abstract.go`'s callers of these specific methods.

### Impact Explanation
If an attacker-controlled string (e.g., a ref name, custom clone path, or cache/artifact path segment) containing `$(...)` or backticks reaches `IfDirectory`, `IfFile`, `SourceEnv`, `RmFilesRecursive`, or `RmDirsRecursive`, the generated bash script executes that payload as a command substitution inside the runner-generated script, executing in the job's shell context (or, for the shell executor, potentially the runner-managed host user context) — i.e., stronger-context command execution beyond what the pipeline author's script content should be able to do implicitly through path/config fields.

### Likelihood Explanation
The precondition is that some job-configurable value (ref name, custom path, cache key/paths, etc.) is passed unescaped through one of the affected `%q`-based `BashWriter` methods. The quoting bug itself is confirmed directly from source: `%q` and `b.escape` are demonstrably different sanitization routines, and the affected methods bypass the shell-safe one. Full exploitability depends on finding a concrete attacker-reachable value flowing into one of these calls, which requires further tracing of `shells/abstract.go` callers that I could not complete with certainty in the available iterations.

### Recommendation
Route the `path`/`name` arguments in `IfDirectory`, `IfFile`, `SourceEnv`, `RmFilesRecursive`, and `RmDirsRecursive` through `b.escape` (or an equivalent shell-safe quoting function) instead of Go's `%q`, so that `$`, backticks, and parentheses are neutralized the same way they are for `Command`/`Variable`/`ExportRaw`. Audit all `Linef`/`Line` call sites in `shells/bash.go` (and the analogous PowerShell writer) for use of `%q` or other non-shell-aware quoting on any value that can originate from job/pipeline configuration.

### Proof of Concept
Go unit test idea in `shells/bash_test.go`:
1. Construct a `BashWriter` and call `w.IfDirectory("$(touch /tmp/pwned)")`.
2. Assert that the generated line is `if [ -d $'$(touch /tmp/pwned)' ]; then` (ANSI‑C quoted, literal) rather than `if [ -d "$(touch /tmp/pwned)" ]; then` (which bash would execute).
3. Optionally, feed the generated script into an actual `bash` subprocess with a sentinel file check to confirm whether `/tmp/pwned` is created — before the fix it is created (proving execution), after the fix it is not.

func (b *BashWriter) RmFilesRecursive(path string, name string) {
	b.IfDirectory(path)
	// `find -delete` is not portable; https://unix.stackexchange.com/a/194348
	// The '+' `find -exec` terminator is the default as it performs less invocations on supported systems.
	//   Other systems (e.g. z/OS) will use the ';' terminator when the initial 'test find' command fails, causing `$et` to be updated.
	//   The intitial `test find` command is used to prevent undesirable stderr output from a failed execution using the `+` terminator.
	b.Linef(`et='+' ; find /dev/null -exec true {} + 2>/dev/null || et=';' ; find %q -name %q -type f -exec rm -f {} "${et}"`, path, name)
	b.EndIf()
}

func (b *BashWriter) RmDirsRecursive(path string, name string) {
	b.IfDirectory(path)
	// `find -delete` is not portable; https://unix.stackexchange.com/a/194348
	// The '+' `find -exec` terminator is the default as it performs less invocations on supported systems.
	//   Other systems (e.g. z/OS) will use the ';' terminator when the initial 'test find' command fails, causing `$et` to be updated.
	//   The intitial `test find` command is used to prevent undesirable stderr output from a failed execution using the `+` terminator.
	b.Linef(`et='+' ; find /dev/null -exec true {} + 2>/dev/null || et=';' ; find %q -name %q -type d -depth -exec rm -rf -- {} "${et}"`, path, name)
	b.EndIf()
}
