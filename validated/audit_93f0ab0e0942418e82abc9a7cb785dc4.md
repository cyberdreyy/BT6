### Title
Instant-withdraw receipts from a prior epoch are permanently unclaimable after default finalization - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`finalizeDefaultRecovery` builds the defaulted instant-withdraw claim basis using only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch's bucket — gated solely on `pendingInstantWithdraws != 0`. If an instant-withdraw request was made in an earlier epoch and remained partially unfunded across an epoch transition, its claim is not included in `defaultPendingClaimBasis`, yet `defaultInstantWithdrawsFinalized` is set to `true`. The affected user can never clear their receipt (the defaulted path only inspects `defaultRecoveryEpoch`, and the funded path reverts against the isolated recovery reserve), permanently freezing their claim while the leftover reserve is overpaid to other claimants. This is the direct analog of the Y2K M-4 bug: value allocated to a bucket that no claim path can ever reach.

### Finding Description
- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` only when `pendingInstantWithdraws != 0` [1](#0-0) . `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` are keyed by the *request* epoch [2](#0-1) , but `pendingInstantWithdraws` is a global that survives epoch transitions via partial funding in `collectInstantWithdrawFunds` [3](#0-2) .
- On default in a later epoch, `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount / totalBasis` where `totalBasis` excludes the stale instant claim, then sets `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` = true [4](#0-3) .
- When the victim calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` which is 0 for their old-epoch receipt, so nothing is cleared and `pendingInstantWithdraws` stays non-zero [5](#0-4) . Execution then falls through to the funded path: `_burn(_user, amount)` and `_transferFundedClaim`, which reverts with `NotAllowed` whenever paying the claim would dip into `defaultRecoveryReserve` [6](#0-5) [7](#0-6) .
- The reserve itself was sized excluding the victim's basis, so even ignoring the revert there is no allocation for them — equivalent to emissions locked on a nullified epoch: accounted in the pending counter, absent from every reachable claim basis.

### Impact Explanation
Permanent freezing of the victim's instant-withdraw receipt (its full underlying value) and a permanently stuck `pendingInstantWithdraws` remainder. The overpriced `defaultRecoveryPrice` also misallocates the reserve to other claimants (recovery above their fair pro-rata share), an implicit transfer of the frozen claim's value. Loss equals the carried-over unfunded instant claim amount.

### Likelihood Explanation
Requires (a) an instant withdraw only partially funded at epoch start — explicitly contemplated by `_defaultPrefundedInstantReserve`'s "still-unfunded remainder" logic [8](#0-7) , (b) an epoch rollover while the remainder persists, and (c) borrower default. All steps sequence around honest privileged calls only; the unprivileged user just holds a receipt. Caveat: if `pendingInstantWithdraws` can never survive a normal `stopEpoch`/epoch increment in practice (i.e., the queue always fully funds or clears it), the stale-epoch state is unreachable — the PoC must first demonstrate carry-over.

### Recommendation
Include unfunded instant claims from *all* epochs in `defaultPendingClaimBasis` (e.g., track a global `totalInstantClaims` rather than `instantWithdrawClaimsByEpoch[epochNumber]`, or carry stale per-epoch buckets forward), and make `_claimDefaultedInstantWithdrawRequest` settle any epoch ≤ `defaultRecoveryEpoch`, clearing `pendingInstantWithdraws` accordingly.

### Proof of Concept
Foundry fork PoC sketch (mirror `testFinalizeDefaultHaircutsPendingInstantRedeems` in `test/foundry/IdleCreditVault.t.sol`):
1. Deposit via AA tranche; enable instant withdraws; user calls `requestInstantWithdraw(X)`.
2. At `startEpoch`, arrange `collectInstantWithdrawFunds` to pull only `X/2` (partial funding) so `pendingInstantWithdraws == X/2`.
3. Let the epoch end normally (`stopEpoch`), incrementing `epochNumber`; `instantWithdrawClaimsByEpoch[N] == X`, new epoch bucket = 0.
4. Trigger borrower default in epoch N+1 (`_checkDefault`), then `finalizeDefault(recovered, src)`.
5. Assert `defaultInstantWithdrawsFinalized == true` while `instantWithdrawClaimsByEpoch[N+1] == 0` → victim's basis excluded.
6. `vm.prank(user); cdoEpoch.claimInstantWithdrawRequest()` → reverts `NotAllowed` in `_transferFundedClaim` (or pays 0); `pendingInstantWithdraws` remains `X/2` forever.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;

      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
```
