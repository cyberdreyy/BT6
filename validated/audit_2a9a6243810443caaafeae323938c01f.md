### Title
`depositDuringEpoch` and `writeOffDeposit` credit nominal `_amount` instead of actual received balance — FoT/rebase underlyings mint unbacked tranche shares and inflate expected epoch interest - (contracts/IdleCDOEpochVariant.sol)

### Summary
The external bug class is "vault credits the requested amount instead of the balance delta after `transferFrom`, breaking accounting for fee-on-transfer/rebase tokens." The direct-deposit path in this codebase was already fixed for this (`_deposit` mints on `_contractTokenBalance(_token) - _preBal`), but the mid-epoch deposit path `depositDuringEpoch` and the write-off fulfillment path `fullfillWriteOffRequest`/`writeOffDeposit` still use the nominal `_amount` everywhere after pulling tokens. If the vault's underlying charges a transfer fee or rebases, shares, `expectedEpochInterest`, strategy-token minting and the borrower transfer are all denominated in more tokens than were actually received — a solvency/fair-mint break, not just a UI issue.

### Finding Description
In `IdleCDOEpochVariant._deposit` (the pre-epoch deposit flow), the code correctly measures the received delta:

- `IdleCDOCreditVault._deposit` records `uint256 _preBal = _contractTokenBalance(_token)` before `_transferUnderlyingsFrom(...)` and mints on `_contractTokenBalance(_token) - _preBal`.

The same contract's epoch-running deposit path does not:

```solidity
// contracts/IdleCDOEpochVariant.sol:684-732
_transferUnderlyingsFrom(msg.sender, address(this), _amount);   // received may be < _amount
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;  // uses nominal _amount
_mintShares(_tranche, msg.sender, _minted, _amount);
expectedEpochInterest += interest;                              // interest on nominal _amount
IdleCreditVault(strategy).mintStrategyTokens(_amount);          // strategy tokens for nominal _amount
_transferUnderlyings(_borrower(), _amount);                     // sends out nominal _amount
```

Every downstream accounting step uses the caller-supplied `_amount`:

1. `_minted` is priced as if the full `_amount` entered the pool — the depositor is minted principal-plus-prorated-interest shares on tokens that never arrived.
2. `expectedEpochInterest += interest` books interest on the nominal amount, inflating the expected interest used at `stopEpoch` to compute tranche prices.
3. `mintStrategyTokens(_amount)` and `_transferUnderlyings(_borrower(), _amount)` push the nominal amount to the borrower/strategy; with a FoT token the vault either transfers out tokens belonging to existing depositors (direct theft of prior NAV) or reverts, making `depositDuringEpoch` unusable.

The same nominal-amount pattern exists in the write-off surface:

- `IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` (`contracts/IdleCreditVaultWriteOffEscrow.sol:139-149`) pulls `_underlyings`, then computes `_totFee` on the nominal amount and does `underlyingToken.safeTransfer(_user, _underlyings - _totFee)`. With a FoT underlying the escrow received less than `_underlyings`, so the payout to the lender either reverts (request permanently stuck; the lender's tranches are already escrowed) or is subsidized by the contract's balance.
- `writeOffDeposit` in `IdleCDOEpochVariant` similarly burns tranches/credits the nominal underlying amount when the borrower writes off debt, overstating the debt reduction for a FoT underlying.

This is gated by: epoch running, `block.timestamp < epochEndDate`, `isDepositDuringEpochDisabled == false` (owner flag, enabled in normal operation for fixed-APR vaults), `!isAYSActive`, `!isProgrammableBorrower`, `!skipDefaultCheck`, tranche supply > 0, and `isWalletAllowed(msg.sender)` — i.e., only a KYC-passing lender, which is an in-scope attacker. None of the existing guards help: `_skimDonatedAssets` runs before the pull (so it does not correct for the shortfall), `_guarded`/`_updateAccounting` operate on the nominal amount, and the balance-delta protection that exists in `_deposit` was simply not replicated here.

### Impact Explanation
Insolvency / unfair mint. An attacker depositing `_amount` of a FoT underlying (fee `f`) receives tranche shares and booked interest worth `_amount + trancheInterest`, while the pool's NAV only grows by `_amount * (1 - f)`. Worse, the vault immediately forwards the full `_amount` to the borrower and mints `_amount` of strategy tokens — the `f * _amount` shortfall is paid out of existing depositors' NAV. Repeating deposits scales the theft linearly; at epoch end `stopEpoch` distributes `expectedEpochInterest` that was inflated by interest computed on phantom principal, further diluting honest tranche holders. On the write-off path, the borrower reduces debt by the nominal `_underlyings` while the lender/escrow absorbs the fee, or fulfillment reverts and the lender's escrowed tranche tokens are frozen.

### Likelihood Explanation
Requires the vault underlying to be a fee-on-transfer or balance-decreasing rebase token. The vaults are per-underlying deployments, so this is conditional on onboarding such a token — the same assumption under which the original Blueberry report was accepted as Medium (their vaults likewise whitelisted tokens). Within that assumption the exploit is deterministic, permissionless to any whitelisted lender during a running epoch, and repeatable. No privileged action is needed; the owner enabling `isDepositDuringEpochDisabled = false` is the normal operating mode for fixed-APR vaults.

### Recommendation
In `depositDuringEpoch` (and the analogous prefunded/`writeOffDeposit` paths), measure the received amount and use it everywhere:

```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_amount = _contractTokenBalance(token) - _preBal;
if (_amount == 0) return 0;
```

Then compute `interest`, `trancheInterest`, `_minted`, `expectedEpochInterest`, `mintStrategyTokens` and the borrower transfer on the received `_amount`. In `IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest`, take `_underlyings = balanceAfter - balanceBefore` before computing `_totFee` and the lender payout. Alternatively, document that FoT/rebase underlyings are unsupported and enforce it at deployment.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

/// Minimal FoT token (1% burn on transfer) standing in for the vault underlying.
contract FoTToken is IERC20Detailed /* simplified for PoC */ {
    // standard ERC20 with _transfer burning 1% of amount
}

contract FoTMidEpochDepositTest is Test {
    IdleCDOEpochVariant cdo;
    IdleCreditVault strategy;
    FoTToken fot;
    address AAtranche;
    address borrower = address(0xB0);
    address owner = address(this);
    address manager = address(0xM);
    address honest = address(0xH);
    address attacker = makeAddr("kycAttacker"); // passes isWalletAllowed

    function setUp() public {
        // deploy vault with `fot` as `token`, AA/BB tranches, borrower = borrower
        // whitelist honest + attacker in KeyringIdleWhitelist
        // honest deposits 10_000e18 via depositAA (pre-epoch)
        // manager: setEpochParams(365 days, 0); strategy.setAprs(10e18, 10e18)
        // startEpoch(); warp to mid-epoch; owner: setIsDepositDuringEpochDisabled(false)
    }

    function testFoTMidEpochDepositInflatesShares() public {
        uint256 amount = 1_000e18;
        fot.mint(attacker, amount);
        vm.startPrank(attacker);
        fot.approve(address(cdo), amount);
        uint256 minted = cdo.depositDuringEpoch(amount, AAtranche);
        vm.stopPrank();

        // vault received only 990e18 (1% FoT), but:
        // - attacker minted shares priced on 1000e18 + prorated interest
        // - expectedEpochInterest grew by interest on the full 1000e18
        // - strategy.mintStrategyTokens(1000e18) and 1000e18 forwarded to borrower
        uint256 vaultReceived = 990e18;
        uint256 attackerValue = minted * cdo.virtualPrice(AAtranche) / 1e18;
        assertGt(attackerValue, vaultReceived, "attacker credited more than delivered");
        // borrower was sent `amount`, i.e. 10e18 came out of honest depositors' NAV
        assertEq(fot.balanceOf(borrower), amount * 99 / 100 /*minus FoT on that leg*/);
        // honest NAV at epoch end is reduced by the shortfall + inflated expectedEpochInterest
    }
}
```

Notes on confidence: I verified the balance-delta protection in `_deposit` (both `IdleCDO` and `IdleCDOCreditVault`) and the nominal-amount usage in `depositDuringEpoch` (lines 685–732) and `fullfillWriteOffRequest` (lines 139–149). I did not fully read `writeOffDeposit`'s body in `IdleCDOEpochVariant`; it is referenced by the escrow as the borrower's burn path and should be confirmed to apply the same fix.
