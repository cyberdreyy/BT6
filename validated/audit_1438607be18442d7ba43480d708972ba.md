### Title
Unsynchronized concurrent writes to the shared build trace allow build/service container log bytes to interleave — (File: `common/buildlogger/build_logger.go`, `executors/kubernetes/kubernetes.go`)

### Summary
`runInContainerWithExec` streams the build container's stdout/stderr through a `Logger.Stream()`-derived writer while `captureContainerLogs`/`captureServiceContainersLogs` concurrently stream service-container logs through *separate* `Logger.Stream()` instances into the same underlying trace (`l.base`). Because `Logger.wrap()` creates a brand-new `sync.Mutex` (via `internal.NewSync`) for every `Stream()` call instead of sharing one mutex over the common base writer, concurrent writers from different containers are not mutually exclusive at the point where they actually touch the shared trace.

### Finding Description
`runInContainerWithExec` (`executors/kubernetes/kubernetes.go:3280-3311`) is fed `stdout, stderr` obtained from `s.getExecutorIoWriters()`, which are built from `BuildLogger.Stream(...)`. In parallel, service log capture (`executors/kubernetes/kubernetes.go:3491-3517`, `executors/docker/services.go:338-366`) obtains its own, independent `Stream()` writer per service via `s.BuildLogger.Stream(buildlogger.StreamStartingServiceLevel, buildlogger.Stdout)` and wraps it in `service_helpers.InlineServiceLogWriter` [1](#0-0) , which itself issues **three separate, non-atomic `Write()` calls per line** (prefix, body, suffix).

Each call to `Logger.Stream()`/`Logger.wrap()` constructs an entirely new processing chain (masker → urlsanitizer → tokensanitizer → timestamper) and wraps it with a **new** `internal.NewSync` mutex: [2](#0-1) 
This mutex only serializes writes made through that one `Stream()` instance; it does not provide mutual exclusion against a different `Stream()` instance (e.g. the build-container stream vs. a service-container stream, or service A's stream vs. service B's stream) that ultimately writes to the same shared `l.base` writer. Since the build script's stdout copy loop (from `exec.Run` inside `runInContainerWithExec`) and each service's async log-tailing goroutine run concurrently and independently, and each performs multiple discrete physical writes down to `l.base` for what is logically one "line" of output, there is no single point of synchronization guaranteeing that one container's bytes are fully flushed before another's are interleaved.

Attacker-controlled inputs that make this reachable by an unprivileged pipeline author:
- Defining one or more `services:` in `.gitlab-ci.yml` with `CI_DEBUG_SERVICES` enabled, causing concurrent service log streaming alongside the build script's `runInContainerWithExec` execution.
- Job script/service output timing/volume, which an attacker can tune to maximize the race window between the prefix/body/suffix writes in `InlineServiceLogWriter.Write` and the build stream's writes.

Existing protections (masking via `masker.New`, `tokensanitizer`, `urlsanitizer`) operate *inside* each stream's own chain, before the interleaving point, so a secret fully captured within one `Write()` call to one stream is still masked correctly in isolation. This limits — but does not eliminate — the risk to "secret exposure": masking correctness is not directly defeated for values that arrive as a single call within one stream, but the underlying invariant "log output must preserve exact container ownership" is broken regardless, since interleaved prefix/body/suffix or output chunks from a different container can be spliced into the middle of another container's segment.

### Impact Explanation
The primary concrete, reproducible impact is **log integrity/output tampering**: build-container and service-container log bytes can be interleaved at a sub-line granularity in the job trace, corrupting the displayed origin of log lines (`[service:X]` framing) and potentially confusing log consumers/automation that parse job traces by container ownership. Whether this rises to full "secret exposure" depends on whether a secret payload gets split across multiple physical `Write()` calls within a single stream (plausible for large/buffered output, e.g. long lines from `remotecommand` exec streaming), which I could not conclusively verify without inspecting `common/trace.go`'s `Write` implementation and `internal/sync.go`'s exact locking semantics (not fully confirmed in this review).

### Likelihood Explanation
This requires only an unprivileged pipeline author to define concurrently-running services (with `CI_DEBUG_SERVICES` on) alongside a build script — a fully standard, unprivileged CI configuration. The race window is timing-dependent (both writers must be active concurrently and hit `l.base` interleaved), making exploitation probabilistic rather than deterministic, but readily reproducible under load/stress with high-throughput log output on both sides.

### Recommendation
Share a single mutex across all `Stream()`-derived writers that ultimately write to the same `Logger.base`, rather than constructing a fresh `sync.Mutex` per `Stream()` call in `Logger.wrap()`. E.g., move the `internal.NewSync` wrapping to guard `l.base` itself (one shared instance stored on `Logger`), so that all concurrently-produced stream chains (build, helper, and each service) serialize their final writes against a common lock, guaranteeing that a full line/log unit from one container is written atomically before another can interleave.

### Proof of Concept
Go unit test in `common/buildlogger`:
1. Construct a `Logger` with a `Trace` backed by a `bytes.Buffer` (or the existing `trace.New()` test helper).
2. Obtain two `Stream()` writers (`s1 := l.Stream(StreamWorkLevel, Stdout)`; `s2 := l.Stream(StreamStartingServiceLevel, Stdout)`).
3. From two goroutines, repeatedly write distinct, easily-identifiable markers of substantial length (e.g. `strings.Repeat("A", 4096)+"\n"` from goroutine 1, `strings.Repeat("B", 4096)+"\n"` from goroutine 2) many times concurrently.
4. After both goroutines finish, parse the buffer and assert that every output line is either entirely `A`s or entirely `B`s (i.e., `assert.False(t, strings.Contains(line, "A") && strings.Contains(line, "B"))` for every line).
5. Expected failure: some lines contain a mix of `A` and `B` bytes, demonstrating that writes from the two `Stream()` instances are not mutually exclusive at the shared base writer.

func (sw *InlineServiceLogWriter) Write(p []byte) (int, error) {
	n := 0

	for n < len(p) {
		end := bytes.IndexByte(p[n:], '\n')
		if end < 0 {
			end = len(p[n:])
		}

		if _, err := sw.sink.Write(sw.prefix); err != nil {
			return n, err
		}

		nn, err := sw.sink.Write(p[n : n+end])
		n += nn
		if len(p[n:]) > 0 && err == nil {
			n++
		}
		if err != nil {
			return n, err
		}

		if _, err := sw.sink.Write(sw.suffix); err != nil {
			return n, err
		}
	}

	return n, nil
}

// wrap wraps the underlying writer with "filters". Order here somewhat
// matters, and the order they're instantiated in is the reverse order in which
// writes are processed, e.g. last added filter is the first to process data.
//
// order:
// - sync writer to ensure that multiple writes cannot happen concurrently
// - mask phrases (masker.New)
// - mask sensitive URL parameters (urlsanitizer.New)
// - mask secrets with a prefixed token (tokentanitizer.New)
// - split log lines and add timestamps (timestamper.New)
func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
	if l.timestamping {
		w = timestamper.New(w, timestamper.StreamType(streamType), uint8(streamID), true)
	}

	w = tokensanitizer.New(w, l.maskTokenPrefixes)
	w = urlsanitizer.New(w)
	w = masker.New(w, l.maskPhrases)
	w = internal.NewSync(w)

	return w
}
