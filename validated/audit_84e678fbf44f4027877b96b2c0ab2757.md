### Title
Loss-adjusted withdraw receipts redeem at par because `lossRecoveryPriceByEpoch` is keyed to the post-stop `epochNumber` while claims look up the request epoch - (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
When `stopEpochWithDuration` realizes a loss, `IdleCreditVault.collectWithdrawFunds` stores the haircut in `lossRecoveryPriceByEpoch[epochNumber]` using the already-incremented epoch counter, but `_claimLossAdjustedWithdrawRequest` (and the re-request guard in `requestWithdraw`) look the price up under `lastWithdrawRequest[_user]`, which still holds the epoch in which the request was made. The haircut is therefore never applied: the loss-adjusted receipt falls through to `_claimFundedWithdrawRequest` and is paid at full par even though the borrower only funded `pendingToFund < pendingBasis`. This mirrors the CVE bug class (a stale/misleading state presented during a transition): the claim path reads an epoch marker that no longer reflects the epoch where the loss was recorded.

### Finding Description
The lifecycle is:

1. During a running epoch/buffer (strategy `epochNumber == N`), a lender calls `IdleCDOEpochVariant.requestWithdraw`, which calls `IdleCreditVault.requestWithdraw`. It stores `lastWithdrawRequest[_user] = N`, `withdrawsRequestsByEpoch[_user][N] += amount`, `withdrawsRequests[_user] += amount`, and `pendingWithdraws += amount` (`IdleCreditVault.sol:260-294`).
2. The manager stops the epoch with a loss via `stopEpochWithDuration(_interest, _apr, _duration, _lossAmount)`. Inside `IdleCDOEpochVariant._afterStopEpochWithDuration`, `this.getFundsFromBorrower(...)` is executed first (line 408); the deposit into the strategy performed there runs while `isEpochRunning` is still true, so `IdleCreditVault.deposit` executes `epochNumber += 1` (`IdleCreditVault.sol:607-610`), moving the counter to `N+1`.
3. Immediately after, `_strategy.collectWithdrawFunds(_pendingWithdraws)` is called (line 410). Because `_amount < pendingBasis`, it computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis`, zeroes `pendingWithdraws`, and stores `lossRecoveryPriceByEpoch[epochNumber]` — i.e. under `N+1`, not `N` (`IdleCreditVault.sol:411-430`). Only `pendingToFund = pendingBasis - pendingLoss` underlying was transferred into the strategy.
4. The user claims through `IdleCDOEpochVariant.claimWithdrawRequest` → `IdleCreditVault.claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user] = N` and finds `lossRecoveryPriceByEpoch[N] == 0`, so it returns 0 (`IdleCreditVault.sol:789-795`). `_claimFundedWithdrawRequest` then passes its gate (`epochNumber (N+1) > lastWithdrawRequest (N)`, `IdleCreditVault.sol:326`) and pays `withdrawsRequests[_user]` in full via `_transferFundedClaim`.

The same wrong key defeats the guard in `requestWithdraw` (`IdleCreditVault.sol:261-271`), which is supposed to force a user to claim a loss-adjusted receipt before opening a new one: since `lossRecoveryPriceByEpoch[N]` reads 0, the guard never triggers.

Note: the bug is in the key used at *claim* time, not at storage time. The fix must reconcile `lastWithdrawRequest`/per-epoch receipt data with the post-increment `epochNumber` used when the loss price is written. A consistent alternative is to store `lossRecoveryPriceByEpoch` under the epoch that pending receipts were actually requested in (the pre-increment counter).

### Impact Explanation
Direct theft / insolvency of the strategy's funded withdraw pool. When a `stopEpochWithDuration` loss is realized, only `pendingToFund` underlyings are held against an aggregate receipt basis of `pendingBasis`. Each claimer nevertheless receives the un-haircutted `claimBasis`. Early claimers withdraw more than their pro-rata share and drain the strategy balance, so the last claimers' funded receipts are left unbacked (permanent loss of up to the full pending-loss portion per claimant, and revert-DoS on subsequent claims once the balance is exhausted). Example: `pendingBasis = 100`, funded `80` (20% loss) — the first claimer with a 50 receipt takes 50 instead of 40; remaining claimers share only 30 against a 50 basis.

### Likelihood Explanation
Requires only the ordinary, intended `stopEpochWithDuration` loss flow (manager is honest and supplies a legitimate `_lossAmount`) plus a user with a pending normal withdraw receipt — no privileged misbehavior, no oracle manipulation. Any partial repayment by the borrower short of `pendingWithdraws` triggers it. Attacker is a regular KYC'd lender/tranche holder, in scope.

### Recommendation
Key the loss-adjusted claim consistently with the stored epoch. Either:
- in `collectWithdrawFunds`, write `lossRecoveryPriceByEpoch[epochNumber - 1]` (the epoch receipts were requested under, given `deposit` increments the counter earlier in the same `stopEpoch`), or
- in `_claimLossAdjustedWithdrawRequest` and the `requestWithdraw` guard, look up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user] + 1]` and clear `withdrawsRequestsByEpoch`/`apr0Users` for the request epoch while applying the price stored for the settlement epoch.

Add a fork test: request in epoch N, `stopEpochWithDuration` with partial funding, assert `claimWithdrawRequest` pays `claimBasis * lossRecoveryPrice / 1e18` and that a second `requestWithdraw` before claiming reverts.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (IdleCreditVault loss-adjusted claim pays par)
// Setup: epoch variant CDO + IdleCreditVault strategy, user FASA holds AA tranches.

// 1) Epoch running/buffer, strategy.epochNumber() == N
cdoEpoch.requestWithdraw(ONE_TRANCHE, address(tranche)); // lastWithdrawRequest[FASA] = N
assertEq(strategy.lastWithdrawRequest(FASA), N);
assertEq(strategy.withdrawsRequestsByEpoch(FASA, N), expectedBasis);

// 2) Manager stops epoch with a loss; borrower funds only pendingToFund < pendingBasis
(uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
deal(address(underlying), strategy.borrower(), repay, true);
vm.prank(strategy.borrower());
underlying.approve(address(cdoEpoch), repay);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(10e18, 0, duration, lossAmount);

// strategy.epochNumber() is now N+1; haircut stored under N+1
assertEq(strategy.epochNumber(), N + 1);
assertGt(strategy.lossRecoveryPriceByEpoch(N + 1), 0);
assertEq(strategy.lossRecoveryPriceByEpoch(N), 0); // claim lookup key -> miss

// 3) User claims: receives full par instead of haircutted amount
uint256 balBefore = underlying.balanceOf(FASA);
vm.prank(FASA);
cdoEpoch.claimWithdrawRequest();
uint256 got = underlying.balanceOf(FASA) - balBefore;
assertEq(got, expectedBasis); // BUG: should be expectedBasis * lossRecoveryPrice / 1e18
// Strategy now underfunded for remaining receipts -> insolvency for later claimers.
```
