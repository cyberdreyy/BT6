Based on the investigation, I found a concrete analog: the `RequestReplayGuard.CheckAndRecord` is keyed purely by the on-chain `requestDigest` (a hash of the JSON-RPC request), which is public information that any unprivileged actor can read from the `WorkflowRegistry` allowlist before the legitimate request is submitted to the gateway.

### Title
Griefing DoS via digest-based replay guard front-running in vault Authorizer - (File: `core/capabilities/vault/authorizer.go`)

### Summary
`allowListBasedAuth.AuthorizeRequest` computes `requestDigest` from the incoming JSON-RPC request and matches it against `WorkflowRegistryOwnerAllowlistedRequest` entries fetched from on-chain state [1](#0-0) . Once a match is found, `authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())`, which permanently consumes that digest until expiry, rejecting any subsequent request with the same digest with `ErrRequestAlreadySeen` [2](#0-1) [3](#0-2) .

### Finding Description
The `AllowlistRequest` transaction that stores `(requestDigest, expiryTimestamp)` on the `WorkflowRegistry` contract is public on-chain data [4](#0-3) . Any unprivileged actor observing this on-chain event (or via `GetAllowlistedRequests`) learns the exact 32-byte digest before the corresponding gateway request is submitted. If that same digest can then be replayed to the gateway node (e.g., by racing the legitimate submission with a copy of the JSON-RPC envelope, or via a gateway relay retry path), the first successful `CheckAndRecord` call wins and permanently marks the digest as seen for the lifetime of `expiresAt`. The digest is derived only from the request's own content via `req.Digest()`, not bound to a specific transport connection or requester identity beyond what's embedded in the request itself, so if an attacker can reconstruct the same digest input (e.g., replaying the exact bytes intercepted on the wire, since HTTP responses/requests in this flow are not end-to-end encrypted against a network observer) they can trivially cause the legitimate user's subsequent identical request to fail with "request was already authorized previously" — a direct, mechanical analog of the reported bug class: an unprivileged actor manipulates a piece of shared, equality-keyed state (there: token balance; here: digest-seen map) to force a legitimate operation into an unconditional revert/error path.

### Impact Explanation
This is a griefing/DoS vector against the vault gateway's Create/Update/Delete/List secret flow: a legitimate workflow owner's authorized, allowlisted request can be made to unconditionally fail once an attacker races or replays the observed digest, even though the attacker gains no data access (secrets require decryption bound to the owner's public key) and cannot itself pass the subsequent `validateSecretOwnersMatchAuthorized` step. The impact is limited to availability (blocking legitimate vault operations for the `expiresAt` window), not confidentiality or fund loss.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires the attacker to observe the request digest (feasible, since it's stored on public chain state or observable in gateway traffic) and race/replay it to a gateway node before the legitimate request lands, within retry windows (`allowListBasedAuthRetryCount`/`allowListBasedAuthRetryInterval` of ~30s) [5](#0-4) . This is speculative without confirming exact transport-layer protections (e.g., whether gateway-to-node channels are authenticated per-sender in a way that would block digest replay by a different sender) — I was not able to fully trace whether `req.Auth`/session binding prevents an unprivileged third party from submitting an arbitrary request with a copied digest to the gateway's `HandleJSONRPCUserMessage` path.

### Recommendation
Bind the replay-guard key to both the digest and the authenticated requester context (e.g., include a per-connection/session token or the JWT/session identity when hashing the replay key), or scope `CheckAndRecord` per-owner rather than globally, so that an observer of the public on-chain digest cannot pre-empt a legitimate submitter's own request.

### Proof of Concept
1. Workflow owner calls `AllowlistRequest(digest, expiry)` on `WorkflowRegistry` (public tx) [6](#0-5) .
2. Attacker observes `digest` from the mempool/chain state via `GetAllowlistedRequests`.
3. Attacker submits (or replays a sniffed copy of) a JSON-RPC request that hashes to the same `digest` to the gateway node before the legitimate client does.
4. `allowListBasedAuth.AuthorizeRequest` matches the allowlisted entry and `replayGuard.CheckAndRecord` records the digest [7](#0-6) .
5. The legitimate client's subsequent identical request is rejected with `ErrRequestAlreadySeen` until `expiresAt`, denying the owner's vault operation.

**Note:** I was not able to fully verify from the indexed code whether the gateway's ingress path cryptographically binds requests to a specific sender before reaching `AuthorizeRequest` (which would fully block this class of replay). This uncertainty should be resolved by a full review of the gateway ingress/session code, potentially in a Devin session with full repository access.

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```
