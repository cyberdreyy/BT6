## Title
Deleting a multisig member does not purge their stale confirmations from other pending requests, allowing execution below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`, also present in `multisig/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only removes pending requests (and their confirmation sets) that were **originally submitted** by the member being deleted. It never scans the `confirmations` set of *other* still-pending requests to strip out a confirmation the deleted member may have cast as a co-signer. Because `confirm()` counts `confirmations.len()` directly against `num_confirmations` without re-validating that every entry in the set is still a current member, a request can later be executed with fewer live, currently-authorized confirmers than `num_confirmations` requires — the confirmation count and the set of confirming live members silently diverge.

### Finding Description
`confirm()` compares the raw stored confirmation count to the threshold and executes once it is reached: [1](#0-0) 

`delete_member()` only cleans up requests whose *original submitter* (`r.member`) is the member being removed; it does not touch the `confirmations` `HashSet<String>` of any request that the deleted member merely co-signed as a confirmer: [2](#0-1) 

The correct invariant the contract needs to maintain is:

```
count(confirmations for request R) == count(distinct *current* members who confirmed R)
```

`delete_member` breaks this equality: a confirmation cast by a member who is later deleted remains recorded in `confirmations`, so `confirmations.len()` overstates the number of currently-authorized approvers for that request. The identical pattern exists in the older `multisig` contract's `DeleteKey` action, which likewise only purges requests originally signed by the removed key: [3](#0-2) 

### Impact Explanation
This is a threshold-authorization bypass: a `MultiSigRequest` (e.g. `Transfer`, `AddKey`, `FunctionCall`) can be executed via `execute_request` while the number of *currently valid* members who actually approved it is strictly less than `num_confirmations`. This matches the "multisig request executed below threshold" Critical impact category — funds or privileged actions (adding an access key, deploying a contract, transferring NEAR) can be authorized by fewer live signers than the configured security threshold, undermining the entire multisig custody guarantee.

### Likelihood Explanation
No malicious insider collusion is strictly required beyond normal multisig operation: any member who is removed (voluntarily or via governance) after having confirmed a pending request leaves a live stale confirmation behind. Any remaining member submitting/confirming the same still-open request will unknowingly benefit from (or could deliberately exploit) the stale count to push a request through with one fewer live confirmer than intended. This is a straightforward two-request sequence achievable by members who are already permitted to call `add_request`/`confirm`/execute `DeleteMember`, well within an "unprivileged" (i.e., a single legitimate member, not the full quorum) attacker's reach for this scenario.

### Recommendation
When deleting a member in `delete_member`, iterate all pending requests' `confirmations` sets and remove the deleted member's entry (not just requests they originally submitted). Alternatively, on `confirm()`, filter/re-count `confirmations` against `self.members` before comparing to `num_confirmations`, so confirmations from members no longer part of the multisig can never count toward the threshold. Apply the same fix to the `DeleteKey` handling in `multisig/src/lib.rs`.

### Proof of Concept
Using `multisig2::MultiSigContract` with members `[A, B, C, D]` and `num_confirmations = 3`:

1. `C` calls `add_request(R1)` (e.g. `Transfer` to some receiver). `confirmations[R1] = {}`.
2. `A` calls `confirm(R1)` → `confirmations[R1] = {A}` (len 1 < 3, not executed).
3. `D` calls `confirm(R1)` → `confirmations[R1] = {A, D}` (len 2 < 3, not executed).
4. Separately, members reach quorum (3 confirmations from `A, B, C`) on a `DeleteMember{member: D}` request, executing `delete_member(D)`: [4](#0-3) 
   Since `R1.member == C` (not `D`), `R1` and `confirmations[R1] = {A, D}` are left untouched. `D` is removed from `self.members` and loses its key/account membership.
5. Members are now `{A, B, C}` with `num_confirmations` still `3`.
6. `C` calls `confirm(R1)`. `confirmations[R1].len() + 1 == 3 >= num_confirmations (3)` → `execute_request(R1)` fires the `Transfer` (or `AddKey`, etc.), even though only `A` and `C` are currently live members who ever approved `R1` — `D`'s stale confirmation counted toward the threshold after being removed from the multisig. [5](#0-4)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
