### Title
KYC-Revoked Tranche Holders Cannot Initiate `requestWithdraw`, Leaving Positions Frozen Without a Counterparty - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`isWalletAllowed()` gates every entry point that creates a withdrawal request (`IdleCDOEpochVariant.requestWithdraw`, `depositDuringEpoch`, and `IdleCDOEpochQueue.requestWithdraw`), while the payout functions (`claimWithdrawRequest`, `claimInstantWithdrawRequest`) are not gated. A lender who legitimately held tranche tokens and is later removed from the Keyring whitelist (credential expiry, policy change) can never create a withdraw request, and tranche tokens being a plain `ERC20` with no transfer hook means the only remaining exit is finding a willing counterparty via `IdleCreditVaultWriteOffEscrow`. This mirrors the external bug class: loss of whitelist status after acquisition leads to indefinite freezing of the underlying position.

### Finding Description
In `IdleCDOEpochVariant`, wallet eligibility is enforced on request creation:

- `_deposit` reverts via `_checkNotAllowed(!isWalletAllowed(msg.sender))` (contracts/IdleCDOEpochVariant.sol:645)
- `depositDuringEpoch` includes `!isWalletAllowed(msg.sender)` in its revert condition (contracts/IdleCDOEpochVariant.sol:668)
- `requestWithdraw` applies the same check — confirmed by the repo's own test `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw`, which mocks `IKeyring.checkCredential` to `false` and asserts `cdoEpoch.requestWithdraw(...)` reverts with `NotAllowed` (test/foundry/IdleCreditVaultWriteOffEscrow.t.sol:289-291)
- `IdleCDOEpochQueue.requestWithdraw` calls `_checkAllowed(msg.sender)`, which requires `cdoEpoch.isWalletAllowed(wallet)` (contracts/IdleCDOEpochQueue.sol:131-143, 415-421)

`isWalletAllowed` is a live external call: `IKeyring(keyring).checkCredential(keyringPolicyId, _user)` (contracts/IdleCDOEpochVariant.sol:984-987), so status can change after tokens are acquired. Meanwhile, `claimWithdrawRequest()` and `claimInstantWithdrawRequest()` (contracts/IdleCDOEpochVariant.sol:967-979) forward to `IdleCreditVault` with no whitelist check — but they only pay out requests that already exist. `IdleCDOTranche` is a plain `ERC20` with no `_beforeTokenTransfer` hook (contracts/IdleCDOTranche.sol), so tokens remain transferable, yet there is no protocol-level path to turn tranche tokens into a withdrawal claim without `isWalletAllowed`.

### Impact Explanation
A holder whose Keyring credential lapses owns tranche tokens with no way to open a withdrawal request in any epoch phase (the check applies during the running epoch when requests are made). Their claim on the vault's underlying is frozen indefinitely unless a third party fulfills a `WriteOffEscrow` request or buys the tokens OTC — neither is guaranteed liquidity. The frozen amount equals the holder's full tranche position value. Unlike the external report, claims for *previously submitted* requests are unaffected, so the freeze applies only to positions without an in-flight request.

### Likelihood Explanation
Requires two conditions: the vault is configured with a non-zero `keyring` (deployed by `IdleCreditVaultFactory` whenever `keyring != address(0)`), and a holder's credential is revoked or expires while they still hold tranche tokens without a pending request. KYC expiry/revocation is a routine operational event, not an attack; however the factory does whitelist the `IdleCDOEpochQueue` itself and existing in-flight claims remain claimable, which limits exposure to holders who never queued a request.

### Recommendation
Do not gate `requestWithdraw` on `isWalletAllowed` — restrict the whitelist check to value-inflow paths (`_deposit`, `depositDuringEpoch`, `requestDeposit`) and let any token holder burn tranche tokens into a withdrawal request. Alternatively, check the credential of the *recipient* at `claimWithdrawRequest` time (funds delivery), not at request creation, since the request only records a claim and does not move funds to the user. Note the repo's own test (`testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw`) encodes the current revert as expected behavior, so this may be an intentional compliance design — if so, document that non-KYC holders must exit via `IdleCreditVaultWriteOffEscrow` or secondary transfer.

### Proof of Concept
Foundry sketch (fork/unit, mirroring `IdleCreditVaultWriteOffEscrow.t.sol` setup where `LP` is a KYC'd depositor holding `tranche` tokens):

```solidity
function testRevokedHolderCannotRequestWithdraw() external {
    // epoch running; LP holds tranche tokens and has NOT submitted a withdraw request
    _stopCurrentEpoch(); // or run during epoch per variant rules

    // simulate Keyring revocation for LP
    vm.mockCall(
        keyring,
        abi.encodeWithSelector(IKeyring.checkCredential.selector, keyringPolicyId, LP),
        abi.encode(false)
    );

    assertFalse(cdoEpoch.isWalletAllowed(LP));
    uint256 bal = tranche.balanceOf(LP);
    assertGt(bal, 0);

    // cannot open a withdrawal request: reverts NotAllowed
    vm.prank(LP);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.requestWithdraw(bal, address(tranche));

    // and the queued path also reverts via _checkAllowed
    vm.startPrank(LP);
    tranche.approve(address(queue), bal);
    vm.expectRevert(NotAllowed.selector);
    queue.requestWithdraw(bal);
    vm.stopPrank();

    // claimWithdrawRequest does not revert, but pays nothing: no request was ever created
    vm.prank(LP);
    cdoEpoch.claimWithdrawRequest(); // no-op, LP retains locked tranche tokens
}
```

Expected result: LP's entire tranche position is unrecoverable through any protocol withdrawal path until they either regain credentials or find a `WriteOffEscrow`/OTC counterparty.
