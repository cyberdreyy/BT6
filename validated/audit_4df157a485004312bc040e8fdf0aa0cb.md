### Title
Post-default instant withdraw requests are attributed to the already-finalized default epoch and drain `defaultRecoveryReserve` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` has no post-default handling, so after `finalizeDefaultRecovery` a new instant-withdraw request is recorded under `instantWithdrawsRequestsByEpoch[user][epochNumber]`, where `epochNumber` still equals `defaultRecoveryEpoch`. The next `claimInstantWithdrawRequest` treats it as a defaulted-epoch receipt and pays it out of the fixed `defaultRecoveryReserve` — a basis that was never included in `defaultPendingClaimBasis` at finalization. This mirrors the CVE bug class: the same finalized pending-entry bucket is consumed by an entity added after the accounting was closed, breaking "one receipt, one payout" and making the reserve insolvent for legitimate claimants.

### Finding Description
- `requestInstantWithdraw` (lines 356–375) calls `_ensureDefaultRecoveryInitialized()` but, unlike `requestWithdraw` (lines 247–258), has no `defaultRecoveryFinalized` branch. Post-default it still executes `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`.
- `epochNumber` only increments in `deposit` during a running epoch (lines 607–611). After a default there is no further `stopEpoch`, so `epochNumber == defaultRecoveryEpoch` set in `finalizeDefaultRecovery` (line 693).
- `claimInstantWithdrawRequest` (lines 380–393) calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (line 844) and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` (line 915).
- Because `defaultPendingClaimBasis` (lines 644–649) was evaluated at finalization, the reserve was sized `reserveAmount = recovered + prefunded` against the pre-finalization basis only. Any post-default instant receipt inflates `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` after the fact and is paid from a reserve that does not cover it.

### Impact Explanation
Two outcomes, both in scope: (a) an attacker who holds strategy tokens (or deposits post-default through the CDO at the depressed recovery price) requests an instant withdraw and claims, extracting reserve funds never budgeted for them — direct theft of recovery assets; (b) once the reserve is overdrawn, `defaultRecoveryReserve -= _amount` underflows in `_transferDefaultRecovery`, so honest defaulted-epoch claimants' claims revert permanently — permanent freezing of unclaimed yield. Loss is bounded by the reserve size and the attacker's ability to source receipt basis post-default, but reaches 100% of `defaultRecoveryReserve` in the worst case.

### Likelihood Explanation
Requires: a finalized default (`defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`), and the IdleCDO still routing `requestInstantWithdraw` calls post-default. The vault-side code places no guard (asymmetric with `requestWithdraw`, which explicitly handles post-default requests), so the strategy itself permits it. The honest CDO is assumed to forward user requests; if the CDO hard-blocks all user calls while `defaulted()`, the finding degrades to a latent accounting flaw rather than an exploitable path — this is the main uncertainty, as the CDO-side gating for post-default instant withdrawals was not fully verified.

### Recommendation
In `requestInstantWithdraw`, either revert when `defaultRecoveryFinalized` is true, or route post-default instant requests through a separate epoch key (e.g., record under a sentinel epoch ≠ `defaultRecoveryEpoch`) and pay them only via `_transferFundedClaim` from non-reserved balance. Also clear per-epoch instant entries on funded claims to avoid stale `instantWithdrawsRequestsByEpoch` dust.
