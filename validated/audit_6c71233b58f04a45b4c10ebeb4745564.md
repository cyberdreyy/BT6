## Confirmed: `get_builder_withdrawals` creates a Withdrawal with an uncapped amount while the CL-side deduction is capped

### Title
Builder pending withdrawal mints uncapped `amount` to the execution layer while `apply_withdrawals` only deducts `min(amount, balance)` from the builder — Gwei created out of thin air - (File: specs/gloas/beacon-chain.md)

### Summary
This is the same bug class as the Timeswap `borrow()` finding: a state-affecting quantity (`zIncrease`, attacker-supplied) is written into `pool.state.z` verbatim, while the actual value transferred/collected is computed separately and can be smaller. In `TimeswapPair`, this let the attacker inflate collateral accounting without paying for it. In `specs/gloas/beacon-chain.md`, `get_builder_withdrawals` constructs the `Withdrawal.amount` field (the amount the **execution layer will mint to `fee_recipient`**) directly from `withdrawal.amount` (the requested/pending amount), while `apply_withdrawals` deducts only `min(withdrawal.amount, builder_balance)` from `state.builders[builder_index].balance` on the **consensus layer**. When the builder's balance is smaller than the requested withdrawal amount, the EL-side mint and the CL-side deduction diverge.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md, "New `get_builder_withdrawals`") builds each `Withdrawal` straight from the pending withdrawal's requested amount: [1](#0-0) 

This `Withdrawal` object is what becomes `state.payload_expected_withdrawals`, and it is this exact `amount` field that the execution layer is required to honor (mint to `address`) when building/validating the corresponding execution payload — the CL/EL withdrawal-amount contract is `amount == requested amount`, not a capped value.

`apply_withdrawals`, however, deducts a **capped** amount from the builder's CL-tracked balance: [2](#0-1) 

So if `withdrawal.amount > builder_balance`, the EL mints `withdrawal.amount` to `fee_recipient`, while the CL only debits `builder_balance` (capping the loss to what the builder actually had). The delta `withdrawal.amount - builder_balance` is Gwei created out of nothing — paid to the withdrawal's `fee_recipient`, who need not be the builder's owner.

Test code in the repo explicitly documents and asserts this capped-deduction/uncapped-amount behavior as expected: [3](#0-2) [4](#0-3) 

Crucially, the mismatch is reachable because a builder can be added to `builder_pending_withdrawals` with a requested `amount` **larger than the builder's current balance** with no verification at insertion time that `amount <= balance`:
- `process_execution_payload_bid` only checks `can_builder_cover_bid` at bid time, computed against the current balance at that moment — it does not re-check at settlement time.
- Between bid time (when `BuilderPendingWithdrawal.amount` is fixed) and settlement (`apply_withdrawals`), the builder's balance can fall further (e.g. another withdrawal or `builder_pending_withdrawals` entry drains it first), so by the time this entry is processed `builder_balance < withdrawal.amount`.

This is exactly analogous to Timeswap: `zIncrease` (attacker/builder chosen, fixed early) is written unconditionally into a downstream quantity, while the true available/collectible amount (`state.z`'s real backing collateral / the builder's real balance) is computed and enforced separately and can be smaller — creating a state where the recorded/committed value exceeds what was actually available.

### Impact Explanation
This breaks the "Gwei created, destroyed or paid to a non-owner" equality (Critical impact per the task rules): the execution layer mints `withdrawal.amount` Gwei to `fee_recipient` while the consensus layer only removes `builder_balance` (a strictly smaller amount) from that builder. The excess is fabricated ETH with no corresponding backing balance — a supply-inflation bug, paid to an address (`fee_recipient`) that is not necessarily the builder itself.

### Likelihood Explanation
Reaching the divergent state requires the builder's balance to drop below the previously-queued withdrawal's `amount` before that specific pending withdrawal entry is processed. Given `builder_pending_withdrawals` is a FIFO queue and multiple entries for the same builder can be queued (each `bid` with `amount>0` from the same builder over consecutive slots creates additional queue entries), an attacker-builder can order/size bids so that an earlier-queued entry's `amount` exceeds the balance remaining once later entries (or sweep withdrawals) have already drained it — well within a single builder's own unprivileged control over their own bid sequence. No coalition, client bug, or peer cooperation is required.

### Recommendation
Cap the `amount` field placed into the `Withdrawal` object in `get_builder_withdrawals` (and any other builder-withdrawal constructor) to `min(withdrawal.amount, state.builders[builder_index].balance)`, matching what `apply_withdrawals` actually deducts, so the EL-minted amount and CL-deducted amount are always identical.

### Proof of Concept
1. Builder `B` has `balance = X`.
2. `B` submits two bids/requests that both queue `BuilderPendingWithdrawal` entries against `B`: entry `W1` with `amount = X` (satisfies `can_builder_cover_bid` at time of bid since balance was `X` and no prior pending withdrawal existed yet), then entry `W2` with `amount` for another purpose is queued and processed first (FIFO), draining balance to `0` before `W1` is reached (e.g. via a sweep withdrawal or another pending withdrawal entry being processed first in `get_expected_withdrawals`'s ordering).
3. When `get_builder_withdrawals` processes `W1`, it emits `Withdrawal(amount=X, address=W1.fee_recipient, ...)` unconditionally — see [1](#0-0) .
4. `apply_withdrawals` then executes `state.builders[B].balance -= min(X, 0) == 0` — see [2](#0-1) .
5. The execution payload commits to withdrawing `X` Gwei to `W1.fee_recipient` (per `state.payload_expected_withdrawals`), and the EL mints `X` Gwei there, while the CL-tracked builder balance only decreased by `0`. `X` Gwei has been created without any corresponding balance decrease — confirmed directly by the repo's own test `test_builder_withdrawal_insufficient_balance` which asserts exactly this behavior (`builder_balances={builder_index: 0}` while `withdrawal_amounts_builders={builder_index: withdrawal_amount}` with `withdrawal_amount > available_balance`): [3](#0-2) .
