### Title
View-role user can read a bridge's `OutgoingToken` (external-adapter auth secret) via `GET /v2/bridge_types/{name}` - ([File: core/web/bridge_types_controller.go])

### Summary
`BridgeTypesController.Show` returns a `presenters.BridgeResource` built by `NewBridgeResource`, which unconditionally copies `BridgeType.OutgoingToken` into the response with a JSON tag that has no `omitempty`/redaction. The route is registered without any role gate (`RequiresEditRole`/`RequiresAdminRole`), so any authenticated user — including a `view`-role user — can retrieve the bridge's `OutgoingToken`.

### Finding Description
The route table registers Show with only the base `authv2` group (session/token authentication), not wrapped in a role check: [1](#0-0) 

`BridgeTypesController.Show` fetches the `BridgeType` from the ORM and passes it straight to the presenter with no field filtering based on caller role: [2](#0-1) 

`presenters.NewBridgeResource` always copies `OutgoingToken` from the stored `BridgeType`, and the struct's JSON tag `outgoingToken` has no `omitempty`, so it is always serialized: [3](#0-2) 

Unlike `IncomingToken` — which is never persisted in plaintext (`BridgeType` only stores `IncomingTokenHash`/`Salt`, and the plaintext value is only available transiently at creation time via `BridgeTypeAuthentication`, explicitly attached to the response only in `Create`) — `OutgoingToken` **is** stored in plaintext on `BridgeType` and is used by the node to authenticate itself to the external adapter when it calls out: [4](#0-3) [5](#0-4) 

Role checks in this codebase are enforced per-route by explicit wrapper functions (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`), and `UserRoleView` is the lowest role, intended to be read-only/least-privileged: [6](#0-5) [7](#0-6) 

Since `Show` (and also `Index`, `Update`, `Destroy` responses) is not wrapped with any of these role checks, a `view`-role session or API token is sufficient to retrieve `OutgoingToken` for any bridge by name, confirmed by the existing test that only checks name/URL/confirmations and never asserts the token is filtered: [8](#0-7) [9](#0-8) 

### Impact Explanation
`OutgoingToken` is a bearer-style credential the Chainlink node uses to authenticate itself to the external adapter (per `BridgeType.OutgoingToken` field and its use as `Authorization`/token material toward the EA). A low-privileged `view`-role user (or API token scoped to view) can enumerate/guess bridge names (via `Index`) and then call `Show` to obtain this credential, potentially allowing them to directly call the external adapter with the node's identity, or to spoof responses/impersonate the node toward that adapter. This is a credential-disclosure/secret-leak issue, matching the "sensitive-data/secret exposure to lower-privileged role" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: any valid authenticated session or API token with `view` role (the lowest privilege tier) is sufficient — no edit/run/admin privileges are required. The exploit is a single unauthenticated-relative-to-role, unauthenticated-relative-to-secrets `GET` request to a documented endpoint (`/v2/bridge_types/{name}`), fully reproducible and repeatable for every bridge configured on the node.

### Recommendation
- Redact `OutgoingToken` from `BridgeResource` for non-privileged/`view`-role callers (e.g., only populate it for `edit`/`admin` roles, or omit it entirely from `Show`/`Index`/`Update`/`Destroy` responses and only reveal it via an explicit privileged action), mirroring how `IncomingToken` is handled (never persisted/returned except transiently at creation).
- Alternatively, gate `GET /v2/bridge_types/:BridgeName` (and `/v2/bridge_types` index) behind `auth.RequiresEditRole` (or a new `RequiresRunRole`-equivalent) if bridge secrets must remain visible to some read path, ensuring `view`-role tokens cannot read secrets.
- Add a JSON tag/`omitempty` plus explicit nulling of `OutgoingToken` in the presenter for view-only responses, and add a regression test asserting `view`-role callers never receive `outgoingToken`.

### Proof of Concept
1. In `core/web/bridge_types_controller_test.go`, add `TestBridgeController_Show_ViewRoleLeaksOutgoingToken`:
   - Create an app and a bridge via `app.BridgeORM().CreateBridgeType` with a known `OutgoingToken`.
   - Create an HTTP client authenticated as a `view`-role user (see existing patterns using `cltest.NewApplication` and a view-role session/API token helper).
   - `GET /v2/bridge_types/{name}` with that client.
   - Parse response into `presenters.BridgeResource` and assert `resource.OutgoingToken != ""` and equals the bridge's stored token — demonstrating the leak.
2. Unit-level presenter test (extending `core/web/presenters/bridges_test.go`): call `presenters.NewBridgeResource(bridge)` and `jsonapi.Marshal`, and assert the marshaled JSON contains `outgoingToken` regardless of any role context (since the presenter has no role awareness) — showing the redaction gap must be fixed at the controller/route layer, not the presenter.

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func TestBridgeController_Show(t *testing.T) {
	t.Parallel()

	app := cltest.NewApplication(t)
	require.NoError(t, app.Start(t.Context()))

	client := app.NewHTTPClient(nil)

	bt := &bridges.BridgeType{
		Name:          bridges.MustParseBridgeName(testutils.RandomizeName("showbridge")),
		URL:           cltest.WebURL(t, "https://testing.com/bridges"),
		Confirmations: 0,
	}
	ctx := t.Context()
	require.NoError(t, app.BridgeORM().CreateBridgeType(ctx, bt))

	resp, cleanup := client.Get("/v2/bridge_types/" + bt.Name.String())
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusOK, resp.StatusCode, "Response should be successful")

	var resource presenters.BridgeResource
	cltest.ParseJSONAPIResponse(t, resp, &resource)
	assert.Equal(t, bt.Name.String(), resource.Name, "should have the same name")
	assert.Equal(t, bt.URL.String(), resource.URL, "should have the same URL")
	assert.Equal(t, bt.Confirmations, resource.Confirmations, "should have the same Confirmations")

	resp, cleanup = client.Get("/v2/bridge_types/nosuchbridge")
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusNotFound, resp.StatusCode, "Response should be 404")
}
