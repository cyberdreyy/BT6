### Title
Stale confirmations from deleted members are still counted toward the `num_confirmations` threshold, allowing requests to execute with fewer live confirmers than required - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges confirmations for requests **originated** by the removed member, but does not scrub that member's confirmation from other pending requests it had merely confirmed. Those stale confirmations remain in the `confirmations: LookupMap<RequestId, HashSet<String>>` map and are still counted by `confirm()` against `num_confirmations`, so a pending request can later reach quorum and execute using a confirmation from an account that is no longer a multisig member. This mirrors the report's root cause class: an accounting mapping (`committee_sizes` / here, confirmations recorded) is not kept in sync with the authoritative set (`committee` members / here, `self.members`) when that set is changed.

### Finding Description
The contract tracks confirmations per request as a `HashSet<String>` keyed by `request_id`: [1](#0-0) 

`confirm()` counts entries in this set and compares against `self.num_confirmations` without ever re-validating that each recorded confirmer is still a current member: [2](#0-1) 

`delete_member()` removes the departing member from `self.members` and cleans up only the requests it originated (`r.member == member`); it does not scan `self.confirmations` for entries where the removed member appears as a confirmer on requests created by someone else: [3](#0-2) 

Because of this, the invariant that should hold — "confirmations counted == confirmations from currently live members" — is broken once a confirmer (not a request-originator) is removed while a request they confirmed is still pending.

### Impact Explanation
This lets a request (including a `Transfer` of NEAR, or `AddKey`/`AddMember`/`DeleteMember` actions) execute once the confirmation count nominally reaches `num_confirmations`, even though the actual number of *live* members that confirmed it is one (or more) less. This effectively lowers the K in the K-of-N scheme after membership changes, i.e. "a multisig request executed below threshold" — matching the Critical impact bucket: funds can move (Transfer action) or membership/keys can be altered with fewer real confirmers than the configured security threshold requires.

### Likelihood Explanation
This does not require a malicious insider or owner privilege beyond the ordinary, already-authorized flow of member removal (`DeleteMember`) that any legitimate multisig deployment will use over its lifetime (e.g. rotating out a departing team member). Any request left pending with a partial confirmation from the soon-to-be-removed member, combined with a later, otherwise-legitimate `DeleteMember` execution, silently creates this under-threshold execution window. No special timing exploit or attacker-controlled deployment parameters are needed — only the ordinary operational sequence "confirm a pending request → remove that confirmer from the committee before the request is fully confirmed."

### Recommendation
When a member is deleted, iterate over all pending `requests`/`confirmations` entries and remove the departing member's string key from every confirmation `HashSet`, not just from requests it originated. Alternatively, revalidate membership of every entry in the confirmation set at `confirm()`-time (e.g. filter the set against `self.members` before counting) so `confirmations.len()` always reflects live members.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` for a `Transfer` request `R` (receiver arbitrary) → `confirmations[R] = {A}`.
3. `B` calls `confirm(R)` → `confirmations[R] = {A, B}` (2 of 3, not yet executed).
4. Through the normal governance flow, members confirm and execute a separate request that runs `DeleteMember { member: B }`. `delete_member` checks only `members.len() - 1 >= num_confirmations` (4-1=3 ≥ 3, passes) and removes `B` from `self.members`. It does **not** touch `confirmations[R]`, because `R`'s originator was `A`, not `B`.
5. Now live members = `{A, C, D}`.
6. `C` calls `confirm(R)`. `confirmations[R].len() + 1 == 3 >= num_confirmations(3)` → request `R` executes the `Transfer`.
7. Result: `R` executed with confirmations from `{A, B, C}`, but `B` is no longer a member — only `A` and `C` are live confirmers (2 of 3 live members), one fewer than the configured `num_confirmations` threshold. The threshold was satisfied only because a stale confirmation from a removed member was still counted. [4](#0-3) [5](#0-4)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
