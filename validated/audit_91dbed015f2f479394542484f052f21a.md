## Analysis: Signer weight double-counted across accept/reject tallies (asymmetric guard, "isOwner/owners" desync analog)

### Title
Stale rejection weight is never cleared when a signer later accepts, letting one signer's weight be miscounted on both sides of the 70%/30% tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run` (part of the node's `SigningCoordinator`) maintains a `BlockStatus` per block with two supposedly-mutually-exclusive counters, `total_weight_approved` and `total_weight_rejected`, plus two membership guards that are meant to move together: `gathered_signatures` (keyed set for the accept path) and `responded_signers` (keyed set for the reject path). The two response branches use different, non-synchronized guards, exactly like the MultiSig report's `isOwner` mapping vs. `owners` array getting out of sync: the reject branch's guard variable is never consulted/updated by the accept branch, so a signer who first rejects and then legitimately reconsiders and accepts gets counted in *both* totals, and the stale rejection weight is never retracted.

### Finding Description
In the `Rejected` branch, admission into the tally is gated purely by `responded_signers`: [1](#0-0) 
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block
        .total_weight_rejected
        .saturating_add(signer_entry.weight);
```
In the `Accepted` branch, admission is gated by a *different* set, `gathered_signatures`, and `responded_signers` is only inserted afterward as a side effect, never checked: [2](#0-1) 
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block
        .total_weight_approved
        .saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```
Because `Accepted` never checks `responded_signers`, a signer who already rejected (and is thus already in `responded_signers`, with their weight already folded into `total_weight_rejected`) is still treated as "new" by the accept path the first time they accept, so their weight is *added again* into `total_weight_approved` — while the earlier `total_weight_rejected` contribution is never subtracted. (The opposite order, accept-then-reject, is correctly guarded, since the reject branch's `responded_signers.insert` returns `false` on the second call.)

This one-directional flaw is legitimately reachable: the signer's own local state machine explicitly allows `LocallyRejected -> LocallyAccepted` on re-evaluation, per the documented block lifecycle and `should_reevaluate_reject_reason` logic: [3](#0-2) 
```
    PreCommitted --> LocallyAccepted : mark_locally_accepted = WE SIGN
    Unprocessed --> LocallyRejected : mark_locally_rejected
    PreCommitted --> LocallyRejected : mark_locally_rejected
    LocallyRejected --> LocallyAccepted : re-evaluated
```
So a single signer (one-slot actor via gossip/StackerDB, no majority or foreign key needed) sending `Rejected` and later `Accepted` for the same `signer_signature_hash` is enough to trigger the desync.

### Impact Explanation
`SigningCoordinator::wait_for_block_signer_signatures` (in `signer_coordinator.rs`) polls this same `BlockStatus` and checks the rejection-abort condition before the acceptance condition: [4](#0-3) 
The stale, permanently-retained rejection weight (never decremented when the rejecting signer later accepts) can push `total_weight_rejected.saturating_add(weight_threshold) > total_weight` even though the currently-live opposition is below the actual blocking minority (>30%), causing the coordinator to wrongly abort a block that in truth has (or would have) enough live support — a liveness wedge on block production. Equivalently, one signer's weight is simultaneously counted for both approval and rejection, breaking the intended invariant that a signer's response weight must be attributed to exactly one side of the tally at a time (`aggregated-weight vs verified-accepts` equality break), mirroring the MultiSig report's core defect where two structures meant to track the same membership fact diverge.

### Likelihood Explanation
This requires only one signer to exercise the documented, ordinary reconsideration path (`LocallyRejected -> LocallyAccepted`) for a block that was initially rejected for a re-evaluable reason and later found valid (e.g., a conflict going stale, or a corrected validation result) — normal signer operation, not adversarial collusion, majority control, or key compromise.

### Recommendation
Use a single canonical "has this signer already been tallied, and on which side" guard shared by both branches (e.g., store an enum `Accepted|Rejected` keyed by `slot_id`), and when a signer's recorded response flips from `Rejected` to `Accepted` (or vice versa), explicitly subtract the stale weight from the old bucket before adding it to the new one, so `total_weight_approved + total_weight_rejected` for any given signer never exceeds that signer's own weight.

### Proof of Concept
1. Node's `StackerDBListener` starts tracking `BlockStatus` for a proposed block, `weight_threshold` computed for a 3-signer set with weights 34/33/33 (blocking minority = 33).
2. Signer A (weight 34) sends `BlockResponse::Rejected` for the block (e.g., due to a since-stale reorg conflict) → `responded_signers = {A}`, `total_weight_rejected = 34`.
3. `total_weight_rejected(34).saturating_add(weight_threshold)` does not yet exceed `total_weight`, so mining continues waiting.
4. Signer A later re-evaluates (conflict becomes stale, `should_reevaluate_reject_reason` allows it) and sends `BlockResponse::Accepted` for the *same* `signer_signature_hash`.
5. In `stackerdb_listener.rs`, the accept branch checks only `gathered_signatures.contains_key(&slot_id)` (false, first accept) → `total_weight_approved += 34`. `total_weight_rejected` is left at 34 (never decremented).
6. Now `total_weight_rejected = 34` and `total_weight_approved = 34` simultaneously for a total signer set of weight 100 — signer A's weight is double-booked across both mutually exclusive tallies. Depending on the arrival order of subsequent messages from B/C, the coordinator's rejection-abort branch (checked first) can trip using A's stale phantom rejection weight combined with a genuine rejection from B or C, wrongly declaring `SignersRejected` for a block that in fact now has legitimate majority support (A having accepted), stalling block production.
