### Title
`/v2/config` and `/v2/config/v2` routes lack role-based authorization, allowing any authenticated token (run/view role) to read effective node configuration - ([File: core/web/router.go])

### Summary
The `authv2` route group requires only a valid session/API token via `auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)`, which sets `SessionUserKey` regardless of the user's `Role`. Unlike nearly every other sensitive route in `v2Routes` (e.g. `/keys/eth/import`, `/users`, `/log`), the `/config` and `/config/v2` routes registered at `authv2.GET("/config", cc.Show)` and `authv2.GET("/config/v2", cc.Show)` are not wrapped in any `auth.RequiresRunRole`, `auth.RequiresEditRole`, or `auth.RequiresAdminRole` check, so a `run`-role (or even `view`-role) API token can call `ConfigController.Show` and retrieve the full effective node TOML configuration.

### Finding Description
`ConfigController.Show` (`core/web/config_controller.go:23-42`) calls `cc.App.GetConfig().ConfigTOML()` and returns the effective (or user) TOML configuration as JSON, with no role check inside the handler itself. Route registration in `core/web/router.go:283-285`:
```go
cc := ConfigController{app}
authv2.GET("/config", cc.Show)
authv2.GET("/config/v2", cc.Show)
```
This is inside the `authv2` group defined at `core/web/router.go:245-248`, which only enforces `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)`. `AuthenticateByToken` (`core/web/auth/auth.go:78-112`) validates the API key/secret pair and sets `SessionUserKey` to the matched `*clsessions.User` — with no role filtering. Compare this to the surrounding routes, all of which are explicitly wrapped: `auth.RequiresRunRole`, `auth.RequiresEditRole`, or `auth.RequiresAdminRole` (`core/web/router.go:251-320`). No such wrapper exists for `/config` or `/config/v2`, so `auth.RequiresRunRole`'s check that rejects `UserRoleView` (`core/web/auth/auth.go:200-217`) — or any admin-only gate — never runs for this endpoint. Any minted API token, including one intended only for `run`-role job triggering (or even `view`-role), reaches `ConfigController.Show` and receives the full effective node configuration.

### Impact Explanation
This is an authorization/role-bypass bug matching Chainlink's "unauthorized access to sensitive node configuration" impact class. The effective TOML config returned by `ConfigTOML()` reflects the node's merged configuration (chain RPC endpoints, feature flags, logging, database, and other operational settings defined in `core/services/chainlink/config_general.go`), which is intended to be admin-visible information. A `run`- or `view`-role credential holder — who should only be able to trigger jobs or view limited data — can escalate their effective read scope to admin-level configuration visibility, an information-disclosure/privilege-escalation issue. It is not confirmed from available code whether `ConfigTOML()`'s effective output includes plaintext secrets (secrets are handled separately by `secretsTOML`/`Secrets` fields, redacted per `config_general.go:32`), so the impact is scoped to config-value disclosure rather than direct secret leakage; this uncertainty is noted since the redaction logic for `ConfigTOML()` itself was not fully traced.

### Likelihood Explanation
Exploitation requires only a valid API token of any role (the lowest of which, `run`, is intended solely for job triggering) or a valid user session of any role — no admin privileges needed. Since `/config` performs no role check whatsoever, the attack is trivially and fully repeatable with a single authenticated GET request.

### Recommendation
Wrap the `/config` and `/config/v2` route handlers with an appropriate role guard, e.g. `auth.RequiresAdminRole(cc.Show)` (or at minimum `auth.RequiresEditRole`), consistent with other configuration/administrative endpoints in `v2Routes`.

### Proof of Concept
1. In a Go handler-level integration test (e.g. extending `core/web/config_controller_test.go` patterns), create a user/API token with `Role: sessions.UserRoleRun`.
2. Issue `GET /v2/config` (and `/v2/config/v2`) with `X-API-KEY`/`X-API-SECRET` headers set to that run-role token.
3. Assert current (buggy) behavior: HTTP 200 with the `ConfigV2Resource` JSON payload returned — i.e. `ConfigController.Show` executes despite `Role == UserRoleRun`.
4. Assert desired behavior after fix: HTTP 403 Forbidden (matching `auth.RequiresAdminRole`'s `jsonAPIError(c, http.StatusForbidden, ...)` at `core/web/auth/auth.go:239-254`) for `run`/`view`/`edit` tokens, and 200 only for `admin`-role tokens.
