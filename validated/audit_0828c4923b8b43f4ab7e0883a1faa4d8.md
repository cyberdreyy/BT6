### Title
`_skimDonatedAssets` only skims raw underlying — donated `strategyToken` inflates `getContractValue` and enables a share-inflation/donation attack on tranche deposits - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
The codebase correctly identified the ERC4626-style donation bug class and added `_skimDonatedAssets()` before accounting in every state-changing path (`_deposit`, `depositDuringEpoch`, `requestWithdraw`, `updateAccounting`, `finalizeDefault`). However, the skim only removes raw `token`:

`contracts/IdleCDOEpochVariant.sol:794-796`
```solidity
function _skimDonatedAssets() internal {
    _transferUnderlyings(feeReceiver, _contractTokenBalance(token));
}
```

`getContractValue()` in `IdleCDOCreditVault` counts **two** balance components:

`contracts/IdleCDOCreditVault.sol:125-128`
```solidity
function getContractValue() public override view returns (uint256) {
    return _contractTokenBalance(strategyToken) + _contractTokenBalance(token) - unclaimedFees;
}
```

A donation of `strategyToken` (the `IdleCreditVault` share token) directly to the CDO is **never skimmed** and is fully counted in `nav` by `_updateAccounting()` (`IdleCDOCreditVault.sol:227`), crystallizing into `priceAA`/`priceBB`. This is exploitable by an unprivileged user because the protocol itself hands transferable `strategyToken` to regular users: `requestInstantWithdraw` mints vault receipt tokens directly to `msg.sender` (`IdleCDOEpochVariant.sol:765`), so any KYC'd tranche holder can obtain `strategyToken` on the open flow and transfer them.

### Finding Description
Attack sequence (closed-pool/buffer phase, fixed-APR epoch vault):

1. Attacker (KYC-passing lender) is the first AA depositor: `depositAA(1)` → `minted = 1 * ONE_TRANCHE_TOKEN / oneToken` at initial `priceAA = oneToken` (`IdleCDOCreditVault.sol:74`, `:339-341`). Tiny supply, NAV_AA = 1.
2. Attacker obtains `strategyToken` worth `D` underlying via a normal deposit + instant-withdraw receipt (`requestInstantWithdraw` mints the receipt to the user), then **transfers the `strategyToken` directly to the CDO**. No code path removes it.
3. Victim calls `depositAA(V)` with `V < D`. `_deposit` → `_skimDonatedAssets()` (skims `token` only → donation survives) → `_updateAccounting()` crystallizes: `nav` includes the donated `strategyToken`, so `totalGain ≈ D`, `lastNAVAA += ~D`, and `priceAA = lastNAVAA * ONE / supply` becomes huge (`_virtualPriceAux`, `IdleCDOCreditVault.sol:336`).
4. Victim mints `_minted = V * ONE_TRANCHE_TOKEN / priceAA` (`IdleCDO.sol:439` equivalent in `IdleCDOCreditVault._mintSharesAtCurrPrice`) — near zero shares for `V << D`, while `_mintShares` credits the full `V` to `lastNAVAA`.
5. Attacker calls `requestWithdraw` (or withdraws after next accounting) — their dust tranche balance now claims `~D + V` of NAV at the inflated price, stealing the victim's principal in excess of the donation cost (profit ≈ `V − dust`).

Broken invariant: fair mint/burn — tranche shares must be minted at a price that cannot be manipulated by unsolicited transfers. The donation-isolation guard exists but covers only half of the NAV numerator.

### Impact Explanation
Direct theft of victim deposits at vault (re)initialization or whenever a tranche's supply/NAV is small relative to an achievable donation. Loss ≈ victim deposit amount minus rounding residue; attacker funds the donation from their own instant-withdraw receipt, which is returned via the inflated claim plus stolen principal — same economics as the referenced Surge report.

### Likelihood Explanation
- Attacker is fully unprivileged: KYC lender + tranche holder + instant-withdraw receipt holder, all explicitly allowed roles.
- Requires `strategyToken` to be transferable to arbitrary addresses — standard for the vault receipt minted in `requestInstantWithdraw`; this is the one assumption to confirm in the PoC (if receipts are soul-bound/escrowed, severity drops).
- No guard intercepts it: `_checkDefault` watches `_strategyPrice` *decreases*; `_guarded` caps deposits, not NAV composition; `_skimDonatedAssets` ignores `strategyToken`; `virtualPrice`/`_managedContractValue` exclude raw `token` but still count the full `strategyToken` balance (`IdleCDOCreditVault.sol:133-137`), so even view previews reflect the inflation.

### Recommendation
Extend `_skimDonatedAssets` (or `_managedContractValue`/accounting) so that `strategyToken` held by the CDO is reconciled against internally-tracked issued strategy tokens (e.g., expected balance = sum of deposits minus withdrawn/receipt-burned amounts), forwarding any excess to `feeReceiver` before `_updateAccounting` reads `getContractValue()`. Alternatively, price mints off `_managedContractValue()`-style managed accounting rather than raw `balanceOf`, and/or seed a minimum initial tranche supply at initialization.

### Proof of Concept
Foundry fork sketch against the epoch credit-vault CDO:

```solidity
// Setup: epoch vault initialized, attacker is KYC'd (isWalletAllowed == true)
// 1. First-depositor seed
vm.prank(attacker);
idleCDO.depositAA(1); // mints ~1e12 AA shares, lastNAVAA = 1

// 2. Attacker obtains strategyToken via instant-withdraw receipt
//    (second KYC'd EOA or same attacker on a second deposit+requestInstantWithdraw
//     when _isInstantWithdrawEnabled and apr drop > instantWithdrawAprDelta)
uint256 D = 100 * ONE_SCALE;
// attacker now holds IdleCreditVault receipt tokens worth D underlying
vm.prank(attacker);
IERC20(address(strategy)).transfer(address(cdoEpoch), D); // donation NOT skimmed

// 3. Victim deposits
vm.prank(victim);
idleCDO.depositAA(190 * ONE_SCALE);
// _skimDonatedAssets() removes only `token`; _updateAccounting() counts D
// priceAA inflated ~D/supply → victim minted ≈ 190e6*1e18 / (D*1e6) ≈ 0 shares
assertLt(AAtranche.balanceOf(victim), 1e13); // dust vs attacker's ~1e12

// 4. Attacker requests withdraw / redeems at inflated price
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche));
// _trancheToUnderlyings(shares) ≈ shares * inflatedPrice / ONE
// attacker claims ~(D + 190e6) against a vault holding 190e6 + receipt claim on D
// → net extraction of victim principal
```

Expected result: victim receives ~0 AA shares for a 190-underlying deposit; attacker's claim exceeds their contributed capital, demonstrating theft via un-skimmed `strategyToken` donation. Caveat: if the `IdleCreditVault` receipt token restricts transfers (clawback/whitelist), the donation vector narrows but the accounting gap remains — any path that leaves foreign `strategyToken` on the CDO inflates NAV.
