### Title
`_checkSameBlock` uses `tx.origin`+`block.number` hash, causing false-positive withdraw reverts on L2s (temporary freezing of funds) - (File: contracts/IdleCDO.sol)

### Summary
`IdleCDO._deposit` stores `keccak256(abi.encodePacked(tx.origin, block.number))` in `_lastCallerBlock` via `_updateCallerBlock()` (`contracts/IdleCDO.sol:241`, `contracts/IdleCDO.sol:1016-1018`), and `_withdraw` reverts with `SameBlock()` whenever the current `keccak256(tx.origin, block.number)` equals the stored value (`contracts/IdleCDO.sol:479`, `contracts/IdleCDO.sol:1021-1023`). The same pattern exists in `IdleTokenFungible._checkMintRedeemSameTx` (`contracts/IdleTokenFungible.sol:368`, `contracts/IdleTokenFungible.sol:793-795`) and its Optimism variant. Because `block.number` on Arbitrum returns the (slowly updated) L1 block number and stays constant across many L2 transactions, and because relayers/Account-Abstraction bundlers make distinct users share the same `tx.origin`, two *different* transactions can produce the identical hash — an exact analog of the reported `currentBlockOriginHash` false-positive.

### Finding Description
The guard intends to prevent deposit+withdraw (mint+redeem) inside a single transaction to block flash-loan price manipulation. However the identity key `(tx.origin, block.number)` is not unique to a transaction:

- On `IdleCDOArbitrum` (`contracts/arbitrum/IdleCDOArbitrum.sol`) — a deployed, in-scope production variant — `block.number` is the L1 block number, which remains constant for a stretch of L2 blocks. Any user who calls `depositAA`/`depositBB` in L1 block N cannot call `withdrawAA`/`withdrawBB` until the L1 block number increments, even though these are separate L2 transactions.
- With relayers/ERC-4337 bundlers (relevant on zkSync Era — the repo has an `unknown-1101` deployment manifest — and Polygon where `IdleCDOPoLidoVariant` uses the same check), `tx.origin` is the bundler/relayer EOA. A deposit routed through a bundler sets `_lastCallerBlock` to `hash(bundler, block.number)`, and *any other user's* withdrawal routed through the same bundler in a block with the same number reverts.

An unprivileged attacker can weaponize this as griefing: by submitting a minimal `depositAA` through a shared relayer/bundler, they cause all withdrawals from other users submitted via that relayer in the same (L1) block to revert. Since `_checkSameBlock()` runs before `_updateAccounting()` and there is no try/catch fallback, the whole withdraw tx reverts.

### Impact Explanation
Broken invariant: liveness of withdrawals — a user holding tranche tokens cannot redeem principal + interest. The impact is temporary freezing of user funds (withdrawals revert with `SameBlock()`) for the duration that `block.number` stays constant (on Arbitrum this can span many L2 blocks; under a shared bundler it persists as long as the bundler's transactions land in the same numbered block). During a market stress event this delayed exit has real fund impact (e.g., inability to exit before a loss/`Default` event). Loss magnitude: time-value and slippage on the full tranche position of affected users; griefing cost to the attacker is only a dust deposit.

### Likelihood Explanation
High on the Arbitrum deployment where `block.number` granularity is coarse and deposits are direct (`directDeposit = true`, `contracts/arbitrum/IdleCDOArbitrum.sol:29`); any ordinary sequence of deposit-then-withdraw by the same EOA within one L1 block fails. With AA/bundler infrastructure the false positive requires only two unrelated users sharing a relayer. On mainnet the check is mostly benign (one block ≈ one opportunity window), which is why it survives there, but the code is shared verbatim by the L2 variants.

### Recommendation
Include `block.timestamp` (and optionally `block.basefee`/`block.difficulty`, which on L2s carry per-L2-block entropy) in the stored hash, or better, use a per-transaction marker that cannot collide across transactions — e.g., store `keccak256(tx.origin, block.number, block.timestamp)` or simply track `lastDepositBlock[tx.origin]` combined with `block.timestamp`. Alternatively, replace the origin-hash mechanism entirely with a per-account `lastActionTimestamp`/`lastActionBlock` mapping keyed on `msg.sender`, which eliminates cross-user false positives through shared relayers.
