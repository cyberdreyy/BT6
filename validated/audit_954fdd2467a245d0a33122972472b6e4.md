### Title
`MultisigFactory::create` has no rollback/refund callback, permanently freezing the attached NEAR deposit if the deployment sub-call fails - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` builds a single promise batch (`create_account` → `deploy_contract` → `transfer` → `function_call("new", ...)`) and returns it directly, with no `.then()` callback to itself. Unlike the sibling factories in this repository (`LockupFactory` and `StakingPoolFactory`), which each implement an `on_*_create` callback that refunds the caller's attached deposit if the batch fails, `MultisigFactory::create` has no such mechanism. If the batched promise fails for any reason, the attached NEAR is not returned to the caller and there is no other function in the contract to reclaim it.

### Finding Description
`LockupFactory::create` and `StakingPoolFactory::create_staking_pool` both attach a callback that inspects `is_promise_success()` and, on failure, explicitly returns the attached deposit to `predecessor_account_id`: [1](#0-0) [2](#0-1) [3](#0-2) 

`MultisigFactory::create`, however, only issues the batched promise with no `.then(ext_self::...)` callback and no refund logic whatsoever: [4](#0-3) 

The account name used for the new multisig (`format!("{}.{}", name, env::current_account_id())`) is fully attacker-controllable, and `create` is payable and callable by anyone with no reservation/commit-scheme, no uniqueness tracking (unlike `StakingPoolFactory`, which maintains `staking_pool_account_ids: UnorderedSet<AccountId>` and removes the entry on failure), and no minimum-deposit check comparable to `LockupFactory`/`StakingPoolFactory`. Concretely:
- An unprivileged party can pre-create (or race-create) the sub-account `name.multisig-factory` before a victim's `create` call executes, or the victim can simply mis-set `num_confirmations > members.len()` (a check enforced in `multisig2::new`), causing the deployed `new` call, or the `create_account` step itself, to fail.
- Because the batch has no attached callback, when any step in the promise chain fails, the NEAR that was attached to the outer `create` call is not returned to the original caller. It stays on the `MultisigFactory` contract's own balance (or is stuck as a dangling transfer within the failed receipt, depending on which step failed) with no owner-agnostic or public function anywhere in `multisig-factory/src/lib.rs` to withdraw or reclaim it.

This is a direct structural analog of the reported issue: an intermediary contract (`RubiconRouter` there, `MultisigFactory` here) performs an action that custodies a user's asset on the user's behalf, and the codebase provides no cancellation/refund path back to the original depositor when that action does not complete as intended — breaking the equality "value attached by the caller == value ultimately controlled by that caller or refunded to them."

### Impact Explanation
This matches the Critical criteria "funds permanently frozen": once a `create` call's batched promise fails (whether from a collided/attacker-claimed account name, an invalid `num_confirmations`, or insufficient attached balance for storage), the attached NEAR tokens cannot be recovered by the caller through any function of `MultisigFactory`. There is no owner-only or public withdraw method in the contract to sweep such stranded balance out to the original depositor either, so the loss is permanent from the depositor's perspective.

### Likelihood Explanation
Likelihood is moderate to high: the `name` parameter is entirely attacker-choosable and account-name squatting/front-running is a well-known primitive on NEAR (the attacker need only observe a pending `create` transaction, or predict a commonly-used name, and pre-create the same sub-account). Even without any attacker involvement, ordinary user error (e.g., supplying `num_confirmations` greater than `members.len()`, which `multisig2::new` should reject) is sufficient to trigger the unrecoverable state, since no validation of these arguments occurs in `MultisigFactory::create` itself before firing the promise batch.

### Recommendation
Add a callback analogous to `LockupFactory::on_lockup_create` / `StakingPoolFactory::on_staking_pool_create`: chain `.then(ext_self::on_multisig_create(...))` after the deployment batch, check `is_promise_success()`, and if the deployment failed, `Promise::new(predecessor_account_id).transfer(attached_deposit)` to return the caller's funds. Additionally, validate `num_confirmations <= members.len()` (and any other constraints enforced by `multisig2::new`) inside `MultisigFactory::create` before spending gas/attaching deposit, and consider tracking created account IDs (as `StakingPoolFactory` does) to detect and reject name collisions early rather than relying on the sub-call to fail.

### Proof of Concept
1. Attacker observes (or predicts) that a victim intends to call `MultisigFactory::create(name: "alice", members: [...], num_confirmations: k)`.
2. Attacker calls `create_account` (or the factory's own `create`) for `alice.multisig-factory` first, claiming the account name.
3. Victim's `create` call executes: the promise batch's `create_account` step fails because the account already exists.
4. Because `MultisigFactory::create` (`multisig-factory/src/lib.rs:28-49`) has no `.then()` callback, the NEAR the victim attached is not returned to them; no function in the contract allows the victim to reclaim it.
5. Contrast with `LockupFactory::on_lockup_create` (`lockup-factory/src/lib.rs:171-198`) and `StakingPoolFactory::on_staking_pool_create` (`staking-pool-factory/src/lib.rs:200-239`), which explicitly transfer the attached deposit back to `predecessor_account_id` on failure — the exact remediation missing from `MultisigFactory`.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
