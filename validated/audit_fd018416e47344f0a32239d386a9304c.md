### Title
Miner can indefinitely reset the tenure liveness timer with conflicting/inferior proposals, wedging signers onto a stalled tenure and preventing fallback - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` treats *any* proposal that fails the height/tip check — a block that does not confirm as many blocks as expected, or one that conflicts with a block the signer has only pre-committed to — as valid "miner activity" and refreshes `last_activity_time` for the tenure, even though the proposal itself is rejected and never becomes a signed, canonical block.

### Finding Description
The activity timer that gates the fallback decision ("has the current miner gone dark, so we should fall back to the prior tenure") is updated on two paths that do not require the proposal to ever succeed: [1](#0-0) 

and [2](#0-1) 

In both branches the block is *not* accepted — it is either lower/equal height than the known tip or conflicts with a fresh pre-commit — yet `signer_db.update_last_activity_time(...)` is still called with the current wall-clock time. `is_timed_out` (`SortitionStateV1::is_timed_out` / `SortitionStateV2::is_timed_out`, invoked from `SortitionState::is_timed_out` at [3](#0-2) ) measures elapsed time since this same `last_activity_time` against `block_proposal_timeout` to decide whether the state machine should fall back to the prior tenure's miner (`docs/signer-flows.md` section 8, the `TO -- "no signed block, and inactive past block_proposal_timeout" --> FALL` transition).

Because the timer is refreshed by *any* rival/inferior proposal regardless of whether it ever produces a globally accepted block, a single miner (one slot, no majority of signers needed) can keep the tenure "alive" forever by periodically gossiping a fresh, but always-invalid-height or conflicting-with-pre-commit, `BlockProposal` at intervals shorter than `block_proposal_timeout`. Each such message resets the clock exactly like the Carapace bug's per-cycle `withdrawalRequests[msg.sender] = _sTokenAmount` overwrite resets the withdrawal delay: the code tracks only "was there *any* recent signal," not "did a signal actually make legitimate progress," so the delay/timeout mechanism can be trivially and repeatedly reset by the party it was meant to constrain.

### Impact Explanation
This is a liveness wedge (High): as long as the current miner (or anyone able to gossip proposals attributed to that miner's tenure) keeps sending distinct-but-rejected proposals faster than `block_proposal_timeout`, `is_timed_out` never returns true, so `check_miner_inactivity`'s `FALL` branch (`make_miner_state(prior sortition)`) never fires, and signers never fall back to a viable prior/alternate tenure. The network can be stalled on a tenure that never produces a signable block, without requiring a majority of signers, another signer's key, or any auth token — only the ability to keep proposing (or replaying) blocks from the current miner's tenure.

### Likelihood Explanation
Reachable by a single miner controlling one slot plus normal StackerDB gossip. No majority of signers is required, and no cryptographic material beyond the miner's own signing key is needed; the attacker simply needs to keep issuing distinct block proposals (varying timestamp/height so they are treated as "new" and re-evaluated) that fall into the two activity-crediting branches of `check_latest_block_in_tenure` faster than the configured `block_proposal_timeout`.

### Recommendation
Do not credit `last_activity_time` for proposals that fail the height/conflict checks in `check_latest_block_in_tenure`. If some activity credit is still desired for legitimate reorg attempts, bound how many times/how long a single tenure may extend its own inactivity window this way (e.g., track first-seen time of the stalled state and cap total extension), so a stream of always-rejected proposals cannot indefinitely suppress the fallback-to-prior-tenure transition.

### Proof of Concept
1. Miner M starts a tenure at consensus hash `CH`; signers observe its first (only) proposal but it never reaches 70% pre-commit/signature (e.g., M deliberately proposes a block that is quickly superseded or never valid).
2. Before `block_proposal_timeout` elapses, M gossips another `BlockProposal` for `CH` with a lower/equal `chain_length` than the last known info, or one that conflicts with an outstanding pre-commit.
3. `check_latest_block_in_tenure` rejects the proposal for chain-progress purposes (`Ok(false)`) but still calls `signer_db.update_last_activity_time(&CH, now)` per [4](#0-3)  or [5](#0-4) .
4. M repeats step 2 indefinitely, each time before the timeout window closes.
5. `SortitionState::is_timed_out` ( [3](#0-2) ) always sees a recent `last_activity_time` and never reports the tenure as timed out, so `check_miner_inactivity`'s fallback to the prior tenure (`docs/signer-flows.md`, section 8) never triggers — the signer set is wedged waiting on M's tenure indefinitely, even though M never produces a block that advances the chain.

                consensus_hash,
                signer_db,
                eval,
                local_address,
                proposal_config.block_proposal_timeout,
            ),
