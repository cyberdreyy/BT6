## Analysis

The bug-class hint (VTab/VTabCursor state consistency violated by unsynchronized concurrent mutation in rusqlite) maps most directly onto the coordinator-side vote tally in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`: two independent counters (`total_weight_approved`, `total_weight_rejected`) are updated by two separate message-handling branches that share only a partial guard (`gathered_signatures` for one branch, `responded_signers` for the other), so the same signer's weight can land in both aggregates for the same block, corrupting the "aggregated-weight vs verified-accepts" equality the miner relies on.

### Title
A single signer's stale rejection weight is never retracted when it later accepts, letting the coordinator miscount and spuriously abort a block that has real supermajority support - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` maintains one `BlockStatus` per proposed block with two independent weight tallies, `total_weight_approved` and `total_weight_rejected`, fed by the `BlockResponse::Accepted` and `BlockResponse::Rejected` branches of the StackerDB message handler [1](#0-0) . These two branches use different, non-shared idempotency guards, so a signer that first rejects and later accepts the same block gets counted into both totals, and `total_weight_rejected` is never decremented when the signer's vote flips.

### Finding Description
In the `Rejected` branch, a signer's weight is only added the first time its slot id is inserted into the shared `responded_signers` set: `if block.responded_signers.insert(slot_id) { block.total_weight_rejected = ... }` [2](#0-1) .

In the `Accepted` branch, the weight is added based on a *different* guard, `gathered_signatures`, not `responded_signers`: `if !block.gathered_signatures.contains_key(&slot_id) { block.total_weight_approved = ... }`, after which `block.gathered_signatures.insert(slot_id, signature)` and `block.responded_signers.insert(slot_id)` both run unconditionally [3](#0-2) .

Consequence: if a signer sends a `Rejected` message first (populating `responded_signers` and `total_weight_rejected`, but not `gathered_signatures`), and later sends an `Accepted` message for the *same* block sighash, the accept branch's check (`!gathered_signatures.contains_key`) still passes — because `gathered_signatures` was never touched by the reject path — so `total_weight_approved` is incremented too. `total_weight_rejected` is never decremented or reconciled. The same signer's weight is now counted simultaneously in both aggregates, breaking the invariant that `total_weight_approved` and `total_weight_rejected` are mutually exclusive views of live signer opinion.

This matters because `SignCoordinator::wait_for_supermajority` (in `signer_coordinator.rs`) evaluates the two aggregates independently, checking the *rejection* condition first, on every poll of the shared `BlockStatus`:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { .. });
} else if block_status.total_weight_approved >= self.weight_threshold {
    ... return Ok(...);
}
``` [4](#0-3) 

Because a stale reject can persist indefinitely in `total_weight_rejected` after the same signer flips to accept, this stale weight (combined with other genuinely-rejecting signers) can trip the `> self.total_weight - weight_threshold` blocking-minority condition and return `SignersRejected` even though the signer that originally rejected has since accepted and the live accepting weight has actually reached (or would reach) the real approval threshold. The reject-branch check is evaluated first in the loop, so a stale reject can pre-empt a legitimate accept outcome on the very same poll where `total_weight_approved` would otherwise have satisfied the threshold.

### Impact Explanation
This is a miscounted-response defect in the node-side coordinator that tallies signer votes for block approval. It causes the miner to conclude a block was rejected by a blocking minority (`NakamotoNodeError::SignersRejected`) using stale, already-superseded rejection weight from a signer that has since accepted, even though the real, current signer support may already satisfy the approval threshold. This is a liveness wedge: valid blocks with sufficient real signer support can be discarded/retried by the miner due to phantom rejection weight that is never retracted, matching the "miscounted response" / liveness-wedge category called out as in-scope impact.

### Likelihood Explanation
A single Byzantine or misbehaving signer (one StackerDB slot) can trigger this deterministically and unilaterally, without needing a majority: it need only broadcast a `BlockRejected` message for a sighash and later broadcast a valid `BlockAccepted` message (a legitimate, correctly-signed acceptance) for the same sighash over its own StackerDB slot. No cooperation from other signers, no auth token, and no majority control is required — only the signer's own key, which every signer already possesses to sign accepts/rejects legitimately. Both messages pass signature verification (`signer_pubkey.verify(...)` for accepts, `recover_public_key()` match for rejects), so neither branch rejects the messages as malformed.

### Recommendation
Use a single per-signer, per-block vote state (e.g., an enum `{Accepted, Rejected}` keyed by slot id) instead of two independently-guarded aggregates. When a signer's vote transitions from Rejected to Accepted (or vice versa), atomically move the signer's weight out of the old aggregate and into the new one under the same `blocks` mutex, rather than only ever adding to a tally and gating solely on "have I seen this slot before" per branch.

### Proof of Concept
1. Coordinator proposes a block with sighash `H`, waits in `wait_for_supermajority`, watching `BlockStatus` for `H`.
2. A single signer `S` (one StackerDB slot, weight `w`) broadcasts `BlockResponse::Rejected` for `H`. `stackerdb_listener.rs` records: `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
3. Enough other signers reject such that `total_weight_rejected` is just under `total_weight - weight_threshold` (not yet triggering `SignersRejected`).
4. Signer `S` reconsiders (re-validates, sees the block is fine) and broadcasts a legitimately-signed `BlockResponse::Accepted` for the same `H`. In the Accepted branch, `gathered_signatures.contains_key(S)` is `false` (S never accepted before), so `total_weight_approved += w` — while `total_weight_rejected` still includes `S`'s earlier `w`.
5. Now `total_weight_rejected` (still containing `S`'s stale weight) plus other real rejecters can cross `self.total_weight - self.weight_threshold`, causing `wait_for_supermajority` to return `NakamotoNodeError::SignersRejected` on the very next poll — even though `S`'s current, valid vote is Accept and the true rejecting weight (excluding `S`) may be well under the blocking-minority threshold, and the true accepting weight (including `S`) may already meet `weight_threshold`.
