Based on the code and existing test coverage, this scenario is already guarded against and does not constitute an exploitable vulnerability.

**Tracing the claimed equality**: The question assumes that once both siblings reach `PreCommitted`, there is no further guard before `handle_block_pre_commit`'s threshold race lets both cross to a signature. This is false. `check_proposal`'s `DuplicateBlockFound` check is indeed proposal-time-only [1](#0-0) , but `handle_block_pre_commit` re-runs a second, independent guard at the moment the threshold is crossed — specifically before actually calling `mark_locally_accepted`.

After the chainstate re-check (`check_block_against_signer_db_state`) passes, the code computes `get_signed_conflicts` for any block at the same or higher height in *any* tenure, and refuses to sign if a fresh, still-live conflict exists [2](#0-1) . This is exactly the "own-tenure branch" the docs describe as covering the gap left by `DuplicateBlockFound` only running at proposal arrival [3](#0-2) .

**Existing test coverage confirms the guard holds**: The `async_sibling_validation` test module in `stacks-signer/src/v0/tests.rs` explicitly drives the exact race the question describes — two sibling tenure-start blocks A and B, both validated and pre-committed within the async-validation window, with A's validation completing first and being signed [4](#0-3) . The test `signer_refuses_to_sign_second_sibling_tenure_start` asserts B stays in `PreCommitted` state with `signed_self.is_none()` while A's signature is fresh — i.e., the exact attack the question hypothesizes is rejected [5](#0-4) . Additional tests (`stale_sibling_still_refused_when_canonical_tip_at_height`, `reproposal_cannot_bypass_fresh_conflict`) cover the re-proposal and staleness edge cases and also confirm the guard holds until the conflict is definitively dead [6](#0-5) .

**Why the "PreCommitted state alone" framing is wrong**: `PreCommitted` explicitly carries no signature per the documented state machine [7](#0-6) , and reaching pre-commit threshold does not bypass the conflict check — the freshness/conflict evaluation in `handle_block_pre_commit` is precisely the "re-check at the moment of threshold crossing" that the question incorrectly assumes is missing.

        // re-proposed tenure-start block after the first failed to reach consensus), but a
        // signature must not be superseded while it's still "fresh". A signed block at the
        // same or higher height in ANY tenure is a conflict: two blocks at the same height are
        // siblings no matter which tenure they belong to (e.g. the next tenure's tenure-start
        // block conflicts with the current tenure's block at the same height). Blocks in
        // tenures whose reorg we sanctioned under the reorg-timing rules are excluded, but
        // only while the sortition the permit was granted to is still canonical
        // (`check_parent_tenure_choice` records the permit, `reorg_permit_stands` re-derives
        // its validity from the node); every other question about whether a conflict is
        // still live is derived from the node in `conflict_still_blocks`.
        //
        // Unlike the chainstate check above, a refusal here is "for now" rather than a
        // broadcast rejection: a later pre-commit re-evaluation may still sign the block once
        // the conflicting signature has gone stale.
        let conflicts = match self
            .signer_db
            .get_signed_conflicts(block_info.block.header.chain_length, &block_hash)
        {
            Ok(conflicts) => conflicts,
            Err(e) => {
                warn!("{self}: Failed to query the signed blocks. Refusing to sign block {block_hash}: {e:?}");
                return;
            }
        };
        let freshness_cutoff = get_epoch_time_secs().saturating_sub(
            self.proposal_config
                .tenure_last_block_proposal_timeout
                .as_secs(),
        );
        // A fresh signature only blocks while the block it covers could still be part of the
        // chain: see `conflict_still_blocks`, which asks the node whether it is. Check
        // freshness first: it is a local timestamp comparison, while `reorg_permit_stands`
        // and `conflict_still_blocks` each query the node, so stale conflicts cost no
        // round-trips.
        if let Some(conflict) = conflicts.iter().find(|conflict| {
            conflict.last_endorsed > freshness_cutoff
                && !self.reorg_permit_stands(stacks_client, conflict)
                && self.conflict_still_blocks(
                    stacks_client,
                    conflict,
                    block_info.block.header.chain_length,
                )
        }) {
            warn!(
                "{self}: Reached the pre-commit threshold for a block, but we have recently signed or accepted a different block at the same or higher height. Refusing to sign.";

                "block_height" => block_info.block.header.chain_length,
                "conflicting_signer_signature_hash" => %conflict.signer_signature_hash,
                "conflicting_block_height" => conflict.stacks_height,
                "conflicting_consensus_hash" => %conflict.consensus_hash,
