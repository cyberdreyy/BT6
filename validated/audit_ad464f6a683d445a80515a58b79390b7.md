## Analog Analysis

The external bug: `QueryInterface` returns a pointer without incrementing the reference count — the returned reference stays registered after the caller has consumed it, so a later release double-counts a stale reference. The closest analog in this codebase is the instant-withdraw receipt lifecycle in `IdleCreditVault`: when a user claims a funded instant withdrawal, the aggregate receipt is cleared but the per-epoch references (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) are never decremented — a stale "reference" that gets counted again at default finalization.

**Verification of the asymmetry:**

- `requestInstantWithdraw` records three per-epoch counters: `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`, and `pendingInstantWithdraws` [1](#0-0) 
- `claimInstantWithdrawRequest` burns the receipt and zeroes only `instantWithdrawsRequests[_user]` — the two by-epoch mappings are untouched [2](#0-1) 
- The only place `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` are decremented is `_claimDefaultedInstantWithdrawRequest`, which assumes they still represent unpaid basis [3](#0-2) 
- `defaultPendingClaimBasis` re-adds the full `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` at finalization [4](#0-3) 
- `_defaultPrefundedInstantReserve` treats `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` as underlying already held in the strategy — which is false for claims that were already paid out [5](#0-4) 

### Title
Claimed instant-withdraw receipts are never removed from per-epoch claim accounting, inflating default-recovery basis and bricking recovery claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears `instantWithdrawsRequests[_user]` but never decrements `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. If the same epoch later defaults with `pendingInstantWithdraws != 0`, the already-paid amount is counted again in `defaultPendingClaimBasis` and phantom "prefunded" reserve, diluting the recovery price for all honest claimants and leaving `defaultRecoveryReserve` larger than the contract's real balance so the last claimants' `_transferDefaultRecovery` calls revert permanently.

### Finding Description
When a user's instant-withdraw request is funded via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`, `pendingInstantWithdraws` is decremented but `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` keep the full amount. When the user then calls `claimInstantWithdrawRequest` (through the CDO) they are paid at par, yet the stale per-epoch entries survive. If, within the same `epochNumber`, another user's instant request remains unfunded (`pendingInstantWithdraws != 0`) and the borrower defaults, `finalizeDefaultRecovery`:

1. adds the stale `instantWithdrawClaimsByEpoch[epochNumber]` (including the already-paid amount) to `totalBasis`, so `recoveryPrice = reserveAmount / totalBasis` is pushed below the fair ratio — every honest defaulted and post-default claimant is diluted by exactly the attacker's double-counted basis;
2. computes `prefundedReserve = instantBasis - pendingInstant`, crediting the contract with funds it already transferred out, so `defaultRecoveryReserve` exceeds `underlyingToken.balanceOf(this)` — `_transferDefaultRecovery` (`reserve -= amount` / `safeTransfer`) reverts for the last claimants, permanently freezing part of the recovery.

Additionally, if the same user has any newer instant receipt in the default epoch, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[user][epoch]` (stale + new) and does `instantWithdrawsRequests[_user] -= claimBasis`, which underflows and reverts — permanently freezing that user's entire claim.

### Impact Explanation
Direct theft via dilution plus permanent freezing: the attacker instant-withdraws at par during the buffer, claims, and the stale receipt lowers `defaultRecoveryPrice` for every other claimant while the phantom prefunded reserve makes the aggregate reserve unbacked. Quantified: a stale claimed amount `X` inflates `totalBasis` by `X` and `defaultRecoveryReserve` by up to `X` without backing, so honest claimants lose `X * recovered / (trueBasis + X)` in aggregate and the last claimant(s) cannot claim at all. Attacker requirements: any KYC-passing lender requesting an instant withdrawal during the buffer of the epoch that defaults — no privileged role needed.

### Likelihood Explanation
Requires the combination: instant withdraws enabled, a funded-and-claimed instant request whose epoch equals `defaultRecoveryEpoch`, `pendingInstantWithdraws != 0` at finalization (i.e., a partially unfunded instant queue in that same epoch — plausible when borrower liquidity is short, exactly the scenario preceding a default), and a subsequent default. The window is narrow (same-epoch buffer→default), but partially-funded instant queues naturally co-occur with defaults, and no existing guard clears the stale epoch records — `_ensureDefaultRecoveryInitialized` only checks `pendingInstantWithdraws != 0`, not the by-epoch maps.

### Recommendation
In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user]` per epoch (or track and clear the funded epoch entries) and reduce `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, so paid claims leave no per-epoch residue. Alternatively, recompute `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` from currently unpaid receipts only (e.g., derive from `instantWithdrawsRequests` aggregates rather than cumulative epoch counters).

    _onlyIdleCDO();

    // burn strategy tokens from cdo

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
