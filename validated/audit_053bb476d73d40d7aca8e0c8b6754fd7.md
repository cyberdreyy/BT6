### Title
Withdrawal-Credential Preregistration Binding Can Be Bypassed via the Legacy `Deposit` Path, Allowing Pending-Deposit Principal to Be Redirected to an Unbound Validator — ([File: specs/_features/eip8205/beacon-chain.md])

### Summary
EIP-8205 introduces a `StoredPreregistration` mechanism that is supposed to bind a validator `pubkey` to specific `withdrawal_credentials` *before* the validator's first deposit lands, explicitly "protecting delegated staking deployments against deposit front-running" [1](#0-0) . The binding is enforced only in the new execution-layer `process_deposit_request` path [2](#0-1) . The legacy in-block `Deposit`/`process_deposit`/`apply_deposit` path, which still exists unmodified through Electra/Gloas and is still wired into `process_operations`, never consults `get_active_preregistration` and can add the validator with arbitrary `withdrawal_credentials` [3](#0-2) . Because `apply_pending_deposit` (used to apply the later, correctly-bound deposit) routes purely by pubkey membership rather than by matching withdrawal credentials [4](#0-3) , the pubkey owner can steer any subsequently-arriving deposit to a validator record whose withdrawal credentials they, not the depositor, control.

### Finding Description
`process_preregistration_request` stores a `pubkey → withdrawal_credentials` binding, signed by the pubkey owner, and `process_deposit_request` is explicitly modified to check that binding before enqueueing a `PendingDeposit` [5](#0-4) .

However, the state-transition function still processes legacy `Deposit` operations from `body.deposits` through `process_deposit` → `apply_deposit`, which is unmodified by EIP-8205 and only checks whether the pubkey is *already* a validator, not whether a preregistration binding exists for it:

```python
def apply_deposit(...):
    validator_pubkeys = [v.pubkey for v in state.validators]
    if pubkey not in validator_pubkeys:
        if is_valid_deposit_signature(pubkey, withdrawal_credentials, amount, signature):
            add_validator_to_registry(state, pubkey, withdrawal_credentials, Gwei(0))
        else:
            return
    ...
``` [6](#0-5) 

The pubkey owner (the same party who signed the `PreregistrationRequest`) can trivially produce a *validly signed* legacy `Deposit` for the same pubkey but with **different** `withdrawal_credentials`, because the deposit signature is proof-of-possession of the BLS key, not proof of adherence to any preregistration. This legacy deposit takes precedence and adds the validator to `state.validators` with attacker-chosen credentials, entirely ignoring the still-active `StoredPreregistration` (which is only garbage-collected/consumed by the deposit-request path) [7](#0-6) .

Once this happens, when the legitimately preregistration-checked deposit (submitted by the delegated-staking protocol expecting funds to be bound to its own address `W`) is later applied via `apply_pending_deposit`, the routing logic only checks pubkey membership, not credential equality:

```python
def apply_pending_deposit(state: BeaconState, deposit: PendingDeposit) -> None:
    validator_pubkeys = [v.pubkey for v in state.validators]
    if deposit.pubkey not in validator_pubkeys:
        ...
    else:
        validator_index = ValidatorIndex(validator_pubkeys.index(deposit.pubkey))
        increase_balance(state, validator_index, deposit.amount)
``` [4](#0-3) 

Since the pubkey is already claimed by the attacker's validator record (with credentials `W'`, not `W`), the protocol's deposited Gwei is silently credited to the balance of the validator whose withdrawal credentials point to the attacker's address `W'`. The `PendingDeposit`'s own `withdrawal_credentials` field is never compared to the validator's actual `withdrawal_credentials` at apply time.

This breaks the equality that EIP-8205 preregistration is meant to guarantee: *deposits bound to a preregistered pubkey are paid out under the preregistered withdrawal credentials*. Instead, Gwei intended for owner `W` ends up permanently controlled (including on exit/withdrawal) by `W'`.

### Impact Explanation
This is a concrete Gwei-paid-to-a-non-owner scenario: the entire economic guarantee EIP-8205 was introduced to provide (protecting delegated staking deployments from having deposits hijacked to attacker-controlled withdrawal credentials) is defeated by a code path (`process_deposit`/`apply_deposit`/`apply_pending_deposit`) that was never updated to check the new binding. Any party who can generate the validator's BLS keypair (e.g. a dishonest node operator working for a delegated-staking protocol) can unilaterally redirect the protocol's principal to their own withdrawal address, with no cooperation from any other network participant, client bug, or coalition required — this is achievable by a single actor following the spec exactly as written.

### Likelihood Explanation
High. The attacker only needs to: (1) control the BLS private key for the pubkey used in the preregistration (normal for a node operator generating their own validator keys), and (2) win a simple race to get their legacy `Deposit` included on-chain before/around the time the protocol's `DepositRequest`-driven `PendingDeposit` is applied. No signature forgery, no majority stake, and no protocol/client bug are required — only use of a still-valid, spec-sanctioned legacy code path that the new feature failed to harden.

### Recommendation
- Modify `apply_deposit` (legacy `Deposit` path) to also consult `get_active_preregistration` and reject/redirect deposits for a pubkey with an active preregistration whose `withdrawal_credentials` do not match, mirroring the check already added to `process_deposit_request`.
- Modify `apply_pending_deposit` to verify that `deposit.withdrawal_credentials` matches `state.validators[index].withdrawal_credentials` before crediting balance, rather than routing purely by pubkey membership, so that a deposit cannot be silently absorbed by a validator record with different credentials.
- Alternatively, disable/reject legacy `Deposit` operations entirely for any pubkey that has an active `StoredPreregistration`.

### Proof of Concept
1. Attacker (holds `privkey_V` for `pubkey_V`) signs and submits a `PreregistrationRequest(pubkey=pubkey_V, withdrawal_credentials=W)` on behalf of a delegated-staking protocol; it is processed by `process_preregistration_request` and stored as an active `StoredPreregistration` [8](#0-7) .
2. The protocol prepares a `DepositRequest(pubkey_V, W, amount, sig)` to be submitted later, trusting the binding to guarantee funds go to `W`.
3. Before that request lands, the attacker crafts and gets included a legacy `Deposit(pubkey_V, W', amount', valid_signature_over(pubkey_V, W', amount'))` — validly signed since the attacker owns `privkey_V`. `process_deposit` → `apply_deposit` adds `pubkey_V` to `state.validators` with `withdrawal_credentials = W'`, without consulting the preregistration [6](#0-5) .
4. The protocol's `DepositRequest` is later processed by `process_deposit_request`: preregistration is still active and credentials/signature match `W`, so it is enqueued as a `PendingDeposit` [2](#0-1) .
5. During epoch processing, `apply_pending_deposit` finds `pubkey_V` already present in `state.validators` (from step 3) and simply increases that validator's balance — i.e., the balance of the validator bound to `W'`, not `W` [4](#0-3) .
6. Result: the protocol's deposited Gwei is now controlled by, and will be withdrawn to, `W'` (attacker), even though the entire preregistration mechanism was designed to prevent exactly this outcome.

#### New `is_active_preregistration`

*Note*: Activity is evaluated against the slot of the outstanding parent
payload, whose execution requests are the ones being applied during block
processing. Once stored, a binding therefore remains active for subsequently
processed payloads whose slots are below its stored `expiry_slot`, regardless of
when the expired record is physically swept.

```python
def is_active_preregistration(state: BeaconState, preregistration: StoredPreregistration) -> bool:
    parent_slot = state.latest_execution_payload_bid.slot
    return parent_slot < preregistration.expiry_slot

def process_preregistration_request(state: BeaconState, request: PreregistrationRequest) -> None:
    pubkey = request.pubkey

    # An active binding for this pubkey makes the new request a no-op,
    # whether the duplicate is exact or conflicting
    if get_active_preregistration(state, pubkey) is not None:
        return

    # A pubkey with an existing validator cannot be preregistered
    if pubkey in [validator.pubkey for validator in state.validators]:
        return

    # A pubkey with a valid pending deposit cannot be preregistered
    if is_pending_validator(state.pending_deposits, pubkey):
        return

    # The capacity check counts only active records, so the timing of the
    # garbage-collection sweep does not affect admission. It applies to
    # appends and to replacements alike, since both create an active binding
    active_preregistrations = [
        preregistration
        for preregistration in state.validator_preregistrations
        if is_active_preregistration(state, preregistration)
    ]
    if len(active_preregistrations) >= PREREGISTRATIONS_LIMIT:
        return

    if not is_valid_preregistration_signature(state, request):
        return

    preregistration = StoredPreregistration(
        pubkey=pubkey,
        withdrawal_credentials=request.withdrawal_credentials,
        expiry_slot=state.slot + PREREGISTRATION_EXPIRY_SLOTS,
    )
    index = get_stored_preregistration_index(state, pubkey)
    if index is not None:
        # Replace the expired record in place
        state.validator_preregistrations[index] = preregistration
    else:
        state.validator_preregistrations.append(preregistration)
```

##### Modified `process_deposit_request`

*Note*: The function `process_deposit_request` is modified to enforce an active
preregistration binding.

```python
def process_deposit_request(state: BeaconState, deposit_request: DepositRequest) -> None:
    # [New in EIP8205]
    preregistration = get_active_preregistration(state, deposit_request.pubkey)
    if preregistration is not None:
        if deposit_request.withdrawal_credentials != preregistration.withdrawal_credentials:
            return

        if not is_valid_deposit_signature(
            deposit_request.pubkey,
            deposit_request.withdrawal_credentials,
            deposit_request.amount,
            deposit_request.signature,
        ):
            return

        remove_stored_preregistration(state, deposit_request.pubkey)

    state.pending_deposits.append(
        PendingDeposit(
            pubkey=deposit_request.pubkey,
            withdrawal_credentials=deposit_request.withdrawal_credentials,
            amount=deposit_request.amount,
            signature=deposit_request.signature,
            slot=state.slot,
        )
    )
