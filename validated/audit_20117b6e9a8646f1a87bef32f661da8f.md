No vulnerability found for this question.

**Reasoning:**

The premise of the question misunderstands both the fee model and the reachability of the described scenario.

1. **Fees are charged once, at the source action, not per shard-hop.** The balance-impacting cost (`storage_cost` = `global_contract_storage_amount_per_byte * code.len()`) is deducted from the deploying account's balance exactly once in `action_deploy_global_contract`, before any distribution receipt is even created. [1](#0-0) . The subsequent `GlobalContractDistributionReceipt::forward` calls carry no balance/fee logic whatsoever — they only clone `target_shard` and `already_delivered_shards` metadata while forwarding the same `code`/`nonce`. [2](#0-1) 

2. **Per-shard application charges "compute", not balance.** `apply_distribution_current_shard` charges only a `Compute` budget (`deploy_global_contract_execution_base`/`_per_byte`) used for chunk scheduling limits — this is not a balance/token cost and cannot cause fund loss or theft. [3](#0-2) 

3. **Delivering the code to every shard is the intended function of "Global Contracts", not a bug.** The entire purpose of the feature is: pay once, code becomes usable from every shard via `UseGlobalContractAction`. `forward_distribution_next_shard` walks the shard layout and forwards to exactly one un-visited shard per hop, terminating when `already_delivered_shards` covers all shards. [4](#0-3) 

4. **No attacker-reachable path to force "concurrent forward() calls".** `forward()` is invoked once per `GlobalContractDistribution` receipt application, deterministically by the runtime as part of chunk processing (`apply_global_contract_distribution_receipt`) — it is not parameterized by any attacker-controlled transaction field (no action, deposit, or delegate action can pass a `target_shard` or trigger duplicate forwarding). Producing "two concurrent forward() calls from a stale target_shard" would require duplicating/replaying an internal system receipt during consensus/chunk application, which is a validator/node/consensus-layer concern explicitly excluded by the rules (no chunk-producer/validator access). [5](#0-4) 

5. **Even hypothetical duplicate delivery to the same shard is idempotency-safe and has no balance impact.** `check_and_update_nonce` allows `incoming_nonce >= stored_nonce` by design (documented rationale: nonce is written eagerly at `initiate_distribution` time) so re-processing at worst re-writes identical code/re-precompiles (wasted compute, no token effect) — not a fee bypass. [6](#0-5) [7](#0-6) 

Since no balance/fee is charged per shard delivery, there is nothing to "diverge" between an "authoritative delivery count" and per-shard bookkeeping, and there is no unprivileged-attacker-controllable trigger for the described concurrent-forward scenario.

// Checks if the incoming nonce is fresh and updates the stored nonce. Returns
// true if the nonce is fresh, false if it's stale. The nonce is set
// immediately and the freshness check allows the same nonce (>=).
fn check_and_update_nonce(
    global_contract_data: &GlobalContractDistributionReceipt,
    identifier: &GlobalContractCodeIdentifier,
    state_update: &mut TrieUpdate,
) -> Result<bool, RuntimeError> {
    let nonce_key = TrieKey::GlobalContractNonce { identifier: identifier.clone() };
    let stored_nonce = get_nonce(state_update, &nonce_key)?;
    let incoming_nonce = global_contract_data.nonce();

    // Allow the same nonce since the nonce is updated immediately when
    // initiating distribution to prevent multiple distributions with the same
    // nonce from being initiated.
    if incoming_nonce < stored_nonce {
        return Ok(false);
    }

    set_nonce(state_update, nonce_key, incoming_nonce);
    Ok(true)
}

fn forward_distribution_next_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    epoch_info_provider: &dyn EpochInfoProvider,
    state_update: &mut TrieUpdate,
    receipt_sink: &mut ReceiptSink,
    receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
) -> Result<(), RuntimeError> {
    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(
        global_contract_data
            .already_delivered_shards()
            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );
    let Some(next_shard) = shard_layout
        .shard_ids()
        .filter(|shard_id| !already_delivered_shards.contains(&shard_id))
        .next()
    else {
        return Ok(());
    };
