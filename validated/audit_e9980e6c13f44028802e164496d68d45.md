### Title
Vote commission `u16` basis-points value is silently clamped to `u8::MAX` when reported to unprivileged RPC callers, misrepresenting the true commission rate - (File: `vote/src/vote_state_view.rs`, `programs/vote/src/vote_state/handler.rs`)

### Summary
Since SIMD-0291/SIMD-0185, a validator's vote commission is stored internally as `inflation_rewards_commission_bps: u16` (0–65,535 bps), but the legacy `commission()` accessor exposed to callers (including RPC) converts this to a `u8` by clamping any value above 25,500 bps (250%) down to `u8::MAX` (255, i.e. "100%" in the legacy 0–100 scale). This mirrors the `UniProxy.properDepositRatio` bug class: an out-of-range value is silently forced into a bounded display range instead of being rejected or faithfully represented, so RPC consumers cannot distinguish a validator with 100% commission from one with, say, 655% commission.

### Finding Description
`VoteStateHandler::commission()` and `VoteStateView::commission()` both clamp `inflation_rewards_commission_bps` (a `u16` that SIMD-0291 explicitly allows to hold any value, since capping happens only later during reward calculation, not at storage time) to `u8::MAX` when downcasting for legacy display/consumption: [1](#0-0) [2](#0-1) 

The test comments explicitly acknowledge the intent to avoid "misleading values" from `u16`-to-`u8` wraparound, but the chosen fix (clamping to 255) still collapses all values from 25,500 bps up to 65,535 bps into a single "100%" display value, discarding the actual magnitude — exactly analogous to how `UniProxy.properDepositRatio` clamped `depositRatio`/`hypeRatio` into `[0.1, 10]` before comparison, allowing arbitrarily large true ratios to be represented/accepted as if they were within the intended bound.

This `commission()` value is surfaced through the RPC layer (e.g. `getVoteAccounts`), which is called by unprivileged/unauthenticated RPC clients: [3](#0-2) 

### Impact Explanation
Any unprivileged RPC caller querying vote account state (e.g. via `getVoteAccounts` or by decoding the vote account) receives a commission value that has been silently clamped rather than accurately reported. A validator (or a malicious/compromised vote account) could set `inflation_rewards_commission_bps` far above 10,000 (100%), and RPC/delegation tooling relying on `commission()` would report it as a flat 255/"100%" instead of reflecting the true, more extreme value. This is a wrong-data-returned condition reachable by any RPC query — falling under the accepted "wrong-slot/fork/account data returned" impact category, since delegators and staking UIs make decisions based on this misreported field.

### Likelihood Explanation
Reaching this code path requires no privilege: any RPC client calling `getVoteAccounts` or fetching/decoding a vote account triggers the `commission()` conversion. The only precondition is that a vote account's `inflation_rewards_commission_bps` be set above 25,500 (achievable by the vote account's authorized party through normal `set_inflation_rewards_commission_bps`-style updates, which the code comments confirm are permitted above 10,000 bps at the program level).

### Recommendation
Do not clamp the `u16` basis-points value to a `u8` display value. Either change the RPC/public-facing type to a wider integer (e.g., `u16` or `u32`) that can faithfully represent the full range, or explicitly document/return an out-of-range sentinel/error rather than silently coercing to 255, so RPC consumers cannot mistake a clamped display value for the true commission.

### Proof of Concept
1. Set a vote account's `inflation_rewards_commission_bps` to a value greater than 25,500 (e.g., `u16::MAX = 65535`) via the vote program's commission-setting instruction (permitted at the program level per the handler tests).
2. Query the account via RPC `getVoteAccounts` (or decode the vote state directly) as an unprivileged client.
3. Observe that the returned `commission` field reports `255` regardless of whether the true stored value was 25,501 or 65,535, as demonstrated by the parameterized test cases: [4](#0-3) [5](#0-4) 

**Note on confidence:** I was unable to retrieve the exact implementation body/line numbers of the `commission()` getters themselves (only the corresponding test files, which encode and verify the clamping behavior) before running out of tool iterations. The behavior is confirmed via these tests and their explanatory comments, but readers should independently verify the getter implementations in `vote/src/vote_state_view.rs` and `programs/vote/src/vote_state/handler.rs` for full certainty.

    fn test_v4_commission_getter_clamps_extreme_bps() {
        // Verify commission() clamps to u8::MAX for extreme bps values
        // instead of wrapping around. SIMD-0291 allows storing any u16 as
        // inflation_rewards_commission_bps — the legacy getter must not
        // produce misleading values.
        for (bps, expected) in [
            (10_000, 100),   // normal
            (25_500, 255),   // exact boundary, no clamping needed
            (25_501, 255),   // just past boundary, clamped
            (25_600, 255),   // would wrap to 0 without clamping
            (u16::MAX, 255), // would wrap to 143 without clamping

            let vote_state = VoteStateV4 {
                inflation_rewards_commission_bps: bps,
                ..Default::default()
            };
            let handler = VoteStateHandler::new_v4(vote_state);
            assert_eq!(handler.commission(), expected);
        }

    fn test_vote_state_view_v4_commission_clamps() {
        // The VoteStateView commission() getter must clamp values
        // > u8::MAX to u8::MAX for V4 accounts with large bps.
        for (bps, expected) in [
            (0u16, 0u8),
            (10_000, 100),

            let state = VoteStateV4 {
                inflation_rewards_commission_bps: bps,
                ..VoteStateV4::default()
            };
            let versioned = VoteStateVersions::new_v4(state);
            let buf = Arc::new(bincode::serialize(&versioned).unwrap());
            let view = VoteStateView::try_new(buf).unwrap();
            assert_eq!(view.commission(), expected);
        }
