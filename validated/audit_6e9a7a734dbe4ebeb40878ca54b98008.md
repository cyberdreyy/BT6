### Title
Response cache key omits `WorkflowID`, causing cross-workflow HTTP response confusion in the HTTP capability gateway handler - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

### Summary
The `responseCache` used by the HTTP Handlers V2 gateway (`core/services/gateway/handlers/capabilities/v2/response_cache.go`) is documented as providing "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage." However, the underlying `OutboundHTTPRequest.Hash()` cache key is only "a hash of the request (method, URL, headers, body, workflowOwner)" and explicitly excludes `WorkflowID`, as both the code comment and the corresponding unit tests confirm. This is directly analogous to the `Seer.sol` bug: a value that should be one of two inputs used together (here, `WorkflowID` alongside `WorkflowOwner`) is silently dropped, so the cache boundary is narrower than documented and than the system relies on for correctness.

### Finding Description
`responseCache` stores HTTP action responses keyed by `req.Hash()`: [1](#0-0) [1](#0-0) 

The struct's own comment states the hash is only over "method, URL, headers, body, workflowOwner" — `WorkflowID` is not part of the key: [2](#0-1) 

This is confirmed by `TestRequestHash` in the test suite, which explicitly asserts that two requests with different `WorkflowID` values but otherwise identical fields produce the **same** hash: [3](#0-2) 

while a difference in `WorkflowOwner` alone does change the hash: [4](#0-3) 

Yet the module's own README documents the opposite guarantee — that cache entries are scoped by workflow ID specifically to prevent cross-workflow leakage: [5](#0-4) 

`Fetch`/`Set` are called directly from `makeOutgoingRequest` in `http_handler.go`, using `req.Hash()` as the sole cache key, with no additional `WorkflowID` disambiguation performed by the caller: [6](#0-5) 

The `Fetch` implementation itself only uses `cacheKey := req.Hash()` for both the fast-path lookup and the singleflight-guarded write path, so any two requests colliding on `(method, URL, headers, body, workflowOwner)` — regardless of `WorkflowID` — will read and write the exact same cache slot: [7](#0-6) 

**Root cause parallel to the reported bug class:** just as `Seer.sol` computed two candidate values (`high`, `low`) but only propagated one (`high`) while discarding the other needed for correct, safe usage, the gateway's cache key computes/derives request identity from multiple candidate discriminators (owner, ID) but only threads `WorkflowOwner` through the hash while silently discarding `WorkflowID`, despite the system's documented design (and the caller's semantics, `CacheSettings.Store`/`MaxAgeMs` scoped "per workflow") assuming per-workflow isolation.

### Impact Explanation
Any two workflows sharing the same `WorkflowOwner` (e.g., a single builder/owner address that deploys multiple distinct workflows, or workflows deployed on behalf of multiple end users under one on-chain owner identity — a normal, unprivileged multi-workflow deployment pattern) that issue outbound HTTP actions with the same `Method`/`URL`/`Headers`/`Body` but different `WorkflowID` will read and write the same cache entry. This means:
- Workflow B can receive Workflow A's cached HTTP response body (`Fetch` returns `cachedResp.response` on a hash collision) even though the two are logically distinct workflows.
- If HTTP action responses influence workflow logic (e.g., pricing data, authorization decisions, personalized data, or trigger conditions gating on-chain actions), a workflow can act on stale or foreign data belonging to a sibling workflow, defeating the intended per-workflow cache isolation and producing incorrect, cross-workflow "response confusion."
- This silently violates the documented "Workflow Isolation" guarantee, which downstream workflow authors and operators rely on when setting `CacheSettings.Store=true`/`MaxAgeMs>0` per-workflow.

### Likelihood Explanation
Medium: exploitation/triggering does not require a malicious node or network-layer manipulation — it only requires two workflows under the same owner making outbound HTTP action requests with identical `Method`/`URL`/`Headers`/`Body` while caching is enabled (`CacheSettings.Store`/`MaxAgeMs`), which is a realistic and unprivileged usage pattern (e.g., templated workflows, or multiple workflow instances hitting the same public API endpoint). No authentication bypass is needed; it's a functional cache-key defect reachable purely through normal HTTP capability action usage.

### Recommendation
Include `WorkflowID` (in addition to `WorkflowOwner`) in the cache-key hash computation for `OutboundHTTPRequest`, matching the documented behavior in the README, so that cache entries are correctly scoped per-workflow and not merely per-owner. Add/extend tests to assert that different `WorkflowID` values under the same `WorkflowOwner` produce different hashes, and audit other cache/response-aggregation paths in this handler for the same "documented isolation vs. actual key derivation" mismatch.

### Proof of Concept
1. Two workflows, `WF-A` (`WorkflowID = "workflow-A"`) and `WF-B` (`WorkflowID = "workflow-B"`), are deployed under the same `WorkflowOwner`.
2. Both issue an `OutboundHTTPRequest` with identical `Method`, `URL`, `Headers`, and `Body`, and both set `CacheSettings.Store = true` / `CacheSettings.MaxAgeMs > 0`.
3. `WF-A`'s request executes first via `makeOutgoingRequest` → `responseCache.Fetch`, performs the real HTTP call, and stores the result under `req.Hash()`.
4. `WF-B` issues its request; because `req.Hash()` does not include `WorkflowID` (per `response_cache.go` lines 15-17 and confirmed by `response_cache_test.go` lines 139-149), the fast-path check in `Fetch` finds the same cache key and returns `WF-A`'s cached response directly to `WF-B`, without making a new HTTP call or validating that the response belongs to `WF-B`'s workflow. func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
```go
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
```
