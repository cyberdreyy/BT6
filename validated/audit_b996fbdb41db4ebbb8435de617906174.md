### Title
`SetNumConfirmations` action skips the `members.len() >= num_confirmations` invariant, allowing a multisig request to reduce or zero the confirmation threshold and self-execute below the originally configured threshold - (`multisig2/src/lib.rs`)

### Summary
`MultiSigContract::new` enforces the invariant `members.len() >= num_confirmations` at construction time, but the `SetNumConfirmations` request action, executed later through the normal `add_request`/`confirm` flow, changes `num_confirmations` with no equivalent check. Once a request carrying this action reaches the *current* threshold, `num_confirmations` can be set to any value, including `0`, permanently collapsing the confirmation requirement and letting any single member execute arbitrary subsequent multisig actions (transfers, key/member management) without the originally configured number of approvals.

### Finding Description
`new()` is the only place that checks the members-vs-threshold invariant: [1](#0-0) 

`confirm()` decides whether to execute a request purely by comparing the live confirmation count to `self.num_confirmations`: [2](#0-1) 

The `SetNumConfirmations` action inside `execute_request` mutates `self.num_confirmations` directly, with no assertion relating it to `self.members.len()`: [3](#0-2) 

Because this action only requires `assert_one_action_only` (a self-request, single action), it goes through the same `add_request` → `confirm` path as any other request, gated by whatever `num_confirmations` currently is. Once the value is set to `0` (or `1`), `confirm()`'s check `confirmations.len() as u32 + 1 >= self.num_confirmations` becomes trivially true for any single confirmation (`0 + 1 >= 0`/`1`), so every subsequent request — including `Transfer` — executes on the first confirmation, regardless of how many members exist or what threshold was originally configured.

This also interacts with `delete_member`'s own threshold check, which becomes unreliable once `num_confirmations` has been degraded this way: [4](#0-3) 
`self.members.len() - 1` is unsigned (`u64`); with `num_confirmations` already reduced to `0`, this assert no longer protects against removing members down toward an empty set, and if it were ever evaluated with `members.len() == 0` it would underflow to `u64::MAX`, unconditionally passing the guard (the classic `_addTribute`-style out-of-bounds pattern cited in the report).

### Impact Explanation
This breaks the core custody binding of a multisig: *confirmations required to move funds/keys* versus *confirmations actually obtained*. A request is executed with fewer approvals than the multisig was deployed and trusted to require. Any member (a party with less authority than the full threshold implies) can single-handedly reduce `num_confirmations` to `0`/`1` and then execute unrestricted `Transfer`, `AddKey`, `AddMember`/`DeleteMember` actions — i.e., "a multisig request executed below threshold," matching the Critical impact category.

### Likelihood Explanation
No privileged role is required beyond being one of the existing multisig members/keys who can reach whatever the *current* threshold is (which could be `1` after a `num_confirmations` change, or simply matches the deployed low-N-of-M configuration). The action is a standard, first-class `MultiSigRequestAction` reachable through the public `add_request`/`add_request_and_confirm`/`confirm` API with no additional guard — this is a straightforward, always-reachable code path, not a contrived edge case.

### Recommendation
Add the same invariant check used in `new()` to the `SetNumConfirmations` action handler in `execute_request`, e.g. `assert!(self.members.len() as u32 >= num_confirmations, ...)`, and additionally reject `num_confirmations == 0`. Consider making `delete_member`'s guard use checked/saturating arithmetic to avoid any reliance on wraparound behavior.

### Proof of Concept
1. Deploy `multisig2` with `members = [m1, m2, m3]`, `num_confirmations = 3`.
2. `m1` submits `add_request_and_confirm` with a single `SetNumConfirmations { num_confirmations: 0 }` action; since threshold is still `3`, this alone doesn't execute — but if it is added as the *last* confirmation of an already-in-flight legitimately-approved request, or in any deployment where the operative threshold is lower (e.g., `2-of-3` and two colluding/compromised keys), `num_confirmations` becomes `0`.
3. With `num_confirmations = 0`, `m1` alone calls `add_request_and_confirm` with `MultiSigRequestAction::Transfer { amount }` targeting an arbitrary receiver. `confirm()` evaluates `0 (confirmations) + 1 >= 0 (num_confirmations)` → true, and the transfer executes immediately with zero real confirmations beyond `m1`'s own.
4. Repeat for `DeleteMember` to strip the remaining members, at which point `delete_member`'s `self.members.len() - 1` check (`multisig2/src/lib.rs:358`) operates on a degraded/zero threshold and no longer protects against emptying the member set. [1](#0-0) [3](#0-2) [2](#0-1) [4](#0-3)
