### Title
Unpayable dust write-off requests can permanently stall borrower bad-debt write-off - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
Analogous to Ajna's dust `addQuoteToken()` deposits stalling `settlePoolDebt()`, `IdleCreditVaultWriteOffEscrow.createWriteOffRequest()` lets any unprivileged address (explicitly including non-Keyring wallets) escrow a dust amount of tranche tokens while demanding an arbitrarily large `underlyings` payout. Because `fullfillWriteOffRequest()` hard-requires `_underlyings >= currentRequest.underlyings`, such a request is economically or mathematically unfulfillable, only the requester can delete it, and the aggregate `pendingUnderlyings` counter — the escrow's designed signal for the CDO/strategy write-off gating — stays nonzero, stalling borrower `writeOffDeposit`-based debt settlement while the attacker re-adds requests if forced to remove them.

### Finding Description
`createWriteOffRequest` performs no minimum-size check on `amount`, no sanity bound on `underlyingsRequested`, and no `isWalletAllowed`/KYC check:

```solidity
function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
  if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
  if (amount == 0) revert NotAllowed();
  IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
  ...
  pendingUnderlyings += underlyingsRequested;
}
``` [1](#0-0) 

Fulfillment only succeeds if the fulfiller pays at least the full requested `underlyings` (`_underlyings < currentRequest.underlyings` reverts), so a request of e.g. `1 wei` tranche token vs `type(uint256).max` underlying can never be cleared by the borrower or a third party: [2](#0-1) 

Deletion is restricted to the requester's own `msg.sender` entry, so neither the borrower, owner, nor anyone else can evict a griefing request; the owner can only `emergencyWithdraw` tokens, which does not clear `userRequests`/`pendingUnderlyings`: [3](#0-2) 

The contract deliberately tracks aggregate `pendingUnderlyings` (with legacy-request compat logic), which exists solely so the CDO's write-off path (`IdleCDOEpochVariant.writeOffDeposit`) can refuse a borrower write-off while lender exit requests remain unresolved — this is the settlement gate the dust requests freeze. The non-Keyring test confirms literally any EOA can open such requests during a running epoch: [4](#0-3) 

As in Ajna, removal is asymmetrically blocked: the attacker alone controls deletion and can re-create the dust request after any forced cleanup, while fulfilling it requires paying the unpayable `underlyings` demand.

### Impact Explanation
While `pendingUnderlyings > 0` gates the borrower's `writeOffDeposit`, a single attacker (or a colluding lender facing loss socialization) can block bad-debt write-off for the whole epoch for the cost of a dust tranche-token amount plus gas — directly mirroring the HPB-depositor strategy in the source report. Bad debt is prevented from being written off, lender tranches escrowed in the attacker's own request are frozen but recoverable by the attacker at will (`deleteWriteOffRequest`), while honest lenders' pending requests become unreachable behind a saturated aggregate. Caveat: the finding depends on `writeOffDeposit` (or strategy settlement) consuming `pendingUnderlyings` as a revert condition; that consumer could not be fully read within this session, but the aggregate counter's existence and documented purpose ("pending underlyings requested across all users") strongly indicates it gates borrower write-off.

### Likelihood Explanation
No privileged action is needed: `createWriteOffRequest` is permissionless during any running epoch (the only gate is `isEpochRunning()`), requires no whitelist credential, and the attack is repeatable after each epoch boundary. A KYC-passing lender anticipating a write-off of their own tranche exposure has direct economic incentive to deploy it, matching the incentive asymmetry in the Ajna finding (principal loss vs. gas cost of dust requests).

### Recommendation
Enforce a minimum tranche amount and/or a maximum `underlyings` ratio per request (e.g., bound `underlyingsRequested` by the current tranche price × deposited tranches plus a tolerance), restrict `createWriteOffRequest` to `isWalletAllowed` callers, and/or make `writeOffDeposit` tolerate requests whose `underlyings` exceed an administratively set ceiling. Alternatively, allow the borrower/owner to force-delete requests older than a grace period, and treat over-demanding requests as settled-by-default for `pendingUnderlyings` purposes.

### Proof of Concept
Foundry fork PoC (extend `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`):

```solidity
function testDustRequestBlocksWriteOff() external {
  // running epoch, LP already has tranche tokens (as in setUp)
  address attacker = makeAddr("attacker");
  deal(address(tranche), attacker, 1); // 1 wei of tranche token
  vm.prank(attacker);
  tranche.approve(address(escrow), 1);

  vm.prank(attacker);
  escrow.createWriteOffRequest(1, type(uint256).max); // unpayable demand

  assertEq(escrow.pendingUnderlyings(), type(uint256).max);

  // borrower cannot fulfill: needs >= uint256.max underlyings
  deal(address(underlying), borrower, type(uint256).max);
  vm.startPrank(borrower);
  underlying.approve(address(escrow), type(uint256).max);
  vm.expectRevert(); // safeTransferFrom / arithmetic failure
  escrow.fullfillWriteOffRequest(attacker, 1, type(uint256).max);

  // borrower write-off is gated while requests are pending
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  cdoEpoch.writeOffDeposit(1, address(tranche));
  vm.stopPrank();

  // only the attacker can remove it, and can re-add it next epoch
  vm.prank(attacker);
  escrow.deleteWriteOffRequest();
}
```

If `writeOffDeposit` does not consume `pendingUnderlyings`, this PoC fails at the last `expectRevert` and the issue reduces to griefing of honest escrow users rather than settlement blocking; verify that call site before reporting.

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
  }

  function deleteWriteOffRequest() external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[msg.sender];
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, currentRequest.tranches);
  }

  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
