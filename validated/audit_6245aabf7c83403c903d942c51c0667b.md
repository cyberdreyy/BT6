### Title
Write-off fulfilment parameters are public calldata — any fulfiller can front-run the borrower's `fullfillWriteOffRequest` and steal the below-NAV tranche discount intended for debt write-off - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol])

### Summary
Analogous to CVE-2023-35789 — where credentials passed as command-line arguments become visible to any local observer — `fullfillWriteOffRequest` requires the fulfiller to echo the exact request parameters (`_tranches`, `_underlyings`) as plaintext calldata, and the contract explicitly allows "any wallet" to call it. An attacker observing the borrower's pending fulfilment transaction can copy the arguments verbatim and front-run it, buying the lender's discounted tranche tokens for themselves. The borrower loses the write-off discount they were paying to capture, and the attacker's cost is bounded by the lender's ask while the received tranche tokens retain full claim on vault NAV.

### Finding Description
`IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` is permissionless by design (`// @dev this function can be called by any wallet`) and validates the fill by checking `currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings` [1](#0-0) . Both the stored ask (`userRequests[_user]`) and the fulfiller's exact payment amount are fully observable: the ask is public storage, and the fulfiller's tx calldata is visible in the mempool before execution. There is no commit-reveal, no fulfiller whitelist, and no binding of the fulfilment to `msg.sender` — whoever lands first with matching parameters gets the tranche tokens [2](#0-1) .

The economic premise of the escrow is that the borrower fulfils requests at a discount to NAV, then calls `writeOffDeposit` on the CDO to burn the tranches against their debt — the gap between `_underlyings` paid and the tranches' redemption value is the borrower's profit and the lender's early-exit price. A front-running fulfiller captures that entire spread: they pay `_underlyings` and receive tranche tokens redeemable at a higher implied value through normal withdraw requests.

Existing guards do not stop this: `nonReentrant` is irrelevant to front-running, `WrongRequest` is satisfied by copying calldata, and the function has no fulfiller authentication by explicit design.

### Impact Explanation
Theft of the write-off spread from the honest borrower. Quantified loss per fulfilment: `tranches × virtualPrice(tranche) − _underlyings` (minus exit fee), which is exactly the discount the lender offered. Example: a lender escrows 100,000 tranche tokens (NAV ≈ $100,000) asking $60,000; the attacker front-runs with identical parameters, pays $60,000, receives tranches worth ~$100,000 of vault claims — a ~$40,000 transfer of value that the protocol design allocated to the borrower for retiring debt. Because the borrower can no longer obtain tranches at that price, the debt write-off either does not happen or must be renegotiated at a worse price.

### Likelihood Explanation
Medium. It requires an active write-off escrow request priced below NAV and a fulfilment transaction broadcast publicly — both are normal protocol operations while the epoch is running (`createWriteOffRequest` reverts unless `isEpochRunning()`). Any unprivileged EOA qualifies as a fulfiller; no KYC, no tranche holdings, no privileged role is needed. Standard mempool monitoring / generalised front-running infrastructure detects and copies the calldata mechanically. The only mitigants are private transaction relays used at the borrower's discretion, which the contract does not enforce.

### Recommendation
Bind fulfilment to an authorized fulfiller or a commit step, e.g.:
- Store an optional `expectedFulfiller` (or borrower-only flag) on `WriteOffRequest` and check `msg.sender` in `fullfillWriteOffRequest`; or
- Accept a hash of the fulfil terms at request creation (`createWriteOffRequest` stores `fulfilHash`), requiring the fulfiller to supply matching parameters — but crucially also check `msg.sender == borrower` or an allowlisted party, since hashing alone still leaks nothing yet still permits any caller; or
- Simplest: since the stated purpose is debt write-off by the borrower, gate `fullfillWriteOffRequest` with `if (msg.sender != borrower) revert NotAllowed()` — this preserves trustlessness (lender gets paid their stored ask) while removing the front-running surface entirely.

### Proof of Concept
Foundry fork sketch:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract WriteOffFrontrunPoC is Test {
    // ... existing test setup deploying IdleCDOEpochVariant + IdleCreditVaultWriteOffEscrow ...

    function testFrontrunBorrowerFulfilment() public {
        // Epoch running; LENDER escrows 100_000e18 tranches asking 60_000e6 underlying
        uint256 tranches = 100_000e18;
        uint256 ask = 60_000e6;

        vm.startPrank(LENDER);
        tranche.approve(address(escrow), tranches);
        escrow.createWriteOffRequest(tranches, ask);
        vm.stopPrank();

        // Attacker (arbitrary EOA) sees borrower's fullfillWriteOffRequest(LENDER, tranches, ask)
        // in the mempool and submits identical calldata first.
        address attacker = makeAddr("frontrunner");
        deal(underlying, attacker, ask);
        vm.startPrank(attacker);
        IERC20(underlying).approve(address(escrow), ask);
        escrow.fullfillWriteOffRequest(LENDER, tranches, ask);
        vm.stopPrank();

        // Attacker received the discounted tranches; borrower's tx now reverts with Is0()
        assertEq(tranche.balanceOf(attacker), tranches);
        vm.prank(BORROWER);
        vm.expectRevert(Is0.selector);
        escrow.fullfillWriteOffRequest(LENDER, tranches, ask);

        // Attacker's profit: tranche NAV claim (~100k) minus ~60k paid, minus 0.1% exit fee
        uint256 navValue = tranches * cdo.virtualPrice(address(tranche)) / 1e18;
        assertGt(navValue, ask);
    }
}
```

Uncertainty note: I could not fully verify the `writeOffDeposit` flow details in `IdleCDOEpochVariant.sol` within the iteration budget, but the front-running vulnerability in `fullfillWriteOffRequest` stands on its own regardless of the post-purchase write-off mechanics — the permissionless fill plus fully observable parameters is sufficient for the theft.

  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }
