### Title
Permissionless `propagate_staked_settings` bypasses `FREEZE_SETTINGS`, overwriting risk parameters on frozen staked banks - ([File: programs/marginfi/src/instructions/marginfi_group/propagate_staked_settings.rs])

### Summary
`propagate_staked_settings` is a fully permissionless instruction that unconditionally copies `StakedSettings` fields (oracle, asset weights, deposit limit, `total_asset_value_init_limit`, `oracle_max_age`, `risk_tier`, and staked-oracle flags) onto any `ASSET_TAG_STAKED` bank, without ever checking the bank's `FREEZE_SETTINGS` flag. This lets any unprivileged caller overwrite exactly the fields that `FREEZE_SETTINGS` is documented to make immutable, breaking the "credible commitment" invariant for staked banks regardless of transaction ordering.

### Finding Description
`lending_pool_configure_bank` correctly honors `FREEZE_SETTINGS`: when the flag is set, `bank.configure_unfrozen_fields_only` restricts admin updates to `deposit_limit`/`borrow_limit` only [1](#0-0) . Likewise `lending_pool_configure_bank_interest_only` and `lending_pool_configure_bank_limits_only` check the flag before mutating anything else [2](#0-1) .

However, `propagate_staked_settings` — a permissionless instruction reachable by any signer with no authority checks in its `Accounts` struct — writes directly to `bank.config.oracle_keys[0]`, `asset_weight_init`, `asset_weight_maint`, `deposit_limit`, `total_asset_value_init_limit`, `oracle_max_age`, `risk_tier`, and the staked-oracle bits of `bank.flags`, with **no check of `FREEZE_SETTINGS` at all**: [3](#0-2) 

The `PropagateStakedSettings` accounts struct requires only that the bank belongs to the group and has `ASSET_TAG_STAKED`; there is no signer with special privilege and no `FREEZE_SETTINGS` gate: [4](#0-3) 

Contrast this with the documented invariant: "`FREEZE_SETTINGS`... provides a credible commitment that the bank's risk parameters, oracle configuration, interest rate curves, and other settings will not change. It can only be set through the `configure_bank` instruction by the group admin" [5](#0-4) .

Exploit flow for a staked bank with `FREEZE_SETTINGS` set:
1. Group admin freezes a staked bank via `configure_bank(freeze_settings=true)`, intending oracle/weights/limits/risk_tier to be immutable.
2. At any later time (no race condition or same-slot interleaving needed — this works unconditionally, any block, forever), an unprivileged caller invokes the permissionless `propagate_staked_settings` for that bank.
3. The instruction unconditionally overwrites `oracle_keys[0]`, `asset_weight_init/maint`, `deposit_limit`, `total_asset_value_init_limit`, `oracle_max_age`, `risk_tier`, and `STAKED_ORACLE_FLAGS`, sourced from the group's `StakedSettings` PDA (itself editable only by the group admin, but its content need not match what the admin intended when freezing this specific bank — e.g., the admin may have intentionally diverged a frozen bank's config from group defaults via `configure_bank` before freezing it, as the code comment on `StakedSettings` explicitly anticipates: "Administrators can also edit the bank manually, i.e. with `configure_bank`, to temporarily make changes such as raising the deposit limit for a single bank" [6](#0-5) ).
4. The frozen bank's risk parameters silently diverge from the admin's frozen/intended values, with no `FREEZE_SETTINGS` violation logged or blocked.

The interleaving/TOCTOU framing in the question is not actually necessary to trigger this: because `propagate_staked_settings` never checks the flag, the bypass is durable and repeatable at will, not merely a race window.

### Impact Explanation
This breaks the authority boundary that `FREEZE_SETTINGS` is meant to enforce for staked-collateral banks: an unprivileged, permissionless caller can change the bank's oracle, asset weights, deposit limit, `total_asset_value_init_limit`, and risk tier even after the admin has explicitly frozen the bank to "credibly commit" to those values. This is a durable state inconsistency with direct financial impact — asset weights and oracle changes affect collateral valuation and liquidation eligibility, and risk_tier changes can make positions instantly liquidatable or worthless as collateral. This is not a pure liquidity issue, oracle-bad-data issue, or DoS — it is an authorization-bypass / invariant-violation on bank risk configuration, in scope under the bounty rules.

### Likelihood Explanation
Fully feasible with no special preconditions beyond: (a) the target bank being an `ASSET_TAG_STAKED` bank with `FREEZE_SETTINGS` set, and (b) the group's `StakedSettings` account differing from the frozen bank's current config (a routine state, since staked settings can be edited by the admin for the group at any time via `edit_staked_settings`, independent of any specific bank's frozen state). The action requires no signature/authority beyond paying the transaction fee, and is repeatable indefinitely.

### Recommendation
In `propagate_staked_settings`, load the bank's `FREEZE_SETTINGS` flag and either: (a) skip mutating frozen fields entirely (mirroring `configure_unfrozen_fields_only` semantics), or (b) reject the instruction outright with an error (e.g. `MarginfiError::Unauthorized` or a new `BankFrozen` error) when `bank.get_flag(FREEZE_SETTINGS)` is true, so that a frozen staked bank is fully excluded from permissionless propagation just as it is excluded from admin `configure_bank` mutation of the same fields.

### Proof of Concept
Rust integration test (bankrun/program-test style, extending existing `s06_propagateSets` coverage):
1. Create a group with `StakedSettings`, add a staked bank, and let `propagate_staked_settings` apply initial settings.
2. As admin, call `lending_pool_configure_bank` with `freeze_settings = Some(true)` on the staked bank; assert `bank.flags & FREEZE_SETTINGS != 0`.
3. As admin, call `edit_staked_settings` to change `oracle`, `asset_weight_init`, `deposit_limit`, `risk_tier` on the group's `StakedSettings` (simulating settings drift unrelated to the specific frozen bank).
4. As an arbitrary unprivileged keypair (no admin signature), call permissionless `propagate_staked_settings` targeting the frozen bank.
5. Assert the call succeeds (no `FREEZE_SETTINGS`-related error) and that `bank.config.oracle_keys[0]`, `asset_weight_init`, `deposit_limit`, `risk_tier` now equal the new `StakedSettings` values — proving the frozen bank's "immutable" fields were mutated by an unprivileged, permissionless caller.
6. Expected (fixed) behavior: the call should either no-op on frozen fields or fail, and `bank.config` should remain unchanged post-freeze.

pub fn propagate_staked_settings(ctx: Context<PropagateStakedSettings>) -> Result<()> {
    let settings = ctx.accounts.staked_settings.load()?;
    let mut bank = ctx.accounts.bank.load_mut()?;

    let (oracle_before, oracle_after) = (bank.config.oracle_keys[0], settings.oracle);

    bank.config.oracle_keys[0] = settings.oracle;
    bank.config.asset_weight_init = settings.asset_weight_init;
    bank.config.asset_weight_maint = settings.asset_weight_maint;
    bank.config.deposit_limit = settings.deposit_limit;
    bank.config.total_asset_value_init_limit = settings.total_asset_value_init_limit;
    bank.config.oracle_max_age = settings.oracle_max_age;
    bank.config.risk_tier = settings.risk_tier;
    bank.flags &= !STAKED_ORACLE_FLAGS;
    bank.flags |= settings.flags & STAKED_ORACLE_FLAGS;

    // Only validate the oracle info if it has changed
    if oracle_before != oracle_after {
        bank.config
            .validate_oracle_setup(ctx.remaining_accounts, None, None, None)?;
    }

    bank.config.validate()?;

    Ok(())
}

#[derive(Accounts)]
pub struct PropagateStakedSettings<'info> {
    pub marginfi_group: AccountLoader<'info, MarginfiGroup>,

    #[account(
        has_one = marginfi_group @ MarginfiError::InvalidGroup
    )]
    pub staked_settings: AccountLoader<'info, StakedSettings>,

    #[account(
        mut,
        constraint = {
            let bank = bank.load()?;
            bank.group == marginfi_group.key() &&
                bank.config.asset_tag == ASSET_TAG_STAKED
        }
    )]
    pub bank: AccountLoader<'info, Bank>,
}
