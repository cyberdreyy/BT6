### Title
Multisig `new()` does not verify member uniqueness, allowing an unreachable confirmation threshold that permanently freezes contract funds - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::new` accepts a caller-supplied `members: Vec<MultisigMember>` and validates the confirmation threshold using `members.len()` — the raw list length — before deduplicating entries. Deduplication only happens implicitly afterward, one member at a time, via `self.members.insert(...)` on an `UnorderedSet`. If the supplied list contains duplicate entries (the same `AccountId` or `PublicKey` repeated), the length check passes even though the resulting *unique* member set is smaller than `num_confirmations`, making the threshold permanently unreachable and freezing any funds the contract subsequently holds. This mirrors the reported TSS bug class: the initializer trusts an unvalidated "players/members" array for a security-critical count without checking uniqueness.

### Finding Description
In `new`:
```rust
pub fn new(members: Vec<MultisigMember>, num_confirmations: u32) -> Self {
    assert(
        members.len() >= num_confirmations as usize,
        "Members list must be equal or larger than number of confirmations",
    );
    ...
    for member in members {
        promise = multisig.add_member(promise, member);
    }
    multisig
}
``` [3](#0-2) 

The uniqueness check happens nowhere in this path. `add_member` inserts into `UnorderedSet<MultisigMember>`, which silently no-ops on duplicate insertion:
```rust
fn add_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    self.members.insert(&member.clone().into());
    ...
}
``` [2](#0-1) 

So calling `new(members: [A, A, A], num_confirmations: 3)` passes the `members.len() >= num_confirmations` assertion (3 >= 3), but after the loop `self.members` contains only the single unique member `A`. `num_confirmations` is stored as `3`, yet only one distinct key/account (`A`) can ever call `confirm`. Because `confirm`'s per-request `confirmations` set is keyed by `member.to_string()` (a `HashSet<String>`), the same member cannot confirm twice for a single request:
```rust
assert(
    !confirmations.contains(&member.to_string()),
    "Already confirmed this request with this key",
);
``` [4](#0-3) 

With only one real member and a threshold of 3, `confirmations.len() as u32 + 1` can never reach `3`. No request — including `DeleteMember`, `SetNumConfirmations`, or any `Transfer` — can ever be executed, because every mutating action (including lowering the threshold) itself requires reaching the same unreachable `num_confirmations`. Contrast this with `delete_member`, which does enforce a live invariant against the actual `self.members.len()`:
```rust
assert(
    self.members.len() - 1 >= self.num_confirmations as u64,
    "Removing given member will make total number of members below number of confirmations",
);
``` [5](#0-4) 
This shows the codebase's own invariant is "real unique member count vs. `num_confirmations`" — but `new()` fails to enforce that exact invariant at construction time, because it checks the pre-dedup input length instead of the post-dedup member set size.

### Impact Explanation
This breaks the custody/authorization binding: `num_confirmations` (confirmations required to move funds or change contract state) versus the actual number of distinct signers capable of granting them. If the deployer (accidentally, via a buggy client, or a malicious deployer front-running a legitimate multisig setup) supplies a members array with duplicates such that unique members < `num_confirmations`, any NEAR subsequently transferred into that multisig account becomes permanently frozen — no `Transfer`, `AddMember`, `DeleteMember`, or `SetNumConfirmations` request can ever gather enough distinct confirmations to execute, and there is no external escape hatch (no owner, no timeout). This matches the "Critical … funds permanently frozen" impact category.

### Likelihood Explanation
This is triggered purely by the initialization arguments passed to `new`, which is called directly by whoever deploys/initializes the multisig account (an unprivileged deployer action, not requiring any victim key, redeploy, or social engineering beyond constructing the `members` argument). Any client bug that produces a members list with an accidental duplicate (e.g., the same account/public key added twice while collecting members) — or a deliberately malicious deployer — silently produces a permanently-bricked multisig once funded, with no error at deploy time and no way to detect it before deposits are made and confirmations are attempted.

### Recommendation
In `new`, deduplicate `members` (e.g., insert into the `UnorderedSet` first, or use a `HashSet` to normalize by `member.to_string()`) and validate `num_confirmations` against the resulting *unique* count rather than `members.len()` of the raw input, mirroring the invariant already enforced in `delete_member`.

### Proof of Concept
1. Deploy `multisig2` and call `new` with `members = [{"account_id": "alice"}, {"account_id": "alice"}, {"account_id": "alice"}]` and `num_confirmations = 3`.
2. The assertion `members.len() >= num_confirmations` (3 >= 3) passes.
3. `self.members` ends up containing only `{"account_id": "alice"}` (a single unique member) due to `UnorderedSet` deduplication in `add_member`.
4. Fund the contract account with NEAR via a normal transfer.
5. `alice` calls `add_request` + `confirm` for a `Transfer` request; `confirmations.len() + 1 == 1 < 3`, so the request is never executed.
6. No other distinct member exists to add further confirmations, and no request (including one to lower `num_confirmations`) can ever reach the threshold — the deposited NEAR is permanently frozen.
