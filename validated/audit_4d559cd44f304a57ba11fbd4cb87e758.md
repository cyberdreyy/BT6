### Title
Blacklisted USDC fee recipient turns `stopEpoch` revert into a spurious borrower default and can permanently brick `finalizeDefault` recovery - (File: contracts/IdleCDOEpochVariant.sol)

### Summary

The Arrakis bug class — a reward `safeTransfer` to a possibly-blacklisted recipient bundled inside a privileged state-change — maps directly onto idle-tranches' fee payout inside `stopEpoch`/`stopEpochWithDuration` and the donation skim inside `startEpoch`, `finalizeDefault`, `updateAccounting`, `_deposit`, `requestWithdraw` and `depositDuringEpoch`. Here the impact is worse than in the report: the fee transfer in `_stopEpoch` sits **inside** the `try` over `this.getFundsFromBorrower`, so a USDC blacklist revert is swallowed by `catch` and misinterpreted as a borrower default (`defaulted = true`, epoch force-stopped, withdraw requests disabled). The skim call in `finalizeDefault` sits before any recovery logic, so dust plus a blacklisted `feeReceiver` can permanently block default finalization and user recovery claims.

### Finding Description

`_transferFeeUnderlyings` performs two `safeTransfer`s of the underlying (e.g. USDC) to `feeReceiver` and `owner()` (`contracts/IdleCDOCreditVault.sol:587-591`), and `_skimDonatedAssets` transfers the contract's full raw underlying balance to `feeReceiver` (`contracts/IdleCDOEpochVariant.sol:793-796`).

In `_stopEpoch` (`contracts/IdleCDOEpochVariant.sol:408-505`):

- Line 419 (`_transferFeeUnderlyings(_pendingWithdrawFees)`) and line 456 (`_transferFeeUnderlyings(_fees)`) execute inside the `try { this.getFundsFromBorrower(...) }` block.
- Line 355 `_skimDonatedAssets()` executes before the try block.
- If `feeReceiver` or `owner()` is blacklisted in USDC, `safeTransfer` reverts. The revert inside `try` is caught at line 501 and routed to `_handleBorrowerDefault` (`contracts/IdleCDOEpochVariant.sol:577-599`), which sets `defaulted = true`, pauses the contract, stops the epoch and disables AA/BB withdraw requests — even though the borrower repaid in full.
- Worse, `getFundsFromBorrower` already moved the borrower's repayment into the CDO before the fee transfer reverted, so the vault sits on repaid cash while declared in default.

For `finalizeDefault` (`contracts/IdleCDOEpochVariant.sol:194-225`), `_skimDonatedAssets()` at line 197 runs unconditionally. If any unprivileged user has direct-transferred even 1 wei of underlying to the CDO (donations are expected — the code explicitly skims them), and `feeReceiver` is blacklisted, `finalizeDefault` reverts forever, blocking `finalizeDefaultRecovery` and all defaulted-receipt payouts.

`setFeeParams` lets the owner rotate `feeReceiver`, and `feeSplit = FULL_ALLOC` can zero the owner share (the `_amount == 0` early return in `_transferUnderlyings` skips the blacklisted leg). Recovery is therefore possible only while at least one of {`feeReceiver`, `owner()`} is transferable. If both end up blacklisted — or if `feeReceiver` is blacklisted and the skim revert cannot be cleared because each new donation re-arms it — the spurious default / blocked finalization is permanent.

### Impact Explanation

- **Spurious borrower default**: honest borrower repays; the blacklist revert on the fee leg triggers `_handleBorrowerDefault`, freezing withdraw requests and forcing the vault into the default/loss-finalization flow, where active LPs and pending receipts are resolved through `finalizeDefault` instead of normal claims.
- **Permanent freezing of recovery**: dust + blacklisted `feeReceiver` bricks `finalizeDefault`, so `DefaultDistributor`/`_claimDefaulted*` payouts and post-default claims never happen.
- **Temporary DoS of the whole epoch machine**: a single dust donation while `feeReceiver` is blacklisted reverts `startEpoch` (line 242), `stopEpoch` (line 355), `requestWithdraw` (line 747), `_deposit` (line 647), `depositDuringEpoch` (line 679) and `updateAccounting` (line 159) until `setFeeParams` rotates the receiver — and an attacker can keep re-donating dust each time it is skimmed.

### Likelihood Explanation

USDC (the intended underlying for these credit vaults) has an active blacklist, and fee multisigs/`owner()` are not immune to it. The trigger requires a privileged recipient to be blacklisted — not attacker-controlled — but once true, any unprivileged user can weaponize it with a dust donation, and a routine honest `stopEpoch` converts it into a wrongful default. Conditional, high-impact; consistent with Medium.

### Recommendation

Pull fee payouts out of the epoch-critical path:

1. Move `_transferFeeUnderlyings` and the `_fees`/`_pendingWithdrawFees` settlement **outside** the `try/catch` (and ideally after `isEpochRunning = false`), or accumulate them into `unclaimedFees` and let `feeReceiver`/`owner()` pull via a separate `claimFees()` instead of push.
2. Make `_skimDonatedAssets` non-fatal: wrap the transfer in a `try/catch` (or transfer to a pull-based escrow) so a blacklisted `feeReceiver` cannot block `stopEpoch`, `finalizeDefault`, `startEpoch`, deposits or requests.
3. In `finalizeDefault`, skip or best-effort the skim — donated dust must never gate LP recovery.

    }
