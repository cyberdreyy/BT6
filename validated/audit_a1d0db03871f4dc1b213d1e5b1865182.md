### Title
Stale rejection weight is never reconciled when a signer switches to acceptance, letting the node coordinator act on a stale/threshold that no longer reflects verified signer votes — (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` (the node-side signing coordinator that tallies `BlockResponse` messages from signers) maintains two independent, never-reconciled weight counters per proposed block: `total_weight_approved` and `total_weight_rejected`. A signer's weight is added to `total_weight_rejected` the first time it rejects a block, and is *never removed* if that same signer later re-evaluates and accepts the same block. The accept-path guard only checks a different set (`gathered_signatures`), never `responded_signers`/the reject tally, so the reject weight recorded earlier is permanently retained even after the signer's final, verified verdict flips to acceptance. This lets the coordinator make a rejection/threshold decision using aggregated weight that no longer matches any signer's current, verified vote — a single (or few) gossiping signer can trigger this simply by exercising the signer's own supported "re-evaluate" transition (`LocallyRejected → LocallyAccepted`), with no majority required.

### Finding Description
The coordinator tracks per-block vote weight in a shared `BlockStatus` guarded by a mutex, updated from two branches of the same match statement:

- Accept branch: gates re-adding weight on `block.gathered_signatures.contains_key(&slot_id)` only, and inserts the slot into `responded_signers` as a side effect. [1](#0-0) 

- Reject branch: gates weight addition on `block.responded_signers.insert(slot_id)` returning `true` (i.e., "first time we've heard from this signer at all"). [2](#0-1) 

Because these are two different guard sets, the following sequence is possible and is not defended against:

1. Signer S sends `Rejected` for block B first. `responded_signers.insert(S) == true` → `total_weight_rejected += w_S`.
2. Signer S later legitimately re-evaluates the same block and sends `Accepted` for B (this is an explicitly supported signer-side transition: `LocallyRejected --> LocallyAccepted : re-evaluated`). [3](#0-2) 
3. The accept branch only checks `gathered_signatures.contains_key(&S)`, which is still empty for S, so it happily adds `w_S` to `total_weight_approved` as well.

The result: `w_S` is now counted in *both* `total_weight_rejected` and `total_weight_approved` simultaneously, and `total_weight_rejected` is never decremented to reflect S's updated, current verdict. The coordinator's threshold decision loop reads exactly these two stale, non-exclusive counters to decide the outcome: [4](#0-3) 

This breaks the intended equality that the aggregated per-block weight tally should reflect each signer's single, current/verified vote — directly analogous to the Maia bug where a downstream consumer (`callOut`) kept trusting a stale flag instead of consulting the current, authoritative state (`isBridgeAgent`). Here the coordinator keeps trusting a stale `total_weight_rejected` entry instead of consulting the signer's current (accepted) state.

### Impact Explanation
Because rejection weight is sticky and never reconciled against a later acceptance, a small number of signers who legitimately change their mind (as designed, via re-evaluation) can leave "phantom" rejection weight in `total_weight_rejected` for a given block. Combined with a handful of *other* signers who genuinely reject, this stale weight can push `total_weight_rejected.saturating_add(weight_threshold) > total_weight` and trip the rejection branch in `wait_for_signer_signatures_or_timeout` even though every signer's *current* vote would actually clear the acceptance threshold. This is a liveness wedge: the block-production coordinator can be made to believe a valid, ultimately-supermajority-approved block was rejected, forcing unnecessary re-mining, `failed_txid` exclusion bookkeeping (which also derives from the same stale/duplicated weight accounting) and stalling the tenure — matching the "signer wedged / acting on a stale threshold" High-impact category. It does not require a majority of signers to be malicious or offline; only one signer's own, permitted vote-flip is needed to introduce the inconsistency (additional genuine rejecters merely need to reach the remaining gap).

Note: the final cryptographic signature set attached to the block (`gathered_signatures`, keyed uniquely by slot) is not directly inflated by this bug — a slot cannot appear twice in the map — so this does not by itself let an invalid/non-canonical block get signed. The concrete, provable break is the loss of equality between the aggregated tally and the verified/current signer votes, which can wedge liveness or misclassify transactions as "problematic" based on stale weight.

### Likelihood Explanation
Vote re-evaluation from reject to accept for the same proposal is an explicit, documented, and used feature of the signer state machine (`should_reevaluate_block` / `should_reevaluate_reject_reason`, and the `LocallyRejected → LocallyAccepted` transition), so the triggering condition is a normal operational event, not an exotic edge case, and requires only StackerDB gossip from the signer(s) involved — no majority collusion, no auth token, no external system access.

### Recommendation
Track a single, exclusive "current vote" (and its weight) per signer/slot for a given block, replacing the independent `total_weight_approved` / `total_weight_rejected` counters with a per-slot verdict map. When a signer's newest message flips the verdict, subtract their weight from the previous bucket before adding it to the new one (or simply recompute both weight totals by summing over the per-slot verdict map on each update) so that `total_weight_rejected` and `total_weight_approved` are always partitions of `responded_signers`, mirroring the same invariant used for the actual signature set (`gathered_signatures`, keyed by slot).

### Proof of Concept
1. Coordinator opens a proposal for block B with signer S (weight `w_S`) among the signer set.
2. S sends `BlockResponse::Rejected` for B → `responded_signers = {S}`, `total_weight_rejected = w_S`.
3. S subsequently re-evaluates (as its own state machine legitimately permits) and sends `BlockResponse::Accepted` for the same B → accept branch checks only `gathered_signatures` (still empty for S) → `total_weight_approved = w_S`, `gathered_signatures = {S: sig}`.
4. Now `total_weight_rejected` still equals `w_S` even though S's current, verified vote is "accept." If other signers with combined weight `w_R` also reject, the loop's check `total_weight_rejected.saturating_add(weight_threshold) > total_weight` uses `w_S + w_R`, which can trip the rejection path even though the true, current combined weight of rejecting signers is only `w_R` (which alone may be below the blocking threshold).
