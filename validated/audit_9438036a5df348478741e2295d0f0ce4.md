### Title
Unbounded, unauthenticated `savedCallbacks` flood enables oldest-first eviction of other users' pending capability callbacks - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`(*handler).HandleLegacyUserMessage` inserts every incoming user message into the shared `h.savedCallbacks` map keyed only by attacker-supplied `MessageId`, with no per-sender quota or allowlist check (explicitly marked `// TODO: apply allowlist and rate-limiting here`). `(*handler).pruneCallbacks` evicts strictly by `createdAt` oldest-first when the map exceeds `MaxSavedCallbacks`, with no notion of sender identity, so a high-volume requester can force eviction of another user's still-pending callback.

### Finding Description
`HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) accepts a `web_api_trigger` request, and after only payload/timestamp/method validation (no allowlist or per-sender rate limit — see the `TODO` at line 384), stores the callback: `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` (line 412). Any caller who can reach this handler and control `msg.Body.MessageId` (attacker-chosen, only required to be unique) can insert arbitrary numbers of entries.

`pruneCallbacks` (lines 299-339) runs on a periodic ticker (`Start`, lines 269-285). It first deletes expired entries by age, then, if `len(h.savedCallbacks) > MaxSavedCallbacks`, sorts all remaining entries by `createdAt` and deletes everything except the newest `MaxSavedCallbacks/2` (lines 314-334). This eviction logic has no concept of sender/requester identity — it is purely global oldest-first pruning. If a victim's legitimate callback was saved before the attacker floods `MaxSavedCallbacks/2`+ new entries (each with a fresh timestamp/newer `createdAt`), the victim's older entry is deleted along with other stale ones, and the attacker's flood entries survive since they're newer. The victim's callback entry — including its `SendResponse` closure back to the original request context — is silently dropped with no error, no retry, and no signal to the victim other than an eventual timeout on their side.

Because `HandleLegacyUserMessage` performs no rate limiting, allowlisting, or per-sender cap on saved callback count, and `pruneCallbacks` doesn't account for sender identity, an unauthenticated/low-privilege caller who can send `HandleLegacyUserMessage`-routed messages can trigger this cross-user denial.

### Impact Explanation
Impact is a scoped denial-of-service against a specific victim's in-flight capability request: the victim's `SendResponse` callback is orphaned, so their capability request that was already dispatched to DON nodes never gets its response delivered back to the caller, effectively silently dropping the result of a triggered capability execution for that request. This matches a "denial of service impacting a single client/request" style bounty class rather than node-wide compromise, since the underlying node/gateway continues operating and only a specific pending request is affected. It does not expose secrets, escalate privileges, or move funds; the confidentiality/integrity of other data is unaffected.

### Likelihood Explanation
Preconditions: attacker only needs enough send access to reach `HandleLegacyUserMessage` (which the code explicitly treats as unauthenticated/unthrottled given the TODO) and knowledge that a victim's request was recently submitted (or simply flooding continuously to catch any in-flight request). No credentials beyond ordinary user-level API access to the gateway are required. This is fully within the "unprivileged" attacker model (unauthenticated/low-privilege gateway client). It's repeatable at will and only requires generating `MaxSavedCallbacks/2` (default 10,000, since `defaultMaxSavedCallbacks = 20000`) unique messages with valid timestamps/signature-transformable structure, which is a bulk-request cost but not otherwise gated.

### Recommendation
Add a per-sender cap/allowlist and rate limiting on `savedCallbacks` insertion in `HandleLegacyUserMessage` before storing a new callback (address the existing TODO at line 384), and change `pruneCallbacks` eviction to be per-sender aware (e.g., track counts/keys per sender and only evict a sender's own oldest entries when that sender exceeds its quota) rather than a single global oldest-first sort across all senders.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `MaxSavedCallbacks` set to a small test value (e.g., 10).
2. Seed one "victim" callback directly via `h.savedCallbacks["victim-id"] = &savedCallback{id: "victim-id", createdAt: time.Now(), Callback: victimCallback}` where `victimCallback.SendResponse` is a mock that records if it was ever invoked/orphaned.
3. Simulate "attacker" flood: insert `MaxSavedCallbacks` additional entries with unique ids and `createdAt` timestamps strictly after the victim's, either via direct map insertion or by calling `HandleLegacyUserMessage` in a loop with valid signed/structured payloads and unique `MessageId`s.
4. Call `h.pruneCallbacks()`.
5. Assert `_, found := h.savedCallbacks["victim-id"]; !found` — the victim's callback was evicted — while the attacker's newer entries remain, demonstrating the sender-agnostic oldest-first eviction silently drops the victim's pending response channel.
