### Title
Stale block-response weight lets a superseded vote get double-counted in the miner's signer coordinator - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener`'s message loop maintains two separate per-block bookkeeping structures — `gathered_signatures`/`total_weight_approved` for `BlockResponse::Accepted` and `responded_signers`/`total_weight_rejected` for `BlockResponse::Rejected` — but the guard that prevents double-counting a signer's weight is asymmetric between the two arms, so a signer's *earlier* vote can remain permanently baked into the tally after that signer sends a *later, superseding* response for the same block.

### Finding Description
In the `Accepted` arm, the weight-add guard is keyed on `gathered_signatures`: [1](#0-0) 
while the `Rejected` arm's guard is keyed on `responded_signers`: [2](#0-1) 

Both arms insert into `responded_signers` (line 465 and 515), but only the `Accepted` arm tests a *different* set (`gathered_signatures`) before adding weight. Consequence:

- If a signer first sends `Accepted` (weight added to `total_weight_approved`, `slot_id` inserted into both `gathered_signatures` and `responded_signers`) and later — after re-evaluating the block, e.g. because a conflicting block appeared or `check_block_against_signer_db_state` now fails — sends `Rejected` for the *same* `signer_signature_hash`, the `Rejected` arm's guard `block.responded_signers.insert(slot_id)` returns `false` (already present), so the rejection weight is **not** added. But the earlier acceptance weight in `total_weight_approved` and the earlier signature in `gathered_signatures` are **never removed**.
- The signer protocol explicitly allows this "accepted → rejected" reconsideration path; `BlockInfo::check_state` permits the `LocallyAccepted → LocallyRejected` transition (documented in `docs/signer-flows.md` §2's state diagram): [3](#0-2) 

As a result, `total_weight_approved` (and the cached `gathered_signatures` map that the coordinator returns as the final signature set) can hold a stale, no-longer-endorsed signature. This breaks the equality the coordinator relies on — that `total_weight_approved` reflects the *current, verified* set of accepting signers — analogous to the reported bug where `totalVolumeOfBorrowersAmountinWei`/`totalCdsDepositedAmount` were mutated without reconciling the prior cumulative contribution, leaving a stale aggregate that no longer matches the real underlying state.

The coordinator consumes this stale aggregate directly to decide the outcome and to assemble the pushed signature set: [4](#0-3) 
When `block_status.total_weight_approved >= self.weight_threshold` (line 541), it returns `block_status.gathered_signatures.values().cloned().collect()` — which still contains the stale signature from the signer that has since rejected the block.

### Impact Explanation
This is a safety-relevant equality break: the coordinator treats a signer's superseded, withdrawn acceptance as still-valid weight toward the 70% signing threshold. A single signer who legitimately reconsiders and rejects a block it previously accepted (a normal, documented state transition) has its stale signature silently retained by the miner. If the remaining, still-approving signers' honest weight is below threshold, the miner can nonetheless assemble and broadcast a signature set that reaches threshold only because of this one stale/withdrawn vote — i.e. a block gets treated as sufficiently signed by weight that does not currently correspond to real, verified accepts. This maps to "aggregated-weight vs verified-accepts" divergence and can enable pushing/broadcasting a block that a signer has actively rejected using their earlier (still cryptographically valid but not currently intended) signature.

### Likelihood Explanation
No majority collusion or external actor is required — this is triggerable by the ordinary behavior of a single honest signer that changes its mind (accept → reject) for the same block hash, a transition the state machine explicitly supports (`LocallyAccepted → LocallyRejected`). The miner-side StackerDB listener processes each signer message independently and never re-verifies previously accepted weight after a subsequent rejection from the same signer, so the stale-weight condition is a straightforward consequence of the existing code path rather than requiring adversarial signer counts.

### Recommendation
Use the same set (`responded_signers`) — or an explicit "current stance" map keyed by `slot_id` — to gate weight accounting symmetrically in both arms, and when a signer's vote changes (accept→reject or reject→accept), subtract the previously counted weight (and remove any stale entry from `gathered_signatures`) before adding the new weight, so `total_weight_approved`/`total_weight_rejected` and `gathered_signatures` always reflect only the signer's latest, current response.

### Proof of Concept
1. Miner proposes block `B` with `signer_signature_hash = H`; total signer weight = 100, threshold = 70.
2. Signers `S2..Sn` (combined weight 69) send `Accepted` for `H`; `S1` (weight 5) also sends `Accepted` for `H`. `total_weight_approved = 74 >= 70` — but suppose in a race, `S1`'s message is processed alongside others such that without `S1`, weight is 69 (<70).
3. `S1`, after re-evaluating (e.g., a conflicting block or chainstate change causes `check_block_against_signer_db_state` to now fail — a state legitimately reachable via `LocallyAccepted → LocallyRejected`), sends `Rejected` for the same `H`.
4. In `stackerdb_listener.rs`, the `Rejected` arm's guard `block.responded_signers.insert(slot_id)` (line 515) returns `false` because `S1`'s `slot_id` was already inserted during step 2's `Accepted` handling — so `total_weight_rejected` is not incremented, but `total_weight_approved` (74, including `S1`'s stale weight) and `gathered_signatures` (including `S1`'s stale signature) are untouched and remain as-is.
5. `signer_coordinator.rs` observes `total_weight_approved (74) >= weight_threshold (70)` and returns/pushes the signature set including `S1`'s stale signature (line 541–545), even though `S1` currently rejects block `B`. [5](#0-4) [6](#0-5)
