### Title
Multi-epoch withdraw receipts overflow the single-slot `lastWithdrawRequest` loss lookup, letting loss-epoch receipts claim at par and drain funded reserves - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`collectWithdrawFunds` records a haircut per request epoch in `lossRecoveryPriceByEpoch[epochNumber]`, but `_claimLossAdjustedWithdrawRequest` only ever looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — a single storage slot holding only the user's *latest* request epoch. A user who holds a loss-adjusted receipt in epoch N and then makes any new withdraw request in epoch N+1 permanently overwrites the "buffer" that indexes the haircut table, so the epoch-N receipt falls through to `_claimFundedWithdrawRequest`, which pays the full aggregate `withdrawsRequests[_user]` at par. The haircut is bypassed and the excess is paid out of funds reserved for other claimants, directly mirroring the gnupot bug class: attacker-controlled data (an extra request epoch) overflowing a fixed-size lookup into adjacent accounting.

### Finding Description
When `stopEpochWithDuration`-style loss funding occurs, `IdleCDO` calls `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws`, which stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` and zeroes `pendingWithdraws` (`IdleCreditVault.sol:411-430`). Per-user/per-epoch receipt basis stays in `withdrawsRequestsByEpoch[_user][epoch]` and `withdrawsRequests[_user]`.

At claim time (`claimWithdrawRequest`, `IdleCreditVault.sol:301-314`):

1. `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and `lossRecoveryPriceByEpoch[lossEpoch]` (`IdleCreditVault.sol:789-792`). `lastWithdrawRequest[_user]` is overwritten on every `requestWithdraw` (`lastWithdrawRequest[_user] = currentEpoch`, line 282).
2. If the user's latest request epoch has no haircut (`lossRecoveryPrice == 0`), the function returns 0 and `_claimFundedWithdrawRequest` pays `amount = withdrawsRequests[_user] + apr0 buckets` in full via `_transferFundedClaim` (`IdleCreditVault.sol:319-349`).

There is no iteration over the user's historical request epochs and no per-epoch `lossRecoveryPriceByEpoch` check for anything except the single latest epoch. `withdrawsRequestsByEpoch` retains the epoch-N basis forever, and `_claimFundedWithdrawRequest` never checks whether any component epoch was haircut — the epoch-N receipt is simply paid at par.

Attack trace (normal, non-prefunded mode, APR ≠ 0):
1. Attacker (KYC'd AA holder) deposits and calls `requestWithdraw` in epoch N → `lastWithdrawRequest[attacker] = N`, `withdrawsRequestsByEpoch[attacker][N] = X`.
2. Epoch N ends; borrower short-pays: `collectWithdrawFunds(funded < pendingWithdraws)` sets `lossRecoveryPriceByEpoch[N] = r < 1e18`. The strategy now holds only `funded` for all epoch-N receipts.
3. Epoch N+1 runs (normal or APR0 toggled back). Attacker calls `requestWithdraw(1 wei)` → `lastWithdrawRequest[attacker] = N+1`, `withdrawsRequests` now aggregates X + dust.
4. Epoch N+1 stops normally and is fully funded. Attacker calls `claimWithdrawRequest`: `lossRecoveryPriceByEpoch[N+1] == 0` → loss path skipped; `_claimFundedWithdrawRequest` pays the entire `withdrawsRequests` balance (including the epoch-N X) at par, reverting only via the `_transferFundedClaim` reserve guard if it would dip into `defaultRecoveryReserve` — which is 0 absent a default.

The other epoch-N claimants' haircuts were sized pro-rata against `pendingBasis`; the attacker withdrawing X at par overpays by `X * (1e18 - r) / 1e18`, leaving the strategy underfunded — the last claimants' transfers revert on `safeTransfer` (insolvency), i.e., theft by first-claimer.

### Impact Explanation
Direct theft / insolvency: every other holder of a loss-epoch receipt is entitled only to `r` of their basis, but the attacker extracts 100% of theirs plus the haircut amount of others, limited by total funded balance. With `r = 0.5e18` and a 1M-underlying receipt, the attacker steals ~500k underlying beyond their fair share, and equivalent claims by honest users permanently revert.

### Likelihood Explanation
Requires a realized stop-epoch loss (partial funding of pending withdrawals — an intended code path, `previewLossAdjustedWithdrawFunds` exists for it) plus two unprivileged `requestWithdraw` calls across two epochs. No privileged cooperation needed; the attacker is an ordinary tranche holder. Both requests are normal user actions explicitly supported by the contract.

### Recommendation
Track loss-adjusted epochs per user rather than keying off the single `lastWithdrawRequest` slot: e.g., store a per-user list/bitmap of request epochs that have a nonzero `lossRecoveryPriceByEpoch`, or iterate `withdrawsRequestsByEpoch` epochs when claiming and apply the haircut to each epoch's basis separately before paying funded receipts at par. Alternatively, on `collectWithdrawFunds` shortfall, mark a per-user claim structure so `_claimFundedWithdrawRequest` cannot pay a loss-epoch component at par.

### Proof of Concept
Foundry fork PoC (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testLossHaircutBypassedBySecondRequest() external {
    // deposits -> epoch 0 -> epoch N request by attacker and victim
    _depositWithUser(attacker, 1000e6, true);
    _depositWithUser(victim,   1000e6, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    vm.prank(attacker); cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(victim);   cdoEpoch.requestWithdraw(0, address(AAtranche));
    uint256 pending = strategy.pendingWithdraws();

    // epoch 1: borrower funds only half -> lossRecoveryPriceByEpoch[1] = 0.5e18
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, pending / 2); // partial funding
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(...); // path invoking collectWithdrawFunds(pending/2)

    // attacker makes a fresh dust request in epoch 2
    _startEpochAndCheckPrices(2);
    vm.prank(attacker); cdoEpoch.requestWithdraw(1, address(AAtranche));
    _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch()); // fully funded

    // attacker claims: pays full epoch-1 basis at par, haircut skipped
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker); cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - pre, pending / 4); // > 50% share

    // victim's fair (halved) claim now reverts / strategy is insolvent
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Uncertainty: the exact `stopEpochWithDuration` signature in `IdleCDOEpochVariant.sol` was not fully read; the PoC uses the manager-driven partial-funding path that ends in `IdleCreditVault.collectWithdrawFunds` with `_amount < pendingWithdraws`, which is the documented trigger for `lossRecoveryPriceByEpoch`.
