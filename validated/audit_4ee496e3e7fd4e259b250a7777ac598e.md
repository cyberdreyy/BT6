### Title
Legacy WebAPI trigger handler silently overwrites in-flight callbacks on `MessageId` collision, enabling cross-user response hijack - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`ValidatedMessageFromReq` (`core/services/gateway/handlers/common/message_util.go`) only parses and signature-validates a message; it performs no uniqueness/idempotency check on `req.ID`/`MessageId`, and that responsibility is left entirely to each handler. Some handlers (`vault`, `confidentialrelay`, `capabilities/v2` HTTP trigger) implement an explicit "reject if `req.ID` already active" check, but the legacy WebAPI trigger handler in `core/services/gateway/handlers/capabilities/handler.go` does not, allowing an attacker to overwrite another user's pending callback by submitting a signed request with the same `MessageId`.

### Finding Description
`ValidatedMessageFromReq` simply unmarshals and validates the signature of the message body (`core/services/gateway/handlers/common/message_util.go:36-58`); it never checks whether `m.Body.MessageId` collides with any handler's currently tracked in-flight state.

The gateway's HTTP entrypoint `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) dispatches legacy requests (those with a `DonId` set) to `Handler.HandleLegacyUserMessage`. For the WebAPI capability DON, this is `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go:341-421`. After validating the payload and signature, it does:

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
```

There is **no check** for an existing entry at `msg.Body.MessageId` before this assignment — unlike `vault/handler.go:466-472` and `confidentialrelay/handler.go:368-374`, which explicitly return `errors.New("request ID already exists: ...")` when `h.activeRequests[req.ID] != nil`, and unlike `capabilities/v2` HTTP trigger handler which rejects duplicate request IDs with an "in-flight request" error (see `core/services/gateway/handlers/capabilities/v2/http_trigger_handler_test.go:317-355`).

Because `HandleLegacyUserMessage` accepts any signed message (authorization/allowlisting is explicitly a `// TODO` at `handler.go:384`) and simply overwrites `savedCallbacks[MessageId]`, an attacker who knows or predicts a victim's pending `MessageId` can send their own signed `web_api_trigger` request using that same ID before the victim's DON response returns. This replaces the victim's callback entry with the attacker's.

When the DON node's response eventually arrives, `handleWebAPITriggerMessage` (`handler.go:148-162`) looks the response up purely by `MessageId`:

```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
```

The response — containing the victim's original request result — is delivered to the attacker's callback instead of the victim's, while the victim's HTTP request either times out or never receives a response.

### Impact Explanation
This is a cross-user response confusion / request hijack: an attacker can receive data intended for another user's session by colliding on a guessable/observable `MessageId`, and the victim's request effectively fails silently (denial of service for that request). If the underlying request/response payload contains sensitive data returned via `web_api_target`/`web_api_trigger` flows, this results in unauthorized disclosure of another user's response data — matching the "cross-user response confusion" bounty impact class.

### Likelihood Explanation
Exploitation requires: (1) ability to send a signed gateway message with `Method=web_api_trigger` and an arbitrary chosen `DonId`/`MessageId` — reachable by any keyholder able to sign a message, since `HandleLegacyUserMessage` performs no allowlist/authorization check before saving the callback; and (2) knowledge of the victim's exact in-flight `MessageId` at the right time window (before the DON response returns). This is feasible whenever a caller's `MessageId` construction scheme is deterministic/predictable (the codebase itself demonstrates this pattern elsewhere via `messageID(url, parts...)` using `sha256` in `core/services/workflows/artifacts/store.go:414-423`), or when the ID is otherwise observable. The race window is limited to node processing latency, and is repeatable per request.

### Recommendation
In `handler.HandleLegacyUserMessage`, before inserting into `h.savedCallbacks`, check for an existing entry keyed by `msg.Body.MessageId` (and ideally scope the key by `(Sender, MessageId)` as `RequestCache` in `core/services/gateway/handlers/common/requestcache.go` already does) and reject the request with a conflict error if one is already in flight, mirroring the pattern used in `vault/handler.go` and `confidentialrelay/handler.go`.

### Proof of Concept
Go test plan (handler-level, in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct handler with a mocked `DON`.
2. Create `callback1` and register a legacy message `msg1` with `MessageId = "shared-id"`, signed by victim key; call `HandleLegacyUserMessage(ctx, msg1, callback1)`. Assert `savedCallbacks["shared-id"]` is `callback1`.
3. Before any node response arrives, construct `msg2` with the same `MessageId = "shared-id"` signed by an attacker key, and call `HandleLegacyUserMessage(ctx, msg2, callback2)`.
4. Assert this call succeeds (no error returned) and `savedCallbacks["shared-id"]` now points to `callback2` (overwritten).
5. Simulate the DON node responding with the victim's expected payload via `handleWebAPITriggerMessage`/`HandleNodeMessage` using `MessageId = "shared-id"`.
6. Assert `callback2.Wait(ctx)` (attacker's callback) receives the response, while `callback1.Wait(ctx)` (victim's callback) never receives a response (times out), demonstrating cross-user response hijack.

Expected (buggy) result: step 4 succeeds silently with overwrite; step 6 shows attacker callback receiving victim's data. After the fix, step 3 should return an error such as `"request ID already exists"` and `savedCallbacks["shared-id"]` should remain `callback1`.
