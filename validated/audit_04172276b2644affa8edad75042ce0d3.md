This is an important finding: the B-20 token address only embeds a **9-byte truncated hash tail** (72 bits of entropy) rather than a full 32-byte keccak256 digest, unlike Uniswap V3's pool address collision issue which relies on a full 160-bit computed address. This is a meaningfully weaker analog than the original report but shares the "address collision from truncated/derived address" bug class.

### Title
B-20 token address derivation uses a 9-byte (72-bit) hash tail, enabling brute-force address collision - (File: crates/common/precompiles/src/b20_factory/variant.rs)

### Summary
`B20Variant::compute_address_from_hash` derives a B-20 token's deployment address by taking only the first 9 bytes of `keccak256(creator, salt)` and splicing them into address bytes `[11..20]`, with a fixed prefix and variant byte occupying bytes `[0..11]`. This gives only 72 bits of address entropy, far below the 160-bit space of a normal Ethereum/CREATE2 address, making collision attacks computationally realistic rather than the "practically impossible" assumption normal address derivation relies on.

### Finding Description
`compute_address_from_hash` truncates the hash to 9 bytes: [1](#0-0) 

`create_b20` in `FactoryV1` relies solely on this truncated-hash address plus an "already deployed" code-emptiness check to decide whether a caller can claim an address: [2](#0-1) 

`address_hash` itself comes from `keccak256((caller, call.salt))` computed by the factory dispatcher, and any account (`caller`) fully controls both the `caller` address (to a limited extent, if they can also control or predict `caller`) and the `salt` (fully attacker-chosen, 32 bytes): [3](#0-2) 

Because only 9 bytes (72 bits) of the hash are used as the address tail, and the `salt` is a free 32-byte input fully controlled by the calling EOA/contract, a party willing to spend on the order of 2^36 hash evaluations (birthday-bound, feasible with commodity/cloud hardware or ASIC/GPU farms) can find a `salt` value that reproduces a specific *victim* token's 9-byte tail for a given `creator`, or — more critically — grinds a `salt` so that a token deployed by an *attacker-controlled* `creator` collides with an address someone else has already granted allowances/roles to, or that an off-chain integrator has cached as "the" address for a given `(creator, salt)`.

This differs from a standard Ethereum CREATE2 collision (feasible only via 2^80 preimage work against a full 160-bit address); the B-20 scheme intentionally discards 23 of the 32 hash bytes, cutting the required work down to the birthday-bound of a 72-bit space.

### Impact Explanation
An attacker who can find a colliding `salt` can cause `createB20` to deploy a token contract at an address that any off-chain system, other protocol, or user believed corresponded to a specific different `(creator, salt)` pair (e.g., one they had approved token allowances to, whitelisted in a policy, or referenced in `initCalls`/permits bound to that address). Since B-20 addresses are the *entire* identity used by `isB20`/`isB20Initialized` and by any external contract that trusts the deterministic-address scheme for allowlisting or approvals, a collision lets an attacker deploy their own token/admin-controlled contract at a victim's expected address, potentially draining allowances or hijacking policy trust placed in that address — directly mirroring the "address collision -> drained allowances" impact described in the source report.

### Likelihood Explanation
Exploitability requires ~2^36 hash computations (birthday bound over a 72-bit space) to find a colliding `(creator, salt)` producing the desired 9-byte tail. This is computationally intensive but firmly within reach of well-resourced attackers today (GPU/ASIC clusters), and the cost only decreases over time, matching the profile ("nearly guaranteed with more compute in years") in the original report — but here the entropy is deliberately reduced from 160 to 72 bits, so the attack is drastically more practical than the Uniswap V3 case discussed in the source report.

### Recommendation
Do not truncate the derivation hash. Use the full 32-byte `keccak256(creator, salt)` (or embed the variant/prefix via a different mechanism that does not discard entropy, e.g. storing the variant in a side mapping keyed by the full-entropy address) so that address collision requires the full ~2^128 birthday-bound work of a standard 160-bit address space.

### Proof of Concept
1. Attacker picks a target victim `(victim_creator, salt_v)` pair (or an address they want to imitate) and computes `target_tail = keccak256(victim_creator, salt_v)[..9]`, as computed in [4](#0-3) .
2. Attacker iterates over candidate `salt` values with their own `attacker_creator`, computing `keccak256(attacker_creator, salt)[..9]` until it equals `target_tail` — expected ~2^36 tries (birthday bound for 72 bits), feasible on GPU hardware.
3. Attacker calls `createB20` with the found `salt`; `create_b20` in `crates/common/precompiles/src/b20_factory/logic/v1.rs` computes the same 9-byte tail via `variant.compute_address_from_hash(address_hash)` (line 201) and deploys the attacker's token at the identical address the victim's `(creator, salt)` pair would have produced, since only the tail (and the fixed prefix/variant byte) determine the address.
4. Any external system, allowance, or policy that had trusted "address = f(creator, salt)" for the original pair now interacts with the attacker's contract instead.

```rust
    pub fn compute_address_from_hash(self, hash: B256) -> (Address, [u8; 9]) {
        let mut tail = [0u8; 9];
        tail.copy_from_slice(&hash[..9]);

        let mut addr_bytes = [0u8; 20];
        addr_bytes[..11].copy_from_slice(&self.address_prefix());
        addr_bytes[11..].copy_from_slice(&tail);

        (Address::from(addr_bytes), tail)
    }
```
