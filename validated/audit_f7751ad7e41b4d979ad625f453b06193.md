### Title
`delegation_pool::set_beneficiary_for_operator` is missing the `operator_beneficiary_change_enabled` feature-flag gate that its `staking_contract` analog enforces - ([File: aptos-move/framework/aptos-framework/sources/delegation_pool.move])

### Summary
The `RubiconMarket` bug is a case where a boolean gate (`buyEnabled`) was checked in one code path (`_buys`) but not in the sibling path (`super.buy`) that reaches the same feature, so disabling the feature was not effective when reached via the alternate path. The Aptos framework has a structurally identical gap: the `operator_beneficiary_change_enabled` feature flag gates `staking_contract::set_beneficiary_for_operator` but is never checked in the delegation-pool analog, `delegation_pool::set_beneficiary_for_operator`.

### Finding Description
`staking_contract::set_beneficiary_for_operator` explicitly requires the feature to be turned on before allowing an operator to redirect commission payouts to a new beneficiary address: [1](#0-0) 

The equivalent entry function in `delegation_pool.move`, which performs the same "operator changes beneficiary" state transition for delegation pools, has no such check at all: [2](#0-1) 

I confirmed via repo-wide search that `operator_beneficiary_change_enabled` / `OPERATOR_BENEFICIARY_CHANGE` is referenced only in `staking_contract.move`, `features.move`, and related SDK/docs artifacts — never in `delegation_pool.move`. This means the on-chain feature flag that governance uses to enable or disable the "operator can redirect commission to a beneficiary" capability has zero effect on delegation pools: any operator of a delegation pool can call `delegation_pool::set_beneficiary_for_operator` and redirect all future commission distributions regardless of the flag's state.

This is the direct analog of the report's root cause: a capability-disable switch is enforced on only one of two structurally equivalent code paths that reach the same effect, so the switch cannot fully disable the behavior.

### Impact Explanation
If Aptos governance ever needs to disable operator-beneficiary changes network-wide (e.g., the flag exists specifically so this feature can be turned off, implying it was considered risky enough to need a kill-switch, presumably due to abuse potential such as compromised operator keys redirecting rewards, or a discovered accounting bug in the beneficiary-switch/distribution logic), that disablement is silently ineffective for every delegation pool. Operators retain the ability to redirect commission payouts to an address of their choosing via delegation pools even while the corresponding staking-contract path is locked down. This is a commission/beneficiary-payout redirection primitive that governance believed it had shut off, corrupting the intended "disabled" state for a subset of stake infrastructure (delegation pools), directly matching the report's "Impacts" bucket of *beneficiary payout ... corruption that credits the wrong account*.

### Likelihood Explanation
Likelihood is conditioned on governance actually disabling the feature flag (a privileged action, but the resulting bypass itself requires no privilege — any existing delegation-pool operator can trigger it). Given that the flag is a global on/off toggle intended to be authoritative across the framework, and delegation pools are the dominant staking mechanism on mainnet, the blast radius if the flag is ever toggled off is broad and immediate.

### Recommendation
Add the same guard used in `staking_contract::set_beneficiary_for_operator` to `delegation_pool::set_beneficiary_for_operator`:
```move
assert!(
    features::operator_beneficiary_change_enabled(),
    std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
);
```
placed at the top of the function in `aptos-move/framework/aptos-framework/sources/delegation_pool.move`, mirroring `aptos-move/framework/aptos-framework/sources/staking_contract.move:810-816`.

### Proof of Concept
1. Governance disables the feature via `features::change_feature_flags(... OPERATOR_BENEFICIARY_CHANGE ..., disable)`.
2. Attempt `staking_contract::set_beneficiary_for_operator(operator, new_beneficiary)` → aborts with `EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED` as expected [3](#0-2) .
3. Call `delegation_pool::set_beneficiary_for_operator(operator, new_beneficiary)` for any delegation pool the operator controls → succeeds unconditionally, updating `BeneficiaryForOperator` and redirecting all future commission distributions [4](#0-3) , proving the governance-level disablement is not enforced for delegation pools.

Note: I was unable to trace the original PR/AIP that introduced `operator_beneficiary_change_enabled` to confirm the exact historical motivation for the flag (the repo snapshot only contains a single "Initial commit"), so the specific abuse scenario governance was guarding against is inferred rather than directly documented in this codebase snapshot.

```text
    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensure payment to the current beneficiary, one should first call `synchronize_delegation_pool`
    /// before switching the beneficiary. An operator can set one beneficiary for delegation pools, not a separate
    /// one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });

```
