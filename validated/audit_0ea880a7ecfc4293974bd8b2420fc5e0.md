### Title
Unauthenticated `web_api_trigger` flood causes premature eviction and cross-user response confusion in `savedCallbacks` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` accepts any ECDSA-signed `MethodWebAPITrigger` request without checking DON membership or a sender allowlist (explicit `// TODO: apply allowlist and rate-limiting here` at handler.go:384), and unconditionally inserts the callback keyed only by the attacker-controlled `MessageId` into the shared `h.savedCallbacks` map with no rate limiting, no per-sender quota, and no uniqueness check against existing entries. Because `pruneCallbacks` (handler.go:299-334) evicts strictly by creation time (oldest half of entries removed once `len(savedCallbacks) > MaxSavedCallbacks`), an attacker can flood the map with cheaply-generated signed requests to force early eviction of a victim's older, still-pending callback, and because the map is keyed solely by `MessageId` (no sender binding), it can also be overwritten directly by anyone reusing the same ID.

### Finding Description
The path is: gateway `ProcessRequest` (gateway.go:264-269) → `handler.HandleLegacyUserMessage` (handler.go:341-421). The only checks performed are payload decoding, a `Timestamp` staleness check, and method equality to `MethodWebAPITrigger`; there is no verification that the signer is a member of any DON, workflow owner, or otherwise authorized, as explicitly flagged by the `TODO` comment at handler.go:384. Any holder of an arbitrary ECDSA keypair can produce a validly-signed `api.Message` (`msg.Sign(privateKey)` in api/message.go) and pass `msg.Validate()`, since `Validate()` only checks field lengths/signature format and extracts whatever signer produced the signature — it does not check the signer against an allowlist.

Once validated, the handler does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
``` [1](#0-0) 
with no check for an existing entry and no per-sender limiting on how many entries one attacker may create. `pruneCallbacks` runs on a periodic ticker and, when the map exceeds `MaxSavedCallbacks`, sorts all entries by `createdAt` and deletes the oldest half:
```go
sort.Slice(entries, func(i, j int) bool {
    return entries[i].createdAt.Before(entries[j].createdAt)
})
for _, e := range entries[:len(entries)-maxSize/2] {
    delete(h.savedCallbacks, e.id)
``` [2](#0-1) 
This guarantees the oldest — i.e., the longest-pending, most likely legitimate — callbacks are always evicted first when an attacker floods the map with fresh entries, since new attacker spam is always newer than a victim's already-waiting request. When the eviction removes the victim's entry, the subsequent legitimate DON response for that `MessageId` is silently dropped in `handleWebAPITriggerMessage` (handler.go:148-162), because the lookup `found` is `false` and no response is ever delivered to the victim (denial of service, silent timeout).

Additionally, since the map is keyed purely by attacker/victim-chosen `MessageId` with no sender binding, if any two callers (attacker and victim, or attacker's own repeated calls after eviction) submit the same `MessageId`, the later call silently overwrites the earlier `savedCallback` entry — so a delayed DON response for the original request could be delivered into a different, newer callback that reused the freed/overwritten slot, i.e., response misdelivery/correlation confusion across requests.

### Impact Explanation
This is a Denial-of-Service against legitimate `web_api_trigger` callers of the affected DON's gateway handler: an unauthenticated/unprivileged attacker with only a self-generated ECDSA key can starve or evict a victim's in-flight trigger callback, causing the victim to receive no response (timeout) even though the DON correctly processed and returned an answer. Because the map is keyed only by `MessageId`, it also creates the potential for response object confusion between unrelated requests that share an ID window. This matches the "Denial of Service" / unintended service disruption impact class rather than fund loss or credential disclosure, since the underlying HTTP outgoing message flow and node authentication remain intact.

### Likelihood Explanation
Feasibility is high: crafting a `MethodWebAPITrigger` message requires only generating an ECDSA keypair and signing the message body (`Sign()` in api/message.go), which is cheap and requires no allowlist membership, DON registration, or credentials — precisely because the enforcement described in the `TODO` comment (handler.go:384) does not exist. The only friction is the JSON-RPC request-ID length cap (200 chars, gateway.go:228) and the default `MaxSavedCallbacks` (20000) / prune interval (30s), both of which are easily exceeded by an attacker issuing tens of thousands of trigger requests in a short window, which is entirely repeatable and does not depend on network-layer or host-level access.

### Recommendation
- Implement the allowlist/authorization check called out in the `TODO` at handler.go:384 before accepting a `MethodWebAPITrigger` request (e.g., restrict to configured workflow owners or DON-recognized senders), and add per-sender rate limiting analogous to `nodeRateLimiter` for incoming user trigger requests.
- Scope `savedCallbacks` keys by `(sender, MessageId)` rather than `MessageId` alone, and reject inserts that would silently overwrite an existing unexpired entry.
- Consider fair eviction (e.g., per-sender caps or random eviction among a sender's own entries) rather than pure oldest-first eviction, so a single attacker cannot force eviction of other senders' pending callbacks.

### Proof of Concept
Go handler-level test plan (extending `handler_test.go`):
1. Configure `HandlerConfig{MaxSavedCallbacks: N, CallbackPruneIntervalSec: small}`.
2. Register one legitimate `triggerRequest` (victim) via `HandleLegacyUserMessage`, capture its callback and `createdAt`.
3. Loop generating `N` new ECDSA keys, each signing a distinct `MethodWebAPITrigger` message with a unique `MessageId`, and call `HandleLegacyUserMessage` for each — assert no allowlist rejection occurs for these unrelated signers.
4. Call `handler.pruneCallbacks()` (or wait for the ticker) and assert, via `handler.savedCallbacks`, that the victim's entry has been deleted while attacker entries (created after it) remain.
5. Simulate the DON's legitimate late response for the victim (`HandleNodeMessage` with `MethodWebAPITrigger`) and assert `handleWebAPITriggerMessage` returns without invoking `savedCb.SendResponse` (i.e., `found == false`), proving the victim's callback never receives the DON's answer.
6. (Extension) Submit a second request reusing the victim's original `MessageId` from a different signer and assert `h.savedCallbacks[id]` now points to the new signer's callback, demonstrating overwrite/response-confusion potential.
