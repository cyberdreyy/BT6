### Title
Confidential Transfer `Withdraw` parser mislabels/omits proof-context accounts when `account_indexes` length is inconsistent with offset flags - ([File: transaction-status/src/parse_token/extension/confidential_transfer.rs])

### Summary
`parse_confidential_transfer_instruction`'s `Withdraw` arm only validates a minimum of 4 accounts via `check_num_token_accounts`, but the actual number of optional accounts (instructions sysvar, equality proof context, range proof context) needed depends on `equality_proof_instruction_offset`/`range_proof_instruction_offset`. The offset-walking loop guards each optional slot with `offset < account_indexes.len().saturating_sub(1)` purely to avoid indexing past the reserved owner slot, not to verify the account list actually matches the claimed offset configuration.

### Finding Description
For `ConfidentialTransferInstruction::Withdraw`, the parser reads offsets from instruction data and walks `account_indexes` sequentially, attaching `"instructionsSysvar"`, `"equalityProofContextStateAccount"`, and `"rangeProofContextStateAccount"` based only on whether there is "room" left before the final (owner) slot: [1](#0-0) 

`check_num_token_accounts(account_indexes, 4)` only guarantees a floor of 4 accounts, regardless of whether 0, 1, 2, or 3 optional accounts are actually required by the claimed offset flags: [2](#0-1) 

`parse_signers` then unconditionally assigns whatever account sits at the final computed `offset` to `"owner"` (or splits into multisig/signers) without cross-checking that this position is actually the intended owner slot: [3](#0-2) 

An attacker who is submitting their own transaction can set `equality_proof_instruction_offset`/`range_proof_instruction_offset` to values inconsistent with the number of accounts supplied (e.g., signal that both proofs use `ContextStateAccount` mode — implying two extra context accounts are needed — but only supply the 4-account minimum). The offset-walking loop will then consume only as many slots as fit before the boundary check trips, attaching a context-state-account label to what may actually be intended as the owner account, and silently omitting the other expected field (e.g. `rangeProofContextStateAccount` never appears) — while `parse_token` still returns `Ok(...)` with a well-formed, plausible-looking JSON object rather than `InstructionNotParsable`. The existing test suite (`test_withdraw`) only exercises offset/account-count combinations that are internally consistent (i.e., exactly the right number of accounts for each proof-location configuration) and does not test the boundary/short-account-list cases.

### Impact Explanation
This is scoped strictly to the “decoder … misreporting” category: `getTransaction`/`accountSubscribe`/`logsSubscribe` with `jsonParsed` encoding for a self-submitted `Withdraw` confidential-transfer instruction can display an incorrect `"owner"` field (pointing at what is actually a proof-context account) and can silently drop an expected `equalityProofContextStateAccount`/`rangeProofContextStateAccount` field, while still returning a structurally valid, plausible object. It does not affect execution correctness, consensus state, or another party's funds/accounts — the raw (non-parsed) `accounts` array of the transaction remains fully faithful and unaffected; only the convenience `jsonParsed` labeling for the attacker's own transaction is wrong.

### Likelihood Explanation
Fully attacker-controlled and reproducible with a single crafted transaction (no special privileges, one RPC call/subscription). The precondition is simply constructing a `Withdraw` instruction where the account list length does not match what the declared offsets imply — trivial to do since the attacker builds both the instruction data and account list themselves.

### Recommendation
In the `Withdraw` (and equivalently `Transfer`, `TransferWithFee`, `ConfidentialMintBurn::Mint/Burn`, `WithdrawWithheldTokensFromMint`) arms, compute the exact expected account count from the offset flags up front (e.g., `2 + has_sysvar as usize + (eq_offset==0) as usize + (rng_offset==0) as usize + 1` for owner) and call `check_num_token_accounts` (or an equivalent exact-length check) with that derived value before doing any offset walking. If the actual `account_indexes.len()` doesn't match, return `ParseInstructionError::InstructionNotParsable(ParsableProgram::SplToken)` instead of proceeding with the best-effort boundary-guarded walk that can mislabel accounts.

### Proof of Concept
Extend `test_withdraw` (transaction-status/src/parse_token/extension/confidential_transfer.rs) with an inconsistent case:
```rust
#[test]
fn test_withdraw_inconsistent_account_count() {
    let token_account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let authority = Pubkey::new_unique(); // intended owner
    let stray = Pubkey::new_unique();     // will be mislabeled

    // Claim both proofs are ContextStateAccount (offset == 0), which per
    // the "All Contexts" case requires 5 accounts: account, mint, eq_ctx,
    // rng_ctx, owner. Instead, truncate to only 4 accounts.
    let mut instruction = inner_withdraw(
        &spl_token_2022_interface::id(),
        &token_account,
        &mint,
        42,
        9,
        &PodAeCiphertext::default(),
        &authority,
        &[],
        ProofLocation::ContextStateAccount(&stray), // eq
        ProofLocation::ContextStateAccount(&authority), // rng - reuse authority to simulate truncation
    ).unwrap();
    // Manually truncate the account list to simulate offset/account-count mismatch
    instruction.accounts.pop(); // drop last account (originally owner slot)

    let message = Message::new(&[instruction], None);
    let result = parse_token(
        &message.instructions[0],
        &AccountKeys::new(&message.account_keys, None),
    );

    // Expected (fixed) behavior: parser should reject rather than mislabel
    assert!(matches!(
        result,
        Err(ParseInstructionError::InstructionNotParsable(_))
    ), "parser should reject inconsistent offset/account-count combos instead of returning a plausible-but-wrong object, got: {:?}", result);
}
```
Currently this assertion fails: `parse_token` returns `Ok(...)` with `"owner"` set to `stray` (the eq-proof context account) instead of `authority`, and `rangeProofContextStateAccount` silently missing, demonstrating the misreporting.

fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
