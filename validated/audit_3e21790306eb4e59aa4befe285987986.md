### Title
Epoch interest minted at `stopEpoch` accrues to permanently locked min-liquidity shares when all real lenders have exited — ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
Analog of "rewards emitted while there are no stakers are lost": `stopEpoch` mints/accounts epoch interest unconditionally (`_strategy.mintStrategyTokens(_grossInterest)`), and `_updateAccounting`/`_virtualPriceAux` distribute that gain pro-rata over tranche `totalSupply`. Because a minimum-liquidity amount of tranche tokens is permanently locked at `address(1)` on first deposit (observed in `test/foundry/IdleCreditVault.t.sol` asserting `balanceOf(address(1)) == 10**3` after `depositAA`), tranche supply never returns to zero. If every real lender exits through withdrawal requests/claims, all subsequent interest is attributed to the dead shares and can never be claimed by anyone — the yield is permanently frozen inside the vault.

### Finding Description
- In `_afterStopEpoch`/`stopEpoch` flow, interest is realized without checking whether any real tranche holders remain: `if (_grossInterest != 0) _strategy.mintStrategyTokens(_grossInterest)` then `_updateAccounting()` (`contracts/IdleCDOEpochVariant.sol`, around lines 428–436).
- `_updateAccounting` credits `unclaimedFees` and calls `_virtualPriceAux` for AA and BB; gains are added to `lastNAVAA`/`lastNAVBB` and expressed through `priceAA`/`priceBB` (`contracts/IdleCDOCreditVault.sol:222-249`).
- `_virtualPriceAux` only short-circuits when `trancheSupply == 0` or `_lastNAV == 0` (`contracts/IdleCDO.sol:366-370`). With the dead min-liquidity share, supply is ~1000 wei > 0, so the full epoch gain (or its tranche share per `trancheAPRSplitRatio`) raises the tranche price — but the only holder is `address(1)`, which can never redeem.
- Unlike the MultiRewards case there is no recovery path: there is no governance sweep for tranche-attributed NAV (only `unclaimedFees` are minted to `feeReceiver`/`owner` in the minted-fee branch). The portion of gain attributed to tranche NAV is stuck forever.

### Impact Explanation
Permanent freezing of unclaimed yield. The loss equals all interest realized (minted or repaid) in epochs where the tranche's real-holder supply is zero — potentially a full epoch's `_grossInterest` in minted-interest mode, or all strategy yield accrued between the last real exit and the next deposit in the non-epoch IdleCDO path. New depositors cannot recover it either: they mint at the already-inflated `priceAA`/`priceBB`, so the frozen gain is never re-attributed.

### Likelihood Explanation
Low. Requires every real holder of a tranche (or both tranches for the classic IdleCDO case) to fully exit while the borrower/strategy keeps generating interest and the pool remains open (`epochEndDate != 0`, not closed/defaulted). Min-liquidity dead shares guarantee the accounting path stays live, so once the precondition holds the loss is deterministic and proportional to the interest accrued during the empty-holder window.

### Recommendation
When a tranche's effective supply is only the dead min-liquidity amount (or, more robustly, when `lastNAVAA + lastNAVBB` collapses to the dead-share remainder), route the epoch gain to `unclaimedFees`/`feeReceiver` instead of `lastNAV*`, or add a governance function to sweep NAV attributable to the locked seed shares. Alternatively, skip `mintStrategyTokens(_grossInterest)` in `stopEpoch` when no real tranche supply remains.

### Proof of Concept
Conceptual Foundry fork sequence (exact helper names per `test/foundry/IdleCreditVault.t.sol`):

```solidity
function test_InterestFrozenWhenAllRealHoldersExit() public {
    // minted-interest mode so interest is created at stopEpoch regardless of holders
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);   // burns ~1000 wei min liquidity to address(1)
    idleCDO.depositBB(amount);   // burns ~1000 wei min liquidity to address(1)

    _startEpochAndCheckPrices(0);

    // all real holders request full withdrawal during the epoch
    idleCDO.requestWithdraw(AAtranche.balanceOf(address(this)), address(AAtranche));
    idleCDO.requestWithdraw(BBtranche.balanceOf(address(this)), address(BBtranche));

    // borrower repays principal + interest; or interest is minted via mintStrategyTokens
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, expectedFundsEndEpoch);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, grossInterest);

    // real holders claim; afterwards real-holder supply of both tranches is 0
    idleCDO.claimWithdrawRequest();

    // next epoch runs (or strategy price keeps appreciating) with only dead shares
    _toggleEpoch(true, 0, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, expectedFundsEndEpoch2);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, grossInterest2);

    // epoch-2 interest was booked into lastNAV/price but is owned solely by address(1):
    // virtualPrice increased while tranche totalSupply is only ~1000 wei dead shares,
    // and no call exists to recover the attributed gain -> permanently frozen.
    assertGt(cdoEpoch.virtualPrice(address(AAtranche)), ONE_SCALE);
    assertEq(AAtranche.totalSupply(), 1000); // only min-liquidity dead shares
}
```

Caveat: I could not fully trace whether withdraw-request tranche tokens are burned at request time or at claim time relative to the `mintStrategyTokens`/`_updateAccounting` ordering inside `stopEpoch`; the foundry PoC should confirm the burn ordering, but the invariant break (gain booked to NAV owned exclusively by dead shares) holds as long as interest is realized after the last real holder's claim.
