### Title
Multisig `confirm` counts confirmations from removed members, allowing execution below live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` authorizes execution once `confirmations.len() + 1 >= num_confirmations`, but a member who confirmed a request and is later removed via `DeleteMember` still counts toward that threshold, because `delete_member` never purges that member's entries from the `confirmations` map for pending requests.

### Finding Description
The binding this contract is supposed to maintain is: `confirmations counted == confirmations from currently-live members`. In `confirm`, the check is purely numeric:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
``` [4](#0-3) 

`confirmations` is a `HashSet<String>` of serialized `MultisigMember` identities added in the `else` branch [5](#0-4) . There is no step, anywhere in `add_member`/`delete_member`/`execute_request`, that walks `self.requests`/`self.confirmations` to remove a stale confirmation belonging to a member who has since been deleted. `execute_request`'s `DeleteMember` branch only calls `self.delete_member(promise, member)`, which manipulates the `members` set and detaches an access key/account, with no interaction with `confirmations` [6](#0-5) .

Consequently, if a member confirms request `R` and is later removed (e.g., because they are compromised, off-boarded, or malicious), request `R`'s confirmation set still contains that member's stale entry. Any subsequent confirming members only need to bring the *total count* (including the stale, no-longer-authorized entry) up to `num_confirmations`, effectively executing the request with fewer live-member approvals than the threshold requires.

### Impact Explanation
This breaks the "a multisig request executed below threshold" invariant explicitly called out as Critical impact: the number of currently authorized signers who actually approved the request is less than `num_confirmations`, yet funds can be transferred, keys added, or contracts redeployed via `execute_request` (`Transfer`, `AddKey`, `DeployContract`, etc.) [7](#0-6) . This is a direct authorization-threshold bypass allowing NEAR to move, or the contract to be re-deployed/keys added, by a set of parties who do not collectively meet the configured K-of-N requirement.

### Likelihood Explanation
Requires only unprivileged/normal multisig workflow actions: (1) a member confirms a pending request, (2) that member is removed via a legitimate `DeleteMember` request (a routine operational action, e.g. offboarding an employee or rotating a compromised key), and (3) the original request is left pending and later confirmed to threshold by the remaining members while their pre-removal confirmation is still silently counted. No attacker-controlled deployment or foundation privilege is needed beyond the standard `DeleteMember` action already supported by the contract; this is a realistic sequence in normal member-rotation operations.

### Recommendation
When executing a `DeleteMember` action (or generally whenever membership changes), iterate over all outstanding `self.requests` and prune the removed member's entry from the corresponding `self.confirmations` sets before comparing lengths, or re-validate at `confirm`-time that every entry in the confirmation set for `request_id` still corresponds to a current member of `self.members`, discounting stale entries from the threshold count.

### Proof of Concept
1. Multisig deployed with `num_confirmations = 2`, members `[Alice, Bob, Carol]`.
2. Alice creates a `Transfer` request `R` via `add_request`; Alice calls `confirm(R)` — confirmations = `{Alice}` (1/2, not yet executed) [5](#0-4) .
3. Carol and Bob submit and confirm a separate `DeleteMember { member: Alice }` request to threshold, removing Alice from `self.members`. `delete_member` never touches `self.confirmations` for request `R`.
4. Bob calls `confirm(R)`. `confirmations.len() (1, still containing Alice) + 1 >= 2` is true, so `execute_request` runs the `Transfer` [4](#0-3) .
5. The transfer executes with only Bob as a currently-live confirming member, even though the contract requires 2 live-member confirmations — Alice's stale, no-longer-valid confirmation was silently counted.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
