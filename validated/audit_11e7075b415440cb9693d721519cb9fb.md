### Title
`IdleCDOCreditVault._deposit` mints tranche shares with no minimum-shares slippage bound - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
The credit-vault deposit path (`depositAA`/`depositBB` → `_deposit`) mints tranche tokens purely at the current recomputed price with no `minShares`/slippage parameter. An unprivileged tranche-token holder can frontrun a victim's deposit by directly transferring underlying to the CDO (inflating `getContractValue` and therefore the tranche price), causing the victim to mint fewer shares, then recover the donation plus a share of the victim's loss by redeeming their own tranche tokens.

### Finding Description
`_deposit` calls `_updateAccounting()`, which folds any change in `getContractValue()` (including unrequested direct `token` transfers sitting in the CDO balance) into `lastNAVAA`/`lastNAVBB` and tranche prices, then mints `amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` shares via `_mintSharesAtCurrPrice` with no lower bound on the minted amount. [1](#0-0) [2](#0-1) [3](#0-2) 

The share mint formula has no `minShares` check, so a price move between tx submission and execution silently reduces the victim's shares. Because `getContractValue` includes the contract's raw token balance, a donation executed before the victim's transaction is booked as `totalGain` inside `_virtualPriceAux`, raising the mint price. The same applies to `IdleCDO._deposit`. [4](#0-3) [5](#0-4) [6](#0-5) 

### Impact Explanation
A victim lender receives fewer tranche tokens than `virtualPrice` quoted at submission time; the difference accrues to existing holders, dominated by the attacker who donated. Quantified loss: `loss ≈ victimDeposit * donation / (NAV + donation)` capped by the victim deposit size. Recovery path for the attacker is a normal `_withdraw` of their tranche tokens after the victim's deposit lands (subject to the same-block check and epoch gating in the credit vault, so the redeem happens in a later block/epoch phase).

### Likelihood Explanation
Requires the attacker to hold tranche tokens (permitted: any tranche-token holder is an allowed attacker), to send underlying directly to the CDO to move the price, and to win ordering against the victim. No privileged action is needed; `_updateAccounting` treats the donated balance as gain whether or not a dedicated skim/isolation mechanism exists — if such a skim guard is present in the deployed variant, this vector is mitigated, but none is enforced inside `_deposit`/`_mintSharesAtCurrPrice` themselves, and the missing `minShares` parameter independently means honest price drift (fee accrual, harvest, epoch interest) also produces unbounded mint slippage.

### Recommendation
Add a `minShares` (or `maxPrice`) parameter to `depositAA`/`depositBB`/`depositDuringEpoch` threaded into `_deposit`, and revert in `_mintSharesAtCurrPrice` when `_minted < minShares`. Optionally exclude unsolicited direct transfers from `getContractValue` via a tracked-balance/`_skimDonatedAssets` mechanism.

// test/foundry/DepositSlippage.t.sol
function test_depositSlippage_donation() public {
    // state: running vault, attacker holds BB (or AA) tranche tokens
    uint256 victimDep = 1_000_000e6;
    uint256 donation  = 100_000e6; // moves tranche price up ~donation/NAV

    uint256 priceBefore = vault.virtualPrice(AA);
    uint256 expectedShares = victimDep * 1e18 / priceBefore;

    // 1. attacker frontruns: direct transfer to CDO inflates getContractValue()
    deal(USDC, attacker, donation);
    vm.prank(attacker);
    IERC20(USDC).transfer(address(cdo), donation);

    // 2. victim deposit executes at inflated price
    vm.prank(victim);
    uint256 minted = cdo.depositAA(victimDep); // no minShares param exists

    // 3. victim minted fewer shares than quoted; loss accrues to holders
    assertLt(minted, expectedShares);

    // 4. attacker later redeems tranche tokens recovering donation + share of loss
    vm.warp(block.timestamp + 1 days);
    vm.prank(attacker);
    cdo.withdrawBB(attackerShares);
    // attacker net profit = share of victim's shortfall - residual donation split
}

Caveat I could not fully verify within available context: whether the deployed `IdleCDOCreditVault`/`IdleCDO` build includes a `_skimDonatedAssets`/tracked-balance guard that already excludes direct transfers from `getContractValue`. If such isolation exists and is applied before `_updateAccounting`, the donation vector is blocked and the residual issue is only unprotected honest slippage, which is informational-to-low rather than a fund-theft path.

    if (_amount == 0) {
      return _minted;
    }
    // check that we are not depositing more than the contract available limit

    // interest accrued since last depositXX/withdrawXX is splitted between AA and BB
    // according to trancheAPRSplitRatio. NAVs of AA and BB are updated and tranche
    // prices adjusted accordingly
    _updateAccounting();
    // get underlyings from sender
    address _token = token;
    uint256 _preBal = _contractTokenBalance(_token);
    _transferUnderlyingsFrom(msg.sender, address(this), _amount);
    // mint tranche tokens according to the current tranche price
    _minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
    // update trancheAPRSplitRatio
    _updateSplitRatio(_getAARatio(true));

  function _updateAccounting() internal virtual returns (bool shutdown) {
    _accrueManagementFee();
    uint256 _lastNAVAA = lastNAVAA;
    uint256 _lastNAVBB = lastNAVBB;
    uint256 _lastNAV = _lastNAVAA + _lastNAVBB;
    uint256 nav = getContractValue();
    uint256 _aprSplitRatio = trancheAPRSplitRatio;
    // If gain is > 0, then collect some fees in `unclaimedFees`
    if (nav > _lastNAV) {
      unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
    }
    (uint256 _priceAA, int256 _totalAAGain) = _virtualPriceAux(AATranche, nav, _lastNAV, _lastNAVAA, _aprSplitRatio);
    (uint256 _priceBB, int256 _totalBBGain) = _virtualPriceAux(BBTranche, nav, _lastNAV, _lastNAVBB, _aprSplitRatio);
    lastNAVAA = uint256(int256(_lastNAVAA) + _totalAAGain);

    int256 totalGain = int256(_nav) - int256(_lastNAV);
    // Ordinary zero-delta interactions keep their saved price for compatibility. Forced
    // accounting recomputes NAV per share, which is required after discounted mid-epoch deposits.
    if (totalGain == 0 && !skipDefaultCheck) return (_tranchePrice(_tranche), 0);

    // Remove performance fee for gains
    if (totalGain > 0) {
      totalGain -= totalGain * int256(fee) / int256(FULL_ALLOC);
    }

    bool _isAATranche = _tranche == AATranche;
    // A class with no saved NAV cannot be revived by later gains. If only this class has saved
    // NAV, it receives the full gain or loss; otherwise both classes participate.
    if (_lastTrancheNAV == 0) {
      _totalTrancheGain = 0;
    } else if (_lastNAV == _lastTrancheNAV) {
      _totalTrancheGain = totalGain;
    } else {
      if (totalGain > 0) {
        // Split the net gain, according to _trancheAPRSplitRatio, with precision loss favoring the AA tranche.
        int256 totalBBGain = totalGain * int256(FULL_ALLOC - _trancheAPRSplitRatio) / int256(FULL_ALLOC);
        // The new NAV for the tranche is old NAV + total gain for the tranche
        _totalTrancheGain = _isAATranche ? (totalGain - totalBBGain) : totalBBGain;
      } else {
        int256 maxBBLoss = -int256(lastNAVBB);
        int256 totalBBLoss = totalGain > maxBBLoss ? totalGain : maxBBLoss;
        _totalTrancheGain = _isAATranche ? totalGain - totalBBLoss : totalBBLoss;
      }
    }
    // Split the new NAV (_lastTrancheNAV + _totalTrancheGain) per tranche token
    _virtualPrice = uint256(int256(_lastTrancheNAV) + _totalTrancheGain) * ONE_TRANCHE_TOKEN / trancheSupply;
