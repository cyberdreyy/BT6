### Title
Stale `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch` entries survive a funded instant-withdraw claim and are re-counted in `defaultPendingClaimBasis`, diluting (and permanently stranding) the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog of the "trimming leaves data in storage" bug class: `claimInstantWithdrawRequest` clears only the aggregate counter `instantWithdrawsRequests[_user]` but never removes the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in the same epoch while some *other* instant receipt is still unfunded, `defaultPendingClaimBasis()` re-reads the stale epoch bucket and counts already-claimed-and-paid receipts a second time. The finalized `defaultRecoveryPrice` is therefore computed against an inflated `totalBasis`, every recovery claimant (including active tranche holders) is permanently underpaid, and the corresponding slice of `defaultRecoveryReserve` is stranded forever.

### Finding Description
Relevant storage writes:

- `requestInstantWithdraw` records `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount`, `instantWithdrawClaimsByEpoch[epochNumber] += _amount`, `pendingInstantWithdraws += _amount` (lines 366–374).
- `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` (line 401); it does not touch the per-epoch claim bucket.
- `claimInstantWithdrawRequest` pays out the aggregate and sets `instantWithdrawsRequests[_user] = 0` but never deletes `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` (lines 387–392) — the "keys left in storage" analog.
- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines 644–649).
- `finalizeDefaultRecovery` uses that inflated basis in `totalBasis`, lowering `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (lines 679–692), and burns/mints CDO-held strategy tokens against the diluted `activeFinalNAV` (lines 699–705).

Attack sequence (all unprivileged, epoch N running, instant withdrawals enabled):

1. Attacker calls `requestInstantWithdraw(X)` — epoch bucket N records X.
2. Borrower/CDO funds it via `collectInstantWithdrawFunds(X)` → `pendingInstantWithdraws` back to 0.
3. Attacker calls `claimInstantWithdrawRequest` and receives X underlying. Stale `instantWithdrawsRequestsByEpoch[attacker][N] = X` and `instantWithdrawClaimsByEpoch[N] = X` remain.
4. Any user (can also be the attacker) requests another instant withdraw `Y` in the same epoch that is only partially/never funded → `pendingInstantWithdraws = Y`, `instantWithdrawClaimsByEpoch[N] = X + Y`.
5. Borrower defaults within epoch N; guardian/manager runs `_handleBorrowerDefault` → `finalizeDefaultRecovery`. Basis includes `X + Y` although only `Y` is still owed.
6. `defaultRecoveryPrice` is diluted by `X / totalBasis`; all default claims and the active-side NAV crystallization pay out at the lower price. The `X * recoveryPrice` portion of `defaultRecoveryReserve` is never claimed (`_claimDefaultedInstantWithdrawRequest` underflows/reverts for the attacker since `instantWithdrawsRequests[attacker]` was zeroed) and is permanently locked in the vault.

### Impact Explanation
Every defaulted-epoch claimant — pending withdraw-receipt holders, unfunded instant withdrawers, and active AA/BB holders whose strategy-token NAV is crystallized at `activeFinalNAV` — receives `X / totalBasis` less than their entitlement. The unclaimed residue (`X * defaultRecoveryPrice / RECOVERY_FULL`) is permanently stranded in the vault because the only path that could consume it reverts on underflow. This is a quantifiable, permanent loss of recovery funds to all legitimate claimants caused by storage data that should have been deleted at claim time — the same failure mode as keys/signatures left in storage after trimming.

### Likelihood Explanation
Requires: instant withdrawals enabled, one fully-funded-and-claimed instant receipt, a second unfunded instant receipt, and a borrower default all inside the same epoch. Defaults are rare and the epoch must remain running for steps 2–5, but no privileged misbehavior is needed — the sequence around honest owner/manager/borrower calls is entirely composed of unprivileged user transactions. Stale per-epoch accounting is deterministic once it occurs, so whenever this ordering happens the dilution is guaranteed.

### Recommendation
Mirror the normal-withdraw cleanup already done in `_clearWithdrawClaimForEpoch`: when a funded instant receipt is claimed in `claimInstantWithdrawRequest`, also clear `instantWithdrawsRequestsByEpoch[_user][epoch]` for the epoch(s) it belongs to and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount (attributing it to the correct epoch, e.g. via a `lastInstantWithdrawRequestEpoch` marker, since instant claims can span epochs). At minimum, exclude already-claimed basis from `instantWithdrawClaimsByEpoch` so `defaultPendingClaimBasis` only counts still-owed receipts.

### Proof of Concept
Foundry fork test (against the repo's own harness, e.g. `test/foundry/IdleCreditVault.t.sol` style):

```solidity
function testStaleInstantEpochBucketDilutesDefaultRecovery() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);          // enter epoch 1 buffer
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    // Alice (attacker) and Bob deposit and start the epoch
    uint256 tranchesAlice = _depositWithUser(attacker, 1_000e6);
    uint256 tranchesBob   = _depositWithUser(victim,   1_000e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    uint256 epoch = strategy.epochNumber();

    // 1) attacker instant withdraw, fully funded, then claimed
    _requestInstantWithdraw(attacker, tranchesAlice);
    uint256 x = strategy.instantWithdrawsRequests(attacker);
    deal(defaultUnderlying, borrower, x, true);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), x);
    // manager pulls instant funds back through the CDO instant-withdraw path
    // (getInstantWithdrawFunds -> collectInstantWithdrawFunds(x))
    // ... then:
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();   // pays X, leaves stale epoch bucket

    // 2) victim instant withdraw Y in the SAME epoch, left unfunded
    _requestInstantWithdraw(victim, tranchesBob);
    assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), x + strategy.instantWithdrawsRequests(victim));

    // 3) borrower defaults before funding Y
    _handleBorrowerDefaultWithRecovery(recoveryAmount);

    // basis used by finalizeDefaultRecovery is x + y instead of y
    // -> defaultRecoveryPrice is diluted; stranded reserve = x * defaultRecoveryPrice / 1e5
    uint256 reserve = strategy.defaultRecoveryReserve();
    // victim claims at diluted price; the x-share is never claimable again
    vm.prank(victim);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(strategy.defaultRecoveryReserve(), 0, 'stale basis left stranded recovery dust');
}
```

Note on confidence: the code inspection confirms the stale per-epoch buckets are never cleared on the funded claim path and are re-read by `defaultPendingClaimBasis`; the exact default-entry flow (`_handleBorrowerDefault` in `IdleCDOEpochVariant`) was not fully re-verified line-by-line within the iteration budget, so the PoC skeleton uses the repo's existing default helpers rather than re-deriving that call chain.
