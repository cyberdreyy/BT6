### Title
Already-claimed instant-withdraw receipts are never removed from `instantWithdrawClaimsByEpoch`, inflating the default-recovery reserve and price — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external bug is a resource leak: `netlbl_cipsov4_add_std` allocates `doi_def->map.std` and no path ever frees it. The vault analog is bookkeeping that is written at request time but never released on the funded path: `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are incremented in `requestInstantWithdraw` and are only ever decremented inside `_claimDefaultedInstantWithdrawRequest`. A user whose instant withdrawal is fully funded and claimed at par leaves both counters permanently elevated, exactly like an allocated object that is never freed. When a later partial default is finalized in the same epoch, `_defaultPrefundedInstantReserve` and `defaultPendingClaimBasis` treat those already-paid-out funds as still-reserved basis, so `finalizeDefaultRecovery` computes a fictitious reserve and an inflated `defaultRecoveryPrice`.

### Finding Description
In `requestInstantWithdraw`, per-epoch accounting is recorded:

- `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`
- `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`

The funded claim path `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]`, zeroes the aggregate, and pays out — but never touches the two per-epoch counters. Only the defaulted path `_claimDefaultedInstantWithdrawRequest` clears them.

At finalization, `defaultPendingClaimBasis()` adds the full `instantWithdrawClaimsByEpoch[epochNumber]` (including already-claimed receipts) whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve()` counts `instantBasis - pendingInstant` as underlyings still held by the strategy. Funds that were claimed at par were transferred out, yet they are counted twice: once as claim basis and once as prefunded reserve. `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is therefore computed with a fabricated reserve component that does not exist as a balance.

### Impact Explanation
`defaultRecoveryPrice` is inflated relative to real held funds. Earlier claimants — including an attacker who deliberately keeps a defaulted-epoch receipt — withdraw `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` via `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve`. Once the real underlying balance is exhausted, subsequent claimants' `safeTransfer` reverts, permanently freezing their recovery share. The result is direct theft of the unfunded instant claimants' and normal receipt holders' recovery by earlier claimants, plus permanent freezing of the remainder. Broken invariant: one receipt one payout / reserve isolation — paid-out funds are double-counted as recovery backing.

### Likelihood Explanation
Requires a common sequence in a running epoch: (1) an instant withdraw request that gets fully funded via `collectInstantWithdrawFunds` and claimed at par; (2) at least one instant withdraw request that remains unfunded (`pendingInstantWithdraws != 0`); (3) borrower default with `finalizeDefaultRecovery` executed before `epochNumber` increments (epochNumber only bumps at `stopEpoch`/`deposit`). The attacker is an ordinary KYC'd tranche holder performing steps (1) and holding any defaulted-epoch receipt; all privileged actors (borrower funding, manager default handling) behave honestly. No existing guard prevents it: `_transferFundedClaim` only protects the reserve on the funded side, and nothing validates `instantWithdrawClaimsByEpoch` against actually-held balances.

### Recommendation
On the funded claim path in `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (or track the request epoch) and `instantWithdrawClaimsByEpoch[currentEpoch]` by the claimed amount, mirroring the cleanup `_claimDefaultedInstantWithdrawRequest` performs — i.e., "free" the per-epoch allocation when the receipt is paid, not only when it is defaulted.

### Proof of Concept
Foundry fork PoC outline:

1. Start an epoch; attacker (KYC'd AA holder) calls `cdo.requestInstantWithdraw(A)` → strategy mints receipt, `instantWithdrawsRequestsByEpoch[attacker][N] = A`, `instantWithdrawClaimsByEpoch[N] = A`, `pendingInstantWithdraws = A`.
2. CDO funds it (`collectInstantWithdrawFunds(A)` → `pendingInstantWithdraws = 0`), attacker calls `claimInstantWithdrawRequest` and receives `A` at par. Per-epoch counters remain `A`.
3. Victim calls `requestInstantWithdraw(B)` → `instantWithdrawClaimsByEpoch[N] = A + B`, `pendingInstantWithdraws = B`; only part (or none) is funded.
4. Borrower defaults; `finalizeDefaultRecovery(R, source)` runs at `epochNumber = N`:
   - `prefundedReserve = (A + B) - pendingInstant ≥ A` counts already-paid `A` as reserve,
   - `basis += A + B` includes the claimed `A`,
   - `recoveryPrice` is set against a reserve that does not contain `A`.
5. Attacker also holds a defaulted-epoch normal withdraw receipt of `A` (from `requestWithdraw` earlier in epoch N, which minted receipt tokens). Calling `claimWithdrawRequest` pays `A * inflatedPrice`, overdrawing the reserve.
6. Victim's `_claimDefaultedInstantWithdrawRequest` for `B` reverts on `safeTransfer`/`defaultRecoveryReserve` underflow → permanent loss of the recovery share. Assert `underlying.balanceOf(attacker)` exceeds `A + fairShare` and victim's claim reverts.
