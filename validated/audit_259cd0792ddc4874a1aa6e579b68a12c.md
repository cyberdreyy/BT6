## Title
Minority signers (>30% weight, well under the 70% supermajority) can force the entire signer set to capitulate their miner-view state machine to a stale/false view — `capitulate_miner_view` (File: `stacks-signer/src/v0/signer_state.rs`)

### Summary
The Nakamoto signer protocol requires a 70% weighted supermajority (`NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD == 7`) to reach agreement on anything consensus-relevant: block signatures, the global burn view, and the global signer-state machine via `determine_global_state`/`determine_global_burn_view`. However, `LocalStateMachine::capitulate_miner_view` in `stacks-signer/src/v0/signer_state.rs` contains a branch that accepts a candidate `current_miner` view with only the **blocking-minority threshold** (`reached_disagreement`, i.e. strictly more than 30% of weight) instead of the 70% agreement threshold, whenever the claimed tenure already has at least one globally accepted block recorded locally. [1](#0-0) 

This is precisely the multisig-collusion pattern in the external report: instead of requiring `p` (70%) agreement to move the shared state forward, a subset as small as `n−p+1` (i.e. just over 30%) can force the majority to accept their claimed state.

### Finding Description
`capitulate_miner_view` tallies weight per distinct `StateMachineUpdateMinerState::ActiveMiner` claim broadcast by peers over StackerDB: [2](#0-1) 

The gating logic is:
```
if !eval.reached_disagreement(*entry) {
    continue;   // needs >30% weight to even be considered
}
let nmb_blocks = signerdb.get_globally_accepted_block_count_in_tenure(tenure_id).unwrap_or(0);
if nmb_blocks == 0 && !eval.reached_agreement(*entry) {
    continue;   // only requires 70% if the tenure has ZERO globally accepted blocks
}
```
`reached_agreement` requires ≥70% of total weight; `reached_disagreement` requires only >30% of total weight: [3](#0-2) 

So whenever `nmb_blocks > 0` — i.e. the claimed tenure has already produced at least one block that reached the *real* 70% global-acceptance threshold at some point in the past (a fact independently knowable/public, not something the colluders need to fabricate) — the code drops the acceptance bar for *that specific claim* down to just over 30% weight. Any group of colluding signers holding just over 30% weight can then broadcast `StateMachineUpdate` messages naming an `ActiveMiner`/tenure/parent-tenure view of their choosing (as long as it references a tenure with ≥1 previously globally-accepted block), and `capitulate_viewpoint`/`capitulate_miner_view` will cause every other (honest) signer's local state machine to adopt this minority-chosen view: [4](#0-3) 

This directly parallels the multisig report's core flaw: a sub-`p` set (`n−p+1`) can unilaterally force acceptance of a state that legitimately requires `p` (70%) consensus, because a secondary code path silently substitutes the blocking-minority threshold for the supermajority threshold under a specific precondition. Everywhere else in this codebase (`determine_global_state`, `determine_global_burn_view`, `determine_latest_supported_signer_protocol_version`) strictly gates on `reached_agreement` (70%); `capitulate_miner_view` is the outlier.

### Impact Explanation
Once the local state machine's `current_miner`/`parent_tenure_last_block` is corrupted by a sub-30%-blocking-but-not-70%-approving minority, this state feeds directly into block-proposal evaluation (`check_block_against_signer_db_state`, `check_proposal`, and the `SortitionsView`/`GlobalStateView` machinery documented in `docs/signer-flows.md` section 7–8) and into whether the miner is considered timed out (`check_miner_inactivity`). A minority-forced, incorrect miner view can cause the honest 70%+ of signers to:
- reject valid proposals from the actual sortition-winning miner (because the state machine now claims a different `current_miner`/parent tenure), wedging block production — a liveness wedge requiring only ~31% colluding weight rather than 70%; or
- shift agreement about which tenure is the legitimate parent, affecting subsequent proposal validation.

This matches the "High" impact bucket: a signer (or the whole honest set) wedged into never signing valid blocks / acting on a stale view, achievable by a minority far below the required supermajority.

### Likelihood Explanation
No majority collusion, no auth token, and no other signer's key are required — only slightly over 30% of the signer set's weight broadcasting crafted (but otherwise well-formed) `StateMachineUpdate` gossip messages over StackerDB naming a tenure that already has at least one globally-accepted block (a condition that is either trivially true for the previous tenure, or that a well-resourced minority can arrange). This is exactly the scenario class the prompt calls out: "a set of owners (less than required) can force" a state transition normally gated behind the full threshold.

### Recommendation
Remove the `nmb_blocks > 0` carve-out in `capitulate_miner_view`, or replace it with a check that still requires `reached_agreement` (70%) for adopting a *new* miner-view candidate; the `nmb_blocks` fact can be used as corroborating evidence but must not be allowed to substitute for the supermajority threshold. Align this function with `determine_global_state`/`determine_global_burn_view`, which correctly gate solely on `reached_agreement`.

### Proof of Concept
1. Set up a signer set where a colluding cohort holds weight `w` with `30% * total_weight < w < 70% * total_weight` (e.g. 35% of weight across N signers).
2. Have the colluding cohort broadcast (via StackerDB) `StateMachineUpdate` messages all agreeing on a crafted `ActiveMiner` state referencing a `tenure_id` that already has ≥1 globally accepted block recorded in every signer's local `SignerDb` (any prior, already-settled tenure works), but with a `parent_tenure_last_block`/`parent_tenure_last_block_height` that misrepresents the tenure's up-to-date tip.
3. Every honest signer's `process_event` → `capitulate_viewpoint` → `capitulate_miner_view` loop (`stacks-signer/src/v0/signer_state.rs:1019-1054`) tallies the colluders' claim, passes `reached_disagreement` at ~35% weight, finds `nmb_blocks > 0` for that tenure, and skips the `reached_agreement` check — adopting the colluders' `ActiveMiner` state as `new_miner` even though it never reached 70% support.
4. Observe that the honest majority's local state machines now disagree with the true sortition-derived current miner, causing rejections of the legitimate miner's subsequent block proposals (verifiable by comparing `check_block_against_state` outcomes before/after the crafted broadcast).

    /// Check if the supplied vote weight crosses the global agreement threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_agreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }

    /// Check if the supplied vote weight crosses the blocking minority threshold.
    /// Returns true if it has, false otherwise.
    pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
        u64::from(vote_weight)
            > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
                / 10
    }
