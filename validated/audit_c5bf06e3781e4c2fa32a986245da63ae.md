### Title
`setJobSpanAttributes` places raw variable values into exported OTEL spans without checking the `Masked` flag - ([File: commands/tracing.go])

### Summary
`setJobSpanAttributes` (commands/tracing.go:84-93) obtains `CI_PIPELINE_ID`/`CI_PIPELINE_SOURCE` via `build.Variables.Value(key)`, which performs a last-match key lookup over the entire `Variables` slice and returns the raw `Value` field regardless of the variable's `Masked` flag. Because trace-log masking (`helpers`/`buildlogger` masker) is only applied to the job log writer, any variable value routed through this function is exported to the configured OTLP endpoint completely unmasked.

### Finding Description
`Variables.value()` (common/spec/variables.go:107-123) iterates the slice from the end and returns the first key match without ever inspecting `Variable.Masked`. `setJobSpanAttributes` calls this generic `Value()` accessor for two hardcoded keys and forwards the result straight into `span.SetAttributes` (commands/tracing.go:85-92), which is later exported via `otlptracehttp`/`otlptracegrpc` to a potentially external, non-GitLab-controlled collector (`exporterForEndpoint`, commands/tracing.go:121-212). No masking, redaction, or `Masked`-flag check exists anywhere on this path, unlike the job-log write path which routes through the masker in `common/buildlogger`.

The scoped exploit (an unprivileged job author defining a custom job variable literally named `CI_PIPELINE_ID`/`CI_PIPELINE_SOURCE` to shadow the predefined ones) does not, however, demonstrate a cross-tenant secret leak from Runner's perspective: whether such a name collision is permitted, and whether the *value* placed under that key can be the *content* of a separate protected/masked secret the attacker does not already control, is determined entirely by GitLab Rails' pipeline/variable resolution logic before the job payload ever reaches Runner. Runner just consumes whatever `Variables` slice it is given in the job payload; it does not implement precedence rules between predefined and custom variables. If the attacker is the one defining the colliding variable's value directly, the "leaked" value is simply data they already authored/possess, not a secret exfiltrated from another party.

### Impact Explanation
Concrete Runner-side impact is limited to: **any variable that reaches Runner under the exact key `CI_PIPELINE_ID` or `CI_PIPELINE_SOURCE` with `Masked=true` will have its raw value shipped unmasked to the configured OTEL endpoint.** This is a real gap relative to the stated invariant that masked values must never leave via any export path. It does **not**, by itself, allow an unprivileged attacker to exfiltrate another user's or project's protected secret, because Runner never iterates over arbitrary job variables in this function — only these two fixed keys are read — and whether a genuinely foreign secret can be forced into one of those two keys is a GitLab-server variable-resolution question outside this repository, not a Runner logic bug.

### Likelihood Explanation
Low-to-moderate as a standalone Runner bug: it requires (a) an OTEL tracing endpoint to be configured by the runner operator (opt-in feature via `spec.Tracing`), and (b) a variable named exactly `CI_PIPELINE_ID`/`CI_PIPELINE_SOURCE` arriving with `Masked=true` in the job payload — a condition Runner does not itself create or validate. Absent evidence that GitLab's server-side variable precedence lets an unprivileged user's custom variable both collide with a predefined key name and carry another party's protected secret value, this remains a defense-in-depth gap in Runner rather than a demonstrated end-to-end secret-exfiltration exploit fully within this codebase.

### Recommendation
In `setJobSpanAttributes`, avoid using the generic, override-able `Variables.Value()` lookup for telemetry. Instead, source `pipeline_id`/`pipeline_source` from a non-overridable, dedicated field on `build.JobInfo`/`build.Runner` payload (if available) rather than the mutable `Variables` bag, or explicitly skip/redact any variable with `Masked == true` before it is allowed to reach `span.SetAttributes`, consistent with the masking guarantee applied to job logs.

### Proof of Concept
```go
func TestSetJobSpanAttributes_DoesNotMaskVariables(t *testing.T) {
    build := &common.Build{
        JobResponse: common.JobResponse{
            Variables: common.JobVariables{
                {Key: "CI_PIPELINE_ID", Value: "super-secret-value", Masked: true},
            },
        },
    }
    recorder := tracetest.NewSpanRecorder() // or a fake oteltrace.Span capturing SetAttributes calls
    span := recorder.StartSpan(...)

    setJobSpanAttributes(span, build, &common.RunnerConfig{})

    attrs := recorder.Ended()[0].Attributes()
    for _, a := range attrs {
        assert.NotContains(t, a.Value.AsString(), "super-secret-value",
            "masked variable value must not appear in exported span attributes")
    }
}
```
Expected today: the assertion fails, confirming the raw masked value is present in the span attribute — proving the gap in this function, independent of whether a full cross-tenant exploit chain exists upstream in GitLab's variable resolution.
