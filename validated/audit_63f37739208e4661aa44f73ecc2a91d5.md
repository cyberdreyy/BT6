### Title
View-role user can read bridge OutgoingToken and configuration via unguarded `GET /v2/bridge_types/:BridgeName` - (File: core/web/router.go)

### Summary
The route `GET /v2/bridge_types/:BridgeName` is registered under `authv2` (authenticated) but with no `RequiresEditRole`/`RequiresAdminRole` wrapper, unlike its sibling `POST`/`PATCH`/`DELETE` routes. Any authenticated user, including one with the lowest `view` role, can call `BridgeTypesController.Show`, which returns `presenters.NewBridgeResource(bt)` including the bridge's `OutgoingToken`, `URL`, and other configuration fields.

### Finding Description
In `core/web/router.go` the bridge routes are:
```go
authv2.GET("/bridge_types", paginatedRequest(bt.Index))
authv2.POST("/bridge_types", auth.RequiresEditRole(bt.Create))
authv2.GET("/bridge_types/:BridgeName", bt.Show)
authv2.PATCH("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Update))
authv2.DELETE("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Destroy))
``` [1](#0-0) 

Both `Index` and `Show` lack any role guard — only `auth.Authenticate` applies, which succeeds for any valid session or API token regardless of role (`view`, `run`, `edit`, `admin`). `BridgeTypesController.Show` loads the bridge from the ORM and serializes it via `presenters.NewBridgeResource(bt)`:
```go
jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
``` [2](#0-1) 

The presenter includes `OutgoingToken` with no `omitempty` tag (always serialized), plus `URL`, `Confirmations`, `MinimumContractPayment`, and `UseConnectionManager`:
```go
type BridgeResource struct {
	JAID
	Name          string `json:"name"`
	URL           string `json:"url"`
	Confirmations uint32 `json:"confirmations"`
	IncomingToken          string       `json:"incomingToken,omitempty"`
	OutgoingToken          string       `json:"outgoingToken"`
	...
}
``` [3](#0-2) 

`IncomingToken` is only populated at creation time (`bta.IncomingToken` set in `Create`) and is not stored in the `BridgeType` DB struct as plaintext (only `IncomingTokenHash`+`Salt`), so it does not leak via `Show`. However, `OutgoingToken` is stored in plaintext on `bridges.BridgeType` and is always included in the resource:
```go
type BridgeType struct {
	...
	OutgoingToken          string
	...
}
``` [4](#0-3) 

The `RequiresEditRole` and `RequiresAdminRole` middlewares in `core/web/auth/auth.go` demonstrate that the codebase's intended authorization model treats bridge mutation as edit-restricted, but read (`GET`) was left unguarded on both `Index` and `Show`. [5](#0-4) 

### Impact Explanation
`OutgoingToken` is a credential used by the bridge/external adapter integration (analogous to a shared secret used when the node calls out to the external adapter, or the adapter authenticates callbacks). Its disclosure to a low-privilege `view` role user constitutes exposure of a secret/credential beyond the intended privilege boundary that the codebase otherwise explicitly protects (create/update/delete are `edit`-gated). This matches a "sensitive data / credential disclosure to unauthorized role" impact class. The `URL` field can also reveal internal-network adapter endpoints not meant for `view`-role visibility.

### Likelihood Explanation
Precondition is minimal: an existing authenticated node API user with the lowest privilege role (`view`), or a `view`-scoped API token. Given a valid session/token, the request is a trivial, repeatable `GET /v2/bridge_types/:BridgeName` (or `GET /v2/bridge_types` for all bridges) with no additional bypass needed — the middleware chain for these two routes simply omits any role check.

### Recommendation
Wrap `GET /bridge_types` and `GET /bridge_types/:BridgeName` with an appropriate role guard (e.g., `auth.RequiresEditRole`, matching the mutation endpoints), or redact `OutgoingToken`/`URL` from `presenters.BridgeResource` for view-role responses. At minimum, apply `omitempty`/role-based filtering to `OutgoingToken` similar to how `IncomingToken` is already treated as create-only.

### Proof of Concept
Go handler-level integration test plan (in `core/web/bridge_types_controller_test.go` style):
1. Create a bridge via an `edit`/`admin` session (`POST /v2/bridge_types`), capturing the returned `OutgoingToken`.
2. Create a second test client authenticated with a `view`-role user (`cltest.NewUserWithSession` / equivalent helper with `sessions.UserRoleView`).
3. Issue `GET /v2/bridge_types/:BridgeName` using the view-role session.
4. Assert response status is `200 OK` (not `401`/`403`).
5. Assert the JSON body contains `outgoingToken` equal to the captured token value, proving disclosure to a role that should not have edit-level visibility.
6. Repeat for `GET /v2/bridge_types` (Index) to confirm the same issue for the list endpoint.

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
```

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
