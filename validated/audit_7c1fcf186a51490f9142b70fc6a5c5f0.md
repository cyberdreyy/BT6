### Title
Zero-share deposit steals user funds when accrued interest inflates tranche price — `IdleCDOCreditVault._mintSharesAtCurrPrice` mints 0 tranche tokens without reverting - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault._deposit` pulls the user's underlying and then mints shares via `_mintSharesAtCurrPrice`, which computes `_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` with no `minted > 0` check. An attacker who is the first depositor can seed the AA (or BB) tranche with a 1-wei deposit, then let epochs accrue minted interest (`isInterestMinted` / `mintStrategyTokens`) so NAV — and therefore tranche price — grows against the same dust-sized supply. Any subsequent depositor whose `_amount` is below the inflated `priceAA`/`priceBB` receives **0 tranche tokens while their entire deposit is kept**, and their funds are absorbed into the attacker's NAV share. This is the direct analog of the wxETH drip-inflation / first-1-wei-deposit bug, with the honest epoch interest playing the role of the drip.

### Finding Description
The share-mint path in the credit vault:

```solidity
// contracts/IdleCDOCreditVault.sol
function _mintSharesAtCurrPrice(uint256 _amount, address _to, address _tranche) internal virtual returns (uint256 _minted) {
    // calculate # of tranche token to mint based on current tranche price: _amount / tranchePrice
    _minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche);
    _mintShares(_tranche, _to, _minted, _amount);
}
```

And `_deposit` (lines 191–212) transfers the tokens unconditionally before minting:

```solidity
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
...
IIdleCDOStrategy(strategy).deposit(_amount);
```

`_mintShares` credits `lastNAVAA`/`lastNAVBB` with the full `_underlyings` even when `_shares == 0`, so the deposit is permanently socialized to existing holders.

Price inflation without donations: `_virtualPriceAux` computes `virtualPrice = (lastTrancheNAV + trancheGain) * ONE_TRANCHE_TOKEN / trancheSupply`. With `isInterestMinted` enabled (mandatory for programmable borrowers), `IdleCreditVault.mintStrategyTokens` increases strategy-token NAV during each epoch while tranche supply stays fixed. The `_skimDonatedAssets` guard only removes *raw underlying* donations — it cannot remove legitimately accrued strategy-token interest, so no existing guard stops this. `_guarded(_amount)` is only a maximum-deposit check; there is no minimum.

Attack sequence (buffer/running epoch phases):
1. Attacker (a KYC-passing lender) is the first depositor: `depositAA(1)` during a buffer period → receives `1e18` AA tranche tokens, `lastNAVAA = 1`, `priceAA = 1e18`.
2. Attacker is the sole LP while the manager honestly starts/stops epochs. Each epoch with minted interest grows `strategyToken` NAV; `priceAA` rises to `NAV * 1e18 / 1e18` wei. With NAV of e.g. 100e18, `priceAA ≈ 100e18` (i.e. each tranche token is backed by ~100 underlying).
3. Victim calls `depositAA(D)` with `D < priceAA / 1e18` units… more precisely any `D` such that `D * 1e18 / priceAA == 0`, i.e. `D < NAV` when supply was 1 wei. `_minted == 0`, the full `D` is transferred into the strategy, and `lastNAVAA += D` accrues entirely to the attacker's single share.
4. Attacker later `requestWithdraw`s / withdraws the whole NAV, extracting victim's deposit.

### Impact Explanation
Direct theft of user funds: the victim's entire deposit is lost and credited to the attacker. The quantified loss equals any deposit `< tranchePrice / ONE_TRANCHE_TOKEN` underlyings. In the wxETH PoC framing, the "minimum amount to get a single share" grows linearly with accrued interest; e.g. with 1 wei supply and NAV grown to ~0.104 tokens (the report's 15-min, 70-token-drip row analog: ~$187 at $1,800/ETH for an ETH-denominated vault, proportionally more for longer sole-staker periods), a victim depositing just below that threshold loses it all.

### Likelihood Explanation
Same constraints the judge accepted as Medium in the original report: the attacker must be the first/only tranche holder while interest accrues (single exchange rate, so inflation benefits the only share outstanding). Front-running the first deposit at deployment plus a manager honestly running epochs is sufficient; no privileged cooperation is needed — `startEpoch`/`stopEpoch`/`mintStrategyTokens` are honest operations that do the inflating. Dust-loss rounding also affects ordinary small deposits once price > 1, but material theft requires the sole-staker window.

### Recommendation
Revert when the computed mint amount is zero in `IdleCDOCreditVault._mintSharesAtCurrPrice` (and the base `IdleCDO._mintSharesAtCurrPrice`/`IdleCDOAmphorVariant` override for consistency):

```diff
  function _mintSharesAtCurrPrice(uint256 _amount, address _to, address _tranche) internal virtual returns (uint256 _minted) {
      _minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche);
+     _checkNotAllowed(_minted == 0); // or revert ZeroShares()
      _mintShares(_tranche, _to, _minted, _amount);
  }
```

Optionally seed an initial minimum deposit or dead-share mint at first deposit to bound relative inflation, mirroring the wxETH `mintAmount > 0` fix.

### Proof of Concept
Foundry fork PoC sketch against `IdleCDOEpochVariant` + `IdleCreditVault` (minted-interest mode):

```solidity
// Setup: vault with isInterestMinted = true, attacker = KYC'd user
// Phase 1: buffer period, attacker first depositor
underlying.mint(attacker, 1);
vm.prank(attacker);
idleCDO.depositAA(1);                       // gets 1e18 AA tranche tokens, lastNAVAA = 1

// Phase 2: honest epochs accrue minted interest (manager/borrower honest)
//   repeat startEpoch()/stopEpoch() until strategyToken NAV of CDO reaches ~NAV_TARGET
//   priceAA() now == NAV_TARGET * 1e18 / 1e18

// Phase 3: victim deposits less than NAV_TARGET
uint256 victimDeposit = navTarget - 1;
underlying.mint(victim, victimDeposit);
vm.prank(victim);
uint256 minted = idleCDO.depositAA(victimDeposit);

assertEq(minted, 0, "victim received zero shares");
assertEq(AAtranche.balanceOf(victim), 0);
assertEq(underlying.balanceOf(victim), 0); // funds taken

// Phase 4: attacker withdraws full NAV incl. victim's deposit
//   requestWithdraw + claim -> attacker balance > initial 1 wei + victimDeposit
```

Note: this assessment is based on the indexed code. I confirmed `_mintSharesAtCurrPrice` lacks a zero-share guard and that `_skimDonatedAssets` only handles raw underlying donations; I did not fully enumerate every `_deposit` override path in `IdleCDOEpochVariant`, but the minted-interest inflation channel does not depend on donation handling, so the finding stands on `contracts/IdleCDOCreditVault.sol` and `contracts/IdleCDOEpochVariant.sol` as cited.
