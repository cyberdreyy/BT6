### Title
Own-tenure conflict guard fails to prevent equivocation when the node hasn't yet observed the earlier signed tenure-change block - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit`'s own-tenure duplicate guard (the second conflict check, right after the chainstate re-check) only refuses to sign a new tenure-change block when the node's live tenure tip is already `>=` the proposed block's height. If the node has not yet observed/confirmed the earlier block this signer already signed for the same tenure (e.g. because that block was only locally accepted and never pushed/relayed to this signer's node), the tip query returns a height below the proposal, and the code lets the signer sign the second, conflicting tenure-change block — an equivocation for a single tenure/height, driven entirely by the timing of an ordinary one-slot miner's proposals.

### Finding Description
`check_block_against_signer_db_state` (the chainstate re-check run just before this guard) is documented and commented in the code as checking the **parent** tenure for a tenure-change block, not its own tenure: [1](#0-0) 

Because of this documented gap, the code adds a second, explicit "own-tenure conflict" guard: [2](#0-1) 

This guard only fires (`return;`, refusing to sign) when `stacks_client.get_tenure_tip(consensus_hash)` succeeds **and** `tip_height >= block_info.block.header.chain_length`. In every other outcome — the tenure tip not yet at that height, *or* the RPC call erroring — the code merely logs and falls through to sign: [3](#0-2) [4](#0-3) 

The conflicts considered here come from `get_signed_conflicts`, which is documented (in `docs/signer-flows.md`, section 5) to include blocks this very signer has already signed ("A signed block at the same or higher height in ANY tenure is a conflict"): [5](#0-4) 

So the sequence is:
1. Miner proposes tenure-change block A for tenure T at height H. Signer S validates, pre-commits, reaches the 70% pre-commit threshold, and signs A via `mark_locally_accepted` — but A is only *locally* accepted; it has not yet been pushed to / observed by S's own node (e.g. broadcast delay, node briefly unreachable, or the aggregator hasn't yet gathered enough signatures from the rest of the set to push it).
2. The same miner (or a re-broadcast/gossip path) proposes a second, different tenure-change block B, also claiming to start tenure T at height H (same `consensus_hash`, different content/txs).
3. `check_block_against_signer_db_state` checks B's **parent** tenure (per the documented behavior for tenure-change blocks), not tenure T itself, so it does not detect that S already signed A in T.
4. The own-tenure guard (lines 1432-1457) is reached. It finds A as a conflict in the same tenure and (since A is not a cross-tenure reorg case) `reorg_permit_stands` returns false for it, so the `if` condition is entered. It then queries `get_tenure_tip(T)` on S's own node. Because the node has not yet processed/confirmed anything in tenure T (A was never pushed), the returned tip height is below H — or the call errors — so the refusal branch (`tip_height >= chain_length`) is skipped.
5. S proceeds to `mark_locally_accepted` and sign B, having already signed A for the identical height/tenure.

This is the same root-cause pattern as the referenced report: a value is verified/committed at time T1 (the signer's own "I already signed A for this tenure/height" fact) and then re-derived from an external, mutable, and momentarily-lagging source (the node's live tenure tip) at time T2 to gate a second, conflicting commitment — and the re-derivation can be stale exactly when it matters, letting the second signature through.

### Impact Explanation
This breaks the "one signed block per height per tenure" invariant that the pre-commit/conflict-guard machinery exists to enforce (as stated in `docs/signer-flows.md` section 5). A single signer ends up having put its signature over two different, conflicting tenure-change blocks for the same tenure and height. If enough signers hit the same node-lag window (plausible, since a slow/partitioned node is common and not adversary-controlled), both blocks can independently accumulate threshold signatures, producing two competing, fully-signed blocks for the same tenure start — a concrete equivocation/fork risk that a one-slot miner can trigger purely by timing two proposals around this window, with no majority-of-signers collusion required. This matches the Critical class in scope: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
Likelihood is moderate-to-high in adversarial timing terms: a miner does not need any signer cooperation — it only needs to (a) get one signer to reach its own local pre-commit/signature threshold for block A while (b) that signer's own node has not yet been told about A (normal during network jitter, RPC hiccups, or simply because block-push happens asynchronously after threshold), and then (c) immediately propose a competing tenure-change block B for the same tenure/height. Since `get_tenure_tip` failure is explicitly handled by falling through to "treat the tenure as unconfirmed" (line ~1449-1456), an attacker can also induce this by simply causing transient RPC unavailability to the signer's node, which is a normal, low-cost occurrence rather than a majority-controlled action.

### Recommendation
For the own-tenure guard, treat "we have already locally or globally signed a conflicting tenure-change block for this tenure" as sufficient to refuse signing regardless of what the live `get_tenure_tip` RPC currently reports, i.e. default to refusing (not signing) whenever the RPC errors or the tip has not yet caught up, instead of defaulting to permit signing in the ambiguous case. Alternatively, extend `check_block_against_signer_db_state`'s tenure-change handling to also check the block's **own** tenure for previously-signed blocks (not just the parent tenure), closing the gap at its source rather than relying solely on the live-tip guard.

### Proof of Concept
1. Boot a signer set with signer S tracking node N.
2. Have the miner propose tenure-change block A for tenure T at height H; let S's pre-commit weight for A cross 70% and let S sign A (`mark_locally_accepted`), but block the broadcast/push of A to N (e.g. via the existing `TEST_SKIP_BLOCK_BROADCAST`/network fault-injection test hooks used elsewhere in the test suite, or simply delay N's RPC).
3. Confirm via `stacks_client.get_tenure_tip(T)` on N that its reported tip height is still `< H` (tenure T not yet observed by N).
4. Propose a second, distinct tenure-change block B for the same tenure T at height H (different tx set/ordering) and drive its pre-commit weight over 70% as well.
5. Observe S calls `mark_locally_accepted` a second time for B despite having already signed A for the same tenure/height, confirmed via the `handle_block_pre_commit` code path at `stacks-signer/src/v0/signer.rs:1432-1478`.

Note: this analysis is based on the explicit code and inline documentation in `handle_block_pre_commit` and `docs/signer-flows.md`; I was not able to fully inspect the exact implementations of `get_signed_conflicts`, `reorg_permit_stands`, and `get_tenure_tip` (only their call sites) within the available tool budget, so the precise conditions under which `reorg_permit_stands` returns false for a same-tenure conflict, and the exact staleness window of `get_tenure_tip`, should be independently confirmed against `stacks-signer/src/signerdb.rs` and `stacks-signer/src/client/stacks_client.rs` before treating this as fully proven.
