### Title
Funded instant-withdraw receipts are never cleared from the per-epoch ledgers, enabling double payout from the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2021-47416 — where a resource stayed in the `MDIOBUS_ALLOCATED` state so `mdiobus_free()` used the wrong cleanup path and leaked memory — `IdleCreditVault.claimInstantWithdrawRequest` leaves paid instant-withdraw receipts marked in the per-epoch ledgers (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`). A later borrower default in the same epoch then treats already-paid receipts as outstanding claims, inflating `defaultPendingClaimBasis` and letting the paid user claim a second time from `defaultRecoveryReserve`.

### Finding Description
`requestInstantWithdraw` records a receipt in three places: the aggregate `instantWithdrawsRequests[_user]`, the per-epoch `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]` (`IdleCreditVault.sol:366-374`). The normal claim path `claimInstantWithdrawRequest` burns the receipt tokens, zeroes `instantWithdrawsRequests[_user]`, and pays via `_transferFundedClaim` (`IdleCreditVault.sol:387-392`), but it never clears the two per-epoch entries — the "wrong state" cleanup, mirroring the kernel bug where the wrong state skipped `put_device()`.

Consequences after a default in that epoch (`defaultRecoveryEpoch == epochNumber`):

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-649`). Already-claimed funded receipts still sit in this ledger, so the claim basis is inflated and `recoveryPrice` computed in `finalizeDefaultRecovery` (`IdleCreditVault.sol:688`) is pushed down — a real haircut on legitimate claimants.
2. `_claimDefaultedInstantWithdrawRequest` keys off `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (`IdleCreditVault.sol:843-848`), which was never cleared for the already-paid user. On the next `claimInstantWithdrawRequest`, once `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, the stale entry is paid out again at `defaultRecoveryPrice` from `defaultRecoveryReserve` (`IdleCreditVault.sol:382-385, 842-856`) — a second payout for a receipt whose tokens were already burned.

### Impact Explanation
Direct theft / insolvency: each stale receipt lets a holder drain `defaultRecoveryReserve` a second time, and the inflated basis simultaneously lowers `defaultRecoveryPrice` for everyone else. The loss is bounded by total funded instant claims in the default epoch but is fully unprivileged — any user with an instant-withdraw receipt triggers it by simply claiming normally before the default and again after finalization.

### Likelihood Explanation
Requires an epoch with at least one funded-and-claimed instant withdrawal plus at least one still-pending instant withdrawal (`pendingInstantWithdraws != 0`) in the epoch where the borrower defaults — a normal operating state, since `collectInstantWithdrawFunds` funds the queue incrementally. The attacker performs only two ordinary `claimInstantWithdrawRequest` calls; no privileged cooperation is needed, and no existing guard (the `_transferFundedClaim` reserve check only guards the funded path, `_onlyIdleCDO` is satisfied) stops the second claim.

### Recommendation
In `claimInstantWithdrawRequest`, mirror the default-claim cleanup: locate the user's per-epoch entries and decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount when paying a funded claim (or track a funded-claims sub-ledger). Alternatively, have `defaultPendingClaimBasis` subtract already-claimed amounts, and gate `_claimDefaultedInstantWithdrawRequest` on receipts that are still unfunded rather than merely recorded.

### Proof of Concept
A Foundry fork test can reproduce it with the standard harness used in `test/foundry/IdleCDOEpochQueue.t.sol` (`testProcessPostDefaultWithdrawalAsNormalClaim` shows the default/finalize scaffolding): during a running epoch, user A calls `requestWithdraw` on the CDO to create an instant receipt; after `instantWithdrawDeadline`, the manager calls `getInstantWithdrawFunds` and A calls `claimInstantWithdrawRequest` — A is paid, yet `instantWithdrawsRequestsByEpoch[A][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` remain non-zero. Keep one unfunded instant receipt outstanding (`pendingInstantWithdraws > 0`), let the borrower default (`stopEpoch` returning nothing), and call `finalizeDefault`/`finalizeDefaultRecovery`. Then `defaultPendingClaimBasis` includes A's already-paid amount (lowering `defaultRecoveryPrice`), and a second `claimInstantWithdrawRequest` for A routes through `_claimDefaultedInstantWithdrawRequest` and transfers `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` again. Assert `underlying.balanceOf(A)` increased twice and that `defaultRecoveryReserve` decreases by more than A's legitimate basis.

One caveat I could not fully verify within the search budget: the exact condition setting `defaultInstantWithdrawsFinalized` and `defaultRecoveryEpoch` — if `defaultRecoveryEpoch` is pinned to a different epoch than the request epoch, the double-claim leg may be unreachable, though the basis-inflation leg via `instantWithdrawClaimsByEpoch[epochNumber]` still stands whenever the receipts and the default share an epoch.
