### Title
Shared read-write volume mounts across build/service/init containers in Concrete (steps) pods break role isolation - (File: executors/kubernetes/steps_pod.go)

### Summary
`stepsPreparePodConfig` and its helpers assemble a Concrete-mode pod where the build container, every attacker-declared service container, and the bootstrap init container all mount the exact same volumes via `stepsVolumeMounts()`, with no `ReadOnly` flags anywhere. This gives a user-controlled service image read-write access to the build workspace (`repo`), the cache directory, and — critically — the `scripts` emptyDir that holds the `gitlab-runner-helper` binary the build container later executes as `steps serve`.

### Finding Description
`stepsVolumeMounts()` [1](#0-0)  is used unconditionally by:
- the bootstrap init container, which writes the helper binary [2](#0-1) 
- the build container [3](#0-2) 
- **every user-declared service container**, via `stepsServiceContainer` [4](#0-3) 

None of the returned `api.VolumeMount` entries set `ReadOnly: true`, so the "scripts" volume (containing the copied `gitlab-runner-helper` binary at `s.stepsRunnerBinaryPath()`), the optional "repo" build-workspace volume, and the optional "cache" volume are all mounted read-write into service containers whose image name is fully attacker-controlled (a pipeline author's `services:` entry in `.gitlab-ci.yml`).

The build container's `Command` is `<scriptsDir>/gitlab-runner-helper steps serve` [5](#0-4) . Kubernetes starts all non-init containers (build + services) concurrently once the init container(s) finish; there is no ordering or read-only guarantee that prevents a fast-starting malicious service container from overwriting the file at that path in the shared "scripts" emptyDir before the build container's process actually execs it. Because the volume is writable from the service container and the path is fixed and predictable (`s.stepsRunnerBinaryPath()`), an attacker who controls only the service image definition can plant a malicious binary that will be executed inside the build container's higher-trust context (its own security context, environment, and network access) — a service-to-build privilege/role crossing.

Even without winning that race, the shared, writable "repo" and "cache" volumes let a service container read or tamper with build-container-owned files (checked-out source, extracted cache contents, files a script might write locally) that a service is not supposed to have any visibility into, which is itself a build/service role-boundary violation for any workspace content the job treats as build-only.

Existing protections do not stop this: `verifyAllowedImages` only restricts *which images* may be used [6](#0-5) , not what those (allowed) images can access once running; there is no per-role volume scoping or read-only enforcement in `stepsVolumeMounts`, and the docstring at lines 445-449/530-531 explicitly documents the volumes as "shared" without noting the read-write/service exposure implication.

### Impact Explanation
A pipeline author who can only define a `services:` image (an ordinary CI capability, no special runner privileges) can:
1. Read files from the build workspace/cache emptyDir that were not intended to be visible to services (secret exposure scoped to that job's own build container — files, not GitLab-wide secrets, but still a role/trust violation).
2. Win a startup race to overwrite the `gitlab-runner-helper` binary in the shared `scripts` emptyDir, causing the build container to execute attacker-supplied code with the build container's security context instead of the intended helper binary — a stronger-context execution outcome matching the "Expected Immunefi impact."

### Likelihood Explanation
Preconditions are trivial: any pipeline author who can add a `services:` entry (standard, unprivileged CI capability) can exploit the shared-volume read/write access immediately and deterministically for file read/tamper on `repo`/`cache`. The binary-overwrite race is timing-dependent (service image pull/start speed vs. build image pull/start speed) but is fully attacker-influenceable — the attacker can choose a minimal/fast-pulling service image and can pad the build image pull time is not required since the race is against container *start*, not image content; a distro-less/scratch service image will reliably start and write to the shared emptyDir before a larger build image is ready, making repeatable exploitation realistic.

### Recommendation
- Give service containers their own volume-mount set (mirroring legacy `getVolumeMounts` behavior) that excludes the `scripts` emptyDir and the build workspace/cache volumes entirely, unless a service explicitly and intentionally needs one of them.
- If services genuinely need cache/workspace access for legitimate use cases, mount those volumes `ReadOnly: true` for service containers.
- Mount the `scripts` volume `ReadOnly: true` everywhere except the bootstrap init container that writes the binary, so no runtime container (service or build) can mutate the helper binary after bootstrap.

### Proof of Concept
Go unit test in `executors/kubernetes/steps_pod_test.go` style:
```go
func TestStepsServiceContainer_DoesNotMountBuildOrScriptsVolumes(t *testing.T) {
    // build an executor with one service declared in s.options.Services
    c, err := s.stepsServiceContainer("svc", spec.Image{Name: "attacker/image"}, securityContext)
    require.NoError(t, err)

    for _, vm := range c.VolumeMounts {
        // assert the service container has no mount named "scripts", "repo", or "cache"
        assert.NotEqual(t, "scripts", vm.Name, "service container must not access the helper-binary volume")
        assert.NotEqual(t, "repo", vm.Name, "service container must not access the build workspace")
        if vm.Name == "cache" {
            assert.True(t, vm.ReadOnly, "cache volume must be read-only for service containers")
        }
    }
}
```
Expected current (failing) result: the service container's `VolumeMounts` includes `scripts`, `repo`, and `cache`, all with `ReadOnly: false`, demonstrating the role-confusion bug. A PoC job would declare a minimal `services:` image whose entrypoint writes an attacker payload to `<scriptsDir>/gitlab-runner-helper` and asserts (via job log/artifact) that the build container's `steps serve` process executed attacker-controlled code instead of the real helper.

func (s *executor) stepsVolumeMounts() []api.VolumeMount {
	mounts := []api.VolumeMount{
		{
			Name:      "scripts",
			MountPath: s.scriptsDir(),
		},
	}

	mounts = append(mounts, s.getVolumeMountsForConfig()...)

	if s.isDefaultBuildsDirVolumeRequired() {
		mounts = append(mounts, api.VolumeMount{
			Name:      "repo",
			MountPath: s.AbstractExecutor.RootDir(),
		})
	}

	if s.isDefaultCacheDirVolumeRequired() {
		mounts = append(mounts, api.VolumeMount{
			Name:      "cache",
			MountPath: s.AbstractExecutor.CacheDir(),
		})
	}

	return mounts
}
