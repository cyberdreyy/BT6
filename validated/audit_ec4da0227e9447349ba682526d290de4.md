### Title
Unauthenticated `create()` lets any attacker deploy a victim's canonical lockup account with an attacker-controlled whitelist - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create()` computes the deterministic lockup account for `owner_account_id` and deploys it using `staking_pool_whitelist_account_id` taken directly from the caller-supplied `whitelist_account_id: Option<ValidAccountId>` with no check that `predecessor_account_id` matches, is authorized by, or is even related to `owner_account_id`. Any unprivileged account can pay the minimum deposit and pre-create the *canonical* lockup address for an arbitrary victim, baking in a whitelist contract the attacker owns.

### Finding Description
The intended binding is: `LockupArgs.staking_pool_whitelist_account_id == LockupFactory.whitelist_account_id` for any lockup whose `owner_account_id` did not itself explicitly request an override.

In the actual code: [1](#0-0) [2](#0-1) 

```rust
pub fn create(
    &mut self,
    owner_account_id: ValidAccountId,
    ...
    whitelist_account_id: Option<ValidAccountId>,
) -> Promise {
    ...
    let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
        account_id.into()
    } else {
        self.whitelist_account_id.clone()
    };
    ...
}
``` [3](#0-2) 

There is no `assert!` comparing `env::predecessor_account_id()` to `owner_account_id`, no `assert_called_by_foundation`-style check, and no requirement that the deploying caller *is* the intended owner. The only guard is the deposit-size check `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)`, which any funded attacker can satisfy.

The lockup account address is fully deterministic from `owner_account_id`:
```rust
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
``` [4](#0-3) 

An attacker calls:
```
factory.create(owner_account_id = "victim.near",
                lockup_duration = ...,
                lockup_timestamp = None,
                vesting_schedule = None,
                release_duration = None,
                whitelist_account_id = Some("attacker-fake-whitelist.near"))
```
paying only `MIN_ATTACHED_BALANCE`. This deploys the canonical lockup account for `victim.near` with `staking_pool_whitelist_account_id = "attacker-fake-whitelist.near"` instead of the factory's trusted `whitelist_account_id`. Because `owner_account_id` inside the deployed `LockupArgs` is checked by string equality against `predecessor_account_id` in the lockup's `assert_owner`-style checks (not by an actual access key), `victim.near` still ends up as the nominal "owner" able to call owner-only methods such as `select_staking_pool` — but any pool-whitelist check performed by that lockup will consult the attacker's fake whitelist contract, which can be coded to always return `is_whitelisted() == true`.

This is confirmed by the repository's own existing test `test_create_lockup_with_custom_whitelist_success`, which demonstrates that supplying an arbitrary `whitelist_account_id` is accepted unconditionally, with no ownership check tying the caller to `owner_account_id`. [5](#0-4) 

### Impact Explanation
This pre-empts the NEAR Foundation's (or the token owner's) legitimate `create()` call for `victim.near`'s canonical lockup account — since the account name is deterministic, once the attacker occupies it, the rightful deployer can never deploy the real lockup with the correct, trusted whitelist at that address. Any future funds later staked from that lockup via `select_staking_pool` are validated against a whitelist contract the attacker controls, defeating the entire staking-pool safety check for that lockup. This matches the Critical category "a lockup deployed with parameters its rightful creator never chose." The attack is fully repeatable against every account name the attacker chooses to front-run, at the cost of only `MIN_ATTACHED_BALANCE` (~3.5 NEAR) per victim.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only enough NEAR to cover `MIN_ATTACHED_BALANCE` and a self-deployed "whitelist" contract exposing `is_whitelisted`. No privileged role, key, or prior relationship with the victim is required, and the call is a single unauthenticated transaction to the public factory contract. This makes the finding highly feasible and cheaply repeatable across arbitrary target account names.

### Recommendation
Restrict who may supply a custom `whitelist_account_id`: either require `env::predecessor_account_id() == owner_account_id.as_ref()` when `whitelist_account_id.is_some()`, or remove the parameter entirely and only allow the factory's `foundation_account_id` to override it via a separate, `assert_called_by_foundation`-gated method. Additionally, consider requiring `predecessor_account_id` to match `owner_account_id` (or being the foundation) for `create()` in general to prevent unauthorized front-running of the deterministic lockup account.

### Proof of Concept
```rust
#[test]
fn test_third_party_cannot_override_whitelist_for_victim() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker (not the owner/victim) calls create() for victim's account
    context.is_view = false;
    context.predecessor_account_id = String::from(attacker_account_id()); // attacker, NOT account_tokens_owner()
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());

    contract.create(
        account_tokens_owner(), // owner_account_id = victim, never consented
        lockup_duration,
        None,
        None,
        None,
        Some(custom_whitelist_account_id()), // attacker-controlled fake whitelist
    );

    // Assert: staking_pool_whitelist_account_id used differs from the factory's trusted whitelist,
    // even though owner_account_id (victim) never authorized this override and never called create().
    // (Captured by inspecting the serialized LockupArgs passed in the scheduled Promise::function_call,
    // or by deploying to near-workspaces/near-sdk-sim and reading back
    // lockup_contract.get_staking_pool_whitelist_account_id() != whitelist_account_id())
}
```
This demonstrates that `LockupArgs.staking_pool_whitelist_account_id != LockupFactory.whitelist_account_id` is reachable with `predecessor_account_id != owner_account_id`, breaking the intended binding without any consent from the victim owner.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,

    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
