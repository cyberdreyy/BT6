### Title
Stale rejection weight is never retracted when a signer flips to acceptance, corrupting the miner-side vote tally in `StackerDBListener` (`BlockStatus`) - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::poll_for_missed_chunks`/message-handling loop (the block starting around line 364 of `stacks-node/src/nakamoto_node/stackerdb_listener.rs`) tallies signer votes into a shared `BlockStatus` (`total_weight_approved`, `total_weight_rejected`, `responded_signers`, `gathered_signatures`). The `Accepted` branch guards its weight addition solely against `gathered_signatures.contains_key(&slot_id)` [1](#0-0) , while the `Rejected` branch guards its weight addition against `responded_signers.insert(slot_id)` [2](#0-1) . These are two independent sets, and neither branch checks the *other* bucket before crediting weight, nor retracts weight already credited to the other bucket. A signer that rejects a block and later re-votes to accept the same block (a normal, protocol-sanctioned event — the signer explicitly supports "re-evaluating" prior rejections, see `should_reevaluate_reject_reason`/`should_reevaluate_block`) ends up with its weight counted in **both** `total_weight_approved` and `total_weight_rejected` simultaneously for the same block, permanently.

### Finding Description
This is the same bug class as the reported `notifyRewardAmount` issue: a check validates a fresh credit/debit in isolation ("is this weight already in *this* bucket?") without reconciling the other bucket that represents the same underlying resource (a signer's single, current vote). The stacks-signer's own local vote bookkeeping (`stacks-signer/src/signerdb.rs`) already had to fix exactly this defect — `add_block_signature` clears any prior rejection record for that signer, and `add_block_rejection_signer_addr` refuses to record a rejection if a signature already exists — confirmed by the `reject_then_accept`/`accept_then_reject` unit tests and the CHANGELOG entry "Do not count both a block acceptance and a block rejection for the same signer/block." [3](#0-2) [4](#0-3) 

That reconciliation was never carried over to the miner-side coordinator's `BlockStatus` tracking in `stackerdb_listener.rs`:

- `Accepted` handler: only checks `!block.gathered_signatures.contains_key(&slot_id)` before adding `signer_entry.weight` to `total_weight_approved`; it does **not** check or clear `block.responded_signers`/prior rejection credit. [1](#0-0) 
- `Rejected` handler: only checks `block.responded_signers.insert(slot_id)` before adding weight to `total_weight_rejected`; it does not check whether the signer had already been credited (or will later be credited) with an acceptance. [2](#0-1) 

Concretely: signer S (weight W) sends `Rejected` first → `responded_signers` gets S's slot, `total_weight_rejected += W`. S later re-evaluates and sends `Accepted` for the *same* `signer_signature_hash` → `gathered_signatures` does not yet contain S's slot, so the guard passes and `total_weight_approved += W` as well. S's weight W is now double-booked into both tallies for the lifetime of that `BlockStatus` entry; the stale rejection is never retracted.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality that `signer_coordinator.rs` relies on to decide the fate of a proposed block:
- The rejection-threshold check `total_weight_rejected.saturating_add(weight_threshold) > total_weight` [5](#0-4)  is evaluated using a tally that can contain weight from signers who have *since* switched to approving the block. Because that check runs before the acceptance check in the polling loop [6](#0-5) , a block that in fact has enough live, current acceptances to cross the 70% signing threshold can still be declared `NakamotoNodeError::SignersRejected` by the miner because of stale, already-retracted rejection weight that was never cleared.
- This is a liveness wedge on the miner/coordinator path: a legitimately supported block can be discarded/reworked by the miner due to corrupted vote accounting, without requiring a majority of malicious signers — a single signer naturally re-evaluating its vote (an explicitly supported protocol behavior) is sufficient to leave stale weight in the wrong bucket. It matches the "liveness wedge" impact category for a coordinator-level accounting defect analogous to the reward-tally miscount in the source report.

### Likelihood Explanation
The trigger requires no more than one signer legitimately changing its vote for a block it already responded to, which the protocol explicitly permits via `should_reevaluate_reject_reason`/`should_reevaluate_block` (e.g. rejections for `NotFoundError`, `UnknownParent`, `NoSignerConsensus`, `ConnectivityIssues`, etc. are marked re-evaluable) [7](#0-6) . Given asynchronous block validation and normal reorg/timeout handling described throughout `docs/signer-flows.md`, a signer rejecting-then-accepting (or the reverse) the identical block hash is a realistic, unprivileged occurrence, not requiring cooperation from other signers.

### Recommendation
Mirror the reconciliation logic already implemented in `stacks-signer/src/signerdb.rs` inside `BlockStatus`'s accept/reject handling in `stackerdb_listener.rs`:
- When processing an `Accepted` message for a signer already present in `responded_signers` due to a prior rejection, retract that signer's weight from `total_weight_rejected` before/while crediting `total_weight_approved` (and vice versa for `Rejected` overriding a prior `Accepted`).
- Track per-signer "current vote" (accept/reject) rather than two independently-guarded, never-reconciled buckets, so weight is always attributed to exactly one bucket at a time, matching the invariant already enforced in the per-signer signerdb.

### Proof of Concept
1. Coordinator tracks a `BlockStatus` for block `B` with `weight_threshold` = 70% of `total_weight`.
2. Signer S (weight W ≥ enough to matter) sends `BlockResponse::Rejected(B)`. In `stackerdb_listener.rs`, `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += W`. [2](#0-1) 
3. S subsequently re-evaluates (protocol-sanctioned reconsideration, e.g. after the node revalidates the block or a transient error clears) and sends `BlockResponse::Accepted(B)` for the same `signer_signature_hash`. `gathered_signatures` does not contain S's slot yet, so the guard passes → `total_weight_approved += W`. [1](#0-0) 
4. `total_weight_rejected` still includes S's now-stale W. If enough other signers' genuine (non-stale) rejections plus S's stale W push `total_weight_rejected.saturating_add(weight_threshold) > total_weight`, the coordinator returns `NakamotoNodeError::SignersRejected` [8](#0-7)  even though the real, current signer positions (including S's acceptance) would have permitted the block to cross the 70% acceptance threshold instead.

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
