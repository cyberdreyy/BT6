### Title
Cross-user response hijacking via unscoped `MessageId` key in gateway `WebAPIHandler` - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` in the gateway's `WebAPIHandler` stores the per-request response callback in `h.savedCallbacks` keyed **only** by the client-supplied `msg.Body.MessageId`, with no binding to the requester's identity. Because `MessageId` is fully attacker-controlled and the map key is not scoped per-sender (unlike the `RequestCache` used elsewhere in the same package), an unprivileged client can cause its own callback to overwrite another user's pending callback for the same `MessageId`, hijacking the trigger response meant for the original caller.

### Finding Description
The gateway exposes `ProcessRequest` → `HandleLegacyUserMessage` to any external, unauthenticated client hitting the gateway's HTTP endpoint [1](#0-0) . `msg.Body.MessageId` originates directly from the client-supplied JSON-RPC request `ID` and is not required to be unique or bound to a signer identity beyond appearing in the signed payload of the *sender's own* message [2](#0-1) [3](#0-2) .

In `WebAPIHandler.HandleLegacyUserMessage`, the callback for a pending request is stored keyed solely by this attacker-controlled `MessageId`: [4](#0-3) 

When a DON node later responds, `HandleNodeMessage` validates only that the *node* is who it claims to be (`msg.Body.Sender != nodeAddr`), then dispatches to `handleWebAPITriggerMessage`, which looks up and deletes the saved callback purely by `MessageId`: [5](#0-4) [6](#0-5) 

If two different unprivileged users submit requests with the same `MessageId` while the first is still in-flight, the map entry is silently overwritten (last writer wins) with no error, no per-sender scoping, and no rejection of the collision. The subsequent node response for that `MessageId` is then delivered to whichever caller last wrote the entry — not necessarily the original requester. This is structurally identical to the reported bug class: a "resource" (here, the response channel/callback) is not bound to the correct calling context, so an unprivileged party can redirect it to themselves.

Notably, this pattern is already fixed correctly elsewhere in the very same package: `RequestCache` scopes cache entries by a composite `globalId{sender, id}` key instead of a bare ID [7](#0-6) , but the `capabilities/handler.go` `savedCallbacks` map does not use this safer construction. A test comment in the handler's test file even flags this gap explicitly: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` [8](#0-7) .

### Impact Explanation
An unprivileged external client can:
1. Cause a legitimate user's response (potentially containing sensitive trigger/workflow execution data) to be delivered to the attacker instead — cross-user response confusion / disclosure.
2. Cause the legitimate user's request to silently time out / never receive a response — denial of service for that specific request.

This matches the "cross-user response confusion" category explicitly accepted by the validation criteria, and is reachable purely from an unprivileged HTTP client hitting the internet-facing gateway, without any node or peer compromise.

### Likelihood Explanation
Exploitability depends on the attacker being able to submit a request with the same `MessageId` as a victim's in-flight request within the callback's live window (bounded by `CallbackMaxAgeSec`, default 120s, and pruning). If client SDKs generate `MessageId`s predictably (e.g., sequential counters, timestamps, or short/low-entropy identifiers), or if the attacker can simply race many requests with self-chosen IDs against a known workflow endpoint that legitimate users also call, collision is practically achievable. The `Validate()` function only bounds `MessageId` length (≤128 bytes) and disallows trailing null bytes — no entropy or format requirement is enforced [3](#0-2) , making crafted collisions straightforward for an attacker who controls their own `MessageId` value.

### Recommendation
Scope `savedCallbacks` (and its lookup on node response) by a composite key that includes the requester's identity/context, not just the raw `MessageId` — mirroring the `globalId{sender, id}` pattern already used in `RequestCache` [7](#0-6) . Concretely:
- Change `h.savedCallbacks` to be keyed by `(msg.Body.Sender, msg.Body.MessageId)` (or an internally generated, gateway-side unique correlation ID) instead of `msg.Body.MessageId` alone.
- On node response lookup in `handleWebAPITriggerMessage`, reject/ignore responses whose `MessageId` maps to a callback whose original sender does not correspond to the same logical request context, preventing silent overwrite across different callers.
- Consider migrating this handler to use the existing `RequestCache` abstraction rather than a bespoke unscoped map.

### Proof of Concept
1. Attacker sends `web_api_trigger` request to the gateway with `MessageId = "victim-id"` (this can be any client-chosen JSON-RPC `ID` up to 128 bytes) — `HandleLegacyUserMessage` stores attacker's callback under key `"victim-id"`.
2. Concurrently (or shortly before), a legitimate user's client happened to submit a request also carrying `MessageId = "victim-id"` (predictable/guessed or coincidental due to low-entropy ID generation) — its callback is stored, then immediately overwritten by the attacker's in step 1 (or vice versa, depending on race order) because both writes hit `h.savedCallbacks["victim-id"]` [4](#0-3) .
3. A DON node processes the (legitimate) request and sends its response back through the gateway using `MessageId = "victim-id"`.
4. `HandleNodeMessage` → `handleWebAPITriggerMessage` looks up `savedCallbacks["victim-id"]`, finds whichever callback is currently stored (potentially the attacker's), and delivers the response payload to that caller [6](#0-5) .
5. The attacker receives a response intended for the victim; the victim either receives the attacker's unrelated response or times out.

Note: I was unable to fully verify how gateway client SDKs generate default `MessageId`/request `ID` values in production (e.g., whether they use high-entropy UUIDs) since that logic likely lives in external/consumer code not indexed here; this affects the practical likelihood assessment but not the root-cause validity of the missing sender-scoping in the callback map.
