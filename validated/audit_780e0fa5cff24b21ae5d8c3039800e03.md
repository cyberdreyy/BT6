### Title
`setRoleAdmin` accepts any `newAdminRole` value with no validation, permanently freezing role management - ([File: crates/common/precompiles/src/b20_asset/logic/v1.rs])

### Summary
The B20 asset and stablecoin precompile logic exposes `set_role_admin`, which lets a role's current admin reassign that role's admin to an arbitrary `B256` value with no validation that the new admin role is non-zero, distinct, or actually held by any account. This mirrors the reported `L2ECO.updateTokenRoleAdmin` issue: a single privileged call with an unchecked new-admin value can permanently and irrecoverably remove the ability to manage a critical role (e.g. `Mint`, `Burn`, `Rebase`).

### Finding Description
`set_role_admin` in the B20 asset/stablecoin logic modules only checks that the *caller* holds the current admin role for `role`; it performs no validation on `new_admin_role` itself before writing it to storage: [1](#0-0) 

The same unchecked pattern is duplicated in the v2 logic and in the stablecoin variant: [2](#0-1) [3](#0-2) [4](#0-3) 

Once `role_admin(role)` is overwritten with a role id that nobody holds (including `B256::ZERO`, an unused custom role hash, or simply a typo'd/mis-encoded role id), the only enforcement gate for future `grant_role`/`revoke_role` calls on that role is `B20Guards::ensure_role(token, caller, admin)` — which checks membership in the *new* admin role: [5](#0-4) [6](#0-5) 

If no account holds the new admin role, `ensure_role(...)` will always revert with `AccessControlUnauthorizedAccount`, so nobody — not even the token's `DefaultAdmin` — can call `grantRole`/`revokeRole` for that role again through the unprivileged path (`privileged=false`). The token's factory-privileged escape hatch is limited: only `DefaultAdmin` grants are always factory-callable (`role == DefaultAdmin.id() || !privileged` triggers `ensure_role_admin_mutations_available`), but non-`DefaultAdmin` roles whose admin is corrupted lose the standard, non-factory administrative recovery path entirely; recovery would depend on out-of-band factory-privileged intervention, if any exists, rather than any on-contract self-service mechanism.

### Impact Explanation
Any account holding the current admin role for a functional role (e.g., `Mint`, `Burn`, `Rebase`, `Metadata`) can call `setRoleAdmin` with a bogus `newAdminRole` (zero, an unrelated role id, or a role nobody has been granted) in a single transaction. This permanently locks out the standard `grantRole`/`revokeRole` administration path for that role, since no account can satisfy `ensure_role(token, caller, admin)` against an unpopulated admin role. For roles gating supply-affecting operations (mint/burn/rebase), this results in permanent freezing of the ability to onboard or remove minters/burners/rebasers — directly analogous to the original `L2ECO.updateTokenRoleAdmin` impact of "cannot add or remove minters, burners and rebasers."

### Likelihood Explanation
This requires a signed transaction from an account that already holds the current admin role for the target role — an accidental or malicious call by a legitimately privileged operator, exactly as described in the reference report (human error with an irrecoverable, unvalidated critical-role update). No additional privilege escalation or external condition is needed beyond the existing admin-role holder issuing one call.

### Recommendation
Add validation in `set_role_admin` (across the asset and stablecoin, v1 and v2, logic modules) to reject degenerate `new_admin_role` values — e.g., disallow `B256::ZERO` unless intentionally supported, and/or require that at least one account currently holds `new_admin_role` before the assignment is committed, similar to the recommendation in the source report (non-zero validation or a two-step admin transfer with an explicit acceptance step).

### Proof of Concept
1. Token deployed; `ADMIN` holds `DefaultAdmin` and is admin of `Mint` role (default `role_admin(Mint) == DefaultAdmin`).
2. `ADMIN` calls `setRoleAdmin(Mint.id(), <unused_role_id>)` via the precompile (unprivileged path), which succeeds because `ADMIN` holds `DefaultAdmin` (the previous admin role for `Mint`): [7](#0-6) 
3. Any subsequent unprivileged `grantRole(Mint.id(), X)` or `revokeRole(Mint.id(), X)` call now requires the caller to hold `<unused_role_id>`, which no account holds — every such call reverts with `AccessControlUnauthorizedAccount`, permanently freezing `Mint` role administration through the standard path.

    fn set_role_admin(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        role: B256,
        new_admin_role: B256,
        privileged: bool,
    ) -> Result<()> {
        let previous_admin_role = token.accounting().role_admin(role)?;
        if !privileged {
            self.ensure_role_admin_mutations_available(token, caller)?;
            B20Guards::ensure_role(token, caller, previous_admin_role)?;

        token.accounting_mut().set_role_admin(role, new_admin_role)?;

        )
    }

    /// Ensures `caller` has `role`.
    pub fn ensure_role<T: Token + ?Sized>(token: &T, caller: Address, role: B256) -> Result<()> {
        if token.accounting().has_role(role, caller)? {
            Ok(())
        } else {
            Err(BasePrecompileError::revert(IB20::AccessControlUnauthorizedAccount {
                account: caller,
                neededRole: role,
            }))
        }
    }
