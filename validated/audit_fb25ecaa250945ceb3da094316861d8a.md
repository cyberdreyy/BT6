### Title
Stale Confirmations From Removed Multisig Members Allow Requests To Execute Below The Live-Member Threshold - (File: multisig2/src/lib.rs)

### Summary
The `MultiSigContract::confirm` function in `multisig2/src/lib.rs` counts confirmations stored in the `confirmations: LookupMap<RequestId, HashSet<String>>` map without verifying that each confirming identity is still a current member of `self.members`. Because `delete_member` only purges requests *created by* the removed member and never scans other pending requests' confirmation sets, a confirmation cast by a member who is later removed remains counted toward the `num_confirmations` threshold. This breaks the intended custody binding that a request may only execute once `num_confirmations` *live* members have approved it.

### Finding Description
`confirm()` computes eligibility to execute purely from the stored confirmation count: [1](#0-0) 

It never re-validates that the accounts/keys already present in `confirmations` are still members. Meanwhile `delete_member` only cleans up requests where the removed member was the *originating signer*, not confirmations that member left on other pending requests: [2](#0-1) 

So the intended invariant `|confirmations(request) ∩ current_members| ≥ num_confirmations` is replaced in practice by the weaker, incorrect check `|confirmations(request)| ≥ num_confirmations`, which can include identities no longer in `self.members`.

### Impact Explanation
This matches the "Critical" impact class: a multisig request (including a `Transfer` action moving NEAR out of the contract) can be executed with fewer than `num_confirmations` *live* member approvals, i.e. a request executed below threshold. The stale confirmation effectively lets a removed/compromised member's earlier approval continue to count toward moving funds or performing privileged actions (`AddKey`, `DeployContract`, `AddMember`/`DeleteMember`) after they've lost membership.

### Likelihood Explanation
This requires only ordinary multisig usage flow, not any special privilege beyond being (or having been) a member: a member creates or confirms a sensitive request, is later removed from the multisig through the normal `DeleteMember` governance flow, and the still-pending request later gets confirmed by other members to reach the nominal threshold. No code hash checks, redeploys, or foundation-only actions are needed — it's a direct consequence of missing confirmation invalidation on membership change, which is a realistic and even expected scenario (member removal typically happens exactly because trust in that member was lost, e.g. key compromise, yet their prior confirmation still counts).

### Recommendation
When a member is removed via `delete_member`, iterate over all pending requests' confirmation sets and remove the departing member's identity (or normalize confirmations by removing entries for members no longer in `self.members`), or check membership of each confirming identity in `confirm()`/`execute_request()` before counting them toward `num_confirmations`. Equivalent purging should be applied in the corresponding `multisig/src/lib.rs` (v1) implementation and `assert_valid_request`.

### Proof of Concept
1. Deploy `MultiSigContract::new` with members `[A, B, C]` and `num_confirmations = 3`.
2. Member `A` calls `add_request` with a `Transfer { amount }` request to an attacker-controlled account, then `confirm` (adds `A` to `confirmations`). [3](#0-2) 
3. Member `B` calls `confirm(request_id)`, adding `B` to `confirmations` (count = 2, still below threshold 3).
4. Members governance flow removes `B` from the multisig via a separate `DeleteMember { member: B }` request that reaches its own threshold and executes, calling `delete_member`. This only removes requests *created by* `B`; the pending Transfer request created by `A` (with `B`'s confirmation already recorded) is untouched. [4](#0-3) 
5. Member `C` calls `confirm(request_id)`. `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates `2 + 1 >= 3` → true, and `execute_request` transfers the funds — even though only `A` and `C` are currently live members approving (2 live approvals), while `B`'s stale confirmation counted toward the nominal 3-of-3 threshold. [5](#0-4)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
