### Title
External-initiator credentials bypass the "EI not allowed" check in `PipelineRunsController.Create` and can trigger arbitrary job runs by integer job ID - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` unconditionally stashes a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` under `SessionUserKey` for any valid EI credential. `PipelineRunsController.Create` tries to block EIs from using the integer-job-ID path with `_, isUser := auth.GetAuthenticatedUser(c)`, but `GetAuthenticatedUser` reads that same `SessionUserKey`, so it returns `true` for external initiators too. As a result, a holder of only EI credentials can hit `POST /v2/jobs/:ID/runs` with any integer job ID and trigger `RunJobV2` for a job it was never provisioned against.

The comment ("only users are allowed to run jobs using int IDs - EIs not allowed") documents the intended authorization boundary, but the implementation checks `isUser` via `GetAuthenticatedUser`, which — per the code above — is also true for EI-authenticated requests. There is no code path that distinguishes a real dashboard/API-token user from an EI once `SessionUserKey` is set, and no verification that the job ID being requested corresponds to a job the specific EI (`SessionExternalInitiatorKey`) was registered against (e.g., via an `ExternalInitiatorWebhookSpec` binding). Consequently, `prc.App.RunJobV2(ctx, jobID, nil)` is invoked for arbitrary integer job IDs supplied by the EI, regardless of the EI's actual provisioning scope.

### Impact Explanation
An external-initiator credential — a narrowly-scoped, low-privilege credential intended only to trigger the specific webhook job(s) it was registered for — can instead trigger pipeline runs for **any** job on the node addressable by an integer ID (non-webhook jobs included, since the webhook/UUID path is separately blocked with `job.ErrJobTypeRemoved`). This is an authorization/role-binding bypass leading to unauthorized job execution, which can cause unintended on-chain transactions, fund movement (e.g. keeper/OCR-triggerable specs), or resource exhaustion — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Exploitation requires only a single valid, low-privilege EI credential pair (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret`) issued by the node operator for some unrelated purpose. No admin/session/API-key access is needed. The request is a single unauthenticated-by-scope `POST /v2/jobs/:ID/runs` with an arbitrary integer `:ID`. This is fully repeatable and deterministic given the flawed `isUser` check.

### Recommendation
In `PipelineRunsController.Create`, distinguish real users from external initiators explicitly, e.g. reject the request if `auth.GetAuthenticatedExternalInitiator(c)` returns an EI object, rather than relying on `GetAuthenticatedUser` returning a synthetic user. Additionally, avoid using a shared `SessionUserKey` to represent EI identity — EIs should carry their own distinct session marker so role-based checks (`RequiresRunRole`, `GetAuthenticatedUser`) cannot be satisfied by EI-only credentials unless explicitly intended, and per-job EI authorization should be validated against the EI's registered webhook binding before invoking `RunJobV2`.

### Proof of Concept
Handler-level integration test (`core/web/pipeline_runs_controller_test.go` style):
1. Set up a test app with a real user-created job (`jobA`, non-webhook, integer ID) and a separately registered `ExternalInitiator` `EI1` that has no association with `jobA`.
2. Build request: `POST /v2/jobs/{jobA.ID}/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to `EI1`'s valid credentials only (no session cookie, no API token).
3. Assert:
   - Response status is `200`/`201` and a `pipelineRun` resource is returned (i.e., `prc.App.RunJobV2` was invoked) — proving the "EIs not allowed" comment is not enforced.
   - Additionally assert via `auth.GetAuthenticatedUser(c).Role == clsessions.UserRoleRun` and `isUser == true` inside a unit test of `AuthenticateExternalInitiator` + `GetAuthenticatedUser`, confirming the root cause that EI sessions are indistinguishable from user sessions at the `isUser` check.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
