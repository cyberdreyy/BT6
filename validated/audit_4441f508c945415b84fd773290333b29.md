### Title
Post-close withdraw requests are recorded as funded receipts and paid at par from other claimants' reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is an HTTP desync: the same byte stream is interpreted under two different parsing regimes, letting an attacker smuggle a second request through a path that treats it as already-validated. The credit-vault analog is a **funding-regime desync** in `IdleCreditVault.requestWithdraw`: a withdraw request created after the pool is closed (`epochEndDate == 0`) is written into the *funded* receipt ledgers (`withdrawsRequests`, `withdrawsRequestsByEpoch`) and backed by freshly minted strategy-token receipts, but is deliberately excluded from `pendingWithdraws` because no `stopEpoch` will ever fund it. `claimWithdrawRequest` then evaluates the same request under the funded-claim regime and pays it at par, spending underlyings that belong to legitimately funded receipts of other users.

### Finding Description
In `requestWithdraw` (IdleCreditVault.sol:243-295), the strategy reads `isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0`. For a closed pool it still:

- burns `_principal` strategy tokens from the CDO and mints `_amount` receipt tokens to the user (lines 273-275),
- records the request in `withdrawsRequests[_user] += _amount` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 292-293),

but skips `pendingWithdraws += _amount` because `isClosed` is true (lines 277-280). The comment states the intent: a closed pool already recalled all funds and has no later `stopEpoch`, so this receipt is *never* funded by the borrower.

The claim path then interprets that same receipt as funded. `_claimFundedWithdrawRequest` (lines 319-350) gates on `epochNumber <= lastWithdrawRequest[_user]` **only when `epochEndDate() != 0`**. Once the pool is closed this maturity check is skipped entirely, so `normalAmount = withdrawsRequests[_user]` — which includes the never-funded post-close request — is paid at par via `_transferFundedClaim`. `claimWithdrawRequest` (lines 301-314) simply routes to this path when `defaultRecoveryFinalized` is false.

The vault's underlying balance at that point consists of funds pulled in by `collectWithdrawFunds` during the final `stopEpoch`, earmarked for genuinely funded receipts (test `testHealthyCloseProcessesQueuedWithdrawalAsNormalClaim` confirms normal claims are paid from this balance after close). `_transferFundedClaim` (lines 897-907) only protects `defaultRecoveryReserve`, which is zero in a healthy close — so the unfunded receipt spends other users' funded money.

Pre-conditions for the attack: the CDO's `requestWithdraw` entry point remains callable while the pool is closed (gated by `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and `isWalletAllowed`, not by `epochEndDate != 0` on the strategy side — the strategy explicitly branches on `isClosed` rather than reverting), and the attacker holds or acquires tranche tokens / receipt basis to pass `_amount`/`_principal` through the CDO burn.

### Impact Explanation
Direct theft. Each unit of post-close request mints a receipt that is paid 1:1 in underlying from the strategy's claim reserve, while adding zero corresponding funding. The attacker can drain up to the full unclaimed funded balance (the sum of all not-yet-claimed `withdrawsRequests` payouts), leaving legitimate claimants' transactions reverting on insufficient balance — permanent loss for them, quantified as `underlyingToken.balanceOf(strategy)` at the time of the exploit. This breaks the "one receipt, one payout" and solvency invariants: total receipt basis exceeds funded underlying.

### Likelihood Explanation
Likelihood is moderate-to-high in a closed-pool terminal state: it requires no privileged action and no timing race — the pool close is a normal, publicly visible terminal event (`stopEpoch(0, 1)`), and the window stays open as long as any funded claim remains uncollected. It does require the CDO variant to keep the withdraw-request flags enabled after close and the attacker to hold tranche tokens (acquirable on the market or pre-positioned before close). Note: the CDO-side gating for closed pools was not fully verified — if `IdleCDOEpochVariant.requestWithdraw` independently reverts when `epochEndDate == 0`, the strategy-side `isClosed` branch is dead code and the attack is unreachable; the explicit `isClosed` handling and the test suite exercising post-close claims suggest the path is intended to be reachable.

### Recommendation
Treat closed-pool requests as a distinct class instead of silently reclassifying them as funded receipts:

- In `requestWithdraw`, either revert when `IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0`, or record such requests in a dedicated unfunded/post-close mapping (e.g., reuse the `postDefaultRequests` pattern) so they can never be paid by `_claimFundedWithdrawRequest`.
- In `_claimFundedWithdrawRequest`, bound `normalAmount` to per-epoch receipts that were actually funded (e.g., only epochs `<= epochNumber` with no recorded loss haircut), rather than the raw `withdrawsRequests` aggregate.
- Alternatively, enforce the closed-pool check at the CDO entry point so the strategy's `isClosed` branch is provably unreachable.

### Proof of Concept
Conceptual Foundry fork trace (mirroring `test/foundry/IdleCDOEpochQueue.t.sol:902` and `IdleCreditVault.t.sol` claim tests):

```solidity
// Setup: healthy epoch vault, users A (funded claimant) and attacker E hold AA tranches.
idleCDO.depositAA(...);            // A and E deposit
cdoEpoch.startEpoch();             // manager

// A requests withdraw during epoch N.
vm.prank(A); cdoEpoch.requestWithdraw(aTranches, AA);
// E keeps tranches idle (or buys them just before close).

// Manager closes pool with _interest = 1 (repay all, epochEndDate -> 0).
// Borrower funds pendingWithdraws incl. A's receipt; collectWithdrawFunds pulls
// the underlying into the strategy.
cdoEpoch.stopEpoch(0, 1);
assertEq(cdoEpoch.epochEndDate(), 0);

// A does not claim yet; strategy holds funded underlying for A's receipt.
uint256 reserve = underlying.balanceOf(address(strategy));

// Desync: E requests AFTER close. Strategy mints receipt tokens and records
// withdrawsRequests[E] += amt but does NOT increase pendingWithdraws.
vm.prank(E); cdoEpoch.requestWithdraw(eTranches, AA);

// Claim path: epochEndDate()==0 skips the epochNumber > lastWithdrawRequest gate.
// E is paid at par from A's funded reserve.
uint256 balPre = underlying.balanceOf(E);
vm.prank(E); cdoEpoch.claimWithdrawRequest();
assertEq(underlying.balanceOf(E) - balPre, eRequestAmount); // stolen funds

// A's funded claim now underflows / reverts on insufficient strategy balance.
vm.prank(A);
vm.expectRevert();                 // safeTransfer fails: balance drained
cdoEpoch.claimWithdrawRequest();
```

Key lines: funding skip at `IdleCreditVault.sol:259` and `:277-280`, receipt recording at `:292-293`, skipped maturity gate at `:326`, par payout at `:338-349`, and the reserve guard that only covers `defaultRecoveryReserve` at `:899-905`.
