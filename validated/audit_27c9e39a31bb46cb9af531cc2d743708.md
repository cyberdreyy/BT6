### Title
Unauthenticated workflow existence oracle via distinguishable error messages before authentication - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`HandleUserTriggerRequest` calls `resolveWorkflowID` before `authorizeRequest`, so any unauthenticated caller of the gateway's HTTP trigger endpoint can distinguish "workflow does not exist" from "workflow exists but auth failed" purely from the returned JSON-RPC error message, without ever presenting valid credentials. This lets an attacker enumerate valid `(workflowOwner, workflowName, workflowTag)` triples or `workflowID` values against a private node.

### Finding Description
`HandleUserTriggerRequest` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:88-102`) executes in this order:
1. `h.validatedTriggerRequest` — only format validation, no auth.
2. `h.resolveWorkflowID` — looks up the workflow by ID or by `(owner, name-hash, tag)` in `h.workflowMetadataHandler`. If not found, it calls `handleUserError` with message `"Workflow not found..."` [1](#0-0) .
3. `h.authorizeRequest` — only reached if step 2 succeeds. It validates `req.Auth` (a JWT/signature) via `h.workflowMetadataHandler.Authorize`, and on failure returns `"Auth failure: "+err.Error()"` [2](#0-1) .

Because step 2 runs strictly before step 3, an attacker who sends a request with garbage/empty `req.Auth` will get:
- `"Workflow not found..."` if the guessed `(owner, name, tag)`/`workflowID` does not exist, or
- `"Auth failure: ..."` if it does exist (since resolution succeeded and only then does auth fail).

The gateway entry point `gateway.ProcessRequest` performs no authentication itself before dispatching to `HandleJSONRPCUserMessage` → `HandleUserTriggerRequest` [3](#0-2) , so this endpoint is reachable by any network client with zero credentials — auth is entirely handled inside the per-workflow JWT check in `authorizeRequest`.

This is already visible in the existing regression test, which explicitly branches on the two distinct messages ("Auth failure" vs "workflow not found") to detect whether a workflow has loaded yet [4](#0-3) , confirming the messages are reliably distinguishable over the network.

### Impact Explanation
An unauthenticated attacker can confirm the existence of a specific workflow (by ID, or by owner+name+tag triple) on a target Chainlink node/gateway without needing any valid signing key. This breaks the "information confinement" invariant: existence of a private workflow's identity (owner address, workflow name, tag) should not be confirmable pre-authentication. This does not directly enable job execution, fund movement, or credential theft — the impact is limited to enumeration/reconnaissance of a customer's private workflow inventory, which is a legitimate information-disclosure concern but does not itself grant privilege escalation or unauthorized action.

### Likelihood Explanation
Trivial and fully repeatable: no preconditions beyond network access to the gateway's HTTP endpoint. An attacker can brute-force/guess `workflowOwner` (often a known EVM address), `workflowName`, and `workflowTag`, sending each combination with an empty/garbage `Auth` field and reading the JSON-RPC error message to determine existence. No rate limiting protects this path since `checkRateLimit` runs after `authorizeRequest`, i.e., after resolution succeeds.

### Recommendation
Return a uniform error message/code for both "workflow not found" and "auth failure" cases (e.g., a generic "Unauthorized" response) so that pre-auth requests cannot distinguish resource existence from credential failure. Alternatively, reorder or fold `resolveWorkflowID` and `authorizeRequest` checks so failure responses are indistinguishable regardless of which check failed, and apply consistent timing/backoff to avoid timing side channels as well.

### Proof of Concept
Go table test in `http_trigger_handler_test.go`:
1. Register one workflow (`workflowID`, `workflowOwner="0xaaaa..."`, `workflowName="secret-workflow"`, `workflowTag="v1"`) via `registerWorkflow`.
2. Case A ("known-existing"): build a trigger request selecting the registered `(workflowOwner, workflowName, workflowTag)`, set `req.Auth = "garbage-token"`, call `handler.HandleUserTriggerRequest`, capture the callback response, assert the error message contains `"Auth failure"`.
3. Case B ("known-nonexistent"): same request but with a different, unregistered `(workflowOwner, workflowName, workflowTag)`, same garbage `req.Auth`, call `HandleUserTriggerRequest`, assert error message contains `"Workflow not found"`.
4. Assert the two response messages differ, demonstrating the existence oracle: `require.NotEqual(t, respA.Error.Message, respB.Error.Message)` while both used equally invalid credentials — proving an attacker can distinguish workflow existence without ever supplying valid auth.

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
