### Title
Signer weight double-counted in both approval and rejection tallies after a vote flip — corrupts the coordinator's aggregated-weight quorum accounting - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
In the mining-node's `StackerDBListener` block-response handler, a signer's weight is credited to `total_weight_approved` if the signer's slot is not yet present in `gathered_signatures`, but the check does not consult `responded_signers` (which is also updated by the `Rejected` branch). Consequently, a signer that first rejects a block and later legitimately flips to accept it has its weight counted in **both** `total_weight_rejected` and `total_weight_approved` for the same block, with no corresponding subtraction. This breaks the intended equality that each signer's weight should be attributed to only one side of the aggregated tally.

### Finding Description
`handle_block_response` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` maintains a `BlockStatus` per proposal with `total_weight_approved`, `total_weight_rejected`, `gathered_signatures`, and `responded_signers`.

- On `Rejected`, weight is added to `total_weight_rejected` guarded by `block.responded_signers.insert(slot_id)` [1](#0-0) , and `responded_signers` now contains that slot.
- On `Accepted`, weight is added to `total_weight_approved` guarded only by `!block.gathered_signatures.contains_key(&slot_id)` — a completely different set [2](#0-1) . Since a prior `Rejected` message never populates `gathered_signatures`, a later `Accepted` from the same signer passes this guard and adds the signer's weight to `total_weight_approved` as well, while `total_weight_rejected` is never decremented.
- `reset_rejections` only clears `total_weight_rejected` on a proposal timeout, not when a signer changes its vote [3](#0-2) , so the stale rejected weight persists indefinitely for that block.

A vote flip from reject to accept is not a fringe or adversarial-only path: the signer's own state machine explicitly supports re-evaluating and reversing a rejection when the reject reason is re-evaluable (e.g. connectivity/timeout-based rejections), and re-sends a fresh `BlockResponse` after that re-evaluation [4](#0-3) . Any single signer (no majority required) can therefore cause its own weight to be simultaneously present in the coordinator's rejected and approved totals for one block.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality the coordinator relies on to decide block fate: `get_block_status`'s loop uses `total_weight_rejected` to detect a blocking-minority rejection (`> total_weight - weight_threshold` triggers `SignersRejected`) and `total_weight_approved` to detect quorum (`>= weight_threshold` triggers acceptance) [5](#0-4) . With one signer's weight counted on both sides, the sum `total_weight_approved + total_weight_rejected` can exceed `total_weight`, meaning the rejection tally is artificially inflated by weight that has actually moved to acceptance. This can cause the coordinator to falsely conclude a blocking rejection minority exists (rejecting/excluding transactions or aborting a block that in fact has legitimate quorum), i.e., a rejection is effectively still "recounted" toward blocking a block the signer no longer opposes — a miscounted response as called out in-scope.

### Likelihood Explanation
Triggerable by a single signer through ordinary, legitimate protocol behavior (reject due to a re-evaluable reason, then accept on re-proposal/re-evaluation) — no majority collusion, no auth token, no StackerDB-transport exploit required. Any signer with even a small weight share can reproduce this every time its vote legitimately flips.

### Recommendation
In the `Accepted` branch, guard weight crediting (and any residual `total_weight_rejected` contribution) using the same `responded_signers` set used by `Rejected`, and when a signer's response changes from rejected to accepted, subtract its weight from `total_weight_rejected` before adding it to `total_weight_approved` (or otherwise make the two tallies mutually exclusive per signer slot).

### Proof of Concept
1. Coordinator inserts a `BlockStatus` for a proposal via `insert_block` (`total_weight_approved = 0`, `total_weight_rejected = 0`) [6](#0-5) .
2. Signer S (weight W) sends `BlockResponse::Rejected` for the block due to a re-evaluable reason (e.g. `ConnectivityIssues`). `responded_signers.insert(S)` succeeds, `total_weight_rejected += W`.
3. Signer S's local state machine later re-evaluates and legitimately reverses to acceptance (per `should_reevaluate_reject_reason`/pre-commit re-evaluation path in `stacks-signer/src/v0/signer.rs`), and it broadcasts `BlockResponse::Accepted` for the same block.
4. Coordinator receives the `Accepted` message; `gathered_signatures` does not yet contain S's slot, so the `!block.gathered_signatures.contains_key(&slot_id)` guard passes and `total_weight_approved += W`.
5. Now `total_weight_approved + total_weight_rejected` includes W twice for the same signer, even though `total_weight_rejected` was never decremented — corrupting both quorum checks in `get_block_status`.
