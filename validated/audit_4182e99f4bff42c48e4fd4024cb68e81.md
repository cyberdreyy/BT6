### Title
Cross-role disclosure of ExternalInitiator `AccessKey`/`OutgoingToken` via unrestricted `GET /v2/external_initiators` - ([File: core/web/external_initiators_controller.go])

### Summary
`ExternalInitiatorsController.Index` returns every external initiator record in the node (paginated, no per-record filtering) and is exposed through `presenters.ExternalInitiatorResource`, which includes the `AccessKey` and `OutgoingToken` fields for all initiators. Unlike `Create`/`Destroy`, this handler is not gated the same way and any authenticated caller who can reach the endpoint receives credential material belonging to initiators they did not create.

### Finding Description
`ExternalInitiatorsController.Index` (`core/web/external_initiators_controller.go`, lines 50-59) fetches all rows from `eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)` with no filter tying results to the caller's identity, and maps each row through `presenters.NewExternalInitiatorResource` [1](#0-0) .

`ExternalInitiatorResource` includes `AccessKey` and `OutgoingToken` in its JSON output for every initiator returned: [2](#0-1) 

By contrast, the create-time response type `ExternalInitiatorAuthentication` (returned only once, to the creator, from `Create`) additionally carries the plaintext `Secret`/`OutgoingSecret`, which correctly are *not* included in the list-view resource: [3](#0-2) 

So the claim in the proof idea that `HashedSecret`/`Salt`/`OutgoingSecret` leak through `Index` is **not substantiated** — those fields are correctly excluded from `ExternalInitiatorResource`. However, `AccessKey` (the initiator's bearer credential used to authenticate incoming webhook calls) and `OutgoingToken` (half of the outgoing HMAC credential pair used when the node calls back out to the initiator's URL) are returned for every initiator in the node, regardless of who created it.

I was not able to conclusively verify from the indexed content of `core/web/router.go` whether the `GET /v2/external_initiators` route requires `RequiresEditRole`/`RequiresAdminRole` versus only session authentication plus `paginatedRequest` — grep only returned match counts, not the actual route registration line, and I could not fetch the exact snippet in the remaining tool budget. This is a material unknown: if the route is in fact gated behind `RequiresEditRole` (matching the general API's role model where "Run"/view role sessions cannot call most `/v2/*` admin endpoints), then a Run-role session cannot reach `Index` at all, and the described bypass does not exist. Separately, external-initiator credentials themselves (the `AccessKey`/`Secret` pair issued by `Create`) are, in this codebase, only accepted by the webhook-specific authentication middleware for job-run submission — not by the general session/API-token authentication stack that protects `/v2/*` admin routes — so an "external-initiator credential holder" (as opposed to a low-privileged human session/API-token user) does not appear to have a path to call `GET /v2/external_initiators` at all.

### Impact Explanation
If the `Index` route is reachable by any authenticated API-token/session user regardless of role (View/Run vs Edit/Admin), the impact is disclosure of `AccessKey` and `OutgoingToken` for all external initiators configured on the node to a lower-privileged user, who could then impersonate those initiators for incoming webhook calls (using `AccessKey` + the value they'd still need — the incoming secret is not leaked, limiting exploitability) or observe the outgoing token used for calls to third-party URLs. This is a partial credential-material disclosure, not a full "secrets never leave" violation, since `IncomingSecret`/`OutgoingSecret`/any hashed values are correctly redacted from the list response.

### Likelihood Explanation
Likelihood is uncertain and could not be confirmed with the available tooling. It depends entirely on the actual role requirement on the `GET /v2/external_initiators` route registration in `core/web/router.go`, which I could not verify precisely, and on whether the general auth stack accepts external-initiator credentials at all (it appears not to, based on the separation between `Create`'s webhook-specific auth token issuance and the admin API's session/role-based auth).

### Recommendation
Regardless of the above uncertainty, as defense in depth: (1) confirm/enforce that `GET /v2/external_initiators` requires the same minimum role as `Create`/`Destroy` (edit/admin), consistent with treating `AccessKey`/`OutgoingToken` as sensitive; (2) consider omitting `AccessKey`/`OutgoingToken` from the list resource entirely (only show a non-sensitive identifier such as name/URL/created/updated timestamps), since list views rarely need live credential material.

### Proof of Concept
Not confirmed as exploitable given the information available; a definitive PoC requires reading the exact route-registration lines in `core/web/router.go` to determine whether `Index` is behind `RequiresEditRole` and whether external-initiator credentials are accepted by the general auth middleware. Suggested verification steps for a follow-up session with full repo access:
1. Read `core/web/router.go` around the `external_initiators` route group to confirm the middleware/role chain on `GET`, `POST`, `DELETE`.
2. Read `core/web/auth/auth.go` to confirm which middleware (`AuthenticateByToken`, `RequiresEditRole`, external-initiator auth) applies to `/v2/external_initiators`.
3. Write a Go handler-level integration test creating two initiators, authenticating with a Run/View-role session or API token, calling `GET /v2/external_initiators`, and asserting whether the request is rejected (403) or returns `AccessKey`/`OutgoingToken` for initiators not owned by the caller.

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
type ExternalInitiatorResource struct {
	JAID
	Name          string         `json:"name"`
	URL           *models.WebURL `json:"url"`
	AccessKey     string         `json:"accessKey"`
	OutgoingToken string         `json:"outgoingToken"`
	CreatedAt     time.Time      `json:"createdAt"`
	UpdatedAt     time.Time      `json:"updatedAt"`
}

func NewExternalInitiatorResource(ei bridges.ExternalInitiator) ExternalInitiatorResource {
	return ExternalInitiatorResource{
		JAID:          NewJAID(strconv.FormatInt(ei.ID, 10)),
		Name:          ei.Name,
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,
		OutgoingToken: ei.OutgoingToken,
		CreatedAt:     ei.CreatedAt,
		UpdatedAt:     ei.UpdatedAt,
	}
}
```
