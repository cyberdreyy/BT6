### Title
Unprivileged account-squatting via `LockupFactory::create` custom `whitelist_account_id` overrides Foundation whitelist for a victim's deterministic lockup address - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the lockup account deterministically from `owner_account_id` alone (`sha256(owner_account_id)` prefix), and lets the caller freely pass `whitelist_account_id` with no ownership or Foundation check. An unprivileged attacker can call `create(owner_account_id='victim.near', whitelist_account_id=Some('attacker-owned.near'), ...)` before the legitimate party does, permanently occupying the victim's deterministic lockup address with the attacker's own whitelist contract baked into the deployed `LockupContract`.

### Finding Description
Binding claimed: `staking_pool_whitelist_account_id` stored in the deployed `LockupContract` for `owner_account_id = O` should equal the whitelist that the Foundation (via `LockupFactory::new`'s `self.whitelist_account_id`) or `O`'s rightful creator intended, i.e. `lockup.staking_pool_whitelist_account_id == factory.whitelist_account_id` (default path) or a value that `O`'s legitimate controller chose.

In `lockup-factory/src/lib.rs`, `create` computes the lockup account purely from `owner_account_id`: [1](#0-0) 
There is no `assert_owner`, `assert_called_by_foundation`, or any check that `env::predecessor_account_id()` is related to `owner_account_id` or is the Foundation. The `whitelist_account_id: Option<ValidAccountId>` parameter is taken directly from the caller and, if `Some`, fully overrides `self.whitelist_account_id` for that deployed lockup — exactly what `test_create_lockup_with_custom_whitelist_success` exercises legitimately: [2](#0-1) 

Since NEAR account creation is first-come-first-served and the target account id `hex(sha256(owner_account_id)[..20]).<factory>` is deterministic and depends only on the public string `owner_account_id`, any unprivileged attacker can:
1. Observe/guess that `victim.near` intends to (or one day will) get a lockup from this factory.
2. Call `create(owner_account_id='victim.near', lockup_duration=..., whitelist_account_id=Some('attacker-owned.near'))` themselves, attaching the minimum deposit `MIN_ATTACHED_BALANCE`.
3. The Promise chain creates the account, deploys the lockup code, and calls `new` with `staking_pool_whitelist_account_id = 'attacker-owned.near'` instead of the Foundation's curated whitelist: [3](#0-2) 
4. This is a permanent, one-time-only account name; the real `victim.near` (or the Foundation acting for them) can no longer create the intended lockup at that address, and every future `select_staking_pool` call by `owner_account_id = victim.near` on that squatted contract consults `attacker-owned.near`'s whitelist instead of the Foundation's.

`on_lockup_create`'s only guard is `assert_self()` plus `is_promise_success()`, which validate the callback is from self and that the sub-promise succeeded — neither checks who the caller of `create` was, nor validates the value of `whitelist_account_id`: [4](#0-3) 
No existing guard (`assert_owner`, `assert_called_by_foundation`, `is_valid_account_id`, etc.) restricts who may supply a custom whitelist or which account may be used as `owner_account_id`. `is_valid_account_id` in `lockup/src/lib.rs::new` only checks that the whitelist string is a syntactically valid account, not that it is the Foundation's: [5](#0-4) 

### Impact Explanation
If the attacker later (or contemporaneously) directs `select_staking_pool` calls on the squatted lockup toward an unvetted/malicious "staking pool" registered only in `attacker-owned.near`'s whitelist, funds deposited/staked from that lockup (funded by the deposit the attacker or later the real party sends) can be delegated to a pool the Foundation never vetted, matching **Critical**: "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The squat is a one-time, permanent action per victim account name and is repeatable across any number of distinct victim `owner_account_id` values, so blast radius scales with how many legitimate lockup owners have not yet claimed their deterministic address.

### Likelihood Explanation
The attacker only needs to know (or guess) a target `owner_account_id` string and attach `MIN_ATTACHED_BALANCE` (3.5 NEAR) — no special privilege, key, or foundation role is required, matching the stated unprivileged attacker capabilities. The attack is trivially repeatable for any not-yet-created lockup account, and costs only the deposit amount (which the attacker front-loads into the squatted contract, not lost outright, though effectively locked in a squatted contract they don't own as owner).

### Recommendation
Restrict who may supply a non-default `whitelist_account_id` in `create` — e.g., require `env::predecessor_account_id() == self.foundation_account_id` (or remove caller-supplied override entirely) when overriding the Foundation-curated default. Additionally, consider deriving the lockup account id from both `owner_account_id` and `predecessor_account_id`/a nonce, or require the transaction predecessor to equal `owner_account_id`, to prevent unrelated third parties from squatting a victim's deterministic lockup address at all.

### Proof of Concept
```rust
#[test]
fn test_attacker_overrides_whitelist_for_victim_owner() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker (not victim, not foundation) calls create for victim's owner_account_id
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.testnet");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // stands in for "victim.near"
        lockup_duration,
        None,
        None,
        None,
        Some(custom_whitelist_account_id()), // attacker-controlled whitelist
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    contract.on_lockup_create(
        lockup_account(),
        ntoy(30).into(),
        String::from("attacker.testnet"),
    );

    // Assert: the deployed lockup's whitelist differs from factory's Foundation-curated default,
    // even though "victim.near" (account_tokens_owner()) never authorized the attacker's whitelist.
    // In a full near-sdk-sim / near-workspaces integration test, deserialize the deployed
    // LockupContract state at `lockup_account()` and assert:
    // lockup.staking_pool_whitelist_account_id == custom_whitelist_account_id()
    // != contract.whitelist_account_id (the factory default) == whitelist_account_id()
}
```
This mirrors `test_create_lockup_with_custom_whitelist_success` but with the predecessor set to an unrelated attacker account rather than the owner/foundation, demonstrating that `whitelist_account_id != factory.whitelist_account_id` is accepted with no authorization check.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
