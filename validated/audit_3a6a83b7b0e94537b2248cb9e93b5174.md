### Title
`depositDuringEpoch` credits the nominal `_amount` instead of the actual received balance — ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The crossbeam-channel bug is an accounting assumption: code assumes the allocated capacity equals the number of elements handed in, and later frees based on that wrong size. The direct analog in `IdleCDOEpochVariant` is `depositDuringEpoch`, which assumes the contract received exactly `_amount` underlying and performs three separate balance-sheet mutations on that assumption — minting discounted tranche shares, minting `_amount` strategy tokens, and forwarding `_amount` to the borrower — without measuring the actual balance delta. The normal deposit path (`IdleCDOCreditVault._deposit`) explicitly guards against this by minting on `balanceAfter - balanceBefore`, so the mid-epoch path is inconsistent with the vault's own accounting discipline. With a fee-on-transfer or deflationary underlying (or any underlying whose `transferFrom` delivers less than requested), the vault mints shares, strategy-token claims and borrower debt for value it never received, creating a solvency shortfall borne by other tranche holders.

### Finding Description
In `depositDuringEpoch`, underlyings are pulled with `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` at line 685, and every downstream step uses the nominal `_amount`: the discounted mint `(_amount + trancheInterest) * _trancheTotSupply / expectedFinal` at line 724, `IdleCreditVault(strategy).mintStrategyTokens(_amount)` at line 730, and `_transferUnderlyings(_borrower(), _amount)` at line 732. If the token delivers `_amount - fee`, the contract still forwards the full `_amount` to the borrower, minting strategy tokens and tranche shares for the full `_amount`. Contrast with `IdleCDOCreditVault._deposit` (lines 203–206), which computes `_contractTokenBalance(_token) - _preBal` and mints on the received amount. The crossbeam parallel is exact: the "buffer size" (`_amount`) is assumed rather than measured, and the destructor-style accounting (NAV increases, share mint, borrower transfer) reconstructs state from the wrong size.

### Impact Explanation
If the underlying ever takes a haircut on `transferFrom` (fee-on-transfer, burn-on-transfer, or a rebasing token that rounds down), each `depositDuringEpoch` call inflates `lastNAV*`/`expectedEpochInterest`, mints full-value tranche shares and strategy tokens, and pushes `_amount` underlying to the borrower — funded partly by residual vault balance. The deficit is realized at `stopEpoch`/`claimWithdrawRequest` as an insolvency shortfall socialized across tranche holders (BB first). Even absent an exotic token, the inconsistency means an attacker with a KYC-passed wallet could combine this with a donation timed between the `_skimDonatedAssets` and transfer steps is prevented, so the exposure is specifically the assumed-vs-actual received amount.

### Likelihood Explanation
Conditional rather than certain. `depositDuringEpoch` requires an epoch running, `isDepositDuringEpochDisabled == false`, `isAYSActive == false`, non-programmable borrower, and a KYC-passed caller — all attainable by an unprivileged lender. The residual precondition is an underlying token that does not deliver the full `transferFrom` amount; current production underlyings are plain stablecoins, which makes present-day exploitability low, but the vault code is agnostic to the underlying and the safe deposit path already defends against exactly this class, indicating the invariant is intended to hold.

### Recommendation
Mirror the `_deposit` pattern: measure `uint256 received = _contractTokenBalance(token)` delta around `_transferUnderlyingsFrom`, revert or proceed on `received` instead of `_amount` for the mint calculation, `mintStrategyTokens`, and the borrower transfer. Alternatively, add an explicit `received == _amount` check reverting on shortfall.

### Proof of Concept
Foundry fork/test: deploy the epoch CDO stack with a mock fee-on-transfer underlying (1% transfer fee). Sequence: (1) lender deposits via `depositAA` in buffer; (2) `startEpoch`; (3) warp to mid-epoch, owner sets `isDepositDuringEpochDisabled = false`; (4) KYC'd attacker calls `depositDuringEpoch(1000e6, AATranche)` — contract receives 990 but mints shares/strategy tokens for ~1000 + prorated interest and forwards 1000 to borrower; (5) `stopEpoch` — `getContractValue` shows a deficit equal to the fee, and the last withdrawer's `claimWithdrawRequest`/`withdrawAA` reverts or pays less than `virtualPrice` implies. I was unable to fully verify the exact `_transferUnderlyingsFrom`/borrower-transfer revert behavior line-by-line within the available context, so the PoC should confirm whether the shortfall manifests as an underflow revert or a silent NAV inflation.
