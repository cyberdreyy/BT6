### Title
Reward-cycle-unscoped `block_lookup` in `check_submitted_block_proposal` lets a miner's cross-cycle-labeled proposal corrupt/overwrite a signer's own block record - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`stacks-signer/src/v0/signer.rs` exposes two lookup paths for the same `blocks` table: the scoped `block_lookup_by_reward_cycle` (used by `handle_block_proposal`, `handle_block_rejection`, `handle_block_signature`, `handle_block_validate_ok`, `handle_block_validate_reject`) and the raw, unscoped `SignerDb::block_lookup` (used directly by `check_submitted_block_proposal` and by the associated function in `chainstate/mod.rs`). This is structurally identical to the ShellHub bug class: one code path enforces a scoping check (tenant/reward-cycle) and a sibling path on the same resource skips it.

### Finding Description
`SignerDb::block_lookup` resolves a `BlockInfo` purely by `signer_signature_hash`, with no `reward_cycle` predicate: [1](#0-0) 

Every other consumer of block state in `v0/signer.rs` wraps this with a reward-cycle equality check before trusting the result: [2](#0-1) 

`check_submitted_block_proposal`, however, calls the raw, unscoped `self.signer_db.block_lookup(&proposal_signer_sighash)` and immediately trusts `block_info.has_reached_consensus()` and `block_info.state` to decide whether to skip evaluation or fire a rejection: [3](#0-2) 

The `blocks` table's primary key is the `signer_signature_hash` alone, not `(reward_cycle, signer_signature_hash)`, and `insert_block` performs `INSERT OR REPLACE`: [4](#0-3) 

Crucially, `signer_signature_hash` commits only to block-header/content state — *not* to the `reward_cycle` field carried alongside it in the gossip-level `BlockProposal` message (the schema comment even says so explicitly, arguing the sighash alone is sufficient across "burnchain, PoX, and stacks forks", but says nothing about the wrapper's `reward_cycle` field, which is attacker/miner-supplied and unverified against the block's actual sortition-derived cycle): [5](#0-4) 

`handle_block_proposal` only gates entry by `block_proposal.reward_cycle != self.reward_cycle`, then stores/overwrites the row keyed solely by the block's hash, with `reward_cycle` taken from the (unverified) proposal wrapper: [6](#0-5) [7](#0-6) 

Because two adjacent-reward-cycle `Signer` instances run concurrently in the same signer process during the reward-cycle boundary (confirmed by the parity/overlap handling in `process_event`) and share one on-disk `SignerDb`: [8](#0-7) 

a single miner can broadcast the identical block content twice, tagged with two different `reward_cycle` values in the `BlockProposal` wrapper. The properly-scoped `block_lookup_by_reward_cycle` correctly treats the second submission as "unknown" for the second cycle's signer instance and lets it proceed to a fresh evaluation and `insert_block`, which — because the primary key is the sighash alone — silently overwrites the first cycle's finalized row (`state`, `valid`, `signed_group`/`signed_self`, `reward_cycle`) with the second cycle's values. Any subsequent call into the *unscoped* `check_submitted_block_proposal` (or the unscoped lookup in `chainstate/mod.rs`) for that same hash then reads back state that was never produced under that instance's own reward cycle/weight set, letting stale-cycle acceptance state (`has_reached_consensus()`) be trusted across reward-cycle contexts: [9](#0-8) 

This breaks the "aggregated-weight vs verified-accepts" equality: acceptance/rejection bookkeeping computed under one reward cycle's signer set and weight thresholds can be read and acted upon by the other reward cycle's `Signer` instance for the identical block hash, without either instance ever re-verifying that the state it is trusting was actually produced under its own signer set.

### Impact Explanation
This falls under the High-impact bucket: a signer instance can be wedged into acting on stale/foreign-context block state (`has_reached_consensus`, `state`, `signed_group`) instead of state produced under its own verified reward-cycle signer set, similar in kind to "acting on a stale reward set/threshold." It also enables silent corruption/loss of the locally persisted acceptance record for a block that was already correctly, locally signed and broadcast, undermining the equivocation/idempotency guarantees the `reward_cycle`-scoped lookups were specifically designed to provide.

### Likelihood Explanation
Triggering requires only a single miner-controlled slot (the block-proposer) rebroadcasting the same already-mined block bytes with a different `reward_cycle` field during the narrow reward-cycle boundary/overlap window where two `Signer` instances are concurrently active and sharing one `SignerDb`. No majority collusion, no other signer's key, and no auth token are needed — only crafting the gossip-level wrapper field, which is not bound to the block's cryptographic hash.

### Recommendation
Make `check_submitted_block_proposal` (and the raw lookup in `chainstate/mod.rs`) go through `block_lookup_by_reward_cycle` (or an equivalent explicit `reward_cycle` check) instead of the raw `SignerDb::block_lookup`. Additionally, change the `blocks` table's primary key to `(reward_cycle, signer_signature_hash)` (or otherwise refuse to overwrite a row whose stored `reward_cycle` differs from the incoming proposal's) so that `INSERT OR REPLACE` can never clobber one reward cycle's finalized block record with another cycle's data for a colliding hash.

### Proof of Concept
1. Miner (one slot) proposes block `X` with `BlockProposal{ block: X, reward_cycle: N, .. }` during the tail of cycle `N`. Signer instance `A` (`reward_cycle = N`) validates it, the honest signer set signs it, `state` becomes `GloballyAccepted`, row keyed by `hash(X)` stored with `reward_cycle = N`.
2. During the boundary overlap, the same miner rebroadcasts the identical block bytes `X` as `BlockProposal{ block: X, reward_cycle: N+1, .. }`. Signer instance `B` (`reward_cycle = N+1`), also live in the same process/db, passes its own reward-cycle gate, calls `block_lookup_by_reward_cycle(hash(X))` → returns `None` (correctly scoped), treats it as a fresh proposal, and calls `insert_block`, which `INSERT OR REPLACE`s the row for `hash(X)`, overwriting `A`'s `state=GloballyAccepted`/`signed_group` with `B`'s fresh `Unprocessed` state and `reward_cycle = N+1`.
3. `A`'s next `process_event` call invokes `check_submitted_block_proposal`, which does `self.signer_db.block_lookup(&hash(X))` (unscoped) and now reads `B`'s row instead of its own — trusting foreign-reward-cycle bookkeeping for a hash it believes belongs to its own reward cycle.

    /// Check the current tracked submitted block proposal to see if it has timed out.
    /// Broadcasts a rejection and marks the block locally rejected if it has.
    fn check_submitted_block_proposal(&mut self) {
        let Some((proposal_signer_sighash, block_submission)) =
            self.submitted_block_proposal.take()
        else {
            // Nothing to check.
            return;
        };
        if block_submission.elapsed() < self.block_proposal_validation_timeout {
            // Not expired yet. Put it back!
            self.submitted_block_proposal = Some((proposal_signer_sighash, block_submission));
            return;
        }
        // For mutability reasons, we need to take the block_info out of the map and add it back after processing
        let mut block_info = match self.signer_db.block_lookup(&proposal_signer_sighash) {
            Ok(Some(block_info)) => {
                if block_info.has_reached_consensus() {
                    // The block has already reached consensus.
                    return;
                }
                block_info
            }
            Ok(None) => {
                // This is weird. If this is reached, its probably an error in code logic or the db was flushed.
                // Why are we tracking a block submission for a block we have never seen / stored before.
                error!("{self}: tracking an unknown block validation submission.";
                    "signer_signature_hash" => %proposal_signer_sighash,
                );
                return;
            }
            Err(e) => {
                error!("{self}: Failed to lookup block in signer db: {e:?}",);
                return;
            }
        };

    /// Helper for getting the block info from the db while accommodating for reward cycle
    pub fn block_lookup_by_reward_cycle(
        &self,
        block_hash: &Sha512Trunc256Sum,
    ) -> Option<BlockInfo> {
        let block_info = self
            .signer_db
            .block_lookup(block_hash)
            .inspect_err(|e| {
                error!("{self}: Failed to lookup block hash {block_hash} in signer db: {e:?}");
            })
            .ok()
            .flatten()?;
        if block_info.reward_cycle == self.reward_cycle {
            Some(block_info)
        } else {
            None
        }
    }
