### Title
Legacy web_api_trigger gateway path lacks caller allowlist/rate-limiting, allowing any message-signature holder to fan out arbitrary trigger payloads to all DON nodes - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` validates message structure, signature format, timestamp freshness, and method name, but performs no allowlist or role-based authorization check on the sender before registering a callback in `h.savedCallbacks` and broadcasting the request via `don.SendToNode` to every `h.donConfig.Members`. The code explicitly marks this gap with `// TODO: apply allowlist and rate-limiting here`.

### Finding Description
The gateway's `ProcessRequest` in `core/services/gateway/gateway.go` decodes an incoming JSON-RPC request, calls `msg.Validate()` (in `core/services/gateway/api/message.go`), and then, for legacy DON-ID-addressed requests, dispatches directly to `h.HandleLegacyUserMessage(ctx, msg, callback)`. [1](#0-0) 

`Message.Validate()` only checks structural constraints (signature hex length, message ID/method/DonId length, receiver length) and calls `ExtractSigner()` to recover an address into `m.Body.Sender` — it does not check that the recovered sender is on any allowlist. [2](#0-1) 

Inside `HandleLegacyUserMessage`, the checks performed are: payload JSON-decodable, `Timestamp != 0`, and message not stale — followed immediately by the comment `// TODO: apply allowlist and rate-limiting here` and a method-name check. No code path verifies the sender against `HandlerConfig` or `DONConfig`-level allow rules before proceeding. [3](#0-2) 

After that, the message is transformed via `common.ValidatedRequestFromMessage`, registered in `h.savedCallbacks[msg.Body.MessageId]`, and broadcast with `don.SendToNode(ctx, member.Address, req)` for every DON member — with no gating on sender identity. [4](#0-3) 

Neither `HandlerConfig` nor `handler` struct contain any allowlist field or authorizer dependency (unlike the vault capability's `gw_handler.go`, which uses an explicit `Authorizer`/`AuthorizeRequest`), confirming no allowlist enforcement exists anywhere in this call chain for `capabilities.handler`. [5](#0-4) [6](#0-5) 

This confirms the question: any caller who can produce a structurally valid, signed `api.Message` (signature just needs to be a valid 65-byte ECDSA signature recoverable to *some* address — the code never checks it against a permitted set) targeting `MethodWebAPITrigger` with a `webapicap.TriggerRequestPayload` reaches the fan-out and callback registration with zero authorization gate. The existing test suite explicitly acknowledges this gap: `handler_test.go` has a `TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated`. [7](#0-6) 

### Impact Explanation
Any party able to produce an arbitrary ECDSA keypair and sign a well-formed `api.Message` (no credential beyond generating a valid EC signature is required — `ExtractSigner` accepts any valid signature, not one from a pre-approved key) can force the gateway to broadcast a `MethodWebAPITrigger`-tagged `TriggerRequestPayload` to every node in `h.donConfig.Members`. This matches the "unauthorized job/workflow triggering" impact class: an unprivileged/unauthenticated party can cause DON nodes to receive and act on attacker-supplied trigger requests, and register a callback that will forward whatever the first responding node returns back to the (attacker-controlled) caller — a form of request impersonation/unauthorized-action-triggering, with a lesser but real risk of internal-node-response disclosure to an unauthorized requester.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs network access to the gateway's user-facing HTTP endpoint and the ability to generate an ECDSA keypair to sign the message locally (`Message.Sign`/`SignKS` show the signing scheme is simply over aligned message fields with any private key — no proof of DON/operator identity is required). The request must pass basic structural validation (`Validate()`), have a non-zero, non-stale `Timestamp` in the payload, and use `Method: MethodWebAPITrigger`. All of this is fully attacker-controlled and repeatable indefinitely, since there is no allowlist or per-sender rate limiting (`nodeRateLimiter` only rate-limits DON→gateway outgoing traffic keyed by `nodeAddr`, not user-facing traffic into `HandleLegacyUserMessage`). [8](#0-7) 

### Recommendation
Implement the allowlist/rate-limiting check called out by the TODO before proceeding past method validation in `HandleLegacyUserMessage`: verify `msg.Body.Sender` (populated by `Validate()`/`ExtractSigner()`) against a configured allowlist (per DON or per capability, similar to `core/capabilities/vault/allow_list_based_auth.go`'s `Authorizer` pattern) and apply a per-sender rate limiter, rejecting the request with an appropriate error code (e.g., a new `Unauthorized`/`RateLimited` error) prior to writing to `h.savedCallbacks` or calling `don.SendToNode`.

### Proof of Concept
Go handler-level test plan (extend `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Build a `handler` via `NewHandler` with a `DONConfig` containing several `Members`, and a mock `handlers.DON` (`don.SendToNode`) using `mockery`-generated mocks.
2. Construct a signed `api.Message` (`triggerRequest` helper already present in the test file) with `Method = MethodWebAPITrigger`, a valid `webapicap.TriggerRequestPayload`, signed by an arbitrary/unregistered private key (i.e., not part of any configured allowlist, since none currently exists).
3. Call `handler.HandleLegacyUserMessage(ctx, msg, cb)`.
4. Current (vulnerable) expected behavior: `don.SendToNode` mock is invoked once per `donConfig.Members` entry, and `handler.savedCallbacks[msg.Body.MessageId]` is populated — assert this happens with `mockDON.AssertNumberOfCalls(t, "SendToNode", len(members))` and `require.NotEmpty(t, handler.savedCallbacks)`.
5. Desired (fixed) behavior test: after adding allowlist enforcement, assert that for a sender not on the allowlist, `SendToNode` is never called (`mockDON.AssertNotCalled(t, "SendToNode", mock.Anything, mock.Anything, mock.Anything)`), `savedCallbacks` remains empty, and `callback.SendResponse` is invoked with an unauthorized/error code.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
