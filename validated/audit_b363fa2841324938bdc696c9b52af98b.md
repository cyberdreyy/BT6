### Title
Stale confirmations from removed multisig members still count toward `num_confirmations`, allowing a request to execute with fewer live-member confirmations than the configured threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` implement a K-of-N confirmation scheme where a `MultiSigRequest` executes once `confirmations.len() >= num_confirmations`. When a member/key is removed via `DeleteMember`/`DeleteKey`, the contract only purges *requests created by* that member, but never scrubs that member's existing confirmations recorded on *other* still-pending requests. Those stale confirmations continue to count toward the threshold, so a request can execute even though fewer than `num_confirmations` currently-live members actually approved it.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` increments/records confirmations in a `HashSet<String>` keyed by the confirming member's identity, and executes the request once the size reaches `num_confirmations`: [1](#0-0) 

`delete_member()` only deletes *requests originated by* the removed member (matched via `r.member == member`), and only clears the `num_requests_pk` counter and the member set — it never inspects or updates the `confirmations` map for other outstanding requests where that member had already voted: [2](#0-1) 

The invariant the contract is supposed to guarantee is:
`confirmations.len() >= num_confirmations` ⇔ `num_confirmations` **currently live** members approved the request.

Because stale confirmations are never removed, the real invariant enforced is:
`confirmations.len() (including confirmations from members removed afterwards) >= num_confirmations`,

which is a strictly weaker guarantee. A confirmation cast by member M before M is removed remains valid forever, silently reducing the number of *live* approvals actually required to execute future pending requests.

The same pattern exists in the older `multisig/src/lib.rs` contract: the `DeleteKey` action removes only requests created by the deleted `signer_pk`, not that key's confirmations recorded on other requests: [3](#0-2) 
while `confirm()` executes purely based on the size of the `confirmations` set versus `num_confirmations`: [4](#0-3) 

### Impact Explanation
This breaks the core custody guarantee of the multisig: funds (`Transfer`, `FunctionCall` with deposit, `AddKey`/`AddMember` to grant control, etc.) can be moved by executing a request that has fewer than `num_confirmations` *currently live* member approvals, because one or more of the counted confirmations belong to members that have since been removed from the multisig. This directly matches the "a multisig request executed below threshold" Critical impact category — the K-of-N security assumption that requests require simultaneous agreement from K live parties is violated.

### Likelihood Explanation
Exploitation requires normal multisig operation flow (not any special/foundation privilege): a request is created and confirmed by fewer than `num_confirmations` members, one of the confirming members is subsequently removed via a legitimate `DeleteMember`/`DeleteKey` request, and the original pending request is left in place (or newly created and only partially confirmed by remaining live members). The removed member's earlier confirmation still counts, so the remaining live members only need to supply `num_confirmations - (stale confirmations)` additional approvals to trigger execution — a lower bar than intended. This can occur naturally (e.g. rotating out a departing team member without cleaning up their in-flight votes) or be engineered by a member who confirms a request and then arranges/accepts their own removal, knowing their vote will persist.

### Recommendation
When removing a member/key (`delete_member` / `DeleteKey`), iterate over all active requests and strip the removed member's identity from each request's confirmation set (not just requests they originated), or alternatively validate at `confirm()`/execution time that every recorded confirmation still belongs to a current member of `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(members=[A,B,C,D,E], num_confirmations=3)`.
2. B creates request X (`add_request`), a `Transfer` to an attacker-controlled account.
3. A confirms X (`confirmations = {A}`, size 1, below threshold).
4. A separate request to `DeleteMember{A}` is created and confirmed by B, C, D (3 confirmations) and executes — A is removed from `self.members`; per `delete_member`, only requests where `r.member == A` (i.e., requests A personally created) are purged, so request X (created by B) is untouched, and A's confirmation entry inside `confirmations` for request X is never cleared.
5. Now only 4 live members (B, C, D, E) remain. C confirms X (`confirmations = {A, C}`, size 2). D confirms X (`confirmations = {A, C, D}`, size 3) → `confirm()` sees `confirmations.len() as u32 + 1 >= num_confirmations` (or already `>=`) and executes the `Transfer`, even though only 2 currently-live members (C and D) actually approved it — one confirmation slot was filled by A, a member no longer part of the multisig at execution time.     /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
