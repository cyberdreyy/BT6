### Title
Unbounded cross-user eviction of pending gateway callbacks via savedCallbacks flooding - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` stores every valid trigger request into the shared `h.savedCallbacks` map keyed by attacker-controlled `MessageId`, with no rate limiting or per-sender quota (explicitly marked `TODO`). `handler.pruneCallbacks`, run periodically or under load, evicts the oldest half of all entries once `len(savedCallbacks) > MaxSavedCallbacks`, silently deleting other users' pending callbacks with no response ever delivered to them.

### Finding Description
Any party who can produce a valid ECDSA signature over a well-formed message (checked only by `Message.Validate()`, which validates format and signature but not any sender allowlist) can submit `web_api_trigger` requests to the gateway's legacy JSON-RPC endpoint, reaching `gateway.ProcessRequest` → `handler.HandleLegacyUserMessage`. Each accepted message is stored unconditionally: `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` (handler.go:412), with unique `MessageId` values fully controlled by the caller and no per-sender limit. `pruneCallbacks` (handler.go:299-339) only trims size when total map length exceeds `MaxSavedCallbacks`, sorting by `createdAt` and deleting the oldest `len(entries)-maxSize/2` entries — this is confirmed by `TestPruneCallbacks/enforces_max_size_by_evicting_oldest` in handler_test.go:518-539, which shows entries "a" and "b" (submitted earlier) get silently deleted while "d" (latest) survives, with no error surfaced to the evicted callback's original requester. Since a legitimate victim's earlier-submitted, still-pending request would be among the oldest entries, an attacker flooding `MaxSavedCallbacks+1` (default 20000, `defaultMaxSavedCallbacks`) unique-`MessageId` requests can cause the victim's callback to be evicted before any node response arrives, and the victim's original HTTP request will simply hang until gateway-side timeout with no indication of the cause. The `// TODO: apply allowlist and rate-limiting here` comment (handler.go:384) confirms this control gap is a known, unaddressed omission rather than defense-in-depth already present elsewhere.

### Impact Explanation
This is a cross-user denial-of-response: a legitimate user's in-flight `web_api_trigger` request can be silently dropped without any error, matching Chainlink's "Denial of Service"/service disruption impact class for gateway components — no funds or keys are exposed, but availability/isolation of another user's request is violated by an unprivileged flood.

### Likelihood Explanation
Feasibility is high: the attacker needs only to produce arbitrary signed messages (any ECDSA keypair, no allowlist enforced by `Message.Validate()`), and must send roughly `MaxSavedCallbacks` (default 20000) requests before pruning triggers eviction, well within reach given no rate limiting is implemented in this path. Pruning runs automatically every `CallbackPruneIntervalSec` (default 30s), so repeated bursts reliably reproduce the eviction.

### Recommendation
Add per-sender quotas/rate limiting for `HandleLegacyUserMessage` (the TODO already flags this), and change `pruneCallbacks` to send a timeout/error response to evicted callbacks via `SendResponse` before deletion instead of silently dropping them, so requesters are not left hanging indefinitely.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Set `handler.config.MaxSavedCallbacks` to a small value (e.g. 10).
2. Seed `handler.savedCallbacks["victim"] = &savedCallback{id: "victim", createdAt: earliestTime, Callback: victimCb}` where `victimCb` is a `hc.NewCallback()` that has not yet received a response.
3. Add `MaxSavedCallbacks` attacker entries with later `createdAt` timestamps (simulating flooding via unique `MessageId`s through repeated `HandleLegacyUserMessage` calls).
4. Call `handler.pruneCallbacks()`.
5. Assert `handler.savedCallbacks` no longer contains `"victim"`, and assert `victimCb.Wait` (with a short timeout) returns a timeout/error, proving the victim never receives `SendResponse` and no error was surfaced to them.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}

}
