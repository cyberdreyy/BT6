### Title
`check_parent_tenure_choice` mis-times an unrecorded `approved_time` as "late-arriving," letting an attacker miner get a legitimately-timed single-block tenure reorg improperly sanctioned - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` is the sole gate that decides whether a new miner is allowed to build off (reorg) something other than the prior sortition's tenure. It permits the reorg for a given victim tenure when that tenure's first block was proposed "too close" to the next Bitcoin block (`first_proposal_burn_block_timing`). When the signer's local `BlockInfo.approved_time` for that victim block is unset, the function silently substitutes `0` for the elapsed time instead of treating the timing as unknown, which always satisfies the "poorly timed" condition and auto-permits the reorg regardless of the tenure's actual, legitimate timing.

### Finding Description
The relevant logic lives in `check_parent_tenure_choice`: [1](#0-0) 

```rust
let checked_proposal_timing = if let Some(sortition_state_received_time) = sortition_state_received_time {
    let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
        sortition_state_received_time.saturating_sub(approved_at)
    } else {
        info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
        0
    };
    if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
        // ... superseded_tenures.push(tenure); continue; (reorg permitted for this tenure)
    }
    true
} else {
    false
};
```

The intended invariant: a reorg over a tenure that produced a single block is sanctioned (`mark_tenure_superseded`) only if that block was proposed too close to the next sortition to legitimately count as chain progress — i.e., the elapsed time between the block's approval and the new sortition being received must be *provably* short. The `else` branch collapses "we don't know the timing" into `proposal_to_sortition = 0`, which is the minimum possible value and therefore always less than `first_proposal_burn_block_timing` (a strictly positive duration per `stacks-signer/src/config.rs`). This turns "unknown timing" into "always poorly timed," inverting the safety check: the equality this function is supposed to enforce — *approved-parent-choice is canonical only if the abandoned tenure was actually mistimed* — silently becomes *always true when local bookkeeping is incomplete*.

`local_block_info.approved_time` is stamped only when this particular signer personally pre-committed to the block (see `mark_pre_committed`, referenced in `docs/signer-flows.md` section 4: "stamps approved_time"). A signer can legitimately reach `GlobalStateEvaluator`/consensus-visible agreement about a block without ever setting this local field itself — e.g., a signer that joined the set after that tenure's block was already globally accepted, or one that lost/reset its `SignerDb` and rebuilt state from the node (`get_first_approved_block_in_tenure` still returns the `BlockInfo` row, but with `approved_time = NULL` if it was inserted through a path other than its own pre-commit, such as replaying an observed group signature). This is exactly the "losing the equivocation guard on restart" class of issue: local per-signer bookkeeping used for a safety-relevant decision is not restored/derived robustly and defaults to the more permissive branch.

A single, one-slot malicious (or even honest-but-opportunistic) miner that wins the very next sortition can exploit this by proposing a tenure-change block whose `TenureChangePayload.prev_tenure_consensus_hash` targets an earlier sortition than the immediately-prior one — i.e., attempt to reorg a tenure that legitimately produced exactly one, well-timed, globally-accepted block. `check_parent_tenure_choice` is invoked per-signer, independently, during proposal validation (`v1.rs`/`v2.rs` `validate_tenure_change_payload` → `check_parent_tenure_choice`, gating `RejectReason::ReorgNotAllowed`). Any signer lacking `approved_time` for that victim block (through no attacker action beyond simply mining the reorging proposal) will incorrectly conclude the reorg is sanctioned, mark the victim tenure `superseded` via `record_superseded_tenure`/`mark_tenure_superseded`, and thereafter treat its own prior signature over that tenure's block as excluded from the conflict guard (`reorg_permit_stands` in `stacks-signer/src/v0/signer.rs`), clearing the way to sign the attacker's non-canonical reorging block.

### Impact Explanation
This breaks the approved-parent-vs-canonical equality that `check_parent_tenure_choice` exists to enforce: a signer can be induced to treat an improper reorg of a legitimately, canonically-produced tenure as sanctioned, and then sign a block that illegitimately reorgs it — the Critical impact category ("a signer signing an invalid, non-canonical, or conflicting block"). It is also, independently, an instance of "losing the equivocation guard on restart/rejoin," since the root cause is `approved_time` not being reliably present for signers who did not personally witness the original pre-commit.

### Likelihood Explanation
The trigger requires only (a) a single miner winning the next sortition and choosing to build a tenure-change block against a non-immediate parent, and (b) at least one signer whose local `approved_time` field is unset for the targeted victim block — a state reachable through ordinary, non-adversarial events (signer restart with DB loss, late join, or having only observed the group signature rather than personally pre-committing). No majority of signers, no signer key compromise, and no auth_token/local access are required; it is a pure logic flaw reachable via the normal proposal-validation code path exercised by every proposal.

### Recommendation
- Do not default `proposal_to_sortition` to `0` when `approved_time` is unknown. Treat an unknown timing as inconclusive and fail closed (do not permit the reorg / return `Ok(false)`) rather than fail open, consistent with the conservative fallback used elsewhere in this same function (e.g., when `get_tenure_forking_info` returns empty, the code explicitly rejects rather than permits).
- If a "late-arriving proposal" heuristic is still desired for blocks the signer never personally approved, derive the timing from a node-verifiable, canonical timestamp (e.g., the block's own header/tenure-tip timing from the Stacks node) rather than defaulting to a value that always satisfies the "poorly timed" branch.
- Add signer-side self-consistency checks (or a node round trip) to backfill/verify `approved_time` for tenure blocks it did not personally pre-commit to, before using its absence as a security-relevant signal.

### Proof of Concept
1. Tenure T1 produces exactly one block B1, which reaches global acceptance (70% signatures) canonically and with normal timing (not close to the next Bitcoin block).
2. Signer S restarts (or joins the signer set) after B1 was already globally accepted; S's `SignerDb` row for B1 has `approved_time = NULL` (S never personally pre-committed B1 — it learned of B1 only via the node's chain state / an observed group signature).
3. An attacker wins the next sortition and proposes a tenure-change block B2 whose `prev_tenure_consensus_hash` points to the sortition before T1 (i.e., attempts to reorg T1/B1) rather than T1 itself.
4. On S, `check_parent_tenure_choice` runs: `tenures_reorged` includes T1; `globally_accepted_blocks == 1` (passes the "at most one block" gate); `local_block_info.approved_time` is `None`, so `proposal_to_sortition = 0`; `Duration::from_secs(0) < first_proposal_burn_block_timing` is true, so T1 is pushed into `superseded_tenures` and the reorg over T1 is permitted — even though B1's actual timing was fine.
5. S marks T1 `superseded`, `reorg_permit_stands` subsequently excludes B1 as a conflict, and S proceeds to sign B2, i.e., a non-canonical reorg of a legitimately-produced tenure.
