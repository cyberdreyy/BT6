### Title
External Initiator credential grants unrestricted `RunJobV2` access to arbitrary job IDs via broken `isUser` check - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` sets the same `SessionUserKey` context value used for regular session/token users, giving every authenticated External Initiator (EI) a `clsessions.User{Role: UserRoleRun}` object. `PipelineRunsController.Create` in `core/web/pipeline_runs_controller.go` uses `isUser := auth.GetAuthenticatedUser(c)` — which is `true` for EI-authenticated requests too — to gate the integer-job-ID run path, despite an explicit comment stating "only users are allowed to run jobs using int IDs - EIs not allowed."

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) validates the EI's `AccessKey`/`Secret` against the stored `ExternalInitiator` row, then unconditionally does:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [1](#0-0) 

`PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go:89-128`) is the handler for `POST /v2/jobs/:ID/runs`. It determines whether to allow the integer-job-ID run path solely via:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
    ...
}
``` [2](#0-1) 

`auth.GetAuthenticatedUser` simply checks for the presence of `SessionUserKey` in the gin context:
```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	...
	user, ok := obj.(*clsessions.User)
	return user, ok
}
``` [3](#0-2) 

Because `AuthenticateExternalInitiator` also sets `SessionUserKey`, `isUser` evaluates to `true` for a valid EI-authenticated request — contradicting the developer's own comment that EIs are excluded from this path. There is no check for `GetAuthenticatedExternalInitiator` to reject EI callers, and `RunJobV2(ctx, jobID, nil)` (as exposed through the `chainlink.Application` interface) takes no caller/requester argument that could be used to verify the EI is bound to that specific `jobID`. The historical EI→job binding mechanism (the `externalInitiators` TOML list on webhook job specs, matched via job UUID) is defunct in this codebase: webhook-type jobs are rejected outright (`job.ErrJobTypeRemoved`), as shown by `Create`'s early UUID rejection and confirmed by `TestRunner_WebhookJobRemoved`, which asserts job creation with `externalInitiators` now returns `422 Unprocessable Entity`. [4](#0-3) [5](#0-4) 

Thus, if the route for `POST /v2/jobs/:ID/runs` is wired (via `Authenticate(...)`) to accept `AuthenticateExternalInitiator` as one of its auth methods, any valid EI credential holder can call this endpoint with an arbitrary integer job ID and trigger a run for a job they have no relationship to, since no per-job authorization check exists downstream of the broken `isUser` gate.

### Impact Explanation
This is an authorization/role-bypass allowing an External Initiator (a low-privilege, narrowly-scoped credential intended to trigger only its own bound job) to trigger pipeline runs for any job on the node by integer ID. Depending on job configuration, this can cause unauthorized on-chain transactions, unwanted resource consumption, or unauthorized data submission — matching Chainlink's "unauthorized job run" bounty impact class.

### Likelihood Explanation
Exploitability requires only a valid EI `AccessKey`/`Secret` pair (the minimal, lowest-privilege credential type in the system) and knowledge or brute-forcible guessing of a target integer job ID. No admin/session/API-token privileges are needed. The flaw is deterministic and repeatable given the request path is reachable. The main uncertainty (not fully confirmed via available search) is exact router wiring in `core/web/router.go` — I could not verify from the index whether the `/v2/jobs/:ID/runs` `POST` route is registered with `AuthenticateExternalInitiator` among its accepted auth methods. If it is not included in that route's `Authenticate(...)` middleware chain, EI requests would already fail authentication before reaching `Create`, and this specific proof-of-concept would not be exploitable through this route (though the `isUser`/comment mismatch is still a genuine logic defect).

### Recommendation
Do not rely on `GetAuthenticatedUser` alone to gate the "user-only" integer-ID run path. Explicitly check `auth.GetAuthenticatedExternalInitiator(c)` and reject (403) if an EI is present, regardless of the synthetic `SessionUserKey` set for EIs. If EIs should retain job-triggering ability, restore an explicit binding check (e.g., verify the requested job's `ExternalJobID`/associated EI matches the authenticated `ExternalInitiator.ID`) before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test plan (Go, using `httptest` + `cltest.TestApplication`, similar to `TestRunner_WebhookJobRemoved` / `TestPipelineRunsController_ShowRun_InvalidID` patterns):
1. Create two jobs, `jobA` and `jobB`, with distinct integer IDs (e.g., OCR jobs as in `setupPipelineRunsControllerTests`).
2. Create an `ExternalInitiator` via `cltest.CreateExternalInitiatorViaWeb` unrelated to either job.
3. Send `POST /v2/jobs/<jobA.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's credentials (no session cookie, no API token).
4. Assert whether the router permits this request to reach `PipelineRunsController.Create` (verify via `core/web/router.go` route registration for `/v2/jobs/:ID/runs`).
5. If reachable: assert response is `200 OK` with a created pipeline run (vulnerability confirmed — EI triggered a run for a job it has no declared relationship to) versus the expected `401/403` (if route excludes `AuthenticateExternalInitiator`, or if job-binding is enforced).
6. Repeat for `jobB.ID` to confirm the EI can trigger runs for any arbitrary integer job ID, not just one it's authorized for.
