### Title
Cross-Block Rejection-Weight Undercounting via Non-Composite Primary Key in `block_rejection_signer_addrs` - (File: stacks-signer/src/signerdb.rs)

### Summary
The `block_rejection_signer_addrs` table is created with `PRIMARY KEY (signer_addr)` instead of a composite key over `(signer_signature_hash, signer_addr)`. Since a signer's local rejection ledger is keyed by address alone, only the *first ever* rejected block hash a given signer address is recorded against can persist; every subsequent rejection of a *different* block by that same address fails to insert and is silently dropped from the tally used to determine 30%-weight global rejection.

### Finding Description
The table is declared as: [1](#0-0) 

Note `PRIMARY KEY (signer_addr)` — there is no dependency on `signer_signature_hash` in the uniqueness constraint, even though the column is present and semantically should distinguish rejections per block.

`add_block_rejection_signer_addr` reads/writes as if uniqueness were per `(signer_signature_hash, signer_addr)`: [2](#0-1) 

It queries `existing_code` scoped by both `signer_signature_hash` and `signer_addr` (correctly finding "no row" if the address has never rejected *this specific* block hash before), then falls into the `None` branch and issues a plain `INSERT` (not `INSERT OR REPLACE`/`UPSERT`) of `(new_block_hash, addr, reject_code)`. If that same `addr` already has a row in the table for *any other* block hash (which is true for essentially every active signer after its first-ever rejection, since the only code path that deletes a row for that address is scoped to the same `signer_signature_hash` when a signature is later recorded — it never removes rows for other block hashes), this `INSERT` violates the `PRIMARY KEY (signer_addr)` constraint and returns a `DBError`.

The caller, `handle_block_rejection`, treats this error as non-fatal and simply logs and continues rather than returning: [3](#0-2) 

Execution then falls through to compute the rejection tally via `get_block_rejection_signer_addrs(block_hash)` and compares `total_reject_weight` against `min_weight`/`total_weight` to decide whether to `mark_globally_rejected`: [4](#0-3) 

Because the failed `INSERT` never persisted, `get_block_rejection_signer_addrs(block_hash)` does not include the rejecting signer's weight for this new block — the signer's *genuine, freshly broadcast rejection* silently vanishes from the local tally used to compute `total_reject_weight`, even though the signer correctly validated the block as invalid and broadcast a rejection. This breaks the equality between "signers who actually rejected block X" and "signers counted as having rejected block X" in each peer's local view.

### Impact Explanation
This is a liveness wedge on the 30%-weight global-rejection mechanism (`docs/signer-flows.md`'s TALLY step: "over 30% rejected → 70% is now impossible → globally rejected"). Once any given signer address has had one rejection persisted for one block hash, its rejection weight can never again be counted toward any *different* block's rejection tally in any peer's local `SignerDb`, since the delete-on-signature path only clears the row for the exact same `signer_signature_hash`: [5](#0-4) 

In normal, expected chain operation (competing/invalid proposals, forks, reorgs), this condition is reached almost immediately for the whole signer set. From that point forward, invalid or conflicting blocks may never accumulate the recorded 30% rejection weight needed to reach `GloballyRejected`, even when a genuine supermajority is actively rejecting. This can wedge the state machine: signers keep silently waiting instead of settling a decision on a bad block, which matches the "High — a signer wedged into never reaching a needed threshold / losing an equivocation guard" impact class, since rejection accounting is a core safety/liveness gate that other checks (e.g., miner-invalidation logic, reorg-permit expiry) depend on.

### Likelihood Explanation
Reachable by a single miner (or gossip alone), without needing majority collusion, another signer's key, or the auth token: the miner only needs to cause a signer to reject two different blocks over the signer's lifetime (e.g. one clearly invalid proposal, then a later different invalid/conflicting proposal, or naturally occurring reorgs/timeouts). Because `add_block_rejection_signer_addr` is invoked on the standard proposal-rejection path (`handle_block_rejection`, `handle_block_validate_reject`, etc.) for every rejected block, the very first rejection any signer ever records will permanently "consume" that signer's `signer_addr` slot in the table, and all subsequent distinct-block rejections silently fail. This makes the bug essentially certain to manifest in any long-running signer.

### Recommendation
Change the primary key of `block_rejection_signer_addrs` to the composite `(signer_signature_hash, signer_addr)` (with an appropriate migration to widen the constraint and preserve existing rows), and update `add_block_rejection_signer_addr`'s insert to use `INSERT OR REPLACE`/upsert semantics keyed on that composite, matching the intent already implied by the `SELECT ... WHERE signer_signature_hash = ?1 AND signer_addr = ?2` lookup logic. Also propagate/handle `DBError` from this call as a hard failure path (or retry) rather than continuing to tally an incomplete rejection set.

### Proof of Concept
1. Signer `S` receives an invalid `BlockProposal` for block `A` (e.g., bad consensus hash/BitVec, as in `block_proposal_rejection`-style scenarios) and calls `handle_block_rejection` → `add_block_rejection_signer_addr(A, S, reason)`. Table now has one row: `(A, S, code)`.
2. The same or another miner subsequently proposes an unrelated, differently-invalid block `B` (different `signer_signature_hash`). Signer `S` also rejects `B`.
3. `add_block_rejection_signer_addr(B, S, reason)` runs its `existing_code` lookup filtered by `(B, S)` → returns `None` (no row yet for `B`). It executes `INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (B, S, reason)`, which violates `PRIMARY KEY (signer_addr)` since `S` already has a row for `A`. `self.db.execute` returns an `Err`.
4. `handle_block_rejection` logs a warning but does not return, and computes `total_reject_weight` for block `B` via `get_block_rejection_signer_addrs(B)`, which does **not** include `S`'s weight (its row was never inserted).
5. If enough signers hit this same pattern (near-certain over normal signer-set lifetime), block `B`'s local rejection tally under-reports true rejecting weight, and `mark_globally_rejected` for `B` may never trigger even though a real supermajority rejects it — wedging consensus finalization for that block.

    /// Record an observed block rejection_signature
    pub fn add_block_rejection_signer_addr(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        addr: &StacksAddress,
        reject_reason: RejectReasonPrefix,
    ) -> Result<bool, DBError> {
        // If this signer/block already has a signature, do not allow a rejection
        let sig_qry = "SELECT EXISTS(SELECT 1 FROM block_signatures WHERE signer_signature_hash = ?1 AND signer_addr = ?2)";
        let sig_args = params![block_sighash, addr.to_string()];
        let exists = self.db.query_row(sig_qry, sig_args, |row| row.get(0))?;
        if exists {
            warn!("Cannot add block rejection because a signature already exists.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %addr,
                "reject_reason" => ?reject_reason
            );
            return Ok(false);
        }

        // Check if a row exists for this sighash/signer combo
        let qry = "SELECT reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2 LIMIT 1";
        let args = params![block_sighash, addr.to_string()];
        let existing_code: Option<i64> =
            self.db.query_row(qry, args, |row| row.get(0)).optional()?;

        let reject_code = reject_reason as i64;

        match existing_code {
            Some(code) if code == reject_code => {
                // Row exists with same reject_reason, do nothing
                debug!("Duplicate block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(false)
            }
            Some(_) => {
                // Row exists but with different reject_reason, update it
                let update_qry = "UPDATE block_rejection_signer_addrs SET reject_code = ?1 WHERE signer_signature_hash = ?2 AND signer_addr = ?3";
                let update_args = params![reject_code, block_sighash, addr.to_string()];
                self.db.execute(update_qry, update_args)?;
                debug!("Updated block rejection reason.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
            None => {
                // Row does not exist, insert it
                let insert_qry = "INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (?1, ?2, ?3)";
                let insert_args = params![block_sighash, addr.to_string(), reject_code];
                self.db.execute(insert_qry, insert_args)?;
                debug!("Inserted block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
        }
