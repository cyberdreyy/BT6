### Title
Unchecked RLP length fields in MPT node decoding can panic the fault-proof program - (File: `crates/proof/mpt/src/util.rs`)

### Summary
`base-proof-mpt`'s `rlp_list_element_length` helper decodes RLP length headers taken directly from attacker-suppliable trie-node preimage bytes and uses them, unchecked, both in a subtraction and in an unconditional buffer `advance()`, mirroring the MaraDNS `Decompress.c` pattern where an unvalidated `rdlength`/`total` difference is fed straight into a downstream operation that aborts the process. This function backs `TrieNode::decode`, the single entry point used by both the L1 and L2 MPT walkers in the fault-proof program.

### Finding Description
`rlp_list_element_length` decodes an RLP list header and then walks the list by repeatedly decoding inner headers and advancing the cursor by each inner element's declared `payload_length`, with no check that the declared length actually fits in the remaining buffer: [1](#0-0) 

Specifically:
- Line 68, `let len_after_consume = buf.len() - header.payload_length;`, subtracts an attacker-controlled `header.payload_length` from `buf.len()` with no prior `buf.len() >= header.payload_length` guard.
- Line 73, `buf.advance(header.payload_length);`, advances the cursor by each inner element's declared length with no check that it fits within the remaining slice.

Every other RLP decode path in this codebase explicitly guards against this exact situation before consuming/advancing, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) 

`rlp_list_element_length` is the sole exception, and it is called directly from `TrieNode::decode`: [5](#0-4) 

`TrieNode::decode` is the universal entry point used to parse MPT nodes fetched from the preimage oracle on both L1 and L2 during fault-proof execution: [6](#0-5) [7](#0-6) 

These providers back `OrderedListWalker`, used to walk L1 receipts/transactions tries and the L2 state trie while deriving the claimed output root.

### Impact Explanation
The preimage oracle only guarantees `keccak256(data) == requested_hash`; it places no constraint on the byte content otherwise. A dispute-game participant supplying witness/preimage data for a node they themselves construct (any keccak preimage they choose to commit to) can craft an inner RLP element inside a `TrieNode`'s payload with a declared length larger than the remaining bytes in the node. This drives `buf.advance()` (and, depending on the RLP crate's bounds behavior, potentially the earlier subtraction) past the actual buffer size, causing an unrecoverable panic/abort of the fault-proof program instead of a clean decode error. Because this code path is executed inside the fault-proof program that computes/verifies the claimed output root, a crash here prevents the program from completing execution — a denial of service against the dispute-resolution machinery ("node halt" / inability to produce a provable output), which is one of the explicitly in-scope impact classes for this analog.

### Likelihood Explanation
Every RLP-consuming path elsewhere in the repository defensively checks `buf.len() < header.payload_length` before slicing/advancing — the omission in `rlp_list_element_length` is an isolated gap, not a systemic design choice, making it a plausible oversight. The trigger requires only a single, self-consistent malformed MPT node (any bytes an attacker chooses, since they control the corresponding preimage), reachable by any actor able to supply witness data into a dispute game's preimage oracle (a defined in-scope actor: "dispute-game participant"). I was not able to fully confirm within tool budget whether the release profile used to build the fault-proof program enables `overflow-checks` (which would additionally make line 68's subtraction itself panic); however, the `buf.advance()` call on line 73 is independent of that setting and, based on the consistent bounds-checking pattern applied everywhere else in this codebase before calling `advance`, is the confirmed unconditional panic surface.

### Recommendation
In `rlp_list_element_length` (crates/proof/mpt/src/util.rs), before using `header.payload_length`:
1. Validate `header.payload_length <= buf.len()` immediately after decoding the outer header, returning `alloy_rlp::Error::InputTooShort` otherwise, mirroring the pattern used in `crates/common/consensus/src/receipts/receipt.rs` and `crates/common/consensus/src/transaction/eip8130/tx.rs`.
2. Inside the loop, before `buf.advance(header.payload_length)`, validate the same bound for each inner element's header and return an error instead of advancing unconditionally.

### Proof of Concept
Construct a crafted MPT node preimage `P` such that `keccak256(P) == H` for some hash `H` the attacker controls as an intermediate trie reference used in the dispute game's witness data:
- `P` begins with a valid outer RLP list header whose declared `payload_length` fits within `P`'s remaining bytes (so the function proceeds into the inner loop).
- The first inner element inside that list is encoded with an RLP string/list header whose declared `payload_length` is larger than the number of bytes actually remaining in `P`.

When `TrieNode::decode(&mut P.as_ref())` is called (e.g., via `OracleL1ChainProvider::trie_node_by_hash` or `OracleL2ChainProvider::trie_node_by_hash` while walking a receipts/transactions/state trie), `rlp_list_element_length` will reach `buf.advance(header.payload_length)` with `header.payload_length` exceeding `buf.len()`, panicking the fault-proof program instead of returning a decode error.

pub(crate) fn rlp_list_element_length(buf: &mut &[u8]) -> alloy_rlp::Result<usize> {
    let header = Header::decode(buf)?;
    if !header.list {
        return Err(alloy_rlp::Error::UnexpectedString);
    }
    let len_after_consume = buf.len() - header.payload_length;

    let mut list_element_length = 0;
    while buf.len() > len_after_consume {
        let header = Header::decode(buf)?;
        buf.advance(header.payload_length);
        list_element_length += 1;
    }
    Ok(list_element_length)
}

impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }

impl<T: CommsClient> TrieProvider for OracleL1ChainProvider<T> {
    type Error = OracleProviderError;

    fn trie_node_by_hash(&self, key: B256) -> Result<TrieNode, Self::Error> {
        // On L1, trie node preimages are stored as keccak preimage types in the oracle. We assume
        // that a hint for these preimages has already been sent, prior to this call.
        crate::block_on(async move {
            TrieNode::decode(
                &mut self
                    .oracle
                    .get(PreimageKey::new(*key, PreimageKeyType::Keccak256))
                    .await
                    .map_err(OracleProviderError::Preimage)?
                    .as_ref(),
            )
            .map_err(OracleProviderError::Rlp)
        })
    }
