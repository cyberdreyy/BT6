### Title
Unfunded instant-withdraw receipts from earlier epochs escape the default haircut and are claimed at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`defaultPendingClaimBasis` gates the inclusion of instant-withdraw claims on the *aggregate* `pendingInstantWithdraws` flag but then reads only `instantWithdrawClaimsByEpoch[epochNumber]` — the check is on one field while the access is on another. This mirrors CVE-2024-50158: the driver exported pacing stats only on GenP5/P7 adapters but guarded the stats write with a check on `rdev->dbr_pacing`, touching memory that doesn't exist for that mode. Here, any unfunded instant receipt recorded under an *earlier* epoch index is silently excluded from the default-epoch claim basis, yet remains payable at par afterward.

### Finding Description
`requestInstantWithdraw` records receipts per epoch in `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`, while `pendingInstantWithdraws` is a global unfunded remainder that can persist across many epochs [1](#0-0) . When a default is finalized, `defaultPendingClaimBasis` adds only the *current* epoch's claims whenever `pendingInstantWithdraws != 0` [2](#0-1) . The companion `_defaultPrefundedInstantReserve` makes the same wrong-index assumption: `instantBasis - pendingInstant` compares current-epoch basis against the all-epochs remainder [3](#0-2) .

After finalization, `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` [4](#0-3) , then `claimInstantWithdrawRequest` falls through and pays the user's *entire remaining* `instantWithdrawsRequests` aggregate — including the earlier-epoch unfunded receipts — at par via `_transferFundedClaim` [5](#0-4) .

### Impact Explanation
Two symmetric failures depending on strategy balance:

- **Theft at par**: if the strategy holds underlying beyond `defaultRecoveryReserve` (e.g., partially collected instant funds or borrower-send leftovers counted via `defaultRecoveryReserve`), the earlier-epoch receipt holder withdraws 100% while every default-epoch claimant is haircut by `defaultRecoveryPrice`. The par payout consumes balance that economically belongs to the recovery pool, reducing what late claimants can draw before `balance - reserve < _amount` reverts [6](#0-5) .
- **Permanent freeze**: if no surplus exists, the earlier-epoch claimant's `_transferFundedClaim` reverts forever — their receipt is neither included in `defaultPendingClaimBasis` (so no recovery share was provisioned) nor payable at par. Their funds are permanently stuck with no recovery path.

Loss is quantified as `instantWithdrawClaimsByEpoch[e]` for any `e < defaultRecoveryEpoch` whose claims are still unfunded — up to the full unfunded remainder `pendingInstantWithdraws - instantWithdrawClaimsByEpoch[epochNumber]`.

### Likelihood Explanation
Requires: an instant-withdraw request that remains unfunded across an `epochNumber` boundary (borrower never fully funds `collectInstantWithdrawFunds`), followed by a borrower default and `finalizeDefaultRecovery`. The attacker is any KYC'd lender/tranche holder whose request happens to be stranded — no privileged cooperation needed, and there is no guard forcing same-epoch instant claims. The accounting hole is deterministic once the state exists; `requestInstantWithdraw` has no check preventing a new request while an old one is unfunded [7](#0-6) .

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, include *all* outstanding instant receipt basis, not just `instantWithdrawClaimsByEpoch[epochNumber]` — e.g., track a cumulative `totalInstantWithdrawClaims` updated alongside `instantWithdrawClaimsByEpoch`, and use it for both basis and prefunded-reserve computation. Alternatively, clear per-epoch instant claims for every epoch with unfunded basis in `_claimDefaultedInstantWithdrawRequest` rather than only `defaultRecoveryEpoch`, so stranded receipts receive the recovery haircut instead of a par claim.

### Proof of Concept
Foundry fork test sketch (mode: instant-withdraw enabled, epoch variant):

```solidity
// 1. enable instant withdraws; userA deposits and requests instant withdraw in epoch N.
//    CDO never calls collectInstantWithdrawFunds -> pendingInstantWithdraws == X.
// 2. stopEpoch/startEpoch -> epochNumber becomes N+1.
// 3. userB requests instant withdraw of Y -> instantWithdrawClaimsByEpoch[N+1] = Y;
//    pendingInstantWithdraws == X + Y.
// 4. borrower defaults; finalizeDefaultRecovery runs with _recoveredAmount.
//    basis = pendingWithdraws + instantWithdrawClaimsByEpoch[N+1]  // X excluded
//    prefundedReserve = max(0, Y - (X+Y)) == 0                     // collected funds ignored
// 5. cdo.claimInstantWithdrawRequest(userA):
//    _claimDefaultedInstantWithdrawRequest clears instantWithdrawsRequestsByEpoch[A][N+1] == 0,
//    then burns instantWithdrawsRequests[A] == X and calls _transferFundedClaim(A, X)
//    -> pays X at par (draining surplus) or reverts permanently (freeze),
//       while userB claims only Y * defaultRecoveryPrice.
assertGt(strategy.instantWithdrawsRequests(userA), 0);
// expected: A receives X at par despite never being in recovery basis
```

    // burn strategy tokens from cdo

    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests

  }

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
