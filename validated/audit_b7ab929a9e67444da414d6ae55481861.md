Based on my investigation, I found a plausible structural analog in GitLab Runner's Kubernetes executor: the `AllowedUsers`/`AllowedGroups` restriction (meant to block jobs from running containers as disallowed UIDs/GIDs, e.g. root) can be bypassed when a `PodSecurityContext` or `ContainerSecurityContext` override is present, because the UID/GID validation is only applied to the job-supplied user string and is skipped once a pod/container security context value is used.

### Title
AllowedUsers/AllowedGroups restriction bypass via PodSecurityContext/ContainerSecurityContext override - (File: `executors/kubernetes/kubernetes.go`, function `getSecurityContextWithUIDGID`)

### Summary
GitLab Runner's Kubernetes executor supports an admin-configured allowlist, `AllowedUsers`/`AllowedGroups`, intended to prevent CI jobs from running build/service/helper containers as disallowed UIDs/GIDs (most notably `root`). This restriction is enforced only against the job-derived user string (`jobUser`) inside `getSecurityContextWithUIDGID`. When a `PodSecurityContext` or `ContainerSecurityContext` (with `RunAsUser`/`RunAsGroup` set) is supplied — which can originate from CI/CD-variable overwrites when the runner admin enables the standard `*_overwrite_allowed` regex config — that value is applied directly to the resulting security context without ever being checked against `AllowedUsers`/`AllowedGroups`. This mirrors the composer report's root cause: a secondary/alternate code path (`_deposit()`/cross-chain composer vs. `getSecurityContextWithUIDGID`'s security-context branch) performs the privileged operation without re-verifying the same restriction that the "normal" path enforces.

### Finding Description
The restriction check is designed around `jobUser` (the value derived from the job's declared user, e.g. `image: user: "1000:1001"`), which is validated against `AllowedUsers`/`AllowedGroups` and rejected (returns `-1`/logs a warning) if not permitted, as seen in the test cases: [1](#0-0) 

However, when a `PodSecurityContext.RunAsUser`/`RunAsGroup` or `ContainerSecurityContext.RunAsUser`/`RunAsGroup` is present, it is used to directly override the resulting UID/GID — bypassing the allowlist check entirely, as demonstrated by the test cases explicitly named for this behavior: [2](#0-1) 

The same bypass pattern exists for service containers, where a `ContainerSecurityContext` set on a service overrides the job user and the allowlist entirely, independent of whether the job's own user would have failed validation: [3](#0-2) 

All of these values flow through `getSecurityContextWithUIDGID`, which is exercised directly by the tests: [4](#0-3) 

I was not able to retrieve the exact body of `getSecurityContextWithUIDGID` in `executors/kubernetes/kubernetes.go` within this session's tool-call budget — only its call sites and behavior as documented by the test suite are confirmed above. The precise line-level logic inside the function itself should be verified directly before filing a report.

### Impact Explanation
`AllowedUsers`/`AllowedGroups` is a security control (analogous to `SOFT_RESTRICTED_STAKER_ROLE`) that lets a runner administrator prevent jobs from running as root or other disallowed identities inside build/service/helper containers, which matters especially on non-ephemeral, multi-tenant runners as called out in GitLab Runner's own security documentation: [5](#0-4) 

If a pod/container security context (settable via CI/CD variable overwrite when the admin has enabled the corresponding overwrite-allowed regex, a normal supported customization feature) can override the UID/GID without re-validation, a job could run as `root` or another disallowed UID/GID inside the container despite the administrator's explicit allowlist — defeating the intended isolation/restriction control, the same way the composer bypasses `StakediTry`'s restriction role.

### Likelihood Explanation
This requires the runner administrator to have enabled the pod/container security-context overwrite feature (a legitimate, documented capability, not an inherently "insecure" opt-in like `privileged` mode or `docker.sock` exposure). Given that feature is enabled, any pipeline author able to set the relevant CI/CD variable (typically requiring at least Developer-level trigger access) can exercise the bypass — no trusted-role compromise or admin misconfiguration beyond enabling a documented feature is required.

### Recommendation
In `getSecurityContextWithUIDGID` (and the analogous service-container security-context path), when `AllowedUsers`/`AllowedGroups` are configured, the effective `RunAsUser`/`RunAsGroup` resolved from `PodSecurityContext`/`ContainerSecurityContext` overrides should also be validated against the allowlist before being applied, not just the `jobUser`-derived value.

### Proof of Concept
The existing unit tests already demonstrate the bypass behavior (they assert the bypass succeeds rather than being rejected): [2](#0-1) [3](#0-2) 

Note: I could not confirm within this session whether these test names reflect intentionally-accepted current behavior (i.e., the maintainers consider security-context overrides an intentional escape hatch that supersedes `AllowedUsers`/`AllowedGroups` by design) or an unaddressed gap — this distinction should be verified against `getSecurityContextWithUIDGID`'s full implementation and any related documentation/changelog before treating this as a confirmed, previously-unknown vulnerability.
