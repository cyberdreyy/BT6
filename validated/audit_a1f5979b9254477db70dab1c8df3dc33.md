### Title
Loss-adjusted withdraw receipts are paid at par when a later request overwrites `lastWithdrawRequest` — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
When a stop-epoch loss underfunds pending withdraw receipts, `collectWithdrawFunds` records a per-epoch haircut in `lossRecoveryPriceByEpoch[epochNumber]` and clears `pendingWithdraws`. The claim path only looks up that haircut via `lastWithdrawRequest[_user]`, a single-slot marker that is overwritten on every new `requestWithdraw`. A user who makes a second withdraw request in a later, fully funded epoch causes their old haircutted receipt to bypass `_claimLossAdjustedWithdrawRequest` entirely and be paid at par by `_claimFundedWithdrawRequest`, even though the vault only ever received the discounted funding.

### Finding Description
The bug is a size/bounds-style accounting mismatch analogous to CVE-2020-25085: one code path "writes" a per-epoch haircut indexed by epoch, while the claim path "reads" it through a single stale index.

- `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` when the borrower underfunds receipts [1](#0-0) .
- `_claimLossAdjustedWithdrawRequest` derives the loss epoch solely from `lastWithdrawRequest[_user]` [2](#0-1) .
- `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and aggregates the new request into `withdrawsRequests[_user]` [3](#0-2) .
- `_claimFundedWithdrawRequest` then pays the full `withdrawsRequests[_user]` aggregate at par and burns the receipts, with no per-epoch haircut check [4](#0-3) .

Broken invariant: "one receipt, one haircut-adjusted payout." The per-epoch record `withdrawsRequestsByEpoch[_user][lossEpoch]` retains the correct data, but no claim path consults it once `lastWithdrawRequest` moves past the loss epoch.

### Impact Explanation
Direct theft / insolvency. After a loss epoch funds receipts at e.g. 50%, the vault holds only `pendingBasis * 0.5` for those receipts. Once the same user files any later request and waits one epoch, `claimWithdrawRequest` pays 100% of the aggregate `withdrawsRequests[_user]` via `_transferFundedClaim`, drawing the unfunded difference from underlyings that belong to other pending claimants and instant-withdraw reserve. Quantified loss: `claimBasis_lossEpoch * (1 - lossRecoveryPrice/RECOVERY_FULL)` per affected user, taken from other users' funded claims; sufficient in aggregate to make later claims revert on insufficient balance (permanent freezing of unclaimed withdrawals).

### Likelihood Explanation
Requires a realized `stopEpochWithDuration` loss (honest manager call during borrower underpayment) followed by the same user re-requesting a withdraw — both normal, unprivileged user actions. No privileged-role misbehavior needed. The guard `epochNumber <= lastWithdrawRequest` still passes because a further `stopEpoch` bumps `epochNumber` before the claim. No existing guard (skim, default revert, epoch gating) intercepts this path.

### Recommendation
Iterate `withdrawsRequestsByEpoch` (or track a per-user list of request epochs) in `_claimFundedWithdrawRequest` and apply `lossRecoveryPriceByEpoch` to each epoch's basis rather than keying the haircut off `lastWithdrawRequest`. Alternatively, keep a per-user set of loss epochs so a new request cannot orphan a still-unclaimed haircutted receipt.
