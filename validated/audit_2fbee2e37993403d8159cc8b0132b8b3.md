### Title
Denied Sponsor Bypasses Coin Deny List via `balance_from_sponsor` Withdrawal — (`crates/sui-core/src/authority.rs`)

### Summary

`handle_coin_deny_list_checks` collects coin types from **all** declared withdrawals (including sponsor-sourced ones) but then calls both `check_coin_deny_list_v1` and `check_coin_deny_list_v2_during_signing` with only `tx_data.sender()`. The `gas_owner` (sponsor) is never checked. A denied sponsor can therefore withdraw their regulated coin address-balance via an explicit `FundsWithdrawalArg { withdraw_from: WithdrawFrom::Sponsor, type_arg: Balance(regulated_coin) }` input, bypassing the deny list entirely.

### Finding Description

`handle_coin_deny_list_checks` builds `funds_withdraw_types` by iterating over `declared_withdrawals`, which is the output of `process_funds_withdrawals_for_signing`. That function aggregates **all** withdrawals — both `WithdrawFrom::Sender` and `WithdrawFrom::Sponsor` — into a single map keyed by `AccumulatorObjId`. The map value carries the owner address (`SuiAddress`) for each entry, so the sponsor's address is present in the map. [1](#0-0) 

However, `funds_withdraw_types` only extracts the **coin type string** from each entry — it discards the owner. Both deny-list checks then receive only `tx_data.sender()`: [2](#0-1) 

`FundsWithdrawalArg::balance_from_sponsor` is a public constructor that accepts any `TypeTag` and sets `withdraw_from: WithdrawFrom::Sponsor`: [3](#0-2) 

`owner_for_withdrawal` resolves `WithdrawFrom::Sponsor` to `tx.gas_owner()`: [4](#0-3) 

At execution time the VM correctly resolves the sponsor's address for the withdrawal: [5](#0-4) 

So the signing-time deny-list gate is the only place where the sponsor's address should be checked — and it is not.

### Impact Explanation

A coin issuer denies the sponsor's address for a regulated coin (e.g., USDC). The sponsor still holds a `Balance<USDC>` in their address-balance accumulator. By constructing a sponsored PTB with an explicit `CallArg::FundsWithdrawal(FundsWithdrawalArg { withdraw_from: Sponsor, type_arg: Balance(USDC), ... })`, the sponsor's address is never evaluated against the deny list. The withdrawal proceeds, and the regulated coin balance is transferred out. This directly violates the invariant that denied addresses cannot transact with the regulated coin — the core guarantee of the coin deny list mechanism.

### Likelihood Explanation

The sponsor must sign the transaction (so they are a willing participant in their own bypass). They can use any second address they control as the sender. The `balance_from_sponsor` constructor is public, accepts any `TypeTag`, and there is no signing-time guard restricting it to SUI. The attack requires no privileged access beyond controlling the denied address.

### Recommendation

In `handle_coin_deny_list_checks`, after building `funds_withdraw_types`, also collect the set of **sponsor-sourced coin types** (i.e., entries in `declared_withdrawals` whose owner address equals `tx_data.gas_owner()` and whose type is a non-SUI regulated coin). Run a second deny-list check against `tx_data.gas_owner()` for that subset. Alternatively, restructure the check to iterate over `(owner, coin_type)` pairs from `declared_withdrawals` and check each owner independently.

### Proof of Concept

1. Deploy a regulated coin `RCOIN` and deny `sponsor_addr` via `coin::deny_list_add`.
2. Fund `sponsor_addr`'s address-balance accumulator with `RCOIN`.
3. Construct a `TransactionData` with:
   - `sender = any_addr` (not denied)
   - `gas_data.owner = sponsor_addr` (denied)
   - PTB input: `CallArg::FundsWithdrawal(FundsWithdrawalArg::balance_from_sponsor(amount, rcoin_type_tag))`
4. Sign with both `any_addr` and `sponsor_addr`.
5. Submit. `handle_coin_deny_list_checks` calls `check_coin_deny_list_v1(any_addr, ...)` — `any_addr` is not denied, check passes. `sponsor_addr` is never evaluated.
6. Transaction executes; `sponsor_addr`'s `RCOIN` balance is withdrawn and transferred, despite the active denial. [6](#0-5) [7](#0-6)

    fn handle_coin_deny_list_checks(
        &self,
        tx_data: &TransactionData,
        checked_input_objects: &CheckedInputObjects,
        receiving_objects: &ReceivingObjects,
        epoch_store: &Arc<AuthorityPerEpochStore>,
    ) -> SuiResult<()> {
        use sui_types::balance::Balance;

        let declared_withdrawals = tx_data.process_funds_withdrawals_for_signing(
            self.chain_identifier,
            self.coin_reservation_resolver.as_ref(),
        )?;

        let funds_withdraw_types = declared_withdrawals
            .values()
            .filter_map(|(_, type_tag, _)| {
                Balance::maybe_get_balance_type_param(type_tag)
                    .map(|ty| ty.to_canonical_string(false))
            })
            .collect::<BTreeSet<_>>();

        if epoch_store.coin_deny_list_v1_enabled() {
            check_coin_deny_list_v1(
                tx_data.sender(),
                checked_input_objects,
                receiving_objects,
                funds_withdraw_types.clone(),
                &self.get_object_store(),
            )?;
        }

        if epoch_store.protocol_config().enable_coin_deny_list_v2() {
            check_coin_deny_list_v2_during_signing(
                tx_data.sender(),
                checked_input_objects,
                receiving_objects,
                funds_withdraw_types.clone(),
                &self.get_object_store(),
            )?;
        }

        Ok(())
    }
