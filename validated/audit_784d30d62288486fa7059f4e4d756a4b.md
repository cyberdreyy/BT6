### Title
Token Transfer Replay Guard Keyed Only by Nonce, Not by `(source_chain, nonce)` — Permanent Fund Lock When Multiple Source Chains Are Supported - (File: bridge/evm/contracts/SuiBridge.sol)

### Summary

`SuiBridge.sol` tracks processed token-transfer messages with `mapping(uint64 nonce => bool isProcessed) public isTransferProcessed`. The key is the bare `message.nonce` (the per-source-chain sequence number). When the bridge is configured to accept transfers from more than one source chain — a configuration that is explicitly supported by the protocol (e.g., `ETH_CUSTOM` accepting both `SUI_TESTNET` and `SUI_CUSTOM`) — nonces from different source chains collide in this single namespace. Processing a transfer from source chain A with nonce N permanently blocks the identically-numbered transfer from source chain B, locking the user's bridged tokens forever.

### Finding Description

`BridgeConfig` stores a `mapping(uint8 chainId => bool isSupported) public supportedChains` that is populated with an arbitrary array of source-chain IDs at initialization time. [1](#0-0) 

The `valid_routes()` table in the Move layer explicitly lists routes where two different Sui chains (`SUI_TESTNET = 1` and `SUI_CUSTOM = 2`) both route to the same EVM chain (`ETH_CUSTOM = 12`): [2](#0-1) 

On the EVM side, `SuiBridge` stores the processed-transfer guard as:

```solidity
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
``` [3](#0-2) 

`transferBridgedTokensWithSignatures` checks and sets this mapping using only `message.nonce`:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
// ...
isTransferProcessed[message.nonce] = true;
``` [4](#0-3) 

The same pattern is repeated verbatim in `SuiBridgeV2.transferBridgedTokensWithSignaturesV2`: [5](#0-4) 

Crucially, `MessageVerifier.verifyMessageAndSignatures` performs the chain-ID check **only for non-TOKEN_TRANSFER message types**; for token transfers it is skipped entirely:

```solidity
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    require(
        message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID"
    );
    ...
}
``` [6](#0-5) 

Each source chain's bridge contract maintains its own independent nonce counter starting at 0. When two source chains are both accepted by the same EVM bridge deployment, their nonce sequences are identical (0, 1, 2, …) and will collide in the shared `isTransferProcessed` map from the very first transfer.

### Impact Explanation

When an `ETH_CUSTOM` bridge is configured to accept both `SUI_TESTNET` and `SUI_CUSTOM`:

1. User A bridges tokens from `SUI_TESTNET` → nonce 0 is processed → `isTransferProcessed[0] = true`.
2. User B bridges tokens from `SUI_CUSTOM` → nonce 0 → `require(!isTransferProcessed[0])` reverts with `"SuiBridge: Message already processed"`.
3. User B's tokens were already burned/locked on the Sui side; they can never be claimed on the EVM side. The funds are permanently lost.

This matches the **permanent fund lock** impact class (High/Medium) in the allowed-impact gate.

### Likelihood Explanation

The collision is **deterministic and inevitable**: both source chains start their nonce counters at 0. The very first transfer from the second source chain will collide with the first transfer from the first source chain. No special attacker action is required; ordinary bridge users trigger the condition simply by using the bridge normally. The only prerequisite is a bridge deployment that lists more than one Sui source chain in `supportedChains`, which the protocol's own route table explicitly anticipates.

### Recommendation

Key the processed-transfer guard by the composite `(source_chain, nonce)` pair instead of bare nonce:

```solidity
// Before
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
require(!isTransferProcessed[message.nonce], ...);
isTransferProcessed[message.nonce] = true;

// After
mapping(uint8 sourceChain => mapping(uint64 nonce => bool isProcessed)) public isTransferProcessed;
require(!isTransferProcessed[message.chainID][message.nonce], ...);
isTransferProcessed[message.chainID][message.nonce] = true;
```

Apply the same fix to `SuiBridgeV2.transferBridgedTokensWithSignaturesV2`.

### Proof of Concept

Assume an `ETH_CUSTOM` bridge initialized with `supportedChains = [SUI_TESTNET, SUI_CUSTOM]`.

1. **Transfer 1** — source `SUI_TESTNET`, nonce 0, recipient `alice`:
   - `verifyMessageAndSignatures` passes (signatures valid, chain-ID check skipped for TOKEN_TRANSFER).
   - `onlySupportedChain(SUI_TESTNET)` passes.
   - `isTransferProcessed[0]` is `false` → transfer executes, tokens sent to `alice`.
   - `isTransferProcessed[0]` set to `true`.

2. **Transfer 2** — source `SUI_CUSTOM`, nonce 0, recipient `bob` (tokens already burned on Sui):
   - `verifyMessageAndSignatures` passes.
   - `onlySupportedChain(SUI_CUSTOM)` passes.
   - `require(!isTransferProcessed[0])` → **reverts**: `"SuiBridge: Message already processed"`.
   - `bob`'s tokens are permanently locked; no recovery path exists.

The root cause is the same class as the EIP712 DOMAIN_SEPARATOR bug: the replay-protection domain does not include the full message context (source chain identity), so messages from distinct domains share a single nonce namespace and collide.
