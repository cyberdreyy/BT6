## Finding

Front-running an unauthenticated `lockup-factory` `create()` call lets an attacker permanently install a malicious `staking_pool_whitelist_account_id` on a victim's deterministic lockup account before the legitimate funder's transaction lands.

### Title
Front-runnable, deterministic lockup account ID in `LockupFactory::create` allows an attacker to seed a victim's lockup with a malicious staking-pool whitelist - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the to-be-created lockup account solely from `sha256(owner_account_id)` and accepts an attacker-supplied `whitelist_account_id` override with no restriction on who may call it. Because the resulting account ID is fully deterministic and independent of the caller, an unprivileged attacker who observes a pending, legitimate `create` transaction in the mempool for a given `owner_account_id` can front-run it with their own `create` call (cheaper deposit, malicious whitelist), permanently claiming that lockup account before the victim's transaction executes.

### Finding Description
`create()` computes the lockup account deterministically from only `owner_account_id`: [1](#0-0) 

There is no check binding the call to a specific funder, no reservation/commit step, and the `staking_pool_whitelist_account_id` used to initialize the lockup is fully attacker-controllable via the optional `whitelist_account_id` parameter, defaulting only if omitted: [2](#0-1) 

An attacker Bob who sees Alice's pending `create(owner_account_id="carol", ..., whitelist_account_id=None)` transaction (intending to fund Carol's lockup with the legitimate foundation whitelist) can submit `create(owner_account_id="carol", ..., whitelist_account_id=Some("bob-fake-whitelist"))` with just the `MIN_ATTACHED_BALANCE` (3.5 NEAR) and have it mined first, since the deterministic account ID `sha256("carol").<factory>` is identical either way: [3](#0-2) 

When Alice's original transaction then executes, `Promise::new(lockup_account_id).create_account()` fails because the account already exists, and the whole batch fails; the callback refunds Alice's deposit but does nothing to remove or fix Bob's already-deployed lockup: [4](#0-3) 

The result: Carol (the intended beneficiary) ends up owning a lockup contract that was deployed and initialized by Bob, with `staking_pool_whitelist_account_id` pointing at Bob's contract instead of the NEAR-Foundation-controlled whitelist. This whitelist is exactly the trust boundary the lockup relies on when the owner delegates NEAR to a staking pool: `select_staking_pool` only checks the pool against `self.staking_pool_whitelist_account_id`, whatever that has been set to: [5](#0-4) [6](#0-5) 

The whitelist's entire purpose, per the project's own documentation, is to guarantee that delegated tokens "can not be lost, locked, or stolen" by only approving vetted staking-pool code: [7](#0-6) [8](#0-7) 

By substituting a whitelist contract that Bob fully controls (e.g., one that always returns `is_whitelisted == true`), Bob can later cause Carol to delegate her locked NEAR to a "staking pool" that Bob's fake whitelist blesses but that is not the vetted spec-compliant staking pool contract — breaking exactly the binding the whitelist is supposed to guarantee (approved-whitelist code vs. arbitrary attacker code).

This is the same bug class as the referenced report: a security-critical parameter (`parameterize`/`staking_pool_whitelist_account_id`) of a not-yet-finalized deployment is mutable by an unprivileged third party who can front-run the legitimate actor's transaction, permanently locking in attacker-chosen values because the target identity (proposal / deterministic account) is public and fixed ahead of time.

### Impact Explanation
This is a Critical-severity "wrongly parameterised deployment": the deployed lockup's `staking_pool_whitelist_account_id` — the sole gate controlling which staking pools the owner is permitted to delegate to — is substituted by an unprivileged attacker instead of being set to the NEAR-Foundation-approved whitelist, which can lead to the owner's locked/unvested NEAR being lost or stolen when staking through a pool that the swapped whitelist wrongly approves.

### Likelihood Explanation
Any transaction to `create` a lockup for a well-known `owner_account_id` is visible in the mempool prior to inclusion; the attacker only needs to submit a competing transaction with a higher priority/gas or simply race it, and the required deposit is the same minimal `MIN_ATTACHED_BALANCE` already used to fund any lockup, so the cost of the attack is low. The victim's transaction itself does not need to specify a custom whitelist for the attack to matter — omitting `whitelist_account_id` in the legitimate call is the common case and is exactly what the attacker's front-run overrides.

### Recommendation
Do not derive the lockup account ID purely from `owner_account_id`; alternatively, require `create` to be restricted to (or co-signed by) the account paying/predecessor that matches the intended owner or a pre-registered funder, and/or disallow overriding `staking_pool_whitelist_account_id` entirely except when called by the foundation, always defaulting to the factory's configured whitelist for user-initiated creations.

### Proof of Concept
1. Alice prepares `create(owner_account_id="carol", lockup_duration=..., vesting_schedule=None, whitelist_account_id=None)` with `attached_deposit = 35 NEAR`, intending to fund Carol's lockup using the default (foundation) whitelist.
2. Bob observes this pending transaction and submits `create(owner_account_id="carol", lockup_duration=..., vesting_schedule=None, whitelist_account_id=Some("bob-fake-whitelist"))` with `attached_deposit = MIN_ATTACHED_BALANCE (3.5 NEAR)`, referencing the same deterministic account `sha256("carol").<factory>` computed at `lockup-factory/src/lib.rs:119-121`.
3. Bob's transaction is included first, successfully creating and initializing the lockup at that deterministic address with `staking_pool_whitelist_account_id = "bob-fake-whitelist"`.
4. Alice's transaction executes afterward; `create_account()` on the already-existing address fails, the whole promise batch fails, and `on_lockup_create` refunds Alice's 35 NEAR — but Carol's lockup remains the one Bob deployed.
5. Later, Carol (owner) calls `select_staking_pool("bobs-malicious-pool")`; because `staking_pool_whitelist_account_id` points to Bob's contract, it returns `is_whitelisted = true` regardless of the pool's actual behavior, letting Carol delegate to an unvetted/malicious staking pool contract that Bob controls.

### Staking

NEAR is the proof of stake network. The owner of the lockup contract might hold a large percentage of the network tokens.
The owner may want to stake these tokens (including locked/unvested tokens) to help secure the network and also earn staking rewards that are distributed to the network validator.
This contract doesn't allow to directly stake from this account, so the owner can delegate tokens to a [staking pool contract](https://github.com/near/initial-contracts/tree/master/staking-pool).

The owner can choose the staking pool for delegating tokens.
The staking pool contract and the account have to be approved by the whitelisting contract to prevent tokens from being lost, locked, or stolen.
Whitelisting contract is set at the moment of initializing the Lockup contract by [`staking_pool_whitelist_account_id`](https://github.com/near/core-contracts/blob/master/lockup/src/lib.rs#L190) field.
Once the staking pool holds tokens, the owner of the staking pool can use them to vote on the network governance issues, such as enabling transfers.
So the owner needs to pick the staking pool that fits the best.

**File:** whitelist/README.md (L3-19)
```markdown
The purpose of this contract is to maintain the whitelist of the staking pool contracts account IDs that are approved
by NEAR Foundation.

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.
The staking pool should guarantee that the delegated tokens can not be lost or locked, such as the lockup contract should be
able to recover delegated tokens back to the lockup from a staking pool. In order to enforce this, only approved (whitelisted)
accounts of staking pool contracts can receive delegated tokens from lockup contracts.

If NEAR Foundation has to approve every single staking pool account it might lead to a bottleneck and centralization
To address this NEAR Foundation can whitelist the account IDs of staking pool factory contracts.

The whitelisted staking pool factory contract will be able to whitelist accounts of staking pool contracts.
A factory contract creates and initializes a staking pool contract in a secure and permissionless way.
This allows anyone on the network to be able to create a staking pool contract for themselves without needing approval from the NEAR
Foundation. This is important to maintain the decentralization of the decision making and network governance.

To be able to address mistakes, NEAR Foundation has the ability to remove staking pools and staking pool factories from the whitelists.
```
