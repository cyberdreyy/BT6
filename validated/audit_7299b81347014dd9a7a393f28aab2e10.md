### Title
Unprivileged ERC4626 vault liquidity drain indefinitely blocks `stopEpoch`, freezing all tranche withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
In programmable-borrower mode, `IdleCDOEpochVariant.stopEpoch` resolves epoch interest from `ProgrammableBorrower.totalInterestDueNow()` and then calls `ProgrammableBorrower.onStopEpoch`, which must pull any on-hand shortfall out of the external ERC4626 vault. If the vault position economically covers the shortfall (`shortfall <= _currentVaultAssets()`) but the vault does not have enough *instantly withdrawable* liquidity, `vault.withdraw` reverts and the catch block reverts `StopEpochVaultLiquidityUnavailable`, reverting the whole `stopEpoch`. An unprivileged user of the borrower's ERC4626 vault can withdraw available vault liquidity (or borrow it, in lending-style vaults) right before each settlement attempt — the same "attack the thin liquidity venue" pattern as the Cascade incident — keeping the epoch un-settled and every pending withdraw receipt frozen.

### Finding Description
`onStopEpoch` in `contracts/strategies/idle/ProgrammableBorrower.sol:239-253`:

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

Two observations:

1. `_currentVaultAssets()` is `vault.convertToAssets(shares)` (`ProgrammableBorrower.sol:546-549`), i.e., the *economic* value of the position. `vault.withdraw` instead depends on the vault's *available liquidity* (`maxWithdraw`). For ERC4626 vaults that lend or re-deploy assets (the intended use: "keep undrawn capital parked inside an ERC4626 vault"), `maxWithdraw` can be far below `convertToAssets`. So the guard at line 245 passes the withdrawal into the `try` while liquidity is insufficient.

2. The `catch` reverts the entire transaction instead of letting the epoch settle with what's available. `stopEpoch` in `IdleCDOEpochVariant` therefore reverts atomically: `epochNumber` in `IdleCreditVault` is never incremented (`IdleCreditVault.sol:326` requires `epochNumber > lastWithdrawRequest` for claims), so all `withdrawsRequests`/`instantWithdrawsRequests` receipts are unclaimable, and interest accounting never finalizes.

Attack sequence (running epoch, programmable mode):
- Attacker (any holder of shares in the ERC4626 vault the facility uses — explicitly an unprivileged actor) monitors mempool/timing for `stopEpoch` calls after `epochEndDate`.
- Attacker calls `vault.withdraw`/`redeem` (or borrows, if the vault is a lending market) to drain available liquidity below `shortfall` while keeping `convertToAssets` above it.
- Every `stopEpoch`/`stopEpochWithDuration` call reverts with `StopEpochVaultLiquidityUnavailable`. `onDefault` cannot be triggered either — that path is reached only after the hook returns and `transferFrom` fails; a reverting hook never reaches it.
- The epoch stays `isEpochRunning == true` with `block.timestamp > epochEndDate`; depositors cannot request new withdrawals meaningfully (claims still gated on `epochNumber`), and existing receipts cannot be paid.

The attacker only needs to keep vault liquidity thin — they earn their normal vault yield meanwhile and can unwind at will, making the griefing cheap and repeatable each time liquidity refills.

### Impact Explanation
Temporary freezing of funds with quantifiable scope: while the attack is active, 100% of tranche-holder principal plus accrued epoch interest is locked — no claims (`claimWithdrawRequest`, `claimInstantWithdrawRequest`), no new epoch, no close-pool settlement, and no default path (the revert happens before the `transferFrom` failure that triggers default handling). Epochs cannot roll, so NAV never crystallizes. The freeze persists exactly as long as the attacker maintains vault illiquidity; for a utilization-based vault the attacker pays only the opportunity cost/fee of holding the borrowed/withdrawn position, while pool TVL (potentially millions in underlying) is stuck. This mirrors the Cascade incident mechanically: manipulate the state of a low-liquidity external venue at the precise settlement moment to weaponize a protocol flow that assumes that venue is liquid.

### Likelihood Explanation
- The `try/catch` + retryable design explicitly anticipates transient illiquidity, but nothing bounds how long it can last, and there is no fallback path (e.g., settling with partial liquidity, redeeming shares pro-rata, or escalating to default after N failed stops).
- The attacker needs no privilege: holding shares in the chosen ERC4626 vault suffices, and vault choice is external to attacker control requirements.
- Cost to sustain the attack is limited to the vault's own withdrawal/borrow costs; the attacker can target only the settlement window and repeat opportunistically.
- Guarded: this only applies to deployments with `isProgrammableBorrower == true`; non-programmable pools are unaffected. Standard (non-vault) borrowers are also unaffected.
- Caveat I could not fully verify: whether production deployments actually point `vault` at a liquidity-constrained ERC4626 (vs. an always-liquid wrapper). If the configured vault always satisfies `maxWithdraw == convertToAssets`, the issue reduces to design hardening.

### Recommendation
- Make the failure mode liveness-safe instead of reverting: on a failed `vault.withdraw`, return a distinct status so `IdleCDOEpochVariant` can either settle with available liquidity, enter a bounded "pending settlement" state that still lets funded receipts be claimed, or escalate to default handling after a grace period.
- Alternatively, use `vault.redeem(shares)` proportional to what's actually withdrawable (`vault.maxWithdraw(address(this))`) rather than a fixed-asset `withdraw`, and account the realized delta via `epochWithdrawnFromVault`.
- Add a permissionless/keeper deadline: if `block.timestamp > epochEndDate + maxSettlementDelay` and the vault withdrawal keeps failing, allow the epoch to be force-stopped with the realized amount, crystallizing any shortfall through the existing BB-first loss waterfall rather than reverting.

```solidity
pragma solidity 0.8.10;

import "forge-std/Test.sol";

contract StopEpochLiquidityFreezePoC is Test {
    // cdoEpoch: IdleCDOEpochVariant with isProgrammableBorrower = true
    // pb: ProgrammableBorrower, vault: ERC4626 whose maxWithdraw < convertToAssets

    function testStopEpochFrozenByVaultLiquidityDrain() external {
        // 1. Setup: KYC'd lender deposits AA during buffer; manager starts epoch.
        //    onStartEpoch deposits idle funds into the ERC4626 vault.
        //    Lender calls requestWithdraw -> pendingWithdraws > 0.

        // 2. Warp past epochEndDate.
        vm.warp(cdoEpoch.epochEndDate() + 1);

        // 3. Attacker (unprivileged vault shareholder) drains vault liquidity so
        //    vault.maxWithdraw(address(pb)) < shortfall, while
        //    vault.convertToAssets(pbShares) >= shortfall.
        vm.prank(attacker);
        vault.withdraw(vault.maxWithdraw(attacker), attacker, attacker);

        // 4. Every manager stopEpoch reverts; epochNumber never increments.
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdoEpoch.stopEpoch(0, 0);

        // repeat: attacker keeps liquidity drained; settlement stays blocked
        assertTrue(cdoEpoch.isEpochRunning());
        assertEq(creditVault.epochNumber(), epochBefore);

        // 5. Lender receipt is unclaimable because epoch never rolled.
        vm.expectRevert(NotAllowed.selector);
        cdoEpoch.claimWithdrawRequest();
    }
}
```

Expected result: `stopEpoch` reverts on each attempt for as long as vault liquidity is suppressed; all pending receipts remain frozen with no default-path escape, matching the loss socialization/liveness impact class.
