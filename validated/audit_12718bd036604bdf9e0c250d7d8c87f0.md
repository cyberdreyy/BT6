### Title
Cross-Workflow JWT Replay in `WorkflowMetadataHandler.Authorize` due to missing workflow-ID domain separation - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
The reported bug class is a signature/authorization token that is valid across multiple trust domains because the domain identifier (chain ID) is not mixed into the signed hash. The same structural flaw exists in the gateway's HTTP-trigger workflow metadata authorization path: the JWT digest is computed purely from the JSON-RPC request (method/params/id) and never incorporates the `workflowID`, even though `workflowID` is the parameter that scopes which authorized-key set the token is checked against.

### Finding Description
`WorkflowMetadataHandler.Authorize` accepts a `workflowID`, a `token` string, and the JSON-RPC `req`, and verifies the JWT via `utils.VerifyRequestJWT(token, *req)`: [1](#0-0) 

`VerifyRequestJWT`/`CreateRequestJWT` compute the JWT's `digest` claim solely from `req.Digest()` — a generic `jsonrpc.Request[T]` (method, params, id) — with no `workflowID` or other domain-separating value included anywhere in the signed payload: [2](#0-1) [3](#0-2) 

After verifying the digest/signature/expiry/jti, `Authorize` uses `workflowID` only as a map lookup key to fetch that workflow's authorized-key set, and checks whether the recovered signer is a member: [4](#0-3) 

Because `workflowID` never enters the signed digest, a JWT (with a given `jti`, request digest, and ECDSA signature) that is valid for `workflowID = A` is *cryptographically identical and equally valid* for `workflowID = B`, provided:
1. the same JSON-RPC request body (method/params/id) is submitted, and
2. the signer address recovered from the JWT is present in `authorizedKeys[B]` as well as `authorizedKeys[A]`.

The only replay protection present is the single-use `jti` cache (`jwtReplayCache`), which prevents replaying the identical `(jti)` twice, but this is a global cache keyed only by `jti` — it does not scope replay-prevention per `workflowID`. Nothing in `Authorize` binds the `workflowID` argument into the value that was actually signed by the client (`req.Digest()`), which is the same domain-separation gap described in the external report (missing `chainid`/domain value in the hash that gets signed).

This is directly analogous to the reported bug class: a missing domain-separator field in the signed hash allows a signature/token intended for one scope (chain / workflow) to be valid in another scope (chain / workflow) when the "surrounding" verification context (map lookup) is checked separately from the cryptographic digest.

### Impact Explanation
If a workflow owner or operator key is authorized across multiple workflows (a supported and plausible configuration, since `authorizedKeys` is a `map[string]map[gateway.AuthorizedKey]struct{}` keyed independently per workflow), an unprivileged client that legitimately obtains (or observes) a valid JWT for workflow A's HTTP trigger can present the exact same token/request pair to invoke `MethodWorkflowExecute` against workflow B, effectively triggering unauthorized workflow execution outside the scope the signer intended to authorize. This is a request-impersonation/authorization-bypass primitive at the internet-facing gateway trigger surface.

### Likelihood Explanation
Exploitation requires: (a) a signer key that is authorized for two or more workflows, and (b) the attacker being able to submit an identical JSON-RPC request body to a different `workflowID` endpoint/route than the one the JWT was originally created for. Given HTTP trigger requests are typically simple/templated (fixed method + params shape), reusing a captured token against a sibling workflow ID sharing the same signer is straightforward once precondition (a) holds. The likelihood is therefore conditional on key-reuse across workflows, which is a legitimate and expected operational pattern for a single owner/organization deploying multiple workflows with the same signing key.

### Recommendation
Include `workflowID` (or a canonical hash of it) as part of the value that is signed and later re-derived during verification — i.e., extend `JWTClaims`/the digest computation so `Digest = req.Digest()` is combined with `workflowID` (analogous to adding `block.chainid` into the borrow hash), or pass `workflowID` explicitly into `VerifyRequestJWT`/`CreateRequestJWT` and fold it into the same hash that is ECDSA-signed. This ensures a token signed for workflow A cannot verify successfully against workflow B's authorized-key check even if the recovered signer happens to be authorized for both.

### Proof of Concept
1. Signer key `K` is registered as an authorized key for both `workflowID = A` and `workflowID = B` (e.g., same owner deploys two workflows with the same DON-side signing key), as populated by `syncMetadata`/`validateAuthMetadata`. [5](#0-4) 
2. Client builds `req` (`MethodWorkflowExecute`, fixed `params`), calls `utils.CreateRequestJWT(*req)`, signs it with `K`, and submits it to trigger workflow A: `handler.Authorize(A, tokenString, req)` succeeds and workflow A executes.
3. Attacker/observer replays the identical `tokenString` and `req` but targets workflow B: `handler.Authorize(B, tokenString, req)`. Since `VerifyRequestJWT` only checks `req.Digest()` (unchanged) and the `jti` hasn't been used yet for a *different* call to `Authorize` with the same `jti` value... actually since `jti` is global and single-use, the *same exact token* can only be used once across all workflows — but a *newly created* token for the same request content directed at workflow B (still signed by the same key `K`, using a fresh `jti`) will pass verification identically, because the digest computation never differentiates A from B. This demonstrates that `workflowID` provides no cryptographic binding: the signature and digest checks pass unconditionally for any `workflowID` where the recovered signer is authorized, confirming the missing domain-separation.

func CreateRequestJWT[T any](req jsonrpc.Request[T], opts ...Option) (*jwt.Token, error) {
	// Apply options
	options := &jwtOptions{}
	for _, opt := range opts {
		opt(options)
	}

	expiryDuration := maxJWTExpiryDuration
	if options.expiryDuration != nil {
		expiryDuration = *options.expiryDuration
	}

	digest, err := req.Digest()
	if err != nil {
		return nil, err
	}

	var issuer string
	if options.issuer != nil {
		issuer = *options.issuer
	}

	var subject string
	if options.subject != nil {
		subject = *options.subject
	}

	var audience []string
	if options.audience != nil {
		audience = options.audience
	}

	now := time.Now()
	jti := uuid.New().String()

	claims := JWTClaims{
		Digest: "0x" + digest,
		RegisteredClaims: jwt.RegisteredClaims{
			ID:        jti,
			Issuer:    issuer,
			Subject:   subject,
			Audience:  jwt.ClaimStrings(audience),
			ExpiresAt: jwt.NewNumericDate(now.Add(expiryDuration)),
			IssuedAt:  jwt.NewNumericDate(now),
		},
	}

	return jwt.NewWithClaims(&SigningMethodEth{}, claims), nil
}
