### Title
Legacy Webhook-type jobs with int32 IDs bypass the UUID-based webhook-removal guard and can still be triggered via `RunJobV2` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` only blocks webhook job runs when the supplied `:ID` parses as a UUID [1](#0-0) , but any job — including a legacy `Webhook`-type job whose primary key is a normal int32 (as all `jobs` rows use) — that is addressed by its int32 ID skips this check entirely and is passed straight to `prc.App.RunJobV2(ctx, jobID, nil)` [2](#0-1) . The `job.ErrJobTypeRemoved` enforcement that exists in the codebase is only present in the job-creation path (`core/services/job/orm.go`), not in the run-execution path, so a pre-existing Webhook job is not re-validated for its type before a run is created.

### Finding Description
The comment at line 103 explains the intent: "Webhook runs used external job UUIDs; that job type has been removed," and the code assumes the *only* way a client could address a Webhook job is via its old UUID-based external ID. If that assumption is false — e.g. a Webhook-type job persisted in the `jobs` table before the type was retired still has (and is always addressable by) its normal int32 primary key — then the `uuid.Parse(idStr)` check at line 104 never fires for that job, and execution falls through to the `isUser` branch, where `strconv.ParseInt` succeeds and `RunJobV2` is invoked unconditionally for any int32 ID, with no re-check of `job.Type` against the removed-type list [2](#0-1) . Grepping the codebase shows `job.ErrJobTypeRemoved` is referenced only in `core/services/job/orm.go` (creation-time validation) and `core/web/resolver/mutation.go` (GraphQL job-creation mutation), never in the run-execution call chain from `PipelineRunsController.Create` → `Application.RunJobV2`, meaning there is no equivalent guard at run time. The only defense against running a webhook-type job is the format-based UUID heuristic, not an actual type check, so it is bypassed whenever the job is (still) reachable by an int32 ID.

### Impact Explanation
A run-role authenticated user (an explicitly in-scope, low-privileged attacker per the rules) can trigger execution of a job type (`Webhook`) that the product intentionally disallows from running, via `POST /v2/jobs/<intID>/runs`. This is an authorization/validation bypass resulting in "unauthorized job run" — the exact impact class called out in the rules — potentially causing unintended pipeline execution, resource consumption, or triggering side effects tied to a job that should be inert.

### Likelihood Explanation
Exploitability depends on the precondition that a Webhook-type job row still exists in the database (e.g., created before the type was removed) and remains addressable by its int32 ID rather than only its now-unsupported UUID. Given that all jobs share the same `jobs` table and int32 primary key regardless of type, this precondition is plausible on any node that was upgraded rather than created fresh after the Webhook type removal. The attacker only needs run-role credentials and knowledge (or enumeration) of the job's int32 ID — no admin/operator access is required, matching the allowed attacker profile.

### Recommendation
Perform the job-type check at run time as well as creation time: after resolving the job (or before invoking `RunJobV2`), look up the job's `Type` and reject with `job.ErrJobTypeRemoved` if it is `job.Webhook`, rather than relying solely on the UUID-format heuristic in `PipelineRunsController.Create`.

### Proof of Concept
1. Seed a job row directly with `Type = job.Webhook` and a pipeline spec, having it assigned a normal int32 ID (simulating a legacy row that predates the webhook-type removal).
2. As a run-role authenticated test user, call `POST /v2/jobs/<intID>/runs`.
3. Assert the current behavior: the request succeeds and returns a `pipelineRun` resource (200/201), instead of returning `422 Unprocessable Entity` wrapping `job.ErrJobTypeRemoved` as intended.
4. Contrast with calling the same endpoint using the job's UUID (if one exists) to show the UUID-guard correctly returns the `ErrJobTypeRemoved` error, confirming the int32 path is the only bypass vector.
