### Title
Mid-epoch `isInterestMinted` toggle causes cash-vs-mint accounting imbalance at `stopEpoch` - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
The VLAN bug is a refcount imbalance: a resource is added at device-up only if a feature flag is set, and removed at device-down only if the flag is still set — toggling the flag between the two lifecycle events leaks or double-frees the resource. The direct analog in `IdleCDOEpochVariant` is `isInterestMinted`. `startEpoch` reads the flag to decide whether the borrower must return epoch interest in cash, and `stopEpoch` reads the flag again to decide whether to pull that cash or simply mint unbacked strategy tokens. Unlike `setIsProgrammableBorrower` (line 178: `_checkNotAllowed(isEpochRunning)`), `setIsInterestMinted` (line 166-170) has **no `isEpochRunning` guard**, so the flag can be toggled between the paired accounting events.

### Finding Description
At `startEpoch` (line 273) the flag decides `_toSend = isInterestMinted ? _totEpochDeposits : lastEpochInterest + _totEpochDeposits`, i.e. whether prior-epoch interest cash is pushed to the strategy. At `stopEpoch` (lines 374-376) the flag is read again: `bool _mintInterest = isInterestMinted && !_isRequestingAllFunds;` and `uint256 _amountToPullFromBorrower = _mintInterest ? 0 : _expectedInterest;`. If `_mintInterest` is true, the borrower is never asked to repay `expectedEpochInterest` in cash; instead line 430 mints `_grossInterest` strategy tokens (`_strategy.mintStrategyTokens(_grossInterest)`) that are backed by nothing.

Sequence (non-programmable pool, where the setter is unrestricted):
1. Buffer: `isInterestMinted == false`; deposits, epoch starts normally. The borrower's contractual obligation for `expectedEpochInterest` is a cash repayment at `stopEpoch`.
2. During the running epoch, the owner (honest privileged role — allowed under the scope rules as a sequenced precondition, exactly like the `ethtool -K` toggle in the kernel report) calls `setIsInterestMinted(true)`. No revert, because the only check is `!_isMinted && isProgrammableBorrower`.
3. At `stopEpoch`, `_mintInterest == true`, so `_amountToPullFromBorrower = 0`. The borrower's interest cash is never pulled (`getFundsFromBorrower(_pendingWithdraws)` only), yet `mintStrategyTokens(_grossInterest)` mints strategy tokens 1:1 with the unpaid interest, and `unclaimedFees += _pendingWithdrawFees` plus share mints to `feeReceiver`/`owner` further dilute NAV.

There is no later code path that pulls the skipped interest: `expectedEpochInterest` is reset to 0 at line 475. The minted strategy tokens are permanently backed only by the borrower's goodwill, since nothing in the contract can recover that specific debt after the stop.

Broken invariant: strategy-token supply must equal real underlying backing (fair mint/burn). The phantom `mintStrategyTokens` inflates `getContractValue`/`tranchePrice`, so withdrawal requests priced off the inflated NAV are paid out of the strategy's real principal cash — early claimants are overpaid at the expense of remaining LPs, i.e. insolvency/socialized loss. This mirrors CVE-2025-38470 exactly: both ends of a paired add/remove operation key off the current value of a mutable flag instead of the value recorded when the resource was created.

### Impact Explanation
An attacker holding tranche tokens (a KYC-passing lender — an in-scope unprivileged role) requests a withdrawal during the buffer after this toggle sequence, and `claimWithdrawRequest` pays out at the inflated tranche price from real pool cash. Loss bounded by `expectedEpochInterest` (plus the fee-minted shares), extracted from principal belonging to other LPs — up to the full epoch interest for a large pool. If `isInterestMinted` was instead true at start and flipped false before stop, the asymmetry inverts (cash pulled for an epoch whose accounting assumed minting, plus `sendInterestAndDeposits` mismatches at the next start), producing an equivalent bookkeeping skew.

### Likelihood Explanation
Requires only an owner/manager calling `setIsInterestMinted` during a running epoch — a routine configuration action the contract explicitly permits (the sibling setter blocks it, suggesting this guard was simply missed on this flag). The attacker needs only to be a tranche holder sequencing `requestWithdraw`/`claimWithdrawRequest` around the honest privileged calls. No borrower misbehavior, no oracle, no external vault needed.

### Recommendation
Mirror the kernel fix: record the interest-settlement mode when the epoch is *opened* and use the recorded value at stop, rather than re-reading a mutable flag. Concretely, add `_checkNotAllowed(isEpochRunning)` to `setIsInterestMinted` (matching `setIsProgrammableBorrower`), or snapshot `epochInterestMinted = isInterestMinted` in `startEpoch` and use that snapshot for `_mintInterest` in `_stopEpoch`.

### Proof of Concept
Foundry fork sketch (using the existing harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testMidEpochInterestMintedToggleUnbackedMint() external {
    uint256 amount = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amount);        // attacker LP deposits
    idleCDO.depositBB(amount);
    _startEpochAndCheckPrices(0);     // epoch starts with isInterestMinted == false

    // owner (honest, sequenced precondition) flips the flag mid-epoch
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    uint256 expectedInt = cdoEpoch.expectedEpochInterest();
    uint256 stratBefore = IERC20(strategyToken).totalSupply();

    // borrower funds only the withdraw-request liability; no interest cash is pulled
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, IdleCreditVault(address(strategy)).pendingWithdraws());
    vm.prank(manager);
    cdoEpoch.stopEpoch(newApr, 0);

    // strategy tokens were minted for interest that was never paid in cash
    assertEq(
        IERC20(strategyToken).totalSupply() - stratBefore,
        expectedInt,
        "unbacked strategy tokens minted"
    );

    // attacker's withdraw request is priced off inflated NAV and paid from real cash
    uint256 bal = cdoEpoch.requestWithdraw(0, address(AAtranche));
    cdoEpoch.claimWithdrawRequest();  // overpaid; remaining LPs absorb the shortfall
}
```
