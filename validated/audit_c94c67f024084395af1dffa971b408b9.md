### Title
Rejection tally silently drops votes across different blocks due to a mis-scoped `PRIMARY KEY` on `block_rejection_signer_addrs` - (File: `stacks-signer/src/signerdb.rs`)

### Summary
The signer's local rejection-vote table `block_rejection_signer_addrs` is keyed only by `signer_addr`, not by the `(signer_signature_hash, signer_addr)` pair that the code's own query logic assumes. This is the exact bug class from the external report: a shared/under-scoped key (there, a PDA missing `asset_mint`; here, a SQL table missing `signer_signature_hash` from its primary key) causes state belonging to one "instance" (there, a bridge/mint; here, one block proposal) to silently clobber or block state for another instance that happens to reuse the same partial key (there, `(chain, emitter)`; here, `signer_addr`). The result is that a signer's valid, authenticated rejection of a second block is silently dropped from the local tally, permanently under-counting the rejection weight used to decide whether a block is `GloballyRejected`.

### Finding Description
The table is declared as: [1](#0-0) 

```rust
static CREATE_BLOCK_REJECTION_SIGNER_ADDRS_TABLE: &str = r#"
CREATE TABLE IF NOT EXISTS block_rejection_signer_addrs (
    signer_signature_hash TEXT NOT NULL,
    signer_addr TEXT NOT NULL,
    PRIMARY KEY (signer_addr)
) STRICT;"#;
```

The `PRIMARY KEY` is `signer_addr` alone, even though the comment directly above it (copied from the sibling `block_signatures`/`block_rejection` design intent) explains that `signer_signature_hash` is supposed to disambiguate different blocks/forks. Because of `STRICT` table semantics and no `ON CONFLICT`/`OR REPLACE` clause, SQLite enforces global uniqueness of `signer_addr` across the *entire* table, i.e., across every block hash ever seen, not per-block.

`add_block_rejection_signer_addr` however is written as if the composite `(signer_signature_hash, signer_addr)` were unique per row: [2](#0-1) 

It first checks for an existing row scoped to `(block_sighash, addr)`. If a signer previously rejected a *different* block hash, that lookup returns `None` (no match on `signer_signature_hash`), so the code falls into the `None` branch and issues a plain `INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (...)`. Because a row for that same `signer_addr` already exists (tied to the earlier, different block hash), this `INSERT` violates the `PRIMARY KEY (signer_addr)` constraint and fails with a `DBError`.

The caller, `store_and_process_block_rejection`, treats this as a soft failure and simply logs a warning, returning without recording the vote: [3](#0-2) 

```rust
match self.signer_db.add_block_rejection_signer_addr(
    block_hash,
    signer_address,
    reject_reason,
) {
    Err(e) => {
        warn!("{self}: Failed to save block rejection signature: {e:?}",);
    }
    Ok(false) => return, // We already have this signature, do not process it again.
    Ok(true) => (),
}
...
let rejection_addrs = match self.signer_db.get_block_rejection_signer_addrs(block_hash) { ... };
let total_reject_weight = self.compute_signature_signing_weight(...);
```

So any authenticated, valid `BlockRejection` from `signer_address` for a second, distinct `block_hash` is never added to `rejection_addrs`, and `total_reject_weight` for that second block is computed as if that signer never voted. The weight-threshold comparison that decides whether to `mark_globally_rejected` therefore under-counts real rejection weight: [4](#0-3) 

This is triggered purely by ordinary network conditions requiring only a single miner (plus normal signer gossip): whenever a miner produces two distinct block proposals over time (e.g. re-proposing after a rejected block, or forking tenures) and the *same* signer rejects both, every other signer node that observes both rejections will successfully record the first and then silently fail to record the second, third, etc. No majority of signers, no key compromise, and no StackerDB-transport trickery is needed — only the ordinary occurrence of one signer rejecting more than one block hash during the node's runtime.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts/rejects" equality: the locally computed `total_reject_weight` for a block can be strictly less than the true weight of valid, authenticated rejections received, because rejections for any block hash other than the first one recorded for a given `signer_addr` are dropped by a DB constraint violation rather than being counted. This can prevent `store_and_process_block_rejection` from ever reaching the rejection threshold needed to call `mark_globally_rejected`, wedging the signer set's ability to conclude a negative consensus decision on an invalid/conflicting block even though a genuine blocking minority exists. Per the impact categories, this is a liveness wedge (signers unable to correctly act on the true aggregated rejection weight), and in cases where it stalls rejection of an invalid block indefinitely it edges toward a safety-relevant miscount of the rejection tally.

### Likelihood Explanation
High reachability, low complexity: this requires no more than a single miner producing two distinct block proposals (a routine event — reorgs, tenure changes, and miner retries all naturally create multiple `signer_signature_hash`es) and one signer rejecting more than one of them, which any node observing that signer's gossip will hit automatically. No majority collusion, no key compromise, and no special StackerDB manipulation is required — it is a straightforward consequence of the table schema.

### Recommendation
Change the schema (and its migration) so `block_rejection_signer_addrs` is keyed by the composite `(signer_signature_hash, signer_addr)`, matching the assumptions already encoded in `add_block_rejection_signer_addr`'s queries, e.g.:

```sql
CREATE TABLE IF NOT EXISTS block_rejection_signer_addrs (
    signer_signature_hash TEXT NOT NULL,
    signer_addr TEXT NOT NULL,
    reject_code INTEGER NOT NULL,
    PRIMARY KEY (signer_signature_hash, signer_addr)
) STRICT;
```
A migration should be added to move existing rows into the corrected table (analogous to `MIGRATE_BLOCKS_TABLE_2_BLOCKS_TABLE_3`), and `add_block_rejection_signer_addr`'s `INSERT`/`UPDATE` logic should be re-validated against the corrected key.

### Proof of Concept
Using the existing test harness pattern in `signerdb.rs` (see `reject_then_accept` at lines 3234-3263 for the harness style), the following demonstrates the failure:

```rust
#[test]
fn reject_two_different_blocks_from_same_signer_fails_second_insert() {
    let db_path = tmp_db_path();
    let db = SignerDb::new(db_path).expect("Failed to create signer db");

    let block_a = Sha512Trunc256Sum::from_data("block-a".as_bytes());
    let block_b = Sha512Trunc256Sum::from_data("block-b".as_bytes());
    let signer = StacksAddress::burn_address(false);

    // Signer rejects block A -- succeeds, row (block_a, signer) inserted.
    assert!(db
        .add_block_rejection_signer_addr(&block_a, &signer, RejectReasonPrefix::InvalidParentBlock)
        .unwrap());

    // Signer later rejects a DIFFERENT block B -- this INSERT violates the
    // PRIMARY KEY(signer_addr) constraint because a row for `signer` already
    // exists (tied to block_a), even though (block_b, signer) is a distinct pair.
    let result = db.add_block_rejection_signer_addr(&block_b, &signer, RejectReasonPrefix::InvalidParentBlock);
    assert!(result.is_err(), "expected PRIMARY KEY violation on cross-block rejection");

    // Block B's rejection tally never includes `signer`'s vote.
    assert!(db.get_block_rejection_signer_addrs(&block_b).unwrap().is_empty());
}
```

Because the table's `PRIMARY KEY` is `signer_addr` alone [1](#0-0) , the second `add_block_rejection_signer_addr` call for `block_b` hits the `None` branch of the match and issues a raw `INSERT` [5](#0-4) , which fails against the existing `block_a` row, causing `store_and_process_block_rejection` to silently drop that vote from the weight tally [6](#0-5) .

    /// Record an observed block rejection_signature
    pub fn add_block_rejection_signer_addr(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        addr: &StacksAddress,
        reject_reason: RejectReasonPrefix,
    ) -> Result<bool, DBError> {
        // If this signer/block already has a signature, do not allow a rejection
        let sig_qry = "SELECT EXISTS(SELECT 1 FROM block_signatures WHERE signer_signature_hash = ?1 AND signer_addr = ?2)";
        let sig_args = params![block_sighash, addr.to_string()];
        let exists = self.db.query_row(sig_qry, sig_args, |row| row.get(0))?;
        if exists {
            warn!("Cannot add block rejection because a signature already exists.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %addr,
                "reject_reason" => ?reject_reason
            );
            return Ok(false);
        }

        // Check if a row exists for this sighash/signer combo
        let qry = "SELECT reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2 LIMIT 1";
        let args = params![block_sighash, addr.to_string()];
        let existing_code: Option<i64> =
            self.db.query_row(qry, args, |row| row.get(0)).optional()?;

        let reject_code = reject_reason as i64;

        match existing_code {
            Some(code) if code == reject_code => {
                // Row exists with same reject_reason, do nothing
                debug!("Duplicate block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(false)
            }
            Some(_) => {
                // Row exists but with different reject_reason, update it
                let update_qry = "UPDATE block_rejection_signer_addrs SET reject_code = ?1 WHERE signer_signature_hash = ?2 AND signer_addr = ?3";
                let update_args = params![reject_code, block_sighash, addr.to_string()];
                self.db.execute(update_qry, update_args)?;
                debug!("Updated block rejection reason.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
            None => {
                // Row does not exist, insert it
                let insert_qry = "INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (?1, ?2, ?3)";
                let insert_args = params![block_sighash, addr.to_string(), reject_code];
                self.db.execute(insert_qry, insert_args)?;
                debug!("Inserted block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
        }
    }
