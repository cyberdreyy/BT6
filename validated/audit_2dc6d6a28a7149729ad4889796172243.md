### Title
`onStopEpoch` uses the raw shortfall as the ERC4626 withdraw target instead of clamping to `maxWithdraw`, making `stopEpoch` revert and freezing LP funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

Analogous to the Uniswap report — where a user-supplied `sqrtPriceLimitX96` was passed as the internal swap's price *target* instead of being translated via `getSqrtPriceTarget` — `ProgrammableBorrower.onStopEpoch` passes the raw `_amountRequired - onHand` shortfall directly as the `assets` argument of `vault.withdraw()` without translating it against the vault's actual withdrawal capacity (`maxWithdraw(address(this))`). For ERC4626 vaults with limited liquidity (the standard for Morpho-style / utilization-based vaults), `withdraw(assets)` reverts whenever `assets > maxWithdraw`, even when the share position economically covers the shortfall. The result is that `stopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, blocking epoch settlement and freezing all pending withdrawals.

### Finding Description

In `onStopEpoch`, the coverage check uses the economic value of the vault position:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:239-253
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
    uint256 shortfall = _amountRequired - onHand;
    // checks ECONOMIC coverage, not withdrawal capacity
    if (shortfall > _currentVaultAssets()) return true;
    try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        ...
    } catch {
        revert StopEpochVaultLiquidityUnavailable();
    }
}
```

`_currentVaultAssets()` is `vault.convertToAssets(balanceOf(this))` — the full position value. But `vault.withdraw(shortfall, ...)` can only succeed if `shortfall <= vault.maxWithdraw(address(this))`, which for any vault with less-than-full idle liquidity is strictly smaller than the position value. The same defect exists in `_borrow` (line 452): `vault.withdraw(shortfall, ...)` reverts whenever vault liquidity is constrained, even though `availableToBorrow()` reports the full `convertToAssets` value as borrowable.

This is the exact bug-class shape of the reference finding: a bound/derived quantity (`maxWithdraw`, like `getSqrtPriceTarget`'s clamped target) is ignored, and the raw input amount is used as the step target, so the call reverts in the common case.

### Impact Explanation

`IdleCDOEpochVariant.stopEpochWithDuration` (contracts/IdleCDOEpochVariant.sol:398) calls `onStopEpoch` inside the stop flow; a revert there bubbles up and aborts the whole stop transaction. While vault liquidity is constrained, the epoch cannot be stopped: `isEpochRunning` stays true, `pendingWithdraws` cannot be funded or claimed, deposits are gated, and `_beforeUnpause` blocks unpausing. All pending receipt payouts plus the epoch's interest stay locked for the duration — a temporary freezing of LP funds proportional to `pendingWithdraws + expectedEpochInterest`, exploitable repeatedly each time the manager retries.

### Likelihood Explanation

An unprivileged attacker only needs to be "a user of the programmable borrower's ERC4626 vault" — an explicitly in-scope actor. By withdrawing idle liquidity from the shared vault (or borrowing it if the vault is a lending market) so that `maxWithdraw(ProgrammableBorrower) < shortfall <= convertToAssets(shares)`, the attacker deterministically forces `StopEpochVaultLiquidityUnavailable` on the next `stopEpoch` call. No privileged cooperation is required; the honest manager/keeper call to `stopEpoch` itself becomes the reverting transaction, mirroring the report's "swap TXs will revert in most cases".

### Recommendation

Translate the requested amount into the achievable withdrawal target before calling the vault — either clamp via `min(shortfall, vault.maxWithdraw(address(this)))` and account for the residual through the default path, or use `redeem` bounded by `maxRedeem`/`previewRedeem` so the call only ever asks for liquidity the vault can actually serve. The same clamp applies in `_borrow` at line 452.

### Proof of Concept

Foundry-style reproduction (against the existing test harness patterns in `test/foundry/ProgrammableBorrowerEpochInvariant.t.sol`):

```solidity
function test_StopEpochRevertsOnLimitedVaultLiquidity() public {
    // epoch running; ProgrammableBorrower holds vault shares worth more
    // than the vault's remaining idle liquidity
    uint256 required = pb.availableToBorrow();       // covered by convertToAssets
    // attacker (unprivileged vault user) drains idle liquidity so that
    // vault.maxWithdraw(pb) < shortfall < convertToAssets(shares)
    uint256 liquid = underlying.balanceOf(address(vault));
    vm.prank(attacker);
    vault.withdraw(liquid - dust, attacker, attacker);

    // shortfall economically covered: convertToAssets >= required
    assertGt(pb.vaultSharesBalance() > 0 ? vault.convertToAssets(vault.balanceOf(address(pb))) : 0,
             required);

    // honest manager tries to stop the epoch -> revert, funds stay frozen
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpochWithDuration(0, newApr, epochDuration, 0);
}
```

The revert is purely deterministic arithmetic: `withdraw(shortfall)` is issued while `shortfall > maxWithdraw`, which every conformant ERC4626 must reject.
