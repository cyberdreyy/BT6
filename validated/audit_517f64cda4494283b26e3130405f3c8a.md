### Title
Blacklisted/non-receiving redeem `receiver` can DoS batched `solveRequestsVault`/`solveRequestsDirect` calls - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2._solveRedeemVaultFixedPrice` and `_solveRedeemVaultAutoPrice` transfer the redeemed token directly to the user-supplied `request.receiver` via plain `token.safeTransfer(...)` on the success path, with no failure fallback. `_solveRequestDirect`'s redeem success path does the same via `token.safeTransferFrom(msg.sender, request.receiver, request.tokens)`. This is inconsistent with every other transfer path in the same file (refunds, cancellations) which route through `_transferWithFallback`, which tries the transfer and falls back to the original requester if it reverts. Since `requestRedeem`/`request.receiver` is attacker-controlled and requests are solved in batches (`RequestV2[] requests` loops in `solveRequestsVault`/`solveRequestsDirect`), one malicious redeem request whose `receiver` is a blacklisted USDC address (or any address that reverts on receipt) reverts the entire batch transaction, exactly the pattern from the referenced Y2K/Carousel `mintRollover` report.

### Finding Description
An ordinary user calls `requestRedeem(token, unitsIn, minTokensOut, ..., receiver)` (the overloaded variant accepting an explicit `receiver`, per `IProvisionerV2.sol` lines 369-386/447+) setting `receiver` to a known USDC-blacklisted address. This request sits in `asyncRequestHashes` until a solver later calls `solveRequestsVault` or the permissionless `solveRequestsDirect` with a batch that includes it, alongside other legitimate users' requests: [1](#0-0) 

Inside the loop, `_solveRequestDirect`/`_solveRedeemVaultFixedPrice`/`_solveRedeemVaultAutoPrice` are called per request. On the success (non-refund) branch, the token transfer to `request.receiver` is a bare `safeTransfer`/`safeTransferFrom`, not wrapped in the try/fallback helper used elsewhere: [2](#0-1) [3](#0-2) [4](#0-3) 

Compare this to the refund/cancel/deadline-expired branches, which all use the guarded helper: [5](#0-4)  and `_clearHashAndTransferRefund` [6](#0-5) 

Because the "happy path" transfer is unguarded, a single poisoned request causes the whole `solveRequestsVault`/`solveRequestsDirect` transaction to revert, blocking every other request bundled in that call — the same broken invariant (unconditional loop transfer without failure isolation on an attacker-chosen receiver) as the reported Carousel `mintRollover` issue.

### Impact Explanation
Any solver batch that unknowingly includes the poisoned redeem request reverts entirely, delaying settlement/yield realization for all other users' async redeem (and via `solveRequestsVault`, deposit) requests bundled in the same call. This is a temporary freeze of user funds/yield rather than a permanent loss, since: (a) `refundRequest`/`cancelRequest` for the expired/cancelled poisoned request itself correctly use `_transferWithFallback` and thus succeed even with a blacklisted receiver, and (b) once identified, solvers can exclude the specific malicious request from future batches. This aligns with a Medium-severity "temporary freezing of funds/yield" impact — solvers must discover and isolate the bad request first, during which legitimate users' requests in shared batches are blocked/delayed.

### Likelihood Explanation
Feasible with a purely ordinary-user transaction sequence: any account can call `requestRedeem` with an arbitrary `receiver`, no privileged role is required to create the poisoned request. Exploitation requires that a solver batches it together with genuine requests, which is realistic given `RequestV2[]` batches are typically built by scanning all pending outstanding requests for gas efficiency, until the operator explicitly filters it out. The permissionless `solveRequestsDirect` path is directly attacker-reachable without any solver cooperation.

### Recommendation
Route the success-path token/unit transfers to `request.receiver` in `_solveRedeemVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, and `_solveRequestDirect` through the same `_transferWithFallback` (or an equivalent try/catch-with-fallback-to-requester) pattern already used for refunds, so that a single unreceivable address cannot revert an entire solve batch.

### Proof of Concept
1. Deploy `ProvisionerV2` wired to a mock ERC20 that reverts transfers to a designated "blacklisted" address (simulating USDC blacklist behavior).
2. As `attacker`, deposit and obtain vault units, then call `requestRedeem(token, unitsIn, minTokensOut, solverTip, deadline, maxPriceAge, isFixedPrice, receiver = BLACKLISTED_ADDR)` to create a pending redeem request hash.
3. As `victim`, create a normal, otherwise-solvable redeem request with a valid `receiver`.
4. As an authorized solver, call `solveRequestsVault(token, [attackerRequest, victimRequest], "", "")` (or `solveRequestsDirect` for the permissionless path).
5. Assert the call reverts (due to the mock token reverting on transfer to `BLACKLISTED_ADDR` inside `_solveRedeemVaultFixedPrice`/`_solveRequestDirect`), and that `victimRequest`'s `asyncRequestHashes` entry remains untouched/unsolved, demonstrating the DoS on the batch.
6. Contrast with calling `refundRequest`/`cancelRequest` on the attacker's own poisoned request, which succeeds (falls back to `request.user`) — confirming the asymmetry between guarded and unguarded transfer paths.

    function _clearHashAndTransferRefund(
        IERC20 token,
        RequestV2 calldata request,
        address requester,
        uint256 amount,
        IERC20 transferToken
    ) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        require(asyncRequestHashes[requestHash], Aera__HashNotFound());
        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;
        // Interactions: transfer amount to receiver, fallback to requester on transfer failure
        _transferWithFallback(transferToken, requester, request.receiver, amount);

        // Log refund event
        if (_isRequestTypeDeposit(request.requestType)) {
            emit DepositRefunded(requestHash);
        } else {
            emit RedeemRefunded(requestHash);
        }
    }

    /// @notice Transfers amount to receiver and falls back to requester if receiver transfer fails
    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
