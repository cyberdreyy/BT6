### Title
Unprivileged ERC4626 vault liquidity drain blocks `stopEpoch` and freezes all tranche withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The SSRF report is about an unauthenticated attacker forcing the server to reach an arbitrary external endpoint whose behavior the application does not control. The analog in idle-tranches is the programmable-borrower epoch settlement path: `IdleCDOEpochVariant._stopEpoch` unconditionally calls `ProgrammableBorrower.onStopEpoch`, which in turn calls `vault.withdraw(shortfall, ...)` on an externally controlled ERC4626 vault (e.g., a Morpho vault). Any unprivileged user of that shared vault/market can exhaust its withdrawable liquidity, making `vault.withdraw` revert, which makes `onStopEpoch` revert `StopEpochVaultLiquidityUnavailable`, which makes the entire `stopEpoch` transaction revert. While the liquidity is withheld, the epoch can never be stopped, so no tranche holder can withdraw and pending withdraw receipts can never be funded.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, the programmable-borrower hook is a bare external call (not wrapped in try/catch), so any revert in the hook bubbles up and aborts the whole stop flow (`contracts/IdleCDOEpochVariant.sol:395-404`):

```solidity
if (!IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)) {
```

In `ProgrammableBorrower.onStopEpoch`, when IdleCDO needs cash (`_amountRequired > onHand`), the code first checks economic coverage (`shortfall > _currentVaultAssets()` returns early-`true` to let the default path run), but then performs the liquidity-sensitive call in a try/catch that converts any vault withdrawal failure into a hard revert (`contracts/strategies/idle/ProgrammableBorrower.sol:239-253`):

```solidity
if (shortfall > _currentVaultAssets()) return true;
try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
  ...
} catch {
  revert StopEpochVaultLiquidityUnavailable();
}
```

The vault is a public ERC4626 (e.g., a Morpho Blue vault such as Gauntlet USDC Prime, used in the fork tests). Its `withdraw` reverts whenever idle market liquidity is below the requested amount. Any third party — not a lender, not the borrower, just a participant in the same Morpho market — can supply cheap collateral and borrow out the market's available liquidity, or redeem/borrow through the vault's other markets, driving `maxWithdraw(programmableBorrower)` below the shortfall for as long as they keep the position open.

### Impact Explanation
Temporary freezing of all vault funds with quantifiable effect: while the ERC4626 vault's liquidity is exhausted, every `stopEpoch` call reverts, `isEpochRunning` stays `true`, the pool stays paused (`_pause()` from `startEpoch`), withdraw requests cannot be filed or claimed, and `claimWithdrawRequest`/`collectWithdrawFunds` for already-pending receipts (which are funded inside the same `stopEpoch` success path via `_strategy.collectWithdrawFunds(_pendingWithdraws)`) never execute. The freeze affects 100% of pool NAV and lasts exactly as long as the attacker maintains the drained-liquidity position; unfreezing requires repaying the borrowed liquidity or new supply entering the market. Note the `_isRequestingAllFunds` close-pool path is also blocked, so owner-initiated wind-down is griefed too. This is inherent-external-dependency risk rather than logic error, and the code comments show the revert is intentional ("transient ERC4626 liquidity failures can be retried"), but nothing limits how long an attacker can sustain the "transient" condition.

### Likelihood Explanation
Requires an attacker with enough collateral to borrow out the target vault's idle liquidity on the underlying Morpho markets — capital-intensive but permissionless, and the borrow cost is only the market borrow APR for the freeze duration. It is most practical near epoch end when `_amountRequired` (pending withdraws) is large relative to residual idle liquidity. Existing guards do not stop it: `shortfall > _currentVaultAssets()` only catches the *uncovered* case (shares worth less than the shortfall); the attacker targets the *covered but illiquid* case. `setVault` is owner/manager-gated and cannot be invoked while shares remain (`ProgrammableBorrower.sol:158-170`), and `emergencyExitVault` hits the same liquidity wall. There is no default triggered (revert precedes `_handleBorrowerDefault`), so the only recourse is waiting for liquidity to return — i.e., the freeze is genuinely attacker-controlled in duration.

### Recommendation
- In `onStopEpoch`, treat a liquidity-blocked `vault.withdraw` the same way as other shortfalls instead of reverting: return `false` (letting IdleCDO take the measured-default path) or attempt `maxWithdraw`-bounded partial withdrawals and return the actually-available amount.
- Alternatively, have IdleCDO wrap the hook in try/catch and fall back to a "liquidity-pending" state that still closes the epoch accounting while deferring only the cash pull.
- Operationally, prefer ERC4626 vaults whose `withdraw` is backed by multiple markets, and add a keeper that pre-positions liquidity before `epochEndDate` (e.g., via `emergencyExitVault` during the epoch when liquidity is available), since `epochPendingWithdraws` is already reserved for exactly this purpose.

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ProgrammableBorrower, StopEpochVaultLiquidityUnavailable} from "../contracts/strategies/idle/ProgrammableBorrower.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IMMVault} from "../contracts/interfaces/morpho/IMMVault.sol";
import {IMorpho, MarketParams, Position} from "../contracts/interfaces/morpho/IMorpho.sol";

// Fork: mainnet, setup identical to testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable
// in test/foundry/ProgrammableBorrowerCreditVault.t.sol (IdleCDOEpochVariant + IdleCreditVault +
// ProgrammableBorrower pointing at a Morpho ERC4626 vault such as GAUNTLET_USDC_PRIME).
contract StopEpochLiquidityFreezeTest is Test {
    // ... reuse fixture: cdoEpoch, strategy, programmableBorrower, morphoVault, IMorpho morpho ...

    function testAttackerFreezesStopEpochByDrainingVaultLiquidity() external {
        uint256 amount = 10_000 * 1e6;
        vm.prank(owner);
        cdoEpoch.setIsInterestMinted(true);
        idleCDO.depositAA(amount);
        cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
        _startEpoch(); // onStartEpoch deposits all idle USDC into the Morpho vault

        // Attacker: any EOA. Supply collateral to the Morpho markets backing the vault and
        // borrow out the idle liquidity so maxWithdraw(programmableBorrower) < pendingWithdraws.
        uint256 pending = strategy.pendingWithdraws();
        MarketParams[] memory markets = _vaultMarkets(morphoVault);
        for (uint256 i; i < markets.length; i++) {
            (,,,, uint256 borrowShares,) = // attacker borrows up to available liquidity
            _borrowFromMarket(markets[i]); // supply wstETH/etc collateral, borrow loan asset
        }
        assertLt(morphoVault.maxWithdraw(address(programmableBorrower)), pending);

        // Epoch ends; honest manager tries to settle -> hard revert, epoch stays running.
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdoEpoch.stopEpoch(0, 0);
        assertTrue(cdoEpoch.isEpochRunning());          // frozen: still running
        assertEq(strategy.pendingWithdraws(), pending); // receipts unfunded

        // Repeatable: every retry reverts while attacker keeps liquidity borrowed.
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdoEpoch.stopEpoch(0, 0);

        // Only when the attacker repays does settlement succeed -> temporary freeze
        // whose duration is attacker-controlled.
        _repayFromMarket(markets);
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, 0);
        assertFalse(cdoEpoch.isEpochRunning());
    }
}
```

Note on confidence: the reversion behavior is deliberately coded ("Hook reverts bubble so transient ERC4626 liquidity failures can be retried") and covered by `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable`, so if the audit scope treats tested/intended revert-on-illiquidity as acknowledged, this finding should be downgraded accordingly. The unresolved exposure is the *sustained* freeze: nothing in the retry design bounds how long a third party can keep the epoch unstoppable.
