### Title
Missing allowlist/rate-limit on legacy web_api_trigger user messages allows unbounded job-trigger flooding - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Finding Description
`gateway.ProcessRequest` in `core/services/gateway/gateway.go` decodes an incoming HTTP request, resolves the legacy DON handler via `msg.Body.DonId`, and directly invokes `h.HandleLegacyUserMessage(ctx, msg, callback)` for any legacy request that passes basic structural validation (`msg.Validate()`), with no per-caller or per-token quota check at this layer. [1](#0-0) 

Inside `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go`), the request is checked for decodability, a non-zero timestamp, and staleness, but the code that follows is explicitly marked `// TODO: apply allowlist and rate-limiting here` before dispatching the message to every DON member via `don.SendToNode`. [2](#0-1) 

The only rate limiter instantiated in this handler, `h.nodeRateLimiter`, is consumed exclusively in `handleWebAPIOutgoingMessage`, which is reached from `HandleNodeMessage` (node→gateway direction for `web_api_target`/`compute_action`/`workflow_syncer`), not from the user-facing `HandleLegacyUserMessage` path. [3](#0-2) [4](#0-3)  Consequently, a caller with any credential sufficient to authenticate at `ProcessRequest` (this legacy path uses `msg.Validate()`/`jsonrpc2.DecodeRequest` with an `auth` string, not per-user quota state) can submit an unbounded number of distinct-`MessageId` `web_api_trigger` messages, each of which is unconditionally forwarded with `don.SendToNode` to all DON members. [5](#0-4) 

This contrasts with the newer v2 HTTP trigger handler (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`), which explicitly enforces a per-workflow-owner rate limit via `h.userRateLimiter.AllowErr(ctx)` in `checkRateLimit` before dispatch. [6](#0-5)  The legacy path has no equivalent control, confirming the gap is a genuine missing check rather than duplicated/irrelevant enforcement elsewhere.

### Impact Explanation
Any caller able to satisfy the legacy request's basic auth/format checks can trigger unlimited `web_api_trigger` job executions across every node of a targeted DON, at a rate limited only by attacker throughput, not the gateway. This matches the "unauthorized job/run triggering at unbounded rate" impact class — a quota/allowlist bypass leading to DON node/job resource exhaustion (denial-of-service against the DON and downstream external endpoints/job runs), without requiring any operator or admin access.

### Likelihood Explanation
Preconditions are minimal: possession of whatever credential the gateway's user-facing HTTP endpoint accepts for a legacy DON request (an `auth` string passed to `jsonrpc2.DecodeRequest`) and knowledge of a valid `DonId`. The vulnerable code path is unconditionally reached on every legacy `web_api_trigger` call — there is no probabilistic or racing element, and the flaw is a literal `TODO` stub, making this fully repeatable and trivial to automate (send N messages with distinct `MessageId`s in a tight loop).

### Recommendation
Implement the missing allowlist and rate-limiting in `HandleLegacyUserMessage` before the `don.SendToNode` fan-out, mirroring the v2 design: enforce a per-caller/per-token (or per-workflow-owner equivalent) rate limiter (e.g., reuse `ratelimit.RateLimiter` or `limits.RateLimiter` keyed by the authenticated sender identity) and a caller allowlist check, rejecting requests that exceed quota or are not allowlisted with `api.HandlerError`/`api.UserMessageParseError`-style responses, consistent with existing error-handling conventions in the function.

### Proof of Concept
Go table/unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` via `NewHandler` with a mock `handlers.DON` (using the existing `handlermocks.DON`) and a mock `handlers.Callback`.
2. Build 1000 valid `api.Message` instances with method `web_api_trigger`, distinct `MessageId`s, valid non-zero `Timestamp` (recent), and valid signatures/structure so `common.ValidatedRequestFromMessage` succeeds.
3. In a loop, call `handler.HandleLegacyUserMessage(ctx, msg, callback)` for each message.
4. Assert: (a) `don.SendToNode` mock is invoked once per DON member per message (i.e., call count == 1000 × len(members)) with no calls ever failing due to rate limiting; (b) no `callback.SendResponse` invocation ever returns an `api.HandlerError`/quota-exceeded error code; (c) contrast this with `handleWebAPIOutgoingMessage`, where an equivalent loop over `HandleNodeMessage` for `web_api_target` does return `"rate limit exceeded for node %s"` once `h.nodeRateLimiter` is exhausted — demonstrating the asymmetry between the node-outgoing path (rate-limited) and the user-triggering path (unlimited).

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	msg, err := common.ValidatedMessageFromResp(resp)
	if err != nil {
		return err
	}
	if msg.Body.Sender != nodeAddr {
		return errors.New("message sender mismatch when reading from node ")
	}
	start := time.Now()
	switch msg.Body.Method {
	case MethodWebAPITrigger:
		err = h.handleWebAPITriggerMessage(ctx, msg, nodeAddr)
	case MethodWebAPITarget, MethodComputeAction, MethodWorkflowSyncer:
		err = h.handleWebAPIOutgoingMessage(ctx, msg, nodeAddr)
	default:
		err = fmt.Errorf("unsupported method: %s", msg.Body.Method)
	}
	h.metrics.recordHandleDuration(ctx, time.Since(start), msg.Body.Method, err == nil)
	return err
}

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	// TODO orgID https://smartcontract-it.atlassian.net/browse/CRE-1707
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}
