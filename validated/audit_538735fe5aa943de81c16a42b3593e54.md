### Title
Loss-adjusted withdraw receipts bypass the haircut because `lossRecoveryPriceByEpoch` is keyed by the post-increment epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.collectWithdrawFunds` records a stop-epoch loss under `lossRecoveryPriceByEpoch[epochNumber]` using the epoch counter *after* `deposit()` has already incremented `epochNumber` during `stopEpoch`, while the receipts it is meant to haircut were registered under the pre-increment value stored in `lastWithdrawRequest[_user]` and `withdrawsRequestsByEpoch[_user][requestEpoch]`. The epoch-key mismatch makes `_claimLossAdjustedWithdrawRequest` look up the wrong epoch (price `0`) and fall through to `_claimFundedWithdrawRequest`, which pays receipts at full face value even though the borrower only funded a reduced amount.

### Finding Description
- `requestWithdraw` snapshots the user's request epoch as `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch]`, where `currentEpoch = epochNumber` at request time (buffer phase). [1](#0-0) 
- `deposit()` increments `epochNumber` when called while `isEpochRunning()` is true, i.e. inside `stopEpoch` when repaid funds are deposited. [2](#0-1) 
- `collectWithdrawFunds` is only reached later in the same `stopEpoch` flow, and when the borrower underfunds (`_amount < pendingBasis`) it writes `lossRecoveryPriceByEpoch[epochNumber]` — now `requestEpoch + 1` — and zeroes `pendingWithdraws`. [3](#0-2) 
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the pre-increment epoch — finds `0`, returns early, and `_claimFundedWithdrawRequest` pays the entire `withdrawsRequests` balance at par via `_transferFundedClaim`. [4](#0-3) 

The same misalignment weakens the `requestWithdraw` guard at lines 263–271 in the other direction for a user whose `lastWithdrawRequest` equals the *storing* epoch, but the primary impact is the skipped haircut.

### Impact Explanation
The strategy only holds `pendingToFund < pendingBasis` underlying after a loss-adjusted `stopEpoch`. Paying each receipt at full face value over-distributes the funded amount: early claimers receive unhaircutted payouts (effectively stealing the loss share of later claimers), and once the funded reserve is drained, remaining claims revert on the underlying transfer — permanent freezing of the unclaimed portion of funded withdraw receipts. This breaks the "one receipt one (haircutted) payout" and loss-socialization invariants, with a quantifiable loss equal to `pendingBasis - pendingToFund` misallocated.

### Likelihood Explanation
Requires `stopEpochWithDuration`/`stopEpoch` to realize a loss while pending withdraw receipts exist (`pendingBasis != 0` and `_lossAmount > 0` but `< totalBasis` per `previewLossAdjustedWithdrawFunds`). Loss realization is an honest manager/borrower action (e.g., underperforming epoch), and pending receipts are a normal state — no attacker-privileged role needed. The bug triggers deterministically whenever this path executes; the attacker only needs to hold a pending receipt and claim before other users.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the request epoch, not the already-incremented counter. In `collectWithdrawFunds`, store the price under `epochNumber - 1` (the epoch the pending receipts requested in), or snapshot the request epoch before `deposit()` increments it and pass it through. Add a regression test: pending receipt → `stopEpoch` with partial loss funding → `claimWithdrawRequest` pays exactly `claimBasis * lossRecoveryPrice / 1e18`, and `pendingWithdraws`/strategy balance reconcile.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
