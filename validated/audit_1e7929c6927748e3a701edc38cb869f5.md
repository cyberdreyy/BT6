### Title
Stale LDAP API token role retained indefinitely when `UpstreamSyncInterval=0` and no other auth event triggers `Work()` - ([File: core/sessions/ldapauth/sync.go])

### Summary
`FindUserByAPIToken` trusts the `user_role` value cached in `ldap_user_api_tokens` without any upstream revalidation on the request path itself, relying entirely on `LDAPServerStateSyncer.Work` to keep that cached role in sync with the upstream LDAP group membership. With the default `UpstreamSyncInterval` of `0s`, `Start` runs `Work(ctx)` exactly once and never schedules `run()`'s ticker loop, so the cached role for a demoted user's API token is never refreshed unless some other code path calls `Work()` again.

### Finding Description
`AuthenticationProvider.FindUserByAPIToken` (`core/sessions/ldapauth/ldap.go:205-236`) reads `user_role` directly from `ldap_user_api_tokens` and returns it as the authenticated user's role — no upstream LDAP lookup is performed per request, by design, per the comment at `core/sessions/ldapauth/ldap.go:210-212`: "user role and email are cached ... via the UpstreamSyncInterval config and reaper.go sync implementation".

The only mechanism that re-derives roles from upstream and pushes updates into `ldap_user_api_tokens` is `LDAPServerStateSyncer.Work` (`core/sessions/ldapauth/sync.go:93-284`), which issues LDAP group queries and does a `CASE WHEN` bulk `UPDATE ldap_user_api_tokens SET user_role = ...` (`core/sessions/ldapauth/sync.go:262-274`).

`Start` (`core/sessions/ldapauth/sync.go:56-68`) decides how `Work` is scheduled:
```go
if !l.config.UpstreamSyncInterval().IsInstant() {
    go l.run()
} else {
    l.Work(ctx)
}
```
When `UpstreamSyncInterval` is left at its zero-value default, `IsInstant()` is true, so the `else` branch executes: `Work(ctx)` runs exactly once at node startup, and the ticker-based `run()` goroutine (`core/sessions/ldapauth/sync.go:76-91`) is never started. There is no other code in `sync.go` or `ldap.go` that re-invokes `Work()` on a per-request or per-login basis — `CreateSession` (`core/sessions/ldapauth/ldap.go:396-457`) only calls `FindUser`, which performs its own upstream `FindUser` query for interactive logins (not `Work`), and `FindUserByAPIToken` performs no upstream check at all.

Consequently, for an API token issued while a user was Admin, if that user is demoted upstream after the one-shot `Work()` call at startup, and no admin restarts the node or otherwise triggers a fresh `Work()`, the row in `ldap_user_api_tokens` keeps `user_role = 'admin'` indefinitely. Every request authenticated with that token via `FindUserByAPIToken` returns the stale elevated role, and `RequiresEditRole`/`RequiresAdminRole` gated routes in `core/web/router.go` will authorize the demoted user based on this stale cached role.

### Impact Explanation
This is a privilege-retention/authorization-bypass issue: a demoted LDAP user's API token continues to grant Admin/Edit-level access to `RequiresEditRole`/`RequiresAdminRole` routes after their access should have been revoked upstream, until an operator restarts the node, sets a non-zero `UpstreamSyncInterval`, or some other event triggers `Work()`. This matches the "role/authorization bypass" and "indefinite privilege retention" impact class described in the question. However, note the exploit requires the token to have already been legitimately issued at a higher role before demotion — it is a stale-authorization/revocation-latency bug rather than a bypass of the authentication mechanism itself.

### Likelihood Explanation
Preconditions: (1) LDAP auth mode enabled with API tokens (`UserApiTokenEnabled`), (2) `UpstreamSyncInterval` left at its default `0s` (a common/default deployment configuration, not an unusual misconfiguration), (3) the token holder was previously granted a higher role and is later demoted upstream, and (4) no node restart or alternate `Work()` trigger occurs in the interim. Given default configuration is the triggering condition and no additional attacker action beyond normal API-token usage is needed, likelihood is credible for long-lived, non-restarted node deployments using default LDAP config, though it's fundamentally a configuration-timing gap rather than an actively exploitable request-crafting vulnerability.

### Recommendation
Do not rely solely on a fixed-interval background sync for authorization freshness. Options: (1) treat `UpstreamSyncInterval=0` as "sync on every Work-eligible auth event" rather than "sync once at startup only," e.g., also invoke `Work()` (rate-limited via `UpstreamSyncRateLimit`) from `FindUserByAPIToken` and `AuthorizedUserWithSession` so cached roles are revalidated opportunistically per request; (2) emit a startup warning when `UpstreamSyncInterval` is `0` making clear that periodic revalidation is disabled; (3) consider enforcing a sane non-zero default for `UpstreamSyncInterval` instead of treating `0` as "run once."

### Proof of Concept
Go integration test plan (in `core/sessions/ldapauth`):
1. Configure a fake `LDAPClient`/mock LDAP server where a user `victim@example.com` is initially a member of the Admin group.
2. Construct `LDAPServerStateSyncer` with `config.UpstreamSyncInterval() = 0` and call `Start(ctx)`; assert `Work()` ran once (e.g., via a call counter or by asserting the DB row was created/updated at startup).
3. Insert a row into `ldap_user_api_tokens` for `victim@example.com` with `user_role = 'admin'` (simulating `SetAuthToken` after admin login).
4. Update the fake LDAP backend so `victim@example.com` is now only a member of the View group (demotion).
5. Do not call `Work()` again and do not trigger any `CreateSession`/`FindUser` call for this user.
6. Call `FindUserByAPIToken(ctx, token)` and assert the returned `sessions.User.Role` is still `UserRoleAdmin` (stale), demonstrating the token retains elevated privileges.
7. Then explicitly call `syncer.Work(ctx)` and re-run `FindUserByAPIToken`, asserting the role is now correctly `UserRoleView`, confirming the only remediation path is an explicit/periodic `Work()` invocation.
