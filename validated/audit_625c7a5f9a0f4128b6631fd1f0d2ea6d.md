### Title
Raw internal error details leaked to unauthenticated caller via jsonAPIError in AuthenticateByToken - ([File: core/web/auth/auth.go])

### Summary
In `AuthenticateByToken`, any `FindUserByAPIToken` failure other than `sql.ErrNoRows`/`clsessions.ErrUserSessionExpired` is returned unwrapped (line 98), and the `Authenticate` middleware passes that raw error directly to `jsonAPIError`, which serializes `err.Error()` into the HTTP response body sent to the unauthenticated caller.

### Finding Description
`AuthenticateByToken` calls `authr.FindUserByAPIToken(ctx, token.AccessKey)`. On error, it only special-cases `sql.ErrNoRows` and `clsessions.ErrUserSessionExpired` to return the generic `auth.ErrorAuthFailed`; any other error (e.g., a DB connectivity/timeout error, or a wrapped internal error from the ORM/vault layer) is returned as-is: [1](#0-0) .

This error propagates up through `Authenticate`, which loops over auth methods and, on failure, calls `jsonAPIError(c, http.StatusUnauthorized, err)` with the raw error: [2](#0-1) .

`jsonAPIError` (duplicated in `core/web/auth/helpers.go` and `core/web/helpers.go`) writes `err.Error()` directly into the JSON response body when the error is not already a `*models.JSONAPIErrors`: [3](#0-2) .

Any request with an `X-API-KEY`/`X-API-SECRET` header pair reaches this code path unauthenticated — the attacker does not need valid credentials, just headers that route into `FindUserByAPIToken`. If the underlying store returns any error other than "no rows" (e.g., a database timeout, connection failure, or a driver-level error containing connection info or query fragments), that error's string representation is returned verbatim in the HTTP response body to the caller.

### Impact Explanation
This is an information-disclosure issue: an unauthenticated attacker could receive internal error strings (potentially including DB driver messages, connection details, or other backend implementation details) in the HTTP response, aiding further reconnaissance/attack planning against the node's backend. It does not by itself grant authentication bypass, privilege escalation, or fund movement — the underlying `FindUserByAPIToken` still must fail for a non-not-found reason (e.g., a DB outage or transient/internal error) for this branch to trigger, which is not attacker-controllable on demand. This fits the "sensitive information disclosure" class rather than a critical/authentication-bypass class.

### Likelihood Explanation
Low-to-moderate. The attacker needs no credentials — just to send any request with API key headers, which is trivially repeatable. However, actually triggering the vulnerable branch requires the backing data store (Postgres via the ORM) to return an error other than `sql.ErrNoRows`, which is not something normally reachable through pure application-level input (it typically requires a genuine backend fault, e.g., DB downtime/timeouts) rather than attacker-crafted input. There is no confirmed way shown in the repo for the attacker to force an arbitrary internal error deterministically from an unauthenticated request; this is largely dependent on incidental backend failures.

### Recommendation
In `AuthenticateByToken` (and similarly in `AuthenticateExternalInitiator`, which wraps and returns backend errors too), do not propagate the raw underlying error to the HTTP layer. Log the actual error server-side (e.g., via a logger from context) and return a generic `auth.ErrorAuthFailed` (or a new generic "internal authentication error") to the caller for any non-benign error, so `jsonAPIError` never surfaces internal error text for authentication failures.

### Proof of Concept
1. Add a Go test in `core/web/auth/auth_test.go` using a mocked `Authenticator` (from `core/sessions/mocks` or a custom stub satisfying the `Authenticator` interface).
2. Configure `FindUserByAPIToken` mock to return `nil, errors.New("dial tcp 10.0.0.5:5432: connect: connection refused")` (simulating an internal DB error, not `sql.ErrNoRows`).
3. Set `X-API-KEY`/`X-API-SECRET` headers on a test `gin.Context`/`httptest.ResponseRecorder`, and invoke the `Authenticate(store, AuthenticateByToken)` middleware handler.
4. Assert the HTTP status is 401 and that the response JSON body's error message equals the raw injected string (demonstrating leakage), i.e. `strings.Contains(w.Body.String(), "10.0.0.5:5432")` is true.
5. As a regression check post-fix, assert the response body only contains a generic message (e.g., "invalid API key or secret") and never contains the injected internal error text.

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
