### Title
`Signer::determine_response` signs based on stale `valid=Some(true)` ignoring terminal `GloballyRejected` state - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`Signer::determine_response` decides Accept/Reject solely from `BlockInfo::valid`, never consulting `BlockInfo::state` or calling `BlockInfo::check_state`/`move_to`. Because `mark_globally_rejected` does not reset `valid`, a block that this signer previously locally-accepted (`valid = Some(true)`) can be pushed to `BlockState::GloballyRejected` by other signers' rejection votes while `valid` stays `true`; a simple re-proposal of the same block hash then makes this signer emit a fresh `BlockAccepted` signature for a hash it has recorded as terminally rejected.

### Finding Description
The invariant that should hold: once `BlockInfo::state == GloballyRejected`, no code path should be able to produce a signed `Accepted` response for that `signer_signature_hash`. `BlockInfo::check_state` intentionally forbids `GloballyRejected -> LocallyAccepted`: [1](#0-0) 

However `mark_globally_rejected` only calls `move_to(GloballyRejected)`; it does **not** touch `self.valid`: [2](#0-1) 

And `check_state` explicitly *permits* the transition `LocallyAccepted -> GloballyRejected` (it only forbids `GloballyAccepted -> GloballyRejected`): [3](#0-2) 

So the following sequence is reachable purely through normal protocol messages, no privileged role required:

1. A signer receives a block proposal, validates it, and locally accepts it: `mark_locally_accepted` sets `valid = Some(true)`, state `LocallyAccepted`. [4](#0-3) 
2. Enough *other* signers gossip rejections for the same hash. `store_and_process_block_rejection` tallies rejection weight and, once the 70% threshold makes acceptance impossible, calls `block_info.mark_globally_rejected()` — this succeeds because the current state (`LocallyAccepted`) is not `GloballyAccepted`, and `valid` is left untouched at `Some(true)`. [5](#0-4) 
3. The block_info now has `state = GloballyRejected`, `valid = Some(true)`, `reject_reason = None` (this signer never rejected it locally).
4. The miner (single-slot attacker or the original miner) re-broadcasts the *same* `BlockProposal` (identical `signer_signature_hash`). `handle_block_proposal` looks up the cached `block_info` and calls `should_reevaluate_block`. [6](#0-5) 
5. `should_reevaluate_block`'s early-exit guard `globally_approved_and_responded()` only matches `BlockState::GloballyAccepted`, never `GloballyRejected`, so it does not short-circuit here: [7](#0-6) [8](#0-7) 
6. `should_reevaluate_reject_reason(block_info)` returns `false` because `reject_reason` is `None` (this signer accepted, it never rejected), so the code takes the `!should_reevaluate_reject_reason` branch, skips the `PreCommitted` re-send path (state is `GloballyRejected`, not `PreCommitted`), and calls `self.determine_response(block_info)`: [9](#0-8) 
7. `determine_response` reads only `block_info.valid` (`Some(true)`) and calls `create_block_acceptance`, producing and sending a real `BlockAccepted` signature over a hash whose recorded state is `GloballyRejected`: [10](#0-9) 

No `move_to`/`check_state` call gates `determine_response`, so the state-machine's own terminal-rejection guard is bypassed entirely by reading a stale field.

### Impact Explanation
This breaks the fail-closed/uniqueness property: a signer must never sign (or claim acceptance) over a hash it has recorded as terminally rejected. The immediate, code-confirmed effect is that this signer's own instance emits and gossips an `Accepted` `BlockResponse` (a valid signature) for a `GloballyRejected` block. This is a genuine safety-relevant inconsistency at the signer level ("rejection recounted as acceptance" locally), matching the Critical category as scoped by the question.

Note for completeness/objectivity: whether this stray signature can actually flip network-wide consensus depends on the receiving signers'/aggregation-side guards. `store_and_process_block_rejection` shows the pattern "store the vote for audit, but `return` early if `block_info.has_reached_consensus()`" before tallying; if `store_and_process_block_signature` follows the same symmetric pattern (not fully retrievable from the indexed context), other signers/nodes that already recorded the hash as `GloballyRejected` would record but not re-tally the stray acceptance, bounding — but not eliminating — the blast radius. Node-side reconciliation is explicitly out of scope for this audit. Regardless, the signer-local violation of the terminal-state invariant is real and reproducible.

### Likelihood Explanation
- Preconditions: the signer must have locally accepted a block (`valid = Some(true)`) that the wider signer set subsequently rejects to the point of `mark_globally_rejected` — a realistic split-decision scenario (e.g. the signer validated before a conflicting/competing block or a chain-state change caused peers to reject).
- Attacker cost: only requires the ability to gossip/re-send the identical `BlockProposal` message (same `signer_signature_hash`) — well within "one miner slot plus gossip," no signer key or majority weight needed.
- Repeatable: yes, any time this local-accept/global-reject divergence occurs for a signer, a repeated proposal retriggers the same bug deterministically.
- The bug is in `determine_response`/`should_reevaluate_block`'s guard logic, not in any external validation layer, so it is not otherwise prevented by the existing `check_block_against_state`, sortition, or auth checks.

### Recommendation
Make `determine_response` (and the `should_reevaluate_block` global-approval guard) authoritative on `BlockInfo::state`, not just `.valid`:
- Short-circuit immediately if `block_info.has_reached_consensus()` (covers both `GloballyAccepted` and `GloballyRejected`), returning the terminal response consistent with `state`, before ever inspecting `.valid`.
- Fix `globally_approved_and_responded` to also match `GloballyRejected` (or add a parallel check), so `should_reevaluate_block` never routes a terminally-rejected block into `determine_response`.
- Consider having `mark_globally_rejected` reconcile `valid` to `Some(false)` for consistency with `mark_locally_rejected`.

fn determine_response_must_not_accept_globally_rejected_block() {
    let (mut block_info, _proposal) = create_block(); // helper already used in signerdb tests
    // Simulate: signer locally accepted the block
    block_info.mark_locally_accepted(false).unwrap();
    assert_eq!(block_info.valid, Some(true));
    assert_eq!(block_info.state, BlockState::LocallyAccepted);

    // Simulate: enough other signers rejected -> globally rejected.
    // check_state permits LocallyAccepted -> GloballyRejected; valid is untouched.
    block_info.mark_globally_rejected().unwrap();
    assert_eq!(block_info.state, BlockState::GloballyRejected);
    assert_eq!(block_info.valid, Some(true)); // stale flag

    // A signer instance re-evaluating this stale BlockInfo (e.g., via
    // should_reevaluate_block/process_pending_responses_for_block) calls determine_response.
    let response = signer.determine_response(&block_info);

    // EXPECTED (fixed behavior): must be None or a Rejected response, never Accepted,
    // because the recorded state is terminal-rejected.
    match response {
        Some(BlockResponse::Accepted(_)) => panic!(
            "determine_response produced an Accepted response for a GloballyRejected block \
             (valid={:?}, state={:?})", block_info.valid, block_info.state
        ),
        _ => {}
    }
