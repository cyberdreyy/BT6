### Title
First-deposit share inflation via direct token donation lets an attacker mint a victim 0 tranche shares and steal their entire deposit - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
`IdleCDOCreditVault._deposit` mints tranche tokens as `_amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` with no minimum-shares check and, unlike `IdleCDOEpochVariant._deposit`, no `_skimDonatedAssets()` call. Because `getContractValue()` counts raw underlying sitting on the CDO, a direct `token.transfer` donation inflates NAV and, after `_updateAccounting()`, the stored tranche price. An attacker who seeds a tranche with a 1-wei first deposit (minting ~1 share when `token` has 18 decimals) and then donates more than the victim's deposit drives the share price above `victimAmount * 1e18`, so the victim is minted exactly 0 shares while `_mintShares` still credits their full `_amount` to `lastNAVAA`/`lastNAVBB`. The attacker then redeems their single share for the entire NAV, stealing the victim's deposit.

### Finding Description
In `IdleCDOCreditVault._deposit` (contracts/IdleCDOCreditVault.sol:191-212) the flow is: `_updateAccounting()` → transfer underlying in → `_mintSharesAtCurrPrice(balanceDelta, msg.sender, _tranche)` → strategy deposit. `_mintSharesAtCurrPrice` (lines 344-348) computes `_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` and `_mintShares` (lines 355-363) mints `_minted` shares but unconditionally adds the full `_underlyings` to `lastNAVAA`/`lastNAVBB`. There is no `if (_minted == 0) revert` and no minimum-liquidity lock.

`_tranchePrice` returns the stored `priceAA`/`priceBB`, which `_updateAccounting` refreshes via `_virtualPriceAux` as `(lastTrancheNAV + trancheGain) * ONE_TRANCHE_TOKEN / trancheSupply` (lines 306-336). NAV (`getContractValue`) includes `_contractTokenBalance(token)` — raw tokens held by the CDO — so a donation counts as `totalGain`, is split to whichever tranche has supply (when only one tranche class exists, `totalGain` goes entirely to it), and permanently raises that tranche's price.

The donation-isolation fix exists but only in the epoch wrapper: `IdleCDOEpochVariant._deposit` calls `_skimDonatedAssets()` before `super._deposit` (contracts/IdleCDOEpochVariant.sol:644-650), and `depositDuringEpoch` also skims and even reverts on `trancheSupply == 0` (lines 677-679). The base `IdleCDOCreditVault._deposit` and `IdleCDO._deposit` (contracts/IdleCDO.sol:234-264) have no equivalent guard, so any deployment of those variants with an 18-decimal underlying (e.g. DAI) is exposed.

Attack path (AA tranche, 18-decimal `token`, tranche supply 0, `priceAA == oneToken` initially):
1. Attacker calls `depositAA(1)` → `_minted = 1 * 1e18 / 1e18 = 1` share; `lastNAVAA = 1`; `trancheSupply = 1`.
2. Attacker does `token.transfer(cdo, victimAmount)` directly (unprivileged donation).
3. Attacker calls `depositAA(1)` again → `_updateAccounting()` sees `totalGain ≈ victimAmount`, assigns it fully to AA, sets `priceAA ≈ (1 + victimAmount) * 1e18 / 1`. The 1-wei deposit mints 0 shares; supply stays 1.
4. Victim's `depositAA(V)` executes: `minted = V * 1e18 / priceAA ≈ V / (V + 1) = 0` shares. `_mintShares` still does `lastNAVAA += V`, absorbing the victim's funds into NAV owned by the attacker's 1 share.
5. Next block (same-block withdraw is blocked by `_checkSameBlock`), attacker calls `withdrawAA(0)` → `toRedeem = 1 * priceAA / 1e18 ≈` the full NAV including the victim's deposit.

No guard stops this: `_guarded` is only a TVL cap, `_checkDefault`/`lossToleranceBps` only react to losses, `whenNotPaused` is satisfied, there is no skim in this contract, and no `minted > 0` assertion exists. For 6-decimal underlyings the required donation is `V * 1e12`, which is uneconomical, so the exposure is limited to 18-decimal-underlying deployments of the non-epoch variants.

### Impact Explanation
Direct theft of the full first deposit into any empty tranche: the victim receives 0 tranche tokens and cannot withdraw (`_checkIs0` on zero balance), while the attacker's single share becomes redeemable for the entire tranche NAV. Loss equals the victim's deposited amount minus dust.

### Likelihood Explanation
Requires a tranche with zero supply and an 18-decimal underlying, plus front-running/ordering the victim's first deposit — standard mempool conditions. The epoch variant is protected by `_skimDonatedAssets` and the supply-0 revert in `depositDuringEpoch`, but `IdleCDOCreditVault`/`IdleCDO` remain callable directly in deployments using them, and the absence of the guard in the base class makes any future non-epoch deployment vulnerable.

### Recommendation
- Add a `_skimDonatedAssets()`-equivalent donation sweep (send contract token balance in excess of accounted NAV to `feeReceiver`) at the top of `IdleCDOCreditVault._deposit`, mirroring `IdleCDOEpochVariant._deposit`.
- Revert in `_mintSharesAtCurrPrice`/`_mintShares` when `_amount > 0` but `_minted == 0`.
- Enforce a minimum first-deposit size and/or mint/burn a dead-share reserve on the first deposit so `trancheSupply` can never be 1 wei-share.

### Proof of Concept
Foundry test against an `IdleCDOCreditVault` instance whose `token` has 18 decimals (reuse the existing credit-vault test harness in `test/foundry/IdleCreditVault.t.sol`, deployed without the `IdleCDOEpochVariant` skim override):

```solidity
function testFirstDepositorDrain() public {
    address attacker = makeAddr("attacker");
    address victim = makeAddr("victim");
    uint256 victimDeposit = 1_000 * 1e18;

    underlying.mint(attacker, victimDeposit + 2);
    underlying.mint(victim, victimDeposit);

    // 1) seed the AA tranche with 1 wei -> 1 share (priceAA == oneToken)
    vm.startPrank(attacker);
    underlying.approve(address(cdo), type(uint256).max);
    cdo.depositAA(1);
    assertEq(AAtranche.balanceOf(attacker), 1);

    // 2) donate more than the victim's deposit directly to the CDO
    underlying.transfer(address(cdo), victimDeposit);

    // 3) trigger _updateAccounting via a second 1-wei deposit
    cdo.depositAA(1);
    vm.stopPrank();

    // 4) victim deposits V and receives 0 shares
    vm.startPrank(victim);
    underlying.approve(address(cdo), type(uint256).max);
    uint256 minted = cdo.depositAA(victimDeposit);
    vm.stopPrank();
    assertEq(minted, 0, "victim minted 0 shares");

    // 5) attacker redeems next block for ~all NAV (incl. victim funds)
    vm.roll(block.number + 1);
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdo.withdrawAA(0);
    assertGt(underlying.balanceOf(attacker) - pre, victimDeposit, "attacker drained victim deposit");
}
```

Note: I could not verify the exact initial value of `priceAA`/`priceBB` storage (assumed `oneToken` from the `supply == 0 → return (oneToken, 0)` branch in `_virtualPriceAux`) or whether all production deployments route through `IdleCDOEpochVariant`; if every live deployment uses the epoch wrapper, the residual risk is confined to `IdleCDOCreditVault`/base-`IdleCDO` deployments and should be treated as defense-in-depth rather than an actively exploitable path.
