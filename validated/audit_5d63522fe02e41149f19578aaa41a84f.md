### Title
Instant performance-fee updates allow lenders to front-run withdrawal fees - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault.setFeeParams` applies a new performance fee immediately. A KYC-approved tranche holder can observe an honest owner’s pending fee increase and call `requestWithdraw` first, permanently fixing the withdrawal receipt under the old fee.

### Finding Description
`setFeeParams` validates and stores `fee`, `feeSplit`, `managementFee`, and `feeReceiver` in one transaction, without a proposal or activation timestamp. [1](#0-0) 

`requestWithdraw` calculates fees from the current `fee` value and immediately fixes `_underlyings` for the user’s receipt. It then records that fixed amount in the credit vault and burns the tranche tokens. [2](#0-1) 

For positive projected yield, `_totalWithdrawFees` includes the performance fee through `_netGainAfterFees`, which multiplies the remaining gain by the current `fee`. [3](#0-2) 

Therefore, an unprivileged lender can sequence around the owner transaction:

```text
attacker.requestWithdraw(...)
owner.setFeeParams(..., increasedFee, ...)
```

The receipt remains denominated using the old fee, and the later claim pays the pre-increase amount. The user’s transaction is otherwise valid: `requestWithdraw` only requires a supported tranche, withdrawal requests to be enabled, and `isWalletAllowed(msg.sender)`. [4](#0-3) 

### Impact Explanation
This causes direct loss of protocol fees. For example, with a 10% fee increase and 1,000 USDC of projected withdrawal yield, the attacker preserves approximately 100 USDC that would have been charged as performance fees after the update.

Because withdrawal receipts mint a fixed strategy-token amount, the avoided fee is not recalculated when the receipt is later claimed. [5](#0-4) 

### Likelihood Explanation
Likelihood is medium. The attack requires:

- a withdrawal-enabled epoch phase;
- a KYC-approved tranche holder;
- an observable owner transaction increasing `fee` or `managementFee`;
- successful transaction ordering before the owner transaction.

No privileged compromise, default, oracle manipulation, or special market condition is required.

### Recommendation
Introduce a two-step fee update:

1. `proposeFeeParams(...)` stores the proposed values and an `activationTimestamp`.
2. `applyFeeParams()` becomes callable only after a configured delay.
3. Optionally allow cancellation before activation.
4. Emit the proposed values and activation time.

Alternatively, apply updated fees only to withdrawal requests made after the next epoch boundary, giving users the remainder of the current epoch to react.

### Proof of Concept
This test can be added to `test/foundry/IdleCreditVault.t.sol`, which already deploys a mainnet-fork credit vault with `initialProvidedApr = 10e18`, a 36.5-day epoch, and a five-day buffer.

```solidity
function testFrontRunPerformanceFeeIncrease() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // Existing credit-vault fixture:
    // - fee == 0
    // - managementFee == 0
    // - initialProvidedApr == 10%
    // - withdrawal requests are allowed
    idleCDO.depositAA(amount);

    uint256 snapshot = vm.snapshot();

    // Quote/receipt under the current 0% performance fee.
    uint256 amountBeforeFeeIncrease =
        cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Replay the same withdrawal after the owner raises the fee.
    vm.revertTo(snapshot);
    vm.prank(owner);
    cdoEpoch.setFeeParams(
        cdoEpoch.feeReceiver(),
        10_000,              // 10% performance fee
        cdoEpoch.feeSplit(),
        cdoEpoch.managementFee()
    );

    uint256 amountAfterFeeIncrease =
        cdoEpoch.requestWithdraw(0, address(AAtranche));

    uint256 avoidedFee = amountBeforeFeeIncrease - amountAfterFeeIncrease;
    assertGt(avoidedFee, 0, "receipt should be cheaper before fee update");

    // Actual exploit ordering: the lender requests before the owner update.
    vm.revertTo(snapshot);
    uint256 attackerReceipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

    vm.prank(owner);
    cdoEpoch.setFeeParams(
        cdoEpoch.feeReceiver(),
        10_000,
        cdoEpoch.feeSplit(),
        cdoEpoch.managementFee()
    );

    // The receipt was fixed before the fee change and remains at the old amount.
    assertEq(attackerReceipt, amountBeforeFeeIncrease);
    assertEq(attackerReceipt, amountAfterFeeIncrease + avoidedFee);
}
```

With the fixture’s parameters, the projected epoch yield is approximately 1,000 USDC on a 10,000 USDC deposit. Increasing `fee` to `10_000` makes the post-update receipt approximately 100 USDC smaller, while the front-running receipt preserves that amount for the attacker.

  /// @notice Apply projected management and performance fees to a positive gain.
  function _netGainAfterFees(uint256 _gain, uint256 _managementFee) private view returns (uint256 netGain) {
    if (_managementFee >= _gain) return netGain;
    // remove mgmt fee and performance fee
    _gain -= _managementFee;
    return _gain - _gain * fee / FULL_ALLOC;
  }

  /// @notice Calculate total fees charged on a withdrawal request.
  /// @param _principal Principal leaving live NAV.
  /// @param _interest Projected interest for the requested principal.
  /// @return Total management and performance fees to subtract from principal plus projected interest.
  function _totalWithdrawFees(uint256 _principal, uint256 _interest) private view returns (uint256) {
    uint256 _mgmtFee = _calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration());
    // When interest covers management fees, interest - netGain equals management fee plus performance fee.
    return _mgmtFee >= _interest ?
      _mgmtFee :
      _interest - _netGainAfterFees(_interest, _mgmtFee);
