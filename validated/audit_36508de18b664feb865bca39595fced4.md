### Title
Unbounded per-request cost in `index_scan_accounts` when secondary-index bucket accounts fail post-index filters, bypassing `byte_limit_for_scan` abort - ([File: accounts-db/src/accounts_db.rs])

### Finding Description
`AccountsDb::index_scan_accounts` iterates every pubkey returned by `self.accounts_index.get_index_key_pubkeys(&index_key)` and unconditionally performs a full `self.do_load(...)` for each one before calling `scan_func`, checking `config.is_aborted()` only once per loop iteration: [1](#0-0) 

`get_index_key_pubkeys` materializes the entire secondary-index bucket for the given `IndexKey` (e.g. `SplTokenMint`) into a `Vec<Pubkey>` up front, with no size cap: [2](#0-1) 

The only cost bound, `byte_limit_for_scan`, is enforced in `Accounts::load_by_index_key_with_filter`, but it is only incremented for accounts that pass the caller-supplied `filter`: [3](#0-2) [4](#0-3) 

The RPC path `get_filtered_spl_token_accounts_by_mint` reaches this via `get_filtered_indexed_accounts` with an `IndexKey::SplTokenMint(mint_key)` plus post-index filters (`TokenAccountState`, `Memcmp` on the mint offset): [5](#0-4) 

Because the abort/byte-accumulation logic (`config.abort()`) is only triggered when `filter(account)` returns `true` (`use_account`), an attacker can store, under a single rate-limited stream of prior transactions, a very large number of accounts that are indexed under one `SplTokenMint` key (satisfying the mint-offset bytes used by the secondary index's insertion logic in `update_spl_token_secondary_indexes`) but that are crafted so the RPC-side post-filters (`TokenAccountState`/`Memcmp`) reject them — e.g. by corrupting the SPL-token "initialized" state byte or owner program after insertion, or exploiting the documented edge case where an account remains indexed under a mint after being "wiped and reinitialized," as explicitly called out in the code comment: [6](#0-5) 

For every such rejected account, `sum` in `accumulate_and_check_scan_result_size` never increases, so `config.abort()` is never called, and `config.is_aborted()` never becomes true — meaning `index_scan_accounts`'s loop cannot early-exit and must call `do_load` (a real storage/page-cache read) for every pubkey in the bucket. The cost of the single `getTokenAccountsByOwner` call thus scales with the size of the attacker-controlled index bucket rather than with `byte_limit_for_scan`.

### Impact Explanation
A single `getTokenAccountsByOwner` request can force the validator's RPC thread to perform an unbounded number of `do_load` storage reads (one per indexed-but-filtered-out pubkey), consuming CPU and I/O disproportionate to any configured `byte_limit_for_scan`. This matches the "unbounded cost for a single low-rate call" bounty category — a soft-DoS on accounts-db shared read paths (scan tracker, storage) that can degrade concurrent reads/scans for other RPC clients, without requiring elevated privileges, multiple calls, or unfiltered `getProgramAccounts`.

### Likelihood Explanation
The precondition — being able to write many small accounts into a single `SplTokenMint` secondary-index bucket that are structured to fail the RPC's redundant post-filters — is achievable purely through normal, rate-limited on-chain writes (creating/reinitializing SPL token accounts under one mint). No validator/leader/gossip control or config access is required. The exploit needs only a single `getTokenAccountsByOwner` call to trigger the full unfiltered walk of the bucket, making it fully repeatable once the bucket is populated.

### Recommendation
Bound the cost of `index_scan_accounts` independent of the caller-supplied `filter`'s pass/fail outcome — e.g., cap or count the number of raw `do_load` calls performed against the secondary-index bucket (not just bytes of accepted results), or check `config.is_aborted()`/a separate load-count limit before invoking `do_load`, so that filtered-out accounts still contribute to the abort condition. Additionally, consider enforcing a maximum bucket size for secondary indexes or requiring paginated/streaming access when a bucket is large, rather than materializing the full pubkey list in `get_index_key_pubkeys` and reading every entry from storage in a single request.

### Proof of Concept
Add an accounts-db integration test that:
1. Builds an `AccountsDb` with `AccountIndex::SplTokenMint` enabled (`spl_token_mint_index_enabled()`), following the pattern in `test_flush_purged_zero_lamport_account_purges_secondary_index`.
2. Stores N (e.g. 500,000) small SPL-token-like accounts all sharing the same mint key so they are inserted into `spl_token_mint_index`, but structured (e.g. `SPL_TOKEN_INITIALIZED_OFFSET` byte left unset, or owner not `spl_generic_token::token::id()`) so a `TokenAccountState`-style filter passed to `load_by_index_key_with_filter` rejects every one.
3. Calls `Accounts::load_by_index_key_with_filter` once with `byte_limit_for_scan = Some(small_value)` and a filter matching the RPC's rejecting behavior, i.e. `|_account| false`.
4. Asserts wall-clock time / number of `do_load` invocations (instrumented via a counting wrapper or `datapoint` hook) scales with N and exceeds a fixed bound derived from `byte_limit_for_scan`, demonstrating the abort never fires (`config.is_aborted()` stays false throughout) despite the byte limit being configured — proving cost is proportional to bucket size, not to `byte_limit_for_scan`.
