### Title
Local-admin identity granted purely by case-insensitive email match without verifying that account's password - (File: core/sessions/ldapauth/ldap.go)

### Summary
`POST /sessions` reaches `SessionsController.Create` → `AuthenticationProvider().CreateSession` → `ldapAuthenticator.CreateSession`, which authenticates the caller's password solely against the upstream LDAP directory, then calls `FindUser` to determine the session's role. [1](#0-0)  Inside `FindUser`, if a row in the local `users` table matches the supplied email case-insensitively, that row's full identity (including `Role`) is returned and used for the session — without ever checking that row's `hashed_password`. [2](#0-1) 

### Finding Description
`CreateSession` binds to the LDAP server using `ldap.EscapeFilter(strings.ToLower(sr.Email))` and the attacker-supplied password: `conn.Bind(searchBaseDN, sr.Password)`. If this succeeds, the code assumes the request is legitimate and calls `l.FindUser(ctx, escapedEmail)` purely to resolve a role for the session/audit record. [3](#0-2) 

`FindUser` first checks the **local** `users` table (used for CLI/local-admin accounts) with a case-insensitive match: `SELECT * FROM users WHERE lower(email) = lower($1)`. If a row is found, it is returned immediately as the authenticated user, including its `Role` — no comparison is made between the local row's `HashedPassword` and `sr.Password`, and no confirmation is made that the LDAP-authenticated identity is actually the same account as the local-admin row. [2](#0-1) 

This differs from every other secret-verification path in the same package and sibling `localauth`/`oidcauth` packages, which explicitly guard against this exact "lookup vs. verified identity" mismatch by re-comparing the queried row's email in Go with `constantTimeEmailCompare` before trusting the row:
- `ldapAuthenticator.localLoginFallback` [4](#0-3) 
- `localauth.orm.CreateSession` [5](#0-4) 
- `oidcauth.oidcAuthenticator.localLoginFallback` [6](#0-5) 

In the vulnerable branch of `FindUser`, that safeguard is entirely absent, and — more importantly — the row's password is never checked at all in this call path, because the password was already "verified" against a completely different credential store (the upstream LDAP directory). The two identities (the LDAP-bound account and the local `users` row) are only linked by a `lower()` string match, so:

1. Any account that successfully binds to the LDAP server (i.e., any holder of valid LDAP credentials for *some* directory entry) whose `uid`/email happens to match — case-insensitively — an existing row in the local `users` table (used for the node's CLI-created local admin), is handed that row's `Role` and treated as that identity for the resulting `ldap_sessions` entry, without the local admin's actual `hashed_password` ever being checked.
2. Because matching is case-insensitive (`lower(email) = lower($1)`) and no normalization/whitespace handling is applied elsewhere, an attacker who controls (or can create) an LDAP account whose email differs only in case from the local-admin's stored email can trigger this collision.

This satisfies the audit's invariant violation: "the identity looked up and the identity whose secret is verified must be the same row" — here they are not even from the same authentication backend, and the case-insensitive lookup widens the collision surface beyond exact string matches.

### Impact Explanation
If the local `users` table contains an admin-role account (the CLI-provisioned local admin, which coexists with LDAP auth per this file's design) whose email collides case-insensitively with any account in the external LDAP directory, an attacker who controls that LDAP account's password (their own account, not the admin's) is granted an authenticated session with the local admin's `Role` (potentially `UserRoleAdmin`), stored in `ldap_sessions` and usable for subsequent authenticated requests. This maps to the Immunefi "Critical: node takeover" class — an attacker obtains admin control of the node (key export, unauthorized transaction submission) without ever knowing the local admin's real password. [7](#0-6) 

### Likelihood Explanation
This requires: (1) the node configured with the LDAP authentication provider, (2) at least one local CLI admin row present in the `users` table (explicitly supported and documented as coexisting with LDAP auth), and (3) an email collision (case-insensitive) between that local row and some account the attacker controls in the external LDAP directory. Given the local admin account is typically created using the real operator's own email/uid, and organizations often provision LDAP accounts with the same or predictably-cased email, this collision is realistic in typical deployments, not purely theoretical misconfiguration — it is a structural flaw in how `FindUser` reconciles two independent identity stores.

### Recommendation
In `FindUser`, before trusting/returning `foundLocalAdminUser`, verify that the row genuinely corresponds to the account whose credential was checked: either (a) do not consult the local `users` table at all from the LDAP-bind-success path (since that row's password was never verified), and only allow local-admin fallback via the dedicated `localLoginFallback` path that does check `HashedPassword` and does the `constantTimeEmailCompare` guard, or (b) require an exact (not merely case-insensitive) match plus explicit password verification against `foundLocalAdminUser.HashedPassword` whenever this branch is taken from `CreateSession`.

### Proof of Concept
Go handler-level integration test plan:
1. Seed the local `users` table with an admin row, e.g. `email = "Admin@Example.com"`, role `admin`, with some `hashed_password` unknown to the attacker.
2. Configure a fake/mock LDAP server (via the `LDAPClient`/`LDAPConn` test doubles already used in `ldap_test.go`) with a distinct directory account `uid=admin@example.com` (or any case-variant) whose password is `attackerpass`, and ensure this LDAP account has no assigned RBAC groups.
3. Call `ldapAuthenticator.CreateSession(ctx, sessions.SessionRequest{Email: "admin@example.com", Password: "attackerpass"})`.
4. Assert: the call succeeds (`err == nil`), and the resulting `ldap_sessions` row's `user_role` is `admin` — even though `attackerpass` was never checked against the local admin row's `hashed_password`.
5. Contrast with `localLoginFallback`/`localauth.orm.CreateSession`, which correctly reject case-only-collision cross-identity confusion via `constantTimeEmailCompare` plus `CheckPasswordHash`, to demonstrate the missing guard is specific to this branch of `FindUser`.

```go
func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}
```

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}
```
