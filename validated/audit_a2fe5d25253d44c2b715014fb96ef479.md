### Title
User `script` command can neutralize `trapTerm` and reinstate SIGTERM script-body-dump leak - (File: functions/script_legacy/internal/script_header.go)

### Summary
`ScriptHeader.Generate` installs `trap exit 1 TERM` once at the top of the generated script, but `ScriptGenerator.GenerateScript` / `CommandProcessor.writeNormalCommand` then splice each user-supplied `script` command directly into that same top-level shell — unlike `shells/bash.go`'s `Finish()` and `scriptwriter.go`'s `buildBashScript`, which run user commands inside a subshell (`(trap 'exit 1' TERM; eval ...) < /dev/null`) so the trap can't be touched by the payload. Because the trap here lives in the same shell process as the user's commands, a command such as `trap - TERM` runs with full trap-modification privilege and undoes the protection for the remainder of the script.

### Finding Description
`ScriptHeader.Generate` (functions/script_legacy/internal/script_header.go:49-73) emits:
```
#!<shell>
trap exit 1 TERM
...
```
`ScriptGenerator.GenerateScript` (functions/script_legacy/internal/script_generator.go:41-64) then calls `CommandProcessor.ProcessCommand` for each command in the caller-supplied `commands []string`, which in `writeNormalCommand` (functions/script_legacy/internal/command_processor.go:49-60) writes the command verbatim into the buffer right after the header — there is no subshell wrapping, no `eval`, and no re-installation of the trap around/after each command.

This is architecturally different from the two other script generators in the same repo that address the exact same SIGTERM-dump issue (issue #39005):
- `shells/bash.go` `Finish()` wraps the whole user body in `(trap 'exit 1' TERM; eval ...) < /dev/null`, re-declaring the trap inside an isolated subshell.
- `functions/concrete/run/stages/internal/scriptwriter/scriptwriter.go` `buildBashScript` does the same: `(trap 'exit 1' TERM; eval ...) < /dev/null`.

In both of those, even if the user's command runs `trap - TERM`, it only clears the trap for the inner eval'd subshell process; the outer subshell that receives SIGTERM from the cancellation kill loop retains its own, separately-scoped trap (bash resets traps to default across subshell entry, and setting a trap inside `eval` only affects the current shell environment of the subshell, not the parent). By contrast, in `script_header.go`'s design there is only one shell process for the whole script — the trap and the user commands share the same shell environment — so `trap - TERM` (or redefining `trap ... TERM` to something else) issued as one of the `script` array entries directly overwrites the protection installed by `trapTerm`.

Attacker-controlled input: the `script` input array consumed by `script_legacy.Run` (functions/script_legacy/script_legacy.go:97-105) is fully attacker-controlled pipeline/job configuration (an unprivileged pipeline author defines the `script:` commands executed under `FF_SCRIPT_TO_STEP_MIGRATION`). No validation or sanitization of command content is performed before splicing it into the shared script (only ANSI-escape hex-escaping of the echoed log line is applied, not the command itself).

Exploit flow:
1. Pipeline author defines a job step whose `script` includes `trap - TERM` (or `trap 'echo pwned' TERM`) as an early command, followed by a long-running command (e.g., `sleep 30`) so cancellation lands mid-script.
2. Runner (with `FF_SCRIPT_TO_STEP_MIGRATION` enabled) generates the script via `ScriptGenerator.GenerateScript`, producing a single shell script where `trap exit 1 TERM` and the attacker's `trap - TERM` both execute in the same shell.
3. Job is cancelled; Runner's cancellation path sends SIGTERM to the script process(es), same as documented for issue #39005.
4. Because the trap has been cleared/redefined by the attacker's own command, the shell no longer performs a clean `exit 1` on SIGTERM. On an affected bash version (< 4.4 or ≥ 5.3, per the comment in `shells/bash.go:74-88`), the default signal-death path fires, and bash dumps the currently executing command/pipeline text to stderr, which flows into the job trace/log.
5. If any subsequent (or the currently executing) command in the script contains an interpolated secret (e.g., `curl -H "Authorization: Bearer $SECRET_TOKEN" ...`), the literal command text — with the shell-level variable expansion already substituted or the raw literal command depending on what gets printed — can be exposed in the dumped output, landing in the job log outside masking's control (masking works on values as printed by application code, not necessarily on this raw signal-death diagnostic text).

### Impact Explanation
This reinstates the exact log-leak class that `trapTerm`/issue #39005 was designed to prevent, but self-inflicted by trivial user script content rather than requiring a bash-version edge case alone. On an affected bash build, a cancelled job can dump script body/command text (potentially containing secrets embedded via variable expansion in command arguments) to the job's public trace, violating the "cancellation must never expose masked/secret values" invariant, scoped specifically to the `FF_SCRIPT_TO_STEP_MIGRATION` code path exercised by `script_legacy.go`.

### Likelihood Explanation
Preconditions: `FF_SCRIPT_TO_STEP_MIGRATION` enabled (opt-in feature flag) and an affected bash version in the execution environment (< 4.4 or ≥ 5.3). Given those, the exploit requires nothing more than an unprivileged pipeline author writing `trap - TERM` as one line of their own `script:` — a completely ordinary, permitted shell command with no special privilege — and getting the job cancelled while a later command with a secret is running or about to run. This is trivially reproducible and repeatable; it does not depend on race conditions beyond normal cancellation timing already exercised by GitLab's own `RunBuildWithScriptBodyLeakOnCancel` regression test for the other two code paths.

### Recommendation
Mirror the fix already applied in `shells/bash.go` and `scriptwriter.go`: wrap the user command body in an isolated subshell that re-declares the TERM trap, e.g. change `ScriptGenerator.GenerateScript` (or `ScriptHeader.Generate`) to emit something like:
```
trap exit 1 TERM
...
( trap exit 1 TERM; <user commands> ) < /dev/null
exit 0
```
so that any `trap` command a user issues only affects the inner subshell's trap table for that process, while the outer script process (the one actually receiving SIGTERM from the cancellation kill-loop) keeps its own independent, non-attacker-modifiable trap. Alternatively, if isolating into a subshell is impractical for this particular script format, at minimum disallow/neutralize `trap` reassignment on the TERM signal from user-supplied commands, or re-assert `trap exit 1 TERM` immediately after each user command is executed.

### Proof of Concept
Go test in `functions/script_legacy/internal` (extending the existing `executor_test.go`/`script_generator_test.go` patterns), plus an integration-style PoC:

```go
func TestScriptHeader_UserTrapOverridesTermTrap(t *testing.T) {
    gen := NewScriptGenerator(ScriptGeneratorConfig{ShellPath: "/bin/bash"})
    commands := []string{
        "trap - TERM", // attacker neutralizes the protective trap
        "echo SECRET_MARKER_$MY_SECRET",
        "sleep 30",
    }
    script := gen.GenerateScript(commands)

    // Demonstrates the generated script contains both the protective trap
    // AND an unguarded user command capable of clearing it in the SAME shell.
    require.Contains(t, script, "trap exit 1 TERM")
    require.Contains(t, script, "trap - TERM")
}
```

2. Job script: `["trap - TERM", "echo build-started", "export TOKEN=s3cr3t-canary", "sleep 60 # uses $TOKEN in a later masked command"]`.
