### Title
Unfunded instant-withdraw receipts pay out in full from other users' funded claims — (`File: contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
CVE-2018-4443 is a memory-corruption bug: stale state is interpreted as valid data. The strongest analog in idle-tranches is a stale-claim corruption in `IdleCreditVault.claimInstantWithdrawRequest`: the strategy pays out the entire aggregate `instantWithdrawsRequests[_user]` balance without checking whether that balance was actually funded via `collectInstantWithdrawFunds`, mixing funded and unfunded receipt portions into a single claimable integer. A user can combine an already-funded instant receipt with a newly-created unfunded instant request and claim both at par, spending underlyings reserved for other users' funded normal/instant withdraw claims.

### Finding Description
`requestInstantWithdraw` mints a strategy-token receipt to the user and increases both `instantWithdrawsRequests[_user]` and the unfunded remainder `pendingInstantWithdraws` [1](#0-0) . Funding arrives later when the CDO calls `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls underlying from the CDO [2](#0-1) .

However `claimInstantWithdrawRequest` pays out `instantWithdrawsRequests[_user]` in full and never consults `pendingInstantWithdraws` or `instantWithdrawsRequestsByEpoch` to determine how much of the user's aggregate was actually funded [3](#0-2) . It also never decrements `pendingInstantWithdraws`, so after the claim the strategy still believes the unfunded remainder exists while the user's aggregate counter has been zeroed — corrupted accounting that understates outstanding borrower obligations.

The only isolation guard, `_transferFundedClaim`, protects solely `defaultRecoveryReserve` and only when it is non-zero [4](#0-3) . Before default, all funded normal receipts (`_transferFundedClaim` target for `_claimFundedWithdrawRequest` and `_claimLossAdjustedWithdrawRequest`) and funded instant receipts sit in the same undifferentiated underlying balance, so an unfunded instant claim spends them directly.

Unlike the normal-withdraw path — which enforces one-epoch gating via `epochNumber <= lastWithdrawRequest[_user]` [5](#0-4)  — the instant path has no per-epoch funding check, and `requestInstantWithdraw` has no equivalent of the `requestWithdraw` guard that forces users to claim previous receipts before stacking new ones [6](#0-5) .

### Impact Explanation
Direct theft and insolvency: the attacker withdraws underlyings they were never funded for, paid from the same strategy balance backing other users' funded withdraw receipts. Loss is quantified as the unfunded portion of the attacker's `instantWithdrawsRequests` claim (up to the full second request amount), and manifests as the last funded claimants being unable to withdraw (permanent freezing of their claims). Additionally, `pendingInstantWithdraws` is left permanently overstated, which corrupts `defaultPendingClaimBasis` if a default is later finalized [7](#0-6) .

### Likelihood Explanation
Requires the instant-withdraw mode and a sequencing where the CDO routes `claimInstantWithdrawRequest` while part of the user's aggregate is still unfunded (e.g., user holds an old funded instant receipt, then files a new instant request in a subsequent epoch before the next collection, or only partial funding was collected because available liquidity was lower than `instantWithdrawClaimsByEpoch[epochNumber]` — a state the code explicitly contemplates in `_defaultPrefundedInstantReserve` [8](#0-7) ). The attacker is an ordinary KYC'd tranche holder; all privileged actors remain honest. Likelihood is moderate: it depends on the CDO permitting a claim call while `pendingInstantWithdraws` covers part of the user's aggregate, which the strategy itself does not enforce.

### Recommendation
- Track the funded portion per user (or per epoch) and cap `claimInstantWithdrawRequest` to it, e.g. pay `min(instantWithdrawsRequests[_user], fundedInstantForUser)`; or
- In `claimInstantWithdrawRequest`, subtract the still-unfunded share: derive the user's unfunded portion from `instantWithdrawsRequestsByEpoch[_user][epochNumber]` vs `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch`, and decrement `pendingInstantWithdraws` for whatever portion of the claim is being paid early, so bookkeeping stays consistent.
- Mirror the `requestWithdraw` stacking guard so a user must claim outstanding instant receipts before opening new ones.

### Proof of Concept
Foundry fork PoC (schematic; run against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. Epoch 1: enable instant withdraws, attacker requests instant withdraw X.
//    Manager stops epoch; CDO calls collectInstantWithdrawFunds(X) -> funded.
//    Attacker does NOT claim.
// 2. Epoch 2: attacker calls requestInstantWithdraw(Y) again.
//    Strategy: instantWithdrawsRequests[attacker] = X + Y,
//    pendingInstantWithdraws += Y (unfunded).
// 3. Before the CDO collects Y (or while only partially collected),
//    attacker calls cdo.claimInstantWithdrawRequest().
// 4. Strategy pays X + Y via _transferFundedClaim; with defaultRecoveryReserve == 0
//    the guard passes as long as the strategy balance (which includes other
//    users' funded normal/instant claims) >= X + Y.
// 5. Assert: attacker received Y more than funded; pendingInstantWithdraws still
//    counts Y (accounting corrupted); a second user's funded claim of Z now
//    reverts on insufficient balance or leaves the vault insolvent by Y.

assertEq(IIdleCreditVault(strategy).instantWithdrawRequests(attacker), 0);
assertGt(IIdleCreditVault(strategy).pendingInstantWithdraws(), 0); // stale Y
vm.expectRevert(); // victim's funded claim
cdoEpoch.claimWithdrawRequest();
```

Uncertainty: whether `IdleCDOEpochVariant.claimInstantWithdrawRequest` itself gates on full collection before forwarding to the strategy could not be fully verified within the available analysis; if the CDO blocks the call, the strategy-level check is still the correct defense-in-depth fix, and the `pendingInstantWithdraws` accounting drift on claim remains a defect regardless.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.

    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
