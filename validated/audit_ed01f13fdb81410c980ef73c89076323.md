### Title
Loss-adjusted withdraw receipts keyed to a stale epoch escape the haircut and claim at par, draining the credit vault - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Keycloak bug (CWE-73) lets an attacker force a lookup outside the expected context. The analog in `IdleCreditVault` is the epoch key used to retrieve a pending receipt's loss-recovery price: the price is written under `epochNumber` at collect time (`collectWithdrawFunds`, line 421) while claims read it under `lastWithdrawRequest[_user]` (line 790), and `epochNumber` is incremented inside `deposit()` during `stopEpoch` (lines 607-610). An unprivileged lender can therefore hold a receipt keyed to epoch N while its haircut is stored under epoch N+1, traverse to the "wrong path" (a zero entry), and be paid at par on funds that were only partially collected — an insolvency for all other pending claimants.

### Finding Description
`requestWithdraw` records the receipt under the current `epochNumber`:

- `lastWithdrawRequest[_user] = currentEpoch` (line 282)
- `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (line 293)

On a lossy stop (`stopEpochWithDuration`/`previewLossAdjustedWithdrawFunds` path), the CDO funds only `pendingToFund` and calls `collectWithdrawFunds`, which stores:

```solidity
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

But `epochNumber` is bumped inside `deposit()` — which runs during the same stopEpoch while `isEpochRunning()` is still true (lines 607-610, comment: "deposit done on stopEpoch ... so we reset the counter `epochNumber += 1`"). Funding a loss necessarily requires the borrower-repayment deposit first, so the recovery price lands under `epochNumber = N+1`, while every receipt it should haircut is keyed under `N`.

At claim time, `_claimLossAdjustedWithdrawRequest` traverses the epoch key stored on the user:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];      // == N
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]; // 0 (written at N+1)
if (lossRecoveryPrice == 0) return amount;           // silently skips the haircut
```

Execution then falls into `_claimFundedWithdrawRequest`, whose only gating is `epochNumber > lastWithdrawRequest[_user]` — now satisfied because `epochNumber` is `N+1` — and pays the full `withdrawsRequests[_user]` at par via `_transferFundedClaim`. The same stale-key confusion defeats the request-time guard at lines 263-270: `lossRecoveryPriceByEpoch[lastWithdrawRequest]` reads 0 for epoch N, so a user with an unclaimed, haircutted receipt can freely open a new request in a later epoch, consolidating basis that then also escapes the N+1 haircut or is wrongly haircutted by an unrelated epoch's price.

### Impact Explanation
The vault only collected `pendingToFund = pendingBasis - pendingLoss` underlying, yet pays out the full `pendingBasis`. The shortfall is taken from underlying held for other funded claims and the default/recovery reserve, so either:

- the attacker withdraws more than their fair, loss-socialized share (direct theft of other claimants' funded proceeds), or
- later claimants' `claimWithdrawRequest` calls revert on insufficient balance — permanent freezing of unclaimed, already-funded yield.

Loss amount ≈ `pendingLoss` (the intended aggregate haircut), bounded only by pending withdraw volume at the lossy stop. The broken invariant is the loss waterfall: the stopEpoch loss is meant to be shared pro-rata by pending receipts, but a wrong epoch key lets receipts claim outside the loss context — exactly the "read a Vault file outside the expected context" primitive of CVE-2024-10492.

### Likelihood Explanation
Triggering requires only a normal user flow: an allowed (KYC'd) wallet calls `requestWithdraw` in epoch N, then the epoch is stopped with a realized loss (`_lossAmount > 0`, partially funded) — an honest manager/borrower action, not attacker-controlled. Any pending receipt then pays at par instead of the haircut. Because the key mismatch arises from the `deposit()`→`epochNumber++`→`collectWithdrawFunds` ordering inside a single stop, the bug is systematic rather than a race: every pending receipt in that epoch escapes. (Caveat: the exact call order inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` — whether `collectWithdrawFunds` is ever invoked before the epoch-bumping `deposit` — could not be fully verified within this scan; if it were, receipts made in the new epoch would instead be haircutted by a price stored under a key that precedes their request epoch, which is the same class of cross-epoch confusion in the opposite direction.)

### Recommendation
Use a single, consistent epoch key for loss-adjusted receipts:

- In `collectWithdrawFunds`, store the price under the epoch in which the receipts were created — e.g., `lossRecoveryPriceByEpoch[epochNumber - 1]` or an explicit `_receiptEpoch` parameter passed by the CDO — matching `lastWithdrawRequest`/`withdrawsRequestsByEpoch`.
- Alternatively, snapshot `epochNumber` into a `pendingWithdrawEpoch`/`lastLossEpoch` variable at `stopEpoch` entry and use it for both the write in `collectWithdrawFunds` and the reads in `_claimLossAdjustedWithdrawRequest`/`requestWithdraw`.
- Add a regression test: request in epoch N → `stopEpoch` with `_lossAmount > 0` and partial funding → assert the claim equals `basis * lossRecoveryPrice / 1e18`, not the par amount.

### Proof of Concept
```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
// Assumes the repo's existing IdleCreditVault.t.sol harness: cdoEpoch, strategy,
// AAtranche, defaultUnderlying, manager, borrower helpers (_depositWithUser,
// _startEpochAndCheckPrices, _forceLastEpochAprToZero).

contract LossEpochKeyTraversalPoC is Test {
    function test_PendingReceiptEscapesLossHaircut() external {
        uint256 ONE_SCALE = 1e6; // USDC-like underlying
        address alice = makeAddr("alice");
        address bob = makeAddr("bob");

        uint256 depositAmt = 100_000 * ONE_SCALE;
        _depositWithUser(alice, depositAmt, true);
        _depositWithUser(bob, depositAmt, true);
        idleCDO.depositAA(depositAmt); // helper per repo harness

        _startEpochAndCheckPrices(0);

        // Alice requests a withdraw during epoch N (epochNumber == N)
        uint256 aliceTranche = IERC20(AAtranche).balanceOf(alice);
        vm.prank(alice);
        uint256 aliceBasis = cdoEpoch.requestWithdraw(aliceTranche / 2, address(AAtranche));

        IdleCreditVault vault = IdleCreditVault(address(strategy));
        uint256 reqEpoch = vault.epochNumber();
        assertEq(vault.lastWithdrawRequest(alice), reqEpoch, "receipt keyed at epoch N");

        // Epoch ends with a realized loss; borrower funds only pendingToFund
        vm.warp(cdoEpoch.epochEndDate() + 1);
        uint256 loss = 10_000 * ONE_SCALE;
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, loss); // stopEpochWithDuration path

        // Price was stored under epochNumber AFTER deposit() bumped it
        uint256 storeEpoch = vault.epochNumber();
        assertEq(storeEpoch, reqEpoch + 1, "epochNumber bumped during stop");
        uint256 storedPrice = vault.lossRecoveryPriceByEpoch(storeEpoch);
        assertGt(storedPrice, 0, "loss price stored under N+1");
        assertEq(vault.lossRecoveryPriceByEpoch(reqEpoch), 0, "receipt epoch N has no price");

        // Alice's claim: _claimLossAdjustedWithdrawRequest reads epoch N -> 0,
        // falls through to _claimFundedWithdrawRequest and pays PAR
        uint256 balPre = IERC20(defaultUnderlying).balanceOf(alice);
        vm.prank(alice);
        cdoEpoch.claimWithdrawRequest();
        uint256 paid = IERC20(defaultUnderlying).balanceOf(alice) - balPre;

        uint256 fair = aliceBasis * storedPrice / 1e18;
        assertGt(paid, fair, "receipt paid above haircut");
        assertEq(paid, aliceBasis, "receipt paid fully at par despite loss");

        // Solvency check: strategy now holds less underlying than the sum of
        // remaining funded claims + reserves -> later claimants revert/freeze.
        uint256 remainingOwed = vault.pendingWithdraws(); // includes others' funded basis
        assertLt(
            IERC20(defaultUnderlying).balanceOf(address(vault)),
            remainingOwed,
            "strategy underfunded: other claimants' yield frozen"
        );
    }
}
```
