### Title
Cross-user response leakage via unauthenticated client-controlled MessageId collisions in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each user's response callback keyed solely by `msg.Body.MessageId`, a value taken verbatim from the JSON-RPC request `ID` supplied by the calling client with no server-side uniqueness enforcement or per-session namespacing. Two unprivileged callers targeting the same DON who choose (or happen to collide on) the same `MessageId` will silently overwrite each other's `savedCallback` entry, so the node's later response—looked up only by that shared key in `handleWebAPITriggerMessage`—is delivered to whichever caller registered last, not necessarily the caller whose trigger produced that response.

### Finding Description
`ValidatedMessageFromReq` sets `m.Body.MessageId = req.ID` directly from the untrusted client-supplied JSON-RPC request ID [1](#0-0) , bounded only by `MessageIdMaxLen` (128 bytes) with no uniqueness constraint [2](#0-1) . `HandleLegacyUserMessage`, which is reachable by any unprivileged caller hitting the gateway's user-facing endpoint for a given DON, then unconditionally inserts (and overwrites) into `h.savedCallbacks[msg.Body.MessageId]` without checking whether an entry already exists: [3](#0-2) 
Because the handler instance is shared per-DON across all users, a second unprivileged caller who submits a `web_api_trigger` request with the same `MessageId` string as a still-pending first caller silently replaces the first caller's `savedCallback` entry with their own, losing the mapping to the first caller without any notification.

When a DON node later responds to the *first* caller's original request, `handleWebAPITriggerMessage` looks the response up purely by `msg.Body.MessageId` (the node echoes back whatever MessageId it was given) and delivers the payload to whichever callback currently occupies that map slot—the second caller's: [4](#0-3) 
The node-message path itself does validate that `msg.Body.Sender` matches the connected `nodeAddr` [5](#0-4) , so this is not a node-impersonation bug; the vulnerability is purely in the unauthenticated overwrite of the response-routing table by user-controlled key collision at registration time, before any node is involved. No allowlist, rate limiter, or uniqueness check protects `h.savedCallbacks` insertion against this collision.

### Impact Explanation
This is a cross-user response confusion: an unprivileged attacker who submits a `web_api_trigger` request with a `MessageId` matching (or racing) a victim's in-flight request can cause the victim's legitimate node response—including whatever HTTP body/headers the victim's trigger fetched—to be delivered to the attacker's own HTTP callback instead of the victim's, while the victim's own request silently times out. This matches the "cross-user response confusion / leaking one user's trigger result to another" impact class explicitly called out in the audit scope.

### Likelihood Explanation
Exploitability requires only: (1) knowledge or guessing/enumeration of another concurrent caller's chosen `MessageId` (feasible if the ID space is small, predictable, sequential, or client-default — e.g., many JSON-RPC clients default to small integers or short strings), or (2) an attacker simply racing many trigger requests with the same fixed/guessed `MessageId` value against a victim's known request pattern to increase collision probability. No credentials beyond ordinary gateway-user access to submit a `web_api_trigger` request are needed, and the race is repeatable at will by the attacker.

### Recommendation
Do not key `savedCallbacks` purely by client-supplied `MessageId`. Either (a) generate the map key server-side (e.g., a gateway-generated UUID) and use the client's `MessageId` only for correlation in the response payload, or (b) namespace the key by a tuple that includes a per-connection/session identifier or a gateway-assigned nonce (e.g., `nodeAddr` is not enough since the response consumer differs from the sender). At minimum, `HandleLegacyUserMessage` should reject/fail the request with an error if `msg.Body.MessageId` already exists in `h.savedCallbacks` instead of silently overwriting it.

### Proof of Concept
Go handler-level test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler `h` with a mocked `handlers.DON`.
2. Create two fake `handlers.Callback` implementations (`cbA`, `cbB`) that record whatever `UserCallbackPayload` they receive.
3. Call `h.HandleLegacyUserMessage(ctx, msgA, cbA)` with a valid `web_api_trigger` payload and `MessageId = "X"`.
4. Before any node responds, call `h.HandleLegacyUserMessage(ctx, msgB, cbB)` with a different trigger payload but the same `MessageId = "X"`.
5. Assert `h.savedCallbacks["X"]` now stores `cbB` (i.e., `cbA`'s entry was overwritten with no error returned to `cbA`).
6. Simulate the DON node responding to A's original request via `h.HandleNodeMessage` with a `resp` whose `ID` (validated MessageId) is `"X"` and a valid node signature/`nodeAddr` matching a legitimate DON member.
7. Assert that `cbB.SendResponse` was invoked with A's response payload (cross-delivery), and `cbA.SendResponse` was never invoked (silent loss/leak).

```go
func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
```
