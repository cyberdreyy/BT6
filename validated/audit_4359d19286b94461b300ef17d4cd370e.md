### Title
Unfunded instant-withdraw receipts can drain funded claims — receipt funding-state confusion in `claimInstantWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2016-9576 is a type-confusion bug: `blk_rq_map_user_iov` failed to restrict the iterator type, letting a write primitive be driven by a read-shaped request into arbitrary kernel memory. The credit-vault analog is a receipt-class confusion in `IdleCreditVault`: `claimInstantWithdrawRequest` treats *every* instant-withdraw receipt as a funded claim, even receipts whose underlyings have not yet been collected from the borrower via `collectInstantWithdrawFunds`. The function burns the user's full `instantWithdrawsRequests[_user]` balance and calls `_transferFundedClaim`, which only ring-fences `defaultRecoveryReserve` — it does not reserve other users' already-collected-but-unclaimed withdraw funds that sit in the same vault balance.

### Finding Description
- `requestInstantWithdraw` mints the user a 1:1 strategy-token receipt and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` before any underlying is sourced (IdleCreditVault.sol:356-375).
- Funding arrives asynchronously: `collectInstantWithdrawFunds` later decrements `pendingInstantWithdraws` and pulls underlyings from the CDO (IdleCreditVault.sol:398-403), mirroring how `collectWithdrawFunds` pulls normal-claim funds (IdleCreditVault.sol:411-430).
- `claimInstantWithdrawRequest` does not distinguish "receipt created in current epoch, not yet funded" from "receipt backed by collected funds." It burns `instantWithdrawsRequests[_user]` in full and pays `_transferFundedClaim(_user, amount)` from the vault's underlying balance (IdleCreditVault.sol:380-392).
- `_transferFundedClaim` only guards `defaultRecoveryReserve`; any other underlyings held by the vault — i.e., normal withdraw funds collected via `collectWithdrawFunds` that honest users have not yet claimed — are spendable (IdleCreditVault.sol:897-907).
- The CDO-side wrapper `IdleCDOEpochVariant.claimInstantWithdrawRequest` only checks `allowInstantWithdraw`; there is no per-receipt funded/pending type check analogous to `epochNumber <= lastWithdrawRequest` gating used for normal claims (IdleCDOEpochVariant.sol:975-979, IdleCreditVault.sol:326-328).

### Impact Explanation
A KYC-passing lender (unprivileged attacker) whose instant receipt is still unfunded can claim it anyway and be paid out of the vault's float of collected, not-yet-claimed withdraw funds belonging to other users. This is a one-receipt-one-payout invariant break: the attacker's unfunded receipt is paid at par while honest users' funded claims are drained, causing direct theft of unclaimed withdrawal proceeds up to the vault's collected-but-unclaimed balance. The confusion mirrors the CVE: a request of one "type" (pending/unfunded) is serviced by the code path meant for another type (funded claim).

### Likelihood Explanation
Requires the instant-withdraw mode to be active (APR dropped by more than `instantWithdrawAprDelta` at request time) and the vault to be holding collected claim funds — a normal state between `stopEpoch`/`collectWithdrawFunds` and user claims. The attacker's only actions are `requestWithdraw` (routed to instant) followed by `claimInstantWithdrawRequest` before funding arrives. Owner/manager/borrower remain honest. Caveat: I was unable to fully confirm whether the CDO-level instant-claim path enforces an `instantWithdrawDelay` or a per-receipt funded flag before reaching the vault; the vault code itself contains no such check, so the exposure exists at minimum whenever the delay/eligibility gate is satisfied before `collectInstantWithdrawFunds` executes.

### Recommendation
Track funded vs. pending instant receipts separately (e.g., an `instantWithdrawsFundedByEpoch`/`fundedInstantBasis` counter incremented only by `collectInstantWithdrawFunds`), and have `claimInstantWithdrawRequest` pay only the funded portion, mirroring how normal claims are gated on `epochNumber > lastWithdrawRequest`. Alternatively, reserve collected normal-claim funds (`pendingWithdraws`-style earmark) inside `_transferFundedClaim` so instant claims cannot spend them.

### Proof of Concept
Foundry fork PoC sketch (not executed — the funding-gate caveat above must be verified against `instantWithdrawDelay` enforcement):
1. Lender A deposits AA, epoch 0 runs and stops; A calls `requestWithdraw` (normal path) — `pendingWithdraws` grows.
2. Manager `stopEpoch`s epoch 1; borrower repays; `collectWithdrawFunds` pulls A's funds into the vault (unclaimed).
3. Attacker B (KYC'd) deposits BB in the buffer, triggers an instant request (`lastEpochApr > unscaledApr + instantWithdrawAprDelta`), receiving an unfunded receipt in `instantWithdrawsRequests[B]`.
4. Before `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` runs, B calls `cdoEpoch.claimInstantWithdrawRequest()`.
5. Assert: vault burned B's receipt and transferred underlying equal to B's request, reducing vault balance below the sum needed for A's claim; A's subsequent `claimWithdrawRequest` reverts or underpays.
