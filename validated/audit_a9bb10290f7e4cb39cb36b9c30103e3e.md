### Title
Builder withdrawal payload amount is uncapped while the corresponding builder balance deduction is capped, creating Gwei out of thin air - (File: specs/gloas/beacon-chain.md)

### Summary
In the Gloas fork, `get_builder_withdrawals` copies the *requested* amount stored in `state.builder_pending_withdrawals[i].amount` verbatim into the `Withdrawal.amount` field that is committed to the block and that the execution layer is required to honor exactly. However, `apply_withdrawals` only decreases the builder's on-chain balance by `min(withdrawal.amount, builder_balance)`. When the queued request amount exceeds the builder's balance at processing time, the CL commits to (and the EL must pay) the full uncapped amount while only the capped (smaller) amount is actually removed from the builder's balance — the same "commit untrimmed, deduct trimmed" pattern as the Allora `RewardDelegateStake`/`AddDelegateStake`/`RemoveDelegateStake` bug.

### Finding Description
`get_builder_withdrawals` builds the committed `Withdrawal` entries straight from the pending queue's requested amount, with no capping to the builder's current balance: [1](#0-0) 

That `Withdrawal` list becomes `state.payload_expected_withdrawals`, which the accompanying spec note states the execution layer is *required to honor* — i.e., the EL will credit `withdrawal.amount` in full to the recipient address.

`apply_withdrawals` (modified in Gloas) then only decreases the builder's tracked balance by the amount actually available, saturating the deduction: [2](#0-1) 

So for a builder pending withdrawal whose `amount` exceeds `builder.balance` at processing time, the CL side removes only `builder_balance` Gwei from `state.builders[i].balance`, but the `Withdrawal` object committed into the block — and therefore the amount the execution layer will mint to `withdrawal.fee_recipient` — is the full, uncapped `amount`. The equality "Gwei removed from CL builder balance == Gwei credited on the EL side by the committed withdrawal" is broken; more Gwei is paid out than was ever backed by a balance decrease.

This exact scenario is anticipated and asserted as correct behavior by the existing spec test: [3](#0-2) 

The test explicitly documents: `builders[0].balance: 0 (deduction capped to available balance)` while `withdrawal.amount: MIN_DEPOSIT_AMOUNT + 123 Gwei (requested amount)` is the value placed into `payload_expected_withdrawals` — i.e., the committed/paid amount is larger than the amount actually deducted.

Notably, the spec authors were aware of this exact class of bug for the *validator* sweep path and explicitly called out the supply-inflation risk there: [4](#0-3) 

but the same reasoning was not applied to protect the builder-pending-withdrawal path, where `get_builder_withdrawals` (unlike `get_pending_partial_withdrawals`, which correctly uses `min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)` for validators) omits any `min()` capping against the builder's balance.

### Impact Explanation
This breaks a Critical-severity invariant: Gwei is created and paid to a recipient beyond what was actually deducted from any account's tracked balance. Whenever `builder.balance < queued withdrawal.amount` at sweep time (which can occur naturally — e.g., multiple pending withdrawals queued against the same builder that cumulatively exceed its balance, or a fee-consuming operation reducing the builder's balance between queuing and processing), the committed `Withdrawal.amount` sent to the execution layer will exceed the Gwei actually removed from the CL-tracked builder balance, resulting in unbacked Gwei minted to the `fee_recipient`.

### Likelihood Explanation
This requires no malicious coalition, privileged access, or client bug — it is a straightforward, spec-level accounting mismatch reachable by any builder that queues withdrawal requests whose cumulative or individual amount depletes/exceeds its own balance before the sweep processes them (a normal, permitted state transition, and one the spec's own test suite exercises and asserts as "expected" behavior).

### Recommendation
Cap the committed `Withdrawal.amount` in `get_builder_withdrawals` to the builder's actual available balance (accounting for withdrawals already queued earlier in the same processing batch), mirroring the `min(...)` capping already used in `get_pending_partial_withdrawals` for validators, so the amount promised to (and paid by) the execution layer never exceeds the amount actually deducted from the builder's balance.

### Proof of Concept
1. Register a builder with `balance = X`.
2. Queue two (or more) `BuilderPendingWithdrawal` entries against the same builder whose amounts sum to more than `X` (e.g., first entry requests `X - 1`, second requests `2`), as constructed directly in the existing test `test_builder_withdrawal_insufficient_balance_realistic_bounds`.
3. Run `process_withdrawals`; observe that `get_builder_withdrawals` emits `Withdrawal` objects whose `amount` fields sum to more than `X` and are placed in `state.payload_expected_withdrawals` (committed to the block), while `apply_withdrawals` only decreases `state.builders[i].balance` down to `0` (capped) — see asserted outcome in [5](#0-4) .
4. The execution layer, obligated to honor the committed `Withdrawal.amount` values, credits the fee recipient more Gwei than was ever deducted from the builder's CL-tracked balance.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
