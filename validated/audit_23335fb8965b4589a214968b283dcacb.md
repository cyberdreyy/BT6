### Title
Non-monotonic vote-account epoch-credits data causes u64 underflow panic in `calc_earned_credits` during epoch-boundary reward distribution - (File: runtime/src/inflation_rewards/points.rs)

### Summary
`calc_earned_credits` computes `final_epoch_credits - initial_epoch_credits` as a plain `u64` subtraction with no ordering check, assuming the pair always satisfies `final >= initial`. This assumption is only guaranteed for vote accounts that went through the vote program's own `increment_credits` logic; it is never enforced when the account is loaded into `stakes_cache`/`VoteAccount`, so a vote-program-owned account with hand-crafted, non-monotonic epoch-credits data can drive this subtraction to underflow.

### Finding Description
`calc_earned_credits` performs the unchecked subtraction: [1](#0-0) 

It is reached for every delegated stake at each epoch boundary via `tower_epoch_credits_iter`, which iterates the raw `(Epoch, final_epoch_credits, initial_epoch_credits)` tuples decoded straight from `VoteStateView`: [2](#0-1) 

The tuples originate from `EpochCreditsItem`, which is decoded purely by reinterpreting little-endian bytes with no relational check between the two credit fields: [3](#0-2) 

`VoteAccount::try_from` (the gatekeeper used everywhere a vote account is admitted into `stakes_cache`, e.g. `check_and_store`) only validates the account **owner** and that `VoteStateView::try_new` can parse the fixed struct layout — it performs no semantic/monotonicity validation of epoch-credits entries: [4](#0-3) [5](#0-4) 

In legitimate vote-program execution, `increment_credits` always constructs entries where `final_credits >= initial_credits` (it only ever adds via `saturating_add`): [6](#0-5) 

However, an account's byte content and owner field in the Solana account model can be fully controlled by *any* program that currently owns the account — including a program the attacker deploys and controls. Since Solana allows the currently-executing owner of an account to reassign that account's `owner` field to an arbitrary pubkey (a legitimate, widely used pattern), an unprivileged attacker can: (1) deploy their own on-chain program, (2) have it create/own an account and write arbitrary bytes forming a well-formed-but-semantically-invalid `VoteStateV3`/`VoteStateV4` layout (crafted `EpochCreditsItem` where `credits < prev_credits`), and (3) reassign that account's owner to `solana_vote_program::id()`. This account then passes `VoteAccount::try_from`'s owner+layout checks and is cached as a normal vote account by `StakesCache::check_and_store`. A stake account can subsequently be delegated to it, since delegation only checks the target's owner equals the vote program id, not deep state validity.

At the next epoch boundary, `calculate_reward_points_partitioned` → `calculate_points_for_tower` → `tower_epoch_credits_iter` → `calc_earned_credits` processes this account's tuple with `credits_in_stake < initial_epoch_credits` and `final_epoch_credits < initial_epoch_credits`, triggering the underflowing subtraction at line 170.

### Impact Explanation
If the workspace build enables `overflow-checks` (a common Solana/Agave practice for release builds — I could not fully re-confirm the exact profile block in this session before running out of tool calls, so this should be independently verified), the underflow panics inside `Bank::calculate_reward_points_partitioned`, which runs deterministically during epoch-boundary bank freeze/reward processing on every validator replaying that slot — causing a cluster-wide validator crash (liveness-halting bug), which is the highest-severity "Loss of Availability" / crash category under Agave's bounty scope. If overflow-checks are not enabled, the subtraction instead wraps to a near-`u64::MAX` value, producing a massively inflated `earned_credits`/reward computation — a consensus-affecting economic-integrity bug. Either way this is a scoped, high-impact finding.

### Likelihood Explanation
The precondition (owner-reassignment to a builtin program ID by an attacker-controlled program) is a standard, unprivileged, low-cost technique requiring only program deployment and a handful of transactions — no validator, leader, or key-compromise privilege. The bug is deterministically reproducible: crafting the exact byte layout only requires matching `VoteStateFrame`'s expected layout, which is documented/derivable from `vote_state_view.rs`. It is repeatable across epochs and forks since the malicious account persists on-chain once created.

### Recommendation
- In `calc_earned_credits`, replace the raw subtraction with `final_epoch_credits.checked_sub(initial_epoch_credits)` (or `saturating_sub`), treating any inversion as zero earned credits, and add a `debug_assert!`/telemetry alert for the anomalous case.
- Additionally, validate epoch-credits monotonicity (each entry's `final_credits >= initial_credits`, and non-decreasing across the list) inside `VoteStateFrame::try_new`/`VoteAccount::try_from` so malformed vote accounts are rejected before being cached as valid delegation targets, rather than relying solely on downstream arithmetic guards.

```rust
            initial_epoch_credits,
            &mut new_credits_observed,

    );
```

```rust
pub struct EpochCreditsItem {
    epoch: [u8; 8],
    credits: [u8; 8],
    prev_credits: [u8; 8],
}

#[derive(Debug, PartialEq, Clone, Copy)]
#[cfg_attr(feature = "frozen-abi", derive(AbiExample))]
pub(super) struct EpochCreditsListFrame {
    pub(super) len: u8,
}

impl EpochCreditsListFrame {
    pub(super) fn read(cursor: &mut std::io::Cursor<&[u8]>) -> Result<Self> {
        let len = solana_serialize_utils::cursor::read_u64(cursor)
            .map_err(|_err| VoteStateViewError::AccountDataTooSmall)? as usize;
        let len = u8::try_from(len).map_err(|_| VoteStateViewError::InvalidEpochCreditsLength)?;
        let frame = Self { len };
        cursor.consume(frame.total_item_size());
        Ok(frame)
    }
}

impl ListFrame for EpochCreditsListFrame {
    type Item = EpochCreditsItem;

    fn len(&self) -> usize {
        self.len as usize
    }
}

impl EpochCreditsItem {
    #[inline]
    pub fn epoch(&self) -> u64 {
        u64::from_le_bytes(self.epoch)
    }
    #[inline]
    pub fn credits(&self) -> u64 {
        u64::from_le_bytes(self.credits)
    }
    #[inline]
    pub fn prev_credits(&self) -> u64 {
        u64::from_le_bytes(self.prev_credits)
    }
}

impl From<&EpochCreditsItem> for (Epoch, u64, u64) {
    fn from(item: &EpochCreditsItem) -> Self {
        (item.epoch(), item.credits(), item.prev_credits())
```

```rust
    pub fn increment_credits(&mut self, epoch: Epoch, credits: u64) {
        // increment credits, record by epoch

        // never seen a credit
        if self.epoch_credits().is_empty() {
            self.epoch_credits_mut().push((epoch, 0, 0));
        } else if epoch != self.epoch_credits().last().unwrap().0 {
            let (_, credits, prev_credits) = *self.epoch_credits().last().unwrap();

            if credits != prev_credits {
                // if credits were earned previous epoch
                // append entry at end of list for the new epoch
                self.epoch_credits_mut().push((epoch, credits, credits));
            } else {
                // else just move the current epoch
                self.epoch_credits_mut().last_mut().unwrap().0 = epoch;
            }

            // Remove too old epoch_credits
            if self.epoch_credits().len() > MAX_EPOCH_CREDITS_HISTORY {
                self.epoch_credits_mut().remove(0);
            }
        }

        self.epoch_credits_mut().last_mut().unwrap().1 = self
            .epoch_credits()
            .last()
            .unwrap()
            .1
            .saturating_add(credits);
    }
```
