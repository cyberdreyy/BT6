Based on my investigation, I found a genuine local analog to the H-09 bug class — not a "wrong address" typo, but a wrong-timing state mutation that bypasses the delegation-pool's lockup-cycle accounting, corrupting `pending_inactive` share values for delegators. The root cause lives in `stake::join_validator_set_internal`.

### Title
Rejoining the validator set after lockup expiry silently inactivates `pending_inactive` stake outside the delegation pool's OLC accounting, zeroing delegators' unlocked balances - (File: `aptos-move/framework/aptos-framework/sources/stake.move`)

### Summary
`join_validator_set_internal` contains logic that, when an inactive validator's lockup has already expired, force-merges the entire `pending_inactive` balance into `inactive` on the underlying `StakePool` **before** `delegation_pool::synchronize_delegation_pool` ever runs: [1](#0-0) 

This settling step is invisible to `delegation_pool`, which tracks pending-inactive stake per `observed_lockup_cycle` (OLC) and only advances the OLC and reconciles balances via `calculate_stake_pool_drift`/`synchronize_delegation_pool`, based on its own comparison of the stake pool's `pending_inactive` value against the pool's internally-tracked shares total.

### Finding Description
Delegators unlock stake into `pending_inactive` via `delegation_pool::unlock` -> `stake::unlock`, and the delegation pool tracks the value in a `pool_u64::Pool` keyed by the current `observed_lockup_cycle`: [2](#0-1) 

A test explicitly documents the expected invariant that while a validator is inactive, `pending_inactive` stake is **not** inactivated and the OLC does not advance: [3](#0-2) 

However, when the operator later calls `stake::join_validator_set` to rejoin (a routine, unprivileged-relative-to-delegators operation performed only by the operator, who does not need delegator consent), `join_validator_set_internal` unconditionally moves all `pending_inactive` into `inactive` if the lockup already expired: [4](#0-3) 

This is done directly on `StakePool.pending_inactive`/`StakePool.inactive` coin fields, completely bypassing the delegation-pool synchronization path (`synchronize_delegation_pool` / `calculate_stake_pool_drift`) that is normally the only mechanism allowed to detect and reconcile lockup-cycle transitions: [5](#0-4) 

When `synchronize_delegation_pool` eventually runs afterward, it computes `commission_pending_inactive` by comparing the on-chain `pending_inactive` (now silently zeroed by the join) against `pending_inactive_shares_pool(pool).total_coins()` (the delegation pool's shares-tracked value, still holding the pre-join balance): [6](#0-5) 

Since actual `pending_inactive` is now less than the pool's tracked total, the `if (pending_inactive > pool_pending_inactive)` branch is skipped (treated as ordinary "slashing"), and the pool then calls:
```
pending_inactive_shares_pool_mut(pool).update_total_coins(pending_inactive - commission_pending_inactive);
```
with `pending_inactive == 0`, which sets the entire pending-inactive shares pool's `total_coins` to `0` — wiping out every delegator's unlocked-but-not-yet-withdrawn balance for that OLC: [7](#0-6) 

Meanwhile, the actual coins are sitting in `StakePool.inactive`, but the delegation pool's OLC never advanced through the mechanism that would let `withdraw_internal` recognize and redeem it correctly (`pending_withdrawal_exists`/`observed_lockup_cycle` gating), and `pool.total_coins_inactive` was never updated to reflect this backdoor inactivation.

### Impact Explanation
Delegators' `pending_inactive` stake (funds they explicitly unlocked, intending to withdraw once the lockup ends) can be permanently zeroed out of the delegation pool's share accounting the moment the operator restakes the validator after lockup expiry. This is a direct loss-of-funds / share-accounting corruption: the coins are still physically present in the `StakePool`, but delegators' claim rights (shares) to them are erased, making them unrecoverable through the normal `withdraw` path. This satisfies "permanent lock or non-recoverable loss of claim rights" and "share-accounting corruption that ... traps value" under the required impacts.

### Likelihood Explanation
Rejoining the validator set after a lockup expiry while inactive is an ordinary operational action any operator performs routinely (e.g., a validator resuming operation after temporary downtime or after a delegator-triggered unlock). No special privilege beyond normal operator control is needed, and no delegator cooperation or malicious intent is required — the trigger condition (`lockup expired` + `pending_inactive > 0` + operator rejoins) can occur in ordinary operation.

### Recommendation
Do not merge `pending_inactive` into `inactive` inside `join_validator_set_internal`. Lockup-cycle transitions should only be observed and applied through the delegation pool's own `calculate_stake_pool_drift`/`synchronize_delegation_pool` flow (or equivalently, `staking_contract`'s distribution flow), so that share accounting and the underlying `StakePool` balances always move in lockstep. If settling is necessary for voting-power correctness, it should call into (or trigger) the delegation pool's synchronization before/atomically with the `StakePool` state change, not mutate `StakePool.inactive`/`pending_inactive` unilaterally.

### Proof of Concept
1. Delegation pool created; delegator delegates stake; validator becomes active.
2. Validator leaves the validator set (`stake::leave_validator_set`), becomes inactive.
3. Delegator calls `delegation_pool::unlock(delegator, pool_address, amount)` -> stake moves from `active` to `pending_inactive` on the `StakePool`; delegation pool buys `pending_inactive` shares for the delegator at the current OLC (per `test_inactivate_no_excess_stake`, no inactivation happens while inactive).
4. Time passes so `stake_pool.locked_until_secs` is exceeded (lockup expired) while the validator is still inactive.
5. Operator calls `stake::join_validator_set(operator, pool_address)`. Because `locked_until_secs > 0` and `now_seconds() >= locked_until_secs`, `join_validator_set_internal` executes `coin::merge(&mut stake_pool.inactive, coin::extract_all(&mut stake_pool.pending_inactive))`, silently zeroing `pending_inactive` on the `StakePool` — with no corresponding delegation-pool OLC advance or `total_coins_inactive` update.
6. Any subsequent `synchronize_delegation_pool` call computes `pending_inactive == 0 < pool_pending_inactive` (the delegation-tracked amount), skips commission crediting, and calls `pending_inactive_shares_pool_mut(pool).update_total_coins(0)`, zeroing the delegator's pending-inactive share value.
7. Delegator's `withdraw` call for that pending balance yields nothing, despite the underlying coins existing in `StakePool.inactive`.

Note: I was unable to fully trace the exact `lockup_cycle_ended` boolean computation inside `calculate_stake_pool_drift` (its body was not fully retrieved in my search), so I cannot 100% rule out that some other check inside that function independently catches this exact drop-to-zero case before the share-zeroing update executes. This is the one open verification gap in this analysis; a Devin session with full file access should read the complete body of `calculate_stake_pool_drift` in `delegation_pool.move` to confirm whether it detects and correctly handles a `pending_inactive` value that drops to zero without a corresponding `lockup_cycle_ended` signal.

        let config = staking_config::get();
        let (minimum_stake, maximum_stake) = staking_config::get_required_stake(&config);
        // Settle any pending_inactive whose lockup has already expired so it is not counted
        // as voting power. An inactive validator's pending_inactive is never processed by
        // update_stake_pool, so we must do it here before evaluating the minimum stake.
        // Only settle when locked_until_secs > 0 (i.e., a lockup was ever explicitly set);
        // a value of 0 means the pool was just created and the lockup has not been initialised yet.

    /// Synchronize delegation and stake pools: distribute yet-undetected rewards to the corresponding internal
    /// shares pools, assign commission to operator and eventually prepare delegation pool for a new lockup cycle.
    public entry fun synchronize_delegation_pool(
        pool_address: address
    ) acquires DelegationPool, GovernanceRecords, BeneficiaryForOperator, NextCommissionPercentage {
        assert_delegation_pool_exists(pool_address);
        let pool = borrow_global_mut<DelegationPool>(pool_address);
        let (
            lockup_cycle_ended,
            active,
            pending_inactive,
            commission_active,
            commission_pending_inactive
        ) = calculate_stake_pool_drift(pool);

        // zero `pending_active` stake indicates that either there are no `add_stake` fees or
        // previous epoch has ended and should release the shares owning the existing fees
        let (_, _, pending_active, _) = stake::get_stake(pool_address);
        if (pending_active == 0) {
            // renounce ownership over the `add_stake` fees by redeeming all shares of
            // the special shareholder, implicitly their equivalent coins, out of the active shares pool
            redeem_active_shares(pool, NULL_SHAREHOLDER, MAX_U64);
        };

        // distribute rewards remaining after commission, to delegators (to already existing shares)
        // before buying shares for the operator for its entire commission fee
        // otherwise, operator's new shares would additionally appreciate from rewards it does not own

        // update total coins accumulated by `active` + `pending_active` shares
        // redeemed `add_stake` fees are restored and distributed to the rest of the pool as rewards
        pool.active_shares.update_total_coins(active - commission_active);
        // update total coins accumulated by `pending_inactive` shares at current observed lockup cycle
        pending_inactive_shares_pool_mut(pool).update_total_coins(pending_inactive - commission_pending_inactive);
