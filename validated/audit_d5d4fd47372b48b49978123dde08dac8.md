### Title
Loss-adjusted withdraw haircut is written under the post-increment epoch index, letting pending receipts claim at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` keys per-epoch receipt data by `epochNumber`, but `epochNumber` is incremented inside `deposit()` during the stop-epoch flow while receipt ownership is written under the pre-increment index at request time. When `collectWithdrawFunds` records `lossRecoveryPriceByEpoch[epochNumber]` after that increment, the haircut lands in an epoch bucket that no user's `lastWithdrawRequest` points to. Loss-adjusted receipts then fall through to `_claimFundedWithdrawRequest` and are paid at par, draining underlying funded for other claimants or the default-recovery reserve.

### Finding Description
Receipt ownership is written under the request-time epoch: `requestWithdraw` stores `withdrawsRequestsByEpoch[_user][currentEpoch]` and `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:281-293`).

`epochNumber` is incremented inside `deposit()` whenever `IIdleCDOEpochVariant(idleCDO).isEpochRunning()` is still true — which the comment identifies as the deposit performed during `stopEpoch` "before setting the var to false" (`IdleCreditVault.sol:607-610`).

The stop-epoch loss haircut is stored under whatever `epochNumber` is at collect time: `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (`IdleCreditVault.sol:421`).

Claim resolution looks up the haircut via `lastWithdrawRequest[_user]` (the *request* epoch), not the collect epoch: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol:790-791`), and the new-request guard does the same (`IdleCreditVault.sol:261-262`).

If `collectWithdrawFunds` executes after the epoch-incrementing `deposit()` inside `stopEpoch` — the natural ordering, since the CDO must first hold repaid funds before `safeTransferFrom(idleCDO, ...)` succeeds — the haircut is stored under `N+1` while every receipt of that epoch is indexed under `N`. The `lossRecoveryPriceByEpoch[N]` lookup returns 0, the loss-adjusted claim path is skipped, and `_claimFundedWithdrawRequest` passes its gate (`epochNumber <= lastWithdrawRequest` is false once `epochNumber` is `N+1`) and pays the full `withdrawsRequests[_user]` basis (`IdleCreditVault.sol:326-349`).

### Impact Explanation
Broken invariant: one receipt one payout at the funded price. A pending withdraw receipt from a loss-adjusted epoch is paid 100% of principal + interest even though the borrower only funded `pendingToFund` (the haircut amount). The excess is paid directly from strategy-held underlying — i.e., stolen from the pool that backs other receipts and, post-default, from `defaultRecoveryReserve` claimants. Loss scales with the haircut size: for a stop-epoch loss of L on pending basis P, each claimant extracts `claimBasis - claimBasis * (P-L)/P` in excess.

### Likelihood Explanation
Likelihood is conditional on `stopEpoch` ordering in `IdleCDOEpochVariant`: this requires `collectWithdrawFunds` (or `collectInstantWithdrawFunds`/`deposit`) to run after the `deposit()` call that increments `epochNumber`. The in-code comment confirms the increment happens mid-`stopEpoch`, but I could not fully read `IdleCDOEpochVariant.stopEpoch` within this analysis to confirm whether the collect call precedes or follows the incrementing deposit; the math only works if collect runs after the increment. No privileged-role abuse is needed — any KYC'd tranche holder with a pending request triggers the overpay on the next ordinary `claimWithdrawRequest`. The existing guards (lines 263-271, `_transferFundedClaim` reserve check at lines 899-905) key on the same mismatched index, so they do not stop it; `_transferFundedClaim` only reverts if the reserve itself would be spent, which is a partial mitigation, not a fix.

### Recommendation
Make the haircut index consistent with the request index: either snapshot `epochNumber` before any epoch-incrementing deposit inside `stopEpoch` and pass it explicitly to `collectWithdrawFunds`, or store the haircut under `epochNumber - 1` semantics documented for both write and read paths, and add an invariant test asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` is found for every loss-adjusted epoch.

### Proof of Concept
Foundry fork test outline (attacker = ordinary KYC'd AA/BB holder):

```solidity
// test/foundry/IdleCreditVault.t.sol style
function test_LossHaircutWrittenToWrongEpoch() public {
    // 1. Epoch N running: user deposits AA, requests withdraw of amount X.
    cdo.requestWithdraw(X, AATranche);            // withdrawsRequestsByEpoch[user][N] = X
    assertEq(strategy.lastWithdrawRequest(user), N);

    // 2. Borrower repays less than owed -> manager calls stopEpochWithDuration(_lossAmount>0).
    //    Internally: deposit() increments epochNumber to N+1, then collectWithdrawFunds
    //    stores lossRecoveryPriceByEpoch[N+1] instead of [N].
    vm.prank(manager);
    cdo.stopEpochWithDuration(lossAmount);
    assertEq(strategy.epochNumber(), N + 1);
    assertEq(strategy.lossRecoveryPriceByEpoch(N), 0);        // haircut misplaced
    assertGt(strategy.lossRecoveryPriceByEpoch(N + 1), 0);

    // 3. User claims: loss-adjusted path skipped, funded path pays full X.
    uint256 balBefore = underlying.balanceOf(user);
    cdo.claimWithdrawRequest(user);
    assertEq(underlying.balanceOf(user) - balBefore, X);      // paid at par, not X*price
}
```

Expected: claim pays `X * lossRecoveryPrice / 1e18`. Actual (under the ordering above): full `X`, with the shortfall borne by remaining claimants / recovery reserve.
