### Title
Unprivileged dust instant-withdraw permanently bricks withdrawals and default recovery on non-initialized `IdleCreditVault` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is "a flag left in a state where a dependent variable is never set, so a core function unconditionally reverts." The idle-tranches analog is `_ensureDefaultRecoveryInitialized()`: for a vault whose `defaultRecoveryInitialized` storage slot is `false` (any deployment upgraded to this implementation rather than initialized fresh — `initialize` sets it `true`, upgrades do not), a single wei of `pendingInstantWithdraws` makes `requestWithdraw`, `requestInstantWithdraw`, `collectWithdrawFunds` (loss path), `previewLossAdjustedWithdrawFunds` (loss path) and `finalizeDefaultRecovery` revert forever. An unprivileged KYC-passing lender can keep `pendingInstantWithdraws` non-zero with a dust instant-withdraw request.

### Finding Description
`_ensureDefaultRecoveryInitialized()` reverts whenever `pendingInstantWithdraws != 0` (line 926) and, unlike `pendingWithdraws`, pending instant withdrawals are *never* normalized automatically — the comment at line 923 states this explicitly:

```solidity
function _ensureDefaultRecoveryInitialized() internal {
    if (defaultRecoveryInitialized) return;
    if (pendingInstantWithdraws != 0) revert NotAllowed();
    ...
}
```

`pendingInstantWithdraws` is only decremented in `collectInstantWithdrawFunds()` (line 401), which requires the IdleCDO to actually hold and transfer the underlying. While an epoch is running, all underlying sits with the borrower, so the CDO cannot fully fund the instant queue — a request made then remains pending for the entire epoch. Crucially, `requestInstantWithdraw` is callable by any KYC-allowed lender through the CDO and burns/mints receipts 1:1 with `_amount`, so a 1-wei request sets `pendingInstantWithdraws = 1`.

Once non-zero:
- Every `requestWithdraw` (line 245) and `requestInstantWithdraw` (line 358) reverts — the normal withdraw pipeline is bricked.
- `finalizeDefaultRecovery` (line 663) reverts — after a borrower default, recovery accounting can never be finalized, so `defaultRecoveryPrice` is never set and neither `_claimDefaultedWithdrawRequest` nor `_claimDefaultedInstantWithdrawRequest` can pay out. Any recovered underlying pulled via `reserveDefaultRecovery` or sitting in the vault is frozen.
- `collectWithdrawFunds` (line 416) and `previewLossAdjustedWithdrawFunds` (line 453) revert on the loss path, so `stopEpochWithDuration` with a realized loss cannot complete either — compounding the freeze.

Even if the CDO eventually funds the queue, the attacker (or any user) can re-open a dust instant request, re-arming the revert before `finalizeDefaultRecovery` is called — there is no privileged call to force-initialize once instant receipts exist.

### Impact Explanation
- **Before a default:** all queued withdrawals are DoS'd for as long as the attacker maintains a dust pending instant request (gas-cheap; the only cost is a 1-wei locked principal).
- **After a borrower default:** `finalizeDefaultRecovery` can be permanently griefed, freezing the entire `defaultRecoveryReserve` and all defaulted-epoch receipt claims — direct, quantifiable loss equal to the recovered amount plus all pending receipt basis (`defaultPendingClaimBasis()`).

### Likelihood Explanation
Pre-conditions: (a) the vault was upgraded rather than freshly initialized (`defaultRecoveryInitialized == false`), which is exactly the state this lazy-init path exists for; (b) instant withdrawals are enabled. The attacker needs only to be a KYC-passing lender able to route `requestInstantWithdraw` through the CDO — an explicitly in-scope unprivileged actor. No privileged misbehavior required; the honest manager cannot clear the condition because `pendingInstantWithdraws` has no admin reset.

### Recommendation
Allow the CDO/manager to force-initialize recovery accounting by migrating outstanding instant receipts into a funded-reserve bucket, or make `collectInstantWithdrawFunds`/finalization tolerate a `pendingInstantWithdraws` remainder instead of hard-reverting. At minimum, add an owner/manager escape hatch that zeroes a dust `pendingInstantWithdraws` after the corresponding claim basis has been moved to `instantWithdrawClaimsByEpoch` accounting, mirroring how `pendingWithdraws` is normalized for closed pools.

### Proof of Concept
Foundry fork sketch (epoch variant CDO + upgraded `IdleCreditVault` with `defaultRecoveryInitialized == false`):

```solidity
// setup: vault upgraded, defaultRecoveryInitialized == false, epoch running
vm.prank(kycUser);          // attacker is a normal KYC lender
idleCDO.depositAA(1);       // dust position

// attacker requests a 1-wei instant withdraw via the CDO path
vm.prank(kycUser);
cdoEpoch.requestInstantWithdraw(1, address(AAtranche)); // routes to strategy
assertEq(creditVault.pendingInstantWithdraws(), 1);

// 1) normal withdraw requests are bricked
vm.prank(otherUser);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.requestWithdraw(amount, address(AAtranche));

// 2) borrower defaults; owner finalizes
vm.prank(owner);
cdoEpoch.updateAccounting(); // marks defaulted
vm.prank(owner);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.finalizeDefault(recovered, recoverySource); // calls finalizeDefaultRecovery -> reverts

// 3) recovery funds frozen: claims always hit the uninitialized guard
assertFalse(creditVault.defaultRecoveryFinalized());
```
