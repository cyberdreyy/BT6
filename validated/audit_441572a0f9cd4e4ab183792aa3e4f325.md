## Analysis

I found a concrete analog of the reported bug class (a counter incorrectly incremented without checking mutual-exclusivity of state) in the node-side coordinator's block-status tracking.

### Root cause

In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, `StackerDBListener::run` processes `BlockResponse` messages from each signer and maintains two independent, additive weight tallies on a shared `BlockStatus`: `total_weight_approved` and `total_weight_rejected`.

For an `Accepted` message, the weight is added guarded only by whether the slot already appears in `gathered_signatures`: [1](#0-0) 

For a `Rejected` message, the weight is added guarded by whether the slot is already present in `responded_signers`: [2](#0-1) 

Because the `Accepted` branch also inserts into `responded_signers` (line 465), the guard works correctly in the accept→reject order (the second, rejecting message is ignored for weight purposes). But in the **reject→accept** order, the `Accepted` branch's guard (`!gathered_signatures.contains_key(&slot_id)`) does not check `responded_signers` at all, so a signer that first rejects and later accepts the same block gets its weight added to `total_weight_rejected` *and* `total_weight_approved` — both permanently, with no decrement path anywhere in the file.

This is directly analogous to the reported `num_txs` bug: a tally is incremented on every state transition instead of only when the underlying set membership actually changes, breaking the invariant that `total_weight_approved` + `total_weight_rejected` should never double-count a single signer's weight (the "aggregated-weight vs verified-accepts" equality).

### Reachability and impact

- This requires only a single signer's own StackerDB slot (its own key), sending two ordinary, validly-signed `BlockResponse` messages for the same block: first `Rejected`, then `Accepted`. No majority, no other signer's key, and no node/consensus interaction is needed — it is entirely within the sending signer's control (matching the "one-slot" reachability bar and explicitly not requiring another signer's key).
- The stale, phantom rejected weight is consumed by `SignerCoordinator::get_block_status` in `stacks-node/src/nakamoto_node/signer_coordinator.rs` to decide whether to abort a valid block proposal: [3](#0-2) 

Since `total_weight_rejected` never decreases even after that signer legitimately flips to accept, it can push `total_weight_rejected` past the blocking-minority threshold even though the true, current opinion of the signer set favors acceptance — causing the miner to spuriously declare `NakamotoNodeError::SignersRejected`, exclude transactions, or abandon a block that in reality has legitimate accept support. This is a liveness degradation on the miner/coordinator side rather than a consensus-safety break by itself, since the double count lands in two distinct counters rather than inflating a single threshold counter beyond real unique weight.

I want to flag a caveat before finalizing: I could not find, within the indexed portion of this codebase, any code path that clears/decrements `total_weight_rejected` or otherwise reconciles `responded_signers` when a later `Accepted` arrives, which supports treating this as a genuine, unguarded gap rather than an intentional design choice — but I'd recommend a full read of `stackerdb_listener.rs` in a live Devin session to double check there isn't a reconciliation step elsewhere (e.g., in `reset_rejections`) that I may have missed given index size limits.

### Title
Signer weight double-counted across accept/reject tallies on reject→accept flip - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tracks `total_weight_approved` and `total_weight_rejected` as two independently-guarded, monotonically increasing counters on `BlockStatus`. The `Accepted` branch only guards against re-adding weight using `gathered_signatures`, not `responded_signers`, so a signer that rejects and later accepts the same block has its weight added to both tallies, permanently inflating `total_weight_rejected` beyond what the current signer opinions justify.

### Finding Description
`handle` logic for `BlockResponse::Rejected` sets `responded_signers.insert(slot_id)` and adds to `total_weight_rejected` if that insert returns `true` (line 515-518). `BlockResponse::Accepted` sets `total_weight_approved` if `gathered_signatures` does not already contain the slot (line 443-446), and only afterwards also inserts into `responded_signers` (line 464-465). Because the `Accepted` path never checks `responded_signers`, a signer whose earlier `Rejected` message already set that flag will still have its `Accepted` weight counted, while its previously-tallied rejected weight is never removed. The two tallies are meant to represent a signer's mutually exclusive current stance but are not reconciled against each other.

### Impact Explanation
The stale rejected weight is consumed directly by `SignerCoordinator::get_block_status` (`stacks-node/src/nakamoto_node/signer_coordinator.rs` lines 509-540) to decide whether to abort a proposed block and to categorize failed txids for exclusion. A single misbehaving or simply flip-flopping signer can cause the miner to incorrectly treat a block as rejected by the network (triggering `NakamotoNodeError::SignersRejected`, transaction exclusion, or block resubmission) even though the real, current signer weight favors acceptance — a liveness degradation reachable without any majority.

### Likelihood Explanation
Reachable by any single signer using only its own key/slot on StackerDB, by sending an ordinary `Rejected` message followed later by an `Accepted` message for the same block hash — both are normal, validly-signed protocol messages.

### Recommendation
Track a single, authoritative "current vote" per slot_id (e.g., an enum of Accepted/Rejected with its weight) instead of two independently-guarded additive counters, and recompute `total_weight_approved`/`total_weight_rejected` from that map on each update, mirroring the pattern already used correctly in `stacks-signer/src/v0/signer.rs::store_and_process_block_signature` and `handle_block_rejection`, which recompute weight totals fresh from the DB-backed sets rather than maintaining incrementally-mutated counters.

### Proof of Concept
1. Signer S (slot_id = k) receives block proposal B.
2. S publishes `BlockResponse::Rejected` for B on its StackerDB slot → `responded_signers.insert(k)` succeeds, `total_weight_rejected += weight(k)`.
3. S later publishes `BlockResponse::Accepted` for the same B on the same slot (e.g., after reconsidering, or a compromised/buggy signer deliberately does this) → `gathered_signatures.contains_key(k)` is `false`, so `total_weight_approved += weight(k)` is also applied.
4. `total_weight_rejected` now permanently includes S's weight even though S's final/current stance is acceptance, and this stale value is used by `get_block_status` in `signer_coordinator.rs` to potentially reject block B via the `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` check.
