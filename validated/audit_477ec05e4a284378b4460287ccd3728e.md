### Title
Funded instant-withdraw claims never clear `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, enabling double payout and reserve insolvency after default finalization — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Like CVE-2019-19317 (a bitmask that silently omits tracked bits, leaving stale state), `IdleCreditVault.claimInstantWithdrawRequest` pays out a funded instant-withdraw receipt but omits clearing the per-epoch bookkeeping (`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`). The stale bits are later consumed by `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and `_claimDefaultedInstantWithdrawRequest`, producing an inflated recovery basis, phantom reserve, and a second claimable receipt for the already-paid user.

### Finding Description
The normal (funded) instant-withdraw claim path burns the user's receipt tokens and zeroes only the aggregate `instantWithdrawsRequests[_user]`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:380-393
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` when the CDO funds the request, but neither it nor the claim clears `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch` — those are only cleared on the defaulted-receipt path (`_claimDefaultedInstantWithdrawRequest`).

Consequences when a default is later finalized in the same epoch (`finalizeDefaultRecovery`):

1. `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still contains already-paid receipts — `totalBasis` is overstated.
2. `_defaultPrefundedInstantReserve()` counts `instantBasis - pendingInstant` as already-held reserve even though those tokens were already paid out — `reserveAmount`/`defaultRecoveryPrice` are computed against tokens that do not exist.
3. The paid user's `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` is still nonzero, so `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` lets the same receipt be claimed a second time at `defaultRecoveryPrice`, drawing down `defaultRecoveryReserve`.

### Impact Explanation
Broken invariants: one receipt one payout, and solvency of the recovery reserve. The attacker (any KYC-passed lender) who claimed an instant withdrawal at par claims the same basis again from `defaultRecoveryReserve`, and every other defaulted receipt/active holder is diluted because `defaultRecoveryPrice` was computed on phantom funds. When real claimants withdraw last, `defaultRecoveryReserve`/strategy balance is exhausted and `_transferDefaultRecovery` reverts or underpays — direct theft plus permanent freezing of remaining claims, quantified at up to the full stale instant-claim amount times the recovery price.

### Likelihood Explanation
Requires: instant withdraws enabled; a user requests and is funded/claims within epoch N; another pending instant request (or nonzero `pendingInstantWithdraws`) exists when the borrower defaults and `finalizeDefaultRecovery` runs before `epochNumber` increments. All steps are reachable by unprivileged users plus honest manager/borrower sequencing; no privileged misbehavior needed.

### Recommendation
In `claimInstantWithdrawRequest` (or in `collectInstantWithdrawFunds`), clear the per-epoch accounting for funded receipts: decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (tracking the request epoch per user, e.g., a `lastInstantWithdrawRequest` mapping), so stale bits cannot re-enter default recovery accounting.

### Proof of Concept
Foundry fork sketch on `IdleCreditVault`/`IdleCDOEpochVariant`:

1. Enable instant withdrawals via `setInstantWithdrawParams`; LP `A` deposits AA, epoch N runs.
2. `A` calls `cdoEpoch.requestInstantWithdraw` → strategy mints receipt, `instantWithdrawsRequestsByEpoch[A][N] = X`, `instantWithdrawClaimsByEpoch[N] = X`.
3. Manager funds it: CDO transfers underlying, `collectInstantWithdrawFunds(X)` → `pendingInstantWithdraws = 0`.
4. `A` calls `claimInstantWithdrawRequest` → paid X at par. Assert `instantWithdrawClaimsByEpoch[N]` is still `X` (the bug).
5. LP `B` requests instant withdraw `Y` in same epoch N → `pendingInstantWithdraws = Y`, `instantWithdrawClaimsByEpoch[N] = X + Y`.
6. Borrower defaults; call `finalizeDefault`/`finalizeDefaultRecovery` → `defaultPendingClaimBasis` includes `X + Y`; `_defaultPrefundedInstantReserve` adds phantom `X`.
7. `A` calls `claimInstantWithdrawRequest` again → `_claimDefaultedInstantWithdrawRequest` pays `X * defaultRecoveryPrice` a second time from `defaultRecoveryReserve`.
8. Assert the reserve is drained and `B`'s (or a later claimant's) `_transferDefaultRecovery` reverts on insufficient balance — double payout plus insolvency.
