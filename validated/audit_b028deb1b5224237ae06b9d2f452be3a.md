### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing requests to execute below the live-member quorum - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts entries in the `confirmations` set for a request against `num_confirmations` without verifying that each confirming identity is still a current member. `delete_member` only purges pending requests/confirmations that were *created* by the removed member, not confirmations that member *gave* to other members' still-pending requests. As a result, a request can be executed once the raw confirmation count reaches the threshold even though one or more of the counted confirmations came from an account that has since been removed from the multisig, breaking the binding `confirmations counted == live members confirming`.

### Finding Description
`confirm()` executes a request purely based on set size: [1](#0-0) 

`delete_member()` only cleans up requests whose creator (`r.member`) is the member being removed; it does not scan other requests' `confirmations` sets to strip entries belonging to the removed member: [2](#0-1) 

Sequence that breaks the binding:
1. Multisig has members `{A, B, C}` with `num_confirmations = 2`.
2. `B` calls `add_request` to create malicious request `R` (e.g. `Transfer` to an attacker-controlled account). `confirmations[R] = {}`.
3. `A` calls `confirm(R)`. Since `0 + 1 < 2`, it is not executed; `confirmations[R] = {A}`.
4. Through a separate, legitimately-confirmed multisig request, `A` is removed via `DeleteMember`. `delete_member` only removes requests where `r.member == A` (i.e., requests *created* by `A`); `R` was created by `B`, so `confirmations[R] = {A}` is left untouched. Members are now `{B, C}`, still with `num_confirmations = 2`.
5. `B` calls `confirm(R)`. `current_member()` returns `B` (still valid). Check: `confirmations.len() (1, from stale A) + 1 (B) = 2 >= num_confirmations (2)` → `execute_request(R)` runs.

`R` executes with only one live, still-authorized member (`B`) actually approving it in real time, satisfying a 2-of-N threshold with effectively 1 live confirmation plus a phantom vote from a deleted member.

### Impact Explanation
This is a threshold bypass on the on-chain multisig account: `MultiSigRequestAction::Transfer`, `AddKey`, `FunctionCall`, etc. can be executed with fewer live approving members than `num_confirmations` requires. This directly matches the Critical impact category "a multisig request executed below threshold," and can lead to unauthorized transfer of NEAR held by the multisig account or unauthorized key/permission changes on it.

### Likelihood Explanation
No special privilege beyond normal multisig member participation is required to trigger the divergence — it only requires: (a) a pending request that has partial confirmations, and (b) a later, otherwise-legitimate `DeleteMember` action removing one of the confirmers. Membership churn (removing a compromised, departing, or malicious member) is an expected, routine multisig operation, and any pending request with a stale confirmer at that time is silently left in an inconsistent, exploitable state. The bug requires no ignored initialization, no owner/foundation collusion beyond normal governance actions, and no off-chain assumptions.

### Recommendation
In `confirm()`, validate at count time that every account/key in `confirmations` set is still present in `self.members` (or actively prune stale confirmations on any membership change). Alternatively, when deleting a member in `delete_member()`, iterate all pending `requests`/`confirmations` (not just those created by the removed member) and remove the removed member's entry from every confirmations set, decrementing effectively so pending requests correctly reflect only live confirmers.

### Proof of Concept
Given the code in `multisig2/src/lib.rs`:
- `confirm()` at lines 294-315 checks `confirmations.len() as u32 + 1 >= self.num_confirmations` with no liveness check on the confirmers.
- `delete_member()` at lines 356-379 only removes confirmations/requests where `r.member == member` (the member's own created requests), leaving that member's confirmation on other members' pending requests intact.

Reproduction outline (conceptual, matching contract semantics):
1. `new({members: [A,B,C], num_confirmations: 2})`.
2. As `B`: `add_request({receiver_id: <multisig_account>, actions:[Transfer{amount}]})` → `request_id = 0`.
3. As `A`: `confirm(0)` → not executed, `confirmations[0] = {A}`.
4. Via a properly confirmed `DeleteMember{member: A}` request, remove `A`. `confirmations[0]` remains `{A}` since request 0 was created by `B`, not `A`.
5. As `B`: `confirm(0)` → `1 (stale A) + 1 (B) = 2 >= 2` → `execute_request` runs the `Transfer`, moving funds out of the multisig despite only one currently-live member (`B`) having approved in real time. [1](#0-0) [2](#0-1)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
