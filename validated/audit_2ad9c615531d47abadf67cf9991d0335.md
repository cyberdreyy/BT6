### Title
Symlinked directory components bypass workspace-root containment checks, letting `CreateZipArchive` package files from outside the assigned build directory - (File: helpers/archives/zip_create.go, commands/helpers/file_archiver.go)

### Summary
`CreateZipArchive` itself performs no path containment validation at all — it trusts the `fileNames` list and calls `os.Lstat`/`os.Open`/`os.Readlink` on the literal strings [1](#0-0) . The only containment check happens upstream in `commands/helpers/file_archiver.go`, and that check is purely lexical (string-based `filepath.Abs`/`filepath.Rel`), never resolving symlinks with `filepath.EvalSymlinks`. A job-controlled directory symlink whose name has no `..` component passes the check trivially while the OS transparently follows the symlink at open/lstat time, allowing files outside the workspace root to be read into an artifact/cache zip.

### Finding Description
The containment logic lives in `fileArchiver.process()` and `fileArchiver.findRelativePathInProject()`: [2](#0-1) [3](#0-2) 

Both only compute `filepath.Abs`/`filepath.Rel` — purely lexical string manipulation that never touches the filesystem to resolve real paths — and reject a path only if the resulting relative string literally begins with `..`. If an attacker (an unprivileged pipeline author) creates a directory symlink inside the workspace, e.g. `ln -s /some/other/path attacker_link`, and then references it via `artifacts: paths: ["attacker_link/secret.txt"]` in `.gitlab-ci.yml`, the string `attacker_link/secret.txt` never contains `..`, so `findRelativePathInProject` and `process` both approve it as "inside" the workspace even though the real, resolved location is elsewhere.

`doublestar.FilepathGlob(rel, doublestar.WithNoFollow())` only prevents *wildcard expansion* from descending into symlinked directories [4](#0-3) ; it does not stop a literal (non-glob) path component that is a symlink from being resolved by the OS when the resulting match is later passed to `filepath.Walk` and then to `c.process`/`c.add`, which call `os.Lstat` on the literal string [5](#0-4) . Standard POSIX path resolution follows symlinks for all intermediate path components regardless of Go's `filepath.Walk` policy (which only refuses to *recurse into* a symlinked directory, not refuse an explicit path that traverses through one).

Once the file name reaches `CreateZipArchive`, there is no second containment check — `createZipEntry`/`createZipFileEntry` simply `os.Lstat`/`os.Open` the string and copy its contents into the zip [6](#0-5) . The project's own engineering notes explicitly flag this exact class of bug: "`filepath.Walk` does not follow directory symlinks... check whether the walk root is a symlink and resolve it with `filepath.EvalSymlinks` before calling Walk" — a rule that is not applied in `file_archiver.go`'s lexical checks. [7](#0-6) 

### Impact Explanation
On executors where the job's OS user can read files outside its own build directory (shell/ssh executors on a shared host, or any executor with a mounted shared volume reachable at a predictable path — e.g. another project's cache directory, shared secrets, or system files readable by the runner user), a pipeline author can smuggle those files into the job's artifact or cache zip via a directory symlink plus a matching `paths:` entry. The resulting artifact is uploaded and downloadable by anyone with artifact-read access to the job, producing secret exposure or cross-project information disclosure. Impact is bounded by filesystem permissions of the runner's OS user, so it does not grant privilege escalation, but it does violate the stated invariant that "artifact or cache packaging must remain inside the assigned workspace root."

### Likelihood Explanation
Preconditions: the attacker only needs the ability to author `.gitlab-ci.yml` and create files in the job's working directory — both are standard, unprivileged pipeline-author capabilities. Feasibility is high on shell/ssh executors or any setup with predictable shared mount paths; it is largely mitigated on well-isolated container executors (Docker/Kubernetes) where the container filesystem doesn't expose other projects' data at accessible paths, but system files inside the container itself (or shared volumes explicitly configured by the admin) remain reachable. It is fully repeatable since it relies on standard symlink semantics, not a race condition.

### Recommendation
In `commands/helpers/file_archiver.go`, resolve the real path with `filepath.EvalSymlinks` (or an equivalent walk that lstat's each path component) before computing the relative path and containment check in `findRelativePathInProject` and `process`, rejecting any resolved path that escapes `c.wd`. Additionally, consider having `CreateZipArchive`/`createZipEntry` perform a defense-in-depth check against a caller-supplied root, since it currently has no containment logic of its own.

### Proof of Concept
Go test to add near `TestGlobbedFilePath` in `commands/helpers/file_archiver_test.go`:
```go
func TestFileArchiver_SymlinkedDirectoryEscapesWorkspace(t *testing.T) {
    wd := t.TempDir()
    outside := t.TempDir()
    secret := filepath.Join(outside, "secret.txt")
    require.NoError(t, os.WriteFile(secret, []byte("TOP-SECRET"), 0600))

    require.NoError(t, os.Chdir(wd))
    require.NoError(t, os.Symlink(outside, filepath.Join(wd, "attacker_link")))

    c := &fileArchiver{Paths: []string{"attacker_link/secret.txt"}}
    require.NoError(t, c.enumerate())

    // EXPECTED (post-fix): the escaping file must NOT be collected
    for path := range c.files {
        assert.NotContains(t, path, "secret.txt",
            "file outside workspace root was collected: %s", path)
    }
}
```
Expected result today: the assertion fails — `c.files` contains `attacker_link/secret.txt`, and if fed to `CreateZipArchive`, the produced zip embeds the content of `outside/secret.txt`, confirming the escape.

func createZipFileEntry(archive *zip.Writer, fh *zip.FileHeader) error {
	fh.Method = zip.Deflate
	fw, err := archive.CreateHeader(fh)
	if err != nil {
		return err
	}

	file, err := os.Open(fh.Name)
	if err != nil {
		return err
	}

	_, err = io.Copy(fw, file)
	_ = file.Close()
	if err != nil {
		return err
	}
	return nil
}

func createZipEntry(archive *zip.Writer, fileName string) error {
	fi, err := os.Lstat(fileName)
	if err != nil {
		logrus.Warningln("File ignored:", err)
		return nil
	}

	fh, err := zip.FileInfoHeader(fi)
	if err != nil {
		return err
	}
	fh.Name = fileName
	fh.Extra = createZipExtra(fi)
	// Set EFS flag to indicate that filenames and comments are UTF-8 encoded
	fh.Flags |= 0x800

	switch fi.Mode() & os.ModeType {
	case os.ModeDir:
		return createZipDirectoryEntry(archive, fh)

	case os.ModeSymlink:
		return createZipSymlinkEntry(archive, fh)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningln("File ignored:", fileName)
		return nil

	default:
		return createZipFileEntry(archive, fh)
	}
}

func (c *fileArchiver) process(match string) bool {
	var absolute, relative string
	var err error

	absolute, err = filepath.Abs(match)
	if err == nil {
		// Let's try to find a real relative path to an absolute from working directory
		relative, err = filepath.Rel(c.wd, absolute)
	}

	if err == nil {
		// Process path only if it lives in our build directory
		if !strings.HasPrefix(relative, ".."+string(filepath.Separator)) {
			excluded, rule := c.isExcluded(relative)
			if excluded {
				c.exclude(rule)
				return false
			}

			err = c.add(relative)
		} else {
			err = errors.New("not supported: outside build directory")
		}
	}
