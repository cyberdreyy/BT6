### Title
Confirmations from revoked multisig keys are not purged, allowing requests to execute below the live-signer threshold - (File: `multisig/src/lib.rs`)

### Summary
In `MultiSigContract`, when a public key is revoked via the `DeleteKey` action, the contract only removes pending *requests that were originally added by that key* — it does not remove *confirmations* that key previously cast on requests added by other keys. As a result, a request can reach `num_confirmations` and execute even though one or more of the counted confirmations came from a key that has since been deleted from the account, meaning fewer than `num_confirmations` currently-live keys actually approved the action.

### Finding Description
The invariant the contract is supposed to enforce is:

`confirmations.len() >= num_confirmations` should mean "at least `num_confirmations` **currently valid** account keys approved this request."

`confirm()` checks this equality purely by counting entries in the `confirmations: HashSet<PublicKey>` for a request: [1](#0-0) 

Confirmations are added keyed only by `env::signer_account_pk()`, with no re-validation against the account's current key set at confirmation time or at count time.

The only place stale confirmations get cleaned up is inside the `DeleteKey` action handler, and it only clears requests where the deleted key was the *original request submitter* (`r.signer_pk == pk`) — it does not scan the `confirmations` sets of *other* requests to strip out the deleted key: [2](#0-1) 

So the equality that should hold — *confirmations counted == confirmations from live members* — is broken: a pending request created by key `A` and confirmed by key `B`, where `B` is later removed via a `DeleteKey` request submitted by key `A` (or any other key), keeps `B`'s public key in its `confirmations` set forever. When a third live key `C` later calls `confirm()`, `B`'s stale confirmation still counts toward `num_confirmations`, letting the request execute (e.g. a `Transfer` or `AddKey`) with only `C` actually being a currently-authorized signer contributing at that moment, while `B`'s vote is a ghost from a revoked identity.

### Impact Explanation
This lets a multisig request (transfer of NEAR, adding a full-access key, deploying a contract, etc.) execute with effectively fewer live/authorized confirmations than `num_confirmations` requires, because a revoked key's stale confirmation is still counted. This directly matches "a multisig request executed below threshold," which the scope classifies as Critical — funds can move, or a new full-access key can be added to the multisig account, with less real authorization than the configured k-of-n policy demands.

### Likelihood Explanation
This requires no attacker privilege beyond being one of the multisig's own currently valid keyholders (a normal, expected state for a multisig in production, since key rotation/revocation of team members is a standard operational event). No compromise of a "victim key" is needed — the flaw is purely in the bookkeeping: revocation (`DeleteKey`) never audits other pending requests' `confirmations` sets. Any organization that rotates/removes a signer while a request from before the removal is still pending will hit this path.

### Recommendation
When executing `MultiSigRequestAction::DeleteKey`, iterate over all pending requests' `confirmations` sets (not just requests originally added by the deleted key) and remove the deleted public key from each. Alternatively, validate at `confirm()`/execution time that every public key in a request's `confirmations` set still corresponds to an access key currently on the account before counting it toward `num_confirmations`.

### Proof of Concept
Using the existing test harness in `multisig/src/lib.rs`:
1. Deploy `MultiSigContract::new(2)` (2-of-n) with keys `K1` (original), and add `K2` via an `AddKey` request confirmed by `K1` alone is not enough (needs 2), so assume account starts with `K1` and `K2` as live keys, `num_confirmations = 2`.
2. `K1` calls `add_request` with `Transfer{amount}` to some receiver → `request_id = R1`, `confirmations(R1) = {}`.
3. `K2` calls `confirm(R1)` → `confirmations(R1) = {K2}` (not yet enough, needs 2).
4. `K1` submits and self-confirms a separate request `R2 = DeleteKey{K2}` (assume it reaches threshold, e.g. threshold temporarily lowered or a third key co-signs) → `K2` is deleted from the account. Per `execute_request`'s `DeleteKey` branch (`multisig/src/lib.rs:198-216`), only requests where `signer_pk == K2` are purged; `R1` (added by `K1`, merely confirmed by `K2`) is untouched, so `confirmations(R1)` still equals `{K2}`.
5. A new key `K3` is added to the account (or any remaining live key), and calls `confirm(R1)`. In `confirm()` (`multisig/src/lib.rs:248-266`), `confirmations.len() as u32 + 1 = 2 >= num_confirmations (2)`, so `R1` executes the `Transfer` — approved by `K2` (revoked, no longer a valid account key) and `K3`, i.e. only one genuinely live confirmation instead of the required two.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
