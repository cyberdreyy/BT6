This confirms the vulnerability. The `common.requestCache` (used by the production capabilities/vault/confidentialrelay handlers) keys pending requests by `globalId{sender, messageId}` [1](#0-0)  precisely to avoid ID collisions between different senders, and even rejects duplicate `(sender, id)` pairs [2](#0-1) . `dummyHandler`, by contrast, keys `savedCallbacks` solely by `msg.Body.MessageId` with no sender component [3](#0-2) , so two different signers submitting the same attacker-chosen `MessageId` causes the second write to silently overwrite the first callback in the shared map.

### Title
Cross-user response delivery due to sender-agnostic MessageId keying in dummyHandler.savedCallbacks - (File: core/services/gateway/handlers/handler.dummy.go)

### Summary
`dummyHandler` stores pending user callbacks in a map keyed only by `msg.Body.MessageId`, without incorporating the message sender, unlike the production `requestCache` used by other handlers which keys by `(sender, id)`. Two unauthenticated/unprivileged gateway clients that submit a legacy user message or `HandleJSONRPCUserMessage` with the same `MessageId` concurrently will collide in the map, causing one user's request/response to be delivered to another user's HTTP callback.

### Finding Description
`gateway.ProcessRequest` creates a fresh `Callback` for every incoming HTTP request and invokes `h.HandleLegacyUserMessage` (or `HandleJSONRPCUserMessage`, which sets `msg.Body.MessageId = jsonRequest.ID` and delegates to `HandleLegacyUserMessage`) [4](#0-3) . Both the JSON-RPC request `ID` and the legacy `MessageId` field are attacker/client-controlled values, only bounded by length (`MessageIdMaxLen`, and a 200-char cap in `ProcessRequest`) [5](#0-4) [6](#0-5) . Nothing ties the ID to the sender's identity or connection.

In `HandleLegacyUserMessage`, the handler unconditionally overwrites `d.savedCallbacks[msg.Body.MessageId]` with the new callback under a single mutex, with no uniqueness/collision check [3](#0-2) . If sender A and sender B (two different signing keys, different `Sender`) each submit a message using the same `MessageId` string concurrently, whichever request is processed second replaces the first request's saved callback in the map.

When node responses come back, `HandleNodeMessage` looks up `d.savedCallbacks[msg.Body.MessageId]` (the response's own ID, echoed from the request) and delivers the payload to whatever callback is currently stored there [7](#0-6) . The check `nodeAddr != msg.Body.Sender` at line 95 only validates that the responding node's transport address matches the *node's own* signature on the response — it does nothing to verify that the response's `MessageId` legitimately corresponds to the specific waiting HTTP client. Consequently, a node's response intended for user A's request can be routed to user B's blocked HTTP `callback.Wait(ctx)` in `gateway.ProcessRequest`, and user A's connection instead times out or receives no data (DoS) or receives B's stale/incorrect response.

This contrasts with the production `requestCache` implementation used by other handlers (capabilities, vault, confidentialrelay), which explicitly keys by `globalId{sender, id}` and rejects a duplicate `(sender, id)` pair with `"request already exists"` [8](#0-7) , demonstrating that this isolation invariant is a known design requirement that `dummyHandler` fails to enforce.

### Impact Explanation
This is a cross-user response confusion / isolation violation: an unprivileged, unauthenticated gateway HTTP client can cause another concurrent client's response (potentially containing sensitive capability-execution output) to be delivered to the attacker's own connection, or cause the victim's request to hang/time out (DoS of that specific capability execution). This matches the "cross-user response confusion" impact class called out in the audit scope.

### Likelihood Explanation
Exploitability depends entirely on `dummyHandler` being the active handler for a DON/service in the gateway configuration. Per `gateway.go`'s `setupFromNewConfig`, handlers are instantiated per configured service via `HandlerFactory.NewHandler`, and `dummyHandler` is created via `NewDummyHandler` [9](#0-8) . No signature or authentication check ties `MessageId` to a per-connection scope — any two unauthenticated clients can trivially choose the same ID and race requests to trigger the collision. If `dummyHandler` is only used for testing/demo DON shards and not for the production `workflows`/`vault` services (which use `requestCache` with sender-scoped keys instead), real-world exposure is limited to whatever handler type is configured to use it; I could not fully verify from the indexed files whether `dummyHandler` is wired into any production-facing service configuration versus only used in tests/examples.

### Recommendation
Key `savedCallbacks` by a composite of `(msg.Body.Sender, msg.Body.MessageId)` instead of `MessageId` alone, mirroring `common.requestCache`'s `globalId{sender, id}` approach, and reject/reuse-detect duplicate keys rather than silently overwriting.

### Proof of Concept
Go test plan in `core/services/gateway/handlers/handler.dummy_test.go`:
1. Create a `dummyHandler` with a `testConnManager`.
2. Construct message A signed by key A and message B signed by key B (different `Sender` addresses), both with `MessageId = "collide"`.
3. Call `handler.HandleLegacyUserMessage(ctx, &msgA, cbA)` then `handler.HandleLegacyUserMessage(ctx, &msgB, cbB)`.
4. Assert `len(d.savedCallbacks) == 1` and that the entry corresponds to `cbB` only (via reflection/exported test hook, or by proceeding to step 5).
5. Simulate a node response for message A's content (echoing `MessageId = "collide"`, `Sender` = node address) via `handler.HandleNodeMessage`.
6. Assert that `cbB.Wait(ctx)` receives the response (wrong recipient) while `cbA.Wait(ctx)` times out — demonstrating cross-user delivery/DoS.
