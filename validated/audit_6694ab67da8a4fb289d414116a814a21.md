### Title
Cross-caller response hijacking via `MessageId` collision in gateway `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores the caller's `Callback` in `h.savedCallbacks` keyed **only** by the client-supplied `msg.Body.MessageId`, with no binding to the caller's identity/session. Because `MessageId` is fully attacker-controlled (only length/charset is validated) and global uniqueness is never enforced, a second unprivileged gateway client can deliberately submit a request using the same `MessageId` as a concurrent, unrelated request, overwriting the first caller's saved callback and hijacking the eventual DON response.

### Finding Description
`HandleLegacyUserMessage` registers the caller's callback like this: [1](#0-0) 

The only validation performed on `MessageId` is in `Message.Validate()`, which checks length bounds and a null-byte suffix — it never checks uniqueness against in-flight requests, and it never binds the ID to the signer: [2](#0-1) 

The gateway's inbound entrypoint `ProcessRequest` calls `msg.Validate()` (which only derives `Sender` from the signature) and then routes to `HandleLegacyUserMessage` — it never checks `MessageId` against other outstanding requests or other senders: [3](#0-2) 

When a node eventually responds, `handleWebAPITriggerMessage` looks up the callback purely by `MessageId` and delivers the response to whatever callback currently occupies that slot, with no sender/session check: [4](#0-3) 

Exploit flow:
1. Legitimate caller A sends a signed `HandleLegacyUserMessage` request with `MessageId = "X"`. The gateway stores `savedCallbacks["X"] = callbackA` and forwards the request to all DON members.
2. Before the DON responds, attacker B (an unprivileged, independently-authenticated gateway client) sends its own signed request also using `MessageId = "X"` (nothing prevents this — B signs the message with its own key, and `Validate()`/`ProcessRequest` only check length/signature validity, not ID collision). This overwrites `savedCallbacks["X"] = callbackB`.
3. When a DON node responds to A's original request (echoing `MessageId = "X"`), `handleWebAPITriggerMessage` finds `savedCallbacks["X"]` — now `callbackB` — and delivers A's workflow response data to B instead of A.

This is a genuine cross-user response confusion caused purely by the absence of per-sender/session isolation in the `savedCallbacks` key, reachable by two unprivileged external callers with no DON/node compromise required.

### Impact Explanation
An unprivileged attacker who can predict or brute-force/guess a `MessageId` used by a concurrent legitimate request (or simply races many collisions across a busy gateway) can capture another user's workflow trigger response — which may include sensitive HTTP callback data, secrets processed by the DON, or job execution results — resulting in disclosure of one user's data to another unauthorized caller (cross-user data leakage / broken caller isolation).

### Likelihood Explanation
Exploitability depends on the attacker either guessing a victim's `MessageId` or winning a race where many gateway users happen to pick overlapping IDs (e.g., callers using low-entropy or sequential IDs, which the API neither generates nor requires to be random). No node, operator, or admin privileges are needed — only the ability to send signed messages to the gateway as any registered/allowed key, and a window between the victim's request registration and the DON's response. This is a timing-dependent but concretely reachable race with no defense in the code path, so likelihood is moderate: it requires ID predictability/collision but no privileged access.

### Recommendation
Bind `savedCallbacks` entries to both `MessageId` and the caller's `Sender` (e.g., composite key `Sender+MessageId`), reject new `HandleLegacyUserMessage` requests that reuse an in-flight `MessageId` from any other identity, and verify the sender of the eventual DON response payload matches the sender who originally registered the callback for that key before delivering it.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two `api.Message`s, `msgA` and `msgB`, signed by two different private keys, both using `MessageId = "collide-1"`.
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)`; assert `handler.savedCallbacks["collide-1"]` stores `cbA`.
3. Call `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` before any node responds; assert `handler.savedCallbacks["collide-1"]` now stores `cbB` (overwrite, no rejection/error returned).
4. Simulate the DON node responding to `msgA`'s original request via `handler.HandleNodeMessage`/`handleWebAPITriggerMessage` with `MessageId = "collide-1"`.
5. Assert that `cbB.Wait()` (attacker B's callback) receives the response — i.e., `cbA.Wait()` times out or never fires — demonstrating that caller A's response was misdelivered to caller B.
Expected (secure) behavior: `HandleLegacyUserMessage` for `msgB` should either be rejected due to `MessageId` collision with an in-flight request from a different sender, or callbacks should be keyed per-sender so `cbA` still receives its own response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.

		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
