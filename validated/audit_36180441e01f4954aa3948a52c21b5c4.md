### Title
BB tranche holders can front-run `stopEpochWithDuration(_lossAmount)` with `requestWithdraw` to escape the BB-first loss waterfall - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The StakeWise finding is a self-liquidation race: a user dodges the liquidation penalty by liquidating themselves before a liquidator does. The idle-tranches analog is `requestWithdraw`: any tranche holder can atomically convert tranche tokens into a fixed-price withdrawal receipt at any time while `isEpochRunning` is true, including after `epochEndDate` has passed but before the manager's loss-bearing `stopEpochWithDuration` executes. Because pending receipts share the loss pro rata while active positions absorb it BB-first, a BB holder can self-exit into the receipt bucket and sidestep the first-loss penalty.

### Finding Description
`requestWithdraw` is gated only by `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and `isWalletAllowed` — there is no check that the epoch end has been reached or that a loss realization is imminent [1](#0-0) . It prices tranches via `_trancheToUnderlyings` at the pre-loss NAV and immediately mints a fixed-denomination receipt via `creditVault.requestWithdraw` [2](#0-1) . When the manager later calls `stopEpochWithDuration(..., _lossAmount)`, the loss is split by `previewLossAdjustedWithdrawFunds`: "pending receipts share the pending portion of the loss pro rata … the remaining active-position loss uses the ordinary BB-first tranche waterfall" [3](#0-2) , [4](#0-3) .

A BB holder whose tranche would be partially or fully wiped can observe (or anticipate, since `block.timestamp >= epochEndDate` only gates the manager call, not `requestWithdraw`) a pending `stopEpochWithDuration` with `_lossAmount > 0`, front-run it with `requestWithdraw`, and convert a position destined for the BB-first waterfall into a pro-rata receipt haircut. This mirrors the reported bug exactly: an unprivileged user front-runs a privileged settlement transaction to exchange a penalty-grade outcome for a milder one.

### Impact Explanation
The loss-waterfall invariant ("BB absorbs losses first, AA is protected") is broken. The escaping BB holder receives a pro-rata haircut instead of the BB-first haircut; the difference is socialized onto the remaining LPs — other BB holders who did not exit absorb more, and once BB is exhausted, AA holders. With e.g. a loss equal to the BB NAV, an honest BB holder is fully wiped while a front-running BB holder loses only `pendingReceipts / totalBasis` of their position — a direct, quantified transfer of loss proportional to the size of the raced position. This is not merely theoretical value-shift: it is realized NAV theft from remaining LPs.

### Likelihood Explanation
Requires only a KYC-passed tranche holder and a mempool-observable (or publicly anticipated) `stopEpochWithDuration`/`stopEpoch` call carrying `_lossAmount`. Loss events are exactly when managers broadcast these calls, so the window is maximal when the exploit matters most. No privileged role, oracle manipulation, or cooperation is needed; the attacker simply calls a standard user function first. Likelihood is bounded by the race being winnable, but the reward (escaping first-loss absorption) scales with position size.

### Recommendation
Gate withdrawal requests on epoch settlement state: disallow (or queue at post-loss price) `requestWithdraw` once `block.timestamp >= epochEndDate`, or commit the epoch's loss inside a two-step settlement so that the tranche→receipt conversion price used by `requestWithdraw` cannot be fixed at a pre-loss NAV after the loss is publicly known. Alternatively, apply the same BB-first waterfall to pending receipts by recording the tranche identity of each request, so converting into a receipt does not change the holder's loss position.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

function testBBFrontRunsLossViaRequestWithdraw() external {
    // Setup: depositAA + depositBB of equal size, start epoch, APR 0 to isolate loss
    idleCDO.depositAA(10_000 * ONE_SCALE);   // honest senior
    idleCDO.depositBB(10_000 * ONE_SCALE);   // honest BB (victim benchmark)
    // attacker also holds BB
    vm.prank(attacker);
    idleCDO.depositBB(5_000 * ONE_SCALE);

    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    _startEpochAndCheckPrices(0);

    uint256 lossAmount = 12_000 * ONE_SCALE; // > full BB NAV -> BB wipe + AA spillover
    vm.warp(cdoEpoch.epochEndDate() + 1);    // epoch over, still isEpochRunning

    // Attacker sees pending manager tx stopEpochWithDuration(..., lossAmount)
    // and front-runs: converts BB tranches into a pending receipt at pre-loss price.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(BBtranche)); // full balance -> receipt

    // Manager stop executes the loss: pending bucket takes pro-rata share,
    // remaining active BB takes the rest of the BB-first waterfall.
    uint256 duration = cdoEpoch.epochDuration();
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, duration, lossAmount);

    // Attacker's receipt haircut is only pendingBasis / totalBasis of lossAmount,
    // while honest BB holders absorbed the full BB-first share.
    // Attacker withdraws > fair share; remaining LPs' NAV is correspondingly lower.
}
```

Key assertions: `virtualPrice(BBtranche) == 0` (honest BB wiped) while the attacker's claimable receipt ≈ `preLossValue * (1 - pendingShare)` with `pendingShare << 1`. Caveat I could not fully verify within available iterations: the exact pro-rata split inside `IdleCreditVault.previewLossAdjustedWithdrawFunds` (the snippet confirms the documented policy but not the arithmetic), and whether `allowBBWithdrawRequest` could already be false in the raced configuration — it is set `true` at every successful non-default stop, so a normal running epoch exposes the race.
