### Title
Stale rejection weight is never cleared when a signer flips to acceptance, causing double-counted weight in the `StackerDBListener` block tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tallies signer weight for a proposed block in two independent counters, `total_weight_approved` and `total_weight_rejected`, and gates each increment with its own idempotency check. The rejection path uses the shared `responded_signers` set as its guard, while the acceptance path uses the separate `gathered_signatures` map as its guard. Because these are two different sets, a signer who first rejects and later signs (accepts) the same block gets counted in *both* totals: their weight is added once to `total_weight_rejected` when they reject, and — since `gathered_signatures` never saw their slot — added again to `total_weight_approved` when they later accept, with `total_weight_rejected` never being decremented. This mirrors the "double locking of funds" bug class: a new commitment (weight credited to a new bucket) is layered on top of an old one without clearing/unlocking the prior contribution first.

### Finding Description
In the `Accepted` branch, `total_weight_approved` is only incremented if the slot is not already in `gathered_signatures`: [1](#0-0) 

In the `Rejected` branch, `total_weight_rejected` is only incremented if `responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot has responded at all, whether by accept or reject): [2](#0-1) 

The `BlockStatus` struct keeps these as two unrelated fields with no cross-invalidation: [3](#0-2) 

Sequence that breaks the invariant `total_weight_approved + total_weight_rejected == Σ(weight of currently-held vote per unique signer)`:
1. Signer S (slot `k`, weight `w`) sends `BlockResponse::Rejected` for block `H`. `responded_signers.insert(k)` → `true`, so `total_weight_rejected += w`.
2. S later sends `BlockResponse::Accepted` for the same block `H` (a legitimate, protocol-sanctioned action — the signer flow explicitly allows a signer to "stay silent... may sign later if the rival dies out" and to sign after an earlier rejection once conditions change, per `handle_block_pre_commit`/`handle_block_response` in `stacks-signer/src/v0/signer.rs`).
3. In the `Accepted` handler, `gathered_signatures` does not yet contain `k`, so `total_weight_approved += w` executes.
4. `total_weight_rejected` is never decremented, so S's weight `w` is now counted in *both* totals simultaneously.

This directly affects the block-acceptance decision in `SigningCoordinator::run`, where the rejection check is evaluated first and, on success, aborts the block outright: [4](#0-3) 

Because the rejection branch (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`) is checked before the approval branch, a stale, double-counted rejection weight can push the coordinator into believing a supermajority rejected the block and return `Err(NakamotoNodeError::SignersRejected)` even though the actual currently-standing set of signers now supports (or would support) the block once their flip is honored.

### Impact Explanation
This is a liveness wedge reachable by a single signer's ordinary, protocol-permitted behavior (reject-then-sign), gossiped through StackerDB and observed by the one-slot miner's `StackerDBListener`/`SigningCoordinator`. It can cause the coordinator to discard a validly signed, canonical block as globally rejected (`SignersRejected`), forcing the miner thread to abandon block construction even when the honest, currently-held votes would meet the 70% signing threshold. It also violates the implicit invariant that a signer's weight is counted in exactly one bucket at a time, corrupting both tallies used for threshold decisions (`total_weight_approved >= weight_threshold` and `total_weight_rejected + weight_threshold > total_weight`).

### Likelihood Explanation
No majority coordination, key compromise, or auth token is required — a single ordinary signer following the documented reject-then-sign flow (or a signer changing its mind due to timing/reorg considerations, as the coordinator explicitly plans for) triggers the stale counter. The bug only requires that a signer post a `Rejected` message for a block and subsequently post an `Accepted` message for that same block hash — both are normal `BlockResponse` messages the miner listener already handles.

### Recommendation
When processing an `Accepted` (or `Rejected`) `BlockResponse` for a slot that has previously registered the opposite verdict, remove/decrement the stale contribution from the other counter (or track per-slot current-vote state instead of two independently-gated counters) so that each signer's weight is reflected in exactly one of `total_weight_approved` / `total_weight_rejected` at any time, mirroring how `signerdb.rs::add_block_signature` explicitly deletes any prior rejection row for the same signer/block before recording a signature.

### Proof of Concept
1. Reward set has signer S with weight `w`, plus enough other weight so the true remaining rejecting weight (excluding S) is just under the blocking minority threshold (`total_weight - weight_threshold`).
2. S broadcasts `BlockResponse::Rejected` for block `H` → `StackerDBListener` sets `responded_signers = {k}`, `total_weight_rejected = w + (other genuine rejecters)`.
3. Enough of the remaining honest weight accepts, but the sum without S's flip is still slightly under `weight_threshold` for approval and just under blocking minority for rejection — a live, contested block.
4. S subsequently broadcasts `BlockResponse::Accepted` for `H` (legitimate per the documented "sign later if the rival dies out" flow) → `gathered_signatures` gets `k`, `total_weight_approved += w`, but `total_weight_rejected` still includes S's earlier `w`.
5. `SigningCoordinator::run` now observes `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (because S's weight is double counted) and returns `Err(SignersRejected)`, discarding a block that legitimately has enough current acceptance weight, or alternatively reports a lower percent_approved than reality while `total_weight_rejected` remains inflated — demonstrating the tally corruption described above.
