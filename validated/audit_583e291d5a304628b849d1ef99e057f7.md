### Title
`UpdateCommissionBps` removes any timing restriction on commission changes, letting a vote account's authorized withdrawer instantly seize a full epoch's stake rewards - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The `BoostAggregator` bug lets a fee-collecting owner raise `protocolFee` to 100% at will and redirect all of a depositor's already-accrued rewards to themselves. The directly analogous, reachable-by-a-single-transaction path in Agave is the vote program's commission-update instructions. The legacy `UpdateCommission` instruction enforces a timing rule that limits mid-epoch commission increases, but the newer `UpdateCommissionBps` instruction (SIMD-0291/SIMD-0123) explicitly removes that rule, allowing the vote account's authorized withdrawer to change the commission that stakers' inflation/block rewards will be split by, at any time, with no minimum-delay guarantee unless the separate `delay_commission_updates` feature is active.

### Finding Description
`update_commission` (legacy path) enforces `is_commission_update_allowed` whenever the new commission is an increase and `disable_commission_update_rule` is false: [1](#0-0) 

By contrast, `update_commission_bps`, which sets `inflation_rewards_commission_bps` (the field actually consumed by reward calculation when the `commission_rate_in_basis_points` feature is active), performs no timing check at all — the code comment states this outright ("No commission update rule, per SIMD-0249 and SIMD-0291"), requiring only the authorized withdrawer's signature: [2](#0-1) 

The instruction is dispatched directly from `VoteInstruction::UpdateCommission`/commission-bps variants in `vote_processor.rs`, reachable via a single ordinary vote-program transaction signed by the authorized withdrawer, with `disable_commission_update_rule` gated on the `delay_commission_updates` feature: [3](#0-2) 

Reward calculation reads the effective commission for a stake's epoch rewards from `vote_state.inflation_rewards_commission()` unless `delay_commission_updates` is enabled, in which case it instead consults a previous-epoch cached snapshot to delay the effect by one epoch: [4](#0-3) 

That commission value is then used to split the epoch's stake reward between the voter (commission collector) and the staker via `commission_split`/`commission_split_preserve_lamports`, where a 10_000 bps (100%) commission routes the *entire* reward to the voter and zero to the staker: [5](#0-4) [6](#0-5) 

If `delay_commission_updates` is not active on a given cluster/epoch (it is a feature-gated behavior, not an unconditional invariant), the authorized withdrawer of any vote account can submit an `UpdateCommissionBps` transaction immediately before epoch-boundary reward calculation and set commission to 10_000 bps, causing all delegators' inflation/stake rewards for that epoch to be redirected to the commission collector, then lower it back afterward. This is exactly the `BoostAggregator` pattern: a fee percentage controlled by a single privileged-but-not-globally-trusted key can be pushed to 100% to seize funds that other parties (stakers) believed they were entitled to, with no per-account snapshot of "the rate the user delegated under."

### Impact Explanation
A malicious or compromised vote-account withdraw authority can, in a single unsigned-by-victims transaction, capture 100% of that epoch's inflation and/or block-revenue rewards owed to every staker delegated to that vote account, when the mitigating `delay_commission_updates` feature is not engaged for the relevant path/epoch. This is real, uncompensated fund redirection of stake rewards away from delegators to the commission collector — a direct analog to "unconstrained fee/commission field lets an owner steal accrued rewards."

### Likelihood Explanation
Likelihood is bounded by the same trust caveat the original report received (Medium, not High): it requires control of the vote account's authorized-withdrawer key, not an arbitrary unprivileged sender. However, unlike `BoostAggregator`'s owner (who cannot touch funds already withdrawn), a vote-account withdraw authority is routinely delegated-to by many independent stakers who have no visibility into, or control over, when the operator changes commission, and the `update_commission_bps` code path was deliberately built with *no* rate-of-change or minimum-notice protection ("No commission update rule"), whereas the legacy path retains one. This makes the SIMD-0291 bps path strictly weaker than the pre-existing legacy protection for the identical fund-safety property, and the protection against the attack fully depends on the orthogonal `delay_commission_updates` feature being active for a given epoch/path.

### Recommendation
Ensure `UpdateCommissionBps` (and any other commission-mutating instruction) is unconditionally covered by the epoch-snapshot delay logic used in `redeem_delegation_rewards`, independent of whether `delay_commission_updates`/`commission_rate_in_basis_points` are separately toggled, so that commission changes can never retroactively affect the reward computed for the epoch in which they were made. Consider re-adding a minimum-notice/rate-limit rule (mirroring `is_commission_update_allowed`) to `update_commission_bps` rather than relying solely on downstream feature flags.

### Proof of Concept
1. Attacker controls (or the operator is malicious) an authorized withdrawer for vote account `V`, which has many stakers delegated to it.
2. Near the end of an epoch, before epoch-boundary reward calculation (`calculate_rewards_for_partitioning`/`redeem_delegation_rewards`), submit a transaction invoking `VoteInstruction::UpdateCommissionBps(10_000, CommissionKind::InflationRewards)` — this succeeds unconditionally per `update_commission_bps` (no timing check), signed only by the authorized withdrawer.
3. If `delay_commission_updates` is not active (or the relevant snapshot mechanism does not cover the path being exploited), reward calculation reads `vote_state.inflation_rewards_commission()` at 10_000 bps.
4. `commission_split`/`commission_split_preserve_lamports` route 100% of the epoch's stake reward to the voter (commission collector) and 0% to every staker delegated to `V`.
5. Attacker submits another `UpdateCommissionBps` afterward to restore the original low commission, resuming normal appearance for future epochs while having captured one full epoch of all delegators' rewards.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

#[cfg_attr(any(test, feature = "dev-context-only-utils"), qualifiers(pub(crate)))]
fn commission_split(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let on = u128::from(on);
            // Calculate mine and theirs independently and symmetrically instead of
            // using the remainder of the other to treat them strictly equally.
            // In Tower, this is also to cancel the rewarding if either of the parties
            // should receive only fractional lamports, resulting in not being rewarded at all.
            // Thus, note that we intentionally discard any residual fractional lamports.
            let mine = on
                .checked_mul(u128::from(split))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let theirs = on
                .checked_mul(u128::from(
                    MAX_BPS
                        .checked_sub(split)
                        .expect("commission cannot be greater than MAX_BPS"),
                ))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;

            (mine as u64, theirs as u64, true)
        }
    }
}

fn commission_split_preserve_lamports(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let staker_bps = MAX_BPS
                .checked_sub(split)
                .expect("commission cannot be greater than MAX_BPS");
            let staker_rewards = u128::from(on)
                .checked_mul(u128::from(staker_bps))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let staker_rewards = staker_rewards as u64;
            let voter_rewards = on
                .checked_sub(staker_rewards)
                .expect("staker rewards cannot exceed total rewards");

            (voter_rewards, staker_rewards, true)
        }
    }
}
