### Title
Stale `block_pre_commits` rows are never invalidated on rejection, letting a withdrawn pre-commit's weight still count toward the signing threshold - (File: stacks-signer/src/signerdb.rs, stacks-signer/src/v0/signer.rs)

### Summary
`SignerDb::add_block_pre_commit` records a signer's pre-commit to a block in the `block_pre_commits` table keyed by `(signer_signature_hash, signer_addr)`, and this row is never deleted or invalidated once that same signer later rejects the very same block. `get_block_pre_committers` unconditionally returns every address ever recorded, and `handle_block_pre_commit` sums their weight via `compute_signature_signing_weight` to decide whether the 70% pre-commit threshold has been reached. This is structurally identical to the reported `shareBalance` bug: a membership record that should have been retracted (a curator's zero balance / a signer's withdrawn pre-commit) is left in the map and keeps being counted in an aggregate that gates a state transition (reward distribution / signing a block).

### Finding Description
`add_block_pre_commit` only ever inserts/replaces a row for `(hash, addr)`: [1](#0-0) 

`get_block_pre_committers` reads back every address that has ever pre-committed to that exact block hash, with no filter for signers who have since rejected the block: [2](#0-1) 

When a peer's rejection is processed, only the separate `block_rejection_signer_addrs` table is touched (`add_block_rejection_signer_addr`); it neither reads nor deletes anything from `block_pre_commits`: [3](#0-2) 

`handle_block_pre_commit` is the sole place that tallies pre-commit weight and gates signing. On every incoming (or replayed) pre-commit message it re-fetches *all* historical committers and sums their current signer weight, regardless of whether some of those addresses have since rejected the same block: [4](#0-3) 

The only guard against acting on stale data is the *local* signer's own `block_info.valid` flag (set by our own rejection), not the state of other signers who already retracted their pre-commit: [5](#0-4) 

So the equality that should hold — "pre-commit weight == weight of signers who currently still endorse this block" — is broken: it actually computes "weight of every signer who *ever* pre-commited to this block, whether or not they've withdrawn that endorsement by rejecting it since."

### Impact Explanation
This is an aggregated-weight vs. verified-accepts mismatch. A signer using `handle_block_pre_commit` to decide it has crossed the ≥70% pre-commit threshold may do so using weight contributed by signers who have already rejected the block (e.g., because a miner produced a conflicting/competing proposal at the same height that caused those signers to flip from pre-commit to rejection via `store_and_process_block_rejection`/`mark_locally_rejected`). Because the stale `block_pre_commits` rows persist forever, a late or replayed pre-commit gossip message (from a slow signer, or simply re-delivery over StackerDB) can retrigger `handle_block_pre_commit`, recompute the tally including the withdrawn weight, and push the local signer over threshold to sign a block that a meaningful fraction of the signer set has already rejected as invalid/conflicting. This falls under the "High" impact bucket in the rules — the aggregated weight is not the verified/current set of accepts, undermining the integrity of the 70% threshold that gates block signing.

### Likelihood Explanation
The trigger requires only normal protocol behavior plus a fork/conflicting proposal from a single miner (in scope, "a one-slot miner (plus gossip)"): propose block A, let it accumulate pre-commits, then cause a subset of those same signers to reject A (e.g., by making a conflicting sibling proposal that trips `check_block_against_signer_db_state`/`get_signed_conflicts`), and rely on gossip re-delivery/late arrival of one more pre-commit message for A to re-trigger the weight tally in `handle_block_pre_commit`. No majority of signers, no signer keys, and no auth token are needed — this is entirely a data-retention bug in `SignerDb`.

### Recommendation
When a signer's rejection for a block is recorded (`add_block_rejection_signer_addr` / `store_and_process_block_rejection`), also delete (or otherwise invalidate) that signer's row in `block_pre_commits` for the same `signer_signature_hash`, so `get_block_pre_committers` only ever returns currently-standing pre-commits. Alternatively, have `handle_block_pre_commit`'s weight computation subtract out any address present in `block_rejection_signer_addrs` for the same hash before tallying `compute_signature_signing_weight`.

### Proof of Concept
Not independently executed against a live signer cluster; this analysis is based on static code tracing of `stacks-signer/src/signerdb.rs` and `stacks-signer/src/v0/signer.rs`. A concrete PoC would:
1. Start a signer set with signers S1..Sn observing block A's proposal.
2. Have S1..Sk send `BlockPreCommit(A)`, driving `handle_block_pre_commit` to accumulate their weight in `block_pre_commits`.
3. Have S1..Sk subsequently reject A (e.g., via a conflicting proposal B at the same height, or a chainstate re-check failure), calling `store_and_process_block_rejection`, and confirm (by querying `block_rejection_signer_addrs`) that their rows in `block_pre_commits` are unaffected/still present.
4. Replay one of S1..Sk's original `BlockPreCommit(A)` message (or have any other signer send a fresh late pre-commit for A), and observe that `get_block_pre_committers(A)` still returns S1..Sk, inflating `compute_signature_signing_weight` past the threshold in `handle_block_pre_commit`, despite those signers having withdrawn support for A.

    /// Record an observed block rejection_signature
    pub fn add_block_rejection_signer_addr(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        addr: &StacksAddress,
        reject_reason: RejectReasonPrefix,
    ) -> Result<bool, DBError> {
        // If this signer/block already has a signature, do not allow a rejection
        let sig_qry = "SELECT EXISTS(SELECT 1 FROM block_signatures WHERE signer_signature_hash = ?1 AND signer_addr = ?2)";
        let sig_args = params![block_sighash, addr.to_string()];
        let exists = self.db.query_row(sig_qry, sig_args, |row| row.get(0))?;
        if exists {
            warn!("Cannot add block rejection because a signature already exists.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %addr,
                "reject_reason" => ?reject_reason
            );
            return Ok(false);
        }

        // Check if a row exists for this sighash/signer combo
        let qry = "SELECT reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2 LIMIT 1";
        let args = params![block_sighash, addr.to_string()];
        let existing_code: Option<i64> =
            self.db.query_row(qry, args, |row| row.get(0)).optional()?;

        let reject_code = reject_reason as i64;

        match existing_code {
            Some(code) if code == reject_code => {
                // Row exists with same reject_reason, do nothing
                debug!("Duplicate block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(false)
            }
            Some(_) => {
                // Row exists but with different reject_reason, update it
                let update_qry = "UPDATE block_rejection_signer_addrs SET reject_code = ?1 WHERE signer_signature_hash = ?2 AND signer_addr = ?3";
                let update_args = params![reject_code, block_sighash, addr.to_string()];
                self.db.execute(update_qry, update_args)?;
                debug!("Updated block rejection reason.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
            None => {
                // Row does not exist, insert it
                let insert_qry = "INSERT INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr, reject_code) VALUES (?1, ?2, ?3)";
                let insert_args = params![block_sighash, addr.to_string(), reject_code];
                self.db.execute(insert_qry, insert_args)?;
                debug!("Inserted block rejection.";
                    "signer_signature_hash" => %block_sighash,
                    "signer_address" => %addr,
                    "reject_reason" => ?reject_reason
                );
                Ok(true)
            }
        }
    }
