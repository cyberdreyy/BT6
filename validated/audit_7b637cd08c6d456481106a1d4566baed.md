### Title
Unbounded per-call CPU/memory cost for base64 encoding of attacker-sized Buffer/ProgramData accounts via getAccountInfo(jsonParsed) - ([File: account-decoder/src/parse_bpf_loader.rs])

### Summary
`parse_bpf_upgradeable_loader` unconditionally base64-encodes the entire trailing program payload of a `Buffer`/`ProgramData` account with no size cap, and the RPC layer's only size guard (`encode_account` in `rpc/src/rpc.rs`) only rejects oversized requests for `Binary`/`Base58` encodings, not for `Base64` or `JsonParsed`. An attacker can therefore write a large (up to `MAX_PERMITTED_DATA_LENGTH`, ~10MB) `Buffer` account cheaply and force a single `getAccountInfo`/`jsonParsed` (or plain `base64`) call to pay CPU/allocation cost proportional to that attacker-chosen size.

### Finding Description
`encode_ui_account` (`account-decoder/src/lib.rs:46-101`) dispatches on requested encoding. For `Base64` it directly calls `BASE64_STANDARD.encode(slice_data(account.data(), data_slice_config))` with no length check [1](#0-0) . For `JsonParsed`, it calls `parse_account_data_v3`, and only falls back to base64 of the raw data if parsing fails [2](#0-1) .

For a `bpf_loader_upgradeable`-owned account, `parse_account_data_v3` routes to `parse_bpf_upgradeable_loader` (`account-decoder/src/parse_bpf_loader.rs:13-64`). For `Buffer` and `ProgramData` variants, it unconditionally does `BASE64_STANDARD.encode(&data[offset..])` over the *entire* remainder of the account data, with no cap independent of `account.data().len()` [3](#0-2) . Since this call succeeds (it's a valid `Buffer`/`ProgramData` header), the `JsonParsed` fallback path in `encode_ui_account` is never hit — the full-size base64 encode happens inside the "successful" parse path itself.

At the RPC layer, `encode_account` (`rpc/src/rpc.rs:2575-2601`) is the only gate that checks size, and it explicitly limits its check to `Binary`/`Base58`:
```
if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
    && ... > MAX_BASE58_BYTES { ... Err(...) }
else { Ok(encode_ui_account(...)) }
``` [4](#0-3) 
No equivalent ceiling exists for `Base64` or `JsonParsed`, so `encode_ui_account`/`parse_bpf_upgradeable_loader` is invoked directly on the full account data regardless of size.

An attacker with no privileged access can create a `Buffer` account (via `InitializeBuffer`/`Write` instructions of the upgradeable loader) sized up to `MAX_PERMITTED_DATA_LENGTH` (referenced throughout `programs/bpf_loader/src/lib.rs`), paying only rent-exemption lamports, and populate it with arbitrary bytes as the "program" payload. A single subsequent `getAccountInfo(pubkey, {encoding: 'jsonParsed'})` (or `{encoding: 'base64'}`) call forces the validator's RPC thread to allocate and base64-encode the entire buffer in one synchronous call, scaling cost with attacker-chosen size rather than any fixed RPC-side limit.

### Impact Explanation
This is a single-call, single-client RPC cost-amplification bug: one `getAccountInfo` call against an attacker-controlled ~10MB `Buffer`/`ProgramData` account causes the responding RPC/JSON-RPC worker to perform O(account size) allocation and base64 encoding work, with no explicit ceiling from the RPC layer for `Base64`/`JsonParsed` encodings (only `Binary`/`Base58` are capped by `MAX_BASE58_BYTES`). Repeated at up to the permitted one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` rate, this causes multi-hundred-millisecond+ per-call stalls, degrading RPC responsiveness — this matches Agave's "unbounded resource consumption from a single low-rate RPC call" bounty category.

### Likelihood Explanation
Fully feasible with unprivileged access: creating and writing a large `Buffer` account only requires rent-exempt lamports and standard `bpf_loader_upgradeable` `InitializeBuffer`/`Write` instructions, no special authority is needed to *create* a Buffer (only to later deploy/upgrade with it). Once written, the account persists on-chain and can be queried repeatedly via the public JSON-RPC `getAccountInfo` method, making the attack trivially repeatable without further cost beyond the one-time rent deposit (recoverable by closing the buffer).

### Recommendation
Enforce a maximum data size (or require the RPC layer to reject/require `dataSlice`) uniformly across all `UiAccountEncoding` variants — not just `Binary`/`Base58` — in `encode_account` (`rpc/src/rpc.rs`), and/or add a bound in `parse_bpf_upgradeable_loader`/`encode_ui_account` so that base64 encoding of `Buffer`/`ProgramData` payloads is capped (e.g., falling back to raw base64 truncated by `dataSlice` or an explicit RPC config limit) before the parser encodes the full trailing payload.

### Proof of Concept
```rust
// account-decoder/src/parse_bpf_loader.rs (add to test module)
#[test]
fn test_parse_bpf_upgradeable_loader_buffer_cost_scales_with_size() {
    use std::time::Instant;
    let authority = Pubkey::new_unique();
    let bpf_loader_state = UpgradeableLoaderState::Buffer {
        authority_address: Some(authority),
    };
    for size in [1024usize, 1024 * 1024, 10 * 1024 * 1024] {
        let mut account_data = bincode::serialize(&bpf_loader_state).unwrap();
        account_data.extend(vec![0x41u8; size]); // attacker payload up to MAX_PERMITTED_DATA_LENGTH
        let start = Instant::now();
        let parsed = parse_bpf_upgradeable_loader(&account_data).unwrap();
        let elapsed = start.elapsed();
        // Assertion that SHOULD hold if a cap existed but currently does not:
        // elapsed should be bounded independent of `size`; instead it scales with `size`.
        println!("size={size} elapsed={elapsed:?}");
        match parsed {
            BpfUpgradeableLoaderAccountType::Buffer(buf) => {
                if let UiAccountData::Binary(b64, _) = buf.data {
                    assert_eq!(b64.len(), (size as f64 * 4.0 / 3.0).ceil() as usize + 4 /* rough */);
                }
            }
            _ => panic!("unexpected"),
        }
    }
}
```
Expected result: encode time and output size grow linearly with `size` up to `MAX_PERMITTED_DATA_LENGTH` (~10MB), demonstrating no RPC-side or parser-side cap. An integration test in `rpc/src/rpc.rs` calling `getAccountInfo` with `{encoding: "jsonParsed"}` against a bank-stored account owned by `bpf_loader_upgradeable::id()` with `UpgradeableLoaderState::Buffer` header + 10MB payload would show the same unbounded latency, confirming `encode_account`'s size guard (`rpc/src/rpc.rs:2581-2600`) does not apply to `Base64`/`JsonParsed`.
