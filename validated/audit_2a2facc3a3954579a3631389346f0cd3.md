### Title
Instant-withdraw receipts are fungible against the pooled strategy balance — an unfunded receipt can steal funds collected for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2021-36047 (improper input validation enabling unintended execution/impact), `IdleCreditVault.claimInstantWithdrawRequest` pays out the caller's entire `instantWithdrawsRequests` receipt balance from the strategy's pooled underlying without validating that the caller's specific request was funded via `collectInstantWithdrawFunds`. Funding and claiming are fully decoupled: `pendingInstantWithdraws` is only decremented when the CDO funds the queue, and receipts are minted to users at request time, so any unfunded receipt holder can spend underlying that was collected for other claimants or that sits in the strategy (e.g., the prefunded instant reserve from a failed borrower send at `startEpoch`).

### Finding Description [1](#0-0) 

`requestInstantWithdraw` burns the CDO's strategy tokens and mints a receipt to the user, incrementing `pendingInstantWithdraws` [2](#0-1) . Later, `collectInstantWithdrawFunds` pulls underlying into the strategy and decrements `pendingInstantWithdraws`, but the funded underlying is not earmarked per request or per epoch [3](#0-2) . `claimInstantWithdrawRequest` then:

- reads `amount = instantWithdrawsRequests[_user]` with no check that epoch advanced, no check that the request was funded, and no decrement of `pendingInstantWithdraws` to account for the payment;
- burns the receipt and transfers strategy underlying via `_transferFundedClaim`, which only guards `defaultRecoveryReserve` — not the funded-but-unclaimed instant pool.

Compare with `claimWithdrawRequest`/`_claimFundedWithdrawRequest`, which explicitly gate on `epochNumber > lastWithdrawRequest[_user]` [4](#0-3) . Instant claims have no equivalent per-request lifecycle validation.

Concrete sequence (attacker = KYC'd lender / instant-withdraw user, all privileged actors honest):

1. Buffer/running epoch, instant withdrawals enabled. Victim A requests an instant withdraw; manager stops the epoch; the CDO calls `collectInstantWithdrawFunds` and pulls A's underlying into the strategy. `pendingInstantWithdraws` decreases by A's amount, but `instantWithdrawsRequests[A]` still holds the claim until A calls.
2. Attacker B, holding a small tranche position, requests an instant withdraw through the CDO (their receipt is minted; `pendingInstantWithdraws` increases — this request is unfunded because the epoch already stopped).
3. B calls `claimInstantWithdrawRequest` via the CDO. The function pays B the full receipt amount out of the pooled strategy balance — i.e., out of the underlying that was collected to pay A.
4. A's subsequent claim either reverts on insufficient balance or is paid from other users' funded reserves.

The same flaw applies to underlying already held by the strategy from `_defaultPrefundedInstantReserve` sources (borrower-send funds that failed at epoch start, or partial instant prefunding): before `defaultRecoveryFinalized`, `defaultRecoveryReserve` is 0 so `_transferFundedClaim`'s guard does not protect that balance, and any unfunded instant receipt can drain it.

### Impact Explanation
Direct theft of funded-but-unclaimed instant-withdraw proceeds and of the prefunded instant reserve. Loss is bounded by the strategy's unreserved underlying balance, which equals the aggregate of all funded instant claims not yet claimed plus any stranded borrower-send funds — in a real deployment this is the entire pending instant payout queue. The "one receipt one funded payout" invariant is broken because funding is tracked only in aggregate (`pendingInstantWithdraws`) while claims consume from a shared, unattributed balance.

### Likelihood Explanation
Requires the instant-withdraw feature to be enabled (supported in `IdleCDOEpochVariant` non-prefunded mode) and a window where the strategy holds collected underlying while new instant requests can still be opened — which occurs naturally in the buffer period and around epoch transitions. The attacker only needs a KYC-passing wallet and a tranche position to mint an instant receipt; no privileged role, oracle manipulation, or default is required. Pre-default this also works against any underlying the strategy happens to hold, not just funded claims.

### Recommendation
Track instant-withdraw funding state per request epoch (e.g., `instantWithdrawFundedByEpoch` or a per-request funded flag/basis recorded in `instantWithdrawsRequestsByEpoch` at `collectInstantWithdrawFunds` time) and in `claimInstantWithdrawRequest` pay only the funded portion, decrementing `pendingInstantWithdraws`-equivalent accounting symmetrically — mirroring how `withdrawsRequestsByEpoch` + `lossRecoveryPriceByEpoch` attribute normal claims to epochs. Alternatively, gate claims on `epochNumber` advancement and earmark collected funds per claim epoch.

### Proof of Concept
Conceptual Foundry fork PoC (test scaffolding mirrors `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Setup: idleCDO (IdleCDOEpochVariant) + IdleCreditVault strategy,
// instant withdraw enabled via cdoEpoch.setInstantWithdrawParams(delay, aprDelta, false).

// 1) Victim A deposits and requests instant withdraw
idleCDO.depositAA(10_000e6); // victim A (or test contract)
cdoEpoch.requestInstantWithdrawAA(10_000e6); // mints receipt to A, pendingInstantWithdraws += 10k

// 2) Manager stops epoch; borrower repays; CDO funds the instant queue
vm.prank(manager); cdoEpoch.stopEpoch(apr, 0);
// CDO internally calls strategy.collectInstantWithdrawFunds(...) -> underlying moved to strategy
assertEq(underlying.balanceOf(address(strategy)), 10_000e6);
assertEq(strategy.pendingInstantWithdraws(), 0);

// 3) Attacker B opens an instant withdraw (buffer period before next startEpoch)
vm.startPrank(attacker);
idleCDO.depositAA(1_000e6);
cdoEpoch.requestInstantWithdrawAA(1_000e6); // receipt minted to B, unfunded
// B claims immediately through the CDO claim path
cdoEpoch.claimInstantWithdrawRequest(attacker);
vm.stopPrank();

// 4) B received underlying that was collected for A
assertEq(underlying.balanceOf(attacker), 1_000e6);
// A's later claim now reverts / is short-paid
vm.expectRevert(); // insufficient strategy balance
cdoEpoch.claimInstantWithdrawRequest(victimA);
```

Caveat: the exact claim entry point on the CDO side (whether `claimInstantWithdrawRequest` is reachable directly by users or routed through a queue/orchestrator) was not fully verified in this pass; the strategy-level invariant violation (no funding validation on claims) is confirmed in `IdleCreditVault.sol` lines 380–393 regardless of which caller path triggers it.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```
