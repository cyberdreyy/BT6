### Title
Stale confirmations from deleted multisig members remain counted toward execution threshold, allowing requests to execute with fewer live signers than `num_confirmations` - (File: `multisig2/src/lib.rs`)

### Summary
The external report's bug class — an action executing without the full set of intended, live authorizations — maps onto `multisig2`'s `DeleteMember` / `confirm` logic. When a member is removed via `DeleteMember`, the contract only purges requests and confirmations *originated by* that member, but does not scrub confirmations that member previously cast on requests originated by *other* members. Those stale confirmations remain in the `confirmations` set and continue to count toward `num_confirmations` when a later `confirm()` call checks the threshold.

### Finding Description
`delete_member()` removes outstanding requests keyed by `r.member == member` (i.e., requests the deleted member created), but does nothing to `confirmations` entries where the deleted member is merely one of the confirmers on someone else's request: [1](#0-0) 

Meanwhile, `confirm()` determines whether to execute purely by counting entries in the `confirmations` `HashSet<String>` against `self.num_confirmations`, without re-validating that every counted confirmer is still a current member: [2](#0-1) 

The binding that should hold is: `confirmations counted == confirmations from members that are members at execution time`. Because `delete_member` never scrubs stale confirmations on requests it didn't originate, this becomes `confirmations counted >= confirmations from live members`, i.e. an inequality favoring premature execution.

Concretely:
1. Members A, B, C, D exist, `num_confirmations = 3`.
2. B adds a request (e.g., `Transfer` of funds, or `AddKey`/`AddMember` granting new access).
3. A confirms it (1 confirmation: A). D confirms it (2 confirmations: A, D). Request is now one confirmation away from executing but not yet executed.
4. Before the third confirmation is cast, a separate request to `DeleteMember { member: D }` is created and confirmed by A, B, C (3 of them), executing and removing D from `self.members`.
5. `delete_member` only removes requests/confirmations where `r.member == D` (i.e., requests D personally created) — the pending request from step 2 was created by B, so D's confirmation on it is untouched.
6. Now only C (a live member) needs to confirm the pending request from step 2. C confirms — `confirmations.len() + 1 = 3 >= num_confirmations (3)` — and the request executes.
7. The request executed with confirmations from {A, D, C}, but D is no longer a member at execution time. Effectively only 2 of 3 confirmations came from currently-authorized members, i.e., the request executed below the intended live-member threshold.

This directly parallels the report's core issue: an action (fund transfer / privileged action) is authorized/executed using state (a stale confirmation) that no longer corresponds to a currently valid authorization, similar to the Gnosis-Safe report's "not linked to signed/valid state" theme.

### Impact Explanation
This breaks the multisig's authorization threshold guarantee: a `Transfer`, `AddKey`, `AddMember`, `FunctionCall`, or other privileged `MultiSigRequestAction` can execute with fewer genuinely live, currently-authorized confirmations than `num_confirmations` requires. This maps to "a multisig request executed below threshold" — a Critical impact per the rubric, since it allows movement of NEAR/tokens or privilege escalation (e.g., adding an attacker-controlled key/member) without the full intended quorum of live signers.

### Likelihood Explanation
Exploitation requires: (a) a legitimate multisig member to be removed (a routine, expected multisig operation — e.g., offboarding a compromised or departing signer) while (b) that member has an outstanding confirmation on some other pending request. This is a realistic operational sequence for any active multisig with several concurrently pending requests, and does not require any privileged attacker capability beyond normal member behavior/timing — a departing/compromised member's stale vote silently persists and can be leveraged by the remaining signers (or by the very member being removed, if their confirmation was cast maliciously in anticipation of removal) to push a request through with less than the configured threshold of *live* approval.

### Recommendation
When a member is deleted, iterate over `self.confirmations` for all pending requests and remove the deleted member's entry from every confirmation set (not just requests they authored), or alternatively re-validate at `confirm()`/execution time that every address in the `confirmations` set is still present in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
See the reproduction narrative above (steps 1–7): create request R1 (by B), gather confirmations from A and D, remove D from the multisig via a separate `DeleteMember` request, then have C confirm R1. R1 executes because `confirmations.len()+1 >= num_confirmations` counts D's confirmation even though D is no longer a member, verified against: [3](#0-2) [4](#0-3)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
