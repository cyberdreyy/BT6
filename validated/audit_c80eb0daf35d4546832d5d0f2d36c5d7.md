### Title
Unauthenticated CPU/Resource-Exhaustion DoS via Unbounded `topics` Array in Gateway Web API Trigger Requests - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's legacy user-message path for `web_api_trigger` explicitly forwards every incoming HTTP client message to all DON members with **no allowlist check and no rate limiting**, and the per-node trigger handler then iterates every registered workflow against every entry of an attacker-controlled, effectively unbounded `topics` array. This mirrors the CL-2020-26 bug class ("Unlimited gossip RPC size" / hashmap-flooding CPU DoS caused by accepting unbounded, unrated attacker-controlled repeated fields): an unprivileged, unauthenticated HTTP caller can force O(registeredWorkflows × topics) map-lookup work on every capability-DON node per request, and can repeat this as fast as the gateway's generic connection limits allow.

### Finding Description
`handler.HandleLegacyUserMessage` in [1](#0-0)  only checks that the payload decodes, that the `Timestamp` is non-zero, and that the message isn't stale (`MaxAllowedMessageAgeSec`). Immediately before dispatching to the method-routing switch, the code contains an explicit unaddressed gap:

```go
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
``` [2](#0-1) 

After that check, the raw request is fanned out to **every member of the DON** unconditionally:
```go
for _, member := range h.donConfig.Members {
    err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
``` [3](#0-2) 

There is no per-sender, per-IP, or global rate limiter applied to this ingress path (the `nodeRateLimiter` in this handler only throttles node→gateway traffic, not user→gateway traffic), and no allowlist of senders/topics is enforced at the gateway.

On each DON node, `triggerConnectorHandler.HandleGatewayMessage` decodes the attacker-supplied JSON payload (`webapicap.TriggerRequestPayload`), whose `Topics []string` field is unbounded by schema (`event_trigger-schema.json` declares it merely as `"type":"array","items":{"type":"string"}"` with no `maxItems`) [4](#0-3) , and then `processTrigger` performs a nested loop over all registered workflows and all supplied topics:

```go
for _, trigger := range h.registeredWorkflows {
    for _, topic := range topics {
        if trigger.allowedTopics[topic] {
``` [5](#0-4) 

Because the request travels via `hc.ValidatedRequestFromMessage`/legacy JSON-RPC codec with only the gateway's generic body-size cap (default 1 MB, `defaultMsgSizeBytes` in `wsserver.go`) as an upper bound [6](#0-5) , an attacker can pack hundreds of thousands of short topic strings into a single request, well within that byte budget, and this cost is multiplied by the number of workflows registered on the node — with zero allowlist/rate-limit gate at the gateway to stop repeated submission.

### Impact Explanation
Every capability DON node processes attacker-supplied `Topics` against all of its `registeredWorkflows` on every incoming request, with the fan-out to all DON members done unconditionally by the gateway. Repeated large-topics submissions from an unauthenticated client can degrade CPU availability across the whole capability DON simultaneously (not just the gateway), impacting workflow trigger processing for legitimate users — a direct availability/DoS impact analogous to the Teku gossip RPC CPU/OOM disclosure.

### Likelihood Explanation
The `web_api_trigger` method and its `HandleLegacyUserMessage` path are reachable by any unauthenticated actor able to reach the gateway's HTTP/WS ingress (this is the intended, internet-facing entry point for triggering workflows via the Web API Trigger capability). The code contains an explicit acknowledged gap ("TODO: apply allowlist and rate-limiting here"), and the nested-loop cost model is unconditioned on the number of topics submitted, making exploitation straightforward with a single crafted JSON body — no privileged credentials or DON-node compromise required.

### Recommendation
- Enforce a maximum `Topics` array length (and reject duplicates) both in the JSON schema validation and defensively in `processTrigger` before iterating.
- Apply the allowlist and rate limiting called out by the TODO in `HandleLegacyUserMessage` (per-sender and/or global) before forwarding to DON members, rather than deferring all authorization/rate-limiting to the trigger-capability layer on each node.
- Consider bounding total work per request as `min(len(topics), N) × len(registeredWorkflows)` or restructuring the lookup to avoid the full cross-product (e.g., invert to `topic -> workflows` index) to reduce blast radius even if array size limits are bypassed.

### Proof of Concept
1. Craft a `webapicap.TriggerRequestPayload` with `trigger_id: "web-api-trigger@1.0.0"`, a valid recent `timestamp`, and `topics` populated with as many short unique strings as fit under the gateway's ~1 MB body limit (e.g., ~150k 6-byte strings).
2. Sign and send this as a `web_api_trigger` legacy request to the gateway HTTP endpoint, matching the flow demonstrated in `core/scripts/gateway/web_api_trigger/invoke_trigger.go` [7](#0-6) .
3. Because `HandleLegacyUserMessage` performs no allowlist/rate-limit check, the request is forwarded to all DON members; each node runs `processTrigger`'s nested loop over `len(registeredWorkflows) × len(topics)` map lookups.
4. Repeat the request continuously (no sender-level throttling exists at this layer) to sustain elevated CPU load across the capability DON.

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	body := msg.Body
	var payload webapicap.TriggerRequestPayload
	codec := api.JsonRPCCodec{}
	err := json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if payload.Timestamp == 0 {
		h.lggr.Errorw(ErrDecodingPayload)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload,
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
		h.lggr.Errorw("stale message")
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.HandlerError),
				"stale message",
				nil,
			),
			ErrorCode: api.HandlerError,
		})
	}
	// TODO: apply allowlist and rate-limiting here
	if msg.Body.Method != MethodWebAPITrigger {
		h.lggr.Errorw("unsupported method", "method", body.Method)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UnsupportedMethodError),
				"invalid method "+msg.Body.Method,
				nil,
			),
			ErrorCode: api.UnsupportedMethodError,
		})
	}
