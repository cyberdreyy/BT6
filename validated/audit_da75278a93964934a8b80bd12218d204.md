### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, letting a request execute below the effective live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
When a multisig member is removed via `MultiSigRequestAction::DeleteMember`, `delete_member` only purges *requests that member originally created*, but never scrubs that member's confirmation entries from *other* pending requests that member had merely confirmed. `confirm()` later counts `confirmations.len()` against `num_confirmations` without re-validating that every entry in the confirmation set still corresponds to a live member. This lets a request execute using a mix of live and stale (removed-member) confirmations, so the number of *live* approvals backing an executed request can be strictly less than `num_confirmations`.

### Finding Description
`confirm()` computes whether a request is ready to execute purely from the size of the `confirmations` `HashSet`: [1](#0-0) 

The invariant the contract is supposed to maintain is:
`len(confirmations(request)) == number of *current* members who approved` ⟺ `confirmations.len() >= num_confirmations` implies threshold live approvals.

`delete_member` breaks this invariant. It only removes requests that the *removed member itself created* (`r.member == member`), and only decrements that member's own `num_requests_pk` bookkeeping — it never walks other requests' `confirmations` sets to strip out the removed member's stale approval: [2](#0-1) 

So if member `B` confirmed request `X` (created by `A`) before being removed, `X.confirmations` still contains `B` after `B` is deleted. `confirm()` has no step that re-checks liveness of existing entries in the set — it only checks the *current* caller's membership via `assert_valid_request`/`current_member()`: [3](#0-2) [4](#0-3) 

Thus a request can reach `confirmations.len() + 1 >= num_confirmations` and execute even though one (or more) of the counted confirmations belongs to an account/key that is no longer a multisig member — i.e., the confirmations counted diverge from the confirmations of live members, breaking the threshold-vs-live-member-set binding: `confirmations_counted(request) == live_member_confirmations(request)` no longer holds.

The original `multisig/src/lib.rs` (v1) has the identical pattern: `DeleteKey` only removes requests whose *creator* (`signer_pk`) matches the deleted key, not confirmations the deleted key placed on other requests: [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a Critical-class impact: "a multisig request executed below threshold." Any legitimate membership change (e.g., offboarding a departed signer, rotating a compromised key) that leaves behind confirmations the departed member placed on still-pending requests silently lowers the effective quorum for those requests. The multisig can then authorize `Transfer`, `DeployContract`, `AddKey`/`AddMember`, or `FunctionCall` actions with fewer live approvals than `num_confirmations` mandates, undermining the entire custody guarantee the multisig is meant to provide.

### Likelihood Explanation
This does not require any malicious multisig member or attacker privilege beyond ordinary, expected multisig operation: creating a request, having it partially confirmed, and later removing one of the confirming members (a routine key-rotation/offboarding action) is sufficient to leave a stale confirmation in place. No collusion or intent to defraud is needed — the flaw triggers from normal, non-adversarial administrative use whenever a member removal happens while there are pending, partially-confirmed requests.

### Recommendation
When removing a member in `delete_member` (and analogously `DeleteKey` in `multisig/src/lib.rs`), iterate over **all** pending requests' `confirmations` sets (not just requests the member created) and remove that member's entry, or alternatively re-validate every confirming identity against the current `members` set at the moment `confirm()` decides whether the threshold has been reached, discarding stale entries before counting.

### Proof of Concept
1. Initialize `multisig2` with `num_confirmations = 3` and members `A, B, C, D`.
2. `A` calls `add_request_and_confirm(X)` → `confirmations(X) = {A}`.
3. `B` calls `confirm(X)` → `confirmations(X) = {A, B}` (2 < 3, not yet executed).
4. Via a separate, properly-confirmed governance request, the group removes `B` as a member (`DeleteMember`); `delete_member` asserts `members.len()-1 (=3) >= num_confirmations (3)` so removal succeeds; members are now `A, C, D`. `X`'s `confirmations` set is untouched because `X.member == A`, not `B`.
5. `C` calls `confirm(X)` → `confirmations(X).len() (2) + 1 = 3 >= num_confirmations (3)` → `X` executes immediately in `execute_request`, even though only `A` and `C` are live members who actually approved it — one confirmation (`B`'s) came from a removed member, so `X` executed with fewer live approvals than the configured 3-of-4 (now 3-of-3) threshold requires.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
