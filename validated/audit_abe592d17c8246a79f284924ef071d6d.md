### Title
Excess SUI Payment Not Returned in `purchase_with_cap` — (`File: crates/sui-framework/packages/sui-framework/sources/kiosk/kiosk.move`)

---

### Summary

`kiosk::purchase_with_cap` checks that the buyer's payment is **at least** `min_price`, but then deposits the **entire** coin into the kiosk's profits without returning the surplus to the buyer. Any SUI above `min_price` is permanently transferred to the kiosk owner.

---

### Finding Description

`purchase_with_cap` is the exclusive-listing purchase path. A `PurchaseCap<T>` is created by the kiosk owner with a `min_price`; any caller may then purchase the item by supplying a `Coin<SUI>` whose value is ≥ `min_price`.

The relevant code:

```move
// kiosk.move lines 426-437
let paid = payment.value();
assert!(paid >= min_price, EIncorrectAmount);   // ← only a lower-bound check
...
coin::put(&mut self.profits, payment);           // ← entire coin taken
...
(item, transfer_policy::new_request(id, paid, object::id(self)))
``` [1](#0-0) 

The function never splits the coin to extract exactly `min_price` and return the remainder. `coin::put` merges the whole `Coin<SUI>` object into `self.profits`.

Contrast this with the standard `purchase` path, which enforces an **exact** match:

```move
assert!(price == payment.value(), EIncorrectAmount);
``` [2](#0-1) 

The asymmetry is the root cause: `purchase_with_cap` intentionally allows overpayment (to support auction-style min-price semantics) but fails to refund the excess.

---

### Impact Explanation

A buyer who passes a `Coin<SUI>` larger than `min_price` permanently loses the surplus to the kiosk owner's profit balance. For example, if `min_price = 100 SUI` and the buyer supplies a 1 000 SUI coin, 900 SUI is silently captured. This is a direct, irreversible fund loss for an ordinary SUI holder triggered by a public framework function — matching the **harmful smart-contract behavior** class in the allowed impact gate.

---

### Likelihood Explanation

- `purchase_with_cap` is a public framework function callable by any address.
- Third-party contracts and wallets that integrate the Kiosk primitive may pass an unsplit coin (e.g., the gas coin or a merged coin) without first splitting off exactly `min_price`, especially when `min_price` is dynamic or unknown at build time.
- The `PurchaseCap` flow is explicitly designed for intermediary applications, increasing the surface area for integrators who do not manually split.

---

### Recommendation

Before depositing, split the coin to the exact required amount and return the remainder to the caller:

```move
public fun purchase_with_cap<T: key + store>(
    self: &mut Kiosk,
    purchase_cap: PurchaseCap<T>,
    mut payment: Coin<SUI>,
    ctx: &mut TxContext,
): (T, TransferRequest<T>) {
    let PurchaseCap { id, item_id, kiosk_id, min_price } = purchase_cap;
    id.delete();
    let id = item_id;
    let paid = payment.value();
    assert!(paid >= min_price, EIncorrectAmount);
    assert!(object::id(self) == kiosk_id, EWrongKiosk);

    // Return excess to the buyer
    if (paid > min_price) {
        let excess = payment.split(paid - min_price, ctx);
        transfer::public_transfer(excess, ctx.sender());
    };

    df::remove<Listing, u64>(&mut self.id, Listing { id, is_exclusive: true });
    coin::put(&mut self.profits, payment);   // now exactly min_price
    self.item_count = self.item_count - 1;
    df::remove_opt<Lock, bool>(&mut self.id, Lock { id });
    let item = dof::remove<Item, T>(&mut self.id, Item { id });
    (item, transfer_policy::new_request(id, min_price, object::id(self)))
}
```

Alternatively, enforce an exact-match check (`paid == min_price`) and require callers to split before calling, consistent with the non-cap `purchase` function.

---

### Proof of Concept

1. Kiosk owner places an item and calls `list_with_purchase_cap` with `min_price = 100`.
2. A `PurchaseCap<T>` is issued and handed to a buyer (or a third-party contract).
3. The buyer calls `purchase_with_cap` passing a `Coin<SUI>` with value `1_000`.
4. The assertion `1_000 >= 100` passes.
5. `coin::put(&mut self.profits, payment)` deposits all 1 000 SUI into the kiosk's profits.
6. The buyer receives the item and a `TransferRequest` recording `paid = 1_000`, but **900 SUI is permanently lost** to the kiosk owner.
7. The kiosk owner calls `withdraw` to extract the full 1 000 SUI profit. [3](#0-2)
