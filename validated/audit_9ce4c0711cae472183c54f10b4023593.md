## Title
Stale confirmations from a deleted key are not purged, allowing execution below live-member threshold - (multisig/src/lib.rs)

### Summary
`DeleteKey` only removes requests that the deleted key *originated* (matched by `signer_pk`) and clears `num_requests_pk` for that key, but it never scans `confirmations` for entries where the deleted key appears as a *confirmer* on requests created by other members. This lets a confirmation cast with a since-deleted key continue to count toward `num_confirmations`, allowing a request to execute with fewer live, authorized confirmations than the configured threshold.

### Finding Description
The binding that should hold is: **for every request that executes, `confirmations.len() >= num_confirmations` where every public key in `confirmations` still exists as a live access key on the account.** The contract breaks the second half of this binding.

In `execute_request`, the `DeleteKey` branch purges requests and the `num_requests_pk` counter, but only for requests whose `signer_pk` (the request's *creator*) equals the deleted key: [1](#0-0) 

It never inspects the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map for entries belonging to *other* requests where the deleted key acted only as a *confirmer* (not creator). The `confirm` function counts confirmation-set size directly against `num_confirmations` with no liveness check on the stored keys: [2](#0-1) 

Exploit flow:
1. Member A creates a request `R` (e.g., a `Transfer` to some receiver) — `add_request` stores `signer_pk = A`.
2. Member B confirms `R` once — `confirmations[R] = {B}`. Since `1 < num_confirmations` (e.g., 2), no execution happens yet.
3. Separately, the multisig approves a `DeleteKey { public_key: B }` request (e.g., because B is being offboarded/rotated) and it executes. The cleanup code at lines 202-214 only removes requests whose `signer_pk == B` (there are none, since B never created a request) and clears `num_requests_pk[B]`. `R`'s confirmation set `{B}` is left untouched even though B's key no longer exists on-chain.
4. Member C later confirms `R`. `confirmations[R]` becomes `{B, C}`, size 2, meeting `num_confirmations = 2`, and `execute_request` runs — even though only C is a currently live, authorized signer; B's "vote" is a ghost from a deleted key.

None of the existing guards catch this: `assert_valid_request` only checks the request/confirmation maps exist, not that confirming keys are still live; `assert_self_request` only checks receiver_id; there is no re-validation of confirmer keys' liveness at confirm-time or at delete-key-time.

### Impact Explanation
This lets a request move funds (`Transfer`, `FunctionCall` with deposit, `AddKey`/`DeleteKey` on the account itself, etc.) with fewer live signers than `num_confirmations` mandates, because a stale confirmation from a deleted key still counts. This directly matches the Critical category "a multisig request executed below `num_confirmations` live members," and can result in unauthorized transfer of NEAR held by the multisig account. It is repeatable any time a key with an outstanding confirmation on someone else's pending request is later deleted before that request finalizes.

### Likelihood Explanation
This requires the multisig to have a pending, under-threshold request with at least one confirmation, and later a `DeleteKey` action against the confirming key's public key while that pending request is still open. Key rotation/offboarding of a member is a normal multisig operation, so the precondition (deleting a key that has an outstanding confirmation elsewhere) is realistic, not contrived, and costs nothing extra beyond the normal request/confirm/execute flow already available to members.

### Recommendation
When executing `DeleteKey`, iterate over `self.confirmations` (not just `self.requests` filtered by `signer_pk`) and remove the deleted public key from every confirmation set; if this drops any request's confirmation count in a way that changes eligibility, no further action needed since counts are re-evaluated only in `confirm`. Alternatively, validate confirmer keys' liveness at `confirm`/execution time before counting them toward `num_confirmations`.

### Proof of Concept
```rust
#[test]
fn stale_confirmation_survives_delete_key() {
    let amount = 1_000;
    // Key A creates the contract and initializes with num_confirmations = 2
    testing_env!(context_with_key(key_a(), amount));
    let mut c = MultiSigContract::new(2);

    // Key A creates request R (transfer), signer_pk = A
    let r = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let request_id = c.add_request(r.clone());

    // Key B confirms once -> confirmations[R] = {B}, count 1 < 2
    testing_env!(context_with_key(key_b(), amount));
    c.confirm(request_id);
    assert_eq!(c.confirmations.get(&request_id).unwrap().len(), 1);

    // Multisig deletes key B via a separate self request (simulating offboarding)
    testing_env!(context_with_key(key_a(), amount));
    let delete_req = MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteKey { public_key: key_b_b58() }],
    };
    c.add_request_and_confirm(delete_req); // executes with just A (num_confirmations misconfig for demo, or use 2nd confirmer)

    // BINDING CHECK: R's confirmation set should no longer contain deleted key B
    let confs = c.confirmations.get(&request_id).unwrap();
    assert!(!confs.contains(&key_b()), "stale confirmation from deleted key B still present"); // FAILS on current code

    // Key C confirms -> count becomes 2 (B ghost + C), executes despite B being deleted
    testing_env!(context_with_key(key_c(), amount));
    c.confirm(request_id);
    assert_eq!(c.requests.get(&request_id), None, "request executed using a stale, deleted-key confirmation");
}
```
This test demonstrates the equality `confirmations[R] ⊆ {live keys}` is violated: `B ∈ confirmations[R]` after `B` is deleted, and the request subsequently executes counting `B`'s stale vote, i.e., with only one truly live confirming key against a `num_confirmations = 2` threshold.

        self.assert_valid_request(request_id);

        assert!(
            !confirmations.contains(&env::signer_account_pk()),

        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
