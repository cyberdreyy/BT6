### Title
BB tranche holders escape first-loss waterfall by queuing a withdraw before a loss is realized at `stopEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the Hubble report where a user strips collateral counting unrealized PnL and then lets the insurance fund absorb the liquidation cost, here a junior (BB) tranche holder who anticipates a realized loss can call `requestWithdraw` during the buffer period and convert their position into a "pending receipt". At `stopEpochWithDuration`, pending receipts do not retain tranche identity, so the pending share of the loss is socialized pro-rata across AA and BB receipts instead of hitting BB first.

### Finding Description
`requestWithdraw` burns the caller's tranche tokens and mints a strategy-token receipt via `IdleCreditVault.requestWithdraw`, removing the position from live NAV (`_withdrawOps`) before the next `stopEpoch` [1](#0-0) .

When the manager later calls `stopEpochWithDuration(..., _lossAmount)`, the loss is split between pending receipts and active positions by `previewLossAdjustedWithdrawFunds`:

```
uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
pendingToFund   = pendingBasis - pendingLoss;
activeLoss      = _lossAmount - pendingLoss;
``` [2](#0-1) 

The contract itself documents the broken invariant: "pending receipts share the pending portion of the loss pro rata because tranche identity is not stored" [3](#0-2) . `collectWithdrawFunds` then records a single `lossRecoveryPriceByEpoch[epochNumber]` paid identically to every receipt of that epoch via `_claimLossAdjustedWithdrawRequest` [4](#0-3) , while only the remaining `activeLoss` goes through the BB-first waterfall (`burnStrategyTokens` + `_forceUpdateAccounting`) [5](#0-4) .

Because the loss amount is a parameter supplied at stop time (not already in NAV), `_updateAccounting` inside `requestWithdraw` cannot catch it — there is no guard converting a BB-originated receipt back into first-loss capital.

### Impact Explanation
A BB holder with knowledge of an upcoming `_lossAmount` (losses are declared by the manager at stop, and a pending loss is often inferable from borrower distress) requests withdrawal in the buffer phase. Their would-be first-loss exposure is instead diluted pro-rata across all pending receipts — including AA receipts — and across the remaining active pool. Concretely, if the BB requester's receipt is the only pending receipt, a loss that should be borne 100% by their BB position is instead split `pendingBasis/totalBasis` to them and `activeBasis/totalBasis` to active LPs; the AA pending receipt holders absorb junior losses, and remaining BB holders' coverage of AA is unchanged in ratio but the escaping BB pays only the pro-rata share. This is a direct transfer of loss from the attacker to other LPs, violating the AA/BB loss-waterfall invariant.

### Likelihood Explanation
Requires only a normal tranche holder and a queued `requestWithdraw` in the epoch phase before `stopEpochWithDuration` realizes a loss — no privileged role. The gain is bounded by the difference between BB-first and pro-rata loss allocation, but on large pending positions the shifted loss can be substantial. Not stopped by `Default` checks since the loss does not yet exist in NAV at request time.

### Recommendation
Store the tranche identity (or an AA/BB split basis) for each pending receipt at `requestWithdraw` time, and in `previewLossAdjustedWithdrawFunds` apply the pending-side loss BB-first: exhaust BB-originated pending basis before haircutting AA receipts.

### Proof of Concept
Foundry fork PoC sketch (modeled on `testRedeemWithLossSocialized` in `test/foundry/IdleCreditVault.t.sol:5253`):

```solidity
// Setup: attacker deposits BB, victim deposits AA. Epoch running normally.
idleCDO.depositAA(amountAA);               // victim
vm.prank(attacker);
idleCDO.depositBB(amountBB);

// Buffer phase: attacker anticipates a stopEpoch loss
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(BBtranche)); // position -> pending receipt

// Manager stops epoch declaring a loss smaller than BB NAV
uint256 loss = amountBB / 2;               // would be fully absorbed by BB
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(newApr, 0, duration, loss);

// Expected (BB-first): attacker receipt loses `loss`, claim = amountBB - loss; AA untouched.
// Actual: lossRecoveryPrice = 1 - loss*pendingBasis/totalBasis/pendingBasis applied pro-rata;
// the attacker's receipt loses only loss * pendingBasis/(activeBasis+pendingBasis),
// and any AA pending receipt is haircutted by the same price.
uint256 claimed = IdleCreditVault(strategy).claimWithdrawRequest(attacker);
assertGt(claimed, amountBB - loss);        // attacker paid less than BB-first loss
```

The assertion `claimed > amountBB - loss` (with the shortfall borne by AA active LPs and any AA pending receipts) demonstrates the escaped first-loss obligation.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
