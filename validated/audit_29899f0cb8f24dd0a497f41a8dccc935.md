### Title
APR0 withdraw request permanently bricks `stopEpoch` once APR is raised — any lender can freeze the pool - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.requestWithdraw` lets any KYC-passed lender open an APR0 withdrawal bucket (`apr0TotalPrincipal`) whenever `unscaledApr == 0`. At `stopEpoch` time, `prepareStopEpochWithApr0` reverts with `NotAllowed` if `apr0TotalPrincipal != 0 && unscaledApr != 0`. Because `unscaledApr` is a plain manager-set parameter, an unprivileged attacker can sandbag the vault: open a dust APR0 request while APR is 0, then wait. The next routine honest-manager APR increase + `stopEpoch` permanently reverts, freezing all funds (deposits, pending receipts, and borrower repayments) with no recovery path in the epoch state machine.

### Finding Description
The analog of the LibTIFF invalid read is an unguarded state read that turns an attacker-crafted input into a hard revert inside a critical, non-bypassable path.

1. While `unscaledApr == 0` (APR0 mode), a lender calls `IdleCDOEpochVariant.requestWithdraw(_amount, tranche)` (IdleCDOEpochVariant.sol:739). This reaches `IdleCreditVault.requestWithdraw` → `_requestWithdrawApr0`, which does `_apr0User.principal += _amount; apr0TotalPrincipal += _amount` (IdleCreditVault.sol:567-577). No minimum amount, no limit — 1 wei suffices.
2. The honest manager later raises the APR via `setAprs` (or the equivalent orchestrator call), making `unscaledApr != 0`.
3. At epoch end, `stopEpoch` calls `prepareStopEpochWithApr0`, which hits:
   ```solidity
   uint256 _principal = apr0TotalPrincipal;
   if (_principal == 0) return ...;
   if (unscaledApr != 0) {
     revert NotAllowed();   // IdleCreditVault.sol:506-508
   }
   ```
   Every subsequent `stopEpoch` reverts the same way. There is no function to clear `apr0TotalPrincipal` or force-settle `apr0Users[_user]` without a successful stop, and `apr0TotalPrincipal` is only reset to 0 at the end of `prepareStopEpochWithApr0` (line 540) — which is unreachable once the revert condition holds.
4. The epoch state machine cannot advance: no `stopEpoch` → no `epochNumber` increment → `claimWithdrawRequest` reverts for all pending requesters via the `epochNumber <= lastWithdrawRequest` gate (IdleCreditVault.sol:326), deposits/withdraws remain blocked, and borrower repayments cannot be booked. The only exits are a code upgrade or setting APR back to 0 forever — i.e., permanent freezing of funds in any fixed-APR deployment that ever passes through an APR0 window.

### Impact Explanation
Permanent freezing of all pool funds: lender principal, accrued interest, funded withdraw receipts held in the vault, and `pendingWithdraws`/`defaultRecoveryReserve` accounting all become unreachable because the epoch can never stop while a dust APR0 bucket exists. The attacker's cost is one minimal `requestWithdraw` while APR is 0; there is no economic loss to the attacker.

### Likelihood Explanation
Trigger conditions are realistic: APR0 is a supported mode (`_requestWithdrawApr0`, `apr0RateByEpoch`, dedicated tests), the attacker only needs to be a KYC-passed wallet (`isWalletAllowed`) with any tranche balance or even a dust deposit, and the enabling action (manager raising APR after a 0-APR epoch) is an honest routine operation — the attacker does not need any privileged party to misbehave, only to act normally. The revert is unconditional once both states hold, so the freeze is deterministic, not probabilistic.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert when `unscaledApr != 0`. Instead settle the stale APR0 bucket at zero rate (skip the interest allocation, zero `apr0TotalPrincipal`, and let `_settleApr0` return principal via the settled bucket at claim time), or clear/migrate `apr0Users` entries explicitly. Alternatively, gate `_requestWithdrawApr0` so requests cannot be opened while APR is 0 unless the deployment is configured APR0-only, or allow a permissionless `settleApr0(user)` that finalizes the bucket without a full `stopEpoch`.

### Proof of Concept
Foundry fork sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_stopCurrentEpochWithApr`, `_startEpochAndCheckPrices`):

```solidity
function testApr0DustRequestFreezesStopEpoch() external {
    // Pool running with apr == 0 (APR0 mode already exercised by
    // testApr0WithdrawGetsInterestAtStopEpoch setup).
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // Attacker: KYC-passed lender, dust deposit + dust APR0 request.
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, 1);            // 1 wei underlying
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // apr0TotalPrincipal = 1
    assertEq(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 1);

    // Honest manager raises APR for the next epoch — routine operation.
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);

    // Epoch end: every stopEpoch now reverts NotAllowed inside
    // prepareStopEpochWithApr0 (apr0TotalPrincipal != 0 && unscaledApr != 0).
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Repeat: permanently bricked. epochNumber never increments, so all
    // pending withdraw claims revert via the epochNumber <= lastWithdrawRequest
    // gate; no lender can exit.
}
```

Caveat: this assumes `unscaledApr` can be set nonzero while `apr0TotalPrincipal > 0` (i.e., `setAprs` has no guard rejecting the change while APR0 buckets are open). If `setAprs` itself reverts on nonzero `apr0TotalPrincipal`, the freeze still materializes the next time APR transitions through 0→nonzero, since `stopEpoch` is unconditionally reached while the bucket is open.
