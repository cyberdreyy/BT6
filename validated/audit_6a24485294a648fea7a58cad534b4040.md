## Analog Found: Lock-Release-Before-Commit Race in `LimitClassCache` Invalidation

### Title
Generation counter incremented outside the cache write lock in `clear_limit_class_cache` allows a stale EIP-8130 account-lock classification to be re-cached after invalidation - ([File: crates/execution/txpool/src/validator.rs])

### Summary
The CVE describes `queued_write_lock_slowpath()` releasing/exposing the lock's true acquisition to a race because the `atomic_cmpxchg` that commits the write-lock state was not ordered with a concurrent reader's operations, letting the reader observe pre-acquisition state after the lock was nominally held. The analogous flaw in Base's txpool validator is a lock-then-release-then-commit split: `invalidate_limit_class_cache` correctly performs the cache mutation and the generation bump `fetch_add` **while still holding** the `limit_class_cache` write guard [1](#0-0) , but `clear_limit_class_cache` drops the write guard (a temporary) before bumping the generation counter:

```rust
pub fn clear_limit_class_cache(&self) {
    self.limit_class_cache.write().clear();
    self.limit_class_cache_generation.fetch_add(1, Ordering::Release);
}
``` [2](#0-1) 

### Finding Description
`account_lock` and `is_high_rate_account` use a classic check-then-commit pattern to avoid re-inserting a stale value after a concurrent invalidation: they snapshot `generation` before reading state, and only insert into `limit_class_cache` if `generation == self.limit_class_cache_generation()` while holding the cache write lock [3](#0-2) . This scheme is only race-free if every invalidation path advances the generation counter atomically with (or strictly before releasing) the cache mutation that it is supposed to guard.

`invalidate_limit_class_cache` respects this: the `cache` write guard captured by `let mut cache = self.limit_class_cache.write();` remains borrowed through the final `fetch_add(..., Ordering::Release)` call, since the guard variable is still in scope [1](#0-0) .

`clear_limit_class_cache` does not: `self.limit_class_cache.write().clear();` creates a temporary write guard that is dropped at the end of that statement — before the generation `fetch_add` executes. This opens a window between "cache cleared" and "generation advanced" in which a concurrent validator thread can:
1. Miss the (just-cleared) cache for `account_state(account)`.
2. Fall through to the `prefetched` or `sload` branch and read the **old** classification (or a classification read before the clear was even needed).
3. Re-acquire the cache write lock and check `generation == self.limit_class_cache_generation()` — which still succeeds because the generation has not yet been bumped.
4. Re-insert the stale `AccountState`/`trusted` classification into the freshly-cleared cache.

This is precisely the qrwlock bug pattern: the "unlock"/clear step is externally observable (cache miss) before the accompanying ordering token (generation) is committed, letting another thread's read-modify sequence interleave into that gap and reintroduce state the clear was meant to invalidate.

### Impact Explanation
`LimitClassCache` backs the EIP-8130 account lock/high-rate-payer classification that gates txpool admission policy: `sender_locked`/`payer_locked` control unlimited vs. signature-capped admission, and `payer_trusted` (`qualifies_as_high_rate_lock` + `is_high_rate_account`) controls whether a payer is admitted into the balance-bounded `PayerBook` fast path instead of the count-based limiter [4](#0-3) . `clear_limit_class_cache` is specifically invoked after a "state-diff feed gap" — i.e., exactly when the validator can no longer trust incremental invalidation and must treat the whole cache as untrustworthy [2](#0-1) . If a stale entry survives that clear due to the race, an account that has since become locked/unlocked, or a payer whose trusted/high-rate classification has changed, can be misclassified for an arbitrary period afterward (until the next slot/code invalidation touches that specific account). This can let a payer wrongly retain "trusted/high-rate" balance-bounded admission (bypassing the payer count limit) or let a locked account wrongly retain unlimited signature admission — a policy-bypass in the transaction admission control that an ordinary transaction sender/payer can trigger by timing transactions around a feed-gap-triggered cache clear.

### Likelihood Explanation
Requires two ordinary, attacker-influenceable conditions to coincide: (1) a `StateDiffInvalidation`/feed-gap event that calls `clear_limit_class_cache` (triggered by normal chain reorg/gap handling in `pool.rs`), and (2) concurrent `validate_one`/`account_lock` calls for the affected account racing in the tiny window between the cache `.clear()` temporary guard drop and the subsequent `fetch_add`. Since transaction validation runs on a task executor processing many pool submissions concurrently while invalidation runs from state-diff delivery, this is a realistic (though narrow, single-instruction-window) race under load — no special privileges are needed, only ordinary transaction submission timed around a chain-state update.

### Recommendation
Extend the write-lock scope in `clear_limit_class_cache` so the generation `fetch_add` happens under the same guard used to clear the cache (mirroring `invalidate_limit_class_cache`), e.g.:
```rust
pub fn clear_limit_class_cache(&self) {
    let mut cache = self.limit_class_cache.write();
    cache.clear();
    self.limit_class_cache_generation.fetch_add(1, Ordering::Release);
}
```

### Proof of Concept
1. Thread A (invalidation) calls `clear_limit_class_cache()`; it executes `self.limit_class_cache.write().clear()` and the guard is released.
2. Before Thread A's next line (`fetch_add`) runs, Thread B (validating a transaction for account `X`) calls `account_lock`, observes a cache miss (cleared), reads `X`'s state via the pre-invalidation `prefetched`/`sload` path, captures `generation = old_generation`.
3. Thread B locks `limit_class_cache.write()`, checks `generation == self.limit_class_cache_generation()` — still `old_generation` since Thread A has not yet incremented it — and inserts the stale classification for `X`.
4. Thread A's `fetch_add` now runs, advancing the generation, but the stale entry for `X` is already committed into the cache and will be served to future admissions until some other invalidation event specifically touches `X`'s slot/code again. [2](#0-1) [3](#0-2)

    pub fn invalidate_limit_class_cache(&self, diffs: &[crate::AccountStateDiff]) {
        let mut cache = self.limit_class_cache.write();
        // Advance the generation for every classification surface change, even
        // on a cache miss: a validation may have read the old state but not yet
        // inserted it. Its guarded insertion or later pool admission must see a
        // changed generation rather than retain that stale classification.
        let mut changed = false;
        for diff in diffs {
            if diff.code_changed {
                changed = true;
                cache.invalidate_code(diff.address);
            }
            if diff.address == AccountConfigurationStorage::ADDRESS {
                for slot in &diff.changed_slots {
                    changed = true;
                    cache.invalidate_slot(slot);
                }
            }
            // A balance change is not part of the cached classification, but it
            // seeds a trusted payer's `PayerBook` on first admission.
            // `on_balance_changed` only corrects payers that already have a book;
            // a trusted payer with no book yet would otherwise seed it from the
            // (now stale) validation snapshot. Advance the generation so an
            // admission whose validation predates this diff re-validates against
            // the fresh balance.
            //
            // Restricted to *known-trusted* payers: only they use the balance
            // book, and a trusted payer with a pending transaction was just
            // classified into the cache during that validation. Ordinary balance
            // churn — the vast majority, and unrelated to any book — must not
            // advance the generation and bounce unrelated admissions.
            if diff.balance.is_some() && cache.is_trusted_cached(diff.address) {
                changed = true;
            }
        }
        if changed {
            self.limit_class_cache_generation.fetch_add(1, Ordering::Release);
        }
    }

    fn account_lock(
        &self,
        state: &dyn StateProvider,
        local_chain_id: u64,
        now: u64,
        account: Address,
        generation: u64,
        prefetched: Option<AccountState>,
    ) -> LockStatus {
        // Invalidation may advance the generation immediately after this read.
        // Pool admission rejects the captured classification if that happens.
        let cached = self.limit_class_cache.write().account_state(account);
        let account_state = if let Some(value) = cached {
            ValidatorMetrics::classification_state_reads("cache").increment(1);
            value
        } else if let Some(value) = prefetched {
            // Authorization already read this slot for this snapshot; reuse the
            // recorded value and seed the cache (generation-gated exactly like a
            // fresh read) rather than issuing a second SLOAD.
            ValidatorMetrics::classification_state_reads("prefetch").increment(1);
            let mut cache = self.limit_class_cache.write();
            if generation == self.limit_class_cache_generation() {
                cache.insert_account_state(account, value);
            }
            value
        } else {
            ValidatorMetrics::classification_state_reads("sload").increment(1);
            let mut storage = StateProviderPrecompileStorage::new(state, local_chain_id, now);
            let value = match StorageCtx::enter(&mut storage, |ctx| {
                AccountConfigurationStorage::new(ctx).get_account_state(account)
            }) {
                Ok(value) => value,
                Err(error) => {
                    tracing::warn!(
                        error = %error,
                        account = %account,
                        "EIP-8130 account lock classification read failed"
                    );
                    // Fail closed: an unreadable account is treated as unlocked
                    // (the all-zero state word), so it never earns locked or
                    // high-rate admission privileges.
                    return AccountState::from_word(U256::ZERO).lock_status(now);
                }
            };
            let mut cache = self.limit_class_cache.write();
            if generation == self.limit_class_cache_generation() {
                cache.insert_account_state(account, value);
            }
            value
        };
        account_state.lock_status(now)
    }
