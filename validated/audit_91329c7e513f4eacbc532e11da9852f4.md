### Title
Gateway fan-outs unauthenticated/unauthorized-for-workflow trigger requests to all DON members before any allowlist check - (`core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`handler.HandleLegacyUserMessage` validates message shape, signature well-formedness, and timestamp freshness, but the `// TODO: apply allowlist and rate-limiting here` comment marks a genuine gap: there is no per-workflow `allowedSenders` check before the message is forwarded via `don.SendToNode` to every member in `h.donConfig.Members`. Any signer who can produce a well-formed, freshly-timestamped `MethodWebAPITrigger` message can force the gateway to broadcast to the entire DON, regardless of whether that sender is registered in any workflow's trigger allowlist.

### Finding Description
`HandleLegacyUserMessage` at `core/services/gateway/handlers/capabilities/handler.go:341-421` performs the following checks in order: JSON payload decode, `payload.Timestamp != 0`, staleness bound via `h.config.MaxAllowedMessageAgeSec`, and `msg.Body.Method == MethodWebAPITrigger`. Then it calls `common.ValidatedRequestFromMessage(msg)` (signature-format/well-formedness validation) and immediately loops: [1](#0-0) 

None of the preceding checks reference `payload.Workflow`-specific `allowedSenders` (that enforcement exists only downstream, in `core/capabilities/webapi/trigger/trigger.go`, which runs on each DON node, not in the gateway). Because the allowlist check is deferred entirely to node-side `trigger.go` logic, the gateway itself performs an unconditional fan-out to `h.donConfig.Members` for any syntactically valid, fresh, correctly-method-tagged message — this is exactly what the TODO comment flags as missing. An attacker who is not on any workflow's `allowedSenders` can still cause the gateway to dispatch the request to every DON node, consuming gateway and per-node processing/rate-limiter budget and network resources, and exposing routing behavior (workflow/topic disclosure via error responses from each node) before any per-workflow authorization occurs.

### Impact Explanation
This matches "unauthorized fan-out load" — a minor DoS/resource-amplification issue rather than unauthorized fund movement or full authentication bypass, since final workflow admission is still gated by the `allowedSenders` check in `core/capabilities/webapi/trigger/trigger.go` at each DON node. The gateway's failure to pre-filter, however, lets any holder of a validly-signed key (even one not permissioned for any workflow) force N-node fan-out per request, and lets them probe/trigger processing paths on nodes that don't belong to them, which corresponds to Chainlink's "allowlist bypass causing unauthorized/abusive network load" bounty impact class — bounded because actual workflow execution still requires passing the node-side allowlist.

### Likelihood Explanation
Preconditions are low: attacker only needs any valid signing key accepted by `common.ValidatedRequestFromMessage` (i.e., a well-formed signature, not necessarily one enrolled in a workflow's allowlist) and a fresh timestamp. No special role or admin credential is required, and the request is trivially repeatable at will, making this a low-effort, low-cost, freely repeatable amplification vector.

### Recommendation
Implement per-workflow allowlist and rate-limiting checks in `HandleLegacyUserMessage` before the `don.SendToNode` fan-out loop — reject/short-circuit with `api.UnauthorizedError` (or similar) when the sender is not present in the target workflow's `allowedSenders`, and apply a per-sender rate limiter (the handler already has `nodeRateLimiter` infrastructure for node-originated messages; add an equivalent for legacy user messages) prior to iterating `h.donConfig.Members`.

### Proof of Concept
Handler-level Go test plan (extends existing `core/services/gateway/handlers/capabilities/handler_test.go` patterns):
1. Construct a `handler` via `NewHandler` with a `donConfig.Members` list of N mock nodes and a mock `don` implementing `handlers.DON`.
2. Build a valid `webapicap.TriggerRequestPayload` with `Timestamp = time.Now().Unix()`, wrap in `api.Message` with `Method = MethodWebAPITrigger`, signed by a key that is deliberately NOT present in the target workflow's `allowedSenders` configuration.
3. Call `handler.HandleLegacyUserMessage(ctx, msg, callback)`.
4. Assert `don.SendToNode` (mocked) was invoked once per member in `donConfig.Members` (i.e., `len(donConfig.Members)` calls), confirming full fan-out occurred despite the sender not being allowlisted for any workflow — demonstrating the missing check at the line marked by the TODO comment.
