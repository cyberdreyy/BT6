### Title
Stale confirmations from removed access keys allow a multisig request to execute below the live-member threshold - ([File: multisig/src/lib.rs])

### Summary
`MultiSigContract::confirm()` counts confirmations recorded in the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map against `num_confirmations`, but when a public key is revoked via `MultiSigRequestAction::DeleteKey`, the contract only purges *requests originated by* that key — it never removes that key's confirmation from *other* pending requests it had merely confirmed. A stale confirmation from an already-deleted key therefore keeps counting toward the threshold, letting a request execute with fewer currently-authorized signers than `num_confirmations` requires.

### Finding Description
The intended invariant is: `confirmations.len() >= num_confirmations` should mean that at least `num_confirmations` *currently valid* multisig keys approved the request. The code breaks this equality.

`confirm()` simply checks the size of the stored confirmation set: [1](#0-0) 

When a key is deleted, the `DeleteKey` branch of `execute_request()` removes only requests where the deleted key was the *original signer* (`r.signer_pk == pk`), and clears `num_requests_pk` for that key — it never scans or prunes the key's entries inside `self.confirmations` for requests it had confirmed but did not originate: [2](#0-1) 

Since `confirmations` is keyed independently of `requests`/`num_requests_pk`, a confirmation added by a key before that key's removal is never invalidated: [3](#0-2) [4](#0-3) 

The only gate on `confirm()`/`add_request()` is that the call is a self-call (`predecessor_account_id == current_account_id`), verified in `assert_valid_request`: [5](#0-4) 
There is no check that every entry inside a request's stored `confirmations` set still corresponds to a public key that currently holds an access key on the account.

### Impact Explanation
This directly matches the "Critical" impact category: a multisig request executed below threshold. Suppose the multisig requires `num_confirmations = 3`. Key A confirms a `Transfer` request (1/3). Later, key A is revoked via a separate `DeleteKey` request (e.g., an employee leaving, a compromised key rotation). The transfer request's confirmation set still contains A's public key. Only two more of the remaining, currently-valid keys need to confirm for `confirmations.len() + 1 >= 3` to hold, and the transfer executes — even though only 2 of the currently authorized signers actually approved it. The recorded confirmation count diverges from the live set of authorized signers, breaking the custody binding `confirmations counted == live members who approved`, and results in unauthorized fund movement (`Transfer`), key additions (`AddKey`), or contract upgrades (`DeployContract`) approved by fewer live signers than configured.

### Likelihood Explanation
This requires no external attacker capability beyond normal multisig operation: any organization that revokes a compromised or departing signer's key while requests are pending will silently degrade its actual confirmation threshold for those pending requests. Given that key rotation/removal is an expected, routine multisig operation (the contract itself provides `DeleteKey` for this purpose), and the bug triggers automatically without any additional malicious step, the likelihood of encountering this state is high in normal operational use.

### Recommendation
When executing `DeleteKey`, iterate over all entries in `self.confirmations` (not just requests signed by the deleted key) and remove the deleted public key from every confirmation set; if removal drops a request's count in a way that changes its status, ensure it is left in a consistent, re-confirmable state. Alternatively, validate at `confirm()`/execution time that every public key present in a request's confirmation set still owns a valid access key on the contract account before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with keys A, B, C, D, E as access keys on the account.
2. Key A calls `add_request_and_confirm(Transfer{...})` → request R has confirmations `{A}`.
3. Via a separate, already-fully-confirmed request, execute `DeleteKey{public_key: A}` — this removes requests *originated* by A and clears `num_requests_pk[A]`, but does not touch `confirmations[R]`, which still contains `A`.
4. Key B calls `confirm(R)` → confirmations `{A, B}` (2/3, but only B is a live signer).
5. Key C calls `confirm(R)` → `confirmations.len() + 1 = 3 >= 3` → `execute_request` runs the `Transfer`, even though A's key was already revoked and only B and C are actual current signers (2 live confirmations, not 3). [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
