## Analysis

I found a plausible analog. `msg.Body.MessageId` in the gateway's legacy JSON-RPC path comes directly from the client-supplied JSON-RPC `id` field (`request.ID`), with no server-side uniqueness enforcement — it is only length- and null-byte-checked in `Message.Validate()`. [1](#0-0) [2](#0-1) 

This attacker-controlled ID is used as the sole key into the handler's `savedCallbacks` map, and a new request simply overwrites whatever was previously stored under that key with no check for an in-flight duplicate: [3](#0-2) 

### Title
Legacy Gateway Callback Map Overwritten by Attacker-Chosen Duplicate MessageId - (File: core/services/gateway/handlers/capabilities/handler.go)

### Finding Description
`HandleLegacyUserMessage` unconditionally writes into `h.savedCallbacks[msg.Body.MessageId]` without checking whether an entry for that key already exists [3](#0-2) . The `MessageId` is not a server-generated nonce; it is the JSON-RPC request `id` copied verbatim from the client's request during decoding [1](#0-0) , and `Validate()` only bounds its length/charset, never its uniqueness or unpredictability [2](#0-1) .

This mirrors the reported bug class: instead of a true per-request nonce, an externally influenced/guessable value is used as the map key, so a second call with a colliding key silently overwrites the first entry rather than being rejected or namespaced. When `handleWebAPITriggerMessage` later looks up and deletes the callback by `MessageId` on the node's response, only the most recently stored callback for that ID is honored [4](#0-3) , so the original caller's request/callback entry is orphaned/lost.

Note that this is the unprivileged, internet-facing legacy gateway path (`ProcessRequest` → `HandleLegacyUserMessage`), reachable without any prior authentication beyond message signature validation [5](#0-4) .

By contrast, the newer JSON-RPC v2 trigger handler explicitly guards against this class of bug by rejecting duplicate in-flight request IDs (`"in-flight request ID: %s has already been used"`), confirming the project is aware of and has fixed this exact pattern elsewhere [6](#0-5) , but the legacy `capabilities` handler was not updated with the same protection.

### Impact Explanation
An unprivileged client can send two legacy gateway requests (`web_api_target`/`compute_action`/`workflow_syncer`) using the same `MessageId` (their own JSON-RPC `id`) while a legitimate caller's request with that same/guessable ID is still in flight. The second `SendToNode` call's map write overwrites the first entry, so:
- The first caller's HTTP callback is dropped/never called back (the caller will only get the request-timeout path in `gateway.ProcessRequest`), causing loss of responses.
- Because whichever entry is stored last wins, and `handleWebAPITriggerMessage` matches purely on `MessageId` from the node's response, there is a risk of cross-request response confusion: a node response tagged with that `MessageId` could be delivered to the second (attacker's) callback rather than the legitimate first requester, depending on timing.

This is a moderate-severity availability/response-integrity issue in the gateway's node-message routing rather than a fund-movement or credential-disclosure bug, but it directly corresponds to the reported bug class of "map/store entries overwritten because the key used is not a true collision-resistant nonce."

### Likelihood Explanation
The `MessageId` is fully attacker-supplied (it's just the JSON-RPC `id`), requires no privilege beyond making an HTTP request to the public gateway endpoint, and there is no uniqueness/coalescing check before the map write [3](#0-2) . Triggering the overwrite requires only sending a second request with a colliding ID while the first is outstanding — a low-cost, easily reproducible race that only needs guessing/reusing an ID (or coordinating with a system that reuses well-known/short IDs).

### Recommendation
In `HandleLegacyUserMessage`, before storing the callback, check whether `h.savedCallbacks[msg.Body.MessageId]` already exists and reject the second request (mirroring the `in-flight request ID` conflict check already present in `http_trigger_handler.go`'s `setupCallback`) [6](#0-5) . Alternatively, derive an internal collision-resistant key (e.g., combine `MessageId` with sender/signature or a server-generated UUID) rather than trusting the client-controlled ID directly as the sole map key.

### Proof of Concept
1. Attacker A sends a legacy gateway JSON-RPC request with `id: "X"`, method `web_api_target`, valid signature — this reaches `HandleLegacyUserMessage`, which stores `savedCallbacks["X"] = callbackA` and forwards to DON nodes [7](#0-6) .
2. Before the DON responds, Attacker B sends another legacy request also with `id: "X"` (a value they can freely choose, since it's just the client-controlled JSON-RPC id). This overwrites `savedCallbacks["X"]` with `callbackB` [3](#0-2) .
3. When a DON node later responds with `MessageId: "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds only `callbackB`, deletes the entry, and sends the response there [4](#0-3) . Attacker A's original callback is never invoked and times out (`RequestTimeoutError` path in `gateway.ProcessRequest`) [8](#0-7) .

**Uncertainty**: I could not verify how frequently `MessageId` collisions would occur in production (e.g., whether legitimate clients typically choose random/high-entropy IDs, which would reduce accidental collisions but not intentional attacker-crafted collisions), nor did I find explicit test coverage proving this exact overwrite scenario for the legacy `capabilities` handler (unlike the v2 `http_trigger_handler_test.go`, which does test duplicate-ID rejection). A Devin session with full repo/test access could confirm this by writing a reproduction test against `handler_test.go` in `core/services/gateway/handlers/capabilities/`.
