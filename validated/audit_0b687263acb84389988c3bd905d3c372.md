### Title
Signer block-acceptance signatures omit chain-id binding, unlike block-rejection signatures - ([File: libsigner/src/v0/messages.rs])

### Summary
The Stacks signer protocol signs two very different kinds of messages over a block: `BlockAccepted` (an acceptance vote, and ultimately the signature embedded in the canonical Nakamoto block header) and `BlockRejection` (a rejection vote). `BlockRejection` explicitly binds its digest to `chain_id` via a SIP‑018 structured-data domain, but `BlockAccepted` — and the actual header-level signer signature verified by consensus — is computed and verified purely from `signer_signature_hash()`, with no `chain_id` or other domain separator in the signed digest at all. This is the same class of defect as the reported EIP‑2612 issue: a signature that omits a chain-binding value from its digest can be replayed across any context that shares the same message bytes but a different chain identity.

### Finding Description
`BlockRejection` explicitly folds `chain_id` into its signing digest through `make_structured_data_domain`: [1](#0-0) 

By contrast, `BlockAccepted` carries a `signature` field but has no `hash()`/`sign()`/`verify()` helpers at all that incorporate any domain or chain-id — the struct is a bare `(signer_signature_hash, signature, metadata, response_data)` tuple: [2](#0-1) 

The signer produces the accept signature by signing `block.header.signer_signature_hash()` directly, with nothing else mixed in: [3](#0-2) 

This same raw hash is what consensus itself verifies when tallying signer weight on a Nakamoto block header — `verify_signer_signatures` recovers the public key from `message = self.signer_signature_hash()` alone, with no chain-id check anywhere in the loop: [4](#0-3) 

So there are two parallel signing paths in the same protocol:
- Reject path: digest = SIP‑018(`"block-rejection"`, `"1.0.0"`, `chain_id`) over `signer_signature_hash` — chain-id bound.
- Accept path (both the gossip `BlockAccepted` message and the header-embedded `signer_signature` that consensus checks): digest = raw `signer_signature_hash` — **not** chain-id bound.

This asymmetry means the protocol authors clearly considered chain-id binding necessary (it was deliberately added to the reject path) but never applied the same protection to the accept/signing path that actually authorizes blocks into the canonical chain — exactly the "chainID not part of the signed schema" pattern from the report, applied to the artifact with the highest consequence (the signature that gets a block accepted).

### Impact Explanation
This meets the Critical bar of "a cross-context-valid signature": the exact same signer signature bytes that made block `B` canonical on one chain context are valid, unmodified, as a vote/acceptance for byte-identical block content presented in any other context that shares the same `chain_id` handling code path but a different chain identity (e.g., two networks/branches that arise from a contentious protocol fork, forked test networks reusing genesis/keys, or any deployment where the same signer key set and same block bytes could appear under a different logical chain). Because `verify_signer_signatures` — the consensus-level check that determines whether a block has enough signing weight to be accepted — never examines `chain_id`, an attacker who can get identical header bytes accepted/gossiped in a second context does not need any new signer cooperation: the previously-broadcast signature is directly reusable to satisfy the threshold there too.

### Likelihood Explanation
The likelihood is bounded by how difficult it is to get two contexts to share `signer_signature_hash()`-equal block header bytes; ordinarily `signer_signature_hash()` is derived from header fields that are network/context-specific (consensus hash, parent block id, etc.), so accidental collision is unlikely. However, the vulnerability is a **design gap**, not a hash-collision requirement: the fix path chosen for `BlockRejection` (explicit chain-id domain separation) demonstrates the maintainers recognized the need for this binding, yet it was omitted from the higher-stakes accept/signing path. Any future scenario reusing the same header-construction logic across two chain identities (deliberate hard fork, or a second network instance built from the same signer key material) inherits full signature replay with no additional attacker capability beyond gossip/relay, satisfying the "one-slot miner plus gossip" threat model in scope.

### Recommendation
Bind `chain_id` (or another persistent per-chain domain identifier) into the digest signed for `BlockAccepted` and into the header-level `signer_signature_hash()`/`verify_signer_signatures` check, mirroring the SIP‑018 domain approach already used for `BlockRejection`. At minimum, `verify_signer_signatures` in `stackslib/src/chainstate/nakamoto/mod.rs` should reject signatures whose digest was not computed over the current network's `chain_id`, and `BlockAccepted`/`create_block_acceptance` should adopt the same `make_structured_data_domain`-based construction as `BlockRejection`.

### Proof of Concept
1. Take a signer's `create_block_acceptance` signature for block `B` (signed over `B.header.signer_signature_hash()`, no chain-id) as shown at `stacks-signer/src/v0/signer.rs:473-497`.
2. Present the identical `B` (or any block whose `signer_signature_hash()` is byte-identical) in a second chain context (e.g., a post-fork branch, or a second deployment sharing signer keys) with a different `chain_id`.
3. `verify_signer_signatures` (`stackslib/src/chainstate/nakamoto/mod.rs:1097-1144`) recomputes only `message = self.signer_signature_hash()` and recovers the public key — it performs no `chain_id` comparison, so the reused signature counts toward the threshold in the second context exactly as it did in the first, whereas the analogous `BlockRejection::verify` path would have differed because its digest is chain-id-scoped (`libsigner/src/v0/messages.rs:1802-1825`).

pub struct BlockAccepted {
    /// The signer signature hash of the block that was accepted
    pub signer_signature_hash: Sha512Trunc256Sum,
    /// The signer's signature across the acceptance
    pub signature: MessageSignature,
    /// Signer message metadata
    pub metadata: SignerMessageMetadata,
    /// Extra versioned block response data
    pub response_data: BlockResponseData,
}

impl StacksMessageCodec for BlockAccepted {
    fn consensus_serialize<W: Write>(&self, fd: &mut W) -> Result<(), CodecError> {
        write_next(fd, &self.signer_signature_hash)?;
        write_next(fd, &self.signature)?;
        write_next(fd, &self.metadata)?;
        write_next(fd, &self.response_data)?;
        Ok(())
    }

    fn consensus_deserialize<R: Read>(fd: &mut R) -> Result<Self, CodecError> {
        let signer_signature_hash = read_next::<Sha512Trunc256Sum, _>(fd)?;
        let signature = read_next::<MessageSignature, _>(fd)?;
        let metadata = read_next::<SignerMessageMetadata, _>(fd)?;
        let response_data = read_next::<BlockResponseData, _>(fd)?;
        Ok(Self {
            signer_signature_hash,
            signature,
            metadata,
            response_data,
        })
    }
}
