### Title
`store_and_process_block_signature` broadcasts a signed block even when `mark_locally_accepted` fails, letting a rejected/conflicting block be pushed as if it reached the signing threshold - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`stacks-signer/src/v0/signer.rs::store_and_process_block_signature` mirrors the `_performCall`/`anyExecute` bug class: it calls a fallible state-transition function, only logs on `Err`, and — unlike every sibling handler in the same file — never returns on failure. Execution falls through into `insert_block` and `broadcast_signed_block` regardless of whether the local `BlockInfo` was actually moved into `LocallyAccepted`.

### Finding Description
`BlockInfo::mark_locally_accepted` (`stacks-signer/src/signerdb.rs:280-289`) unconditionally mutates `signed_group`/`valid`/`approved_time`/`signed_self` *before* calling `move_to`, and only `move_to`'s `check_state` result is returned as `Result<(), String>`: [1](#0-0) 

`check_state` (`signerdb.rs:314-329`) makes `LocallyAccepted` unreachable once a block is `GloballyRejected` or `GloballyAccepted` — these are documented as terminal ("Global states are terminal against each other", `docs/signer-flows.md:135`). So if a block was already driven to `GloballyRejected` (via the rejection-threshold path in `handle_block_response`/`store_and_process_block_rejection`, see `docs/signer-flows.md:349-375`), a later call to `mark_locally_accepted` **must** fail and must not be allowed to produce a broadcast.

But in `store_and_process_block_signature`: [2](#0-1) 

the `if let Err(e) = block_info.mark_locally_accepted(true) { ... warn ... }` block has **no `return`**. Every other handler in this same file that calls a `mark_*` function on the same struct (`handle_block_validate_ok`, `handle_block_validate_reject`, `check_submitted_block_proposal`, `handle_block_pre_commit`) explicitly `return`s to stop further action when the transition is disallowed and consensus hasn't been reached; this one does not. Consequently, after an `Err`, the code still calls `self.signer_db.insert_block(block_info)` and unconditionally `self.broadcast_signed_block(...)`, which per `docs/signer-flows.md:367,372` is what hands the block off to `handle_post_block`/the node for processing — the exact same "continue past a failure that should have aborted state" pattern as the Arbitrum report's missing `success` check.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" and "rejection vs acceptance" equality the state machine is supposed to enforce: a block that this signer's own DB already recorded as terminally `GloballyRejected` can still be re-broadcast as a signed/accepted block once accumulated signature weight in `get_block_signatures` crosses the 70% threshold, because that tally is computed purely from stored per-signer signatures (`stacks-signer/src/v0/signer.rs:2474-2513`) independent of the rejection tally. A single equivocating signer who first sends a `BlockRejection` (contributing to an otherwise-honest >30% rejection quorum that drives the block to `GloballyRejected`) and later replays/late-delivers a `BlockAccepted` signature for the same block can cause this signer to push the "rejected" block to its node as though it were validly signed — i.e., a rejection recounted as an acceptance and a signature broadcast for a block whose local state says it is not canonical. This matches the required Critical impact class in the rules ("a rejection recounted as an accept").

### Likelihood Explanation
The trigger requires only ordinary asynchronous message delivery plus one Byzantine/duplicating signer sending conflicting `BlockResponse` messages (Reject then, later, an Accept signature) for the same block over StackerDB gossip — no majority collusion is needed, matching the "one-slot miner (plus gossip)" scope. The missing `return` is a straightforward control-flow omission that any code reviewer diffing this function against its siblings (`handle_block_validate_ok`, `handle_block_pre_commit`) would immediately notice follow a different pattern.

### Recommendation
In `store_and_process_block_signature`, treat `mark_locally_accepted`'s `Err` the same way the sibling handlers do: if the transition fails and the block has not already reached consensus in the *accepting* direction, `return` immediately and do not call `insert_block`/`broadcast_signed_block`. Concretely:
```rust
if let Err(e) = block_info.mark_locally_accepted(true) {
    warn!("{self}: Failed to mark block as locally accepted: {e:?}");
    return;
}
```
(or restrict the fallthrough to only the case where `block_info.state` was already exactly `LocallyAccepted`/`GloballyAccepted` with equal validity, not `GloballyRejected`).

### Proof of Concept
1. Signer set genuinely rejects a malformed/conflicting block `B`; ≥30% weight of `BlockRejection` messages arrive and `store_and_process_block_rejection` calls `mark_globally_rejected()`, moving local `BlockInfo` for `B` to `GloballyRejected` (per `docs/signer-flows.md:349-375`).
2. A single malicious signer that had earlier signed `B` (or replays/delays its own acceptance) sends (or its stale `BlockAccepted` message finally arrives via StackerDB gossip) a signature for `B`.
3. `handle_block_signature` → `store_and_process_block_signature` runs; `get_block_signatures` tally including this delayed/duplicated signature crosses the 70% `min_weight` threshold.
4. `block_info.mark_locally_accepted(true)` is called on a `BlockInfo` already in `GloballyRejected` state; `check_state` returns `false` for that transition, so `move_to` returns `Err`, which is only logged.
5. Execution falls through (no `return`) to `self.signer_db.insert_block(block_info)` and `self.broadcast_signed_block(...)`, pushing block `B` — a block the signer's own state machine had terminally rejected — to the stacks node as though the signing threshold had been legitimately reached.

*(Note: I was not able to execute this scenario in a live test harness from the index alone; the control-flow gap itself — missing `return` after the `Err` branch, in contrast to every other `mark_*` caller in the same file — is directly verified from source and is the root cause being reported.)*

    /// Mark this block as valid and the appropriate timestamps if they aren't already set, and attempt to mark it as locally accepted.
    pub fn mark_locally_accepted(&mut self, group_signed: bool) -> Result<(), String> {
        if group_signed {
            self.signed_group.get_or_insert(get_epoch_time_secs());
        } else {
            self.valid = Some(true);
            self.approved_time.get_or_insert(get_epoch_time_secs());
            self.signed_self.get_or_insert(get_epoch_time_secs());
        }
        self.move_to(BlockState::LocallyAccepted)
    }

    /// Mark this block's signed group time if not already set and attempt to mark it as globally accepted.
    pub fn mark_globally_accepted(&mut self) -> Result<(), String> {
        self.signed_group.get_or_insert(get_epoch_time_secs());
        self.move_to(BlockState::GloballyAccepted)
    }

    /// Mark this block as invalid and attempt to mark it as locally rejected
    pub fn mark_locally_rejected(&mut self) -> Result<(), String> {
        self.valid = Some(false);
        self.move_to(BlockState::LocallyRejected)
    }
