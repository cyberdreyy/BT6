### Title
Unbounded memory allocation via `base_meterBundle`'s unbounded transaction list - ([File: crates/execution/metering/src/rpc.rs])

### Summary
`base_meterBundle` accepts a `Bundle { txs: Vec<Bytes> }` from any RPC caller and decodes/executes every entry with no count or size cap, unlike every other user-controlled collection in this codebase (SSZ payload transactions, EIP-8130 call phases, validity predicates, `eth_getProof` keys), which are explicitly length-bounded to prevent allocation amplification before rejection.

### Finding Description
`Bundle` is a bare wrapper around a `Vec<Bytes>` with no bound on element count or element size [1](#0-0) . The `base_meterBundle` RPC method takes this `Bundle` directly as a parameter [2](#0-1) , and the handler decodes it into a `ParsedBundle` — iterating over every raw transaction byte string, RLP/2718-decoding it, and recovering its signer — before any size/count check runs [3](#0-2) . The handler then fetches state and calls `meter_bundle`, which executes each decoded transaction in sequence and records per-transaction, per-opcode metering data [4](#0-3) .

This is structurally the same bug class as the CalDAV `expand` vulnerability: a single client-controlled request contains a nested collection whose size is fully attacker-controlled, and the server materializes it all in memory (decoded transactions, recovered signers, per-tx opcode/gas metering vectors) before enforcing any cap. Contrast this with the deliberate hardening applied elsewhere in the same repo for exactly this class of issue:
- SSZ execution-payload transactions are capped at `MAX_TRANSACTIONS_PER_PAYLOAD` before allocation [5](#0-4) , with a regression test specifically measuring allocation-amplification [6](#0-5) .
- `SendRawTransactionValidityOptions.validity` aborts deserialization mid-stream once it exceeds `DEFAULT_MAX_VALIDITY_PREDICATES`, explicitly to avoid allocating "tens of thousands" of items before a late check runs [7](#0-6) .
- `eth_getProof` storage keys are capped at `MAX_PROOF_KEYS` [8](#0-7) .
- EIP-8130 call phases are capped at `MAX_CALL_PHASES_PER_TX` for the same stated reason ("prevents ... amplifying into unbounded allocations") [9](#0-8) .

`base_meterBundle`'s `Bundle.txs` has no analogous cap anywhere in the searched code path.

### Impact Explanation
An RPC client able to reach `base_meterBundle` (exposed both directly as a `base_*` namespace method and internally invoked by the ingress RPC path for `sendRawTransaction` metering [10](#0-9) ) can submit a request containing a very large number of raw transaction byte blobs. Each is 2718-decoded, signer-recovered, and executed/metered, and results (including per-opcode `OpcodeGas` entries) are accumulated per-transaction. A large-enough submitted list drives unbounded heap growth in a single request, potentially exhausting node memory and causing the process to crash or be OOM-killed — the same "single malicious request → memory exhaustion / DoS" outcome as the CalDAV `expand` bug, but reached instead through an RPC bundle-metering call.

### Likelihood Explanation
Medium-to-High if `base_meterBundle` (or the ingress path that calls it on every `sendRawTransaction`) is reachable without heavyweight authentication, since the only gating visible is generic JSON-RPC body-size limits, whose configuration I could not verify from the code searched (this may be set at the node/HTTP-server level and could mitigate the issue; I was unable to confirm a `max_request_body_size` value scoped to this endpoint). Given the codebase's own explicit, repeated pattern of adding count/size caps specifically to defend against this exact CWE-770-style amplification elsewhere, the absence of such a cap here looks like an oversight rather than an accepted risk.

### Recommendation
Add an explicit bound on `Bundle.txs` (count and/or aggregate byte size), enforced during deserialization (mirroring the bounded-visitor pattern used for `SendRawTransactionValidityOptions`) or immediately at the top of the `meter_bundle` RPC handler before `ParsedBundle::try_from` runs, so oversized bundles are rejected before decode/signer-recovery/execution allocate memory proportional to attacker input.

### Proof of Concept
Send a JSON-RPC request to `base_meterBundle` with `txs` containing an extremely large array of valid-but-numerous (or maximally-sized) raw transaction byte strings. Because no cap exists on `Bundle.txs`, the node will decode, recover signers for, and attempt to execute/meter all of them in one request, consuming memory proportional to the submitted array size before any rejection can occur — analogous to the CalDAV report expanding 300 events with 1000-character descriptions into ~2 GB.

**Note on confidence**: I was unable to locate or verify a request-body-size limit specifically applied to the `base_meterBundle` endpoint or the broader ingress/metering RPC server configuration within the indexed code; if such a limit exists at the HTTP/JSON-RPC transport layer and is small enough, it would reduce (but likely not eliminate, depending on the configured size) the practical impact of this finding.

/// The maximum number of transactions in an execution payload, per
/// `MAX_TRANSACTIONS_PER_PAYLOAD` in the Ethereum consensus specs.
pub const MAX_TRANSACTIONS_PER_PAYLOAD: usize = 1 << 20;

/// The maximum number of withdrawals in a Base execution payload.
///
/// Base sets the withdrawals root directly and requires the SSZ `withdrawals`
/// list to be present but empty (see [`BaseExecutionPayloadV4`]), so any
/// non-empty list is invalid and is rejected during decode.
pub const MAX_WITHDRAWALS_PER_PAYLOAD: usize = 0;

/// SSZ `transactions` list bounded to [`MAX_TRANSACTIONS_PER_PAYLOAD`].
///
/// Transactions are variable-length SSZ items, so the decoder derives their
/// count from the list's leading offset. Bounding the count rejects a frame that
/// declares more transactions than the protocol allows *before* one entry per
/// declared element is allocated, closing the pre-authentication
/// allocation-amplification vector.
#[cfg(feature = "std")]
#[derive(Debug)]
pub struct BoundedTransactions(pub Vec<Bytes>);

#[cfg(feature = "std")]
impl ssz::Decode for BoundedTransactions {
    fn is_ssz_fixed_len() -> bool {
        false
    }

    fn from_ssz_bytes(bytes: &[u8]) -> Result<Self, ssz::DecodeError> {
        ssz::decode_list_of_variable_length_items(bytes, Some(MAX_TRANSACTIONS_PER_PAYLOAD))
            .map(Self)
    }
}
