### Title
Timing side-channel in `AuthenticateExternalInitiator` allows EI AccessKey enumeration - ([File: core/web/auth/auth.go], [File: core/bridges/external_initiator.go])

### Summary
`AuthenticateExternalInitiator` returns an identical `auth.ErrorAuthFailed` error for both an unknown AccessKey and a known AccessKey with a wrong Secret, so the *error shape* is not distinguishable. However, the two code paths perform materially different amounts of work: an unknown key short-circuits on the DB lookup returning `sql.ErrNoRows`, while a known key additionally computes `auth.HashedSecret` (a KDF/hash over the salt) before the constant-time compare. This asymmetry is a timing side-channel that can be used to enumerate valid AccessKeys.

### Finding Description
In `core/web/auth/auth.go`: [1](#0-0) 
- For an unknown AccessKey, `store.FindExternalInitiator` returns `sql.ErrNoRows`, and the function returns immediately with `auth.ErrorAuthFailed` — no hashing occurs.
- For a known AccessKey, `FindExternalInitiator` succeeds, and the code proceeds to call `bridges.AuthenticateExternalInitiator(eia, ei)`: [2](#0-1) 
which computes `auth.HashedSecret(eia, ea.Salt)` before doing the `subtle.ConstantTimeCompare`. This extra hashing step is only executed on the "known key" path.

Both branches ultimately produce the exact same error value/response shape (`auth.ErrorAuthFailed` → `401` via `jsonAPIError`), so there is no distinguishable error-type or body difference. But the additional cryptographic work (`auth.HashedSecret`) performed only when the AccessKey exists creates a measurable timing difference between "unknown key" and "known key, wrong secret" requests. An attacker who can send many external-initiator authenticated requests (unauthenticated, since this is the auth path itself) could statistically distinguish valid from invalid AccessKeys by response latency, enabling enumeration of provisioned External Initiator AccessKeys.

I was unable to fully inspect the internals of `auth.HashedSecret` in `core/auth/auth.go` in this session to quantify the exact computational cost of the KDF/hash it uses, so the magnitude of the timing gap (and thus real-world exploitability over network jitter) is not fully verified.

### Impact Explanation
If exploitable, this only discloses whether an AccessKey exists — it does not disclose the Secret itself (the compare is constant-time and the error is uniform), and does not by itself grant authentication or fund movement. This maps to a low-severity information-disclosure/enumeration issue rather than authentication bypass, since the Secret remains protected by a constant-time comparison and unguessable random value.

### Likelihood Explanation
Exploitation requires an unauthenticated attacker to send a large number of requests to an EI-authenticated endpoint (reachable via `AuthenticateExternalInitiator` middleware) and perform statistical timing analysis, which is noisy over real networks and requires knowledge of the hashing cost delta. No credentials are required, but the practical feasibility depends on network conditions and the actual cost of `auth.HashedSecret`, which was not confirmed in this session.

### Recommendation
Ensure constant-time behavior regardless of whether the AccessKey exists: when `FindExternalInitiator` returns `sql.ErrNoRows`, perform a dummy/no-op call to `auth.HashedSecret` with a fixed dummy salt (or otherwise pad execution time) before returning `auth.ErrorAuthFailed`, so the unknown-key and wrong-secret paths take statistically indistinguishable time.

### Proof of Concept
Go benchmark/table test in `core/web/auth/auth_test.go`:
1. Seed one known ExternalInitiator (AccessKey `K1`, Secret `S1`, random salt).
2. For N iterations, measure `AuthenticateExternalInitiator` latency for:
   - `(AccessKey=unknown, Secret=random)`
   - `(AccessKey=K1, Secret=wrong)`
   - `(AccessKey=K1, Secret=S1)`
3. Assert all three return equivalent error type/status (`auth.ErrorAuthFailed` / 401) for the first two.
4. Compare mean/median latency of case 1 vs case 2 across many trials; a statistically significant gap (correlated with `auth.HashedSecret` cost) demonstrates the side channel.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}
