### Title
Operator/beneficiary can opt out of direct coin transfers to permanently brick `staking_contract` distribution, freezing the staker's stake, commission and operator-switch paths - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when a recipient has (a) explicitly disabled `allow_arbitrary_coin_transfers` via `set_allow_direct_coin_transfers` and (b) is not already registered for `AptosCoin`. [1](#0-0) 
This is the Move analog of the `payable.transfer()` failure mode from the external report: a value-transfer call inside a shared, multi-party flow can be made to unconditionally revert by one of the parties, and because Move transactions are atomic, that single failing deposit reverts the *entire* surrounding transaction, not just the failing leg.

### Finding Description
`distribute_internal` in `staking_contract.move` iterates over every shareholder in the contract's `distribution_pool` (the staker and the operator/beneficiary) and calls `aptos_account::deposit_coins` for each one in an unconditional loop: [2](#0-1) 
If the operator (or their set beneficiary) has called `aptos_account::set_allow_direct_coin_transfers(operator_signer, false)` and never registers a `CoinStore<AptosCoin>`, then every call to `deposit_coins(operator/beneficiary, ...)` aborts.

Crucially, `distribute_internal` is not only invoked from the public `distribute` entry function — it is force-called as a mandatory first step inside the staker's own exit and management paths:
- `unlock_stake` (used to withdraw/unstake) calls `distribute_internal` unconditionally before doing anything else. [3](#0-2) 
- `unlock_rewards` calls `unlock_stake`, inheriting the same dependency. [4](#0-3) 
- `switch_operator` (the staker's designated escape hatch to move away from a bad operator "without going through the lengthy process to unstake") also force-calls `distribute_internal` before removing the old operator. [5](#0-4) 
- `update_commision` also force-calls `distribute_internal`. [6](#0-5) 

Since `beneficiary_for_operator`/`set_beneficiary_for_operator` let the operator freely pick any address as the payout recipient at any time, an operator can wait until they have unpaid commission pending, then set their own account (or a fresh address they control) to opt out of direct transfers and never register `CoinStore<AptosCoin>`, guaranteeing `deposit_coins` aborts for their share on every future `distribute_internal` call. [7](#0-6) 

Because every one of the staker's exit paths (`unlock_stake`, `unlock_rewards`, `switch_operator*`, `update_commision`, `distribute`) routes through `distribute_internal`, the operator — an unprivileged counterparty the staker merely delegated to, not a privileged/governance role — can unilaterally and permanently prevent the staker from ever unlocking, withdrawing, or switching away from them, as long as any nonzero distribution is pending to that recipient.

### Impact Explanation
This breaks the "Owner, operator, voter, beneficiary… boundaries must hold" and "Unlock, reactivate, withdraw… paths must not… strand it permanently" invariants explicitly called out for this scan. An operator (untrusted delegate, never granted staker/owner rights) can strand the staker's principal and rewards indefinitely by making their own commission payout un-depositable, since the staker cannot bypass `distribute_internal` through any exposed entry function in `staking_contract.move`. This is a high-severity denial-of-service / fund-freezing bug on mainnet-relevant delegated staking flows, though it does not by itself let the operator steal the staker's principal — it strands it.

### Likelihood Explanation
Likelihood is high: any operator can trivially call the public `aptos_account::set_allow_direct_coin_transfers(signer, false)` on themselves (or on any beneficiary account they control) and simply never call `coin::register<AptosCoin>`. No special privileges, timing, or race conditions are required, and the state can be set up in advance of accruing any commission.

### Recommendation
`distribute_internal` should not let a failure to pay one shareholder block payment to the others or block the staker's own unlock/withdraw/switch-operator paths. Options:
- Make per-recipient distribution failure-tolerant: wrap each `aptos_account::deposit_coins` call so that if it would abort (e.g., check `coin::is_account_registered` / `can_receive_direct_coin_transfers` beforehand), fall back to depositing into an escrow/claimable balance for that recipient instead of aborting the whole transaction.
- Decouple `unlock_stake`, `unlock_rewards`, `switch_operator*`, and `update_commision` from requiring `distribute_internal` to succeed — e.g., let commission accrue as pending shares that the operator can claim later via `distribute`/`request_commission`, without gating the staker's own unlock/withdraw/switch rights on that operator payout succeeding.

### Proof of Concept
1. Staker creates a staking contract with `operator` via `create_staking_contract`, with commission_percentage > 0.
2. Stake pool earns rewards over an epoch (`stake::end_epoch`).
3. `operator` calls `aptos_account::set_allow_direct_coin_transfers(operator, false)` and never registers `CoinStore<AptosCoin>` (or sets a fresh unregistered address as beneficiary via `set_beneficiary_for_operator`). [7](#0-6) 
4. Any subsequent call to `unlock_stake`, `unlock_rewards`, `switch_operator`, `switch_operator_with_same_commission`, `update_commision`, or `distribute` for this staker/operator pair triggers `distribute_internal`, which calls `aptos_account::deposit_coins(operator_or_beneficiary, coin::extract(...))` and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. [8](#0-7) [9](#0-8) 
5. The staker now has no available entry function in `staking_contract.move` to unlock, withdraw, or switch away from `operator`; the stake is permanently stuck under a hostile operator.

Note: I was not able to fully trace whether `vesting.move`'s `distribute`/`withdraw_stake` paths (which call `staking_contract::distribute`) share an identical unconditional dependency without any bypass — the vesting `distribute` at lines 719-756 has the same unbounded loop pattern with `aptos_account::deposit_coins`, so the same class of issue likely propagates to vesting contracts, but I did not verify every vesting entry point for a bypass in this session. [10](#0-9)

    /// Distribute any withdrawable stake from the stake pool.
    public entry fun distribute(contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        // Distribute coins to all shareholders in the vesting contract.
        let grant_pool = &vesting_contract.grant_pool;
        let shareholders = &grant_pool.shareholders();
        shareholders.for_each_ref(|shareholder| {
            let shareholder = *shareholder;
            let shares = pool_u64::shares(grant_pool, shareholder);
            let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
            let share_of_coins = coin::extract(&mut coins, amount);
            let recipient_address = get_beneficiary(vesting_contract, shareholder);
            aptos_account::deposit_coins(recipient_address, share_of_coins);
        });

        // Send any remaining "dust" (leftover due to rounding error) to the withdrawal address.
        if (coin::value(&coins) > 0) {
            aptos_account::deposit_coins(vesting_contract.withdrawal_address, coins);
        } else {
            coin::destroy_zero(coins);
        };

        emit(
            Distribute {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
                amount: total_distribution_amount,
            },
        );
    }
