### Title
Zip extraction path traversal via unsanitized `file.Name` allows writing/chmod outside job workspace - ([File: helpers/archives/zip_extract.go])

### Summary
`ExtractZipArchive` in `helpers/archives/zip_extract.go` uses `file.Name` from the zip archive directly as a filesystem path with no join-to-root or `..`/prefix validation, unlike the tar+zstd extractor which enforces a chroot check. The zip legacy extractor (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`) even accepts a `dir` parameter that it never uses when calling `archives.ExtractZipArchive`, so a crafted zip.File name with `..` segments can write/chmod files relative to the process CWD instead of the intended cache/artifact directory.

### Finding Description
`ExtractZipArchive` (helpers/archives/zip_extract.go:85-110) iterates `archive.File` and calls `extractZipFile(file)` and `lchmod(file.Name, file.Mode())` using `file.Name` verbatim. `extractZipFile` (lines 61-83) does `os.MkdirAll(filepath.Dir(file.Name), 0o777)` then dispatches to `extractZipFileEntry`/`extractZipSymlinkEntry`/`extractZipDirectoryEntry`, all of which call `os.OpenFile`/`os.Symlink`/`os.Mkdir` directly on `file.Name` with no `filepath.Abs`+`HasPrefix` containment check against a base directory [1](#0-0) .

By contrast, `tarzstd`'s extractor computes `path = filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects any path that doesn't have `e.dir` as prefix [2](#0-1) . The zip legacy extractor's `NewExtractor` accepts a `dir` field but `Extract` never uses it — it just calls `archives.ExtractZipArchive(zr)`, discarding the containment boundary entirely [3](#0-2) .

`lchmod` on Windows (helpers/archives/os_windows.go:9-13) is a thin wrapper over `os.Chmod(name, mode.Perm())` with no path containment of its own, so it will happily chmod whatever path was already written by `extractZipFile` [4](#0-3) .

Reachability: `CacheExtractorCommand.Execute` opens the cache archive, computes `wd` via `os.Getwd()`, calls `archive.NewExtractor(format, f, size, wd)`, and then `extractor.Extract(...)` [5](#0-4) . For the `zip` format this resolves through `archive.Register`/`NewExtractor` to the ziplegacy extractor, which drops `dir` and calls `ExtractZipArchive` unchecked [6](#0-5) . Because the extraction paths are relative (not absolute) and use `file.Name` untouched, `..\..\` sequences in the zip entry name resolve relative to the process's current working directory during extraction, allowing writes outside the intended cache/build root — including into another project's directory if the shared runner's working-directory layout or subsequent `Chdir` calls put sibling project paths within reach of the traversal.

The archive itself is attacker-controlled: a pipeline author can populate `cache:paths` or `artifacts:paths` contents (which get zipped) with symlinks/arbitrary names, or — more directly — supply the cache/artifact archive via a controlled upstream (e.g. custom cache/artifact store misconfigurations) whose zip entries contain the crafted names, since the archiver honors `zip.File.Name` however it was set on write. No existing check in `ExtractZipArchive`, `extractZipFile`, or `lchmod` validates or rejects `..` segments, absolute paths, or containment within `e.dir`/`wd`.

### Impact Explanation
On a shared multi-tenant runner host (Windows or otherwise, since `zip_extract.go` is platform-agnostic and only `lchmod` is OS-specific), a crafted zip cache/artifact can write and chmod files outside the current job's workspace. If the traversal depth and shared builds-root layout align, this can corrupt or tamper with files in a sibling project's build/cache directory, persisting after the job that produced it completes — a concrete cross-project integrity/availability impact matching the scoped impact of "medium persistent multi-tenant disruption."

### Likelihood Explanation
Requires a shared runner host serving multiple projects/jobs under a common builds root (stated precondition) and an attacker who can control the contents of a zip archive extracted by Runner (cache extraction or artifact download). Crafting a zip with traversal-laden `file.Name` entries is straightforward with standard zip-writing libraries; the missing containment check makes this fully reproducible via unit test.

### Recommendation
In `helpers/archives/zip_extract.go`, add a base-directory containment check mirroring `tarzstd_extractor.go`: resolve each `file.Name` against the target root with `filepath.Join`+`filepath.Abs`, verify the result has the root as prefix (or equals the root), and reject/skip entries that would escape. Ensure `ExtractZipArchive`/`extractZipFile` receive and honor an explicit `dir` parameter (as `ziplegacy.extractor.dir` already receives but discards) rather than operating on `file.Name` relative to CWD, and apply the same check before calling `lchmod`.

### Proof of Concept
```go
func TestExtractZipArchive_PathTraversalRejected(t *testing.T) {
    dir := t.TempDir()
    outsideDir := t.TempDir() // simulate sibling project directory

    buf := &bytes.Buffer{}
    zw := zip.NewWriter(buf)
    // crafted entry pointing outside dir, mimicking a sibling project's cache path
    rel, _ := filepath.Rel(dir, filepath.Join(outsideDir, "pwned"))
    f, _ := zw.Create(rel) // e.g. "..\\..\\otherproject\\cache\\pwned"
    _, _ = f.Write([]byte("owned"))
    zw.Close()

    zr, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))

    wd, _ := os.Getwd()
    _ = os.Chdir(dir)
    defer os.Chdir(wd)

    err := archives.ExtractZipArchive(zr)
    require.NoError(t, err) // current behavior: no error is returned

    // Assert the file was NOT created outside dir (this currently fails,
    // proving the vulnerability)
    _, statErr := os.Stat(filepath.Join(outsideDir, "pwned"))
    require.True(t, os.IsNotExist(statErr), "file must not be written outside extraction root")
}
```
Expected result on the current code: the assertion fails because `extractZipFile` writes `pwned` outside `outsideDir`'s intended root (relative to CWD), and the subsequent `lchmod` call chmods that same out-of-bounds path — demonstrating the missing containment check.

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}

// Extract extracts files from the reader to the directory passed to

	if err != nil {
		return err
	}
