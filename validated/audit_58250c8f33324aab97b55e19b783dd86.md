## Analysis: Untrusted `decimals` Field in SPL-Token Checked Instruction Parsing

### Title
Unprivileged transaction sender controls the `decimals` field used to compute `tokenAmount`/`feeAmount` in JSON-RPC parsed instruction output, causing misreported token amounts - (File: `transaction-status/src/parse_token.rs`)

### Summary
The bug class in the external report is that a value which should be constrained/canonical (the AMM pair fee) is instead attacker-settable and gets consumed downstream without cross-checking against the value the protocol actually expects, producing economically wrong results. The closest reachable analog in agave is in the SPL-Token "checked" instruction parsers used by the `jsonParsed` transaction/instruction decoding path: the `decimals` value is taken verbatim from attacker-controlled instruction data and used to compute the human-readable `tokenAmount`/`feeAmount` fields returned to RPC clients, with no cross-check against the real decimals recorded on the referenced mint account.

### Finding Description
`transaction-status/src/parse_token.rs::parse_token` handles `TokenInstruction::TransferChecked`, `ApproveChecked`, `MintToChecked`, and `BurnChecked`. In each case the `decimals` field is destructured straight out of the unpacked instruction (attacker-supplied, since any unprivileged user constructs the instruction bytes) and used to build a `SplTokenAdditionalDataV2`, which is then fed straight into `token_amount_to_ui_amount_v3`: [1](#0-0) 

The same pattern occurs for the `Token-2022` `TransferCheckedWithFee` extension instruction, where both `tokenAmount` and `feeAmount` are derived from the attacker-supplied `decimals`: [2](#0-1) 

`token_amount_to_ui_amount_v3` in `account-decoder/src/parse_token.rs` blindly trusts the passed-in `decimals` to compute `ui_amount` and `ui_amount_string`: [3](#0-2) 

Nowhere in this decoding path is the supplied `decimals` compared against the actual decimals recorded in the referenced mint account (the way `rpc/src/parsed_token_accounts.rs::get_mint_owner_and_additional_data` / `get_additional_mint_data` correctly derive decimals from the real mint state for account decoding): [4](#0-3) 

This parsing code runs unconditionally on any instruction whose opcode matches a `TokenInstruction` variant, regardless of whether the instruction ultimately succeeds or fails at runtime. Any unprivileged user can submit a transaction containing a `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked`/`TransferCheckedWithFee` instruction with a `decimals` value that does not match the real mint (e.g. `255` vs. the mint's actual `6`), get it included in a block (the instruction fails on-chain but the transaction and its `meta`/logs are still recorded and paid-for), and have `getTransaction`/`getConfirmedTransaction`/transaction subscriptions with `encoding: jsonParsed` report a `tokenAmount.uiAmount`/`uiAmountString` computed from the bogus decimals rather than the mint's true decimals.

### Impact Explanation
This is a decoder-misreporting bug reachable by any unprivileged user through a standard JSON-RPC read (`getTransaction`, `getConfirmedTransaction`, `blockSubscribe`/`transactionSubscribe`, etc. with `jsonParsed` encoding). It causes RPC consumers (wallets, explorers, indexers) to display/derive economically incorrect token amounts for a transaction that is fully attacker-crafted, without any privileged action involved — directly analogous to the external report's core issue of an economically significant value (fee/decimals) that is unprivileged-user-controlled and consumed without validation against the canonical value.

### Likelihood Explanation
High likelihood of triggering: it requires only constructing and submitting an ordinary token instruction with a deliberately wrong `decimals` byte — no special permissions, timing, or multiple RPC calls are needed. The instruction may fail at runtime (SPL-Token program enforces decimals matching for execution), but the transaction is still landed on-chain and its `jsonParsed` representation is still served with the misleading amount.

### Recommendation
When parsing `TransferChecked`/`ApproveChecked`/`MintToChecked`/`BurnChecked`/`TransferCheckedWithFee` (and any other "checked" SPL-Token/Token-2022 instructions) for `jsonParsed` output, resolve the referenced mint account's actual `decimals`/extension config (as already done in `rpc/src/parsed_token_accounts.rs::get_mint_owner_and_additional_data`) and use that canonical value for `token_amount_to_ui_amount_v3`, falling back to (or clearly flagging) the instruction-supplied `decimals` only when the mint cannot be resolved, rather than trusting the instruction bytes unconditionally.

### Proof of Concept
1. Craft a `TransferChecked` instruction (`spl_token_2022_interface::instruction::transfer_checked`) targeting a real mint with, e.g., 6 decimals, but set the `decimals` parameter to `0` and `amount` to `1_000_000`.
2. Submit the transaction. On execution the SPL-Token program will reject it (decimals mismatch), but the transaction is still included in a block with `meta.err` set.
3. Query the transaction via `getTransaction` with `encoding: "jsonParsed"`. The `transferChecked` `tokenAmount` field will show `uiAmount: 1000000, decimals: 0` (attacker-chosen) instead of `uiAmount: 1, decimals: 6` (the mint's real precision), i.e., the RPC decoder misreports the transferred amount by 6 orders of magnitude based purely on attacker-supplied data, as seen in the direct pass-through at [1](#0-0) .

```rust
pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
```

```rust
/// Analyze a mint Pubkey that may be the native_mint and get the mint-account owner (token
/// program_id) and decimals
pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}
```
