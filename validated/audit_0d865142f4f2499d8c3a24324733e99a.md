### Title
Signer weight double-counted across accept/reject on vote flip — miner-side tally breaks accept/reject mutual exclusivity - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` tallies `BlockStatus.total_weight_approved` and `total_weight_rejected` as two independently-incrementing counters keyed off two separate sets (`gathered_signatures` and `responded_signers`). A single signer who first rejects a block proposal and later accepts (signs) the same block has their weight added to `total_weight_rejected` on the first message and *also* added to `total_weight_approved` on the second, because the accept-path guard only checks `gathered_signatures` (not `responded_signers`) before crediting weight. This is the same "state replaces/accumulates without netting the other side" defect class as the reported `_approve` bug: one side of a mutually-exclusive tally is incremented without ever decrementing the other, so a signer's weight can be counted on both accept and reject simultaneously.

### Finding Description
In `handle_block_response`-equivalent code in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- On `BlockResponse::Accepted`: weight is added to `total_weight_approved` only if `!block.gathered_signatures.contains_key(&slot_id)`, then `gathered_signatures.insert(slot_id, signature)` and `responded_signers.insert(slot_id)` are unconditionally performed. [1](#0-0) 

- On `BlockResponse::Rejected`: weight is added to `total_weight_rejected` only `if block.responded_signers.insert(slot_id)` (i.e. first response ever from that slot). [2](#0-1) 

Walk through the sequence "reject, then accept" from the same signer slot:
1. `Rejected` arrives first → `responded_signers.insert(slot_id)` returns `true` (first time) → `total_weight_rejected += weight`.
2. `Accepted` arrives second → the accept-path only checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (this signer never signed before) → `total_weight_approved += weight`. It does **not** check or clear `responded_signers`, and it never subtracts the signer's weight from `total_weight_rejected`.

Result: after the flip, both `total_weight_approved` and `total_weight_rejected` include this signer's weight. The invariant that each signer's weight is counted on at most one side (`total_weight_approved + total_weight_rejected <= total_weight`) is broken.

By contrast, the signer-local persistence layer (`stacks-signer/src/signerdb.rs`) deliberately implements the correct, mutually-exclusive bookkeeping: `add_block_signature` clears any prior rejection record for that signer address, and `add_block_rejection_signer_addr` is a no-op once a signature already exists — exactly the netting behavior this report's external analogy (`permitIncrease`/`permitDecrease`) recommends, and it is enforced by unit tests: [3](#0-2) 
This confirms the project is aware of and intentionally prevents this exact bug class at the per-signer authoritative store, but the independent, coarser-grained tally in the miner-facing `StackerDBListener` (used only to decide when to stop waiting and either push or reject a block) does not carry the same guarantee.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality that `SignerCoordinator`/`StackerDBListener` relies on to decide whether >70% weight has approved or a blocking >30% minority has rejected a block: [4](#0-3) 
A signer that flips its vote (legitimate scenario documented and tested elsewhere in the codebase, e.g. `locally_rejected_blocks_overriden_by_global_acceptance`/`locally_accepted_blocks_overriden_by_global_rejection`) inflates the sum of the two counters beyond `total_weight`. Depending on which threshold is hit first, this can cause the coordinator to declare a spurious `SignersRejected` (denying/excluding transactions or stalling the tenure) using inflated rejection weight that double-books weight already also credited as an accept, or vice versa let a block appear approved. This is a liveness/tally-integrity defect reachable by a single signer's own votes (no majority or key compromise required), matching the "rejection recounted / aggregated weight vs verified accepts" impact class.

### Likelihood Explanation
Reachable by any single signer simply sending a `Rejected` `BlockResponse` followed later by an `Accepted` `BlockResponse` for the same `signer_signature_hash` over StackerDB — a message sequence the protocol otherwise permits and even anticipates (a signer that rejects for stale reasons can reconsider and sign later, per `should_reevaluate_reject_reason`/related v0 signer flows). No majority collusion, key theft, or auth-token access is required — only the attacking/erratic signer's own two legitimately-signed messages.

### Recommendation
In `stackerdb_listener.rs`, make `total_weight_approved` and `total_weight_rejected` mutually exclusive per slot, mirroring the netting already implemented in `signerdb.rs::add_block_signature`/`add_block_rejection_signer_addr`: before crediting weight to one counter, check whether the slot's weight was already credited to the other counter and, if so, subtract it first (or track a single `HashMap<slot_id, Vote>` and recompute the two weight sums from that canonical per-slot state on every update, rather than maintaining two independently-incrementing running totals).

### Proof of Concept
1. Configure `num_signers` signers, weight_threshold at 70%, blocking minority at >30%.
2. Have one signer slot `S` (weight `w`) send `BlockResponse::Rejected` for a proposed block `B` — `total_weight_rejected` becomes `w`.
3. Have slot `S` subsequently send `BlockResponse::Accepted` for the same block `B` (a legitimate "reconsider and sign" flow) — because `gathered_signatures` does not yet contain `S`, `total_weight_approved` also becomes (at least) `w`.
4. Now `total_weight_approved + total_weight_rejected` counts `S`'s weight twice, inflating both tallies used by `wait_for_block_signatures`'s threshold checks in `signer_coordinator.rs`, potentially triggering a premature `SignersRejected` (or an inflated approved-weight report) despite fewer distinct signers actually holding a live rejecting (or approving) opinion than the raw counters suggest.
