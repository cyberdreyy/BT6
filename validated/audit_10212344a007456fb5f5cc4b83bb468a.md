### Title
Loss-adjusted withdrawal haircut is keyed to the post-increment `epochNumber`, letting same-epoch receipts claim at par and drain funded recovery — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.collectWithdrawFunds` records a partial-funding haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is incremented inside `deposit()` when the CDO deposits repaid borrower funds during the same `stopEpoch` while `isEpochRunning()` is still true. Withdraw receipts are tagged with the pre-increment epoch (`lastWithdrawRequest[_user] = currentEpoch` in `requestWithdraw`). If the haircut price is stored under `epochNumber = N+1` while all affected receipts are indexed under epoch `N`, the epoch-keyed lookup in `_claimLossAdjustedWithdrawRequest` reads slot `N`, finds no haircut, and falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` in full from a strategy balance that only holds the haircutted amount. This is the closest analog of the CVE-2024-6101 out-of-bounds access: an index into epoch-scoped storage resolves to a slot outside the one where the haircut was written, so the bounds check silently misses and the wrong accounting branch executes.

### Finding Description
Relevant code, all in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` tags the receipt with the epoch at request time: `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 260, 282, 293).
- `deposit()` increments `epochNumber` whenever `IIdleCDOEpochVariant(idleCDO).isEpochRunning()` is still true, i.e. during the stop-epoch deposit leg: `epochNumber += 1` (lines 607–611).
- `collectWithdrawFunds` writes the haircut under the *current* `epochNumber` at call time: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (line 421).
- `_claimLossAdjustedWithdrawRequest` only applies the haircut when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` (lines 789–800); otherwise `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` at par via `_transferFundedClaim` (lines 338–349).

The invariant "one receipt, one haircutted payout" depends on the write key (`epochNumber` inside `collectWithdrawFunds`) matching the read key (`lastWithdrawRequest`). Because `deposit()` mutates `epochNumber` mid-`stopEpoch`, any stop-epoch flow that calls `collectWithdrawFunds` after the funding deposit stores the haircut under `epochNumber + 1`, while every receipt it is supposed to haircut is stored under the previous epoch. The same off-by-one applies to `apr0RateByEpoch` (written under `epochNumber` in `prepareStopEpochWithApr0`, line 537) and to `defaultPendingClaimBasis`/`instantWithdrawClaimsByEpoch[epochNumber]` (lines 644–648), which share the same index discipline.

Caveat: I could not confirm the exact ordering of `deposit()` vs `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpoch`/`_afterStopEpochWithDuration` within the available context. If `collectWithdrawFunds` executes before the incrementing deposit, the keys match and this specific vector closes; the PoC below is designed to determine that ordering empirically.

### Impact Explanation
If the key mismatch exists, every pending receipt of the loss epoch is paid at 100% instead of `lossRecoveryPrice`. The strategy only holds `pendingBasis * lossRecoveryPrice / 1e18` after `collectWithdrawFunds`, so the first claimers over-withdraw and the last claimers' transactions revert for insufficient balance — direct underpayment/insolvency for late claimers and theft of other users' haircut shares by early claimers, quantified as `pendingBasis * (1 - lossRecoveryPrice)`. If the ordering is correct, the residual risk is the mirror image: any future caller that bumps `epochNumber` before `collectWithdrawFunds` reopens it.

### Likelihood Explanation
The trigger requires a `stopEpochWithDuration`-style stop where the borrower under-funds `pendingWithdraws` (`_amount < pendingBasis`), which is an honest manager/borrower path, plus at least one pending withdraw receipt — all achievable by an unprivileged KYC'd lender who calls `requestWithdraw` during the epoch. Exploitability hinges entirely on the intra-`stopEpoch` ordering of `epochNumber += 1` relative to `collectWithdrawFunds`, which the PoC resolves.

### Recommendation
Snapshot the request epoch once per stop and use it consistently: either capture `uint256 requestEpoch = epochNumber` before the funding deposit and key `lossRecoveryPriceByEpoch[requestEpoch]`, `apr0RateByEpoch[requestEpoch]`, and `defaultRecoveryEpoch`, or move the `epochNumber += 1` increment out of `deposit()` into an explicit post-stop step that runs strictly after `collectWithdrawFunds`. Add an invariant test asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[u]] != 0` for every user whose receipt was haircut.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
// Foundry fork test against the repo's own fixtures (test/foundry/IdleCreditVault.t.sol)
function testLossEpochKeyMismatch() external {
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(userA, amount, true);

    // epoch N starts, userA requests a normal withdraw -> tagged epoch N
    _startEpochAndCheckPrices(0);
    vm.prank(userA);
    uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche));
    uint256 reqEpoch = strategy.epochNumber();

    // borrower under-funds so collectWithdrawFunds takes the loss branch
    uint256 funded = basis * 60 / 100; // 60% funded, 40% loss
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - (basis - funded));
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, lossAmount, 3 days, 0);

    // Key check: which epoch received the haircut vs which epoch the user is tagged with
    uint256 haircutAtReq   = strategy.lossRecoveryPriceByEpoch(reqEpoch);
    uint256 haircutAtReqP1 = strategy.lossRecoveryPriceByEpoch(reqEpoch + 1);
    // BUG condition: haircutAtReq == 0 && haircutAtReqP1 != 0

    // userA now claims: if the key mismatched, _claimFundedWithdrawRequest pays at par
    uint256 balPre = underlying.balanceOf(userA);
    vm.prank(userA);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(userA) - balPre;

    // Expect: paid == funded (60%); BUG: paid == basis (100%), funded by other receipts' share
    assertGt(paid, funded);
}
```
Run with `forge test --fork-url $RPC --mt testLossEpochKeyMismatch`. A second user claiming after `userA` demonstrates the insolvency leg (their claim reverts or pays less than their haircutted entitlement).
