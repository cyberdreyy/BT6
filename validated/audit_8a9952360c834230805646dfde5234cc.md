Based on the investigation, I found a genuine analog to the reported "transfer to unchecked/zero address" bug class in the builder-payment flow of the Gloas fork.

### Title
Builder payment `fee_recipient` is never validated against the proposer's committed preference in `process_execution_payload_bid` - (File: specs/gloas/beacon-chain.md)

### Summary
`process_execution_payload_bid` records a `BuilderPendingPayment` using `bid.fee_recipient` — an address chosen unilaterally by the builder inside the *signed* bid — without ever checking it against the value the proposer actually broadcast in `SignedProposerPreferences`. The only place such a check exists is a soft, non-authoritative `IGNORE` rule in the gossip validator, which does not gate state-transition validity and can be bypassed by any out-of-protocol bid delivery path that the spec explicitly allows.

### Finding Description
`process_execution_payload_bid` in [1](#0-0)  validates the builder's activity/funds, the bid signature, slot, parent hash/root, and randao — but at no point does it assert `bid.fee_recipient == <the proposer's declared fee_recipient for that slot>`. The value is taken straight from the builder-signed message and stored as the destination of the pending payment: [2](#0-1) 

The intended semantics are described in `gloas/builder.md`: "Set `bid.fee_recipient` to be an execution address to receive the payment. The proposer's preferred fee recipient is obtained from the `SignedProposerPreferences`..." [3](#0-2)  — i.e., the protocol's stated intent is that this payment is *committed to the proposer*, not to whatever address the builder decides to write into the bid.

The only enforcement of `bid.fee_recipient == proposer_preferences.fee_recipient` lives in the p2p gossip validator as an `IGNORE` (not `REJECT`) condition: [4](#0-3) 
`IGNORE` only prevents further relay of the message on that specific gossip topic — it has no bearing on block/state validity. Meanwhile, the validator specification for constructing a block explicitly permits bids obtained via non-gossip channels: "The block proposer MAY obtain these signed messages by other off-protocol means" [5](#0-4) , and the only correctness condition stated for inclusion is that the bid "MUST satisfy the verification conditions found in `process_execution_payload_bid`" [6](#0-5)  — which, as shown above, never checks `fee_recipient`.

Later, `apply_parent_execution_payload` settles this payment by moving it into `builder_pending_withdrawals` using the same unchecked `fee_recipient`, which ultimately determines the real, on-chain EL withdrawal destination during `process_withdrawals`: [7](#0-6) 

### Impact Explanation
This breaks the equality that the protocol design (and the p2p soft-check) presumes: "the destination the proposer authorized to receive payment" must equal "the destination that actually receives the Gwei." Since `process_execution_payload_bid` is the sole state-transition-level gate, a bid delivered to a proposer through any legitimate off-gossip channel (explicitly sanctioned by `validator.md`) with a `fee_recipient` that doesn't match what that proposer broadcast is still fully spec-valid and accepted by every conformant node. The net effect: a builder payment that was supposed to go to the block's proposer can be misdirected to a different address (including one under nobody's control, i.e., effectively burned) without any consensus-level rejection — matching the "builder payment ... misdirected, doubled or escaped" High-severity class, and structurally identical to the reported bug's "transfer `to` an unchecked/uncontrolled address."

### Likelihood Explanation
This does not require a coalition, a client bug, or a network partition to be *spec-valid* — it only requires that a block-inclusion path other than the primary gossip topic be used (explicitly permitted by the spec) and that the accepting node/proposer's own logic relies on `process_execution_payload_bid` as its sole correctness gate, matching the letter of `validator.md`'s "MUST satisfy" language. Because the actual redirection can only benefit the builder (who authors `fee_recipient`) at the proposer's expense, and does not require the proposer's active or malicious complicity, this is squarely a state-transition specification gap rather than an economic attack on the attacker's own stake.

### Recommendation
Add an explicit assertion in `process_execution_payload_bid` (or in whatever function commits `bid.fee_recipient` into `BuilderPendingPayment`/`BuilderPendingWithdrawal`) that `bid.fee_recipient` matches the `fee_recipient` from the most recently valid `SignedProposerPreferences` for `bid.slot`/`bid.builder_index`'s corresponding proposer, promoting the current gossip-layer `IGNORE` check to a consensus-level `REJECT`/`assert` so that mismatched bids cannot be included in a valid block regardless of delivery channel.

### Proof of Concept
1. Validator `P` is the proposer for slot `S` and broadcasts `SignedProposerPreferences` with `fee_recipient = A` for slot `S`.
2. Builder `B` (registered, active, sufficient balance) constructs a valid `ExecutionPayloadBid` for slot `S` with `fee_recipient = Z` (any address `B` prefers, e.g., `0x00...00` or an address `B` controls), signs it correctly, and satisfies all other fields checked by `process_execution_payload_bid` (`parent_block_hash`, `parent_block_root`, `prev_randao`, `slot`, blob commitment count, `can_builder_cover_bid`).
3. `B` delivers this signed bid to `P` off-gossip (e.g., via a relay/builder API, as explicitly permitted by `gloas/validator.md`), bypassing the gossip-only `IGNORE` filter in `p2p-interface.md`.
4. `P` includes the bid in the block for slot `S` and the block passes state transition, since `process_execution_payload_bid` never checks `fee_recipient` against `P`'s preferences.
5. When the payment settles (`apply_parent_execution_payload` → `settle_builder_payment` → `process_withdrawals`), the Gwei is withdrawn to `Z`, not `A`, even though every other network validator accepts the block as fully valid.

```python
def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
