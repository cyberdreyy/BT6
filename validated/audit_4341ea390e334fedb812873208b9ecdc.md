### Title
Multisig `delete_member` fails to purge stale confirmations, allowing a request to execute below the effective live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` removes a member from `members` and cleans up only the *requests they created* and their `num_requests_pk` entry, but it never scans `self.confirmations` to strip that member's confirmation from *other* pending requests they had confirmed. `confirm()` later counts confirmations purely by set size against `num_confirmations`, with no check that every confirming identity is still a current member. A stale confirmation from a removed member therefore still counts toward the threshold, letting a request execute with fewer *live* approvals than `num_confirmations` requires.

### Finding Description
The binding that must hold is:
`confirmations counted toward execution == confirmations from currently-live members`

`add_request` creates an empty confirmation set for a new request: [1](#0-0) 

`confirm` checks membership of the *caller* only, then blindly counts the existing `HashSet<String>` size plus one against `num_confirmations` to decide whether to execute: [2](#0-1) 

`delete_member` removes the member from the `members` set and deletes only requests *created by* that member, along with their `num_requests_pk` entry — it does not touch `self.confirmations` entries for other members' requests that this member had already confirmed: [3](#0-2) 

So once a member confirms request `R` (created by someone else) and is later removed via a legitimate `DeleteMember` action, `R`'s `confirmations` set still contains the removed member's identity string. Any subsequent live member's `confirm()` call on `R` counts that stale entry, potentially reaching `num_confirmations` with fewer than `num_confirmations` *currently valid* approvers — analogous to the reported bug where a validator predicate failed to account for a state transition (`WithdrawalDone` → `WithdrawalPossible`) and let stale state be counted again, corrupting the Oracle's accounting invariant.

### Impact Explanation
This breaks the core multisig safety guarantee ("a multisig request executed below threshold" — funds/actions authorized by fewer than `num_confirmations` live signers). Any `MultiSigRequestAction::Transfer`, `AddKey`, `FunctionCall`, etc. pending confirmation can be executed later with effectively fewer live approvals than configured, i.e. NEAR can be moved (or access keys added) by a set of members that never collectively reached the required threshold. This matches the "Critical" impact category: NEAR moved by a party not entitled to it / a multisig request executed below threshold.

### Likelihood Explanation
This requires only ordinary multisig operation, not a malicious member: a pending request accumulates a partial confirmation, then a later, legitimate `DeleteMember` action removes that confirmer (e.g., an employee leaving), and a different current member later confirms the still-pending old request. No collusion or privileged misuse beyond normal multisig lifecycle is needed — just an ordering of routine events (partial confirm → member removal → later confirm), making this readily reachable in practice.

### Recommendation
When `delete_member` (and `add_member`, if it changes effective quorum semantics) executes, iterate over all `requests`/`confirmations` and strip the removed member's identity from every confirmation set (not just requests they authored), or re-validate at `confirm()`/execution time that every entry in the confirmations set still corresponds to a current member (filtering with `self.members.contains(...)`) before comparing the count to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. `A` calls `add_request` to create request `R` = `Transfer { amount: X }` to an attacker/controlled account. `confirmations[R] = {}`.
3. `B` calls `confirm(R)`. `confirmations.len() = 0`, `0 + 1 < 2`, so no execution; `confirmations[R] = {B}`.
4. Separately, a legitimate multisig request `D = DeleteMember{ member: B }` is created and confirmed by `A` and `C` (2/3, meets threshold), executing `delete_member(B)`. `members` becomes `[A, C]`; `B`'s own created requests are cleaned up, but `confirmations[R] = {B}` is left untouched since `R` was created by `A`, not `B`.
5. Later, `C` calls `confirm(R)`. `current_member()` succeeds for `C`. `confirmations[R].len() = 1` (stale `B`), `1 + 1 = 2 >= num_confirmations(2)` → `execute_request(R)` fires, transferring `X` NEAR.
6. Result: `R` executed with confirmations from `B` (no longer a member) and `C` — only one truly live member (`C`) approved, despite `num_confirmations = 2` requiring two live approvals. Funds moved under an authorization set that never reached the configured live threshold.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
