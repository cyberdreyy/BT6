### Title
Unprivileged vault user can DoS `stopEpoch` by draining the programmable borrower's ERC4626 liquidity — withdrawals frozen indefinitely - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower.onStopEpoch` hardcodes a zero-tolerance assumption that `vault.withdraw(shortfall)` will succeed whenever the vault share position nominally covers the shortfall. Because the configured ERC4626 vault is a public pool, any unprivileged vault user can keep its asset liquidity drained, causing the withdraw to revert and making `IdleCDOEpochVariant.stopEpoch` uncallable — a repeatable mempool griefing attack that freezes all lender withdrawal requests.

### Finding Description
At `contracts/strategies/idle/ProgrammableBorrower.sol:240-253`, when IdleCDO calls `onStopEpoch` to pull `_amountRequired`, the contract computes `shortfall = _amountRequired - onHand` and: [1](#0-0) 

- If `shortfall > _currentVaultAssets()` it returns `true` and lets the later `transferFrom` fail into the default path.
- Otherwise it calls `vault.withdraw(shortfall, ...)` inside a `try/catch` that reverts with `StopEpochVaultLiquidityUnavailable`.

`_currentVaultAssets()` is `vault.convertToAssets(shares)` — a *valuation* of the position, not a liquidity guarantee. For a public ERC4626 vault (e.g., a Morpho/idle-liquidity vault where shares are worth enough but the pool's cash is borrowed or withdrawn), `convertToAssets` still reports full value while `withdraw` reverts on insufficient liquidity.

This is the direct analog of the reported bug: instead of a hardcoded 1% slippage tolerance, the tolerance here is effectively zero — any liquidity shortfall makes the honest keeper/manager `stopEpoch` transaction revert, and an attacker watching the mempool can ensure the vault stays drained. The guard that exists (`shortfall > _currentVaultAssets()`) checks only share value, so it does not stop the revert; the `try/catch` converts an external liquidity failure into a hard revert of the entire epoch state machine.

### Impact Explanation
While an epoch is running, lenders cannot withdraw directly — they hold `withdrawsRequestsByEpoch` receipts redeemable only after `stopEpoch` settles and funds are moved to `IdleCreditVault`. If `stopEpoch` cannot execute:

- Pending withdrawal requests are frozen indefinitely (temporary freezing of funds, not just a UX DoS — lenders' principal plus accrued interest is locked behind the epoch stop).
- `startEpoch` for the next epoch cannot run either, so all accounting halts: no deposits, no new requests, no claims.
- During a falling market or borrower distress this is exactly the harm the original report describes: users needing to exit are blocked while the attacker pays only gas to keep the vault drained (borrowing or withdrawing available liquidity whenever it refills).

Loss is quantified as the full value of pending withdraw requests for the duration of the freeze, plus forgone ability to react to credit events.

### Likelihood Explanation
- Attacker needs only to be an ordinary user of the public ERC4626 vault (borrow against it or withdraw liquidity) — no privileged role.
- The attack is repeatable per block: watch mempool for `stopEpoch`, front-run with a borrow/withdraw that removes vault liquidity, and re-drain whenever liquidity returns.
- Feasibility depends on the configured vault being a shared public pool; for a dedicated vault with enough idle liquidity the revert path is unreachable, so likelihood is medium rather than high.

### Recommendation
- Do not let an external vault liquidity failure revert the whole stop flow. Instead, pull what is available (partial `withdraw`/`redeem`), account the uncovered remainder as the epoch shortfall, and route it through the existing default/loss path, or queue it as vault-share-denominated debt to be claimed via `emergencyExitVault` later.
- Alternatively, reserve liquidity ahead of `epochEndDate` (pre-withdraw the expected `epochPendingWithdraws` during the epoch) so the stop transaction never depends on live vault liquidity.
- Add a manager escape hatch that skips the vault withdraw and proceeds with on-hand funds only, so griefing cannot permanently block the epoch machine.

```solidity
// Setup: IdleCDOEpochVariant + ProgrammableBorrower wired to a public ERC4626 vault
// (e.g. a Morpho vault holding USDC). Lender has a pending withdraw request; epoch is running.

function testStopEpochGriefedByVaultDrain() external {
    // 1. Epoch running; lender requested withdrawal -> epochPendingWithdraws > 0
    // 2. Attacker (any EOA) keeps vault liquidity drained:
    //    - either vault.borrow(supplierCash) on the underlying market, or
    //    - vault.withdraw(available) as a large shareholder,
    //    such that vault.deposit/withdraw reverts on insufficient cash while
    //    convertToAssets(programmableBorrowerShares) still covers `shortfall`.

    // 3. Manager/keeper calls stopEpoch at epochEndDate
    vm.warp(cdo.epochEndDate());
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdo.stopEpoch();

    // 4. Repeat each block: attacker re-drains any newly available liquidity.
    //    Lender's claimWithdrawRequest remains uncallable -> funds frozen.
}
```

Pre-conditions: `isInterestMinted` mode (required for programmable borrower), `_pendingInstant() == 0`, epoch active so `shortfall <= _currentVaultAssets()` but vault cash < `shortfall`. The revert propagates out of `onStopEpoch`, reverting `stopEpoch` — no state changes, so the attack is infinitely repeatable at gas-only cost to the attacker.
