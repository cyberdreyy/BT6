### Title
Attacker-induced ERC4626 `deposit` revert is misclassified as borrower default, freezing all LP funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.onStartEpoch` calls the external ERC4626 `vault.deposit` with no `try/catch` and no validation of the returned shares (`_depositToVault`, ProgrammableBorrower.sol:378-385). `IdleCDOEpochVariant.startEpoch` wraps the borrower funding path in a catch-all `try this.sendFundsToBorrower(...) { ... _startEpochProgrammableBorrower(...) } catch { ... _handleBorrowerDefault(...) }` (IdleCDOEpochVariant.sol:295-303). Any revert from the third-party vault's `deposit` — which any unprivileged vault depositor can force by filling the vault's deposit cap or otherwise making deposits revert — is therefore swallowed and re-interpreted as "the borrower did not receive the funds," triggering the hard default path (`defaulted = true`, pause, epoch stopped, withdraw requests disabled). A null-pointer-deref-style crash in a component the caller wrongly trusts is mapped here to an unguarded external hook whose failure is wrongly escalated into a credit event.

### Finding Description
The epoch state machine assumes `onStartEpoch`'s vault deposit is as reliable as a plain ERC20 transfer, but it is not:

- `_depositToVault` executes `vault.deposit(_assetAmount, address(this))` with no revert isolation and no check that minted `shares` are non-zero or correctly valued (ProgrammableBorrower.sol:378-385). Standard ERC4626 vaults revert when `maxDeposit` is exceeded (deposit caps, paused vaults, utilization limits).
- In `IdleCDOEpochVariant.startEpoch`, the programmable-borrower notification `_startEpochProgrammableBorrower` executes **inside** the `try` block whose `catch` unconditionally calls `_handleBorrowerDefault(_toBorrower)` (IdleCDOEpochVariant.sol:295-303). The catch cannot distinguish "transfer to borrower failed" from "the ERC4626 vault rejected the deposit."
- `_handleBorrowerDefault` sets `defaulted = true`, calls `IProgrammableBorrower.onDefault()`, pauses the CDO, stops the epoch, and disables `allowAAWithdrawRequest`/`allowBBWithdrawRequest` (IdleCDOEpochVariant.sol:577-599). The borrower never actually failed to pay: its funds were simply parked into a vault that was temporarily (or permanently, if the attacker keeps it saturated) rejecting deposits.
- The alternate start path at IdleCDOEpochVariant.sol:286-289 calls `_startEpochProgrammableBorrower` with no `try` at all, so the same revert bricks `startEpoch` outright, leaving deposited underlyings parked in the strategy and no epoch ever running.

No existing guard prevents this: `sendFundsToBorrower` succeeded (borrower got the cash is irrelevant — the failure is in the vault deposit), `isProgrammableBorrower` mode has no `try` around the internal hook, and `onStopEpoch` carefully try/catches `vault.withdraw` (ProgrammableBorrower.sol:246-253) while `onStartEpoch` does not do the same for `vault.deposit` — an asymmetric trust assumption on the same external contract.

### Impact Explanation
An unprivileged user of the same ERC4626 vault (an explicitly in-scope attacker class) can keep the vault's deposit capacity saturated so `vault.deposit` always reverts. Consequences:

- Every `startEpoch` call that reaches the programmable hook converts a benign vault rejection into a protocol-wide borrower default: the CDO is paused, the epoch is stopped, and all withdrawal requests are disabled (IdleCDOEpochVariant.sol:587-598). All active LP funds are frozen until governance runs `finalizeDefault`, which prices a *fake* default and can haircut receipts through `defaultRecoveryPrice`/`defaultPendingClaimBasis` — permanent loss of unclaimed yield and principal value, not merely a transient revert.
- In the unguarded path (IdleCDOEpochVariant.sol:286-289), `startEpoch` reverts forever while funds sit undeployed: deposits and pending withdraw receipts are frozen for the duration the attacker maintains saturation — a quantified, attacker-controlled freezing of the entire pool's NAV.
- Recovery requires privileged intervention (`finalizeDefault` / `restoreOperations` / `rescueTokens`), so the freeze duration is bounded by operator response, satisfying "temporary freezing" — and if `finalizeDefault` runs, the misclassified default crystallizes into real haircut losses.

### Likelihood Explanation
Requires (a) a programmable-borrower deployment (factory-supported), and (b) an ERC4626 vault whose `deposit` can be made to revert by a third party — deposit caps and pausable vaults are standard (Morpho/MetaMorpho-style caps, per-asset supply limits). The attack costs only the capital to fill the cap and can be repeated each time it drains, so the griefing is sustainable. No privileged role misbehavior is needed; owner/manager calls happen exactly as designed and still produce the wrong outcome.

### Recommendation
Mirror the `onStopEpoch` pattern: wrap `vault.deposit` in `try/catch` inside `_depositToVault` (or inside `onStartEpoch`) and return a status instead of reverting, so IdleCDO can distinguish "borrower transfer failed" (real default) from "vault liquidity/capacity failure" (retryable, keep the epoch in buffer). Additionally, in `IdleCDOEpochVariant.startEpoch`, move `_startEpochProgrammableBorrower` out of the `sendFundsToBorrower` try/catch or give it its own guarded block that reverts rather than defaulting, and validate that `vault.deposit` returned non-zero shares for non-zero assets.
