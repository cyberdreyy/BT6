### Title
A dust APR0 withdrawal request permanently blocks `stopEpoch` once APR is raised — epoch freeze / griefing DoS - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0` (`IdleCreditVault.sol:505-508`). Any tranche-token holder can open an APR0 withdraw request of arbitrary size (even dust) during an APR=0 epoch, which sets `apr0Users[user].principal` and increments `apr0TotalPrincipal` (`IdleCreditVault.sol:567-577`). `apr0TotalPrincipal` is only cleared inside `prepareStopEpochWithApr0` at line 540 — *after* the revert check — so once the manager (an honest actor) raises the APR for the next epoch, every subsequent `stopEpoch`/`stopEpochWithDuration` call reverts before reaching the reset. The running epoch can never be stopped while APR > 0, freezing all lender and borrower funds in the vault.

This mirrors CVE-2019-3883: a cheap unauthenticated request that hangs forever because the "timeout" path (stopEpoch) does not apply to it, leaving the worker (the epoch) stuck.

### Finding Description
- `requestWithdraw` on the vault mints a receipt and, when `unscaledApr == 0` and the pool is not closed, routes to `_requestWithdrawApr0`, which does `apr0Users[_user].principal += _amount` and `apr0TotalPrincipal += _amount` (`IdleCreditVault.sol:285-286`, `:567-577`). There is no minimum amount, so a KYC'd tranche holder can deposit a dust amount and request withdraw for ~1 wei.
- `prepareStopEpochWithApr0` is invoked by `IdleCDOEpochVariant._stopEpoch` (confirmed by references in `contracts/IdleCDOEpochVariant.sol`). It early-returns only when `_principal == 0`; otherwise it reverts if `unscaledApr != 0` (`IdleCreditVault.sol:502-508`).
- The only code that zeroes `apr0TotalPrincipal` is line 540 of the same function, which is unreachable after the revert. No user claim path clears it either: `_settleApr0` moves `principal` → `settledPrincipal` but does not touch `apr0TotalPrincipal` (`IdleCreditVault.sol:545-565`), and `_clearWithdrawClaimForEpoch` only decrements it during default-recovery clearing (`IdleCreditVault.sol:822-828`), which requires the epoch to stop and default first — itself unreachable because stopEpoch reverts.
- Attack sequence (running epoch, APR = 0):
  1. Attacker deposits dust into AA/BB tranche and calls `requestWithdraw` → `apr0TotalPrincipal = dust > 0`.
  2. Epoch ends; honest manager calls `stopEpochWithDuration(newApr > 0, ...)` or directly `setAprs` to raise APR for the next epoch. `setAprs` itself succeeds.
  3. `stopEpoch` reverts with `NotAllowed` at the `unscaledApr != 0` guard. Retries revert identically; `apr0TotalPrincipal` can never be reset because the reset sits below the guard.
  4. Result: `isEpochRunning` stays true, `epochEndDate` stays in the past, no `startEpoch`/`stopEpoch`/`claimWithdrawRequest` can proceed, and lender principal plus borrower repayment is frozen until the manager sets APR back to 0. The attacker can re-arm the attack every APR=0 epoch for ~1 wei of capital.

### Impact Explanation
Temporary freezing of all vault funds (all tranche holders and queued withdrawals) for at least the duration of one blocked epoch, recurring indefinitely each time APR is raised while an APR0 request exists. The only recovery is for the manager to notice and restore `unscaledApr = 0` via `setAprs` so stopEpoch can succeed — meaning a single dust request forces governance/manager intervention and delays every user's withdrawal by a full buffer/epoch cycle, with no attacker cost beyond gas and dust collateral.

### Likelihood Explanation
Requires an APR=0 deployment (explicitly supported and tested, e.g. the queue tests note "This credit vault has apr set to 0"), a KYC-passing lender or any tranche holder (allowed attacker classes), and an honest APR increase — a routine manager action. Any user can also trigger it accidentally by requesting a withdrawal in an APR0 epoch before a scheduled APR change, making the freeze likely in normal operation, not just adversarially.

### Recommendation
Clear `apr0TotalPrincipal` (or gate only the interest split, not the stop) when `unscaledApr != 0`, e.g. move the `apr0TotalPrincipal = 0` reset above the revert check, or drop the revert entirely and treat APR0 pending principal as an ordinary normal-request bucket when the APR has been raised. Alternatively, auto-settle open APR0 requests into `withdrawsRequests` when APR transitions away from 0.

### Proof of Concept
```solidity
// Foundry test against the epoch-variant credit vault (APR = 0)
function testApr0DustRequestFreezesStopEpoch() external {
    // 1) Vault running with unscaledApr == 0; attacker holds a dust tranche balance
    uint256 dust = 1;
    deal(underlying, attacker, dust);
    vm.startPrank(attacker);
    IERC20(underlying).approve(address(idleCDO), dust);
    idleCDO.depositAA(dust);                    // buffer-period deposit -> mints at next epoch
    vm.stopPrank();

    vm.prank(manager);
    cdoEpoch.startEpoch();                      // epoch N running, APR = 0

    // 2) Attacker requests withdrawal of the dust tranche -> apr0TotalPrincipal = dust
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(dust, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // 3) Epoch ends; honest manager raises APR for next epoch
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    strategy.setAprs(5e18, 5e18);               // unscaledApr != 0 now

    // 4) Every stopEpoch reverts: guard at IdleCreditVault.sol:506-508
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // 5) Retry / user claim does not clear apr0TotalPrincipal -> epoch stuck
    assertTrue(cdoEpoch.isEpochRunning());
    // Only recovery: manager sets APR back to 0 before stopEpoch can succeed.
}

  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
  }
