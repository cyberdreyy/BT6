### Title
Transient ERC4626 liquidity exhaustion can indefinitely block `stopEpoch` and freeze all credit-vault withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.onStopEpoch()` reverts when the ERC4626 vault has enough share value but temporarily lacks redeemable underlying liquidity, and `IdleCDOEpochVariant._stopEpoch()` calls the hook outside its borrower-funding `try/catch`. An unprivileged ERC4626 market participant can exhaust vault liquidity after a lender submits a withdrawal request, causing every `stopEpoch` attempt to revert and leaving active principal plus pending receipts frozen until liquidity returns. [1](#0-0) [2](#0-1) 

### Finding Description
At epoch start, the programmable borrower snapshots pending withdrawal obligations but deposits the contract’s entire underlying balance into the ERC4626 vault rather than retaining `epochPendingWithdraws` as liquid cash. [3](#0-2) 

At epoch stop, if the CDO requires more than the borrower’s on-hand balance, the borrower calls `vault.withdraw()` for the shortfall and reverts with `StopEpochVaultLiquidityUnavailable` whenever the external vault cannot currently satisfy that withdrawal. [1](#0-0) 

The CDO invokes `onStopEpoch()` before its `try this.getFundsFromBorrower(...)` block, so this hook revert is not converted into the existing borrower-default path. [2](#0-1) 

A lender can create a nonzero required amount through `requestWithdraw()`, which the strategy adds to `pendingWithdraws`. [4](#0-3) [5](#0-4) 

After the epoch starts, an unprivileged participant in a lending-backed ERC4626 vault can borrow or otherwise consume all available vault liquidity while leaving the programmable borrower’s shares economically backed. [6](#0-5) 

Because `stopEpoch` cannot complete, `isEpochRunning` remains true and the normal path that reopens requests or permits matured claims is never reached. [7](#0-6) 

### Impact Explanation
The attack temporarily freezes the entire pool’s active principal and every matured withdrawal receipt for the duration of the ERC4626 liquidity shortage. [1](#0-0) [7](#0-6) 

For a pool with `A` active assets and `P` pending withdrawal receipts, the quantified temporarily inaccessible amount is `A + P`; the minimum required vault withdrawal is only `max(0, P - onHand)`, so even dust-sized pending liquidity can make the stop transition depend on the external vault. [8](#0-7) [9](#0-8) 

The issue is not merely increased gas or an unavailable view because it blocks the only normal epoch-settlement transition and prevents users from reaching claimable funds. [10](#0-9) [7](#0-6) 

### Likelihood Explanation
The lender-side prerequisite is a normal withdrawal request, which requires only the same wallet eligibility needed to deposit. [11](#0-10) [12](#0-11) 

The external prerequisite is an ERC4626 vault whose underlying can be borrowed, redeemed, or reserved by other users such that `withdraw()` temporarily fails despite `convertToAssets()` still covering the shortfall. [1](#0-0) [13](#0-12) 

No owner, manager, borrower, or CDO compromise is required, and repeating liquidity exhaustion around each settlement attempt can extend the freeze. [14](#0-13) [15](#0-14) 

### Recommendation
Keep `epochPendingWithdraws` outside the ERC4626 vault when `onStartEpoch()` deposits idle funds, or otherwise maintain a segregated liquid reserve equal to the pending withdrawal basis. [3](#0-2) 

If the shortfall exceeds the pending reserve and vault withdrawal fails, handle that failure through an explicit epoch-settlement path instead of allowing it to permanently block every `stopEpoch` retry while the vault remains illiquid. [1](#0-0) [2](#0-1) 

Alternatively, wrap the hook call in a controlled failure path only when its accounting effects can safely be distinguished from a real borrower default, since `onStopEpoch()` mutates buffer and epoch state on success. [16](#0-15) 

### Proof of Concept
The following Foundry test shape demonstrates the broken invariant on a fork where `vault` is a lending-backed ERC4626 exposing `borrowAllAvailableLiquidity()`.

```solidity
// test/foundry/ProgrammableBorrowerLiquidityDoS.t.sol
function testStopEpochBlockedByExternalVaultLiquidity() public {
    vm.createSelectFork(vm.envString("MAINNET_RPC"), blockNumber);

    // lender is KYC-passed and vaultUser is an ordinary ERC4626 market user.
    token.approve(address(cdo), type(uint256).max);

    vm.prank(lender);
    uint256 trancheAmount = cdo.depositAA(poolAmount);

    // Create a matured-at-stop obligation.
    vm.prank(lender);
    cdo.requestWithdraw(trancheAmount, address(AAtranche));

    vm.prank(manager);
    cdo.startEpoch();

    // External vault user consumes all spendable vault liquidity while the
    // ProgrammableBorrower's shares remain worth more than the shortfall.
    vm.prank(vaultUser);
    ILiquidityVault(address(programmableBorrower.vault()))
        .borrowAllAvailableLiquidity();

    vm.warp(cdo.epochEndDate());

    uint256 required = creditVault.pendingWithdraws();
    uint256 onHand = token.balanceOf(address(programmableBorrower));
    assertGt(required, onHand);
    assertGt(vault.convertToAssets(vault.balanceOf(address(programmableBorrower))), required - onHand);

    // The revert happens before getFundsFromBorrower try/catch.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdo.stopEpoch(nextApr, 0);

    assertTrue(cdo.isEpochRunning());
    assertEq(creditVault.withdrawsRequests(lender), trancheAmount);
}
```

The deterministic sequence is: buffer-phase deposit and `requestWithdraw`, `startEpoch`, external-vault liquidity exhaustion, `warp` past `epochEndDate`, then every `stopEpoch` call reverts before the CDO’s existing default handling can run. [4](#0-3) [1](#0-0) [2](#0-1)
