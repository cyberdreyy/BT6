### Title
Stale confirmations from removed multisig members can push a request past threshold with fewer live approvals - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` tallies confirmations from a `HashSet<String>` keyed by member identity and executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations` [1](#0-0) . `delete_member` only purges *requests originated by* the removed member and their `num_requests_pk` entry; it does not scrub that member's existing confirmations recorded on *other* still-pending requests [2](#0-1) . This is the same class of flaw as `_updateSponsor`'s missing "still-valid" check before completing an action — the contract commits to a stale piece of state (an old approval) instead of re-validating it against current membership at execution time.

### Finding Description
The binding the multisig is supposed to enforce is:
`confirmations counted at execution == approvals from members who are live members at execution time`.

The actual code breaks this equality:
1. Member A confirms `request_id = X` while still a member. `confirmations[X] = {A}`.
2. Any member (via a separate confirmed `DeleteMember` request) removes A from `self.members`. `delete_member` iterates `self.requests` and removes only requests whose *original submitter* (`r.member`) is A [3](#0-2) ; it never inspects the `confirmations` map for entries where A appears as a *confirmer* on someone else's request.
3. Request `X` (submitted by another member, confirmed by A before removal) still has `confirmations[X] = {A}`.
4. Enough *currently live* members now confirm `X` to make `confirmations.len() + 1 >= num_confirmations` true — but this count includes A's stale confirmation. The request executes even though the number of confirmations from members who are *currently* part of the multisig is one less than `num_confirmations`.

`add_request`/`confirm` never re-verify that every entry inside `confirmations` for a request corresponds to an account still present in `self.members` [4](#0-3) ; `current_member()` is only used to validate the *caller* of the current `confirm` call, not the historical confirmers already stored in the set.

### Impact Explanation
This crosses the "a multisig request executed below threshold" Critical bucket explicitly listed in scope. A K-of-N multisig is the custody control for the account's funds and permissions (`Transfer`, `AddKey`, `FunctionCall`, further `AddMember`/`DeleteMember` actions, contract upgrades via `DeployContract`) [5](#0-4) . If a request can execute with fewer than `num_confirmations` *live* approvals because one counted "confirmation" belongs to a member who has since been removed, an attacker who can get themselves added briefly (or exploit timing between confirmation and removal) can move funds or add a rogue key with less real consensus than the account owners intended — a direct authorization-threshold bypass, not merely a griefing/DoS issue.

### Likelihood Explanation
This does not require the foundation, a contract owner, or social engineering to trigger the *mechanism* — the only actors involved are the multisig's own members acting through normal, in-scope calls (`confirm`, and any already-confirmed `DeleteMember` action). The realistic trigger is ordinary operational sequencing: a member confirms a pending request, then is later removed for a legitimate reason (key compromise, offboarding) before the request is fully confirmed or executed — a routine operational pattern for multisig wallets, not an exotic attack path. Because `delete_member` silently leaves the stale confirmation counted, the vulnerability activates without any special crafted transaction ordering or front-running race.

### Recommendation
When executing `confirm`, filter/recompute the confirmation count using only entries in `confirmations[request_id]` that are still present in `self.members` (or, simpler, have `delete_member` iterate the `confirmations` map for every pending request and strip the removed member's confirmation, mirroring what it already does for `requests` keyed by submitter). Re-validate current membership of every confirmer at the point the `>= num_confirmations` decision is made.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D, E}`, `num_confirmations = 3`.
2. Submit `request_id = X` (a `Transfer` action) as member `B`.
3. `A` calls `confirm(X)` → `confirmations[X] = {A}` (1/3), request not yet executed [6](#0-5) .
4. Separately, a fully-confirmed `DeleteMember{member: A}` request executes, removing `A` from `self.members`. `delete_member` only removes requests where `r.member == A` as *submitter* — request `X` was submitted by `B`, so it is untouched, and `confirmations[X] = {A}` remains [7](#0-6) .
5. Members `C` and `D` (2 live confirmations) call `confirm(X)`. On `D`'s call, `confirmations.len() as u32 + 1 = 3 >= num_confirmations (3)` — true, and `execute_request` fires the `Transfer` [8](#0-7) .
6. Result: the transfer executed with confirmations from `{A(removed), C, D}` — only 2 of the 3 approvals came from members currently part of the multisig, i.e., the request executed below the intended live-member threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
