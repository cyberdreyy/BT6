### Title
Loss-recovery haircut keyed to the post-increment epoch is never applied to pending withdraw receipts — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.collectWithdrawFunds` stores a partial-funding haircut under `lossRecoveryPriceByEpoch[epochNumber]` [1](#0-0) , but `epochNumber` is only incremented inside `deposit()` when the epoch is still running, i.e., during `stopEpoch` processing [2](#0-1) . Withdraw receipts are recorded under the epoch in which they were requested (`withdrawsRequestsByEpoch[user][currentEpoch]`, `lastWithdrawRequest[user] = currentEpoch`) [3](#0-2) , and every consumer of the haircut looks the price up by the *request* epoch stored in `lastWithdrawRequest`, not by the epoch counter at funding time [4](#0-3) . When `collectWithdrawFunds` is invoked after the epoch bump during `stopEpoch`, the haircut is written under `epochNumber = N+1` while the receipts it must discount live under epoch `N` — the same "index used before the count/base is set" ordering defect as CVE-2024-38562.

### Finding Description
The vulnerability chain:

1. In `requestWithdraw`, receipts are indexed by the epoch at request time: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `lastWithdrawRequest[_user] = currentEpoch` (epoch `N`) [3](#0-2) .
2. At `stopEpoch`, borrower repayment arrives via `deposit()`, which — because `isEpochRunning()` is still true — executes `epochNumber += 1` before the CDO calls `collectWithdrawFunds(_amount)` with a shortfall [5](#0-4) .
3. `collectWithdrawFunds` then writes `lossRecoveryPriceByEpoch[epochNumber]` — i.e., under `N+1` — instead of under `N`, the epoch that owns the pending basis [6](#0-5) .
4. Both guards and claims resolve the haircut by the request epoch: `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` returns `0` for epoch `N` [7](#0-6) [8](#0-7) . `_claimLossAdjustedWithdrawRequest` early-returns, and `_claimFundedWithdrawRequest` — which only requires `epochNumber > lastWithdrawRequest[_user]`, now satisfied — pays the full unhaircutted `withdrawsRequests[_user]` basis at par [9](#0-8) .
5. Additionally, because the guard in `requestWithdraw` sees a zero price under epoch `N`, users can freely stack new requests without first claiming the loss-adjusted receipt, compounding the over-claim [10](#0-9) .

The invariant "a shortfall at `stopEpoch` is socialized pro-rata across pending receipts via `lossRecoveryPriceByEpoch`" is broken: the haircut exists in storage but is unreachable for the epoch it was meant to discount.

### Impact Explanation
Any unprivileged tranche holder with a pending withdraw request in a loss epoch claims their full nominal basis instead of `basis * lossRecoveryPrice / 1e18`. The strategy only received `_amount < pendingBasis` from the borrower, so paying receipts at par drains underlying that belongs to subsequent claimants and active LPs — direct theft/insolvency bounded by `pendingBasis - _amount` of the loss epoch. Early claimants extract up to 100% of their receipts while later claimants and the reserve are left underfunded; this is a first-come-first-served extraction of the shortfall with a quantifiable loss equal to the unapplied haircut amount.

### Likelihood Explanation
Requires an epoch ending with a partial borrower repayment (`stopEpochWithDuration`-style loss while `pendingWithdraws > 0`) and at least one pending receipt — a normal adverse-market path, not a privileged action. The trigger is purely ordering inside honest `stopEpoch` execution, so once a loss epoch occurs with pending receipts, every unprivileged requester in that epoch benefits automatically. No existing guard stops it: `_claimFundedWithdrawRequest`'s epoch gating passes because `epochNumber` was already bumped, and the loss-adjusted path is skipped due to the zero lookup [11](#0-10) .

Caveat: the exploit depends on `deposit()` (epoch bump) preceding `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpoch` — I was unable to fully trace that call order in `IdleCDOEpochVariant.sol` within this analysis. If the funding call precedes the bump, the same defect instead strands the haircut under the pre-increment epoch `N` while `defaultPendingClaimBasis`/instant accounting read `epochNumber` after the bump — either ordering produces a mismatched index; the direction of the mismatch determines whether receipts over-claim or are frozen.

### Recommendation
Key the loss-recovery price by the epoch that owns the pending receipts, not the mutable counter at collection time. Options:
- Capture the request epoch explicitly (e.g., `lossRecoveryPriceByEpoch[epochNumber - 1]` is fragile; better to track a dedicated `pendingReceiptsEpoch` set when `pendingWithdraws` transitions from zero, cleared when the bucket empties), and store `lossRecoveryPriceByEpoch[pendingReceiptsEpoch]` in `collectWithdrawFunds`.
- Alternatively, move `epochNumber += 1` out of `deposit()` into an explicit `bumpEpoch()` called at a fixed point in `stopEpoch` after all funding/collection calls, so reads and writes of epoch-indexed state are consistent within a stop.
- Add an invariant test: after a `stopEpoch` with `_amount < pendingWithdraws`, a requester must receive exactly `basis * lossRecoveryPrice / 1e18` and `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` must be non-zero.

### Proof of Concept
Foundry fork scenario (mainnet fork at a block where the vault holds underlying; attacker = ordinary KYC'd tranche holder):

```solidity
// test/foundry/LossEpochMiskeyed.t.sol
function test_LossHaircutBypassed() public {
    // Epoch N running: attacker requests withdraw of 100e18 via CDO.requestWithdraw
    // -> withdrawsRequestsByEpoch[attacker][N] = 100e18, lastWithdrawRequest[attacker] = N

    // Borrower repays only 50e18 of the 100e18 pending basis at stopEpochWithDuration:
    //   deposit() -> epochNumber becomes N+1
    //   collectWithdrawFunds(50e18) -> lossRecoveryPriceByEpoch[N+1] = 0.5e18
    //     (receipts keyed under N never see this price)

    // Attacker calls CDO.claimWithdrawRequest():
    //   _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[N] == 0 -> returns 0
    //   _claimFundedWithdrawRequest: epochNumber (N+1) > lastWithdrawRequest (N) -> OK
    //   pays attacker 100e18 * 1.0 instead of 50e18

    uint256 bal = underlying.balanceOf(attacker);
    assertEq(bal, 100e18);            // expected 50e18 under correct haircut
    assertEq(lossRecoveryPriceByEpoch(N), 0);          // unreachable haircut
    assertGt(lossRecoveryPriceByEpoch(N + 1), 0);      // stranded under wrong epoch
}
```

Expected outcome: attacker recovers full nominal basis despite a 50% funded epoch, leaving the strategy insolvent for remaining claimants by the unapplied 50e18 haircut.

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
