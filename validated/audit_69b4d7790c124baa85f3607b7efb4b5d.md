Based on my investigation, I found a concrete miscounting analog on the node-side coordinator that mirrors the `OrderBook._remove()` class of bug: a weight tally that is not correctly retracted when the underlying vote set changes, breaking the equality between aggregated weight and the true set of current votes.

### Title
Stale rejection weight is never retracted when a signer flips from Reject to Accept, corrupting `total_weight_rejected`/`total_weight_approved` accounting - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s in-memory `BlockStatus` tally (`total_weight_approved`, `total_weight_rejected`) is the miner-side analog of `OrderBook.index.length`: it is supposed to always equal the weight of the *current* set of signer votes. When a signer legitimately changes its vote from Reject to Accept (a state transition the signer state machine explicitly allows — `LocallyRejected --> LocallyAccepted: re-evaluated`), the coordinator adds the signer's weight to `total_weight_approved` but never subtracts it from `total_weight_rejected`, leaving stale rejection weight permanently counted.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the `Rejected` branch adds weight keyed off `responded_signers`: [1](#0-0) 

while the `Accepted` branch adds weight keyed off a *different* set, `gathered_signatures`: [2](#0-1) 

Because these two additions are gated on different membership checks, a signer S that first rejects (setting `responded_signers.insert(S)` → `total_weight_rejected += w`) and later legitimately reconsiders and accepts (per `docs/signer-flows.md`'s documented `LocallyRejected --> LocallyAccepted` transition, driven by `should_reevaluate_reject_reason`) will pass the `!gathered_signatures.contains_key(&slot_id)` check and add `w` to `total_weight_approved` too — `total_weight_rejected` is never decremented. Unlike the signer-local `SignerDb`, which explicitly enforces the correct invariant in `add_block_signature` (it deletes any prior rejection row for that signer before recording the signature, as proven by the `reject_then_accept` unit test): [3](#0-2) [4](#0-3) 

the coordinator's `BlockStatus` struct has no equivalent retraction: [5](#0-4) 

This is the exact `index.length` class of bug: a counter that is incremented on one transition but never decremented on the corresponding reverse transition, so it drifts from the true underlying set size/weight.

### Impact Explanation
`total_weight_rejected` is used to decide whether a block should be treated as globally rejected and to drive the miner's rejection-based retry/backoff timeout and to compute which failed txids to exclude: [6](#0-5) 
Because a signer that has since reconsidered and accepted the block still counts toward `total_weight_rejected` forever, the miner can (a) apply an inflated/stale rejection-driven timeout backoff indefinitely, and (b) reach the "signers rejected" branch and treat certain txids as blocking-minority-flagged even after the flagging signer no longer holds that opinion, both of which are liveness-degrading. This is a High-severity liveness wedge: legitimate signer reconsideration (which the protocol explicitly supports for re-evaluable reject reasons) cannot fully "heal" the miner's view of the vote, permanently biasing it toward false-rejection behavior for as long as that block hash is tracked.

### Likelihood Explanation
This requires only a single signer to go through the documented, ordinary `Reject → re-evaluate → Accept` path (e.g. `RejectReason::NotFoundError`, `NoSortitionView`, `ConnectivityIssues`, etc., all of which are marked re-evaluable in `should_reevaluate_reject_reason`), which is a normal operational occurrence (transient node lag, burn-view races) — no majority or privileged access is needed, and it is entirely gossip/StackerDB-driven.

### Recommendation
In the `Accepted` handler, before adding weight, check and clear the signer's prior contribution to `total_weight_rejected` (mirroring what `SignerDb::add_block_signature` already does by deleting the stale rejection row): if `slot_id` is present in `responded_signers` due to a prior rejection (and not already in `gathered_signatures`), subtract the signer's weight from `total_weight_rejected` (via `saturating_sub`) before adding it to `total_weight_approved`, keeping the two tallies mutually exclusive per signer, matching the signer-local DB invariant.

### Proof of Concept
1. Coordinator tracks a block, `total_weight = 100`, `weight_threshold = 70`.
2. Signer S (weight 10) sends `BlockResponse::Rejected` → `responded_signers.insert(S)` succeeds → `total_weight_rejected = 10`.
3. S's node catches up (e.g. missing burn view resolved) and, per `should_reevaluate_reject_reason`, S re-validates and sends `BlockResponse::Accepted` for the same block.
4. In the `Accepted` handler, `!block.gathered_signatures.contains_key(&S)` is true (S never accepted before) → `total_weight_approved += 10`.
5. `total_weight_rejected` remains 10 — S's weight is now counted in both tallies simultaneously, and will remain in `total_weight_rejected` for the lifetime of that `BlockStatus` entry even though S no longer rejects the block, corrupting the rejection-based timeout/backoff and failed-txid exclusion logic in `get_block_status`.
