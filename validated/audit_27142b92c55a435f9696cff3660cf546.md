### Title
Stale acceptance/rejection weight persists on the node side after a signer re-evaluates its vote for the same block - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node-side vote tally in `handle_signer_messages` (in `stackerdb_listener.rs`) keeps two independent weight counters, `total_weight_approved` and `total_weight_rejected`, each de-duplicated against a *different* set (`gathered_signatures` for approvals, `responded_signers` for both). Because a signer's `BlockInfo` state machine explicitly allows `LocallyAccepted -> LocallyRejected` and `LocallyRejected -> LocallyAccepted` re-evaluation for the *same* block hash, a signer that flips its vote can have its old vote's weight remain permanently counted in one bucket while its new, superseding vote is added to the other — the two tallies are never reconciled against each other. This mirrors the reported bug class: a quantity ("activity"/weight) is counted correctly in one code path but the cross-context interaction between two counting paths is not accounted for, producing a miscounted aggregate.

### Finding Description
`docs/signer-flows.md` documents the `BlockInfo` state machine explicitly permitting bidirectional transitions between local decisions for one block: [1](#0-0) 

On the node side, `StackerDBListener` tracks `BlockStatus` with two separate counters and two separate dedup sets: [2](#0-1) 

When an `Accepted` message arrives, weight is added to `total_weight_approved` only if the slot is not already in `gathered_signatures`, and the slot is then also inserted into the shared `responded_signers` set: [3](#0-2) 

When a `Rejected` message arrives, weight is added to `total_weight_rejected` only if `responded_signers.insert(slot_id)` returns `true` (i.e., the slot wasn't already present in that set): [4](#0-3) 

Consequences of the same-block vote-flip case:
- **Accept, later Reject** (`LocallyAccepted -> LocallyRejected`): the slot is already in `responded_signers` from the earlier `Accepted` branch, so the later `Rejected` message's weight is silently dropped from `total_weight_rejected` — but the earlier acceptance weight is *never removed* from `total_weight_approved`. The miner-side tally in `signer_coordinator.rs` can therefore reach `total_weight_approved >= self.weight_threshold` using weight from a signer that has since rejected the block. [5](#0-4) 
- **Reject, later Accept** (`LocallyRejected -> LocallyAccepted`): the slot is already in `responded_signers` from the earlier `Rejected` branch, but the `Accepted` branch checks a *different* set (`gathered_signatures`), so the later acceptance is still counted, leaving the stale rejection weight also permanently counted in `total_weight_rejected`.

Neither counter is ever decremented for the superseded vote; only `reset_rejections` clears `total_weight_rejected`, and it is invoked solely on a full proposal-retry timeout, not on a per-signer vote flip. [6](#0-5) 

The signer-side re-evaluation path that can legitimately produce this flip is `handle_block_validate_response` / pre-commit-threshold re-check flows, which explicitly re-run chainstate checks and can flip a previously-accepted decision to a rejection (or vice versa) for the same `signer_signature_hash`: [7](#0-6) 

### Impact Explanation
This breaks the equality "aggregated weight == set of currently-valid accepts/rejects": the node's `total_weight_approved`/`total_weight_rejected` counters can retain weight from a vote a signer has explicitly withdrawn. In the accept→reject direction this is the closest analog to "a rejection recounted as acceptance" from the bug class: the retracted acceptance still counts toward the 70% signing threshold on the node/coordinator side, potentially causing the miner to treat the block as sufficiently approved (and push it) even though the signer that originally supplied that weight now considers the block invalid/non-canonical per its own chainstate re-check. In the reject→accept direction, a stale rejection remains counted toward the 30% blocking minority, which can wedge a still-valid, now-approved block into being treated as rejected — a liveness hazard.

### Likelihood Explanation
This requires only a single signer (no majority) that re-evaluates its own vote for the same block due to ordinary state-machine transitions the code and docs explicitly support (e.g., a signed conflict going stale, or a chainstate re-check flipping validity between the validate-ok and pre-commit-threshold checkpoints). It needs no malicious majority collusion and no protocol-breaking message — just the normal re-proposal/re-evaluation flow already exercised by existing tests. However, I was not able to fully trace `BlockInfo::check_state`/`mark_locally_rejected`/`mark_locally_accepted` internals in `stacks-signer/src/signerdb.rs` within the available tool budget (grep confirmed the functions exist but I could not read their bodies to confirm exactly which triggers legitimately produce a second, contradictory `BlockResponse` broadcast for an already-responded-to hash versus being suppressed by `has_reached_consensus()`/"already responded" guards visible in `signer.rs`). This uncertainty affects confidence in the practical reachability of the double-broadcast, and should be verified against the full state-transition guard logic before treating this as fully confirmed.

### Recommendation
Reconcile the two counters against a single per-signer "current vote" record instead of two independently-gated sets: when a signer's vote for a given `signer_signature_hash` changes from Accepted to Rejected (or vice versa), subtract the previously-counted weight from the old bucket before adding it to the new one, rather than gating solely on set-membership. Alternatively, track a per-slot "current decision" enum and always recompute `total_weight_approved`/`total_weight_rejected` from that single source of truth rather than maintaining two independently-updated running totals.

### Proof of Concept
Conceptual sequence (not independently executed against a live cluster within this investigation):
1. Signer S sends `BlockResponse::Accepted` for block B. Node's `stackerdb_listener` adds S's weight to `total_weight_approved` and inserts S's slot into `responded_signers`.
2. Chain state changes (e.g., a competing block at the same height becomes signed) causing S to re-evaluate B via `check_block_against_signer_db_state`, which flips S's local decision to rejected and broadcasts `BlockResponse::Rejected` for the same `signer_signature_hash`.
3. Node's listener processes the `Rejected` message: `responded_signers.insert(slot_id)` returns `false` because S's slot is already present, so `total_weight_rejected` is never incremented — while S's stale weight remains in `total_weight_approved` from step 1.
4. If enough other signers approve, `signer_coordinator.rs`'s `total_weight_approved >= self.weight_threshold` check can be satisfied partly on S's withdrawn vote, and the coordinator proceeds to treat the block as approved. [8](#0-7) [9](#0-8)

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
