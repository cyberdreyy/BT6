### Title
Overwritten `lastWithdrawRequest` lets a user claim a loss-adjusted receipt at par, escaping the epoch haircut - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch`, and `_claimLossAdjustedWithdrawRequest` uses `lastWithdrawRequest[_user]` as the *only* key to look up `lossRecoveryPriceByEpoch`. If a user has a pending withdraw receipt in an epoch that ends with `stopEpochWithDuration(_lossAmount)` (a loss/haircut epoch), and then submits a second withdraw request in a later epoch before claiming, the loss-epoch marker is "freed" (overwritten). The old receipt's per-epoch basis (`withdrawsRequestsByEpoch[user][lossEpoch]`) still exists and is still included in the aggregate `withdrawsRequests[user]`, so it falls through to `_claimFundedWithdrawRequest`, which pays the *entire* aggregate at par. This is the on-chain analog of a use-after-free: the haircut metadata tied to the old epoch is lost while the claim basis survives and is paid out under the wrong (un-haircutted) price.

### Finding Description
- `requestWithdraw` records `withdrawsRequests[_user] += _amount`, `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, and then overwrites `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) .
- `claimWithdrawRequest` first tries `_claimLossAdjustedWithdrawRequest`, which computes `lossEpoch = lastWithdrawRequest[_user]` and returns 0 if `lossRecoveryPriceByEpoch[lossEpoch] == 0` [2](#0-1) .
- If the marker was overwritten to a non-loss epoch, the loss path returns 0 and `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` — which still contains the loss-epoch amount — at par via `_transferFundedClaim` [3](#0-2) .
- The loss-adjusted funding was only `claimBasis * lossRecoveryPrice / RECOVERY_FULL` for that epoch (the borrower funds the haircutted amount at `stopEpochWithDuration`), so paying it in full overdraws the funded reserve.
- No guard prevents a new `requestWithdraw` while an old unclaimed loss-adjusted receipt exists, and nothing else indexes `lossRecoveryPriceByEpoch` by the original request epoch — the single `lastWithdrawRequest` slot is reused for both purposes.

### Impact Explanation
Direct theft / insolvency. With `lossRecoveryPriceByEpoch[E1] = p < 1`, a user's E1 receipt of `B` is funded with only `B * p` underlying. By submitting a dust second request in a later epoch, the user receives `B` in full (plus the second receipt) instead of `B * p`. The excess `B * (1 - p)` is taken from underlyings reserved for other users' funded claims — the last claimants become unpayable, or the loss is socialized onto non-withdrawing tranche holders, defeating the loss-waterfall invariant that withdrawers in a loss epoch must absorb `1 - p`.

### Likelihood Explanation
Fully attacker-controlled sequence by an unprivileged tranche holder (KYC-passing lender):
1. Epoch E1 (running): attacker calls `requestWithdraw` for a large amount.
2. Manager calls `stopEpochWithDuration(_lossAmount)` — E1 becomes a loss epoch, `lossRecoveryPriceByEpoch[E1] = p`.
3. In the next buffer/epoch E2, attacker calls `requestWithdraw` with a minimal amount → `lastWithdrawRequest` = E2.
4. After one more epoch boundary (to pass the `epochNumber <= lastWithdrawRequest` check), attacker calls `claimWithdrawRequest`; loss path misses (no price at E2), funded path pays the whole aggregate at par.

Only requirements: the pool uses `stopEpochWithDuration` with a nonzero loss (an honest-manager action in a distressed epoch), and the attacker holds tranche tokens. No privileged collusion needed.

### Recommendation
Do not reuse `lastWithdrawRequest` as the loss-epoch index. Iterate/queue the user's request epochs, or store per-epoch loss-claim state: in `_claimLossAdjustedWithdrawRequest`, check `lossRecoveryPriceByEpoch` for *every* epoch with a nonzero `withdrawsRequestsByEpoch[_user][epoch]` (e.g., track a small per-user epoch list), and prevent `requestWithdraw` from overwriting the marker while an unresolved loss-adjusted receipt exists — or eagerly settle the loss-adjusted portion (burn + payout) at the next `requestWithdraw`/`claimWithdrawRequest` before recording the new epoch.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: standard epoch variant, deposit AA, epoch running
uint256 req1 = cdoEpoch.requestWithdraw(largeTrancheAmt, address(AAtranche)); // E1
// manager stops with loss: borrower funds only haircutted amount
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(lossAmount, newDuration);   // sets lossRecoveryPriceByEpoch[E1] = p
// attacker re-requests dust in new epoch E2 -> lastWithdrawRequest overwritten
uint256 req2 = cdoEpoch.requestWithdraw(1, address(AAtranche));                // E2
// advance past one epoch boundary
_startEpochAndCheckPrices(...); _stopEpochAndCheckPrices(...);
// claim: loss path keyed on E2 misses; funded path pays req1 + req2 at par
cdoEpoch.claimWithdrawRequest();
assertEq(received, req1 + req2);        // expected-correct: req1 * p + req2
assertLt(vaultFundedReserve, 0);        // other claimants' funds drained
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
