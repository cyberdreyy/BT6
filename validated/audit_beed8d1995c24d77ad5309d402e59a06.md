### Title
Taker can bypass destination-chain withdrawal window via `rescueFunds` by manipulating unchecked timelock offsets - (`contracts/BaseEscrowFactory.sol`, `contracts/BaseEscrow.sol`, `contracts/libraries/TimelocksLib.sol`)

### Summary
`createDstEscrow` only forces the `deployedAt` bits of the caller-supplied `timelocks` to `block.timestamp` and validates only the `DstCancellation` stage against `srcCancellationTimestamp`. All other stage offsets (`DstWithdrawal`, `DstPublicWithdrawal`, `SrcWithdrawal`, etc.) are taken verbatim from the taker-supplied `dstImmutables.timelocks`. Since `RESCUE_DELAY` is a fixed, escrow-implementation-level constant, a taker can set the `DstWithdrawal` offset to a value larger than `RESCUE_DELAY`, which makes `rescueStart` resolve to a timestamp *before* the maker's normal withdrawal window ever opens. The taker (the only authorized caller of `rescueFunds`) can then call `rescueFunds` immediately after `RESCUE_DELAY` seconds to drain the tokens they deposited for the maker, before the maker ever gets a chance to withdraw with the secret.

### Finding Description
`createDstEscrow` in `contracts/BaseEscrowFactory.sol`: [1](#0-0) 
only overwrites the `deployedAt` bits of `immutables.timelocks` and checks a single stage (`DstCancellation`) against `srcCancellationTimestamp`. It performs no check on `DstWithdrawal`, `DstPublicWithdrawal`, or any relationship between those offsets and `RESCUE_DELAY`.

`TimelocksLib.get` and `TimelocksLib.rescueStart` compute absolute times as `deployedAt + offset`: [2](#0-1) 
Because `deployedAt` is common to both computations (forced to `block.timestamp` at deployment), the relative ordering of `rescueStart` vs. `DstWithdrawal`/`DstCancellation` is entirely determined by the raw offset bits the taker chooses (`RESCUE_DELAY` vs. `dstWithdrawalOffset`/`dstCancellationOffset`).

`BaseEscrow.rescueFunds` is only gated by the rescue-delay check and caller check: [3](#0-2) 
There is no additional invariant enforced anywhere that `rescueStart(timelocks, RESCUE_DELAY) >= DstCancellation` (or `>= DstWithdrawal`), so if the taker sets `dstWithdrawalOffset > RESCUE_DELAY` and/or `dstCancellationOffset > RESCUE_DELAY`, `rescueFunds` becomes callable strictly before `withdraw`/`publicWithdraw`/`cancel` become callable in `contracts/EscrowDst.sol`: [4](#0-3) 

Since the taker fully controls `dstImmutables` at `createDstEscrow` call time (this is the taker's own transaction, not signed/committed by the maker on the destination chain), they can trivially choose these offsets to violate the intended ordering `withdrawal < cancellation < rescueStart`.

### Impact Explanation
The destination escrow holds the taker's deposited tokens (`dstImmutables.amount` plus native safety deposit) that are meant to be delivered to the maker once the maker reveals the secret (already used by the taker to withdraw the maker's source-chain funds). By front-running the withdrawal window with `rescueFunds`, the taker can reclaim the full token balance of the destination escrow for themselves via an arbitrary `amount`/`token` argument, before the maker's `withdraw`/`publicWithdraw` window ever opens. This is a direct theft of funds meant for the maker in the swap — the taker gets both legs of the trade (the maker's source tokens and their own destination tokens back), which is a Critical-severity direct theft of user funds/protocol insolvency scenario for the swap.

### Likelihood Explanation
High. This requires no privileged role — it is executed entirely by an ordinary resolver/taker who is already the only party allowed to call `createDstEscrow` and `rescueFunds` for that escrow. It only requires choosing timelock offsets when constructing `dstImmutables`, something entirely within the taker's control, and waiting `RESCUE_DELAY` seconds (a fixed, typically much shorter duration than the deliberately-large windows makers might expect for withdrawal).

### Recommendation
In `createDstEscrow`, validate that all destination timelock stage offsets (`DstWithdrawal`, `DstPublicWithdrawal`, `DstCancellation`) are strictly less than `RESCUE_DELAY` (or otherwise enforce `rescueStart(timelocks, RESCUE_DELAY) >= get(Stage.DstCancellation)`), rejecting the escrow creation otherwise. The same invariant should be checked for the source-side timelocks in `_postInteraction`/`createSrcEscrow` for `EscrowSrc`, since the same offset-vs-`RESCUE_DELAY` relationship applies there.

### Proof of Concept
1. Taker calls `createDstEscrow` with `dstImmutables.timelocks` encoding `DstWithdrawal offset = RESCUE_DELAY + 1`, `DstPublicWithdrawal offset = RESCUE_DELAY + 1`, and `DstCancellation offset <= srcCancellationTimestamp` (still satisfying the only enforced check) but also set greater than `RESCUE_DELAY`.
2. `immutables.timelocks.setDeployedAt(block.timestamp)` sets `deployedAt`; `DstCancellation` check passes because it only compares against `srcCancellationTimestamp`, not `RESCUE_DELAY`.
3. Taker funds the escrow as required (`safeTransferFrom`/native value).
4. At `block.timestamp + RESCUE_DELAY`, `rescueStart` is reached, but `DstWithdrawal`/`DstCancellation` (`block.timestamp + RESCUE_DELAY + 1`) is not yet reached.
5. Taker calls `rescueFunds(token, fullEscrowBalance, immutables)` — passes `onlyCaller`, `onlyValidImmutables`, and `onlyAfter(rescueStart)` — and drains the full destination escrow balance to themselves, before the maker's window (`withdraw`/`publicWithdraw`) ever opens and before `cancel` is even callable.

This can be confirmed with a Foundry test mirroring `test/libraries/TimelocksLib.t.sol` / `test/unit/EscrowFactory.t.sol` patterns, asserting `rescueStart < timelocks.get(Stage.DstWithdrawal)` for a chosen offset combination, then asserting a successful `rescueFunds` call and zero escrow balance prior to the maker's withdrawal window.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function setDeployedAt(Timelocks timelocks, uint256 value) internal pure returns (Timelocks) {
        return Timelocks.wrap((Timelocks.unwrap(timelocks) & ~uint256(_DEPLOYED_AT_MASK)) | value << _DEPLOYED_AT_OFFSET);
    }

    /**
     * @notice Returns the start of the rescue period.
     * @param timelocks The timelocks to get the rescue delay from.
     * @return The start of the rescue period.
     */
    function rescueStart(Timelocks timelocks, uint256 rescueDelay) internal pure returns (uint256) {
        unchecked {
            return rescueDelay + (Timelocks.unwrap(timelocks) >> _DEPLOYED_AT_OFFSET);
        }
    }

    /**
     * @notice Returns the timelock value for the given stage.
     * @param timelocks The timelocks to get the value from.
     * @param stage The stage to get the value for.
     * @return The timelock value for the given stage.
     */
    function get(Timelocks timelocks, Stage stage) internal pure returns (uint256) {
        uint256 data = Timelocks.unwrap(timelocks);
        uint256 bitShift = uint256(stage) * 32;
        // The maximum uint32 value will be reached in 2106.
        return (data >> _DEPLOYED_AT_OFFSET) + uint32(data >> bitShift);
```
