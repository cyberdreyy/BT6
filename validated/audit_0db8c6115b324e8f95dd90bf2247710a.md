### Title
Unauthenticated attacker can flood `savedCallbacks` to prematurely evict another user's still-valid, pending trigger callback via `pruneCallbacks` age-sort eviction - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` inserts every signed `web_api_trigger` request into a single shared, unbounded-until-pruned map `h.savedCallbacks` keyed only by message ID, with no per-sender quota or allowlist enforcement (explicitly marked as a TODO). `pruneCallbacks` evicts entries purely by global creation-time ordering once the map exceeds `MaxSavedCallbacks`, so any signer able to submit many valid, signed `web_api_trigger` messages can push the map past capacity and cause the oldest entries — which may belong to a different, legitimate, still-pending user — to be deleted before the DON ever responds, silently dropping that victim's response.

### Finding Description
`HandleLegacyUserMessage` validates message shape/timestamp/method and signature via `common.ValidatedRequestFromMessage`, then unconditionally stores the callback: [1](#0-0) [2](#0-1) 

There is no per-sender rate limiting or allowlisting applied before the entry is added to the shared `map[string]*savedCallback`; the code comment explicitly flags this gap ("TODO: apply allowlist and rate-limiting here"). The `nodeRateLimiter` in this file only limits *node* (DON member) outbound messages, not the inbound user/message submission path.

`pruneCallbacks` runs periodically and performs two passes:
1. Deletes entries older than `CallbackMaxAgeSec` (expiry-based, correct).
2. If the map is still larger than `MaxSavedCallbacks`, it sorts **all remaining entries globally by `createdAt`** and deletes the oldest half down to `maxSize/2`, regardless of which sender owns them: [3](#0-2) 

Because eviction in step 2 is keyed solely on `createdAt` with no per-sender partitioning, an attacker (any holder of a valid keypair capable of building a correctly-signed `web_api_trigger` message — no special role required) can repeatedly submit fresh signed requests to keep the map size above `MaxSavedCallbacks`. Any legitimate victim's callback that was inserted earlier than the attacker's flood, and is still within `CallbackMaxAgeSec` and awaiting a DON response, sorts into the "oldest" bucket and gets deleted by the capacity-based eviction — before `handleWebAPITriggerMessage` has a chance to look it up: [4](#0-3) 

When the legitimate DON response later arrives, `h.savedCallbacks[msg.Body.MessageId]` is no longer present, `found` is `false`, and the function silently returns `nil` — the victim's response is dropped with no error surfaced anywhere, and the victim's request simply times out client-side.

This is a genuine cross-user denial path reachable purely from an unprivileged, unauthenticated-role attacker who only needs to be able to sign gateway messages (any keypair works — the check is only that the message is well-formed and self-consistent, not that the sender is privileged).

### Impact Explanation
Impact is denial-of-response-delivery for arbitrary other gateway users: an attacker with no special privilege can cause legitimate, still-pending `web_api_trigger` requests from other users to have their DON responses silently dropped, purely by flooding the shared `savedCallbacks` map past `MaxSavedCallbacks` (default 20000). This is a resource-exhaustion / lack-of-isolation issue causing availability impact on a shared gateway resource, matching a "Denial of Service" class bounty impact rather than fund loss or credential disclosure.

### Likelihood Explanation
Feasibility depends on the attacker's ability to sustain a submission rate sufficient to exceed `MaxSavedCallbacks` (20000 by default) within the `CallbackMaxAgeSec` window (120s default) while timing a burst against a specific victim's request. This requires generating a large volume of validly-signed and well-formed `web_api_trigger` messages, and no rate limiting/allowlisting currently exists at this insertion point to prevent it (confirmed by the explicit TODO in the code). The requirement to precisely target a specific victim's message ID reduces reliability somewhat (the attacker cannot choose exactly which victims get evicted, only that whichever pending requests are globally "oldest" at prune time — which will disproportionately include long-pending legitimate users — are the ones dropped), but a sustained flood makes eventual collateral eviction of legitimate pending callbacks likely, not merely theoretical.

### Recommendation
- Add per-sender/per-key rate limiting and/or allowlisting before inserting into `savedCallbacks` at `HandleLegacyUserMessage`, closing the existing TODO.
- Change eviction under capacity pressure to be fair across senders (e.g., per-sender quotas/sub-maps or per-sender FIFO limits) instead of a single globally shared map sorted only by `createdAt`.
- Alternatively, reject new insertions with a clear error once `MaxSavedCallbacks` is reached, instead of silently evicting older, still-valid entries belonging to other users.

### Proof of Concept
Go handler-level test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with a small `MaxSavedCallbacks` (e.g., 10) and `CallbackMaxAgeSec` large enough that nothing expires naturally during the test.
2. Insert one "victim" callback via `HandleLegacyUserMessage` with a distinct message ID and a callback whose `SendResponse` is tracked via a channel/flag.
3. Immediately after, flood the handler with `MaxSavedCallbacks` additional distinct signed `web_api_trigger` messages from "attacker" identities (new message IDs, later `createdAt`), pushing `len(h.savedCallbacks)` above `MaxSavedCallbacks`.
4. Invoke `h.pruneCallbacks()` directly (simulating the periodic ticker).
5. Assert that the victim's message ID has been deleted from `h.savedCallbacks` even though it has not exceeded `CallbackMaxAgeSec`.
6. Simulate the DON response arriving for the victim via `HandleNodeMessage`/`handleWebAPITriggerMessage` and assert `SendResponse` is never called on the victim's callback (response silently dropped), demonstrating the denial.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
