### Title
Cross-user response hijacking via MessageId collision in gateway capabilities handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` stores a pending user callback in `h.savedCallbacks` keyed only by the client-supplied `msg.Body.MessageId`, with no check for an existing entry and no binding to `msg.Body.Sender`. An attacker who sends a second signed `web_api_trigger` request using the same `MessageId` as a still-pending victim request overwrites the victim's callback entry, so the eventual DON response for that MessageId is delivered to the attacker's callback instead of the victim's.

### Finding Description
`MessageId` is a fully client-controlled string, only length/format-validated in `Validate()` and never derived from or bound to the sender's address [1](#0-0) . In `HandleLegacyUserMessage`, after basic payload/staleness/method checks, the handler unconditionally writes into the shared map: `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}` [2](#0-1)  — there is no check for whether an entry with that key already exists, and no association of the stored callback with the original sender.

When any DON node later responds with that `MessageId`, `handleWebAPITriggerMessage` looks the callback up strictly by `msg.Body.MessageId`, deletes it, and invokes `SendResponse` on whatever callback object is currently stored: `savedCb, found := h.savedCallbacks[msg.Body.MessageId]` ... `return savedCb.SendResponse(...)` [3](#0-2) . Because the map key/value pair has no per-sender scoping, the following sequence works:
1. Victim sends a valid signed `web_api_trigger` request with `MessageId = X`; `HandleLegacyUserMessage` stores victim's callback at `savedCallbacks[X]` and forwards the request to all DON members.
2. Before the DON responds, attacker (any holder of an ECDSA key, no privileged role) sends their own signed `web_api_trigger` request also using `MessageId = X`. Since nothing rejects a duplicate/colliding ID, `HandleLegacyUserMessage` overwrites `savedCallbacks[X]` with the attacker's callback.
3. A DON node responds with `MessageId = X` (either to the original or the colliding request — the response method only checks `msg.Body.Sender == nodeAddr`, not which client originated it). `handleWebAPITriggerMessage` fetches `savedCallbacks[X]`, which is now the attacker's callback, and calls `SendResponse` on it.
4. The victim's callback is silently orphaned/dropped; the attacker receives the response instead.

The existing test suite even documents unresolved sender/allowlist validation as a known gap: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` [4](#0-3) , and no test exercises MessageId collision between two distinct callers.

### Impact Explanation
This breaks the invariant that a gateway request/response is attributable to exactly one authenticated sender: a response intended for a legitimate user's capability execution request (which may carry sensitive computed data, e.g., a workflow trigger result) is routed to an attacker-controlled callback/connection. This is a cross-user response confusion / request-impersonation class issue, potentially leaking data intended for another user and disrupting the victim's request (denial of response).

### Likelihood Explanation
The only precondition is the ability to sign an arbitrary `web_api_trigger` message with any ECDSA key (no allowlisting or role check is performed before the map write, as explicitly flagged by the `// TODO: apply allowlist and rate-limiting here` comment at [5](#0-4) ) and knowledge/guessability of the victim's chosen `MessageId` (a client-chosen string up to `MessageIdMaxLen`, often predictable if callers use sequential/timestamp-derived IDs). The race window is the duration between the victim's request being accepted and the DON's first response, which is easily exploitable by an automated attacker racing requests. This is repeatable in a handler-level unit test with no special dependencies.

### Recommendation
Bind `savedCallbacks` entries to `(Sender, MessageId)` rather than `MessageId` alone, or reject/renew requests when an entry for the same `MessageId` already exists (return an error to the second sender instead of overwriting). Additionally verify the responding message routes back only to the callback whose original request had matching sender/ID pair, and consider enforcing per-sender MessageId uniqueness/allowlisting as already flagged by the existing TODO.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build handler with a mocked `DON`.
2. Craft `victimMsg` and `attackerMsg`, both signed with distinct ECDSA keys, both using identical `MessageId = "collide-1"` and valid `web_api_trigger` payloads.
3. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCb)`; assert `handler.savedCallbacks["collide-1"].Callback == victimCb`.
4. Call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCb)`; assert `handler.savedCallbacks["collide-1"].Callback == attackerCb` (overwritten).
5. Simulate a DON node response with `MessageId = "collide-1"` via `handler.HandleNodeMessage`/`handleWebAPITriggerMessage`.
6. Assert `attackerCb.SendResponse` was invoked (attacker received the response) and `victimCb.Wait` times out / never receives a response — demonstrating the victim's original request result is delivered to the attacker's callback due to the shared, sender-agnostic `MessageId` key.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")

		return errors.New("invalid DON ID length")

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
