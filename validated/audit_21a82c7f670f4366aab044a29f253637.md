### Title
Anyone can set the fixed APR while `idleCDO` is unset, enabling inflated interest claims — (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setApr`, `setAprs` and `setAprsWithBuffer` skip their only authorization check whenever `idleCDO == address(0)`. During the window between `initialize()` and the owner's `setWhitelistedCDO()` call, any unprivileged EOA can set `lastApr`/`unscaledApr` to the maximum cap (`DEFAULT_MAX_APR = 20e18`, i.e. 2000%/yr). Once the CDO is wired in, `startEpoch`/`stopEpoch` use `lastApr` to derive `expectedEpochInterest`, so the borrower is billed inflated interest (enriching a lender-attacker) or the epoch defaults because repayment is impossible.

### Finding Description
The guard is conditional on the CDO being configured:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:225-235
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;
  // if cdo is not yet set we skip the check (this can happen only during the setup)
  if (_cdo != address(0)) {
    if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  }
  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
```

`setAprs` and `setAprsWithBuffer` (lines 206-220) are `external` wrappers that delegate to this same check, so they are equally callable by anyone in the same window. This mirrors the referenced bug class: an authorization gate that is silently bypassed rather than enforced, giving an unauthorized party access to a privileged action.

Every other state-mutating entry point in the vault (`deposit`, `requestWithdraw`, `requestInstantWithdraw`, `claim*`, `collect*`, `prepareStopEpochWithApr0`, `finalizeDefaultRecovery`, etc.) goes through `_onlyIdleCDO()` — but those are all unreachable before `idleCDO` is set anyway, so `setApr*` is the only externally callable state change in the setup window.

### Impact Explanation
If `initialize` and `setWhitelistedCDO` are not executed atomically (e.g. separate transactions or a proxy deployed then wired later), an attacker front-runs `setWhitelistedCDO` and sets `lastApr = unscaledApr = maxApr` (20e18, ~2000% annualized). Consequences:

- **Theft/inflation of borrower liability:** `expectedEpochInterest` in the CDO is derived from `lastApr`; the borrower must repay principal + inflated interest. If the attacker is also a lender (KYC-passing or via tranche tokens), they capture the excess.
- **Forced default / loss socialization:** if the inflated interest exceeds what the borrower can repay, `stopEpoch` funding fails or `_handleBorrowerDefault` is triggered, crystallizing a loss that is socialized BB-first across honest LPs.

Cap: `maxApr` defaults to `DEFAULT_MAX_APR = 20e18` and can only be lowered by the owner, so the inflation is bounded at ~2000%/yr scaled over the epoch duration — still large enough to materially misprice or break an epoch.

### Likelihood Explanation
Conditional on deployment ordering. If the deployment script calls `initialize` and `setWhitelistedCDO` in one transaction (standard for this codebase's factories), the window does not exist and the finding is informational. If wiring is multi-transaction (proxy deploy → initialize → CDO set), a generalized front-runner or an attacker watching the mempool can hit it. Once `idleCDO` is set, the attack surface permanently closes. Hence low-to-moderate likelihood, but zero cost to attempt.

### Recommendation
Remove the skip-check branch: revert when `idleCDO == address(0)` and `msg.sender` is not `owner()`/`manager`, or require `msg.sender == owner()` during setup and CDO/manager afterwards. Alternatively, fold APR initialization into `initialize` (which already sets `lastApr`/`unscaledApr` from `_apr`) so no post-init call is needed before the CDO is whitelisted.

### Proof of Concept
Foundry fork-style PoC against a deployed `IdleCreditVault` proxy after `initialize` but before `setWhitelistedCDO`:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "contracts/strategies/idle/IdleCreditVault.sol";

contract SetAprUnauthorizedTest is Test {
    IdleCreditVault vault;
    address attacker = address(0xbeef);

    function setUp() public {
        vault = new IdleCreditVault(); // implementation; use proxy in fork test
        // On a fork: point `vault` at the deployed proxy that has been
        // initialize()d but whose setWhitelistedCDO() has not yet run.
        // vault.initialize(USDC, owner, manager, borrower, "B", 5e18);
    }

    function testAnyoneCanSetAprBeforeCDOSet() public {
        assertEq(vault.idleCDO(), address(0));
        uint256 cap = vault.maxApr(); // DEFAULT_MAX_APR = 20e18

        vm.prank(attacker);
        vault.setAprs(cap, cap); // no revert: auth check skipped

        assertEq(vault.lastApr(), cap);
        assertEq(vault.unscaledApr(), cap);
        // subsequent owner setWhitelistedCDO() locks in the inflated APR;
        // the first epoch's expectedEpochInterest is computed from `cap`.
    }
}
```

Note: I was unable to verify the deployment/factory path (whether `initialize` and `setWhitelistedCDO` run atomically) within this session. If deployment is confirmed atomic, this reduces to a defense-in-depth issue rather than an exploitable vulnerability.
