### Title
Stale confirmations from deleted multisig keys count toward `num_confirmations` threshold, allowing execution below the live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
The `MultiSigContract::confirm` function in `multisig/src/lib.rs` authorizes and executes a pending request purely by comparing the size of a `HashSet<PublicKey>` of past confirmations against `num_confirmations`, without re-validating that each previously-recorded confirming public key is still an active access key on the account. Meanwhile, `DeleteKey` (`multisig/src/lib.rs` lines 198-216) only purges *requests originated by* the removed key, not confirmations that key placed on *other still-pending* requests. As a result, a key that is later removed from the multisig can still count toward approving unrelated pending requests, letting a request execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
The invariant the multisig is supposed to enforce is: **live confirming members ≥ num_confirmations** before executing a request (`confirmations.len() ≥ num_confirmations` should equal **the number of currently-authorized keys that approved**). The contract instead tracks confirmations as a persistent set keyed by request id, and the count check at [1](#0-0)  only checks set cardinality:

```
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    ...
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else { ... }
}
``` [2](#0-1) 

When a key is removed via `MultiSigRequestAction::DeleteKey`, the cleanup logic only removes requests that the *removed key itself created* (`r.signer_pk == pk`), and it deletes the on-chain access key via `promise.delete_key(pk)`. It does **not** scan `self.confirmations` to strip that key's approval from other outstanding requests:

```
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    let request_ids: Vec<u32> = self.requests.iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k).collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [3](#0-2) 

So if key `A` confirms request `R` and is later removed from the account (its access key deleted on-chain by a separate, properly-approved `DeleteKey` request), `A`'s stale confirmation for `R` remains inside `self.confirmations[R]`. `assert_valid_request` at [4](#0-3)  never re-validates the previously stored confirmers — it only checks that `R` exists and that a confirmations entry exists, and only enforces `predecessor_account_id == current_account_id` (i.e., that the call comes through the account, satisfied by any valid access key on the account, not that *every* confirmer in the set is still live). Consequently, one more live key confirming `R` can push `confirmations.len()+1 >= num_confirmations`, and `R` executes even though the number of *currently authorized* approvers is one less than `num_confirmations`.

### Impact Explanation
This breaks the core custody binding of the multisig: **a request should only execute once `num_confirmations` currently-authorized keys have approved it**, not once `num_confirmations` *approvals ever recorded* (including from now-revoked keys) exist. A removed/compromised key's earlier confirmation persists as "phantom" authorization weight for unrelated pending requests (e.g., `Transfer`, `AddKey`, `FunctionCall` with attached deposit), letting a request — including a fund transfer — execute with effectively fewer live signers than the configured threshold `K`. This directly matches the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
This requires no attacker privilege beyond being one of the multisig's own keyholders and normal contract usage: any legitimate confirmation followed by a later (unrelated, properly-approved) key removal creates the stale-confirmation condition automatically — there is no special exploit setup needed, just ordinary account key-rotation combined with a pending, not-yet-fully-confirmed request. The bug is deterministic given that ordering of events, not probabilistic or reliant on external actors.

### Recommendation
When executing `DeleteKey` (and equivalently in `multisig2`'s `DeleteMember`), iterate over **all** `self.confirmations` entries and remove the deleted public key/member from every confirmation set, not just from requests the removed key itself created. Alternatively, when checking the threshold in `confirm`, re-validate that every public key in the stored confirmation set is still a valid access key on the account before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with `num_confirmations = 3` and exactly keys `A`, `B`, `C`.
2. `A` calls `add_request` to create request `R` (e.g., `Transfer` to an external account), then `A` calls `confirm(R)` → `confirmations[R] = {A}`.
3. `B` calls `confirm(R)` → `confirmations[R] = {A, B}` (2 of 3, not yet executed).
4. Separately, `A`, `B`, `C` create and approve (3-of-3) a `DeleteKey{public_key: A}` request; it executes, calling `promise.delete_key(A)` — `A`'s on-chain access key is now invalid. Per [3](#0-2) , this only removes requests where `A` was the *creator*; it does not touch `confirmations[R]`, which still contains `A`.
5. `C` calls `confirm(R)`. In `confirm`, `confirmations.len()` is `2` (still containing stale `A` and `B`); `2 + 1 >= 3` is true, so `R` (the `Transfer`) executes via `execute_request`, even though only `B` and `C` are live, currently-authorized keys — one fewer than the required `num_confirmations = 3`. The transfer executes below the intended threshold.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
