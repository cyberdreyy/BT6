## Analog Found: EIP-8130 JIT Account-Change Replay Allows Reinstating a Revoked Actor

### Title
Replayable JIT `AuthorizeActor` Grants Survive `RevokeActor` and Can Silently Reinstate a Revoked Signer - ([File: crates/execution/eip8130/src/apply.rs])

### Summary
EIP-8130's "JIT" (just-in-time, unsequenced) local account-change channel intentionally allows a signed `AuthorizeActor` batch to be replayed indefinitely — it consumes no sequence counter and remains valid until the account's `local_epoch` is explicitly incremented via a separate `IncrementLocalEpoch` change. `RevokeActor` does not bump the epoch. Consequently, a JIT `AuthorizeActor` grant with a zero ("no expiry") or still-future expiry that was ever broadcast on-chain (and is therefore publicly visible calldata) can be re-submitted by anyone at any later time to silently re-authorize the actor it names, even after the account's owner has explicitly revoked that same actor — unless the owner also remembers to increment the local epoch. This mirrors the report's root cause: a signed authorization token ("link") that is valid for its whole nominal life and is never marked consumed/invalidated on the security-relevant event (password change / revoke), enabling repeated unauthorized reinstatement.

### Finding Description
The JIT (unsequenced) path is defined in `AccountChangeApplier::apply_config_change_with_account_state`: [1](#0-0) 

Only an already-*expired* JIT grant is skipped; a grant with expiry `0` ("no expiry" sentinel) or a still-future expiry is applied verbatim, and because the batch's low sequence half is the `UNSEQUENCED` sentinel, applying it does **not** advance `local_sequence`, so the exact same signed batch stays authorizable again and again: [2](#0-1) 

The only mechanism that invalidates such a replayable grant is `IncrementLocalEpoch`, a separate, explicit change type: [3](#0-2) 

`RevokeActor`, by contrast, only clears the actor's storage slot for the current state — it performs no epoch bump and has no coupling to the JIT replay window at all: [4](#0-3) [5](#0-4) 

The authorization gate for a JIT batch (`unsequenced_local_batch_skips_sequence_check`) confirms that a JIT batch authorizes "regardless of the account's current local sequence" — there is no state that ties its validity to whether the actor it grants has since been revoked: [6](#0-5) 

Because every EIP-8130 transaction (including its `account_changes`, containing the `SignedAccountChanges.signature`) is public calldata once included in a block, any historical JIT `AuthorizeActor` batch is permanently available to anyone who can read the chain — it is not a secret held only by the original signer. If the account owner later issues a `RevokeActor` for that same actor (without also issuing `IncrementLocalEpoch`), the revocation is not durable: the previously-broadcast JIT batch remains a valid, replayable authorization and can be resubmitted in a fresh EIP-8130 transaction to silently reinstate the revoked actor with its original scope (e.g. admin/operator), exactly as the report's captured activation/recovery token remained usable after the password had already been changed.

### Impact Explanation
An actor grant issued through the JIT/unsequenced channel functions as a de-facto standing credential that outlives an explicit `RevokeActor` unless the account owner separately remembers to call `IncrementLocalEpoch`. Since the EIP-8130 documentation frames `RevokeActor` as the mechanism to remove an actor's authority, an owner who revokes a compromised or no-longer-trusted key (session key, delegate, operator) via `RevokeActor` alone is left believing the actor is gone, while anyone holding (or having merely observed) the original JIT grant transaction can replay it to restore that actor's scope — including admin (`scope == 0`) grants, which govern config changes, sender/payer operations, and delegation. This is a concrete unauthorized-operation / account-takeover vector on the EIP-8130 account-abstraction path, directly reachable by any anonymous transaction sender who submits an `AccountChange::ConfigChange` carrying the replayed batch.

### Likelihood Explanation
Exploitation requires no privileged access: the attacker only needs the calldata of a previously-included EIP-8130 transaction that contained a JIT `AuthorizeActor` change with expiry `0` or a still-future expiry — data that is trivially obtainable from any full node, block explorer, or the P2P/RPC transaction history, since Base is a public L2. The victim account owner must have relied on `RevokeActor` without pairing it with `IncrementLocalEpoch` for that channel, which is not enforced or warned against anywhere in the applier or authorizer code paths reviewed. Given that JIT batches are explicitly documented as "replayable... until the local epoch moves," and the revoke path never moves it, this is a realistic operational gap rather than a contrived edge case.

### Recommendation
Either (a) make `RevokeActor` automatically bump `local_epoch` for the account when it fires on the Local channel, invalidating any previously-issued JIT grants at the old epoch, or (b) require/force pairing every `RevokeActor` change with an `IncrementLocalEpoch` change in the same batch at the protocol/apply layer, or (c) bind JIT `AuthorizeActor` grants to a single-use nonce/hash-tracking scheme (mirroring the nonce-free `expiring_nonce_seen` replay-protection design already used elsewhere in this crate for `NONCE_KEY_MAX` transactions) so a specific granted signature cannot be reapplied after the actor it names has been revoked.

### Proof of Concept
1. Account `A`'s admin signs and broadcasts an EIP-8130 transaction containing a `SignedAccountChanges` batch on the `Local` channel with `sequence = UNSEQUENCED` (JIT) and one `AuthorizeActor` change granting actor `X` `scope = SCOPE_UNRESTRICTED` (admin) with `expiry = 0` (never expires). This lands per `AccountChangeApplier::apply_config_change_with_account_state` (crates/execution/eip8130/src/apply.rs:400-420), and is now permanently visible calldata in block history.
2. Later, `A`'s admin decides to remove `X` and broadcasts a `RevokeActor` change for `X` (any channel). This clears `X`'s `actor_config` slot per `revoke_actor_with_account_state` (crates/execution/eip8130/src/apply.rs:755-789) but does not touch `local_epoch`.
3. An attacker (or anyone who observed step 1's calldata) resubmits the *exact same* `SignedAccountChanges` JIT batch from step 1 as the `account_changes` of a new EIP-8130 transaction. `ConfigChangeAuthorizer::check_channel_sequence` accepts it unconditionally for `UNSEQUENCED` (crates/execution/eip8130/src/config.rs:430-444), and `apply_config_change_with_account_state` re-applies the `AuthorizeActor` change (expiry `0` is never skipped), reinstating `X` with unrestricted admin scope on account `A` — with no signature from `A`'s current admin required for this specific transaction.

    /// Applies an `IncrementLocalEpoch` op, mirroring `_applyIncrementLocalEpoch`:
    /// a strict `local_epoch += 1` (rejecting the terminal `u32::MAX`) that also
    /// resets `local_sequence` to 0, retiring every unlanded local signature (each
    /// commits the full 64-bit `localEpoch ‖ localSequence` word). Allowed on
    /// either channel — a Multichain batch may bump the local epoch without a
    /// separate Local batch. The payload MUST be empty.
    fn apply_increment_local_epoch(
        payload: &[u8],
        state: &mut AccountState,
    ) -> Result<(), ApplyError> {
        if !payload.is_empty() {
            return Err(ApplyError::InvalidChangePayload);
        }
        // `local_epoch` stores a `uint32`; only the terminal value cannot advance
        // (the epoch half has no reserved sentinel).
        if state.local_epoch == u64::from(u32::MAX) {
            return Err(ApplyError::EpochSaturated);
        }
        state.local_epoch += 1;
        state.local_sequence = 0;
        Ok(())
    }

    pub fn revoke_actor_with_account_state(
        storage: &mut AccountConfigurationStorage<'_>,
        account: Address,
        actor_id: B256,
        state: &mut AccountState,
    ) -> Result<u32, ApplyError> {
        let config = storage.actor_config_slot(account, actor_id)?;
        let is_self = actor_id == AccountConfigurationStorage::self_actor_id(account);
        if config.authenticator != Address::ZERO {
            Self::revoke_explicit_actor(storage, account, actor_id, config)?;
            // Defense-in-depth: an explicit self actor is necessarily non-k1, and
            // `authorize_actor_with_account_state`/`apply_create` already set
            // DEFAULT_EOA_REVOKED and zeroed the inline scope/expiry when it was
            // installed. Re-assert that invariant here (a no-op on the in-tree
            // install paths) instead of depending on the authorize path, so a
            // future direct `set_actor_config` writer cannot leave a live inline
            // secp256k1 home behind an explicit self entry. `state` is already
            // loaded and flushed by the caller, so this adds no storage access.
            // This clears a populated explicit `actor_config`, so it is not the
            // discounted inline-self shape.
            if is_self {
                Self::disable_inline_self(state);
            }
            return Ok(0);
        }
        if !is_self || state.default_eoa_revoked() {
            // Idempotent: the actor is already absent — no explicit `actor_config`
            // entry, and either a non-self id or a self whose inline secp256k1 key
            // is revoked. Mirrors `_applyRevoke`'s `if (!_isAuthorized(...)) return;`
            // (eip-8130 #100): no state change and no `ActorRevoked` event. All
            // three conservatively reset-priced revoke slots (`actor_config` and
            // both policy slots) are empty for an absent actor, so the whole revoke
            // is discounted.
            return Ok(3);
        }
