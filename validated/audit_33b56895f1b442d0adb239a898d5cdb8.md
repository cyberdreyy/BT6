### Title
Boundary-value health inconsistency between borrow/withdraw checks and liquidation checks allows liquidation of break-even ("healthy") accounts - (File: programs/marginfi/src/state/marginfi_account.rs)

### Summary
The risk engine defines two different health predicates for the same underlying comparison of assets vs. liabilities. `check_account_init_health`, used by `borrow`/`withdraw`/protocol-integration withdraw instructions to gate risky actions, treats an account as healthy when `assets >= liabs` (non-strict). `check_pre_liquidation_condition_and_get_account_health`, used by `liquidate`, `start_receivership`/`start_deleverage`, and `pulse_health`, treats an account as healthy only when `account_health > 0` (strict). At the exact boundary where `assets == liabs`, the first check reports the account as healthy (permitting a borrow/withdraw to leave the account in exactly this state), while the second reports it as not healthy, thereby permitting liquidation.

### Finding Description
In `check_account_init_health`: [1](#0-0) 
the healthy flag is computed as `assets >= liabs` (non-strict inequality), and the instruction only rejects the transaction (`RiskEngineInitRejected`) when `!healthy`, i.e., when `assets < liabs`. So a borrow/withdraw that results in `assets == liabs` is explicitly permitted.

In `check_pre_liquidation_condition_and_get_account_health`: [2](#0-1) 
`healthy` is computed as `account_health > I80F48::ZERO` (strict inequality), and if `healthy && !ignore_healthy` the function errors with `HealthyAccount`, blocking liquidation only when the account is *strictly* healthy. At `assets == liabs`, `account_health == 0`, so `healthy` is `false`, and the function does **not** block liquidation — it proceeds to allow the liquidator to seize collateral.

`check_account_init_health` is called from the standard borrow/withdraw paths (e.g. `programs/marginfi/src/instructions/marginfi_account/borrow.rs`, `programs/marginfi/src/instructions/marginfi_account/withdraw.rs`, and the third-party integration withdraw instructions in `solend/withdraw.rs`, `kamino/withdraw.rs`, `drift/withdraw.rs`, `juplend/withdraw.rs`), while `check_pre_liquidation_condition_and_get_account_health` is called from `programs/marginfi/src/instructions/marginfi_account/liquidate.rs` and `liquidate_start.rs` (`start_receivership`/`start_deleverage`). This is the exact same class of bug described in the external report: `adjust()`-equivalent logic permits equality (`<=`), while `getLiquidatableDebt()`-equivalent logic requires strict inequality (`>`), leaving a one-point gap at the boundary where the two functions disagree on account health.

### Impact Explanation
A user can legitimately borrow or withdraw up to the point where `assets == liabs` — this action is accepted by `check_account_init_health` and the resulting account state is marked `HEALTHY` in the on-chain `health_cache` (also observable via `pulse_health`, since `check_account_init_health` is reused there too). However, the very same account, in that exact state, is not protected from liquidation: `check_pre_liquidation_condition_and_get_account_health` will not raise `HealthyAccount` and liquidation proceeds. This is a direct financial-effect inconsistency — a user's account that was just validated and permitted to exist in a given state by the protocol's own borrow/withdraw risk check can be immediately liquidated, causing the user to lose collateral (minus applicable liquidation discount/fee) despite having done nothing to violate the health constraint enforced on their own action.

### Likelihood Explanation
This requires a liability/asset ratio to land exactly at the boundary (`assets == liabs`), which is a low-probability but deterministically reachable state (e.g., a user borrowing the maximum permitted amount such that maintenance-weighted assets exactly equal maintenance-weighted liabilities, or price movement bringing the account to that exact value). Because oracle prices update continuously and the boundary is a single point rather than a range, exact equality is unlikely to persist but can be hit by design (e.g. a liquidator/bot targeting max-borrow accounts) or transiently during price cache updates, making the bug reachable without any privileged access — it only requires normal user borrow/withdraw actions and a liquidator monitoring for this boundary condition.

### Recommendation
Make the health predicates consistent by using the same strict/non-strict convention in both functions. Since `check_account_init_health` uses `assets >= liabs` for healthy, `check_pre_liquidation_condition_and_get_account_health` should use `account_health >= I80F48::ZERO` for healthy (or vice versa — align both to a single agreed convention), e.g.:
```rust
// in check_pre_liquidation_condition_and_get_account_health
let healthy = account_health >= I80F48::ZERO;
```
This ensures that any account state accepted as healthy by the borrow/withdraw risk check cannot simultaneously be treated as liquidatable by the liquidation risk check.

### Proof of Concept
1. User calls `borrow` (or any withdraw instruction) with an amount such that, after the action, `assets == liabs` under `RequirementType::Initial` weights used by `get_health_components`. `check_account_init_health` computes `healthy = assets >= liabs = true`, so the transaction succeeds — see [1](#0-0) .
2. Because maintenance weights typically differ from initial weights, assume market conditions (or a bank config where maintenance weighting also yields exact equality) bring `RequirementType::Maintenance` assets/liabs to be exactly equal as well.
3. A liquidator calls `liquidate`, which invokes `check_pre_liquidation_condition_and_get_account_health` via `programs/marginfi/src/instructions/marginfi_account/liquidate.rs` lines 178-185. Since `account_health == 0`, `healthy = false`, and the function does not raise `HealthyAccount` — see [2](#0-1) .
4. The liquidation proceeds, seizing the user's collateral even though the account was validated as healthy by the borrow/withdraw check moments earlier.
