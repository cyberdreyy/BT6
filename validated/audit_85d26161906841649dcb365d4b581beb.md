### Title
Nonce transaction age-check bypasses authority verification when `strict_nonce_authority_check=false`, allowing unauthorized force-advance/consumption of a victim's durable nonce - (File: runtime/src/bank/check_transactions.rs)

### Summary
`check_nonce_transaction_validity` only compares the signer at `NONCED_TX_MARKER_IX_INDEX` against `nonce_data.authority` when `strict_nonce_authority_check` is `true`. The main transaction-processing path, `check_age_and_compute_budget_limits`, calls `check_transaction_age` with this flag hard-coded to `false` [1](#0-0) , so a transaction whose marker instruction lists an unrelated signer instead of the true nonce authority is still classified as a valid durable-nonce transaction.

### Finding Description
`check_nonce_transaction_validity` loads the nonce account data via `load_message_nonce_data`, and only rejects the transaction for authority mismatch when `strict_nonce_authority_check` is set: [2](#0-1) . `check_transaction_age` forwards whatever `strict_nonce_authority_check` value it receives straight into this function [3](#0-2) .

There are exactly two call sites:
- `check_transaction_without_status_cache` (forwarding-only path) passes `true` [4](#0-3) .
- `check_age_and_compute_budget_limits` (the path used for the main leader/replay transaction check, feeding `CheckedTransactionDetails`) passes `false` [1](#0-0) .

An attacker who knows a nonce account's address and its current stored `authority` pubkey (both are public, on-chain data) can build a transaction whose instruction at `NONCED_TX_MARKER_IX_INDEX` references that nonce account and lists an attacker-controlled key as the "authority" signer instead of the real authority. Because `message.get_durable_nonce()` (used inside `load_message_nonce_data`) only validates the instruction's shape/account layout, not that the listed signer matches the stored authority, and because the authority-vs-signer comparison is skipped entirely when `strict_nonce_authority_check=false`, the transaction is accepted as a legitimate nonce transaction by the main check path. The existing test suite documents the authority-check code path (`test_check_nonce_transaction_validity_missing_ix_pubkey_fail`) but never exercises the case of a *present-but-wrong* signer under `strict_nonce_authority_check=false`, which is exactly the gap being described.

Being classified as a nonce transaction is significant because Solana's durable-nonce fee/replay-protection design forces the nonce account to advance whenever a transaction is recognized as nonce-based — independent of whether the inner instruction later fails signature verification inside the system program. So the runtime's classification decision here (not the system program's internal authority check) is the gate that determines whether the victim's nonce gets consumed at all.

### Impact Explanation
This corresponds to the "replays or short-changes fees and nonces" bounty category. Concretely: an attacker without the authority key can cause a victim's durable nonce account to be force-advanced/consumed, invalidating any pending legitimate transaction the victim built against that nonce value (denial-of-service/griefing on nonce-based transactions), and can do so by paying for and controlling their own transaction rather than the victim's key.

### Likelihood Explanation
Preconditions are minimal for an unprivileged attacker: the nonce account address and its stored `authority` pubkey are both public on-chain state, readable via RPC. The attacker only needs to sign with their own key and submit a transaction whose recent_blockhash equals the nonce's current durable value and whose marker-index instruction references the nonce account. This is fully repeatable against any nonce account whose value the attacker can observe before it changes.

### Recommendation
Make the authority check unconditional in `check_nonce_transaction_validity` (or otherwise ensure `check_age_and_compute_budget_limits` cannot classify a transaction as nonce-eligible unless the recorded `nonce_data.authority` is actually among the signers of the marker instruction), removing/deprecating the `strict_nonce_authority_check=false` code path used by the main leader/replay flow.

### Proof of Concept
```rust
#[test]
fn test_check_nonce_transaction_validity_wrong_signer_not_strict_should_fail_but_passes() {
    let (bank, _mint_keypair, custodian_keypair, nonce_keypair, _) =
        setup_nonce_with_bank(10_000_000, |_| {}, 5_000_000, 250_000, None).unwrap();
    let custodian_pubkey = custodian_keypair.pubkey();
    let nonce_pubkey = nonce_keypair.pubkey();

    // Attacker's own key, NOT the recorded nonce authority.
    let attacker_keypair = Keypair::new();
    let attacker_pubkey = attacker_keypair.pubkey();

    let nonce_hash = get_nonce_blockhash(&bank, &nonce_pubkey).unwrap();
    // Marker ix lists attacker_pubkey as "authority" instead of the true authority.
    let message = new_sanitized_message(Message::new_with_blockhash(
        &[
            system_instruction::advance_nonce_account(&nonce_pubkey, &attacker_pubkey),
            system_instruction::transfer(&custodian_pubkey, &nonce_pubkey, 100_000),
        ],
        Some(&custodian_pubkey),
        &nonce_hash,
    ));

    // strict_nonce_authority_check = false (as used by check_age_and_compute_budget_limits)
    let result = bank.check_nonce_transaction_validity(
        &message,
        &bank.next_durable_nonce(),
        false,
        false,
    );
    // Vulnerable: returns Some((nonce_pubkey, ..)) despite attacker not holding
    // nonce_data.authority's key.
    assert!(result.is_some());
}
```
I was not able to trace, within the available tool budget, the downstream rollback/nonce-advance logic in `svm/src/rollback_accounts.rs` and `svm/src/nonce_info.rs` to confirm with certainty whether the nonce state is unconditionally rewritten purely based on this classification (independent of the system program's later, correctly-enforced authority check on the actual `AdvanceNonceAccount` instruction). This should be verified directly against those files before treating the "force-advance" impact as fully confirmed; the classification gap itself in `check_nonce_transaction_validity`, however, is directly confirmed by the code above.
