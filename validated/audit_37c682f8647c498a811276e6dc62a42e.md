### Title
Signer replaces its live, unfinished per-cycle instance without checking for unprocessed blocks, silently dropping in-flight validation/pre-commit state - (`stacks-signer/src/runloop.rs`)

### Summary
`RunLoop::refresh_runloop` keeps only two `Signer` instances alive at once, keyed by `reward_cycle % 2` (`stacks-signer/src/runloop.rs:194`). When the runloop needs to configure the *next* reward cycle (`N+2`), it calls `refresh_signer_config(N+2)` (`stacks-signer/src/runloop.rs:342-362`), which unconditionally does `self.stacks_signers.insert(reward_index, new_signer_config)` into the slot for `reward_index = (N+2) % 2 == N % 2` — the very slot that may still hold the not-yet-finished `Signer` for the older cycle `N`. This overwrite happens *before* `cleanup_stale_signers` runs its safety check, and `cleanup_stale_signers` is the only place that gates removal on `!signer.has_unprocessed_blocks()` (`stacks-signer/src/runloop.rs:471-500`). The unconditional insert in `refresh_signer_config` bypasses that guard entirely.

### Finding Description
`RunLoop::refresh_runloop` (`stacks-signer/src/runloop.rs:387-448`) does, in order:
1. Refresh signer for `current_reward_cycle` if not configured.
2. Refresh signer for `next_reward_cycle` if in prepare phase and not configured (`stacks-signer/src/runloop.rs:435-439`).
3. Only *afterwards* call `cleanup_stale_signers(current_reward_cycle)` (`stacks-signer/src/runloop.rs:441`).

`is_configured_for_cycle` (`stacks-signer/src/runloop.rs:450-458`) only checks whether the slot's stored `reward_cycle()` equals the target cycle — it says nothing about whether the previous occupant of that slot has finished its work. Since `next_reward_cycle = current_reward_cycle + 1` and the map is keyed by `% 2`, `next_reward_cycle`'s slot is exactly the slot occupied by `current_reward_cycle - 1` (i.e., cycle `N`, one full cycle behind `current`). `refresh_signer_config` (`stacks-signer/src/runloop.rs:342-362`) builds a brand-new `Signer` (fresh in-memory state via `Signer::new`) and does:
```rust
self.stacks_signers.insert(reward_index, new_signer_config);
```
with no call to, or awareness of, `has_unprocessed_blocks()`. This directly bypasses the exact safety check that `cleanup_stale_signers` was written to enforce:
```rust
ConfiguredSigner::RegisteredSigner(signer) => {
    if !signer.has_unprocessed_blocks() {
        ...
        to_delete.push(*idx);
    }
}
```
(`stacks-signer/src/runloop.rs:485-489`)

The `Signer` struct's in-flight tracking state — `submitted_block_proposal: Option<(Sha512Trunc256Sum, Instant)>` (`stacks-signer/src/v0/signer.rs:124`), the miner-view capitulation timers, and `local_state_machine` — exists only in that in-memory `Signer` instance and is discarded on replacement. Persisted `BlockInfo` rows survive in `SignerDb` (shared `db_path` across cycles), but the new `Signer` for cycle `N+2` will never re-adopt them: `block_lookup_by_reward_cycle` (`stacks-signer/src/v0/signer.rs:2667-2684`) filters strictly on `block_info.reward_cycle == self.reward_cycle`, so any `BlockValidationResponse` that later arrives for a block belonging to the discarded cycle `N` is met with:
```rust
debug!("{self}: Received a block validate response for a block we have are not tracking. Ignoring...");
```
(`stacks-signer/src/v0/signer.rs:1915-1919`)

### Impact Explanation
This is a liveness wedge on the discarded reward-cycle's tail state: if cycle `N`'s `Signer` still had an outstanding submitted-for-validation proposal or unprocessed pre-commit tracking (which is precisely the condition `has_unprocessed_blocks()` is meant to protect), the premature replacement means:
- The pending `/v3/block_proposal` validation slot (`submitted_block_proposal`) is lost, so `check_pending_block_validations` on the *new* `N+2` instance has no memory of it.
- Any late-arriving `BlockValidateOk`/`BlockValidateReject` for that block is silently dropped because the block's `reward_cycle` (`N`) no longer matches `self.reward_cycle` (`N+2`) of the surviving instance in that slot.
- The signer therefore never sends a pre-commit/signature response for a block it had legitimately promised to evaluate, and never broadcasts a rejection either — the block is neither accepted nor rejected by this signer going forward, even though it may be a fully valid, canonical block from the tail of tenure `N`.

This matches the "signer wedged into never signing valid blocks" / stale-state class of High-severity issue: state that should gate a slot-reuse decision (`has_unprocessed_blocks`) is silently ignored by a second code path (`refresh_signer_config`) that shares the same underlying map keyed on cycle parity — directly analogous to the cookie-leakage root cause of shared mutable state (the `httpx.AsyncClient`) being reused across different logical contexts (different users) without being reset/isolated between them.

### Likelihood Explanation
Reachable purely by chain progression/timing without needing a signer majority, another signer's key, or local access: `refresh_signer_config(next_reward_cycle)` fires automatically once the runloop enters the next reward cycle's prepare phase (`is_in_next_prepare_phase`), which is driven only by burn-chain height. Any tenure `N` whose validation/pre-commit round is still outstanding when the *following* cycle's prepare phase begins (e.g., a slow validation response, network delay, or a miner/tenure that runs unusually long near a cycle boundary) triggers the unconditional overwrite before `cleanup_stale_signers`'s guard would otherwise have deferred cleanup. This requires unusual but not implausible timing (a stalled or delayed validation exactly spanning a full reward cycle boundary), so likelihood is moderate rather than routine.

### Recommendation
In `refresh_signer_config`, before inserting a new `ConfiguredSigner` into `stacks_signers`, check whether the existing occupant of that slot (if any) still `has_unprocessed_blocks()`. If so, defer configuring the next cycle's signer (log/warn and retry on a later pass) rather than overwriting it, mirroring the exact guard already implemented in `cleanup_stale_signers`. Alternatively, reorder the logic so cleanup (with its safety check) always runs before any slot is reused, and refuse to overwrite a slot whose current occupant reports unprocessed work.

### Proof of Concept
Conceptual reproduction (network-level timing, no special privileges needed):
1. Let reward cycle `N` (parity `p`) run normally; near the very end of cycle `N`, have the miner submit a tenure-extension/validation request for a block, and let the node's validation response be delayed (e.g., a slow-to-respond, congested, or otherwise pending `/v3/block_proposal` call) so that `Signer` for cycle `N` still has `submitted_block_proposal.is_some()` / unresolved pre-commit tracking after the burn-chain moves into cycle `N+1`.
2. Because `has_unprocessed_blocks()` is `true`, `cleanup_stale_signers(N+1)` correctly declines to remove the cycle-`N` `Signer` from slot `p`.
3. Let the burn-chain height reach the prepare phase for cycle `N+2` while the cycle-`N` `Signer` is still in that same slot `p` (since `(N+2) % 2 == N % 2`).
4. `refresh_runloop` calls `refresh_signer_config(N+2)`, which builds a fresh `Signer` and does `self.stacks_signers.insert(p, new_signer_config)`, discarding the cycle-`N` `Signer` and its `submitted_block_proposal`/pending-validation state — bypassing the `has_unprocessed_blocks()` guard entirely.
5. When the delayed `BlockValidateOk`/`BlockValidateReject` for cycle `N`'s block finally arrives, it is routed to the surviving slot-`p` `Signer` (now configured for `N+2`); `block_lookup_by_reward_cycle` rejects it because `block_info.reward_cycle (N) != self.reward_cycle (N+2)`, and the response is logged as "not tracking" and dropped — the signer never signs or rejects that block.

Note: I was not able to fully verify, within the index's available context, whether `has_unprocessed_blocks()` covers *every* form of relevant unfinished state on `Signer` (e.g., whether it also accounts for outstanding pre-commit broadcasts awaiting threshold, not just `submitted_block_proposal`), since the full body of `has_unprocessed_blocks` was not retrieved in my searches. This affects only the precise scope of "unprocessed" state that gets silently dropped, not the core finding that `refresh_signer_config`'s insert is unconditional and bypasses whatever check `cleanup_stale_signers` performs.
