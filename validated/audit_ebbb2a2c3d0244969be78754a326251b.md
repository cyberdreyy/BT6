### Title
Gateway HTTP Action Response Cache Key Omits `WorkflowID`, Breaking Documented Workflow Isolation - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's HTTP action response cache is documented and intended to be workflow-scoped, but the cache key (`req.Hash()`) does not actually include `WorkflowID` — only method, URL, headers, body, and `WorkflowOwner`. This mirrors the reported bug class: a component's real state-mutation/keying logic silently diverges from its declared invariant (like `burnFrom` mutating balances but not `_totalSupply`), producing a false guarantee that downstream logic and operators rely on.

### Finding Description
The gateway's v2 HTTP capability README explicitly documents the caching contract: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [1](#0-0) .

However, the actual cache implementation stores and looks up entries using `req.Hash()` as the sole key [2](#0-1) , and the code comment for the cache struct itself states the hash is built from "method, URL, headers, body, workflowOwner" — `WorkflowID` is absent [3](#0-2) .

This is confirmed by the test suite itself, which explicitly asserts the broken invariant as expected behavior: "having different workflowID results in same Hash" — two requests with `WorkflowID` set to `"workflow-123"` and `"workflow-456"` respectively (identical method/URL) produce identical `Hash()` values [4](#0-3) . Only `WorkflowOwner`, not `WorkflowID`, actually affects the hash [5](#0-4) .

The cache is populated and read directly from unprivileged, node-originated HTTP action requests flowing through the gateway's `makeOutgoingRequest`/`HandleNodeMessage` path, where `CacheSettings.Store` and `CacheSettings.MaxAgeMs` (both attacker/workflow-controlled fields in the request) determine whether a response is cached and reused across subsequent calls [6](#0-5) .

### Impact Explanation
Because the cache key does not include `WorkflowID`, any two workflows that share the same `WorkflowOwner` (or in cases where owner scoping is weak/empty) and issue outbound HTTP requests with the same method/URL/headers/body will read and write the exact same cache entry, regardless of being logically distinct workflows. This directly contradicts the documented "Workflow Isolation" guarantee and can lead to:
- Cross-workflow response confusion: a workflow can receive a cached HTTP response that was actually fetched/produced in the context of a different workflow.
- Reduced/incorrect execution semantics for workflows that assume per-workflow HTTP action responses are isolated, since the actual endpoint call may be skipped (cache hit) and a stale or wrongly-scoped response returned instead.
- Because HTTP Action outbound requests can carry request-specific data (e.g., varying by workflow logic though sharing URL/method), this can silently corrupt workflow execution results across otherwise-unrelated workflow runs under the same owner.

This is analogous to the reported ERC20 issue in that the code's documented "supply"/isolation invariant is not actually enforced by the state-key generation logic, creating an inconsistency that downstream consumers (workflow executions, operators reading the README) will incorrectly trust.

### Likelihood Explanation
High reachability: any workflow node (unprivileged relative to the gateway) that issues `OutboundHTTPRequest` messages with `CacheSettings.Store=true` and `MaxAgeMs>0` triggers this caching path automatically — no special privilege is required beyond normal HTTP Action usage [7](#0-6) . The condition for collision (same owner, same method/URL/headers/body, different `WorkflowID`) is plausible in real deployments where multiple workflow instances/versions belonging to the same owner target the same external endpoint.

### Recommendation
Include `WorkflowID` in the value hashed by `OutboundHTTPRequest.Hash()` so the cache key genuinely enforces per-workflow isolation as documented, or explicitly update the documentation/comments to reflect that isolation is only owner-scoped (not workflow-scoped) if that is the intended design, and audit callers that assume workflow-level isolation.

### Proof of Concept
The existing test already demonstrates the flaw as passing (expected) behavior: [4](#0-3) 
```go
t.Run("having different workflowID results in same Hash", func(t *testing.T) {
    req1 := createTestRequest("GET", "https://example.com")
    req1.WorkflowID = "workflow-123"

    req2 := createTestRequest("GET", "https://example.com")
    req2.WorkflowID = "workflow-456"

    hash1 := req1.Hash()
    hash2 := req2.Hash()
    require.Equal(t, hash1, hash2, "Hash should be the same regardless of WorkflowID")
})
```
Given the `Fetch`/`Set` cache logic keyed purely by this hash [2](#0-1) , a workflow with `WorkflowID = "workflow-456"` making an identical outbound HTTP action request as a prior `"workflow-123"` execution (same owner, method, URL, headers, body) will receive `"workflow-123"`'s cached response instead of issuing a fresh request, confirming cross-workflow response reuse.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
