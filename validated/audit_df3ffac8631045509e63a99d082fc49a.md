### Title
Owner can break the `lastApr <= maxApr` invariant by lowering `maxApr` below the in-flight epoch APR, allowing over-cap (unbacked) minted interest - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setMaxApr` writes the new cap directly with no consistency check against the currently active `lastApr`. Because `setApr`/`setAprs`/`setAprsWithBuffer` are the only enforcers of `apr <= maxApr`, an honest owner can lower `maxApr` below the running epoch's scaled APR. The cap is then defeated for the in-flight epoch: `IdleCDOEpochVariant._stopEpoch` computes `expectedEpochInterest` from the stale, over-cap `lastApr`, and the `maxApr` sanity check on line 379 of `IdleCDOEpochVariant.sol` only applies to an explicit `_interest > 1` override — never to the expected-interest path. In minted-interest mode (`isInterestMinted == true`) the over-cap interest is fronted by minting strategy tokens that are only backed if the programmable borrower's own `borrowerApr` ledger settles enough; when `borrowerApr < lastApr` the excess minted tokens are unbacked and dilute tranche holders at withdrawal. This is the same bug class as the FlatMoney `setSkewFractionMax` finding: an owner setter that changes a bound without re-checking the current state against it, breaking the "current value <= bound" invariant mid-flight.

### Finding Description
- `setMaxApr` (`contracts/strategies/idle/IdleCreditVault.sol:198-200`) assigns `maxApr = _maxApr` unconditionally. There is no `require(lastApr <= _maxApr)` analog of `checkSkewMax(0)`.
- `setApr` (`IdleCreditVault.sol:225-235`) enforces `apr <= maxApr` only at the moment a *new* APR is written, so the check is one-directional: lowering the bound never revalidates the live rate.
- During `stopEpoch`, `expectedEpochInterest` is derived from the pre-change `lastApr`/`unscaledApr`, and `IdleCDOEpochVariant.sol:378-379` caps interest at `maxApr` only when the manager passes an `_interest > 1` override. A normal `stopEpoch(0, 0)` silently honors the over-cap rate.
- With `isInterestMinted`, `IdleCDOEpochVariant.sol:428-432` mints `_grossInterest` strategy tokens and settles via `IProgrammableBorrower.settleBorrowerInterest()`. The borrower's debt accrues at `borrowerApr` (`ProgrammableBorrower.setBorrowerApr`), an independent rate. If the owner lowered `maxApr` specifically because `borrowerApr` can't support the vault APR, the minted delta above the cap is unbacked and is socialized into tranche NAV.

### Impact Explanation
Any unprivileged tranche holder who deposits (or simply holds) during the over-cap epoch is paid interest priced at the old `lastApr` even though the owner intended to bound it at `maxApr`. In minted mode the excess is created as strategy tokens before cash settlement; if the programmable borrower's ledger (`borrowerPrincipal`/`borrowerInterestAccrued` at `borrowerApr`) settles less than `_grossInterest`, the unbacked mint inflates `getContractValue`/`virtualPrice`, letting withdrawing lenders redeem at a price not covered by real assets — insolvency/dilution borne by remaining LPs. Loss is quantified as `contractValue * (lastApr - maxApr) * epochDuration / YEAR` (scaled), accruing for the remainder of the in-flight epoch even though the cap was meant to prevent exactly this.

### Likelihood Explanation
Requires only an honest-owner sequencing mistake identical to the source report: owner submits `setMaxApr` to tighten risk mid-epoch while `lastApr` is already higher. No malicious privileged action is needed; the invariant is violated by design gap, not by the caller. Exploitation is passive — any lender in the running epoch benefits, and an alert lender can deposit during the buffer/after APR is known to capture over-cap yield.

### Recommendation
Validate the bound against live state inside `setMaxApr`, mirroring the report's `checkSkewMax(0)` fix:

```solidity
function setMaxApr(uint256 _maxApr) external onlyOwner {
    if (_maxApr != 0 && lastApr > _maxApr) revert NotAllowed();
    maxApr = _maxApr;
}
```

Additionally, apply the same `maxApr` bound to the `expectedEpochInterest` path in `_stopEpoch` (not just the `_interest > 1` override) so the cap is enforced on the rate actually honored at settlement.

### Proof of Concept
Foundry sketch (fork-style, mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testSetMaxAprBelowCurrentAprBreaksCap() external {
    IdleCreditVault cv = IdleCreditVault(address(strategy));

    // epoch running at scaled APR = lastApr (e.g. 20e18 cap, lastApr = 15e18)
    _depositWithUser(user1, 10000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    uint256 apr = cv.getApr(); // 15e18

    // honest owner tightens the cap below the live rate — no revert possible
    vm.prank(owner);
    cv.setMaxApr(apr / 2);
    assertGt(cv.getApr(), cv.maxApr()); // invariant apr <= maxApr broken

    // manager stops epoch with no override: expected interest uses stale lastApr
    // and bypasses the maxApr check at IdleCDOEpochVariant.sol:378-379
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true); // minted mode: over-cap interest is fronted as tokens
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // minted strategy tokens reflect lastApr, exceeding interestAt(maxApr) cap
    // -> unbacked amount = contractValue * (lastApr - maxApr) * dt / YEAR
    //    dilutes virtualPrice for non-withdrawing LPs
}
```
