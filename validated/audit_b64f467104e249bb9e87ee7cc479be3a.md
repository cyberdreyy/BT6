### Title
Cross-user response hijacking via `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each user's response callback in `h.savedCallbacks` keyed solely by the attacker-controllable `msg.Body.MessageId`, with no binding to the requester's `Sender`/signing key. An attacker can submit a second request with the same `MessageId` as a victim's in-flight request, overwriting the victim's callback entry so that the eventual DON response is delivered to the attacker instead of the victim.

### Finding Description
`MessageId` is a free-form string chosen by the caller and only constrained by length/null-suffix checks in `Message.Validate()` [1](#0-0) . It is not derived from the signer's address, so any two different signers can pick the identical `MessageId`.

In `HandleLegacyUserMessage`, after validating the payload the handler unconditionally writes to the shared map without checking for an existing entry or the previous entry's sender: [2](#0-1) 

When a DON node later responds, `HandleNodeMessage` only checks that the responding node's address matches (`msg.Body.Sender != nodeAddr`) [3](#0-2) , then dispatches by `MessageId` in `handleWebAPITriggerMessage`, which looks up and deletes `h.savedCallbacks[msg.Body.MessageId]` and forwards the response to whatever callback is currently stored there: [4](#0-3) .

Exploit flow:
1. Victim sends a `web_api_trigger` request with `MessageId = "X"`; gateway stores `savedCallbacks["X"] = victimCallback` and forwards the request to all DON members.
2. Before any node responds, attacker submits a request with the same `MessageId = "X"` (their own valid signature satisfies `Message.Validate()`); gateway overwrites `savedCallbacks["X"] = attackerCallback`.
3. When a node responds for the original ID `"X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `attackerCallback`, deletes the entry, and delivers the response there — the attacker receives the response intended for the victim while the victim's original `callback.Wait` call times out.

The code already contains an explicit acknowledgment that sender/allowlist validation for this path is missing: a test comment states "Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated" [5](#0-4) . No allowlist, per-sender scoping, or MessageId uniqueness enforcement exists anywhere else on this path (confirmed by review of `common.ValidatedRequestFromMessage`, `gateway.ProcessRequest`, and the handler itself).

### Impact Explanation
This is cross-user response confusion / request impersonation: an unauthenticated attacker can hijack another user's gateway response, causing attacker-controlled reception of data intended for the victim (e.g., HTTP trigger/target results, workflow execution outputs) and denial-of-service against the victim's request (silent timeout). This matches Chainlink's bounty class for unauthorized access to another user's data/response and cross-user isolation break in the Gateway.

### Likelihood Explanation
Exploitation requires only the ability to submit gateway HTTP requests with an attacker-chosen `MessageId` and a valid but arbitrary signing key — no privileges, allowlist membership, or special access are needed. The attacker must win a small race window (submit before the DON responds), which is feasible since DON round-trip times are on the order of the configured timeout (seconds), and the attack is trivially repeatable/scriptable by guessing or observing predictable/short MessageIds, or by flooding many candidate MessageIds.

### Recommendation
Scope `savedCallbacks` entries by both `MessageId` and the requester's verified `Sender`/signature (e.g., key by `(Sender, MessageId)` tuple), and/or reject a `HandleLegacyUserMessage` call that would overwrite an existing unexpired `MessageId` entry (return a collision error to the second caller instead of silently overwriting). Additionally, tie the response delivered by `handleWebAPITriggerMessage` back to the original requester identity to prevent delivery mismatch even if MessageId collisions occur.

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Create two distinct private keys (`victimKey`, `attackerKey`).
2. Build `victimMsg` with `MessageId = "X"`, signed with `victimKey`; call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`.
3. Before delivering any node response, build `attackerMsg` with the same `MessageId = "X"`, signed with `attackerKey`; call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)`.
4. Assert `handler.savedCallbacks["X"]` now stores the callback registered under `attackerCallback`, not `victimCallback` (inspect internal map, or infer via behavior).
5. Simulate a DON node response for `MessageId="X"` via `handler.HandleNodeMessage(ctx, resp, nodeAddr)`.
6. Assert `attackerCallback.Wait(ctx)` returns the response payload while `victimCallback.Wait(ctx)` times out/never resolves — demonstrating the victim's response was delivered to the attacker.

```go
func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
```
