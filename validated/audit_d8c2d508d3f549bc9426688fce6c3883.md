### Title
Unfunded instant-withdraw receipts from epochs older than the default epoch are excluded from `defaultPendingClaimBasis`, inflating `defaultRecoveryPrice` and draining `defaultRecoveryReserve` so later claimants are permanently frozen - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`defaultPendingClaimBasis()` only adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — to the default claim basis, while `pendingInstantWithdraws` (the aggregate unfunded instant queue) can span multiple epochs. After `finalizeDefaultRecovery`, instant receipts requested in an epoch older than `defaultRecoveryEpoch` are never cleared by `_claimDefaultedInstantWithdrawRequest` (which only reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`), so they fall through to `_transferFundedClaim`, which reverts against the isolated reserve. At the same time, the understated `totalBasis` produces an inflated `defaultRecoveryPrice`, overpaying earlier claimants and leaving insufficient reserve for the rest.

### Finding Description
The dnsmasq bug class (stale/out-of-bounds read yielding denial of service) maps to stale-epoch reads in the withdrawal accounting: the code reads the wrong epoch slot when computing default claim basis.

- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and bumps `pendingInstantWithdraws` (IdleCreditVault.sol:356-375).
- `collectInstantWithdrawFunds` can fund only part of the queue, so `pendingInstantWithdraws != 0` can persist across `stopEpoch`/`epochNumber` increments (IdleCreditVault.sol:398-403).
- On default, `defaultPendingClaimBasis` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — i.e. only receipts opened during the *default* epoch. Old-epoch unfunded instant receipts contribute to `pendingInstantWithdraws != 0` (so `defaultInstantWithdrawsFinalized = true` and `_defaultPrefundedInstantReserve` subtracts the full `pendingInstant`) but are absent from the claim basis (IdleCreditVault.sol:644-649, 696, 716-723).
- `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`; an old-epoch receipt keeps `instantWithdrawsRequests[_user] > 0`, so `claimInstantWithdrawRequest` then calls `_transferFundedClaim`, which reverts because `balance - reserve < amount` once the reserve holds the whole balance (IdleCreditVault.sol:842-856, 897-906).

Resulting broken invariants: (1) recovery price is computed over too small a basis (`recoveryPrice = reserveAmount / totalBasis` with `totalBasis` missing old-epoch instant claims), overpaying every claimant that does claim; (2) reserve solvency — `defaultRecoveryReserve` decrements per claim and can hit zero before all eligible claims are paid; (3) "one receipt one payout" — old-epoch instant receipt holders are permanently frozen.

### Impact Explanation
Two concrete harms in the `defaulted/finalized` phase:
- Recovery-price inflation: with `instantBasis(actual) = instantWithdrawClaimsByEpoch[defaultEpoch] + oldEpochInstant`, omitting the old part raises `defaultRecoveryPrice` above the fair ratio, so each defaulted-epoch claimant and each active LP's `activeFinalNAV` is overpaid relative to entitlement, and the fixed `reserveAmount` is exhausted early — later claimants' `safeTransfer`s revert (direct insolvency of unclaimed yield).
- Permanent freezing: a user whose instant request was pending since a prior epoch can never claim — `_claimDefaultedInstantWithdrawRequest` returns 0 for them and `_transferFundedClaim` reverts against the reserve guard.

### Likelihood Explanation
Requires the (honest) borrower to leave `pendingInstantWithdraws` partially unfunded across at least one epoch boundary, then a borrower default and `finalizeDefaultRecovery` — all driven by honest privileged actors, with the victim being any unprivileged user who opened an instant request in an earlier epoch. Partial instant funding is an explicitly designed-for path (prefunded reserve logic exists precisely because it happens), so the precondition is realistic in stressed pools.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, use the full unfunded instant queue rather than only the current-epoch bucket — e.g. track a global `totalInstantWithdrawClaims` (or add `pendingInstantWithdraws`-denominated basis) instead of `instantWithdrawClaimsByEpoch[epochNumber]`; symmetrically, `_claimDefaultedInstantWithdrawRequest` should clear a user's entire unfunded instant basis (`instantWithdrawsRequests[_user]` capped at what was unfunded), not only `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`.

### Proof of Concept
Foundry fork sketch (pool in `instant` mode):
1. Epoch N running: user A calls `requestInstantWithdraw(100, A)` via CDO. Borrower funds nothing → `pendingInstantWithdraws = 100`, `instantWithdrawClaimsByEpoch[N] = 100`.
2. `stopEpoch` → `epochNumber = N+1`. Epoch N+1: user B calls `requestInstantWithdraw(100, B)`; user C has a normal `requestWithdraw(300)` (also unfunded). `pendingInstantWithdraws = 200`, `instantWithdrawClaimsByEpoch[N+1] = 100`.
3. Borrower defaults; CDO calls `finalizeDefaultRecovery(recovered, source)` with `recovered = 200`.
4. `defaultPendingClaimBasis = 300 + 100 = 400` (A's 100 excluded). `totalBasis = activeBasis + 400`, `recoveryPrice = reserve/totalBasis` — inflated vs. fair basis of 500.
5. B and C claim, each overpaid; `defaultRecoveryReserve` drains below entitlement. A calls `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` clears 0 (A's basis is in epoch N, not `defaultRecoveryEpoch = N+1`), then `_transferFundedClaim` reverts (`balance - reserve < 100`).
6. Assert: `defaultRecoveryReserve` is exhausted before all claims and A's receipt is permanently frozen — revert `NotAllowed`.
