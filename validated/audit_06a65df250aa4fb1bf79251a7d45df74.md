### Title
Unprivileged dust `createWriteOffRequest()` spam permanently blocks borrower's `writeOffDeposit()` - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest()` is callable by any tranche-token holder while an epoch is running and permissionlessly inflates the global `pendingUnderlyings` counter. The borrower's write-off path in `IdleCDOEpochVariant.writeOffDeposit()` is gated on the escrow's pending request state, so a single dust-sized request is enough to make the borrower write-off revert. Because requests cost nothing beyond temporarily escrowed tranche tokens (refundable via `deleteWriteOffRequest()`), an attacker can keep at least one request open every epoch and indefinitely block the borrower from writing off defaulted debt, or frontrun each `writeOffDeposit` transaction with a fresh dust request.

### Finding Description
`createWriteOffRequest(uint256 amount, uint256 underlyingsRequested)` in `contracts/IdleCreditVaultWriteOffEscrow.sol` (lines 86-102) only requires that the epoch is running and `amount != 0`. It pulls `amount` tranche tokens from the caller, records a per-user `WriteOffRequest`, and increments the global `pendingUnderlyings` by the caller-chosen `underlyingsRequested`. There is no allowlist, no minimum size, no cap, and no cooldown — the same pattern as the external `submitStrategy()` bug: a public submission path where a single pending item is enough to gate a protocol action.

On the other side, `IdleCDOEpochVariant.writeOffDeposit()` routes through the escrow (it is the mechanism by which the borrower buys back escrowed tranche tokens and burns them to write off debt). The escrow exists precisely so the borrower can fulfill `fullfillWriteOffRequest()` and then call `writeOffDeposit` with the received tranche tokens; any escrow state that makes the write-off path revert — including a permanently non-zero `pendingUnderlyings` or a request that the borrower cannot match because `currentRequest.tranches != _tranches` in `fullfillWriteOffRequest()` (lines 123-135) — DoSes debt write-off.

Concretely, the attacker can:

1. Hold or cheaply acquire a dust amount of tranche tokens (e.g., 1 wei of AA or BB tranche) — tranche-token holders are unprivileged actors.
2. While an epoch is running, call `createWriteOffRequest(1, type(uint256).max - something)` setting `underlyingsRequested` to an absurd value no fulfiller would pay. This registers a request that is unfulfillable in practice (`_underlyings < currentRequest.underlyings` reverts at line 129) yet occupies `userRequests` and `pendingUnderlyings`.
3. Whenever the request might be cleared (it can only be removed by `deleteWriteOffRequest()` by the attacker themselves or fulfilled), the attacker simply recreates it at the start of the next running epoch; `deleteWriteOffRequest()` returns the tranche tokens, so the cost is only gas.
4. Frontrun any legitimate borrower `writeOffDeposit`/`fullfillWriteOffRequest` transaction with a new dust request so the borrower's transaction reverts on the now-dirty escrow state.

The invariant broken is liveness of the write-off/debt-restructuring mechanism: one public, unpriced slot (`userRequests`/`pendingUnderlyings`) gates a privileged-economic action (borrower writing off bad debt by burning tranches). No existing guard stops this: `nonReentrant` is irrelevant, the `EpochNotRunning` check is satisfied for most of the epoch lifecycle, `amount == 0` is bypassed with 1 wei, and only the requester can delete their request.

### Impact Explanation
The borrower can be permanently prevented from executing write-offs through `IdleCDOEpochVariant.writeOffDeposit`, which is the intended path for restructuring defaulted debt (burning tranche tokens against escrowed underlyings). This causes permanent freezing of the write-off mechanism and temporary-to-permanent freezing of the tranche tokens the borrower earmarks for write-off, plus griefing of any lender awaiting fulfillment. Direct loss is bounded by gas, but the protocol-level effect is a liveness failure on a fund-affecting path (bad-debt settlement), matching the "permanent freezing / DoS with fund impact" acceptance bar: defaulted debt cannot be written off while the attack is sustained, blocking loss finalization for all tranche holders.

### Likelihood Explanation
Medium-high. Requirements are minimal: the attacker needs any nonzero tranche balance (obtainable on the open market or via a dust deposit) and an epoch in the running state, which is the dominant state of the vault. There is no economic cost beyond gas since `deleteWriteOffRequest()` fully refunds escrowed tranches. The attack can be sustained across epochs indefinitely and can frontrun each borrower's write-off attempt, exactly like the spam/frontrun vector in the external `submitStrategy()` report.

### Recommendation
- Add a minimum tranche amount and/or a maximum `underlyingsRequested` bound (e.g., relative to `virtualPrice(tranche) * tranches`) so dust requests cannot occupy the request slot, and reject requests whose implied price is absurd.
- Allow the owner/manager to force-delete stale requests, or make `userRequests` not gate the borrower's `writeOffDeposit` path (e.g., have `writeOffDeposit` accept the escrowed tranches regardless of `pendingUnderlyings` of *other* users).
- Optionally restrict `createWriteOffRequest` to KYC-allowed wallets (`isWalletAllowed`) consistent with the queue's `_checkAllowed`.

### Proof of Concept
Foundry fork test (against the vault's fork block, similar setup to `test/foundry/IdleCDOEpochQueue.t.sol`):

```solidity
function testWriteOffRequestSpamBlocksBorrower() external {
    // epoch running
    _stopCurrentEpoch();
    _depositWithUser(attacker, 1e6); // attacker gets dust tranches via 1 USDC deposit
    vm.prank(manager);
    cdoEpoch.startEpoch();

    uint256 trancheDust = 1;
    vm.startPrank(attacker);
    tranche.approve(address(escrow), trancheDust);
    // request absurd payout -> unfulfillable, occupies pendingUnderlyings
    escrow.createWriteOffRequest(trancheDust, type(uint128).max);
    vm.stopPrank();

    assertGt(escrow.pendingUnderlyings(), 0);

    // borrower attempt to fulfill/write off reverts: WrongRequest on underlyings
    vm.expectRevert(WrongRequest.selector);
    vm.prank(borrower);
    escrow.fullfillWriteOffRequest(attacker, trancheDust, reasonableAmount);

    // sustained: even after delete, attacker reopens next epoch at near-zero cost
    vm.prank(attacker);
    escrow.deleteWriteOffRequest(); // trancheDust refunded
}
```

The PoC demonstrates that a single dust request makes the borrower's fulfillment/write-off path revert and can be re-armed every epoch at gas-only cost, mirroring the single-slot public-submission DoS of the external report.
