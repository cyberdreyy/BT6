### Title
Withdrawal-claim entrypoints skip the `isWalletAllowed` Keyring gate that guards every other user path - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` enforces the Keyring KYC check (`isWalletAllowed`) on all state-changing user entrypoints — `_deposit`, `depositDuringEpoch`, and `requestWithdraw` — but the two disbursement handlers `claimWithdrawRequest` and `claimInstantWithdrawRequest` dispatch straight into `IdleCreditVault` without it. This mirrors the fastify bug class: a protected handler is reachable through an alternate route that skips its declared preHandler, so the access-control hook attached to the vault's lifecycle never runs for the claim path.

### Finding Description
The canonical user flow applies `isWalletAllowed(msg.sender)` in three places:

- `IdleCDOEpochVariant._deposit` (contracts/IdleCDOEpochVariant.sol:645) — `_checkNotAllowed(!isWalletAllowed(msg.sender))`
- `IdleCDOEpochVariant.depositDuringEpoch` (contracts/IdleCDOEpochVariant.sol:668)
- `IdleCDOEpochVariant.requestWithdraw` (contracts/IdleCDOEpochVariant.sol:743)

But the payout handlers omit it entirely:

```solidity
// contracts/IdleCDOEpochVariant.sol:967-979
function claimWithdrawRequest() external {
  IdleCreditVault(strategy).claimWithdrawRequest(msg.sender);
}

function claimInstantWithdrawRequest() external {
  _checkNotAllowed(!allowInstantWithdraw);
  IdleCreditVault(strategy).claimInstantWithdrawRequest(msg.sender);
}
```

`isWalletAllowed` (contracts/IdleCDOEpochVariant.sol:984-987) is a live check against the external `IKeyring.checkCredential(keyringPolicyId, _user)` registry, so its result can change *after* a request is created. The strategy-side handlers (`IdleCreditVault.claimWithdrawRequest` / `claimInstantWithdrawRequest`, contracts/strategies/idle/IdleCreditVault.sol:301-314 and 380-393) only check epoch timing, receipt bookkeeping, and `_onlyIdleCDO` — they burn the caller's receipt and `safeTransfer` underlying with no credential re-validation. Strategy-token receipts are non-transferable (`IdleCreditVault._transfer` reverts unless `msg.sender == idleCDO`, contracts/strategies/idle/IdleCreditVault.sol:939-942), so the receipt holder cannot route the claim through an allowed intermediary — but conversely, nothing stops the (now-disallowed) receipt holder from claiming directly.

Attack sequence in the **stopped/buffer** or **defaulted-finalized** phase:

1. Wallet W passes Keyring, calls `requestWithdraw` — the KYC hook runs and a receipt is minted to W (strategy tokens, `instantWithdrawsRequests[W]` / `withdrawsRequestsByEpoch[W][epoch]`).
2. Keyring revokes W's credential (sanctions, policy rotation, expired KYC) — or W's status simply lapses.
3. W calls `claimInstantWithdrawRequest` (once `allowInstantWithdraw`) or `claimWithdrawRequest` (once `epochNumber > lastWithdrawRequest[W]`, or immediately after pool close/`finalizeDefault` since `epochEndDate == 0` skips the wait check at `IdleCreditVault.sol:326`).
4. The CDO dispatches to the strategy handler without ever re-running `isWalletAllowed`, and W receives underlying from `defaultRecoveryReserve` / funded balance via `_transferFundedClaim` / `_transferDefaultRecovery` (contracts/strategies/idle/IdleCreditVault.sol:897-917).

The same gap exists for `IdleCDOEpochQueue.claimDepositRequest` / withdrawal claims routed via the queue (contracts/IdleCDOEpochQueue.sol:373-389), which pay out based on `userDepositsEpochs`/`epochWithdrawPrice` with no credential check on the claiming EOA.

### Impact Explanation
Broken invariant: **access control** — the protocol's declared wallet gate is bypassed for every disbursement. A wallet that the Keyring policy currently rejects can still pull funded underlyings (including from the isolated `defaultRecoveryReserve`) out of the vault. Quantified loss: up to the disallowed wallet's full claim basis — every pending normal, APR0, instant, loss-adjusted, and post-default receipt held by a revoked wallet is payable despite the gate; on a defaulted pool, those payouts directly deplete `defaultRecoveryReserve` ahead of compliant claimants at the same `defaultRecoveryPrice`. This is exactly the fastify pattern: the auth hook guards the "create" route but the shared payout dispatcher serves the request without it.

### Likelihood Explanation
Requires only that a receipt holder loses (or never regains) Keyring standing between request and claim — a routine operational event for credential-gated pools, not an edge case requiring privileged misbehavior. No privileged role acts maliciously; the gap is a missing check in unprivileged code paths. It is limited to funds the wallet is already owed, so the loss is to the pool's compliance perimeter and, under default recovery, a first-come drain of the shared reserve by wallets the policy has excluded.

### Recommendation
Add `_checkNotAllowed(!isWalletAllowed(msg.sender))` to `claimWithdrawRequest` and `claimInstantWithdrawRequest` in `IdleCDOEpochVariant`, and apply the CDO's `isWalletAllowed` check in `IdleCDOEpochQueue.claimDepositRequest` and its withdrawal-claim path. If post-revocation claims are *intended* policy, document that the gate is request-time-only; otherwise the check must run at payout time where the funds actually move.

### Proof of Concept
```solidity
// Foundry fork-style PoC against a deployed IdleCDOEpochVariant + IdleCreditVault.
// Assumes: keyring set via setKeyringParams(keyring, policyId), epoch machinery as in
// test/foundry/IdleCreditVault.t.sol helpers (_startEpochAndCheckPrices etc.).

function testClaimBypassesKeyringRevocation() external {
    // 1. attacker deposits + requests withdraw while KYC'd
    vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector, policyId, attacker), abi.encode(true));
    vm.startPrank(attacker);
    uint256 minted = cdoEpoch.depositAA(10_000e6);
    // run epoch 0, stop with lower APR to enable instant requests
    vm.stopPrank();
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, apr / 4, expectedFundsEndEpoch());

    vm.prank(attacker);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche)); // KYC check passes

    // 2. epoch starts; funds for instant requests collected (or pool closed / defaulted+finalized)
    _startEpochAndCheckPrices(1);   // allowInstantWithdraw = true when cash covers requests
    // -- OR: warp past instantWithdrawDelay and call getInstantWithdrawFunds()

    // 3. Keyring revokes the attacker
    vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector, policyId, attacker), abi.encode(false));

    // sanity: attacker can no longer call any gated entrypoint
    vm.prank(attacker);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.requestWithdraw(1, address(AAtranche));

    // 4. ...but the claim handler pays out anyway — no isWalletAllowed on this route
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();   // succeeds despite revoked credential
    assertEq(underlying.balanceOf(attacker) - balPre, requested);
    assertEq(strategyToken.balanceOf(attacker), 0);
}
```

The same trace works through `claimWithdrawRequest` after `epochNumber` advances (or immediately when `epochEndDate == 0` post-close/post-`finalizeDefault`), and through `IdleCDOEpochQueue.claimDepositRequest` for queue-routed receipts.
