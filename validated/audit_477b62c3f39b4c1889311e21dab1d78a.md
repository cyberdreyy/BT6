### Title
Attached deposit is permanently burnt (not refunded) when `action_deterministic_state_init` fails with `LackBalanceForState` - ([File: runtime/runtime/src/deterministic_account_id.rs])

### Summary
When `check_storage_stake` reports `LackBalanceForState` because `action.deposit < missing_amount`, `action_deterministic_state_init` sets `result.result` to an `Err` and returns `Ok(())` on line 79 without ever crediting `action.deposit` to the account or emitting a `Receipt::new_balance_refund`. Unlike the success path (lines 59-72, 87-91), which explicitly refunds any unused portion of `action.deposit`, the failure path silently drops the entire deposit with no accounting anywhere in state or in outgoing receipts.

### Finding Description
The function computes `deposit_refund` from `action.deposit` only in the two `Ok`/`LackBalanceForStorageStaking` arms of the `match` on `check_storage_stake` [1](#0-0) . In the branch where `missing_amount > action.deposit` (i.e. the deposit is insufficient by as little as 1 yoctoNEAR), the code sets the action error and returns immediately: [2](#0-1) 

No code path in this branch touches `account.set_amount`, and no `Receipt::new_balance_refund` is constructed — that only happens later, guarded by the `deposit_refund > Balance::ZERO` check that is unreachable from this branch because of the early `return Ok(())` [3](#0-2) . The `action.deposit` value carried by the receipt (already debited from the sender when the outgoing receipt was created) is therefore neither credited to the receiving deterministic account nor refunded to the balance-refund receiver, and disappears from the accounted token supply for that receipt.

By contrast, the success paths (full refund when no additional storage is needed, or partial refund of `action.deposit - missing_amount` when some is needed) both correctly compute and emit a refund receipt. The asymmetry indicates the `LackBalanceForState` arm is missing the equivalent "refund the deposit that could not be used" logic.

### Impact Explanation
This is a token-loss bug (deflationary bug), not user-fund theft from a third party: the deposit lost belongs to whoever attached it to the `DeterministicStateInitAction` (the transaction signer/relayer), and it is that same party's funds that get permanently and unrecoverably burnt instead of refunded. Any ordinary user (not necessarily malicious) who under-provisions the deposit for a deterministic-account state-init transaction — e.g. because client-side estimation of `missing_amount` is imprecise, or because storage cost parameters are updated between quoting and execution — will have their entire deposit vanish rather than be refunded, matching a "token inflation or loss" bounty category. An attacker with only ordinary client privileges can trivially and repeatably trigger this against their own transactions, but it also affects innocent users who don't perfectly estimate their deposit.

### Likelihood Explanation
Trivial and fully within reach of an unprivileged client: craft a receipt containing a `DeterministicStateInitAction` with `action.deposit = missing_amount - 1` yoctoNEAR (attacker fully controls the deposit field and knows/can compute `missing_amount` from public storage-staking parameters and `state_init` size). No signature, nonce, access-key, or gas-metering check prevents submitting an under-funded deposit — those checks validate the transaction's authenticity/affordability, not that the attached deposit exceeds the dynamically-computed storage-staking requirement, which is only checked inside this function. The bug is deterministic and repeatable on every call with an insufficient deposit.

### Recommendation
In the `Err(StorageStakingError::LackBalanceForStorageStaking(missing_amount)) if missing_amount > action.deposit` branch, before returning, push a `Receipt::new_balance_refund(receipt.balance_refund_receiver(), action.deposit)` (guarded by `action.deposit > Balance::ZERO`) so the unused deposit is returned to the sender, mirroring the accounting done in the success branches.

### Proof of Concept
Unit test in `runtime/runtime/src/deterministic_account_id.rs` (or a runtime/test-loop integration test):
1. Construct an `ApplyState`/`TrieUpdate` and a `DeterministicStateInitAction` with a `state_init` whose storage requirement yields a known `missing_amount` (e.g. via `check_storage_stake` on an account created by `create_deterministic_account`).
2. Set `action.deposit = missing_amount - 1`.
3. Call `action_deterministic_state_init` with `maybe_account = None` and a `receipt` with a defined `balance_refund_receiver()`.
4. Assert:
   - `result.result` is `Err(ActionErrorKind::LackBalanceForState { .. })`.
   - `result.new_receipts` is empty (no `Receipt::new_balance_refund` pushed).
   - `account.amount()` (the freshly-inserted account) remains `0`, i.e. the deposit was neither credited nor refunded — confirming `action.deposit` yoctoNEAR (100% of the attached deposit) is unaccounted for and effectively burnt.

        Ok(_) => {
            // no additional storage needed, refunding all
            action.deposit
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(missing_amount)) => {
            if missing_amount <= action.deposit {
                // use exactly as much as needed and refund the rest
                let new_balance = safe_add_balance(account.amount(), missing_amount)?;
                account.set_amount(new_balance);
                action
                    .deposit
                    .checked_sub(missing_amount)
                    .expect("just checked missing_amount <= action.deposit")
            } else {
                result.result = Err(ActionErrorKind::LackBalanceForState {
                    account_id: account_id.clone(),
                    amount: missing_amount,
                }
                .into());
                return Ok(());
            }
        }
        Err(StorageStakingError::StorageError(err)) => {
            return Err(RuntimeError::StorageError(StorageError::StorageInconsistentState(err)));
