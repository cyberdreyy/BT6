### Title
Missing zero-price validation lets any fulfiller take escrowed tranche tokens without paying - (File: `contracts/IdleCreditVaultWriteOffEscrow.sol`)

### Summary
`createWriteOffRequest` validates only that the deposited tranche amount is nonzero, while `fullfillWriteOffRequest` accepts a fulfilment whenever the supplied underlying amount is at least the stored request. [1](#0-0) [2](#0-1)  Therefore, a request accidentally created with `underlyingsRequested == 0` can be fulfilled atomically by an arbitrary EOA for zero underlying, transferring all escrowed tranche tokens to the attacker. [3](#0-2) 

### Finding Description
The write-off escrow is intended to exchange a lender's tranche tokens for the amount of underlying specified in the request. [4](#0-3)  During a running epoch, a tranche holder can escrow `amount` tokens and store an arbitrary `underlyingsRequested` value; the function rejects a zero tranche amount but does not reject a zero underlying amount. [5](#0-4) 

Fulfilment is permissionless and only requires `_tranches == currentRequest.tranches` and `_underlyings >= currentRequest.underlyings`. [6](#0-5)  For a zero-price request, passing `_underlyings = 0` passes this validation, performs a zero-value `transferFrom`, calculates a zero exit fee, sends zero underlying to the seller, and sends the full escrowed tranche balance to the caller. [7](#0-6) 

This is the credit-vault analogue of the report's lax input validation: a malformed user-supplied value is accepted into a privileged asset-release path and interpreted as an executable order rather than rejected as invalid. [8](#0-7) 

### Impact Explanation
An unprivileged fulfiller can acquire the entire tranche balance escrowed under a zero-price request without paying underlying to the lender. [3](#0-2)  A KYC-passing attacker can subsequently request withdrawal through the CDO, while any attacker can retain or transfer the tranche tokens if token transfers are unrestricted. [9](#0-8) 

The loss is the full underlying redemption value of the escrowed tranche tokens, less only gas costs. [10](#0-9)  For example, a malformed request escrowing `10_000e18` tranche tokens can be cleared for `0` underlying rather than a positive requested amount. [1](#0-0) 

### Likelihood Explanation
The exploit requires a lender or an integration to create a request with `underlyingsRequested == 0`, so it depends on malformed user input rather than purely attacker-controlled state. [1](#0-0)  Once such a request exists, exploitation is atomic, permissionless, and does not require borrower, owner, manager, or KYC privileges. [11](#0-10) 

The existing validation explicitly distinguishes an empty tranche deposit from a wrong fulfilment but omits the corresponding minimum-price check, making this a concrete missing-validation defect rather than a theoretical escrow disagreement. [12](#0-11) [2](#0-1) 

### Recommendation
Reject zero-price write-off requests at creation by requiring `underlyingsRequested != 0`. [13](#0-12)  As defense in depth, also require `_underlyings != 0` in `fullfillWriteOffRequest` so any legacy zero-price request cannot be executed without the owner first rescuing or deleting it. [2](#0-1)

```solidity
function testPocZeroPriceRequestFulfilledWithoutPayment() external {
    address attacker = makeAddr("zeroPriceBuyer");
    uint256 trancheAmount = 10_000e18;

    // Victim creates a malformed request asking for zero underlying.
    vm.prank(LP);
    escrow.createWriteOffRequest(trancheAmount, 0);

    uint256 lpUnderlyingBefore = underlying.balanceOf(LP);
    uint256 attackerTrancheBefore = tranche.balanceOf(attacker);

    // Arbitrary attacker fulfils the request with no token approval or payment.
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, trancheAmount, 0);

    (uint256 remainingTranches, uint256 remainingUnderlyings) =
        escrow.userRequests(LP);

    assertEq(remainingTranches, 0, "request was not cleared");
    assertEq(remainingUnderlyings, 0, "zero-price ask was not cleared");
    assertEq(escrow.pendingUnderlyings(), 0, "pending accounting mismatch");

    assertEq(
        underlying.balanceOf(LP),
        lpUnderlyingBefore,
        "victim received underlying"
    );
    assertEq(
        tranche.balanceOf(attacker) - attackerTrancheBefore,
        trancheAmount,
        "attacker did not receive escrowed tranches"
    );
}
```

```text
  /// @notice create a write-off request by depositing tranche tokens and setting the amount of underlyings requested
  /// @param amount of tranche tokens to deposit
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  /// @notice fulfill the write-off request by buying the escrowed tranche tokens
  /// @param _user address of the user that made the write-off request
  /// @param _tranches amount of tranche tokens to transfer
  /// @param _underlyings amount of underlyings to transfer
  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
