### Title
Divergent duplicate-tenure-block detection (`get_last_globally_accepted_block` in v1 vs `get_last_signed_block` in v2) allows a v1-consensus signer to countersign a second, conflicting tenure-change block for the same tenure - ([File: stacks-signer/src/chainstate/v1.rs, stacks-signer/src/chainstate/v2.rs])

### Summary
`GlobalStateView::validate_tenure_change_payload` (v2) rejects a tenure-change proposal for a tenure it has already *locally or globally* signed a block in, via `SignerDb::get_last_signed_block` [1](#0-0) . `SortitionsView::validate_tenure_change_payload` (v1) only rejects if a block in that tenure was already *globally* accepted, via `SignerDb::get_last_globally_accepted_block` [2](#0-1) . If a v1 signer has locally (but not yet globally) signed block A for tenure T, it will happily countersign a second, different tenure-change block B for the same tenure T — a same-signer equivocation that a v2 signer, using the same signerdb, would correctly reject.

### Finding Description
The equality that must hold for signer safety is: *for a given tenure, once a signer has signed one block, it must never sign a second, conflicting block for that same tenure* (no equivocation). This equality is enforced differently by the two chainstate implementations:

- v2's `validate_tenure_change_payload` calls `signer_db.get_last_signed_block(&block.header.consensus_hash)`, which returns a block if it is in any signed state (locally accepted OR globally accepted) [3](#0-2) .
- v1's `validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, which only returns a block once the network as a whole has confirmed it, ignoring a block the signer itself has already locally signed [4](#0-3) .

Root cause: this is not the shared `check_tenure_change_confirms_parent`/`check_latest_block_in_tenure` path (that logic lives once in `SortitionData` in `stacks-signer/src/chainstate/mod.rs` and is identical for both versions [5](#0-4) ). The divergence is in the *duplicate-block-in-current-tenure* guard that each version implements independently at the bottom of its own `validate_tenure_change_payload`. v1 was written to only guard against a globally-accepted duplicate; v2 tightened this to also catch a merely-locally-signed duplicate.

Exploit flow for a v1-consensus signer:
1. Attacker wins one miner slot for tenure T and gossips a first tenure-change block A. A v1 signer signs it, moving it to `BlockState::Signed`/locally accepted, but the network as a whole has not yet reached the global-acceptance threshold (e.g., other signers are slow, or a bitcoin/stacks tip race).
2. Attacker crafts a second, different tenure-change proposal B for the same tenure T (same `prev_tenure_consensus_hash`, different content/`signer_signature_hash`), and gossips it as a `BlockProposal` before A reaches global acceptance.
3. On the v1 signer, `get_last_globally_accepted_block(T)` still returns `None` (A is only locally accepted), so the `DuplicateBlockFound`-style guard does not fire, and — provided the other, version-agnostic checks (miner pkh, bitvec, parent-tenure choice, timeout) pass — the signer proceeds to sign B as well.
4. A v2 signer presented with the same B correctly detects A via `get_last_signed_block` and rejects B with `RejectReason::DuplicateBlockFound`.

This produces the exact broken equality the question describes: the same crafted proposal B is `Ok` under v1's rule set and `Err(DuplicateBlockFound)` under v2's, off the identical signerdb fixture and node state.

### Impact Explanation
This breaks the "a signer never signs two conflicting blocks for the same tenure" safety property for any signer still running the v1 rule set. If enough v1-weighted signers hold this behavior simultaneously with a stalled global-acceptance vote on A (e.g., a mixed-protocol-version reward cycle during an upgrade window), the aggregate signature set could accumulate valid signatures split across A and B for the same tenure, i.e., two different blocks for the same consensus hash each obtaining part of the required weighted threshold. That matches "Critical — a signer signing an invalid/conflicting block (chain safety)". The bug is deterministic and repeatable for every v1-consensus signer as long as A remains only locally accepted when B is gossiped.

### Likelihood Explanation
Preconditions required: (a) a v1-consensus signer that has already locally signed a first tenure-change block A for a tenure but has not yet observed/produced global acceptance of A, and (b) the attacker's ability to get a second tenure-change block B for the same tenure gossiped as a `BlockProposal` before A globally confirms. Both are achievable by an unprivileged party controlling a single miner slot: winning one sortition lets them produce the initial tenure-change block, and — since Stacks allows a still-valid miner to re-propose/replace an unconfirmed tenure-start block — craft and gossip a second variant. No majority of signers, no compromised keys, and no node/RPC exploitation are needed; only crafting proposals and normal StackerDB gossip that a signer already consumes. This requires a real mixed-version deployment window (v1 signers coexisting with v2 signers, i.e. before/at the `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` boundary) to produce the split-vote outcome; that window is a real, if temporary, operational condition during signer-set upgrades.

### Recommendation
Change v1's `validate_tenure_change_payload` to use the same "already signed" semantics as v2: replace `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` with `signer_db.get_last_signed_block(&block.header.consensus_hash)` (or equivalent) so that a locally-signed-but-not-yet-globally-accepted block in the current tenure also blocks a competing tenure-change proposal, matching v2's stricter guard. Alternatively, hoist this duplicate check into the shared `SortitionData` path in `stacks-signer/src/chainstate/mod.rs` so both versions can never diverge on this rule again.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests/` (mirroring existing fixtures in `v1.rs`/`v2.rs` tests):
1. Build a signerdb fixture and insert block A for tenure T with `BlockState::Signed` (locally accepted, `signed_self` set, not `GloballyAccepted`).
2. Construct block B: a `NakamotoBlock` with a `TenureChangePayload` whose `prev_tenure_consensus_hash` matches A's parent, and `consensus_hash == T`, but a distinct body producing a different `signer_signature_hash`.
3. Call `SortitionsView::check_proposal` (v1) with this fixture and assert `Ok(())` is returned (v1 does not detect the duplicate because `get_last_globally_accepted_block(T)` is `None`).
4. Call `GlobalStateView::check_proposal` (v2) with the identical fixture/block B and assert `Err(RejectReason::DuplicateBlockFound)` is returned (v2 detects it via `get_last_signed_block(T)` returning A).
5. Assert the two results differ (`v1_result.is_ok() != v2_result.is_ok()`), proving the claimed equality/divergence directly.

    /// It checks the local DB first, and if the block is not present in the local DB, it asks the
    /// Stacks node for the highest processed block header in the given tenure (and then caches it
    /// in the DB).
    ///
    /// The rationale here is that the signer DB can be out-of-sync with the node.  For example,

        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,

            block,
            signer_db,
            client,
            tenure_last_block_proposal_timeout,
            reorg_attempts_activity_timeout,
        )
