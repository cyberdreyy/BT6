### Title
Malicious operator can permanently freeze a staker's unlocked stake by rejecting direct APT transfers - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract.move` pays out both operator commission and staker withdrawals from a single, shared `distribution_pool` inside `distribute_internal`. Every payout path (`distribute`, `unlock_stake`, `request_commission`, `switch_operator`) first forces a full `distribute_internal` call that atomically loops over **all** shareholders in the pool (staker + operator/beneficiary) and pays each one with `aptos_account::deposit_coins`. If any single deposit in that loop aborts, the whole transaction reverts — including the legitimate staker's own withdrawal in the same call.

### Finding Description
`aptos_account::deposit_coins` (`aptos-move/framework/aptos-framework/sources/aptos_account.move:111-131`) aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when the recipient is not registered for `AptosCoin` **and** `can_receive_direct_coin_transfers` is false. Any account can set this flag to `false` for itself via `aptos_account::set_allow_direct_coin_transfers` before ever registering an `AptosCoin` `CoinStore` [1](#0-0) .

`distribute_internal` in `staking_contract.move` loops through `distribution_pool.shareholders()` and calls `aptos_account::deposit_coins(recipient, ...)` for each entry (operator's commission is redirected to `beneficiary_for_operator(operator)`), inside a single `while` loop, in a single transaction [2](#0-1) . This function is invoked as a mandatory first step from every user-facing entry point that would let a staker access unlocked funds: `distribute` [3](#0-2) , `unlock_stake` (which calls `distribute_internal` before adding the staker's new distribution) [4](#0-3) , `request_commission`, and critically `switch_operator`, which also force-distributes before letting the staker move away from the operator [5](#0-4) .

Because a staker can only ever `switch_operator` to a *new* operator by first successfully flushing the old operator's pending distribution, a malicious/griefing operator who disables direct coin transfers on their own (unregistered) account before any commission becomes withdrawable causes every one of these entry points to permanently abort as soon as inactive/pending_inactive commission exists in the pool. There is no per-recipient try/skip mechanism and no alternate withdrawal path that bypasses `distribution_pool`/`distribute_internal` in this file — the staker's principal, having already unlocked at the underlying `stake` module level, becomes unreachable through `staking_contract` as long as the operator keeps refusing direct transfers.

### Impact Explanation
This traps the staker's stake (and any accrued rewards) that have already progressed to `inactive`/withdrawable state at the `stake` pool level, but can never be moved out of the `StakingContract` wrapper because the shared distribution loop always reverts. It fits the "Permanent lock or non-recoverable loss of claim rights in stake ... commission ... flows" and "Operator commission ... payout ... corruption that ... traps value" impact categories: an unprivileged operator (chosen by the staker, but never granted admin/staker rights over the staker's principal) can indefinitely deny the staker access to their own already-unlocked funds.

### Likelihood Explanation
Setup cost is trivial and fully within an operator's own unprivileged capabilities: call `aptos_account::set_allow_direct_coin_transfers(operator, false)` and never register/deposit `AptosCoin` to that address. No special privilege, timing race, or governance action is required. The staker has no way to detect this in advance from the `staking_contract` state alone (a false flag is set on an arbitrary future operator's account), and once commission accrues, every escape path (`distribute`, `unlock_stake`, `switch_operator`) is blocked simultaneously.

### Recommendation
Do not let a failure to pay one shareholder (especially an untrusted operator/beneficiary) block payment to the others. Options:
- Process each shareholder's deposit independently, catching/aborting individually (or using a lazy/pull-based claim per shareholder) rather than one atomic loop that reverts entirely on a single failure.
- Allow `switch_operator`/`unlock_stake` to proceed for the staker's own portion even if the operator's commission distribution fails, e.g. by moving the operator's stuck commission into a separate reclaimable/pending state rather than gating the staker's withdrawal on it.
- Alternatively, verify the operator/beneficiary can actually receive `AptosCoin` (registered or has direct transfers enabled) before allowing them to be set/kept as operator, similar to `vesting::set_beneficiary`'s `assert_account_is_registered_for_apt` check, though this only guards against the initial state and does not stop an operator from disabling transfers afterward — a pull-based/per-recipient distribution design is the more robust fix.

### Proof of Concept
1. Operator `O` calls `aptos_account::set_allow_direct_coin_transfers(O, false)` and never registers a `CoinStore<AptosCoin>` for itself.
2. Staker `S` calls `staking_contract::create_staking_contract(S, O, voter, amount, commission_pct, seed)`, unaware of step 1.
3. Time passes; commission accrues and `O`'s share becomes `pending_inactive`/`inactive` once lockup rolls over.
4. `S` calls `unlock_stake(S, O, amount)` (or `request_commission`/`distribute`/`switch_operator`) to withdraw their now-unlocked stake.
5. Inside `distribute_internal`, when the loop reaches `O` (or `beneficiary_for_operator(O)`) as a recipient, `aptos_account::deposit_coins(O, coins)` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` because `O` is unregistered and has disabled direct transfers.
6. The entire transaction reverts, so `S` cannot withdraw their own already-unlocked stake either, and `switch_operator` (which also calls `distribute_internal` first) fails the same way, leaving `S` with no path to reclaim funds while `O` keeps refusing transfers.

*Note: I was not able to execute this scenario in a live Move test environment within this session; the trace above is derived from static analysis of the cited code paths in `staking_contract.move` and `aptos_account.move`. Confirming the exact abort behavior (e.g., whether `unlock_with_cap`/`stake` module state changes are rolled back atomically with the `distribute_internal` abort) would benefit from an actual Move unit test run in a Devin session with full repo/tooling access.*
