### Title
Cross-user response hijacking via unchecked overwrite of `h.savedCallbacks[msg.Body.MessageId]` in `HandleLegacyUserMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`(h *handler).HandleLegacyUserMessage` stores each user's `Callback` in `h.savedCallbacks` keyed only by the attacker-controllable `msg.Body.MessageId`, without checking whether an entry already exists for that key. Since `MessageId` is an arbitrary client-chosen string (bounded only by length/null-byte checks, not tied to the sender's signing key), a second concurrent request using the same `MessageId` silently overwrites the first request's saved callback, so the eventual DON response is delivered to the second (attacker) caller instead of the original submitter.

### Finding Description
`HandleLegacyUserMessage` validates payload/timestamp/method, then unconditionally does: [1](#0-0) 
with no check for an existing entry at `msg.Body.MessageId`. The `MessageId` originates from a client-supplied JSON-RPC request ID / legacy message body, validated only for length and trailing-null constraints in `Message.Validate`, not bound to the sender's identity: [2](#0-1) 
The gateway's `ProcessRequest` decodes the incoming request, validates the message (which derives `Sender` from the signature but does not derive or constrain `MessageId`), and passes it straight to `HandleLegacyUserMessage`: [3](#0-2) 
Later, when a DON node responds with that `MessageId`, `handleWebAPITriggerMessage` looks up and deletes the single entry keyed by `MessageId` and delivers the response to whichever callback is currently stored: [4](#0-3) 
If an attacker (an unprivileged client of the gateway's user-facing HTTP endpoint) submits a second legacy request with the same `MessageId` as an in-flight legitimate request before the DON responds, the attacker's `savedCallback` overwrites the victim's entry in the map. When the DON eventually responds, `handleWebAPITriggerMessage` finds only the attacker's callback and invokes `SendResponse` on it, delivering the (possibly sensitive) trigger response payload to the attacker while the legitimate caller's `Wait()` on the gateway (`gateway.go:278`) times out and receives `RequestTimeoutError`. No authentication, allowlist, or per-sender binding of `MessageId` prevents this, since `MessageId` uniqueness across different senders is not enforced anywhere in the validation path.

### Impact Explanation
This is a cross-user response confusion / request hijacking bug: an unprivileged gateway user can intercept the DON's response intended for another user's legacy web-API-trigger request, disclosing response data (attacker-controlled data returned to another user in reverse — here, the victim's data returned to the attacker) and simultaneously causing denial-of-service to the legitimate requester (unrecoverable timeout of their request). This matches the "cross-user response confusion" impact class called out in the audit rules.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs the ability to submit legacy user requests to the gateway's user-facing endpoint (an unauthenticated/unprivileged capability inherent to the gateway's public API) and needs to know or predict the `MessageId` of a targeted victim request while it is still in flight (the window between `HandleLegacyUserMessage` storing the callback and the DON's `handleWebAPITriggerMessage` response arriving). If `MessageId`s are predictable, sequential, or observable (e.g., reflected in client/application logs, or chosen from a constrained ID space), this is fully attacker-reproducible and requires no special privileges — matching the stated PRECONDITIONS (two concurrent legacy requests with same `MessageId`, different callbacks).

### Recommendation
Do not allow a new `HandleLegacyUserMessage` call to silently overwrite an existing, still-pending `savedCallbacks` entry: check for existing entries under `h.mu` and reject/error the new request when a live callback for the same `MessageId` is currently outstanding (e.g., return `api.HandlerError`/duplicate-message error), or key the pending-callback map on a composite of `(MessageId, Sender)` so that responses are only routed back to the exact matching sender who submitted the request. Additionally consider binding `MessageId` uniqueness/ownership more strongly by validating it against the ephemeral session or generating it server-side rather than trusting a client-picked value.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build `handler` via existing `setupHandler(t)` helper.
2. Build `msgVictim := triggerRequest(t, nodes[0].PrivateKey, ..., messageID="dup-id", ...)` signed with the victim's key, and `cbVictim := hc.NewCallback()`.
3. Call `handler.HandleLegacyUserMessage(ctx, msgVictim, cbVictim)`; assert `handler.savedCallbacks["dup-id"]` now holds `cbVictim`.
4. Build `msgAttacker := triggerRequest(t, nodes[1].PrivateKey, ..., messageID="dup-id", ...)` (same MessageId, different sender/key) and `cbAttacker := hc.NewCallback()`.
5. Call `handler.HandleLegacyUserMessage(ctx, msgAttacker, cbAttacker)`; assert `handler.savedCallbacks["dup-id"]` now holds `cbAttacker` (overwritten), and `cbVictim` was discarded.
6. Simulate a DON node response for `"dup-id"` via `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)` → internally calls `handleWebAPITriggerMessage`.
7. Assert `cbAttacker.Wait(ctx)` returns the DON's response payload successfully, while `cbVictim.Wait(ctx)` times out / never receives a response — demonstrating that the attacker's callback intercepted the victim's response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

		// Send first response from a node back to the user, ignore any other ones.

	return nil

func (m *Message) Validate() error {

		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {

	}
