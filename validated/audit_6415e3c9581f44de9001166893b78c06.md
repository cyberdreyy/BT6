## Title
Any single unregistered/opted-out shareholder or beneficiary can permanently DoS `staking_contract::distribute` and `vesting::distribute`, freezing payouts to *all* other stakers/operators/shareholders sharing the pool - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`, `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`staking_contract::distribute_internal` and `vesting::distribute` iterate over every shareholder in a shared `Pool`/`pool_u64` and push funds to each one via `aptos_account::deposit_coins` inside a single atomic loop. Because `deposit_coins` aborts if the recipient hasn't registered for `AptosCoin` and has opted out of unsolicited direct transfers (`aptos_account::set_allow_direct_coin_transfers(account, false)`), any one uncooperative recipient in the shared distribution list can cause the entire `distribute()`/`distribute_internal()` transaction to abort — blocking payout to every other, unrelated shareholder in the same pool. This is functionally identical to the external report's pattern: an untrusted payee revert during a shared payout DoS's the whole batch. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`distribute_internal` in `staking_contract.move` drains the `distribution_pool` shareholder-by-shareholder in a `while` loop, calling `aptos_account::deposit_coins(recipient, coin::extract(&mut coins, amount_to_distribute))` for each shareholder before moving to the next: [1](#0-0) 

The same all-or-nothing pattern exists in `vesting::distribute`, which loops all shareholders of `grant_pool` and calls `aptos_account::deposit_coins` for each: [5](#0-4) 

`aptos_account::deposit_coins` will abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the target account is not registered for `AptosCoin` **and** has disabled arbitrary/unsolicited coin transfers: [3](#0-2) 

Any account can flip that flag off with the fully unprivileged, self-serve entry function `set_allow_direct_coin_transfers`: [6](#0-5) 

Because Move transactions are atomic, an abort anywhere inside the shareholder loop reverts the *entire* `distribute`/`distribute_internal` call — including payouts already computed for every other shareholder, the staker's own principal withdrawal, and the operator's/beneficiary's commission. This is directly analogous to the external report's Denial-of-Service class: an untrusted payee ("secondary fee address" in the report; here, an arbitrary co-shareholder or the operator's beneficiary) can hijack the outcome of a shared payout process reachable by any unprivileged actor.

Concretely:
- In `staking_contract`, a staker can call `unlock_stake` (which internally forces `distribute_internal`) or anyone can call `distribute`. If the operator's beneficiary (set via `set_beneficiary_for_operator`, itself unprivileged for the operator) or any staker with pending distribution shares has disabled arbitrary coin transfers, `distribute`/`unlock_stake`/`switch_operator`/`request_commission` (all of which force `distribute_internal`) will permanently revert for that pool. [7](#0-6) [8](#0-7) 
- In `vesting`, any one of many `shareholders` in the same vesting contract can brick `distribute`, `distribute_many`, `terminate_vesting_contract` (which calls `distribute` first) and thus `admin_withdraw` for the whole contract. [9](#0-8) 

### Impact Explanation
This traps value and denies withdrawal/claim rights for accounts that are *not* the griefer: other stakers' unlocked principal, other shareholders' vested/rewarded coins, and the operator's/beneficiary's commission all become permanently unreachable through the standard distribution path as long as the uncooperative recipient remains in the shareholder set (their entry is only removed once fully redeemed, which never happens because the call keeps reverting). This matches the "Stake And Lockup Gate" criteria: non-recoverable loss of claim rights and share-accounting/payout corruption trapping value that belongs to uninvolved accounts.

### Likelihood Explanation
The precondition is trivial and fully unprivileged: any address can call `aptos_account::set_allow_direct_coin_transfers(account, false)` and simply never call `coin::register<AptosCoin>` (or, on the operator side, an operator can set their `beneficiary_for_operator` to such an address). No special role, timing, or race condition is required — it's a self-serve state that anyone sharing a `staking_contract`/`delegation`/vesting pool can set on their own account to grief co-participants.

### Recommendation
Do not perform value-bearing payouts to untrusted/opted-out addresses inside a loop shared by multiple beneficiaries. Options:
1. Change `distribute_internal`/`vesting::distribute` to skip (rather than abort on) recipients who cannot accept a direct/implicit transfer, and instead credit their share to a per-account claimable balance that they can pull separately (pull-over-push pattern), so one non-cooperative recipient cannot block payouts to others.
2. Alternatively, force-register the CoinStore/primary store for AptosCoin regardless of the `DirectTransferConfig` opt-out for payouts arising from stake/vesting/commission distributions specifically (since these are not "arbitrary unsolicited" transfers but contractually owed distributions), or catch/skip failures per-recipient using `try`-style patterns (e.g., checking `coin::is_account_registered` / `can_receive_direct_coin_transfers` up front and rerouting non-eligible shares to a fallback claimable store) instead of aborting the whole batch.

### Proof of Concept
1. Staker `S` creates a `staking_contract` with operator `O` via `staking_contract::create_staking_contract`.
2. `O` calls `staking_contract::set_beneficiary_for_operator(O, B)` to set beneficiary `B` (unprivileged, operator-only action over their own beneficiary).
3. `B` calls `aptos_account::set_allow_direct_coin_transfers(B, false)` and never registers a `CoinStore`/primary store explicitly for `AptosCoin` beyond what account creation may already provide — concretely, `B` is a resource/newly created account that has opted out and remains "not accepting direct transfers" per `can_receive_direct_coin_transfers`.
4. Rewards accrue; `O`/`S` calls `request_commission` (or any path triggering `distribute_internal`), and `S` calls `unlock_stake` to withdraw part of the principal.
5. `distribute_internal` computes distribution shares for both `S` (principal) and `B` (commission) and begins the redemption loop; when it reaches `B`'s share and calls `aptos_account::deposit_coins(B, ...)`, the call aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The whole transaction reverts, so `S`'s already-unlocked, unrelated principal withdrawal is also rolled back and remains stuck in the pool for as long as `B` keeps opting out — repeatable indefinitely since `B` fully controls this flag on their own account. [10](#0-9) [11](#0-10)

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }

    #[view]
    /// Return true if `account` can receive direct transfers of coins that they have not explicitly registered to
    /// receive.
    ///
    /// By default, this returns true if an account has not explicitly set whether the can receive direct transfers.
    public fun can_receive_direct_coin_transfers(
        account: address
    ): bool acquires DirectTransferConfig {
        !exists<DirectTransferConfig>(account)
            || borrow_global<DirectTransferConfig>(account).allow_arbitrary_coin_transfers
    }
