### Title
Post-default withdraw requests are paid 1:1 from the fixed `defaultRecoveryReserve`, letting a new claimant steal defaulted users' recovery - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug is a use-after-free: a request pointer was re-pointed at a lock entry that another task then freed, so the tracepoint dereferenced stale accounting. The credit-vault analog is in `IdleCreditVault`: after `finalizeDefaultRecovery` crystallizes a fixed `defaultRecoveryReserve` sized only for the *default-epoch* claim basis, `requestWithdraw` still lets any holder create a brand-new `postDefaultRequests` receipt. `_claimPostDefaultWithdrawRequest` then pays that fresh receipt **1:1 out of the same reserve**, even though the reserve was sized as `totalBasis * recoveryPrice` (i.e., haircut). The new receipt consumes recovery accounting that belongs to — and was already "spent" for — defaulted claimants, so the last claimants' payouts revert on underflow/insolvency while the attacker extracts un-haircut value.

### Finding Description
`finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * 1e18 / totalBasis` where `totalBasis` includes only active CDO strategy tokens plus `defaultPendingClaimBasis()` (pending normal + unfunded instant receipts), and stores `defaultRecoveryReserve = reserveAmount` (`IdleCreditVault.sol:686-692`). The reserve is therefore fully allocated to default-epoch claims at the haircut ratio.

When `defaultRecoveryFinalized` is true, `requestWithdraw` takes the post-default branch (`IdleCreditVault.sol:247-257`): it burns `_amount` of CDO strategy tokens, mints the user a receipt of `_amount`, and records `postDefaultRequests[_user] = _amount`. The comment says "The CDO passes an already-haircut amount because finalization lowered virtualPrice first" — so `_amount` ≈ `trancheValue * recoveryPrice`.

`_claimPostDefaultWithdrawRequest` (`IdleCreditVault.sol:760-767`) then pays that already-haircut `_amount` **again at full 1:1** via `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` (`IdleCreditVault.sol:912-917`). The haircut is thus applied twice in opposite directions incorrectly: the attacker buys/burns tranches at the post-default (haircutted) price, but claims reserve dollars at par.

Concretely, with `recoveryPrice = 0.5`: tranches that cost the attacker `X * 0.5` underlying-equivalent mint a `postDefaultRequests` receipt of `X * 0.5`, which is then paid `X * 0.5` from a reserve that was sized assuming those same funds owed `X * 0.5` *to defaulted claimants as well*. Every post-default claim consumes reserve that was never provisioned for it. Once `defaultRecoveryReserve` is exhausted, later legitimate `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` calls revert on `defaultRecoveryReserve -= _amount` underflow — permanent freezing of the remaining claimants' recovery — and if the attacker claims before them, they are paid out of defaulted users' share. This mirrors the UAF precisely: the reserve entry a defaulted claimant's receipt points at is "freed" (consumed) by a racing post-default claimant that was never in the `totalBasis` accounting.

### Impact Explanation
Direct theft and permanent freezing of unclaimed recovery funds. Maximum extractable amount approaches `defaultRecoveryReserve` itself: an attacker holding (or buying cheap post-default) tranches can repeatedly `requestWithdraw`/`claimWithdrawRequest` (the only gate is that the *same* user must clear a previous request first — a fresh EOA per iteration or sequential claims suffices) until the reserve is drained. Defaulted withdraw-receipt holders and defaulted instant-receipt holders then cannot claim at all (`_transferDefaultRecovery` underflows), so their recovery — the entire remaining reserve — is lost. Loss is bounded only by the attacker's post-default tranche holdings, but since each receipt is haircut-priced yet paid at par, the reserve is drained at ~`recoveryPrice`-on-the-dollar cost. The existing guards do not stop this: `_hasWithdrawRequest` only blocks *the same* user re-requesting, `_transferFundedClaim`'s reserve guard only protects funded (non-recovery) claims, and nothing tracks a remaining-claim-basis ceiling for post-default payouts.

### Likelihood Explanation
Requires a borrower default followed by `finalizeDefault`/`finalizeDefaultRecovery` (honest manager action — sequencing around them is allowed), then any unprivileged tranche-token holder or KYC-passing lender can execute with two permissionless calls per iteration (`requestWithdraw`, then `claimWithdrawRequest`) while `defaultRecoveryFinalized` is true. No privileged cooperation, no oracle manipulation, no flash capital needed beyond buying discounted tranches. The economic gain is guaranteed whenever `recoveryPrice < 1e18`, i.e., in every default with partial recovery. Likelihood is high conditional on a default occurring.

### Recommendation
Either fund post-default receipts separately or pay them at the recovery ratio. Concretely, in `requestWithdraw`'s post-default branch, escrow the receipt against newly sourced funds (e.g., require the CDO to deposit underlying into the strategy for the receipt) instead of minting a claim on `defaultRecoveryReserve`; or change `_claimPostDefaultWithdrawRequest` to pay `amount * defaultRecoveryPrice / RECOVERY_FULL` so the haircut is applied consistently — but note the CDO already passes a haircutted amount, so the cleaner fix is to pay post-default claims from a distinct counter (e.g., a `postDefaultReserve` funded at request time) and revert in `_transferDefaultRecovery` when `postDefaultRequests` claims would touch `defaultRecoveryReserve`. Also add an invariant check that `defaultRecoveryReserve` covers exactly the outstanding defaulted-epoch claim basis.

### Proof of Concept
Foundry fork PoC sketch (pattern follows `test/foundry/IdleCreditVault.t.sol` default tests):

```solidity
// 1. Users A (victim) and B deposit into AA; startEpoch; requestWithdraw for both.
_depositWithUser(victim, 100_000 * ONE_SCALE, true);
_depositWithUser(attacker, 100_000 * ONE_SCALE, true);
vm.prank(victim);   cdoEpoch.requestWithdraw(victimTrancheBal, address(AAtranche));
// attacker keeps tranches liquid (no request)

// 2. Honest manager: start epoch, borrower repays 0 -> default.
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr, 0);
assertTrue(cdoEpoch.defaulted());

// 3. Manager finalizes with partial recovery, e.g. 50% of basis.
uint256 recovered = /* activeBasis + pendingBasis */ * 5e17 / 1e18;
deal(defaultUnderlying, manager, recovered);
vm.startPrank(manager);
IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
cdoEpoch.finalizeDefault(recovered, manager);
vm.stopPrank();
assertEq(strategy.defaultRecoveryPrice(), 5e17); // 50% recovery

// 4. Attacker mints a post-default receipt at the haircutted price.
vm.prank(attacker);
uint256 receipt = cdoEpoch.requestWithdraw(attackerTrancheBal / 2, address(AAtranche));
uint256 reserveBefore = strategy.defaultRecoveryReserve();

// 5. Attacker claims 1:1 from the recovery reserve.
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();
assertEq(underlying.balanceOf(attacker) - balPre, receipt);        // paid at PAR
assertEq(reserveBefore - strategy.defaultRecoveryReserve(), receipt);

// 6. Repeat until reserve < victim claim; victim's defaulted claim now reverts.
// ... attacker loops requestWithdraw/claimWithdrawRequest with remaining tranches ...
vm.prank(victim);
vm.expectRevert(); // defaultRecoveryReserve underflow in _transferDefaultRecovery
cdoEpoch.claimWithdrawRequest();
```

Expected: attacker receives `receipt` underlying at par while having burned tranches worth `receipt` (haircutted); `defaultRecoveryReserve` shrinks by an amount never included in `totalBasis`; victim's `_claimDefaultedWithdrawRequest` reverts once reserve is exhausted → theft of ~`(1 - recoveryPrice)` margin per iteration plus permanent freeze of remaining recovery.
