### Title
Permissionless `fullfillWriteOffRequest` lets anyone force-fill a zero-price write-off and steal a lender's escrowed tranche tokens — (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The Yamcs bug is a missing-input-validation-in-codegen flaw: an attacker-controlled string is spliced raw into a privileged execution context, and a single missing escape turns a routine read-only call into arbitrary execution. The credit-vault analog is `IdleCreditVaultWriteOffEscrow`: a lender's `WriteOffRequest` fields are accepted raw into `userRequests`, and the permissionless `fullfillWriteOffRequest` consumes them without validating that the request ever demanded a nonzero price. A request created with `underlyingsRequested == 0` can be force-filled by any EOA for `0` underlyings, and the fulfiller walks away with all escrowed tranche tokens.

### Finding Description
`createWriteOffRequest` validates only that `amount != 0`; `underlyingsRequested` is stored unchecked:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:86-101
if (amount == 0) revert NotAllowed();
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
pendingUnderlyings += underlyingsRequested;
```

`fullfillWriteOffRequest` is explicitly callable by "any wallet" (line 122) and only enforces `currentRequest.tranches == _tranches` and `_underlyings >= currentRequest.underlyings` (line 129). For a request with `underlyings == 0`, the second check passes for `_underlyings == 0`, so the fulfiller pays nothing (the `safeTransferFrom` of 0 succeeds) and receives `_tranches` tranche tokens at line 151. Like the `LikeExpression` sink — where a value that should have been constrained is embedded raw and then executed — the escrow embeds the lender's `underlyings` ask raw and the fulfillment path executes against it without a lower bound.

The lender loses the tranche tokens permanently: the request is deleted (line 135) and `deleteWriteOffRequest` cannot recover them. This is not protected by `nonReentrant`, `EpochNotRunning`, KYC, or any ownership check — fulfillment is intentionally open.

### Impact Explanation
Direct theft of escrowed tranche tokens, quantified as the full `tranches` amount of any request with `underlyings == 0`. Two realistic victim paths:

1. A lender (or its UI/integration) creates a request with `underlyingsRequested = 0` by mistake or because it intends to signal "any offer" — the escrow semantics treat it as a literal zero ask that anyone can settle.
2. An attacker front-runs `createWriteOffRequest` — no, the attack needs no front-running: any time a zero-price request exists in a running epoch, the attacker calls `fullfillWriteOffRequest(victim, victimRequest.tranches, 0)` and takes the tranche tokens, which represent a claim on vault NAV and can be used for withdraw requests / write-off against the borrower.

Loss is bounded by the victim's escrowed balance but is total for that balance, i.e., direct theft of user funds with no fund recovery path.

### Likelihood Explanation
Medium. Exploitation requires only an EOA, no privileges, and one external call. The precondition is the existence of a zero-ask request — plausible given (a) no input validation discourages it, (b) `deleteWriteOffRequest` plus re-create is the only way to fix a mistaken request, and the fulfill can land in the same block as creation, and (c) integrators may treat `underlyingsRequested = 0` as "no minimum" rather than "free". The contract provides no event-based guard or minimum-price floor (`MAX_EXIT_FEE` bounds only the fee, not the ask).

### Recommendation
Mirror the `amount == 0` check on the price side and tighten fulfillment:

```solidity
// in createWriteOffRequest, contracts/IdleCreditVaultWriteOffEscrow.sol:90
if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
```

Additionally, defence-in-depth (parallel to "bind the pattern instead of inlining"): require `msg.sender == borrower` in `fullfillWriteOffRequest`, or require the fulfiller to have been pre-approved by the requester, so a request's stored fields can't be executed against by arbitrary third parties.

### Proof of Concept
Foundry fork/unit PoC (against deployed or freshly initialized escrow):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract WriteOffZeroPriceTest is Test {
  IdleCreditVaultWriteOffEscrow escrow;
  IERC20Detailed tranche;
  IERC20Detailed underlying;
  address lender = makeAddr("lender");
  address attacker = makeAddr("attacker");
  uint256 constant TRANCHES = 100e18;

  function setUp() public {
    // deploy escrow proxy initialized against a running-epoch IdleCDOEpochVariant,
    // e.g. a mainnet fork of an existing vault escrow, or local deployment with
    // isEpochRunning() == true.
    // escrow = ...; tranche = IERC20Detailed(escrow.tranche());
    // underlying = IERC20Detailed(escrow.underlying());
    deal(address(tranche), lender, TRANCHES);
    vm.prank(lender);
    tranche.approve(address(escrow), type(uint256).max);
  }

  function testStealZeroPriceRequest() public {
    // Lender escrows tranche tokens demanding 0 underlyings (accepted, unchecked)
    vm.prank(lender);
    escrow.createWriteOffRequest(TRANCHES, 0);

    // Attacker (any EOA, no privileges) force-fills with 0 underlyings
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(lender, TRANCHES, 0);

    // Attacker holds the lender's tranche tokens; lender's request is gone
    assertEq(tranche.balanceOf(attacker), TRANCHES);
    (uint256 t, uint256 u) = escrow.userRequests(lender);
    assertEq(t, 0);
    assertEq(u, 0);
    assertEq(underlying.balanceOf(attacker), 0); // paid nothing
  }
}
```

Note: the PoC requires an `IdleCDOEpochVariant` whose `isEpochRunning()` returns true (running epoch phase); the escrow itself is otherwise self-contained, so a fork test against a live vault escrow or a mock CDO suffices.
