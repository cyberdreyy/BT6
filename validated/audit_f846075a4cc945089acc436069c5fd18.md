### Title
`simulateTransaction` RPC can panic the JSON-RPC service by targeting an unfrozen bank - ([File: rpc/src/rpc.rs], [File: runtime/src/bank.rs])

### Summary
The `simulateTransaction` JSON-RPC handler resolves a `Bank` via `JsonRpcRequestProcessor::get_bank_with_config()` and then calls `Bank::simulate_transaction()`, which unconditionally asserts the bank is frozen (`assert!(self.is_frozen(), "simulation bank must be frozen")`). When the request's commitment resolves to the currently-building "processed"/working bank — which is not yet frozen — this assertion fires and panics, exactly mirroring the external report's bug class: an operation that silently assumes a state-transition precondition (there, `finalize()` before `setSchedules()`; here, "frozen" before "simulate") can be invoked out of order by an unprivileged caller, turning a single request into a denial of service.

### Finding Description

which in turn calls `bank(commitment)`. For the default/`Processed` commitment level, `bank()` returns "the heaviest slot" — i.e., the current working bank from `BankForks`, without any check that it has been frozen: [3](#0-2) 

The simulation is then executed with: [4](#0-3) 

`Bank::simulate_transaction()` unconditionally asserts the bank is frozen before delegating to `simulate_transaction_unchecked()`: [5](#0-4) 

The repository's own regression test demonstrates this exact panic is reachable purely through the RPC entry point, with no privileged access required: [6](#0-5) 

This is structurally the same class of bug as the `DaosLive`/`DaosVesting` finding: a state-ordering invariant ("bank must be frozen" / "vesting must be finalized before scheduling") is enforced only via a hard failure (`assert!`/`revert`) rather than being made unreachable by construction, and an unprivileged caller can trigger the violating state transition with ordinary, permitted inputs (calling `simulateTransaction` with `commitment: "processed"` while the working bank for the current slot has not yet been frozen, e.g., early in a slot before `Bank::freeze()` is invoked by the replay/banking pipeline).

### Impact Explanation
An `assert!` panic on the thread executing the RPC request is a hard crash path, not a recoverable `Result`. Given the JSON-RPC HTTP server is configured with `.threads(1)` and driven by the shared Tokio runtime handle (`rpc/src/rpc_service.rs`), a panic on this path can take down the request-processing worker responsible for RPC handling for the node, effectively causing a denial of service against the node's public JSON-RPC surface from a single unprivileged request. Because the request pattern requires no special privileges (just crafting a `simulateTransaction` call with default/processed commitment during a natural window when the working bank is not frozen), this matches the "unbounded impact from a single low-privilege request" class called out as in-scope.

### Likelihood Explanation
Likelihood depends on timing: the working bank returned for `CommitmentLevel::Processed` is frozen only after the leader (or replay stage) finishes processing entries for a slot via `Bank::freeze()`. There is a window during each slot — while the bank is actively being built — where it is not yet frozen. An external caller sending `simulateTransaction` (default commitment, i.e. `Processed`) during that window against the local RPC node will reliably hit this assertion, as proven by the existing unit test that reproduces the exact panic message using an unfrozen bank. This does not require multiple clients, unfiltered scans, or crafted snapshots — a single well-timed RPC call is sufficient.

### Recommendation
Do not use `assert!` to enforce the "bank must be frozen" invariant on a path reachable from external RPC input. Instead, `simulate_transaction`/`get_bank_with_config` should either:
- explicitly wait for/select a frozen bank when a working (unfrozen) bank is resolved for simulation, or
- return a `Result`/RPC error (e.g. equivalent to `RpcCustomError`) when the resolved bank is unfrozen, rather than asserting and panicking.

### Proof of Concept
The existing test in the repository already demonstrates the panic deterministically: [6](#0-5) 
It constructs an `RpcHandler`, deliberately leaves the working bank unfrozen (`assert!(!bank.is_frozen())`), and issues a `simulateTransaction` JSON-RPC request, which panics with `"simulation bank must be frozen"` inside `Bank::simulate_transaction()` (`runtime/src/bank.rs`, line 3815). In production, the same condition is reached whenever an external client submits `simulateTransaction` (with default/`processed` commitment) during the interval in a slot before `Bank::freeze()` is called on the working bank.

impl JsonRpcRequestProcessor {
    fn get_bank_with_config(&self, config: RpcContextConfig) -> Result<Arc<Bank>> {
        let RpcContextConfig {
            commitment,
            min_context_slot,
        } = config;
        let bank = self.bank(commitment);
        if let Some(min_context_slot) = min_context_slot
            && bank.slot() < min_context_slot
        {
            return Err(RpcCustomError::MinContextSlotNotReached {
                context_slot: bank.slot(),
            }
            .into());
        }
        Ok(bank)
    }

    #[allow(deprecated)]
    fn bank(&self, commitment: Option<CommitmentConfig>) -> Arc<Bank> {
        debug!("RPC commitment_config: {commitment:?}");

        let commitment = commitment.unwrap_or_default();
        if commitment.is_confirmed() {
            let bank = self
                .optimistically_confirmed_bank
                .read()
                .unwrap()
                .bank
                .clone();
            debug!("RPC using optimistically confirmed slot: {:?}", bank.slot());
            return bank;
        }

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })
    }
