### Title
Post-close `requestWithdraw` mints an instantly-claimable receipt that is never added to `pendingWithdraws`, letting a user drain the funded pending-withdrawal reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Xen bug is a race between pagetable promotion and demotion: an operation checks state under one regime and completes after the object has transitioned to another, because an earlier fix (XSA-299) missed a corner case. The analog in `IdleCreditVault` is a phase-transition race between `requestWithdraw` and `claimWithdrawRequest` across the "closed pool" boundary (`epochEndDate() == 0`). A withdraw request created in the closed phase skips both the `pendingWithdraws` funding bucket and the one-epoch claim delay, so it is paid immediately, at par plus interest, out of the underlying balance that was funded by the borrower exclusively for pre-close pending receipts.

### Finding Description
In `requestWithdraw`, when `IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0` (`isClosed`), the strategy:

- burns only `_principal` strategy tokens from the CDO but mints `_amount` (principal + accrued interest at current virtual price) receipt tokens to the user — `IdleCreditVault.sol:273-275`;
- deliberately skips `pendingWithdraws += _amount` because "a successfully closed pool already recalled all funds and has no later stopEpoch" — `IdleCreditVault.sol:276-280`;
- still records `withdrawsRequests[_user] += _amount` and `withdrawsRequestsByEpoch` — `IdleCreditVault.sol:292-293`;
- still sets `lastWithdrawRequest[_user] = currentEpoch` — `IdleCreditVault.sol:282`.

The claim-side gate in `_claimFundedWithdrawRequest` is `if (epochEndDate() != 0 && epochNumber <= lastWithdrawRequest[_user]) revert NotAllowed();` — `IdleCreditVault.sol:326`. In the closed phase the first conjunct is false, so the fresh receipt is claimable in the same transaction. `_transferFundedClaim` (`IdleCreditVault.sol:897-907`) then pays the full `_amount` from the strategy's underlying balance, which after a healthy close consists solely of funds collected via `collectWithdrawFunds` for earlier pending receipts (`IdleCreditVault.sol:411-430`).

The phase check and the payout therefore act on two different accounting regimes: the request is accounted under the closed-pool regime (no `pendingWithdraws`, no funding pull), but it settles through the funded-claim path designed for receipts that were fully funded at the last `stopEpoch`. No guard rejects a first request in the closed phase — `_hasWithdrawRequest`/`lossRecoveryPriceByEpoch` checks only fire for users with prior receipts, and the `defaultRecoveryFinalized` early-return path is not taken on a healthy close.

### Impact Explanation
An attacker holding tranche tokens calls `IdleCDOEpochVariant.requestWithdraw` immediately after the final `stopEpoch` that closes the pool (`epochEndDate == 0`), then calls `claimWithdrawRequest` in the same or next transaction. The strategy pays `amount = trancheTokens * virtualPrice` underlyings entirely from the balance reserved for legitimate pre-close pending receipts. Because `pendingWithdraws` was never incremented and no `collectWithdrawFunds` pull occurs, every wei paid out is a wei taken from users whose requests were funded during the closing `stopEpoch`. The last legitimate claimant's `claimWithdrawRequest` reverts on insufficient balance (permanent freezing / direct theft) up to the full amount the attacker extracts, which is bounded only by the attacker's tranche holdings — i.e., the entire funded reserve can be drained by sufficiently large post-close requests.

### Likelihood Explanation
Requirements: a credit vault that reaches the closed state (a normal, intended terminal state — see `testHealthyCloseProcessesQueuedWithdrawalAsNormalClaim` in `test/foundry/IdleCDOEpochQueue.t.sol`), unclaimed pending receipts still held in the strategy, and any unprivileged tranche holder (KYC-passing lender). No privileged collusion, timing precision, or oracle manipulation is needed — the attack is atomic in a single transaction in the closed phase. The main open dependency is whether the vault ever retains unclaimed funded receipts while tranche tokens remain circulating; the epoch-queue design (users can claim "at any time even if a new epoch started", `IdleCreditVault.sol:320-324`) makes stale unclaimed receipts expected rather than exceptional.

### Recommendation
In `requestWithdraw`, treat the closed-pool phase symmetrically with the funded-claim path: either

- revert when `isClosed` for new requests (users redeem tranches through the CDO instead), or
- skip `withdrawsRequests`/`lastWithdrawRequest` accounting and settle post-close requests through a dedicated path that is paid from the CDO's own post-close balance rather than the strategy's funded-receipt reserve — analogous to the `postDefaultRequests` bucket used after `defaultRecoveryFinalized` (`IdleCreditVault.sol:252-257`), which keeps post-transition claims out of the pre-transition accounting.

### Proof of Concept
Foundry fork sketch (based on the harness in `test/foundry/IdleCreditVault.t.sol` / `test/foundry/IdleCDOEpochQueue.t.sol`):

```solidity
function testPostCloseRequestDrainsFundedReserve() external {
    // 1. Epoch running: userV (victim) requests withdraw -> pendingWithdraws = V
    uint256 vTranches = _depositWithUser(VICTIM, 1000e6);
    _requestWithdrawWithUser(VICTIM, vTranches);

    // 2. Attacker still holds tranches (no withdraw request)
    uint256 aTranches = _depositWithUser(ATTACKER, 1000e6);

    // 3. Healthy close: borrower repays principal+interest, manager stops with
    //    full repayment sentinel; collectWithdrawFunds funds pendingWithdraws.
    //    epochEndDate() == 0 afterwards.
    uint256 repay = strategy.pendingWithdraws() + cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    deal(address(underlying), borrower, repay);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), repay);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager); cdoEpoch.stopEpoch(0, 1);
    assertEq(cdoEpoch.epochEndDate(), 0);          // closed phase
    // victim does NOT claim yet (allowed to claim at any later time)

    // 4. Attacker requests + claims in the closed phase (same block)
    uint256 stratBalPre = underlying.balanceOf(address(strategy));
    uint256 aReq = cdoEpoch.requestWithdraw(aTranches, address(AAtranche));
    // epochEndDate()==0 => _claimFundedWithdrawRequest gate skipped, pays at once
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(ATTACKER), 0);
    // No funding pull happened: strategy balance fell below funded basis
    assertLt(underlying.balanceOf(address(strategy)), stratBalPre - aReq + 1 /*approx*/);

    // 5. Victim's previously funded receipt can no longer be paid in full
    vm.expectRevert(); // ERC20 transfer amount exceeds balance (or NotAllowed)
    vm.prank(VICTIM); cdoEpoch.claimWithdrawRequest();
}
```

Notes/limits: the PoC assumes `IdleCDOEpochVariant.requestWithdraw` remains callable when `epochEndDate() == 0`; the strategy code explicitly branches on `isClosed` rather than reverting (`IdleCreditVault.sol:259,276-280`), indicating the path is intended to be reachable. Exact payoff equals `aTranches * virtualPrice / ONE_TRANCHE`, capped by the residual funded balance.
