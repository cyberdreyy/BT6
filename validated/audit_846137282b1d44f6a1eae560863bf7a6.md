### Title
Loss-adjusted withdraw receipts escape their haircut and are paid at par when a newer request overwrites `lastWithdrawRequest` - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The double-free bug class maps to a double-accounting/double-payout flaw in `IdleCreditVault.claimWithdrawRequest`. A user's loss-adjusted receipt from `stopEpochWithDuration(_lossAmount)` is keyed to `lastWithdrawRequest[_user]`, but a subsequent `requestWithdraw` silently overwrites that marker. On the next claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch` only under the *latest* epoch, finds nothing, and the older receipt falls through to `_claimFundedWithdrawRequest`, which pays the aggregate `withdrawsRequests[_user]` at par — even though the borrower only funded the haircut amount. The same thing happens if the later epoch ends in a finalized default: `_clearWithdrawClaimForEpoch` zeroes `lastWithdrawRequest`, again orphaning the older loss-adjusted epoch marker.

### Finding Description
- `requestWithdraw` stores the per-epoch amount in `withdrawsRequestsByEpoch[_user][currentEpoch]`, adds it to the aggregate `withdrawsRequests[_user]`, and unconditionally sets `lastWithdrawRequest[_user] = currentEpoch`, discarding the previous epoch marker [1](#0-0) .
- `_claimLossAdjustedWithdrawRequest` only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`; there is no iteration over older epochs and no per-epoch receipt of the loss-adjusted epoch is otherwise tracked [2](#0-1) .
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` (which still contains the E1 principal, because `_clearWithdrawClaimForEpoch` was never run for E1) at par and burns the full amount [3](#0-2) .
- Funding for E1 was only the loss-adjusted amount (`pendingWithdraws` is cleared when the borrower funds the haircut total during `stopEpochWithDuration`), so paying E1 principal at par spends underlyings that belong to other claimants/active LPs. `_transferFundedClaim` only protects `defaultRecoveryReserve`, not other funded receipts [4](#0-3) .
- Second variant: after `finalizeDefault`, `claimWithdrawRequest` runs `_claimDefaultedWithdrawRequest`, which clears the default-epoch piece and resets `lastWithdrawRequest` to 0 when it equals `defaultRecoveryEpoch` [5](#0-4) [6](#0-5) . An older loss-adjusted receipt is again orphaned and paid at par via `_claimFundedWithdrawRequest`, draining the strategy's non-reserve balance.

### Impact Explanation
Direct theft/insolvency: the attacker redeems one funded (haircut) pool of underlyings for a par payout. Loss is `(1 - lossRecoveryPrice/RECOVERY_FULL) * claimBasis` per orphaned receipt — up to the full receipt value if `lossRecoveryPrice` is small. The excess is taken from underlyings backing other users' funded receipts or active tranche NAV, breaking the loss-socialization invariant ("one receipt, one haircut payout").

### Likelihood Explanation
Requires only unprivileged actions: deposit, `requestWithdraw` in an epoch that ends via `stopEpochWithDuration(_lossAmount > 0)`, then `requestWithdraw` again in the next epoch, wait one epoch boundary, and call `claimWithdrawRequest`. Honest manager/borrower calls are sequenced around the attacker's actions per the threat model. The same orphaning triggers in the default path with no extra attacker effort.

### Recommendation
Track the loss-adjusted claim epoch per user independently of `lastWithdrawRequest` (e.g., a `lossAdjustedEpoch[_user]`/`lossBasisByEpoch` mapping set when `lossRecoveryPriceByEpoch` is written for the user's request epoch, or persist per-epoch receipt markers so `_claimLossAdjustedWithdrawRequest` can locate older epochs). In `_claimFundedWithdrawRequest`, exclude any epoch that has a non-zero `lossRecoveryPriceByEpoch` from the par payout, and never reset `lastWithdrawRequest` while an unclaimed loss-adjusted receipt exists.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossAdjustedReceiptPaidAtPar() external {
    uint256 amount = 10_000 * ONE_SCALE;
    address user = makeAddr('user');
    _depositWithUser(user, amount, true);

    // Epoch 0: user requests withdraw of full position
    vm.prank(user);
    uint256 receiptE1 = cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);
    // Stop epoch 0 with a loss: lossRecoveryPriceByEpoch[E1] is written,
    // borrower funds only the haircut amount
    uint256 loss = receiptE1 / 2;
    _stopEpochWithDurationAndLoss(loss); // wrapper around stopEpochWithDuration(apr, 0, duration, loss)

    // Epoch 1 buffer: user deposits again and requests another withdraw,
    // overwriting lastWithdrawRequest[user] = E2
    _depositWithUser(user, amount, true);
    vm.prank(user);
    uint256 receiptE2 = cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Claim: _claimLossAdjustedWithdrawRequest looks up epoch E2 -> price 0 -> skipped.
    // _claimFundedWithdrawRequest pays withdrawsRequests[user] = E1 + E2 at par.
    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(user) - balPre;

    // E1 should have been paid at lossRecoveryPrice (receiptE1 - loss share);
    // instead it is paid in full.
    assertEq(paid, receiptE1 + receiptE2, 'E1 receipt escaped loss haircut');
    // Invariant break: strategy paid out more than was funded for E1.
}
```

The identical sequence ending in `_checkDefault()` + `finalizeDefault` reproduces it through `_claimDefaultedWithdrawRequest` zeroing `lastWithdrawRequest`.

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
