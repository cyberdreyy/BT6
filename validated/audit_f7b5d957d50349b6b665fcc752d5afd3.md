### Title
`StakingRewards.depositReward` does not reserve already-accrued unclaimed rewards, so rolling a new reward period can make the contract insolvent in `rewardsToken` - ([File: contracts/StakingRewards.sol](https://github.com/ThankGod76/idle-tranches--016/blob/main/contracts/StakingRewards.sol))

### Summary
`StakingRewards.depositReward` (the renamed `notifyRewardAmount`, called by the honest `rewardsDistribution` role, i.e. the IdleCDO contract distributing incentives to tranche stakers) validates the new `rewardRate` against the contract's *entire* `rewardsToken` balance. That balance already includes rewards that stakers have earned but not yet claimed via `getReward()`. When a new period is started while old rewards remain unclaimed, the accrued-but-unclaimed balance is silently re-allocated to the new period, and the contract can become insolvent: later claimers' `getReward()` reverts on the ERC20 transfer.

### Finding Description
In `depositReward` (contracts/StakingRewards.sol:129-153):

```solidity
uint balance = rewardsToken.balanceOf(address(this));
require(rewardRate <= balance / rewardsDuration, "Provided reward too high");
```

This mirrors the classic Synthetix check, but it is only correct if the full balance is attributable to the *new* reward amount plus the current period's leftover. In this contract, rewards that have already vested to users sit in `rewards[account]` mappings and remain in the token balance until `getReward()` is called (contracts/StakingRewards.sol:108-115). There is no accounting that subtracts the sum of earned-but-unclaimed rewards (plus the `leftover` from the in-flight period) from `balance` before approving the new `rewardRate`.

Concretely:
1. `rewardsDistribution` (IdleCDO) calls `depositReward(_, R)` funding period 1. An unprivileged staker stakes and earns rewards.
2. The period ends (or is extended mid-period via the `leftover` path at lines 136-140). The staker does not claim.
3. `rewardsDistribution` calls `depositReward(_, R)` again for a new period. The solvency check passes because the staker's unclaimed `earned` rewards are still counted in `balance`.
4. New rewards stream on top of the old obligations. Once the balance is drained by early claimers, late claimers' `getReward()`/`exit()` revert with an ERC20 "transfer amount exceeds balance" failure.

The same pattern exists verbatim in `contracts/DelegateStakingRewardsIDLE.sol:151-167`.

### Impact Explanation
Direct insolvency / permanent freezing of unclaimed yield: the contract commits to pay out more `rewardsToken` than it can ever hold. Early claimers receive amplified rewards relative to their entitlement while later claimers are permanently unable to claim unless new funds are injected (recovery is only possible via owner funding or `recoverERC20`, which cannot distinguish stranded rewards). Loss is bounded by the total unclaimed accrued rewards at rollover, i.e. up to a full period's reward budget.

### Likelihood Explanation
Requires only that `rewardsDistribution` rolls a new reward period while stakers hold unclaimed `earned` balances — a routine, expected operation — and a single unprivileged staker who simply delays claiming (normal user behavior, no active exploit needed). The guard at line 147 does not stop it precisely because it measures the wrong quantity. The condition `block.timestamp >= periodFinish` makes the bug deterministic on every rollover with unclaimed rewards.

### Recommendation
Track outstanding reward obligations (e.g. an `unclaimedRewards` accumulator incremented in `updateReward` when `rewards[account]` is credited and decremented in `getReward`), and validate `rewardRate <= (balance - totalUnclaimed - leftover) / rewardsDuration`, or alternatively fund the new period such that `balance - totalUnclaimed` covers `reward * duration`. Apply the same fix to `DelegateStakingRewardsIDLE.depositReward`.

### Proof of Concept
Foundry test against `contracts/StakingRewards.sol` (adapted from the report; assumes a mock ERC20 `token` and `stakingToken`):

```solidity
function test_depositReward_insolvency() public {
    address operator = rewardsDistribution; // honest privileged caller
    address alice = address(0xA11CE);       // unprivileged staker

    // Period 1: fund 1 ether of rewards, Alice stakes
    vm.startPrank(operator);
    token.mint(operator, 2 ether);
    token.approve(address(staking), 2 ether);
    staking.depositReward(address(0), 1 ether);
    vm.stopPrank();

    vm.prank(operator); // operator stakes on behalf if needed; else Alice stakes directly
    staking.stake(1 ether);

    vm.warp(block.timestamp + 7 days); // period 1 fully vests to Alice, she doesn't claim

    // Period 2: only 1 ether total in contract, but check passes because
    // Alice's ~1 ether unclaimed reward is still counted in `balance`
    vm.prank(operator);
    staking.depositReward(address(0), 0); // even 0 re-commits leftover; use small top-up for realism

    // Attacker-free path: another staker joins and claims early, draining balance
    // Then Alice's claim reverts:
    vm.warp(block.timestamp + 7 days);
    vm.prank(alice);
    vm.expectRevert(); // ERC20: transfer amount exceeds balance
    staking.getReward();
}
```

The revert occurs because `rewards[alice]` (~1 ether) plus period-2 streaming obligations exceed the contract's actual `rewardsToken` balance.
