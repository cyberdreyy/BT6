### Title
JWT replay cache check-then-act race allows concurrent requests with the same jti to both pass authorization - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` and later calls `h.jwtCache.recordUsage(claims.ID)` as two separate lock acquisitions rather than one atomic operation, leaving a TOCTOU window. Two concurrent `Authorize` calls carrying the identical token/jti can both observe `isReplay` as `false` before either records usage, allowing a single signed JWT to authorize two workflow-trigger requests.

### Finding Description
`Authorize` verifies the JWT, then calls `isReplay` under an `RLock`/`RUnlock` pair, performs unrelated authorized-key lookups, and only afterward calls `recordUsage` under a separate `Lock`/`Unlock` pair: [1](#0-0) 
The `isReplay` and `recordUsage` methods are independent critical sections: [2](#0-1) 
Because there is no single lock spanning the "check" and "record" operations (i.e., no compare-and-set / atomic `LoadOrStore`), two goroutines calling `Authorize` concurrently with the same jti can both execute `isReplay` (each acquiring and releasing the `RWMutex` independently) and both observe `exists == false`, since neither has yet written to `cache.cache`. Both goroutines then proceed past the replay check, both pass the authorized-key lookup (same signer key), and both eventually call `recordUsage`, with the second call silently overwriting the timestamp. The net effect: a single JWT/jti authorizes two (or more, under sufficient concurrency) accepted requests instead of one.

### Impact Explanation
This breaks the request-binding / anti-replay invariant explicitly claimed by the `jwtReplayCache` (comment: "manages used JWT IDs to prevent replay attacks"). An attacker holding one valid, signed JWT for a workflow trigger can fire concurrent requests to trigger the same workflow execution more than once using a single authorization, which corresponds to the "unauthorized job run" bounty impact class — the attacker is not gaining new signing capability, but is bypassing the single-use guarantee intended to bind one signature to exactly one workflow execution.

### Likelihood Explanation
Preconditions are minimal: attacker only needs one valid JWT (already possesses a legitimate signer credential/jti, as required to reach `Authorize` at all) and the ability to send two requests to the gateway at (near) the same time — a trivial network-level race, not requiring elevated privileges. The race window depends on scheduling, but is realistically exploitable by firing many concurrent duplicate requests to increase the chance of a hit; it is fully reproducible in a unit test via goroutines calling `Authorize` concurrently.

### Recommendation
Make replay-check-and-record atomic under a single lock, e.g. add a method such as `checkAndRecord(jti string) bool` on `jwtReplayCache` that holds a single `Lock()` for the whole check + insert, and have `Authorize` call it once instead of separately calling `isReplay` then `recordUsage` (or use `sync.Map` with `LoadOrStore` semantics). The authorized-key checks that happen between `isReplay` and `recordUsage` should not affect whether the jti is atomically marked used at the earliest point once JWT verification succeeds.

### Proof of Concept
Go unit test outline:
1. Construct a `WorkflowMetadataHandler` with a valid `authorizedKeys` entry for a `workflowID` and one signer key matching a test JWT.
2. Generate a single valid JWT (with jti = "jti-1") signed by the test signer for that `workflowID`/request.
3. Launch N (e.g., 20) goroutines that all call `h.Authorize(workflowID, token, req)` concurrently with the same token.
4. Collect results; assert that **at most one** call returns `(key, nil)` and the rest return the "JWT token has already been used" error.
5. Current implementation is expected to fail this assertion under sufficient concurrency (more than one goroutine returns success), demonstrating the TOCTOU window between `isReplay` and `recordUsage`.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
