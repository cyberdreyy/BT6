### Title
Zip extraction path (`ExtractZipArchive`) lacks path-traversal/absolute-path validation, unlike the tar+zstd extractor - ([File: helpers/archives/zip_extract.go])

### Summary
The zip extraction code path used by the legacy zip extractor (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`, format `archive.Zip`) delegates to `archives.ExtractZipArchive`, which writes each zip entry's `file.Name` directly via `os.MkdirAll`/`os.Create`/`os.Symlink` with **no check** that the resolved path stays inside the target extraction directory. This is inconsistent with the sibling `tarzstd` extractor, which explicitly computes `filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects entries that escape the `dir` chroot with `"cannot be extracted outside of chroot"`.

### Finding Description
`CacheExtractorCommand.Execute` (`commands/helpers/cache_extractor.go:618-664`) determines the cache archive format via `openArchive(c.File)` and calls `archive.NewExtractor(format, f, size, wd)` followed by `extractor.Extract(ctx)`, with the stated invariant that extraction must confine all entries under `wd`.

For the `archive.Zip` format, the registered extractor implementation (`ziplegacy.extractor.Extract`, `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go:26-33`) stores `dir` in its struct but **never uses it**:
```go
func (e *extractor) Extract(ctx context.Context) error {
	zr, err := zip.NewReader(e.r, e.size)
	...
	return archives.ExtractZipArchive(zr)
}
```
`archives.ExtractZipArchive` (`helpers/archives/zip_extract.go:85-110`) iterates zip entries and only checks for `.git` directory entries via `errorIfGitDirectory`; it then calls `extractZipFile(file)`, which does:
```go
os.MkdirAll(filepath.Dir(file.Name), 0o777)
...
os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, ...)   // regular files
os.Symlink(string(data), file.Name)                                // symlinks
```
`file.Name` is taken verbatim from the archive header with no `filepath.Clean`, no rejection of absolute paths, and no containment check against `wd`/`e.dir`. This contrasts directly with the `tarzstd` extractor's explicit chroot enforcement (`commands/helpers/archive/tarzstd/tarzstd_extractor.go:57-64`), showing the invariant is known and enforced in one code path but missing in the other.

Because extraction runs relative to the process's current working directory (`os.Getwd()` in `Execute`), a zip entry name such as `../../etc/cron.d/evil` or an absolute path resolves outside `wd` and is written there, or a symlink entry can be planted pointing outside the sandbox before subsequent same-named "regular file" entries write through it.

### Impact Explanation
If an attacker can get a crafted zip cache archive accepted as the downloaded/local cache file (per the stated precondition), extraction can create/overwrite files outside the job working directory — e.g., in the shared helper container filesystem, `/builds` sibling job directories, or other paths reachable from the extraction process's cwd — matching the scoped impact of cross-tenant/workspace corruption via extraction.

### Likelihood Explanation
Requires the stated precondition (an attacker-crafted archive being accepted as the cache payload). Given that precondition, exploitation is trivial and deterministic: any zip entry with `../` segments or an absolute path is honored verbatim. The `.zip` format is the default/legacy cache format (cache files are named `.zip` per `commands/helpers/cache_extractor.go:576-579`), so this path is reachable by default cache handling, not an edge case.

### Recommendation
Add the same containment check used by `tarzstd` to zip extraction: for each `file.Name`, resolve `filepath.Abs(filepath.Join(dir, file.Name))` and reject the entry if it does not have `dir` as a prefix (or use `filepath.Rel` and reject `..`-prefixed results) before calling `os.MkdirAll`/`os.Create`/`os.Symlink`. This requires threading the `dir` parameter through `ExtractZipArchive`/`extractZipFile` (currently unused in `ziplegacy.extractor`) and applying it consistently, including for symlink targets.

### Proof of Concept
Go unit test in `helpers/archives`:
```go
func TestExtractZipArchive_RejectsPathTraversal(t *testing.T) {
    tmp := t.TempDir()
    zipPath := filepath.Join(tmp, "evil.zip")
    f, _ := os.Create(zipPath)
    zw := zip.NewWriter(f)
    w, _ := zw.Create("../../evil.txt")
    w.Write([]byte("pwned"))
    zw.Close()
    f.Close()

    wd := filepath.Join(tmp, "workdir")
    os.MkdirAll(wd, 0755)
    os.Chdir(wd) // simulate CacheExtractorCommand's wd

    err := ExtractZipFile(zipPath)
    require.NoError(t, err) // current behavior: no error

    _, statErr := os.Stat(filepath.Join(tmp, "evil.txt")) // outside wd
    assert.NoError(t, statErr, "file was written outside wd — path traversal succeeded")
}
```
Expected (fixed) behavior: `ExtractZipArchive`/`ExtractZipFile` should return an error for the traversal entry, and `evil.txt` should never be created outside `wd`, analogous to `tarzstd`'s existing `"cannot be extracted outside of chroot"` test coverage.
