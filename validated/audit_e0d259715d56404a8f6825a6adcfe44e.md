### Title
Node-side signature/rejection tallying lets a stale acceptance survive a signer's later rejection, letting retracted signatures still count toward the signing threshold - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The `StackerDBListener` that the miner-side `SigningCoordinator` uses to tally signer responses for a proposed block keeps two independent weight counters, `total_weight_approved` and `total_weight_rejected`, gated by two independent, non-interacting dedup sets (`gathered_signatures` for accepts, `responded_signers` for both). A signer that first accepts (signs) a block and later legitimately re-evaluates and rejects the same block — a transition the signer's own state machine explicitly allows (`LocallyAccepted → LocallyRejected`) — has its rejection silently dropped by the node's tally, while the earlier signature remains counted toward `total_weight_approved` forever. This is the direct analog of the ERC1155 report: two parallel "balance" trackers (accept-weight vs. reject-weight) are updated independently, and pruning/retracting one side does not update the other, so a state that should no longer be valid (the earlier signature) keeps being usable.

### Finding Description
`BlockStatus` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` tracks: [1](#0-0) 

On `BlockResponse::Accepted`, the code adds the signer's weight to `total_weight_approved` only if the slot isn't already in `gathered_signatures`, then unconditionally inserts the slot into both `gathered_signatures` and `responded_signers`: [2](#0-1) 

On `BlockResponse::Rejected`, the code adds the signer's weight to `total_weight_rejected` only if `responded_signers.insert(slot_id)` returns `true` (i.e., the slot wasn't already present): [3](#0-2) 

Because the Accepted branch already inserted the slot into `responded_signers` at line 465, a later legitimate rejection from the same signer for the same block finds `responded_signers.insert(slot_id)` returning `false` and is therefore never added to `total_weight_rejected`. Nothing in either branch removes the slot from `gathered_signatures` or decrements `total_weight_approved` when a rejection later arrives. The stale signature — over a block the signer has since determined should not be finalized — remains fully counted toward the acceptance threshold, and the rejection carries zero effective weight.

This transition (sign, then reject on re-evaluation) is not hypothetical: the signer's own `BlockState` model explicitly documents and implements it. [4](#0-3) 

The signer broadcasts this later verdict via the normal rejection path (`handle_block_rejection`/`store_and_process_block_rejection` in `stacks-signer/src/v0/signer.rs`), sending a `BlockResponse::Rejected` for a block it previously accepted and signed — the same message type the node's listener processes above.

### Impact Explanation
This breaks the equality the coordinator relies on: "signature weight currently counted toward acceptance" should reflect signers' *current* verdicts, not a union of every verdict ever sent. A signer who signs, then legitimately retracts via rejection (e.g., because a conflicting block was later signed, or a chainstate re-check failed), cannot get its weight removed from `total_weight_approved` in `SigningCoordinator`/`stackerdb_listener.rs`. If enough signers' historical (now-retracted) signatures are what pushes `total_weight_approved >= self.weight_threshold`, the miner treats the block as approved and pushes it to the node — effectively a rejection being (mis-)counted as an ongoing acceptance, the exact "rejection recounted as an accept" class called out as Critical impact. This can let a block reach the network as finalized/pushed based on stale, no-longer-endorsed signatures, i.e., a form of the miner acting on signatures that the signing quorum has already withdrawn.

### Likelihood Explanation
Triggering this needs only a single well-behaved signer legitimately re-evaluating and rejecting a block it already signed — a state transition the codebase itself models and permits (`LocallyAccepted → LocallyRejected` in `signerdb.rs`/`signer.rs`) and that can occur under ordinary conditions (a competing/conflicting block later reaching the pre-commit threshold, or a chainstate recheck failing after signing due to a race with another proposal). No majority collusion, no additional keys, and no StackerDB-transport tricks are required — a lone signer's ordinary, in-protocol vote sequence (accept, then later reject) is sufficient to leave stale weight in the miner's tally.

### Recommendation
- Short term: in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, when processing `BlockResponse::Rejected`, if the slot is already present in `block.gathered_signatures`, remove it and subtract the signer's weight from `total_weight_approved` before (or in addition to) any rejection-weight accounting, so the two counters cannot diverge from a signer's latest verdict. Symmetrically, treat a slot present in the reject-only `responded_signers` set (from a prior rejection) consistently when a later Accepted arrives.
- Long term: track a single per-signer "latest verdict" (accept-with-signature vs. reject) instead of two independently-updated weight totals and two different dedup sets, and derive `total_weight_approved`/`total_weight_rejected` from that single source of truth on every update.

### Proof of Concept
1. Miner proposes block B to signer set S with weight threshold T.
2. Signer X (weight w) validates B, signs, and broadcasts `BlockResponse::Accepted` — node's `StackerDBListener` adds w to `total_weight_approved`, inserts X's slot into `gathered_signatures` and `responded_signers`.
3. Before B crosses T, another block reaches a competing state in X's local view (e.g., a sibling proposal at the same height in another tenure crosses X's pre-commit threshold, or a chainstate recheck at signing time later fails) causing X's local signer state machine to legitimately transition `LocallyAccepted → LocallyRejected` and broadcast `BlockResponse::Rejected` for B (per `docs/signer-flows.md` section 2 and `handle_block_rejection` in `stacks-signer/src/v0/signer.rs`).
4. Node's `StackerDBListener` receives the rejection: `responded_signers.insert(X_slot)` returns `false` (already inserted in step 2), so `total_weight_rejected` is **not** incremented, and X's weight/signature is never removed from `total_weight_approved`/`gathered_signatures`.
5. If accumulated `total_weight_approved` (including X's stale w) reaches T from other signers' contemporaneous accepts, the coordinator (`signer_coordinator.rs`) treats the block as approved and pushes it, even though X has withdrawn its endorsement. [5](#0-4)
