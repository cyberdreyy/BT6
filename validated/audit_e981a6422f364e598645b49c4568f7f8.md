### Title
External initiator credentials bypass job/EI binding and can trigger arbitrary jobs by numeric ID via `PipelineRunsController.Create` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` sets the same `SessionUserKey` context value used for real authenticated users, hardcoded to `UserRoleRun`, with no external-initiator/job binding attached. `PipelineRunsController.Create` uses `auth.GetAuthenticatedUser(c)` merely to check "is *some* user object present" (`isUser`) before running the int32-ID job-run path, so a valid EI credential satisfies `isUser == true` and can trigger `RunJobV2` for any job ID, not just a job bound to that initiator.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is mounted in the `userOrEI` group with three alternative auth methods tried in order — `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession` — behind `auth.RequiresRunRole`: [1](#0-0) 

`AuthenticateExternalInitiator` validates the EI's AccessKey/Secret against the `external_initiators` table, then unconditionally sets a fabricated user object with `UserRoleRun` on the same context key (`SessionUserKey`) used for real session/token users, without recording any binding to a specific job: [2](#0-1) 

`RequiresRunRole` only checks `user.Role != UserRoleView`, so the fabricated EI "user" passes: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code comment claims "only users are allowed to run jobs using int IDs - EIs not allowed," but the actual check is `_, isUser := auth.GetAuthenticatedUser(c)`, which is `GetAuthenticatedUser`'s presence check on `SessionUserKey` — a key that is populated identically for EI-authenticated requests: [4](#0-3) [5](#0-4) 

Since `isUser` is true for an EI request too, the numeric-ID branch executes `prc.App.RunJobV2(ctx, jobID, nil)` for whatever `:ID` is supplied in the URL, with no check that the job is associated with the authenticated external initiator (job/EI binding, historically expressed via matching `externalJobID`/EI-name in webhook specs, is now entirely absent from this code path since webhook jobs were removed per `job.ErrJobTypeRemoved`). Any valid EI credential can therefore trigger a run for any job in the node by supplying its integer job ID.

### Impact Explanation
An external-initiator credential (job-runner-only role, intended to be scoped to triggering a specific bound job) can trigger pipeline runs for arbitrary jobs on the node — cross-EI/cross-job unauthorized run execution. Depending on the job's tasks, this can cause unauthorized transaction submission, unwanted OCR/direct-request executions, or resource abuse, matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Only a valid EI AccessKey/Secret pair is required (obtainable by any party legitimately or illegitimately holding one EI's credentials) — no admin/edit/session privileges needed. The attack is a single unauthenticated-role HTTP `POST /v2/jobs/<any int ID>/runs` request with the EI's headers; fully repeatable and requires no race condition or timing.

### Recommendation
Distinguish EI-authenticated "users" from real session/token users, e.g. by setting a distinct context key or a `User` field flagging `IsExternalInitiator` plus the associated EI name/ID, and have `PipelineRunsController.Create` check that flag directly (not merely `GetAuthenticatedUser` presence) so EI credentials cannot use the int32 `RunJobV2` path unless the target job is actually bound to that specific external initiator. Re-introduce (or restore) a job/EI binding check before invoking `RunJobV2` for EI-authenticated requests.

### Proof of Concept
1. In a `web` package integration test using `cltest.NewApplicationWithConfig`, create two jobs, `jobA` and `jobB` (e.g., simple OCR or direct-request jobs with distinct IDs).
2. Register external initiator `EI-A` via `POST /v2/external_initiators`, capture its `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/<jobB.ID>/runs` (numeric ID of a job unrelated to `EI-A`) using `EI-A`'s `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers via `cltest.UnauthenticatedPost`.
4. Assert the response status is `200`/`201` (run created) and that `pipeline_runs` table gained a row for `jobB` — proving `EI-A` triggered a job it has no configured binding to.
5. Contrast with expected behavior: assert instead that the response should be `401`/`403` once binding is enforced, and that `pipeline_runs` count for `jobB` stays unchanged when using unrelated EI credentials.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

	obj, ok := c.Get(SessionUserKey)

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (prc *PipelineRunsController) Create(c *gin.Context) {
	ctx := c.Request.Context()
	respondWithPipelineRun := func(jobRunID int64) {
		pipelineRun, err := prc.App.PipelineORM().FindRun(ctx, jobRunID)
		if err != nil {
			jsonAPIError(c, http.StatusInternalServerError, err)
			return
		}
		res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
		jsonAPIResponse(c, res, "pipelineRun")
	}

	idStr := c.Param("ID")

	// Webhook runs used external job UUIDs; that job type has been removed.
	if _, err := uuid.Parse(idStr); err == nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, fmt.Errorf("cannot run job of type %q: %w", job.Webhook, job.ErrJobTypeRemoved))
		return
	}

	_, isUser := auth.GetAuthenticatedUser(c)
	// only users are allowed to run jobs using int IDs - EIs not allowed
	if isUser {
		// Is it an int32? Then process it regardless of type
		var jobID int32
		jobID64, err := strconv.ParseInt(idStr, 10, 32)
		if err == nil {
			jobID = int32(jobID64)
			jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
			if err != nil {
				jsonAPIError(c, http.StatusInternalServerError, err)
				return
			}
			respondWithPipelineRun(jobRunID)
			return
		}
	}

	jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("bad job ID"))
}
