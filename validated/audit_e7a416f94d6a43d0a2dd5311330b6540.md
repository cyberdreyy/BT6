### Title
Unauthenticated APR overwrite while `idleCDO` is unset lets an attacker inflate borrower interest owed to early depositors - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog of CVE-2015-8787 (a network packet reaching an incompletely configured interface hits a missing check): `IdleCreditVault.setApr` deliberately skips its caller check when `idleCDO == address(0)`, i.e. while the vault is "incompletely configured" between `initialize` and `setWhitelistedCDO`. Any unprivileged EOA can call `setApr`/`setAprs` in that window and pin `lastApr`/`unscaledApr` to the `DEFAULT_MAX_APR` cap of `20e18` (2000% scaled APR). Once the owner links the CDO and the epoch machine runs, `IdleCDOEpochVariant.startEpoch` computes `expectedEpochInterest` from the attacker-set APR via `_calcInterest(getContractValue())`, and the honest borrower is billed that inflated amount, which is distributed to tranche holders — including the attacker who deposited.

### Finding Description
- `setApr` at `IdleCreditVault.sol:225-235` only enforces `msg.sender == idleCDO || msg.sender == manager` when `idleCDO != address(0)`. During setup (`token` set, `idleCDO` still zero) the call is fully permissionless, bounded only by `maxApr` (default `20e18`, set in `initialize` at line 143).
- `setAprs`/`setAprsWithBuffer` (lines 206-220) funnel through the same unguarded path, so both `unscaledApr` and `lastApr` are attacker-controlled.
- After `setWhitelistedCDO` (line 954) wires the vault to `IdleCDOEpochVariant`, nothing re-validates the APR: `startEpoch` (IdleCDOEpochVariant.sol:233-262) calls `_skimDonatedAssets`, then `_calcInterest(getContractValue())` using `lastApr` scaled over `epochDuration + bufferPeriod`, and stores the result in `expectedEpochInterest`. The borrower must repay `pendingWithdraws + expectedEpochInterest` at `stopEpoch`.
- The attacker deposits into the AA/BB tranche during the buffer phase (KYC is satisfiable per the threat model), so the inflated, borrower-funded interest accrues to attacker-held tranche tokens via the normal `_updateAccounting`/`virtualPrice` gain split.
- Existing guards do not stop it: the skim only removes raw donations, `maxApr` merely caps at 20e18, and there is no "APR was set post-initialization by CDO/manager" flag. The only mitigation is operational (linking the CDO in the same transaction as `initialize`, which the factory may do, but the contract surface itself does not enforce it).

### Impact Explanation
Direct theft: the borrower — treated as honest — is forced to repay principal plus interest computed at up to `20e18` scaled APR, orders of magnitude above the intended rate. For a vault with TVL `T` and epoch+buffer of ~1 year, `expectedEpochInterest ≈ 20 * T`; even a short epoch yields a multiple of T. The attacker claims this through tranche redemptions; the loss is bounded only by what the borrower can repay, and a partial repayment still over-pays the attacker pro rata before other creditors.

### Likelihood Explanation
Requires the deployment/upgrade window where `initialize` has run but `setWhitelistedCDO` has not — exactly the "incompletely configured" state of the CVE. It is a narrow but real window: front-runnable on public mempool deployments, and always present on any vault whose CDO link is set in a later transaction or where `setWhitelistedCDO` is re-pointed after `idleCDO` was cleared. No privileged cooperation is needed; the attacker only needs to be a KYC-passing lender to harvest the inflated yield.

### Recommendation
Remove the setup bypass: gate `setApr`/`setAprs`/`setAprsWithBuffer` behind `msg.sender == idleCDO || msg.sender == manager` unconditionally (allow `manager` to seed the initial APR instead), or require `idleCDO != address(0)` and record the APR atomically at CDO-link time. Alternatively, have `startEpoch` ignore `lastApr` unless it was written after `idleCDO` was set.

### Proof of Concept
```solidity
// Foundry fork PoC (schematic)
IdleCreditVault vault = IdleCreditVault(factory.deployVault(...)); // initialize() runs, idleCDO == 0

// Attacker acts before owner calls setWhitelistedCDO
vm.prank(attacker);
vault.setAprs(20e18, 20e18); // no NotAllowed revert; lastApr = maxApr cap

// Honest owner links the CDO
vm.prank(owner);
vault.setWhitelistedCDO(address(cdoEpoch));

// Attacker deposits during buffer phase
vm.startPrank(attacker);
underlying.approve(address(cdoEpoch), amount);
cdoEpoch.depositAA(amount);
vm.stopPrank();

// Honest manager starts the epoch; expectedEpochInterest uses attacker APR
vm.prank(manager);
cdoEpoch.startEpoch();
assertEq(vault.lastApr(), 20e18);                  // attacker-written APR persisted
assertGt(cdoEpoch.expectedEpochInterest(), legitimateInterest); // borrower billed inflated interest
```

Caveat: I could not fully verify whether `IdleCreditVaultFactory` always links the CDO in the same transaction as `initialize` (which would reduce the attack to a front-running/misconfiguration window rather than a guaranteed one), nor whether this setup bypass is already documented as intended behavior. The unauthenticated `setApr` path itself is confirmed at `contracts/strategies/idle/IdleCreditVault.sol:225-235`.
