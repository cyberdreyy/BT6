### Title
Post-default withdraw requests pay 1:1 from the shared default recovery reserve, stealing funds earmarked for defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The libigl bug class — attacker-controlled input overflowing the bounds of the structure it was written into — maps here to receipt accounting that writes past the bounds of the reserve meant to back it. `requestWithdraw` after `defaultRecoveryFinalized` mints a receipt and stores `postDefaultRequests[_user]`, and `_claimPostDefaultWithdrawRequest` pays it 1:1 via `_transferDefaultRecovery`, which blindly decrements `defaultRecoveryReserve` (lines 915-916). That reserve was sized in `finalizeDefaultRecovery` as `recoveredAmount + prefundedReserve + defaultRecoveryReserve` to cover exactly the pre-finalization claim basis at `defaultRecoveryPrice` (lines 685-692). No new underlying is added when a post-default receipt is created — `requestWithdraw` burns CDO strategy tokens but performs no token pull (lines 247-257) — so every post-default payout draws down recovery funds that belong to earlier defaulted claimants.

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `defaultRecoveryFinalized` is true the code mints `_amount` receipt tokens and records `postDefaultRequests[_user] = _amount` without transferring or reserving any underlying:

```solidity
_burn(msg.sender, _amount);
_mint(_user, _amount);
postDefaultRequests[_user] = _amount;
```

`_claimPostDefaultWithdrawRequest` then pays the full `_amount` from `defaultRecoveryReserve`. The reserve was computed only as enough to pay the pre-finalization basis (`activeBasis + pendingBasis`) times `recoveryPrice`; nothing funds post-default requests. Unlike `_transferFundedClaim`, which explicitly guards `balance - reserve >= _amount` to protect the reserve (lines 899-905), `_transferDefaultRecovery` has no bound check tying total recovery payouts to the finalized basis.

### Impact Explanation
A KYC-passing lender holding tranche tokens after `finalizeDefaultRecovery` calls `requestWithdraw` on the CDO, receives a post-default receipt, and immediately claims it 1:1 at the already-haircut amount — consuming the isolated reserve at a better effective rate than defaulted-epoch claimants, who only recover `claimBasis * defaultRecoveryPrice`. Each such claim permanently reduces `defaultRecoveryReserve`, so earlier defaulted receipt holders (normal, APR0, and instant requests finalized into recovery) find their claims underfunded or reverting on transfer: direct theft plus permanent freezing of unclaimed recovery. The loss equals the cumulative post-default payouts diverted from the reserve.

### Likelihood Explanation
Requires only the pool to be in the finalized-default phase and the attacker to hold any tranche tokens (acquirable on the open market or via earlier deposits). No privileged cooperation is needed; `_ensureDefaultRecoveryInitialized`, the `_onlyIdleCDO` gate, and the funded-claim guard do not stop it because the drain happens inside `_transferDefaultRecovery` itself. Uncertainty: if the CDO separately transfers underlying to the vault when routing a post-default request, the reserve drain would be offset — I could not fully verify the CDO-side `requestWithdraw` funding path within available iterations; the strategy code itself performs no such pull.

### Recommendation
Fund post-default receipts from a distinct bucket instead of `defaultRecoveryReserve` — e.g., track `postDefaultReserve` incremented by an explicit underlying transfer from the CDO/borrower at request time, and pay post-default claims via a `_transferFundedClaim`-style path that cannot touch the recovery reserve. Alternatively, revert post-finalization `requestWithdraw` until all defaulted claims are settled.
