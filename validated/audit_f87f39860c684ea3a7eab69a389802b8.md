### Title
Miner can indefinitely suppress the block-proposal inactivity timeout by pulsing conflicting/stale proposals — ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
The signer's "current miner timed out" check (`SortitionState::is_timed_out`) is meant to detect an unresponsive/misbehaving miner and fall back to the prior tenure after `block_proposal_timeout` of inactivity. However, the activity clock it reads (`last_activity_time`) is refreshed not only by legitimate progress but also by cheap, rejected, non-advancing proposals. A miner can "pulse" a conflicting/stale block proposal just before the timeout window closes, resetting the clock, and repeat this indefinitely — mirroring the reported "delinquency pulse" pattern where a borrower briefly restores a threshold condition right before a grace period expires to avoid ever being marked delinquent.

### Finding Description
`SortitionState::is_timed_out` (v1: `stacks-signer/src/chainstate/v1.rs:52-94`; v2: `stacks-signer/src/chainstate/v2.rs:45-89`) computes `elapsed = now - last_activity`, where `last_activity` comes from `SignerDb::get_last_activity_time` (falling back to the burn-block receive time if never set), and declares the tenure timed out only if `elapsed > block_proposal_timeout`.

`last_activity_time` is written by `SignerDb::update_last_activity_time` (`stacks-signer/src/signerdb.rs:2248-2257`), and the call site that drives this for an in-progress tenure is `SortitionData::check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:376-448`): [1](#0-0) 

This function runs at proposal arrival, at validate-ok, and at signing time (per `docs/signer-flows.md:389-420`) and is invoked with `tenure_id` equal to the block's *own* tenure when checking `confirms_latest_block_in_same_tenure` for non-tenure-change blocks. Concretely:
- If the proposal's `chain_length` does not exceed the last signed block in its own tenure, the proposal is rejected as non-advancing — but the code still refreshes `last_activity_time` for that tenure as long as the reference block hasn't aged past `reorg_attempts_activity_timeout` (or has no `signed_group` timestamp at all, i.e., only locally accepted).
- Separately, if the proposal merely conflicts with a *pre-committed* (unsigned) block that's still "fresh" (`stacks-signer/src/chainstate/mod.rs:422-448`), the activity timer is refreshed too, again without the proposal doing anything toward chain progress.

Neither branch requires the proposal to be valid, canonical, or make any forward progress — it only has to be shaped so it doesn't outright fail earlier checks (matching consensus hash, recoverable miner pubkey, etc.), and to arrive from the single miner who won that sortition (no majority of other parties needed).

Because `is_timed_out` is what gates `SortitionMinerStatus::InvalidatedBeforeFirstBlock` in `check_proposal` (`stacks-signer/src/chainstate/v1.rs:144-163`), and because that invalidation is itself the prerequisite the miner-coordination docs describe for allowing the *previous* miner to tenure-extend (`docs/signing.md:61-96`, `sample/conf/mainnet-miner-conf.toml:211-235`), a miner that never intends to build a valid, advancing tenure can nonetheless keep itself perpetually "Valid" by re-issuing a cheap conflicting/stale proposal at an interval shorter than `block_proposal_timeout`. This is directly analogous to the reported bug class: a state whose "grace/timeout" clock resets on a low-cost action that does not resolve the underlying delinquency (here: an unresponsive/malicious miner never producing an accepted block), letting the actor dodge the intended consequence indefinitely within the life of that tenure.

### Impact Explanation
While this tenure is held hostage, the signer set:
- never marks the current miner `InvalidatedBeforeFirstBlock`, and therefore
- never permits the previous miner to legitimately tenure-extend (both miner and signer configs gate tenure-extend on this invalidation happening first),

so the network gets no new canonical blocks from this tenure and no fallback to the prior miner either, until the next Bitcoin sortition naturally rotates the tenure. This is a liveness wedge on the signer/miner coordination state machine reachable by a single miner (one sortition winner) plus ordinary stackerdb gossip of proposals — no majority of other signers or another signer's key is required.

### Likelihood Explanation
Moderate-to-high for a miner willing to sacrifice its own block rewards to grief the network: it only needs to construct proposals that reuse or slightly modify an already-seen conflicting/lower/pre-committed block header and re-broadcast one before each `block_proposal_timeout` window elapses. No cryptographic breakage or majority collusion is needed, since these are ordinary miner-signed proposals rejected on chain-length grounds, not signature or consensus checks.

### Recommendation
Do not let non-advancing / rejected proposals refresh the same activity clock that gates `is_timed_out`/miner invalidation indefinitely. Options analogous to the report's remediation:
- Track activity resets cumulatively/capped per-tenure (e.g., only allow a bounded number of resets, or a bounded total grace budget) rather than allowing the clock to be pushed out forever by repeated low-cost pulses.
- Require a proposal to be "activity" only if it clears additional legitimacy bars (e.g., only pre-commit-worthy proposals, not any conflicting/stale one), or decouple the reorg/pre-commit "count-as-activity" logic in `check_latest_block_in_tenure` from the miner-timeout clock consulted by `is_timed_out`, so the timeout is driven strictly by progress (new signed/pre-committed blocks that actually advance chain height), not by mere resubmission of stale/conflicting proposals.

### Proof of Concept
1. Miner M wins a sortition and becomes `cur_sortition` with `miner_status = Valid`.
2. M proposes (or the network already has) an accepted/pre-committed block B at height H in M's tenure.
3. M repeatedly broadcasts a new proposal B′ with `chain_length <= H` (conflicting with B or with a fresh pre-commit), timed so each is received before `block_proposal_timeout` elapses since the previous refresh.
4. Each such proposal is routed through `check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:390-417` or `:422-448`), which rejects the proposal but calls `signer_db.update_last_activity_time(&block.header.consensus_hash, now)`.
5. `SortitionState::is_timed_out` therefore never sees `elapsed > block_proposal_timeout`, so `check_proposal` never sets `SortitionMinerStatus::InvalidatedBeforeFirstBlock`.
6. The previous miner can never satisfy the gate to tenure-extend, and the signer set continues waiting on M's tenure, which never produces a globally accepted block — reproducing the "borrower stays delinquent forever by pulsing right before grace expiry" pattern in the miner/signer inactivity mechanism.

Note: I was not able to execute this scenario against a running signer/test harness (no filesystem/terminal access here); the above is derived purely from reading the cited logic paths. A background Devin session with repo access could write an integration test (mirroring `stacks-node/src/tests/signer/v0/reorg.rs`'s existing `reorg_attempts_activity_timeout` tests) to empirically confirm the clock never expires under repeated pulsing.
