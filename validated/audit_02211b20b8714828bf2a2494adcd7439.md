### Title
Response/error `id` corruption when client-supplied `req.ID` contains a literal `"::"` substring on paths that never apply an owner prefix - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
`sendSuccessResponse` and `errorResponse` unconditionally strip everything up to and including the **first** occurrence of `vaulttypes.RequestIDSeparator` (`"::"`) from the request/response ID, assuming that substring always marks an owner-prefix boundary added by `GatewayVaultRequestProcessor.authorizeAndStamp`. On several reachable code paths the ID is never owner-prefixed before this stripping happens, so a client-chosen ID that legitimately contains `"::"` is truncated, breaking the JSON-RPC 2.0 requirement that `response.id == request.id`.

### Finding Description
The prefixing scheme only exists inside `authorizeAndStamp` in `core/capabilities/vault/gateway_vault_request_processor.go`, which sets `req.ID = authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID` [1](#0-0) . `sendSuccessResponse`/`errorResponse` blindly assume every ID they see went through that stamping and strip up to the first `"::"` [2](#0-1) [3](#0-2) .

Several call sites reach `errorResponse`/`sendSuccessResponse` with a raw, never-prefixed, attacker-controlled `req.ID`:

1. **Unsupported method path**: in `HandleJSONRPCUserMessage`, if `req.Method` is not `vaulttypes.MethodPublicKeyGet` and not a gateway secrets method, `sendImmediateUserResponse` is called directly on the raw client `req` before any authorization or prefixing occurs [4](#0-3) , which calls `errorResponse(req, ...)` [5](#0-4) .

2. **Invalid-params path**: `ProcessRequest` validates request structure and returns `InvalidVaultParamsError` *before* calling `authorizeAndStamp` (which does the prefixing) — see the per-method processors, e.g. `processCreateSecretsRequest`, where validation happens before `p.authorizeAndStamp(...)` is invoked [6](#0-5) . On this error, `HandleJSONRPCUserMessage` calls `h.sendImmediateUserResponse(ctx, req, callback, api.InvalidParamsError, err)` with the still-unprefixed `req.ID` [7](#0-6) .

3. **`vault.publicKey.get` path**: this method bypasses `requestProcessor.ProcessRequest` (and therefore the owner-prefix stamping) entirely [8](#0-7) . When the cache misses, the raw client ID is fanned out to nodes and the node's `resp.ID` (identical to the client's raw ID) is passed to `sendSuccessResponse`, which still applies the `"::"`-stripping logic meant only for owner-prefixed IDs [2](#0-1) .

In all three cases, if the attacker supplies `req.ID` such as `"abc::123"` (which passes the only validation: non-empty and ≤200 chars [9](#0-8) ), the stripping logic misinterprets `"abc"` as an owner prefix and returns `"123"` to the client instead of the original `"abc::123"`, violating the JSON-RPC id-echo invariant.

### Impact Explanation
This causes cross-request/response ID confusion on the client side for a legitimate, authenticated caller — the client cannot reliably correlate its own request with the returned response, which can break client-side retry/dedup/correlation logic and downstream automation. It does not directly leak secrets, escalate privileges, or perform an action on another user's data; the impact is scoped to protocol-correctness/client-side confusion (matches a "logic error / spec-violation" class rather than authentication or authorization bypass).

### Likelihood Explanation
Trivially reproducible by any caller able to submit a `vault.*` JSON-RPC request through the gateway (unauthenticated for `vault.publicKey.get`/unsupported methods, or requiring only a session/credential capable of sending a request with invalid params for the secrets methods). No special privilege is required — the attacker only needs to choose an ID containing `"::"`. It's deterministic and repeatable on every request that hits one of the three paths above.

### Recommendation
Do not use a heuristic substring search to reverse the owner-prefix stamping. Instead, only strip the prefix when the handler control-flow logically knows the ID was stamped by `authorizeAndStamp` (i.e., track/pass a boolean or use `strings.Cut` against the exact known-authorized-owner value it stamped, not any `"::"` in the string), and skip the stripping step entirely for `vault.publicKey.get` and any error paths that fire before authorization/prefixing occurred (unsupported-method / invalid-params). Alternatively, carry the *original* client-submitted ID through the request lifecycle in a separate field, and always echo that verbatim in responses instead of trying to reverse-derive it from a mutated `req.ID`/`resp.ID`.

### Proof of Concept
Go table test in `core/services/gateway/handlers/vault/handler_test.go`:
1. For `errorResponse`: construct `jsonrpc.Request[json.RawMessage]{ID: "abc::123", Method: "vault.secrets.unsupported"}` and call `h.errorResponse(req, api.UnsupportedMethodError, err, nil)`; decode the raw response and assert the returned `id` equals `"abc::123"` (currently fails, returns `"123"`).
2. For `sendSuccessResponse` on the `vault.publicKey.get` path: simulate a cache-miss public key request with `req.ID = "owner1::reqA"` submitted directly by a client (not stamped by `authorizeAndStamp`), have a mock node reply with `resp.ID` identical to the submitted ID, and assert the final callback payload's `id` matches the original client ID exactly rather than being truncated to `"reqA"`.
3. For the invalid-params path: submit `vault.secrets.create` with a malformed params body and `req.ID` containing `"::"` before authorization runs; assert the `InvalidParamsError` response's `id` equals the original submitted ID.

```go
func (h *handler) sendSuccessResponse(ctx context.Context, l logger.Logger, ar *activeRequest, resp *jsonrpc.Response[json.RawMessage]) error {
	// Strip the owner prefix from the response ID before sending it back to the user
	// This ensures compliance with JSONRPC 2.0 spec, which requires response id to match request id
	index := strings.Index(resp.ID, vaulttypes.RequestIDSeparator)
	if index != -1 {
		resp.ID = resp.ID[index+2:]
	}
```

```go
func (h *handler) sendImmediateUserResponse(
	ctx context.Context,
	req jsonrpc.Request[json.RawMessage],
	callback gwhandlers.Callback,
	errorCode api.ErrorCode,
	err error,
) error {
	switch errorCode {
	case api.InvalidParamsError, api.UnsupportedMethodError, api.UserMessageParseError:
		h.metrics.requestUserError.Add(ctx, 1, metric.WithAttributes(
			attribute.String("don_id", h.donConfig.DonId),
		))
	default:
	}
	return callback.SendResponse(h.errorResponse(req, errorCode, err, nil))
}
```
