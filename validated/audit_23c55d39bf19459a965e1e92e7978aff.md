### Title
Builder withdrawal `amount` sent to the execution layer is not capped to the builder's actual balance, while the CL-side balance deduction is - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` copies the *requested* `BuilderPendingWithdrawal.amount` verbatim into the `Withdrawal.amount` field that is committed to `state.payload_expected_withdrawals` and which the execution layer is required to honor. `apply_withdrawals`, however, only debits the builder's CL balance by `min(withdrawal.amount, builder_balance)`. When a builder's balance at settlement time is lower than the committed withdrawal amount, the EL pays out the full uncapped amount while the CL only removes the smaller, capped amount from `state.builders[...].balance` — this is the exact "cap one side, forget the other" pattern from the TellerV2 `_repayLoan` bug.

### Finding Description
In `get_builder_withdrawals` (`specs/gloas/beacon-chain.md:1802-1834`), the withdrawal that will end up in `state.payload_expected_withdrawals` is built as: [1](#0-0) 

```python
withdrawals.append(
    Withdrawal(
        index=withdrawal_index,
        validator_index=convert_builder_index_to_validator_index(builder_index),
        address=withdrawal.fee_recipient,
        amount=withdrawal.amount,
    )
)
``` [2](#0-1) 

`withdrawal.amount` is copied unchanged from `state.builder_pending_withdrawals`, with **no clamp against the builder's actual current balance**.

`process_withdrawals`'s own doc-note states this is binding on the execution layer:
"any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer." [3](#0-2) 

Meanwhile, the actual bookkeeping deduction in `apply_withdrawals` **is** capped:

```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [4](#0-3) 

This is structurally identical to the TellerV2 finding: an "owed"/"available" quantity is adjusted (`paymentAmount = _owedAmount` in TellerV2; `min(withdrawal.amount, builder_balance)` here) for internal accounting, but the value that is actually **sent/committed externally** (`_payment` struct in TellerV2; `Withdrawal.amount` here) is left untouched, so external payment and internal accounting diverge.

The spec's own test suite explicitly exercises and asserts this exact divergent state: a builder with only 1 ETH balance but a withdrawal requesting 5 ETH results in `builders[0].balance == 0` (capped) while `payload_expected_withdrawals[0].amount == 5 ETH` (uncapped) is still what's handed to the execution layer: [5](#0-4) 

### Impact Explanation
If a builder's balance at withdrawal-settlement time is lower than the amount committed in `BuilderPendingWithdrawal.amount`/`Withdrawal.amount`, the execution layer credits `fee_recipient` with the full, uncapped amount, while the beacon state only reduces `builder.balance` by the smaller, capped amount. This breaks the "Gwei accounted equals Gwei paid" equality: Gwei is effectively created out of thin air and paid out, which is a Critical-severity condition per the rules ("Gwei created, destroyed or paid to a non-owner").

### Likelihood Explanation
Whether a builder's balance can actually fall below a still-pending committed withdrawal amount depends on whether `can_builder_cover_bid` and `get_pending_balance_to_withdraw_for_builder` (referenced in the table of contents at `specs/gloas/beacon-chain.md`) correctly account for **all** currently-queued `builder_pending_payments`/`builder_pending_withdrawals` for that builder at bid-acceptance time. I was not able to fully inspect the body of `can_builder_cover_bid` within the available context/time to confirm whether it closes this race for multiple concurrently-queued bids/withdrawals from the same builder. If it does not fully account for cumulative pending commitments, this state is reachable through entirely honest, spec-following protocol operation (no malicious peer, coalition, or client bug required) — simply multiple bids/settlements for the same builder overlapping in the pending-withdrawal queue. This uncertainty should be resolved before treating this as a confirmed, currently-exploitable bug, but the code-level equality violation (uncapped `Withdrawal.amount` vs capped balance deduction) is unambiguous and present in the spec text regardless.

### Recommendation
Cap `Withdrawal.amount` to the builder's actual available balance (accounting for other already-queued pending withdrawals for that builder) at the point `get_builder_withdrawals` constructs the `Withdrawal`, mirroring the same `min()` clamp used later in `apply_withdrawals`, so that the amount committed to the execution layer can never exceed what the beacon state will actually deduct — analogous to the TellerV2 recommendation of "adjust the memory struct" so the sent value always matches the internally capped value.

### Proof of Concept
1. Builder `B` accrues (or is credited with) a `BuilderPendingWithdrawal` entry with `amount = X` in `state.builder_pending_withdrawals` (via `settle_builder_payment`, `specs/gloas/beacon-chain.md:1518-1527`, or the direct-append path in `apply_parent_execution_payload`, `specs/gloas/beacon-chain.md:1761-1770`).
2. Before this withdrawal is processed, `state.builders[B].balance` drops below `X` (e.g., another pending withdrawal for the same builder is processed first, or - if `can_builder_cover_bid`/pending-balance accounting is insufficient - simply because multiple bids for `B` were queued concurrently).
3. `process_withdrawals` → `get_expected_withdrawals` → `get_builder_withdrawals` emits `Withdrawal(amount=X, address=fee_recipient, ...)` unchanged (`specs/gloas/beacon-chain.md:1822-1829`), which is placed into `state.payload_expected_withdrawals` — the value the execution layer is bound to pay.
4. `apply_withdrawals` then only deducts `min(X, builder.balance)` from `state.builders[B].balance` (`specs/gloas/beacon-chain.md:1929`), leaving `state.builders[B].balance = 0` while `X - balance` worth of Gwei is still paid out by the EL to `fee_recipient` with no corresponding CL-side backing.
5. This exact scenario (5 ETH requested, 1 ETH balance, withdrawal amount reported as the full 5 ETH, balance capped to 0) is directly demonstrated in `test_builder_withdrawal_insufficient_balance` (`tests/core/pyspec/.../test_process_withdrawals.py:116-156`), confirming the divergent-amount state is a value the spec code can produce.
