### Title
Deterministic-account front-running: attacker's `CreateAccount` + `AddKey` on a not-yet-initialized derived id survives a later `DeterministicStateInitAction`, giving the attacker a full-access key on an account that NEP-616 users will treat as solely controlled by derivation - ([File: runtime/runtime/src/deterministic_account_id.rs])

### Summary
`action_deterministic_state_init`'s "uninit -> active" transition only checks `account.contract().is_none()` before deploying the derived state, and `check_actor_permissions` treats `Action::DeterministicStateInit` as a no-op that never checks `actor_id`. Because the derived account id is a public, deterministic function of the `DeterministicAccountStateInit` content (enforced by `validate_deterministic_state_init` pinning `receiver_id == derive_near_deterministic_account_id(state_init)`), any unprivileged attacker who can compute/observe that id ahead of time can front-run the legitimate deployment with an ordinary `CreateAccount` + `AddKey(FullAccess)` transaction, leaving a still-valid attacker-controlled access key on the account after the deriver's later `DeterministicStateInitAction` executes.

### Finding Description
- `validate_deterministic_state_init` in `runtime/runtime/src/action_validation.rs:435-471` requires `derived_id == receiver_id` where `derived_id = derive_near_deterministic_account_id(&action.state_init)`. This is the entire "authorization" model for deterministic accounts: the id itself is the credential, and it is computable by anyone who knows the `state_init` content (this is the intended NEP-616 counterfactual-address property, analogous to CREATE2 addresses). [1](#0-0) 

- `action_deterministic_state_init` (`runtime/runtime/src/deterministic_account_id.rs:15-94`) only distinguishes "nonexist" (no account) from "uninit" (account exists but `contract().is_none()`). If an account already exists at the derived id with no contract deployed - regardless of how it got there - the code silently treats it as the NEP-616 "uninit" state and deploys the state init on top of it: [2](#0-1) 

- The comment on `create_deterministic_account` documents the *only* defense the authors built: when the account is first materialized via the `DeterministicStateInit` action itself, `actor_id` is deliberately left as the predecessor (not set to `account_id`), specifically "to prevent hijacking the account" and "preventing `AddKey`, `DeployContract`, or any other actions that only the account owner is permitted to do": [3](#0-2) 

  This defense is scoped to the case where the *only* path that created the account is `DeterministicStateInit`. It does nothing for accounts pre-created by an ordinary `CreateAccount` action, where `actor_id` is set equal to `account_id` (standard `CreateAccount` semantics), which is exactly what `check_actor_permissions` also allows unconditionally for `Action::CreateAccount` and treats `Action::DeterministicStateInit` as a no-op for actor checks: [4](#0-3) 

- Attack sequence: an attacker who knows (or can compute) the `state_init` a victim/dapp intends to use for a deterministic account can compute `derived_id` themselves via the same public `derive_near_deterministic_account_id` function, and submit a transaction to that `derived_id` containing `CreateAccount` followed by `AddKey(FullAccess)` in the same receipt, before the legitimate `DeterministicStateInitAction` is ever submitted. This requires the id to be eligible for permissionless top-level creation (length above `AccountCreationConfig.min_allowed_top_level_account_length`), which the question states holds for the derived id format at `PROTOCOL_VERSION` 87. `check_account_existence` for `CreateAccount` only requires `account.is_none()`, which is true because the account doesn't exist yet. After this receipt, the attacker holds a full-access key and `actor_id == account_id` (standard `CreateAccount` behavior).
- Later, when the legitimate deriver submits the real `DeterministicStateInitAction` to the same `derived_id`, `action_deterministic_state_init` finds `maybe_account = Some(account)` (attacker-created, no contract), evaluates `account.contract().is_none()` as true, and deploys the deterministic state on top of the existing account. Nothing in this path removes or invalidates the attacker's previously added access key, and `check_actor_permissions`'s no-op arm for `DeterministicStateInit` never re-validates who is allowed to have keys on the account.
- Net result: the account now runs the deterministically-derived contract/state that the dapp/wallet expects, while an attacker-controlled full-access key silently remains attached to it - a persistent authorization escalation the invariant ("a promise/derived id should never carry keys its rightful deriver never authorized") explicitly forbids.

### Impact Explanation
This is an authorization-escalation / unauthorized-transaction primitive: any wallet, dapp, or protocol that relies on the deterministic-account-id guarantee (i.e., "this address is solely controlled by whoever can produce this exact `state_init`") can have funds/assets sent to, or contract permissions granted on, an account that an unrelated attacker already has a full access key for. This directly enables theft of funds deposited to or routed through the account once the attacker signs transactions with their key (e.g., `Transfer`, further `FunctionCall`, or `DeleteKey` to lock out the legitimate deriver), matching the "Unauthorized transaction" / authorization-escalation bounty category.

### Likelihood Explanation
- The attacker needs no privileges beyond an ordinary funded account able to sign and broadcast transactions to a public RPC endpoint - it satisfies the "unprivileged attacker" constraint.
- The key precondition is that the attacker can predict/compute the `derived_id` before the legitimate `DeterministicStateInitAction` lands. Since `derive_near_deterministic_account_id` is a pure deterministic function of the (public, or externally-knowable) `state_init` content, this is the intended counterfactual-address property of NEP-616 - the same property that makes the derivation useful also makes it front-runnable by anyone with knowledge of the intended `state_init` ahead of time (e.g., factory patterns where code hash and initial data are fixed/predictable, or observed in a pending mempool transaction before it's included).
- The race only requires beating a single receipt to inclusion; on NEAR, an attacker transaction targeting a not-yet-existing account is cheap (top-level account creation + one `AddKey`) and fully repeatable against any deterministic id the attacker can precompute.
- The stated precondition (`min_allowed_top_level_account_length` allowing dotless creation for the derived id's length at `PROTOCOL_VERSION` 87) is required for permissionless `CreateAccount` at that id; I was not able to independently confirm the exact length format of `derive_near_deterministic_account_id`'s output in this session, so this precondition should be verified in the PoC.

### Recommendation
Do not treat "account exists with no contract" as sufficient evidence that an account is a valid NEP-616 "uninit" deterministic account. Options:
1. Mark accounts created via `create_deterministic_account`/the `DeterministicStateInit` path with an explicit account-kind flag, and require that flag (not merely `contract().is_none()`) before allowing the "uninit -> active" transition in `action_deterministic_state_init`.
2. Alternatively, reject `DeterministicStateInitAction` outright if the existing account already has any access keys (i.e., the account was materialized through means other than the deterministic-init flow), since a legitimately "uninit" deterministic account should never have accumulated keys.
3. Ensure `check_actor_permissions` (or an equivalent gate before `action_deterministic_state_init`) actively rejects deployment onto any pre-existing account that isn't provably a fresh deterministic-account shell.

### Proof of Concept
Runtime/test-loop integration test (mirroring `test-loop-tests/src/tests/deterministic_account_id.rs`):
1. Compute `derived_id = derive_near_deterministic_account_id(&state_init)` for a chosen `DeterministicAccountStateInit` (global contract code identifier + data), ensuring its length passes `AccountCreationConfig.min_allowed_top_level_account_length` from `RuntimeConfigStore::new_config()` (or equivalent) at `PROTOCOL_VERSION` 87.
2. Submit attacker transaction #1: receiver = `derived_id`, actions = `[CreateAccount, AddKey(attacker_pubkey, FullAccess)]`, signed/funded by an ordinary attacker account. Apply and assert success (account created, `AccessKey` for `attacker_pubkey` present at `derived_id`).
3. Submit victim transaction #2 (later block/receipt): `Action::DeterministicStateInit(DeterministicStateInitAction { state_init, deposit })` targeting `derived_id`. Apply and assert success (contract deployed, `account.contract()` now `Some(...)`).
4. Assert: an `AccessKey` for `attacker_pubkey` still exists at `derived_id` (query via `TrieKey::AccessKey`), and no `DeleteKey` action was ever executed by the deriver - confirming the attacker retains full-access control over the "deterministically owned" account after legitimate initialization.

fn validate_deterministic_state_init(
    limit_config: &LimitConfig,
    action: &DeterministicStateInitAction,
    receiver_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    validate_global_contract_identifier(action.state_init.code())?;

    let derived_id = derive_near_deterministic_account_id(&action.state_init);

    if derived_id != *receiver_id {
        return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver {
            derived_id,
            receiver_id: receiver_id.clone(),
        });
    }
