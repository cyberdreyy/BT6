### Title
Static (non-symlink-aware) validation of `GIT_CLONE_PATH` in `getCustomBuildDir` allows TOCTOU directory-escape via a pre-planted symlink at the computed `BuildDir` path - ([File: common/build.go])

### Finding Description
`Build.getCustomBuildDir` (common/build.go:473-492) validates a user-supplied `GIT_CLONE_PATH` purely lexically: it computes `filepath.Rel(rootDir, dir)` and rejects the path only if the *string* result starts with `..`. [1](#0-0) 
This check never touches the filesystem — it does not call `os.Lstat`, `filepath.EvalSymlinks`, or any equivalent — so it cannot detect that a directory (or an intermediate path component) already existing on disk at that location is a symlink pointing outside `rootDir`. `StartBuild` (common/build.go:494-534) calls this function once during the prepare stage and stores the accepted string in `b.BuildDir`; the actual filesystem operations (directory creation, `git init`/`git clone`, submodule checkout) happen much later, in the shell script generation (`shells/abstract.go`, e.g. `setupTemplateDir`) or in `functions/concrete/run/stages/get_sources.go`, driven by the executor (`mkdir`, `cd`, native `os.MkdirAll`, git commands). Those later operations use normal OS path resolution, which **does** follow symlinks.

For this to be exploitable an attacker needs write access to the `builds_dir` location that a *later* job's computed `BuildDir` will use, before that job's `StartBuild`/get-sources runs. The realistic precondition is a shared, persistent `builds_dir` (e.g. shell executor, or Docker/Kubernetes with a persistent host-mounted builds volume) combined with slot reuse: `ProjectRunnerID`/concurrency-slot-based path (`b.ProjectUniqueDir`, common/build.go:424-446) can be reused by a different job/pipeline run sequentially on the same runner slot. An attacker who controls a job (their own pipeline) can set `GIT_CLONE_PATH` to a path that passes the lexical `..`-prefix check (it is nominally "within" `rootDir`) but is—or becomes, once the job creates it—a symlink to a location outside `rootDir`. If that symlink persists on the shared builds volume and a later job (their own subsequent job, or possibly another project sharing the same slot/path) computes the same `BuildDir`, that job's checkout will silently write through the pre-existing symlink to the escaped target, because none of the later mkdir/git operations re-validate that the resolved real path is still inside `rootDir`.

### Impact Explanation
If exploited, a job's checkout output (repository contents, `.git` config with credentials/tokens if `safe.directory`/credential files are written there, build artifacts) can be written outside the intended `rootDir`/project tree, potentially into another job's or project's working directory, or into arbitrary filesystem locations reachable from the executor's filesystem namespace. This violates the "file operations must stay within intended build/cache/artifact roots" invariant.

### Likelihood Explanation
Exploitability depends heavily on infrastructure conditions the runner does not fully control: a persistent, shared `builds_dir` across jobs (not the default for containerized executors that use ephemeral volumes), slot/path reuse across job boundaries, and `custom_build_dir` being enabled (it's opt-in and off by default, and disabled by default for the shell executor per `TestBuildWithCustomClonePath`). [2](#0-1)  Even with those preconditions, cross-*project* exploitation additionally requires the attacker to know/predict another project's exact deterministic `BuildDir` path and for that other project's job to actually land in the same reused slot at the right time — a narrow, mostly self-inflicted or same-attacker-controlled scenario rather than a generally reachable cross-tenant attack. No code in the repository (docs, CHANGELOG, or comments) documents this TOCTOU as a known/accepted risk; only the unrelated, already-fixed lexical "`..`" escape (issue 25913) is referenced. [3](#0-2) 

### Recommendation
After computing the candidate `BuildDir` in `getCustomBuildDir`, and again immediately before/at first filesystem use in the executor's prepare/get-sources stage, resolve the real path (`filepath.EvalSymlinks`, falling back gracefully when the path doesn't yet exist) and re-verify it is contained in the resolved `rootDir`; reject with `ConfigurationError` if resolution places it outside. Additionally, before creating/using the build directory, check with `os.Lstat` whether the leaf (or any pre-existing path segment) is a symlink and refuse to proceed (or remove/replace it) rather than following it.

### Proof of Concept
Go unit test sketch for `common/build.go`:
```go
func TestGetCustomBuildDir_SymlinkTOCTOU(t *testing.T) {
    rootDir := t.TempDir()
    outside := t.TempDir()

    // Simulate a prior job planting a symlink at the path a later job
    // will compute for GIT_CLONE_PATH, pointing outside rootDir.
    clonePath := filepath.Join(rootDir, "go/src/gitlab.com/test-namespace/test-repo")
    require.NoError(t, os.MkdirAll(filepath.Dir(clonePath), 0o755))
    require.NoError(t, os.Symlink(outside, clonePath))

    b := &Build{ /* ... minimal Job/Runner setup ... */ }
    dir, err := b.getCustomBuildDir(rootDir, clonePath, true, false)
    require.NoError(t, err) // passes today: only lexical check

    // Simulate later checkout writing into dir (e.g. os.MkdirAll(dir, ...))
    require.NoError(t, os.MkdirAll(filepath.Join(dir, "checkout-marker"), 0o755))

    real, err := filepath.EvalSymlinks(dir)
    require.NoError(t, err)
    // Assertion that should hold but currently fails:
    assert.True(t, strings.HasPrefix(real, rootDir),
        "checkout escaped rootDir via pre-existing symlink: %s", real)
}
```
Expected: with current code, `getCustomBuildDir` returns no error and the final assertion fails, demonstrating the checkout resolves outside `rootDir`. A fix should make `getCustomBuildDir` (or a pre-checkout guard) reject this case, causing the test to fail earlier with a `ConfigurationError` instead of silently writing outside `rootDir`.
