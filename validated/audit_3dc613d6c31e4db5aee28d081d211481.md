### Title
Unchecked NEAR transfer result in `internal_withdraw` desynchronizes the staking pool's ledger from its real NEAR balance - (File: `staking-pool/src/internal.rs`)

### Summary
`staking-pool/src/internal.rs::internal_withdraw` permanently decrements the account's `unstaked` balance and the pool-wide `last_total_balance` ledger and *then* fires a bare `Promise::new(account_id).transfer(amount)` with no `.then()` callback that verifies the transfer actually succeeded. [1](#0-0) 

Every other cross-contract/async action in this same contract and the sibling `lockup` contract follows the opposite, safe pattern: they attach a callback that calls `is_promise_success()` and only commit the ledger change (or roll it back) after the promise resolves — see `on_staking_pool_deposit`, `on_staking_pool_deposit_and_stake`, and `on_staking_pool_withdraw` in `staking-pool/src` and `lockup/src/owner_callbacks.rs`. [2](#0-1) 

### Finding Description
The binding that must hold is: `last_total_balance == actual NEAR balance the contract holds`. This equality is what the pool's reward-detection logic (`ping`) relies on to distinguish real staking rewards (NEAR that showed up on the account without a matching ledger decrease) from ordinary withdrawals.

In `internal_withdraw`:
```
account.unstaked -= amount;
self.internal_save_account(&account_id, &account);
...
Promise::new(account_id).transfer(amount);
self.last_total_balance -= amount;
``` [3](#0-2) 

The state mutations (`account.unstaked -= amount`, `self.last_total_balance -= amount`) are committed synchronously in the same receipt as the function call. The `Promise::new(...).transfer(amount)` is a *separate*, asynchronous receipt whose outcome is never checked — there is no `.then(ext_self::on_withdraw(...))` and no later call to `is_promise_success()`. If that transfer receipt fails for any reason, the NEAR that was supposed to leave the contract never does, yet `last_total_balance` was already reduced as if it had. From that point on, the contract's real NEAR balance is *higher* than `last_total_balance` believes, exactly the kind of desynchronization the external report describes (an un-verified transfer breaking the equality between the ledger and the actual asset holdings) — the same class of bug as H02's unchecked ERC20 transfer, just expressed on the NEAR-native transfer/ledger pair instead of an ERC20 `transfer()` return value.

Contrast this with the deposit/stake/unstake paths in the same contract, all of which are guarded by callbacks and `is_promise_success()`, confirming the withdraw path is the one place in this contract where the check was omitted. [4](#0-3) [5](#0-4) 

The same unguarded pattern exists in `w-near/src/w_near.rs::near_withdraw`, which burns the caller's wNEAR balance via `self.ft.internal_withdraw(...)` and only afterward fires an unguarded `Promise::new(account_id).transfer(amount + 1)`, with no callback verifying the transfer landed. [6](#0-5) 
This breaks the 1:1 invariant `wNEAR minted == NEAR held by wrap.near`: a failed transfer receipt still leaves the wNEAR ledger permanently decremented for tokens whose backing NEAR never left the contract.

### Impact Explanation
If the transfer receipt fails after the ledger has already been decremented, the pool's `last_total_balance` under-reports the NEAR actually held by the contract. Since `last_total_balance` is the baseline `ping()`/reward-detection logic diffs against to compute newly-earned staking rewards, the erroneously "missing" balance would be misattributed as a staking reward on the next `ping()`, inflating `total_staked_balance` and the pool's share price for every staker (including the party who triggered the failed withdrawal), and diverting a cut to the owner via `reward_fee_fraction`. This is an accounting value (the ledger) diverging from reality (the real NEAR balance) that other parties (all current stakers, the owner) settle on — the High-impact category in the rules. In `w-near`, an equivalent failure permanently destroys wNEAR backing, breaking the wrap/unwrap solvency invariant.

### Likelihood Explanation
A plain `Promise::new(account_id).transfer(amount)` action targeting an *existing* account almost never fails on NEAR, which is likely why the original authors omitted the check here while adding it everywhere else. Triggering an actual transfer failure requires the destination account to become invalid between the `withdraw()` call and the transfer receipt's execution (e.g., the account is deleted in an intervening transaction) — a narrow, timing-dependent precondition. I was not able to verify the exact contents of the reward-detection (`ping`) function to confirm precisely how the resulting delta is treated, so the magnitude/exact mechanics of the reward-inflation consequence should be verified directly in the deployed `ping`/`internal_ping` logic before treating this as a fully proven, high-likelihood exploit path.

### Recommendation
Attach a `.then()` callback to the withdrawal transfer in both `staking-pool/src/internal.rs::internal_withdraw` and `w-near/src/w_near.rs::near_withdraw`, check `is_promise_success()` in that callback, and only finalize (or otherwise roll back) the ledger decrement (`account.unstaked`, `last_total_balance`, or the burned wNEAR balance) once the transfer's success is confirmed — mirroring the pattern already used for `on_staking_pool_deposit`, `on_staking_pool_withdraw`, and the `lockup` contract's foundation/owner callbacks.

### Proof of Concept
Not independently reproducible from static analysis alone: exploitation requires forcing a normally-reliable native `Transfer` action to fail (e.g. by deleting the destination account in a transaction that lands between the `withdraw`/`near_withdraw` call and execution of the resulting transfer receipt), and the downstream reward-misattribution consequence depends on `ping()` internals that were not directly retrieved during this analysis. The root-cause code path — unconditional ledger decrement immediately followed by an unchecked `Promise::new(...).transfer(...)` with no success callback — is confirmed at the cited lines.

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }
