### Title
Signer fails open and signs a conflicting block when `get_tenure_tip` errors during the own-tenure conflict check - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
In `handle_block_pre_commit`, the "own-tenure" conflict guard that decides whether a same-tenure conflicting block still blocks a new signature treats an RPC error from the stacks-node (`get_tenure_tip`) as "conflict does not block" and falls through to sign. This directly contradicts the fail-safe philosophy documented and implemented everywhere else in the same file (`conflict_still_blocks`, `reorg_permit_stands`), where node-unreachable/error conditions are explicitly treated as "keep the conflict blocking" because, as the code's own comments state, "wrongly signing cannot be taken back."

### Finding Description
`handle_block_pre_commit` is the sole place a signer converts accumulated pre-commit weight into an actual block signature [1](#0-0) . Before signing, it re-checks for conflicting blocks already signed/accepted at the same height, including conflicts within the proposed block's own tenure:

```
if conflicts.iter().any(|conflict| {
    conflict.consensus_hash == block_info.block.header.consensus_hash
        && !self.reorg_permit_stands(stacks_client, conflict)
}) {
    match stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash) {
        Ok(tip) => { ... if tip_height >= chain_length { return; } }
        Err(e) => {
            warn!("... Treating the tenure as unconfirmed.");
        }
    }
}
``` [2](#0-1) 

When `get_tenure_tip` returns `Err`, the match arm only logs a warning and does **not** `return`; execution falls through the surrounding `if`, past the `!conflicts.is_empty()` info log, straight into `mark_locally_accepted` and `handle_block_signature`, producing a signature [3](#0-2) .

This is the opposite of the documented and implemented default elsewhere in the same file. `conflict_still_blocks`, used for the general (non-own-tenure) conflict path, explicitly states in its doc comment: "If we have no saved burn block, or the node is unreachable, the conflict keeps blocking. That only delays the replacement until our signature goes stale, whereas wrongly signing cannot be taken back," and its implementation returns `true` (conflict still blocks) on every RPC error [4](#0-3) [5](#0-4) . Similarly, `reorg_permit_stands` treats a node error as "void the permit" (the safe direction, since voiding restores the blocking conflict) [6](#0-5) .

The own-tenure branch is the only conflict-check in this function that fails open: an unreachable/erroring node causes the signer to *assume* the tenure hasn't reached the conflicting height and proceed to sign a block that duplicates or conflicts with state the node may have already built. This breaks the one-per-tenure/height signing invariant the rest of the function is explicitly designed to protect (see the surrounding "signed conflicts... in ANY tenure" comment block) [7](#0-6) .

### Impact Explanation
This allows a signer to produce a valid signature over a conflicting block within the same tenure whenever a transient error occurs on the call to `get_tenure_tip` (node restart, timeout, connection reset, load spike) at the exact moment the pre-commit threshold is reached. Because the signer's own db already recorded a fresh, still-relevant same-tenure conflict at this point (that's why the branch is entered at all), signing anyway means the signer contributes to signature material for a block that may equivocate with a block the network/node already confirmed at or above that height — a concrete "signing a conflicting block" outcome, which the task rules classify as Critical impact.

### Likelihood Explanation
The trigger condition (an RPC error on `get_tenure_tip`) does not require a majority of signers, another signer's key, or the auth token — only ordinary conditions such as node restarts, RPC timeouts, or transient network issues coinciding with reaching the pre-commit threshold for a same-tenure conflicting block, which is a normal part of tenure-extend/re-proposal flows that a single miner (plus normal peer gossip of pre-commits) can produce. The inconsistency with the two sibling functions in the same file, which explicitly document and implement the opposite (fail-closed) behavior for the same class of RPC failures, strongly indicates this is an unintentional divergence rather than a deliberate design choice.

### Recommendation
Make the own-tenure conflict check fail closed on `Err`, matching `conflict_still_blocks` and `reorg_permit_stands`: when `get_tenure_tip` errors, treat the conflict as still blocking (i.e., `return` without signing) rather than falling through to sign. For example:
```rust
Err(e) => {
    warn!("{self}: Failed to fetch the canonical tip of the proposed block's tenure: {e:?}. Refusing to sign.");
    return;
}
```

### Proof of Concept
1. Signer A has previously signed/locally-accepted block `B1` in tenure `T` at height `h` (recorded via `get_signed_conflicts`).
2. Miner proposes a competing block `B2` in the same tenure `T` at height `h` (or the same block is re-proposed after a timeout); enough pre-commits arrive to cross the weight threshold, and `reorg_permit_stands` returns `false` for the conflict (no permit recorded) so control reaches the own-tenure branch at [8](#0-7) .
3. At this moment, the signer's call to `stacks_client.get_tenure_tip(&consensus_hash)` fails (e.g., node briefly down/restarting, or a request timeout) and returns `Err`.
4. Per [9](#0-8) , the signer only logs a warning and does not return, falling through to `mark_locally_accepted` and `handle_block_signature` at [10](#0-9) , producing a signature over `B2` despite the known, still-fresh, same-tenure conflict with `B1`.
