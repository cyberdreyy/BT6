### Title
`GET /v2/bridge_types?size=N` has no upper bound on page size, letting any authenticated view-role user dump the entire `bridge_types` table including `OutgoingToken` in one request - ([File: core/web/api.go])

### Summary
`ParsePaginatedRequest` only rejects `size < 1`, it never enforces a maximum, and `BridgeTypesController.Index` passes that unbounded `size` straight to the ORM as a SQL `LIMIT`. `GET /v2/bridge_types` is behind `auth.Authenticate` only (no `RequiresEditRole`/`RequiresViewRole`/`RequiresAdminRole` wrapper), and `BridgeResource` unconditionally includes `OutgoingToken` for every returned bridge with no role-based redaction.

### Finding Description
The route is registered as `authv2.GET("/bridge_types", paginatedRequest(bt.Index))` [1](#0-0)  — unlike the mutating verbs on the same resource (`POST`/`PATCH`/`DELETE`), which are wrapped in `auth.RequiresEditRole`, the `GET` is reachable by any authenticated session/token regardless of role (including the lowest `UserRoleView`).

`paginatedRequest` parses `size`/`page` via `ParsePaginatedRequest`, which only validates `size >= 1` — there is no upper cap: `if size, err = strconv.Atoi(sizeParam); err != nil || size < 1 { ... }` [2](#0-1) .

`BridgeTypesController.Index` forwards that unbounded `size` directly as the query limit: `bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)` [3](#0-2) , and the ORM uses it verbatim as SQL `LIMIT`: `sql := "SELECT * FROM bridge_types ORDER BY name asc LIMIT $1 OFFSET $2;"` [4](#0-3) .

Each row is converted to a `BridgeResource`, which always serializes `OutgoingToken` (no `omitempty`, no role check) — only `IncomingToken` is treated specially (only populated on `Create`): `OutgoingToken string \`json:"outgoingToken"\`` [5](#0-4) , populated from the DB value in `NewBridgeResource` [6](#0-5) .

Because there is neither a page-size cap nor role-based field redaction, a caller with the lowest privileged role (`view`) authenticated via session or API token can send `GET /v2/bridge_types?size=100000` and receive every bridge row — including every `OutgoingToken` — in a single response.

### Impact Explanation
This matches the "secret disclosure" bounty class: `OutgoingToken` is a bearer credential the node uses to authenticate itself to external bridge adapters. A low-privilege `view`-role user (who should only be able to read non-sensitive job/run metadata) can exfiltrate every configured bridge's outgoing secret in one request, enabling impersonation of the node to those external adapters/bridge services.

### Likelihood Explanation
Minimal precondition: any valid authenticated credential reaching the node API with role `view` or higher (a "restricted API token" holder as allowed by the threat model) and network access to `/v2/bridge_types`. No admin/edit role or special config needed — a single crafted GET request with `size=<row_count>` (or any value ≥ total bridge count) suffices, and it is fully repeatable.

### Recommendation
- Enforce a hard upper bound (e.g., `PaginationMax`) in `ParsePaginatedRequest` in `core/web/api.go`, rejecting or clamping `size` values above the limit.
- Gate `GET /v2/bridge_types` behind at least `auth.RequiresEditRole` (or a new `RequiresViewRole` check that still redacts secrets), consistent with the other bridge mutation routes in `core/web/router.go`.
- Redact `OutgoingToken` from `BridgeResource` in list/read responses (e.g., mask it or omit it entirely, similar to how `IncomingToken` is only surfaced on `Create`), in `core/web/presenters/bridges.go`.

### Proof of Concept
Go handler-level integration test (extending `TestBridgeTypesController_Index` in `core/web/bridge_types_controller_test.go`):
1. Seed >2 bridge types via `orm.CreateBridgeType`, recording their `OutgoingToken` values.
2. Authenticate an HTTP client with a `view`-role user/API token (not edit/admin).
3. `GET /v2/bridge_types?size=100000`.
4. Assert the response returns `http.StatusOK` and `resources` contains ALL seeded bridges in one page (no capping), and that each `resources[i].OutgoingToken` matches the corresponding seeded `bt.OutgoingToken`, proving bulk secret exfiltration with a single oversized `size` and a view-only role.
5. Expected secure behavior: either the server clamps `size` to a maximum (e.g., 100) forcing pagination, or the `view`-role request is rejected with `401/403`, or `OutgoingToken` is redacted/empty in the response for non-privileged roles.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}
