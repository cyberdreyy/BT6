## Title
Stale confirmations from a deleted multisig key are never invalidated, allowing a request to execute below the live-key threshold - (File: `multisig/src/lib.rs`)

### Summary
The `multisig` contract's `DeleteKey` action removes a departing key's *own pending requests* but never scrubs that key's *confirmations on other pending requests*. Because `confirm()` only counts entries already stored in the `confirmations` set (never re-validating that each entry belongs to a currently-authorized key), a request confirmed by a key before it is deleted still counts toward `num_confirmations` after deletion. This lets a request execute with fewer genuinely-live confirmations than the configured threshold — the same class of bug as the reported issue, where a check meant to guarantee "each entry is a distinct, currently valid item" is incomplete and silently accepts stale/duplicate-like state.

### Finding Description
`add_request` creates a request with an empty `confirmations: HashSet<PublicKey>` [1](#0-0) . Any authorized key can call `confirm`, which inserts its own `signer_account_pk` into that set, or executes the request once `confirmations.len() + 1 >= num_confirmations` [2](#0-1) .

When a key is removed via `MultiSigRequestAction::DeleteKey`, the cleanup logic only deletes requests *added by* that public key, and only removes `num_requests_pk` bookkeeping for it:
```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [3](#0-2) 

It never scans `self.confirmations` for entries containing `pk` on requests added by *other* keys. `confirm()` and `assert_valid_request()` also never re-check that every public key already recorded in a request's `confirmations` set is still a valid multisig key [4](#0-3) .

**Binding broken:** the number of confirmations counted toward `num_confirmations` should equal the number of confirmations from *currently authorized* keys. Instead, `confirmations.len()` includes confirmations from keys that have since been deleted, so `live_confirmations < num_confirmations` can still trigger `execute_request`.

### Impact Explanation
This lets a request execute (including `Transfer`, `AddKey`, `FunctionCall`, etc.) with fewer genuinely live signers than the configured threshold `K`, i.e. a multisig request executed below threshold — the Critical-impact category explicitly listed in scope ("a multisig request executed below threshold"). Funds or authority changes controlled by the multisig can be moved/executed without the intended quorum of currently trusted keys.

### Likelihood Explanation
This requires a normal, expected operational sequence for any long-lived multisig: a member's key is rotated/removed (a routine, non-privileged-attacker-required event from the multisig's own governance) after having confirmed a still-pending request that a different key added. No special exploit conditions, redeploys, or foundation involvement are needed beyond the ordinary `DeleteKey` action that any funded multisig will eventually execute during key rotation. The window is any time between a confirmation and a later key deletion where the confirmed request is still outstanding.

### Recommendation
On `DeleteKey`, iterate `self.confirmations` for *all* requests (not just ones added by `pk`) and remove `pk` from each confirmation set; alternatively, on every `confirm()`/execution check, filter the counted confirmations to only those public keys that currently exist as multisig access keys before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(2)` with keys `A`, `B`, `C` (K=2 of 3).
2. `A` calls `add_request` for `Transfer { amount }` to `attacker` (request `R1`, added by `A`, confirmations = {}).
3. `B` calls `confirm(R1)` → `confirmations(R1) = {B}` (1 confirmation, below threshold, not yet executed).
4. Separately, `A` and `C` submit and confirm a `DeleteKey { public_key: B }` request (2-of-3, executes normally) — `B`'s key is removed from the account. Cleanup only removes requests where `signer_pk == B`; `R1` was added by `A`, so it and its confirmation set `{B}` are untouched.
5. `A` calls `confirm(R1)` → `confirmations(R1).len() + 1 == 2 >= num_confirmations(2)` → `execute_request` runs the `Transfer`, even though `B` is no longer a valid multisig key and only one currently-live key (`A`) ever confirmed `R1`. [5](#0-4) [3](#0-2)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
