### Title
Withdraw receipts minted with a full epoch of projected interest are instantly claimable after pool close, letting early claimers overdraw recalled funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the am65-cpsw bug — where an SKB is allocated *before* the XDP program outcome is known and the allocation is wasted/leaked on non-`XDP_PASS` paths — `IdleCreditVault.requestWithdraw` mints a full withdrawal receipt (principal **plus** one epoch of projected interest) *before* checking the closed-pool outcome. When the pool is closed (`epochEndDate == 0`), no future epoch will ever run, so the projected interest portion of the receipt is value that will never be earned — yet the receipt is still minted, recorded in `withdrawsRequests`, and immediately claimable at par, draining funds that belong to other receipt holders and active LPs.

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw`, the requested amount is `principal + interest - fees`, where `interest` comes from `_calcInterestWithdrawRequest`. That helper only short-circuits when `epochDuration == 0`; a closed pool only clears `epochEndDate`, so a request made after pool close still accrues a *full epoch* of projected interest even though the borrower will never run another epoch and no interest will ever be generated.

The strategy then evaluates the outcome too late, in `contracts/strategies/idle/IdleCreditVault.sol` `requestWithdraw`:

- Line 275: `_mint(_user, _amount)` — the receipt (including phantom interest) is minted **before** the closed-pool branch is evaluated.
- Lines 277-280: `if (!isClosed) pendingWithdraws += _amount;` — in a closed pool the receipt is *not* added to `pendingWithdraws`, but it is still written to `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch` (lines 292-293) and `lastWithdrawRequest` (line 282).

On the claim side, `_claimFundedWithdrawRequest` explicitly treats closed pools as instantly claimable (the `epochEndDate() != 0` guard at line 326 is skipped when closed, and the comment at lines 334-336 confirms immediate claims are intended in pool-close mode). `_transferFundedClaim` pays 1:1 from the strategy's underlying balance, which in a closed pool is the finite amount recalled from the borrower — a fixed pie that must cover *all* receipts and remaining LP value.

The broken invariant is fair mint/burn / solvency: a receipt is minted for `principal + projectedInterest` while the pool backing it contains only recalled principal plus the interest earned up to the last real epoch. Each such post-close request inflates aggregate claims above the strategy balance.

### Impact Explanation
Any KYC-passed tranche holder can, after the pool is closed and all funds have been recalled to the strategy:

1. Call `IdleCDOEpochVariant.requestWithdraw` — minting a receipt for `principal + one full epoch of projected interest` (at the last APR, which can be up to `maxApr` = 20e18 scaled, i.e. ~20%/epoch equivalent on top of principal).
2. Immediately call `claimWithdrawRequest` → `IdleCreditVault.claimWithdrawRequest` → `_claimFundedWithdrawRequest` → `_transferFundedClaim`, receiving the inflated amount at par.

Each early claimer extracts `principal * (1 + epochInterest)` instead of their fair `principal` share. Since the closed pool holds only the recalled lump sum, the excess paid to early claimers is directly stolen from later claimants and remaining LPs, who find the strategy undercollateralized — a direct theft / insolvency for later withdrawers, quantifiable as roughly `epochInterest` per requester (≈ APR-scaled share of the entire pool NAV for a full-epoch-duration request).

### Likelihood Explanation
- Attacker needs only to be a KYC-passed tranche holder (in-scope unprivileged role).
- Preconditions: pool closed via the `_interest == 1` repay-all path (a legitimate, owner/manager-driven flow — `epochEndDate == 0`), `allowAAWithdrawRequest`/`allowBBWithdrawRequest` still enabled, and strategy holding recalled underlyings.
- No existing guard stops it: the loss-recovery guard (lines 263-271) only blocks users with prior loss-adjusted receipts; `pendingWithdraws` bookkeeping is skipped but `withdrawsRequests` is not; `_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve`, not other claimants.
- Uncertainty: if the honest manager disables withdraw-request flags upon closing the pool, the window shrinks; nothing enforces that ordering, and the funded-claim path is explicitly designed to remain open post-close.

### Recommendation
Evaluate the closed-pool outcome *before* allocating the receipt — mirroring the upstream fix (move SKB allocation after the XDP verdict):

- In `IdleCDOEpochVariant.requestWithdraw` (or in `_calcInterestWithdrawRequest`), return zero projected interest when the pool is closed (`epochEndDate == 0`), since no epoch will run.
- In `IdleCreditVault.requestWithdraw`, when `isClosed`, either revert on requests that include interest, or record only the principal basis so the minted receipt equals the actually-funded amount.
- Optionally cap total claimable in closed-pool mode to the strategy's underlying balance pro rata across `withdrawsRequests`.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol` harness, cf. `testClosePool` at line 5380):

```solidity
function testClosedPoolWithdrawInflation() external {
    // Setup: two KYC'd AA depositors, 50/50
    uint256 amountWei = 10000 * ONE_SCALE;
    idleCDO.depositAA(amountWei);              // attacker (this contract)
    address victim = makeAddr('victim');
    _depositWithUser(victim, amountWei, true);

    // Run one epoch, then stop with _interest == 1 sentinel to close the pool
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    // borrower repays everything; closePool path sets epochEndDate = 0
    deal(defaultUnderlying, borrower, IERC20(defaultUnderlying).balanceOf(borrower) + 2 * amountWei);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 1); // repay-all sentinel
    assertEq(cdoEpoch.epochEndDate(), 0);      // pool closed

    uint256 stratBal = underlying.balanceOf(address(strategy));

    // Attacker requests withdraw AFTER close: receipt includes a full epoch of interest
    uint256 trancheBal = IERC20(AAtranche).balanceOf(address(this));
    uint256 requested = cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));
    assertGt(requested, _trancheToUnderlyingValue(trancheBal)); // > pure principal

    // Immediately claimable because epochEndDate() == 0 skips the wait
    uint256 pre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 claimed = underlying.balanceOf(address(this)) - pre;
    assertEq(claimed, requested);

    // Victim's pro-rata share is now undercollateralized
    vm.prank(victim);
    uint256 victimReq = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(victim), address(AAtranche));
    assertLt(underlying.balanceOf(address(strategy)), victimReq); // insolvency for later claimer
}
```

Expected result: the attacker's claim succeeds and includes interest for an epoch that never ran; the strategy's remaining balance is less than the victim's fair claim, demonstrating theft/insolvency of ~`epochInterest` per post-close request.
