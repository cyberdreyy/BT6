### Title
Instant, unrestricted validator commission update (`UpdateCommissionBps`) can retroactively capture already-accrued delegator rewards - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
`update_commission_bps` (SIMD-0291/SIMD-0123) lets a vote account's authorized withdrawer change `inflation_rewards_commission_bps` or `block_revenue_commission_bps` to any value up to 10,000 bps (100%) at any slot, with no epoch-timing restriction, unlike the legacy `update_commission` path. This mirrors the `BoostAggregator.setProtocolFee` bug class: an "aggregator" (vote account) that holds funds/credits belonging to third parties (delegators) lets its privileged owner (authorized withdrawer) unilaterally raise the fee to 100% and intercept value that should flow to depositors (stakers).

### Finding Description
The legacy commission update path enforces a timing rule so that commission increases can only take effect if raised in the first half of an epoch, and additionally the reward-calculation code defers a full epoch when `delay_commission_updates` is active: [1](#0-0) 

The newer basis-points update path, however, explicitly removes any timing restriction: [2](#0-1) [3](#0-2) 

For `CommissionKind::InflationRewards`, the reward-distribution code in the runtime does apply a mitigating delay: when `delay_commission_updates` is active it deliberately fetches the commission from a *prior* epoch's cached vote-account snapshot rather than the live value, which prevents an instant 100% commission bump from stealing already-earned inflation rewards: [4](#0-3) 

No equivalent delayed-snapshot mechanism was found for `CommissionKind::BlockRevenue`. `calculate_block_reward` distributes `pending_delegator_rewards` — lamports already accumulated in the vote account for delegators — proportionally to `stake / total_active_stake` without re-applying or re-checking `block_revenue_commission_bps` at distribution time: [5](#0-4) 

The split between validator and delegator shares for block revenue is instead performed earlier, at the point revenue is deposited into the vote account via the `DepositDelegatorRewards` instruction (SIMD-0123), which reads whatever `block_revenue_commission_bps` value is currently stored in the vote account at call time: [6](#0-5) 

Because `update_commission_bps` can change `block_revenue_commission_bps` instantly and without restriction, a validator's authorized withdrawer can raise it to 10,000 bps immediately before block-revenue deposit instructions are processed in a slot, capture 100% of that period's revenue that would otherwise accrue to delegators as `pending_delegator_rewards`, and then lower it back — exactly analogous to the `BoostAggregator` owner setting `protocolFee` to 100% to steal already-staked users' rewards.

### Impact Explanation
If confirmed, this allows a malicious/self-interested validator (vote account authorized withdrawer — a role trusted with configuration but not expected to be able to unilaterally seize delegator earnings) to redirect delegators' share of block revenue rewards to itself with no on-chain delay or protection, unlike the equivalent inflation-rewards commission path which is explicitly protected via epoch-delayed snapshots. This is a fund-diversion / unauthorized-state-mutation issue affecting delegator reward accounting.

### Likelihood Explanation
Medium-to-Low confidence: the `update_commission_bps` "no timing restriction" behavior for `BlockRevenue` is directly confirmed in code and comments, but I was unable to fully inspect the exact implementation of the `DepositDelegatorRewards` instruction handler / `deposit_delegator_rewards` in `programs/vote/src/vote_state/mod.rs` and `handler.rs` within the available iterations to conclusively verify whether it reads live `block_revenue_commission_bps` at deposit time versus some other rate-limited or averaged mechanism. This is the crux of the finding and should be verified before treating it as confirmed; if `deposit_delegator_rewards` also applies a delay or historical commission snapshot (as `redeem_delegation_rewards` does for inflation rewards), the vulnerability would not exist for block revenue either.

### Recommendation
- Apply the same epoch-delayed commission mechanism used for `inflation_rewards_commission_bps` (via `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`) to `block_revenue_commission_bps` when splitting deposited revenue, so that a commission increase cannot affect revenue that was already earned/collected under a prior rate.
- Alternatively, record and use the commission rate that was in effect at the time revenue accrued (per-deposit rate tracking), mirroring the community-suggested fix for the original `BoostAggregator` finding (tracking the fee at time of deposit rather than reading a live, owner-controlled value).

### Proof of Concept
1. Validator identity delegates stake from many delegators to its vote account (VoteStateV4, `block_revenue_sharing` feature active).
2. Just before a slot in which block-revenue deposits are expected, the authorized withdrawer submits `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::BlockRevenue }` — accepted instantly per `update_commission_bps` with no timing check. [7](#0-6) 
3. `DepositDelegatorRewards` processes the block's collected revenue using the now-100% commission, so the validator (or its designated block-revenue collector) receives the full amount instead of the delegator-proportional share.
4. The authorized withdrawer lowers `block_revenue_commission_bps` back to its prior value for subsequent blocks, evading long-term detection while having captured one or more blocks' worth of delegator rewards.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
