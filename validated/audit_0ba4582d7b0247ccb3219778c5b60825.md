### Title
Loss-adjusted withdraw receipts are repaid at par after a later defaulted claim clears `lastWithdrawRequest`, stealing the haircut from the recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimWithdrawRequest` uses the single-slot `lastWithdrawRequest[_user]` to locate a loss-adjusted receipt, but `_claimDefaultedWithdrawRequest` clears that marker first. A user holding an older `stopEpochWithDuration` loss-adjusted receipt plus a newer defaulted-epoch receipt gets the loss-adjusted receipt paid at full par by `_claimFundedWithdrawRequest` instead of at `lossRecoveryPriceByEpoch`, overpaying them out of funds that belong to other claimants.

### Finding Description
The claim waterfall runs in this order (`IdleCreditVault.sol:301-314`):

```solidity
amount = _claimPostDefaultWithdrawRequest(_user);
if (amount != 0) return amount;
amount = _claimDefaultedWithdrawRequest(_user);   // clears lastWithdrawRequest
amount += _claimLossAdjustedWithdrawRequest(_user); // keyed on lastWithdrawRequest
return amount + _claimFundedWithdrawRequest(_user); // pays withdrawsRequests at par
```

Three cooperating defects:

1. `_claimLossAdjustedWithdrawRequest` (lines 789-801) looks up the loss epoch via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. It only ever sees the *latest* request epoch.
2. `_clearWithdrawClaimForEpoch` (lines 832-836) sets `lastWithdrawRequest[_user] = 0` when the cleared epoch equals the marker. So after `_claimDefaultedWithdrawRequest` runs for the default epoch, the marker is 0 and the older loss epoch is never found.
3. The loss epoch's per-epoch basis `withdrawsRequestsByEpoch[_user][lossEpoch]` is never cleared, so `withdrawsRequests[_user]` still contains it. `_claimFundedWithdrawRequest` then burns the receipt tokens and pays the *full* basis via `_transferFundedClaim`, even though `collectWithdrawFunds` only transferred `claimBasis * lossRecoveryPrice / RECOVERY_FULL` for it.

Note the comments at lines 818-819 and 833-835 claim remaining receipts "are older and already funded" — true for fully-funded epochs, but false for loss-adjusted epochs, which were funded at a haircut. The shortfall is effectively "freed" collateral being reused at par, mirroring the use-after-free pattern in the reference bug.

### Impact Explanation
A user extracts `claimBasis * (1 - lossRecoveryPrice/RECOVERY_FULL)` more underlying than entitled. The excess is paid from strategy-held underlyings that either back other funded receipts or sit in `defaultRecoveryReserve` (if the `_transferFundedClaim` reserve guard at lines 899-905 lets the balance through — the guard only protects the reserve when `balance - reserve < _amount`, so funded-but-haircutted balances are unprotected). Result: direct theft / insolvency of other claimants proportional to the loss haircut on the skipped receipt.

### Likelihood Explanation
Requires this sequence by one unprivileged user, all via public `requestWithdraw`/`claimWithdrawRequest`:

1. Buffer/running epoch E1: user requests withdraw. `stopEpochWithDuration` realizes a loss → `collectWithdrawFunds` funds at `lossRecoveryPrice < RECOVERY_FULL`.
2. User requests again in epoch E2 (allowed; new request just overwrites `lastWithdrawRequest`).
3. Borrower defaults in E2; `finalizeDefault`/`finalizeDefaultRecovery` set `defaultRecoveryFinalized`, `defaultRecoveryEpoch = E2`.
4. User calls `claimWithdrawRequest` once. The E1 loss receipt is never haircutted and pays at par.

No privileged cooperation needed; the user only needs two withdraw requests across the loss and default epochs.

### Recommendation
Track loss-adjusted claims per epoch rather than through `lastWithdrawRequest`. Either iterate/settle `withdrawsRequestsByEpoch` entries that have a non-zero `lossRecoveryPriceByEpoch`, or store a separate `lossEpochs` list per user, so `_claimLossAdjustedWithdrawRequest` cannot be skipped by a later request or by the default-claim path zeroing the marker. Alternatively, subtract loss-adjusted bases from `withdrawsRequests[_user]` at `collectWithdrawFunds` time so the par-funded path never sees them.

### Proof of Concept
Foundry fork PoC (sketch, in repo style):

```solidity
// test/foundry/IdleCreditVault.t.sol style
function testLossAdjustedReceiptPaidAtParAfterDefault() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amountWei);

    // E1: request withdraw, then stopEpochWithDuration with a loss
    uint256 req1 = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
    uint256 lossEpoch = strategy.epochNumber();
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 loss = pendingBasis / 2; // 50% haircut on pending receipts
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(loss);
    _stopCurrentEpochWithLoss(loss); // borrower funds only pendingToFund
    assertLt(strategy.lossRecoveryPriceByEpoch(lossEpoch), RECOVERY_FULL);

    // E2: request again so lastWithdrawRequest moves to E2
    cdoEpoch.requestWithdraw(mintedAA / 4, address(AAtranche));

    // Default E2 and finalize recovery
    _defaultAndFinalizeRecovery();

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // E1 receipt paid at par instead of at lossRecoveryPrice -> overpayment
    uint256 fairE1 = req1 * strategy.lossRecoveryPriceByEpoch(lossEpoch) / RECOVERY_FULL;
    assertGt(paid, fairE1); // attacker received more than the haircutted amount
    // funded/reserve balance for remaining claimants is drained by the excess
}
```

Key assertions: `withdrawsRequestsByEpoch[user][lossEpoch]` remains non-zero after the claim, and `paid` equals the un-haircutted `req1` plus the defaulted claim.
