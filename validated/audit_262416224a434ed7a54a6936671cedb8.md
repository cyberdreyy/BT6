### Title
Multisig executes requests using stale confirmations from removed members, executing below the live-member threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
Both the account-based multisig (`multisig2/src/lib.rs`) and the access-key-based multisig (`multisig/src/lib.rs`) purge outstanding requests and confirmations only for requests that the *removed member itself created*, but never scrub that removed member's confirmations from *other* pending requests it had merely confirmed. Because `confirm()` only compares the raw size of the stored confirmation set to `num_confirmations` — without re-validating that every public key/member in that set is still a current member — a request can later execute using a confirmation count that includes one or more members who have since been deleted, i.e., it executes with fewer *live* confirmations than `num_confirmations` actually requires.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` only cleans up requests originated by the member being deleted: [1](#0-0) 
```
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
```
This filters on `r.member == member`, i.e. only requests *created* by the removed member. Any confirmation that member added to a request *created by someone else* is left in the `confirmations` map untouched.

`confirm()` then executes a request purely by counting the stored confirmation-set size, with no re-check that every entry in that set still corresponds to a current member: [2](#0-1) 
```
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let member = self.current_member()...;
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert(!confirmations.contains(&member.to_string()), ...);
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(member.to_string());
        ...
    }
}
```

The same pattern exists in the older, access-key based `multisig/src/lib.rs`: `DeleteKey` only purges requests where `r.signer_pk == pk` (requests created by that key), leaving that key's confirmations on other requests intact: [3](#0-2) 
```
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
```
and `confirm()` executes on raw set size, again with no membership re-check: [4](#0-3) 

The custody binding this breaks is: `confirmations recorded for a request` should equal `confirmations from currently authorized members` before execution. Instead, the contract enforces only `len(recorded confirmations) >= num_confirmations`, which can include confirmations from members/keys already deleted from the multisig.

### Impact Explanation
This lets a `Transfer`, `FunctionCall`, `AddKey`, `AddMember`, `DeleteMember`, etc. request execute even though the number of members who are *currently* authorized and actually confirmed it is below `num_confirmations`. This directly matches the Critical impact category "a multisig request executed below threshold," since NEAR (or contract control) can move/execute based on a K-of-N guarantee that no longer holds — the K includes at least one confirmation from a member who is provably no longer part of the multisig at execution time.

### Likelihood Explanation
This requires: (1) a member confirms a request they did not create, (2) that member is later removed via `DeleteMember`/`DeleteKey` (a normal, expected multisig operation, e.g. to revoke a compromised or departing member), and (3) the original request is later pushed over threshold by other legitimate confirmations. All three steps are ordinary multisig lifecycle events with no special privilege needed beyond being a normal, at-the-time-valid member — the flaw is in the cleanup logic, not in an attacker forging access. Given that member rotation (removing a departing/compromised signer) is a core intended use case of this contract, the likelihood of hitting this state is high in real operational use.

### Recommendation
When removing a member/key (`DeleteMember`/`DeleteKey`), iterate over **all** pending requests' confirmation sets (not just requests the member created) and strip that member's/key's confirmation from each. Alternatively, validate at `confirm()`/execution time that every entry in the confirmation set is still a current member (e.g., intersect the stored confirmation set with the live `members` set before comparing to `num_confirmations`).

### Proof of Concept
Using `multisig2` with members `{A, B, C, D, E}` and `num_confirmations = 3`:
1. `B` calls `add_request_and_confirm(R1)` where `R1` is `Transfer{ amount, receiver_id: <B-controlled account> }`. Confirmations(`R1`) = `{B}`.
2. `A` calls `confirm(R1)`. Confirmations(`R1`) = `{B, A}` (2/3, not yet executed).
3. Separately, members detect `A` is compromised. `C` creates and the group confirms a `DeleteMember{A}` request (via `C`,`D`,`E`), which executes `delete_member`, removing `A` from `members`. Because `R1.member == B` (not `A`), the cleanup loop in `delete_member` does **not** touch `R1`'s confirmations; `{B, A}` remains stored.
4. Now the live member set is `{B, C, D, E}`.
5. `C` calls `confirm(R1)`. Confirmations(`R1`) becomes `{B, A, C}`, size `3 >= num_confirmations(3)`, so `execute_request` runs the `Transfer` — even though only `B` and `C` are live members who actually confirmed; `A`'s confirmation is stale from a removed member. The transfer executes with only 2 live confirmations instead of the required 3.
