### Title
Block-proposal tenure validation anchors canonicity checks on the block's own (possibly orphaned) burn view instead of the sortdb's real canonical tip - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
`NakamotoBlockProposal::validate` derives `sort_tip` from `burn_view_consensus_hash` via a raw, non-canonicity-filtered lookup (`SortitionDB::get_block_snapshot_consensus`), then opens `db_handle` rooted at that very sortition and uses it as the reference frame for `check_block_has_valid_tenure`. Because the reference frame is the block's own (attacker-supplied) burn view rather than the SortitionDB's actual canonical tip, an Extend `TenureChange` naming an orphaned-but-historically-connected `burn_view_consensus_hash` can pass every check while never being compared against `SortitionDB::get_canonical_burn_chain_tip`.

### Finding Description
The equality that must hold is: the tenure/burn-view consensus hash a proposal claims must equal a consensus hash that is an ancestor of the sortdb's **actual current canonical tip**. Instead, the code establishes the "canonical" frame from the claim itself: [1](#0-0) 

`burn_view_consensus_hash` comes from `NakamotoChainState::get_block_burn_view`, and for a `TenureChangeCause::Extend` it is taken directly from the attacker-crafted `tenure_change.burn_view_consensus_hash`: [2](#0-1) 

The only check performed here is that the attacker-chosen `burn_view_consensus_hash`'s own fork passes through the parent's burn view at the correct height (`get_ancestor_sort_id` relative to `handle.context.chain_tip`, which is rooted at the attacker's chosen hash) — never that this hash is itself an ancestor of the **live** canonical tip.

`sort_tip` is then fetched with a raw, canonicity-blind query: [3](#0-2) 

This SQL only filters on `pox_valid`, not on which sortition_id is on the currently-canonical fork; orphaned-fork rows remain queryable forever.

`db_handle` is then opened with `chain_tip = sort_tip.sortition_id` (the attacker-influenced/possibly-orphaned sortition), and `check_block_has_valid_tenure` calls `has_consensus_hash`, whose canonicity check is *relative to that same chain_tip*, not the sortdb's real tip: [4](#0-3) 

Since the tenure's real consensus hash (unaffected by the reorg, since `tenure_consensus_hash == prev_tenure_consensus_hash` for Extend causes) predates the fork divergence point, it is trivially an ancestor of the orphaned `sort_tip` too — the check passes even though `sort_tip`/`burn_view_consensus_hash` is no longer on the node's actual canonical fork. The same self-referential pattern recurs in `get_expected_burns` (keyed off the same orphaned `burn_view_consensus_hash`) and in `check_valid_consensus_hash`, which is likewise evaluated relative to a handle's `chain_tip` rather than the true tip: [5](#0-4) 

Nowhere in `validate()` (traced through the transaction-execution loop) is `sort_tip`/`burn_view_consensus_hash` compared against `SortitionDB::get_canonical_burn_chain_tip(sortdb.conn())` — the function that other code paths (e.g. `validate_nakamoto_tenure_snapshot`) correctly use as the true canonicity anchor: [6](#0-5) 

Root cause: canonicity of the burn view is checked *relative to itself*, not relative to the live canonical tip, so a proposal can smuggle in a now-orphaned but historically-valid `burn_view_consensus_hash` via `TenureChangeCause::Extend` and have `validate()` return `Ok`.

### Impact Explanation
This breaks the CANONICITY safety property: the node's `/v3/block_proposal` endpoint — which signers trust as the authoritative gate before signing — can return `Ok` for a block whose tenure/burn view is not on the node's actual current canonical Bitcoin fork. A signer that relies on this Ok result to cast an approval would sign a non-canonical block, directly matching the Critical bucket ("a signer signing an invalid, non-canonical, or conflicting block"). This is not a one-off; it is repeatable for any subsequent tenure-extend proposal referencing the same orphaned burn view, and the orphaned row persists in the `snapshots` table indefinitely (not scrubbed after a reorg), so it is not strictly a narrow race window — it remains exploitable as long as the orphaned sortition record exists and a valid ancestor relationship to the (still-canonical) parent tenure can be constructed.

### Likelihood Explanation
Preconditions: a genuine burnchain reorg must have occurred so that some previously-canonical sortition (usable as `burn_view_consensus_hash`) becomes orphaned but still historically descends from an ongoing tenure's parent burn view. The attacker needs only their own miner slot to broadcast the crafted `TenureChangeCause::Extend` block proposal (or equivalent StackerDB gossip) — no signer majority, no auth token, no local access. Reorgs of the required shape are an environmental precondition outside the attacker's full control, which somewhat limits pure attacker-controlled likelihood, but once such a reorg happens the exploit window is not small (the vulnerable code path performs no time-bounded canonical check at all).

### Recommendation
In `NakamotoBlockProposal::validate`, after computing `sort_tip` from `burn_view_consensus_hash`, explicitly verify `sort_tip`/`burn_view_consensus_hash` is an ancestor of `SortitionDB::get_canonical_burn_chain_tip(sortdb.conn())` (mirroring the logic in `validate_nakamoto_tenure_snapshot`) before using it to build `db_handle`. Apply the same true-canonical-tip check inside `get_block_burn_view` for the `Extend` cause, rather than only checking ancestry within the claimed burn view's own fork.

    /// Verify that the given Nakamoto block attaches to the canonical burnchain fork.
    /// Return Ok(snapshot) on success, where `snapshot` is the sortition corresponding to this
    /// block's tenure.
    /// Return Err(..) otherwise
    fn validate_nakamoto_tenure_snapshot(
        db_handle: &SortitionHandleConn,
        block: &NakamotoBlock,
    ) -> Result<BlockSnapshot, ChainstateError> {
        // find the sortition-winning block commit for this block, as well as the block snapshot
        // containing the parent block-commit.  This is the snapshot that corresponds to when the
        // miner begain its tenure; it may not be the burnchain tip.
        let consensus_hash = &block.header.consensus_hash;

        let sort_tip = SortitionDB::get_canonical_burn_chain_tip(db_handle)?;

        // burn chain tip that selected this commit's block (the tenure sortition)
        let Some(tenure_burn_chain_tip) =
            SortitionDB::get_block_snapshot_consensus(db_handle, consensus_hash)?
        else {
            warn!("No sortition for {}", consensus_hash);
            return Err(ChainstateError::InvalidStacksBlock(
                "No sortition for block's consensus hash".into(),
            ));
        };

        // tenure sortition is canonical
        let Some(ancestor_sort_id) = get_ancestor_sort_id(
            db_handle,
            tenure_burn_chain_tip.block_height,
            &sort_tip.sortition_id,
        )?
        else {
            // not canonical
            warn!("Invalid consensus hash: snapshot is not canonical"; "consensus_hash" => %consensus_hash);
            return Err(ChainstateError::InvalidStacksBlock(
                "No sortition for block's consensus hash -- not canonical".into(),
            ));
        };
        if ancestor_sort_id != tenure_burn_chain_tip.sortition_id {
            // not canonical
            warn!("Invalid consensus hash: snapshot is not canonical"; "consensus_hash" => %consensus_hash);
            return Err(ChainstateError::InvalidStacksBlock(
                "No sortition for block's consensus hash -- not canonical".into(),
            ));
        };

        Ok(tenure_burn_chain_tip)
    }

    /// Is a consensus hash's sortition valid on the fork represented by this handle?
    /// Return Ok(true) if so
    /// Return Ok(false) if not (including if there is no sortition with this consensus hash)
    /// Return Err(..) on DB error
    pub fn has_consensus_hash(&self, consensus_hash: &ConsensusHash) -> Result<bool, db_error> {
        let Some(sn) = SortitionDB::get_block_snapshot_consensus(self, consensus_hash)? else {
            // no sortition with this consensus hash
            return Ok(false);
        };

        let Some(expected_sortition_id) =
            get_ancestor_sort_id(self, sn.block_height, &self.context.chain_tip)?
        else {
            // no ancestor at this sortition height relative to this chain tip
            // (e.g. perhaps this consensus hash is in the "future" relative to this chain tip)
            return Ok(false);
        };

        Ok(sn.sortition_id == expected_sortition_id)
    }

    /// Check that a consensus hash is on the canonical burnchain fork
    /// Returns Some(corresponding snapshot) if so
    /// Returns None if it's not on the canonical fork
    pub(crate) fn check_valid_consensus_hash<SH: SortitionHandle>(
        sort_handle: &mut SH,
        ch: &ConsensusHash,
    ) -> Result<Option<BlockSnapshot>, ChainstateError> {
        // the target sortition must exist, and it must be on the canonical fork
        let Some(sn) = SortitionDB::get_block_snapshot_consensus(sort_handle.sqlite(), ch)? else {
            // no sortition
            warn!("Invalid consensus hash: no such snapshot"; "consensus_hash" => %ch);
            return Ok(None);
        };
        let Some(ancestor_sn) = sort_handle.get_block_snapshot_by_height(sn.block_height)? else {
            // not canonical
            warn!("Invalid consensus hash: snapshot is not canonical"; "consensus_hash" => %ch);
            return Ok(None);
        };
        if ancestor_sn.sortition_id != sn.sortition_id {
            // not canonical
            return Ok(None);
        }
        Ok(Some(sn))
    }
