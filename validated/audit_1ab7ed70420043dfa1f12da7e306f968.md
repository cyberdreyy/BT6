### Title
v1 chainstate's tenure-change duplicate-block guard checks only globally-accepted blocks, letting a signer sign a second conflicting tenure-start block in the same tenure it already locally accepted - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
Like the Froxlor advisory, where the API path used a weaker, generic validator (`Validate::validate` with a permissive regex) instead of the strict, purpose-specific check the web UI used (`isset($languages[$def_language])`), the Stacks signer has two chainstate implementations that are supposed to enforce the exact same invariant — "don't sign two competing tenure-change blocks in the same tenure" — but use inconsistent strength queries: `chainstate/v2.rs`'s `validate_tenure_change_payload` checks `get_last_signed_block` (locally **or** globally accepted), while `chainstate/v1.rs`'s `validate_tenure_change_payload` checks only `get_last_globally_accepted_block`.

### Finding Description
The duplicate-tenure-block guard exists to stop a signer from signing a second, competing tenure-change block for a tenure it has already committed a signature to. In v2: [1](#0-0) 

it queries `signer_db.get_last_signed_block(&block.header.consensus_hash)`, which is documented to cover blocks that are locally accepted *or* globally accepted (i.e., anything this signer has actually signed).

In v1, the same logically-equivalent guard uses a strictly weaker query: [2](#0-1) 

`get_last_globally_accepted_block` only returns a block once the *group* has reached global acceptance for it — it says nothing about whether *this signer itself* has already locally signed a different tenure-change block for the same tenure that has not yet gathered group consensus. Per the code's own comment on the v2 path ("Only blocks we have signed... count here: a block we have merely pre-committed to carries no signature from us, so it is safe to accept a competing tenure-start block"), the correct equality that must be preserved is "signed-by-me vs. new-competing-proposal", not "globally-accepted vs. new-competing-proposal." v1 checks the wrong side of that equality.

The duplicate check is also proposal-time-only and is never re-run later: [3](#0-2) 

so on the v1 path the only other backstop is the pre-commit-time "own tenure conflict" logic (section 5 of `docs/signer-flows.md`, `get_signed_conflicts`/`reorg_permit_stands`/`conflict_still_blocks` in `stacks-signer/src/v0/signer.rs`). I could not fully verify within the remaining budget whether that later stage queries signed blocks broadly enough to always catch what the weaker v1 proposal-time check missed (i.e., whether `get_signed_conflicts` is filtered the same way `get_last_globally_accepted_block` is, or the way `get_last_signed_block` is). If that later stage also only considers globally-accepted state — or if a race lets the pre-commit threshold for the second tenure-change block cross before the first block's own signature is durably recorded/considered — the weaker v1 check becomes the only gate and a v1-configured signer can end up signing two conflicting tenure-start blocks for the same tenure, one of which is necessarily non-canonical.

### Impact Explanation
If the v1 gap is not fully closed by the later pre-commit-time conflict check, this breaks the "signed vs conflicting" equality that the signer is supposed to enforce per tenure: the signer would produce a valid signature over a second, conflicting tenure-change block for a tenure it already signed a different block for. That is a Critical-class outcome per the rules given ("a signer signing an invalid, non-canonical, or conflicting block"), because it directly threatens the one-signature-per-tenure-start guarantee that protects against tenure equivocation/forking.

### Likelihood Explanation
This requires no majority of signers and no other signer's key — a single miner (the report's threat model: "a one-slot miner plus gossip") can trigger it by proposing a second tenure-change block for the same tenure after a first one was locally (but not yet globally) accepted by a given signer, while that signer is still running the v1 chainstate path (pre-global-signer-state-machine activation, per `check_block_against_local_state` in `stacks-signer/src/v0/signer.rs:875-939`). The likelihood is bounded by how effective the pre-commit-time conflict guard is as a backstop, which I was unable to fully confirm as in-scope for this pass — this is the residual uncertainty in the finding.

### Recommendation
Change `chainstate/v1.rs`'s `validate_tenure_change_payload` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` (matching v2's stricter, "signed by me" semantics) instead of `get_last_globally_accepted_block`, so the duplicate/conflict check is consistent across both chainstate versions and does not rely solely on the later pre-commit-time conflict resolution to catch equivocation that the proposal-time gate was designed to prevent.

### Proof of Concept
1. Operate a signer running the pre-activation (v1) chainstate path (`SortitionsView::check_proposal` reachable via `check_block_against_local_state`, `stacks-signer/src/v0/signer.rs:875-939`).
2. Miner proposes tenure-change block A for tenure T; the signer validates and locally accepts/signs A (`mark_locally_accepted`), but A does not yet reach the group's 70% pre-commit/global-acceptance threshold (e.g., other signers are slow or partitioned).
3. Miner (or a competing miner via a fork) proposes a second, conflicting tenure-change block B for the same tenure T.
4. `SortitionsView::check_proposal` → `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:461-520`) calls `get_last_globally_accepted_block(&B.header.consensus_hash)`, which returns `None` because A was never globally accepted — the duplicate check silently passes.
5. B is submitted for node validation and proceeds toward pre-commit/signing; whether the signer ultimately signs B depends entirely on the later, less-targeted pre-commit-time conflict logic rather than the dedicated proposal-time duplicate-block guard that v2 enforces correctly.
