### Title
Unauthenticated signer event-receiver HTTP endpoint allows forged `/proposal_response` to make a signer sign an invalid/unvalidated block — ([File: libsigner/src/events.rs])

### Summary
The `stacks-signer` process's local HTTP listener (`SignerEventReceiver`) accepts `/proposal_response`, `/stackerdb_chunks`, `/new_burn_block`, and `/new_block` POSTs from anyone who can reach the bound socket, with no authentication and no verification that the sender is the trusted `stacks-node`. The signer's own default sample config binds this listener to `0.0.0.0:<port>` rather than loopback. This is the same bug class as the ActiveMQ advisory: an API surface that is supposed to be trusted-only (Jolokia/Message REST API in ActiveMQ; the node→signer event-push API here) ships without any authentication, so "anyone" who can reach it can interact with it directly — in this case, injecting a forged block-validation verdict.

### Finding Description
`SignerEventReceiver::next_event` in `libsigner/src/events.rs` dispatches incoming HTTP POST requests purely by URL path, with zero authentication or origin/peer verification: [1](#0-0) 

`bind()` opens a plain HTTP server on the configured socket with no auth middleware: [2](#0-1) 

The sample/reference signer config explicitly binds this listener on all interfaces by default: [3](#0-2) 

Contrast this with the node-side `/v3/block_proposal` endpoint, which requires an `authorization` header matching a shared secret before it will even parse the body: [4](#0-3) 

The signer's own event API provides no equivalent protection in the direction node→signer (or, more precisely, anyone→signer, since the receiver cannot distinguish the real node from an attacker).

On the consuming side, `handle_block_validate_response` / `handle_block_validate_ok` in `stacks-signer/src/v0/signer.rs` treats a `BlockValidateResponse::Ok` delivered via `/proposal_response` as authoritative proof that the node's chainstate validated the block (correct state transition, valid transactions, cost limits, etc.). It only checks that the `signer_signature_hash` matches a block it is already locally tracking (from a legitimately-gossiped `BlockProposal`); it performs no independent verification of the actual block execution/correctness — that trust is placed entirely in whoever posted to `/proposal_response`: [5](#0-4) 

The block only gets marked `LocallyRejected` if `check_block_against_signer_db_state` (a signer-local anti-conflict/anti-reorg check, not a chainstate-correctness check) fails; otherwise it is `mark_pre_committed`, broadcast as a pre-commit, and ultimately signed once threshold weight of pre-commits/other spoofed responses is reached: [6](#0-5) 

### Impact Explanation
This breaks the "signed vs. validated" equality that the signer protocol is built on (per `docs/signer-flows.md`: "the stacks-node answers the `/v3/block_proposal` submission... only then advertises willingness to sign"). An attacker who can reach a signer's event-receiver port (bound to `0.0.0.0` by default per the sample config) does not need to be the node, does not need the `auth_token`/`auth_password`, and does not need control of a majority of signers. A single malicious miner (one sortition slot) can:
1. Propose a block via the normal `BlockProposal` gossip path that is actually invalid/non-canonical (e.g., contains a bad state transition that the real node would reject), causing the signer to store a `BlockInfo` with `valid: None` while it awaits the node's real verdict.
2. Race the real node's answer by POSTing a forged `BlockValidateResponse::Ok` for that exact `signer_signature_hash` directly to the signer's exposed HTTP port.
3. The signer accepts the forged "Ok" as if the node had validated the block, skips real chainstate validation, and proceeds through `mark_pre_committed` → pre-commit gossip → (if enough signers are similarly spoofed, or the attacker also forges/aggregates weight) `mark_locally_accepted` and signs the block.

This is a Critical-class outcome per the rules: a signer producing a valid cryptographic signature over a block that was never actually validated by the trusted stacks-node — i.e., signing a potentially invalid/non-canonical block.

### Likelihood Explanation
Requires the attacker to: (a) control at least one miner slot to legitimately get a candidate (possibly invalid) block gossiped and tracked by signers, and (b) have network reachability to the signer's event-receiver port before the genuine node's validation response arrives. Reachability is realistic because the documented/sample signer configuration binds `0.0.0.0`, and there is no code-level authentication mechanism at all on this listener (unlike the node's `/v3/block_proposal`, which is loopback + shared-secret gated). No majority-signer collusion or key compromise is needed to win the local race against a single target signer.

### Recommendation
- Require the same mutual-authentication mechanism used for `/v3/block_proposal` (a shared `auth_token`/`auth_password` header check) on all `SignerEventReceiver` endpoints (`/proposal_response`, `/stackerdb_chunks`, `/new_burn_block`, `/new_block`), rejecting unauthenticated requests before parsing.
- Default-bind the signer's event listener to loopback (`127.0.0.1`) unless explicitly overridden, and update sample configs (`mainnet-signer-conf.toml`) accordingly.
- At minimum, verify the request originates from the configured `node_host` peer/IP as defense in depth.

### Proof of Concept
1. Start a signer with default sample config (`endpoint = "0.0.0.0:30000"`, no auth on the event receiver).
2. As a malicious miner, propose (via StackerDB gossip, the normal `BlockProposal` path) a block that is actually invalid according to the real node's chainstate rules; the target signer stores it with `valid: None` (`stacks-signer/src/v0/signer.rs` proposal-handling path, `insert_block`).
3. Before the genuine node responds, send a raw HTTP POST to the signer's bound address:
   ```
   POST /proposal_response HTTP/1.1
   Content-Type: application/json

   {"Ok": {"signer_signature_hash": "<hash of the invalid block>", "block": "<hex>", "cost": {...}, "size": ..., "validation_time_ms": 0}}
   ```
   (matching `BlockValidateResponse::Ok` JSON shape parsed by `process_event::<T, BlockValidateResponse>`, `libsigner/src/events.rs:440`).
4. Observe the signer log/handle `handle_block_validate_ok` treats this as authoritative, calls `mark_pre_committed`, and broadcasts a pre-commit for the block — without the real node ever having validated it (`stacks-signer/src/v0/signer.rs:1960-1984`).
