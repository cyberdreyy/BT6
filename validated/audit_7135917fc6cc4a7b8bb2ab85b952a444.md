### Title
Unbounded retry-on-Temporary-error loop in the fault-proof driver's `produce_payload` — ([File: crates/proof/driver/src/pipeline.rs])

### Summary
`DriverPipeline::produce_payload`, the default trait method used by the fault-proof program's derivation driver, retries *every* `PipelineErrorKind::Temporary` variant unconditionally via `continue`, instead of narrowing the retry to the one condition that can actually resolve with more local data (`PipelineError::NotEnoughData`). This mirrors the CVE-2017-6467 bug class: a parser loop lacking a tight restriction on when to keep looping versus bail out, so a crafted/degenerate input (or a stalled pipeline state) drives the loop forever.

### Finding Description
`produce_payload` steps the derivation pipeline and, on any `StepResult::OriginAdvanceErr`/`StepFailed` carrying `PipelineErrorKind::Temporary(_)`, does an unconditional `continue` back to the top of the loop: [1](#0-0) 

Compare this with the equivalent sequencer-side derivation actor, which deliberately narrows the retry condition to `PipelineError::NotEnoughData` only, and treats any other `Temporary` error as a reason to yield rather than spin: [2](#0-1) 

`PipelineError` documents `Eof` and `NotEnoughData` as distinct: `Eof` means "the channel bank has been completely drained ... may require waiting for new L1 blocks", while only `NotEnoughData` is the truly retriable "more data may already be buffered" condition: [3](#0-2) 

Both are wrapped identically as `PipelineErrorKind::Temporary`: [4](#0-3) 

Because `produce_payload` does not distinguish between them, any stage returning `PipelineError::Eof.temp()` (e.g. `ChannelBank::read` when the channel queue is empty) is retried in a tight loop with no forward progress in the fault-proof program's fixed-input environment: [5](#0-4) 

Unlike a live sequencer/verifier, which can eventually receive new L1 blocks and legitimately resolve `Eof`, the fault-proof program (`crates/proof/driver`) derives from a bounded, pre-populated preimage oracle for a fixed L1 window. If the pipeline ever reaches a state where a stage keeps handing back `Temporary(Eof)` (or any other `Temporary` variant) without the origin advancing and without escalating to `PipelineErrorKind::Critical(PipelineError::EndOfSource)`, `produce_payload`'s `continue` never reaches the `self.next()` check and never returns — an unbounded busy loop, directly analogous to the Wireshark Netscaler parser's infinite loop on a malformed/bounded file whose size restrictions weren't tight enough to force termination.

`Driver::advance_to_target`, the sole caller of `produce_payload` in the fault-proof driver, only special-cases `Critical(EndOfSource)`; it has no independent timeout or step-count cap of its own, so it fully depends on `produce_payload` to terminate: [6](#0-5) 

### Impact Explanation
The fault-proof program runs inside a resource-bounded, cycle-metered VM (cannon/zkVM) executing a fault dispute game step. An unbounded busy loop in the driver means the program never terminates, never computes an output root, and the honest party cannot produce a valid response within the dispute-game clock — leading to the program either hitting the VM's hard step limit (producing no or a wrong/incomplete provable output) or timing out the off-chain prover entirely. This can prevent an honest challenger/defender from responding correctly to a bisection step, undermining the fault-proof game's guarantee of eventually reaching a correct, provable output root — a "node halt / wrong or missing provable output root" class impact per the validation scope.

### Likelihood Explanation
Reachability requires only that some pipeline stage return a `Temporary` error other than `NotEnoughData` (most plausibly `Eof`) at a point where the pipeline cannot make further progress and does not itself escalate to `Critical(EndOfSource)`. I was not able to fully trace every stage transition (in particular the exact conditions under which `L1Traversal`/origin-advance stages escalate `Eof` to `EndOfSource` versus leave it as `Temporary`) within the available investigation budget, so I cannot confirm with certainty that this path is reachable from attacker-controlled L1 batch/channel data without further tracing of `L1Traversal` and `ChannelBank`/`ChannelAssembler` interplay. This is a real logic gap (unconditional retry on the whole `Temporary` category rather than the single condition that can resolve without new data) but confirming an end-to-end trigger requires deeper stage-by-stage analysis than I completed.

### Recommendation
In `crates/proof/driver/src/pipeline.rs`, mirror the actor's narrower handling: only `continue` on `PipelineErrorKind::Temporary(PipelineError::NotEnoughData)`; treat any other `Temporary` variant (notably `Eof`) as a terminal/yield condition (or explicitly map it to `Critical(EndOfSource)`), and add a bounded consecutive-no-progress counter (as is already done in the test harness) so any residual stall degrades to an explicit error instead of an infinite loop.

### Proof of Concept
Not independently constructed — a concrete PoC would require crafting L1 batch/channel data (or a preimage-oracle state) that drives a derivation stage to repeatedly return `PipelineError::Eof.temp()` (or another non-`NotEnoughData` `Temporary` error) from `produce_payload`'s call to `self.step(...)` without the origin ever advancing and without the pipeline escalating to `Critical(EndOfSource)`. I was unable to verify within the available time whether such a state is reachable from attacker-controlled batch data alone; this would need to be validated with a running fault-proof-program harness before treating the finding as fully proven.
