### Title
Integer overflow/underflow in gateway staleness check allows replay of stale/malicious WebAPI trigger messages - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The Bitcoin Core commit fixes a signed integer overflow that occurs when an untrusted, attacker/malformed time field is added to a `time.Duration` without bounds checking. In the Chainlink gateway, `HandleLegacyUserMessage` performs an analogous unsafe operation: it casts an attacker-controlled `payload.Timestamp` field directly to `uint` and compares it against `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec`, without validating that the signed timestamp value is sane before the cast.

### Finding Description
`HandleLegacyUserMessage` decodes a JSON payload from an unauthenticated/unprivileged external message and performs the staleness check entirely with unsigned arithmetic on a value that originates as a signed field: [1](#0-0) 

Specifically:
```
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    ... "stale message" ...
}
```
`payload.Timestamp` comes from `webapicap.TriggerRequestPayload`, populated via `json.Unmarshal(body.Payload, &payload)` from a `MessageBody.Payload` that is fully attacker-controlled (arbitrary JSON number), the same class of "malformed time field" that triggered the referenced Bitcoin overflow. Casting an attacker-supplied signed integer to `uint` (`uint(payload.Timestamp)`) is undefined/wraps for negative or out-of-range values in Go, exactly mirroring the underlying bug class in the external report (untrusted time field feeding unchecked integer arithmetic that governs a security-relevant comparison, causing overflow/wraparound instead of a rejected/handled input).

This staleness check is the primary anti-replay control on this path — the code even documents that the allowlist/rate-limiting for this exact message type is not yet implemented: [2](#0-1) 

The request reaches this code without DON-membership enforcement: `Message.Validate()` only checks field lengths/format and extracts an ECDSA signer, it does not check the signer against any authorization list before this handler runs: [3](#0-2) 
Any actor able to generate a keypair and sign a `Message` can therefore reach `HandleLegacyUserMessage` and control `payload.Timestamp`.

### Impact Explanation
By supplying a crafted `Timestamp` (e.g., a negative int64 or a value causing the unsigned wraparound), an unprivileged sender can make the staleness comparison always evaluate false, bypassing the only anti-replay/freshness gate on this path (the allowlist gate is explicitly noted as not yet implemented). This allows replay or injection of stale/forged `web_api_trigger` messages toward DON nodes, undermining the freshness guarantee the check was designed to enforce.

### Likelihood Explanation
The path is reachable directly from the Gateway's public request-processing entry point (`gateway.ProcessRequest` → legacy message path) by any actor able to produce a validly-formatted, self-signed `Message`, with no DON-membership/allowlist check applied before the staleness comparison. Constructing an out-of-range timestamp value is trivial (pure JSON payload manipulation), making exploitation straightforward once the flow is understood.

### Recommendation
Validate `payload.Timestamp` before using it in unsigned arithmetic: reject negative values or values outside a sane range prior to any cast, and perform the staleness comparison using signed `int64` arithmetic (`time.Now().Unix()`, `payload.Timestamp`, and `MaxAllowedMessageAgeSec` all as `int64`) with explicit bounds checks instead of relying on `uint` wraparound behavior. Additionally, implement the still-pending allowlist/rate-limiting check noted in the code before this staleness gate is relied upon as the sole freshness control.

### Proof of Concept
1. Craft a legacy `api.Message` with `Body.Method = "web_api_trigger"`, a validly-formatted signature (self-signed with any ECDSA key), and a `Payload` JSON containing `webapicap.TriggerRequestPayload{Timestamp: <negative or out-of-range int64>}`.
2. Send it to the Gateway's public endpoint so it is routed to `handler.HandleLegacyUserMessage` (per `gateway.ProcessRequest`'s legacy-DON-ID branch). [4](#0-3) 
3. Because `uint(payload.Timestamp)` wraps for the crafted value, the staleness check `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` evaluates to `false` regardless of actual message age, and the message is forwarded to all DON members instead of being rejected as stale.

		return errors.New("invalid method name length")

		return errors.New("method name ending with null bytes")

		return errors.New("invalid DON ID length")
