### Title
Metrics endpoint Bearer token compared with non-constant-time `!=` enabling timing side-channel - ([File: core/web/router.go])

### Summary
`prometheusHandler` in `core/web/router.go` compares the caller-supplied `Authorization` header directly against the expected `"Bearer " + token` string using Go's built-in `!=` operator, which is not a constant-time comparison. [1](#0-0)  This can, in theory, leak timing information proportional to the number of matching prefix bytes, since Go's string equality returns early on the first differing byte after a length check.

### Finding Description
The `/metrics` route is registered without going through the normal `auth.Authenticate` middleware stack; it is wired up directly in `prometheusUse`, which calls `prometheusHandler(p.Token, h)` as the sole gatekeeper for the endpoint. [2](#0-1) 

Inside `prometheusHandler`, when a token is configured (`PrometheusAuthToken`), the handler builds the expected value `bearer := "Bearer " + token` and checks `if header != bearer` to reject non-matching requests. [3](#0-2)  Standard Go string comparison (`==`/`!=`) first compares lengths and then performs a byte-by-byte scan that exits on the first mismatch — it is not implemented with `crypto/subtle.ConstantTimeCompare` or similar, so in principle response latency could vary slightly based on how many leading bytes of the guessed token match the real secret.

An unauthenticated network client can reach this comparison directly by sending GET requests to the metrics path (`p.MetricsPath`, typically `/metrics`) with different `Authorization: Bearer <guess>` values — no session, API token, or role is required, satisfying the "unauthenticated client" attacker model.

### Impact Explanation
If successfully exploited, an attacker could incrementally recover the Prometheus scrape token via timing measurements and then read the `/metrics` endpoint, exposing internal Prometheus counters/gauges (queue depths, job counts, internal service metrics, potentially some operational fingerprinting data). This maps to a scoped "sensitive information disclosure" impact class rather than any authentication bypass of the core node API, key material, or fund-movement paths — the metrics token guards only observability data, not job execution, keys, or funds.

### Likelihood Explanation
Exploitability is low in practice. The comparison operates over an in-process HTTP handler where network jitter, Go runtime scheduling, GC pauses, and TLS/HTTP/gzip overhead introduce noise many orders of magnitude larger than the sub-nanosecond timing difference from a single byte mismatch in a short string comparison. Extracting a token (typically a reasonably long random string) via remote timing analysis over a real network is considered highly impractical, though not theoretically impossible with a large number of samples in a low-latency/low-jitter environment (e.g., same host or same rack). No misconfiguration is required beyond `PrometheusAuthToken` being set (this endpoint is unauthenticated if the token is empty, which is a separate, out-of-scope configuration concern). No privilege beyond unauthenticated network access is needed to attempt the attack, but the attack requires unusually favorable network conditions and a large volume of timed requests to be effective.

### Recommendation
Replace the direct string comparison with a constant-time comparison, e.g.:
```go
if subtle.ConstantTimeCompare([]byte(header), []byte(bearer)) != 1 {
    c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
    return
}
```
using `crypto/subtle.ConstantTimeCompare`, ensuring both byte slices are of consistent length before comparison (or hash both values with a fixed-size MAC/hash first) to avoid leaking length information as well.

### Proof of Concept
Go handler-level test plan (`core/web/router_test.go` or a new test file):
1. Build a `gin.Engine` with only the `prometheusHandler(token, dummyHandler)` route registered, using a fixed, sufficiently long `token`.
2. For a range of guessed tokens that share an increasing correct prefix length (0, 25%, 50%, 75%, 99% correct prefix) vs. a token that is wrong in the very first byte, send N (e.g., 10,000) requests each with `Authorization: Bearer <guess>` and record `time.Now()` before/after `ServeHTTP`.
3. Compute mean/median latency per prefix-length bucket and compare distributions (e.g., via a statistical test such as Welch's t-test or simply comparing means with a threshold).
4. Assert that the fix (using `subtle.ConstantTimeCompare`) makes latency independent of prefix match length (variance below a defined negligible threshold, e.g., < 1% relative difference), while document that the current `!=` implementation may show a measurable (even if small and noisy) trend correlating with prefix match length under controlled, low-noise conditions (e.g., running the test with `GOMAXPROCS=1` and disabling GC via `debug.SetGCPercent(-1)` during the timing loop to reduce noise).
5. Use the result to confirm the code path lacks constant-time comparison, independent of whether the timing signal is remotely exploitable.

```go
func prometheusUse(p *ginprom.Prometheus, e *gin.Engine, handlerOpts promhttp.HandlerOpts) {
	var (
		r prometheus.Registerer = p.Registry
		g prometheus.Gatherer   = p.Registry
	)
	if p.Registry == nil {
		r = prometheus.DefaultRegisterer
		g = prometheus.DefaultGatherer
	}
	h := promhttp.InstrumentMetricHandler(r, promhttp.HandlerFor(g, handlerOpts))
	e.GET(p.MetricsPath, prometheusHandler(p.Token, h))
	p.Engine = e
}
```

```go
func prometheusHandler(token string, h http.Handler) gin.HandlerFunc {
	return func(c *gin.Context) {
		if token == "" {
			h.ServeHTTP(c.Writer, c.Request)
			return
		}

		header := c.Request.Header.Get("Authorization")

		if header == "" {
			c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
			return
		}

		bearer := "Bearer " + token

		if header != bearer {
			c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
			return
		}

		h.ServeHTTP(c.Writer, c.Request)
	}
```
