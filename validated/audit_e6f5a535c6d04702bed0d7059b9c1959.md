### Title
Borrower repayments after a hard default are accepted but never enter the recovery waterfall - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
Analogous to the Teller report (repaying a loan whose collateral was already liquidated), `ProgrammableBorrower.repay()` / `executeRepay()` remain fully callable after `IdleCDOEpochVariant._handleBorrowerDefault` fires `onDefault()`, and `finalizeDefault`/`finalizeDefaultRecovery` never credit post-default inflows to the recovery reserve. A borrower (or its executor) who repays a defaulted facility sees its debt bookkeeping cleared while the repaid underlying is stranded in the `ProgrammableBorrower` contract — outside the `defaultRecoveryReserve`, outside `totalBasis`, and unreachable by defaulted claimants, exactly like repaying into an already-liquidated position.

### Finding Description
- `stopEpoch`/`getInstantWithdrawFunds` catch borrower funding failure and call `_handleBorrowerDefault`, which sets `defaulted = true` and invokes `IProgrammableBorrower.borrower().onDefault()`. `onDefault` only flips `epochAccountingActive = false`; it does not gate `repay()` (contracts/IdleCDOEpochVariant.sol:577-599; contracts/strategies/idle/ProgrammableBorrower.sol:289-301).
- `_repay` still clears `borrowerInterestDebt`, `borrowerInterestAccrued`, and `borrowerPrincipal` via `safeTransferFrom`, pulling real underlying from the borrower. Because `epochAccountingActive` is false, the funds are not redeployed to the vault; the `currentEpochInterestPaid` portion is dumped into `bufferInterest`, which is only ever consumed by `totalInterestDueNow()`/stop-epoch accounting — a path that can never run again after a hard default (contracts/strategies/idle/ProgrammableBorrower.sol:466-533).
- On the CDO side, `finalizeDefault` skims all raw underlying sitting on the CDO to `feeReceiver` as a "donation" before computing recovery, and `finalizeDefaultRecovery` computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` — deliberately excluding any borrower-sent funds sitting on the strategy (contracts/IdleCDOEpochVariant.sol:194-210; contracts/strategies/idle/IdleCreditVault.sol:661-709).
- After finalization the situation is worse: `reserveDefaultRecovery` reverts once `defaultRecoveryFinalized` is set (contracts/strategies/idle/IdleCreditVault.sol:631-633), and the comment on `finalizeDefault` states "Finalization is one-time and cannot be topped up through this recovery path" — so a post-finalization repayment is permanently excluded from `defaultRecoveryPrice`. Every defaulted and post-default receipt then claims `claimBasis * defaultRecoveryPrice` from the fixed `defaultRecoveryReserve` (`_transferDefaultRecovery`, contracts/strategies/idle/IdleCreditVault.sol:912-917), while the repaid cash sits idle in `ProgrammableBorrower` recoverable only via privileged `rescueTokens` to the owner — never to LPs.

### Impact Explanation
Direct, quantified loss equal to the repaid amount. The borrower's ledger debt is erased (so it has no claim to a refund), yet the repayment neither reduces the crystallized LP loss nor reaches `defaultRecoveryReserve`. One of two outcomes occurs: (a) repayment lands on the CDO/strategy and is skimmed to `feeReceiver` by `_skimDonatedAssets` at the next `stopEpoch`/`finalizeDefault`, or (b) repayment lands in `ProgrammableBorrower` and is stranded, claimable only through owner `rescueTokens`. In both cases recovery claimants stay haircut and the payer loses the funds — the same "repay into an already-liquidated position" loss as the Teller issue.

### Likelihood Explanation
The window is permanently open after `defaulted = true` and there is no revert path: `repay()` has no `defaulted`/`epochAccountingActive == true` check, executors can trigger it via `executeRepay`, and nothing warns the borrower that repayment no longer affects tranche recovery. The protocol's own design acknowledges borrower-returned funds belong in recovery (`reserveDefaultRecovery(_toBorrower)` on the failed `sendFundsToBorrower` path), so a borrower paying down its defaulted debt is a natural, expected action — yet the same economic inflow through the sanctioned `repay()` entrypoint is silently dropped from the recovery waterfall.

### Recommendation
- Revert in `ProgrammableBorrower._repay` (and `executeRepay`) once `epochAccountingActive == false` due to default, or expose a `defaulted` flag set by `onDefault()` that blocks repayment.
- Alternatively/additionally, route repaid underlying from `ProgrammableBorrower` to the CDO/strategy so it is accounted via `reserveDefaultRecovery` before finalization, and treat strategy-held borrower inflows as part of `reserveAmount` in `finalizeDefaultRecovery` rather than leaving them unaccounted.
- In `IdleCDOEpochVariant.finalizeDefault`, consider counting CDO-held underlying attributable to borrower repayment as recovery instead of unconditionally donating it via `_skimDonatedAssets`.

### Proof of Concept
Foundry fork PoC against the programmable-borrower suite (pattern follows `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testRepayAfterDefaultIsStranded() external {
    uint256 amount = 10_000 * oneScale;
    uint256 drawAmount = 4_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);

    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(drawAmount);

    // Epoch ends, borrower cannot fund -> hard default (liquidation analog)
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1);
    assertTrue(cdoEpoch.defaulted());
    assertFalse(programmableBorrower.epochAccountingActive());

    // Borrower still owes principal; repays through the sanctioned entrypoint
    uint256 owed = programmableBorrower.borrowerPrincipal();
    deal(USDC, revolvingBorrower, owed, true);
    uint256 strategyBalPre = underlying.balanceOf(address(strategy));
    uint256 borrowerBalPre = underlying.balanceOf(revolvingBorrower);

    vm.prank(revolvingBorrower);
    (uint256 iPaid, uint256 pPaid) = programmableBorrower.repay(0);

    // Debt cleared and cash pulled...
    assertEq(pPaid, owed);
    assertEq(programmableBorrower.borrowerPrincipal(), 0);
    assertEq(underlying.balanceOf(revolvingBorrower), borrowerBalPre - owed);
    // ...but recovery reserve/strategy backing is unchanged: funds stranded
    assertEq(underlying.balanceOf(address(strategy)), strategyBalPre);
    assertEq(underlying.balanceOf(address(programmableBorrower)), owed);

    // Finalize recovery: repaid funds are excluded from totalBasis/reserve
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 recovered = activeBasis * 7e17 / ONE_TRANCHE;
    deal(USDC, manager, recovered);
    vm.startPrank(manager);
    underlying.approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // Repayment never raised defaultRecoveryPrice; still stuck in the borrower contract
    assertEq(underlying.balanceOf(address(programmableBorrower)), owed);
    assertLe(strategy.defaultRecoveryReserve(), recovered + 10_000);
}
```

The invariant broken: one receipt one payout plus solvency of the recovery waterfall — protocol accepts value that extinguishes borrower debt without crediting the pool that absorbed the loss.
