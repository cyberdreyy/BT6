### Title
Unchecked `fec_set_count`/`fec_set_index` arithmetic in `BlockIdRepairService::process_block_id_repair_response` allows a single malicious repair reply to trigger integer overflow / unbounded allocation - (File: core/src/repair/block_id_repair_service.rs)

### Summary
`process_block_id_repair_response` derives `fec_set_index` values directly from an attacker-supplied `fec_set_count` in a `ParentFecSetCount` response with no upper-bound validation, then later performs unchecked `u32` addition (`fec_set_index + DATA_SHREDS_PER_FEC_BLOCK as u32`) when processing the corresponding `FecSetRoot` response. Both the multiplication used to derive `fec_set_index` and the later addition to compute `end_index` can overflow, and the unbounded `(0..fec_set_count)` range itself can also cause unbounded memory allocation from a single response.

### Finding Description
In the `ParentFecSetCount` arm of `process_block_id_repair_response`, the fec-set indices used for follow-up `FecSetRoot` requests are computed with no bound check on the attacker-controlled `fec_set_count`: [1](#0-0) 

This is a wincode-deserialized field from a peer's response object (`BlockIdRepairResponse::ParentFecSetCount { fec_set_count, .. }`), verified only via nonce/merkle-proof checks in `register_response` (which validate that the response corresponds to an outstanding request, not that `fec_set_count` is sane): [2](#0-1) 

If `fec_set_count` is chosen near `u32::MAX`, the `(0..fec_set_count)` range causes the multiplication `i * DATA_SHREDS_PER_FEC_BLOCK as u32` to overflow well before the loop completes, and the `.extend(...)` call attempts to push up to `fec_set_count` entries into `pending_repair_requests` (an unbounded `BinaryHeap`), which is itself a large-scale, single-response memory-amplification vector.

Later, when a corresponding `FecSetRoot` response arrives, the (already possibly wrapped/overflowed) `fec_set_index` recovered from our own tracked outgoing request is used unchecked: [3](#0-2) 

`end_index = fec_set_index + DATA_SHREDS_PER_FEC_BLOCK as u32` has no `checked_add`/`saturating_add` guard, so if a debug/overflow-checked build is used, this add panics; in a release build without `overflow-checks`, it silently wraps, producing a corrupted `(start_index..end_index)` range which is empty or otherwise incorrect, feeding bogus `ShredForBlockId` requests into the pipeline.

Note: I was unable to confirm from available context whether this workspace's release Cargo profile sets `overflow-checks = true` (common in Solana/Agave-derived repos to treat overflow as a hard bug). This determines whether the overflow manifests as a validator panic (abort) versus a silent, non-crashing logic bug (wrapped range). Either way, the lack of validation on `fec_set_count`/`fec_set_index` and the lack of checked arithmetic are confirmed defects in the code as shown.

### Impact Explanation
A single malicious peer response to an outstanding `ParentFecSetCount` request can (a) cause unbounded allocation into `pending_repair_requests` from one packet, and (b) drive `fec_set_index` values that, combined with the unchecked `+ DATA_SHREDS_PER_FEC_BLOCK` addition in the `FecSetRoot` handler, either panic the validator process (if overflow checks are compiled in) or corrupt the derived shred-index request range (if not). This falls under "validator abort via one crafted repair reply" / unbounded cost for a single response in the given scope.

### Likelihood Explanation
Preconditions require the attacker to be an already-eligible repair peer replying to our own outstanding `ParentFecSetCount` request (reachable by any node that a validator sends repair requests to, per the described repair protocol, no special stake/leader/gossip control needed beyond serving repair responses), then replying to the follow-on `FecSetRoot` request we ourselves generate. The nonce/merkle-proof check in `register_response` only authenticates that the response matches an outstanding request/slot — it does not bound `fec_set_count` or re-derive `fec_set_index` safely. This makes the path feasible with a single crafted reply pair.

### Recommendation
- Bound `fec_set_count` from `ParentFecSetCount` responses to a sane maximum (e.g., derived from known max shreds per block) before iterating/extending `pending_repair_requests`.
- Use `checked_mul`/`checked_add` (or `saturating_*`) when deriving `fec_set_index` from `fec_set_count`, and when computing `end_index = fec_set_index + DATA_SHREDS_PER_FEC_BLOCK as u32`, dropping/rejecting requests that would overflow rather than proceeding.
- Cap the number of entries added to `pending_repair_requests` per response.
