### Title
Flash-loan share-dilution attack on `lending_pool_emissions_deposit` lets an attacker steal reward/emissions value from genuine bank depositors - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
`lending_pool_emissions_deposit` is a fully permissionless instruction that injects tokens directly into a bank's `liquidity_vault` and immediately re-prices `asset_share_value` for the whole pool, exactly as `LiquidityDeployer.deployLiquidity` injects the WETH fee directly into the ERC-4626-style `LiquidityPool`. Because marginfi's `lending_account_deposit`/`lending_account_withdraw` place no restriction on depositing and withdrawing in the same transaction or slot, an attacker can flash-loan the bank's underlying asset, deposit it to temporarily dominate `total_asset_shares`, trigger (or wait for) an emissions deposit, then withdraw immediately at the new inflated `asset_share_value` — capturing almost the entire reward at the expense of the bank's existing, genuine long-term depositors.

### Finding Description
`lending_pool_emissions_deposit` performs a lump-sum, one-shot injection of value into the shared pool that instantaneously raises `asset_share_value` for all shareholders proportionally: [5](#0-4) 

The accounts context shows the only signer requirement is `depositor: Signer<'info>` — there is no `has_one = admin` or group-admin gate, i.e. it is callable by anyone with funds to donate: [6](#0-5) 

Meanwhile, ordinary deposit/withdraw flows do not block same-block or same-transaction round-trips: `lending_account_deposit` only checks `ACCOUNT_DISABLED`/`ACCOUNT_IN_RECEIVERSHIP` [2](#0-1) , and `lending_account_withdraw` similarly has no flash-loan/cooldown guard [3](#0-2) . Users are also explicitly permitted to perform flashloans within a single atomic transaction [4](#0-3) .

Combining these facts: whenever a legitimate emissions/reward deposit is about to be made into a bank (whether by a project, community member, or admin acting as `depositor`), an attacker who front-runs it with a large flash-loaned deposit can capture the bulk of the reward and then exit in the same transaction, diluting the actual long-term depositors who were the intended beneficiaries of the reward. This is architecturally identical to the RUSH1-7 root cause: a fee/reward is transferred directly into a share-priced vault without any locking mechanism, and deposit+withdraw are not restricted from occurring in the same block/transaction.

### Impact Explanation
This allows a flash-loan-funded attacker to redirect nearly all of an emissions/incentive deposit intended for real depositors to themselves, diluting existing shareholders' expected yield. Depending on the size of the emissions deposit relative to the flash-loanable liquidity of the underlying asset, this can transfer significant value away from genuine LPs on a per-bank basis with essentially zero capital cost to the attacker (aside from flash-loan fees and gas/compute). It is a direct value-redirection / misappropriation of protocol-directed incentive funds, matching the "High" severity classification of the analogous RUSH1-7 finding.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: `lending_pool_emissions_deposit` is permissionless and its calls are typically observable in the mempool/transaction history before confirmation (or can be time-coordinated if scheduled), and Solana flashloans (`lending_account_start_flashloan`/`lending_account_end_flashloan`, or general deposit+withdraw composition within one atomic tx) are natively supported by marginfi and by third-party flash-loan sources for most liquid mints. Any attacker capable of borrowing a large amount of the target bank's underlying asset for a single transaction can execute this attack whenever an emissions/incentive event occurs.

### Recommendation
- Prevent deposit and withdrawal of the same position within the same transaction or the same slot (e.g., record the slot of the last deposit per balance and block a withdraw for that balance in the same slot), mirroring the remediation suggested in the RUSH1-7 report.
- Alternatively, restrict `lending_pool_emissions_deposit` (and any other same-bank value-injection instruction) to only inject value that vests/accrues over time (e.g., stream it via the existing time-based interest accrual mechanism) rather than instantaneously repricing `asset_share_value` in a single atomic step.
- Consider gating `lending_pool_emissions_deposit` behind a minimum notice period, an admin-only authorization, or a commit-reveal/streaming mechanism so a flash-loaned deposit cannot be timed precisely against the injection.

### Proof of Concept
1. Attacker flash-loans a very large amount `F` of a bank's underlying mint.
2. Attacker calls `lending_account_deposit` for `F`, minting `F / asset_share_value` new asset shares and becoming the overwhelming majority shareholder of the bank (state changes shown at [7](#0-6) ).
3. In the same transaction, the attacker (or a coordinated/observed third party) calls the permissionless `lending_pool_emissions_deposit(amount = Z)`, which transfers `Z` into the bank's `liquidity_vault` and raises `asset_share_value` for the entire pool [8](#0-7) .
4. Still within the same transaction, the attacker calls `lending_account_withdraw` with `withdraw_all = true`, redeeming their shares at the newly inflated `asset_share_value` [9](#0-8) , and repays the flash loan.
5. As attacker's share of `total_asset_shares` approaches 100% (via a sufficiently large flash loan `F`), the attacker recovers nearly the entirety of `Z` back, while genuine long-term depositors (whose shares were diluted during the attacker's temporary deposit) receive almost none of the intended reward — reproducing the RUSH1-7 "flash-loan stake to bypass fee/steal yield" pattern.

```rust
/// Permissionlessly deposit same-mint emissions directly into the bank liquidity vault,
/// increasing depositor value through asset share value.
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```
