### Title
Multisig confirmation threshold can be re-parameterized to `0` (or below the live key/member count) with no validation, letting a single key bypass the K-of-N requirement - (File: multisig/src/lib.rs)

### Summary
The `SetNumConfirmations` request action lets the multisig itself change `num_confirmations` — the number of confirmations required before any request (transfers, key changes, contract deploys, function calls) executes — but the value is written with no bounds check at all. This is the exact bug class described in the report: a critical governance parameter (`self.num_confirmations`, functionally analogous to `PLURALITY`/threshold parameters) is re-parameterized without sanity/threshold checks, and the resulting invalid state breaks the fundamental custody binding the contract is supposed to enforce: "confirmations counted versus live members."

### Finding Description
`confirm()` decides whether a request executes by comparing the number of collected confirmations against `self.num_confirmations`: [1](#0-0) 

```
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    ...
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else { ... }
}
```

`self.num_confirmations` is set from `SetNumConfirmations` with no validation whatsoever: [2](#0-1) 

```
MultiSigRequestAction::SetNumConfirmations { num_confirmations } => {
    self.assert_one_action_only(receiver_id, num_actions);
    self.num_confirmations = num_confirmations;
    return PromiseOrValue::Value(true);
}
```

There is no assertion that `num_confirmations > 0`, and no assertion relating it to the actual number of live multisig keys/members. The `new()` constructor has the same gap — it accepts an arbitrary `u32` with no lower bound: [3](#0-2) 

Once `num_confirmations` is set to `0` (or `1`), the equality the contract is supposed to preserve — "a request executes only if confirmations collected ≥ the configured threshold, and that threshold reflects the intended K-of-N policy" — breaks: with `num_confirmations = 0`, the check `confirmations.len() as u32 + 1 >= self.num_confirmations` is true even before any confirmation is recorded (0 + 1 >= 0), so a single call to `confirm()` by any one of the multisig's access keys immediately executes the request — including `Transfer`, `AddKey` (granting full access), `DeployContract`, or arbitrary `FunctionCall` actions — with zero real confirmations. This state is permanent going forward for every future request until reparameterized again.

The identical pattern (same missing bound) exists in the account-based `multisig2` contract: [4](#0-3) 

### Impact Explanation
This is Critical: once `num_confirmations` is degraded to `0`/`1`, a single key holder can move all NEAR held by the multisig account, add a full-access key to hijack the account entirely, or deploy arbitrary new contract code — all without reaching the intended K-of-N quorum. This directly matches the report's "a multisig request executed below threshold" impact category, and matches the custody binding named in the rules: confirmations counted versus live members.

### Likelihood Explanation
Reaching this state does not require compromising the foundation or an external victim key — it only requires the current quorum (however it was configured) to approve one `SetNumConfirmations` request, which is a normal, expected multisig operation (changing the threshold, e.g., temporarily lowering it, or from operator error). Because there is no invariant enforced (`num_confirmations >= 1`, or `num_confirmations <= number of registered keys/members`), a single mistaken or malicious proposal accepted by the current quorum permanently and silently converts the multisig into a single-key-controlled account for every subsequent request, with no recovery path other than another `SetNumConfirmations` request — which itself now only needs one signer.

### Recommendation
Add an invariant check in both the `new()` initializer and the `SetNumConfirmations` handler (in `multisig/src/lib.rs` and the equivalent in `multisig2/src/lib.rs`):
- Require `num_confirmations >= 1`.
- Require `num_confirmations` does not exceed the number of currently registered keys/members, so the threshold can never be unreachable or trivially satisfiable.
Apply the same style of `assert_valid()` pattern already used elsewhere in the codebase (e.g., `RewardFeeFraction::assert_valid` in `staking-pool/src/lib.rs`) to validate this parameter before committing it.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 2` and 3 access keys (K1, K2, K3), matching intended 2-of-3 policy.
2. K1 calls `add_request_and_confirm` with `{"receiver_id": multisig_account, "actions": [{"type": "SetNumConfirmations", "num_confirmations": 0}]}`.
3. K2 calls `confirm(request_id)` — this reaches the *current* threshold of 2, so `self.num_confirmations` becomes `0`. (Existing test `test_change_num_confirmations` in `multisig/src/lib.rs` lines 660-673 shows this call path works with no validation, just with `num_confirmations: 2` instead of `0`.)
4. Now K1 alone calls `add_request_and_confirm` with `{"receiver_id": multisig_account, "actions": [{"type": "Transfer", "amount": "<entire balance>"}]}`.
5. In `confirm()`, `confirmations.len() as u32 + 1 >= self.num_confirmations` evaluates `0 + 1 >= 0` → `true`, so the transfer executes immediately with only K1's single confirmation — bypassing the intended 2-of-3 threshold entirely.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
