### Title
Unprivileged ERC4626 vault user can indefinitely block `stopEpoch` via `onStopEpoch` liquidity recall - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary

The external bug is a "sleeping-in-atomic-context" flaw: a blocking teardown call (`nfsd_file_put_local` → `fput` → `down_read`) was executed while an RCU read lock was held, because two resource puts were combined to save an indirect reference. The idle-tranches analog is a blocking external call executed inside the epoch-stop critical path: `IdleCDOEpochVariant._stopEpoch` invokes `ProgrammableBorrower.onStopEpoch`, which performs a `vault.withdraw(shortfall, ...)` on an external ERC4626 vault while the CDO's epoch state is mid-transition. The hook's solvency gate (`shortfall > _currentVaultAssets()` → return true and let `transferFrom` default) checks *economic* coverage via `convertToAssets`, but the subsequent `vault.withdraw` requires *redeemable liquidity* — a strictly stronger condition. Any unprivileged depositor of that ERC4626 vault can open that gap by redeeming the vault's liquid assets, forcing `StopEpochVaultLiquidityUnavailable` to revert and bubble out of `stopEpoch`, permanently (as long as liquidity stays scarce) blocking epoch settlement for all tranche holders. [1](#0-0) 

### Finding Description

`ProgrammableBorrower.onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:231-268) is called by `IdleCDOEpochVariant._stopEpoch` before funds are pulled (contracts/IdleCDOEpochVariant.sol:395-404):

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  // If the vault shares do not economically cover the shortfall, let IdleCDO's later
  // transferFrom fail and use the existing default path.
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The two release paths — "not covered economically" (return true → CDO `transferFrom` fails → `_handleBorrowerDefault`) and "covered but withdraw fails" (revert) — were combined under a single check that only validates the weaker condition. `_currentVaultAssets()` is `convertToAssets(shares)` (line 546-549): share *value*. A standard ERC4626 lending-style vault (Morpho, Euler, Aave-wrapped, etc.) can have shares worth more than its instantly withdrawable cash. `vault.withdraw` reverts whenever `shortfall > vault liquid assets`, even though `shortfall <= convertToAssets(shares)`.

In `IdleCDOEpochVariant._stopEpoch` the revert propagates uncaught — the `try/catch` only wraps `this.getFundsFromBorrower`, and the comment at line 397 explicitly states "Hook reverts bubble so transient ERC4626 liquidity failures can be retried" (contracts/IdleCDOEpochVariant.sol:396-404). So `stopEpoch` / `stopEpochWithDuration` revert entirely, every time the vault is illiquid.

### Impact Explanation

An unprivileged user of the programmable borrower's ERC4626 vault (an explicitly in-scope attacker) can:

1. Wait for an epoch to be running with `pendingWithdraws` and interest obligations requiring `shortfall > 0` at stop time (the common case — idle cash is parked in the vault precisely so `_amountRequired` exceeds `onHand`).
2. Redeem/withdraw the vault's available liquidity down to below the upcoming `shortfall` (or front-run the manager's `stopEpoch` call in the mempool with a redeem, since the required amount is computable from public state: `pendingWithdraws + expectedEpochInterest - onHand`).
3. Every `stopEpoch` call then reverts with `StopEpochVaultLiquidityUnavailable`. The epoch can never stop while the vault stays illiquid; the attacker can keep it illiquid for as long as they hold a large vault position or the underlying vault lent assets out.

Consequences while frozen:

- All `pendingWithdraws` receipts cannot be funded — `claimWithdrawRequest` stays reverted/insolvent for pending claimants.
- All tranche holders' deposits and accrued interest are locked: no `stopEpoch` → no new buffer period → `requestWithdraw` proceeds but claims never get funded, and `claimInstantWithdrawRequest` funding (`getInstantWithdrawFunds` → borrower pull) is equally blocked.
- `emergencyExitVault` does not help: `vault.redeem` hits the same liquidity wall (line 361-372).
- Because the revert happens *before* `_accrueManagementFee`/`expectedEpochInterest` are persisted for this attempt, the only recovery is `finalizeDefault`-style escalation, which forces a real borrower default and loss socialization (`_handleBorrowerDefault` path in `IdleCDOEpochVariant`) even though the borrower is solvent — i.e., the attacker can also manufacture a default declaration by keeping the vault illiquid until governance chooses to default.

Quantified loss: temporary freezing of 100% of pool TVL for the duration the attacker suppresses vault liquidity, plus potential forced-default socialization of the full epoch liability (`_amountToPullFromBorrower + _pendingWithdraws`).

### Likelihood Explanation

- Attacker requirement: any ERC4626 vault depositor — no KYC, no role, no IdleCDO interaction needed. The vault is shared external infrastructure; the borrower sleeve explicitly parks pool capital there alongside third-party depositors.
- Triggering liquidity scarcity costs the attacker only the opportunity cost of holding vault shares; a redeem transaction is atomic and can be timed against `epochEndDate` or the manager's `stopEpoch` transaction.
- The guards don't help: `_checkOnlyIdleCDO` restricts the caller, not the vault state; `shortfall > _currentVaultAssets()` precisely fails to check the actual revert condition (`vault` cash liquidity); no flag, pause, or skim path applies. The design even relies on "retryable" reverts, which is exactly what makes the freeze repeatable instead of one-shot.
- Caveat: this assumes the configured ERC4626 vault admits external depositors and can be liquidity-constrained (true of any lending-market vault; not true of a hypothetical always-liquid wrapper). This dependency on the deployment's vault choice is the main uncertainty.

### Recommendation

Split the two release conditions the way the kernel fix split the two puts — make the hook decide "covered vs not" using the same criterion the withdrawal actually needs:

- In `onStopEpoch`, gate on withdrawable liquidity rather than `convertToAssets`: use `vault.maxWithdraw(address(this))` (ERC4626 standard) as the coverage check, i.e., `if (shortfall > vault.maxWithdraw(address(this))) return true;` so a genuinely illiquid-but-solvent position falls into the deterministic default path instead of an unbounded revert loop. This mirrors the upstream fix: do the cheap `nfsd_serv_put` under the lock and move the heavyweight `fput` outside — here, do the coverage check with the same primitive the blocking call uses.
- Alternatively, catch the withdrawal failure and convert it to the default path (`return true` on `catch`, letting `transferFrom` fail deterministically) so a vault liquidity outage produces a bounded, well-defined outcome (default/recovery) rather than an indefinite freeze of every claim.
- As defense-in-depth, allow `emergencyExitVault`/manager to force the epoch into the default flow when `maxWithdraw` remains below the required shortfall, so settlement is never hostage to third-party vault liquidity.

### Proof of Concept

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {ProgrammableBorrower} from "../contracts/strategies/idle/ProgrammableBorrower.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

/// Minimal ERC4626-shaped vault that is solvent (convertToAssets covers
/// the borrower's shares) but whose *cash* can be drained by any depositor.
contract IlliquidVault {
    IERC20Detailed public asset;
    uint256 public totalShares;
    uint256 public totalManaged; // shares are backed 1:1 economically
    mapping(address => uint256) public balanceOf;
    uint256 public liquid;       // actually withdrawable now

    constructor(address _asset) { asset = IERC20Detailed(_asset); }

    function deposit(uint256 a, address to) external returns (uint256 s) {
        s = a; // 1:1
        asset.transferFrom(msg.sender, address(this), a);
        balanceOf[to] += s; totalShares += s; totalManaged += a; liquid += a;
    }
    // any depositor can pull cash below what ProgrammableBorrower will need
    function withdraw(uint256 a, address to, address owner) external returns (uint256 s) {
        require(a <= liquid, "insufficient vault liquidity"); // <- revert condition
        s = a;
        balanceOf[owner] -= s; totalShares -= s; liquid -= a;
        asset.transfer(to, a);
    }
    function convertToAssets(uint256 s) external view returns (uint256) { return s; }
}

contract StopEpochVaultLiquidityDoS is Test {
    // wiring: standard IdleCreditVault deployment with isProgrammableBorrower,
    // deposits made, epoch started, borrower drew funds, users queued withdraws.
    // ...

    function test_vaultDepositorBlocksStopEpoch() external {
        IlliquidVault v = IlliquidVault(address(pb.vault()));

        // 1) Attacker (unprivileged ERC4626 depositor) drains vault liquidity
        //    to just below the upcoming shortfall:
        //    shortfall = pendingWithdraws + expectedEpochInterest - pb.onHand
        uint256 shortfall = cdoEpoch.expectedEpochInterest()
                          + creditVault.pendingWithdraws()
                          - underlying.balanceOf(address(pb));
        vm.prank(vaultWhale); // attacker, only needs vault shares
        v.withdraw(v.liquid() - (shortfall - 1), vaultWhale, vaultWhale);

        // Invariant gap: economically covered (passes return-true gate) ...
        assertLe(shortfall, v.convertToAssets(v.balanceOf(address(pb))));
        // ... but not withdrawable.
        assertLt(v.liquid(), shortfall);

        // 2) Honest manager calls stopEpoch after epochEndDate -> always reverts.
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdoEpoch.stopEpoch(newApr, expectedInterest);

        // 3) Frozen while attacker keeps liquidity suppressed:
        //    - claimWithdrawRequest for pending receipts unfunded
        //    - no buffer period, no new epoch, getInstantWithdrawFunds unusable
        //    - emergencyExitVault also reverts on vault liquidity
        vm.prank(manager);
        vm.expectRevert(); // vault.redeem -> insufficient vault liquidity
        pb.emergencyExitVault(0);
    }
}
```

The PoC is reproducible on a Foundry fork/mock of the real configured ERC4626 vault: seed `ProgrammableBorrower` with shares, have an attacker redeem vault cash below `shortfall`, then show every `stopEpoch`/`stopEpochWithDuration` reverts and `emergencyExitVault` is equally blocked, demonstrating temporary freezing of the entire pool and the option to force a spurious borrower default.
