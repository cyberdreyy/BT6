### Title
Unbounded and Instant Validator Commission via `UpdateCommissionBps` (No Cap, No Delay) - (File: programs/vote/src/vote_state/mod.rs)

### Summary
The vote program's basis-points commission update path (`update_commission_bps`, backing `VoteInstruction::UpdateCommissionBps`) lets the vote account's authorized withdrawer set `inflation_rewards_commission_bps` or `block_revenue_commission_bps` to any `u16` value with no upper-bound validation and no timelock, unlike the legacy percentage-based `update_commission` path which at least enforces an epoch-half update rule. This mirrors the BribeVault `setFee` finding: an "admin" (the authorized withdrawer) can set a fee (commission) up to (and beyond) 100% instantly, retroactively affecting stakers/delegators who already delegated under a lower commission, with no time for them to react.

### Finding Description
`update_commission_bps` in [1](#0-0)  takes `commission_bps: u16` and writes it directly via `set_inflation_rewards_commission_bps`/`set_block_revenue_commission_bps` after only checking the `authorized_withdrawer` signature — there is no check that `commission_bps <= 10_000` (100% in basis points), and the code explicitly documents "No commission update rule, per SIMD-0249 and SIMD-0291" at line 844, meaning none of the epoch-timing restrictions that gate the legacy commission field apply here.

By contrast, the legacy `update_commission` at [2](#0-1)  enforces `is_commission_update_allowed(clock.slot, epoch_schedule)` whenever the new commission increases, blocking commission increases in the second half of an epoch. The basis-points path (added for SIMD-0291/SIMD-0123 "block revenue sharing" and SIMD-0249 "delay commission updates") removes even this weak protection, and adds no replacement upper-bound or timelock check.

The instruction is dispatched unconditionally once feature-gated in [3](#0-2) , gated only on `commission_rate_in_basis_points` and `delay_commission_updates` feature activation, `not` on any value sanity check.

### Impact Explanation
`commission_bps` is consumed by the epoch reward distribution logic (referenced pervasively in `runtime/src/inflation_rewards/mod.rs` and `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`) to split staking/block-revenue rewards between the validator and its delegators. Because the value is an unchecked `u16` (range 0–65535) rather than being clamped to `[0, 10_000]` basis points, a validator's withdraw authority can:
1. Set `commission_bps` above 10,000 (>100%), which — depending on how downstream arithmetic treats the value (e.g., `min(commission_bps, 10_000)` fallback vs. unchecked multiply/divide) — can either siphon more than the intended reward share from delegators or cause a panic/overflow in reward-splitting arithmetic during epoch boundary processing (a replay-path correctness/availability concern).
2. Instantly increase commission with no epoch-half restriction and no advance notice, retroactively degrading the yield of stakers who already delegated under a lower commission — the direct analog of the BribeVault admin "changing fees for already made deposits."

This is a validator/authorized-withdrawer-level privilege abuse against delegators, reachable by any ordinary user who has already staked to that vote account (the affected party) with no recourse, and the vulnerable state mutation occurs entirely inside the unprivileged vote program instruction path.

### Likelihood Explanation
Likelihood is high for the "no cap / no timelock" abuse against delegators, since it requires only the authorized withdrawer signing a normal transaction with `VoteInstruction::UpdateCommissionBps` — no special privilege beyond what is already granted to any vote account's withdraw authority, and it's the intended interface once the associated features (`commission_rate_in_basis_points`, `delay_commission_updates`, and `block_revenue_sharing` for the `BlockRevenue` kind) are active on the cluster.

### Recommendation
- Enforce `commission_bps <= 10_000` in `update_commission_bps` before calling `set_inflation_rewards_commission_bps`/`set_block_revenue_commission_bps`, returning `InstructionError::InvalidInstructionData` otherwise.
- Reintroduce a delay/epoch-boundary rule (as SIMD-0249's name "delay commission updates" implies) for basis-points commission increases so delegators have advance notice, consistent with the older `is_commission_update_allowed` check for legacy commission.
- Audit downstream reward-splitting code in `runtime/src/inflation_rewards/mod.rs` / `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` to confirm it does not assume `commission_bps <= 10_000`, and add defensive clamping/asserts to prevent arithmetic overflow or incorrect reward splits if an out-of-range value is ever stored on-chain (e.g., from before validation is added).

### Proof of Concept
1. Delegator stakes to vote account `V` when `V.block_revenue_commission_bps == 0`.
2. `V`'s authorized withdrawer submits a transaction with `vote_instruction::update_commission_bps(V, withdrawer, CommissionKind::BlockRevenue, 65535)` (or any value > 10,000).
3. `update_commission_bps` at [4](#0-3)  accepts the value unconditionally (only checking the withdrawer's signature) and stores it via `set_block_revenue_commission_bps`, with no epoch-timing restriction and no upper-bound check.
4. At the next epoch boundary reward distribution, the delegator's rewards are computed using the unbounded `commission_bps`, either fully expropriating rewards (commission effectively capped/misapplied at >100%) or, if downstream arithmetic is unchecked, causing incorrect distribution/panic — with no opportunity for the delegator to react before the change takes effect.

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
