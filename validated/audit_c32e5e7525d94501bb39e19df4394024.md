### Title
Stale confirmations from removed multisig members are not purged, allowing a pending request to execute below the configured confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` decides whether to execute a pending request purely by comparing the size of the `confirmations` set for that request against `num_confirmations` [1](#0-0) . When a member is removed via `DeleteMember`, `delete_member` only purges requests that member itself *created* (`r.member == member`), and only clears `num_requests_pk` for that member — it never scans the `confirmations` map to strip that member's approvals from requests *created by other members* [2](#0-1) . This breaks the intended binding: `confirmations counted == approvals from currently live members`.

### Finding Description
`confirm()` treats a request as authorized once `confirmations.len() + 1 >= num_confirmations` [3](#0-2) . The confirmations set is keyed only by request id and stores member identifiers (`member.to_string()`), with no re-validation that every entry still belongs to a current member of `self.members` at execution time.

`delete_member()` is the only place that prunes confirmation state for a removed member, and it does so incompletely:
```
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
self.num_requests_pk.remove(&member.to_string());
self.members.remove(&member);
```
`r.member` is the member who *originally added* the request, not everyone who has confirmed it [4](#0-3) . So if member `M` confirms (but did not create) request `R`, and `M` is later removed from the multisig, `R`'s confirmation set still contains `M`'s stale approval. `assert_valid_request`/`current_member` checks are only enforced for the caller of `add_request`/`confirm`/`delete_request`, not for the historical entries already stored in `confirmations` [5](#0-4) .

The equality that should hold is:
`confirmations.len() at execution == number of currently-live members who explicitly approved`

After a member is removed, this becomes:
`confirmations.len() at execution > number of currently-live members who explicitly approved`

allowing a request to reach `num_confirmations` using fewer than `num_confirmations` distinct, currently-trusted approvers.

The same structural flaw exists in the original `multisig/src/lib.rs`, where `DeleteKey` only removes requests whose `signer_pk` (creator) matches the deleted key, and likewise never purges that key's confirmations recorded on requests created by other keys [6](#0-5) .

### Impact Explanation
This is a Critical-severity binding break per the listed impact categories: "a multisig request executed below threshold." An attacker (or an account whose key/membership is being revoked for cause, e.g. suspected compromise) can leave a stale approval on a still-pending sensitive request (e.g. `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`). Even after the multisig legitimately votes to remove that member, the phantom confirmation still counts, letting the remaining honest members unknowingly finalize the request with fewer live approvals than the configured `num_confirmations` requires — moving NEAR or granting access with weaker authorization than the multisig's own threshold guarantees.

### Likelihood Explanation
This does not require any privileged deployment or foundation action beyond ordinary multisig operation: any legitimate multisig usage flow (member confirms a request, then is later removed for any reason — key rotation, suspected compromise, or normal membership churn) triggers it. No malicious code deployment or off-chain compromise is needed for the underlying flaw to exist; only ordinary request/confirm/delete-member sequencing is required to demonstrate it.

### Recommendation
When executing `DeleteMember` (and `DeleteKey` in `multisig/src/lib.rs`), iterate over **all** pending requests' `confirmations` sets (not just requests created by the removed member) and strip the removed member's entry from each; re-check whether removal drops a request below quorum). Alternatively, re-validate at execution time in `confirm()`/`execute_request()` that every entry in the `confirmations` set still corresponds to a member in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3` [7](#0-6) .
2. `A` calls `add_request_and_confirm` for a sensitive `Transfer`/`FunctionCall` request `R` — confirmations = `{A}` (1/3).
3. `B` calls `confirm(R)` — confirmations = `{A, B}` (2/3), not yet executed.
4. Members submit and confirm (3/3, using A, C, D) a `DeleteMember{B}` request; it executes and removes `B` from `self.members` via `delete_member` [2](#0-1) . Because `R` was created by `A`, not `B`, the loop over `self.requests` does not touch `R`, so `R`'s confirmation set `{A, B}` is left untouched.
5. `C` (a legitimate remaining member) calls `confirm(R)`. `confirmations.len() + 1 == 3 >= num_confirmations (3)`, so `R` executes [3](#0-2) , even though only `A` and `C` are currently-trusted members who approved it — one confirmation short of the intended 3-of-3 live-member threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
