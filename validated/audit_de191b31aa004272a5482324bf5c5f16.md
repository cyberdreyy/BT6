### Title
Re-activating `DefaultDistributor` mis-prices the redemption rate and permanently strands part of the default-recovery fund - (File: contracts/DefaultDistributor.sol)

### Summary
`DefaultDistributor.setIsActive(true)` computes the claim `rate` as `token.balanceOf(this) / trancheToken.totalSupply()`. Claims do not burn the tranche tokens — `claim()` only transfers them into the distributor (`contracts/DefaultDistributor.sol:38-40`). Because `totalSupply()` never decreases, toggling `isActive` off and back on after partial claims divides the *remaining* underlying over the *full* supply, including tranches that were already paid out and are now locked inside the distributor itself. Every subsequent claim is under-paid and the un-claimable remainder is stranded in the contract.

### Finding Description
- `claim()` pulls the caller's entire tranche balance and pays `trancheBal * rate / ONE_TRANCHE`, keeping the received tranche tokens in the contract rather than burning them (lines 35–41).
- `setIsActive(true)` recomputes `rate` from the current underlying balance divided by the still-unchanged `totalSupply` (lines 45–51).

Concrete sequence (mirrors `TokenLock.revoke()` stranding `releasableAmount + surplusAmount`):

1. Pool defaults; `DefaultDistributor` is funded with 100 underlying and tranche `totalSupply` is 100. Owner calls `setIsActive(true)` → `rate = 1.0`.
2. Alice claims her 50 tranches → receives 50 underlying. Distributor now holds 50 underlying + 50 (already-paid) tranche tokens.
3. Owner calls `setIsActive(false)` then `setIsActive(true)` (e.g., pausing claims while awaiting additional recovery, an action the contract explicitly supports).
4. `rate` is recomputed as `50 / 100 = 0.5`, because the 50 tranches escrowed in the distributor still count in `totalSupply`.
5. Bob claims his 50 tranches → receives only 25 underlying. The remaining 25 underlying can never be paid out: further re-activations only lower the rate, and no function distributes the residual. It is stranded (recoverable only via the owner-only `transferToken` escape hatch), i.e. permanently frozen for the claimants it was owed to.

### Impact Explanation
Portion of the default-recovery fund proportional to `claimedSupply / totalSupply` at re-activation is either under-paid to remaining claimants or permanently locked in the distributor. In the example, 25% of the fund is stranded after a single toggle. The invariant "one tranche, pro-rata recovery payout" is broken by an accounting denominator that ignores tokens already redeemed.

### Likelihood Explanation
Requires the honest owner to deactivate and reactivate claims — a plausible operational action (pausing claims pending a recovery top-up or a fix). No attacker privilege is needed; any tranche holder claiming after re-activation suffers the loss automatically. Conditional but non-malicious trigger, consistent with a medium-severity distribution bug.

### Recommendation
Either burn the tranche tokens received in `claim()` (so `totalSupply` reflects only unclaimed supply), or track the entitled amount explicitly, e.g. store `rate` once and make `setIsActive` only toggle the flag, or compute `rate = initialBalance * ONE_TRANCHE / initialSupply` at first activation and never recompute. Alternatively, forbid re-activation once claims have occurred (`require(tranche.balanceOf(address(this)) == 0)` inside `setIsActive(true)`).

### Proof of Concept
Foundry test against `DefaultDistributor` (mock ERC20s suffice):

```solidity
function testReactivationStrandsFunds() public {
    MockERC20 token = new MockERC20("UND", "UND");
    MockERC20 tranche = new MockERC20("TR", "TR");
    DefaultDistributor dist = new DefaultDistributor(address(token), address(tranche), owner);

    tranche.mint(alice, 50e18);
    tranche.mint(bob, 50e18);
    token.mint(address(dist), 100e6);

    vm.prank(owner); dist.setIsActive(true);           // rate = 1.0

    vm.startPrank(alice);
    tranche.approve(address(dist), 50e18);
    dist.claim(alice);                                 // alice: +50
    vm.stopPrank();

    vm.startPrank(owner);
    dist.setIsActive(false);
    dist.setIsActive(true);                            // rate = 50/100 = 0.5
    vm.stopPrank();

    vm.startPrank(bob);
    tranche.approve(address(dist), 50e18);
    dist.claim(bob);                                   // bob: +25, expected 50
    vm.stopPrank();

    assertEq(token.balanceOf(address(dist)), 25e6);    // stranded forever
    assertEq(token.balanceOf(bob), 25e6);
}
```

Note: I verified the rate/claim accounting directly in `contracts/DefaultDistributor.sol`; I did not trace every call site of `setIsActive` in `IdleCDOEpochVariant`, so the exact operational trigger (when the owner toggles claims) is inferred from the contract's exposed API rather than confirmed upstream usage.
