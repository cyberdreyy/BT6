### Title
Truncated `get_tenures_fork_info` list (DEPTH_LIMIT=10) lets `check_parent_tenure_choice` approve an illegal deep reorg - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` assumes `client.get_tenure_forking_info` returns every tenure strictly between `self.prior_sortition` and `self.parent_tenure_id`, using `tenure.consensus_hash == self.parent_tenure_id` as the loop's implicit stop condition. The node-side RPC handler backing this call silently truncates the walk after `DEPTH_LIMIT = 10` tenures without returning an error, so for any parent choice more than 10 tenures back the returned list never contains an entry equal to `self.parent_tenure_id`, and the tenures between depth 10 and the true parent are never evaluated at all.

### Finding Description
The claimed equality is: the set of tenures actually walked by `check_parent_tenure_choice`'s loop must equal exactly `{tenures strictly between prior_sortition and parent_tenure_id}`.

`stackslib/src/net/api/get_tenures_fork_info.rs` implements the RPC handler behind `client.get_tenure_forking_info`: [1](#0-0) [2](#0-1) 

The `while depth < DEPTH_LIMIT && cursor.consensus_hash != recurse_end` loop stops after 10 real sortitions even if `cursor.consensus_hash` (which should equal `recurse_end`, i.e. `parent_tenure_id`) was never reached, and returns `Ok(results)` with **no error** — the caller cannot distinguish a truncated, incomplete answer from a complete one.

On the signer side, `check_parent_tenure_choice` relies on this list reaching the parent tenure to know when to stop checking: [3](#0-2) 

If `parent_tenure_id` is more than 10 tenures behind `prior_sortition` on the actual canonical fork (a normal, easily reachable chain depth in live operation — no majority-signer or node-compromise assumption needed), the returned `tenures_reorged` list contains only the 10 nearest tenures to `prior_sortition`, none of which equals `parent_tenure_id`. The `continue` at line 205-208 therefore never fires, and — more importantly — every tenure beyond depth 10 (i.e., the tenures actually adjacent to the true, deep parent, which is exactly where a violating tenure with `globally_accepted_blocks > 1` would plausibly sit) is **never inspected** by the `globally_accepted_blocks > 1` rule at lines 210-223. If the 10 nearest tenures all happen to satisfy the rule (empty tenures, or single-block tenures, or late-timed proposals — all plausible on a live network), the loop falls through to `Ok(true)` at line 294, and the signer signs a tenure-change that reorgs away multiple already-globally-accepted blocks from tenures the check never looked at.

The attacker's action is simply choosing, in their own winning block-commit, a `parent_tenure_id` far enough back (>10 real tenures) on the canonical fork — something entirely within a single miner slot's control and requiring no coordination with other signers, no node compromise, and no protocol violation at the block-commit layer (the whole point of `check_parent_tenure_choice` is to police reorgs that the node's own commit-chaining rules do not forbid).

No existing guard catches this: `tenures_reorged.is_empty()` only guards the case where the RPC returns literally nothing; a non-empty but truncated list passes through silently, and there is no check anywhere that the last element of `tenures_reorged` actually equals `parent_tenure_id`.

### Impact Explanation
This breaks canonicity: a signer can be induced to sign a tenure-change block that discards tenures with more than one globally-accepted block — precisely the situation `check_parent_tenure_choice` exists to prevent — because the violating tenure lies beyond the RPC's undocumented 10-tenure horizon. This matches the Critical category (a signer signing an invalid/non-canonical/conflicting block, i.e., permitting an illegal reorg). The exploit is repeatable by any single winning miner slot against any chain state where 10+ tenures separate `prior_sortition` from the chosen ancient parent.

### Likelihood Explanation
Preconditions are modest: the current canonical fork must have at least 10 tenures between the tip and some earlier tenure that has more than one globally-accepted block (a very common state on a live network, not a contrived "malformed" fork). The attacker needs only to win one miner slot and craft a block-commit/tenure-change naming that old parent — a normal capability already assumed for this attacker class. No majority of signers, no auth_token, no local access, and no special RPC manipulation is required; the truncation is a deterministic property of the honest node's own RPC handler (`DEPTH_LIMIT = 10`), not something the attacker needs to forge.

### Recommendation
Make `get_tenures_fork_info`'s handler return an explicit error (or a truncation marker) when `depth` reaches `DEPTH_LIMIT` before `cursor.consensus_hash == recurse_end`, instead of silently returning a partial list. On the signer side, `check_parent_tenure_choice` should verify that the returned `tenures_reorged` list actually terminates at `self.parent_tenure_id` (e.g., check that the last entry's `consensus_hash == self.parent_tenure_id`, or that `parent_sortition_id`/height chains are contiguous) and treat a non-terminating/truncated response the same as `tenures_reorged.is_empty()` (reject the tenure choice, `Ok(false)`), or raise the depth limit / add pagination that the signer drives until it truly reaches the parent.

### Proof of Concept
Rust test plan (in `stacks-signer/src/chainstate/tests/v2.rs`, alongside `refused_reorg_supersedes_nothing`):
1. Build a mock `StacksClient`/mocked `get_tenure_forking_info` response that returns exactly `DEPTH_LIMIT` (10) `TenureForkingInfo` entries walking back from `prior_sortition`, none of which has `consensus_hash == parent_tenure_id` (simulating the real RPC's silent truncation).
2. Seed `SignerDb` so that a tenure entry *beyond* the returned 10 (i.e., one that would exist between the 10th returned entry and the true `parent_tenure_id`) has `get_globally_accepted_block_count_in_tenure(...) > 1` — this tenure is never in the returned list.
3. Ensure the 10 returned entries all pass the rule (e.g., `first_block_mined: None` or `globally_accepted_blocks <= 1`).
4. Call `check_parent_tenure_choice` and assert it currently returns `Ok(true)` — i.e., it approves the reorg even though a real violating tenure exists beyond the truncation boundary, demonstrating the missed-tenure direction of the broken equality.
5. As the fix-validation counterpart, assert that after adding a "list must terminate at `parent_tenure_id`" check, the same setup returns `Ok(false)`.
