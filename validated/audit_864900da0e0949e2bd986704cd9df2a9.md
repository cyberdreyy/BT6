### Title
EI-authenticated requests are treated as `isUser` in `PipelineRunsController.Create`, allowing integer-ID job runs despite the "EIs not allowed" comment - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` sets the same `SessionUserKey` context value used for genuine session/token users, populating it with a synthetic `User{Role: UserRoleRun}`. Both `RequiresRunRole` and `PipelineRunsController.Create`'s `isUser` check rely solely on `auth.GetAuthenticatedUser`, which cannot distinguish this synthetic EI user from a real run-role user, so an EI credential satisfies `isUser` and reaches `prc.App.RunJobV2(ctx, jobID, nil)` for any parseable int32 job ID.

### Finding Description
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` authenticates the EI access key/secret and then does: [1](#0-0) 
This sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` — the exact same context key (`SessionUserKey`) that `AuthenticateBySession`/`AuthenticateByToken` use for real user sessions: [2](#0-1) [3](#0-2) 

`RequiresRunRole` (the wrapper applied to `prc.Create`) only checks `GetAuthenticatedUser` and rejects `UserRoleView`: [4](#0-3) 
Since the EI synthetic user has `Role: UserRoleRun` (not `View`), it passes this wrapper unimpeded.

Inside `Create`, the code comment explicitly states the intent that only real users (not EIs) should be able to run int-ID jobs, but the check is: [5](#0-4) 
`isUser` is set from `auth.GetAuthenticatedUser(c)`, which returns `true` for the EI synthetic user because it's stored under the same `SessionUserKey`. There is no check of `auth.GetAuthenticatedExternalInitiator(c)` to exclude EI-originated requests, and no distinction between a "real" user object and the synthetic one injected for EIs. As a result, any int32 job ID parses successfully and `prc.App.RunJobV2(ctx, jobID, nil)` is invoked directly, bypassing the webhook/job-UUID binding model that EIs are supposed to be restricted to.

### Impact Explanation
An external-initiator credential (which is meant to be scoped to triggering webhook-bound job runs via job UUID) can instead trigger arbitrary job runs on any job by integer ID — including OCR or other non-webhook job types unrelated to that initiator — via `RunJobV2`. This is an authorization bypass allowing an EI credential holder to perform actions (arbitrary job execution) beyond its intended scope, matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
The precondition is only a valid EI access key/secret (no session cookie or user API token needed) — a credential class explicitly listed as an allowed attacker profile. The exploit is a single unauthenticated-relative-to-users HTTP POST to `/v2/jobs/<int32-id>/runs` with the EI headers set, and is deterministic/repeatable since the code path is unconditional on any additional runtime configuration.

### Recommendation
In `PipelineRunsController.Create`, explicitly exclude external-initiator-authenticated requests from the `isUser` branch, e.g. check `auth.GetAuthenticatedExternalInitiator(c)` and reject if present, or have `AuthenticateExternalInitiator` store EI identity under a distinct context type/key that is not accepted by the `isUser` branch (while still satisfying `RequiresRunRole`'s role check via a separate mechanism).

### Proof of Concept
Go handler-level integration test (extends existing `core/web/pipeline_runs_controller_test.go` patterns):
1. Set up an app with `build.IsProd()==false`, create an External Initiator credential, and create an OCR (non-webhook) job with a known int32 `ID`.
2. `POST /v2/jobs/<int32-ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI credential, and no session cookie or `X-API-KEY`/`X-API-SECRET`.
3. Assert current (vulnerable) behavior: response is `201 Created` with a pipeline run resource, and `prc.App.RunJobV2` was invoked — demonstrating the "EIs not allowed" comment is not enforced.
4. Expected/fixed behavior: response should be `422`/`401`/`403` and `RunJobV2` should not be called for EI-authenticated requests on int-ID jobs.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
