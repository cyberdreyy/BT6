### Title
Single-step `changeAdmin` can permanently transfer or brick control of the KYC whitelist - (File: contracts/KeyringIdleWhitelist.sol)

### Summary
`KeyringIdleWhitelist` controls which lenders bypass or satisfy Keyring credential checks via `isWalletAllowed`/`checkCredential` gating in the credit-vault deposit path. Its `changeAdmin` updates `admin` in a single transaction with no pending-admin/accept step and no zero-address check. A single mistyped or compromised-calldata `newAdmin` either hands whitelist control to an arbitrary unprivileged address or permanently bricks admin functions. The same one-shot pattern exists for critical roles in `IdleCreditVault`/`ProgrammableBorrower` (multiple `manager`/`guardian`/`borrower`/`feeReceiver` assignments), but `KeyringIdleWhitelist.changeAdmin` is the cleanest in-scope analog.

### Finding Description
In `contracts/KeyringIdleWhitelist.sol:87-94`:

```solidity
function changeAdmin(address newAdmin) external {
    if (msg.sender != admin) {
        revert NotAdmin(msg.sender);
    }
    address oldAdmin = admin;
    admin = newAdmin;
    emit AdminChange(oldAdmin, newAdmin);
}
```

The admin is the sole authority over `setWhitelistStatus` (lines 102-112), which decides which entities can bypass `Keyring(keyring).checkCredential(policyId, entity)` in `checkCredential` (lines 78-80). There is:
- No two-step propose/accept flow (no `pendingAdmin`, no `acceptAdmin`).
- No `newAdmin != address(0)` check (unlike OpenZeppelin `transferOwnership`, which at least blocks zero).

A fat-fingered `newAdmin` (typo, copied wrong address, or an address the protocol does not control) is irreversible: the previous admin immediately loses all power because authorization is checked against `admin` itself.

### Impact Explanation
- If `newAdmin` resolves to an unprivileged attacker-controlled EOA (e.g., attacker front-runs a known-fat-finger pattern, or the typo collides with an active address), the attacker gains whitelist control: they can whitelist themselves and any accomplice to bypass Keyring KYC gating for lender onboarding, and de-whitelist honest KYC'd lenders, breaking the access invariant that only credentialed/whitelisted entities may lend.
- If `newAdmin` is a dead/zero address, `setWhitelistStatus` is permanently bricked: no entity can ever be added or removed. Lenders awaiting whitelisting are permanently blocked from depositing (freezing of protocol intake), and an entity that must be de-whitelisted (compromised lender, revoked KYC) can never be removed — the whitelist state is frozen for the contract's lifetime.

### Likelihood Explanation
Requires a human/admin error on a rarely-called function — the classic medium-severity profile for this bug class (matching the Sherlock finding's own Medium rating). The privileged roles are honest, so this is not exploitable at will by the unprivileged attacker; the loss is contingent on the misconfiguration event, which is exactly what two-step ownership patterns exist to prevent.

### Recommendation
Implement a two-step admin transfer:

```solidity
address public pendingAdmin;

function changeAdmin(address newAdmin) external {
    if (msg.sender != admin) revert NotAdmin(msg.sender);
    if (newAdmin == address(0)) revert ZeroAddress();
    pendingAdmin = newAdmin;
    emit AdminChangeProposed(admin, newAdmin);
}

function acceptAdmin() external {
    if (msg.sender != pendingAdmin) revert NotAdmin(msg.sender);
    emit AdminChange(admin, pendingAdmin);
    admin = pendingAdmin;
    delete pendingAdmin;
}
```

Apply the same propose/accept pattern to other critical single-step role setters in `IdleCreditVault`/`ProgrammableBorrower` (manager, guardian, borrower, feeReceiver).

### Proof of Concept
Foundry test sketch (drop into `test/foundry/`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {KeyringIdleWhitelist} from "../../contracts/KeyringIdleWhitelist.sol";

contract ChangeAdminBug is Test {
    KeyringIdleWhitelist wl;
    address admin = address(0xA);
    address attacker = address(0xBAD);

    function setUp() public {
        wl = new KeyringIdleWhitelist(address(0x1), admin);
    }

    function test_TypoHandsControlToAttacker() public {
        // admin fat-fingers newAdmin -> attacker address
        vm.prank(admin);
        wl.changeAdmin(attacker);

        // attacker now controls the KYC whitelist
        vm.prank(attacker);
        wl.setWhitelistStatus(attacker, true);
        assertTrue(wl.whitelist(attacker));

        // attacker de-whitelists an honest lender; old admin is powerless
        vm.prank(attacker);
        wl.setWhitelistStatus(address(0xCAFE), false);
        vm.prank(admin);
        vm.expectRevert();
        wl.setWhitelistStatus(address(0xCAFE), true);
    }

    function test_ZeroAddressPermanentlyBricksWhitelist() public {
        vm.prank(admin);
        wl.changeAdmin(address(0)); // no zero-check

        vm.prank(admin);
        vm.expectRevert();
        wl.setWhitelistStatus(address(0xCAFE), true); // management frozen forever
    }
}
```

Both scenarios are irreversible because no recovery or accept step exists.
