### Title
Debug/pprof endpoints wired near `graphqlHandler` lack role checks, exposing memory/goroutine/cmdline data to any authenticated (view-role) or, for LOOP-plugin routes, fully unauthenticated client - ([File: core/web/router.go])

### Finding Description
`NewRouter` wires `graphqlHandler` alongside several debug-oriented route groups on the same node API listener (default `:6688`): `debugRoutes`, `metricRoutes` (Go `net/http/pprof`), and `loopRoutes` (LOOP plugin metrics/pprof). [1](#0-0) 

Two distinct authorization gaps exist:

1. **`metricRoutes` (pprof) mounted under `authv2` with no role wrapper.** Inside `v2Routes`, almost every sensitive handler is wrapped with `auth.RequiresEditRole`/`auth.RequiresRunRole`/`auth.RequiresAdminRole`, but `metricRoutes(authv2)` is called bare — it only inherits the group's base `auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)` middleware, which accepts **any** valid role including `UserRoleView`, the lowest privilege level. [2](#0-1) [3](#0-2) [4](#0-3) 
This exposes `/v2/debug/pprof/cmdline`, `/heap`, `/goroutine`, `/profile`, `/trace`, `/allocs`, `/block`, `/mutex`, `/threadcreate` to any user who can authenticate with a low-privilege ("view") session — confirmed by `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` explicitly checking `user.Role` in `core/web/auth/auth.go`, none of which is applied to `metricRoutes`. [5](#0-4) 

2. **`debugRoutes` (`/debug/vars`, Go `expvar`) mounted with authentication only, no role check.** Same pattern: any authenticated session (including `view` role) can dump process vars. [6](#0-5) 

3. **`loopRoutes` registered on the base `api` group with no authentication middleware at all.** `NewRouter` calls `loopRoutes(app, api)` directly on the shared `api` group (which only carries rate-limiting/session middleware, not `auth.Authenticate`), and `loopRoutes` itself adds no auth wrapper before registering `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol`. [7](#0-6) [8](#0-7) 
This means an **unauthenticated** HTTP client reaching the node API port can hit `pluginPPROFHandler`/`pluginMetricHandler` directly, retrieving pprof cmdline/heap/goroutine data for LOOP plugin processes without any credential.

Together these confirm the audited invariant is violated: debug endpoints do not require the highest role, and the LOOP plugin debug endpoints are reachable with zero authentication.

### Impact Explanation
- pprof `cmdline` can leak process command-line arguments, which in some deployments include secrets/flags (matching the "key passwords" impact class cited in the question).
- pprof `heap`/`goroutine`/`profile`/`trace` dumps can leak in-memory secrets (private keys, tokens, session data) since Chainlink holds keystore material and passwords in process memory during normal operation.
- `/debug/vars` (`expvar`) exposes internal runtime counters/build info to low-privilege sessions.
- The unauthenticated LOOP-plugin pprof/metrics routes are the most severe: zero credential needed to pull pprof dumps from the LOOP plugin subprocess.

This matches Chainlink's "server credential/key theft" bounty class: node secrets/memory retrievable from a running node by an attacker who should not have that level of access.

### Likelihood Explanation
- For `metricRoutes`/`debugRoutes`: an attacker only needs the lowest-privilege "view" role (e.g., a read-only operator credential, or any account they can create/be granted, or a stolen low-priv session cookie) — no admin/edit/run role is required. This is fully reproducible: any `view`-role session hitting `/v2/debug/pprof/heap` succeeds where it should be `403 Forbidden`.
- For `loopRoutes`: no credential at all is needed, only network reachability to the node API listener, making this trivially and universally exploitable wherever LOOP plugins are deployed.

### Recommendation
- Wrap `metricRoutes(authv2)` calls with `auth.RequiresAdminRole` for each pprof sub-route (or gate the whole `pprofGroup` with an admin-role middleware) in `core/web/router.go`.
- Wrap `debugRoutes`'s `/debug/vars` handler with `auth.RequiresAdminRole` as well.
- Require authentication (and admin role) on `loopRoutes` by moving its registration under `authv2` (or adding `auth.Authenticate(...)` + `auth.RequiresAdminRole` explicitly) instead of the unauthenticated `api` group.

### Proof of Concept
Add handler-level integration tests in `core/web` (pattern similar to existing router tests):
1. Create a test app with users of role `view`, `edit`, `run`, `admin`.
2. For each debug path (`/v2/debug/pprof/heap`, `/v2/debug/pprof/cmdline`, `/v2/debug/pprof/goroutine`, `/debug/vars`), issue authenticated requests as `view` role and assert current behavior returns `200 OK` (proving the bug) instead of the expected `403 Forbidden`.
3. For LOOP plugin routes (`/plugins/:name/metrics`, `/plugins/:name/debug/pprof/heap`), issue a request with **no** session cookie/token at all and assert current behavior returns `200 OK` instead of `401 Unauthorized`.
4. After applying the fix (adding `auth.RequiresAdminRole` wrappers / authentication to `loopRoutes`), re-run the same table test and assert `view`/anonymous requests now receive `401`/`403`, while `admin`-role requests still receive `200`.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
