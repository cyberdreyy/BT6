### Title
Builder pending withdrawal committed as `withdrawal.amount` (uncapped) while the actual balance deduction is capped at `min(amount, balance)` — (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` emits a `Withdrawal` whose `amount` field is the raw, uncapped `withdrawal.amount` requested by the pending builder withdrawal, but the actual state mutation performed later in `apply_withdrawals` caps the deduction to `min(withdrawal.amount, builder_balance)`. This mirrors the Canto `CNote.repayBorrowFresh` bug: the amount the payer (here, the execution layer / EL minting logic) is told to pay out (`Withdrawal.amount`, which the EL must credit in full to `withdrawal.address` per the payload commitment) differs from the amount actually subtracted from the source of funds (the builder's on-chain balance).

### Finding Description
`get_builder_withdrawals` in `specs/gloas/beacon-chain.md` builds the withdrawal record straight from the pending request without capping to the builder's balance: [1](#0-0) 

That withdrawal is included in `state.payload_expected_withdrawals`, which the execution layer is contractually bound to honor by crediting `withdrawal.amount` of ETH to `withdrawal.address` (this is the entire point of the withdrawals mechanism — the EL must mint exactly what the CL commits to). Meanwhile `apply_withdrawals` performs the actual CL-side balance deduction, capping it to the builder's real balance: [2](#0-1) 

So if `withdrawal.amount > builder.balance`, the CL only debits `builder.balance` (down to zero) from `state.builders[builder_index].balance`, but the committed `Withdrawal.amount` (the full, uncapped request) is what the execution layer will actually credit to `fee_recipient`. This breaks the equality "Gwei debited from source == Gwei credited to recipient": more ETH is minted/credited on the EL side than was ever removed from the builder's CL balance.

The test suite explicitly documents and accepts this as intended behavior rather than a bug fix, describing the withdrawal amount as "requested amount" even under insufficient balance: [3](#0-2) [4](#0-3) 

The design doc for this feature area even states the mismatch as a known input-space fact ("Actual = `min(amount, builder.balance)`") without capping the committed withdrawal amount to match: [5](#0-4) 

By contrast, the analogous `get_pending_partial_withdrawals` for regular validators correctly caps the *committed* withdrawal amount itself to what the state can actually support (`min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)`), keeping the committed amount and the deducted amount in agreement: [6](#0-5) 

### Impact Explanation
This is a genuine "Gwei created" style break: the EL must credit `withdrawal.amount` of ETH per the payload commitment (this is fundamental to the withdrawals mechanism — the payload's withdrawals list *is* the specification of what value is created for recipients), while the CL only ever removes `min(withdrawal.amount, builder.balance)` from `state.builders[...].balance`. Any shortfall (`withdrawal.amount - builder.balance`) is ETH paid to `fee_recipient` on the EL side with no corresponding debit anywhere in the CL state — a net supply inflation, matching the "Gwei created ... paid to a non-owner" critical impact category. This requires no malicious peer or coalition: it fires whenever a builder's `builder_pending_withdrawals` entry requests more than the builder's current balance (e.g., because the balance was reduced by an intervening slashing, exit, or another withdrawal between the time the pending withdrawal was queued and when it is processed).

### Likelihood Explanation
Builder balances can change between when a `BuilderPendingWithdrawal` is queued (e.g., via `settle_builder_payment`) and when it is processed in a later slot's `get_builder_withdrawals` sweep — for instance further builder exits, slashings, or other pending withdrawals draining the same builder's balance first within the same `get_expected_withdrawals` call, or across blocks. `state.builder_pending_withdrawals` amounts are also set once at settlement time and not re-validated against the live balance before the `Withdrawal` object is emitted, so any reduction in builder balance before processing directly produces an uncapped commitment.

### Recommendation
Cap the committed `Withdrawal.amount` in `get_builder_withdrawals` to the builder's actual available balance at the time the withdrawal record is built (mirroring the pattern used in `get_pending_partial_withdrawals`), e.g.:
```python
amount = min(withdrawal.amount, state.builders[builder_index].balance)
```
and use that capped `amount` both in the emitted `Withdrawal` and inside `apply_withdrawals`, so the ETH committed to the execution layer always equals the ETH actually removed from `state.builders[...].balance`.

### Proof of Concept
1. `state.builders[B].balance = 1 ETH`.
2. `state.builder_pending_withdrawals` contains an entry for builder `B` with `amount = 5 ETH` (queued earlier when balance was higher, or accepted without an amount-vs-balance check at settlement time — see `settle_builder_payment` / the "older than previous epoch" append path at `specs/gloas/beacon-chain.md` lines 1761-1770 which appends `parent_bid.value` directly with no balance check).
3. `get_builder_withdrawals` emits `Withdrawal(amount=5 ETH, address=fee_recipient)` — [7](#0-6) .
4. `apply_withdrawals` deducts only `min(5 ETH, 1 ETH) = 1 ETH` from `state.builders[B].balance`, leaving it at 0 — [8](#0-7) .
5. The execution layer, following the committed payload, credits `fee_recipient` with the full 5 ETH per the `Withdrawal` record, while only 1 ETH was ever removed from CL state — a 4 ETH unbacked mint, confirmed as expected test behavior in `test_builder_withdrawal_insufficient_balance` (`withdrawal.amount: 5 ETH (requested amount)`, `builders[0].balance: 0`) — [9](#0-8) .
