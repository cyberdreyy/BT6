### Title
Unprotected job can spoof the `-protected` cache volume namespace by crafting a cache key, defeating protected/unprotected cache isolation - ([File: executors/docker/internal/volumes/manager.go], [File: executors/docker/volume.go])

### Summary
`createVolumesManager` in `executors/docker/volume.go` sets `ManagerConfig.Protected = e.Build.IsProtected() || protectedKeyIdx >= 0`, where `protectedKeyIdx` is derived from user-controlled cache key strings. [1](#0-0)  Because cache volume names are computed purely from the project's `UniqueName` + a hash of the destination path plus this single boolean suffix (not from the specific cache key text), an attacker running an *unprotected* pipeline can force `Protected=true` by defining a cache entry whose (fully variable-expandable) key ends in `-protected`, causing their cache volume to collide in name with the volume that protected-ref jobs on the same project use.

### Finding Description
`Cache.Key` is a job-controlled, `inputs:"expand"` field fully controllable by the pipeline author (any `.gitlab-ci.yml` `cache: key:` value, including variables expanded at job time). [2](#0-1) 

`createVolumesManager` scans **all** cache entries of the job and sets the manager-wide `Protected` flag to true if *any* key ends in `-protected` (and not `-non_protected`) — regardless of whether the ref is actually protected: [3](#0-2) 

This flag is consumed in `manager.withProtected`, which appends the literal suffix `-protected` to the computed volume name whenever `m.config.Protected` is true: [4](#0-3) 

The actual volume name in `createCacheVolume` is built from `m.config.UniqueName` (project-scoped, not ref-scoped) plus a hash of the destination path, with the protected suffix appended: [5](#0-4) 

Since `UniqueName` (`e.Build.ProjectRealUniqueName()`) and the destination hash are the same for every job in the same project regardless of which ref triggered it, the only differentiator between a "protected-ref cache" and an "unprotected-ref cache" for the same cache path is this single suffix. An unprivileged contributor triggering an unprotected pipeline (e.g., an MR from a fork, or any job on a non-protected branch) can add an extra `cache:` entry (or rename an existing one) with a key ending in `-protected` to flip their own job's `Protected` flag to `true`. Their reusable cache volume then gets created/reused under the exact same name that protected-branch jobs use for the same cache path, allowing the attacker's job to read and write into what is supposed to be the isolated "protected" cache namespace.

This directly undermines the protection mechanism described in the code's own comments (work item 494478), whose stated purpose is to prevent an unprotected/fork job from sharing (and poisoning) the cache volume used by protected-branch pipelines. The existing check (`e.Build.IsProtected() || protectedKeyIdx >= 0`) is an OR, so it can only ever escalate an unprotected job into the protected namespace — it has no gate preventing an unprotected job from opting itself into that namespace.

### Impact Explanation
An unprivileged pipeline author (e.g., submitting an MR from a fork, whose pipeline runs unprotected) can deliberately populate the protected-ref cache volume for a project/path with attacker-controlled contents. When a maintainer later runs a protected pipeline (e.g., on `main` or a protected tag) that reuses the same cache path, it will pull in the attacker-poisoned cache — a build/cache poisoning vector against protected branches, which is exactly the class of attack the `-protected` suffix mechanism was introduced to prevent.

### Likelihood Explanation
- Preconditions: attacker only needs pipeline authoring rights sufficient to add/modify a `cache: key:` field (trivial for any contributor with an MR, including forks in `.gitlab-ci.yml` if the project runs pipelines for external MRs).
- No special runner or docker privileges are required; this leverages ordinary Docker executor cache-volume handling.
- Fully repeatable and deterministic given the same project cache destination path.

### Recommendation
Do not let the *value* of a cache key control whether a build's cache is treated as protected. Base the protected-namespace decision solely on `e.Build.IsProtected()` (the actual authoritative ref-protection state provided by GitLab), and remove (or restrict to trusted/internal use) the `protectedKeyIdx` heuristic that trusts user-supplied cache key text. If the intent is to let job authors *opt out* of a protected cache when the ref actually is protected, that should be a separate, narrowly-scoped mechanism that cannot be used by unprotected jobs to opt *into* the protected namespace.

### Proof of Concept
Add a table-driven Go test around `createVolumesManager` covering:
1. Build with `GitInfo.Protected = false` and `Cache = [{Key: "mykey-protected"}]`.
2. Assert `config.Protected == true` results from `createVolumesManager`.
3. Follow with a unit test on `manager.createCacheVolume`/`withProtected` showing that the resulting volume name equals the volume name computed for a second build on the same project with `GitInfo.Protected = true` and an ordinary cache key (i.e., same `UniqueName` + same destination hash + same `-protected` suffix) — demonstrating the name collision that allows cross-namespace cache read/write.

```go
var createVolumesManager = func(e *executor) (volumes.Manager, error) {
	// Note if any of the cache keys includes the `-protected` suffix (but not the `-non_protected` suffix).
	// See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
	protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
		return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
	})

	config := volumes.ManagerConfig{
		CacheDir:      e.Config.Docker.CacheDir,
		BasePath:      e.Build.FullProjectDir(),
		UniqueName:    e.Build.ProjectRealUniqueName(),
		TemporaryName: e.getProjectUniqRandomizedName(),
		DisableCache:  e.Config.Docker.DisableCache,
		Driver:        e.Config.Docker.VolumeDriver,
		DriverOpts:    e.Config.Docker.VolumeDriverOps,
		// the volume should be protected if the ref is protected OR if any of the cache volumes have the protected
		// suffix. See https://gitlab.com/gitlab-org/gitlab/-/work_items/494478.
		Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,
	}
```
