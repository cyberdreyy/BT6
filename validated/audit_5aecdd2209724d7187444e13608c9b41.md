The external report describes a pattern specific to a perpetuals/margin-style protocol: a `GlobalCollateralConfiguration.checkWithdrawLimits` global-percentage withdrawal rate limiter inside `AccountCollateral::updateBalance`, which incidentally applies to protocol-initiated fee debits in `MatchOrderModule::executeMatchOrder`, causing legitimate operations to revert when unrelated user withdrawals have consumed the shared quota.

None of these constructs (`MatchOrderModule`, `AccountCollateral`, `GlobalCollateralConfiguration`, `checkWithdrawLimits`) exist anywhere in this repository.

The closest conceptual mechanism in Aera's actual code is the sync-redeem epoch cap in `ProvisionerV2`, tracked via `_syncRedeemEpochRedeemedNumeraire` and enforced by `_requireEpochCapNotExceeded` inside `_syncRedeem` [1](#0-0) . However, this differs from the reported root cause in the key way that matters:

- The epoch cap is a deliberate, user-facing rate limiter applied only to voluntary `redeem`/`withdraw` calls [2](#0-1) .
- Protocol-initiated debits — e.g., deposit/redeem cancellation fees burned in `cancelRequest` — go through a direct `IMultiDepositorVault.exit()` call that bypasses `_syncRedeem` and its epoch-cap check entirely [3](#0-2) .
- Async solve paths (`_solveDepositVaultAutoPrice`, `_solveDepositVaultFixedPrice`, etc.) that hit the deposit cap use non-reverting guard helpers (`_guardDepositCapExceeded`) that emit an event and skip the individual request rather than reverting the whole batch [4](#0-3) .

So there is no coupling in Aera's code where a fee/protocol-initiated debit shares a global limit counter with ordinary user withdrawals in a way that would cause unrelated, ordinary-user transactions to revert. This is a genuinely distinct root cause not present as an analog in this codebase.

    /// @param epochRedeemNumeraire The pre-computed numeraire value of this redeem for epoch cap accounting
    /// @param epochCapNumeraire The effective epoch cap in numeraire
    /// @param epochRedeemedNumeraire The numeraire already redeemed in the current epoch (cached from _rollEpochIfNeeded)
    function _requireEpochCapNotExceeded(
        uint256 epochRedeemNumeraire,
        uint256 epochCapNumeraire,
        uint256 epochRedeemedNumeraire

        epochRedeemedNumeraire += epochRedeemNumeraire;
