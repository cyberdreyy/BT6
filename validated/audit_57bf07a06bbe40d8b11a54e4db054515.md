### Title
Account-subscription notification suppression on fork switch due to comparing only slot numbers, not fork/bank identity - (File: `rpc/src/rpc_subscriptions.rs`)

### Summary
The Sherlock report describes a bug where a lifecycle-tracking check (`_killWoundedAgents`) compares only a status enum, without verifying *when*/in which cycle that status was set, so a later state transition through the same status value is misinterpreted as the earlier one. The closest reachable analog in Agave's unprivileged JSON-RPC pubsub path is `filter_account_result` in `rpc/src/rpc_subscriptions.rs`, which decides whether to notify an `accountSubscribe` client purely by comparing the numeric slot at which the account was last modified against the numeric slot it last notified — without distinguishing which bank/fork instance produced that slot number.

### Finding Description
`check_commitment_and_notify` calls `filter_account_result` to decide whether an account update should be pushed to a subscriber: [1](#0-0) 

The comparison is `last_modified_slot != last_notified_slot`; if the two slot numbers are equal, no notification is emitted, and the stored `last_notified_slot` (in the subscription's shared state) is left unchanged: [2](#0-1) 

The comment in `filter_account_result` acknowledges that a `last_modified_slot < last_notified_slot` case can occur "because we last notified for a fork," but the code only special-cases the "less than" direction (implicitly, by always notifying when slots differ) — it does not verify that an *equal* slot number corresponds to the *same* bank instance. Agave's replay pipeline can produce multiple competing banks sharing the same slot number (sibling forks before one is chosen), each with potentially different account state. `Bank::get_account_modified_slot` (referenced from `rpc/src/rpc_subscriptions.rs` line 957) returns only the numeric slot the account was last written in, not a bank id or hash, so the equality check used for suppression cannot distinguish "the account was truly not touched since last notification" from "the account was touched again, coincidentally at the same slot number, but on a different fork with different content." This mirrors the report's root cause: a `status`/state check performed without confirming *which* instance (round/fork) produced it.

### Impact Explanation
If a validator's replay stage switches from one fork to a sibling fork that shares a slot number where the subscribed account was also modified, an `accountSubscribe`/`programSubscribe` client can silently miss an account-state change, continuing to hold or act on stale/incorrect account data returned earlier for the abandoned fork. This falls under "wrong-slot/fork/account data returned" from a read-only, unprivileged JSON-RPC pubsub subscription — no special privileges are required, only a live account subscription during a fork switch.

### Likelihood Explanation
This requires a genuine chain-fork/reorg event that revisits the same slot number with a modification to the exact subscribed account, which is not attacker-controlled directly and depends on network/leader-schedule conditions; it is a latent correctness bug rather than a directly triggerable single-RPC-call exploit. It is plausible but not trivially reproducible on demand by an unprivileged caller.

### Recommendation
Track fork identity (e.g., bank id/hash) alongside `last_notified_slot` in the account/program subscription state, and only suppress notification when both the slot and the originating bank instance are unchanged; alternatively, always re-notify when a fork switch is detected for the subscribed slot.

### Proof of Concept
Not independently reproduced; based on static analysis of `filter_account_result` and `check_commitment_and_notify` control flow described above. Confirming exploitability would require constructing a controlled fork scenario in a test harness (e.g., extending `rpc/src/rpc_subscriptions.rs` test module) where two sibling banks at the same slot both modify the subscribed pubkey, and observing that the subscriber's second update is dropped due to the slot-equality short-circuit.

fn filter_account_result(
    result: Option<(AccountSharedData, Slot)>,
    params: &AccountSubscriptionParams,
    last_notified_slot: Slot,
    bank: Arc<Bank>,
) -> (Option<UiAccount>, Slot) {
    // If the account is not found, `last_modified_slot` will default to zero and
    // we will notify clients that the account no longer exists if we haven't already
    let (account, last_modified_slot) = result.unwrap_or_default();

    // If last_modified_slot < last_notified_slot this means that we last notified for a fork
    // and should notify that the account state has been reverted.
    let account = (last_modified_slot != last_notified_slot).then(|| {
        if is_known_spl_token_id(account.owner())
            && params.encoding == UiAccountEncoding::JsonParsed
        {
            get_parsed_token_account(&bank, &params.pubkey, account, None)
        } else {
            encode_ui_account(&params.pubkey, &account, params.encoding, None, None)
        }
    });
    (account, last_modified_slot)
}
