### Title
Unchecked side effects of `mark_locally_accepted`/`mark_pre_committed` corrupt `BlockInfo.valid`/`signed_self` on a terminal `GloballyRejected` block, causing a stray signature broadcast - (File: `stacks-signer/src/signerdb.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
`BlockInfo::mark_pre_committed` and `BlockInfo::mark_locally_accepted` mutate persistent fields (`valid`, `approved_time`, `signed_self`) *before* calling the fallible `move_to()` state-transition check, and return the `move_to()` `Result` to the caller without rolling back those mutations on failure. Callers in `stacks-signer/src/v0/signer.rs` (`handle_block_validate_ok`, `handle_block_pre_commit`) inspect the `Err` but their guard conditions (`has_reached_consensus()`) treat `GloballyAccepted` and `GloballyRejected` as equally "safe to ignore," so the corrupted, un-rolled-back fields get persisted to `SignerDb` and drive further protocol actions (a pre-commit broadcast, and ultimately a real signature broadcast) on a block that has already reached the terminal `GloballyRejected` state.

### Finding Description
`BlockInfo::check_state` (`stacks-signer/src/signerdb.rs:314-329`) intentionally makes `GloballyRejected` a terminal state that cannot transition to `PreCommitted` or `LocallyAccepted`: [1](#0-0) 

However, `mark_pre_committed` and `mark_locally_accepted` mutate `self.valid`, `self.approved_time`, and (for the latter) `self.signed_self` *unconditionally*, before ever calling `move_to`: [2](#0-1) 

If `move_to` then fails (because `check_state` rejects the transition from `GloballyRejected`), the function returns `Err`, but the field mutations already happened and are **not reverted**. The `state` field itself remains `GloballyRejected` (untouched), but `valid`/`approved_time`/`signed_self` are now inconsistent with that state.

In `handle_block_validate_ok` (`stacks-signer/src/v0/signer.rs:1961-1970`), the caller checks the `Err` from `mark_pre_committed`, but only returns early if the block has **not** reached consensus *and* is not `LocallyAccepted`: [3](#0-2) 
Since `has_reached_consensus()` is true for both `GloballyAccepted` and `GloballyRejected`, the guard does not distinguish between them. It was clearly written to tolerate the legitimate race where the block already reached `GloballyAccepted` (harmless to leave `valid=true`), but it also silently swallows the error for `GloballyRejected`, where writing `valid=Some(true)` is a corruption of the record. Execution then falls through to persist the block and broadcast a pre-commit: [4](#0-3) 

This is reachable without a majority of colluding signers: a `GloballyRejected` verdict is reached via `mark_globally_rejected`, driven purely by *other* signers' rejection weight tally (>30%) independent of this signer's own decision. If this local signer's own `/v3/block_proposal` validation (submitted earlier) is still in flight when the group crosses the 30% rejection threshold and marks the block `GloballyRejected` (this signer's own `valid` field is still `None` at that point — the early-return guard at line 1932 `if block_info.valid.is_some() { ...; return; }` does not trigger), then when the node's `BlockValidateOk` finally arrives, `handle_block_validate_ok` proceeds to call `mark_pre_committed()`, which sets `valid = Some(true)` on a `GloballyRejected` `BlockInfo`, and — because of the `has_reached_consensus()` guard — the code does not bail out. It persists this corrupted state to `SignerDb::insert_block` and calls `send_block_pre_commit` + `handle_block_pre_commit` for itself.

The exact same unchecked-mutation-before-fallible-move pattern also exists in `mark_locally_accepted` (`stacks-signer/src/signerdb.rs:280-289`), used inside `handle_block_pre_commit`'s SIGN path: [5](#0-4) 
Here too, the guard `if !block_info.has_reached_consensus() { warn!(...) }` swallows the `Err` for a `GloballyRejected` block (since `has_reached_consensus()` is true), and the code still calls `insert_block`, `create_block_acceptance`, `handle_block_signature`, and `send_block_response` — i.e., it broadcasts an actual **signature over a block that has already been globally rejected by the signer set**, and writes `signed_self = Some(now)` into the persisted `BlockInfo` despite `state` remaining `GloballyRejected`.

This is the direct analog of the H-03 "unchecked `transfer`/`transferFrom` result" bug class: a fallible operation's boolean/`Result` outcome is not honored uniformly, and code proceeds as if the operation succeeded (here: as if the state transition to `PreCommitted`/`LocallyAccepted` succeeded), causing state corruption and, downstream, a signer emitting a signature that should never have been produced.

### Impact Explanation
This breaks the "signed vs validated" and "approved-parent vs canonical" equalities the state machine relies on: a block explicitly marked `GloballyRejected` (because the signer set collectively decided it, e.g., >30% weight rejected it as invalid) can have its `valid` flag flipped back to `true` and, worse, receive an actual signature (`signed_self`) and be broadcast as an acceptance from this signer via `handle_block_signature`/`send_block_response`. This is a **Critical** impact per the grading rubric: "a signer signing an invalid, non-canonical, or conflicting block." It also corrupts the persisted `SignerDb` record for a supposedly terminal, already-decided block, undermining any later liveness/conflict logic (e.g., `get_signed_conflicts`, `has_signed_block_in_tenure`) that relies on `signed_self`/`valid` being trustworthy once a block is `GloballyRejected`.

### Likelihood Explanation
The trigger requires only ordinary network timing, not signer collusion: a miner proposes a block; a subset of signers (>30% weight) independently validate and reject it quickly, causing `mark_globally_rejected` to fire from their tallied `BlockResponse::Rejected` messages before this signer's own submitted `/v3/block_proposal` validation (which can be arbitrarily slow depending on tx execution cost) returns. Because `block_info.valid` is still `None` for this signer when its own validation finally comes back `Ok`, the early-return check at line 1932 does not short-circuit, and the corrupted-mutation path is entered. No attacker-controlled majority or leaked keys are needed — only normal validation latency variance across independently-run nodes, which a miner can amplify by crafting a block whose execution cost is borderline/expensive (increasing variance in validation completion time across the signer set).

### Recommendation
Make `mark_pre_committed` and `mark_locally_accepted` atomic with respect to their `Result`: compute/attempt the `move_to` transition first, and only mutate `valid`/`approved_time`/`signed_self` if the transition succeeds (or explicitly revert the mutations on `Err`). Additionally, in `handle_block_validate_ok` and `handle_block_pre_commit`, change the guard from `has_reached_consensus()` to explicitly check `state != BlockState::GloballyRejected` (treating `GloballyRejected` distinctly from `GloballyAccepted`), so that a validation response racing behind a global rejection cannot resurrect a dead block or produce a stray signature/pre-commit for it.

### Proof of Concept
1. Miner proposes block `B` with a transaction whose execution time is highly variable/expensive.
2. Signers `S2..Sn` (>30% weight) validate `B` quickly via their nodes and reject it (`handle_block_validate_reject` → `mark_locally_rejected`), and once their tallied rejection weight exceeds 30%, some signer (or this signer itself via `handle_block_rejection`) calls `mark_globally_rejected` on `B`'s `BlockInfo`, setting `state = GloballyRejected`, while `S1`'s own `valid` field remains `None` (S1's local validation submission to its node is still pending).
3. `S1`'s node's slow validation eventually returns `BlockValidateOk` for `B`. `handle_block_validate_ok` fires: `block_info.valid.is_some()` is `false` (still `None`), so processing continues.
4. `check_block_against_signer_db_state` finds no chainstate conflict (S1's own node accepted `B`), so the `else` branch calls `block_info.mark_pre_committed()`. This sets `valid = Some(true)`, `approved_time = Some(now)`, then `move_to(PreCommitted)` fails (`Err`) because `state == GloballyRejected`.
5. The guard `!has_reached_consensus() && state != LocallyAccepted` is `false` (since `has_reached_consensus()` is `true`), so the function does **not** return early.
6. `self.signer_db.insert_block(&block_info)` persists `BlockInfo{state: GloballyRejected, valid: Some(true), approved_time: Some(now)}` — a corrupted record.
7. `send_block_pre_commit` broadcasts a pre-commit for `B` to the network, and `handle_block_pre_commit(self_address, B)` is invoked; because `valid` is now `true`, the `!block_info.valid.unwrap_or(false)` short-circuit no longer blocks it. If pre-commit weight (recorded independently in `block_pre_commits`, potentially including S1's and other stale pre-commits from before the rejection) reaches the 70% threshold and no fresh conflicting signature blocks it, `mark_locally_accepted(false)` is called, again setting `signed_self = Some(now)` before its own `move_to` fails — and the guard `!has_reached_consensus()` again fails to stop execution, so `handle_block_signature` and `send_block_response` broadcast S1's actual signature/acceptance over a block already decided `GloballyRejected` by the signer set.

Note: I could not directly execute or step through this in a live test environment; this trace is derived purely from static reading of `stacks-signer/src/signerdb.rs` and `stacks-signer/src/v0/signer.rs` as indexed. The precise weight/timing conditions needed to actually cross the pre-commit/signing threshold in step 7 (i.e., whether enough stale pre-commits exist to reach 70%) would need to be confirmed with a live/integration test, since it depends on the specific mix of pre-commit vs. rejection timing across the signer set.

    /// Check if the block state transition is valid
    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted
            ),
            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
