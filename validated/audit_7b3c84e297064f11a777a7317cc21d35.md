### Title
Stale per-epoch instant-withdraw basis is never cleared on claim, inflating default recovery and permanently freezing recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the null-pointer dereference in `CIccProfileXml::ParseBasic()` (dereferencing a record that was logically deleted but whose pointer still exists), `claimInstantWithdrawRequest` clears only the aggregate receipt `instantWithdrawsRequests[_user]` but never clears the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If the pool later defaults in that same epoch, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` dereference the stale basis as if the claim were still open, counting already-paid-out funds as recovery reserve and already-satisfied claimants as recovery basis. The stale claimant's post-default claim then underflows on `instantWithdrawsRequests[_user] -= claimBasis` (revert), while the phantom reserve inflates `defaultRecoveryPrice` above actual backing, leaving later recovery claimants unfunded.

### Finding Description
`claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]`, zeroes it, and pays out, but never touches `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` or `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

Those per-epoch records are only cleared inside `_claimDefaultedInstantWithdrawRequest`, which runs exclusively after `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` [2](#0-1) .

After default, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [3](#0-2) , and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying already held in the strategy [4](#0-3) . A claimed (paid-out) instant receipt inflates both: it is counted as claimant basis and as reserve, even though the underlying left the contract. `finalizeDefaultRecovery` then computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over the inflated, partially-phantom reserve [5](#0-4) .

### Impact Explanation
Two effects:

1. **Insolvency of the recovery reserve**: `defaultRecoveryPrice` is computed as if the already-paid instant claim's underlying were still held. Defaulted-epoch claimants (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`, `DefaultDistributor` active claims) are paid `claimBasis * defaultRecoveryPrice` from `defaultRecoveryReserve`. The phantom portion has no backing, so total owed exceeds the reserve — the last claimants' `safeTransfer` reverts, permanently freezing their recovery proceeds.

2. **Null-deref-style revert for the stale claimant**: when the already-claimed user calls `claimInstantWithdrawRequest` post-default, `_claimDefaultedInstantWithdrawRequest` reads a nonzero `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, then executes `instantWithdrawsRequests[_user] -= claimBasis` on a zeroed aggregate → arithmetic underflow → revert [2](#0-1) .

Broken invariant: one receipt one payout / donation isolation — a receipt already paid at par is counted a second time as recovery basis and as prefunded reserve.

### Likelihood Explanation
Requires, within one epoch: (a) an instant-withdraw request that is funded via `collectInstantWithdrawFunds` and claimed while its per-epoch records remain, and (b) at least one other unfunded instant request outstanding so `pendingInstantWithdraws != 0` at `finalizeDefaultRecovery`, plus a borrower default in that epoch. All steps are normal user/keeper flows (`requestInstantWithdraw`, `getInstantWithdrawFunds`, `stopEpoch(0, loss)`, `finalizeDefault`) with no privileged misbehavior. Caveat: I could not fully verify the exact epoch-tag alignment (request-time `epochNumber` vs `defaultRecoveryEpoch`) or whether the UI path allows claiming a funded instant receipt mid-epoch; if the per-epoch tag never matches the default epoch, impact reduces to the underflow-revert only.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch records for the request's epoch before paying out (mirroring `_clearWithdrawClaimForEpoch`): iterate/zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]`. Alternatively, make `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` derive instant basis from `instantWithdrawsRequests` aggregates that are guaranteed cleared on claim, and add an underflow guard (`claimBasis = min(claimBasis, instantWithdrawsRequests[_user])`) in `_claimDefaultedInstantWithdrawRequest`.

### Proof of Concept
Foundry fork sketch (against an `IdleCDOEpochVariant` deployment with instant withdraws enabled):

```solidity
// Epoch N buffer: A and B request instant withdrawals via the CDO.
vm.prank(userA); cdoEpoch.requestInstantWithdraw(amountA, AAtranche);
vm.prank(userB); cdoEpoch.requestInstantWithdraw(amountB, AAtranche);

// startEpoch N: keeper funds only A's request fully (partial funding path),
// pendingInstantWithdraws stays == amountB.
vm.prank(manager); cdoEpoch.startEpoch();

// A claims during epoch N -> instantWithdrawsRequests[A] = 0,
// but instantWithdrawsRequestsByEpoch[A][N] and instantWithdrawClaimsByEpoch[N]
// still contain amountA.
vm.prank(userA); cdoEpoch.claimInstantWithdrawRequest();
assertEq(strategy.instantWithdrawsRequests(userA), 0);
assertGt(strategy.instantWithdrawsRequestsByEpoch(userA, N), 0); // stale

// Borrower defaults at stopEpoch of epoch N (no deposit -> epochNumber stays N).
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager); cdoEpoch.stopEpoch(0, lossAmount);

// finalizeDefault: prefundedReserve counts amountA as held reserve,
// defaultRecoveryPrice is inflated by phantom backing.
uint256 recovered = /* partial recovery */;
deal(underlying, manager, recovered);
vm.startPrank(manager);
IERC20(underlying).approve(strategy, recovered);
cdoEpoch.finalizeDefault(recovered, manager);
vm.stopPrank();

// 1) Stale claimant's call reverts (underflow on zeroed aggregate).
vm.prank(userA);
vm.expectRevert(); // arithmetic underflow
cdoEpoch.claimInstantWithdrawRequest();

// 2) Sum of all defaulted-epoch claims exceeds defaultRecoveryReserve;
//    the last claimant's _transferDefaultRecovery safeTransfer reverts ->
//    permanent freeze of part of the recovery pool.
```

Validated guards: `_onlyIdleCDO`, `defaulted()` check in `finalizeDefaultRecovery`, `isEpochWithdrawZero`-style checks — none clear or sanity-check the stale per-epoch instant records.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
