## Finding

### Title
Stale confirmations from removed multisig members/keys still count toward `num_confirmations`, allowing execution below the live-member threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
When a multisig member (or access key, in `multisig` v1) is removed via `DeleteKey`/`DeleteMember`, the contract only purges *requests originated by* that member and clears their `num_requests_pk` counter. It never scans the `confirmations` sets of *other, still-open* requests to strip that member's prior confirmation. Because `confirm()` counts raw confirmation-set size against `num_confirmations` without re-validating that every counted confirmer is still a member, a stale confirmation from a departed member can be combined with confirmations from current members to execute a request with fewer *live* member confirmations than the configured threshold requires.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` only cleans up requests where the removed member is the *originator* (`r.member == member`): [1](#0-0) 

It never touches `self.confirmations` for requests originated by *other* members that the removed member had previously confirmed. The v1 equivalent in `multisig/src/lib.rs`'s `DeleteKey` action has the same shape — it filters `requests` by `r.signer_pk == pk` (originator only) before deleting the key: [2](#0-1) 

The threshold check in `confirm()` simply counts the size of the stored confirmation set and compares it to `num_confirmations`, with no re-check that every entry in that set is a currently-valid member/key: [3](#0-2) [4](#0-3) 

**Binding broken:** confirmations counted (`confirmations.len()`) should equal confirmations from *live* members, i.e. `confirmations ⊆ members`. After a member is removed, this invariant is violated for any request they had previously confirmed but did not originate — their stale confirmation remains in the set and is still counted.

### Impact Explanation
This crosses the "confirmations counted versus live members" custody boundary explicitly listed as in-scope: a multisig request can be executed with fewer confirmations from currently authorized members than `num_confirmations` mandates, because a phantom confirmation from a removed member/key fills one of the required slots. This is a Critical-severity issue per the rules ("a multisig request executed below threshold") — it allows a coalition smaller than the intended threshold (e.g. 2 of 3 remaining live members plus one stale confirmation from an ousted member, effectively bypassing the "3rd" required approver) to move funds, add/delete keys, or execute arbitrary `FunctionCall`/`Transfer` actions.

### Likelihood Explanation
No special privilege beyond being (or having previously been) an ordinary confirming member is required, and no deployment misconfiguration is involved — this is a straightforward sequence of otherwise-legitimate operations:
1. A request is created by member B.
2. Member A (who is later removed) confirms the request without reaching threshold.
3. Member A is removed via `DeleteMember`/`DeleteKey` through a normal, correctly-approved multisig action (e.g. because the key was compromised, rotated, or the member left).
4. The request from step 1 remains open with A's confirmation still counted.
5. Enough remaining live members confirm to reach `num_confirmations`, and the request executes — even though only `num_confirmations - 1` *live* members actually approved it.

This requires only ordinary usage patterns (open requests + a routine member/key removal), making it readily reachable in production multisig operation.

### Recommendation
When removing a member/key, iterate all open requests' confirmation sets (not just requests they originated) and remove the departing member/key from each. Alternatively, re-validate at `confirm()`-time (and at threshold-check time) that every public key/account in a request's confirmation set is still a current member, discounting stale entries before comparing against `num_confirmations`.

### Proof of Concept
Using `multisig2` semantics (analogous for `multisig` v1 with `DeleteKey`):
1. Deploy with 3 members (A, B, C) and `num_confirmations = 3`.
2. B calls `add_request` for a `Transfer` action → `request_id = 0`.
3. A calls `confirm(0)` → `confirmations[0] = {A}` (1/3, below threshold, not yet executed).
4. Members submit and confirm a separate request with action `DeleteMember { member: A }`, reaching threshold and executing — A is removed as a member/key. `delete_member` only cleans up requests *originated* by A; request `0` (originated by B) is untouched, so `confirmations[0]` still contains A.
5. B calls `confirm(0)` → `confirmations[0].len() + 1 == 2 + 1 == 3 >= num_confirmations (3)` → request executes, even though the only *live* confirmers are B and C (2 of 3 required), with A's stale confirmation making up the third. [5](#0-4) [6](#0-5)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);

            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
