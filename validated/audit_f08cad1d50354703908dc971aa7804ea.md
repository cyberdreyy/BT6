### Title
Permissionless CREATE1-based `deployCreditVault`/`deployRevolvingCreditVault` allows an attacker to front-run or reorg-swap a vault deployment and steal deposits sent to the predicted address - (File: contracts/IdleCreditVaultFactory.sol)

### Summary
`IdleCreditVaultFactory` deploys all credit vault components (vault proxy, strategy, queue, escrow, whitelist) via plain `new TransparentUpgradeableProxy(...)` in `_deployProxy` — i.e. CREATE1 — so every deployed address is a pure function of `(factory address, factory nonce)`. Both `deployCreditVault` and `deployRevolvingCreditVault` are `external` with no access control, so an unprivileged attacker can call the factory themselves and consume the next nonce. An attacker can therefore front-run an honest deployment (or exploit a chain reorg) so that a vault with attacker-chosen configuration occupies the exact address the honest deployment was predicted to land at. Any transaction built against the predicted address — most critically a lender `deposit` into the AA/BB tranche — is then routed into the attacker's vault.

### Finding Description
`_deployProxy` (contracts/IdleCreditVaultFactory.sol:280-286) uses CREATE1:
```solidity
return address(new TransparentUpgradeableProxy(implementation, proxyAdmin, data));
```
Consequently the vault address depends only on the factory's nonce, not on the deployment parameters. `deployCreditVault` (line 92) and `deployRevolvingCreditVault` (line 126) are callable by anyone. The attacker supplies `CreditVaultParams` and `StrategyData`, which include `implementation`, `borrower`, `manager`, `feeReceiver`, and `underlying`.

Attack scenario mirroring the PoolTogether report:
1. Idle (or a vault creator) sends `deployCreditVault` to deploy vault `V` at predicted address `0x1234` (factory nonce `N`).
2. Bob runs a bot watching for the `CreditVaultDeployed` event / mempool and immediately calls `depositAA`/`deposit` into `0x1234`.
3. Alice front-runs the deployment with her own `deployCreditVault` call (higher gas), consuming nonce `N`. Her vault — with herself as `borrower` and `feeReceiver`, or even an attacker-controlled `implementation` — is deployed at `0x1234`. The honest deployment shifts to nonce `N+1` (or is displaced in a reorg).
4. Bob's deposit lands in Alice's vault. If Alice set herself as `borrower` in `StrategyData`, the `IdleCreditVault` strategy lets the borrower draw down the pooled underlying; if she supplied a malicious `implementation`, the proxy delegates to arbitrary code and the deposited tokens are trivially extractable.

### Impact Explanation
Direct theft of user funds: any deposit or interaction that targets the deterministically-predicted vault address is captured by the attacker's vault. Loss is bounded only by the volume of transactions that rely on the predicted address between the hijack and detection — for a monitored/announced deployment this is the full deposit amount of front-run victims. This breaks the fair-mint / deposit-routing invariant: funds intended for the protocol vault are minted as shares in a hostile vault.

### Likelihood Explanation
- The functions are permissionless, so no privileged role is needed.
- The bug was judged valid for PoolTogether's identical `VaultFactory` CREATE1 pattern and was mitigated by switching to CREATE2.
- Exploitation requires either mempool front-running (the attacker's deploy consumes the nonce first) or a reorg replacing the deployment — feasible on any chain where the factory operates. The value extracted scales with automated depositor bots or integrators that precompute or react to the predicted address, exactly the pattern described in the original report.

### Recommendation
Deploy the vault, strategy, and ancillary proxies with CREATE2 using a salt derived from the full deployment configuration (e.g., `keccak256(abi.encode(cvParams, strategyData, ancillaryParams, msg.sender))`), or restrict `deployCreditVault`/`deployRevolvingCreditVault` to the treasury/owner so nonces cannot be consumed by arbitrary callers. CREATE2 makes the deployed address a commitment to the configuration, so a front-run or reorg cannot place a differently-configured vault at the predicted address.

### Proof of Concept
A Foundry test reproducing the hijack (sketch — assumes standard test scaffolding from `test/foundry/IdleCreditVaultFactory.t.sol`):

```solidity
function testFrontRunDeployHijacksPredictedAddress() external {
  MockFactoryERC20 underlying = new MockFactoryERC20("USDC", "USDC", 6);
  IdleCreditVaultFactory factory = _deployFactory();
  IdleCreditVaultFactory.CreditVaultParams memory cvParams = _makeCreditVaultParams(creatorFeeReceiver);
  cvParams.underlying = address(underlying);
  IdleCreditVaultFactory.AncillaryParams memory anc = _emptyAncillary();

  // Predict the strategy proxy address = factory at current nonce
  uint256 nonce = vm.getNonce(address(factory));
  address predictedStrategy = vm.computeCreateAddress(address(factory), nonce);

  // Attacker front-runs: same factory, own config (attacker = borrower/manager/feeReceiver)
  IdleCreditVaultFactory.StrategyData memory atkData =
    _makeStrategyData(address(new IdleCreditVault()), address(underlying), address(factory), "Atk", 12e18);
  atkData.borrower = attacker;
  atkData.manager = attacker;
  vm.prank(attacker);
  factory.deployCreditVault(cvParams, atkData, anc); // consumes nonce, strategy lands at predictedStrategy

  // Victim bot deposits into the vault whose strategy sits at predictedStrategy
  // resolve cv from CreditVaultDeployed event; underlying.approve + cv.depositAA(amount)
  // The strategy's borrower (attacker) can now pull the deposited underlying,
  // or a malicious `implementation` would have made extraction trivial.
  assertEq(IdleCreditVault(predictedStrategy).borrower(), attacker);
}
```

The PoC demonstrates that a second caller's parameters determine the contract at the predicted address — identical code shape to the PoolTogether finding and remediated the same way.
