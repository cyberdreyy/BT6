### Title
Fee-on-transfer underlying tokens inflate `IdleCreditVault` strategy-token supply beyond actual backing, causing vault insolvency - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The credit vault strategy `deposit()` assumes that pulling `_amount` of `token` from the IdleCDO results in `_amount` tokens received, and mints `_amount` strategy tokens 1:1. For fee-on-transfer underlyings, the strategy actually receives `_amount - fee`, so every deposit mints `fee` units of unbacked strategy-token claims. The same assumption propagates through `IdleCDOCreditVault._deposit`, which forwards the nominal `_amount` to the strategy even though it correctly minted tranche shares using the balance delta.

### Finding Description
In `IdleCDOCreditVault._deposit` (contracts/IdleCDOCreditVault.sol:191-212) the tranche-share mint is already balance-delta safe: `_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, ...)`. However, the function then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the nominal `_amount`, not the received amount. [1](#0-0) 

Inside `IdleCreditVault.deposit` (contracts/strategies/idle/IdleCreditVault.sol:596-617), the strategy does `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` followed unconditionally by `_mint(msg.sender, _amount)`. The minted strategy tokens are the CDO's claim on vault assets (strategy tokens are valued 1:1 with underlyings per the `burnStrategyTokens` docstring, and `getContractValue` counts them at that price). [2](#0-1) [3](#0-2) 

For a fee-on-transfer `token`, the strategy balance increases by `_amount - fee` while it mints `_amount` strategy tokens to the CDO. The CDO's recorded NAV (`lastNAVAA`/`lastNAVBB` plus strategy-token valuation) therefore overstates real vault assets by `fee` on every deposit. This is the same bug class as the Metrom report: accounting uses the nominal transfer amount instead of the balance delta. No existing guard catches it — `_guarded`, `_updateAccounting`, and `skipDefaultCheck` all operate on the inflated numbers, and `_skimDonatedAssets`/reserve logic does not reconcile strategy holdings.

### Impact Explanation
Each deposit with a fee-on-transfer underlying permanently creates `fee` underlying units of unbacked liability. When the borrower repays only real assets, total claims (strategy tokens held by the CDO plus pending withdraw receipts plus APR0 principal) exceed the vault's underlying balance, so late withdrawers and receipt claimants face a permanent shortfall equal to the accumulated fee leakage — a direct solvency break and permanent freezing of the unbacked `fee`-worth of funds per deposit.

### Likelihood Explanation
Requires the vault to be deployed on a fee-on-transfer or fee-capable underlying (e.g., USDT if its fee mechanism were ever enabled, or any FOT ERC20 chosen at `initialize`). The underlying is fixed at deployment and selected by the honest owner, so the precondition is environmental rather than attacker-controlled; unprivileged depositors merely trigger it through the normal `depositAA`/`depositBB` path during the buffer phase. Consistent with the source report's Medium severity.

### Recommendation
Measure actual received tokens in `IdleCreditVault.deposit` and mint/forward accordingly, and have `IdleCDOCreditVault._deposit` pass the received amount to the strategy:

```solidity
// IdleCreditVault.deposit
uint256 _preBal = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 _received = underlyingToken.balanceOf(address(this)) - _preBal;
_mint(msg.sender, _received);
// use _received for totEpochDeposits accounting
```
and in `IdleCDOCreditVault._deposit` call `strategy.deposit(_contractTokenBalance(_token) - _preBal)` (captured before the strategy pull).

### Proof of Concept
Reproducible Foundry fork PoC sketch:

```solidity
// Deploy IdleCDOCreditVault + IdleCreditVault with a FOT mock as `token`
// (or fork a FOT token, e.g. enabling USDT's basisPointsRate via its owner slot).

// 1. Attacker (KYC-passing lender) approves and calls depositAA(1000e6) during buffer phase.
uint256 minted = cdo.depositAA(1000e6);
// CDO minted tranche shares for 1000e6 - fee (correct), but:

// 2. Strategy received 1000e6 - fee, yet minted 1000e6 strategy tokens to the CDO.
assertEq(strategy.balanceOf(address(cdo)), 1000e6);
assertEq(token.balanceOf(address(strategy)), 1000e6 - fee);

// 3. getContractValue() reports NAV inflated by `fee`; lastNAVAA += 1000e6 - fee
//    while strategy-token balance claims the full 1000e6.

// 4. After borrower repays only real assets, claimWithdrawRequest / instant
//    withdraw for the last `fee` units of claims reverts on insufficient balance —
//    permanent freezing of `fee` per deposit.
```

Uncertainty note: I confirmed the mint-without-balance-delta in `IdleCreditVault.deposit` and the nominal-amount forwarding in `IdleCDOCreditVault._deposit` directly from source. The exact `getContractValue` aggregation of strategy tokens was not fully read in this iteration, but strategy tokens are documented as 1:1 claims on underlying, which is sufficient for the insolvency invariant to hold.
