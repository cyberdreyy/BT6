### Title
Gateway Vault handler correlates DON responses to pending requests only by a client-reusable JSON-RPC ID, enabling cross-request response confusion analogous to the Lens publication-ID reuse bug - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
The gateway-side Vault handler identifies a "pending" client request purely by its JSON-RPC `req.ID` (owner-prefixed). Once a response is delivered, the ID is freed and can be immediately reused by a new, unrelated request from the same owner. Late-arriving DON node responses for the old (already-completed) request are matched only by this reused ID, and — for nodes whose signed payload omits the `requestId` field — the aggregator explicitly skips the request-ID equality check before accepting a quorum/signature-valid response. This mirrors the Lens finding: an identifier that is not bound to the request's content can be reassigned to different content over time, so a message intended for one request gets applied to a different one.

### Finding Description
`newActiveRequest` keys pending requests solely by `req.ID` and rejects only requests that are *currently* in-flight with the same ID: [1](#0-0) 

As soon as a response is sent, the entry is deleted from `activeRequests`, freeing the ID for reuse: [2](#0-1) 

`HandleNodeMessage` looks up the pending request purely by `resp.ID` with no verification that the response actually corresponds to the content of the currently active request with that ID: [3](#0-2) 

The owner-prefixed ID (`authorizedOwner + RequestIDSeparator + originalRequestID`) is derived only from the *authorized owner* plus the client-supplied ID, not from a digest of the request contents: [4](#0-3) 

The aggregator's signature-based fast path binds a response to the request only via `payloadRequestID == requestID`, but this check is explicitly skipped when the signed payload's `requestId` is empty ("temporarily tolerate ... nodes that have not upgraded"): [5](#0-4) 

Putting this together: a client (or the same authorized owner) can send request A with ID `X`, receive quorum before all nodes reply, and have the pending-request entry deleted. If the same owner (or attacker legitimately authorized under that owner, e.g. a delegated workflow) immediately sends a new, different request B reusing ID `X`, a late-arriving, otherwise-valid signed response for request A (from a node whose payload has no `requestId`, or whose payload matches by coincidence/legacy format) can be accepted by `HandleNodeMessage`/`Aggregate` and delivered as the result for request B — because the correlation is by reusable ID, not by request content.

### Impact Explanation
If a stale/late DON response for one Vault operation (e.g., a `SecretsList`/`SecretsCreate` result) is delivered to a caller who submitted a *different* request under the same reused ID, this is a concrete instance of cross-request/cross-response confusion in the gateway: the wrong result (e.g., stale secret identifiers, or a "success" acknowledgement for a delete/update the user never actually initiated) can be returned to the second caller. Because the ID space is only owner-scoped and not content-bound, and reuse is not prevented across time (only rejected while "active"), the guarantee that "response you get corresponds to the request you sent" can be broken — the same underlying issue as the Lens report, where an ID not tied to content allowed an action to apply to the wrong resource once the ID was reassigned.

### Likelihood Explanation
Exploiting this requires: (1) an unprivileged/authorized client to reuse a request ID shortly after a prior request under that ID completes and is deleted from `activeRequests` (fully client-controlled, since the client picks `req.ID`), and (2) a slow node response for the earlier request to arrive after the new request is registered, and (3) the signature validation path to accept it without requestId matching (only possible for nodes/messages lacking `requestId` in the signed payload, called out in code as a temporary tolerance) or with a coincidental quorum digest match. This is a narrower race than the original Lens report (which required only a chain re-org), but the mechanism — ID reuse breaking content binding — is directly analogous, and item (1) is entirely within an unprivileged client's control.

### Recommendation
- Do not reuse client-chosen JSON-RPC IDs as the sole correlation key across time; bind pending-request tracking (and the signature/quorum validation) to a digest of the request content (e.g., `req.Digest()`, already computed elsewhere in the codebase for the replay guard) in addition to/instead of the raw ID.
- Remove or gate the temporary tolerance in `validateUsingSignatures` that accepts responses when `payloadRequestID` is empty; until all nodes are upgraded, require quorum-only validation for such responses rather than accepting a single/lightweight signature match without requestId verification.
- Consider not deleting/freeing `activeRequests[req.ID]` until all in-flight node responses for that ID have been drained (or use a short cool-down monotonic sequence component in the internal correlation key) so a stale response cannot land on a newly created request with the same client-supplied ID.

### Proof of Concept
Conceptual (cannot be fully executed without live DON nodes, but the code path is directly traceable):
1. Authorized owner sends Vault request A: `{"id": "X", "method": "vault_listSecretIdentifiers", ...}`. Gateway computes `activeRequests["ownerA::X"]`.
2. 2F+1 nodes respond quickly and quorum is reached; `sendResponse` deletes `activeRequests["ownerA::X"]` (`core/services/gateway/handlers/vault/handler.go:823-833`), but one slow node has not yet replied.
3. Same owner immediately sends a different Vault request B, again with `"id": "X"` (client fully controls this): `newActiveRequest` succeeds because the map entry was cleared (`handler.go:466-481`).
4. The slow node's late response for request A arrives (`HandleNodeMessage`, `handler.go:489-513`), is looked up via `resp.ID == "ownerA::X"`, found (now request B's entry), and if it passes the signature check without a requestId match (`aggregator.go:287-307`) or coincidentally satisfies quorum digest, it is delivered to the *callback for request B* via `sendSuccessResponse`.
5. The caller of request B receives a result/acknowledgement that actually pertains to request A's content.

**Uncertainty**: I was not able to fully verify in this codebase snapshot whether all currently-deployed DON nodes always populate `requestId` in the signed payload (which would make the bypass path in step 4 unreachable in practice), nor observe a live multi-node timing test demonstrating the race. This is flagged as a design-level gap in the correlation mechanism rather than a demonstrated end-to-end exploit.

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	l := logger.With(h.lggr, "method", resp.Method, "requestID", resp.ID, "nodeAddr", nodeAddr)
	l.Debugw("handling node response")

	if !h.nodeRateLimiter.Allow(nodeAddr) {
		l.Debugw("node is rate limited", "nodeAddr", nodeAddr)
		return nil
	}

	ar := h.getActiveRequest(resp.ID)
	if ar == nil {
		// Request is not found, so we don't need to send a response to the user
		// This can happen if a slow node responds after the request has already been completed
		l.Debugw("no pending request found for ID")
		return nil
	}

	ok := ar.addResponseForNode(nodeAddr, resp)
	if !ok {
		l.Errorw("duplicate response from node, ignoring", "nodeAddr", nodeAddr)
		return nil
	}

	copiedResponses := ar.copiedResponses()
	resp, err := h.aggregator.Aggregate(ctx, l, ar.req.ID, copiedResponses, resp)

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}

	p.lggr.Debugw("authorized gateway vault request", "method", req.Method, "requestID", req.ID, "owner", authorizedOwner, "orgID", authResult.OrgID(), "workflowOwner", authResult.WorkflowOwner())
	return &AuthorizedGatewayVaultRequest{
		Req:        *req,
		AuthResult: authResult,
	}, nil
}
