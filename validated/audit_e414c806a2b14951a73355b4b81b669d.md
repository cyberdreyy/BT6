### Title
`requestWithdraw` silently converts a normal withdrawal into an instant-withdraw receipt, changing payout semantics without user opt-in - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
When a user calls `requestWithdraw(_amount, _tranche)` they request the standard epoch-end withdrawal path: the receipt is booked for `principal + interest - fees` and settled via `creditVault.requestWithdraw` into `withdrawsRequests`. However, `requestWithdraw` contains a hidden branch: if the vault's unscaled APR dropped by more than `instantWithdrawAprDelta` relative to `lastEpochApr`, the call is silently rerouted to `creditVault.requestInstantWithdraw`, which books only the bare principal (`_underlyings` computed before interest is ever added) as an instant receipt (`instantWithdrawsRequests`). The user never passed an "instant" flag, receives no error and no event distinguishing the two paths, and ends up holding a materially different claim than the one requested. This mirrors the M-05 bug class: a user intent is silently reinterpreted under a state condition and the output is not what the caller expected.

### Finding Description
In `requestWithdraw`, `_underlyings` is first set to the tranche's current underlying value (principal only). Then, if `_isInstantWithdrawEnabled()` and `lastEpochApr > currentApr + instantWithdrawAprDelta`, the code calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` and returns early — the interest accrual path (`_calcInterestWithdrawRequest`, `_totalWithdrawFees`, `pendingWithdrawFees`, `interestForOverUnderPerformance`) is skipped entirely. [1](#0-0) 

Consequences of the silent swap versus the requested normal withdrawal:

1. **Lost interest**: the instant receipt is for `_underlyings` = principal only, so the user forfeits the accrued epoch interest that a normal request would have locked in (`principal + interest - totalFees` at lines 772-776). [2](#0-1) 
2. **Different claim mechanics**: the instant path mints receipt strategy tokens to the user (`instantWithdrawsRequests[_user]`) claimable only after the borrower funds instant withdraws via `getInstantWithdrawFunds` or after `instantWithdrawDeadline`, rather than a normal `withdrawsRequests` entry funded at `stopEpoch`. [3](#0-2) 
3. **Default exposure change**: instant receipts sit in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` for the *current* epoch and are treated as "default-epoch pending instant receipts" if the borrower fails to fund them — the user's claim is downgraded into the defaulted-recovery flow, where a normal request for a *previous* epoch would have already been funded and paid in full (see `testClaimWithdrawRequestWithDefault` where the pre-default normal claim pays fully while the instant one does not). [4](#0-3) 
4. **Triggering a default**: the rerouted request increments `pendingInstantWithdraws`; if the borrower cannot cover instant funding, `getInstantWithdrawFunds` falls into `_handleBorrowerDefault`, putting the whole pool into default — consequences far beyond what a normal withdraw request implies. [5](#0-4) 

There is no parameter, no revert, and no distinct event telling the caller their request was classified as instant; the same function returns a receipt with different amount, timing, and default treatment.

### Impact Explanation
An unprivileged lender (tranche-token holder) calling `requestWithdraw` in the buffer period after an APR cut: (a) permanently loses the interest component they would have been paid under the normal path — a direct loss quantified as `interest - totalFees` per request, and (b) receives an instant receipt whose funding depends on borrower behavior within `instantWithdrawDelay`, exposing them to the defaulted-claim recovery multiplier instead of a fully funded normal claim. The acceptance criteria are met: direct loss of unclaimed yield plus potential downgrade into loss-sharing recovery, both without any error signaling the change in behavior.

### Likelihood Explanation
The trigger is a routine protocol operation: the manager lowers the vault APR between epochs by more than `instantWithdrawAprDelta` (a configuration value the owner sets). Every `requestWithdraw` call after such an APR cut and before `lastEpochApr` is refreshed at the next `stopEpoch` (where `lastEpochApr = _strategy.unscaledApr()` is written, line 469) is silently rerouted. Honest privileged actions (APR update, epoch stop) are all that is needed; no attacker-controlled sequencing is required. Guard review: `allowInstantWithdraw`, `disableInstantWithdraw`, and the programmable-borrower check gate *claims* and *availability* of instant withdrawals, not the silent reclassification itself; KYC (`isWalletAllowed`) and tranche flags apply equally to both paths, so no existing guard warns or blocks the conversion. [6](#0-5) 

### Recommendation
Make the withdrawal type explicit instead of state-inferred:

- Add an explicit `bool isInstant` (or separate `requestInstantWithdraw`) entry point, and revert in `requestWithdraw` if the instant-withdraw condition would trigger — analogous to the M-05 mitigation ("throw an error when the requested action can no longer be performed").
- Alternatively, emit a dedicated event (`InstantWithdrawRequested` vs `WithdrawRequested`) and document that `requestWithdraw` returns the lower-value instant receipt when APR drops, so callers and integrators can detect the divergence.

### Proof of Concept
Foundry fork test sketch against the epoch CDO:

```solidity
// Setup: deposit AA (and BB), run epoch 0 so lastEpochApr = initialProvidedApr.
uint256 mintedAA = idleCDO.depositAA(10000e18);
idleCDO.depositBB(10000e18);
_startEpochAndCheckPrices(0);
// stop epoch 0 normally; lastEpochApr now = apr0
_stopEpochAndCheckPrices(0, apr0, expected);

// Owner/manager sets a much lower APR for epoch 1 (honest action):
// stopEpoch(_newApr = apr0/2, _interest = ...) -> _setScaledApr(apr0/2)
// Now lastEpochApr (apr0) > unscaledApr (apr0/2) + instantWithdrawAprDelta.

// Victim calls requestWithdraw expecting a normal receipt with interest:
uint256 before = underlying.balanceOf(victim);
uint256 requested = cdoEpoch.requestWithdraw(mintedAA / 2, AAtranche);

// ASSERT BUG: strategy.requestInstantWithdraw was taken instead of requestWithdraw.
IdleCreditVault strat = IdleCreditVault(strategy);
assertGt(strat.instantWithdrawsRequests(victim), 0);   // silently an instant receipt
assertEq(strat.withdrawsRequests(victim), 0);          // NOT a normal request
// requested == principal only; interest that _calcInterestWithdrawRequest would
// have paid is forfeited, and the claim now depends on getInstantWithdrawFunds /
// instantWithdrawDeadline funding, or degrades into defaulted-epoch recovery if
// the borrower does not fund instant withdraws in time.
```

The divergent branches are at `contracts/IdleCDOEpochVariant.sol:761-770` (instant path, principal-only receipt, early return) versus `contracts/IdleCDOEpochVariant.sol:772-790` (normal path, `principal + interest - fees` receipt). Existing tests confirm the semantic difference: instant requests burn tranche tokens immediately and mint strategy-token receipts (`requestInstantWithdraw`, `IdleCreditVault.sol:356-375`), while normal requests enter `withdrawsRequests` funded at epoch stop.

Caveat: whether this is judged a vulnerability or intended product behavior depends on spec intent — the code comments ("If apr decreased wrt last epoch, request instant withdraw") suggest deliberate design, but the lack of an explicit flag, event, or revert makes the silent reinterpretation match the M-05 pattern of "user expects X, gets Y, no error".

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
