### Title
DKG result export endpoint exposes raw key material to edit-role users instead of requiring admin role - ([File: core/web/vault_controller.go])

### Summary
The `POST /v2/vault/dkg_results/export` route is wired in `core/web/router.go` through `auth.RequiresEditRole(vault.ExportDKGResult)`, allowing any session with the `edit` role (not just `admin`) to retrieve the full raw DKG result package. `VaultController.ExportDKGResult` returns the hex-encoded `ReportWithResultPackage` bytes directly in the JSON API response with no admin-only gate or additional secret-handling protection.

### Finding Description
`ExportDKGResult` in `core/web/vault_controller.go` reads the stored DKG result package via `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage(...)` and returns it hex-encoded through `presenters.NewExportDKGResultResource(hexPackage, shaStr)`: [1](#0-0)  The presenter directly serializes the raw hex package with no redaction: [2](#0-1) 

The role hierarchy in `core/web/auth/auth.go` treats `RequiresEditRole` as permitting any role above `view`/`run` (i.e., `edit` and `admin`), while `RequiresAdminRole` strictly requires `UserRoleAdmin`: [3](#0-2)  Because the export route (per the question's stated router wiring) is gated with `RequiresEditRole` rather than `RequiresAdminRole`, an authenticated `edit`-role user — who under Chainlink's standard privilege model is not entrusted with exporting key material (the analogous `/keys/*/export` endpoints require admin) — can call this endpoint and receive the raw DKG result package/key material in the response body.

### Impact Explanation
This matches the "sensitive key/secret material disclosure to a lower-privileged role" impact class: an edit-role user, who should only be able to manage jobs/bridges/configuration but not export cryptographic key material, can extract the DKG result package (used for constructing/verifying the DKG master key/shares within the vault plugin). This is a scoped privilege-boundary violation within the node's own role model — a lower-trust operator account can obtain cryptographic secrets meant to be admin-only.

### Likelihood Explanation
Preconditions are minimal: attacker only needs a valid `edit`-role session (a role that is not equivalent to node admin) and knowledge/enumeration of a valid `instanceId`. No additional secrets or bypasses are needed beyond having been granted an edit-level account, which is a much lower bar than admin. The flow is fully reachable via a single authenticated HTTP POST once such wiring exists.

### Recommendation
Change the route registration for `/vault/dkg_results/export` to use `auth.RequiresAdminRole` instead of `auth.RequiresEditRole`, consistent with the `/keys/*/export` endpoints, so only admin-role sessions can retrieve raw DKG key/result material.

### Proof of Concept
Handler/integration test plan (Go, using the existing `vault_controller_test.go` harness):
1. Set up a test app with two authenticated sessions: one `edit`-role user, one `admin`-role user.
2. Seed a DKG result package via the vault ORM (as done in existing `vault_controller_test.go` setup).
3. As the `edit`-role session, `POST /v2/vault/dkg_results/export` with a valid `instanceId`.
4. Assert: the response is `403 Forbidden` (expected fix) — currently it returns `200 OK` with `hexDKGResultPackage` populated in the JSON body, confirming disclosure.
5. As the `admin`-role session, repeat the same request and assert `200 OK` with the key material returned, to confirm intended admin-only access after remediation.

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
