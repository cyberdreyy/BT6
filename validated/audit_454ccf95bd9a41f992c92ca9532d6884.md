### Title
Unauthenticated flooding of legacy `savedCallbacks` map enables age-based pruning to evict pending victim callbacks and drop/misdeliver DON responses - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` inserts every validly-formed (but otherwise unauthenticated/unauthorized) trigger request into the shared `h.savedCallbacks` map with no per-sender rate limiting or allowlist check, as explicitly flagged by the `// TODO: apply allowlist and rate-limiting here` comment. Because `pruneCallbacks` evicts the oldest entries strictly by `createdAt` once `len(savedCallbacks) > MaxSavedCallbacks`, an attacker able to cheaply generate many validly-signed messages can inflate the map and cause a victim's still-pending callback to be pruned before the DON responds.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:250-269`) only calls `msg.Validate()` for legacy requests, which checks message structure/signature validity, not sender authorization or per-user quota [1](#0-0) . It then routes directly into `HandleLegacyUserMessage` without any allowlist or rate limiter gate — the code itself documents this gap: `// TODO: apply allowlist and rate-limiting here` [2](#0-1) .

Every successfully-parsed request is stored keyed by `msg.Body.MessageId`: [3](#0-2) 

`pruneCallbacks`, run on a timer, first removes callbacks older than `CallbackMaxAgeSec` (default 120s), and only if the map is *still* over `MaxSavedCallbacks` (default 20000) does it sort remaining entries by `createdAt` and evict the oldest half: [4](#0-3) 

Since `nodeRateLimiter` only limits messages coming *from DON nodes* (`handleWebAPIOutgoingMessage`), not user-submitted legacy trigger requests, and `msg.Validate()` requires only a self-consistent keypair signature (not any privileged credential), an unauthenticated attacker can generate large volumes of distinct, validly-signed `MessageId`s cheaply and flood `savedCallbacks` past `MaxSavedCallbacks` faster than the DON can respond to any individual request. If this happens within the `CallbackPruneIntervalSec` window (30s, well under the 120s max age), the size-based branch triggers and evicts the *oldest* half of entries by creation time regardless of whether they are legitimate pending requests awaiting a response — including a victim's request submitted just before the flood. Once evicted, the victim's entry is gone from the map; when the DON later responds via `handleWebAPITriggerMessage`, the lookup `savedCb, found := h.savedCallbacks[msg.Body.MessageId]` fails and the response is silently dropped [5](#0-4) . If an attacker later reissues the same `MessageId` (map keys are not globally unique/reserved beyond current in-memory presence) a new callback could occupy that key.

### Impact Explanation
This is an availability/response-integrity issue scoped to the legacy `web_api_trigger` DON message path: a victim's request can have its response silently dropped due to unrelated attacker traffic, causing the gateway HTTP call to eventually hit `callback.Wait(ctx)` timeout in `gateway.ProcessRequest` and return a `RequestTimeoutError` to the victim [6](#0-5) . This matches a DoS/availability impact class rather than a direct fund-movement or secret-disclosure bug; there is no confirmed cross-user data leak, only response loss/denial for the targeted `MessageId`.

### Likelihood Explanation
Feasibility depends on real-world constraints not fully verifiable from this code alone: reaching `MaxSavedCallbacks` (20000, config default) requires generating and sending at least that many distinct signed legacy messages within the ~30s prune interval, and each message must pass `msg.Validate()`, decode a well-formed `TriggerRequestPayload`, and pass the timestamp freshness check — all attacker-controllable with only a keypair and no privileged credential, as noted in the TODO comment. However, upstream infrastructure (load balancer/API gateway rate limits, TLS handshake cost, or an allowlist configured at deployment) outside this file could mitigate real-world exploitability; those layers are not visible in this codebase and are explicitly excluded from scope (network/infra-level mitigations). Within the code shown, no per-IP/per-key throttle exists before `savedCallbacks` insertion.

### Recommendation
- Implement the still-pending `// TODO: apply allowlist and rate-limiting here` — add per-sender/per-key rate limiting and/or an allowlist check in `HandleLegacyUserMessage` before inserting into `savedCallbacks`.
- Change `pruneCallbacks` size-eviction policy to avoid evicting entries under configured `CallbackMaxAgeSec` regardless of map size, or at minimum log/alert when the oldest-half eviction removes non-expired entries so operators can detect abuse.
- Consider bounding insertions with a per-sender cap independent of global map size, so no single attacker can consume the entire capacity budget.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `MaxSavedCallbacks` set low (e.g., 10) and `CallbackPruneIntervalSec` short, matching existing test helpers (`triggerRequest(...)`) used in `handler_test.go`.
2. Call `HandleLegacyUserMessage` once for a "victim" message with a fresh `MessageId`, capturing its callback (do not let the DON respond yet).
3. Immediately call `HandleLegacyUserMessage` for `> MaxSavedCallbacks` "attacker" messages with unique `MessageId`s and distinct signing keys, all with `createdAt` timestamps effectively equal/earlier than the victim's (or by directly invoking `pruneCallbacks()` after insertion to simulate the timer).
4. Assert (via `handler.savedCallbacks`, guarded by `handler.mu`) whether the victim's `MessageId` was evicted despite being unexpired (`now - createdAt < CallbackMaxAgeSec`).
5. Then simulate the DON response for the victim's `MessageId` via `handleWebAPITriggerMessage`/`HandleNodeMessage` and assert whether `savedCb.SendResponse` is invoked or the response is silently dropped (`found == false`).

Expected (vulnerable) result: victim entry evicted before response arrives, and the later DON response is silently dropped since `found` is `false` in `handleWebAPITriggerMessage`.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

		// Send first response from a node back to the user, ignore any other ones.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
