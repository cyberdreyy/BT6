### Title
Missing Minimum Amount Check in Bridge `send_token` Allows Dust-Transfer Flooding and Bridge Authority Wallet Drain — (File: `crates/sui-framework/packages/bridge/sources/bridge.move`)

### Summary

The `send_token` and `send_token_v2` functions in the Sui native bridge accept any token amount strictly greater than zero. There is no minimum viable transfer amount enforced on-chain. An ordinary SUI holder who owns even 1 unit of a bridged token (e.g., 1 satoshi of WBTC) can call `send_token` repeatedly, burning their tokens on Sui and emitting a `TokenDepositedEvent` for each call. Off-chain bridge authorities must process every such event by submitting a transaction on the target EVM chain, paying ETH gas each time. Because the gas cost of an Ethereum transaction far exceeds the value of a 1-satoshi transfer, this drains the bridge authority's ETH signing wallet and can prevent legitimate bridge transfers from being processed.

### Finding Description

`send_token` is a `public fun` on the shared `Bridge` object, callable by any account:

```move
public fun send_token<T>(
    bridge: &mut Bridge,
    target_chain: u8,
    target_address: vector<u8>,
    token: Coin<T>,
    ctx: &mut TxContext,
) {
    let inner = load_inner_mut(bridge);
    let bridge_seq_num = inner.get_current_seq_num_and_increment(message_types::token());
    let token_id = inner.treasury.token_id<T>();
    let token_amount = token.balance().value();
    assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
    assert!(token_amount > 0, ETokenValueIsZero);   // ← only guard: strictly > 0
    ...
    inner.send_token_internal(target_chain, token, message);
    event::emit(TokenDepositedEvent { ... amount: token_amount ... });
}

`send_token_internal` immediately burns the coin and stores a `BridgeRecord`:

```move
fun send_token_internal<T>(inner: &mut BridgeInner, target_chain: u8, token: Coin<T>, message: BridgeMessage) {
    assert!(!inner.paused, EBridgeUnavailable);
    assert!(chain_ids::is_valid_route(inner.chain_id, target_chain), EInvalidBridgeRoute);
    inner.treasury.burn(token);   // ← irreversible burn
    inner.token_transfer_records.push_back(message.key(), BridgeRecord { ... });
}

The `TransferLimiter` (`check_and_record_sending_transfer`) only enforces an **upper** bound (route limit in USD) and is only consulted on the **receiving** side during `execute_token_transfer` (ETH→SUI claims). It is never consulted during `send_token` (SUI→ETH outbound), and it enforces no lower bound at all: [3](#0-2) 

`send_token_v2` has the identical gap — only `token_amount > 0` is checked: [4](#0-3) 

### Impact Explanation

1. **Bridge authority ETH wallet drain.** Every `TokenDepositedEvent` must be picked up by off-chain bridge authorities and settled on Ethereum. A 1-satoshi WBTC transfer (~$0.0003) costs far less than a single Ethereum transaction (~$1–$10 in gas). An attacker who submits 10,000 such calls drains the bridge authority's ETH signing wallet of tens of thousands of dollars while spending only a negligible amount of bridged token.

2. **Permanent fund loss / lock for users.** Once `send_token` executes, the user's tokens are irreversibly burned on Sui. If the bridge authority's ETH wallet is exhausted, pending `BridgeRecord` entries cannot be settled on Ethereum, permanently locking the corresponding value. Even without a full drain, dust transfers that are economically unviable to settle leave the user's Sui-side tokens burned with no corresponding release on Ethereum.

3. **DoS of legitimate bridge traffic.** A flooded `token_transfer_records` linked table and an exhausted ETH signing wallet block all legitimate bridge transfers until the authority wallet is refilled and the backlog is cleared.

### Likelihood Explanation

- `send_token` is a `public fun` on a shared object — any account can call it without any capability or permission.
- Bridged tokens (WBTC, ETH, USDC, USDT) are freely obtainable on Sui. An attacker needs only a tiny balance.
- The attack requires no special knowledge beyond the public ABI.
- The `ETokenValueIsZero` guard (`token_amount > 0`) is the only on-chain protection; it does not prevent dust amounts.

### Recommendation

1. **Enforce a per-token minimum transfer amount** in `send_token` and `send_token_v2`, analogous to how `validator_set::request_add_stake` enforces `MIN_STAKING_THRESHOLD`: [5](#0-4) 

   Store a `min_transfer_amount: VecMap<u8, u64>` (keyed by `token_id`) in `BridgeTreasury` or `BridgeInner`, and assert `token_amount >= min_transfer_amount[token_id]` before burning.

2. **Initialize minimum amounts at bridge genesis** for every supported token, sized so that the USD value of the minimum transfer exceeds the expected Ethereum gas cost of settlement by a safe margin.

### Proof of Concept

```move
// Attacker holds 10_000 units of WBTC (each unit = 1 satoshi, ~$0.0003 total)
// Bridge is live, not paused, route Sui→Ethereum is valid.
let i = 0;
while (i < 10_000) {
    // mint 1 satoshi of WBTC to attacker (or attacker already holds it)
    let dust = coin::mint<WBTC>(&mut treasury_cap, 1, ctx);
    // send_token accepts amount=1 because 1 > 0
    bridge::send_token<WBTC>(
        &mut bridge,
        chain_ids::eth_mainnet(),
        evm_address,   // attacker's EVM address
        dust,
        ctx,
    );
    // TokenDepositedEvent emitted; bridge authority must now pay ETH gas to settle
    i = i + 1;
};
// Result: 10_000 BridgeRecord entries queued; bridge authority ETH wallet drained
// by ~$10_000–$100_000 in gas; legitimate transfers blocked.
```

Each iteration passes the only guard (`token_amount > 0`), burns the coin irreversibly via `treasury::burn`, and appends a `BridgeRecord` to the shared linked table, forcing off-chain authorities to submit an Ethereum transaction whose gas cost dwarfs the transferred value.

public(package) fun check_and_record_sending_transfer<T>(
    self: &mut TransferLimiter,
    treasury: &BridgeTreasury,
    clock: &Clock,
    route: BridgeRoute,
    amount: u64,
): bool {
    // Create record for route if not exists
    if (!self.transfer_records.contains(&route)) {
        self
            .transfer_records
            .insert(
                route,
                TransferRecord {
                    hour_head: 0,
                    hour_tail: 0,
                    per_hour_amounts: vector[],
                    total_amount: 0,
                },
            )
    };
    let record = self.transfer_records.get_mut(&route);
    let current_hour_since_epoch = current_hour_since_epoch(clock);

    record.adjust_transfer_records(current_hour_since_epoch);

    // Get limit for the route
    let route_limit = self.transfer_limits.try_get(&route);
    assert!(route_limit.is_some(), ELimitNotFoundForRoute);
    let route_limit = route_limit.destroy_some();
    let route_limit_adjusted = (route_limit as u128) * (treasury.decimal_multiplier<T>() as u128);

    // Compute notional amount
    // Upcast to u128 to prevent overflow, to not miss out on small amounts.
    let value = (treasury.notional_value<T>() as u128);
    let notional_amount_with_token_multiplier = value * (amount as u128);

    // Check if transfer amount exceed limit
    // Upscale them to the token's decimal.
    if (
        (record.total_amount as u128)
            * (treasury.decimal_multiplier<T>() as u128)
            + notional_amount_with_token_multiplier > route_limit_adjusted
    ) {
        return false
    };

    // Now scale down to notional value
    let notional_amount =
        notional_amount_with_token_multiplier / (treasury.decimal_multiplier<T>() as u128);
    // Should be safe to downcast to u64 after dividing by the decimals
    let notional_amount = (notional_amount as u64);

    // Record transfer value
    let new_amount = record.per_hour_amounts.pop_back() + notional_amount;
    record.per_hour_amounts.push_back(new_amount);
    record.total_amount = record.total_amount + notional_amount;
    true
}
