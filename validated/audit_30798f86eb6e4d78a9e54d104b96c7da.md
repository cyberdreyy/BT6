### Title
`SystemInstruction::CreateAccount` account-creation griefing via forced lamport transfer causes transaction reversion (front-running DoS) - (File: `programs/system/src/system_processor.rs`)

### Summary
The System Program's `create_account()` helper unconditionally rejects account creation if the target address already holds a non-zero lamport balance, returning `SystemError::AccountAlreadyInUse`. Because any unprivileged account can receive lamports via a plain `SystemInstruction::Transfer` without the recipient's signature, an attacker can pre-fund a soon-to-be-created address with a single lamport to permanently force this check to fail, reverting the victim's legitimate `CreateAccount` transaction — the same "forcing balance into a target to break a strict zero-balance precondition" class of bug described in the external report.

### Finding Description
`create_account()` in the system program checks whether the destination account already has a non-zero balance before allowing allocation/assignment: [1](#0-0) 

```
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(...);
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
```

Because Solana's `Transfer` instruction only requires the *sender* to sign, and imposes no restriction on the destination account being unowned, uninitialized, or otherwise "off limits" (see `transfer`/`transfer_verified`), an attacker can send any amount of lamports (as little as 1) to a predictable/known target address (e.g., an address about to be created by an app, or a PDA-adjacent basic keypair address seen in mempool) before the legitimate `CreateAccount` transaction lands: [2](#0-1) [3](#0-2) 

Once the target has any lamports, every future `CreateAccount` instruction addressing it fails with `AccountAlreadyInUse`, exactly mirroring the reported Solidity bug class: "a check requiring zero balance... creates a denial-of-service vector where an attacker can prevent legitimate [account creation] by forcing [lamports] into the [account]... allow[ing] transaction front-running attacks that grief legitimate users by making their transactions revert."

Notably, the codebase already contains the analogous fix for this exact problem: `SystemInstruction::CreateAccountAllowPrefund`, gated by the `create_account_allow_prefund` feature, explicitly skips the zero-balance requirement ("Create a new account without checking for 0 lamports... Intended for use where account has already had rent paid in whole or in part before creation"): [4](#0-3) [5](#0-4) 

This confirms the root cause and its recommended fix pattern (allowing prefunded balances instead of requiring zero) were already recognized as an issue class by Agave, but the legacy `CreateAccount` instruction — which remains in active, default use by essentially all existing wallets/programs/CLIs (e.g. `system_instruction::create_account` used throughout `cli/`, `program-test/`, SBF test programs) — still retains the original strict check.

### Impact Explanation
This is a low-severity griefing/DoS primitive rather than a fund-theft or consensus-safety bug: it does not steal funds or corrupt state, but it lets any unprivileged network participant reliably and cheaply (1 lamport + a transfer transaction) prevent legitimate account creation at a target address, causing dependent transactions to revert. This can be used to front-run/grief dApp flows that create deterministic or predictable-but-not-PDA addresses (vote/nonce/stake bootstrap flows, airdrop/onboarding flows, ATA-like custom initializers that use plain keypairs instead of PDAs), forcing failed transactions, wasted fees, and application-level denial of service.

### Likelihood Explanation
High reachability: any user can submit an ordinary, unprivileged `SystemInstruction::Transfer` to any address (no target signature required) prior to the intended `CreateAccount` transaction, and the check triggers deterministically. Exploitability is limited to callers who create non-PDA, keypair-based accounts without either avoiding pre-funding (checking `get_account` first client-side does not prevent a same-slot race) or using `CreateAccountAllowPrefund`. This is a long-known Solana ecosystem quirk (the reason `CreateAccountAllowPrefund` and PDA-based account patterns exist), so likelihood of accidental/malicious triggering is high but impact per occurrence is limited to a stuck transaction, not a security breach.

### Recommendation
For the legacy `CreateAccount` path, consider migrating callers toward `CreateAccountAllowPrefund` (already implemented) by default, or relaxing `create_account()`'s check to tolerate a pre-existing lamport balance as long as the account has no data and is still owned by the system program (mirroring the report's suggested fix of comparing balances/state rather than requiring an absolute zero precondition) — i.e., verify "unused" via data length and owner rather than lamport balance alone.

### Proof of Concept
1. Attacker observes (or predicts) that address `X` (a plain `Keypair`, not a PDA) is about to be used as the destination of a `SystemInstruction::CreateAccount` instruction by a victim (e.g. visible in an unconfirmed transaction, or from a standard bootstrap flow like nonce/vote/stake account creation in `cli/src/nonce.rs`).
2. Attacker submits `SystemInstruction::Transfer { lamports: 1 }` from any funded wallet to `X`. This requires no signature from `X` and succeeds unconditionally per `transfer_verified` (`programs/system/src/system_processor.rs:216-243`).
3. The victim's subsequent `CreateAccount` instruction targeting `X` hits the `to.get_lamports() > 0` branch in `create_account()` (`programs/system/src/system_processor.rs:164-171`) and fails with `SystemError::AccountAlreadyInUse`, reverting the victim's transaction.
4. Repeatable indefinitely and cheaply (1 lamport per attempt) against any newly-observed address before it is created, unless the victim's tooling uses `CreateAccountAllowPrefund` instead of `CreateAccount`.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}

fn transfer(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    if !instruction_context.is_instruction_account_signer(from_account_index)? {
        ic_msg!(
            invoke_context,
            "Transfer: `from` account {} must sign",
            instruction_context.get_key_of_instruction_account(from_account_index)?,
        );
        return Err(InstructionError::MissingRequiredSignature);
    }

    transfer_verified(
        from_account_index,
        to_account_index,
        lamports,
        invoke_context,
        instruction_context,
    )
}
