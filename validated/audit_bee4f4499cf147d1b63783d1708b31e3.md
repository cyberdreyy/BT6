## Title
Confirmations from a deleted multisig key persist and continue to count toward `num_confirmations`, allowing execution below the intended live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
The multisig contract's `confirm()` function authorizes execution once the number of stored public keys in `self.confirmations` for a request reaches `num_confirmations`. When a key is removed via `MultiSigRequestAction::DeleteKey`, the contract only purges requests that were *added* by that key; it does not scan and remove that key's confirmations on other, still-pending requests added by different keys. This breaks the intended equality **confirmations counted == confirmations from currently-live members**, letting a request execute using a stale confirmation from an already-revoked key.

### Finding Description
`confirm()` checks the size of the stored confirmations set against `self.num_confirmations`: [1](#0-0) 

When a `DeleteKey` action executes, cleanup is scoped only to requests whose `signer_pk` (the original requester) equals the deleted key — confirmations that the deleted key placed on *other* pending requests (added by a different signer) are never removed: [2](#0-1) 

Because `HashSet<PublicKey>` confirmations are never revalidated against the current set of live access keys/members, a public key that has been deleted from the account can still contribute a "confirmation" that was recorded before its removal. NEAR's runtime only enforces that a key must be valid *at the time it signs a transaction* (e.g., when it originally called `confirm`) — it does not retroactively invalidate previously stored confirmations when the key is later deleted. `assert_valid_request()` also performs no such re-validation: [3](#0-2) 

This is the same class of bug as the reported issue: a value used to authorize an action (`withdrawableRewardsOf` snapshot vs. actual withdrawn state; here, "confirmations count" vs. actual live signer set) is computed/cached before a state change (withdrawal; here, key deletion) and is not corrected afterward, so a stale record is honored as if it were still current.

### Impact Explanation
This crosses the "a multisig request executed below threshold" Critical impact bucket. An attacker who is (or colludes with) a current or former key holder can get a malicious request (e.g., `Transfer`, `AddKey`, `FunctionCall`) executed with fewer *currently valid* member approvals than `num_confirmations` mandates, because one or more of the counted confirmations belong to a public key that has since been deleted from the account. This directly undermines the K-of-N security guarantee the multisig is supposed to provide and can result in unauthorized transfer of funds held by the multisig account.

### Likelihood Explanation
This requires a compromised or colluding key that is later removed (a realistic operational event — e.g., rotating out a suspected-compromised signer) while a request it confirmed is still pending. Since `add_request`/`confirm` allow requests to remain open indefinitely (subject only to the `active_requests_limit` and `REQUEST_COOLDOWN` for deletion), and nothing forces cleanup of stale confirmations on key removal, the scenario is plausible in normal multisig lifecycle management (member rotation) rather than requiring an exotic setup.

### Recommendation
On `DeleteKey` (and any member-removal action in `multisig2`), iterate over all pending requests' confirmation sets and strip out the removed public key/member, not just requests originated by that key. Alternatively, revalidate at `confirm()`/execution time that every public key in the stored confirmations set is still a valid access key/member of the account before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with `num_confirmations = 3` and keys `K1, K2, K3, K4`.
2. `K1` calls `add_request_and_confirm(R)` where `R` is a `Transfer` to an attacker-controlled account — confirmations(`R`) = `{K1}`.
3. `K3` calls `confirm(R)` — confirmations(`R`) = `{K1, K3}` (still below threshold of 3).
4. Separately, the team detects `K3` is compromised and submits/confirms a `DeleteKey { public_key: K3 }` request (approved via `K1`/`K2`/`K4` reaching `num_confirmations`). This executes `execute_request`'s `DeleteKey` branch, which only removes requests where `r.signer_pk == K3` — request `R` (added by `K1`) is untouched, so confirmations(`R`) remains `{K1, K3}` even though `K3`'s access key no longer exists on-chain: [2](#0-1) 
5. `K2` calls `confirm(R)`. `confirmations.len() + 1 >= num_confirmations` evaluates `2 + 1 >= 3` → true, so `execute_request(R)` fires the `Transfer`, even though only `K1` and `K2` are currently live approvers (`K3`'s stale confirmation made up the third "vote"). [4](#0-3) 

Funds move out of the multisig account with only 2 of the 4 currently-valid members' consent, violating the declared 3-of-N guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
