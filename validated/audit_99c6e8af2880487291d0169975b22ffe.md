### Title
`DeleteMember` fails to purge a removed member's confirmations from requests it did not create, allowing execution below `num_confirmations` live members - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` only deletes requests and confirmations for requests whose *creator* (`r.member`) equals the removed member; it does not scan `self.confirmations` values for entries where the removed member merely *confirmed* someone else's request. As a result, stale confirmations from a deleted member remain counted toward `num_confirmations`, letting requests execute with fewer live confirmers than required.

### Finding Description
Binding claimed to hold: for every pending request `r`, `|{live members who confirmed r}| == num_confirmations` must be true whenever `r` executes. The code violates this because cleanup in `delete_member` is scoped incorrectly: [1](#0-0) 

```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    assert(
        self.members.len() - 1 >= self.num_confirmations as u64,
        "Removing given member will make total number of members below number of confirmations",
    );
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    ...
    self.members.remove(&member);
    ...
}
```

`r.member` is the original request *creator* set once in `add_request`: [2](#0-1) 

The filter `r.member == member` therefore only removes requests that member M itself created, and wipes their confirmation sets outright. It never inspects the `HashSet<String>` values inside `self.confirmations` for other (still-pending) requests that M merely *confirmed* but did not create. Any such request retains M's confirmation entry after M is deleted from `self.members`.

The membership-count assert (`self.members.len() - 1 >= self.num_confirmations`) only bounds the *total* member count post-removal; it says nothing about per-request confirmer validity, so it does not catch this.

Exploit flow: with a 2-of-3 multisig (members A, B, M), A creates 3 separate transfer requests (each created by A, not M), each is confirmed by M and by B, leaving each request one confirmation short of `num_confirmations` in terms of *distinct still-relevant* confirmers is not the issue — rather each already has 2 live confirmations (M + B) satisfying 2-of-3 currently. The attack works by having M and one other member (say B) each confirm N different requests to 1-of-2 (not yet executed, since `num_confirmations` is 2, so each waits at 1 confirmation from M only, or similarly 2 confirmations but M is one of them). Then the remaining live members (A, B) submit a `DeleteMember{member: M}` request and execute it (this only requires their own confirmations, not M's, and does not touch A/B's other pending unrelated requests because `r.member` for those requests is A, not M — so they are untouched, retaining M's stale confirmation). After deletion, M is removed from `self.members`, but M's confirmation string remains inside `self.confirmations` for each of the N pending requests. Any single additional live member confirming each of the N requests pushes their confirmation counts to `num_confirmations`, and `execute_request` proceeds — counting M (no longer a member) as one of the confirmers. This lets `Transfer` requests execute with only `num_confirmations - 1` genuinely live confirming members.

### Impact Explanation
Multiple pending `Transfer` (or other) requests can be finalized and executed using a stale, no-longer-valid confirmation from a removed member, moving NEAR out of the multisig account with fewer live signers than the configured threshold. This is a direct violation of "a multisig request executed below `num_confirmations` live members," which is explicitly listed as Critical impact. The blast radius scales with however many pending requests M had confirmed but not created before removal (N requests, each independently exploitable), and is repeatable any time a member is removed while having outstanding confirmations on requests it did not create.

### Likelihood Explanation
Preconditions: multisig has ≥3 members with `num_confirmations` such that a member removal is legally allowed (`members.len()-1 >= num_confirmations`); at least one member M has confirmed (but not created) one or more pending requests; the remaining members execute a `DeleteMember{member: M}` request (a normal, legitimate multisig operation, not requiring any privileged/foundation role — any set of members reaching `num_confirmations` can do this, and per the audit's "existing legitimate members act normally" framing this is a plausible operational event, e.g., a compromised key or offboarding a member). No special attacker capability beyond normal multisig operation is required to trigger the state; the divergent state persists silently until any remaining member(s) confirm the stale request(s), completing an under-authorized execution. This is a straightforward, deterministic bug in the cleanup filter, easily reproduced.

### Recommendation
In `delete_member`, iterate over `self.confirmations` for *all* pending `request_id`s (not just those created by `member`) and remove `member`'s entry from each confirmation `HashSet`, in addition to fully deleting requests originally created by `member`. E.g.:
```rust
for (request_id, mut confs) in self.confirmations.iter() {
    if confs.remove(&member.to_string()) {
        self.confirmations.insert(&request_id, &confs);
    }
}
```
This should be done before/alongside the existing removal of requests keyed by `r.member == member`, ensuring no request retains a confirmation from a member no longer in `self.members`.

### Proof of Concept
```rust
#[test]
fn test_delete_member_leaves_stale_confirmation() {
    // Setup: members A, B, M ; num_confirmations = 2
    testing_env!(context_with_account(A, amount));
    let mut c = MultiSigContract::new(vec![A, B, M], 2);

    // A creates 3 separate transfer requests (creator = A, not M)
    let r1 = c.add_request(transfer_request(receiver1, amt));
    let r2 = c.add_request(transfer_request(receiver2, amt));
    let r3 = c.add_request(transfer_request(receiver3, amt));

    // M confirms all three requests (1st confirmation each)
    testing_env!(context_with_account(M, amount));
    c.confirm(r1);
    c.confirm(r2);
    c.confirm(r3);

    // B and A create+confirm a DeleteMember{M} request (2/2 confirmations from A, B)
    testing_env!(context_with_account(A, amount));
    let del_req = c.add_request_and_confirm(delete_member_request(M));
    testing_env!(context_with_account(B, amount));
    c.confirm(del_req); // executes: M removed from self.members

    // Assert M removed
    assert!(!c.members.contains(&M));

    // BUG: confirmations for r1, r2, r3 still contain M's entry
    assert!(c.confirmations.get(&r1).unwrap().contains(&M.to_string()));
    assert!(c.confirmations.get(&r2).unwrap().contains(&M.to_string()));
    assert!(c.confirmations.get(&r3).unwrap().contains(&M.to_string()));

    // B alone confirms each remaining request -> reaches num_confirmations=2
    // even though only B is a genuinely live confirmer (M removed)
    testing_env!(context_with_account(B, amount));
    c.confirm(r1); // executes despite only 1 live confirmer (B)
    c.confirm(r2); // executes despite only 1 live confirmer (B)
    c.confirm(r3); // executes despite only 1 live confirmer (B)

    // All three transfers executed with live-confirmer count == num_confirmations - 1 == 1
    assert_eq!(c.requests.len(), 0); // all fully executed/removed
}
```
This demonstrates the binding `distinct live members confirmed == num_confirmations` is violated for all N=3 requests simultaneously after a single `DeleteMember` call.
