## Analysis

The reference bug class is: an attacker can trigger a state update (a "credit"/timestamp refresh) that is supposed to only follow genuine progress, but the code grants the credit even when no real progress occurred, corrupting a downstream time-based calculation. The strongest reachable analog in this repo is in the signer's **tenure-inactivity/miner-fallback** logic.

### Title
Malicious Miner Can Grief Tenure-Inactivity Fallback by Refreshing `last_activity_time` With Proposals That Are Rejected/Make No Progress - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` treats a block proposal that fails its own freshness/height checks (i.e., is about to be rejected) as legitimate "miner activity" and refreshes `tenure_activity.last_activity_time` for that tenure. This is the exact bug pattern from the external report: a state timestamp that is supposed to reflect real progress is instead refreshed by an action that produces none, letting an attacker indefinitely postpone downstream time-based logic — here, the fallback that hands the active-miner role to the previous, valid tenure when the current miner goes inactive.

### Finding Description
In `check_latest_block_in_tenure` [1](#0-0) , when a proposed block does not confirm as many blocks as expected (`chain_length <= info.block.header.chain_length`), the function is about to reject the proposal (`return Ok(false)`), but first it explicitly credits the tenure with fresh activity: [2](#0-1) 

The comment even states the rationale directly: *"treat any attempt to reorg a locally accepted block as valid miner activity ... The miner may just be slow, so count this invalid block proposal towards valid miner activity."* A second, similar credit happens for proposals that only conflict with a pre-committed (unsigned) block: [3](#0-2) .

This activity timestamp is stored via `update_last_activity_time` / `get_last_activity_time` [4](#0-3) , and it feeds the miner-inactivity decision in `check_miner_inactivity`: [5](#0-4) 
which only proceeds to hand the active-miner role back to the prior, canonical-tip miner if `is_timed_out` returns true [6](#0-5) . Per the documented flow, `is_timed_out` never trips if the miner has signed a block in the tenure, and otherwise depends on the tenure being inactive past `block_proposal_timeout` [7](#0-6) .

Because every signer independently runs `check_latest_block_in_tenure` on every proposal it receives — this check runs at proposal time, at validate-ok, and at signing, per the doc [8](#0-7)  — a miner that never manages to get a block signed can keep the whole signer set's local `last_activity_time` fresh simply by resubmitting stale/duplicate/lower-height proposals that are guaranteed to be rejected.

### Impact Explanation
This wedges the signer set's fallback mechanism: `check_miner_inactivity` is the only path that reassigns the active-miner role away from a stalled tenure to the previous valid one [9](#0-8) . If `last_activity_time` never goes stale, `is_timed_out` never fires, `check_miner_inactivity` returns early at line 313-315, and the signer set is stuck waiting indefinitely on a miner that is not producing valid, signed blocks — a liveness wedge matching the "signer wedged into never signing valid blocks" criterion.

### Likelihood Explanation
This requires only the current tenure's single miner (a "one-slot miner") acting alone, no majority collusion, no other signer's key, and no privileged access — it simply needs to keep sending block proposals with an unhelpful/lower `chain_length`, which every signer receives and processes identically. This is a low-cost, self-serve griefing vector directly analogous to the report's "call the fee function repeatedly to reset the timer without contributing value."

### Recommendation
Do not refresh `last_activity_time` merely because a proposal was received and rejected. Only credit activity when the miner demonstrates real progress — e.g., a proposal that would otherwise pass validation but is superseded by a fresher signed/pre-committed block, not one that is strictly stale/duplicate/lower relative to the tenure's own known tip. This mirrors the referenced report's fix: don't update the tracked timestamp unless the action being credited actually represents value/progress.

### Proof of Concept
1. Miner M wins the current tenure slot but never gets a block signed (`has_signed_block_in_tenure` stays false).
2. Periodically (faster than `block_proposal_timeout`), M resubmits a stale/duplicate/lower-`chain_length` block proposal for its own tenure.
3. Each signer runs `check_latest_block_in_tenure`, rejects the proposal, but first calls `signer_db.update_last_activity_time(...)` [10](#0-9) .
4. `is_timed_out` never observes a stale `last_activity_time`, so `check_miner_inactivity` [11](#0-10)  keeps returning early.
5. The signer set never falls back to the prior valid miner, and the tenure/chain stalls indefinitely while M contributes nothing but rejected proposals.

**Caveat:** I was not able to fully inspect the body of `SortitionState::is_timed_out` in `stacks-signer/src/chainstate/v1.rs`/`v2.rs` within the available iterations to confirm byte-for-byte that it reads `get_last_activity_time` (as opposed to some other combined signal); the causal link is strongly supported by the code's own comments and the documented flow (`docs/signer-flows.md`), but this final wiring should be double-checked directly in `v1.rs`/`v2.rs` if greater certainty is required.

    pub fn update_last_activity_time(
        &mut self,
        tenure: &ConsensusHash,
        last_activity_time: u64,
    ) -> Result<(), DBError> {
        debug!("Updating last activity for tenure"; "consensus_hash" => %tenure, "last_activity_time" => last_activity_time);
        self.db.execute("INSERT OR REPLACE INTO tenure_activity (consensus_hash, last_activity_time) VALUES (?1, ?2)", params![tenure, u64_to_sql(last_activity_time)?])?;
        Ok(())
    }

    /// Get the last activity timestamp for a tenure (identified by consensus_hash)
    pub fn get_last_activity_time(&self, tenure: &ConsensusHash) -> Result<Option<u64>, DBError> {
        let query =
            "SELECT last_activity_time FROM tenure_activity WHERE consensus_hash = ? LIMIT 1";
        let Some(last_activity_time_i64) = query_row::<i64, _>(&self.db, query, &[tenure])? else {
            return Ok(None);
        };
        let last_activity_time = u64::try_from(last_activity_time_i64).map_err(|e| {
            error!("Failed to parse db last_activity_time as u64: {e}");
            DBError::Corruption
        })?;
        Ok(Some(last_activity_time))
    }

## 7. The chainstate checks (shared)

`check_latest_block_in_tenure` answers "does this block confirm the tip we
expect?" and it runs in three places: at proposal arrival (inside
`check_proposal`), at validate-ok, and at the moment of signing. _Which_ tenure
it is asked about depends on the block: a tenure-change block is checked against
its **parent** tenure, every other block against its **own**. Never both. The
pivotal helper is `get_tenure_last_block_info`, which considers only blocks that
carry a signature (`get_last_signed_block`): a pre-commit never vetoes anything,
it only counts as miner activity.
