### Title
Post-default `requestWithdraw` mints par-payable receipts without reserving `defaultRecoveryReserve`, oversubscribing the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` has a post-default branch that mints a claimable receipt (`postDefaultRequests[_user]`) which is later paid **1:1 out of `defaultRecoveryReserve`** via `_transferDefaultRecovery`, but the request path never increases `defaultRecoveryReserve` nor checks that the reserve covers the new claim. This is the same bug class as the external report: a fulfillment/claim path that creates claimables without bumping the reservation ledger, so `sum(claimable) > reserve` and later claimants' withdrawals revert.

### Finding Description
In `requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:243-258), once `defaultRecoveryFinalized` is set, a user holding strategy-token receipts calls through `IdleCDOEpochVariant.requestWithdraw`, which burns their position and calls `IdleCreditVault.requestWithdraw`. The post-default branch:

```solidity
if (defaultRecoveryFinalized) {
  if (_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0) {
    revert NotAllowed();
  }
  _burn(msg.sender, _amount);
  _mint(_user, _amount);
  postDefaultRequests[_user] = _amount;
  return;   // no reserve top-up, no solvency check
}
```

The only guard is that the user has no open receipt — there is no check that `defaultRecoveryReserve >= _amount`, and `defaultRecoveryReserve` is not incremented here. `defaultRecoveryReserve` is sized in `finalizeDefaultRecovery` (line 686-692) as `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve`, and `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` where `totalBasis` covers only *pre-default* claims (active basis + `defaultPendingClaimBasis`). Claims then consume the reserve on a first-come basis: `_transferDefaultRecovery` (line 912-917) does `defaultRecoveryReserve -= _amount` and reverts on underflow.

Concretely: after finalization, `defaultRecoveryReserve` exactly covers `totalBasis * recoveryPrice` worth of defaulted and pending claims (plus the active-LP share that flows through this reserve for pending receipts). A post-default requester burns tranche tokens priced at the haircut and receives a **par claim on the same reserve**. Because their original pro-rata share of recovery sits on the active-holder side (DefaultDistributor / `activeFinalNAV` accounting, lines 699-705) and is *not* moved into `defaultRecoveryReserve` at request time, every post-default claim is net-new spending against a reserve that was sized without it.

The analogous oversubscription invariant from the external report holds:

```
defaulted claims (claimBasis * defaultRecoveryPrice)
+ sum(postDefaultRequests)  >  defaultRecoveryReserve
```

Whoever calls `claimWithdrawRequest` first (line 303-307 routes to `_claimPostDefaultWithdrawRequest` → `_transferDefaultRecovery`) drains the reserve; defaulted-epoch receipt holders and later post-default claimants hit the underflow revert in `defaultRecoveryReserve -= _amount` and can never claim.

**Uncertainty caveat:** whether `IdleCDOEpochVariant`'s post-default `requestWithdraw` path atomically tops up `defaultRecoveryReserve` (e.g., by pulling the requester's DefaultDistributor share or calling `reserveDefaultRecovery`, lines 629-633) could not be fully verified — `reserveDefaultRecovery`'s docstring describes a different trigger ("borrower funding fails after funds were already returned"). If the CDO does top up 1:1 at request time, the finding collapses; nothing in `IdleCreditVault.requestWithdraw` itself performs or requires that top-up, and the function returns early without any reserve interaction.

### Impact Explanation
Direct theft / permanent freezing of unclaimed funds, quantified by `min(sum(postDefaultRequests), defaultRecoveryReserve)`. An early post-default claimant (any tranche-token holder — an unprivileged lender) is paid from the recovery reserve that `finalizeDefaultRecovery` sized for defaulted-epoch receipt holders; those receipt holders' `claimWithdrawRequest` calls then revert permanently on `defaultRecoveryReserve -= _amount` underflow (line 915). The loss equals the post-default payout, taken from passive defaulted claimants.

### Likelihood Explanation
Requires a defaulted, finalized facility with residual recovery (`defaultRecoveryPrice` between 0 and `RECOVERY_FULL`) and at least one post-default withdraw request racing pending defaulted claims. Sequence: borrower defaults → `finalizeDefaultRecovery` sets the reserve → an unprivileged tranche holder calls `requestWithdraw` (allowed, only `_hasWithdrawRequest` checked) → calls `claimWithdrawRequest` before defaulted receipt holders claim. No privileged misbehavior is needed; owner/manager/borrower remain honest. Likelihood is gated by how often real facilities reach partial-recovery finalization with active tranche holders still requesting — a plausible but not constant condition — and by the unverified CDO-side top-up caveat above.

### Recommendation
Make reservation accounting single-sourced, mirroring the external fix:
- In the post-default branch of `requestWithdraw`, either (a) increment `defaultRecoveryReserve` by atomically pulling the requester's recovery share into the strategy before minting `postDefaultRequests[_user]`, or (b) track post-default claims in a separate, fully-funded ledger instead of paying them from `defaultRecoveryReserve`.
- Add a solvency guard: `require(defaultRecoveryReserve - pendingDefaultedClaims >= _amount)` or, equivalently, revert when a post-default request would make aggregate claims exceed the reserve.
- Keep `_transferFundedClaim`'s `balance < reserve` guard (line 900-904) so funded receipts can never spend the recovery reserve, and extend the same protection in the opposite direction for post-default claims.

### Proof of Concept
Reproducible Foundry test outline (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function test_postDefaultRequest_drainsRecoveryReserve() public {
    // Setup: deposit for user1 (AA) and user2 (AA), start epoch.
    // user1 requests a normal withdraw -> withdrawsRequestsByEpoch[user1][epoch] = X.

    // Borrower defaults. Manager calls finalizeDefaultRecovery with partial
    // recovery R (e.g. 50% of totalBasis). defaultRecoveryReserve is now
    // exactly sized for totalBasis * defaultRecoveryPrice; recoveryPrice < RECOVERY_FULL.

    // Attacker: user2 (ordinary tranche holder, unprivileged) requests a
    // post-default withdraw via cdoEpoch.requestWithdraw(user2Balance, AATranche).
    // IdleCreditVault mints postDefaultRequests[user2] = haircutAmount
    // with NO increase to defaultRecoveryReserve.

    // Attacker claims first:
    vm.prank(user2);
    cdoEpoch.claimWithdrawRequest(); // _transferDefaultRecovery pays 1:1

    // Invariant broken: user2 was paid haircutAmount from the reserve even
    // though totalBasis already consumed 100% of it.
    // Victim: user1's defaulted-epoch receipt claim now reverts.
    vm.prank(user1);
    vm.expectRevert(); // defaultRecoveryReserve -= claimBasis * price underflows
    cdoEpoch.claimWithdrawRequest();
}
```

The key assertions: `defaultRecoveryReserve` is unchanged by the post-default `requestWithdraw`, `postDefaultRequests[user2]` is payable at par from that reserve, and `user1`'s funded defaulted claim permanently reverts afterward.
