### Title
Stale confirmations from deleted multisig members count toward the execution threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` in `multisig2/src/lib.rs` removes a departing member's own *created* requests but leaves their confirmation entries on other members' pending requests untouched, and `confirm()` counts confirmations purely by set size without validating that each confirming party is still a current member. This lets a request execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
`delete_member` (multisig2/src/lib.rs, lines 356-379) filters requests by `r.member == member`, i.e. only requests *authored* by the removed member: [1](#0-0) 
It never inspects `self.confirmations` entries belonging to requests authored by *other* members that the removed member may have confirmed. Those `HashSet<String>` entries still contain the removed member's identity string.

`confirm()` (multisig2/src/lib.rs, lines 292-315) then decides execution purely from the confirmation set's cardinality: [2](#0-1) 
There is no check that every entry in `confirmations` corresponds to a member still present in `self.members`. The binding the contract is supposed to enforce is: `confirmations from live members >= num_confirmations`. What is actually enforced is: `|confirmations set (possibly containing removed members)| >= num_confirmations`. These diverge once any confirming member is removed while their confirmation on an unrelated pending request is still outstanding.

The same pattern exists in the older `multisig/src/lib.rs`, where `DeleteKey` only clears confirmations for requests whose `signer_pk` equals the deleted key (the request's author), not requests the key merely confirmed: [3](#0-2) 
and `confirm()` there has the identical raw-length check: [4](#0-3) 

### Impact Explanation
This crosses the "confirmations counted versus live members" authorization boundary explicitly called out as in-scope. A multisig configured for `k`-of-`n` should never execute a request (e.g. `Transfer`, `AddKey`, `FunctionCall`) with fewer than `k` approvals from currently authorized members. Because a removed member's stale confirmation is still counted, an attacker (or a legitimately-removed but still-partially-approved former signer) can help push a request to execution with effectively fewer live-member confirmations than the configured threshold — a multisig request executed below the intended/current threshold, matching the Critical impact category ("a multisig request executed below threshold").

### Likelihood Explanation
This requires only ordinary contract usage: a member confirms a pending request created by someone else, and is later removed via a normal `DeleteMember` request (no special privilege beyond being a legitimate multisig operation). No malicious deployment, redeploy, or external actor is needed — it's a straightforward sequencing of otherwise-valid operations that any set of members would naturally perform (confirm requests, later rotate/remove a member).

### Recommendation
When removing a member in `delete_member` (and `DeleteKey` in the v1 `multisig` contract), iterate over `self.requests`/`self.confirmations` for *all* pending requests (not just ones authored by the removed member) and strip the removed member's identity from each confirmation set. Alternatively/additionally, have `confirm()` recompute the count by intersecting the stored confirmation set with `self.members` (i.e., `confirmations.iter().filter(|m| self.members.contains(m)).count()`) before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `D` calls `add_request` creating request `R` (e.g. a `Transfer`).
3. `A` calls `confirm(R)` → `confirmations[R] = {A}`.
4. `B` calls `confirm(R)` → `confirmations[R] = {A, B}` (2 < 3, not yet executed).
5. Separately, members execute a `DeleteMember{member: A}` request (requires 3 confirmations from `{A,B,C,D}`, achievable without touching `R`). `delete_member` removes `A` from `self.members` and only purges requests where `r.member == A` — `R` was authored by `D`, so its confirmations (`{A, B}`) are left intact.
6. Members are now `{B, C, D}`; `num_confirmations` is still 3.
7. `C` calls `confirm(R)` → `confirmations.len() == 2` (`{A,B}`) `+ 1 == 3 >= num_confirmations (3)` → the request executes, even though only `B` and `C` are actual live-member approvals (2 of 3 current members), because `A`'s stale confirmation was never scrubbed. [5](#0-4)
