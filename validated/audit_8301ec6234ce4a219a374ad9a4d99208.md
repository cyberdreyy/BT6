### Title
Unstaked balance is debited from the internal ledger before NEAR delivery is confirmed, with no callback/refund on transfer failure - ([File: staking-pool/src/internal.rs])

### Summary
The `staking-pool` contract's `internal_withdraw` function decrements a user's accounted `unstaked` balance and the contract-wide `last_total_balance` immediately, then fires an unattached `Promise::new(account_id).transfer(amount)` with no `.then()` callback to verify the transfer succeeded. This breaks the same "value debited vs. value delivered" binding described in the WeVE (M-17) analog: the ledger commits to having paid the user before the actual payment is confirmed, and there is no path to detect failure or refund the user's claim if the outgoing transfer receipt fails.

### Finding Description
`internal_withdraw` in `staking-pool/src/internal.rs` performs the debit synchronously and unconditionally: [1](#0-0) 

```
account.unstaked -= amount;
self.internal_save_account(&account_id, &account);
...
Promise::new(account_id).transfer(amount);
self.last_total_balance -= amount;
```

There is no `.then(ext_self::on_withdraw(...))` callback, unlike every other cross-contract state transition in this same codebase that touches money or shares. For comparison, the sibling method `internal_restake` in the very same file attaches a callback and checks the promise result before making further state changes: [2](#0-1) 

Likewise, `lockup/src/owner_callbacks.rs`'s `on_staking_pool_withdraw`, `lockup-factory`'s `on_lockup_create`, and `staking-pool-factory`'s `on_staking_pool_create` all follow the pattern of: (1) issue promise, (2) attach callback, (3) call `is_promise_success()`, (4) only commit the state change (or refund) once the promise result is known: [3](#0-2) [4](#0-3) 

`internal_withdraw`, by contrast, commits the debit unconditionally at the time the `Promise` is *scheduled*, not after it is known to have succeeded. The invariant that should hold is:

`account.unstaked_before - account.unstaked_after == amount actually transferred to account_id`

If the outgoing `Transfer` action fails at execution (e.g. the contract's genuinely liquid/non-staked balance is insufficient to cover `amount` at the point the receipt executes — which can occur because `last_total_balance`/`account.unstaked` is an internally tracked accounting value that is not atomically reconciled against `env::account_balance()` at withdrawal time, and because staking/restaking activity via `internal_restake` can lock up the account's real balance between the time a user's `unstaked` entry is credited and the time they call `withdraw`), the ledger has already been permanently decremented (`account.unstaked -= amount`, `self.last_total_balance -= amount`) while the user receives zero NEAR. There is no callback that would catch this and restore `account.unstaked`, so the tokens are non-recoverable — the same "recorded claim vs. asset actually held" violation as the WeVE report, just manifesting on the NEAR side of the ledger rather than via LayerZero retries.

### Impact Explanation
This crosses the "value debited vs. value delivered" boundary called out in the rules. If the transfer fails, the user's recorded claim (`account.unstaked`) is destroyed without the corresponding NEAR being delivered, and `last_total_balance` is decremented as if the payout succeeded, permanently understating the pool's true obligations (an accounting value diverging from reality that other validators/delegators settle on, since `last_total_balance` feeds directly into reward distribution in `internal_ping`). This qualifies as Critical impact per the rubric ("claims exceeding assets held" / funds permanently frozen for the affected user) since the loss is unrecoverable and no owner/foundation/redeploy action is required to trigger or fix it after the fact.

### Likelihood Explanation
This is triggerable by any unprivileged staking-pool delegator simply by calling `withdraw`/`withdraw_all` — no owner, foundation, multisig member, or malicious validator is required. The precondition (outgoing transfer receipt failing due to the contract's real liquid balance being less than its internally tracked `last_total_balance`/`unstaked` sum) is a design gap rather than a common everyday occurrence, so likelihood is bounded by how often the pool's liquid balance and internal accounting diverge (e.g., through repeated stake/restake cycles, reward rounding, or the guarantee fund being drawn down) — but the code path itself has zero protection when it does happen.

### Recommendation
Mirror the pattern already used elsewhere in this codebase (`lockup/src/owner_callbacks.rs::on_staking_pool_withdraw`, `staking-pool-factory::on_staking_pool_create`): attach a `.then()` callback to the `Promise::new(account_id).transfer(amount)` call in `internal_withdraw`, use `is_promise_success()` in that callback, and only decrement `account.unstaked` / `self.last_total_balance` (or restore them on failure) once the transfer's outcome is known.

### Proof of Concept
Conceptual sequence (analog to the WeVE report's PoC, expressed in this repo's terms):
1. A delegator unstakes and, after the unstaking delay, has `account.unstaked = X` recorded via `internal_get_account`/`internal_save_account`.
2. Delegator calls `withdraw(X)` (or `withdraw_all`) — `staking-pool/src/lib.rs::withdraw` → `internal_withdraw`.
3. `internal_withdraw` immediately sets `account.unstaked -= X` and `self.last_total_balance -= X`, then fires `Promise::new(account_id).transfer(X)` with no callback: [5](#0-4) 
4. If that outgoing transfer receipt fails at execution (contract's real spendable balance < X at that point), the NEAR is never delivered to `account_id`.
5. Because there is no `.then()` callback checking `is_promise_success()`, the contract state is never rolled back — `account.unstaked` remains decremented and the delegator has permanently lost their claim to `X` NEAR with no refund path, exactly analogous to the WeVE tokens being burned/consumed while the corresponding USDC+VELO redemption reverted with no refund in the original report.

    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }
