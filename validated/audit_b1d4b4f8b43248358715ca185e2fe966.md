### Title
Cross-user response hijacking via unauthenticated messageId collision in `handler.savedCallbacks` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`NewHandler`'s `HandleLegacyUserMessage` stores the caller's response callback in a map keyed solely by the attacker/client-supplied `msg.Body.MessageId`, with no check that the ID is unique or that the same signer originally owns it. Any external client can register (or re-register) a callback under a `messageId` that collides with another party's in-flight trigger, capturing whatever node response ultimately arrives for that ID instead of the legitimate requester.

### Finding Description
`HandleLegacyUserMessage` unconditionally writes to the shared map without checking for an existing entry: [1](#0-0) 

The only correlation used when a node later responds is the bare `MessageId` string, matched in `handleWebAPITriggerMessage`, which looks up, deletes, and immediately forwards the raw node response to whichever callback is currently stored under that ID — with no verification that the responding message's signer/session corresponds to the original requester who registered the callback: [2](#0-1) 

Because `CallbackMaxAgeSec` (a "grace window", default 120s) keeps entries alive until pruning or until a first response is consumed, an attacker who knows or can predict a victim's `messageId` (or who reuses their own prior ID before it is pruned) can submit a new `HandleLegacyUserMessage` call with the identical `MessageId` during that window. This overwrites the map entry, so the next node response tagged with that `MessageId` — which may be a legitimate response en route for the original requester — is delivered to the attacker's callback instead. `pruneCallbacks` only removes stale entries by age/pressure and does nothing to prevent this overwrite: [3](#0-2) 

There is no signer binding, no per-sender namespacing, and no duplicate-ID rejection anywhere in this path, so the invariant "the response returned to a user is the one that corresponds to their own verified request" does not hold.

### Impact Explanation
An unprivileged internet client sending signed gateway requests can hijack another user's Web API trigger response (or inject their own crafted node responses into another party's callback context) purely by colliding `MessageId` values within the callback grace window. This is a cross-user response confusion vulnerability: sensitive oracle job output intended for one workflow/user can be delivered to an unrelated attacker, and/or the legitimate user's expected response can be dropped/never obtained by the rightful requester once its callback slot is overwritten.

### Likelihood Explanation
Exploitability requires only that the attacker know or predict a `MessageId` in current use — no operator, admin, node, or DON privilege is needed, matching the "any internet client with an arbitrary externally-owned key" attacker model. If `MessageId`s used by real workflows are derived from public/predictable values (e.g., deterministic trigger event IDs, timestamps, or values echoed in logs), collision is straightforward and repeatable within the `CallbackMaxAgeSec` window (default 120s).

### Recommendation
Bind saved callbacks to the original requester's identity (e.g., verified signer address) in addition to `MessageId`, reject `HandleLegacyUserMessage` calls that attempt to reuse an already-registered `MessageId` (return an error instead of overwriting), and validate on response delivery that the responding node message correlates to the same request context (DonId + sender + messageId tuple) that was originally saved.

### Proof of Concept
Go handler-level test plan (extends `handler_test.go`):
1. Call `handler.HandleLegacyUserMessage` for "victim" with `MessageId = "shared-id"` and a mock `handlers.Callback` (`victimCB`) expecting `SendResponse` to be invoked once.
2. Before any node responds, call `handler.HandleLegacyUserMessage` again with the same `MessageId = "shared-id"` but a different signed sender, supplying a mock `handlers.Callback` (`attackerCB`).
3. Simulate a DON node response via `handler.HandleNodeMessage` with `MessageId = "shared-id"` corresponding to the victim's original trigger.
4. Assert that `attackerCB.SendResponse` is called with the victim's response payload and `victimCB.SendResponse` is never called — demonstrating the map entry was overwritten and the response was misdirected to the attacker within the `CallbackMaxAgeSec` grace window.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

	}
	return nil
}

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}
