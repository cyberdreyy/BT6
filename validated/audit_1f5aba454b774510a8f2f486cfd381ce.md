### Title
Cache STS/SAS credentials in `GoCloudURL.Environment` are excluded from trace masking and can be leaked via `CI_DEBUG_TRACE` - ([File: shells/abstract.go])

### Summary
`getCacheDownloadURLAndEnv`/`getCacheUploadURLAndEnv` in `shells/abstract.go` pass the short-lived AWS STS credentials (from `s3Adapter.GetGoCloudURL` → `FetchCredentialsForRole`) or Azure SAS token (from `azureAdapter.getEnv`) into `writeCacheExports`, which writes them as literal plaintext via `ShellWriter.DotEnvVariables` directly into the generated job script. These values are never added to the job's `spec.Variable{Masked: true}` set, so they are absent from the trace logger's mask list built once in `Build.getNewLogger` (`MaskPhrases: b.GetAllVariables().Masked()`, `common/build.go:1642`).

### Finding Description
The exploitable path:

1. `shells/abstract.go:addCacheUploadCommand` (and `addExtractCacheCommand`) call `getCacheUploadURLAndEnv`/`getCacheDownloadURLAndEnv`, which invoke `adapter.GetGoCloudURL(ctx, upload)`. [1](#0-0) 
2. For S3 with `RoleARN`/`UploadRoleARN`, `s3Adapter.GetGoCloudURL` calls `FetchCredentialsForRole`, returning `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN` in `goCloudURL.Environment`. [2](#0-1) 
For Azure, `azureAdapter.getEnv` returns `AZURE_STORAGE_SAS_TOKEN` in the same map. [3](#0-2) 
3. `addCacheUploadCommand`/`addExtractCacheCommand` pass that `env` map to `b.writeCacheExports(w, env)`, which calls `w.DotEnvVariables(...)`. [4](#0-3) 
4. `BashWriter.DotEnvVariables` emits the credentials as a literal `cat << EOF > file ... EOF` heredoc directly embedded in the generated shell script text (not through `Variable()`, and not run through any redaction). [5](#0-4) 
5. Separately, the trace/log masking list is computed **once**, at job start, purely from `b.GetAllVariables().Masked()` — i.e., only variables explicitly flagged `Masked: true` by GitLab (CI/CD variables, secrets, job token, etc.). The dynamically-fetched cache credentials are generated later during script construction and are never registered as masked phrases. [6](#0-5) 
6. If the job author sets `CI_DEBUG_TRACE=true` (an ordinary, user-controlled CI/CD variable, validated only by `validateDebugTraceSettings`/`IsDebugTraceEnabled`, not admin-gated unless the runner operator explicitly sets `DebugTraceDisabled`), the generated script enables `set -o xtrace`, causing every line of the script — including the `cat << EOF ... AWS_SESSION_TOKEN="..." ... EOF` heredoc written by `writeCacheExports` — to be echoed with a `+`/`++` prefix into stdout, which becomes the job trace. [7](#0-6) 
Existing tests confirm `xtrace` causes literal export/echo lines to appear in the trace verbatim (e.g. `++ export CI_RUNNER_SHORT_TOKEN=` style output for ordinary exported vars). [8](#0-7) 
7. Because the masker (`common/buildlogger/internal/masker`) only replaces phrases present in `l.maskPhrases`, and the STS/SAS values were never included there, the xtrace echo of these values passes through unmasked. [9](#0-8) 

This differs from the vulnerability's second half — cross-tenant scope of the AWS role — which appears well mitigated: `FetchCredentialsForRole` calls `generateSessionPolicy(bucketName, objectName, upload)` and passes the resulting narrow session `Policy` to `AssumeRole`, scoping the temp credentials to the specific project's cache object rather than the whole bucket. That part of the described threat is not substantiated by the code; no broken ARN/object-path scoping was found. The masking gap is the concrete, reachable bug.

### Impact Explanation
Any pipeline author (not just an admin) who sets `CI_DEBUG_TRACE=true` on a job that also uses `cache:` with S3 `RoleARN`/`UploadRoleARN` or Azure GoCloud cache backends will have the short-lived STS/SAS credentials for their own project's cache object printed in cleartext to the job log/trace. Because logs can be exported, cached, or scraped by anyone with read access to job logs (which may be broader than access to the runner's cache config), this converts an internal short-lived credential into a persistently-viewable secret for the credential's remaining validity window (up to the STS session's ~1 hour, or the SAS token's configured lifetime). Since these credentials are scoped to a specific object/ARN (based on `generateSessionPolicy`), the practical impact is limited to that job's own cache object rather than cross-project data — but it is still a clear violation of the stated invariant "cache credentials from `GoCloudURL.Environment` must be masked in traces," and it defeats the very purpose of using short-lived, narrowly scoped credentials instead of long-lived static keys (an attacker with log access gets a working credential without needing runner or cloud-provider access).

### Likelihood Explanation
- Preconditions: runner configured with S3 cache + `RoleARN`/`UploadRoleARN`, or Azure cache; `DebugTraceDisabled` not set by the runner operator (this is the default).
- Attacker action: an ordinary pipeline author sets `CI_DEBUG_TRACE: "true"` in `.gitlab-ci.yml` or as a job variable — no elevated privilege required, and this is officially documented/supported functionality.
- Trigger: cache push (`addCacheUploadCommand`) or pull (`addExtractCacheCommand`) stage runs.
- Repeatable: deterministic; will occur on every cache stage run with debug tracing enabled.

### Recommendation
Add every value from `GoCloudURL.Environment` (and any other dynamically fetched cache credential map) to the trace logger's mask-phrase list before executing the cache stages — e.g., have `addCacheUploadCommand`/`addExtractCacheCommand` call something like `info.Build.MaskValues(env values...)` or otherwise push the values through the same masking pipeline used for `spec.Variable{Masked:true}`, prior to writing them into the script. Alternatively, avoid embedding raw secret values into script text at all when `CI_DEBUG_TRACE` may be enabled — e.g., write the values through a mechanism (`w.Variable` with an existing masked/no-echo primitive, or via stdin/`--env-file` piping outside of `xtrace`'d script body) that is never echoed by `set -o xtrace`.

### Proof of Concept
Go integration test (extending `common/buildtest/masking.go` pattern):
```go
func TestCacheCredentialsMaskedUnderDebugTrace(t *testing.T) {
    // 1. Configure runner with S3 cache backend using RoleARN pointing at a
    //    mock STS server (as in cache/s3v2/s3_test.go newMockSTSHandler),
    //    returning known AWS_SESSION_TOKEN="LEAK-ME-TOKEN".
    // 2. Build a job with:
    //      Cache: [{Key: "k", Paths: []string{"foo"}}]
    //      Variables: [{Key:"CI_DEBUG_TRACE", Value:"true"}]
    // 3. Run build.Run(ctx, cfg, trace) capturing trace output (as in
    //    buildtest.testBuildWithMasking).
    // 4. Assertions:
    assert.NotContains(t, traceOutput, "LEAK-ME-TOKEN")          // currently FAILS: token appears in xtrace output
    assert.Contains(t, traceOutput, "[MASKED]")                   // expected masked marker
}
```
This should currently fail (proving the bug): with `CI_DEBUG_TRACE=true`, the `cat << EOF ... AWS_SESSION_TOKEN="LEAK-ME-TOKEN" ... EOF` line from `writeCacheExports`/`DotEnvVariables` is echoed verbatim by `set -o xtrace` and is not present in `b.GetAllVariables().Masked()`, so the masker never redacts it.

	env := map[string]string{

		"AZURE_STORAGE_DOMAIN":  a.config.StorageDomain,

	}

func (b *BashWriter) DotEnvVariables(baseFilename string, variables map[string]string) string {
	dotEnvFile := b.TmpFile(baseFilename)

	var sb strings.Builder
	fmt.Fprintf(&sb, "cat << EOF > %s\n", dotEnvFile)
	sb.WriteString(helpers.DotEnvEscape(variables))

	b.Line(sb.String())

	return dotEnvFile

func (b *Build) validateDebugTraceSettings() []error {

		return errs

		errs = append(errs, fmt.Errorf("CI_DEBUG_SERVICES: usage is disabled on this Runner"))

	b.buildSettings.CIDebugTrace = false
	b.buildSettings.CIDebugServices = false

	return errs
}

func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
	if l.timestamping {
		w = timestamper.New(w, timestamper.StreamType(streamType), uint8(streamID), true)
	}

	w = tokensanitizer.New(w, l.maskTokenPrefixes)
	w = urlsanitizer.New(w)
	w = masker.New(w, l.maskPhrases)
	w = internal.NewSync(w)

	return w
}
