### Title
Unbounded ERC4626 deposit in `onStartEpoch` lets a vault depositor temporarily freeze the pool - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.onStartEpoch` deposits the borrower's entire idle ERC20 balance into the configured ERC4626 vault in a single call. There is no `maxDeposit` check, partial deposit, or fallback path that leaves excess funds idle. An unprivileged user of the external vault can consume its remaining deposit capacity before `IdleCDOEpochVariant.startEpoch`, causing `vault.deposit` to revert and making the epoch-start transaction terminate without changing state.

### Finding Description
`onStartEpoch` snapshots the borrower's total assets, then passes `underlyingToken.balanceOf(address(this))` to `_depositToVault`. `_depositToVault` unconditionally calls `vault.deposit(_assetAmount, address(this))` for the full amount. [1](#0-0) [2](#0-1) 

`IdleCDOEpochVariant.startEpoch` calls this hook through `_startEpochProgrammableBorrower` after funding accounting has already begun. Because hook reverts are not caught on the start path, any ERC4626 deposit revert aborts `startEpoch` and leaves `isEpochRunning` false. [3](#0-2) [4](#0-3) 

An ERC4626 depositor can force this condition whenever:

```text
0 < vault.maxDeposit(programmableBorrower)
    < ProgrammableBorrower.underlyingToken.balanceOf(programmableBorrower)
```

For example, if a capacity-limited vault initially has enough room for the borrower’s `X` idle assets, the attacker deposits enough of their own assets to leave only `X - 1` capacity. The next `startEpoch` tries to deposit all `X`, reverts inside the ERC4626 vault, and aborts. The attacker can repeat the deposit whenever capacity reopens, extending the freeze.

### Impact Explanation
The borrower’s entire idle pool balance is temporarily frozen in the buffer phase. In the tested configuration this can be the full pool NAV not already represented by matured withdraw receipts. No deposit, borrower draw, epoch interest settlement, or new withdrawal-request lifecycle can proceed until a `startEpoch` call succeeds.

The attacker does not need a privileged role in Idle Tranches or the external vault. They only need the ability allowed by the vault’s public ERC4626 interface to deposit assets and consume deposit capacity. The attack freezes an amount equal to `underlyingToken.balanceOf(programmableBorrower)` each time it prevents the epoch from opening.

### Likelihood Explanation
The attack is feasible for ERC4626 integrations with public deposits and a finite `maxDeposit`, supply cap, allocation cap, or market-capacity limit. The attacker needs enough underlying to reduce remaining capacity below the borrower’s idle balance and may need to repeat the action after capacity expands. Neither KYC status in Idle Tranches nor ownership of the borrower contract is required.

The current code intentionally treats ERC4626 liquidity failures at `stopEpoch` as retryable, but the analogous deposit-capacity failure at `startEpoch` is also bubbled while leaving the pool unable to advance. [5](#0-4) 

### Recommendation
Cap the epoch-start deposit to the vault’s currently available capacity and retain the remainder as idle on-hand assets. For example:

```solidity
uint256 idle = underlyingToken.balanceOf(address(this));
uint256 capacity = vault.maxDeposit(address(this));
uint256 depositAmount = idle < capacity ? idle : capacity;
_depositToVault(depositAmount, 0);
```

Use `previewDeposit` or guarded error handling where the vault may expose inconsistent `maxDeposit` behavior. Ensure subsequent calls can retry the residual deposit, and include idle cash in `totalUnderlying`, `availableToBorrow`, and stop-epoch liquidity accounting, as those functions already do. [6](#0-5) [7](#0-6) 

### Proof of Concept
A Foundry fork test can reproduce this against a production ERC4626 vault with finite deposit capacity:

```solidity
function testExternalVaultDepositorBlocksEpochStart() external {
    vm.createSelectFork(vm.envString("MAINNET_RPC_URL"), FORK_BLOCK);

    uint256 amount = 10_000 * oneScale;
    deal(USDC, address(this), amount);
    IERC20Detailed(USDC).approve(address(idleCDO), amount);
    idleCDO.depositAA(amount);

    // Funds are sent to ProgrammableBorrower during the buffer phase.
    uint256 idleAmount = IERC20Detailed(USDC).balanceOf(address(programmableBorrower));
    assertGt(idleAmount, 0);

    IERC4626 externalVault = programmableBorrower.vault();
    uint256 capacity = externalVault.maxDeposit(address(programmableBorrower));

    // Integration precondition: the vault could initially accept the full idle balance.
    assertGe(capacity, idleAmount);

    // Unprivileged vault user consumes capacity until only idleAmount - 1 remains.
    uint256 attackerDeposit = capacity - idleAmount + 1;
    deal(USDC, attacker, attackerDeposit);
    vm.startPrank(attacker);
    IERC20Detailed(USDC).approve(address(externalVault), attackerDeposit);
    externalVault.deposit(attackerDeposit, attacker);
    vm.stopPrank();

    assertLt(externalVault.maxDeposit(address(programmableBorrower)), idleAmount);

    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);

    vm.expectRevert();
    vm.prank(manager);
    cdoEpoch.startEpoch();

    assertFalse(cdoEpoch.isEpochRunning());
    assertEq(
        IERC20Detailed(USDC).balanceOf(address(programmableBorrower)),
        idleAmount,
        "idle pool NAV remains trapped"
    );
}
```

The same sequence succeeds if the attacker does not consume capacity, isolating the failure to the uncapped full-balance `vault.deposit` call rather than borrower insolvency or an Idle Tranches privileged action.
