### Title
Distinguishable login error messages in `localLoginFallback` enable user-email enumeration via `POST /sessions` - ([File: core/sessions/oidcauth/oidc.go])

### Finding Description
`oidcAuthenticator.localLoginFallback` first looks up the user by email with `oi.ds.GetContext(ctx, &user, SQLSelectUserbyEmail, sr.Email)` and, if the email does not exist, immediately returns the raw SQL error (e.g. `sql.ErrNoRows`) without any audit event. [1](#0-0) 
If the email exists but does not exactly match (a redundant constant-time check after the query already filtered `lower(email) = lower($1)`), it audits `audit.AuthLoginFailedEmail` and returns `errors.New("invalid email")`. [2](#0-1) 
If the email matches but the password hash check fails, it audits `audit.AuthLoginFailedPassword` and returns `errors.New("invalid password")`. [3](#0-2) 

The HTTP handler `SessionsController.Create` in `core/web/sessions_controller.go` calls `CreateSession`, and on any error simply forwards the raw `err` (whose `.Error()` text is one of the three distinct messages above) into the response via `jsonAPIError(c, http.StatusUnauthorized, err)`. [4](#0-3) 

Because the underlying error text differs between "unknown email" (raw SQL error text), "invalid email" (mismatch after lookup — practically unreachable given the case-insensitive query, but still a distinct code path/message), and "invalid password" (valid email, wrong password), an unauthenticated attacker submitting `POST /sessions` with different emails can distinguish whether a given email exists in the `users` table purely from the HTTP response body, even though the HTTP status code (`401`) is identical in all cases. This directly violates the required invariant that login failure responses must not reveal which credential half was wrong.

### Impact Explanation
This is a **user enumeration** vulnerability (email/account existence disclosure), which is a low-to-moderate severity information-disclosure issue under standard authentication soundness/bounty impact taxonomies. It does not itself grant credential bypass, session hijack, or fund movement, but it materially assists credential-stuffing and targeted-phishing/brute-force campaigns against confirmed valid Chainlink Node operator/admin accounts by letting an attacker cheaply confirm which emails are registered on a node's local-admin login endpoint.

### Likelihood Explanation
No privileges are required — this is reachable by any unauthenticated client capable of sending `POST /sessions` requests to the node's Operator UI/API. It is fully deterministic and repeatable: sending the same wrong password against a known-valid email versus a random/unknown email will consistently produce different error text in the response body, and this behavior does not depend on timing side channels, race conditions, or any special configuration beyond `localLoginFallback` being reachable (i.e., the OIDC authenticator's local-admin fallback path, which is the default/always-available local-login mechanism for `POST /sessions`).

### Recommendation
Return a single generic error (e.g., `errors.New("invalid credentials")`) and a single generic audit event for both the "email not found" and "password mismatch" branches of `localLoginFallback`, ensuring identical error text/response body regardless of which check failed. Apply the same generic-message treatment for the raw `sql.ErrNoRows` path so an unregistered email produces byte-identical error output to a known email with a wrong password. Consider auditing the specific failure reason server-side only (not surfaced in the HTTP response) for internal forensic purposes.

### Proof of Concept
Table-driven Go test plan against `SessionsController.Create` (handler-level integration test using `cltest` test app, mirroring the existing pattern in `core/web/sessions_controller_test.go`):
1. Seed one known local admin user (`known@example.com` / `correct-password`).
2. Case A: `POST /sessions` with `{"email": "unknown@example.com", "password": "whatever"}`.
3. Case B: `POST /sessions` with `{"email": "known@example.com", "password": "wrong-password"}`.
4. Assert both requests return `401 Unauthorized`.
5. Assert the response bodies are **not** identical today (proving the bug): Case A currently surfaces a SQL/"user not found"-style message while Case B surfaces `"invalid password"`; after the fix, both should return the same generic `"invalid credentials"` (or equivalent) body — the test should assert body equality as the target/fixed-state behavior.
6. Additionally unit-test `oidcAuthenticator.localLoginFallback` directly with (a) an unknown email and (b) a known email/wrong password, asserting `err.Error()` is identical in both cases and that the audited event type does not differ in a way observable by the caller.

func (oi *oidcAuthenticator) localLoginFallback(ctx context.Context, sr clsessions.SessionRequest) (clsessions.User, error) {
	var user clsessions.User
	err := oi.ds.GetContext(ctx, &user, SQLSelectUserbyEmail, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		oi.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}
