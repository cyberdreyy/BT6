### Title
`base_meterBundle`/`base_meterBlockByHash`/`base_meterBlockByNumber` RPC error responses leak unsanitized internal error details to any anonymous caller - (File: `crates/execution/metering/src/rpc.rs`)

### Summary
The `base`-namespace metering RPC handlers embed the raw `Display` output of internal provider/database/EVM errors directly into the JSON-RPC error `message` field returned to the caller, instead of returning a generic, sanitized error like most other RPC modules in this codebase do.

### Finding Description
`MeteringApiImpl` implements `meter_bundle`, `meter_block_by_hash`, `meter_block_by_number`, and the internal helper `get_l1_block_info`/`meter_block_internal`. On failure, each of these formats the underlying error (`e`) with `{e}` interpolation straight into the RPC error message returned to the client: [1](#0-0) [2](#0-1) [3](#0-2) 

This is the same anti-pattern the JSPUI advisory describes: unsanitized internal exception detail is passed straight through to an untrusted, externally-reachable interface. In this codebase, other RPC surfaces deliberately avoid this — e.g. the admin RPC redacts sequencer/internal errors into a generic `InternalError`: [4](#0-3) 

and the audit RPC explicitly logs the real error server-side but returns only `"internal server error"` to the caller: [5](#0-4) 

The metering RPC methods are registered under the public `base` namespace: [6](#0-5) 

and are explicitly exposed to unauthenticated/"client"-tier RPC callers in the reference proxy configuration: [7](#0-6) 

so any anonymous eth JSON-RPC client can trigger these code paths (e.g. by submitting a bundle referencing a nonexistent/malformed block, or crafting a bundle that fails deep inside block execution) and receive the verbatim internal error text (database/provider error strings, EVM execution failure internals, `anyhow`/`eyre` error chains) in the JSON-RPC response.

### Impact Explanation
While this does not directly cause fund loss, this is a direct CWE-209 information-disclosure analog of the reported bug class: internal implementation details (provider/database error text, internal error type names, potentially internal file/state identifiers surfaced through error `Display` implementations) are returned unsanitized to an anonymous, network-reachable caller. This information can help an attacker fingerprint internals and craft more targeted follow-on attacks against the node, which is exactly the risk articulated in the source advisory (Medium, CWE-209).

### Likelihood Explanation
High likelihood of triggering: the `base_meterBundle`, `base_meterBlockByHash`, and `base_meterBlockByNumber` methods are reachable by any RPC client with no authorization, and error paths (missing block, malformed bundle, execution failures) are easy to hit with everyday malformed/edge-case input.

### Recommendation
Mirror the pattern already used elsewhere in the codebase (`crates/consensus/rpc/src/admin.rs`, `crates/infra/audit/src/rpc.rs`): log the full error server-side with `error!`/`tracing`, but return a generic, sanitized `ErrorObjectOwned` (e.g. `ErrorCode::InternalError` with a fixed message) to the RPC caller for all internal/provider/execution failure branches in `crates/execution/metering/src/rpc.rs`. Preserve distinct, safe messages only for legitimately client-facing validation errors (e.g., "Block not found").

### Proof of Concept
1. Start a Base node with the metering extension enabled and RPC exposed (as in the reference `proxyd.toml`, `base_meterBundle`/`base_meterBlockByHash`/`base_meterBlockByNumber` are `client`-tier, i.e., unauthenticated).
2. As an anonymous RPC client, call `base_meterBlockByHash` with a hash that triggers a provider-level error (or `base_meterBundle` with a bundle that fails deep in block metering/execution).
3. Observe the JSON-RPC error response's `message` field contains the raw `{e}`-formatted internal error string, e.g. `"Failed to get block: <raw provider error>"` or `"Block metering failed: <raw evm/execution error>"`, as constructed in `crates/execution/metering/src/rpc.rs` lines 259-309 and 94-109.

/// Maps public sequencer admin failures without exposing internal details.
fn sequencer_admin_error(error: SequencerAdminAPIError) -> ErrorObject<'static> {
    match error {
        SequencerAdminAPIError::NotLeader => {
            ErrorObject::owned(-32002, "Node is not the conductor leader.", None::<()>)
        }
        SequencerAdminAPIError::RequestError(_)
        | SequencerAdminAPIError::ResponseError
        | SequencerAdminAPIError::ErrorAfterSequencerWasStopped(_)
        | SequencerAdminAPIError::LeaderOverrideError(_) => {
            ErrorObject::from(ErrorCode::InternalError)
        }
    }
}
