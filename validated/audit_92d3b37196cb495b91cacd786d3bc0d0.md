### Title
Zero-price rounding revert inside `stopEpoch`'s try block forces a solvent borrower into `defaulted` and strands repaid funds to `feeReceiver` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2016-4957 (a single anomalous unauthenticated packet crashes the ntpd daemon), a single anomalous `stopEpochWithDuration` input — a near-total `_lossAmount` while `pendingWithdraws` is large — hits a rounding edge in `collectWithdrawFunds` that reverts *inside* the try block of `_stopEpoch`. The catch clause treats this as a borrower default: `defaulted = true`, the pool pauses, all withdraw requests close, and the borrower repayment that was already pulled into the CDO is stranded. At `finalizeDefault`, `_skimDonatedAssets` sweeps that stranded repayment to `feeReceiver` instead of into the recovery reserve.

### Finding Description
`IdleCreditVault.collectWithdrawFunds` computes a per-epoch haircut when the funded amount is less than the pending basis, and deliberately reverts when the price rounds to zero:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:414-421
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
// Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
if (lossRecoveryPrice == 0) revert NotAllowed();
```

The intended guard for a *total* loss lives earlier, in `previewLossAdjustedWithdrawFunds` (`_lossAmount >= totalBasis` reverts), which is called *outside* the try block in `_stopEpoch`, so it aborts cleanly. But there is a dead band: `previewLossAdjustedWithdrawFunds` floors `pendingLoss = _lossAmount * pendingBasis / totalBasis`, so `pendingToFund` is always ≥ 1 when `_lossAmount < totalBasis`. When `pendingBasis > 1e18` and `_lossAmount` lies in the narrow band just below `totalBasis` (width ≈ `totalBasis / pendingBasis`), `pendingToFund` becomes `1 … pendingBasis/1e18 − 1`, making `lossRecoveryPrice` equal 0.

`collectWithdrawFunds` is invoked *inside* the try block in `IdleCDOEpochVariant._stopEpoch` (line 410), after `getFundsFromBorrower` has already pulled `_amountToPullFromBorrower + _pendingWithdraws` from the borrower into the CDO. The revert is caught and routed to `_handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws)`, which sets `defaulted = true`, pauses the vault, and disables all withdraw requests — even though the borrower repaid successfully.

The pulled cash remains as raw underlying on the CDO. When the honest owner/manager later calls `finalizeDefault`, the first thing it does is `_skimDonatedAssets()`, which sends the CDO's entire raw underlying balance to `feeReceiver` (lines 196-199). That repaid interest/principal is therefore never added to `defaultRecoveryReserve` and is permanently diverted away from tranche holders and receipt claimants. `defaulted` can never be cleared, and `finalizeDefault` sets `epochDuration = 0` / `epochEndDate = 0`, permanently closing the pool — the "daemon crash".

### Impact Explanation
- The repaid epoch interest (and any other underlying sitting on the CDO) is skimmed to `feeReceiver` during `finalizeDefault` — a direct loss of yield owed to AA/BB LPs and receipt holders, quantified as `_expectedInterest + pendingToFund` plus any residual CDO balance.
- The recovery basis (`activeBasis + pendingBasis`) is left undercollateralized by exactly the skimmed amount, so every claimant's `defaultRecoveryPrice` is lower than it should be.
- The pool is permanently shut down (`defaulted` is irreversible; `epochDuration = 0` after finalization) despite the borrower having honored the recall — a permanent freeze of the vault's normal operation.

### Likelihood Explanation
Triggering requires `pendingWithdraws > 1e18` in underlying units at the moment of a near-total-loss `stopEpochWithDuration`. For a 6-decimal underlying (USDC) that is >1e12 USDC pending — unrealistic. For an 18-decimal underlying (the strategy accepts any `IERC20Detailed` token), ~2 whole tokens of pending receipts suffice, which a single unprivileged KYC-passed lender can create by depositing and calling `requestWithdraw`. The manager then only needs to pass a `_lossAmount` in the integer band `[totalBasis − totalBasis/pendingBasis, totalBasis)` — i.e., a genuinely near-total loss where the borrower repaid only a few wei — which is a realistic input for a distressed stop. The attacker supplies the pending-basis precondition; the honest manager's ordinary loss-stop supplies the trigger, consistent with the "sequence around honest privileged calls" rule.

### Recommendation
Move the `collectWithdrawFunds` call out of the try/catch (or precompute and validate `lossRecoveryPrice` inside `previewLossAdjustedWithdrawFunds` so a zero price reverts *before* borrower funds are pulled). Additionally, route already-pulled underlying held by the CDO into `defaultRecoveryReserve` (or back to the strategy) inside `_handleBorrowerDefault`, rather than leaving it skimmable as a donation by `finalizeDefault`.

### Proof of Concept
Foundry fork PoC outline (18-decimal underlying assumed; for 6-decimal underlyings, scale the deposit above 1e18 raw units):

```solidity
function testZeroPriceStopForcedDefault() external {
    // 1. KYC'd attacker deposits ~2 tokens and requests a withdrawal,
    //    creating pendingWithdraws = ~2e18 (> 1e18).
    deal(address(underlying), attacker, 2e18);
    vm.startPrank(attacker);
    idleCDO.depositAA(2e18);
    idleCDO.requestWithdraw(AAtranche.balanceOf(attacker), address(AAtranche));
    vm.stopPrank();
    uint256 pendingBasis = strategy.pendingWithdraws();   // > 1e18

    // 2. Epoch runs; borrower suffers a near-total loss. Manager calls
    //    stopEpochWithDuration with _lossAmount = totalBasis - 1, the unique
    //    integer that makes pendingToFund = 1 while passing the < totalBasis guard.
    uint256 totalBasis = /* activeBasis + pendingBasis, mirrored from previewLossAdjustedWithdrawFunds */;
    // borrower approves repayment of expectedInterest + pendingToFund (=1)
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, duration, totalBasis - 1);

    // 3. collectWithdrawFunds(1) computed lossRecoveryPrice = 1e18 / pendingBasis = 0
    //    -> revert inside try -> catch -> _handleBorrowerDefault
    assertTrue(cdoEpoch.defaulted());          // solvent borrower marked defaulted
    assertTrue(cdoEpoch.paused());
    uint256 stranded = underlying.balanceOf(address(cdoEpoch));
    assertGt(stranded, 0);                     // pulled repayment stranded on CDO

    // 4. finalizeDefault skims the stranded repayment to feeReceiver
    uint256 feeRecvPre = underlying.balanceOf(cdoEpoch.feeReceiver());
    vm.prank(owner);
    cdoEpoch.finalizeDefault(recovered, recoverySource);
    assertEq(underlying.balanceOf(cdoEpoch.feeReceiver()), feeRecvPre + stranded);
    assertEq(strategy.defaultRecoveryReserve(), recovered); // stranded funds excluded
}
```
