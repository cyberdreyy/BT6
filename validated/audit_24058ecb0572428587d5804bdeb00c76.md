### Title
Cross-Workflow Response Cache Poisoning/Disclosure via `WorkflowID`-Agnostic Cache Key in Gateway HTTP Action Handler - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
Chainlink's Gateway v2 HTTP capability handler caches outbound HTTP action responses to avoid redundant external calls. The cache key is generated by `gateway_common.OutboundHTTPRequest.Hash()`, which the test suite explicitly documents as covering method/URL/headers/body/`WorkflowOwner` — but **excludes `WorkflowID`** (`core/services/gateway/handlers/capabilities/v2/response_cache_test.go:139-149`, "having different workflowID results in same Hash"). The handler's own README claims "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" (`core/services/gateway/handlers/capabilities/v2/README.md:69-72`), but the actual implementation does not include `WorkflowID` in the cache key, contradicting that guarantee.

### Finding Description
`makeOutgoingRequest` in `core/services/gateway/handlers/capabilities/v2/http_handler.go:403-441` dispatches an `OutboundHTTPRequest` (unmarshaled directly from a node-supplied JSON-RPC result, `core/services/gateway/handlers/capabilities/v2/http_handler.go:406-407`) and, depending on `CacheSettings`, calls `h.responseCache.Fetch(...)` or `h.responseCache.Set(...)`. Both operations key the shared in-memory map solely by `req.Hash()` (`core/services/gateway/handlers/capabilities/v2/response_cache.go:49,67,115`). `req.Hash()` incorporates workflow **owner** but not workflow **ID**, meaning two distinct workflows belonging to the same owner (or any two workflows whose owner field can be influenced/reused) that issue outbound HTTP requests with identical method/URL/headers/body will read and write the *same* cached entry.

This mirrors the reported bug class: a resource created under one context (a specific workflow's private/derived HTTP response) becomes visible to, and effectively owned by, a different, unrelated context (another workflow) with no mechanism for the original requester to scope, invalidate, or "unshare" that cached data before the TTL (`OutboundRequestCacheTTLMs`, default 10 minutes, `core/services/gateway/handlers/capabilities/v2/http_handler.go:40`) naturally expires it. Because the request content — including headers/body which can carry sensitive response-shaping parameters or reflect authenticated data from the external endpoint — is attacker/node-controlled, a workflow operator can deliberately craft requests matching another workflow's cache key to read stale, potentially sensitive cached responses, or to poison the cache so the other workflow receives attacker-influenced data instead of a fresh fetch (when `CacheSettings.MaxAgeMs > 0`, `Fetch` is used and returns whatever is stored under that hash, `core/services/gateway/handlers/capabilities/v2/response_cache.go:66-107`).

### Impact Explanation
This is a cross-workflow response confusion vulnerability: an unprivileged or lower-privileged workflow (with knowledge of/matching another workflow's method+URL+headers+body+owner) can obtain another workflow's cached third-party HTTP response, or inject a poisoned response into another workflow's cache, without any authorization check tying cache entries to the requesting `WorkflowID`. There is also no user-facing mechanism to purge or invalidate a specific cache entry — it is only removed via TTL expiry in `DeleteExpired` (`core/services/gateway/handlers/capabilities/v2/response_cache.go:122-136`), directly analogous to the original report's "can't be changed/deleted" characteristic.

### Likelihood Explanation
Requires the attacking party to control or predict the exact `Method`, `URL`, `Headers`/`MultiHeaders`, `Body`, and `WorkflowOwner` fields of a target request — feasible for workflows sharing an owner, or for common/well-known outbound endpoints (e.g., predictable public API calls) where two independent workflows would naturally hash identically. The `CacheSettings.Store`/`MaxAgeMs` flags are also fully attacker(node)-controlled per request, meaning the attacker can force `Store: true` for their own crafted request to seed a colliding entry, and the victim's subsequent `MaxAgeMs > 0` fetch will read it.

### Recommendation
Include `WorkflowID` (and ideally a distinguishing workflow execution/reference identifier) in `OutboundHTTPRequest.Hash()` so cache entries are strictly scoped per workflow, matching the documented "Workflow Isolation" guarantee. Additionally, consider exposing an explicit cache-invalidation path scoped to `WorkflowID`/owner rather than relying purely on TTL expiry.

### Proof of Concept
1. Workflow A (owner `0xabc`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings: {Store: true, MaxAgeMs: 0}}` that returns a sensitive/authenticated 200 response; the gateway calls `responseCache.Set` under key `Hash(method, url, headers, body, "0xabc")` (`http_handler.go:433-441`, `response_cache.go:110-120`).
2. Workflow B, also under owner `0xabc` (or crafted to reuse the same owner value in its request), issues an identical `OutboundHTTPRequest{..., CacheSettings: {MaxAgeMs: 600000}}` shortly after.
3. `responseCache.Fetch` computes the same `req.Hash()` (workflow ID differs but is not part of the hash, per `response_cache_test.go:139-149`) and returns Workflow A's cached response to Workflow B without any authorization check (`response_cache.go:66-77`).

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
