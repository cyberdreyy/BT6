### Title
Fail-open fallback in `check_latest_block_in_tenure` lets a signer approve a non-canonical/conflicting block reorg when the stacks-node RPC is blocked - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` (used by both `check_tenure_change_confirms_parent` and `confirms_latest_block_in_same_tenure`, per `docs/signer-flows.md` and its call sites in `stacks-signer/src/chainstate/mod.rs`) is the guard that decides whether a proposed block legitimately confirms/extends the highest known block of a tenure. When neither the local SignerDB nor a locally-tracked pre-commit can veto the proposal, it falls back to asking the stacks-node for the tenure tip via `client.get_tenure_tip(tenure_id)`. If that RPC call fails for any reason, the code does not reject or defer — it assumes the proposal is valid.

### Finding Description [1](#0-0) 

```rust
let tip = match client.get_tenure_tip(tenure_id) {
    Ok(tip) => tip.anchored_header,
    Err(e) => {
        warn!(
            "Failed to fetch the tenure tip for the parent tenure: {e:?}. Assuming proposal is higher than the parent tenure for now.";
            ...
        );
        return Ok(true);
    }
};
```

This is functionally the inverse-but-equivalent version of the reported Chainlink-oracle bug class: instead of an unguarded external call *reverting* and causing a DoS, the guarded external call *fails* and the failure path silently converts into "trust the caller" (`Ok(true)`), i.e., fail-open. This is confirmed by `docs/signer-flows.md`, which documents this exact branch: "`NODE -- "node unreachable" --> OK2(["assume higher — node's proposal endpoint is the backstop"])`" [2](#0-1) .

The safety of this design assumes the node-side `/v3/block_proposal` validation endpoint (`postblock_proposal.rs`) is the ultimate backstop for tenure/parent-height correctness. However, `check_latest_block_in_tenure` is also invoked by `check_block_against_signer_db_state`, which runs not only at proposal arrival but also again "at validate-ok, and at the moment of signing" [3](#0-2) . If the RPC to the local stacks-node becomes unreachable/blocked at the moment the signer is about to countersign (post validate-ok), this check degrades to a no-op and the signer will not independently detect that the proposal fails to confirm the actual known tip of the tenure — it just defers entirely to the earlier full node validation and its own (potentially stale/incomplete) local DB knowledge.

### Impact Explanation
This does not by itself force acceptance of a block the node rejects (node-side `validate()` is a separate, still-enforced code path), so it is not a full "signing an invalid block" scenario on its own. But it removes one of the two independent techniques (SignerDB cross-check vs. node cross-check) meant to catch a miner replaying/attempting a reorg of an already-globally-accepted tenure tip that the local SignerDB doesn't yet know about (e.g., a signer that was just added or fell behind and whose local DB is incomplete, matching the documented rationale: "the signer DB can be out-of-sync with the node" [4](#0-3) ). In that specific scenario — DB out of sync AND node RPC blocked/errored at the same evaluation instant — a signer could confirm/sign a block that conflicts with the tenure's actual known tip, i.e., a rejection-worthy proposal is instead treated as valid. This maps to the report's targeted equality: "approved-parent vs canonical."

The severity is bounded because triggering it requires the coincidence of (a) local SignerDB being behind and (b) the node RPC being unavailable at that moment — conditions outside a lone miner's direct control (the miner cannot force the signer's own node connection to fail). This weakens it from a guaranteed Critical break to a conditional High-risk gap: a liveness/soundness backstop silently disabled under a plausible but not miner-triggerable fault condition.

### Likelihood Explanation
Low-to-medium. A one-slot miner alone cannot force the signer's connection to its own stacks-node to fail; that requires an operational fault (RPC downtime, network partition, or connectivity blip) coincident with a period of SignerDB lag (e.g., signer just onboarded, or restarted and hasn't backfilled tenure history). This is realistic in production (signer/node deployed on separate hosts, restarts, maintenance windows) but is not purely miner-triggerable, unlike the strict scope requirement ("a one-slot miner (plus gossip) can trigger"). This weakens confidence that the finding fully satisfies the strict "miner-triggerable" requirement in the rules, since it primarily requires an infra fault rather than a crafted proposal alone.

### Recommendation
Do not fail open on `get_tenure_tip` errors in `check_latest_block_in_tenure`. Instead:
- Treat the RPC failure as inconclusive and hold/defer the proposal (return an error/`Pending` rather than `Ok(true)`), forcing the signer to retry rather than approve; or
- Require that this check only ever be satisfied by a positive confirmation (local DB or node), never by an error branch, consistent with how other lookups in this function reject on `ClientError` (e.g. `signer_db.get_last_accepted_block` at line 425-426 propagates the error instead of assuming success).
- At minimum, distinguish "connection error" from "definitively no tenure yet" so a transient RPC outage cannot silently disable this specific reorg-detection backstop, especially at the final pre-signing check.

### Proof of Concept
Conceptual PoC (requires operational fault, not purely miner-craftable):
1. Signer S has an incomplete/stale SignerDB (e.g., freshly joined, or missed messages) for tenure T, so `get_last_accepted_block(T)` and `get_tenure_last_block_info` both return `None`/lower height than the network's actual accepted tip.
2. At the moment S evaluates a proposal (either at initial `check_proposal` or at signing time via `check_block_against_signer_db_state`), S's connection to its local stacks-node RPC (`get_tenure_tip`) errors (timeout/connection refused/restart).
3. `check_latest_block_in_tenure` hits the `Err(e)` branch at `stacks-signer/src/chainstate/mod.rs:452-460` and returns `Ok(true)`, treating the proposal as confirming/exceeding the tenure's real tip even though it doesn't.
4. S proceeds to sign a proposal that a fully-informed check (SignerDB caught up, or the RPC succeeding) would have rejected as `SortitionViewMismatch`/`ConnectivityIssues`-worthy, per `docs/signer-flows.md` line 420-423.

Note: I could not fully trace every downstream caller effect (e.g., exact interplay with `check_block_against_signer_db_state`'s error-vs-mismatch code paths in `signer.rs`) within the available iterations; this should be verified against the full `stacks-signer/src/v0/signer.rs` implementation of `check_block_against_signer_db_state` to confirm whether an RPC error there is otherwise distinguished from a definitive pass.
