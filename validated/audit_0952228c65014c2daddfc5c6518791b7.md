## Analysis

Tracing the "uncontained token errors" bug class (all-or-nothing loop over untrusted recipients) into Aptos stake/vesting code, the strongest analog is in the reward/commission distribution loops of `vesting.move` and `staking_contract.move`.

### Title
Single Recipient Opting Out of Direct Coin Transfers Permanently Blocks Distribution to All Co-Shareholders/Stakers - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`, `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`vesting::distribute` and `staking_contract::distribute_internal` iterate over *all* shareholders/recipients within a single atomic transaction and pay each one via `aptos_account::deposit_coins`. That function aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient is not yet registered for the coin type and has explicitly disabled direct transfers via `aptos_account::set_allow_direct_coin_transfers`. Because the loop is not fault-isolated, any single unregistered/opted-out recipient reverts the entire distribution for every other shareholder or the operator/staker in the same call.

### Finding Description
`vesting::distribute` loops over the immutable shareholder set of a vesting contract and calls `aptos_account::deposit_coins(recipient_address, share_of_coins)` for each one: [1](#0-0) 

`staking_contract::distribute_internal` has the analogous pattern, looping over `distribution_pool.shareholders()` (staker, operator/beneficiary) and calling `aptos_account::deposit_coins` per recipient inside a `while` loop: [2](#0-1) 

`aptos_account::deposit_coins` asserts `can_receive_direct_coin_transfers(to)` whenever the recipient is not yet registered for `CoinType`, aborting with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` otherwise: [3](#0-2) 

`can_receive_direct_coin_transfers` returns false whenever the account has called `set_allow_direct_coin_transfers(false)` — a fully unprivileged, self-service `public entry fun`: [4](#0-3) 

Since `distribute` is also invoked internally (and must succeed) by `terminate_vesting_contract` and `admin_withdraw`, and `staking_contract::distribute_internal` is invoked by `request_commission`, `unlock_stake`, `switch_operator`, and `update_commission_percentage`, a revert inside the loop blocks not just the reward payout but every one of these dependent lockup/withdrawal/commission operations: [5](#0-4) [6](#0-5) 

This is structurally identical to the report's root cause: an all-or-nothing loop over externally-influenced/untrusted recipients where one recipient's transfer failure reverts value transfer to every other legitimate party.

### Impact Explanation
A single shareholder in a vesting contract's shareholder list — set once at contract creation and not removable — or a single participant among a staking contract's staker/operator/beneficiary set, can call `set_allow_direct_coin_transfers(false)` on their own address before that address is ever registered to receive the relevant coin. From that point on:
- `vesting::distribute` (and hence `vest`, `distribute_many`, `terminate_vesting_contract`, `admin_withdraw`) permanently aborts, stranding vested rewards for **all** shareholders of that contract, not just the opted-out one.
- `staking_contract::distribute_internal` (and hence `unlock_stake`, `request_commission`, `update_commission_percentage`, `switch_operator`) permanently aborts, stranding the staker's principal/rewards and the operator's commission.

This matches the required impact category "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary, or vesting flows" since legitimate co-shareholders/operators have no code path to bypass a stuck co-recipient and recover their own already-earned funds.

### Likelihood Explanation
Triggering the block requires no privilege beyond calling `set_allow_direct_coin_transfers` on one's own account (a normal, permissionless entry function) before the account is registered for the coin, combined with that address already being (or having been added as) a shareholder/distribution recipient. Vesting contract admins commonly add many shareholders they do not fully control (e.g., employees/investors), so a malicious or careless shareholder can trigger this unilaterally, without needing the admin's or other shareholders' cooperation.

### Recommendation
Make the distribution loops fault-tolerant: wrap each per-recipient payout so a failure to deposit for one recipient does not abort the whole transaction (e.g., catch/skip via `move_to`-based pending-claim accounting, or use `coin::deposit` fallback logic that credits an internal claimable balance instead of hard-failing when `can_receive_direct_coin_transfers` is false), analogous to converting redemption into an internal accounting operation as recommended in the original report.

### Proof of Concept
1. Vesting admin creates a vesting contract with shareholders `[A, B]`, `A` receiving 25%, `B` 75% (as in the existing test fixture referenced at `aptos-move/framework/aptos-framework/sources/vesting.move` tests around lines 1201–1260).
2. Before the first `distribute` call, account `A` (never having registered/received `AptosCoin` before) calls `aptos_account::set_allow_direct_coin_transfers(false)`.
3. Stake pool accrues rewards; `distribute(contract_address)` is called (by anyone, or via `vest`, `terminate_vesting_contract`, `admin_withdraw`).
4. In the `for_each_ref` loop over `shareholders`, when reaching `A`, `aptos_account::deposit_coins` hits the `!coin::is_account_registered<AptosCoin>(A)` branch, evaluates `can_receive_direct_coin_transfers(A) == false`, and aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The entire `distribute` transaction reverts — `B`'s 75% share, which would otherwise have been paid, remains stuck in the vesting contract's stake pool indefinitely, and no legitimate call to `distribute`/`vest`/`terminate_vesting_contract`/`admin_withdraw` can succeed while `A` keeps this setting.

**Note:** I was not able to fully verify, within the available tool budget, whether Aptos Coin's migration to the Fungible Asset primary-store model changes the `coin::is_account_registered<AptosCoin>` semantics in a way that could make already-existing/touched accounts always "registered" and thus bypass this specific check. The abort path itself is present and documented in the formal spec (`aptos_account.spec.move`, `RegistCoinAbortsIf`/`can_receive_direct_coin_transfers`), and applies unconditionally to never-before-registered addresses, which is realistic for freshly designated vesting shareholders. Confirming the exact FA-migration interaction would require deeper reading of `coin.move`'s `is_account_registered`/`deposit` implementation than the remaining iterations allowed.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
