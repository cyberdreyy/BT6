### Title
RPC `getProgramAccounts` griefing via cheap account creation causes unbounded full-index scan and RPC node resource exhaustion - ([File: rpc/src/rpc.rs])

### Summary
The `StakePet` finding is a classic "cheap creation of many objects → unbounded downstream iteration → resource exhaustion" bug class. The closest reachable analog in Agave is the `getProgramAccounts` RPC path: when the validator does not have the `ProgramId` secondary index enabled (the default, opt-in-only configuration), `JsonRpcRequestProcessor::get_filtered_program_accounts` falls back to a full, unindexed scan of every account in the bank for every call, with filtering applied only after the scan. Because creating accounts on Solana only requires paying the rent-exempt minimum (a small, fixed, non-scaling cost with no explicit floor tied to "usefulness" of the account, similar to `StakePet::create`'s missing minimum-deposit check), an attacker can mass-create a very large number of low-value accounts and thereby make every subsequent unfiltered `getProgramAccounts`/`get_filtered_program_accounts` scan on that validator arbitrarily expensive, degrading or crashing the RPC service for legitimate callers.

### Finding Description
`JsonRpcRequestProcessor::get_program_accounts` (`rpc/src/rpc.rs`, `pub async fn get_program_accounts`, lines 603-671) dispatches to `get_filtered_program_accounts` [1](#0-0) .

`get_filtered_program_accounts` checks whether the `ProgramId` secondary index is configured; if not, it performs a full bank-wide scan via `bank.get_filtered_program_accounts`, applying the caller-supplied filters only in-memory after the scan completes, with no cap on the number of accounts scanned or matched: [2](#0-1) .

Secondary indexes such as `AccountIndex::ProgramId` are opt-in validator configuration (`--account-index` flag), not enabled by default, as seen from the account secondary index configuration surface [3](#0-2) . Without that index, every `getProgramAccounts` call for a given `program_id` walks the *entire* set of live accounts held by the accounts index/AccountsDb.

This is structurally identical to the `StakePet` bug: `StakePet::create` had no minimum deposit, so an attacker could cheaply mint unbounded pet NFTs, and `StakePetManager::getDeadNonBuriedPets` then had to iterate over all of them, exhausting gas. Here, account creation on Solana requires only the rent-exemption minimum lamports (no floor tied to how "useful"/distinguishable the account needs to be for the scan to treat it as a candidate), so an attacker can mass-produce a very large number of accounts owned by an arbitrary program ID. Any RPC caller who then requests `getProgramAccounts` for that owner (or an owner sharing similar cardinality) forces the RPC node to walk the full, growing account set on every single request.

### Impact Explanation
This does not corrupt consensus state or forge funds, but it does map to the allowed "RPC crash / ingest starvation" impact bucket: a low-cost, ordinary-user-triggerable action (mass account creation via ordinary transactions) degrades an unprivileged, frequently-used RPC method (`getProgramAccounts`) for all clients of that RPC node, potentially causing request timeouts, thread-pool/blocking-task starvation (`self.runtime.spawn_blocking`), and memory pressure from materializing large intermediate `Vec<(Pubkey, AccountSharedData)>` results before filtering completes [4](#0-3) . This affects RPC service availability, not validator consensus safety.

### Likelihood Explanation
Medium. It requires no privileged access — any funded account can submit ordinary System Program `CreateAccount` transactions to mass-produce accounts under a chosen owner (cost scales roughly linearly with the number of accounts times the rent-exempt minimum, which is a fixed small floor per empty account, analogous to `StakePet::create` having no deposit floor). It is mitigated somewhat because: (a) validators can enable the `ProgramId`/other secondary indexes to bound cost, and (b) `getProgramAccounts` is already a well-known, widely-discussed expensive RPC call in the Solana ecosystem, so many RPC operators already restrict or disable it. This is a known operational risk rather than a novel exploit, which lowers confidence that it represents an unreported vulnerability class specific to this codebase.

### Recommendation
- Enforce a hard account-count/time budget on unindexed `get_filtered_program_accounts` scans, returning an error (as is already done for `get_filtered_indexed_accounts` with its `limit` parameter, see `bank.get_filtered_indexed_accounts(..., Some(limit))`) rather than allowing unbounded full scans regardless of index configuration.
- Consider making `getProgramAccounts` without filters/secondary index either rate-limited per caller or gated behind a configuration flag by default, rather than allowing it unconditionally on any public-facing JSON-RPC endpoint.
- Ensure the cost of scanning is not proportional to attacker-controlled, cheaply-created account counts without an offsetting cap, mirroring the `StakePet` fix of introducing a floor/cap that makes the griefing vector cost-prohibitive.

### Proof of Concept
1. An attacker submits many ordinary `CreateAccount` transactions via the System Program, each creating a minimal-size account owned by a single attacker-chosen `program_id`, paying only the rent-exempt minimum per account.
2. On a validator/RPC node that does not have the `ProgramId` secondary index enabled (default), any client calls `getProgramAccounts(program_id)`.
3. `get_filtered_program_accounts` (`rpc/src/rpc.rs`, lines 2262-2308) executes the unindexed branch, which must scan through the full accounts set to find and filter matches, with no limit on the number of accounts considered.
4. As the attacker increases the number of accounts under that `program_id`, the scan cost, memory usage, and response latency grow correspondingly, degrading the RPC node's ability to service other `getProgramAccounts` (and potentially other) requests in a timely manner.
