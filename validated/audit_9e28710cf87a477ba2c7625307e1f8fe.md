### Title
`isTransferProcessed` Keyed by Nonce Alone Enables Permanent Fund Lock Across Multiple Source Chains — (`bridge/evm/contracts/SuiBridge.sol`)

---

### Summary

`SuiBridge.sol` and `SuiBridgeV2.sol` track processed token-transfer messages with a mapping keyed by `message.nonce` (a bare `uint64`) rather than by `(message.chainID, message.nonce)`. Because the bridge supports multiple source chains and each source chain independently increments its own nonce counter from zero, nonce values from different source chains inevitably collide. The first transfer processed for nonce N permanently marks `isTransferProcessed[N] = true`, making every subsequent legitimate transfer from any other source chain that happens to carry the same nonce irreversibly unclaimable. Tokens already locked or burned on the originating chain can never be released on the EVM side.

---

### Finding Description

**Partial-identifier replay guard in `SuiBridge.sol`**

`SuiBridge` declares its processed-transfer registry as:

```solidity
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
``` [1](#0-0) 

Every inbound token transfer is gated by:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
// ...
isTransferProcessed[message.nonce] = true;
``` [2](#0-1) 

`SuiBridgeV2.transferBridgedTokensWithSignaturesV2` inherits the same storage slot and applies the identical guard:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
// ...
isTransferProcessed[message.nonce] = true;
``` [3](#0-2) 

**The nonce is source-chain-local, not globally unique**

`BridgeUtils.Message` carries a `chainID` field that identifies the *source* chain:

```solidity
struct Message {
    uint8 messageType;
    uint8 version;
    uint64 nonce;
    uint8 chainID;   // source chain for TOKEN_TRANSFER
    bytes payload;
}
``` [4](#0-3) 

Each source chain maintains its own independent nonce counter starting at 0. Two different source chains will therefore produce identical nonce values (0, 1, 2, …) for entirely different transfers.

**The `verifyMessageAndSignatures` modifier deliberately skips the chain-ID and sequential-nonce checks for `TOKEN_TRANSFER`**

```solidity
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    require(message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID");
    require(message.nonce == nonces[message.messageType], "MessageVerifier: Invalid nonce");
    nonces[message.messageType]++;
}
``` [5](#0-4) 

For `TOKEN_TRANSFER` the modifier only verifies committee signatures over the full message hash — it does not enforce any ordering or source-chain constraint on the nonce. The only duplicate-detection mechanism is `isTransferProcessed[message.nonce]`, which is blind to `chainID`.

**Multiple source chains are explicitly supported**

`transferBridgedTokensWithSignatures` accepts any source chain that passes `onlySupportedChain(message.chainID)`:

```solidity
function transferBridgedTokensWithSignatures(...)
    external
    nonReentrant
    verifyMessageAndSignatures(message, signatures, BridgeUtils.TOKEN_TRANSFER)
    onlySupportedChain(message.chainID)
``` [6](#0-5) 

`onlySupportedChain` delegates to `committee.config().isChainSupported(targetChainID)`, a configurable set. The bridge is therefore designed to accept transfers from multiple source chains simultaneously.

---

### Impact Explanation

When source chain A processes its N-th transfer (nonce = N) and a relayer calls `transferBridgedTokensWithSignatures` on the EVM bridge, `isTransferProcessed[N]` is set to `true`. Any subsequent call for a transfer from source chain B that also carries nonce = N — a transfer whose tokens are already locked or burned on chain B — will revert with `"SuiBridge: Message already processed"`. There is no recovery path: the mapping entry is permanent and no admin function exists to clear it. The recipient on the EVM side permanently loses access to the bridged funds.

This matches the **permanent fund lock** impact class in the allowed scope.

---

### Likelihood Explanation

Nonce collisions are not edge cases — they are structurally guaranteed. Both source chains start at nonce 0 and increment monotonically. After the first transfer on each chain, nonce 0 collides; after the second, nonce 1 collides; and so on. Any ordinary user who submits a valid committee-signed transfer from one source chain before the corresponding transfer from another source chain is submitted triggers the lock for the second transfer's recipient. No special privilege is required beyond the ability to call a public function with a valid committee-signed message.

---

### Recommendation

Key `isTransferProcessed` by the composite `(chainID, nonce)` pair instead of nonce alone:

```solidity
// Before
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;

// After
mapping(uint8 chainID => mapping(uint64 nonce => bool isProcessed)) public isTransferProcessed;
```

Update all reads and writes accordingly:

```solidity
require(!isTransferProcessed[message.chainID][message.nonce], "SuiBridge: Message already processed");
// ...
isTransferProcessed[message.chainID][message.nonce] = true;
```

Apply the same fix to `SuiBridgeV2`.

---

### Proof of Concept

Assume the bridge is configured to support two source chains: chain A (`chainID = 0`) and chain B (`chainID = 1`).

1. A user on chain A initiates a transfer; the source bridge assigns it `nonce = 5`. The committee signs the message `{messageType=TOKEN_TRANSFER, version=1, nonce=5, chainID=0, payload=...}`.

2. A relayer calls `transferBridgedTokensWithSignatures(signaturesA, messageA)`. The call succeeds; `isTransferProcessed[5] = true`.

3. Independently, a user on chain B initiates a transfer; the source bridge assigns it `nonce = 5` (its own counter). The committee signs `{messageType=TOKEN_TRANSFER, version=1, nonce=5, chainID=1, payload=...}`.

4. A relayer calls `transferBridgedTokensWithSignatures(signaturesB, messageB)`. The call reverts:
   ```
   require(!isTransferProcessed[5], "SuiBridge: Message already processed");
   // isTransferProcessed[5] == true  →  revert
   ```

5. The user's tokens on chain B are permanently locked. No admin escape hatch exists.

The same scenario applies to `SuiBridgeV2.transferBridgedTokensWithSignaturesV2` because it reads and writes the same `isTransferProcessed` storage mapping inherited from `SuiBridge`. [1](#0-0) [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9)

    modifier verifyMessageAndSignatures(
        BridgeUtils.Message memory message,
        bytes[] memory signatures,
        uint8 messageType
    ) {
        // verify message type
        require(message.messageType == messageType, "MessageVerifier: message does not match type");
        // verify signatures
        committee.verifySignatures(signatures, message);
        // increment message type nonce
        if (messageType != BridgeUtils.TOKEN_TRANSFER) {
            // verify chain ID
            require(
                message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID"
            );
            require(message.nonce == nonces[message.messageType], "MessageVerifier: Invalid nonce");
            nonces[message.messageType]++;
        }
        _;
    }
