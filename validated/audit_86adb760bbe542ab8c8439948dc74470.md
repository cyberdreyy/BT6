### Title
ERC4626 vault share-price donation inflates programmable-borrower epoch interest and mints unbacked strategy tokens, letting a vault user drain LP principal - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
The external bikeshed bug is "untrusted input (a crafted source file) causes arbitrary external content to be folded into the output." The analog is the programmable-borrower's external ERC4626 vault: its price is untrusted input that `totalInterestDueNow()` folds directly into epoch-interest accounting. In minted-interest mode, a donation to the vault inflates the reported interest, which `IdleCDOEpochVariant._stopEpoch` converts into freshly minted strategy tokens and higher tranche prices — value the attacker then withdraws at other LPs' expense. The `maxApr` sanity check that would bound this is unreachable for programmable borrowers.

### Finding Description
`ProgrammableBorrower._vaultNetInterest()` computes epoch interest as the delta between `epochStartVaultAssets + epochDepositedToVault` and `_currentVaultAssets() + epochWithdrawnFromVault` (ProgrammableBorrower.sol:337-347), where `_currentVaultAssets()` is `vault.convertToAssets(vault.balanceOf(this))`. `convertToAssets` reflects *total vault assets*, so any donation to the vault (direct underlying transfer into an ERC4626 that prices by `totalAssets/totalSupply`) raises the CDO's `convertToAssets` and therefore `vaultInterestAccrued()`.

`totalInterestDueNow()` returns that inflated interest (ProgrammableBorrower.sol:330-334). In `_stopEpoch`, when `isProgrammableBorrower` is set, `_resolveStopEpochInterest` returns `totalInterestDueNow()` and enforces `_interest <= 1` (IdleCDOEpochVariant.sol:1001-1005). The `maxApr` cap check is gated on `isInterestMinted && _interest > 1` (IdleCDOEpochVariant.sol:377-380), which is unreachable since `_interest` is forced to `0` or `1` for programmable borrowers. So arbitrary donation-inflated interest flows to `_strategy.mintStrategyTokens(_grossInterest)` (line 430), `_updateAccounting()` raises AA/BB tranche prices, and `unclaimedFees` also grows.

A donation-only inflation is mostly recoverable by the donor through their own vault shares, so the profitable variant is: attacker is an LP holding AA tranches *and* a vault shareholder. The donation moves value from the vault's total assets (which the attacker partly owns) into the CDO's epoch interest; the minted strategy tokens raise the AA tranche price; the attacker then exits via `requestWithdraw`/`claimWithdrawRequest` at the inflated price. The inflated price is paid out of the pool's real underlying when the borrower repays or when other requests are settled — i.e., the attacker captures a fraction of the donation at inflated tranche terms while the rest of the LPs absorb the phantom interest.

### Impact Explanation
Attacker profit ≈ donated amount × (attacker share of the inflated tranche appreciation) minus donation dilution. Concretely, donating `D` to the vault mints ~`D` of phantom strategy-token interest, raising AA/BB virtual prices proportionally. The attacker holding AA tranches redeems at the higher price, extracting up to `D × (AA share of tranche NAV)` in extra underlying from the pool — a direct theft of other lenders' principal, scaled by donation size. In minted mode the phantom tokens are real `IdleCDOTranche` supply backed by nothing, so redemption of the attacker's position is paid by remaining LPs (insolvency transferred to last-out withdrawers).

### Likelihood Explanation
Attacker requirements match the allowed set: an unprivileged user of the programmable borrower's ERC4626 vault plus a KYC-passing lender (tranche holder). No privileged call is needed — the honest owner/manager calls `stopEpoch` as usual, and the forged interest is pulled straight from `totalInterestDueNow()`. Pre-conditions: the pool runs in `isProgrammableBorrower` + `isInterestMinted` mode and uses a donation-sensitive ERC4626 (asset-priced vaults, i.e., any vault whose `convertToAssets` reflects raw transfers — true of standard ERC4626 without virtual shares/decimals hardening, or via first-depositor inflation where the attacker seeds the vault before CDO deposit). The one check that would cap interest (`maxApr`) is dead code on this path.

### Recommendation
Apply the `maxApr` bound to the programmable-borrower path: in `_stopEpoch`, after `_resolveStopEpochInterest`, enforce `_grossInterest <= _calcInterestWithApr(getContractValue(), _maxApr) + _pendingWithdrawFees` whenever `isProgrammableBorrower && isInterestMinted` (or always for programmable borrowers), reverting or clamping. Independently, have `ProgrammableBorrower` accrue vault interest on a cost-basis / realized-yield basis (track `epochDepositedToVault − epochWithdrawnFromVault` PnL only on actual `deposit`/`withdraw`, or snapshot `shares × avgEntryPrice`), so donations that raise `convertToAssets` do not count as epoch interest. Optionally use a vault-internal `totalAssets` that ignores unsolicited transfers.

### Proof of Concept

// test/foundry/VaultDonationInflation.t.sol
function test_DonationInflatesEpochInterest() public {
    // Setup: IdleCDOEpochVariant with isProgrammableBorrower && isInterestMinted,
    // ProgrammableBorrower pointed at vault V (ERC4626, asset == underlying).
    // 1. Buffer phase: attacker (KYC'd) deposits X underlying, receives AA tranches.
    vm.prank(attacker); cdo.depositAA(X);
    // Honest manager starts epoch; funds flow to ProgrammableBorrower -> vault V.
    vm.prank(manager); cdo.startEpoch();
    // 2. Attacker also deposits into vault V to hold shares, then donates D
    //    underlying directly to V, raising convertToAssets of the borrower's shares.
    vm.prank(attacker); underlying.transfer(address(V), D);

    // 3. Honest manager stops the epoch. _interest must be 0/1 for programmable
    //    borrowers, so the maxApr check at IdleCDOEpochVariant.sol:377 is skipped.
    vm.prank(manager); cdo.stopEpoch(0, 0);

    uint256 priceAfter = cdo.virtualPrice(AA);
    assertGt(priceAfter, priceBefore);

    // ... advance epoch, claimWithdrawRequest ...

}
