### Title
Attacker-controlled MessageId collision in HandleLegacyUserMessage allows hijacking of another user's pending gateway callback, causing cross-user response confusion - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`Message.Validate()` only checks length/format of `MessageId`, not uniqueness, and it is fully attacker-chosen (any string ≤128 bytes, not tied to signer identity). [1](#0-0)  `HandleLegacyUserMessage` unconditionally overwrites `h.savedCallbacks[msg.Body.MessageId]` with the new caller's callback, with no check for an existing pending entry. [2](#0-1)  This lets an unauthenticated HTTP client of the gateway's user-facing endpoint submit a second, unrelated signed request re-using a `MessageId` that a legitimate victim is already waiting on, hijacking delivery of whichever response arrives at `handleWebAPITriggerMessage` first. [3](#0-2) 

### Finding Description
The gateway's user-facing HTTP endpoint (`ProcessRequest` in `gateway.go`) decodes and signature-validates a legacy `api.Message`, then routes it to `HandleLegacyUserMessage` for `MethodWebAPITrigger`. [4](#0-3)  Any client (unauthenticated wrt DON membership — it just needs any ECDSA key to produce a valid signature over the message body) can reach this path.

`Message.Validate()` verifies signature format, length bounds on `MessageId`/`Method`/`DonId`, and that the signature recovers to a signer address, but never checks that `MessageId` is unique or bound to the sender's identity — any two different signers can pick the exact same `MessageId` string. [5](#0-4) 

In `HandleLegacyUserMessage`, after successful validation, the handler stores the new request's callback into the shared map keyed purely by `msg.Body.MessageId`, with no existence check:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
``` [2](#0-1) 

If a legitimate user already has a pending request with `MessageId = X` (waiting on `savedCallbacks[X]`), an attacker can send their own signed message reusing `MessageId = X`, which silently overwrites the map entry, replacing the victim's callback with the attacker's own. When a DON node responds (the response's `ID` is echoed back as `msg.Body.MessageId` via `ValidatedMessageFromResp`), `handleWebAPITriggerMessage` looks up and deletes `savedCallbacks[X]` and delivers whichever response arrives first to whichever callback is currently stored under that key:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [6](#0-5) 

Because both the victim's and the attacker's requests are independently broadcast to all DON members under the same `MessageId`, nodes will process and respond to both, and whichever response reaches the gateway first is delivered through the callback currently occupying the map slot — which, after the overwrite, no longer necessarily corresponds to the request that produced that response. This is a cross-user response confusion: the victim's response can be delivered over the attacker's HTTP connection (data leak to attacker), or the attacker can cause the victim to receive a response to a request they didn't send (response injection/DoS to victim), depending on timing. No allowlist, rate limiter (the node-side rate limiter in `handleWebAPIOutgoingMessage` does not apply here; the code explicitly notes "TODO: apply allowlist and rate-limiting here" on the *user* path), or uniqueness check prevents this. [7](#0-6) 

### Impact Explanation
This is a real cross-user data/response confusion vulnerability: an unprivileged network attacker who can reach the gateway's public user HTTP endpoint can (a) receive another legitimate user's HTTP-trigger response data intended only for that user, or (b) inject an unexpected/attacker-influenced response into a victim's pending request, causing incorrect application behavior on the victim's side. Depending on the payload contents (which can include workflow execution results, potentially containing sensitive data returned by DON capability nodes), this maps to Chainlink's "unauthorized access to another user's data/response" / "authentication bypass leading to information disclosure" bounty impact class.

### Likelihood Explanation
Exploitability requires only: (1) network access to the gateway's public user-facing endpoint, (2) the ability to generate a valid ECDSA signature over an arbitrary message (any key works — there is no allowlist enforced at this layer), and (3) knowledge or guessing of the victim's in-flight `MessageId`. If `MessageId`s are predictable, sequential, or otherwise observable (e.g., echoed back in earlier gateway responses, or reused/short by client libraries), an attacker can trivially win the race within the ~120s callback TTL window (`defaultCallbackMaxAgeSec`). [8](#0-7)  The attack is repeatable and requires no elevated privileges.

### Recommendation
In `HandleLegacyUserMessage`, check for an existing entry in `savedCallbacks` under the same `MessageId` before inserting, and reject the new request (respond with a conflict/duplicate error) rather than silently overwriting the previous callback. Additionally, consider scoping `savedCallbacks` keys by `(sender, MessageId)` or including a per-request nonce derived from the signer to prevent unrelated senders from colliding on the same key.

### Proof of Concept
Go handler-level test plan (extending `handler_test.go`):
1. Construct `handler` with a mock `handlers.DON` that simply records `SendToNode` calls (no real responses needed to observe the overwrite).
2. Create two distinct signed `api.Message`s, `msgVictim` and `msgAttacker`, both with `MessageId = "shared-id"` but signed by two different private keys, both `Method = MethodWebAPITrigger`.
3. Create two `handlers.Callback` instances (victim and attacker) via `common.NewCallback()`.
4. Call `handler.HandleLegacyUserMessage(ctx, msgVictim, victimCallback)`, then immediately `handler.HandleLegacyUserMessage(ctx, msgAttacker, attackerCallback)`.
5. Assert that `handler.savedCallbacks["shared-id"].Callback` now equals `attackerCallback`, not `victimCallback` (demonstrating the victim's entry was silently overwritten).
6. Simulate a DON node response for `MessageId = "shared-id"` (constructed to look like it answers the victim's original request) by calling `handler.handleWebAPITriggerMessage(ctx, respMsg, nodeAddr)`.
7. Assert that `attackerCallback.Wait(ctx)` returns the response (i.e., delivered to the attacker), while `victimCallback.Wait(ctx)` times out / never receives a response — proving cross-user response confusion and loss of the victim's own callback.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
