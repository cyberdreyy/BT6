### Title
Stake-account state divergence between epoch-rewards calculation and distribution can panic validators via `assert_eq!` in `build_updated_stake_reward` - (File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
Agave's partitioned epoch-rewards mechanism, like `CoreRouter.redeem()`, computes a payout amount (`stake_reward`) at one point in time (reward *calculation*, at the epoch boundary) and applies it several blocks later at *distribution* time against a possibly-changed account. Instead of verifying that the account's current state matches the assumptions made during calculation, the code hard-asserts equality, which is a `panic!` in production code reachable from ordinary user transactions if the pre/post state ever diverges.

### Finding Description
`begin_partitioned_rewards` snapshots stake accounts and calculates `InflationReward.stake` (the delegation's *new* target stake, post-reward) at the epoch boundary [1](#0-0) . This calculation, like `exchangeRateStored()` in the reported bug, is a snapshot that becomes stale as soon as further blocks are produced, because reward distribution is deliberately spread out over `REWARD_CALCULATION_NUM_BLOCKS`/`num_partitions` blocks via `distribute_partitioned_epoch_rewards` [2](#0-1) .

When each partition is finally applied, `build_updated_stake_reward` re-fetches the *live* stake account from `stakes_cache_accounts` (current state, not the calculation-time snapshot) and applies the pre-computed reward delta [3](#0-2) . Unlike the `CoreRouter` bug, this code path does not blindly trust the pre-computed amount for lamports (it uses `checked_add_lamports`, an actual mutation of the live account) — but it does blindly trust the pre-computed *delegation stake* value when `adjust_delegations_for_rent` is disabled, verifying it only via a hard `assert_eq!`:

```rust
let expected_delegation = stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(
    expected_delegation, new_stake.delegation.stake,
    "stake reward delegation must be consistent with the updated stake account lamport balance"
);
``` [4](#0-3) 

`stake.delegation.stake` here comes from the **live** cached stake account fetched at distribution time, while `partitioned_stake_reward.inflation.stake` (used to build `new_stake`) is the value computed at the earlier *calculation* time. If the live delegation's `stake` field differs from what was assumed at calculation time — for example because the stake account was split, merged, redelegated, or otherwise mutated by an ordinary user transaction between calculation and the (up to `num_partitions`, potentially hundreds of) distribution blocks — this assertion fails and panics the validator process, exactly analogous to how `CoreRouter` mismanages funds when `LToken`'s actual state at redemption time differs from the state assumed when `expectedUnderlying` was computed.

The code comment at line 330 acknowledges the assumption that "stake accounts are checked in calculation, and further state mutation prevent[ed] by stake-program restrictions", implying there is supposed to be a protocol-level invariant (feature-gated stake-program restrictions) blocking any user transaction from mutating a stake account's delegation while rewards are pending for it. I was not able to fully verify, within the given tool budget, that this invariant is enforced for *all* mutation paths (e.g., `Merge`, `Redelegate`, `Split`, or interactions gated by different feature-set combinations) or that it holds across all `adjust_delegations_for_rent`/`use_fixed_point_stake_math` feature combinations that alter how `new_stake.delegation.stake` is derived.

### Impact Explanation
If any reachable ordinary-user code path can mutate a stake account's `delegation.stake` between the reward-calculation snapshot and the corresponding distribution block (which can be many blocks later, up to `num_partitions`), the `assert_eq!` panics the bank/validator process during normal block replay — a consensus-halting/liveness-affecting bug (replay-path panic), which is explicitly an accepted impact category for this scan.

### Likelihood Explanation
Likelihood is uncertain without confirming the completeness of the "stake accounts are checked in calculation, and further state mutation prevented by stake-program restrictions" invariant across all relevant instruction paths and feature-gate states (`adjust_delegations_for_rent` false branch specifically). If that invariant has any gap, likelihood is high since epoch-reward distribution happens every epoch on mainnet and the reward window spans many blocks during which ordinary transactions are processed.

### Recommendation
Replace the hard `assert_eq!` with a recoverable error path (as is already done for the `adjust_delegations_for_rent` and `AccountNotFound`/`ArithmeticOverflow` cases, which return `Result<_, DistributionError>` and are handled via burning the reward instead of crashing) so that any state divergence between calculation and distribution time degrades gracefully (e.g., burn/skip the reward) instead of panicking the validator. Additionally, audit all stake-program instruction handlers to confirm they conclusively reject any user-initiated mutation of `delegation.stake` for accounts with pending, uncommitted partitioned rewards, across all supported feature-gate combinations.

### Proof of Concept
Not constructed — would require either (a) a stake-program code path that permits changing `delegation.stake` for an account referenced in `PartitionedStakeReward` between the calculation block and its distribution block despite the stated restriction, or (b) a `use_fixed_point_stake_math`/feature-gate combination that causes calculation-time and distribution-time delegation math to diverge even without any user transaction. Confirming or ruling this out requires deeper review of the stake program's instruction processors than was possible within this scan's tool budget.

    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);
