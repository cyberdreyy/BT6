### Title
Instant-withdraw claims pay unfunded receipts — `claimInstantWithdrawRequest` ignores `pendingInstantWithdraws` and `requestInstantWithdraw` lacks the claim-before-rerequest guard added to `requestWithdraw` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The normal withdraw path was hardened to track receipts per epoch (`withdrawsRequestsByEpoch`, `lossRecoveryPriceByEpoch`, `lastWithdrawRequest`) and to force users to claim an existing loss-adjusted receipt before opening a new request. None of that was carried forward to the instant-withdraw path: `requestInstantWithdraw` performs no existing-receipt/funding check, and `claimInstantWithdrawRequest` pays the full aggregate `instantWithdrawsRequests[user]` without verifying that the user's requests were actually funded via `collectInstantWithdrawFunds`. Since `allowInstantWithdraw` is a global flag enabled by the first successful `getInstantWithdrawFunds`, an attacker can stack a second, unfunded instant request on top of a funded one and drain underlying that belongs to other users' funded claims.

### Finding Description
In `IdleCreditVault`:

- `requestWithdraw` reverts if the user's `lastWithdrawRequest` epoch has a pending loss-adjusted receipt — the "claim before re-request" fix.
- `requestInstantWithdraw` (lines 356-375) has no equivalent guard: it just burns CDO tokens, mints a receipt, and adds to `instantWithdrawsRequests[user]`, `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `pendingInstantWithdraws`.
- `claimInstantWithdrawRequest` (lines 380-393) burns the whole aggregate `instantWithdrawsRequests[user]` and calls `_transferFundedClaim(_user, amount)`, i.e. it pays for receipts that may never have been funded by the borrower.

The only gate is `allowInstantWithdraw` in `IdleCDOEpochVariant.claimInstantWithdrawRequest` (line 977), which is set globally to `true` the first time `getInstantWithdrawFunds` succeeds (line 570). Crucially, `instantWithdrawDeadline` gates only the funding call `getInstantWithdrawFunds` (line 561) — it does not prevent new `requestInstantWithdraw` calls after the deadline, and nothing in `claimInstantWithdrawRequest` checks `pendingInstantWithdraws` or `instantWithdrawsRequestsByEpoch` against what was actually collected.

### Impact Explanation
Broken invariant: one receipt, one funded payout. The attacker receives underlying equal to `amount1 + amount2` while only `amount1` (plus other users' reserves) was ever transferred into the strategy. The excess `amount2` is paid out of underlying held by the strategy to back *other* users' funded instant claims (and any loss-adjusted/default reserves held there) — direct theft, quantified as the size of the attacker's second unfunded request, bounded only by their tranche balance and the strategy's reserves. Victim users then find their claims underfunded (insolvency for the last claimers).

### Likelihood Explanation
Attacker is a normal KYC'd lender — fully in scope. Requirements:

1. Epoch running, past `instantWithdrawDeadline`, `getInstantWithdrawFunds` already called once (normal operation — manager does this every epoch when instant requests exist), so `allowInstantWithdraw == true`.
2. Attacker makes a second `requestInstantWithdraw` — allowed because nothing disables instant requests after the deadline and `requestInstantWithdraw` has no re-request guard.
3. Attacker calls `claimInstantWithdrawRequest` before any second funding round — the manager is honest, so the attacker simply front-runs/acts before the next `getInstantWithdrawFunds`; even if funding eventually happens, the theft already occurred.
4. The strategy must hold enough underlying — true whenever other users' funded claims (or recovery reserves) remain unclaimed, which is the common case since claims are lazy.

No existing guard stops this: `_onlyIdleCDO` is satisfied via the CDO, `defaultRecoveryFinalized` is false in the normal path, and there is no per-epoch funding check on the instant claim path.

### Recommendation
- In `claimInstantWithdrawRequest`, cap the payout at the funded portion: track per-epoch funded amounts (e.g., deduct only `instantWithdrawsRequestsByEpoch` entries whose epoch was funded) or revert while the user's receipt exceeds `instantWithdrawClaimsByEpoch[epoch] - pendingInstantWithdraws` attributable funding.
- In `requestInstantWithdraw`, revert if `instantWithdrawsRequests[_user] != 0` until the prior request is claimed, mirroring the `requestWithdraw` guard, and/or disallow new instant requests after `instantWithdrawDeadline` until the next epoch.

### Proof of Concept
```solidity
// test/foundry/InstantWithdrawUnfundedClaim.t.sol
// Fork setup mirrors test/foundry/IdleCreditVault.t.sol helpers.
function testUnfundedInstantRequestStealsReserves() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18); // epoch #1 buffer

    uint256 instantDelay = 100;
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 1e18, false);

    address victim   = makeAddr("victim");
    address attacker = makeAddr("attacker");
    uint256 amt = 100e6;

    _depositWithUser(victim,   amt);
    _depositWithUser(attacker, amt);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // both request instant withdrawals
    _requestInstantWithdrawWithUser(victim,   IERC20(AAtranche).balanceOf(victim));
    _requestInstantWithdrawWithUser(attacker, IERC20(AAtranche).balanceOf(attacker));

    // deadline passes; manager funds the pending instant batch once
    vm.warp(block.timestamp + instantDelay + 1);
    deal(defaultUnderlying, borrower, 2 * amt);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds(); // allowInstantWithdraw = true; pendingInstantWithdraws = 0

    // victim does NOT claim yet; funds sit in the strategy.
    // attacker files a SECOND instant request in the same running epoch.
    // This request is unfunded: pendingInstantWithdraws becomes amt, nothing collected.
    _depositWithUser(attacker, amt); // or re-deposit via depositDuringEpoch-equivalent path
    _requestInstantWithdrawWithUser(attacker, amt);

    // attacker claims the full aggregate: funded amt + unfunded amt
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    // attacker received 2*amt while only amt of his receipts was ever funded
    assertEq(underlying.balanceOf(attacker) - balPre, 2 * amt, "unfunded receipt paid");

    // victim's funded claim is now underfunded: strategy balance insufficient
    uint256 stratBal = underlying.balanceOf(address(strategy));
    assertLt(stratBal, IdleCreditVault(address(strategy)).instantWithdrawsRequests(victim),
        "victim claim underfunded");
}
```

Note: the exact helper names (`_requestInstantWithdrawWithUser`, `_useStandardEpochVariant`) follow the existing harness in `test/foundry/IdleCDOEpochQueue.t.sol`/`IdleCreditVault.t.sol`; the PoC requires only that `requestInstantWithdraw` remain callable after `instantWithdrawDeadline` in the running epoch, which `IdleCDOEpochVariant.getInstantWithdrawFunds` (line 561) confirms is not blocked by the deadline check itself.
