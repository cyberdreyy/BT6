### Title
Attacker-controlled `whitelist_account_id` in `LockupFactory::create` lets any caller deploy a lockup at the victim's deterministic address with a hostile staking-pool whitelist - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` accepts an optional `whitelist_account_id` argument from the caller and, if present, uses it verbatim as `staking_pool_whitelist_account_id` for the newly deployed lockup instead of always using the canonical `self.whitelist_account_id` set at factory `new()`. Because the lockup's on-chain account name is fully deterministic from `owner_account_id` (`sha256(owner_account_id)[..20] . factory`), any unprivileged account can front-run the legitimate creation for a given `owner_account_id` and deploy a lockup whose `staking_pool_whitelist_account_id` points at a contract the attacker controls.

### Finding Description
The broken binding: the protocol assumes
`deployed_lockup.staking_pool_whitelist_account_id == LockupFactory.whitelist_account_id` (the canonical, foundation-vetted whitelist) for every lockup produced by the factory.

In `create`, this equality is not enforced: [1](#0-0) 
```
pub fn create(
    ...
    whitelist_account_id: Option<ValidAccountId>,
) -> Promise {
    ...
    let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
        account_id.into()
    } else {
        self.whitelist_account_id.clone()
    };
```
Any caller (unprivileged, just needs `MIN_ATTACHED_BALANCE`) can pass `whitelist_account_id = Some(attacker_contract)`. That value is embedded directly into the `LockupArgs.staking_pool_whitelist_account_id` field sent to the deployed lockup's `new()`: [2](#0-1) 

The lockup account itself is fully deterministic and depends only on `owner_account_id`: [3](#0-2) 
`format!("{}.{}", hex::encode(sha256(owner_account_id)[..20]), factory)`. Because `create_account()` fails if the account already exists, whoever's transaction lands first for a given `owner_account_id` "claims" that address permanently.

Root cause / exploit flow: an attacker deploys their own contract implementing `is_whitelisted` that always returns `true`, then calls `create(owner_account_id = <victim>, ..., whitelist_account_id = Some(<attacker_whitelist>))` before the rightful creator (e.g. NEAR Foundation) does so for the same `owner_account_id`. The resulting lockup at the victim's canonical, expected address is deployed with `staking_pool_whitelist_account_id` pointing at the attacker's contract, and with `lockup_duration`/`vesting_schedule`/`release_duration` values the attacker chose, not the rightful creator. Later calls from the (still victim-owned, since `owner_account_id` is embedded as owner) lockup's `select_staking_pool` will always pass the whitelist check via `ext_whitelist::is_whitelisted` against the hostile contract: [4](#0-3) 
so the safety net that is supposed to stop an owner from staking with a scam pool is silently defeated, and any real vesting/lockup deployment intended for that `owner_account_id` will subsequently fail because the account is already occupied.

No existing guard prevents this: `create` performs only `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)` and no check that `whitelist_account_id` matches `self.whitelist_account_id`; `assert_owner`/`assert_called_by_foundation` are lockup-side checks that only govern who can act *after* the lockup exists, not who is allowed to set the whitelist at creation time.

### Impact Explanation
This matches the explicit Critical category "a lockup deployed with parameters its rightful creator never chose." The concrete consequence is that the intended lockup account for a given `owner_account_id` can be permanently squatted with an attacker-chosen whitelist (and attacker-chosen `lockup_duration`/`vesting_schedule`/`release_duration`), blocking the legitimate deployment and, if the owner later selects a staking pool, removing the whitelist's protective guarantee since the check resolves against an attacker-controlled contract. The `owner_account_id` field itself remains the victim's account (so the attacker cannot directly withdraw funds without the victim's key), which limits the direct fund-theft path but the deployment-parameter tampering and destruction of the whitelist invariant for that lockup are real and repeatable for any `owner_account_id` not yet claimed.

### Likelihood Explanation
The attack requires only `MIN_ATTACHED_BALANCE` (3.5 NEAR) and knowledge of a target `owner_account_id` that has not yet had its lockup created — both are public/observable (the target account name and mempool visibility of the legitimate creator's pending transaction). It is fully repeatable across any number of not-yet-created `owner_account_id`s and costs the attacker only gas plus the refundable-if-failed deposit for the accounts they don't successfully claim.

### Recommendation
Remove the caller-suppliable `whitelist_account_id` parameter from `create` (or restrict it to `assert_called_by_foundation`/owner-only override) so every lockup produced by the factory always uses `self.whitelist_account_id`. If a legitimate need exists to allow custom whitelists, gate it behind an owner/foundation-authenticated call, not an open, unprivileged entrypoint.
