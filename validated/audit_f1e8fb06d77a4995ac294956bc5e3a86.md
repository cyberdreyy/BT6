### Title
Stale write-off requests remain fillable after tranche value collapses - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`createWriteOffRequest` escrows tranche tokens and records a fixed underlying ask, but it only requires the epoch to be running at creation time. [1](#0-0)  `fullfillWriteOffRequest` later checks only that the stored tranche amount matches and that the fulfiller pays at least the stored ask; it does not check the current epoch, default status, tranche price, or an expiry. [2](#0-1)  A borrower default or realized epoch loss can therefore occur between listing and fulfillment, leaving the buyer paying the pre-loss price for tranches whose redemption value has collapsed.

### Finding Description
The escrow takes custody of the seller's tranche tokens, so the seller cannot withdraw collateral after creating the request. [3](#0-2)  However, the economic state represented by those tokens remains mutable because epoch settlement can realize losses, burn strategy tokens, and update tranche prices. [4](#0-3)  A failed borrower repayment marks the pool defaulted and disables the epoch. [5](#0-4)  `finalizeDefault` can then crystallize a zero-recovery outcome by reducing active NAV and forcing accounting so tranche prices expose the loss. [6](#0-5) 

None of those state transitions invalidate an existing write-off request. Any fulfiller may still call `fullfillWriteOffRequest`; the function deletes the request, pulls the stale underlying amount, pays the seller net of the fee, and delivers the impaired tranches. [7](#0-6)  The only seller-side escape is `deleteWriteOffRequest`, which is optional and rational to leave open after the tranche price falls. [8](#0-7) 

### Impact Explanation
A buyer can lose the entire agreed underlying payment. For example, a lender escrows `10_000e18` AA tranche tokens and requests `10_000e6` USDC while the tokens are worth approximately par; after a zero-recovery default, the buyer still pays `10_000e6`, the lender receives `9_990e6` after the default 0.1% fee, and the buyer receives tokens with `virtualPrice == 0`. [9](#0-8)  This breaks the intended fair-exchange invariant of the escrow: the asset quantity is preserved, but its vault-backed value is not.

### Likelihood Explanation
Likelihood depends on an epoch transition, explicit loss, or borrower default occurring before an open ask is filled. Requests are intentionally long-lived because there is no expiry or epoch binding, and fulfillment is permissionless. [10](#0-9)  A lender does not need privileged access and can leave stale asks open when credit conditions deteriorate; the honest manager-triggered default or loss call supplies the state change. Although a buyer can inspect `virtualPrice` off-chain, the contract permits the stale trade and provides no protection at execution.

### Recommendation
Bind each request to the epoch and vault state in which it was created. Store `IdleCreditVault(strategy).epochNumber()` and a creation-time tranche value or minimum acceptable price, and make fulfillment revert if the epoch changed, `isEpochRunning` is false, `defaulted` is true, or current tranche value is below a fulfiller-specified floor. Alternatively, automatically invalidate all open requests on epoch stop/default and require sellers to relist at the post-transition price. Add an expiry and allow repricing through explicit cancellation and recreation rather than silently carrying stale asks across accounting events.

### Proof of Concept
Insert this test into `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, which already deploys the escrow against a mainnet-fork `IdleCDOEpochVariant`:

```solidity
function testStaleWriteOffRequestFulfilledAfterDefault() external {
    uint256 requestedTranches = 10_000e18;
    uint256 requestedUnderlyings = 10_000e6;
    address buyer = makeAddr("staleAskBuyer");

    // Seller lists tranches while the epoch is running and prices are healthy.
    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, requestedUnderlyings);

    // Honest epoch lifecycle: repayment fails, the pool defaults, and recovery is zero.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(address(underlying), borrower, 0);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), 0);

    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted(), "borrower default was not recorded");

    vm.prank(manager);
    cdoEpoch.finalizeDefault(0, address(1));
    assertEq(
        cdoEpoch.virtualPrice(address(tranche)),
        0,
        "defaulted tranche should be worthless"
    );

    // The stale ask remains executable after the tranche price collapsed.
    deal(address(underlying), buyer, requestedUnderlyings);
    vm.startPrank(buyer);
    underlying.approve(address(escrow), requestedUnderlyings);
    escrow.fullfillWriteOffRequest(
        LP,
        requestedTranches,
        requestedUnderlyings
    );
    vm.stopPrank();

    uint256 fee = requestedUnderlyings * escrow.exitFee() / escrow.FULL_VALUE();
    assertEq(
        tranche.balanceOf(buyer),
        requestedTranches,
        "buyer did not receive escrowed tranches"
    );
    assertEq(
        underlying.balanceOf(buyer),
        0,
        "buyer did not pay the stale underlying ask"
    );
    assertEq(
        underlying.balanceOf(LP),
        requestedUnderlyings - fee,
        "seller did not receive stale ask proceeds"
    );
    assertEq(
        cdoEpoch.virtualPrice(address(tranche)),
        0,
        "purchased tranches have redemption value"
    );
}
```

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens

      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });

  function deleteWriteOffRequest() external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[msg.sender];
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, currentRequest.tranches);

  function _handleBorrowerDefault(uint256 funds) internal {
    defaulted = true;
    // Do not reopen instant claims here. They remain disabled when funding is pending;
    // successful full funding is the only path that enables them before finalization.

    if (isProgrammableBorrower) {
