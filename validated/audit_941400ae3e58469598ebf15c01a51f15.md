No vulnerability found for this question.

**Reasoning:**

The described double-counting path does not exist because both `vesting::unlock_rewards` and the underlying `staking_contract::unlock_rewards`/`unlock_stake` recompute rewards from a running `principal` baseline that is updated on every call, not from a delta since the last epoch boundary.

- `vesting::unlock_rewards` computes rewards via `total_accumulated_rewards`, which is `total_active_stake - remaining_grant - commission_amount`, then calls `unlock_stake(vesting_contract, amount)` [1](#0-0) .
- That flows into `staking_contract::unlock_rewards`, which calls `staking_contract_amounts` to get `accumulated_rewards` and then calls `unlock_stake(staker, operator, staker_rewards)` [2](#0-1) .
- Inside `unlock_stake`, `request_commission_internal` is invoked first, which immediately sets `staking_contract.principal = total_active_stake - commission_amount` [3](#0-2) , and then `unlock_stake` further decrements `staking_contract.principal -= amount` after unlocking the staker's share [4](#0-3) .

After the first call, `principal` is updated to equal `total_active_stake` (baseline reset), so a second call within the same epoch (before any new rewards accrue) computes `accumulated_rewards = total_active_stake - principal = 0`, and `unlock_stake` short-circuits when `amount == 0` [5](#0-4) . This means the second `unlock_rewards` call unlocks nothing — it cannot double count.

This exact scenario is already covered by an existing regression test in the framework, `test_unlock_rewards_twice_should_not_double_count`, which calls `unlock_rewards` twice in the same epoch and asserts that `pending_inactive` stake matches only the first accrual [6](#0-5) .

Since the accounting invariant (principal re-baselining after every unlock) already blocks the proposed attack path, and a passing test in the codebase confirms this, the finding is rejected per the Review Path's requirement to "reject if role checks and accounting invariants already block the path."
