### Title
Zip extraction lacks zip-slip path sanitization, allowing `os.Lchown`/`os.Chtimes`/file writes outside the intended extraction directory - ([File: helpers/archives/zip_extract.go], [File: helpers/archives/zip_extra_unix.go])

### Summary
`ExtractZipArchive` in `helpers/archives/zip_extract.go` writes, chmods, and processes extra fields for every `file.Name` in a zip archive without ever validating that the resolved path stays within the intended extraction root. `processZipUIDGidField` (`helpers/archives/zip_extra_unix.go:37-48`) then calls `os.Lchown(file.Name, UID, GID)` directly on that unsanitized name, so a crafted archive entry with a traversal name (e.g. `../../other-project/checkout/file`) plus a `ZipUIDGidFieldType` extra field can change ownership of a file outside the job's own directory tree.

### Finding Description
`extractZipFile`/`extractZipDirectoryEntry`/`extractZipSymlinkEntry`/`extractZipFileEntry` in `helpers/archives/zip_extract.go:12-83` use `file.Name` directly for `os.Mkdir`, `os.Symlink`, `os.OpenFile`, etc., with no `filepath.Abs`/prefix check against the extraction root. This is in contrast to the sibling tar/zstd extractor (`commands/helpers/archive/tarzstd/tarzstd_extractor.go:56-64`), which explicitly computes `filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects any path that escapes the chroot (`"cannot be extracted outside of chroot"`). No equivalent guard exists anywhere in `helpers/archives/zip_extract.go` or `zip_extra.go`. The only path-related check present is `errorIfGitDirectory`, which only guards against `.git` directory overwrite, not traversal.

After all files are written, `ExtractZipArchive` (`helpers/archives/zip_extract.go:98-107`) calls `processZipExtra(&file.FileHeader)` for every entry, which dispatches on the `ZipUIDGidFieldType`/`ZipTimestampFieldType` extra fields (`helpers/archives/zip_extra.go:96-121`) to `processZipUIDGidField`, which performs `os.Lchown(file.Name, int(ugField.UID), int(ugField.Gid))` (`helpers/archives/zip_extra_unix.go:48`) using the same unsanitized `file.Name`.

Since `archive/zip.FileHeader.Name` is entirely attacker-controlled (it's just a string field read from the archive being decompressed, e.g. built by a job or supplied as a cache/artifact archive), a job that controls the zip content processed by `ExtractZipFile`/`ExtractZipArchive` (cache restore, artifact extraction) can supply a header name containing `../` sequences. If `extractZipFileEntry`/`extractZipSymlinkEntry` succeeds in first creating (or an existing file already resolves to) a path outside the extraction root — which is possible because `os.MkdirAll(filepath.Dir(file.Name), ...)` and `os.OpenFile` follow the traversal with no containment check — the subsequent `Lchown` call in `processZipUIDGidField` operates on that same out-of-root path.

### Impact Explanation
On a shared runner filesystem where multiple jobs/projects share a host filesystem (shell/custom executors, or shared cache/build directories), a job can craft a cache or artifact zip whose entries traverse out of its own build/cache directory and change ownership (`os.Lchown`) of files belonging to another job or project, or of shared runner state, without needing write permission through legitimate means. This is a genuine path-containment failure feeding directly into a privileged filesystem mutation (`Lchown`), matching the described "cross-project state corruption" scoped impact — contingent on the ownership boundary actually being crossable, which depends on OS file permissions allowing the traversal write/lchown to succeed (the job's own user must have permission on the target path for `Lchown`/`Mkdir` to succeed, since `Lchown` only changes ownership, it does not grant new access, and typically requires either owning the file or running as root).

### Likelihood Explanation
Reachable whenever a job-controlled zip archive is extracted via `ExtractZipArchive`/`ExtractZipFile` — this includes cache restoration (`commands/helpers/cache_extractor.go`) and artifact download (`commands/helpers/archive/ziplegacy`, `fastzip`) paths. No CI-config-level sanitization of zip entry names was found in this file or its direct callers. The main mitigating factor limiting real cross-project impact is standard OS filesystem permissions on shared runner hosts (the job's OS user must have write/ownership access to the target path for the traversal write and the `Lchown` to actually succeed), and most default configurations isolate job directories by unique paths/users, which is not verified in this codebase and depends on runner/executor configuration.

### Recommendation
Add a path-containment check identical in spirit to the tarzstd extractor's guard before any filesystem operation in `helpers/archives/zip_extract.go`: compute `filepath.Abs` (or `filepath.Join` + `filepath.Clean`) of `file.Name` against the known extraction root, reject (or skip with a warning) any entry whose resolved path does not have the root as a prefix, and apply the same check before calling `processZipExtra`/`processZipUIDGidField`/`processZipTimestampField` so `os.Lchown`/`os.Chtimes` never target a path outside the root.

### Proof of Concept
Go unit test (place in `helpers/archives/zip_extract_test.go` or similar):
```go
func TestExtractZipArchiveRejectsPathTraversal(t *testing.T) {
    dir := t.TempDir()
    outsideDir := t.TempDir()
    targetFile := filepath.Join(outsideDir, "victim")
    require.NoError(t, os.WriteFile(targetFile, []byte("victim"), 0644))

    // build a zip with a traversal entry name that resolves to targetFile
    rel, _ := filepath.Rel(dir, targetFile)
    traversalName := rel // e.g. "../<tmp2>/victim"

    var buf bytes.Buffer
    zw := zip.NewWriter(&buf)
    fh := &zip.FileHeader{Name: traversalName}
    fh.SetMode(0644)
    w, _ := zw.CreateHeader(fh)
    _, _ = w.Write([]byte("evil"))
    zw.Close()

    zr, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))

    origWD, _ := os.Getwd()
    os.Chdir(dir)
    defer os.Chdir(origWD)

    err := ExtractZipArchive(zr)
    require.NoError(t, err) // extraction "succeeds" silently

    content, _ := os.ReadFile(targetFile)
    // BUG: file outside extraction root got overwritten
    assert.Equal(t, "victim", string(content), "file outside extraction root should not have been modified")
}
```
Expected result today: the assertion fails because `targetFile` content becomes `"evil"`, proving the missing containment check. A companion test can add a `ZipUIDGidFieldType` extra field to the header and assert that `os.Lstat(targetFile).Sys().(*syscall.Stat_t).Uid/Gid` is unchanged from before extraction, which currently fails as well since `os.Lchown` is invoked on the traversal path.
