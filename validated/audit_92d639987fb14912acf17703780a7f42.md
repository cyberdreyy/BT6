### Title
Gateway `HandleLegacyUserMessage` staleness check has no upper bound on `payload.Timestamp`, allowing indefinite replay of a single signed web_api_trigger message - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The freshness check in `HandleLegacyUserMessage` only rejects messages that are too old; it never rejects messages whose `payload.Timestamp` is set arbitrarily far in the future. An attacker who can produce one validly-signed `web_api_trigger` message (e.g. a sender already present in a workflow's `allowedSenders` list, or any signer if the gateway-level `// TODO: apply allowlist and rate-limiting here` remains unimplemented) can set a far-future timestamp and replay the exact same signed message indefinitely, since the gateway staleness gate will never flag it as stale.

### Finding Description
The relevant check is: [1](#0-0) 

`uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` only tests the "too old" direction. If `payload.Timestamp` (an attacker-controlled `int64` field in `webapicap.TriggerRequestPayload`, see [2](#0-1) ) is set to a value far beyond the current time (e.g. decades in the future), `uint(payload.Timestamp)` becomes a very large number, so `now - maxAge > timestamp` is always false — the message is never treated as stale, regardless of how much wall-clock time actually elapses.

There is no complementary check that rejects timestamps that are unreasonably ahead of `time.Now()`. The schema comment even documents the intended (but unimplemented) behavior: "Timestamp of the event (unix time), needs to be within certain freshness to be processed" ( [3](#0-2) ).

Once the staleness gate is bypassed, the message proceeds to `common.ValidatedRequestFromMessage` and is fanned out to all DON members unconditionally: [4](#0-3) 

On the workflow-node side, `triggerConnectorHandler.processTrigger` enforces `allowedSenders`/topic/rate-limit checks but performs **no freshness/timestamp validation of its own** — I found no `Timestamp` check anywhere in `core/capabilities/webapi/trigger/trigger.go`: [5](#0-4) 

So the only place in the reachable code path that is supposed to enforce message freshness is the gateway's staleness check, and it can be permanently defeated by choosing a future timestamp once at signing time. Because the gateway forwards the byte-identical signed `Message` on every replay (same `Signature`, same `MessageId`, same `Payload`), the attacker never needs to re-sign anything — one captured/self-signed request stays "fresh" forever and can be resubmitted to the gateway HTTP endpoint at will.

### Impact Explanation
This is a logic flaw that defeats the intended anti-replay/staleness control (`MaxAllowedMessageAgeSec`) for legacy web-API trigger messages. Any sender capable of producing one valid signature for a `web_api_trigger` message can convert it into a permanently-replayable credential, allowing them to repeatedly re-trigger workflow executions with the same payload at arbitrary times of their choosing rather than being bound to the intended freshness window. This maps to the "unauthorized job run" bounty class: repeated/unbounded capability trigger execution outside the designed request-validity window. The severity is bounded by the fact that `allowedSenders`/topic authorization at the node (`processTrigger`) still gates whether the trigger actually reaches a registered workflow, so this is a control-bypass on the freshness/anti-replay guarantee rather than a full authentication bypass.

### Likelihood Explanation
Exploitation only requires the ability to produce one ECDSA-signed `api.Message` for method `web_api_trigger` with a payload whose `Timestamp` is set far in the future — trivial for anyone with a private key accepted by `msg.Validate()`/`ExtractSigner`. No additional privileges, node access, or repeated signing are needed; the same captured request can be replayed indefinitely via the gateway's public `ProcessRequest`/HTTP endpoint. This is fully deterministic and repeatable.

### Recommendation
Add an upper-bound check alongside the existing lower-bound (staleness) check, e.g. reject if `uint(payload.Timestamp) > uint(time.Now().Unix()) + h.config.MaxAllowedMessageAgeSec` (or a dedicated clock-skew tolerance), so timestamps set arbitrarily in the future are also rejected. Additionally, consider adding message-ID/trigger-event-ID based replay protection independent of the timestamp, and enforce the same freshness bound at the node's `processTrigger`, not solely at the gateway.

### Proof of Concept
Go unit test to add to `core/services/gateway/handlers/capabilities/handler_test.go`:
```go
t.Run("future timestamp bypasses staleness check", func(t *testing.T) {
    farFuture := strconv.FormatInt(time.Now().Unix()+int64(100*365*24*3600), 10) // ~100 years ahead
    futureMsg := triggerRequest(t, nodes[0].PrivateKey, []string{"daily_price_update"}, "", farFuture, "")
    cb := hc.NewCallback()
    err := handler.HandleLegacyUserMessage(ctx, futureMsg, cb)
    require.NoError(t, err)

    // EXPECTED (fixed behavior): should be rejected as invalid/out-of-range timestamp
    // ACTUAL (current behavior): message is forwarded to DON members as if fresh
    don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)
    r, err := cb.Wait(t.Context())
    require.NoError(t, err)
    require.NotEqual(t, api.NoError, r.ErrorCode, "message with far-future timestamp must not be accepted as fresh")
})
```
Run this alongside the existing `"sad case stale message"` test to demonstrate the staleness check catches only the past-timestamp direction and misses the future-timestamp direction, confirming indefinite replay validity.

// processTrigger iterates over each topic, checking against senders and rateLimits, then starting event processing and responding
func (h *triggerConnectorHandler) processTrigger(ctx context.Context, gatewayID string, body *api.MessageBody, sender ethCommon.Address, payload webapicap.TriggerRequestPayload) error {
	// Pass on the payload with the expectation that it's in an acceptable format for the executor
	wrappedPayload, err := values.WrapMap(payload)
	if err != nil {
		return fmt.Errorf("error wrapping payload %w", err)
	}
	topics := payload.Topics

	// empty topics is error for V1
	if len(topics) == 0 {
		return errors.New("empty Workflow Topics")
	}

	// workflows that have matched topics
	matchedWorkflows := 0
	// workflows that have matched topic and passed all checks
	fullyMatchedWorkflows := 0
	for _, trigger := range h.registeredWorkflows {
		for _, topic := range topics {
			if trigger.allowedTopics[topic] {
				matchedWorkflows++
				if !trigger.allowedSenders[sender.String()] {
					err = fmt.Errorf("unauthorized Sender %s, messageID %s", sender.String(), body.MessageId)
					h.lggr.Debugw(err.Error())
					continue
				}
				if !trigger.rateLimiter.Allow(body.Sender) {
					err = fmt.Errorf("request rate-limited for sender %s, messageID %s", sender.String(), body.MessageId)
					continue
				}
				fullyMatchedWorkflows++
				TriggerEventID := body.Sender + payload.TriggerEventId

				// Emit trigger execution started event
				workflowExecutionID, genErr := events.GenerateExecutionID(trigger.workflowID, TriggerEventID)
				if genErr != nil {
					h.lggr.Errorw("failed to generate execution ID", "err", genErr)
					workflowExecutionID = ""
				}
				emitErr := events.EmitTriggerExecutionStarted(ctx, map[string]string{}, TriggerEventID, workflowExecutionID)
				if emitErr != nil {
					h.lggr.Errorw("failed to emit trigger execution started event", "err", emitErr)
				}

				tr := capabilities.TriggerResponse{
					Event: capabilities.TriggerEvent{
						TriggerType: TriggerType,
						ID:          TriggerEventID,
						Outputs:     wrappedPayload,
					},
				}
				select {
				case <-ctx.Done():
					return nil
				case trigger.ch <- tr:
					// Sending n topics that match a workflow with n allowedTopics, can only be triggered once.
					break
				}
			}
		}
	}
