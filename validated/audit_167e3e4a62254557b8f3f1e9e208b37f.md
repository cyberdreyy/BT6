### Title
Uncapped builder withdrawal amount lets execution layer pay more Gwei than the beacon state actually deducts from the builder - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` places the raw, unclamped requested `withdrawal.amount` from `state.builder_pending_withdrawals` into the `Withdrawal` object that becomes part of `state.payload_expected_withdrawals`. This is the value the execution layer is committed to pay to `withdrawal.fee_recipient`. Later, `apply_withdrawals` only reduces `state.builders[builder_index].balance` by `min(withdrawal.amount, builder_balance)`. If a queued request amount exceeds the builder's real balance, the CL state saturates the deduction at the available balance, but the EL-committed `Withdrawal.amount` (and therefore the actual ETH paid out) remains the full, un-saturated request. This breaks the "no Gwei created" equality: value paid on the execution side exceeds value destroyed on the consensus side.

### Finding Description
In `get_builder_withdrawals` (specs/gloas/beacon-chain.md): [1](#0-0) 
the withdrawal envelope amount is copied straight from the pending request:
```python
withdrawals.append(
    Withdrawal(
        index=withdrawal_index,
        validator_index=convert_builder_index_to_validator_index(builder_index),
        address=withdrawal.fee_recipient,
        amount=withdrawal.amount,
    )
)
```
There is no `min(withdrawal.amount, state.builders[builder_index].balance)` clamp here, unlike the validator sweep path (`amount=balance` / `balance - max_effective_balance`) which always derives the amount from the actual on-chain balance.

Later, `apply_withdrawals` performs the actual balance mutation and explicitly saturates it: [2](#0-1) 
```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
```

`state.payload_expected_withdrawals` (set from these same `Withdrawal` objects via `update_payload_expected_withdrawals`) is the value the execution layer is required to honor when it builds/validates the payload — i.e., it is the source of truth for how much ETH is minted to `withdrawal.address`. Because the amount recorded there is `withdrawal.amount` (uncapped), while the CL-side ledger only destroys `min(withdrawal.amount, builder_balance)` of stake, the two sides diverge whenever a pending request's amount exceeds the builder's actual balance at processing time.

The unit test for this exact configuration confirms the divergence is the spec's actual behavior, not a test artifact: [3](#0-2) 
Here a `builder_pending_withdrawals` entry requests 5 ETH while the builder only has 1 ETH; the assertions show `withdrawal_amounts_builders={builder_index: withdrawal_amount}` (i.e. the committed/paid amount is the full 5 ETH request) while `builder_balances={builder_index: 0}` (only 1 ETH was actually deducted).

### Impact Explanation
This breaks the equality "Gwei destroyed on the consensus side == Gwei paid on the execution side" for builder withdrawals. The execution layer mints/pays `withdrawal.amount` (5 ETH in the test) to `fee_recipient`, an address chosen by whoever queued the `BuilderPendingWithdrawal`, while only 1 ETH of real stake is removed from the builder's balance. The remaining 4 ETH is Gwei paid to a recipient without any corresponding stake being burned/consumed — i.e., Gwei created and paid to a (potentially) non-owner party, which per the rubric is a Critical-severity class of finding ("Gwei created, destroyed or paid to a non-owner").

This is a stronger, deterministic analog of the original external report's rounding/timing unfairness: instead of merely disadvantaging users due to non-linear rebasing, here the specification itself allows a committed payment that is arithmetically inconsistent with the balance actually deducted, whenever `builder_pending_withdrawals` entries are not strictly bounded to be `<= builder.balance` at all times up to and including processing.

### Likelihood Explanation
Whether this is reachable depends on whether some other, unlisted-in-scope mechanism guarantees `builder_pending_withdrawals[i].amount <= builders[builder_index].balance` at all times between enqueue and processing (e.g., enforced at request time and immutable balance in between). Within the in-scope withdrawal-processing code itself, no such invariant is asserted or maintained — `get_builder_withdrawals` performs no balance check, and the balance could change between when a withdrawal was queued and when it is processed (e.g., via other balance-affecting operations on `state.builders[...].balance`, or simply a withdrawal request amount that was queued larger than the balance in the first place). Given the test file explicitly exercises and asserts this exact "insufficient balance" scenario as expected/passing behavior, the code path is definitely reachable under normal spec execution, not merely a theoretical edge case.

### Recommendation
Clamp the committed withdrawal amount to the available balance at the point the `Withdrawal` object is constructed in `get_builder_withdrawals`, mirroring what `apply_withdrawals` does for the actual balance mutation:
```python
amount=min(withdrawal.amount, state.builders[builder_index].balance)
```
so that the amount committed to the execution layer (and thus the amount minted to `fee_recipient`) can never exceed what is actually deducted from `state.builders[builder_index].balance`, preserving the Gwei conservation invariant between the CL and EL.

### Proof of Concept
1. Builder `B` has `state.builders[B].balance = 1_000_000_000` (1 ETH).
2. `state.builder_pending_withdrawals` contains `BuilderPendingWithdrawal(builder_index=B, fee_recipient=addr, amount=5_000_000_000)` (5 ETH request), and is due for processing.
3. `get_builder_withdrawals` runs, appending `Withdrawal(validator_index=convert(B), address=addr, amount=5_000_000_000)` unmodified into `withdrawals`.
4. `get_expected_withdrawals` returns this withdrawal; `update_payload_expected_withdrawals` sets `state.payload_expected_withdrawals` to include it — this is the amount the execution layer will pay to `addr`.
5. `apply_withdrawals` runs: `builder_balance = 1_000_000_000`; `state.builders[B].balance -= min(5_000_000_000, 1_000_000_000)` → `state.builders[B].balance = 0`.
6. Net result: execution layer pays 5 ETH to `addr`, but only 1 ETH of builder stake was destroyed on the consensus layer — 4 ETH of unbacked Gwei is created and paid out.
This exact sequence is validated (as expected/passing) by `test_builder_withdrawal_insufficient_balance`: [4](#0-3)
