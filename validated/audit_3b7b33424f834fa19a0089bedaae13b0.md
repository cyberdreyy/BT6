### Title
Zip-slip in `helpers/archives.ExtractZipArchive` (used by `ziplegacy` extractor) lacks the extraction-root containment check present in `tarzstd` - ([File: helpers/archives/zip_extract.go], [File: commands/helpers/archive/ziplegacy/zip_legacy_extractor.go])

### Summary
`ziplegacy.extractor.Extract` (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go:26-33`) forwards directly to `archives.ExtractZipArchive` (`helpers/archives/zip_extract.go:85-110`), which writes every zip entry using `file.Name` verbatim (`os.OpenFile(file.Name, ...)`, `os.MkdirAll(filepath.Dir(file.Name), ...)`, `os.Symlink`) with **no check that the resolved path stays inside the target directory**. In contrast, `tarzstd.extractor.Extract` explicitly enforces `filepath.Abs` + `strings.HasPrefix(path, e.dir+separator)` containment before writing (`commands/helpers/archive/tarzstd/tarzstd_extractor.go:57-64`). The `dir` parameter passed to `ziplegacy.NewExtractor` is not even used inside `Extract` at all, confirming the containment logic is entirely absent for that path.

### Finding Description
Call path confirmed:
- `CacheExtractorCommand.Execute` / `ArtifactsDownloaderCommand.Execute` → `openArchive(c.File)` (`commands/helpers/cache_extractor.go:646`, `commands/helpers/artifacts_downloader.go:125`) → `archive.NewExtractor(format, f, size, wd)` → registered extractor's `Extract`.
- `openArchive` (`commands/helpers/artifacts_downloader.go:148-173`) selects the format purely by **sniffing the first 4 magic bytes** of the downloaded file: zstd magic → `archive.TarZstd`, gzip magic → `archive.Gzip`, and **default (no match) → `archive.Zip`**. Ordinary zip data has no reserved magic bytes checked here, so any non-zstd archive defaults to `archive.Zip`.
- By default (unless `FF_USE_FASTZIP` is enabled), `archive.Zip`/`archive.ZipZstd` extractor is `ziplegacy.NewExtractor` (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go:19-22`, registered in `commands/helpers/archive/ziplegacy/zip_legacy_archiver.go:16-21`), so `archive.Zip` is in fact the **default/most common** format for artifacts and caches, not an edge case requiring special "forcing."
- `ziplegacy.extractor.Extract` ignores `e.dir` and calls `archives.ExtractZipArchive(zr)`, which for every `zip.File` entry calls `extractZipFile(file)` → `os.MkdirAll(filepath.Dir(file.Name), ...)` and `os.OpenFile(file.Name, ...)`/`os.Symlink` using the **raw entry name from the zip file with no `..`, absolute-path, or containment validation** (`helpers/archives/zip_extract.go:41-83`). The only defensive check present (`errorIfGitDirectory`, `helpers/archives/path_check_helper.go`) blocks `.git`-prefixed paths only, not `../` traversal or absolute paths.
- Whether an attacker can get an actual crafted-traversal entry into the zip depends on the archiver side, which was not fully verified: `ziplegacy`'s `Archive` (`commands/helpers/archive/ziplegacy/zip_legacy_archiver.go:35-43`) calls `archives.CreateZipArchive` with raw file paths from the enumerated `files` map, and `createZipEntry` (`helpers/archives/zip_create.go:52-83`) sets `fh.Name = fileName` directly without stripping to a relative/contained name (unlike `tarzstd.archiver.Archive`, which computes `filepath.Rel(a.dir, path)` and enforces its own `a.dir`-prefix chroot check at `commands/helpers/archive/tarzstd/tarzstd_archiver.go:72-76`). I was not able to fully trace how `fileArchiver`/`enumerate()` populates the `files` map (relative vs. absolute names, symlink-follow behavior) to confirm end-to-end that a pipeline-author-controlled symlink or `cache:paths`/`artifacts:paths` entry can produce a traversal-named zip entry from the archiver side. That gap should be verified before treating this as fully proven end-to-end (vs. only proven for the extraction side, and for any zip file the runner is asked to extract such as a downloaded/malformed cache blob).

### Impact Explanation
If a malicious or malformed zip archive (with entries like `../../etc/passwd`, absolute paths, or symlink entries pointing outside the tree) is extracted via `archive.Zip`/`archive.ZipZstd` format (the default extraction path, distinct from `tarzstd`), files can be written or overwritten outside the intended cache/artifact/build root, since `archives.ExtractZipArchive` has no root-containment enforcement. This violates the stated invariant that "all archive.Extractor implementations must enforce identical extraction-root containment regardless of format."

### Likelihood Explanation
The extraction-side gap (`ExtractZipArchive` missing containment) is concrete and directly readable in the code, and it is reached by the **default** code path for any zip-format archive (not a rarely-hit branch), since `openArchive` defaults to `archive.Zip` whenever the input isn't zstd/gzip-magic-prefixed. However, full exploitability requires a source of an actual malicious zip with traversal entry names reaching the Runner's extractor (e.g., a compromised/tampered cache object in shared storage, or a bug on the archiver side allowing traversal-named entries to be created from job-controlled inputs). I could not fully confirm the archiver-side path within the available context, so likelihood of a complete unprivileged-attacker-to-impact chain is only partially verified.

### Recommendation
Add the same containment check used in `tarzstd.extractor.Extract` to `archives.ExtractZipArchive` / `ziplegacy.extractor.Extract`: resolve each `file.Name` with `filepath.Join(dir, file.Name)`, take `filepath.Abs`, and reject (or skip with a warning, consistent with the existing warning-based error handling) any entry whose resolved path does not have `dir+separator` as a prefix (and is not `dir` itself). Apply the same fix to symlink target validation (`extractZipSymlinkEntry`) since symlinks can also escape the root even if the entry name itself is contained.

### Proof of Concept
```go
// helpers/archives/zip_extract_traversal_test.go
func TestExtractZipArchive_PathTraversal(t *testing.T) {
    dir := t.TempDir()
    outsideMarker := filepath.Join(filepath.Dir(dir), "pwned_"+filepath.Base(dir))
    defer os.Remove(outsideMarker)

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    fh := &zip.FileHeader{Name: "../" + filepath.Base(outsideMarker)}
    w, _ := zw.CreateHeader(fh)
    w.Write([]byte("pwned"))
    zw.Close()

    // simulate cwd == dir, as ziplegacy extractor relies on process cwd / dir param
    orig, _ := os.Getwd()
    os.Chdir(dir)
    defer os.Chdir(orig)

    zr, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    err := archives.ExtractZipArchive(zr)
    require.NoError(t, err)

    // BUG: file was written outside dir
    _, statErr := os.Stat(outsideMarker)
    assert.NoError(t, statErr, "expected traversal write to escape target dir, proving missing containment")
}
```
Differential fuzz test idea: feed the same crafted `zip.Reader` with a `../` entry through `ziplegacy.NewExtractor(r, size, dir)` and a tar+zstd equivalent through `tarzstd.NewExtractor`, both targeting the same `dir`; assert `tarzstd`'s `Extract` returns an error ("cannot be extracted outside of chroot") while `ziplegacy`'s `Extract` succeeds and leaves a file outside `dir` — demonstrating the inconsistency described in the invariant.
