### Title
Post-default instant withdraw requests reuse the defaulted epoch key, letting a user mint recovery-priced claims against `defaultRecoveryReserve` for funds never part of the default basis - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`finalizeDefaultRecovery` records `defaultRecoveryEpoch = epochNumber`, and `epochNumber` is only incremented inside `deposit()` when the CDO reports `isEpochRunning()` — which cannot be true after default. `requestWithdraw` has an explicit `defaultRecoveryFinalized` branch that routes post-default receipts to `postDefaultRequests`, but `requestInstantWithdraw` has no such guard: it unconditionally writes `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`, i.e. the same epoch key used by the defaulted-epoch claim accounting. A later `claimInstantWithdrawRequest` runs `_claimDefaultedInstantWithdrawRequest`, which reads that same per-user epoch slot and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` out of the isolated `defaultRecoveryReserve`. This is the analog of the CVE's "out-of-bounds write into a buffer later read as trusted data": an attacker-controlled write lands in a slot that recovery accounting treats as pre-default claim basis.

### Finding Description
- `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (lines 690–696). After default, no code path can bump `epochNumber` (`deposit()` increments it only when `isEpochRunning()` is true, line 607–610).
- `requestInstantWithdraw` (lines 356–375) performs `_ensureDefaultRecoveryInitialized()` but never checks `defaultRecoveryFinalized`. It adds the new amount to `instantWithdrawsRequestsByEpoch[_user][epochNumber]` — which equals `defaultRecoveryEpoch` — and to `instantWithdrawClaimsByEpoch[epochNumber]`.
- On claim, `claimInstantWithdrawRequest` (lines 380–393) invokes `_claimDefaultedInstantWithdrawRequest` because `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. That function reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — now including the post-default deposit — clears it, decrements `instantWithdrawsRequests` and `instantWithdrawClaimsByEpoch[defaultEpoch]`, burns only `claimBasis` receipt tokens, and transfers `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from `defaultRecoveryReserve` (lines 842–856).
- Broken invariant: recovery reserve must only pay claims that existed in the default basis (`totalBasis` at finalization, lines 679–688). A post-default receipt was never in `totalBasis`, never suffered the haircut, yet draws down the same reserve at `defaultRecoveryPrice` — theft of other claimants' recovery funds (a new instant request of size X pays out `X * recoveryPrice`, diluted from defaulted claimants whose own payouts shrink by the reserve drain).

### Impact Explanation
Any tranche-token holder able to trigger a CDO instant-withdraw request after default finalization (e.g. during the buffer of a pool that defaulted with pending instant claims) mints a receipt that immediately converts into recovery-reserve underlying at the finalized recovery price. Direct theft of the isolated `defaultRecoveryReserve`; each wei drained reduces payouts to legitimate defaulted-epoch and post-default claimants. Loss bounded by the reserve size and the attacker's mintable receipt amount.

### Likelihood Explanation
Requires: (a) a default finalized via `finalizeDefaultRecovery` with `defaultInstantWithdrawsFinalized == true` (pending instant bucket non-zero at finalization — the prefunded-instant scenario the code explicitly handles), and (b) the CDO's instant-withdraw path remaining callable post-default. `requestInstantWithdraw` in the strategy has no `defaulted`/`defaultRecoveryFinalized` check, mirroring the fact that `requestWithdraw` needed an explicit post-default branch — the instant path was simply missed. Likelihood is moderate: it needs a defaulted pool, but the exploit then needs only ordinary user transactions; no privileged action is involved.

### Recommendation
In `requestInstantWithdraw`, revert when `defaultRecoveryFinalized` is true (or route post-default instant receipts into a separate mapping keyed by a strictly-increasing epoch, e.g. `defaultRecoveryEpoch + 1`). Equivalently, gate `claimInstantWithdrawRequest`'s defaulted-branch so `_claimDefaultedInstantWithdrawRequest` only clears basis that existed at finalization — e.g. cap `claimBasis` at the value snapshotted into `instantWithdrawClaimsByEpoch` before finalization.

### Proof of Concept
A Foundry fork PoC would: (1) deposit into AA/BB, `startEpoch`, then `requestInstantWithdraw` for a victim so `pendingInstantWithdraws` is partially funded; (2) trigger `_handleBorrowerDefault`/`finalizeDefault` and `finalizeDefaultRecovery` so `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized` are true and `defaultRecoveryEpoch == epochNumber`; (3) as attacker, deposit tranche tokens and call the CDO instant-withdraw path so `requestInstantWithdraw` writes `instantWithdrawsRequestsByEpoch[attacker][epochNumber] == defaultEpoch`; (4) call `claimInstantWithdrawRequest(attacker)` and assert the attacker received `amount * defaultRecoveryPrice / 1e18` and `defaultRecoveryReserve` decreased — funds never included in `totalBasis`. Caveat: step (3) requires confirming `IdleCDOEpochVariant`'s instant-withdraw entrypoint does not revert when `defaulted()` is true; if it does, the finding reduces to a defense-in-depth gap rather than an exploitable path, which I could not fully verify within this analysis.
