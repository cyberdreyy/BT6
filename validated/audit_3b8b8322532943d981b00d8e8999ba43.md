## Title
Full stake-account withdrawal during the partitioned epoch-reward distribution window causes already-earned rewards to be silently burned - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
Agave's epoch-reward payout is split into two phases: a **calculation** phase run once at the epoch boundary (which computes each stake account's earned inflation reward for the just-completed epoch and queues it as a `PartitionedStakeReward`), and a **distribution** phase spread over many subsequent blocks of the new epoch, which actually credits the lamports to the stake account. If, in the window between calculation and the specific block that distributes a given account's reward, the staker submits an ordinary `Withdraw` instruction that fully withdraws and closes the stake account, the already-earned reward for that account is looked up in the *live* stakes cache at distribution time, fails to be found, and is unconditionally burned rather than paid — an exact analog of the GaugeV2 `emergencyWithdraw()` issue, where withdrawing wipes out rewards that were earned but not yet "settled".

### Finding Description
`build_updated_stake_reward` looks the stake account up in the **current** `stakes_cache_accounts` map at distribution time, not a frozen snapshot from calculation time: [1](#0-0) 

If the account is not present, it returns `DistributionError::AccountNotFound`: [2](#0-1) 

`StakesCache::check_and_store` removes a stake delegation from the cache the moment the account's lamports reach zero — exactly what happens when a `Withdraw` instruction empties/closes the account: [3](#0-2) 

Back in `store_stake_accounts_in_partition`, any `AccountNotFound` (or other) error results in the previously computed `stake_reward_amount` being added to `stake_reward_lamports_burned` instead of `stake_reward_lamports_minted` — the reward is discarded, not paid to anyone: [4](#0-3) 

The code's own comment acknowledges the assumption that this "should never" occur because "stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions": [5](#0-4) 

That assumption does not hold across the full calculation→distribution window: a stake that was delegated and earning rewards during rewarded epoch `N` can have `deactivation_epoch = N`, making its effective stake zero starting epoch `N+1` (the distribution epoch) — at which point the stake program's own `Withdraw` instruction permits the staker to withdraw *all* lamports and close the account, since there is no remaining active/activating/deactivating stake to protect. Nothing in the stake program checks whether an epoch-reward payout for that account is still pending in the partitioned-distribution queue. There is a unit test that explicitly exercises and expects the `AccountNotFound` burn path for a non-existent stake pubkey, confirming the burn behavior is a real, reachable code path rather than a theoretical one: [6](#0-5) 

Distribution of a full epoch's worth of stake rewards is intentionally spread across many blocks (`REWARD_CALCULATION_NUM_BLOCKS` and subsequent partitions) specifically so it doesn't have to happen atomically at the epoch boundary, which is exactly what creates the window for this race.

### Impact Explanation
Any staker whose stake becomes fully deactivated in the reward-eligible epoch can, immediately after the new epoch begins, submit a normal, unprivileged `Withdraw` instruction to close out their stake account before the runtime's own partitioned distribution reaches their pubkey. The reward they legitimately earned for the prior epoch (calculated and queued) is then permanently and silently burned — capitalization is reduced accordingly by omission from `stake_reward_lamports_minted` — with no error surfaced to the user and no path to reclaim it. This is a direct, unsigned loss of stake-reward funds for the affected account, matching the "stake or reward corruption" / fund-loss impact category. It also creates non-deterministic outcomes purely dependent on transaction timing relative to internal, non-user-visible distribution scheduling.

### Likelihood Explanation
This requires no special privileges, precompiles, or malicious leader/peer behavior — only an ordinary sequence of stake operations (`DeactivateStake` then, once effective stake hits zero, `WithdrawStake` for the full balance) timed to land before the runtime processes that specific stake pubkey's partition. Because reward distribution is deliberately spread across many blocks of the epoch, there is a non-trivial window (up to nearly the number of partitioned blocks) in which this is achievable by simply monitoring epoch/slot progress and submitting the withdrawal transaction promptly at the start of the new epoch.

### Recommendation
Either (a) exclude/adjust the withdrawable amount so a stake account cannot be fully closed while it still has a pending, uncredited `PartitionedStakeReward` entry for a prior epoch, or (b) have the distribution phase pay the burned/undeliverable reward to a designated fallback (e.g., re-credit if the account is later recreated, or treat consistently with other "burned" reward handling) instead of unconditionally discarding it, or (c) snapshot the exact set of eligible stake accounts/lamports needed for distribution at calculation time so distribution cannot be starved by intervening withdrawals.

### Proof of Concept
1. Delegate a stake account and let it earn rewards through epoch `N`.
2. Near the end of epoch `N`, call `deactivate_stake` so `deactivation_epoch = N`.
3. At the epoch boundary, the runtime's calculation phase (`redeem_delegation_rewards`) computes a nonzero `stake_reward` for epoch `N` and queues a `PartitionedStakeReward` for later distribution in epoch `N+1`.
4. As soon as epoch `N+1` starts, effective stake for the account is `0` (fully deactivated), so `withdraw` now permits withdrawing the entire balance, closing the account (`lamports == 0`).
5. `StakesCache::check_and_store` removes the delegation from `stake_delegations` immediately upon processing the withdraw transaction: [3](#0-2) 
6. When the runtime later reaches the block/partition responsible for distributing this account's queued reward, `build_updated_stake_reward` fails with `DistributionError::AccountNotFound`: [1](#0-0) 
7. `store_stake_accounts_in_partition` records this as `stake_reward_lamports_burned` rather than minting it to the (now-closed) account: [7](#0-6) 
8. The staker never receives the reward they earned for epoch `N`, with no error and no recovery path.
