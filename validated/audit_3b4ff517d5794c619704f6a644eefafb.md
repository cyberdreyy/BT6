### Title
Panic in `SourceBuffer::new_checked_with_verified_build_hash` when buffer account data length equals `size_of_buffer_metadata()` exactly - ([File: runtime/src/bank/builtins/core_bpf_migration/source_buffer.rs])

### Summary
`new_checked_with_verified_build_hash` computes `end_offset` by scanning the *entire* `data` slice (not just the ELF portion after `offset`) for the last non-zero byte, then slices `&data[offset..end_offset]`. When `data.len() == UpgradeableLoaderState::size_of_buffer_metadata()`, the account contains only the bincode-serialized `Buffer` metadata, whose enum discriminant is a non-zero byte located at an index below `offset`. This forces `end_offset < offset`, and the subsequent slice expression panics because the slice start index exceeds the end index.

### Finding Description
In `source_buffer.rs`:

```rust
let offset = UpgradeableLoaderState::size_of_buffer_metadata();
let end_offset = data.iter().rposition(|&x| x != 0).map_or(offset, |i| i + 1);
let buffer_program_data = &data[offset..end_offset];
``` [1](#0-0) 

`data.iter().rposition(...)` searches the whole account buffer, including the metadata bytes before `offset`, rather than only the ELF-bytes region `data[offset..]`. `UpgradeableLoaderState::Buffer { authority_address }` bincode-serializes to a non-zero 4-byte enum discriminant (variant index `1`) followed by an `Option<Pubkey>` tag/byte. When `data.len() == offset` exactly (i.e., no ELF bytes are appended at all), the entire account content is just this metadata, and its non-zero discriminant byte sits at an index strictly less than `offset`. `rposition` therefore returns that low index, producing `end_offset = i + 1 < offset`. The subsequent slice operation `&data[offset..end_offset]` then panics with a Rust runtime bounds-order panic ("slice index starts at `offset` but ends at `end_offset`") because slicing requires `start <= end`.

This is reachable because `new_checked_with_verified_build_hash` first calls `new_checked`, whose only content requirement is that `data.len() >= buffer_metadata_size` and that the first `buffer_metadata_size` bytes bincode-deserialize as `UpgradeableLoaderState::Buffer { .. }` [2](#0-1) . Nothing in `new_checked` rejects a buffer account whose data length equals `buffer_metadata_size` exactly — an attacker can write such a minimally-sized, syntactically valid Buffer account (owned by `bpf_loader_upgradeable`) on-chain ahead of the migration.

### Impact Explanation
This reproduces the same decoder-panic class as the previously identified scenario (out-of-range `data[offset..end_offset]` slicing due to scanning the whole array instead of the ELF-only region), but here the panic is *guaranteed* rather than merely possible: whenever `data.len() == size_of_buffer_metadata()`, the Buffer variant's non-zero discriminant is necessarily inside `data[0..offset]`, so `end_offset < offset` unconditionally. This crashes the validator process handling the core BPF migration path that reads this attacker-controlled buffer account, matching the "decoder panic" / validator crash impact category.

### Likelihood Explanation
Preconditions are minimal and fully within attacker capability: write a buffer account owned by `bpf_loader_upgradeable` containing exactly `size_of_buffer_metadata()` bytes of bincode-serialized `UpgradeableLoaderState::Buffer { authority_address: None }` (5 bytes: discriminant `[1,0,0,0]` + option tag `0`), with no trailing ELF bytes. This is a single on-chain account write, requiring no privileged validator/gossip/leader control, and is deterministically triggered the next time the core BPF migration logic processes that buffer address via `new_checked_with_verified_build_hash`.

### Recommendation
Fix `end_offset` computation to search only within `data[offset..]`, not the whole array, e.g.:
```rust
let end_offset = data[offset..]
    .iter()
    .rposition(|&x| x != 0)
    .map_or(offset, |i| offset + i + 1);
```
This guarantees `end_offset >= offset` always, eliminating the panic for both this degenerate case and the general case where trailing metadata bytes are non-zero.

### Proof of Concept
```rust
#[test]
fn test_source_buffer_zero_length_elf_no_panic() {
    let bank = create_simple_test_bank(0);
    let buffer_address = Pubkey::new_unique();

    let buffer_metadata_size = UpgradeableLoaderState::size_of_buffer_metadata();
    // data.len() == buffer_metadata_size exactly: no ELF bytes at all.
    let mut data = vec![0u8; buffer_metadata_size];
    bincode::serialize_into(
        &mut data[..],
        &UpgradeableLoaderState::Buffer { authority_address: None },
    )
    .unwrap();

    store_account(&bank, &buffer_address, &data, &bpf_loader_upgradeable::id());

    // Expect a graceful error (e.g., BuildHashMismatch or InvalidBufferAccount),
    // not a panic on `&data[offset..end_offset]`.
    let result = std::panic::catch_unwind(|| {
        SourceBuffer::new_checked_with_verified_build_hash(
            &bank,
            &buffer_address,
            Hash::default(),
        )
    });
    assert!(result.is_ok(), "decoder panicked on minimally-sized buffer account");
}
```
Expected current behavior: the test panics inside the slice expression `&data[offset..end_offset]` (`offset > end_offset`). Expected behavior after fix: the call returns `Err(CoreBpfMigrationError::BuildHashMismatch(..))` without panicking, for all `data.len()` in `[buffer_metadata_size, buffer_metadata_size + N]` under fuzzing.
