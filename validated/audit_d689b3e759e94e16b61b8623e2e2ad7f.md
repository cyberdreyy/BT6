### Title
Stale confirmations from removed multisig members allow request execution below the intended threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member()` in `multisig2/src/lib.rs` only purges confirmations for requests that the *removed* member originally created, but never scrubs that member's confirmation entries from other requests they had merely confirmed (but did not originate). Because `confirm()` counts entries in the `confirmations` set without verifying the confirmers are still live members, a request can later be pushed past `num_confirmations` using a mix of live-member confirmations plus one or more stale confirmations from accounts/keys that have since been removed from the multisig.

### Finding Description
`confirm()` decides whether to execute a request purely by counting set size against the fixed threshold: [1](#0-0) 

`delete_member()` is the only place confirmations get cleaned up in response to membership changes, and it filters strictly on `r.member == member`, i.e., requests *authored* by the deleted member: [2](#0-1) 

There is no corresponding scan of the `confirmations: LookupMap<RequestId, HashSet<String>>` map to strip out entries belonging to the just-removed member for requests authored by *someone else*. As a result, if member `D` confirms a request `R` authored by member `A`, and `D` is later removed via a legitimate `DeleteMember` request, `R`'s confirmation set still contains `D`'s entry. Any subsequent `confirm()` calls by the remaining live members count `D`'s stale entry toward the threshold in the check at line 304, allowing `R` to execute with fewer *live* member confirmations than `num_confirmations` requires.

The equality this breaks: `confirmations counted == live members who approved`. After the bug, `confirmations counted > live members who approved`, so `execute_request` fires while the actual number of currently-authorized approvers is below the configured `num_confirmations`.

### Impact Explanation
This is a Critical-class issue per the defined impact list: "a multisig request executed below threshold." An attacker who is one of the remaining members (or colludes with fewer members than the required threshold) can push through transfers, `AddKey`, `DeployContract`, or other privileged actions using a confirmation count that mixes live and stale (revoked) approvals, defeating the K-of-N security guarantee the multisig is supposed to provide.

### Likelihood Explanation
Likelihood is Medium: it requires (1) a member confirming a request without being its author, and (2) that member later being removed from the multisig before the request is confirmed to completion or deleted. Both conditions are ordinary, expected multisig operations (membership churn is a normal maintenance action), and nothing in the contract prevents or warns about this sequence — the existing test suite (`add_key_delete_key_storage_cleared`) only covers cleanup of requests *authored* by the deleted member, leaving the non-originator confirmation-leak path completely untested.

### Recommendation
When deleting a member in `delete_member()`, iterate over all entries in `self.confirmations` (not just requests authored by the member) and remove the deleted member's string key from every confirmation set, or alternatively recompute confirmation validity at execution time by intersecting the stored confirmation set with the current `self.members` set (and only counting confirmations from currently valid members) before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize multisig with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request(R)` (e.g., a `Transfer` action) — `R` has 0 confirmations, authored by `A`.
3. `D` calls `confirm(R)` → `confirmations[R] = {D}` (1 of 3).
4. Members confirm and execute a separate `DeleteMember { member: D }` request, removing `D` from `self.members`. Because `delete_member()` only scans `self.requests` for entries where `r.member == D`, and `R` was authored by `A`, `R`'s confirmation set is left untouched — it still contains `D`.
5. `A` calls `confirm(R)` → `confirmations[R] = {D, A}`, size 2, check `2 + 1 >= 3` fails, so `confirmations[R]` becomes `{D, A}` (2 of 3, one of which, `D`, is no longer a member).
6. `B` calls `confirm(R)` → size before insert is 2, `2 + 1 >= 3` succeeds → `execute_request(R)` runs.

Only `A` and `B` — 2 live members — actually approved `R`; `D`'s stale confirmation from before removal was still counted, allowing the request to execute with 2 live approvals instead of the required 3, i.e., below the configured multisig threshold. [3](#0-2) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
