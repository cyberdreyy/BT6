### Title
Quadratic-time replay-set prefix search in `find_majority_prefix_replay_set` allows a single signer to CPU-wedge peer signers - ([File: libsigner/src/v0/signer_state.rs])

### Summary
`GlobalStateEvaluator::find_majority_prefix_replay_set` computes the longest common prefix among all signers' `tx_replay_set`s by repeatedly popping one transaction off a candidate prefix and, on every iteration, re-scanning every stored replay set with `Vec::starts_with`. This is the same bug class as the Mistune `parse_link_text` advisory: an outer O(N) loop combined with an O(N) (or O(M·N)) inner re-scan per iteration yields O(M·N²) work, where N is attacker-controlled and M is the number of tracked signer addresses.

### Finding Description
`find_majority_prefix_replay_set` in `libsigner/src/v0/signer_state.rs` (lines 196-275) is invoked from `determine_global_state()` [1](#0-0)  whenever there is no exact agreement on the `tx_replay_set` among signers. The truncation loop: [2](#0-1) 

pops one `StacksTransaction` at a time from `candidate_prefix` and, for **each** pop, iterates over `tx_replay_sets` (one entry per known signer address) calling `replay_set.0.starts_with(&candidate_prefix)`, which itself is O(len(candidate_prefix)). With N transactions in the largest replay set and M distinct signer addresses that submitted a `StateMachineUpdate`, this is O(M·N²).

The input `N` is attacker-controlled: `StateMachineUpdateContent::V1`/`V2` messages carry a `replay_transactions: Vec<StacksTransaction>` field [3](#0-2) . Any single signer (one StackerDB slot) can broadcast a `SignerMessage::StateMachineUpdate` with a very large, syntactically-valid `replay_transactions` vector. On receipt, `handle_state_machine_update` unconditionally stores it and hands it to the evaluator with no size/length bound: [4](#0-3) 

Once inserted, `GlobalStateEvaluator::insert_update` accepts the update for any known address without validating replay-set length [5](#0-4) . Crucially, `determine_global_state()` (and thus `find_majority_prefix_replay_set`) is not a one-shot cost: it is re-executed on essentially **every** `process_event` iteration via `capitulate_viewpoint`, which is called both at the top and bottom of every `process_event` call regardless of the incoming event type [6](#0-5) . So a single malicious `StateMachineUpdate` chunk keeps re-triggering the quadratic computation on every subsequent event the victim signer processes, not just once.

### Impact Explanation
This does not directly break a signature/equality invariant, but it creates a liveness wedge consistent with the "High" bucket in scope: a victim signer's event loop becomes CPU-bound reprocessing the attacker's oversized replay set on every `process_event` call (including on `BlockValidationResponse` and `SignerMessages` for legitimate block proposals). Because `check_submitted_block_proposal`/`check_pending_block_validations`/`handle_event_match` all run inside the same `process_event` invocation and after `capitulate_viewpoint`, sufficient delay in the quadratic computation can cause the signer to miss its `tenure_last_block_proposal_timeout` / block-signing deadlines, effectively wedging it into not signing valid blocks in a timely manner while it churns through the malicious update. A single one-slot signer can trigger this against every other signer in the reward-cycle set (no majority required — it only needs to be a known address in `address_weights` for its update to be accepted).

### Likelihood Explanation
Likelihood is moderate-to-high: any signer (not requiring majority or excess privilege) can submit a `StateMachineUpdate` with an arbitrarily large `replay_transactions` field, since there is no visible upper bound enforced on this vector during deserialization or during `insert_update`. Because `determine_global_state()`/`capitulate_viewpoint` runs on virtually every event-loop pass, the cost is paid repeatedly by every peer signer for as long as the poisoned update remains the latest one stored for that address (until superseded).

### Recommendation
- Enforce a strict maximum length on `replay_transactions` (both at message-validation time and defensively in `GlobalStateEvaluator::insert_update`), rejecting/ignoring updates whose replay set exceeds a small bound.
- Rework `find_majority_prefix_replay_set` to avoid re-scanning all replay sets per truncation step — e.g., by building a trie/radix structure over replay-set prefixes once, or computing weighted prefix-agreement via a single linear-time pass (e.g., grouping by prefix hashes at each length using a rolling computation) instead of O(N) `starts_with` calls repeated O(N) times.
- Cache/rate-limit calls to `determine_global_state()` inside `capitulate_viewpoint` so it isn't unconditionally recomputed on every `process_event` pass when the underlying `address_updates` map has not changed.

### Proof of Concept
1. As any one signer (own private key, own StackerDB slot), construct a `SignerMessage::StateMachineUpdate` with `StateMachineUpdateContent::V1` (or `V2`) whose `replay_transactions` field contains a large number (e.g., tens of thousands) of syntactically valid, distinct `StacksTransaction`s (e.g., minimal `TokenTransfer`s with unique nonces/memos), matching the pattern used in tests to build `StateMachineUpdateMessage::new(..., StateMachineUpdateContent::V1 { ..., replay_transactions: <huge vec> })` [7](#0-6) .
2. Broadcast this chunk to the signer's `.signers-*` StackerDB contract for the `StateMachineUpdate` message slot.
3. Every peer signer receiving it calls `handle_state_machine_update` → `global_state_evaluator.insert_update(address, update)` [4](#0-3) , storing the oversized replay set with no length check.
4. On every subsequent `process_event`, `capitulate_viewpoint` invokes logic that flows into `determine_global_state()` → `find_majority_prefix_replay_set`, which repeatedly performs O(N) `starts_with` scans across all `tx_replay_sets` while iteratively truncating an O(N)-length prefix, reproducing the same superlinear blowup pattern demonstrated by the Mistune PoC (`"[" * n` timings) but with `n` = number of replay transactions.
5. Measure wall-clock time of `process_event` before/after injecting the crafted update; expected superlinear growth as `N` increases, consistent with degraded signer responsiveness.

Note: I was unable to fully verify (within this pass) whether there is an upstream size cap on `StateMachineUpdateContent`/`replay_transactions` enforced elsewhere in message validation (e.g., overall StackerDB chunk size limits acting as an indirect bound on `N`), since the codec/validation path for `StateMachineUpdate` deserialization limits was not fully inspected. If StackerDB chunk size caps effectively bound `N` to a small value, the quadratic blowup may be less severe in practice; this should be confirmed against the actual `MAX_MESSAGE_LEN`/StackerDB chunk size constants before treating this as fully proven at scale.

    fn handle_state_machine_update(
        &mut self,
        signer_public_key: &Secp256k1PublicKey,
        update: &StateMachineUpdate,
        received_time: &SystemTime,
    ) {
        let replay_txids = update.content.replay_txids();
        let pubkey = signer_public_key.to_hex();
        info!(
            "{self}: Received state machine update from signer {pubkey}: {update}";
            "replay_txids" => ?replay_txids
        );
        let address = StacksAddress::p2pkh(self.mainnet, signer_public_key);
        // Store the state machine update so we can reload it if we crash
        if let Err(e) = self.signer_db.insert_state_machine_update(
            self.reward_cycle,
            &address,
            update,
            received_time,
        ) {
            warn!("{self}: Failed to update global state in signerdb: {e}");
        }
        self.global_state_evaluator
            .insert_update(address, update.clone());
    }
