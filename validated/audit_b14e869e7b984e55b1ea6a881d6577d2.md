Confirmed vulnerability. In `store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2442-2538`), when the group signature-weight threshold is reached, the code calls `block_info.mark_locally_accepted(true)` and only *warns* if it returns an `Err` (which it will, per `BlockInfo::check_state`, whenever the block has already reached `GloballyRejected`) — it does **not** stop execution. It unconditionally proceeds to `self.signer_db.insert_block(block_info)` and then `self.broadcast_signed_block(...)` → `handle_post_block` → `post_block()`, pushing the block to the node regardless of the failed state transition.

### Title
Delayed/replayed peer signatures push an already-globally-rejected block to the node - (File: stacks-signer/src/v0/signer.rs)

### Summary
`store_and_process_block_signature` treats a failed `mark_locally_accepted` transition as non-fatal (log-only) whenever `block_info.has_reached_consensus()` is true, then unconditionally broadcasts the block to the stacks-node. This mirrors the Ambire "recovery replay after cancellation" bug class: a decision (`GloballyRejected`, the "cancellation") is finalized, but late-arriving/gossip-replayed acceptance messages that were in flight before the cancellation are still processed as if the cancellation never happened, and the terminal-state guard exists in `BlockInfo::check_state` but its `Err` is deliberately swallowed at the call site instead of aborting the push.

### Finding Description
The intended invariant, documented in `docs/signer-flows.md` (section 2) and enforced by `BlockInfo::check_state` (`stacks-signer/src/signerdb.rs:314-329`), is that global states are terminal against each other: `GloballyRejected -> LocallyAccepted` must fail. [1](#0-0) 

`store_and_process_block_signature` relies on this guard being fatal, but it isn't: [2](#0-1) 

If `mark_locally_accepted` fails because `block_info.state == GloballyRejected`, `has_reached_consensus()` returns `true` (it matches `GloballyRejected` too — `stacks-signer/src/signerdb.rs:344-349`), so the `warn!` branch is skipped entirely and the code falls straight through to `insert_block` and `broadcast_signed_block(...)`, which serializes the block with the collected signatures and POSTs it to the local stacks-node via `handle_post_block` → `stacks_client.post_block()` (`stacks-signer/src/v0/signer.rs:2559-2583`, `stacks-signer/src/client/stacks_client.rs:612-648`).

The trigger requires no majority collusion: a subset of signers whose acceptances/signatures were broadcast before a >30% rejection weight tipped the block to `GloballyRejected` (see `handle_block_response`/`handle_block_rejection` in section 6 of `docs/signer-flows.md:349-387`) can have those acceptance messages arrive late at another signer's mailbox (ordinary network delay/StackerDB polling latency, no attacker action needed) or be redelivered/gossiped again — exactly analogous to the Ambire nonce not being bumped on cancellation, letting a stale "enqueue" message reactivate the flow after a "cancel" was already recorded. Here the "cancel" is `mark_globally_rejected`, and the "stale enqueue" is the delayed/duplicate `BlockResponse::Accepted` messages that reach `store_and_process_block_signature` after that.

Because the code does not check `block_info.state` (or the `mark_locally_accepted` result) before calling `broadcast_signed_block`, a signer can re-push a block its own signer set has already collectively rejected, sending a signed (by the honest signers who accepted before the rejection tipped) but globally-rejected block to its stacks-node for processing.

### Impact Explanation
This breaks the "signed vs validated"/"rejection recounted as an accept" equality explicitly called out as Critical: a block that the signer set already reached a global rejection decision on is nonetheless pushed to the node as if fully accepted, because the terminal-state check's failure is treated as advisory rather than blocking. Depending on how many genuine acceptance signatures are attached, `post_block` could get the node to accept a block the signer set had decided to reject, undermining the state machine's core safety property that global states are terminal.

### Likelihood Explanation
Likelihood is not negligible: it requires only ordinary message reordering/delay between the moment enough rejections tip a block to `GloballyRejected` and the arrival of already-in-flight acceptance/signature messages from signers who accepted earlier — no majority collusion, no key compromise, just gossip timing, which the "plus gossip" clause in scope explicitly allows. `handle_block_response`'s dispatch path for `Accepted` messages routes directly into `store_and_process_block_signature` without first checking `block_info.state` against `GloballyRejected`.

### Recommendation
In `store_and_process_block_signature`, treat a failed `mark_locally_accepted` as fatal: return immediately (do not `insert_block`/`broadcast_signed_block`) whenever the error indicates the block already reached a terminal `GloballyRejected` state, instead of only warning when `!has_reached_consensus()`. E.g.:
```rust
if let Err(e) = block_info.mark_locally_accepted(true) {
    warn!("{self}: refusing to broadcast: {e:?}");
    return;
}
```
removing the `has_reached_consensus()` carve-out that currently lets `GloballyRejected` fall through silently.

### Proof of Concept
1. Signer set (5 signers, weight-equal) proposes/validates block B; signers S1–S3 broadcast `BlockResponse::Accepted` (60% weight, below 70% threshold) before any rejections are seen by signer S5.
2. S4 and a majority-weight rejecting group broadcast `BlockResponse::Rejected` for B; on S5, `handle_block_rejection`/`store_and_process_block_rejection` tallies >30% weight and calls `mark_globally_rejected()`, moving S5's local `block_info.state` to `GloballyRejected` (`stacks-signer/src/v0/signer.rs`, section 6 path).
3. S1's or S2's earlier `Accepted` message (or a StackerDB redelivery of the same slot content) reaches S5 late and is dispatched to `store_and_process_block_signature` for the already-`GloballyRejected` block B.
4. Weight tally in that function counts the accumulated signatures (S1, S2, S3) against `min_weight`; if it happens to cross the 70% threshold from S5's local signature-weight view (e.g., due to view differences on `signer_weights`/asynchronous rejection propagation), `mark_locally_accepted(true)` is called and fails with `Err` because `check_state` blocks `GloballyRejected -> LocallyAccepted`.
5. Because `has_reached_consensus()` is `true` for `GloballyRejected`, the `warn!` is skipped and no `return` happens; execution falls through to `insert_block` and `broadcast_signed_block`, causing S5 to POST the block to its stacks-node via `handle_post_block`/`post_block`, despite S5's own signer DB already recording the block as `GloballyRejected`.
