### Title
V1 `validate_tenure_change_payload` duplicate-tenure guard checks only globally-accepted blocks, missing self-signed but not-yet-globally-accepted blocks - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`SortitionsView::validate_tenure_change_payload` in the v1 (local state) chainstate module guards against re-signing a competing tenure-change block by calling `signer_db.get_last_globally_accepted_block(...)`, whereas the equivalent v2 (`GlobalStateView::validate_tenure_change_payload`) code calls `signer_db.get_last_signed_block(...)`. Because a block only reaches "globally accepted" after a signer-set quorum, a block that this signer has already locally accepted/signed (but that hasn't yet reached global quorum) is invisible to v1's guard, letting a second, competing tenure-change block for the same tenure pass this check.

### Finding Description
The equality that must hold is: *for a given tenure, if this signer has already produced a signature over a block in that tenure (i.e., the block reached at least `LocallyAccepted`), no competing tenure-start block for the same tenure may pass the duplicate-block check.* v2 enforces exactly this via `get_last_signed_block` [1](#0-0) , with an explicit code comment stating that only blocks the signer has signed (locally or globally accepted) should count, while merely pre-committed (unsigned) blocks should not block a competing tenure-start.

v1 instead uses `get_last_globally_accepted_block`, which only returns a block once it has reached network-wide quorum acceptance, not merely this signer's own local acceptance/signature: [2](#0-1) .

Exploit flow: an attacker who wins a single miner slot proposes a normal (non-tenure-change) block for their tenure. The victim signer locally accepts and signs it (`LocallyAccepted`), but before enough other signers do so it does not reach `GloballyAccepted`. The attacker then crafts and gossips a second, competing tenure-change `BlockProposal` for the same tenure (e.g., claiming the tenure needs a restart/fork). This reaches `handle_block_proposal -> check_block_against_local_state -> SortitionsView::check_proposal -> validate_tenure_change_payload`. Because `get_last_globally_accepted_block` returns `None` (the earlier block never reached quorum), the `DuplicateBlockFound` rejection at v1.rs:517 is never triggered, and validation proceeds — potentially leading the victim signer to sign a second, conflicting block at the same tenure/height.

### Impact Explanation
This breaks the uniqueness/chain-safety invariant that a signer must never sign two conflicting blocks in the same tenure. If the same signer contributes its signature to both the original and the competing tenure-change block, this materially weakens the double-signature/equivocation protection the pre-commit-time guard is meant to provide, since the last line of defense at proposal-validation time is bypassed for any block that is locally-but-not-globally accepted. This matches the Critical impact category: a signer signing a conflicting block (chain safety/uniqueness violation) purely from v1's narrower proposal-time duplicate check.

### Likelihood Explanation
Preconditions: v1 (local-state) signer runtime active; an earlier block for the tenure has reached `LocallyAccepted` but has not yet crossed the `GloballyAccepted` quorum threshold — a normal, easily-occurring timing window whenever signer responses are still being aggregated. The attacker only needs to control a single miner slot (to craft the competing tenure-change block) and be able to gossip the proposal — no majority of signers, no privileged role, and no auth token are required. This is directly reproducible any time a proposal is signed locally before the global-acceptance threshold is reached, making it feasible and repeatable across tenures.

### Recommendation
Change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to call `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the v2 implementation and its documented rationale (only unsigned/pre-committed blocks should be treated as replaceable).

### Proof of Concept
Add a test to `stacks-signer/src/chainstate/tests/v1.rs`, modeled on the existing v2 test `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs`:
1. Set up a `SortitionsView` (v1) with a current sortition/tenure.
2. Insert into `SignerDb` a block for that tenure with state `BlockState::LocallyAccepted` (not `GloballyAccepted`).
3. Construct a second, competing `NakamotoBlock` containing a `TenureChangePayload` for the same tenure/consensus hash.
4. Call `SortitionsView::check_proposal` (v1) on the competing block.
5. Assert the call currently returns `Ok(())` (bug) instead of `Err(RejectReason::DuplicateBlockFound)`.
6. After applying the fix (`get_last_signed_block`), assert it returns `Err(RejectReason::DuplicateBlockFound)`, matching v2's behavior.
