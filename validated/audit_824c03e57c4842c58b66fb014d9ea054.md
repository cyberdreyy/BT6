This confirms the analog. `RequestCache` (the newer, correctly-designed cache used elsewhere in the gateway) keys pending requests by `globalId{sender, id}` [1](#0-0)  — explicitly scoping the client-controlled `MessageId` to the authenticated `Sender` to prevent collisions between different senders. The legacy `WebAPIHandler`, however, keys its `savedCallbacks` map purely by the client-supplied `MessageId`, with no sender-scoping, which is the root cause of the analog.

### Title
Cross-user response hijacking/DoS via unscoped, attacker-controlled MessageId collisions in WebAPI gateway handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The `WebAPIHandler.HandleLegacyUserMessage` stores pending user callbacks in a map keyed solely by the client-supplied `MessageId` field, with no binding to the requesting sender/session. Any unprivileged user of the gateway can choose an arbitrary `MessageId` (bounded only by a length check), so a malicious client can pick a `MessageId` that collides with another in-flight legitimate request, silently overwriting that user's pending callback entry. This is directly analogous to the reported gold-card `_commit`/`recommit` bug class: an unprivileged actor controls a value (there, the "try again" trigger; here, the correlation ID) that governs which party ultimately receives an outcome, and the protocol offers no mechanism to prevent a party from manipulating that shared, weakly-scoped state to their advantage.

### Finding Description
`HandleLegacyUserMessage` validates the message and then does: [2](#0-1) 

The only validation performed on `MessageId` is a length/format check inside `Message.Validate()`: [3](#0-2) 

There is no uniqueness enforcement and no scoping by `Sender` — unlike the sibling `RequestCache` abstraction used elsewhere in the gateway, which explicitly composes the key from `{sender, id}` precisely to avoid this class of collision: [1](#0-0) [4](#0-3) 

When a node later responds with the same `MessageId`, the handler looks the callback up purely by that ID and delivers the raw node response to whichever callback is currently registered under it, then deletes the entry: [5](#0-4) 

Because the map assignment (`h.savedCallbacks[msg.Body.MessageId] = ...`) unconditionally overwrites any existing entry, an attacker who submits a second `web_api_trigger` request using the same `MessageId` as an observed/guessed victim request will silently replace the victim's callback. The victim's original HTTP connection then either hangs until the attacker's (or some node's) response resolves the entry, receiving a response that was never meant for it, or times out/loses its response entirely once the entry is deleted by the collision. Entries only expire via a 120-second age-based pruning loop, so there is a real window during which collision is exploitable: [6](#0-5) [7](#0-6) 

### Impact Explanation
This produces cross-user response confusion at the internet-facing gateway boundary: a low-privilege, unauthenticated-beyond-signature client can (a) cause another legitimate client's in-flight `web_api_trigger` request to never receive its correct response (denial of service targeted at a specific request), or (b) receive a response payload that was generated for a different user's request if it happens to resolve into the attacker-owned callback slot. Since `web_api_trigger` responses can carry workflow trigger data intended for a specific requester, this is a legitimate impersonation/response-confusion vector reachable by any client capable of submitting a request to the gateway — no operator or node compromise required.

### Likelihood Explanation
`MessageId` is fully attacker-chosen (only length-bounded to 128 bytes and must not end in a null byte), and the gateway is explicitly internet-facing, accepting user requests from arbitrary unprivileged clients. Guessing or intentionally reusing a `MessageId` requires only that the attacker submit requests using IDs it controls; if IDs are generated client-side with low entropy (e.g., sequential counters, timestamps, or predictable UUIDs from a shared web UI/SDK) collisions become straightforward to engineer, and even without prediction, an attacker can simply flood the handler with many chosen IDs concurrently with a targeted victim's expected ID pattern to increase collision probability. No special role or node access is needed, matching the "unprivileged actor" criteria.

### Recommendation
Scope the `savedCallbacks` key by both `Sender` and `MessageId` (mirroring the `globalId{sender, id}` pattern already used in `RequestCache`), and reject/queue rather than silently overwrite on collision — i.e., replicate the `NewRequest` behavior in `requestcache.go` that returns `"request already exists"` instead of clobbering an existing entry: [4](#0-3) 

### Proof of Concept
1. Victim submits a `web_api_trigger` legacy request to the gateway with `MessageId = "X"`; `HandleLegacyUserMessage` stores `h.savedCallbacks["X"] = victimCallback` and forwards the message to all DON members.
2. Before the DON responds (within the 120s callback TTL), an attacker submits its own `web_api_trigger` request also using `MessageId = "X"` (nothing prevents this — validation only checks length/null-suffix). This overwrites the map: `h.savedCallbacks["X"] = attackerCallback`.
3. When any node responds with `MessageId = "X"` (whether triggered by the victim's or the attacker's forwarded request), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `attackerCallback`, deletes the entry, and delivers the response to the attacker.
4. The victim's original request either receives no response (its callback reference was discarded) or, depending on timing, receives the attacker-influenced response instead of its own — confirming cross-user response confusion caused entirely by unprivileged, gateway-facing input with no cost or node compromise required.
