### Title
Miner Can Indefinitely Refresh Tenure Activity Timer With Never-Finalized Competing Proposals, Blocking Inactivity Fallback - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_latest_block_in_tenure` treats any proposal that merely conflicts with a block the signer has only *pre-committed to* (no signature) as valid "miner activity," calling `signer_db.update_last_activity_time(...)` even though the proposal is rejected (`is_fresh_pre_commit && ... => return false path is not taken here, activity is still stamped`). A single miner controlling the current tenure slot can therefore keep resetting its own activity clock by repeatedly proposing distinct, individually-valid competing blocks at or below the height it has already had pre-committed, without ever letting any of them reach the 70% pre-commit/signature threshold, and without ever producing a block that gets finalized.

### Finding Description
The relevant logic is in `SortitionData::check_latest_block_in_tenure`: [1](#0-0) 

This block explicitly notes: *"A block we have only pre-committed to must NOT veto this proposal, but ... this should still count as activity for the miner."* It calls `update_last_activity_time` for the *tenure* (keyed by `block.header.consensus_hash`) whenever the incoming proposal conflicts with a fresh pre-commit, regardless of whether the incoming proposal itself ever accumulates any pre-commit weight or is ever signed.

This function is invoked both at proposal-arrival time and at signing time via `confirms_latest_block_in_same_tenure` / `check_tenure_change_confirms_parent`: [2](#0-1) 

The activity timestamp this maintains is exactly what feeds `check_miner_inactivity` / `SortitionState::is_timed_out`, which decides whether the signer set gives up on the current miner's tenure and falls back to the prior tenure (per `docs/signer-flows.md` section 8, "TO -- no signed block, and inactive past block_proposal_timeout --> FALL: fall back to prior tenure"): [3](#0-2) 

Because a single miner (the current tenure holder — a one-slot actor, no signer collusion needed) can author an unlimited number of distinct valid transaction sets at the same chain height, each new proposal:
1. Validates fine (executes correctly against the node), so it reaches `PreCommitted`.
2. Conflicts with the previous still-fresh pre-commit at the same/lower height, so it is rejected by `check_latest_block_in_tenure`'s early-return path (line 433, `is_fresh_pre_commit && ... <= ...`).
3. That rejection path nonetheless calls `update_last_activity_time`, refreshing the tenure's liveness clock — with no requirement that the proposal ever gather pre-commit weight, be signed, or be finalized.

This is directly analogous to the reported `increaseAmountFor` griefing bug: a cheap, repeatable, single-actor action ("deposit a tiny amount," here "author another never-finishing proposal") resets a timer (`lock timer` / `last_activity_time`) that governs an important state-machine transition (unlock eligibility / miner-inactivity fallback), without the state machine's stronger invariant (full stake commitment / 70% consensus) ever being satisfied.

### Impact Explanation
This lets a single misbehaving or stalling miner keep the signer set's activity timer perpetually "fresh" while never finalizing any block, indefinitely delaying `check_miner_inactivity`'s fallback to the prior tenure (`FALL["fall back to prior tenure: make_miner_state(prior sortition)"]`). This is a liveness wedge: signers are prevented from timing out a non-productive miner and recovering block production, matching the High-impact class "a signer wedged into never signing valid blocks" due to a stuck/stalled miner-inactivity guard that a single miner can trigger without any majority-signer collusion.

### Likelihood Explanation
High reachability: it only requires control of the current sortition/tenure slot (a single miner), the ability to submit multiple distinct, individually-valid block proposals at the same chain height, and no cooperation from other signers or miners. No signer misbehavior or majority collusion is required — the vulnerable code path fires on every signer independently as they each locally evaluate `check_latest_block_in_tenure`.

### Recommendation
Do not treat conflicts against a **pre-committed-only** (unsigned) block as unconditional "miner activity." Either:
- Bound how often `update_last_activity_time` can be refreshed per tenure by a *pre-commit-only* conflict (e.g., only once per height, or only if the new proposal itself makes measurable progress such as a higher chain length than any previously-seen proposal), or
- Require the competing proposal to actually gain pre-commit weight before it is allowed to refresh the activity timer, since a fully signed/globally-accepted competing block already provides an activity signal through other paths (`get_tenure_last_block_info`).
This removes the ability of a single actor to indefinitely stall the inactivity fallback purely by proposing distinct never-finalized alternatives.

### Proof of Concept
1. Miner M is the current tenure's active miner (holds the sortition).
2. At height H, M proposes block B1; it validates and is pre-committed by signers (`mark_pre_committed`, stamping `approved_time`), but never reaches the 70% pre-commit threshold (M does not gossip enough support, or simply lets it stall).
3. Before `tenure_last_block_proposal_timeout` elapses, M proposes block B2 at the same height H (different transaction set, same parent). It also validates.
4. Each signer runs `check_latest_block_in_tenure`: B2 conflicts with the still-fresh pre-commit B1 at `chain_length <= info.block.header.chain_length`, hits the `is_fresh_pre_commit` branch (mod.rs:428-447), and calls `update_last_activity_time` for M's tenure — even though B2 is rejected and B1 was never signed.
5. M repeats step 3 with B3, B4, … before each preceding proposal's pre-commit window expires.
6. `check_miner_inactivity`/`is_timed_out` never observes an idle gap large enough to trigger fallback (`FALL`) to the prior tenure, so the signer set never gives up on M's unproductive tenure, stalling block production indefinitely — a liveness wedge triggerable by the single active miner.
