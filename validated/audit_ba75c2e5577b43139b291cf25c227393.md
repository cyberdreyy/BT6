### Title
`lossRecoveryPriceByEpoch` haircut is keyed to a single epoch while `pendingWithdraws` is aggregate — receipts from other epochs escape the loss and drain the funded reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Analogous to the Deneb tree-height bug (a constant/epoch-bound parameter applied across a state transition it no longer describes), `IdleCreditVault.collectWithdrawFunds` sizes a loss haircut on the **aggregate** `pendingWithdraws` basis but stores the resulting `lossRecoveryPrice` under **one** epoch (`lossRecoveryPriceByEpoch[epochNumber]`). Whether a user's receipt is haircut is decided solely by `lastWithdrawRequest[_user] == lossEpoch` in `_claimLossAdjustedWithdrawRequest`. Withdraw receipts recorded in any other epoch claim at par through `_claimFundedWithdrawRequest` even though the reserve collected by `collectWithdrawFunds` was reduced by a loss computed over all pending receipts — including theirs.

### Finding Description
In `collectWithdrawFunds`, when the borrower-funded `_amount` is less than `pendingBasis` (the global `pendingWithdraws`), the contract stores a pro-rata `lossRecoveryPrice` for `epochNumber` only: [1](#0-0) 

The haircut is later applied only to users whose `lastWithdrawRequest` equals that epoch: [2](#0-1) 

A user whose `lastWithdrawRequest` points to any other epoch (an earlier, already-funded-by-design epoch, or a later epoch where the guard at lines 263–270 was bypassed because the loss price did not yet exist at request time) skips `_claimLossAdjustedWithdrawRequest` and redeems `withdrawsRequests[_user]` at par via `_claimFundedWithdrawRequest`/`_transferFundedClaim`: [3](#0-2) 

But the underlying reserve held by the strategy is only `_amount = pendingBasis - pendingLoss`, where `pendingLoss` was amortized over **all** pending receipts (`previewLossAdjustedWithdrawFunds` splits `_lossAmount` between the aggregate `pendingBasis` and the active basis): [4](#0-3) 

So par-claiming receipts from non-loss epochs consume value that was priced assuming they too would be haircutted.

### Impact Explanation
Broken invariant: loss socialization / solvency of the funded-claim reserve. An unprivileged lender holding a stale-epoch receipt withdraws at par from a reserve that only contains `pendingBasis * lossRecoveryPrice / RECOVERY_FULL`. Every such claim is a direct transfer of the haircut to the remaining claimers: the last claimer(s) of the loss epoch find the reserve depleted and are permanently frozen (insolvency), while the attacker withdraws strictly more than their fair post-loss share — direct theft quantified as `claimBasis * (1 - lossRecoveryPrice/RECOVERY_FULL)` per escaped receipt, up to draining the reserve entirely.

### Likelihood Explanation
Only unprivileged actions are required: deposit, `requestWithdraw` in an epoch, and simply *not claiming* before a subsequent `stopEpochWithDuration(_lossAmount)` produces a partial `collectWithdrawFunds` — an event triggered by honest manager/borrower activity (a real borrower shortfall), not by the attacker. The `requestWithdraw` guard (lines 263–270) only blocks re-requesting while `lossRecoveryPriceByEpoch[lastWithdrawRequest] != 0` with an unreceived receipt; it does not stop pre-existing receipts in *other* epochs from claiming at par, nor does it prevent a user from holding an old unclaimed receipt while a later epoch is haircutted. No privileged misbehavior needed; sequence around honest `stopEpochWithDuration`.

### Recommendation
Track the haircut basis per epoch rather than via a single `lastWithdrawRequest` lookup: store `lossRecoveryPriceByEpoch` consistently for every epoch that contributed to `pendingBasis` (or store the haircut price directly on the per-epoch receipt `withdrawsRequestsByEpoch[user][epoch]`), and have `_claimLossAdjustedWithdrawRequest` iterate/apply a haircut to *any* receipt whose epoch's loss price is non-zero — not just `lastWithdrawRequest[_user]`. Alternatively, compute `pendingLoss` only over receipts actually recorded in the loss epoch and fully fund older ones.

```text
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait

    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();

    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
```

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
