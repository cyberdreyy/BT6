### Title
Unfunded instant-withdraw receipts from a pre-default epoch escape the recovery haircut and are paid at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The credit vault tracks instant-withdraw receipt basis per epoch (`instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`), but the unfunded remainder (`pendingInstantWithdraws`) is a single epoch-agnostic counter. When a default is finalized, `defaultPendingClaimBasis()` only folds `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — into the recovery basis, and `_defaultPrefundedInstantReserve()` likewise only reads the current epoch's claims. An instant receipt requested in epoch N that stays unfunded through `startEpoch`/`stopEpoch` into epoch N+1 (the default epoch) is therefore invisible to the recovery accounting: it is not haircut, yet `claimInstantWithdrawRequest` still pays the residual `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim`, drawing on strategy underlyings that include the `defaultRecoveryReserve`. This is the analog of CVE-2018-7639's unhandled "case 16" over-read: an unhandled sub-case (non-current-epoch instant receipts) is treated at full value while every other defaulted claim is haircut.

### Finding Description
Relevant code:

- `defaultPendingClaimBasis()` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` only for `epochNumber`, the default epoch.
- `_defaultPrefundedInstantReserve()` (lines 716-722) compares `pendingInstantWithdraws` against `instantWithdrawClaimsByEpoch[epochNumber]` only; if the unfunded remainder belongs to an older epoch, `instantBasis <= pendingInstant` yields `prefundedReserve = 0`.
- `_claimDefaultedInstantWithdrawRequest()` (lines 842-855) clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`.
- `claimInstantWithdrawRequest()` (lines 380-393) then unconditionally pays the remaining `instantWithdrawsRequests[_user]` at par with `_transferFundedClaim`.

Sequence (instant-withdraw mode enabled, non-programmable borrower):

1. Epoch N running: attacker calls `requestWithdraw` on the instant path → `requestInstantWithdraw` mints receipt, `pendingInstantWithdraws += amount`, `instantWithdrawsRequestsByEpoch[user][N] += amount`.
2. Manager does not call `getInstantWithdrawFunds` (or `getFundsFromBorrower` fails), so the receipt stays unfunded; `allowInstantWithdraw` stays false.
3. `stopEpoch`/`startEpoch` roll the vault to epoch N+1. Nothing clears or migrates the old receipt; `pendingInstantWithdraws` still counts it, but `instantWithdrawClaimsByEpoch[N+1]` is 0.
4. Epoch N+1 ends in borrower default (`_handleBorrowerDefault` sets `defaulted = true`, `isEpochRunning = false`). Attacker cannot withdraw-request further, but the existing receipt stands.
5. `finalizeDefaultRecovery`: `defaultPendingClaimBasis()` returns `pendingWithdraws + 0` for instant claims; `prefundedReserve = 0`. The attacker's receipt is excluded from `totalBasis`, so `recoveryPrice` is computed as if it did not exist.
6. Because `defaultInstantWithdrawsFinalized = (pendingInstantWithdraws != 0)` is true, the claim path first clears the (empty) default-epoch bucket, then pays `instantWithdrawsRequests[user]` at par from the strategy's underlyings — i.e., from `defaultRecoveryReserve` and any funded cash.

### Impact Explanation
The attacker receives a 100%-of-par payout on an unfunded receipt while every other defaulted claim (active LPs, normal pending receipts, same-epoch instant receipts) receives `recoveryPrice < 1`. The payment consumes `defaultRecoveryReserve` (or funded instant cash belonging to others), so later claimants' payouts revert or are reduced: direct theft of recovery proceeds proportional to the attacker's unfunded instant amount, potentially up to the entire reserve if the reserve is smaller than the unhaircutted claim.

### Likelihood Explanation
Requires only an unprivileged KYC'd lender path: a single `requestInstantWithdraw` in an epoch that ends without the manager funding instant withdrawals, followed by a borrower default in a later epoch. Instant requests have a deadline-based funding flow (`getInstantWithdrawFunds` requires `block.timestamp >= instantWithdrawDeadline`), so a stopEpoch can legitimately occur before funding; the receipt then straddles an epoch boundary. No privileged misbehavior needed — the attacker's actions are just requesting and later claiming.

Uncertainty: I could not fully verify in this iteration whether `claimInstantWithdrawRequest` on the CDO side (`IdleCDOEpochVariant`) gates post-default instant claims on `allowInstantWithdraw`; if the CDO blocks the call entirely after default, the residue may be frozen rather than paid at par — still a violation (permanent freezing of the attacker's receipt notwithstanding, the haircut inconsistency remains, and the reserve mis-sizing in `defaultPendingClaimBasis` stands).

### Recommendation
Make the pending-instant accounting epoch-aware end-to-end:

- In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, iterate or aggregate `instantWithdrawClaimsByEpoch` across all epochs with nonzero claims (or maintain a global `instantWithdrawClaims` total alongside `instantWithdrawClaimsByEpoch`) so unfunded instant receipts of any epoch join the recovery basis.
- In `claimInstantWithdrawRequest`, clear *all* epoch buckets for the user (not only `defaultRecoveryEpoch`) through the recovery-priced path, paying each unfunded receipt at `defaultRecoveryPrice`.
- Add a regression test: request instant withdraw in epoch N, roll to epoch N+1, default, finalize, then assert the claim pays `basis * defaultRecoveryPrice` and that `defaultRecoveryReserve` decreases only by haircut amounts.

### Proof of Concept
Foundry fork PoC sketch (mirroring `testFinalizeDefaultHaircutsPendingInstantRedeems` in `test/foundry/IdleCreditVault.t.sol`, but with the instant request one epoch earlier):

```solidity
function testInstantReceiptFromOlderEpochEscapesHaircut() external {
    // enable instant withdraws
    uint256 delay = cdoEpoch.instantWithdrawDelay();
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(delay, 1000, false);

    address attacker = makeAddr('attacker');
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(attacker, amount, true);

    _startEpochAndCheckPrices(0);                       // epoch 0 running
    vm.prank(attacker);
    uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant path
    // manager never calls getInstantWithdrawFunds -> receipt unfunded
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    _startEpochAndCheckPrices(1);                       // epoch 1 running

    // borrower defaults in epoch 1
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    IdleCreditVault cv = IdleCreditVault(address(strategy));
    // attacker's basis is NOT in the recovery basis
    assertEq(cv.defaultPendingClaimBasis(), cv.pendingWithdraws());

    uint256 recovered = cv.defaultPendingClaimBasis() * 7e17 / 1e18 + cv.getContractValue() * 7e17 / 1e18;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    // BUG: paid at par instead of basis * defaultRecoveryPrice / 1e18
    assertEq(IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre, basis);
    // reserve drained by the unhaircutted payout
}
```
