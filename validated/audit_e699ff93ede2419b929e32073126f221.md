### Title
Global Shared Pending-Request Cache Allows Unprivileged Sender to Exhaust Capacity and Block Other Users' Gateway Requests - (File: core/services/gateway/handlers/common/requestcache.go)

### Summary
The gateway's generic `RequestCache` used by internet-facing action/trigger handlers (e.g. `core/services/gateway/handlers/capabilities/v2/http_handler.go`) enforces a single **global** `maxCacheSize` limit shared by all senders. Any unprivileged caller can fill this shared cache with distinct pending requests, causing `NewRequest` to reject requests from all other users with "request cache is full" until the offending entries expire after `timeout`. This mirrors the PearVault pattern: a cheap, unprivileged action inflates a shared pending-state counter that gatekeeps a shared resource for every other legitimate user, and the griefing persists until the attacker's own entries are processed or time out.

### Finding Description
`requestCache.NewRequest` keys pending entries by `{sender, messageId}` but bounds the overall cache with one global counter checked via `len(c.cache) >= int(c.maxCacheSize)`: [1](#0-0) 

There is no per-sender or per-workflow quota inside this structure — only a single shared `maxCacheSize` for the whole cache instance: [2](#0-1) 

Because the key includes the caller-supplied `MessageId`, a single allowlisted/unprivileged sender can generate many distinct message IDs (each a legitimate, cheap request) and hold them open in the cache (they remain until `ProcessResponse` completes them or the `timeout` fires): [3](#0-2) 

This structure is used by the gateway's internet-facing HTTP action handler (`core/services/gateway/handlers/capabilities/v2/http_handler.go`), which is reachable by any allowlisted/unprivileged workflow client sending JSON-RPC requests to the gateway. Note: I was not able to fully re-verify the exact `maxCacheSize` instantiation value/configuration wiring in `http_handler.go` due to tool-call limits, so it's uncertain whether an additional per-sender guard is layered on top at that call site.

### Impact Explanation
If the shared cache lacks a per-sender cap in front of it, one unprivileged, otherwise-authorized client can fill the entire pending-request table with junk/low-cost requests, causing `NewRequest` to return "request cache is full" for every other legitimate sender's request until the attacker's entries drain via `timeout`. This is a griefing/DoS on the gateway's action-handling path for all DON clients, analogous to the PearVault `totalPendingShares` griefing where one user's pending action blocked all others' operations until processed. It does not directly cause fund loss or credential disclosure, but it denies service to legitimate unprivileged users of the gateway.

### Likelihood Explanation
Likelihood depends on whether the call site in `http_handler.go` layers a per-sender limit (e.g., `PerSenderBurst`/`PerSenderRPS` from the documented `RateLimiterConfig`) before requests reach `RequestCache.NewRequest`. The existing `README.md` for this handler package documents dual global/per-sender rate limiting, which may mitigate request *rate* but does not inherently cap concurrent *pending* cache slots consumed per sender — rate limiting throttles new-request throughput, not the number of entries a sender can keep alive simultaneously up to the shared `maxCacheSize`. Because I could not fully confirm the wiring inside `http_handler.go` in this session, likelihood is assessed as **uncertain/moderate** pending direct code confirmation.

### Recommendation
Add a per-sender (or per-workflow) quota on outstanding entries within `RequestCache`, independent of the global `maxCacheSize`, so no single sender can consume the entire shared cache capacity. Reject or evict cheap/incomplete requests preferentially when a sender exceeds its individual share, and consider proportionally reserving cache capacity per authenticated sender rather than a single shared counter.

### Proof of Concept
1. As an allowlisted-but-otherwise-unprivileged workflow client, send `maxCacheSize` distinct JSON-RPC requests to the gateway's HTTP action/trigger endpoint, each with a unique `MessageId`, without necessarily completing/allowing their aggregation to finish quickly.
2. Each call succeeds and occupies a slot in the shared `cache` map via `NewRequest`.
3. Once `len(c.cache) >= maxCacheSize`, any other legitimate user's request to the same handler hits the `len(c.cache) >= int(c.maxCacheSize)` branch and receives `"request cache is full"`, denying them service until the attacker's entries are removed via `ProcessResponse` or `timeout` expiry.

Note: This finding is presented with moderate confidence due to remaining uncertainty about the exact per-sender protections (if any) applied at the `http_handler.go` call site, which I was unable to fully verify within the available tool-call budget.

```go
func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
```

```go
func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}
```
