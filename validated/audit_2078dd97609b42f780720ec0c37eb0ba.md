### Title
Unbounded-depth JSON parsing of attacker-controlled Config account data causes RPC/validator crash - ([File: account-decoder/src/parse_config.rs])

### Summary
`parse_config` deserializes the `info` field of a `Config`-program account and feeds it directly into `serde_json::from_str` with no depth, size, or structural validation. Because any unprivileged user can create a `Config`-program account whose first key is the well-known `validator_info::id()` (which does not need to be a signer) and whose payload is fully attacker-controlled, an attacker can embed a maliciously deep/nested JSON document. When an RPC node subsequently serves that account with `jsonParsed` encoding, the recursive-descent `serde_json` parser can stack-overflow and crash the validator's RPC process from a single request.

### Finding Description
`parse_config` in [1](#0-0)  deserializes the config account's `ConfigKeys` via `bincode`, then calls `parse_config_data::<String>` to extract the raw `info` string, and finally parses that string as JSON with `serde_json::from_str(&validator_info.config_data)` at [2](#0-1) , with no bound on nesting depth or payload size.

The `info` string originates from on-chain account data that is entirely attacker-controlled: the `Config` account's data layout only requires that the first key equal `validator_info::id()` (with `signer: false`), so no real signature authority is enforced over the content — see the `ConfigKeys`/`get_config_data` handling used here [3](#0-2) . Any user can therefore submit a `Config`-program instruction constructing an account that matches this shape and stuff an arbitrarily deep JSON string (e.g., deeply nested arrays) into the `info` payload. Client-side length constants such as `MAX_LONG_FIELD_LENGTH`/`MAX_VALIDATOR_INFO` in [4](#0-3)  are only enforced by the CLI publisher path (`cli/src/validator_info.rs`), not by the on-chain Config program itself, so they provide no protection against a direct, hand-crafted transaction.

This account decoding path is reachable from unprivileged JSON-RPC calls such as `getAccountInfo`/`getProgramAccounts` with `encoding: "jsonParsed"`, which route through `parse_account_data_v3` into `parse_config` [5](#0-4) . `serde_json`'s default parser is a recursive-descent parser with no built-in recursion-depth limit, so parsing a sufficiently deeply nested JSON value can exhaust the thread stack and crash the process.

### Impact Explanation
A single unprivileged RPC request against a maliciously crafted, cheaply created `Config` account can crash the RPC-serving validator process (stack overflow / abort), a concrete validator-process crash triggered by one request as called out in the validation criteria.

### Likelihood Explanation
Likelihood is moderate: it requires (1) crafting and funding a `Config`-program account with the specific key layout and a deeply nested JSON payload (inexpensive, no special privilege needed), and (2) inducing (or waiting for) any client to query that account with `jsonParsed` encoding — an attacker can trivially do this themselves against a target RPC node with a single `getAccountInfo` call.

### Recommendation
Validate/limit the JSON before or during parsing of the `info`/`config_data` field: reject payloads whose size exceeds the intended `MAX_VALIDATOR_INFO`/`MAX_LONG_FIELD_LENGTH` bounds server-side (not just client-side in the CLI), and/or use a JSON parser configured with a bounded recursion depth (or a hand-rolled depth check before calling `serde_json::from_str`) so a stack overflow cannot be triggered by attacker-supplied account data.

### Proof of Concept
1. Submit a `Config`-program `store` instruction creating a new account where `ConfigKeys.keys[0] == (validator_info::id(), false)`, and whose serialized `config_data` (a bincode `String`) contains a deeply nested JSON string, e.g. `"[".repeat(200_000) + "]".repeat(200_000)`.
2. Query the account via JSON-RPC: `getAccountInfo(<account_pubkey>, {"encoding": "jsonParsed"})`.
3. The RPC handler calls `parse_account_data_v3` → `parse_config` → `serde_json::from_str` on the attacker payload at [2](#0-1) , causing unbounded recursive descent and a stack overflow that crashes the RPC process handling the request.

pub fn parse_config(data: &[u8], _pubkey: &Pubkey) -> Result<ConfigAccountType, ParseAccountError> {
    let parsed_account = deserialize::<ConfigKeys>(data).ok().and_then(|key_list| {
        if !key_list.keys.is_empty() && key_list.keys[0].0 == validator_info::id() {
            parse_config_data::<String>(data, key_list.keys).and_then(|validator_info| {
                Some(ConfigAccountType::ValidatorInfo(UiConfig {
                    keys: validator_info.keys,
                    config_data: serde_json::from_str(&validator_info.config_data).ok()?,
                }))
            })
        } else {
            None
        }
    });
    parsed_account.ok_or(ParseAccountError::AccountNotParsable(
        ParsableAccount::Config,
    ))
}

pub fn parse_account_data_v3(
    pubkey: &Pubkey,
    program_id: &Pubkey,
    data: &[u8],
    additional_data: Option<AccountAdditionalDataV3>,
) -> Result<ParsedAccount, ParseAccountError> {
    let program_name = PARSABLE_PROGRAM_IDS
        .get(program_id)
        .ok_or(ParseAccountError::ProgramNotParsable)?;
    let additional_data = additional_data.unwrap_or_default();
    let parsed_json = match program_name {
        ParsableAccount::AddressLookupTable => {
            serde_json::to_value(parse_address_lookup_table(data)?)?
        }
        ParsableAccount::BpfUpgradeableLoader => {
            serde_json::to_value(parse_bpf_upgradeable_loader(data)?)?
        }
        ParsableAccount::Config => serde_json::to_value(parse_config(data, pubkey)?)?,
        ParsableAccount::Nonce => serde_json::to_value(parse_nonce(data)?)?,
        ParsableAccount::SplToken | ParsableAccount::SplToken2022 => serde_json::to_value(
            parse_token_v3(data, additional_data.spl_token_additional_data.as_ref())?,
        )?,
        ParsableAccount::Stake => serde_json::to_value(parse_stake(data)?)?,
        ParsableAccount::Sysvar => serde_json::to_value(parse_sysvar(data, pubkey)?)?,
        ParsableAccount::Vote => serde_json::to_value(parse_vote(data, pubkey)?)?,
    };
