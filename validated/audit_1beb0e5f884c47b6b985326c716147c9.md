### Title
Cross-user callback hijack via MessageId collision in `pruneCallbacks`/`savedCallbacks` map keyed only by MessageId - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending user callback in `h.savedCallbacks` keyed solely by `msg.Body.MessageId`, which is the JSON-RPC request ID fully controlled by the requesting client. Because the map key does not incorporate `msg.Body.Sender`, a second, unrelated (but validly signed) request that reuses the same `MessageId` as an in-flight legitimate request overwrites the first user's saved callback, causing the eventual DON response for that `MessageId` to be delivered to the attacker instead of the original requester.

### Finding Description
In `HandleLegacyUserMessage` [1](#0-0) , the callback is saved with:
```go
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
```
No check is made for whether an entry already exists for that `MessageId`, and no binding to `msg.Body.Sender` is stored as part of the key or verified on overwrite/lookup.

`msg.Body.MessageId` originates directly from the JSON-RPC request `ID` supplied by the calling client, only bounded by a length check (`len(jsonRequest.ID) > 200`) in `gateway.ProcessRequest` [2](#0-1)  and by `api.Message.Validate()`'s `MessageIdMaxLen`/null-byte checks [3](#0-2) . Crucially, `Validate()` derives `Body.Sender` from the signature [4](#0-3)  but never ties `Sender` to `MessageId` uniqueness — any signer can pick any `MessageId` string.

Later, when a node responds via `handleWebAPITriggerMessage`, the response is routed purely by `MessageId`:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [5](#0-4) 

Exploit flow:
1. Legitimate user A sends a request through `gateway.ProcessRequest` → `HandleLegacyUserMessage`, with a validly-signed message carrying `MessageId = "X"`. This stores `savedCallbacks["X"] = callbackA` and forwards the request to all DON members.
2. Before the DON responds, attacker B (an unprivileged but validly-signing gateway client) sends their own `HandleLegacyUserMessage` request, also with `MessageId = "X"` (attacker fully controls this field and only needs their own valid signature — no forgery of A's signature is required). This overwrites `savedCallbacks["X"] = callbackB`.
3. When a DON node eventually responds for message `X` (in reply to A's original triggered work), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, now bound to attacker B's `Callback`, and delivers the (possibly sensitive) result to B instead of A.
4. A's original HTTP request either hangs until gateway-side timeout (`callback.Wait(ctx)` in `gateway.go`) or silently receives no response, effectively a denial of service plus response redirection to the attacker.

No existing check (`Validate()`, rate limiter, `pruneCallbacks`) prevents this: `Validate()` only checks length/format, not uniqueness against sender; `pruneCallbacks` only removes stale/excess entries by age/count, not per-sender ownership [6](#0-5) .

### Impact Explanation
This is a cross-user response confusion vulnerability: an unprivileged, unauthenticated-relative-to-other-users attacker (any client capable of signing and sending a gateway request) can redirect another user's DON/webapi-trigger response to themselves, potentially exposing data intended for another user, and simultaneously deny service to the legitimate requester. This matches the "cross-user response confusion" / unauthorized access to another user's response bounty impact class described in the audit scope.

### Likelihood Explanation
Exploitability requires only: (1) the ability to send signed `web_api_trigger` messages to the gateway (any onboarded/allowlisted DON member key or any client whose key is accepted by the gateway's signature validation — no special privilege beyond a valid signing key), and (2) predicting or guessing the victim's `MessageId`. If `MessageId`s are predictable, sequential, low-entropy, or attacker-observable (e.g., echoed in logs, timing-based, or client-chosen deterministic values such as workflow/execution IDs as seen in `getMessageID` [7](#0-6) ), the collision is trivially reproducible; even with random IDs, repeated flooding increases collision probability over time given no uniqueness enforcement. The underlying flaw (unkeyed-by-sender overwrite) is deterministic and 100% reproducible once a collision occurs.

### Recommendation
Key `h.savedCallbacks` by a composite of `(Sender, MessageId)` rather than `MessageId` alone, or reject/generate-new-ID when a collision with a still-pending entry occurs from a different sender. Additionally, when responses come back from DON nodes in `handleWebAPITriggerMessage`, verify that the callback being resolved matches the original sender/session context, not just the ephemeral `MessageId`.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler with a mock `handlers.DON` accepting `SendToNode` for any address.
2. Create two `api.Message` structs, `msgA` and `msgB`, each independently signed by two different private keys (so `Body.Sender` differs after `Validate()`), but both sharing the same `Body.MessageId = "shared-id"` and `Body.Method = MethodWebAPITrigger`.
3. Call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` then `h.HandleLegacyUserMessage(ctx, msgB, callbackB)`.
4. Assert (expected-to-fail under current code): `len(h.savedCallbacks) == 1` and the single entry's stored `Callback` is `callbackB`, i.e., `callbackA` was silently overwritten.
5. Simulate the DON response for `MessageId = "shared-id"` via `h.handleWebAPITriggerMessage(ctx, respMsg, nodeAddr)` and assert `callbackB.SendResponse` (not `callbackA.SendResponse`) was invoked — demonstrating cross-user response delivery.
6. A fixed version should either key the map by `(Sender, MessageId)` (so both entries coexist and each callback receives only its own response) or reject the second `HandleLegacyUserMessage` call with a conflict error when `MessageId` is already in-flight for a different sender.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}

func getMessageID(req capabilities.CapabilityRequest) (string, error) {
