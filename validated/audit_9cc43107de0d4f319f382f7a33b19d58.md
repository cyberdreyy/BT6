### Title
JWT Replay-Cache TOCTOU Allows Single-Use Token to Authorize Duplicate Workflow Executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The `WorkflowMetadataHandler.Authorize` function is meant to guarantee that each signed JWT (`jti`) can authorize exactly one gateway-routed workflow trigger request. Like the LOC contract's failure to atomically update `creditedTokenAmount` before allowing another redemption, this handler checks replay status and marks the token as used in two separate, non-atomic steps, allowing concurrent requests bearing the same token to both pass authorization.

### Finding Description
`Authorize` performs the check-then-act sequence:
1. `h.jwtCache.isReplay(claims.ID)` — acquires `jwtReplayCache.mu` as a read lock, checks membership, releases the lock.
2. ... authorization/signer checks ...
3. `h.jwtCache.recordUsage(claims.ID)` — acquires the lock again to insert the `jti`. [1](#0-0) 

Because the "already used?" check and the "mark as used" write are not performed under a single critical section, two (or more) concurrent `Authorize` calls presenting the identical valid, signed JWT can both observe `isReplay == false` before either has called `recordUsage`. Both then pass the remaining authorized-key checks and both return a valid `*gateway.AuthorizedKey`, letting the caller trigger the workflow multiple times with a single one-time-use token — directly paralleling the LOC bug where `_redeemLOC` fails to update state before the next reuse is permitted.

The underlying cache primitives themselves are simple map operations, each individually lock-protected but not composed atomically by the caller: [2](#0-1) 

### Impact Explanation
This is reachable by an unprivileged HTTP-trigger client through the internet-facing gateway message-handling path (`HandleUserTriggerRequest` → `Authorize`), the same path validated by the "duplicate JWT token and request ID" test as a security boundary. A successful race lets an attacker cause duplicate/unauthorized job runs (workflow executions) from what is supposed to be a single-use, single-request authorization credential — i.e., an authentication/role-bypass class impact (unauthorized job run) rather than merely a race-condition curiosity, since the entire purpose of the replay cache is to enforce exactly-once execution semantics per signed request.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker (or a legitimate but malicious workflow client) to fire the same signed request concurrently (e.g., two parallel HTTP connections) before the first request's `recordUsage` call lands — a narrow but realistic race window given normal request-handling concurrency in the gateway. No cryptographic material needs to be forged; the attacker only needs the valid signed JWT they already legitimately possess and network-level ability to submit it twice concurrently.

### Recommendation
- **Short term:** Make the "check unused" and "mark used" operations atomic under a single lock acquisition (e.g., add a `checkAndRecord(jti) bool` method on `jwtReplayCache` that does compare-and-set under one `mu.Lock()`), and reject the second concurrent request deterministically.
- **Long term:** Add concurrency/race tests (e.g., `go test -race` scenarios firing the same JWT concurrently) and consider persisting replay state so restarts/multiple gateway instances cannot bypass the check either.

### Proof of Concept
1. Register a workflow and its authorized signer key as in `TestWorkflowMetadataHandler_Authorize`.
2. Create one valid signed JWT for a given request (`token, err := utils.CreateRequestJWT(*req)`, signed with `privateKey`).
3. Launch two goroutines that both call `handler.Authorize(workflowID, tokenString, req)` at (approximately) the same time before either observes the other's write.
4. Under the current implementation, both goroutines can enter the window between `isReplay` (false for both) and `recordUsage`, so both may return `nil` error and a valid `*gateway.AuthorizedKey`, whereas the existing sequential test only demonstrates the second call failing when it happens strictly after the first completes: [3](#0-2)

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
