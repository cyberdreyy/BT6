## Analog Found

### Title
Builder pending withdrawals commit an uncapped `amount` to the execution layer while the consensus layer only deducts `min(amount, balance)`, minting unbacked Gwei — (File: `specs/gloas/beacon-chain.md`)

### Summary
This is the consensus-specs analog of the CoreRouter H-17 bug class: a withdrawal amount is calculated and *committed* without checking it against the payer's actual available balance, so the entity that pays out ends up promising more value than it actually holds/deducts. In `CoreRouter`, the redemption amount ignored the possibility that the shared collateral pool had shrunk due to liquidation. In Gloas, `get_builder_withdrawals` computes the `Withdrawal.amount` that gets committed to the execution payload directly from the raw `BuilderPendingWithdrawal.amount`, without capping it to the builder's actual `balance`. The capping only happens later, inside `apply_withdrawals`, and only affects the CL's internal bookkeeping (`state.builders[..].balance`) — not the `amount` field that was already committed and that the execution layer is required to honor.

### Finding Description
`get_builder_withdrawals` builds `Withdrawal` records straight from the pending-withdrawal queue with no balance check: [1](#0-0) 

These records become part of `state.payload_expected_withdrawals`, which the spec explicitly states the execution layer "is required to honor... in the execution layer": [2](#0-1) 

But when the CL actually applies these withdrawals to its own state, it silently caps the deduction to whatever balance the builder has, allowing the balance to go to zero without ever validating that the *committed* amount matches what was deducted: [3](#0-2) 

The report's own input-space documentation acknowledges this is expected, by-design behavior rather than an edge case that's rejected: [4](#0-3) [5](#0-4) 

The spec's own test suite proves this state is reachable and treated as valid: a builder with 1 ETH balance and a pending withdrawal request for 5 ETH produces a committed `Withdrawal` of the full 5 ETH, while only 1 ETH is actually removed from the builder's balance: [6](#0-5) [7](#0-6) 

This is the exact bug class from the report: the amount promised/paid out (`withdrawal.amount`, committed to the block and honored unconditionally by the EL) is calculated independently of the actual "collateral" available (`builder.balance`) at settlement time. Compare this with the properly-designed sibling function for validator partial withdrawals, which caps the amount *before* it is placed into the `Withdrawal` record, so the committed amount and the actually-available balance can never diverge: [8](#0-7) 

`get_builder_withdrawals` has no equivalent capping step — it is the "CoreRouter.redeem" of this codebase: it computes what to hand out from a stale/unclamped quantity while the actual backing balance (the builder's) can already be smaller.

### Impact Explanation
If `withdrawal.amount` (5 ETH in the test, more generally `requested_amount - builder.balance` in excess) is what the execution layer is contractually required to credit to `fee_recipient`, but the consensus layer only ever deducts `min(amount, balance)` (1 ETH) from the builder's stake, then Gwei is effectively created out of thin air and paid to the withdrawal's `fee_recipient` — a non-owner relative to the actual remaining stake. This falls squarely under "Gwei created ... or paid to a non-owner," the Critical-severity bar. Unlike a partition/timing/DoS concern, this is a deterministic, spec-following state transition that every honest node will compute identically — the loss is not the attacker's own stake, it's unbacked ETH manufactured on the EL side.

### Likelihood Explanation
The precondition — a builder's `builder_pending_withdrawals` amount exceeding its current `balance` — is explicitly modeled and tested by the spec's own test suite as a normal, expected code path (`test_builder_withdrawal_insufficient_balance*`, `test_all_builder_withdrawals_zero_balance`), not a contrived edge case. The exact mechanism by which a builder's balance can fall below its already-queued pending withdrawal total prior to processing (e.g., ordering of multiple pending withdrawal entries against a shared balance, or timing relative to `can_builder_cover_bid` checks at bid-placement time) was not fully traced in this session and would need confirmation from a Devin session with full repository access; but the *test suite itself demonstrates the state (amount > balance) is reachable and is currently handled by silently capping the CL deduction rather than rejecting/adjusting the committed withdrawal amount*.

### Recommendation
`get_builder_withdrawals` (and any other constructor of a `Withdrawal` record backed by a shared/mutable balance) must cap the committed `amount` to the actual available balance *at the point the `Withdrawal` object is created* — mirroring what `get_pending_partial_withdrawals` already does for validators (`min(balance - MIN_ACTIVATION_BALANCE, amount)`) — so the amount honored by the execution layer can never exceed what the consensus layer actually removes from the builder's collateral.

### Proof of Concept
Using the existing spec-provided helper (`prepare_process_withdrawals`) and the already-present test `test_builder_withdrawal_insufficient_balance`:
1. Set `state.builders[0].balance = 1 ETH`.
2. Queue `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5 ETH, fee_recipient=X)]`.
3. Run `process_withdrawals(state)`.
4. Observe: `state.payload_expected_withdrawals` contains a `Withdrawal(amount=5 ETH, address=X)` (see assertion `withdrawal_amounts_builders={builder_index: withdrawal_amount}` in the cited test), which the execution layer is required to honor and credit in full to `X`.
5. Observe: `state.builders[0].balance` decreases only by 1 ETH (`min(5 ETH, 1 ETH)`), per the cited `apply_withdrawals` logic.
6. Result: 4 ETH is credited on the execution layer with no corresponding stake removed on the consensus layer — unbacked Gwei creation. [6](#0-5)

```markdown
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
```

```python
@with_gloas_and_later
@spec_state_test
def test_builder_withdrawal_insufficient_balance(spec, state):
    """
    Test builder withdrawal with insufficient balance.

    Input State Configured:
        - state.builders[0]: Builder exists with only 1 ETH balance
        - builder_pending_withdrawals: Contains 1 entry requesting 5 ETH
        - builders[0].balance: 1 ETH (insufficient for requested 5 ETH)

    Output State Verified:
        - payload_expected_withdrawals: Contains 1 withdrawal
        - withdrawal.amount: 5 ETH (requested amount)
        - builders[0].balance: 0 (deduction capped to available balance)
        - builder_pending_withdrawals: Reduced by 1 (processed even if capped)
        - next_withdrawal_index: Incremented by 1
    """
    builder_index = 0
    withdrawal_amount = spec.Gwei(5_000_000_000)
    available_balance = spec.Gwei(1_000_000_000)

    prepare_process_withdrawals(
        spec,
        state,
        builder_indices=[builder_index],
        builder_withdrawal_amounts={builder_index: withdrawal_amount},
        builder_balances={builder_index: available_balance},

    pre_state = state.copy()
    yield from run_gloas_withdrawals_processing(spec, state)

        spec,

        pre_state,

        builder_balances={builder_index: 0},
```
