### Title
Missing predecessor/receiver authorization check allows hijacking a victim account's AccountId-mode global contract namespace - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`action_deploy_global_contract` in [1](#0-0)  registers a `GlobalContractIdentifier::AccountId(account_id)` entry using only the executing receipt's receiver account (`account_id`), with no check that the action's `predecessor_id` (who actually authorized/paid for the deploy) equals that account. Neither `ReceiptManager::append_action_deploy_global_contract` [2](#0-1)  nor `validate_deploy_global_contract_action` [3](#0-2)  perform any authorization check beyond a code-size limit.

### Finding Description
`action_deploy_global_contract` computes the global contract identifier for `AccountId` mode directly from `account_id`, which is the account the enclosing receipt is being applied to (i.e., the receipt's `receiver_id`), via `initiate_distribution` [4](#0-3) . There is no parameter or check comparing this to `receipt.predecessor_id()` anywhere in this call chain. `validate_deploy_global_contract_action` only checks `action.code.len()` against `max_contract_size` [3](#0-2) , and `append_action_deploy_global_contract` in the host-function/receipt-manager layer simply appends the action to whatever receipt index is passed in, with no receiver/account check [2](#0-1) .

If a receipt whose `receiver_id` is victim account `V` carries a `DeployGlobalContractAction{ deploy_mode: AccountId }`, the code registers `GlobalContractIdentifier::AccountId(V)` pointing at the attacker-supplied bytecode — regardless of who the `predecessor_id` (sender) of that receipt is. Any other account can later invoke `UseGlobalContract(GlobalContractIdentifier::AccountId(V))` [5](#0-4)  and receive attacker-controlled code while trusting it was "deployed by V."

The unresolved question is whether an unprivileged attacker can actually get such a receipt created with `receiver_id = V` while `predecessor_id/signer_id = attacker`. Storage cost for the deploy is paid from `account.amount()` — i.e., V's own balance [6](#0-5)  — which would be economically odd for a legitimate flow but is not itself a blocking check. I could not confirm within my available tool budget whether `runtime/runtime/src/verifier.rs` or transaction/action admission elsewhere in the codebase disallows a directly-signed transaction with `signer_id != receiver_id` for actions like `DeployGlobalContract`/`DeployContract`. If no such restriction exists (as none was found in the three files directly implementing this action), the attack path is reachable via an ordinary signed transaction: `{signer_id: attacker, receiver_id: V, actions: [DeployGlobalContract{code: evil_bytecode, deploy_mode: AccountId}]}`.

### Impact Explanation
If reachable, this is an authorization escalation across accounts: an unprivileged attacker can plant arbitrary bytecode under a victim's `AccountId` identifier in the global contract registry, letting any third party that does `UseGlobalContract(AccountId(V))` unknowingly execute attacker-controlled code while believing it originates from V. This maps to NEAR's authorization-escalation-across-accounts bounty category and could lead to downstream theft of funds from any account/protocol that trusts the `AccountId(V)` code provenance.

### Likelihood Explanation
Feasibility is entirely gated on whether the transaction-admission/verifier layer permits a signer to target an arbitrary `receiver_id` with a `DeployGlobalContract` action and have it execute against that receiver's account — a precondition I was unable to confirm or refute with certainty from the files reviewed. The three files directly responsible for this action (`receipt_manager.rs`, `action_validation.rs`, `global_contracts.rs`) contain no such check themselves.

### Recommendation
In `action_deploy_global_contract` (or upstream in `validate_deploy_global_contract_action`), for `GlobalContractDeployMode::AccountId`, require that the receipt's `predecessor_id` equals the receipt's `receiver_id` (and thus the `account_id` being deployed under), rejecting the action otherwise with a dedicated `ActionErrorKind`/`ActionsValidationError` variant.

### Proof of Concept
Add a unit test in `runtime/runtime/src/action_validation.rs` (or a runtime/test-loop integration test) that constructs a receipt with `predecessor_id = "attacker.near"`, `receiver_id = "victim.near"`, and action `DeployGlobalContractAction{ code, deploy_mode: AccountId }`, and asserts the action is rejected unless `predecessor_id == receiver_id`. A companion test-loop test should assert that after applying such a receipt (if currently accepted), `GlobalContractIdentifier::AccountId("victim.near")` resolves to attacker-supplied bytecode, then assert this should be an error post-fix.

        .saturating_mul(deploy_contract.code.len() as u128);

        &deploy_contract.deploy_mode,
        apply_state.shard_id,

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
