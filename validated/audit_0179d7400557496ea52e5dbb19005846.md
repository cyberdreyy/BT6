### Title
Post-default instant-withdraw receipts join the defaulted epoch bucket and drain the shared recovery reserve — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`requestInstantWithdraw` does not check `defaultRecoveryFinalized`. After default finalization, `epochNumber` never increments again (no further `stopEpoch`/`deposit` while defaulted), so a new instant-withdraw request is recorded in `instantWithdrawsRequestsByEpoch[user][epochNumber]` where `epochNumber == defaultRecoveryEpoch`. `claimInstantWithdrawRequest` then routes it through `_claimDefaultedInstantWithdrawRequest`, which pays `claimBasis * defaultRecoveryPrice` out of `defaultRecoveryReserve` — reserve that was sized at finalization to cover only the claims that existed then. This is the credit-vault analog of a use-after-free: state (the recovery bucket keyed by `defaultRecoveryEpoch`) that was logically finalized/"freed" is reused for new receipts, letting a post-default attacker claim against a fixed reserve.

### Finding Description
In `IdleCreditVault.requestInstantWithdraw` (lines 356–375) there is no `defaultRecoveryFinalized` branch, unlike `requestWithdraw` (lines 247–258), which explicitly diverts post-default requests into the prefunded `postDefaultRequests` path. The function burns CDO strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws`.

In `claimInstantWithdrawRequest` (lines 380–392), when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, `_claimDefaultedInstantWithdrawRequest` (lines 842–856) reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. Since `defaultRecoveryEpoch` is set to the then-current `epochNumber` in `finalizeDefaultRecovery` (line 693) and `epochNumber` only advances via `deposit` during `stopEpoch` (lines 607–611) — unreachable after default — a receipt created *after* finalization is indistinguishable from a defaulted-epoch receipt.

The payout is funded from `defaultRecoveryReserve` via `_transferDefaultRecovery`, but the reserve amount and `defaultRecoveryPrice` were computed in `finalizeDefaultRecovery` (lines 686–692) over `totalBasis` that excluded any future receipts. Each post-default instant request therefore withdraws `amount * defaultRecoveryPrice / 1e18` of reserve that belongs to legitimate defaulted claimants, and simultaneously decrements `pendingInstantWithdraws` (line 852) corrupting the unfunded-remainder accounting.

### Impact Explanation
An attacker holding (or flash-acquiring) tranche tokens can call `requestInstantWithdraw` after default finalization and immediately `claimInstantWithdrawRequest`, extracting up to `requestAmount * defaultRecoveryPrice` underlying from the fixed recovery reserve. Repeated requests (the reserve check is only solvency of the strategy balance, not per-claim accounting) can drain the reserve, causing direct theft from and permanent underfunding of all other defaulted-epoch receipt holders and post-default claimants. Loss is quantifiable: each claim removes `amount * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve` that was never provisioned for it.

### Likelihood Explanation
Requires the vault to operate in a mode where instant withdraws are enabled (not programmable mode, which asserts `pendingInstantWithdraws == 0`), the CDO to still permit `requestInstantWithdraw` after `defaulted()` (the strategy side imposes no barrier, and the symmetric `requestWithdraw` path shows post-default requests are expected to remain possible), and a non-trivial `defaultRecoveryPrice`. The attacker only needs tranche tokens at the (post-default, heavily discounted) price, making the cost of the receipt basis low relative to the reserve payout.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: either revert when `defaultRecoveryFinalized` is true, or route the request into an explicitly funded bucket (e.g., `postDefaultRequests`-style accounting backed by newly pulled funds) so it can never touch `defaultRecoveryReserve` or the `defaultRecoveryEpoch` receipt mapping. Additionally, `_claimDefaultedInstantWithdrawRequest` could verify the receipt epoch was recorded strictly before finalization.

```solidity
// Foundry fork PoC sketch (against test/foundry/IdleCreditVault.t.sol harness)
// 1. LP deposits AA, epoch runs, borrower defaults; manager triggers default flow.
// 2. Someone calls finalizeDefault on IdleCDOEpochVariant -> strategy.finalizeDefaultRecovery(recovered, source)
//    -> defaultRecoveryFinalized = true; defaultRecoveryEpoch = epochNumber; defaultRecoveryPrice = p.
// 3. Attacker (holding discounted tranche tokens) calls:
//      cdoEpoch.requestInstantWithdraw(attackerTrancheBalance, tranche);
//    strategy mints receipt, writes instantWithdrawsRequestsByEpoch[attacker][epochNumber]
//    where epochNumber == defaultRecoveryEpoch.
// 4. Attacker calls cdoEpoch.claimInstantWithdrawRequest();
//    _claimDefaultedInstantWithdrawRequest pays amount * p / 1e18 from defaultRecoveryReserve.
// 5. Repeat until strategy underlying balance < remaining legitimate claims * p.
// Assert: sum of all payouts > defaultRecoveryReserve earmarked at finalization;
//         a legitimate defaulted claimant's claim reverts or pays less than basis * p.
```

Caveat: I could not fully verify whether `IdleCDOEpochVariant.requestInstantWithdraw` reverts when `defaulted()` is true (the grep did not return the function body). If the CDO hard-blocks instant requests post-default at the entry point, the strategy-side gap is unreachable and the finding reduces to a defense-in-depth issue.
