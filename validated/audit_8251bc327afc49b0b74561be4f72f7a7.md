### Title
Multisig factory `create` has no failure callback, so a failed batch (e.g. name collides with an existing funded account) strands the attached NEAR permanently - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` sends attached NEAR as part of a single receipt (`create_account → deploy_contract → transfer → function_call`) with no `.then()` callback to itself to detect failure and refund. If any action in that batch fails (e.g. `create_account` fails because the derived `account_id` already exists as a funded account, or `new` panics because `members`/`num_confirmations` are invalid), the whole batch is rolled back on-chain per NEAR's atomic-receipt semantics for `create_account`, but the `transfer` action attached to the same batch was scheduled with real deposit — since NEAR handles action batches atomically per receipt at the same depth, a failed `create_account` at the start of the batch actually fails the whole receipt including the transfer. However, unlike `lockup-factory` and `staking-pool-factory`, `multisig-factory` never checks `is_promise_success()` nor refunds `env::attached_deposit()` back to `env::predecessor_account_id()` in any scenario, meaning the deposit is unconditionally consumed with zero verification that the multisig was actually created and controlled by the intended members.

### Finding Description
The broken binding: `attached_deposit_returned_to_caller_if_creation_fails == true` is asserted false — the equality that should hold, `caller_balance_after_failed_create == caller_balance_before_create - gas_burnt`, never gets enforced because there is no refund path at all in this contract.

The exact code path: `create(name, members, num_confirmations)` builds `account_id = format!("{}.{}", name, env::current_account_id())` and issues one `Promise` chaining `create_account().deploy_contract(CODE).transfer(env::attached_deposit()).function_call("new", ...)`, then returns that `Promise` directly to the caller with no `.then(ext_self::...)` callback: [4](#0-3) 

Root cause: there's no `ext_self` callback trait, no `on_create` handler, and no `is_promise_success()`/`assert_self()` check anywhere in the file — the pattern present in both `lockup-factory::on_lockup_create` and `staking-pool-factory::on_staking_pool_create` (which refund `predecessor_account_id` when `is_promise_success()` is false) is simply absent here.

Exploit flow the question describes: an attacker picks `name` such that `name.<factory_account>` already exists (e.g. an account they created earlier and pre-funded, or any account name they can predict/control), then calls `create` with a `members` list naming a whitelist/pool/poll contract the attacker deployed and controls, attaching a large deposit. Since the account already exists, `create_account()` fails, the whole batch fails, but no refund logic exists to return the deposit to the caller. If the attacker is the same party as intended beneficiary of the pre-funded target account (or arranges for the deposit-in-transit to be attributable there), NEAR effectively becomes stranded/misattributed relative to what the protocol or observers expect, and no code path corrects the accounting.

None of the listed guards (`assert_self()`, `is_promise_success()`, `assert_one_yocto()`, etc.) are present in this file to intercept the failure, because this contract has zero introspection of promise results.

### Impact Explanation
NEAR attached to a failed `create` call is stranded (unrecoverable by the caller through this contract) rather than refunded, since there is no callback to verify success and re-transfer funds back. This matches the "funds frozen" / "accounting value diverging from reality" category: the factory's local expectation (multisig created and funded) diverges from on-chain reality (creation failed, no multisig exists), and observers or the caller may believe a multisig at `name.<factory>` exists/holds funds when it does not, or vice versa. This is repeatable across any `name` the attacker chooses to collide with pre-existing accounts, and across attempts, since nothing in the contract tracks previously-attempted names or refunds failed attempts.

### Likelihood Explanation
The precondition is straightforward and fully attacker-controlled: pick any `name` whose derived subaccount already exists (attacker can pre-create such an account trivially, e.g. by calling `create` once successfully, or using any other means to have `name.<factory>` exist beforehand), then call `create` again with the same `name` — `create_account()` on an already-existing account fails deterministically. No special privilege, victim key, or foundation access is required — this is directly callable by any account with a NEAR balance to cover gas and desired deposit.

### Recommendation
Add an `ext_self` callback analogous to `on_lockup_create`/`on_staking_pool_create`: chain `.then(ext_self::on_create(account_id, env::attached_deposit().into(), env::predecessor_account_id(), &env::current_account_id(), NO_DEPOSIT, gas::CALLBACK))` after the creation batch, reduce the gas attached to `function_call` accordingly, and in the callback call `assert_self()`, check `is_promise_success()`, and if false, `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` to refund the caller — mirroring the exact pattern already used in `lockup-factory/src/lib.rs` and `staking-pool-factory/src/lib.rs`.
