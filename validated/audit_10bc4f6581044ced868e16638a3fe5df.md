### Title
Cross-user response hijacking via unvalidated, attacker-chosen `MessageId` collision - ([File: core/services/gateway/handlers/common/message_util.go])

### Summary
`ValidatedMessageFromReq` copies the attacker-controlled `jsonrpc2.Request.ID` directly into `m.Body.MessageId` with no uniqueness or ownership binding to the signer. Downstream, `handler.HandleLegacyUserMessage` stores the per-request callback in a map keyed solely by this `MessageId`, so a second signed request that reuses an in-flight victim's `MessageId` silently overwrites the first entry, allowing the attacker to receive the DON's response intended for another user.

### Finding Description
`ValidatedMessageFromReq` in `core/services/gateway/handlers/common/message_util.go` performs no check that `req.ID` is unique or bound to `req`'s signer before assigning it to `m.Body.MessageId`: [1](#0-0) 

This message is then passed into `handler.HandleLegacyUserMessage`, which stores the callback keyed only by `msg.Body.MessageId`, unconditionally overwriting any pre-existing entry for the same ID: [2](#0-1) 

The corresponding response path, `handleWebAPITriggerMessage`, looks up and deletes the callback purely by `MessageId`, with no verification that the message's originating `Sender` matches whoever owns the currently-stored callback: [3](#0-2) 

The only sender-related check on the return path is `msg.Body.Sender != nodeAddr` in `HandleNodeMessage`, which validates that the *DON node* signed the response — it says nothing about which *user* originally submitted the request that this `MessageId` belongs to: [4](#0-3) 

Exploit flow:
1. Victim submits a signed legacy gateway request with `MessageId = X`; the gateway stores `savedCallbacks[X] = victimCallback` and forwards the request to all DON members.
2. Before the DON responds, the attacker submits their own signed request with `req.ID = X` (same value). `ValidatedMessageFromReq` accepts it unconditionally (no uniqueness check), and `HandleLegacyUserMessage` overwrites `savedCallbacks[X]` with `attackerCallback`.
3. When a DON node later responds with `MessageId = X` (which could correspond to either request depending on network timing, since both were forwarded to nodes under the same ID), `handleWebAPITriggerMessage` delivers the result to whatever callback currently occupies `savedCallbacks[X]` — potentially the attacker's callback even though the payload was produced for the victim's request, or vice versa.
4. `The dummyHandler` implementation exhibits the identical unguarded overwrite pattern: `d.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}`. [5](#0-4) 

Nothing in the request path (`ValidatedMessageFromReq`, `HandleLegacyUserMessage`, or the gateway's `ProcessRequest`) checks whether `MessageId` is already in-flight for a different signer before accepting/overwriting it. [6](#0-5) 

### Impact Explanation
This is a cross-user response/request confusion: an unprivileged attacker who can send signed gateway requests can hijack another user's DON response for a chosen `MessageId`, or clobber another user's pending request such that they never receive their own response (denial of response) while the attacker instead receives it. Since `web_api_target`/`compute_action` responses may embed sensitive external-endpoint data intended for the victim's workflow, this can result in disclosure of another user's response data to an unauthorized party — matching the "cross-user response confusion" / unauthorized access to another user's data class in Chainlink's bounty scope.

### Likelihood Explanation
Exploitability requires: (1) the attacker be able to submit an arbitrary signed gateway request (any address holder can do this — no special role needed), and (2) the attacker know or guess a victim's in-flight `MessageId` and win the race to overwrite `savedCallbacks[X]` before the DON response arrives (a window of up to `CallbackMaxAgeSec`, default 120s). `MessageId` values are entirely client-chosen and not required to be random/unpredictable by any validation in `ValidatedMessageFromReq` or `Message.Validate()`, so if client tooling uses low-entropy or predictable IDs (sequence numbers, timestamps), guessing is feasible; if truly random UUIDs are used by all clients, practical likelihood drops, but no server-side control enforces this. This is a real, reproducible race condition, not a purely theoretical corner case.

### Recommendation
Bind the callback storage to both `MessageId` and the requester's identity (e.g., key by `(sender, MessageId)` or embed the sender's address/signature hash into the internal lookup key rather than relying solely on client-supplied `MessageId`). Additionally, reject a new request whose `MessageId` already has an active, non-expired callback registered instead of silently overwriting it in `HandleLegacyUserMessage`/`dummyHandler.HandleLegacyUserMessage`, and verify the DON's echoed message's implicit request-sender association matches the original requester before delivering the response.

### Proof of Concept
Go test plan (in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct two distinct signers, `signerA` (victim) and `signerB` (attacker), each producing a `triggerRequest` with identical `MessageId` (e.g., manually set the same request ID string for both, bypassing normal random generation).
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` then immediately `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` before any node response arrives.
3. Assert `handler.savedCallbacks[X]` now refers to `cbB` (attacker), demonstrating `cbA` was silently displaced.
4. Simulate a DON node response for `MessageId = X` via `handler.HandleNodeMessage`, and assert that `cbB.Wait(ctx)` receives the response (should have gone to `cbA`), while `cbA.Wait(ctx)` times out — proving cross-user response delivery/denial.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
