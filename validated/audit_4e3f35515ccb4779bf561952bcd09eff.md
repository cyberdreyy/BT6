### Title
Variables.Set() has no key/flag protection, allowing an attacker-supplied variable to silently overwrite an Internal/Masked/File variable of the same Key - (File: common/spec/variables.go)

### Summary
`Variables.Set()` deduplicates purely by `Key`, using unconditional last-write-wins semantics with no check on the `Internal`, `Masked`, or `File` flags of the variable being replaced. Any code path that calls `Set()` with an attacker-influenced variable set after (or together with) an internal variable of the same `Key` will let the attacker's entry evict the internal one from `*Variables`.

### Finding Description
`Set()` builds a `map[string]Variable` keyed only by `v.Key` from the incoming `newJobVars`, then does: [1](#0-0) 

```
*b = slices.DeleteFunc(*b, func(v Variable) bool {
    _, exists := newVarsByKey[v.Key]
    return exists
})
```

This deletes **any** existing entry in `*b` whose `Key` matches a key present in the new batch — regardless of whether that existing entry is `Internal: true`, `Masked: true`, or `File: true` — and then appends the new (attacker-controlled) entry unconditionally. There is no comparison of flags, no precedence rule, and no rejection/merge-preserving logic for protected variables. The companion `value()`/`Get()` lookup (lines 107-123) likewise scans from the end of the slice and returns whichever entry is physically last for a given `Key`, again with no flag-aware precedence.

Because `Set()` treats every key purely as an interchangeable map entry, the *only* thing preventing an unprivileged job variable from clobbering an internal variable such as a Runner-generated `CI_JOB_TOKEN`, cache key, or checkout URL variable is whatever ordering/filtering happens **before** `Set()` is called (e.g., GitLab backend-side protection of predefined variable names, or Runner-side ordering that appends internal vars after job vars). `Set()` itself provides zero enforcement of the stated invariant "internal/protected variables must not be overwritable by job-supplied variables of the same key."

### Impact Explanation
If any call site in `Build` assembly merges job-supplied variables into `Build.Variables` via `Set()` after (or in the same call as) internal variables — e.g., a Runner-internal `CI_JOB_TOKEN`, artifact/cache path variable, or checkout URL variable — an attacker who controls job variable `Key`/`Value` pairs can overwrite that internal variable's value while `Internal`/`Masked` protections are lost entirely (since the whole `Variable` struct, including flags, is replaced by the attacker's entry). This could lead to credential leakage across jobs/projects or redirection of cache/artifact/checkout operations to attacker-chosen destinations, as described in the scoped impact.

### Likelihood Explanation
This is fully reachable if `Set()` is invoked with an unprivileged job's variables after internal variables already occupy `*Variables` (matching the stated call sequence: "Build assembles base internal vars -> Build merges job vars via Variables.Set(jobVars...)"). No special privilege is needed beyond defining a job/pipeline variable with a colliding `Key` — an unprivileged pipeline author's normal capability. The likelihood ultimately depends on whether any external protection (GitLab backend filtering of colliding predefined-variable names, or Runner call-site ordering that always appends internal vars *after* job vars) is enforced outside of this function; I could not fully confirm the exact `Build`-level call order into `Set()` in this repository from available file contents, so the concrete end-to-end reachability through a specific `Build` method could not be independently verified beyond the function-level defect itself.

### Recommendation
Make `Set()` flag-aware: when an existing entry for a `Key` has `Internal: true` (or any other "protected" marker), reject or ignore replacement attempts from non-internal callers, or require callers to explicitly opt in to overriding protected keys. At minimum, add a guard such as:
```go
*b = slices.DeleteFunc(*b, func(v Variable) bool {
    nv, exists := newVarsByKey[v.Key]
    return exists && !(v.Internal && !nv.Internal)
})
```
and drop map entries that would violate that rule before appending, so an internal variable can only be replaced by another internal variable.

### Proof of Concept
```go
func TestSet_InternalNotOverwritable(t *testing.T) {
    vars := Variables{
        {Key: "CI_JOB_TOKEN", Value: "s3cr3t-token", Internal: true, Masked: true},
    }

    // attacker-supplied job variable with the same Key, non-internal
    vars.Set(Variable{Key: "CI_JOB_TOKEN", Value: "attacker-value", Internal: false})

    got := vars.Get("CI_JOB_TOKEN")
    assert.Equal(t, "s3cr3t-token", got, "internal variable must not be overwritable by job-supplied variable of same key")
}
```
Expected today: the assertion fails — `Get("CI_JOB_TOKEN")` returns `"attacker-value"`, proving `Set()` allows the internal variable to be silently replaced.

```go
func (b *Variables) Set(newJobVars ...Variable) {
	if len(newJobVars) < 1 {
		return
	}

	newVarsByKey := make(map[string]Variable, len(newJobVars))

	for _, v := range newJobVars {
		// for multiple newJobVars with the same key, only keep the last one
		newVarsByKey[v.Key] = v
	}

	*b = slices.DeleteFunc(*b, func(v Variable) bool {
		_, exists := newVarsByKey[v.Key]
		return exists
	})

	for _, v := range newVarsByKey {
		*b = append(*b, v)
	}
}
```
