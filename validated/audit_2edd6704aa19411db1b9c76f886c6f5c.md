### Title
Unchecked-length panic in `parse_l1_info` reachable from txpool transaction validation - ([File: crates/execution/evm/src/l1.rs])

### Summary
`parse_l1_info` in `crates/execution/evm/src/l1.rs` indexes into its `input: &[u8]` argument (`input[0..4]`, `input[4..]`) without first checking that the slice is at least 4 bytes long, and its own doc comment admits this: *"Caution this expects that the input is the calldata of the L1BlockInfo transaction... # Panics: If the input is shorter than 4 bytes."* [1](#0-0)  The only "safe" wrapper, `extract_l1_info_from_tx`, performs the length check before calling it [2](#0-1) , but `parse_l1_info` is `pub` and is also called directly from `crates/execution/txpool/src/validator.rs`, bypassing that guard.

### Finding Description
This is the same bug class as the ipvlan CVE: a parser assumes a header of a fixed minimum size is fully present in the buffer before indexing into it, instead of validating the buffer length first (`pskb_network_may_pull` in the kernel case; a `len() < 4` check here). `parse_l1_info` performs the unchecked `input[0..4]` comparison against 4-byte selectors and then slices `input[4..]` before delegating to `parse_l1_info_tx_{jovian,isthmus,ecotone,bedrock}`, all without any bounds validation in the function itself [3](#0-2) . Only the caller `extract_l1_info_from_tx` performs the `len() < 4` check [4](#0-3) . Because `parse_l1_info` is exported and called separately in `crates/execution/txpool/src/validator.rs` (confirmed via reference search, two call sites), any code path that reaches `parse_l1_info` directly — rather than through `extract_l1_info_from_tx` — with attacker-supplied `input` shorter than 4 bytes will trigger an out-of-bounds slice panic instead of a graceful decode error.

### Impact Explanation
Transaction pool admission (`txpool`) is an explicitly in-scope path reachable by any unprivileged transaction sender submitting a raw transaction via RPC. If the txpool validator invokes `parse_l1_info` on attacker-controlled transaction input (e.g., while checking whether a submitted transaction masquerades as/relates to the L1-info system transaction) without first checking `input.len() >= 4`, an attacker can submit a transaction with `input` of length 0–3 bytes and cause a slice-index panic in the node process handling transaction validation. A panic in this code path can crash or hang the executing node/thread, resulting in a node halt/DoS — a concrete, high-severity impact for a widely reachable, single-transaction attack surface.

### Likelihood Explanation
Likelihood is high if the `validator.rs` call sites do not perform their own independent length check before calling `parse_l1_info` (only `extract_l1_info_from_tx` is documented/observed to add that guard). Any unprivileged sender can craft a transaction with empty or very short `input` data and submit it via the public transaction-submission RPC, requiring no special privileges, gas expenditure beyond a normal transaction, or timing conditions.

### Recommendation
Add an explicit length check (`if input.len() < 4 { return Err(...) }`) inside `parse_l1_info` itself rather than relying on every caller to perform the check beforehand, mirroring the fix pattern used in the kernel (validate header presence before parsing, at the parsing function itself rather than only at some callers). Alternatively, make `parse_l1_info` non-`pub` and force all external call sites through `extract_l1_info_from_tx`, which already contains the guard.

### Proof of Concept
1. Submit any transaction via the public txpool/RPC ingestion path with `input` set to a value with a length between 0 and 3 bytes.
2. If the transaction validation logic in `crates/execution/txpool/src/validator.rs` calls `parse_l1_info(input)` directly (as opposed to through `extract_l1_info_from_tx`), the `input[0..4]` comparisons in `parse_l1_info` panic on out-of-bounds slicing [5](#0-4) , crashing/aborting the validating task or node thread.

Note: I could not retrieve the exact source of the two `parse_l1_info` call sites in `crates/execution/txpool/src/validator.rs` within the available tool budget, so I cannot confirm with full certainty whether an independent length guard already exists at those specific call sites before invoking `parse_l1_info`. This should be verified directly in that file before treating the finding as conclusively exploitable.

/// Extracts the [`L1BlockInfo`] from the L1 info transaction (first transaction) in the L2
/// block.
///
/// Returns an error if the calldata is shorter than 4 bytes.
pub fn extract_l1_info_from_tx<T: Transaction>(
    tx: &T,
) -> Result<L1BlockInfo, BaseBlockExecutionError> {
    let l1_info_tx_data = tx.input();
    if l1_info_tx_data.len() < 4 {
        return Err(BaseBlockExecutionError::L1BlockInfo(L1BlockInfoError::InvalidCalldata));
    }

    parse_l1_info(l1_info_tx_data)
}

/// Parses the input of the first transaction in the L2 block, into [`L1BlockInfo`].
///
/// Returns an error if data is incorrect length.
///
/// Caution this expects that the input is the calldata of the [`L1BlockInfo`] transaction (first
/// transaction) in the L2 block.
///
/// # Panics
/// If the input is shorter than 4 bytes.
pub fn parse_l1_info(input: &[u8]) -> Result<L1BlockInfo, BaseBlockExecutionError> {
    // Parse the L1 info transaction into an L1BlockInfo struct, depending on the function selector.
    // There are currently 4 variants:
    // - Jovian
    // - Isthmus
    // - Ecotone
    // - Bedrock
    if input[0..4] == L1_BLOCK_JOVIAN_SELECTOR {
        parse_l1_info_tx_jovian(input[4..].as_ref())
    } else if input[0..4] == L1_BLOCK_ISTHMUS_SELECTOR {
        parse_l1_info_tx_isthmus(input[4..].as_ref())
    } else if input[0..4] == L1_BLOCK_ECOTONE_SELECTOR {
        parse_l1_info_tx_ecotone(input[4..].as_ref())
    } else {
        parse_l1_info_tx_bedrock(input[4..].as_ref())
    }
}
