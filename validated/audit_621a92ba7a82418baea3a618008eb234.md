### Title
Loss-adjusted withdraw receipts are paid at par once a newer request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` distinguishes "funded-at-par" receipts from "loss-adjusted" receipts only via `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`. When a user's haircut receipt from a `stopEpochWithDuration` loss epoch is followed by any later withdraw request, the loss-epoch tag is no longer consulted and the entire aggregated `withdrawsRequests[user]` — including the haircutted basis — is paid at par through `_claimFundedWithdrawRequest`, letting the attacker over-claim underlyings that were never funded.

### Finding Description
`collectWithdrawFunds(_amount)` records a haircut when `_amount < pendingWithdraws`: it stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws`, while only pulling the reduced `_amount` from the CDO [1](#0-0) . The haircut is later applied only in `_claimLossAdjustedWithdrawRequest`, which looks up the recovery price using `lastWithdrawRequest[_user]` as the epoch key [2](#0-1) .

The "type tag" of a receipt (funded vs loss-adjusted) is therefore inferred from a single mutable per-user slot. `requestWithdraw` overwrites `lastWithdrawRequest[_user] = currentEpoch` and adds the full basis to both `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` [3](#0-2) . If the user makes a second withdraw request in a later, fully-funded epoch, `lastWithdrawRequest` points at an epoch with `lossRecoveryPriceByEpoch == 0`, so `_claimLossAdjustedWithdrawRequest` returns 0 [4](#0-3) . `_claimFundedWithdrawRequest` then pays `normalAmount = withdrawsRequests[_user]` — which still contains the uncleared haircutted basis from the loss epoch — entirely at par via `_transferFundedClaim` [5](#0-4) .

### Impact Explanation
The loss epoch was funded with only `claimBasis * lossRecoveryPrice / RECOVERY_FULL` underlying, but the user withdraws the full `claimBasis`. The excess `claimBasis * (1 - lossRecoveryPrice)` is stolen from strategy-held underlyings, directly reducing funds available for other pending receipts and LPs — a solvency/fair-payout invariant break with quantified loss equal to the unapplied haircut. The `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve` (nonzero only after a borrower default), so it does not stop this [6](#0-5) .

### Likelihood Explanation
The attacker is an ordinary KYC'd tranche holder and needs only: (1) an epoch stopped via `stopEpochWithDuration`/`_lossAmount` where their pending receipt is haircut (an honest manager action on realized loss), (2) a later withdraw request in a healthy epoch, then (3) a single `claimWithdrawRequest` call. No privileged role is attacker-controlled; the bug triggers on a routine sequence.

### Recommendation
In `_claimFundedWithdrawRequest` (or before it), iterate `withdrawsRequestsByEpoch` entries or track per-user loss epochs so that any epoch with `lossRecoveryPriceByEpoch != 0` is always routed through the haircut path regardless of `lastWithdrawRequest`. Alternatively, in `requestWithdraw`, revert or settle outstanding loss-adjusted receipts before allowing a new request, so the aggregate `withdrawsRequests` never mixes haircutted and par-funded basis.

### Proof of Concept

```solidity
// Setup: deposit `tranches` for attacker; startEpoch; requestWithdraw(tranches).
// Epoch E ends with a realized loss:
//   manager calls cdoEpoch.stopEpochWithDuration(..., _lossAmount) such that
//   strategy.collectWithdrawFunds(x) is invoked with x < pendingBasis,
//   storing lossRecoveryPriceByEpoch[E] = p < RECOVERY_FULL.
// Attacker does NOT claim. Next epoch E+1:
//   attacker deposits again (or holds residual tranches) and calls requestWithdraw
//   -> lastWithdrawRequest[attacker] = E+1; withdrawsRequests[attacker] += basis_E1
//   Epoch E+1 stops healthy and fully funded.
//   attacker calls cdoEpoch.claimWithdrawRequest():
//     _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[E+1] == 0 -> 0
//     _claimFundedWithdrawRequest: pays withdrawsRequests[attacker] = basis_E + basis_E1 at par
// Assert: underlying received > basis_E * p / FULL + basis_E1  (stole basis_E * (1-p))
```

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
