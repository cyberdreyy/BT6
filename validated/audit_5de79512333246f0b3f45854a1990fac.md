### Title
Stale confirmations from removed multisig members are still counted toward the approval threshold, allowing a request to execute below the required live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` (multisig2) removes a member from `self.members` and deletes only the requests *added* by that member, but leaves intact any confirmations that member cast on *other* still-pending requests. Because `confirm()` counts confirmations purely by `HashSet` length (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without checking that every recorded confirmer is still a current member, a request can execute once the counted confirmations reach `num_confirmations` even though one or more of those confirmations came from an account that is no longer part of the multisig.

### Finding Description
The binding that should hold is:
`live confirmations for request R == confirmations from accounts in self.members at execution time`

Instead, `confirm()` in [1](#0-0)  only checks the size of the `confirmations` `HashSet` against `num_confirmations`; it never re-validates that each entry in that set is still contained in `self.members`.

`delete_member` in [2](#0-1)  only cleans up requests where `r.member == member` (i.e., requests the removed member *created*), and only removes the `num_requests_pk` entry for that member. It never scans `self.confirmations` for entries where the removed member had *confirmed* someone else's still-open request.

As a result:
1. Member `B` confirms a pending request `R` that was created by member `A` (`confirmations = {A, B}`).
2. Member `B` is later removed via a separate `DeleteMember` request approved by the required threshold.
3. `R` remains pending with `confirmations = {A, B}` still stored — `B`'s entry is never purged because `R` was not created by `B`.
4. Any additional live member `C` confirms `R`. `confirmations.len() + 1 = 3` reaches `num_confirmations`, and `R` executes via `execute_request` in [3](#0-2) , even though only two currently-live members (`A`, `C`) actually approved it.

The v1 contract (`multisig/src/lib.rs`) has the analogous `remove_request` cleanup in [4](#0-3)  which is likewise only invoked on the request-owner's own requests during delete/confirm, not on stale confirmations from other now-removed keys; however v1's membership is implicit (any account access key), reducing the direct applicability, whereas v2's explicit `members: UnorderedSet<MultisigMember>` makes the mismatch concrete and directly exploitable.

### Impact Explanation
This breaks the multisig's core authorization guarantee: a K-of-N threshold can be satisfied with fewer than K currently-live approvers. This directly matches the Critical impact category "a multisig request executed below threshold," since transfers, key additions, contract deployments, or further membership changes can be pushed through with the counted approval of an account that has already been removed from the multisig.

### Likelihood Explanation
This requires no privileged bypass — it only requires the normal governance sequence that every multisig eventually performs: a member confirms a request, and later that same member is legitimately removed (e.g., due to key rotation, compromise, or offboarding) while other requests they confirmed remain pending. Any request that has partial confirmations at the time a confirming member is removed is affected; no attacker collusion beyond normal request/confirm/delete-member operations is needed.

### Recommendation
When removing a member in `delete_member`, iterate over all pending requests' `confirmations` sets (not only those the member created) and strip the removed member's entry. Alternatively, when counting confirmations in `confirm()`, filter the stored confirmation set against current `self.members` before comparing against `num_confirmations`, so that confirmations from accounts no longer in the member set are not counted toward the threshold.

### Proof of Concept
1. Deploy `MultiSigContract::new(members: [A, B, C, D], num_confirmations: 3)`.
2. `A` calls `add_request_and_confirm(R)` where `R` is `Transfer` to some receiver → `confirmations(R) = {A}`.
3. `B` calls `confirm(R)` → `confirmations(R) = {A, B}` (2/3, not yet executed) — see [1](#0-0) .
4. Separately, `A`, `C`, `D` create and confirm a `DeleteMember { member: B }` request that reaches threshold and executes `delete_member(B)` — see [2](#0-1) . Note this only removes requests where `r.member == B`; `R` was created by `A`, so it is untouched and `confirmations(R)` still equals `{A, B}`.
5. `C` (a genuine current member) calls `confirm(R)`. `confirmations.len() + 1 == 3 == num_confirmations`, so `R` executes via `execute_request`, even though `B` is no longer a member and only `A` and `C` are live approvers.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .expect("Failed to remove existing element");
        // decrement num_requests for original request signer
        let original_signer_pk = request_with_signer.signer_pk;
        let mut num_requests = self.num_requests_pk.get(&original_signer_pk).unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_signer_pk, &num_requests);
        // return request
        request_with_signer.request
    }
