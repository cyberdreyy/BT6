Based on the code I reviewed, this finding is not a valid vulnerability.

## Analysis

`formatETHKeyResponse` at [1](#0-0)  simply formats whatever `key`/`state` was placed into the Gin context by `Create`, `Import`, `Export`, or `Chain`, and `Index` at [2](#0-1)  lists all keys from `ethKeyStore.GetAll` with no per-caller filter.

However, the premise of the question — that this "leaks other users' objects" — doesn't hold in this codebase's authorization model:

1. **ETH keys are node-wide resources, not per-user resources.** There is no ownership field tying a `ethkey.KeyV2`/`ethkey.State` to a particular Chainlink node-user. The node operates a single shared keystore; all authenticated node users share the same key set by design. There is no multi-tenant "your keys vs. my keys" concept anywhere in `core/services/keystore` or `core/sessions`.

2. **The route wiring confirms this is intentional.** In `v2Routes`, `/v2/keys/evm` (`GET`, i.e. `Index`) is reachable by any authenticated user via `authv2.GET("/keys/evm", ekc.Index)` with no role wrapper at all (weaker than "view"), while mutating actions require higher roles: `Create` requires `auth.RequiresEditRole`, and `Delete`/`Import`/`Export`/`Chain` all require `auth.RequiresAdminRole`. [3](#0-2) 

3. **The existing RBAC test suite documents this as expected behavior.** The route-rules table marks `GET /v2/keys/eth` (and by extension `/v2/keys/evm`) as `viewOnlyAllowed: true`, meaning a view-role user is explicitly entitled to list all node ETH keys — this is asserted, not accidental. [4](#0-3) [5](#0-4) 

4. **Chainlink's role model (`UserRoleAdmin`/`Edit`/`Run`/`View`) governs *privilege level* for a single shared node, not per-resource ownership scoping.** [6](#0-5)  There is no "entitlement" concept where different node-users see different subsets of the node's own blockchain addresses — every admin user of a given Chainlink node is expected to see the full list of that node's transmitter/sender addresses, which are not secrets (private key material is never included in this response; only address, balances, chain settings).

Since there is no per-user ownership model for ETH keys, a view-role user seeing the full key listing is not "cross-user response confusion" or unauthorized disclosure — it is the intended behavior of a single-tenant node with role-tiered access, and it does not expose private key material (`Export` requiring admin role is the actual privileged operation, correctly gated).

### No Vulnerability found for this question.

func (ekc *ETHKeysController) Index(c *gin.Context) {
	ethKeyStore := ekc.app.GetKeyStore().Eth()
	var keys []ethkey.KeyV2
	var err error
	keys, err = ethKeyStore.GetAll(c.Request.Context())
	if err != nil {
		err = errors.Errorf("error getting unlocked keys: %v", err)
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
	states, err := ethKeyStore.GetStatesForKeys(c.Request.Context(), keys)
	if err != nil {
		err = errors.Errorf("error getting key states: %v", err)
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
	var resources []presenters.ETHKeyResource
	for _, state := range states {
		key, err := ethKeyStore.Get(c.Request.Context(), state.Address.Hex())
		if err != nil {
			jsonAPIError(c, http.StatusInternalServerError, err)
			return
		}

		r := createETHKeyResource(c, ekc, key, state)

		resources = append(resources, *r)
	}
	// Put disabled keys to the end
	sort.SliceStable(resources, func(i, j int) bool {
		return !resources[i].Disabled && resources[j].Disabled
	})

	jsonAPIResponseWithStatus(c, resources, "keys", http.StatusOK)
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

	}
