### Title
Response cache key omits `WorkflowID`, causing cross-workflow HTTP response confusion for the same workflow owner - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The Gateway's HTTP Action `responseCache` is documented as being "scoped by workflow ID to prevent cross-workflow data leakage," but the underlying `OutboundHTTPRequest.Hash()` used as the cache key deliberately ignores `WorkflowID` and only incorporates `WorkflowOwner`. As a result, two different workflows belonging to the same owner that issue an HTTP action with the same method/URL/headers/body will read and reuse each other's cached HTTP responses. This is analogous to the `estimatedAPR()` bug class: a value (here, a cached response) is served to a consumer under stale/incorrect scoping assumptions that no longer reflect the actual state (here, which workflow the response belongs to), because the "freshness/ownership" check the code relies on (the hash key) does not capture a dimension (workflow identity) that the documented invariant claims it does.

### Finding Description
`responseCache` stores entries keyed by `req.Hash()`: [1](#0-0) 

Fetch/Set operate purely on this hash key with a TTL, with no additional per-workflow segregation: [2](#0-1) 

The system's own test suite proves the hash intentionally excludes `WorkflowID` while including `WorkflowOwner`: [3](#0-2) [4](#0-3) 

However, the component's design documentation states the opposite guarantee — that cache entries are workflow-scoped to prevent cross-workflow leakage: [5](#0-4) 

The cache is consumed directly from the gateway's node-message handling path (`makeOutgoingRequest`), which is reachable whenever a workflow node issues an `HTTPAction` request through the gateway: [6](#0-5) 

Because the cache key is derived only from `(method, URL, headers, body, workflowOwner)` and not `workflowID`, any two workflows deployed by the same owner (a common pattern — an owner may run many concurrent workflows) that make an outbound HTTP action request with identical method/URL/headers/body will hit the same cache entry. Workflow B can receive the cached HTTP response that was actually fetched (and possibly customized/parameterized) for Workflow A, or vice versa — even though these are logically distinct executions that the documentation claims are isolated.

### Impact Explanation
This is a cross-user/cross-workflow response confusion bug: an unprivileged workflow owner running multiple workflows (or a single owner's multiple deployed workflow versions) can have one workflow's execution silently consume cached HTTP response data intended for/produced by a different workflow. If the two workflows expected different data (e.g., different query parameters encoded only in body/headers not covered exactly, or expected freshness semantics), this leads to logic errors, incorrect on-chain reports, or data leakage between workflows sharing an owner — violating the explicitly documented isolation guarantee. Severity is bounded by requiring identical `(method, URL, headers, body)` across workflows of the same owner, but this is a realistic scenario for owners running templated/parameterized workflow families that hit the same well-known endpoints.

### Likelihood Explanation
Moderate. It requires: (1) the same `WorkflowOwner` running two or more distinct workflows, and (2) those workflows issuing outbound HTTP action requests with identical `Method`, `URL`, `Headers`, and `Body`, and (3) `CacheSettings.MaxAgeMs > 0` or `Store: true` on the request. This is a common pattern for owners that deploy multiple versions/instances of similar workflows against the same external API.

### Recommendation
Include `WorkflowID` in the cache key computation (`Hash()`), or otherwise partition the `responseCache` map by workflow ID in addition to the existing owner/request hash, so that cache entries are genuinely isolated per-workflow as documented in `README.md`.

### Proof of Concept
1. Workflow A (owner `0xabc`, workflowID `wf-A`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", WorkflowOwner: "0xabc", WorkflowID: "wf-A", CacheSettings: {MaxAgeMs: 5000, Store: true}}`. The gateway fetches and caches the response under `Hash()` (which does not include `WorkflowID`), per `Fetch`/`Set` in `response_cache.go`.
2. Workflow B (same owner `0xabc`, different workflowID `wf-B`) issues an identical `OutboundHTTPRequest` except `WorkflowID: "wf-B"`.
3. Per `response_cache_test.go` lines 139–149, `req1.Hash() == req2.Hash()` when only `WorkflowID` differs.
4. Workflow B's request hits the cache entry stored for Workflow A within the TTL window and receives Workflow A's cached response instead of issuing its own fresh HTTP call — contradicting the documented "Workflow Isolation" guarantee in `README.md`.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)

		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
