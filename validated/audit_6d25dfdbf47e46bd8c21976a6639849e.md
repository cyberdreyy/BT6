## Analog Found: Unsigned integer underflow bypasses the gateway's message-freshness check

### Title
Signed-to-unsigned timestamp underflow bypasses gateway staleness/replay check for legacy trigger messages - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The Vyper report's root cause is that a bounds check (`start + length <= max`) is performed with unsigned arithmetic that can silently wrap around when attacker-controlled values are used, letting the attacker slip past a check meant to constrain access. Chainlink's internet-facing Gateway `HandleLegacyUserMessage` path contains the same bug class: a freshness/anti-replay check is computed with unsigned (`uint`) arithmetic over an attacker-controlled, signed `int64` timestamp, so a negative timestamp wraps to a huge unsigned value and defeats the "stale message" check entirely.

### Finding Description
The Gateway's public HTTP entrypoint `ProcessRequest` accepts unauthenticated, client-supplied JSON-RPC/legacy messages and, for legacy requests (no DonId-less service routing), dispatches them straight to the registered handler's `HandleLegacyUserMessage`: [1](#0-0) 

For the web-api trigger capability, `HandleLegacyUserMessage` unmarshals the fully client-controlled `payload.Timestamp` (`int64`) from the message body and then performs the freshness check:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    ... "stale message" ...
}
``` [2](#0-1) 

`payload.Timestamp` is declared as a signed `int64` field of `TriggerRequestPayload`, fully controlled by the request body the unprivileged client submits: [3](#0-2) 

Casting a negative (or otherwise attacker-chosen extreme) `int64` timestamp to `uint` wraps around to a value near `math.MaxUint64`, which is always greater than `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`. This mirrors the Vyper report's core issue exactly: a bounds/range check implemented with unsigned arithmetic over an untrusted value, without first validating that the subtraction/cast cannot overflow, allows the check to be bypassed by construction rather than by genuinely satisfying the intended condition.

### Impact Explanation
The staleness check exists specifically to bound the freshness of "legacy" web-api trigger messages before they are forwarded to all DON members via `don.SendToNode`: [4](#0-3) 
Bypassing it lets an unprivileged client craft or replay a message with an invalid/very old or negative timestamp that is nonetheless treated as "fresh," undermining the anti-staleness/anti-replay guarantee the gateway is meant to enforce for every workflow node it fans the request out to. Combined with a previously captured, validly-signed message, this weakens replay protection at the gateway boundary — the same class of "check silently defeated by integer wraparound" issue as the original report, just manifesting as a freshness/replay control bypass rather than an out-of-bounds memory/storage read.

### Likelihood Explanation
The path is reachable by any unauthenticated network client hitting the gateway's public endpoint (`ProcessRequest` → legacy handler routing) — no gateway-level authentication or allowlist gates this particular check, since allowlisting is explicitly marked as not-yet-implemented at this handler ("TODO: apply allowlist and rate-limiting here"): [5](#0-4) 
Constructing a negative `int64` JSON value for `timestamp` is trivial, making the wraparound easy to trigger.

### Recommendation
Perform the freshness comparison using signed arithmetic (or `time.Time`/`time.Duration` comparisons) instead of casting an attacker-controlled `int64` to `uint`, e.g. compare `payload.Timestamp` directly against `time.Now().Unix() - int64(h.config.MaxAllowedMessageAgeSec)`, and additionally reject non-positive or otherwise out-of-range timestamps before performing any arithmetic, analogous to adding an explicit overflow guard as recommended in the original report.

### Proof of Concept
1. Send a legacy-format Gateway request whose JSON payload sets `"timestamp": -1` (or any negative `int64`).
2. In `HandleLegacyUserMessage`, `uint(payload.Timestamp)` wraps to `18446744073709551615` (max uint64), so `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec > uint(payload.Timestamp)` evaluates to `false`.
3. The "stale message" branch is skipped, and the message proceeds to be validated/forwarded to all DON members, even though its timestamp is invalid/should have been rejected as stale.
