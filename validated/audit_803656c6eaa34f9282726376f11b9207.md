### Title
Cross-user callback hijack via `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each in-flight user callback in a single global map keyed only by the attacker-controllable `msg.Body.MessageId`, with no binding to the sender's identity. Any external caller can send a request with a `MessageId` equal to another user's currently in-flight `MessageId`, causing `h.savedCallbacks[msg.Body.MessageId]` to be overwritten and the original caller's response callback to be silently replaced by the attacker's.

### Finding Description
`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` performs message validation (payload decoding, timestamp presence, staleness via `MaxAllowedMessageAgeSec`, method check, and signature-based transformation via `common.ValidatedRequestFromMessage`) but none of these checks restrict or namespace `msg.Body.MessageId` per sender: [1](#0-0) 

The only structural constraint on `MessageId` is generic length/null-byte validation in `api.Message.Validate`, and it is not tied to the `Sender` field extracted from the signature: [2](#0-1) [3](#0-2) 

Because the `savedCallbacks` map is keyed solely by `MessageId` (shared across all users of the DON handler instance) and protected only by a mutex for concurrency-safety (not uniqueness), a second `HandleLegacyUserMessage` call with a colliding `MessageId` — signed by an attacker's own key, thus passing signature verification — simply overwrites the map entry for that key: [4](#0-3) 

When the DON node's response for the original (victim's) request eventually arrives, `handleWebAPITriggerMessage` looks up the callback purely by `msg.Body.MessageId` and delivers the response to whichever callback is currently stored — now the attacker's: [5](#0-4) 

The handler explicitly notes that allowlisting is not yet implemented (`// TODO: apply allowlist and rate-limiting here`), confirming any external, unprivileged signer can reach this code path: [6](#0-5) 

### Impact Explanation
This is a cross-user response confusion / request hijack: an attacker can receive another user's gateway response (which may contain sensitive workflow trigger/target output routed through the gateway), and the legitimate caller never receives their response (denial of service for that request). This maps to the Chainlink bounty "unauthorized action on another user's request / cross-user response confusion" impact class.

### Likelihood Explanation
Exploitation requires the attacker to know (or guess/observe) the exact `MessageId` string used by a victim's in-flight request and to time their own signed message to arrive before the node's response for that ID. If `MessageId`s are generated by clients using non-random or predictable schemes, or are otherwise observable (e.g., via logs, timing side channels, or client reuse), this is straightforwardly repeatable by any unauthenticated/unprivileged holder of a signing key, since there is no per-sender allowlist or MessageId ownership check gating `HandleLegacyUserMessage`. If MessageIds are always cryptographically random and never leaked, practical exploitation likelihood is lower, but the code contains no defense-in-depth against this collision regardless of ID entropy.

### Recommendation
Key `savedCallbacks` by a composite of `(Sender, MessageId)` rather than `MessageId` alone, and reject/ignore a `HandleLegacyUserMessage` call whose `(Sender, MessageId)` collides with an existing unexpired entry from a different sender. Correspondingly, node responses should be matched by the same composite key (the response should carry back sender/receiver context sufficient to reconstruct it) so that only the original submitting sender's callback can ever be resolved.

### Proof of Concept
Go handler-level test plan (in `core/services/gateway/handlers/capabilities/handler_test.go` style):
1. Construct `handler` via `NewHandler` with a `don` mock that records `SendToNode` calls.
2. Build victim message `msgA` signed with `keyA`, `MessageId = "shared-id"`, valid `Timestamp`, method `MethodWebAPITrigger`; call `h.HandleLegacyUserMessage(ctx, msgA, callbackA)` where `callbackA.SendResponse` sets `gotA`.
3. Build attacker message `msgB` signed with `keyB`, same `MessageId = "shared-id"`; call `h.HandleLegacyUserMessage(ctx, msgB, callbackB)` where `callbackB.SendResponse` sets `gotB`.
4. Simulate the DON node response for `MessageId = "shared-id"` by calling `h.HandleNodeMessage`/`handleWebAPITriggerMessage` path with a `resp` whose `MessageId` matches.
5. Assert: `gotB` is populated (attacker received the response) while `gotA` remains empty — demonstrating the victim's callback was silently overwritten and never invoked, confirming the cross-user hijack.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
