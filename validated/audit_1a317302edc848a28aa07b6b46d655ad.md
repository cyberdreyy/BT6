### Title
`check_parent_tenure_choice` undercounts a reorged tenure's finalized blocks by relying on the signer's own possibly-stale local `GloballyAccepted` state instead of the node's authoritative tenure data - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner may reorg away prior tenures by counting "globally accepted blocks already signed" using `SignerDb::get_globally_accepted_block_count_in_tenure`, which only counts rows in this one signer's local database whose `state == GloballyAccepted`. The node's own authoritative `TenureForkingInfo` response (which includes `nakamoto_blocks`, a full accounting of blocks the node has actually processed for the tenure) is never consulted for this decision, and the subsequent timing check only ever inspects the *first* approved block in the tenure. A tenure that in truth has two blocks - one already globally finalized network-wide, one merely `LocallyAccepted` in this particular signer's DB because of ordinary propagation lag - is evaluated as if it had only one, and the reorg can be wrongly permitted.

### Finding Description
In `check_parent_tenure_choice` (stacks-signer/src/chainstate/mod.rs), for each tenure being reorged: [1](#0-0) 

the guard is:
```
let globally_accepted_blocks =
    signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
if globally_accepted_blocks > 1 { return Ok(false); }
```
`get_globally_accepted_block_count_in_tenure` is implemented as a `MAX(stacks_height) - MIN(stacks_height) + 1` over rows with `state = GloballyAccepted` in *this signer's own* `blocks` table: [2](#0-1) 

A row transitions to `GloballyAccepted` only once this particular signer has itself processed enough aggregated `BlockResponse`/push traffic to conclude the threshold was met - this is a local, asynchronous belief, not the network's true finalization state. The existing regression test in `signerdb.rs` explicitly documents that a `LocallyAccepted` block is excluded from the count: [3](#0-2) 

If a tenure `T` has block `A` (globally finalized, network-wide) and block `B` (also globally finalized network-wide, but this signer's local DB still shows it as `LocallyAccepted` due to an ordinary propagation race), the count returns `1`, so the `>1` veto never fires.

The remaining checks in the same function do not close the gap: `tenure.first_block_mined` (from the node's `TenureForkingInfo`, see `stackslib/src/net/api/get_tenures_fork_info.rs`) only tells the signer *that* a first block exists, and the timing test is run only against `get_first_approved_block_in_tenure`, i.e., the earliest approved block (`A`) — `B`'s existence and timing are never examined: [4](#0-3) 

Critically, `TenureForkingInfo::nakamoto_blocks` — the node's authoritative list of every Nakamoto block actually recorded for the tenure — is returned by the node's `/v3/tenures/fork_info` endpoint: [5](#0-4) 

but is never read anywhere in `check_parent_tenure_choice`; the decision is made purely from this signer's own possibly-lagging local rows plus a boolean "any block mined" flag. Since `A`'s proposal-to-sortition timing can legitimately be tight (it is the tenure's first block, produced right after the prior sortition), the function returns `Ok(true)`, and the reorg is sanctioned. `validate_tenure_change_payload` then treats the reorg as valid: [6](#0-5) 

and the tenure is marked superseded, releasing this signer's own prior signature (if any) over `B` as a conflict, after which it proceeds to sign the attacker's tenure-change block that discards both `A` and, critically, the already-finalized `B`.

### Impact Explanation
This breaks canonicity/reorg-depth safety: a signer signs a tenure-change block that discards a block (`B`) that has already reached the 70%-weight global acceptance threshold on the network - i.e., a properly finalized block. If enough signers hit this same local-state race at the same moment, this can contribute toward finalizing a chain that conflicts with previously finalized state, which is the Critical "signer signing an invalid, non-canonical, or conflicting block" category. The flaw is deterministic given the described local-state precondition; it is not a one-off and would recur any time the same lag occurs.

### Likelihood Explanation
The attacker needs only: (1) to win a single sortition (their own BTC-backed miner slot, no signer collusion required), and (2) to submit their tenure-change proposal for a `parent_tenure_id` that skips tenure `T` while at least one signer's local `SignerDb` has not yet promoted `T`'s second block to `GloballyAccepted` — a natural, recurring race given that global-acceptance promotion is driven by asynchronous StackerDB/gossip propagation to each signer individually. No majority-signer collusion, node compromise, or auth_token access is needed; the attacker only crafts the tenure-change `BlockProposal` and its timing. Feasibility depends on the propagation-lag window being hit for a decisive fraction of signer weight, but the underlying code defect (count and timing check scoped to local, stale rows and ignoring the node's `nakamoto_blocks` truth) is unconditional and present on every evaluation.

### Recommendation
`check_parent_tenure_choice` should not derive the "more than one block already produced" decision solely from this signer's local `GloballyAccepted` rows. It should instead consult the node's authoritative `tenure.nakamoto_blocks` (already returned by `get_tenure_forking_info`) to determine the true number of blocks recorded for the tenure, and should evaluate proposal timing against the *last* block in the tenure (or all blocks), not only the first approved one, before permitting a reorg.

### Proof of Concept
Rust test plan (in `stacks-signer/src/chainstate/tests/v2.rs`, alongside `refused_reorg_supersedes_nothing`):
1. Build `cur_sortition` whose `parent_tenure_id` differs from `prior_sortition` (a reorg), mirroring `setup_test_environment`.
2. Pre-load `SignerDb` for tenure `T` with two blocks:
   - Block `A` at height `h`, `mark_globally_accepted()`.
   - Block `B` at height `h+1`, `mark_locally_accepted(false)` only (never promoted to `GloballyAccepted`).
3. Mock the node's `get_tenure_forking_info` response for `T` with `first_block_mined = Some(A_id)` and `nakamoto_blocks` containing **both** `A` and `B` (simulating that the node/network has already finalized both).
4. Assert `signer_db.get_globally_accepted_block_count_in_tenure(&T) == 1` (confirms the undercount).
5. Call `cur_sortition.data.check_parent_tenure_choice(&mut signer_db, &client, &Duration::from_secs(30))` and assert it returns `Ok(true)` — demonstrating the reorg is wrongly permitted even though tenure `T` has two globally-finalized blocks per the node's own authoritative data.
6. Add a second assertion showing the desired behavior: the check should return `Ok(false)` when the true tenure block count (from `nakamoto_blocks`) exceeds 1, establishing the equality violated by the current implementation.

    /// Return the count of globally accepted blocks in a tenure (identified by its consensus hash)
    pub fn get_globally_accepted_block_count_in_tenure(
        &self,
        tenure: &ConsensusHash,
    ) -> Result<u64, DBError> {
        let query = "SELECT COALESCE((MAX(stacks_height) - MIN(stacks_height) + 1), 0) AS block_count FROM blocks WHERE consensus_hash = ?1 AND state = ?2";
        let args = params![tenure, &BlockState::GloballyAccepted.to_string()];
        let block_count_opt: Option<u64> = query_row(&self.db, query, args)?;
        match block_count_opt {
            Some(block_count) => Ok(block_count),
            None => Ok(0),
        }
    }
