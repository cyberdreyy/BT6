## Title
`staking_contract` distribution pool merges operator commission with staker principal withdrawal when `staker == operator`, redirecting the staker's own unlocked stake to the operator's beneficiary — (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract.move` keys its `distribution_pool` (a `pool_u64::Pool`) purely by account address, using the operator's address as the special "pay-to-beneficiary" marker. `create_staking_contract` never asserts `staker != operator`, so a self-operated validator can legitimately set up a contract where `staker_address == operator`. In that configuration, `unlock_stake` merges the staker's principal-withdrawal distribution and the operator's commission distribution into the exact same shareholder slot, and `distribute_internal` then unconditionally reroutes the *entire* merged balance to `beneficiary_for_operator(operator)` — sending the staker's own unlocked principal to the beneficiary instead of back to the staker. This mirrors the Aleo `unbond_public` bug class: two logically distinct roles (here, "staker recipient" vs "operator/commission recipient") collapse onto one address key, and downstream logic that assumes they're distinct silently misroutes funds.

### Finding Description
In `create_staking_contract_with_coins` there is no check preventing `staker == operator`: [1](#0-0) 

When `unlock_stake` is invoked, it first pays out commission by calling `request_commission_internal`, which calls `add_distribution(operator, staking_contract, operator, commission_amount)` — buying shares in `distribution_pool` for the shareholder key `operator`: [2](#0-1) 

It then records the staker's own withdrawal via `add_distribution(operator, staking_contract, staker_address, amount)`: [3](#0-2) 

`add_distribution` simply does `distribution_pool.buy_in(recipient, coins_amount)` keyed by address: [4](#0-3) 

If `staker_address == operator`, both calls buy shares into the **same** shareholder slot in the pool, since `pool_u64` has no concept of "role" — only address identity. When funds are eventually distributed, `distribute_internal` redeems the merged share balance for that single shareholder and, because the shareholder address equals `operator`, unconditionally substitutes the recipient with `beneficiary_for_operator(operator)`: [5](#0-4) 

The beneficiary mechanism is designed only to redirect *commission* payouts, as documented in `set_beneficiary_for_operator`: [6](#0-5) 

But because the staker-withdrawal distribution and the commission distribution share the identical address key when `staker == operator`, the beneficiary redirect silently captures the staker's own principal along with the commission — there is no conditional distinguishing "this share came from a staker withdrawal" vs. "this share came from operator commission," exactly the same class of error as the Aleo bug where a shared address collapsed two distinct intents (`force unbond` vs `partial unbond`) into one logic branch.

### Impact Explanation
A self-operated validator (staker address == operator address — a fully supported, unrestricted configuration) who later calls `set_beneficiary_for_operator` to route commission to a separate wallet (e.g., an exchange or cold-storage address, a documented and intended feature) will have **all subsequent `unlock_stake` principal withdrawals** silently redirected to that beneficiary address instead of returned to themselves. This is a share-accounting corruption that credits the wrong account and can permanently strand the staker's own principal at an address they may not control equally (the beneficiary is intended only to receive commission, not principal). This satisfies the "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account or traps value" impact category.

### Likelihood Explanation
No code path prevents `staker == operator`, and self-staking/self-operating (an operator running their own validator without a separate staking-contract owner) plus later setting a distinct beneficiary (e.g. for tax/custody separation) is a plausible real-world operational pattern that is nowhere warned against in code or docs. Any user hitting this combination triggers the bug deterministically on the very next `unlock_stake` + `distribute` cycle.

### Recommendation
In `distribute_internal`, distinguish the staker-withdrawal distribution from the operator-commission distribution by using a role-specific sentinel key (analogous to delegation_pool's `NULL_SHAREHOLDER`) instead of relying purely on address equality with `operator`, or explicitly assert `staker != operator` in `create_staking_contract_with_coins` to eliminate the address collision, or track distributions with a `(recipient, is_commission)` tagged structure rather than a flat address-keyed `pool_u64::Pool`.

### Proof of Concept
1. `staker` (address `S`) calls `create_staking_contract(staker=S, operator=S, voter=V, amount, commission_percentage=10, seed)` — self-operated validator; no assertion blocks `operator == staker`.
2. `S` calls `staking_contract::set_beneficiary_for_operator(S, beneficiary=B)` where `B != S` (e.g., a custody wallet meant only to receive commission).
3. Validator earns rewards; `S` calls `unlock_stake(S, operator=S, amount=X)`:
   - `request_commission_internal` buys shares for shareholder `S` (=operator) worth `commission_amount`.
   - `add_distribution(operator=S, ..., recipient=staker_address=S, amount=X)` buys **more** shares for the same shareholder `S`, merging `X` (staker principal) with `commission_amount`.
4. After lockup expiry, anyone calls `distribute(S, S)`. In `distribute_internal`, the single shareholder `S` is redeemed for `commission_amount + X`; since `recipient == operator (S)`, it is rerouted to `beneficiary_for_operator(S) = B`.
5. Result: `B` receives `commission_amount + X`, while `S` (the actual staker who called `unlock_stake` to reclaim `X` of their own principal) receives nothing — their unlocked principal was misdirected to the beneficiary.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

        let pool_address = staking_contract.pool_address;
        emit(
            RequestCommission {
                operator,
                pool_address,
                accumulated_rewards,
                commission_amount
            }
        );

        commission_amount
    }

    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }

    /// Add a new distribution for `recipient` and `amount` to the staking contract's distributions list.
    fun add_distribution(
        operator: address,
        staking_contract: &mut StakingContract,
        recipient: address,
        coins_amount: u64,
    ) {
        let distribution_pool = &mut staking_contract.distribution_pool;
        let (_, _, _, total_distribution_amount) =
            stake::get_stake(staking_contract.pool_address);
        update_distribution_pool(
            distribution_pool,
            total_distribution_amount,
            operator,
            staking_contract.commission_percentage
        );

        distribution_pool.buy_in(recipient, coins_amount);
        let pool_address = staking_contract.pool_address;
        emit(AddDistribution { operator, pool_address, amount: coins_amount });
    }
