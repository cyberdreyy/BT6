### Title
Post-default `requestWithdraw` mints new receipts against the fixed `defaultRecoveryReserve`, letting late requesters drain recovery owed to defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The analog to "extending an expired lock to gain the same benefit as an honest long-term locker" is the post-finalization `requestWithdraw` path in `IdleCreditVault`. Once `finalizeDefaultRecovery` crystallizes a fixed `defaultRecoveryReserve` and `defaultRecoveryPrice` sized only against the default-epoch `totalBasis` (active + pending claims), any KYC-passing tranche holder can still open a new `postDefaultRequests` receipt that is minted 1:1 and later paid out of that same never-replenished reserve. The adversary "extends" a finalized default epoch into fresh claims, receiving recovery funds that were allocated exclusively to users whose claims existed at finalization.

### Finding Description
In `requestWithdraw`, when `defaultRecoveryFinalized` is true the function burns the CDO's strategy tokens, mints `_amount` receipt tokens to `_user`, records `postDefaultRequests[_user] = _amount`, and returns — without ever increasing `defaultRecoveryReserve` or adding the new basis to `totalBasis` [1](#0-0) .

The reserve, however, was sized exactly once in `finalizeDefaultRecovery`: `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve`, `recoveryPrice = reserveAmount / totalBasis`, where `totalBasis` counts only pre-finalization active and pending claims [2](#0-1) . `defaultPendingClaimBasis()` likewise only aggregates `pendingWithdraws` and the default-epoch instant claims known at that moment [3](#0-2) .

`claimWithdrawRequest` then routes post-default receipts through `_claimPostDefaultWithdrawRequest`, which the code comments describe as "already priced after the haircut and backed by the reserve" [4](#0-3)  — but nothing ever backs them. The "extend expired lock" parallel is exact: an entitlement window (the default epoch, already closed and priced) is reopened by `postDefaultRequests` so the latecomer draws on the same payout pool as honest default-epoch claimants, while retaining full optionality about when to exercise it. The only preconditions are holding a nonzero claimable balance and having no open request (`_hasWithdrawRequest`, `instantWithdrawsRequests`, `postDefaultRequests` all zero), which an attacker satisfies trivially by claiming or simply never requesting before the default.

### Impact Explanation
Direct theft / insolvency of the recovery reserve. Every post-finalization request is paid from `defaultRecoveryReserve` at the finalized price even though that reserve's `recoveryPrice` was computed as `reserveAmount / totalBasis` with no slack for future claims. If the recovery price is `p` and the attacker requests amount `A`, they extract `A * p` (or `A` at par in the post-default path) of underlying that pro-rata belongs to defaulted-epoch claimants; once the reserve is exhausted, honest users calling `claimWithdrawRequest`/`_claimDefaultedWithdrawRequest` receive nothing — permanent loss equal to the drained amount, capped only by the attacker's tranche position. Unlike the source bug (mere voting-power inflation), here the dilution maps directly to underlying tokens.

### Likelihood Explanation
- Requirements are minimal: the attacker needs any tranche position redeemable via `requestWithdraw` (KYC'd lender or secondary-market buyer of tranche tokens) and the sequence is a single `cdoEpoch.requestWithdraw` + `claimWithdrawRequest`.
- Timing is favorable to the attacker: defaulted pools can sit unfinalized-claim-pending for extended periods, and nothing in `requestWithdraw` blocks post-finalization requests — the code deliberately preserves "request/claim UX after default" [5](#0-4) .
- All existing guards are bypassed by construction: the default-epoch receipt checks only block *re-requesting while a request is open*, the loss-adjusted guard checks `lossRecoveryPriceByEpoch[lastWithdrawRequest]` (zero post-default since requests route to `postDefaultRequests`), and no solvency check compares the growing `postDefaultRequests` aggregate against the immutable `defaultRecoveryReserve`.
- Uncertainty: this assumes `_claimPostDefaultWithdrawRequest`/`_transferDefaultRecovery` decrement `defaultRecoveryReserve` (the comments at lines 105 and 304-306 state post-default requests are "backed by default recovery reserve"); the function bodies were not fully inspected due to index limits. If the payout were sourced elsewhere, the finding collapses.

### Recommendation
```diff
 function requestWithdraw(uint256 _amount, address _user, uint256 _principal) external {
     _onlyIdleCDO();
     _ensureDefaultRecoveryInitialized();
     if (_amount == 0) return;
     if (defaultRecoveryFinalized) {
         if (_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0) {
             revert NotAllowed();
         }
         _burn(msg.sender, _amount);
         _mint(_user, _amount);
         postDefaultRequests[_user] = _amount;
+        // Either fund the new receipt basis explicitly ...
+        defaultRecoveryReserve += _amount; // only if the CDO simultaneously transfers _amount here
+        // ... or revert and force post-default exits through the ordinary recovery claim path
         return;
     }
```
Alternatively (safer), revert on post-finalization `requestWithdraw` and require users to redeem through the finalized recovery claim only, since the reserve can never be honestly enlarged without an accompanying underlying transfer into the strategy. An invariant test should assert `sum(postDefaultRequests) <= defaultRecoveryReserve - sum(defaulted-claim basis * recoveryPrice)`.

### Proof of Concept
Foundry fork test (extend `test/foundry/IdleCreditVault.t.sol` patterns; assumes AA deposit + epoch + borrower default + `finalizeDefaultRecovery`):

```solidity
function testPostDefaultRequestDrainsRecoveryReserve() external {
    uint256 amount = 10_000 * ONE_SCALE;
    // honest user + attacker deposit
    _depositWithUser(honest, amount, true);
    _depositWithUser(attacker, amount, true);
    _startEpochAndCheckPrices(0);

    // honest user requests withdraw during the defaulting epoch (not yet funded)
    vm.prank(honest);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // borrower defaults; owner/manager finalize recovery with partial funds
    _stopEpochDefaulting();                       // defaulted = true
    uint256 recovered = strategy.defaultPendingClaimBasis() / 2; // 50% recovery
    deal(defaultUnderlying, recoverySource, recovered);
    vm.prank(recoverySource);
    underlying.approve(address(strategy), recovered);
    vm.prank(manager);
    cdoEpoch.finalizeDefault(recovered, recoverySource); // sets reserve/price/finalized

    uint256 reserveBefore = strategy.defaultRecoveryReserve();
    uint256 price = strategy.defaultRecoveryPrice();

    // attacker "extends" the finalized epoch: opens a brand-new post-default request
    vm.startPrank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    cdoEpoch.claimWithdrawRequest();
    vm.stopPrank();

    // attacker was paid from the fixed reserve although he was never in totalBasis
    uint256 attackerPaid = underlying.balanceOf(attacker);
    assertGt(attackerPaid, 0, "post-default request paid from reserve");

    // reserve shrank below what honest defaulted claims are owed -> honest claim insolvent
    uint256 honestBasis = strategy.withdrawsRequests(honest);
    uint256 reserveAfter = strategy.defaultRecoveryReserve();
    assertLt(reserveAfter, (honestBasis * price) / 1e18, "reserve can no longer cover honest claim");

    vm.prank(honest);
    cdoEpoch.claimWithdrawRequest(); // reverts on transfer or pays less than basis*price
    assertLt(underlying.balanceOf(honest), (honestBasis * price) / 1e18, "honest claimant shortchanged");
}
```

Expected result: `attackerPaid > 0` while `reserveAfter` falls short of the honest defaulted claim, reproducing the expired-entitlement-extension theft with unprivileged transactions only (no owner/manager/borrower misbehavior — finalization is a legitimate flow).
