The pipeline `SvmTokenInfo::unpack_token_account` → `svm_token_info_to_token_balance` → `token_amount_to_ui_amount_v3` already handles the full `u8` range (0–255) for `decimals` and `u64` range for `amount` without panicking, and produces a faithful decimal rendering.

Key points from the code:

- `SvmTokenInfo::unpack_token_account` simply copies `decimals` and `amount` verbatim from the unpacked mint/account bytes into the struct; no arithmetic is performed here that could overflow or panic. [1](#0-0) 

- `token_amount_to_ui_amount_v3` (the non-interest/non-scaled path) computes `ui_amount` via `10_usize.checked_pow(decimals as u32)`, which returns `None` rather than panicking when `decimals` is large enough to overflow `usize` (e.g., 255), so `ui_amount` becomes `None` instead of producing garbage or crashing. [2](#0-1) 

- `ui_amount_string` is computed by `real_number_string_trimmed` → `real_number_string`, which casts `decimals` to `usize` before doing arithmetic (`decimals + 1`), so there is no `u8` overflow, and the string is built with `format!("{:01$}", amount, decimals + 1)` plus a decimal point insertion — this is a faithful left-padded decimal rendering regardless of how large `decimals` is. [3](#0-2) 

- This exact boundary behavior (decimals=20, decimals=25, amount up to `u64::MAX` with `decimals=0`) is already covered by existing unit tests, which assert both that no panic occurs and that `ui_amount_string` matches `real_number_string_trimmed`, with `ui_amount` correctly becoming `None` when it would overflow `f64`/`usize` representation. [4](#0-3) 

- The reported `decimals` and `amount` fields in the final `UiTokenAmount` are always the raw, unmodified values passed in — `decimals` is copied directly and `amount` is `amount.to_string()` — so there is no possibility of misreporting these fields independent of `ui_amount`/`ui_amount_string` computation. [5](#0-4) 

Since decoding arbitrary attacker-controlled `decimals` (0–255) and `amount` (0–u64::MAX) values through this exact pipeline does not panic and does not produce a `ui_amount_string` that is inconsistent with the raw `amount`/`decimals` pair (only `ui_amount` degrades gracefully to `None` when it cannot be represented as `f64`), the described invariant violation does not exist in this codebase.

pub fn real_number_string(amount: u64, decimals: u8) -> String {
    let decimals = decimals as usize;
    if decimals > 0 {
        // Left-pad zeros to decimals + 1, so we at least have an integer zero
        let mut s = format!("{:01$}", amount, decimals + 1);
        // Add the decimal point (Sorry, "," locales!)
        s.insert(s.len() - decimals, '.');
        s
    } else {
        amount.to_string()
    }
}
