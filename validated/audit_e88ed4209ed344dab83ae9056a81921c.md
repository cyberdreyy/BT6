### Title
Unfunded instant-withdraw receipts from a prior epoch escape default accounting and are frozen or paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug class is an out-of-bounds write keyed by an index the attacker influences: instant-withdraw receipts are bucketed per epoch (`instantWithdrawsRequestsByEpoch[user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`), but all default-recovery logic only ever reads the *current* `epochNumber` slot. A receipt minted in epoch N that remains unfunded when a default is finalized in epoch N+1 falls out of every recovery-basis/clearance index, while it still sits in the aggregate `instantWithdrawsRequests[user]` that `claimInstantWithdrawRequest` pays at par.

### Finding Description
`requestInstantWithdraw` records receipts under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`, and adds the amount to both `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` [1](#0-0) . `pendingInstantWithdraws` only decreases when the CDO calls `collectInstantWithdrawFunds`, so if the borrower never funds the instant queue, the receipt stays pending across the `epochNumber += 1` bump in `deposit` [2](#0-1) .

On default finalization, `defaultPendingClaimBasis` adds instant claims only for `instantWithdrawClaimsByEpoch[epochNumber]` — the slot of the *finalization* epoch [3](#0-2) . Likewise `_defaultPrefundedInstantReserve` reserves only `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` [4](#0-3) , and `_claimDefaultedInstantWithdrawRequest` clears and haircuts only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` [5](#0-4) .

After finalization, `claimInstantWithdrawRequest` still pays the full aggregate `instantWithdrawsRequests[_user]` — which includes the stale-epoch receipt — at par through `_transferFundedClaim` [6](#0-5) . The stale slot was never written into the recovery basis ("out of bounds" relative to the finalize-time index), never haircut, and never decremented from `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` on the defaulted path.

### Impact Explanation
Two symmetric breaks of the "one receipt, recovery-priced payout" invariant:

- If `_transferFundedClaim` finds non-reserve balance (e.g., yield, prefunded leftovers, or reserve shortfall accounting), the stale receipt is paid **at par while every same-vintage claimant is haircut** — direct theft of recovery value from defaulted-epoch claimants and active LPs, since the basis used to price `defaultRecoveryPrice` excluded this claim.
- If all strategy balance is tracked as `defaultRecoveryReserve` (the normal post-finalization state), `_transferFundedClaim` refuses to spend the reserve and the claim reverts: the user's legitimately funded/owed receipt is **permanently frozen**, because no path ever clears `instantWithdrawsRequests[_user]` for the old epoch — `_claimDefaultedInstantWithdrawRequest` only touches `defaultRecoveryEpoch`, and `requestInstantWithdraw` has no guard forcing old receipts to be claimed first.

Either outcome is a permanent loss/freeze of user funds proportional to the stale instant receipt amount.

### Likelihood Explanation
Requires: (1) an instant-withdraw request that stays unfunded (`pendingInstantWithdraws > 0`) past an epoch boundary — possible whenever the borrower's returned liquidity doesn't cover the instant queue before `stopEpoch`/`startEpoch` rolls `epochNumber`; (2) a later borrower default finalized via `finalizeDefaultRecovery` with `pendingInstantWithdraws != 0` so `defaultInstantWithdrawsFinalized` is set. The attacker is just an ordinary tranche holder who requested an instant withdraw early; sequencing is around honest manager/borrower calls. Likelihood is moderate: it needs a default plus a straddling unfunded instant receipt, but no privileged misbehavior.

### Recommendation
In `defaultPendingClaimBasis`, `finalizeDefaultRecovery`, and `_claimDefaultedInstantWithdrawRequest`, account for instant receipts from *all* epochs, not just `instantWithdrawClaimsByEpoch[epochNumber]`/`defaultRecoveryEpoch` — e.g., track a global outstanding instant claim basis, or iterate/clear `instantWithdrawsRequestsByEpoch` for every epoch slot with a nonzero entry for the user. Alternatively, add a guard in `requestInstantWithdraw`/`requestWithdraw` that forces settlement or blocks new requests while an unfunded instant receipt exists, mirroring the `lastWithdrawRequest`/`lossRecoveryPriceByEpoch` guard in `requestWithdraw` [7](#0-6) .

    uint256 amt = 100_000 * ONE_SCALE;
    uint256 tr = idleCDO.depositAA(amt);
    vm.prank(manager); cdoEpoch.startEpoch();

    // 2. APR drops -> requestWithdraw takes instant path; strategy mints
    //    instant receipt in epoch N (instantWithdrawsRequestsByEpoch[user][N],
    //    instantWithdrawClaimsByEpoch[N], pendingInstantWithdraws += amt).
    //    Borrower never funds the instant queue (no collectInstantWithdrawFunds).
    //    warp past instantDelay not needed: receipt stays pending.
    cdoEpoch.requestWithdraw(tr, address(AAtranche));

    // 3. Epoch rolls: stopEpoch + startEpoch -> deposit() bumps epochNumber to N+1
    //    while pendingInstantWithdraws is still > 0.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager); cdoEpoch.stopEpoch(0, 0);
    vm.prank(manager); cdoEpoch.startEpoch();

    // 4. Borrower defaults; owner/manager finalizes recovery.
    //    defaultPendingClaimBasis() counts pendingWithdraws +
    //    instantWithdrawClaimsByEpoch[N+1] -- attacker's epoch-N instant receipt
    //    is excluded from `basis`, so defaultRecoveryReserve/defaultRecoveryPrice
    //    ignore it; _claimDefaultedInstantWithdrawRequest clears only slot N+1.
    //    ... _handleBorrowerDefault / finalizeDefaultRecovery flow ...

    // 5. Attacker claims. instantWithdrawsRequests[user] still holds the
    //    epoch-N amount and is paid at par via _transferFundedClaim, or the
    //    call reverts if all balance is reserve -> frozen funds.
    cdoEpoch.claimInstantWithdrawRequest(); // path after defaultRecoveryFinalized
}

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
