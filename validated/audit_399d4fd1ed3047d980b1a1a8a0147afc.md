### Title
Zero-balance `skip_deduct` path in `promise_batch_action_function_call_weight` mints unbacked 1-yoctoNEAR deposits, enabling token inflation and bypassing `assert_one_yocto`-style authorization checks - (File: `runtime/near-vm-runner/src/logic/logic.rs`)

### Summary
`promise_batch_action_function_call_weight` contains a `skip_deduct` branch that, when `amount == 1`, `config.one_yocto_on_promise` is enabled, and the caller's tracked `current_account_balance` is zero, forwards a real `deposit = 1` `FunctionCall` action to an outgoing receipt while only bumping `result_state.subsidized_amount` instead of calling `deduct_balance`. No compensating debit occurs anywhere else in the code path, so the 1 yoctoNEAR delivered to the receiver is created out of thin air, and it can be repeated arbitrarily (unbounded inflation) as well as satisfy any victim contract's `assert_one_yocto`-style authorization check without the caller ever possessing or paying that deposit.

### Finding Description
In `promise_batch_action_function_call_weight` [1](#0-0) , the balance handling is:

```
let skip_deduct = amount == Balance::from_yoctonear(1)
    && self.config.one_yocto_on_promise
    && self.result_state.current_account_balance.is_zero();
if skip_deduct {
    self.result_state.subsidized_amount = ...checked_add(amount)...;
} else {
    self.result_state.deduct_balance(amount)?;
}
self.ext.append_action_function_call_weight(receipt_idx, method_name, arguments, amount, gas, GasWeight(gas_weight))
```

The `amount` value (a real, unfaked `Balance::from_yoctonear(1)`) is unconditionally forwarded into `append_action_function_call_weight`, which becomes the `Action::FunctionCall.deposit` field of the outgoing receipt [2](#0-1) . When `skip_deduct` is taken, `deduct_balance` is never invoked, so the caller's balance is untouched — yet the receipt still instructs the runtime to transfer 1 yoctoNEAR of real value to the receiver upon receipt application (`account.set_amount(outcome.balance)` and later attaching deposit at receipt application). The only bookkeeping that occurs is `result.subsidized_amount = safe_add_balance(result.subsidized_amount, outcome.subsidized_amount)` in `action_function_call` [3](#0-2) , which is purely additive statistics/metadata and performs no debit against any account or the network's total supply.

The condition only checks the in-memory `current_account_balance` tracked for the duration of the current function-call execution — it is zero simply because the contract hasn't been funded yet within this call, not because the deposit was actually earned or paid. An attacker can:
1. Deploy a contract with `amount()==0`.
2. Call the host function `promise_batch_action_function_call_weight` with `amount=1` repeatedly (as many times as gas allows within one execution, and across unlimited subsequent blocks/transactions as long as `current_account_balance` remains zero for that call), each time targeting any receiver (including a victim FT/NEP-141-style contract that authorizes privileged branches via `assert_one_yocto`/deposit==1 checks).
3. Each resulting receipt carries `Action::FunctionCall { deposit: 1, .. }` exactly as required by the victim's authorization check, with no debit from the attacker's account.

This breaks the fundamental invariant that promise deposits must be backed by a real, deducted balance, which is the same invariant that lets victim contracts treat "attached deposit == 1" as proof the caller actually spent value (in the normal protocol, function-call access keys cannot attach non-zero deposits and are also unable to bypass this since deposits must be deducted from the calling account — the entire security value of `assert_one_yocto` patterns rests on deposits being real balance transfers). Here that guarantee is broken by construction.

No existing check catches this: `deduct_balance` is simply skipped, there's no reconciliation of `subsidized_amount` against total supply, storage staking, or account balances elsewhere in `runtime/runtime/src/lib.rs`. The comment in the code ("Allow attaching exactly 1 yoctoNEAR ... without needing to be seeded with balance first") documents the flawed intent directly.

### Impact Explanation
This is unconditional token inflation: any zero-balance contract can synthesize real, spendable 1-yoctoNEAR deposits in outgoing receipts with no corresponding debit, and can do so as many times as gas budget and repeated transactions allow, with no upper bound over time. This maps to the "Token inflation or loss" NEAR bounty category, and secondarily to "authorization escalation" since it fabricates the exact deposit==1 signal that many production contracts (NEP-141 `ft_transfer_call`/`storage_unregister`-style `assert_one_yocto` patterns) rely on as an authorization gate, letting an attacker trigger privileged branches on a victim contract without ever paying the required deposit.

### Likelihood Explanation
Fully attacker-reachable with no privileged access: the attacker only needs to deploy an ordinary wasm contract and call it via a normal signed transaction. `config.one_yocto_on_promise` needs to be enabled in the active `RuntimeConfig` for this branch to be reachable — this is a per-protocol-version parameter and not attacker-controlled, so whether this is exploitable on a live network depends on whether that flag is turned on in the deployed runtime config; if it is enabled, the exploit is trivial, free (costs only normal gas), and fully repeatable.

### Recommendation
Remove or gate the `skip_deduct` bypass so that `deduct_balance` is always called for any non-zero `FunctionCall` deposit, regardless of the caller's currently-tracked balance; if a legitimate "zero balance account" subsidy feature is desired, it must be backed by an explicit, bounded, and correctly-accounted subsidy pool (e.g., debited from protocol treasury/total-supply bookkeeping) rather than silently skipping the debit while still emitting a real deposit in the outgoing receipt.

### Proof of Concept
Unit test in `runtime/near-vm-runner/src/logic/tests/promises.rs` (or an integration test in `runtime/runtime/src/tests/apply.rs`):
1. Configure `VMConfig` with `one_yocto_on_promise = true`.
2. Set up a `VMLogic` context where `current_account_balance = 0`.
3. Create a promise and call `promise_batch_action_function_call_weight` with `amount = 1`.
4. Assert: `result_state.subsidized_amount == 1`, and `result_state.current_account_balance` remains `0` (no deduction occurred).
5. Inspect the appended action via the receipt/ext mock and assert `Action::FunctionCall.deposit == 1` exactly, confirming the outgoing receipt carries a real, unbacked 1-yoctoNEAR deposit.
6. End-to-end: apply the resulting receipt against a mock/victim contract account and assert its balance increases by 1 yoctoNEAR while no other account's balance decreased — demonstrating net supply inflation.
