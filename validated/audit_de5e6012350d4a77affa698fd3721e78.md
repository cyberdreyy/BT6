### Title
Carried `unclaimedFees` are permanently locked after a close-pool `stopEpoch` — ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
The external report describes fees credited to an accounting counter (`getCollectedFees`) that is never transferred out, permanently locking their backing. The direct analog exists in `IdleCDOEpochVariant.stopEpochWithDuration`: accrued management/performance fees that exceed gross epoch interest remain in `unclaimedFees` and continue reducing NAV, and once the pool is closed (`_isRequestingAllFunds`, `epochDuration = 0`, `epochEndDate = 0`) there is no code path that ever transfers or mints them out, even though `stopEpoch` recalls the full gross principal that backs them. The fee value is frozen in the contract forever.

### Finding Description
`unclaimedFees` is incremented in two places in `IdleCDOCreditVault`:

- `_updateAccounting()` adds the performance fee on gains: `unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC` (contracts/IdleCDOCreditVault.sol:230-232).
- `_accrueManagementFee()` adds the time-based management fee: `unclaimedFees += _calculateManagementFee(...)` (contracts/IdleCDOCreditVault.sol:552-555).

The accrued fees are excluded from NAV via `getContractValue()` subtracting `unclaimedFees` (line 125-128), so their token backing is explicitly reserved inside the contract.

The only payout path is inside `stopEpochWithDuration` (contracts/IdleCDOEpochVariant.sol:438-459):

```solidity
uint256 _fees = unclaimedFees;
if (_mintInterest) {
    // mint AA shares for feeReceiver/owner
} else {
    uint256 _availableForFees = _grossInterest > _pendingWithdrawFees ? _grossInterest - _pendingWithdrawFees : 0;
    if (_fees > _availableForFees) {
        _fees = _availableForFees;
    }
    _transferFeeUnderlyings(_fees);
}
// Any fee that cannot be paid in cash remains accrued and continues reducing NAV.
unclaimedFees -= _fees;
```

When `_grossInterest` is small (or zero, as in a close-pool stop where `_isRequestingAllFunds` requests principal-only repayment, `_interest == 1`), `_availableForFees` caps the payout at the gross interest, and the remainder stays accrued. The test `testClosePoolRecallsGrossPrincipalBackingCarriedFees` confirms the borrower is then made to repay `grossPrincipal = getContractValue() + carriedFee`, i.e. the underlyings backing the unpaid fees are pulled into the contract. On that same call the close-pool branch sets `epochDuration = 0` and `epochEndDate = 0` (lines 488-493): the pool is permanently closed, no further `startEpoch`/`stopEpoch` cycle can occur, and no other function in `IdleCDOCreditVault` or the epoch variant ever decrements or pays out `unclaimedFees`. There is no `harvest`/`_depositFees`/`collectFees` equivalent in the credit-vault code — those exist only in legacy `IdleCDO` (`_depositFees`, contracts/IdleCDO.sol:460-470), which credit vaults intentionally do not inherit.

### Impact Explanation
Permanent freezing / leak of value identical in class to the Gondi finding. Fee underlyings are (a) deducted from user NAV via `getContractValue() - unclaimedFees`, and (b) physically present in the contract (recalled gross principal or residual interest), yet no function can move them to `feeReceiver`/`owner()` or to users. The locked amount equals the carried `unclaimedFees` balance at close, which can be arbitrarily large: a high `managementFee` over a long epoch accrues fees well beyond a single epoch's gross interest (see `testStopEpochCarriesManagementFeesAboveGrossInterest`, where `carriedFee = accruedManagementFee - lowGrossInterest` is left accrued). Tranche holders cannot recover it either, because claims/withdrawals are priced off NAV that excludes it. No guard (skim, default revert, epoch gating) rescues the funds — the value is simply stranded.

### Likelihood Explanation
Requires a configuration where accrued fees exceed one epoch's gross interest — a realistic state, exercised by the protocol's own tests (`testStopEpochCarriesManagementFeesAboveGrossInterest`, `testClosePoolRecallsGrossPrincipalBackingCarriedFees`), followed by the manager closing the pool (`stopEpoch(..., 1)`). Pool closure is a normal, expected end-of-life operation. No privileged misbehavior is needed; the honest `manager`/`owner` calls trigger the lock deterministically.

### Recommendation
Add a `collectFees` method (or pay out the full `unclaimedFees` balance inside the close-pool branch of `stopEpochWithDuration`, where the contract already holds the recalled principal covering it). At minimum, on `_isRequestingAllFunds`, compute `_availableForFees` against `unclaimedFees`-backed cash actually held (`_contractTokenBalance(token)` / strategy-token redemption) rather than only `_grossInterest - _pendingWithdrawFees`, then `unclaimedFees = 0`.

### Proof of Concept
Foundry-style test following the conventions in `test/foundry/IdleCreditVault.t.sol`:

```solidity
function testCarriedFeesLockedAfterClose() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 managementFeeRate = 2_000;      // 2%/yr
    uint256 lowGrossInterest = 100 * ONE_SCALE;

    idleCDO.depositAA(amount);
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, managementFeeRate);

    vm.startPrank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    IdleCreditVault(address(strategy)).setApr(initialProvidedApr);
    cdoEpoch.startEpoch();
    vm.stopPrank();

    // epoch 1: gross interest far below accrued management fee
    deal(defaultUnderlying, borrower, lowGrossInterest);
    vm.warp(cdoEpoch.epochEndDate());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, lowGrossInterest);

    uint256 carriedFee = cdoEpoch.unclaimedFees();
    assertGt(carriedFee, 0);

    // epoch 2 opened then closed via _isRequestingAllFunds; borrower repays
    // gross principal which includes the token backing of carriedFee
    _setManagementFee(0);
    vm.prank(manager);
    cdoEpoch.startEpoch();
    uint256 grossPrincipal = strategyToken.balanceOf(address(cdoEpoch));
    deal(defaultUnderlying, borrower, grossPrincipal);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 tlBalPre = underlying.balanceOf(TL_MULTISIG);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1); // close pool: epochEndDate = 0 forever

    // _availableForFees == 0 (no gross interest in close mode) => nothing paid
    assertEq(underlying.balanceOf(TL_MULTISIG) - tlBalPre, 0);
    assertEq(cdoEpoch.unclaimedFees(), carriedFee);        // still accrued
    assertEq(cdoEpoch.epochEndDate(), 0);                  // pool closed, no future stop
    // carriedFee underlyings sit in the contract with no sweep/claim path
    assertGe(underlying.balanceOf(address(cdoEpoch))
             + strategyToken.balanceOf(address(cdoEpoch)),
             carriedFee);
}
```

Invariant broken: fee accounting reserves underlyings that can never be disbursed (`unclaimedFees` monotonically non-decreasing after pool close while its backing is held by the contract) — permanent freezing of collected fees, a leak of value.

Note: I verified this against `contracts/IdleCDOCreditVault.sol`, `contracts/IdleCDOEpochVariant.sol`, and the Foundry tests; I could not exhaustively check every periphery contract (e.g. a donation-skim helper) for an alternative fee-sweep path, so if such a sweeper exists and is callable post-close, the residual could instead be recovered by it — which would still leave the fees unpaid to their intended receivers.
