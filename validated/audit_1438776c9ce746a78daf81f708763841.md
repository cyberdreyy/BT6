### Title
Stale confirmations from removed multisig members can push a request past the confirmation threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`DeleteMember`/`DeleteKey` removes a member/key from the multisig but only deletes the *requests that member submitted*, leaving that member's confirmation entries intact on requests submitted by other members. `confirm()` counts confirmations purely by set size versus `num_confirmations`, without re-checking that every confirming principal is still a current member. This lets a request execute with fewer live-member confirmations than the configured threshold, effectively executing a multisig request below its true, current threshold.

### Finding Description
`execute_request`'s `DeleteMember` branch calls `delete_member` [1](#0-0) , which is: [2](#0-1) 

It only clears requests where `r.member == member` (i.e., requests the removed member *submitted*), and removes the member from `self.members`. It never scans `self.confirmations` for other requests where the removed member appears as a *confirmer*.

`confirm()` decides whether to execute purely from the size of the confirmations set: [3](#0-2) 

Because a removed member's stale confirmation remains counted, `confirmations.len() + 1 >= num_confirmations` can become true using confirmations from principals who are no longer members. The binding that should hold — *confirmations counted == confirmations from currently live members* — is broken: `count(confirmations recorded) ≠ count(confirmations from live members)`.

The identical pattern exists in the original `multisig/src/lib.rs` `DeleteKey` action [4](#0-3)  and `confirm()` [5](#0-4) .

### Impact Explanation
This crosses the authorisation/threshold boundary explicitly called out as Critical: "a multisig request executed below threshold." An attacker who is (or colludes with) a soon-to-be-removed member can pre-plant a confirmation on a malicious request (e.g., a `Transfer` or `FunctionCall` draining funds), have that member removed through a legitimate governance action, and later have the remaining confirmations complete the count using the stale, no-longer-authorized confirmation — resulting in execution of a transfer/action that never received the required number of confirmations from currently authorized members.

### Likelihood Explanation
Requires: (1) an attacker who is a multisig member (or a colluding member) to add and confirm a malicious request before being removed, and (2) the member removal to occur afterward without another party noticing/cleaning the stale confirmation, and (3) enough additional confirmations from remaining members to reach `num_confirmations` counting the stale one. This requires multi-party coordination but no privileged foundation/redeploy access — a legitimate, if compromised or malicious, existing multisig member can set this up entirely through normal `add_request`/`confirm`/`DeleteMember` calls.

### Recommendation
When removing a member (`DeleteMember`/`DeleteKey`), scan all outstanding `confirmations` sets (not just requests submitted by that member) and remove the removed member's entry from each. Alternatively, at `confirm()`-time, re-validate that every principal in the stored confirmations set is still `self.members.contains(...)` before counting it toward `num_confirmations`, discarding stale confirmations from removed members.

### Proof of Concept
1. Multisig has 3 members `{A, B, C}`, `num_confirmations = 2`.
2. `A` calls `add_request` for a malicious `Transfer` to attacker-controlled account (not confirmed yet).
3. `B` calls `confirm(request_id)` → `confirmations = {B}` (1 < 2, not executed).
4. Separately, `A` and `C` confirm a `DeleteMember{B}` request (reaching threshold 2), which executes `delete_member(B)`. Since `B` did not submit the Transfer request, its confirmations set `{B}` is untouched; `B` is removed from `self.members`.
5. `C` calls `confirm(request_id)` on the Transfer request → `confirmations.len() (1) + 1 = 2 >= num_confirmations (2)` → `execute_request` runs, transferring funds, even though only `C` is currently a live authorized member confirming (plus the stale, now-invalid confirmation from removed member `B`).
