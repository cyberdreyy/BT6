## Finding: Stale Confirmations From Removed Keys Are Not Purged, Allowing Requests To Execute Below The True Live-Signer Threshold

### Title
Multisig request execution counts confirmations from deleted keys, letting a request execute below the real threshold of live signers - (File: `multisig/src/lib.rs`)

### Summary
The `MultiSigContract::confirm` function checks `confirmations.len() + 1 >= self.num_confirmations` to decide whether a pending request has reached the required threshold, but `DeleteKey` only purges *requests created by* the removed public key, not that key's confirmations recorded on *other* still-pending requests. As a result, a confirmation from a key that has since been removed remains counted toward the threshold, letting a request execute even though fewer currently-valid keys actually approved it than `num_confirmations` requires.

### Finding Description
The equality the contract is supposed to preserve is:

`confirmations.len() >= num_confirmations` ⇔ `(number of currently authorized keys that approved the request) >= num_confirmations`

The `confirm` method increments/checks a `HashSet<PublicKey>` per request: [1](#0-0) 

When a key is removed via the `DeleteKey` action, the contract only cleans up requests that were *created* by that key (`r.signer_pk == pk`), and clears `num_requests_pk` for that key. It never scans other requests' `confirmations` sets to strip out the removed key: [2](#0-1) 

The `MultiSigContract` struct stores `confirmations` and `requests` as independent maps, and nothing links a `PublicKey`'s removal to the `confirmations` collections of unrelated request IDs: [3](#0-2) 

Because of this, a confirmation cast by key `C` on request `X` remains permanently recorded in `self.confirmations[X]` even after `C` is deleted from the contract's access keys by a separate, properly-confirmed `DeleteKey` request. When enough *other* keys later confirm `X`, the stale entry from `C` is counted toward `num_confirmations`, and `execute_request` fires: [4](#0-3) 

The existing test for key deletion only verifies cleanup of requests created by the deleted key, not confirmations left by that key on other requests, so this gap is not covered: [5](#0-4) 

### Impact Explanation
This breaks the core custody guarantee of a k-of-n multisig: that `num_confirmations` *distinct, currently authorized* keys must approve an action (including `Transfer`, `FunctionCall`, `AddKey`, etc.) before it executes. If one confirming key is later revoked (e.g., because it was compromised, an employee left, or a key rotation occurred) before the request reaches quorum, its stale confirmation still counts. The request can then execute with only `num_confirmations - 1` (or fewer) live, currently-authorized signers actually agreeing on it — a multisig request executed below its own configured threshold, matching the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
This does not require a malicious multisig member colluding maliciously in real time — it can happen from an entirely legitimate operational sequence: (1) a key confirms a pending request, (2) that key is later removed for unrelated reasons (rotation, compromise response, offboarding) via a normal `DeleteKey` request, (3) subsequent honest confirmers, unaware the count includes a now-invalid key, push the request over threshold. Any multisig contract that rotates or revokes keys while requests are pending is exposed. No special privilege beyond normal request/confirm/delete-key usage (already part of the contract's intended workflow) is needed to trigger the unintended state.

### Recommendation
When executing a `DeleteKey` action, iterate over all entries in `self.confirmations` (not just requests created by the removed key) and remove the deleted public key from each request's confirmation set. Alternatively, when counting confirmations in `confirm`, filter the stored `HashSet<PublicKey>` against the current set of contract access keys before comparing against `num_confirmations`, so revoked keys can never contribute to a quorum.

### Proof of Concept
1. Deploy `MultiSigContract::new(3)` with keys `A, B, C, D` as full-access keys.
2. Key `A` calls `add_request` for a malicious `Transfer` (request `X`).
3. Key `B` calls `confirm(X)` → `confirmations[X] = {B}` (len 1 < 3, stored).
4. Key `C` calls `confirm(X)` → `confirmations[X] = {B, C}` (len 2 < 3, stored) — see `confirm` logic at [6](#0-5) .
5. Separately, the organization submits and confirms (3-of-4, using `A, D`, and one more key) a `DeleteKey { public_key: C }` request to revoke `C` (e.g. `C` was compromised). `execute_request` removes only requests created by `C`; `confirmations[X]` still contains `C` — see [2](#0-1) .
6. Key `D` calls `confirm(X)` → `confirmations[X].len() + 1 == 3 >= num_confirmations(3)`, so `execute_request` fires the `Transfer`, even though `C`'s approval is no longer valid — only `B` and `D` are truly live signers who approved `X` alongside the now-revoked `C`, one short of the intended 3 live confirmations.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
