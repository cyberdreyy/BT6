### Title
Replay-guard digest is consumed before owner-binding validation, allowing pre-emptive DOS of another user's Vault request - (File: `core/capabilities/vault/authorizer.go`)

### Summary
`AuthorizeRequest` in the node's Vault authorization pipeline records a request's replay-guard digest *before* it validates that the request's declared secret owner matches the authorized caller. An attacker who can get their own (different-owner) request past the authentication step (allowlist or JWT) can pre-consume the digest of an identical request that a legitimate user is about to send, causing the legitimate user's subsequent, properly-authorized request to be rejected as a duplicate — exactly the "cheap frontrunning to burn a shared, order-dependent guard" pattern in the referenced `pay()` DOS report.

### Finding Description
`authorizer.AuthorizeRequest` performs the following steps in order: [1](#0-0) 

1. `authorizeRequest` — authenticates the caller via allowlist or JWT and returns an `AuthResult` containing a `digest` (derived from the request's content, e.g. method/id/params) and the caller's `AuthorizedOwner()`.
2. `a.replayGuard.CheckAndRecord(authResult.Digest(), ...)` — **immediately marks the digest as seen**, regardless of whether the request will ultimately be accepted.
3. Only *after* that, `validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner())` checks that the owner embedded in the request params (e.g. `ListSecretIdentifiersRequest.Owner`, `EncryptedSecret.Id.Owner`) actually matches the authenticated caller's owner.

The owner-binding check exists specifically to prevent an authenticated-but-wrong-owner caller from acting on someone else's secrets: [2](#0-1) 

Because step 2 happens before step 3, an attacker who is a legitimately-authenticated (but unrelated) Vault caller can:
1. Construct a JSON-RPC request whose `method`, `id`, and `params` (including the victim's `owner` field) are byte-for-byte identical to a request the victim is expected to send (e.g. a `vault.secrets.list` or `vault.secrets.create` call with a predictable/observed ID and target owner).
2. Submit it using their *own* valid authentication (their own JWT or allowlist credentials), which will pass the authentication step and return an `AuthResult` for the attacker's own owner, but with a `digest` computed over the (attacker-supplied) request content that matches the victim's future identical request.
3. The replay guard is populated with that digest via `CheckAndRecord` before the owner mismatch is caught in step 3.
4. The attacker's own call is then correctly rejected by `validateSecretOwnersMatchAuthorized` (owner mismatch) — but the digest is already burned.
5. When the victim later sends their legitimate, correctly-owned, correctly-authorized request with the same digest, `CheckAndRecord` returns `ErrRequestAlreadySeen`, and the victim's request is rejected as a replay even though they never actually sent it before.

The replay guard itself has no way to distinguish "this digest was genuinely processed for owner X" from "this digest was recorded by an authenticated-but-mismatched caller Y" — `CheckAndRecord` only takes the digest and expiry: [3](#0-2) 

This is directly analogous to the reported `TimeswapPair.pay()` bug: a low-cost, largely inconsequential action by an unprivileged attacker (an owner-mismatched but authenticated call, versus a 1-wei repayment) permanently consumes a shared state guard (the replay digest / `due.debt` counter) needed for a legitimate user's subsequent operation, causing a revert/denial for that legitimate operation. The vault code even documents that a replay-guard rejection is expected to only occur for genuine retries of an already-accepted request: [4](#0-3) 
— which is violated once an attacker can trigger `ErrRequestAlreadySeen` for a request the victim never successfully sent.

### Impact Explanation
A DoS on Vault secret operations (`vault.secrets.list`, `.create`, `.update`, `.delete`) for a targeted owner/request: the legitimate user's call is denied with "request was already authorized previously" even though it is their first genuine attempt, and repeating the identical request will keep failing until the digest's `expiresAt` elapses. This can be used to block a user's secret creation/update/list/delete requests, degrading availability of a security-sensitive capability. Because the attack requires only that the attacker be *some* authenticated Vault caller (not the victim), and costs the attacker nothing beyond one rejected call, it can be repeated cheaply.

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or observe the exact `method`/`id`/`params` of the victim's upcoming request (including the victim's owner and any deterministic `request_id`). This may be harder for random/unique IDs, but request IDs and owners are not secrets in this protocol (they appear in gateway traffic, DON logs, or can be deterministic per workflow), and the code path itself provides no additional protection beyond ID unpredictability. The root cause — check-ordering that lets replay-guard state mutate on paths that are subsequently rejected — is a straightforward logic bug independent of any specific ID-guessing difficulty.

### Recommendation
Reorder the checks in `authorizer.AuthorizeRequest` so that `validateSecretOwnersMatchAuthorized` (and any other request-validity checks) run *before* `replayGuard.CheckAndRecord`, ensuring the replay guard is only updated for requests that are fully valid and authorized end-to-end. Alternatively, bind the replay-guard digest to the authorized owner (e.g., hash owner + request digest) so a mismatched-owner caller cannot pre-consume the same guard slot as the correct owner's request.

### Proof of Concept
1. Victim intends to send `{"method":"vault.secrets.list","id":"req-1","params":{"owner":"0xVictim","namespace":"main"}}`, authenticated as `0xVictim`.
2. Attacker, authenticated as their own distinct identity `0xAttacker` (valid JWT/allowlist entry), submits the exact same JSON-RPC payload (`method`, `id`, `params` including `owner: "0xVictim"`) but signs/authenticates as themselves.
3. `authorizeRequest` succeeds for the attacker (they are a valid Vault caller), returning an `AuthResult` with `workflowOwner = 0xAttacker` and `digest = Digest(req)` (computed from the request content, which includes `"owner":"0xVictim"`).
4. `replayGuard.CheckAndRecord(digest, expiry)` succeeds and records the digest — matching `TestRequestReplayGuard_DuplicateRejected` behavior in [5](#0-4) .
5. `validateSecretOwnersMatchAuthorized(req, "0xAttacker")` fails because `listReq.Owner ("0xVictim") != workflowOwner ("0xAttacker")`, per [6](#0-5) , and the attacker's call is rejected.
6. Victim now sends the identical, correctly-authorized request. `CheckAndRecord` returns `ErrRequestAlreadySeen`, exactly reproducing the test assertion pattern for duplicate requests shown in [7](#0-6) , but here triggered by the attacker rather than a genuine retry — denying the victim's first legitimate call.

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}

// validateSecretOwnersMatchAuthorized checks that secret identifiers in the request payload
// match the authorized workflow owner. This is read-only validation; owner prefixing and
// param stamping happen later in GatewayVaultRequestProcessor.
func validateSecretOwnersMatchAuthorized(req jsonrpc.Request[json.RawMessage], workflowOwner string) error {
	switch req.Method {
	case vaulttypes.MethodPublicKeyGet:
		return nil
	case vaulttypes.MethodSecretsCreate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var createReq vaultcommon.CreateSecretsRequest
		if err := json.Unmarshal(*req.Params, &createReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(createReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsUpdate:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var updateReq vaultcommon.UpdateSecretsRequest
		if err := json.Unmarshal(*req.Params, &updateReq); err != nil {
			return err
		}
		return validateEncryptedSecretOwnerMismatch(updateReq.EncryptedSecrets, workflowOwner)
	case vaulttypes.MethodSecretsDelete:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var deleteReq vaultcommon.DeleteSecretsRequest
		if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
			return err
		}
		return validateSecretIdentifierOwnerMismatch(deleteReq.Ids, workflowOwner)
	case vaulttypes.MethodSecretsList:
		if req.Params == nil {
			return errors.New("request params must not be nil")
		}
		var listReq vaultcommon.ListSecretIdentifiersRequest
		if err := json.Unmarshal(*req.Params, &listReq); err != nil {
			return err
		}
		if vaultutils.NormalizeOwner(listReq.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("list secrets owner %q does not match authorized workflow owner %q", listReq.Owner, workflowOwner)
		}
		return nil
	default:
		return fmt.Errorf("owner validation not implemented for method %q", req.Method)
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func TestRequestReplayGuard_DuplicateRejected(t *testing.T) {
