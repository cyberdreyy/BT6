Based on the analysis, I confirmed a concrete accounting flaw in the miner's `StackerDBListener` weight-tally logic.

### Title
Signer vote flip (reject→accept) is double-counted in both `total_weight_rejected` and `total_weight_approved`, letting stale rejections wedge otherwise-valid blocks - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`BlockStatus` tracks per-block weight tallies using two independent guards: the accept path gates on `gathered_signatures` (a map keyed only by accepted signatures) while the reject path gates on the shared `responded_signers` set [1](#0-0) . Because these are different collections, a signer who first rejects and later accepts the same block (an explicitly supported re-evaluation transition, `LocallyRejected --> LocallyAccepted`) has its weight permanently retained in `total_weight_rejected` with no retraction path, while also being freshly added to `total_weight_approved`.

### Finding Description
In the rejected-message handler, weight is added only once, gated by `block.responded_signers.insert(slot_id)` returning `true`: [2](#0-1) . That same `responded_signers` set is also mutated by the accept path [3](#0-2) , but the accept path's own weight-add decision is instead gated by `block.gathered_signatures.contains_key(&slot_id)` [4](#0-3) , a completely separate map.

Consequence: if signer S rejects block B first (S's slot id inserted into `responded_signers`, weight added to `total_weight_rejected`) and later, after re-evaluating, sends an `Accepted` for B, the accept path only checks `gathered_signatures` (empty for S), so it happily adds S's weight to `total_weight_approved` as well — but nothing ever removes S's earlier contribution from `total_weight_rejected`. The two weight totals, which the docs/state model treat as describing disjoint partitions of the signer set (`docs/signer-flows.md` sections 5–6, `BlockState`'s mutually exclusive `LocallyAccepted`/`LocallyRejected` terminal-ish states before global resolution) can now simultaneously and permanently overcount the same signer weight in both buckets, so `total_weight_approved + total_weight_rejected` can exceed `total_weight`.

This breaks the "aggregated-weight vs verified-accepts/rejects" equality the coordinator relies on to decide the block's fate: [5](#0-4) .

### Impact Explanation
A signer's own transient/legitimate flip from reject to accept (which the signer-side state machine explicitly allows and even the docs describe as a normal re-evaluation) leaves a stale reject weight that is never cleared on the miner side. Combined with genuine rejections from other signers, this stale weight can push `total_weight_rejected.saturating_add(weight_threshold) > total_weight` and force the coordinator into the `SignersRejected` / blocking-minority path even though the true, current tally of signers actively rejecting the block never reached the 30% blocking minority — a liveness wedge that can deny a valid, sufficiently-signed block from being pushed, without needing a majority of colluding signers.

### Likelihood Explanation
This requires nothing more than the normal, protocol-sanctioned reject→accept re-evaluation behavior from a single signer (or a signer deliberately toggling votes), observable purely via StackerDB gossip that the miner listens to — no majority collusion, no stolen keys, no node compromise. This is a plausible and easily reproduced sequence in real operation (e.g., a signer initially rejects due to a transient node/validation hiccup, then accepts once conditions clear).

### Recommendation
Use a single, consistent per-slot vote-state map (not two independently-updated collections) to decide whether/how to (re-)tally a signer's weight, and when a signer's vote flips, subtract the weight from the old bucket before adding it to the new one, keeping `total_weight_approved + total_weight_rejected` bounded by `total_weight` at all times.

### Proof of Concept
1. Miner proposes block B; signers S1..Sn receive it.
2. Signer S (weight w) sends `BlockResponse::Rejected` for B → `responded_signers` gets S's slot id, `total_weight_rejected += w`.
3. Other genuine rejecters push `total_weight_rejected` close to the 30% blocking-minority boundary (still short of it without S).
4. S re-evaluates and sends `BlockResponse::Accepted` for B → since `gathered_signatures` has no entry for S, `total_weight_approved += w` is added; `total_weight_rejected` still contains S's earlier `w`.
5. Now `total_weight_rejected` (still including S's stale weight) crosses the blocking-minority threshold in `signer_coordinator.rs`, triggering `NakamotoNodeError::SignersRejected` even though the real, current reject total (excluding S, who now accepts) never reached it.
