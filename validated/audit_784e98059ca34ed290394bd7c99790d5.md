### Title
Missing deduplication/ownership check in `handler.HandleLegacyUserMessage` allows unprivileged callers to hijack or DoS another user's pending gateway callback via `MessageId` collision - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's legacy Web API capability handler stores the caller's response callback keyed only by the client-supplied `msg.Body.MessageId`, without checking whether an entry for that ID already exists or verifying the request originates from the same caller who created it. This mirrors the reported `MarketERC20::permit` bug class: a request that legitimately depends on an externally-supplied identifier lacks a check binding that identifier to the actual caller/owner, letting a third party interfere with or squat on someone else's in-flight, ID-keyed operation.

### Finding Description
In `HandleLegacyUserMessage`, the handler blindly assigns:
```go
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
``` [1](#0-0) 

There is no check for an existing entry (as the newer v2 `httpTriggerHandler.setupCallback` does with its "in-flight request ID" rejection), and no binding of `MessageId` ownership to the request's signer/caller. `Message.Validate()` only validates length/format constraints on `MessageId`, not uniqueness or ownership: [3](#0-2) .

Later, when a DON node responds, `handleWebAPITriggerMessage` looks up and deletes whatever callback is currently stored under that `MessageId` and delivers the response to it — with no verification that it's the correct/original caller's callback: [4](#0-3) .

Because `MessageId` is entirely attacker-chosen (bounded only by `MessageIdMaxLen`) and this legacy path performs no per-message caller/session authentication distinguishing one external user from another using the same DON, an unprivileged actor can send a request using the same `MessageId` as a legitimate, still-pending request for the same DON, silently overwriting the map entry. The legitimate caller's original callback reference is lost/replaced, so it will never receive its response (a hung/DoS'd request), while the attacker's callback receives whatever response the DON node returns for that message ID.

### Impact Explanation
This is a griefing/DoS and cross-user response-confusion vulnerability: an unprivileged client can silently deny another user's pending gateway request or capture a response meant for someone else's `MessageId`, purely by guessing or observing a public identifier and reusing it before the legitimate response returns. This is directly analogous to the reported issue where lack of a caller-binding check on a per-user identifier (spender in `permit`, `MessageId` here) lets an unrelated party interfere with someone else's pending action.

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or observe a legitimate, in-flight `MessageId` before the corresponding node response arrives (window governed by DON round-trip latency), and only affects the legacy `HandleLegacyUserMessage` path (the newer v2 HTTP trigger handler already guards against this). Likelihood is moderate: it requires no privileged access or valid credentials, only submitting a JSON-RPC/legacy request to the gateway with a chosen `MessageId`.

### Recommendation
Add an explicit conflict check in `HandleLegacyUserMessage` mirroring `httpTriggerHandler.setupCallback` — reject (rather than overwrite) requests whose `MessageId` already has an active `savedCallback` entry, and/or scope `savedCallbacks` keys to include a caller-bound component (e.g., authenticated session/workflow key) so a `MessageId` collision from a different caller cannot overwrite another's pending callback.

### Proof of Concept
1. Legitimate user A sends a legacy gateway request with `MessageId = "X"` to a given DON; the handler stores A's callback under `savedCallbacks["X"]` and forwards the request to DON nodes.
2. Before the DON node responds, attacker B sends another legacy request to the same DON using the identical `MessageId = "X"` (fully attacker-controlled and only length/charset validated).
3. The handler overwrites `savedCallbacks["X"]` with B's callback (`handler.go:411-414`), discarding A's reference.
4. When the DON node eventually responds with `MessageId = "X"`, `handleWebAPITriggerMessage` looks up and deletes the (now B's) entry and delivers the response to B, not A (`handler.go:148-161`). A's request hangs indefinitely (DoS) and B receives a response for a request it never legitimately issued.
