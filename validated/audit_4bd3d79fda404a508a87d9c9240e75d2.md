### Title
Debug/pprof and expvar endpoints only require authentication, not admin role, allowing view-role users to dump process memory and goroutines - (File: core/web/router.go)

### Summary
The pprof debug endpoints registered by `metricRoutes` and the `/debug/vars` expvar endpoint registered by `debugRoutes` are gated only by `auth.Authenticate` (any valid session or API token), without any `auth.RequiresAdminRole`/`RequiresEditRole` wrapper. This lets a low-privileged `view`-role user (the lowest role in the system) retrieve full heap dumps, goroutine stacks, and process cmdline info from a running node.

### Finding Description
In `NewRouter`, `debugRoutes(app, api)` registers `/debug/vars` behind `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` only [1](#0-0) . This does not require any specific role — any authenticated session, including one with `UserRoleView`, satisfies `auth.Authenticate`, which only checks that authentication succeeds and never checks `user.Role` [2](#0-1) .

Similarly, inside `v2Routes`, the pprof/metrics routes are mounted via `metricRoutes(authv2)` at the end of the `authv2` block [3](#0-2) . The `authv2` group itself is only wrapped with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` [4](#0-3) . Unlike every other sensitive route in this file (`/keys/*`, `/users`, `/transfers`, etc.), which are explicitly wrapped with `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole` [5](#0-4) , the routes added by `metricRoutes` have no such role wrapper: [6](#0-5) 

Because Go's `net/http/pprof` handlers are used directly (`pprof.Cmdline`, `pprof.Trace`, `pprof.Handler("heap")`, `pprof.Handler("goroutine")`, etc.), any authenticated user — regardless of role — can retrieve:
- Full process command line (`/v2/debug/pprof/cmdline`)
- Heap/goroutine/allocs dumps (`/v2/debug/pprof/heap`, `/goroutine`, `/allocs`) which can contain in-memory secrets, private key material, or session tokens processed by the node
- CPU/execution traces (`/v2/debug/pprof/trace`, `/profile`)

The role check functions `RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole` compare `user.Role` against `UserRoleView`/`UserRoleRun`/`UserRoleEdit`/`UserRoleAdmin` [7](#0-6) [8](#0-7) , but none of these wrappers are applied to `metricRoutes` or `debugRoutes`, so the lowest-privilege `view` role (and any run/edit role) passes straight through to the pprof/expvar handlers.

Note: this is not reachable by a fully unauthenticated client — `auth.Authenticate` does enforce that a valid session or API token exists. The vulnerability is a **role/privilege bypass**: any authenticated principal, even the lowest-privileged `view` role (intended for read-only dashboard access), can reach debug endpoints that should be restricted to `admin`.

### Impact Explanation
A `view`-role user (the least privileged authenticated role, intended only for read access to non-sensitive resources) can pull heap and goroutine dumps and full process command-line arguments from a live Chainlink node. Depending on what's resident in memory at request time (decrypted keys, session secrets, DB connection strings passed via flags), this can leak sensitive node secrets to a user who should not have had that level of access. This matches a credential/secret-disclosure impact via privilege escalation (a `view` user obtaining `admin`-only capability), scoped below the "Critical: unauthenticated full compromise" tier because authentication is still required, but still a legitimate authorization-bypass finding.

### Likelihood Explanation
Exploitation only requires possession of any valid, low-privileged Chainlink node account (view/run/edit role) or a scoped API token — a credential level explicitly listed as in-scope "attacker" in the rules (view/run-role user, restricted API token holder). No admin/operator/host access is required. The request is a simple GET to `/v2/debug/pprof/heap`, `/v2/debug/pprof/cmdline`, etc., with valid session cookies or `X-API-KEY`/`X-API-SECRET` headers for a view-role account. This is trivially repeatable.

### Recommendation
Wrap all routes added by `metricRoutes` and `debugRoutes` with `auth.RequiresAdminRole`, consistent with the other sensitive administrative endpoints in `v2Routes`, e.g.:
```go
pprofGroup.GET("/", auth.RequiresAdminRole(ginHandlerFromHTTP(pprof.Index)))
```
and:
```go
group.GET("/vars", auth.RequiresAdminRole(func(c *gin.Context) { expvar.Handler().ServeHTTP(c.Writer, c.Request) }))
```

### Proof of Concept
Handler-level integration test plan (using `httptest` + the app's test harness, e.g. `cltest.NewApplication`):
1. Create two users: one `UserRoleAdmin`, one `UserRoleView`, using existing test helpers (`cltest.MustRandomUser` / session creation utilities).
2. Build the router via `web.NewRouter(app, nil)`.
3. Authenticate as the `view`-role user (obtain session cookie via `POST /sessions`).
4. Issue `GET /v2/debug/pprof/heap`, `GET /v2/debug/pprof/cmdline`, `GET /v2/debug/pprof/goroutine`, and `GET /debug/vars` with the view-role session cookie.
5. Assert: response status is `200 OK` and body contains pprof/expvar payload (proving unauthorized-role access is currently allowed) — this should fail after the fix (expect `403 Forbidden` per `RequiresAdminRole`).
6. Repeat step 4 with no session/token at all — assert `401 Unauthorized` (confirming true anonymous access is already blocked, isolating the bug to role-level, not authentication-level, bypass).

// Authenticate is middleware which authenticates the request by attempting to
// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
