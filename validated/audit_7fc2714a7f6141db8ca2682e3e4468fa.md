### Title
JWT replay-protection check-then-record race in HTTP Trigger `Authorize()` allows anti-replay bypass - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize()` is the entry point that authenticates every inbound HTTP-trigger request from unprivileged external clients. It is supposed to guarantee that each JWT (`jti`) can be used at most once, but the "is this JWT already used" check and the "mark this JWT as used" write are two separate, unsynchronized-as-a-unit operations separated by additional logic (workflow lookup, signer authorization). This mirrors the reported Popcorn Vault bug where `takeFees()`'s balance check is decoupled from the state mutation that should immediately follow it, letting an external actor race the two operations and reuse stale state.

### Finding Description [1](#0-0) 

`Authorize()` performs, in order:
1. `claims, signer, err := utils.VerifyRequestJWT(token, *req)` — verifies the JWT signature.
2. `h.jwtCache.isReplay(claims.ID)` — checks (read-lock) whether this `jti` has been seen before.
3. Workflow/signer authorization lookups against `h.authorizedKeys` (unguarded map read, no `h.mu` lock at all, while `syncMetadata` mutates the same map under `h.mu.Lock()` on a separate goroutine — a related, but secondary, data race).
4. Only at the very end: `h.jwtCache.recordUsage(claims.ID)` — the write that actually marks the JWT as consumed.

Because `isReplay` (read) and `recordUsage` (write) are not atomic with respect to each other, two concurrent `HandleUserTriggerRequest` calls carrying the **same signed JWT** can both pass the `isReplay` check before either call reaches `recordUsage`. Both goroutines then proceed to fan the same authenticated trigger request out to the workflow DON. This is exactly the "check outdated state, then mutate it late" pattern in the report: the Vault's `changeAdapter()`/fee accounting used a stale `totalAssets()` snapshot because the mint (state write) happened before the balance-affecting transfer completed; here the authorization decision is made and acted upon before the replay-cache state write that should have foreclosed the second, colliding invocation.

`jwtReplayCache` itself is internally lock-protected (`sync.RWMutex`), but that only prevents corruption of the map — it does nothing to serialize the check-then-act sequence in `Authorize()`, since the caller releases its "logical" claim on the `jti` in between.

### Impact Explanation
An unprivileged client that possesses one valid, signed JWT can trigger the same workflow-execution request multiple times concurrently, bypassing the single-use anti-replay guarantee that is explicitly documented as a security control (`JWTReplayPeriodMs` / "JWT IDs are cached to prevent replay attacks"). Depending on the downstream workflow semantics, this enables duplicate/unauthorized workflow executions (e.g., duplicate on-chain actions, double-spend-like effects, or repeated invocation of rate-limited/paid actions) from a single authorized signature — i.e., unauthorized job/workflow run triggering, which the validation rules explicitly call out as an acceptable impact class.

### Likelihood Explanation
The race window is real but narrow: an attacker (or any client with retry logic) simply needs to fire the same signed JWT twice in quick succession/concurrently — no privileged access, no node cooperation, no special network conditions are required, only network-level ability to send two HTTP-ish gateway requests back-to-back. This is a purely client-triggerable condition, matching the "unprivileged actor" scope of the review. Likelihood is Medium: it requires precise timing to win the race, but is trivially automatable by an external client.

### Recommendation
Make the replay check-and-mark atomic: acquire the `jwtCache` write lock once, and under a single critical section perform "check `isReplay`" and, if not a replay, immediately `recordUsage`/insert before releasing the lock and only then proceed with workflow/signer authorization (or perform authorization first only against non-consuming data, then finalize the replay-cache insert transactionally with a fallback to revert-on-failure). Concretely, replace `isReplay()` + later `recordUsage()` with a single `checkAndRecord(jti) (alreadyUsed bool)` method that does both under one lock acquisition in `jwtReplayCache`. Separately, guard `h.authorizedKeys` reads in `Authorize()` with `h.mu.RLock()`/`RUnlock()` to eliminate the concurrent unguarded map access race with `syncMetadata`.

### Proof of Concept
Not independently executed against a live gateway in this review; the race is demonstrated purely by code inspection of `Authorize()` at [2](#0-1) , where `isReplay` and `recordUsage` are separated by workflow-lookup logic instead of being combined into one atomic check-and-set operation, and by `jwtReplayCache`'s definition as a plain `RWMutex`-guarded map ( [3](#0-2) ) whose `isReplay`/`recordUsage` methods are called independently rather than as one locked transaction. A concrete PoC would require constructing two goroutines issuing `HandleUserTriggerRequest` with an identical signed JWT and asserting both are accepted (not exercised here due to the ask-only scope of this analysis).

**Note on scope/uncertainty:** The `isReplay`/`recordUsage` method bodies inside `jwtReplayCache` (exact lock granularity) were not directly read in this session — only their call sites and the struct definition were confirmed. If those two methods are already combined into a single locked call internally (which the current code does not show), this finding would not hold; based on the call-site code inspected, they are invoked as two separate calls with authorization logic in between, which is sufficient to constitute the race regardless of each individual method's internal locking.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
