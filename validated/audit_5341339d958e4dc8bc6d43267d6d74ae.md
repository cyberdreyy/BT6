# Analysis Result

## Title
Async deposit/redeem refunds on cancellation and expiry are sent to `request.receiver` instead of the request creator who escrowed the funds - (File: v3/src/core/ProvisionerV2.sol)

### Summary
`ProvisionerV2` lets a user create an async `deposit`/`redeem` request specifying an arbitrary `receiver` address that is unrelated to (and not necessarily approved by) the caller who actually pays the escrowed tokens/units. When that request is cancelled by the creator, expires, or is refunded, the escrowed amount is returned to `request.receiver` first, and only falls back to the original requester if the transfer to `receiver` reverts — mirroring exactly the Dinari M-3 root cause where cancellation refunds went to `order.recipient` instead of the order creator.

### Finding Description
`requestDeposit`/`requestRedeem` pull tokens/units from `msg.sender` while allowing the caller to name any non-zero `receiver`, with only a zero-address check via `_validateRequest` — no `_requireValidReceiver`/approval check is applied for this async path (that stricter check is only used for sync `deposit`/`mint`). [1](#0-0) [2](#0-1) 

`request.user` (the payer/creator) is stored separately from `request.receiver`. When the creator self-cancels via `cancelRequest` (`msg.sender == request.user` is enforced), the refund is routed through `_clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token)`. [3](#0-2) 

`_clearHashAndTransferRefund` and its underlying `_transferWithFallback` send the refund to `request.receiver` primarily, only falling back to the actual requester if `receiver == requester` or the transfer to `receiver` reverts: [4](#0-3) 

The same pattern recurs for permissionless `refundRequest` after deadline, and for expired-request handling inside the solver paths (`_solveDepositVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, `_solveRequestDirect`) — all use `request.user` only as a fallback and `request.receiver` as the primary destination: [5](#0-4) [6](#0-5) [7](#0-6) 

Since the funds/units were actually escrowed from `request.user` (they paid via `safeTransferFrom(msg.sender, ...)` in `requestDeposit`/`requestRedeem`), and `receiver` never contributed anything, a cancelled or expired request returns the payer's own principal to an unrelated third party instead of back to the payer — the exact failed-guard pattern described in the Dinari M-3 report ("refund is sent to order.recipient instead of the order creator").

### Impact Explanation
Any user who creates an async deposit or redeem request naming a different `receiver` (e.g., for an intended OTC-style direct solve, or simply a mistaken/third-party address) permanently loses their escrowed principal to that `receiver` address if the request is cancelled or expires, since `_transferWithFallback` only reroutes to the requester when the primary transfer technically fails. This is a direct, irreversible loss of user principal funds held by the `ProvisionerV2` contract.

### Likelihood Explanation
No privileged role is required. Any ordinary user can trigger this by calling `requestDeposit`/`requestRedeem` with a `receiver` different from themselves and then calling `cancelRequest` (self-triggered) or waiting for the deadline and calling permissionless `refundRequest`/letting a solver process the expired request. This requires only standard user-level transactions and no oracle manipulation, governance action, or malicious peer.

### Recommendation
Refunds on cancellation and expiry (`_clearHashAndTransferRefund`, `_solveDepositVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, `_solveRequestDirect`, `_transferWithFallback`) should transfer the escrowed amount back to `request.user` (the party who actually deposited the tokens/units), not to `request.receiver`, since `receiver` never contributed the escrowed funds.

### Proof of Concept
1. On a local fork, deploy/attach to `ProvisionerV2` with async deposits enabled for a test token.
2. User A calls `requestDeposit(token, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge, isFixedPrice, receiver=B)`; confirm `token.balanceOf(A)` decreases by `tokensIn` and the provisioner holds the escrow.
3. Before the request is solved, A calls `cancelRequest(token, request)` (deposit cancellations enabled).
4. Assert `token.balanceOf(B)` increased by the refunded amount while `token.balanceOf(A)` did not recover the escrowed principal — demonstrating A's funds were sent to B instead of returned to A.

    function cancelRequest(IERC20 token, RequestV2 calldata request) external nonReentrant {
        // Requirements: self-cancel caller must be request user
        require(msg.sender == request.user, Aera__CallerIsNotRequestUser());

        if (_isRequestTypeDeposit(request.requestType)) {
            // Requirements: deposit cancellation toggle must be enabled
            require(_depositCancellationsEnabled, Aera__DepositRequestCancellationDisabled());

            uint256 refundAmount = request.tokens;
            // Requirements: pre-deadline self-cancel applies cancellation fee
            if (block.timestamp < request.deadline) {
                uint256 cancellationFee = _computeDepositCancellationFeeTokens(token);
                // Requirements: cancellation fee cannot exceed escrowed amount
                require(cancellationFee <= refundAmount, Aera__CancellationFeeExceedsRequestAmount());
                if (cancellationFee != 0) {
                    unchecked {
                        // unchecked: safe because cancellationFee <= refundAmount is enforced above
                        refundAmount -= cancellationFee;

                    // Interactions: transfer cancellation fee to vault
                    token.safeTransfer(MULTI_DEPOSITOR_VAULT, cancellationFee);
                }
            }

            // Effects + interactions: clear hash, emit refund event, and transfer net token amount with fallback
            _clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token);

    function _clearHashAndTransferRefund(
        IERC20 token,
        RequestV2 calldata request,
        address requester,
        uint256 amount,
        IERC20 transferToken
    ) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        require(asyncRequestHashes[requestHash], Aera__HashNotFound());
        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;
        // Interactions: transfer amount to receiver, fallback to requester on transfer failure
        _transferWithFallback(transferToken, requester, request.receiver, amount);

        // Log refund event
        if (_isRequestTypeDeposit(request.requestType)) {
            emit DepositRefunded(requestHash);
        } else {
            emit RedeemRefunded(requestHash);
        }
    }

    /// @notice Transfers amount to receiver and falls back to requester if receiver transfer fails
    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
