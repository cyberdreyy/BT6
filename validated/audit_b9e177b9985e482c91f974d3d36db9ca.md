### Title
Vault liquidity drain blocks `onStopEpoch` and freezes epoch settlement - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable` whenever the configured ERC4626 vault cannot fulfill `vault.withdraw(shortfall)`, even when the vault shares economically cover the shortfall on paper (`_currentVaultAssets()` uses `convertToAssets`, which values the position, not available liquidity). Any unprivileged EOA can make this revert persistent by borrowing the underlying liquidity out of the Morpho markets the vault is allocated to, causing `IdleCDOEpochVariant.stopEpoch` to revert and freezing all tranche withdrawals for the duration of the liquidity shortage.

### Finding Description
`stopEpoch` calls `IProgrammableBorrower.onStopEpoch`, which attempts `vault.withdraw(shortfall, ...)` inside a `try/catch` and reverts on failure [1](#0-0) . The preceding guard only checks `shortfall > _currentVaultAssets()` [2](#0-1) , i.e., share *valuation*, not withdrawable liquidity — the analog of trusting a response field that does not reflect the connection's actual state (the CVE's PREAUTH/null-deref pattern: a code path assumes a precondition that an external party can invalidate). For MetaMorpho-style vaults, `convertToAssets` counts assets supplied to underlying markets, while `withdraw` reverts if idle liquidity is insufficient. An attacker who borrows the available liquidity in those Morpho markets makes every `stopEpoch` call revert, blocking `stopEpoch`, epoch interest settlement, and consequently all `claimWithdrawRequest`/`claimInstantWithdrawRequest` payouts that depend on the stopped epoch, without any privileged action.

### Impact Explanation
Temporary freezing of funds: every pending and future withdraw request is stuck until third-party Morpho borrowers repay or positions are liquidated, which the pool cannot force. Tranche holders suffer delayed redemptions and the pool cannot even enter the default path (`_handleBorrowerDefault` is only reached when `onStopEpoch` returns `false`, not when it reverts) [3](#0-2) . Loss is the time value plus potential price impact of forced delayed exits; it scales with the full pending-withdraw amount and NAV parked in the vault.

### Likelihood Explanation
The attacker only needs collateral to borrow in the same Morpho markets the MetaMorpho vault allocates to — no role, no KYC. Cost is borrow interest for the freeze duration plus temporary collateral lockup; the attack is griefing (no direct profit), so likelihood is moderate. The comment "transient ERC4626 liquidity failures can be retried" acknowledges transient failure but not adversarially sustained liquidity withdrawal.

### Recommendation
Add a fallback: when `vault.withdraw` fails despite covered shares, treat it as a stopEpoch-failure mode that still settles epoch accounting (e.g., record the deficit and route into a degraded/default state, or allow `stopEpoch` to proceed with the on-hand amount and mark the shortfall), rather than reverting the whole epoch transition. Alternatively, cap the portion of NAV deployable into vaults whose underlying markets can be fully borrowed, or pre-declare the epoch "stopped-with-shortfall" so withdraw claims can be processed pro rata.

### Proof of Concept
Foundry fork PoC sketch (mainnet fork with the live MetaMorpho vault and USDC):

```solidity
// 1. Lender deposits AA; manager startEpoch -> PB deposits NAV into morphoVault.
idleCDO.depositAA(amount);
cdoEpoch.stopEpoch(...); // buffer
cdoEpoch.startEpoch(...);

// 2. Attacker (unprivileged EOA with collateral) borrows all available
//    liquidity from each Morpho market the vault allocates to.
for each market in morphoVault.config(...):
    morpho.borrow(marketParams, market.idleLiquidity(), 0, attacker, attacker);

// 3. Warp past epochEndDate; manager calls stopEpoch.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);

// 4. Assert epoch still running: epochEndDate != 0 path unchanged,
//    withdraw requests cannot be claimed; revert persists while liquidity is out.
vm.prank(manager);
vm.expectRevert(); // still reverts on retry
cdoEpoch.stopEpoch(0, 0);
```

Key assertion: `convertToAssets(shares) >= shortfall` (guard passes) while `morphoVault.withdraw` reverts due to zero idle market liquidity, demonstrating the mismatch between the valuation check and the executable withdrawal.
