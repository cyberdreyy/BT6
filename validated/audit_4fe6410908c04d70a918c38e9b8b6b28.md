Confirmed. In both `multisig/src/lib.rs` and `multisig2/src/lib.rs`, when a member/key is removed, the contract only purges *requests originally authored by* that member — it does not scan the `confirmations` map for other pending requests that the removed member had *confirmed* (but not authored). Those stale confirmations remain counted toward `num_confirmations` for those other requests.

### Title
Stale confirmations from removed multisig members let a request execute below the live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`DeleteMember` (multisig2) and `DeleteKey` (multisig v1) only remove pending requests whose *original signer* is the member/key being removed. They never scrub that member's confirmation entries from other requests they merely co-signed. A request can therefore reach `num_confirmations` and execute even though one of the counted "confirmations" belongs to an account/key that is no longer a multisig member at execution time.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` (lines 356–379) computes `request_ids` as requests where `r.member == member` (the request's *author*), and only clears confirmations for those: [1](#0-0) 
It does not iterate `self.confirmations` to strip the removed member's identifier from confirmation sets of requests authored by *other* members. The same pattern exists in `multisig/src/lib.rs`'s `DeleteKey` handler, which filters requests `where r.signer_pk == pk` (the request author) before clearing confirmations: [2](#0-1) 

Meanwhile, `confirm` counts confirmations purely by set membership/length and executes once the threshold is met, with no re-validation that every entry in the `confirmations` set still corresponds to a current member: [3](#0-2) [4](#0-3) 

The binding that should hold is: `confirmations counted for execution == confirmations from currently-live members`. This invariant can be violated:

1. Member A creates request R1 (self-confirms).
2. Member B (soon to be removed) confirms R1 — insufficient count yet, R1 stays pending.
3. Members execute a separate, properly-authorized `DeleteMember{B}` request. `delete_member` only removes requests *authored* by B; R1 (authored by A) is untouched, and B's stale entry remains in `confirmations[R1]`.
4. Member C confirms R1. If `confirmations.len()+1 >= num_confirmations`, R1 executes — using B's confirmation even though B is no longer a member.

### Impact Explanation
This breaks the K-of-N authorization guarantee: a request (e.g., a `Transfer` of the multisig account's NEAR, an `AddKey`/`AddMember`, or a `FunctionCall`) can execute with fewer live-member approvals than `num_confirmations` requires, because a stale approval from an already-removed member is counted. This matches the "Critical — a multisig request executed below threshold" impact category: funds can be moved, or the access-control set itself can be further manipulated, with fewer real approvals than the configured threshold.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an existing pending request that has been partially confirmed by a member, and (b) that member subsequently being removed via a legitimate `DeleteMember`/`DeleteKey` action, before the pending request is confirmed to completion or explicitly deleted (requests persist until confirmed/deleted; there's a 15-minute `REQUEST_COOLDOWN` before deletion, giving ample time). This is a normal governance sequence (member rotation) in any multisig with concurrent outstanding requests, not a contrived edge case, and requires no privileged access beyond being an ordinary member who happens to co-sign a request before departing.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over all entries in `confirmations` (not just requests authored by the departing member) and remove the departing member's identifier from every confirmation set. Alternatively, at `confirm`-time, filter/validate the confirmation set against current `members` before counting/executing, discarding stale entries from members no longer present.

### Proof of Concept
Using `multisig2/src/lib.rs` test harness (`members()` = Alice, Bob, AccessKey1, AccessKey2; `num_confirmations = 3`):
1. `MultiSigContract::new(members(), 3)`.
2. As Alice: `add_request_and_confirm(request_transfer)` → R1 has 1 confirmation (Alice).
3. As AccessKey1: `confirm(R1)` → R1 has 2 confirmations (Alice, AccessKey1). Still pending (2 < 3).
4. Execute a separate, fully-confirmed request removing `AccessKey1` via `DeleteMember{member: AccessKey1}` (`delete_member`, lines 356–379) — this only clears confirmations/requests where `r.member == AccessKey1` (i.e., requests AccessKey1 authored), leaving R1's confirmation set (`{Alice, AccessKey1}`) untouched.
5. As Bob: `confirm(R1)` → `confirmations.len() + 1 == 3 >= num_confirmations`, so R1 executes the `Transfer`, even though only 2 of the 3 confirmations (Alice, Bob) come from currently live members — AccessKey1's stale confirmation was counted toward the threshold.

This can be verified/extended directly from the existing test `add_key_delete_key_storage_cleared` pattern [5](#0-4)  by adding a second, independently-authored pending request that the soon-to-be-removed member also confirms, then asserting it still executes below the intended live threshold after removal.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
