### Title
Zip symlink extraction allows attacker-controlled, unvalidated link targets - ([File: helpers/archives/zip_extract.go])

### Summary
`extractZipSymlinkEntry` reads the zip entry's data (the symlink target/"Linkname") and passes it directly to `os.Symlink(string(data), file.Name)` with no validation that the target is confined to the extraction root. This is reachable from the legacy zip extractor (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go` `Extract` → `archives.ExtractZipArchive` → `extractZipFile` → `extractZipSymlinkEntry`), which handles artifact/cache archives uploaded by an unprivileged pipeline job.

### Finding Description
`extractZipSymlinkEntry` in [1](#0-0)  reads the raw file content of a zip entry marked `os.ModeSymlink` and calls `os.Symlink(string(data), file.Name)` unconditionally — there is no check that `data` (the link target) is a relative path confined under the extraction directory, no rejection of absolute paths (e.g. `/etc/cron.d/malicious`), and no rejection of `..`-escaping relative paths (e.g. `../../outside`).

The dispatch that reaches this function is confirmed: `extractZipFile` routes any entry with `os.ModeSymlink` to `extractZipSymlinkEntry` [2](#0-1) , and `ExtractZipArchive` iterates every file in an untrusted zip archive calling `extractZipFile` for each [3](#0-2) . The legacy zip extractor's `Extract` method feeds a job-supplied archive reader directly into `archives.ExtractZipArchive` [4](#0-3) .

Note: the file-*name* (`file.Name`) path-traversal case (zip-slip on the symlink's own location) may be constrained by other checks (`path_check_helper.go`, `path_error_tracker.go`) that I was not able to fully inspect given the iteration budget, but those checks — as far as observed — govern the *entry name*, not the *symlink target content* written via `os.Symlink`. No code path in `extractZipSymlinkEntry` sanitizes or rejects the target value itself.

### Impact Explanation
The immediate result of `os.Symlink(string(data), file.Name)` with an attacker-chosen absolute/traversal target is a dangling symlink inside the job workspace whose target points outside the extraction root (e.g., to `/etc/cron.d/malicious` or a path outside the build directory). By itself, creating a symlink does not write to the target — but any subsequent step in the same job that writes through that symlink path (e.g., a script step, cache/artifact packaging step, or another extraction pass that writes into `file.Name` believing it's a plain path within the workspace) will actually write/read at the symlink's resolved (attacker-chosen) location. This matches the scoped impact described: a dangling symlink usable by a later file-write step to redirect I/O outside the workspace.

### Likelihood Explanation
This is a legacy code path (`ziplegacy`); the default zip extraction in GitLab Runner has moved to `fastzip` (`commands/helpers/archive/fastzip/zip_fastzip_extractor.go`), which delegates to the third-party `saracen/fastzip` library rather than this in-repo `zip_extract.go` code. I could not fully verify, within the available tool budget, whether `ziplegacy`'s `ExtractZipArchive`/`extractZipSymlinkEntry` is still registered/selected by default, behind a feature flag, or only used for artifact restoration compatibility scenarios (e.g., `commands/helpers/archiver.go`, `cache_extractor.go`, `artifacts_downloader.go` all reference the `archive` package's generic `Extractor` interface, which could resolve to either implementation depending on registration). If this legacy path remains reachable for real artifact/cache downloads (which are fully attacker-controlled — a pipeline author can control the artifact/cache zip contents), the attack is trivially repeatable: craft a zip entry with `os.ModeSymlink` and `Linkname` data set to an absolute path or `../` escape, upload as a job artifact/cache, and have Runner extract it on a subsequent job/stage.

### Recommendation
In `extractZipSymlinkEntry`, validate the symlink target before calling `os.Symlink`: reject absolute paths, and for relative paths compute `filepath.Join(filepath.Dir(file.Name), string(data))`, clean it, and verify (via `filepath.Rel` or a prefix check against the resolved extraction root) that it does not escape the extraction directory. Reject/skip the entry (with a warning, consistent with existing `tracker.actionable` warning pattern) if the target would escape.

### Proof of Concept
```go
func TestExtractZipSymlinkEntry_RejectsEscapingTarget(t *testing.T) {
    dir := t.TempDir()
    require.NoError(t, os.Chdir(dir))

    var buf bytes.Buffer
    zw := zip.NewWriter(&buf)

    hdr := &zip.FileHeader{Name: "evil-link"}
    hdr.SetMode(os.ModeSymlink | 0777)
    w, err := zw.CreateHeader(hdr)
    require.NoError(t, err)
    _, err = w.Write([]byte("/etc/cron.d/malicious"))
    require.NoError(t, err)
    require.NoError(t, zw.Close())

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    err = ExtractZipArchive(zr)
    require.NoError(t, err) // extraction currently "succeeds" without error

    target, err := os.Readlink(filepath.Join(dir, "evil-link"))
    require.NoError(t, err)
    // Expected (after fix): target should be rejected/confined, not absolute/outside dir
    assert.False(t, filepath.IsAbs(target), "symlink target must not be absolute/escape extraction root")
}
```
Expected pre-fix behavior: the assertion fails because `target` is `/etc/cron.d/malicious`, proving the unvalidated symlink target is written as-is.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}
