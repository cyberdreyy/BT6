### Title
Stale confirmations from deleted multisig members still count toward `num_confirmations` threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member()` in `multisig2/src/lib.rs` only purges outstanding requests and confirmation sets for requests that were *originally submitted* by the removed member. It never scans other members' outstanding requests to strip a confirmation the removed member had already cast on them. Because `confirm()` counts raw confirmation-set length against `self.num_confirmations` without validating that every entry in the set still corresponds to a current member, a request can execute using a "confirmation" from an account/key that is no longer part of the multisig.

### Finding Description
`confirm()` determines whether to execute a request purely by set cardinality: [1](#0-0) 

`confirmations` is a `HashSet<String>` keyed by `member.to_string()`, populated whenever a member calls `confirm()` without yet reaching the threshold: [2](#0-1) 

When a member is removed via `DeleteMember`, `delete_member()` is invoked: [3](#0-2) 

The cleanup loop at lines 362-371 filters `self.requests` by `r.member == member`, i.e. it only removes requests (and their confirmation sets) that the *departing* member originally created with `add_request`. It does **not** iterate over `self.confirmations` for requests created by *other* members that the departing member had already confirmed. Any such stale entry — a string equal to `member.to_string()` — remains inside another request's confirmation `HashSet` after `self.members.remove(&member)` deletes them from the live member set.

Because `confirm()`'s threshold check (`confirmations.len() as u32 + 1 >= self.num_confirmations`) only counts set size, it does not re-verify that every prior confirming identity in the set is still `self.members.contains(...)`. The equality the contract is supposed to guarantee — "confirmations counted == confirmations from currently authorized members" — is broken: confirmations counted can exceed confirmations from live members by the number of departed members who confirmed but never triggered execution before being removed.

### Impact Explanation
This allows a multisig request to execute with fewer *live* member confirmations than the configured `num_confirmations`, directly matching the Critical category "a multisig request executed below threshold." Example with `num_confirmations = 2`, members `{A, B, C}`:
1. `A` calls `add_request_and_confirm(X)` → confirmations = `{A}`.
2. `B` calls `confirm(X)` → `1 + 1 = 2 >= 2`? No — with 2 members already `{A}`, adding B gives len 1, +1=2, so it would execute immediately in a 2-of-3 setup only if len+1 reaches threshold; adjust to num_confirmations=3 for a clearer walk-through: members `{A,B,C,D}`, `num_confirmations = 3`.
   - `A` adds+confirms X → confirmations = `{A}`.
   - `B` confirms X → confirmations = `{A,B}` (len 2 < 3, not yet executed).
   - `B` is removed via a separate `DeleteMember{B}` request approved by the required threshold (this is a legitimate governance action, e.g. removing a compromised/departing signer) — `delete_member` does not touch request `X`'s confirmation set because `X.member == A`, not `B`.
   - Now only `A, C, D` are live members, threshold still 3.
   - `C` confirms X → confirmations.len() (2, still containing stale `B`) + 1 = 3 >= 3 → `execute_request` fires, moving funds/actions with effectively only 2 live-member confirmations (`A`, `C`) instead of the intended 3.
3. This lets a transfer, `AddKey`, or `FunctionCall` action execute below the governance-mandated threshold, which for `Transfer` actions directly moves NEAR out of the contract without the required live-member authorization.

### Likelihood Explanation
Requires no attacker-controlled deployment or foundation privilege beyond the ordinary lifecycle every multisig will exercise: creating a request, having it partially confirmed, and later removing a member (turnover, key rotation, compromise response) before that request is cleaned up — all standard, documented flows (`add_request`, `confirm`, `DeleteMember`) reachable by any legitimate member acting in normal order. No malicious code deployment or victim key is needed; the remaining members simply don't realize a stale confirmation is silently counted. The `multisig/src/lib.rs` (v1, key-only) contract has the analogous `remove_request` cleanup restricted to the deleting signer's own requests as well, so the same class of issue is present there too, though multisig2 is the clearer, actively-referenced implementation.

### Recommendation
When deleting a member, iterate all outstanding `confirmations` (not just requests filed by that member) and remove the departing member's string key from every confirmation set. Alternatively, when checking the threshold in `confirm()`, filter `confirmations` to only those entries still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
