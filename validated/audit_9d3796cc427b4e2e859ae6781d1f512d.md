### Title
Hardcoded `TRANSFERS_STARTED` timestamp in `LockupFactory::create` releases lockup tokens earlier than intended - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory` hardcodes the "transfers enabled" timestamp to a fixed constant `1602614338293769340` (13 October 2020) rather than deriving it from the actual transfers-enabled poll result or current time. This is the same bug class as the AuraVault `INFLATION_PROTECTION_TIME` finding: a fixed, past-dated constant is baked into logic that is supposed to represent a moving reference point, silently degrading the schedule every time the code is reused after that date.

### Finding Description
`LockupFactory::create` builds the `LockupArgs` sent to a newly deployed lockup contract. It sets `transfers_information` to `TransfersInformation::TransfersEnabled { transfers_timestamp: TRANSFERS_STARTED }`, where: [1](#0-0) [2](#0-1) 

`TRANSFERS_STARTED` is a hardcoded past timestamp, not derived from `env::block_timestamp()` or any oracle/poll at the time the factory deploys the lockup account.

In the deployed `LockupContract`, this `transfers_timestamp` is combined with the caller-supplied `lockup_duration` to compute the effective unlock (`lockup_timestamp`) via `max(transfers_timestamp + lockup_duration, lockup_timestamp)` in `get_locked_amount`: [3](#0-2) 

The doc comment for `LockupContract::new` explicitly documents the intended formula as `max(transfers_timestamp + lockup_duration, lockup_timestamp)`: [4](#0-3) 

Because `transfers_timestamp` is always anchored to Oct 2020 regardless of when `create()` is actually called, the `lockup_duration` component of the unlock schedule is computed relative to a fixed date in the past rather than relative to the deployment time. The custody binding being broken is: `unlock_timestamp == transfers_enabled_time + lockup_duration`, where `transfers_enabled_time` should track when transfers were actually enabled (or, in this factory-created path, effectively "now"), but instead is permanently pinned to 2020-10-13.

### Impact Explanation
For any lockup created via `LockupFactory::create` that relies on the `lockup_duration` (rather than an explicit `lockup_timestamp`) to gate token release, the effective unlock date is computed as `1602614338293769340 + lockup_duration` — a fixed point that recedes further into the past relative to "now" every day the factory is used. The practical effect mirrors the AuraVault bug: the intended one-time-relative duration decays and eventually reaches zero, causing tokens that are supposed to be locked for `lockup_duration` from deployment to instead unlock immediately (or in the near future) once deployed sufficiently long after Oct 2020. This is an early release of locked tokens, matching the Critical impact category ("locked or unvested tokens released early") since it is a schedule value used by `get_locked_amount`/`get_owners_balance` that other parties (the owner, and by extension any staking/transfer logic) settle on.

### Likelihood Explanation
This triggers automatically, without any attacker action beyond simply calling `create()` on `LockupFactory` (which any account can do by paying `MIN_ATTACHED_BALANCE`) and relying on the default `lockup_duration`-based release path instead of supplying an explicit `lockup_timestamp`. No privileged role, redeploy, or malicious validator is required — it's a direct consequence of the hardcoded constant already being years in the past relative to any realistic deployment/usage date.

### Recommendation
Do not hardcode `TRANSFERS_STARTED` as a fixed past timestamp used to represent "transfers enabled" for freshly created lockups. Either:
- Use the real transfer-poll/vote result for `TransfersInformation::TransfersEnabled` when transfers have genuinely already been enabled network-wide (unaffected by time), or
- If the factory intends "lockup starts counting from now," pass `env::block_timestamp()` at creation time instead of the constant, or require callers to always supply an explicit `lockup_timestamp` and disallow relying on `lockup_duration` alone in this code path.

### Proof of Concept
1. `LockupFactory::create` is called with only `lockup_duration` set (no `lockup_timestamp`), as supported by the API and exercised by `test_create_lockup_success`: [5](#0-4) 
2. The factory deploys the child lockup contract with `transfers_information.transfers_timestamp = TRANSFERS_STARTED = 1602614338293769340` regardless of the current chain time: [2](#0-1) 
3. In the deployed `LockupContract`, `get_locked_amount` computes `lockup_timestamp = max(transfers_timestamp + lockup_duration, lockup_timestamp_arg)`; since `transfers_timestamp` is fixed at 2020-10-13, as real wall-clock time advances past `1602614338293769340 + lockup_duration`, the tokens are already unlocked at the moment of deployment (or shortly after), even though the owner/depositor expects `lockup_duration` to run from the actual deployment date: [6](#0-5)
