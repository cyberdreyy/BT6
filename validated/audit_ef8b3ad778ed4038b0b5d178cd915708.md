Based on my analysis of `multisig/src/lib.rs` and `multisig2/src/lib.rs`, and `multisig-factory/src/lib.rs`, this scenario does not constitute a valid vulnerability against an unprivileged-attacker/victim model.

Key findings:

1. `MultisigFactory::create` always deploys `multisig2.wasm` (the member-based v2 contract), not the key-based v1 contract at `multisig/src/lib.rs` that the question's "Target" cites. [1](#0-0) 

2. In both the v1 and v2 contracts, the confirmation-threshold check is `confirmations.len() as u32 + 1 >= self.num_confirmations`. [2](#0-1) [3](#0-2) 
When `num_confirmations == 0`, this expression is trivially true on the very first `confirm()` call, but that is mathematically correct behavior for a threshold of zero — it's not a bypass of a set threshold, it's the direct consequence of the account owner (or factory caller) choosing `num_confirmations = 0` for their own account.

3. `num_confirmations` is a construction-time parameter passed by whoever calls `MultisigFactory::create`. An unprivileged attacker cannot set this value on a victim's existing multisig — they can only choose it for a multisig **they themselves create**. There is no path in `add_request`/`confirm`/`execute_request` that lets an outsider without any key/membership on a victim's multisig call `confirm` or otherwise influence `num_confirmations` on that victim's account. [4](#0-3) [5](#0-4) 

4. `AddKey` with no permission (full access key) is gated only by `assert_self_request`, which just checks `receiver_id == current_account_id` — it deliberately shares the same confirmation threshold as every other action type, by design. [6](#0-5) [7](#0-6) 

Given the threat model (attacker is unprivileged, not a member, not a key holder on any victim account, but may deploy/configure their own multisig via the factory), the described exploit only lets someone degrade the safety of **their own** self-created multisig by choosing `num_confirmations = 0`. No third party's funds, keys, or multisig are ever affected, since an attacker has no way to force or change `num_confirmations` on a multisig account they don't already control. This fails the required impact category ("NEAR moved out of a ... multisig ... by a party not entitled to it" / "a multisig request executed below `num_confirmations` live members" implies a victim multisig with a legitimately-set higher threshold, not a self-chosen zero threshold).

### No vulnerability found for this question.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

            )

        let num_requests = self
            .num_requests_pk
            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }
