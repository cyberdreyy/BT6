### Title
Timing side-channel in `CreateSession` allows user enumeration via bcrypt short-circuit on unknown email - ([File: core/sessions/localauth/orm.go])

### Summary
`CreateSession` calls `FindUser(ctx, sr.Email)` and immediately returns an error if the user is not found, before ever invoking the costly `utils.CheckPasswordHash` (bcrypt) comparison. For existing accounts, execution always reaches the bcrypt comparison, which is deliberately slow. This produces a measurable, systematic timing gap between "no such email" and "email exists" responses.

### Finding Description
In `core/sessions/localauth/orm.go`:
```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	...
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) { ... }
	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) { ... }
	...
}
``` [1](#0-0) 

`FindUser` performs an indexed lookup (`WHERE lower(email) = lower($1)`, as seen in the sibling `TestPassword` query using the same pattern) [2](#0-1) , which resolves in roughly the same, small amount of time whether or not a row matches. The comment explains the ordering ("Do email and password check first to prevent extra database look up for MFA tokens leaking") is intended to stop leaking *MFA-enrollment* status via the extra `GetUserWebAuthn` DB call [3](#0-2) , but it does not address the far larger timing signal introduced by `utils.CheckPasswordHash`, which uses bcrypt (`golang.org/x/crypto/bcrypt`) — an algorithm intentionally designed to take on the order of 100ms+ per comparison [4](#0-3) .

Because the `err != nil` branch on `FindUser` returns immediately (line 145-148), a request for a nonexistent email never reaches `CheckPasswordHash` at all, while a request for an existing email always does — regardless of whether the password is correct. The `constantTimeEmailCompare` check only executes after `FindUser` has already succeeded, so it cannot mask the fact that `FindUser` failed for unknown emails; it only guards against case-mismatch timing once a user record is loaded. The `sessions_controller_test.go`/`POST /sessions` route in `core/web` exercises this exact function directly from an unauthenticated request, confirming the code path is reachable by any unauthenticated attacker [5](#0-4) .

### Impact Explanation
An unauthenticated attacker can distinguish "email exists" from "email does not exist" by measuring response latency of `POST /sessions`: nonexistent emails return fast (DB miss only), existing emails are always slower (DB hit + bcrypt compare). This is a user/account enumeration side channel. It does not itself grant authentication bypass, session hijack, or credential disclosure — it only leaks account existence, which the code's own comment shows the developers consider worth defending against for the related MFA-status leak, but the same rationale extends to email existence.

### Likelihood Explanation
No credentials or privileges are required — the `/sessions` POST endpoint is unauthenticated by design. Exploitation requires only network access and repeated timing measurements (statistical averaging over many requests to overcome noise), which is standard practice for this class of side channel. The vulnerability is deterministic in the code (bcrypt always more expensive than a DB-miss lookup) so it is reliably repeatable given enough samples to average out network/DB jitter.

### Recommendation
Perform a dummy `bcrypt` comparison (or equivalent, constant-cost work) for the "user not found" branch before returning, so that the total time spent for a nonexistent email approximates the time spent for an existing one with a wrong password. Alternatively, restructure `CreateSession` to always run `CheckPasswordHash` against a fixed/dummy hash when `FindUser` fails, only branching on outcome after both paths have incurred equivalent bcrypt cost.

### Proof of Concept
Go benchmark/integration test plan:
1. Seed one real user via `orm.CreateUser` with a known bcrypt-hashed password (as in `TestORM_CreateSession`) [6](#0-5) .
2. In a loop (e.g., 100 iterations), call `orm.CreateSession(ctx, sessions.SessionRequest{Email: existingEmail, Password: "wrongpassword"})` and record elapsed time; separately call with `Email: "nonexistent@test.org", Password: "wrongpassword"` and record elapsed time.
3. Compute median/average durations for both groups.
4. Assert that the "existing email + wrong password" group's average duration is significantly greater (e.g., >50ms difference, consistent with bcrypt cost) than the "nonexistent email" group, demonstrating the observable timing oracle. A fixed test would assert the two durations are within a small tolerance (e.g., <5ms) after adding dummy-hash comparison mitigation.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
