### Title
Cross-job unauthorized run trigger via External Initiator credentials lacking job-binding check - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` and its routing in `core/web/router.go` authenticate requests via `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`, then only check `isUser` and role via `RequiresRunRole` before executing `App.RunJobV2(ctx, jobID, nil)` for any numeric job ID supplied in the URL. Because `AuthenticateExternalInitiator` injects a synthetic `clsessions.User{Role: UserRoleRun}` into `SessionUserKey` regardless of which job the EI was registered against, `GetAuthenticatedUser` returns `isUser == true` for any valid EI credential, and `Create` never consults `auth.GetAuthenticatedExternalInitiator(c)` or the target job's external-initiator bindings to verify the EI is authorized for that specific job.

### Finding Description
The route is registered as: [1](#0-0) 

`AuthenticateExternalInitiator` looks up the EI by header credentials and, on success, unconditionally sets a generic run-role user object into the session, independent of any job ID: [2](#0-1) 

`RequiresRunRole` only checks that `user.Role != UserRoleView` — it has no notion of "which job" the caller is permitted to run: [3](#0-2) 

In `Create`, the only gate is `_, isUser := auth.GetAuthenticatedUser(c)`, which is `true` for both real session/token users and for any EI (since the synthetic user object satisfies the type assertion). Once `isUser` is true, the numeric job ID from the URL path is parsed and passed straight to `App.RunJobV2(ctx, jobID, nil)` with no cross-check against the authenticated EI's registered job(s): [4](#0-3) 

The controller never calls `auth.GetAuthenticatedExternalInitiator(c)` to retrieve the actual `*bridges.ExternalInitiator` and compare it against the target job's `ExternalInitiatorSpec`/external initiators list, so there is no enforcement of the invariant that a request must be attributable to exactly one authorized job for that specific EI.

### Impact Explanation
Any holder of a valid EI credential — which is a scoped, low-privilege credential meant to trigger runs only for job(s) it was explicitly registered against — can trigger pipeline runs on **any** job reachable by numeric ID, including jobs it was never bound to. This is unauthorized job execution across job/tenant boundaries: an EI meant for job A can execute job B's pipeline (potentially causing unintended fund movement, oracle report submission, or other side effects tied to job B's tasks), matching the Chainlink bounty impact class of "unauthorized job run" / authorization bypass.

### Likelihood Explanation
The only precondition is possession of one valid EI credential (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers matching any `bridges.ExternalInitiator` row) — no admin/edit privileges, no knowledge of other jobs' EI bindings, and no special network position are required. The attack is a single `POST /v2/jobs/<anyNumericJobID>/runs` request and is fully repeatable against any job whose ID is guessed or discovered (job IDs are small sequential integers exposed via `GET /v2/jobs`).

### Recommendation
In `PipelineRunsController.Create`, when the authenticated principal is an External Initiator (detected via `auth.GetAuthenticatedExternalInitiator(c)`), look up the target job's associated external initiator(s)/spec and reject the request (403) unless the authenticated EI matches the job's registered initiator. Do not rely solely on the synthetic `UserRoleRun` flag to authorize job execution for EI-authenticated requests; instead thread the EI identity through to an explicit binding check against the job record before calling `RunJobV2`.

### Proof of Concept
Go handler-level integration test plan:
1. Create two webhook-capable jobs, Job A and Job B, each via the jobs API.
2. Create one `bridges.ExternalInitiator` (EI-A) and register/bind it only to Job A (however job/EI association is modeled, e.g. via the job's webhook spec `ExternalInitiators` list).
3. Using EI-A's `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, send `POST /v2/jobs/<jobB.ID>/runs`.
4. Assert the response is non-2xx (expected: 403 Forbidden after fix; currently returns 200 with a created pipeline run resource, demonstrating the bug).
5. Query `pipeline_runs` for `jobB.ID` and assert zero new rows were inserted as a result of EI-A's request (currently a row is inserted, confirming unauthorized execution).

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
