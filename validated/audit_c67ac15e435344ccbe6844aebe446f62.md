### Title
Unprivileged ERC4626 vault user can block `stopEpoch` via liquidity drain, freezing pending withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The analog of the Renovate injection bug is untrusted, attacker-influenced external input flowing unsanitized into a trusted control-flow sink: `ProgrammableBorrower.onStopEpoch` lets the configured ERC4626 vault's live withdrawable liquidity decide whether `IdleCDOEpochVariant.stopEpoch` succeeds or reverts. Any unprivileged user of that vault (an explicitly allowed attacker class) can drain its available liquidity so that `vault.withdraw` reverts, causing `StopEpochVaultLiquidityUnavailable` to bubble up and revert the entire `stopEpoch` call. Repeated each time the manager retries, this indefinitely freezes epoch settlement and all pending withdraw requests.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` calls `IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, _isRequestingAllFunds)` and requires `true` to proceed [1](#0-0) . Inside `onStopEpoch`, when on-hand cash is insufficient, the code attempts `vault.withdraw(shortfall, ...)` inside a try/catch, and on catch reverts with `StopEpochVaultLiquidityUnavailable` [2](#0-1) . The comment explicitly says "Hook reverts bubble so transient ERC4626 liquidity failures can be retried," confirming the failure is propagated, not contained.

The vault's available liquidity is fully attacker-influenced: in share-based lending vaults (e.g., Morpho-style ERC4626) any user can withdraw their own shares or borrow the free liquidity, making `vault.withdraw(shortfall)` revert even though `convertToAssets` still reports full value. Because `_currentVaultAssets()` uses `convertToAssets` (which counts lent-out assets), the early-out `if (shortfall > _currentVaultAssets()) return true` does not trigger — the position is solvent but illiquid [3](#0-2) . The revert then bubbles through `onStopEpoch` and reverts the whole `stopEpoch`, leaving `isEpochRunning = true`, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` states unchanged, and every receipt in `withdrawsRequestsByEpoch` unclaimable.

The attack is cheap to repeat: the attacker front-runs each `stopEpoch` attempt by borrowing/withdrawing vault liquidity in the same block, and restores it afterward — pure MEV gas cost plus transient capital, while lenders' funds stay locked. There is no fallback path: `emergencyExitVault` is owner-only and itself calls `vault.redeem`, which fails identically under drained liquidity [4](#0-3) .

### Impact Explanation
Temporary freezing of funds, quantified: all pending withdraw requests (`_pendingWithdraws`) plus the full pool NAV remain locked for as long as the attacker sustains liquidity drainage — each manager retry costs the attacker only one block of vault liquidity plus gas. Tranche holders cannot request new withdrawals (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` remain off once the epoch stalls past `epochEndDate` in the failed-stop state), and borrower interest keeps accruing to the borrower's benefit at `borrowerApr` while lenders' claims are frozen. This is a direct fund-impact DoS, not gas-only.

### Likelihood Explanation
Requires only an unprivileged account interacting with the external ERC4626 vault — no role, KYC, or protocol permission. Preconditions: programmable-borrower mode with an ERC4626 vault whose free liquidity can be manipulated (standard for lending-market vaults), and an active epoch with `_amountToPullFromBorrower + _pendingWithdraws` exceeding the PB contract's idle cash. No existing guard stops it: `nonReentrant` doesn't help (attacker never enters the PB contract), `_checkOnlyIdleCDO` gates only the hook caller, and the skim/default flags are downstream of the revert point.

### Recommendation
Do not let external vault liquidity failures bubble as hard reverts that block epoch settlement. Options: (a) treat an ERC4626 `withdraw`/`redeem` failure as `success = false` so IdleCDO routes through `_handleBorrowerDefault` rather than a repeatable revert; (b) pull only the liquidity actually available (`min(shortfall, vault.maxWithdraw(address(this)))`) and let the subsequent `transferFrom` shortfall drive the default decision; (c) keep the revert path but make stopEpoch resumable without re-executing the vault withdrawal, e.g., record the recall demand so a later call only retries the transfer.

### Proof of Concept
Reproducible Foundry fork test (scaffold on `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, which already deploys a Morpho-style vault):

```solidity
// Setup: programmable mode, depositAA(amount), start epoch, request AA withdraw.
// attacker = EOA holding vault shares (or borrowing vault liquidity).

// 1. Manager calls stopEpoch at epochEndDate -> succeeds normally (baseline).

// 2. Attack: in one tx before each stopEpoch attempt:
vm.startPrank(attacker);
vault.borrow(liquidityAvailable); // or vault.withdraw(attackersShares)
vm.stopPrank();

vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(newApr, 0);

assertTrue(cdoEpoch.isEpochRunning());          // epoch never settles
// pending withdraw receipt unclaimable:
vm.expectRevert(); // or returns 0
IdleCreditVault(strategy).claimWithdrawRequest(...);

// 3. Attacker repays/redeposits; repeat step 2 for every retry -> indefinite freeze.
```

Uncertainty noted: the exact share-vault liquidity mechanics depend on the concrete ERC4626 integration (the test suite uses a Morpho-like vault); on a vault where `convertToAssets` already reflects illiquidity, the `shortfall > _currentVaultAssets` early-out could route to `return true` and force a spurious borrower default instead — an equally severe outcome (honest borrower defaulted, pool paused) reachable by the same unprivileged manipulation.

    if (_shares == 0) {
