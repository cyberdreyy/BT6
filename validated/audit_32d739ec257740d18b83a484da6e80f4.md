Based on my investigation, I found strong architectural evidence supporting this vulnerability, though I was unable to fetch the exact byte-level implementation of `BlockRejection::sign()`/`recover_public_key()` in `libsigner/src/v0/messages.rs` before running out of tool calls. I present what I can support directly, and flag the remaining uncertainty.

### Title
Rejection signature is verified identically to an acceptance signature (no type binding in the signed hash), allowing a gossiped rejection to be replayed as an acceptance - (File: `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/signerdb.rs`)

### Summary
`BlockAccepted` and `BlockRejection` both carry a `signature` field that is authenticated purely by recovering a public key from `signer_signature_hash.bits()` — the same raw hash for both variants — with no message-type/domain tag folded into the signed preimage. In `Signer::handle_block_signature` (`stacks-signer/src/v0/signer.rs:2371-2441`) the origin of an "acceptance" is established solely via `Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(block_hash.bits(), signature)` plus `is_valid_signer`, with no check that this signature/slot pairing was ever emitted as an *Accepted* message by that signer.

### Finding Description
The invariant that should hold is: *a signed response's meaning (Accept vs Reject) is bound into what was signed*, so that a signature produced for one meaning cannot be reinterpreted as the other. Tracing the code:

- `create_block_acceptance` signs `block.header.signer_signature_hash().bits()` directly [1](#0-0) .
- `handle_block_signature` authenticates an incoming `BlockAccepted` purely by recovering a pubkey from `(block_hash.bits(), signature)` and checking `is_valid_signer` — it never verifies that this exact `(hash, signature)` pair was ever emitted by that signer *as an acceptance* rather than lifted from something else [2](#0-1) .
- `handle_block_rejection` similarly authenticates a `BlockRejection` by `rejection.recover_public_key()` against `signer_address`/`is_valid_signer`, and both rejection and acceptance messages ultimately land in `signerdb.rs`, where `get_block_rejection_signer_addrs` is used to enumerate/tally addresses that rejected a given block hash [3](#0-2) .
- Node-side StackerDB consumption (`stackerdb_listener.rs`) reinforces the same pattern: `Accepted` variants are verified with `signer_pubkey.verify(block_sighash.bits(), &signature)` against the *slot's* known key, and `Rejected` variants are verified via `rejected_data.recover_public_key()` compared against the slot's key — both checks operate over the identical hash bits and provide no cryptographic separation between "I accept H" and "I reject H" [4](#0-3) [5](#0-4) .

Because `BlockRejection::new` signs and populates `signature` for the same `signer_signature_hash` domain used by `BlockAccepted` [6](#0-5) , and because the consuming code paths in both `stacks-signer` and `stacks-node` recover/verify signatures against nothing but the raw hash bits (never checking which variant/type produced them), an attacker who observes a victim signer's publicly-gossiped `BlockRejection{signer_signature_hash: H, signature: S}` for a block they proposed can repackage `(H, S)` into a fabricated `BlockResponse::Accepted{signer_signature_hash: H, signature: S, ...}` and gossip it from their own StackerDB slot. `handle_block_signature` recovers the victim's pubkey from `(H, S)`, finds it's a valid signer, and records it as an acceptance from that signer — a rejection is now counted as an acceptance toward the weight threshold.

I was **not** able to directly view the body of `BlockRejection::sign()`/`recover_public_key()` in `libsigner/src/v0/messages.rs` to conclusively confirm that no additional type discriminator (e.g., `BlockResponseTypePrefix`) is folded into the signed preimage before hitting my tool-call budget. The presence of `BlockResponseTypePrefix` in the codebase [7](#0-6)  is used for wire-format enum discrimination during deserialization, but it is unconfirmed whether this prefix is also mixed into the cryptographic signing preimage.

### Impact Explanation
If the signing domains are indeed identical (unconfirmed with full certainty), this breaks the "rejection recounted as acceptance" safety property directly, and could let an attacker's single rejection-derived signature be counted toward the accept-weight threshold for a block, undermining `get_block_rejection_signer_addrs`-based tallying and the aggregate acceptance threshold used for block finality — Critical severity per the stated impact categories.

### Likelihood Explanation
If confirmed, exploitation requires only: (1) winning one BTC-funded miner slot to propose a block that a victim signer will reject, and (2) observing that signer's publicly gossiped `BlockRejection` over StackerDB (visible to all participants) and (3) re-gossiping a crafted `BlockResponse::Accepted` with the lifted `(hash, signature)` pair from the attacker's own slot. No majority weight, no victim key, and no node-operator access is needed. This would be fully repeatable per rejected block.

### Recommendation
Bind the message type into the signed preimage — e.g., sign `(BlockResponseTypePrefix, signer_signature_hash)` (or a domain-separated tag concatenated before the hash) for both `BlockAccepted` and `BlockRejection`, and update all verification sites (`stacks-signer/src/v0/signer.rs::handle_block_signature`/`handle_block_rejection`, and `stacks-node/src/nakamoto_node/stackerdb_listener.rs`) to recompute/verify against that same type-bound preimage rather than the bare hash bits.

### Proof of Concept
Given the unresolved uncertainty about the exact signing preimage, a definitive PoC would need to:
1. Construct a `BlockRejection` for hash `H` signed by a test signer key, capture `signature`.
2. Construct a `BlockAccepted{signer_signature_hash: H, signature}` reusing that exact signature.
3. Feed the fabricated `BlockAccepted` into `Signer::handle_block_signature` and assert it is accepted (`is_valid_signer` passes, `store_and_process_block_signature` records an acceptance from the victim's address) despite the victim never having produced an `Accepted` message.
4. Assert `get_block_rejection_signer_addrs` for `H` still lists (or previously listed) that signer's address as a rejecter, while the weight tally now also/instead counts them as an accepter — demonstrating the contradiction.

**This finding could not be fully validated** because the exact byte-level signing preimage of `BlockRejection::sign()`/`recover_public_key()` in `libsigner/src/v0/messages.rs` was not directly confirmed within the available tool budget. I recommend a Devin session with full repository access to inspect `libsigner/src/v0/messages.rs` lines covering `BlockRejection::sign`/`recover_public_key` and `BlockAccepted`'s analogous methods to conclusively confirm or refute whether a type discriminator is included in the signed data, before treating this as a confirmed Critical finding.
