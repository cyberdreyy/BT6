### Title
Instant-withdraw claims pay out from strategy-held epoch deposits before they are borrower-funded — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`claimInstantWithdrawRequest` pays a user's full `instantWithdrawsRequests` balance immediately, at par, from whatever underlying the strategy currently holds — with no check that the instant-withdraw queue was actually funded via `collectInstantWithdrawFunds` (which only runs at epoch start, pulling `pendingInstantWithdraws` from the IdleCDO). Between epochs (buffer phase) the strategy custodies all LP deposits (`deposit()` does `safeTransferFrom` into `address(this)`), so an unprivileged lender can request an instant withdraw and claim in the same block, draining next-epoch principal, while `pendingInstantWithdraws` still forces the CDO to fund the same receipt again at `startEpoch`.

### Finding Description
The flow:

1. `deposit()` moves underlying into the strategy and mints strategy tokens to the CDO; funds stay in the strategy until epoch start (`IdleCreditVault.sol:596-617`).
2. `requestInstantWithdraw` burns CDO strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[user]` and `pendingInstantWithdraws` (`:356-375`).
3. `claimInstantWithdrawRequest` has **no funding/epoch gate**: it pays `instantWithdrawsRequests[user]` via `_transferFundedClaim` straight from the strategy balance (`:380-393`). The CDO wrapper in `IdleCDOEpochVariant.claimInstantWithdrawRequest` only checks the `allowInstantWithdraw` flag — there is no "epoch started / funds collected" check (`IdleCDOEpochVariant.sol:975-979`).
4. At the next `startEpoch`, the CDO calls `collectInstantWithdrawFunds(pendingInstantWithdraws)` which debits the still-nonzero `pendingInstantWithdraws` and pulls the same amount from the CDO (`:398-403`), double-sourcing the receipt: once from strategy-held deposits (theft), once from CDO liquidity.

Net effect: the attacker extracts instant liquidity that was never provisioned, and the same receipt is funded twice. If the CDO cannot cover the pull, `startEpoch` reverts and the pool is frozen.

### Impact Explanation
Direct theft of underlying equal to the attacker's instant-withdraw request, taken from deposits destined for the borrower, followed by a duplicate obligation (`pendingInstantWithdraws`) on the CDO. Broken invariant: one receipt → one funding source → one payout. Loss is bounded by the attacker's deposit but scales with repeated deposits across buffers.

### Likelihood Explanation
Requires `allowInstantWithdraw` enabled and a buffer phase where the strategy holds underlying (the normal state between stopEpoch and startEpoch). Any KYC-passed tranche holder can deposit, request, and claim atomically before the epoch starts; no privileged actor needed.

### Recommendation
Track funded vs. unfunded instant claims: only pay `claimInstantWithdrawRequest` amounts that were actually collected via `collectInstantWithdrawFunds` (e.g., gate claims on a per-epoch funded flag, or decrement `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` when paying unfunded claims), and/or revert claims while the current-epoch instant bucket remains unfunded.

### Proof of Concept
Foundry fork sketch (mirror `test/foundry/IdleCreditVault.t.sol` setup with `allowInstantWithdraw = true`):

```solidity
// buffer phase: deposits sit in `strategy`
idleCDO.depositAA(100_000 * ONE_SCALE);          // attacker + honest LPs
uint256 attackerShares = AA.balanceOf(attacker);

vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(attackerShares); // receipt minted, pendingInstantWithdraws += X

vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();          // pays X from strategy-held deposits NOW

// at startEpoch, CDO is charged again for pendingInstantWithdraws == X
vm.prank(manager);
cdoEpoch.startEpoch();                           // collectInstantWithdrawFunds pulls X from CDO
// => attacker paid once from deposits, CDO pays again => net drain / insolvency
```

I was unable to exhaustively verify whether `IdleCDOEpochVariant.requestInstantWithdraw` gates requests to specific phases or prefunds claims through a separate path — if requests are only allowed while an epoch is running *and* the strategy holds no claimable underlying, the drain is unreachable and this reduces to a funded-queue reordering. That gating should be confirmed before reporting.
