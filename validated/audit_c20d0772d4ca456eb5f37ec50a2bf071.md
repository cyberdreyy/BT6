### Title
Reject-then-Accept from the same signer double-counts weight into both `total_weight_approved` and `total_weight_rejected` - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tracks per-block consensus with a single `BlockStatus` holding two *independent* weight accumulators, `total_weight_approved` and `total_weight_rejected`, plus two *different* de-duplication sets: `gathered_signatures` (keyed by slot_id, guards the accept path) and `responded_signers` (a `HashSet<u32>`, guards the reject path but is also unconditionally populated by the accept path). [1](#0-0) 
Because the accept path checks `gathered_signatures` while the reject path checks `responded_signers`, a signer that rejects a block first and later legitimately re-evaluates to accept the same block causes its weight to be added to *both* tallies.

### Finding Description
On `BlockResponse::Accepted`, the weight is added only if the slot is not yet in `gathered_signatures`, after which both `gathered_signatures` and `responded_signers` are populated: [2](#0-1) 

On `BlockResponse::Rejected`, the weight is added only if `responded_signers.insert(slot_id)` returns `true` (i.e., first time this slot has "responded" at all): [3](#0-2) 

Evaluate both orderings for the same signer/slot on the same block:

- **Accept → Reject:** Accept adds to `total_weight_approved`, inserts into `gathered_signatures` and `responded_signers`. The later Reject checks `responded_signers.insert(slot_id)`, which returns `false` (already present) — the reject weight is correctly *not* added. No double count.
- **Reject → Accept:** Reject checks `responded_signers.insert(slot_id)`, which returns `true` (first time) — `total_weight_rejected` is incremented and `responded_signers` now contains the slot. The later Accept checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` because the reject path never touches `gathered_signatures` — so `total_weight_approved` is *also* incremented for the same signer weight, and only then is the slot added to `gathered_signatures`.

The result: a single signer's weight is now counted in both `total_weight_approved` and `total_weight_rejected` simultaneously for the same block, breaking the invariant that the two tallies represent disjoint, mutually-exclusive sets of signer weight.

Critically, `Reject → Accept` for the *same block* is not a contrived edge case — it is the documented, legitimate signer state-machine transition `LocallyRejected → LocallyAccepted : re-evaluated` (a signer may reject a block because of a transient conflict, then re-evaluate and sign it once the conflict goes stale): [4](#0-3) 
Any signer that rejects, then later re-signs the same proposal (e.g. after a conflicting sibling block becomes stale, per the pre-commit re-check flow in `signer.rs`) will trigger this on the node's coordinator listener.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality the coordinator relies on: `total_weight_approved` no longer reflects the true weight of signers who currently endorse the block, because it can include weight from a signer that also currently appears in `total_weight_rejected`. In `signer_coordinator.rs`, the acceptance/rejection decision is made purely from these two counters (`block_status.total_weight_approved >= self.weight_threshold` and `block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight`): [5](#0-4) 
A single signer's double-counted weight can push `total_weight_approved` over threshold with less genuine independent signer support than the weight number implies, or inflate the rejection tally beyond what a rejecting quorum actually holds — i.e., a rejection's weight is effectively still "alive" and reused to help satisfy acceptance. This matches the report's root cause pattern (a single shared balance being drawn against by two supposedly-independent accounting paths) mapped onto signer weight instead of token balance.

### Likelihood Explanation
Requires only a single signer (one slot) to send a Reject message followed later by an Accept/signature message for the same block — a flow the signer's own local state machine already performs whenever a locally-rejected block is re-evaluated and later signed (`LocallyRejected → LocallyAccepted`). No majority collusion, no additional key material, and no StackerDB protocol violation is needed; it is triggered by normal signer behavior under conflict-then-resolution conditions, or trivially by a byzantine (but otherwise valid, single-key) signer that deliberately reorders its own messages.

### Recommendation
Use a single authoritative per-slot "current verdict" state (e.g., an enum `Accepted(sig)`/`Rejected` keyed by slot_id) instead of the two independently-guarded sets `gathered_signatures` and `responded_signers`. When a slot transitions from Rejected to Accepted (or vice versa), first subtract the previously counted weight from the old tally before adding it to the new one, so a given slot's weight only ever contributes to exactly one of `total_weight_approved` / `total_weight_rejected` at a time.

### Proof of Concept
1. Node creates a `BlockStatus` for block `B` with `total_weight_approved = 0`, `total_weight_rejected = 0`, empty `responded_signers`/`gathered_signatures`.
2. Signer `S` (slot `k`, weight `w`) sends `BlockResponse::Rejected` for `B`.
   - `responded_signers.insert(k)` → `true` → `total_weight_rejected += w`.
3. Signer `S` later re-evaluates locally (as permitted by `LocallyRejected → LocallyAccepted`), signs `B`, and its acceptance/signature message for `B` reaches the node.
   - `gathered_signatures.contains_key(&k)` → `false` (never set on the reject path) → `total_weight_approved += w`.
   - `gathered_signatures.insert(k, sig)`; `responded_signers.insert(k)` (no-op, already present).
4. Final state: `total_weight_rejected = w` and `total_weight_approved = w` from the same signer's weight `w`, simultaneously — the two supposedly disjoint tallies both contain `S`'s weight, which the coordinator in `signer_coordinator.rs` uses directly to decide accept/reject.
