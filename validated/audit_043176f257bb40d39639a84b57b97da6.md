### Title
Stale confirmations from removed multisig keys count toward quorum, allowing a request to execute below the live-member threshold - ([File: multisig/src/lib.rs])

### Summary
The multisig contract's `DeleteKey` action removes an access key from the account but only purges pending requests that key *itself created* — it never removes confirmations that key placed on *other* requests. Because `confirm()` counts raw confirmation-set size against `num_confirmations` without verifying that each confirming public key is still a live key on the account, a request confirmed by a key that is later deleted can still execute later using that now-invalid confirmation to satisfy quorum, effectively lowering the number of *live* members whose approval was actually required.

### Finding Description
`confirm()` reads the stored confirmation set for a request and checks only its cardinality against `self.num_confirmations`: [1](#0-0) 

The `DeleteKey` action handler in `execute_request` cleans up state for the deleted key, but the cleanup is scoped only to requests where the key is the **originating signer** (`r.signer_pk == pk`); it does not scan `self.confirmations` for entries where the deleted key appears as a *confirmer* of someone else's request: [2](#0-1) 

`remove_request`, used both by `confirm()` (on quorum reached) and by `DeleteKey`, likewise never validates that the public keys inside a request's confirmation `HashSet` are still valid keys on the account — it just counts them: [3](#0-2) 

Consequently the binding the contract is supposed to enforce — *"a request executes only once `num_confirmations` distinct live members approved it"* — breaks into:

`recorded confirmations (including keys removed after confirming) >= num_confirmations` while `live confirming members < num_confirmations`.

### Impact Explanation
This lets a pending `Transfer` (or any other) request execute while having fewer live-member approvals than the configured threshold, i.e. **a multisig request executed below threshold**, one of the explicitly listed Critical impacts. NEAR held by the multisig account can be moved out with less authorization than the account's own security policy (`num_confirmations`) requires.

### Likelihood Explanation
The trigger sequence is a normal, supported multisig workflow — creating a request, having it partially confirmed, and later rotating out a key via `DeleteKey` (e.g., because the key holder left, or the key was suspected compromised) — with no unusual permissions, redeploys, or external actors required. Any surviving member benefits from the stale confirmation without additional action; it just needs one more live confirmation to reach the counted threshold instead of the intended number of live approvals. No key theft, social engineering, or malicious validator is needed, only the deletion of a key that had previously confirmed an unrelated still-pending request.

### Recommendation
When executing `DeleteKey` (or `DeleteMember` in multisig2), iterate over all active `confirmations` entries (not just requests where the key is `signer_pk`) and remove the deleted key/member from every confirmation set, re-checking whether the request should remain pending. Alternatively, when counting confirmations in `confirm()`/quorum checks, filter the confirmation set against the currently valid key/member set before comparing to `num_confirmations`, so confirmations from now-removed keys never count.

### Proof of Concept
1. Deploy `multisig` with keys `{A, B, C}` and `num_confirmations = 2` (`MultiSigContract::new(2)`, keys added via `AddKey`).
2. `A` calls `add_request` to create a `Transfer` request (`request_id = 1`) to some attacker-controlled receiver. No auto-confirm.
3. `B` calls `confirm(1)`. `confirmations = {B}`; since `0 + 1 < 2`, the request stays pending (see `confirm()` logic at `multisig/src/lib.rs:255-265`).
4. `A` and `C` create and confirm a separate `DeleteKey { public_key: B }` request targeting `alice()`/the multisig account itself, reaching quorum (2 confirmations) and executing it. The `DeleteKey` branch (`multisig/src/lib.rs:198-216`) removes `B`'s access key and clears only requests where `signer_pk == B` — request `1` (created by `A`, merely confirmed by `B`) is untouched, and `B`'s stale confirmation remains inside `self.confirmations.get(&1)`.
5. `A` calls `confirm(1)`. `confirmations` currently `= {B}` (stale), so `len() + 1 = 2 >= num_confirmations (2)` — the request executes and the `Transfer` is sent, even though only one currently-live key (`A`) actually approved it after `B` was removed.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
