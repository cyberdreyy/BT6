Confirmed: no `increaseAllowance`/`decreaseAllowance` variants exist anywhere in this codebase — `approve()` is the only allowance-mutation entrypoint across both B20 asset and stablecoin precompiles (v1 and v2).

### Title
B20 token `approve()` overwrites allowance by absolute value, enabling the classic front-run double-spend of allowance - (File: `crates/common/precompiles/src/b20_asset/logic/v2.rs`)

### Summary
The `approve` implementation shared across the B20 Asset and Stablecoin precompiles (v1 and v2) sets a spender's allowance to an absolute new value with no reference to the previously observed allowance, and the codebase provides no `increaseAllowance`/`decreaseAllowance` alternative. This is structurally the same class of bug as the reported `OlympusTreasury.setDebt` issue: an admin/owner action that unconditionally overwrites a spending-limit variable can be front-run by the already-approved, non-admin party (the spender) to extract more value than the owner ever intended to authorize.

### Finding Description
`approve()` calls `token.accounting_mut().set_allowance(caller, spender, amount)` directly, replacing whatever allowance previously existed: [1](#0-0) 

The same unconditional overwrite pattern appears in the v1 Asset logic, and in both v1 and v2 of the Stablecoin logic: [2](#0-1) [3](#0-2) [4](#0-3) 

`transfer_from` consumes the allowance by reading the current stored allowance and writing back `allowance - amount`, so a spender transaction that lands before the owner's `approve` re-write consumes against the *old* allowance in full, and the owner's pending `approve` transaction then independently re-establishes a *fresh* allowance on top: [5](#0-4) 

There is no `increaseAllowance`/`decreaseAllowance`-style delta API anywhere in the repository to avoid this — `approve` is the only mutator exposed on the ABI surface for both the Asset and Stablecoin variants: [6](#0-5) 

### Impact Explanation
An owner who calls `approve(spender, newAmount)` to *reduce* (or *increase*) a spender's allowance can have that transaction front-run by the spender (an unprivileged, previously-approved account, not an admin) in the public mempool/txpool. The spender first calls `transferFrom` to drain the old allowance, then lets the owner's `approve` transaction land, giving the spender a second, independent budget equal to the new allowance. The total amount extracted (`oldAllowance + newAmount`) can exceed what the owner ever intended to authorize at any single point in time, resulting in direct, unauthorized token theft from the owner's balance — the same "loss-of-funds via stale-value overwrite front-run" outcome described in the source report, mapped onto B20 token allowances instead of `OlympusTreasury` debt accounting.

### Likelihood Explanation
This requires only a standard unprivileged, already-approved spender (any address the owner has ever given a nonzero allowance to) monitoring the txpool for the owner's `approve` call and racing it with a `transferFrom`/`transferFromWithMemo` call — both are ordinary signed transactions reachable through the public B20 precompile dispatch path, no special role or admin privilege is required by the attacker. This is the same MEV/front-running pattern well known for standard ERC-20 `approve`, and it is fully reachable on Base's public mempool/block-building path for every B20 Asset and Stablecoin token instance.

### Recommendation
Add `increaseAllowance(spender, addedValue)` and `decreaseAllowance(spender, subtractedValue)` entrypoints (matching OpenZeppelin's mitigation for the same class of bug) that adjust the stored allowance relative to its current value rather than overwriting it, and document/encourage their use instead of `approve` for any allowance change other than an initial 0→N grant. Alternatively, make `approve` revert unless the caller-supplied "expected current allowance" matches the on-chain value (compare-and-swap semantics), directly mirroring the fix recommended for `OlympusTreasury.setDebt`.

### Proof of Concept
1. Owner Alice has previously called `approve(Bob, 500)` on a B20 Asset/Stablecoin token — allowance(Alice, Bob) = 500.
2. Alice decides to reduce Bob's allowance and submits `approve(Bob, 0)`.
3. Bob observes Alice's pending `approve(Bob, 0)` transaction in the mempool and front-runs it with `transferFrom(Alice, Bob, 500)`, which succeeds because it reads the still-current allowance (500) via `token.accounting().allowance(from.get(), caller)?` and passes the `allowance < amount` check.
4. Alice's `approve(Bob, 0)` then executes, calling `set_allowance(Alice, Bob, 0)` — this only resets the *future* allowance and does not, and cannot, recover the 500 tokens already transferred.
5. Bob has extracted the full old allowance (500 tokens) despite Alice's clear intent (visible on-chain, in the same block/mempool window) to revoke it — an unauthorized transfer of funds enabled purely by the unconditional-overwrite semantics of `approve`/`set_allowance`.

    fn approve(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        spender: Address,
        amount: U256,
    ) -> Result<()> {
        if caller == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidApprover { approver: caller }));
        }
        if spender == Address::ZERO {
            return Err(BasePrecompileError::revert(IB20::InvalidSpender { spender }));
        }
        token.accounting_mut().set_allowance(caller, spender, amount)?;
        token
            .accounting_mut()
            .emit_event(IB20::Approval { owner: caller, spender, amount }.encode_log_data())
    }
