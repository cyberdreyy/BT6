### Title
Multisig request can execute below the live confirmation threshold using stale confirmations from removed members - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` counts votes toward `num_confirmations` from the `confirmations` set stored for a request without verifying that every account/key already in that set is still a current member. `delete_member()` only purges requests whose *creator* (`request_with_signer.member`) is the member being removed; it does not scrub that member's confirmation entries from other, still-pending requests. As a result, a request can reach the required `num_confirmations` count while counting a vote from an account that has already been removed from the multisig, executing privileged actions (including fund transfers) with fewer live, authorized approvers than the configured threshold.

### Finding Description
`MultiSigContract` stores per-request confirmations in `self.confirmations: LookupMap<RequestId, HashSet<String>>` [1](#0-0) . `confirm()` simply compares the size of this set against the live `self.num_confirmations` field and, once the threshold is met, executes the request: [2](#0-1) 

Note that `self.num_confirmations` is read live, so config changes to the threshold itself are respected. However, nothing in `confirm()` re-validates that each `String` already present in `confirmations` still corresponds to a live `MultisigMember` in `self.members`.

When a member is removed via the `DeleteMember` action (itself executed through the multisig quorum, calling `delete_member()`): [3](#0-2) 

the cleanup logic only removes:
- requests where `r.member == member` (i.e., requests *created/signed* by the removed member), and their confirmations, and
- the `num_requests_pk` entry for that member.

It does **not** scan `self.confirmations` for entries where the removed member had confirmed a *different* request created by someone else. Those stale confirmations remain in the `HashSet<String>` for that other, still-pending request.

**Binding broken:** the protocol's implicit invariant is `confirmations counted at execution == confirmations from currently authorized members`. After a member removal, this becomes `confirmations counted at execution == confirmations from currently authorized members ∪ {stale votes from removed members}`, i.e., claims exceed the live authorization set.

### Impact Explanation
Concretely, with `members = {A, B, C, D}` and `num_confirmations = 3`:
1. `B` creates request `R` (e.g., a `Transfer` action) via `add_request` [4](#0-3) .
2. `A` confirms `R`: `confirmations(R) = {A}` (1 < 3, not executed).
3. Separately, the multisig approves and executes a `DeleteMember { member: A }` request, removing `A` from `self.members`. `delete_member()` does not touch `confirmations(R)` because `R`'s creator was `B`, not `A`.
4. `C` and `D` (now the only members besides `B`) confirm `R`: `confirmations(R) = {A, C, D}` → size 3, `>= num_confirmations (3)` → `execute_request(R)` runs.

The transfer/action executes counting `A`'s stale, no-longer-authorized vote as one of the three required confirmations, even though only two currently authorized members (`C`, `D`, plus the original creator `B`) actually endorsed it live. This is a multisig request executed below the effective/live threshold — matching the explicitly in-scope Critical impact category ("a multisig request executed below threshold"). Funds can be moved, keys added, or contracts deployed with insufficient live authorization.

### Likelihood Explanation
This requires no privileged access beyond being a multisig member at some point and does not require any misconfiguration outside the documented flow: creating a request, having it partially confirmed, then having the confirming member later removed (a normal, expected multisig lifecycle event — member rotation), followed by other members confirming later. Any member (including a since-removed, possibly malicious or compromised, one) benefits from this by having their old confirmation "count" long after their authorization was revoked. Because member removal and request confirmation are independent, uncoordinated operations, this can happen unintentionally in normal operation, not only via deliberate attack, making it moderately likely to be triggered.

### Recommendation
When counting confirmations in `confirm()` (and when displaying `get_confirmations`/`get_num_confirmations`), filter the stored confirmation set to only those entries that are still present in `self.members` before comparing against `self.num_confirmations`. Additionally, `delete_member()` (and any equivalent path that removes members) should actively strip the removed member's entry from every request's `confirmations` set, not just from requests it created, e.g.:

```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    // Remove stale confirmations by this member from ALL pending requests, not just ones they created
    let member_key = member.to_string();
    let request_ids: Vec<u32> = self.requests.keys().collect();
    for request_id in request_ids {
        if let Some(mut confirmations) = self.confirmations.get(&request_id) {
            if confirmations.remove(&member_key) {
                self.confirmations.insert(&request_id, &confirmations);
            }
        }
    }
    ...
}
```

### Proof of Concept
Reproduction using the existing test harness pattern in `multisig2/src/lib.rs` (as shown in `test_multi_3_of_n`):
1. Deploy with `members = {A, B, C, D}`, `num_confirmations = 3`.
2. As `B`, call `add_request` with a `Transfer` action to attacker-controlled `receiver_id`.
3. As `A`, call `confirm(request_id)` → confirmations = `{A}`.
4. Separately drive to completion a `DeleteMember { member: A }` request through the normal 3-of-4 quorum (using `B`, `C`, `D`), removing `A` from `self.members`.
5. As `C`, then `D`, call `confirm(request_id)` on the original request.
6. Observe: on `D`'s call, `confirmations.len() == 3` (`{A, C, D}`) which is `>= num_confirmations (3)`, so `execute_request` runs and the transfer is sent — despite `A` no longer being a member, i.e., only 2 live members (`C`, `D`) plus the stale removed member `A` reached quorum instead of 3 live authorized members.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
