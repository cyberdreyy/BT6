### Title
Zip extraction follows attacker-controlled symlinks in intermediate path components, allowing `lchmod`/metadata writes outside the extraction root - ([File: helpers/archives/zip_extract.go])

### Summary
`ExtractZipArchive` extracts zip entries with no validation that a path segment is a symlink pointing outside the extraction root, and its `lchmod` guard (`AT_SYMLINK_NOFOLLOW`) only protects the *final* path component, not intermediate ones. An attacker can craft a zip with a symlink entry followed by a nested entry whose path traverses that symlink, causing writes and permission changes to land on a file/directory outside the intended extraction root.

### Finding Description
`ExtractZipArchive` (`helpers/archives/zip_extract.go:85-110`) runs two passes over `archive.File`:

1. First pass calls `extractZipFile`, which for a `os.ModeSymlink` entry calls `extractZipSymlinkEntry` (`helpers/archives/zip_extract.go:22-39`). This creates a symlink at `file.Name` pointing to an **attacker-controlled, unchecked target** (`string(data)` read directly from the zip entry contents) — there is no validation that the symlink target stays within the extraction root.
2. If a later entry in the same archive is named e.g. `evil/payload`, `extractZipFile` calls `os.MkdirAll(filepath.Dir(file.Name), 0o777)` (`helpers/archives/zip_extract.go:63`) and then `extractZipFileEntry` opens `evil/payload` for writing (`helpers/archives/zip_extract.go:41-59`). Because `evil` already exists as a symlink to an external directory, `MkdirAll`'s `os.Stat` (which follows symlinks) treats it as an existing directory and the subsequent file write traverses the symlink component, landing outside the extraction root — a classic "zip-slip via symlink" pattern.
3. In the second pass, `lchmod(file.Name, file.Mode())` is called for every entry (`helpers/archives/zip_extract.go:99`). `lchmod` (`helpers/archives/os_unix.go:12-28`) uses `unix.Fchmodat(..., AT_SYMLINK_NOFOLLOW)` (non-Linux) or is skipped entirely for symlink-mode entries on Linux. Critically, `AT_SYMLINK_NOFOLLOW` only affects whether the **final** path component is followed if it is itself a symlink — it does **not** prevent resolution of symlinks in intermediate path components (e.g., `evil` in `evil/payload`). So `lchmod("evil/payload", attacker_mode)` still traverses the `evil` symlink and applies the attacker-chosen mode bits to the real, external target.
4. `processZipExtra` (`helpers/archives/zip_extra.go:96-121`) similarly processes `ZipUIDGidFieldType`/`ZipTimestampFieldType` extra fields and calls `os.Chtimes(file.Name, ...)` (`helpers/archives/zip_extra.go:64`) — a plain `os.Chtimes`, which follows symlinks with no `NOFOLLOW` protection at all, compounding the issue for timestamp metadata (and `processZipUIDGidField`, not shown here but presumably calling `os.Lchown`/`os.Chown`, would need the same scrutiny).

The only existing path check, `errorIfGitDirectory` (`helpers/archives/path_check_helper.go:13-31`), only rejects paths starting with `.git` — there is **no** check anywhere in this extraction path for absolute paths, `..` traversal, or symlink-based path traversal (`zip-slip`). This confirms the invariant ("archive contents must never affect targets reachable only via attacker-controlled symlinks outside the extraction root") is violated.

### Impact Explanation
An attacker who controls a cache/artifact zip (e.g., via a job that produces a cache archive later restored by another job, or a maliciously crafted artifact) can create a symlink to an arbitrary path outside the extraction directory and then use a nested entry name to write file content and set arbitrary permission bits (and potentially ownership/timestamps) on files reachable through that symlink, outside the intended build/cache root. This is broader than "chmod only" — it also enables arbitrary content writes outside the root via the same first-pass symlink traversal, with `lchmod`/`Chtimes` amplifying by also mutating mode/time metadata on the external target.

### Likelihood Explanation
Feasible and fully attacker-controlled: zip entry order, names, symlink target contents, and Unix mode bits in `zip.FileHeader.SetMode` are all attacker-supplied when constructing a malicious cache/artifact archive. No special privileges are needed beyond being able to supply such an archive that the Runner will later extract via `ExtractZipArchive`/`ExtractZipFile`. It is deterministic and repeatable — the same crafted archive will reproduce the effect on every extraction under the same OS.

### Recommendation
- Resolve and validate the final real path of every extraction target before creating/writing/chmod'ing it, rejecting entries whose resolved path (following any intermediate symlinks) escapes the extraction root (a `filepath.EvalSymlinks`/prefix-check against the root, similar to standard zip-slip mitigations).
- Reject symlink entries whose target (absolute or relative) escapes the extraction root at creation time, before the second-pass metadata operations run.
- When performing metadata operations (`lchmod`, `Chtimes`, uid/gid changes), verify that no path component other than the very last is a symlink, or use `openat2`/`O_NOFOLLOW`-based directory-relative resolution instead of relying solely on `AT_SYMLINK_NOFOLLOW` for the last segment.

### Proof of Concept
```go
func TestExtractZipArchive_SymlinkPathTraversal(t *testing.T) {
    tmpRoot := t.TempDir()
    outsideDir := t.TempDir()
    outsideFile := filepath.Join(outsideDir, "payload")
    require.NoError(t, os.WriteFile(outsideFile, []byte("orig"), 0o644))

    // Build a zip: 1) symlink "evil" -> outsideDir  2) file "evil/payload" with mode 0777
    var buf bytes.Buffer
    zw := zip.NewWriter(&buf)

    symHeader := &zip.FileHeader{Name: "evil"}
    symHeader.SetMode(os.ModeSymlink | 0o777)
    w, _ := zw.CreateHeader(symHeader)
    _, _ = w.Write([]byte(outsideDir))

    fileHeader := &zip.FileHeader{Name: "evil/payload"}
    fileHeader.SetMode(0o777) // attacker-chosen mode
    w2, _ := zw.CreateHeader(fileHeader)
    _, _ = w2.Write([]byte("hacked"))

    require.NoError(t, zw.Close())

    r, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    wd, _ := os.Getwd()
    require.NoError(t, os.Chdir(tmpRoot))
    defer os.Chdir(wd)

    err = ExtractZipArchive(r)
    require.NoError(t, err)

    // Assert: the file outside the extraction root was overwritten and its mode changed
    content, err := os.ReadFile(outsideFile)
    require.NoError(t, err)
    assert.Equal(t, "hacked", string(content), "content outside extraction root must not be overwritten")

    info, err := os.Stat(outsideFile)
    require.NoError(t, err)
    assert.NotEqual(t, os.FileMode(0o777), info.Mode().Perm(), "external file mode must not be changed by archive contents")
}
```
Expected (secure) result: both assertions fail to reproduce the attack (content/mode remain original), proving the fix works; on the current code, the test demonstrates the write and mode change occurring on `outsideFile`, confirming the vulnerability.
