### Title
Reorg-permit / conflict-liveness checks validate burn-hash existence but never re-check the resolved `consensus_hash`, letting a PoX-forked sortition silently satisfy a stale canonicality check - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`reorg_permit_stands` and `conflict_still_blocks` both decide whether a previously-recorded burnchain identity (`superseded_by.burn_block_hash` / `conflict.consensus_hash`'s burn block) is "still canonical" by asking the node `get_sortition_by_burn_hash(hash)` and treating **any** `Ok(_)` response as proof that the exact sortition/tenure originally recorded is still live. Neither function compares the `consensus_hash` field of the returned `SortitionInfo` against the `consensus_hash` that was actually recorded (`superseded_by.consensus_hash` or `conflict.consensus_hash`). This is structurally the same defect as the LiquidJS advisory: the safety check is performed on a stand-in identifier (a burn-header-hash "path") and its mere successful resolution is accepted as proof of identity, while the actual object the identifier now resolves to (a specific `consensus_hash`/sortition) is never re-verified to be the one that was originally checked.

### Finding Description
`reorg_permit_stands` (`stacks-signer/src/v0/signer.rs`, ~1222-1247) looks up `conflict.superseded_by` (a `(consensus_hash, burn_block_hash)` pair recorded by `SignerDb::mark_tenure_superseded` when a reorg was sanctioned, see `stacks-signer/src/signerdb.rs` `mark_tenure_superseded`) and calls:

```rust
match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
    Ok(_) => true,
    Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => false,
    Err(_) => false,
}
``` [1](#0-0) 

`conflict_still_blocks` does the analogous thing for `conflict.consensus_hash`'s stored burn block:

```rust
match stacks_client.get_sortition_by_burn_hash(&burn_block.block_hash) {
    Ok(_) => {
        // The tenure's sortition is still canonical: ...
    }
    ...
}
``` [2](#0-1) 

Both call sites discard the returned `SortitionInfo` (`Ok(_)`), so they never check `sortition_info.consensus_hash == superseded_by.consensus_hash` (or `== conflict.consensus_hash`). `get_sortition_by_burn_hash` itself just forwards `/v3/sortitions/burn/:hash` and returns whatever `SortitionInfo` the node resolves for that burn header hash against its current chain state:

```rust
pub fn get_sortition_by_burn_hash(&self, burn_hash: &BurnchainHeaderHash) -> Result<SortitionInfo, ClientError> {
    ...
    let sortition_info = response.json::<Vec<SortitionInfo>>()?;
    sortition_info.first().cloned().ok_or_else(...)
}
``` [3](#0-2) 

A `ConsensusHash` in Stacks incorporates PoX-fork state, not just the underlying burnchain block hash (`SortitionInfo.consensus_hash` and `sortition_id` are explicitly documented as "unique across PoX forks and burnchain forks", while `burn_block_hash` is not) — see `SortitionInfo`'s own doc comments:

```rust
/// This sortition ID ... incorporates PoX forking information and the burn block hash
/// to obtain an identifier that is unique across PoX forks and burnchain forks.
pub sortition_id: SortitionId,
/// The consensus hash ... incorporates PoX forking information and burn op information
/// to obtain an identifier that is unique across PoX forks and burnchain forks.
pub consensus_hash: ConsensusHash,
``` [4](#0-3) 

That means the same `BurnchainHeaderHash` can legitimately resolve to a *different* `consensus_hash`/`sortition_id` once the node's PoX-fork view changes (a PoX-anchor-block reorg, which does not require a majority of signers — it is driven purely by the burnchain and the node's own chain-selection). The check "does `get_sortition_by_burn_hash(hash)` still succeed" therefore answers "does *some* sortition still exist at this burn hash" rather than "is the specific sortition/tenure I recorded still canonical" — exactly the string-vs-canonical-target gap in the LiquidJS advisory (the containment check validated the requested path string, not the file actually opened after symlink resolution).

### Impact Explanation
`reorg_permit_stands` returning `true` for a burn hash that now resolves to a *different* `consensus_hash` than the one recorded as `superseded_by` means the signer treats a stale/irrelevant reorg permit as still authorizing exclusion of a genuine, still-live conflicting signed block from `get_signed_conflicts` (`stacks-signer/src/signerdb.rs`). The signer would then sign a new block in a tenure whose conflicting sibling it should still be defending against, while its earlier signature over that sibling remains a live, aggregable "bearer instrument" (per the code's own comments in `docs/signer-flows.md`, a rejection is revocable but a signature is not). That reproduces exactly the class of impact this scan targets: a signer producing a signature over a block that conflicts with one it already signed, i.e. the pre-commit/conflict equality guard (`signed vs. still-canonical-permit`) can be broken by presenting a burn hash whose resolution has silently drifted to an unrelated PoX fork rather than the one that was actually sanctioned.

### Likelihood Explanation
This does not require a majority of signers, another signer's key, or any auth/local access — it is triggered purely by ordinary burnchain/PoX-fork activity (which a one-slot miner-adjacent bad actor can influence by causing a fork/spend pattern that produces a competing PoX anchor block) combined with the existing, already-recorded reorg-permit/conflict state. It is a logic gap in code the signer runs on every pre-commit re-evaluation (`handle_block_pre_commit`), so the window is any PoX fork that recycles a burn header hash under a different consensus_hash while a `superseded_tenures` record or a `get_signed_conflicts` entry for that burn block still exists in the signer's DB (records are pruned only after `MAX_FORK_DEPTH` = 100 burn blocks, so a nearby PoX reorg is squarely in scope).

### Recommendation
In both `reorg_permit_stands` and `conflict_still_blocks`, use the `SortitionInfo` actually returned by `get_sortition_by_burn_hash` (not just `Ok(_)`) and require `sortition_info.consensus_hash == superseded_by.consensus_hash` (respectively `== conflict.consensus_hash`) before treating the sortition as still representing the originally recorded tenure. If the returned `consensus_hash` differs, treat it the same as a 404 (the originally recorded sortition is gone / superseded by a different PoX fork), not as confirmation that the recorded permit/conflict is still live.

### Proof of Concept
1. Signer observes tenure 1 (consensus_hash `CH1`, burn hash `BH`) get reorged by tenure 2 under the reorg-timing rules; `check_parent_tenure_choice` calls `mark_tenure_superseded(CH1, height, CH2, BH2)`, recording `superseded_by = (CH2, BH2)` for tenure 1's conflicts [5](#0-4) .
2. A PoX-anchor-block reorg occurs on the burnchain such that the node's canonical PoX fork now resolves burn hash `BH2` to a *different* consensus hash `CH2'` (a distinct sortition/tenure), while `BH2` still returns `Ok` from `/v3/sortitions/burn/:hash`.
3. On the next pre-commit evaluation for a block conflicting with tenure 1, `reorg_permit_stands` calls `get_sortition_by_burn_hash(BH2)`, gets `Ok(SortitionInfo{consensus_hash: CH2', ..})`, and — because it never compares `CH2'` to the recorded `CH2` — returns `true` [6](#0-5) .
4. The conflict from tenure 1 is excluded from `get_signed_conflicts`'s blocking set even though the permit that was actually sanctioned (`CH2`) no longer corresponds to the sortition the burn hash currently represents, and the signer proceeds to sign a new block, producing a second signature over a genuinely conflicting chain state.

    pub fn get_sortition_by_burn_hash(
        &self,
        burn_hash: &BurnchainHeaderHash,
    ) -> Result<SortitionInfo, ClientError> {
        debug!("StacksClient: Getting sortition info by burn hash";
            "burn_hash" => %burn_hash,
        );
        let path = self.sortition_by_burn_hash_path(burn_hash);
        let response = self.stacks_node_client.get(&path).send()?;
        if !response.status().is_success() {
            return Err(ClientError::RequestFailure(response.status()));
        }
        let sortition_info = response.json::<Vec<SortitionInfo>>()?;
        sortition_info.first().cloned().ok_or_else(|| {
            ClientError::InvalidResponse("No sortition info found for given burn hash".into())
        })
    }

    /// Record that we permitted the tenure identified by `superseded_by_*` to reorg this one
    /// under the reorg-timing rules (`first_proposal_burn_block_timing`).
    ///
    /// Having sanctioned the replacement, our own signature over what this tenure built must not
    /// then block it: its blocks stop counting as conflicts (see
    /// [`SignerDb::get_signed_conflicts`]). Recorded when the reorg is permitted rather than
    /// derived at signing time, because by the time a replacement reaches the pre-commit
    /// threshold the sortition view that sanctioned the reorg may be long gone.
    ///
    /// The permit is only honored while the permitting tenure's sortition is still canonical
    /// (checked against the node when the record is applied): if a burnchain fork orphans it,
    /// the reorg we sanctioned can no longer happen, so the record must not keep suppressing
    /// this tenure's conflicts. A re-permit by a different tenure replaces the record, so the
    /// latest permitting sortition is the one checked. Records age out via
    /// [`SignerDb::prune_superseded_tenures`].
    pub fn mark_tenure_superseded(
        &mut self,
        consensus_hash: &ConsensusHash,
        burn_block_height: u64,
        superseded_by_consensus_hash: &ConsensusHash,
        superseded_by_burn_block_hash: &BurnchainHeaderHash,
    ) -> Result<(), DBError> {
        self.db.execute(
            "INSERT OR REPLACE INTO superseded_tenures (consensus_hash, burn_block_height, superseded_by_consensus_hash, superseded_by_burn_block_hash, superseded_at) VALUES (?1, ?2, ?3, ?4, ?5)",
            params![
                consensus_hash,
                u64_to_sql(burn_block_height)?,
                superseded_by_consensus_hash,
                superseded_by_burn_block_hash,
                u64_to_sql(get_epoch_time_secs())?
            ],
        )?;
        Ok(())
    }
