### Title
A single APR-0 withdraw request permanently bricks `stopEpoch` after any APR bump — temporary freeze of all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.requestWithdraw` routes requests made while `unscaledApr == 0` into a separate APR0 bucket that increments the global `apr0TotalPrincipal` counter. `prepareStopEpochWithApr0` (called at the top of every `IdleCDOEpochVariant._stopEpoch`) reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0 && unscaledApr != 0`. `apr0TotalPrincipal` can only be cleared by a successful `prepareStopEpochWithApr0` run (which requires `unscaledApr == 0`) or by post-default receipt clearing. An unprivileged KYC-passing lender can therefore plant a persistent "APR0 landmine": while the pool runs at APR 0, they open a withdraw request; from then on, if the manager ever raises the APR (a routine, legitimate `setApr`/`setAprsWithBuffer` call on the strategy), every subsequent `stopEpoch`/`stopEpochWithDuration` reverts and the epoch can never close until the APR is forced back to 0.

### Finding Description
- `requestWithdraw` calls `_requestWithdrawApr0(_amount, _user)` whenever `unscaledApr == 0` and the pool is not closed, which does `apr0TotalPrincipal += _amount` (IdleCreditVault.sol:285-286, 567-577).
- `_stopEpoch` unconditionally calls `_strategy.prepareStopEpochWithApr0(_interest)` before pulling borrower funds (IdleCDOEpochVariant.sol:362).
- `prepareStopEpochWithApr0` reverts if `apr0TotalPrincipal != 0` and `unscaledApr != 0` (IdleCreditVault.sol:505-508), and is the only non-default path that resets `apr0TotalPrincipal = 0` (line 540).
- The revert happens before the try/catch around `getFundsFromBorrower`, so it is not converted into a default — the whole `stopEpoch` transaction reverts.
- Because `epochNumber` never increments, pending withdraw receipts can never mature (`_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest`), new requests still revert or accumulate, and all LP principal stays locked with the borrower.
- Manager-level workaround exists (call `strategy.setAprsWithBuffer(0, ...)` to restore `unscaledApr = 0`, then stop), so the freeze is temporary rather than permanent — but the vault is bricked for as long as the honest manager does not diagnose and revert the APR change, and any automated/scheduled APR update (e.g. `IdleCreditVaultManagerOrchestrator`) re-triggers the wedge.

### Impact Explanation
Analog of the CVE-2019-2950 hang/DoS class: a low-cost attacker transaction (one `requestWithdraw` during an APR-0 phase) creates a state where the core epoch-transition function deterministically reverts. All lender principal and pending withdrawal payouts are frozen for the duration of the wedge — quantified as the entire pool TVL plus `pendingWithdraws` until the manager resets the APR to 0 and re-stops the epoch. This also indefinitely delays funding of already-filed withdraw receipts, since `epochNumber` cannot advance.

### Likelihood Explanation
Requires the pool to operate an epoch at `unscaledApr == 0` (a supported mode — `stopEpoch(0, 0)` sets it, and APR0 accounting exists precisely for this) and a later APR increase while the APR0 bucket is still open. Both conditions arise in normal operations: a lender only needs to call `requestWithdraw` once during the zero-APR window, and there is no warning to the manager that `setApr` will wedge the vault. No malicious privileged role, no default, and no oracle dependence is needed.

### Recommendation
Do not hard-revert in `prepareStopEpochWithApr0` when `unscaledApr != 0`. Either:
- settle/close the APR0 bucket with zero accrued APR0 interest (`apr0RateByEpoch[epochNumber] = 0; apr0TotalPrincipal = 0`) and continue, or
- block mid-epoch APR changes while `apr0TotalPrincipal != 0` inside `setApr`/`setAprsWithBuffer`, so the inconsistent state is unreachable rather than making `stopEpoch` uncallable.

### Proof of Concept
Foundry fork PoC (against the existing `IdleCreditVault.t.sol` harness conventions):

```solidity
function testApr0RequestWedgedStopEpoch() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    // epoch 0 runs at a nonzero APR, then stop it with newApr = 0
    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                 // unscaledApr is now 0
    assertEq(strategy.unscaledApr(), 0);

    // attacker: any KYC'd lender opens a withdraw request during the APR-0 phase
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, ONE_SCALE, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0);   // landmine armed

    // honest manager starts the APR-0 epoch, then mid-epoch bumps the APR
    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.prank(manager);
    strategy.setAprsWithBuffer(initialProvidedApr, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());

    // every stopEpoch now reverts: epoch can never close, funds frozen
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // still running, claims cannot mature
    assertTrue(cdoEpoch.isEpochRunning());
}
```

Note on confidence: the revert path is confirmed directly in `prepareStopEpochWithApr0` (IdleCreditVault.sol:505-508) and the counter lifecycle in `_requestWithdrawApr0`/line 540; I did not execute the PoC, so exact harness helper names (`_depositWithUser`, `_startEpochAndCheckPrices`) should be adapted to the test file. If the manager is assumed to never change APR while an APR0 bucket is open, the practical likelihood drops, but nothing in the code enforces that assumption.
