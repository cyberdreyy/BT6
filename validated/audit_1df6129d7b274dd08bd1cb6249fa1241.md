### Title
Unrestricted stake delegation mutation during the partitioned reward distribution window triggers a deterministic panic on `assert_eq!` in `build_updated_stake_reward` - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The Lido report describes a class of bug where value/state computed at one point in time (an oracle report / burn calculation) can be invalidated or exploited because an attacker mutates the underlying accounted state (shares) between calculation and settlement. The Agave analog is in the partitioned epoch-rewards pipeline: stake rewards are computed once, at the epoch boundary, from a `stakes_cache` snapshot [1](#0-0) , but the resulting `PartitionedStakeReward` entries are not applied atomically — they are deferred and paid out over many subsequent blocks in the same epoch [2](#0-1) . During this window, normal user transactions can still mutate the affected stake accounts (e.g., topping up an existing delegation via a second `DelegateStake`, or otherwise changing `Stake.delegation.stake`). When the deferred payout is finally applied, `build_updated_stake_reward` performs a hard `assert_eq!` comparing the just-fetched, possibly-mutated on-chain delegation to the delegation value computed at the earlier snapshot time, and panics if they disagree.

### Finding Description
Reward calculation happens once, up-front, at the epoch boundary and captures a `PartitionedStakeReward` (which embeds a frozen `stake_account.delegation().stake` value) for every stake account [3](#0-2) . Actual distribution to individual stake accounts is deferred and spread over `get_reward_distribution_num_blocks` blocks — up to 10% of the slots in an epoch [4](#0-3) . This is exactly the "compute now, settle later" pattern that produced the Lido bug (report computed against balances that can change before it is executed).

During that multi-block window, `distribute_partitioned_epoch_rewards` processes one partition per block [5](#0-4)  and, for each stake account, re-fetches the **current** stake account from `stakes_cache` and calls `build_updated_stake_reward`:

`stake.delegation.stake` here is the account's **current** delegation at distribution time, while `new_stake.delegation.stake` is the delegation baked into the `PartitionedStakeReward` at **calculation** time (old delegation + reward). This assert is only bypassed when `adjust_delegations_for_rent` (feature `relax_post_exec_min_balance_check`) is active, which caps/reconciles the delegation instead of asserting [7](#0-6) . When that feature is not active, the code path is the strict `assert_eq!`.

The comment on the caller states the (unverified) assumption underpinning safety: "Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned" [8](#0-7) . I was unable to find any actual enforcement of this restriction anywhere in the codebase — searches for a stake-program-side or bank-side check that blocks stake-account mutation while that account has a pending/queued `PartitionedStakeReward` returned no results outside of the `partitioned_epoch_rewards` module itself and `program-test`. Ordinary, permissionless stake operations (e.g., calling `DelegateStake` again on an already-delegated account to top up its stake to the same vote account, which the stake program supports as a normal user operation) change `Stake.delegation.stake` without any epoch-rewards-awareness.

### Impact Explanation
If a staker (or anyone able to submit a transaction touching their own stake account) changes their stake account's `delegation.stake` between the epoch-boundary reward calculation and the block in which their `PartitionedStakeReward` partition is processed, the `assert_eq!` in `build_updated_stake_reward` fails. Because this code runs deterministically inside `Bank::distribute_epoch_rewards_in_partition` for every validator replaying the same block, this is not a leader-only crash — it is a consensus-critical panic that every validator processing that block would hit identically, which qualifies as a transaction-triggered cluster halt (validators panicking while executing bank state is one of the accepted high-impact categories).

### Likelihood Explanation
The distribution window spans many blocks (up to 10% of an epoch's slots) [4](#0-3) , giving an attacker (or even an unwitting normal user) ample time to submit an ordinary `DelegateStake` top-up transaction against their own already-delegated stake account before their partition is processed. This requires only a single, unprivileged, self-signed transaction — no special privileges, no cross-validator coordination, and no reliance on `relax_post_exec_min_balance_check` being inactive is unusual since it's the older/default code path guarded by a feature gate, meaning clusters that haven't activated `relax_post_exec_min_balance_check` are exposed. I was not able to fully confirm whether some other layer (e.g., a stake-program lockout condition I didn't locate) prevents such mutations while a reward is pending; this uncertainty should be resolved before treating this as fully confirmed.

### Recommendation
- Do not use a hard `assert_eq!`/panic to enforce delegation consistency between calculation-time and distribution-time state; treat any mismatch as a recoverable `DistributionError` (as is already done for `AccountNotFound` and `ArithmeticOverflow`) so a stake-account owner topping up their delegation cannot crash the bank.
- Alternatively, explicitly verify (and add a regression test for) the claimed "stake-program restriction" that prevents mutation of stake accounts with an outstanding partitioned reward; if no such restriction actually exists, one should be added (e.g., reject stake-program instructions against accounts referenced in the active `EpochRewardStatus::Distribution` set), or the reward math should be made robust to delegation changes the same way `adjust_delegations_for_rent` already handles it, unconditionally rather than only under a feature flag.

### Proof of Concept
1. On a cluster/bank where `relax_post_exec_min_balance_check` is not active (so `adjust_delegations_for_rent == false` in `store_stake_accounts_in_partition`).
2. At an epoch boundary, own a delegated stake account `S` with delegation `D` to vote account `V`; the reward-calculation phase computes a `PartitionedStakeReward` for `S` embedding `new_stake.delegation.stake = D + reward`.
3. Before the block in which `S`'s partition index is processed (any block within the multi-block distribution window), submit a normal `DelegateStake` instruction on `S` (topping up the same vote account `V` with additional undelegated lamports), changing the live delegation to `D' != D`.
4. When `distribute_partitioned_epoch_rewards` reaches `S`'s partition, `build_updated_stake_reward` computes `expected_delegation = D' + reward`, compares it against the cached `new_stake.delegation.stake = D + reward`, finds them unequal, and panics via `assert_eq!`, crashing bank processing on every validator that processes this block [9](#0-8) .

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }

    // Calculate rewards from previous epoch and distribute reward commissions
    pub(in crate::bank) fn calculate_rewards(
        &self,
        stake_history: &StakeHistory,
        stake_delegations: Vec<(&Pubkey, &StakeAccount<Delegation>)>,
        cached_vote_accounts: CachedVoteAccounts<'_>,
        rewarded_epoch: Epoch,
        reward_epoch_delegated_stakes: RewardEpochDelegatedStakes,
        reward_calc_tracer: Option<impl Fn(&RewardCalculationEvent) + Send + Sync>,
        thread_pool: &ThreadPool,
        metrics: &mut RewardsMetrics,
    ) -> Arc<PartitionedRewardsCalculation> {
        // We hold the lock here for the epoch rewards calculation cache to prevent
        // rewards computation across multiple forks simultaneously. This aligns with
        // how banks are currently created- all banks are created sequentially.
        // As such, this lock does not actually introduce contention because bank
        // creation (and therefore reward calculation) is always done sequentially.
        //
        // However, if we plan to support creating banks in parallel in the future, this logic
        // would need to change to allow rewards computation on multiple forks concurrently.
        // That said, there's still a compelling reason to keep this lock even in a parallel
        // bank creation model: we want to avoid calculating rewards multiple times for the same
        // parent bank hash. This lock ensures that.
        //
        // Creating bank for multiple forks in parallel would also introduce contention for compute resources,
        // potentially slowing down the performance of both forks. This, in turn, could delay
        // vote propagation and consensus for the leading fork—the one most likely to become rooted.
        //
        // Therefore, it seems beneficial to continue processing forks sequentially at epoch
        // boundaries: acquire the lock for the first fork, compute rewards, and let other forks
        // wait until the computation is complete.
        let mut epoch_rewards_calculation_cache =
            self.epoch_rewards_calculation_cache.lock().unwrap();
        let rewards_calculation = epoch_rewards_calculation_cache
            .entry(self.parent_hash)
            .or_insert_with(|| {
                Arc::new(self.calculate_rewards_for_partitioning(
                    stake_history,
                    stake_delegations,
                    cached_vote_accounts,
                    rewarded_epoch,
                    reward_epoch_delegated_stakes,
                    reward_calc_tracer,
                    thread_pool,
                    metrics,
                ))
            })
            .clone();
        drop(epoch_rewards_calculation_cache);

        rewards_calculation
    }
