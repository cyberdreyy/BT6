### Title
Missing allowlist/rate-limit enforcement on legacy gateway `web_api_trigger` path allows unauthenticated broadcast of trigger requests to all DON nodes - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The `OmoRouter.mint()` report describes a function that forwards a call to a privileged downstream component while skipping a required preparatory/gating step (pulling and approving assets), making the delegated call unsafe/unusable. The analogous pattern in this codebase is `handler.HandleLegacyUserMessage` in the Gateway's capabilities handler: it forwards a `web_api_trigger` request to every node in the DON, but the code explicitly documents — and skips — the gating step ("apply allowlist and rate-limiting") that should occur before the request is dispatched.

### Finding Description
`gateway.ProcessRequest` is the entry point invoked directly from the internet-facing HTTP server for legacy (non-JSON-RPC) requests [1](#0-0) . For legacy requests it resolves a handler by DON ID and calls `h.HandleLegacyUserMessage(ctx, msg, callback)` without any prior allowlist or authorization check at the gateway layer [1](#0-0) .

Inside `HandleLegacyUserMessage`, the code validates payload decoding, checks a non-zero timestamp, and checks for staleness, but the authorization step is only stubbed with a comment:

```go
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
``` [2](#0-1) 

Immediately after this, the handler saves a callback and broadcasts the raw request to **every member of the DON**, with no check on the sender's identity, workflow ownership, or any allowlist:

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()

// Send original request to all nodes
for _, member := range h.donConfig.Members {
    err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
``` [3](#0-2) 

This is a direct structural analog to the reported bug class: a function that is documented to require a gating/validation step before delegating to a sensitive downstream operation, but the implementation omits that step, leaving the downstream call (here, dispatch to DON nodes) reachable without the intended control. In contrast, the newer JSON-RPC vault gateway path (`GatewayHandler.HandleGatewayMessage`) does enforce an `Authorizer`/allowlist check (`requestProcessor.ProcessRequest` → `AuthorizeRequest`) before performing any privileged action [4](#0-3) , confirming that allowlist enforcement is the expected control that is missing on the legacy path.

### Impact Explanation
Any unprivileged client capable of reaching the gateway's public HTTP endpoint can submit a legacy `web_api_trigger` message that is broadcast to all DON node members without allowlist verification. This is an internet-facing gateway path (`HTTPRequestHandler.ProcessRequest`) [5](#0-4) , so the missing check bypasses the allowlist/quota controls that are supposed to gate which senders may trigger workflow executions on the DON, constituting an allowlist bypass / unauthorized job (workflow) trigger.

### Likelihood Explanation
The affected function is reachable directly from the internet-facing gateway HTTP handler with no authentication middleware visible in `httpserver.go` beyond an opaque `auth` string parameter passed through to `ProcessRequest` [6](#0-5) , and the code path is explicitly marked as incomplete via the `TODO: apply allowlist and rate-limiting here` comment, indicating the gap is a known, unaddressed omission in production code rather than a hypothetical.

### Recommendation
Implement the allowlist and rate-limiting check called out in the TODO comment inside `HandleLegacyUserMessage` before saving the callback and broadcasting `req` to `h.donConfig.Members`, mirroring the `Authorizer.AuthorizeRequest` gating already used by the JSON-RPC vault gateway handler (`gw_handler.go`). Reject/short-circuit with an error response for any message whose sender is not present in the applicable allowlist, and apply a sender/global rate limiter analogous to `nodeRateLimiter` before dispatch.

### Proof of Concept
Not independently verifiable from static code alone: confirming exploitability requires tracing whether any authorization/allowlist check occurs upstream in the specific gateway wiring/configuration outside the reviewed files (e.g., in `multihandler.go` or DON-specific handler configuration) that might mitigate this at another layer — that could not be fully confirmed within the available search budget. The static code path itself, however, shows no allowlist enforcement between message receipt and DON-wide broadcast in `HandleLegacyUserMessage`.

func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}
