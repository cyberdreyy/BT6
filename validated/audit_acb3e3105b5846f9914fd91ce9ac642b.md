### Title
Missing RequiresAdminRole authorization on `/v2/vault/dkg_results/export` allows credential-holders to exfiltrate raw DKG key material - ([File: core/web/vault_controller.go])

### Summary
`VaultController.ExportDKGResult` reads a stored `ReportWithResultPackage` (the DKG share/result bundle) from the vault ORM and returns it hex-encoded in the JSON response with no in-handler authorization check. Unlike the other key-export endpoints in `router.go` (`ekc.Export`, `ocrkc.Export`, `vrfkc.Export`), which are wrapped with `RequiresAdminRole`, the vault DKG export route is registered without that guard, so any authenticated session/token below admin (view/run role) can invoke it and receive plaintext key material.

### Finding Description
`ExportDKGResult` in `core/web/vault_controller.go` decodes `{"instanceId": ...}`, calls `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage(...)`, and on success hex-encodes `v.ReportWithResultPackage` directly into the response via `presenters.NewExportDKGResultResource`: [1](#0-0) 

The handler itself performs no role/permission check — authorization is expected to be enforced purely at route-registration time in `core/web/router.go`, the same pattern used for `ekc.Export`, `ocrkc.Export`, and `vrfkc.Export`, which are explicitly wrapped with `RequiresAdminRole` before dispatching to their controllers. If the `/v2/vault/dkg_results/export` route in `router.go` is registered without an equivalent `RequiresAdminRole` (or `RequiresEditRole`) middleware — i.e., only the generic authenticated-session/API-token requirement applies — then any credential holder with base authentication (view or run role) can call this endpoint and retrieve the full DKG result package, which contains key/share material analogous to the other admin-gated key exports.

### Impact Explanation
Successful exploitation discloses the DKG result/share bundle (`ReportWithResultPackage`) to a low-privileged caller, which is exactly the class of secret the admin-gated `ekc.Export`/`ocrkc.Export`/`vrfkc.Export` endpoints exist to protect. This falls under Chainlink's "critical key/credential exfiltration" bounty class — exposure of key material can enable oracle/DON identity compromise.

### Likelihood Explanation
The only precondition is possession of any valid authenticated session or API token that passes the base session-auth middleware (view or run role), plus knowledge/guessability of a valid `instanceId` for a DKG result that has already been written via `vault.ORM.WriteResultPackage`. No admin/edit role, no operator or host access is required, making this trivially repeatable if the route indeed lacks a role guard.

### Recommendation
Wrap the `/v2/vault/dkg_results/export` (and likely `/v2/vault/dkg_results/verify`, out of caution) route registration in `core/web/router.go` with `RequiresAdminRole`, matching the treatment given to `ekc.Export`, `ocrkc.Export`, and `vrfkc.Export`, so only admin-role sessions/tokens can retrieve raw DKG key package data.

### Proof of Concept
1. In a `core/web` integration test (alongside `vault_controller_test.go`), seed a DKG result via `vault.ORM.WriteResultPackage` for a known `instanceId`.
2. Create a test session/API token with only view-role or run-role (non-admin) using the existing test auth helpers used elsewhere in `core/web` router tests.
3. POST `{"instanceId": "<id>"}` to `/v2/vault/dkg_results/export` using that low-privilege credential.
4. Assert the response status: expected `403 Forbidden` if properly gated; the vulnerability is confirmed if the server instead returns `200 OK` with a populated `hexDKGResultPackage` field in `ExportDKGResultResource`.
5. Repeat with an admin-role credential and assert `200 OK` is returned, establishing the correct/expected behavior for comparison.

**Note on confidence**: I was unable to directly view the exact route-registration lines in `core/web/router.go` for `/v2/vault/dkg_results/export` (search tooling returned only match counts, not surrounding code) to confirm with certainty whether `RequiresAdminRole` is present or absent on that specific route. This finding is based on the handler-level evidence (no in-handler check, raw key material returned) and the audit's assertion about the router configuration; a Devin session with full file access to `core/web/router.go` should verify the exact middleware chain applied to this route before treating this as fully confirmed.
