### Title
Stale confirmations from deleted multisig members allow request execution below the live confirmation threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member()` in `multisig2/src/lib.rs` removes a member's own outstanding *requests* but never purges that member's *confirmations* that were cast on other members' still-pending requests. `confirm()` later counts confirmations purely by set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without validating that every entry in the set still corresponds to a current member. This breaks the binding "confirmations counted == live members who confirmed," allowing a request to execute with fewer than `num_confirmations` *live* signers.

### Finding Description
When a request is created, `add_request` stores it and an empty `HashSet<String>` of confirmations keyed by `request_id` [1](#0-0) . Members confirm via `confirm()`, which inserts their stringified `MultisigMember` identity into that set, and executes the request once `confirmations.len() + 1 >= num_confirmations` [2](#0-1) .

Membership changes go through `DeleteMember`, handled by `delete_member()`:
```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    assert(...);
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
``` [3](#0-2) 

This filter only matches requests where `r.member == member`, i.e. requests that the removed member *created*. It does **not** scan `self.confirmations` (a separate `LookupMap<RequestId, HashSet<String>>`) for entries where the removed member had confirmed a request created by *someone else*. Such confirmations remain in the set indefinitely.

Consequently, a request confirmed by member A, then A is removed via `DeleteMember`, still carries A's confirmation in `self.confirmations[request_id]`. When the remaining live members later call `confirm()`, the code only checks `confirmations.len()` — it never re-validates that each string in the set corresponds to `self.members.contains(...)`. This lets the request execute with `num_confirmations - 1` live signers plus one now-invalid signature, i.e., strictly fewer live, currently-authorized approvals than the configured threshold requires.

Equality that should hold but is broken:
`confirmations.len()` (recorded) == number of confirmations from accounts currently in `self.members` (live authorized signers).

Before the attack: request X has confirmations {A, B} where A, B, C are members, `num_confirmations = 3`. Confirmation count 2 < 3, correctly pending.
Admin action: `DeleteMember{A}` executes (itself required 3 confirmations, but is a separate request/action from X). A is removed from `self.members`; the confirmations map for request X is untouched (X ≠ the DeleteMember request), so `confirmations[X]` still = {A, B}.
After: only B and C remain as legitimate signers, yet `confirmations[X].len() == 2` already includes stale A. C calls `confirm(X)`: `len()+1 = 3 >= num_confirmations(3)` → request X executes, funded/authorized by only 2 currently-valid members (B, C) plus one stale approval from a removed member A — executing below the intended live-member threshold.

### Impact Explanation
This matches the Critical impact category "a multisig request executed below threshold." Any pending request (including `Transfer`, `AddKey`/full-access-key grants, `DeployContract`, `FunctionCall`) can be pushed to execution using a stale confirmation from a member who has since been removed (e.g., for being compromised or malicious), effectively lowering the real quorum required and undermining the security guarantee that K-of-N *current* members must approve an action. In the worst case this lets NEAR be transferred, a full access key added, or the contract's code replaced with only `K-1` live approvals, defeating the purpose of the multisig.

### Likelihood Explanation
This is reachable purely through the multisig's own privileged-but-unprivileged-relative-to-each-other members: any member can confirm a request before being removed, and removal is a normal governance action (`DeleteMember`, itself requiring K confirmations, but independent of any other pending request's confirmation set). No attacker needs to be the multisig owner in an illegitimate sense — a legitimate but subsequently-revoked member's confirmation silently persists and is later exploited by the remaining members (or simply causes an unintended under-threshold execution) with a normal sequence of confirm/delete-member operations. No special privileges beyond being (or having been) an existing multisig member are required, and the flaw is in the contract logic itself, not a misconfiguration.

### Recommendation
In `delete_member()`, also purge the removed member's entry from every request's confirmation set (or lazily filter it out in `confirm()`/`execute_request()` before counting). Concretely:
```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    // Remove this member's confirmation from ALL pending requests, not just ones they created
    let member_str = member.to_string();
    let request_ids: Vec<u32> = self.requests.iter().map(|(k, _)| k).collect();
    for request_id in request_ids {
        if let Some(mut confirmations) = self.confirmations.get(&request_id) {
            if confirmations.remove(&member_str) {
                self.confirmations.insert(&request_id, &confirmations);
            }
        }
    }
    // ... existing logic to also delete requests they authored
}
```
Alternatively, when counting in `confirm()`, filter `confirmations` to only strings still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}` and `num_confirmations = 3`.
2. A creates request X (e.g., `Transfer`) via `add_request`.
3. A confirms X via `confirm(X)` → `confirmations[X] = {A}`.
4. B confirms X via `confirm(X)` → `confirmations[X] = {A, B}` (2 < 3, still pending).
5. Separately, members create and fully confirm a `DeleteMember{A}` request (requires 3/3 confirmations from A, B, C, or any legitimate quorum reached before A's removal is desired) — this executes and removes A from `self.members`, but `confirmations[X]` is untouched and still contains A.
6. C now calls `confirm(X)`. `confirmations[X].len() + 1 == 3 >= num_confirmations (3)` → request X executes, transferring funds/authorizing the action with only B and C as live, currently-valid confirmers (2 live members) instead of the required 3. [2](#0-1) [3](#0-2)
