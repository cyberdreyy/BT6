### Title
Matured instant-withdraw receipts can be claimed at par by front-running `stopEpoch`/`stopEpochWithDuration`, escaping loss socialization and draining liquidity earmarked for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The mapped bug class is: a time-gated, unprivileged "exit/cancel" action that stays executable right up to the privileged settlement transaction, allowing an attacker to front-run settlement and walk away with full value while honest participants absorb the loss. In idle-tranches the analog is the instant-withdraw flow: `requestInstantWithdraw` mints a 1:1 strategy-token receipt and queues `pendingInstantWithdraws`; after the CDO-side `instantDelay` matures, `claimInstantWithdrawRequest` pays the full requested amount from funded vault balance with no epoch-state, loss-price, or epoch-gating check. An attacker who keeps a matured instant-withdraw receipt unclaimed can watch the mempool for the manager's `stopEpoch`/`stopEpochWithDuration(_lossAmount)` (or `collectWithdrawFunds`) transaction and front-run it with a claim at par.

### Finding Description
- `requestInstantWithdraw` burns CDO-held strategy tokens, mints the user a receipt, and only increments accounting (`instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, `pendingInstantWithdraws`); no funds move at request time (`contracts/strategies/idle/IdleCreditVault.sol:356-375`).
- `claimInstantWithdrawRequest` clears `instantWithdrawsRequests[_user]`, burns the receipt and calls `_transferFundedClaim(_user, amount)` at full face value. It contains no check that the epoch is running/stopped, no haircut via `lossRecoveryPriceByEpoch`, and no check that the amount is covered by funds actually collected via `collectInstantWithdrawFunds`; `pendingInstantWithdraws` is not even decremented in the claim path (`contracts/strategies/idle/IdleCreditVault.sol:380-393`, `398-403`).
- Settlement of the epoch is privileged and atomic-ish: `stopEpoch` / `stopEpochWithDuration` computes the loss split (`previewLossAdjustedWithdrawFunds`) and pulls the funded amount via `collectWithdrawFunds`, storing `lossRecoveryPriceByEpoch[epochNumber]` when receipts are only partially funded (`contracts/strategies/idle/IdleCreditVault.sol:411-460`). Any underlyings sitting in the vault/CDO buffer before that pull are fair game for a matured instant claim.
- Like `buyerCancel` being callable until the keeper's confirm lands, the instant claim remains callable until the settlement transaction executes; the only protection is timing, not an authorization or state gate.

### Impact Explanation
Direct theft / loss escape. The attacker redeems matured instant-withdraw receipts at 100% of face value immediately before a loss-bearing `stopEpoch` is mined. The withdrawn underlyings either (a) come out of the same vault balance that `collectWithdrawFunds`/`epochPendingClaims` accounting expects to use to honor queued withdraw claimants (queue pays `amount * epochWithdrawPrice / ONE_TRANCHE` from `IdleCDOEpochQueue.claimWithdrawRequest`, `contracts/IdleCDOEpochQueue.sol:393-411`), forcing later claimants' transfers to fail or be short-changed, or (b) let the attacker sidestep the pro-rata loss that `previewLossAdjustedWithdrawFunds` would have assigned, pushing the entire loss onto remaining AA/BB holders contrary to the waterfall. Quantified loss equals the attacker's matured `instantWithdrawsRequests` balance, up to the available funded reserve.

### Likelihood Explanation
Requires only an unprivileged tranche holder who has passed KYC (`isWalletAllowed`), a deposit, and one instant-withdraw request aged past `instantDelay`. Front-running a predictable, infrequent manager transaction (`stopEpoch` at `epochEndDate`) is standard mempool activity; no privileged role, no oracle manipulation, and no borrower cooperation is needed. Likelihood is moderate: the attacker must pre-position the receipt and the vault must hold sufficient liquid balance at claim time, but both are normal conditions in the instant-withdraw mode.

### Recommendation
Gate `claimInstantWithdrawRequest` on epoch state: revert when a stop is pending/imminent (e.g., block.timestamp >= epochEndDate or a `stopping` flag set in `_beforeStopEpoch`), and route instant claims through the same loss-adjusted pricing as normal receipts — e.g., check `lossRecoveryPriceByEpoch[requestEpoch]` before paying at par, or require matured receipts to be funded via `collectInstantWithdrawFunds` and decrement `pendingInstantWithdraws` in the claim path so unfunded receipts cannot draw on the shared reserve.

### Proof of Concept
Foundry fork PoC sketch (matches `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testInstantClaimFrontrunsLossyStopEpoch() external {
    // setup: attacker deposits AA, pool running with other LPs
    uint256 amount = 10000 * ONE_SCALE;
    _depositWithUser(attacker, amount);          // KYC'd lender
    _startEpochAndCheckPrices(0);

    // attacker requests instant withdraw for full balance
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(attackerTrancheBal, address(AAtranche));

    // attacker lets instantDelay mature but deliberately does NOT claim
    skip(instantDelay + 1);

    // borrower realizes a loss; manager submits stopEpochWithDuration(loss)
    // attacker sees it in the mempool and front-runs with the matured claim
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();      // pays full amount at par

    // manager's tx now settles a larger loss onto remaining LPs,
    // or collectWithdrawFunds/strategy balance is short for pending claimants
    uint256 loss = poolValue * 30 / 100;
    deal(defaultUnderlying, borrower, neededFunds);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(loss, epochDuration);

    // assert: attacker received 100% while lossRecoveryPriceByEpoch < RECOVERY_FULL
    // and queued claimants' claimWithdrawRequest underflows the vault reserve
}
```

Note: I verified the vault-side claim paths directly, but could not read the exact CDO-side `claimInstantWithdrawRequest`/`stopEpoch` gating lines in `IdleCDOEpochVariant.sol` within the available iterations; the PoC assumes the CDO forwards matured instant claims without an epoch-stop check, consistent with the vault-side code shown.
