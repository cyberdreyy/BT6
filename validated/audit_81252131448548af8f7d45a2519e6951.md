### Title
Unbounded backend-controlled `Content-Range` total drives unbounded chunk-slice allocation in artifact parallel download - (File: helpers/transfer/content_range.go, helpers/transfer/parallel_download.go, network/gitlab.go)

### Summary
`ParseContentRangeTotal` parses the numeric total from a `Content-Range` response header with no upper bound (only `>0` is checked), and this value is passed straight through `network/gitlab.go`'s `DownloadArtifacts` probe path into `ParallelRangeDownload`/`parallelDownloadRanges`, which allocates one `byteRange` entry per chunk via `append` in a loop bounded only by `contentLength/chunkSize`. A malicious/compromised artifact storage endpoint (reached via the job-token-authenticated redirect Location) can return an arbitrary huge `Content-Range: bytes */N` (e.g. N ≈ math.MaxInt64) to force the runner to attempt an allocation/loop of astronomical size.

### Finding Description
In `helpers/transfer/content_range.go` (lines 15-34), `ParseContentRangeTotal` accepts `bytes */N` (the range part being irrelevant) and only validates that `N` parses as an `int64` and is `> 0` — there is no maximum-size sanity check [1](#0-0) .

In `network/gitlab.go`, `DownloadArtifacts` follows a redirect to object storage, sends a job-token-authenticated `Range: bytes=0-0` probe, and if the response is `206` it parses `Content-Range` via `ParseContentRangeTotal`, using the returned `contentLength` directly (only checked for `<= 0`) as input to `tryArtifactParallelDownload` [2](#0-1) .

`ParallelRangeDownload` calls `parallelDownloadRanges(contentLength, chunkSize)`, which loops `for offset := int64(0); offset < contentLength; offset += chunkSize` and appends a `byteRange` struct on every iteration [3](#0-2) . With `contentLength` near `math.MaxInt64` and any realistic (small) `chunkSize`, this loop must execute on the order of `contentLength/chunkSize` iterations — a number far beyond what memory or CPU can service — before any chunk is fetched or any per-chunk `io.LimitReader` safeguard (mentioned in the doc comment) ever applies. The `io.LimitReader` protection described in the `ParallelRangeDownload` doc comment only bounds *each chunk's* read size; it does not bound the *number* of chunks computed up front, so it does not mitigate this path at all [4](#0-3) .

Neither `ParseContentRangeTotal` nor `normalizeParallelDownloadInputs`/`parallelDownloadRanges` impose any cap relative to job-configured artifact size limits, available memory, or a maximum reasonable chunk count. I was not able to fully inspect `tryArtifactParallelDownload`'s body (chunk size/concurrency selection) within the tool budget, but nothing in the code paths I did inspect (`ParseContentRangeTotal`, the probe handling in `DownloadArtifacts`, and `parallelDownloadRanges`) shows any bound being applied to `contentLength` before it reaches the allocation loop.

### Impact Explanation
Because the runner process is shared across concurrently executing jobs (each job's `UpdateJob`/`PatchTrace` polling goroutines run in the same process), an attacker-controlled artifact-storage response consumed by one job's `DownloadArtifacts` call can trigger a memory/CPU blowup building the `chunks` slice, potentially exhausting process memory and causing an OOM kill or severe scheduler starvation. This would disrupt polling/heartbeat goroutines for other, unrelated jobs running in the same runner process, i.e., persistent multi-tenant DoS that outlives the triggering job's own cancellation.

### Likelihood Explanation
Preconditions: `UseParallelArtifactTransfer` feature flag must be enabled, and the artifact download must follow a `302`/`307` redirect to an endpoint the attacker controls or can manipulate the response of. An unprivileged pipeline author does not directly control the artifact storage backend, so exploitation depends on the artifact fetch being redirected to a location whose response the attacker can influence (e.g., through a controlled/malicious "object storage" endpoint if such a redirect target is attacker-influenced in a given deployment). Given the runner code itself provides no bound, if such a redirect target is attacker-reachable, exploitation is straightforward and repeatable (a single crafted `Content-Range` header suffices).

### Recommendation
Add an explicit upper bound in `ParseContentRangeTotal` (or immediately after calling it in `network/gitlab.go`) rejecting/clamping totals above a sane maximum (e.g., a configured max artifact size), and additionally bound the computed chunk count in `parallelDownloadRanges`/`normalizeParallelDownloadInputs` (e.g., reject or fall back to single-stream download if `contentLength/chunkSize` exceeds a reasonable chunk-count ceiling) before allocating the `chunks` slice.

func TestParallelDownloadRanges_HugeContentLengthBlowsUpAllocation(t *testing.T) {
    const hugeN = int64(math.MaxInt64)
    const chunkSize = int64(1024 * 1024) // 1MB, a realistic default

    done := make(chan struct{})
    go func() {
        _ = parallelDownloadRanges(hugeN, chunkSize) // expected: should error/cap, not attempt ~8.8e12 appends
        close(done)

    case <-done:
        t.Fatal("expected function to be bounded/error out, but it completed an unbounded allocation")
    case <-time.After(2 * time.Second):

func parallelDownloadRanges(contentLength, chunkSize int64) []byteRange {
	var chunks []byteRange
	for offset := int64(0); offset < contentLength; offset += chunkSize {
		length := chunkSize
		if offset+length > contentLength {
			length = contentLength - offset
		}
		chunks = append(chunks, byteRange{offset, length})
	}
	return chunks
}
