### Title
Stale confirmations from a deleted multisig key/member still count toward the confirmation threshold, allowing request execution below the required K-of-N - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`DeleteKey` (multisig v1) and `DeleteMember` (multisig2) only purge *requests originated by* the removed key/member; they never scrub that key/member's existing *confirmations* on other still-pending requests. Because `confirm()` counts confirmations purely by set size against `num_confirmations`, a confirmation cast by a member who is later removed keeps counting toward the threshold on any request it was not itself the author of. This lets a request execute with fewer than `num_confirmations` currently-valid members, breaking the K-of-N custody guarantee.

### Finding Description
In `multisig/src/lib.rs`, the `DeleteKey` branch of `execute_request` only cleans up requests where `r.signer_pk == pk`: [1](#0-0) 

It does not touch `self.confirmations` entries for *other* requests where `pk` appears as a confirming (but not originating) key. Likewise in `multisig2/src/lib.rs`, `delete_member` filters only `r.member == member` requests for removal: [2](#0-1) 

Meanwhile `confirm()` in both versions determines execution purely from the recorded confirmation set size versus `num_confirmations`, with no re-validation that every confirming principal is still a current member at execution time: [3](#0-2) [4](#0-3) 

This breaks the equality that should hold: `confirmations_recorded(request) == confirmations_by_live_members(request)`. Once a member/key that already confirmed request X is removed via a *different* request Y (`DeleteKey`/`DeleteMember`), request X's confirmation set still contains the removed principal. A subsequent `confirm(X)` by only `num_confirmations - 1` genuinely current members will reach the threshold and trigger `execute_request`, because the stale confirmation from the removed member is silently counted as valid.

### Impact Explanation
This is a Critical-impact finding per the custody binding "a multisig request executed below threshold." An attacker who is one of N members (or colludes with fewer than K live members) can:
1. Get a request R (e.g., a `Transfer` of all funds) partially confirmed by a member M who is about to be, or will be, removed.
2. Have M removed via `DeleteMember`/`DeleteKey` (a legitimate, unrelated governance action, e.g. offboarding a departing member).
3. Confirm R with only `num_confirmations - 1` remaining live members — M's stale confirmation still counts, satisfying the `>= num_confirmations` check and executing R (e.g. transferring out account funds) despite fewer than K currently valid members having approved it.

This directly moves NEAR out of the multisig-controlled account with fewer independent confirmations than the K-of-N policy requires — an authorization boundary crossed with concrete fund-movement consequence.

### Likelihood Explanation
Requires no privileged foundation/owner action beyond normal multisig operation: member removal (`DeleteMember`/`DeleteKey`) is a standard, expected multisig governance action, and any member can create/confirm requests. The only precondition is that a request already carries a confirmation from a member who is subsequently removed while the request remains pending — a realistic operational sequence (e.g., rotating out a compromised or departing key while other requests are in flight). No special privileges beyond being an existing multisig member/key holder are needed.

### Recommendation
When removing a member/key (`DeleteKey` / `DeleteMember`), scan **all** active requests' confirmation sets (not just requests they authored) and strip the removed principal's confirmation from each, decrementing/re-evaluating accordingly. Alternatively, when `confirm()` evaluates whether the threshold is met, revalidate that every principal in `confirmations` is still a current member (via `self.members`) before counting it, rather than trusting historically recorded confirmations.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 3` and members `{A, B, C, D}`.
2. A calls `add_request` for request `R1` = `Transfer { amount }` to an attacker-controlled account, then `confirm(R1)` (1/3 confirmations: A).
3. B calls `confirm(R1)` (2/3 confirmations: A, B).
4. Separately, D creates and the required K members confirm a `DeleteMember { member: B }` request, which executes and calls `delete_member`. This only removes requests *authored by* B; `R1` (authored by A) is untouched and B's confirmation on `R1` remains in `self.confirmations[R1]`.
5. C now calls `confirm(R1)`. `confirmations.len() + 1 = 3 >= num_confirmations (3)` — R1 executes, transferring funds, even though B (whose confirmation is counted) is no longer a member and only two currently-valid members (A, C) actually approved. [4](#0-3) [2](#0-1)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
