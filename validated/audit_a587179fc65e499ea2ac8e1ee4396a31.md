## Finding: Stale confirmations from deleted multisig members count toward the confirmation threshold

The bug-class hint (an assertion/state-consistency crash in a fork tracking list) maps here to a stale-state consistency bug in the multisig contract: confirmations recorded for a request are not purged for a member who confirmed it once that member is later removed from the multisig, letting execution proceed with fewer *live* member votes than `num_confirmations` requires.

### Title
Multisig executes requests using confirmations from deleted (no-longer-live) members - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` only removes confirmations/requests that were *created by* the removed member; it never scans other pending requests to purge confirmations that the removed member cast as a *voter*. Those stale votes remain in the `confirmations` `HashSet` and are still counted by `confirm`, so a request can reach `num_confirmations` and execute even though fewer live members actually voted for it.

### Finding Description
`confirm` counts votes purely by set size, with no check that voters are still members: [1](#0-0) 

`delete_member` cleans up only requests originated by the deleted member (`r.member == member`) and that member's `num_requests_pk` entry — it never removes the deleted member's confirmation entries from other requests they merely confirmed: [2](#0-1) 

The binding that should hold is: `confirmations.len()` for a live/pending request == number of *current* members who voted for it. `delete_member` breaks this equality by leaving a removed member's vote counted, since the confirmations map is keyed by `request_id` (populated by any confirmer) rather than scoped to requests created by that member: [3](#0-2) 

### Impact Explanation
This crosses the threshold/authorization boundary explicitly called Critical in scope: "a multisig request executed below threshold." Concretely, a `Transfer`, `AddKey`, `FunctionCall`, or `DeployContract` request can execute with only `num_confirmations - 1` *live* members actually approving it, because one vote is a phantom from an account that has since been removed as a member (e.g., via a legitimate `DeleteMember` action executed for unrelated reasons — key rotation, compromised key removal, membership rebalancing). Funds or privileged actions (`AddKey`, `DeployContract`) can move/execute without the intended quorum of currently-trusted signers.

### Likelihood Explanation
This requires no attacker-controlled deployment or malicious node — only ordinary multisig lifecycle events (a member confirms a pending request, then is later removed via a normal `DeleteMember` request, a common operational action e.g., during key rotation). It does not require exceeding `active_requests_limit`, controlling gas, or a redeploy; it is triggered purely by ordering of otherwise-legitimate multisig calls (`confirm` then `DeleteMember` then `confirm`), all reachable by regular multisig members without any privileged bypass.

### Recommendation
In `delete_member`, iterate all pending requests' `confirmations` sets and remove any entry matching `member.to_string()`, decrementing effectively toward the un-inflated count; alternatively, in `confirm`, filter the stored confirmation set against `self.members` before comparing `confirmations.len()` against `num_confirmations`, so only entries belonging to *current* members are counted.

### Proof of Concept
1. Initialize `MultiSigContract::new([A, B, C, D], 3)` (`num_confirmations = 3`).
2. Member A calls `add_request(transfer_request)` → `request_id = R` (creator = A).
3. Member B calls `confirm(R)` → `confirmations[R] = {B}` (1/3).
4. Separately, members create/confirm a `DeleteMember{ member: B }` request (reaching 3/3 confirmations from A, C, D as normal governance) → executes `delete_member(B)`. Since `R` was created by A (not B), `R`'s confirmations are untouched; `confirmations[R]` still contains `B`, even though `B` is no longer in `self.members`.
5. Member A calls `confirm(R)` → `confirmations[R].len()+1 = 2 → 2 >= 3`? No.
   Member C calls `confirm(R)` → `confirmations[R].len()+1 = 2+1 = 3 >= 3` → `execute_request` runs the transfer.
6. Result: the transfer executed with only A and C as genuinely live confirming members (2 live votes), plus one stale vote from removed member B, satisfying `num_confirmations = 3` without 3 live members' approval. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
