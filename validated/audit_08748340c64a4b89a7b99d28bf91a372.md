### Title
Signer can sign two conflicting tenure-start blocks for the same tenure because `chainstate/v1.rs::validate_tenure_change_payload` checks only globally-accepted blocks, not locally-accepted ones - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in the v1 chainstate module guards against re-signing a tenure-start block by calling `signer_db.get_last_globally_accepted_block(...)`, which only returns a block once it has reached global (majority) acceptance. If the signer has already locally accepted (but not yet globally accepted) a tenure-start block for a given consensus hash, this guard returns `None` and a second, distinct tenure-change block for the same tenure passes validation and gets signed. The v2 implementation of the identical check explicitly avoids this gap by using `get_last_signed_block`, which the code comments confirm includes both locally and globally accepted blocks.

### Finding Description
The equality that must hold is: for a given tenure-start (identified by `consensus_hash`), at most one distinct block may ever be signed by this signer (uniqueness/no-equivocation).

In `stacks-signer/src/chainstate/v1.rs`, `validate_tenure_change_payload` performs, in order:
1. Parent tenure match check (line 472) [1](#0-0) 
2. `check_tenure_change_confirms_parent` (line 484) [2](#0-1) 
3. `check_parent_tenure_choice` (line 497) [3](#0-2) 
4. The final duplicate-block guard, which calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` and only rejects with `DuplicateBlockFound` if a globally accepted block already exists for that consensus hash [4](#0-3) .

None of steps 1–3 check whether the signer has already locally signed a *different* tenure-start block for the same consensus hash — they only check parent-tenure linkage and reorg legitimacy, not intra-tenure duplication. Step 4 is the only duplication guard, and it is scoped to global acceptance only.

By contrast, the v2 equivalent (`GlobalStateView::validate_tenure_change_payload`) performs the same four-step sequence but uses `signer_db.get_last_signed_block(&block.header.consensus_hash)` for the final guard, with an explicit comment stating: "Only blocks we have signed (locally or globally accepted) count here" [5](#0-4) . This confirms that the intended semantics of the duplication guard is "any block this signer has already signed," not merely "any block that has reached global consensus," and that v1's use of `get_last_globally_accepted_block` is a narrower, insufficient check.

Exploit flow: A signer locally accepts/signs tenure-start block A for consensus_hash X (recorded in signerdb as locally accepted, not yet globally accepted — e.g., insufficient other signers have yet responded). An attacker, having won the sortition slot, crafts a second, distinct block B also claiming `prev_tenure_consensus_hash` linking correctly to the real parent tenure (satisfying checks 1–3) but with different transactions/timestamp, using the same consensus hash X. When this signer evaluates B via `validate_tenure_change_payload` (v1 path), `get_last_globally_accepted_block(X)` returns `None` (since A is only locally accepted), so the function returns `Ok(())`, and the signer proceeds to sign B — producing two conflicting signed blocks (A and B) for the same tenure-start.

### Impact Explanation
This breaks the uniqueness/no-equivocation safety property for tenure-start blocks: the same signer produces two valid signatures for two conflicting blocks at the same tenure-start height. If this occurs across the threshold of signers (with each signer following this same faulty v1 logic before a block reaches global acceptance), it can produce two competing quorum certificates for the same tenure, i.e., a chain safety violation (conflicting canonical blocks). This matches the Critical severity bucket: "a signer signing an invalid, non-canonical, or conflicting block (chain safety)."

### Likelihood Explanation
Preconditions: signer is running the v1 chainstate module, has locally accepted (but not yet globally accepted) a tenure-start block for consensus hash X — a normal, frequently-occurring intermediate state during signing rounds, especially under any network latency or partial connectivity. The attacker only needs to win one miner slot (as posited) and gossip a second, distinct valid-looking `BlockProposal` for the same tenure before the first block becomes globally accepted. No majority collusion, no auth_token, and no local access are required — only crafting a competing proposal and pushing it through the normal signer message flow. This is repeatable in every tenure where the local-vs-global timing window exists.

### Recommendation
Change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` (line 506) to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the v2 implementation, so that the duplicate-tenure-start guard covers both locally and globally accepted blocks.

### Proof of Concept
```rust
// stacks-signer/src/chainstate/tests/v1.rs (illustrative)
#[test]
fn v1_duplicate_tenure_start_not_caught_when_only_locally_accepted() {
    // 1. Set up a SignerDb and seed it with a tenure-start block `block_a`
    //    for consensus_hash X, marked as *locally accepted* only
    //    (i.e., insert via the locally-accepted path, do NOT mark globally accepted).
    signer_db.insert_block(&block_a_info_locally_accepted).unwrap();

    // 2. Construct a distinct tenure-start block `block_b` for the same
    //    consensus_hash X, with a valid prev_tenure_consensus_hash matching
    //    the real parent tenure (so checks at lines 472, 484, 497 all pass).
    let result = view.validate_tenure_change_payload(
        &proposed_by, &tenure_change_b, &block_b, &mut signer_db, &client,
    );

    // 3. Assert: EXPECTED (fixed) behavior -> Err(RejectReason::DuplicateBlockFound)
    // 4. ACTUAL (buggy) behavior on v1 -> Ok(()), proving get_last_globally_accepted_block
    //    fails to see the locally-accepted block_a.
    assert!(matches!(result, Err(RejectReason::DuplicateBlockFound)));
}
```
Contrast this with the existing v2 test suite behavior (`stacks-signer/src/chainstate/tests/v2.rs`), where the equivalent seeded-locally-accepted-block scenario correctly returns `DuplicateBlockFound` via `get_last_signed_block`.
