### Title
`DefaultDistributor.claim` burns the full tranche balance but pays an unvalidated recipient — wrong or zero `_to` causes permanent loss - (File: contracts/DefaultDistributor.sol)

### Summary
`DefaultDistributor.claim` is the post-default redemption path for tranche holders. It pulls the caller's **entire** tranche balance, then pays out the proportional underlying to a caller-supplied `_to` address that is never validated (`contracts/DefaultDistributor.sol:35-41`). If `_to` is `address(0)`, a mistyped address, or a contract that cannot handle the underlying, the tranche tokens are still irrevocably escrowed into the distributor while the underlying payout is lost forever — there is no revert, retry, or recovery mechanism. This is the same bug class as the external `BitVMBridge.burn(_btc_addr)` report: a permissionless burn-and-payout function with an unvalidated destination parameter and no way to recover misdirected funds.

### Finding Description
```solidity
// contracts/DefaultDistributor.sol
function claim(address _to) external {
  require(isActive, '!ACTIVE');
  IERC20 tranche = IERC20(trancheToken);
  uint256 trancheBal = tranche.balanceOf(msg.sender);
  tranche.safeTransferFrom(msg.sender, address(this), trancheBal);
  IERC20(token).safeTransfer(_to, trancheBal * rate / ONE_TRANCHE);
}
```

Two issues compound here:

1. **No `_to` validation.** There is no `_to != address(0)` check and no check that `_to` differs from, e.g., the distributor itself or the tranche contract. Standard ERC-20 `transfer`/`safeTransfer` do not revert on `address(0)` or most arbitrary destinations, so the transaction succeeds while the funds become unspendable.
2. **Full-balance burn before payout.** `trancheBal = tranche.balanceOf(msg.sender)` claims the caller's *entire* position in one shot. A single bad `_to` argument destroys the whole recovery entitlement, not just a partial amount. Once executed, the tranche tokens sit inside the distributor (they count toward nothing for the user) and the underlying is gone; `transferToken` is owner-only and is an emergency escape for the pool, not a user-level recovery path.

The invariant broken is fair burn/payout atomicity: the receipt (tranche tokens) is consumed but the payout does not necessarily reach a controllable address.

### Impact Explanation
Permanent loss of the caller's entire default-recovery entitlement. After a borrower default, `rate` is fixed by `setIsActive` against the tranche `totalSupply`; a lender holding, e.g., 1,000,000 tranche tokens loses `1,000,000 * rate` underlying by passing `address(0)` or an inaccessible `_to`. Loss = 100% of that user's recovery, with no on-chain remedy.

### Likelihood Explanation
Likelihood is driven by user error rather than an attacker, mirroring the external report. `claim` is a permissionless, single-shot, full-balance operation exposed directly to end users (likely via a frontend where `_to` could be miswired, defaulted to zero, or set to an exchange/contract address). The function is callable by any EOA or contract; there is no economic countermeasure once `isActive` is set. Because the whole balance is claimed at once, a single mistake is total.

### Recommendation
Add `require(_to != address(0), 'IS_0')` in `claim`, matching the `Is0` guard style used elsewhere (e.g., `IdleCreditVaultWriteOffEscrow.emergencyWithdraw`). Preferably drop the `_to` parameter entirely and pay `msg.sender` (as `claimWithdrawRequest`/`claimInstantWithdrawRequest` do), or add an optional claim window + owner-mediated re-route for misdirected payouts. Optionally allow partial claims so a mistake does not consume the entire position.

### Proof of Concept
Foundry fork-style test sketch (place under `test/foundry/`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";
import {DefaultDistributor} from "../../contracts/DefaultDistributor.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MockToken is ERC20 {
  constructor(string memory n) ERC20(n, n) { _mint(msg.sender, 1_000_000e18); }
}

contract DefaultDistributorClaimToTest is Test {
  function testClaimToZeroAddressLosesFunds() public {
    MockToken underlying = new MockToken("UNDERLYING");
    MockToken tranche = new MockToken("TRANCHE");
    address owner = makeAddr("owner");
    DefaultDistributor dist = new DefaultDistributor(address(underlying), address(tranche), owner);

    // fund distributor with recovery underlying
    underlying.transfer(address(dist), 500_000e18);

    address user = makeAddr("user");
    tranche.transfer(user, 100_000e18);

    vm.prank(owner);
    dist.setIsActive(true); // rate = 500_000 / 1_000_000 = 0.5

    // user accidentally passes address(0) as recipient
    vm.startPrank(user);
    tranche.approve(address(dist), type(uint256).max);
    dist.claim(address(0));
    vm.stopPrank();

    // entire tranche balance is gone, underlying is at 0x0 and unrecoverable
    assertEq(tranche.balanceOf(user), 0);
    assertEq(underlying.balanceOf(user), 0);
    assertEq(underlying.balanceOf(address(0)), 50_000e18); // trancheBal * rate
  }
}
```

The same test with `_to` set to any inaccessible contract address (e.g., the distributor itself or a paused token contract) demonstrates the identical permanent-loss path.
