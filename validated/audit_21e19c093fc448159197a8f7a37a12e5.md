### Title
Missing role check on `GET /v2/external_initiators` discloses all initiators' AccessKey and OutgoingToken to any authenticated user regardless of role - ([File: core/web/router.go])

### Summary
`GET /v2/external_initiators` is registered as `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` with no `auth.Requires*Role` wrapper, unlike the sibling `POST`/`DELETE` routes on the same resource which are wrapped in `auth.RequiresEditRole`. Any authenticated identity that can pass `authv2`'s auth methods (`AuthenticateByToken`, `AuthenticateBySession`) - including the lowest-privileged `UserRoleView` and `UserRoleRun` users - can call this endpoint and receive every registered external initiator's `Name`, `URL`, `AccessKey`, and `OutgoingToken`.

### Finding Description
`v2Routes` mounts `eia.Index` unguarded: [1](#0-0) . In contrast, `Create`/`Destroy` for the same resource require `auth.RequiresEditRole`, showing the intended minimum privilege was "edit" but `Index` was left with no check at all - the least-restrictive routes (`GET`) in this file are usually intentionally open for read access, but here they leak sensitive fields.

`eia.Index` fetches all `bridges.ExternalInitiator` rows and maps them through `presenters.NewExternalInitiatorResource`, which serializes `AccessKey` and `OutgoingToken` verbatim: [2](#0-1) [3](#0-2) .

Note: contrary to the question's premise, an EI-authenticated identity cannot actually reach this route. `AuthenticateExternalInitiator` is only wired into the separate `userOrEI` group, which exposes just `/ping` and `POST /jobs/:ID/runs`: [4](#0-3) . The `authv2` group that contains `/external_initiators` only accepts `AuthenticateByToken` and `AuthenticateBySession`: [5](#0-4) . So the concrete attacker is a Chainlink **user** account with the lowest role (`UserRoleView`) authenticated via session or API token - not an EI credential holder. This is still a genuine role-bypass: `RequiresEditRole`/`RequiresRunRole` gate every other mutating and even some read endpoints in this controller pair, but `Index` has zero gating, allowing a view-only user to read data that should require edit privileges.

### Impact Explanation
A minimally-privileged (`view` or `run`-role) authenticated user can enumerate all external initiators' `AccessKey` and `OutgoingToken` values via a single paginated GET request, which are supposed to be scoped to the EI/admin that created them. Knowing valid `AccessKey`s materially reduces the credential space an attacker needs to brute-force (only the paired `Secret` remains unknown) for impersonating other initiators' inbound job-trigger requests, and disclosure of `OutgoingToken` may allow spoofing outbound webhook validation depending on how downstream EI implementations use it. This matches a credential/secret-disclosure impact class - unauthorized access to another principal's authentication material due to a missing authorization check.

### Likelihood Explanation
Fully feasible and repeatable: any node operator who provisions a `view`-role or `run`-role user account (a common, low-trust delegation pattern) can immediately call `GET /v2/external_initiators` with no additional privilege escalation required. The route is reachable with a single authenticated GET request and no rate limiting beyond the general authenticated rate limiter.

### Recommendation
Wrap the `GET /v2/external_initiators` route with at least `auth.RequiresEditRole` (matching the `Create`/`Destroy` routes on the same resource), or, if broader read access is intended, redact `AccessKey`/`OutgoingToken` from `presenters.ExternalInitiatorResource` for non-admin/non-edit roles.

### Proof of Concept
Go handler-level integration test (pattern following `core/web/external_initiators_controller_test.go`):
1. Seed two external initiators via the ORM (`CreateExternalInitiator`), each with distinct `AccessKey`/`OutgoingToken`.
2. Create a user with `sessions.UserRoleView` (or `UserRoleRun`) and authenticate via `AuthenticateBySession`/`AuthenticateByToken`.
3. Issue `GET /v2/external_initiators` with that low-privilege session/token.
4. Assert: current behavior returns HTTP 200 with a JSON body containing both initiators' `accessKey` and `outgoingToken` fields.
5. Expected/fixed behavior: response should be `401`/`403` for `view`/`run` roles (matching `RequiresEditRole` on `Create`/`Destroy`), or the leaked fields should be omitted for those roles.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

type ExternalInitiatorResource struct {
	JAID
	Name          string         `json:"name"`
	URL           *models.WebURL `json:"url"`
	AccessKey     string         `json:"accessKey"`
	OutgoingToken string         `json:"outgoingToken"`
	CreatedAt     time.Time      `json:"createdAt"`
	UpdatedAt     time.Time      `json:"updatedAt"`
}

func NewExternalInitiatorResource(ei bridges.ExternalInitiator) ExternalInitiatorResource {
	return ExternalInitiatorResource{
		JAID:          NewJAID(strconv.FormatInt(ei.ID, 10)),
		Name:          ei.Name,
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,
		OutgoingToken: ei.OutgoingToken,
		CreatedAt:     ei.CreatedAt,
		UpdatedAt:     ei.UpdatedAt,
	}
}
