### Title
Web API trigger callback cache keyed only by attacker-controlled `MessageId` allows cross-user response hijacking - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`message.ExtractSigner` itself correctly derives the `Sender` from the caller's own signature over the message body, so an attacker cannot forge another address's signature. However, the request-identity binding breaks down downstream: `handler.HandleLegacyUserMessage` stores the pending user callback in `h.savedCallbacks` keyed **only** by the caller-supplied `msg.Body.MessageId`, with no sender check and no "already exists" guard, unlike the sibling vault/confidentialrelay handlers.

### Finding Description
`Message.Validate()` calls `ExtractSigner()` to compute `m.Body.Sender` from the signature, and this value is trustworthy per-message [1](#0-0) . But `MessageId` is fully attacker-chosen (bounded only by length checks) and is not cryptographically bound to the sender as part of any lookup key in the WebAPI trigger flow.

In `HandleLegacyUserMessage`, after validating the incoming request, the gateway registers the user's response callback like this: [2](#0-1) 
There is no check for a pre-existing entry with the same `MessageId` (unlike `newActiveRequest` in the vault and confidentialrelay handlers, which explicitly reject collisions: [3](#0-2) ). Because of this, if a victim's request with `MessageId = X` is currently in flight (registered in `savedCallbacks["X"]`), an attacker can submit their own signed request with the same `MessageId = X` before the DON node responds. Since the map write is an unconditional overwrite under `h.mu.Lock()`, the attacker's callback silently replaces the victim's in `h.savedCallbacks["X"]`.

When the DON node later responds, `handleWebAPITriggerMessage` looks the response up purely by `msg.Body.MessageId` (no sender check) and delivers it to whatever callback is currently stored: [4](#0-3) 
This means the victim's response (which may include workflow-trigger acknowledgement data or errors, depending on what the DON returns for `MethodWebAPITrigger`) is delivered to the attacker's HTTP connection instead of the victim's, and the victim's original request either times out or never gets a reply.

### Impact Explanation
This is a genuine cross-user response confusion / request-identity binding failure: request identity (the map key) does not include the authenticated sender, exactly as the invariant in the question states should be required. The concrete impact here is scoped to the `MethodWebAPITrigger` legacy path in `core/services/gateway/handlers/capabilities/handler.go`, not the vault/confidential-relay secret-disclosure paths (those already key by `req.ID` with existence checks, and the underlying `requestcache.go` correctly uses `globalId{sender, id}` as the key). So while this confirms the general class of bug described in the question, it does not by itself demonstrate "vault/DKG secret shares or decrypted user secrets disclosed" — the vault and confidentialrelay handlers, which are the actual custodians of such secrets, already reject `MessageId`/`req.ID` collisions rather than silently overwrite. The demonstrable impact is limited to hijacking/redirecting another user's WebAPI-trigger callback response.

### Likelihood Explanation
Any internet client with an arbitrary EOA key can sign and submit a gateway message; no privileged role is required. The attacker only needs to guess or observe a victim's in-flight `MessageId` (these are often predictable/sequential or externally observable depending on client implementation) and race their own request in before the DON node's response arrives. This is straightforward to test deterministically in a unit test by directly calling `HandleLegacyUserMessage` twice with the same `MessageId` from different callbacks before invoking `HandleNodeMessage`.

### Recommendation
Change `savedCallbacks` to be keyed by `(Sender, MessageId)` (mirroring `globalId` in `core/services/gateway/handlers/common/requestcache.go`), and add an explicit "already exists" rejection in `HandleLegacyUserMessage` before storing a new callback, consistent with `newActiveRequest` in the vault and confidentialrelay handlers.

### Proof of Concept
Go handler-level test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler with `HandlerConfig` as usual; create two `api.Message` requests with `Method: MethodWebAPITrigger`, identical `Body.MessageId = "shared-id"`, but signed by two different ECDSA keys (`victimKey`, `attackerKey`) so `Body.Sender` differs after `Validate()`.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)` — assert it succeeds and registers `savedCallbacks["shared-id"]`.
3. Call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` with the same `MessageId` — assert (bug) it succeeds and silently overwrites the entry (no error returned), whereas expected/fixed behavior should return `"request ID already exists"`.
4. Simulate a DON node response for `MessageId = "shared-id"` via `HandleNodeMessage` and assert which callback channel receives it — demonstrate that `attackerCallback.Wait(ctx)` receives the response while `victimCallback.Wait(ctx)` times out, proving cross-user response delivery.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
