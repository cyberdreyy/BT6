### Title
`parse_signers` classifies owner vs. multisig authority purely by `CompiledInstruction.accounts.len()`, causing misreporting of a single-owner authority as a multisig authority (or vice versa) - ([File: transaction-status/src/parse_token.rs])

### Summary
`parse_signers` in `transaction-status/src/parse_token.rs` decides whether to emit `"owner"`/`"authority"` (single signer) or `"multisigOwner"`/`"multisigAuthority"` + `"signers"` (multisig) purely by comparing `accounts.len()` to `last_nonsigner_index + 1`, with no knowledge of whether the account at `last_nonsigner_index` is actually a multisig account on-chain. Because the SPL Token program's own `validate_owner` decides single-vs-multisig based on the *account's owner/data*, not on how many extra accounts a client chose to include in the instruction, a transaction sender can append arbitrary extra account keys after a plain single-owner authority and cause the RPC parser to mislabel it as a multisig authority with fabricated "signers".

### Finding Description
`parse_signers` is called from every `TransferChecked`/`ApproveChecked`/`BurnChecked`/`Transfer`/`Approve`/etc. arm of `parse_token`: [1](#0-0) 

Its full logic: [2](#0-1) 

`check_num_token_accounts` only enforces a *minimum* account count (`check_num_accounts`), it does not fix the account list to an exact length, so any number of extra trailing accounts is legal at the instruction-parsing layer: [3](#0-2) 

On-chain, the SPL Token/Token-2022 program's `validate_owner` decides single-owner vs. multisig by inspecting whether the account at the authority position is owned by the token program and sized like a `Multisig` account — it does *not* derive that decision from how many accounts the instruction happened to list. If the authority is a plain keypair (not multisig-owned), the program takes the "single signer" branch and never consumes/validates any trailing accounts at all; they are functionally inert padding that Solana's runtime will still happily load as valid account-index references in the `CompiledInstruction`.

An unprivileged client can therefore submit a legitimate, successfully-executing `TransferChecked` (or `Approve`/`Burn`/etc.) instruction where:
- `accounts[last_nonsigner_index]` = a normal single-owner signer wallet (real authority, `is_signer = true`),
- one extra, unrelated account key is appended at `accounts[last_nonsigner_index + 1]` (it need not even be a signer of the transaction, since the token program's single-owner branch never inspects it).

This transaction is valid and will land on-chain. When later fetched via `getTransactionParsed` (or `getConfirmedTransactionParsed`), the call sequence `parse_token -> parse_signers` sees `accounts.len() == last_nonsigner_index + 2 > last_nonsigner_index + 1` and takes the multisig branch, emitting `"multisigAuthority": <the real single owner>` and `"signers": [<arbitrary unrelated pubkey>]`, even though on-chain semantics never treated the account as a multisig or validated that pubkey as a co-signer of the authority. The reverse mislabeling (reporting a real multisig authority as a single "owner") is not symmetrically achievable, because a genuine multisig authorization always requires at least `m ≥ 1` trailing signer accounts to satisfy on-chain signature thresholds, so a real multisig transaction will always have `accounts.len() > last_nonsigner_index + 1`.

No existing guard (parameter-limit, commitment, subscription-quota, or length check) prevents this: `check_num_token_accounts` is a minimum-only bound, and there is no on-chain-data check (e.g., inspecting the referenced account's owner/data) in the RPC decoder to confirm the authority account is actually a `Multisig`.

### Impact Explanation
This is a decoder/parse-fidelity bug reachable from a single `getTransactionParsed` RPC call on attacker-controlled, previously-confirmed transaction data — it returns wrong/misleading account-role data (`"multisigAuthority"`/`"signers"` instead of `"authority"`) for a legitimate single-owner instruction. This matches the "wrong ... account data returned ... or decoder ... misreporting" category in scope, with concrete impact of misreported token authority/signer semantics to any client relying on `jsonParsed` transaction history (wallets, explorers, compliance tooling).

### Likelihood Explanation
Fully client-controlled and trivially repeatable: any wallet or SDK can construct a `TransferChecked`/`Approve`/`Burn`-family instruction with one extra, unrelated account key appended after the authority position, submit it once, and any subsequent `getTransactionParsed` call by any observer will show the misclassification. No special privileges, staking, or validator control needed — only a normal signed transaction and a standard RPC read.

### Recommendation
Do not infer single-owner vs. multisig purely from `accounts.len()`. Either:
- Fetch/inspect the referenced authority account's owner and data length (when available, e.g., via account-info lookups already used elsewhere in `transaction-status`/`account-decoder`) to confirm it is truly an SPL `Multisig` account before taking the multisig branch, or
- At minimum, document/flag this heuristic's known limitation and cross-check against the actual account for `jsonParsed` output where account state is accessible, since RPC "parsed" output is documented as best-effort but should not silently fabricate a `"signers"` list from unrelated accounts.

```rust
// transaction-status/src/parse_token.rs (test module)
#[test]
fn test_parse_signers_misclassifies_single_owner_as_multisig() {
    let source = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let destination = Pubkey::new_unique();
    let real_single_owner = Pubkey::new_unique(); // plain keypair, NOT a multisig account on-chain
    let unrelated_padding_account = Pubkey::new_unique(); // never validated as a co-signer on-chain

    let ix = transfer_checked(
        &spl_token_2022_interface::id(),
        &source,
        &mint,
        &destination,
        &real_single_owner,
        &[], // no real multisig signers
        100,
        2,
    )
    .unwrap();

    // Simulate a client appending one extra, functionally-inert account
    let mut ix = ix;
    ix.accounts.push(solana_instruction::AccountMeta::new_readonly(
        unrelated_padding_account,
        false, // not even a signer
    ));

    let message = Message::new(&[ix], None);
    let compiled_instruction = &message.instructions[0];
    let account_keys = AccountKeys::new(&message.account_keys, None);

    let parsed = parse_token(compiled_instruction, &account_keys).unwrap();
    let info = parsed.info;

    // BUG: parser reports a multisig authority + fabricated "signers" list,
    // even though on-chain validate_owner would take the single-owner branch
    // and never treat `unrelated_padding_account` as a signer of the authority.
    assert!(info.get("multisigAuthority").is_some(), "should NOT classify as multisig, but heuristic does");
    assert!(info.get("authority").is_none(), "true single-owner semantics lost");
}
```
Expected result on current code: the test demonstrates `parse_signers` reports `"multisigAuthority"`/`"signers"` for what is, per actual SPL Token program semantics, a plain single-owner authorization — confirming the fidelity mismatch.

```rust
fn parse_signers(
    map: &mut Map<String, Value>,
    last_nonsigner_index: usize,
    account_keys: &AccountKeys,
    accounts: &[u8],
    owner_field_name: &str,
    multisig_field_name: &str,
) {
    if accounts.len() > last_nonsigner_index + 1 {
        let mut signers: Vec<String> = vec![];
        for i in accounts[last_nonsigner_index + 1..].iter() {
            signers.push(account_keys[*i as usize].to_string());
        }
        map.insert(
            multisig_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
        map.insert("signers".to_string(), json!(signers));
    } else {
        map.insert(
            owner_field_name.to_string(),
            json!(account_keys[accounts[last_nonsigner_index] as usize].to_string()),
        );
    }
}
```
