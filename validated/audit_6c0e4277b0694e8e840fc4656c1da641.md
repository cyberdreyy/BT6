### Title
Unfunded instant-withdraw receipts paid at par from other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a user's *aggregate* `instantWithdrawsRequests[_user]` balance at par whenever the CDO-level `allowInstantWithdraw` flag is true, without checking whether the newest receipt (recorded in `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `pendingInstantWithdraws`) has actually been funded via `collectInstantWithdrawFunds`. This mirrors the CVE-2021-34866 bug class: a user-supplied object (a fresh, unfunded instant receipt) is interpreted as a different type (a funded receipt), letting the attacker drain underlyings that belong to other claimants and buffer depositors.

### Finding Description
The claim path in `IdleCreditVault.sol` burns and pays the full aggregate:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [1](#0-0) 

Funding state is tracked separately: `requestInstantWithdraw` increments `pendingInstantWithdraws` and `instantWithdrawsRequestsByEpoch[user][epochNumber]` [2](#0-1) , while `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` and pulls the underlying from the CDO [3](#0-2) . Nothing in the claim function distinguishes "funded" receipt epochs from "unfunded" ones — the only guard is `_transferFundedClaim`, which merely protects `defaultRecoveryReserve` [4](#0-3) .

On the CDO side, `claimInstantWithdrawRequest` only checks `allowInstantWithdraw` [5](#0-4) . That flag is set to `true` inside `startEpoch` once instant claims are covered [6](#0-5)  and is not re-scoped per receipt epoch. After `getInstantWithdrawFunds` funds epoch-N instant receipts, the flag can remain true into the following buffer window, during which new `requestInstantWithdraw` calls create receipts that will only be funded at the *next* `startEpoch`/`getInstantWithdrawFunds`. The strategy contract meanwhile holds real underlyings: buffer-phase deposits pulled in by `deposit` [7](#0-6)  and previously collected instant funding for other users' receipts.

Attack sequence (buffer phase, standard epoch mode, instant withdraws enabled):
1. Other users have funded instant receipts; the strategy holds their underlying, plus fresh buffer deposits (`totEpochDeposits`).
2. Attacker calls `requestWithdraw` on the CDO, routed to `requestInstantWithdraw`; their receipt is minted and `pendingInstantWithdraws` grows — but no funds are collected yet.
3. `allowInstantWithdraw` is still true from the prior funding round, so the attacker calls `claimInstantWithdrawRequest` and is paid the full amount at par from the strategy's pooled underlyings.
4. At the next `startEpoch`, `pendingInstant > totUnderlyings` (the attacker already removed the cash), so `collectInstantWithdrawFunds` under-funds the queue and other users' legitimate claims revert or are haircut — the attacker's withdrawal was effectively paid out of other claimants' funded reserve and new depositors' principal.

### Impact Explanation
Direct theft / dilution with quantified loss: every wei of an unfunded instant receipt claimed early is paid from underlyings earmarked for other instant claimants or from next-epoch deposits (`_toSend`/`_toBorrower` accounting in `startEpoch`). Honest instant claimants then face reverts (`NotAllowed` via insufficient balance) or lose their funded payout — a temporary-to-permanent freezing of their claim equal to the attacker's unfunded receipt size, up to the full strategy underlying balance. The "one receipt one payout, funded before claim" invariant is broken.

### Likelihood Explanation
Requires only an unprivileged KYC-passing lender holding tranche tokens. Preconditions: instant withdrawals enabled (`setInstantWithdrawParams`), a prior funding round leaving `allowInstantWithdraw = true`, and the strategy holding underlyings during the buffer (normal deposit flow). No privileged collusion is needed; the attacker only sequences `requestWithdraw` → `claimInstantWithdrawRequest` in the buffer window. Caveat: the exploitability window depends on the exact flag lifecycle — I verified `allowInstantWithdraw` is set true in `startEpoch` and after defaults, but index limits prevented confirming every write to it (e.g., whether `stopEpoch`/`_beforeStopEpoch` unconditionally clears it during the buffer). If the flag is always cleared at `stopEpoch`, the window closes and this reduces to a non-issue; a fork PoC is required to confirm.

### Recommendation
In `claimInstantWithdrawRequest`, pay only receipts whose epochs were funded: track a funded watermark per epoch (e.g., `instantFundedByEpoch` set in `collectInstantWithdrawFunds`), and revert or exclude `instantWithdrawsRequestsByEpoch[_user][epochNumber]` amounts still counted in `pendingInstantWithdraws`. Alternatively, have the CDO clear `allowInstantWithdraw` whenever `pendingInstantWithdraws != 0` at the strategy, so new unfunded receipts cannot ride on a stale flag.

### Proof of Concept
Foundry fork PoC sketch (in `test/foundry/IdleCreditVault.t.sol` harness style):

```solidity
function testUnfundedInstantReceiptPaidFromOthersFunds() external {
    // epoch 0: deposit, run, stop with low APR so instant withdraws enabled
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 4, _expectedFundsEndEpoch());

    // victim requests instant withdraw in epoch-1 buffer
    uint256 victimReq = cdoEpoch.requestWithdraw(victimTranches, address(AAtranche));
    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds();                       // victim receipt funded; allowInstantWithdraw = true

    // epoch 1 stops, epoch-2 buffer begins; attacker deposits sit in strategy
    _stopEpochAndCheckPrices(1, initialProvidedApr / 4, _expectedFundsEndEpoch());
    _depositWithUser(donor, 50_000 * ONE_SCALE, true); // fresh deposits now held by strategy

    // attacker requests instant withdraw (unfunded until next startEpoch)
    vm.prank(attacker);
    uint256 atkReq = cdoEpoch.requestWithdraw(atkTranches, address(AAtranche));

    // flag still true -> attacker claims immediately, paid from strategy balance
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - pre, atkReq);

    // next startEpoch under-funds the queue; victim's claim now reverts/shortfalls
    _startEpochAndCheckPrices(2);
    vm.prank(victim);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Expected: the attacker receives `atkReq` underlyings before any `collectInstantWithdrawFunds` for that receipt, and the strategy's residual balance can no longer cover the victim's funded receipt — demonstrating an unfunded receipt being confused for a funded one.

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
