### Title
Login endpoint returns distinguishable error messages that leak local CLI admin account existence - ([File: core/sessions/ldapauth/ldap.go])

### Summary
The `/sessions` login endpoint (`SessionsController.Create` → `ldapAuthenticator.CreateSession`) falls back to `localLoginFallback` whenever the LDAP bind fails, and this fallback re-runs the same `SELECT * FROM users WHERE lower(email) = lower($1)` local-admin lookup pattern used in `FindUser`. The raw, distinguishable error returned from this query (`sql.ErrNoRows` vs. `"invalid password"`) is passed unmodified to the HTTP layer, letting an unauthenticated caller determine whether a submitted email belongs to a local CLI admin account.

### Finding Description
`FindUser` first queries the local admin table directly with `SELECT * FROM users WHERE lower(email) = lower($1)` [1](#0-0) , and `CreateSession` (the code path invoked by the login endpoint) also calls `localLoginFallback`, which performs the same query pattern directly and returns its result verbatim to the caller: [2](#0-1) 

In `CreateSession`, the LDAP bind is attempted first; if it fails (which happens for *any* login attempt that is not a valid upstream LDAP credential — including all local admin accounts, since they don't exist in LDAP), the code falls back to `localLoginFallback` regardless of whether `FindUser` separately found a match: [3](#0-2) 

`localLoginFallback`'s behavior differs based on account existence:
- Unknown email or upstream-only (non-local) email → the `GetContext` call returns `sql.ErrNoRows`, which is returned **raw** as `err` (e.g., `"sql: no rows in result set"`).
- Known local admin email with wrong password → `"invalid password"` is returned instead.

The `SessionsController.Create` handler passes this error directly to the client: [4](#0-3) 

`jsonAPIError` places the error's message text into the JSON response body, so the raw distinguishable strings (`"sql: no rows in result set"` vs `"invalid password"`) are visible to an unauthenticated caller. No authentication, role, or signature check precedes this path — the endpoint is intentionally open to unauthenticated login attempts.

### Impact Explanation
This is a genuine unauthenticated user-enumeration issue: an attacker submitting arbitrary emails with any (wrong) password to `POST /sessions` can distinguish "email belongs to a local CLI admin account" (`"invalid password"`) from "email is unknown or is an upstream-LDAP-only user" (`"sql: no rows in result set"`). This maps to Chainlink's user-enumeration / information-disclosure impact class, enabling attackers to build a target list of local admin accounts for credential-stuffing or password-spraying attacks, since local admin accounts are high-value (they bypass LDAP-driven revalidation/reaper controls per the package's own documentation) [5](#0-4) .

### Likelihood Explanation
No credentials, roles, or prior access are required — only network access to the login endpoint and an attacker-chosen email/password pair. The behavior is deterministic and repeatable per attempt, making it a low-effort, highly reliable enumeration primitive, limited only to nodes configured with the LDAP authentication provider.

### Recommendation
Normalize all authentication failure paths in `CreateSession` and `localLoginFallback` to return a single generic error (e.g., `"invalid email or password"`) regardless of whether the failure originates from `sql.ErrNoRows`, email mismatch, or password mismatch, and ensure `SessionsController.Create` does not forward internal/db-derived error text to the client. Additionally consider constant-time behavior between the local-admin and non-local-admin branches to avoid timing-based enumeration.

### Proof of Concept
Go handler-level integration test plan for `core/sessions/ldapauth/ldap_test.go` (or a `sessions_controller_test.go` HTTP-level test):
1. Configure a `ldapAuthenticator` with a mock LDAP client whose `Bind` always fails (simulating incorrect/absent upstream credentials).
2. Seed the local `users` table with one local admin account (`admin@local.test`).
3. Call `CreateSession` (or hit `POST /sessions`) with:
   - `email=admin@local.test`, wrong password → assert error is `"invalid password"`.
   - `email=unknown@nowhere.test` (not in `users` table, not in LDAP) → assert error is/contains `"sql: no rows in result set"` (or whatever raw DB error propagates).
4. Assert the two returned error strings/response bodies differ in a way that reveals account-type existence, proving the enumeration oracle.

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}

	isLocalUser := false
	if returnErr != nil {
		// Unable to log in against LDAP server, attempt fallback local auth with credentials, case of local CLI Admin account
		// Successful local user sessions can not be managed by the upstream server and have expiration handled by the reaper sync module
		foundUser, returnErr = l.localLoginFallback(ctx, sr)
		isLocalUser = true
	}

	// If err is still populated, return
	if returnErr != nil {
		return "", returnErr
	}

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
