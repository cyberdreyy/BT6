### Title
Unbounded RocksDB Iteration in `getSignaturesForAddress` Allows Attacker-Inflated Address History to Starve RPC Threads - (File: `ledger/src/blockstore.rs`)

### Summary
`Blockstore::get_confirmed_signatures_for_address2()` scans the `address_signatures_cf` column family backwards for a given address until it collects `limit` confirmed results. The scan-termination condition is not bounded by the number of records it must skip — an attacker who inflates the number of ledger entries recorded for an address (analogous to repeatedly calling `incrementWindow()` in the original report) can force any subsequent `getSignaturesForAddress` RPC call against that address to walk an arbitrarily long chain of index entries, tying up RPC-handling resources.

### Finding Description
`get_confirmed_signatures_for_address2` builds a reverse RocksDB iterator over `address_signatures_cf` keyed by `(address, slot, transaction_index, signature)` and loops: [1](#0-0) 

The loop's only exit conditions are: (1) `address_signatures.len() == limit` (the results-so-far count), (2) the iterator hits a slot below `lowest_slot`, or (3) the iterator moves past the target address key entirely. Crucially, entries whose slot is neither rooted nor in `confirmed_unrooted_slots` are skipped with `continue` — i.e., they consume an iteration and a RocksDB read but never advance `address_signatures.len()` toward `limit`: [2](#0-1) 

This is directly analogous to `Splitter.claimForAllWindows()` in the original report: the number of loop iterations is proportional to a counter (`address_signatures_cf` entries for the address / `currentWindow`) that grows monotonically and can be inflated by an attacker simply by causing many transactions to reference the target address, including transactions that land on minority forks and are never rooted/confirmed. Just as `incrementWindow()` let anyone impersonating a `IRoyaltyVault` bump `currentWindow`, an ordinary user can submit large volumes of transactions touching an address (their own address, or any address they can name in a transaction they submit) to inflate this per-address index without any per-address cap.

Amplification: if a caller supplies an `until` signature that is not found in the ledger (`found_until = false` in the caller at `rpc.rs`), `lowest_slot` falls back to `first_available_block`, forcing the scan to walk the *entire* retained ledger history for that address rather than stopping early: [3](#0-2) 

This function is reached directly from the public `getSignaturesForAddress` JSON-RPC method (gated only by the non-privileged, commonly-enabled `--enable-rpc-transaction-history` flag, not by any special authorization): [4](#0-3) 

### Impact Explanation
A malicious but unprivileged user can (1) spam transactions that reference a chosen address over many slots — including on forks that later fail to root — to grow the address's index far beyond what is needed for legitimate history queries, then (2) issue `getSignaturesForAddress` calls (optionally with a crafted/absent `until`) that force full-depth scans. Because RPC request handling threads are a finite, shared pool, repeated or concurrent expensive scans degrade or stall `getSignaturesForAddress` (and potentially other RPC requests sharing the same worker pool) for legitimate users — a denial-of-service on the RPC request-handling path, matching the "ingest starvation / RPC crash" impact category for this bug class.

### Likelihood Explanation
Any account with `--enable-rpc-transaction-history` enabled (a standard, non-privileged RPC configuration used by many public RPC providers) is affected. No special privileges, leaked keys, or consensus-level access are required — only the ability to submit ordinary transactions and issue RPC calls, both available to any unprivileged user.

### Recommendation
Bound the number of RocksDB entries the loop is allowed to inspect per address per call (independent of `limit`), and/or cap per-address index growth / apply a hard iteration ceiling with an explicit "results truncated" response, similar to the fix recommended in the original report (bound iteration explicitly rather than relying on an attacker-influenced or unbounded termination condition). Additionally, consider rejecting or short-circuiting requests where `until` cannot be resolved to a known slot quickly, rather than falling back to a full-history scan.

### Proof of Concept
1. Attacker submits a large number of transactions that reference address `A` (as fee payer or account key) across many slots; some transactions can be arranged to land on forks that are never rooted, so they occupy `address_signatures_cf` slots but are filtered out (`continue`) rather than counted toward `limit`.
2. Attacker (or anyone) calls `getSignaturesForAddress(A, until=<unresolvable-signature>)` (or simply relies on the inflated non-confirmed entry count) against an RPC node with transaction history enabled.
3. `get_confirmed_signatures_for_address2` iterates the reverse RocksDB cursor for `A` from `highest_slot` down to `first_available_block`, performing a read for every recorded entry (confirmed or not) before it can satisfy `limit` or exhaust the range, occupying the RPC worker for the duration of the scan.
4. Repeating this call concurrently exhausts the RPC thread pool serving `getSignaturesForAddress` (and any other RPC requests sharing it), producing a denial of service.
