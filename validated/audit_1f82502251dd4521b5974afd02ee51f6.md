### Title
Unfunded instant-withdraw receipts are claimable immediately and drain other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Linux bug publishes a request into a lookup structure (`idr`) before its refcount is initialized, so an early consumer (`p9_read_work`) acts on a half-formed request and frees it prematurely. The analog in `IdleCreditVault` is the instant-withdraw flow: `requestInstantWithdraw` publishes a claimable receipt (`_mint` to the user plus `instantWithdrawsRequests[_user] += _amount`) **before** the request is funded, and `claimInstantWithdrawRequest` lets that receipt consume arbitrary strategy-held underlying — including underlying that `collectInstantWithdrawFunds` already collected to back *other* users' funded-but-unclaimed instant receipts.

### Finding Description
In `requestInstantWithdraw` (lines 356–375), the strategy burns the CDO's tokens, mints receipt tokens to the user, and records `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws`. Nothing at request time marks the request as "unfunded" in a way that later gates the claim.

`claimInstantWithdrawRequest` (lines 380–393) then:

1. Reads `amount = instantWithdrawsRequests[_user]` — nonzero immediately after the request.
2. Burns the freshly minted receipt tokens (no-op economically).
3. Zeroes the request and calls `_transferFundedClaim(_user, amount)`, which transfers `underlyingToken.balanceOf(address(this))` up to `amount` with **no epoch check and no funded/unfunded distinction**.

`_transferFundedClaim` (lines 897–907) only guards the `defaultRecoveryReserve` — and even that guard is bypassed entirely when `defaultRecoveryReserve == 0`. There is no check that the claim's funding was actually collected via `collectInstantWithdrawFunds` (lines 398–403), which is the only function that pulls underlying from the CDO and decrements `pendingInstantWithdraws`. Funding state and claim state are tracked in separate variables that are never cross-checked at claim time — the same "published before initialized" ordering defect as the kernel `idr`/`refcount` race.

Attack sequence:

1. User A (honest) requests an instant withdraw in epoch N. At `stopEpoch`, the CDO calls `collectInstantWithdrawFunds`, pulling A's underlying into the strategy and decrementing `pendingInstantWithdraws`. A's claim sits funded but unclaimed (claims are user-initiated and lag funding by design).
2. Attacker B, a KYC-passing tranche holder, calls `requestInstantWithdraw(amount)` on the CDO during epoch N+1. The strategy mints B receipt tokens and sets `instantWithdrawsRequests[B] = amount`; `pendingInstantWithdraws` increases but no underlying is collected.
3. B immediately calls `claimInstantWithdrawRequest` (no waiting period exists for instant claims — that is their purpose). `_transferFundedClaim` sees `defaultRecoveryReserve == 0` and transfers A's funded underlying to B.
4. A's subsequent claim reverts on insufficient balance or pays less — A's funds are permanently stolen by B.

The same ordering applies whenever the strategy transiently holds underlying (e.g., deposits in `deposit()` before they are forwarded to the borrower), making the window wider than just funded instant claims.

### Impact Explanation
Direct theft: B receives underlying at par for a receipt that was never funded, paid out of principal/claims belonging to other users. A's funded claim becomes unpayable, so the theft is permanent, not a temporary freeze. Loss equals the strategy's spendable underlying balance at claim time, up to B's request size, bounded only by how many tranche tokens B can acquire.

### Likelihood Explanation
Medium-high. Preconditions are modest: a funded-but-unclaimed instant withdraw must exist in the strategy, which is the normal resting state between `collectInstantWithdrawFunds` and a user's manual claim. B needs only tranche tokens and KYC clearance — both unprivileged-attacker capabilities. No privileged-role misbehavior, oracle manipulation, or default is required; the exploit runs entirely in the running/buffer epoch phases with two ordinary user transactions. The one caveat is that the CDO-side wrapper (`IdleCDOEpochVariant`, which contains its own instant-withdraw logic per the grep hits) was not fully inspected — if it independently gates claims on collected funding, exploitation is blocked at that layer; the strategy-level defect stands regardless.

### Recommendation
Track funded vs. pending instant receipts explicitly: record per-request (or per-epoch) funded amounts at `collectInstantWithdrawFunds` time and let `claimInstantWithdrawRequest` pay only the funded portion, or revert until `collectInstantWithdrawFunds` has covered `instantWithdrawsRequests[_user]`. Equivalently, extend the `_transferFundedClaim` reserve-style guard to a general "funded instant balance" invariant so unfunded receipts can never consume collected underlying.

### Proof of Concept
```solidity
// Foundry fork test sketch against IdleCreditVault + IdleCDOEpochVariant
function testUnfundedInstantClaimDrainsFundedClaim() external {
    // --- setup: epoch running, user A deposits and requests instant withdraw ---
    _depositWithUser(userA, 1000e6);
    cdoEpoch.requestInstantWithdraw(amtA, tranche, userA);   // receipt minted to A

    // --- honest stopEpoch collects funding for A's claim ---
    _stopCurrentEpoch();                                     // CDO calls collectInstantWithdrawFunds
    assertEq(underlying.balanceOf(address(strategy)), amtA); // A's funds now sit in strategy
    assertEq(strategy.pendingInstantWithdraws(), 0);         // fully funded remainder = 0

    // --- attacker B requests an instant withdraw; NO funding collected ---
    _depositWithUser(attackerB, amtB);                       // B holds tranche tokens
    uint256 balBefore = underlying.balanceOf(attackerB);
    cdoEpoch.requestInstantWithdraw(amtA, tranche, attackerB); // pendingInstantWithdraws += amtA

    // --- B claims immediately; request was never funded ---
    cdoEpoch.claimInstantWithdrawRequest(attackerB);
    assertEq(underlying.balanceOf(attackerB) - balBefore, amtA); // B stole A's funded claim
    assertEq(underlying.balanceOf(address(strategy)), 0);

    // --- A's claim is now unpayable ---
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest(userA);
}
```

Note: the exact CDO entry-point names may differ (`IdleCDOEpochVariant` wraps `requestInstantWithdraw`/`claimInstantWithdrawRequest`); the PoC should call whatever user-facing functions forward to the strategy. If the CDO wrapper itself blocks the unfunded claim, the strategy-level gap remains as defense-in-depth debt but the exploit path is closed.
