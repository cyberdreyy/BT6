This is a legitimate finding. `rescueFunds` in `contracts/BaseEscrow.sol` contains no check that distinguishes the escrow's live, committed principal from genuinely "stuck" assets — it will transfer *any* `token`/`amount` the caller specifies to `msg.sender`, as long as the caller is the immutables-encoded `taker` and `block.timestamp` is past `rescueStart`.

### Title
Taker can use `rescueFunds` to steal the maker's source-chain principal instead of returning it via `cancel` - (File: `contracts/BaseEscrow.sol`)

### Summary
`EscrowSrc` locks the maker's tokens at deployment and is designed to release them back to the maker via `cancel`/`publicCancel` if the swap is not completed (e.g., the destination escrow is never created). However, `BaseEscrow.rescueFunds` provides an unrestricted alternate exit for the `taker`: after `RESCUE_DELAY` elapses, the taker can call `rescueFunds(immutables.token, immutables.amount, immutables)` and receive the maker's original, still-live principal directly, bypassing the intended maker-refund path entirely.

### Finding Description
`rescueFunds` is gated only by:
- `onlyCaller(immutables.taker.get())`
- `onlyValidImmutables(immutables.hash())`
- `onlyAfter(immutables.timelocks.rescueStart(RESCUE_DELAY))` [1](#0-0) 

None of these checks verify that the requested `token`/`amount` correspond to funds that are "extra"/accidentally sent rather than the exact swap principal (`immutables.token`, `immutables.amount`) that is still sitting in the contract awaiting `cancel`. Because `cancel`/`publicCancel` in `EscrowSrc` have no upper time bound (`onlyAfter` only, no `onlyBefore`), the maker-refund path technically remains "available" forever, but nothing stops the `taker` from racing ahead and draining the exact same balance for themselves via `rescueFunds` once `RESCUE_DELAY` has passed. [2](#0-1) 

In the scenario described (partial fill around the 25% band, destination escrow never created), the source escrow sits fully funded with the maker's principal. If the taker simply never calls `withdraw`, never triggers `cancel`, and no third party calls `publicCancel` before `RESCUE_DELAY` elapses, the taker can unilaterally call `rescueFunds(immutables.token, immutables.amount, immutables)` and redirect the maker's tokens to themselves the instant the rescue window opens — a strict race the taker controls (they know exactly when `rescueStart` occurs and can submit at that block).

### Impact Explanation
This is direct theft of the maker's principal, which should have been refunded via `cancel`. It matches the Critical bounty tier: "direct theft of user funds at rest or in motion... caused by these production contracts."

### Likelihood Explanation
Requires only an unprivileged taker (any address that filled the order) to withhold action until `RESCUE_DELAY`, and to front-run any `publicCancel` caller. No admin/governance/relayer trust assumptions are needed — only that no one else calls `cancel`/`publicCancel` first, which is plausible for low-visibility or low-liquidity orders that lack active keeper coverage of the access-token holder set.

### Recommendation
`rescueFunds` should not be able to touch the swap's live principal balance for the `immutables.token`. Practical mitigations include tracking whether the escrow has already resolved (withdrawn/cancelled) and blocking rescue of `immutables.token` up to `immutables.amount` while unresolved, or requiring `rescueFunds` to only move balances in excess of `immutables.amount` for `immutables.token` (i.e., true "stuck"/accidental deposits), leaving the committed principal exclusively reachable through `withdraw`/`cancel`/`publicCancel`.

### Proof of Concept
1. Maker fills part of an order (~25% partial fill); `EscrowSrc` clone is deployed and funded with the maker's principal via `postInteraction`. [3](#0-2) 
2. Taker never creates the corresponding destination escrow, so the swap can never complete via secret reveal.
3. Taker (and everyone else with the access token) takes no action through `SrcWithdrawal`, `SrcPublicWithdrawal`, `SrcCancellation`, and `SrcPublicCancellation` windows.
4. Once `block.timestamp >= immutables.timelocks.rescueStart(RESCUE_DELAY)`, the taker calls:
```solidity
escrowSrc.rescueFunds(immutables.token, immutables.amount, immutables);
```
5. `_uniTransfer` sends `immutables.amount` of `immutables.token` (the maker's full principal) to `msg.sender` (the taker), even though `cancel`/`publicCancel` — which would have returned it to the maker — was still technically callable. [4](#0-3)
