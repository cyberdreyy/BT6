### Title
Multisig factory `create` has no callback to verify `new` succeeded, permanently freezing deposits when account creation succeeds but init fails - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` builds a single batched promise (`create_account` + `deploy_contract` + `transfer` + `function_call("new", ...)`) but, unlike `lockup-factory::create` and `staking-pool-factory::create_staking_pool`, it attaches no `.then(...)` callback to check `is_promise_success()` and no logic to refund the deposit or otherwise recover if the `new` call fails [1](#0-0) . If the account/contract/transfer actions succeed but `new` runs out of gas or otherwise reverts (e.g. because `env::prepaid_gas() - CREATE_CALL_GAS` leaves too little gas for `new`'s execution), the new account is left deployed, funded with the attacher's deposit, but uninitialized (`state_exists()` false), and there is no factory-side mechanism to reclaim the funds.

### Finding Description
The binding that should hold is: `deposit locked into <name>.<factory>` is provably released back to the caller when `new` fails, i.e. `attacker_balance_after_failed_init == attacker_balance_before - tx_fees` (deposit returned). In `multisig-factory/src/lib.rs::create`, this equality is never enforced because there is no callback that inspects the promise result of the `function_call` to `new`:

```
multisig-factory/src/lib.rs:34-49
Promise::new(account_id)
    .create_account()
    .deploy_contract(CODE.to_vec())
    .transfer(env::attached_deposit())
    .function_call(
        b"new".to_vec(),
        ...
        env::prepaid_gas() - CREATE_CALL_GAS,
    )
```

Compare this to `lockup-factory::create`/`on_lockup_create` and `staking-pool-factory::create_staking_pool`/`on_staking_pool_create`, both of which `.then(ext_self::on_..._create(...))`, call `assert_self()`, check `is_promise_success()`, and on failure execute `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` to refund the caller [2](#0-1) [3](#0-2) . The multisig factory has no analogous `on_create` callback at all.

The `create_account`, `deploy_contract`, and `transfer` actions in a NEAR batched promise each succeed independently of whether the subsequent `function_call` to `new` succeeds; a failure in `new` (e.g. insufficient gas because `env::prepaid_gas() - CREATE_CALL_GAS` is small, or the attacker deliberately calls with prepaid gas just above `CREATE_CALL_GAS` so the remaining gas is too small for `new` to complete) does not roll back the account creation, contract deployment, or deposit transfer — those are already committed as part of the receipt. Since there's no `.then()` callback watching the result, the factory does nothing when `new` fails: the account remains created, funded, and with the multisig contract code deployed but no state (`state_exists() == false`), so no owner/members were ever set and there is no path to call `new` again (the wasm entry likely panics with "already initialized" only if state exists — but since state doesn't exist, technically `new` could be re-invoked by anyone knowing the account name, though the factory provides no interface to do so, and the deposited NEAR sits in an account nobody can administer through the intended multisig API). The attacker can create this state for themselves or, more importantly, for any account name — including one a legitimate user later intends to use — since account creation is first-come-first-served by name.

### Impact Explanation
Funds attached to the `create` call (deposit for storage/operation of the new multisig) become stuck in an account with deployed-but-uninitialized multisig code and no callback-driven refund, matching "funds permanently frozen" under the Critical impact category. Unlike the lockup and staking-pool factories, which both guarantee a refund via `on_lockup_create`/`on_staking_pool_create` on failure, the multisig factory has no such safety net, so any accidental or attacker-induced init failure (out-of-gas due to low prepaid gas) freezes the attached deposit with no recovery path through this contract. This is repeatable across any account name the attacker chooses to sacrifice, though the primary loss is to the caller's own deposit — the severity concern is the invariant break itself (an under-funded create leaving a half-initialised, frozen multisig) rather than third-party fund theft.

### Likelihood Explanation
The attacker only needs to call `create` with `prepaid_gas` set just high enough to avoid the `env::prepaid_gas() - CREATE_CALL_GAS` underflow panic (which would abort the whole transaction and prevent any account creation) but low enough that the gas remaining for the `new` call is insufficient to complete initialization. This requires no privileges beyond being able to send a transaction with a chosen `gas` value and deposit — entirely within the attacker's control and trivially reproducible.

### Recommendation
Add a `.then(ext_self::on_create(...))` callback to `MultisigFactory::create` that calls `assert_self()`, checks `is_promise_success()`, and on failure either deletes/refunds the deposit back to `env::predecessor_account_id()` (mirroring `lockup-factory::on_lockup_create` and `staking-pool-factory::on_staking_pool_create`), and reserve enough fixed gas for the callback itself (as `gas::CALLBACK` does in the other factories) rather than relying solely on `env::prepaid_gas() - CREATE_CALL_GAS` for the `new` call.

### Proof of Concept
Using `near-sdk`'s `testing_env!`/`PromiseResult` pattern (as already used in `lockup-factory`/`staking-pool-factory` test suites):
1. Call `MultisigFactory::create(name, members, num_confirmations)` with `attached_deposit = X` and `prepaid_gas` set just above `CREATE_CALL_GAS` (e.g. `CREATE_CALL_GAS + 1_000_000_000_000`), simulating gas too low for `new` to succeed.
2. Simulate the receipt execution with `testing_env_with_promise_results(context, PromiseResult::Failed)` for the `new` function_call's outcome.
3. Assert there is no callback method (`on_create`) exposed on `MultisigFactory` to inspect and no `Promise::new(predecessor_account_id).transfer(...)` issued anywhere in `create` — confirm by grepping `multisig-factory/src/lib.rs` for `is_promise_success`/`ext_self`/`.then(` (absent), contrasted with `lockup-factory/src/lib.rs` and `staking-pool-factory/src/lib.rs` which contain these (present) [4](#0-3) .
4. Because no unit test in the repo can call the deployed account's `new` state directly without `near-workspaces`/`near-sdk-sim` sandbox to inspect the created account's `state_exists()` and balance after a failed `new`, full confirmation requires a `near-workspaces` integration test that: deploys `MultisigFactory`, calls `create` with constrained gas causing `new` to fail (assert via returned execution outcome), then queries the created sub-account's state (`view_state` returns empty / `state_exists()` false) and balance (still holds the attached deposit), demonstrating `attacker_balance_after != attacker_balance_before - tx_fees` (no refund occurred) — violating the equality stated above.

const CODE: &[u8] = include_bytes!("../../multisig2/res/multisig2.wasm");

/// This gas spent on the call & account creation, the rest goes to the `new` call.
const CREATE_CALL_GAS: u64 = 50_000_000_000_000;

#[derive(Serialize, Deserialize)]
#[serde(crate = "near_sdk::serde", untagged)]
pub enum MultisigMember {
    AccessKey { public_key: Base58PublicKey },
    Account { account_id: AccountId },
}

#[near_bindgen]
#[derive(BorshSerialize, BorshDeserialize, Default)]
pub struct MultisigFactory {}

#[near_bindgen]
impl MultisigFactory {
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
}

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
