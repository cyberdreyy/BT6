## Title
Node-side StackerDB listener double-counts a single signer's weight across both accept and reject tallies when a signer flips its vote (Reject → Accept) — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The stacks-node `StackerDBListener` — which the mining coordinator (`SignerCoordinator::propose_block` / `get_block_status`) relies on to decide whether a proposed block was globally accepted or rejected — tallies `total_weight_approved` and `total_weight_rejected` from two **independently-guarded** structures. A single signer that first rejects a block and later legitimately (or maliciously) accepts the *same* block has its weight counted in *both* totals, breaking the invariant that a signer's weight should count toward exactly one side of the tally.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the `Accepted` branch gates adding weight to `total_weight_approved` on `block.gathered_signatures.contains_key(&slot_id)`, then unconditionally inserts the slot into `responded_signers`: [1](#0-0) 

The `Rejected` branch gates adding weight to `total_weight_rejected` on `block.responded_signers.insert(slot_id)` (i.e. "have we ever recorded a response for this slot before, regardless of which kind"): [2](#0-1) 

Because these two guards are asymmetric:
- **Accept-then-Reject**: the reject branch's `responded_signers.insert(slot_id)` returns `false` (already inserted by the earlier accept), so the reject weight increment is skipped — no double count.
- **Reject-then-Accept**: the accept branch only checks `gathered_signatures` (empty for this signer, since they never accepted before), so it adds the signer's weight to `total_weight_approved` — even though that same signer's weight is already sitting in `total_weight_rejected` from their earlier rejection. Nothing ever removes/decrements the stale entry.

This means a single signer, using only their own key (no majority, no other signer's key needed), can have their weight represented on **both** sides of the ledger simply by sending a `BlockRejection` followed later by a `BlockAccepted` for the same `signer_signature_hash`. This is not even necessarily malicious: the `stacks-signer` protocol itself supports a signer reconsidering and accepting a block it previously rejected once the reject reason becomes stale (`should_reevaluate_reject_reason`, documented in `docs/signer-flows.md`), so this vote-flip is a normal, expected occurrence, not just a crafted edge case.

### Impact Explanation
`SignerCoordinator::get_block_status` evaluates the **rejection** condition before the **acceptance** condition: [3](#0-2) 

Because `total_weight_rejected` can retain phantom weight from a signer who has since switched to accept, `total_weight_rejected + weight_threshold > total_weight` can be reached without a genuine blocking minority (>30%) of distinct signers currently opposing the block. This can cause the miner to spuriously treat an actually-signable block as `SignersRejected`, permanently or temporarily banning transactions (`permanently_excluded_txids` / `temporarily_excluded_txids`) based on inflated per-txid weight that includes a stale, superseded rejection. This is a liveness wedge on the mining/coordination path: blocks that should reach consensus can be treated as rejected, and transactions can be unfairly excluded from future block templates, based on double-counted weight from a single signer's outdated vote.

### Likelihood Explanation
This requires only one signer (using their own valid key) to send a `Rejected` response and later an `Accepted` response for the same block — a sequence the stacks-signer client itself performs as normal behavior when reconsidering a stale rejection reason. No majority collusion, no other signer's key, and no StackerDB auth token compromise is needed. Any signer operator (or a compromised/misbehaving single signer) can trigger it deliberately by replaying a crafted `Rejected` chunk followed by an `Accepted` chunk to its own slot.

### Recommendation
Track exactly one recorded weight-contribution state per slot (e.g., store an enum `{Accepted, Rejected}` per `slot_id` instead of two independently-updated collections), and when a signer's message changes vote for the same block, remove/adjust the previously counted weight from the stale side before adding to the new side, so `total_weight_approved` and `total_weight_rejected` cannot both include the same signer's weight simultaneously.

### Proof of Concept
1. Node proposes block `B` (`signer_signature_hash = H`) to the signer set via `SignerCoordinator::propose_block`.
2. Malicious/normal signer `S` (weight `w`) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `H`. `stackerdb_listener.rs` records `responded_signers.insert(slot_S)` → `total_weight_rejected += w`.
3. Signer `S` later sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `H` (a legitimate reconsideration per `should_reevaluate_reject_reason`, or simply crafted by `S`).
4. In the `Accepted` handler, `block.gathered_signatures.contains_key(&slot_S)` is `false` (first acceptance), so `total_weight_approved += w` is applied unconditionally — `total_weight_rejected` is never decremented.
5. Now `total_weight_approved + total_weight_rejected` exceeds `total_weight` by `w`; if enough such flips occur (or combined with a few genuinely rejecting signers), `total_weight_rejected + weight_threshold > total_weight` can trip in `get_block_status` even though the real, current rejecting weight is below the 30% blocking minority, causing the miner to wrongly treat a signable block as rejected and to ban transactions based on the inflated per-txid weight.
