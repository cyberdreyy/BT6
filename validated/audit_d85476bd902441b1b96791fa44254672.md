### Title
Transient ERC4626 liquidity exhaustion can indefinitely block epoch settlement and queued withdrawals - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower.onStopEpoch` treats a covered but failed `vault.withdraw` as a hard transaction revert rather than allowing the epoch stop to fail over to the borrower-default path. [1](#0-0)  An unprivileged user of the configured ERC4626 vault can temporarily withdraw available underlying liquidity immediately before the epoch stop, causing `stopEpoch` to revert while `isEpochRunning` remains true and pending withdrawal receipts remain unfunded. [2](#0-1) 

### Finding Description
During a running programmable-borrower epoch, manager-called `IdleCDOEpochVariant.stopEpoch` first invokes `IProgrammableBorrower.onStopEpoch` for the full cash amount needed for withdrawals, even when interest is minted rather than pulled. [3](#0-2)  If the programmable borrower does not already hold enough underlying, it checks that the current vault-share value economically covers the shortfall, then calls `vault.withdraw`. [4](#0-3)  A failure inside that withdrawal is caught and rethrown as `StopEpochVaultLiquidityUnavailable`, so the CDO does not enter its borrower-default handler. [5](#0-4) 

Because the revert occurs before `getFundsFromBorrower`, `collectWithdrawFunds`, the epoch-state reset, and `epochNumber` advancement, all state survives unchanged. [6](#0-5)  `IdleCreditVault.claimWithdrawRequest` still rejects a request from the same epoch until `epochNumber` has advanced, so a lender cannot exit through the funded-withdrawal path while the repeated stop failures persist. [7](#0-6) 

### Impact Explanation
An attacker who can consume the external vault's available liquidity can freeze the CDO at the running-epoch boundary for as long as the vault refuses covered withdrawals. [8](#0-7)  For example, with `pendingWithdraws = 10,000 USDC` and only `9,999 USDC` withdrawable from the ERC4626 vault, every settlement call reverts even though `convertToAssets` reports that the programmable borrower's shares cover the shortfall. [4](#0-3) 

The affected amount is the entire pending withdrawal basis plus the active NAV that cannot move to the buffer phase; in a vault with `N` underlying of pending receipts, `N` underlying is temporarily frozen. [9](#0-8)  The protocol eventually recovers if vault liquidity returns or owner/manager successfully unwinds through `emergencyExitVault`, so the impact is temporary freezing rather than direct theft or permanent insolvency. [10](#0-9) 

### Likelihood Explanation
The attacker only needs to be an ordinary ERC4626 vault user, not the borrower, owner, manager, guardian, or another trusted role. [11](#0-10)  They can observe the published `epochEndDate`, drain or occupy the vault's withdrawable liquidity just before settlement, and restore it later after repeating the block for multiple settlement attempts. [2](#0-1) 

The attack is constrained by the external vault design and liquidity conditions: it does not work when the programmable borrower already holds enough cash on hand, when the shares do not economically cover the requested amount, or when the vault has no transient withdrawal limit. [12](#0-11)  Where the integrated vault supports flash liquidity withdrawal or utilization-driven withdrawal limits, however, no protocol privilege is needed to trigger the revert. [5](#0-4) 

### Recommendation
Add a bounded settlement-failure mechanism rather than allowing an external ERC4626 withdrawal failure to remain retryable indefinitely. [5](#0-4)  For example, record a settlement-failure timestamp or count in `ProgrammableBorrower`, permit `IdleCDOEpochVariant` to treat failures after the configured grace period as a defaultable liquidity failure, and allow owner/manager emergency vault redemption to update the same pending liability accounting. [13](#0-12) 

### Proof of Concept
A Foundry PoC can reuse the existing `MockStopEpochLiquidityVault` withdrawal-limit harness, which models an ERC4626 vault whose share valuation remains positive while withdrawals revert. [14](#0-13) 

```solidity
function testExternalVaultLiquidityBlocksEpochSettlement() public {
    uint256 depositAmount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(depositAmount);

    // A KYC-passing lender opens a normal withdrawal before epoch start.
    vm.prank(lender);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Attacker action in a real vault: borrow/redeem available cash so the
    // programmable borrower's shares still cover the liability, but
    // vault.withdraw(pendingWithdraws) reverts due to liquidity/maxWithdraw.
    vault.setWithdrawLimit(strategy.pendingWithdraws() - 1);

    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning(), "epoch remains running");
    assertFalse(cdoEpoch.defaulted(), "covered withdrawal failure is not defaulted");
    assertEq(strategy.pendingWithdraws(), depositAmount, "receipt remains unfunded");

    vm.expectRevert(NotAllowed.selector);
    vm.prank(lender);
    cdoEpoch.claimWithdrawRequest();

    // Repeat the same sequence while the attacker keeps vault liquidity below
    // pendingWithdraws. Once liquidity is restored, settlement succeeds.
    vault.setWithdrawLimit(type(uint256).max);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
}
```

```text
  /// @notice Handle borrower default
  function _handleBorrowerDefault(uint256 funds) internal {
    defaulted = true;
    // Do not reopen instant claims here. They remain disabled when funding is pending;
    // successful full funding is the only path that enables them before finalization.

    if (isProgrammableBorrower) {
      IProgrammableBorrower(_borrower()).onDefault();
    }

    // deposits should be already prevented
    if (!paused()) {
      _pause();
    }

    // stop the current epoch
    isEpochRunning = false;

    // prevent withdrawals requests
    allowAAWithdrawRequest = false;
    allowBBWithdrawRequest = false;

    emit BorrowerDefault(funds);
  }
```
