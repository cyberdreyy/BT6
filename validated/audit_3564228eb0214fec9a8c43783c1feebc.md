### Title
Buffer-phase donations inflate `getContractValue()` in `_updateAccounting`, enabling a first-depositor share-inflation attack that steals subsequent depositors' funds - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault._deposit` calls `_updateAccounting()`, which prices tranches against `getContractValue()`. That value is `strategyToken balance + raw token balance - unclaimedFees` (lines 125-128). During the buffer phase no interaction skims raw underlying donations: `_skimDonatedAssets()` is only invoked inside `updateAccounting`, `finalizeDefault`, `startEpoch`, `_stopEpoch`, and `depositDuringEpoch`. An attacker can therefore be the first depositor with a dust amount, donate a large raw `token` transfer, and watch the next victim's deposit be priced against the donation-inflated `priceAA`/`priceBB`, minting them nearly zero tranche tokens while their principal accrues to the attacker's single share.

### Finding Description
Bug-class mapping: "maliciously crafted input corrupts memory handling → arbitrary code execution" maps to "unsolicited external token transfer corrupts accounting state → attacker-controlled payout", i.e. the vault share-inflation / donation surface (`_deposit`, `_mintSharesAtCurrPrice`, `getContractValue`, `_skimDonatedAssets`).

Concrete trace in buffer phase (epoch not running, `isEpochRunning == false`, unpaused):

1. Attacker (KYC-passing lender) calls `depositAA(1 wei)` → minted 1 tranche token at `priceAA = oneToken`; `lastNAVAA = 1`.
2. Attacker `token.transfer(cdo, D)` — a raw donation. `getContractValue()` now returns `1 + D` (strategy tokens) + raw `D`... precisely: the dust was forwarded to the strategy so `strategyToken balance ≈ 1`, plus raw token balance `D`, minus fees → `nav ≈ 1 + D` while `lastNAV ≈ 1`.
3. Victim calls `depositAA(V)`. Inside `_deposit` (lines 191-212), `_updateAccounting()` runs first: `nav > _lastNAV`, gain `D` is split and crystallized into `priceAA ≈ D` per share, and `unclaimedFees` takes `D * fee / FULL_ALLOC`. Note the accounting path uses `getContractValue()` (raw-token-inclusive), *not* `_managedContractValue()` which deliberately excludes raw underlyings.
4. `_mintSharesAtCurrPrice` computes `V * ONE_TRANCHE_TOKEN / priceAA ≈ V * ONE / D`. For `D > V`, the victim mints 0 or dust shares while `_mintShares` adds the full `V` to `lastNAVAA` — the victim's principal is attributed to NAV but they hold no claim on it.
5. Attacker calls `requestWithdraw(0, AATranche)` (or withdraws, depending on variant). `_trancheToUnderlyings` values their 1 share at the inflated price ≈ `1 + D + V` underlyings; the burn/receipt is honored at `claimWithdrawRequest` / `claimInstantWithdrawRequest` from `IdleCreditVault`, paying out the victim's real principal plus the donation.

The skim in `depositDuringEpoch`, `startEpoch`, `_stopEpoch`, and `finalizeDefault` proves the developers consider raw CDO-held underlyings non-NAV donations — `_managedContractValue()`'s docstring states "Raw underlyings held by the CDO are excluded because unsolicited transfers are skimmed on interactions" (lines 131-133). But that invariant is not enforced on buffer-phase `_deposit`/`requestWithdraw`/`_withdraw`, where `getContractValue()` counts them directly.

### Impact Explanation
Direct theft. Any unprivileged KYC-passing lender who is first into a fresh or fully-redeemed AA tranche (or who can get dust supply while NAV is low) can sandwich an honest depositor: deposit dust → donate → victim deposits → attacker requests withdrawal. The attacker extracts approximately the victim's full deposit minus donation cost; with `D` sized so the victim mints 0 shares, attacker profit ≈ `V - dust`. Loss to the victim is their entire principal; solvency/fair-mint invariant ("shares ∝ NAV contributed") is broken.

### Likelihood Explanation
- Attacker requirements are minimal: an unprivileged KYC-passing lender and capital for the donation (returned at withdrawal, so the only real cost is gas).
- No privileged actor needs to be malicious; the owner/guardian merely must not call `updateAccounting` between the donation and the victim deposit, and the whole sequence can be executed atomically around the victim's mempool transaction.
- The vulnerable window (tranche supply exists but is tiny, or first deposit) occurs naturally at vault deployment and after full exits.
- Existing guards do not stop it: `_guarded` only caps deposit size, `_checkSameBlock` only blocks same-block deposit→withdraw for the *same* caller in the base `_withdraw`, the skim is absent from the buffer-phase path, and `skipDefaultCheck`/`Default` reverts only trigger on losses, not donation "gains".

### Recommendation
Call `_skimDonatedAssets()` at the top of `_deposit` and at the top of `requestWithdraw`/`_withdraw`/`_updateAccounting` entry points during the buffer phase, or make `_updateAccounting` use `_managedContractValue()` semantics so raw underlyings never enter NAV. Additionally enforce a minimum initial mint and/or a dead-share lock on first deposit to remove the classic inflation surface entirely.

### Proof of Concept
Foundry fork PoC (against the credit-vault fixture in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testBufferPhaseDonationInflatesSharePrice() external {
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");
    uint256 D = 2_000_000 * ONE_SCALE;
    uint256 V = 1_000_000 * ONE_SCALE;

    // Attacker is first depositor with dust
    deal(defaultUnderlying, attacker, D + 1);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), type(uint256).max);
    cdoEpoch.depositAA(1);
    // Raw donation: no skim occurs because no privileged interaction runs
    IERC20Detailed(defaultUnderlying).transfer(address(cdoEpoch), D);
    vm.stopPrank();

    // Victim deposit is priced against donation-inflated priceAA
    deal(defaultUnderlying, victim, V);
    vm.startPrank(victim);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), V);
    uint256 mintedVictim = cdoEpoch.depositAA(V);
    vm.stopPrank();

    // Victim mints ~0 shares for a full deposit
    assertLt(mintedVictim, ONE_SCALE, "victim under-minted");

    // Attacker requests withdrawal of entire tranche balance at inflated price
    vm.prank(attacker);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Attacker's claim ≈ D + V (donation + victim principal)
    assertGt(requested, D + V - 100, "attacker drains victim principal");
}
```

Uncertainty note: exact claim-settlement plumbing (`claimWithdrawRequest` liquidity sourced from `IdleCreditVault`) was not fully traced in this pass, but the share-under-minting and NAV attribution in `_deposit`/`_updateAccounting`/`_mintShares` are confirmed by the cited code, and the strategy pays receipts 1:1 in `token`, so the inflated claim is redeemable against real vault assets once an epoch cycle completes.
