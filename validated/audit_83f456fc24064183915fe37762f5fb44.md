### Title
`parse_bpf_upgradeable_loader` miscomputes ELF offset for immutable ProgramData accounts, corrupting `jsonParsed` output for Core BPF migrated programs - ([File: account-decoder/src/parse_bpf_loader.rs])

### Summary
`Bank::new_target_program_data_account` (`runtime/src/bank/builtins/core_bpf_migration/mod.rs:76-121`) always places the ELF payload at the fixed offset `UpgradeableLoaderState::size_of_programdata_metadata()`, independent of whether `upgrade_authority_address` is `Some` or `None`, matching the convention used by every other writer of this account type in the codebase (`programs/bpf_loader/src/lib.rs:258`, `:441`, `:972`). However, `parse_bpf_upgradeable_loader` (`account-decoder/src/parse_bpf_loader.rs:43-52`) computes the offset conditionally, subtracting `size_of(Pubkey)` (32 bytes) when the authority is `None`. This mismatch causes `getAccountInfo` with `jsonParsed` encoding to return corrupted program data for any immutable (authority `None`) BPF Upgradeable Loader ProgramData account.

### Finding Description
The writer side, `Bank::new_target_program_data_account`, is invoked from `migrate_builtin_to_core_bpf` and `upgrade_loader_v2_program_with_loader_v3_program` with an `upgrade_authority_address` that can legitimately be `None` (explicitly documented and covered by `test_migrate_none_authority_with_some_buffer_authority`, `runtime/src/bank/builtins/core_bpf_migration/mod.rs:1021-1087`). Regardless of the authority option: [1](#0-0) 
the ELF is always copied starting at the fixed constant `programdata_metadata_size`. This same "always-fixed-offset" convention is used by the actual on-chain BPF Loader Upgradeable program when creating/deploying/extending ProgramData accounts: [2](#0-1) 
and when consuming programdata for execution: [3](#0-2) 

The RPC decoder, however, computes a *different*, conditional offset: [4](#0-3) 
When `upgrade_authority_address` is `None`, bincode serializes `Option::None` as a 1-byte tag instead of 1 byte + 32-byte pubkey, so the decoder subtracts `serialized_size(&Pubkey::default())` (32 bytes) from the fixed metadata size, producing an offset 32 bytes smaller than the true ELF start. Since the account's actual byte layout always reserves the full fixed-size header (with the unused 32 bytes left as zero padding by `bincode::serialize_into`/`AccountSharedData::new_data_with_space`, which only writes as many bytes as the enum variant actually serializes into), the decoder reads 32 bytes too early, prepending 32 zero bytes from the padding onto the "data" field it returns, while the reported length is unaffected by any bounds check — there is no assertion anywhere that the computed offset matches the real header boundary.

This is directly reachable by a single unprivileged `getAccountInfo(programDataAddress, {encoding: "jsonParsed"})` call against any BPF Upgradeable Loader ProgramData account whose authority is `None` — including, but not limited to, accounts produced by `migrate_builtin_to_core_bpf`/`upgrade_loader_v2_program_with_loader_v3_program` with `config.upgrade_authority_address = None`, and more generally any immutable/finalized program on the network (`solana program set-upgrade-authority --final`).

### Impact Explanation
This is a decoder-fidelity / wrong-data bug: the RPC-reported `data` field for `jsonParsed` `BpfUpgradeableLoaderAccountType::ProgramData` (`UiProgramData.data`) does not faithfully represent the raw account bytes for any immutable program's ProgramData account — it is corrupted by a fixed 32-byte offset error (32 zero-padding bytes prepended, and the payload length inflated to match). This falls under "wrong-data returned" / "decoder... misreporting" scoped impact for a single low-rate read request, matching an Agave RPC-correctness bounty category. No consensus state, funds, or validator crash is affected — the impact is limited to consumers relying on `jsonParsed` account data for immutable programs.

### Likelihood Explanation
Highly reachable and repeatable: any completed migration or upgrade that sets the target's `upgrade_authority_address` to `None` (explicitly supported, tested code path in `migrate_builtin_to_core_bpf`), or any independently-deployed immutable BPF Upgradeable Loader program (a common real-world configuration achieved via a standard CLI finalize command), will trigger this on every subsequent `getAccountInfo(jsonParsed)` call against its ProgramData account, with no special preconditions beyond knowing/deriving the ProgramData address (deterministic PDA).

### Recommendation
Make `parse_bpf_upgradeable_loader`'s offset calculation for `ProgramData` (and `Buffer`) unconditional, always using `UpgradeableLoaderState::size_of_programdata_metadata()` (respectively `size_of_buffer_metadata()`) regardless of whether the authority `Option` is `Some` or `None`, to match the fixed-layout convention used by every writer of these account types.

### Proof of Concept
```rust
// account-decoder/src/parse_bpf_loader.rs (test)
#[test]
fn test_parse_bpf_upgradeable_loader_programdata_none_authority_offset_bug() {
    use {bincode::serialize, solana_pubkey::Pubkey};

    let elf = vec![7u8; 64]; // arbitrary program bytes
    let slot = 42;

    // Mirror the ACTUAL on-chain / bank layout: fixed metadata size regardless
    // of Some/None authority (see runtime/src/bank/builtins/core_bpf_migration/mod.rs
    // new_target_program_data_account, and programs/bpf_loader/src/lib.rs).
    let programdata_metadata_size = UpgradeableLoaderState::size_of_programdata_metadata();
    let mut data = vec![0u8; programdata_metadata_size + elf.len()];
    bincode::serialize_into(
        &mut data[..programdata_metadata_size],
        &UpgradeableLoaderState::ProgramData {
            slot,
            upgrade_authority_address: None,
        },
    )
    .unwrap();
    data[programdata_metadata_size..].copy_from_slice(&elf);

    let parsed = parse_bpf_upgradeable_loader(&data).unwrap();
    if let BpfUpgradeableLoaderAccountType::ProgramData(ui) = parsed {
        assert_eq!(ui.authority, None);
        // EXPECTED (correct): decoded data should equal the real ELF bytes exactly.
        let decoded = match ui.data {
            UiAccountData::Binary(b64, _) => BASE64_STANDARD.decode(b64).unwrap(),
            _ => panic!("unexpected encoding"),
        };
        assert_eq!(decoded, elf); // FAILS on current code: decoded is prefixed with 32 zero bytes
    } else {
        panic!("expected ProgramData variant");
    }
}
```
Expected result on current code: `decoded` contains 32 leading zero bytes followed by `elf`, i.e. `decoded.len() == elf.len() + 32` and `decoded != elf`, demonstrating the decoder returns corrupted account data for immutable ProgramData accounts (including any produced through `Bank::migrate_builtin_to_core_bpf`/`upgrade_loader_v2_program_with_loader_v3_program` with a `None` upgrade authority).
