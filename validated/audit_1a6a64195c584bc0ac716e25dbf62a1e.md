### Title
Stale block-rejection weight is never cleared when a signer later accepts the same block, corrupting the miner's aggregated approve/reject tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The Alchemix report's core pattern is: a privileged reset zeroes an aggregate counter, but a subsequent, permissionless message (re-vote/poke) is folded into a *different* aggregate without the stale contribution ever being subtracted, so a value that should be mutually exclusive gets counted on both sides of a threshold check. The same class of bug exists in the stacks-node miner-side `StackerDBListener`, which tallies signer `BlockResponse` votes into two independent counters, `total_weight_approved` and `total_weight_rejected`, per `BlockStatus`.

### Finding Description
`BlockStatus` tracks, per proposed block, a single `responded_signers: HashSet<u32>` plus two separate weight tallies: [1](#0-0) 

When a `BlockResponse::Rejected` arrives, the code gates the weight add on `responded_signers.insert(slot_id)` and adds the signer's weight to `total_weight_rejected`: [2](#0-1) 

When a `BlockResponse::Accepted` (signature) arrives for the *same* block, the gate used is a *different* set — `gathered_signatures.contains_key(&slot_id)` — not `responded_signers`, and it adds the signer's weight to `total_weight_approved`: [3](#0-2) 

Because the two paths gate on different sets, a single signer who first rejects and then later accepts the *same* block (a supported, documented flow — see `signer_can_accept_rejected_block` and the CHANGELOG note "For some rejection reasons, a signer will reconsider a block proposal that it previously rejected") gets counted **twice**: once permanently in `total_weight_rejected` (never decremented — there is no code path that removes a slot from `responded_signers`/subtracts its weight from `total_weight_rejected` when that signer later accepts) and once in `total_weight_approved`.

This breaks the invariant the miner's `SignerCoordinator::get_block_status` loop relies on — that `total_weight_approved` and `total_weight_rejected` are disjoint subsets of `total_weight` — since the sum can now exceed `total_weight`: [4](#0-3) 

By contrast, the *signer-side* `SignerDb` explicitly guards against this exact defect ("Do not count both a block acceptance and a block rejection for the same signer/block"), and `add_block_rejection_signer_addr`/`add_block_signature` mutually clear each other's row: [5](#0-4) 

No equivalent clearing exists in the miner-side `stackerdb_listener.rs` tally.

### Impact Explanation
This is the node-side analog of "acting on a stale threshold." A single signer (no majority required) can legitimately reject a proposal and then, per the documented reconsideration flow, accept a later (or the same, reconsidered) proposal. The miner's aggregator keeps that signer's weight permanently lodged in `total_weight_rejected` while also crediting it to `total_weight_approved`. With the right timing, this phantom rejection weight combined with genuine reject weight from other signers can trip `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` (line 511-513), causing the miner to declare the block `SignersRejected` and abandon it — even though the actual, currently-live weight of rejecting signers never crossed the blocking-minority threshold. This is a liveness wedge on block/tenure progress driven purely by stale, uncleared aggregate state, matching the report's "resettable/duplicated aggregate counter" bug class.

### Likelihood Explanation
Reachable by a single signer's ordinary, protocol-sanctioned reconsideration behavior (reject → later accept the same or a re-proposed block), requiring no majority collusion, no key compromise, and no auth token. The reconsideration path is a first-class, tested feature of the signer (`signer_can_accept_rejected_block`, PR #5880), so the double counting is not a corner case but a routine occurrence whenever a signer's earlier rejection reason becomes moot.

### Recommendation
In `stackerdb_listener.rs`, gate both the accept and reject weight additions on the same authoritative per-slot state (e.g., track each slot's current vote and, on a switch from `Rejected` to `Accepted` for the same slot, subtract the signer's weight from `total_weight_rejected` before adding it to `total_weight_approved`, and vice versa), mirroring the mutual-exclusion logic already implemented in `SignerDb::add_block_signature` / `add_block_rejection_signer_addr`.

### Proof of Concept
1. Miner proposes block `B`; signers `S1..Sn` are tracked in a fresh `BlockStatus`.
2. Signer `S1` (weight `w1`) sends `BlockResponse::Rejected` for `B` (e.g. stale/timing rejection). `stackerdb_listener` sets `responded_signers.insert(S1)`, `total_weight_rejected += w1`.
3. `B` (or a re-proposal of it) is subsequently deemed valid by `S1` (per the documented reconsideration flow), and `S1` sends `BlockResponse::Accepted`. `gathered_signatures.contains_key(S1)` is `false`, so `total_weight_approved += w1` is added — `total_weight_rejected` is never decremented.
4. If other signers, whose combined weight is `w_r`, independently reject `B` for unrelated (possibly transient) reasons, the coordinator checks `total_weight_rejected (w1 + w_r) + weight_threshold > total_weight`. Because `w1` is phantom (its owner has already switched to accept), this check can trip even though the true, currently-live rejecting weight `w_r` alone would not cross the blocking minority.
5. The miner returns `NakamotoNodeError::SignersRejected`, discarding the block/txids, wedging tenure progress based on stale aggregate state rather than the signers' actual current votes.
