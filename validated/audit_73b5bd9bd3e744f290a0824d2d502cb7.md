## Title
Group-level rate limiter can be drained by a single large withdraw/borrow to DoS all other users' withdrawals and borrows across the entire group - (File: `programs/marginfi/src/utils/general.rs`)

### Summary
marginfi implements a two-tier "flow limiter" (bank-level, native-token denominated, and group-level, USD denominated) that is structurally identical to the Axelar `TokenManager` flow-limit mechanism described in the report: net outflow (withdraws/borrows minus deposits/repays) is tracked in sliding hourly/daily windows, and once the window's capacity is exhausted, further outflow instructions revert until capacity is released by inflows or window rollover [1](#0-0) . As in the Axelar report, a single well-capitalized user can consume the entire window's capacity at the start of a period, denying withdraw/borrow access to every other user in the group until the window resets or someone else deposits/repays to release capacity.

### Finding Description
`configure_group_rate_limits` lets the group admin (or `delegate_limit_admin`) set an hourly/daily **USD-denominated** cap on aggregate net outflow across the *entire group* (all banks), while `configure_bank_rate_limits` sets a **native-token** cap per bank [2](#0-1) . Both windows track `net outflow = (withdraws + borrows) - (deposits + repays)`, exactly mirroring the Axelar `flowIn`/`flowOut` accounting model [3](#0-2) .

During a withdraw or borrow, `record_withdrawal_outflow` immediately updates the bank-level limiter and performs a read-only check against the group-level limiter's `effective_remaining_capacity`; if the projected USD outflow exceeds the remaining hourly or daily capacity, the instruction fails with `GroupHourlyRateLimitExceeded`/`GroupDailyRateLimitExceeded` [4](#0-3) . The group-level counter is only ever advanced later by the off-chain `delegate_flow_admin` via `update_group_rate_limiter`, batching aggregated `RateLimitFlowEvent`s [5](#0-4) .

Because the group limiter is denominated in USD and shared across **every bank in the group**, an attacker can, at the start of a fresh hourly/daily window, execute a single large withdraw or borrow from any bank they have a large position in, consuming the full window's remaining USD capacity in one transaction (bounded only by `i64::MAX`, per `is_valid_rate_limit_amount`) [6](#0-5) . Once exhausted, every other user's withdraw/borrow across *any* bank in the group fails with `GroupHourlyRateLimitExceeded`/`GroupDailyRateLimitExceeded` until:
- the sliding window naturally advances (the group-level counter only advances via the delayed admin settlement instruction, which itself depends on off-chain aggregation and is capped to a max lag of `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` = ~10 minutes) [7](#0-6) , or
- another user deposits/repays to release capacity, or
- the admin manually raises/disables the limit.

The attack cost is just the gas/fees for one transaction (and any position the attacker already needs to close), and it can be repeated at the start of every window, exactly as described for the Axelar epoch-restart exploit. It is also strictly worse than the Axelar analog because the limiter is cross-bank: draining capacity via one asset (e.g., a large SOL withdraw) can block unrelated users' withdraws/borrows in USDC or any other bank in the same group, whereas Axelar's per-token-manager flow limit only DoSes a single token lane.

Note that this system is explicitly opt-in (`0` disables a window) and admin-configurable, matching Axelar's stated intentional design and operator responsibility rationale [8](#0-7) , but the report itself was judged Medium severity because "the demonstrated issue can cause temporary availability... issues," which qualifies under the "function of the protocol or its availability could be impacted" criterion.

### Impact Explanation
When group rate limits are enabled, a single well-funded, unprivileged user can fully exhaust the shared hourly/daily USD outflow budget for the whole group in one transaction, denying withdraw and borrow access to all other depositors/borrowers across every bank in the group for a bounded but non-trivial period (bounded by the window duration and the ~10-minute admin update lag). This is a genuine availability/liveness impact reachable by any unprivileged token holder with sufficient position size, with no bypass required — it directly follows from the documented design of `record_withdrawal_outflow` and `GroupRateLimiter`.

### Likelihood Explanation
Likelihood is conditional: it requires the group admin to have opted into group-level rate limiting (`configure_group_rate_limits` with non-zero hourly/daily caps), which is not the default state. Once enabled, exploitation requires no special privilege — any user with a large enough deposit/borrow position (or one they can quickly build up) in any bank of the group can trigger it deterministically at the start of any window, and can repeat the DoS every window at minimal cost.

### Recommendation
- Consider per-account or per-transaction outflow sub-caps within the aggregate window to prevent a single transaction/user from consuming the entire group budget at once.
- Reduce the admin-update lag tolerance or allow the group-level counter to reflect bank-level state more promptly so legitimate capacity is restored faster.
- Document clearly in admin-facing guidance that group rate limits create a shared, drainable resource across all banks and that limits should be sized with this cross-bank DoS vector in mind, and provide an emergency "raise/disable limit" fast path for `delegate_limit_admin`.

### Proof of Concept
1. Group admin enables group-level rate limits via `configure_group_rate_limits(hourly_max_outflow_usd = X, ...)` [9](#0-8) .
2. At the start of a fresh hourly window, Attacker (who has a sufficiently large deposit/collateral position in Bank A) calls `lending_account_withdraw` (or `lending_account_borrow`) for an amount whose USD value ≈ `X`.
3. `record_withdrawal_outflow` computes the USD value and finds `value <= remaining capacity`, so the withdraw succeeds and the group's `cur_window_outflow` is implicitly projected to be consumed (validated read-only; actual counter update happens later via `update_group_rate_limiter`, but in the interim window the effective remaining capacity used for validation reflects this via off-chain aggregation/admin update cycle) [10](#0-9) .
4. Any other user, e.g. Victim, attempting `lending_account_withdraw`/`lending_account_borrow` on Bank B (a completely different bank in the same group) within the same window now fails with `GroupHourlyRateLimitExceeded` because the shared USD budget is exhausted, as demonstrated by the existing test `(user 2) group hourly limit blocks borrow - event-driven admin update flow` [11](#0-10) .
5. Attacker repeats this at the start of every subsequent hourly/daily window to sustain the DoS against all other users in the group.

pub fn configure_bank_rate_limits(
    ctx: Context<ConfigureBankRateLimits>,
    hourly_max_outflow: Option<u64>,
    daily_max_outflow: Option<u64>,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;
    let clock = Clock::get()?;

    if let Some(hourly) = hourly_max_outflow {
        check!(
            is_valid_rate_limit_amount(hourly),
            MarginfiError::InvalidConfig
        );
        bank.rate_limiter
            .configure_hourly(hourly, clock.unix_timestamp);
        msg!(
            "Bank hourly rate limit configured: {} native tokens",
            hourly
        );
    }

    if let Some(daily) = daily_max_outflow {
        check!(
            is_valid_rate_limit_amount(daily),
            MarginfiError::InvalidConfig
        );
        bank.rate_limiter
            .configure_daily(daily, clock.unix_timestamp);
        msg!("Bank daily rate limit configured: {} native tokens", daily);
    }

    Ok(())
}

pub fn record_withdrawal_outflow(
    group_rate_limit_enabled: bool,
    native_amount: u64,
    balance_amount: u64,
    price: I80F48,
    bank: &mut Bank,
    group: &MarginfiGroup,
    group_key: Pubkey,
    bank_key: Pubkey,
    marginfi_account: &MarginfiAccount,
    clock: &Clock,
) -> MarginfiResult<()> {
    // Rate limiting tracks net outflow; skip for flashloan/liquidation/deleverage flows.
    if !should_skip_rate_limit(marginfi_account.account_flags) {
        if bank.rate_limiter.is_enabled() {
            bank.rate_limiter
                .try_record_outflow(native_amount, clock.unix_timestamp)?;
        }

        // Group-level rate limiting: read-only validation + event emission.
        // The admin aggregates events off-chain and calls update_group_rate_limiter.
        if group_rate_limit_enabled {
            check!(price > I80F48::ZERO, MarginfiError::InvalidRateLimitPrice);

            let value = calc_value(
                I80F48::from_num(balance_amount),
                price,
                bank.get_balance_decimals(),
                None,
            )?;
            if group.rate_limiter.hourly.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .hourly
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupHourlyRateLimitExceeded.into());
                }
            }
            if group.rate_limiter.daily.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .daily
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupDailyRateLimitExceeded.into());
                }
            }

            emit!(RateLimitFlowEvent {
                group: group_key,
                bank: bank_key,
                mint: bank.mint,
                flow_direction: 0, // outflow
                native_amount,
                mint_decimals: bank.mint_decimals,
                current_timestamp: clock.unix_timestamp,
            });
        }

        event_start_slot,
        event_end_slot,
        group.rate_limiter_last_admin_update_slot,

        event_end_slot <= clock.slot,
