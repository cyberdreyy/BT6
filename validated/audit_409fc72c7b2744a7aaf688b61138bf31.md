Based on my research, the strongest reachable analog to the reported "untrusted/mutable `decimals()` used in calculations" bug class is in the transaction-status instruction-parsing code (`transaction-status/src/parse_token.rs` and its extension modules), which is directly reachable by any unprivileged JSON-RPC client via `getTransaction`/`getConfirmedTransaction` with `jsonParsed` encoding.

### Title
Untrusted, attacker-controlled `decimals` field from SPL-Token "*Checked" instruction data is trusted verbatim when building `jsonParsed` `tokenAmount` UI values, causing decoder misreporting - (File: transaction-status/src/parse_token.rs)

### Summary
The transaction-status JSON-RPC instruction parser for SPL-Token/Token-2022 "*Checked" instructions (`TransferChecked`, `ApproveChecked`, `MintToChecked`, `BurnChecked`, `TransferCheckedWithFee`, confidential-transfer `Deposit`/`Withdraw`, `BurnCheckedInstructionData`, etc.) builds the human-readable `tokenAmount`/`uiTokenAmount` field solely from the `decimals` byte embedded in the raw, attacker-supplied instruction data, without ever cross-checking it against the actual on-chain mint account's `decimals` field.

### Finding Description
`parse_token` extracts `decimals` straight out of the decoded instruction payload and immediately feeds it into `SplTokenAdditionalDataV2::with_decimals(decimals)` / `token_amount_to_ui_amount_v3`, e.g.: [1](#0-0) 
The same pattern repeats for `ApproveChecked`, `MintToChecked`, `BurnChecked`: [2](#0-1) 
and in the transfer-fee and permissioned-burn/confidential-transfer extension parsers: [3](#0-2) [4](#0-3) [5](#0-4) 

`token_amount_to_ui_amount_v3` (account-decoder) then computes `ui_amount`/`ui_amount_string` purely as a function of this unverified `decimals` value: [6](#0-5) 

This mirrors the external report's core issue: a value that should be treated as an authoritative, validated constant (the mint's real `decimals`) is instead taken from an untrusted, attacker-controlled source (raw instruction bytes) and used directly in a financial-display calculation, with no cross-reference to the actual `Mint` account state (which is available and used correctly elsewhere, e.g. `rpc/src/parsed_token_accounts.rs::get_mint_owner_and_additional_data` which does read the real mint account).

### Impact Explanation
Any unprivileged RPC consumer calling `getTransaction`/`getConfirmedTransaction`/`getConfirmedBlock` with `jsonParsed` encoding on a transaction containing a "*Checked" token instruction sees a `tokenAmount.uiAmount`/`uiAmountString`/`decimals` field that reflects whatever decimals the transaction's signer chose to embed, not the mint's true decimals. When the on-chain SPL Token(-2022) program successfully executes such an instruction it does independently validate `decimals == mint.decimals`, so for *successful* instructions the displayed value happens to be correct; however, for *failed* transactions/instructions (mismatched decimals is one of the ways such an instruction fails) the raw, bogus decimals value is still parsed and returned verbatim to callers, since instruction parsing operates on the message contents regardless of execution outcome. This is a decoder-misreporting issue (wrong/misleading data returned from a read query), which falls in the explicitly accepted impact category, but does not rise to a crash, deadlock, or consensus-state mutation.

### Likelihood Explanation
Trivial and fully unprivileged: any user can submit (or have already-submitted, publicly-visible on any RPC node) a transaction embedding a "*Checked" instruction with an arbitrary `decimals` byte, and any third party who later queries that transaction via `jsonParsed` encoding will observe the misreported UI amount for the failed instruction.

### Recommendation
Where accurate reporting matters, the instruction parser should not synthesize `uiAmount`/`decimals` purely from instruction bytes for failed transactions, or should clearly flag/derive it only when the accompanying transaction succeeded and/or cross-check the value against the mint account fetched from the bank/blockstore (as `rpc/src/parsed_token_accounts.rs` already does for account/mint encoding), rather than trusting attacker-controlled instruction data as if it were verified.

### Proof of Concept
1. Craft and submit (even a transaction that will fail) a `TransferChecked`/`MintToChecked`/`BurnChecked`/`ApproveChecked` instruction whose `decimals` field intentionally does not match the real mint's `decimals` (this instruction will fail at runtime because the token program checks it).
2. The transaction, though failed, is still recorded in the ledger with its message intact.
3. Call `getTransaction`/`getConfirmedTransaction` with `encoding: "jsonParsed"` on this transaction signature.
4. Observe that `meta`/`transaction.message.instructions[].parsed.info.tokenAmount` reports the attacker-chosen bogus `decimals`/`uiAmount`/`uiAmountString`, computed via `token_amount_to_ui_amount_v3` in `account-decoder/src/parse_token.rs`, with no cross-check against the actual mint account decimals.

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
    UiTokenAmount {
        ui_amount,
        decimals,
        amount: amount.to_string(),
        ui_amount_string,
    }
}
