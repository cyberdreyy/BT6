### Title
Program deployment can be permanently DoS'd via pre-funding of the ProgramData PDA - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
`process_loader_upgradeable_instruction`'s `DeployWithMaxDataLen` handler derives the `ProgramData` account address deterministically from the new program's pubkey and invokes the strict `system_instruction::create_account` via `native_invoke_signed` to create it. Because the PDA address is fully predictable off-chain before the deploy transaction lands, any unprivileged actor can pre-fund it with a trivial lamport transfer, causing the subsequent `create_account` CPI to fail permanently with `AccountAlreadyInUse`.

### Finding Description
In `programs/bpf_loader/src/lib.rs`, the `DeployWithMaxDataLen` instruction computes the ProgramData PDA with [1](#0-0) 
and then creates it with the plain, strict `create_account`: [2](#0-1) 

That CPI is handled by the system program's `create_account`, which unconditionally rejects any target account that already has non-zero lamports: [3](#0-2) 

Because `Pubkey::find_program_address(&[new_program_id.as_ref()], program_id)` is fully deterministic and computable by anyone who knows (or observes, e.g. from a pending/broadcast transaction) the new program's pubkey, an attacker can submit an ordinary `system_instruction::transfer` of a few lamports to that PDA before the deployer's `DeployWithMaxDataLen` transaction lands. When the deploy transaction executes, the CPI `create_account` call fails with `SystemError::AccountAlreadyInUse`, aborting the whole deployment atomically — the program never becomes deployed and the specific program address becomes permanently unusable for `DeployWithMaxDataLen` (any retry hits the same pre-funded, already-in-use PDA).

Notably, Agave's own system program already contains a mitigation pattern for exactly this bug class — `create_account_allow_prefund`/`CreateAccountAllowPrefund`, gated by the `create_account_allow_prefund` feature — which allocates/assigns first and treats existing lamports as a valid pre-payment rather than failing: [4](#0-3) 
However, the `bpf_loader_upgradeable`'s `DeployWithMaxDataLen` path was not updated to use this safer primitive and still calls the strict `create_account`, so it remains exposed to the exact griefing pattern described in the external report.

### Impact Explanation
This allows any unprivileged network participant to permanently block deployment of a specific program address by front-running with a trivial SOL transfer to its predictable `ProgramData` PDA. This is a denial-of-service against the program deployment path of a core, always-enabled builtin loader (`bpf_loader_upgradeable`), forcing developers/projects to abandon vanity or pre-announced program addresses and wasting the rent/fees already spent writing the Buffer account. It does not directly steal funds or corrupt consensus, but it is a concrete, unauthorized state-mutation-triggered failure of a fundamental builtin-program code path reachable by an ordinary transaction.

### Likelihood Explanation
Likelihood is moderate-to-high: the attack only requires knowledge of the program address about to be deployed (commonly known ahead of time, e.g. published vanity addresses, CI/CD pipelines, or observable via mempool/QUIC ingest of the buffer-writing or deploy transactions) and a single cheap `system_instruction::transfer`. No special privileges, validator access, or race beyond normal transaction submission ordering are needed.

### Recommendation
Update `DeployWithMaxDataLen` (and any analogous PDA-creation CPI in `bpf_loader`/loader-v3, e.g. any other `system_instruction::create_account` call for deterministic PDAs) to use the fund/allocate/assign pattern — or the existing `create_account_allow_prefund` system instruction — instead of the strict `create_account`, so that a pre-funded target account does not abort account initialization.

### Proof of Concept
1. Deployer prepares to deploy a program with keypair `P` (program id `P.pubkey()`), writes an ELF to a Buffer account, and derives `programdata_key = find_program_address(&[P.pubkey().as_ref()], bpf_loader_upgradeable::id())`.
2. Before the deployer's `DeployWithMaxDataLen` transaction is confirmed, an attacker who has learned `P.pubkey()` (from a pending/broadcast tx, a public vanity address, or CI logs) sends a plain `system_instruction::transfer` of a few lamports to `programdata_key`.
3. The deployer's `DeployWithMaxDataLen` transaction executes; the CPI at `programs/bpf_loader/src/lib.rs:296-310` calls `create_account`, which sees `to.get_lamports() > 0` in `programs/system/src/system_processor.rs:164-171` and returns `SystemError::AccountAlreadyInUse`, failing the whole deploy transaction.
4. Any retry with the same `P.pubkey()` fails identically, since the PDA remains permanently pre-funded/"in use," permanently blocking deployment for that program address — directly mirroring the `create_account` pre-funding DoS proof-of-concept from the external report, but reachable inside Agave's own `bpf_loader_upgradeable` builtin.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
