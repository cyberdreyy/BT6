**Reasoning summary:** Duplicate/overlapping account keys are rejected during transaction sanitization *before* any transaction reaches `calculate_cost_for_executed_transaction`. This function is only invoked on transactions that were already sanitized and successfully processed/committed [1](#0-0) [2](#0-1) .

The duplicate-key check is enforced by `validate_account_locks`/`has_duplicates` in `accounts-db/src/account_locks.rs`, which returns `TransactionError::AccountLoadedTwice` for any account-key list containing duplicates, and this check is applied both after static message parsing and again after address-lookup-table resolution to catch ALT-introduced duplicates [3](#0-2) [4](#0-3) .

This is exercised by existing regression tests demonstrating that a hand-crafted message with a duplicated account key is rejected with `AccountLoadedTwice` prior to execution, both at the bank level and the entry-validation level: `test_duplicate_account_key` [5](#0-4) , `test_bank_process_and_record_transactions_all_unexecuted` [6](#0-5) , and `test_validate_entry_transactions_account_loaded_twice` [7](#0-6) . RPC-submitted transactions are sanitized the same way via `sanitize_transaction`/`RuntimeTransaction::try_create` [8](#0-7) [9](#0-8) .

Since `calculate_cost_for_executed_transaction` is unreachable with duplicate/overlapping account keys — any such transaction is rejected at sanitization with `TransactionError::AccountLoadedTwice` before reaching cost accounting or execution — the described privilege-accounting confusion cannot occur through this path.

pub fn validate_account_locks(
    account_keys: AccountKeys,
    tx_account_lock_limit: usize,
) -> TransactionResult<()> {
    if account_keys.len() > tx_account_lock_limit {
        Err(TransactionError::TooManyAccountLocks)
    } else if has_duplicates(account_keys) {
        Err(TransactionError::AccountLoadedTwice)
    } else {
        Ok(())
    }
}

thread_local! {
    static HAS_DUPLICATES_SET: RefCell<AHashSet<Pubkey>> = RefCell::new(AHashSet::with_capacity(MAX_TX_ACCOUNT_LOCKS));
}

/// Check for duplicate account keys.
fn has_duplicates(account_keys: AccountKeys) -> bool {
    // Benchmarking has shown that for sets of 32 or more keys, it is faster to
    // use a HashSet to check for duplicates.
    // For smaller sets a brute-force O(n^2) check seems to be faster.
    const USE_ACCOUNT_LOCK_SET_SIZE: usize = 32;
    if account_keys.len() >= USE_ACCOUNT_LOCK_SET_SIZE {
        HAS_DUPLICATES_SET.with_borrow_mut(|set| {
            let has_duplicates = account_keys.iter().any(|key| !set.insert(*key));
            set.clear();
            has_duplicates
        })
    } else {
        for (idx, key) in account_keys.iter().enumerate() {
            for jdx in idx + 1..account_keys.len() {
                if key == &account_keys[jdx] {
                    return true;
                }
            }
        }
        false
    }
}

    pub fn try_create(
        tx: VersionedTransaction,
        message_hash: MessageHash,
        is_simple_vote_tx: Option<bool>,
        address_loader: impl AddressLoader,
        reserved_account_keys: &HashSet<Pubkey>,
    ) -> Result<Self> {
        if tx.message.instructions().len()
            > solana_transaction_context::MAX_INSTRUCTION_TRACE_LENGTH
        {
            return Err(solana_transaction_error::TransactionError::SanitizeFailure);
        }

        for instr in tx.message.instructions() {
            if instr.accounts.len() > solana_transaction_context::MAX_ACCOUNTS_PER_INSTRUCTION {
                return Err(solana_transaction_error::TransactionError::SanitizeFailure);
            }
        }

        let statically_loaded_runtime_tx =
            RuntimeTransaction::<SanitizedVersionedTransaction>::try_from(
                SanitizedVersionedTransaction::try_from(tx)?,
                message_hash,
                is_simple_vote_tx,
            )?;
        Self::try_from(
            statically_loaded_runtime_tx,
            address_loader,
            reserved_account_keys,
        )
    }
