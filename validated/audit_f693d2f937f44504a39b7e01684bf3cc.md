## Finding: Confirmations from Removed Multisig Members/Keys Remain Valid, Allowing Request Execution Below the Configured Threshold

### Title
Stale confirmations from deleted multisig members/keys are still counted toward `num_confirmations`, letting a request execute with fewer live approvers than the configured threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
Both multisig contracts store confirmations for a request in a flat set keyed only by `request_id`, and `confirm()` decides whether to execute a request purely by counting the *size* of that set against `num_confirmations` [1](#0-0) . When a member (or access key) is removed via `DeleteMember`/`DeleteKey`, the cleanup logic only purges confirmations for requests that the *removed member originally created*, not confirmations that member cast on *other* requests [2](#0-1) . A removed member's stale confirmation therefore continues to count toward the threshold, letting a request execute with fewer live, currently-authorized confirmers than `num_confirmations` requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [3](#0-2) 

`delete_member()` is the only place that prunes confirmations related to a removed member, and it filters strictly by request *ownership* (`r.member == member`, i.e. the member who created/added the request), not by participation in `confirmations`: [2](#0-1) 

Because `self.confirmations` is a separate `LookupMap<RequestId, HashSet<String>>` that is never scanned for the deleted member's string on requests they merely *confirmed* (but didn't create), those entries survive the deletion untouched.

The equality that should hold is:
`confirmations counted for request R == confirmations cast by current live members of the multisig`

After removing a member who had confirmed (but not created) request `R`, this becomes:
`confirmations counted for request R == confirmations cast by live members + 1 (stale)`

which lets `R` reach `num_confirmations` with one fewer live signer than intended.

The identical pattern exists in the older `multisig` contract: `DeleteKey` only cleans up requests where `r.signer_pk == pk` (i.e., requests created by that key), leaving that key's confirmations on other requests intact: [4](#0-3) 

### Impact Explanation
This breaks the multisig's core custody guarantee: "K of N live signers must approve a request." A request (e.g., a `Transfer` moving NEAR out of the account, or an `AddKey`/`AddMember` granting new authority) can be executed with only `K-1` currently-authorized approvals plus one stale approval from a member who has since been removed (e.g., because their key was known-compromised or they left the organization). This matches the report's Critical-impact category: "a multisig request executed below threshold," since funds can move, or authority can be granted, without the intended number of currently-trusted parties agreeing.

### Likelihood Explanation
This requires no privilege beyond being (or having been) a legitimate multisig member/key holder at some point — a normal operational event (member rotation/removal after a request was already partially confirmed) triggers it. It does not require compromising a currently active key, redeploying the contract, or any owner/foundation intervention beyond the routine `DeleteMember`/`DeleteKey` action that multisig operators are expected to use for key rotation. Any pending request that received a confirmation before a rotation is silently left with an extra, now-unauthorized "vote" that remaining members may not be aware of.

### Recommendation
When removing a member/key (`delete_member` / `DeleteKey` handling), scan and prune that member's entry from the `confirmations` set of *every* request, not just requests they created. Alternatively, validate at `confirm()`-time (and at threshold-check time) that every account/key present in a request's confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm` for `Transfer { amount }` to an attacker-controlled receiver → request `R` has `confirmations = {A}` (count 1).
3. Members legitimately rotate out `A` (e.g., its key was suspected compromised) via a separate, properly-confirmed `DeleteMember { member: A }` request. `delete_member` removes only requests `A` created; since `A` did not create `R`, `R`'s confirmation set is untouched → `confirmations = {A}` still, even though `A` is no longer a member [5](#0-4) .
4. `B` calls `confirm(R)` → `confirmations = {A, B}` (count 2, `< 3`, not yet executed).
5. `C` calls `confirm(R)` → `confirmations = {A, B, C}` (count 3, `>= num_confirmations`) → `execute_request` fires and the transfer is sent [6](#0-5) .
6. Result: the transfer executed with only `B` and `C` as live, currently-authorized approvers — one fewer than the configured `num_confirmations = 3` — because `A`'s stale confirmation was still counted.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
