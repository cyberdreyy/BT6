## Analog Found

### Title
Rejection-weight tally can silently lose votes across different blocks due to a signer-address-only primary key - (File: `stacks-signer/src/signerdb.rs`)

### Summary
The `block_rejection_signer_addrs` table, which backs the global-rejection weight tally computed in `store_and_process_block_rejection`, is keyed only by `signer_addr`, not by `(signer_signature_hash, signer_addr)`. This means a signer can only ever have one recorded rejection in the whole database at a time: rejecting a second, different block silently overwrites (and thereby erases) the recorded rejection for the first block. The in-memory tally therefore no longer equals the true set of votes cast for a given block, which is the invariant the 30%-blocking-minority rejection threshold depends on.

### Finding Description
`store_and_process_block_rejection` computes the global-rejection decision purely from what `get_block_rejection_signer_addrs(block_hash)` returns from the DB: [1](#0-0) 

That query reads from `block_rejection_signer_addrs`, whose schema is: [2](#0-1) 

The table stores `signer_signature_hash` as a plain column but declares `PRIMARY KEY (signer_addr)` — i.e. uniqueness is enforced per signer, not per `(block, signer)`. Any insert that uses `INSERT OR REPLACE` (as the analogous pre-commit/signature helpers do elsewhere, e.g. the pending-response tables at [3](#0-2)  and [4](#0-3) ) on this table will replace the *only* row a given `signer_addr` can own, regardless of which block hash it previously pointed to.

Concretely: a signer rejects Block A (hash H_A) — a row `(H_A, S)` is written. If that same signer later rejects a different, unrelated Block B (hash H_B) — which happens routinely in Nakamoto whenever competing tenure-start proposals, re-proposed blocks after a timeout (`check_submitted_block_proposal`), or sibling blocks at the same height occur — the row for `S` is overwritten to `(H_B, S)`. From that point on, `get_block_rejection_signer_addrs(H_A)` no longer returns `S`, even though `S` genuinely, validly rejected block A and that vote was accepted at the time (`add_block_rejection_signer_addr` returned `Ok(true)`), and `store_and_process_block_rejection` had already logged/used it toward A's tally.

This is the direct analog of the "bad debt keeps accruing" bug class: in the JPEG'd report, a value that should stop being counted (uncollectible debt) is never excluded from the accrual computation, silently corrupting a running total against reality. Here, a value that *should* remain counted (a genuine, previously-validated rejection vote for block A) is silently dropped from the running total because the storage model conflates two logically distinct tallies (one per block) into a single per-signer slot. In both cases, a persisted "total" (accrued interest / rejection weight) diverges from the true, currently-valid set of inputs, because the accounting structure does not exclude/partition stale entries correctly.

### Impact Explanation
`total_reject_weight` computed in `store_and_process_block_rejection` ( [5](#0-4) ) is the sole input to the decision of whether a block reaches `GloballyRejected`. If genuine rejection votes for a still-pending block are silently evicted because the same signers also voted on other, unrelated blocks (which is expected background activity across tenure changes and re-proposals), the tally for the pending block can permanently understate the real rejection weight. The block can then be left stuck in a `LocallyRejected`/`Unprocessed` limbo — never crossing either the accept or the (set_size - threshold + 1) reject threshold — which wedges the signer's tenure/consensus state machine on that block indefinitely (a liveness wedge on the signer's per-block bookkeeping), rather than resolving deterministically as the design intends.

### Likelihood Explanation
This does not require a majority of signers or any key compromise — it is triggered purely by the ordinary, single-signer-visible sequence of any signer address rejecting two different blocks over time (a routine occurrence with competing/duplicate proposals, timeouts in `check_submitted_block_proposal`, and tenure-change forks), combined with the schema's per-signer (not per-block) primary key. I was not able to fully verify, within the available context, the exact SQL used by `add_block_rejection_signer_addr` (its body was not retrieved before the tool budget ran out) to confirm it indeed uses `INSERT OR REPLACE` rather than an upsert scoped to `(signer_signature_hash, signer_addr)`; this should be confirmed by reading that function directly, since it determines whether the described overwrite is actually reachable in the current code path or whether an additional guard prevents it.

### Recommendation
Change the primary key of `block_rejection_signer_addrs` to `(signer_signature_hash, signer_addr)` (matching the pattern already used for `block_pre_commits` and `block_signatures`, which are keyed to avoid exactly this kind of cross-block collision), and add a migration to backfill/rebuild the table under the corrected key. Re-verify `add_block_rejection_signer_addr`'s SQL explicitly scopes its upsert to the specific block hash.

### Proof of Concept
1. Signer `S` receives Block A proposal (hash `H_A`), determines it invalid, calls `store_and_process_block_rejection`, which calls `signer_db.add_block_rejection_signer_addr(H_A, S, reason)`, inserting row `(H_A, S)` into `block_rejection_signer_addrs`.
2. Before A reaches consensus, a competing/re-proposed Block B (hash `H_B`, e.g. a re-proposal after `check_submitted_block_proposal`'s timeout, per [6](#0-5) ) arrives; `S` also rejects it, calling `add_block_rejection_signer_addr(H_B, S, reason)`.
3. Because the table's only key is `signer_addr`, this second insert overwrites the row for `S` from `(H_A, S)` to `(H_B, S)`.
4. A subsequent call to `get_block_rejection_signer_addrs(H_A)` ( [7](#0-6) ) no longer includes `S`, so `total_reject_weight` for block A is computed short by `S`'s weight — even though `S` did, and still would, reject A. If A's true rejection weight was only barely above the blocking-minority threshold, this silent loss can keep A from ever reaching `GloballyRejected`.
