### Title
Missing boundary validation on operator fee scalar/constant applied from L1 SystemConfig updates - (File: crates/common/genesis/src/updates/operator_fee.rs)

### Summary
`SystemConfig::process_config_update_log` decodes `OperatorFee` update logs and applies the resulting `operator_fee_scalar` (u32) and `operator_fee_constant` (u64) directly to the node's `SystemConfig` with no boundary/sanity check on their magnitude, mirroring the pattern in the referenced report where `_interestPer3Min` is accepted by `queueCollateralChange` without validation against reasonable bounds.

### Finding Description
`OperatorFeeUpdate::try_from` decodes the raw scalar and constant bytes straight out of the ABI-encoded log payload with no range check: [1](#0-0) 
`OperatorFeeUpdate::apply` then unconditionally overwrites the live `SystemConfig` fields: [2](#0-1) 
`SystemConfig` itself declares these fields as bare `Option<u32>`/`Option<u64>` with no documented or enforced maximum: [3](#0-2) 
and the log-processing pipeline applies every successfully-decoded update without any additional validation step before or after `apply`: [4](#0-3) 

These scalar/constant values flow directly into the operator-fee formula that is charged to every non-deposit L2 transaction: [5](#0-4) 
and are debited from every payer's balance during transaction settlement: [6](#0-5) 
and in the standard-fee handler path: [7](#0-6) 

### Impact Explanation
Because `operator_fee_scalar`/`operator_fee_constant` have no upper bound at decode time or apply time, a value at or near `u32::MAX`/`u64::MAX` (whether from operator error, a mis-encoded log, or a compromised/malicious L1 `SystemConfigOwner`) is accepted and applied verbatim. Once applied, every L2 transaction is charged the resulting operator fee via `operator_fee_charge_inner`, which multiplies `gas * scalar` (further amplified under the Jovian multiplier) — an unbounded scalar can make ordinary transactions cost an exorbitant, unpayable, or fund-draining fee, directly mirroring the "loss of funds" impact called out in the original report for an unvalidated `_interestPer3Min`.

### Likelihood Explanation
This requires the entity controlling the L1 `SystemConfig` contract (the privileged config owner) to emit a bad `ConfigUpdate(OperatorFee)` log — either by operator error (e.g., a decimal/units mistake, directly analogous to the original report's "missed decimal") or a compromised owner key. There is no additional guard in the derivation pipeline (`update_with_receipts` / `process_config_update_log`) to catch or reject an out-of-range value before it takes effect, so likelihood is tied entirely to operational/key-security assumptions around the SystemConfig owner, same as the CollateralBook admin in the original report.

### Recommendation
Add explicit sanity-bound validation for `operator_fee_scalar` and `operator_fee_constant` in `OperatorFeeUpdate::try_from` (or in `SystemConfig::process_config_update_log`/`apply`), rejecting or clamping values above a documented maximum (e.g., a scalar corresponding to at most some small fixed percentage overhead) before they are merged into the live `SystemConfig`, consistent with how other config fields could similarly benefit from bounds checks to prevent a single malformed or malicious L1 log from imposing unbounded fees on all L2 users.

### Proof of Concept
1. On L1, the `SystemConfigOwner` (or an attacker who has compromised that key, or simply makes an encoding mistake) emits a `ConfigUpdate` log with `updateType = OperatorFee` and payload bytes encoding `operator_fee_scalar = 0xFFFFFFFF` (u32::MAX) as shown in the existing test fixture pattern: [8](#0-7) 
2. `SystemConfig::update_with_receipts` picks up this log during L1 derivation and calls `process_config_update_log`, which decodes it via `OperatorFeeUpdate::try_from` with no bounds check and calls `.apply(self)`, overwriting `operator_fee_scalar` unconditionally.
3. On the next L2 block, `operator_fee_charge_inner` computes `gas.saturating_mul(operator_fee_scalar) / OPERATOR_FEE_SCALAR_DECIMAL` (or with the Jovian multiplier) for every non-deposit transaction: [9](#0-8) 
4. This inflated `operator_cost` is charged upfront from every transaction payer's balance in `settle_fees`/`before_execution`, resulting in massively excessive or unpayable fees for all L2 users until a corrective `ConfigUpdate` log is emitted, at which point funds already collected into `OPERATOR_FEE_VAULT` are not automatically returned.

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }

impl TxHandlerHooks<BaseEvmTypes> for BaseTxHandlerHooks {
    fn before_execution(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        upfront_fee: U256,
    ) -> HandlerResult<()> {
        // Charge the upfront gas cost, the L1 data fee, and the operator fee (on the gas limit)
        // from the caller. Both fees are stashed for settlement so it charges/refunds against the
        // exact amounts collected here, without recomputing them.
        let l1_fee = Self::l1_fee(host, envelope);
        let operator_fee = Self::operator_fee(host, envelope, envelope.gas_limit());
        let ext = host.ext_mut();
        ext.l1_fee = l1_fee;
        ext.operator_fee = operator_fee;
        // `validate_sender` only checks the gas cost and value; the L1 and operator fees are
        // charged on top here via `charge_upfront`'s wrapping subtraction, so reject an
        // underfunded caller up front rather than let its balance wrap to a spurious value.
        Self::ensure_can_pay_fees(host, envelope, caller, l1_fee, operator_fee)?;
        charge_upfront(
            host,
            caller,
            upfront_fee.saturating_add(l1_fee).saturating_add(operator_fee),
        )
    }
