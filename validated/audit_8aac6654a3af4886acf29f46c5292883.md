### Title
Loss-adjusted withdraw receipts permanently blocked from claiming — haircut price stored under wrong epoch after `epochNumber` bump - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` records a user's receipt under the *current* `epochNumber` (`lastWithdrawRequest` and `withdrawsRequestsByEpoch`). During `stopEpochWithDuration`, the strategy's `deposit()` bumps `epochNumber` **before** `collectWithdrawFunds` runs, so the haircut `lossRecoveryPriceByEpoch` is keyed to the *new* epoch while receipts point to the *old* one — mirroring CVE-2018-7184, where the "received" timestamp is written under attacker-shifted state rather than the state the packet belonged to. The loss-adjusted claim path therefore never fires, and the funded-claim path pays receipts at par from an under-funded reserve.

### Finding Description
- `requestWithdraw` stores `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` using `epochNumber` at request time (IdleCreditVault.sol:282-293).
- In `deposit()` the comment at line 607-610 explicitly says "deposit done on stopEpoch" and increments `epochNumber` while the epoch is still running (IdleCreditVault.sol:607-610).
- `collectWithdrawFunds` then writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` — under the already-incremented epoch (IdleCreditVault.sol:414-421).
- `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. the *old* epoch, reads 0, and silently returns (IdleCreditVault.sol:789-795).
- The guard at request time has the same blind spot: `lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]` reads the old epoch, so the "claim before re-requesting" protection never triggers (IdleCreditVault.sol:261-271).
- Net effect: after a `stopEpochWithDuration` with `_lossAmount > 0` that results in a haircut (`_amount < pendingBasis`), affected receipts are claimable via `_claimFundedWithdrawRequest` (IdleCreditVault.sol:319-349), which pays `withdrawsRequests[_user]` at par even though only the haircutted amount was funded into the vault (`pendingWithdraws` was set to 0 at line 420).

### Impact Explanation
Broken invariant: loss waterfall / one receipt one payout. Receipts that should pay `claimBasis * lossRecoveryPrice / 1e18` either:
- pay full par, over-drawing the strategy's underlying reserve (early claimants steal from later claimants → insolvency), or
- revert on insufficient underlying once the funded amount is drained → permanent freezing of remaining users' claims.
Loss equals `claimBasis * (1 - lossRecoveryPrice)` per affected epoch, up to the whole pending bucket.

### Likelihood Explanation
Requires only a realized loss path (`stopEpochWithDuration` / partial borrower funding), which is a normal, non-default epoch transition triggered by the honest borrower repaying short. Any unprivileged tranche holder requesting a withdraw in that epoch is affected; exploitability depends on the `deposit()` → `collectWithdrawFunds` ordering inside `stopEpoch` in `IdleCDOEpochVariant`, which the code comments ("deposit done on stopEpoch … so we reset the counter") strongly suggest runs before fund collection.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the epoch that owned the receipts — either snapshot `epochNumber` before the bump, or write the haircut under `epochNumber - 1` / pass the request epoch explicitly from the CDO. Also align the `requestWithdraw` re-entry guard and `_claimLossAdjustedWithdrawRequest` lookup with the same epoch key.
