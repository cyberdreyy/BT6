### Title
Drained ERC4626 liquidity in `ProgrammableBorrower.onStopEpoch` makes every `stopEpoch` revert, indefinitely freezing all tranche funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
The Skytable CVE is an accept-loop that exits early on a mis-checked return value, shutting the whole server down with minimal bandwidth. The analog in idle-tranches is the epoch-stop "run loop": `IdleCDOEpochVariant._stopEpoch` must complete for the pool to reopen withdrawals, and in programmable mode it delegates liquidity recall to `ProgrammableBorrower.onStopEpoch`. That hook performs a single all-or-nothing `vault.withdraw(shortfall)`; if the external ERC4626 vault lacks liquidity it reverts `StopEpochVaultLiquidityUnavailable`, bubbling out of `stopEpoch` so the epoch can never be stopped while the vault is illiquid. An unprivileged user of the same ERC4626 vault can drain its liquidity (e.g., max borrow) right before `epochEndDate`, turning every subsequent `stopEpoch` call into an early exit — a cheap, repeatable DoS that freezes all lender principal and pending withdrawal claims.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, the programmable path calls the borrower hook and only handles a `false` return as a default; a revert propagates and aborts the whole stop [1](#0-0) .

In `ProgrammableBorrower.onStopEpoch`, when on-hand cash is below the required amount, the hook first checks whether vault shares economically cover the shortfall and returns `true` early (deliberately pushing the failure to IdleCDO's `transferFrom` → default path); otherwise it attempts one full `vault.withdraw(shortfall)` and reverts `StopEpochVaultLiquidityUnavailable` on failure [2](#0-1) .

The broken pieces:
- The withdraw is all-or-nothing: it requests the full `shortfall` instead of `min(shortfall, vault.maxWithdraw(address(this)))`, so even 1 wei of missing liquidity reverts the entire epoch stop.
- The early-return at line 245 compares `shortfall > _currentVaultAssets()` (share *value*), which stays high even when withdrawable liquidity is zero — exactly the "incorrect check of return/accounting value" shape of the CVE. Share value covering the debt does not imply the withdraw can succeed.
- `stopEpoch` is gated to after `epochEndDate` and is the only path that flips `isEpochRunning = false`, unpauses, and re-enables `allowAAWithdrawRequest`/`allowBBWithdrawRequest` [3](#0-2) . While it reverts, deposits are paused (`_beforeUnpause` blocks unpause during a running epoch [4](#0-3) ), pending withdrawal requests cannot be funded, and `claimWithdrawRequest`/`claimInstantWithdrawRequest` never receive liquidity.

Unlike the intended default path, this revert leaves the pool in limbo: not defaulted (so no recovery distribution via `DefaultDistributor`), not stopped (so no claims), and the attacker can sustain it by keeping vault liquidity exhausted — e.g., holding a large borrow position in a Morpho-style vault, which only costs borrow interest, not bandwidth, mirroring the CVE's low-cost DoS.

### Impact Explanation
Temporary-to-indefinite freezing of 100% of pool funds: all AA/BB tranche principal, accrued interest, and all pending withdrawal requests stay locked as long as the attacker keeps the ERC4626 vault illiquid. Because each retry reverts identically, the freeze persists for the duration of the attacker's liquidity drain (permanent if the vault's liquidity is borrowed and never repaid). Fund impact equals the entire vault NAV plus pending claims.

### Likelihood Explanation
Requires (a) a credit vault in programmable-borrower mode where idle funds are parked in a shared ERC4626 vault whose liquidity can be permissionlessly borrowed/withdrawn (the threat model explicitly includes "a user of the programmable borrower's ERC4626 vault"), and (b) an epoch with `pendingWithdraws` or principal recall requiring a vault withdrawal (`shortfall > 0`), which is the normal case whenever idle liquidity exceeds on-hand cash. The behavior is already codified as the intended revert path in `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable` and `testProgrammableBorrowerStopEpochDoesNotTrustBrokenMaxWithdraw` [5](#0-4) , i.e., retryable-by-design but with no bound on how long the vault can be kept illiquid, and no partial-withdraw fallback.

### Recommendation
In `ProgrammableBorrower.onStopEpoch`, withdraw only the available liquidity (`shortfall = min(shortfall, vault.maxWithdraw(address(this)))`, or `redeem` a capped share amount) and treat a still-uncovered residual the same way as line 245 — return `true` and let IdleCDO's `transferFrom` default the pool — rather than reverting. A shortfall that can never be recovered is economically a default and should be crystallized via `_handleBorrowerDefault` (enabling `DefaultDistributor` recovery), not an infinitely retryable revert that freezes funds without a default claim path.

### Proof of Concept
Foundry fork PoC sketch (Mainnet fork with a real ERC4626 vault such as Gauntlet USDC Prime, per `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// test/foundry/PocStopEpochVaultDrain.t.sol
function testVaultLiquidityDrainFreezesStopEpoch() external {
    _setUpProgrammableBorrowerCreditVault(GAUNTLET_FORK_BLOCK, GAUNTLET_USDC_PRIME);
    IERC4626 vault = IERC4626(GAUNTLET_USDC_PRIME);

    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
    _startEpochAndCheckPrices(0);

    // Attacker: unprivileged user of the same ERC4626 vault drains/borrows
    // all liquidity so vault.withdraw(shortfall) always reverts.
    // e.g., flash-free liquidity via a max borrow on the underlying Morpho market,
    // or use MockStopEpochLiquidityVault.setWithdrawLimit(shortfall - 1).
    // ... attacker keeps liquidity < pendingWithdraws for arbitrary duration ...

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Every stopEpoch call exits early with a revert — the epoch can never stop.
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning(), "epoch still running");
    assertFalse(cdoEpoch.defaulted(), "no default crystallized - no recovery path");

    // All user funds frozen: requests cannot be claimed, deposits paused,
    // unpause blocked by _beforeUnpause while isEpochRunning.
    vm.expectRevert(); // NotAllowed / no liquidity
    cdoEpoch.claimWithdrawRequest(requestId);

    // Repeated retries keep reverting as long as the attacker holds liquidity out.
    vm.warp(block.timestamp + 30 days);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
}
```

A deterministic variant uses `MockStopEpochLiquidityVault` (already in the test suite): set `setWithdrawLimit(pendingWithdraws - 1)` so `vault.withdraw(shortfall)` reverts while `convertToAssets` still covers the shortfall, showing that the `_currentVaultAssets()` check at `ProgrammableBorrower.sol:245` passes and the failure surface is purely liquidity-based.
