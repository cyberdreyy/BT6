### Title
Session.Kill does not prevent later exec requests from creating a new terminal connection - (File: session/session.go)

### Summary
`Session.Kill` only closes and nils the currently-active `s.terminalConn`; it never clears `s.interactiveTerminal` or sets a "killed" flag. A concurrent `/exec` request that is past the `terminalSetCh`/`terminalAvailable` check can call `newTerminalConn`, which — because `s.terminalConn == nil` after `Kill` ran — happily calls `s.interactiveTerminal.TerminalConnect()` and installs a brand-new connection, even though the job/session is being torn down.

### Finding Description
`execHandler` (session/session.go:146-191) checks `terminalAvailable()` and then calls `newTerminalConn()` (session/session.go:200-216), which under `s.lock` checks `if s.terminalConn != nil { return connectionInUseError }` and otherwise calls `s.interactiveTerminal.TerminalConnect()` and stores the result in `s.terminalConn`. `Session.Kill()` (session/session.go:263-275) is the only teardown hook exposed by `Session`; it takes the same `s.lock`, closes `s.terminalConn` if set, and sets it to `nil` — but does not clear `s.interactiveTerminal`, nor does it set any sentinel to reject future `TerminalConnect()` calls, nor does it cancel/replace the interactive terminal reference that was installed by `Build.run` via `SetInteractiveTerminal` (common/build.go:1247-1249).

Because `Kill()` and `newTerminalConn()` share the same mutex, there's no data race on the `terminalConn` field itself, but there is a logical race in the protocol: if `execHandler`'s request arrives and reaches the lock strictly after `Kill()` has already run and released the lock, `s.terminalConn` will be `nil`, so `newTerminalConn` proceeds to call `TerminalConnect()` on the executor's `interactiveTerminal` implementation (e.g. `commandExecutor.TerminalConnect` in executors/docker/terminal.go:49) regardless of whether the executor is mid-Cleanup/teardown. `TerminalConnect` for the Docker executor does its own container lookup (`watchForRunningBuildContainer`) and spins up a `context.WithCancel(s.Context)` derived exec session; if the executor's `s.Context` hasn't yet been cancelled or if the container hasn't yet been removed by `Cleanup()`, this succeeds and a fresh `ContainerExecCreate`/`ContainerExecAttach` shell is started against a container that is in the process of being destroyed.

There is no code path that ties `Session.Kill()` to disabling `s.interactiveTerminal`, and no ordering guarantee enforced between the caller of `Kill()` (whoever cancels the session on job cancellation/timeout) and the executor's own context cancellation / `Cleanup()`. The existing "no multiple connections" guard (`connectionInUseError`) only prevents concurrent connections while one is already active — it does not prevent a *new* connection after the old one has been explicitly killed.

### Impact Explanation
An attacker who is an authorized job/session token holder (any pipeline author with access to the job's session endpoint) can race a job cancellation/timeout with a flood of `/exec` requests. If a request slips through after `Session.Kill()` clears `terminalConn` but before (or concurrently with) executor `Cleanup()`/container removal, a new interactive shell/exec process can be spawned against a container/host resource that is supposed to already be torn down. This is a dangling command execution outside the job's intended lifecycle boundary — the shell may keep running commands, mutate build/volume state, or race with the teardown/removal logic (e.g., `docker.go` `Cleanup()`'s `removeContainer` calls), potentially causing resource leaks or unexpected side effects on shared infra (autoscaled VMs, Kubernetes pods) after the job is nominally finished.

### Likelihood Explanation
This requires a job author (or anyone with the session token, since the token is the only auth boundary) to send `/exec` websocket upgrade requests concurrently with a job cancellation or timeout — a client-controllable, easily automatable pattern (flood `/exec` right when cancelling the pipeline via API). No admin privileges are needed. The race window depends on scheduler timing between `Session.Kill()` and the executor's own context cancellation/cleanup, which is plausible given they are triggered by independent code paths (`Build.run`'s signal handling in common/build.go and each executor's async `Cleanup()`), making this reasonably reproducible under load/race testing, though not deterministic on every attempt.

### Recommendation
Make `Session.Kill()` a true terminal state: introduce a `killed bool` (or `closed` state) flag on `Session`, set it under `s.lock` in `Kill()`, and check/reject in both `terminalAvailable()` and `newTerminalConn()` (return an error such as `sessionClosedError`) once killed. Optionally also clear `s.interactiveTerminal` in `Kill()` so any subsequent `TerminalConnect()` attempt fails fast rather than reaching the executor.

func TestExecAfterKillDoesNotConnect(t *testing.T) {
	session, err := NewSession(nil)
	require.NoError(t, err)
	session.Token = "tok"

	mockTerminal := terminal.NewMockInteractiveTerminal(t)
	// TerminalConnect should NOT be called after Kill()
	mockTerminal.On("TerminalConnect").Return(nil, errors.New("should not be called")).Maybe()

	session.SetInteractiveTerminal(mockTerminal)

	require.NoError(t, session.Kill()) // simulate job cancellation teardown

	req := httptest.NewRequest(http.MethodGet, session.Endpoint+"/exec", nil)
	req.Header.Add("Connection", "upgrade")
	req.Header.Add("Upgrade", "websocket")
	req.Header.Add("Authorization", "tok")

	w := httptest.NewRecorder()
	session.Handler().ServeHTTP(w, req)

	resp := w.Result()
	// Expect Runner to reject with e.g. 503/410, not attempt TerminalConnect
	assert.NotEqual(t, http.StatusSwitchingProtocols, resp.StatusCode)
	mockTerminal.AssertNotCalled(t, "TerminalConnect")
}

func (s *Session) execHandler(w http.ResponseWriter, r *http.Request) {
	logger := s.log.WithField("uri", r.RequestURI)
	logger.Debug("Exec terminal session request")

	if !websocket.IsWebSocketUpgrade(r) {
		logger.Error("Request is not a web socket connection")
		http.Error(w, http.StatusText(http.StatusMethodNotAllowed), http.StatusMethodNotAllowed)
		return
	}

	ctx, cancel := context.WithTimeout(r.Context(), time.Minute)
	defer cancel()

	// There's a chance we'll get a interactive terminal connection before
	// we've hooked up the terminal to the underlying executor.
	//
	// When this occurs, we effectively wait for the terminal to be hooked up,
	// the request to be cancelled, or 1 minute (whichever comes first).
	select {
	case <-s.terminalSetCh:
	case <-ctx.Done():
	}

	if !s.terminalAvailable() {
		logger.Error("Interactive terminal not set")
		http.Error(w, http.StatusText(http.StatusServiceUnavailable), http.StatusServiceUnavailable)
		return
	}

	terminalConn, err := s.newTerminalConn()
	if _, ok := err.(connectionInUseError); ok {
		logger.Warn("Terminal already connected, revoking connection")
		http.Error(w, http.StatusText(http.StatusLocked), http.StatusLocked)
		return
	}

	if err != nil {
		logger.WithError(err).Error("Failed to connect to terminal")
		http.Error(w, http.StatusText(http.StatusInternalServerError), http.StatusInternalServerError)
		return
	}

	defer s.closeTerminalConn(terminalConn)
	logger.Debugln("Starting terminal session")
	terminalConn.Start(w, r, s.TimeoutCh, s.DisconnectCh)
}

func (s *Session) newTerminalConn() (terminal.Conn, error) {
	s.lock.Lock()
	defer s.lock.Unlock()

	if s.terminalConn != nil {
		return nil, connectionInUseError{}
	}

	conn, err := s.interactiveTerminal.TerminalConnect()
	if err != nil {
		return nil, err
	}

	s.terminalConn = conn

	return conn, nil
}

func (s *Session) Kill() error {
	s.lock.Lock()
	defer s.lock.Unlock()

	if s.terminalConn == nil {
		return nil
	}

	err := s.terminalConn.Close()
	s.terminalConn = nil

	return err
}

	// inform the user in an interactive way that the container has no started

		return nil, err
