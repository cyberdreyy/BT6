### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing a request to execute below the live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges confirmations for requests that were *added by* the member being removed. It never scans the `confirmations` map to strip that member's confirmation from requests added by *other* members. Because `confirm()` counts raw `HashSet<String>` length without validating that every entry still belongs to a current member, a member who confirmed a request and was later removed still contributes to reaching `num_confirmations`, letting a request execute with fewer live approvers than the configured threshold. The identical structural flaw exists in the legacy `multisig/src/lib.rs` (`DeleteKey` only clears requests added by that key, not confirmations left by it on other requests).

### Finding Description
The confirmation counting binding that must hold is:

```
confirmations.len() (at execution time) == number of DISTINCT LIVE members who confirmed
```

`confirm()` breaks this equality because it never re-validates the stored confirmation set against the live `members` set: [1](#0-0) 

`delete_member` only removes confirmations tied to requests that the removed member *itself* created, not confirmations that member cast on requests created by someone else: [2](#0-1) 

`assert_valid_request`, called from `confirm`, only checks that the *caller* confirming right now is a current member — it does nothing to validate the pre-existing entries already sitting in the `confirmations` `HashSet<String>`: [3](#0-2) 

So once a member's confirmation is recorded on request `R`, that string stays in `confirmations.get(&R)` forever (until `R` is executed or deleted), even after `DeleteMember { member }` removes that member from `self.members`. The stale confirmation still counts in `confirmations.len() as u32 + 1 >= self.num_confirmations` on subsequent `confirm()` calls by other, still-live members.

The exact same class of bug (as the audited `GameItems::safeBatchTransferFrom` finding) applies here: the "primary" transfer path (adding/removing a member) does not propagate its invalidation to a secondary, less obviously connected code path (`confirmations` map keyed independently of `members`), so a security-relevant boundary (membership) is not consistently enforced across every place that binding matters.

### Impact Explanation
This lets a multisig request execute with a number of *live* approving members strictly below the configured `num_confirmations`. Since `MultiSigRequestAction::Transfer`, `AddKey`, `FunctionCall`, `DeployContract`, etc. are all gated purely by this threshold check, an attacker (or a compromised/former member) can get a `Transfer` or `FunctionCall` executed while control has nominally shifted to fewer members than the threshold requires — i.e., NEAR moved, or contract state changed, by a party not fully entitled under the current governance configuration. This matches the "a multisig request executed below threshold" Critical impact category.

### Likelihood Explanation
This does not require compromising any keys beyond what an ordinary member already has. It only requires:
1. A member confirms some pending request (a routine, everyday multisig action).
2. That member is later removed via a normal `DeleteMember` action (e.g., off-boarding, key rotation, compromise response) — an entirely expected/likely governance operation.
3. The already-pending request from step 1 is later confirmed by the remaining live members.

No attacker-controlled malicious deployment or foundation-only privilege is needed; the sequence occurs naturally whenever member turnover happens while requests are outstanding, which is a realistic and likely operational scenario for any long-lived multisig.

### Recommendation
When removing a member in `delete_member`, iterate over *all* active requests' confirmation sets (not just those the member authored) and strip the removed member's entry from each. Alternatively, change `confirm()` to recompute/verify confirmation count by intersecting the stored confirmation set with the current `self.members` set before comparing against `num_confirmations`, ensuring stale confirmations from removed members never count towards the threshold. Apply the equivalent fix to the legacy `multisig/src/lib.rs` `DeleteKey` handling.

### Proof of Concept
Assume `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.

1. `B` calls `add_request` to create request `R1` (e.g., `Transfer{ amount }` to some receiver).
2. `C` calls `confirm(R1)` → `confirmations[R1] = {C}` (1 of 3, not yet executed) — per [1](#0-0) .
3. Through a separate, properly-confirmed `DeleteMember{ member: C }` request (A, B, D confirm it, reaching threshold 3), `C` is removed from `self.members`. `delete_member` only cleans up requests *added by* `C`; `R1` (added by `B`) is untouched, so `confirmations[R1]` still contains `C` — per [2](#0-1) .
4. `B` calls `confirm(R1)` → `confirmations[R1].len() (=1) + 1 = 2 < 3` → not executed yet, `confirmations[R1] = {C, B}`.
5. `D` calls `confirm(R1)` → `confirmations[R1].len() (=2) + 1 = 3 >= 3` → `execute_request` runs the `Transfer`.

Result: `R1` executed with confirmations effectively from `{C (removed), B, D}` — only 2 currently-live members (`B`, `D`) actually approved it, even though `num_confirmations = 3` and the live member set is `{A, B, D}`. The threshold was bypassed using a stale confirmation from a removed member.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
