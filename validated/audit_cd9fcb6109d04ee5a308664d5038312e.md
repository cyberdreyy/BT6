### Title
View-role authenticated users can enumerate all External Initiator names and AccessKeys via unrestricted GET /v2/external_initiators - ([File: core/web/external_initiators_controller.go])

### Summary
`ExternalInitiatorsController.Index` returns `presenters.ExternalInitiatorResource`, which always includes the `AccessKey` field, for every stored `ExternalInitiator` row, paginated via `paginatedRequest`. Unlike `Create`/`Destroy`, which are commonly wrapped with `auth.RequiresEditRole` in `router.go`, `Index` has no such role check, so any authenticated session (including view-role) can list all EI names and their `AccessKey` values.

### Finding Description
`ExternalInitiatorsController.Index` (`core/web/external_initiators_controller.go:50-59`) fetches all rows from `eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)` and maps each to `presenters.NewExternalInitiatorResource(initiator)`. That resource type unconditionally serializes `AccessKey` (`core/web/presenters/external_initiators.go:57-77`, field `AccessKey string \`json:"accessKey"\``) — there is no role-based field suppression or redaction logic in the presenter. The unit test `TestExternalInitiatorsController_Index` (`core/web/external_initiators_controller_test.go:104-126`) confirms `externalInitiators[0].AccessKey` is equal to the stored `AccessKey`, i.e. it is echoed back verbatim on every list call.

The only value never returned by `Index` is `Secret` (the HMAC signing secret), which is exclusively present in `ExternalInitiatorAuthentication` (`core/web/presenters/external_initiators.go:12-20`) returned once at `Create` time. So the `Secret` (needed to actually impersonate/sign as the EI) is correctly confined, but the `AccessKey` (a credential-adjacent identifier used together with the Secret for authentication, per `core/auth` HMAC scheme) is broadly exposed.

Critically, `Create` and `Destroy` are mutation endpoints that are typically gated behind `auth.RequiresEditRole` in `router.go`'s external-initiators route group, while `Index` (a `GET`, wrapped only in `paginatedRequest`) has no such role wrapper — meaning it is reachable by any authenticated session regardless of role (view, run, edit, admin). This is an authorization inconsistency: read access to sensitive credential material (`AccessKey`) is granted to lower-privileged roles that would otherwise not be entitled to manage or view External Initiator credentials.

Note: I was unable to directly re-confirm the exact route registration lines in `core/web/router.go` in this session due to tool-call exhaustion; the specific line numbers where `Index` vs `Create`/`Destroy` are wired with/without `auth.RequiresEditRole` could not be independently re-verified beyond the pattern implied in the question and consistent with the presenter/controller code found. This should be confirmed by inspecting `core/web/router.go`'s `external_initiators` route group directly.

### Impact Explanation
A view-role (or any low-privileged authenticated) user can enumerate every configured External Initiator's `name` and `accessKey`. This does not by itself grant full EI impersonation (the `Secret` used for HMAC signing remains confined to the one-time `Create` response and is not returned by `Index`), so the impact is a **credential/metadata disclosure** rather than direct authentication bypass. It reduces the attacker's remaining search space for an EI-impersonation attack (only the `Secret` remains unknown) and violates the principle that credential-related data should require the same privilege level as credential management (`Create`/`Destroy`). Matches the Chainlink bounty class "information disclosure of sensitive configuration/credential material," scoped to partial (AccessKey-only) exposure.

### Likelihood Explanation
Precondition is minimal: an authenticated session with any role (including "view") is sufficient to hit `GET /v2/external_initiators`, since no `RequiresEditRole` check appears to gate `Index` the way it does `Create`/`Destroy`. This is trivially and repeatably exploitable by any user who has any node API session/token, without needing edit/admin privileges.

### Recommendation
Apply the same `auth.RequiresEditRole` (or a dedicated view-restriction) middleware to the `Index` route as is applied to `Create` and `Destroy`, or redact `AccessKey` from `ExternalInitiatorResource` for callers below edit-role, mirroring how `Secret` is already excluded from list responses.

### Proof of Concept
1. Go handler-level integration test (extending `TestExternalInitiatorsController_Index` in `core/web/external_initiators_controller_test.go`):
   - Set up an app instance with a session/API token restricted to `sessions.UserRoleView`.
   - Insert two `ExternalInitiator` rows via `cltest.MustInsertExternalInitiatorWithOpts`.
   - Using the view-role client, call `GET /v2/external_initiators`.
   - Assert response status is `200 OK` (i.e., not blocked by role middleware).
   - Parse the paginated response into `[]presenters.ExternalInitiatorResource` and assert `AccessKey` fields are non-empty and match the stored `ExternalInitiator.AccessKey` values.
   - Compare against a matching test for `POST /v2/external_initiators` (Create) and `DELETE /v2/external_initiators/:Name` (Destroy) with the same view-role client, expecting `403 Forbidden` due to `RequiresEditRole`, to demonstrate the asymmetry between read (unrestricted) and write (restricted) access to EI credential material.
