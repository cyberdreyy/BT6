### Title
Callback ID collision in `savedCallbacks` map allows cross-user hijack of triggered-response delivery - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores the caller-provided callback in `h.savedCallbacks[msg.Body.MessageId]` without checking for an existing entry or binding the entry to the requester's identity. Since `MessageId` is a client-chosen (attacker-controlled) string with no server-side uniqueness enforcement, an attacker can submit a second `web_api_trigger` request reusing a victim's pending `MessageId`, silently overwriting the victim's saved callback and later receiving the DON's response intended for the victim.

### Finding Description
The reachable path is: gateway HTTP API → `gateway.ProcessRequest` [1](#0-0)  → for a legacy request (`msg.Body.DonId` set), `msg.Validate()` is called, which only validates signature/length/format, not uniqueness of `MessageId` and does not tie it to any previously used ID [2](#0-1) . It then dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)`.

Inside `HandleLegacyUserMessage`, after payload/timestamp/method validation (none of which reference `Sender` or check for ID collisions), the handler unconditionally overwrites the map entry: [3](#0-2) 

There is no check like `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { reject }`, and the map key has no sender component (e.g., `sender+":"+MessageId`). `MessageId` is fully attacker-supplied via the JSON-RPC request `ID` / message body field [4](#0-3) , and its only server-side constraints are length/printability, not uniqueness or ownership [5](#0-4) .

When the DON node responds, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `msg.Body.MessageId`, with no cross-check against which user originally submitted that ID: [6](#0-5) 

The only sender check performed, in `HandleNodeMessage`, verifies that the DON node's signature matches the `nodeAddr` the gateway is talking to — it authenticates the *node*, not the original *end-user* who submitted the trigger request — so it does not prevent this class of hijack: [7](#0-6) 

Exploit flow:
1. Victim submits a legitimate `web_api_trigger` request with `MessageId = Z`. `savedCallbacks[Z] = victimCallback` is stored and forwarded to all DON members.
2. Before any node responds, attacker (any unprivileged client capable of signing their own gateway message) submits their own `web_api_trigger` request also using `MessageId = Z`. Because the map write at line 412 is unconditional and unkeyed by sender, `savedCallbacks[Z]` is overwritten with `attackerCallback`.
3. When a DON node responds (either to the victim's or the attacker's forwarded request, since both were sent with ID `Z`), `handleWebAPITriggerMessage` looks up `savedCallbacks[Z]`, finds the attacker's callback, deletes the entry, and delivers the on-chain-triggered response envelope to the attacker instead of the victim.

The existing test `savedCallbacks stored only when message is valid` only asserts that invalid messages don't leave stale entries; it never exercises two distinct callbacks sharing one `MessageId`, so this collision path is untested [8](#0-7) .

### Impact Explanation
This is a cross-user response confusion / callback hijack: an attacker with no special privileges can cause another user's `web_api_trigger` response (which may contain sensitive trigger event data, e.g., off-chain data results forwarded from the DON) to be delivered to the attacker instead of the legitimate requester, or can cause the victim's own request to silently hang (attacker's callback is delivered and then evicted, leaving the victim's request without a response). This matches the "cross-user response confusion" / unauthorized access to another user's request data impact class.

### Likelihood Explanation
The attacker only needs the ability to submit a signed `api.Message` to the gateway (an unauthenticated/unprivileged capability shared by any DON API user) and to guess or observe the victim's `MessageId` and win a race before the DON responds. `MessageId` is entirely client-chosen with no randomness requirement enforced server-side, so if a calling application uses predictable IDs (sequence numbers, timestamps, well-known values) this is straightforward to exploit; even with less predictable IDs, the race window (until the first DON response arrives) provides a feasible exploitation opportunity. No admin/operator access, DON compromise, or network position is required — only ordinary message-signing capability.

### Recommendation
Bind `savedCallbacks` entries to a key that is not solely under the requester's control and reject/isolate collisions, e.g.:
- Compose the map key from `(sender_address, MessageId)` rather than `MessageId` alone, and additionally validate that the response's node-forwarded `MessageId` correlates back to the same sender before delivering it.
- Reject a `HandleLegacyUserMessage` call that maps to an already-in-use key (return a collision error to the caller rather than silently overwriting).
- Alternatively, generate the internal request-tracking ID server-side (e.g., a gateway-generated UUID) and only use the client-supplied `MessageId` for building the outward response envelope, never as the internal correlation key used across multiple senders.

### Proof of Concept
Add a table/unit test to `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build `victimMsg := triggerRequest(t, nodes[0].PrivateKey, ..., "" /*default MessageId "12345"*/)`.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCb)`; assert `handler.savedCallbacks["12345"]` is set to the victim's callback (inspect internal state).
3. Build `attackerMsg` signed with a different private key but with the same hard-coded `MessageId = "12345"` (modify `triggerRequest` helper to accept an explicit ID, or construct the message manually and sign with an unrelated key).
4. Call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCb)`.
5. Assert (current buggy behavior) that `handler.savedCallbacks["12345"]` now points to `attackerCb`, not `victimCb` — i.e., the overwrite occurred.
6. Simulate a DON node response for `MessageId = "12345"` via `handler.HandleNodeMessage(...)`, then assert that `attackerCb.Wait(ctx)` receives the response while `victimCb.Wait(ctx)` times out/never resolves, proving the response was hijacked.
7. Recommended fix would make step 4 return an error (or fail to overwrite) so that step 6 confirms `victimCb` still receives the response.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

	}
