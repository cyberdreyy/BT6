### Title
Signer weight double-counted into both `total_weight_approved` and `total_weight_rejected` after a reject-then-accept flip - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tracks two independent weight tallies for a proposed block: `total_weight_approved` (deduplicated via `gathered_signatures`) and `total_weight_rejected` (deduplicated via `responded_signers`). A single signer that first rejects a block and later accepts the same block (a normal, expected sequence per the documented pre-commit/conflict-resolution flow in `docs/signer-flows.md`, where a signer may refuse "for now" and sign later once a conflict goes stale) gets its weight counted into `total_weight_rejected` on the reject message, and then *also* counted into `total_weight_approved` on the later accept message, because the accept path's dedup check (`gathered_signatures.contains_key(&slot_id)`) is independent of the reject path's dedup set (`responded_signers`).

### Finding Description
In the `BlockResponse::Accepted` arm [1](#0-0) , weight is added to `total_weight_approved` only if `slot_id` is not already in `gathered_signatures`, and the slot is inserted into both `gathered_signatures` and `responded_signers`.

In the `BlockResponse::Rejected` arm [2](#0-1) , weight is added to `total_weight_rejected` only if `slot_id` is not already in `responded_signers`, and the slot is inserted into `responded_signers` only (never into `gathered_signatures`).

Because the two dedup sets are asymmetric:
- Accept-then-Reject is safe: `responded_signers` already contains the slot from the accept step, so the later reject is a no-op for the reject tally.
- **Reject-then-Accept is not safe**: after a reject, `responded_signers` contains the slot but `gathered_signatures` does not. When the later accept arrives, the accept path's guard checks `gathered_signatures` (not `responded_signers`), so it is *not* deduplicated against the earlier reject, and the same signer's weight is added a second time — once into `total_weight_rejected` and once into `total_weight_approved`.

The equality broken is: each signer's weight should be attributable to only one of "accepted" or "rejected" for a given block signature hash at any point in time; here the same signer's weight is simultaneously counted toward both tallies, and `total_weight_rejected` is never decremented even though the signer's final/current position is acceptance.

### Impact Explanation
The node-side coordinator (`signer_coordinator.rs::get_block_status`) uses these two cumulative, monotonically-increasing tallies to decide the miner's fate for a block: reject if `total_weight_rejected + weight_threshold > total_weight` [3](#0-2) , else accept once `total_weight_approved >= weight_threshold` [4](#0-3) . Since `total_weight_rejected` only grows and is never corrected when the underlying signer later accepts, a signer (or several signers) that legitimately reject-then-accept (a scenario the signer's own state machine explicitly supports, per `docs/signer-flows.md` section 5's "refuse to sign for now... may sign once conflict is stale") can push stale rejection weight that persists indefinitely. If enough signers follow this reject→accept pattern, the miner can conclude "signers rejected the block" (hitting the `SignersRejected` branch, banning/excluding transactions and abandoning a proposal) even though those same signers have, by weight, also crossed the acceptance threshold — a liveness wedge on the mining loop: a block that should be accepted can instead be reported/treated as rejected because of unretracted stale rejection weight from signers who flipped to accept. This does not forge a block or signature (the accept path still requires a valid signature verified via `signer_pubkey.verify` [5](#0-4) ), so it is not a Critical-severity signing bug, but it is a High-severity liveness wedge: it can cause the miner to wedge into a false-rejection branch instead of signing/using a validly-approved block, achievable by a single (or a few) one-slot signer(s) simply exercising the documented and expected reject→accept transition, with no majority or key compromise required.

### Likelihood Explanation
This requires no adversarial signer collusion or majority — it is triggered by the normal operation of a single signer whose local chainstate view causes it to reject a proposal and later, per the documented conflict-resolution timing rules, accept the same block once the conflicting signature/tenure state becomes stale. This is an entirely plausible and even expected sequence in reorg/conflict scenarios described in `docs/signer-flows.md` (pre-commit threshold section, "conflict_still_blocks", "reorg_permit_stands"). The bug is deterministic given that sequence — no timing race or network manipulation needed beyond the signer sending two ordinary StackerDB messages for the same block hash.

### Recommendation
Use a single deduplication mechanism (e.g., track, per slot_id, the signer's current vote — accept or reject — with the associated weight) instead of two independent sets (`gathered_signatures`/insert-once and `responded_signers`/insert-once). When a signer's vote changes from reject to accept (or vice versa), subtract the weight from the old tally and add it to the new one, so `total_weight_approved` and `total_weight_rejected` always reflect the signer's *current* position, and the two tallies remain mutually exclusive and always sum to at most `total_weight`.

### Proof of Concept
1. Miner proposes block `B` to signer set with total weight `W` and `weight_threshold = 0.7W`.
2. Signer `S` (weight `w`) evaluates the proposal and, per `check_block_against_signer_db_state`, currently finds a fresh conflicting signed sibling — it sends `BlockResponse::Rejected` for `B`. In `stackerdb_listener.rs`, `total_weight_rejected += w`; `responded_signers.insert(slot_S)`.
3. Shortly after, the conflicting sibling's signature goes stale or is proven dead (`conflict_still_blocks` returns false), and `S`'s local pre-commit logic now signs `B`, sending `BlockResponse::Accepted`.
4. In `stackerdb_listener.rs`, the accept handler checks `gathered_signatures.contains_key(&slot_S)` — false (never inserted by the reject path) — so it executes `total_weight_approved += w` again.
5. Now `total_weight_rejected` still equals `w` (never decremented) and `total_weight_approved` also includes `w`. If enough signers with combined weight `> 0.3W` follow this same reject→accept pattern before enough *other* signers respond, `signer_coordinator.rs::get_block_status` can hit `total_weight_rejected + weight_threshold > total_weight` and return `SignersRejected`, abandoning a block that the same signers have concurrently signed enough weight to approve — a wedge/inconsistency in the miner's decision logic driven entirely by normal single-signer state transitions.
