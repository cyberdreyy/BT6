### Title
Deterministic lockup address squatting via unprivileged `create()` front-run - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` is `#[payable]` and callable by any account that attaches `MIN_ATTACHED_BALANCE`; it deploys a lockup at the fully deterministic address `hex::encode(&env::sha256(owner_account_id)[..20]).<factory>` with no check that the caller is entitled to act for `owner_account_id`. Any unprivileged attacker can compute this address for a victim who has not yet received their real grant and call `create` first with attacker-chosen `vesting_schedule`, `release_duration`, `lockup_duration`, `lockup_timestamp` and `whitelist_account_id`, permanently occupying that address before the legitimate grantor.

### Finding Description
The broken binding: `lockup_account_id(owner) == terms_chosen_by(owner's_grantor)`. In reality, `lockup_account_id` only depends on `owner_account_id` via `env::sha256`, and the terms attached to it are whatever the *first successful caller* of `create` supplies: [1](#0-0) [2](#0-1) 

`create` performs no check that `env::predecessor_account_id()` is the owner, the foundation, or any privileged party — it is reachable by any account that attaches `MIN_ATTACHED_BALANCE`: [3](#0-2) [4](#0-3) 

Exploit flow:
1. Attacker picks a real/likely-future grantee account (`owner_account_id`) whose lockup has not been created yet.
2. Attacker calls `create(owner_account_id, attacker_lockup_duration, attacker_lockup_timestamp, attacker_vesting_schedule, attacker_release_duration, attacker_whitelist_account_id)` with `MIN_ATTACHED_BALANCE`.
3. Because `Promise::new(lockup_account_id).create_account()` succeeds (the account name does not yet exist), the attacker's parameters are the ones written into `LockupInformation`/`VestingInformation` on first-time initialization of that address.
4. When the legitimate grantor (e.g. NEAR Foundation) later calls `create` for the same `owner_account_id` with the real intended terms and full grant deposit, the `create_account()` action fails because the account already exists. Since NEAR batches these actions (`create_account`, `deploy_contract`, `transfer`, `function_call`) into one receipt, the whole receipt fails atomically, `is_promise_success()` returns `false` in `on_lockup_create`, and the deposit is refunded to the grantor: [5](#0-4) 

No guard such as `assert_owner`, `assert_called_by_foundation`, or a pre-registration/reservation mechanism exists anywhere in `lockup-factory/src/lib.rs` or `utils.rs` to prevent an arbitrary account from claiming the address first: [6](#0-5) 

The result: the address that the ecosystem (wallets, explorers, the foundation's own tooling) treats as "the lockup for `owner_account_id`" permanently carries attacker-chosen `vesting_schedule`/`release_duration`/`whitelist_account_id`/`lockup_duration`/`lockup_timestamp` instead of the grantor's intended terms — matching exactly the listed Critical impact "a lockup deployed with parameters its rightful creator never chose."

### Impact Explanation
The squatted contract is permanently deployed with attacker-controlled lockup/vesting/whitelist parameters at the address the ecosystem expects to hold the victim's real grant terms. While `owner_account_id` itself is still the real owner (giving them owner-only rights over the squatted contract), the terms — cliff/vesting schedule, release duration, staking-pool whitelist — are whichever the attacker chose, not what the grantor intended, and this can never be corrected because the real grantor's `create` call will always fail once the name is taken (NEAR account names are unique and immutable once created). This blocks the legitimate grant flow at that specific derived address indefinitely and could mislead any party (custodians, the owner, or automated tooling) that trusts the address-to-terms binding. The attacker's own `create` cost (`MIN_ATTACHED_BALANCE`) is not recovered, and no NEAR is directly extracted from the grantor (their deposit is refunded), so this is a name-squatting/parameter-substitution attack rather than direct fund theft through this path.

### Likelihood Explanation
Any unprivileged account can perform this by simply calling `create` for a chosen `owner_account_id` before the real grantor does, at a fixed cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per victim. It requires no special privileges, no victim key, and no race beyond front-running a future, predictable, publicly-known grant (e.g. announced/expected grantee lists). It is repeatable across any number of `owner_account_id`s the attacker wishes to squat, each costing only the minimum deposit.

### Recommendation
Restrict `create` to a privileged caller (e.g. `assert_called_by_foundation`/an allow-listed grantor role), or require the `owner_account_id` (or a signed authorization from it) as `predecessor_account_id`/require a separate reservation step controlled by the foundation before allowing account creation at the derived address.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(

                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

use near_sdk::{env, PromiseResult};

pub fn assert_self() {
    assert_eq!(env::predecessor_account_id(), env::current_account_id());

pub fn is_promise_success() -> bool {
    assert_eq!(env::promise_results_count(), 1, "Contract expected a result on the callback");
    match env::promise_result(0) {
        PromiseResult::Successful(_) => true,
        _ => false,
    }
}
