### Title
Gas metering bypass in `bls12381_impl!` when `value_ptr` is the register sentinel (`u64::MAX`) — `elements_count` is computed from `value_len` before it is known whether `value_len` is a byte-length or a register id - ([File: runtime/near-vm-runner/src/logic/bls12381.rs])

### Finding Description
`bls12381_impl!` computes the number of chargeable elements strictly from the raw `value_len` argument and pays for it before resolving what `value_len` actually means: [1](#0-0) 

`get_memory_or_register!` (used at line 48) implements NEAR's well‑known pointer/length convention for these host functions: when `value_ptr == u64::MAX` the call is redirected to read from a register, and in that branch the `value_len` slot is reinterpreted as the **register id**, not as a byte count — the macro dispatches to `internal_read_register(value_len)` rather than to the memory-bounded read. This is the standard sentinel convention used across many single-buffer host functions (`sha256`, `keccak256`, `ripemd160`, `ecrecover`, the `bls12381_*` family, etc.) in `runtime/near-vm-runner/src/logic/logic.rs`.

Because `elements_count = value_len / $ITEM_SIZE` (line 45) and `pay_per(...)` (line 46) both execute *before* the ptr/len dispatch inside `get_memory_or_register!` is resolved, an attacker who sets `value_ptr = u64::MAX` and `value_len = <small register id>` causes the fee computation to treat the register id as if it were a byte length, producing an `elements_count` that has no relationship to the actual size of the register's contents. If the attacker previously wrote a large buffer (`N * BLS_P1_SIZE` bytes) into that register via `write_register`, and then calls `bls12381_p1_sum` with `value_ptr = u64::MAX` and `value_len` equal to that register's small numeric id (e.g. register 0 or 1), `elements_count = value_len / 97` will evaluate to 0 or a tiny number, so `pay_per` charges for (near) zero elements. `get_memory_or_register!` then returns the **entire** register buffer (all `N` elements), and the underlying `p1_sum` implementation iterates the full buffer with `chunks_exact(BLS_P1_SIZE + 1)`, performing `N` expensive elliptic-curve point additions — none of which were paid for by `pay_per`.

This violates the metering totality invariant (bytes/elements processed ≤ bytes/elements charged) purely from unprivileged, single-transaction, contract-controlled inputs (`value_ptr`, `value_len`, and prior `write_register` content) — no validator/node/network privilege is required.

### Impact Explanation
This is a fee-payment bypass allowing an unprivileged contract to trigger unbounded (up to the register size limit, e.g. up to ~100MB / 96–97 bytes ≈ hundreds of thousands of point operations) BLS12-381 elliptic-curve computation while paying only the base fee and the (cheap) cost of writing the register, not the per-element compute fee that is specifically priced to reflect the real cost of BLS12-381 math. Repeated/parallel invocation of this pattern lets an attacker consume disproportionate CPU relative to gas paid, which is a resource-exhaustion/computational-DoS vector against chunk producers processing the transaction, risking degraded block/chunk production performance under sustained abuse.

### Likelihood Explanation
The attacker only needs standard, unprivileged capabilities: fund an account, deploy a contract, call `write_register`-equivalent host functions to populate a register with a large buffer, then call `bls12381_p1_sum` (or any function built with `bls12381_impl!`) with `value_ptr = u64::MAX` and a small `value_len` acting as the register id. This is fully reproducible and repeatable at will, and costs the attacker only the price of writing the register content plus the base fee of the BLS call — no signature/nonce/access-key check intercepts this because the request is a fully valid function call action executed by the contract's own wasm code.

### Recommendation
Resolve the pointer/register dispatch (i.e., materialize the actual `data` buffer and know its true length) before computing `elements_count` and calling `pay_per`. Concretely, in `bls12381_impl!`, move the `get_memory_or_register!` call before the gas computation, and compute `elements_count` from `data.len() / $ITEM_SIZE` (the resolved buffer length) rather than from the raw `value_len` parameter, then pay for that length prior to invoking `$impl_fn_name`.

### Proof of Concept
1. Deploy a contract that, in a single function call: (a) writes `N * 97` bytes (`N` large, e.g. 100_000) into register `0` using the register-write host call; (b) invokes `bls12381_p1_sum(value_len = 0, value_ptr = u64::MAX, register_id = 1)`.
2. Instrument/assert on `gas_counter` burnt for the `bls12381_element` fee component: expected burnt corresponds to `elements_count = 0 / 97 = 0` (i.e., no per-element fee charged).
3. Instrument the `p1_sum` implementation (or its `chunks_exact(BLS_P1_SIZE + 1)` loop) to count iterations, and assert it performs `N` (not `0`) point-addition operations.
4. Assert: `bytes_processed (N * 97) > bytes_charged_for (0)`, demonstrating the metering totality invariant is violated.
