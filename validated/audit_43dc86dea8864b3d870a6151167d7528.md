### Title
CORS wildcard allowlist bypass via missing dot-boundary check in suffix match - ([File: core/services/gateway/network/httpserver.go])

### Summary
`httpServer.isAllowedOrigin` validates wildcard entries like `*.remix.com` using a raw `strings.HasSuffix` check without requiring a `.` boundary before the allowed suffix, so an attacker-registered domain such as `evilremix.com` passes the check and is treated as an allowed origin.

### Finding Description
In `isAllowedOrigin`, for wildcard entries the code strips the `*.` prefix and then does: [1](#0-0) 
`strings.HasSuffix(originHost, allowedHost)` only checks that `originHost` ends with the literal string `allowedHost` (e.g. `"remix.com"`); it does not verify that the character immediately preceding the match is a `.` (i.e., that `originHost` is actually a subdomain, not just a domain that happens to end with the same characters). Thus `evilremix.com` satisfies `HasSuffix("evilremix.com", "remix.com")` and is incorrectly treated as matching `*.remix.com`.

This function is invoked directly from `handleRequest`, which is the exposed HTTP handler for gateway requests, reading the caller-controlled `Origin` header with no authentication required to influence the check: [2](#0-1) 
An unauthenticated attacker can register `evilremix.com`, serve a page from it, and send a browser request to the gateway with `Origin: https://evilremix.com`. The gateway will respond with `Access-Control-Allow-Origin: https://evilremix.com`, extending CORS trust intended only for `*.remix.com` subdomains to the attacker's unrelated domain.

### Impact Explanation
This is an allowlist boundary-check bypass: the wildcard CORS origin allowlist can be bypassed by any attacker who registers a domain sharing a suffix with the allowed root domain (no subdomain relationship required). If any browser-based, credential-bearing flow is ever layered on top of this endpoint (cookies, or JS that auto-attaches bearer tokens), this enables cross-origin reads from an attacker-controlled origin that should not be trusted — a boundary/allowlist bypass consistent with an authorization/allowlist bypass impact class.

### Likelihood Explanation
Preconditions: gateway operator configures `CORSEnabled: true` and includes a wildcard entry in `CORSAllowedOrigins` (e.g. `https://*.remix.com`). No credentials or special role are needed by the attacker — only registering an inexpensive domain with the matching suffix (e.g. `evilremix.com`) and hosting a page there. This is deterministic and repeatable for any wildcard entry.

### Recommendation
Require a dot boundary when matching wildcard suffixes, e.g. after stripping `*.`, check `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` instead of a bare `strings.HasSuffix(originHost, allowedHost)`.

### Proof of Concept
Add a table-driven Go test in `core/services/gateway/network/httpserver_test.go`:
```go
func TestIsAllowedOrigin_WildcardSuffixBoundary(t *testing.T) {
    s := &httpServer{config: &HTTPServerConfig{CORSAllowedOrigins: []string{"https://*.remix.com"}}, lggr: logger.Test(t)}
    assert.True(t, s.isAllowedOrigin("https://sub.remix.com"))   // legit subdomain
    assert.False(t, s.isAllowedOrigin("https://evilremix.com"))  // attacker domain, should be rejected but currently passes
}
```
Run against current code to confirm `isAllowedOrigin("https://evilremix.com")` returns `true` (bug), then apply the dot-boundary fix and confirm it returns `false`.
