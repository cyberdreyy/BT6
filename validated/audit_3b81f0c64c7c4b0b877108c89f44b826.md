### Title
Builder payment `fee_recipient` is never validated on-chain against the proposer's committed preference, allowing bid value to be paid to an arbitrary address - (File: specs/gloas/beacon-chain.md)

### Summary
In the Gloas builder-payment flow, a builder's `bid.value` (Gwei owed to the block proposer) is paid out to `bid.fee_recipient`, an address chosen solely by the builder. The consensus state-transition function `process_execution_payload_bid` never checks that `fee_recipient` matches the proposer's committed `SignedProposerPreferences`. That match is only enforced as a soft, non-binding `IGNORE` rule in gossip validation, not as a `REJECT` rule and not inside the state transition itself. This mirrors the reported `burnAndBridge` bug class: a value-transfer function accepts a caller-supplied destination address with no whitelist/consistency check against the intended, protocol-recognized recipient.

### Finding Description
`process_execution_payload_bid` records the pending payment using whatever `fee_recipient` is present in the bid, with no cross-check against any state-tracked "correct" proposer address: [1](#0-0) 

The only place `fee_recipient` is ever compared to the proposer's own preference is in the p2p gossip validator, and even there it is an `IGNORE` (i.e., "don't relay it"), not a `REJECT` that would make the bid/block invalid: [2](#0-1) 

The honest-proposer instructions in `validator.md` list the exact conditions a bid `MUST` satisfy to match `process_execution_payload_bid` — signature validity, balance coverage, slot/parent/randao matching — but do **not** include "fee_recipient equals my committed preference": [3](#0-2) 

Yet the builder-side documentation states the protocol's intent unambiguously: the `fee_recipient` field is supposed to carry the proposer's declared preferred address, and "the builder will pay the proposer what it promised": [4](#0-3) 

Once a bid with an attacker-chosen `fee_recipient` is embedded in a block (via any means other than the honest gossip pipeline — e.g. direct submission, a non-conforming relay, or a proposer/builder that doesn't independently re-verify the address), `apply_parent_execution_payload`/`settle_builder_payment` and `get_builder_withdrawals` faithfully carry that `fee_recipient` all the way to an actual `Withdrawal`, paying real Gwei to it: [5](#0-4) 

At no point in this pipeline — `process_execution_payload_bid` → `apply_parent_execution_payload` → `settle_builder_payment` → `get_builder_withdrawals` → `apply_withdrawals` — is `fee_recipient` validated against a whitelist or against the state's own record of who is entitled to that block's builder payment. The state transition function will accept and finalize a block containing such a bid as fully valid.

### Impact Explanation
This falls under "Gwei ... paid to a non-owner," a Critical-severity category per the rubric. The builder's committed payment (`bid.value`), which by protocol design and documentation is meant to compensate the specific proposer of the slot, can be routed to any `ExecutionAddress` the builder names, with the consensus rules offering no on-chain assurance that the value ever reaches the intended proposer. All spec-following nodes that import the block will agree on this incorrect payment destination — it isn't a fork-choice/finality split, but it is a state-transition-level acceptance of an unvalidated, attacker/builder-controlled destination for value the protocol intends to belong to someone else, exactly the pattern flagged in the `burnAndBridge` report (missing recipient/destination whitelist before an irrevocable transfer of value).

### Likelihood Explanation
Likelihood is bounded by the fact that the primary safety net (gossip-level fee_recipient matching) is a soft `IGNORE`, and well-behaved proposer implementations following `validator.md`'s explicit "MUST" checklist would not independently re-verify `fee_recipient` before inclusion, since it is not listed as a required check mirroring `process_execution_payload_bid`. Any proposer, relay, or builder path that bypasses/loosens the gossip filtering layer (which the spec itself allows: "MAY obtain these signed messages by other off-protocol means") can place a bid with an arbitrary `fee_recipient` into a canonical block, and the state transition function will accept it as valid. No coalition, malicious peer partition, or majority stake is required — only a single builder crafting a self-serving `fee_recipient` value in an otherwise well-formed, signed bid.

### Recommendation
Move the `fee_recipient`-matches-proposer-preference check out of the soft gossip `IGNORE` rule and into `process_execution_payload_bid` (or an equivalent state-transition assertion) as a hard `REJECT`/`assert`, so that bids/blocks committing a mismatched `fee_recipient` are invalid at the consensus level, not merely discouraged at the network layer.

### Proof of Concept
Conceptual sequence illustrating the gap:
1. Proposer P for slot `s` broadcasts `SignedProposerPreferences` with `fee_recipient = A` (P's own address).
2. Builder B constructs `bid` with `bid.value = V > 0` but sets `bid.fee_recipient = C` (an address B controls), signs it correctly, and satisfies every other field checked by `process_execution_payload_bid` (slot, parent hash/root, randao, balance coverage, signature).
3. This bid reaches the block proposer through a non-gossip channel (explicitly allowed: "The block proposer MAY obtain these signed messages by other off-protocol means" — [6](#0-5) ) or a relay/proposer implementation that skips the gossip-layer preference check.
4. `process_execution_payload_bid` accepts the bid unconditionally with respect to `fee_recipient` (only checking slot/parent/randao/signature/balance, not fee_recipient) — [7](#0-6) .
5. The block is included and finalized by all spec-following nodes as valid.
6. When the payment settles, `V` Gwei flows to `C`, not to `A`, via `get_builder_withdrawals`'s direct use of `withdrawal.fee_recipient` — [8](#0-7) .

Before: the protocol's documented invariant is "builder pays the proposer what it promised" (fee_recipient == proposer's declared address). After: `V` Gwei is paid to `C`, an address with no on-chain-verified relationship to the slot's proposer, while the block remains fully valid per `process_execution_payload_bid`.

##### Signed execution payload bid

To obtain `signed_execution_payload_bid`, a block proposer building a block on
top of a `state` MUST take the following actions in order to construct the
`signed_execution_payload_bid` field in `BeaconBlockBody`:

- Listen to the `execution_payload_bid` gossip global topic and save an accepted
  `signed_execution_payload_bid` from a builder. The block proposer MAY obtain
  these signed messages by other off-protocol means.
- The `signed_execution_payload_bid` MUST satisfy the verification conditions
  found in `process_execution_payload_bid` with the alias
  `bid = signed_execution_payload_bid.message`, that is:
  - For external builders, the signature MUST be valid.
  - For self-builds, set `bid.builder_index` to `BUILDER_INDEX_SELF_BUILD`.
  - For self-builds, the signature MUST be `bls.G2_POINT_AT_INFINITY` and the
    `bid.value` MUST be zero.
  - The builder balance can cover the `bid.value`.
  - The `bid.slot` is for the proposal block slot.
  - The `bid.parent_block_hash` equals
    `state.latest_execution_payload_bid.block_hash` if
    `should_build_on_full(store, head, get_current_slot(store))` is true,
    otherwise `state.latest_execution_payload_bid.parent_block_hash`.
  - The `bid.parent_block_root` equals the current block's `parent_root`.
  - The `bid.prev_randao` equals
    `get_randao_mix(state, get_current_epoch(state))`.
- Select one bid and set
  `block.body.signed_execution_payload_bid = signed_execution_payload_bid`.

## Builder activities

Builders have two optional activities: submitting bids and submitting payloads.
Builders can submit bids to produce execution payloads. They can broadcast these
bids in the form of `SignedExecutionPayloadBid` objects. These objects encode a
commitment to reveal an execution payload in exchange for a payment. When their
bids are chosen by the corresponding proposer, builders are expected to
broadcast an accompanying `SignedExecutionPayloadEnvelope` object honoring the
commitment. If a proposer accepts a builder's bid, the builder will pay the
proposer what it promised whether it submits the payload or not.

### Constructing the `SignedExecutionPayloadBid`

Builders can broadcast a payload bid for the current or the next slot's proposer
to include. They produce a `SignedExecutionPayloadBid` as follows.

01. Set `bid.parent_block_hash` to be the parent hash of the constructed
    payload, that is `payload.parent_hash`.
02. Set `bid.parent_block_root` to be the head of the consensus chain. This can
    be obtained from the beacon state as
    `hash_tree_root(state.latest_block_header)`. The `parent_block_root` and
    `parent_block_hash` must be compatible, in the sense that they both should
    come from the same `state` and `store` by the method described in this and
    the previous point.
03. Construct an execution payload. This can be performed with an external
    execution engine via a call to `engine_getPayloadV6`.
04. Set `bid.block_hash` to be the block hash of the constructed payload, that
    is `payload.block_hash`.
05. Set `bid.prev_randao` to be the previous RANDAO of the constructed payload,
    that is `payload.prev_randao`. This value **MUST** equal
    `get_randao_mix(parent_state, get_current_epoch(parent_state))`, where
    `parent_state` is the post-state of `bid.parent_block_root`.
06. Set `bid.slot` to be the slot for which this bid is aimed. This slot
    **MUST** be either the current slot or the next slot.
07. Set `bid.fee_recipient` to be an execution address to receive the payment.
    The proposer's preferred fee recipient is obtained from the
    `SignedProposerPreferences` whose `message.proposal_slot` matches `bid.slot`
    and whose `message.dependent_root` matches
    `get_shuffling_dependent_root(store, bid.parent_block_root, compute_epoch_at_slot(bid.slot))`,
    where `store` is the fork choice store.
