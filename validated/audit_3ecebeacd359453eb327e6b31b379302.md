### Title
Performance fee double-counted on recovery of realized epoch loss because `lastNAV` is not a high-water mark — ([File: contracts/IdleCDOEpochVariant.sol])

### Summary

`IdleCDOCreditVault._updateAccounting()` (used by `IdleCDOEpochVariant`) accrues performance fees on the delta `nav - lastNAV` where `lastNAV = lastNAVAA + lastNAVBB` is a *last-seen* value, not a high-water mark. `lastNAV` is ratcheted *down* whenever a loss is crystallized — either through `_virtualPriceAux` distributing a loss in the ordinary `_updateAccounting()` call inside `stopEpoch`, or through the explicit `_lossAmount` path in `stopEpochWithDuration` which burns strategy tokens and then calls `_forceUpdateAccounting()`. On the next epoch's `stopEpoch`, the borrower's interest repayment raises `nav` above the *lowered* `lastNAV`, so `unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC` charges a performance fee on what is merely recovery of principal that was already burned as loss. The exact mirror of the external report: a lowered baseline converts recovery into "new yield," paid to `feeReceiver`/`owner` while LPs are still underwater.

### Finding Description

Relevant code:

`contracts/IdleCDOCreditVault.sol` (fee accrual on any positive delta, then `lastNAV` written to current nav, up or down):

```solidity
uint256 _lastNAV = _lastNAVAA + _lastNAVBB;
uint256 nav = getContractValue();
// If gain is > 0, then collect some fees in `unclaimedFees`
if (nav > _lastNAV) {
  unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
}
...
lastNAVAA = uint256(int256(_lastNAVAA) + _totalAAGain); // can move down
lastNAVBB = uint256(int256(_lastNAVBB) + _totalBBGain); // can move down
```

`contracts/IdleCDOEpochVariant.sol` `_stopEpoch` (lines 496–500) realizes the loss and lowers the baseline:

```solidity
if (_lossAmount != 0) {
  _strategy.burnStrategyTokens(_lossAmount);
  // Realize the active loss immediately through the ordinary BB-first waterfall.
  _forceUpdateAccounting();
}
```

Then in the *next* epoch, `_stopEpoch` again calls `_updateAccounting()` (line 436), which sees `nav > lastNAV` purely because NAV recovered toward its pre-loss level, and accrues `fee * (nav - lastNAV)`. The fee is then paid in cash via `_transferFeeUnderlyings(_fees)` (capped by `_grossInterest - _pendingWithdrawFees`, lines 451–456), or in minted-interest mode minted as AA tranche shares to `feeReceiver`/`owner` (lines 442–448), diluting LPs further.

Concrete trace (fixed-APR, non-minted, `fee = 10%`):

1. Epoch 0: TVL 1000. Borrower repays full interest; `lastNAV` settles at 1000 + net interest.
2. Epoch 1: manager calls `stopEpochWithDuration(…, _lossAmount = 200)` (a legitimate realized-loss path, e.g. partial borrower repayment funded via `collectWithdrawFunds`). Strategy tokens are burned; `_forceUpdateAccounting` writes `lastNAV ≈ 800` (BB-first waterfall).
3. Epoch 2: borrower pays 100 interest. `nav` goes 800 → 900. `_updateAccounting` computes `totalGain = +100` and books `unclaimedFees += 10`, even though cumulative performance vs. the pre-loss NAV (1000) is still −100 and the 100 is recovery of principal, not new yield.
4. `feeReceiver` is paid 10 (cash or AA shares); `netInterest` credited to LPs is reduced accordingly. Repeatable every loss-then-partial-recovery cycle: each cycle leaks up to `fee * _lossAmount` worth of LP recovery to the fee wallet.

No guard prevents this: there is no high-water-mark storage, `skipDefaultCheck`/`Default` revert only engages when a loss exhausts BB (i.e., still-lower `lastNAV`, same bug after `restoreOperations`), and `previewLossAdjustedWithdrawFunds`/`lossRecoveryPriceByEpoch` only haircut pending receipts — they do not protect the fee baseline.

### Impact Explanation

Direct theft of value from tranche LPs to `feeReceiver`/`owner`: up to `fee × realizedLoss` is extracted per loss-recovery cycle, and in minted-interest mode the fee is minted as AA shares, permanently diluting LP NAV. The leak recurs every time the pool recovers after any `stopEpochWithDuration(_lossAmount)` or loss-socializing `updateAccounting`, and even small realized losses in a high-fee vault produce a material, repeated skim while affected LPs remain below their pre-loss value.

### Likelihood Explanation

Any realized partial loss (the supported `_lossAmount` codepath exists precisely for this) followed by any interest-bearing epoch triggers it, and a nonzero `fee` is standard config. No attacker action is needed beyond normal LP deposits/withdrawals that invoke `_updateAccounting`; the fee accrual happens automatically inside honest `stopEpoch` calls. A user could also force crystallization by calling `depositAA`/`withdrawAA` right after the loss accounting and again after recovery, ensuring the inflated `unclaimedFees` is booked.

### Recommendation

Track a high-water mark `lastNavHWM` updated only when `nav` exceeds it, and accrue fees on `nav - lastNavHWM` instead of `nav - lastNAV` (equivalently: only update `lastNAVAA`/`lastNAVBB` downward for tranche pricing while keeping the fee baseline at its historical peak, restoring it on recovery). Apply symmetrically in `IdleCDOCreditVault._updateAccounting`, `IdleCDO._updateAccounting`, and the minted-interest fee minting path in `IdleCDOEpochVariant._stopEpoch` so that recovery of a realized loss is never treated as new yield.

### Proof of Concept

A Foundry test extending `test/foundry/IdleCreditVault.t.sol` (reuse `_setFeeParams(TL_MULTISIG, 10_000, FULL_ALLOC, 0)`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `deal(defaultUnderlying, borrower, …)`):

```solidity
function testFeeDoubleCountOnLossRecovery() external {
    uint256 amount = 10_000 * ONE_SCALE;
    _setFeeParams(TL_MULTISIG, 10_000, FULL_ALLOC, 0); // 10% performance fee
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // Epoch 0: normal stop, interest paid, lastNAV = principal + netInterest
    _startEpochAndCheckPrices(0);
    uint256 navBeforeLoss = cdoEpoch.getContractValue();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 interest0 = cdoEpoch.expectedEpochInterest();
    deal(defaultUnderlying, borrower, interest0);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, 365 days, 0);

    // Epoch 1: realized loss of 20% of NAV lowers lastNAV baseline
    _startEpochAndCheckPrices(1);
    uint256 loss = navBeforeLoss / 5;
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, 365 days, loss);
    uint256 navPostLoss = cdoEpoch.getContractValue();
    uint256 feesPostLoss = cdoEpoch.unclaimedFees();

    // Epoch 2: borrower repays interest that only recovers part of the loss
    _startEpochAndCheckPrices(2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, 365 days, 0);

    // Cumulative NAV is still below navBeforeLoss, yet fees grew:
    assertLt(cdoEpoch.getContractValue(), navBeforeLoss, "pool still underwater");
    assertGt(cdoEpoch.unclaimedFees(), feesPostLoss,
        "performance fee charged on recovery of burned principal");
}
```

Key assertion: `unclaimedFees` increases even though `getContractValue()` after the recovery epoch is strictly below its pre-loss value — feeReceiver profit is extracted from LP principal/recovery, matching the external report's "recovery counted as new yield" invariant break.
