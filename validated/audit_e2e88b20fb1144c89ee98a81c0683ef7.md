### Title
Second withdraw request overwrites `lastWithdrawRequest`, letting a loss-adjusted receipt escape its haircut and claim at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The kernel bug reuses a single `nfs_pgio_header` scratch buffer across multiple requests: state set up once is freed/reused, leaving a stale pointer that decodes garbage for subsequent replies. The credit-vault analog lives in `IdleCreditVault`: the "scratch" state that decides *how* a pending withdraw receipt must be paid (par, loss-adjusted, or defaulted) is keyed by the single mutable slot `lastWithdrawRequest[_user]`. A user who holds a receipt that was haircut via `lossRecoveryPriceByEpoch` can issue a second `requestWithdraw` in a later epoch, overwriting the marker. The loss-adjusted claim path then becomes unreachable for the old epoch while the underlying claim basis (`withdrawsRequests[_user]` / `withdrawsRequestsByEpoch`) persists, so `_claimFundedWithdrawRequest` pays the haircutted receipt at par — the same "stale state reused for a new request" failure, manifesting as paying out more than was ever funded.

### Finding Description
When `stopEpoch` realizes a loss, `IdleCDOEpochVariant` calls `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws`. The shortfall is recorded as `lossRecoveryPriceByEpoch[epochNumber]` and `pendingWithdraws` is zeroed — i.e., pending receipts are only partially funded and must later be claimed through `_claimLossAdjustedWithdrawRequest`, which pays `claimBasis * lossRecoveryPrice / RECOVERY_FULL` [1](#0-0) .

The loss-adjusted path locates the user's claimable epoch exclusively via `lastWithdrawRequest[_user]`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
``` [2](#0-1) 

But `requestWithdraw` unconditionally overwrites this marker on every new request and accrues the new amount into the same aggregate `withdrawsRequests[_user]` bucket [3](#0-2) . After the marker is overwritten:

- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[newEpoch] == 0` and returns 0, so the old epoch's haircut is never applied.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still contains the haircutted epoch's basis, since `_clearWithdrawClaimForEpoch` was never invoked for it — **in full, at par**, burning the receipt tokens and transferring funded underlyings [4](#0-3) .

The gate in `_claimFundedWithdrawRequest` (`epochNumber <= lastWithdrawRequest[_user]` → revert) only enforces a one-epoch wait; it does not distinguish funded vs loss-adjusted sub-receipts inside the aggregate [5](#0-4) . Per-epoch bookkeeping (`withdrawsRequestsByEpoch`) exists precisely to separate these, but the funded path pays the aggregate without consulting it.

Broken invariant: one receipt one payout / loss waterfall — a receipt the borrower funded only `p%` of is paid 100%, with the excess drawn from the strategy's funded reserve that backs other users' claims.

### Impact Explanation
Direct theft / insolvency. If an epoch ends with a realized loss and pending receipts are funded at, e.g., 50% (`lossRecoveryPriceByEpoch[E] = RECOVERY_FULL/2`), any affected holder of a loss-adjusted receipt can deposit-or-request again in a subsequent epoch, wait one epoch, and `claimWithdrawRequest` for the **full** original basis. The un-funded half is paid out of the strategy's underlying reserve (`_transferFundedClaim`), stealing from every other pending receipt holder and LP. Loss scales linearly with the haircut size and the attacker's receipt share; in a large-loss epoch (e.g., 90% haircut), the attacker extracts ~10× what they are owed, up to draining the entire funded withdraw reserve.

### Likelihood Explanation
Requires an epoch that ends via `stopEpochWithDuration(_lossAmount)` with `_lossAmount > 0` and pending withdraws — an honest borrower/manager flow, not attacker-controlled privileges. Any unprivileged tranche holder with a pending receipt in that epoch qualifies, and the second `requestWithdraw` only requires holding tranche tokens (the attacker can deposit fresh, or even request, claim nothing, and re-request). No KYC bypass needed — the attacker is an ordinary allowed lender. The code comment itself acknowledges the overwrite pattern ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait another epoch"), so the trigger path is a documented usage pattern, not an edge case.

### Recommendation
Key loss-adjusted claims by iterating the user's per-epoch receipts rather than a single `lastWithdrawRequest` marker. Concretely:

1. In `_claimLossAdjustedWithdrawRequest`, do not rely solely on `lastWithdrawRequest[_user]`; check every epoch for which `withdrawsRequestsByEpoch[_user][epoch] != 0` (or track a per-user claimable-epoch set) and apply `lossRecoveryPriceByEpoch[epoch]` when non-zero.
2. In `_claimFundedWithdrawRequest`, compute the payable amount as `withdrawsRequests[_user]` **minus** any per-epoch portions that have a non-zero `lossRecoveryPriceByEpoch` haircut, so the funded path can never pay a haircutted receipt at par.
3. Alternatively, fold loss-adjusted epochs into `withdrawsRequestsByEpoch` at `collectWithdrawFunds` time by writing the realized per-epoch basis, so no later request can orphan the haircut state.

### Proof of Concept
Foundry fork test outline (extend `test/foundry/` harness style of `IdleCDOEpochQueue.t.sol`):

```solidity
function testLossAdjustedReceiptEscapesHaircut() external {
    // epoch N running; user deposits, requests withdraw of all tranches
    uint256 tranches = _depositWithUser(attacker, 100e6);
    _requestWithdrawWithUser(attacker, tranches);      // lastWithdrawRequest[attacker] = N
    // borrower realizes loss at stopEpoch: collectWithdrawFunds funds only 50%
    // => lossRecoveryPriceByEpoch[N] = RECOVERY_FULL/2, pendingWithdraws = 0
    _stopCurrentEpochWithLoss(pendingBasis / 2);

    // attacker requests again in epoch N+1 (small fresh deposit), marker overwritten
    uint256 t2 = _depositWithUser(attacker, 1e6);
    _requestWithdrawWithUser(attacker, t2);            // lastWithdrawRequest[attacker] = N+1
    _stopCurrentEpochWithApr(apr);                     // fund epoch N+1 fully at par
    _advanceOneEpoch();                                // pass funded-claim gating

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdo.claimWithdrawRequest();                        // -> strategy.claimWithdrawRequest(attacker)
    // BUG: _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[N+1]==0, skips;
    // _claimFundedWithdrawRequest pays withdrawsRequests[attacker] (epoch-N basis + N+1) at par.
    // Expected haircutted payout was ~50% of epoch-N basis; attacker receives ~100%.
    assertGt(underlying.balanceOf(attacker) - balPre, expectedHaircuttedPayout);
}
```

Verification: compare the claimed amount against `withdrawsRequestsByEpoch[attacker][N] * lossRecoveryPriceByEpoch[N] / RECOVERY_FULL + t2Payout`; the delta is stolen reserve.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;

    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
