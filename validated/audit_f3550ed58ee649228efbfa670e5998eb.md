### Title
Missing workflow/DON ownership check in `CapabilityController.ExecuteCapability` allows cross-workflow capability execution by any run-role user - (File: core/web/capability_controller.go)

### Summary
`CapabilityController.ExecuteCapability` accepts an arbitrary, client-supplied `CapabilityRequest` (including its `WorkflowID`/`WorkflowExecutionID` metadata) and forwards it directly to `capability.Execute()` without verifying that the authenticated session/user is authorized for that specific workflow, DON, or capability. The route is registered only behind `auth.RequiresRunRole`, which checks the caller's coarse-grained role (`run` vs `view` vs `admin`) and performs no per-resource ownership check.

### Finding Description
The handler reads the raw `capabilityRequest` bytes from the client, unmarshals them into a `commoncap.CapabilityRequest` (which carries `RequestMetadata.WorkflowID` and `WorkflowExecutionID`), looks up the named capability from the global `capabilityRegistry`, and calls `capability.Execute(ctx, capabilityRequest)`: [1](#0-0) 

Nothing in this flow cross-checks `capabilityRequest.Metadata.WorkflowID` against the identity of the caller established by `RequiresRunRole`. The auth wrapper only asserts the session's role is at least `run`: [2](#0-1) 

There is no concept of workflow ownership enforced anywhere in this call chain — `GetAuthenticatedUser` only returns role/email, and the handler never consults it to constrain which `WorkflowID` values are permissible. As the existing test suite confirms, `ExecuteCapability` accepts and executes any well-formed `CapabilityRequest` containing an arbitrary `WorkflowID` (`"test-workflow"`), with no authorization check tying it to a caller: [3](#0-2) 

Since the route is registered in `core/web/router.go` guarded only by `build.IsDev()` and `auth.RequiresRunRole` (per the audit prompt's file references), a valid run-role session is sufficient to reach `ExecuteCapability` and supply any `WorkflowID` in the request body — including one belonging to a different tenant/workflow the caller does not own.

### Impact Explanation
A low-privileged run-role user can invoke capabilities scoped to workflows/DONs they do not own by crafting a `CapabilityRequest` payload referencing another tenant's `WorkflowID`. Depending on what the targeted capability does (e.g., write/target/trigger capabilities), this can result in unauthorized job/capability execution on behalf of another workflow, cross-tenant capability invocation, or unintended side effects (e.g., triggering on-chain writes or external actions) attributable to a workflow the attacker does not control — this maps to Chainlink's "unauthorized job run" / authorization bypass impact class.

### Likelihood Explanation
Preconditions are minimal: any valid run-role session (the lowest privileged non-view role) and the node built/running with `build.IsDev()==true`, which is the default in CI/dev/test builds. No knowledge of internal secrets is required beyond guessing or discovering a target `WorkflowID` (which may be enumerable or known from other API responses). The request is a single, repeatable HTTP POST, making this a low-effort, high-repeatability path once dev-mode is enabled — a concerning default for CI/e2e/dev environments where this route is live.

### Recommendation
Bind the request to the caller's authorized workflow context: derive the permitted `WorkflowID`(s) for the authenticated session/API-token (or the DON/job it corresponds to) and reject any `CapabilityRequest` whose `Metadata.WorkflowID` does not match. Alternatively, remove the generic `CapabilityRequest` bytes from client input entirely and instead have the server construct/attach the trusted workflow identity server-side (e.g., derived from the caller's associated job/workflow record) rather than trusting the client-supplied metadata. At minimum, add an explicit ownership check between `auth.GetAuthenticatedUser(c)` and the capability request's `WorkflowID` before calling `capability.Execute`.

### Proof of Concept
Handler-level Go test plan:
1. Set up `gin` engine identical to `TestCapabilityController_ExecuteCapability`, but wrap the route with `auth.RequiresRunRole` and inject a session user (role `run`) associated with `WorkflowID = "workflow-A"` (e.g., via a fake session/user-workflow mapping table, if one exists, or via `c.Set(auth.SessionUserKey, ...)`).
2. Craft a `CapabilityRequest` with `Metadata.WorkflowID = "workflow-B"` (owned by a different user) and marshal into `CapabilityRequestOuter`.
3. POST to `/v2/execute_capability` as the "workflow-A" run-role session.
4. Assert: the current implementation returns `http.StatusOK` and executes the capability (as shown by `TestCapabilityController_ExecuteCapability`), demonstrating no rejection occurs for mismatched `WorkflowID` — expected/fixed behavior should instead assert `http.StatusForbidden`/`StatusUnauthorized` and that `capability.Execute` is never called (verified via mock `AssertNotCalled`).

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

			"result": &values.String{Underlying: "success"},
		}},
	}
	executableCap.EXPECT().Execute(mock.Anything, mock.AnythingOfType("capabilities.CapabilityRequest")).Return(expectedResponse, nil)

	controller := web.CapabilityController{App: mockApp}

	inputsMap, err := values.NewMap(map[string]any{
		"test": "input",
	})
	require.NoError(t, err)

	configMap, err := values.NewMap(map[string]any{
		"config": "value",
	})
	require.NoError(t, err)

	capabilityRequest := commoncap.CapabilityRequest{
		Metadata: commoncap.RequestMetadata{
			WorkflowID:          "test-workflow",
			WorkflowExecutionID: "test-execution",
		},
		Config: configMap,
		Inputs: inputsMap,
	}

	capabilityRequestBytes, err := pb.MarshalCapabilityRequest(capabilityRequest)
	require.NoError(t, err)
	requestBody := web.CapabilityRequestOuter{
		CapabilityName:    capabilityName,

	}
	reqJSON, err := json.Marshal(requestBody)
	require.NoError(t, err)

	w := httptest.NewRecorder()
	engine := gin.New()

	req, err := http.NewRequestWithContext(t.Context(), http.MethodPost, "/v2/capabilities/execute", bytes.NewBuffer(reqJSON))
	require.NoError(t, err)
	req.Header.Set("Content-Type", "application/json")

	engine.ServeHTTP(w, req)
