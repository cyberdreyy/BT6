### Title
Stale single-slot `lastWithdrawRequest` lets multi-epoch receipts escape the `lossRecoveryPriceByEpoch` haircut — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to CVE-2015-8964 (reading stale memory that no longer describes the real state), `IdleCreditVault` keeps only one epoch marker per user (`lastWithdrawRequest`). When a user has pending withdraw receipts in *two* different epochs and the epoch stops with a `stopEpochWithDuration` loss, `_claimLossAdjustedWithdrawRequest` applies the haircut only to the receipt of the *latest* epoch; the older epoch's receipt falls through to `_claimFundedWithdrawRequest` and is paid at par — even though `collectWithdrawFunds` only funded the aggregate `pendingWithdraws` at the haircut price. The user is overpaid out of funds reserved for other claimants.

### Finding Description
- `requestWithdraw` records per-epoch basis in `withdrawsRequestsByEpoch[user][currentEpoch]` but stores only one marker: `lastWithdrawRequest[user] = currentEpoch` (line 282). A user may legally hold unfunded receipts from multiple epochs: the guard at lines 263-271 only reverts if the *previous* `lastWithdrawRequest` epoch already has a nonzero `lossRecoveryPriceByEpoch`, which is not the case when the earlier receipt was created before any loss epoch.
- `collectWithdrawFunds` funds the whole `pendingWithdraws` aggregate at `_amount < pendingBasis` and stores `lossRecoveryPriceByEpoch[epochNumber]` (lines 411-421). The loss is shared pro rata across *all* pending receipts (`previewLossAdjustedWithdrawFunds`, lines 440-460).
- On claim, `_claimLossAdjustedWithdrawRequest` reads only `lossEpoch = lastWithdrawRequest[_user]` (line 790) and `_clearWithdrawClaimForEpoch` clears only `withdrawsRequestsByEpoch[user][lossEpoch]`, decrementing `withdrawsRequests[user]` by just that epoch's amount (lines 815-820).
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — the older epoch's receipt — in full at par (lines 338-349), because the gate `epochNumber <= lastWithdrawRequest[user]` passes after the marker was reset to 0 at line 835.

Broken invariant: every pending receipt that was funded at `lossRecoveryPrice` must be claimed at that price. The single-slot marker "loses" the older epoch, exactly like the tty structure exposing stale data.

### Impact Explanation
Direct theft / insolvency. If a user has `r0` pending from epoch N-1 and `r1` from epoch N, and epoch N stops with funded ratio `p < 1`, the strategy receives `(r0 + r1) * p` but pays `r1 * p + r0`. The excess `r0 * (1 - p)` is paid from the same funded pool that backs other users' loss-adjusted claims, so later claimants (or the reserve) absorb the shortfall. The attacker controls `r0` size by depositing/requesting arbitrary amounts, so the theft scales linearly.

### Likelihood Explanation
Requires only unprivileged actions: deposit AA/BB (KYC-permitted lender), `requestWithdraw` in two consecutive epochs, then `claimWithdrawRequest` after a manager-called `stopEpochWithDuration` with `_lossAmount > 0` and partial funding — a designed code path, not an edge case. No privileged misbehavior needed; the loss need not be adversarial.

### Recommendation
Track per-epoch pending receipts exhaustively instead of a single marker: e.g. iterate/accumulate all epochs with nonzero `withdrawsRequestsByEpoch[user]` that have a `lossRecoveryPriceByEpoch`, or store a per-user list of request epochs; alternatively, in `requestWithdraw`, revert if *any* unfunded receipt exists (extend the existing guard so `lastWithdrawRequest` semantics cannot strand an older epoch's haircut).
