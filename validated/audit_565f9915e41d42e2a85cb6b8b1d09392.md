**Reasoning summary:**

The proposed attack path conflates two unrelated things: `get_account_transaction_summaries` (and its API handler `list_txn_summaries_by_account`) is a read-only query endpoint that only reads already-committed transaction summaries from storage via `get_account_transaction_summaries_iter` [1](#0-0) [2](#0-1) . It has no interaction with transaction submission, execution, or replay-protector validation — it cannot be used to resubmit or replay a transaction.

Actual replay protection for orderless (nonce-based) transactions is enforced in the Move prologue via `check_for_replay_protection_orderless_txn`, which calls `nonce_validation::check_and_insert_nonce` [3](#0-2) . This function rejects any resubmission of the same `(sender, nonce)` pair whose expiration time hasn't yet passed the replay-protection overlap window, returning `false` (causing `PROLOGUE_ENONCE_ALREADY_USED`) [4](#0-3) . A captured, already-executed `staking_contract::request_commission` transaction with the same nonce cannot be re-executed through `submit_transaction` because the VM prologue runs this check before entry-function execution for every submission, sequence-number-based or orderless [5](#0-4) .

Even setting aside replay protection, the commission-distribution logic itself is idempotent by design. `request_commission_internal` computes the commission delta from `staking_contract.principal` (`last_recorded_principal`) versus current total active stake, and immediately updates `staking_contract.principal` to the new total before returning [6](#0-5) . A second call in the same epoch/state would compute zero additional commission, which is explicitly covered by the framework test `test_operator_cannot_request_same_commission_multiple_times` [7](#0-6) .

Both layers — nonce-based replay protection at the VM/prologue level and idempotent commission accounting at the Move logic level — independently block the described attack. There is no unprivileged path by which replaying a captured commission transaction, whether via the summaries API or the submission endpoint, can double-trigger commission distribution or corrupt operator commission accounting.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

        let pool_address = staking_contract.pool_address;
        emit(
            RequestCommission {
                operator,
                pool_address,
                accumulated_rewards,
                commission_amount
            }
        );

        commission_amount
    }
