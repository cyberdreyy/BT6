### Title
`setEpochParams` does not re-scale `scaledApr`, so epoch interest is computed against stale epoch duration — ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCDOEpochVariant.setEpochParams` updates `epochDuration` and `bufferPeriod` but never calls `_setScaledApr`, even though `scaledApr` (stored in `IdleCreditVault` via `setAprsWithBuffer`) is a derived value that depends on both parameters. This is a direct analog of the Bond `setIntervals`/`tuneBelowCapacity` bug: a derived parameter that must be recomputed when its inputs change is left stale. The protocol itself acknowledges the dependency — `stopEpochWithDuration` calls `setEpochParams` and then immediately re-scales the APR to correct it, but plain `setEpochParams` has no such correction. [1](#0-0) [2](#0-1) 

### Finding Description
`scaledApr` is set by `_setScaledApr`, which forwards `epochDuration` and `bufferPeriod` to `IdleCreditVault.setAprsWithBuffer` — it is an APR normalized for the configured epoch length plus buffer. [3](#0-2) 

`setEpochParams` is callable by the owner/manager only when no epoch is running (i.e., exactly when APR/duration reconfiguration happens), and it writes `epochDuration`/`bufferPeriod` without re-scaling. [1](#0-0) 

The stale value is then consumed on the next `startEpoch`, where `expectedEpochInterest` is computed via `_calcInterest(getContractValue())`, which uses `scaledApr`. That expected interest determines how much cash is pulled from the borrower in `_stopEpoch` (`_amountToPullFromBorrower` / `getFundsFromBorrower`). [4](#0-3) [5](#0-4) 

Attack sequence (all privileged calls are honest operator actions):

1. Vault running with `epochDuration = 30 days`, `scaledApr` scaled for 30 days. Epoch stops normally; `stopEpoch` re-scales APR for the current duration (line 471). [6](#0-5) 
2. Owner calls `setEpochParams(15 days, bufferPeriod)` to shorten the epoch. `scaledApr` remains scaled for 30 days — effectively ~2x too high relative to the new duration.
3. During the buffer window, an unprivileged KYC'd attacker deposits a large position (`depositAA`).
4. Owner calls `startEpoch`; `expectedEpochInterest` is computed with the doubled effective APR.
5. At `stopEpoch`, the vault pulls the inflated interest amount from the borrower; `_updateAccounting` distributes it pro-rata to tranche holders, including the attacker, who then requests/claims withdrawal at the inflated price.

The symmetric case (owner lengthens `epochDuration`) under-charges the borrower, silently transferring LP yield to the borrower. The NatSpec comment only warns that `bufferPeriod` must not change; there is no warning that `epochDuration` changes require an APR re-scale, and there is no public re-scale function other than `stopEpochWithDuration`/`stopEpoch`, which can only run at epoch end. [7](#0-6) 

### Impact Explanation
Broken invariant: fair mint/burn / solvency of the fixed-APR interest obligation. When `epochDuration` is shortened, `expectedEpochInterest` is overstated by roughly `oldDuration/newDuration` (e.g., 2x for a 30d→15d change), and the excess is pulled from the honest borrower at `stopEpoch` and distributed to tranche holders. An attacker who front-runs `startEpoch` with a deposit captures a pro-rata share of the overpayment — direct theft of borrower funds, quantified as `(stale scaled APR − correct scaled APR) × NAV × duration`. In the lengthening direction, LP yield is permanently lost to the borrower.

### Likelihood Explanation
Changing `epochDuration` between epochs is a normal, permitted operator action (`setEpochParams` is explicitly not-blocked between epochs; only `epochDuration == 0`/running/defaulted are rejected). The bug triggers deterministically on the next epoch once duration is changed through `setEpochParams` rather than `stopEpochWithDuration`. No guard (skim, flags, gating) prevents it, since the stale value is read inside the normal `startEpoch`/`stopEpoch` flow. The attacker only needs a KYC-passing deposit during the buffer, which is within the allowed attacker model.

Caveat I could not fully verify within the iteration limit: the exact normalization formula inside `IdleCreditVault.setAprsWithBuffer` (whether `scaledApr` scales linearly with `epochDuration + bufferPeriod`). If the scaling is not linear, the magnitude changes but the staleness defect remains: any duration/buffer dependence makes the stored APR wrong after `setEpochParams`.

### Recommendation
Re-scale the stored APR whenever epoch timing parameters change, mirroring the `stopEpochWithDuration` fix pattern: after updating `epochDuration`/`bufferPeriod` in `setEpochParams`, call `_setScaledApr(strategy.unscaledApr())` (or store the unscaled APR and derive `scaledApr` lazily at `startEpoch`/`stopEpoch` from the *current* duration). Alternatively, remove `setEpochParams`'s ability to change `bufferPeriod`/`epochDuration` independently and force all duration changes through `stopEpochWithDuration`, which already performs the re-scale.

### Proof of Concept
Foundry fork PoC sketch (based on `test/foundry/IdleCreditVault.t.sol` harness, e.g., `testOnlyOwnerOrManagerVariables` setup):

```solidity
// precondition: vault live, epochDuration = 30 days, scaledApr set, not running
uint256 apr = strategy.unscaledApr();
uint256 nav = cdo.getContractValue();

// 1) honest owner shortens epoch via the non-rescaling setter
vm.prank(owner);
cdo.setEpochParams(15 days, cdo.bufferPeriod());

// scaledApr is unchanged — still scaled for 30 days
// assertEq(strategy.apr(), scaledAprFor30d); // stale

// 2) attacker (KYC'd) deposits during buffer
deal(underlying, attacker, amount);
vm.prank(attacker);
cdo.depositAA(amount);

// 3) start epoch — expectedEpochInterest uses stale scaledApr
vm.prank(manager);
cdo.startEpoch();
uint256 expected = cdo.expectedEpochInterest();
// expected is ~2x what the borrower should owe for a 15d epoch

// 4) borrower funds and stop; excess interest is paid to tranche holders
vm.warp(cdo.epochEndDate() + 1);
// borrower pays inflated _amountToPullFromBorrower at getFundsFromBorrower
vm.prank(manager);
cdo.stopEpoch(apr, 0);

// attacker claims withdraw at inflated tranche price:
// profit ≈ attackerShare * (interest_30d_scale - interest_15d_scale)
assertGt(attackerRedeemValue, attackerPrincipal + fairInterest);
```

Key assertion: `expectedEpochInterest` after step 3 equals the 30-day-scaled interest despite `epochDuration == 15 days`, demonstrating that the derived parameter was not refreshed when `setEpochParams` ran — the same defect class as the Bond `tuneBelowCapacity` omission.

```text
  /// @notice update epoch duration
  /// @dev IMPORTANT: bufferPeriod should not be changed once set otherwise interest calculations will be wrong
  /// @param _epochDuration duration in seconds
  /// @param _bufferPeriod time between 2 epochs
  function setEpochParams(uint256 _epochDuration, uint256 _bufferPeriod) public {
    _checkOnlyOwnerOrManager();
    // cannot set epoch params if epoch is running
    // cannot set epochDuration to 0 as it's reserved for closing the pool
    // and cannot set epochDuration if previously was set to 0 as borrower repaid all funds
    _checkNotAllowed(defaulted || isEpochRunning || _epochDuration == 0 || epochDuration == 0);
    epochDuration = _epochDuration;
    bufferPeriod = _bufferPeriod;
  }
```

```text
  function stopEpochWithDuration(uint256 _newApr, uint256 _interest, uint256 _duration, uint256 _lossAmount) public {
    // stop epoch checks that msg.sender is allowed
    _stopEpoch(_newApr, _interest, _lossAmount);
    if (_interest != 1 && !defaulted) {
      // buffer period is not changed
```
