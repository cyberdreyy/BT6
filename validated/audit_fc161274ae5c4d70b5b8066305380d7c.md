### Title
Stale cached share-value indexes for uninvolved banks skew liquidation health computation - ([File: programs/marginfi/src/instructions/marginfi_account/liquidate.rs])

### Summary
`lending_account_liquidate` only forces an interest accrual on the two banks directly involved in the liquidation (`asset_bank` and `liab_bank`) before computing the liquidatee's health, but the health computation itself (`get_health_components`, invoked via `check_pre_liquidation_condition_and_get_account_health`) iterates over **every active balance** in the liquidatee's `lending_account`, including balances in banks that were not accrued in this transaction. This is the same bug class as the reported Compound/Morpho issue: the liquidation decision is made using potentially outdated cached indexes (`asset_share_value` / `liability_share_value`) for positions that aren't the target of this particular liquidation call.

### Finding Description
In `lending_account_liquidate`, interest is explicitly accrued only for the two banks passed as accounts: [1](#0-0) 

Immediately after, `check_pre_liquidation_condition_and_get_account_health` is called to determine whether the liquidatee is actually liquidatable: [2](#0-1) 

That function delegates to `get_health_components`, which loops over **all** of the liquidatee's active balances (not just the asset/liab pair being liquidated) to sum weighted asset/liability values: [3](#0-2) 

For each balance, the weighted value is computed from the bank's cached `asset_share_value`/`liability_share_value`: [4](#0-3) 

These share values (`Bank.asset_share_value` / `Bank.liability_share_value`) live in the `Bank` account itself and are only mutated inside `Bank::accrue_interest`, which must be explicitly invoked (either by the touching instruction, or by the standalone permissionless `accrue_interest` instruction used in tests): [5](#0-4) 

Because `lending_account_liquidate` only calls `bank.accrue_interest(...)` on `asset_bank` and `liab_bank`, any *other* bank in which the liquidatee holds a balance (a third collateral or debt position not chosen for this liquidation call) retains whatever `asset_share_value`/`liability_share_value` was last written — which can be stale if nobody has interacted with that bank recently. The health check that gates whether the account "IsLiquidatable" (`account_health <= 0`) is therefore computed with a mix of freshly-accrued values for the two involved banks and possibly stale values for all other banks in the account, exactly mirroring the reported Morpho/Compound defect where `_isLiquidatable` only updates indexes for the borrow/collateral pair while iterating all entered markets.

### Impact Explanation
When a liquidatee has more than two active positions, the account's true maintenance health can differ from the on-chain computed health because interest owed/earned on the untouched banks isn't reflected. This can:
- Understate a liquidatee's true liabilities (if a stale liability bank hasn't compounded interest), making an actually-liquidatable account appear healthy and blocking `MarginfiError::HealthyAccount` rejection of legitimate liquidations — protocol accrues additional bad debt while a truly underwater position sits unliquidated.
- Or overstate/understate an unrelated collateral position's value, distorting the exact health margin used in `check_post_liquidation_condition_and_get_account_health`'s "must strictly improve" invariant, potentially permitting a liquidation sizing decision based on an inaccurate health snapshot.

This is a real accounting/timing inconsistency with financial effect (delayed liquidations / bad debt accumulation), matching the Medium severity of the original finding, though it requires a naturally multi-position account with an inactive third bank rather than being independently triggerable by an attacker to forcibly redirect value.

### Likelihood Explanation
This occurs under ordinary conditions any time a liquidatee holds a position in a bank with low trading/interaction volume (so its `accrue_interest` hasn't run recently) in addition to the asset/liab pair being liquidated. No malicious setup is required — it is a systemic consequence of interest only being accrued for the two banks named in the liquidate instruction while the health engine still reads all balances. A liquidator can mitigate this only if they know to proactively call the permissionless `accrue_interest` instruction on every other bank in the target's position set before submitting the liquidation, which is not enforced or automatic.

### Recommendation
Before computing `check_pre_liquidation_condition_and_get_account_health` in `lending_account_liquidate` (and similarly in `start_receivership`/`end_receivership`), accrue interest for **every bank referenced by the liquidatee's active balances**, not just `asset_bank` and `liab_bank`. This can be done by iterating `liquidatee_marginfi_account.lending_account.balances` and calling `bank.accrue_interest(...)` on each corresponding bank loaded from `remaining_accounts` prior to invoking `get_health_components`, ensuring the health computation always reflects live compounded values, matching Compound's live `borrowIndex` recommendation from the source report.

### Proof of Concept
1. Set up a liquidatee account with three balances: Bank A (asset collateral), Bank B (liability being targeted for liquidation), and Bank C (a second liability or collateral position in a bank with no recent activity so its `last_update`/share values are stale).
2. Advance the clock significantly so that Bank C, if accrued, would show materially different (e.g., larger) liability value, but do not send any transaction that touches Bank C (no deposit/withdraw/borrow/repay/accrue_interest on Bank C).
3. Call `lending_account_liquidate` targeting `asset_bank = A`, `liab_bank = B`. Per `liquidate.rs` lines 155-167, only A and B get `accrue_interest`.
4. `check_pre_liquidation_condition_and_get_account_health` sums maintenance value across all balances (A, B, C) via `get_health_components`, using Bank C's stale `liability_share_value` from before the elapsed time.
5. Observe that the computed `account_health` differs from the value that would be obtained if Bank C had also been accrued — in cases where this masks true liability growth, an account that should be liquidatable (`account_health <= 0` post-accrual) instead reports `account_health > 0` and the transaction reverts with `MarginfiError::HealthyAccount`, blocking a legitimate liquidation of an insolvent position.
