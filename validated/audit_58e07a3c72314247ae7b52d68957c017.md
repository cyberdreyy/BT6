### Title
Early division in `_calcInterestWithApr` truncates the scaled APR and permanently underpays epoch interest to lenders - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`_calcInterestWithApr` performs `(_apr / 100)` before multiplying by the amount and epoch duration. Because the stored APR is a scaled APR (scaled by `setAprsWithBuffer` to cover `epochDuration + bufferPeriod`), it is almost never a multiple of 100. The premature division truncates the fractional APR, so `expectedEpochInterest`, withdraw-request interest, write-off interest, and mid-epoch deposit pricing are all computed on a systematically understated rate, causing lenders to permanently lose yield.

### Finding Description
In `contracts/IdleCDOEpochVariant.sol:807-809`:

```solidity
function _calcInterestWithApr(uint256 _amount, uint256 _apr) internal view returns (uint256) {
    return _amount * (_apr / 100) * epochDuration / (365 days * ONE_TRANCHE_TOKEN);
}
```

`_apr / 100` is evaluated first, discarding the sub-100 remainder of the scaled APR. The APR stored in `IdleCreditVault` is set via `setAprsWithBuffer(_newApr, epochDuration, bufferPeriod)` (`IdleCDOEpochVariant.sol:544-546`), i.e. `newApr * (epochDuration + bufferPeriod) / epochDuration`. With the defaults (30-day epoch, 5-day buffer) a 10% APR becomes `1000 * 35 / 30 = 1166`, so `_apr / 100` yields `11` instead of `11.66` — roughly 5.7% of the intended interest is dropped before any multiplication. For scaled APRs below 200 the truncation can halve the computed interest, and below 100 it produces zero interest for the entire epoch.

This truncated value feeds every interest path:
- `startEpoch` sets `expectedEpochInterest = pendingWithdrawFees + _calcInterest(getContractValue())` (`IdleCDOEpochVariant.sol:260-262`), and `stopEpoch` pulls only `_amountToPullFromBorrower = _expectedInterest` from the borrower (`IdleCDOEpochVariant.sol:373-408`). Whatever is truncated is never requested; the borrower keeps it.
- In minted-interest mode only `_grossInterest` (derived from the truncated expectation) is minted as strategy tokens (`IdleCDOEpochVariant.sol:428-430`), so the missing yield is never credited to tranche holders at all.
- `requestWithdraw`/`writeOffDeposit` price interest via `_calcInterestWithdrawRequest`, which calls `_calcInterest` twice (`IdleCDOEpochVariant.sol:865,875`), so both the receipt amount and `interestForOverUnderPerformance` are understated.
- `depositDuringEpoch` computes `trancheInterest` and `expectedEpochInterest` accrual from the same truncated rate (`IdleCDOEpochVariant.sol:693-728`).

### Impact Explanation
Lenders permanently lose a quantifiable fraction of epoch yield — up to `apr % 100` scaled-APR units, i.e. up to ~1 percentage point of nominal APR, and up to 100% of interest when the scaled APR is under 100 (e.g. nominal ~2.9% APR with default durations: `200 * 35/30 = 233` is fine, but a nominal APR of ~2.5% → scaled ~291; a nominal APR under ~0.86% truncates to zero when scaled < 100... precisely, any scaled APR in `(0,100)` yields zero interest). For common configurations the loss is single-digit percent of the expected interest each epoch, compounding every epoch. This is a direct, permanent loss of unclaimed yield to AA/BB tranche holders and to withdraw-request receipt holders whose payouts are fixed at request time from the understated interest.

### Likelihood Explanation
The bug triggers deterministically on every epoch for any scaled APR that is not an exact multiple of 100, which is the norm given the `(epoch + buffer) / epoch` scaling factor. No malicious actor or special market condition is required; honest owner/manager/borrower operation suffices. The main mitigant is that deployments using APRs that happen to scale to round multiples of 100 are unaffected, and the relative loss shrinks for large APRs.

### Recommendation
Reorder the expression to multiply before dividing:

```solidity
return _amount * _apr * epochDuration / (100 * 365 days * ONE_TRANCHE_TOKEN);
```

Verify against overflow for the intended magnitude of `_amount` (underlying units) and `_apr`; if necessary use `Math.mulDiv`. Apply the same fix in the test mirror `_calcInterestAtApr` (`test/foundry/IdleCreditVault.t.sol:3556-3558`) so expectations match production.

### Proof of Concept
Conceptual Foundry test (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testAprTruncationLosesInterest() external {
    // default: epochDuration = 30 days, bufferPeriod = 5 days
    // set nominal apr 10% => scaled apr = 1000 * 35 / 30 = 1166 (not a multiple of 100)
    uint256 tvl = 1_000_000 * ONE_SCALE;
    uint256 scaledApr = 1166;

    uint256 computed = cdoEpochExposed._calcInterestWithApr(tvl, scaledApr);
    uint256 correct  = tvl * scaledApr * 30 days / (100 * 365 days * 1e18);

    // computed uses 1166/100 = 11, correct uses 11.66 -> ~5.7% of interest lost
    assertLt(computed, correct);
    assertApproxEqRel(computed * 100 / correct, 9430, 1e16); // ~94.3% of true interest
}
```

The same check can be run end-to-end: deposit, `startEpoch`, then compare `expectedEpochInterest` against `getContractValue() * scaledApr * epochDuration / (100 * 365 days * 1e18)` — it will be lower by the truncated remainder, and `stopEpoch` will pull exactly that lower amount from the borrower, crystallizing the loss.
