### Title
Stale confirmations from removed multisig members count toward execution threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` counts entries in the `confirmations` `HashSet` for a request against `num_confirmations` without verifying that every recorded confirmer is still a current member. `delete_member` (and, in the older `multisig` contract, the `DeleteKey` action) only purges requests that the removed member/key originally *created*; it never scans `confirmations` on other, still-pending requests to strip out that member's prior confirmation. A confirmation recorded while a signer was a valid member therefore persists and is later counted as live authorization even after that signer is removed from the multisig, exactly mirroring the reported bug class where a party's recorded approval is not invalidated when the underlying authorization (NFT ownership / membership) changes hands.

### Finding Description
`confirm` in `multisig2/src/lib.rs` checks only set membership/count, not liveness of confirmers: [1](#0-0) 

`delete_member` removes the member and access key, and cleans up only requests that member itself created (`r.member == member`); it does not touch `self.confirmations` for requests created by *other* members that this member had previously confirmed: [2](#0-1) 

The same pattern exists in the original `multisig/src/lib.rs`, where `DeleteKey` only removes `request_ids` filtered by `r.signer_pk == pk` (requests the deleted key created), leaving that key's confirmations on other requests intact: [3](#0-2) [4](#0-3) 

The binding that should hold is: `count(confirmations[request_id]) == count(live members who confirmed request_id)`. Once a member is removed, this equality breaks — `confirmations[request_id]` still includes the removed member's stale approval, while the true count of live confirmers is one less.

### Impact Explanation
This directly matches the in-scope "Critical" impact category: *"a multisig request executed below threshold."* Because a stale confirmation from a since-removed member can push a pending request's confirmation count to `num_confirmations`, the request (e.g. a `Transfer`, `AddKey`/`AddMember`, or `FunctionCall` action moving or controlling NEAR funds) can execute with fewer currently-authorized signers than the configured threshold actually requires — effectively allowing NEAR to be moved by a party (or set of parties) not entitled to authorize it under the current membership set.

### Likelihood Explanation
No privileged action beyond ordinary multisig usage is required: a pending request only needs a partial set of confirmations before one confirmer is removed via a normal, legitimate `DeleteMember`/`DeleteKey` request (e.g. rotating out a departing member or a compromised key) — this is expected multisig operational activity, not an edge case. Once removal happens, any remaining live member(s) confirming later unknowingly execute the request below the intended threshold. The condition arises purely from ordinary sequencing of unprivileged/`member`-level calls (`add_request`, `confirm`, `DeleteMember`), with no need to bypass initialization or exploit a redeploy.

### Recommendation
When a member/key is deleted, iterate over all pending requests (or lazily validate at `confirm`/execution time) and strip the removed member's entry from every `confirmations` set, not just requests they authored. Alternatively, at confirmation-count time, filter `confirmations[request_id]` to only members still present in `self.members` before comparing against `num_confirmations`, ensuring the count reflects only currently-live confirmers.

### Proof of Concept
1. Initialize `MultiSigContract::new(members: [A, B, C, D], num_confirmations: 3)`. [5](#0-4) 
2. Member `A` calls `add_request` to create request `R1` (e.g., `Transfer` funds to an external account). [6](#0-5) 
3. Member `B` calls `confirm(R1)` → confirmations = `{A, B}` (2 confirmations, below threshold 3). [1](#0-0) 
4. Member `C` calls `confirm(R1)` → confirmations = `{A, B, C}` — still assume threshold logic requires it not to fire yet (adjust ordering/threshold as needed, e.g. num_confirmations=4 with 5 members) so `R1` remains pending with `C`'s stale confirmation recorded.
5. Separately, members execute a `DeleteMember { member: C }` request (a routine, legitimate action, e.g. offboarding). `delete_member` removes `C` from `self.members` and deletes access key, but does not remove `C`'s confirmation from `R1`'s `confirmations` set. [2](#0-1) 
6. Member `D` (a live member) calls `confirm(R1)`. The count check `confirmations.len() as u32 + 1 >= self.num_confirmations` uses the stale `C` entry plus `D`, reaching the threshold and executing `R1` even though only `A`, `B`, and `D` are currently live members confirming — one fewer live signer than the configured threshold requires. [7](#0-6) 

This demonstrates the request executes below the intended live-member threshold, allowing NEAR to be transferred (or other privileged actions like `AddKey`) with insufficient current authorization — a Critical-severity violation of the confirmations-vs-live-members binding.

        let current_member = self.current_member().unwrap_or_else(|| {
            env::panic_str(
                "Predecessor must be a member or transaction signed with key of given account",
            )

            .get(&current_member.to_string())
            .unwrap_or(0)
            + 1;
        assert(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some.",
        );
        self.num_requests_pk
            .insert(&current_member.to_string(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            member: current_member,
            added_timestamp: env::block_timestamp(),
            request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
