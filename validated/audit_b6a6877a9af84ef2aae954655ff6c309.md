Confirmed: the flashblocks WebSocket publisher's `Listener::run` accepts unbounded TCP connections with no cap on total concurrent connections, and per the docker-compose deployment config it binds to `0.0.0.0` (externally reachable) at [1](#0-0) , distinct from the internal control-plane RPC actor which already enforces `max_connections` and `ConcurrencyLimitLayer` as a deliberate backstop [2](#0-1) .

### Title
Unauthenticated denial of service via unbounded flashblocks WebSocket connection acceptance - (File: `crates/builder/publish/src/listener.rs`)

### Summary
The flashblocks WebSocket publisher's accept loop in `Listener::run` accepts every incoming TCP connection and spawns a new tokio task per connection with only a 10-second handshake timeout, with no limit on the total number of concurrent connections that can be open at once.

### Finding Description
`Listener::run` loops on `listener.accept()` and, for every accepted socket, immediately spawns a `tokio::spawn` task performing the WebSocket handshake (`accept_hdr_async`) bounded only by `HANDSHAKE_TIMEOUT` (10s), then proceeds to run a `BroadcastLoop` for the client indefinitely: [3](#0-2) . There is no cap on the number of concurrently accepted connections, no per-IP connection limiting, and no backpressure mechanism, unlike the sibling internal RPC actor which explicitly caps `max_connections` and layers a `ConcurrencyLimitLayer`/`LoadShedLayer` as a documented mitigation against exactly this class of resource-exhaustion attack: [4](#0-3) . The `WebSocketPublisher::with_capacity` constructor binds the raw `TcpListener` and hands it straight to this unbounded `Listener::run` loop: [5](#0-4) . In the reference HA deployment, this listener is explicitly exposed on `0.0.0.0` rather than localhost: [1](#0-0) .

### Impact Explanation
Each accepted connection consumes a file descriptor and spawns a tokio task that lives for up to the handshake timeout (or indefinitely once upgraded, since `BroadcastLoop` has no idle/read timeout apparent in this file). An unauthenticated remote attacker can open connections faster than they time out, exhausting file descriptors, memory, and scheduler/task capacity on the builder node's flashblocks endpoint. This can prevent legitimate flashblocks subscribers (e.g., downstream infrastructure relying on sub-block payload streaming) from connecting, and depending on resource pressure could degrade or crash the builder process serving block production — a node/service availability impact matching the "no impact" threshold only if truly isolated, but here it threatens the flashblocks service specifically and any co-located resources (fd table, memory) shared with block-building.

### Likelihood Explanation
Likelihood is high wherever the flashblocks port is reachable from untrusted networks (as configured with `--flashblocks.addr=0.0.0.0` in the provided HA compose file). The attack requires only the ability to open raw TCP connections to the exposed port — no authentication, valid WebSocket handshake completion, or protocol knowledge is needed to consume a connection slot until the 10-second timeout elapses.

### Recommendation
Add an explicit cap on total concurrent connections (and optionally per-IP limits) in `Listener::run`, similar to the `max_connections`/`ConcurrencyLimitLayer` backstop already used in `launch_rpc_server`. Reject or defer accepting new connections once the limit is reached, and consider a shorter TCP-level idle timeout before the WebSocket handshake begins.

### Proof of Concept
1. Deploy the builder with `--flashblocks.addr=0.0.0.0 --flashblocks.port=1111` as in `etc/docker/docker-compose.ha.yml`.
2. From an external host, open thousands of raw TCP connections to `1111` without completing the WebSocket handshake (e.g., using a simple script that connects and holds the socket open, or connects/disconnects rapidly in a loop).
3. Observe the builder's file descriptor count and tokio task count grow unbounded via `tokio::spawn` in `Listener::run`, degrading or exhausting resources for legitimate flashblocks subscribers.
