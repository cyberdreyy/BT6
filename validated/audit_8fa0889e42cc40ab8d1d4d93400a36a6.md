### Title
Unbounded CPU cost from zstd compression of large accounts via `getAccountInfo` `base64Zstd` encoding - ([File: account-decoder/src/lib.rs])

### Finding Description
`encode_ui_account` in [1](#0-0) handles the `Base64Zstd` case by feeding the *entire* account data buffer into `zstd::stream::write::Encoder` with no length pre-check: [2](#0-1) 

This contrasts with the `Binary`/`Base58` paths, which explicitly reject data larger than `MAX_BASE58_BYTES` (128 bytes) before doing any encoding work via `encode_bs58`: [3](#0-2) 

The RPC entrypoint `encode_account` in `rpc/src/rpc.rs` only applies the `MAX_BASE58_BYTES` guard for `Binary`/`Base58` encodings; `Base64` and `Base64Zstd` fall straight through to `encode_ui_account` with no size cap: [4](#0-3) 

`get_account_info` calls `get_encoded_account` → `encode_account` inside a `spawn_blocking` task, which isolates the async runtime but does not bound the cost of the work itself: [5](#0-4) [6](#0-5) 

An attacker can, via ordinary transactions (e.g. `Allocate`/`CreateAccount`/program `extend`), grow an account's data up to `MAX_PERMITTED_DATA_LENGTH` (10 MiB), which is explicitly permitted on-chain: [7](#0-6) 

A single subsequent `getAccountInfo(pubkey, {encoding: "base64Zstd"})` call then forces the validator to zstd-compress the full 10 MiB buffer synchronously within that request's blocking task, with CPU/memory cost scaling with the attacker-controlled account size, and no documented or enforced per-request cap analogous to `MAX_BASE58_BYTES`.

### Impact Explanation
A single low-rate RPC call (one call, well under `CLUSTER_SLOT_TIME_TARGET / 2`) against a public JSON-RPC node forces disproportionate CPU/memory work in the compression path proportional to on-chain account size (up to 10 MiB), rather than being bounded by an explicit per-request limit. This matches the "unbounded cost for a single low-rate call" RPC DoS category in scope, since it requires only unprivileged client access and a previously-stored large account (allowed on-chain data, no privileged config needed).

### Likelihood Explanation
Fully feasible with unprivileged access: growing an account to `MAX_PERMITTED_DATA_LENGTH` is a standard, permitted on-chain operation (e.g., via `Allocate`/`CreateAccount` or program data extension), and the attacker fully controls the account's owner/pubkey they query. Once the account exists, every subsequent `getAccountInfo`/`getMultipleAccounts`/`getProgramAccounts` call with `base64Zstd` encoding against it repeats the cost—repeatable indefinitely with a single call each time.

### Recommendation
Add an explicit size guard for `Base64`/`Base64Zstd` encodings analogous to the `MAX_BASE58_BYTES` check for `Binary`/`Base58` in `encode_account` (`rpc/src/rpc.rs`), or cap the amount of data passed into `zstd::stream::write::Encoder` in `encode_ui_account` (`account-decoder/src/lib.rs`), rejecting/erroring or falling back to plain `Base64` for slices exceeding a fixed threshold, independent of the account's actual on-chain size.

        elapsed
    );

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
