### Title
Post-default withdraw requests pay 1:1 out of `defaultRecoveryReserve` with no matching funding, draining the reserve owed to defaulted-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
After `finalizeDefaultRecovery` runs, new withdraw requests are routed through the `postDefaultRequests` path in `IdleCreditVault.requestWithdraw`. That path only burns the CDO's strategy tokens and mints a user receipt — it never pulls underlying into the strategy nor increases `defaultRecoveryReserve`. When the user claims, `_claimPostDefaultWithdrawRequest` pays the full receipt 1:1 via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve`. The reserve was sized at finalization to cover only the defaulted-epoch claim basis (`defaultPendingClaimBasis` = `pendingWithdraws` + unfunded instant claims). Post-default payouts are therefore unfunded outflows that steal underlying reserved for defaulted claimants. This is the vault analog of a use-after-free: a receipt is created from accounting state that was already "freed" (finalized), and its later claim dereferences a reserve bucket that was never sized for it.

### Finding Description
`finalizeDefaultRecovery` sets `defaultRecoveryReserve = reserveAmount` where `reserveAmount` covers only `totalBasis = activeBasis + pendingBasis` claims (`IdleCreditVault.sol:686-693`).

After finalization, `requestWithdraw` takes the early-return branch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:247-257
if (defaultRecoveryFinalized) {
  if (_hasWithdrawRequest(_user) || ...) revert NotAllowed();
  _burn(msg.sender, _amount);   // burns CDO strategy tokens
  _mint(_user, _amount);        // user receipt
  postDefaultRequests[_user] = _amount;
  return;                       // no safeTransferFrom, no reserve top-up
}
```

The claim path then spends the recovery reserve:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:760-767
function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
  amount = postDefaultRequests[_user];
  postDefaultRequests[_user] = 0;
  _burn(_user, amount);
  _transferDefaultRecovery(_user, amount);   // defaultRecoveryReserve -= amount
}
```

No code path adds underlying to the strategy or increases `defaultRecoveryReserve` for post-default receipts — the CDO-side haircut on `_amount` only reduces how much is drawn, not where it is drawn from. Burning CDO strategy tokens reduces the active claim basis but adds zero underlying backing, since post-finalization the strategy's underlying balance is exactly `defaultRecoveryReserve` (+ funded-withdraw surplus, which is separately guarded by `_transferFundedClaim`).

Attack sequence (all unprivileged, KYC-passing lender as attacker, in `defaulted`/`finalized` phase):

1. Borrower defaults; owner/manager (honest) calls `finalizeDefault(recovered, source)`. Reserve `R` is set for defaulted claims totaling `B = pendingBasis` at `recoveryPrice = R * 1e18 / totalBasis`.
2. Attacker (a tranche holder with post-haircut value) calls `IdleCDOEpochVariant.requestWithdraw(amount, tranche)` → strategy mints `postDefaultRequests[attacker] = amount`.
3. Attacker calls `claimWithdrawRequest` → receives `amount` underlying from `defaultRecoveryReserve`.
4. Legitimate defaulted-epoch claimants calling `claimWithdrawRequest` later either get less than `claimBasis * recoveryPrice` (reserve exhausted) or revert on `defaultRecoveryReserve -= _amount` underflow / empty balance — permanent freezing of unclaimed recovery.

Invariant broken: "one receipt one payout" / reserve isolation — `defaultRecoveryReserve` must satisfy `Σ defaulted claims × recoveryPrice`; post-default receipts add outflows that were never in `totalBasis`.

### Impact Explanation
Direct theft and permanent freezing of unclaimed recovery yield. An attacker with any post-default tranche position (acquired before default or via normal deposits) can convert a haircut-priced receipt into a 1:1 drain of the isolated recovery reserve. Loss is bounded by `min(postDefaultRequests made, defaultRecoveryReserve)`; every unit drawn reduces what defaulted claimants (including honest users) can recover, and residual claimants are permanently frozen via underflow revert once the reserve is depleted.

### Likelihood Explanation
Requires only that default recovery has been finalized and that the attacker holds tranche tokens post-default — a routine state after `finalizeDefault`. No privileged action, no timing race, and no guard stops it: `_hasWithdrawRequest` only blocks repeat requests, `_transferFundedClaim`'s reserve guard does not apply to `_transferDefaultRecovery`, and nothing validates that post-default payouts were funded. Uncertainty: if `IdleCDOEpochVariant.claimWithdrawRequest` (not fully read here) transfers additional underlying to the strategy covering post-default payouts, solvency impact is mitigated; the strategy code itself contains no such funding, so reserve accounting is still decremented for claims outside `totalBasis` regardless.

### Recommendation
Either fund post-default receipts explicitly — pull the haircut underlying amount into the strategy and add it to `defaultRecoveryReserve` at request time (`defaultRecoveryReserve += _amount` plus a `safeTransferFrom`), or pay post-default claims through `_transferFundedClaim` from non-reserve balance instead of decrementing the reserve. Add an invariant test asserting `underlying.balanceOf(strategy) >= defaultRecoveryReserve` after every post-default request/claim.
