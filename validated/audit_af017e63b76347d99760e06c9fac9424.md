### Title
Anyone can squat a victim's derived lockup address and dictate its terms before the real grantor - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` is a public, unprivileged, `#[payable]` entrypoint that deterministically derives the new lockup's account id purely from `owner_account_id` (`hex::encode(&env::sha256(owner_account_id.as_bytes())[..20])`), with no check that the caller is the foundation or that no lockup for that owner exists yet. Any account can front-run the legitimate grant by calling `create` first for a chosen `owner_account_id`, permanently occupying the address the real grantor would later target, and can set `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration` and `whitelist_account_id` to whatever it wants.

### Finding Description
The invariant the system depends on is:
`lockup_account_id_of(owner) == the terms chosen by owner's legitimate grantor`

But the binding actually enforced by the code is only:
`lockup_account_id_of(owner) = hex::encode(sha256(owner)[..20]) . factory_account_id` — a pure function of `owner_account_id`, with no authorization check on who may call it. [1](#0-0) 

`create()` only asserts `env::attached_deposit() >= MIN_ATTACHED_BALANCE` — there is no `assert_called_by_foundation`, no owner-only check, and no verification that a lockup for this `owner_account_id` hasn't already been created or isn't already pending. It then immediately schedules `Promise::new(lockup_account_id).create_account().deploy_contract(CODE).transfer(deposit).function_call("new", LockupArgs{...})` using attacker-supplied `owner_account_id`, `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `whitelist_account_id` (or the factory default) verbatim. [2](#0-1) 

Exploit flow:
1. Attacker picks `owner_account_id = victim.near` (the account for which a legitimate lockup grant is expected but not yet created).
2. Attacker calls `create(victim.near, attacker_duration, attacker_timestamp, attacker_vesting, attacker_release_duration, attacker_whitelist)` with `MIN_ATTACHED_BALANCE`.
3. `Promise::new(lockup_account_id).create_account()` succeeds because the account does not yet exist, deploying `lockup_contract.wasm` with attacker-chosen terms, and `on_lockup_create` logs success — `is_promise_success()` is true, so no rollback occurs.
4. When the real grantor (foundation) later calls `create(victim.near, real_terms, ...)`, `Promise::new(lockup_account_id).create_account()` fails at the protocol level because the account id is already taken; `on_lockup_create`'s `is_promise_success()` returns false, and the foundation's deposit is refunded via `Promise::new(predecessor_account_id).transfer(attached_deposit.0)`. [3](#0-2) 

The victim's account is still recorded as `owner_account_id` inside the attacker-deployed lockup (so the victim nominally "owns" it and can call owner-gated methods), but every parameter that governs when/how funds unlock — `lockup_duration`, `lockup_timestamp`, `release_duration`, `vesting_schedule`, and the `staking_pool_whitelist_account_id` used to validate delegation targets — was fixed by the attacker, not by the grantor who was supposed to control them. None of the existing guards (`assert_self()`, `is_promise_success()` in `on_lockup_create`) address authorization of who may call `create`; they only manage promise-result bookkeeping after the fact.

### Impact Explanation
This exactly matches the explicitly enumerated Critical impact: "a lockup deployed with parameters its rightful creator never chose." Because the derived address is a pure function of `owner_account_id`, the attack is repeatable against any account expected to receive a future grant, and once squatted the address can never legitimately be reused (the real creation always fails and only refunds the deposit, it never displaces the attacker's contract). Depending on `whitelist_account_id` and `vesting_schedule` chosen by the attacker, funds later sent to that address (by the victim, by tooling that recomputes the "expected" lockup address, or by the real grantor's failed-but-partially-processed flow) could be staked only with attacker-controlled staking pools or released under attacker-chosen unlock schedules.

### Likelihood Explanation
The only precondition is knowledge of the `owner_account_id` that will eventually receive a lockup (typically public information, e.g., known token-sale participants or foundation grant recipients) and `MIN_ATTACHED_BALANCE` (3.5 NEAR) plus gas, both attacker-affordable. `create` has no allowlist or role check, so this is trivially and repeatably executable by any account against any not-yet-provisioned owner.

### Recommendation
Restrict `create` to the foundation account (or another privileged/authorized caller) via an `assert_called_by_foundation`-style check, and/or maintain on-chain state recording which `owner_account_id`s have already been granted/reserved so repeated or front-run calls for the same owner are rejected. Alternatively, derive the lockup address from something the attacker cannot front-run (e.g., a value pre-committed or signed by the foundation) rather than purely from `owner_account_id`.

### Proof of Concept
```rust
// in lockup-factory/src/tests (extends existing test module)
#[test]
fn test_attacker_squats_owner_lockup_address() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    let victim = account_tokens_owner(); // the eventual real grantee
    let lockup_duration: WrappedTimestamp = 63036000000000000u64.into();

    // 1. Attacker (any unprivileged account) front-runs the grant.
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(victim.clone(), lockup_duration, None, None, None,
        Some(/* attacker-controlled whitelist */ custom_whitelist_account_id()));

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let ok = contract.on_lockup_create(lockup_account(), ntoy(35).into(), String::from("attacker.near"));
    assert!(ok); // attacker's contract now lives at hex(sha256(victim))+factory

    // 2. Real grantor later tries to create the legitimate lockup for the same owner.
    context.predecessor_account_id = account_near(); // foundation
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(victim.clone(), lockup_duration, None, None, None, None);

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    // create_account fails because the id is already taken by the attacker's contract.
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let ok2 = contract.on_lockup_create(lockup_account(), ntoy(35).into(), account_near());
    assert_eq!(ok2, false); // legitimate creation permanently fails; deposit is refunded,
                            // but the address is forever bound to attacker-chosen terms.
}
```
This demonstrates the binding `lockup_account_id_of(victim) == terms chosen by victim's real grantor` is broken: after step 1, `lockup_account_id_of(victim)` is permanently bound to attacker-chosen `lockup_duration`/`whitelist_account_id`, and the legitimate creation in step 2 can never succeed at that address.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
