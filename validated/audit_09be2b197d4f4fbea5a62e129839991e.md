### Title
Cross-user callback collision via sender-independent `MessageId` key in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's `ProcessRequest` only length-checks `jsonRequest.ID` (`gateway.go:228-231`), while the actual dispatch/callback bookkeping for legacy requests uses `msg.Body.MessageId`, a value set independently inside the decoded message body. The capabilities handler's `savedCallbacks` map is keyed solely by `MessageId` with no sender component, so any signer who submits a request with a `MessageId` matching another user's in-flight request will overwrite that user's saved callback.

### Finding Description
`ProcessRequest` decodes the raw JSON-RPC envelope, decodes it into an `api.Message` via `g.codec.DecodeJSONRequest`, and only validates `len(jsonRequest.ID)` [1](#0-0) . For legacy requests it calls `msg.Validate()` (which checks DON-level fields/signature) and then dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)` [2](#0-1) .

Inside the capabilities handler, the outstanding request is stored keyed purely by `msg.Body.MessageId`: [3](#0-2) 

And when a node response arrives, it is looked up and deleted using the same sender-independent key: [4](#0-3) 

Nothing in this path binds `MessageId` to the sender's identity/address before it is used as the map key — `msg.Validate()` and the DON/service lookup logic (`gateway.go:250-262`) do not enforce per-sender uniqueness of `MessageId` at the handler layer. As a result, if a second signer submits a legacy request with a `MessageId` identical to another user's still-outstanding request to the same DON handler, `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` at line 412 silently overwrites the first entry. The original caller's callback reference is lost from the map; when the DON node response for the original message arrives, it will be delivered to whichever callback is currently stored under that key (the second/attacker's callback), or the second caller's original response can instead be lost/overwritten depending on race timing.

### Impact Explanation
This is a cross-user response confusion: an attacker can cause another user's `HandleLegacyUserMessage` callback to be silently discarded, or receive/steal delivery of a response intended for another user's request, by choosing the same `MessageId`. This falls under "cross-user response confusion" in the accepted impact list, since request/callback isolation across users is violated at `core/services/gateway/handlers/capabilities/handler.go:150` and `:411-412`.

### Likelihood Explanation
Exploitability depends on the attacker being able to (a) submit a legacy signed request to the same gateway/DON handler with an attacker-chosen `MessageId`, and (b) know or predict a victim's outstanding `MessageId` within the callback's live window (bounded by `defaultCallbackMaxAgeSec` = 120s) [5](#0-4) . Any client capable of sending a validly-signed gateway message (an unprivileged but registered DON member/user, as required by the threat model) can pick an arbitrary `MessageId`; there is no code visible in this trace that binds it to sender identity or enforces global uniqueness beyond the raw map assignment. This makes the collision straightforward to trigger deterministically in a two-request unit test, though real-world exploitation requires the attacker to learn or guess a target's in-flight `MessageId` (e.g., via a shared/predictable ID scheme, or observed error/echo responses), which limits — but does not eliminate — practical likelihood.

### Recommendation
Namespace `savedCallbacks` (and any similar per-request maps in `handlers/capabilities/handler.go`) by a composite key of `(sender/signer address, MessageId)` rather than `MessageId` alone, mirroring the `{sender,id}` tuple approach already used elsewhere in `RequestCache`. Additionally, validate `msg.Body.MessageId` (length/format) at decode/validate time in `gateway.go`/`api/message.go`, consistent with the existing `jsonRequest.ID` length check.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two `api.Message` values with distinct valid sender signatures/addresses but identical `Body.MessageId` and `Body.Method = MethodWebAPITrigger`.
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, callbackA)` then `handler.HandleLegacyUserMessage(ctx, msgB, callbackB)` on the same `handler` instance.
3. Assert `h.savedCallbacks[messageId]` now references `callbackB`'s saved entry (`id` field / pointer equality), i.e., `callbackA`'s entry has been evicted/overwritten.
4. Simulate a node response for the original message via `handleWebAPITriggerMessage` and assert the response is delivered to `callbackB` (attacker) instead of `callbackA` (victim), or that `callbackA.Wait(ctx)` times out/never resolves.
