### Title
DoS of deposit/withdraw/rebalance value calculations when L2 sequencer is down or in grace period, with no owner-controlled override - ([File: v2/AeraVaultAssetRegistry.sol])

### Summary
`AeraVaultAssetRegistry.spotPrices()` reverts with `Aera__SequencerIsDown` or `Aera__GracePeriodNotOver` whenever the configured Chainlink L2 sequencer uptime feed reports the sequencer down or within the 1-hour grace period after recovery [1](#0-0) . This mirrors the exact root-cause pattern of the referenced Arrakis report: a hard revert on sequencer-check failure with no owner-controlled mechanism to disable the check in an emergency.

### Finding Description
`spotPrices()` is a core pricing primitive used by `AeraVaultV2` for computing asset registry value (deposit/withdraw accounting and guardian rebalance submissions rely on it, as referenced by `IAssetRegistry.spotPrices()` and called from `v2/AeraVaultV2.sol`) [2](#0-1) . The function performs:
```
if (address(sequencer) != address(0)) {
    (, answer, startedAt,,) = sequencer.latestRoundData();
    if (answer != 0) revert Aera__SequencerIsDown();
    if (block.timestamp < startedAt + GRACE_PERIOD_TIME) revert Aera__GracePeriodNotOver();
}
``` [3](#0-2) 
`sequencer` and `GRACE_PERIOD_TIME` (3600 seconds, hardcoded constant) are both `immutable`/`constant`, and there is no `onlyOwner` function anywhere in the contract to pause, bypass, or shorten this check [4](#0-3) . This is the same failed-guard pattern as the reported issue: a legitimate, ordinary operational event (L2 sequencer outage/restart) causes an unconditional revert with no owner escape hatch.

### Impact Explanation
While the sequencer is down, or for up to one hour after it resumes, any call path that depends on `spotPrices()` for valuation (deposit/withdraw settlement math and guardian rebalance value checks in `AeraVaultV2`) will revert. This is a temporary, protocol-wide freeze of vault operations tied to L2 downtime — consistent with a Medium-severity temporary DoS/freeze classification, not fund theft.

### Likelihood Explanation
This requires no attacker action — it triggers automatically any time the L2 sequencer used for the configured `sequencer` feed goes down or restarts, which is an operational event outside protocol control. The vulnerable code is unconditionally reachable by any external call to `spotPrices()` whenever `sequencer != address(0)`.

### Recommendation
Add an owner-gated pause/override for the sequencer check (e.g., a `setSequencerCheckPaused(bool)` function restricted to the asset registry owner) so operations can continue in emergencies, matching the fix suggested in the referenced report.

### Proof of Concept
Not independently constructed here — I could not fully trace, within the available tool budget, the exact call chain from `AeraVaultV2` deposit/withdraw/rebalance functions into `spotPrices()` to confirm which specific user-facing functions revert and under what conditions (e.g., whether `value()` is called synchronously in `deposit`/`withdraw`). This should be verified with a local Foundry fork test that mocks a Chainlink `AggregatorV2V3Interface` sequencer feed returning `answer != 0` (or a recent `startedAt`), then calls `AeraVaultV2.deposit`/`withdraw`/guardian rebalance functions and asserts the revert with `Aera__SequencerIsDown`/`Aera__GracePeriodNotOver`, before treating this as a confirmed live finding.
