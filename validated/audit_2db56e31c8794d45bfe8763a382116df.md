### Title
Unauthenticated raw error disclosure via AuthenticateByToken error passthrough to jsonAPIError - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateByToken` returns the raw `err` from `authr.FindUserByAPIToken` whenever it is not `sql.ErrNoRows` or `clsessions.ErrUserSessionExpired`, instead of the generic `auth.ErrorAuthFailed`. That raw error then flows up through `Authenticate` into `jsonAPIError`, which serializes it with `err.Error()` directly into the JSON:API response body sent back to the (unauthenticated) caller.

### Finding Description
The authentication middleware chain works as follows: any request carrying `X-API-KEY`/`X-API-SECRET` headers is routed through `auth.Authenticate(store, auth.AuthenticateByToken, ...)` [1](#0-0) . Inside `AuthenticateByToken`, the user lookup is performed via `authr.FindUserByAPIToken(ctx, token.AccessKey)` [2](#0-1) . If that call fails with `sql.ErrNoRows` or `clsessions.ErrUserSessionExpired`, the code correctly normalizes the response to the generic `auth.ErrorAuthFailed`. For any other error (e.g., a DB timeout, driver-level error, or any wrapped error surfaced by the storage/auth provider), the function returns `err` unmodified.

That returned error propagates to `Authenticate`'s loop: `err = method(c, store); if !errors.Is(err, auth.ErrorAuthFailed) { break }` [3](#0-2) . Because the error is not `auth.ErrorAuthFailed`, the loop breaks immediately (also short-circuiting evaluation of any subsequent auth methods) and calls `jsonAPIError(c, http.StatusUnauthorized, err)` [4](#0-3) .

`jsonAPIError` does not redact or generalize the error; unless it type-asserts to `*models.JSONAPIErrors`, it calls `c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))`, directly embedding `err.Error()` into the HTTP response body: [5](#0-4) .

This means any error text produced along the `FindUserByAPIToken` code path (implemented per auth provider, e.g., `core/sessions/localauth/orm.go`, `core/sessions/ldapauth/ldap.go`, `core/sessions/oidcauth/oidc.go`) that is not exactly `sql.ErrNoRows`/`ErrUserSessionExpired` will be echoed verbatim to the requester. An unauthenticated attacker only needs to supply the `X-API-KEY`/`X-API-SECRET` headers (any nonempty values) to reach this code path — no valid credentials are required to trigger the lookup and its error handling.

### Impact Explanation
This is an information-disclosure issue: internal error strings (potentially including database driver messages, LDAP/OIDC provider error text, connection details, or other implementation internals) can be returned to an unauthenticated caller. This maps to Chainlink's "sensitive information disclosure" bounty class rather than direct fund loss or key compromise. It does not itself grant authentication bypass or role escalation — `AuthenticateUserByToken`'s success path is untouched, and the disclosure only occurs on the token-verification failure path.

### Likelihood Explanation
Trivial to reach and reproducible by any unauthenticated network client: simply sending any HTTP request carrying non-empty `X-API-KEY`/`X-API-SECRET` headers to an API-token-protected route executes `AuthenticateByToken`. The likelihood of actually causing a non-`ErrNoRows`/non-`ErrUserSessionExpired` error to occur depends on triggering a genuine backend failure (e.g., a database hiccup, LDAP/OIDC provider fault, or other transient/implementation error) during the lookup — this is not fully attacker-controlled and may occur only intermittently or under specific backend conditions, which somewhat lowers day-to-day exploitability but the code path itself is unconditionally reachable pre-authentication.

### Recommendation
In `core/web/auth/auth.go`'s `AuthenticateByToken`, wrap/replace the unexpected error case so no raw backend error is ever returned to the HTTP layer — e.g., log the original error server-side and return `auth.ErrorAuthFailed` (or a generic wrapped error) for all `FindUserByAPIToken` failures, mirroring the pattern already used for `sql.ErrNoRows`/`ErrUserSessionExpired`. More broadly, `jsonAPIError` should not directly embed arbitrary `err.Error()` output for errors originating from data-layer operations; only pre-sanitized/user-facing errors should reach it.

### Proof of Concept
Go handler-level test plan:
1. Create a mock `Authenticator` (reuse the existing mock used in `core/web/auth/auth_test.go`) whose `FindUserByAPIToken` returns a wrapped error such as `errors.New("pq: connection to host db-internal.prod failed: password authentication failed for user \"cl_admin\"")`.
2. Build a `gin.Engine` with a route protected by `auth.Authenticate(mockAuthr, auth.AuthenticateByToken)`.
3. Send an HTTP request with `X-API-KEY: anything` and `X-API-SECRET: anything` headers (no valid token needed).
4. Assert the HTTP response status is `401`.
5. Assert the response JSON body's `errors[0].detail` (or equivalent JSON:API error field) contains the exact injected string (e.g., `"pq: connection to host db-internal.prod failed"`), proving the raw backend error leaked to an unauthenticated caller instead of a generic "authentication failed" message.
6. As a control, repeat with `FindUserByAPIToken` returning `sql.ErrNoRows` and confirm the body instead contains the generic `auth.ErrorAuthFailed` message — demonstrating the inconsistent handling.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
