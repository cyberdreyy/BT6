### Title
`sendInterestAndDeposits` can drain `defaultRecoveryReserve`, permanently underfunding default-recovery claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The vault isolates defaulted/post-default claim backing in `defaultRecoveryReserve`, and `_transferFundedClaim` explicitly enforces that this reserve can never be spent by ordinary funded claims. However, `sendInterestAndDeposits` — the function that sweeps held underlying back to the CDO during deposit/epoch flows — has no such guard. Like CVE-2022-26358's RMRR regions that must remain continuously mapped while a device is active, the recovery reserve must remain continuously backed while receipts are outstanding; once normal operations resume, any deposit-triggered sweep can re-route reserve backing back into the pool, leaving defaulted and post-default claimants underfunded.

### Finding Description
In `IdleCreditVault.sol`, recovery liquidity is tracked only by the `defaultRecoveryReserve` counter, not by a segregated balance. `_transferFundedClaim` (lines 897–906) checks `balance - reserve >= _amount` before paying an old funded claim, with the comment that old receipts "can never spend underlyings reserved for default recovery claimants." But `sendInterestAndDeposits` (lines 581–585) executes `underlyingToken.safeTransfer(idleCDO, _amount)` with no reserve check:

```solidity
function sendInterestAndDeposits(uint256 _amount) external {
  _onlyIdleCDO();
  if (_amount == 0) return;
  IERC20Detailed(token).safeTransfer(idleCDO, _amount);
}
```

The same gap exists for `transferToken` (onlyOwner, honest) — but `sendInterestAndDeposits` is invoked by the honest `idleCDO` during ordinary user-facing flows (deposit forwarding / epoch funding), so an unprivileged lender's `depositAA`/`depositBB` after `restoreOperations` (or any CDO path that pulls idle strategy cash) can consume underlying that finalization earmarked for recovery claims. The reserve counter is then larger than the actual balance, and subsequent `_transferDefaultRecovery` transfers revert on the ERC20 level (insufficient balance) or pay later claimants short — while the drained funds are re-lent to the borrower or distributed to active depositors.

### Impact Explanation
Direct loss / permanent freezing of unclaimed recovery payouts. After `finalizeDefaultRecovery`, every defaulted-epoch receipt and every post-default request is paid exclusively out of `defaultRecoveryReserve` via `_transferDefaultRecovery`, which decrements the counter by the payout. If the backing balance is reduced below the counter by a reserve-blind sweep, the last N claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert (safeTransfer on insufficient balance) — their recovery is permanently frozen — and the corresponding tokens are effectively redistributed to whoever received the swept funds (new depositors / borrower). Loss is bounded by `defaultRecoveryReserve` outstanding at the time, i.e., up to the full unpaid recovery amount.

### Likelihood Explanation
Requires a default that has been finalized with `defaultRecoveryReserve > 0` and at least one still-unclaimed defaulted or post-default receipt, plus resumed CDO operations that pull underlying from the strategy. Post-default `requestWithdraw` is deliberately kept live (`postDefaultRequests` flow), and `restoreOperations` exists precisely to resume the pool — so the state combination is reachable through normal, honest sequences with attacker-controlled sequencing only in that any user can trigger the deposit path that sweeps funds. No privileged misbehavior is needed; the missing guard is the defect (the analogous guard exists for `_transferFundedClaim`, showing the invariant was intended but not enforced on this path).

### Recommendation
Apply the same reserve isolation to every outward underlying transfer: in `sendInterestAndDeposits`, revert unless `underlyingToken.balanceOf(address(this)) - defaultRecoveryReserve >= _amount` (mirroring `_transferFundedClaim`), and apply the same check in `transferToken` when `_token == token`. Alternatively hold the reserve in a separate accounting bucket/balance that is never sweepable.

### Proof of Concept
A Foundry fork test in `test/foundry/IdleCreditVault.t.sol`:

1. Users deposit AA/BB; run epoch 0; borrower funds epoch normally.
2. In epoch 1, attacker calls `cdoEpoch.requestWithdraw` (normal or instant, unfunded).
3. `stopEpoch` with shortfall → `_checkDefault()` state (`defaulted == true`).
4. Manager calls `cdoEpoch.finalizeDefault(partialRecovery, manager)` → `finalizeDefaultRecovery` sets `defaultRecoveryPrice < 1e18` and `defaultRecoveryReserve = R > 0`.
5. Manager calls `restoreOperations` / deposits resume. Attacker calls `idleCDO.depositAA(X)`; the CDO pulls/returns strategy-held underlying via `sendInterestAndDeposits` (or an epoch-start sweep), reducing the strategy balance below `R`.
6. Attacker (or any defaulted claimant) calls `cdoEpoch.claimWithdrawRequest()` → `_transferDefaultRecovery` decrements the counter but `safeTransfer` reverts with insufficient balance, or the final claimant receives less than `claimBasis * defaultRecoveryPrice`.

Assert: `underlying.balanceOf(strategy) < strategy.defaultRecoveryReserve()` after step 5, and the claim in step 6 reverts — proving reserve backing was not kept continuously accessible.

Caveat: I could not fully trace which exact IdleCDOEpochVariant user-facing call invokes `sendInterestAndDeposits` post-`restoreOperations` (only 2 matches in that file, unexpanded); if no path ever pulls strategy-held underlying while a reserve is outstanding, severity reduces to a defense-in-depth inconsistency rather than exploitable loss.
