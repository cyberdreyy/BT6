### Title
Stale-epoch instant-withdraw receipts are excluded from default recovery basis and permanently frozen — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault` records instant-withdraw receipt basis per request epoch in `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`, but default finalization and defaulted-claim settlement only ever read the slot for the *current* `epochNumber` / `defaultRecoveryEpoch`. The aggregate counters `pendingInstantWithdraws` and `instantWithdrawsRequests[user]` are epoch-agnostic. If an instant receipt stays unfunded across an epoch boundary (borrower underfunds instant liquidity at `stopEpoch`, epoch advances via `deposit()` incrementing `epochNumber` at `IdleCreditVault.sol:610`), that receipt becomes a "stale-epoch" claim: it is skipped when computing `defaultPendingClaimBasis()` (`IdleCreditVault.sol:644-649`), skipped by `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`), and then reverts in `_transferFundedClaim` because every other claimant's reserve share was inflated by the missing basis. This is the direct analog of an out-of-bounds read: accounting indexed by epoch is read at the wrong index, so a real claim is invisible to the recovery calculation while still consuming the aggregate.

### Finding Description
- `requestInstantWithdraw` writes basis to `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` (`IdleCreditVault.sol:367-372`), but only bumps the global `pendingInstantWithdraws`.
- `epochNumber` is incremented inside `deposit()` whenever `isEpochRunning()` (i.e., during `stopEpoch`) (`IdleCreditVault.sol:607-611`). Instant receipts that remain unfunded after `stopEpoch` keep their old-epoch slot while `pendingInstantWithdraws` stays > 0.
- On borrower default, `finalizeDefaultRecovery` computes `pendingBasis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` (`IdleCreditVault.sol:644-649`). A stale-epoch instant claim contributes to `pendingInstantWithdraws` (which gates inclusion via `if (pendingInstantWithdraws != 0)`) but its *basis* is read from the new epoch's slot, which is 0 — the claim is silently dropped from `totalBasis` while `defaultInstantWithdrawsFinalized` is set true (`IdleCreditVault.sol:696`).
- At claim time, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — 0 for the stale claim — returns 0, and `claimInstantWithdrawRequest` falls through to `_burn(_user, instantWithdrawsRequests[_user])` + `_transferFundedClaim` (`IdleCreditVault.sol:387-392`). `_transferFundedClaim` reverts because `balance - reserve < amount`: the reserve was sized for a basis that included the stale claim's funds but the recovery price never gave the stale claimant a share (`IdleCreditVault.sol:897-907`).
- Result: the stale claimant's recovery share is redistributed to all other recovery claimants (inflated `defaultRecoveryPrice`), and the stale claimant can never claim — the guard at `IdleCreditVault.sol:904` makes the claim permanently revert.

### Impact Explanation
An unprivileged tranche-token holder who requested an instant withdraw that went unfunded across one epoch boundary loses their entire claim: their receipt tokens are worthless and their pro-rata recovery is siphoned to other claimants (including an attacker who holds a normal defaulted receipt and deliberately waits for finalization). Loss is quantified as the stale claimant's full receipt basis, and the freeze is permanent (default recovery is a one-shot finalization; no re-finalization path exists).

### Likelihood Explanation
Requires the borrower to underfund instant-withdraw liquidity at a `stopEpoch` (a realized-loss or partial-funding event, which the codebase explicitly supports via `collectInstantWithdrawFunds`/`pendingInstantWithdraws` remainder), followed by a later epoch and then a borrower default. Instant withdraws must be enabled on the CDO. The sequence needs no attacker privilege — only ordinary epoch transitions around honest privileged calls — but depends on a default occurring after a cross-epoch unfunded instant receipt, which is a narrow but reachable window in stressed pools.

### Recommendation
Key pending instant accounting to the epoch(s) that actually hold claims instead of assuming `epochNumber`/`defaultRecoveryEpoch` owns all pending instant basis. Concretely: track the oldest unfunded instant epoch (or a global `instantClaimsBasis` aggregate independent of epoch), use it in `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and `_claimDefaultedInstantWithdrawRequest` (iterate or fold all epochs' basis for the user), so stale-epoch instant receipts are haircut and paid from the recovery reserve like every other defaulted claim.

### Proof of Concept
Foundry fork test (schematic; extend `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testStaleEpochInstantReceiptFrozenAfterDefault() external {
    // 1. LP deposits AA, epoch starts, borrower receives funds.
    _depositWithUser(victim, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // 2. During buffer/running phase victim requests instant withdraw.
    //    Borrower only partially funds instant liquidity at stopEpoch,
    //    so pendingInstantWithdraws > 0 after epoch N -> N+1.
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(victimShares, address(AAtranche));
    // underfund instant bucket at stopEpoch (loss path)
    deal(defaultUnderlying, borrower, partialFunds);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr, loss); // pendingInstantWithdraws remains > 0, epochNumber bumped
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // 3. Next epoch runs; borrower defaults. Owner finalizes default.
    //    defaultPendingClaimBasis() reads instantWithdrawClaimsByEpoch[epochNumber]
    //    which no longer contains the victim's claim.
    _runEpochThenDefaultAndFinalize();

    // 4. Victim claim reverts: defaultEpoch slot is empty -> falls to
    //    _transferFundedClaim which reverts against the recovery reserve.
    vm.prank(victim);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimInstantWithdrawRequest();

    // 5. Other claimants received an inflated defaultRecoveryPrice that
    //    absorbed the victim's reserve share.
}
```

Note: I was unable to fully trace `IdleCDOEpochVariant.stopEpoch`/`getInstantWithdrawFunds` within the available iterations to confirm the exact underfunding path that leaves `pendingInstantWithdraws > 0` across `epochNumber` increment; the strategy-side code unconditionally supports that remainder (`collectInstantWithdrawFunds` decrements, never forces to zero), so the staleness window exists iff the CDO permits a `stopEpoch` to conclude with instant requests unfunded, which `previewLossAdjustedWithdrawFunds`/`collectInstantWithdrawFunds` partial-funding semantics imply.
