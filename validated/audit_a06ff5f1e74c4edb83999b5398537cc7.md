Confirmed root-cause candidate found. The missing `return` after the failed type-assertion at line 226-230 of `core/sessions/oidcauth/oidc.go` is a genuine unchecked-failure-continues-execution bug, structurally analogous to the reported HTLC issue (failure signal is observed but not honored, so execution proceeds on invalid/incomplete state).

### Title
Missing `return` after failed email-claim extraction lets OIDC login proceed and create an authenticated session with an empty user identity - (File: core/sessions/oidcauth/oidc.go)

### Summary
In `handleTokenExchange`, when the `email` claim cannot be type-asserted from the ID token claims map, the handler writes an HTTP 500 body but does not `return`. Execution falls through and continues to map the role, write a new row to `oidc_sessions`, log an "AuthLoginSuccessNo2FA" audit event, and set/save a valid session cookie — all using an empty-string email — then responds `200 {"success": true}` to the client despite having already sent the 500 response.

### Finding Description
`handleTokenExchange` performs several checks that correctly `return` on failure (invalid JSON, state mismatch, token exchange failure, missing `id_token`, ID token verification failure, claims parsing failure, `ExtractIDClaimValues` failure). The email extraction check breaks this pattern: [1](#0-0) 
```
	email, ok := claims["email"].(string)
	if !ok {
		oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
		c.String(http.StatusInternalServerError, "Failed to get email from claims")
	}
	oi.lggr.Tracef("Received and validated ID claims: %v\n", idClaims)
```
No `return` statement exists in this `if !ok` block. Because Gin does not implicitly stop a handler after `c.String()`/`c.JSON()` is called (it only writes to the response, it does not abort the goroutine), execution proceeds to the role mapping and the session-creation code below: [2](#0-1) 
```
	role, err := oi.IDClaimsToUserRole(
		idClaims,
		oi.config.AdminClaim(),
		oi.config.EditClaim(),
		oi.config.RunClaim(),
		oi.config.ReadClaim(),
	)
	...
	clSession := clsessions.NewSession()
	_, err = oi.ds.ExecContext(
		ctx,
		"INSERT INTO oidc_sessions (id, user_email, user_role, created_at) VALUES ($1, $2, $3, now())",
		clSession.ID,
		strings.ToLower(email),
		role,
	)
	...
	oi.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, map[string]any{"email": email})

	// save session
	ginSession.Set(webauth.SessionIDKey, clSession.ID)
	err = ginSession.Save()
	...
	c.JSON(http.StatusOK, ExchangeTokenResponse{
		Success: true,
	})
```
The resulting session row is created with `user_email = ""` and whatever `role` was derived from the (still valid) group claims, and a working session cookie is issued to the client, mapped in `AuthorizedUserWithSession` by session ID (not by email), so this empty-email session is fully functional for subsequent API authentication: [3](#0-2) 

This is the same class of defect as the reported analog: a failure/negative-result signal from an operation (`ok == false` from the type assertion, analogous to `transferFrom` returning `false`) is observed and logged, but the code does not halt/abort as it should, and instead proceeds to commit state (session row + issued cookie) as if the operation had succeeded.

### Impact Explanation
An unprivileged client (any actor able to complete the OAuth2/OIDC front-channel flow up to the token-exchange callback, or an identity provider misconfiguration/response that omits the plain `email` claim while still supplying the mapped role claims) can obtain a fully valid, cookie-authenticated Chainlink node session bound to an empty `user_email`. Because `AuthorizedUserWithSession` looks sessions up purely by session ID, this session is indistinguishable from a normal one for all subsequent RBAC-gated Operator UI/API calls, and the user's effective role is still derived from `IDClaimsToUserRole`, so a caller could receive Admin/Edit/Run access under an empty identity, breaking auditability (the audit log records `email: ""`) and identity attribution across the node's authenticated actions.

### Likelihood Explanation
This path is reachable purely through the standard, unprivileged OIDC login flow (`handleSignIn` → provider redirect → `handleTokenExchange`), requiring no special network position or malicious peer/node. Triggering it requires only that the IdP's token response claims lack a top-level string `email` field (e.g., IdP configured to omit it, return it as a different type, or omit it while still returning group/role claims used by `ExtractIDClaimValues`/`IDClaimsToUserRole`) — a scenario plausible under provider misconfiguration or a permissive/compromised IdP client. Chainlink's OIDC configuration is admin-controlled, but the actor exploiting the bug (the browser/session initiating the exchange) is an ordinary unprivileged client, not an operator.

### Recommendation
Add a `return` statement inside the `if !ok` block after `c.String(...)` in `handleTokenExchange` (core/sessions/oidcauth/oidc.go, around line 226-230), matching the pattern used by all other error branches in this function, so that email-extraction failure aborts the handler before role mapping, session insertion, audit logging, and cookie issuance occur.

### Proof of Concept
1. Configure (or compromise/misconfigure) the OIDC provider so its ID token/userinfo claims include the RBAC group claim(s) consumed by `ExtractIDClaimValues`/`IDClaimsToUserRole` but omit (or type-mismatch) the top-level `email` claim.
2. As an unauthenticated client, initiate `GET /sessions_oidc/signin` (or equivalent `handleSignIn` route) to start the flow, complete the provider login, and get redirected back with `code`/`state`.
3. Client calls the token exchange endpoint (`handleTokenExchange`) with the valid `code`/`state`.
4. `claims["email"].(string)` assertion fails (`ok == false`); the handler writes a 500 body but does not return.
5. Execution continues: `IDClaimsToUserRole` succeeds using the group claims, `INSERT INTO oidc_sessions (... user_email='' ...)` is executed, `AuthLoginSuccessNo2FA` is audited with `email: ""`, and `ginSession.Save()` sets a working session cookie; the handler ultimately writes `200 {"success": true}` after the earlier 500.
6. The returned session cookie is now valid and, per `AuthorizedUserWithSession`, authenticates all subsequent requests as a user with the mapped role and an empty email, confirming an authenticated session was established despite the intended failure path.

func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
