### Title
`claimInstantWithdrawRequest` pays aggregate cross-epoch instant receipts from funds reserved for earlier requesters — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The CVE's bug class is an out-of-bounds read: the parser reads data past the bounds of the record it was meant to consume. The analog in `IdleCreditVault` is a scope/confusion read: `claimInstantWithdrawRequest` pays the **aggregate** `instantWithdrawsRequests[_user]` balance out of the strategy's held underlying, without checking which epoch the receipts were created in or whether those receipts were ever funded by `collectInstantWithdrawFunds`. A request created in a later epoch reads (and drains) the funded balance that belongs to earlier-epoch receipts.

### Finding Description
Instant withdraws are funded through `collectInstantWithdrawFunds`, which pulls underlying from the CDO into the strategy and decrements `pendingInstantWithdraws` (`IdleCreditVault.sol:398-403`). Funds collected this way sit in the strategy to cover the receipts that were pending at that time.

However, `requestInstantWithdraw` (`IdleCreditVault.sol:356-375`) can be invoked for a new epoch while older funded receipts are still unclaimed: it simply increases `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`. When `claimInstantWithdrawRequest` runs (`IdleCreditVault.sol:380-393`), it reads `instantWithdrawsRequests[_user]` — the aggregate across all epochs — burns that full amount of receipt tokens, and calls `_transferFundedClaim(_user, amount)`, transferring underlying held by the strategy with no epoch-scoped funding check. The per-epoch accounting (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) is only consulted in the post-default path (`_claimDefaultedInstantWithdrawRequest`), not to gate funding eligibility of a normal claim.

So a user who submits an instant-withdraw request *after* funding arrived for earlier requesters can claim immediately, paying themselves out of underlying that was collected to back other users' receipts. This is exactly an out-of-bounds read analog: the claim reads outside the boundary (epoch/funding cohort) of the data that was actually funded.

### Impact Explanation
Direct theft: the attacker's new, unfunded instant receipt is paid at par from underlying reserved for earlier instant-withdraw requesters. Those earlier users' claims then fail (`_transferFundedClaim` will revert on insufficient balance) or are left permanently underfunded — a "one receipt one payout" invariant violation where the same funded liquidity is consumed twice.

### Likelihood Explanation
Requires an instant-withdraw funding event to leave unclaimed underlying in the strategy while new instant requests are still accepted by the CDO. The strategy itself enforces no epoch or funding gating on `claimInstantWithdrawRequest`, so the only protection is CDO-side sequencing of `requestInstantWithdraw` relative to `collectInstantWithdrawFunds`, which this analysis could not fully verify. If any window exists where new instant requests are accepted while funded claims remain unclaimed, an unprivileged tranche-token holder can execute the theft atomically (request, then claim).

### Recommendation
Track instant claims per epoch like the default path already does: gate `claimInstantWithdrawRequest` so a receipt is only payable from funds collected for its own `instantWithdrawsRequestsByEpoch` cohort (e.g., maintain a `fundedInstantByEpoch` watermark set in `collectInstantWithdrawFunds`), or have the CDO reject new `requestInstantWithdraw` calls while unfunded-but-collected reserves exist. Do not pay the aggregate `instantWithdrawsRequests` balance without verifying the claim's epoch was funded.

### Proof of Concept
Foundry fork sketch (fork mainnet at a block where an `IdleCreditVault` strategy with a live `IdleCDOEpochVariant` CDO exists):

```solidity
// Preconditions: epoch N running; userA has an unfunded instant request.
// 1. Epoch stops / next epoch starts; CDO calls
//    strategy.collectInstantWithdrawFunds(amountForA) — underlying for A's
//    receipt now sits in the strategy, A has not claimed yet.
// 2. Attacker (KYC'd tranche holder) calls CDO -> strategy.requestInstantWithdraw(x, attacker)
//    during the new epoch (epoch N+1).
// 3. Attacker calls CDO -> strategy.claimInstantWithdrawRequest(attacker).
//    Strategy reads instantWithdrawsRequests[attacker] == x, burns x receipts,
//    and transfers x underlying — sourced from A's funded reserve.
// 4. Assert: attacker underlying balance increased by x;
//    strategy underlying balance < sum of remaining funded instant receipts;
//    userA's subsequent claimInstantWithdrawRequest reverts or underpays.
```

Note: full verification of step 2 requires confirming the CDO does not gate `requestInstantWithdraw` against outstanding funded-but-unclaimed instant reserves; that gating logic in `IdleCDOEpochVariant.sol` could not be fully read within the tool budget. If such gating exists and is airtight, this finding reduces to a latent footgun rather than an active exploit.
