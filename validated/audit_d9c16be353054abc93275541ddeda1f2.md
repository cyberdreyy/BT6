### Title
`/v2/resume/:runID` Endpoint Bypasses All Node Authentication for Job Run Completion - ([File: core/web/router.go])

### Summary
The Solana report describes a structural bug class: a privileged state-changing operation (token exit) has two execution paths — one that enforces policy (normal transfer via the `TransferHook`) and one that bypasses it entirely (the bridge burn/remint path, which uses a different low-level mechanism that skips the hook). The chainlink node has a structurally analogous pattern in its HTTP API surface: the pipeline-run "resume" operation, which finalizes/completes a job run and can inject arbitrary task results, has a "normal" path guarded by session/token/external-initiator authentication and a second path that is deliberately placed in the unauthenticated route group and skips all `Authenticate`/role middleware.

### Finding Description
Job runs are normally resumed/completed only through routes protected by the `Authenticate` middleware chain, which requires a valid session cookie, API token, or external-initiator credential, e.g. the `userOrEI` group used for `/v2/jobs/:ID/runs`: [1](#0-0) .

However, `v2Routes` registers the resume endpoint directly on the unauthenticated group before any auth middleware is attached: [2](#0-1) 

This `PATCH /v2/resume/:runID` handler is `PipelineRunsController.Resume`, which accepts a `runID` (task UUID) and a JSON body describing the task result, then calls directly into `ResumeJobV2` to finish the task and resume the pipeline — with no session, API token, or external-initiator check performed anywhere in the handler: [3](#0-2) 

This mirrors the report's bug class exactly: the "normal" job-run-triggering path (`userOrEI` group, requiring `AuthenticateExternalInitiator`/`AuthenticateByToken`/`AuthenticateBySession` plus `RequiresRunRole`) enforces access control, but a second, functionally-equivalent path that mutates the same underlying resource (a pending pipeline run's result/value) is wired up without any authentication check. The audit event name `audit.UnauthedRunResumed` [4](#0-3)  confirms this is a known, deliberate design choice — the node relies solely on the unguessability of the `runID` UUID as the sole factor, rather than caller identity/role, exactly the kind of "intentional design property" callout the external report describes for Securitize's bridge burn path.

### Impact Explanation
Any unprivileged network client who obtains or guesses a pending run's `taskID` (e.g. via a leaked async bridge `responseURL`, log exposure, monitoring, or a race with an async bridge adapter) can call this unauthenticated endpoint to inject an arbitrary result/error value and force-resume the pipeline run — without needing any node credentials, session, or external-initiator secret. This is the same class of risk flagged in the source report: normal, credentialed paths enforce access control, but an operationally-equivalent bypass path lets an unauthenticated actor complete/mutate a privileged state transition (a job run whose result can feed into subsequent bridge/transmission tasks), undermining the same "who is authorized to affect this job run" assumption that the report's transfer-hook policy is meant to guarantee on the token side.

### Likelihood Explanation
Likelihood is bounded by the fact that `runID` is a random UUID that must be known to the attacker (it is not systematically leaked to arbitrary parties by design), and this endpoint is used intentionally as a webhook callback target for async bridge tasks: [5](#0-4) . Still, this is reachable by any unauthenticated network client with the correct URL, with zero cryptographic or role verification — a materially weaker bar than every other job-affecting endpoint in the router.

### Recommendation
If the current behavior is intended (as Securitize similarly deemed their bridge gap "intentional"), it should at minimum be documented as a security-relevant design decision, and the `runID` should be treated/generated as a bearer secret with sufficient entropy and never logged/echoed to third parties. If not intended to be a blanket-unauthenticated capability, add a scoped authentication method (e.g., a dedicated resume-token check bound to the specific pending run) before invoking `ResumeJobV2`, mirroring how the report recommends adding an explicit "validate bridge exit" policy check before allowing the bypassing action.

### Proof of Concept
1. Create/observe an async bridge or webhook job whose task emits a `responseURL` containing `/v2/resume/<taskID>` (as constructed in `finalizeAndMarshalBridgeRequestData`, `task.bridge.go:363-373`).
2. As an unauthenticated client (no session cookie, no `X-API-KEY`/`X-API-SECRET`, no `X-Chainlink-EA-*` headers), send:
   `PATCH /v2/resume/<taskID>` with body `{"error":"..."}` or `{"value":"..."}`.
3. The request hits the `unauthedv2` group directly (`core/web/router.go:243`), never passing through `auth.Authenticate`, and `PipelineRunsController.Resume` completes the pending run with attacker-supplied data.

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```
