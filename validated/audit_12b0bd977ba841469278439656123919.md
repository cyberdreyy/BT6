### Title
APR change while an APR0 withdraw bucket is open permanently reverts `stopEpoch`, freezing the epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` hard-reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged KYC-passed lender can open an APR0 withdraw request (which leaves `apr0TotalPrincipal > 0` until the next `stopEpoch`), after which any routine APR change by the honest manager (`setAprs`) makes every subsequent `stopEpoch` call revert. The epoch can never be stopped, `epochNumber` never advances, and all deposits and withdraw claims are frozen until the manager manually restores `unscaledApr == 0`. This mirrors CVE-2024-9369's bug class: insufficient validation of an input/state combination (an APR write concurrent with an open APR0 bucket) producing an out-of-bounds state write — here, a state transition that bricks the epoch state machine.

### Finding Description
- `requestWithdraw` in `IdleCreditVault` (contracts/strategies/idle/IdleCreditVault.sol:285-286) routes requests to `_requestWithdrawApr0` whenever `unscaledApr == 0`, incrementing the global `apr0TotalPrincipal` (line 576).
- `prepareStopEpochWithApr0` (line 490) is called unconditionally at the top of `IdleCDOEpochVariant._stopEpoch` (contracts/IdleCDOEpochVariant.sol:362), **before** the try/catch that handles borrower default, and reverts `NotAllowed` when `apr0TotalPrincipal != 0 && unscaledApr != 0` (lines 506-508).
- `setAprs`/`setApr` (lines 206-235) can be called by `manager` at any time with no check that an APR0 bucket is open, and `_setScaledApr` at the end of a successful `stopEpoch` also sets `unscaledApr` to the next epoch's APR. The new-APR write is not validated against the open APR0 bucket.
- Crucially, the revert is not wrapped by the borrower's try/catch in `_stopEpoch`, so the entire epoch-close path (interest accrual, `collectWithdrawFunds`, `epochNumber` bump, `allowAA/BBWithdrawRequest` re-enable) reverts atomically. All pending `claimWithdrawRequest` calls also stay blocked because `_settleApr0` requires `reqEpoch < epochNumber`, which can never increment while `stopEpoch` reverts.

### Impact Explanation
Temporary freezing of the entire vault TVL: while `unscaledApr != 0` and the APR0 bucket is open, `stopEpoch` can never execute, so the epoch cannot end, withdraw requests cannot be funded or claimed, and deposits remain gated. Loss is bounded to a freeze (no theft) and is recoverable only by the manager setting `unscaledApr` back to 0 via `setAprs`, but until that remediation the borrower keeps all principal and lenders have no exit. There is no on-chain guard preventing the state combination, and no alerting path — the freeze is discovered only when `stopEpoch` starts reverting.

### Likelihood Explanation
Requires (a) an epoch running under APR 0 (a supported mode per the APR0 tests), (b) any unprivileged lender opening a withdraw request during that epoch — a normal user action costing only gas, and (c) the manager setting a non-zero APR while the bucket is open, which is a routine operational action the code explicitly supports (`setAprs` is callable mid-epoch and is exercised in tests at test/foundry/IdleCreditVault.t.sol:2986). The attacker controls step (b) and can hold a dust-sized request open indefinitely; step (c) needs no attacker influence. Likelihood is moderate: it needs a specific operational sequence, but nothing in the contracts prevents it.

### Recommendation
Validate APR transitions against the open APR0 bucket at write time. Either revert `setAprs`/`setApr` when `apr0TotalPrincipal != 0` and the new `unscaledApr != 0` (forcing the bucket to settle at `stopEpoch` first), or — better — settle the bucket inside `prepareStopEpochWithApr0` when APR is non-zero by paying APR0 requesters principal only (rate 0) instead of reverting. This removes the state combination that makes the epoch state machine unclosable.

### Proof of Concept
Foundry fork test sketch (modeled on `testApr0WithdrawGetsInterestAtStopEpoch` in test/foundry/IdleCreditVault.t.sol:2979):

```solidity
function testAprChangeWhileApr0BucketOpenBricksStopEpoch() external {
    // Setup: deposit and start epoch with APR = 0 (APR0 mode)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _forceLastEpochAprToZero();

    // Attacker (any KYC'd lender) opens an APR0 withdraw request
    cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // Manager performs a routine mid-epoch APR update
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(5e17, 5e17);

    // Epoch can never be stopped: prepareStopEpochWithApr0 reverts
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest()
        + IdleCreditVault(address(strategy)).pendingWithdraws());
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Claims are also frozen: epochNumber cannot advance past the request epoch
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```
