### Title
Deterministic, unauthenticated lockup address lets anyone squat `victim.near`'s lockup, permanently blocking every future legitimate `create` for that owner - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the lockup sub-account solely from `sha256(owner_account_id)`, with no nonce, no privilege check, and no record of who "owns" that address. Anyone can call `create(owner_account_id="victim.near", ...)` first with parameters of their own choosing; every subsequent legitimate `create` call for `victim.near` will then have its `create_account()` fail (account already exists), routing through `on_lockup_create`'s failure branch, refunding the grantor but never delivering funds/lockup to `victim.near`.

### Finding Description
Broken binding: `NEAR delivered to the intended lockup for victim.near == NEAR the grantor attempted to lock`. After a squat, for every later legitimate grantor this becomes `0 == attached_deposit`, while the refund binding `attached_deposit + 0 delivered == env::attached_deposit()` still holds.

Root cause is in `LockupFactory::create`:
```
lockup-factory/src/lib.rs:119-121
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id =
    format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
``` [1](#0-0) 
This address is a pure function of `owner_account_id` - no caller identity, no salt, no on-chain record of prior attempts. `LockupFactory`'s persisted state contains only `whitelist_account_id` and `foundation_account_id`, so nothing tracks which addresses are already "claimed":
```

    whitelist_account_id: AccountId,
    foundation_account_id: AccountId,

``` [2](#0-1) 

Exploit flow:
1. Attacker (any unprivileged account) calls `create(owner_account_id="victim.near", lockup_duration=..., vesting_schedule=None or attacker-chosen, ...)` with `MIN_ATTACHED_BALANCE`. `Promise::new(lockup_account_id).create_account().deploy_contract(CODE).transfer(...).function_call("new", ...)` succeeds and deploys a lockup at the deterministic address, `on_lockup_create` sees `is_promise_success() == true` and returns `true` - no refund, contract now permanently occupies that account with the attacker's chosen parameters.
2. Any subsequent legitimate grantor calls `create(owner_account_id="victim.near", ...)` with correct parameters and deposit. The `Promise::new(lockup_account_id).create_account()` step now fails at the protocol level because the account already exists, so the whole promise chain up to `function_call` fails.
3. `on_lockup_create` is invoked with `PromiseResult::Failed`; `is_promise_success()` returns `false`, hitting:
```
lockup-factory/src/lib.rs:187-197
} else {
    env::log(...);
    Promise::new(predecessor_account_id).transfer(attached_deposit.0);
    false
}
``` [3](#0-2) 
The grantor's deposit is refunded (settlement holds), but `victim.near` never receives any lockup with correct parameters - the AUTHORISATION guarantee ("the intended lockup gets created for the intended owner") is permanently broken as long as the squatted contract lives at that address, since the address can never change.

None of the existing guards prevent this: `assert_self()` only checks the callback is self-invoked, `is_promise_success()` only detects success/failure of the already-executed (and now permanently blocked) creation attempt; there is no `assert_owner`, whitelist check, or uniqueness reservation on `owner_account_id` before the sub-account is created.

### Impact Explanation
This matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose" - the attacker's first squatting call deploys a lockup for `victim.near` with parameters the attacker picked (duration, vesting, whitelist), and additionally causes every subsequent NEAR Foundation/grantor attempt to create the *correct* lockup for `victim.near` to permanently fail with only a refund, i.e., funds intended for `victim.near` never arrive and can never arrive at the canonical lockup address (frozen/undeliverable permanently, not just for one epoch). This is repeatable for any target account name and costs the attacker only `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squat, which they can even reclaim indirectly since they control the squatted contract.

### Likelihood Explanation
No privileged role, key, or foundation cooperation is required. The attacker only needs to know `victim.near`'s account id (public), compute `sha256`, and call the public, payable `create` method with `MIN_ATTACHED_BALANCE` before anyone else does for that owner. This is fully feasible pre-emptively for any account whose lockup hasn't yet been created, and is repeatable across every distinct `owner_account_id`.

### Recommendation
Bind lockup creation to an authorized caller/process rather than a purely name-derived deterministic address with no reservation: e.g., require `predecessor_account_id == owner_account_id` or `predecessor_account_id == foundation_account_id`/an allow-listed grantor set before allowing `create` for a given `owner_account_id`, and/or maintain a persisted set of already-created (or reserved) `owner_account_id`s in `LockupFactory` state so a second `create` for the same owner is rejected up-front with a clear error rather than silently allowing squatting followed by silent failure.

### Proof of Concept
```rust
#[test]
fn test_squatted_owner_blocks_legitimate_create() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    let lockup_duration: WrappedTimestamp = 63036000000000000u64.into();

    // Attacker squats victim's lockup address first, with attacker-chosen params.
    context.predecessor_account_id = String::from("attacker");
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner() /* "victim.near" */, lockup_duration, None, None, None, None);

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let squat_result = contract.on_lockup_create(
        lockup_account(), // deterministic address for victim.near
        ntoy(35).into(),
        String::from("attacker"),
    );
    assert_eq!(squat_result, true); // squatted lockup now "owns" the address

    // Legitimate grantor now tries to create the correct lockup for the same owner.
    context.predecessor_account_id = String::from("legit_grantor");
    context.attached_deposit = ntoy(40);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // create_account() fails because address already exists -> Failed promise result.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(40).into(),
        String::from("legit_grantor"),
    );

    // Settlement holds: refund equals attached deposit, so no NEAR is stolen.
    assert_eq!(res, false);
    // Authorisation breaks: no lockup state was created/updated for victim.near
    // with legit_grantor's parameters; the address is permanently occupied by
    // the attacker's squat contract deployed in the first call.
}
```
