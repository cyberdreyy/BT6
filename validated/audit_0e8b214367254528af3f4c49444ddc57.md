### Title
JWT replay guard has a TOCTOU race allowing a single-use JWT to authorize two concurrent requests - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` calls `jwtCache.isReplay(claims.ID)` and, only after further processing, calls `jwtCache.recordUsage(claims.ID)`, with the read and write protected by separate lock acquisitions (`RLock`/`RUnlock` then a later, independent `Lock`/`Unlock`). Two concurrent `Authorize` calls carrying the same JWT (`jti`) can both pass `isReplay` before either calls `recordUsage`, allowing the same JWT to authorize two requests despite the code's explicit "each JWT used once" guarantee.

### Finding Description
`Authorize` (workflow_metadata_handler.go:80-108) performs:
1. `claims, signer, err := utils.VerifyRequestJWT(token, *req)` — validates JWT signature/claims.
2. `h.jwtCache.isReplay(claims.ID)` — takes `cache.mu.RLock()`, checks map membership, and releases the lock (workflow_metadata_handler.go:399-405).
3. Authorized-key lookup logic (lines 92-104).
4. `h.jwtCache.recordUsage(claims.ID)` — takes a brand-new `cache.mu.Lock()` and inserts the entry (workflow_metadata_handler.go:407-412).

Because the read lock is released between steps 2 and 4, there is no atomicity across the check-then-act sequence. If two goroutines call `Authorize` with the same `token`/`claims.ID` concurrently:
- Goroutine A calls `isReplay(jti)` → false (not yet in cache), lock released.
- Goroutine B calls `isReplay(jti)` → false (A hasn't called `recordUsage` yet), lock released.
- Both proceed through the authorized-key check (idempotent, no interlock there either) and both call `recordUsage(jti)`, which simply overwrites the same map entry.
- Both calls to `Authorize` return `(&key, nil)` — i.e., both requests are authorized using the same JWT.

The replay cache's purpose (per its own comment, "manages used JWT IDs to prevent replay attacks") is defeated for the concurrent case. This is a genuine "check-then-act" race: `isReplay` and `recordUsage` operate on the same map but are not combined into a single atomic operation (e.g., a `Get-or-set` under one lock, or a `LoadOrStore`).

### Impact Explanation
This breaks the single-use invariant on JWTs used to authorize workflow-trigger capability requests via the gateway. An attacker (or automated retry client) holding one valid JWT can fire two (or more) concurrent requests and have all of them accepted as authorized, provided they win the race window between `isReplay` and `recordUsage`. This maps to a "quota bypass / duplicate capability execution" class of impact — the same signed authorization is consumed more than once, potentially triggering duplicate workflow executions or duplicate consumption of victim-owned resources tied to that single JWT, when the system's design explicitly intends exactly-once semantics per `jti`.

The severity is bounded: this does not grant new authorization capabilities beyond what a single valid JWT would already grant once (no privilege escalation, no key/secret disclosure, no bypass of signature verification or authorized-key membership check) — it only allows the same already-valid authorization to be exercised twice instead of once.

### Likelihood Explanation
Exploitation requires only possession of one valid, unexpired, correctly signed JWT (already assumed available to the token holder per problem statement) and the ability to send two requests concurrently, which any client can trivially do. No special role or privilege is needed beyond holding the JWT that would normally be presented once. The race window (time between `isReplay`'s `RUnlock` and `recordUsage`'s `Lock` while authorized-key lookups run) is narrow but real, non-zero, and reliably reproducible under controlled concurrency (as in a Go test forcing the race with synchronization barriers), and could be widened in practice by network jitter or scheduling delays between two near-simultaneous requests to the gateway.

### Recommendation
Make the replay-check-and-record operation atomic: acquire `cache.mu.Lock()` once, check for existence, and if absent, insert immediately, all under the same critical section (equivalent to a `sync.Map`-style `LoadOrStore` or a single locked "check-and-set" method), e.g.:
```go
func (cache *jwtReplayCache) checkAndRecord(jti string) bool { // returns true if already used
    cache.mu.Lock()
    defer cache.mu.Unlock()
    if _, exists := cache.cache[jti]; exists {
        return true
    }
    cache.cache[jti] = time.Now()
    return false
}
```
Then call this single method in `Authorize` immediately after JWT verification, before doing the authorized-key check, so replayed/concurrent requests are rejected atomically and as early as possible.

### Proof of Concept
Go test plan (to be added to `workflow_metadata_handler_test.go`):
1. Construct a `WorkflowMetadataHandler` with a valid workflow ID registered in `authorizedKeys`, and a valid signed JWT with a fixed `claims.ID` (`jti`) whose signer matches an authorized key.
2. Use two goroutines with a `sync.WaitGroup` and a barrier (e.g., a channel closed to release both goroutines simultaneously, or `sync.WaitGroup`/`chan struct{}` gating) so both goroutines call `h.Authorize(workflowID, token, req)` as close to simultaneously as possible with the identical token.
3. Insert an artificial delay (e.g., via a hook or by wrapping `isReplay`/authorized-key lookup with a small `time.Sleep`) between `isReplay` and `recordUsage` to reliably force the race window in a test environment, or run the concurrent calls thousands of times in a loop (`-race` enabled) to catch the race statistically.
4. Collect both results; assert that in a correct implementation exactly one call returns `(*gateway.AuthorizedKey, nil)` and the other returns the "JWT token has already been used" error. Currently (bug present) both calls succeed with `nil` error, demonstrating the double-authorization.
5. Optionally run with `go test -race` to confirm there's no data race on the map itself (locks do prevent that), while still asserting the logical double-authorization bug via the assertion in step 4.
