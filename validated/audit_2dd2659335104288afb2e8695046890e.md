### Title
Cache-key-controlled `-protected` volume naming lets an unprotected-branch job collide with / poison a protected-branch cache volume - ([File: executors/docker/volume.go], [File: executors/docker/internal/volumes/manager.go])

### Summary
`config.Protected` for the Docker volume manager is not derived solely from GitLab-verified `GitInfo`/`e.Build.IsProtected()`; it is OR'd with an attacker-controllable condition based on the job's `.gitlab-ci.yml` cache `Key` text ending in `-protected`. Because the resulting volume name and the emitted `protected` label are both driven by this OR'd, job-supplied value, an unprivileged job on an unprotected ref can force its cache volume to be created with the same suffix and same `protected=true` label as a genuinely protected-branch cache volume for the same project/cache path.

### Finding Description
In `executors/docker/volume.go` (`createVolumesManager`): [1](#0-0) 

`e.Build.Cache` entries and their `Key` field come straight from `.gitlab-ci.yml`, fully controlled by the pipeline author. `protectedKeyIdx` is set whenever any cache key ends in `-protected` (and doesn't end in `-non_protected`), and `config.Protected` becomes `e.Build.IsProtected() || protectedKeyIdx >= 0` — i.e., true if the ref is protected **or** if the job author simply names a cache key ending in `-protected`, regardless of actual branch protection.

This `config.Protected` flows into `manager.createCacheVolume`/`withProtected` in `executors/docker/internal/volumes/manager.go`: [2](#0-1) [3](#0-2) 

The volume name (`<UniqueName>-cache-<hash(destination)>[-protected]`) depends on `UniqueName` (`e.Build.ProjectRealUniqueName()`, project-scoped, not branch-scoped) and `hashedDestination` (derived from the cache mount **destination path** declared in `.gitlab-ci.yml`, not the cache `Key`). Since neither of these two components is influenced by branch protection, the only thing that differentiates a protected-branch cache volume from an unprotected one for the same project and same cache destination path is the `-protected` suffix — which is exactly the value an attacker can now force via cache-key naming. If an unprotected-branch job declares a cache with `Key: "x-protected"` and `Paths` matching the same destination used by a legitimate protected-branch cache entry, `createCacheVolume` computes the identical `volumeName` and identical `"protected": "true"` label as the genuine protected-branch volume, causing Docker's `VolumeCreate` to resolve to (or the runner to treat as) the same existing volume rather than isolating it — the attacker's build then mounts and can read/poison that shared volume.

There is no check anywhere that ties the emitted `protected` label or volume name back to the verified `GitInfo.Protected` alone; the label literally reports `m.config.Protected` (the OR'd, spoofable value), so downstream consumers of this label (and the volume-name-based isolation itself) can be fooled into believing an unprotected job's cache is "protected" and, more importantly, get funneled into reusing the real protected volume.

### Impact Explanation
An unprivileged pipeline author on an unprotected branch can, without any special privilege, cause their job's cache volume to collide with (reuse) a protected-branch project's cache volume for a shared cache path, or fabricate a volume that is falsely labeled `protected=true`. This breaks the protected/unprotected cache storage segregation invariant and allows reading or poisoning protected-branch cache contents, subsequently affecting privileged CI jobs that consume that cache.

### Likelihood Explanation
Fully feasible with only pipeline-config access (`.gitlab-ci.yml` edit rights on an unprotected branch, e.g., an MR from a fork/feature branch) — no admin or infrastructure compromise needed. It requires the attacker to know (or guess/enumerate) the cache destination path used by the protected branch's job, which is commonly a well-known path (e.g., `node_modules/`, `.cache/`, `vendor/`) and often visible in the shared `.gitlab-ci.yml` itself. This makes the attack straightforward and repeatable on any runner using the docker executor with named (non-host-based) cache volumes.

### Recommendation
Do not let job-supplied cache key text influence `ManagerConfig.Protected` or the volume-naming/label decision at all. Base `config.Protected` solely on the GitLab-verified `e.Build.JobInfo`/`GitInfo.Protected` (i.e., `e.Build.IsProtected()`), removing the `protectedKeyIdx` OR-condition in `executors/docker/volume.go`. If a "protected cache key" convention must be supported, validate it against a GitLab-provided/verified indicator rather than trusting the literal string suffix supplied by the job author.

### Proof of Concept
Go unit test extension in `executors/docker/internal/volumes/manager_test.go`, and an integration scenario:

1. Unit test: Build two `ManagerConfig`s with identical `UniqueName` and identical cache destination path, one with `Protected: true` (simulating real protected ref) and one with `Protected: true` achieved only via `protectedKeyIdx >= 0` logic replicated from `volume.go` (simulating attacker on unprotected ref). Call `createCacheVolume` for both and assert:
   - `volumeName` for the "attacker" config equals `volumeName` for the "real protected" config (proving collision), even though `e.Build.IsProtected()` would be `false` for the attacker's build.
2. Integration-style PoC job plan:
   - Job A (on protected branch): `cache: {key: shared-cache, paths: [.cache/]}` — creates volume `X-cache-<hash>-protected` with label `protected=true`.
   - Job B (on unprotected feature branch, same project): `cache: {key: shared-cache-protected, paths: [.cache/]}` — assert that the computed `volumeName` and Docker volume label match Job A's exactly, and that Job B's container mounts/can write into the same Docker volume that Job A used, despite Job B running on an unprotected ref.
