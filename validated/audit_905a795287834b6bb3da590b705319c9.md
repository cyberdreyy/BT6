### Title
Blacklisted withdrawers permanently lose funded claims because payouts are bound to the receipt owner - ([File: contracts/strategies/idle/IdleCreditVault.sol, contracts/IdleCDOEpochQueue.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Identical bug class to the Teller report: payouts are sent to a hardcoded recipient (the receipt owner) with no way to specify an alternate receiver. If the vault underlying is a blacklistable token (USDC/USDT — the standard underlying for these credit vaults) and the user address is blacklisted after requesting a withdrawal, the funded claim can never be paid out. The situation is worse than the original report because strategy-token receipts are deliberately non-transferable (`_transfer` reverts for anyone except the IdleCDO and `setCanTransfer` can only ever set `false`), so the user cannot even move the claim to a clean address. The same hardcoded-`msg.sender` pattern exists in `IdleCDOEpochQueue.claimWithdrawRequest` / `claimDepositRequest` for queued (epoch-based) withdrawers.

### Finding Description
All user-facing payout paths send underlying to a fixed address:

- `IdleCreditVault._claimFundedWithdrawRequest` ends with `_transferFundedClaim(_user, amount)` (`contracts/strategies/idle/IdleCreditVault.sol:349`), which does `underlyingToken.safeTransfer(_user, _amount)` (`contracts/strategies/idle/IdleCreditVault.sol:906`).
- `claimInstantWithdrawRequest` also pays via `_transferFundedClaim(_user, amount)` (`contracts/strategies/idle/IdleCreditVault.sol:392`).
- Default-recovery payouts go through `_transferDefaultRecovery(_user, ...)` → `underlyingToken.safeTransfer(_user, _amount)` (`contracts/strategies/idle/IdleCreditVault.sol:912-916`), used by `_claimDefaultedInstantWithdrawRequest`, `_claimDefaultedWithdrawRequest` and post-default claims.
- `claimWithdrawRequest(_user)`/`claimInstantWithdrawRequest(_user)` take a `_user` parameter, but it is caller-supplied by the IdleCDO/strategy plumbing and the receipt accounting is bound to that address — there is no recipient override.

The escape hatch that would normally save a blacklisted user — transferring the claim token — is explicitly disabled:

- `IdleCreditVault._transfer` reverts with `NotAllowed` for any caller other than `idleCDO` (`contracts/strategies/idle/IdleCreditVault.sol:939-941`).
- `setCanTransfer` only permits setting `canTransfer = false`; the comment states receipt claims are "address-bound" and enabling transfers is "permanently disabled" (`contracts/strategies/idle/IdleCreditVault.sol:948-951`).

In the queue variant the same applies: `IdleCDOEpochQueue.claimWithdrawRequest` zeroes `userWithdrawalsEpochs[msg.sender][_epoch]` and then `safeTransfer`s to `msg.sender` (`contracts/IdleCDOEpochQueue.sol:401-410`); `claimDepositRequest` sends tranche tokens to `msg.sender` (`contracts/IdleCDOEpochQueue.sol:388`). Note the request bookkeeping is cleared *before* the transfer, so a reverting (blacklisted) transfer leaves the receipt cleared in state yet permanently unclaimable in practice.

`DefaultDistributor.claim` is the one place that got this right — it accepts a `_to` recipient (`contracts/DefaultDistributor.sol:35-41`) — which shows the protocol is aware of the need for a recipient parameter but the withdraw/recovery paths lack it.

### Impact Explanation
For a vault whose underlying is a blacklistable stablecoin (e.g. USDC, the canonical underlying for `IdleCreditVault`), a user blacklisted after their withdraw request is funded loses the full claim amount permanently: every claim call reverts at the `safeTransfer`, and the non-transferable receipt means no other address can claim on their behalf. Same for default-recovery distributions paid through `_transferDefaultRecovery` and for queue-based withdrawers/depositors whose claims are keyed to `msg.sender`. Funds remain locked in `IdleCreditVault`/the queue forever (only rescuable by privileged `transferToken`-style emergency functions, which is an owner action, not user-accessible). Impact = permanent freezing of otherwise withdrawable funds; matches the "permanent freezing" acceptance criterion.

### Likelihood Explanation
Low-to-medium: it requires (a) the vault underlying to be a centrally-blacklistable token — true for USDC/USDT vaults, which are the primary deployments — and (b) the specific user to be blacklisted by the token issuer while holding a pending/funded receipt. This is exactly the Medium-severity rating given in the source report; no attacker action is needed beyond the environmental blacklist event, which is outside the unprivileged-attacker constraint anyway (the "attacker" framing is moot — the victim is a normal lender).

### Recommendation
Add an optional recipient parameter to the claim functions (e.g. `claimWithdrawRequest(address _user, address _to)`, `queue.claimWithdrawRequest(uint256 _epoch, address _to)`), defaulting to `_user`/`msg.sender`. Keep the receipt burn/zeroing keyed to `_user` but transfer underlying to `_to`, mirroring the existing `DefaultDistributor.claim(address _to)` design.

### Proof of Concept
```solidity
// SPDX-License-Identifier: Apache 2.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "contracts/strategies/idle/IdleCreditVault.sol";
import {MockBlacklistToken} from "./mocks/MockBlacklistToken.sol"; // USDC-like: reverts transfer to blacklisted

contract BlacklistClaimFreezePoC is Test {
    // Assume standard fixtures: vault with `underlying` = blacklistable mock,
    // `cdo` = whitelisted IdleCDOEpochVariant, alice = KYC'd lender.

    function test_BlacklistedUserClaimFrozen() public {
        // --- Epoch N: running ---
        // alice deposits via CDO and requests withdraw of 100e6 underlying
        requestWithdrawThroughCDO(alice, 100e6);

        // --- stopEpoch funds the receipt ---
        // borrower repays; collectWithdrawFunds pulls 100e6 into the vault
        stopEpochAndFundWithdraws(100e6);

        // --- token issuer blacklists alice (external event) ---
        MockBlacklistToken(underlying).blacklist(alice);

        // --- alice tries to claim: funded claim path ---
        // IdleCDO -> vault.claimWithdrawRequest(alice)
        // -> _claimFundedWithdrawRequest -> _transferFundedClaim
        // -> underlyingToken.safeTransfer(alice, 100e6) REVERTS
        vm.startPrank(address(cdo));
        vm.expectRevert(); // "Blacklisted" / SafeERC20 revert
        vault.claimWithdrawRequest(alice);

        // --- alice cannot transfer the receipt either ---
        // strategy-token transfers are permanently disabled
        vm.stopPrank();
        vm.prank(alice);
        vm.expectRevert(IdleCreditVault.NotAllowed.selector);
        vault.transfer(bob, vault.balanceOf(alice)); // reverts: _transfer guard

        // --- instant-withdraw and default-recovery paths are equally frozen ---
        // claimInstantWithdrawRequest -> _transferFundedClaim(alice, ...) reverts
        // _transferDefaultRecovery(alice, ...) reverts the same way

        // Result: 100e6 of funded underlying is permanently locked in the vault;
        // alice's receipt accounting remains but can never be paid out to any address.
        assertEq(MockBlacklistToken(underlying).balanceOf(alice), 0);
    }
}
```
