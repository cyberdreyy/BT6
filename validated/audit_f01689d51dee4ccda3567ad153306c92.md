This codebase is a fixed-timelock atomic-swap escrow system, not a variable-rate lending protocol. The reported bug is about an inverted/misconfigured threshold comparison in Aave's fixed-rate loan rebalancing logic (`LendingPool.sol` rebalance boundary check), a mechanism that has no structural counterpart here. There is no "rebalance," "rate," or comparable configurable-boundary-that-gets-inverted concept anywhere in this repo — timelocks are fixed `uint32` offsets baked into `Immutables.timelocks` at deployment and checked via strict `onlyAfter`/`onlyBefore` modifiers in `EscrowSrc.sol` and `EscrowDst.sol` [1](#0-0) , computed by simple offset addition in `TimelocksLib.get` [2](#0-1) , with no analogous "acceptable range" recomputation or rebalance-triggering entry point that an unprivileged actor could call repeatedly to exploit an inverted threshold. Fee/rate-bump arithmetic (`FeeCalcLib.getFeeAmounts`, auction rate bump in `EscrowFactory.t.sol`) is a one-way deterministic calculation performed once at order fill, not a periodically-rechecked boundary subject to being permanently outside its intended safe zone [3](#0-2) .

No matches for "rebalance" exist in the repository, and no other threshold-comparison logic resembles the reported bug class under the required unprivileged-user attacker model and bounty scope.

    function getFeeAmounts(
        uint256 amount,
        uint256 protocolFee,
        uint256 integratorFee,
        uint256 integratorShare
    ) internal pure returns (uint256 integratorFeeAmount, uint256 protocolFeeAmount) {
        uint256 denominator = _BASE_1E5 + integratorFee + protocolFee;
        uint256 integratorFeeTotal = amount.mulDiv(integratorFee, denominator);
        integratorFeeAmount = integratorFeeTotal.mulDiv(integratorShare, _BASE_1E2);
        protocolFeeAmount = amount.mulDiv(protocolFee, denominator) + integratorFeeTotal - integratorFeeAmount;
    }
