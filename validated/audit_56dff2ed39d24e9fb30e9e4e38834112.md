### Title
Multisig Factory `create()` Has No Failure Callback — Attached Deposit Is Lost If Account Creation Fails - ([File: multisig-factory/src/lib.rs])

### Summary
`MultisigFactory::create()` issues a single batched promise (`create_account` → `deploy_contract` → `transfer` → `function_call`) to a derived multisig account, but unlike the sibling factories in this same codebase (`lockup-factory`, `staking-pool-factory`), it attaches **no callback** to check whether the promise succeeded. If the batched receipt fails — e.g. the derived `account_id` already exists, or is otherwise invalid — the entire batch (including the `transfer` of `env::attached_deposit()`) fails, and the caller's attached NEAR is never returned to them, nor is any multisig contract created.

### Finding Description
`MultisigFactory::create()` at [1](#0-0)  builds the account id as `format!("{}.{}", name, env::current_account_id())` and sends a single promise batch containing `create_account()`, `deploy_contract()`, `transfer(env::attached_deposit())`, and `function_call("new", ...)` — with no uniqueness check on `account_id` and no `.then(...)` callback to itself.

Compare this to the two other factories in the same repository that create sub-accounts and transfer deposits to them:
- `lockup-factory` explicitly checks the promise result in `on_lockup_create` and refunds `predecessor_account_id` if creation failed: [2](#0-1) .
- `staking-pool-factory` does the same, additionally guarding against duplicate IDs before sending the promise and rolling back the reservation on failure: [3](#0-2) .

`multisig-factory` has neither the duplicate-name guard nor the `is_promise_success()` callback/refund logic: [4](#0-3) . When the underlying batched receipt fails (e.g., because `name.multisig-factory-account` already exists, so `create_account` fails), NEAR's runtime refunds the unused/failed receipt balance to the **signer of that receipt**, which is the factory contract itself (`env::current_account_id()`), not the original transaction's predecessor who attached the deposit. The user's attached deposit is debited from their transaction but never delivered to a working multisig, and there is no code path in the factory that returns it to them — breaking the binding between "value debited from the caller" and "value delivered/refunded."

This is the same class of defect flagged in the external report: an operation that can fail during account creation, where the calling contract's accounting/refund logic does not correctly account for that failure mode, letting funds become effectively unrecoverable by the rightful party.

### Impact Explanation
Funds attached by a legitimate user to create a multisig are permanently stuck in the factory contract's balance with no method exposed to reclaim or redistribute them to the affected caller, matching "funds permanently frozen" for the specific user's deposit.

### Likelihood Explanation
Any caller who picks a `name` that collides with an existing multisig sub-account (or otherwise causes `create_account` to fail) will trigger this loss unintentionally — no attacker action or privileged party is required, only an ordinary `create()` call with a colliding/invalid name.

### Recommendation
Add a callback (`on_multisig_create`, mirroring `on_lockup_create` / `on_staking_pool_create`) to `multisig-factory/src/lib.rs` that checks `is_promise_success()` and calls `Promise::new(predecessor_account_id).transfer(attached_deposit)` when the creation receipt fails, and add an account-existence/uniqueness check before issuing the creation promise, consistent with the other factories in this repository.

### Proof of Concept
1. Call `multisig-factory.create({ name: "alice", members: [...], num_confirmations: 1 })` with attached deposit `D`, successfully creating `alice.multisig-factory`.
2. Call `multisig-factory.create({ name: "alice", members: [...], num_confirmations: 1 })` again with a new attached deposit `D2` from a different (or same) predecessor.
3. The batched receipt's `create_account()` action fails because `alice.multisig-factory` already exists; the whole batch (including `transfer(D2)`) fails.
4. `D2` is refunded to the factory contract's own balance (the receipt signer), not to the calling account; `multisig-factory` exposes no function to return `D2` to the caller — the deposit is lost to the caller.

const CODE: &[u8] = include_bytes!("../../multisig2/res/multisig2.wasm");

/// This gas spent on the call & account creation, the rest goes to the `new` call.
const CREATE_CALL_GAS: u64 = 50_000_000_000_000;

#[derive(Serialize, Deserialize)]
#[serde(crate = "near_sdk::serde", untagged)]
pub enum MultisigMember {
    AccessKey { public_key: Base58PublicKey },
    Account { account_id: AccountId },
}

#[near_bindgen]
#[derive(BorshSerialize, BorshDeserialize, Default)]
pub struct MultisigFactory {}

#[near_bindgen]
impl MultisigFactory {
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
}

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
