### Title
Write-off requests created during a running epoch can be fulfilled after the epoch ends at a stale price - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` enforces that the escrow is opened only while `isEpochRunning()` is true, mirroring the "schedule action only before its execution window" intent of the Delay app. However, `fullfillWriteOffRequest` — the counterpart that settles the deal — performs no epoch-state or deadline check at all. A fulfiller can therefore settle a request long after the epoch in which it was priced has ended, buying the escrowed tranche tokens at a price negotiated under stale `virtualPrice` conditions. This is the same bug class as the Delay app finding: a terminal action (`pauseExecution` / `fullfillWriteOffRequest`) remains callable after the execution window implied by the setup action has already elapsed.

### Finding Description
`createWriteOffRequest` gates on epoch state and snapshots the economics of the deal at creation time: the lender escrows `tranches` and names `underlyingsRequested`, implicitly priced against the tranche value while the epoch is locked (`IdleCreditVaultWriteOffEscrow.sol:86-102`). `fullfillWriteOffRequest` only verifies the request exists and that `_tranches`/`_underlyings` match (`IdleCreditVaultWriteOffEscrow.sol:123-131`), then transfers underlyings to the lender and tranche tokens to the fulfiller (`IdleCreditVaultWriteOffEscrow.sol:139-151`). It is permissionless ("this function can be called by any wallet") and never checks `isEpochRunning()`, `defaulted`, or `epochEndDate`.

Meanwhile tranche `virtualPrice` is not static: each `stopEpoch`/`stopEpochWithDuration` that repays interest increases `virtualPrice` (`IdleCDOEpochVariant.sol:331-390` flow mints strategy tokens to the CDO), and a loss event via `_updateAccounting`/`updateAccounting` decreases it following the BB-first waterfall. A write-off request priced at time T against a lower AA `virtualPrice` can be fulfilled at time T+k after one or more profitable `stopEpoch` calls — the fulfiller acquires tranche tokens redeemable for strictly more underlying than the `underlyingsRequested` the lender fixed at creation.

Concretely: lender escrows 10,000 AA tranches asking 10,000 USDC (price ≈ 1.0). Epoch stops with +2% interest → AA `virtualPrice` ≈ 1.02. Fulfiller (any EOA, not the borrower) calls `fullfillWriteOffRequest(lender, 10_000e18, 10_000e6)`, pays 10,000 USDC, receives tranches worth ~10,200 USDC of claim. The ~200 USDC delta is value extracted from the lender, who signed up for a mark-to-epoch price. The same gap applies in the loss direction: a fulfiller can dump fulfillment onto a lender after `updateAccounting` crystallizes a loss only if the price moved against the fulfiller it simply doesn't fill — the asymmetry (fill option with no expiry) is itself the flaw.

### Impact Explanation
Permanent loss for the lender equal to `(virtualPrice_at_fulfillment − virtualPrice_at_pricing) × tranches`, uncapped. It also enables theft-adjacent griefing after pool default/close: once `defaulted` is true or `epochDuration == 0` (closed pool, `IdleCDOEpochVariant.sol:222-224`), write-off requests should arguably be void, yet they remain fulfillable forever at whatever post-default `defaultRecoveryPrice`-like value the tranches carry, with the lender still bound to the stale `underlyingsRequested`.

### Likelihood Explanation
Requires a lender to leave a request open across an epoch boundary and a fulfiller willing to settle; both are unprivileged roles explicitly in scope (write-off fulfiller and tranche-token holder). The window is long: `epochDuration` is typically 30 days plus a `bufferPeriod`, and requests persist indefinitely until `deleteWriteOffRequest`. `deleteWriteOffRequest` exists but is opt-in — a lender that is inactive or expects the request to lapse with the epoch has no protection. No existing guard (skim, default revert, `only-CDO`, KYC on the fulfiller side — fulfillment is open to "any wallet") blocks settlement after the epoch stops.

### Recommendation
Add an epoch-validity check to `fullfillWriteOffRequest`, e.g. require `IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()` (the same condition under which the request was created), or record the epoch number/`epochEndDate` at creation and revert fulfillment once `block.timestamp > epochEndDate` or the epoch has rolled over. Alternatively let the fulfiller pass the expected max-price/min-tranches so stale fills revert on price drift.

### Proof of Concept
A Foundry fork test would: deposit AA so `virtualPrice(AA) == 1.0`; `startEpoch`; lender calls `createWriteOffRequest(amount, amountUSDC)`; warp past `epochEndDate`; fund borrower and `stopEpoch` with positive APR so `virtualPrice(AA)` rises; then `fullfillWriteOffRequest(lender, tranches, underlyings)` from a third-party fulfiller succeeds (it should revert). Assert `tranche.balanceOf(fulfiller)` corresponds to a claim worth more underlying than `underlyings` paid, quantifying the lender's loss as `tranches × (newVirtualPrice − oldVirtualPrice) / 1e18`.
