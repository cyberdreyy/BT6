### Title
Permissionless `juplend_init_position` allows front-running/griefing of one-time bank activation - (File: `programs/marginfi/src/instructions/juplend/init_position.rs`)

### Summary
`lending_pool_add_bank_juplend` (admin-only) creates a JupLend-wrapped bank in the `Uninitialized`/`Paused` state, deferring activation to a separate, permissionless, one-time instruction, `juplend_init_position`, which performs a seed deposit and flips the bank to `Operational`. [1](#0-0)  Because this activation step is permissionless and gated only by `operational_state == Uninitialized`, anyone can call it ahead of the admin's intended finalization transaction, analogous to the reported issue where `UniswapV3Pool.initialize()` could be called before the intended launch-finalization step.

### Finding Description
`juplend_init_position` is explicitly documented and implemented as callable by anyone ("permissionless, one-time per bank"), and simply requires the caller to supply a minimum seed amount (≥10 native units) from their own token account: [2](#0-1)  The account constraints only validate `operational_state == Uninitialized` before allowing activation, with no signer/authority restriction tying the caller to the group admin: [3](#0-2)  The `lib.rs` entrypoint comment confirms the instruction is permissionless: [4](#0-3) 

This mirrors the reported bug class: a step meant to be the final part of a controlled launch/setup sequence (pool `initialize()` in the Trugly report; bank activation via seed deposit here) is exposed as an unprivileged, front-runnable call. An attacker monitoring the mempool for the admin's `lending_pool_add_bank_juplend` transaction can immediately submit their own `juplend_init_position` with the bare minimum amount (10 units) before the admin's own activation transaction lands.

### Impact Explanation
If the admin's own setup script bundles `add_bank` + `juplend_init_position` (potentially with a larger, intentional seed amount) as sequential transactions, an attacker's front-run causes the admin's own `juplend_init_position` call to fail with `JuplendBankAlreadyActivated` (confirmed by the constraint check and the regression test asserting this error) [5](#0-4) , forcing the admin to detect and skip that step. This is a denial-of-service against the intended finalization flow: the admin loses control over exactly when/how/with what seed amount the bank is activated, and the bank becomes operational with attacker-chosen (minimal) parameters instead of the admin's intended ones. I was not able to fully verify in this session whether the size of the seed deposit affects fToken/share exchange-rate precision enough to enable a first-depositor/inflation-style value-redirection attack (this would require reviewing `programs/marginfi/src/instructions/juplend/deposit.rs` and `programs/marginfi/src/state/price.rs`, which I could not complete due to tool errors in the final iteration).

### Likelihood Explanation
Moderate. This requires an attacker to monitor for `lending_pool_add_bank_juplend` transactions and race a `juplend_init_position` transaction against the admin's own intended activation transaction, which is a low-cost, well-understood MEV/front-running pattern on Solana. The instruction is intentionally permissionless per the code comments, so there is no privileged path preventing this race outright.

### Recommendation
Consider one of:
- Making `juplend_init_position` require the group admin's signature (or gate it via a group-admin-authorized flag set during `lending_pool_add_bank_juplend`), removing the permissionless race window; or
- Performing the seed deposit atomically within `lending_pool_add_bank_juplend` itself (mirroring the report's recommendation to "initialize the pool during its creation") so there is no window between bank creation and activation for a third party to intervene.

### Proof of Concept
1. Admin submits `lending_pool_add_bank_juplend` to create a new JupLend-wrapped bank (starts `Uninitialized`).
2. Attacker observes the pending/landed bank-creation transaction and, before the admin's own `juplend_init_position` transaction lands, submits their own `juplend_init_position` call with `amount = 10` (the documented minimum) using their own funded token account.
3. The bank transitions from `Uninitialized` to `Operational` using the attacker's seed deposit and bump/CPI accounts, per the activation logic. [6](#0-5) 
4. The admin's subsequent `juplend_init_position` transaction fails with `JuplendBankAlreadyActivated` since `operational_state` is no longer `Uninitialized` (confirmed by the constraint at lines 75-76 and the existing regression test for re-activation attempts). [7](#0-6)

pub fn juplend_init_position(ctx: Context<JuplendInitPosition>, amount: u64) -> MarginfiResult {
    // Require minimum seed deposit amount (same as other integrations)
    require_gte!(
        amount,
        10,
        MarginfiError::JuplendInitPositionDepositInsufficient
    );

    // Transfer underlying tokens from fee payer -> liquidity vault
    ctx.accounts.cpi_transfer_user_to_liquidity_vault(amount)?;

    // Deposit into JupLend via CPI: liquidity_vault -> f_token_vault
    let authority_bump = ctx.accounts.bank.load()?.liquidity_vault_authority_bump;
    ctx.accounts.cpi_juplend_deposit(amount, authority_bump)?;

    // Activate (one-time): Uninitialized -> Operational.
    {
        let mut bank = ctx.accounts.bank.load_mut()?;
        bank.config.operational_state = BankOperationalState::Operational;
    }

    Ok(())
}
