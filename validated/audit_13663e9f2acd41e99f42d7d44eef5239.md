### Title
Post-default instant withdraw requests drain the fixed default-recovery reserve at the recovery haircut, stealing from defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` has an explicit `defaultRecoveryFinalized` branch that routes new requests into `postDefaultRequests` and pays them 1:1 from already-haircut amounts. `requestInstantWithdraw` has no equivalent branch: after `finalizeDefaultRecovery` it still burns/mints receipts and increments `instantWithdrawsRequestsByEpoch[user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws`. Because `epochNumber` never advances after default, the new receipt is recorded under `defaultRecoveryEpoch` and is later paid from `defaultRecoveryReserve` at `defaultRecoveryPrice` via `_claimDefaultedInstantWithdrawRequest`, even though it was never part of the `totalBasis` the reserve was sized for.

### Finding Description
The bug class is a state-confusion between epoch phases: code written for the pre-default "request/fund/claim" lifecycle is still reachable after the "defaulted/finalized" phase begins, so new claims are admitted into a closed, fixed-size recovery bucket.

In `requestWithdraw` the post-default case is handled deliberately [1](#0-0) : the CDO passes an already-haircut amount and the request is parked in `postDefaultRequests`, paid 1:1 from the reserve via `_claimPostDefaultWithdrawRequest` [2](#0-1) .

`requestInstantWithdraw` only calls `_ensureDefaultRecoveryInitialized` and then unconditionally mints a fresh receipt and registers it in the current-epoch instant claim bucket [3](#0-2) .

At finalization, `defaultRecoveryEpoch = epochNumber` and `defaultRecoveryReserve` is sized as `reserveAmount` against a fixed `totalBasis` [4](#0-3) . Since no further `stopEpoch`/`deposit` runs after default, `epochNumber` stays equal to `defaultRecoveryEpoch`, so a post-default instant request lands in `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`.

On claim, `claimInstantWithdrawRequest` runs `_claimDefaultedInstantWithdrawRequest` because `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` [5](#0-4) . That function reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — which now includes the attacker's new receipt — burns the freshly minted strategy tokens and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` out of `defaultRecoveryReserve` [6](#0-5) , decrementing the shared reserve in `_transferDefaultRecovery` [7](#0-6) .

Broken invariant: the reserve is computed once as `reserveAmount / totalBasis`; any claim added after finalization is pure dilution. Each attacker claim consumes `claimBasis * price` of reserve that belongs to pre-existing defaulted claimants, so the last legitimate claimants' `_transferDefaultRecovery` calls underflow/revert — their recovery is permanently frozen/stolen.

### Impact Explanation
An attacker converts burned tranches (priced near zero post-default) into a recovery-reserve claim at `defaultRecoveryPrice`. Every unit claimed reduces `defaultRecoveryReserve` without any corresponding unit having been included in `totalBasis`, so honest defaulted withdraw/instant claimants and post-default requestors recover strictly less; terminal claimants revert on underflow in `defaultRecoveryReserve -= _amount`, permanently losing the remainder. Loss is bounded by the attacker's post-default receipt size, which is limited only by their tranche balance bought at defaulted prices — i.e. near-total reserve capture is possible if the attacker holds a large share of tranches.

### Likelihood Explanation
Requires (a) a borrower default with `finalizeDefaultRecovery` executed and `pendingInstantWithdraws != 0` at finalization so `defaultInstantWithdrawsFinalized` is true (any unfunded instant queue at default), and (b) the CDO's instant-withdraw path being reachable after default — i.e. `_isInstantWithdrawEnabled()` configured and `lastEpochApr > unscaledApr + instantWithdrawAprDelta` at request time (plausible when the default epoch's stored APR exceeds a post-default APR that was lowered or set to 0). The attacker is an ordinary tranche holder; no privileged role is needed. The one mitigating unknown I could not fully verify in the indexed code is the exact `lastEpochApr`/`unscaledApr` values the CDO leaves after default, which gates step (b) — the strategy-side flaw stands regardless.

### Recommendation
In `requestInstantWithdraw`, add the same post-default guard used in `requestWithdraw`: when `defaultRecoveryFinalized` is true, either revert (instant withdrawals have no funding source post-default) or route through `postDefaultRequests` accounting with a haircut applied by the caller. Also add the `_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0` consistency check so post-default instant receipts can never enter `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws` after `defaultRecoveryEpoch` is sealed.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Setup: depositAA/depositBB, run epochs, create an instant withdraw request
// that is only partially funded so pendingInstantWithdraws > 0.
// 1) Trigger borrower default (no funds dealt at stopEpoch / getInstantWithdrawFunds).
// 2) Finalize: cdoEpoch.finalizeDefaultRecovery(recovered, source);
//    -> defaultRecoveryReserve sized against fixed totalBasis; epochNumber == defaultRecoveryEpoch.
// 3) Attacker (tranche holder) calls cdoEpoch.requestWithdraw(amount, tranche)
//    while lastEpochApr > unscaledApr + instantWithdrawAprDelta, so the CDO calls
//    strategy.requestInstantWithdraw -> receipt minted into
//    instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch].
// 4) Attacker calls cdoEpoch.claimInstantWithdrawRequest()
//    -> _claimDefaultedInstantWithdrawRequest pays attacker * defaultRecoveryPrice
//       from defaultRecoveryReserve.
// 5) Honest defaulted claimants call claimWithdrawRequest / claimInstantWithdrawRequest
//    -> earlier claimants get less than claimBasis * price; the last one reverts
//       (defaultRecoveryReserve underflow / insufficient balance), proving reserve theft.
```

Assert: `defaultRecoveryReserve` decreases by attacker payout while `totalBasis` never included the attacker receipt; sum of all defaulted claims paid > `reserveAmount`, ending in a revert for the final claimant.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
    _transferDefaultRecovery(_user, amount);
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
