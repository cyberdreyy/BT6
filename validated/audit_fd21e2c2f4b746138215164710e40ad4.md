### Title
Post-default withdraw requests are paid at par from the fixed-size `defaultRecoveryReserve`, draining funds reserved for defaulted-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The CVE-2023-27907 bug class is an out-of-bounds write: attacker-controlled input corrupts state beyond its intended bounds. The analog in this codebase is a claim that is written *outside* the funded recovery basis: after `finalizeDefaultRecovery` crystallizes a fixed `defaultRecoveryReserve` sized only for claims existing at finalization, `requestWithdraw` still mints brand-new receipts (`postDefaultRequests`) that are later paid 1:1 out of that same reserve. Each post-default claim spends recovery underlyings that were accounted to defaulted-epoch receipt holders, so the last claimants' payouts revert on underflow — a direct theft of their recovery share.

### Finding Description
`finalizeDefaultRecovery` sizes the reserve exactly for the claim basis known at that moment: `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis` includes only active tranche basis and `defaultPendingClaimBasis()` (pending withdraws + unfunded instant receipts) — no future claims. The reserve is then stored in `defaultRecoveryReserve` (`IdleCreditVault.sol:686-692`).

After finalization, `requestWithdraw` takes a dedicated branch: it requires the user have no prior receipts, burns the CDO's strategy tokens, mints receipt tokens to the user, and stores `postDefaultRequests[_user] = _amount` (`IdleCreditVault.sol:247-257`). No underlying is pulled into the strategy and the reserve is not increased.

`claimWithdrawRequest` then routes post-default receipts to `_claimPostDefaultWithdrawRequest`, which pays `amount` in full via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` and transfers reserve underlyings (`IdleCreditVault.sol:760-767`, `912-917`). Because the reserve was sized to `recoveryPrice * totalBasis`, every wei paid to a post-default receipt is wei that was accounted to a defaulted-epoch claimant. Once cumulative post-default payouts exceed rounding slack, `_transferDefaultRecovery` underflows (`defaultRecoveryReserve -= _amount`) or the transfer fails, permanently freezing the remaining defaulted claims — while the post-default claimant walked away at par.

The haircut argument doesn't save it: the post-default request amount is already reduced by the lowered `virtualPrice`, but the reserve assumes *every* defaulted claim is also multiplied by `recoveryPrice` (e.g., 40%). Paying a new claim 1:1 consumes ~1/0.4 = 2.5x more reserve per unit of pre-loss basis than the accounting reserved for it.

### Impact Explanation
Any KYC-passed tranche holder can, after default finalization, call `requestWithdraw` (the code explicitly preserves this UX: "Preserve request/claim UX after default") and then `claimWithdrawRequest` to extract reserve underlyings at par. Loss is quantifiable: up to the full `defaultRecoveryReserve` can be redirected to post-default requesters while earlier defaulted-epoch receipts — including unfunded instant-withdraw receipts — are left unclaimable (permanent freezing + direct theft of recovery funds).

### Likelihood Explanation
Requires the pool to have defaulted and `finalizeDefaultRecovery` to have run, plus an open withdraw-request flag for at least one tranche class (the code comments state AA requests can be left open through a loss/emergency path, and the `postDefaultRequests` machinery exists precisely to serve this flow). Given that state, the attack is a single permissionless sequence by any wallet-allowed tranche holder — request, then claim — with no privileged collusion. Note: I could not fully verify which `allowAAWithdrawRequest`/`allowBBWithdrawRequest` configuration is live post-finalization in every deployment; if both flags are always false after default, the CDO-side `requestWithdraw` gate blocks the entry point and this reduces to dead code rather than an exploitable bug.

### Recommendation
Fund post-default receipts separately or haircut them at request time against the reserve. Options:
- In `requestWithdraw`'s post-default branch, store the claim but require the CDO to transfer the corresponding underlyings into the strategy (new funding), rather than spending `defaultRecoveryReserve`.
- Alternatively, price post-default claims at `defaultRecoveryPrice` when paying (i.e., treat them as additional basis), or revert post-default requests entirely since no new lending can occur after default.
- At minimum, cap `_claimPostDefaultWithdrawRequest` payouts so `defaultRecoveryReserve` can never drop below `defaultRecoveryPrice * remaining defaulted basis`.

### Proof of Concept
Foundry fork sketch (model on `test/foundry/IdleCreditVault.t.sol` default/finalization tests):

```solidity
// 1. LPs depositAA/depositBB; manager startEpoch; borrower defaults.
// 2. Owner/guardian run the default path; CDO calls
//    strategy.finalizeDefaultRecovery(recovered, source) with
//    recovered < totalBasis  => defaultRecoveryPrice = r < 1e18.
//    defaultRecoveryReserve = recovered + prefunded (fixed sum).
// 3. Attacker (KYC'd wallet holding AA tranche tokens worth X post-haircut):
//      cdo.requestWithdraw(attackerBal, AATranche);   // creates postDefaultRequests[attacker]=X
//      cdo.claimWithdrawRequest();                    // pays X at par from reserve
// 4. Victim with defaulted-epoch receipt basis B calls
//      cdo.claimWithdrawRequest();                    // expects B*r
//    -> reverts: defaultRecoveryReserve underflow or insufficient balance.
// assert: attacker received X; reserve decreased by X;
//         victim claim reverts though B*r was reserved at finalization.
```

Key assertions: `strategy.defaultRecoveryReserve()` decreases by the full post-default payout while no new basis was added at finalization, and a pre-existing defaulted receipt's claim of `basis * defaultRecoveryPrice / 1e18` reverts after the attacker's claim.
