### Title
Front-running the deterministic lockup address lets an unprivileged attacker permanently hijack `victim.near`'s lockup parameters - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` is a fully public, unauthenticated method whose target account id is derived solely from `owner_account_id` (`sha256(owner_account_id)[..20].<factory>`), with no check that the caller is the intended grantor, owner, or foundation. Any account can front-run the legitimate grantor's `create` transaction for the same `owner_account_id` by getting its own `create_account()` promise executed first, permanently claiming the deterministic address with attacker-chosen `lockup_duration`, `vesting_schedule`, and `staking_pool_whitelist_account_id`, and causing the legitimate call to fail and refund.

### Finding Description
The binding the deployment model assumes is:
`LockupArgs deployed at sha256(owner_account_id)[..20].<factory> == LockupArgs chosen by the party the real owner/grantor authorized to create their lockup`

The address is computed purely from `owner_account_id`: [1](#0-0) 

`create` is `#[payable]` and public with no `assert_called_by_foundation`, no owner check, and no restriction on `predecessor_account_id`; it only checks the deposit amount: [2](#0-1) 

Because the target account id depends only on `owner_account_id` and NEAR account creation is exclusive (`create_account()` fails if the account already exists), whichever `create` call's `Promise::new(lockup_account_id).create_account()...` is included/executed first wins the address, regardless of who the "real" grantor is: [3](#0-2) 

The callback `on_lockup_create` only checks `is_promise_success()`; on failure it refunds the *predecessor's* deposit and returns `false` — it has no way to detect or reverse the fact that the address was already taken by different `LockupArgs`: [4](#0-3) 

Exploit flow: an attacker observing (or even just racing, since no observation is strictly required — any account can call `create("victim.near", ...)` at any time before the legitimate grantor) submits `create(owner_account_id="victim.near", lockup_duration=0, lockup_timestamp=None, vesting_schedule=None, release_duration=None, whitelist_account_id=Some("evil.near"))` with `attached_deposit = MIN_ATTACHED_BALANCE`. If this transaction's `create_account()` action executes before the legitimate grantor's transaction for the same `owner_account_id`, the attacker's `LockupArgs` (no vesting, attacker-chosen whitelist, zero lockup duration) get deployed at the deterministic address. The legitimate grantor's later `create` call for `victim.near` then has its `create_account()` fail (account already exists), `is_promise_success()` returns `false` in `on_lockup_create`, the deposit is refunded to the legitimate grantor, and `victim.near`'s canonical lockup address is permanently occupied by attacker-chosen parameters — none of which the real grantor or `victim.near` ever authorized.

No existing guard (`assert_self`, `is_promise_success`, `assert_one_yocto`, etc.) prevents this because none of them check *who* is allowed to call `create` for a given `owner_account_id` in the first place — the vulnerability is the complete absence of caller authentication/reservation for the deterministic address.

### Impact Explanation
This matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attacker can set `lockup_duration=0` (no lockup at all) and a `staking_pool_whitelist_account_id` pointing to a staking pool the attacker controls, meaning once/if funds are later associated with this account (e.g., if the real grantor is confused into believing the address is correct, or any subsequent flow trusts the deterministic address for `victim.near`), the account has no real vesting/lockup protection and its whitelist is attacker-controlled. This is repeatable for any `owner_account_id` value across the lifetime of the factory — the attacker just needs to always win the race for the account they want to hijack. Blast radius: any account that has a legitimate lockup being prepared through the factory before this attacker-observed/raced transaction lands.

### Likelihood Explanation
The precondition is only `attached_deposit >= MIN_ATTACHED_BALANCE` (3.5 NEAR) which any unprivileged account can afford, and getting a transaction included before another pending transaction — a standard front-running/priority-gas scenario, requiring no special privileges, keys, or roles. This is fully within the defined "unprivileged attacker" capability of sending transactions with attached deposits. No foundation, owner, or multisig involvement is required.

### Recommendation
Restrict `create` so that the deterministic address can only be claimed by (or on behalf of) `owner_account_id` itself, e.g. require `predecessor_account_id() == owner_account_id` (or a signed authorization from the owner), or otherwise bind the derived account id to include a caller-agnostic uniqueness that cannot be squatted by an unrelated third party, and/or gate `create` behind `assert_called_by_foundation` as originally intended for a curated grantor list.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs tests module
#[test]
fn test_frontrun_hijacks_deterministic_address() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker front-runs with owner_account_id = victim, attacker-chosen params
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = MIN_ATTACHED_BALANCE;
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // "victim.near" equivalent
        0u64.into(),            // lockup_duration = 0
        None,
        None,
        None,
        Some(custom_whitelist_account_id()), // "evil.near"
    );

    // Attacker's create_account succeeds first
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let attacker_result = contract.on_lockup_create(
        lockup_account(),
        MIN_ATTACHED_BALANCE.into(),
        String::from("attacker.near"),
    );
    assert_eq!(attacker_result, true); // attacker's LockupArgs are now live at the address

    // Legitimate grantor's later create for the SAME victim.near now fails at create_account
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), LOCKUP_DURATION.into(), None, None, None, None);

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed); // account already exists
    let legit_result = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner()),
    );
    assert_eq!(legit_result, false); // legitimate grantor's deposit refunded, attacker's args remain live
}
```
This demonstrates: `attacker_result == true` (attacker's zero-duration, attacker-whitelisted `LockupArgs` deployed) while `legit_result == false` (legitimate grantor's identical-target `create` call fails and is refunded), proving the deterministic-address binding is broken by an unprivileged front-running caller.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
