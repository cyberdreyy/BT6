### Title
Post-default withdraw requests mint instant claims against the fixed `defaultRecoveryReserve`, letting a tranche holder drain recovery funds earmarked for defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` has a post-default fast path that mints a receipt into `postDefaultRequests[_user]` without adding any backing, while `_claimPostDefaultWithdrawRequest` pays it 1:1 out of `defaultRecoveryReserve`. The reserve was sized at finalization to cover only pre-default claim basis (`totalBasis` at `defaultRecoveryPrice`), so every post-default request creates a new unbacked claim that races honest defaulted claimants for the same finite reserve.

### Finding Description
After a borrower default is finalized via `finalizeDefaultRecovery`, the strategy stores `defaultRecoveryReserve = reserveAmount` and `defaultRecoveryPrice`, intended to pay all defaulted receipts (normal, APR0, instant) plus active-LP recovery. Subsequently, `requestWithdraw` takes a special branch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:247-257
if (defaultRecoveryFinalized) {
  if (_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0) {
    revert NotAllowed();
  }
  _burn(msg.sender, _amount);
  _mint(_user, _amount);
  postDefaultRequests[_user] = _amount;
  return;
}
```

The claim path then pays that receipt at par directly from the recovery reserve with no epoch-wait, no funding event, and no increase to the reserve:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:760-767
amount = postDefaultRequests[_user];
if (amount == 0) return amount;
postDefaultRequests[_user] = 0;
_burn(_user, amount);
_transferDefaultRecovery(_user, amount);   // decrements defaultRecoveryReserve
```

The comment says post-default requests are "already backed by default recovery reserve" and "the CDO passes an already-haircut amount because finalization lowered virtualPrice" — but the haircut only sizes the *receipt amount*; the *payout* still draws on `defaultRecoveryReserve`, which was computed as `reserveAmount = _recoveredAmount + prefundedReserve + priorReserve` against `totalBasis` of pre-default claims only (lines 679-692). No underlying is added to the strategy when a post-default request is created (`_burn`/`_mint` are pure receipt token operations; `postDefaultRequests` adds no funding). Therefore:

`sum(defaulted claims × recoveryPrice) + sum(postDefaultRequests × 1.0) > defaultRecoveryReserve`

is guaranteed for any non-zero post-default request. Claims are first-come-first-served, and `_transferDefaultRecovery` simply decrements the reserve and transfers — once the reserve is exhausted, remaining defaulted-epoch claimants (normal receipts via `_claimDefaultedWithdrawRequest`, instant receipts via `_claimDefaultedInstantWithdrawRequest`) get zero or the transaction reverts on underflow/insufficient balance.

This is the same bug class as the report: two representations of the "same" protected resource (post-default receipts vs defaulted-epoch receipts) are checked against different guards, while both resolve to the same finite asset pool downstream.

### Impact Explanation
Direct theft of defaulted-epoch recovery funds. Any tranche holder (a permitted unprivileged actor) can, immediately after `finalizeDefaultRecovery`, call `IdleCDOEpochVariant.requestWithdraw` → `IdleCreditVault.requestWithdraw` → `claimWithdrawRequest` in the same or next transaction and pull up to the full `defaultRecoveryReserve` ahead of honest claimants, whose claims then become unpayable. Loss is bounded by `defaultRecoveryReserve` (the entire recovered amount, e.g. all recovered USDC from the default), which can be arbitrarily close to 100% of honest claimants' expected recovery.

### Likelihood Explanation
- Preconditions: borrower defaults (a real, anticipated event — the entire `finalizeDefaultRecovery`/`DefaultDistributor` machinery exists for it) and at least one defaulted receipt holder has not yet claimed.
- The attacker needs only to hold tranche tokens post-default (any KYC-passing lender) and win the claim ordering — the post-default claim has *no* epoch-wait gate unlike normal funded claims (`_claimFundedWithdrawRequest` checks `epochNumber <= lastWithdrawRequest`), so the attacker can request and claim atomically or faster than users waiting on the UI.
- Repeatability: the guard `postDefaultRequests[_user] != 0` resets on claim, so an attacker can split across multiple addresses to extract arbitrarily large fractions.
- No existing guard stops it: `_onlyIdleCDO` passes (request goes through the CDO), the `_hasWithdrawRequest` check only blocks users with *existing* receipts, and `skipDefaultCheck`/defaulted flags do not gate this path — the code intentionally keeps `requestWithdraw` usable after default.

### Recommendation
Do not pay post-default requests from `defaultRecoveryReserve`. Options:
- Track a separate funded bucket: post-default requests should only become claimable after the borrower/strategy actually funds them (e.g., require a `collectWithdrawFunds`-style transfer that increments a dedicated balance), or
- If post-default requests are meant to be paid from *newly recovered* funds, increment `defaultRecoveryReserve` only when real underlying arrives, or
- Revert `requestWithdraw` while `defaultRecoveryFinalized` until the reserve is fully consumed/migrated, matching the "one receipt, one payout" invariant.

### Proof of Concept
Foundry fork-style test against the repo's own harness (`test/foundry/IdleCreditVault.t.sol` provides the deployment helpers):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "./IdleCreditVault.t.sol"; // reuse setup: cdoEpoch, strategy (IdleCreditVault), underlying, LP

contract PostDefaultReserveDrain is IdleCreditVaultTest {
  function testPostDefaultClaimDrainsRecoveryReserve() external {
    // --- setup: epoch running, LP (honest) + attacker both hold AA tranches ---
    uint256 dep = 100_000e6;
    _depositAA(LP, dep);
    _depositAA(ATTACKER, dep);
    _startEpoch();                 // borrower draws funds

    // honest LP requests withdraw during the epoch (pending receipt, epoch N)
    vm.prank(LP);
    cdoEpoch.requestWithdraw(dep / 2, address(AATranche));

    // --- borrower defaults; owner/manager (honest) finalize recovery ---
    _stopEpochWithDefault();                       // cdoEpoch.defaulted() == true
    uint256 recovered = /* partial recovery funded by borrower/manager */;
    _finalizeDefaultRecovery(recovered);           // sets defaultRecoveryReserve/Price/Epoch

    uint256 reservePre = strategy.defaultRecoveryReserve();
    uint256 price    = strategy.defaultRecoveryPrice();
    assertGt(reservePre, 0);
    assertLt(price, 1e18);                         // haircut applied

    // --- attacker: post-default request + claim, no epoch wait ---
    uint256 attackerTranches = AATranche.balanceOf(ATTACKER);
    vm.startPrank(ATTACKER);
    cdoEpoch.requestWithdraw(attackerTranches, address(AATranche)); // mints postDefaultRequests
    uint256 claimed = cdoEpoch.claimWithdrawRequest();              // paid 1:1 from reserve
    vm.stopPrank();

    // attacker pulled reserve without any new funding
    assertEq(strategy.defaultRecoveryReserve(), reservePre - claimed);
    assertGt(claimed, 0);

    // --- honest LP's defaulted receipt now underfunded/reverts ---
    uint256 lpBasis = strategy.withdrawsRequestsByEpoch(LP, strategy.defaultRecoveryEpoch());
    uint256 lpExpected = lpBasis * price / 1e18;
    if (strategy.defaultRecoveryReserve() < lpExpected) {
      vm.prank(LP);
      vm.expectRevert(); // reserve exhausted: underflow in _transferDefaultRecovery or failed transfer
      cdoEpoch.claimWithdrawRequest();
    }
  }
}
```

Key assertion: `claimed > 0` was paid out of `defaultRecoveryReserve` even though `finalizeDefaultRecovery` sized that reserve only for pre-default basis, and no underlying was added when `postDefaultRequests[ATTACKER]` was created. The honest LP's recovery claim is correspondingly reduced or unpayable — quantified theft of unclaimed default-recovery yield.
