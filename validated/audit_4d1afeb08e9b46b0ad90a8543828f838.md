### Title
Secp256r1 precompile decompresses attacker-controlled EC points via OpenSSL, reachable class for CVE-2022-0778-style infinite-loop DoS - ([File: precompiles/src/secp256r1.rs])

### Summary
The `secp256r1` precompile parses a compressed elliptic-curve public key taken directly from transaction instruction data and calls into OpenSSL's `EcPoint::from_bytes` to decompress it, exactly the operation class that CVE-2022-0778 broke (an infinite loop in `BN_mod_sqrt()` when OpenSSL attempts to compute the y-coordinate for a compressed point whose x-coordinate is not a valid quadratic residue on the curve).

### Finding Description
`verify()` reads the compressed public key bytes straight out of transaction instruction data with no validation beyond a fixed-size slice check, then hands them to OpenSSL for point decompression: [1](#0-0) [2](#0-1) 

`EcPoint::from_bytes` on a compressed-form point internally invokes OpenSSL's `EC_POINT_set_compressed_coordinates`, which calls `BN_mod_sqrt()` to recover the y-coordinate from the x-coordinate. In OpenSSL versions affected by CVE-2022-0778, feeding this routine a maliciously crafted x-coordinate that is not a quadratic residue causes `BN_mod_sqrt()` to loop forever, hanging the calling thread. Because this parsing happens inside the secp256r1 precompile — which every validator executes deterministically while processing a transaction that references the `Secp256r1SigVerify` program — an attacker who submits such a transaction can trigger the hang on every validator that processes it, not just one node.

### Impact Explanation
If the linked OpenSSL is a vulnerable version, an unprivileged user can submit a single transaction containing a `secp256r1` precompile instruction with a crafted 33-byte compressed public key whose x-coordinate has no valid square root mod p. Every validator that reaches this instruction during transaction verification would hang inside `BN_mod_sqrt()`, causing a network-wide denial of service / cluster halt — this is the "transaction-triggered cluster halt" impact class explicitly in scope.

### Likelihood Explanation
This is contingent on the actual OpenSSL version linked by the build. The `openssl` crate typically links against the system OpenSSL (or a vendored copy if the `vendored` Cargo feature is enabled); I was not able to fully confirm the pinned/vendored OpenSSL version from the indexed `Cargo.lock` contents (the file content available to me was truncated to just the header comment), so I cannot definitively confirm whether the currently used OpenSSL version is patched against CVE-2022-0778. If a patched version (OpenSSL ≥ 1.1.1n / ≥ 3.0.2, or equivalent 1.0.2 backport) is linked, this specific CVE would not be exploitable, though the general pattern of decompressing untrusted EC points via OpenSSL remains a latent risk class worth auditing whenever the OpenSSL dependency is bumped.

### Recommendation
- Verify and pin the OpenSSL version linked into the validator build (via `cargo tree` / build inspection of `openssl-sys`) to confirm it is ≥ the CVE-2022-0778 fixed versions.
- Consider validating that the decompressed point actually lies on the curve and add a bound/timeout or explicit quadratic-residue check before calling into `EcPoint::from_bytes` with attacker-supplied compressed coordinates, so a future regression in the underlying crypto library cannot cause a full-cluster hang from a single transaction.
- Add fuzz/regression tests that feed non-quadratic-residue x-coordinates to `secp256r1::verify` to ensure the precompile fails fast rather than blocking.

### Proof of Concept
1. Craft a `secp256r1` precompile instruction (per `Secp256r1SignatureOffsets` layout) whose 33-byte compressed public key field encodes an x-coordinate for which `x^3 - 3x + b mod p` is not a quadratic residue on P-256.
2. Submit a transaction containing this instruction.
3. On a validator linked against an OpenSSL version vulnerable to CVE-2022-0778, `verify()` at [3](#0-2)  calls `EcPoint::from_bytes`, which enters `BN_mod_sqrt()` and loops indefinitely, hanging the validator's transaction processing thread for every node that processes the transaction.

**Uncertainty note:** I could not confirm the exact OpenSSL version pinned by this repository's `Cargo.lock`/`openssl-sys` build metadata beyond finding references to the `openssl` crate; the actual file contents needed to confirm the version were not available through the indexed search (likely due to index size limits on lock files). Confirming exploitability requires checking the resolved OpenSSL version in the build environment, which I could not fully do from the available index. A Devin session with full repository/build access would be needed to check `Cargo.lock`'s `openssl-sys` version and any `vendored` feature flags to conclusively confirm or rule out exploitability.
