### Title
Zip legacy extractor lacks path-containment (chroot) enforcement present in tarzstd extractor - ([File: helpers/archives/zip_extract.go])

### Summary
The `ziplegacy` extractor (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`) forwards directly into `archives.ExtractZipArchive` → `extractZipFile`, which writes to `file.Name` from the zip entry with no path validation, no join against the extraction root, and no chroot/prefix check. This is in stark contrast to the `tarzstd` extractor, which explicitly computes `filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects any path that escapes `e.dir` via `strings.HasPrefix`.

### Finding Description
`archive.NewExtractor(format, r, size, dir)` dispatches by `Format` to one of three registered constructors [1](#0-0) . For the `ziplegacy` implementation, `NewExtractor` stores `dir` on the `extractor` struct but `Extract` never uses it — it simply calls `zip.NewReader` and hands the result to `archives.ExtractZipArchive`: [2](#0-1) .

`ExtractZipArchive` iterates zip entries and calls `extractZipFile(file)` for each, using `file.Name` verbatim: [3](#0-2) . `extractZipFile` does `os.MkdirAll(filepath.Dir(file.Name), ...)` and then `os.OpenFile(file.Name, ...)` / `os.Symlink(data, file.Name)` / `os.Mkdir(file.Name, ...)` with zero normalization, zero join-with-root, and zero prefix/containment check: [4](#0-3) .

Compare this to `tarzstd`'s extractor, which is the counter-example the question cites: it computes the absolute path relative to `e.dir` and explicitly rejects any entry whose resolved path does not stay under `e.dir` [5](#0-4) . The `fastzip` extractor delegates directly to the `saracen/fastzip` third-party library's `Extract`, which is a different code path not reviewable here (not part of this repo's index), but is a widely-used library that implements path traversal ("zip slip") protection internally; that claim is not independently verified in this audit and is noted as unverified. [6](#0-5) 

The `Format` used to select which extractor implementation runs is derived from `openArchive(c.File)`'s format detection in `CacheExtractorCommand.Execute`, and the archive bytes themselves are attacker-supplied cache content (the cache file is downloaded from a URL/GoCloud bucket the job/pipeline controls, or is a locally-produced cache from a prior job step): [7](#0-6) . I was unable to locate the exact `openArchive`/format-detection function in this index (search only surfaced an unrelated match in `artifacts_downloader.go`), so I cannot confirm from source exactly how the legacy-zip vs zipzstd/fastzip format is distinguished from magic bytes; this is a gap in verification, not a refutation of the vulnerability itself, since the `ziplegacy` code path's lack of containment is independently confirmed regardless of how it is selected.

Given that `Format` values registered include `Zip` (legacy zip, mapped to `ziplegacy`) as distinct from `ZipZstd`/`TarZstd`, and that the cache/artifact "legacy zip" fallback path exists specifically for compatibility with old Runner cache files (per `zip_legacy_archiver.go`/`zip_legacy_extractor.go` naming), an entry with a crafted `file.Name` such as `../../../../etc/passwd` or `/etc/passwd` (zip permits absolute/traversal names in the central directory) will be extracted straight to that OS path via `os.OpenFile`, with no root-relative validation, if the cache format that reaches this code path is legacy zip.

### Impact Explanation
If the ziplegacy extractor is reached with attacker-crafted zip entries (path traversal or absolute paths), a job can write/overwrite arbitrary files on the executor's filesystem outside the intended build/cache directory (`e.dir`/`wd`), violating the "file operations must stay within intended build/cache/artifact roots" invariant. Depending on the executor (shell, docker-in-VM, etc.) and where the runner process runs relative to the job sandbox, this could allow overwriting files on the host running the runner helper binary (for shell executor or container executors where the cache-extractor runs on the host/VM rather than fully isolated), which is a directory-traversal / arbitrary file write, not merely a documented admin trust decision.

### Likelihood Explanation
The attacker needs to get a zip-format cache archive with traversal/absolute entry names processed via the `ziplegacy` code path. This requires: (1) control over cache archive bytes (feasible — a job can construct or influence its own cache tarball before it is uploaded/downloaded, or if cache content originates from another entity trusted by the runner such as a shared cache bucket the pipeline author controls) and (2) the format-detection logic actually selecting `ziplegacy` for that payload (unverified in this session because `openArchive`'s implementation wasn't found in the index). Given `ziplegacy` is a real, still-registered/reachable extractor with no path-containment code whatsoever, and the divergence from `tarzstd`'s explicit chroot check is unambiguous in the source, this is a plausible, code-confirmed logic bug (missing check) even though the exact format-selection trigger condition needs confirmation via a Devin session with fuller repo access.

### Recommendation
Add the same chroot/path-containment enforcement in `extractZipFile` (or in `ExtractZipArchive`/`ziplegacy.Extract`) that `tarzstd_extractor.go` performs: join each `file.Name` against the extraction root (`e.dir`), take `filepath.Abs`, and reject entries whose resolved path does not have `e.dir` (or `e.dir+separator`) as a prefix, mirroring `commands/helpers/archive/tarzstd/tarzstd_extractor.go:57-64`. Since `archives.ExtractZipArchive`/`extractZipFile` currently take no `dir` parameter at all, this requires threading the extraction root through `ExtractZipArchive(archive *zip.Reader, dir string)` → `extractZipFile(file, dir)` and updating all callers (`ziplegacy.extractor.Extract`, `ExtractZipFile`, and any artifacts-downloader callers) accordingly.

### Proof of Concept
Go unit test in `helpers/archives/zip_extract_test.go` (or a new test file):
1. Build an in-memory `*zip.Writer` containing one entry named `../../../../tmp/pwned-zipslip-test` (or, on the test's platform, a path that resolves outside a temp extraction directory) with arbitrary content.
2. Create a `zip.Reader` from the buffer and call `archives.ExtractZipArchive(zr)` (or `ziplegacy.NewExtractor(...).Extract(ctx)`) from a controlled working directory / `dir`.
3. Assert: the file must NOT be created outside the intended extraction directory — currently it WILL be created outside (bug), the test should assert `os.Stat` on the resolved outside-root path succeeds today (proving the bug) and fails once the containment check recommended above is added (regression test after fix: expect `Extract` to return an error like tarzstd's `"%s cannot be extracted outside of chroot (%s)"`).
4. Differential companion test: run the identical zip byte stream through the `fastzip` extractor's `Extract` and the `tarzstd` extractor's `Extract` (converted to an equivalent tar+zstd stream) and assert both either error out or confine the write inside `dir`, while the `ziplegacy` path does not — demonstrating the inconsistency across backends as required by the invariant in the question.

func extractZipDirectoryEntry(file *zip.File) (err error) {
	err = os.Mkdir(file.Name, file.Mode().Perm())

	// The "directory does exist" error is not an error for us
	if os.IsExist(err) {
		err = nil
	}
	return
}

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}
