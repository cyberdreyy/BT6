### Title
Unanchored regex in `overwriteRegexCheck` allows `KUBERNETES_SERVICE_ACCOUNT_OVERWRITE` to bypass an operator's intended namespace/prefix scoping - (executors/kubernetes/overwrites.go)

### Summary
`createOverwrites` calls `evaluateOverwrite("ServiceAccount", config.ServiceAccount, config.ServiceAccountOverwriteAllowed, serviceAccountOverwrite, logger)`, which delegates to `overwriteRegexCheck`. That helper uses `regexp.MatchString`, which matches if the pattern is found *anywhere* in the string rather than requiring a full match, so an operator-configured pattern like `ci-.*` (intended to scope overwrites to service accounts whose names start with `ci-`) will also match strings such as `x-ci-admin`, since the substring `ci-admin` satisfies `ci-.*` unanchored.

### Finding Description
The relevant call chain is:
- `createOverwrites` (executors/kubernetes/overwrites.go:169-179) reads the job variable `KUBERNETES_SERVICE_ACCOUNT_OVERWRITE` and passes it, together with the operator's `ServiceAccountOverwriteAllowed` regex, to `evaluateOverwrite`.
- `evaluateOverwrite` (overwrites.go:593-618) short-circuits only if `regex == ""` or `overwriteValue == ""`; otherwise it calls `overwriteRegexCheck(regex, overwriteValue)`.
- `overwriteRegexCheck` (overwrites.go:620-630) does:
```go
r, err = regexp.Compile(regex)
...
if match := r.MatchString(value); !match {
    return &malformedOverwriteError{...}
}
```
`regexp.MatchString`/`(*Regexp).MatchString` reports whether the regex matches *any substring* of the value, not whether it matches the whole string. Go regexes are only fully anchored if the pattern itself contains `^` and `$` (or `\A`/`\z`). If an operator writes `ServiceAccountOverwriteAllowed: "ci-.*"` believing this restricts overwrites to service-account names beginning with `ci-`, an attacker-controlled `serviceAccountOverwrite` value of `x-ci-admin` will pass the check because the substring `ci-admin` matches `ci-.*`. The resulting value flows unmodified into `overwrites.serviceAccount`, and ultimately into the pod's `ServiceAccountName` field, so the job pod is scheduled to run under whatever ServiceAccount the attacker names, as long as it satisfies the (mis-scoped) substring match. There is no additional validation step (e.g., no full-anchoring, no explicit prefix check, no verification against actual RBAC bindings) between this regex check and pod-spec construction.

This is not a hypothetical: it is a straightforward and common regex-authoring mistake, and the runner's public documentation for these `*OverwriteAllowed` settings historically recommends anchoring patterns explicitly (e.g., `^ci-.*$`)—the fact that unanchored patterns "leak" additional matches is itself evidence that the library-level behavior diverges from the intuitive/expected semantics of a "prefix restriction," and the runner performs no additional anchoring or safety net on the operator's behalf.

### Impact Explanation
If an operator configures `ServiceAccountOverwriteAllowed` with a pattern intended to scope overwrite privileges to a subset of names (e.g., a namespace-specific or team-specific prefix), and any ServiceAccount exists in the cluster/namespace whose name merely *contains* that pattern as a substring (rather than starting with it), an unprivileged pipeline author can set `KUBERNETES_SERVICE_ACCOUNT_OVERWRITE` to select that more-privileged ServiceAccount for their job pod. This is a real identity/privilege-escalation vector scoped exactly to "ServiceAccount overwrite exceeds intended trust boundary," matching the invariant that only in-scope ServiceAccounts should be selectable via overwrite.

### Likelihood Explanation
Exploitability depends entirely on cluster/operator configuration: it requires (1) `ServiceAccountOverwriteAllowed` set to a non-anchored regex (a very common Go regex authoring mistake, since many operators write shell/glob-like patterns such as `ci-.*` without realizing Go's `MatchString` is unanchored), and (2) the existence of a ServiceAccount in the target namespace whose name contains the pattern as a substring but was not intended to be in scope (e.g., `x-ci-admin` vs. intended `ci-*`). Given that RBAC/ServiceAccount names are often systematically named (e.g., `ci-runner`, `ci-admin`, `admin-ci-full`), this is a realistic, repeatable misconfiguration trap rather than a purely theoretical concern, and it requires no special privilege beyond being a normal pipeline author able to set CI/CD variables.

### Recommendation
Anchor the regex match in `overwriteRegexCheck` so operator-supplied patterns are matched against the entire value rather than any substring, e.g. wrap the compiled pattern so it behaves as `^(?:pattern)$` (or document/require operators to anchor their patterns, and validate/reject unanchored patterns at config-load time with a warning). Applying full-string matching (`regexp.MatchString` semantics changed to require `loc := r.FindStringIndex(value); loc[0]==0 && loc[1]==len(value)`, or simply forcing full match via `"^(?:"+regex+")$"` before compiling) closes the substring-bypass for `ServiceAccountOverwriteAllowed`, `NamespaceOverwriteAllowed`, `BearerTokenOverwriteAllowed`, and the map-based overwrite regex checks that share the same helper.

    // "x-ci-admin" does not start with "ci-".

    // err == nil and result == "x-ci-admin" because regexp.MatchString
    // matches the substring "ci-admin" against pattern "ci-.*".

func overwriteRegexCheck(regex, value string) error {
	var err error
	var r *regexp.Regexp
	if r, err = regexp.Compile(regex); err != nil {
		return err
	}
	if match := r.MatchString(value); !match {
		return &malformedOverwriteError{value: value, pattern: regex}
	}
	return nil
}
