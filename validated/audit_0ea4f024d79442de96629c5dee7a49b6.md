### Title
Unbounded ERC4626 exchange lets a vault shareholder steal programmable-borrower deposits - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` accepts whatever number of ERC4626 shares the configured vault returns for deposits and accepts whatever shares a fixed-asset withdrawal burns, without enforcing a minimum-share or maximum-share bound. `onStartEpoch()` deposits every idle asset through `_depositToVault()`, while `_repay()` uses the same unprotected path during an active epoch. [1](#0-0) [2](#0-1)  A vault user can inflate the vault’s assets-per-share immediately before the deposit—most cheaply by becoming the first shareholder of a newly selected ERC4626 vault and donating assets that the vault counts in `totalAssets()`—so the borrower receives zero or near-zero shares while the transferred assets remain claimable by the attacker’s shares.

### Finding Description
`_depositToVault()` calls `vault.deposit(_assetAmount, address(this))` and only emits the returned share amount; it never compares that amount with `previewDeposit()` or a caller-supplied minimum. [2](#0-1)  The same omission affects repayment redeployments, where `_repay()` passes the transferred assets to `_depositToVault()` after reducing the borrower’s accounting balances. [3](#0-2)   

Epoch starts are directly reachable through `startEpoch()`: the CDO sends the buffered funds to the borrower, then `onStartEpoch()` deposits the borrower contract’s entire token balance. [4](#0-3) [1](#0-0)  The receiver is always `ProgrammableBorrower`, so no other contract validates that the vault minted a fair number of shares. [2](#0-1) 

The configured vault is intentionally arbitrary provided that its `asset()` matches the CDO token; the code does not require a particular ERC4626 implementation, minimum existing supply, virtual shares, or dead-share protection. [5](#0-4) [6](#0-5)  ERC4626 previews explicitly need not reflect execution-time exchange conditions, so reading `convertToShares()` or `convertToAssets()` before the transaction is not equivalent to enforcing slippage at execution. [7](#0-6) 

The fixed-asset withdrawal paths have the complementary issue: `onStopEpoch()` and `_borrow()` request an exact asset amount and accept the returned number of burned shares without a maximum-share bound. [8](#0-7) [9](#0-8)  `emergencyExitVault()` similarly redeems a fixed share amount without a minimum-asset bound. [10](#0-9) 

### Impact Explanation
The broken invariant is fair minting between underlying assets and external-vault shares. For a donation-based ERC4626, an attacker who owns all or nearly all vault shares can first mint one share and donate enough underlying so that `assets * totalSupply / totalAssets` rounds to zero for the next deposit. `ProgrammableBorrower` still transfers the full deposit, receives no meaningful claim, and the attacker later redeems the vault shares for both the donation and the victim deposit.

The affected transaction sequences are:

- **Buffer to running:** a lender or attacker deposits a small amount into the CDO; the attacker inflates the selected vault’s share price; the honest manager calls `startEpoch()`; `onStartEpoch()` deposits the full balance and accepts the manipulated share amount. [11](#0-10) [12](#0-11) 
- **Running epoch:** the honest borrower calls `repay()`; `ProgrammableBorrower` decreases borrower debt and redeploys the cash through the same unchecked `vault.deposit()` call. [13](#0-12) 
- **Stop or borrow:** a manipulated conversion rate can cause `vault.withdraw()` to burn a materially different number of shares than expected even though the requested asset amount is fixed. [8](#0-7) [9](#0-8) 

The direct loss on the zero-share branch is the deposited asset amount, less only any share value actually minted to `ProgrammableBorrower`. The attacker must be a vault shareholder and have enough capital to inflate the vault conversion rate, so the strongest practical case is an empty or newly integrated ERC4626 vault where the attacker can hold all outstanding shares before the borrower’s first deposit.

### Likelihood Explanation
Likelihood is configuration-dependent. `setVault()` accepts any compatible ERC4626 vault, including one with little or no existing supply and a `totalAssets()` implementation that includes direct deposits or underlying-position donations. [6](#0-5)  A first shareholder can inflate the price before the first `onStartEpoch()` deposit, and subsequent attacker redemptions recover the donation plus the under-minted deposit.

For a large established MetaMorpho vault, permanently buying dominant share ownership and donating enough assets to force a zero-share deposit can be capital intensive. That reduces practical likelihood but does not remove the missing bound: the code also does not protect fixed-share `redeem()` calls from receiving too few assets or fixed-asset `withdraw()` calls from burning too many shares. [8](#0-7) [10](#0-9) 

### Recommendation
Add execution-time bounds to every ERC4626 exchange:

- Change `_depositToVault(uint256 assets, uint256 principalAssets)` to accept `minShares`, and revert when `vault.deposit()` returns less than that bound. [2](#0-1) 
- Pass manager-supplied `minShares` through `IdleCDOEpochVariant.startEpoch()`/`_startEpochProgrammableBorrower()` into `onStartEpoch()`, because the deposited amount is only finalized inside that transaction. [4](#0-3) 
- Add a `minShares` argument to `repay()`/`executeRepay()` or compute a conservative bound inside the same transaction and revert on an insufficient mint. [3](#0-2) 
- For fixed-asset withdrawals, add a `maxShares` bound and compare it to the returned share count. [8](#0-7) [9](#0-8) 
- For `emergencyExitVault()`, add a `minAssets` argument and compare it to `vault.redeem()`’s returned amount. [10](#0-9) 
- Reject configured vaults that are empty or lack inflation resistance during initialization and `setVault()`.

### Proof of Concept
The following Foundry PoC uses the existing mainnet-fork fixture in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, which initializes `ProgrammableBorrower` against a live ERC4626 vault and enables programmable-borrower mode. [14](#0-13)  The donation step is shown against the vault’s underlying Morpho market because supplying on behalf of the MetaMorpho vault increases vault assets without minting MetaMorpho shares; for an empty donation-accounting ERC4626, a direct ERC20 donation has the same effect.

```solidity
// Add to test/foundry/ProgrammableBorrowerCreditVault.t.sol
function testProgrammableBorrowerDepositAcceptsManipulatedSharePrice() external {
    address attacker = makeAddr("vaultShareholder");
    uint256 depositAmount = 1; // one underlying unit is enough for a zero-share mint

    // Keep minted-interest mode so the epoch only needs principal movement.
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    // Buffer-period CDO deposit. This amount is sent to ProgrammableBorrower
    // and deposited into the ERC4626 vault by startEpoch().
    idleCDO.depositAA(depositAmount);

    uint256 pbSharesBefore = morphoVault.balanceOf(address(programmableBorrower));
    uint256 supplyBefore = morphoVault.totalSupply();
    uint256 assetsBefore = morphoVault.totalAssets();

    // For a donation-accounting ERC4626, make the next deposit round to zero:
    // shares = depositAmount * supply / (assets + donation) == 0.
    //
    // On MetaMorpho this donation can be performed by supplying directly to
    // Morpho with `onBehalf = address(morphoVault)`, creating a vault-owned
    // market position without minting MetaMorpho shares.
    uint256 donation = depositAmount * supplyBefore + 1;
    deal(USDC, attacker, donation, true);

    bytes32 marketId = morphoVault.withdrawQueue(0);
    IMorpho.MarketParams memory market =
        IMorpho(MORPHO_BLUE).idToMarketParams(marketId);

    vm.startPrank(attacker);
    underlying.approve(MORPHO_BLUE, donation);
    IMorpho(MORPHO_BLUE).supply(
        market,
        donation,
        0,
        address(morphoVault),
        ""
    );
    vm.stopPrank();

    uint256 manipulatedAssets = morphoVault.totalAssets();
    assertGt(manipulatedAssets, assetsBefore);

    // Honest manager transaction: CDO sends the buffered deposit to
    // ProgrammableBorrower, which calls vault.deposit() with no minShares.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    uint256 pbSharesAfter = morphoVault.balanceOf(address(programmableBorrower));
    assertEq(pbSharesAfter, pbSharesBefore, "deposit minted zero vault shares");

    // The borrower no longer holds the deposited cash or a claim on it.
    assertEq(underlying.balanceOf(address(programmableBorrower)), 0);
}
```

The concrete accounting failure is that `epochStartVaultAssets` is set to the pre-deposit asset amount even when `vault.deposit()` returns zero shares, so the lost external-vault claim is not rejected at the boundary. [1](#0-0) [2](#0-1)
