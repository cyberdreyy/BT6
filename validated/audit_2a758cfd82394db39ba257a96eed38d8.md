### Title
Unprotected singleton initializer allows front-running seizure of `global_fee_admin` and fee-destination wallet - (File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs)

### Summary
`init_global_fee_state` creates the program-wide `FeeState` PDA (a singleton derived only from `FEE_STATE_SEED`), and the caller-supplied `admin` and `fee_wallet` arguments are written unconditionally with no authorization check that the caller is the legitimate deployer/upgrade authority. This is the same bug class as the RocketPool `RocketStorage` finding: a temporarily unprotected initializer for a critical global singleton, exploitable by front-running the legitimate setup transaction.

### Finding Description
`InitFeeState` only requires `payer: Signer<'info>` and derives the PDA with `seeds = [FEE_STATE_SEED.as_bytes()]`, `bump`, `payer = payer` [1](#0-0) . The handler writes `admin_key` and `fee_wallet` (both are attacker-controllable arguments) directly into `fee_state.global_fee_admin` and `fee_state.global_fee_wallet` with no `has_one`, `constraint`, or comparison against any known/deployed authority [2](#0-1) . The instruction is exposed permissionlessly in `lib.rs`, documented only as "(Runs once per program)" with no enforced access restriction [3](#0-2) . Because Anchor's `init` constraint only guarantees the PDA doesn't already exist — it does not gate *who* may be the first to create it — any signer able to pay rent can call this instruction before the legitimate deployer does, becoming the permanent `global_fee_admin` and setting `global_fee_wallet` to an address they control. Since `FeeState` is a fixed-seed singleton, once created it can never be re-initialized, permanently locking in the attacker's values (mirroring the original RocketStorage `initialised` bootstrapping bug where the fix was to gate write access until a trusted account finished setup).

Once seized, the attacker (as `global_fee_admin`) has standing authority to call `edit_global_fee_state`, which is protected only by `has_one = global_fee_admin` on the `FeeState` PDA [4](#0-3) , letting them freely redirect `global_fee_wallet`, change all program-wide fee parameters (`bank_init_flat_sol_fee`, `liquidation_flat_sol_fee`, `program_fee_fixed`, `program_fee_rate`, `liquidation_max_fee`, `order_execution_max_fee`, `order_init_flat_sol_fee`), and set `pause_delegate_admin` [5](#0-4) . The values cached from `FeeState` are subsequently pulled into every newly created `MarginfiGroup` via `set_initial_configuration`/`fee_state_cache`, meaning the poisoned fee wallet and rates would be propagated protocol-wide to all future groups [6](#0-5) .

### Impact Explanation
Successful front-running gives the attacker permanent control of the sole `global_fee_admin` role and redirection of the protocol-wide fee wallet — a durable, financially impactful authorization bypass affecting every bank/group's program fees going forward, since `FeeState` cannot be recreated once initialized.

### Likelihood Explanation
This requires only observing the mempool/pending transaction for the deployer's `init_global_fee_state` call (or simply racing to call it before the legitimate deployer, e.g., immediately after program deployment/upgrade when the seed is publicly known/derivable) and submitting a higher-priority transaction with attacker-chosen `admin`/`fee_wallet` arguments — no special privileges, secrets, or existing state are needed, similar to the original RocketStorage race condition.

### Recommendation
Restrict `init_global_fee_state` (and `init_global_fee_state_v2`) to a fixed, hardcoded trusted authority (e.g., verify `payer.key()` against the program's upgrade authority via the `ProgramData` account, or a hardcoded constant pubkey) rather than accepting an arbitrary `admin`/`fee_wallet` from any signer, analogous to the RocketStorage fix of gating writes to a temporary trusted guardian until bootstrapping completes.

### Proof of Concept
1. Deployer deploys/upgrades the marginfi program; the `FeeState` PDA (seed `FEE_STATE_SEED`) does not yet exist.
2. Attacker monitors for the program deployment and, before the deployer's `init_global_fee_state` transaction lands, submits their own transaction calling `init_global_fee_state(admin: attacker_pubkey, fee_wallet: attacker_wallet, ...)` with a higher priority fee.
3. Because `InitFeeState` only requires `payer: Signer`, this succeeds — `fee_state.global_fee_admin = attacker_pubkey` and `fee_state.global_fee_wallet = attacker_wallet` are permanently set [7](#0-6) .
4. The deployer's original `init_global_fee_state` transaction now fails (`init` constraint fails since the PDA already exists), and since it's a singleton there is no recovery path except a program upgrade.
5. The attacker now calls `edit_global_fee_state` at will to redirect fees and manipulate fee parameters for the entire protocol [8](#0-7) .
