### Title
Dust withdrawal request permanently bricks `processWithdrawRequests` for an epoch, freezing all queued withdrawals - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
`IdleCDOEpochQueue.processWithdrawRequests()` computes the epoch withdrawal price as `_underlyingsRequested * ONE_TRANCHE / _pending` and reverts with `Is0()` when the result rounds to zero. Because `requestWithdraw(amount)` accepts arbitrarily small tranche amounts and `_cdo.requestWithdraw()` → `IdleCreditVault.requestWithdraw()` silently returns 0 underlyings for dust requests, a single 1-wei withdrawal request makes the division round to zero and the manager transaction revert. Like the markdown-it-py bug, an unhandled degenerate input (invalid UTF-8 there, a dust denomination here) crashes the processing path — here it permanently DoSes the epoch's withdrawal pipeline.

### Finding Description
In `contracts/IdleCDOEpochQueue.sol`:

- `requestWithdraw(uint256 amount)` (lines 131–143) has no minimum-amount check. Any tranche-token holder can queue `amount = 1` wei for `nextEpoch`, setting `epochPendingWithdrawals[nextEpoch] = 1`.
- `processWithdrawRequests()` (lines 301–329) calls `_cdo.requestWithdraw(_pending, tranche)`, which routes to `IdleCreditVault.requestWithdraw` (`contracts/strategies/idle/IdleCreditVault.sol:243`). For `_pending = 1` wei of an 18-decimal tranche against a 6-decimal underlying (e.g. USDC), the underlyings owed round down to 0, and `IdleCreditVault.requestWithdraw` early-returns `0` without reverting (line 246 `if (_amount == 0) return;` path applies to the converted amount, and no min check exists upstream).
- Back in the queue: `_epochPrice = 0 * ONE_TRANCHE / 1 = 0` → `revert Is0()` (lines 318–321). The whole call reverts, so `epochPendingWithdrawals[_epoch]` is never cleared and `epochWithdrawPrice[_epoch]` is never set.

Because the dust request cannot be removed by anyone except the attacker (`deleteWithdrawRequest` is `msg.sender`-scoped), every subsequent `processWithdrawRequests()` call for that epoch reverts identically. All honest users who queued withdrawals in the same epoch cannot be processed; they must individually call `deleteWithdrawRequest` to recover their tranche tokens and re-queue in a later epoch — a forced, repeatable delay of withdrawals at near-zero attacker cost (~1 wei of tranche tokens per epoch).

### Impact Explanation
Temporary freezing of funds: every withdrawal queued in the targeted epoch is unprocessable while the dust request stands. Victims keep their tranche tokens (recoverable via `deleteWithdrawRequest`) but are denied the withdrawal service for the epoch and must wait at least one additional epoch cycle. The attacker can repeat the attack every epoch for the cost of dust, indefinitely delaying the withdrawal pipeline for all queue users. This is a DoS with direct fund-availability impact, not a pure gas/loop speculation — the revert is deterministic and input-driven.

### Likelihood Explanation
Requires only an unprivileged tranche-token holder (or KYC-passing lender with dust balance) calling `requestWithdraw(1)` during the buffer period. No privileged role, no timing race, no capital at risk. The only mitigating factor is that damage is limited to delayed withdrawals rather than theft, and honest users retain an escape path via `deleteWithdrawRequest`.

### Recommendation
Enforce a minimum withdrawal request size in `IdleCDOEpochQueue.requestWithdraw` (e.g. require the implied underlyings amount to be non-zero), or handle the zero-price case in `processWithdrawRequests` the same way `processWithdrawalClaims` handles the zero-payout case: record a zero-price marker (`isEpochWithdrawZero[_epoch] = true`), clear `epochPendingClaims`, and let users clear their receipts rather than reverting the whole epoch. Alternatively, revert inside `IdleCreditVault.requestWithdraw` when the converted underlying amount is zero so dust requests fail at request time.

### Proof of Concept
```solidity
// Foundry fork test against an AA/BB queue for a 6-decimals underlying vault
function testDustWithdrawRequestBlocksEpochProcessing() external {
    // Setup: vault in buffer period, epochNumber = E, honest user queues a normal withdraw
    _requestWithdrawWithUser(FASA, 1000 * ONE_TRANCHE); // honest queued withdraw for epoch E+1

    // Attacker: any tranche holder queues a 1-wei withdraw for the same epoch
    address attacker = makeAddr("dust-attacker");
    deal(address(tranche), attacker, 1);
    vm.prank(attacker);
    queue.requestWithdraw(1); // epochPendingWithdrawals[E+1] += 1

    // Epoch rolls over; manager tries to process queued withdrawals
    _stopCurrentEpochWithApr(10e18);
    assertEq(strategy.epochNumber(), E + 1);

    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(Is0.selector));
    queue.processWithdrawRequests(); // _underlyingsRequested rounds to 0 -> epochPrice 0 -> Is0

    // Retry is equally impossible; pendingClaims never opens
    assertEq(queue.epochPendingWithdrawals(E + 1), 1000 * ONE_TRANCHE + 1);
    assertFalse(queue.pendingClaims());

    // Honest user's only escape is deleting the request and re-queueing next epoch
    vm.prank(FASA);
    queue.deleteWithdrawRequest(E + 1); // gets tranche tokens back, withdrawal delayed >= 1 epoch
}
```
