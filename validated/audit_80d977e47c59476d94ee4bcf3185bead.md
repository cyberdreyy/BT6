## Title
Stale confirmations from removed members are still counted toward the confirmation threshold, allowing a multisig request to execute below the required number of live signers - (`multisig2/src/lib.rs`)

## Summary
`MultiSigContract::delete_member` only purges the outstanding *requests* that were **created** by the removed member; it does not purge the member's **confirmations** on requests created by other members. `confirm()` later counts `confirmations.len() + 1 >= self.num_confirmations` without verifying that every previously recorded confirmer is still a current member, so a stale confirmation left by a removed member is counted as if it were a live vote, letting a request execute with fewer genuinely live confirmations than `num_confirmations` requires.

## Finding Description
`confirm()` treats the size of the `confirmations` set as the number of valid votes: [1](#0-0) 

`delete_member()` cleans up state for the removed member, but the cleanup of outstanding requests is scoped only to requests *authored* by that member (`r.member == member`); confirmations the member cast on requests authored by *other* members are left untouched in the `confirmations: LookupMap<RequestId, HashSet<String>>` map: [2](#0-1) 

Because `current_member()` is only checked for the account calling `confirm()`/`add_request()` — never re-validated for entries already stored in a request's `confirmations` set — a member's vote recorded before removal remains valid forever for that request.

The invariant that should hold is:
```
confirmed_count(request) == |{ m ∈ confirmations(request) : m ∈ members }|
```
but the code enforces only `confirmed_count(request) == |confirmations(request)|`, which diverges once any confirmer is removed from `members` while their vote is still recorded on a not-yet-executed request.

## Impact Explanation
This is a Critical-class issue per the given impact list: "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`, or any other sensitive multisig action can be executed with fewer genuinely live confirmations than `num_confirmations`, because a removed member's stale vote is silently counted. This can result in unauthorized transfers of NEAR held by the multisig account, or unauthorized privileged actions (e.g. `AddKey`) being approved without the intended quorum of active signers.

## Likelihood Explanation
The only precondition is the ordinary, expected lifecycle of a multisig: a member confirms a pending request, and later (before that request is confirmed to completion) is removed via a `DeleteMember` action — a normal governance operation, not a special/malicious deployment. No attacker privilege beyond being one of the remaining legitimate members confirming the request is required; this makes the bug directly reachable through documented, in-scope multisig operations (`add_request`, `confirm`, `execute_request` → `delete_member`).

## Recommendation
When a member is deleted, also strip that member's entry from the `confirmations` set of every *other* outstanding request (not just requests they authored), or alternatively re-validate membership of each entry in `confirmations` at the time `confirm()` computes the threshold (`confirmations.iter().filter(|m| self.members.contains(m)).count()`).

## Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. Member `A` calls `add_request` to create request `X` (e.g. `Transfer`), without confirming it (`self.requests[X].member == A`, `confirmations[X] == {}`).
3. Member `D` calls `confirm(X)` → `confirmations[X] == {D}` (1 vote, below threshold, not yet executed) — see `confirm()` at [3](#0-2) .
4. Separately, a `DeleteMember { member: D }` request is created and confirmed by 3 of the remaining members (allowed since `members.len() - 1 (=3) >= num_confirmations (=3)`), executing `delete_member(D)`. Because request `X` was authored by `A`, not `D`, the loop in `delete_member` at [4](#0-3)  does not touch it, so `confirmations[X]` still contains `D` even though `D` is no longer in `self.members`.
5. Member `B` now calls `confirm(X)`. `confirmations[X].len() (=1) + 1 == 2 < 3` — one more confirmation is still needed.
6. Member `C` calls `confirm(X)`. Now `confirmations[X].len() (=2) + 1 == 3 >= num_confirmations (=3)`, so `execute_request` runs the `Transfer` — even though only `B` and `C` are genuinely live members who confirmed (`D`'s vote is stale), i.e. only 2 live confirmations authorized an action gated at 3-of-4.

This demonstrates the request executes below the intended live-member threshold, directly mirroring the "cache not rebuilt on removal" class of bug from the external report, applied here to the `confirmations`/`members` binding instead of `operatorCache`/`operators`.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
