One key question remains: in the stopEpoch flow, is `epochNumber` incremented before `collectWithdrawFunds` sets `lossRecoveryPriceByEpoch[epochNumber]`, and under which epoch key receipts are recorded. Let me check the epoch-variant stop flow.### Title
Post-default instant-withdraw receipts bypass the recovery haircut and drain the reserve at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`requestWithdraw` correctly forks post-default requests into the haircut-aware `postDefaultRequests` bucket, but `requestInstantWithdraw` has no such fork. After `finalizeDefaultRecovery`, the CDO can still mint instant-withdraw receipts via `requestInstantWithdraw`, which accumulate into the aggregate `instantWithdrawsRequests[user]`. `claimInstantWithdrawRequest` then pays that aggregate at par through `_transferFundedClaim`, while only the default-epoch keyed entry (`instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`) is routed through the reserve/haircut path. Like the sch_ets bug — where classes that shouldn't be in the round-robin list still got serviced — receipts that are not part of the finalized per-epoch claim list are still paid as if funded.

### Finding Description
In `requestInstantWithdraw` (`IdleCreditVault.sol:356-375`) there is no `defaultRecoveryFinalized` check:

```solidity
function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    _burn(msg.sender, _amount);
    _mint(_user, _amount);
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    pendingInstantWithdraws += _amount;
}
```

After `finalizeDefaultRecovery` sets `defaultRecoveryFinalized = true` and `defaultRecoveryEpoch = epochNumber` (`IdleCreditVault.sol:690-696`), any new instant request is keyed to `currentEpoch`, which is **not** `defaultRecoveryEpoch`. Then in `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`):

```solidity
if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
    _claimDefaultedInstantWithdrawRequest(_user);   // clears only [user][defaultEpoch]
}
uint256 amount = instantWithdrawsRequests[_user];   // aggregate, includes post-default receipts
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);                // pays full amount at par
```

`_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`) only decrements `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`. Receipts created post-default under `epochNumber != defaultEpoch` survive in `instantWithdrawsRequests[user]` and are paid 1:1 from the strategy's underlying balance — the same balance backing `defaultRecoveryReserve` claims. Additionally, `pendingInstantWithdraws` is incremented for these new requests, so `_claimDefaultedInstantWithdrawRequest`'s saturating subtraction (`pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis`) can zero the unfunded-remainder counter using reserve-backed basis, further desynchronizing the accounting.

A related stale-entry variant exists pre-default: unfunded instant receipts from a *prior* epoch remain in `instantWithdrawsRequests`/`pendingInstantWithdraws` but are excluded from `defaultPendingClaimBasis`, which only adds `instantWithdrawClaimsByEpoch[epochNumber]` (`IdleCreditVault.sol:644-649`). After finalization those old receipts are still paid at par by the funded-claim path, while no recovery basis was reserved for them.

### Impact Explanation
An attacker (any KYC-passing lender / tranche holder) can, after borrower default and `finalizeDefaultRecovery`, trigger `requestInstantWithdraw` through the CDO's instant-withdraw path and then `claimInstantWithdrawRequest`. The new receipt — never funded and never haircut — is paid at par, directly draining `defaultRecoveryReserve` that honest defaulted-epoch claimants and post-default requesters rely on. This is direct theft of recovery funds; quantified loss equals the attacker's instant-withdraw amount, up to the full reserve, leaving honest claims permanently underfunded (insolvency for remaining claimants).

### Likelihood Explanation
Requires the pool to have defaulted and recovery to have been finalized (honest manager/owner actions), plus the instant-withdraw path to remain reachable post-default. No attacker-controlled privileged role is needed — the only callables are `_onlyIdleCDO` entry points exercised through normal user instant withdrawals. The missing `defaultRecoveryFinalized` branch in `requestInstantWithdraw` (present in `requestWithdraw` at `IdleCreditVault.sol:247-257`) makes this a systematic accounting gap, not a race.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert, or route the request into `postDefaultRequests`-style accounting paid from the reserve at the finalized haircut. Also ensure `claimInstantWithdrawRequest` only pays epochs that were actually funded — track a per-epoch funded basis rather than paying the aggregate `instantWithdrawsRequests` at par — and include all unfunded instant receipt epochs in `defaultPendingClaimBasis` at finalization.

### Proof of Concept
Foundry fork PoC outline:

1. Deploy `IdleCDOEpochVariant` + `IdleCreditVault` (instant withdraws enabled, `instantDelay` elapsed). Users deposit; epoch starts; borrower draws funds.
2. User A requests an instant withdraw during epoch N (creates `instantWithdrawsRequestsByEpoch[A][N]`, `pendingInstantWithdraws > 0`, unfunded).
3. Epoch N ends without funding the instant queue; borrower defaults (`_handleBorrowerDefault`); owner calls `finalizeDefaultRecovery` with partial recovery → `defaultRecoveryFinalized = true`, `defaultRecoveryEpoch = N`, `defaultRecoveryPrice < 1e18`.
4. Attacker (tranche holder) initiates a new instant withdraw via the CDO → `requestInstantWithdraw` mints a receipt under `instantWithdrawsRequestsByEpoch[attacker][N]`'s successor key and increments `instantWithdrawsRequests[attacker]`.
5. Attacker calls CDO → `claimInstantWithdrawRequest`: `_claimDefaultedInstantWithdrawRequest` clears only `[attacker][defaultRecoveryEpoch]`; the remaining aggregate (the fresh post-default receipt, and in the stale-entry variant user A's old receipt) is paid at par via `_transferFundedClaim` from `defaultRecoveryReserve`.
6. Assert: attacker received full underlying despite `defaultRecoveryPrice < 1`; an honest user's subsequent `claimWithdrawRequest`/`_claimDefaultedWithdrawRequest` reverts on insufficient reserve or pays less than `claimBasis * defaultRecoveryPrice`.

Uncertainty note: the exact internals of `_transferFundedClaim` vs. `_transferDefaultRecovery` (whether they draw from one commingled underlying balance) could not be fully confirmed within the search budget, but `finalizeDefaultRecovery` holds the reserve in the strategy's own underlying balance (`IdleCreditVault.sol:686-709`), so any par payout of unfunded receipts necessarily competes with that reserve.
