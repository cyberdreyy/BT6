### Title
Second withdraw request overwrites `lastWithdrawRequest`, letting a loss-epoch receipt bypass the haircut and claim at par - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The path-traversal analog: `claimWithdrawRequest` locates a loss-adjusted receipt through a single pointer, `lastWithdrawRequest[_user]`, instead of resolving the actual epoch bucket that owns the receipt. Like CWE-22, an attacker-controlled "index" (a newer request epoch) steers the claim logic outside the intended scope: the loss-epoch entry in `withdrawsRequestsByEpoch[_user][lossEpoch]` is never traversed, the haircut in `lossRecoveryPriceByEpoch` is skipped, and the same principal is paid out at par by `_claimFundedWithdrawRequest`.

### Finding Description
`requestWithdraw` records receipts per epoch but keeps only one "latest epoch" cursor:

- `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (IdleCreditVault.sol:282-293).
- On a `stopEpochWithDuration` loss, `collectWithdrawFunds` funds only `pendingBasis * price` and stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (IdleCreditVault.sol:411-421).
- `claimWithdrawRequest` tries the loss-adjusted path via `_claimLossAdjustedWithdrawRequest`, which reads `lossEpoch = lastWithdrawRequest[_user]` and returns 0 if `lossRecoveryPriceByEpoch[lossEpoch] == 0` (IdleCreditVault.sol:789-800), then falls through to `_claimFundedWithdrawRequest`, which pays the aggregate `withdrawsRequests[_user]` at par (IdleCreditVault.sol:319-349).

Attack sequence:

1. During running epoch A, attacker calls `requestWithdraw(X)`: `withdrawsRequestsByEpoch[attacker][A] = X`, `withdrawsRequests[attacker] = X`, `lastWithdrawRequest[attacker] = A`, receipt minted.
2. Epoch A ends via `stopEpochWithDuration(_lossAmount)`: borrower funds only `X * price` (price < `RECOVERY_FULL`); `lossRecoveryPriceByEpoch[A] = price`; `pendingWithdraws` is zeroed.
3. During running epoch A+1, the attacker calls `requestWithdraw(Y)` **without claiming**. `lastWithdrawRequest` is overwritten to A+1; the epoch-A entry remains in `withdrawsRequestsByEpoch` and in `withdrawsRequests`. The code explicitly supports this pattern ("if a user does not claim a withdraw request and instead requests another withdraw…", IdleCreditVault.sol:323-324).
4. Epoch A+1 stops normally; `Y` is funded at par.
5. Attacker calls `claimWithdrawRequest`: `_claimLossAdjustedWithdrawRequest` probes `lossRecoveryPriceByEpoch[A+1]` (= 0, no loss that epoch) and returns; `_claimFundedWithdrawRequest` passes its guard (`epochNumber = A+2 > A+1`) and pays `X + Y` at par, even though only `X*price + Y` was ever funded.

The epoch-A loss receipt was never cleared through `_clearWithdrawClaimForEpoch(_user, A, …)`, so the haircut is permanently escaped.

### Impact Explanation
Direct theft / insolvency: the vault transfers `X` underlying for a receipt backed by only `X*price` funded assets. The shortfall `X*(1 - price)` is drained from the vault's held recovery/funded pool, i.e., from other users' funded withdraw claims or default-recovery reserve. Loss is quantified as `X * (1 - lossRecoveryPrice)` per attacker, repeatable every loss epoch, and first-come claimants are left unbacked (permanent freezing of remaining claims). Invariant broken: loss waterfall — a pending receipt in a loss epoch must settle at `lossRecoveryPriceByEpoch`, not par.

### Likelihood Explanation
Requires only an unprivileged tranche holder: two `requestWithdraw` calls straddling a loss epoch. Loss epochs via `stopEpochWithDuration` are a normal protocol path, and the multi-request flow is explicitly supported. No privileged collusion needed; borrower/manager remain honest — the haircut accounting itself is what leaks.

### Recommendation
Do not key loss-adjusted claims solely off `lastWithdrawRequest`. Iterate or track all epochs with `lossRecoveryPriceByEpoch` set for the user's `withdrawsRequestsByEpoch` entries (e.g., store per-request loss pricing at stop time, or keep a per-user list of unfunded loss epochs), and have `_claimFundedWithdrawRequest` exclude any epoch bucket that carries a nonzero `lossRecoveryPriceByEpoch` until it is settled through `_clearWithdrawClaimForEpoch`.

### Proof of Concept
Foundry fork PoC sketch (based on `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_requestWithdrawWithUser`, `_stopCurrentEpochWithApr`):

```solidity
function testLossEpochReceiptPaysParAfterSecondRequest() external {
    // epoch A running
    _depositWithUser(attacker, 100e6);
    _requestWithdrawWithUser(attacker, X);          // lastWithdrawRequest = A
    // stopEpochWithDuration with loss: only X*price funded
    _stopEpochWithLoss(lossAmount);                 // lossRecoveryPriceByEpoch[A] = price

    // epoch A+1 running: attacker requests again without claiming
    _requestWithdrawWithUser(attacker, Y);          // lastWithdrawRequest overwritten = A+1
    _stopCurrentEpochWithApr(normalApr);            // Y funded at par; epochNumber = A+2

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    // received X + Y at par; funded was X*price + Y
    assertEq(underlying.balanceOf(attacker) - balPre, X + Y);
    // epoch-A bucket never cleared through the loss path:
    assertGt(strategy.withdrawsRequestsByEpoch(attacker, A), 0); // conceptual check
}
```

Expected result: `IdleCreditVault` pays out `X * (1 - price)` more underlying than was funded for the loss-epoch receipt, depleting funds backing other claimants.

One caveat: the exact key used for `lossRecoveryPriceByEpoch` in `collectWithdrawFunds` (`epochNumber` at the moment of the call relative to the `epochNumber += 1` in `deposit`, IdleCreditVault.sol:610) should be confirmed against the `stopEpoch` ordering in `IdleCDOEpochVariant`; the exploit holds as long as a second request can move `lastWithdrawRequest` past the loss-keyed epoch, which the per-epoch mapping design confirms is possible.
