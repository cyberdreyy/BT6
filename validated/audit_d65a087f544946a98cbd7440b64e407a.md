### Title
Instant-withdraw receipts can be claimed at par against other users' funded withdraw reserves because `claimInstantWithdrawRequest` never checks that the request was actually funded - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`requestInstantWithdraw` mints a 1:1 strategy-token receipt and records the request instantly, but no underlying is delivered to the vault until `collectInstantWithdrawFunds` is called by the CDO during epoch stop. `claimInstantWithdrawRequest` then pays the full aggregate `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim`, which only protects `defaultRecoveryReserve` and happily spends any other underlying the strategy happens to hold — including borrower-funded `pendingWithdraws` backing other users' queued withdrawals. An attacker can therefore request an instant withdrawal and immediately claim it against funds reserved for other claimants, leaving them unpayable. This mirrors the CVE class (out-of-bounds memory read/write corrupting unrelated state): the claim path touches a funding bucket it does not own.

### Finding Description

`requestInstantWithdraw` burns the CDO's strategy tokens and mints receipts to the user, incrementing `instantWithdrawsRequests` and `pendingInstantWithdraws`, but transfers no underlying [1](#0-0) . The funding leg is `collectInstantWithdrawFunds`, which pulls underlying from the CDO — it only runs when the epoch is stopped [2](#0-1) .

`claimInstantWithdrawRequest` has no funding, epoch, or delay check in the non-default path — it burns the aggregate request and calls `_transferFundedClaim` [3](#0-2) . `_transferFundedClaim` only shields `defaultRecoveryReserve`; every other underlying balance (notably funds collected via `collectWithdrawFunds` to back `pendingWithdraws` of other users' matured requests) is spendable [4](#0-3) . Note the asymmetry with normal requests: `_claimFundedWithdrawRequest` enforces `epochNumber > lastWithdrawRequest` before paying, precisely so claims only happen after `stopEpoch` funded them [5](#0-4) . No equivalent gate exists for instant requests — the only CDO-side check is the `allowInstantWithdraw` flag [6](#0-5) .

Attack sequence (running epoch, instant withdrawals enabled):
1. Epoch is running; strategy already holds underlying collected at the previous `stopEpoch` to fund user B's matured `pendingWithdraws` receipt (or buffer liquidity).
2. Attacker (any KYC-passing lender) calls CDO `requestInstantWithdraw(amount)`, receiving `amount` receipt tokens with no funding behind them.
3. Attacker calls CDO `claimInstantWithdrawRequest`, which routes to the strategy and transfers `amount` underlying at par — consuming B's funded reserve.
4. When B later calls `claimWithdrawRequest`, `_transferFundedClaim` underflows/reverts: permanent freezing of B's matured claim, or direct theft if B claims nothing.

### Impact Explanation
Direct theft / permanent freezing of other users' funded withdrawal proceeds, equal to the lower of the attacker's instant request size and the strategy's unreserved underlying balance. The "one receipt one payout" and funded-claim isolation invariants are broken: unfunded instant receipts are redeemed against a shared balance earmarked for matured normal claims.

### Likelihood Explanation
Requires `allowInstantWithdraw` enabled and underlying sitting in the strategy at claim time — a routine state between `stopEpoch` funding and user claims (the funding window is exactly when matured claimants are expected to withdraw). The attacker only needs to hold tranche tokens and pass `isWalletAllowed`. Caveat I could not fully verify: the CDO may gate `claimInstantWithdrawRequest` on an `instantDelay`/post-funding timestamp inside `IdleCDOEpochVariant` (grep returned line counts, not bodies); if such a gate enforces "claim only after `collectInstantWithdrawFunds`," severity drops — but the strategy-level absence of any funded/unfunded distinction still means partially funded instant queues are paid at par to first-come claimants while `pendingInstantWithdraws` remains nonzero.

### Recommendation
Track funded vs unfunded instant receipts in `IdleCreditVault`: add a `fundedInstantWithdraws` counter incremented in `collectInstantWithdrawFunds`, and cap the claimable amount in `claimInstantWithdrawRequest` at the funded portion (or store a per-epoch instant funding price like `lossRecoveryPriceByEpoch`). Alternatively, gate claims in the CDO until after the epoch-stop funding call and shortfall-haircut remaining receipts.

function testInstantClaimDrainsFundedReserve() external {
    // Setup: standard epoch variant, allowInstantWithdraw = true,
    // underlying = USDC fork; borrower, manager honest.

    // Epoch N stop: borrower repays; strategy.collectWithdrawFunds pulls
    // underlying to back user B's matured pendingWithdraws receipt.
    _stopCurrentEpochAndFundPendingWithdraws(); // strategy now holds B's funded amount

    // Epoch N+1 running. Attacker deposits, then requests instant withdraw.
    deal(underlying, attacker, attackAmount);
    _depositWithUser(attacker, attackAmount);
    uint256 tranches = IERC20(address(AAtranche)).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(tranches); // mints receipt, pendingInstantWithdraws += X

    // No funding collected for this epoch's instant queue yet.
    // Attacker claims immediately and receives B's funded reserve.
    uint256 balBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - balBefore, 0, "unfunded instant claim paid");

    // User B's matured claim now reverts/underpays.
    vm.prank(userB);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
