### Title
Unbounded, timelock-free `operatorFeeScalar`/`operatorFeeConstant` updates let the SystemConfig owner impose arbitrary extra charges on already-signed transactions - ([File: crates/common/genesis/src/updates/operator_fee.rs])

### Summary
Base's Isthmus operator fee (`operator_fee_scalar`, `operator_fee_constant`) is set via an L1 `SystemConfig` `ConfigUpdate` log and propagated to L2 execution with no upper bound and no delay, mirroring the `BribeVault.setFee` finding: an admin-controlled fee parameter can be set to an extreme value and takes effect immediately for transactions users have already signed/broadcast.

### Finding Description
`OperatorFeeUpdate::try_from` decodes the raw `operator_fee_scalar` (`u32`) and `operator_fee_constant` (`u64`) straight out of the L1 log payload with no range/sanity check, and `OperatorFeeUpdate::apply` writes them unconditionally into `SystemConfig`: [1](#0-0) [2](#0-1) 

These values feed directly into `L1FeeParams::operator_fee_charge_inner`, which multiplies the tx's `gas_limit` by the scalar (times an additional 100x multiplier post-Jovian) plus the constant, with no cap on the result other than saturating arithmetic: [3](#0-2) 

This charge is deducted from the caller up front and enforced as a hard requirement to include the transaction — `ensure_can_pay_fees` in the EVM2 handler (and the equivalent `LackOfFundForMaxFee` check in the mainnet handler) requires `gas_limit*max_fee_per_gas + value + l1_fee + operator_fee` to be covered by the sender's balance: [4](#0-3) [5](#0-4) 

Because the operator fee is not part of the transaction the user signs (it is derived solely from the current `L1BlockInfo`/`SystemConfig` at execution time), the SystemConfig owner can commit a `ConfigUpdate(OperatorFee)` log on L1 that changes `operator_fee_scalar`/`operator_fee_constant` at any time. There is no timelock: the change becomes active for L2 blocks as soon as derivation crosses the epoch containing the update (as demonstrated by `operator_fee_config_update_propagates_to_l1_info`), meaning transactions a user already signed and pushed to the mempool — before ever seeing the new fee — are executed (or fail) under a fee schedule they never agreed to: [6](#0-5) 

There is no protocol-level ceiling equivalent to the "cap fee at e.g. 30%" recommendation from the original report — `operator_fee_scalar` can be set up to `u32::MAX` and `operator_fee_constant` up to `u64::MAX`, and nothing in `SystemConfig`, `OperatorFeeUpdate`, or the execution-side consumers (`crates/common/evm/src/l1block.rs`, `crates/common/evm2/src/handler.rs`) validates or bounds these values.

### Impact Explanation
An operator fee set to a maliciously (or accidentally) large value has two concrete effects analogous to the original finding:
1. Already-signed, already-broadcast transactions can suddenly be charged a drastically larger operator fee than the sender anticipated when they signed the transaction and estimated their required balance, since the fee is computed at execution time, not commit time — this is effectively a "frontrun" of user transactions by a config-level fee change, resulting in unexpected/excessive fund extraction from users into `Predeploys::OPERATOR_FEE_VAULT`.
2. Because the fee has no upper bound, it can be set arbitrarily high, causing previously-fundable transactions to be rejected en masse (`LackOfFundForMaxFee` / `InsufficientFunds`), effectively a chain-wide denial of transaction inclusion, or draining significantly more than expected from callers who do have sufficient balance.

### Likelihood Explanation
This requires the L1 `SystemConfig` owner (a privileged governance key, analogous to the "admin" role in the original report) to emit an `OperatorFee` `ConfigUpdate` log; it is not exploitable by an arbitrary unprivileged actor. However, the code path itself is the same design flaw described in the source report: no protocol-enforced fee ceiling and no timelock/delay between the fee change and its effect on pending user transactions.

### Recommendation
- Enforce a maximum bound on `operator_fee_scalar` and `operator_fee_constant` (e.g., in `OperatorFeeUpdate::try_from`/`apply` or at the point `SystemConfig` values are consumed) so a single governance action cannot impose unbounded extra costs.
- Consider a timelock/delay between when an `OperatorFee` `ConfigUpdate` is committed on L1 and when it becomes active on L2, giving users a window to react, and/or bind the operator fee charged to what was current at the time the transaction was accepted into the pool rather than at execution time.

### Proof of Concept
1. Deploy/activate Isthmus with `operator_fee_scalar = 0`.
2. User signs and broadcasts an EIP-1559 transaction with `gas_limit = G`, funding their balance for `gas_limit*max_fee_per_gas + value` only (no headroom for operator fee), matching the harness pattern in `operator_fee_config_update_propagates_to_l1_info`.
3. Before the transaction is included, the SystemConfig owner emits a `ConfigUpdate(OperatorFee)` log setting `operator_fee_scalar = u32::MAX`, `operator_fee_constant = u64::MAX` (as encoded/tested in `actions/harness/src/l1/miner.rs::enqueue_operator_fee_update`).
4. Once the L2 epoch advances past the L1 block containing that log, `operator_fee_charge_inner` computes a massive additional cost for the pending transaction.
5. The transaction, previously affordable, is now rejected with `InsufficientFunds`/`LackOfFundForMaxFee` (enforced in `ensure_can_pay_fees` / `validate_against_state_and_deduct_caller`), or if the sender happens to have excess balance, is charged far more than they intended toward `Predeploys::OPERATOR_FEE_VAULT` — all without the sender's consent or any opportunity to react, exactly mirroring the "admin can setFee to grief already-settled/pending user actions with no cap and no timelock" pattern from the source finding.

    /// Calculates the operator fee for a given `gas` amount.
    ///
    /// Missing scalars fall back to zero to match the execution path during the
    /// txpool bootstrap window before the first L1 attributes deposit.
    pub fn operator_fee_charge_inner(&self, gas: U256, upgrade: BaseUpgrade) -> U256 {
        let operator_fee_scalar = self.operator_fee_scalar.unwrap_or_default();
        let operator_fee_constant = self.operator_fee_constant.unwrap_or_default();

        let product = if Self::is_enabled(upgrade, BaseUpgrade::Jovian) {
            gas.saturating_mul(operator_fee_scalar)
                .saturating_mul(U256::from(OPERATOR_FEE_JOVIAN_MULTIPLIER))
        } else {
            gas.saturating_mul(operator_fee_scalar) / U256::from(OPERATOR_FEE_SCALAR_DECIMAL)
        };
        product.saturating_add(operator_fee_constant)
    }

    fn ensure_can_pay_fees(
        host: &mut Evm<'_, BaseEvmTypes>,
        envelope: &BaseTxEnvelope,
        caller: Address,
        l1_fee: U256,
        operator_fee: U256,
    ) -> HandlerResult<()> {
        let Some(tx) = envelope.as_standard() else {
            return Ok(());
        };
        if !host.feature(EvmFeatures::FEE_CHARGE) || !host.feature(EvmFeatures::BALANCE_CHECK) {
            return Ok(());
        }
        let required = U256::from(tx.gas_limit())
            .saturating_mul(U256::from(tx.max_fee_per_gas()))
            .saturating_add(tx.value())
            .saturating_add(l1_fee)
            .saturating_add(operator_fee);
        let balance =
            host.state_mut().account(&caller, false).map_err(HandlerError::Fatal)?.balance();
        if balance < required {
            return Err(HandlerError::InsufficientFunds);
        }
        Ok(())
    }

///     Block 4  (ts= 8)     epoch 0  – OLD fee params

///                                     → NEW fee params applied
///   Batched in L1:
///     L1 block 2: batches for L2 blocks 1–5
///     L1 block 3: batch  for L2 block 6
/// ```
///
/// Configuration: all forks through Isthmus are active at genesis so the
