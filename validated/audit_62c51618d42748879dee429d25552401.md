### Title
Stale confirmations from revoked multisig members still count toward the confirmation threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
When a multisig key (`multisig`) or member (`multisig2`) is revoked via a `DeleteKey`/`DeleteMember` request, the contract only purges *other pending requests originally created by* that key/member. It never scans the `confirmations` set of *other* requests to strip out a confirmation the revoked key/member had already cast as a co-signer (not as the originator). That confirmation remains valid and still counts toward `num_confirmations` for the still-pending request, so a request can later execute having received fewer confirmations from *currently authorized* members than the configured threshold.

### Finding Description
In `multisig/src/lib.rs`, `execute_request`'s `DeleteKey` branch removes only requests whose `signer_pk` (the original creator) matches the deleted key: [1](#0-0) 

Similarly, in `multisig2/src/lib.rs`, `delete_member` filters requests by `r.member == member`, again matching only the original requester, not co-confirmers: [2](#0-1) 

Meanwhile, `confirm()` simply checks the raw size of the `confirmations` set against `num_confirmations`, with no re-validation that every entry in that set is still a live member/key at execution time: [3](#0-2) [4](#0-3) 

The intended invariant is: `count(confirmations for request R) == count(confirmations from members who are still authorized signers)`. Because revocation only cleans up requests *created by* the removed key/member and never scans other requests' `confirmations` sets for entries belonging to that key/member, this invariant breaks — a confirmation from an already-revoked signer persists and is counted toward the threshold on execution.

### Impact Explanation
This matches the Critical impact category "a multisig request executed below threshold": a transaction can be executed on behalf of the multisig account (transferring NEAR, deploying code, adding/deleting keys, etc.) using fewer *currently valid* confirmations than `num_confirmations` actually requires, because one or more of the counted confirmations belong to a member/key that has since been removed. This is an authorization-boundary violation — the multisig's core guarantee (K-of-N live signers must approve) is broken.

### Likelihood Explanation
Exploitation only requires ordinary multisig usage patterns already supported by the contract: a member who is a co-signer on one or more pending requests but not their originator, and who is later revoked (e.g., a departing team member, a compromised key being rotated out, or a malicious member who confirms requests then gets removed). No special privilege beyond being (formerly) a legitimate member is required, and the remaining members have no visibility that a "confirmation" they're counting on already belongs to a revoked signer, since `get_confirmations`/`get_num_confirmations` still report it.

### Recommendation
When executing `DeleteKey`/`DeleteMember`, iterate over the `confirmations` map for *all* pending requests (not just requests the target originated) and remove the revoked key's/member's confirmation entry, decrementing tracked counts accordingly. Alternatively, at `confirm()`/execution time, filter the `confirmations` set to only currently valid members before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig initialized with members `{A, B, C}`, `num_confirmations = 2`.
2. `A` calls `add_request` for a sensitive `FunctionCall`/`Transfer` request `R` (not yet executable, 0 confirmations).
3. `B` calls `confirm(R)` — `R.confirmations = {B}` (1 of 2).
4. Members submit and confirm a separate request `DeleteMember { member: B }` (or `DeleteKey`), which passes and executes — `delete_member`/execute_request DeleteKey only removes requests *created by* `B`; `R` (created by `A`) is untouched, and `R.confirmations` still contains `B`.
5. `C` calls `confirm(R)` — `R.confirmations.len() + 1 = 2 >= num_confirmations`, so `execute_request(R)` runs, even though only `A`'s absence of confirmation and `C`'s confirmation come from currently valid members plus a stale confirmation from the now-removed `B` — effectively 1 live confirmation (`C`) plus a phantom one (`B`) satisfied the 2-of-3 threshold.             "Already confirmed this request with this key"
        );

        } else {

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);

        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
