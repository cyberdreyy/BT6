### Title
Stale confirmations from deleted multisig members are still counted toward the execution threshold - ([File: multisig2/src/lib.rs])

### Summary
`DeleteMember` in the `multisig2` contract only purges pending *requests that the removed member itself created*; it never scans `self.confirmations` for other pending requests that the removed member had already *confirmed*. Because the removed member's vote remains in the `HashSet<String>` for those other requests, `confirm()` can later reach `num_confirmations` using fewer live, current members than the configured threshold — breaking the K-of-N custody binding the contract is supposed to enforce.

### Finding Description
`confirm()` counts votes purely from the `confirmations` map keyed by `member.to_string()`, and executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

`delete_member()`, invoked from `execute_request` for the `DeleteMember` action, removes the member from `self.members` and cleans up only the requests where that member was the *original requester* (`r.member == member`). It never removes the member's entry from `self.confirmations` for requests created by *other* members: [2](#0-1) 

The `confirmations` set stores plain `String` identities with no link back to `self.members`, and nothing in `confirm()` re-validates that every entry in `confirmations` still corresponds to a current member: [3](#0-2) [4](#0-3) 

Sequence:
1. `num_confirmations = 3`, members = {A, B, C, D}.
2. Member A calls `add_request_and_confirm` (or confirms) on request R (created by, say, B). `confirmations[R] = {A}`.
3. Members vote through a separate `DeleteMember{A}` request (with 3 live confirmations from B, C, D). `delete_member` removes A from `self.members`; R is untouched because `r.member == B`, not A. `confirmations[R]` still contains `"A"`.
4. Now only {B, C, D} are legitimate members, and the threshold is still 3-of-3 (or whatever K was set), but R's confirmation set already has A's stale vote.
5. B confirms R → `confirmations.len()==1(A)+1(B)=2`, not yet enough. C confirms R → `len()==2+1=3 >= 3` → `execute_request(R)` fires with only **B and C** as live confirmers, i.e., 2 live votes counted as 3.

This directly breaks the binding: `confirmations_counted == live_members_who_approved`. After the fix should be true, but the bug lets `confirmations_counted > live_members_who_approved`.

### Impact Explanation
This allows a multisig request to be executed with fewer live-member confirmations than `num_confirmations` requires, i.e. "a multisig request executed below threshold" — explicitly listed as Critical impact. Since `MultiSigRequestAction` includes `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, `DeployContract`, an attacker who can arrange for a stale confirmation to exist on a pending high-value request (e.g., a `Transfer` of the contract's NEAR balance) can get it executed with one fewer live approver than the configured policy, moving NEAR without proper authorization.

### Likelihood Explanation
This does not require any external validator/RPC compromise, redeploy, or key theft — it is a straightforward sequencing bug reachable purely through the contract's normal, documented operations (`add_request`, `confirm`, and the standard `DeleteMember` governance action). Any coalition of members can trigger it deliberately, or it can happen incidentally in normal member-rotation workflows (a common operational event), making it not merely theoretical.

### Recommendation
When removing a member in `delete_member`, iterate over all pending `self.requests` (not just those authored by the removed member) and strip the removed member's entry from the corresponding `self.confirmations` set, e.g.:
```rust
for (request_id, _) in self.requests.iter() {
    if let Some(mut confs) = self.confirmations.get(&request_id) {
        if confs.remove(&member.to_string()) {
            self.confirmations.insert(&request_id, &confs);
        }
    }
}
```
Alternatively, validate at `confirm()` time that every entry counted in `confirmations.len()` still corresponds to a member in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
```
// num_confirmations = 3, members = {A, B, C, D}
add_request(R) by B                     // confirmations[R] = {}
confirm(R) as A                          // confirmations[R] = {A}, len=1 < 3

// Separate governance request to remove A, confirmed by B, C, D (3-of-4)
add_request(DeleteMember{A})
confirm as B / C / D -> executes delete_member(A)
   -> self.members no longer contains A
   -> confirmations[R] still == {A}   // BUG: not cleaned

confirm(R) as B                          // confirmations[R] = {A, B}, len=2 < 3
confirm(R) as C                          // confirmations[R] = {A, B, C}, len=3 >= 3
   -> execute_request(R) fires with only B and C as live confirmers
   -> R (e.g., a Transfer action) executes despite only 2 of the 3 required *live* confirmations
```

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
