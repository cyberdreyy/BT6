Confirmed. Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` exhibit the same flaw: when a member/key is removed via `DeleteKey`/`DeleteMember`, only that member's *own* requests and their confirmations are purged (`self.requests.iter().filter(...r.signer_pk == pk...)` in multisig, `r.member == member` in multisig2). Confirmations that a departing member previously cast on *other* still-pending requests (originated by other members) are never scrubbed from the `confirmations` set for that `request_id`. `confirm()` counts quorum purely from `confirmations.len()`, with no re-validation that each entry is still a current member [1](#0-0) , so a stale confirmation from a now-removed member still counts toward `num_confirmations`, letting a request execute with fewer live-member approvals than the configured threshold.

### Title
Stale confirmations from removed multisig members still count toward quorum, allowing request execution below the live-member threshold - (File: `multisig2/src/lib.rs`, also present in `multisig/src/lib.rs`)

### Summary
`delete_member` (multisig2) / the `DeleteKey` action (multisig) only clean up requests *originated* by the removed member; they do not scrub that member's confirmations from other pending requests. `confirm()` then trusts the raw size of the stored `confirmations` set to decide when `num_confirmations` has been reached, without checking that each confirming identity is still in `self.members` (multisig2) or still holds an active key (multisig1).

### Finding Description
- `delete_member` only filters requests where `r.member == member` (the request's original signer) and removes those: [2](#0-1) 
- It does not scan the `confirmations` map for *other* requests where the removed member had already cast a confirmation, so those entries remain.
- `confirm()` computes quorum as `confirmations.len() as u32 + 1 >= self.num_confirmations` purely from the stored `HashSet<String>` size: [3](#0-2) 
- There is no invariant re-checked at execution time that every string in `confirmations` corresponds to a member still present in `self.members`.
- The identical pattern exists in the older `multisig` contract, where `DeleteKey` only removes requests keyed by `r.signer_pk == pk` and leaves stale entries in other requests' `confirmations` sets, while `confirm()` again just counts `confirmations.len()`: [4](#0-3) 

This breaks the intended binding "confirmations counted == confirmations from currently-live members." A confirmation cast while a member was still valid remains counted forever, even after that member is deleted, as long as the request itself isn't touched by the deletion path.

### Impact Explanation
This allows a multisig request (e.g. a `Transfer` of NEAR funds, an `AddKey`/`AddMember` granting new access, or a `DeployContract` upgrade) to reach and cross the `num_confirmations` threshold and execute even though the number of genuinely live, authorized members currently agreeing is below the configured threshold. This is a request executed with fewer than the required live confirmations, which is an unauthorized action against the multisig's core security guarantee (K-of-N authorization), matching the Critical impact class "a multisig request executed below threshold."

### Likelihood Explanation
The precondition is a normal, expected operational sequence with no special privilege beyond being an existing member at the time of confirming: (1) a member confirms request A while still a member, (2) that member is later removed via a `DeleteMember`/`DeleteKey` request (routine key rotation/offboarding), (3) request A (unrelated to the removed member) is still pending and gets one more confirmation from a remaining member, crossing threshold using the stale confirmation as one of the counted votes. No attacker needs elevated privileges beyond normal multisig membership at confirmation time, and member turnover is a realistic, common lifecycle event for these contracts.

### Recommendation
When removing a member/key, iterate over all pending requests' confirmation sets (not just the requests the member itself created) and strip the removed member's identity from each. Alternatively/additionally, `confirm()` should re-validate at execution time that all entries in the `confirmations` set still correspond to current `members` before counting them toward `num_confirmations`.

### Proof of Concept
1. Initialize a multisig with 3 members `A`, `B`, `C` and `num_confirmations = 2`.
2. `A` calls `add_request` to create request `R` (e.g. `Transfer` funds to some address).
3. `A` calls `confirm(R)` — 1 confirmation stored, request not yet executed.
4. A separate request `D` is created and confirmed by `A`, `B`, `C` to `DeleteMember { member: A }` (reaching threshold 2, e.g. confirmed by `B` and `C`); `A` is removed from `self.members`, and `delete_member` only cleans requests where `r.member == A` — since `R`'s originating member field may be `A` too if `A` created it, but consider instead that `A` merely *confirmed* (not created) some other pending request `R2` created by `B`. `delete_member(A)` does not touch `R2`'s confirmations, so `A`'s confirmation on `R2` survives.
5. `C` (a live member) later calls `confirm(R2)`. `confirmations.len()` for `R2` is now 2 (`A`'s stale entry + `C`'s new one), meeting `num_confirmations = 2`, so `R2` executes — even though only one currently-live member (`C`) actually approved it, below the intended 2-live-member threshold.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
