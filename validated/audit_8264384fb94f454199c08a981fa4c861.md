### Title
Interest rate config changes are applied retroactively over unsettled accrual time - ([File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs])

### Summary
`lending_pool_configure_bank` and `lending_pool_configure_bank_interest_only` update `bank.config.interest_rate_config` in place without first "settling" the interest owed for the period since `last_update` under the *old* rate curve. The next time `accrue_interest` runs, the entire elapsed `time_delta` (which may span a long period under the old config) is charged/credited using the *new* rate curve, mispricing interest and fees for that whole window. This mirrors the Gondi `M-15` bug class: a duration-dependent state variable (`last_update` / accrued-but-unsettled interest) is not recalculated/settled when its governing config parameter changes, so newly-set parameters are prematurely applied over a stale time window.

### Finding Description
`Bank::accrue_interest` computes interest for the whole gap between `self.last_update` and the current timestamp using a single `InterestRateCalc` built from the bank's *current* `interest_rate_config`: [1](#0-0) [2](#0-1) 

There is no concept of splitting `time_delta` across rate-curve boundaries; the whole delta is charged at whatever `interest_rate_config` happens to be in effect at the moment `accrue_interest` executes.

Both admin config-update entry points mutate `interest_rate_config` directly without calling `accrue_interest` beforehand to settle the pending period under the old curve:

- `lending_pool_configure_bank` → `Bank::configure`, which calls `self.config.interest_rate_config.update(ir_config)` with no preceding accrual: [3](#0-2) [4](#0-3) 

- `lending_pool_configure_bank_interest_only` behaves identically: [5](#0-4) 

By contrast, other bank-mutating flows (e.g. `lending_pool_emissions_deposit`) are careful to call `bank.accrue_interest(...)` immediately before mutating economically sensitive state: [6](#0-5) 

This pattern is missing from both configure-bank paths. If a bank goes untouched (no deposit/borrow/withdraw/repay/liquidate) for a period, `last_update` stays stale. If the admin (or `delegate_curve_admin`) changes the interest curve during that stale window, the next `accrue_interest` call (triggered permissionlessly by any user action or `lending_pool_accrue_bank_interest`) will apply the *new* curve retroactively across the *entire* stale `time_delta`, not just from the moment of the config change onward.

### Impact Explanation
This causes an exploitable misvaluation of accrued interest and fees:
- If rates are raised, borrowers suddenly owe more interest than they should for time that already elapsed under the old (lower) rate — an unexpected, retroactive liability increase that can push previously-healthy accounts into liquidation.
- If rates are lowered, depositors receive less yield than the old config entitled them to for the elapsed period, and protocol/insurance fee components configured differently can also be mis-collected for time that occurred under the old fee schedule.
- Because `accrue_interest` triggers on ordinary user actions (deposit/borrow/repay/withdraw/liquidate) as well as the permissionless `lending_pool_accrue_bank_interest` instruction, any unprivileged user can trigger the incorrect retroactive accrual simply by interacting with the bank after the admin changes the curve — the miscalculation is not gated behind any privileged action, it is baked into the shared bank state and surfaces on the next permissionless-or-user-triggered accrual.
- The magnitude of the misvaluation scales with how long the bank has been idle (`time_delta`) and the magnitude of the rate-curve change, and directly redistributes value between lenders/borrowers/fee recipients in a way none of them agreed to for that period.

### Likelihood Explanation
Likelihood is moderate-to-high: interest rate configuration changes are routine admin operations (rebalancing curves, adjusting fees), and marginfi banks frequently see periods with no activity (illiquid/low-volume banks, isolated-risk assets, newly listed banks). Any subsequent permissionless accrual call (via `lending_pool_accrue_bank_interest` or ordinary user actions) will trigger the mispriced retroactive accrual without any special conditions or race required — it only requires an admin config change followed by the ordinary passage of time and the bank's next state-touching transaction.

### Recommendation
Before applying an interest-rate config update, force an accrual against the *current* config so `last_update` is caught up to `now` and any interest through that point is settled under the old rate:
```rust
// in lending_pool_configure_bank / lending_pool_configure_bank_interest_only
let clock = Clock::get()?;
let group = ctx.accounts.group.load()?;
bank.accrue_interest(clock.unix_timestamp, &group, /* bank key if needed */)?;
// ... then apply bank.configure(&bank_config) / interest_rate_config.update(...)
```
This ensures the old curve only ever applies to the time period during which it was actually in effect, and the new curve only applies going forward from the moment of the config change, eliminating retroactive mispricing — directly analogous to the Gondi fix of settling/recalculating dependent state at the point of config change rather than allowing it to be silently carried forward.

### Proof of Concept
1. Admin creates a bank with interest curve A (e.g. low borrow APR) and users deposit/borrow, establishing `last_update = T0`.
2. Bank sees no further deposit/borrow/withdraw/repay/liquidate/accrue-interest activity for a long period (e.g. 30 days) — `last_update` remains `T0`.
3. Admin (via `lending_pool_configure_bank_interest_only`, gated only by `delegate_curve_admin`) changes the interest curve to B with a much higher borrow APR, without any accrual happening first:
   - `programs/marginfi/src/instructions/marginfi_group/configure_bank_lite.rs` lines 12-35 directly mutate `bank.config.interest_rate_config` from A to B; `last_update` is untouched.
4. Any user (e.g. a borrower, or an unrelated third party calling the permissionless `lending_pool_accrue_bank_interest`) triggers `accrue_interest` at `T0 + 30 days`.
5. `accrue_interest` computes `time_delta = 30 days` and calculates the *entire* 30 days of interest using curve B (the new, higher rate), even though curve A was in effect for essentially all of that period — see `programs/marginfi/src/state/bank.rs` lines 511-564, where `time_delta` and the newly-updated `self.config.interest_rate_config` are combined without any per-period splitting.
6. Borrowers now owe interest computed at curve B's higher rate for the full 30-day window instead of curve A's lower rate, an unexpected and unauthorized retroactive increase in their liability that could not have been anticipated or hedged against.

        // Settings are not frozen, everything updates

pub fn lending_pool_configure_bank_interest_only(
    ctx: Context<LendingPoolConfigureBankInterestOnly>,
    interest_rate_config: InterestRateConfigOpt,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;
    msg!(
        "Configuring bank: {:?} mint: {:?}",
        ctx.accounts.bank.key(),
        bank.mint
    );

    // If settings are frozen, interest rates can't update.
    if bank.get_flag(FREEZE_SETTINGS) {
        msg!("WARN: Bank settings frozen, did nothing.");
    } else {
        bank.config
            .interest_rate_config
            .update(&interest_rate_config);
        bank.config.interest_rate_config.validate()?;
        msg!("Bank configured!");
    }

    Ok(())
}
