### Title
Loss-adjusted withdraw receipts are paid at par when the user requests again in a later epoch, draining other claimants' funded recovery - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `collectWithdrawFunds` partially funds pending receipts, the shortfall is recorded per request epoch in `lossRecoveryPriceByEpoch[epochNumber]`. The claim path, however, only consults `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If the same wallet makes any later withdraw request, `lastWithdrawRequest` is overwritten with the newer epoch, the older loss-adjusted receipt is never routed to the haircut path, and the full aggregate `withdrawsRequests[_user]` is paid at par through `_claimFundedWithdrawRequest`. An unprivileged lender can therefore escape the loss socialization and withdraw more underlying than the strategy reserved, leaving other epoch-N claimants permanently unable to claim.

### Finding Description
The flow:

1. User requests a normal withdraw in epoch N (`requestWithdraw` → `IdleCreditVault.requestWithdraw`). `withdrawsRequestsByEpoch[user][N] += amount`, `withdrawsRequests[user] += amount`, `lastWithdrawRequest[user] = N`, and the user holds a strategy-token receipt minted 1:1 (`_mint(_user, _amount)`) (IdleCreditVault.sol:271-294).
2. At `stopEpochWithDuration(_lossAmount)` the borrower repays less than `pendingWithdraws`. `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[N] = _amount * 1e18 / pendingBasis` and sets `pendingWithdraws = 0`, while the strategy receives only the haircut `_amount` of underlying for all epoch-N receipts (IdleCreditVault.sol:411-429).
3. In a later buffer period (epoch N+1), the same user calls `requestWithdraw` again with remaining tranche tokens. `lastWithdrawRequest[user]` is overwritten to N+1 and `withdrawsRequests[user]` now aggregates both epochs' basis.
4. Epoch N+1 ends fully funded (`_amount >= pendingBasis`), so no entry in `lossRecoveryPriceByEpoch[N+1]`.
5. The user calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` = `lossRecoveryPriceByEpoch[N+1]` = 0 and returns 0 (IdleCreditVault.sol:789-795). The epoch-N haircut entry is never looked up.
   - `_claimFundedWithdrawRequest` then pays `amount = normalAmount + apr0...` where `normalAmount = withdrawsRequests[user]` includes the entire epoch-N basis at par (IdleCreditVault.sol:338-349).

The strategy only holds `N_amount * recoveryPrice + N+1_amount` in underlying for this user's two receipts, but it pays out `N_amount + N+1_amount`. The difference is taken from underlying that was funded for other epoch-N claimants. The last of those claimants later hits `_transferFundedClaim`'s `balance - reserve < _amount` revert (or an ERC20 transfer failure) and their haircut share is permanently unclaimable.

The `epochNumber <= lastWithdrawRequest` freshness gate does not help: after epoch N+1 stops, `epochNumber > lastWithdrawRequest` passes normally. `_clearWithdrawClaimForEpoch` is never reached for epoch N because the loss-adjusted path keyed off the overwritten `lastWithdrawRequest`.

### Impact Explanation
Direct theft plus permanent freezing of unclaimed funds. The attacker extracts the loss portion that should have been socialized across all epoch-N receipt holders. Quantified loss equals `N_amount * (1 - lossRecoveryPrice)` per attacker receipt, up to the entire unfunded remainder of the loss-adjusted epoch; other claimants' residual claims revert forever once the strategy balance is drained.

### Likelihood Explanation
Requires (a) an epoch ending via `stopEpochWithDuration` with a partial repayment (a legitimate, manager-invoked loss event), and (b) the attacker holding additional tranche tokens to place a second withdraw request in a later epoch — both routine user actions. No privileged cooperation, no default, no timing race. Any user with positions across two epochs satisfies the precondition accidentally, and a deliberate attacker can split deposits specifically to exploit it.

### Recommendation
Track all loss-adjusted epochs per user, not just `lastWithdrawRequest`. Options:
- In `_claimLossAdjustedWithdrawRequest`, iterate or store a per-user list/bitmap of epochs with nonzero `lossRecoveryPriceByEpoch` where `withdrawsRequestsByEpoch[user][epoch] != 0`, and clear each haircut claim before paying the funded remainder.
- Alternatively, at `collectWithdrawFunds` time, move haircut receipt basis out of `withdrawsRequests[user]`/`withdrawsRequestsByEpoch` into a separate loss-claim mapping so the funded-claim path can never pay them at par.
- At minimum, revert in `requestWithdraw` when the user has an unsettled receipt in an epoch with `lossRecoveryPriceByEpoch != 0`.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testPocLossAdjustedReceiptPaidAtPar() external {
    // Setup: deposits by attacker and victim, epoch 0 runs and stops normally.
    idleCDO.depositAA(10_000 * ONE_SCALE);                 // attacker
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);    // victim AA
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // Both request normal withdraws in epoch 1 (attacker uses only half so
    // they keep tranche tokens for the second request).
    uint256 reqAttacker = cdoEpoch.requestWithdraw(
        IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(1);

    // stopEpochWithDuration with a loss: borrower repays only a fraction of
    // pendingWithdraws -> lossRecoveryPriceByEpoch[1] < 1e18.
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 lossAmount = pendingBasis / 2; // 50% loss on pending receipts
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), type(uint256).max);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, epochDuration, lossAmount);
    uint256 price = strategy.lossRecoveryPriceByEpoch(1);
    assertGt(price, 0);
    assertLt(price, 1e18);

    // Attacker requests again in epoch 2 -> lastWithdrawRequest overwritten to 2.
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch()); // fully funded

    // Claim: loss-adjusted path misses epoch 1 (lastWithdrawRequest == 2),
    // funded path pays the WHOLE aggregate at par.
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // Attacker received epoch-1 basis at par instead of haircut.
    assertEq(paid, reqAttacker + req2);          // overpayment of reqAttacker*(1-price)

    // Victim's haircut claim now reverts: strategy balance < reserved claim.
    vm.prank(victim);
    vm.expectRevert();                            // _transferFundedClaim NotAllowed / ERC20 revert
    cdoEpoch.claimWithdrawRequest();
}
```
