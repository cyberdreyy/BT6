### Title
External ERC4626 liquidity withdrawal can revert `stopEpoch` and freeze programmable-pool withdrawals - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
In programmable-borrower mode, `IdleCDOEpochVariant._stopEpoch` delegates liquidity provisioning to `ProgrammableBorrower.onStopEpoch` before pulling funds for matured withdrawal receipts. [1](#0-0)  If the borrower has enough ERC4626 share value to cover the shortfall but the vault lacks immediately withdrawable liquidity, `vault.withdraw` is attempted and its failure reverts `StopEpochVaultLiquidityUnavailable`, propagating the revert through `stopEpoch`. [2](#0-1) 

### Finding Description
At epoch start, the programmable borrower deposits idle underlying into the configured ERC4626 vault and records the epoch accounting baseline. [3](#0-2)  During a normal programmable stop, IdleCDO requests cash only for `pendingWithdraws` because programmable deployments use minted-interest accounting. [4](#0-3)  `onStopEpoch` compares the cash shortfall with the borrower’s share value and returns `true` when the shares cannot economically cover the shortfall, allowing IdleCDO’s later transfer failure to enter the default path. [5](#0-4)  However, when the shares are economically sufficient, the function calls `vault.withdraw`; a liquidity-based vault revert is converted into `StopEpochVaultLiquidityUnavailable` instead of returning `false`. [6](#0-5) 

Because `stopEpoch` only treats a `false` return as a default and does not catch the hook revert, the entire stop transaction fails. [7](#0-6)  An unprivileged user of the same ERC4626 vault can create this condition by publicly withdrawing or otherwise consuming the vault’s liquid underlying until available liquidity is below the pool’s required withdrawal amount, while the programmable borrower’s shares still value above that amount.

### Impact Explanation
This is a temporary freezing of user funds equal to the amount IdleCDO must source at stop: normally `pendingWithdraws`, and on a close-pool stop the recalled principal plus pending liabilities. [8](#0-7)  For example, if the programmable borrower must source 1,000,000 underlying for matured receipts and the ERC4626 vault has only 900,000 liquid underlying while the borrower’s shares remain worth more than 1,000,000, every `stopEpoch` call reverts until at least 100,000 liquidity returns. The freeze duration is bounded by the external vault’s liquidity restoration rather than by an epoch timer, because retrying `stopEpoch` reaches the same reverting `vault.withdraw` path while the shortage persists. [6](#0-5) 

### Likelihood Explanation
The attacker does not need a privileged role, borrower access, Keyring status, or a tranche position; they only need the ability to use the external ERC4626 vault and reduce its withdrawable liquidity. The prerequisites are a programmable-borrower deployment, an active epoch with a stop-time cash requirement greater than the borrower’s on-hand underlying, and a vault state where liquid underlying is below that requirement but share value is not. Those exact conditions are distinguished in `onStopEpoch`: insufficient economic share value returns `true`, while economically covered withdrawal failure reverts. [2](#0-1) 

### Recommendation
Treat a covered `vault.withdraw` liquidity failure consistently with insufficient share value: return `false` or otherwise let IdleCDO execute its default/loss path instead of reverting. Alternatively, wrap `vault.withdraw`, detect the realized shortfall, and surface a bounded recoverable state that cannot repeatedly block the entire epoch transition; if retryability is intended, document that external-vault liquidity is a liveness dependency and consider a separate privileged fallback after a defined grace period.

### Proof of Concept
```solidity
// Foundry fork test outline for a live programmable-borrower deployment.
function test_ERC4626LiquidityShortageFreezesStopEpoch() public {
    // Existing forked deployment.
    IdleCDOEpochVariant cdo = IdleCDOEpochVariant(CDO);
    IdleCreditVault creditVault = IdleCreditVault(cdo.strategy());
    ProgrammableBorrower pb = ProgrammableBorrower(creditVault.borrower());
    IERC20Detailed underlying = IERC20Detailed(cdo.token());
    IERC4626 externalVault = pb.vault();

    address lp = makeAddr("lp");
    address vaultLp = makeAddr("external-vault-lp");

    // 1. LP deposits and creates a normal pending withdrawal during buffer.
    uint256 depositAmount = 1_000_000e6;
    deal(address(underlying), lp, depositAmount);
    vm.startPrank(lp);
    underlying.approve(address(cdo), depositAmount);
    cdo.depositAA(depositAmount);
    cdo.requestWithdraw(0, cdo.AATranche());
    vm.stopPrank();

    uint256 required = creditVault.pendingWithdraws();
    assertGt(required, 0);

    // 2. Start the epoch; ProgrammableBorrower deposits idle cash into the ERC4626 vault.
    vm.prank(cdo.owner());
    cdo.startEpoch();
    assertEq(underlying.balanceOf(address(pb)), 0);

    // 3. As an unprivileged user of the same ERC4626 vault, drain liquid
    //    underlying while PB's shares still economically cover `required`.
    //    On a fork this is done by redeeming pre-acquired vault shares or
    //    consuming the vault's public liquidity source.
    uint256 liquidBefore = underlying.balanceOf(address(externalVault));
    uint256 pbShareValue = externalVault.convertToAssets(externalVault.balanceOf(address(pb)));
    assertLt(liquidBefore, required);
    assertGe(pbShareValue, required);

    vm.prank(vaultLp);
    externalVault.redeem(
        externalVault.balanceOf(vaultLp),
        vaultLp,
        vaultLp
    );

    assertLt(underlying.balanceOf(address(externalVault)), required);
    assertGe(externalVault.convertToAssets(externalVault.balanceOf(address(pb))), required);

    // 4. Honest manager attempts to settle the epoch. The hook reaches
    //    vault.withdraw(shortfall), the vault reverts for liquidity, and the
    //    whole stopEpoch call reverts instead of defaulting or settling.
    vm.warp(cdo.epochEndDate() + 1);
    vm.prank(creditVault.manager());
    vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
    cdo.stopEpoch(0, 0);

    // 5. Funds remain frozen: the epoch is still running and the receipt cannot be claimed.
    assertTrue(cdo.isEpochRunning());
    vm.prank(lp);
    vm.expectRevert();
    cdo.claimWithdrawRequest();
}
```
