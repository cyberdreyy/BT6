### Title
Epoch-key off-by-one lets withdraw/instant receipts escape loss and default haircuts — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The `IdleCreditVault` records withdraw and instant-withdraw receipts under the *request* epoch (`epochNumber` at request time), but both `lossRecoveryPriceByEpoch` and `defaultRecoveryEpoch` are keyed under the epoch counter *after* `deposit()` has already incremented `epochNumber` during `stopEpoch`. Because the claim paths look up receipts and haircut prices with mismatched epoch keys, a receipt that should be loss-adjusted or default-haircut falls through to the at-par funded claim path, letting an attacker withdraw the full amount while honest claimants absorb the loss. This is the closest analog to CVE-2020-5221: a "path" (receipt epoch) escapes its intended confinement boundary (the epoch's haircut) and reaches funds it should never touch.

### Finding Description
- Receipts are keyed by request epoch: `requestWithdraw` sets `lastWithdrawRequest[_user] = epochNumber` and `withdrawsRequestsByEpoch[_user][epochNumber]`, and `requestInstantWithdraw` sets `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` (lines 282–293, 367–374).
- `deposit()` increments `epochNumber` whenever it is called while `isEpochRunning()` is true — i.e., the strategy-token mint that happens inside `stopEpoch`/`stopEpochWithDuration` bumps the counter *before* the loss/default bookkeeping lands (lines 607–611). Confirmed by tests: `epochNumber` is `1` immediately after the first `stopEpoch` (`test/foundry/IdleCreditVault.t.sol:5756`).
- `collectWithdrawFunds` therefore stores the haircut as `lossRecoveryPriceByEpoch[epochNumber]` under the *post-increment* epoch (line 421), while `lastWithdrawRequest[_user]` still points at the *pre-increment* epoch. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 790–791), gets `0`, and returns early — so the claim proceeds to `_claimFundedWithdrawRequest`, which pays the full `withdrawsRequests[_user]` at par (lines 338–349).
- The same mismatch hits defaults: `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` (the already-incremented counter, line 693), but `_claimDefaultedInstantWithdrawRequest` and `defaultPendingClaimBasis` look up `instantWithdrawsRequestsByEpoch[...][defaultEpoch]` and `instantWithdrawClaimsByEpoch[epochNumber]` under that new key (lines 844, 647). Instant receipts opened in the defaulted epoch are stored under the old key, so they are (a) excluded from `defaultPendingClaimBasis` and the prefunded-reserve computation (`_defaultPrefundedInstantReserve`, lines 716–723) and (b) never matched by `_claimDefaultedInstantWithdrawRequest`, falling through to `claimInstantWithdrawRequest`'s at-par `_burn`/`_transferFundedClaim` (lines 387–392).

### Impact Explanation
Broken invariant: one receipt, one (haircutted) payout / loss waterfall confinement.

- In the `stopEpochWithDuration` loss path, the borrower underfunds `pendingWithdraws` and the protocol records a `lossRecoveryPrice < 1e18` — but under a key no claimant ever reads. Every requester from that epoch claims 100% at par. The strategy then pays out more underlying than was funded; the shortfall is borne by later claimants or the recovery reserve (insolvency / direct theft of the haircut amount).
- In the default path, unfunded instant receipts of the defaulted epoch are omitted from `totalBasis`, inflating `defaultRecoveryPrice`, and are then paid at par out of strategy underlyings — draining funds that belong to haircutted normal receipt holders and active tranche holders (direct theft; the `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, and the stolen funds were never added to the reserve because `_defaultPrefundedInstantReserve` computed `instantBasis = instantWithdrawClaimsByEpoch[N+1] = 0`).
- Quantified loss: an attacker requesting an instant or normal withdraw of `X` in the epoch that ends in a loss/default recovers `X` instead of `X * recoveryPrice / 1e18`; the excess `X * (1 - recoveryPrice/1e18)` is stolen from other claimants.

### Likelihood Explanation
- Attacker needs only a KYC-passing lender wallet (allowed class) calling `requestWithdraw` (or triggering `requestInstantWithdraw` via the APR-drop path) during a running epoch — fully permissionless within the threat model.
- The trigger conditions (a `stopEpochWithDuration` loss, or a borrower default finalized via `finalizeDefaultRecovery`) are ordinary protocol operations performed by honest privileged roles, exactly as the rules require.
- Caveat: the exploitability of the loss path depends on `deposit()` (the `epochNumber` increment) executing before `collectWithdrawFunds` inside the same `stopEpoch` flow. The `deposit()` comment ("deposit done on stopEpoch … so we reset the counter") and `epochNumber == 1` after the first `stopEpoch` in tests support this ordering, but the exact call order inside `IdleCDOEpochVariant.stopEpoch`/`_afterStopEpochWithDuration` was not fully traced here. The default-path mismatch is independent of that ordering: receipts are *always* keyed under the request epoch while `defaultRecoveryEpoch` is the post-stop counter.

### Recommendation
Normalize the epoch key domain. Either (a) record receipts under `epochNumber + 1` (the epoch in which they settle), or (b) store `lossRecoveryPriceByEpoch` and `defaultRecoveryEpoch` under `epochNumber - 1` / the value captured before the `deposit()` increment. Additionally, harden the claims: in `_claimFundedWithdrawRequest` and `claimInstantWithdrawRequest`, revert if the resolved receipt epoch has a non-zero `lossRecoveryPriceByEpoch` or equals `defaultRecoveryEpoch`, so an unmatched key can never silently fall through to the at-par path.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_expectedFundsEndEpoch`, `deal`):

```solidity
function testReceiptEscapesLossHaircut() external {
  uint256 amount = 1000 * ONE_SCALE;
  idleCDO.depositAA(amount);                    // test contract / KYC'd user

  _startEpochAndCheckPrices(0);                 // epoch 0 running, epochNumber == 0

  // attacker (any allowed wallet) requests withdraw during epoch 0
  address attacker = makeAddr("attacker");
  // ... give attacker AA tranche tokens via depositAA ...
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(0, address(AAtranche)); // lastWithdrawRequest[attacker] == 0

  uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();

  // borrower partially repays -> stopEpochWithDuration realizes a loss
  uint256 loss = pending / 2;
  deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - loss);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, 3 days, loss);

  // epochNumber is now 1; lossRecoveryPriceByEpoch[1] = (pending - loss)*1e18/pending
  assertEq(IdleCreditVault(address(strategy)).epochNumber(), 1);
  assertGt(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(1), 0);
  assertEq(IdleCreditVault(address(strategy)).lastWithdrawRequest(attacker), 0); // stale key

  // attacker claims at par: _claimLossAdjustedWithdrawRequest reads
  // lossRecoveryPriceByEpoch[0] == 0 -> falls through to _claimFundedWithdrawRequest
  uint256 balPre = underlying.balanceOf(attacker);
  cdoEpoch.claimWithdrawRequest(); // via CDO, msg.sender = attacker
  uint256 got = underlying.balanceOf(attacker) - balPre;

  uint256 haircut = pending * IdleCreditVault(address(strategy))
      .lossRecoveryPriceByEpoch(1) / 1e18;
  assertGt(got, haircut);        // receipt escaped the loss boundary
  assertEq(got, pending);        // paid at par despite underfunding
}
```

Equivalent default-path variant: open `requestInstantWithdraw` in epoch N, let the epoch end in borrower default, call `finalizeDefault`/`finalizeDefaultRecovery` — the receipt is stored under epoch N while `defaultRecoveryEpoch == N+1`, so `claimInstantWithdrawRequest` pays at par while `defaultPendingClaimBasis` (which read `instantWithdrawClaimsByEpoch[N+1] == 0`) excluded it from the recovery basis.
