### Title
APR0 epoch interest under-distributed via truncated per-epoch rate; residual borrower-funded yield permanently frozen in `IdleCreditVault` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The GMX M-10 bug is a rounding asymmetry: the code specially handles the case where a fee rounds down to **zero**, but discards fractional amounts when the value is **1.X**. The same pattern exists in `IdleCreditVault.prepareStopEpochWithApr0` / `_settleApr0`: the code guards the case where the APR0 interest gross rounds to zero (`if (_apr0InterestGross != 0)`), but when it is non-zero it stores a *truncated* per-principal rate (`apr0RateByEpoch`) and then applies a *second* truncation per user (`(_principal * _rate) / 1e18`). The full untruncated `_apr0NetInterest` is added to `pendingWithdraws`, so the borrower funds interest that the truncated rate can never fully distribute — the residual is permanently locked in the vault.

### Finding Description
In `prepareStopEpochWithApr0` (`contracts/strategies/idle/IdleCreditVault.sol:490-541`):

```solidity
uint256 _apr0InterestGross = _interestNetOfFees * _principal / _totalPrincipalForSplit;
if (_apr0InterestGross != 0) {
    uint256 _apr0Fee = _apr0InterestGross * _cdo.fee() / FULL_ALLOC;
    _apr0NetInterest = _apr0InterestGross - _apr0Fee;
    _adjPendingWithdrawFees += _apr0Fee;
    _expInterest -= _apr0NetInterest;
}
...
if (_apr0NetInterest != 0) {
    pendingWithdraws += _apr0NetInterest;                              // full amount funded
    apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal; // truncation #1
}
```

Two truncations then occur on the claim side:

- `apr0RateByEpoch[epoch] = _apr0NetInterest * 1e18 / _principal` truncates the rate when `_apr0NetInterest` is not an exact multiple of `_principal` (i.e., whenever the effective rate is "1.X wei per unit"). Unlike the `lossRecoveryPrice == 0` revert in `collectWithdrawFunds` (line 419), no guard or remainder tracking exists for the fractional part.
- `_settleApr0` (line 561) computes `settledInterest += (_principal * _rate) / 1e18`, truncating again per user.

Meanwhile `pendingWithdraws` was increased by the **untruncated** `_apr0NetInterest`, so at `stopEpoch` the borrower funds the full net interest. Each APR0 user's claim (`_claimFundedWithdrawRequest`, lines 338-349) pays out `settledPrincipal + settledInterest`, where `settledInterest` is strictly less than their pro-rata share. The aggregate claimable interest is strictly less than `pendingWithdraws`'s APR0 component.

### Impact Explanation
Broken invariant: **one receipt, one payout / conservation of funded interest**. The borrower is charged (and the CDO collects, via `collectWithdrawFunds`) the full `_apr0NetInterest`, but the claim path can only ever pay out `floor` of it. The residual underlying sits in `IdleCreditVault` with no accounting path: it is not `defaultRecoveryReserve`, not claimable via `withdrawsRequests`/`apr0Users`, and inflates the contract's token balance. It can only be recovered by the honest owner via `transferToken`, i.e., it is permanently frozen unclaimed yield from the protocol-accounting standpoint.

Additionally, the inflated `pendingWithdraws` is used as `pendingBasis` in `defaultPendingClaimBasis` (line 645) and in `previewLossAdjustedWithdrawFunds` (line 441), so the phantom basis slightly dilutes recovery/loss ratios for other claimants if a subsequent default or `stopEpochWithDuration` loss occurs.

Loss is bounded by roughly `#APR0Users + rate truncation remainder` wei per epoch, but it accrues every epoch in which APR0 requests exist and realized interest doesn't divide evenly — which is the common case.

### Likelihood Explanation
- Requires an APR=0 epoch with at least one pending `requestWithdraw` (unprivileged lender action: `requestWithdraw` → `IdleCreditVault.requestWithdraw` → `_requestWithdrawApr0`).
- Requires the honest manager/borrower to call `stopEpoch` with an override interest > 1, or normal `expectedEpochInterest` — no attacker control needed; the truncation is deterministic whenever `_apr0NetInterest * 1e18 % _principal != 0` or `_principal * _rate % 1e18 != 0`.
- No existing guard stops it: the only zero-guards are `_apr0InterestGross != 0` and `lossRecoveryPrice == 0`; fractional remainders are silently dropped, exactly matching the M-10 pattern.

### Recommendation
Track fractional amounts even when the amount is non-zero. Concretely:

- Store the APR0 interest as a cumulative rate with remainder handling, e.g. keep a `apr0Remainder` accumulator, or compute each user's interest directly as `principal * _apr0NetInterest / apr0TotalPrincipalForEpoch` (store `_apr0NetInterest` and `_principal` per epoch instead of the pre-divided rate), avoiding double truncation.
- Alternatively, increase `pendingWithdraws` by the *sum of distributable* interest (i.e., recompute `rate * principal / 1e18`) rather than the untruncated `_apr0NetInterest`, so funded amount equals claimable amount.

### Proof of Concept
Foundry fork sketch (APR0 mode):

```solidity
// Setup: vault with unscaledApr == 0 (APR0 epoch), users A and B KYC'd.
// 1. Epoch running. A and B requestWithdraw so apr0TotalPrincipal = P (e.g. 3 * ONE).
vm.prank(userA); cdo.requestWithdraw(amountA, AAtranche);
vm.prank(userB); cdo.requestWithdraw(amountB, AAtranche);

// 2. Honest manager stops epoch with override interest such that
//    _apr0NetInterest is not divisible by principal, e.g. net = 10, principal = 3.
vm.prank(manager); cdo.stopEpoch(interestOverride);

//    Inside prepareStopEpochWithApr0:
//      pendingWithdraws += 10
//      apr0RateByEpoch[e] = 10e18 / 3 = 3333333333333333333 (truncated)

// 3. Both users claim after epoch rolls.
cdo.claimWithdrawRequest(userA); // settledInterest = (1 * 3333333333333333333)/1e18 = 3 (if P split 1/1/1)
cdo.claimWithdrawRequest(userB); // same truncation

// Assert: sum(paidInterest) < 10 (funded), residual underlying remains in IdleCreditVault
assertLt(totalClaimed, pendingWithdrawsFunded);
assertGt(underlying.balanceOf(address(vault)), vault.defaultRecoveryReserve());
```

The residual can never be attributed to any receipt and is excluded from `pendingWithdraws` only partially (claim decrements `claimBasis`, which itself used the truncated rate — see `_withdrawClaimAmountsForEpoch` line 876), so `pendingWithdraws` also retains a phantom basis that pollutes future `previewLossAdjustedWithdrawFunds` / `defaultPendingClaimBasis` computations.
