### Title
Per-account write-lock cost budget can be exhausted by cheap spam transactions, DoSing legitimate transactions to the same account for the remainder of the block - (File: `cost-model/src/cost_tracker.rs`)

### Summary
The LayerZero bug lets any unprivileged user drain a shared resource (ETH held by `CrossChainRouter` for message fees) with cheap, unnecessary operations, blocking legitimate cross-chain calls that depend on that resource. Agave has an analogous shared, per-block resource: the `CostTracker`'s per-writable-account compute-unit budget (`MAX_WRITABLE_ACCOUNT_UNITS`). Any unprivileged transaction sender can write-lock a target account with minimal-cost transactions until that account's cost budget for the block is exhausted, which then causes `WouldExceedAccountMaxLimit`/`WouldExceedMaxAccountCostLimit` rejections for every other transaction (including higher-value, legitimate ones such as liquidations or repayments) that needs to write-lock the same account for the rest of that block.

### Finding Description
`CostTracker::would_fit` enforces a fixed per-account cost ceiling shared by all transactions that write-lock a given account in a block: [1](#0-0) 

The limit itself is a small, statically-sized budget (`MAX_WRITABLE_ACCOUNT_UNITS = 24_000_000` CU) intended to bound parallelism/contention on hot accounts: [2](#0-1) 

This account-level budget is a shared resource analogous to the ETH balance in the LayerZero router: it is consumed on a first-come, first-served basis by any transaction that write-locks the account, regardless of the caller's intent or the "value" of the operation. A malicious, unprivileged actor can submit a stream of minimal-cost transactions (e.g., trivial system transfers or no-op instructions with `WRITE_LOCK_UNITS` cost each) that write-lock a specific target account (e.g., a popular DeFi pool's state account, an oracle account, or any account a victim protocol's critical instruction must write) until `cost_by_writable_accounts[account]` reaches `account_cost` for that block: [3](#0-2) 

Once exhausted, every other transaction touching that account — including legitimate, high-value operations like liquidations, repayments, or critical protocol state updates — is rejected during banking-stage cost-tracking with `WouldExceedMaxAccountCostLimit`, exactly mirroring the LayerZero pattern where legitimate cross-chain calls revert because the shared ETH-for-gas resource was drained by cheap, unnecessary calls: [4](#0-3) 

The rejection surfaces through the normal transaction execution/commit path used by every ordinary user transaction: [5](#0-4) 

### Impact Explanation
An attacker with no special privileges — just enough SOL to pay minimal transaction fees — can selectively deny block inclusion to any transaction that must write-lock a specific target account, for as long as they are willing to keep spamming (the budget resets each new block, so this requires continuous per-block spam, similar to the report's "many unnecessary cross-chain operations"). For time-sensitive operations such as liquidations, oracle updates, or repayments that must write a hot shared account, this can cause missed liquidation windows, stale oracle prices, or delayed repayments — the same class of loss (delayed liquidation/repayment causing unfair user losses) described in the LayerZero report.

### Likelihood Explanation
The attack requires no special access: any funded keypair can submit a sequence of minimal-cost transactions targeting a chosen writable account. The per-account budget (`MAX_WRITABLE_ACCOUNT_UNITS`) is far smaller than the block budget (`MAX_BLOCK_UNITS`), so exhausting a single hot account's slice is cheaper than saturating the whole block, and the cost model’s `WRITE_LOCK_UNITS` cost is fixed and low regardless of the fee paid, making the resource easy and inexpensive to consume relative to its protective intent. This is a recognized economic griefing vector against the cost-tracker design rather than a memory-safety or consensus bug, so likelihood is high for griefing a known target account, though it is continuously mitigable by leader/validator-side heuristics (not part of the core structural fix).

### Recommendation
Consider incorporating paid priority fee / fee-per-CU into per-account admission decisions (not just raw CU cost) so cheap spam cannot cheaply monopolize a hot account's budget, and/or allow legitimate high-priority transactions to preempt/evict lower-priority ones that already reserved account budget within the same block (similar to how `forwarding_stage`/scheduler already evict low-priority packets by priority under capacity). Additionally, consider making `MAX_WRITABLE_ACCOUNT_UNITS` dynamically scale or exposing per-account contention metrics to schedulers so known hot accounts used by critical protocols are not trivially exhaustible by low-fee transactions.

### Proof of Concept
Not executed; the vulnerable enforcement path is deterministic and unit-tested for exhaustion behavior, e.g. `test_cost_tracker_chain_reach_limit`, `test_cost_tracker_reach_limit`, and `test_cost_tracker_try_add_is_atomic`, which demonstrate that once an account's chained cost reaches the limit, `would_fit`/`try_add` reject any further transaction touching that account for the remainder of the block: [6](#0-5) [7](#0-6)

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum CostTrackerError {
    /// would exceed block max limit
    WouldExceedBlockMaxLimit,

    /// would exceed account max limit
    WouldExceedAccountMaxLimit,

    /// would exceed account data block limit
    WouldExceedAccountDataBlockLimit,

    /// would exceed account data total limit
    WouldExceedAccountDataTotalLimit,
}

impl From<CostTrackerError> for TransactionError {
    fn from(err: CostTrackerError) -> Self {
        match err {
            CostTrackerError::WouldExceedBlockMaxLimit => Self::WouldExceedMaxBlockCostLimit,
            CostTrackerError::WouldExceedAccountMaxLimit => Self::WouldExceedMaxAccountCostLimit,
            CostTrackerError::WouldExceedAccountDataBlockLimit => {
                Self::WouldExceedAccountDataBlockLimit
            }
            CostTrackerError::WouldExceedAccountDataTotalLimit => {
                Self::WouldExceedAccountDataTotalLimit
            }
        }
    }
}

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

fn check_block_cost_limits<Tx: TransactionWithMeta>(
    bank: &Bank,
    tx_costs: &[Option<TransactionCost<'_, Tx>>],
) -> TransactionResult<()> {
    let mut cost_tracker = bank.write_cost_tracker().unwrap();
    for tx_cost in tx_costs.iter().flatten() {
        cost_tracker
            .try_add(tx_cost)
            .map_err(TransactionError::from)?;
    }

    Ok(())
}
