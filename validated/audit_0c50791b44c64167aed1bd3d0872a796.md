### Title
Multisig confirmation threshold is read live instead of being cached per-request, allowing pending requests to execute below the confirmation count members agreed to - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` store a single mutable `num_confirmations` field that acts as the pass threshold for every outstanding request. Each request's confirmations accumulate in a persistent `HashSet` keyed by `request_id`, but the threshold compared against that set inside `confirm()` is always the *current* contract-level `num_confirmations`, never a value captured when the request was created. Since `num_confirmations` can itself be changed by another multisig request (`SetNumConfirmations`), lowering the threshold retroactively "grandfathers in" confirmations collected under the old, stricter rule, letting a pending high-value request (e.g. a `Transfer`) execute with fewer independent approvals than the members who confirmed it originally required.

### Finding Description
The confirmation-count check lives in `confirm()`: [1](#0-0)

`self.num_confirmations` is compared live, and it can be mutated by any other request via `SetNumConfirmations`: [2](#0-1) 

The identical pattern exists in `multisig2/src/lib.rs`'s `confirm()`: [3](#0-2) 

and its `SetNumConfirmations` handling: [4](#0-3) 

No request stores a "required confirmations" value at creation time — the `MultiSigRequestWithSigner`/`MultiSigRequestWithSigner` structs only track `signer_pk`/`member` and `added_timestamp`: [5](#0-4) [6](#0-5) 

This is the same bug class as the external report: a threshold (`num_confirmations` here, `passThresholdBps` there) that governs whether an in-flight item has "passed" is read from live, mutable global state rather than being snapshotted at the item's creation, so a parameter change executed through the exact same governance mechanism silently changes the requirements of already-in-progress items.

### Impact Explanation
Concretely:
1. Multisig starts with `num_confirmations = 5` (n ≥ 5 members).
2. A member creates request `R1` (e.g., `Transfer` of contract funds). Four members confirm — `confirmations(R1).len() == 4`, which is `< 5`, so `R1` is *not* executed yet; it sits pending, and every one of those 4 confirmers reasonably expects a 5th independent approval is still required.
3. Separately, a `SetNumConfirmations { num_confirmations: 4 }` request is proposed and reaches the current threshold of 5 confirmations, and executes, setting `self.num_confirmations = 4`.
4. Any single additional member (or even a colluding 5th signer) now calls `confirm(R1)`. The check becomes `4 + 1 >= 4` → true, and `R1` (the fund transfer) executes immediately via `execute_request`.

The binding broken is: *confirmations recorded for a request* versus *the threshold the confirming members believed was in force*. The transfer executes below the pass threshold the original approvers signed up for — this is explicitly the Critical impact category "a multisig request executed below threshold." Funds move (or keys/contract code are changed, since `AddKey`/`DeployContract`/`AddMember`/`DeleteMember` go through the identical `confirm()` gate) without the number of genuinely independent approvals the multisig's configured security model intended at the time those approvals were cast.

### Likelihood Explanation
This does not require any external actor, redeploy, or compromised key — only the participation of members/keys already authorized to call `add_request`/`confirm`, using only the contract's own documented `SetNumConfirmations` action. No malicious code path outside the multisig's own methods is needed; only a normal sequence of two concurrently pending requests is required, which is explicitly supported by the design (multiple active requests per key, `active_requests_limit` up to 12). A minority coalition that can reach the *current* threshold (which may already be attainable, e.g. in smaller multisigs or with colluding signers) can use a threshold-lowering request to unlock previously-insufficient confirmations on another pending request.

### Recommendation
Cache the required confirmation count on the `MultiSigRequestWithSigner` struct (and `multisig2`'s equivalent) at the time the request is created via `add_request`, and compare against that cached value inside `confirm()` instead of the live `self.num_confirmations`. Alternatively, invalidate/reset confirmations on all pending requests whenever `SetNumConfirmations` executes, so accumulated confirmations can never be evaluated against a different threshold than the one in effect when they were cast.

### Proof of Concept
```
// multisig contract initialized with num_confirmations = 5, members [A..G]
let mut c = MultiSigContract::new(5 /* or new(members, 5) for multisig2 */);

// Step 1: A creates a large Transfer request
let r1 = c.add_request(MultiSigRequest {
    receiver_id: attacker_or_target,
    actions: vec![MultiSigRequestAction::Transfer { amount: big_amount.into() }],
});

// Step 2: B, C, D confirm (A already confirmed via add_request_and_confirm, or A confirms separately)
// -> confirmations(r1).len() == 4, still short of 5, request stays pending

// Step 3: A separate request lowers the threshold, reaching the *current* 5-confirmation bar
let r2 = c.add_request(MultiSigRequest {
    receiver_id: current_account_id,
    actions: vec![MultiSigRequestAction::SetNumConfirmations { num_confirmations: 4 }],
});
// 5 members confirm r2 -> executes -> c.num_confirmations == 4

// Step 4: any 5th/new member calls confirm(r1)
c.confirm(r1);
// check: confirmations(r1).len() (4) + 1 >= c.num_confirmations (4) -> true
// -> Transfer executes with the number of approvals members believed was insufficient
//    (4 confirmations gathered under a 5-confirmation regime, released by 1 more confirm
//    cast only after the threshold was lowered)
```

The existing test `test_change_num_confirmations` in both `multisig/src/lib.rs` (lines 660-673) and `multisig2/src/lib.rs` (lines 746-762) confirms that `SetNumConfirmations` mutates `self.num_confirmations` in place with no re-validation of any other pending request's confirmations, which is the root cause enabling the above sequence.

        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
