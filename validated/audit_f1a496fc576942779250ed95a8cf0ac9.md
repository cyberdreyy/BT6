### Title
Unbounded externally-manipulated ERC4626 interest feeds unbacked strategy-token minting in `stopEpoch`, inflating NAV into insolvency - ([contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
In minted-interest + programmable-borrower mode, `stopEpoch` prices the whole epoch off a single externally influenced value, `IProgrammableBorrower.totalInterestDueNow()`. That value includes "vault interest" computed as `vault.convertToAssets(shares)` minus an internally tracked principal baseline (`ProgrammableBorrower._vaultNetInterest`). An unprivileged attacker can inflate `_currentVaultAssets()` — e.g. by depositing into the ERC4626 vault and transferring the resulting shares directly to `ProgrammableBorrower` (or donating underlying to a vault that counts raw balances) — and the inflated delta is counted as epoch "interest". The CDO then mints that amount of unbacked strategy tokens via `mintStrategyTokens` and calls `_updateAccounting`, permanently inflating tranche prices and the NAV used to price every withdrawal request, with no bound check on the auto-resolved path.

### Finding Description
`stopEpoch` resolves interest automatically when `_interest == 0`/sentinel, producing `_grossInterest` from the strategy. In programmable-borrower mode the strategy-facing value is `ProgrammableBorrower.totalInterestDueNow()`, which returns `vaultInterest + borrowerInterestAccruedNow() + bufferInterest - loss` (`contracts/strategies/idle/ProgrammableBorrower.sol` ~L330-334). `vaultInterest` comes from `_vaultNetInterest`:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol ~L337-347
uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
```

`_currentVaultAssets()` is `vault.convertToAssets(vault.balanceOf(address(this)))` (~L546-549). Any shares or underlying pushed into the contract outside the tracked `epochDepositedToVault`/`epochStartVaultAssets` baseline is counted as profit. There is no sanity bound: the only cap on `_grossInterest` (`maxApr` check at `IdleCDOEpochVariant.sol` ~L377-380) is gated on `_interest > 1`, i.e. only on the manual-override path, not on the automatic borrower-derived path.

On success, `stopEpoch` executes (minted-interest mode):

```solidity
// contracts/IdleCDOEpochVariant.sol ~L428-436
if (_mintInterest) {
  if (_grossInterest != 0) _strategy.mintStrategyTokens(_grossInterest);
  unclaimedFees += _pendingWithdrawFees;
}
_updateAccounting();
```

`mintStrategyTokens` mints IdleCreditVault shares to the CDO with no underlying transferred in. `getContractValue`/`virtualPrice` then treats these tokens as real NAV, so every withdraw request priced by `requestWithdraw`/`previewLossAdjustedWithdrawFunds`/`claimWithdrawRequest` is denominated against phantom assets. This is exactly the external report's bug class: an externally set number (`totalInterestDueNow`, analog of `uopt`) is piped directly into minting authority with no `[ulow, ucrit]`-style bound on the automated path.

### Impact Explanation
Insolvency with quantified loss equal to the manipulated delta `X`: the pool's recorded NAV is `realAssets + X` while backing remains `realAssets`. Early claimants (including any attacker-held tranche position) withdraw at the inflated `virtualPrice` and drain real underlying; once the pool's cash is exhausted, the remaining `withdrawsRequests`/`withdrawsRequestsByEpoch` receipts can never be funded — permanent freezing/unpaid claims for up to `X` of underlying. Fee receivers are additionally minted AA shares (`_mintSharesAtCurrPrice(feeReceiverAmount, ...)`), compounding the unbacked supply. Because the deficit is minted rather than donated, the loss is socialized across all remaining tranche holders and receipt holders rather than absorbed by the attacker.

### Likelihood Explanation
- Attacker is unprivileged: any EOA can deposit into the whitelisted ERC4626 vault and transfer the minted vault shares to the `ProgrammableBorrower` contract address, or send underlying to a vault whose `convertToAssets` tracks `balanceOf`. No privileged role is needed; the honest manager's routine `stopEpoch` call is the trigger.
- Conditions: `isProgrammableBorrower == true` and `isInterestMinted == true` (the required mode per `_checkProgrammableBorrowerMode`), epoch running and past `epochEndDate`.
- It is griefing-priced, not strictly profitable for a passive donor (cost ≈ deficit created), but the attacker can pre-position tranche holdings / pending withdraw receipts to recover a fraction `f·X` of the fake interest at the expense of slower claimants, and the insolvency impact is unconditional.
- Existing guards do not stop it: `_skimDonatedAssets` only skims *CDO-held underlying*, not vault-share inflation inside `ProgrammableBorrower`; the `maxApr` bound is bypassed on the automatic interest path; `onStopEpoch` returning true does not validate the interest figure.

### Recommendation
Bound the auto-resolved interest in `stopEpoch` for programmable-borrower deployments, mirroring the H-04 fix: revert (or clamp and flag for manual review) when `_grossInterest` exceeds the contractual ceiling, e.g. `_calcInterestWithApr(getContractValue(), maxApr) + pendingWithdrawFees + borrowerInterest` — apply the existing L377-380 check unconditionally rather than only when `_interest > 1`. Complementarily, in `ProgrammableBorrower`, snapshot `vaultShares` at `startEpochAccounting` and compute `_currentVaultAssets` only over the checkpointed share balance (or track `epochDepositedShares`), so unsolicited share/underlying transfers are not counted as epoch PnL; ideally route unexpected-token recovery through `rescueTokens`/`_skimDonatedAssets` to `feeReceiver` instead of into `totalInterestDueNow`.

### Proof of Concept
Foundry fork, based on `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup (real MetaMorpho vault, `setIsProgrammableBorrower(true)`, `setIsInterestMinted(true)`, `strategy.setAprs(0,0)`):

```solidity
function testVaultShareDonationInflatesStopEpochInterest() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0); // PB deposits idle funds into Morpho vault

    // Attacker: deposit into the ERC4626 vault and push the shares to ProgrammableBorrower.
    // These shares are outside epochStartVaultAssets/epochDepositedToVault, so they are
    // counted by _vaultNetInterest as pure epoch "gain".
    uint256 donation = 500 * oneScale;
    deal(USDC, attacker, donation, true);
    vm.startPrank(attacker);
    underlying.approve(vaultAddress, donation);
    uint256 donatedShares = morphoVault.deposit(donation, attacker);
    morphoVault.transfer(address(programmableBorrower), donatedShares);
    vm.stopPrank();

    uint256 fakeInterest = programmableBorrower.totalInterestDueNow();
    assertApproxEqAbs(fakeInterest, donation, 10, "inflated epoch interest");

    uint256 cdoSharesPre = IERC20(strategyToken).balanceOf(address(cdoEpoch));
    uint256 realAssets = underlying.balanceOf(address(cdoEpoch))
        + _programmableVaultAssets(); // includes the donation

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Unbacked strategy tokens minted: CDO book value now exceeds redeemable underlying.
    uint256 cdoSharesPost = IERC20(strategyToken).balanceOf(address(cdoEpoch));
    assertApproxEqAbs(cdoSharesPost - cdoSharesPre, fakeInterest, 10, "unbacked mint");

    // NAV says everyone can withdraw principal + fakeInterest, but only `realAssets`
    // (which includes the attacker's own donation) exists. After honest users claim
    // `realAssets`, the last receipt holders' claims are unfunded => insolvency == donation size.
}
```

Key assertions: `totalInterestDueNow()` rises by the donated amount with zero economic activity; `stopEpoch` mints that amount of IdleCreditVault shares to the CDO; `virtualPrice(AATranche)` rises while redeemable cash does not; subsequent `claimWithdrawRequest` calls succeed only until the pool's real underlying is exhausted, leaving the remainder permanently unpaid.
