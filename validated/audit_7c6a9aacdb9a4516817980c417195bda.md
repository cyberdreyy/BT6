Confirmed: `get_builder_withdrawals` in `specs/gloas/beacon-chain.md` builds each `Withdrawal.amount` directly from `withdrawal.amount` (the raw, requested amount stored in `state.builder_pending_withdrawals`), with no cap against `state.builders[builder_index].balance`. That withdrawal object is what gets included in `state.payload_expected_withdrawals` and must be honored by the execution layer (the EL mints/credits `Withdrawal.amount` to `Withdrawal.address` unconditionally, per the Capella/Gloas withdrawal contract). Only later, in `apply_withdrawals`, is the *builder's internal accounting* capped: `state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)`.

### Title
Builder pending withdrawal can mint execution-layer ETH exceeding the builder's CL balance - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` copies the *requested* `amount` from `state.builder_pending_withdrawals` into the outgoing `Withdrawal` object without capping it to the builder's actual balance. `apply_withdrawals`, however, deducts only `min(withdrawal.amount, builder_balance)` from the builder's CL balance [1](#0-0) . Since the execution layer credits the recipient with the full `Withdrawal.amount` committed in `payload_expected_withdrawals` regardless of the CL-side deduction, a builder (or anyone able to enqueue a `BuilderPendingWithdrawal` with `amount` greater than the builder's balance) can cause the EL to mint/pay out more ETH than was ever backed by the builder's stake.

### Finding Description
The withdrawal amount used for the two sides of the transition diverges:
- EL-facing commitment (what actually gets paid to `fee_recipient` on execution layer): `withdrawal.amount` taken verbatim from the queue entry [2](#0-1) .
- CL-side balance deduction (what is actually removed from the builder's stake): `min(withdrawal.amount, builder_balance)` [3](#0-2) .

This is structurally the same class of bug as the UniProxy report: two computations of "the amount that matters" that are supposed to be equal but are not — one drives the on-chain transfer/commitment, the other drives the internal balance bookkeeping, and the transfer side is not capped by the bookkeeping side (in UniProxy it was the reverse: bookkeeping/deposit used the smaller number while the actual swap output was larger, stranding funds; here the payout side uses the larger, uncapped number while the balance side is capped, minting excess). The test suite explicitly documents and accepts this asymmetry as expected behavior: `test_builder_withdrawal_insufficient_balance` sets a builder balance of 1 ETH but a pending withdrawal request of 5 ETH, and asserts the resulting `payload_expected_withdrawals` entry has `amount == 5 ETH` while `builders[0].balance == 0` [4](#0-3) . The accompanying report table also states this directly: "Actual = `min(amount, builder.balance)`" is applied only to the *balance decrement*, not to the emitted withdrawal amount [5](#0-4) .

The equality broken is: *Gwei paid out via `Withdrawal.amount` (committed to the execution layer and thus minted/paid to `fee_recipient`) must equal the Gwei actually removed from the paying party's consensus-layer balance.* Here it does not — the EL pays the full requested amount while the CL only ever removes the builder's available balance, capping at zero once exhausted.

### Impact Explanation
This falls under "Gwei created ... or paid to a non-owner." If a `BuilderPendingWithdrawal` with an inflated `amount` (larger than the builder's balance) can be enqueued — whether through a bug elsewhere in request validation, a race between balance-reducing operations (e.g. concurrent slashing or another withdrawal) and the pending withdrawal's `amount` field being fixed at insertion time, or any path that allows `amount` to exceed `builder.balance` by the time it is processed — the execution layer will credit `fee_recipient` with more ETH than the builder ever had backing it on the beacon chain. This is unbacked ETH creation, i.e., inflation of the total supply beyond what any validator/builder deposited, which is a Critical-class impact per the rubric ("Gwei created, destroyed, or paid to a non-owner").

### Likelihood Explanation
The `amount` field of `BuilderPendingWithdrawal` is fixed when the withdrawal request is queued, but the builder's `balance` can decrease afterward (e.g., other withdrawals processed earlier in the same sweep, or balance-reducing operations between queuing and processing, since `builder_pending_withdrawals` can sit in the queue for multiple slots given `BUILDER_PENDING_WITHDRAWALS_LIMIT` = 2^20). Whether the honest request-creation path can *itself* produce a request whose `amount` later exceeds `balance` depends on validation logic in the (not fully located within budget) builder withdrawal request processing function, which is not shown in the snippets retrieved. The test suite treats the “insufficient balance” case as a normal, expected input rather than an unreachable state, which suggests the spec authors consider a mismatch between requested `amount` and current `builder.balance` a reachable condition, deliberately handling it by capping the CL debit — without correspondingly capping the EL-facing withdrawal amount. This indicates the underlying invariant (EL payment amount ≤ CL balance actually available) is not spec-enforced by `get_builder_withdrawals` itself, though I could not verify from the retrieved code whether the *request-creation* function additionally caps `amount` to `balance` at insertion time, which would make this unreachable in practice — I flag this as unresolved due to index coverage.

### Recommendation
Cap the `amount` field written into the emitted `Withdrawal` in `get_builder_withdrawals` (and, if applicable, `get_builders_sweep_withdrawals`'s analogous full-balance withdrawal) to the builder's *current* balance at withdrawal-processing time, i.e. use `min(withdrawal.amount, state.builders[builder_index].balance)` when constructing the `Withdrawal` object, so the amount actually committed to the execution layer never exceeds what `apply_withdrawals` deducts from the builder's consensus-layer balance.

### Proof of Concept
1. Enqueue `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, fee_recipient=ADDR, amount=5_000_000_000)]` while `state.builders[0].balance = 1_000_000_000` (exactly the setup used in `test_builder_withdrawal_insufficient_balance`) [6](#0-5) .
2. Call `process_withdrawals(state)`. `get_expected_withdrawals` → `get_builder_withdrawals` emits `Withdrawal(validator_index=convert_builder_index_to_validator_index(0), address=ADDR, amount=5_000_000_000)` [7](#0-6) .
3. `apply_withdrawals` decrements `state.builders[0].balance` by only `min(5_000_000_000, 1_000_000_000) = 1_000_000_000`, leaving balance at `0` [3](#0-2) .
4. `state.payload_expected_withdrawals` (and hence the execution payload's `withdrawals` list that the EL must honor) still records `amount = 5_000_000_000` for `ADDR`, so the execution layer will credit `ADDR` with 5 ETH even though only 1 ETH was ever removed from the builder's consensus-layer balance — a 4 ETH mint with no corresponding CL-side debit.
