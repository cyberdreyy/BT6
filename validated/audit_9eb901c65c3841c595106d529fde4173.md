### Title
Full JWT token (`req.Auth`) logged in cleartext via struct serialization in `HandleJSONRPCUserMessage` - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
While `authorizer.AuthorizeRequest` in `core/capabilities/vault/authorizer.go` itself only logs the boolean `hasAuth` field and never the raw token, the gateway-side vault handler logs the entire `req` struct — which includes the raw `Auth` JWT string — before any authorization occurs. This confirms the attacker-controlled JWT/token value can end up in node logs via a different, higher-level log statement in the same request-handling flow.

### Finding Description
In `core/services/gateway/handlers/vault/handler.go`, `HandleJSONRPCUserMessage` executes: [1](#0-0) 

specifically the line:
```go
h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
``` [2](#0-1) 

This passes the full `jsonrpc.Request[json.RawMessage]` value (`req`) as a structured log field before any auth check happens (`req.Method == vaulttypes.MethodPublicKeyGet` check and `h.requestProcessor.ProcessRequest` occur afterwards). The `Auth` field of `jsonrpc.Request` is a plain exported string set directly from the client-supplied `Authorization` header/JWT (as seen throughout the codebase, e.g. `req.Auth = mustMintVaultJWTForRequest(...)` and `req.Auth != ""` checks in `authorizer.go`) [3](#0-2) . Sugared structured loggers (zap `Debugw`) serialize struct arguments via reflection/JSON, which will include all exported fields — meaning the raw token value ends up verbatim in the log output at `Debug` level, regardless of whether the JWT is malformed, truncated, expired, or otherwise fails validation later in `authorizeJWTBasedAuth`.

The downstream `authorizer.go` code is itself safe — it consistently logs only `"hasAuth", req.Auth != ""` rather than the raw value [4](#0-3) . However, this good practice is undermined by the handler-level `Debugw("handling vault request", ..., "request", req)` call that logs the same `req` value with `Auth` populated, before the safe authorizer path is even reached.

Because this log statement fires unconditionally for every JSON-RPC vault request that reaches the gateway handler (an unauthenticated/any client can trigger it simply by sending any vault method request with `Auth` set), an attacker who submits a request with a JWT/token value (even garbage/malformed) causes their own token to be written into the node's log stream in cleartext.

### Impact Explanation
This matches the "sensitive secret/key disclosure via logs" bounty impact class: JWT/bearer tokens submitted by users are written unredacted into gateway node logs at `Debug` level. If the node operator or infrastructure ships `Debug`-level logs to a shared/lower-privileged log aggregation system, an attacker's own or (if debug logging captures request context broadly enough) potentially other tokens observed by log consumers could be exposed. The primary and directly provable impact is self-disclosure of the caller's own JWT into node logs — since Vault JWTs are short-lived and organization/owner-scoped, disclosure of a caller's own token to a lower-privileged log consumer than the caller is a real confidentiality violation of the secret-confinement invariant, even though it does not directly grant the attacker anything beyond what they already possess.

### Likelihood Explanation
Trivial and 100% repeatable: any unauthenticated client of the gateway can send a `vault.*` JSON-RPC request with any string in `req.Auth` (valid, malformed, or truncated JWT) and the `Debugw("handling vault request", ...)` line at `core/services/gateway/handlers/vault/handler.go:412` will unconditionally include it, since it fires prior to method dispatch and prior to any authorization/validation. No special role or credential is needed beyond the ability to send a request to the gateway's vault handler.

### Recommendation
Remove the raw `req` struct from the `Debugw("handling vault request", ...)` log call at `core/services/gateway/handlers/vault/handler.go:412`, replacing it with only non-sensitive fields (e.g., `method`, `requestID`, and `hasAuth`, mirroring the pattern already used in `authorizer.go`). More broadly, audit all `logger.Logger` calls across the vault gateway/handler code that pass the full `jsonrpc.Request` struct as a log argument (e.g., `fetchVaultPublicKey`'s `"request", getPublicKeyRequest` logs) and either redact the `Auth` field before logging or implement a custom `MarshalLogObject`/`String()` for `jsonrpc.Request` that masks the `Auth` field.

### Proof of Concept
Go test plan (handler-level, using a capturing test logger):
1. Construct a `logger.Logger` backed by an in-memory/observed zap core (e.g. `zaptest/observer`) so all logged fields can be inspected.
2. Build a `handler` via `newHandlerWithAuthorizer` with a mock `Authorizer`/`requestProcessor` that will reject the request (simulate malformed JWT failure).
3. Call `handler.HandleJSONRPCUserMessage(ctx, req, callback)` with `req.Auth = "malformed.truncated.jwt"` and `req.Method = vaulttypes.MethodSecretsCreate` (or any gateway secrets method).
4. Inspect all captured log entries emitted during the call, in particular the "handling vault request" entry at line 412.
5. Assert: `require.NotContains(t, entry.ContextMap()["request"], "malformed.truncated.jwt")` fails today (proving the vulnerability), because the observed `"request"` field marshals the `req` struct including `Auth: "malformed.truncated.jwt"` verbatim.
6. After applying the fix (logging `hasAuth` instead of `req`), re-run the same test and assert the raw token string never appears in any captured log entry across the whole `HandleJSONRPCUserMessage` call.

func (a *authorizer) authorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	// Requests without req.Auth continue using the allowlist-based path for backwards compatibility.
	// Existing clients do not populate the auth field yet, so treating an empty value as JWT would break them.
	if req.Auth == "" {
		return a.authorizeAllowListBasedAuth(ctx, req)
	}
	return a.authorizeJWTBasedAuth(ctx, req)
}
