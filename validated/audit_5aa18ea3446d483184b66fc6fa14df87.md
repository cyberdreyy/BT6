### Title
Buffer-period ERC4626 vault losses are excluded from withdrawal pricing, allowing early receipt holders to exit at par and concentrate principal losses on remaining LPs - ([contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower` tracks negative vault PnL as `bufferedVaultDelta`, but `requestWithdraw` prices tranche redemptions only from the CDO’s strategy-token balance. A lender can therefore request withdrawal after an external-vault loss but before `startEpoch` carries that loss into epoch accounting. `stopEpoch(0, 0)` then resolves programmable-borrower interest with `totalInterestDueNow()`, which floors vault losses at zero rather than reporting a principal loss, so the pending receipt is funded in full while the remaining active LPs absorb the entire loss.

### Finding Description
`IdleCDOCreditVault.getContractValue()` values the pool as strategy tokens plus raw underlying minus fees; it does not include the borrower’s ERC4626 position. [1](#0-0) 

During the buffer phase, `requestWithdraw` calls `_updateAccounting()` and prices the requested tranche tokens using the current saved tranche price, but that accounting cannot see the loss still held inside the programmable borrower’s external vault position. [2](#0-1) 

When the next epoch starts, `ProgrammableBorrower.onStartEpoch()` computes `bufferedVaultDelta` as the difference between the current vault value and the prior `bufferStartVaultAssets`. [3](#0-2) 

A permanent ERC4626 loss during the buffer therefore becomes a negative `bufferedVaultDelta`. `_vaultNetInterest()` reports that value as `loss`, but `totalInterestDueNow()` merely subtracts it from vault interest, borrower interest, and buffer interest and returns zero if the loss exceeds those gains. [4](#0-3) 

The normal `stopEpoch(0, 0)` entry point passes `_lossAmount = 0`. [5](#0-4)  In minted-interest programmable mode, IdleCDO requests only pending withdrawal cash, sends it to `IdleCreditVault`, and calls accounting without burning any strategy tokens. [6](#0-5)  A loss burn occurs only when the caller separately supplies `_lossAmount` through `stopEpochWithDuration`; `stopEpoch` does not derive that value from `vaultLoss()`. [7](#0-6) 

Consequently, a pending receipt created after the loss is treated as fully funded at its stale pre-loss basis. The withdrawal reserve is paid before the unrealized vault shortfall is crystallized, while active tranche holders retain strategy tokens backed by the impaired residual vault position.

### Impact Explanation
This violates fair loss distribution and creates a first-come, first-served payout from impaired assets.

Example:

- Active LP value: 1,000 underlying.
- Buffer-period external-vault loss: 200.
- Epoch interest and buffer interest: 10.
- Attacker pending withdrawal basis: 500.

`totalInterestDueNow()` returns zero because `10 - 200` is floored at zero. [8](#0-7)  `stopEpoch` still pulls and funds the full 500 pending receipt because `_lossAmount` is zero. [9](#0-8)  The attacker exits with 500, while only approximately 300 of vault value remains for positions whose stale accounting basis is 500.

The loss borne by remaining LPs is quantified as the funded pending amount multiplied by the vault haircut. In this example, the attacker escapes approximately `500 * 20% = 100` underlying of loss, which is transferred to non-withdrawing holders.

### Likelihood Explanation
No privileged attacker is required. The attacker only needs to be an allowed tranche-token holder and call `requestWithdraw` during the buffer after a loss exists in the programmable borrower’s ERC4626 position but before that loss is carried into a new epoch. [10](#0-9) 

The sequence relies only on ordinary manager calls to `startEpoch()` and `stopEpoch(0, 0)`. `startEpoch()` is the normal way the borrower snapshots buffer PnL and reserves pending withdrawals. [11](#0-10)  The exploitable condition is the interval between an external vault loss and that next epoch start.

Existing controls do not prevent it:

- `requestWithdraw` accounting checks CDO-held strategy tokens, not the borrower vault’s impaired value.
- `totalInterestDueNow()` cannot return a negative principal adjustment because it floors at zero.
- Normal `stopEpoch` never invokes the loss-adjusted pending-withdrawal path because it supplies a zero `_lossAmount`.
- `stopEpochWithDuration` can pass a manual loss, but the standard programmable-borrower stop flow does not require or derive that parameter, leaving stale-basis withdrawals available through the ordinary path. [12](#0-11) 

### Recommendation
Account for programmable-borrower vault losses before accepting buffer withdrawal requests and before funding pending receipts.

At minimum:

1. Include `IProgrammableBorrower.vaultLoss()` in the NAV used by `requestWithdraw` or force fresh loss accounting before minting withdrawal receipts.
2. Change the programmable stop flow so `totalInterestDueNow()` returns both net interest and the unabsorbed principal loss.
3. Automatically pass that unabsorbed loss into `previewLossAdjustedWithdrawFunds()` and `burnStrategyTokens()`, rather than relying on an operator to call `stopEpochWithDuration` with a correct manual `_lossAmount`.
4. Alternatively, disable withdrawal requests in programmable mode whenever `vaultLoss()` or negative `bufferedVaultDelta` is non-zero until a loss-adjusted epoch transition completes.
5. Add regression tests where a vault loss occurs during the buffer, withdrawals are requested before `startEpoch`, and pending receipts receive the same haircut as active tranche holders.

### Proof of Concept
A Foundry fork test should follow this sequence against a programmable-borrower deployment with an ERC4626 vault:

```solidity
function testBufferVaultLossWithdrawalEscapesHaircut() public {
    uint256 depositAmount = 1_000e6;
    uint256 withdrawAmount = 500e6;

    // Two allowed LPs hold AA shares.
    _depositWithUser(attacker, withdrawAmount, true);
    _depositWithUser(victim, withdrawAmount, true);

    // Finish epoch N so epochEndDate/bufferPeriod make the buffer withdrawal
    // window available.
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    _stopEpochAndCheckPrices(0, apr, borrowerRepayment);

    // While still in the buffer, impair the underlying ERC4626 position by 20%.
    // On a fork, this can be reproduced by applying the target vault's actual
    // loss mechanism or by overwriting its accounted totalAssets/solvency state.
    _applyPermanentVaultLoss(programmableBorrower.vault(), 200e6);

    // CDO accounting still sees the old strategy-token balance, so the receipt
    // is created at the stale pre-loss tranche price.
    vm.prank(attacker);
    uint256 receiptBasis = cdoEpoch.requestWithdraw(0, address(aaTranche));
    assertEq(receiptBasis, withdrawAmount);

    // startEpoch snapshots the -200 vault delta into bufferedVaultDelta.
    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Interest is less than the vault loss, so pool-facing interest floors at 0.
    assertEq(programmableBorrower.totalInterestDueNow(), 0);

    // Honest borrower approves enough residual liquidity for the stale receipt.
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), receiptBasis);

    // Ordinary programmable stop does not supply a loss amount.
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Attacker claims at stale par despite the impaired vault.
    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - attackerBefore, receiptBasis);

    // Remaining residual backing is approximately 300, while the victim's
    // recorded claim basis remains approximately 500.
    assertApproxEqAbs(
        programmableBorrower.totalUnderlying(),
        300e6,
        tolerance,
        "entire vault loss remains with active LP"
    );
}
```

The core assertion is that the pending receipt is paid `receiptBasis` even though the aggregate programmable-borrower backing was reduced by the vault loss before the receipt was priced.

  function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);
    // Reset the epoch accounting baseline from the exact pre-start total assets so the new epoch
    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;

  function totalInterestDueNow() external view returns (uint256) {
    (uint256 vaultInterest, uint256 loss) = _vaultNetInterest();
    uint256 totalGain = vaultInterest + borrowerInterestAccruedNow() + bufferInterest;
    return totalGain > loss ? totalGain - loss : 0;
  }

  /// @notice Compute the net vault delta split into interest and loss (mutually exclusive).
  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
      loss = uint256(-netDelta);
    }
