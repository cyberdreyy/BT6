### Title
`setApr` in `IdleCreditVault` is callable by anyone while `idleCDO` is unset, letting an attacker inject an arbitrary epoch APR - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the missing `onlyPoolManager` modifier on `setPoolActive`, `IdleCreditVault.setApr` is a `public` state-changing function whose own NatSpec says "only cdo and manager can set the apr" ( [1](#0-0) ), yet its authorization check is skipped entirely whenever `idleCDO == address(0)` ( [2](#0-1) ). Any EOA can therefore set `lastApr` — the fixed APR that drives all interest accounting — during the post-`initialize`, pre-CDO-linking window.

### Finding Description
`initialize` does not set `idleCDO` ( [3](#0-2) ). The guard in `setApr` only reverts `NotAllowed` if `idleCDO` is non-zero and `msg.sender` is neither the CDO nor the manager; otherwise the only constraint is the `maxApr` cap ( [4](#0-3) ). The comment "this can happen only during the setup" acknowledges the hole but leaves it permissionless. Because `setApr` is `public`, `setAprs` and `setAprsWithBuffer` inherit the same unprotected window ( [5](#0-4) ).

`lastApr` is returned verbatim by `getApr` ( [6](#0-5) ), which the CDO queries via `_getStrategyApr` on every accounting update and which determines `expectedEpochInterest` for the epoch. An attacker who sets `lastApr` to `DEFAULT_MAX_APR` (20e18) before the first epoch starts causes the vault to book interest far above the agreed borrower rate.

### Impact Explanation
Broken invariant: fair mint/burn and solvency. Interest is minted to AA/BB tranche NAVs (`lastNAVAA`/`lastNAVBB` updated through `_updateAccounting` in `IdleCDOCreditVault`, [7](#0-6) ) at the inflated rate. When the honest borrower repays only the real agreed amount, the vault's claimable assets fall short of the minted tranche NAV: either BB holders absorb the shortfall via the loss waterfall, or withdraw requests become permanently unclaimable — insolvency equivalent to a loss socialization of `strategyTokenBalance * (inflatedApr - realApr) * epochDuration / YEAR`, up to roughly 20% of TVL per epoch year-equivalent.

### Likelihood Explanation
Exploitable only in the window between `initialize` and the transaction that links `idleCDO` — i.e., if deployment is not atomic, or via front-running on a public mempool. `maxApr` caps the damage at `DEFAULT_MAX_APR` unless the owner later raises it. The attacker needs no role, no deposit, and no KYC.

### Recommendation
Require an explicit authorization in `setApr` even when `idleCDO` is unset (e.g., `msg.sender == owner() || msg.sender == manager` during setup), or set `idleCDO` inside `initialize`/the factory in the same transaction so the `_cdo == address(0)` branch is unreachable externally.

```text
  /// @notice set the fixed apr
  /// @dev only cdo and manager can set the apr. If manager manually set apr from 
  /// here it will not be scaled to include the buffer period
  function setApr(uint256 _apr) public {
    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
  }
```
