### Title
Post-default instant withdraw receipts are recorded in the default epoch's ledger and paid from the isolated recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.requestInstantWithdraw` has no post-default handling: unlike `requestWithdraw` (which routes post-default requests into `postDefaultRequests`), an instant request made after `finalizeDefaultRecovery` is written into `instantWithdrawsRequestsByEpoch[_user][epochNumber]` where `epochNumber` equals `defaultRecoveryEpoch`. `claimInstantWithdrawRequest` then misclassifies that new receipt as a defaulted-epoch receipt and pays it from `defaultRecoveryReserve` at `defaultRecoveryPrice`, spending reserve that was sized only for pre-default claimants and corrupting `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` accounting for every other defaulted claimant.

### Finding Description
After a borrower default, `IdleCDOEpochVariant.finalizeDefault` calls `IdleCreditVault.finalizeDefaultRecovery`, which fixes `defaultRecoveryEpoch = epochNumber` (line 693), `defaultRecoveryReserve` (line 691) and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (line 696). No further `stopEpoch` runs, so `epochNumber` stays pinned at `defaultRecoveryEpoch` for the life of the vault.

`requestInstantWithdraw` (lines 356-375) is not epoch-class aware: it unconditionally executes `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` and `pendingInstantWithdraws += _amount` with `currentEpoch = epochNumber`, which post-default is `defaultRecoveryEpoch`. Compare with `requestWithdraw` (lines 247-257), which explicitly detects `defaultRecoveryFinalized` and stores the receipt in `postDefaultRequests` to keep it out of the defaulted-epoch ledgers.

On the claim side, `claimInstantWithdrawRequest` (lines 380-393) calls `_claimDefaultedInstantWithdrawRequest` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. That function reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (line 844) - which now contains the *post-default* receipt - burns it, and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` (line 915). It also executes `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` (line 853) and `pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis` (line 852), so a mix of pre- and post-default receipts silently zeroes the unfunded-remainder counter.

The broken invariant is receipt-class isolation: one receipt must map to one funding regime. Here a receipt minted after the haircut is settled under the default-epoch recovery ratio and consumes reserve earmarked for pre-default claims, while the CDO-side `collectInstantWithdrawFunds` (lines 398-403) pulls funding keyed on `pendingInstantWithdraws`, which has already been corrupted.

### Impact Explanation
Two concrete impacts:

- Theft/insolvency of the recovery reserve: a post-default instant receipt burns CDO strategy tokens that are worth only `defaultRecoveryPrice` post-haircut, yet its claim decrements `defaultRecoveryReserve`. Since `reserveAmount` was sized exactly for `totalBasis` of pre-default claims (lines 679-691), every reserve unit spent on a post-default claimant is a unit a legitimate defaulted claimant can never receive. Late claimants either get truncated payouts or revert when `defaultRecoveryReserve` underflows in `_transferDefaultRecovery`.
- Permanent freezing: with post-default entries mixed into `instantWithdrawClaimsByEpoch[defaultEpoch]`, the per-claim subtraction at line 853 can be driven inconsistent with `pendingInstantWithdraws`, causing `pendingInstantWithdraws -= _amount` in `collectInstantWithdrawFunds` (line 401) or `defaultRecoveryReserve -= _amount` to revert on underflow, freezing remaining claims.

### Likelihood Explanation
The trigger requires only that the CDO still routes `requestInstantWithdraw` post-default: `allowInstantWithdraw` is `!disableInstantWithdraw && !isProgrammableBorrower` (line 840) and is not gated on `defaulted()`, and the vault-level `requestInstantWithdraw` has no `defaulted`/`defaultRecoveryFinalized` guard of its own (unlike `requestWithdraw`). Any KYC-passed lender holding tranche tokens can open the receipt; claimability additionally needs `defaultInstantWithdrawsFinalized` (i.e., the default epoch had unfunded instant requests), which is the common case when instant requests outran prefunded cash. Uncertainty: if `IdleCDOEpochVariant.requestInstantWithdraw` reverts when the pool is defaulted (e.g., via an `isEpochRunning` check), the exploit path narrows to users who requested instants *before* default but whose funding accounting gets corrupted by the aggregate `instantWithdrawsRequests` ledger sharing; the reserve-mixing defect in `_claimDefaultedInstantWithdrawRequest`/`claimInstantWithdrawRequest` stands regardless because post-default receipts are the only writers left for `instantWithdrawsRequestsByEpoch[*][defaultRecoveryEpoch]`.

### Recommendation
Mirror the `requestWithdraw` post-default handling for instant withdrawals: in `requestInstantWithdraw`, when `defaultRecoveryFinalized`, either revert or record the request in a dedicated post-default bucket (e.g., `postDefaultInstantRequests[_user]`) that never touches `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws`, and pay it from a separately tracked balance rather than `defaultRecoveryReserve`. Alternatively, gate `_claimDefaultedInstantWithdrawRequest` on receipts created strictly before finalization (e.g., a per-user `instantRequestFinalizationFlag` timestamp) so post-default entries in the default-epoch slot are never haircut-paid from the reserve.

### Proof of Concept
Foundry fork sketch (network: mainnet fork with an `IdleCDOEpochVariant` + `IdleCreditVault` pool where `allowInstantWithdraw` is true):

```solidity
function testPostDefaultInstantDrainsRecoveryReserve() public {
    // --- Setup: deposits, epochs, default, finalizeDefaultRecovery ---
    _depositWithUser(alice, 1000e6);          // KYC'd lender
    _depositWithUser(bob,   1000e6);
    vm.prank(alice);
    cdo.requestInstantWithdraw(500e6, AAtranche); // pre-default instant receipt, partially unfunded
    _runEpochThenDefault();                   // borrower fails repayment
    cdo.finalizeDefault(recovered, manager);  // sets defaultRecoveryEpoch, reserve, price < RECOVERY_FULL

    uint256 reserve = vault.defaultRecoveryReserve();
    uint256 epoch   = vault.defaultRecoveryEpoch();
    assertEq(epoch, vault.epochNumber());     // epoch pinned forever

    // --- Attack: Eve requests an instant withdraw AFTER finalization ---
    _depositWithUser(eve, 100e6);
    vm.prank(eve);
    cdo.requestInstantWithdraw(100e6, AAtranche);
    // receipt lands in the *default epoch* ledger
    assertEq(vault.instantWithdrawsRequestsByEpoch(eve, epoch), 100e6);

    // --- Claim: misclassified as defaulted receipt, paid from reserve ---
    vm.prank(eve);
    cdo.claimInstantWithdrawRequest();
    uint256 paid = 100e6 * vault.defaultRecoveryPrice() / RECOVERY_FULL;
    assertEq(vault.defaultRecoveryReserve(), reserve - paid); // reserve leaked

    // Alice's legitimate defaulted claim now reverts or is short by `paid`
    vm.prank(alice);
    vm.expectRevert();                        // defaultRecoveryReserve underflow / NotAllowed
    cdo.claimInstantWithdrawRequest();
}
```

Note: if `IdleCDOEpochVariant.requestInstantWithdraw` reverts while `defaulted()`, the PoC reduces to the accounting-corruption variant - a pre-default unfunded instant claimant (Alice) plus a second user whose `instantWithdrawsRequests` aggregate straddles pre/post-default classifications, showing `pendingInstantWithdraws` being zeroed early and `collectInstantWithdrawFunds` reverting, freezing the queue's claims.
