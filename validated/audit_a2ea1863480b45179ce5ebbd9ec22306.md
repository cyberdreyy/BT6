### Title
Disabling the ZK ElGamal Proof program also blocks `CloseContextState`, permanently locking lamports in proof context accounts - (File: `programs/zk-elgamal-proof/src/lib.rs`)

### Summary
The zk-elgamal-proof program's entrypoint contains a single, coarse "pause" gate that rejects *all* instructions—including `CloseContextState`—whenever the `disable_zk_elgamal_proof_program` feature is active and `reenable_zk_elgamal_proof_program` is not. This is structurally identical to the reported sDaiStrategy bug class: a global pause flag blocks the withdrawal/exit path along with the deposit path, trapping user funds that were already committed to the system.

### Finding Description
The program entrypoint performs the pause check before dispatching to any instruction handler: [1](#0-0) 

This check applies uniformly to every `ProofInstruction` variant, including `CloseContextState`, which is the only mechanism by which a user can reclaim the lamports locked in a `ProofContextState` account: [2](#0-1) 

`CloseContextState` is implemented by `process_close_proof_context`, which is the sole path that zeroes out a proof context account's lamports/data and returns the lamports to the authorized owner: [3](#0-2) 

Because the entrypoint gate short-circuits *before* the `match` on `ProofInstruction`, there is no carve-out that allows `CloseContextState` to execute while other (proof-creating) instructions are disabled. Once a `ProofContextState` account exists (created by a `Verify*` instruction, which allocates and rent-funds the account), the only way to recover its lamports is via `CloseContextState` through this same entrypoint. If governance activates `disable_zk_elgamal_proof_program` without also activating `reenable_zk_elgamal_proof_program`, any ordinary user holding an open `ProofContextState` account cannot close it and reclaim its rent-exempt lamports until governance flips the feature set again—an event entirely outside the user's control.

This mirrors the external report's root cause exactly: a boolean "pause" flag that blocks both entry and exit operations, when the exit/withdraw path should always remain available to let users recover their own funds regardless of pause state.

### Impact Explanation
Ordinary users (not privileged operators) who have created `ProofContextState` accounts (e.g., for confidential transfer proof verification workflows) have lamports locked in these accounts as rent. If the pause feature is activated, those lamports become inaccessible for as long as the pause remains in effect—a duration controlled entirely by validator/governance feature-activation decisions, not by the account owner. This is a fund-lock/denial-of-withdrawal condition reachable from an ordinary user's own transaction attempting to close an account they own.

### Likelihood Explanation
The `disable_zk_elgamal_proof_program` / `reenable_zk_elgamal_proof_program` feature-gate pair exists precisely to allow temporarily disabling this program (e.g., in response to a proof-system vulnerability), so activation of the disable flag without immediately activating the reenable flag is a realistic operational scenario, not a purely theoretical one. Any user with an outstanding `ProofContextState` account at that time is affected.

### Recommendation
Move the pause check (`disable_zk_elgamal_proof_program && !reenable_zk_elgamal_proof_program`) so that it does not block `ProofInstruction::CloseContextState`. Only the proof-verification/creation instructions (which create new locked state) should be gated by the pause; the close/withdraw path should remain callable at all times so that users can always reclaim lamports from accounts they already own, consistent with the general principle that pausing a system must never block asset recovery.

### Proof of Concept
1. A user submits a `VerifyZeroCiphertext` (or any `Verify*`) instruction with an accompanying context-state account, creating a `ProofContextState` account funded with rent-exempt lamports and owned by the zk-elgamal-proof program, with `context_state_authority` set to the user.
2. Governance/validators activate the `disable_zk_elgamal_proof_program` feature (and `reenable_zk_elgamal_proof_program` remains inactive).
3. The user later submits `ProofInstruction::CloseContextState` naming their own context-state account as account 0, a destination account as account 1, and themselves as the signing owner (account 2).
4. Entrypoint dispatch, at [1](#0-0) , evaluates the pause condition before reaching the `match` and returns `InstructionError::InvalidInstructionData` for every instruction type—`CloseContextState` never executes, so `process_close_proof_context` is never reached and the account's lamports remain locked until the feature configuration changes.

fn process_close_proof_context(invoke_context: &mut InvokeContext) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let owner_pubkey = {
        if !instruction_context.is_instruction_account_signer(2)? {
            return Err(InstructionError::MissingRequiredSignature);
        }

        *instruction_context.get_key_of_instruction_account(2)?
    };

    let proof_context_account_pubkey = *instruction_context.get_key_of_instruction_account(0)?;
    let destination_account_pubkey = *instruction_context.get_key_of_instruction_account(1)?;
    if proof_context_account_pubkey == destination_account_pubkey {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut proof_context_account = instruction_context.try_borrow_instruction_account(0)?;
    if *proof_context_account.get_owner() != id() {
        return Err(InstructionError::InvalidAccountOwner);
    }
    let proof_context_state_meta =
        ProofContextStateMeta::try_from_bytes(proof_context_account.get_data())?;
    if proof_context_state_meta.proof_type == ProofType::Uninitialized.into() {
        return Err(InstructionError::UninitializedAccount);
    }

    let expected_owner_pubkey = proof_context_state_meta.context_state_authority;

    if owner_pubkey != expected_owner_pubkey {
        return Err(InstructionError::InvalidAccountOwner);
    }

    let mut destination_account = instruction_context.try_borrow_instruction_account(1)?;
    destination_account.checked_add_lamports(proof_context_account.get_lamports())?;
    proof_context_account.set_lamports(0)?;
    proof_context_account.set_data_length(0)?;
    proof_context_account.set_owner(system_program::id().as_ref())?;

    Ok(())
}
