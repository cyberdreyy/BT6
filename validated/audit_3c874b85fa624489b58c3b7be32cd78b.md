### Title
Queued withdraw requests can be cancelled after the epoch loss is known, letting a user dodge the loss haircut - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
`IdleCDOEpochQueue.deleteWithdrawRequest` lets any requester cancel a queued withdrawal at any time — including during the buffer period immediately after `stopEpochWithDuration` has publicly declared a `_lossAmount`, but before the manager calls `processWithdrawRequests` and freezes the request at the post-loss `epochWithdrawPrice`. This creates a free option: request a withdrawal during the running epoch, observe the epoch outcome, and either let the request be processed (if no loss) or delete it to recover unimpaired tranche tokens (if a loss was declared). The analogue to the delayed-cancel timelock bug is the asymmetry between when a queued action becomes irreversible and when its outcome becomes known.

### Finding Description
`requestWithdraw` locks tranche tokens in the queue for `epochNumber + 1` while the epoch is running (`contracts/IdleCDOEpochQueue.sol:131-143`). `deleteWithdrawRequest` refunds the tranche tokens as long as `epochWithdrawPrice[_requestEpoch]` is still 0, with no check on whether the epoch is running, stopped, or in the buffer period (`contracts/IdleCDOEpochQueue.sol:203-218` — the comment explicitly states requests "can be deleted even if the epoch is running").

The price for queued withdrawals is only fixed when the manager calls `processWithdrawRequests`, which calls `cdoEpoch.requestWithdraw(_pending, tranche)` and stores `_underlyingsRequested * ONE_TRANCHE / _pending` as `epochWithdrawPrice` (`contracts/IdleCDOEpochQueue.sol:298-329`). When an epoch is stopped with a loss via `stopEpochWithDuration(..., _lossAmount)`, the loss is applied to the strategy's accounting before `processWithdrawRequests` runs, so the queue's epoch withdraw price reflects the haircut.

Sequence:

1. Epoch running: attacker calls `queue.requestWithdraw(shares)`; tokens are locked for epoch N+1.
2. Manager calls `stopEpochWithDuration(apr, 0, duration, lossAmount)` declaring a loss. This is on-chain and publicly visible.
3. Before/independently of the manager calling `processWithdrawRequests` (buffer period, or the request can simply sit unprocessed across an `startEpoch`/`stopEpoch` boundary as in `testDeleteWithdrawRequestForNonProcessedEpoch`), the attacker calls `deleteWithdrawRequest(N+1)` and gets back their full tranche tokens, which still price at the pre-loss virtual price.
4. Other queued withdrawers are processed at the loss-adjusted `epochWithdrawPrice`.

The attacker effectively exits at pre-loss price while the loss is socialized over everyone else, including the remaining queued withdrawers who were locked into the same epoch.

### Impact Explanation
Any user with a queued withdrawal can selectively escape a declared loss, receiving back tranche tokens worth more than the haircutted `epochWithdrawPrice` that honest requesters receive. The avoided haircut is value extracted from the pool: the loss that should have been borne pro-rata by the cancelling requester is shifted onto remaining withdrawers and tranche holders. Loss magnitude scales with `lossAmount` and the size of the attacker's queued position; a whale requester can dodge the full haircut on their entire queued balance.

### Likelihood Explanation
The preconditions are minimal: the attacker only needs a KYC-passed wallet (`_checkAllowed` in `requestWithdraw`, `:415-421`) and a queued request, which is the natural state of any user intending to withdraw. The window is deterministic — `stopEpochWithDuration` is a public transaction, the declared `_lossAmount` is visible in the mempool/calldata and on-chain state, and `deleteWithdrawRequest` is permissionless and ungated, so it can be called in the same block right after the stop, or any time later while the request is still unprocessed. There is no guard (skim, flag, or epoch check) preventing deletion between loss declaration and price fixation.

### Recommendation
Restrict `deleteWithdrawRequest` so a queued withdraw request cannot be cancelled once the epoch it targets has been stopped — e.g., require `cdoEpoch.isEpochRunning()` and that the request's target epoch is still `epochNumber + 1` (i.e., disallow deletion during the buffer period after the epoch in which the request was made), or record and enforce that requests for an epoch become immutable once `stopEpoch`/`stopEpochWithDuration` executes for the preceding epoch. Symmetrically, consider whether `deleteRequest` for deposits needs a similar boundary check.

### Proof of Concept
Foundry fork PoC sketch (pattern follows `testDeleteWithdrawRequestForNonProcessedEpoch` / `testProcessWithdrawalClaimsWithZeroRoundedQueuePayout` in `test/foundry/IdleCDOEpochQueue.t.sol`):

```solidity
function testDeleteWithdrawRequestAfterDeclaredLoss() public {
    _stopCurrentEpoch();                          // enter epoch #1 buffer
    address attacker = makeAddr('attacker');
    address honest = makeAddr('honest');
    uint256 attackerTranches = _depositWithUser(attacker, 100e6);
    uint256 honestTranches   = _depositWithUser(honest,   100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();                        // epoch #1 running

    _requestWithdrawWithUser(attacker, attackerTranches);
    _requestWithdrawWithUser(honest, honestTranches);

    uint256 reqEpoch = strategy.epochNumber() + 1;

    // stop epoch with a declared loss (see test file for loss plumbing:
    // compute lossAmount vs totalBasis, fund borrower with partial repayment)
    _stopCurrentEpochWithLoss(lossAmount);        // loss now public, epochWithdrawPrice[reqEpoch] still 0

    // BEFORE manager calls queue.processWithdrawRequests():
    vm.prank(attacker);
    queue.deleteWithdrawRequest(reqEpoch);        // succeeds: attacker recovers full tranche tokens
    assertEq(tranche.balanceOf(attacker), attackerTranches);

    // honest user's request is processed at the loss-adjusted price
    vm.prank(manager);
    queue.processWithdrawRequests();
    vm.prank(manager);
    queue.processWithdrawalClaims(strategy.epochNumber());

    uint256 honestBalPre = underlying.balanceOf(honest);
    vm.prank(honest);
    queue.claimWithdrawRequest(strategy.epochNumber());
    uint256 honestReceived = underlying.balanceOf(honest) - honestBalPre;

    // attacker exits at pre-loss virtualPrice; honest gets haircutted price
    assertLt(honestReceived, honestTranches * cdoEpoch.virtualPrice(address(tranche)) / 1e18);
}
```

The key assertion is that `deleteWithdrawRequest` succeeds after `stopEpochWithDuration` has fixed the loss into strategy accounting but before `processWithdrawRequests` freezes `epochWithdrawPrice`, returning tranche tokens redeemable at the pre-loss virtual price while the honest requester is haircutted.
