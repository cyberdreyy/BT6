## Analysis

The Besu advisory describes a missing **presence check**: a validation function correctly *detects* that a required field is missing, but the caller failed to wire that detection into an enforceable rejection rule, so processing continued as if everything were valid. There is a directly analogous pattern in the chainlink-node OIDC authentication flow.

### Title
Missing `return` after failed email-claim presence check lets OIDC token exchange complete authentication and create a session despite detecting a missing identity field - (File: `core/sessions/oidcauth/oidc.go`)

### Summary
`oidcAuthenticator.handleTokenExchange` explicitly checks whether the OIDC ID token's `email` claim is present, logs an error, and writes an error HTTP response when it is missing — but it does not `return` after doing so. Execution falls through and completes the full login flow: it derives an RBAC role from the (successfully validated) group claims, inserts a new row into `oidc_sessions` with an empty `user_email`, sets the session cookie, and finally overwrites the earlier error write with an `HTTP 200` JSON success response.

### Finding Description
In `handleTokenExchange`: [1](#0-0) 

the `!ok` branch (missing/non-string `email` claim) logs and writes an error body but has no `return` statement, unlike every other error branch in the same function (compare the `id_token` missing check and the ID-token verification failure check, which both `return` immediately): [2](#0-1) [3](#0-2) 

Because of the missing `return`, the code proceeds to compute the RBAC role from `idClaims` and to persist a new authenticated session keyed to an empty `user_email`: [4](#0-3) 

and then sets the session cookie and responds with success: [5](#0-4) 

The same `oidc_sessions.user_email` column is later used to bulk-invalidate a user's other sessions purely by string equality on email: [6](#0-5) 

### Impact Explanation
An OIDC-authenticated principal whose ID token carries valid group claims (satisfying `IDClaimsToUserRole`) but lacks (or has a non-string) `email` claim will still receive a fully functional, cookie-backed session with a real RBAC role — the server never actually enforces the "email required" rule it claims to check. All such sessions are persisted with the same empty-string `user_email`. Because `ClearNonCurrentSessions` matches and deletes sessions purely by `lower(user_email)`, any authenticated holder of one such degraded session can invoke session-clearing logic that deletes every other session sharing the empty email — including sessions of unrelated authenticated users who also hit this code path — a cross-user session interference/impersonation-adjacent condition caused directly by the missing presence enforcement. It also breaks audit attribution (`audit.AuthLoginSuccessNo2FA` records an empty `email`), undermining accountability for privileged actions taken under that session's role.

### Likelihood Explanation
Reachability requires only that the configured OIDC identity provider issue (or the requester's identity/config in that provider lacks) an `email` claim in the ID token — no privilege beyond being able to complete an OIDC login flow is required to reach this branch; the group/role claims used to grant the session's role are independently and correctly validated, so the missing-email condition alone is sufficient to trigger the fall-through. This depends on the OIDC provider's claim configuration (e.g., email scope not granted or optional), making the likelihood moderate rather than trivial, matching the "Remote / Medium" characterization used in the source bug class.

### Recommendation
Add a `return` immediately after the error response in the `!ok` branch of the `email` claim check (and audit the other missing-`return` branch at the DB-insert-error path a few lines below it, which has the same pattern), so that any detected missing required identity field aborts the authentication flow instead of silently completing it.

### Proof of Concept
1. Configure a chainlink node with OIDC auth where the IdP's ID token for some authenticated principal omits the `email` claim (or returns it as a non-string), while the principal's claims still satisfy one of the configured RBAC group claims.
2. Complete the `/oidc-login` → `/oidc-exchange` flow as this principal.
3. Observe `handleTokenExchange` logs "Failed to get email from claims" and writes an `InternalServerError` body, but does **not** return: it proceeds to insert an `oidc_sessions` row with `user_email = ''`, sets a valid session cookie, and finally responds `200 {"success":true}`.
4. The returned session cookie is fully functional against `AuthorizedUserWithSession` (`core/sessions/oidcauth/oidc.go:351`), granting the derived role with `Email` empty.
5. Any other principal reaching this same fallthrough shares the identical `user_email=''` row-matching key; calling `/sessions` clear-other-sessions functionality (`ClearNonCurrentSessions`) from one such session invalidates the other unrelated user's session.

func (oi *oidcAuthenticator) ClearNonCurrentSessions(ctx context.Context, sessionID string) error {
	var email string
	if err := oi.ds.GetContext(ctx, &email, "SELECT user_email FROM oidc_sessions WHERE id = $1", sessionID); err != nil {
		return err
	}
	_, err := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE lower(user_email) = lower($1) AND id != $2", email, sessionID)
	return err
}
