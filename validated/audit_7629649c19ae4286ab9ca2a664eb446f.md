### Title
Withdraw parser's account-count heuristic mislabels a proof-context account as `owner` when `account_indexes` length is inconsistent with zero offsets - ([File: transaction-status/src/parse_token/extension/confidential_transfer.rs])

### Summary
`parse_confidential_transfer_instruction`'s `Withdraw` branch decides which account slot is `equalityProofContextStateAccount`, `rangeProofContextStateAccount`, or the signer/owner slot using a heuristic bound (`account_indexes.len().saturating_sub(1)`) instead of a value derived deterministically from the proof-offset flags. An attacker who crafts a raw transaction with `equality_proof_instruction_offset == 0`, `range_proof_instruction_offset == 0`, but only 4 account indices (instead of the 5 required by the real spec for that combination) causes the parser to skip assigning `rangeProofContextStateAccount` and instead label that same account key as `owner` in `parse_signers`.

### Finding Description
In the `Withdraw` arm [1](#0-0) , `offset` starts at 2, and each of the three conditional blocks (sysvar, equality-context, range-context) only assigns an account key if `offset < account_indexes.len().saturating_sub(1)`. This bound is meant to "reserve" the last account for the owner/multisig-signers, but it is derived purely from the *length of the supplied account list*, not from the semantics implied by the offset flags. `check_num_token_accounts(account_indexes, 4)` [2](#0-1)  only enforces a minimum of 4 accounts, even though the real spl-token-2022 Withdraw instruction requires 5 accounts when both proof offsets are 0 (account, mint, equality-context, range-context, authority).

Exploit flow: an attacker submits (or the parser later processes via `getTransaction`) a `CompiledInstruction` for `ConfidentialTransferInstruction::Withdraw` with `equality_proof_instruction_offset = 0`, `range_proof_instruction_offset = 0`, and `account_indexes.len() == 4` (account, mint, ctx-lookalike, bystander-key). With `offset=2`: `has_sysvar` is `false` so no sysvar consumed; the equality-context check succeeds (`2 < 4-1=3`) and assigns `account_indexes[2]` as `equalityProofContextStateAccount`, `offset` becomes 3; the range-context check then evaluates `3 < 3` which is `false`, so `rangeProofContextStateAccount` is *not* assigned even though `range_proof_instruction_offset == 0` says it should be. `parse_signers` is then called with `offset = 3`, labeling `account_indexes[3]` — which per protocol should be the range-proof context account — as `"owner"` [3](#0-2) .

This transaction will fail at runtime in the real spl-token-2022 program (insufficient accounts), but Solana still records failed transactions with their original instruction/account layout, and `parse_token`/`parse_confidential_transfer_instruction` is invoked unconditionally on any transaction message regardless of execution outcome when serving `getTransaction`/`getConfirmedTransaction`/transaction-history RPC responses. The check-guard here (`check_num_token_accounts`, which only enforces a lower bound of 4) does not prevent the mismatched-length case that decouples the offset semantics from the heuristic threshold, so the misassignment is fully reachable from unprivileged, single-call RPC read paths on attacker-controlled/attacker-submitted transaction data.

### Impact Explanation
This is a decoder/parse-fidelity bug: it does not corrupt consensus state or crash the validator, but it causes JSON-RPC responses (`getTransaction`, `getConfirmedTransaction`, and any parsed-instruction display) to report a bystander/proof-context account key as the confidential-withdraw `owner`, which is a misreported authority/owner for a token instruction — matching the "wrong data returned to a query" / decoder-misreporting bounty category rather than a crash or consensus bug.

### Likelihood Explanation
Fully attacker-controlled and reproducible with a single crafted transaction: the attacker only needs to submit (it will fail on-chain, but still be queryable) or otherwise get indexed a transaction containing a `Withdraw` instruction with `equality_proof_instruction_offset = 0`, `range_proof_instruction_offset = 0`, and exactly 4 account indices. No validator/leader/staked privileges are required — an unprivileged client constructing a raw message and calling `getTransaction` on it after inclusion (even as a failed tx) triggers the mislabeling deterministically.

### Recommendation
Replace the length-based heuristic (`offset < account_indexes.len().saturating_sub(1)`) with an explicit, deterministic account count computed directly from `equality_proof_instruction_offset` and `range_proof_instruction_offset` (i.e., compute the expected number of leading accounts before the authority/signer slot based on the offset flags, matching the real spl-token-2022 instruction builder logic), and fail parsing (or emit an explicit inconsistency marker) rather than silently reassigning the leftover account to `owner` when `account_indexes.len()` does not match the expected count for the given offsets.

### Proof of Concept
Rust unit test to add to `transaction-status/src/parse_token/extension/confidential_transfer.rs`:

```rust
#[test]
fn test_withdraw_account_count_mismatch_mislabels_owner() {
    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let bystander = Pubkey::new_unique(); // should be rangeProofContextStateAccount per spec
    let account_keys = AccountKeys::new(&[
        spl_token_2022_interface::id(),
        account,
        mint,
        Pubkey::new_unique(), // equality proof context
        bystander,
    ], None);

    // Manually build WithdrawInstructionData bytes with both offsets = 0,
    // but supply only 4 account indices instead of the required 5.
    let instruction_data = build_withdraw_data(/* eq_offset */ 0, /* range_offset */ 0, /* amount */ 42, /* decimals */ 9);
    let account_indexes: [u8; 4] = [1, 2, 3, 4]; // account, mint, eq_ctx, bystander

    let parsed = parse_confidential_transfer_instruction(
        &instruction_data,
        &account_indexes,
        &account_keys,
    ).unwrap();

    // Bug: bystander (meant to be rangeProofContextStateAccount) is reported as "owner"
    assert_eq!(parsed.info["owner"], json!(bystander.to_string()));
    assert!(parsed.info.get("rangeProofContextStateAccount").is_none());
}
```

Expected (post-fix) assertion: the test should instead fail parsing or correctly report `bystander` as `rangeProofContextStateAccount` and never populate `owner` from an account that is not the actual authority/signer per the spl-token-2022 spec.
