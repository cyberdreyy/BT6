### Title
`kamino_harvest_reward` fails to bind `user_state`/`farm_state`/`user_reward_ata` to the target `bank`, allowing harvest against a mismatched obligation - (File: `programs/marginfi/src/instructions/kamino/harvest_reward.rs`)

### Summary
`KaminoHarvestReward` accepts `user_state`, `farm_state`, and `user_reward_ata` as fully `UncheckedAccount`s with no on-chain constraint tying them to the `bank` account's stored obligation reference, unlike sibling instructions (`kamino_withdraw`, `kamino_deposit`) which explicitly bind `integration_acc_1`/`integration_acc_2` to the bank. This lets a caller supply a `bank` (and its `liquidity_vault_authority` signer) that does not match the `user_state`/`farm_state` pair actually being harvested from.

### Finding Description
In `programs/marginfi/src/instructions/kamino/harvest_reward.rs`, `kamino_harvest_reward` performs:
1. `cpi_harvest_rewards` — CPI's into the Kamino Farms program using `payer = liquidity_vault_authority` (PDA-signed for the passed-in `bank`), together with attacker-supplied `user_state`, `farm_state`, `global_config`, `rewards_vault`, `rewards_treasury_vault`, `farm_vaults_authority`, and `user_reward_ata`. [1](#0-0) 
2. Computes `received` as the balance delta on `user_reward_ata`, then transfers `received` from `user_reward_ata` to `destination_token_account` (the global fee wallet's ATA), again signing with the same `bank`'s `liquidity_vault_authority`. [2](#0-1) 

Critically, the `Accounts` struct only validates the `bank`'s asset tag and derives `liquidity_vault_authority` from `bank.key()`, but places **no constraint** binding `user_state`/`farm_state` to `bank` (e.g., no `address = bank.load()?.integration_acc_2` check), and no `associated_token::authority = liquidity_vault_authority` constraint on `user_reward_ata`: [3](#0-2) 

By contrast, other Kamino integration instructions such as `kamino_withdraw` explicitly load and bind `integration_acc_2` (the obligation/user-state account) to the specific `bank` being operated on, and the off-chain CLI (`p0-cli`) derives `user_state` strictly from `bank.integration_acc_2`: [4](#0-3) [5](#0-4) 

This means the on-chain instruction itself relies entirely on an implicit, off-chain-only convention (client always fetches `bank.integration_acc_2`) rather than an enforced on-chain guard — the exact "same owner context" binding described in the question is missing at the marginfi layer. Whether this is fully exploitable end-to-end also depends on whether the actual Kamino Farms program performs an internal `user_state.owner == payer` check; that logic lives outside this repository (only its IDL/mocked CPI stub is present here), so I cannot confirm from this codebase alone whether the downstream program would reject a `payer`/`user_state` mismatch. The `user_reward_ata`→`destination_token_account` transfer_checked in step 2 does require `user_reward_ata`'s actual SPL owner field to equal `liquidity_vault_authority` for that specific `bank`, which limits (but does not fully close) the value-redirection surface: it does not stop harvesting from a mismatched obligation, only stops sending proceeds anywhere but the fee wallet.

### Impact Explanation
If the Kamino Farms program does not itself enforce `user_state.owner == payer`, an attacker can invoke `kamino_harvest_reward` with `bank` = Bank A (to get a signer, `liquidity_vault_authority_A`) while supplying `user_state`/`farm_state` belonging to a different obligation (e.g., Bank B's Kamino position). This would let Bank A's harvest flow drain accrued rewards intended for Bank B's obligation, permanently altering the Kamino reward-accrual bookkeeping for Bank B and violating the stated invariant "claim exactly once from the correct obligation." Even though funds still land at the canonical global fee wallet ATA (limiting direct attacker profit), this breaks reward accounting integrity across banks/obligations and can starve the legitimate bank of its rewards — a durable, cross-bank state inconsistency with financial impact on the correct owner of the harvested rewards.

### Likelihood Explanation
The instruction is permissionless (no signer check beyond the transaction fee payer) and reachable by any caller who can construct arbitrary account metas, matching the "unprivileged attacker" threat model. The only friction is that the exploit's full impact hinges on undocumented (from this repo's perspective) internal validation of the real, off-chain Kamino Farms program, which cannot be confirmed here. The missing on-chain binding in marginfi's own `Accounts` struct, however, is a concrete and reproducible code-level gap regardless of that external dependency.

### Recommendation
Add on-chain constraints binding `user_state` and `farm_state` to the specific `bank` being harvested (e.g., `address = bank.load()?.integration_acc_2` and `address = bank.load()?.integration_acc_1` farm-state analog), and constrain `user_reward_ata` with `associated_token::authority = liquidity_vault_authority` and `associated_token::mint = reward_mint`, mirroring the pattern already used in `kamino_withdraw`/`kamino_deposit`.

### Proof of Concept
Extend `tests/specs/kamino/k13_KfarmsHarvestReward.spec.ts`:
1. Set up two Kamino banks (Bank A, Bank B) each with their own farm obligation/`user_state`/`farm_state`/reward ATA, both accruing rewards.
2. Call `kaminoHarvestReward` with `bank = Bank A` but `userState`/`farmState` swapped to Bank B's values, keeping `userRewardAta` owned by Bank A's `liquidity_vault_authority` (required for the final transfer to succeed).
3. Assert (a) whether the transaction succeeds despite the mismatch (would indicate the on-chain program does not itself detect the cross-bank swap), and (b) that Bank B's on-chain reward accrual/farm `user_state` was consumed while Bank B's own subsequent `kaminoHarvestReward` call yields zero rewards — demonstrating the "claim exactly once from the correct obligation" invariant is violated at the marginfi account-constraint layer.

pub fn kamino_harvest_reward(
    ctx: Context<KaminoHarvestReward>,
    reward_index: u64,
) -> MarginfiResult {
    let pre_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    ctx.accounts.cpi_harvest_rewards(reward_index)?;
    let post_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    let received = post_transfer_balance - pre_transfer_balance;
    ctx.accounts
        .cpi_transfer_obligation_owner_to_destination(received)?;
    Ok(())
}

impl<'info> KaminoHarvestReward<'info> {
    pub fn cpi_harvest_rewards(&self, reward_index: u64) -> MarginfiResult {
        let program = self.farms_program.to_account_info();
        let accounts = HarvestReward {
            payer: self.liquidity_vault_authority.to_account_info(),
            user_state: self.user_state.to_account_info(),
            farm_state: self.farm_state.to_account_info(),
            global_config: self.global_config.to_account_info(),
            reward_mint: self.reward_mint.to_account_info(),
            user_reward_token_account: self.user_reward_ata.to_account_info(),
            rewards_vault: self.rewards_vault.to_account_info(),
            rewards_treasury_vault: self.rewards_treasury_vault.to_account_info(),
            farm_vaults_authority: self.farm_vaults_authority.to_account_info(),
            scope_prices: optional_account!(self.scope_prices),
            token_program: self.token_program.to_account_info(),
        };
        let bump = self.bank.load()?.liquidity_vault_authority_bump;
        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), bump);
        let cpi_ctx = CpiContext::new_with_signer(program.key(), accounts, signer_seeds);
        harvest_reward(cpi_ctx, reward_index)?;
        Ok(())
    }
