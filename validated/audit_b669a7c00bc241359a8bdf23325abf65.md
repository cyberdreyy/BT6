### Title
Cross-request response hijacking via unkeyed savedCallbacks map overwrite in legacy WebAPI trigger handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each request's callback in the shared `h.savedCallbacks` map keyed only by the attacker-supplied `msg.Body.MessageId`, with no duplicate/in-flight check. Two concurrent `gateway.ProcessRequest` calls (from different, potentially unrelated senders) using the same `MessageId` will race on this map, so the DON's response for one request can be delivered to the other request's HTTP caller.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:266-278`) creates a fresh `handlerscommon.NewCallback()` per HTTP call and blocks on `callback.Wait(ctx)`. For legacy DON-routed messages it calls `h.HandleLegacyUserMessage(ctx, msg, callback)`.

In `core/services/gateway/handlers/capabilities/handler.go:411-414`:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
```
This unconditionally overwrites any existing entry for the same `MessageId`. Later, `handleWebAPITriggerMessage` (`core/services/gateway/handlers/capabilities/handler.go:148-161`) looks the callback up and deletes it by `msg.Body.MessageId` alone:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
```
`msg.Body.MessageId` is fully attacker-controlled (`core/services/gateway/api/message.go:42-43`), and `Message.Validate()` only checks length/format and signature validity — it never enforces that the ID is unique across senders or in-flight requests (`core/services/gateway/api/message.go:54-88`).

Exploit flow:
1. Attacker A sends a legacy signed request with `MessageId = "X"`. `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA` and forwards to DON nodes.
2. Before the DON responds, Attacker/User B (or the same attacker in a second connection, since MessageId is not scoped to sender/session) sends another legacy request with the same `MessageId = "X"`. This overwrites `savedCallbacks["X"] = callbackB`.
3. When a DON node responds for A's original request (echoing `MessageId = "X"`), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, which is now `callbackB`, and delivers A's response data to B's HTTP connection via `callbackB.SendResponse`.
4. A's own `callback.Wait(ctx)` then times out (or later receives B's response if B's request finishes first and overwrote A's slot before A resolves), causing responses to be misdirected between unrelated HTTP callers.

This directly matches the pattern flagged in the question: unlike `v2/http_trigger_handler.go`'s `setupCallback` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:398-405`), which explicitly checks `if _, found := h.callbacks[requestID]; found` and rejects with `jsonrpc.ErrConflict`, the legacy `capabilities/handler.go` path has no such duplicate-ID guard.

### Impact Explanation
Cross-user response confusion: an unauthenticated/unprivileged HTTP client of the gateway can cause another user's legacy DON response payload (which may contain data intended only for that user, e.g., API/workflow execution results) to be delivered into the attacker's own HTTP response, or cause the victim's legitimate response to be lost/misdirected to a third party. This matches the "request impersonation / attacker-controlled data returned to another user" bounty impact class.

### Likelihood Explanation
No special privilege is required — any client able to send a signed legacy request to the gateway's public HTTP endpoint can choose an arbitrary `MessageId` value (only length/format constrained, not uniqueness constrained across senders). The race window exists between `HandleLegacyUserMessage` storing the callback and the DON's async response arriving (potentially tens of milliseconds to seconds), which is a realistic and repeatable window for two racing requests. This is a pure timing race, easily reproduced in tests with two goroutines.

### Recommendation
In `capabilities/handler.go`'s `HandleLegacyUserMessage`, check for an existing in-flight entry with the same `MessageId` under `h.mu` and reject the new request (e.g., `UserMessageParseError`/conflict) before storing the callback, mirroring the duplicate-ID guard already present in `v2/http_trigger_handler.go`'s `setupCallback`. Additionally consider binding the map key to `(Sender, MessageId)` rather than `MessageId` alone, since `Sender` is derived from the verified signature.

### Proof of Concept
Handler-level integration test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two valid, differently-signed `triggerRequest` messages (different `PrivateKey`/sender) but with the identical `MessageId` "dup-id".
2. Fire both through `handler.HandleLegacyUserMessage` concurrently from two goroutines, each with its own `hc.NewCallback()` (`callbackA`, `callbackB`), synchronized so the second write happens right after the first (use a lock/signal to force the overwrite deterministically).
3. Simulate the DON responding to the first request only, by calling `handler.handleWebAPITriggerMessage(ctx, respMsgForA, nodeAddr)` where `respMsgForA.Body.MessageId == "dup-id"` and payload is a marker unique to A's expected data.
4. Assert `callbackB.Wait(ctx)` receives A's marker payload (proving cross-user leakage) while `callbackA.Wait(ctx)` times out or never resolves — demonstrating that B's HTTP response body ends up containing data destined for A's request, violating request binding.
