### Title
Unbounded per-slot notification cost for `programSubscribe` scales with attacker-controlled account churn - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
A single `programSubscribe` subscription on an attacker-owned program has its per-slot notification cost driven entirely by `Bank::get_program_accounts_modified_since_parent`, which scans *all* accounts stored in that slot owned by the program with no cap on the returned count. `check_commitment_and_notify` then iterates the full result set and calls `notifier.notify` once per account, so the number of outbound pubsub messages (and their aggregate serialization/JSON-parsing cost) scales linearly with however many program-owned accounts the attacker creates/modifies in a single slot.

### Finding Description
`notify_watchers` handles `SubscriptionParams::Program` by calling: [1](#0-0) 
which invokes `bank.get_program_accounts_modified_since_parent(&params.pubkey)`: [2](#0-1) 
This delegates to `Accounts::load_by_program_slot`, which scans the *entire* account storage for the current slot via `scan_slot`/`scan_account_storage`, collecting every account owned by `program_id` with no size or count limit: [3](#0-2) 

The result vector is passed into `check_commitment_and_notify`, which runs `filter_program_results` (encoding each account, e.g. base58/base64/jsonParsed) and then loops over every filtered item, invoking `notifier.notify` for each one individually: [4](#0-3) [5](#0-4) 

There is no per-subscription cap on the number of accounts returned/encoded/sent for a program subscription — unlike `getProgramAccounts` over HTTP, which can require a secondary index or scan-size limit for large account sets (see `get_filtered_indexed_accounts`'s `byte_limit_for_scan` parameter used elsewhere), `load_by_program_slot` bypasses that path entirely since it only scans a single slot's storage rather than the full index. The `RpcProgramAccountsConfig` filters (`verify_filters`/`optimize_filters`) only validate filter *syntax* (max filter count/bytes for memcmp/dataSize), not the number of *matching* accounts that will be returned.

Because this only inspects storage for a single slot, the attacker cannot decouple the cost from the block's own resource limits (compute budget, transaction count per block) — the cost is bounded by how many program-owned accounts can be created/mutated within the compute/transaction capacity of one slot, not by an independent subscription-level cap. Still, this means one subscription's notification cost is fully driven by attacker-supplied on-chain activity rather than a fixed, small, per-subscription limit.

### Impact Explanation
This matches the "unbounded cost for a single low-rate call" bounty category: with one `programSubscribe` websocket call, an attacker who authors many account-creating/mutating transactions to their own program within a single slot causes the validator's pubsub delivery path to encode and emit one notification message per modified account for that slot, with no independent bound tied to the subscription itself. This increases CPU cost (encoding/serialization) and outbound network traffic proportional to attacker-chosen account churn per slot, for every node serving that RPC subscription.

### Likelihood Explanation
Feasible with just: (1) deploying/owning a program, (2) opening a single `programSubscribe` on it, and (3) submitting transactions (within the block's compute/transaction capacity) that create/modify many program-owned accounts in one slot. This is fully reproducible and repeatable every slot without violating the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` restriction, since only the initial subscribe call counts as an RPC call — subsequent account writes are normal on-chain transactions.

### Recommendation
Add a bounded cap to program-subscription notification generation: e.g., limit the number of accounts returned/encoded per notification batch in `filter_program_results`/`check_commitment_and_notify` for `Program` subscriptions (analogous to `byte_limit_for_scan` used for indexed scans), and/or coalesce per-slot program account changes into a single capped notification with an explicit "too many results" signal instead of one message per account.

### Proof of Concept
Integration test plan (extends existing `test_program_subscribe`/`test_program_subscription` style tests in `rpc/src/rpc_subscriptions.rs` and `client-test/tests/client.rs`):
1. Create a `Bank`/`BankForks`, register a `RpcSubscriptions` with one `programSubscribe` on an attacker-owned `program_id` (no filters).
2. In slot N, submit N `system_transaction::create_account` (or a custom program storing accounts) transactions creating N distinct accounts owned by `program_id`, then freeze/notify the bank for that slot.
3. Repeat with increasing N (e.g. 10, 100, 1000, 5000 — as many as fit in one slot's compute/tx-count limits).
4. Count outbound pubsub notifications and measure total serialized payload size / CPU time in `check_commitment_and_notify`/`filter_program_results`.
5. Assert: notification count/payload size grows linearly with N with no cap, i.e. `notifications.len() == N` for all tested N, demonstrating the absence of a bounded per-subscription notification limit (as contrasted with `test_get_filtered_indexed_accounts_limit_exceeded` in `runtime/src/bank/tests.rs`, which shows such a limit exists for `getProgramAccounts` scans but not here).

fn filter_program_results(
    accounts: Vec<(Pubkey, AccountSharedData)>,
    params: &ProgramSubscriptionParams,
    last_notified_slot: Slot,
    bank: Arc<Bank>,
) -> (impl Iterator<Item = RpcKeyedAccount> + use<>, Slot) {
    let accounts_is_empty = accounts.is_empty();
    let encoding = params.encoding;
    let filters = params.filters.clone();
    let keyed_accounts = accounts.into_iter().filter(move |(_, account)| {
        filters
            .iter()
            .all(|filter_type| filter_allows(filter_type, account))
    });
    let accounts = if is_known_spl_token_id(&params.pubkey)
        && params.encoding == UiAccountEncoding::JsonParsed
        && !accounts_is_empty
    {
        let accounts = get_parsed_token_accounts(bank, keyed_accounts);
        Either::Left(accounts)
    } else {
        let accounts = keyed_accounts.map(move |(pubkey, account)| RpcKeyedAccount {
            pubkey: pubkey.to_string(),
            account: encode_ui_account(&pubkey, &account, encoding, None, None),
        });
        Either::Right(accounts)
    };
    (accounts, last_notified_slot)
}

    /// Returns all the accounts from `slot`
    ///
    /// If `program_id` is `Some`, filter the results to those whose owner matches `program_id`
    pub fn load_by_program_slot(
        &self,
        slot: Slot,
        program_id: Option<&Pubkey>,
    ) -> Vec<KeyedAccountSharedData> {
        self.scan_slot(slot, |stored_account| {
            program_id
                .map(|program_id| program_id == stored_account.owner())
                .unwrap_or(true)
                .then(|| (*stored_account.pubkey(), stored_account.take_account()))
        })
    }
