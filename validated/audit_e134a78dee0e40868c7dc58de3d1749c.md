### Title
Instant-withdraw receipts can be claimed before borrower funding is collected, double-spending the strategy's funded-claim reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays out the full aggregate `instantWithdrawsRequests[_user]` at par in underlying, with no check that the receipts being claimed were actually funded by a prior `collectInstantWithdrawFunds` call. Unlike normal withdraw claims, which enforce a one-epoch maturity via `epochNumber <= lastWithdrawRequest`, the instant path has no maturity/funding gate at all. An unprivileged user can request an instant withdrawal during a running epoch (after the epoch's instant-withdraw funding was already collected at `startEpoch`) and immediately claim it, receiving underlying that belongs to other users' funded-but-unclaimed receipts.

### Finding Description
`requestInstantWithdraw` burns the CDO's strategy tokens, mints receipt tokens to the user, and increases `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` [1](#0-0) . Funding is decoupled: the CDO pulls underlying only via `collectInstantWithdrawFunds`, which decreases `pendingInstantWithdraws` and transfers tokens in [2](#0-1) . That collection happens once per epoch at epoch start ("funds will get transferred from borrower when epoch starts" [3](#0-2) ), so any request created during a running epoch sits unfunded until the next `startEpoch`.

`claimInstantWithdrawRequest`, however, pays `instantWithdrawsRequests[_user]` unconditionally via `_transferFundedClaim` [4](#0-3) . `_transferFundedClaim` only guards the isolated `defaultRecoveryReserve`; the rest of the strategy's underlying balance — which includes still-unclaimed funded claims of other users — is freely spendable [5](#0-4) . This is the double-free analog: one unit of funded underlying backs two claims (the victim's unclaimed funded receipt and the attacker's unfunded instant receipt), and it is paid out twice.

### Impact Explanation
The attacker receives underlying equal to their instant request without the borrower ever funding it, drawn from the strategy's balance that is reserved for other users' already-funded claims. When the victims later claim, the transfer fails on insufficient balance — a direct theft equal to the attacker's request amount and a permanent/insolvent freeze of the victims' claims. The broken invariant is "one receipt one payout": strategy underlying earmarked for funded receipts is consumed by unfunded ones.

### Likelihood Explanation
Requires `allowInstantWithdraw` enabled and at least one other user's funded instant-withdraw underlying sitting unclaimed in the strategy (or any residual strategy balance). The attacker is an ordinary KYC'd lender calling `requestInstantWithdraw` then `claimInstantWithdrawRequest` mid-epoch through `IdleCDOEpochVariant` [6](#0-5)  — no privileged action needed, and no default/loss precondition.

### Recommendation
Track funded vs unfunded instant receipts separately (e.g., per-epoch `instantWithdrawsRequestsByEpoch` gating like the normal claim path), or have `claimInstantWithdrawRequest` only pay receipts created in epochs that have already gone through `collectInstantWithdrawFunds`. Alternatively, gate `requestInstantWithdraw` at the CDO so requests can only be opened in the window before the funding collection that will cover them.

### Proof of Concept
1. Fork Foundry setup: epoch running, `allowInstantWithdraw == true`. Victim requested an instant withdraw last epoch; its funds were collected by `collectInstantWithdrawFunds` at `startEpoch`, so the strategy holds underlying backing the victim's unclaimed receipt.
2. Attacker calls `IdleCDOEpochVariant.requestInstantWithdraw` mid-epoch: receipt minted, `pendingInstantWithdraws` increases, no funding collected.
3. Attacker immediately calls `claimInstantWithdrawRequest`; `_transferFundedClaim` transfers underlying from the strategy balance that backs the victim's receipt.
4. Victim calls `claimInstantWithdrawRequest`; `underlyingToken.safeTransfer` reverts — funds were double-spent.

Caveat: I was unable to fully read the CDO-side `requestInstantWithdraw` timing guard before iteration limits; if it restricts requests to pre-`startEpoch` windows only, this path is not reachable and the finding reduces to defense-in-depth. A fork PoC should confirm that step 2 is callable while an epoch is running.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
