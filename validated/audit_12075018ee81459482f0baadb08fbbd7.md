### Title
Stale Confirmations From Removed Multisig Members Persist and Count Toward the Confirmation Threshold - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
The reported bug class is that an authoritative identity (`sy_program`) used inside a privileged instruction is never re-validated against the current state of the object that is supposed to own it (the vault), letting a stale/attacker-controlled value stand in for the correct one. The same class of bug exists in this repository's multisig contracts: `confirm()` counts entries in the `confirmations` set without re-validating that each entry still corresponds to a *current* member of `self.members`, and `delete_member()` only purges confirmations for requests that the removed member itself authored, not confirmations the removed member left on requests authored by someone else. This lets a stale confirmation from an already-removed member count toward `num_confirmations`, letting a request execute with fewer live-member confirmations than the configured threshold.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` reads the raw `confirmations` `HashSet<String>` for a request and only checks the *count* against `self.num_confirmations`: [1](#0-0) 

The set is never filtered against `self.members`; it is a persistent map keyed only by request ID, so any confirmation ever inserted stays valid indefinitely unless explicitly removed.

When a member is removed via `DeleteMember`, `delete_member()` removes outstanding requests, but only requests *authored* by the removed member: [2](#0-1) 

```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
```

This filter matches on `r.member` (the request's *creator*), not on membership inside the `confirmations` set for requests created by other members. Consequently, if the removed member had previously confirmed (but not created) some other pending request, that confirmation entry is never cleaned up and remains in `self.confirmations`. `current_member()` is only used to validate the *caller* of `confirm()`, not to re-validate previously stored confirmations: [3](#0-2) 

The binding that should hold is:
`count(live confirmations on request R) == count(confirmations on R made by accounts that are currently in self.members)`

Instead, the implementation enforces:
`count(all historical confirmation entries on request R) >= num_confirmations`

which is not the same equality once membership changes between the time a confirmation is recorded and the time the request is later confirmed to the threshold.

The same structural weakness (confirmations map not scrubbed of an ousted signer's confirmations except on requests they created) is present in the legacy `multisig/src/lib.rs` (`DeleteKey` action / `remove_request`): [4](#0-3) 

### Impact Explanation
This is a Critical-severity, threshold-bypass class of finding per the given impact rubric ("a multisig request executed below threshold"). A pending, unexecuted request (e.g., a `Transfer` of the multisig account's NEAR balance) can be pushed to execution with only `num_confirmations - 1` *live* member confirmations plus one stale confirmation belonging to a member who has since been removed from the multisig — i.e., NEAR funds can be moved by a party set that, at execution time, no longer meets the configured `K`-of-`N` authorization threshold.

### Likelihood Explanation
Exploitation requires an ordinary sequence of legitimate multisig operations (member A confirms someone else's pending request, then A is later removed via a separate `DeleteMember` request) — no special privilege, redeploy, or foundation/owner action is required beyond what any member can already do through `confirm`/`add_request`/`DeleteMember`, all of which are standard multisig flows reachable by any current member. The only precondition is that a request stays pending (below threshold) while membership changes, which is expected in normal multisig usage (e.g., rotating a compromised or departing member while other requests are in flight).

### Recommendation
When counting confirmations in `confirm()`, filter `confirmations` to only those entries whose author is still present in `self.members` before comparing against `self.num_confirmations`. Additionally, `delete_member()` (and the equivalent `DeleteKey` path in `multisig/src/lib.rs`) should purge the removed member's confirmation entries from *all* pending requests' `confirmations` sets, not only from requests the removed member authored.

### Proof of Concept
Assume a `multisig2` contract initialized with `members = {A, B, C}` and `num_confirmations = 2`.

1. `B` calls `add_request` to create Request `X` — a `Transfer` of the account's NEAR balance to an attacker-controlled receiver. `X.member = B`, `confirmations(X) = {}`.
2. `A` calls `confirm(X)`. `confirmations(X) = {A}`; `1 < 2`, so `X` stays pending (not executed).
3. Independently, a `DeleteMember { member: A }` request `Y` is created and confirmed by `B` and `C` (2 live confirmations, meeting threshold), executing and removing `A` from `self.members`. `delete_member()` only removes requests where `r.member == A` (i.e., requests `A` created); Request `X` was created by `B`, so it is untouched and `confirmations(X)` still contains the stale entry `A`.
4. `C` (now the only remaining live confirmer, aside from `B` who never explicitly confirmed `X`) calls `confirm(X)`. `confirmations(X).len() + 1 = 2 >= num_confirmations (2)`, so `execute_request(X)` runs and the `Transfer` executes.
5. Result: Request `X` executed with only one live member's confirmation (`C`) plus one stale confirmation from a member (`A`) who had already been removed from the multisig — funds moved despite failing to meet the actual 2-of-live-members threshold. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
