Confirmed: cache paths are used raw and unsanitized in the RmDir cleanup call.

### Title
Unsanitized cache:paths entries allow rm -rf outside build/cache root during failed-extraction cleanup - (File: shells/abstract.go)

### Summary
`addExtractCacheCommand` writes an `RmDir(cachePath)` for every entry in `Cache.Paths` when cache extraction fails and `FF_CLEAN_UP_FAILED_CACHE_EXTRACT` is enabled, using the raw, job-controlled path string with no normalization or containment check. Since `RmDir` compiles directly to `rm -rf <path>` (bash) or `Remove-Item -Recurse -Force` (PowerShell) on that literal string, an attacker who controls `.gitlab-ci.yml`'s `cache:paths` can supply an absolute path or a `../`-escaping relative path to have the generated job script delete files outside the build directory.

### Finding Description
In `shells/abstract.go`, `cacheExtractor` builds `cacheOptions.Paths` directly from the job spec (`common.Build.Cache[].Paths`, i.e. `cache:paths` in `.gitlab-ci.yml`) with no validation [1](#0-0) . These same raw strings are passed through to `addExtractCacheCommand` as `cachePaths` and, on extraction failure with `FF_CLEAN_UP_FAILED_CACHE_EXTRACT` on, are handed to `w.RmDir(cachePath)` verbatim, with no call to `w.Absolute()`/`w.Join()` to confine them to the build/cache root and no rejection of absolute paths or `..` segments: [2](#0-1) .

`BashWriter.RmDir` turns that string directly into `rm -r -f <path>` (optionally preceded by a `chmod`), with no path canonicalization or root check: [3](#0-2) . `PsWriter.RmDir` similarly resolves the path via `resolvePath` but does not reject absolute or `..`-containing paths either [4](#0-3) .

Because the generated job script has already `cd`'d into the build directory earlier (`writeCdBuildDir` calling `w.Cd(info.Build.FullProjectDir())`, [5](#0-4) ), a relative `cache:paths` entry containing `../../etc` resolves (via normal shell path resolution) to a location outside the build directory, and an absolute entry like `/etc` is used as-is, bypassing the build root entirely. The existing unit tests only assert that `RmDir` is called with the exact `cachePath` strings from the config (e.g. `"path1"`, `"path2"`), confirming no sanitization/rejection step exists in this code path [6](#0-5) .

No path-containment check (e.g. rejecting `filepath.IsAbs` paths or entries resolving outside `BuildDir`) exists anywhere between job config ingestion and the `RmDir` call in this cleanup branch.

### Impact Explanation
An attacker-controlled job can cause the runner's generated build script to run `rm -rf` (or PowerShell's recursive `Remove-Item`) on an attacker-chosen absolute path or a path that escapes the build directory via `../` traversal, provided a cache extraction attempt fails (which the attacker can trivially force, e.g. by making the cache-extractor fail or simply having no cache object present combined with `FF_CLEAN_UP_FAILED_CACHE_EXTRACT=true`). This causes deletion of files outside the job's build/cache root within the execution environment (container or shell-executor filesystem) — a destructive, attacker-triggered file deletion primitive, though it is bounded by whatever filesystem/user permissions the job process itself already has (it does not grant new privileges or escape a properly isolated sandbox, but it does violate the "file operations must stay within intended build/cache/artifact roots" invariant).

### Likelihood Explanation
Fully attacker-controlled and easily reproducible: the attacker only needs to author their own `.gitlab-ci.yml` with a `cache:paths` entry such as `../../etc` (or an absolute path), set/rely on `FF_CLEAN_UP_FAILED_CACHE_EXTRACT` (opt-in feature flag — check current default), and trigger a cache-extraction failure (e.g., no matching cache object). No special runner configuration or admin action is required beyond the feature flag being enabled, and the destructive `RmDir` line executes deterministically on every extraction failure for every path in the list.

### Recommendation
Validate/sanitize each `cachePath` before emitting `RmDir` in `addExtractCacheCommand`: reject or `filepath.Clean`+contain paths that are absolute or that resolve outside the build/cache directory (similar to zip-slip protections already used for archive extraction), e.g. compute the path relative to `info.Build.FullProjectDir()`/`BuildDir` and verify it does not contain `..` traversal that escapes that root, refusing (and warning) instead of calling `w.RmDir` when it does.

### Proof of Concept
Add a unit test in `shells/abstract_test.go` analogous to `TestAbstractShell_extractCacheWithMultipleFallbackKeysWithCleanup`, but set `Cache[0].Paths = []string{"../../etc"}` (or `"/etc"`). Run `shell.cacheExtractor(...)` with a mocked `ShellWriter` and assert that:
- `mockWriter.On("RmDir", "../../etc")` is NOT invoked (fix), or
- currently (bug), the mock records `mockWriter.On("RmDir", "../../etc").Once()` being called exactly as configured — proving the raw, unsanitized traversal path reaches `RmDir` unmodified, matching the existing pattern seen for `"path1"`/`"path2"` in `shells/abstract_test.go:2559-2562`.
