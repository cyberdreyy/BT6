### Title
Re-requesting a withdrawal after a loss-adjusted epoch aliases the haircutted receipt into a par-value funded claim (`lastWithdrawRequest` overwrite) - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2020-12278 is an "equivalent names" bug: two different spellings resolve to the same file, so a security decision made under one name is bypassed under the other. The vault analog is an equivalent-receipt bug: a user's pending withdraw receipt exists under two identities — the per-epoch loss-adjusted ledger `withdrawsRequestsByEpoch[user][epoch]` keyed by `lastWithdrawRequest[user]`, and the aggregate par-value ledger `withdrawsRequests[user]`. Because `requestWithdraw` overwrites `lastWithdrawRequest[user]` on every new request, a receipt that was only partially funded through `lossRecoveryPriceByEpoch` can be re-aliased to a later epoch and then claimed at par via `_claimFundedWithdrawRequest`, stealing the unfunded haircut from other claimants.

### Finding Description
In `requestWithdraw`, each new request accumulates into `withdrawsRequests[user]`/`withdrawsRequestsByEpoch[user][epoch]` and unconditionally sets `lastWithdrawRequest[user] = currentEpoch` (IdleCreditVault.sol:282-294).

When the borrower short-funds a stop, `collectWithdrawFunds` zeroes `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epochNumber] < RECOVERY_FULL` — i.e., only `amount * price` underlying is transferred in for all receipts of that epoch (IdleCreditVault.sol:411-429).

The loss-adjusted claim path, `_claimLossAdjustedWithdrawRequest`, looks up the loss epoch exclusively via `lastWithdrawRequest[user]`:

```
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```
(IdleCreditVault.sol:789-795)

If the user makes a second `requestWithdraw` in a later, fully funded epoch, `lastWithdrawRequest` now points at that epoch, `lossRecoveryPriceByEpoch[newEpoch] == 0`, and the loss path returns 0 without clearing anything. Execution then reaches `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[user]` — still containing the full un-haircutted loss-epoch basis — at par via `_transferFundedClaim`, and burns the corresponding receipt tokens (IdleCreditVault.sol:319-349).

The guards do not stop this:
- The epoch-wait check `epochNumber <= lastWithdrawRequest[user]` passes once the new epoch ends.
- `_claimDefaultedWithdrawRequest` correctly keys on `defaultRecoveryEpoch` (a global), but the loss path keys on the per-user mutable `lastWithdrawRequest` — the two naming schemes for the same receipt are inconsistent, exactly the NTFS-ADS-style equivalence flaw.
- `_transferFundedClaim` only protects `defaultRecoveryReserve`, not other users' loss-adjusted entitlements.

Note the deliberate semantics elsewhere ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests") confirm old receipts are expected to remain payable — but they are payable at par even though only the haircutted amount was ever funded.

### Impact Explanation
Direct theft / insolvency. Suppose epoch N ends with a 50% `lossRecoveryPrice`. Attacker's epoch-N receipt basis is X; the strategy received only X/2 for it. Attacker re-requests Y in epoch N+1 (fully funded). After epoch N+1 stops, `claimWithdrawRequest` pays X + Y at par instead of X/2 + Y, extracting X/2 that belongs to the aggregate pool backing other epoch-N claimants. The attacker needs only to be an allowed (KYC'd) lender; the loss itself is produced by the honest manager/borrower via `stopEpochWithDuration`, so no privileged collusion is required. Other epoch-N claimants are left undercollateralized — late claimants revert or receive less than their `lossRecoveryPrice` entitlement.

### Likelihood Explanation
Requires (a) an epoch closed with a partial-funding loss via `collectWithdrawFunds`/`stopEpochWithDuration` — a supported, non-default code path added for borrower shortfalls, and (b) the attacker holding or creating a pending receipt that epoch and re-requesting in a later epoch, both unprivileged actions. No timing race is needed; the claim can be made at leisure once a subsequent epoch completes. Likelihood is moderate: it needs one loss-adjusted epoch to occur.

### Recommendation
Do not key the loss-adjusted claim on the mutable `lastWithdrawRequest`. Either:
- Track a per-user "oldest unfunded loss epoch" pointer or iterate `lossRecoveryPriceByEpoch` epochs that have entries in `withdrawsRequestsByEpoch[user]` before allowing the funded path, or
- In `requestWithdraw`, revert (or force-clear the loss-adjusted claim) when `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` and `withdrawsRequestsByEpoch[user][thatEpoch] != 0`, so a new request cannot alias an unsettled haircutted receipt.

### Proof of Concept
Foundry fork PoC outline (mirroring `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `deal`):

```solidity
function testLossReceiptAliasedToPar() external {
    // attacker = KYC'd AA holder; victim = another AA holder
    uint256 X = 100_000 * ONE_SCALE;
    uint256 Y = 10_000 * ONE_SCALE;

    _depositWithUser(attacker, X, true);
    _depositWithUser(victim,   X, true);

    // epoch 0 runs, epoch 1 ends with partial funding: lossRecoveryPrice = 50%
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, apr, expected);

    vm.prank(attacker);
    cdoEpoch.requestWithdraw(X, address(AAtranche));   // basis X in epoch 1
    vm.prank(victim);
    cdoEpoch.requestWithdraw(X, address(AAtranche));

    _startEpochAndCheckPrices(1);
    // manager stops epoch with a realized loss so collectWithdrawFunds gets < pendingBasis
    // -> lossRecoveryPriceByEpoch[1] = RECOVERY_FULL / 2
    _stopEpochWithPartialFunding(1);                    // strategy receives 2 * X/2 = X

    // attacker does NOT claim; requests again in epoch 2 (fully funded stop)
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(Y, address(AAtranche));    // lastWithdrawRequest -> epoch 2

    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, apr, expected);         // fully funds Y

    // loss path skipped: lossRecoveryPriceByEpoch[2] == 0
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    // BUG: paid X + Y at par instead of X/2 + Y; strategy is short X/2 for victim
    assertEq(underlying.balanceOf(attacker) - balPre, X + Y);

    // victim's epoch-1 claim (X * 50%) now undercollateralized -> reverts/shortfall
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest();                    // insolvent or drained
}
```

Key assertion: `_claimLossAdjustedWithdrawRequest` returns 0 for the attacker because `lastWithdrawRequest` was overwritten, while `withdrawsRequests[attacker]` still includes the haircutted epoch-1 basis, so `_transferFundedClaim` pays it at par.

Uncertainty noted: the exact helper for a partial-funding stop (`stopEpochWithDuration` plumbing in `IdleCDOEpochVariant`) was not fully traced in this pass, but the strategy-side accounting (`collectWithdrawFunds`, `lossRecoveryPriceByEpoch`, `_claimLossAdjustedWithdrawRequest`, `_claimFundedWithdrawRequest`) is fully verified above and is where the aliasing defect resides.
