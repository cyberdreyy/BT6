### Title
DuplicateBlockFound guard in v1 uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, allowing a signer to sign two conflicting tenure-change blocks for the same tenure - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`SortitionsView::validate_tenure_change_payload` in `v1.rs` checks for a prior block in the current tenure using `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, whereas the newer `v2.rs` implementation deliberately uses `signer_db.get_last_signed_block(&block.header.consensus_hash)` because, per its own comment, "we already confirmed... current tenure is valid... check we are not reorging the tenure blocks. Only blocks we have signed (locally or globally accepted) count here." If a signer has locally accepted (signed) but not yet globally accepted a block in a tenure, v1's guard misses it and lets a second, conflicting tenure-change block for the same tenure be signed.

### Finding Description
The intended equality is UNIQUENESS: for a given tenure (`consensus_hash`)/height, a signer must sign at most one tenure-start block. `v1.rs`'s check: [1](#0-0) 
queries only globally-accepted blocks. `v2.rs`, addressing the exact same duplicate-tenure-change scenario, was changed to query `get_last_signed_block`, explicitly covering "locally or globally accepted" blocks: [2](#0-1) 

Call sequence: `check_proposal` (v1.rs, lines 319-326) invokes `validate_tenure_change_payload` whenever the proposed block contains a tenure-change payload. That function performs the parent-tenure and parent-block checks, then relies solely on `get_last_globally_accepted_block` to detect that this signer already signed a competing tenure-start block for the same tenure. If the signer locally accepted (i.e., produced its own valid signature share for) a prior block in that tenure but the block never reached the global 70% threshold (e.g., due to network partition, competing signer sets, or a stalled aggregation), `get_last_globally_accepted_block` returns `None`, and the duplicate check silently passes, allowing the signer to sign a second, conflicting tenure-change block for the exact same `consensus_hash`.

An attacker who wins one miner slot can exploit this by: (1) submitting a first tenure-change `BlockProposal` for tenure `T` that a target signer signs (locally accepted, but attacker prevents/delays global acceptance by not gossiping/aggregating enough responses across the rest of the signer set), then (2) submitting a second, conflicting tenure-change `BlockProposal` for the same tenure `T` (e.g., different parent commit or different transaction set) to the same signer. Because `get_last_globally_accepted_block` returns `None` for that consensus hash, `validate_tenure_change_payload` does not raise `RejectReason::DuplicateBlockFound`, and the signer proceeds to sign the second, conflicting block.

### Impact Explanation
This breaks the UNIQUENESS/equivocation-guard safety property that a signer must not sign two conflicting blocks for the same tenure/height. If both blocks separately reach threshold across the signer set (e.g., because different subsets of signers see different "first" proposals and each subset's local checks miss the duplicate the same way), this creates two independently signed, conflicting canonical blocks at the same tenure position — a chain safety violation (fork) rather than a mere liveness issue. This is a Critical-severity finding per the "signer signing... conflicting block (chain safety)" category, and it is directly repeatable by any single miner-slot holder able to submit two proposals.

### Likelihood Explanation
Preconditions are attacker-controllable and require no privileged access: the attacker needs to win one miner slot (normal PoX/BTC mining cost) and craft two conflicting `BlockProposal` tenure-change messages for the same tenure, gossiped via the miner's normal proposal channel. The failure state (`get_last_globally_accepted_block` returning `None` while a local-only accepted block exists) is a realistic and even common condition — global acceptance requires aggregating responses from the full signer set and can easily lag or fail to complete before a second competing proposal arrives, especially under normal network latency/partial-signing conditions, not just adversarial partitioning. Because `v2.rs` was already patched for exactly this scenario with `get_last_signed_block`, this reflects an inconsistency where `v1.rs` (still in use, e.g., for pre-migration chainstate versions) retains the vulnerable check. This is repeatable on every tenure boundary that a v1-configured signer processes.

### Recommendation
In `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload`, replace `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` with `signer_db.get_last_signed_block(&block.header.consensus_hash)` (mirroring the v2.rs fix), so that any locally-accepted-but-not-yet-globally-accepted block in the tenure also triggers the `DuplicateBlockFound` rejection, preventing the signer from ever signing two conflicting tenure-change blocks for the same tenure regardless of global-acceptance state.

### Proof of Concept
Rust test plan (to be added under `stacks-signer/src/chainstate/tests/v1.rs`, mirroring the existing `v2.rs` `DuplicateBlockFound` test found via search):
1. Construct a `SignerDb` in-memory instance and a `SortitionsView` (v1) configured with a current sortition for tenure `T`.
2. Build block proposal `A` containing a `TenureChangePayload` for tenure `T` with a valid parent; call `check_proposal`/`validate_tenure_change_payload` and simulate the signer locally accepting it — i.e., insert `A` into `signer_db` via the local-acceptance path (`put_block_state`/equivalent used by `get_last_signed_block` but NOT the globally-accepted path used by `get_last_globally_accepted_block`).
3. Assert `signer_db.get_last_globally_accepted_block(&T)` returns `None` (confirms the precondition: only locally accepted, not global).
4. Assert `signer_db.get_last_signed_block(&T)` returns `Some(A)` (confirms A is visible via the "signed" query, matching v2's guard).
5. Construct a second, conflicting block proposal `B` for the same tenure `T` (different transactions/parent commit) and call `validate_tenure_change_payload(proposed_by, tenure_change_B, &B, &mut signer_db, &client)`.
6. Assert (bug reproduction) that the v1 call returns `Ok(())` instead of `Err(RejectReason::DuplicateBlockFound)` — demonstrating the guard fails to fire.
7. As the fix verification, re-run step 5/6 after patching v1.rs to use `get_last_signed_block`, and assert it now returns `Err(RejectReason::DuplicateBlockFound)`, matching v2's behavior.
