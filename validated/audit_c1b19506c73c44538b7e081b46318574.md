### Title
Address-squatting front-run of `LockupFactory::create` lets an attacker permanently fix a victim's lockup terms and whitelist - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` deploys a new lockup contract at the deterministic account id `hex::encode(&env::sha256(owner_account_id)[..20]).<factory>`, but it is callable by any account with `MIN_ATTACHED_BALANCE` and takes attacker-supplied `vesting_schedule`, `lockup_timestamp`, `release_duration`, and `whitelist_account_id`. Because NEAR account ids can only be created once, an attacker can call `create` for a victim's `owner_account_id` before the legitimate grantor does, permanently occupying that address with attacker-chosen terms and a whitelist/pool contract the attacker controls.

### Finding Description
The invariant the protocol relies on is:

`lockup_account(owner_account_id).terms == grantor_intended_terms(owner_account_id)`

i.e., whichever grantor legitimately owns/controls the vesting grant for `owner_account_id` is the only party whose call to `create` should determine the terms living at that derived address.

In `create`, the only check performed is the deposit size: [1](#0-0) 
There is no `assert_called_by_foundation`, no owner check, and no restriction tying `predecessor_account_id` to `owner_account_id`. Any unprivileged caller can supply an arbitrary `owner_account_id` (the victim's account), and arbitrary `vesting_schedule`, `lockup_timestamp`, `release_duration`, and `whitelist_account_id` (pointing at a whitelist/pool/poll contract the attacker deployed): [2](#0-1) 

The account id created is fully deterministic from `owner_account_id` alone: [3](#0-2) 

`Promise::new(lockup_account_id).create_account()` will only succeed once per account id on NEAR; a second `create_account()` call to the same id fails at the protocol level. `on_lockup_create` only inspects `is_promise_success()` and refunds the deposit on failure — it has no way to detect or prevent squatting, it only handles the case where the *attacker's own* creation transaction fails: [4](#0-3) 

Exploit flow:
1. Attacker deploys a malicious whitelist/pool/poll contract they control.
2. Attacker calls `create(victim_owner_account_id, ..., whitelist_account_id: Some(attacker_whitelist))` with `MIN_ATTACHED_BALANCE` attached, before the legitimate grantor/foundation creates the victim's real lockup.
3. The lockup contract is deployed at `hex::encode(sha256(victim_owner_account_id)[..20]).<factory>` with attacker-chosen `vesting_schedule`, `release_duration`, `lockup_timestamp`, and a `staking_pool_whitelist_account_id` pointing at the attacker's contract instead of the real NEAR Foundation whitelist.
4. When the legitimate grantor later calls `create` for the same `owner_account_id`, `create_account()` fails because the account already exists; `on_lockup_create` sees `is_promise_success() == false` and simply refunds the grantor's deposit — the real grant is silently blocked while the attacker-controlled lockup remains live and is treated by the ecosystem/UI as "the" lockup for that owner.
5. The victim (`owner_account_id`), believing/being told they have a lockup, interacts with (or is directed to) this contract, which only permits staking with whitelisted pools the attacker deployed, or otherwise misroutes flows the protocol treats as trusted.

No existing guard in this file (`assert_self`, `is_promise_success`) restricts *who* may call `create` or validates that `predecessor_account_id` bears any relationship to `owner_account_id`; the squatting is a valid, un-reverted state transition from the contract's point of view.

### Impact Explanation
This satisfies the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attacker permanently fixes the vesting schedule, release duration, and — most dangerously — the staking pool whitelist for the victim's lockup, since the whitelist contract governs which staking pools funds inside the lockup may be delegated to. Directing the whitelist to an attacker-controlled contract lets the attacker later cause the victim (or the foundation topping up the lockup) to have funds routed toward staking pools the attacker chose, which the protocol continues to treat as authorized. This is repeatable against any `owner_account_id` whose real lockup has not yet been created, i.e., against the entire population of not-yet-provisioned grant recipients.

### Likelihood Explanation
The attack requires only `MIN_ATTACHED_BALANCE` (3.5 NEAR) and knowledge of the victim's future `owner_account_id`, which is generally public/predictable (e.g., grant recipients are often known ahead of contract deployment, e.g. team/investor/community addresses). `create` has no access control beyond deposit size, so any account can call it. The attack is cheap, requires no special privileges, and is race-condition-free from the attacker's perspective — the attacker only needs to submit before the legitimate creator does.

### Recommendation
Restrict `create` to be callable only by the foundation account (`assert_called_by_foundation` style check) or require the `owner_account_id` to sign/co-authorize the creation (e.g., via a full-access key action or a pre-registered claim), and/or use a nonce/salt in the derived account id tied to a value only the legitimate grantor can supply, so an attacker cannot squat the deterministic address ahead of the real grant.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs tests module
#[test]
fn test_attacker_squats_victim_lockup_address() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker deploys/owns `attacker_whitelist_account_id()` and calls create
    // for the victim's owner_account_id before the real grantor does.
    context.is_view = false;
    context.predecessor_account_id = String::from(attacker_account_id());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // victim owner_account_id
        lockup_duration,
        None,
        None,
        None,
        Some(attacker_whitelist_account_id()), // attacker-controlled whitelist
    );

    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    contract.on_lockup_create(
        lockup_account(), // deterministic address for account_tokens_owner()
        ntoy(30).into(),
        String::from(attacker_account_id()),
    );
    // At this point lockup_account() is deployed with attacker_whitelist_account_id().

    // Now the legitimate grantor tries to create the real lockup for the same owner.
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // create_account() for an already-existing account id fails at runtime;
    // simulate failure and show funds are refunded, not applied -
    // the attacker-parameterised contract remains the only lockup at that address.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner()),
    );
    assert_eq!(res, false); // legitimate grant never lands; attacker's terms/whitelist persist
}
```
This demonstrates that `lockup_account(owner_account_id).staking_pool_whitelist_account_id` ends up equal to the attacker's chosen `attacker_whitelist_account_id()` rather than the grantor's intended `whitelist_account_id()`, breaking the claimed invariant.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
