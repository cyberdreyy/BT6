### Title
Unbounded per-request CPU cost via zstd compression of attacker-controlled account data in `getAccountInfo`/`getProgramAccounts` with `encoding=base64+zstd` - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account`'s `UiAccountEncoding::Base64Zstd` arm runs `zstd::stream::write::Encoder::write_all`/`finish` over the entire (optionally sliced) account data with no size cap, unlike the `Base58`/`Binary` arms. The RPC-side wrapper `encode_account` in `rpc/src/rpc.rs` only enforces `MAX_BASE58_BYTES` for `Binary`/`Base58` encodings and applies no equivalent cap for `Base64` or `Base64Zstd`, so a single `getAccountInfo` call against an attacker-grown, highly compressible account forces the validator to compress up to the full permitted account size on every request.

### Finding Description
The encode path is:

`rpc/src/rpc.rs::get_account_info` → `get_encoded_account` → `encode_account` → `account_decoder::encode_ui_account` [1](#0-0) [2](#0-1) 

In `encode_account`, the only pre-encoding size guard checks `MAX_BASE58_BYTES` and applies exclusively to `Binary`/`Base58`: [3](#0-2) 

For any other encoding, including `Base64Zstd`, `encode_ui_account` is called directly with no length restriction: [4](#0-3) 

Inside `encode_ui_account`, the `Base64Zstd` arm constructs a `zstd::stream::write::Encoder` and writes the full (sliced) account data into it, then base64-encodes the compressed output: [5](#0-4) 

Unlike `encode_bs58` (used by `Binary`/`Base58`), which explicitly bails out with an error string once the slice exceeds `MAX_BASE58_BYTES` (128 bytes): [6](#0-5) 

there is no analogous length check before the zstd compression path executes. The compression cost is therefore proportional to the size of the account's on-chain data, which an unprivileged attacker fully controls via normal account-resize instructions (e.g. `system_processor`'s account-extend paths bounded only by `MAX_PERMITTED_DATA_LENGTH`). Because zstd compresses highly redundant data (e.g., all zeros) efficiently in terms of output size but still must scan/process the entire input buffer, an attacker can make the *input* to the compressor arbitrarily large (up to `MAX_PERMITTED_DATA_LENGTH`) while keeping the compressed *output* small — the cost is paid on the compression pass over the full buffer, not on the resulting payload size, and no RPC-level cap on the input length to this arm exists independent of the account's own on-chain size. Subscription reads via `rpc_subscriptions.rs::filter_account_result` call the same `encode_ui_account` function with the same lack of a Base64Zstd size guard. [7](#0-6) 

### Impact Explanation
Every single `getAccountInfo` (or `getProgramAccounts`, or `accountSubscribe`) call with `encoding=base64+zstd` against an attacker's own grown account forces the validator's RPC thread to run a full compression pass over the entire account buffer (up to `MAX_PERMITTED_DATA_LENGTH`), with cost scaling with attacker-chosen data size and no independent RPC-side cap. This matches the "unbounded cost for a single low-rate call" category — a single request within the allowed rate (≤1 per `CLUSTER_SLOT_TIME_TARGET/2`) causes CPU-time amplification disproportionate to normal request handling, unlike the `Base58` path which is explicitly capped at 128 bytes before any encoding work is attempted.

### Likelihood Explanation
Fully attacker-controlled and requires no privileged access: the attacker only needs to own/deploy an account (e.g., via the System Program's allocate/extend instructions or any owned program) and grow its data size using normal, permission-less resize instructions up to `MAX_PERMITTED_DATA_LENGTH`, then issue a single `getAccountInfo` call with `{"encoding":"base64+zstd"}`. This is fully repeatable on every call and requires no leader/gossip/validator control, no multiple clients, and no unfiltered `getProgramAccounts`.

### Recommendation
Add an explicit size guard for `UiAccountEncoding::Base64Zstd` (and ideally `Base64`) in `encode_account` (`rpc/src/rpc.rs`) or in `encode_ui_account` (`account-decoder/src/lib.rs`) analogous to the existing `MAX_BASE58_BYTES` check — e.g., reject or downgrade encoding when the sliced data length exceeds a fixed, RPC-configurable ceiling well below `MAX_PERMITTED_DATA_LENGTH`, or bound the zstd compression level/window and impose a hard input-size cap independent of the account's actual on-chain size before invoking `zstd::stream::write::Encoder`.

fn bench_base64_zstd_scales_with_account_size() {
    use std::time::Instant;
    let sizes = [1024usize, 1_000_000, 10_000_000]; // approaching MAX_PERMITTED_DATA_LENGTH

            data: vec![0u8; size], // maximally compressible
            ..Account::default()

        let _ = encode_ui_account(
            &Pubkey::default(),
            &account,
            UiAccountEncoding::Base64Zstd,
            None,
            None,
        );
        let elapsed = start.elapsed();
        println!("size={size} elapsed={elapsed:?}");
        // Assert elapsed time grows with size, i.e. no fixed budget:
        // compare against Base64 baseline cost, which is near-constant per byte
        // and orders of magnitude cheaper for the same size.
    }
    // Expected: Base64Zstd latency grows measurably with `size` up to
    // MAX_PERMITTED_DATA_LENGTH, with no early-exit/size-cap check analogous
    // to `encode_bs58`'s MAX_BASE58_BYTES guard.
}

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
