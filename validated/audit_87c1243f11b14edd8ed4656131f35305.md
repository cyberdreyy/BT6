## Title
Unstaked NEAR permanently frozen when `withdraw`/`withdraw_all` transfer fails, because ledger is debited before the transfer's success is verified - (`staking-pool/src/internal.rs`)

### Summary
`StakingContract::internal_withdraw` decrements the caller's `unstaked` balance and the pool's `last_total_balance` and *then* fires a bare `Promise::new(account_id).transfer(amount)` with no `.then()` callback to confirm the transfer succeeded. [1](#0-0)  If that transfer fails on-chain (e.g. `account_id` no longer exists/insufficient account balance guarantees, or any other receipt-level failure independent of the calling transaction), NEAR balance never leaves the staking pool, but the ledger has already recorded the withdrawal as complete and irreversible - the user's recorded claim (`account.unstaked`) no longer equals what is actually still held for them by the pool, and there is no code path to reconcile it.

### Finding Description
`withdraw`/`withdraw_all` call `internal_withdraw`, which does the following in order: [2](#0-1) 
1. Assert `unstaked >= amount` and the unstaking delay has passed.
2. `account.unstaked -= amount; self.internal_save_account(...)`.
3. `Promise::new(account_id).transfer(amount)`.
4. `self.last_total_balance -= amount`.

Steps 2 and 4 happen synchronously and are committed as final state changes in the same function call, regardless of whether the `transfer` promise created in step 3 actually succeeds when it executes as a separate receipt. Unlike other flows in this codebase (e.g. `staking-pool/src/lib.rs`'s `on_stake_action`, or `lockup/src/owner_callbacks.rs`'s `on_staking_pool_withdraw`), there is no `.then(ext_self::on_withdraw...)` callback using `is_promise_success()` to verify the transfer and roll back `account.unstaked`/`last_total_balance` on failure. Compare this with the pattern used elsewhere in this same repo, where every other promise that moves value is guarded by a callback that checks `is_promise_success()` before committing the state change: [3](#0-2) [4](#0-3) .

The equality that should hold is:
`sum(account.unstaked for all accounts) + total_staked_balance == actual NEAR balance held by the pool contract`

If the outbound `transfer` receipt fails, the right-hand side (actual NEAR still in the contract) stays unchanged, but the left-hand side has already been reduced by `amount` in step 2, and `last_total_balance` (used for reward calculations in `internal_ping`) is also reduced in step 4. The contract's internal accounting now understates the actual balance by `amount`, and the specific account that attempted the withdrawal has no recorded claim to those tokens anymore - the NEAR is stuck in the pool with no ledger entry pointing to it.

### Impact Explanation
This falls under "funds frozen for at least one epoch, or an accounting value diverging from reality where another party settles on it" (High) — and can escalate toward Critical since the affected user permanently loses their claim to the withdrawn amount (their `unstaked` balance is debited with no compensating credit), while `last_total_balance` becomes permanently understated relative to the actual balance held, corrupting reward distribution calculations for all other stakers going forward (`internal_ping` uses `last_total_balance` as the baseline to compute new rewards).

### Likelihood Explanation
Promise `transfer` actions to a `predecessor_account_id` can fail at the receipt level for the standard set of reasons (e.g., the account no longer exists, or fails for any other execution reason at the NEAR protocol level) independent of anything the withdrawing user does maliciously — this doesn't require any privileged access or special conditions beyond a normal `withdraw`/`withdraw_all` call landing on a receipt that fails to apply. No callback exists anywhere in this code path to detect or recover from that failure.

### Recommendation
Attach a `.then()` callback to the `Promise::new(account_id).transfer(amount)` in `internal_withdraw` (mirroring the `is_promise_success()` pattern already used by `on_stake_action` and the lockup/factory callbacks), and only permanently commit the `account.unstaked -= amount` and `self.last_total_balance -= amount` state changes once the callback confirms the transfer succeeded. On failure, restore `account.unstaked` (and leave `last_total_balance` unchanged) so the funds remain claimable.

### Proof of Concept
1. User calls `withdraw_all()` (or `withdraw(amount)`) on the staking pool.
2. `internal_withdraw` executes: `account.unstaked -= amount` is saved, `Promise::new(account_id).transfer(amount)` is scheduled, `last_total_balance -= amount` is applied — all in the same function call/receipt, with no follow-up callback.
3. The `transfer` receipt to `account_id` fails at the protocol level (e.g., destination account issue) after the calling function call receipt has already succeeded and committed state.
4. Contract state now shows the user's `unstaked` balance reduced by `amount` and `last_total_balance` reduced by `amount`, but the NEAR tokens never left the pool contract's actual balance.
5. There is no method in `staking-pool/src/**` that lets the user or anyone else reclaim this `amount` — it is permanently stuck in the pool's actual balance with no accounting entry pointing to it. [5](#0-4)

```rust
    pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }
```

```rust
    /// Withdraws the entire unstaked balance from the predecessor account.
    /// It's only allowed if the `unstake` action was not performed in the four most recent epochs.
    pub fn withdraw_all(&mut self) {
        let need_to_restake = self.internal_ping();

        let account_id = env::predecessor_account_id();
        let account = self.internal_get_account(&account_id);
        self.internal_withdraw(account.unstaked);

        if need_to_restake {
            self.internal_restake();
        }
    }

    /// Withdraws the non staked balance for given account.
    /// It's only allowed if the `unstake` action was not performed in the four most recent epochs.
    pub fn withdraw(&mut self, amount: U128) {
        let need_to_restake = self.internal_ping();

        let amount: Balance = amount.into();
        self.internal_withdraw(amount);

        if need_to_restake {
            self.internal_restake();
        }
    }
```
