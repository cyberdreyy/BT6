### Title
Fleet-wide double-sign of tenure-start blocks due to v1/v2 chainstate divergence in duplicate-block detection - (File: `stacks-signer/src/chainstate/v1.rs`, `stacks-signer/src/chainstate/v2.rs`)

### Summary
`SortitionsView::validate_tenure_change_payload` (v1, `stacks-signer/src/chainstate/v1.rs:461-520`) checks for a prior signed tenure-start block using `signer_db.get_last_globally_accepted_block(...)` (line 505-506), while `GlobalStateView::validate_tenure_change_payload` (v2, `stacks-signer/src/chainstate/v2.rs:306-359`) checks using `signer_db.get_last_signed_block(...)` (line 344-345), which additionally counts `LocallyAccepted` blocks. During a protocol-version transition where the signer set is split between v1 and v2 active protocol versions, this divergence lets the two subsets disagree on whether a competing tenure-start block is a duplicate.

### Finding Description
The uniqueness invariant these functions are meant to enforce is: *a signer must never sign a second, competing tenure-start block for a tenure it has already signed a tenure-start block for.* Both implementations intend to enforce this, but they read different signerdb state to decide "have I already signed a tenure-start block here?":

- v1: `get_last_globally_accepted_block(&block.header.consensus_hash)` — only returns a block if it reached `GloballyAccepted` state. [1](#0-0) 
- v2: `get_last_signed_block(&block.header.consensus_hash)` — returns a block if it is `LocallyAccepted` OR `GloballyAccepted` (per the comment "Only blocks we have signed (locally or globally accepted) count here"). [2](#0-1) 

If tenure-start block A has been `LocallyAccepted` (but not yet `GloballyAccepted`) by a given signer, and a miner then proposes a competing tenure-start block B for the same tenure:
- A signer running the v1 code path finds no globally-accepted block for that consensus hash and proceeds to validate/sign B, producing a second signature over a conflicting tenure-start block.
- A signer running the v2 code path finds A via `get_last_signed_block` and rejects B with `RejectReason::DuplicateBlockFound`.

This is a genuine logic divergence, not a defense-in-depth redundancy: the two code paths use different "has this signer already signed here" predicates, and only the v2 predicate matches the safety property described in v2's own comment. Since which path a given signer runs depends on `determine_active_signer_protocol_version` in `stacks-signer/src/v0/signer.rs`, a network that has a mix of v1-protocol and v2-protocol signers (e.g., mid-rollout of a signer-protocol upgrade) can end up with the v1 subset signing A, then also signing B once A is only locally accepted for them, while the v2 subset rejects B outright. This can fragment the 70% signing threshold across A and B.

### Impact Explanation
This breaks the uniqueness/chain-safety property that at most one tenure-start block per tenure should ever collect a supermajority of signatures. If v1-subset signers sign B while a disjoint set of v2-subset signers have already signed A, both A and B could independently approach or cross the signing threshold, which is the textbook double-sign / chain-fork condition the signer protocol exists to prevent. This matches the Critical category: "a signer signing an invalid, non-canonical, or conflicting block (chain safety)."

### Likelihood Explanation
The precondition is a mixed v1/v2 protocol-version signer fleet — a real, if transient, condition during any signer software rollout where `determine_active_signer_protocol_version` yields different active versions for different signers. Given that precondition, the exploit needs only:
1. The attacker to win a single miner slot (as posited) to construct a tenure-start block A that some signer only `LocallyAccepted`.
2. The attacker (or a natural fork/timing race) to then gossip a competing tenure-start block B for the same tenure before A is globally accepted.

No majority-signer collusion, no compromised keys, and no auth_token access are required — only normal miner block-proposal crafting and StackerDB gossip, matching the unprivileged-attacker model. It is repeatable for every tenure boundary during the mixed-version window.

### Recommendation
Make the v1 duplicate-block check use the same "signed" definition as v2 (i.e., have v1 also call `get_last_signed_block` instead of `get_last_globally_accepted_block`), or otherwise unify both code paths onto a single shared predicate function so that the "already signed a tenure-start block in this tenure" check cannot silently diverge between protocol versions. If v1's weaker check was intentional for some compatibility reason, this needs explicit reconciliation before allowing v1/v2 to coexist in the same signer set.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests` (or a new test module) that:
1. Sets up a `SignerDb` and inserts tenure-start block A for consensus hash `CH`, calling the equivalent of `mark_block_locally_accepted(&A, false)` (i.e., `LocallyAccepted`, not globally accepted).
2. Constructs a competing tenure-start block B for the same `CH` with a valid `TenureChangePayload` whose `prev_tenure_consensus_hash` matches the parent tenure.
3. Calls `v1::SortitionsView::validate_tenure_change_payload(..., B, signer_db, client)` and asserts it returns `Ok(())` (or at least does not return `Err(RejectReason::DuplicateBlockFound)`), because `get_last_globally_accepted_block` returns `None` for A.
4. Calls `v2::GlobalStateView::validate_tenure_change_payload(B_payload, B, parent_tenure_id, signer_db, client, config)` and asserts it returns `Err(RejectReason::DuplicateBlockFound)`, because `get_last_signed_block` returns `Some(A)`.
5. Assert the two outcomes disagree (`res_v1.is_ok() && matches!(res_v2, Err(RejectReason::DuplicateBlockFound))`), proving that the fleet-wide "one signed tenure-start block per tenure" invariant is version-dependent and breakable when v1 and v2 signers coexist. [3](#0-2) [4](#0-3)

    fn validate_tenure_change_payload(
        &self,
        proposed_by: &ProposedBy,
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the sortition's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        let parent_tenure_id = &proposed_by.state().data.parent_tenure_id;
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            self.config.tenure_last_block_proposal_timeout,
            self.config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // now, we have to check if the parent tenure was a valid choice.
        let is_valid_parent_tenure = proposed_by.state().data.check_parent_tenure_choice(
            signer_db,
            client,
            &self.config.first_proposal_burn_block_timing,
        )?;
        if !is_valid_parent_tenure {
            return Err(RejectReason::ReorgNotAllowed);
        }
        let last_in_current_tenure = signer_db
            .get_last_globally_accepted_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }

        }
