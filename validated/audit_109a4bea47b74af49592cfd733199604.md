Unrestricted `owner_account_id` in `LockupFactory::create` allows front-running/squatting a victim's deterministic lockup address with attacker-chosen terms (`release_duration` ~ `u64::MAX`) - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` computes the lockup account address deterministically as `sha256(owner_account_id)[:20].<factory>` and lets any caller supply that `owner_account_id` plus every other parameter (`release_duration`, `vesting_schedule`, `lockup_duration`, `whitelist_account_id`), with no check that the caller is, or is authorized by, the named owner. `LockupContract::new` likewise performs no bound check on `release_duration`. An unprivileged attacker can therefore pre-create the deterministic lockup account for a victim's `owner_account_id` with attacker-chosen terms (e.g. `release_duration` near `u64::MAX`), permanently occupying that address before the real grantor does.

### Finding Description
The invariant claimed is: `address_of(owner_account_id) → terms chosen by owner_account_id's rightful grantor`. In code, the address is `format!("{}.{}", hex::encode(sha256(owner_account_id)[..20]), current_account_id())` [1](#0-0) , and it is derived purely from the `owner_account_id` argument supplied to the public, unauthenticated `create` entrypoint:

```
pub fn create(
    &mut self,
    owner_account_id: ValidAccountId,
    lockup_duration: WrappedDuration,
    lockup_timestamp: Option<WrappedTimestamp>,
    vesting_schedule: Option<VestingScheduleOrHash>,
    release_duration: Option<WrappedDuration>,
    whitelist_account_id: Option<ValidAccountId>,
) -> Promise {
    assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");
``` [2](#0-1) 

The only check is the minimum attached deposit; there is no assertion that `env::predecessor_account_id() == owner_account_id` or any other authorization tying the caller to the owner they name. `release_duration` is passed straight through to `LockupArgs` and ultimately to `LockupContract::new`, which stores it unchecked: `release_duration: release_duration.map(|d| d.0)` [3](#0-2) , with no upper bound assertion anywhere in `new`. Since `WrappedDuration` wraps a `u64`, an attacker can set it to a value close to `u64::MAX`.

Exploit flow:
1. Attacker calls `create(owner_account_id: "victim.near", lockup_duration: 0, release_duration: Some(u64::MAX - epsilon), vesting_schedule: None, whitelist_account_id: attacker-controlled-whitelist)` attaching `MIN_ATTACHED_BALANCE`.
2. The factory issues `Promise::new(lockup_account_id).create_account().deploy_contract(CODE).transfer(...).function_call("new", LockupArgs{...})` [4](#0-3) , creating the account at the address that will forever be identified as "victim.near's lockup" by anyone deriving it the same way (front end, wallets, off-chain tooling, or the real grantor's own script).
3. `LockupContract::new` accepts these arguments as-is: owner is `"victim.near"`, but `release_duration` is attacker-chosen and effectively infinite, and the whitelist can be an attacker-controlled contract [5](#0-4) .
4. Because NEAR account IDs are unique, the real grantor's later legitimate `create` call for the same `owner_account_id` will have its `create_account()` action fail (account already exists), and `on_lockup_create` will simply refund the deposit to the caller [6](#0-5)  — but any party (exchange, foundation script, or the victim) that computes the deterministic address off-chain and sends NEAR to it directly (a common pattern for pre-funding known deterministic addresses) will have those funds land inside the attacker-parameterized contract, subject to a release schedule that never meaningfully completes, and interacting with a staking-pool whitelist the attacker controls.

No existing guard (`assert_owner`, `assert_called_by_foundation`, `is_valid_account_id`, deposit minimum) prevents this, because none of them check the relationship between the caller and the named `owner_account_id`, nor bound `release_duration`.

### Impact Explanation
Funds sent to the deterministic lockup address for a victim's `owner_account_id` are governed by attacker-chosen terms instead of the intended grantor's terms — this matches the explicitly listed Critical impact category "a lockup deployed with parameters its rightful creator never chose." With `release_duration` near `u64::MAX`, the linear unlock schedule effectively never completes, freezing the deposited NEAR indefinitely under the victim's own name but the attacker's rules, and routing later staking delegation into an attacker-controlled staking-pool whitelist. This is repeatable for any account ID an attacker chooses to squat, at the fixed cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per victim address claimed.

### Likelihood Explanation
Any account holder able to send a transaction and attach ~3.5 NEAR can call `create` on the public factory with an arbitrary `owner_account_id` — no privileged role, whitelist membership, or victim key is required. The attack is cheap, fully repeatable across many target account IDs, and requires no cooperation or error from the victim beyond someone eventually funding the precomputed address (a realistic scenario given the factory's design explicitly encourages "any account" to fund a lockup by computing this same deterministic address ahead of time).

### Recommendation
Require `env::predecessor_account_id() == owner_account_id.as_ref()` (or an equivalent authorization, e.g. only the foundation/master account may name a different owner) before creating a lockup in `LockupFactory::create`. Additionally bound `release_duration` (and `lockup_duration`) to sane maximums in `LockupContract::new`, and validate `staking_pool_whitelist_account_id` against a foundation-controlled allowlist rather than accepting attacker-supplied values.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs test module
#[test]
fn test_attacker_squats_victim_lockup_address_with_extreme_release_duration() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker (not "victim.near", not foundation) calls create() naming victim as owner.
    context.is_view = false;
    context.predecessor_account_id = String::from(account_attacker()); // unprivileged caller
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());

    let victim_owner = victim_account_id(); // "victim.near" wrapped as ValidAccountId
    let malicious_release_duration: WrappedDuration = (u64::MAX - 1).into();

    // No assertion anywhere ties predecessor_account_id to victim_owner:
    contract.create(
        victim_owner.clone(),
        0.into(),
        None,
        None,
        Some(malicious_release_duration),
        Some(custom_whitelist_account_id()), // attacker-controlled whitelist
    );

    // Simulate successful callback (in production this becomes the real created account).
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let created = contract.on_lockup_create(
        derived_lockup_account_for(&victim_owner), // sha256("victim.near")[:20].factory
        ntoy(30).into(),
        String::from(account_attacker()),
    );
    assert!(created);

    // Binding check: address_of(victim_owner) should carry victim-grantor-chosen terms,
    // but it now carries attacker-chosen release_duration ~ u64::MAX and attacker whitelist.
    // (Verify via LockupContract::new called with these exact LockupArgs, and inspect
    // `lockup_information.release_duration` == malicious_release_duration.0, proving
    // the invariant "terms == grantor's choice" is broken.)
}
```
This demonstrates that `create` never checks `predecessor_account_id` against `owner_account_id`, and that arbitrary `release_duration`/whitelist values reach `LockupContract::new` unchecked, at the deterministic address any party (including the real grantor) would independently compute for that owner.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
