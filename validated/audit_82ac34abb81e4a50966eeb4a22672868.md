### Title
Unbounded per-request memory/response-size amplification via `getMultipleAccounts` base64 encoding of maximum-size attacker-authored accounts - ([File: rpc/src/rpc.rs])

### Summary
`getMultipleAccounts` only bounds the *count* of pubkeys per request (`MAX_MULTIPLE_ACCOUNTS`, default 100) but places no limit on the *aggregate byte size* of the accounts being encoded. Because each account can independently hold up to the runtime's maximum account size (~10MB) and `encode_ui_account`/`BASE64_STANDARD.encode` copies and base64-inflates each account's raw data with no cumulative size check, a single low-rate call can force the validator to allocate and serialize roughly `MAX_MULTIPLE_ACCOUNTS * max_account_size * 4/3` bytes of response data in one request.

### Finding Description
The RPC entrypoint `rpc_accounts::AccountsDataImpl::get_multiple_accounts` only enforces a count limit on the number of pubkeys: [1](#0-0) 

It performs no check on the total byte size of the accounts the pubkeys resolve to. It then forwards to `JsonRpcRequestProcessor::get_multiple_accounts`, which iterates every pubkey and, for each, spawns a blocking task calling `get_encoded_account`, collecting all results into a single in-memory `Vec`: [2](#0-1) 

`get_encoded_account` → `encode_account` → `encode_ui_account` performs the actual per-account encoding. For `Base64` (the default encoding for this method), it copies the account's full data slice and base64-encodes it with no size cap (unlike the Base58/Binary path, which explicitly rejects data slices larger than `MAX_BASE58_BYTES`): [3](#0-2) [4](#0-3) 

The only quantity bound in this call path is the number of pubkeys, via `MAX_MULTIPLE_ACCOUNTS` (default 100, operator-tunable via `--rpc-max-multiple-accounts`): [5](#0-4) [6](#0-5) 

Because there is no check on `sum(account.data().len())` or on the resulting encoded response size before doing the work, an attacker who funds up to 100 accounts each near the maximum permitted account size (~10MB, enforced by the runtime's account-size limit, not by this RPC path) can submit one `getMultipleAccounts` call with `encoding: "base64"` and force the validator to: (1) read up to ~1GB of account data from the bank, (2) base64-encode it (~1.33GB of encoded output), and (3) hold all of it in memory simultaneously in the `accounts` `Vec` before returning a single, extremely large HTTP response. The per-pubkey count guard does not protect against this because it caps request *arity*, not aggregate *payload size*, and the size of each account is entirely attacker-controlled on-chain data returned later through this API.

### Impact Explanation
This is a scoped, single-call RPC resource-amplification issue: one unprivileged, low-rate JSON-RPC call (`getMultipleAccounts`) can cause the validator's RPC service to allocate/serialize roughly two to three orders of magnitude more memory and network bandwidth than a "normal" 100-key metadata query, because the cost is driven by attacker-authored on-chain account sizes rather than an explicit per-request byte budget. This matches the "RPC DoS from unbounded cost of a single low-rate call" bounty category referenced in the prompt's invariant (cost of one request bounded by explicit limits, not attacker data size).

### Likelihood Explanation
Feasible with only unprivileged actions: fund up to `MAX_MULTIPLE_ACCOUNTS` (100 by default) accounts, write ~10MB of data to each account (well within normal transaction/CPI limits over time, no special privilege required), then issue a single `getMultipleAccounts` call listing all pubkeys with `encoding: "base64"`. This requires no more than one call per `CLUSTER_SLOT_TIME_TARGET / 2` and no multiple clients, satisfying the scope constraints. Repeatable at will once the large accounts exist on-chain.

### Recommendation
Add an aggregate size guard in `JsonRpcRequestProcessor::get_multiple_accounts` (or in `rpc_accounts::AccountsDataImpl::get_multiple_accounts`) that sums the raw (pre-encoding) data length of resolved accounts against a configurable maximum (e.g., a `max_multiple_accounts_response_size` similar in spirit to `max_multiple_accounts`), returning `Error::invalid_params` when the aggregate would exceed the bound, independent of the existing per-pubkey `MAX_MULTIPLE_ACCOUNTS` count limit.

### Proof of Concept
Rust integration test plan (using `JsonRpcRequestProcessor` test harness, e.g., extending tests near `rpc/src/rpc.rs`'s existing `#[cfg(test)] mod tests`):
1. Create a bank via `new_from_bank`/test bank setup.
2. Insert `MAX_MULTIPLE_ACCOUNTS` (100) accounts into the bank, each with `data: vec![0xAA; MAX_PERMITTED_DATA_LENGTH as usize]` (~10MB) owned by an arbitrary program.
3. Call `meta.get_multiple_accounts(pubkeys, Some(RpcAccountInfoConfig { encoding: Some(UiAccountEncoding::Base64), ..Default::default() }))`.
4. Measure the total serialized response size (sum of `UiAccountData::Binary` string lengths) and peak allocation via a custom global allocator or `jemalloc`/`dhat` heap profiling harness.
5. Assert: `total_response_bytes` exceeds any per-request explicit bound (there currently is none), demonstrating the response size scales linearly with attacker-controlled account size × `MAX_MULTIPLE_ACCOUNTS`, i.e., `total_response_bytes ≈ 100 * 10MB * 4/3 ≈ 1.33GB`, with no rejection or truncation occurring — confirming the invariant "cost of one request bounded by explicit limits, not size of attacker-authored data" is violated.

    pub async fn get_multiple_accounts(
        &self,
        pubkeys: Vec<Pubkey>,
        config: Option<RpcAccountInfoConfig>,
    ) -> Result<RpcResponse<Vec<Option<UiAccount>>>> {
        let RpcAccountInfoConfig {
            encoding,
            data_slice,
            commitment,
            min_context_slot,
        } = config.unwrap_or_default();
        let bank = self.get_bank_with_config(RpcContextConfig {
            commitment,
            min_context_slot,
        })?;
        let encoding = encoding.unwrap_or(UiAccountEncoding::Base64);

        let mut accounts = Vec::with_capacity(pubkeys.len());
        for pubkey in pubkeys {
            let bank = Arc::clone(&bank);
            accounts.push(
                self.runtime
                    .spawn_blocking(move || {
                        get_encoded_account(&bank, &pubkey, encoding, data_slice, None)
                    })
                    .await
                    .expect("rpc: get_encoded_account panicked")?,
            );
        }
        Ok(new_response(&bank, accounts))
    }

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
