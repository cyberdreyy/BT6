### Title
Signer accepts a miner-supplied tenure-change parent reference without cross-checking it against the sortition's actual committed parent tenure (v1 sortition path) - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The bug class in the referenced advisory is: a server-side component trusts a caller-supplied *reference* (an identifier that gets resolved by a downstream trusted authority using the server's own credentials/context) without first validating that the reference is legitimate, letting the caller redirect the trusted resolution step. In the Stacks v1 signer chainstate path, the miner-controlled `TenureChangePayload.prev_tenure_consensus_hash` is forwarded straight into `check_tenure_change_confirms_parent` → `check_latest_block_in_tenure`, which asks the signer's own trusted authority (the Stacks node, via `client.get_tenure_tip`) to resolve that consensus hash — without first verifying that the referenced tenure is actually the sortition's real committed parent tenure.

### Finding Description
`SortitionData::check_tenure_change_confirms_parent` (`stacks-signer/src/chainstate/mod.rs:488-504`) simply forwards `tenure_change.prev_tenure_consensus_hash` as the `tenure_id` argument to `check_latest_block_in_tenure`: [1](#0-0) 

`check_latest_block_in_tenure` treats this `tenure_id` as authoritative: it looks up `signer_db.get_last_signed_block(tenure_id)`/`get_last_accepted_block(tenure_id)`, and if nothing local matches, falls back to asking the node itself, `client.get_tenure_tip(tenure_id)`, then compares the returned tip's height against the proposed block's `chain_length`: [2](#0-1) 

The check only compares heights, not tenure identity — any historical (real but unrelated) tenure consensus hash chosen by the miner will almost certainly have a lower height than the proposed block, so the "confirms parent" check trivially passes.

The v2 path explicitly closes this gap: `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v2.rs:306-339`) first checks that `tenure_change.prev_tenure_consensus_hash` equals the actually-committed `parent_tenure_id` derived from the current sortition (obtained from the node's own sortition-info RPC), *before* calling `check_tenure_change_confirms_parent`: [3](#0-2) 

The comment on that check is explicit about the attack it defends against: *"This catches block commits with bad `parent_block_ptr` (e.g., vtxindex=0 exploit)."*

In the v1 path (`stacks-signer/src/chainstate/v1.rs`), `check_proposal` determines `proposed_by` (the sortition record backing the block) purely from `block.header.consensus_hash` matching the current or last sortition, and validates the miner pubkey hash against that sortition's `miner_pkh`: [4](#0-3) 

It then calls `self.validate_tenure_change_payload(&proposed_by, tenure_change, block, signer_db, client)` for tenure-change blocks: [5](#0-4) 

Unlike v2, nothing observed in the v1 flow up to this point cross-checks `tenure_change.prev_tenure_consensus_hash` against `proposed_by.state().data.parent_tenure_id` (the sortition's actual committed parent, which the node derived from the burn-chain block-commit's `parent_block_ptr`). If `validate_tenure_change_payload` (v1) does not itself perform that equality check before delegating to `check_tenure_change_confirms_parent`, a miner can put an arbitrary — but real — prior tenure's consensus hash into `prev_tenure_consensus_hash`, and the height-only check in `check_latest_block_in_tenure` will pass for essentially any chain-length-increasing block, letting a v1 signer sign a tenure-change block whose declared parent tenure does not match the sortition's actual committed parent.

### Impact Explanation
If confirmed, this breaks the "approved-parent vs canonical parent" equality: a v1 signer could co-sign a tenure-change block that falsely claims to extend a tenure other than the one the burn-chain block-commit actually committed to (the exact `vtxindex=0`-style parent-pointer spoof that the v2 check exists to prevent), i.e., a signer signing a non-canonical/conflicting block. This is a Critical-class outcome per the stated impact categories.

### Likelihood Explanation
Triggerable by a single malicious miner during its own one-slot tenure (no majority of signers or other signers' keys required); it only requires that v1 signers are active (protocol version below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`) and that the miner crafts a `TenureChangePayload.prev_tenure_consensus_hash` pointing at a legitimate-but-wrong prior tenure. Whether this is currently exploitable depends entirely on whether `validate_tenure_change_payload` in `v1.rs` performs an equivalent cross-check to v2's — I was not able to view that function's full body before running out of tool calls, so this cannot be fully confirmed from the available context; the comment on the v2 check strongly suggests this equality is not implicit anywhere else in the flow, but I could not verify its presence or absence in the v1 function definition itself.

### Recommendation
In `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload`, add the same cross-check present in v2 (`stacks-signer/src/chainstate/v2.rs:314-325`): reject the proposal if `tenure_change.prev_tenure_consensus_hash != proposed_by.state().data.parent_tenure_id` before calling `check_tenure_change_confirms_parent`, ensuring the tenure-change payload's declared parent is validated against the sortition-derived (node-attested) actual parent tenure, not merely resolved by height.

### Proof of Concept
Not independently reproduced; based on static code-path analysis. A concrete PoC would: (1) have a v1-protocol signer set active, (2) have the current-slot miner emit a tenure-change block whose `TenureChangePayload.prev_tenure_consensus_hash` names some earlier, unrelated (but real) tenure instead of the sortition's actual parent tenure, and (3) observe whether `SortitionState::check_proposal` (v1) accepts/signs it because `check_latest_block_in_tenure`'s height comparison against `client.get_tenure_tip(prev_tenure_consensus_hash)` passes trivially.
