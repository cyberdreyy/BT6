### Title
`getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` fail entirely (return an RPC error instead of results) when any single matched account's data exceeds the Base58 size limit - ([File: rpc/src/rpc.rs])

### Summary
`get_program_accounts`, `get_token_accounts_by_owner`, and `get_token_accounts_by_delegate` build their response by mapping `encode_account` over *every* account matched by the filter/owner/program query and then `collect::<Result<Vec<_>>>()?`-ing the results. `encode_account` returns a hard `Err` whenever the (default) `Binary`/`Base58` encoding is used and a single account's data (after slicing) exceeds `MAX_BASE58_BYTES` (128 bytes). Because the `?` short-circuits the whole batch, one oversized, permissionlessly creatable account among the matched set causes the entire RPC call to fail for the caller, denying access to all the other (unrelated, legitimate) accounts that would otherwise have been returned. This is the same "one bad recipient blocks the whole loop" bug class as the reported `Budget.pay` issue, transplanted to Agave's account-scan RPC handlers.

### Finding Description
`get_program_accounts` defaults to `UiAccountEncoding::Binary` when no encoding is specified: [1](#0-0) 

and then encodes every account returned by the filtered scan with `encode_account`, using `.collect::<Result<Vec<_>>>()?` to build the final `Vec<RpcKeyedAccount>`: [2](#0-1) 

The same pattern (default `Binary` encoding + `collect::<Result<Vec<_>>>()?`) exists in `get_token_accounts_by_owner`: [3](#0-2) [4](#0-3) 

and in `get_token_accounts_by_delegate`: [5](#0-4) [6](#0-5) 

`encode_account` itself explicitly rejects any account whose data (post `data_slice`) is larger than `MAX_BASE58_BYTES` (128 bytes) when the encoding is `Binary` or `Base58`, returning an `InvalidRequest` error rather than skipping/omitting just that one account: [7](#0-6) 

Because these three RPC methods scan for *many* accounts (all accounts owned by a program, or all token accounts owned/delegated to a pubkey) and then map+collect the encoding over the whole set with `?`, a single matching account with more than 128 bytes of data aborts encoding for the *entire* result set. Unlike `getAccountInfo`/`getMultipleAccounts`, which encode one caller-specified pubkey per error scope, these three methods have no way for the caller to exclude the offending account in advance, since the account set is discovered by the scan itself.

An unprivileged user can trivially create such a "poison" account: any account whose *owner* is the target program and whose *data length* exceeds 128 bytes qualifies (e.g., a system-owned account allocated via `system_instruction::allocate` with >128 bytes of space, or a token-account-like account with padding under a token program that permits large account data, or simply an arbitrary account created under a smart-contract program the attacker controls). Once such an account exists, every RPC node serving `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` for that program/owner/delegate with the default (or explicit Binary/Base58) encoding will return an error for the whole query instead of the (potentially large) set of legitimate accounts.

### Impact Explanation
This is a low-cost, permissionless, single-request denial of the account-scan RPC methods (`getProgramAccounts`, `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`) for a given program/owner/delegate: legitimate callers receive an RPC error instead of correct account data, even though the vast majority of matched accounts are perfectly valid and encodable. This mirrors the "one poisoned entry blocks the whole batch" failure mode from the external report, applied to an RPC read path reachable by any unprivileged client.

### Likelihood Explanation
Creating an oversized (>128 byte), program-owned account is cheap and requires no special privileges (just paying for account rent/space), and callers frequently invoke `getProgramAccounts`/`getTokenAccountsByOwner` without specifying a non-default encoding (Binary is the default), so the vulnerable code path is easily triggered in normal usage.

### Recommendation
In `get_program_accounts`, `get_token_accounts_by_owner`, and `get_token_accounts_by_delegate`, do not `collect::<Result<Vec<_>>>()?` over the whole batch when using `Binary`/`Base58` encoding. Either: (1) skip/omit accounts that fail to encode (similar to how `get_parsed_token_accounts` uses `filter_map` to drop accounts that fail JSON parsing rather than erroring the whole call), or (2) reject the oversized account's encoding gracefully per-account (e.g., return an error string/sentinel for that entry only, matching how `encode_bs58` already returns an `"error: data too large..."` string instead of failing for the plain (non-`encode_account`) path), or (3) proactively force `Base64`/`Base64Zstd` encoding for scan-style calls when data may exceed the Base58 threshold.

### Proof of Concept
1. As any funded account, submit a transaction using `system_instruction::allocate` (or an equivalent instruction under a target program) to create/own an account with `>128` bytes of data under a target `program_id` (e.g., the System Program or any program that allows user-created accounts).
2. Call `getProgramAccounts(program_id)` (or `getTokenAccountsByOwner`/`getTokenAccountsByDelegate` for the equivalent token-program scenario) without specifying `encoding` (defaults to `Binary`).
3. Observe that `encode_account` at [8](#0-7)  returns `Err(InvalidRequest)` for the oversized account, and via `.collect::<Result<Vec<_>>>()?` at [2](#0-1)  the entire RPC response becomes an error — no accounts (including the many other legitimate, small ones matching the same program/owner) are returned to the caller.

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
