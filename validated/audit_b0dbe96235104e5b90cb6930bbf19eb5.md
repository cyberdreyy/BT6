### Title
EI credential holder can bypass the "EIs not allowed for int IDs" job-run restriction via synthetic run-role user - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates int32 job-ID execution on `auth.GetAuthenticatedUser(c)` returning `ok==true`, intending this to mean "authenticated as a session/API-token user." However, `auth.AuthenticateExternalInitiator` also stores a synthetic `*clsessions.User{Role: UserRoleRun}` under the same `SessionUserKey`, so `GetAuthenticatedUser` returns `ok==true` for EI-authenticated requests too, defeating the intended restriction.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered with a multi-method auth chain that includes `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, and `auth.AuthenticateBySession`, wrapped by `auth.RequiresRunRole` [1](#0-0) .

`AuthenticateExternalInitiator` validates the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers against a stored `ExternalInitiator` record, and on success explicitly sets `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` — a synthetic user object, not a real session/token-backed user — specifically so that `RequiresRunRole` will pass for EI callers [2](#0-1) .

`GetAuthenticatedUser` simply reads whatever is stored at `SessionUserKey` and returns it with `ok=true` if present, with no way to distinguish whether it was populated by `AuthenticateBySession`/`AuthenticateByToken` (real user) or by `AuthenticateExternalInitiator` (synthetic EI-role-run user) [3](#0-2) .

In `Create`, the comment explicitly states the intent: `// only users are allowed to run jobs using int IDs - EIs not allowed`, and the code branches solely on `isUser` from `GetAuthenticatedUser` [4](#0-3) . Because the EI auth path populates the same `SessionUserKey`, `isUser` evaluates to `true` for a valid EI credential holder, allowing them to reach the `strconv.ParseInt` / `prc.App.RunJobV2(ctx, jobID, nil)` branch for numeric job IDs — exactly the code path the comment says should be excluded for EIs. The distinguishing context key `SessionExternalInitiatorKey` (retrievable via `GetAuthenticatedExternalInitiator`) is set but never checked in `Create`, so there is no code that actually differentiates "real user" from "EI acting as run-role user."

### Impact Explanation
An external-initiator credential holder (which is a lower-trust integration credential, scoped for triggering webhook/UUID-keyed job runs) can trigger jobs referenced by internal numeric (int32) job IDs — a capability the code comment states is intentionally reserved for session/API-token users. This is an authorization/role-boundary bypass: it lets an EI credential run arbitrary jobs by numeric ID that it was not meant to access, potentially triggering fund-moving or other sensitive pipeline runs tied to those job IDs. This maps to Chainlink's "unauthorized job run" / role-authorization-bypass impact class.

### Likelihood Explanation
Preconditions are minimal: possession of a valid, already-provisioned EI access-key/secret pair (a credential class explicitly designed to be less trusted/scoped only for triggering runs by UUID). No admin/session/API-token credential is needed. The attack is a single crafted HTTP request (`POST /v2/jobs/<int-ID>/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) and is fully repeatable for any known/guessable numeric job ID.

### Recommendation
In `PipelineRunsController.Create`, do not rely solely on `auth.GetAuthenticatedUser`'s presence to gate int-ID execution. Explicitly reject requests where `auth.GetAuthenticatedExternalInitiator(c)` succeeds (i.e., where the "user" was synthesized by `AuthenticateExternalInitiator`), or use a dedicated context marker set only by `AuthenticateBySession`/`AuthenticateByToken` to identify genuine user-authenticated requests, distinct from the synthetic EI run-role user.

### Proof of Concept
Handler-level integration test:
1. Set up a `gin.Context` / test router with the `userOrEI` route group exactly as in `v2Routes` (`auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession`, then `auth.RequiresRunRole(prc.Create)`).
2. Seed a valid `ExternalInitiator` record with known access key/secret.
3. Send `POST /v2/jobs/42/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers set to the EI's credentials, and no session cookie / API token.
4. Assert that `auth.AuthenticateExternalInitiator` succeeds and sets `SessionUserKey` (verify via a small unit test directly calling `AuthenticateExternalInitiator` then `auth.GetAuthenticatedUser(c)`, expecting `isUser == true`, `user.Role == UserRoleRun`).
5. Assert the handler's current behavior: `prc.App.RunJobV2` is invoked (mock expectation hit) and the response is `200 OK` with a pipeline run resource — demonstrating the bypass.
6. After the fix, assert the response instead is `422 Unprocessable Entity` with body containing `"bad job ID"`, and `RunJobV2` is never called for EI-originated requests targeting numeric IDs.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
