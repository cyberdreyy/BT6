### Title
Fee-on-transfer underlying mints unbacked `IdleCreditVault` strategy tokens, inflating NAV and draining the liquidity buffer - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCDOCreditVault._deposit` correctly mints tranche shares on the actual received balance delta, but it then forwards the nominal `_amount` to the strategy. `IdleCreditVault.deposit` pulls `_amount` from the CDO and calls `_mint(msg.sender, _amount)` unconditionally — it never measures the balance actually received. With a fee-on-transfer (or deflationary) underlying token, the strategy mints more strategy tokens than the underlying it holds, overstating `getContractValue` and letting the deposit be redeemed for more than its real backing.

### Finding Description
The CDO-side deposit flow is:

1. `IdleCDOCreditVault._deposit` records `_preBal`, pulls `_amount` from the user, and mints tranche tokens using `_contractTokenBalance(_token) - _preBal` — this leg is fee-aware [1](#0-0) .
2. It then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the *nominal* amount, not the received delta [2](#0-1) .
3. `IdleCreditVault.deposit` executes `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` followed by `_mint(msg.sender, _amount)` — minting strategy tokens 1:1 with the *requested* amount regardless of what arrived [3](#0-2) .

This is the exact analog of the Allo `_fundPool` bug: `_strategy.increasePoolAmount(amountAfterFee)` there corresponds to `_mint(cdo, _amount)` here — an accounting credit computed on a value that ignores the fee deducted by the transfer itself.

The double-hop makes it worse than a single miscredit:
- Hop 1 (user → CDO): CDO receives `_amount - f1`, but the strategy then pulls the full `_amount` out of the CDO, draining `f1` from the pre-existing liquidity buffer (other lenders' un-deployed funds, or a revert/DoS if the buffer is insufficient).
- Hop 2 (CDO → strategy): the strategy receives `_amount - f2` but mints `_amount` strategy tokens to the CDO, inflating the recorded NAV by `f2`.

`getContractValue` therefore reports `f2` more than real backing, and `totEpochDeposits += _amount` also records the inflated nominal amount for epoch accounting [4](#0-3) . The same pattern — `transferFrom` followed by accounting on the nominal amount — recurs in `collectWithdrawFunds` / `collectInstantWithdrawFunds` (where `pendingWithdraws`/`pendingInstantWithdraws` is decremented by `_amount` but fewer tokens arrive) [5](#0-4)  and in `finalizeDefaultRecovery` (where `defaultRecoveryReserve` is credited with `_recoveredAmount` rather than the received delta) [6](#0-5) . This is relevant in practice because credit-vault pool currencies include USDT, which carries a (currently zero) transfer-fee parameter that can be activated by the token issuer.

### Impact Explanation
Each deposit of a fee-bearing token (fee rate `r`, amount `A`):
- Mints `A*r` unbacked strategy tokens to the CDO (recorded NAV exceeds real strategy holdings). A depositing attacker gets tranche shares priced on `A - f1` while CDO NAV is inflated by `f2`; redeeming those shares through `requestWithdraw`/`claimWithdrawRequest` or instant-withdraw pays out more than real backing — a direct transfer of `≈ A*r` per deposit from honest LPs and recovery claimants.
- Drains `A*r` from the CDO's on-contract liquidity buffer into the strategy, reducing funds available for instant withdraws and (if the buffer is empty) making deposits revert.
- In `finalizeDefaultRecovery`, a fee-bearing `_recoveredAmount` makes `defaultRecoveryReserve` and `defaultRecoveryPrice` exceed actual holdings, so the last defaulted-receipt claimants' `_transferDefaultRecovery` calls revert — permanently freezing part of recovery funds [7](#0-6) .

### Likelihood Explanation
Requires the vault's `token` to charge (or begin charging) a transfer fee. The protocol explicitly targets credit pool currencies; USDT's fee flag is a realistic enabling condition, and the vulnerability triggers on ordinary, honest deposit/repay/finalize flows — no privileged misbehavior needed. No existing guard stops it: `_guarded`, `_checkDefault`, KYC/`isWalletAllowed`, and `_onlyIdleCDO` are orthogonal, and there is no balance-delta check in `IdleCreditVault.deposit`. (Caveat: if the deployment mandates a strictly fee-free underlying, the issue is latent rather than live.)

### Recommendation
Mirror the fix already applied on the CDO deposit leg — account for balance deltas at every inbound `safeTransferFrom`:
- In `IdleCreditVault.deposit`, snapshot `underlyingToken.balanceOf(address(this))` before and after the pull, mint and accrue `totEpochDeposits` on the delta, and have the CDO pass the actual received amount to `strategy.deposit` (or compute the delta inside the strategy).
- Apply the same delta accounting in `collectWithdrawFunds`, `collectInstantWithdrawFunds`, and `finalizeDefaultRecovery` so `pendingWithdraws`, `pendingInstantWithdraws`, and `defaultRecoveryReserve` reflect tokens actually received.
- Alternatively, document/enforce at deployment that the pool currency must not support transfer fees.

### Proof of Concept
Foundry fork test sketch (USDT with fee enabled via its `BasisPointsRate`/`setParams` surface, or a mock fee-on-transfer ERC20 with identical decimals):

```solidity
// test/foundry/FeeOnTransferDeposit.t.sol
function test_FeeOnTransfer_InflatesStrategyTokens() public {
    // vault deployed with a fee-on-transfer underlying (fee = 1%)
    uint256 A = 1000e6;
    deal(address(underlying), attacker, A);
    vm.startPrank(attacker);
    underlying.approve(address(cdo), A);
    cdo.depositAA(A); // KYC'd lender deposit
    vm.stopPrank();

    // Attacker received shares priced on (A - f1) ~= 990e6,
    // but CDO was charged the full A and the strategy holds only A - 2*f1 = 980e6
    // while minting A strategy tokens to the CDO.
    assertEq(strategy.balanceOf(address(cdo)), A);          // minted on nominal
    assertLt(underlying.balanceOf(address(strategy)), A);   // real backing < claims

    // NAV overstates by f1; attacker's tranche tokens redeem for more
    // than the real assets backing them, paid from other LPs / the buffer.
}
```

Invariant broken: strategy-token supply claims (minted `_amount`) exceed actual underlying custody (`_amount - fee`), i.e. `getContractValue` overstates NAV and one receipt can claim more than its real backing — matching the Allo `_fundPool`/`increasePoolAmount` miscredit.

  /// pending basis, the difference is a stopEpochWithDuration loss assigned to
  /// pending receipts and users later claim through `lossRecoveryPriceByEpoch`.
  /// Reverts if the resulting recovery price rounds to zero at `RECOVERY_FULL` precision.
  /// @param _amount number of funded tokens to collect
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
