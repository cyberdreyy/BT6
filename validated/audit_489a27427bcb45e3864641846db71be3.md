The premise fails because the signer already guards against exactly this scenario. In `handle_block_validate_ok` and `handle_block_validate_reject` (stacks-signer/src/v0/signer.rs), before processing any validation response, the signer checks `block_info.valid.is_some()` and, if a decision was already recorded for that `signer_signature_hash`, logs "Already processed a block validate response for block ... Ignoring validation response." and returns without altering state. [1](#0-0) [2](#0-1) 

The inline comment even names this exact scenario: "This is only really possible when a signer is sharing a node or we have timed out a pending validation and it suddenly arrives" — and that path is exactly what's blocked. So a stale/late/duplicate `BlockValidateOk` (or a second `InvalidBlock`) arriving for a hash the signer already decided on cannot flip or recount the decision. [3](#0-2) 

Separately, the premise of "resubmitting to a second, equally out-of-date signer-associated node" doesn't match the architecture: each `Signer` instance talks to exactly one `stacks_client`/node, tracked via a single `submitted_block_proposal: Option<(Sha512Trunc256Sum, Instant)>` slot, and `check_submitted_block_proposal`/`submit_block_for_validation` govern that one relationship — there is no multi-node fan-out per signer that would let an attacker exploit two independently-stale nodes for the same signer's decision. [4](#0-3) [5](#0-4) 

The equivocation guard in `signerdb.rs` (`add_block_signature` deletes any prior rejection row for the same signer/hash, and `add_block_rejection_signer_addr` refuses to insert a rejection if a signature already exists) is a separate, orthogonal mechanism for aggregating *other signers'* votes on a given block, not a channel through which a single signer's own already-decided verdict gets overwritten. [6](#0-5) 

Because the `valid.is_some()` short-circuit is checked before any state mutation on both the accept and reject paths, the claimed equality — a second (possibly stale/conflicting) validation response silently flipping a prior `InvalidBlock` rejection to a signature — does not hold in this codebase.
