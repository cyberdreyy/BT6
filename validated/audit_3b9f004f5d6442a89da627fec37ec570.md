### Title
Unbounded per-sender trigger request flooding via `HandleLegacyUserMessage` due to missing incoming rate limiting/allowlist - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`(h *handler).HandleLegacyUserMessage` accepts any signed `webAPITrigger` message, validates only staleness and method name, then unconditionally broadcasts the request to every DON member with no per-sender or global rate limiting or subscription check. The only rate limiter in this handler, `h.nodeRateLimiter`, is applied exclusively in `handleWebAPIOutgoingMessage` (the outbound HTTP fetch path triggered by node responses), not on the inbound user-trigger path, leaving trigger submission completely unthrottled.

### Finding Description
The request flow is: `gateway.ProcessRequest` (`core/services/gateway/gateway.go:267-269`) decodes a legacy signed message and calls `h.HandleLegacyUserMessage(ctx, msg, callback)` for the resolved DON handler [1](#0-0) .

Inside `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`), the only checks performed are: JSON payload decodability, a non-zero `Timestamp`, a staleness check against `MaxAllowedMessageAgeSec`, and that `msg.Body.Method == MethodWebAPITrigger`. The code explicitly documents the gap with `// TODO: apply allowlist and rate-limiting here` at line 384 [2](#0-1) . After these checks pass, the handler stores the callback and broadcasts the request to *every* member of the DON: `for _, member := range h.donConfig.Members { err = errors.Join(err, don.SendToNode(ctx, member.Address, req)) }` [3](#0-2) .

The handler struct does define `nodeRateLimiter *ratelimit.RateLimiter` [4](#0-3) , but it is only invoked in `handleWebAPIOutgoingMessage`, keyed by `nodeAddr` (the responding DON node), guarding the outbound HTTP fetch path triggered from node responses — not the inbound `HandleLegacyUserMessage` path: `if !h.nodeRateLimiter.Allow(nodeAddr) { return fmt.Errorf("rate limit exceeded for node %s", nodeAddr) }` [5](#0-4) . There is no per-`Sender` limiter, no subscription/credit check, and `MessageId` uniqueness only affects the ephemeral `savedCallbacks` map — an attacker submitting fresh, distinct `MessageId`s (still valid because `msg.Validate()` in `gateway.ProcessRequest` only checks structural correctness/signature, not economic entitlement) is never throttled. The corresponding test file even carries a TODO confirming this ambiguity: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` [6](#0-5) .

### Impact Explanation
A single unprivileged sender holding any valid signing key (no subscription funding required) can submit unlimited distinct-`MessageId` trigger requests. Each one causes a full DON-wide broadcast (`don.SendToNode` to every member), consuming gateway CPU/network resources and DON node capacity for processing/verifying each incoming trigger — all for free, since no subscription or credit-based accounting gates this path. This matches a resource-exhaustion / quota-bypass class impact: uncontrolled resource consumption on the gateway and DON nodes from a single unprivileged, unfunded sender.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs the ability to sign a gateway message (any private key; `msg.Validate()`/`msg.Sign` require no special DON authorization or funded subscription for the legacy trigger path) and to vary `MessageId` per request. This is fully repeatable and trivially scriptable — a simple loop issuing `HandleLegacyUserMessage`/`ProcessRequest` calls at high frequency from the same `Sender` address will succeed indefinitely with no backoff or rejection.

### Recommendation
Implement the TODO at `core/services/gateway/handlers/capabilities/handler.go:384`: add a per-`Sender` (and/or per-subscription) rate limiter analogous to the `PerSenderRPS`/`PerSenderBurst` pattern already used in `core/capabilities/webapi/outgoing_connector_handler.go`, enforced inside `HandleLegacyUserMessage` before broadcasting to DON members, and reject/backoff requests once a sender's quota is exceeded. Additionally consider gating trigger submission on subscription/allowlist status rather than allowing any validly-signed message through.

### Proof of Concept
Go handler-level test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` via `NewHandler` with a small `donConfig.Members` set and a mock `handlers.DON` (`don.EXPECT().SendToNode(...)`).
2. Generate one signing key (`Sender`) and loop N (e.g., 1000) times, each time building a distinct `MessageId` via `triggerRequest(...)` with a fresh, non-stale `Timestamp` and valid `MethodWebAPITrigger` payload, then call `handler.HandleLegacyUserMessage(ctx, msg, cb)`.
3. Assert: (a) every call returns `nil` error (no rejection), (b) `don.SendToNode` mock is invoked `N * len(donConfig.Members)` times, and (c) no `UserCallbackPayload` with a rate-limit `ErrorCode` (e.g., `api.RateLimitedError`) is ever sent back via the callback — demonstrating the absence of any per-sender throttling, contrasted with `TestGatewayHandler_MakeOutgoingRequest_NodeRateLimiting`, which shows the outgoing path *is* rate-limited while the incoming trigger path is not.
