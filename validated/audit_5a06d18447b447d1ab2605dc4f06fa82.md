### Title
EI credential bypasses "no int-ID job runs for EIs" restriction via synthetic user injection - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates numeric job-ID runs with `isUser` from `auth.GetAuthenticatedUser(c)`, intending to allow only real dashboard/API users (not external initiators) to trigger jobs by integer ID. However, `AuthenticateExternalInitiator` sets the same `SessionUserKey` context value to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` for any successfully authenticated EI, so `GetAuthenticatedUser` returns `ok=true` for EIs too, defeating the intended EI exclusion.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Create` does: [1](#0-0) 
The comment states only real users should be allowed to run int-ID jobs; the check is `_, isUser := auth.GetAuthenticatedUser(c)`.

In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` authenticates a request using EI access key/secret headers (`static.ExternalInitiatorAccessKeyHeader`/`ExternalInitiatorSecretHeader`), and upon success sets: [2](#0-1) 
This places a `*clsessions.User{Role: UserRoleRun}` under `SessionUserKey`, the exact key that `GetAuthenticatedUser` reads: [3](#0-2) 

Because `GetAuthenticatedUser` only checks the presence and type of the value at `SessionUserKey` — not whether the caller authenticated via session/token vs. via EI credentials — an EI-only authenticated request (no session cookie, no API token) yields `isUser == true` in `Create`. This routes the numeric-ID branch to `prc.App.RunJobV2(ctx, jobID, nil)`, exactly the path the code comment says should be excluded for EIs.

### Impact Explanation
This is an authorization-bypass of an intended restriction: EIs (external initiators), which the code explicitly documents as disallowed for integer-ID job runs, can trigger arbitrary job runs by numeric job ID using only EI credentials. This matches the "unauthorized job run" impact class — an EI can invoke `RunJobV2` for any job ID it can guess/enumerate, potentially triggering pipeline execution, resource consumption, or state changes not intended to be reachable via the EI trust boundary.

### Likelihood Explanation
Preconditions are minimal: only a valid EI access key/secret pair (obtainable by any party the node registered as an external initiator, i.e., a legitimate but restricted credential holder — matching the "restricted credential holder" attacker model). No session, no user API token, and no higher role is required. The request is a straightforward `POST /v2/jobs/:ID/runs` with numeric `:ID` and EI auth headers; it's fully reproducible and repeatable for any job ID.

### Recommendation
Distinguish "real user" authentication from "EI-synthesized user" authentication instead of relying solely on `SessionUserKey` presence. Options:
- Check `auth.GetAuthenticatedExternalInitiator(c)` first and treat presence of an EI as disqualifying, regardless of the synthetic user role: e.g., `if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI { return "bad job ID" }`.
- Or don't overwrite `SessionUserKey` in `AuthenticateExternalInitiator`; introduce a dedicated flag/context key (e.g., `SessionIsEIKey`) so `GetAuthenticatedUser` genuinely reflects only session/token-authenticated users, and have `RequiresRunRole`/other role-based middleware use a separate role-check helper that doesn't conflate EI and user identities.

### Proof of Concept
Go handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
1. Set up a test app with an `Authenticator` stub whose `FindExternalInitiator` returns a valid `bridges.ExternalInitiator` for a known access key/secret, and whose `FindUserByAPIToken`/`AuthorizedUserWithSession` are not used.
2. Register the route with `auth.Authenticate(store, auth.AuthenticateExternalInitiator)` only (no session/token method), mirroring the EI-only path.
3. Send `POST /v2/jobs/42/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (per `static.ExternalInitiatorAccessKeyHeader/SecretHeader`) set to the valid EI credential, no session cookie, no `X-API-KEY`.
4. Assert: current behavior — response status `200`/success and `prc.App.RunJobV2` invoked with `jobID=42` (bug reproduced); expected/fixed behavior — response `422 Unprocessable Entity` with body `"bad job ID"`, and `RunJobV2` never called.
5. Additionally unit test `auth.GetAuthenticatedUser` after `AuthenticateExternalInitiator` runs on a mock `*gin.Context`, asserting it currently returns `(user, true)`, demonstrating the root cause independent of the controller.
