### Title
Cross-DON impersonation via missing sender/DON-membership allowlist check in webapicap trigger handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`gateway.ProcessRequest` in `core/services/gateway/gateway.go` only checks that a handler exists for `msg.Body.DonId` via `g.handlers[handlerKey]`, and `Message.Validate()` only checks signature well-formedness/recovers the signer into `Body.Sender` — it does not check DON membership. The downstream `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` explicitly forwards the request to all DON members without validating that `msg.Body.Sender` is an authorized/allowlisted party for that DON.

### Finding Description
`ProcessRequest` (`core/services/gateway/gateway.go:250-262`) resolves the handler purely from `msg.Body.DonId`: [1](#0-0) 
`msg.Validate()` (`core/services/gateway/api/message.go:54-88`) checks structural fields and extracts the signer into `m.Body.Sender`, but performs no check that the recovered `Sender` is a member of, or authorized for, the target DON — any arbitrary ECDSA keypair produces a "valid" signature/sender: [2](#0-1) 
The request is then dispatched to `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`), which explicitly contains the comment `// TODO: apply allowlist and rate-limiting here` right before dispatching the request to all DON node members via `don.SendToNode`: [3](#0-2) 
This is corroborated by the existing test suite itself, which contains an explicit acknowledgment of the gap: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated`: [4](#0-3) 
Because no allowlist/membership check exists anywhere in this path, an attacker who signs a `Message` with any private key, sets `DonId` to a real, configured DON ID, and uses `MethodWebAPITrigger`, will have their request forwarded to that DON's nodes as if from a legitimate sender — impersonating any address as the trigger's `Sender`.

### Impact Explanation
This allows an unauthenticated attacker (no DON membership, no prior authorization) to inject arbitrary web API trigger events, with an attacker-chosen `Sender` value, into any configured DON's workflow trigger pipeline. This is a request/sender impersonation and authorization bypass — matching the bounty class of "unauthorized job run" / "request impersonation," since the DON nodes will process trigger events attributed to a forged sender, potentially initiating workflow executions the attacker is not authorized to trigger.

### Likelihood Explanation
Trivial and fully repeatable: the attacker needs no credentials beyond generating an arbitrary ECDSA keypair (the check is "any valid signing key," not a specific allowlisted one), knowledge of a valid/target `DonId` (these are often not secret — they can be discovered via configuration, docs, or other legitimate requests), and the ability to POST to the gateway's public HTTP endpoint. No operator, admin, or DON compromise is required.

### Recommendation
Enforce a DON/service-specific sender allowlist check before dispatch. Concretely, in `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go`), after `msg.Validate()`/method checks, verify `msg.Body.Sender` against the configured allowlist for the target DON/service (e.g., `h.donConfig` or a dedicated workflow-owner allowlist) and reject with `api.UnauthorizedError` (or similar) if the sender is not authorized, mirroring the "TODO: apply allowlist" comment already present in the code.

### Proof of Concept
Go handler-level integration test:
1. Set up a `capabilities` handler with `setupHandler(t)` bound to `donID = "workflow_don_1"` with a known set of authorized DON members/allowlisted senders (`nodes` in existing test file).
2. Build a `triggerRequest` (as in `handler_test.go`) signed with a **freshly generated, non-member private key** (not in `nodes` or any configured allowlist), with `DonId` set to `"workflow_don_1"` (a valid, existing DON) and `Method = MethodWebAPITrigger`.
3. Call `handler.HandleLegacyUserMessage(ctx, msg, cb)`.
4. Assert (expected fix behavior): the callback response is an authorization error (e.g., `api.UnauthorizedError`) and `don.SendToNode` is never invoked.
5. Current behavior (proving the bug): `err` is `nil`, `don.SendToNode` is called for every DON member, and `cb.Wait` returns a success payload — demonstrating that a completely unauthorized signer's request is processed identically to a legitimate DON member's request.
