One targeted check on the CDO side before finalizing.### Title
Post-default instant withdraw requests drain `defaultRecoveryReserve` by being recorded in the defaulted epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` in `IdleCreditVault` has no handling for the `defaultRecoveryFinalized` state, unlike `requestWithdraw`, which routes post-default requests into the par-paid `postDefaultRequests` path. A post-default instant request is keyed to `epochNumber`, which still equals `defaultRecoveryEpoch`, so `claimInstantWithdrawRequest` treats it as a defaulted-epoch receipt and pays it out of the isolated `defaultRecoveryReserve`.

### Finding Description
After a borrower default is finalized via `finalizeDefaultRecovery`, `defaultRecoveryEpoch` is set to `epochNumber` and `defaultRecoveryPrice`/`defaultRecoveryReserve` define a fixed recovery pool for defaulted claimants (`contracts/strategies/idle/IdleCreditVault.sol:690-696`). `epochNumber` is only incremented inside `deposit()` while an epoch is running, so after default it stays equal to `defaultRecoveryEpoch`.

`requestWithdraw` explicitly protects this state: it rejects users with pending receipts and parks new requests in `postDefaultRequests`, which are paid 1:1 from the reserve only because the CDO already haircut the amount (`lines 247-257`). `requestInstantWithdraw` (`lines 356-375`) performs no such check — it burns CDO strategy tokens, mints a receipt to the user, and records `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount` plus `instantWithdrawClaimsByEpoch[epochNumber] += _amount`. Since `epochNumber == defaultRecoveryEpoch`, the request is indistinguishable from a defaulted-epoch receipt.

Later, `claimInstantWithdrawRequest` sees `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` and calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`, then executes `defaultRecoveryReserve -= payout` via `_transferDefaultRecovery` (`lines 842-855`, `912-917`). The attacker therefore converts a post-default receipt — which was never funded by the borrower and never part of the finalized claim basis — into a payout drawn from the recovery reserve at `defaultRecoveryPrice`. The saturating subtraction `pendingInstantWithdraws = claimBasis >= pending ? 0 : ...` (`line 852`) prevents a revert, so nothing stops the claim.

### Impact Explanation
Any unprivileged tranche holder can, after default finalization, request an instant withdraw and claim it against `defaultRecoveryReserve`, receiving `amount * defaultRecoveryPrice / 1e18` of reserve that belongs exclusively to legitimate defaulted-epoch claimants. Repeating or sizing the request drains the entire reserve, causing direct theft of unclaimed recovery funds and leaving honest claimants with unpayable receipts (permanent loss up to the full reserve).

### Likelihood Explanation
Requires a defaulted-and-finalized vault, which is a supported state — the code explicitly maintains post-default request UX. The attack needs only a tranche-token holder able to call the CDO's withdraw path post-default; no privileged role, oracle, or timing race is involved. The missing `defaultRecoveryFinalized` branch in `requestInstantWithdraw` (present in `requestWithdraw` directly above) makes this a reachable asymmetry rather than an edge case.

### Recommendation
In `requestInstantWithdraw`, mirror the `requestWithdraw` post-default handling: when `defaultRecoveryFinalized` is true, either revert or record the request under a post-default keying (e.g., `epochNumber`-independent mapping or `postDefaultRequests`-style accounting) so it can never be cleared through `_claimDefaultedInstantWithdrawRequest` / `defaultRecoveryEpoch`. Alternatively, key defaulted instant claims by a snapshot of `instantWithdrawClaimsByEpoch` taken at finalization rather than by live per-epoch mappings.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (test/foundry/IdleCreditVault.t.sol harness)
// Precondition: pool defaulted and finalizeDefaultRecovery ran with
// defaultRecoveryPrice > 0 and defaultRecoveryReserve == R.

// Attacker holds tranche tokens (or deposits post-default if allowed).
uint256 atk = 1_000 * ONE_SCALE;

// 1) Post-default instant withdraw request. epochNumber == defaultRecoveryEpoch,
//    so the receipt is recorded into instantWithdrawsRequestsByEpoch[attacker][defaultEpoch]
//    and instantWithdrawClaimsByEpoch[defaultEpoch] despite not being part of
//    the finalized claim basis.
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(atk, address(AAtranche)); // CDO wrapper into strategy.requestInstantWithdraw

// 2) Claim. defaultRecoveryFinalized && defaultInstantWithdrawsFinalized routes to
//    _claimDefaultedInstantWithdrawRequest, which pays atk * defaultRecoveryPrice / 1e18
//    from defaultRecoveryReserve via _transferDefaultRecovery.
uint256 reservePre = IdleCreditVault(address(strategy)).defaultRecoveryReserve();
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();

uint256 paid = underlying.balanceOf(attacker) - balPre;
assertGt(paid, 0);
assertEq(
    IdleCreditVault(address(strategy)).defaultRecoveryReserve(),
    reservePre - paid,
    'post-default instant receipt stole recovery reserve'
);
// Honest defaulted claimants' reserve is reduced by `paid`; the attacker's
// receipt was funded by no one and was never in the finalized basis.
```

Note: I could not fully verify the CDO-side wrapper (`IdleCDOEpochVariant.requestWithdraw`/instant path) does not gate instant requests when `defaulted()` is true, since my remaining iteration budget was exhausted; the vulnerability exists if the CDO forwards instant withdraw requests post-default, which the vault's own post-default UX support (e.g., `postDefaultRequests`) strongly suggests it does.
