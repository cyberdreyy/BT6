### Title
External initiator credentials satisfy `isUser` check in `PipelineRunsController.Create`, allowing EI holders to trigger arbitrary integer-ID job runs despite explicit "EIs not allowed" intent - ([File: core/web/pipeline_runs_controller.go], [File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` unconditionally sets `SessionUserKey` to a synthetic `clsessions.User{Role: UserRoleRun}` for any valid EI credential, which makes `auth.GetAuthenticatedUser` return `ok=true` for EI-authenticated requests exactly as it would for a real session/token user. `PipelineRunsController.Create` uses this same `GetAuthenticatedUser` check to gate its "only users are allowed to run jobs using int IDs — EIs not allowed" logic, so an EI credential holder passes that gate and can trigger `RunJobV2` on any arbitrary integer job ID, with no verification that the job is bound to that EI.

### Finding Description
`AuthenticateExternalInitiator` validates the EI access key/secret against `bridges.ExternalInitiator` and, on success, sets both `SessionExternalInitiatorKey` and `SessionUserKey`: [1](#0-0) 

`RequiresRunRole` only checks `user.Role != UserRoleView`, so the synthetic `UserRoleRun` user passes it just like a real session user would: [2](#0-1) 

In `PipelineRunsController.Create`, the code explicitly states the intent that only real users, not EIs, may trigger runs by integer job ID: [3](#0-2) 

The check `_, isUser := auth.GetAuthenticatedUser(c)` at line 109 only inspects whether `SessionUserKey` is present and is a `*clsessions.User` — it does not check for the *absence* of `SessionExternalInitiatorKey`, nor any binding between the EI and the job. Since `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` evaluates to `true` for EI-authenticated requests. The code then parses the path parameter as `int32` and calls `prc.App.RunJobV2(ctx, jobID, nil)` directly with no ownership or binding check to the calling EI at all — any int32 job ID in the system can be triggered, not just the EI's associated webhook job.

The comment "EIs not allowed" documents that this path was intended to be user-only, but the implementation's use of `GetAuthenticatedUser` (which cannot distinguish a real user session from the EI-synthesized user object) fails to enforce that intent.

### Impact Explanation
Holding only EI credentials for one external initiator (no edit/admin grant on any job), an attacker can trigger job runs (`RunJobV2`) on **any** job addressable by integer ID, not limited to the job(s) bound to that EI via `externalInitiators` TOML config. This is an authorization-exactness violation — unauthorized triggering of pipeline runs on jobs unrelated to the EI's configured binding, potentially causing unwanted on-chain transactions, resource consumption, or interference with unrelated jobs (e.g., OCR/flux monitor/keeper-adjacent pipelines that expose integer-ID runnable specs).

### Likelihood Explanation
Precondition is simply possession of valid `X-External-Initiator-Access-Key`/`X-External-Initiator-Secret` for any registered external initiator — a credential class explicitly weaker than edit/admin. No knowledge of, or relationship to, the target job is required beyond guessing/enumerating its integer ID. The request is a single unauthenticated-cookie POST to `/v2/jobs/:ID/runs` with EI headers, fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject external-initiator-authenticated requests for the integer-ID path by checking `auth.GetAuthenticatedExternalInitiator(c)` and refusing if present (rather than relying solely on `GetAuthenticatedUser`), or have `AuthenticateExternalInitiator` set a distinguishable marker/role (e.g., a dedicated `UserRoleExternalInitiator` or a separate context key) that `RequiresRunRole`/`Create` can differentiate from genuine user sessions.

### Proof of Concept
1. Create a webhook job A with `externalInitiators` bound to EI "ei-1", and create a second, unrelated job B (integer ID) not bound to "ei-1".
2. Authenticate as EI "ei-1" using `AuthenticateExternalInitiator` (via `X-External-Initiator-Access-Key/Secret` headers) and POST to `/v2/jobs/{jobB.ID}/runs`.
3. Assert that `isUser` in `PipelineRunsController.Create` evaluates true for the EI-authenticated context (unit test directly on `auth.GetAuthenticatedUser` after calling `AuthenticateExternalInitiator`), and that the handler-level integration test currently returns `200 OK` with a `pipelineRun` for job B instead of `401/403 Unauthorized`.
4. Expected assertion after fix: response should be `401/403`, and `pipeline_runs` count for job B should remain unchanged.

```go
// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
