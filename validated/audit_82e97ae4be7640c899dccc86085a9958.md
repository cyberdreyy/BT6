Based on my analysis, I cannot fully confirm this vulnerability given the tool budget, but the evidence strongly points to a real canonicity gap.

### Title
`get_block_burn_view` accepts a non-canonical (orphaned) `TenureChange::Extend` burn view as long as it descends from the parent's burn view, letting `validate` root all subsequent tenure/parent checks in a stale sortition fork - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoChainState::get_block_burn_view` [1](#0-0)  only verifies that a `TenureChange::Extend`'s claimed `burn_view_consensus_hash` is a *descendant* of the parent block's stored burn view (via `get_ancestor_sort_id` walking back from the claimed CH's own sortition to the parent's burn-view height) - it never checks that the claimed CH is itself on the current canonical Bitcoin fork. `postblock_proposal::validate` then uses `SortitionDB::get_block_snapshot_consensus` on this attacker-chosen, potentially since-orphaned CH to build `sort_tip`, and roots `check_block_has_valid_tenure`/`check_block_has_valid_parent`/`get_expected_burns`/`validate_normal_nakamoto_block_burnchain` against a `SortitionHandleConn` for that stale fork instead of the canonical tip [2](#0-1) .

### Finding Description
The equality that should hold is: the burn view used to validate a `TenureChange::Extend` block must equal the canonical sortition tip's consensus hash at validation time. Instead, `get_block_burn_view` trusts `tenure_change.burn_view_consensus_hash` from the miner-supplied transaction directly, subject only to a fork-connectivity check against the parent's stored burn view - not canonicity against the current tip [3](#0-2) . If a Bitcoin reorg happened after the parent's burn-view height, an old-fork consensus hash can still satisfy `get_ancestor_sort_id(..., parent_burn_view_sn.block_height, ...) == parent_burn_view_sn.sortition_id`, because both the orphaned and canonical forks share the same ancestor at that height. `validate` then does `SortitionDB::get_block_snapshot_consensus(sortdb.conn(), &burn_view_consensus_hash)` [4](#0-3) , which looks up the snapshot by consensus hash regardless of whether it's canonical, and builds `db_handle`/`burn_dbconn` rooted at that (possibly orphaned) sortition ID, which is then used for `check_block_has_valid_tenure` and burn-total/expected-burns checks [5](#0-4) .

However, I was unable to fully verify two things within the available tool budget that are essential to confirming exploitability:
1. Whether `check_block_builds_on_highest_block_in_tenure` (used by `check_block_has_valid_parent`) independently re-derives/enforces canonicity using `sortdb`'s actual canonical tip rather than the passed-in stale `db_handle`/`sort_tip`.
2. Whether the signer's independent `SortitionsView` (in `stacks-signer/src/chainstate/v1.rs`) performs its own canonicity cross-check of the tenure-extend's `burn_view_consensus_hash` against its locally-tracked canonical tip before accepting the node's validation result - this is the "cross-check" the question's proof idea explicitly requires, and I could not inspect its implementation before running out of iterations.

Additionally, `validate_nakamoto_tenure_snapshot` (used elsewhere in chainstate block-append processing, not confirmed to be reachable from `postblock_proposal::validate`) does perform a canonicity check by comparing against `SortitionDB::get_canonical_burn_chain_tip` [6](#0-5) . If an equivalent canonicity check exists inside the signer's `SortitionsView` or inside `check_block_has_valid_parent`'s downstream calls, this could already close the gap for the signer-signing path even if `postblock_proposal::validate` alone is permissive.

### Impact Explanation
If confirmed exploitable end-to-end (i.e., if the signer's `SortitionsView` does not independently re-derive and compare against the canonical tip), this would let a single-slot miner get a signer to sign a `TenureChange::Extend` block whose approval context (burn view, and thus the sortition-derived expected burns/tenure legitimacy) is bound to a non-canonical, orphaned fork - a canonicity violation (Critical: signer signing a non-canonical block).

### Likelihood Explanation
Requires the attacker to be the current tenure's miner (satisfied by the scoped precondition), and requires a Bitcoin reorg to have occurred after the parent block's burn-view height so that an orphaned-but-still-connectable consensus hash exists. This is a real but non-trivial precondition (reorgs are not attacker-controlled events, though shallow reorgs do occur), making exploitation opportunistic rather than reliably repeatable on demand.

### Recommendation
In `get_block_burn_view`, in addition to the existing ancestor-connectivity check against the parent's burn view, verify that `tenure_change.burn_view_consensus_hash`'s snapshot is itself an ancestor of (or equal to) the *current* canonical sortition tip (e.g., via `SortitionDB::get_canonical_burn_chain_tip` + `get_ancestor_sort_id`, mirroring the check already done in `validate_nakamoto_tenure_snapshot`). This closes the gap regardless of whether downstream callers (`postblock_proposal::validate`, chainstate block processing, or the signer's `SortitionsView`) already have their own redundant canonicity checks.

### Proof of Concept
Given I could not confirm whether `check_block_has_valid_parent`'s downstream logic or the signer's `SortitionsView` already independently prevents this, I cannot assert a definitive exploit. A proof-of-concept would need to:
1. Set up a sortition DB with a Bitcoin reorg after the parent block's burn-view height, producing an orphaned consensus hash `CH_orphan` and a canonical one `CH_canonical`, both descending from the same parent-burn-view ancestor.
2. Craft a `NakamotoBlock` with a `TenureChange` payload (`cause: Extended`, `tenure_consensus_hash`/`prev_tenure_consensus_hash` = current tenure CH, `burn_view_consensus_hash: CH_orphan`).
3. Call `postblock_proposal::NakamotoBlockProposal::validate` and assert whether it incorrectly returns `Ok(..)` (bug) or correctly returns `Err(BlockValidateRejectReason{ reason_code: NonCanonicalTenure/NoSuchTenure, .. })` (guard holds).
4. Separately drive the signer's `SortitionsView` (v1) state machine with the same crafted proposal and assert whether it independently rejects the mismatch between `CH_orphan` and its own canonical tip before any signature is produced.

This requires further investigation of `check_block_builds_on_highest_block_in_tenure` and `stacks-signer/src/chainstate/v1.rs`'s `SortitionsView` to determine if either already enforces canonicity, which I was unable to complete within this session.
