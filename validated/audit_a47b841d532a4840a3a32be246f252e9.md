### Title
Signer Weight Double-Counted on Reject→Accept Vote Change Causes Spurious `SignersRejected` Abort - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::handle_signer_messages` (around lines 386-591 of `stacks-node/src/nakamoto_node/stackerdb_listener.rs`) tallies each signer's weight into either `BlockStatus::total_weight_approved` or `BlockStatus::total_weight_rejected`, keyed by `slot_id`, to decide when the mining coordinator has reached the 70% signing threshold or the 30%+ blocking-rejection threshold. The `Rejected` branch only records weight into `total_weight_rejected` if `block.responded_signers.insert(slot_id)` is true (first response), and there is no code path that ever removes a slot's weight from `total_weight_rejected` once recorded. When that same signer later legitimately reconsiders and sends `BlockResponse::Accepted` for the same block hash, the `Accepted` branch checks only `block.gathered_signatures.contains_key(&slot_id)` (false, since they never accepted before) and unconditionally adds the signer's weight to `total_weight_approved` — without checking or clearing the prior `total_weight_rejected` contribution.

The result: a single signer that flips its vote from Reject to Accept has its weight counted in **both** aggregate totals simultaneously. `total_weight_approved + total_weight_rejected` can now exceed `total_weight`, and the stale rejection weight persists for the lifetime of that block hash's `BlockStatus` entry even after the signer has withdrawn its rejection.

### Finding Description
The coordinator loop in `signer_coordinator.rs` (`SigningCoordinator::wait_on_signature_result`, lines ~482-561) evaluates, on every update:

```rust
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    // ... abort with NakamotoNodeError::SignersRejected
} else if block_status.total_weight_approved >= self.weight_threshold {
    // ... success
}
``` [1](#0-0) 

This check is a proxy for "does a blocking minority (>30% weight) currently reject this block?" The invariant it depends on is that each signer's weight is counted on exactly one side (reject XOR accept) at any point in time — i.e., the aggregate reject/accept weight must reflect the signers' *current* votes, not a stale union of every vote they have ever cast.

That invariant is broken in `stackerdb_listener.rs`:

- `Rejected` handling adds weight to `total_weight_rejected` guarded only by `responded_signers.insert(slot_id)` (first-response gate), with no linkage to whether the signer later accepts: [2](#0-1) 

- `Accepted` handling adds weight to `total_weight_approved` guarded only by `!block.gathered_signatures.contains_key(&slot_id)`, with no check of, or adjustment to, `total_weight_rejected`: [3](#0-2) 

There is no code anywhere in the file (confirmed via `grep` across the repo) that decrements `total_weight_rejected` when a signer later accepts, or vice versa. This is unlike the actual per-signer state machine on the signer side (`stacks-signer/src/v0/signer.rs`), which explicitly re-evaluates and allows a signer's decision to be revised (`should_reevaluate_reject_reason`, `should_reevaluate_block`) — the node-side aggregator was never built to track that a previously-rejecting signer can flip.

Concretely:
1. `poolAmount`-analogous quantity here is "current rejecting weight." Before the flip: signer S (weight w) has rejected; `total_weight_rejected` includes w.
2. Signer S reconsiders (e.g., after a re-proposal, `should_reevaluate_reject_reason` allows this) and sends `Accepted`. `total_weight_approved` now also includes w.
3. After the flip: `total_weight_rejected` still includes w (never cleared), so the aggregate reject tally is now stale/inflated relative to the true, current set of rejecting signers.
4. If other signers' independent rejections (weight ≥ blocking_minority − w) accumulate concurrently, `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can become true purely because of S's stale, superseded rejection weight, even though S no longer opposes the block and the *true* current rejecting weight is below the 30% blocking-minority threshold.

This exactly parallels the external report's bug class: a check is performed against an aggregate/global quantity (`total_weight_rejected`) that is not kept consistent with the specific, current state that actually determines the real-world outcome (whether a blocking minority is currently rejecting), just as the PUT-liquidity check validated total stablecoin value instead of the specific token balance needed at payout time.

### Impact Explanation
This is a liveness wedge on block production: the mining coordinator can spuriously conclude that a "blocking minority" rejects a valid, ultimately-signable block and abort with `NakamotoNodeError::SignersRejected`, discarding legitimate transactions/excluding txids and forcing a retry — even though the actual, current signer weight opposing the block does not meet the 30% blocking threshold. Because `total_weight_rejected` is monotonically increasing and never corrected for reconsidered votes, the effect compounds over the life of a `BlockStatus` entry (i.e., across re-evaluations of the same proposal), making stalls more likely the more often signers change their minds (which the signer-side logic explicitly permits and even encourages via re-proposal flows described in the pre-commit/re-evaluation design). This does not, by itself, let an invalid/non-canonical block get signed (the actual on-chain `verify_signer_signatures` check independently re-derives weight from unique, valid signatures over the header), so it is not a Critical safety break — but it is a High-severity liveness issue matching "a signer [set] wedged into never signing valid blocks" via a miscounted/aggregated tally that diverges from the verified, per-signer current state.

### Likelihood Explanation
No malicious majority or privileged access is required. It only requires an honest signer to reject a proposal for a transient/recoverable reason (e.g., `ConnectivityIssues`, `ValidationFailed` state that later clears) and subsequently accept the same or a re-proposed block hash — a flow the signer-side code explicitly supports (`should_reevaluate_reject_reason`, re-proposal handling in `should_reevaluate_block`, `stacks-signer/src/v0/signer.rs` lines ~1481-1571). Combined with ordinary, independent rejections from a modest number of other signers (which happens routinely under normal network conditions, e.g. slow validation, timeouts), the stale weight can push the aggregate over the abort threshold. This requires no coordinated attack, no key compromise, and no majority — just normal operational variance in signer responsiveness.

### Recommendation
Track each signer's *current* vote per block (e.g., a `HashMap<u32, Vote>` where `Vote` is `Accepted` or `Rejected`) rather than two independently-incrementing weight counters. When a new response for a `slot_id` arrives:
- If the signer's stored vote differs from the previous one, first subtract the previous vote's weight from the corresponding aggregate (`total_weight_approved` or `total_weight_rejected`) before adding it to the new one.
- Only then update `total_weight_approved`/`total_weight_rejected`, guaranteeing each slot's weight is counted on exactly one side at any time, mirroring the "track per-buyToken locked amounts" recommendation from the analogous report (track the up-to-date per-signer vote instead of a cumulative append-only aggregate).

### Proof of Concept
Not directly executable without a live multi-signer harness, but the code-level trace is deterministic:

1. Miner proposes block B; `BlockStatus` for B initialized with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight `w_S`) sends `BlockResponse::Rejected` for B. In `stackerdb_listener.rs`, `responded_signers.insert(slot_S)` → true → `total_weight_rejected += w_S`. [2](#0-1) 
3. Independently, other signers with combined weight `w_R` also reject B, such that `w_S + w_R + weight_threshold > total_weight` is not yet true (block still alive) but `w_R + weight_threshold` alone is not enough either.
4. Signer S later re-evaluates B (e.g. after a delayed re-proposal, per `should_reevaluate_block`/`should_reevaluate_reject_reason`) and sends `BlockResponse::Accepted`. `gathered_signatures.contains_key(slot_S)` is false → `total_weight_approved += w_S`. [3](#0-2) 
   Note `total_weight_rejected` is untouched — it still includes `w_S`.
5. Now `total_weight_rejected == w_S + w_R`, unchanged from step 3, while `total_weight_approved` has increased by `w_S`. If `w_S + w_R + weight_threshold > total_weight` (a condition purely a function of the stale rejected sum, not the live one), `SigningCoordinator::wait_on_signature_result` triggers `NakamotoNodeError::SignersRejected` on the very next poll: [4](#0-3) 
   even though the *current* rejecting weight is only `w_R` (S has switched to Accept), which may be well under the 30% blocking-minority threshold.
