### Title
Stale shared `lastWithdrawRequest` marker lets a user escape the epoch loss haircut and drain other claimers' funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2023-28320 is a shared global buffer accessed without synchronization: many independent operations corrupt one piece of shared state. The closest analog in idle-tranches is `IdleCreditVault`, where per-epoch withdraw receipts share a single mutable marker, `lastWithdrawRequest[_user]`, while loss haircuts are stored per epoch in `lossRecoveryPriceByEpoch`. A new withdraw request overwrites the shared marker, orphaning an older epoch's loss price so its receipts are claimed at par instead of at the haircut recovery price.

### Finding Description
`requestWithdraw` records all receipts under one scalar marker, `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) . When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` stores the haircut under the *current* `epochNumber` in `lossRecoveryPriceByEpoch` and reduces the funded amount [2](#0-1) .

Claims then use that shared marker as the loss-epoch key: `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [3](#0-2) . If the user requests a withdraw in a later epoch, `lastWithdrawRequest` is overwritten, the lookup for the new epoch returns 0, and the loss-adjusted branch is skipped entirely. `claimWithdrawRequest` then falls through to `_claimFundedWithdrawRequest`, which pays the aggregate `withdrawsRequests[_user]` — including the basis that was supposed to be haircut — at par via `_transferFundedClaim` [4](#0-3) . The only epoch gate is `epochNumber <= lastWithdrawRequest` reverting, which does not bind the claim to the loss epoch [5](#0-4) .

### Impact Explanation
The strategy was funded with only `pendingBasis - pendingLoss` by the borrower, but the attacker's receipt is paid at 100%. This breaks the loss-waterfall invariant: one receipt's haircut is escaped and the shortfall is socialized onto every other pending claimer of that epoch — the last claimers' `_transferFundedClaim` transfers revert or pay nothing, permanently freezing their funded receipts. Loss equals the escaped `pendingLoss` share, proportional to the attacker's pending basis.

### Likelihood Explanation
The attacker is an ordinary KYC-passing lender/tranche-token holder (unprivileged). Requirements: (1) have a pending withdraw receipt in an epoch that ends in a `stopEpochWithDuration` loss, and (2) submit a second withdraw request in a subsequent epoch before claiming, which is a normal, permitted user action. No privileged cooperation is needed; the honest manager/borrower sequence around it. Caveat: I was unable to fully verify the epoch-numbering order of `deposit()`/`epochNumber++` relative to `collectWithdrawFunds` inside `stopEpochWithDuration` and the exact revert behavior inside `_transferFundedClaim` on insufficient balance; if the loss price is stored under the same epoch as `lastWithdrawRequest` and later requests cannot orphan it, severity drops to accounting edge cases.

### Recommendation
Track the claim's loss epoch per receipt instead of via the shared `lastWithdrawRequest` scalar — e.g., iterate `lossRecoveryPriceByEpoch` against each epoch present in `withdrawsRequestsByEpoch[_user]`, or store a per-user loss-epoch list — so that a later request cannot orphan an earlier epoch's haircut. Additionally, in `_claimFundedWithdrawRequest`, verify that no uncleared `lossRecoveryPriceByEpoch` entry applies to any of the user's outstanding epochs before paying at par.

  /// @notice Claim a funded non-default withdraw request at par.
  /// @param _user address of the user
  /// @return amount amount claimed
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
