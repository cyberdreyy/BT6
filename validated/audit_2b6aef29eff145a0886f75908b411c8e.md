### Title
Stale confirmations from removed multisig members still count toward execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges pending requests that the removed member *originated*, but never scrubs that member's *confirmations* recorded on other members' still-pending requests. `confirm` then compares `confirmations.len()` against `num_confirmations` without re-validating that every recorded confirmer is still a current member, so a request can be executed using a confirmation from an account/key that has since been removed from the multisig.

### Finding Description
`confirm` decides to execute a request purely by counting entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set: [1](#0-0) 

Membership is only checked for the *caller* of the current `confirm`/`add_request` call via `current_member()`: [2](#0-1) 

When a member is removed via `DeleteMember` → `delete_member`, the cleanup logic only deletes requests where `r.member == member` (i.e., requests the removed member *created*) and removes that member's `num_requests_pk` entry and the `members` set entry: [3](#0-2) 

It never iterates `self.confirmations` to strip the removed member's string from confirmation sets of *other* pending requests that member had previously confirmed but did not create. Those stale confirmations remain in storage and continue to be counted by `confirm`'s `confirmations.len() as u32 + 1 >= self.num_confirmations` check. This breaks the binding "confirmations counted == live members that actually approved": after removal, the recorded confirmation count can still equal or exceed `num_confirmations` even though the number of *live* approving members is one less than the threshold requires.

### Impact Explanation
This directly matches the in-scope "multisig request executed below threshold" impact. An attacker (a current or former member who created/confirmed a request before being removed, or any member colluding with one who is later removed) can get a malicious request (e.g., `Transfer`, `AddKey` with full access, `FunctionCall`) to execute with fewer *live* approving members than `num_confirmations` requires, because a removed member's stale confirmation is still tallied. This is an unauthorised move of NEAR/authority — an actual custody/authorization boundary being crossed with an attacker gaining execution rights they should not have.

### Likelihood Explanation
This requires only a normal, foreseeable multisig operational sequence: (1) a member creates/confirms a request that doesn't yet reach threshold, (2) that confirming member is later removed via `DeleteMember` (a routine multisig maintenance action, e.g., due to key rotation, compromise response, or membership change — not requiring any special exploit), (3) the original (still-pending) request is later confirmed by enough *other* live members to nominally reach the counted threshold, even though one of the counted confirmations belongs to a no-longer-valid member. No privileged or out-of-scope actor is needed beyond the normal multisig members themselves performing routine actions in a realistic order.

### Recommendation
In `delete_member`, iterate all entries of `self.confirmations` (not just `self.requests` filtered by originator) and remove the deleted member's identifier from every confirmation set. Alternatively/additionally, in `confirm`, re-validate that every string in the stored `confirmations` set for a request still corresponds to a current entry in `self.members` before comparing the count against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. Member `A` calls `add_request_and_confirm` with a malicious `Transfer`/`AddKey` request → confirmations = `{A}` (1/3).
3. Member `B` calls `confirm(request_id)` → confirmations = `{A, B}` (2/3), below threshold, so the request stays pending.
4. Via a separate legitimate `DeleteMember` request, the members remove `B` from the multisig (e.g., because `B`'s key was flagged as compromised). `delete_member` (`multisig2/src/lib.rs:356-379`) only clears requests originated by `B`; the pending malicious request from step 2, which `B` merely confirmed, is untouched, and `confirmations` for it still contains `"B"`.
5. Member `C` calls `confirm(request_id)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → `execute_request` runs the malicious `Transfer`/`AddKey`, even though only 2 *live* members (`A` and `C`) actually approved it, one confirmation short of the real 3-of-4 threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

        let member = if env::current_account_id() == env::predecessor_account_id() {

                account_id: env::predecessor_account_id(),
            }

            Some(member)

            None
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
