### Title
Signer vote-flip is double-counted across the approval and rejection weight tallies — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` tallies two independent, supposedly mutually-exclusive weight totals for a proposed block — `total_weight_approved` and `total_weight_rejected` — one per `BlockResponse` variant. The gate used to prevent double-counting on the `Accepted` path (`gathered_signatures.contains_key(&slot_id)`) is entirely disjoint from the gate used on the `Rejected` path (`responded_signers.insert(slot_id)`). If a single signer first rejects a block and later legitimately flips to accepting the very same block (a state transition the signer state machine explicitly supports as `LocallyRejected -> LocallyAccepted` on re-evaluation), that signer's weight is added to `total_weight_rejected` by the first message and then *also* added to `total_weight_approved` by the second message. Nothing ever subtracts the earlier reject weight. The coordinator's threshold arithmetic (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) then operates on a corrupted state where the two weights can sum to more than the total signer weight, letting a stale rejection combine with fresh approvals (or vice-versa) to falsely cross the "block globally rejected" threshold even though a real quorum currently approves the block.

### Finding Description
`StackerDBListener::run` maintains a `BlockStatus` per `signer_signature_hash`: [1](#0-0) 

For `BlockResponse::Accepted`, weight is added only if the slot is not already present in `gathered_signatures`: [2](#0-1) 

For `BlockResponse::Rejected`, weight is added only if the slot is newly inserted into `responded_signers`: [3](#0-2) 

There is no cross-check between the two paths: the `Accepted` handler never looks at `responded_signers`/prior rejection state for that slot, and the `Rejected` handler never looks at `gathered_signatures`. Consequently the same `slot_id`’s weight can land in both `total_weight_approved` and `total_weight_rejected` simultaneously if the signer sends a `Rejected` message followed later by an `Accepted` message for the same block hash (or the reverse order).

This sequence is reachable by a single, honest-but-reconsidering signer. The signer-side state machine explicitly allows a block to move from `LocallyRejected` back to `LocallyAccepted` upon re-evaluation: [4](#0-3) 

and the pre-commit/threshold-crossing path that produces the final signature explicitly re-runs the chainstate checks and can decide to sign a block it had earlier rejected, once a competing conflict is judged stale: [5](#0-4) 

Each such transition causes the signer to broadcast the corresponding `BlockResponse` (`Rejected`, then later `Accepted`) over StackerDB for the *same* block. The `StackerDBListener` on the node side processes each broadcast independently and, as shown above, has no mechanism to retract the earlier tally when the vote changes.

The consumer of these tallies, `signer_coordinator.rs`, checks rejection weight before acceptance weight each loop iteration: [6](#0-5) 

so a stale, never-retracted rejection weight can push `total_weight_rejected + weight_threshold > total_weight` and produce `NakamotoNodeError::SignersRejected` even while `total_weight_approved` (including that very signer's later acceptance) has independently reached, or is approaching, the acceptance threshold. This breaks the intended equality "each signer's weight counts toward exactly one side of the vote" and directly corresponds to the reported bug class: a supplementary/secondary tracking structure (here, `gathered_signatures` vs. `responded_signers`) is not kept consistent with the primary one, letting one entity's authorization state be simultaneously counted under two conflicting classifications.

`reset_rejections` (used only on proposal timeout/retry) demonstrates that the developers are aware rejection weight must sometimes be cleared and re-armed, but that mechanism only runs on the explicit timeout path, not on an ordinary vote flip within the same round: [7](#0-6) 

### Impact Explanation
This is a rejection-vs-acceptance miscount: a single non-majority, otherwise honest signer's legitimate reconsideration causes its weight to be simultaneously and permanently counted in both `total_weight_rejected` and `total_weight_approved` for the same block, without any majority collusion. Depending on timing, this can cause the coordinator to declare a block globally rejected (`SignersRejected`) even though the real, current tally of votes has enough approval weight to meet the 70% threshold, wedging that round of block production and forcing miner-side fallback behavior (txid exclusion, block re-proposal). This matches the specified High/Critical impact class of "a rejection recounted as an accept" / miscounted response breaking the aggregated-weight-vs-verified-accepts equality.

### Likelihood Explanation
The trigger condition — a signer moving from `LocallyRejected` to `LocallyAccepted` for the same block within one round — is an explicitly modeled and supported transition in the signer state machine (not an edge case reachable only via malicious behavior), and can occur under normal operating conditions (e.g., a conflict the signer initially rejected against becomes stale, or the chainstate re-check at pre-commit-threshold time passes after failing earlier). No majority of signers, no attacker keys, and no StackerDB-transport manipulation are required — a single signer's ordinary re-evaluation is sufficient to desynchronize the two tallies on the node side.

### Recommendation
Track a single per-slot "current vote" (accept or reject) in `BlockStatus` instead of two independently-gated counters. When a new `BlockResponse` arrives for a slot that already has a recorded vote of the opposite kind, first subtract that slot's weight from the previous tally (`total_weight_rejected` or `total_weight_approved`) before adding it to the new one, so that at all times each slot's weight contributes to at most one of the two totals.

### Proof of Concept
1. Node proposes block B; `StackerDBListenerComms::insert_block` initializes `BlockStatus` for B with zeroed tallies.
2. Signer S (weight `w`) initially rejects B (e.g., because its own chainstate view conflicts) and broadcasts `BlockResponse::Rejected`. The listener's `Rejected` handler inserts S's slot into `responded_signers` and adds `w` to `total_weight_rejected`.
3. Before the round times out, S's local view is re-evaluated (e.g., the conflicting sibling becomes stale per `check_block_against_signer_db_state`), and S signs B, broadcasting `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. The listener's `Accepted` handler sees S's slot is not in `gathered_signatures` (independent structure) and adds `w` to `total_weight_approved`.
5. `BlockStatus` for B now shows `w` counted in both `total_weight_rejected` and `total_weight_approved`; if enough other signers have also approved, `signer_coordinator`'s check `total_weight_rejected.saturating_add(weight_threshold) > total_weight` can fire from the stale rejection weight even though a legitimate quorum (including S) currently approves B, producing an erroneous `SignersRejected` outcome for a block that should have been accepted.

    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
