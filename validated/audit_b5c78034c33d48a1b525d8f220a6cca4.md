### Title
Shared global token bucket can be drained by an already-throttled sender, causing global-DoS of legitimate requests - (File: `core/services/workflows/ratelimiter/ratelimiter.go`)

### Summary
The reported dForce issue is that a *global* accumulator (daily limit) can be manipulated by a single unprivileged actor because the code that updates the shared/global counter does not properly gate on a per-actor check first, letting one caller degrade service for everyone until an admin intervenes. The same structural pattern exists in chainlink's rate-limiting primitive `RateLimiter.Allow`, which is reused across the gateway/workflow ingestion paths that accept requests from unprivileged, per-workflow or per-node senders.

### Finding Description
`RateLimiter.Allow` unconditionally consumes a token from the shared global bucket on every call, independent of whether the caller's own per-sender bucket already rejected the request: [1](#0-0) 

```go
func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	...
	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
```

Both `senderLimiter.Allow()` and `rl.global.Allow()` are evaluated on every invocation, with no short-circuit when `senderAllow` is already `false`. This means an attacker that has already exhausted their own per-sender quota can keep issuing requests and each one will still decrement the *shared* global bucket, because `Allow()` provides no mechanism to skip the global-token consumption for requests that are already known to be individually disallowed.

The same design (two independently-consumed buckets returned as `(senderAllow, globalAllow)`) is mirrored in the gateway's outgoing/incoming rate limiters used on request paths reachable from unprivileged, per-workflow callers: [2](#0-1) [3](#0-2) 

In `handleSingleNodeRequest`, `req.WorkflowID` is caller-controlled (each workflow the attacker deploys gets a brand-new per-sender bucket with full burst, per `outgoingRateLimiterConfigDefaults`), and every one of the attacker's requests also drains the single shared `globalAllow` bucket used by *all other workflows* on that node: [4](#0-3) 

The workflow-registry syncer path (`v2/helpers.go`) instantiates the identical `ratelimiter.Config` pattern with `GlobalRPS`/`PerSenderRPS` for external event processing: [5](#0-4) 

Because the global bucket refills only at the configured `GlobalRPS`, sustained low-cost traffic from one attacker-controlled sender (or many attacker-created per-sender identities, each still touching the same global bucket) can keep the global bucket perpetually near zero.

### Impact Explanation
This is a denial-of-service against the shared global rate limiter: a single unprivileged sender (a workflow owner controlling their own `WorkflowID`, or any entity able to submit sender-tagged messages) can consume the entire global quota even while being individually throttled, causing legitimate, unrelated workflows/senders to be rejected with "global rate limit exceeded" / "workflow exceeded limit of gateways requests" errors. This matches the "inconvenience for legitimate users" impact described in the report, and can persist as long as the attacker keeps sending requests, since there is no mechanism that isolates a blocked sender's requests from the shared global counter.

### Likelihood Explanation
High. `WorkflowID` (or `sender`) is supplied by the caller and is not required to be scarce — an actor can deploy multiple workflows or vary the sender label to keep tapping fresh per-sender buckets (full burst each time) while continuously depleting the single shared global bucket. No special privilege beyond normal workflow/node participation is required to reach these code paths (`HandleSingleNodeRequest`, `HandleGatewayMessage`).

### Recommendation
Change `Allow` (and its analogs in the gateway `ratelimit` package used by `outgoing_connector_handler.go`) so that the global bucket is only consumed when the per-sender check passes, e.g.:
```go
func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
    senderAllow = senderLimiter.Allow()
    if !senderAllow {
        return false, rl.global.Tokens() > 0 // or just return false, true — do not consume
    }
    globalAllow = rl.global.Allow()
    return senderAllow, globalAllow
}
```
More generally, only debit the shared/global resource after the local (per-sender) gate has already accepted the request, preventing already-rejected traffic from being able to exhaust capacity intended for other tenants.

### Proof of Concept
1. Configure (or use default) `outgoingRateLimiterConfigDefaults`: `GlobalRPS=100`, `GlobalBurst=100`, `PerSenderRPS=5`, `PerSenderBurst=50` (`core/capabilities/webapi/outgoing_connector_handler.go:28-35`).
2. Attacker deploys/controls a workflow and repeatedly calls `HandleSingleNodeRequest` with a fixed `WorkflowID`, or rotates `WorkflowID` values across many attacker-owned workflows.
3. Even once a given `WorkflowID`'s per-sender bucket is exhausted (`workflowAllow=false`), each additional call to `c.outgoingRateLimiter.AllowVerbose(req.WorkflowID)` still consumes one token from the shared `global` bucket (see `Allow` implementation), because there is no short-circuit on `senderAllow==false`.
4. Sustained requests from the attacker keep `globalAllow` at `false`, so unrelated legitimate workflows on the same node receive `errorOutgoingRatelimitGlobal` ("global limit of gateways requests has been exceeded") until the attacker stops.

```go
func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()

	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
```
