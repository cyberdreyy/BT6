### Title
Pending APR0 withdraw requests permanently brick `stopEpoch` once APR is set non-zero, freezing all vault funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The PgBouncer bug is a null-pointer crash: an error response arrives missing an expected field (`SQLSTATE`) and the process dereferences it unconditionally. The in-scope analog is `IdleCreditVault.prepareStopEpochWithApr0`: it assumes the "field" `unscaledApr == 0` is present for the entire lifecycle of an APR0 request, and unconditionally `revert NotAllowed()` when that assumption is violated while `apr0TotalPrincipal != 0`. Because `prepareStopEpochWithApr0` is called inside `stopEpoch`, entering this state makes every subsequent `stopEpoch`/`stopEpochWithDuration` revert — a crash-equivalent that freezes the whole pool.

### Finding Description
`requestWithdraw` creates APR0 receipts whenever `unscaledApr == 0`, incrementing `apr0TotalPrincipal` via `_requestWithdrawApr0` (IdleCreditVault.sol:285-286). The global bucket is only cleared inside `prepareStopEpochWithApr0` (`apr0TotalPrincipal = 0`, line 540) or partially in the default-claim path. Before that cleanup, the function enforces:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:505-508
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

Nothing prevents the manager (an honest actor we may sequence around) from calling `setAprs` to set a non-zero APR while `apr0TotalPrincipal > 0`. From that point every call to `stopEpoch`/`stopEpochWithDuration` reverts inside `prepareStopEpochWithApr0`, so:

- `epochEndDate` passes but the epoch can never be stopped,
- pending withdraw receipts (normal and APR0) can never be funded — `_settleApr0`/`_claimFundedWithdrawRequest` stay unreachable because `epochNumber` never increments,
- new APR0-bucket requests keep reverting the same way; `emergencyShutdown`/loss paths that route through stopEpoch are equally blocked.

The only escape is the manager restoring `unscaledApr` to 0, which re-opens settlement — i.e. temporary freezing of all TVL and unclaimed yield — and during the freeze an unprivileged user can keep griefing any recovery attempt by holding an open APR0 receipt.

### Impact Explanation
Direct temporary freezing of the entire pool: every lender's principal and accrued yield (AA and BB), all pending withdraw receipts, and pending instant requests are locked while `apr0TotalPrincipal != 0 && unscaledApr != 0`. Loss is the full vault TVL for the duration of the freeze; if APR must remain non-zero for business reasons, the freeze is effectively permanent. This matches the accepted "temporary freezing" / "permanent freezing of unclaimed yield" impact classes, not a gas/DoS-only issue, since real user funds are immobilized.

### Likelihood Explanation
The attack path needs only an unprivileged KYC'd lender plus a routine management action:

1. Pool operates in APR0 mode (`unscaledApr == 0`).
2. Attacker deposits and calls `requestWithdraw`, creating an APR0 receipt (`apr0TotalPrincipal > 0`). They simply never claim/settle it.
3. Manager later raises APR (e.g., reactivating yield-bearing epochs via `setAprs`), a normal operational call.
4. From then on `prepareStopEpochWithApr0` reverts on every stopEpoch — no privileged mistake beyond the ordinary APR change is needed, and the attacker can re-open a receipt each time APR returns to 0 to repeat the freeze.

No guard exists linking `setAprs` to `apr0TotalPrincipal`, and `epochEndDate != 0` gating in `_claimFundedWithdrawRequest` (line 326) means the freeze also blocks claims.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert when `unscaledApr != 0`. Instead, settle the outstanding APR0 bucket gracefully: either skip APR0 interest allocation (`_apr0NetInterest = 0`) and still execute `apr0TotalPrincipal = 0` plus record `apr0RateByEpoch[epochNumber] = 0`, converting the receipts to plain funded receipts, or force-settle APR0 principals at the last valid rate. Additionally, make `setAprs` revert when moving from 0 to non-zero while `apr0TotalPrincipal > 0`, so the inconsistent state can never be entered.

### Proof of Concept
Foundry fork PoC (against `test/foundry/IdleCreditVault.t.sol` harness, real vault):

```solidity
function testApr0ReceiptBricksStopEpochAfterAprRaise() external {
  // APR0 mode
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(0, 0);

  // 1) Attacker (KYC'd lender) deposits and requests a withdraw while APR == 0
  address attacker = makeAddr('apr0-freezer');
  _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
  uint256 bal = AAtranche.balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(bal / 4, address(AAtranche));
  assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0, 'apr0 bucket open');

  _startEpochAndCheckPrices(0);

  // 2) Honest manager raises APR while the APR0 receipt is still pending
  vm.prank(manager);
  IdleCreditVault(address(strategy)).setAprs(5e18, 5e18); // e.g. 5%

  // 3) Every subsequent stopEpoch reverts -> epoch can never end, TVL frozen
  deal(address(underlying), borrower, type(uint128).max);
  vm.prank(borrower);
  underlying.approve(address(cdoEpoch), type(uint256).max);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  // repeat: still bricked; pending withdraws and all LP funds remain locked
  assertTrue(cdoEpoch.isEpochRunning(), 'epoch stuck running');
}
```

Note: I was unable to fully inspect `setAprs` for a possible existing guard against `apr0TotalPrincipal > 0` (index excerpt not retrieved); if such a guard exists, the finding reduces to the residual case where APR0 receipts outlive an APR change (e.g., principal added after raise via the non-APR0 path edge cases).
