### Title
Unfunded instant-withdraw receipts are paid from funds reserved for other epochs' claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary

The reported kernel bug is a missing synchronization: `fxls8962af_fifo_flush()` iterates `indio_dev->active_scan_mask` while the device may concurrently exit buffered mode, freeing/invalidating the shared state being consumed. The analog in `IdleCreditVault` is the same bug class: `claimInstantWithdrawRequest()` consumes an aggregate receipt (`instantWithdrawsRequests[_user]`) without synchronizing against the fact that part of that aggregate belongs to a later, still-unfunded epoch. It pays the full sum out of the strategy's funded underlying balance, which is only meant to back already-funded receipts.

### Finding Description

Instant withdrawals are epoch-scoped:

- `requestInstantWithdraw()` increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). Unlike `requestWithdraw()` — which explicitly reverts if the user still holds an unclaimed loss-adjusted receipt so that `lastWithdrawRequest` keeps pointing at the epoch that stores its haircut (IdleCreditVault.sol:261-271) — `requestInstantWithdraw()` has **no** "claim your old funded receipts first" guard and records no per-request funding epoch marker on the aggregate.

- Funding for instant receipts only materializes when the CDO calls `collectInstantWithdrawFunds()` during the epoch-stop flow (`_pendingInstant() != 0` blocks `stopEpoch`, so the CDO must call `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` first), which transfers exactly `pendingInstantWithdraws` worth of underlying into the strategy and zeroes it out (IdleCreditVault.sol:398-403).

- `claimInstantWithdrawRequest()` then burns and pays the *entire* aggregate `instantWithdrawsRequests[_user]` via `_transferFundedClaim`, with no check that the whole aggregate was funded (IdleCreditVault.sol:380-393). It does not compare against `instantWithdrawsRequestsByEpoch` for the current (unfunded) epoch, and unlike `_claimFundedWithdrawRequest` (IdleCreditVault.sol:326) it does not gate on `epochNumber` at all.

Sequence (attacker = any KYC-passed tranche holder):

1. Epoch N running: attacker calls `cdoEpoch.requestInstantWithdraw(...)` (or requests normally and it is routed to the instant bucket at stop). Receipt R1 is recorded in `instantWithdrawsRequests[attacker]`.
2. Manager stops epoch N; the CDO funds R1 via `collectInstantWithdrawFunds` → strategy now holds R1 underlyings, `pendingInstantWithdraws == 0`.
3. Buffer / epoch N+1 starts: attacker does **not** claim. During epoch N+1 the attacker calls `requestInstantWithdraw(R2)` again. Now `instantWithdrawsRequests[attacker] = R1 + R2`, but only R1 is funded; R2 sits in `pendingInstantWithdraws` scheduled to be funded at the next stop.
4. Attacker calls `cdoEpoch.claimInstantWithdrawRequest()` before epoch N+1 is stopped/funded. The strategy burns R1+R2 receipts and transfers R1+R2 underlyings — paying R2 out of underlying that belongs to the funded-claims pool (other users' funded instant receipts and/or `defaultRecoveryReserve`, which `_transferFundedClaim` consults at IdleCreditVault.sol:897+).

This mirrors the CVE exactly: the claim path iterates/consumes shared state (`instantWithdrawsRequests`) that is being concurrently mutated by a different "mode" (a new epoch's unfunded requests) with no `synchronize_irq`-equivalent gate.

### Impact Explanation

Direct theft / insolvency with quantified loss: the attacker extracts R2 underlyings that were never funded for them. Every funded instant claimant (including the `IdleCDOEpochQueue`, which aggregates many users' receipts and calls `claimInstantWithdrawRequest()` in `processWithdrawalClaims`, IdleCDOEpochQueue.sol:347-351) and/or the default-recovery reserve loses up to the size of the attacker's unfunded receipt. The broken invariant is "one receipt, one funded payout" — receipts minted in an epoch are only backed once `collectInstantWithdrawFunds` runs, but the claim path pays them early.

### Likelihood Explanation

Requires only an unprivileged, KYC-passing tranche holder able to make two instant requests across an epoch boundary and to call the public claim — no privileged cooperation, no oracle manipulation, no malformed tokens. The only precondition is that instant withdrawals are enabled (`setInstantWithdrawParams`) and that the attacker's second request lands in `pendingInstantWithdraws` before they claim; both are ordinary user flows. The loss is bounded by the attacker's own deposit size but is fully repeatable each epoch.

### Recommendation

Mirror the synchronization added for normal withdrawals: either (a) revert in `requestInstantWithdraw()` when `instantWithdrawsRequests[_user] != 0` (forcing users to claim funded receipts before appending a new epoch's request — the same fix pattern as the `lossRecoveryPriceByEpoch` guard at lines 263-271), or (b) in `claimInstantWithdrawRequest()`, subtract the current-epoch unfunded portion (`instantWithdrawsRequestsByEpoch[_user][epochNumber]` while `pendingInstantWithdraws > 0`) from the payout and burn only the funded basis.

### Proof of Concept

A Foundry fork PoC would:

1. Deploy/fork the epoch CDO with instant withdrawals enabled (`setInstantWithdrawParams(delay, minAprDiff, true)`), `underlying` = USDC, attacker KYC'd via `isWalletAllowed`.
2. Attacker deposits AA, then calls `cdoEpoch.requestInstantWithdraw` → receipt R1.
3. `vm.warp(epochEndDate+1)`; manager calls `getInstantWithdrawFunds` + `stopEpoch` → strategy holds R1 underlyings, `pendingInstantWithdraws == 0`.
4. Manager calls `startEpoch`; attacker calls `requestInstantWithdraw` again → R2 added to the same `instantWithdrawsRequests` aggregate, `pendingInstantWithdraws == R2`.
5. Attacker calls `cdoEpoch.claimInstantWithdrawRequest()` before any funding of R2.
6. Assert `underlying.balanceOf(attacker)` increased by R1+R2 while only R1 was funded; assert a second funded user's subsequent `claimInstantWithdrawRequest` reverts on insufficient strategy balance (or that `defaultRecoveryReserve` was silently consumed), quantifying the theft as R2.

Note: I verified the strategy-side code paths cited above, but within the available investigation budget I could not read `IdleCDOEpochVariant.claimInstantWithdrawRequest`/`requestInstantWithdraw` entry points to rule out an epoch or funding gate on the CDO wrapper; if such a gate exists there it would mitigate this. If confirmed ungated, the finding stands as described.
