### Title
Permissionless, unauthenticated `create` lets anyone squat a victim's deterministic lockup account with attacker-chosen `lockup_duration`/`release_duration`/`vesting_schedule` - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the lockup account id deterministically as `sha256(owner_account_id) + "." + factory_account_id` and takes `owner_account_id`, `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `whitelist_account_id` directly from the caller with no check that the caller is the grantor/foundation. Any unprivileged account can pre-create the deterministic lockup address for a victim `owner_account_id` with self-chosen (malicious) release terms before the legitimate grantor's call lands, permanently occupying that account name.

### Finding Description
The invariant the question asks to validate is: `lockup_terms_created == lockup_terms_intended_by_grantor` for the account id `sha256(owner_account_id)`. In `create` at [1](#0-0) , the entrypoint is `#[payable]` and callable by any account holding `MIN_ATTACHED_BALANCE` (3.5 NEAR) — there is no `assert_called_by_foundation`, no allow-list of callers, and no check binding `owner_account_id` to `env::predecessor_account_id()`. The lockup account id is fully deterministic from `owner_account_id` alone: [2](#0-1) 

All schedule-defining fields (`lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, `staking_pool_whitelist_account_id`) are taken verbatim from the caller's arguments and forwarded into the newly deployed lockup contract's `new` call: [3](#0-2) 

Because `Promise::new(lockup_account_id).create_account()` can only succeed once per account name, an attacker can call `create(owner_account_id = victim, lockup_duration = 0, lockup_timestamp = None, vesting_schedule = None, release_duration = None, whitelist_account_id = None)` with only `MIN_ATTACHED_BALANCE` attached, ahead of the legitimate grantor's transaction. This deploys a real lockup contract at the exact address the foundation would later target, owned by `victim`, but with attacker-chosen (e.g., immediately-unlocked, no vesting, no foundation revocation) terms — since `foundation_account_id` is only attached when `vesting_schedule.is_some()`: [4](#0-3) 

When the legitimate grantor later calls `create` for the same `owner_account_id` with the real grant amount and real schedule, `create_account()` fails because the account already exists; the callback `on_lockup_create` detects failure via `is_promise_success()` and refunds the deposit to the grantor, but the account name is permanently squatted with the attacker's parameters: [5](#0-4) 

No existing guard (`assert_self`, `is_promise_success`, `MIN_ATTACHED_BALANCE` check) prevents the initial malicious creation, because they only govern the callback/refund path, not who is allowed to choose the schedule for a given `owner_account_id`. The README itself documents that "any user" can create and fund lockups for any owner and that lockups are "auto-generated from the owner account" — confirming there is no authentication tying schedule parameters to the true grantor. [6](#0-5) 

### Impact Explanation
If the foundation or a subsequent depositor is unaware the account was already squatted and transfers the real grant NEAR into the pre-existing (attacker-parameterized) lockup account — either directly or by assuming the earlier `create` succeeded with correct terms — those funds become subject to the attacker's chosen `lockup_duration`/`release_duration`/`vesting_schedule` (e.g., zero lockup duration, no vesting/no foundation termination rights), letting the `owner_account_id` withdraw funds far earlier than the grantor intended, or letting a malicious `staking_pool_whitelist_account_id` be baked in. This matches the "a lockup deployed with parameters its rightful creator never chose" Critical impact category. It is repeatable for every distinct victim `owner_account_id` the attacker wants to pre-empt, at a cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per target, and once squatted the account name is permanently unavailable to the legitimate grantor (the legitimate `create` call fails and only refunds — it cannot overwrite the existing account).

### Likelihood Explanation
The attack requires no privileges beyond an ordinary NEAR account and 3.5 NEAR (`MIN_ATTACHED_BALANCE`) — well within the defined "unprivileged attacker" capability set. The only precondition is that the attacker's `create` transaction for a given `owner_account_id` lands before the legitimate grantor's; since `owner_account_id` values for future grants (employee/investor accounts) are often predictable or publicly known ahead of the grant transaction, this is practically feasible and cheap, and can be attempted for many target accounts in parallel.

### Recommendation
Restrict `create`'s schedule-defining parameters to a trusted caller (e.g., require `env::predecessor_account_id() == foundation_account_id` or maintain a factory-side allow-list of grant issuers), or bind the deterministic lockup account id to more than just `owner_account_id` (e.g., include a grantor-provided nonce/salt known only to the grantor) so a third party cannot pre-claim the deterministic address before the legitimate grant transaction, and/or require multi-party confirmation (grantor + owner) before a lockup account name becomes immutable.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
