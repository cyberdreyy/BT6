### Title
Signer approves a TenureChange-Extend block anchored to an orphaned burn view after a burnchain reorg - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
`NakamotoBlockProposal::validate()` derives the sortition handle it uses for all canonicity checks (`sort_tip`) from the attacker-controlled `burn_view_consensus_hash` embedded in a `TenureChange`-Extend transaction, rather than from the sortition DB's actual canonical burnchain tip. Because `SortitionDB::get_block_snapshot_consensus` and the downstream `has_consensus_hash`/ancestor checks operate on whatever fork the supplied consensus hash resolves to — not the fork containing the node's true current sortition tip — a reorg that orphans that sortition after it was recorded still lets the proposal pass validation.

### Finding Description
In `validate()` [1](#0-0) , the burn view used for the rest of validation is computed via `NakamotoChainState::get_block_burn_view`, which for a tenure-change block simply returns `tenure_change.burn_view_consensus_hash` taken directly from the block/tx the miner crafted [2](#0-1) . The only sanity check performed here is that this claimed burn view is a *descendant* of the parent block's own burn view within the fork rooted at that claimed consensus hash — a purely graph-local, ancestor/descendant check, not a check against the sortition DB's actual canonical tip.

`sort_tip` is then obtained with `SortitionDB::get_block_snapshot_consensus(sortdb.conn(), &burn_view_consensus_hash)`, which is a plain lookup by consensus hash in the `snapshots` table and returns a snapshot regardless of whether that sortition is still on the canonical fork [1](#0-0) . A `db_handle`/`burn_dbconn` is opened rooted at `sort_tip.sortition_id`, and `check_block_has_valid_tenure` then calls `db_handle.has_consensus_hash(tenure_id)` [3](#0-2) .

`has_consensus_hash` itself only checks that `tenure_id`'s sortition is an ancestor of `self.context.chain_tip` (i.e. of `sort_tip.sortition_id`) — it never compares `sort_tip` against `SortitionDB::get_canonical_burn_chain_tip` [4](#0-3) . This contrasts with the pattern used elsewhere in the codebase for real consensus-critical tenure validation, e.g. `validate_nakamoto_tenure_snapshot`, which explicitly fetches `SortitionDB::get_canonical_burn_chain_tip(db_handle)` first and then checks that the tenure's snapshot is an ancestor of *that* tip before accepting it as canonical [5](#0-4) , and `check_valid_consensus_hash` which checks ancestry against the handle's own canonical fork position [6](#0-5) . Neither of these true canonicity patterns is applied to `sort_tip` itself in `postblock_proposal.rs::validate()`.

Exploit flow: a burnchain reorg occurs so that a previously-recorded sortition S (with consensus hash CH) is displaced from the canonical fork by a competing sortition S' at the same height. CH's snapshot row still exists in the `snapshots` table (sortitions are never deleted). A miner crafts a block with a `TenureChange` whose `cause` is `Extended` and whose `burn_view_consensus_hash = CH` (the orphaned sortition). `get_block_burn_view` accepts it because it still descends from the block's parent's burn view (that ancestry relationship predates the reorg and is unaffected by it). `validate()` then opens `sort_tip` = S (the orphaned snapshot) and all further canonicity checks (`check_block_has_valid_tenure`, `get_expected_burns`, `validate_normal_nakamoto_block_burnchain`) are evaluated against the orphaned fork rooted at S, not the node's actual canonical tip. The proposal is accepted with `BlockValidateOk`, and the signer signs a tenure-extend block anchored to a dead/orphaned burn view.

### Impact Explanation
This breaks the CANONICITY safety property: the signer's approval should attest that the tenure/burn view is on the sortition DB's actual current canonical fork, but instead it can attest to any historically-recorded (possibly reorged-out) sortition that is graph-consistent with itself. A signature over such a block is a signature over a chain state the network no longer recognizes as canonical, which is exactly the class of Critical finding described (signer signing an invalid/non-canonical block, chain safety violation). This is achievable by a single unprivileged miner-slot holder crafting one `BlockProposal`; it requires no signer collusion, no auth token, and no majority of signers.

### Likelihood Explanation
The precondition is a burnchain reorg occurring between the time a sortition is recorded and when the miner submits the tenure-extend proposal referencing it as the burn view — burnchain reorgs (even shallow ones) are a normal occurrence on Bitcoin-based burnchains, and the miner fully controls the timing and content of the crafted `TenureChangePayload.burn_view_consensus_hash`. The attacker needs only to win one commit slot (to have a legitimate ongoing tenure to extend) and craft/gossip the proposal — no elevated privileges required. This is repeatable on every reorg opportunity.

### Recommendation
In `NakamotoBlockProposal::validate()`, after resolving `sort_tip` from `burn_view_consensus_hash`, explicitly verify canonicity against the sortition DB's actual current tip: fetch `SortitionDB::get_canonical_burn_chain_tip(sortdb.conn())` and confirm that `sort_tip.sortition_id` is an ancestor of (or equal to) that tip's `sortition_id` at `sort_tip.block_height` — mirroring the pattern already used in `validate_nakamoto_tenure_snapshot` / `check_valid_consensus_hash`. Reject with `NonCanonicalTenure`/`NoSuchTenure` if this check fails, before performing any further validation against the (potentially orphaned) `db_handle`.

### Proof of Concept
Rust test plan (stackslib, using `TestPeer`/mock burnchain reorg harness similar to existing coordinator tests):
1. Advance the burnchain and mine a tenure; record its consensus hash `CH` via `SortitionDB::get_block_snapshot_consensus`. Confirm `CH` is canonical: `sortdb.index_handle_at_tip().has_consensus_hash(&CH) == Ok(true)`.
2. Force a burnchain reorg (as done in existing PoX/reorg fork-choice tests) so a competing sortition at the same height becomes canonical, orphaning `CH`. Confirm `SortitionDB::get_canonical_burn_chain_tip` no longer resolves to `CH`'s fork, while `SortitionDB::get_block_snapshot_consensus(_, &CH)` still returns the old (now non-canonical) snapshot.
3. Build a `NakamotoBlock` with a `TenureChange` transaction of `cause = TenureChangeCause::Extended` and `burn_view_consensus_hash = CH`, referencing the still-ongoing tenure and a valid parent block.
4. Call `NakamotoBlockProposal::validate(...)` on this block against the reorged `sortdb`.
5. Assert the current (vulnerable) behavior returns `Ok(BlockValidateOk)` rather than `Err(BlockValidateRejectReason { reason_code: ValidateRejectCode::NonCanonicalTenure | NoSuchTenure, .. })`, demonstrating the signer would sign a block anchored to the orphaned burn view `CH`. After applying the recommended fix (comparing `sort_tip` against `get_canonical_burn_chain_tip`), assert the call instead returns `Err(..NonCanonicalTenure..)`.

    /// Is a consensus hash's sortition valid on the fork represented by this handle?
    /// Return Ok(true) if so
    /// Return Ok(false) if not (including if there is no sortition with this consensus hash)
    /// Return Err(..) on DB error
    pub fn has_consensus_hash(&self, consensus_hash: &ConsensusHash) -> Result<bool, db_error> {
        let Some(sn) = SortitionDB::get_block_snapshot_consensus(self, consensus_hash)? else {
            // no sortition with this consensus hash
            return Ok(false);
        };

        let Some(expected_sortition_id) =
            get_ancestor_sort_id(self, sn.block_height, &self.context.chain_tip)?
        else {
            // no ancestor at this sortition height relative to this chain tip
            // (e.g. perhaps this consensus hash is in the "future" relative to this chain tip)
            return Ok(false);
        };

        Ok(sn.sortition_id == expected_sortition_id)
    }

    pub(crate) fn check_valid_consensus_hash<SH: SortitionHandle>(
        sort_handle: &mut SH,
        ch: &ConsensusHash,
    ) -> Result<Option<BlockSnapshot>, ChainstateError> {
        // the target sortition must exist, and it must be on the canonical fork
        let Some(sn) = SortitionDB::get_block_snapshot_consensus(sort_handle.sqlite(), ch)? else {
            // no sortition
            warn!("Invalid consensus hash: no such snapshot"; "consensus_hash" => %ch);
            return Ok(None);
        };
        let Some(ancestor_sn) = sort_handle.get_block_snapshot_by_height(sn.block_height)? else {
            // not canonical
            warn!("Invalid consensus hash: snapshot is not canonical"; "consensus_hash" => %ch);
            return Ok(None);
        };
        if ancestor_sn.sortition_id != sn.sortition_id {
            // not canonical
            return Ok(None);
        }
        Ok(Some(sn))
    }
