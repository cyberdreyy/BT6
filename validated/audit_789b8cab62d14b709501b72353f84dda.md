### Title
Unbounded per-notification CPU cost from `programSubscribe` jsonParsed re-parsing of large accounts on every commitment update - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
`RpcSubscriptions::notify_watchers` re-encodes every matching program account on each bank/gossip commitment notification, and for `jsonParsed` encoding this calls `parse_account_data_v3`/`encode_ui_account`, whose cost scales with the account's raw data size (up to `MAX_PERMITTED_DATA_LENGTH`, 10MiB). An attacker can own a program, create one maximal-size account under it, subscribe once via `programSubscribe`, and cause a full parse+serialize of that account on every subsequent commitment-driven notification triggered by the attacker's own low-rate writes, with no per-subscription byte/CPU budget enforced anywhere in this path.

### Finding Description
The subscribe path validates only filters and encoding type, not account size or a cost budget: `rpc_pubsub.rs` `program_subscribe` builds a `ProgramSubscriptionParams` from client-supplied `encoding` (which may be `UiAccountEncoding::JsonParsed`) with no cap on the target program's account sizes [1](#0-0) .

Every time a `NotificationEntry::Bank` or `NotificationEntry::Gossip` event fires (driven by ordinary slot/commitment progression, which the attacker can trigger by submitting a low-rate write to their own account), `process_notifications` calls `RpcSubscriptions::notify_watchers` [2](#0-1) . For `SubscriptionParams::Program`, this calls `bank.get_program_accounts_modified_since_parent` then `filter_program_results` via `check_commitment_and_notify`, with no size or cost check on the returned accounts [3](#0-2) .

`filter_program_results` unconditionally calls `encode_ui_account(&pubkey, &account, encoding, None, None)` for each matched account [4](#0-3) . When `encoding == UiAccountEncoding::JsonParsed`, `encode_ui_account` calls `parse_account_data_v3(pubkey, account.owner(), account.data(), additional_data)`, which runs a full deserialization/serialization of the account's raw byte buffer proportional to `data.len()` [5](#0-4) [6](#0-5) .

No guard in this chain bounds the cost by account size: `SubscriptionControl::subscribe` only enforces a count-based cap (`max_active_subscriptions`, default 1,000,000) and a subscriber-slot guard, not a byte/CPU budget [7](#0-6) . The `queue_capacity_bytes` config only limits the notification *delivery* queue after the (expensive) encode has already run, so it cannot prevent the CPU cost [8](#0-7) . Accounts owned by an attacker-created program are not on the SPL-token fast/known-owner path, so they always take the `encode_ui_account` branch (not `get_parsed_token_accounts`), guaranteeing the `parse_account_data_v3` cost path is hit for a custom program `PARSABLE_PROGRAM_IDS` lookup miss — falling back to base64 re-encoding of the full slice, still proportional to account size [9](#0-8) .

Because `notify_watchers` iterates subscriptions in parallel via `subscriptions.into_par_iter()` [10](#0-9) , the cost is incurred once per commitment update (bank/gossip), which fires roughly once per slot — i.e., at the cluster's slot cadence — independent of how many further RPC calls the attacker issues. The attacker only needs a single `programSubscribe` call and periodic low-rate writes (≤ 1 per `CLUSTER_SLOT_TIME_TARGET/2`) to their own account to keep triggering full-size parsing on each subsequent commitment notification.

### Impact Explanation
This is an unbounded-cost issue for a single low-rate client interaction: one `programSubscribe` subscription with `jsonParsed` encoding on a program owning a single maximal-size account causes the validator's RPC-pubsub notification thread(s) to repeatedly perform O(account size) parsing/serialization work, scaling with the number of commitment-triggering slots. Because `process_notifications` runs the parallel `notify_watchers` synchronously per notification in the pubsub thread pool, sustained large-account subscriptions can consume disproportionate CPU relative to the single request/subscription that established them, degrading RPC/pubsub responsiveness for other clients on the same node. This matches the "unbounded cost for a single low-rate call" RPC-availability impact category.

### Likelihood Explanation
Feasible with unprivileged access only: any client can deploy/own a program (or reuse an existing unprivileged-owned account) and store up to `MAX_PERMITTED_DATA_LENGTH` (10MiB) of data in it, then issue one `programSubscribe` with `encoding: "jsonParsed"`. Every subsequent slot-driven commitment update that touches the account (from the attacker's own low-rate account writes) re-triggers the full encode. No commitment, filter, or quota check blocks this because subscription admission only checks subscription *count*, not account size or the presence of `jsonParsed` on a large-data owner set.

### Recommendation
Enforce a per-subscription cost/byte budget in `notify_watchers`/`filter_program_results` and `check_commitment_and_notify`, e.g., skip or downgrade `jsonParsed` parsing for accounts above a configurable data-size threshold (falling back to `Base64`/`Base64Zstd` without invoking `parse_account_data_v3`), or rate-limit/coalesce re-encoding work per subscription per unit time independent of commitment cadence.

### Proof of Concept
Add an integration test in `rpc/src/rpc_subscriptions.rs` tests module modeled on the existing `test_program_subscribe_*` tests:
1. Create a genesis/bank, deploy a custom `program_id` (unprivileged, attacker-controlled).
2. Create one account owned by `program_id` with `data.len() == MAX_PERMITTED_DATA_LENGTH` (10 MiB) filled with non-parsable garbage bytes.
3. Subscribe via `program_subscribe(program_id, RpcProgramAccountsConfig { account_config: RpcAccountInfoConfig { encoding: Some(UiAccountEncoding::JsonParsed), .. }, .. })`.
4. In a loop of N iterations, mutate one byte of the account (simulating the attacker's own low-rate write, ≤ 1 per `CLUSTER_SLOT_TIME_TARGET/2`) and call `subscriptions.notify_subscribers(CommitmentSlots { slot: i, .. })`.
5. Wrap the loop with `Measure::start`/`elapsed()` (or `std::time::Instant`) around the `notify_subscribers` calls and assert that total CPU time scales approximately linearly with `N * data.len()`, confirming no cap/short-circuit exists (e.g., assert elapsed time exceeds a threshold proportional to `N * 10MiB / expected_throughput`).
6. Compare against a control run using `UiAccountEncoding::Base58`/`Binary` (which skips `parse_account_data_v3`) to show the `JsonParsed` path is measurably and unboundedly more expensive with no cap in between.

pub fn parse_account_data_v3(
    pubkey: &Pubkey,
    program_id: &Pubkey,
    data: &[u8],
    additional_data: Option<AccountAdditionalDataV3>,
) -> Result<ParsedAccount, ParseAccountError> {
    let program_name = PARSABLE_PROGRAM_IDS
        .get(program_id)
        .ok_or(ParseAccountError::ProgramNotParsable)?;
    let additional_data = additional_data.unwrap_or_default();
    let parsed_json = match program_name {
        ParsableAccount::AddressLookupTable => {
            serde_json::to_value(parse_address_lookup_table(data)?)?
        }
        ParsableAccount::BpfUpgradeableLoader => {
            serde_json::to_value(parse_bpf_upgradeable_loader(data)?)?
        }
        ParsableAccount::Config => serde_json::to_value(parse_config(data, pubkey)?)?,
        ParsableAccount::Nonce => serde_json::to_value(parse_nonce(data)?)?,
        ParsableAccount::SplToken | ParsableAccount::SplToken2022 => serde_json::to_value(
            parse_token_v3(data, additional_data.spl_token_additional_data.as_ref())?,
        )?,
        ParsableAccount::Stake => serde_json::to_value(parse_stake(data)?)?,
        ParsableAccount::Sysvar => serde_json::to_value(parse_sysvar(data, pubkey)?)?,
        ParsableAccount::Vote => serde_json::to_value(parse_vote(data, pubkey)?)?,
    };
    Ok(ParsedAccount {
        program: format!("{program_name:?}").to_kebab_case(),
        parsed: parsed_json,
        space: data.len() as u64,
    })
}
