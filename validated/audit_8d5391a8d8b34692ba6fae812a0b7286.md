### Title
Unprotected, front-runnable `init_global_fee_state` allows permanent takeover of the protocol's global fee admin and fee wallet - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
`init_global_fee_state` creates the program-wide, singleton `FeeState` PDA (seeds `[FEE_STATE_SEED]`) and writes attacker-supplied `admin_key`/`fee_wallet` arguments into it, with no constraint on who may call it beyond "any signer paying rent." Because the PDA is created via Anchor's `init` constraint, it can only ever be initialized once; whoever's transaction lands first permanently owns `global_fee_admin` and `global_fee_wallet`. This is the same bug class as the Rocket Pool report: an unprotected initialization path during deployment that a non-privileged attacker can race to seize control of critical global state before the legitimate deployer's transaction confirms.

### Finding Description
The instruction handler blindly trusts caller-supplied values for the two most security-critical fields of `FeeState`: [1](#0-0) 

and the account context enforces no authorization beyond being a fee-paying signer: [2](#0-1) 

There is no `has_one`, hardcoded pubkey `constraint`, or any other gate restricting `payer` to a designated deployer/multisig — any account can call `init_global_fee_state(ctx, admin_key, fee_wallet, ...)` with itself as `admin_key` and any wallet as `fee_wallet`. Because `fee_state` uses `init` with fixed seeds `[FEE_STATE_SEED.as_bytes()]` (a program-wide singleton, not scoped to a specific group or admin), the account can be created exactly once. Whichever transaction is confirmed first "wins" the PDA and its `global_fee_admin`/`global_fee_wallet` fields forever, since every later call to the same instruction will fail (`init` fails if the account already exists), and all subsequent authority over the account (`edit_global_fee_state`) is gated by `has_one = global_fee_admin`: [3](#0-2) 

meaning once an attacker sets themselves as `global_fee_admin`, only they can ever change it again.

This directly parallels the Rocket Pool finding: an "init once" storage/PDA that lacks the equivalent of the `RocketStorage.initialised` guard requiring the caller to be a registered network contract or the guardian's `tx.origin`. Just as an attacker could set `rocketVault` to a malicious address before deployment finished, here an attacker can set `global_fee_wallet` to an address they control before the legitimate deployer's `init_global_fee_state` transaction lands.

Every group's `FeeState.global_fee_wallet`/fee parameters are seeded into the group at `marginfi_group_initialize` time via the cache: [4](#0-3) 

and used at fee-collection time (`lending_pool_add_bank`/`add_bank_with_seed` validate `fee_state.global_fee_wallet` via `has_one`): [5](#0-4) 

so an attacker-controlled `global_fee_wallet` would redirect all bank-init fees, liquidation fees, order fees, and program fees for the entire deployment to the attacker, and an attacker-controlled `global_fee_admin` would let them subsequently reconfigure any fee parameter (`edit_global_fee_state`) at will.

### Impact Explanation
If exploited, an attacker permanently becomes the program-wide `global_fee_admin` and redirects `global_fee_wallet` to an address they control. This diverts protocol-wide fee revenue (bank-init fees, liquidation fees, order-execution fees, and the program fee rate/fixed fee applied across every group and bank in the deployment) to the attacker indefinitely, since the singleton PDA cannot be re-initialized and only the current `global_fee_admin` can change it thereafter. This is a durable, protocol-wide value-redirection and authorization-bypass with direct financial effect, not merely a griefing/DoS outcome.

### Likelihood Explanation
Exploitation requires only submitting a single permissionless transaction calling `init_global_fee_state` before the legitimate deployer does — no privileged role, staked collateral, or oracle manipulation is needed. As in the Rocket Pool case, this is a race that a mempool-watching or block-monitoring attacker could win, especially if the FeeState PDA address (deterministic from the fixed seed `"feestate"` and the known program ID) is derivable and monitorable ahead of the deployer's initialization transaction landing on-chain. The main practical mitigant is that this bug only matters during initial mainnet bootstrapping of the singleton account (a narrow window), similar to how the Rocket Pool bug only mattered during the ~223-transaction deployment sequence — but the underlying code has no on-chain protection against it.

### Recommendation
Add an authorization check to `InitFeeState`/`init_global_fee_state`, analogous to the Rocket Pool fix (`onlyLatestRocketNetworkContract` requiring registration or guardian `tx.origin`): require `payer` to match a hardcoded upgrade authority/program-derived deployer key, or require the call to originate from the program's upgrade authority account (checked via the `BPFLoaderUpgradeable` program's `ProgramData` account), before allowing `FeeState` initialization. Alternatively, bundle `init_global_fee_state` into the same atomic transaction as the program's initial deployment/upgrade so no window exists for a competing transaction to land first.

### Proof of Concept
1. Attacker monitors the chain (or mempool) for the marginfi program's deployment and knows the deterministic `FeeState` PDA address (`find_program_address(["feestate"], marginfi::ID)`).
2. Before the legitimate deployer's `init_global_fee_state` transaction confirms, attacker submits their own transaction calling `init_global_fee_state(ctx, attacker_admin_key, attacker_wallet, ...)` using `InitFeeState { payer: attacker, fee_state: <PDA>, system_program }`.
3. Anchor's `init` constraint successfully creates the singleton `FeeState` account with `global_fee_admin = attacker_admin_key` and `global_fee_wallet = attacker_wallet`, per [6](#0-5) .
4. The legitimate deployer's subsequent `init_global_fee_state` transaction fails (account already initialized).
5. All future groups created via `marginfi_group_initialize` cache the attacker's fee wallet, and all fee-charging instructions (`lending_pool_add_bank`, liquidations, order execution) route fees to the attacker's wallet; only the attacker (as `global_fee_admin`) can subsequently call `edit_global_fee_state` to change these values, per [3](#0-2) .

pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
