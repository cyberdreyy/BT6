This confirms the architecture makes the described attack path infeasible.

The `SnapshotStorageRebuilder::rebuild_storages` function [1](#0-0) . This map is purely a private local data structure (`self.storage`) with no visibility to any other thread or subsystem until the function returns.

Critically, the `AccountsDb` instance that RPC reads from does not exist yet while rebuilding is happening. The call chain is: `rebuild_storages_from_snapshot_dir` (or `unarchive_snapshot`) returns a completed `AccountStorageMap` [2](#0-1) , and then `reconstruct_accountsdb_from_fields` constructs a brand-new `AccountsDb` and calls `accounts_db.storage.initialize(storage)` with the *complete, final* storage map in one atomic step [3](#0-2) . Only after this entire pipeline (rebuild → index generation) completes does `reconstruct_bank_from_fields` produce the `Bank` object [4](#0-3) .

That `Bank` is loaded by `load_blockstore` on a dedicated thread that runs *before* the RPC server is ever started, joined synchronously via `load_snapshot_handle.join()` [5](#0-4) . The JSON-RPC service is only started later in validator startup after `bank_forks` exists and is passed in fully formed [6](#0-5) .

There is no code path where an `AccountsDb`/`Bank` with a "partially rebuilt" storage set is ever installed into `bank_forks` or reachable by the RPC layer — `rebuild_storages` is a synchronous, single-threaded, pre-publication step whose only externally visible side effect is periodic `log_progress()` info-log output (not any data structure RPC reads). There is also no "fallback/default AccountSharedData" behavior implied by this rebuild step; that would be a separate question about `get_account_info`'s handling of missing keys, unrelated to `processed_slot_count`/`num_collisions` bookkeeping.

The premise that a slow `rebuild_storages` call leaves accounts_db "partially registered" and observable to RPC is not supported by the code — the RPC server and `bank_forks` simply do not exist yet during this phase, so no single racing `getAccountInfo` call can observe an intermediate state.
