### Title
Stale rejection weight is never retracted when a signer flips its vote, breaking the aggregated-weight-vs-verified-accepts equality in the miner's `StackerDBListener` - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` tallies `BlockStatus.total_weight_approved` and `BlockStatus.total_weight_rejected` independently, each de-duplicated only against its own bucket (`gathered_signatures` for approvals, `responded_signers` for rejections). Nothing removes a signer's weight from `total_weight_rejected` when that same signer later reconsiders and accepts the block, so the two totals are not mutually exclusive per signer, mirroring the reported class of bug: an aggregate counter (`_totalAuctionTokenAllocation` in the report) that is bumped on one path but never decremented on the corresponding reversal, leaving the tracked total permanently out of sync with ground truth.

### Finding Description
`BlockStatus` keeps two independently-accumulated weight totals: [1](#0-0) 

On `BlockResponse::Accepted`, weight is added only if the slot is not already present in `gathered_signatures`: [2](#0-1) 

On `BlockResponse::Rejected`, weight is added only if the slot is not already present in `responded_signers`: [3](#0-2) 

These are two different sets. A signer that first rejects a block (weight added to `total_weight_rejected`, slot inserted into `responded_signers`) and later reconsiders and accepts the *same* block hash will pass the accept-side dedup check (`!block.gathered_signatures.contains_key(&slot_id)` is still true, because that check is against `gathered_signatures`, not `responded_signers`), so the same signer's weight is *also* added to `total_weight_approved` — with no corresponding subtraction from `total_weight_rejected`. The reject-then-accept path is a legitimate, non-malicious signer behavior: the signer-side flow explicitly allows reconsidering a prior rejection once "the reject reason allows us to reconsider" and a new proposal for the same block arrives, while an accept can never later be overwritten by a reject for the same signer/block (an already-signed block's `signed_self` guard blocks that direction). This asymmetry means only the reject→accept direction is reachable, and it always leaves `total_weight_rejected` permanently containing stale weight that no longer reflects that signer's current vote — exactly the "accounting not updated on reversal" pattern from the report, applied to `total_weight_rejected` instead of `_totalAuctionTokenAllocation`.

Contrast this with the signer-side dedup fix noted in the changelog ("Do not count both a block acceptance and a block rejection for the same signer/block"), which was applied to the signer's own SQL-backed vote store (`add_block_signature`/`add_block_rejection_signer_addr` in `signerdb.rs`) but was not mirrored in this independent, in-memory coordinator implementation.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality explicitly called out as an in-scope safety-relevant analog: `total_weight_approved + total_weight_rejected` can legitimately exceed the actual current set of distinct signer opinions, since a signer's weight can be counted in both buckets simultaneously. The miner's decision logic evaluates: [4](#0-3) 
using `total_weight_rejected` inflated with weight from signers who have already flipped to acceptance. This can make the "rejection makes 70% approval impossible" condition fire earlier or differently than the true, current signer-opinion state warrants, i.e., the coordinator's rejection accounting diverges from the actual, live set of accepting/rejecting signers it claims to represent.

### Likelihood Explanation
The triggering condition (a signer initially rejecting a block for a re-evaluable reason and later accepting a re-proposal of the exact same block) is a documented, ordinary part of the signer protocol's re-proposal handling, not an attack requiring a majority of signers, key compromise, or auth-token access — it only needs a single signer (plus the normal gossip/re-proposal flow) to exhibit this legitimate reconsideration behavior once. No malicious majority is required.

### Recommendation
Track a signer's current vote as a single piece of state per `(block_hash, slot_id)` (e.g., an enum `Accepted`/`Rejected` keyed by slot, rather than two independently-accumulated sets), and when a slot's response changes from rejected to accepted (or vice versa, if ever allowed), subtract the previous weight contribution from its old bucket before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` remain mutually exclusive per signer and their sum never exceeds `total_weight`.

### Proof of Concept
Conceptual sequence (based on the code paths cited above, not independently executed):
1. Signer S (weight w) sends `BlockResponse::Rejected` for block B with a re-evaluable reject reason. `StackerDBListener` records: `responded_signers.insert(slot_S)`, `total_weight_rejected += w`.
2. The miner re-proposes the same block B (or S's local state re-evaluates and decides to sign it) — per the signer-side documented behavior, S is permitted to reconsider a re-evaluable rejection on a fresh proposal and sends `BlockResponse::Accepted` for the same `signer_signature_hash`.
3. In the `Accepted` handler, `block.gathered_signatures.contains_key(&slot_S)` is `false` (that map was never touched by the rejection path), so `total_weight_approved += w` is applied.
4. Result: `total_weight_rejected` still includes `w` from S even though S's current, final vote is acceptance — `total_weight_approved + total_weight_rejected` now double-counts S's weight, and the "impossible to reach 70%" rejection-threshold check at lines 567–574 operates on a `total_weight_rejected` value that no longer reflects S's live opinion.
