### Title
Re-requesting a withdrawal after a loss epoch makes `lastWithdrawRequest` skip the haircut epoch, so the loss-adjusted receipt is later paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a loop/index defect in GnuPG's `armor_filter`: the index is incremented twice where once is intended, so one position is skipped and the write lands out of bounds. The analog in `IdleCreditVault` is the single-slot epoch index `lastWithdrawRequest[_user]`. A user can have withdraw receipts in multiple epochs, but `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch` only at `lastWithdrawRequest[_user]` — the *latest* request epoch. When the user files a new `requestWithdraw` in a later epoch, the index is advanced past the loss epoch ("incremented once too far"), so the loss-epoch receipt is never cleared through the haircut path and is instead paid at par by `_claimFundedWithdrawRequest`.

### Finding Description
1. In `requestWithdraw`, every request overwrites `lastWithdrawRequest[_user] = currentEpoch` and adds the amount to both `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` (`IdleCreditVault.sol:282-293`). Nothing prevents a second request while an older, still-unclaimed receipt exists; the code comments even acknowledge this ("he will have to wait for another epoch to claim both requests").
2. When an epoch is stopped with `stopEpochWithDuration(_lossAmount)`, the borrower funds only the loss-adjusted amount, `pendingWithdraws` is cleared, and `lossRecoveryPriceByEpoch[epoch]` records the haircut. Receipts for that epoch are supposed to be claimed via `_claimLossAdjustedWithdrawRequest`, which pays `claimBasis * lossRecoveryPrice / RECOVERY_FULL` (`IdleCreditVault.sol:789-801`).
3. That path derives the epoch solely from `lastWithdrawRequest[_user]` (`IdleCreditVault.sol:790`). If the user requested again in epoch `lossEpoch + 1`, `lossRecoveryPriceByEpoch[lossEpoch + 1]` is 0, the function returns early, and the loss-epoch receipt in `withdrawsRequestsByEpoch[_user][lossEpoch]` / `withdrawsRequests[_user]` is never haircutted.
4. `claimWithdrawRequest` then falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` in full at par via `_transferFundedClaim` once `epochNumber > lastWithdrawRequest[_user]` (`IdleCreditVault.sol:319-349`).

The broken invariant is the loss waterfall: a stopEpoch-with-loss haircut must apply to every receipt of that epoch, but the single-index lookup skips older epochs exactly like the double-incremented index skips a position.

### Impact Explanation
Direct fund loss / insolvency. The strategy only received the loss-adjusted funding for the loss epoch; the attacker extracts the pre-haircut amount, overpaying themselves by `claimBasis * (1 - lossRecoveryPrice) / RECOVERY_FULL`. Since strategy underlyings are shared, the excess comes out of other claimants' funded receipts or default-recovery reserve accounting, leaving the vault short for later withdrawers. With e.g. a 50% `lossRecoveryPrice`, a user holding a 100k receipt in the loss epoch pockets ~50k underlyings that were never funded.

### Likelihood Explanation
The attacker needs only to be a tranche-token holder (unprivileged): request a withdraw in the epoch that ends with `stopEpochWithDuration(_lossAmount)`, then make a dust-sized second `requestWithdraw` in the following epoch, wait one epoch boundary, and call `claimWithdrawRequest`. No privileged actor involvement, no reentrancy, no oracle manipulation. The only precondition is a loss-adjusted `stopEpochWithDuration`, which is a designed vault mode, not an exceptional state. The single-epoch `lastWithdrawRequest` bookkeeping does not iterate `withdrawsRequestsByEpoch`, so multi-epoch receipts are mishandled by construction.

### Recommendation
Track loss-adjusted epochs per receipt rather than per user: e.g., store a per-epoch flag/queue of unclaimed loss epochs for each user, or iterate `withdrawsRequestsByEpoch[_user][*]` entries that have a nonzero `lossRecoveryPriceByEpoch` before paying the funded claim at par. At minimum, in `_claimFundedWithdrawRequest`, exclude any per-epoch amounts whose `lossRecoveryPriceByEpoch[epoch] != 0` (pay them with the haircut instead), so the haircut cannot be skipped by advancing `lastWithdrawRequest`.

### Proof of Concept
Foundry fork PoC sketch (modeled on `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. Setup credit vault + CDO epoch variant, whitelist attacker.
// 2. Attacker deposits, manager startEpoch() -> epoch N running.
// 3. Attacker requestWithdraw(fullBalance).
// 4. Manager calls stopEpochWithDuration(duration, lossAmount) with
//    lossRecoveryPriceByEpoch[N] == 0.5e18; borrower funds reduced amount.
// 5. New epoch N+1: attacker deposits dust (or keeps residual tranche tokens)
//    and requestWithdraw(1 wei) -> lastWithdrawRequest[attacker] = N+1.
// 6. Epoch N+1 ends normally; epochNumber > lastWithdrawRequest.
// 7. Attacker calls cdoEpoch.claimWithdrawRequest():
//    - _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[N+1]==0 -> returns 0
//    - _claimFundedWithdrawRequest: pays withdrawsRequests[attacker] (includes
//      the full epoch-N receipt) at par.
// 8. assert attacker received > funded loss-adjusted amount; assert vault
//    underlying balance is insufficient for remaining receipts.
```

Key asserted invariant violation: `userReceipt * lossRecoveryPriceByEpoch[N] / RECOVERY_FULL` is the maximum the vault funded for that receipt, yet the payout equals `userReceipt`.
