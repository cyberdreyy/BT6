### Title
Post-default withdraw claims drain `defaultRecoveryReserve` without any replenishment, freezing or stealing defaulted claimants' recovery - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`CVE-2025-24150` is an improper-input-handling bug: attacker-controlled data reaches a trusted sink and is consumed as if it were legitimate. The credit-vault analog is the post-default request path in `requestWithdraw` / `_claimPostDefaultWithdrawRequest`: after `defaultRecoveryFinalized`, a new withdraw request mints the user a receipt and the claim is paid 1:1 out of `defaultRecoveryReserve` — a pool that was sized at finalization to cover only pre-existing defaulted claims and is never topped up by the post-default deposit. Every post-default claim silently consumes reserve earmarked for defaulted-epoch claimants, and once cumulative post-default claims exceed the initial reserve, `defaultRecoveryReserve -= _amount` underflows, permanently freezing all remaining defaulted recovery claims.

### Finding Description
In `IdleCreditVault.sol`, `finalizeDefaultRecovery` sets `defaultRecoveryReserve = reserveAmount`, where `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve`, sized to back `totalBasis * recoveryPrice` worth of defaulted claims (lines 686–692).

After finalization, `requestWithdraw` takes the `defaultRecoveryFinalized` branch (lines 247–257): it burns the CDO's strategy tokens, mints the user a receipt, and records `postDefaultRequests[_user] = _amount`. No underlying is pulled into the strategy in this branch, and nothing increases `defaultRecoveryReserve` — `reserveDefaultRecovery` explicitly reverts once finalized (line 631), and `collectWithdrawFunds` only moves tokens without touching the reserve (lines 411–430).

`claimWithdrawRequest` then routes to `_claimPostDefaultWithdrawRequest` (lines 760–767), which calls `_transferDefaultRecovery(_user, amount)` (line 766). `_transferDefaultRecovery` unconditionally decrements `defaultRecoveryReserve` (line 915) and transfers underlying from the strategy balance.

Two failure modes follow:

1. **Reserve accounting exhaustion → permanent freeze.** Each post-default claim reduces `defaultRecoveryReserve`, but the underlying backing those claims (deposited post-default at the haircut virtualPrice) sits in the contract as plain balance, never credited to the reserve. When cumulative post-default claims exceed the finalized reserve, `defaultRecoveryReserve -= _amount` underflows (Solidity 0.8 checked arithmetic) and reverts. Any defaulted claimant who has not yet claimed — or any later post-default claim — is then permanently bricked: `_transferDefaultRecovery` is the only payout path for defaulted receipts, and there is no owner function that can restore the accounting (the `transferToken` rescue does not fix the underflowed counter).

2. **Order-dependent theft of defaulted recovery.** Before the underflow point is reached, post-default claims are paid at par (1:1) from a reserve priced to pay defaulted claims at `defaultRecoveryPrice < RECOVERY_FULL`. A post-default claimant withdraws freshly deposited funds at 100% while consuming the same reserve units that defaulted claimants (who already absorbed the haircut) rely on — transferring recovered value away from defaulted claimants in proportion to claim ordering.

The broken invariant is recovery-pool isolation: "one unit of `defaultRecoveryReserve` = one unit of defaulted-claim purchasing power." The post-default flow mints new claims against that pool without depositing matching reserve units.

### Impact Explanation
Direct, quantifiable loss: defaulted claimants (any tranche-token holder or lender with a defaulted receipt) lose `sum(postDefaultClaims)` of recovery reserve, up to the entire reserve. Once the reserve counter underflows, all unclaimed defaulted recovery is permanently frozen — a textbook "theft or permanent freezing of unclaimed yield" impact. Loss magnitude equals the aggregate post-default claim volume, capped at `defaultRecoveryReserve`.

### Likelihood Explanation
Requires only that the vault has finalized a default with a non-zero reserve and that post-default deposits/withdraws remain enabled — both are explicitly supported code paths (the post-default branch exists precisely to "preserve request/claim UX after default"). The attacker is an ordinary KYC-passed lender depositing and requesting withdraws in the normal way; no privileged role is needed, and honest privileged calls (deposit, stopEpoch, finalizeDefault) supply the sequencing. Even without malicious intent, ordinary post-default usage corrupts the accounting, making eventual freezing near-certain whenever post-default volume approaches the reserve.

### Recommendation
Track post-default claims against their own backing instead of the recovery reserve. Options:
- In `_claimPostDefaultWithdrawRequest`, route the payout through `_transferFundedClaim` rather than `_transferDefaultRecovery`, since post-default requests are funded by fresh deposits (the reserve guard at line 904 already protects defaulted funds).
- Alternatively, in `requestWithdraw`'s post-default branch, credit `defaultRecoveryReserve` with the underlying the CDO deposits for the request (or add a `_onlyIdleCDO` function that increases the reserve when post-default funds arrive).

### Proof of Concept
Foundry fork PoC sketch (`test/foundry/`):

```solidity
// Setup: running epoch, lender deposits via IdleCDOEpochVariant._deposit,
// borrower draws funds, borrower defaults, finalizeDefault/_handleBorrowerDefault
// runs finalizeDefaultRecovery with reserve = R covering defaulted claims at price p < 1e18.

// 1. Attacker (KYC-passed lender) deposits D underlying post-default at the
//    haircut virtualPrice and calls requestWithdraw via the CDO.
//    postDefaultRequests[attacker] = X (haircut-adjusted, X <= D).
cdo.depositAA(D); // or BB; CDO mints strategy tokens
cdo.requestWithdraw(X); // takes defaultRecoveryFinalized branch

// 2. Attacker claims: paid X at par from defaultRecoveryReserve.
cdo.claimWithdrawRequest();
assertEq(vault.defaultRecoveryReserve(), R - X); // reserve spent with no inflow

// 3. Repeat until cumulative X approaches R. The next defaulted claim
//    (_claimDefaultedWithdrawRequest -> _transferDefaultRecovery) reverts on
//    defaultRecoveryReserve -= amount underflow, even though the strategy
//    balance holds the attacker's deposited funds.
vm.expectRevert(); // arithmetic underflow
cdo.claimWithdrawRequest(); // honest defaulted claimant, frozen forever
```

Assertion of the broken invariant: `defaultRecoveryReserve` must never decrease except when paying defaulted-epoch claims at `defaultRecoveryPrice`; post-default claims violate this with no compensating credit.
