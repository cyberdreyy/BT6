### Title
Instant-withdraw branch in `requestWithdraw` skips all management and performance fees, letting users exit fee-free while the protocol books zero `pendingWithdrawFees` - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`requestWithdraw` computes `_totalWithdrawFees` (upfront management fee for the receipt's time outside live NAV plus net performance fee) only on the queued-withdrawal path. When the APR-delta condition routes the request through `creditVault.requestInstantWithdraw`, the full `_trancheToUnderlyings(_amount)` value is forwarded with no fee subtracted and `pendingWithdrawFees` is never incremented, so the protocol collects nothing on that exit.

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw`, the normal path applies fees before fixing the receipt: [1](#0-0) 

```solidity
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
```

But the instant-withdraw branch above it returns early with the unmodified `_underlyings`: [2](#0-1) 

```solidity
if (_isInstantWithdrawEnabled()) {
  uint256 currentApr = creditVault.unscaledApr();
  if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
    creditVault.requestInstantWithdraw(_underlyings, msg.sender);
    _withdrawOps(_amount, _underlyings, _tranche);
    return _underlyings;
  }
}
```

This mirrors the Dinari bug class exactly: an amount that should include a fee component (`inputValue = recoveredValue + flatFee` missing `percentageFee`) is forwarded without it. Here the "output" to the user is `principal + implicit interest` with zero `totalFees` deducted, and `pendingWithdrawFees` — the counter that `stopEpoch`/`prepareStopEpochWithApr0` later uses to route fees to `feeReceiver` — is not credited: [3](#0-2) 

### Impact Explanation
Every instant withdrawal of size `P` skips `_totalWithdrawFees(P, interest)` — concretely the upfront management fee `_calculateManagementFee(P, _withdrawRequestManagementFeeDuration())` plus the performance fee on projected interest. With `managementFee = 1%` and `fee = 10%`, an instant exit of 1,000,000 USDC denies the protocol ~10,000 USDC of management fee plus the performance fee on the interest. The loss is borne by `feeReceiver`/the protocol and scales linearly with instant-withdraw volume. Note the user's tranche tokens are still burned via `_withdrawOps`, so this is pure fee loss, not share inflation.

### Likelihood Explanation
The trigger requires only that `isInstantWithdrawEnabled` is on and `lastEpochApr > unscaledApr + instantWithdrawAprDelta` — i.e., the borrower/manager lowered the APR for the new epoch, a routine configuration change, not attacker-controlled. Any KYC-passed tranche holder who calls `requestWithdraw` in that window automatically exits fee-free. Caveat: I could not fully trace `IdleCreditVault.requestInstantWithdraw`/`claimInstantWithdrawRequest` in the index within the iteration budget; if the vault charges an equivalent fee internally on the instant path, the finding collapses. The CDO-side evidence (no `_totalWithdrawFees` call, no `pendingWithdrawFees` credit, no `interestForOverUnderPerformance` update) shows the CDO at minimum books no fee for these receipts, which is inconsistent with the explicit fee model exercised in `testRequestWithdrawChargesManagementFeeUpfront` and `testRequestWithdrawChargesPerformanceFeeAfterManagementFee`.

### Recommendation
Apply the same fee haircut in the instant branch before forwarding:

```solidity
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
interestForOverUnderPerformance += diff;
creditVault.requestInstantWithdraw(_underlyings, msg.sender);
_withdrawOps(_amount, principal, _tranche);
return _underlyings;
```
