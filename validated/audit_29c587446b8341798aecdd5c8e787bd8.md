### Title
`delegation_pool::set_beneficiary_for_operator` bypasses the `OPERATOR_BENEFICIARY_CHANGE` governance kill-switch enforced by `staking_contract` - (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
The `OPERATOR_BENEFICIARY_CHANGE` feature flag is meant to be the single governance-controlled switch that allows/disallows operators from redirecting their staking commission to a beneficiary address. `staking_contract::set_beneficiary_for_operator` correctly gates this action behind the flag, but the functionally identical `delegation_pool::set_beneficiary_for_operator` never checks it, so any operator can always change their beneficiary regardless of the flag's on-chain state.

### Finding Description
`staking_contract.move` defines its beneficiary-redirect entry function with an explicit governance gate: [1](#0-0) 

```
public entry fun set_beneficiary_for_operator(
    operator: &signer, new_beneficiary: address
) acquires BeneficiaryForOperator {
    assert!(
        features::operator_beneficiary_change_enabled(),
        std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
    );
    ...
```

The flag is defined once, globally, in `features.move`: [2](#0-1) 

The comparable function in `delegation_pool.move`, which performs the exact same state mutation (redirecting commission payouts for an operator by writing `BeneficiaryForOperator.beneficiary_for_operator`), omits the check entirely: [3](#0-2) 

`delegation_pool.move` does not import or reference the `features` module at all (confirmed via search), so there is no code path in this module that respects the `OPERATOR_BENEFICIARY_CHANGE` flag. This is the same bug class described in the external report: an enable/disable override that is honored in one implementation path but silently skipped in a functionally equivalent sibling path (`BunniHookLogic.beforeSwap` / `BunniQuoter.quoteSwap` both needed the override check; here `staking_contract` and `delegation_pool` both need the `operator_beneficiary_change_enabled` check but only one has it).

### Impact Explanation
If Aptos governance disables `OPERATOR_BENEFICIARY_CHANGE` (e.g., in response to abuse, a bug in beneficiary handling, or a compliance requirement forcing commission to go only to the registered operator address), the intended effect is that no operator anywhere in the network can redirect commission payouts. Operators using `delegation_pool` (which since AIP-26/33 is the primary staking product for third-party delegated stake) can still freely call `set_beneficiary_for_operator` and redirect all future operator commission from every delegator in their pool to an address of their choosing, completely undermining the governance decision. This is a beneficiary-payout corruption that credits the wrong account, matching the "Operator commission, beneficiary payout... corruption that credits the wrong account" impact class, reachable by any unprivileged operator account with no special role required beyond being an operator of a delegation pool they already control legitimately (i.e., they gain a control capability — bypassing a network-wide restriction — that they should not have).

### Likelihood Explanation
Likelihood is Medium: it requires governance to have disabled `OPERATOR_BENEFICIARY_CHANGE` for a reason, at which point every existing/future delegation-pool operator can trivially bypass the restriction with a single permissionless entry-function call. No race condition, timing, or special privilege is needed — the missing check is unconditional.

### Recommendation
Add the same governance gate used in `staking_contract::set_beneficiary_for_operator` to `delegation_pool::set_beneficiary_for_operator`:
```move
assert!(
    features::operator_beneficiary_change_enabled(),
    error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
);
```
and import `aptos_std::features` in `delegation_pool.move`.

### Proof of Concept
1. Aptos governance disables the `OPERATOR_BENEFICIARY_CHANGE` feature flag (index 39) via `features::change_feature_flags`.
2. Attempting `staking_contract::set_beneficiary_for_operator(operator, new_beneficiary)` now aborts with `EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED`, as expected.
3. Any operator who runs a `delegation_pool` (any account that called `initialize_delegation_pool`) calls `delegation_pool::set_beneficiary_for_operator(operator, new_beneficiary)` — this succeeds without any abort, because the function at [4](#0-3)  contains no feature-flag assertion.
4. On the next `synchronize_delegation_pool` call, operator commission is bought into shares for `beneficiary_for_operator(operator)` (the newly-set, ungoverned beneficiary) rather than the operator itself, confirming the redirect takes effect despite the flag being disabled.

```text
    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensure payment to the current beneficiary, one should first call `synchronize_delegation_pool`
    /// before switching the beneficiary. An operator can set one beneficiary for delegation pools, not a separate
    /// one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
    }
```
