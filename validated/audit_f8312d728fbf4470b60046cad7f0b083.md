### Title
Withdrawal receipts are charged upfront management fees even in zero-APR (APR0) epochs where no yield is generated - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` always subtracts `_totalWithdrawFees(principal, interest)` from the user's claim, where the management-fee component is computed independently of the epoch APR. In APR0 mode (or whenever `epochDuration`/scaled APR produces zero interest), `_calcInterestWithdrawRequest` returns `interest == 0`, but `_totalWithdrawFees` still returns the full management fee on principal. That fee is booked into `pendingWithdrawFees` and, at the next `stopEpoch`, is transferred to `feeReceiver`/owner (or minted as shares) regardless of the fact that the pool produced no yield for the user. The user is penalized purely because the operator set/kept a zero APR — the same "fees taken though no rewards were issued" pattern as the external report.

### Finding Description
In `requestWithdraw` (IdleCDOEpochVariant.sol:739-791):

```solidity
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
```

`_calcInterestWithdrawRequest` (lines 856-878) returns `_interest = 0` whenever the effective pool interest is zero — e.g. APR0 deployments where the manager calls `IdleCreditVault.setAprs(0, 0)`, or `epochDuration == 0`. However `_totalWithdrawFees` (lines 900-906) is:

```solidity
uint256 _mgmtFee = _calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration());
return _mgmtFee >= _interest ? _mgmtFee : _interest - _netGainAfterFees(_interest, _mgmtFee);
```

With `_interest == 0`, it returns `_mgmtFee` unconditionally. The withdrawal receipt (`creditVault.requestWithdraw(_underlyings, msg.sender, principal)` at line 788) is therefore minted for `principal - mgmtFee`, and at `stopEpoch` that fee is paid out to `feeReceiver`/owner (lines 439-459) or minted as AA shares, while the user gets back less than deposited and earns nothing.

The invariant broken: fees are a share of generated yield; charging a nonzero management fee against principal when gross yield is zero converts a profit-sharing fee into a principal haircut driven by operator inactivity. There is no refund path — `claimWithdrawRequest` (line 967) pays out the already-haircut receipt amount from the vault, and `pendingWithdrawFees` is unconditionally consumed in `stopEpoch`.

### Impact Explanation
Any KYC-passed lender holding tranche tokens in an APR0-configured vault (APR0 is a supported deployment mode with `setAprs(0,0)`) permanently loses `mgmtFeeRate * duration / 365 days` of principal on every withdrawal request, with the fee accruing to `feeReceiver`/`owner` rather than being burned or redistributed to lenders. Loss is quantified: for a 1% management fee and `epochDuration = 365 days`, a 10,000-asset request loses ~100 assets — matching the repo's own test `testApr0RequestChargesManagementFeeUpfront` which asserts the haircut (`expectedPrincipal = principal - expectedMgmtFee`), showing the charge is real and deterministic.

### Likelihood Explanation
Requires the pool to run (or be configured) with zero epoch APR while `managementFee > 0` — a supported configuration, but one where honest operators would arguably be charging fees with no performance. Existence of an explicit test asserting the behavior lowers likelihood that it survives triage as unintended; likelihood is Low-Medium given the operator is honest and the fee parameters are set to normal values.

### Recommendation
In `_totalWithdrawFees` (or `requestWithdraw`), skip or refund the management fee when the epoch yields no interest for the receipt: e.g. cap `totalFees` to the interest actually credited to the receipt (`min(_mgmtFee, interest + accruedPastInterest)`) or gate the upfront fee on `_getStrategyApr() > 0`. Alternatively, accumulate the fee but refund it at `claimWithdrawRequest` time if the epoch distributed zero interest to that epoch bucket (tracked via `withdrawsRequestsByEpoch` / `lossRecoveryPriceByEpoch`).

### Proof of Concept
Foundry fork sketch against `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
function testApr0WithdrawLosesPrincipalToMgmtFee() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mgmtFeeRate = 1_000; // 1%

    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // APR0: operator sets zero yield
    _setManagementFee(mgmtFeeRate);

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);          // epoch runs, earns 0
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);              // zero interest distributed

    _forceLastEpochAprToZero();

    uint256 trancheReq = IERC20(AAtranche).balanceOf(address(this)) / 2;
    uint256 principal = trancheReq * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;

    uint256 requested = cdoEpoch.requestWithdraw(trancheReq, address(AAtranche));

    // BUG: receipt is haircut even though epoch interest was 0
    uint256 expectedMgmtFee = _calcManagementFee(principal, mgmtFeeRate, cdoEpoch.epochDuration() + cdoEpoch.bufferPeriod());
    assertEq(requested, principal - expectedMgmtFee);       // user loses fee on principal
    assertEq(cdoEpoch.pendingWithdrawFees(), expectedMgmtFee);

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    deal(defaultUnderlying, borrower, pending + expectedMgmtFee);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, expectedMgmtFee); // fund fees only; no user interest

    // feeReceiver collected a management fee despite the pool paying the user zero interest
    assertGt(underlying.balanceOf(TL_MULTISIG), 0);
    cdoEpoch.claimWithdrawRequest();
    // user receives principal - fee: permanent loss caused by operator-configured zero APR
}
```

Uncertainty note: I could not fully verify whether `claimWithdrawRequest` in `IdleCreditVault.sol` applies an additional haircut or a refund path (line-level reads of that file's claim logic were not completed within the iteration budget); the finding rests on the net-of-fee receipt being fixed at `requestWithdraw` time and `pendingWithdrawFees` being consumed at `stopEpoch`, both confirmed in `IdleCDOEpochVariant.sol` and by the repo's own tests (`testApr0RequestChargesManagementFeeUpfront`, `testRequestWithdrawChargesManagementFeeUpfront`), which also means this behavior may already be considered intended by the codebase authors.
