### Title
Unbounded backward tenure-fork walk in `check_parent_tenure_choice`/`get_tenure_forking_info` lets a single miner wedge a signer's event loop - (File: `stacks-signer/src/client/stacks_client.rs`)

### Summary
### Finding Description
A miner does not have to build its tenure off the immediately-prior sortition; `SortitionData::check_parent_tenure_choice` explicitly handles the case where `parent_tenure_id != prior_sortition` (a claimed reorg) by asking the node to enumerate every tenure between the claimed parent and the last sortition: [1](#0-0) 

That enumeration is performed by `StacksClient::get_tenure_forking_info`, which repeatedly calls `get_tenure_forking_info_step` (a `/v3/tenures/fork_info` RPC bounded server-side by `DEPTH_LIMIT` per call) and loops, issuing another round trip each time, until the returned chain of tenures walks all the way back to `chosen_parent`: [2](#0-1) 

The server-side handler (`get_tenures_fork_info.rs`) only bounds a *single* request to `DEPTH_LIMIT` sortitions; it does not stop the *signer* from re-invoking the endpoint indefinitely to keep walking further back: [3](#0-2) 

Because `parent_tenure_id` (`stacks_parent_ch`) is populated straight from the miner's own block-commit (`SortitionData` is built from `SortitionInfo` reported for the winning commit), a single miner fully controls how far back it claims to be reorging: [4](#0-3) 

By winning one sortition and committing a block that names a very old (but still-canonical) tenure as its parent, the miner forces every signer's `handle_block_proposal → check_block_against_state → check_proposal → check_parent_tenure_choice` call to walk the *entire* distance back through chain history in `DEPTH_LIMIT`-sized chunks, each chunk costing a full synchronous HTTP round trip plus sortition-DB reads on the node. This is directly analogous to the reported `projectCost()` bug: the cost of a single request is proportional to unbounded, attacker-influenced accumulated state (chain length) rather than being capped independent of that state.

### Impact Explanation
`process_event` on the v0 signer runs this check synchronously while evaluating a block proposal: [5](#0-4) 

While the multi-round-trip walk is in progress, the signer's single-threaded event loop cannot process other events — new proposals, pre-commits, or block-validation responses for other, valid blocks. A malicious miner can trigger this on demand simply by committing to an old parent tenure, at effectively zero cost to itself (a single block-commit), forcing every signer to burn wall-clock time and node RPC bandwidth on this one proposal. This matches the High-severity criterion: "a signer wedged into never signing valid blocks" for the affected window, since block-proposal timing thresholds (`block_proposal_timeout`, pre-commit freshness windows) are all live during this stall.

### Likelihood Explanation
The attack requires no coordination with other signers or a majority — only that the attacker win a single sortition (a normal, permissionless miner capability) and choose an old `previous_tenure_end`/parent tenure in its block-commit. `check_parent_tenure_choice` already anticipates and validates the "not building off the most recent tenure" case as a first-class, expected code path, meaning this is easily reachable without any error conditions — a rational adversary can maximize the reorg depth to maximize damage.

### Recommendation
Bound the total number of sortitions the signer will walk back in `get_tenure_forking_info` (e.g., cap at `MAX_FORK_DEPTH`, which is already used elsewhere for similar chain-depth bookkeeping), and treat a `parent_tenure_id` further back than that cap as an immediately invalid/rejected proposal rather than paying the cost of walking to it. This mirrors the audited fix pattern of capping/caching the unbounded accumulation instead of always recomputing it fully.

### Proof of Concept
1. A malicious miner wins a sortition.
2. It crafts a block-commit whose parent tenure points to a tenure far in the past (e.g., near genesis or many reward cycles back), which is still canonical on the burnchain.
3. Every signer receives the resulting `BlockProposal`, and `handle_block_proposal` invokes `check_block_against_state` → `check_proposal` → `SortitionData::check_parent_tenure_choice`, which calls `client.get_tenure_forking_info(&self.parent_tenure_id, &self.prior_sortition)`.
4. `get_tenure_forking_info`'s `while` loop repeatedly calls the `/v3/tenures/fork_info` endpoint (each capped at `DEPTH_LIMIT` sortitions server-side) until it reaches `chosen_parent`, requiring `O(chain_depth / DEPTH_LIMIT)` sequential HTTP round trips.
5. During this time, the signer's single event-processing loop is blocked from handling other signer messages/proposals (`stacks-signer/src/v0/signer.rs:577-592`), delaying or missing legitimate block-signing windows for concurrently proposed valid blocks.

Note: I was not able to directly find the numeric value of `DEPTH_LIMIT` or additional caller-side timeouts wrapping this whole walk (e.g., an overall deadline in `handle_block_proposal`) within the indexed portion of the repo, so the exact wall-clock magnitude of the stall could not be fully quantified from the available context; a Devin session with full repository access would be needed to confirm the precise `DEPTH_LIMIT` value and whether any surrounding timeout mitigates the practical severity.

    /// Get information about the tenures between `chosen_parent` and `last_sortition`
    pub fn get_tenure_forking_info(
        &self,
        chosen_parent: &ConsensusHash,
        last_sortition: &ConsensusHash,
    ) -> Result<Vec<TenureForkingInfo>, ClientError> {
        debug!("StacksClient: Getting tenure forking info";
            "chosen_parent" => %chosen_parent,
            "last_sortition" => %last_sortition,
        );
        let mut tenures: VecDeque<TenureForkingInfo> =
            self.get_tenure_forking_info_step(chosen_parent, last_sortition)?;
        if tenures.is_empty() {
            return Ok(vec![]);
        }
        while tenures.back().map(|x| &x.consensus_hash) != Some(chosen_parent) {
            let new_start = tenures.back().ok_or_else(|| {
                ClientError::InvalidResponse(
                    "Should have tenure data in forking info response".into(),
                )
            })?;
            let mut next_results =
                self.get_tenure_forking_info_step(chosen_parent, &new_start.consensus_hash)?;
            if next_results.pop_front().is_none() {
                return Err(ClientError::InvalidResponse(
                    "Could not fetch forking info all the way back to the requested chosen_parent"
                        .into(),
                ));
            }
            if next_results.is_empty() {
                return Err(ClientError::InvalidResponse(
                    "Could not fetch forking info all the way back to the requested chosen_parent"
                        .into(),
                ));
            }
            tenures.extend(next_results);
        }

        Ok(tenures.into_iter().collect())
    }
