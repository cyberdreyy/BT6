### Title
Outgoing webhook credential (`OutgoingToken`) disclosure to unauthorized low-privilege users via `ExternalInitiatorsController.Index` - ([File: core/web/external_initiators_controller.go])

### Summary
`bridges.NewExternalInitiator` generates `OutgoingToken`/`OutgoingSecret` and these are intended to be returned only once at creation time via `presenters.NewExternalInitiatorAuthentication`. However, `presenters.NewExternalInitiatorResource`, used by `ExternalInitiatorsController.Index`, also serializes the stored `OutgoingToken` field, and the `Index` route is reachable by any authenticated user regardless of role, including the lowest-privileged `view` role.

### Finding Description
`bridges.NewExternalInitiator` (`core/bridges/external_initiator.go:38-57`) creates `OutgoingToken` and `OutgoingSecret` as one-time-disclosed webhook credentials, meant to be shown only at creation via `presenters.NewExternalInitiatorAuthentication` [1](#0-0) . These are persisted in the `external_initiators` table (`outgoing_token`, `outgoing_secret` columns) [2](#0-1) .

`ExternalInitiatorsController.Index` loads all `ExternalInitiator` rows via `BridgeORM().ExternalInitiators` (a `SELECT *` returning all fields including `OutgoingToken`) and maps each to `presenters.NewExternalInitiatorResource`, which explicitly copies `OutgoingToken` into the JSON response (`json:"outgoingToken"`) [3](#0-2) [4](#0-3) . This is confirmed by the existing test asserting `externalInitiators[0].OutgoingToken` equals the created value [5](#0-4) .

The route registration for `Index` only wraps the handler in the base authentication middleware, unlike `Create`/`Destroy` which require `auth.RequiresEditRole`: [6](#0-5) . `RequiresEditRole`/`RequiresRunRole` explicitly gate `view`-role users out of edit/run actions [7](#0-6) , but `Index` has no such gate, so any authenticated node user — including one with only `UserRoleView` — can list all external initiators and obtain every `OutgoingToken` ever created, not just their own.

Note: `OutgoingSecret`, `HashedSecret`, and `Salt` are NOT included in `ExternalInitiatorResource`, so only `OutgoingToken` (not the full secret pair) is re-exposed.

### Impact Explanation
This is credential/secret disclosure: the `OutgoingToken` is a persistent bearer credential the Chainlink node attaches to outgoing webhook calls made to an external initiator's configured URL. A low-privileged `view`-role user (who cannot create, edit, or delete jobs/bridges/external initiators) can nonetheless read this token for every external initiator on the node via `GET /v2/external_initiators`, and potentially replay it against the external initiator's webhook receiver to impersonate the node or forge a "callback" to the third-party service, depending on how that service uses the token. This maps to a secret/credential disclosure impact class, scoped to node-operator-managed external initiator integrations, not full node compromise.

### Likelihood Explanation
Preconditions: an operator must have created at least one External Initiator (a supported, common feature) and provisioned a second user account with `view` (or `run`) role — a normal multi-user node setup. No admin/edit privileges are needed by the attacker; any authenticated session or API token with `view` role suffices, and the endpoint is a simple paginated `GET` requiring no special parameters. This is trivially repeatable on any node with more than one user of differing roles.

### Recommendation
Remove `OutgoingToken` (and any other credential fields) from `presenters.ExternalInitiatorResource` used by `Index`/list endpoints, or gate `GET /v2/external_initiators` behind `auth.RequiresEditRole`/`RequiresAdminRole` consistent with the `Create`/`Destroy` routes, since only privileged roles should manage external initiators. Outgoing credentials should only ever be returned once, at creation time, via the dedicated `ExternalInitiatorAuthentication` presenter.

### Proof of Concept
Go handler-level integration test plan (extending `TestExternalInitiatorsController_Index` in `core/web/external_initiators_controller_test.go`):
1. Start app with two users: an `admin` (or `edit`) user who calls `POST /v2/external_initiators` to create an EI and capture the returned `OutgoingToken`.
2. Create a second session/API token for a `view`-role user via `cltest` helpers (`app.NewHTTPClient` with `view` role credentials).
3. As the `view`-role user, call `GET /v2/external_initiators`.
4. Assert HTTP 200 (not 401/403) and that the JSON response body's `externalInitiators[].outgoingToken` field is non-empty and matches the value created in step 1 — demonstrating cross-user, cross-privilege disclosure of the outgoing webhook credential.
5. Additionally assert (regression guard) that `outgoingSecret`, `hashedSecret`, and `salt` never appear in the response body.

func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()

		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
