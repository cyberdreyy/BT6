### Title
Loss haircut is only applied to current-epoch receipts while the loss price is computed over all pending receipts, letting stale (older-epoch) receipts claim at par and drain funded underlyings - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` computes a `lossRecoveryPrice` over the aggregate `pendingWithdraws` (which includes receipts from every epoch), but stores it under `lossRecoveryPriceByEpoch[epochNumber]`. `_claimLossAdjustedWithdrawRequest` only applies that haircut to the receipts recorded under `lastWithdrawRequest[_user]` (the user's latest request epoch). A user holding an unclaimed receipt from an older epoch plus a new receipt in the loss epoch has both amounts counted in the haircut denominator, yet only the latest-epoch portion is haircut; the older portion is then paid at par through `_claimFundedWithdrawRequest`. Total payouts therefore exceed the underlying actually funded, and the shortfall is taken from strategy underlyings owned by other claimants.

### Finding Description
The kernel bug is "handlers read data elements beyond the initialized range" — here the analog is that the loss adjustment is *priced* over a wider basis than the range actually haircut.

- `collectWithdrawFunds` at `IdleCreditVault.sol:411-430`: when `_amount < pendingBasis`, it sets `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` where `pendingBasis` is the global aggregate `pendingWithdraws`, and stores it at `lossRecoveryPriceByEpoch[epochNumber]`.
- `previewLossAdjustedWithdrawFunds` at `IdleCreditVault.sol:440-460` likewise splits `_lossAmount` between active LPs and the *entire* `pendingBasis`.
- `requestWithdraw` at `IdleCreditVault.sol:259-294` explicitly permits a second request while an older receipt is unclaimed: it just overwrites `lastWithdrawRequest[_user] = currentEpoch` and appends to `withdrawsRequestsByEpoch[_user][currentEpoch]`. The revert guard at lines 263-271 only blocks if the *stored* `lastWithdrawRequest` epoch already has a nonzero loss price.
- `_claimLossAdjustedWithdrawRequest` at `IdleCreditVault.sol:789-801` reads `lossEpoch = lastWithdrawRequest[_user]`, clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` via `_clearWithdrawClaimForEpoch` (lines 811-837), which also resets `lastWithdrawRequest[_user] = 0`.
- `_claimFundedWithdrawRequest` at `IdleCreditVault.sol:319-350` then pays the remaining aggregate `withdrawsRequests[_user]` (the older-epoch receipt) at par with `_transferFundedClaim`.

Broken invariant: conservation of funded underlyings. Funding delivered = `pendingBasis * price`. Payouts = `price * (current-epoch basis) + 1.0 * (older-epoch basis)`, exceeding funding by `olderBasis * (1 - price)`.

### Impact Explanation
Direct theft / insolvency with quantified loss. With `P_old` older-epoch pending receipts, `P_new` loss-epoch receipts, and funded fraction `r`: the contract receives `r*(P_old+P_new)` but pays out `r*P_new + P_old`. The attacker with an older-epoch receipt extracts `(1-r)*P_old` more than funded. With r = 0.5 and a large older-epoch receipt, the attacker is made whole at the expense of every other pending claimant and/or the strategy's balance (`_transferFundedClaim` only guards `defaultRecoveryReserve`, not active/pending funds, so the drain succeeds until the balance is exhausted — later claimants' funds are permanently stolen/frozen).

### Likelihood Explanation
Requires a stopEpochWithDuration-style partial loss (`collectWithdrawFunds` with `_amount < pendingBasis`), which is a supported, reachable mode, and an unprivileged lender with receipts spanning two epochs — achievable by simply requesting a withdraw, not claiming, and requesting again in the next epoch (a documented, allowed flow: "if a user does not claim… he will have to wait for another epoch to claim both"). No privileged misbehavior needed; the manager/borrower act honestly and trigger the loss. The guard at `requestWithdraw` does not block this because the loss price is recorded after the second request epoch is set, and no guard re-checks older per-epoch receipts when the haircut is applied.

### Recommendation
When applying a loss haircut, do not compute the price over the aggregate `pendingWithdraws` unless the haircut is applied to the same aggregate set. Either:
- iterate/tag every user's per-epoch receipt basis included in `pendingBasis` (e.g., store a global "pending loss epoch range" and clear each `withdrawsRequestsByEpoch` entry with the price, or reset `lastWithdrawRequest`/aggregate consistently so older receipts are also haircut), or
- split `pendingWithdraws` so `collectWithdrawFunds` prices the loss only against receipts recorded for `epochNumber` (plus APR0 bucket for that epoch), keeping older funded receipts outside the denominator.

### Proof of Concept
Foundry fork test sketch (foundry repo test harness `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. attacker deposits AA, epoch0 starts and stops normally.
_depositWithUser(attacker, amountOld, true);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

// 2. attacker requests withdraw in epoch1, does NOT claim.
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche)); // request epoch = epochNumber N

// 3. next epoch starts; attacker requests AGAIN (allowed, overwrites lastWithdrawRequest).
_startEpochAndCheckPrices(1);
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche));

// pendingWithdraws now includes amountOld + amountNew.

// 4. epoch ends with a partial loss: borrower funds less than pendingBasis.
//    collectWithdrawFunds stores lossRecoveryPriceByEpoch[epochNumber].
deal(defaultUnderlying, borrower, partialFunding);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, lossAmount); // triggers collectWithdrawFunds(partial)

// 5. attacker claims: loss-adjusted on latest-epoch receipt, then PAR on the old receipt.
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 got = underlying.balanceOf(attacker) - balPre;

// 6. invariant: attacker received more than pro-rata share of funded underlyings.
assertGt(got, (amountOld + amountNew) * lossPrice / 1e18,
    'older receipt escaped the loss haircut');

// 7. subsequent honest claimants revert/are underpaid because the contract
//    balance was drained beyond the funded amount.
```

The extra payout equals `amountOld * (1 - lossPrice)`, taken from underlyings that belong to other pending claimants — a direct, quantified theft reproducible purely through unprivileged lender transactions.
