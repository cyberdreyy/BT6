### Title
A single dust withdraw request made while APR is 0 permanently vetoes any non-zero-APR epoch, blocking `stopEpoch` and freezing all lender funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
An unprivileged KYC'd lender can poison the shared `apr0TotalPrincipal` bucket with a dust `requestWithdraw` while `unscaledApr == 0`. On the next `stopEpoch`, `prepareStopEpochWithApr0` unconditionally reverts with `NotAllowed` whenever `unscaledApr != 0`, so the epoch can never be closed under any non-zero APR. Analogous to the Teller `commitCollateral(0)` bug, a trivial attacker transaction flips protocol state into a configuration where the settlement path always reverts.

### Finding Description
`IdleCreditVault.requestWithdraw` routes requests into the APR0 bucket whenever `unscaledApr == 0` and the pool is not closed, increasing `apr0TotalPrincipal` [1](#0-0)  and per-user `apr0Users[_user].principal` [2](#0-1) .

At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which reverts if any APR0 principal is outstanding while `unscaledApr != 0`: [3](#0-2) 

There is no escape hatch for the attacker-created bucket:
- `apr0TotalPrincipal` is only cleared inside `prepareStopEpochWithApr0` itself (line 540) — i.e., only on a successful `stopEpoch`.
- A user's open `principal` can only move to `settledPrincipal` via `_settleApr0`, which requires `principalEpoch < epochNumber` — i.e., after a `stopEpoch` that bumps `epochNumber` [4](#0-3) . Claims therefore cannot drain the bucket before the epoch ends.

So the attack sequence is:

1. Epoch ends; during the buffer the pool's `unscaledApr` is 0 (either because the manager set 0 APR, or in a configuration where the borrower rate is 0 between borrow cycles).
2. Attacker (KYC'd lender) deposits a dust amount and calls `IdleCDOEpochVariant.requestWithdraw(1 wei, tranche)`. This mints the attacker a receipt and sets `apr0TotalPrincipal = 1 wei` [5](#0-4) .
3. The honest manager starts the next epoch with any non-zero APR via `setAprsWithBuffer` [6](#0-5) .
4. At epoch end, the honest manager/owner calls `stopEpoch` → `prepareStopEpochWithApr0` sees `apr0TotalPrincipal != 0` and `unscaledApr != 0` → `revert NotAllowed()`.
5. `epochNumber` never increments, so the attacker's `apr0Users` entry can never settle, and no one else can remove it either. The revert is permanent for as long as APR stays non-zero; the only recovery is to run the entire epoch at `unscaledApr == 0` — i.e., zero yield for all lenders — or default/close the pool.

### Impact Explanation
- **Temporary freezing of all lender funds**: every `stopEpoch` reverts, so pending withdraw requests can never be funded and the pool cannot progress epochs while APR is non-zero. Direct fund impact: the entire vault NAV plus accrued interest is locked behind the reverted settlement path.
- **Yield theft / forced zero-APR**: the only way to regain liveness is for the manager to run epochs at `unscaledApr == 0`, denying all lenders interest for as long as the attacker maintains the bucket — and the attacker can re-request a dust APR0 withdraw each epoch for ~0 cost.

### Likelihood Explanation
- Cost to the attacker is one dust deposit + one `requestWithdraw` (the receipt principal is returned on eventual claim, so net cost is gas only).
- Requires a window where `unscaledApr == 0` and withdraw requests are accepted (buffer period / between epochs). This is a normal supported mode — the APR0 accounting exists precisely for that case — so the precondition is realistic, not exotic.
- The guard at line 506-508 appears designed under the assumption that "APR0 principal is only valid while APR is 0", but nothing prevents an unprivileged user from creating APR0 principal right before the APR changes. The honest manager cannot prevent or clear the bucket.

One caveat I could not fully verify with remaining tooling: the exact `stopEpoch`/`requestWithdraw` call sites in `IdleCDOEpochVariant.sol` (whether `requestWithdraw` is reachable at dust amounts during the buffer and whether `prepareStopEpochWithApr0` is invoked unconditionally in `stopEpoch`). The grep confirms `prepareStopEpochWithApr0` is called from `IdleCDOEpochVariant`, and `requestWithdraw` in the vault has no minimum amount.

### Recommendation
Do not revert on stale APR0 principal; instead force-settle the outstanding bucket at the current epoch's realized rate. Concretely, in `prepareStopEpochWithApr0`, when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, settle the bucket with `apr0RateByEpoch[epochNumber] = 0` (or at the new realized rate pro-rata) and clear `apr0TotalPrincipal`, rather than reverting. Alternatively, reject new `requestWithdraw` calls during the buffer while `unscaledApr == 0` if the next epoch's APR will be non-zero, or let the manager sweep `apr0TotalPrincipal` at `startEpoch` when the APR changes.

### Proof of Concept
Foundry fork test sketch (setup mirrors `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testDustApr0RequestBlocksNonZeroAprStopEpoch() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    address attacker = makeAddr('attacker');

    // Force a zero-APR configuration for the current epoch
    vm.prank(manager);
    creditVault.setAprsWithBuffer(0, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());

    // Attacker deposits dust and requests a dust withdraw while unscaledApr == 0
    _depositWithUser(attacker, 10);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    assertEq(creditVault.apr0TotalPrincipal(), 1, 'apr0 bucket poisoned');

    // Honest manager starts the next epoch with a normal non-zero APR
    vm.prank(manager);
    creditVault.setAprsWithBuffer(initialProvidedApr, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());
    _startEpochAndCheckPrices(0);

    // Fund borrower so stopEpoch would otherwise succeed
    uint256 funds = _expectedFundsEndEpoch();
    deal(defaultUnderlying, creditVault.borrower(), funds);
    vm.prank(creditVault.borrower());
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), funds);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0); // reverts in prepareStopEpochWithApr0

    // No one can clear the bucket: epochNumber never bumps, so _settleApr0 no-ops
    vm.prank(attacker);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
}
```

```text
  function _settleApr0(address _user) internal {
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 _principal = _apr0User.principal;
    if (_principal == 0) {
      return;
    }
    uint256 _reqEpoch = _apr0User.principalEpoch;
    // Settle only after stopEpoch bumped epochNumber (ie after one full wait epoch).
    if (_reqEpoch >= epochNumber) {
      return;
    }
    // Move principal from "open APR0 bucket" to "settled bucket" (same principal, not duplicated).
    _apr0User.settledPrincipal += _principal;
    uint256 _rate = apr0RateByEpoch[_reqEpoch];
    if (_rate != 0) {
      // Convert per-epoch rate to claimable underlying interest.
      _apr0User.settledInterest += (_principal * _rate) / 1e18;
    }
    _apr0User.principal = 0;
    _apr0User.principalEpoch = 0;
```

```text
  function _requestWithdrawApr0(uint256 _amount, address _user) internal {
    // Settle any previous APR0 request first, then start/update current epoch bucket.
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    if (_apr0User.principal == 0) {
      _apr0User.principalEpoch = epochNumber;
    }
    _apr0User.principal += _amount;
    // Epoch-level APR0 principal used only to compute stopEpoch APR0 pro-rata interest.
    apr0TotalPrincipal += _amount;
  }
```
